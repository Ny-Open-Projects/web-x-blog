本节课完成用户服务的开发工作：先对用户服务进行构建，并编写好它的一些部署脚本。

先回顾用户服务的业务。本项目的核心是一个 IM 即时通讯系统，在关系型数据方面，第一块是用户信息：可以通过名称、手机号等方式查找对应的用户，并完成注册和登录等功能，这些是用户服务最基础的功能。

在开发这些功能之前，需要先构建用户服务，并提前编写好部署脚本。之所以这么做，是因为项目在开发过程中会有大量上传、部署等操作，提前将这一系列脚本编写好，后期就可以专注在项目业务本身上，省去不必要的重复过程。

课程内容围绕三个点展开：先构建好项目，然后编辑好用户服务所需要的部署脚本，例如 Makefile、Dockerfile 等，最后基于编写好的脚本进行部署、发布并运行。

先看项目的构建。文档中对项目服务的结构有相应的描述：项目名为 EasyChat。在项目结构上，apps 作为整个项目的应用层，接下来要开发的一些服务都置于 apps 下统一管理。例如当前的用户服务，在用户服务中会有对应的 API 和 RPC，以及一些其他相关的内容，这些都在用户服务目录下，并且都是为用户服务而展开的。

接下来除了用户服务以外，还会有 IM 服务、社交服务等。项目下还会有一个 deploy 目录，用于存放项目过程中会用到的部署相关文件，例如脚本、Dockerfile 以及 Makefile 等。pkg 则是应用于整个 apps 应用层的一些工具包，由自己编写。剩下的是 docker-compose 和 Makefile，Makefile 会作为整个项目启动的脚本文件。

归纳一下这些目录：apps 上会有对应的服务，比如当前定义的用户服务，用户服务中还有 API 和 RPC；deploy 用于存放整个项目部署所需要的一些事项；pkg 作为整个项目所需要的一些工具包；再加上 docker-compose 以及 Makefile，Makefile 会作为项目的一些部署脚本，把相关的部署事项写在里面。

在 deploy 中再定义两个目录：一个是 dockerfile，后期复用的 Dockerfile 都会放到这个目录中；再定义 makefile，用于存放 Makefile 所需要的一些文件；再定义一个 shell，用于存放项目中会复用的一些脚本。这样项目结构就准备好了。

接下来完成用户服务脚本的编写。编写前需要先做一件事，就是把用户服务构建起来，用户服务没有构建起来，就无法编写脚本并测试。

进到当前的项目结构中，先执行 go mod init 进行初始化，让构建的用户服务统一使用当前这个路径。初始化完之后，开始编写用户服务的内容。

首先编写的是 user.proto 文件，它已提前编写好，直接复制过来。在这个文件中定义了整个用户服务需要用到的消息结构体和服务：上面定义了整个用户服务的模型，其下是请求和响应的消息结构体对象，最后定义的是用户服务，并提供了五个方法，包括 ping、登录、注册、获取用户信息以及查找用户。

定义完之后，根据 user.proto 文件构建用户服务，命令在下面，复制过来执行即可。这里有一个细节需要注意：项目开发过程中，会有很多情况需要修改消息结构体的字段属性，以及给服务增加方法，同样的命令可能会执行多次。所以可以在上层定义一个文件，用来存放项目过程中会用到的命令，便于查找，提高开发效率。

当前这个命令需要在 rpc 这个目录下执行，这里将它调整为从根目录执行。很多时候项目操作多数是从根目录进入的，为了提高效率，可以让命令从根目录开始写，再将整个命令复制下来执行。执行完毕没有报错，服务就构建成功了。

然后加载刚刚构建的服务所依赖的包，再进到 logic 中，找到 ping 方法，在 ping 方法中打印一个信息。如果访问 ping 方法能够访问到，就说明用户服务访问正常了。到此，整个服务的基础构建完成。

完成之后，接下来编写脚本。脚本有两个：一个是 Makefile，另一个是 Dockerfile。Makefile 的目的是用来构建容器，Dockerfile 则用于对镜像进行编译，所以这两者并不冲突。

先写 Dockerfile。以之前构建的用户服务为例，在用户服务中会有一个 Dockerfile，其中首先会引入根镜像，然后定义一个目录，用于存放整个程序及配置文件，再把编译好的二进制文件及配置文件复制到容器中，给对应的程序提供运行入口，最后执行入口命令。user-rpc 当前的 Dockerfile 也是这个流程，内容比较多，已提前写好，直接复制过来。

具体来看内容：文件中会引用同一个根镜像；有一段用于设置容器启动时的时区，因为容器如果不设置时区，可能会有误差，这个误差会影响项目的结果，所以时区一定要设置好。时区设置完之后，在底下通过 ARG 这个关键词声明一个属性变量。声明之后的属性变量只会在 Dockerfile 构建时用到，Dockerfile 执行完它就失效了，因为它定义的属性只在 Dockerfile 中生效；而 ENV 定义的变量则会在构建好的容器中生效。ENV 与 ARG 的作用都是定义一个变量，区别是一个作用于容器，一个作用于 Dockerfile。

之所以定义这两个属性值，可以对照之前的 Dockerfile：整体流程并不复杂，但在之后的复用中，服务名会发生改变，服务类型也会发生改变，实际流程中主要变的就是服务名和服务类型，整体执行流程不变。所以定义了两个变量参数，用来代替服务名和服务类型，这样之后再复制的时候只需要改这些地方就可以了，非常轻松。

这里有个小细节注意：默认复制的时候对应的是 etc 目录下的相关路径，所以使用命令的时候可以把这里的路径也指定好。到此，一个 Dockerfile 就准备好了：

```dockerfile
        FROM alpine:3.18
        # 添加时区
        RUN echo -e 「Asia/Shanghai」 > /etc/localtime && \
            echo 「Asia/Shanghai」 > /etc/timezone
        # 设置工作目录
        WORKDIR /$SERVER_NAME
        # 复制配置文件和二进制文件
        COPY ./$SERVER_NAME-$SERVER_TYPE /$SERVER_NAME/bin/
        # 设置启动命令
        ENTRYPOINT [「sh」, 「-c」, 「echo $SERVER_NAME」]
        ```

准备好 Dockerfile 之后，接下来完成 Makefile 的编写。Makefile 只是构建容器，要构建容器还需要依托 Dockerfile 文件。每一次构建容器都手动执行是不合理的：首先要编译好一个二进制可执行文件，执行完之后再根据 Dockerfile 构建镜像，然后设置好标签，再推送到阿里云，总共四个过程。所以把这四个过程通过 Makefile 来解决。

```mermaid
flowchart LR
    A[「编译二进制可执行文件」] --> B[「构建镜像」]
    B --> C[「设置标签」]
    C --> D[「推送到阿里云」]
```

在这里定义一个 Makefile，当前定义的是 user-rpc 下面的 .mk 文件。Makefile 和 Shell 脚本类似，可以执行应用程序的命令。user-rpc 的 .mk 文件也提前写好了，复制过来，内容并不复杂。

从上至下都是定义会用到的文件属性：第一是版本，第二是服务名和服务类型，这个很容易理解。然后是 Docker 会用到的仓库，这里需要改一下，因为使用的是当前命名空间。接下来会用到的服务容器的仓库名，对应这里的仓库名，所以这里也要改一改，把 tst 改为 dev，其他的不用改。接着定义的是编译后的二进制文件的名称，以及在测试环境下面具体依赖于哪一个 Dockerfile 去编译，这里是找到 Dockerfile 去进行编译，这一点要改一下。

属性定义完之后，最重要的还是下面的执行过程。在这个过程中，首先完成对程序的编译，把它变成一个二进制的可执行文件；编译完之后，通过 Dockerfile 去构建镜像文件；再去设置好标签，推送到阿里云服务器上面去。整体来说就是前面写到的四个过程，没有其他变化。使用时只需要更改服务名和服务类型就可以了。值得注意的是，仓库中不用 tst 而是用 dev，这也是一个需要注意的地方，其他没有什么改变。

对应的 .mk 文件内容如下：

```bash
        # 定义服务名和类型
        SERVER_NAME=user
        SERVER_TYPE=rpc
        # 构建命令
        GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o bin/$(SERVER_NAME)$(SERVER_TYPE).go
        # 运行命令
        docker run -d --name $(SERVER_NAME) -p 8080:8080 $(SERVER_NAME):$(VERSION)
        ```

在外层的 Makefile 中，就是引用刚刚定义的这些内容，即 user-rpc-dev，通过 include make 方式来引用要执行的 Makefile 文件地址，让 user 找到 user-rpc 下的 .mk 文件进行执行，执行这个 Makefile 中的 list.tst 指令，因为这一条指令就是下面的这一条指令，执行完之后它会把前面所有的指令都依次执行。

在外层的 Makefile 中也定义一个 list.tst，用它来执行整个所依赖需要的 Makefile。到此就准备好了，把这些内容都同步到自己的机器上，然后去编辑构建好脚本。
