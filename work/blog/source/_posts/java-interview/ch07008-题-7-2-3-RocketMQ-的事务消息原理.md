### 题 7.2.3：RocketMQ 的事务消息原理？

**【参考回答（可背）】**
解决"本地事务与发消息的原子性"：
1. 生产者发**半消息**（half message，对消费者不可见），broker 持久化；
2. 执行本地事务；
3. 根据结果提交/回滚半消息（commit → 消息可见；rollback → 删除）；
4. 若 broker 长时间没收到二次确认 → **回查**：回调生产者的 checkLocalTransaction（查本地事务状态表/流水）决定提交或回滚。
本质：**2PC + 事务状态回查**，把"先发消息还是先落库"的两难用最终一致化解。

**【追问链】**
1. 和本地消息表方案的取舍？→ 本地消息表：业务库一张表 + 定时扫表投递，实现简单、强依赖业务库；事务消息：MQ 侧封装、代码侵入小，但依赖 broker 回查实现质量。团队有基建选事务消息，快速落地选消息表。
2. 消费端失败怎么办？→ 重试队列（16 次梯度退避）→ 死信队列（DLQ）→ 人工/自动处理 + 告警。

**【P10 加分项】**
指出事务消息边界：只保证"本地事务 + 消息到达"原子，**不保证消费成功**——下游失败要靠重试+死信+人工兜底，整条链路是 SAGA 思想。能画出完整时序图（生产者/broker/消费者三泳道）的候选人在此题直接封顶。
