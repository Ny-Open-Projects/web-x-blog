### 题 7.3.1：顺序消息怎么实现？乱序会出什么问题？

**【参考回答（可背）】**
需求场景：同一订单的 创建→支付→发货 必须按序。
Kafka 方案：同 key（订单号）→ 同分区 → 分区内顺序 → **单分区内消费还要单线程**（多线程消费破坏顺序，要按 key 二次哈希到内存队列再串行）。
RocketMQ：MessageQueueSelector 自定义选队列 + 顺序消费模式（MessageListenerOrderly，队列级锁）。
乱序的典型事故：先收到"支付成功"后收到"订单创建"（重试导致），状态机直接拒绝乱序消息 + 告警——**状态机是顺序的最后防线**。

**【追问链】**
1. 顺序与吞吐的矛盾？→ 分区数决定并行度，key 分布倾斜会造成热分区；热点订单拆子序号或接受局部无序+状态机兜底。
2. 全局顺序值得吗？→ 几乎不值得（单分区 = 单点+低吞吐），业务上几乎总能找到 key 维度。

**【P10 加分项】**
"顺序性成本清单"：热分区风险、消费并行度锁死、失败重试会阻塞后续（顺序消费模式下重试是卡队列的）——所以**默认不追求顺序，用幂等+状态机把乱序变成可重放**，这是反直觉但正确的工程判断。
