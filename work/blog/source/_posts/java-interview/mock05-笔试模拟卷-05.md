## 参考答案与解析（自测后再看）

**1.1**（来源 redis）
**答案：A**
**解析：** Lua 脚本复制默认复制"脚本的执行效果"（7.0 起改为复制写命令效果，effect replication）。原因：Redis 7 前复制脚本本身（从库需载入相同脚本），7.0 起 effects 复制（从库执行等效写命令，免脚本传播问题），涉及脚本复制的版本兼容知识。

**1.2**（来源 mongodb）
**答案：A**
**解析：** 读偏好：primary（默认）/primaryPreferred/secondary/secondaryPreferred/nearest。原因：secondary 分摊读压力但读旧数据（复制延迟），nearest 就近读（跨机房），与 write concern 组合构成一致性与延迟矩阵。

**1.3**（来源 mq）
**答案：B**
**解析：** 顺序与幂等的组合矩阵：不要求顺序→幂等即可；同实体有序→分区键+幂等；强顺序→单分区+单消费者+幂等。原因：每档性能递减，业务先证"是否真需要强顺序"（多数只需同实体），幂等是所有档位的公共底线，选型矩阵化回答是 P10 风格。

**1.4**（来源 distributed）
**答案：A**
**解析：** 故障度量四件套：MTTD（发现时长）/MTTA（响应时长）/MTTR（恢复时长）/MTBF（间隔）。原因：MTTD 靠监控覆盖（未发现的故障最贵），MTTA 靠 oncall 机制，MTTR 靠预案与自动化，只看 MTTR 会掩盖发现慢的问题。

**1.5**（来源 ai）
**答案：D**
**解析：** 蒸馏：用大模型生成/标注数据训练小模型，能力近似成本大降。原因：大模型当教师（生成问答对/标注）小模型当学生，部署成本低延迟低，是"能力下放"的主流路径（与量化/LoRA 组合）。

**1.6**（来源 algorithm）
**答案：A**
**解析：** 最长公共子序列（LCS）：dp[i][j] 依赖左/上/左上，编辑距离是其变形（增删改代价）。原因：字符串相似度/版本 diff 的算法基础，空间优化两行滚动，输出具体序列需回溯路径，与 Git diff 思想关联。

**1.7**（来源 java-ai）
**答案：D**
**解析：** 编排状态持久化选型：自研落库（JA-255）vs 工作流引擎（Temporal/Camunda），长任务高可靠用引擎。原因：工作流引擎送重试/超时/补偿/可视化，代价是引入重件，任务时长与可靠性需求决定（AI-021 权衡）。

**1.8**（来源 agent-dev）
**答案：D**
**解析：** 终止条件组合器实现：多条件（完成/步数/预算/取消）的组合判断（任一触发），条件可扩展注册（新终止条件插入）。原因：终止条件的组合器模式（条件策略化），扩展性让新终止条件（如时间窗）可插入，与策略模式联动。

**1.9**（来源 java-basics）
**答案：C**
**解析：** 擦除后签名相同的两个泛型重载方法无法编译，如 f(List<String>) 与 f(List<Integer>)。原因：擦除后两者参数类型都是 List，字节码签名相同。

**1.10**（来源 concurrency）
**答案：B**
**解析：** JIT 逃逸分析可做锁消除与锁粗化。原因：对象不逃逸时其上的同步被整体删除（StringBuffer 局部使用场景），循环内反复加锁会被合并为一次，都是无感知的性能优化。

**1.11**（来源 jvm）
**答案：B**
**解析：** Arthas thread -b 一条命令找出阻塞其他线程最多的线程。原因：线上免重启 attach，thread 查看栈、watch 观测入参返回值、trace 统计方法耗时链路，是本项目沙盒实测过的工具链。

**1.12**（来源 spring）
**答案：D**
**解析：** ApplicationContext 是 BeanFactory 的超集增强版。原因：BeanFactory 基础容器懒加载，ApplicationContext 增加事件、国际化、资源加载、注解支持且默认预初始化 singleton。

**1.13**（来源 mysql）
**答案：A**
**解析：** 扩容方案：翻倍扩容（成倍迁移路由简单）或一致性哈希（数据迁移少）。原因：翻倍扩容按位翻番，旧分片数据一半迁新片，停写窗口小；一致性哈希只迁移 1/n 数据但节点波动影响大。

**1.14**（来源 redis）
**答案：D**
**解析：** Redis 复习主线：数据结构与编码→持久化→主从/哨兵/Cluster→缓存三大问题→分布式锁→场景设计。原因：按面试频率排序，缓存一致性与分布式锁是 P7 分水岭，Cluster 细节是 P8+ 深度，场景设计（秒杀/排行榜/延迟队列）是 P9-P10 综合题。

**1.15**（来源 mongodb）
**答案：C**
**解析：** 写关注 w:1 主确认即返回可能丢写，w:majority 多数派确认不丢。原因：w:1 快（不等从库）、majority 慢但多数派持久，是性能与持久性的旋钮，j:true 额外等 journal 落盘。

**2.1**（来源 mq）
**答案：C**
**解析：** 正确表述应为——本地消息表：业务与消息记录同库事务，异步任务扫描投递+重试+对账。原因：不依赖 MQ 事务消息（跨 MQ 兼容），消息表状态机（待发送/已发送/失败），与 RocketMQ 半消息对比：多一张表少一次回查实现。

**2.2**（来源 distributed）
**答案：D**
**解析：** 正确表述应为——2PC（两阶段提交）：投票（prepare）+执行（commit），协调者单点且阻塞。原因：prepare 后参与者锁定资源等待协调者指令，协调者宕机参与者阻塞（3PC 加超时缓解但仍有问题），XA 是数据库层实现。

**2.3**（来源 ai）
**答案：B**
**解析：** 正确表述应为——RAG vs 微调决策矩阵：知识频繁更新/需溯源→RAG；风格/格式/领域语言内化→微调；常组合（微调调风格+RAG 供知识）。原因：微调改"行为"不改"知识"（新知识微调易过拟合且更新贵），RAG 改知识不改行为，本项目总结的决策矩阵。

**2.4**（来源 algorithm）
**答案：D**
**解析：** 正确表述应为——二分查找：有序+边界处理（左闭右闭/左闭右开两模板选一坚持）。原因：死循环根源：边界收缩条件错误（mid±1 缺失），mid=(left+right)>>>1 防 int 溢出（Java 特有考点），与旋转数组/求边界变形。

**2.5**（来源 java-ai）
**答案：D**
**解析：** 正确表述应为——向量库维度必须与嵌入模型输出维度一致：换嵌入模型等于全量重嵌入加重建索引。原因：维度不匹配写入与检索直接失败，换模型成本是全量重算（AI-067 时效联动），选型期锁定嵌入模型。

**3.1**（来源 agent-dev）
**答案：对。** 解析：推理与行动交替让模型"边做边想"，观察结果反馈下一轮推理，是最易实现与调试的 Agent 模式

**3.2**（来源 java-basics）
**答案：错。** 正确表述：finally 块在 try/catch 之后必然执行（除非 JVM 退出或线程死亡），且其中的 return 会覆盖 try/catch 的返回值与异常。原因：编译器把 finally 代码内联到所有出口路径。

**3.3**（来源 concurrency）
**答案：错。** 正确表述：线程优先级只是提示不可作为正确性工具。原因：优先级映射到 OS 线程优先级但 JVM 不保证严格生效，跨平台行为不一致，正确性永远靠同步原语

**3.4**（来源 jvm）
**答案：错。** 正确表述：unable to create native thread 根因：线程数撞系统限制或内存不足创建栈失败。原因：排查：线程总数（jcmd Thread.print 统计）、ulimit -u、可用内存；解法：虚拟线程改造或线程池治理

**3.5**（来源 spring）
**答案：错。** 正确表述：全链路追踪：Micrometer Tracing/OpenTelemetry 生成 traceId 跨服务传递。原因：通过 HTTP header（W3C traceparent）与 MQ 属性传递，日志 MDC 打 traceId 串起单请求全部日志

**3.6**（来源 mysql）
**答案：错。** 正确表述：ACID 实现：redo log 保持久性、undo log 保原子性（回滚）、锁+MVCC 保隔离性、三者共同保一致性。原因：一致性是目的其他三者是手段，这个映射是事务八股的骨架

**3.7**（来源 redis）
**答案：错。** 正确表述：Redis 主从延迟排查：从库 master_repl_offset 与主库差值、网络、从库负载。原因：延迟大的从库应摘除读流量，replica-lag-flush... 告警阈值按业务容忍设，延迟期间读写分离读到旧数据

**3.8**（来源 mongodb）
**答案：错。** 正确表述：range 分片（范围查询友好）vs hashed 分片（写均匀、范围查询废）。原因：range 支持范围扫描但单调写倾斜，hashed 写分散但点查与范围查询代价不同，按读写模式选

**3.9**（来源 mq）
