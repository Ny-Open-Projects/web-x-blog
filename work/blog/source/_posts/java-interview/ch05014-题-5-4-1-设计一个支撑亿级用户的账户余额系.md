### 题 5.4.1：设计一个支撑亿级用户的账户余额系统（资金安全 + 高并发扣减）

**【参考回答（框架可背：建模 → 一致性 → 并发 → 对账）】**
1. **建模**：账户表 = 余额 + 版本号 + 流水表分离；余额更新只增不减可通过"记账"实现（每笔交易双向流水），支持审计。
2. **并发扣减三方案**：
   - 乐观锁：`update account set balance=balance-100 where id=? and balance>=100`（条件更新防超扣，一行 SQL 原子，**默认方案**）；
   - 悲观锁 select for update（短事务下可用）；
   - 热点账户：**余额分桶**（拆 100 份轮询）或记账缓冲（先记流水异步合并，T+1 落余额，展示用预估）。
3. **一致性**：扣减 + 流水同库同事务；跨账户转账 = 两笔流水的最终一致（消息表/SAGA + 冲正），避免跨库 2PC。
4. **资金安全三道闸（必背）**：
   - 事前：幂等（请求号唯一索引，防重复扣）、限额风控；
   - 事中：条件更新防负余额、隔离级别 RC 降低锁冲突；
   - 事后：**对账系统**——准实时（流式对账延迟告警）+ T+1 全量对账，差异工单自动冲正。
5. **扩展性**：按 user_id 分库分表；平台大商户热点单独通道；审计流水分库按时间归档。

**【追问链】**
1. 余额要展示精确值，缓冲记账怎么保证？→ 展示层读"已落库余额 + 未合并流水增量"，用户视角强一致，底层异步合并。
2. 为什么不用分布式锁？→ 锁是串行化手段，吞吐低且有锁服务故障风险；数据库行锁 + 条件更新在单行内已是原子，分布式锁只适合跨资源协调。

**【P10 加分项】**
资金系统黑话四件套（能说出即有实战）：**对账（reconciliation）、冲正（reversal）、幂等、日切**；再补一句架构观："资金系统宁可降级不可错账，可用性让步于一致性"——这是和普通业务系统相反的价值观，面试官在听这个。
