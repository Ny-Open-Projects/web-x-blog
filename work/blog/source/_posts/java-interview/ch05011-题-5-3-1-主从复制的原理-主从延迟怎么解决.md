### 题 5.3.1：主从复制的原理？主从延迟怎么解决？

**【参考回答（可背）】**
复制三线程：主库 **binlog dump**（推 binlog）→ 从库 **IO 线程**（写 relay log 中继日志）→ 从库 **SQL 线程**（回放）。
并行复制演进：MySQL 5.6 库级并行 → 5.7 **组提交 LOGICAL_CLOCK**（同一组提交的事务并行回放）→ 8.0 **writeset**（按行冲突检测并行，延迟显著改善）。
保证不丢：半同步复制（semi-sync，至少一个从库确认收到 binlog 才返回客户端成功）；更高：MGR（组复制，Paxos 多数派）。
**主从延迟原因**：从库单线程回放慢（大事务、DDL）、机器差、锁冲突。
**延迟方案（分场景背）**：
1. 写后读强一致：**读主库**（写后 N 秒内读主，会话标记法）；
2. GTID/位置等待：确认 binlog 已回放再读；
3. 业务兜底：关键校验（支付结果页）强制读主；
4. 架构级：读写分离路由中间件（ShardingSphere/ProxySQL）内置延迟感知。

**【追问链】**
1. binlog 三种格式的坑？→ statement 有不确定性函数问题（now()/uuid() 主从不一致）；row 量大但安全（默认）；mixed 自动切换但边界难控。
2. 大表 DDL 怎么做？→ Online DDL 有局限（部分操作仍锁表），大表用 gh-ost/pt-osc（影子表+增量同步+原子切换）；8.0 的 INSTANT ADD COLUMN 是例外。

**【P10 加分项】**
高可用架构对比：MHA（外挂切换）/ MGR（Paxos）/ 云厂商 RDS 三节点企业版；讲"RTO/RPO 权衡 + 故障演练"——数据库高可用是要**演练验证**的，不是架构图画出来的。
