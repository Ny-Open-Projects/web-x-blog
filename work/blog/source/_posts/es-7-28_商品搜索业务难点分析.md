# Go 项目开发: 商品搜索业务难点分析（五个坑 + 解法）

大型电商系统的商品搜索有五个绕不开的难点。这一节逐个拆开，给方案也给代码。

**五个难点**：多系统数据同步 → 高召回 + 个性化排序 → 别搜到下架商品 → 非用户维度数据膨胀的性能 → 索引重建。

一句话概括这次的收获：**ES 只负责召回，剩下的都是业务层的事**。

## 纲要

- 难点一：商品数据来自库存 / 价格 / 促销 / 仓库多系统，单表同步搞不定
- `go-mysql-elasticsearch` 只支持 ES 6 以下，**点对点同步多了会打爆数据库**
- canal 做 binlog → Kafka 管道，但 binlog 默认只留 1 天，要接 Kafka 兜住
- **更简单的做法：入库成功就丢 Kafka**，不用二次查库，还能随意组装多表数据
- 白天走增量，夜间全量重灌保证索引完整；再提供批量索引接口按商品 / 商家 ID 重建
- 难点二：召回率低要 **query 纠错（错字 / 漏字）+ 词库扩展（俗称 / 同义 / 上下位词）+ 热门推荐兜底**
- 一次搜索 = 关键词预处理 → 意图识别 → 召回 → 粗排精排 → 运营规则，**ES 只在召回阶段**
- 难点三：ES 是近实时的，**写入后 1 秒内可能搜不到，且没人查询时 refresh 根本不触发**
- 下架时显式 `refresh=true`，**SDK 的 refresh 只刷当前文档的主分片副本，不是全索引**
- 难点四：商品是**全用户共享的**，没法按用户维度路由，查询要打全部分片
- 难点五：mapping 改不动就重建索引；数据大别用 reindex，走**业务双写迁移**
- 全表扫描的深翻问题：**自增主键游标**（`id > lastID`）或 **ID 列表落 Redis/Mongo 批量取**
- 迁移期：从库取数、低峰期提速、新集群 `refresh_interval = -1`

## 难点全景与系统拓扑

五个难点串起来看，本质是**ES 只负责召回，剩下的都是业务层的事**。一次搜索请求从关键词到结果，要过五道工序，ES 只站在"召回"那一段：

```mermaid
flowchart LR
    A["关键词预处理"] --> B["意图识别"]
    B --> C["召回<br/>ES 只负责这段"]
    C --> D["粗排 / 精排"]
    D --> E["运营规则排序"]
    E --> F["结果"]
```

支撑这套链路的系统组件与数据流向：

```dir
search-backend/
├── mysql/                  商品库（库存/价格/促销/仓库）
├── kafka/                  topic: shop_product
├── productconsumer/        消费变更，写 ES
├── elasticsearch/          召回索引
├── search-service/         检索 + 纠错 / 词库 / 兜底
└── redis/                  主键游标 / ID 列表缓存
```

## 一、难点一：多系统的商品数据怎么同步

电商的结构化商品数据要从**库存、价格、促销、仓库**等多个系统抽取，没法靠一张表同步。三条路：

| 方案 | 优点 | 坑 |
| --- | --- | --- |
| `go-mysql-elasticsearch` | 简单，开箱用 | **只支持 ES 6 以下**；点对点，同步到几种存储就要起几个服务连几个数据库连接 |
| canal（binlog → Kafka） | 解耦、下游灵活、转移 DB 压力 | binlog 默认只存 1 天，太短；canal 要集群 + 注册中心保证高可用，**架构复杂度上来了** |
| **入库成功后直接丢 Kafka** | 不用二次查库，能定制组装多表数据 | 要自己保证消息不丢 |

**推荐第三条**：数据入库成功就直接往 Kafka 写，下游消费端按自己需要组装多表数据。再配两道保险：

- **白天走增量**，**夜间全量重灌**保证索引完整
- 提供**批量索引接口**，按商品 ID / 商家 ID 批量取数重建索引

## 二、难点二：召回率低 + 要个性化排序

搜索的使命是"找你所需"——用户已经用关键词表达了意图，理论上切词召回就完事了。但商品搜索不简单，特殊性在这几处：

- **用户不一定能准确表达**：搜"下水道疏通神器"，要能召回"疏通下水道"的功能型商品
- **平台目的是成交**：用户最近老看手机，搜"苹果"就该优先给**苹果手机**，把"水果苹果"降权
- **语言本身复杂**：query 和倒排对不上，就会出现相关性低、召回过少、甚至无结果

针对召回过少，三招连着用：

1. **query 纠错**：一类是错别字，一类是输入过程中丢失的字词
2. **词库扩展**：提前把俗称、别名、同义词、近义词、上位词、下位词建成词库，扩展用户搜索意图
3. **兜底**：用热门商品 / 推荐商品填充，避免无结果页

整个电商搜索体系一次请求大致是：**关键词预处理 → 意图识别 → 召回 → 粗排 / 精排 → 运营规则排序**。意图识别和精排要靠离线分析和 AI，ES 只负责召回这一段。

```go
package main

import "fmt"

// ============ 词库：扩展用户 query 的召回面 ============

// synonymDict：俗称 / 别名 / 同义 / 近义 / 上位词 / 下位词 都往里塞
var synonymDict = map[string][]string{
	"苹果":      {"iphone", "手机", "水果"},
	"下水道疏通神器": {"管道疏通", "疏通剂", "洁厕灵"},
	"电脑":      {"笔记本", "手提电脑", "pc"},
}

// typoDict：常见错别字 → 正确词
var typoDict = map[string]string{
	"香焦": "香蕉",
	"苹国": "苹果",
	"手机枢": "手机壳",
}

// expandQuery：先纠错再扩展，返回扩展词列表
func expandQuery(query string) []string {
	if correct, ok := typoDict[query]; ok {
		query = correct
	}

	expanded := make([]string, 0, 4)
	expanded = append(expanded, query)
	for _, syn := range synonymDict[query] {
		expanded = append(expanded, syn)
	}
	return expanded
}

// 兜底：真没结果时用热门商品顶上
func hotFallback() []int64 {
	return []int64{1001, 1002, 1003}
}

func main() {
	query := "香橙" // 错别字 + 近义，两条路都该救回来
	expanded := expandQuery(query)
	fmt.Println("expanded:", expanded)

	// 召回太少时再补一层同义词
	extra := expandQuery("苹果")
	fmt.Println("extra:", extra)
	fmt.Println("fallback:", hotFallback())
}
```
## 三、难点三：别让下架商品被搜到

ES 是**近实时**的：文档先写进 index buffer，**默认 1 秒后 refresh 到操作系统缓存**才可被搜到。注意一个细节——**这一秒内如果没有搜索请求到达，也不会触发 refresh**，所以文档真正可搜的时间可能更长。

好在 SDK 允许显式指定 refresh。要注意区别：

- **REST 的 refresh API**：刷新指定索引的**全部分片**
- **SDK 里带上 refresh**：只刷新**当前这条文档所在的主分片和副本**

下架场景就该用后者，代价小很多：

```go
package main

import (
	"context"
	"fmt"

	"github.com/olivere/elastic/v7"
)

var esClient *elastic.Client

const indexProduct = "shop_product"

// offShelfProduct：下架商品，必须立刻从索引里消失
func offShelfProduct(id int64) error {
	doc := map[string]interface{}{
		"status": "unsale",
	}

	// Refresh("true")：只刷新这条数据所在的主分片和副本，不是整个索引
	if _, err := esClient.Update().
		Index(indexProduct).
		Id(fmt.Sprintf("%d", id)).
		Doc(doc).
		Refresh("true").
		Do(context.Background()); err != nil {
		return err
	}
	fmt.Println("off shelf:", id)
	return nil
}

func main() {
	if err := offShelfProduct(1001); err != nil {
		fmt.Println("off shelf error:", err)
		return
	}
	fmt.Println("商品已从索引中及时隐藏")
}
```
## 四、难点四：非用户维度的数据膨胀

商品数据**不属于用户维度**——状态正常的商品任何用户都能搜。这意味着**没法用用户维度做 routing**，每个查询都要打到全部分片。

缓解思路（后续小节详细展开）：

- 用**业务维度做 routing**（类目、店铺），让查询只落相关分片
- 大促前**扩容 + 预暖**（segment 落盘、page cache 预热）
- 多级缓存挡掉大部分重复查询（页面缓存 / ID 列表缓存 / request cache / query cache）

## 五、难点五：索引重建与全表扫描

业务过程中难免要改 mapping 或更新词库，而**很多 mapping 的改动必须重建索引**，且只对新数据生效。

- **百万级以内**：低峰期用 `reindex` API，简单直接
- **数据量大**：reindex 跑太久会拖到业务高峰，甚至跑不完 → **业务层双写迁移**：增量双写到新集群，同时从库里把存量数据 bulk 写进新集群，存量写完下线旧集群，读写切到新集群，**全程不停机**

从 MySQL 拉全表的环节，最大的坑是**深分页**。两个解法：

```go
package main

import (
	"context"
	"fmt"

	"github.com/olivere/elastic/v7"
)

const (
	indexProductOld = "shop_product"
	indexProductNew = "shop_product_v2"
	scanBatchSize   = 100 // SQL 每页 100 条
	bulkBatchSize   = 1000 // ES bulk 每批 1000 条
)

var esClient *elastic.Client

type rawProduct struct {
	ID    int64   `json:"id"`
	Name  string  `json:"name"`
	Price float64 `json:"price"`
}

// loadProduct：从从库按 ID 取单条（绝不去扫主库）
func loadProduct(id int64) (*rawProduct, error) {
	return &rawProduct{ID: id, Name: fmt.Sprintf("product-%d", id), Price: 99}, nil
}

// scanAllIDs：自增主键游标分页，避免 offset 深翻
// 关键是 where id > lastID order by id limit N，一定要走主键索引
func scanAllIDs(lastID int64) ([]int64, int64, error) {
	ids := make([]int64, 0, scanBatchSize)
	maxID := lastID

	for {
		// 生产环境这里是：SELECT id FROM t_product WHERE id > ? ORDER BY id LIMIT 100
		batch, next := fakeScanFromDB(lastID)
		if len(batch) == 0 {
			break
		}
		ids = append(ids, batch...)
		lastID = next
		if next <= maxID {
			break
		}
		maxID = next
	}
	return ids, maxID, nil
}

// fakeScanFromDB：模拟数据库按主键游标返回 (本页 ID, 下一页起点)
func fakeScanFromDB(lastID int64) ([]int64, int64) {
	if lastID >= 1000 {
		return nil, lastID
	}
	next := lastID + scanBatchSize
	if next > 1000 {
		next = 1001
	}
	batch := make([]int64, 0, scanBatchSize)
	for id := lastID + 1; id <= next; id++ {
		if id > 1000 {
			break
		}
		batch = append(batch, id)
	}
	return batch, next
}

// rebuildIndex：把一批商品 bulk 写进新索引
func rebuildIndex(ids []int64) error {
	ctx := context.Background()
	bulk := esClient.Bulk().Index(indexProductNew)

	for _, id := range ids {
		doc, err := loadProduct(id)
		if err != nil {
			continue
		}
		bulk.Add(elastic.NewBulkIndexRequest().Id(fmt.Sprintf("%d", id)).Doc(doc))

		if bulk.NumberOfActions() >= bulkBatchSize {
			if _, err := bulk.Do(ctx); err != nil {
				return err
			}
			bulk = esClient.Bulk().Index(indexProductNew)
		}
	}

	if _, err := bulk.Do(ctx); err != nil {
		return err
	}
	fmt.Println("reindex done:", len(ids))
	return nil
}

func main() {
	ids, maxID, err := scanAllIDs(0)
	if err != nil {
		fmt.Println("scan error:", err)
		return
	}
	fmt.Println("scanned ids:", len(ids), "maxID:", maxID)

	if err = rebuildIndex(ids); err != nil {
		fmt.Println("reindex error:", err)
	}
}
```
第二种解法是**在搜索服务里维护商品 ID 列表，持久化到 Mongo / Redis bitmap**，用这些 ID 批量取商品信息，同样绕开深翻。ID 不连续也没关系，主键游标方案天然兼容（有删除、有事务回滚都会产生空洞）。

**迁移期的三条注意**：从**从库**取数减轻主库压力；**业务低峰期**适当提高迁移进度；新集群 **`refresh_interval = -1`** 让写入吞吐更大（等迁移完再调回来）。

## 注意事项

1. **多系统数据同步优先"入库即发 Kafka"**，能省掉 canal 那套的重型组件。
2. **binlog 默认只保留一天**，接 Kafka 就是为了把这个时效兜住。
3. **`go-mysql-elasticsearch` 只支持 ES 6 以下**，上了 7.x 就别考虑了。
4. **点对点同步的存储每多一个就要多一个服务连库**，数据库连接很快成为瓶颈。
5. **白天增量 + 夜间全量重灌**是索引完整性的保底手段。
6. **提供批量索引接口**（按商品 ID / 商家 ID），重推单个商家的数据不用全量重建。
7. **query 纠错要分两类**：错别字、漏字，处理方式不一样。
8. **词库质量决定召回质量**：俗称 / 别名 / 同义 / 近义 / 上下位词，越全召回越好。
9. **一定要有兜底**（热门 / 推荐），否则一搜没结果用户体验直接崩。
10. **ES 近实时的刷新是懒触发的**，没人查的时候可能更慢——对时效敏感的下架场景必须显式 refresh。
11. **SDK 的 refresh 只刷相关主分片副本**，比 REST 全索引刷新便宜得多。
12. **商品没有用户维度**，默认查询就是全分片扇出，要靠业务维度 routing 收敛。
13. **大索引别用 reindex**，老老实实双写迁移。
14. **全表扫描用主键游标**，SQL 里一定要有 `id > lastID` 才能用上主键索引。
15. **迁移期间新集群关掉 refresh**，迁移完记得调回来，否则写入性能白丢一大截。

## 本节作业

1. 把 `scanAllIDs` 换成真 SQL（用 `database/sql` + `WHERE id > ? ORDER BY id LIMIT ?`），并加上 `id` 必须升序的判断，防止游标回退导致漏数据。
2. 给索引重建加断点续跑：把"已写入新索引的 ID"记录到 Redis Set，进程重启后从上次最大 ID 继续，避免重头再扫一遍。
3. 实现方案二的 ID 列表版本：用 Redis bitmap 记录全量商品 ID，写一个按位取出 ID 集合并批量重建索引的函数。

## 总结

商品搜索绕不开五个难点：**多系统数据同步、高召回 + 个性化排序、别搜到下架商品、非用户维度的数据膨胀、索引重建**。这五个问题有一个共同底色——**ES 只负责召回，剩下的都是业务层的事**。

数据同步最省心的做法是"入库成功即发 Kafka"，白天增量、夜间全量重灌，再配批量索引接口兜底；召回率低要靠 query 纠错 + 词库扩展 + 热门兜底三连，但 ES 只在"召回"这一段，意图识别和精排是离线 / AI 的事；近实时刷新是懒触发的，下架这种时效敏感场景必须显式 `refresh=true`（且 SDK 只刷相关分片，比全索引刷新便宜）；商品无用户维度、查询扇出到全分片，要靠业务维度 routing 和多级缓存收敛；mapping 改不动就重建索引，量大走双写迁移而不是 reindex，全表扫描用主键游标绕开深翻。
