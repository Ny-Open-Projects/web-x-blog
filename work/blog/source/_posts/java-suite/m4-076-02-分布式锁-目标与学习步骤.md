# Redis 分布式锁集成运用：资金服务并发扣款防护与账户预警通知开篇

第十八章预警通知的上半场分两条线。第一条线补并发防护：额度调整接口把账户资金动起来之后，同一账户的多笔并发扣款会互相踩踏，用 Spring Integration Redis 给资金服务加上分布式锁，再用 100 笔并发市价单验证加锁与去锁两种结局。第二条线进入用户预警通知：模板由谁设置、条件怎么存、接口怎么校验，最后梳理调度任务生成预警通知记录的流程。

## 先给结论

- 方案选型：Spring Integration 对 Redis 分布式锁做了封装，是轻量级的 EIP（企业集成模式）实现；出自 Spring、抽象设计能力高，可接入 GemFire、基于 JDBC 的数据库、Redis、Zookeeper 等存储组件，替换时只改配置、不改代码。
- 加锁逻辑想清两个问题：粒度控制在账户级别（按账户 ID 加锁，同一时刻每个账户只有一个请求在处理）；拿不到锁先等待，超过 waitTime（5 秒）就抛异常返回。
- 集成三步：公用工程封装 RedisLockService（tryLock 超时抛 WAITING_UNLOCK，unlock 用同一个 Key 释放）；资金服务配置 RedisLockRegistry（Key 取 GlobalConstants.DISTRIBUTE_LOCK_FOR_FINANCE，过期 24 小时）；额度调整接口更新资金前 tryLock、finally 中 unlock。
- 并发验证：10 个模拟客户端各下 10 笔市价单共 100 笔，加锁两次都是 42184500 与预期一致；去掉锁分别是 69935940 与 58372840，线程安全问题实锤。单机模拟大量并发要临时关 SEATA（数据源改回 BizSystemDataSource、注释 @GlobalTransactional 与 XID 绑定），否则事务超时阻塞。
- 预警通知分工：管理员配置止盈止损等模板（支持内置变量）→ APP 用户设置预警条件（股票、预警类型、stopRate 比例、通知方式）→ 交易调度服务生成预警通知记录 → 推送走 APP 推送或阿里云短信邮件的离线推送。
- 生成方案：不监听每口行情报价（用户多、股票多、每秒数口报价，集群压力也巨大），用调度任务每分钟或数秒检测一次，批量加缓存；防骚扰设定 10 分钟内不重复、每天最多 3 次，凌晨三点定时任务重置缓存。

## 分布式锁方案：Spring Integration Redis

Spring Integration 对 Redis 分布式锁做了处理和封装，本质是轻量级的 EIP 实现。它抽象设计能力强，可接入众多存储组件：GemFire 是高性能的分布式内存对象缓存系统，也可以基于 JDBC 的数据库、Redis、Zookeeper；替换组件不改代码，改配置即可。

基本用法以按账户 ID 加锁为例：

```java
// 根据账户 ID 拿到 Lock 对象，传入账户 ID 作为锁的 Key
Lock lock = redisLockRegistry.obtain("accountId");
// 尝试加锁，最多等待 5 秒
boolean isLock = lock.tryLock(5, TimeUnit.SECONDS);
// 处理业务逻辑
// 释放锁
lock.unlock();
```

RedisLockRegistry 内部通过 ConcurrentHashMap 保存锁的信息，tryLock 实质上是在 Redis 里生成对应的锁缓存信息。原子性是锁真正生效的前提，课程给出了正误对照：

```java
// 错误方式：setnx 与 expire 分成两步操作，程序一旦崩溃
// 无法设置过期时间，KEY 一直常驻 Redis，资源无法释放
Long result = jedis.setnx(lockkey, clientId);
if (result == 1) {
    jedis.expire(lockkey, expireTime);
}

// 正确方式：一条命令原子完成加锁与过期设置
String result = jedis.set(lockkey, clientId, "NX", "PX", expireTime);
if ("OK".equals(result)) {
    return true;
}
```

## 资金服务集成：组件封装、锁配置与额度调整加锁

接入前想清楚加锁逻辑：粒度按业务需要定，这里控制在账户级别，按账户 ID 加锁，同一时刻每个账户只有一个请求在处理；拿不到锁先等待，超时就封装异常返回。

分布式锁组件做了进一步封装，代码在公用工程 bulls-stock-common-service 下：RedisLockService 初始化传 RedisLockRegistry（锁的注册管理器）与 waitTime（加锁等待超时时间），提供 tryLock 与 unlock 两个方法：

```java
public boolean tryLock(Object key) throws ComponentException {
    Lock lock = redisLockRegistry.obtain(String.valueOf(key));
    boolean isLock = lock.tryLock(waitTime, TimeUnit.SECONDS);
    if (!isLock) {
        throw new ComponentException(ApplicationErrorCodeEnum.WAITING_UNLOCK);
    }
    return isLock;
}
```

tryLock 超过等待时间拿不到锁就抛异常，成功返回 true；unlock 再通过 RedisLockRegistry 获取 Lock 对象，Key 与 tryLock 保持一致后释放。

资金服务的集成配置在 RedisConfiguration 里完成：定义 RedisLockRegistry，传 RedisConnectionFactory 与注册管理器的 Key（GlobalConstants 里资金服务的 DISTRIBUTE_LOCK_FOR_FINANCE），锁过期 24 小时，加 @Bean 返回；再用它构造 RedisLockService，waitTime 为 5 秒。完成后检查工程的 Redis 连接与缓存配置。

最后把锁加进额度调整接口。gRPC 接口 GrpcStockFinanceService 的 updateAccountBalance（更新账户余额）注入 RedisLockService，只增加两步：

```java
// STEP1：更新账户资金之前，加入分布式锁的控制处理
redisLockService.tryLock(request.getAccountId());
// 更新账户资金
long balance = stockFinanceService.updateBalance(request.getAccountId());
// STEP2：finally 中进行解锁处理
redisLockService.unlock(request.getAccountId());
```

## 并发验证：100 笔市价单的两种结局

测试条件：同一时间开启 10 个客户端，每个客户端下 10 个订单，总共 100 笔。市价下单参数：方向买入、成交价格 5713、成交数量 100 股、股票 ID 为 4、委托类型市价下单。

单笔金额算清楚：5713 × 100 = 571300；佣金 = 571300 × 1.2%（0.012）= 6855.6，去掉小数保留整数 6855；每笔订单总金额 = 571300 + 6855 = 578155，100 笔合计 57815500。账户初始资金一个亿（8 个零），预期结果 = 100000000 − 57815500 = 42184500。

模拟客户端做了并发改造：NettyClientTest 定义 10 个线程，每个线程先调用户登录接口、等待 3 秒，再循环发送 10 次市价下单请求。本机模拟大量并发会造成分布式事务阻塞（`Global transaction[192.168.19.1:8091:2020713605] is timeout and will be rolled back`），这一篇侧重分布式锁运用，先关掉分布式事务：交易服务业务数据源改回 BizSystemDataSource（之前配的是 SEATA 代理数据源）；StockDealService 的 @GlobalTransactional 注解注释；资金服务里全局事务 XID 绑定注释，SEATA 不再生效。

启动交易服务、代理服务、资金服务及 Redis、Nacos 等组件，把 t_trade_account 表的 balance 重置为一个亿。加锁验证：调用完成后可用资金 42184500，与预期一致；资金改回一个亿再跑一次仍是 42184500，分布式锁生效，确保了账户资金操作的数据一致性。

去锁对照：注释掉加锁与解锁处理，重启、重置资金再测，结果 69935940，与预期相差比较大；再验证一次是 58372840，仍有差异。不加锁就无法保证数据一致性，产生线程安全问题；两种场景对照下来，分布式加锁能保障资金服务对资金处理的正确性。

## 账户预警通知开篇：模板、设置接口与生成流程

常见预警通知包含止盈止损通知、股票日内的涨跌幅、变动比例与价格等，课程以最常见且主要的止盈止损通知为例。整体流程：管理员设置预警通知模板，APP 用户设置账户预警条件，交易调度服务按模板与条件生成预警通知记录，最后做推送。推送分两种：常用的 APP 推送和离线方式的推送，离线推送基于阿里云的短信邮件。

**预警通知模板设置接口。** 模板由管理人员配置维护，APP 用户不能设置模板（身份不同、可操作功能不同）；APP 用户设置的是账户预警通知，针对个人，比如设定某只股票的止盈止损价格。模板支持内置变量，调格式不改代码：

```text
尊敬的客户，您所持有的产品${stockCode}，当前价格${stockPrice}元，已达到止损比例${stopProfitRate}，请您及时处理。
```

模板表结构围绕预警类型、通知方式与内容组织：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint(19) | 主键标识 |
| warnType | tinyint(3) | 预警类型（0:止损, 1:止盈） |
| notifyType | varchar(32) | 通知方式（APP:站内信, EMAIL:邮件, SMS:短信） |
| content | varchar(2000) | 模板内容 |
| title | varchar(255) | 消息标题 |
| status | tinyint(3) | 模板状态（0:启用, 1:禁用） |
| lastUpdateBy | bigint(19) | 最后更新人 ID |

占位符支持参数位写法，{0} 代表第一个参数位、从 0 开始；用参数名称也可以，参数位写法能防止参数为空时的空指针异常。数据层用 Spring Data REST 实现三个接口：按预警类型取模板（可能多条，只取一个）、按 ID 取完整对象、保存数据；模板获取加了缓存，保存时同步更新缓存。服务层 saveTemplate：ID 为空即新增，新增时按预警类型校验重复性，一个预警类型一般只有一个模板（止盈、止损各一），重复抛 ACCOUNT_WARN_TEMPLATE_TYPE 异常，再记录最后更新人并保存。Web 层的保存接口 AccountWarnTemplateController 只支持 POST，加 Swagger 注解，把当前登录用户传给 service；不用 Spring Data REST 直接暴露，是它会把增删改查都暴露出去，重要或复杂接口自己控制更合适。

**账户预警通知设置接口。** 设置表字段：账户 ID、股票产品 ID（针对哪只股票设置条件）、stopRate 止盈止损比例（按比例方式设置，按价格方式可扩展字段）、通知方式（站内信、邮件、短信，多个逗号分隔）、操作时间。通知方式可由用户自选，但必须按实际信息：没有手机号不能选短信，没填邮箱不能选邮件。

PB 结构分两层：Netty 对外在 StockMessage 增加 AccountWarnSettingData 响应数据体（属性暂空，将来返回预警通知 ID 可填在这里），请求结构分配序号，ResponseMessage 同步加返回数据包；gRPC 对内定义在用户服务的 stock_user_service.proto，请求与 Netty 基本一致、多带账户 ID，返回只含处理状态与响应消息：

```protobuf
service StockUserService {
    rpc accountWarnSetting (AccountWarnSettingRequest) returns (AccountWarnSettingResponse) {}
}

message AccountWarnSettingRequest {
    int64 accountId = 1;  // 账户ID
    int64 stockId = 2;    // 股票产品ID
    int32 warnType = 3;   // 预警类型 (0: 止损, 1: 止盈)
    double stopRate = 4;  // 止盈止损设置比例 (单位: %)
    string notifyType = 5; // 通知方式(APP:站内信, EMAIL:邮件, SMS:短信, 多个以逗号分隔)
}

message AccountWarnSettingResponse {
    string status = 1;
    string message = 2;
}
```

stopRate 单位是百分号，设定值 2.28 代表 2.28%。右键 Open In Terminal 跑 PB 脚本，先生成 gRPC 的 Java 代码，再生成 Netty 的传输数据结构代码。接口实现放在交易服务工程的用户服务 gRPC 接口 GrpcStockUserService：accountWarnSetting 注释为保存用户设置的预警信息，抛出 ComponentException；service 包下新建 user 子包，定义服务层接口 ITradeUserService 与实现类 TradeUserServiceImpl（@Service、@Autowired 注入），业务在服务层完成。

服务层 saveAccountWarnSetting 的整体流程六步：

1. 根据账户 ID 获取交易账号对象（getById），没找到就抛业务异常：没有找到有效的账号；
2. checkNotifyType 校验通知类型：参数为空直接抛异常；支持多类型（逗号分割），逐个校验是否属于系统支持的 APP、EMAIL、SMS 三种；
3. checkReceiveInfo 检查接收设置方式是否支持：短信通知检查是否设置了手机号，邮件通知检查是否设定了邮箱，APP 站内信不需要校验；
4. checkWarnType 校验预警记录类型：系统只支持止盈、止损（GlobalConstants 的 ACCOUNT_WARN_TYPE_STOP_PROFIT 与 ACCOUNT_WARN_TYPE_STOP_LOSS），超出抛 WARN_TYPE_ERROR；
5. 按账户 ID 与股票产品 ID 查询预警设置（getByAccountAndStock，避免重复记录），存在则更新：只更新 updateTime、notifyType、warnType、stopRate，账户 ID、股票 ID、创建时间不动；不存在则新增；
6. loadAccountWarnSettingCache 加载预警信息到缓存：频繁查库很耗性能，预警设置组装为 BO（冗余用户、股票产品信息，便于后续加工）放入缓存，key 为 ACCOUNT_WARN_SETTING_STOCK 拼接股票产品 ID，以交易账户 ID 关联（每个交易账户的预警设置唯一）。

**防骚扰与缓存重置。** 行情一天内反复变化，价格不断涨跌，可能多次符合预警条件，用户频繁接收不友好。设定 10 分钟之内不重复接收相同的预警信息，一天之内最多发送 3 次；实现上在 AccountWarnSettingBo 里增加上次预警记录时间与预警通知次数两个属性。第二天要能重新接收，靠定时任务重置缓存：服务重启（@PostConstruct）或每天凌晨三点（cron = "0 0 3 ? * *"，开盘之前、休市之后，避开交易时间）执行，查所有预警设置并遍历，查找对应交易账户后重新加载缓存；缓存是覆盖更新，新建 BO 的两个记录都归零，相当于把用户预警设置的缓存记录重置。

**生成流程梳理。** 实时性与性能要兼顾：预警通知需要较高实时性，但能容许一定延迟，不像下单必须尽快处理。不能监听每口行情报价触发预警：平台用户有几十万、上百万、上千万，股票市场有几千只股票，每秒行情还能接收数口报价，即便集群压力也非常巨大，数据成倍增长、非常消耗服务器资源。所以采用调度任务：每分钟或数秒（如 30 秒、10 秒）检测一次，相比监听每口报价极大减少信息处理量，再批量处理并结合缓存，性能与实时性兼顾。

预警通知记录表围绕发送组织：用户信息（用户 ID、账户 ID）、接收者地址（手机存手机号、邮件存邮箱）、notifyType、warnType（止损/止盈）、content 通知内容、发送状态、重试次数、备注（失败记录异常提示）、更新时间。调度任务 GenerateWarnNotifyMessageJob 建在交易调度服务 job 包下的 warning 子包，注释描述为生成账户预警通知记录信息、每分钟执行一次：

```java
@JobHandler(value = "generateWarnNotifyMessageJob")
@Service
@Log4j2
public class GenerateWarnNotifyMessageJob extends IJobHandler {

    @Autowired
    private IAccountWarnSettingService accountWarnSettingService;

    @Override
    public ReturnT<String> execute(String param) throws Exception {
        try {
            // 生成账户预警通知记录
            accountWarnSettingService.generateWarnNotifyMessage();
            return ReturnT.SUCCESS;
        } catch (Exception e) {
            log.error(e.getMessage(), e);
            return ReturnT.FAIL;
        }
    }
}
```

服务层 IAccountWarnSettingService 与实现类 AccountWarnSettingServiceImpl 加 @Service、@Log4j2；generateWarnNotifyMessage() 不需要传参，数据量比较多，要加事务控制、批量提交。整体流程七步：

1. 遍历所有有效股票产品，非有效产品不能交易、不会产生预警通知记录；
2. 根据股票产品 ID 获取行情报价；
3. 遍历对应股票产品下所有账户设置的预警信息；
4. 根据股票产品 ID 获取账户的预警通知设置信息；
5. 做条件判断：是否第一次生成、或上一次预警已超过 10 分钟（10 分钟内再触发不生成），并结合每天最多 3 次的次数判断；
6. 生成预警通知记录信息；
7. 通知次数超过 3 次后当天不再处理生成，将账户的缓存记录移除。

## 小结

上半场两条线是同一主线的两面：资金安全与用户触达。分布式锁部分，Spring Integration Redis 让锁的接入与替换只差一份配置，账户级粒度加 finally 解锁的两步改造，让额度调整接口在 100 笔并发下分毫不差；单机压测临时关闭 SEATA，也提示了实测与生产逻辑的差异。预警通知部分确立了管理员管模板、用户管条件、调度服务管生成的分工：模板带内置变量，设置接口靠校验链保证合法，缓存 BO 加 10 分钟、3 次防骚扰与凌晨三点的缓存重置，为下一讲的记录生成代码打好基础。
