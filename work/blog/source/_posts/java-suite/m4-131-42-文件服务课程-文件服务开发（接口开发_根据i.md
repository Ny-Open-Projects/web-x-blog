# 删除接口双策略实测与按 id 打包下载：从路径斜线坑到 zip 重名处理

按 id 删除附件的代码前一篇已经落地，这一段先把它放到 LOCAL 与 ALI 两种存储策略下各实测一遍——本地策略一次通过，阿里云策略上却暴露出一个 Windows 路径分隔符导致的"删除假成功"bug；随后照接口文档补上第三个删除接口（按业务类型/业务 id 删除），最后开写本章最复杂的接口：根据文件 id 打包下载，单个 id 直接下原文件，多个 id 先压成 zip，还要处理压缩包内的同名文件冲突。

## 先给结论

- 按 id 删除在 LOCAL 策略下实测通过：Nacos 把 pd-file-server.yml 的 type 改成 LOCAL 并发布，重启文件服务后上传的文件落在 endpoint 指定目录的年/月子目录里，DELETE 后数据库记录与磁盘文件同时消失，原 URL 再访问直接 404。
- ALI 策略下删除是"假成功"：接口返回 OK、数据库记录删掉了，但 OSS 上的文件还在、URL 仍能下载——原因是 relativePath 里是反斜线，删除时拼出的 object key 与真实存储的正斜线路径对不上，OSS 根本找不到这个对象。
- 根因与修复：上传时用 Path 取目录分隔符，Windows 下得到 `\`，而日期目录只是 URL/key 的一部分、并不需要在磁盘上创建，改成统一用正斜线拼接后，重新上传删除即恢复正常。
- 按业务删除是按 id 删除的封装：DELETE /attachment/biz 收 AttachmentRemoveDTO（bizId、bizType），先按双条件查库，查到空集合直接 return，非空则 stream 转成 Long[] 复用 remove(ids)——控制台里最终执行的仍是按 id 的 DELETE 语句。
- 打包下载接口 GET /attachment/download 返回 application/octet-stream 二进制流：Controller 无返回值只做转发，Service 查库、判空抛"您下载的文件不存在"、把 Attachment 转成 FileDO，细节全部下沉到独立抽取的 FileBiz。
- FileBiz 三步走：filter 过滤无效文件并 mapToInt 求和得总大小；单文件用原始文件名、多文件用"第一个文件名等.zip"；用 duplicateFile 计数 Map 配合 buildNewFileName 在扩展名前插入"(n)"，解决 zip 内同名覆盖问题。

## 按 id 删除：本地一次通过，阿里云翻车

测试前先在 Nacos 配置中心调整存储策略。配置文件 pd-file-server.yml 的核心结构如下，type 决定走哪种策略，local 与 ali 分别是两种策略各自的参数：

```yaml
docker:
  file:
    type: ALI              # LOCAL ALI MINIO FAST_DFS
    urlPrefix: http://172.37.6.135:8080/   # 本地测试时使用
    local:
      urlPrefix: http://${ip}:${port}
      bucketName: oss-file-service
      endpoint: D:\uploadFiles
    ali:
      endpoint: http://oss-cn-beijing.aliyuncs.com
      accessKeyId: LTAI5t7GdX1234567890
      accessKeySecret: 1234567890abcdef
      bucketName: pinda-file
```

LOCAL 策略的流程：type 改成 local 发布，重启文件服务，清空 pd_attachment 表方便观察。此时上传一个 zip 压缩包（bizId、bizType 都不填），文件会落到 endpoint 指定的本地目录下，并按年/月生成日期子目录；通过 nginx 提供的 HTTP 地址能直接下载到这个文件。接着从数据库复制这条记录的 id，调 DELETE /attachment 删除：响应正常返回，刷新数据库记录已不存在，本地磁盘上的文件也消失了，再用原 URL 访问返回 404。本地策略下的删除链路完整走通。

切到 ALI 策略重测，问题就出来了。同样的"上传 → 确认可下载 → 按 id 删除"，接口返回成功、数据库记录也没了，但那个 URL 依然能下载到文件——阿里云 OSS 上的对象根本没被删掉，删除操作只删了数据库记录。

原因出在相对路径的斜线方向上。上传响应里能看到 relativePath 是 `2020\05` 这种反斜线形式：生成日期目录时用了 Path，在 Windows 系统下目录分隔符就是反斜线；而 URL 地址和 OSS 的 object key 用的都是正斜线。删除时阿里云客户端要拼的是"相对路径 + / + 文件名"：

```java
@Override
public void delete(FileDeleteDO file) {
    OSS client = buildClient();
    // 获得OSS空间名称
    String bucketName = properties.getBucketName();
    // key = 相对路径 + / + 文件名，斜线不一致时 OSS 匹配不到对象
    client.deleteObject(bucketName,
            file.getRelativePath() + StrPool.SLASH + file.getFileName());
}
```

拼出来的是 `2020\05\xxx.zip`，与对象真实的 key `2020/05/xxx.zip` 不匹配，等于按一个不存在的地址去删，自然删不动。

修复思路很直接：这个日期文件夹对 OSS 来说只是 key 的一部分，不会真正在磁盘上创建目录，没必要借助 Path 取系统分隔符，直接按正斜线生成、再兜底替换一遍即可：

```java
String relativePath = LocalDateTime.now()
        .format(DateTimeFormatter.ofPattern(DEFAULT_MONTH_FORMAT_SLASH));
String relativeFileName = relativePath + StrPool.SLASH + fileName;
// 统一成正斜线，避免 Windows 分隔符把 key 拼歪
relativeFileName = StrUtil.replace(relativeFileName, "\\", StrPool.SLASH);
```

重启后重新上传，返回数据里的 relativePath 已经变成正斜线形式；再走一遍删除，数据库记录消失，URL 访问报错找不到文件。基于阿里云的文件删除至此测试通过。这个坑的教训是：本地策略下日期目录真的会落盘，所以要跟随操作系统分隔符；云端策略下它只是 key 的一段字符串，必须固定正斜线——同一个"目录"概念，在两种策略里的语义并不一样。

## 按业务类型/业务 id 删除：查出来转 id，复用旧方法

第三个删除接口的契约如下：

| 项目 | 内容 |
| --- | --- |
| 请求方式 | DELETE |
| 请求路径 | /attachment/biz |
| 请求体 | AttachmentRemoveDTO：bizId（业务 id）、bizType（业务类型），均可选 |
| 返回值 | R<Boolean> |

它要做的事与按 id 删除完全一致——删存储位置的文件、删数据库记录——只是定位条件从 id 换成了业务类型 + 业务 id。实现也走同样的分层：Controller 收 DTO 转发，Service 做查询和编排。

```java
@ApiOperation(value = "根据业务类型或业务id删除文件", notes = "根据业务类型或业务id删除文件")
@DeleteMapping(value = "/biz")
public R<Boolean> removeByBizIdAndBizType(@RequestBody AttachmentRemoveDTO dto) {
    attachmentService.removeByBizIdAndBizType(dto.getBizId(), dto.getBizType());
    return success(true);
}
```

实现类的核心逻辑：

```java
@Override
public void removeByBizIdAndBizType(String bizId, String bizType) {
    // 根据业务类型和业务id查询数据库
    List<Attachment> list = super.list(Wraps.<Attachment>lbQ()
            .eq(Attachment::getBizId, bizId)
            .eq(Attachment::getBizType, bizType));
    if (list.isEmpty()) {
        return;
    }
    // 转成 Long[]，复用按 id 删除
    remove(list.stream().mapToLong(Attachment::getId)
            .boxed().toArray(Long[]::new));
}
```

几个细节：bizId、bizType 传一个或两个都传都可以；查询用 MyBatis-Plus 的条件构造器 lbQ 双条件 eq；查到空集合说明没有可删的附件，直接 return；非空则用 stream 的 mapToLong 取出 id、boxed 装箱、toArray 成 Long[]，交给前面已经实现好的 remove(Long[] ids)——那个方法负责删数据库记录、把记录封装成 FileDeleteDO、再调 fileStrategy.delete 删文件。所以从控制台看，最终发出的 DELETE 语句依然是按 id 删的，按业务删除只是在前面多了一步"按条件查出 id 列表"。

测试沿用阿里云策略：上传文件时 bizId 填 123，确认 URL 可下载；刷新 Swagger 页面找到"根据业务类型/业务id删除"接口，body 传 `{"bizId":"123","bizType":"123"}` 发送，返回 OK；数据库记录消失，控制台里先看到按 bizId+bizType 的 SELECT、再看到 DELETE 语句；原 URL 已无法访问。接口测试通过。

## 打包下载：一条接口，两种形态

下载接口的业务规则分两种情况：客户端只提交一个文件 id，直接下载对应的原始文件；提交多个 id，则把多个原始文件压缩成一个 zip 包，下载的是压缩后的文件。接口契约：

| 项目 | 内容 |
| --- | --- |
| 请求方式 | GET |
| 请求路径 | /attachment/download |
| 请求参数 | ids：query 上的数组，可同时传多个文件 id |
| 响应类型 | application/octet-stream（二进制流） |

Controller 层没有返回值——文件内容要通过输出流写回客户端，而不是封装成 JSON：

```java
@ApiOperation(value = "根据文件ids打包下载", notes = "根据文件ids打包下载")
@GetMapping(value = "/download", produces = "application/octet-stream")
public void download(@RequestParam(value = "ids") Long[] ids,
                     HttpServletRequest request, HttpServletResponse response) {
    attachmentService.download(request, response, ids);
}
```

produces 固定写 application/octet-stream 表示向客户端写回二进制流；request 和 response 也要一起传进 service，写流时要用。Controller 只做参数接收与转发。

Service 实现分三段：查库、判空、转换后交给 FileBiz。

```java
@Override
public void download(HttpServletRequest request, HttpServletResponse response, Long[] ids) {
    // 根据文件id查询数据库，拿文件名、url、大小、类型等信息
    List<Attachment> list = super.listByIds(Arrays.asList(ids));
    if (list.isEmpty()) {
        throw BizException.wrap("您下载的文件不存在！");
    }
    List<FileDO> fileDOList = list.stream().map(file -> FileDO.builder()
            .url(file.getUrl())
            .submittedFileName(file.getSubmittedFileName())
            .size(file.getSize())
            .dataType(file.getDataType())
            .build())
            .collect(Collectors.toList());
    fileBiz.down(fileDOList, request, response);
}
```

id 是客户端传的，可能是构造出来的不存在值，所以查完先判空，空则抛业务异常。下载需要原始文件名（下载下来还要用原始名，而不是存储时的 UUID 名）、数据类型、访问链接、文件大小，这些都在数据库里，查出来经 stream map 成 FileDO 中间对象。至于多文件打包的繁琐细节，单独抽了一个 biz 包下的 FileBiz（@Component + @Slf4j）：写进 service 里就只有这一处能用，抽成独立组件，其他地方也能注入复用。

FileBiz 的 down 方法第一步是过滤并计算总大小：

```java
int fileSize = fileDOList.stream()
        .filter(file -> file != null
                && !DataType.DIR.equals(file.getDataType())   // 目录不下载
                && StringUtils.isNotEmpty(file.getUrl()))      // url 不完整没法下
        .mapToInt(file -> NumberHelper.intValueOf(file.getSize()))
        .sum();
```

正常情况下文件都有效，多过滤一遍是为防目录类型、url 缺失这类脏数据，让程序更健壮；ZipUtils 需要 fileSize 参数，这里用 mapToInt + sum 汇总所有待下载文件的大小。

第二步确定下载文件名：只下载一个文件时，直接取集合第 0 个元素的原始文件名；size 大于 1 时要生成 zip 包名——取第一个文件名最后一个点之前的部分，拼上"等"再补 .zip，比如三个待下载文件都叫 Java编程思想.doc，压缩包就叫"Java编程思想等.zip"。

第三步处理同名冲突并调用工具类。zip 包内文件名不能重复，而 map 的 key 相同时后者会覆盖前者，所以重名文件必须改名后再放进 fileMap：

```java
Map<String, String> fileMap = new LinkedHashMap<>(fileDOList.size());
// 记录重名文件各自重复到第几次
Map<String, Integer> duplicateFile = new HashMap<>(fileDOList.size());
fileDOList.stream()
        .filter(file -> file != null
                && !DataType.DIR.equals(file.getDataType())
                && StringUtils.isNotEmpty(file.getUrl()))
        .forEach(file -> {
            String submittedFileName = file.getSubmittedFileName();
            if (fileMap.containsKey(submittedFileName)) {
                if (duplicateFile.containsKey(submittedFileName)) {
                    // 重复次数加 1
                    duplicateFile.put(submittedFileName,
                            duplicateFile.get(submittedFileName) + 1);
                } else {
                    // 第一次重复
                    duplicateFile.put(submittedFileName, 1);
                }
                submittedFileName = buildNewFileName(submittedFileName,
                        duplicateFile.get(submittedFileName));
            }
            fileMap.put(submittedFileName, file.getUrl());
        });
ZipUtils.zipFilesByInputStream(fileMap, Long.valueOf(fileSize),
        downloadFileName, request, response);
```

buildNewFileName 负责在最后一个点之前插入序号：

```java
private static String buildNewFileName(String fileName, Integer order) {
    return StrUtil.strBuilder(fileName)
            .insert(fileName.lastIndexOf("."), "(" + order + ")")
            .toString();
}
```

效果是 Java编程思想.doc 依次变成 Java编程思想(1).doc、Java编程思想(2).doc——与浏览器重复下载同名文件时自动加序号、不覆盖已有文件是同一个道理。fileMap 用 LinkedHashMap 是为了保持插入顺序；duplicateFile 记录每个重名文件已重复到第几次，保证序号按 1、2、3 顺延。

最终 ZipUtils.zipFilesByInputStream 接收四类参数：文件名到 URL 的映射 fileMap、总大小（工具类要 long，所以 Long.valueOf(fileSize) 转一次）、下载文件名 downloadFileName、request/response。异常直接 throws Exception 往外抛——Controller 层做了统一异常处理，service 和 biz 内部不做捕获。到这里 FileBiz 写完，下载的完整链路已经打通，具体压缩细节封装在工具类内部。

## 小结

这一段把文件服务的"删除家族"凑齐并验证完毕：按 id 删除在 LOCAL 策略下干净利落，在 ALI 策略下暴露出 Windows 分隔符与 OSS key 斜线不一致的 bug，修复方式是日期目录统一正斜线；按业务类型/业务 id 删除没有新逻辑，查出 id 列表复用 remove 即可。打包下载接口则是本章目前最复杂的一个：Controller 无返回值、produces 二进制流，Service 查库判空转 FileDO，重名处理、总大小计算、zip 命名全部下沉到可复用的 FileBiz，最终一行 ZipUtils 调用收尾。回看这三个接口，套路高度一致：Controller 管契约、Service 管编排、Strategy 与工具类管执行，分层越清楚，策略切换和复用就越省事。
