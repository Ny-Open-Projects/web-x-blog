# 查询 Druid 统计列表：Service 层落地与 Postman 联调

连接工具类和 JDBC 语法都备齐之后，cold-druid 查询工程还差最后一环：把「查 Druid」变成一个对外的 HTTP 接口。平台的报警记录页、设备明细页要的都是同一件事，给一组条件，返回温湿度快照列表。这一节沿着接口定义、Service 实现、SQL 组装、结果映射、联调验证的顺序，把列表查询接口完整落地。

## 先给结论

- 查询口分三层：`DruidController` 开路由，`DruidService` 接口定契约，`DruidServiceImpl` 用 JDBC 实现取数。
- 契约里声明两个方法：`queryDruidList` 查数据列表，`queryDruidTumHum` 查设备最近 10 条温湿度；本节实现前者，后者留到温湿度曲线一节，并且会直接复用前者的结果。
- SQL 的底座是 `all_device_message` 表，条件按参数动态拼：设备编码、`__time` 时间区间、`order by __time desc` 加 `limit`。
- 行记录转实体的逻辑收在私有方法 `Rs2Entity` 里，二十多个字段逐个映射，温湿度等数值字段做整型转换。
- 统一返回 `R`：成功时 `code` 为 0、`msg` 为 success，列表挂在 `items`；`finally` 里按结果集、语句、连接的顺序释放。

## 接口契约：Service 层先定两个方法

写实现之前先把契约立起来。`DruidService` 是一个接口，声明两个查询方法（真实代码，包名按规范改写）：

```java
public interface DruidService {
    /**
     * 查询Druid数据列表
     */
    R queryDruidList(@RequestParam Map<String, Object> params);

    /**
     * 查询设备Druid温度湿度（最近10条）
     */
    R queryDruidTumHum(@RequestParam Map<String, Object> params);
}
```

方法签名上有两个细节值得停一下。参数用 `@RequestParam Map<String, Object> params`，前端传来的查询条件原样收进一个 Map，Service 层不必为每个字段写形参，以后加条件时接口签名也不用动。返回值是 `R`，平台的统一响应包装类，所有接口对前端暴露的形状都由它决定。

两个方法分工明确：`queryDruidList` 把 Druid 表里的记录按条件查出来，是报警记录、设备明细这类列表页的数据源；`queryDruidTumHum` 取单台设备最近 10 条温湿度，给温湿度曲线供数。这一节把列表查询做完，曲线方法随后展开。

## 主流程：拼 SQL、执行查询、逐行转实体

实现类 `DruidServiceImpl` 标上 `@Service` 注解交给 Spring 管理，方法体按固定节奏走：拼 SQL、声明资源、取数、转换、包装返回。

```java
@Service("druidService")
public class DruidServiceImpl implements DruidService {
    @Override
    public R queryDruidList(Map<String, Object> params) {
        // 根据参数组装查询条件
        String sql = querySQL(params);

        // 实例化 JDBC 连接工具
        DruidHelper helper = new DruidHelper();
        Connection connection = null;
        Statement st = null;
        ResultSet rs = null;
        try {
            List<MessageEntity> resultList = new ArrayList<>();
            connection = helper.getConnection();
            st = connection.createStatement();
            rs = st.executeQuery(sql);
            while (rs.next()) {
                MessageEntity messageEntity = Rs2Entity(rs);
                resultList.add(messageEntity);
            }

            // 设置返回格式
            Map<String, Object> map = new HashMap<>();
            map.put("items", resultList);
            return R.ok(map);
        } catch (Exception e) {
            e.printStackTrace();
        } finally {
            helper.close(connection, st, rs);
        }
        return R.error();
    }
}
```

动手写的时候，SQL 可以先写死一句 `select * from all_device_message limit 10` 把链路跑通，随后再抽成 `querySQL(params)`，让查询条件跟着参数走：

```java
private String querySQL(Map<String, Object> params) {
    StringBuffer stringBuffer = new StringBuffer();
    stringBuffer.append("SELECT * from all_device_message where 1= 1 ");

    // 设备编码
    String metercode = params.get("metercode").toString().trim();
    if (!metercode.equals("")) {
        stringBuffer.append(" and metercode = '").append(metercode).append("' ");
    }

    // 前台传入开始、结束时间
    String startTime = params.get("stTime").toString().trim();
    if (!startTime.equals("")) {
        stringBuffer.append(" and __time > '").append(startTime).append("' ");
    }
    String endTime = params.get("endTime").toString().trim();
    if (!endTime.equals("")) {
        stringBuffer.append(" and __time < '").append(endTime).append("' ");
    }

    stringBuffer.append(" order by __time desc");

    // 查询条数，不传默认 10
    String limit = params.get("limit") != null ? params.get("limit").toString().trim() : "10";
    stringBuffer.append(" limit ").append(limit);
    return stringBuffer.toString();
}
```

`where 1=1` 是拼条件的惯用起手式，后面的每个条件都从 `and` 开头，参数为空就跳过，无论传不传值 SQL 语法始终成立。时间条件落在 `__time` 列上，这是 Druid 数据表的内置时间列；排序也用它，倒序保证最新的读数排最前，再由 `limit` 控制单页条数，前端默认一页看 10 条正好。

整条调用链如下图，请求从 Controller 进来，Service 拼 SQL 交给 JDBC 工具类，经 Avatica 端点到达 Druid，结果逐行转成实体再包装返回：

```mermaid
flowchart LR
    A["Postman 或前端页面"] --> B["DruidController /select"]
    B --> C["DruidServiceImpl"]
    C --> D["querySQL 组装 SQL"]
    D --> E["DruidHelper 建 JDBC 连接"]
    E --> F["Avatica 端点"]
    F --> G["Druid Broker"]
    G --> H["all_device_message 数据表"]
    H --> I["ResultSet 逐行返回"]
    I --> J["Rs2Entity 转实体"]
    J --> K["R.ok 包 items 返回"]
```

读这张图抓主干：SQL 拼好后真正干活的只有三步，`getConnection` 拿连接、`executeQuery` 发查询、循环里 `Rs2Entity` 把每一行变成 `MessageEntity`。DruidHelper 是前面已经封装好的连接工具，Service 层只管用，不管建连接和释放的细节。

## Rs2Entity：一行记录换一个实体

结果集里的每一行要变成业务对象才能往外传，这段转换收在私有方法里（真实代码节选，字段较多做了精简）：

```java
private MessageEntity Rs2Entity(ResultSet rs) throws Exception {
    MessageEntity messageEntity = new MessageEntity();

    messageEntity.setMetercode(rs.getString("metercode"));
    messageEntity.setMeterid(rs.getString("meterid"));
    messageEntity.setMetername(rs.getString("metername"));
    messageEntity.setHostname(rs.getString("hostname"));
    messageEntity.setHousename(rs.getString("housename"));
    messageEntity.setCompanyname(rs.getString("companyname"));
    // 温湿度等整型字段做类型转换
    messageEntity.setTem(Integer.valueOf(rs.getString("tem")));
    messageEntity.setHum(Integer.valueOf(rs.getString("hum")));
    messageEntity.setTemalert(Integer.valueOf(rs.getString("temalert")));
    messageEntity.setState(Integer.valueOf(rs.getString("state")));
    messageEntity.setCurtime(rs.getString("curtime"));
    // 其余 maxtem、mintem、maxhum、minhum、hostid、houseid、lat、lon 等字段同法逐个 set
    return messageEntity;
}
```

实体字段与 `all_device_message` 表一一对应：设备有编码、主键、名称，主机与仓库各有三件套，公司有名称与主键，温湿度各有当前值、上限、下限，再加告警标志、设备状态、经纬度与采集时间，一套下来正好二十多个字段。

为什么不把 `ResultSet` 直接返回给前端？结果集是和连接绑定的资源，连接一关就失效；只有转成普通对象列表，数据才能脱离连接存活，交给 JSON 序列化后安全地送到前端。温湿度字段走 `Integer.valueOf(rs.getString(...))`，取出来是字符串、装进去是整数，转换在边界上一次做完，前端拿到的直接就是可计算的数值。

## Postman 联调：参数与返回的真实形状

服务启动后用 Postman 打接口。工程端口 8182、上下文路径 `/cold`，Controller 挂在 `apache-druid/query` 下，列表接口的完整地址是：

```bash
curl "http://localhost:8182/cold/apache-druid/query/select?metercode=&stTime=&endTime=&limit=3"
```

四个参数全部可空：`metercode` 传设备编码就按设备过滤，`stTime` 与 `endTime` 传起止时间就按 `__time` 过滤，`limit` 控制条数。返回是 `R` 包装的 JSON（数据为示例）：

```json
{
  "code": 0,
  "msg": "success",
  "items": [
    {
      "metercode": "M0001",
      "metername": "1号温度计",
      "hostname": "1号主机",
      "housename": "1号冷库",
      "tem": 4,
      "hum": 60,
      "state": 1,
      "curtime": "20261106103000"
    }
  ]
}
```

`code` 为 0 加 `msg` 为 success 是 `R.ok` 的默认形状，业务数据统一挂在 `items` 里，每条记录就是实体的全部字段，前端按字段名取值即可渲染列表。到这一步，从 Druid 集群到浏览器页面的取数通道全部打通，报警记录与设备明细两个列表页的数据源就位。

## 常见误区

- **查询条件不做过滤直接拼进 SQL。** 课程写法用字符串拼接演示动态条件，参数值若来自不可信输入就有注入风险。正解：内部平台可对参数做格式校验与白名单，对外系统应改用 PreparedStatement 参数占位或查询构造器。
- **时间条件列名写错。** 错例：`and time > '...'` 或 `and _time > '...'`，直接报列不存在。正解：Druid 的内置时间列是双下划线开头的 `__time`，过滤和排序都用它。
- **资源只在正常路径关闭。** 错例：把 `helper.close` 写在 `return` 之前，一旦查询抛异常连接就泄漏。正解：关闭动作必须放进 `finally`，异常路径与正常路径都执行。
- **两个查询方法各查一遍数据库。** 曲线接口需要的数据其实是列表结果的子集。正解：`queryDruidTumHum` 直接调用 `queryDruidList` 取出 `items` 再加工，SQL 只维护一份，条件变更不用改两处。

## 面试可能被问到的问题

1. 面试官追问：「动态查询条件用字符串拼 SQL，有没有更安全的做法？」
   答：课程演示用 StringBuffer 拼接，重点在理解条件的组装过程。生产环境应改用 PreparedStatement 的参数占位符，或引入查询构造器，把参数值与 SQL 文本分离；同时对 `limit` 这类数字参数做类型校验，避免注入。
2. 面试官追问：「为什么结果集要转成实体列表，不能直接返回吗？」
   答：ResultSet 与数据库连接绑定，连接关闭后不可再读。转成实体列表后数据脱离连接存活，可以被 JSON 序列化、缓存或在层与层之间传递，这也是分层架构里数据访问层与业务层解耦的常规做法。
3. 面试官追问：「温湿度曲线接口为什么复用列表查询，而不是另写一条 SQL？」
   答：曲线需要的就是同一批记录的时间、温度、湿度三列，另写 SQL 会重复维护查询条件。复用 `queryDruidList` 的 `items` 后，Service 层把时间字符串截成时分秒做 x 轴、温度湿度做两个 y 序列，再整体倒序成时间正序即可。
4. 面试官追问：「`R` 这种统一返回结构解决什么问题？」
   答：所有接口用同一外壳，`code` 表示业务状态、`msg` 给出提示、业务数据挂在自己的键下。前端只写一套拦截器处理 code 非 0 的情况，接口之间风格一致，联调与排错成本都下降。
5. 面试官追问：「查询里为什么按 `__time` 倒序加 limit，而不是全查回来再排序？」
   答：Druid 是时序库，数据按时间组织，`__time` 过滤与排序能直接利用存储结构，把排序下推到引擎；全查回来再在应用层排序会把海量明细搬出数据库，内存和带宽都吃不消。监控场景只看最近状态，倒序加 limit 是最贴合意图也最省资源的写法。
