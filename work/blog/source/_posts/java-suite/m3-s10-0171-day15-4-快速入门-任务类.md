# Elastic-Job 快速入门（三）：任务类与 ShardingContext 里的分片参数

数据访问层写完，带分片条件的查询已经就绪，但这条查询还没有人调用。常规分层里应该由业务层调数据访问层，可这个案例的业务太薄，只是一次查询，业务层被省掉，取而代之的是 Elastic-Job 的任务类：框架按 cron 触发它，它去调 Mapper。任务类是框架与业务代码的交界处，它的写法、它从哪里拿分片参数，是这一篇要讲清楚的两件事。

## 先给结论

- 任务类必须实现 `SimpleJob` 接口并重写 `execute` 方法，要执行的定时任务逻辑就写在 `execute` 里，由框架在触发点自动调用。
- `execute` 的入参 `ShardingContext` 是分片上下文，分片总数与当前分片项都从它取，方法是 `getShardingTotalCount()` 与 `getShardingItem()`。
- 不要用 `@Value` 直接把配置文件里的分片参数注进任务类，Elastic-Job 的配置类会把配置组装好，框架再放进 `ShardingContext`，任务类只管取。
- 任务类加 `@Component` 交给 Spring 管理，但这只是第一步，还差 ZooKeeper 注册中心与 Elastic-Job 两个配置类，任务才会真正被调度。
- 打印输出带上分片项编号，控制台才能直观看到每个实例各查了哪部分数据。

## 任务类的骨架：实现 SimpleJob 接口

Elastic-Job 对任务类有明确的格式要求：实现 `com.dangdang.ddframe.job.api.simple.SimpleJob` 接口，重写其中的 `execute` 方法。调用 Mapper 查询数据的代码，就放进这个方法里，之后框架每到 cron 触发点就会自动调用它。写法与业务无关的约定都固定下来了，先看骨架：

```java
import com.dangdang.ddframe.job.api.ShardingContext;
import com.dangdang.ddframe.job.api.simple.SimpleJob;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;

/**
 * 数据查询任务
 */
@Component
public class MyJob implements SimpleJob {

    @Autowired
    private UserMapper userMapper;

    // 执行定时任务
    @Override
    public void execute(ShardingContext shardingContext) {
    }
}
```

三处细节值得留意。**类上加 `@Component`**，让 Spring 扫描到它、把它装配成 Bean，后面的配置类才能引用到这个实例。**注入 `UserMapper`**，数据访问层唯一的查询入口已经备好。**import 的包别引错**，`SimpleJob` 与 `ShardingContext` 都在 `com.dangdang.ddframe.job.api` 体系下，IDE 自动补全时同名类不少，引错包编译虽然能过，运行时框架认不出来。

## ShardingContext：分片参数从哪来

`execute` 方法没有返回值，唯一的参数 `ShardingContext` 是上下文对象。按以往经验，上下文对象就是用来取数据的载体，这次要取的正是分片参数：分片总数与当前分片项。

这两个值能不能直接用 `@Value` 从配置文件注入？可以，但案例没有这么做。原因在于值的流转路径：配置文件里的 `myjob.count` 与 `myjob.cron` 会先被注入到专门的 Elastic-Job 配置类，配置类把它们组装成作业配置交给调度器，框架每次触发任务时再把与本次执行相关的数据存进 `ShardingContext` 传给 `execute`。任务类只需要从上下文里现取现用，取值方法是现成的：

```java
int count = shardingContext.getShardingTotalCount();
int item = shardingContext.getShardingItem();
```

`item` 是当前实例的分片项编号，也就是「正在执行这次任务的是哪台服务器」。把这条数据流画出来，讲的是配置值如何一路抵达任务方法：

```mermaid
flowchart LR
    A[application.properties myjob.count 与 myjob.cron] --> B[ElasticJob 配置类经 @Value 注入]
    B --> C[JobCoreConfiguration 组装作业配置]
    C --> D[SpringJobScheduler 启动调度]
    D --> E[cron 触发 框架构造 ShardingContext]
    E --> F[execute 从上下文取分片总数与分片项]
    F --> G[调用 UserMapper 分片查询]
```

关键在中间两跳：配置类承担「读配置、组配置」的职责，框架承担「把配置值送达执行现场」的职责，任务类与配置文件之间没有直接连线。职责分离之后，同一份任务代码在分片总数改成 5 的环境里一行都不用动。

## 补全任务类：查询与输出

有了分片参数，`execute` 的主体就水到渠成：调 `queryUserById`，把两个分片参数原样传下去，遍历结果打印。为了让分片效果肉眼可见，打印内容必须带上分片项编号：

```java
@Override
public void execute(ShardingContext shardingContext) {
    // 从分片上下文取分片总数与当前分片项
    int count = shardingContext.getShardingTotalCount();
    int item = shardingContext.getShardingItem();

    // 分片查询 传入分片参数 由 SQL 里的 MOD 条件完成分工
    List<User> userList = userMapper.queryUserById(count, item);

    // 输出分片项与查询结果 便于观察各实例的处理范围
    userList.forEach(user -> {
        System.out.println("作业分片：" + item + "-->" + user);
    });
}
```

分片总数为 3 时，三个实例的控制台输出应当各是一份子集：编号 0 的实例打印的数据 id 都是 3 的倍数，编号 1 的实例打印 id 余 1 的记录，编号 2 的实例打印 id 余 2 的记录。观察控制台就能确认，分工既没有重复也没有遗漏，数据访问层那条 `MOD` 条件与框架传下来的分片参数严丝合缝地对上了。

## 距离任务跑起来还差两步

任务类写完，案例还没有完。`execute` 方法此刻没有任何人在调用：任务类只是被 Spring 装配成了 Bean，距离「被调度」还缺两个配置类。一个是 ZooKeeper 注册中心配置，创建 `ZookeeperRegistryCenter` 并连接到注册中心，这一步不能省，Elastic-Job 的选举与分片协调全靠它；另一个是 Elastic-Job 自身的配置类，把任务类、注册中心、cron 与分片总数组装成 `SpringJobScheduler` 并启动。这两个配置类到位后，框架才会按 cron 自动触发 `execute`。

快速入门练的这套姿势，迁移到还款服务上几乎是平移。定时还款的任务类同样实现 `SimpleJob`，`execute` 里把分片参数转交业务层，按讲义补全后的写法如下：

```java
package com.study.finance.repayment.job;

import com.dangdang.ddframe.job.api.ShardingContext;
import com.dangdang.ddframe.job.api.simple.SimpleJob;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;

import java.time.LocalDate;
import java.time.format.DateTimeFormatter;

@Component
public class RepaymentJob implements SimpleJob {

    @Autowired
    private RepaymentService repaymentService;

    @Override
    public void execute(ShardingContext shardingContext) {
        // 调用业务层执行定时还款 传入分片参数完成分片查询
        repaymentService.executeRepayment(
                LocalDate.now().format(DateTimeFormatter.ISO_LOCAL_DATE),
                shardingContext.getShardingTotalCount(),
                shardingContext.getShardingItem());
    }
}
```

对比两个任务类可以看出框架设计的用意：案例的 `MyJob` 直接调 Mapper，因为业务太薄不值得分层；还款的 `RepaymentJob` 调业务层，因为还款涉及扣款、状态流转、放款确认等复杂链路。任务类本身始终只有一件事：从上下文取分片参数，把它交给真正干活的层。

## 常见误区

- **以为加了 `@Component` 任务就会自动执行。** 错例：任务类写完直接启动，控制台没有任何输出。正解：`@Component` 只解决装配，调度还需要 ZooKeeper 注册中心配置类与 Elastic-Job 配置类，由 `SpringJobScheduler` 把任务类、注册中心、cron 组装起来才会触发。
- **SimpleJob 或 ShardingContext 引错包。** 错例：IDE 自动补全选了别的同名类，编译通过但框架无法识别任务类型。正解：确认 import 是 `com.dangdang.ddframe.job.api.simple.SimpleJob` 与 `com.dangdang.ddframe.job.api.ShardingContext`。
- **用 `@Value` 把分片参数注进任务类。** 错例：在任务类字段上直接 `@Value("${myjob.count}")`。正解：分片总数与分片项由框架按本次执行写入 `ShardingContext`，从上下文取值才能拿到「当前实例、当前一轮」的参数，多实例环境下的值各不相同。
- **把分片项当成固定服务器编号去硬编码逻辑。** 错例：在 `execute` 里写死「item 为 0 就查全表」之类的特殊分支。正解：分片项的分配随实例增减动态变化，任务类应当对所有分片项一视同仁，把参数传给查询条件即可。
- **忘记打印分片项导致效果无法验证。** 错例：只打印查询结果，看不出哪个实例处理了哪片。正解：输出里带上 `getShardingItem()` 的值，多实例控制台对照着看，分片是否平均分配一目了然。

## 面试可能被问到的问题

1. 面试官追问：「Elastic-Job 的任务类为什么要实现 SimpleJob 接口？」
   答：`SimpleJob` 是 Elastic-Job 简单作业类型的规范接口，框架只认实现它的类，每到 cron 触发点就回调其 `execute` 方法。任务逻辑写在 `execute` 里，框架负责触发与传参，业务负责执行，两者通过接口解耦。
2. 面试官追问：「ShardingContext 里有什么？分片参数是怎么进来的？」
   答：它是分片上下文对象，携带本次执行的分片信息，常用的有分片总数 `getShardingTotalCount()` 与当前分片项 `getShardingItem()`。配置文件里的值先由配置类组装进作业配置，框架触发任务时再写入上下文传给 `execute`，任务类从上下文现取。
3. 面试官追问：「任务类上加了 @Component 为什么任务还没跑起来？」
   答：`@Component` 只是把任务类交给 Spring 装配成 Bean。要被调度还需要两个配置：ZooKeeper 注册中心配置创建 `ZookeeperRegistryCenter` 并初始化连接，Elastic-Job 配置类把任务类、注册中心与作业配置组装成 `SpringJobScheduler` 启动，之后框架才按 cron 触发。
4. 面试官追问：「多个实例执行同一个任务类，怎么做到各干各的？」
   答：每个实例触发 `execute` 时，框架传入的分片项不同，例如分片总数为 3 时分别是 0、1、2。任务类把分片项传给数据层，SQL 里用 `MOD(id, 分片总数) = 分片项` 过滤，各实例只处理自己片内的数据，不重复也不遗漏。
5. 面试官追问：「快速入门案例里业务层被省掉了，真实项目也这样吗？」
   答：不是。案例业务只是一次查询，直接由任务类调 Mapper 更直白。真实项目如定时还款，任务类 `RepaymentJob` 从上下文取出分片参数后转交 `RepaymentService`，由业务层组织扣款与状态流转等复杂逻辑，任务类只做参数传递，分层随业务复杂度保留。
