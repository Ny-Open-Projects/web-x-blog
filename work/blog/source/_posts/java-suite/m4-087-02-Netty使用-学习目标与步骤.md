# Netty 实战：Server/Client 完整实现与验证 + 数据库设计规范与原则

本章两条主线：前半程用 Netty 搭一个最小可用的通讯服务——父工程 netty-demo 下挂 netty-server 与 netty-client 两个模块，从 ServerBootstrap 配到 pipeline 编解码，跑通双向收发；后半程转入数据库设计，从"为什么需要规范"讲到三范式与反范式的权衡，再落到命名规范、表设计规范与设计原则。

## 先给结论

- Netty 双向通讯的最小工程形态是父工程加两个子模块：netty-demo 只做聚合，netty-server 与 netty-client 各自实现启动类与 Handler；Netty 依赖统一放父工程，避免重复引入。
- 服务端启动的骨架是两个 EventLoopGroup 加一个 ServerBootstrap：bossGroup 监听连接，workGroup 处理已接收的连接；SO_BACKLOG 设 TCP 最大缓存连接个数（默认 128），SO_KEEPALIVE 保持连接正常状态。
- pipeline 里按序挂 StringDecoder、StringEncoder 和自定义 Handler：用 String 内置编解码器就不需处理二进制数据，收到内容直接打印。
- Handler 分工明确：服务端 channelActive 把连接通道收进静态 channelList 供广播下发，客户端 channelActive 记录 serverChannel 供后续逻辑取用；异常统一打印堆栈并关闭通道。
- 数据库是项目最底层设计，参与角色众多（架构师、高级工程师、研发、测试、DBA），没有明确规范协作会非常困难；范式层次清晰但查询要连更多表，反范式是在范式基础上找平衡点——适合业务的设计才是好设计。
- 表设计硬规矩：无特殊情况选 InnoDB，精确浮点用 DECIMAL，varchar(n) 的 n 是字符数不是字节数，timestamp 4 字节 datetime 8 字节，拒绝 3B（大 SQL、大事务、大批量），单表索引四五个就够。

## 工程设计与结构：父工程 + 两个模块

工程设计一句话说清：建立通讯服务端与通讯客户端两个工程，相互发送消息，做简易聊天演示——客户端连接服务端后可以发送消息，服务端也可以下发消息给客户端，两端都通过 Netty 集成实现。

```mermaid
flowchart LR
    C["通讯客户端 netty-client"] <-->|"相互发送消息"| S["通讯服务端 netty-server"]
```

工程结构对应这个设计：

```
netty-demo          # 父工程，只做聚合，不做具体业务实现
├── netty-client    # 客户端模块：启动、连接、收发消息
└── netty-server    # 服务端模块：监听端口、接收与下发消息
```

父工程 pom.xml 声明两个模块，并统一引入 Netty 依赖：

```xml
<modules>
    <module>netty-server</module>
    <module>netty-client</module>
</modules>

<dependencies>
    <dependency>
        <groupId>io.netty</groupId>
        <artifactId>netty-all</artifactId>
        <version>4.1.16.Final</version>
    </dependency>
</dependencies>
```

实现顺序有个细节：起初依赖加在 netty-server 的 pom 里，写客户端时 NioEventLoopGroup 报找不到，于是把依赖上移到父工程，两个子模块都不用各自引用。多模块的依赖，能放父级就放父级。

## 服务端实现：两个核心类与启动参数

服务端要做三件事：接收客户端请求并打印消息；采用字符串编解码器，内容直观；开启输入监听线程，把控制台输入发送给客户端。核心类两个——NettyProviderServer 负责启动 Netty 服务，NettyServerHandler 负责读取处理接收的数据。

NettyProviderServer 通过构造方法注入端口，runServer 承载启动逻辑：

```java
public class NettyProviderServer {
    private int port; // 服务端口

    public NettyProviderServer(int port) {
        this.port = port;
    }

    public void runServer() throws Exception {
        // 定义 boss 监听组
        EventLoopGroup bossGroup = new NioEventLoopGroup();
        // 定义 Worker，用于处理已经被接收的连接
        EventLoopGroup workGroup = new NioEventLoopGroup();
        try {
            // 定义 NIO 服务启动类，配置启动相关参数
            ServerBootstrap sbs = new ServerBootstrap();
            sbs.group(bossGroup, workGroup)
               .channel(NioServerSocketChannel.class)
               .option(ChannelOption.SO_BACKLOG, 128)
               .childOption(ChannelOption.SO_KEEPALIVE, true)
               .childHandler(new ChannelInitializer<SocketChannel>() {
                   @Override
                   public void initChannel(SocketChannel ch) throws Exception {
                       ChannelPipeline pipeline = ch.pipeline();
                       pipeline.addLast(new StringDecoder());      // 解码：解析客户端消息
                       pipeline.addLast(new StringEncoder());      // 编码：发送消息转码
                       pipeline.addLast(new NettyServerHandler()); // 处理接收到的请求数据
                   }
               });
            // 绑定端口，同步方式监听客户端的连接请求
            ChannelFuture cf = sbs.bind(port).sync();
            cf.channel().closeFuture().sync();
        } finally {
            // Netty 的优雅关闭，防止强行中止导致业务逻辑中断
            bossGroup.shutdownGracefully();
            workGroup.shutdownGracefully();
        }
    }

    public static void main(String[] args) throws Exception {
        new NettyProviderServer(9911).runServer();
    }
}
```

几个配置值得展开：

| 配置 | 作用 |
| --- | --- |
| SO_BACKLOG | 设置 TCP 最大缓存连接个数，默认 128；并发量大可调高，一般用默认值即可 |
| SO_KEEPALIVE | 设为 true，保持连接的正常状态 |
| LoggingHandler | Netty 自带日志处理器，开启后会把数据报的报文打印出来，便于跟踪定位问题 |
| shutdownGracefully | 优雅关闭：逻辑没处理完就强行中止线程影响业务稳定性，所以放在 finally 里执行 |

initChannel 是管道的注册入口：先创建 pipeline 对象再依次 addLast——解码器解析转换客户端发来的内容，编码器在发送时做转码，最后挂业务 Handler 处理接收到的数据。

NettyServerHandler 继承 ChannelInboundHandlerAdapter，实现三个方法：

```java
public class NettyServerHandler extends ChannelInboundHandlerAdapter {
    // 记录所有客户端连接通道，服务端下发消息从这里取
    public static List<Channel> channelList = new ArrayList<Channel>();

    @Override
    public void channelActive(ChannelHandlerContext ctx) throws Exception {
        super.channelActive(ctx);
        // 连接通道激活时做记录，监听所有客户端连接
        channelList.add(ctx.channel());
    }

    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) throws Exception {
        // String 编解码器模式下无需额外处理，直接打印
        System.out.println("server--收到消息：" + msg);
    }

    @Override
    public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) throws Exception {
        // 打印异常堆栈，关闭对应的连接通道
        cause.printStackTrace();
        ctx.close();
    }
}
```

channelActive 的价值在广播场景：服务端面向的不只一个客户端，所有连接通道都收进 channelList，下发消息时逐个取出通道发送。最后是输入监听线程：通过 BufferedReader 监听控制台输入，回车确认后遍历 channelList 发送。

## 客户端实现与双向通讯验证

客户端整体逻辑与服务端基本类似，差异两点：客户端要主动连接服务端，构造方法注入 IP 和端口两个连接信息；启动类用 Bootstrap 而不是 ServerBootstrap。实现步骤是六步：定义 EventLoopGroup → 定义启动类 → 配置启动参数 → 连接启动 → 实现数据发送 → 开监听线程把输入信息发送至服务端。

```java
public class NettyClientServer {
    private String ip;    // 服务端 IP
    private int port;     // 服务端端口

    public NettyClientServer(String ip, int port) {
        this.ip = ip;
        this.port = port;
    }

    private void runServer() throws Exception {
        EventLoopGroup group = new NioEventLoopGroup();
        try {
            Bootstrap bs = new Bootstrap();
            bs.group(group)
              .channel(NioSocketChannel.class)
              .option(ChannelOption.SO_KEEPALIVE, true)
              .handler(new ChannelInitializer<SocketChannel>() {
                  @Override
                  protected void initChannel(SocketChannel socketChannel) throws Exception {
                      ChannelPipeline pipeline = socketChannel.pipeline();
                      pipeline.addLast(new StringDecoder());
                      pipeline.addLast(new StringEncoder());
                      pipeline.addLast(new NettyClientHandler());
                  }
              });
            // 连接服务端，同步等待
            ChannelFuture cf = bs.connect(ip, port).sync();
            Channel channel = cf.channel();
            // 连接成功即发送连接请求信息
            channel.writeAndFlush("客户端发起连接请求");
            channel.closeFuture().sync();
        } finally {
            group.shutdownGracefully();
        }
    }

    public static void main(String[] args) throws Exception {
        new NettyClientServer("127.0.0.1", 9911).runServer();
    }
}
```

客户端 Handler 与服务端同构，差别在 channelActive 记录的是与服务端的连接通道：

```java
public class NettyClientHandler extends ChannelInboundHandlerAdapter {
    // 记录与服务端的连接通道，其他逻辑要发消息直接拿它用
    public static Channel serverChannel = null;

    @Override
    public void channelActive(ChannelHandlerContext ctx) throws Exception {
        super.channelActive(ctx);
        serverChannel = ctx.channel();
    }

    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) throws Exception {
        System.out.println("client--收到消息：" + msg);
    }

    @Override
    public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) throws Exception {
        System.err.println("client 读取数据出现异常");
        cause.printStackTrace();
        ctx.close();
    }
}
```

两端启动后验证双向通讯：服务端绑定 9911 端口启动成功，客户端连接 127.0.0.1:9911 后立刻发出"客户端发起连接请求"，服务端收到并打印；客户端输入"我是客户端client"回车，服务端打印；服务端输入"我是服务端server"回车，客户端同样收到。两端均能正常收发相互之间的消息，Netty 通讯服务的集成完整跑通。

验证时踩过一个坑：服务端第一次下发消息直接敲回车，客户端没收到。监听线程从控制台读取内容，回车时没有任何数据就发不出去——每条数据都要先输入完再回车，不能直接按回车。

最后看编码器取舍。本例用 String 内置编解码器，内容直观，不需处理二进制数据；后续项目会结合 Protobuf 二进制序列化做编码解码。实际工作还可自定义编码器：头部放数据包长度、请求类型、CRC 校验，包体承载具体内容，更灵活高效地封装通讯数据。

## 数据库设计：为什么需要规范，如何设计

后半程转入数据库设计，先回答"为什么需要规范"。互联网项目团队分工明确、拆分细致，经常需要彼此协作——有设计人员、研发人员、测试人员、需求产品人员；具体到角色，架构师负责架构设计，高级工程师负责核心功能，研发工程师负责功能实现，还有测试工程师、DBA 等。数据库是项目最底层的设计——如果设计不清晰、结构模糊、规范混乱，众多不同层次、不同职责的人员协作起来会非常困难，很难做成一个成功的项目。所以必须为数据库建立一套明确的设计规范，便于协作。

如何设计？传统数据库设计往往遵循设计范式（三范式），但范式难以满足所有项目要求，于是出现了反范式设计。三范式如下：

| 范式 | 要求 | 例子 |
| --- | --- | --- |
| 第一范式 | 每一列都是不可分割的基本数据项 | 股票名称、股票代码不能再细分；"金融衍生产品"则可分割——下面还包括股票、期货、外汇 |
| 第二范式 | 所有属性必须和主键有完全依赖关系 | 用户编号为主键，用户名、用户地址、性别、身份证等属性完全依赖于它 |
| 第三范式 | 属性不能存在传递依赖（A→B→C） | 股票表含股票编号、名称、市场、交易手续费：手续费由股票市场决定，形成传递依赖，违反第三范式 |

第三范式的股票表例子值得展开：股票编号和名称关联在一起，而不同股票市场有不同交易手续费，是另一层关联维度——两个层次的信息放在一张表里就违反了范式。解法是拆成两张表：一张存股票编号、名称，另一张存股票市场、交易手续费。

范式设计层次关系明确，但缺陷明显：业务查询复杂度高，中间关系表膨胀，查询要连接更多表，性能严重下降——比如根据用户 ID 查名称、地址，每次都得查完整的用户表，带来大量不必要的查询，严重影响系统吞吐性能。反范式不是完全打破范式，而是在范式基础上找平衡点——适合业务的设计才是好设计。

落到实际业务，设计分三步走：

```mermaid
flowchart LR
    A["先拆解：分清核心模块与非核心模块"] --> B["画关系：依赖、包含、聚合、组合"]
    B --> C["再细化：填充属性，适当反范式冗余"]
```

以交易平台为例：撮合交易处理机制、行情订阅与下发是核心模块，用户注册、开户属于周边服务。画关系时把模块串接成整体——一个用户可能下多笔订单，一笔订单下可能分多笔成交记录，必须理清依赖与包含、聚合与组合。细化时该冗余的地方冗余一下，比如冗余一个用户编号这样的关键关联信息；但不能过度反范式，把用户地址、年龄、性别全塞进交易表，既违反范式原则，也会严重影响交易表性能。

## 命名、表设计规范与设计原则

规范不是千篇一律，但要在项目体系内形成一套有效规范。命名规范先立八条：

- 命名要有意义且统一，一眼看出表是干什么的：t_order 订单表、t_user 用户表（t 代表 table）。
- 数据库与表名采用小写、不缩写：数据库如 backend，表如 client_device_info（客户端设备信息）；大写在数据库里也会转成小写处理，一步到位用小写还提升性能。
- 索引统一以 idx_ 为前缀（index 的缩写），看到前缀就知道是索引。
- 命名不要过长，尽量少于 25 个字符：名称太长不易维护，也极容易出错。
- 不使用保留字，否则查询时往往出错。
- 同一字段在不同表中类型和长度保持一致：order 表和 user 表都有 user_id，都以 ID 做主键关联，DBA 一看就知道对应关系。
- 同一数据库不同模块用不同前缀标识：交易 trade_ 开头、业务 b_ 开头、活动 activity_ 开头，看表名就知道功能归属。
- 备份表命名加时间标识：否则备份一多，就说不清是什么时段的数据，恢复维护都麻烦。

表设计规范条目较多，归成一张表：

| 类别 | 规范 | 原因 |
| --- | --- | --- |
| 引擎 | 无特殊情况选 InnoDB | MyISAM 不支持事务，InnoDB 支持事务处理 |
| 主键 | 每个表都应有主键，选自增或长整型字段；多字段可组成唯一且需频繁查询时用复合主键 | 如用户编号+交易商编号：不产生重复数据、节省空间，分别查询也有效率提升 |
| 空值 | 尽量将字段设置为 NOT NULL（不做强制要求） | NULL 需要额外存储空间且不等于空字符串；比较运算更复杂，优化器更难优化；NULL 列占一个额外字节 |
| 数值 | 使用更短小的列，整型列执行速度往往更快 | 基本优化点 |
| 浮点 | 精确浮点数必须用 DECIMAL 代替 FLOAT、DOUBLE | 不用 DECIMAL 会出现精度丢失 |
| 类型 | 用 unsigned 存非负值；用 int unsigned 存 IPv4；整型不加显示长度，用 int 而非 int(4) | 整型存储比字符串类型快；定义显示长度没有实际效果 |
| 文本 | 尽可能不用 TEXT、BLOB，用 VARCHAR 代替，不够就放大（200 不够给 500） | TEXT/BLOB 查询速度远低于 VARCHAR；VARCHAR(n) 的 n 是字符数不是字节数，VARCHAR(255) 最大可存 255 个汉字，按实际长度选 N |
| 字符集 | 选择 UTF-8 | 国际通用编码，不容易出现乱码 |
| 时间 | 存年份用 YEAR，存日期用 DATE，存时间建议 TIMESTAMP（4 字节，DATETIME 是 8 字节） | YEAR/DATE 不存多余的时间戳信息；规划 100 年存储范围用 DATETIME，三到五年 TIMESTAMP 足够 |
| 文件 | 不用 VARBINARY 或 BLOB 存图片和文件 | 放到分布式存储系统专门存文件，MySQL 不适合大量存这类数据 |
| 关联 | Join 操作字段在不同表中类型和命名保持一致 | 保证关联查询正确与效率 |
| 变更 | 更改表结构会影响性能时，要 DBA 与相关设计人员联合评审 | 擅自修改可能给生产环境带来不可预知的严重后果 |

设计原则分四类。核心原则：不在数据库做运算，CPU 计算务必转移到业务层；控制每个表的列数量，字段少而精，建议 20 个字段以内；平衡范式与冗余，效率优先；拒绝 3B（big sql、big transaction、big batch），事务里有上百个操作就要裁分缩小。

字段类原则：用好数值类型，能用整型不用字符型，能用更小类型就用更小；字符串能转数字的最好转化，节约空间、提高查询性能，排序时尤其明显；避免 NULL 字段——NULL 很难查询优化，索引需额外空间，复合索引无效；少用 TEXT，用 VARCHAR 代替。

索引类原则：合理使用索引——改善查询但减慢更新，不是越多越好，加多了影响增改查性能，一张表四五个索引就可以；字符字段大量重复属性时尽量建前缀索引，比如 `alter table x_test add index(x_city(6))`；不在索引列上做计算；InnoDB 主键推荐自增列——主键建聚簇索引、不应被修改、字符串不应做主键，分布式主键可用 UUID；不用外键，由程序保证约束。

SQL 类原则：SQL 尽可能简单——一条 SQL 只能在一个 CPU 上运算，大语句拆小语句减少锁时间，一条大 SQL 可以堵死整个库（比如一个报表查询影响所有查询）；避免触发器、函数，用程序取而代之；大批量更新操作注意开启事务，量越大性能效果越明显。

## 小结

Netty 线：从工程设计到工程结构（父工程聚合 + 双模块），服务端与客户端的启动类、Handler 各司其职，Boss/Worker 事件循环组、SO_BACKLOG、SO_KEEPALIVE、pipeline 编解码链一一落地，最终验证了双向简易通讯；编解码先用 String 内置实现跑通，后续结合 Protobuf 做二进制序列化，进一步可自定义头部加包体的协议。数据库线：最底层设计，规范是协作前提；三范式保证结构清晰，反范式在性能与结构间找平衡，业务设计走"先拆解、画关系、再细化"三步；命名规范、表设计规范与四类设计原则是把设计落到实处的操作手册。
