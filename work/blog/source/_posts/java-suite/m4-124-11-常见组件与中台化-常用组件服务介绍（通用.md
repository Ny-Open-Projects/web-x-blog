# 品达权限系统实战下篇：商品服务开发、已有项目集成与注册登录服务

上一篇把品达通用权限系统的架构与重点代码交代清楚了，这一篇进入实战：先把系统前后端完整跑起来，再用一个商品服务演示"以权限系统为脚手架开发新项目"的全流程，接着说明已有项目如何通过 iframe 与网关路由集成进来，最后引出面向 C 端用户的注册登录服务。

## 先给结论

- 系统运行闭环：后端（网关 + 权限服务）就绪后，解压前端工程 pinda-authority-ui（105MB，node_modules 已预装），执行 `npm run dev` 启动，用内置账号品达/品达123 登录；页面上的组织、菜单数据都动态来自数据库初始化脚本。
- 新项目开发就是在 pd-apps 下建业务模块：商品服务示例创建 pd-goods（下分 entity、server 两个子模块）、pd_goods 库与 pd_goods_info 表，实体用 @TableName 映射，DTO 直接继承实体类。
- pd-goods-server 的配置文件整体复用资料提供的 resources（dozer、mapper、bootstrap.yml、p6spy），再在 Nacos 配置中心为本服务新建配置（数据库指向 pd_goods、Swagger 扫描包、端口）；配置类直接继承 pd-tools-common 里的 BaseConfig，实现复用。
- 网关路由是关键一步：在 Nacos 的 pd-gateway.yml 中为商品服务加路由 `/goods/** → pd-goods-server`，请求必须带 /goods 前缀过网关鉴权；再通过菜单（/goods、goodsinfo）与四条资源权限（goodsInfo:add/update/delete/view）配置商品模块的访问控制。
- 微服务必须在同一 Nacos 分组：商品服务因缺 `group: pinda-tms` 落在默认分组，网关路由找不到服务、页面加载不出数据，补上分组后恢复。
- 已有项目集成的核心是 iframe 内嵌 + 请求改走网关；注册登录服务 cust-auth（auth、auth-common、auth-gateway 三模块，网关端口 8782）面向互联网 C 端用户，支持账号密码、手机验证码、微信扫码、微博、QQ 登录，登录成功自动完成注册。

## 先跑起来：前端工程与内置账号

后端两个服务启动后还差前端。资料里的前端工程是 pinda-authority-ui 压缩包，解压后 node_modules 已经提前装好——前端依赖的 JS 模块非常多，和后端的模块化开发类似。运行前端的前提是安装 Node.js，它之于前端工程就像 JDK 之于 Java 项目，没有运行环境就跑不起来。

进入工程根目录执行 `npm run dev`，编译完成后自动弹出页面，登录页需要输验证码（比如 0×7 这类算式）。登录用内置账号品达/品达123——它就是建表脚本初始化的用户。登录后能看到系统管理里的组织管理，树上的初始化数据同样来自脚本；不想要可以直接删掉，再新增自己的部门、修改名称、在某部门下添加下级，页面操作都很直观。左侧显示哪些菜单，也是在菜单配置里动态配置的，数据同样来自数据库。

整个链路是：前端操作先访问网关服务，网关鉴权通过后路由到权限服务，最终完成权限相关数据的动态维护。

## 新项目开发：以商品服务为例

新项目开发相对简单：把通用权限系统当开发脚手架，直接在 Maven 工程基础上开发业务。示例做一个简化的商品管理（增删改查），重点是展示开发流程。

**第一步，搭环境建模块。** 商品要有自己的库：创建数据库 pd_goods，在其中建商品信息表 pd_goods_info（含 code、name、bar_code、brand_id、one_category_id、price、average_cost 等字段）。然后在 pd-apps 下创建 Maven 模块 pd-goods，再在其下创建两个子模块 pd-goods-entity（实体）与 pd-goods-server（服务）。

**第二步，写实体与 DTO。** entity 模块的 POM 引入 pd-tools-common、Swagger 文档、MyBatis-Plus 等依赖，然后创建实体类：

```java
@Data
@ToString(callSuper = true)
@EqualsAndHashCode(callSuper = true)
@TableName("pd_goods_info")
public class GoodsInfo extends Entity {
    private String name;
    private String barCode;
    private Integer brandId;
    private Integer oneCategoryId;
    private Integer twoCategoryId;
    private Integer threeCategoryId;
    private BigDecimal price;
    private BigDecimal averageCost;
    private LocalDateTime productionDate;
    private Integer shelfLife;
    private String descrip;
}
```

DTO 分得比较细：GoodsInfoPageDTO 继承 GoodsInfo 并扩展两个时间查询属性，GoodsInfoSaveDTO、GoodsInfoUpdateDTO 也直接继承实体类——接口调用、保存、更新各用各的传输对象，分类明确。

**第三步，配置 server 模块。** pd-goods-server 的 POM 拷入依赖坐标（含 Spring Cloud 全家桶）与 build 配置，注意依赖的 pd-goods-entity 版本要写 1.0.0，对不上会报找不到依赖。接着把资料提供的配置文件整包复制到 resources：dozer 文件（对象转换组件，可替代 BeanUtils 做属性拷贝，暂无转换需求就放空文件）、MyBatis 映射文件、bootstrap.yml、日志配置，还有 p6spy——它能在控制台输出 SQL 并记录执行时间。

新服务有自己特定的配置，需要在 Nacos 配置中心新建一个 yml 配置发布，内容重点三处：数据库指向新库 pd_goods、Swagger 要扫描的包（Controller 必须创建在该包下）、服务端口号。

**第四步，启动类与配置类。** 启动类 GoodsServerApplication 是常规组合：@SpringBootApplication 之外，@EnableDiscoveryClient 到 Nacos 注册中心发现服务，@EnableCircuitBreaker 开启熔断，@EnableFeignClients 支持接口远程调用，再加上事务、日志与一个自定义的开启数据校验注解。配置类放在 config 包下，包括全局异常处理、数据库配置（创建数据源与 SqlSessionTemplate）、MyBatis-Plus 拦截器、Web 配置——它们全都继承 BaseConfig，这个父类来自 pd-tools-common，公共配置直接复用。

**第五步，写三层。** GoodsInfoMapper 接口继承 MyBatis-Plus 的 BaseMapper<GoodsInfo>，GoodsInfoService 接口继承 IService，实现类放 impl 包，GoodsInfoController 调 Service 完成增删改查（save、update、removeByIds、分页 page）。到这里后端业务功能就开发完了。

**第六步，配置网关路由。** 这一步很重要：商品服务的请求必须先过网关鉴权，鉴权通过才会路由到商品服务，没有权限就直接响应客户端。在 Nacos 中找到网关服务对应的 pd-gateway.yml，在 zuul.routes 下新增一段规则：

```yaml
zuul:
  prefix: /api
  retryable: false
  routes:
    authority:
      path: /authority/**
      serviceId: pd-auth-server
    goods:
      path: /goods/**
      serviceId: pd-goods-server
```

路由名 goods 随便起，关键是 path：请求商品服务时路径必须包含 /goods 才能匹配上，匹配且鉴权通过后转发到 pd-goods-server。网关服务于众多服务，每个依赖它鉴权的服务都要在这里登记路由。

**第七步，前端与权限配置。** 前端以 pinda-authority-ui 为脚手架，商品相关页面资料已提供——src 下 pinda/goods 目录里两个页面：商品首页与编辑页，直接拷进来用。然后把网关、权限、商品三个服务和前端全部启动，用管理员账号登录，配置菜单与资源权限：在菜单配置里添加"商品管理"菜单（路由 URI /goods，与页面对应，图标随意），选中它再添加下级"商品信息"（路由 URI goodsinfo）；接着在商品信息菜单下配置四条资源权限，请求方式与请求地址必须和 Controller 的注解一一对应：

| 编码 | 名称 | 请求方式 | 请求地址 |
| :--- | :--- | :--- | :--- |
| goodsInfo:add | 新增 | POST | /goodsInfo |
| goodsInfo:update | 修改 | PUT | /goodsInfo |
| goodsInfo:delete | 删除 | DELETE | /goodsInfo |
| goodsInfo:view | 列表 | GET | /goodsInfo/page |

菜单与权限数据最终都保存进数据库。最后配置角色：角色管理里新建一个测试角色（编码随意、状态启用、组织随便选一个部门），为它配置菜单——只勾商品管理与商品信息——再把刚创建的四条权限勾上；然后创建新用户 user-001（密码默认 123456，组织选同一个，岗位随意），回到角色列表点授权，搜索 user-001 绑定进已选用户。刚创建的用户可能因缓存搜不到，刷新页面或去数据库 pd_auth_user 表确认数据已插入即可。用 user-001 登录，只能看到商品管理下的商品信息菜单；用管理员品达登录，能看到全部菜单——角色分配的菜单不同，效果立现。

中间踩过一个坑：页面上商品数据加载不出来。排查发现是 pd-auth-server、pd-goods-server、pd-gateway 三个服务不在同一个分组——网关处理完想路由到商品服务却找不到它。解决方法是在商品服务的注册中心配置里加 `group: pinda-tms`，与权限服务、网关服务同分组；不写就落在默认分组，路由必然失败。改完之后查询、删除都正常了。

## 已有项目集成：iframe 内嵌与网关路由

项目已经开发完，又想用通用权限系统做权限管理与认证鉴权，就是已有项目集成。以开发完成的 TMS 物流项目为例，分三部分：TMS 调整、网关路由配置、权限系统配置。

**TMS 调整主要是前端页面。** 把已有项目的前端页面通过 iframe 形式内嵌到权限系统前端页面中。权限系统前端主体内容区本身就是一个 iframe，内容从配置的地址加载——所以业务系统的页面可以嵌进来展示。原项目的菜单页面不再需要：所有菜单在权限系统统一配置，只要保留表单、列表这类详细页面；如果菜单和列表原本挤在一个大页面里，需要拆分开，iframe 里只展示详情。

**请求地址改造。** 为了统一鉴权，已有前端发的请求要首先经过权限系统的网关处理。网关统一以 /api 开头（如 /api/web-manager），前端开发环境用 proxy 代理到网关端口 8760：

```javascript
devServer: {
  port: 8080,
  proxy: {
    '/api': {
      target: 'http://39.100.244.120:8760/api/web-manager',
      changeOrigin: true,
      ws: true,
      pathRewrite: { '^/api': '' }
    }
  }
}
```

请求经过网关时走前面介绍的那几个过滤器完成鉴权与 token 校验，通过后按 zuul 路由转发到真正的业务服务。已有服务只要注册到 Nacos，就能被网关路由到：

```yaml
zuul:
  routes:
    authority:
      path: /authority/**
      serviceId: pd-auth-server
    pay:
      path: /pay/**
      serviceId: pd-of-pay-server
    web-manager:
      path: /web-manager/**
      serviceId: pd-web-manager
    web-xcz:
      path: /xczx/api/**
      url: http://xc-main-java.ithema.net:7291/api/
```

**权限系统配置**与新项目开发完全一样：在菜单配置下为物流项目建菜单（如机构作业范围列表），菜单下挂资源权限（如 viewtree 的 GET、addtag 的 POST），创建角色分配菜单与权限，再绑定用户。登录后点击菜单，iframe 就会内嵌加载你自己的系统页面。集成的主要工作量在已有前端页面的调整上，后端只需注册进 Nacos。

## 注册登录服务：面向 C 端用户

常用组件的第二个服务是注册登录服务。它和通用权限系统表面相似（都做用户管理、鉴权），区别在用户体系：权限系统管的是企业内部用户——账号由管理员开设并分配角色权限，没有注册功能；注册登录服务面向互联网用户，电商平台、游戏、社交软件这类系统，任何人都可以自行注册、登录。

登录认证几乎是任何一个系统的标配，Web 系统、APP、PC 客户端都需要。以淘宝为例：用手机号注册账号，下单时输入用户名密码登录，一段时间内再次进入不用重新登录，长时间不登录才会要求再次认证。

这套通用注册登录服务提供的登录方式基本涵盖市面主流：用户名密码登录（最传统）、手机验证码登录（输入手机号获取验证码即可，不用记密码）、微信扫码登录，以及微博登录、QQ 登录等第三方登录——服务已与这些三方认证完成对接。还有一个便利点：登录成功自动完成注册，用手机验证码登录的新用户，第一次登录完成后就自动注册了，不用专门去注册页面。

工程结构上，项目根目录为 cust-auth，包含三个模块：auth（注册登录服务核心）、auth-common（功能模块）、auth-gateway（网关服务），另有 docs 与 logs。要跑的服务是网关服务 auth-gateway，端口 8782，启动命令 `java -jar auth-gateway-1.0.0.jar`。

## 小结

- 运行闭环：`npm run dev` 启动前端，品达/品达123 登录，组织与菜单数据动态来自数据库；请求链路是前端 → 网关（鉴权）→ 权限服务。
- 新项目开发七步：建库建表（pd_goods/pd_goods_info）→ pd-apps 下建 pd-goods 与 entity/server 子模块 → 实体 @TableName + DTO 继承实体 → server 模块拷配置（dozer、p6spy 等）并在 Nacos 建服务配置 → 启动类注解组合 + 配置类继承 BaseConfig → Mapper/Service/Controller 三层 → pd-gateway.yml 加 `/goods/**` 路由。
- 权限配置四件套：菜单（/goods、goodsinfo）、四条资源权限（请求方式与 Controller 注解一致）、测试角色只配商品菜单、新用户 user-001 绑定角色后只见授权菜单。
- 三个服务必须同 Nacos 分组（group: pinda-tms），否则网关路由找不到商品服务，页面加载数据失败。
- 已有项目集成：页面 iframe 内嵌（去掉自有菜单页）、请求改走 /api 网关前缀（proxy 指向 8760）、zuul 路由按 serviceId 或 url 转发、服务注册 Nacos；菜单/权限/角色配置与新项目相同。
- 注册登录服务 cust-auth 面向 C 端互联网用户，五种登录方式（账号密码、手机验证码、微信扫码、微博、QQ），登录成功自动注册，网关服务 auth-gateway 端口 8782。
