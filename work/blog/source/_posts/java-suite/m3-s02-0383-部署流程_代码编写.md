# 流程部署接口：把绘制好的 BPMN 文件交给引擎存进数据库

流程图已经在网页设计器里画完，导出成了 `请假.bpmn` 文件。可文件躺在本地磁盘上，引擎根本不认识它。要让引擎接管这条审批链，需要一次「部署」：前端把 BPMN 文件上传到服务端，服务端调用 Activiti 暴露的接口解析文件，把解析结果写进引擎库。听起来环节不少，落到代码上其实就是一个 Controller 接文件、一个 Service 调引擎，这一课把这两个类写出来。

## 先给结论

- 部署的本质是把 BPMN 文件交给 Activiti 解析并写入引擎库的部署相关表，Controller 只负责接住上传的文件。
- Controller 用 `MultipartFile` 接收文件，请求参数名固定为 `file`；返回统一的 `Result`，码用 `ResultCode.SUCCESS`。
- Service 里核心三步：`getOriginalFilename()` 拿文件名；`createDeployment().addBytes(文件名, 字节数组).tenantId(companyId)` 组装部署构建器；`deploy()` 真正落库并返回 `Deployment` 对象。
- `tenantId(companyId)` 是引擎的多租户支持，SaaS 场景下每个企业的流程互相隔离。
- `companyId` 测试阶段先写死一个值，正式代码继承 `BaseController`，直接用当前登录用户所属企业的 id。

## 一、部署在整条审批链路里的位置

画一张图先把位置摆正：

```mermaid
flowchart LR
    A["网页设计器绘制流程"] --> B["导出 bpmn 文件"]
    B -->|"POST /user/process/deploy"| C["ProcessController 接收 MultipartFile"]
    C --> D["ProcessService 组装 DeploymentBuilder"]
    D --> E["RepositoryService 引擎接口"]
    E --> F[("act 库 部署相关表")]
```

设计器只负责产出文件，`bpmn` 文件上传到工程后才算进入引擎的世界，引擎解析后把流程定义落到自己的库里。图中最右侧那一步是引擎内部完成的，代码里要写的只有中间的 Controller 与 Service 两层。

## 二、Controller：接住上传的 BPMN 文件

流程相关的接口统一放进一个流程控制器，路径约定以 `/user/process` 开头：

```java
package com.example.audit.controller;

@CrossOrigin
@RestController
@RequestMapping(value = "/user/process")
public class ProcessController extends BaseController {

    @Autowired
    private ProcessService processService;

    /**
     * 部署新流程
     * 前端将绘制好的流程模型图 bpmn 文件上传到方法中
     * 参数：上传的文件 MultipartFile
     */
    @RequestMapping(value = "/deploy", method = RequestMethod.POST)
    public Result deployProcess(@RequestParam("file") MultipartFile file) throws IOException {
        //companyId 继承自 BaseController，取当前登录用户所属企业的 id
        processService.deployProcess(file, companyId);
        return new Result(ResultCode.SUCCESS);
    }
}
```

几个细节展开说：

**第一，`@CrossOrigin` 解决跨域。** 前端工程与审批服务端口不同，浏览器会拦跨域请求，类上打这个注解放行。

**第二，文件参数是 `MultipartFile`。** Spring Boot 里一切上传的文件都用它承接，方法参数上再加 `@RequestParam("file")` 指定参数名。这里有个省略规则：如果方法参数名恰好也叫 `file`，与前端传的参数名一致，`@RequestParam` 可以不写；参数名对不上时就必须显式声明，否则 Spring 找不到要绑定的值。

**第三，`companyId` 来自父类。** 这个参数决定流程归属哪个企业，测试阶段可以先写死一个占位值跑通流程，但正式代码里它必须继承 `BaseController` 取登录用户对应的企业 id，SaaS 系统里每个请求都属于某个具体企业。

## 三、Service：三步完成部署

新建一个 `ProcessService`，打上 `@Service` 交给容器，把部署逻辑收进来：

```java
package com.example.audit.service;

@Service
public class ProcessService {

    @Autowired
    private RepositoryService repositoryService;

    /**
     * 流程部署
     * @param file      上传的 bpmn 文件
     * @param companyId 企业 id
     */
    public void deployProcess(MultipartFile file, String companyId) throws IOException {
        //1.获取上传的文件名，它会随部署记录一起保存进引擎库
        String fileName = file.getOriginalFilename();
        //2.通过 repositoryService 进行流程部署
        //分步写法：
        //DeploymentBuilder deploymentBuilder = repositoryService.createDeployment();
        //deploymentBuilder.addBytes(fileName, file.getBytes()); //文件名称与文件的字节数组
        //deploymentBuilder.tenantId(companyId);                 //设置租户 id
        //链式写法：一行组装完毕
        DeploymentBuilder deploymentBuilder = repositoryService.createDeployment()
                .addBytes(fileName, file.getBytes())
                .tenantId(companyId);
        //3.真正执行部署并打印部署结果
        Deployment deploy = deploymentBuilder.deploy();
        System.out.println(deploy);
    }
}
```

部署动作一共就三件事：

**第一，取文件名。** `file.getOriginalFilename()` 拿到上传文件的原始名称，比如 `请假.bpmn`。这个名字会作为资源名存进引擎库，后续查询部署资源时靠它辨认。

**第二，组装部署构建器。** `repositoryService.createDeployment()` 返回一个 `DeploymentBuilder`，它是本次部署的「构建者」：`addBytes(文件名, 字节数组)` 把文件内容挂上去，`file.getBytes()` 直接拿到字节，方法会抛 `IOException`，方法签名上要声明；`tenantId(companyId)` 把企业 id 作为租户标记挂上去。`DeploymentBuilder` 的每个配置方法都返回构建器自身，所以像代码里那样一路打点写成一行也完全可以，两种写法效果一致，链式写法更紧凑。

**第三，执行部署。** 前两步都只是在攒配置，调 `deploy()` 才真正触发引擎解析与落库，返回值 `Deployment` 代表这次部署，打印出来能看到引擎生成的部署 id 等信息，方便控制台确认。

## 四、tenantId：引擎自带的多租户标记

为什么部署还要带一个企业 id？因为这是 SaaS 系统，同一套审批服务上跑着多家企业的流程。A 企业部署的请假流程、B 企业部署的加班流程，都躺在同一个引擎库里，区分它们的依据就是租户 id。`tenantId(companyId)` 设置的值会写进部署记录与流程定义记录的租户列，之后查询流程定义、发起流程实例时都可以按租户过滤，各企业只能看到和处理自己的流程。引擎不替你做强制隔离，但把隔离所需的标记都留在了数据里，用不用、怎么用由业务层决定。

## 常见误区

- **前端参数名与后端对不上**：前端传 `fileName`、后端收 `file`，又没写 `@RequestParam` 指明，请求直接报参数缺失。保持两侧参数名一致最省事。
- **把部署当成启动流程**：部署只是把流程定义登记进引擎，此刻还没有任何流程实例在跑。员工真正提交请假单发起实例，是执行阶段的事。
- **`IOException` 不处理**：`file.getBytes()` 是受检异常，方法上不声明就编译不过，别为了图省事在循环里反复吞掉它。
- **`companyId` 一直写死**：测试期写死可以理解，带着写死的值上线，所有企业的流程都会挂到同一个租户名下，隔离形同虚设。
- **上传前不校验文件**：文件为空或不是合法的 BPMN 内容时，`deploy()` 才会报错且报错信息不直观，入口处先判空并校验扩展名能把问题挡在前面。

## 面试可能被问到的问题

1. 面试官追问：「Activiti 部署流程定义的核心 API 链路是什么？」
   答：注入 `RepositoryService`，调 `createDeployment()` 得到 `DeploymentBuilder`，用 `addBytes` 或 `addClasspathResource` 挂上 BPMN 资源，可再设置 `tenantId`、`name` 等属性，最后调 `deploy()` 执行部署，返回 `Deployment` 对象。构建器负责攒配置，`deploy()` 负责真正解析文件并落库。

2. 面试官追问：「`DeploymentBuilder` 为什么能一路链式调下去？」
   答：它的每个配置方法都返回当前构建器对象自身，配置一项返回一次 this，所以可以连续打点。这是典型的建造者模式，把一次复杂部署所需的零散参数收敛成一条可读的语句，最终以 `deploy()` 收口。

3. 面试官追问：「`addBytes` 与 `addClasspathResource` 有什么区别？」
   答：`addBytes` 直接接收字节数组，适合 Web 场景下处理用户上传的文件，`MultipartFile.getBytes()` 一转就能用；`addClasspathResource` 从类路径读资源，适合流程文件随工程打包发布的场景。一个面向上传，一个面向内置资源，底层最终都是把文件字节交给引擎保存。

4. 面试官追问：「多租户在 Activiti 里怎么落地？」
   答：部署时调 `tenantId(租户标识)`，该标识会写进部署、流程定义等记录的租户列；查询流程定义、发起实例时用 `processDefinitionTenantId` 之类的条件按租户过滤。引擎负责存取标记，隔离逻辑由业务层组合查询条件来实现，本项目里租户标识就是企业 id。

5. 面试官追问：「部署成功后，引擎库里发生了哪些变化？」
   答：部署记录表 `ACT_RE_DEPLOYMENT` 新增一条，代表这次部署动作；资源表 `ACT_GE_BYTEARRAY` 存进 BPMN 文件的字节内容；流程定义表 `ACT_RE_PROCDEF` 新增解析后的流程定义记录。三张表相互关联，后续按流程定义发起实例用的就是最后那张表里的数据。
