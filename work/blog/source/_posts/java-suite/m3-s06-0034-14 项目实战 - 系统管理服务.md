# 项目实战：系统管理服务跑通第一组管理接口

> 🔒 安全提示：文中示例的口令/密钥均为课程教学环境演示口径，生产环境的安全要求见《安全与合规须知》。

day2 的基础设施已经齐了：注册中心在 8001 守着，用户服务管登录发 token，网关在 8080 统一分发。还缺一块：企业、仓库、主机、设备这些平台基础数据没有归属的服务，前端的管理页面无接口可调。这一节补上系统管理服务 `cold-admin`，它是 day2 的收官工程，分层套路与用户服务完全同构，做完它，「注册中心加网关加业务服务」的最小微服务闭环就完整了。

## 先给结论

- `cold-admin` 承担企业、仓库、主机、设备四类基础数据的增删改查，外加首页统计与操作日志两个聚合接口。
- 分层结构：Controller 与 Service 在 `cold-admin` 工程里，实体与 Dao 放公共工程 `cold-common`，多个服务共享同一套实体。
- 持久层用 MyBatis-Plus，单表 CRUD 不写 SQL，分页功能要显式注册 `PaginationInterceptor` 分页插件。
- 数据库叫 `cold-admin`，五张表，随包 SQL 文件一键导入。
- 网关追加一条 `cold-admin-router` 路由之后，从 8080 调 `/cold/admin/company/list` 即可跑通前端到数据库的全链路。

## 服务边界与数据模型

系统管理服务管的是「冷库资产的台账」：哪些企业在用这套平台，每家企业有几个仓库，每个仓库部署了哪些采集主机，每台主机下挂了哪些计量设备。四类实体是一条从属链，一企业多仓库，一仓库多主机，一主机多设备：

```mermaid
flowchart LR
    C["cz_company 企业"] -- "1 对 多" --> W["cz_warehouse 仓库"]
    W -- "1 对 多" --> H["cz_host 主机"]
    H -- "1 对 多" --> M["cz_meter 设备"]
    F["Flink 实时计算"] -. "结果写入" -.> R["cz_message_realtime 实时消息"]
```

图里第五张表 `cz_message_realtime` 单独画在旁边是有意为之：它是实时计算链路的落库表，设备上报的数据经 Flink 计算后写进来，系统管理服务只读不写，导入 SQL 时一起建好即可，增删改查逻辑不用为它操心。设备模拟器属于后续章节的内容，本节的四个实体全部是最基础的单表维护。

## 建库、依赖与工程骨架

准备工作从数据库开始。在 MySQL 客户端里新建名为 `cold-admin` 的库，选择对应编码后导入资料包里的 `cold-admin.sql`，五张表连同索引一次到位，课程演示环境用 root 加 123456 登录即可。

工程创建与用户服务同一路径：Spring 骨架生成器生成 Maven 工程，Artifact 取名 `cold-admin`，依赖勾 Eureka Discovery Client，随后在 `pom.xml` 里补上对本平台公共工程与 MyBatis-Plus 的引用，真实工程的关键依赖如下：

```xml
<dependencies>
    <dependency>
        <groupId>com.study.coldchain</groupId>
        <artifactId>cold-common</artifactId>
        <version>0.0.1-SNAPSHOT</version>
    </dependency>
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-netflix-eureka-client</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
        <groupId>com.baomidou</groupId>
        <artifactId>mybatis-plus-boot-starter</artifactId>
        <version>3.1.2</version>
    </dependency>
    <dependency>
        <groupId>mysql</groupId>
        <artifactId>mysql-connector-java</artifactId>
        <scope>runtime</scope>
    </dependency>
</dependencies>
```

`cold-common` 这一引是整套工程的复用要点：企业的 `CompanyEntity`、仓库的 `WarehouseEntity`、主机的 `HostEntity`、设备的 `MeterEntity` 以及对应的 Dao 接口都放在公共工程里，实体带着 `@TableName` 注解直接映射五张表，Dao 继承 MyBatis-Plus 的 `BaseMapper` 就有了全套单表操作。以企业为例：

```java
package com.study.coldchain.common.admin.entity;

@Data
@TableName("cz_company")
public class CompanyEntity implements Serializable {
    @TableId
    private String id;              // 主键，字符串 UUID
    private String company;         // 企业名称
    private String companyaddress;  // 公司地址
    private String companytype;     // 企业类型
    // 其余字段：简称、编号、电话、负责人、网址等
}

@Mapper
public interface CompanyDao extends BaseMapper<CompanyEntity> {
}
```

配置文件两处关键。主配置声明身份与端口：服务名 `cold-admin`、端口 8181、context-path 依旧用 `/cold` 与全平台对齐，再配上 MyBatis-Plus 的驼峰转换、逻辑删除值等全局策略。环境配置接数据库，真实工程用的是 Druid 连接池：

```yaml
spring:
  datasource:
    type: com.alibaba.druid.pool.DruidDataSource
    druid:
      driver-class-name: com.mysql.jdbc.Driver
      url: jdbc:mysql://localhost:3306/cold-admin?useUnicode=true&characterEncoding=UTF-8&useSSL=false
      username: root
      password: 123456      # 课程演示环境；随包配置为内网地址与专用账号
      initial-size: 10
      max-active: 100
      min-idle: 10
```

启动类与用户服务一模一样：`@SpringBootApplication` 加 `@EnableDiscoveryClient`，运行后注册中心里出现 `COLD-ADMIN`。

## Controller：一套标准的 CRUD 写法

管理类接口的形态高度一致，列表分页、单条详情、保存、修改、删除五个动作，企业的 Controller 是典型样本：

```java
@RestController
@RequestMapping("admin/company")
public class CompanyController {
    @Autowired
    private CompanyService companyService;

    /** 列表：page、pagesize、company（模糊查询）走查询参数 */
    @RequestMapping("/list")
    public Result list(@RequestParam Map<String, Object> params) {
        PageUtils page = companyService.queryPage(params);
        return Result.ok(page.getPageMap());
    }

    /** 详情 */
    @RequestMapping("/info/{id}")
    public Result info(@PathVariable("id") String id) {
        CompanyEntity company = companyService.getById(id);
        return Result.ok().put("company", company);
    }

    /** 保存：主键用 UUID 生成 */
    @RequestMapping("/save")
    public Result save(@RequestBody CompanyEntity company) {
        company.setId(UUID.randomUUID().toString());
        companyService.save(company);
        return Result.ok();
    }

    /** 修改与删除 */
    @RequestMapping("/update")
    public Result update(@RequestBody CompanyEntity company) {
        companyService.updateById(company);
        return Result.ok();
    }

    @RequestMapping("/delete")
    public Result delete(String id) {
        companyService.removeById(id);
        return Result.ok();
    }
}
```

返回值统一走公共工程里的 `Result`，它继承自 Map，默认带 `code` 与 `msg` 两个字段，`put` 方法链式追加业务数据，前端拿到的东西结构永远一致。`save` 之前手工 `UUID.randomUUID()` 生成主键，对应 MyBatis-Plus 主键策略里的 `INPUT`（由使用者输入），而不是常见的数据库自增。

## Service 与分页插件

Service 层继承 MyBatis-Plus 的 `ServiceImpl`，通用增删改查直接复用父类方法，唯一需要自己写的是分页查询。企业的实现如下：

```java
@Service("companyService")
public class CompanyServiceImpl
        extends ServiceImpl<CompanyDao, CompanyEntity> implements CompanyService {

    @Override
    public PageUtils queryPage(Map<String, Object> params) {
        int current = params.get("page") == null ? 1 : Integer.valueOf(params.get("page").toString());
        int size = params.get("pagesize") == null ? 10 : Integer.valueOf(params.get("pagesize").toString());
        Page<CompanyEntity> page = new Page<>(current, size);

        // 企业名称模糊查询，条件为空时 like 空串等价于查全部
        String company = params.get("company") == null ? "" : params.get("company").toString();
        QueryWrapper<CompanyEntity> wrapper = new QueryWrapper<>();
        wrapper.lambda().like(CompanyEntity::getCompany, company);

        IPage<CompanyEntity> result = this.page(page, wrapper);
        return new PageUtils(result);
    }
}
```

从查询参数里取页码与页大小构造 `Page` 对象，名称条件用 `QueryWrapper` 的 lambda 写法拼 like，交给 `this.page` 执行后包成公共工程里的 `PageUtils`，它把总记录数、总页数、当前页、数据列表打包成前端要的结构。分页能真正生效还有一个前提：MyBatis-Plus 的分页是插件式实现，必须注册拦截器，配置类只有几行：

```java
@Configuration
public class MybatisPlusConfig {

    @Bean
    public PaginationInterceptor paginationInterceptor() {
        return new PaginationInterceptor();
    }
}
```

仓库、主机、设备三个 Controller 与 Service 完全是同一套模板改个实体名，课程没有逐个演示代码，照抄企业这套即可。

## 注册进网关，全链路验证

服务本身通了之后，把它挂到网关的规则表里。在网关工程的 `spring.cloud.gateway.routes` 下追加一条，格式与用户服务那条完全一致：

```yaml
      - id: cold-admin-router
        uri: lb://cold-admin
        predicates:
        - Path=/cold/admin/**
```

启动顺序沿用前面的习惯：注册中心、`cold-admin`、网关依次起。注册中心 Dashboard 出现 `COLD-ADMIN` 且状态 UP 后，Postman 里把请求地址从 8181 换成网关的 8080，路径不变，列表接口带着 `page` 与 `pagesize` 参数能正常翻页返回，全链路即告打通。至此 day2 收官：注册中心、用户服务、系统管理服务、网关四个进程各司其职，前端页面从此只需要认识 8080 一个端口。

## 常见误区

- **分页插件没注册。** 错例是只写 `this.page` 就以为有分页。正解是 `PaginationInterceptor` 不装，MyBatis-Plus 不会改写 SQL，`page` 参数形同虚设，一次把全表查出来，数据量一大就是事故。
- **实体与 Dao 写进业务工程。** 错例是把 `CompanyEntity` 建在 `cold-admin` 里。正解是放公共工程 `cold-common`，用户服务、监控服务将来都要引用同一套实体，复制一份等于埋下字段不同步的雷。
- **主键策略与代码打架。** 错例是配置了自增却在代码里手工生成 UUID。正解是本平台主键策略为 `INPUT`，实体主键是字符串，保存前 `UUID.randomUUID()` 赋值；若想交给框架生成，就换对应的策略配置，两处必须一致。
- **网关路由缩进错位。** 错例是追加 `cold-admin-router` 时横杠与子键没对齐。正解是严格对齐列表层级，这类错不报异常，只会让 `/cold/admin/**` 全部 404，对照既有规则抄格式最稳。

## 面试可能被问到的问题

1. 面试官追问：「MyBatis-Plus 和 MyBatis 是什么关系？」
   答：MyBatis-Plus 在 MyBatis 之上做增强而不做改变，通用 CRUD 由 `BaseMapper` 与 `ServiceImpl` 提供，单表操作不用写 SQL；复杂联表查询仍然写 XML 映射文件。引入它不需要替换 MyBatis 的任何配置，原有的 Mapper 体系照常工作。
2. 面试官追问：「分页插件是怎么把分页做进去的？」
   答：它是一个 MyBatis 拦截器，拦截到带 `Page` 参数的查询后，先拼一条 count 语句拿总数，再按数据库方言在原 SQL 后追加 limit 与偏移量。所以分页生效依赖插件注册，也依赖正确的方言配置；`IPage` 对象里回填总记录数与页数。
3. 面试官追问：「实体为什么放公共工程而不是各业务服务里？」
   答：平台里多个服务消费同一批表，比如实时计算与系统管理都会碰实时消息表。实体与 Dao 放 `cold-common` 打成 jar 依赖，各服务引用同一份定义，字段变更只改一处；代价是公共工程要控制好稳定性，它一改全体重新编译，所以公共实体要按模块分包、谨慎演进。
4. 面试官追问：「主键用字符串 UUID 还是数据库自增，怎么权衡？」
   答：UUID 无需数据库参与，分库分表、多端预生成主键都方便，且不暴露业务量；代价是字符串索引比整型大、插入时页分裂概率高。单库小表用自增简单高效，分布式多实例写入场景 UUID 或雪花算法更合适。本平台是字符串主键加代码生成 UUID，属于典型的分布式友好选择。
5. 面试官追问：「从浏览器点一下列表页到数据库，这条链路经过哪些组件？」
   答：浏览器把请求发给网关 8080，网关按路由断言匹配 `/cold/admin/**`，从注册中心拿到 `cold-admin` 的实例列表做负载均衡转发；`cold-admin` 的 Controller 接收参数，Service 组装分页与查询条件，MyBatis-Plus 生成 SQL 经 Druid 连接池执行，结果包成 `PageUtils` 与 `Result` 返回，网关原样回传给前端。每一环各管一件事，排查问题时按这条链逐段定位。
