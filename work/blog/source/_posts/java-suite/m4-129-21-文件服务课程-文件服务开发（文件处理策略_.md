# 文件处理策略进阶：本地、FastDFS、阿里云 OSS 三套实现与上传接口开篇

文件服务这一章的核心是「一套抽象、三种实现」。上一节把策略骨架搭好之后，这一段内容先把本地存储的 `LocalServiceImpl` 写完（上传写盘、按路径删除），再照同样的套路实现 FastDFS 策略和阿里云 OSS 策略，最后明确第一个接口——附件上传的接口文档，为接口开发开篇。三条策略全部由 `pinda.file.type` 一个配置项驱动切换，类的结构完全对称。

## 先给结论

- 策略切换靠条件注解：每个配置类都标 `@ConditionalOnProperty(name = "pinda.file.type", havingValue = "...")`，取值分别为 `LOCAL`、`FAST_DFS`、`ALI`，配置哪个值，Spring 就实例化哪个策略处理类，业务代码无感知。
- 本地策略上传五步：`buildClient()` 取 local 配置 → UUID 生成唯一文件名 → 按年月生成日期目录 → `Paths.get` 拼 endpoint/bucketName/日期目录得到绝对路径 → `FileUtils.writeByteArrayToFile` 写盘；写完把 url、filename、relativePath 补进 File 对象供入库。
- FastDFS 上传反而更简单：注入 `FastFileStorageClient`，一行 `storageClient.uploadFile(流, 大小, 后缀, null)` 返回 `StorePath`，URL = uriPrefix + `getFullPath()`，组和远程路径分别存进 group、path 字段。
- FastDFS 文件访问依赖 Nginx：`uriPrefix` 配的是 `http://172.17.0.115:8188/`，即 Nginx 提供的 HTTP 服务地址；`tracker-list` 配 `172.17.0.115:22122`，服务器课程环境已提前搭好。
- 阿里云 OSS 是模板化代码：`OSSClientBuilder` 构建客户端，`doesBucketExist` 兜底建桶，`ObjectMetadata` 设置 Content-Disposition 与 Content-Type，封装 `PutObjectRequest` 后 `putObject`；删除调 `deleteObject(空间名, 相对路径/文件名)`。
- 上传附件接口定型为 `POST /attachment/upload`、multipart/form-data，参数有 file、bizId、bizType、isSingle，响应 `R<AttachmentDTO>`；接口只做两件事——把文件存进配置指定的存储位置，把文件信息写入 pd_attachment 附件表。

## 本地策略收尾：写盘、拼 URL、删除

本地策略的上传方法延续上一节的思路，从配置属性类里取值，再一步步构造存储路径：

```java
@Override
public void uploadFile(File file, MultipartFile multipartFile) throws Exception {
    buildClient(); // properties = fileProperties.getLocal()，不调用它 properties 没有值
    String endpoint = properties.getEndpoint();
    String bucketName = properties.getBucketName();
    String uriPrefix = properties.getUriPrefix();

    // 使用UUID为文件生成新文件名，防止重复
    String fileName = UUID.randomUUID().toString() + StrPool.DOT + file.getExt();

    // 日期目录：年/月两层
    String relativePath = LocalDateTime.now()
            .format(DateTimeFormatter.ofPattern(DateUtils.DEFAULT_MONTH_FORMAT));

    // 上传文件存储的绝对目录：D:/uploadFiles/oss-file-service/2020/05
    String absolutePath = Paths.get(endpoint, bucketName, relativePath).toString();

    // 目标输出文件：绝对目录 + 唯一文件名
    java.io.File outFile = new java.io.File(Paths.get(absolutePath, fileName).toString());

    // 向目标文件写入数据
    FileUtils.writeByteArrayToFile(outFile, multipartFile.getBytes());
}
```

三段路径用 `Paths.get` 拼接而不是手动连字符串，是因为不同操作系统的目录分隔符不一样，`Paths.get` 会按当前系统的分隔符处理。写文件用的是 commons-io 提供的 `FileUtils.writeByteArrayToFile`，参数依次是目标文件和字节数组（从 `multipartFile.getBytes()` 读出）。异常不在 service 里 try-catch，直接往外抛——父类抽象方法签名上已经声明了 `throws Exception`，前后统一。

写盘完成还没结束，上传后的文件要保存进数据库，能确定下来的属性此时要补进 File 对象：

```java
// 文件上传完成后，设置文件相关信息，用于保存到数据库
String url = new StringBuilder(getUriPrefix())
        .append(StrPool.SLASH)
        .append(properties.getBucketName())
        .append(StrPool.SLASH)
        .append(relativePath)
        .append(StrPool.SLASH)
        .append(fileName)
        .toString();
url = StrUtil.replace(url, "\\", StrPool.SLASH); // 防止日期目录带反斜线

file.setUrl(url);
file.setFilename(fileName);          // UUID生成的唯一文件名
file.setRelativePath(relativePath);  // 日期目录
```

URL 的结构是「uriPrefix / bucketName / 年月 / 文件名」，其中 uriPrefix 不为空就直接取配置值。最后多做一步 `replace`：URL 是 HTTP 访问地址，一定用正斜线，如果路径里混进了 Windows 反斜线要统一替换。文件名这里存的是 UUID 生成的唯一名，用户上传的原始文件名也没有扔，对应的是 File 对象的 submittedFileName，同样要入库。另外方法返回值从 `File` 改成了 `void`——传进来的 File 对象是父类构造好传进来的，改它本身就行，抽象父类里的方法签名同步改成 void，保持一致。

删除方法则反过来：上传时把年月目录、唯一文件名存进了数据库，删除时从传进来的 `FileDeleteDO` 里取出来，重新拼出绝对磁盘路径：

```java
@Override
public void delete(FileDeleteDO fileDeleteDO) {
    // 拼接要删除文件的绝对磁盘路径
    String filePath = Paths.get(properties.getEndpoint(),
            properties.getBucketName(),
            fileDeleteDO.getRelativePath(), // 上传时保存的年月目录
            fileDeleteDO.getFileName()).toString(); // UUID唯一文件名，不是原始文件名
    java.io.File file = new java.io.File(filePath);
    FileUtils.deleteQuietly(file);
}
```

这里要划清一条边界：策略处理类只关注文件本身的处理（上传、删除），上传后保存数据、删除后操作数据库这类动作属于业务层的封装，不应该出现在这个类里。

## FastDFS 策略：客户端一行搞定上传

FastDFS 策略的套路与 local 完全一致：新建 `FastDfsAutoConfigure` 配置类，加上 `@Configuration`、`@Slf4j`、`@EnableConfigurationProperties(FileServerProperties.class)`，再用条件注解把触发值换成 FAST_DFS：

```java
@Slf4j
@Configuration
@EnableConfigurationProperties(FileServerProperties.class)
@ConditionalOnProperty(name = "pinda.file.type", havingValue = "FAST_DFS")
public class FastDfsAutoConfigure {
}
```

配套的策略处理类 `FastDfsServiceImpl` 继承 `AbstractFileStrategy`，实现 uploadFile 和 delete 两个抽象方法，别忘了 `@Service` 注解——不加它 Spring 不会实例化这个类。

使用 FastDFS 前要先看配置。yml 里有一段不是自定义配置，而是 fastdfs-client 依赖包要求的标准配置段，重点是 tracker 地址，其余是连接池等常规项：

```yaml
# FastDFS自身配置（由fastdfs-client提供，非自定义）
soTimeout: 1500
connectTimeout: 600
thumb-image:
  width: 150
  height: 150
tracker-list: 172.17.0.115:22122   # tracker服务的IP与端口
pool:
  max-total: 153
  max-wait-millis: 102
```

同时把 `pinda.file.type` 设为 `FAST_DFS`，并配置 `uriPrefix: http://172.17.0.115:8188/`。这个前缀指向的是 Nginx 服务——FastDFS 本身不提供 HTTP 访问能力，要结合 Nginx 的 HTTP 能力才能访问分布式文件系统里存的文件。课程环境里 FastDFS 已提前搭好在远程服务器上并启动成功，课程重点还是文件服务的上传、删除等操作，FastDFS 本身作为已知知识直接使用。

代码里先注入客户端对象，作用类似操作 Redis 时的 Jedis：

```java
@Autowired
private FastFileStorageClient storageClient;
```

有了它，上传就只有一行核心调用，文件名生成、路径组织、文件拷贝这些细节全被客户端封装掉了：

```java
@Override
public void uploadFile(File file, MultipartFile multipartFile) throws Exception {
    // 输入流、文件大小、后缀、元数据（没有就传null）
    StorePath storePath = storageClient.uploadFile(
            multipartFile.getInputStream(),
            multipartFile.getSize(),
            file.getExt(),
            null);

    // 上传完成后设置文件信息，用于保存到数据库
    file.setUrl(fileProperties.getUriPrefix() + storePath.getFullPath());
    file.setGroup(storePath.getGroup()); // FastDFS组，由系统自动分配
    file.setPath(storePath.getPath());  // 远程文件名
}
```

返回的 `StorePath` 携带了分组信息：FastDFS 按组存储，分到哪个组不用关心，那是分布式文件系统自己分配的，`getGroup()` 拿到后存库；`getFullPath()` 是「组 + 路径」的完整路径，拼上 uriPrefix 就是完整访问 URL。删除更直接，上传时存的 group 和 path 此时派上用场：

```java
@Override
public void delete(FileDeleteDO fileDeleteDO) {
    storageClient.deleteFile(fileDeleteDO.getGroup(), fileDeleteDO.getPath());
}
```

## 阿里云 OSS 策略：模板代码加配置

第三种是阿里云 OSS（Object Storage Service，对象存储服务）。配置类 `AliOssAutoConfigure` 还是那四个注解，条件注解的值换成 `ALI`；`AliServiceImpl` 同样继承 `AbstractFileStrategy`。要连阿里云，需要先到阿里云平台申请账号和存储空间（bucket），对应四个配置项：

```yaml
pinda:
  file:
    type: ALI
    ali:
      bucket-name: bladex-loan
      endpoint: http://oss-cn-qingdao.aliyuncs.com  # 开通OSS后分配的访问地址
      access-key-id: LTAI4fhtm...      # 账号，鉴权用
      access-key-secret: SSUJ5QapP...  # 密码，鉴权用
```

不做鉴权的话，任何人都能往申请的空间里传文件，显然不合适。官方示例代码提供了 `OSS` 客户端对象，创建它需要 endpoint、accessKeyId、accessKeySecret 三个参数，都能从配置文件读到，封装成 `buildClient()`：

```java
private OSS buildClient() {
    properties = fileProperties.getAli();
    return new OSSClientBuilder().build(
            properties.getEndpoint(),
            properties.getAccessKeyId(),
            properties.getAccessKeySecret());
}
```

上传方法参照官方示例改造，代码量明显偏多，属于模板代码：

```java
@Override
public void uploadFile(File file, MultipartFile multipartFile) throws Exception {
    OSS client = buildClient();
    String bucketName = properties.getBucketName();
    if (!client.doesBucketExist(bucketName)) { // 防御：空间不存在就创建
        client.createBucket(bucketName);
    }
    String fileName = UUID.randomUUID().toString() + StrPool.DOT + file.getExt();
    // 日期目录，与本地策略一致
    String relativePath = LocalDateTime.now()
            .format(DateTimeFormatter.ofPattern(DateUtils.DEFAULT_MONTH_FORMAT));
    String relativeFileName = relativePath + StrPool.SLASH + fileName;
    relativeFileName = StrUtil.replace(relativeFileName, "\\", StrPool.SLASH);

    // 对象元数据：附件形式上传，文件名用原始文件名
    ObjectMetadata metadata = new ObjectMetadata();
    metadata.setContentDisposition("attachment;filename=" + file.getSubmittedFileName());
    metadata.setContentType(file.getContextType());

    // 封装上传请求：空间名、相对文件名、输入流、元数据
    PutObjectRequest request = new PutObjectRequest(
            bucketName, relativeFileName, multipartFile.getInputStream(), metadata);
    PutObjectResult result = client.putObject(request); // 真正的上传只有这一句
    log.info("上传结果：{}", JSONObject.toJSONString(result));

    // 上传完成后设置文件信息，用于写入文件表
    String url = getUriPrefix() + StrPool.SLASH + relativeFileName;
    url = StrUtil.replace(url, "\\", StrPool.SLASH);
    file.setUrl(url);
    file.setFilename(fileName);
    file.setRelativePath(relativePath);
    file.setGroup(result.getETag());
    file.setPath(result.getRequestId());
    client.shutdown(); // 客户端相当于连接对象，用完关闭
}
```

前面一大堆代码都是在为 `putObject` 这一句做准备。还有一个针对阿里云特点的细节：子类要覆盖父类的 `getUriPrefix()`，因为 OSS 的 endpoint 可能是 https 的，协议要动态判断，最终拼出的是「协议 + bucketName + . + endpoint 域名」这种 OSS 风格的访问地址：

```java
@Override
protected String getUriPrefix() {
    if (StringUtils.isNotEmpty(properties.getUriPrefix())) {
        return properties.getUriPrefix();
    }
    String prefix = properties.getEndpoint().contains("https://") ? "https://" : "http://";
    return prefix + properties.getBucketName() + "." + properties.getEndpoint().replaceFirst(prefix, "");
}
```

删除文件对应官方示例的 `deleteObject` 方法，除了指定从哪个空间删，还要指定文件的相对路径——即上传时保存的日期目录加文件名，这个串是包含后缀在内的完整路径名：

```java
@Override
public void delete(FileDeleteDO fileDeleteDO) {
    OSS client = buildClient();
    client.deleteObject(properties.getBucketName(),
            fileDeleteDO.getRelativePath() + StrPool.SLASH + fileDeleteDO.getFileName());
    client.shutdown();
}
```

## 上传附件接口：先定契约再写实现

三种策略写完，就可以编写第一个接口了——上传附件。按接口文档，它主要完成两个操作：一是把客户端提交的文件上传到指定存储位置，具体存哪里由配置文件的 `type` 决定（FastDFS、本地还是阿里云）；二是把上传的文件信息保存到数据库的 pd_attachment 附件表。一句话概括：文件存好，信息记好。

接口契约如下：客户端以 POST 方式请求 `/attachment/upload`，因为是文件上传，请求的数据类型是 multipart/form-data。请求参数有四个：

| 参数 | 说明 |
| --- | --- |
| file | 附件本身，formData 类型，MultipartFile 数组 |
| bizId | 业务 id |
| bizType | 业务类型 |
| isSingle | 是否单文件 |

文件服务是一个平台，各业务系统都会来调这个接口上传文件，所以需要 bizId 和 bizType 两个字段区分不同的业务：这个文件来自哪个系统、代表什么含义，靠这两个字段判断。文件 id 通常不传，传了就表示是修改操作。isSingle 用于区分当前业务下是单个文件还是多个文件。响应状态码方面，200 表示成功，40001 是会话超时需重新登录，40003 是缺少 token 参数，另外还有系统繁忙、服务超时等定义。

响应体封装在 `R` 对象里（R 代表 return），泛型是 `AttachmentDTO`。这个 DTO 本身没有多余字段，继承自附件类 Attachment，文件上传成功后要把附件的完整信息返回给客户端页面——bizId、bizType、dataType、relativePath、url、icon、createMonth 这些字段都在父类里。

## 小结

这一段把文件服务的三种存储策略全部落地。三种实现的骨架完全对称：一个标注 `@ConditionalOnProperty` 的配置类负责按 `pinda.file.type` 的取值决定是否生效，一个继承 `AbstractFileStrategy` 的处理类实现 uploadFile 和 delete 两个抽象方法，差异只在这两个方法内部——本地策略自己控制文件名、路径、写盘的所有细节；FastDFS 把细节交给 `FastFileStorageClient`，反而最简单；阿里云 OSS 则是一套官方示例改造来的模板代码，多了元数据封装和客户端关闭两个环节。上传完成后统一要做的是把 url、文件名、路径、组等信息补进 File 对象交给业务层入库，数据库操作不进策略类。接口层面，上传附件的契约已经定死：POST /attachment/upload、multipart/form-data、bizId 加 bizType 区分业务、响应 `R<AttachmentDTO>`。下一节就按这份契约实现真正的接口代码。
