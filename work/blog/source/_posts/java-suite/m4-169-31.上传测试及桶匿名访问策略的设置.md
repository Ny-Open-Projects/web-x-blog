# 立可得2.0收尾：MinIO上传测试与桶匿名访问策略、IService清爽写法与优雅自动填充

立可得2.0第二章到这里收束，剩下三件事：用Postman把MinIO文件上传跑通，顺带解决"地址打不开图片"的桶策略问题；再看MyBatis-Plus给业务层带来的两处简化——IService接口让增删改查告别手写，MetaObjectHandler把create_time/update_time的赋值收敛到一处。三件事都不大，但都是项目里每天要碰的日常。

## 先给结论

- 上传接口在售货机微服务（vms-service，端口9004）：POST /sku/fileUpload，参数名取`@RequestParam`里的"fileName"，Postman用form-data且类型要切成File。
- 上传成功返回图片地址（http://192.168.200.128:9001/lkd/vms/logo.png），但浏览器首次打开会被弹回MinIO控制台——不是代码有错，是桶没有配匿名访问策略。
- 解决办法：在MinIO控制台给lkd桶加一条匿名访问规则，prefix填`*`、access选readonly，之后地址即可公开访问。
- BaseMapper简化DAO层人所共知，IService还能简化业务层：接口继承`IService<T>`，基础增删改查不再手写，只声明特殊的业务方法。
- 实现类继承`ServiceImpl<Dao, Entity>`，配合LambdaQueryWrapper构建条件，几行完成分页模糊查询。
- 实现MetaObjectHandler的insertFill/updateFill两个方法即可自动填充时间字段：新增时createTime和updateTime都写当前时间，修改时只更新updateTime，业务代码里再也不用手动set。

## Postman测上传：参数名和form-data是两个易错点

上传代码在售货机微服务里，测试前先把它启动起来。入口是SkuController的fileUpload方法：

```java
@PostMapping(value = "/fileUpload")
@ResponseBody
public String uploadImage(@RequestParam("fileName") MultipartFile file) {
    return fileManager.uploadFile(file);
}
```

Postman里的操作步骤：

1. 新建请求，地址填`http://localhost:9004/sku/fileUpload`——9004是vms-service的server.port，`/sku`是控制器的映射前缀。
2. Body选form-data，key填`fileName`。这个名字必须和方法签名里`@RequestParam("fileName")`一致，否则后端接不到文件。
3. key的类型从Text切换成File，value处出现Select Files按钮，选中一个图片文件（演示用的logo.png）。
4. 点Send，返回200，响应体就是上传后文件的访问地址。

把地址复制出来，形如`http://192.168.200.128:9001/lkd/vms/logo.png`：9001是MinIO端口，lkd是桶名，vms是文件前缀路径。

## 图片打不开？给桶配匿名访问策略

第一次验证往往撞上怪现象：地址粘到浏览器，看到的不是图片，而是被带回了MinIO控制台登录页。

原因在桶身上。lkd桶刚建立时没有任何访问策略，默认不允许匿名访问，浏览器直接GET这个URL自然进不来。这不是代码问题，改一行代码都没用。

解决办法在MinIO控制台里做：

1. 进入Buckets页面，找到lkd桶，点右上角的三个点菜单。
2. 选匿名访问策略的编辑项（Edit Policy / 编辑策略）。
3. prefix输入`*`，表示桶下所有对象路径都生效。
4. access选readonly（只读），点Add保存。

配完策略再开一个新窗口访问刚才的地址，图片正常显示。这一步过了，上传返回的URL才算真正可用，前端页面里就可以直接引用了。

## IService：业务层也能像DAO层一样清爽

用MyBatis-Plus，大家都知道定义一个接口继承BaseMapper，DAO层基本的增删改查方法就不用写了。但很多人不知道，业务层（service层）也可以用同样的思路简化。

立可得1.0里，商品分类的业务接口是这么定义的：

```java
public interface SkuClassService {
    SkuClassEntity findById(Integer id);
    boolean add(SkuClassEntity skuClass);
    boolean update(SkuClassEntity skuClassEntity);
    boolean delete(Integer id);
    List<SkuClassEntity> findList(Map searchMap);
    Page<SkuClassEntity> findPage(long pageIndex, long pageSize, Map searchMap);
}
```

接口里先声明一堆增删改查方法，实现类再挨个实现——这是1.0的做法，重复且无趣。

2.0改用MyBatis-Plus的IService接口，同一个SkuClassService变成：

```java
public interface SkuClassService extends IService<SkuClassEntity> {
    Pager<SkuClassEntity> findPage(long pageIndex, long pageSize, String className);
}
```

父接口里已经定义好了全部基础增删改查方法，这里只剩一个确实特殊的findPage。实现类也跟着清爽：

```java
@Service
public class SkuClassServiceImpl extends ServiceImpl<SkuClassDao, SkuClassEntity>
        implements SkuClassService {

    @Override
    public Pager<SkuClassEntity> findPage(long pageIndex, long pageSize, String className) {
        var page = new Page<SkuClassEntity>(pageIndex, pageSize);
        if (Strings.isNullOrEmpty(className)) {
            this.page(page);                    // 无条件分页
        } else {
            var qw = new LambdaQueryWrapper<SkuClassEntity>();
            qw.like(SkuClassEntity::getClassName, className);  // 名称模糊查询
            this.page(page, qw);
        }
        // ……封装为 Pager 返回
    }
}
```

实现类只需实现自己声明的方法，条件构建交给LambdaQueryWrapper，`like(SkuClassEntity::getClassName, className)`一行完成模糊匹配，分页直接调`this.page(page, qw)`。开发量集中在真正的业务逻辑上，这就是"代码清爽之美"。

## 优雅的自动填充：MetaObjectHandler一处搞定

工程里很多表有相同的字段和相同的逻辑：点位表（node）、货道表（channel）、策略表（strategy）都带create_time和update_time。规则也一样——记录创建时写createTime，修改时写updateTime。如果每段业务代码都手动给这两个属性赋值，既麻烦也不优雅。

MyBatis-Plus为此提供了MetaObjectHandler接口，写一个类实现它的两个方法就能自动填充。课程把这个类放在公共模块service_common的mybatis包（com.lkd.mybatis）下，所有微服务都能共享：

```java
@Slf4j
@Component
public class GeneralMetaObjectHandler implements MetaObjectHandler {

    @Override
    public void insertFill(MetaObject metaObject) {
        try {
            this.setFieldValByPropertyName("createTime", LocalDateTime.now(), metaObject);
            this.updateFill(metaObject);   // 新增时 updateTime 同样要记当前时间
        } catch (Exception e) {
            log.error("GeneralMetaObjectHandler error", e);
        }
    }

    @Override
    public void updateFill(MetaObject metaObject) {
        try {
            this.setFieldValByPropertyName("updateTime", LocalDateTime.now(), metaObject);
        } catch (Exception e) {
            log.error("GeneralMetaObjectHandler error", e);
        }
    }
}
```

两个要点：

- `setFieldValByPropertyName`有三个参数：要填充的字段名、填充的值、metaObject（当前这条新增/修改记录对应的对象）。
- insertFill里除了填createTime，还调用了一次updateFill。因为新增的时候createTime和updateTime都应该记录当前时间；而修改的时候只需要更新updateTime。

填充逻辑写一处就够，实体类和业务方法都不用动。以点位为例，NodeEntity用`@TableName("th_node")`映射表、`@TableField`映射各字段，NodeServiceImpl的新增方法里找不到任何对时间的赋值——干净得很。

验证过程：启动售货机微服务，测试脚本直连9004端口（不走网关，脚本本身也是直接测微服务的）。用node.http脚本调新增点位接口，把名字改成"中山商场"，发送请求后刷新数据库里的th_node表：多出一条"中山商场"记录，create_time和update_time都自动填上了当前时间。自动填充生效。

## 小结

第二章收尾的三件事各有代表性：Postman测上传卡在参数名和form-data类型这两个细节上；地址打不开图片卡在桶策略——给lkd桶配prefix为`*`的readonly匿名规则即可；代码层面的清爽则交给MyBatis-Plus，IService砍掉业务层的模板方法，MetaObjectHandler把时间字段赋值收敛到公共模块的一个类里。工具替你写重复代码，你只写有业务含义的那部分，这是2.0相对1.0最直接的体验差异。
