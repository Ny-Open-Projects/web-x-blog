# 执行计划解读收尾与交易模块建表：订单、成交、仓位三张核心表怎么设计

智牛股项目的数据库篇在这一章横跨两件事：一是把第四章数据库调优的执行计划讲完最后几个字段（key、key_len、ref、rows、Extra），给慢 SQL 分析收个尾；二是切入第五章——整个项目的核心，交易模块的数据库设计。前半部分回答"一条 SQL 慢在哪、怎么定位"，后半部分回答"一个金融交易平台的数据层该怎么建"。两块内容一个偏排查手段、一个偏设计功底，合在一起正好构成数据库能力的完整闭环。

## 先给结论

- 执行计划收尾字段：`key` 是实际用到的索引，`key_len` 是索引长度，`ref` 是关联条件，`rows` 是估算扫描行数，`Extra` 是附加信息；其中 `Using filesort` 和 `Using temporary` 是两个高消耗信号，出现必须排查优化。
- `key_len` 只计算 where 条件用到的索引长度，排序和分组用到的索引不计入；公式为：字符集每字符字节数 × 列长度 + 1（允许 NULL）+ 2（变长列）。
- 交易平台分为交易模块与非交易模块（用户注册、开户、活动等业务功能），设计遵循 FIX 国际金融标准协议，借鉴恒生、金证柜台交易系统并扩充，目标是支撑外汇、期货、CFD 等更广泛的金融产品。
- 交易模块三大核心表：订单表、成交记录表、仓位表。用户下单先写订单，订单按实际成交情况生成成交记录，每笔成交再落到仓位。
- 成交记录与订单、与仓位都是多对一：一张订单可多次成交，所以订单表要同时记初始挂单量和已成交量，成交记录只记每笔明细。
- 表设计大量采用反范式冗余（如 `stockMarket`、`companyId`），目的是让统计报表免于多表关联；冗余只挑关键 ID，单表属性一般不超过 20 个。

## 执行计划的后半场：从 key 到 Extra

上一讲讲到 `possible_keys`（可能用到的索引），这一讲接着往下看剩下几个字段。

**key：实际使用的索引。** `possible_keys` 只是候选，`key` 才是真正走了的那条。演示环境里 `USER_ACCOUNT` 上建了索引，执行计划就能看到查询走了这个索引；当 type 为 `index_merge` 时，key 里可能出现两个以上的索引——联合索引、组合索引合并使用时会这样显示。实际工作中发现 SQL 慢，先看 key 是否符合预期：查询条件没走到索引，方向就明确了——先看 SQL 能不能改写，改不了就补索引。

**key_len：索引长度。** 走了 key 就会有 key_len，它的计算不是拍脑袋：

| 组成部分 | 取值 |
| :--- | :--- |
| 字符集 utf8mb4 | 每字符 4 字节 |
| 字符集 utf8 | 每字符 3 字节 |
| 字符集 gbk | 每字符 2 字节 |
| 字符集 latin1 | 每字符 1 字节 |
| 允许 NULL | 额外 +1 字节 |
| 变长列 varchar | 额外 +2 字节 |

以 varchar(16)、utf8mb4、允许 NULL 为例：16 × 4 = 64，加 NULL 的 1，加变长的 2，共 67 字节。注意 varchar 与 char 的区别：char 是定长，不管实际存几个字符都按声明长度 16 计；varchar 按实际数据长度存取，再加 2 字节记录变长信息。另外，key_len 只统计 where 条件用到的索引长度，order by、group by 即使用到索引也不计入。

**ref：关联条件。** 常量等值查询显示 `const`（比如 `USER_ACCOUNT = 'admin'` 里的固定值）；连接查询显示驱动表的关键字段（如 `u.id`）；如果条件用了表达式或函数，或者条件列发生了内部隐式转换，这里会显示 `func`——看到 func 通常意味着隐式转换，本身就值得排查。

**rows：估算扫描行数。** EXPLAIN 并不真正执行语句，所以 rows 只是根据统计信息估算的结果集数目，存在误差，但足够用来横向比较两条 SQL 的开销。

Extra：附加信息，重点盯两个坏信号。
| Extra 值 | 含义 | 判断 |
| :--- | :--- | :--- |
| Using index | 使用覆盖索引 | 健康 |
| Using where | 服务器层过滤，存储引擎返回的记录不全满足条件 | 正常，按业务条件过滤 |
| Using filesort | 文件排序，用非索引列排序时出现 | 高消耗，必须优化 |
| Using temporary | 用临时表存储中间结果 | 高消耗，必须优化 |

用 UNION 验证 temporary 很直观：

```sql
EXPLAIN SELECT u1.*
FROM s_authority_user u1
UNION
SELECT u2.*
FROM s_authority_user u2;
```

结果里 id 分别为 1、2，select_type 为 PRIMARY 和 UNION，type 都是 ALL，Extra 出现 `Using temporary`——UNION 合并两个结果集时用了临时表。至此执行计划所有属性讲完，第四章也随之收尾：影响数据库性能的六大因素（硬件能力、系统规模、业务模型及架构、数据内部因素、代码设计、数据库配置），加上从 SQL 语句、索引到分库分表、读写分离的调优路径，共同构成完整的调优方法论；type 等级的性能排序（system > const > eq_ref > ref > range > index > ALL）面试中至少要能答出三四个点。

## 交易平台设计与物理模型：三大核心表

进入第五章，先看交易平台整体怎么设计。金融交易平台主要分为两块：**交易模块**和**非交易模块**——后者以业务为主，比如用户注册、用户开户、用户活动。交易模块是整个系统的核心，也是整个数据层的脊背。

设计上遵循 FIX 国际金融标准协议（可参考附件《FixApi文档》），借鉴行业标杆恒生、金证的柜台交易系统，并做扩充改进——它们以股票交易为主，而本平台的目标是支撑更广泛的金融产品：外汇、期货、CFD 等。接口之间传什么数据、核心交易接口怎么实现数据传递、后台数据怎么设计，都围绕这个目标展开。

物理模型的核心是三张交易信息表，数据流转主线非常清晰：

1. **用户下单** → 写入订单表；
2. **订单成交** → 根据实际成交情况生成成交记录，一笔订单可能对应多条成交记录（多对一）；
3. **成交落仓** → 每笔成交记录通过 `positionId` 关联仓位表（多对一），最终影响仓位。

围绕这三张核心表还有一圈周边表，各有明确职责：

| 表 | 作用 |
| :--- | :--- |
| 用户表 | 与订单一对多；成交记录冗余用户关联信息 |
| 用户文件表 | 开户时上传身份证、银行卡等证明文件，验证用户合法合规 |
| 用户账号表 | 平台支撑多个交易系统，每个交易系统对应一个账号，用户与账号一对多；自有交易系统在注册时直接生成开户账号，无需像对接第三方那样走接口审核 |
| 用户账户组表 | 区分普通组、VIP 组；VIP 佣金比例可调低、享有等级特权 |
| 预警设置/通知表 | 用户设预警线（如跌破 10% 通知），触发后产生通知记录，通知与账号多对一 |
| 股票信息表 | 基础数据：名称、代码、分类、市场、币种、单位、标签、状态、市场来源、显示顺序 |
| 股票分类表 | 按市场管理交易时段与佣金比例 |
| 系统全局配置表 | 常量参数、平台佣金、统一手续费、任务调度配置 |
| 序列表 | 分布式微服务下各节点自增 ID 无法保证全局唯一，靠序列表统一生成 |

股票分类表值得多说一句：不同市场交易时段不同——A股下午三点休市，港股四点，美股还有夏令时、冬令时之分，开盘时间可能是九点半或晚上十点半；各市场的佣金比例也可能不同。如果给每只股票单独记一套时间，维护成本会失控，所以统一挂在股票分类上做关联设置。至于序列表，也可以用雪花算法（Snowflake）替代：效率高，但不保证 ID 的连续性和有序性，只能保障局部节点有效，具体运用后面章节再展开。

## 核心表逐张拆解：订单、成交、仓位

**用户表与用户账号表。** 用户表里的 `companyId` 支撑 SaaS 化运作——接入不同公司、各自带用户群体，靠 company ID 区分。集团、运营中心、交易商在平台里统称为"机构"（`institutionTypeId` + `institutionId`），好处是想再扩充一个层级角色时很方便，做统计加工对系统冲击也小。用户账号表的 `balance` 是余额即可用资金——先入金充值才能交易，盈利后余额增加；表里冗余了 companyId、userName、institutionTypeId、companyName 等字段，属于典型的反范式设计：做报表统计时不必再回查用户表。冗余的原则是只挑关键 ID（冗余 companyId 即可，不必连公司名都搬），单表属性一般不超过 20 个。用户账户组表则把币种（CNY/HKD/USD）放在组上——做出入金、结算时不必再去查用户在哪个市场交易；`commissionRate`（佣金比例，单位 %）与 `taxesRate`（税费比例）分开：佣金交给运营平台，税费交给国家机关。

**订单表。**

| 属性 | 说明 |
| :--- | :--- |
| accountId / stockId | 交易账号 ID、股票 ID |
| status | 0 待成交，1 部分成交，2 完全成交，3 手工撤单，4 系统撤单 |
| type | 挂单类型：0 市价单，1 限价单 |
| direction | 买卖方向 |
| initVolume / execVolume | 初始挂单数量 / 实际成交数量 |
| requestPrice / execPrice | 请求价格 / 成交价格 |
| execTime | 成交时间 |
| accountNo / stockCode / stockName | 冗余字段，便于查询和统计 |

状态机背后是真实的交易场景：挂出 1000 手买单，当前市场只有 200 人愿意卖，就成交 200 手——部分成交；随着时间推移卖出的人越来越多，1000 手全部买入——完全成交；自己觉得行情风险太大主动撤掉——手工撤单；挂单不管了，到结算时间（如休市后晚上十点）系统自动撤回——系统撤单。之所以不做实时结算，是因为一天下来平台产生海量订单，实时结算会严重影响整体性能、延迟极大，所以统一设结算点批量处理。

`initVolume` 和 `requestPrice` 为什么要单独记？如果只记实际成交量，就无从追溯这个人初始到底想买多少。而成交价格不等于请求价格的原因有两个：一是市价单按当前市场报价成交，价格本身未知，上一秒 10 块下一秒可能 9.99；二是一笔订单多次成交时会吃到不同档位——想按 10 块买，市场上有 9.99 和 9.98 的卖单都吃掉，要综合算出平均成交价，实际成交价就不是请求价了。挂单类型上，市价单按市场报价直接成交（报价 10.01 就按 10.01 成交），限价单则指定心理价位（就想要 10 块），等市场上有人愿意按这个价卖给你。

**成交记录表。**

| 属性 | 说明 |
| :--- | :--- |
| tradeOrderId | 交易订单号，关联订单表 id |
| positionId | 持仓记录 ID，关联仓位表（多对一） |
| accountId / stockId | 交易账号 ID、股票 ID，用 bigint 支撑大数据量 |
| stockMarket | 股票市场：0 上交所，1 深交所，2 港股，3 美股 |
| execVolume / execPrice / execTime | 成交数量、成交价格、成交时间 |
| direction | 买卖方向 |
| profit | 盈亏，随行情动态变化 |
| commission / taxes | 佣金（平台抽取，千分之一、万分之一这一量级）、税费（如印花税，交给税务而非平台） |
| status | 0 有效，1 无效；成交出现问题或意外情况可作废 |

注意成交记录表没有初始挂单量字段——订单表追溯完整记录，成交记录表只追溯明细，关注每笔成交的数量和价格即可。`stockMarket` 是典型的适度冗余：按市场做统计时直接查这一张表就行，否则要走 stockId → 股票分类 → 股票市场的三层关联，繁琐且影响效率。所有 ID 类字段统一用 bigint，交易平台数据量非常大，类型上要留足余量。

**仓位表。** 仓位顾名思义就是个仓库，存储成交沉淀下来的持仓信息。`costPrice`（成本价）是仓位最核心的指标，而且是动态的：买 1000 手股票花了 1 万块，价格上涨 50% 变成 1.5 万，此时卖出一半仓位，剩 7500 块——刨去 5000 利润，成本只剩 2500，从 1 万降到 2500，盈利卖出会大幅摊低成本。`avgPrice`（成交均价）随不断买卖取平均变化；`validSellVolume`（可卖数量）对应 T+1 制度——当天买入的股票第二天才能卖，所以当天买入 1000 手，可卖数量是 0；`profit`（盈亏）随行情波动不断变化；`interest`（利息）在外汇产品里算隔夜利息，股票场景可由平台自定义策略。表里同样冗余了 accountId、stockId、stockMarket 等关联信息，便于查询统计。

## 小结

第四章的执行计划字段至此全部讲完：慢 SQL 的排查路径就是先看 key 是否符合预期，再看 Extra 里有没有 filesort、temporary 这两个高消耗信号，配合 rows 估算开销，定位不了就回头补索引或改写 SQL。第五章交易模块设计则回答了"金融平台数据层怎么建"：订单、成交、仓位三张核心表支撑多次成交、仓位合并、订单合并等复杂业务场景，撮合处理时怎么往这些表里写数据还有不少考究；反范式冗余服务于报表统计效率；表间关联既不能太复杂也不能过于简单，参考业内多年验证过的规范。这套设计还可以举一反三——把其他金融衍生产品的特征加进去，同样的模型就能支撑外汇、贵金属、期货的交易，股票与它们的底层数据结构并没有特别大的差别。
