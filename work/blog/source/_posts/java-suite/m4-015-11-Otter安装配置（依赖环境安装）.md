# Otter 安装配置全流程：依赖环境、双 MySQL 数据源与 manager/node 组件落地

canal 单元解决了"怎么拿到并解析 binlog"，Otter 再往前一步：同步规则全部页面化，一行代码不用写。前提是先把整套环境立起来。本单元十个视频全程实操，从三台服务器的角色划分、三套 MySQL，到 zookeeper、aria2 两个配套件，再到 manager/node 两个组件的安装与页面配置，最后 node 心跳点亮"已启动"。环境口径：CentOS 7.6，mysql:5.7、zookeeper:3.4.14、Otter 4.2.18，三台阿里云服务器以 IP 尾号 119、97、254 区分。

## 先给结论

- 三台服务器分工明确：119 只装源库，97 只装目标库，254 装 Otter 全家桶，配置数据库、zookeeper、manager、node 全在这一台上；前置依赖只有 JDK 8 和 Docker（19.03.12），课上直接跳过安装。
- MySQL 要起三个容器：源库、目标库之外，第三个给 Otter 自己存配置元数据。三个库共用同一份 docker.cnf 模板，只改 server_id（1、2、3 必须全局唯一）。
- 源库 binlog_format=row 加 log-bin=mysql-bin 是同步的硬前提：Otter 底层内嵌 canal，靠拉 binlog 干活，源库不开 binlog 就无数据可同步。
- 三个库都走"宿主机 conf/data 目录映射"起容器，配置在宿主机写，不用再进容器改文件，比 canal 单元进容器改配置省事得多。
- Otter 配置库初始化三步：建 otter 库、建 canal 用户授全权、执行官方 otter-manager-schema.sql 建出几十张内部表；页面上的配置最终都落到这些表里。
- manager 解压即用，otter.properties 改三处（domain.name 填公网 IP、数据库 URL 追加 autoReconnect=true&useSSL=false、密码 123456），8080 端口 admin/admin 登录；页面先注册 zookeeper 与 node，node 实机写 nid 启动后状态自动翻成"已启动"。

## 环境规划：三台服务器与三类数据库

Otter 的架构决定了环境的形状：同步有源头有去处，两端各要一个 MySQL；manager 与 node 是两个独立的服务进程；zookeeper 做分布式协调；Otter 自身还要一个库存配置。演示环境把角色压进三台服务器：

| 服务器 | 角色 |
| :--- | :--- |
| 39.99.59.119 | 源库：被同步的 MySQL |
| 39.99.56.97 | 目标库：同步数据的目的地 |
| 39.99.60.254 | Otter 组件：配置数据库、zookeeper、manager、node |

三类数据库的说法来自 Otter 的同步模型：用它做数据同步时涉及源数据库、目标数据库，再加一个 Otter 自己的配置数据库，一共三个。分配就按上表的顺序，一机一库。

依赖环境两样。JDK 是解压配环境变量的常规操作：

```bash
tar -zxvf jdk-8u191-linux-x64.tar.gz -C /usr/local/
vi /etc/profile
# 追加两行
export JAVA_HOME=/usr/local/jdk1.8.0_191
export PATH=$JAVA_HOME/bin:$PATH
source /etc/profile
java -version
```

Docker 先卸旧版再装 docker-ce，设开机自启：

```bash
yum remove docker docker-client docker-common docker-latest \
  docker-latest-logrotate docker-engine
yum install -y docker-ce
systemctl enable docker
systemctl start docker
```

装完看到 Docker version 19.03.12 即可。这两步课上没占时间，按讲义命令自行安装。

## 三套 MySQL 落地：一套模板改三处

三个库是同一套手法复制三遍：建宿主机目录、写配置文件、docker run 起容器、远程连上验证。

目录映射是这次的关键改进。装 canal 那会儿为了支持日志读取，要改 MySQL 配置把 binlog_format 设成 row，当时是进容器里改的。这次换个路子：启动容器前把配置目录和数据目录都映射到宿主机，配置文件直接在宿主机写，容器起来即生效。

以源库为例，在 39.99.59.119 上进 /mnt 建目录（目录名任意，演示叫 mysql_src，src 即 source）：

```bash
cd /mnt
mkdir mysql_src
cd mysql_src
mkdir conf data
cd conf
```

conf 下写一个 docker.cnf，MySQL 读的就是它：

```ini
[mysqld]
server_id=1
character-set-server=utf8
collation-server=utf8_general_ci
binlog_format=row
log-bin=mysql-bin
sql_mode='ONLY_FULL_GROUP_BY,NO_AUTO_VALUE_ON_ZERO,STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION'
```

server_id 唯一即可，字符集统一 utf8；重点是 binlog_format=row 与 log-bin=mysql-bin，binlog 必须是 row 格式才能做数据同步，canal 单元里已经强调过一次。随后起容器：

```bash
docker run -d --name otter_mysql1 \
-v /mnt/mysql_src/data:/var/lib/mysql \
-v /mnt/mysql_src/conf:/etc/mysql/conf.d \
-p 3306:3306 \
-e MYSQL_ROOT_PASSWORD=123456 mysql:5.7
```

本地没有 mysql:5.7 镜像会先拉取再启动。docker ps 确认容器在跑，Navicat 远程连 39.99.59.119（root/123456）验证连通。

目标库在 39.99.56.97 上，流程一模一样：目录叫 mysql_dest（与源库的 src 相对，destination 之意），docker.cnf 只把 server_id 改成 2，其余一字不动；docker run 换容器名 otter_mysql2、映射路径换成 mysql_dest：

```bash
docker run -d --name otter_mysql2 \
-v /mnt/mysql_dest/data:/var/lib/mysql \
-v /mnt/mysql_dest/conf:/etc/mysql/conf.d \
-p 3306:3306 \
-e MYSQL_ROOT_PASSWORD=123456 mysql:5.7
```

源库的配置生效情况顺手验证一遍，四条 show variables：

```sql
show variables like 'log_bin';              -- ON，binlog 已开启
show variables like 'binlog_format';        -- ROW
show variables like 'server_id';            -- 1
show variables like 'character_set_server'; -- utf8
```

第三个库在 39.99.60.254 上，目录 mysql_otter，server_id 改成 3，容器名 otter_mysql：

```bash
docker run -d --name otter_mysql \
-v /mnt/mysql_otter/data:/var/lib/mysql \
-v /mnt/mysql_otter/conf:/etc/mysql/conf.d \
-p 3306:3306 \
-e MYSQL_ROOT_PASSWORD=123456 mysql:5.7
```

容器跑起来后远程连上，初始化 Otter 专用库与账号：

```sql
create database otter DEFAULT CHARACTER SET utf8;
CREATE USER 'canal'@'%' IDENTIFIED BY 'canal';
GRANT ALL PRIVILEGES ON otter.* TO 'canal'@'%';
flush privileges;
```

用户名取 canal 不是随手起的：Otter 底层基于 canal 实现，后面登录这个库执行操作的就是 canal 用户，与 canal 单元里建账号是同一个套路。

还差建表。manager 运行需要一套自己的表结构，官方提供 SQL 脚本 otter-manager-schema.sql（GitHub 上 alibaba/otter 仓库 manager 模块的 sql 目录），下载后在 otter 库里执行：

```bash
wget https://github.com/alibaba/otter/blob/master/manager/deployer/src/main/resources/sql/otter-manager-schema.sql
# 连上 otter 库执行
source otter-manager-schema.sql
```

脚本里 create database 和 use 两步已手工做过，直接执行建表部分即可；除了一大批 create table，还有两条 insert，初始化的正是 admin 和 guest 两个用户，后面登录 manager 要用。执行完刷新，otter 库里多出几十张表。这些表全部归 Otter 内部运行使用：管理页面上配的数据源、同步任务最终都写进这些表，人不需要直接操作它们。

## zookeeper、aria2 与 manager：组件逐个落地

zookeeper 在架构里负责协调 node 工作，必须装；装在哪台都行，课上装在第三台，Docker 起单机版（讲义另附集群版步骤，生产再考虑）：

```bash
docker run -d --name my_zookeeper -p 2181:2181 zookeeper:3.4.14
docker logs -f my_zookeeper
# 需要连客户端验证时（讲义命令）
docker run -it --rm --link my_zookeeper:zk zookeeper:3.4.14 zkCli.sh -server zk
```

2181 是 zookeeper 的标准端口，docker logs -f 跟一眼启动日志，无报错即正常。

aria2 是个多线程下载工具，体积很小，Otter 运行时需要它的支持，yum 一条命令：

```bash
yum -y install epel-release aria2
```

manager 是架构图里那个"web 管理"：配置同步规则、设置数据源与同步源，对应一个安装包，跑起来是一个服务进程，node 同理。两个安装包从 GitHub releases 下载，版本 4.2.18：

```bash
wget https://github.com/alibaba/otter/releases/download/otter-4.2.18/manager.deployer-4.2.18.tar.gz
wget https://github.com/alibaba/otter/releases/download/otter-4.2.18/node.deployer-4.2.18.tar.gz
```

node 的包一并下好，一会儿就用到。演示里两个包已提前放在 root 目录，统一安装到 /opt/otter：

```bash
mkdir /opt/otter
cd /opt/otter
mkdir manager
tar -zxvf manager.deployer-4.2.18.tar.gz -C manager
```

解压出四个目录，典型的 Java Web 部署结构：bin 放可执行命令（startup.sh 在里面），conf 放配置文件，lib 放依赖 jar 包，webapp 放页面、js、图片，标准 web 项目的目录样子。

配置只动 conf/otter.properties。这个文件覆盖服务端口、数据库、zookeeper、邮箱四块，本次只需改三处：

```properties
# 1. 管理页面的域名/IP，改成 manager 所在服务器的公网 IP
otter.domain.name = 39.99.60.254

# 2. 数据库连接：指向刚初始化的 otter 库（与 manager 同在 254 一台）
otter.database.driver.url = jdbc:mysql://39.99.60.254:3306/otter?autoReconnect=true&useSSL=false
otter.database.driver.username = root
otter.database.driver.password = 123456
```

端口 8080 可改可不改，演示保持默认；驱动类 com.mysql.jdbc.Driver 不动；URL 尾部手工追加的 autoReconnect=true（自动重连）和 useSSL=false 是两个连接参数。

启动与验证：

```bash
/opt/otter/manager/bin/startup.sh
tail -500f /opt/otter/manager/logs/manager.log
```

日志出现 "the manager server is running now" 且无报错，服务就起来了。浏览器打开 http://39.99.60.254:8080/ 能看到管理界面，但此时是匿名状态（未登录）。登录账号就在初始化脚本那两条 insert 里：admin 和 guest，admin 的密码在表里是密文，明文同样是 admin。用 admin/admin 登录，页眉显示"admin 超级管理员"，manager 安装完成。

## 页面配置与 node 落地：注册在先，安装在后

manager 跑起来只是开始，它还要知道两件事：zookeeper 在哪、node 有哪些。这两件事都在管理界面上完成，使用 Otter 全程不需要编程，所有同步规则都在页面上配。

先配 zookeeper：机器管理 → zookeeper管理 → 添加。集群名称任意、唯一即可，演示用 local-zk；集群地址格式是 IP:端口，多个节点逗号分隔，单机版也照此书写，zk 就在 manager 同一台机器（Docker 起的，端口 2181），直接写公网 IP：

```
39.99.60.254:2181,
```

一个必须注意的细节：地址要以英文逗号结尾，哪怕只有一个节点。漏了逗号页面直接提示"必须以英文逗号结尾"。必填项只有带星号的两个：集群名称、集群地址；描述可写可不写。保存后 zookeeper 配置完成。

再配 node：机器管理 → node管理 → 添加，进入"添加机器"页面。此时 node 还没安装，但可以先把配置注册进去，后面再装实体，顺序不影响。三个字段：

| 字段 | 演示值 | 说明 |
| :--- | :--- | :--- |
| 机器名称 | local-node | 随意起，方便记忆即可 |
| 机器IP | 39.99.60.254 | 不能随意：node 部署在哪台就写哪台的 IP |
| 机器端口 | 1888 | 默认值；单机部署多节点时用端口区分 |

机器名称可以随便写，IP 绝对不能，它必须与 node 实际部署的机器对应，所以装 node 前就要规划好位置。ZK 集群下拉框当前只有 local-zk 一个选项，自动选中。保存后列表里出现 local-node，状态"未启动"，实体还没装，状态自然起不来，装好启动后这里会自动刷新。

顺带过一遍 manager 的菜单全景。同步管理里放 channel（同步任务，下个单元的主角）；配置管理里有数据源配置、数据表配置、canal 解析配置（Otter 使用内置 canal，不必单独装）与主备配置；监控管理看日志与监控列表，同步状态支持查询延迟、吞吐量、同步进度和报警、异常日志；系统管理管权限。用户权限分三级：ADMIN 超级管理员，可管理同步任务、添加数据表、修改 canal 配置；OPERATOR 普通用户，可管理某个同步任务下的配置；ANONYMOUS 匿名用户，只能查询同步状态。manager 的定位就是简化 admin 的操作成本：发布同步任务配置、接收同步任务反馈的状态信息，全部在页面上完成。

最后把 node 装出来。安装包已躺在 /opt/otter，解压出 bin、conf、lib、logs 四个目录：

```bash
cd /opt/otter/
mkdir node
tar -zxvf node.deployer-4.2.18.tar.gz -C node/
```

关键一步在 conf 下创建 nid 文件：

```bash
cd /opt/otter/node/conf/
echo 1 > nid
```

nid 是节点的唯一标识，值不能随便写，必须与 manager 页面上添加 node 时生成的序号一致，页面这个节点序号是 1，这里就写 1，两边靠它对号入座。echo 1 > nid 是 shell 简写：创建文件并写入 1。

node/conf/otter.properties 用默认值即可，唯一要理解的是 otter.manager.address = 127.0.0.1:1099：node 靠这个地址找到 manager 建立通信。node 与 manager 同在 254 一台机器，写 127.0.0.1 就能找到；分开部署时必须换成 manager 所在机器的公网 IP。

```bash
cd /opt/otter/node/bin/
./startup.sh
tail -500f /opt/otter/node/logs/node.log
```

日志出现 "the otter server is running now" 即启动成功。回到 manager 页面刷新机器管理列表，local-node 的状态已从"未启动"变成"已启动"，manager 与 node 建立了通信、保持心跳，节点状态被实时监控到了。

## 小结

整个安装链路是一条流水线：JDK/Docker 打底，三个 MySQL 容器落地（源库 server_id=1 开 row binlog、目标库 server_id=2、配置库 server_id=3 建库建 canal 用户导 schema），zookeeper 单机容器加 aria2，manager 解压改三处配置启动登录，页面上注册 local-zk 与 local-node，最后 node 写 nid 启动、心跳点亮。两个易翻车点值得单独记：zookeeper 集群地址必须以英文逗号结尾，单节点也不例外；node 的 nid 必须与 manager 页面上的节点序号一致，对不上号节点无法归队。到这里环境全部就绪，下个单元在源库和目标库里各建 otter_test 库，开始设置同步任务的五步配置。
