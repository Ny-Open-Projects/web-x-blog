# 补货工单收官：售货机侧补货协议处理与全链路测试

补货工单的最后一块拼图在售货机微服务这一侧。上一节工单微服务已经把补货协议发到了 EMQ，剩下的三步——接收补货协议、更新库存、把补货协议再下发到售货机——都落在售货机微服务的消息处理层。这套逻辑不需要从零写：立可得 1.0 里已经实现过，区别只是 1.0 对接的是 RabbitMQ，如今换成 EMQ，把代码找出来在消息层做适配即可。本篇记录这段改造，再用一条完整的工单流程验证库存是否真的被补上。

## 先给结论

- 补货消息处理类是售货机微服务 `com.liq.business.msghandler` 包下的 `SupplyCgMsgHandler`，通过 `@ProcessType("supplyReq")` 注册进消息分发架构，`process` 方法就是具体处理过程
- 处理顺序：JSON 转 `SupplyCfg` 对象 → 调 `vmService.supply` 按协议更新库存 → 取出售货机编号准备下发
- 下发数据都带版本号：商品配置、价格配置、货道配置、补货信息四种版本，每次下发递增，售货机靠它分辨新旧消息、与服务端保持数据同步
- 每个协议对象都要设置 sn（协议数据 id），取当天时间的纳秒数保证唯一
- 四个协议共用一个主题：`TO_VM_TOPIC` 拼上售货机编号，消息精准投递到指定机器而不是广播
- 端到端测试跑四个微服务（售货机、工单、用户、网关），走完创建、接受、完成，货道 1-1 库存 6 变 7、1-2 库存 0 变 2，链路闭环

## 协议处理类：复用 1.0 的骨架

打开售货机微服务，所有消息处理都在 `com.liq.business.msghandler` 包下，补货对应的是 `SupplyCgMsgHandler`：

```java
@Component
@ProcessType(value = "supplyReq")
public class SupplyCgMsgHandler implements MsgHandler {
    @Autowired
    private VendingMachineService vmService;

    @Override
    public void process(String jsonMsg) throws IOException {
        // 把传过来的 JSON 转成补货协议对象
        SupplyCfg supplyCfg = JsonUtil.getJson(jsonMsg, SupplyCfg.class);
        // 根据补货协议更新售货机库存
        vmService.supply(supplyCfg);
    }
}
```

类上标记的 `supplyReq` 就是补货协议的名称，整个架构靠消息分发机制把不同协议路由到对应的 Handler。`process` 方法的第一步是把收到的 JSON 反序列化成 `SupplyCfg` 对象；第二步调用售货机服务的更新库存方法——比如某个货道原有 6 个商品，补货协议里的数量是 2，库存就会按 6 加 2 更新。这两步在 1.0 里原样可用，真正的改造点在后面的下发部分。

## 版本号与 sn：下发数据的两个标识

下发协议之前，先给数据打上两个标识。

第一个是版本号。根据售货机编号可以查到配置版本对象，里面有四个版本：商品配置版本、价格配置版本、货道配置版本、补货版本。版本号是服务端向售货机发送数据的版本标识：这次发版本 1，下次就标版本 2。售货机收到后据此分辨新旧——自己当前是版本 1，收到版本 2 的消息就知道这是新数据，可以随时记录版本号判断哪些还没接收。售货机与服务端之间的数据同步，靠的就是这套版本机制，后面要做的四项下发也全都用到它。

第二个是 sn，相当于协议数据的 id，每次都必须不一样。为了做到唯一，取的是当天时间的纳秒数：1 秒等于 1000 毫秒，1 毫秒等于 1000 微秒，1 微秒等于 1000 纳秒，`System.nanoTime()` 返回的纳秒级数值几乎不可能重复。

接下来构建四个协议对象——商品信息协议、商品价格协议、货道协议、补货协议——各自设置版本号和 sn：

```java
// 商品配置
SkuCfg skuCfg = vmCfgService.getSkuCfg(innerCode);
skuCfg.setTs(System.nanoTime());
skuCfg.setVersionId(version.getSkucfgVersion());
// 价格配置、货道配置同理，版本分别取
// version.getSkuPriceCfgVersion() / version.getChannelCfgVersion()
```

## 主题拼接与 MQTT 下发

发送到售货机，实际上是发到 EMQ，售货机再去订阅这个主题。四个协议虽然内容不同，但可以共用同一个主题。Topic 常量类里定义了所有主题，其中 `TO_VM_TOPIC` 就是"到售货机"的主题——注意它只是前缀，不是完整格式，完整主题要拼上售货机编号：

```java
String topic = TopicConfig.TO_VM_TOPIC + innerCode;
```

发到哪台售货机，主题里就写哪台的编号。这样 A 售货机只订阅自己的主题，B 售货机不会收到 A 的消息，实现的是精准传递，而不是广播。

发送用 `MqttProducer`（消息生产者），`send` 方法三个参数依次是主题、消息质量（QoS）、发送的内容。把代码里原来的四处 todo 依次替换成四条真实发送：

```java
// 发送商品配置
mqttProducer.send(topic, 2, skuCfg);
// 发送价格配置
mqttProducer.send(topic, 2, skuPriceCfg);
// 发送货道配置
mqttProducer.send(topic, 2, channelCfg);
// 下发补货消息
supplyCfg.setNeedResp(true);
supplyCfg.setVersionId(version.getSupplyVersion());
mqttProducer.send(topic, 2, supplyCfg);
```

到这里，商品、价格、货道、补货四类消息就以协议的形式下发给了售货机——准确说是发进了 EMQ。售货机要拿到消息，需要订阅这个主题再做处理，那部分在后面的售货机端章节展开。

## 全链路测试：创建、接受、完成

代码就绪后，把四个微服务跑起来：售货机微服务、工单微服务、用户微服务（测试要登录）、网关。售货机端还没开发，所以这次只验证服务端链路——库存是否按协议增加；下发到售货机那一步，等售货机端完成后做联调。

测试用 `task.http` 里的脚本按流程走：

1. **创建补货工单**：请求体里带售货机编号和指派人。执行人要选一个具体的运营人员（角色编码 1002），这里指派给 ID 为 4 的张三。执行前 task 表只有 6 条工单、明细表没有记录；执行后多出 1 条工单、2 条明细——1-1 货道补 1 个，1-2 货道补 2 个。
2. **接受工单**：用张三的身份登录。在用户脚本里取张三的手机号，先发短信验证码（验证码到控制台查看），填进 code 后登录拿到 token，填回请求头。把接受工单脚本的工单 ID 改成刚才返回的 7，发送后刷新，工单状态变成 2。
3. **完成工单**：执行前先确认基线数据——售货机 innerCode 为 010001，货道 1-1 库存 6 个、1-2 库存 0 个。按协议，完成后 1-1 应变 7、1-2 应变 2。发送完成工单请求后刷新数据库，两个货道的库存正好变成预期值。

补货流程测试到此完成：工单从创建、指派、接受到完成，库存按明细准确增加，服务端这一侧的链路全部打通。

## 小结

这一篇把补货工单的服务端部分收了尾。协议处理复用了 1.0 的消息处理骨架，改造点集中在下发：四种配置协议带上版本号和纳秒 sn，通过 `MqttProducer` 发到 `TO_VM_TOPIC` 拼售货机编号的主题上，由 EMQ 转发给订阅的售货机。测试侧验证了创建、接受、完成三步之后库存的准确变化。下一阶段进入售货机端开发，补货协议的最后一跳才真正落地。
