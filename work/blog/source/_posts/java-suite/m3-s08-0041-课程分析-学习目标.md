# 课程分析章开篇：三个指标把同一条 ETL 流水线走三遍

清洗把原始日志变成事实表，故事到这里只讲了一半。业务方看不见数据仓库，他们要的是页面上一条趋势曲线。课程分析这一章的任务，就是把清洗结果继续加工成前端能画的数：统计出指标、同步到 MySQL、报表系统出图。章首列了 13 条学习目标，看着很多，拆开其实是三个指标各走一遍同一条流水线，先看懂结构，后面每一课都知道自己在这条线的哪个位置。

## 先给结论

- 13 条学习目标归成三个指标：课程访问量、课程购买量、热门学科排名，几乎每四条一组。
- 每个指标的节奏完全一致：NiFi 采集 → Spark 清洗 → Spark 分析 → NiFi 同步 MySQL → 业务报表系统展示。
- 前端只认 MySQL：分析结果留在数据仓库里业务用不了，必须由 NiFi 落到业务库，一个指标的 ETL 才算闭环。
- 业务报表系统只搭一次，之后任何指标的数据进了 MySQL 业务表，前端接上接口就出图。
- 数据可复用：订单数据同时支撑课程购买量与热门学科排名，排名指标只需补采选课数据。

## 13 条目标归成三个指标

把章首的目标清单按指标重新分组，结构立刻清晰：

| 指标 | 目标序号 | 数据来源 | 采集方式 | 业务产出 |
|---|---|---|---|---|
| 课程访问量 | 1～3 | 在线教育平台埋点日志 | JS 埋点采集，NiFi 可量产测试数据 | 每天课程访问量，前端图表展示 |
| 课程购买量 | 4～8 | 在线教育平台订单库 | NiFi 监控 binlog 实时采集 | 每天课程购买量，同步 MySQL 展示 |
| 热门学科排名 | 9～13 | 订单数据加选课数据 | 订单复用，选课用 NiFi 补采 | 学科维度的销售量、学生人数、销售额与增幅 |

每组内部的顺序也一致：理解需求、采集、清洗、分析、同步 MySQL。需求分析对着原型页做，把指标和维度定下来；采集把原始数据送进数据仓库；清洗在前面章节已经把维度关联、过滤、去重这套动作铺好，直接沿用；分析与同步是本章新增的两段。

## 一条流水线五段链路

三个指标共用同一条流水线，差别只在数据源与统计口径：

```mermaid
flowchart LR
    A["采集 NiFi 或埋点"] --> B["清洗 关联维度 过滤 去重"]
    B --> C["分析 按时间聚合"]
    C --> D["同步 NiFi 从 Hive 到 MySQL"]
    D --> E["展示 业务报表系统"]
```

逐段拆开看。采集负责把原始数据送进数据仓库的源头层，方式跟着数据源走：埋点日志靠采集系统落地，订单、选课这类业务库数据用 NiFi 监控 binlog 实时抽走。清洗是 Spark 程序，产出关联好维度的事实表。分析对事实表按时间维度聚合，结果写进业务表，这一层的数据才是业务口径。同步由 NiFi 完成，走 `SelectHiveQL → ConvertAvroToJSON → SplitJson → EvaluateJsonPath → PutSQL` 的固定流程，把业务表搬到 MySQL。展示由业务报表系统读 MySQL 出图。

重点在第四段：很多人以为分析程序跑完就结束了，其实数据还在 Hive 里，业务系统碰不到。数据仓库里的表是给分析用的，MySQL 里的表才是给前端用的，NiFi 同步这一步是两类存储之间的桥。

## 报表系统与数据复用

业务报表系统由两部分组成：后台是独立的 Spring Boot 工程，对接 MySQL 业务表提供接口，直接打包部署；前端页面对接后台 API 画图。整套系统搭一次就够，因为前端不关心数据从哪来，只认 MySQL 里的业务表。课程访问量先通，此时报表系统只有这一个指标有数据，其余页面空着；课程购买量、热门学科排名的数据后续落库，页面自然点亮，不需要再动系统本身。

热门学科排名这个指标需要销售量、学生人数、销售额三类数据，其中销售相关的数据在课程购买量指标里已经采集清洗过，直接复用，只需用 NiFi 补采学生选课数据。这是数仓分层带来的直接好处：事实表是公共资产，一次清洗，多个指标受益，不是一次性的中间产物。

## 本章的程序长什么样

以课程访问量为例预告一下分析程序的形态，核心就是对事实表做一次以天为单位的聚合：

```scala
// 读取清洗后的事实表
val visitDF = spark.sql(
  "select concat_ws('-',years,months,days) as date_info, years, months, days " +
  "from data_course.course_visit_fact")
// 以天为单位求和
val visitCount = visitDF.groupBy("date_info", "years", "months", "days").count()
```

聚合结果落到业务表 `course_visit_biz`，这张表在数据仓库建库脚本里已经就位：

```sql
CREATE EXTERNAL TABLE IF NOT EXISTS data_course.course_visit_biz
(date_info String,
 count INT)
PARTITIONED BY (years String, months String, days String)
ROW FORMAT DELIMITED FIELDS TERMINATED BY '\t'
STORED AS PARQUET
location '/user/hive/external/data_course/course_visit_biz';
```

两个数据列加三个分区列，结构极简，因为此时过滤去重都在清洗阶段做完了，分析只负责聚合。课程购买量、热门学科排名的分析程序形态类似，只是聚合的维度与指标不同。

## 常见误区

- **以为清洗完就能画图。** 错例：事实表一出来就去找前端要接口。正解：中间还有分析与同步 MySQL 两段，前端只认 MySQL 业务表。
- **每个指标单独搭一套展示系统。** 错例：三个指标搭三个后台三个页面。正解：报表系统一次搭建，指标级的差异只在 MySQL 业务表和接口配置。
- **所有指标都从零采集。** 错例：做热门学科排名时重新采集一遍订单。正解：先盘点已有哪些事实表，销售相关数据直接复用，只补采缺失的选课数据。
- **把分析理解成页面实时计算。** 错例：认为打开页面时后台去数仓库现算。正解：分析是离线批量程序，预先算好存进业务表，页面只做查询展示，这也是 T 加 1 报表的典型形态。

## 面试可能被问到的问题

1. 面试官追问：「讲一下你项目里数据从采集到展示的完整链路。」
   答：按五段讲：NiFi 或埋点采集原始数据进数据仓库；Spark 清洗关联维度、过滤、去重产出事实表；Spark 分析按时间维度聚合产出业务表；NiFi 把业务表同步到 MySQL；业务报表系统读 MySQL 做图表展示。三个指标共用这条链路。
2. 面试官追问：「为什么前端不直接查 Hive，非要同步到 MySQL？」
   答：Hive 面向离线批量分析，单查询秒级到分钟级，并发能力和接口生态都不适合在线服务；MySQL 提供稳定的低延迟点查，前端接口按日期参数查询即可。数据仓库和业务库各司其职，NiFi 同步是两者的桥。
3. 面试官追问：「指标之间怎么做数据复用？」
   答：先分层再盘点。事实表在清洗层沉淀，指标在分析层各自聚合。热门学科排名的销售量与销售额直接用课程购买量清洗好的订单事实表，只补采选课数据算学生人数，避免重复采集与重复清洗。
4. 面试官追问：「业务报表系统为什么要一次搭好？」
   答：报表系统的职责是通用的查询与可视化，与具体指标解耦。新指标接入只需新增 MySQL 业务表和后台接口配置，前端页面复用现有图表组件，所以系统层面只投入一次。
5. 面试官追问：「一个指标的 ETL 到哪一步才算完成？」
   答：以业务数据落进 MySQL 为完成标志。数据停在 Hive 里只能算分析完成，业务系统消费不到；同步到业务库之后，展示环节才有数可用，采集、转换、加载三段才真正闭环。
