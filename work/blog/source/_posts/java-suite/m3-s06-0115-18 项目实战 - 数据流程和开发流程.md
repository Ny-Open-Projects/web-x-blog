# 从设备报文到 Druid 落库：冷链监控平台的数据流程与接入开发流程

统计功能要查历史温湿度，打开管理台一看，数据源里只有早前导入的演示数据，设备的真实快照一条都没有。数据明明在系统里流动，为什么没进 Druid？答案是链路里有一段还没接上：Druid 不会主动去别处取数，它只认自己监听的队列。把整条数据流程看明白，再按开发流程把这段接上，统计才有米下锅。

## 先给结论

- 冷链监控平台的数据是双路落地：Flink 实时计算的结果一路覆盖写 MySQL 实时指标表，另一路回投 Kafka 结果队列，由 Druid 监听消费，历史快照全部沉淀在 Druid。
- 设备提交的是竖杠分隔的简单报文，Netty 采集服务收到后转成 JSON，再推入 Kafka 原始队列。
- Flink 监听原始队列，结合 Redis 里的温湿度阈值实时计算，产出带报警状态的完整快照。
- 让 Druid 接上 Kafka 分两步：配置文件里启用 druid-kafka-indexing-service 扩展并重启；再提交 supervisor 摄入任务。
- 配置文件按部署形态定位：single-server 或 cluster 目录下，再按集群规格选子目录，改的是 _common 下的 common.runtime.properties。

## 全链路数据流程

这张图是平台数据的完整走向：设备报文进 Netty，JSON 化后进 Kafka，Flink 结合 Redis 阈值计算，结果分两路分别落到 MySQL 与 Druid。

```mermaid
flowchart LR
    D["温湿度采集设备"] --> N["Netty 采集服务"]
    N --> K1["Kafka 原始队列"]
    K1 --> F["Flink 实时计算"]
    R["Redis 温湿度阈值"] --> F
    F --> M["MySQL 实时指标表"]
    F --> K2["Kafka 结果队列"]
    K2 --> DR["Druid 数据源"]
```

顺着关键路径读：上游三跳解决「数据怎么进来」，下游两跳解决「数据怎么分家」。MySQL 那一路只保留每台设备的最新读数，供实时报警快速取用；Kafka 到 Druid 这一路保留每一条快照，历史明细与统计都靠它。两条路互补，缺任何一条，页面都会少一块功能。

**第一段链路，设备到 Kafka。** 温度采集器、湿度采集器提交的报文刻意做得非常简单，字段用竖杠分割，一行就是一次读数。报文的拼装规则在工程里是现成的，公共模块的 MessageEntity 有 deviceMessage 方法（真实代码，包名按规范改写）：

```java
public String deviceMessage() {
    StringBuffer sb = new StringBuffer();
    sb.append("SHT");
    sb.append("|").append(this.getMetercode());
    sb.append("|").append(this.getTem());
    sb.append("|").append(this.getHum());
    sb.append("|").append(this.getState());
    sb.append("|").append(this.getLon());
    sb.append("|").append(this.getLat());
    sb.append("|").append(this.getCurtime());
    sb.append("|").append("SH5lb1.2.1R");
    return sb.toString();
}
```

拼出来的一行报文长这样：

```text
SHT|M001|10|20|1|116.39|39.9|20181117172120|SH5lb1.2.1R
```

报文薄是刻意为之：采集设备多半跑在资源受限的硬件上，网络带宽也有限，越短的报文越省。Netty 采集服务按同样的规则拆开竖杠，填进 MessageEntity，再序列化成 JSON 推到 Kafka 原始队列，下游拿到的是结构化数据，不用再解析文本。

**第二段链路，Flink 实时计算。** Flink 任务监听原始队列，每来一条读数就去 Redis 查这台设备的温湿度上下限，当场判定温度与湿度处于高温、正常还是低温状态，连同归属信息、上下限、经纬度一起，组装成一条字段很多的 JSON 快照。

**第三段链路，双路落地。** 同一份快照，写 MySQL 的是实时指标表，按设备主键覆盖写，表里永远是最新一条；回投 Kafka 结果队列的，被 Druid 监听后按时间切段存储。两边的字段结构一致，归属、上下限、读数、报警状态、经纬度、提交时间一个不少，差别只在保留策略。

## 接入开发流程两步走

数据流程图讲的是「数据怎么流」，开发流程讲的是「要让 Druid 接住这路数据，工程师要做哪几件事」。就两步：启用扩展，提交 supervisor 任务。

**第一步，在配置里启用 Kafka Indexing Service。** Druid 的扩展按需装载，改的是安装目录 conf 下、部署形态与集群规格对应子目录里的 common.runtime.properties。课程环境是单机部署、small 规格，完整路径：

```text
/opt/druid/conf/druid/single-server/small/_common/common.runtime.properties
```

用 vim 打开，找到 loadList 一行，把 druid-kafka-indexing-service 加进列表：

```bash
vim /opt/druid/conf/druid/single-server/small/_common/common.runtime.properties
```

```properties
# Extensions Specified in the Load list will be loaded by Druid
druid.extensions.loadList=["druid-hdfs-storage", "druid-kafka-indexing-service", "druid-datasketches", "mysql-metadata-storage"]
```

集群部署时路径结构相同，只是 single-server 换成 cluster 目录、small 换成实际规格（large、xlarge 等），改的都是各规格目录下 _common 里的这一个文件。改完重启 Druid 服务，扩展装载完毕，管理台才具备提交 Kafka 摄入任务的能力。

**第二步，提交 supervisor 任务。** 扩展只是把「监听 Kafka」的能力装进进程，真正让数据流起来的是一份 supervisor 摄入任务：它常驻运行，按规格派出 indexing task 消费结果队列，把消息解析成数据段。这份规格怎么写、提交后怎么验证，下一节结合 all_device_message 数据源逐段拆开讲。

这张图把两步开发串成了完整的接线动作，每一步都是下一步的前提：

```mermaid
flowchart LR
    A["改 common.runtime.properties"] --> B["loadList 加 druid-kafka-indexing-service"]
    B --> C["重启 Druid 服务"]
    C --> D["提交 supervisor 任务"]
    D --> E["Druid 实时落库"]
```

关键路径是重启到提交之间：不重启，扩展没装载，提交入口根本不存在；不提交任务，扩展只是能力储备，队列里依旧没有消费者。

## 为什么扩展要显式装载

**控制启动内容。** loadList 的语义在配置注释里写得很清楚：指定列表时只加载列出的扩展，列表为空一个扩展都不加载，完全不配置则加载扩展目录下的全部内容。生产环境显式列出，启动更快、行为也更可控，少了哪个扩展，看一眼列表就知道。

**运行期不生效。** 扩展随进程启动装载，改完配置不重启，正在运行的 Druid 进程感知不到。这也是排查「管理台提交 supervisor 无响应」这类问题的第一个检查点：确认配置改在正确的文件、进程确实重启过。

**双路而不是单写。** 只写 MySQL，历史查询没有数据；只进 Druid，实时报警的即时查询要跨过段扫描，得不偿失。两条路各司其职，这正是冷热数据分层的雏形，后面的统计需求分析还会回到这个分工上。

## 常见误区

- **配置文件改错位置。** 错例：单机部署却去改 cluster 目录下的文件，重启后扩展没装载。正解：路径按实际部署形态与规格找，single-server 或 cluster 加规格子目录，最后进 _common 改 common.runtime.properties。
- **改完不重启。** 错例：以为配置热生效，直接去管理台提交 supervisor，端点直接报不存在。正解：loadList 随启动装载，必须重启进程。
- **扩展名拼写错误。** 错例：loadList 里写成 druid-kafka-index-service，少一个字，启动日志报扩展不存在。正解：扩展名与 Druid 发行版 extensions 目录下的目录名逐字一致，以 druid-kafka-indexing-service 为准。
- **以为 Druid 直接消费设备报文。** 错例：把 supervisor 指到原始报文队列。正解：Druid 监听的是 Flink 计算后的结果队列，报警状态与完整字段都在这一路里；指错队列，存进去的是没算过的原始读数。

## 面试可能被问到的问题

1. 面试官追问：「平台里同一份设备数据为什么既写 MySQL 又进 Druid？」
   答：冷热分工。MySQL 实时指标表按设备主键覆盖写，只留最新读数，支撑实时报警这类毫秒级查询；Druid 保留每一条历史快照，按时间段查明细、画曲线、做统计都走它。写两份是拿少量存储换两类查询能力。
2. 面试官追问：「设备报文为什么用竖杠分隔这种私有格式，不直接发 JSON？」
   答：采集端硬件与网络受限，竖杠报文字符量少、解析成本低；结构化的负担转移到了 Netty 服务端，转成 JSON 后再进队列，下游统一吃结构化数据。
3. 面试官追问：「让 Druid 消费 Kafka 完整要做哪几步？」
   答：两步。在 common.runtime.properties 的 druid.extensions.loadList 里加 druid-kafka-indexing-service 并重启；然后提交一份 supervisor 摄入规格，声明数据源名、解析格式、队列地址。此后 supervisor 常驻，自动派 task 消费。
4. 面试官追问：「loadList 不配置和配置成空列表有什么区别？」
   答：不配置时 Druid 加载扩展目录下的全部扩展，配置成空列表则一个扩展都不加载。生产上推荐显式列出需要的扩展，启动快、行为确定。
5. 面试官追问：「Flink 在这条链路里解决什么问题？」
   答：实时报警计算。监听原始队列，用 Redis 里的阈值判定每条读数的温湿度状态，组装出完整快照，分别落地 MySQL 与结果队列；没有这一环，Druid 里只有原始读数，报警状态无从谈起。
