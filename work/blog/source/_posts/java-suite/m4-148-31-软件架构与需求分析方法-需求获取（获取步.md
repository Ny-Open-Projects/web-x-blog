# 需求获取六步与五大要素：角色场景、业务流程、数据实体、功能与非功能，电商订单系统收束全章

上一篇理清了需求的来源（干系人）和三个层次（业务/用户/功能），这一篇讲完第一章需求部分：需求获取六步与协作链路、五个需求要素，最后用电商订单系统演练一遍。

## 先给结论

- 需求获取六步：标识干系人 → 沟通交流 → 收集需求（纪要）→ 重要性排序 → 选择需求（按资源和约束筛选）→ 记录需求（编写文档，如功能需求说明书）。
- 需求要素六个：角色、场景、业务流程、数据实体、功能性需求、非功能性需求。
- 角色场景分析以业务活动为主线，每个活动明确五件事：执行角色、前置条件、正常/备选/异常三类场景、执行步骤、业务规则与约束。
- 流程类需求必须做业务流程分析，四步：流程确认 → 角色及业务活动确认 → 活动间关系及数据确认 → 瓶颈分析。
- 数据实体按需求类型分三类：流程类看传递实体，统计类看查询条件和展现实体，接口类看接口传递实体；非功能性需求守技术、时间、合规、数据安全底线。
- 案例：订单系统是电商承上启下的核心子系统，"下订单 → 减库存"必须同时完成，否则超卖或少卖；涉及 C 端用户、B 端商户、电商平台、配送商、第三方平台五个角色。

## 获取六步与角色协作

软件研发是团队性工作，项目组通常有产品经理、架构师、开发、测试人员，还有数据库管理员（DBA）、质检等角色，各阶段和角色的产出是下一个阶段和角色的输入。协作链路：产品经理从最终用户获取需求，形成功能需求说明书和产品原型；架构师据此做概要设计；开发人员据其做详细设计（有时也由架构师或项目组长完成），然后实现功能；最后由测试人员出测试用例。

具体操作上，需求获取分六步：

| 步骤 | 产出 |
|---|---|
| 1. 标识项目干系人 | 干系人列表 |
| 2. 与项目干系人交流 | 沟通计划 |
| 3. 收集需求 | 需求沟通纪要 |
| 4. 重要性排序 | 需求优先级 |
| 5. 选择需求 | 根据资源和约束选择实现的需求 |
| 6. 记录需求 | 编写文档 |

排序是因为并非所有需求优先级相同，重要的优先满足；筛选是因为收集 100 个需求不一定都实现。记录需求即编写文档，产品经理通常写功能需求说明书。

## 要素一：角色与场景

需求要素包括角色、场景、业务流程、数据实体、功能性需求、非功能性需求。先看角色和场景：每个业务活动是对用户使用场景的抽象，电商购物这个活动就包含浏览商品、添加购物车、下单、支付多个场景。分析场景应按业务活动为主线逐个进行，每个活动包含五项内容：

| 分析内容 | 电商购物示例 |
|---|---|
| 明确活动执行角色 | 购物活动由消费者执行 |
| 明确活动执行的前置条件 | 浏览商品无前置条件；下单必须完成登录——未登录点下单会跳到登录页，登录成功才能下单 |
| 明确不同场景 | 正常：登录 → 浏览 → 加购物车 → 下单 → 支付全程顺畅；备选：加购物车时有货，点下单那一刻库存不足；异常：支付时发生异常，业务如何处理 |
| 明确每个场景的执行步骤 | 先找到商品才能加购物车，加了才能下单，下完单才支付 |
| 明确业务规则和约束 | 秒杀每人最多购一件，想买十件不允许；评论有字数限制——包括与业务流程相关的行为规则，与数据实体相关的数据规则（如字段长度） |


## 要素二：业务流程

针对流程类需求必须进行业务流程分析。典型例子是发货环节：支付成功后卖家发货，货物交给物流公司，经多次转运到你所在小区的网点，再分配给快递员派送——整个物流运转就是典型的流程类需求。分析四步：

| 步骤 | 要点 |
|---|---|
| 1. 业务流程确认 | 一个流程为一个业务事件，由外部角色发起或系统内部主动发起（如时间事件、状态事件），发起后触发一系列业务活动；发货流程发起者就是卖家 |
| 2. 角色及业务活动确认 | 每个泳道都必须对应角色，每个角色对应多个业务活动；确认活动时保证粒度——一个业务活动由一个角色完成且有价值 |
| 3. 业务活动间关系及数据确认 | 确定所有业务活动的前后关系，明确流程间传递的数据实体——反馈问题需要有数据载体承载内容，甚至传文档 |
| 4. 流程整体瓶颈分析 | 若某个角色的业务活动工作量较大，或流程涉及高级领导，一般都会造成瓶颈；应想办法分散工作量、提出流程优化建议 |

课程配了"客户反馈问题处理流程图"泳道图：流程分问题收集、问题确认、问题处理三个活动。客户发起——反馈问题；产品经理分析问题并指派研发经理，研发经理接受任务（属于问题收集）；接着确认问题，不是真问题则提供处理说明，是则评估、指派开发人员；开发人员确认修复时间、修复问题（问题处理），测试人员确认修复后上线部署、获取反馈，流程结束。

## 要素三：数据实体

数据实体分析就是分析系统会用哪些具体的数据实体，按需求类型分三类：流程类看业务活动传递的数据实体，统计类看查询条件和展现的数据实体，接口类看接口传递的数据实体。常见实体后缀：entity 是实体直接跟表对应，DTO 是数据传输对象往往传输查询条件，VO 做页面数据展示。分析由粗到细四步：

| 步骤 | 要点 |
|---|---|
| 1. 明确数据实体 | 确认分析范围内所有数据实体，明确哪些是原有、新增、改造实体 |
| 2. 明确实体间关系 | 关系包含 1 对 1、1 对多、多对多；还要分析实体变更是否保留版本，删除（逻辑删除、物理删除）是否影响其它实体 |
| 3. 明确实体字段 | 针对新增或改造的实体，明确新增字段的名称、类型、是否必填、取值方式——人工输入、系统自动继承自其它实体、系统自动计算（需明确公式） |
| 4. 数据权限分析 | 分析不同角色在数据权限上的差异，涉及多级用户时要说明集团/省/市用户的数据隔离 |

数据权限的例子：员工工资属敏感信息，只有直接上级能看到，其他部门员工哪怕是领导岗位，不是直接上级也看不到——这就需要数据权限控制。

## 要素四、五：功能性需求与非功能性需求

功能性需求结合现有系统现状和上述分析，进一步明确实现相应用户场景的系统功能，含四项。功能列表：分析得出业务活动对应的功能/接口列表，明确新增、改造功能——新项目不分新增改造，后期维护才区分。功能/接口关联影响分析：不能改好一处却影响别处，例如改造请购池受理功能可能影响采购项目创建功能；后者修改一个字段取值范围，会影响项目统计分析和同步 ES 系统接口。系统交互原型分析：需求人员应遵循界面规范，与研发沟通确定交互原型，帮助研发或用户理解需求；原型界面应包含名称、入口、原型间关联关系和使用角色，页面内容、格式及排序方法，以及操作要点（交互提示信息、界面规则和约束）。算法分析：涉及复杂算法时需单独分析。

非功能性需求不从业务功能角度，而从可行性、健壮性、可扩展性等方面考虑：

| 非功能性需求 | 要点 |
|---|---|
| 1. 技术可行性 | 系统交互实现方式与研发确认是否可行；需求人员在与研发沟通中要积累哪些功能实现在技术层面很难支撑——比如依赖指纹、语音识别等硬件设备，技术不成熟时很难实现 |
| 2. 时间可行性 | 根据用户的上线时间要求分析是否可满足——比如项目要求双十一上线，分析完发现上不了就不行 |
| 3. 合法安全性分析 | 分析用户需求是否满足国家法规或公司法规要求——系统必须合规合法 |
| 4. 数据安全性分析 | 用户需求是否满足信息系统安全要求——敏感信息可能需要加密处理 |

## 案例：电商订单系统

理论讲完，用电商平台的订单子系统演练一遍。电商所有模块中，订单系统是非常核心的子系统，决定整个流程能否顺畅执行，起承上启下的作用，其他模块都围绕它构建；它出问题或功能流程设计不完善、不准确，将造成整个电商系统整体或局部业务流转不畅，甚至导致项目失败。电商平台以盈利为目的，靠客户提交订单挣钱，订单系统的核心地位由此而来。它管理订单类型和状态，收集商品优惠、用户、收货信息、支付信息等实时数据，并做库存更新、订单下发等动作。业务基本模型涉及用户、商品（库存）、订单、付款，基本流程"下订单 → 减库存"两步必须同时完成——下了订单不减库存会超卖，减了库存没生成订单会少卖，都造成数据不一致。

**角色**：实体角色有五个。C 端用户——消费者，通过移动端 APP 或网页购物，参与商品浏览、添加购物车、提交订单；B 端商户——卖家；电商平台——商家入驻，平台对商户管理；配送商——负责下完单后整个物流转运；第三方平台——如支付等第三方。角色不一定指某个人，有的指平台，只有 C 端用户是个人。

**系统关系**：应用前台有 C 端商城（消费者直接面对）、商户后台（消费者看不见，商家登录后做活动、商品上下架）和渠道；业务中台有订单系统、产品系统、促销系统；服务中台是公共服务，需要直接调，都有统一接口——会员、支付、财务、风控、配送、消息系统。订单系统只是整个大系统的一部分。

**场景（用例）**：从用户角度能做哪些操作。浏览商品——商品来自商品系统，通过它上架、下架、搞优惠活动；添加商品到购物车——购物车本身也是一个系统；点下单进入订单系统；支付走支付系统；支付完成后商家发货走配送系统，最终送到用户手中——每一块对应一个子系统，比如支付直接调支付系统的接口即可完成。用例图是同样内容换一种画法：C 端用户可浏览商品、创建订单、提交订单、线上支付。

**功能**：订单系统业务架构分三层。订单服务是用户日常使用的服务和页面，含创建订单、查询订单、订单数据展示，具体有订单列表（查询历史订单）、订单详情、在线下单，以及为公共业务模块提供的多维度订单数据服务；订单逻辑是核心，包含流程引擎、状态机、价格计算，管理订单创建、支付、生产、确认、完成、取消等流程，涉及状态规则、金额计算、库存扣减规则等；底层服务包括会员、库存、商品、促销、支付、风控服务——仅靠订单系统完不成整个下单支付流程，比如价格计算要调促销服务，促销规则就在其中制定。底层服务背后是公共模块模块化的问题：订单创建要调用分散在各系统中的公共模块，花费大量时间、维护成本非常高，因此需要接入这些公共模块。

## 小结

这一篇收尾第一章需求部分。方法侧：需求获取按六步走；要素六个——角色场景抓五件事、业务流程抓四步泳道分析、数据实体由粗到细拆到字段和数据权限、功能性需求落到功能列表/关联影响/原型/算法、非功能性需求守技术、时间、合规、数据安全四条底线。案例侧：电商订单系统过了一遍方法——五个角色、三层系统关系、场景与用例图、三层业务架构，核心规则是"下订单 → 减库存必须同时完成"。第一章至此完结。
