# 超时订单处理：需求思路、EMQ 延迟消息、代码实现与测试

立可得智能售货机系统里有一个绕不开的场景：用户在小程序端打开了支付窗口，却因为余额不够、不想买了、密码忘了等各种原因没有完成支付，而且也没有点击关闭支付页面的按钮。程序如果不做处理，这笔订单将永远停留在未支付状态。订单支付与出货控制这一章的第 6 节"超时订单处理"，就用 EMQ 自带的延迟消息来解决它：订单创建 10 分钟后仍未支付的，自动置为无效状态。本篇把需求思路、EMQ 延迟消息的用法、代码实现和测试过程一次讲完，这一章的内容到此收束。

## 先给结论

- 需求口径：订单创建 10 分钟后，如果还处于未付款状态（状态值 1），就把它改成无效状态（状态值 4）。
- 技术核心是 EMQ 自带的延迟消息（延迟队列）：消息发出后消费者不会立刻收到，到设定的时间点才收到，像设了一个闹钟。
- 使用前提是打开 EMQ 管理后台的 `emq.mqtt.delayed`（EMQ Delayed Publish Module）模块开关，新装好的 EMQ 这里可能是关闭状态，需要手动开启。
- 发送延迟消息只需在主题前加前缀 `$delayed/{秒数}/`，秒数后面接真实的业务主题，其余发送逻辑和普通消息完全一样。
- 代码分两大步：创建订单时发一条只带订单号的 `OrderCheck` 延迟消息；延迟到期收到消息后，查出仍是创建状态的订单，更新为无效。
- 订阅端不要带 `$delayed` 前缀——那只是发送时用的前缀，不是主题名；`$share/g1/` 是群组订阅前缀，g1 是群组名。

## 需求、实现思路与 EMQ 延迟消息

先看需求。用户在小程序中开启支付之后，因为各种不确定的原因未能完成最终付款，也未点击关闭支付页面的按钮，订单将永远处于未支付状态。这是一种未结束的订单状态，系统需要把这类订单在 10 分钟之后自动处理，将状态置于无效。具体到状态值上：未付款状态是 1，无效状态是 4，要改的就是这个值。

实现思路在 PPT 上就两条：

1. 在订单服务的创建订单方法里，订单创建完成后，把该订单的信息发送到 EMQ 的延迟队列中，延迟处理时间为 10 分钟。
2. 在订单服务里订阅延迟队列主题下的消息，收到消息后检查该订单的状态，如果订单还处于创建状态，则将订单置于无效状态。

所谓延迟队列，就是 EMQ 本身提供的一种能力：消息生产者向 EMQ 发了一条消息，但消费者并不能及时收到，而是到了设定的时间点——比如 10 分钟之后——才能收到这条消息，就像设了一个 10 分钟后响的闹钟。

使用之前要先打开开关。在 EMQ 管理后台找到模块列表中的 `emq.mqtt.delayed`，也就是 EMQ Delayed Publish Module。刚装好 EMQ 时这个开关有可能是关闭的，需要手动开启；状态显示 Enabled（绿色）就表示当前 EMQ 可以使用延迟队列了。

开关打开后，用 EMQ 自带的 WebSocket 工具就能直观验证效果。连接时填 Host `192.168.200.128`、Port `8083`、Path `/mqtt`，连接成功后先订阅 `testtopic/#`（QoS 设为 2）。直接向 `testtopic` 发消息是实时的，发送后立刻就能在订阅列表里收到。要看到延迟效果，把发送主题改成 `$delayed/10/testtopic/aaa`——前缀 `$delayed/` 后面跟延迟秒数 10，再接真实主题；因为订阅用的是 `#` 通配符，后面接任何字符串都能匹配上。发送后左侧的发送面板立即出现这条消息，而右侧的订阅列表要等 10 秒之后才出现，延迟效果一目了然。

## 代码实现：发送延迟消息与接收改状态

整个代码就分两大步：创建订单时发送延迟消息；接收消息之后修改订单状态。

第一步先在 `service_common`（公共服务模块）里定义放到队列中的消息对象，也就是订单检查协议 `OrderCheck`。它除了通用属性外只有一个订单号——做延迟处理时用到订单号就足够了：

```java
@Data
public class OrderCheck extends AbstractContract implements Serializable {
    public OrderCheck() {
        this.setMsgType("OrderCheck");
    }

    private String orderNo;
}
```

然后在创建订单的方法里追加一段代码：实例化 `OrderCheck`、传入订单号，通过消息生产者发送。和以前发消息的唯一差别，是主题前面多了 `$delayed/600/`——600 秒即 10 分钟，后面接订单检查主题：

```java
// 将订单放到延迟队列中，10分钟后检查支付状态！！！！！！！！！！！！
OrderCheck orderCheck = new OrderCheck();
orderCheck.setOrderNo(orderEntity.getOrderNo());
try {
    mqttProducer.send("$delayed/600/" + OrderConfig.ORDER_DELAY_CHECK_TOPIC_2, orderCheck);
} catch (JsonProcessingException e) {
    log.error("send to emq error", e);
}
```

第二步是订阅和状态修改。注意订阅主题时不要写 `$delayed` 前缀，那是发送时用的，不是主题名称；订阅的主题就是 `ORDER_DELAY_CHECK_TOPIC_2` 常量对应的 `order/delayCheck`，实际配置里以群组方式订阅：

```yaml
$share/g1/order/delayCheck
```

`$share/g1/` 表示以群组方式订阅消息，g1 是群组名称。这样订阅之后，10 分钟延迟到期就能把这个消息取回来。

接下来编写处理类，用的还是那套消息处理架构：`@ProcessType` 指定协议名称，实现 `MsgHandler` 接口。`process` 方法里的逻辑也不复杂：先把消息解析成 `OrderCheck`，取出订单号，取不到就直接返回；能取到就按"订单号 + 状态等于创建状态"这两个条件查询订单——查出来是 null，说明订单已经支付完成，不做处理；查得到，说明订单创建 10 分钟之后仍然是未付款状态，就用 `UpdateWrapper` 把状态改成无效并更新：

```java
@Component
@ProcessType(value = "OrderCheck")
public class OrderCheckHandler implements MsgHandler {
    @Autowired
    private OrderService orderService;

    @Override
    public void process(String jsonMsg) throws IOException {
        OrderCheck orderCheck = JsonUtils.getJson(jsonMsg, OrderCheck.class);
        if (orderCheck == null || Strings.isNullOrEmpty(orderCheck.getOrderNo())) return;

        QueryWrapper<OrderEntity> qw = new QueryWrapper<>();
        qw.lambda()
            .eq(OrderEntity::getOrderNo, orderCheck.getOrderNo())
            .eq(OrderEntity::getStatus, VMSYSTEM.ORDER_STATUS_CREATE);

        OrderEntity orderEntity = orderService.getOne(qw);
        if (orderEntity == null || orderEntity.getStatus() != VMSYSTEM.ORDER_STATUS_CREATE) return;

        UpdateWrapper<OrderEntity> uw = new UpdateWrapper<>();
        uw.lambda()
            .eq(OrderEntity::getOrderNo, orderCheck.getOrderNo())
            .set(OrderEntity::getStatus, VMSYSTEM.ORDER_STATUS_INVALID);

        orderService.update(uw);
    }
}
```

创建状态和无效状态分别对应常量 `VMSYSTEM.ORDER_STATUS_CREATE` 和 `VMSYSTEM.ORDER_STATUS_INVALID`，整个接收处理本质上就是一次订单状态的条件更新。

## 测试：把 10 分钟缩成 1 分钟

测试分三步走。第一步，找到发送延迟消息的那行代码，正常写的是 600 秒（10 分钟），为了测试方便先改成 60，也就是 1 分钟——下单一分钟之内不支付，订单就会被置为无效。第二步，启动四个微服务：订单服务、售货机微服务（`VmsServiceApplication`）、小程序微服务（`MicroappApplication`）和小程序网关（`MicroappGatewayApplication`）。第三步，打开微信开发者工具，点击扫一扫，扫立可得售货机的测试二维码进入主界面。

进去之后随便选一个商品——反正不打算支付——进入商品详情页，点击"去支付"，弹出支付二维码后就不付了。此时先查一下订单：列表里新增了一条"青梅绿茶"的订单，下单时状态显示为 0。刷新再等一分钟过去，这条订单的状态就自动变成了 4——延迟队列起了作用，超时订单被成功置为无效。

## 小结

超时订单处理是订单支付与出货控制一章的收官环节。方案完全建立在 EMQ 延迟消息之上：创建订单后向 `$delayed/600/` + 业务主题发一条只含订单号的 `OrderCheck` 消息；订单服务以 `$share/g1/order/delayCheck` 群组方式订阅，延迟到期收到消息后按"订单号 + 创建状态"查询，仍处于未付款的就更新为无效状态。发送端只加一个前缀，接收端只多一次条件更新，就解决了订单永远停留在未支付状态的问题。至此，订单支付与出货控制这一章的内容全部落地。
