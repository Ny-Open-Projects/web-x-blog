# Apache Superset 简介：把数据拖成看板的轻量级 BI

报表需求一周一变，每次都走前端排期改图表页面，开发节奏根本追不上业务；让产品同学自己去数据库写聚合 SQL，也不现实。冷链监控平台的解法是引入一款 BI 工具：Apache Superset。数据接进去，维度指标定义好，图表靠拖拽拼出来，看板自动联动，改动不再占用开发人力。

## 先给结论

- Apache Superset 是 Airbnb 开源、用 Python 构建的轻量级 BI 系统，提供数据挖掘与可视化的交互界面，能搭出可交互的 dashboard（看板）。
- 用法上是三层模型：数据源连接圈定数据库，数据集定义维度与指标，图表绑定可视化类型，最后编排成看板。
- 图表内置基于 D3.js，支持二次开发接入 ECharts、AntV 等可视化框架扩展。
- 本项目选它的决定性理由：与存储层的 Apache Druid 深度集成，海量时序数据的可视化能快速出图。
- 附带能力一揽子收下：SQL 查询工具、轻量语义层、权限体系、查询结果缓存，开箱即用。

## 一、定位：它替你省掉的是哪段工作

BI 即商业智能，通俗讲就是把库里的数据变成管理层看得懂的图表与看板。传统重型 BI 价格贵、实施重，Superset 走轻量路线：Python 构建，部署不重，功能却覆盖了「连数据、定义口径、做图、拼看板」的全流程。

它对数据库的适配面很宽。关系型的 MySQL、SQL Server、Oracle，大数据平台的 HBase、Greenplum，乃至 Apache Druid，都能接进来做实时可视化。这意味着同一个平台可以同时看档案库与时序分析库的数据，不需要为每种存储各配一套报表方案。

几个突出特点按用途归拢。**第一，SQL 查询工具。** 它内置了类似 SQL IDE 的查询界面，连接多种数据库后直接写 SQL 实时查询、抽取数据，做图表之前先用它验证口径，很顺手，只是功能相对基础。**第二，拖拽式建图。** 没有开发经验的产品或业务人员，通过对数据源的选择、字段的拖拽、图表类型的选择、控制面板里的设置，就能创建出相当专业的图表，开发只负责把数据集和权限准备好。**第三，语义层轻量但够用。** 允许定义维度和指标，把「什么是平均温度、按哪个口径统计」这种口径问题定义一次，之后所有图表复用同一套定义，向用户公开的数据指标口径就统一了。**第四，权限体系与缓存。** 有权限体系控制谁能看什么，只是粒度不算特别细；查询与配置做了缓存，重复访问不用每次都打到数据库，开箱即用。

图表生态也值得记一笔：内置图表基于 D3.js 封装，够覆盖常见场景；有二次开发能力时，可以接入 ECharts、AntV 这类图表框架来扩展现有图表类型，不必被内置清单绑死。

## 二、三层模型：从连接到看板

Superset 的使用逻辑可以压缩成一张图，四个概念串成一条链。

```mermaid
flowchart LR
    DB["数据源连接：MySQL、Oracle、HBase、Greenplum、Apache Druid"] --> DS["数据集：圈定表或 SQL 查询，定义维度与指标"]
    DS --> CH["图表：选可视化类型，绑定指标与过滤条件"]
    CH --> DBD["看板：多张图表编排成可交互页面"]
```

关键路径读一遍：数据源连接只解决「连得上」，拿到的是原始表；数据集在这之上做一层抽象，把口径定义成维度与指标；图表从数据集取数，选一种可视化类型并绑定聚合方式；看板把多张图表编排到一个页面，加上联动过滤，就成一个可交互的分析页。排错时按这条链往下捋：连不上查连接，数不对查数据集定义，图不对查图表配置。

## 三、接入 Apache Druid：本项目选它的理由

冷链监控平台的时序数据存在 Apache Druid 里（定位见 Apache Druid 简介一篇），而 Superset 与 Druid 是深度集成的：数据集可以直接建在 Druid 数据源上，海量数据的聚合图表响应依然快，这是其他 BI 工具不一定给得到的体验。服务层组件清单里「Superset 管报表可视化」这个岗位，靠的就是这层集成。

Superset 自身是 Python 应用，装好之后跑一个配置文件管端口、元数据库与缓存（按主流写法补全的示例，本课没有对应源码包）：

```python
# superset_config.py：按主流写法补全的示例
SUPERSET_WEBSERVER_PORT = 8088
# Superset 自己的元数据存 MySQL
SQLALCHEMY_DATABASE_URI = "mysql://superset:pass@mysql1.example.com:3306/superset?charset=utf8"
# 图表查询结果缓存到 Redis，重复访问直接命中
CACHE_CONFIG = {
    "CACHE_TYPE": "redis",
    "CACHE_DEFAULT_TIMEOUT": 600,
    "CACHE_KEY_PREFIX": "superset_results_",
    "CACHE_REDIS_URL": "redis://redis1.example.com:6379/1",
}
```

建好 Druid 数据集后，在 SQL 查询工具里验证一条口径（示例按本课写法补全），确认数字没问题再转成图表：

```sql
SELECT housename,
       COUNT(*) AS report_times,
       MAX(tem) AS max_tem,
       AVG(hum) AS avg_hum
FROM coldchain_meter
WHERE __time >= CURRENT_TIMESTAMP - INTERVAL '1' HOUR
GROUP BY housename
ORDER BY max_tem DESC
```

## 四、与自研前端的关系

平台的表现层分两块：监控主界面、公司设备管理这些业务页面，仍是自研的 Vue 前端，走网关调后台服务；面向数据分析的报表与看板，由 Superset 这个独立平台承接，技术架构篇服务层里「Superset 管报表可视化」说的就是它。两块之间通过数据衔接：后台服务把算好的数据写进存储，Superset 从存储里取数出图。本节的画面以功能介绍文档为主，接入 Druid 数据源、搭看板的实际操作在后续数据可视化章节落地。

## 常见误区

- **把 Superset 当成前端组件库。** 错例：以为它是页面里引入的图表插件。正解：它是独立部署的 Web 平台，有自己的登录、权限和数据管理，前端页面里最多嵌入它的图表或跳转。
- **把数据集等同于数据库连接。** 错例：连上库就开始拖图。正解：数据集是连接之上的抽象层，维度与指标口径定义在这里，跳过这层直接拖图，各图表口径容易各说各话。
- **把权限体系当安全兜底。** 错例：认为配了角色就万事大吉。正解：它的权限粒度不算特别细致，敏感数据还要在数据源与数据集层面另做收敛。
- **以为它只能连 Druid。** 错例：因为本项目强调 Druid 集成就以为绑死。正解：MySQL、SQL Server、Oracle、HBase、Greenplum 等主流数据库都能接，Druid 只是本项目的主要取数点。

## 面试可能被问到的问题

1. 面试官追问：「Superset 解决什么问题，为什么不用自研报表页面？」
   答：它把「连数据、定义口径、做图、拼看板」整条链工具化了，业务人员拖拽就能出图，报表需求变化不再占用开发排期。自研适合深度定制的展示，通用分析类需求用 BI 平台成本低、响应快。
2. 面试官追问：「数据源、数据集、图表、看板分别是什么？」
   答：数据源是数据库连接；数据集在其上圈定表或 SQL 查询，并定义维度与指标口径；图表从数据集取数，绑定可视化类型与聚合方式；看板把多张图表编排成可交互的分析页面，四层自下而上衔接。
3. 面试官追问：「为什么这个项目选 Superset？」
   答：决定性理由是它与 Apache Druid 深度集成，平台的时序分析数据就在 Druid 里，可视化查询能快速处理海量数据；再加上 D3.js 图表生态、可扩展、Python 实现部署轻、拖拽建图门槛低，综合下来最匹配。
4. 面试官追问：「Superset 的权限体系可靠吗？」
   答：它有权限体系，能控制角色对数据源、数据集、看板的可见性，但粒度不算特别细。行级、列级的敏感数据控制需要在数据源与数据集设计时另外收敛，不能全指望平台权限。
5. 面试官追问：「图表类型不够用怎么办？」
   答：内置图表基于 D3.js，具备二次开发能力时可以接入 ECharts、AntV 等可视化框架扩展图表类型；或者先把口径数据用 SQL 查询工具验证后导出，由自研前端补特殊展示，两条路按改动成本选。
