# 亿可控收尾：设备离线前端推送、MyBatis-Plus 二级缓存优化与前后端联调

先交代一下项目全景：亿可控是一个通用物联网设备监控平台，覆盖新零售、共享充电桩、智能家居、安防监控等场景，业务分图形监控、数据详情、看板管理、设备管理、报警管理、系统管理六大块；技术上是 Spring Boot 微服务，消息层用 EMQX，注册与配置中心用 Consul，缓存用 Redis，持久化用 MyBatis-Plus，数据分别落在 MySQL、InfluxDB、ES 三个库。五章课程走到最后一章"GPS 采集搜索与数据透传"的收尾部分，本篇覆盖三件事：给设备断网补上前端推送，用二级缓存和手动 Redis 缓存扛住高频查询，最后跑通前端工程完成前后端联调。

## 先给结论

- 设备断网推送复用既有告警通道：在通知服务里加 disconnectionAlarm 私有方法，构建 AlarmMsg（告警级别 1、告警名称"设备断网"），与指标告警一样发布到 EMQ 的 /device/alarm 主题。
- 触发点挂在线状态透传 onlineTransfer 里：只有 online 为离线才推送，在线状态没必要发。
- 断连消息要区分来源：clientId 以 webclient（前端）或 monitor（服务端）开头的断连直接 return，只有设备断连才推给前端。
- MyBatis-Plus 二级缓存三步走：cache-enabled: true → MybatisRedisCache 实现 MyBatis 的 Cache 接口（存取走 RedisTemplate）→ 在高频 Mapper 上加 @CacheNamespace 指定 implementation 与 eviction。指标、GPS、告警三个 Mapper 需要加。
- 设备数据存在 ES 而不是 MySQL，二级缓存够不着，只能在 findDevice 里手动先查 Redis Hash、未命中回源 ES，再配一个 refreshDevice 在保存、开关、在线状态变更处显式刷新。
- 前后端联调：后端启动微服务；前端装 Node.js + Yarn，yarn install 装依赖，vue.config.js 代理指向 127.0.0.1:9093，yarn serve 起工程后按页面清单逐个验证。

## 设备离线的前端推送

告警的前端推送上一节已经完成：指标超阈值时构建 AlarmMsg 发到 EMQ，前端经 WebSocket 收到。设备离线也要走这条通道——设备断网了，同样需要把消息推给前端。

实现分两步。第一步在通知服务 NoticeService 里加一个私有方法 disconnectionAlarm（断网告警），入参是设备编号，得知道是哪台设备断了；方法里实例化 AlarmMsg，依次设置设备编号、告警级别为 1（一级告警）、离线标志、告警名称"设备断网"、告警类型为告警，然后发送到 EMQ：

```java
// 通知服务 NoticeService：断网告警的前端推送
private void disconnectionAlarm(String deviceId) {
    AlarmMsg alarmMsg = new AlarmMsg();
    alarmMsg.setDeviceId(deviceId);       // 是哪台设备
    alarmMsg.setAlarmLevel(1);            // 一级告警
    alarmMsg.setAlarmName("设备断网");     // 告警名称
    // 离线标志、告警类型等属性按 AlarmMsg 结构补齐后
    // 与指标告警走同一通道：发布到 EMQ 的 /device/alarm 主题
    emqClient.publish("/device/alarm", alarmMsg);
}
```

第二步解决"在哪调"。在线状态透传方法 onlineTransfer 本来就会在设备上下线时执行，直接在这里补一个判断：online 为否（设备离线）才调 disconnectionAlarm；状态是在线就没有必要发这条消息：

```java
// 在线状态透传：设备离线时推送断网告警
if (!online) {
    disconnectionAlarm(deviceId);
}
```

写完启动亿可控做测试：前端清空消息后模拟设备连接再断开，前端能收到断网消息，功能即通。

但这里还有一个要补的坑。断连消息并不只有设备一种：前端（webclient）与 EMQ 之间会断连，服务端（monitor）与 EMQ 之间也会断连，这两种都不应该当成设备离线推给前端。所以在处理逻辑前面再加一层过滤——deviceId 以 webclient 或 monitor 开头的直接 return，除此之外的才都是设备断连，才走推送：

```java
// webclient 是前端，monitor 是服务端，这两类断连不推送
if (deviceId.startsWith("webclient") || deviceId.startsWith("monitor")) {
    return;
}
```

## 缓存优化：MyBatis-Plus 二级缓存打底

缓存优化的动因很直接：物联网报文上报非常频繁，每条报文进来解析时都要先查 MySQL 拿指标配置——analysis 方法里的 baseMapper.selectBySubject(topic) 就是对 MySQL 的查询，这个动作每条报文都会触发一次，数据库压力很大。

用 Redis 当然能解决，但按常规写法引入 RedisTemplate，得在业务代码里加一堆"先查缓存、查不到查库、查完回填"的判断逻辑，虽然灵活，侵入性太强、工作量也大。所以这里选 MyBatis-Plus 提供的二级缓存，简单配置就把问题解决掉，共三步。

第一步，配置文件开启二级缓存：

```yaml
mybatis-plus:
  configuration:
    cache-enabled: true
```

第二步，准备缓存实现类 MybatisRedisCache——这个类工程第一天就已经引入，这里只需理解它。它实现的是 MyBatis 提供的 Cache 接口，接口定义了取 ID、存数据、取数据、移除、清除、取大小、读写锁这一组方法；实现类里这些动作全部交给 RedisTemplate 完成：

```java
public class MybatisRedisCache implements Cache {
    private final ReadWriteLock readWriteLock = new ReentrantReadWriteLock(true);
    private RedisTemplate<String, Object> redisTemplate;
    private String id;

    public MybatisRedisCache(final String id) {
        if (id == null) {
            throw new IllegalArgumentException("Cache instances require an ID");
        }
        this.id = id;
    }

    @Override
    public void putObject(Object key, Object value) {
        if (redisTemplate == null) {
            // 缓存实例由 MyBatis 创建、不归 Spring 管，容器就绪后按需取 Bean
            redisTemplate = (RedisTemplate<String, Object>) SpringUtil.getBean("redisTemplate");
        }
        if (value != null) {
            redisTemplate.opsForValue().set(key.toString(), value);
        }
    }

    @Override
    public Object getObject(Object key) {
        if (redisTemplate == null) {
            redisTemplate = (RedisTemplate<String, Object>) SpringUtil.getBean("redisTemplate");
        }
        try {
            return redisTemplate.opsForValue().get(key.toString());
        } catch (Exception e) {
            log.error("缓存出错", e);
        }
        return null;
    }
    // removeObject / clear / getSize 按同样思路实现
}
```

第三步，在 Mapper 接口上加 @CacheNamespace 注解，implementation 与 eviction 都指定为 MybatisRedisCache。不用所有 Mapper 都加，只挑查询频繁的表：指标配置的 Mapper 最频繁必加；GPS 配置每个指标上报都要读，要加；告警同样高频，也加：

```java
@CacheNamespace(implementation = MybatisRedisCache.class,
                eviction = MybatisRedisCache.class)
public interface QuotaMapper extends BaseMapper<QuotaEntity> {
}
```

加完之后效果是全自动的：该 Mapper 的查询自动走 Redis 缓存，增删改自动更新缓存，业务代码一行不用动。

## 设备查询的手动缓存：数据在 ES，二级缓存够不着

还有一张查询同样频繁的表——设备表。但设备信息不在 MySQL 里，而是存 Elasticsearch，MyBatis-Plus 二级缓存管不到它，只能手动做查询优化。

改动集中在 DeviceServiceImpl 的私有方法 findDevice（按设备 ID 查设备，类里多处调用，原先每次直查 ES）。思路：先注入 RedisTemplate，查询时先查 Redis，查不到再回源 ES。存取用 boundHashOps，Hash 的大 key 用工程预定义常量（值形如"亿可控.dx"），小 key 是设备 ID，取出来的值强转成 DeviceDTO：

```java
@Resource
private RedisTemplate<String, Object> redisTemplate;

private DeviceDTO findDevice(String deviceId) {
    // 先查 Redis：大 key 是工程常量，小 key 是设备 ID
    DeviceDTO deviceDTO = (DeviceDTO) redisTemplate.boundHashOps(CACHE_KEY).get(deviceId);
    if (deviceDTO == null) {
        // 缓存未命中，回源 Elasticsearch
        deviceDTO = esRepository.findDevice(deviceId);
        refreshDevice(deviceDTO);   // 从 ES 查到后同步进 Redis
    }
    return deviceDTO;
}
```

配套再写一个刷新缓存的方法 refreshDevice：入参 DeviceDTO，为 null 直接 return；否则把这条设备数据 put 回 Redis 的 Hash，实现缓存刷新：

```java
private void refreshDevice(DeviceDTO deviceDTO) {
    if (deviceDTO == null) {
        return;
    }
    redisTemplate.boundHashOps(CACHE_KEY).put(deviceDTO.getDeviceId(), deviceDTO);
}
```

剩下的事是把所有会改动设备数据的入口都接上刷新逻辑，这类缓存全是手动操作，漏一处就是脏数据：

| 方法 | 改动 |
| --- | --- |
| findDevice | 先查 Redis，未命中回源 ES，查到后调 refreshDevice 同步缓存 |
| saveDeviceInfo | 保存设备信息后调用 refreshDevice 刷新缓存 |
| setStatus | 设置设备开关：先更新查出的对象状态再刷新缓存，方法改为返回 boolean 值 |
| updateOnline | 更新在线状态：先 setOnline 更新对象属性，再调 refreshDevice 刷新缓存 |

## 前后端联调：把两端真正接起来

代码层面收官后，进入第六小节前后端联调。前后端分离模式下两端都按接口文档开发，理论上应该一次跑通，实际或多或少会有衔接问题；联调的目的就是运行起来把问题暴露出来，根据报错定位是前端的问题还是后端的问题，再修正。

后端侧：确认虚拟机镜像开启后，直接启动亿可控微服务即可。前端侧要先准备运行环境，这个工作只做一次——安装 Node.js 和 Yarn（Yarn 是类似 npm 的包管理工具），两个安装文件在资料"环境\前端环境"目录里。然后解压前端工程到本地目录，在该目录下打开控制台：

```bash
yarn install   # 安装依赖，耗时较长，装完后工程目录下多出 node_modules
yarn serve     # 启动前端工程，首次编译较慢，完成后自动打开浏览器
```

运行前要确认 vue.config.js 的代理配置。开发期前端没有真实后端可连，target 指向的是 mock 地址；联调时要切换到真实后端地址——后端在本地跑就是 127.0.0.1，部署到服务器就写服务器 IP：

```javascript
proxy: {
  '/api': {
    target: 'http://127.0.0.1:9093',
    // target: 'https://mock.boxuegu.com/mock/1094',
    changeOrigin: true,
    pathRewrite: { '/api': '' }
  }
}
```

这段配置把 /api 前缀的请求代理到后端 9093 端口，changeOrigin 改写请求 Origin 头，pathRewrite 把 /api 前缀去掉。当前值已经是 127.0.0.1，无需改动。

| 数据详情 | 设备卡片显示 ID、温度、湿度与状态；按在线/离线/一般报警/严重报警筛选，按设备编号或 ID 搜索；点三个点查看设备具体指标 |

## 小结

本章给亿可控收了尾，三件事各有一条清晰的实施路径。离线推送复用告警通道：disconnectionAlarm 构建"设备断网"告警发到 /device/alarm，挂在 onlineTransfer 里只在离线时触发，并用 webclient/monitor 前缀过滤掉非设备断连。缓存优化分两路：MySQL 里的指标、GPS、告警表走 MyBatis-Plus 二级缓存，开配置、备实现类、加注解三步完成；存 ES 的设备数据走手动 Redis Hash 缓存，findDevice 先缓存后回源，refreshDevice 在保存、开关、在线状态三个变更点显式刷新。联调环节 yarn install + yarn serve 起前端，代理指向 127.0.0.1:9093，按首页、数据详情、设备管理、指标管理、报警管理的清单逐页验证。至此设备从上线、报警、离线到前端呈现的链路全部打通。
