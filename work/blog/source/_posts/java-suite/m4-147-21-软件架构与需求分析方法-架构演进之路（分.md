# 演进之路收尾与服务化：异步解耦、微服务六大组件、大中台小前台，以及需求问题的三个坑

上一篇讲到分布式架构的静态化与 CDN，这一篇先把异步解耦讲完，给架构演进之路收尾；接着进入微服务与服务化，看"大中台、小前台"战略怎么从组件化思想里长出来；最后转到需求侧：最常见的三个需求问题，以及需求从谁那里、按什么层次获取。

## 先给结论

- 异步解耦：部署专门的消息服务器（RabbitMQ、ActiveMQ、RocketMQ、Kafka 这类 MQ），把应用间直接调用变成异步调用——短信晚几秒可接受，扔进消息队列即可，性能增强，依赖减少。
- 微服务是分布式架构的深化：分布式偏部署角度，微服务专注业务拆分与服务组件化，像搭积木，业务单一的服务组件可独立部署。
- 大量微服务带来六大新问题：注册发现、统一接入鉴权、负载均衡、集中配置、熔断、监控，Spring Cloud 生态都有对应组件。
- 服务化的动机是传统企业多套独立系统的重复轮子：B2B、B2C、C2C 每套都有用户、商品、交易、支付，扩展性差、可靠性不高、维护成本大。
- 服务化四大好处：调用简单、代码复用、业务隔离、数据库解耦；代价是小系统没必要拆、分布式事务是挑战、测试运维复杂度上升。
- 常见需求问题三个：不明确、理解不一致、经常变动；需求来自干系人，分业务（why）、用户（what）、功能（how）三层。

## 异步解耦收尾，微服务接棒

异步解耦的做法是部署专门的消息服务器，RabbitMQ、ActiveMQ、RocketMQ、Kafka 等消息中间件都属于消息服务器，它把应用之间的直接调用变成异步调用。有些场景并不需要同步：比如业务完成后要短信通知对方，晚几秒完全可接受，这时把短信内容扔进消息队列，性能得到增强，服务间耦合性自然降低。加上发送方、接收方、消息服务器本身都要分布式部署，异步解耦也属于分布式架构范畴。

至此分布式架构讲完了，它涵盖范围非常广，最直观、接触最多的体现形式还是按业务拆分成多个模块，协调完成某一个业务。

接下来是微服务架构。它和分布式架构相似到难以严格分辨，本质上微服务就是分布式架构的进一步深化，区别在关注点：分布式偏向部署和环境，考虑应用、数据库、缓存在多台服务器上怎么部署；微服务专注系统内部的业务功能，实现服务组件化——把业务按服务拆分，通过组件组合快速开发系统，类似搭积木，业务单一的服务组件可独立部署。


请求链路：客户端经 CDN 和 LB（Load Balance，负载均衡）到网关，由网关转发到一个个微服务，微服务间相互调用。大量分布式服务也带来新问题：

| 新问题 | 具体表现 | 对应组件 |
|---|---|---|
| 服务注册与发现 | 全靠网络调用，调用前得知道对方的 IP、端口、路径 | Eureka、Consul、Nacos、Zookeeper |
| 统一接入与权限控制 | 网关做统一入口，在网关上做权限控制、鉴权 | Gateway、Zuul |
| 负载均衡 | 服务 3 部署两个实例，是轮询还是按机器配置 2:1 分发 | 负载均衡组件 |
| 集中配置 | 每个服务都有自己的配置，需要集中管理 | Zookeeper、Redis、Nacos、Consul |
| 服务熔断 | 调用中间断网时，不能一直等超时把调用方拖死 | Hystrix |
| 服务监控 | 这么多服务是否健康，需要监控追踪 | Sleuth 等追踪组件 |

微服务架构由基础服务组件和业务微服务组件共同组成。好处是快速迭代、持续交付——微服务粒度小，可以针对某一个模块直接迭代；弊端是这些问题都得考虑，好在都有相应的组件。

## 服务化：从重复轮子到大中台小前台

为什么需要服务化？传统企业的软件大多不止一套系统，而是独立大系统的堆积：扩展性差、可靠性不高、维护成本大、重复制造的轮子多。B2B、B2C、C2C 三种模式各是一套独立系统，每套里都有用户管理、商品、交易、支付——三套系统三套用户、三套商品、三套交易，全是重复的轮子。解决思路：组件化、服务化——把公共服务模块单独提出来，其他应用直接调，微服务已在解决这个问题。

组件化，就是将一个大系统按照一定的业务或者技术维度拆分成独立的组件，目的是分而治之、可重用、减少耦合度——原先功能堆在一块耦合度高，按功能拆开后耦合度就降下来了（相互调用不可避免）。两个拆分维度：

| 拆分维度 | 典型组件 | 场景 |
|---|---|---|
| 技术维度 | 文件上传下载组件 | 各服务都要上传下载文件，调组件即可 |
| 技术维度 | 短信发送组件 | 推广短信、登录验证码、下单成功通知，多场景复用 |
| 技术维度 | 搜索组件、缓存组件 | 公共技术能力下沉 |
| 业务维度 | 用户中心、商品中心、支付中心 | 多模块都要支付，不必各写一遍支付逻辑，统一调支付中心接口 |

这种思路阿里巴巴最早提出来，并上升为战略——大中台、小前台。前台应用是淘宝、天猫、闲鱼、菜鸟、支付宝、盒马；支付、结算、交易、商户、用户、搜索等中心被各前台应用共同需要，按业务、技术维度沉淀成一个个服务，最终组成中台服务。前台因此变得轻量：要做什么任务，直接调用对应的服务。把拆好的服务跟前台一组合，就成了一个淘宝应用——微服务架构实际也是这种思想，只是阿里把它上升了一个层次，组合成了业务中台。

服务化的好处有四个：调用简单——每个服务都有统一的调用接口，比如支付对外统一接口；代码复用——提成公共服务后复用性非常强，淘宝、天猫、闲鱼、菜鸟都需要支付，统一调它就行；业务隔离——每个服务都是一块相对独立的微小业务；数据库解耦——不同微服务有自己的数据库。

有利必有弊。第一，业务不复杂的系统不需要微服务架构——几百行上千行代码的小项目用单体架构就非常合适，硬拆是小题大做，要不要服务化看业务复杂度和规模。第二，多个模块数据库之后，分布式事务是一个挑战。第三，增加了测试、运维等事务的复杂性——部署、调试、测试都比单体复杂。对规模大的项目，肯定还是选择服务化，问题虽在，但可以忍受甚至解决。

## 需求的三个坑：不明确、理解不一致、经常变动

架构讲完，转入需求。需求是企业软件开发中非常重要的环节：开发之前做需求分析，分析完再设计，然后才开发。常见问题三点。

| 常见需求问题 | 典型成因 |
|---|---|
| 需求不明确 | 盲人摸象——业务庞大，没人能统领全局，各阶段人员只掌握一段；项目初期业务还在摸索、没有定型；各部门目标和 KPI（关键绩效指标）不一致，需求有冲突——更多是利益冲突，项目上线甚至可能触动个人利益 |
| 需求理解不一致 | 不同的人站在自己的角度对同一个需求理解不一样，做出的东西不是客户想要的 |
| 需求自身经常变动 | 开发到一半客户需求变了，也可能前期分析有偏差做到一半才发现；不管谁引发，都得重新设计、重新开发 |

需求理解不一致有个形象的比喻——秋千。客户说：我家有三个小孩，需要能三人同时玩的秋千，用一根绳子吊在我园子里的树上——他想要一个完整的、多座位的秋千架。项目经理理解的是：一块板子两边用绳子吊起来，挂在树上两个枝子上。设计师想的是：挂在树枝上能荡起来吗？树干挡着呢，除非把树从中截断再支起来。同一个需求，三份理解，做出来的东西肯定不是客户要的。

项目最重要的阶段是进行需求分析，明白真正的需要。项目需求指的是用户真正需要什么，而不是供应商假设用户需要什么、能供应什么。需求的准确定位，就是按照用户的要求，对目标系统提出完整、准确、清晰、具体的要求。需求分析做不好，就会造成需求不断变更，进而影响进度、费用，甚至导致项目失败。

对需求经常变动，要尽可能分清稳定需求和易变需求，以便系统设计时把软件的核心建筑在稳定的需求上，否则将会吃尽苦头。合同层面：一定要说清楚系统的业务边界，做什么、不做什么；合同含含糊糊，日后扯皮的事情就多。

## 需求获取开篇：干系人与需求三层次

需求获取从三个方面看：需求的来源（需求从哪来）、需求的分类、获取步骤。

需求来源非常明确——干系人：对系统有利益关系的个人、团队、组织或者其他系统，直白点说，跟系统有关系的个人或团体都算。项目干系人包括但不限于：

| 干系人 | 角色 |
|---|---|
| 投资方 | 系统投资方，出钱的，主要干系人 |
| 主管方 | 批准、管理系统的（内部小项目可能没有） |
| 最终用户 | 系统受益方，使用系统的人 |
| 操作方 | 操作、维护系统的人或团体 |
| 监管方 | 对系统认证的 |
| 测试方 | 负责系统验收的 |

课程举例：某信贷管理系统，投资方是资金部，主管方是信息化部，用户代表是市场部，最终用户是营业员，监管方是审计部，测试方和操作方也都是信息化部——干系人不是个人而是一个个部门，需求就要从这些干系人那里获取。

再说需求的分类。软件需求通常分三个层次，自上而下：业务需求、用户需求、功能需求，分别对应 why、what、how。

| 层次 | 回答的问题 | 要点 |
|---|---|---|
| 业务需求 | why——为什么要引入这个系统 | 由公司高层提出，目标导向；描述组织或客户的高层次目标，必须业务导向、可度量、合理、可行；来自投资人、用户的管理者、市场或策划部门 |
| 用户需求 | what——用户需要什么样的功能 | 描述用户使用产品必须完成什么任务、怎么完成需求；需跟用户访谈调查，整理使用场景 |
| 功能需求 | how——怎么实现这些功能 | 描述开发人员需要实现什么，是需求的主体；数量级通常比用户需求高一个数量级 |

业务需求就是系统的目标。比如高层决定引入一个系统，希望降低运营成本、提高工作效率；再比如希望实施 CRM（客户管理系统）后，客户满意度达到 80% 以上，这就是可度量的业务目标。业务需求对之后的用户需求和功能需求起限定作用，相当于最高的指导思想。

用户需求必须体现系统能给用户带来什么价值，细分成五类：基本型——产品必须满足的，社交软件不能加好友、音乐产品不能听歌，软件注定失败；期望型——满意度随满足程度线性提升或下降，音乐产品歌曲越多越好；兴奋型——完全出乎用户意料，比如微信的摇一摇；无差异型——满足不满足都没影响，比如产品简介；反向型——起反作用的，比如产品要付费，用户对付费功能普遍不友好。基本型需求一定要保证。

功能需求通常落到一个专门文档：软件需求规格说明书（SRS，Software Requirements Specification），完整描述软件系统预期特性，开发、测试、QA、项目管理都会用到。why、what、how 分别对应业务需求、用户需求、功能需求。

## 小结

本篇两件事。架构侧：异步解耦用消息队列把同步调用改成异步，为分布式架构收尾；微服务以业务拆分为核心把服务组件化，六大治理问题靠注册发现、网关、负载均衡、集中配置、熔断、追踪组件化解；服务化从"重复轮子"出发，按技术、业务两个维度拆出公共能力，阿里把它推到极致就是大中台小前台。需求侧：不明确、理解不一致、经常变动是三个最常见的坑，需求来自干系人，按业务、用户、功能三层自上而下分解，最终落到需求规格说明书。下一节继续需求获取的步骤与需求要素。
