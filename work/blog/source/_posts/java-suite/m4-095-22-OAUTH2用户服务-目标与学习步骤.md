# OAuth2 用户服务改造与网关搭建：统一异常、统一返回、核心类与 Druid 监控配置

认证服务落地之后，用户服务篇要做的是：搭好 stock-user 工程结构，封装统一异常与统一接口数据返回，实现用户登录接口并接入 OAuth2 鉴权，最后整体启动验证。接下来网关服务篇补上网关——它只做统一转发、不做鉴权校验，同时把 Druid 监控数据源集成进用户服务。这两部分走完，从申请 token 到访问受保护资源的完整链路就闭环了。

## 先给结论

- stock-user 按 config、controller、dao、service、startup 分包；pom 引入 web、Nacos 服务发现、actuator 与 Spring Security OAuth2 鉴权相关依赖（starter 封装 oauth2、security、autoconfig 三个组件），另有负载均衡依赖保证认证服务高可用。
- 统一异常分两类：ComponentException 对应工具组件（StreamUtils、MD5 加密等辅助组件抛出），BusinessException 对应业务逻辑（用户不存在、密码错误等，可封装更多信息便于日志排查）；错误码统一实现 IErrorCodeEnum 接口，由 ApplicationErrorCodeEnum 枚举定义服务模块、错误编号、消息与错误级别。
- 异常处理规范：service 业务层统一判断并抛出，controller 层统一捕获封装返回，DAO 层不做判断和 catch；错误编号按服务分段（用户服务 1 开头、订单服务 2 开头），看到错误码就知道是哪个模块的问题。
- 统一返回 ApiRespResult\<T\> 四个字段：code、msg、data、extendData，另有 isSuccess() 便于前端快速判断；success()/error() 静态方法直接传错误码枚举，提示信息统一封装。
- 登录核心逻辑两步：按用户编号查用户，查不到抛 USER_NOT_FOUND；密码按密文方式比对，不一致抛 USER_PWD_ERROR。资源服务配置 @EnableResourceServer 与 @EnableGlobalMethodSecurity(prePostEnabled = true)，RemoteTokenServices + RestTemplate 远程校验 token。
- 网关只转发不鉴权，因此 Gateway 不集成 Spring Security；核心是一个全局过滤器保证 Authorization 头转发不丢，外加两条路由（/user/** 转发 stock-user、/oauth/** 转发 trade-auth），不要开启 Method 限定。Druid 监控放在用户服务，filters 取 stat、wall、log4j，监控后台登录 admin/admin123。

## 统一异常与统一返回：先把周边组件标准化

新增 bulls-stock-user 模块，先补依赖、建包。工程结构与最初"经网关调用返回一个字符串"的简易版本完全不同：config 负责整体配置，controller 提供用户登录接口，dao 是数据层操作接口，service 放业务处理，再加启动类和 VO 对象。pom 核心依赖如下：

```xml
<!-- Spring Boot Web -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
<!-- Nacos 服务注册发现依赖 -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
<!-- Spring Boot 监控组件依赖 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<!-- Spring Security OAuth2 鉴权相关依赖 -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-security</artifactId>
</dependency>
```

这组依赖封装了 oauth2、security、autoconfig 自动化配置三个组件；OAuth2 的 load balance 依赖保证访问认证服务时某个节点出问题，可通过服务名称调用其他认证节点维持高可用。另外还有 common 下抽取的公用工具层、实体层依赖。

统一异常封装在 stock-common-utils 里，目的是规范各微服务对异常的处理：一个请求链路经过多个微服务节点，各节点各自定义一套异常的话，仅凭错误码很难定位是哪个服务抛出来的。封装分两类：

| 异常类型 | 定位 | 典型场景 |
|---|---|---|
| ComponentException 组件异常 | 辅助组件的处理异常，用法相对简单 | StreamUtils 对空字符串的操作、MD5 加密等工具类抛出 |
| BusinessException 业务异常 | 与业务逻辑紧密相关，可封装更多信息便于日志分析排查 | 用户不存在、密码错误、权限信息不合法 |

错误码统一实现 IErrorCodeEnum 接口做抽象，不能随便定义：接口里定义了用户服务模块、系统模块等常量，将来扩充交易服务模块接着扩展即可；并声明获取错误编号、错误码描述、错误级别三个公用方法，错误级别类似日志的 info、warn、error，据此判断错误的严重程度。ApplicationErrorCodeEnum 是应用服务的错误码实现类：

```java
public enum ApplicationErrorCodeEnum implements IErrorCodeEnum {
    SUCCESS("200", "成功"),
    FAILURE("300", "系统异常"),
    COMPONENT_LOAD_PROPERTIES_OBJ_HAD_EXIST("000001", "配置文件加载类已经存在"),
    SYS_ERROR_ENCRYPT_SINGED(IErrorCodeEnum.MODULE_SYSTEM, "000002", "签名加密错误"),
    USER_NOT_FOUND(IErrorCodeEnum.MODULE_USER, "000003", "用户不存在！"),
    USER_PWD_ERROR(IErrorCodeEnum.MODULE_USER, "000004", "用户密码错误！");

    @Override
    public String getModule() {
        return IErrorCodeEnum.MODULE_SYSTEM + this.code;
    }

    @Override
    public String getMessage() {
        return this.message;
    }
}
```

枚举主要有 code、message 两个属性，提供多个构造方法：直接传 code 和 message 时默认用系统模块、普通级别，也可显式指定 module 和错误级别。错误编号要保证不冲突，并按服务分段——用户服务 1 开头、订单服务 2 开头，一看错误码就知道哪个模块出了问题。

使用上也要规范：同一个异常不要在 DAO、service、controller 层层处理抛出，层次混乱且难维护。统一约定为：DAO 不做判断，由 service 业务层做判断处理并抛出，controller 接入层负责捕获，最后封装返回给调用方。

统一接口数据返回用 ApiRespResult\<T\> 泛型类：web 层返回给前端或调用方的格式全部统一，第三方平台或前后端对接清晰规范，也便于统一维护。返回结果固定封装结果码、结果信息、数据对象、扩展信息四部分：

```json
{
  "code": "SYS_200",
  "msg": "成功",
  "extendData": null,
  "data": {
    "id": null,
    "userNo": "admin",
    "name": "admin",
    "userPwd": "ISMVXpXpadDiUoOSoAfww=",
    "phone": "123",
    "companyId": 1,
    "status": 0
  }
}
```

data 放业务数据，比如登录完成后把用户对象整个塞进去；extendData 放附带的定制内容。code 默认初始化为 SUCCESS 的值；error() 方法传入错误码枚举即可，提示信息统一封装，不用手工组装。isSuccess() 便于前端快速判断——不必解析 code 再比对是否等于 200，将来成功码变更前端也不用大改。

## 用户服务核心类：登录接口与资源服务安全配置

stock-user 的 pom 补齐之后，common-dao 下也要加上 MyBatis、数据库连接池 Druid 和 MySQL 驱动依赖。启动类 StockUserApplication 需要一组注解：@SpringBootApplication 标识 Spring Boot 程序，@EnableDiscoveryClient 开启 Nacos 注册发现，@ComponentScan 扫描 com.itcast 基础包，@MapperScan 扫描数据层（数据层采用 MyBatis 实现），@EnableTransactionManagement 开启事务管理器。

数据层 IStockUserDao 只有一个方法：根据用户编号查找用户对象 getUserByUserNo(String userNo)，因为要提供用户登录接口，必须先找到对应用户。对应的 StockUserMapper.xml 放在 dao 下的 mapper 包里，写好后重点检查 namespace 路径能否 Ctrl+点击定位到（能定位说明路径配置 OK），再核对属性映射与 SQL 查询实现。

服务层接口 IStockUserService 与实现类 StockUserServiceImpl，实现的是 userLogin 登录处理：

```java
@Override
public TradeUser userLogin(String userNo, String userPwd) throws ComponentException {
    // 1. 根据用户账号查找用户对象
    TradeUser tradeUser = stockUserDao.getUserByUserNo(userNo);
    if (null == tradeUser) {
        throw new ComponentException(ApplicationErrorCodeEnum.USER_NOT_FOUND);
    }
    // 2. 校验密码
    if (!tradeUser.getUserPwd().equals(userPwd)) {
        throw new ComponentException(ApplicationErrorCodeEnum.USER_PWD_ERROR);
    }
    return tradeUser;
}
```

第一步查用户，没找到说明账号有问题，直接抛异常，后续逻辑不再执行；库里存的是密文，传入的密码要先做加密处理，再与数据库密码比对，两边一致才登录成功，不一致抛密码错误异常。controller 层 StockUserController 注入业务层接口，提供 /user/userLogin 接口，接收 userNo、userPwd 并做参数名映射；外层套 try-catch——按前面的约定，异常在最外层 web 层统一捕获，错误消息、系统错误都能方便地统一包装。提速技巧：先写好实现类，右键 Refactor 生成接口方法时勾选复制注释，javadoc 会一起搬到接口里。

接下来是与 Spring Security OAuth2 集成的安全配置。ResourceSecurityConfigurer 实现 ResourceServerConfigurer 接口，注入 RemoteTokenServices（Spring Security OAuth2 包下，负责远程 token 调用）和 lbRestTemplate，做两件事：给 RemoteTokenServices set 进 RestTemplate 才能实现远程调用访问；再把 tokenServices 放进 ResourceServerSecurityConfigurer。资源服务安全配置里，csrf().disable() 关闭跨站请求伪造，antMatchers 配置需要认证的接口，再按需指定登录页、登录接口、登录失败与成功页面的跳转；其他要暴露或排除的接口可参照认证服务 WebSecurityConfig。lbRestTemplate 支持负载均衡，并覆写 DefaultResponseErrorHandler：响应状态不等于 BAD_REQUEST（400）才交由 super.handleError 处理，其余错误状态都会拦截。注解不能漏：@EnableResourceServer 开启资源服务，@EnableGlobalMethodSecurity(prePostEnabled = true) 开启方法级别安全控制，prePostEnabled 属性要预先开启。

工程配置分四段：服务基本信息（端口 10681、名称 stock-user、Nacos 地址）、Druid 数据源、Spring Security OAuth2 认证配置、MyBatis 配置。作为资源服务，要配置校验接口地址和 client 预置信息：

```yaml
security:
  oauth2:
    resource:
      loadBalanced: true
      token-info-uri: http://trade-auth/oauth/check_token
    client:
      client-id: app
      client-secret: app
      scope: server
      access-token-uri: http://trade-auth/oauth/token
      user-authorization-uri: http://trade-auth/oauth/authorize
mybatis:
  mapper-locations: classpath:/com/itcast/trade/stock/user/dao/mapper/*.xml
```

mybatis 的 mapper-locations 路径务必与实际包路径一致（演示工程包名 com.itcast.trade.stock.user），写错启动验证立刻踩坑。

启动验证按依赖顺序来：Nacos、Redis、认证服务先起来，再启动用户服务。Postman 不带 token 请求 http://127.0.0.1:10681/user/userLogin?userNo=admin&userPwd=admin 返回 unauthorized，说明未经认证、无权访问资源；用密码模式申请 token，回到该请求在 Authorization 里选 Bearer Token（选项不要选错）粘入再发——不再报 401，而是系统异常：找不到数据层接口的实现，后台提示没有绑定对应的 SQL。根因是 mybatis 的 mapper 路径扫描与实际包名不符，改对后重启即可；token 存在 Redis 里，服务重启后依然有效，不用重新申请，直接再访问就能拿到 data 里的完整用户资料。用户服务至此成功加入 OAuth2 统一认证体系。

## 网关方案与 Druid 监控配置

微服务鉴权有两种方案：网关统一鉴权，或各微服务节点自己鉴权。本篇采用后者以保证各节点安全可靠，网关只做统一转发、不做鉴权校验。经过实践摸索：按这个方案 Spring Cloud Gateway 不需要集成 Spring Security——网关职责就是接收客户端请求并转发，这里不需要做 OAuth2 鉴权；微服务自身要鉴权，仍需 Spring Security OAuth2 组件，直接作为资源服务，收到网关转发的 token 后发给认证服务校验。这样也避免了微服务直接对外暴露的安全问题——若只靠网关统一鉴权而节点在外网暴露，第三方就能绕过网关直接访问资源接口。工程里还保留了一段注释掉的 OAuth2 实现，便于后续扩展参考。

Druid 是阿里推出的开源数据库连接池，功能、性能、扩展性都超过 DBCP、C3P0、BoneCP、Proxool、jBoss DataSource 等；在阿里巴巴内部部署超过 600 个应用，经严苛生产环境检验，可靠性较强，可放心使用（选稳定版本）。监控台包含数据源配置信息、SQL 监控、防火墙、URI 监控、Session 监控、Spring 监控等，最常用的是 SQL 监控和数据源配置信息。Druid 集成配置放在用户服务工程，Gateway 不需要——网关只转发，不与数据库产生连接和交互。先看实际配置：

```yaml
spring:
  datasource:
    type: com.alibaba.druid.pool.DruidDataSource
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:mysql://192.168.19.150:3306/trade_stock?useUnicode=true&characterEncoding=utf8
    username: root
    password: 654321
    initial-size: 5
    min-idle: 5
    maxActive: 20
    maxWait: 60000
    timeBetweenEvictionRunsMillis: 60000
    minEvictableIdleTimeMillis: 300000
    validationQuery: SELECT 1 FROM DUAL
    testWhileIdle: true
    testOnBorrow: false
    testOnReturn: false
    poolPreparedStatements: true
    maxPoolPreparedStatementPerConnectionSize: 20
    filters: stat, wall, log4j
    connectionProperties: druid.stat.mergeSql=true;druid.stat.slowSqlMillis=5000
```

把逐项讲过的监控参数与实际配置对照一下：

| 参数 | 作用说明 | 演示工程取值 |
|---|---|---|
| initialSize / maxActive / minIdle | 初始化物理连接个数（显式调用 init 或首次 getConnection 时初始化）、最大连接数、最小空闲连接数 | 5 / 20 / 5 |
| maxWait | 获取连接时的最大等待时间，网络阻塞时不能一直等待 | 60000 |
| validationQuery | 检测连接是否有效的 SQL | SELECT 1 FROM DUAL |
| testWhileIdle | 申请连接时检测：空闲时间大于 timeBetweenEvictionRunsMillis 就执行 validationQuery，建议开启 | true |
| testOnBorrow / testOnReturn | 申请/归还连接时执行 validationQuery 检测，会降低性能 | false / false |
| minEvictableIdleTimeMillis | 连接保持空闲而不被驱逐的最长时间 | 300000 |
| poolPreparedStatements | 是否缓存 PreparedStatement；启用 PSCache 须配 maxPoolPreparedStatementPerConnectionSize 大于 0（大于 0 时自动触发置为 true） | true，配套 20 |
| filters | 按别名配置扩展插件：stat 监控统计、log4j 日志、wall 防 SQL 注入，多个逗号拼接 | stat, wall, log4j |
| connectionProperties | 打开 mergeSql 合并 SQL，slowSqlMillis 设定慢 SQL 阈值 | mergeSql=true; slowSqlMillis=5000 |

细节补充：name 用于区分多数据源，不配置会生成默认名，至少 1.0.5 以上版本才生效；driverClassName 可不配（Druid 按 url 自动识别 dbType），但建议显式配置以防自动识别引发监控问题；exceptionSorter 按 dbType 自动识别，数据库抛出不可恢复异常时抛弃该连接；proxyFilters 类型是 List，与 filters 同时配置时是组合关系，都会生效。

开启监控后台靠 stat-view-servlet 配置：url-pattern 指定为 /druid/*（访问路径务必正确，之后按此路径访问）；IP 白名单 allow 为空则允许所有访问，deny 与 allow 同时存在时 deny 优先；reset-enable: false 不禁用页面上的 Reset All 功能；登录名 login-username: admin、密码 login-password: admin123；enabled: true 打开监控后台开关。web-stat-filter 开启 Web 监控，url-pattern 为 /*，排除静态资源与 /druid/*。

## 网关核心实现：全局过滤器与路由转发

新建 bulls-stock-gateway 模块，pom 依赖不多：spring-cloud-starter-gateway 网关组件、spring-boot-starter-actuator 监控、com.alibaba.cloud 的 Nacos 服务注册发现。启动类 StockGatewayApplication 里 @EnableDiscoveryClient 不可少——网关必须能找到其他微服务的信息，@ComponentScan 指定 com.itcast 基础包。

真正承载 OAuth2 认证转发的是全局过滤器 StockRequestGlobalFilter，放在 filters 包下，实现 GlobalFilter 与 Ordered 接口：

```java
@Component
@Log4j2
public class StockRequestGlobalFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String authentication = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (StringUtils.isNotEmpty(authentication)) {
            log.info("enter stockRequestGlobalFilter filter method: " + authentication);
        }
        return chain.filter(exchange.mutate().build());
    }

    @Override
    public int getOrder() {
        return 0;
    }
}
```

它从请求头取出 Authorization 的值，不为空时打一条日志，并通过 mutate 把头部信息原样带上继续向下转发——OAuth2 认证时会附带额外信息，过滤器保证这些头部信息经 Gateway 转发不丢失，认证校验的完整性才有保障。代码里定义的 HEADER_NAME 常量没有被引用，属调试遗留，清理掉。

application.yml 分两部分：服务基本配置和路由转发配置。discovery.locator.enabled 设为 true，允许通过 Nacos 服务名称路由转发，不用指定具体 IP——服务变更不用回头改网关，既保证高可用又方便维护。routes 是复数可配多条，一组路由以横线开头：

```yaml
spring:
  cloud:
    gateway:
      discovery:
        locator:
          enabled: true
      routes:
        - id: stock-user
          uri: lb://stock-user
          predicates:
            - Path=/user/**
        - id: trade-auth
          uri: lb://trade-auth
          predicates:
            - Path=/oauth/**
logging:
  level:
    root: info
```

每组路由要有唯一 id 标识；uri 用 lb:// 前缀按服务名负载均衡转发；Path=/user/** 表示凡是以 /user 开头访问网关的请求都转发到用户服务——网关端口 10680，客户端请求 /user/login 就匹配这条规则；Path 可配置多个，把开放型接口和带权限控制的接口分门别类做不同控制。注意不要开启 Method=GET,POST 限定：一旦指定，网关就只支持指定的请求类型，DELETE 等请求不会被接收和转发；认证场景申请 token、刷新 token 可能用到不同请求方式，默认允许所有请求方式更稳妥，生产级别有严格要求再按需配置。

## 小结

用户服务篇把只能返回字符串的简易服务升级成 OAuth2 资源服务：工程分层搭建，统一异常与统一返回先行封装，登录核心逻辑落在"查用户、密文比对密码"两步，资源服务靠 @EnableResourceServer + RemoteTokenServices 远程校验 token；启动验证还踩了 mapper 路径配错导致"找不到数据层接口实现"的坑。网关服务篇保持轻量：只做转发不做鉴权，全局过滤器保证 Authorization 头不丢，两条路由按服务名转发用户服务与认证服务；Druid 监控集成在用户服务侧，filters 取 stat、wall、log4j 并开启监控后台。这些公用的地方统一处理后，复用方便、直观清晰，便于后续维护与扩展。
