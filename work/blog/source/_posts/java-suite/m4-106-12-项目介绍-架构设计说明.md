# 智牛股技术架构、四大技术特色、选型方法论（RocketMQ/Sentinel 案例）与工程结构规范

上一篇把智牛股三张架构图铺开，本篇收口：回顾五个服务群的职责边界，看整体技术说明与四大技术特色、18 项技术解决方案与选型方法论，用 RocketMQ 和 Sentinel 两个案例示范"怎么比、怎么选"，最后以工程结构规范收尾。

## 先给结论

- 架构收口的关键：接入层 Nginx 主备组队，Spring Cloud Gateway 按请求路径映射微服务；交易群内部 Spring Boot 2.X + Protobuf + gRPC 连接调用；代理服务无状态，只做接入与分发。
- 服务粒度要微观解耦、宏观统一：基础服务群不能过度耦合；业务服务群不能过度分散；同步服务群涉及资金实时操作，必须保证高实时性与数据安全。
- 组件选型都有对照组：Nacos 优于 Eureka 与 Config，Sentinel 优于 Hystrix（后台可实时改熔断降级策略），RocketMQ 保证消息强一致性，ElasticSearch 搜索应用最广。
- 选型方法论：技术服务于业务，脱离业务是空中楼阁；不变的需求做成平台级服务，多变的需求快速迭代。
- MQ 结论 RocketMQ：金融场景要求严格顺序，Kafka 多 Topic 时衰减严重（256 Topic 时 2215 条/秒，RocketMQ 75000）；熔断结论 Sentinel：资源模型比 Hystrix 的线程池模型更轻更稳。
- 第二章转入工程规范：应用分层、DO/DTO/BO/AO/VO/Query 领域模型、版本号起始必须 1.0.0、接口 I 开头实现类 Implement 结尾。

## 架构收口：五个服务群的职责与边界

架构设计说明是对三个架构层面的回顾总结。接入层与前置服务在生产环境用 Nginx 主备组队接入，通过 Spring Cloud Gateway 调用业务集群，按请求路径映射不同微服务。

交易服务群是项目核心。代理服务负责客户端接入与数据分发，Netty 对接，无状态、不负责具体业务逻辑；内部交易和行情服务群用 Spring Boot 2.X + Protobuf + gRPC 连接调用。行情服务负责第三方行情源接入与订阅下发；交易服务处理撮合、深度成交、委托挂单、撤单等核心逻辑；再加仓位、资金、监控服务。

基础服务群把底层基础模块抽离封装（系统管理、用户中心、统一鉴权等），职能单一、不能过度耦合，便于其他服务接入。业务服务群包含派息分红、拆股强平、支付入金出金、报表、活动等，负责非交易核心的用户业务；要把控服务粒度——微观解耦、宏观统一，不能为了解耦过度分散、流转环节过多，治理部署要加强核心业务管控与稳定性。

任务调度服务群处理异步计算（监听、反写、预警触发），解耦核心业务，采用 ElasticJob 调度框架提升吞吐、可用性与并发能力。同步服务群做交易数据和业务数据的同步——两块数据分离式设计，覆盖用户信息与资金、产品配置与管理、订单交易和流水数据；实时性要求高：结算系统可以隔天结算，涉及资金实时操作必须保证实时性，兼顾数据安全与稳定。

治理上，Spring Cloud 生态有丰富开源治理组件（负载均衡、动态路由、日志采集、全链路监控、熔断降级），这也是很多人从 Dubbo 转向 Spring Cloud 的原因；对比 Istio 网格——它把框架与治理拆分、适合大规模微服务群，数十个微服务的规模没必要上，Spring Cloud 足够驾驭。数据层 PostgreSQL 主从存交易数据、MariaDB 集群存业务数据，读写分离保障主库稳定，集群提升扩展性与高可用。

## 整体技术说明与四大技术特色

整体服务层划分为前端交互、接入层、接口层、服务中间件、数据层与服务管理组件，支持 Jenkins 持续集成、Docker 虚拟化与 DevOps 管理。业务服务集成 Spring Cloud Gateway，支持自定义路由与 OAuth2 统一认证鉴权；交易服务用 Netty NIO 接入、内部 gRPC + Protobuf 通讯。服务注册与统一配置用 Nacos 集群，以 MariaDB 为数据源、Nginx 负载，支持注册发现与统一配置；可按环境管理配置并动态更新。

应用层与通信分内外两线。业务服务通过 Gateway 对外，交易和行情服务通过代理服务对外；代理服务按头部信息（请求类型）路由转发。内部通信采用异步架构 + RocketMQ 集群提升吞吐；服务间通讯用 Spring Boot Starter gRPC + Protobuf——gRPC 性能高于基于 HTTP 的 Feign、Ribbon、RestTemplate，Protobuf 序列化效率高于 JSON，且支持 Java、Go、C 等平台，用于下单、资金查询、订单查询等交易数据处理。Netty 长连接 NIO 框架处理交易数据（异步）与行情数据（高频）。业务数据对外走 HTTP、遵循 RESTful，用 HATEOAS 高阶形态、前后分离方式实现管理后台与配置处理。

中间件选型理由：Redis 三主三从集群扛用户数据、产品数据等热点；MongoDB 集群适合高频次存取且保障持久化（支付信息日志、二次加工数据）；Ceph 强一致性保障可靠，适合金融平台的小文件——证明文件、图像、验证码、银行卡附件；ElasticSearch 搜索应用最广、性能优越，处理埋点、登录日志行为；XXL-JOB 轻量级任务调度，开发迅速、易扩展，大众点评、京东优信二手车、360 金融开箱即用；Seata Server（前身 FESCAR，阿里开源）高性能、易用、侵入低，底层 Netty 实现，处理交易与业务服务之间的事务。

四大技术特色：一是前后分离架构，职责单一、前台更新不影响后台、便于扩展维护；二是交易服务基于 NIO 非阻塞 Netty、对内 gRPC + Protobuf——对外 Netty 传输、对内 gRPC 通讯有效结合；三是业务服务用 Spring Cloud Gateway 统一网关接入（较 Zuul 两到三倍性能提升），前置 Nginx 反向代理，RESTful 短连接与 Netty 流式长连接并存；四是遵循主流、选取先进——Nacos 相比 Eureka 与 Config 性能明显改进，Sentinel 相比 Hystrix 性能更优、可实时修改熔断降级策略，RocketMQ 保证消息强一致性，ES 搜索优越。Seata 是优秀的分布式事务 TCC 框架，不必像两阶段提交那样编写补偿接口；Spring Boot 2.X + Gateway + Spring Security OAuth2 实现统一认证鉴权与 Token 增强技术（TokenEnhancer）；Jenkins、Git、Maven、Docker、Registry 组成持续集成；各集群贴合生产实践，支撑海量数据与高并发。

## 18 项技术解决方案与选型方法论

项目把核心技术手段整理成 18 项解决方案，后续章节逐项落地：

| 解决方案 | 技术选型 |
| --- | --- |
| 服务高可用 | KeepAlived + LVS + Nginx |
| 微服务网关 | Spring Cloud Gateway |
| 微服务高效通讯 | SpringBoot 2.2.x + gRPC + Protobuf + Netty |
| 注册发现与配置管理 | Nacos 集群 + MariaDB + Nginx |
| 熔断降级限流 | Sentinel + Dashboard（动态配置） |
| 分布式事务 | Seata Server |
| 异步消息架构 | RocketMQ 集群 |
| 链路监控 | CAT 集群 |
| 统一鉴权 | OAuth2 + Redis + TokenEnhancer |
| 统一日志 | ElasticSearch + Logstash + Kibana |
| 热点缓存 | Redis 集群 |
| 分布式锁 | Spring Integration Redis |
| 前后分离与文档管理 | Swagger2 聚合文档（与 Spring Data REST 集成） |
| 多数据源 | Spring Boot + Druid + JPA/MyBatis |
| 分布式文件存储 | Ceph 集群 |
| 分布式搜索 | ElasticSearch 集群 |
| 分布式任务调度 | XXL-JOB 集群 |
| 持续集成自动发布 | Jenkins + Git + Maven + Docker + Registry |

选型方法论核心：技术是为业务服务的，脱离业务的技术是空中楼阁。项目不是科研——敏捷迭代对进度产出要求越来越高；技术价值来源于用户与业务的需要。淘宝从单一架构到分布式架构、单机到机房再到阿里云，随业务逐步演进——起步就上几十台节点并不现实，在发展周期内找到合适的技术才最好。

合适的选型让初创公司少走弯路、产品更快推向市场。动手前摸清业务特性与场景、交互复杂度、用户规模、峰值（如双 11）、推广运营计划，再做版本与迭代规划；互联网产品版本周期两周左右即可——拖到三个月，机会就错过了。变与不变要分清：用户管理、系统管理、权限管理这些底层每个项目都离不开，值得精雕细琢、统一鉴权并提供单点登录，做成平台级服务；将来重构底层要花数倍代价且易产生风险。多变的需求（充 100 送 20 活动半个月下掉、用户推荐送金、抽奖）以实现功能为主快速迭代，有市场反应后第二版再补性能与扩展性。

## 两个选型案例：MQ 与熔断组件

第一个案例是 MQ。组件众多：RocketMQ、Kafka、RabbitMQ、ActiveMQ、ZeroMQ，按成熟度、社区、文档、协议、事务、顺序、单机性能等维度对比，ZeroMQ 成熟度不高先排除：

| 维度 | ActiveMQ | RabbitMQ | RocketMQ | Kafka |
| --- | --- | --- | --- | --- |
| 优点 | 功能齐全，开源项目多用 | Erlang 开发，并发支持好 | 上万队列、多消费模式，可靠性好 | 多文件并发写入，高吞吐 |
| 协议 | 遵循 AMQP，支持 OpenWire、STOMP、XMPP | 遵循 AMQP | 借鉴 Kafka 改进的定制协议 | 仿 AMQP，借鉴 ActiveMQ、RabbitMQ 改进 |
| 事务/顺序 | 支持事务，不能保证严格顺序 | 不支持事务，不能保证严格顺序 | 支持事务，保证严格顺序 | 支持事务，不能保证严格顺序 |
| 单机吞吐 | 万级 | 万级 | 约 10 万 TPS | 数十万级，可到百万级 |

金融平台要求较高的性能和数据一致性：ActiveMQ、RabbitMQ 成熟但并非针对高吞吐设计（万级 TPS）；剩下 RocketMQ 与 Kafka。Kafka 单机吞吐确实更高，但金融场景对一致性要求苛刻——Kafka 每个 partition 对应一个物理文件，多 Topic 下不能保证严格顺序，数据容易错乱。压测数据更直观：

| Topic 数 | RocketMQ（条/秒） | Kafka（条/秒） |
| --- | --- | --- |
| 64 | 90000 | 136000 |
| 128 | 78000 | 8500 |
| 256 | 75000 | 2215 |

64 Topic 时 Kafka 领先，128 Topic 跌到 8500，256 Topic 只剩 2215；RocketMQ 稳定在七八万。RocketMQ 接近 Kafka 架构重新设计，支持上千个 Topic 而不衰减，集群模式下 Kafka 不占优势；单机存储不及 Kafka 可靠集群弥补——没有完美的技术。综合看 RocketMQ 更适合金融场景，并经阿里支付场景海量数据验证。

第二个案例是熔断组件：Hystrix 已停止开发，推荐 Resilience4j 与 Sentinel。核心差异在设计模型——Hystrix 采用执行模型，基于 RxJava、线程池执行；Sentinel 采用资源模型，资源定义与配置耦合度更低，设计更具优势。Hystrix 的线程池隔离隔离度高，但上下文切换开销过高、影响低延迟调用；Sentinel 用并发线程数模式流控提供隔离，结合基于响应时间的熔断降级——平均响应时间较高时自动降级，防止过多慢调用占满并发数造成级联阻塞。加上动态规则配置、插件式扩展与控制台监控，Sentinel 在流量控制、系统保护、实时监控方面支持更多，轻量高性能，适合金融交易场景——这就是选它做限流熔断降级组件的原因。

## 环境搭建开篇：工程结构规范

第二章《工程规范与环境搭建》两个目标：掌握工程代码编写规范（利于团队协作、便于扩展维护）；掌握工程环境搭建配置——智牛股采用 Spring Cloud Alibaba 微服务技术解决方案，要完成其环境配置和集成。步骤：先讲工程结构规范（详细参考阿里巴巴 Java 开发手册），再搭建环境、集成 Spring Cloud Alibaba，用简单示例验证。

应用分层把请求链拆成五段：终端显示层负责展示；Web 层接收终端 request、处理完通过 response 返回，也可做成开放接口——前后分离时提供 API 和文档、Ajax 调用；Service 层负责业务逻辑（校验、数据判断）；DAO 层负责数据源操作（MySQL、PostgreSQL）与外部接口、第三方平台（ERP 对接 MES）。数据流向：DAO 取数不做逻辑，交 Service 处理完返回 Web 层。

分层领域模型约定各层之间的对象语言：

| 对象 | 定位 |
| --- | --- |
| DO（Data Object） | 与数据库表结构一一对应，通过 DAO 层向上传输数据源对象 |
| DTO（Data Transfer Object） | 数据传输对象，Service 或 Manager 向外传输；跨进程或远程传输时用，不含业务逻辑 |
| BO（Business Object） | 业务对象，Service 层输出的封装业务逻辑的对象 |
| AO（Application Object） | 应用对象，Web 层与 Service 层之间抽象复用的对象模型，复用度不高 |
| VO（View Object） | 显示层对象，Web 向模板渲染引擎传输（如分页结果返回终端） |
| Query | 数据查询对象，各层接收上层的查询请求 |
| POJO（Plain Ordinary Java Object） | 普通 Java 对象，只有属性及 set/get 方法 |

Query 强制约束：超过两个参数的查询封装必须包装为对象，禁止 Map——调用方不知道要传哪些参数。版本规范围绕 Maven 的 GroupID、ArtifactID、Version 组成唯一版本标识展开：

```text
GroupID    com.(公司/BU).业务线(子业务线)   最多四级
ArtifactID 产品线名-模块名                  如 dubbo-client、spring-boot、spring-mvc
Version    主版本号.次版本号.修订版本号     起始版本必须为 1.0.0，而不是 0.0.1
```

主版本号代表产品方向改变、新功能或较大技术调整；次版本号是影响范围极小的调整；修订版本号修复 bug、优化细节。代码规范：类名方法名驼峰命名、不用数字拼音混合；接口以 I 开头（如 IUserService），实现类以 Implement 结尾；命名风格、常量定义、代码格式、集合处理、并发处理、异常日志等详见阿里巴巴 Java 开发手册。环境侧准备对应版本的 JDK、Maven、Nacos，IDEA 装 Maven Helper、Lombok 插件。

## 小结

四个学习目标到此闭环：了解整体设计与技术栈、掌握金融背景知识、了解技术特色与解决方案、掌握技术选型。三层级支持多种运作模式——平台可作顶层集团给其他交易商提供服务（SaaS 化），也可由独立交易商直接面向 C 端运作；建议用东方财富、同花顺等模拟交易软件加深对交易业务的认知。选型心法：掌握业务背景、抓住业务核心，业务与技术有效结合；技术比对不能固步自封，知道何时何地用何种技术。下一章进入环境搭建与编码。
