# Otter 同步任务配置链路：channel、pipeline、映射关系与数据聚合服务定位

环境装完只是把舞台搭好，这一单元九个视频才是 Otter 的正戏：在管理页面上把"119 源库同步到 97 目标库"这件事一步步配出来，用增删改实测验证，最后揭晓整条同步链路服务的对象，数据聚合微服务 pd-aggregation。全程零代码，只有页面配置和几条 SQL，关键在于把步骤链和每步的卡点记牢。

## 先给结论

- 准备工作只做一件事：源库（119）和目标库（97）里各建一个 otter_test 库（名字任意，字符集 utf8），库里各建同一张商品表 tb_item，同步以这张表为样本。
- 配置链固定六步：数据源（otter-src/otter-dst）→ 数据表（schema 加 table 绑定数据源）→ canal（内嵌模式指向源库）→ channel（行记录模式）→ pipeline（选 node 并关联 canal）→ 映射关系（源表目标表字段级对齐）。
- 两个地址格式细节：canal 的数据库地址必须以英文分号结尾；上一单元的 zookeeper 集群地址以英文逗号结尾，别混。
- channel 建完是"停止"，pipeline 挂在 channel 下，映射关系挂在 pipeline 下；全部配完再点启用，状态才翻成运行。
- 测试朴素直接：源表 insert id=1/title=test，目标表立刻出现；update 成 test123、delete 这条记录，目标表全程跟上；日志管理能看同步信息与吞吐。
- 数据聚合服务 pd-aggregation 只做查询：pd_aggregation 库的表全由 otter 从各业务库同步而来，工程里只有 Controller 分页查询接口，不写任何同步逻辑。

## 准备工作：双库建 otter_test 与 tb_item

node 可以有多个：多台服务器每台都能装一个，在管理界面逐个添加进来即可，当前环境只部署了一个。manager 与 node 都已启动，设置同步任务的条件齐备。

同步的样本任务很明确：119 上的源库，把数据同步到 97 上的目标库。做法是在两台 MySQL 里分别新建一个名叫 otter_test 的库（名字不是必须的，随意，字符集指定 utf8），然后在两个库里各执行同一份建表 SQL：

```sql
DROP TABLE IF EXISTS `tb_item`;
CREATE TABLE `tb_item` (
    `id` bigint(20) NOT NULL COMMENT '商品id，同时也是商品编号',
    `title` varchar(100) NOT NULL COMMENT '商品标题',
    `sell_point` varchar(500) DEFAULT NULL COMMENT '商品卖点',
    `price` bigint(20) NOT NULL COMMENT '商品价格，单位为分',
    `image` varchar(500) DEFAULT NULL COMMENT '商品图片',
    `status` tinyint(4) NOT NULL DEFAULT '1' COMMENT '商品状态，1-正常，2-下架，3-删除',
    `created` datetime NOT NULL COMMENT '创建时间',
    `updated` datetime NOT NULL COMMENT '更新时间',
    PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='商品表';
```

一张商品表，八个字段，源库目标库各一份，结构完全相同。后续所有配置都围绕它展开。

## 六步配置：从数据源到映射关系

整条配置链在页面上自上而下走完：

```mermaid
flowchart LR
    A[准备工作] --> B[1 数据源配置]
    B --> C[2 数据表配置]
    C --> D[3 canal配置]
    D --> E[4 添加channel]
    E --> F[5 添加pipeline]
    F --> G[6 添加映射关系]
    G --> H[启用channel与测试]
```

### 第 1 步：数据源配置，src 与 dst 各登记一个

配置管理 → 数据源配置 → 添加。名称任意，演示源库叫 otter-src、目标库叫 otter-dst（src 即 source，dst 即 destination）；类型 mysql 不用改，用户名 root、密码 123456，编码改成 utf-8，URL 分别指向 39.99.59.119:3306 和 39.99.56.97:3306。填完先点"验证连接数据库"，页面提示"恭喜，数据库通过验证!"再保存——这一步把上一单元起的两台业务库正式登记进 manager。

### 第 2 步：数据表配置，schema 加 table 绑定数据源

配置管理 → 数据表配置 → 添加。schema name 填 otter_test（对应库名），table name 填 tb_item，查找数据源选中 otter-src，验证连接通过后保存；再添加一条完全相同的（schema、table 都一样），数据源换成 otter-dst。源表和目标表至此都登记完毕。

### 第 3 步：canal 配置，内嵌模式指向源库

配置管理 → canal配置 → 添加。Otter 使用内嵌 canal，不必单独装 canal-server，页面上登记一个即可：名称 myCanal（任意），运行模式选内嵌，zookeeper 集群选前面配好的 local-zk，数据源类型 mysql。数据库地址是本步的关键：填源库地址 39.99.59.119:3306，格式为 IP 冒号端口、必须以英文分号结尾；数据库账号 root、密码 123456，其余默认。canal 高级参数保持默认，知道含义即可：connectionCharset 决定获取 binlog 用的编码，position 指定时间戳和日志位置，batchSize 是内存控制参数，buffer 是记录 SQL 的内存缓冲区，heartbeat 配置心跳 SQL 用于主备切换。

### 第 4 步：添加 channel，同步任务的容器

channel 就是一个通道，同步任务都装在通道里。同步管理 → channel管理 → 添加：名称随意，4 到 15 个字符，演示用 myChannel（讲义示例起的是 tms-aggregation，贴合正式业务）；同步模式必须选行记录模式，同步一致性保持默认的"基于数据库反查"，其余不动。保存后列表出现 channel，运行状态"停止"——配置还没完，先不启动。

### 第 5 步：添加 pipeline，指定干活的 node 并关联 canal

点击 channel 名字进入，添加 pipeline。pipeline 名字任意，这次做的是 tb_item 的表同步，演示就叫 tb_item表同步。必选两处：一是 select 机器和 load 机器选 local-node（当前只有一个 node，只能选它；多个 node 时可选多个），二是查找 canal 选中第 3 步配置的 myCanal。其余参数全部默认，页面上有逐条解释，代表性的几个：

| 参数 | 含义 |
| :--- | :--- |
| 并行度 | Otter 调度模型的并行化参数，滑动窗口大小 |
| 数据反查线程数 | 一致性选反查数据库时，反查的并发线程数 |
| 数据载入线程数 | 目标库并行载入的并发线程数 |
| 消费批次大小 | 获取 canal 数据的 batchSize |
| dryRun 模式 | 只记录 load 日志，不真实执行同步 |
| 支持 ddl 同步 | 是否同步 ddl 语句，出错可配置自动跳过 |
| 启用公网同步 | 开启后数据传递依赖 node 的外部 ip |

保存后 pipeline 挂在 channel 下，选择"真正干活的机器"这一步就完成了。

### 第 6 步：添加映射关系，源表目标表字段级对齐

点击 pipeline 名字进入，点添加：源数据表选 otter-src 下的 otter_test.tb_item，目标数据表选 otter-dst 下的 otter_test.tb_item，两张表名字完全相同；权重、视图模式（INCLUDE）以及 EventProcessor、FileResolver 都保持默认。点下一步进入字段映射页，页面已解析出两侧字段：id、title、sell_point、price、image、status、created、updated 八个字段左右对应，全部选上（两张表完全同步），继续下一步保存。映射关系列表里出现这条记录，源表、目标表均为 otter_test.tb_item，状态"未工作"，等通道启用后才会动起来。

## 启动通道与测试：源表增删改，目标表全程跟上

配置全部完成后，到同步管理里点 myChannel 的启用，确认后状态翻成运行。

测试方法朴素：源表操作，目标表验收。先用 Navicat 确认两边 tb_item 都是空的；在 119 源表插入一条 id=1、title=test 的记录（价格、图片、日期随手填）并提交，切到 97 目标表刷新，数据已经进来了。再测 update：源表把 title 改成 test123 提交，目标表同步变过来。最后测 delete：源表删掉这条记录，目标表里同样消失。增删改三类操作全部跟上，同步生效。

监控侧也能看到过程：日志管理里可以查看同步信息、db 大小，运行状态显示工作中，映射关系列表的同步状态同步次数都会动。

## 数据聚合服务 pd-aggregation：同步数据的查询出口

链路跑通后回到本章主角。数据聚合微服务对应的 Maven 工程是 pd-aggregation，提供 TMS 中各种作业、单据、任务的集中查询功能；它操作的数据库是 pd_aggregation，库里所有表和数据都是通过 otter 从其他业务库同步过来的。

这个工程只针对同步过来的数据做查询操作，没有新的技术点，课程直接提供代码拿来用。看两个 Controller 就能明白形态，司机聚合平台：

```java
@Api(tags = "司机聚合平台")
@RestController
@RequestMapping("appDriver")
public class AppDriverController {
    @Autowired
    private DriverService driverService;

    @PostMapping("/page")
    PageResponse<DriverJobDTO> findByPage(@RequestBody AppDriverQueryDTO dto) {
        return driverService.findByPage(dto);
    }
}
```

管理后台聚合平台一口气挂了四个分页查询：

```java
@Api(tags = "管理后台聚合平台")
@RestController
@RequestMapping("webManager")
public class WebManagerController {
    @Autowired
    private WebManagerService webManagerService;

    @PostMapping("/driverJob/page")
    PageResponse<DriverJobDTO> findDriverJobByPage(@RequestBody DriverJobQueryDTO dto) {
        return webManagerService.findDriverJobByPage(dto);
    }

    @PostMapping("/taskPickupDispatchJob/page")
    PageResponse<TaskPickupDispatchDTO> findTaskPickupDispatchJobByPage(@RequestBody TaskPickupDispatchQueryDTO dto) {
        return webManagerService.findTaskPickupDispatchJobByPage(dto);
    }

    @PostMapping("/transportOrder/page")
    PageResponse<TransportOrderDTO> findTransportOrderByPage(@RequestBody TransportOrderQueryDTO dto) {
        return webManagerService.findTransportOrderByPage(dto);
    }

    @PostMapping("/taskTransport/page")
    PageResponse<TaskTransportDTO> findTaskTransportByPage(@RequestBody TaskTransportQueryDTO dto) {
        return webManagerService.findTaskTransportByPage(dto);
    }
}
```

司机任务、取派任务、运输单、运输任务——TMS 各业务库的数据经由 otter 汇入 pd_aggregation，聚合服务用最普通的分页查询把它们集中供给司机端和后台。这正是前面所有安装、配置工作的意义所在：数据从业务库流进聚合库，服务层只管查。

## 小结

九个视频走完一条完整的配置链：双库建 otter_test 与 tb_item 打底，数据源、数据表、canal、channel、pipeline、映射关系六步页面配置，启用 channel 后源表增删改、目标表全程跟上。链路上有四个关键卡点：canal 数据库地址以英文分号结尾、channel 必须选行记录模式、pipeline 要同时指定 node 与 canal、映射关系决定字段级同步范围。数据聚合服务 pd-aggregation 是这条链路的终点：表结构靠 otter 同步，代码只剩查询。下一单元导入数据同步服务代码，把这个库接进 TMS 的真实业务。
