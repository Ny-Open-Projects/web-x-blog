# cron 表达式：把「什么时间执行」写成一行字符串

定时任务绕不开一个前置问题：任务到底什么时候触发。优惠券要在每天上午十点、下午三点、晚上八点发放，财务数据要在每天凌晨一点结算，对账程序每隔十分钟要跑一轮，这些规则各不相同，而且业务方随时可能调整。把触发时间硬编码在代码里显然不现实，业界通行的做法是用一种专门描述时间规则的表达式，也就是 cron 表达式。Elastic-Job 构建在 Quartz 之上，沿用的正是 Quartz 这套 cron 语法，写定时还款任务之前必须先把它的读写规则吃透。

## 先给结论

- cron 表达式的本质就是一个字符串，按空格拆成若干部分，每部分描述一个时间维度，用来表达「什么时刻、以什么频率执行」。
- 完整格式共七部分：秒、分、时、日、月、周、年，其中年可选，所以最少六部分，各部分之间用空格隔开。
- 取值大多从 0 开始，秒和分是 0 到 59，小时是 0 到 23，这个习惯与日常说法不同，容易写错。
- 特殊符号 `*` `?` `-` `,` `/` `L` `W` `#` 是灵活性的来源，重点掌握前五个，`L` `W` `#` 认识即可。
- 定时还款任务测试时用每 5 秒一次的 `0/5 * * * * ?`，真实上线要按业务改写，例如每天早上五点执行一次。

## 七部分结构：一个字符串拆出一张时间表

cron 表达式在编码层面就是一个字符串，但这个字符串有严格的格式约定。它由七部分组成，每部分之间用一个空格隔开，每一部分对应一个时间维度，含义与取值范围各不相同。

| 位置 | 含义 | 取值范围 | 允许的特殊符号 |
|---|---|---|---|
| 第 1 部分 | 秒 | 0-59 | `,-*/` |
| 第 2 部分 | 分 | 0-59 | `,-*/` |
| 第 3 部分 | 时 | 0-23 | `,-*/` |
| 第 4 部分 | 日 | 1-31 | `, -* / ? L W` |
| 第 5 部分 | 月 | 1-12 或 JAN-DEC | `,-*/` |
| 第 6 部分 | 周 | 1-7 或 SUN-SAT（1 表示星期日） | `, -* / ? L #` |
| 第 7 部分 | 年（可选） | 1970-2099 | `,-*/` |

两个格式上的硬约束值得单独强调。**第一，年可以省略。** 日常业务定义时间规则时很少精确到「哪一年」，所以第七部分通常不写，表达式因此最少六部分，绝大多数工程里见到的 cron 都是六段式。**第二，取值大多从 0 开始。** 秒、分从 0 起，小时从 0 起，0 表示零点而不是 1 点；周的取值更是反直觉，1 表示星期日，2 表示星期一，依次往后推，7 表示星期六，读表达式时必须按这个口径换算。

拿一个六段式的例子按位置逐段解读，例如 `0 26,29,33 * * ?`：第 1 段秒是 0，第 2 段分是 26、29、33 三个值，第 3 段小时是 `*` 表示每小时，第 4 段日是 `?`，第 5 段月是 `*`，第 6 段周是 `?`。整体含义就是每小时的 26 分、29 分、33 分各触发一次任务。读表达式的诀窍就是对着这张表逐段对号入座，数清楚段数，再核对每段的取值范围。

## 特殊符号：灵活性从哪来

不同业务对时间规则的要求千差万别，只用固定的数字显然不够，cron 为每个字段准备了一组特殊符号，这是表达式灵活多变的能力来源。

**星号 `*` 表示任意值。** 放在哪个字段就代表该字段取所有可能的值，月字段写 `*` 就是任意一个月，写满星号的段相当于「这个维度不设限」。

**问号 `?` 表示不确定、不指定。** 它只用在日和周这两个字段上，而且两者互斥：日指定了具体值，周就得写 `?`；周指定了具体值，日就得写 `?`。典型场景是「每月 20 号触发」：20 号是几号写在了日字段，而每个月 20 号是星期几根本不确定，周字段没法给值，只能写 `?`，于是表达式写成 `0 0 0 20 * ?`。反过来「每周五触发」则在周字段给值、日字段写 `?`。

**逗号 `,` 表示枚举多个值。** `26,29,33` 就是三个互不连续的时刻，分别在 26 分、29 分、33 分各执行一次。

**中划线 `-` 表示连续区间。** 与逗号的区别在于值是否连续：区间 `1-20` 覆盖从 1 到 20 的每一个值，而 `1,5,20` 只命中这三个点。

**斜杠 `/` 表示频率与间隔。** 这是定时任务里出场率最高的符号，形式是「起点/步长」。`1-15/15` 表示从第 1 分开始，每隔 15 分钟运行一次；秒字段写 `0/5` 就是从 0 秒开始每 5 秒触发一次。`/` 表达的是循环频率，不是一次性区间，这是它与 `-` 的本质区别。

剩下三个符号使用频率低，能认出来即可。**L 是 last 的缩写**，表示最后一天，用在日字段是每月最后一天，用在周字段如 `6L` 表示每月最后一个星期五（按 1 是星期日的口径，6 恰好对应星期五）。**W 表示离给定日期最近的工作日**，如 `15W` 表示离本月 15 日最近的工作日，15 日是周六就提前到周五，是周日就顺延到周一。**井号 `#` 表示第几个周几**，如 `6#3` 表示该月的第三个星期五。这三个符号在实际业务里出现不多，用到时回来查表即可，不必背诵。

## 常用写法：对着例子练解读

符号表看一遍容易晕，真正有效的学习材料是例子。下面几个高频写法覆盖了大多数业务节奏，逐条给出解读。

```text
0/5 * * * * ?      从 0 秒开始每 5 秒执行一次
0 0 23 * * ?       每天的 23 点 0 分 0 秒执行一次
0 0 1 1 * ?        每月 1 号凌晨 1 点执行一次
0 26,29,33 * * ?   每小时的 26 分、29 分、33 分各执行一次
0 0 0 1-20/5 * ?   每月 1 到 20 号，从 1 号起每 5 天执行一次
```

解读这类表达式的固定套路：先数段数确认是不是六段式，再按「秒 分 时 日 月 周」的顺序逐段翻译，最后把各段的限定条件叠加起来。以 `0 0 23 * * ?` 为例，秒与分都是 0，时是 23，日、月、周分别由 `*` 与 `?` 放开限制，叠加之后就是「每天 23 点整」，没有别的歧义。

## 落到定时还款任务上

cron 表达式在项目里不是写死在代码中的，而是作为配置交给调度框架。定时还款任务的触发规则由 Apollo 配置中心下发，还款服务通过 `@Value` 注入，再组装进 Elastic-Job 的作业核心配置：

```java
@Configuration
public class ElasticJobConfig {

    // cron 表达式由 Apollo 的 micro_service.elasticjob 命名空间下发
    @Value("${p2p.job.cron}")
    private String cron;

    @Value("${p2p.job.count}")
    private int shardingCount;

    @Bean(initMethod = "init")
    public SpringJobScheduler initSimpleElasticJob(RepaymentJob repaymentJob,
                                                   ZookeeperRegistryCenter registryCenter) {
        // 作业核心配置携带任务名 cron 与分片总数 cron 就是触发规则
        JobCoreConfiguration core = JobCoreConfiguration
                .newBuilder(repaymentJob.getClass().getName(), cron, shardingCount)
                .build();
        SimpleJobConfiguration simple = new SimpleJobConfiguration(
                core, RepaymentJob.class.getCanonicalName());
        LiteJobConfiguration lite = LiteJobConfiguration
                .newBuilder(simple).overwrite(true).build();
        return new SpringJobScheduler(repaymentJob, registryCenter, lite);
    }
}
```

这条链路用一张图串起来，讲的是 cron 值从配置中心一路走到任务触发的完整路径：

```mermaid
flowchart LR
    A[Apollo 配置中心 p2p.job.cron] --> B[ElasticJobConfig 注入 cron]
    B --> C[JobCoreConfiguration 组装作业配置]
    C --> D[SpringJobScheduler 启动调度器]
    D --> E[按 cron 触发时刻表计时]
    E --> F[到达触发点调用 SimpleJob 的 execute]
```

关键路径在最后两跳：调度器持有 cron 后按它计时，每到触发点就调用一次作业类的 `execute` 方法，cron 决定「何时」，任务类决定「做什么」。讲义里测试用的 cron 是每 5 秒一次，这只是为了让分片效果肉眼可见；真实运行中不可能是这个值，例如可以设定为每天早上五点 `0 0 5 * * ?` 扫一遍到期还款计划，具体取值必须结合业务节奏与系统负载来确定。

## 常见误区

- **把周字段的 1 当成星期一。** 错例：想表达「每周一执行」，周字段写 1。正解：周字段 1 表示星期日，星期一是 2，这是 Quartz 系 cron 的历史约定，写周相关规则时必须按此换算。
- **日与周同时给具体值。** 错例：`0 0 0 20 * 5` 想表达「每月 20 号或每周五执行」。正解：日与周是互斥字段，同时指定会让语义混乱，确定了一个另一个必须写 `?`。
- **把 `/` 当成普通区间。** 错例：认为 `1-15/15` 表示只在第 1 分和第 15 分执行。正解：`/` 的语义是「起点起、按步长循环」，`1-15/15` 是从第 1 分起每隔 15 分钟触发一次。
- **把测试 cron 原样搬上生产。** 错例：联调时为了观察效果配了每 5 秒一次，上线忘了改。正解：上线前按业务节奏重设，例如每天凌晨或早上五点，并评估触发时刻的批量数据量。
- **段数写错导致解析异常。** 错例：写五段或把段序颠倒，调度器启动即报 cron 解析错误。正解：默认六段式「秒 分 时 日 月 周」，逐段核对含义与取值范围后再提交配置。

## 面试可能被问到的问题

1. 面试官追问：「cron 表达式由哪几部分组成？最少几位？」
   答：完整七部分，依次是秒、分、时、日、月、周、年，各部分用空格分隔。年是可选字段，日常业务很少精确到年，所以最少六部分，工程中最常见的就是六段式。
2. 面试官追问：「`?` 和 `*` 有什么区别？为什么日和周要用 `?`？」
   答：`*` 表示该字段取所有可能值，`?` 表示不指定。日和周在语义上互相冲突，两个都指定会破坏表达式的确定性，所以二者互斥：一个给具体值，另一个必须写 `?`，例如每月 20 号触发就是日给 20、周写 `?`。
3. 面试官追问：「`0/5 * * * * ?` 表示什么？`/` 的语义是什么？」
   答：表示从 0 秒开始每 5 秒触发一次。`/` 的语义是「起点/步长」，从起点开始按步长循环触发，表达的是频率而不是一次性区间，与表示连续区间的 `-` 有本质区别。
4. 面试官追问：「周字段的取值口径是什么？6L 是什么意思？」
   答：周字段 1 到 7 对应星期日到星期六，1 是星期日。L 是 last 的缩写，6L 表示每月的最后一个星期五。类似还有 W 表示离指定日期最近的工作日、`#` 表示第几个周几，这三个符号使用频率较低。
5. 面试官追问：「定时还款任务的 cron 为什么放在 Apollo 里而不是写死在代码里？」
   答：触发频率是典型的易变配置，测试阶段用每 5 秒一次方便观察，上线后要改成按业务节奏执行，例如每天早上五点。放在 Apollo 的 `micro_service.elasticjob` 命名空间里，服务通过 `@Value` 注入，调整频率不需要改代码重新发布。
