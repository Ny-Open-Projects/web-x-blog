# 附近售货机搜索测试收官：微信开发者工具联调与虚拟定位

上一讲用测试脚本验证了附近售货机搜索的服务端逻辑，GeoDistance 查询和按距离排序都工作正常。本讲补上这条链路的最后一环：前后端联调。小程序端跑起来之后，首页却查不出任何售货机——原因不在代码，而在模拟器本身没有定位能力。给微信开发者工具虚拟一组经纬度，问题就解决了，LBS 章也在这里收尾。

## 先给结论

- 前后端联调用微信开发者工具来做：进入小程序首页，验证附近售货机列表和地图导航。
- 模拟器是虚拟环境，不是真实手机，本身没有定位能力，首页查不出数据是预期现象，不是 Bug。
- 解决办法：调试器的 Sensor 面板勾选 Enable 启用模拟传感器，手工填入经纬度虚拟值。
- 经纬度直接沿用脚本测试用的那组数据：纬度 39.987282、经度 116.355546，选接近的值也可以。
- 填完点刷新，首页立刻能查到附近的售货机；点「去这里」打开本地地图导航。
- 换到真实手机联调则不需要虚拟定位：手机装了什么地图 App，就会唤起什么地图。

## 一、从脚本测试到前后端联调

服务端这一侧，数据写入 ES 时 location 字段按 geo_point 类型存储，其余字段 keyword 就够；查询时用 GeoDistanceQueryBuilder 圈定圆心和半径，再按距离升序排序——这些在脚本测试里已经逐个验证过。Kibana 控制台里能看到索引结构和数据落库的样子：

```json
PUT /vm
{
  "mappings": {
    "properties": {
      "location": { "type": "geo_point" },
      "nodeId":   { "type": "keyword" },
      "nodeName": { "type": "keyword" },
      "type":     { "type": "keyword" }
    }
  }
}
```

文档里「凯德MALL」这条数据的 location 值是 `39.987282,116.355546`，正好就是联调时要复用的那组坐标。脚本只证明了服务端搜索逻辑正确，用户实际从小程序发起请求、拿到列表、再跳转地图这条完整链路还没有验证过，所以最后一步是前后端联调。联调要确认的点也很具体：小程序发出的请求能不能把经纬度参数带给后端、返回的售货机列表能不能正常渲染、距离字段展示得对不对、点击设备能不能唤起地图。

## 二、模拟器查不出数据：虚拟环境没有定位

打开微信开发者工具，进入工具界面之后就能看到小程序首页。这时会发现，首页的「附近售货机」一栏并没有把数据查出来。

原因要先说清楚：开发者工具里跑的是一个虚拟环境，并不是真实手机。真实手机有定位模块，能拿到当前经纬度；模拟器本身没有定位，小程序端拿不到位置参数，后端的 geo 搜索自然查不出结果。这不是代码问题，所以不用去改服务端，也难怪脚本测试是通的。

## 三、Sensor 面板虚拟经纬度，联调收官

模拟器没有定位，那就虚拟一个。微信开发者工具的调试器里有 Sensor 面板，可以对传感器数据设置虚拟值，经纬度就在这里填：

| 步骤 | 操作 |
| --- | --- |
| 1 | 打开调试器的 Sensor 面板 |
| 2 | 勾选 Enable，启用模拟传感器 |
| 3 | Latitude 填纬度 39.987282 |
| 4 | Longitude 填经度 116.355546 |

面板里还有 Accuracy（定位精度）等其他传感器字段，演示里一并填了默认值。坐标直接选刚才脚本测试用的那组数据即可，填一个接近的值也一样能触发 geo 搜索——ES 里那台「凯德MALL」的坐标本来就是这个点，以它为圆心做距离搜索必然命中。填完之后点刷新，重新加载小程序——刷新完首页就能查到附近售货机的数据了，设备名称、距离都能正常展示出来。

再点某台设备上的「去这里」，会打开本地地图来进行导航。模拟器里打开的是工具自带的地图；换成真实手机联调时，这一步反而不需要虚拟定位，手机装的是什么地图，就会唤起什么地图，跟着导航走到设备跟前就行。

到这里，附近售货机搜索功能的前后端联调就完成了。

## 小结

LBS 章到本讲收束。整条链路回顾下来：需求上是新零售的线上向线下导流；技术上售货机位置不变，选 ES 的 geo_point 存坐标；实现上走「建索引、写入坐标、GeoDistance 查询加距离排序」；验证上先脚本测服务端，再进微信开发者工具联调前端，模拟器没有定位就用 Sensor 面板虚拟经纬度。这也是一个常见的坑：小程序在开发者工具里查不出附近数据，先查定位来源，而不是急着改代码。
