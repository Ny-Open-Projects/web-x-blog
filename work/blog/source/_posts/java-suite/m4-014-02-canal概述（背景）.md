# canal 从原理到安装使用 + Otter 双向同步架构（数据聚合服务前置）

数据聚合服务（pd-aggregation）开篇不写业务代码，先解决一个前置问题：MySQL 的数据变更怎么实时"流"给下游。这一单元十个视频围绕两个组件展开：canal 负责伪装 slave 拉取并解析 binlog，从概述、架构、HA 讲到 Docker 安装与 Java 客户端实测；Otter 站在 canal 之上，把数据同步从"写代码"变成"页面配置"。

## 先给结论

- canal 译意为水道/管道，核心用途是基于 MySQL 增量日志解析提供增量数据订阅和消费；它诞生于阿里杭州-美国双机房的跨机房同步需求，早期靠业务触发器，2010 年起改为解析 binlog。支持 MySQL 5.1.x 到 8.0.x。
- 工作原理一句话：canal 模拟 MySQL slave 的交互协议伪装成从库，向 master 发送 dump 协议，master 把 binary log 推给它；解析出的数据落到哪（另一个 MySQL、Kafka、ES、HBase）由使用者编程决定。
- 架构两层：server 是一个 Java 服务进程，管理多个 instance；instance 才是伪装 slave 干活的单元，内部含 EventParser（数据源接入、协议解析）、EventSink（过滤、加工、分发）、EventStore（存储）、MetaManager（订阅消费信息管理）。
- HA 靠 ZooKeeper：为了减少对 MySQL 的 dump 请求，同一时刻只允许一个 instance 处于 running，其余 standby；谁在 ZooKeeper 创建短暂节点成功谁启动，running 节点消失后其余节点重新抢节点，client 连接前先向 ZooKeeper 询问当前 running 节点。
- 安装两步走：MySQL 容器加 log-bin=mysql-bin、binlog-format=ROW、server_id=1 三项配置并创建 canal 账号（REPLICATION SLAVE/CLIENT 权限）；canal-server 容器改 instance.properties 的 slaveId（唯一即可，演示用 12）和 master.address，重启后 tail 日志确认 destination 生效。
- Java 客户端实测：while(true) 里 getWithoutAck 拿 Message，ROWDATA 类型的 entry 用 RowChange.parseFrom 解析出事件类型和前后数据，最后 ack 确认。一次 insert 对应 TRANSACTIONBEGIN、ROWDATA、TRANSACTIONEND 三条消息；增删改全监听得到，select 监听不到——binlog 不记录查询。

## canal 是什么：跨机房同步催生的 binlog 订阅中间件

canal 的定义只有一句：译意为水道/管道，主要用途是基于 MySQL 数据库增量日志解析，提供增量数据订阅和消费。官方架构图里，MySQL Master 通过 dump 把变更交给 canal，canal 再分发给 Kafka、Elasticsearch、HBase、RocketMQ、Pulsar 等下游。

背景是阿里的双机房部署：杭州和美国两个机房各有一套数据库，杭州数据变更后要同步到美国机房，两边保持一致。早期方案基于业务触发器——本地数据一变，触发器向另一个数据库插入数据；2010 年开始改为解析数据库增量日志：日志天然记录了每一次插入、删除、修改，解析它就能拿到全部变更再同步给对端。这个思路衍生出一批基于日志增量订阅和消费的业务：数据库镜像、数据库实时备份、索引构建和维护、业务缓存刷新，以及带业务逻辑的增量数据处理。

理解 canal 原理前先看 MySQL 主从复制，canal 就是照着它设计的。主从复制三步：master 将数据变更写入二进制日志 binary log，记录叫 binary log events；slave 的 IO Thread 把 master 的日志事件拷贝到自己的中继日志 relay log；slave 的 SQL Thread 重放 relay log 中的事件——master 执行过的 SQL 在从库原样再执行一遍，数据就同步了。

canal 的做法是"不建从库，只借协议"：slave 与 master 的交互协议是定死的，canal 把自己模拟成 slave，向 master 发送 dump 协议；master 收到请求，认为对面就是个从库，开始推送 binary log 给它（原理图上那句 "I am a slave"）；canal 拿到后解析 binary log 对象（原始是 byte 流），还原出执行过的 SQL 和变更前后数据。解析完的数据插回另一个 MySQL、发给 Kafka/ES/HBase，都由使用者编程实现——canal 只负责把日志拿过来、解析出来。

## 架构与 HA：server、instance 与 ZooKeeper 协调

canal 基于 Java 开发，跑起来就是一个服务进程，这个进程叫 server。server 管理多个 instance，每个 instance 对应一个 canal 实例，真正伪装成 slave 从 MySQL dump 数据的是 instance。instance 内部四个模块各司其职：

| 模块 | 职责 |
| :--- | :--- |
| EventParser | 数据源接入：模拟 slave 协议与 master 交互，拉取并解析 binlog |
| EventSink | Parser 和 Store 的连接器：对数据进行过滤、加工、分发 |
| EventStore | 数据存储 |
| MetaManager | 增量订阅与消费信息管理，对外提供订阅、消费支持 |

这套内部结构了解即可，课程定位是面向应用：会安装、会使用、能解析。

canal 本质是个 Java 服务，生产环境必须考虑高可用。它的高可用基于 ZooKeeper 做服务协调，核心约束是：为了减少对 MySQL dump 的请求，同一时间只能有一个 instance 处于 running 状态，其余处于 standby。大致步骤四条：

1. canal server 要启动某个 instance 时，先向 ZooKeeper 做一次尝试启动判断——实现是创建短暂节点，谁创建成功就允许谁启动；
2. 创建节点成功的 server 启动对应 instance，没创建成功的处于备用状态；
3. 一旦 ZooKeeper 发现某个 running 节点（比如 server A）创建的节点消失，立即通知其他 server 再次执行步骤 1，重新选出一个启动 instance；
4. canal client 每次连接时先向 ZooKeeper 询问当前是谁启动了 instance，拿到地址再与之建立链接，链接不可用就重新尝试 connect。

也就是说 A、B 两个 server 启动时抢建节点，抢到的 running，另一个 standby；A 挂了，ZooKeeper 感知到节点消失，B 重新抢节点接管。客户端永远先问 ZooKeeper 再连 canal，服务切换对下游透明。

## 安装与实测：Docker 起服务，Java 客户端订阅解析

### MySQL 端：开 binlog，建账号

canal 要从 master 拉 binlog，MySQL 必须开启 binlog 写入。演示环境用 Docker 起 MySQL 5.7，先在宿主机建好映射目录：

```bash
mkdir /mnt/canal_mysql
docker run -d --name canal_mysql \
  -v /mnt/canal_mysql:/var/lib/mysql \
  -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=123456 \
  mysql:5.7
```

本地没有镜像会自动拉取。接着要改容器内配置，但 MySQL 容器默认没有 vim；直接 apt-get 装走的是国外源，很慢。先在宿主机写一个清华大学 debian 源的 sources.list，docker cp 复制进容器的 /etc/apt/，再进容器执行 `apt-get update && apt-get install vim -y`，下载速度就正常了。

进容器改 /etc/mysql/mysql.conf.d/mysqld.cnf，追加三项固定配置：

```properties
log-bin=mysql-bin
binlog-format=ROW
server_id=1
```

退出容器执行 `docker restart canal_mysql`，再用客户端远程连上验证：

```sql
show variables like 'log_bin';       -- value 为 ON，binlog 已开启
show variables like 'binlog_format'; -- value 为 ROW，说明改成功了
show master status;                  -- 能正常展示即可
```

最后创建 canal 账号，canal server 与 MySQL 通信时的认证就用它，账号名不是固定的，叫 canal 只是一看便知用途：

```sql
CREATE USER canal IDENTIFIED BY 'canal';
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'canal'@'%';
FLUSH PRIVILEGES;
```

### canal-server 端：改 instance.properties

canal-server 同样用 Docker 跑，启动后默认端口 11111：

```bash
docker run -d --name canal-server -p 11111:11111 canal/canal-server:v1.1.4
docker exec -it canal-server /bin/bash
vi canal-server/conf/example/instance.properties
```

要改的地方很少：canal.instance.mysql.slaveId 去掉注释改成 12，只要唯一即可；canal.instance.master.address 改成 MySQL 所在服务器的公网 IP 加 3306，演示环境是 68.79.63.42；dbUsername/dbPassword 默认就是 canal/canal，与刚创建的账号一致，不用动。保存后 `docker restart canal-server`，重新进容器看日志：

```bash
tail -100f canal-server/logs/example/example.log
```

日志里能看到 destination 信息，说明配置已生效。

### Java 客户端：四步解析 binlog

MySQL 里建库 canal_test（字符集 utf8mb4）和 student 表（id、name、age、sex、city 五个字段，id 主键）。Maven 工程 canal-demo 引入客户端依赖——groupId 是 com.alibaba.otter，Otter 与 canal 同门由此可见：

```xml
<dependency>
    <groupId>com.alibaba.otter</groupId>
    <artifactId>canal.client</artifactId>
    <version>1.1.4</version>
</dependency>
```

客户端代码不要求手写，能读懂即可，骨架四步：

```java
String ip = "68.79.63.42";      // 指定 canal server 的 ip
String destination = "example"; // 对应配置文件所在的 example 目录，不用改
// 1. 创建连接对象，连接并订阅
CanalConnector canalConnector = CanalConnectors.newSingleConnector(
        new InetSocketAddress(ip, 11111), destination, "", "");
canalConnector.connect();
canalConnector.subscribe();
int batchSize = 5 * 1024;
while (true) { // 2. 死循环不断获取 canal 的消息
    Message message = canalConnector.getWithoutAck(batchSize);
    long id = message.getId();
    int size = message.getEntries().size();
    if (id == -1 || size == 0) {
        TimeUnit.SECONDS.sleep(1); // 没有数据，等待 1 秒
    } else { // 3. 有数据，逐条解析
        for (Entry entry : message.getEntries()) {
            if (entry.getEntryType() == CanalEntry.EntryType.ROWDATA) {
                RowChange rowChange = RowChange.parseFrom(entry.getStoreValue());
                // 事件类型：INSERT / UPDATE / DELETE
                System.out.println("事件类型是：" + rowChange.getEventType());
                for (RowChange.RowData rowData : rowChange.getRowDatasList()) {
                    // rowData.getBeforeColumnsList() 是改变前的数据
                    System.out.println("改变后的数据：" + rowData.getAfterColumnsList());
                }
            }
        }
        canalConnector.ack(id); // 4. 消息确认
    }
}
```

结构类似最早讲的 JDBC：连的不再是 MySQL 而是 canal server，订阅它的消息。无数据时 id 为 -1 或 size 为 0，睡 1 秒继续；有数据时遍历 message 里的 entries，只有 EntryType 为 ROWDATA 的才是原始数据操作（增删改），RowChange.parseFrom 解析 storeValue 后能拿到事件类型和 RowData 集合——每个 RowData 都能取 getBeforeColumnsList（改变前）和 getAfterColumnsList（改变后），字段级明细一清二楚。最后 ack(id) 告知 server 这条消息已成功接收，和消息队列消费完手动应答是一个意思。

实测效果：程序启动初期先打出几条 QUERY 类型的条目（查询类事件），随后没有操作时一直输出"binlog 消息数量 0"。执行 `insert into student values('1','test',20,'女','北京')`，控制台立刻监听到 3 条消息：TRANSACTIONBEGIN（事务开始）、ROWDATA/INSERT（数据本体，按字段描述——index 0 是 id=1 且 isKey=true，index 1 name=test，index 2 age=20，index 3 sex=女，中文被转义，index 4 city=北京）、TRANSACTIONEND（事务提交）。update 把 name 由 test 改成小名，事件类型 UPDATE，改变前 name=test、改变后 name=小名，前后数据都有；delete 按 id 删掉这条，事件类型 DELETE，改变前是原数据，改变后为空。再执行 select，消息数量还是 0——binlog 只记增删改，不记查询。

## Otter：把 canal 包成"页面配置"的同步系统

canal 用起来要自己写客户端解析，Otter 解决的就是这件事。Otter 底层基于 canal 实现，依赖 canal 接收和解析 MySQL 的 binlog，但对外提供可配置化的同步机制——启动后在它提供的配置界面上直接配置哪个库同步到哪个库、哪个字段对应哪个字段，不用再编程。纯 Java 开发、免费开源，定位是分布式数据同步系统，准实时同步到本地或异地机房的 MySQL/Oracle 数据库。

典型场景五类：异构库同步（mysql 到 mysql/oracle，开源版源端只支持 MySQL 增量，目标库取决于 canal 的功能）；单机房同步（RTT < 1ms）；异地机房同步（如阿里国际站杭州-美国机房，RTT > 200ms）；双向同步（A、B 互为源和目标，需要避免回环算法——否则 A 变更同步到 B、B 再变更又同步回 A，形成死循环——和数据一致性算法）；文件同步（站点镜像，复制产品数据的同时复制产品图片）。

一个典型用法：账户交易明细表数据每天递增，时间一长查询、插入都变慢。用 Otter 把明细同步到历史表并做分表处理，往年交易记录查历史表；源明细表只保留最近一段时间的记录（删一个月甚至几天前的数据）。两边数据一致、单表数据量变小，速度自然就上来了。

架构上，Otter 是 manager + node 的管理系统架构：

| 组件 | 职责 |
| :--- | :--- |
| db | 数据源以及需要同步到的库 |
| canal | 获取数据库增量日志；支持独立部署或内嵌，Otter 用内嵌方式，装完自带 canal，不必单独安装 |
| manager | 提供 Web 管理站点，配置同步规则、数据源等；运行时推送同步配置到 node，node 状态也反馈到 manager |
| zookeeper | 分布式状态调度，协调多个 node 协同工作 |
| node | 工作节点，根据任务配置对数据源进行解析，并同步到目标库 |

使用流程：管理员在浏览器操作 manager 自定义同步任务，manager 把配置推送到 node，node 开启数据同步（底层内嵌 canal 拉取日志），源库一有变化就由 node 同步到目标库，node 再把同步状态反馈给 manager——管理界面上能看到每个 node 的状态。数据 On-Fly（尽可能不落地）保证同步速度，node 支持 failover/loadBalancer。

单机房与跨机房的差别在 node 的部署形态。单机房里一套 manager 推配置给 node，node 同步并回报状态；跨机房时 A、B 两个机房物理隔离，各部署 node，manager 把配置同时推给两个 node，由 ZooKeeper 任务调度决定哪个 node 干活，A 到 B 与 B 到 A 两条数据流同时存在——这正是双向同步的形态。node 内部的数据处理走 S/E/T/L 四阶段：Select 接入、Extract 提取、Transform 转换、Load 加载，属于内部实现，了解即可。对使用者而言，装上服务、在页面配置好，同步就跑起来了。

## 小结

十个视频把数据同步的地基打完。canal 的原理并不神秘：MySQL 主从复制里 slave 用 dump 协议拉 binlog 重放，canal 把自己伪装成 slave 拿到同一份日志，只是不重放，而是解析后交给使用者分发；架构上 server 包 instance，instance 里 Parser、Sink、Store 三段流水线，HA 靠 ZooKeeper 抢节点保证同一时刻只有一个 running。落地用 Docker 两步：MySQL 开 binlog 建 canal 账号，canal-server 改 slaveId 与 master.address；Java 客户端 connect、subscribe、getWithoutAck、parseFrom、ack 一条链，实测增删改全监听、查询不记。Otter 则把 canal 的编程接口升级成配置界面：manager 管配置与调度，node 内嵌 canal 干活，ZooKeeper 协调分布式状态，双向同步靠防回环算法兜底。这套前置知识，就是品达 TMS 数据聚合服务后续所有同步任务的地基。
