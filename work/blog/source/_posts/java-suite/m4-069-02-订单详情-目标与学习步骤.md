# 账户管理开篇：订单详情 gRPC 全链路与持仓服务、仓位总览实现

账户管理一章从两个查询接口起步。前面已经完成了下单、挂单和撤单，用户发出限价委托后最关心的是这张单到底成交没有：部分成交还是完全成交、成交了多少、什么时间成交的，这些都要靠订单详情接口来查，撤单接口需要的订单 ID 入参同样来自这里。本篇打通订单详情从协议定义、交易服务 gRPC 实现、代理转发到客户端验证的完整链路，随后开启第二章仓位总览：搭建持仓服务、定义仓位数据结构，并实现浮动盈亏的核心计算。

## 先给结论

- 订单详情接口实现简单但不可缺：挂单状态跟踪、成交量与成交时间的展示都依赖它，撤单等后续业务也要先拿到订单 ID 才能发起。
- 协议分两层定义：Netty 对外层 GetOrderData 只带订单 ID，返回包 GetOrderResp 承载订单全量字段；内部 gRPC 层 GetOrderRequest 多带一个交易账户 ID，Head 头部请求类型新增 GET_ORDER。
- Protobuf 不支持 Date 类型：可以引入 google/protobuf/timestamp.proto 插件让字段用 Timestamp，也可以直接转时间戳传输。课程选后者，copyProperties 时排除 execTime，再单独 set 时间戳。
- 生产环境要防伪造参数跨账号查询数据：要么对参数报文做非对称加密加 Base64 编码，要么做账号 ID 权限判断，账户 ID 由服务端通过通道关联缓存维护，不能信任客户端传参。
- 代理服务做了小重构：下单处理抽取成 processPlaceOrder 方法，switch 按请求类型分发，工厂里补 GET_ORDER 路由，处理器从此能承载多个交易接口。
- 仓位总览的难点在浮动盈亏计算：全程用长整型，盈亏保留两位小数、比例保留四位小数，避开 double 的精度丢失与科学计数法问题；最新行情报价从 Redis 缓存读取。

## 订单详情：两层协议定义与代码生成

对外层在 StockMessage.proto 里增加请求与响应消息体。请求很简单，一个订单 ID 就够，重点在返回包的字段设计：

```protobuf
message GetOrderData {
  int64 orderId = 2;       // 订单ID
}

message GetOrderResp {
  int64 id = 1;            // 订单ID
  int64 accountId = 2;     // 交易账户ID
  int64 stockId = 3;       // 股票产品ID
  int32 status = 4;        // 订单状态: 0待成交 1部分成交 2完全成交 3手工撤单 4系统撤单
  int32 type = 5;          // 挂单类型: 0市价单 1限价单
  int32 direction = 6;     // 买卖方向: 0买入 1卖出
  int32 initVolume = 7;    // 请求数量
  int32 execVolume = 8;    // 实际成交数量
  double execPrice = 9;    // 成交价格
  int64 requestPrice = 10; // 请求价格
  int64 execTime = 11;     // 成交时间(时间戳)
  string stockCode = 12;   // 股票代码
  string stockName = 13;   // 股票名称
}
```

status 和 type 这两个枚举字段的含义必须写清注释，订单状态跟踪全靠它们。接着在 StockData 消息体里增加 get_order_data 字段（序号 6），返回消息里增加获取订单详情的返回数据包 get_order_response，StockHead 头部的请求类型枚举新增 GET_ORDER（序号 5）。

对内 gRPC 层在 StockTradeDealService.proto 里声明服务方法：

```protobuf
rpc getOrder (GetOrderRequest) returns (GetOrderResponse) {}

message GetOrderRequest {
  int64 accountId = 1;   // 交易账户ID
  int64 orderId = 2;     // 订单ID
}
```

内部请求比对外层多带一个交易账户 ID，给权限校验留出依据。定义完成后在 proto 目录打开终端，执行 protoc 批处理脚本，先生成 gRPC 层代码，再生成 Netty 层传输结构代码，分别刷新工程确认 GetOrderResponse、GetOrderData 等类都生成到位，之后就可以进入逻辑实现。

## 交易服务 gRPC 接口实现

交易服务里重写 GrpcStockDealService 的 getOrder 方法，处理路径是查库、判空、拷贝属性、返回：

```java
@Override
public void getOrder(GetOrderRequest request, StreamObserver<GetOrderResponse> responseObserver) {
    log.info("Process in GrpcStockDealService.getOrder, request: " + request);
    GetOrderResponse.Builder response = GetOrderResponse.newBuilder();
    try {
        // 根据订单ID获取订单详情信息
        TradeOrder order = stockDealService.getOrder(request.getOrderId());
        if (null != order) {
            // execTime 是 Date 类型，Protobuf 不支持，排除后单独转时间戳
            BeanUtils.copyProperties(order, response, new String[]{"execTime"});
            response.setExecTime(order.getExecTime().getTime());
        }
    } catch (Exception e) {
        // 系统异常信息返回
        log.error(e.getMessage(), e);
    }
    responseObserver.onNext(response.build());
    responseObserver.onCompleted();
}
```

service 层的实现就是按订单 ID 查数据库返回 TradeOrder 对象，一层转下来逻辑不长。真正值得展开的是两个注意点。

第一是日期类型的处理。实体里 execTime 是 java.util.Date 类型，而 Protobuf 只支持基本类型，int、long、string 都没问题，Date 不行。想让 Protobuf 支持日期，可以引入它的插件，在 proto 脚本里 `import "google/protobuf/timestamp.proto";` 让字段使用 Timestamp 类型。课程为了简化直接做转换：日期转成时间戳 long 传输，省掉额外插件的引入，这就是上面代码排除 execTime 再单独 set 的原因。

第二是生产环境的安全。课程侧重业务逻辑讲解，没有加严格的安全校验控制，生产上必须防止伪造参数跨账号查询他人数据，这里给了两个方案：

| 方案 | 做法 |
|---|---|
| 参数报文加密 | 报文内容先做非对称加密，再经 Base64 编码转成字符串放进 PB 里传输，第三方截获报文但没有密钥，无法得知传输内容 |
| 账号 ID 权限判断 | 账户 ID 不由客户端随便传递，由服务端通过与客户端的交互记录关联关系；撤单处理时就是这样，交易账号 ID 从缓存里 channel 通道与交易账号 ID 的关联缓存中获取 |

## 代理服务转发与客户端验证

代理服务的交易服务处理器 StockDealProcessor 之前只处理下单，这次先做个小重构：选中下单处理代码，Refactor 菜单里 Extract Method，抽成独立的 processPlaceOrder 方法，让处理器具备承接多种交易接口的结构，方便后续扩展。然后新增 processGetOrder 方法，流程四步：获取请求参数，构造 GetOrderRequest（交易账户 ID 加订单 ID），调用 gRPC 远程接口，成功后组装响应报文（先组装头部信息，再从 gRPC 返回的详情对象拷贝出要给客户端的订单详情），最后经 responseMessage 输出给客户端。

gRPC 接口入口按头部消息的请求类型做路由适配：

```java
@Override
public void processRequest(ChannelHandlerContext channelHandlerContext, StockMessage stockMessage) {
    switch (stockMessage.getStockHead().getRequestType()) {
        case PLACE_ORDER:
            processPlaceOrder(channelHandlerContext, stockMessage);
            break;
        case GET_ORDER:
            processGetOrder(channelHandlerContext, stockMessage);
            break;
        default:
            log.error("Process in StockDealProcessor.processRequest method => Not Match RequestType!");
    }
}
```

default 分支打一条没有找到匹配请求类型的错误日志。接口数量不多时直接在方法内判断就够了，将来接口继续增多，建议再用工厂方法模式做一层封装。路由改完别忘了工厂：StockProcessorFactory 里为 GET_ORDER 补一个 case，让下单和获取订单详情两类请求都能路由到交易服务处理器，处理器内部再按请求类型调各自的处理逻辑。

客户端验证要改三处。BusinessHandler 里增加订单详情调用方法，接收订单 ID 参数组装请求发送；ClientBoundHandler 处理服务端响应的方法里增加 GET_ORDER 分支，打印日志前先做非空判断，GetOrderResponse 存在且里面的 id 不为空才输出订单详情，因为传入的订单 ID 可能是错的，服务端会返回空数据；交互菜单增加指令 5（get order，查询订单详情），输出 enter order ID 提示接收订单 ID 输入，撤单的菜单入口也可以照同样方式补上。

测试时依次启动交易服务、代理服务和模拟客户端，登录后发送指令 5，输入数据库里最新的订单 ID 2534。控制台返回订单详情：请求数量 26000，实际成交数量 19168。回到数据库对照，2534 的状态是 3（手工撤单），实际成交数量同样是 19168，数据一致，整体验证通过。

## 仓位总览：持仓服务搭建与浮动盈亏计算

第二章仓位总览的目标，是让用户下单后能查看自己所有仓位的信息汇总：持仓价格、持仓数量、最新价格、盈亏情况，结合行情变化观察仓位动态。核心逻辑是浮动盈亏的计算，这也是整个实现的难点。

第一步搭建持仓服务，这是交易核心服务里的一个新模块。新建 Maven 模块 bulls-stock-position，基础包 com.itcast.bulls.stock.position，下面建 config、dao、service、grpc 几个子包。POM 依赖包括 Spring Boot、Nacos 服务注册发现、公用的数据层/服务层/工具类工程、实体依赖、RocketMQ 消息总线、Redis 缓存和 gRPC 相关组件，多环境版本先只配置开发环境做简化。

配置文件从已有工程拷贝 bootstrap-dev.yml，端口改为 10698（挂单服务是 10697），整体要点包括 Nacos 配置、RocketMQ 消费端绑定（新服务起一个新名称）、双数据源（交易数据源加业务数据源）、JPA 与 Hibernate 映射、MyBatis 配置（数据层用 MyBatis 实现）、gRPC 服务端端口（保证唯一不被其他服务占用）和线程池配置，Spring Session 这类用不上的配置直接删除：

```yaml
server:
  port: 10698
spring:
  application:
    name: stock-position
  cloud:
    nacos:
      server-addr: 127.0.0.1:8848
```

双数据源的三个配置实现类从原有工程拷到 config 包下，做两处修正：JPA 和 Hibernate 相关内容删掉，这里的双数据源基于 MyBatis 实现；检查 Mapper 数据层接口的扫描路径，交易数据源指向 position 的 dao 包，业务数据源指向 biz 包。业务数据源的数据层接口还没引入，先把 dao 下的两个包拷进来，同时核对实体路径与 map 文件的扫描路径是否对得上。资金服务也要用缓存，RedisConfiguration 一并引入：开启缓存注解，定义 RedisTemplate 模板操作接口，CacheManager 的默认过期时间配置为 24 小时。最后创建启动类 StockPositionApplication，标注 @SpringBootApplication 和 @EnableDiscoveryClient，包扫描指向 com.itcast 基准目录，持仓服务搭建完成。

接着定义仓位总览的两层数据结构。对外层有个设计取舍：获取用户所有仓位不需要定义请求消息对象，账户 ID 由代理服务从缓存中取得后传入，客户端不用传这个参数；返回侧在 ResponseMessage 里增加 getAllPositionsList 字段，用集合承载，因为一个账户会有多条持仓记录。GetAllPositionData 的字段覆盖仓位与盈亏两类信息：

| 字段 | 含义 |
|---|---|
| id / tradeOrderId / accountId | 主键、交易订单号、交易账号 ID |
| stockId / stockCode / stockName | 股票产品标识 |
| costPrice / avgPrice / volume / validSellVolume | 成本价、成交均价、持仓数量、可卖数量（T-1 制度使用，T-0 不限制） |
| stockMarket | 股票市场：0 上交所、1 深交所、2 港股、3 美股 |
| profit / profitRate / interest | 盈亏、盈亏比例、持仓累计利息 |
| lastPrice / execTime / status | 最新报价、成交时间、状态（0 有效 1 无效） |

对内层在 gRPC 目录下新建 stock_position_service.proto，声明获取用户所有仓位信息的接口：

```protobuf
service StockPositionService {
  // 获取所有持仓信息接口
  rpc getAllPositions (GetAllPositionRequest) returns (GetAllPositionResponse) {}
}

message GetAllPositionRequest {
  int64 accountId = 1;   // 账户ID, 由代理服务从缓存获取
}

message GetAllPositionResponse {
  string status = 1;     // 处理状态
  string message = 2;    // 响应消息
  repeated GetAllPositionData getAllPositionData = 3;  // 仓位数据集合
}
```

执行批处理脚本生成两侧代码，检查 GetAllPositionResponse 和 GetAllPositionData 都生成成功后，进入持仓服务的接口实现。grpc 包下新建 GrpcStockPositionService，继承 StockPositionServiceGrpc.StockPositionServiceImplBase，加 @GrpcService 注解；外层逻辑是调 service 按账户 ID 拿到持仓集合，遍历转换成 PB 对象结构塞进响应消息体，最后通过 responseObserver 输出给调用方。

业务逻辑放在 IStockPositionService 接口与 StockPositionServiceImpl 实现类里。先查出持仓列表，逐条计算浮动盈亏：

```java
public List<TradePosition> getAllPositions(Long accountId) {
    List<TradePosition> positionList = tradePositionDao.getAllByAccountId(accountId);
    if (null != positionList) {
        positionList.forEach(pos -> calcProfit(pos));
    }
    return positionList;
}
```

浮动盈亏依赖最新行情报价，报价放在 Redis 缓存里，按行情 key 的缓存空间加股票 ID 取出，缓存对象非空才做计算。两个核心公式如下：

| 指标 | 公式 | 说明 |
|---|---|---|
| 浮动盈亏 | (最新价 - 成本价) × 持仓数量 | 可能为负，最新价低于成本价即亏损 |
| 盈亏比例 | 浮动盈亏 ÷ (成本价 × 持仓数量) | 分母拿成本价不是最新价，结果保留四位小数 |

计算全程采用长整型：盈亏保留两位小数，比例保留四位小数，比如 169988 实际代表的就是 169.9988%。

```java
private void calcProfit(TradePosition pos) {
    // 1. 获取最新的行情报价
    TradeStockQuoteLast quoteLast = getTradeStockQuoteLast(pos.getStockId());
    if (null != quoteLast) {
        // 2. 浮动盈亏: (最新价-成本价)×持仓数量, 长整型保留两位小数
        long diffPrice = MathUtils.sub(quoteLast.getLastPrice(), pos.getCostPrice());
        long profit = MathUtils.mul(diffPrice, pos.getQuantity());
        pos.setProfit(profit);
        pos.setLastPrice(quoteLast.getLastPrice());
        // 3. 盈亏比例: 浮动盈亏/(成本价×持仓数量), 保留四位小数
        long profitRate = MathUtils.div(profit,
                MathUtils.mul(pos.getCostPrice(), pos.getQuantity()), 4);
        pos.setProfitRate(profitRate);
    }
}
```

为什么坚持长整型？double 也能实现计算，但存在精度丢失的可能，还会出现科学计数法。科学计数法只是显示问题，结果本身没有错，可以用 `DecimalFormat("0.##")` 这类格式化方式处理，但在实际工作中，经常要做运算或存在复杂运算的业务，还是尽量采用长整型处理，保持整体计算的准确性。写完后通过 Refactor 把计算方法抽到接口层，gRPC 接口层整个代码就通了。

## 小结

这一篇跨了订单详情和仓位总览两段。订单详情的实现链条短，查库、拷贝、返回三步走完，但它是挂单跟踪、成交统计、撤单这些业务的数据基础，接口虽简单，完善它要考虑的东西不少：防伪造参数跨权限调用、支持批量查询、性能上加缓存，都是生产化的方向。代理服务的交易处理器经这次重构具备了多接口承载能力，switch 分发加工厂路由的组合后续会反复用到。仓位总览这边，持仓服务的搭建是标准动作：新模块、双数据源、MyBatis、Redis、gRPC 一套集成下来；真正的业务核心落在浮动盈亏计算上，长整型加固定小数位的方案既避开了 double 的精度坑，也让客户端展示不会冒出科学计数法。下一篇完成仓位总览的代理转发与功能验证，再做账户资金总览的计算公式、gRPC 接口和业务层实现。
