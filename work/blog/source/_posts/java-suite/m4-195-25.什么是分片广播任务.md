# XXL-JOB分片广播任务：概念、代码实现与三实例并行测试

立可得的自动补货工单要扫描所有运营状态的售货机，再逐台判断是否缺货。售货机一多，单节点串行扫描的总耗时就是每台机器执行时间的加和，长到难以接受。第四章第四小节给出的解法是XXL-JOB的分片广播路由策略：把一份扫描任务拆给执行器集群并行干。这篇把概念、两种数据切分方法、代码实现与三实例并行测试一次讲完。

## 先给结论

- 分片广播是XXL-JOB里比较特殊的一种路由策略：其他策略在多节点部署后只有一个节点执行任务、其余歇着；选分片广播则所有执行器节点都会收到任务，原本一个节点干的活由集群共同完成。
- 分片参数是两个数：分片总数（部署了几个执行器就是几）和当前分片索引（从0开始，三个分片就是0、1、2）。每个执行器都能同时拿到这两个数，据此只处理属于自己的那部分数据，彼此不重复。
- 数据切分有两种常用方法：分页法先统计总数、除以分片数得到每页大小、把索引当页码，代价是多一次count查询；取模法直接在查询条件里写 mod(id, 分片总数) = 当前分片索引，ID连续时分片非常均匀，课程采用后者。
- 代码改动很小：调度中心把"扫描售货机"任务的路由策略从"第一个"改成分片广播；任务方法里用ShardingUtil.getShardingVo()拿分片参数；原查询条件上加一个 mod 取模条件，其余逻辑不变。
- 同一微服务起三份的准备：server.port错开为9004/9104/9204，Consul配置中心里与XXL-JOB的通信端口错开为9980/9988/9989，IDEA勾选"允许同时运行"。
- 测试结果：执行一次生成三条同时刻的调度日志，总分片数都是3、索引分别为0/1/2，三个分片扫到的售货机互不重叠，一份扫描被均摊成三份。

## 为什么要分片广播：把串行扫描改成并行

上一小节已经完成自动补货工单逻辑的编写：扫描所有运营状态的售货机，每台再判断是否存在缺货。实际运营中系统里会有大量售货机，由一个节点把所有售货机轮询一遍，整体耗时就是每台售货机运算时间的总和——一个接一个排队执行，这就是串行。

想缩短时间就要改成并行。最直观的类比是车站买票：只有一个售票窗口就得排长队，同时开几个窗口，整体工作效率立刻提升。

落到工程上，就是多部署几份扫描售货机的程序——也就是售货机微服务，在XXL-JOB的语境里叫执行器。每个节点只扫描一部分数据，各节点加起来正好是全部数据，原本一个微服务的活分给多个微服务同时干，整体时间自然缩短。这就是集群分片广播任务，XXL-JOB里一个比较特殊的路由策略。

看图更直观。假设业务数据总共3万条，分成三个片，部署三个执行器组成集群：

- 执行器1处理第1~10000条，分片参数0/3；
- 执行器2处理第10001~20000条，分片参数1/3；
- 执行器3处理第20001~30000条，分片参数2/3。

每个执行器处理的数据保证不重复，三个加起来正好覆盖全部。分片参数里前者是当前分片索引（从0开始），后者是分片总数。

## 实现思路：分页与ID取模两种切法

实现分两步。第一步改调度中心：把扫描售货机任务的路由策略改成分片广播（原来选的是"第一个"），这样所有节点都会收到任务。第二步改任务执行器：在任务方法里拿到分片参数，再据此对售货机表的数据做切分。

切数据有两种常用方法。

第一种是分页。拿到分片总数和当前索引，相当于把全部数据分成三页，分片索引就是页码。分页查询必须告诉它每页查多少条，所以要先统计售货机总数：总数除以分片数就是每页大小——3万条、3个分片，每页查1万条，再做分页查询。缺点是多一次count查询，每次执行前都得先统计总个数。

第二种是根据ID取模运算。只需在查询条件里加一个条件：id对分片总数取模，结果等于当前分片索引。取模天然把数据相对平均地分成几份，不用再查记录总数。ID连续时分片结果非常均匀；ID不连续时可能不是特别均匀，但省掉了统计这一步。

课程采用第二种。

## 代码实现与测试：三个执行器并行跑

### 改路由策略，拿分片参数

调度中心任务管理里找到"扫描售货机"任务（JobHandler为supplyJobHandler，Cron为0 0 4 * * ?，每天凌晨4点执行），点编辑，把路由策略改为分片广播，保存。

售货机微服务里的SupplyJob类是任务执行的地方，supplyJobHandler方法开头先拿分片参数。XXL-JOB提供了分片工具类ShardingUtil，getShardingVo()返回ShardingVO对象，里面就两个属性：getTotal()是分片总数，getIndex()是当前分片索引。

```java
@XxlJob("supplyJobHandler")
public ReturnT<String> supplyJobHandler(String param) throws Exception {
    // 获取分片参数
    ShardingUtil.ShardingVO shardingVO = ShardingUtil.getShardingVo();
    int numbers = shardingVO.getTotal(); // 分片总数
    int index = shardingVO.getIndex();   // 当前分片索引

    log.info("分片参数：当前分片索引={}，总分片数={}", index, numbers);
    XxlJobLogger.log("分片参数：" + index + "/" + numbers);

    // 获取缺货告警阈值
    Integer percent = taskService.getSupplyAlertValue();

    // 查询运营状态的售货机，id 对分片总数取模等于当前索引，只取本分片的数据
    QueryWrapper<VendingMachineEntity> qw = new QueryWrapper<>();
    qw.eq("v_status", VM_STATUS_RUNNING);
    qw.apply("mod(id, " + numbers + ") = " + index);
    List<VendingMachineEntity> vmList = vmService.list(qw);

    vmList.forEach(vm -> {
        int count = vmService.inventory(percent, vm);
        if (count == 0) {
            XxlJobLogger.log("售货机" + vm.getInnerCode() + "缺货");
            vmService.sendSupplyTask(vm);
        }
    });
    return ReturnT.SUCCESS;
}
```

拿参数之外只加了一个apply条件，其余都是上一小节已有的逻辑。apply是QueryWrapper里可以传一段字符串SQL的方法，内容直接拼进语句，非常灵活；这里拼的是对id取模——mod(id, 分片总数) = 当前分片索引。分片总数不是写死的，从ShardingVO里读出来拼进去。后面照旧：逐台检查库存，缺货就记日志、发补货工单。

日志打了两份：log.info进微服务控制台，XxlJobLogger.log进调度中心的执行日志，两边都能核对分片参数。

### 起三个实例的准备

测试前先清数据：删掉之前测试产生的工单明细表数据，以及工单表里的自动补货工单——有未完成工单挂着，新工单生成不出来。然后把售货机微服务和工单微服务都跑起来。

要看出分片效果，一个售货机微服务实例不够，得同时起三个。同一个微服务起多份，两处端口必须错开：

- server.port：9004之外，第二份改9104，第三份改9204，不改必然端口冲突；
- 配置中心（Consul）里售货机微服务与XXL-JOB通信的端口：原有实例9980，第二份改9988，第三份改9989。

```yaml
xxl:
  job:
    executor:
      port: 9988   # 与调度中心的通信端口，多实例之间必须错开
```

IDEA里同一个类默认只能单实例运行，第二次启动会提示该类正在运行、询问是否停止再运行。到编辑配置窗口勾选右上角的"允许同时运行"，确定之后就能连续启动多个实例。

三份都起来后，打开调度中心刷新执行器页面，三个实例（9980、9988、9989）都注册上来——注册会稍有延迟，没刷出来就再刷一次。

### 执行一次，看三条日志

任务管理里对扫描售货机任务点"执行一次"，提示执行成功。打开调度日志，三条记录同时生成、同一时间执行，总分片数都是3，索引分别为2、1、0。逐条点开执行日志：索引为2的那条扫到尾号1、5的售货机，索引为1的那条扫到尾号0、4、3、7，索引为0的那条扫到尾号6——三份扫描互不重复，原来一个节点的活被均摊成了三份，加起来正好是全部售货机。

## 小结

分片广播解决的是"一个节点串行扫全量太慢"的问题：路由策略从"选一个执行"变成"广播给全体执行"，数据归属靠分片参数划清——每个执行器拿到同样的两个数（分片总数、从0开始的当前索引），用 mod(id, 总数) = 索引 这样一个条件就把数据切得互不重叠。切分方法里取模比分页少了count这一步，课程选它。测试的关键是让三个执行器真正同时在跑：业务端口、与调度中心的通信端口、IDEA的允许同时运行，三件事缺一不可；最后从调度日志的三条同时刻记录、三个不同索引、互不重叠的扫描结果上确认分片生效。
