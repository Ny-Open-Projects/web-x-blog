# 售货机端出货业务：需求思路、出货通知处理与出货上报

第九章深入售货机"五脏六腑"，出货业务是售货机端最核心的一块。用户扫码支付成功后，服务端通过EMQ向售货机发出货通知，售货机选货道、扣库存、记出货流水，再把结果上报服务端，最后清掉本地临时记录。这篇按需求与协议、出货通知处理、出货上报与本地清理三步，把这条核心链路讲透。

## 先给结论

- 出货流程一来一回两个协议：服务端→售货机的vendoutReq（skuId、requestTime、orderNO、timeout、payPrice、payType），售货机→服务端的vendoutResp（success、orderNO、price、skuId、channelId、outTime、resultCode）。resultCode区分出货成功、货道已空、设备故障、出货中等各种结果。
- 由哪个货道出货由售货机端决定：同一商品可能有多个货道，可以随机取一个，也可以从库存最多的货道出。课程实现按货道库存capacity倒序取第一条，即从库存最多的货道出。
- 通知处理做两件事加一个占位：扣货道库存（capacity减一并更新）、插入出货记录；调用串口出货的部分不实现。查不到有库存的货道就置resultCode为货道空、success为false，直接返回。
- 出货上报就是查询、封装、发送三步：按订单号查本地出货记录，构建vendoutResp协议（指定SN、innerCode、needResp，resultCode为零表示成功），用EMQ客户端的publish发布出去。
- 本地出货记录是临时记录：上报送达确认后才删，删除动作挂在EMQ回调的deliveryComplete（送达完成方法）里，而不是发完就删——服务端可能收不到，本地先删就两端不一致了。
- 售货机当机、没来得及上报会造成售货机端与服务端数据不统一，"记录-上报-确认-删除"这套机制正是为兜住这类特殊情况设计的。

## 需求与协议：一来一回的出货约定

回顾出货流程：用户拿起手机扫售货机上的二维码，手机上展现出商品列表；选一个商品完成支付；支付成功后，服务端向售货机端发起出货通知；售货机处理完出货操作，再把结果回馈给服务端。

### 出货通知：服务端→售货机

```json
{
  "msgType": "vendoutReq",
  "sn": "3242424343",
  "innerCode": "01012121",
  "needResp": true,
  "vendoutData": {
    "skuId": 1,
    "requestTime": "2019-07-01T18:29:01",
    "orderNO": "324234234242",
    "timeout": 30,
    "payPrice": 500,
    "payType": 123
  }
}
```

vendoutData告诉售货机：出什么商品（skuId）、请求时间（requestTime）、出货订单号（orderNO）、出货请求的超时时间（timeout）、支付价格（payPrice）和支付类型（payType）。

### 出货上报：售货机→服务端

售货机处理完出货，回馈的结果长这样：

```json
{
  "msgType": "vendoutResp",
  "sn": "1111111",
  "innerCode": "01012121",
  "needResp": true,
  "vendoutResult": {
    "success": true,
    "payType": 123,
    "orderNO": "324234234242",
    "price": 500,
    "skuId": 1,
    "channelId": "1-1",
    "outTime": "2019-05-01T12:01:01",
    "resultCode": 0
  }
}
```

服务端靠orderNO匹配这是哪个订单的结果；price是售价；outTime记录什么时间完成了出货；resultCode是结果码，出货成功、货道已空、设备故障、机器出货中、连续支付、服务器超时都在这里区分。最关键的是channelId——由哪个货道发货，这个运算在售货机端做。

### 实现思路

售货机收到出货通知后的处理链是：调用硬件出货 → 记录出货信息 → 上报服务。硬件调用部分课程不讲：一来受条件所限没有硬件可测，二来这不是软件工程师的学习方向，属于硬件工程师的事。这里忽略硬件操作，重点放在整个处理流程上。

两个必须考虑的点。其一，售货机可能当机、没来得及上报，造成售货机端与服务器之间数据不统一，所以要先在本地记录出货信息，再上报服务端。其二，同一个商品可能存在多个货道，究竟从哪个货道出由售货机决定：随机取一个货道，或者从商品库存最多的货道出货，都可以——做个排序就够了。

## 出货通知处理：扣库存、记流水、留硬件口子

### 协议封装

出货通知的EMQ协议对象分两层，外层VendoutReq持有内层VendoutReqData，具体业务数据都在内层：

```java
@Data
public class VendoutReq extends BaseData {
    private VendoutReqData vendoutData;
}

@Data
public class VendoutReqData {
    private String skuId;        // 商品ID
    private String requestTime;  // 请求时间
    private String orderNo;      // 订单号
    private Integer timeout;     // 超时时间
    private Integer payPrice;    // 支付价格
    private Integer payType;     // 支付类型
    private boolean success;
}
```

### 处理逻辑

服务接口里新建一个专门处理出货通知的方法，入参就是出货协议类型。实现类里要做的是修改库存、增加出货记录，调用串口出货只留占位不实现。

```java
public void vendoutReq(VendoutReq vendoutReq) {
    if (vendoutReq.getVendoutData() == null) {
        return; // 协议数据为空，不做任何操作
    }
    // 实例化出货记录对象，取商品ID并拷贝同名属性，记录出货时间
    VendoutOrder vendoutOrder = new VendoutOrder();
    vendoutOrder.setSkuId(vendoutReq.getVendoutData().getSkuId());
    BeanUtils.copyProperties(vendoutReq.getVendoutData(), vendoutOrder);
    vendoutOrder.setOutTime(new Date());

    // 查有库存的货道：skuId匹配且capacity>=1，按库存倒序
    QueryWrapper<Channel> channelQueryWrapper = new QueryWrapper<>();
    channelQueryWrapper.lambda()
            .eq(Channel::getSkuId, vendoutReq.getVendoutData().getSkuId())
            .ge(Channel::getCapacity, 1)
            .orderByDesc(Channel::getCapacity);
    List<Channel> channelList = channelMapper.selectList(channelQueryWrapper);
    if (channelList == null || channelList.isEmpty()) {
        // 商品已无库存：货道为空
        vendoutOrder.setResultCode(1);
        vendoutOrder.setSuccess(false);
        return;
    }
    // 取库存最多的货道，容量减一并更新
    Channel channel = channelList.get(0);
    channel.setCapacity(channel.getCapacity() - 1);
    channelMapper.updateById(channel);

    // 此处调用串口出货（课程省略）

    // 出货成功：结果码0，记录货道号
    vendoutOrder.setResultCode(0);
    vendoutOrder.setChannelId(channel.getChannelId());
    vendoutOrder.setSuccess(true);
    // 插入出货记录表
    vendoutOrderMapper.insert(vendoutOrder);
}
```

流程拆开看：先判断协议数据是否为空，空就直接返回；实例化出货记录对象，从协议数据中提取商品ID设置进去，属性名相同的字段一并拷贝过来，再记下当前时间作为出货时间。然后查货道，条件是商品ID等于协议里的skuId、货道库存数大于等于1，按库存倒序排序——列表第一条就是库存最多的货道。列表为空说明这个商品已经没有库存，置resultCode为货道空、success为false，直接返回不做任何操作。有货道就取第一条把容量减一、更新货道库存，随后是留空的串口出货调用。出货成功设置结果码0、记录是哪个货道、success置true；失败则设置相应的错误返回码和false。最后执行出货记录的插入，落到出货记录表。

### 回调接入与连调

消息进来走EMQ回调。EmqMsgCallback的messageArrived里先匹配协议名称，是出货通知就解析协议内容，调用上面写的处理逻辑；异常用try-catch兜住记日志；finally里留了个待办——出货完毕上报服务器，这是下一步的事。这一步完成的是本地数据的更改。

```java
if (MsgType.VENDOUT_REQ.getType().equalsIgnoreCase(msgType)) {
    VendoutReq vendoutReq = JSON.parseObject(payload, VendoutReq.class);
    log.info("出货通知 vendoutReq {}", vendoutReq);
    try {
        dataProcessService.vendoutReq(vendoutReq);
    } catch (Exception ex) {
        log.info("出货异常", ex);
    } finally {
        // TODO 出货完毕上报服务器
    }
}
```

代码完成后可以连调：把之前的小程序跑起来下一单，查出货记录表——tb_vendout_order里出现带ORDER_NO、PAY_TYPE、CHANNEL_ID、SKU、PAY_PRICE、OUT_TIME、RESULT_CODE的记录，通知处理就闭环了。

## 出货上报与本地清理：查询、封装、发送，确认后删除

售货机完成出货操作后，要把出货情况上报服务端：结果成功还是失败、走的哪个货道。

上报协议里有个出货结果属性，它的字段和出货记录表结构完全一样——上报数据直接从出货记录表里查出来就行。封装类型VendoutResult因此只定义一个属性，类型直接用了出货记录的表实体类：

```java
@Data
public class VendoutResult extends BaseData {
    private VendoutOrder vendoutResult; // 出货结果，直接复用出货记录表实体类
}
```

实现还是服务接口加方法的路子。上报方法的核心：根据订单号查订单记录，查到就把数据提出来，构建协议类型——实例化协议类，指定售货机编号innerCode、指定SN、needResp设为回馈，返回码resultCode为零表示成功，再把查出来的订单记录赋给vendoutResult属性，整个上报结构就齐了，最后调用EMQ客户端的publish方法发布出去。思路就是查询、封装、发送，比较简单。

### 上报后删除本地记录

上报之后还有一件事：把本地出货记录删掉。出货记录只是临时记录，所有出货记录中没被删除的其实都是有问题的；上报并确认服务端收到后，这笔交易就结束了，本地没必要再存。

封装一个出货完成方法，就一句删除——根据订单号删记录：

```java
public void vendoutComplete(String orderNo) {
    // 出货记录是临时记录，服务端确认收到后即可删除
    vendoutOrderMapper.deleteById(orderNo);
}
```

调用时机要注意：应该在服务端正常接收了消息之后再删，而不是发完就删——发完有可能服务端收不到，本地又没了，数据肯定不一致。怎么判断服务端收到了？EMQ回调类里有送达完成方法deliveryComplete，服务端正确收到上报消息时触发。在这个方法里从参数中提取MQTT message，从消息中提取发送内容，从内容中提取协议名称，判断与出货上报协议一致后，从中提取订单号，按订单号删除出货记录：

```java
@Override
public void deliveryComplete(IMqttToken token) {
    // 服务端已正确收到上报消息
    MqttMessage message = token.getMessage();
    String payload = new String(message.getPayload());
    String msgType = JSONPath.read(payload, "$.msgType").toString();
    if (MsgType.VENDOUT_RESP.getType().equalsIgnoreCase(msgType)) {
        String orderNo = JSONPath.read(payload, "$.vendoutResult.orderNo").toString();
        dataProcessService.vendoutComplete(orderNo); // 按订单号删除本地出货记录
    }
}
```

正常完成一笔交易后，本地这条出货记录就从数据库里删掉了。顺带一提上报异常：网络抖动可能导致上报没送达，服务端和售货机端数据不一致——这正是删除动作必须挂在送达确认之后的原因。

## 小结

出货业务是售货机端的核心链路，协议先定规矩：服务端vendoutReq告诉售货机出什么货，售货机vendoutResp回报从哪个货道出的、结果如何；货道选择权在售货机端，按库存倒序取第一条就实现了"从最多的货道出货"。通知处理三板斧——扣货道库存、插出货记录、留串口出货的口子；查不到有库存的货道就以货道空结果直接返回。上报是查询、封装、发送三步，数据来源就是本地出货记录表；这张表只存临时数据，删除动作挂在EMQ送达完成回调里，确认服务端收到才删。宕机未上报、网络抖动这些异常场景，正是这套"记录-上报-确认-删除"机制要兜住的数据一致性问题。
