# 货物类型管理接口：新增收尾、按 id/全量/分页查询的完整实现

上篇把新增货物类型的 Controller 和两个 Service 接口定了形，但 service 实现类、mapper 接口都还是空头支票，接口测不出结果。本篇先把这些欠账补齐，让新增真正落库、连着关联表一起写通，再顺着讲义把按 id 查询、查询所有、分页查询三个查询接口一次做完。四个接口走完，货物类型管理在 pd-base 这一层的读写就闭环了。

## 先给结论

- Service 接口继承 MyBatis-Plus 的 `IService<T>`，实现类继承 `ServiceImpl<M, T>`（第一个泛型是 Mapper 接口、第二个是实体），getById、saveBatch 这类常规方法直接白拿；Mapper 接口继承 `BaseMapper<T>` 加 `@Mapper` 即可，框架基于代理生成对象，不需要写实现类。
- 主键不靠数据库自增：保存前注入 CustomIdGenerator 生成 ID，nextId 返回数值类型而 id 字段是 String，惯用 `idGenerator.nextId(entity) + ""` 空串拼接完成转换；关联记录逐条设 ID 后调父类 saveBatch 批量入库。
- 默认 CRUD 不需要在 Mapper XML 里写 SQL，只补文档头信息和 namespace 骨架；namespace 必须与接口全限定名一致，Ctrl+点击能跳到接口就说明路径正确。只有框架没提供的自定义方法才需要自己写 SQL。
- 按 id 查询是两步：getById 查主表拿基本信息，再按 goodsTypeId 查关联表，stream map 抽出 truckTypeId 收集成 List 塞进 DTO；关联查询条件用 LambdaQueryWrapper 按 StringUtils.isNotEmpty 动态拼。
- 「查询所有」不是全表：实体里有 status 字段（0 禁用、1 正常），只查 status=1 的正常记录，条件写死不作为参数，也不查关联信息，比按 id 查询还简单。
- 分页是本篇唯一的重活：service 里 new Page 加排序，SQL 交给自定义 findByPage 动态拼接（LIMIT 由 PaginationInterceptor 拦截器自动补），Controller 把 IPage 里的实体转成 DTO 列表，最后 PageResponse.builder() 组装成 pd-common 统一的分页返回。

## 新增收尾：ServiceImpl、BaseMapper 与 XML

新增货物类型在 Controller 层拆成两个动作：保存货物类型本身，以及批量保存货物类型与车辆类型的关联。两个 service 接口都继承 MyBatis-Plus 提供的 IService，泛型分别指向 PdGoodsType 和 PdTruckTypeGoodsType。继承的好处是常规增删改查方法全部现成，接口里只需要声明批量保存这种框架没有的业务方法。

实现类按 base/truck 分包，货物类型的实现类放在 base 下的 impl 包，类上加 @Service，继承 ServiceImpl 并实现自己的接口：

```java
@Service
public class PdGoodsTypeServiceImpl
        extends ServiceImpl<PdGoodsTypeMapper, PdGoodsType>
        implements IPdGoodsTypeService {

    @Autowired
    private CustomIdGenerator idGenerator;

    @Override
    public PdGoodsType saveGoodsType(PdGoodsType pdGoodsType) {
        // 保存之前先生成 id：nextId 返回数值类型，id 是 String，空串拼接转类型
        pdGoodsType.setId(idGenerator.nextId(pdGoodsType) + "");
        baseMapper.insert(pdGoodsType);
        return pdGoodsType;
    }
}
```

ServiceImpl 上两个泛型，第一个是持久层 Mapper 接口，第二个是实体；baseMapper 是从父类继承来的字段，insert 这类方法框架已经提供。保存前必须先设置 id：Controller 传进来的 DTO 根本没有 id，而主键策略是 IdType.INPUT、由应用侧生成，nextId 出来是数值类型，setId 收 String，加一个空串就把类型转过去了。返回值带着生成的 id 回去，Controller 后面组装关联记录还要用它。

关联表的实现类结构完全一样，放在 truck 包的 impl 下。batchSave 里对 list 做 forEach，逐条设置 id（goodsTypeId、truckTypeId 两个字段在 Controller 组装时已经赋好，就差 id），然后直接调父类提供的批量保存方法：

```java
@Override
public void batchSave(List<PdTruckTypeGoodsType> truckTypeGoodsList) {
    truckTypeGoodsList.forEach(truckTypeGoods ->
            truckTypeGoods.setId(idGenerator.nextId(truckTypeGoods) + ""));
    saveBatch(truckTypeGoodsList);
}
```

两个 Mapper 接口对应创建在 mapper 包的 base、truck 子包下，继承 BaseMapper、加 @Mapper 注解就完事：

```java
@Mapper
public interface PdGoodsTypeMapper extends BaseMapper<PdGoodsType> {
}
```

Mapper 不需要实现类：MyBatis-Plus 底层基于代理技术，由框架为接口产生代理对象，直接操作接口即可，代码量省掉一大截。

最后是 mapper 映射文件，resources/mapper 下同样分 base、truck 两层，各建一个与接口同名的 XML。当前这两个文件里什么都不用写，因为调用的增删改查全是框架默认方法，SQL 由框架提供，只需要把文档头信息和 mapper 根标签的骨架摆好：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.itheima.pinda.mapper.truck.PdTruckTypeGoodsTypeMapper">
</mapper>
```

namespace 必须与接口的全限定名对上，写完按住 Ctrl 点击能跳到接口，就说明类路径完全正确；哪天有了框架没提供、需要自定义的方法，才在这里编写 SQL。

启动服务没有报错，用 Swagger 实测。测之前先看库：pd_base 里 pd_goods_type 有 32 条测试数据，关联表 pd_truck_type_goods_type 有 49 条。try it out，id 不用填（由 Id 生成器产生），name 填「3C产品」，status 填 1（正常），truckTypeIds 从 pd_truck_type 表里复制两个真实车辆类型 id 添加进去（它是 List 集合，可以关联多个车辆类型），执行。响应的 DTO 里 id 已经有值，说明保存成功。回数据库验证：pd_goods_type 变成 33 条，新增的正是 3C产品；关联表变成 51 条，多了两条，用 SQL 按货物类型 id 查出来核对：

```sql
SELECT * FROM pd_base.pd_truck_type_goods_type
WHERE goods_type_id = <刚才返回的货物类型id>;
```

刚插入的两条关联记录都能查到，新增接口闭环。

## 按 id 查询与查询所有：查主表 + 查关联的两步套路

### 按 id 查询

前端约定通过路径变量把 id 传过来，方法上要配 `@GetMapping("/{id}")` 和 `@PathVariable`：

```java
@GetMapping("/{id}")
@ApiOperation(value = "根据id查询货物类型")
public GoodsTypeDto findById(@PathVariable(name = "id") String id) {
    // 1. 查货物类型基本信息
    PdGoodsType pdGoodsType = goodsTypeService.getById(id);
    GoodsTypeDto goodsTypeDto = new GoodsTypeDto();
    BeanUtils.copyProperties(pdGoodsType, goodsTypeDto);
    // 2. 查当前货物类型关联的车辆类型id（多对多，可能有多个）
    List<PdTruckTypeGoodsType> list = truckTypeGoodsTypeService.findAll(null, id);
    if (list != null && list.size() > 0) {
        List<String> truckTypeIds = list.stream()
                .map(pdTruckTypeGoodsType -> pdTruckTypeGoodsType.getTruckTypeId())
                .collect(Collectors.toList());
        goodsTypeDto.setTruckTypeIds(truckTypeIds);
    }
    return goodsTypeDto;
}
```

getById 不是接口里自己声明的方法，是继承 IService 白拿的。但只查主表不够：DTO 里还有 truckTypeIds，货物类型和车辆类型是多对多，一个货物类型可能关联多个车辆类型，关联信息得再查一遍。于是在 IPdTruckTypeGoodsTypeService 里扩展一个 findAll(String truckTypeId, String goodsTypeId)，两个条件都可以传也可以不传，返回关联对象集合。实现里用 LambdaQueryWrapper 动态封装条件，为空就忽略：

```java
@Override
public List<PdTruckTypeGoodsType> findAll(String truckTypeId, String goodsTypeId) {
    LambdaQueryWrapper<PdTruckTypeGoodsType> wrapper = new LambdaQueryWrapper<>();
    if (StringUtils.isNotEmpty(truckTypeId)) {
        wrapper.eq(PdTruckTypeGoodsType::getTruckTypeId, truckTypeId);
    }
    if (StringUtils.isNotEmpty(goodsTypeId)) {
        wrapper.eq(PdTruckTypeGoodsType::getGoodsTypeId, goodsTypeId);
    }
    return baseMapper.selectList(wrapper);
}
```

Controller 里调 findAll 时车辆类型 id 没有，直接传 null，只按货物类型 id 查。查回来的关联对象里真正要的是 truckTypeId，stream + map 一个个抽出来，collect 成 `List<String>` 再 setTruckTypeIds。先判 list 非空且 size 大于 0 再做流处理，比较保险。

测试时 id 不能乱填，要从 pd_goods_type 表里复制一条真实存在的（比如 889255497728），执行后响应里除了 name 这些普通属性，truckTypeIds 也带出了关联的车辆类型 id。顺带一提，@ApiOperation 不是必须的注解，不写时文档里显示方法名，写上描述更明确。

### 查询所有

查询所有货物类型，「所有」两个字要打个引号：实体里有 status 字段，0 表示禁用、1 表示正常，所谓查询所有只查状态正常的那些，禁用的不往外吐。条件已经定死，方法不需要参数；也不像按 id 查询那样要查关联信息，只取货物类型基本信息，反而更简单。Controller 层查回实体集合后统一转 DTO：

```java
@GetMapping("/all")
@ApiOperation(value = "查询所有货物类型")
public List<GoodsTypeDto> findAll() {
    List<PdGoodsType> goodsTypeList = goodsTypeService.findAll();
    if (goodsTypeList != null && goodsTypeList.size() > 0) {
        return goodsTypeList.stream().map(goodsType -> {
            GoodsTypeDto goodsTypeDto = new GoodsTypeDto();
            BeanUtils.copyProperties(goodsType, goodsTypeDto);
            return goodsTypeDto;
        }).collect(Collectors.toList());
    }
    return null;
}
```

DTO 与实体的属性一一对应，map 里 new 一个 DTO、BeanUtils.copyProperties 拷贝、返回，最后 collect 收集成集合。service 实现只有一个等值条件：

```java
@Override
public List<PdGoodsType> findAll() {
    QueryWrapper<PdGoodsType> wrapper = new QueryWrapper<>();
    wrapper.eq("status", 1);
    return baseMapper.selectList(wrapper);
}
```

这里顺带理一下调用链：这些接口都是给前端用的，但前端不会直接调 pd-base，而是调 pd-web，由 pd-web 再转发到 pd-base，pd-base 始终待在后端。Swagger 里 try it out 直接执行，返回的 JSON 数组把正常状态的货物类型全带出来了。

## 分页查询：动态 SQL 与 PageResponse 组装

分页查询的返回值统一用 `PageResponse<GoodsTypeDto>`，这是 pd-common 模块里定义的通用分页包装类，凡是分页接口都返回它：counts 总条数、pageSize 页尺寸（每页多少条）、pages 总页数、page 当前页码、items 当前页数据列表。查询条件一共五个：page、pageSize 必传，name（货物类型名称）、truckTypeId、truckTypeName 三个可传可不传（required = false）：

```java
@GetMapping("/page")
@ApiOperation(value = "分页查询货物类型")
public PageResponse<GoodsTypeDto> findByPage(
        @RequestParam(name = "page") Integer page,
        @RequestParam(name = "pageSize") Integer pageSize,
        @RequestParam(name = "name", required = false) String name,
        @RequestParam(name = "truckTypeId", required = false) String truckTypeId,
        @RequestParam(name = "truckTypeName", required = false) String truckTypeName) {
    // ...
}
```

service 接口里声明 findPage，返回 MyBatis-Plus 的 `IPage<PdGoodsType>`：分页由框架实现，框架分页返回的就是这个类型，Page 是它的实现类。实现里先 new Page 把两个分页参数装进去，顺手按 id 升序排，然后调自定义的 mapper 方法查记录、塞回分页对象：

```java
@Override
public IPage<PdGoodsType> findPage(Integer page, Integer pageSize, String name,
                                   String truckTypeId, String truckTypeName) {
    // 封装分页条件
    Page<PdGoodsType> pdPage = new Page<>(page, pageSize);
    // 按货物类型id升序排列
    pdPage.addOrder(OrderItem.asc("id"));
    pdPage.setRecords(baseMapper.findByPage(pdPage, name, truckTypeId, truckTypeName));
    return pdPage;
}
```

Page 对象作为第一个参数传给 mapper，因为之前注册过 PaginationInterceptor 分页拦截器，拦截器看到 Page 参数会自动往 SQL 后面拼 LIMIT 等分页语句，动态 SQL 里完全不用写分页关键字。Mapper 接口声明 findByPage，XML 里写动态 SQL，三个业务条件对应三个 if：

```xml
<select id="findByPage" resultType="com.itheima.pinda.entity.base.PdGoodsType">
    SELECT goods_type.*
    FROM pd_goods_type goods_type
    <if test="truckTypeId != null or truckTypeName != null">
        LEFT JOIN pd_truck_type_goods_type truck_type_goods_type
            ON goods_type.id = truck_type_goods_type.goods_type_id
        <if test="truckTypeName != null">
            LEFT JOIN pd_truck_type truck_type
                ON truck_type_goods_type.truck_type_id = truck_type.id
        </if>
    </if>
    <where>
        goods_type.status = 1
        <if test="truckTypeName != null">
            AND truck_type.status = 1
        </if>
        <if test="name != null">
            AND goods_type.name LIKE CONCAT('%', #{name}, '%')
        </if>
        <if test="truckTypeId != null">
            AND truck_type_goods_type.truck_type_id = #{truckTypeId}
        </if>
        <if test="truckTypeName != null">
            AND truck_type.name LIKE CONCAT('%', #{truckTypeName}, '%')
        </if>
    </where>
</select>
```

结构上有两点值得注意。一是货物类型表里根本没有车辆类型的字段，条件要落在关联表上就得 LEFT JOIN：传了 truckTypeId 或 truckTypeName 才连关联表，传了 truckTypeName 还要再连车辆类型表；上面的 join 与下面的 where 条件一一对应，连表就是为了条件能用。二是 where 里固定 `goods_type.status = 1`，与查询所有的口径一致，用车辆类型表过滤时对它也补了 status=1；name 和 truckTypeName 走 LIKE 模糊查询。

回到 Controller，查回来的 IPage 里装的是实体，最终要返回 PageResponse 装着 DTO，而且分页查出的每条货物类型同样缺关联的车辆类型 id。处理套路和按 id 查询一致：getRecords 拿到记录集合，非空则 stream map，对每条记录调 findAll(null, goodsType.getId()) 查关联、抽 truckTypeId、BeanUtils 拷属性、set 关联字段，collect 成 DTO 列表，最后用 PageResponse 的构建器组装：

```java
IPage<PdGoodsType> goodsTypePage =
        goodsTypeService.findPage(page, pageSize, name, truckTypeId, truckTypeName);
List<PdGoodsType> goodsTypePageRecords = goodsTypePage.getRecords();
if (goodsTypePageRecords != null && goodsTypePageRecords.size() > 0) {
    List<GoodsTypeDto> dtoList = goodsTypePageRecords.stream().map(goodsType -> {
        List<String> truckTypeIds =
                truckTypeGoodsTypeService.findAll(null, goodsType.getId())
                        .stream()
                        .map(pdTruckTypeGoodsType -> pdTruckTypeGoodsType.getTruckTypeId())
                        .collect(Collectors.toList());
        GoodsTypeDto goodsTypeDto = new GoodsTypeDto();
        BeanUtils.copyProperties(goodsType, goodsTypeDto);
        goodsTypeDto.setTruckTypeIds(truckTypeIds);
        return goodsTypeDto;
    }).collect(Collectors.toList());
    return PageResponse.<GoodsTypeDto>builder()
            .items(dtoList)
            .counts(goodsTypePage.getTotal())
            .page(page)
            .pages(goodsTypePage.getPages())
            .pageSize(pageSize)
            .build();
}
return null;
```

counts 从 IPage 的 getTotal 拿（分页查询时拦截器已经算好总数），page、pageSize 用传进来的值，pages 从 getPages 拿，PageResponse 类上的 @Builder 让这一切链式调用就能完成。

Swagger 实测：page=1、pageSize=5，其余先不填，返回 counts=11、分成 3 页、当前第 1 页，items 封装成数组，里面记录的 status 都是 1。加上 name=食品 再查，只剩 1 条，counts 和 pages 都变成 1。再补一个从库里复制的 truckTypeId（123103137595676608），带着食品名查仍是 1 条；把食品去掉只按车辆类型 id 查，查出 8 条，三种条件的过滤都符合预期。

## 小结

- 新增收尾三件套：实现类继承 ServiceImpl(M, T) 白拿 CRUD，Mapper 继承 BaseMapper 交给代理，XML 只写骨架；保存前用 CustomIdGenerator 生成主键，数值转 String 用空串拼接，关联记录 forEach 设 id 后 saveBatch 批量插入，实测主表 32→33 条、关联表 49→51 条。
- 按 id 查询是主表加关联两步：getById 查基本信息，findAll（LambdaQueryWrapper 动态条件）查关联表，stream 抽 truckTypeId 塞进 DTO；@ApiOperation 可选，不写就用方法名。
- 查询所有只查 status=1，条件写死、不查关联，Controller 里 stream map 加 BeanUtils 把实体统一转成 DTO。
- 分页走 Page 对象加自定义 findByPage 动态 SQL：分页关键字由 PaginationInterceptor 拦截器补，业务 SQL 只管三个 if 条件与按需 LEFT JOIN；Controller 把 IPage 记录转成 DTO 列表后 PageResponse.builder() 组装返回。
- 分页测试口径：page=1、pageSize=5 查出 11 条分 3 页；name=食品 收敛到 1 条；按 truckTypeId（123103137595676608）查出 8 条。
