# 分布式 ID 服务收尾：客户端接入三步与四种 ID 生成实测

上一篇把分布式 ID 服务的定位、四类应用场景和 server 端部署交代完了：只依赖 MySQL，服务起在 18099 端口，HTTP 接口直接可调——server 端的 IdController 提供 /increment、/snowflake、/segment 三个接口。这一篇收尾，解决第三方系统怎么接进来的问题：client 模块把这几个接口封装成了工具方法，调用方连接口都不用拼。引依赖、写配置、调静态方法三步走完，再建一个演示工程把四种 ID 全部生成一遍。

## 先给结论

- 接入三步：client 模块先 `mvn install` 装进本地 Maven 仓库（有私服就装私服，全公司团队共享）→ 自己的项目引入 distributedid-client 坐标 → 调 DistributedId 工具类的静态方法取 ID。
- 配置文件 distributedid_client.properties 的名字和位置都不能改：必须叫这个名字、必须放在 resources 根目录，client 包按固定路径读取它获取服务端地址，不按要求写就读不到配置。
- 配置项就三个：distributedid.server 指向 server 的 IP:端口（演示环境 localhost:18099，集群多节点用逗号分隔），readTimeout、connectTimeout 各 5000 毫秒。
- 四种取号方式：autoincrementId(bizType) 从服务端取自增 ID、snowflake() 本地直接生成雪花 ID（不调服务）、snowflakeFromServer() 从服务端取雪花 ID、segment(bizType, batchSize) 号段模式一次取一段。
- bizType 是业务类型，一般就传服务名——不同系统、不同业务共用同一个发号器，靠它区分各自的号，演示里用了 sms 和 tms。
- 实测输出：服务端自增 ID 62、本地雪花 51520929715567616、服务端雪花 51520929712365312，三种路径全部打通。

## 接入三步：装包、引坐标、写配置

server 部署好之后，任何想拿 ID 的系统都是同一个接入姿势。

**第一步，安装 client。** client 模块要先安装到本地 Maven 仓库；如果是团队协作，公司一般有自己的私服，把它装到私服上，整个开发团队就都能用了。

**第二步，引坐标。** 在自己项目的 pom 里加入 client 的依赖：

```xml
<dependency>
    <groupId>com.itcast.distributedid</groupId>
    <artifactId>distributedid-client</artifactId>
    <version>1.0-SNAPSHOT</version>
</dependency>
```

**第三步，写配置文件。** 在 resources 根目录创建 distributedid_client.properties：

```properties
#服务器地址
distributedid.server=localhost:18099
#部署多个的话，可自行添加
#distributedid.server=211.103.136.244:7315,ip2:port,...
#超时时间
distributedid.readTimeout=5000
distributedid.connectTimeout=5000
```

文件名之所以不能改，是因为引入的 client 架包会去读取这个固定名称的文件来获取配置信息，不按它的要求写就读不到。server 地址按实际部署填：演示服务就跑在本地，端口 18099 与服务端 application.yml 的 server.port 对应；如果分布式 ID 服务部署了集群，多个节点的 IP:端口用逗号分隔即可，客户端自己会处理。

## 工具类设计：四种取号路径

DistributedId 类来自 client 包，可以看成一个工具类，里面封装了一批静态方法。核心成员三个：IdGenClientFactory 客户端工厂，负责与 server 远程通信——底层通过 Feign 调到服务端接口，最终 ID 在 server 那边生成；一个本地 Snowflake 实例；还有一个 userMap，按数据中心与机器标识管理多个雪花实例，供多节点场景使用。

```java
public class DistributedId {
    private static IdGenClientFactory clientFactory = IdGenClientFactory.getInstance(null);
    private static Snowflake snowflake = new Snowflake();
    private static Map<String, Snowflake> userMap = new HashMap<>();

    public static Long autoincrementId(String bizType) {
        return clientFactory.getAutoincrementId(bizType);   // 服务端自增 ID
    }

    public static Long snowflake() {
        return snowflake.nextId();                          // 本地雪花，不走网络
    }

    public static Long snowflakeFromServer() {
        return clientFactory.getSnowflakeId();              // 服务端雪花 ID
    }

    public static List<Long> segment(String bizType, Integer batchSize) {
        // 号段模式，一次取回一段
    }
}
```

四个方法对应几条取号路径：自增型必须到服务端取，发号器统一维护；雪花算法本地就能算，也可以选择从服务端取，由服务端统一管控；号段模式一次取回一段 ID 在本地分配，正是前面讲过的趋势递增场景。这些方法与服务端的三个接口一一对应：HTTP 直调与 SDK 封装是同一个发号器的两面，项目里没有其他依赖时直调接口也行，正式开发则推荐引入 client。对使用者来说实现差异被静态方法屏蔽了，调哪个方法、ID 从哪来，一目了然。

## 实操演示：四种 ID 全部生成

建一个第三方演示工程 distributedid-demo，按三步接好：装包、引坐标、把 properties 放进 resources 根目录。然后写一个 main 方法做测试：

```java
public class DistributedIdTest {
    public static void main(String[] args) {
        Long id = 0L;
        // 从服务端获取自增型ID
        id = DistributedId.autoincrementId("sms");
        System.out.println(id);

        // 本地生成雪花算法ID
        id = DistributedId.snowflake();
        System.out.println(id);

        // 从服务端获取雪花算法ID
        id = DistributedId.snowflakeFromServer();
        System.out.println(id);

        // 段模式ID，bizType 区分业务系统
        id = DistributedId.segment("tms");
        System.out.println(id);
    }
}
```

bizType 传的是业务类型，一般对应系统名：这里一个用 sms，一个用 tms——不同系统、不同业务都来调这个服务，通过 bizType 区分各自的号段。执行 main，底层远程调用 server，控制台把几类 ID 都打印了出来：服务端自增 ID 是 62，本地雪花 ID 是 51520929715567616，服务端雪花 ID 是 51520929712365312，号段模式也返回了 Long 型的 ID。

作为使用方，整个过程就非常简单了：静态方法一调，ID 就回来了，远程调用、服务寻址全部被 client 封在里面。整体使用归纳下来就是三步——引坐标、写配置文件、调静态方法拿 ID。

## 小结

- 接入三步：client 装进本地仓库或公司私服 → 项目引 distributedid-client 坐标 → resources 根目录放 distributedid_client.properties，文件名与位置都不可改。
- 配置三个键：distributedid.server 指向 server 地址（集群逗号分隔）、readTimeout 与 connectTimeout 各 5000。
- DistributedId 的静态方法屏蔽了实现差异：autoincrementId 走服务端自增、snowflake 本地生成、snowflakeFromServer 走服务端雪花、segment 号段批量取；bizType 以业务类型（服务名）区分不同系统的号。
- 至此分布式 ID 服务闭环：server 只依赖 MySQL 独立发号，第三方系统三步接入、静态方法取号，全局唯一 ID 对业务方完全透明。
