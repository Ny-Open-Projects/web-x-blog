# 支付入口首次联调：网关路由、入口转发与确认页面渲染验证

页面文件、starter 依赖、Nacos 配置、视图控制器全部就位，接下来该让这条链路真正跑一次。按经验，第一次在浏览器里敲入口地址，结局往往是 404 或一张白页：请求可能根本没到交易服务，可能到了却转发失败，也可能模板找到了但配置没生效。确认页面测试要做的就是把「请求进来、页面出去」这条通路验证到位，网关路由是其中最容易漏的一环。

## 先给结论

- 测试必须走网关：生成二维码时入口前缀 `pay.payurl` 指向的就是网关地址，Nacos 网关配置里要补一条 `transaction-service` 的 `/transaction/**` 路由，缺了它请求进不了交易服务。
- 端口口径：网关 56010，交易服务 56050；入口完整地址形如 `http://127.0.0.1:56010/transaction/pay-entry/{ticket}`，前缀 `/transaction` 在网关被路由，剩余路径原样送到交易服务。
- 本课阶段 ticket 可以先随便填一段字符，验证目标是「入口能进、页面能渲染」，数据准备属于后续环节。
- 页面渲染成功但订单信息全部为空，是预期结果：`payEntry` 目前只做转发，还没解析 ticket。
- 排查按症状分流：404 查路由与服务名，模板渲染异常查后缀与目录，页面输出一串文本查 `@Controller` 注解。

## 路由先行：网关把请求送到交易服务

为什么测试要走网关而不是直连交易服务的 56050 端口？答案藏在生成二维码的环节里：入口 URL 的前缀来自配置项 `pay.payurl`，联调环境它指向网关地址，上线则换成公网域名，顾客手机扫到的 URL 从第一天起就是「域名加 `/transaction/pay-entry/` 加 ticket」的形态。测试如果直连服务端口，验证的就不是用户真实走过的路径，等价于没测。

网关本身不是本课开发的工程，但路由配置要看得懂、改得动。网关的路由规则放在 Nacos 的 `gateway-service.yaml` 里，已经为运营平台、商户平台应用、认证服务各配了一条，规则形态一致：以某个前缀打头的请求，转发给对应的服务。照着既有条目补一条交易服务的：

```yaml
#路由规则
zuul:
  retryable: true
  add-host-header: true
  ignoredServices: "*"
  sensitiveHeaders: "*"
  routes:
    operation-application:
      path: /operation/**
      stripPrefix: false
    merchant-application:
      path: /merchant/**
      stripPrefix: false
    uaa-service:
      path: /uaa/**
      stripPrefix: false
    transaction-service:
      path: /transaction/**
      stripPrefix: false
```

两个细节决定这条路由能不能生效。键名 `transaction-service` 是交易服务注册到 Nacos 的服务名，网关按它去注册中心找可用实例，服务名拼错路由就悬空。`stripPrefix: false` 表示转发时不剥离 `/transaction` 前缀，请求原样送达交易服务；交易服务的入口接口路径是 `/pay-entry/{ticket}`，网关侧多出来的 `/transaction` 前缀正好与入口前缀配置 `pay.payurl` 里的路径约定对齐，整条 URL 拼起来严丝合缝。

## 入口方法与 URL 的对应关系

入口接口骨架在上一课已经建立，把与测试相关的两个对应关系再钉一遍。第一个是路径对应：`@RequestMapping("/pay-entry/{ticket}")` 里的 `{ticket}` 接收的正是 URL 前缀之后挂的那一串编码；生成侧把 `PayOrderDTO` 的 JSON 编码成 ticket 拼在末尾，消费侧从路径里取出来，名字两端一致。第二个是注解对应：方法返回 `forward:/pay-page`，走视图控制器注册的 `/pay-page` 地址落到 `pay` 视图，也就是 `templates/pay.html`：

```java
@Slf4j
@Controller
public class PayController {

    /**
     * 支付入口
     * @param ticket 传入数据，对json数据进行的base64编码
     * @param request
     * @return
     */
    @RequestMapping("/pay-entry/{ticket}")
    public String payEntry(@PathVariable("ticket") String ticket, HttpServletRequest request) {
        //1、准备确认页面所需要的数据（解析ticket，后续环节实现）
        //2、解析客户端的类型（微信、支付宝），此处为后续环节预留
        return "forward:/pay-page";
    }
}
```

测试阶段随便编一段字符填在 ticket 位置也不会立刻出事，方法体还没有解析逻辑，进来就转发。这一点让本课的验证目标很纯粹：通路是否畅通。

## 浏览器验证：页面渲染出来了，数据是空的

改完路由先重启两个服务：网关要加载新路由，交易服务要加载新增的接口方法，少重启哪一个，验证结果都会误导人。然后访问入口地址，ticket 位置随手填一段占位字符，例如 `http://127.0.0.1:56010/transaction/pay-entry/test`。讲义里给的标准地址形态是 `http://127.0.0.1:56010/transaction/pay-entry/...`，省略号就是将来真实 ticket 的位置。

正式场景里用户是用手机扫码进来的，开发期用 Chrome 的手机视图模式预览：开发者工具切换到移动端模拟，页面按手机宽度呈现，效果与真机接近。渲染成功的页面应当出现：蓝色背景的头部区块、表单里的商品名称与订单描述回填框、付款金额输入框、一枚蓝色的「立即支付」按钮。

```mermaid
flowchart LR
    A["浏览器 手机视图"] -->|"GET /transaction/pay-entry/test"| B["网关 56010"]
    B -->|"路由 /transaction/** 不剥离前缀"| C["交易服务 56050"]
    C -->|"payEntry forward:/pay-page"| D["视图控制器 /pay-page"]
    D -->|"视图名 pay + 后缀 .html"| E["FreeMarker 渲染 pay.html"]
    E -->|"确认页面HTML"| A
```

这张图上每一跳都对应一个可能失败的配置点：浏览器到网关这一跳依赖路由存在，网关到交易服务这一跳依赖服务名与注册中心，交易服务内部两跳依赖视图控制器与 FreeMarker 配置。页面成功渲染，说明四个配置点全部就位。至于商品名称、订单描述为什么是空的，讲义里写得很直白：由于没有数据，订单信息均为空。入口还没有解析 ticket、准备页面需要的数据，这个「空」不是缺陷，是下一环节的施工面。

## 报错排查：按症状分流

404 出现时先怀疑路由。Nacos 里 `transaction-service` 条目加了没有，网关重启了没有，交易服务注册上来了没有，URL 里的 `/transaction` 拼写对不对，按这个顺序过一遍，绝大多数 404 停在第二项：改了路由忘了重启网关。

页面报 FreeMarker 渲染异常或者白页，问题在模板侧。`pay.html` 是不是真放在 `resources/templates` 下，`suffix: .html` 配置与文件后缀是否一致，`spring-boot-freemarker.yaml` 是否已在交易服务的 `bootstrap.yml` 的 `ext-config` 里引入。配置引入的核对方法很直接：启动日志会列出加载的配置 data-id，对着看。

浏览器显示一串 `forward:/pay-page` 文本而不是页面，是注解用错了：`@RestController` 把视图名当返回值写进了响应体，改回 `@Controller` 重启即可。数据为空不进排查清单，它不是错误，是尚未实现的功能，断点可以提前埋在 `payEntry` 方法入口，确认请求确实进来，为解析 ticket 的联调做准备。

## 常见误区

- **直连 56050 测试入口。** 错例：为了「排除变量」直接请求交易服务端口，页面通了就收工。正解：入口前缀配置指向网关，用户扫码走的永远是网关链路，测试路径必须与真实路径一致；直连能通只能说明服务活着，不能证明路由正确。
- **网关路由复制了条目，没改服务名或没重启。** 错例：从既有路由复制一段，键名没改或改了但网关未重启，请求 404。正解：路由键名就是 Nacos 服务名，逐字符核对；Nacos 配置变更后网关需要重启或确认热加载生效。
- **忽略 stripPrefix 的语义。** 错例：想当然设为 true，交易服务收到的请求少了 `/transaction` 前缀，接口路径对不上。正解：入口前缀配置里包含 `/transaction`，转发必须保留前缀，`stripPrefix: false` 与配置口径配套使用。
- **把「数据为空」当成渲染失败反复排查。** 错例：看到商品名称空白就回头查模板与配置。正解：先确认页面骨架、样式、按钮是否齐全，骨架齐全而数据为空属于数据准备未实现，等解析 ticket 环节自然解决。

## 面试可能被问到的问题

1. 面试官追问：「网关路由里的 stripPrefix 设为 false，依据是什么？」
   答：入口地址前缀配置为「网关地址加 `/transaction/pay-entry/`」，其中 `/transaction` 是网关识别路由的前缀，`/pay-entry/{ticket}` 才是交易服务里的真实路径。剥离前缀的话请求到达服务时路径对不上接口映射，所以保留前缀原样转发，让服务侧路径与配置口径完整对齐。
2. 面试官追问：「为什么入口 URL 要经过网关，交易服务直接暴露给用户不行吗？」
   答：网关是系统的统一出入口，承担路由、鉴权、限流、日志等横切职责，交易服务作为内网服务不应对公网暴露。二维码上的域名指向网关，配合路由前缀把流量分发到具体服务，服务扩缩容、迁移对用户完全透明，安全策略也集中在一处实施。
3. 面试官追问：「测试时 ticket 随便填一段字符，为什么页面还能正常渲染？」
   答：此刻入口方法体只做 forward 转发，没有对 ticket 做任何解析，路径参数只是被接收而没有被消费，所以任意字符串都不影响渲染。等解析逻辑加入后，非法 ticket 会在 Base64 解码或 JSON 反序列化时失败，入口要有对应的异常处理把用户引向错误页，而不是抛 500。
4. 面试官追问：「确认页面测试通过的标准是什么？」
   答：三层递进。请求层面，网关路由把入口请求正确送达交易服务；渲染层面，FreeMarker 把 pay.html 渲染成完整 HTML，骨架、样式、按钮齐全；预留层面，订单数据为空且原因明确是入口尚未准备数据。前两层证明配置链路无错，第三层为下一环节划定了施工范围。
