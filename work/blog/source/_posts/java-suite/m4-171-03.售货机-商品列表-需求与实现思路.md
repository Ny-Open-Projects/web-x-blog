# 小程序售货机商品列表与详情：需求思路、v1.0 实现与四轮代码优化

立可得第五章「订单支付与出货控制」从小程序端售货机商品查询开篇，包含商品列表和商品详情两个功能。用户拿手机扫售货机上的二维码，打开微信小程序，第一个界面就是商品列表，点击商品图片再进入详情页。这个需求看起来平常，立可得 1.0 的实现里却叠着货道去重、真实价格计算两层逻辑，还留下了一个典型的 N+1 查询性能问题。这篇按课程顺序走完：需求思路、v1.0 代码解析、四轮优化，最后是商品详情的实现与优化。

## 先给结论

- 扫码的本质是传售货机编号：小程序微服务在 VMController 里提供 /v1/skuList 和 /v1/skuDetail 两个接口，自己几乎不写业务逻辑，靠 Feign 远程调用售货机微服务封装好的查询方法。
- 列表不能直接查商品表：售货机编号对应的是货道，多个货道可能放同一个商品，必须按商品去重并把各货道库存累加；返回的价格也不是商品原价，而是货道上按折扣策略算出的真实售价。
- v1.0 的实现结果正确但效率低下：循环货道逐个调用 channelService.getRealPrice 查库，50 个货道就是 1+50=51 次数据库访问。
- 优化砍两刀：库存用 Collectors.groupingBy 加 summingInt 分组聚合；真实价格用 summarizingInt 一次性统计出求和、平均、计数、最大最小值再取最小值。整个方法只剩一次数据库查询，其余全在内存完成，效率高出几十倍。
- 联调排错很典型：vm.http 直连 9004 端口测出库存全为 0，断点排查发现 return 转换时漏了把聚合结果赋给返回对象（setCapacity(entry.getValue())），补上即恢复正常。
- 商品详情的 v1.0 写法（新增 SkuInfoViewModel 和详情接口）其实没必要：商品信息列表接口已经带回，设备编号扫码就知道，只需一个按编号查售货机的接口，在扫码拿列表时顺带把设备地址存到本地。

## 需求与实现思路：从扫码到列表的三步链路

需求本身不复杂：用户扫售货机上的二维码，小程序展示商品列表，每个商品有图片、名称、价格（比如可口可乐 ¥6.50、康师傅 ¥6.30）。关键在于二维码里最核心的信息是售货机编号，后续所有查询都从它出发。

课程文档把实现思路拆成三步：

1. 用户扫码后，小程序端把售货机编号传给后端接口；
2. 后端通过 Feign 调用售货机服务的商品列表接口；
3. 售货机服务封装方法，实现根据售货机编号查询商品列表。

落到代码上有两个位置。一是服务公共模块 service_common，里面定义了视图模型 SkuViewModel，也就是列表里每个元素的载体；二是小程序微服务的 VMController，提供列表和详情两个 REST 接口：

```java
@RestController
@RequestMapping("/v1")
public class VMController {

    // 商品列表：入参是售货机编号
    @GetMapping("/skuList")
    public List<SkuViewModel> skuList(String innerCode) {
        return vmService.getSkuList(innerCode);   // VMService 是 Feign 接口
    }
}
```

小程序微服务的定位值得留意：它专门给小程序端提供后端接口，但很少自己写逻辑，真实业务都在售货机微服务里封装好，由 Feign 接口 VMService 远程调用——访问的就是售货机微服务的 /skuList 地址，并带上售货机编号。

## v1.0 实现：一个「简单」列表背后的两层逻辑

先看 SkuViewModel 的字段定义：skuId 商品ID、skuName 商品名称、classId 类别、price 原价、realPrice 真实售价、capacity 货道余量、image 商品图片、unit 净含量、discount 是否打折。其中最核心的是商品ID、名称、真实售价、余量和图片这几项，前端列表全靠它们渲染。

需求看着简单，v1.0 的实现却不短，原因是两层逻辑绕不开：

1. **去重与库存累加**。系统拿到的是售货机编号，查到的是货道（th_channel 表，带 sku_id、current_capacity 和价格字段）。一台售货机的多个货道可能放同一个商品——五个货道都是冰红茶，页面总不能显示五条，所以要去重；去掉重复后，库存又必须是所有货道的余量之和。
2. **真实价格**。商品表里存的是原价，而实际售卖价格来自货道：给售货机应用打折策略（比如打九折）时，折扣是在原价基础上算到货道价格上的，所以列表要返回的是货道上的真实售价，可能与原价不同。

v1.0 的 getSkuList 方法按这个套路展开。

第一段，查货道列表并用 Stream 过滤掉没装商品的货道：

```java
List<ChannelEntity> channelList = this.getAllChannel(innerCode)
        .stream()
        .filter(c -> c.getSkuId() > 0 && c.getSku() != null)  // skuId 为 0 是空货道
        .collect(Collectors.toList());
```

第二段，循环货道完成去重、库存累加和真实价格查询：

```java
Map<Long, SkuEntity> skuMap = Maps.newHashMap();
channelList.forEach(c -> {
    SkuEntity sku = c.getSku();
    // 查货道上的真实售价（内部是一次数据库查询）
    sku.setRealPrice(channelService.getRealPrice(innerCode, c.getSkuId()));
    if (!skuMap.containsKey(sku.getSkuId())) {
        // 第一次遇到该商品：当前货道的余量就是它的库存
        sku.setCapacity(c.getCurrentCapacity());
        skuMap.put(sku.getSkuId(), sku);
    } else {
        // 再次遇到：库存累加
        SkuEntity value = skuMap.get(sku.getSkuId());
        value.setCapacity(value.getCapacity() + c.getCurrentCapacity());
        skuMap.put(sku.getSkuId(), value);
    }
});
```

第三段，把 Map 转成返回的 List：先 values().stream()，map 转换成 SkuViewModel，再按货道余量降序排序（comparing(SkuViewModel::getCapacity).reversed()），保证库存最多的商品排在上面，卖空的沉底。

## 四轮优化：从 51 次查询到 1 次

第一轮是定位问题。v1.0 返回的结果没有错，但执行效率低：问题出在循环里调用 getRealPrice——它内部是一次数据库查询。50 个货道就是 50 次循环调用，加上开头那次货道列表查询，一共 51 次数据库访问，过于频繁；后面的 Map 转 List 虽然也在循环，但都在内存里，效率没问题。所以目标明确：重写方法，把数据库交互压到最低。

第二轮改写库存聚合。方法第一句「按售货机编号查货道列表」保留，之后不再访问数据库。库存余量不用再写循环判断，直接用 Stream 的分组聚合：

```java
// 相当于 SQL 里的 SUM：按商品分组，对 currentCapacity 求和
Map<SkuEntity, Integer> skuMap = channelList.stream().collect(
        Collectors.groupingBy(ChannelEntity::getSku,
                Collectors.summingInt(ChannelEntity::getCurrentCapacity)));
```

groupingBy 的第一个参数指定按什么分组（结果的 key），第二个参数指定对哪个字段做什么聚合运算；求和有 summingInt、summingLong、summingDouble 三兄弟，按数据类型选用。Map 转回 List 时用 entrySet().stream()——因为键和值都要用，entry.getKey() 拿商品，new 一个 SkuViewModel 后 BeanUtils.copyProperties 拷贝属性；图片字段两边名字不同，需要单独 setImage 补一刀；排序那行从原方法照搬即可。

第三轮把真实价格也搬进内存。如果照抄 v1.0，在聚合之后再调 channelService.getRealPrice(innerCode, skuId)，50 个货道装 10 种商品时调用次数从 50 降到 10，已经优化不少——但依然是 10 次数据库交互。课程的做法是再建一张「价格表」：

```java
// summarizingInt 一次统计出：求和、平均、计数、最大值、最小值
Map<Long, IntSummaryStatistics> skuPrice = channelList.stream().collect(
        Collectors.groupingBy(ChannelEntity::getSkuId,
                Collectors.summarizingInt(ChannelEntity::getPrice)));
```

key 换成商品ID就够用了（其他商品属性已经从 skuMap 拿到）。使用时 skuPrice.get(sku.getSkuId()).getMin() 取最小值——取最大值或平均值也一样，因为同一台售货机上同一商品在不同货道的价格理论上必须一致，如果不一致，说明是别的程序出了 bug 把数据弄乱了。

| 版本 | 数据库访问次数 | 核心实现 | 结论 |
| --- | --- | --- | --- |
| v1.0 | 1 + 货道数 | forEach 循环逐货道查真实价格，手工 Map 去重累加 | 结果正确，50 个货道要 51 次查询 |
| 库存聚合改写 | 1 + 商品种类 | groupingBy + summingInt 聚合库存，价格仍走 channelService | 调用次数从「货道数」降到「商品数」，仍有数据库交互 |
| 最终版 | 1 | summarizingInt 聚合价格统计，全程 Stream 内存运算 | 一次查询，效率高出几十倍 |

第四轮是测试与排错。启动售货机微服务（9004 端口），打开它的测试脚本 vm.http——脚本端口和微服务一致，不需要启动网关，直接测微服务地址。找到「获取售货机商品列表」，传售货机编号 01000002，列表出来了，但商品的库存全是 0。查数据库里 01000002 的货道数据，余量并不是 0，说明逻辑有问题。

在 return 处打断点、debug 重启再测：channelList 数据正确；skuMap 的 key 是商品、value 是聚合库存，value 有值——库存聚合这步没问题。问题就出在 return 的转换里：少了最关键的一句，把聚合结果赋给返回对象。补上 entry.getValue()：

```java
return skuMap.entrySet().stream().map(entry -> {
    SkuEntity sku = entry.getKey();
    sku.setRealPrice(skuPrice.get(sku.getSkuId()).getMin());  // 真实价格取自内存统计
    SkuViewModel skuViewModel = new SkuViewModel();
    BeanUtils.copyProperties(sku, skuViewModel);
    skuViewModel.setImage(sku.getImage());        // 图片字段名不同，单独赋值
    skuViewModel.setCapacity(entry.getValue());   // 聚合后的库存余量，漏了这句库存就是 0
    return skuViewModel;
}).sorted(Comparator.comparing(SkuViewModel::getCapacity).reversed())
  .collect(Collectors.toList());
```

再次启动测试，库存数据正常，与数据库货道余量逐项核对无误，商品列表的优化收工。

## 商品详情：v1.0 的写法与更彻底的优化

商品详情页在列表之后，点击某个商品图片进入，展示商品图片、名称、规格、价格，外加设备编号和设备地址。v1.0 在 service_common 里定义了 SkuInfoViewModel——继承 SkuViewModel 并实现 Serializable，只扩展两个属性：点位地址和设备编号。理由很直接：列表模型里已有的属性不用重复定义，继承再扩展，正好就是详情页需要的返回模型。

VMController 里对应新增了 getSku 方法，接收售货机编号和商品ID，逻辑四步：

1. 按售货机编号和商品编号查出列表同款 SkuViewModel，此时还没有设备信息；
2. 实例化 SkuInfoViewModel，用 BeanUtils.copyProperties 把商品属性全部拷过来；
3. vmService.getVMInfo(innerCode) 查询设备，返回售货机对象；
4. 对象不为 null 时，把设备地址和售货机编号赋给 SkuInfoViewModel，返回。

先查商品、再查设备，整合成一个对象返回——这个写法能用，但课程的结论是：新增的模型对象和方法完全没必要。

- 商品信息不用再查：详情页的商品部分，列表接口已经全部返回过，前端直接用列表数据即可；
- 设备编号不用查：扫码那一刻就知道；
- 设备地址只需查一次：在扫码获取商品列表的同时，顺带调一个设备信息接口把地址拿下来存到本地，点进商品图片时直接显示。

两种方式的体验差别很大：每次点图片都回后端查一遍，后端凭空多出一类压力，前端也要等一次服务端交互才能渲染，多少有延迟；地址在本地时页面即点即开，流畅得多。优化后的接口只剩一个按编号查设备的方法：

```java
// 扫码拿列表时顺带调用一次，把设备地址存到本地
@GetMapping("/innerCode/{innerCode}")
public VendingMachineEntity getVM(String innerCode) {
    return vmService.getVMInfo(innerCode);
}
```

## 小结

商品列表这个「查询需求」的真实施工面远比想象大：链路上小程序微服务只做接口转发，业务收敛在售货机微服务；数据层要处理货道到商品的去重、库存累加和折扣价格三件事。v1.0 用最直观的循环写法把功能做对了，也把 N+1 查询的坑留在了里面——四轮优化把它压到一次数据库访问，剩下的全是 Stream 内存运算，顺带在联调里修了一个聚合结果没赋值的隐蔽 bug。商品详情则反着来：不是急着「后端再提供一个接口」，而是审视哪些信息已经在手上，把一次本可避免的交互直接砍掉。功能写对、写得高效、写得省，是三层不同的功力。
