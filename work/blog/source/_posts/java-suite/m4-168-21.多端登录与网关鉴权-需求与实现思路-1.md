# 立可得2.0多端登录与网关鉴权：一个入口三种登录，附MinIO对象存储落地

立可得2.0冒出了多个端：运营后台、合作商后台、运营运维APP，加上面向C端的用户小程序，登录与鉴权必须重新设计。这篇讲清三端如何用"一个登录入口+一个网关"整合起来，JWT怎么签发和校验，最后把替代阿里云OSS的MinIO讲透：S3概念、部署到上传代码四步。

## 先给结论

- 三端登录方式各不相同：管理员是账号+密码+图形验证码；合作商是手机号+预设密码+图形验证码；运营运维APP是手机号+短信验证码。
- B端三端采用整合模式：一个登录接口靠loginType（0管理员/1运营运维/2合作商）分发，一个网关统一鉴权；隔离模式代码量大但安全性稍好，权衡后选整合。
- 图形验证码用Kaptcha生成：一行产出四位随机文本，按文本出图，文本以客户端token为key存Redis，120秒过期。
- 三种登录最终都走okResp收口：TokenObject携带userId、mobile、loginType，JWT密钥=手机号+固定串，签发与校验同一套逻辑。
- 网关JwtTokenFilter实现GlobalFilter：先放行免鉴权路径，再校验Authorization头中的JWT，失败统一返回401。
- MinIO兼容S3标准，替换OSS核心是省钱；docker-compose一条命令起服务，FileManager封装PutObjectArgs完成上传，返回"外网地址/桶名/文件名"。

## 多端登录的需求与两种方案

先把端的账数清楚：运营后台一端、合作商后台一端、运营APP和运维APP合算一端，共三端；用户小程序面向C端，先不考虑。前三端都是B端企业用户，问题收敛为：这三端登录怎么做。

三端的登录风格并不一致：

| 端 | 登录要素 | 验证码 |
| :--- | :--- | :--- |
| 运营后台（管理员） | 账号 + 密码 | 图形验证码（四位数字或字母组合，带干扰点线） |
| 合作商后台 | 手机号作账号 + 预设密码 | 图形验证码 |
| 运营运维APP | 选择运营或运维 + 手机号 | 短信验证码，回填后登录 |

方案上有两种。隔离模式：不同端开放不同登录入口，三类用户各写一个登录接口，网关也做三个。整合模式：三端同属B端，登录方式有差异但可做兼容——登录入口整合成一个，前端多传一个登录类型值区分，后端按类型走不同校验逻辑；网关也只建一个，鉴权用相同部分完成。

| 方案 | 接口与网关数量 | 代码量 | 安全性 |
| :--- | :--- | :--- | :--- |
| 隔离模式 | 3个登录接口 + 3个网关 | 大 | 相对好一点 |
| 整合模式 | 1个登录接口 + 1个网关 | 少很多 | 稍逊色，可后期整合第三方权限中台弥补 |

课程采用第二种——整合模式，代码量优势明显，安全短板有补救路径。

## 一个登录入口，三种登录实现

### 图形验证码：Kaptcha四步出图

管理员登录运营后台、合作商登录合作商后台都要用图形验证码，作用是防暴力破解。原始实现是random生成随机数字字母、调原生图像绘制库画图、额外加点线干扰符号，繁琐且代码量偏多。这里改用Kaptcha：依赖加进pom，代码几行搞定。

用户微服务的UserController提供生成方法，映射路径/user，实现流程如下：

```java
@GetMapping("/imageCode/{clientToken}")
public void getImageCode(HttpServletResponse httpServletResponse,
        @PathVariable String clientToken) throws IOException {
    String createText = kaptcha.createText();               // 四位随机字母+数字
    BufferedImage challenge = kaptcha.createImage(createText); // 按文本构建图片
    ImageIO.write(challenge, "jpg", httpServletResponse.getOutputStream());
    httpServletResponse.setContentType("image/jpeg");
    httpServletResponse.flushBuffer();
    // 验证码文本存Redis：key是前端生成的客户端token，120秒过期
    redisTemplate.boundValueOps(clientToken).set(createText, 120, TimeUnit.SECONDS);
}
```

clientToken是前端生成的token，用来识别每一个客户端，随请求路径传过来，作为Redis的key；文本存Redis是供登录时取出比对。启动用户微服务（端口9006），浏览器访问`http://127.0.0.1:9006/user/imageCode/abc`（token随便写）就能看到验证码图片，地址本身就是图片，前端直接当img标签的src，刷新一次生成不一样的值。

### LoginReq与LoginResp：一套对象兼容三端

登录逻辑封装在用户微服务里，靠两个对象打通三端。

请求对象LoginReq：loginName（登录名）、password（密码）、mobile（手机号）、code（验证码）、clientToken（客户端token）、loginType（登录类型）。loginType是Int值，0代表运营后台（管理员），1代表运营运维客户端，2代表合作商后台。这个对象兼容三种登录：管理员用loginName+password，合作商用mobile+password，运营运维用mobile+code。

响应对象LoginResp：success（是否成功）、msg（失败原因）、userId、userName、角色编码、regionId（人员所属区域ID）、是否运维人员布尔值（true运维、false运营），以及最重要的token——后端签发的JWT令牌，前端保存起来，下次访问其他接口时带在请求头里。

### 主入口分发与三种校验

UserService的login方法接收LoginReq、返回LoginResp，按loginType分发：

```java
@Override
public LoginResp login(LoginReq req) throws IOException {
    if (req.getLoginType() == VMSYSTEM.LOGIN_ADMIN) {
        return this.adminLogin(req);          // 管理员
    } else if (req.getLoginType() == VMSYSTEM.LOGIN_EMP) {
        return this.empLogin(req);            // 运营运维
    } else if (req.getLoginType() == VMSYSTEM.LOGIN_PARTNER) {
        return this.partnerService.login(req); // 合作商
    }
    return null; // 类型不对，直接返回不成功
}
```

adminLogin校验链条：先用clientToken从Redis取验证码文本，为空或与输入不一致都返回"验证码错误"；再QueryWrapper按loginName查账号，查不到返回"用户名或密码错误"；密码用`BCrypt.checkpw(req.getPassword(), userEntity.getPassword())`比对，不匹配同样报"用户名或密码错误"；通过就调okResp收口。

empLogin给运营运维用：手机号+短信验证码登录，验证码发送时就以手机号为key存进Redis，校验时用mobile取出比对，不一致返回"验证码错误"；再按手机号查唯一用户，查不到提示"不存在该账户"；通过后同样签发token。合作商登录是手机号+图形验证码，放在PartnerService的login里实现：以clientToken取图形验证码校验，按账号查合作商，BCrypt校验密码，错误提示与前两类一致。

### okResp：JWT签发的统一收口

三种登录校验通过后，都走到okResp这个私有方法，传入用户实体与登录类型，返回成功对象并签发令牌：

```java
private LoginResp okResp(UserEntity userEntity, Integer loginType) throws IOException {
    LoginResp resp = new LoginResp();
    resp.setSuccess(true);
    resp.setLoginCode(userEntity.getLoginCode());
    resp.setUserName(userEntity.getUserName());
    resp.setUserId(userEntity.getId());
    resp.setRegionId(userEntity.getRegionId());
    resp.setMsg("登录成功");

    TokenObject tokenObject = new TokenObject();
    tokenObject.setUserId(userEntity.getId());
    tokenObject.setMobile(userEntity.getMobile());
    tokenObject.setLoginType(loginType);
    String token = JWTUtil.createJWT(tokenObject,
            userEntity.getMobile() + VMSYSTEM.JWT_SECRET);
    resp.setToken(token);
    return resp;
}
```

TokenObject是自定义类，令牌携带的对象，封装用户ID、手机号、登录类型。签发密钥是"手机号+固定密钥串"的组合，签发与校验按相同逻辑进行。只用固定串行不行？可以，但安全性不好——密钥串一旦泄漏，被破解风险很高；加上手机号后破解难度变高，相对更安全。

## 接口测试与网关统一鉴权

### 用REST Client测登录

前后端分离模式下，逻辑写完先测接口。常用工具是Postman，这里用VS Code的REST Client插件：.http脚本文件里每一块对应一个接口，块上有注释，接口上方点send request就发送请求。脚本顶部用@定义变量，如hostname等于127.0.0.1，引用时写{{hostname}}——换地址只改一处，比把IP写死在每个接口里方便。token也定义成变量，放Authorization请求头带过去，模拟前端携带令牌。

注意端口：用户微服务跑在9006，脚本里的9007是网关端口——脚本测的是带网关的地址，路径要多带user-service这一级；直连微服务测，端口后面直接就是接口路径，不用带。

管理员登录测试流程：跑起用户微服务和网关，loginType填0，账号admin、密码admin（数据库真实存在）。第一次点send request返回"验证码错误"——脚本里验证码是随便写的；浏览器访问`127.0.0.1:9006/user/imageCode/abc`拿真实验证码（已存Redis，两分钟内有效），把看到的值填进脚本再测，登录成功，响应带token。复制token（不带引号）替换脚本变量，测其他接口直接用；token过期就重新登录拿新值覆盖。密码随便写再测，返回"账户名或密码错误"，链路验证完毕。

### 网关JwtTokenFilter：统一校验JWT

不管哪种登录，最终都返回前端一个JWT令牌。前端再访问服务器资源时要在请求头里携带令牌：不带就拦截，带了就校验，保障后端微服务资源地址安全。校验由Gateway网关统一实现——前端访问微服务都走网关。工程里有两个网关：一个服务管理员、运营运维、合作商，另一个针对小程序。前者里的JwtTokenFilter过滤器，所有通过网关的访问都经过它：

```java
@Component
public class JwtTokenFilter implements GlobalFilter, Ordered {

    @Autowired
    private GatewayConfig gatewayConfig;

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String url = exchange.getRequest().getURI().getPath();
        // 放行不需要鉴权的路径：图形验证码（还没登录）、登录接口本身等
        boolean matchUrl = Arrays.stream(gatewayConfig.getUrls()).anyMatch(url::contains);
        if (matchUrl) {
            return chain.filter(exchange);
        }

        String token = exchange.getRequest().getHeaders().getFirst("Authorization");
        ServerHttpResponse resp = exchange.getResponse();
        if (Strings.isNullOrBlank(token)) return authError(resp);

        try {
            TokenObject tokenObject = JWTUtil.decode(token);
            JWTUtil.VerifyResult verifyResult = JWTUtil.verifyJwt(token,
                    tokenObject.getMobile() + VMSYSTEM.JWT_SECRET);
            if (!verifyResult.isValid()) return authError(resp);
        } catch (Exception e) {
            return authError(resp);
        }
        return chain.filter(exchange); // 校验通过，转发给对应微服务
    }

    @Override
    public int getOrder() { return -188; }

    private Mono<Void> authError(ServerHttpResponse resp) {
        resp.setStatusCode(HttpStatus.UNAUTHORIZED);
        resp.getHeaders().add("Content-Type", "application/json;charset=UTF-8");
        String returnStr = "token验证失败";
        DataBuffer buffer = resp.bufferFactory().wrap(returnStr.getBytes(StandardCharsets.UTF_8));
        return resp.writeWith(Flux.just(buffer));
    }
}
```

逻辑串起来：先取请求URL，命中GatewayConfig配置的免鉴权路径直接放行（典型如图形验证码地址——此时还没登录，以及登录接口本身）；再取请求头Authorization，为空直接authError返回401；非空则JWTUtil.decode解出令牌携带的TokenObject，取手机号，按相同的"手机号+固定密钥串"规则verifyJwt校验，失败或抛异常都返回401；通过才放行转发。authError设置状态码401（HTTP标准的UNAUTHORIZED），响应类型application/json，输出"token验证失败"。getOrder返回-188，值越小优先级越高。

测试同样用REST Client脚本：跑起用户微服务和网关，测人员搜索接口，带正确token能查出结果；token改坏（前面加个1），返回token校验失败、状态码401；不带token同样失败。token过期时重新登录，新token覆盖到脚本变量即可。

## MinIO对象存储：开箱与上传

### S3标准与MinIO特点

对象存储服务通俗讲就是文件存储，图片、视频等文件都可以放进去。1.0用阿里云OSS存商品图片，2.0换MinIO，原因很简单：省钱。OSS是云服务，费用随占用空间和流量增长；MinIO自己搭建，相当于私服，适合存图片、视频、日志、备份、容器/虚拟机镜像这类非结构化数据。

MinIO兼容亚马逊S3云存储服务接口。S3是一套文件存储标准（Simple Storage Service，简单存储服务，名称由三个S开头单词组成），阿里云OSS、七牛云、百度云等平台的对象存储都兼容S3标准。S3的三个基本概念：

- Bucket（桶）：相当于文件系统中的目录，用来区分资源，比如不同应用各放一个桶；
- Object（对象）：相当于文件系统中的文件，一张图片存进去就是一个对象；
- Key：类比文件名。

定位服务器上的资源，指定bucket和key即可；对象大小任意，小到几KB、大到5TB。

MinIO的特点：数据保护用纠删码（Erasure Code）防硬件故障，磁盘损坏一部分也能恢复数据，原理类似二维码缺一角照样扫出来；高性能，标准硬件下读写速率可达55GB/s和35GB/s；可扩容，能搭集群，不同集群还能组成联邦形成全局命名空间，跨数据中心；SDK支持Java、Python、Go等语言；自带友好Web界面，易上手；设计原则"不容易错、更快启动"；API丰富，覆盖文件分享链接（含过期策略）、桶操作、文件列表、上传下载；文件变化可主动通知，上传、删除等事件通过AMQP、MQTT、Elasticsearch、Redis、NATS、MySQL、Kafka、Webhooks等发布出去。

### 部署与管理控制台

课程VM镜像里已装好MinIO且自动启动，直接用；要在空白服务器上装，推荐Docker Compose，创建docker-compose.yml：

```yaml
version: "3"
services:
  minio:
    image: minio/minio:RELEASE.2020-08-26T00-00-49Z
    container_name: minio
    privileged: true
    volumes:
      - /root/common/data/minio/data:/data
    ports:
      - "9001:9000"
    environment:
      MINIO_ACCESS_KEY: minio
      MINIO_SECRET_KEY: minio123
    command: server /data
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9000/minio/health/live"]
      interval: 30s
      timeout: 20s
      retries: 3
```

关键配置：目录映射把数据落到宿主机/root/common/data/minio/data；端口把容器内9000映射成宿主机9001访问；MINIO_ACCESS_KEY和MINIO_SECRET_KEY相当于账号密码，访问这套MinIO全靠这两个参数；command指定启动运行server /data；最后是健康检查。文件所在目录执行`docker-compose up`，无镜像会自动下载、创建容器并启动。

浏览器打开`http://192.168.200.128:9001`进管理控制台，用Access Key minio、Secret Key minio123登录。主界面清爽，刚部署是空白的。点加号有上传文件、创建桶两个按钮。先创建叫"立可得"的桶，再传图片；文件上点三个点可做分享（生成带过期时间的链接）、查看、下载、删除。控制台日常主要用来查看桶里内容，上传走代码。

### 上传代码：四步落地

以售货机微服务（lkd_vms_service）为例，MinIO文件上传四步完成。

第一步，pom引入minio依赖：

```xml
<dependency>
    <groupId>io.minio</groupId>
    <artifactId>minio</artifactId>
    <version>7.1.0</version>
</dependency>
```

第二步，配置文件定义五项配置：账号accessKey、密码secretKey、桶名称bucket、入口地址endpoint（服务具体地址）、外网可访问的根地址readPath。目前两个地址设成一样，生产环境不一样——readPath是外网域名，endpoint是内网可达的IP。

第三步，写配置类读取五项信息：

```java
@Configuration
@ConfigurationProperties("minio")
@Data
public class MinioConfig {
    private String accessKey;
    private String secretKey;
    private String bucket;
    private String endpoint;
    private String readPath;
}
```

第四步，最关键的文件上传管理类FileManager封装上传逻辑。先注入配置类，私有方法buildMinioClient创建连接：`MinioClient.builder()`构建器，credentials传账号密码做身份认证，endpoint指定入口地址，build返回——这套API大量用Builder风格。上传方法：

```java
public String uploadFile(MultipartFile file) {
    try {
        MinioClient minioClient = buildMinioClient();
        // PutObjectArgs封装上传文件信息；第三个参数-1表示整体上传，大于0为分片上传
        PutObjectArgs putObjectArgs = PutObjectArgs.builder()
                .object(file.getOriginalFilename())
                .contentType(file.getContentType())
                .stream(file.getInputStream(), file.getSize(), -1)
                .bucket(minioConfig.getBucket())
                .build();
        minioClient.putObject(putObjectArgs);

        StringBuilder sbPhotoPath = new StringBuilder(minioConfig.getReadPath());
        sbPhotoPath.append("/").append(minioConfig.getBucket())
                   .append("/").append(file.getOriginalFilename());
        return sbPhotoPath.toString();
    } catch (Exception ex) {
        log.error("minio put file error.", ex);
        throw new LogicException("上传文件失败");
    }
}
```

PutObjectArgs封装上传文件信息：object指定上传后的文件名，取原始文件名；contentType是文件类型；stream传输入流、文件大小和分片参数；bucket从配置类读取。putObject执行上传。返回值做路径拼接：readPath、斜杠、桶名、原始文件名——这套代码上传后保留原始文件名，业务上也可重新定义。异常时记日志并抛出"上传文件失败"。

最后一步，Controller注入FileManager调用即可：

```java
@PostMapping("/fileupload")
public String uploadSkuImage(@RequestParam("fileName") MultipartFile file) {
    return fileManager.uploadFile(file);
}
```

传参依然是MultipartFile，但前面要加@RequestParam注解并指定名字，名字可自定义（不一定是fileName），上传测试时表单字段名要和它一致。

## 小结

多端登录的解法是"整合"两个字：一套LoginReq/LoginResp对象靠loginType兼容三种登录，校验链条各自不同但都在okResp收口签发JWT，密钥用"手机号+固定串"提高破解难度。鉴权收敛到网关JwtTokenFilter：免鉴权路径放行，Authorization头里的JWT按相同密钥规则校验，失败统一401。测试用VS Code的REST Client加.http脚本，变量化管理地址与token。存储侧，MinIO以S3兼容、纠删码、联邦扩容和主动通知替换OSS，docker-compose开箱即用，FileManager四步完成上传。登录、鉴权、文件上传三块基建就位，业务开发有了底座。
