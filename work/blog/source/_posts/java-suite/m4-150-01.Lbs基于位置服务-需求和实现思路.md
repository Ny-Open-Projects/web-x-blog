# LBS 基于位置服务：需求分析与附近售货机搜索的完整落地

从这一篇开始进入立可得项目的新篇章——LBS 与选品。立可得是一个物联网新零售项目，2.0 版本新增了「搜索附近售货机」功能：用户不在售货机旁边时，打开小程序就能查到附近的设备在哪、离自己多远，再一键唤起地图导航过去。本篇覆盖这条链路的全部内容：LBS 概念与需求分析、技术选型、ES 索引库创建、设备坐标保存，以及附近售货机搜索的实现与测试。

## 先给结论

- LBS（Location Based Service，基于位置的服务）= 利用设备定位技术采集当前位置，再通过移动互联网共享定位信息；打车软件里实时看车距、交友软件搜附近的人，都是它的典型应用。
- 「搜索附近售货机」是新零售「线上向线下导流」的具体落地：小程序是线上入口，把用户引到线下的售货机消费，直接有助于订单量增长。
- 技术方案主流两种：Redis GEO 和 Elasticsearch GEO。定位信息经常变化、需要实时查看的场景选 Redis（内存操作快）；位置基本不变的场景选 ES。售货机投放后不会来回动，所以立可得选 Elasticsearch。
- 数据侧的关键点：索引 vm 的 location 字段必须是 geo_point 类型，存普通字符串是无法做地理位置搜索的；其余字段用 keyword 就够了。
- 写入链路：投放工单完成时前端采集经纬度 → 工单完成消息触发售货机微服务 → 先查库补全点位信息 → 写入 ES（id 为售货机编号）→ 数据库再存一份副本。
- 查询链路：GeoDistanceQueryBuilder 指定圆心和半径，GeoDistanceSortBuilder 按距离升序排序，结果转成 VmInfoDTO；设备到用户的直线距离不在结果字段里，要从排序值 sortValues 里取。

## 需求分析：把「附近的售货机」说清楚

先解释概念。LBS 是一组英文单词的缩写：Location Based Service，翻译过来就是基于位置的服务。它的定义是：利用设备的定位技术采集当前设备的位置，然后通过移动互联网来共享这个定位信息。听起来抽象，例子很直观——打车软件里，你叫到车之后能实时看到车的位置、距离你多远、预计几分钟到；司机端同样能拿到你的位置，根据导航找到你。交友软件里的「搜索附近的人」也是同一个思路。

立可得 2.0 要做的事情类似：搜索附近售货机。具体场景是——用户身边没有售货机，口渴了想喝饮料，周边又没有超市，这时想起立可得，打开小程序搜索一下，就能看到一个附近售货机的列表，每台设备在什么位置、距离多远一目了然；如果想去现场买，点「去这里」按钮会唤起本地地图导航，跟着导航走到设备跟前就行。

这个功能恰好验证了第一天讲的新零售特点：线上向线下导流。立可得小程序本身是一个线上应用，通过它把用户引到线下的售货机完成消费，对系统订单量的增长是实打实的帮助。

如何实现地理位置的搜索？主流技术方案有两种：

1. **Redis GEO**：适合定位信息经常变化、需要实时刷新查看的场景，Redis 在内存中操作，速度占优。
2. **Elasticsearch GEO**：适合定位信息基本不变的场景。

售货机是不会来回动的，所以采用 Elasticsearch 方案更合适。

实现步骤也就两步。第一步，定位采集——要做搜索之前肯定得先有数据，这是前提：完成投放工单的时候，由前端负责采集设备的位置信息，发给售货机微服务，售货机微服务把它存进 ES。注意这里的「存」不是按普通字符串存，而是有专门的定位类型，只有存成定位类型，后面才能做搜索。第二步，利用 ES 的 GEO 搜索功能实现附近售货机搜索。

## 先建索引库：geo_point 是地理搜索的前提

写代码之前先定数据结构。索引库需要存储售货机编号、售货机类型（饮料机、口红机还是综合机）、点位名称、地址，以及最重要的经纬度信息（设备的定位数据）——前面几项都要在搜索结果界面上展示出来。

在 Kibana 中执行建库语句，索引库名称叫 vm：

```json
PUT /vm
{
  "mappings": {
    "properties": {
      "location": {
        "type": "geo_point"
      },
      "innerCode": {
        "type": "keyword"
      },
      "addr": {
        "type": "keyword"
      },
      "nodeName": {
        "type": "keyword"
      },
      "typeName": {
        "type": "keyword"
      }
    }
  }
}
```

这里有个必须划重点的地方：除了经纬度之外，其他字段用 keyword 类型就可以；但经纬度字段 location 必须用特殊类型 geo_point——它就是坐标类型。只有存储类型是坐标信息，之后才能进行地理位置搜索；如果是普通字符串，这种功能是做不了的。执行完成后返回 acknowledged: true，空的索引库就创建完成。

## 保存设备坐标：投放工单完成时写入 ES

数据有了容器，接下来打通写入链路。目标是在投放工单完成之后，把设备坐标保存到 ES 中，分四步走。

**第一步，加依赖、加配置。** 在售货机微服务中引入 ES 相关依赖，一共三个，版本 7.4.1——与服务端 ES 版本保持一致。然后在售货机微服务的配置文件里加连接地址，注意要放到 spring 节点之下：

```yaml
spring:
  elasticsearch:
    rest:
      urls: http://192.168.200.128:9200
```

这个地址指向虚拟机中的 Elasticsearch。

**第二步，创建视图模型。** 在 service_common 的 vm model 包下创建 VMDistance 类，它是前后端交互的类型，加上 @Data 注解并实现 Serializable 接口：

```java
@Data
public class VMDistance implements Serializable {
    private String innerCode; // 售货机编号，前端传入
    private String addr;      // 地址，后端返回时用，不需要前端传入
    private String nodeName;  // 点位名称，同样不需要前端传入
    private Double lat;       // 纬度
    private Double lon;       // 经度
}
```

**第三步，实现业务逻辑。** 在售货机服务接口中定义方法，返回布尔值，参数就是刚才的视图模型：

```java
Boolean setVMDistance(VMDistance vmDistance);
```

实现里分两块——向 ES 存入、向数据库保存：

```java
@Override
public Boolean setVMDistance(VMDistance vmDistance) {
    // 位置、点位名称等字段前端不会传，先按编号查库补全
    var vmEntity = this.findByInnerCode(vmDistance.getInnerCode());
    if (vmEntity == null) {
        throw new LogicException("该设备编号不存在" + vmDistance.getInnerCode());
    }
    // 存入 ES：索引库名 vm，id 用售货机编号（唯一标识）
    IndexRequest request = new IndexRequest("vm");
    request.id(vmDistance.getInnerCode());
    request.source(
            "addr", vmEntity.getNode().getAddr(),
            "innerCode", vmEntity.getInnerCode(),
            "nodeName", vmEntity.getNode().getName(),
            "typeName", vmEntity.getType().getName(),
            "location", vmDistance.getLat() + "," + vmDistance.getLon());
    try {
        es.index(request, RequestOptions.DEFAULT);
    } catch (IOException e) {
        log.error("保存售货机位置信息失败", e);
        return false;
    }
    // 数据库再保存一份副本；实际搜索时查的是 ES
    vmEntity.setLatitude(vmDistance.getLat());
    vmEntity.setLongitude(vmDistance.getLon());
    this.updateById(vmEntity);
    return true;
}
```

几个细节值得说明。前端只传售货机编号和经纬度，地址、点位名称、类型名称都要靠 findByInnerCode 查数据库补全（声明处顺手用了 JDK 新版本支持的 var，代码更简洁）；存入 ES 的 location 格式是「纬度,经度」——先纬度、加逗号、再经度；es 是注入的 RestHighLevelClient，保存失败打日志并返回 false；数据库里也存一份经纬度副本，但实际搜索时查的是 ES。

**第四步，接入调用点。** 之前完成投放工单的处理逻辑里留了一个 todo——保存设备的坐标，现在可以补上：

```java
@Override
public void process(String jsonMsg) throws IOException {
    TaskCompleteContract contract = JsonUtil.getByJson(jsonMsg, TaskCompleteContract.class);
    if (contract == null || Strings.isNullOrEmptys(contract.getInnerCode())) return;
    // 如果是投放工单，修改设备状态为运行中
    if (contract.getTaskType() == VMSys.TASK_TYPE_DEPLOY) {
        vmService.updateStatus(contract.getInnerCode(), VMSys.VM_STATUS_RUNNING);
        // 保存设备的坐标
        var vmDistance = new VMDistance();
        BeanUtils.copyProperties(contract, vmDistance);
        vmService.setVMDistance(vmDistance);
    }
    // 如果是撤机工单，修改设备状态为撤机中
    if (contract.getTaskType() == VMSys.TASK_TYPE_REVOKE) {
        vmService.updateStatus(contract.getInnerCode(), VMSys.VM_STATUS_REVOKE);
    }
}
```

**测试这条写入链路。** 启动售货机微服务、工单微服务和网关三个服务，打开测试脚本 task.http，依次执行创建投放工单、接受工单、完成工单三个请求。两个细节：一是创建前先到数据库确认测试用的售货机存在，状态字段为 1 表示已投放，要改成 0 才能重新走流程；二是完成工单的脚本有两个，必须选带采集坐标的那个，因为它的请求体里带纬度和经度。三步执行完，task 表里出现一条新记录（ID 为 24）。最后到 Kibana 里查一下：

```json
GET vm/_search
```

数据已经入库，innerCode 为 01000002，经纬度与脚本里传的值完全一致，写入链路验证通过。

## 附近售货机搜索：geo_distance 查询与距离排序

搜索的模型不复杂：在地图上画一个圆，圆心是用户当前的位置，半径就是搜索范围。所谓附近售货机搜索，就是把圆心（用户经纬度）和半径两个条件传给查询逻辑，找出圆内的设备。写代码前先看小程序 API 文档里的「搜索附近售货机」接口（POST 方式），据此创建两个视图模型，都放在 common 工程的 viewmodel 包下——一个封装前端传给后端的请求参数，一个封装后端返回给前端的列表数据：

```java
@Data
public class VmSearch implements Serializable {
    private Double lat;       // 纬度
    private Double lon;       // 经度
    private Integer distance; // 搜索半径，单位米
}

@Data
public class VmInfoDTO implements Serializable {
    private String location;  // 坐标，"纬度,经度" 格式的字符串
    private String innerCode; // 售货机编号
    private String nodeName;  // 点位名称
    private String addr;      // 详细地址
    private Integer distance; // 距离（直线距离），单位米
    private String typeName;  // 售货机类型名
}
```

一个实用技巧：字段名直接从 API 文档里复制过来，防止手写拼错。接着在售货机服务接口定义搜索方法，再到实现类里完成它。整个方法分两块——封装查询条件、封装查询结果。

查询条件部分，SearchRequest 和 SearchSourceBuilder 是做任何查询都有的；ES 的 GEO 搜索提供了专门的构建器 GeoDistanceQueryBuilder，创建时传入要查询的字段 location：

```java
@Override
public List<VmInfoDTO> search(VmSearch vmSearch) {
    SearchRequest searchRequest = new SearchRequest("vm");
    SearchSourceBuilder sourceBuilder = new SearchSourceBuilder();
    // GEO 距离查询：字段是 location
    GeoDistanceQueryBuilder geoQueryBuilder = new GeoDistanceQueryBuilder("location");
    // 指定查询半径：值从 VmSearch 传入，单位默认是米
    geoQueryBuilder.distance(vmSearch.getDistance(), DistanceUnit.DEFAULT);
    // 指定圆心：纬度、经度
    geoQueryBuilder.point(vmSearch.getLat(), vmSearch.getLon());
    // 用布尔查询把 geo 条件包起来
    BoolQueryBuilder boolQueryBuilder = new BoolQueryBuilder();
    boolQueryBuilder.must(geoQueryBuilder);
    sourceBuilder.query(boolQueryBuilder);
    // 由近到远排序
    GeoDistanceSortBuilder sortBuilder = new GeoDistanceSortBuilder(
            "location", vmSearch.getLat(), vmSearch.getLon(), DistanceUnit.DEFAULT);
    sortBuilder.order(SortOrder.ASC);
    sortBuilder.geoDistance(GeoDistance.ARC);
    sourceBuilder.sort(sortBuilder);
    searchRequest.source(sourceBuilder);
    // 执行查询，封装结果
    try {
        SearchResponse searchResponse = es.search(searchRequest, RequestOptions.DEFAULT);
        SearchHits hits = searchResponse.getHits();
        // 范围内没有任何售货机，返回空集合
        if (hits.getTotalHits().value <= 0) {
            return Lists.newArrayList();
        }
        List<VmInfoDTO> vmInfoList = Lists.newArrayList();
        Arrays.stream(hits.getHits()).forEach(h -> {
            try {
                var vmInfo = JsonUtil.getByJson(h.getSourceAsString(), VmInfoDTO.class);
                // 距圆心的直线距离不在结果字段里，在排序值里
                vmInfo.setDistance((int) (double) h.getSortValues()[0]);
                if (vmInfo != null) {
                    vmInfoList.add(vmInfo);
                }
            } catch (IOException e) {
                log.error("解析搜索结果出错", e);
            }
        });
        return vmInfoList;
    } catch (IOException e) {
        log.error("搜索附近售货机出错", e);
        return Lists.newArrayList();
    }
}
```

拆开讲几个关键点：

- **距离与圆心**：distance 方法两个参数——具体值和单位，值从 VmSearch 传过来，单位默认就是米；point 方法指定圆心，参数依次是纬度、经度。
- **布尔查询**：geo 条件要用 BoolQueryBuilder 包起来，must 表示必须满足；之后想加其他条件，按原来的方式构建查询构建器塞进布尔里即可。
- **排序**：前面的查询只保证返回范围内的结果，不保证顺序，而这类查询通常要由近到远排列。GeoDistanceSortBuilder 构建时传三个参数：字段、纬度、经度；order 设为 ASC，升序就是由近到远；再用 geoDistance 方法指定距离算法——ARC 和 PLANE 两种：PLANE 更快但精准度低，ARC 稍慢但精准度高（慢工出细活）。按业务取舍：对速度要求高、精准度要求低选 PLANE；要精准、慢一点没关系选 ARC。
- **结果封装**：查询返回 SearchResponse，getHits 拿到结果；getTotalHits().value 小于等于 0 说明没有任何数据，直接返回空集合。有数据就把 hits 数组转成 stream 流逐条处理，每条记录用 getSourceAsString 拿到查询结果的 JSON 字符串，再转成 VmInfoDTO 对象，这一步同样要做异常处理。
- **距离的取值位置**：设备到用户的直线距离不在结果字段里，而在 h.getSortValues() 里——它返回一个 Object 数组，取第一个元素转成 int。

最后补 Controller 和远程调用。售货机微服务的 Controller 按文档定义 POST /search 接口，直接透传给服务层：

```java
@PostMapping("/search")
public List<VmInfoDTO> search(@RequestBody VmSearch vmSearch) {
    return vmService.search(vmSearch);
}
```

小程序微服务要调这个接口，走 Feign 远程调用：在 service_common 的 feign service 包下的 VmService 接口里把方法包进去，路径前面别忘了加上 /vm 前缀；因为配置了降级类，降级类里也要同步定义这个方法——远程调用失败时返回一个空集合。然后小程序微服务的 Controller 再定义一个 search 方法，内部直接调用 Feign 接口。整条调用链路是：

```mermaid
flowchart LR
    A[小程序] --> B[小程序网关] --> C[小程序微服务] --> D[Feign 远程调用] --> E[售货机微服务] --> F[(Elasticsearch vm)]
```

**测试。** 启动售货机微服务、小程序微服务、小程序专用网关三个服务（前端是通过小程序网关来调用小程序服务的）。用 VS Code 打开测试脚本，执行「搜索附近售货机」，请求体里传纬度、经度和搜索半径。

第一次调用返回的数据是空的——是没有数据，还是出错了？打断点调试，切到售货机微服务，控制台里产生了错误，跟踪到出错的那一行，错误描述很好理解：不能将 double 类型转成 integer 类型。也就是说 sortValues 返回的 Object 实际是个 double（距离带有精度），直接强转成 int 就出问题了。修复方式是中间加一层转换：先把 Object 转成 double，再转成 int，也就是 `(int)(double) h.getSortValues()[0]`。重启微服务再测，数据就能查出来了。

返回结果里的 distance 就是设备距离用户多少米：为 0 表示设备就在眼前，因为测试脚本传的经纬度和库里存的完全一样。把经度的末位稍微改一下（比如 5 改成 9）再测，距离由 0 变成 34——两个数的差越大，距离就越大，数值表现符合预期。后续还可以按文档的测试步骤，用微信开发者工具设置模拟地理位置（纬度 40.060584、经度 116.344116）做联调测试。

## 小结

这篇把立可得 LBS 功能的第一段路走完了：从「搜索附近售货机」的需求出发，选定 Elasticsearch GEO 方案；用 geo_point 类型建好 vm 索引库；在投放工单完成时由售货机微服务把设备坐标写入 ES（数据库留副本）；再用 geo_distance 查询加距离排序实现由近到远的附近搜索，Controller、Feign、降级一路打通，最后通过脚本测试验证并踩掉了 double 强转 int 的坑。两条经验值得带走：一是选型看数据特征，位置变不变决定了用 Redis GEO 还是 ES GEO；二是字段类型决定能力上限，location 必须是 geo_point，否则一切地理搜索无从谈起。这个模块后面还有订单数据同步、选品智能推荐等内容，会接着这条数据链路往下走。
