# 数据库建模三部曲、PowerDesigner 物理建模与 MySQL 调优

数据库设计是后端项目的底层地基。本文围绕智牛股项目梳理数据库建模三部曲、PowerDesigner 物理建模实操，以及数据库调优与 explain 执行计划解读。

## 先给结论

- 数据库建模三步曲是**概念模型 → 逻辑模型 → 物理模型**：概念模型回答业务"是什么"，逻辑模型回答系统"做什么"，物理模型回答"怎么做"（用 SQL 实现）。
- PowerDesigner 以数据库建模起家，与专攻 UML 的 Rational Rose 路径相反，提供 CDM/LDM/PDM 等七种建模类型，日常建表主要用 PDM。
- PD 物理建模流程：New Model 选 Physical Data → Change Current DBMS 指定 MySQL → Toolbox 拖 Table 建表加列 → Index 页建索引 → Generate Database 生成脚本，最后在 Navicat 的 test 库验证执行。
- MySQL 不支持索引的 `DROP INDEX IF EXISTS` 语法，PD 默认模板会生成这条语句导致脚本重复执行报错；一劳永逸的做法是清除生成模板（Database → Edit Current DBMS → Script → Objects → Index → Drop）。
- 影响数据库性能的六大因素：硬件能力、系统规模、业务模型及架构、代码设计、软硬件环境、数据库内部因素；调优手段包括业务设计权衡、加索引、分库分表、读写分离、SQL 调优与 MySQL 配置优化。
- explain 只是预估、不会实际执行；重点看 type（出现 ALL 就要警惕）、possible_keys 与 key（是否走索引）、rows（估算扫描行数）；5.7 之后默认输出 partitions 和 filtered。

## 数据库建模三部曲：概念、逻辑、物理

数据库模型是数据库的基础：模型是现实世界的抽象，数据模型就是对数据特征的抽象。数据库类型依据数据模型划分，任何 DBMS 也是按数据模型有针对性设计的，因此必须把数据库组织成符合 DBMS 规定的数据模型；常见的逻辑数据模型有层次模型、网状模型和关系模型。

概念模型面向用户、面向现实世界，与 DBMS 无关而与业务相关，按用户的观点和业务知识建模。以金融交易市场为例，一个完整交易可抽取出客户、交易账号、股票（含行情报价）、订单（下单挂单生成）、持仓等概念——它告诉业务"是什么"。

逻辑模型是概念模型的具体化：客户有名称、账号、电话、地址等属性，股票包含代码、名称、市场、单位、手续费，订单包含账户、股票代码、手续费、金额。这个阶段要明确划分多少模块、建多少张表、每张表有哪些属性，用于 DBMS 的实现，回答"做什么"。

物理模型是对真实数据库的描述、数据最底层的抽象，面向计算机系统，涉及表、视图、字段、类型、主键、外键、索引、约束、默认值等对象，用数据库语言生成具体 SQL，回答"怎么做"。一般先建概念模型，再加工出逻辑模型，最后设计出物理模型形成 SQL。

## PowerDesigner：建模类型与物理建模实战

PowerDesigner 是最流行的建模软件之一。Rational Rose 专攻 UML 对象建模后再向数据库建模发展，它则以数据库建模起家，后来发展为综合全面的 Case 工具。七种建模类型中，前三类是主线：

| 类型 | 缩写 | 用途 |
| --- | --- | --- |
| 概念数据模型 | CDM | 用 E-R 图组织数据，检验设计的有效性和合理性 |
| 逻辑数据模型 | LDM | 显示实体、属性和关系，介于概念与物理模型之间，可生成针对具体 DBMS 的物理模型；非必须环节 |
| 物理数据模型 | PDM | 基于特定 DBMS 在 CDM/LDM 基础上设计，可生成数据库，也支持对已有库逆向工程 |

另外四种：OOM 用 UML 图描述业务与操作员的关系（软件系统的静态概念模型）；BPM 从业务合伙人观点识别、分解业务流程；ILM 用于分布式数据库间的数据复制；EAM 从业务层、应用层、技术层描述企业架构。

### 实操：从建表到生成 SQL

通过 File → New Model 选择物理数据模型，第一件事不是建表，而是用 Change Current DBMS 选择实际数据库（按需选 MySQL 或 PostgreSQL），使其能生成对应的 SQL 脚本。随后在 Toolbox 选择 Table 在空白区域建表，交易模块订单表按命名规范定为 `t_trade_order`。

在 Columns 页逐个添加列：

- `id`：主键，注释"唯一主键"，勾选 Primary Key 和 Identity 自增；数据量大应改 bigint。
- `accountid`：交易客户 ID，加注释，在 Datatype 中选类型，勾选 NOT NULL。
- `status`：订单状态，取值就那么几种，用 tinyint 给 3 个长度即可，约可存 99 个状态。
- `type`：订单类型，同样 tinyint(3)，减少空间占用；枚举含义在业务章节再展开。
- `orderVolume`：成交数量，int。

每加一列都能在 Preview 页实时看到 SQL。索引在 Index 页创建：按规范以 idx 为前缀命名，给 accountid 建唯一索引写 `idx_accountid` 并勾选 Unique，再双击索引关联列。生成的脚本如下：

```sql
CREATE TABLE `t_trade_order` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '唯一主键',
  `accountid` bigint NOT NULL COMMENT '交易客户ID',
  `status` tinyint(3) NOT NULL COMMENT '订单状态，01:未下单，02:已下单，03:已支付，04:已发货，05:已完成',
  `type` tinyint(3) NOT NULL COMMENT '订单类型，01:普通订单，02:批量订单',
  `orderVolume` int NOT NULL COMMENT '订单数量',
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8;

ALTER TABLE `t_trade_order` COMMENT '订单表';
CREATE UNIQUE INDEX `idx_accountid` ON `t_trade_order` (`accountid`);
```

默认模板会生成 `DROP INDEX IF EXISTS` 语句，而 MySQL 不支持索引的 IF EXISTS 语法：第一次执行报错，表没建成，后续脚本一直失败。一劳永逸的办法是改模板：Database → Edit Current DBMS，在 Script → Objects → Index → Drop 下清除默认内容。生成脚本走 Database → Generate Database，指定目录和文件名（演示中生成到桌面，命名 test.sql），Check Model 建议不勾选；拿到 Navicat Premium 的 test 库执行后，主键、唯一索引、注释都完整生成。后续维护字段只需维护物理模型重新生成脚本；生产环境已有数据则应采用增量脚本方式。

## 数据库调优：六大因素与方法全景

MySQL 是使用最多的开源数据库，但默认设置的性能并非最优，生产环境不做优化就无法发挥最佳性能——阿里就针对 InnoDB 的底层锁机制做过优化。影响性能的原因可归纳为六大类：

| 因素 | 典型问题 |
| --- | --- |
| 硬件能力 | CPU、内存、IO 等硬件瓶颈 |
| 系统规模 | 并发用户数突增或峰值，数据量增长 |
| 业务模型及架构 | 单库设计撑不住高并发大数据量；OLTP 与 OLAP 混在一起 |
| 代码设计 | 无主键（锁全表）、OR/LIKE、游标、参数化、重编译 |
| 软硬件环境 | 操作系统版本低、参数配置不合理 |
| 数据库内部因素 | 索引、隐式转换、数据类型滥用 text/blob、统计信息、自动增长 |

业务模型层面要分清 OLTP 与 OLAP：OLTP 是联机事务处理，面向操作人员的日常处理，数据量少、DML 频繁，读写数十条记录；OLAP 是联机分析处理，面向决策人员做分析决策，数据是历史的、聚集的、多维集成的，一次读上百万条记录，DB 规模在 100GB-TB 级。

### 常用调优方法

**业务设计的合理性**：不是满足一切需求，在性能瓶颈处要权衡取舍。报表不需要强实时性，就不必直接查核心表，采用预生成方式既满足业务要求，又保护核心表。

**增加索引**：简单直接，能极大优化查询性能。种类有主键索引 PRIMARY KEY、唯一索引 UNIQUE、常规索引 INDEX、全文索引 FULLTEXT；底层结构主要是 B+Tree 和 Hash。

| 对比项 | B+Tree | Hash |
| --- | --- | --- |
| 结构 | 自平衡树，值按顺序存储，叶子到根距离相等，叶子节点上增加了指针 | 哈希算法计算哈希值，排序在哈希数组上 |
| 等值查询 | 需多次磁盘 IO，从根节点开始搜索 | 一次计算一次定位，效率非常高 |
| 范围查询 | 顺序组织存储，天然适合，查 2 到 5 只需定位后顺链取数 | 只能等值比较，范围内上万条数据就要计算上万次 |
| 排序 | 支持按索引排序 | 哈希值有序但映射的真实数据不保证有序，无法加速排序 |
| 大量重复值 | 稳定 | 重复值多且数据量大时检索效率不如 B+Tree |

B+ 树减少定位记录的中间过程，MySQL 采用的正是 B+ 树。索引不是一味地加：一张表控制在四到五个以内，索引越多维护文件越大，反而影响增删改查性能。

**分库分表**：分库分解数据压力，生产一般采用集群，按业务特性拆分，提升 IO 吞吐能力；分表化解单表压力，有垂直（按字段拆）和水平（按行拆）两种。单维度拆分常用按时间字段（订单表按月预留 12 张表）或按节点数取模（5 台节点以 5 为基数）；多维度拆分可用基因法——UID 分 8 个库时，用 UID 最后 3 个比特位决定数据落库（2 的 3 次方为 8），其他字段可结合这个基因。分表并非万能，关联查询、分页查询、数据路由都有开销。

**读写分离**：主库处理事务性的增删改，从库处理 select 查询。读写压在同一台服务器上，频繁写入影响读取、读取量大又反过来影响读写；通过主从复制同步数据，再以读写分离提升并发负载能力。

**SQL 语句调优**（面试高频）：

- 调整 WHERE 子句连接顺序，自下而上解析，排最后的条件最先执行；
- 多条 SQL 压缩成一句，减少网络与 IO 开销；
- 用 WHERE 替换 HAVING，HAVING 只在检索出所有记录后才过滤；
- 用简洁的表别名，减少属性解析时间；
- in 和 exists 通常用 exists（in 不走索引但不绝对）；数据量大时改用 join，left join 把数据少的表放左边；
- 用 UNION ALL 替换 UNION：UNION 要去重再排序、耗费 CPU，UNION ALL 直接合并不去重。

**MySQL 配置优化与其他**：连接数按需扩大，缓存尽量调大，数据包大时调大吞吐量，IO 线程按硬件调整，开启闲置连接回收；此外还有索引重建（频繁修改产生碎片，需定期整理）、磁盘碎片优化、版本升级（选有明显改进且稳定的版本）。

## explain 执行计划：把慢查询落到实处

执行计划是分析执行 SQL 语句的过程，包括查询顺序、是否使用索引等信息，由遍历表、走索引、嵌套循环或哈希连接等基本操作组成。在 SQL 前加 explain 即可生成；它只是预估、不会实际执行，对 update 也不生效。输出结果是一张表：

| Column | 含义 |
| --- | --- |
| id | 选择标识符 |
| select_type | 查询类型 |
| table | 输出结果的表名 |
| partitions | 匹配的分区信息 |
| type | 连接类型 |
| possible_keys | 可能使用的索引 |
| key | 实际使用的索引 |
| key_len | 索引字段的长度 |
| ref | 连接匹配条件 |
| rows | 扫描估算的行数 |
| filtered | 按条件过滤的行百分比 |
| Extra | 附加说明信息 |

判断是否走索引，主要结合 possible_keys（可能用到）和 key（实际用到）两项。5.7 以前显示 partitions 需用 explain partitions、显示 filtered 需用 explain extended，5.7 之后默认直接显示。

### 结合实际 SQL 解读

先用脚本在 test 数据库初始化表结构和测试数据。第一条 SQL 查询用户关联的角色信息，涉及 s_authority_user、s_authority_user_role、s_authority_role 三张表，USER_ACCOUNT 是唯一索引：

```sql
EXPLAIN SELECT u.id, u.USER_ACCOUNT, r.ROLE_NAME
FROM s_authority_user u
LEFT JOIN s_authority_user_role ur ON u.id = ur.USER_ID
LEFT JOIN s_authority_role r ON ur.role_id = r.id
WHERE u.USER_ACCOUNT = 'admin';
```

id 相同的行执行顺序由上至下；id 不同则值越大越先执行（与自增主键"ID 越小越先生成"相反）；某行是其他行的 UNION 结果时 id 为 NULL，table 列显示 `<union M,N>`，即 ID 为 M 和 N 的查询行的联合结果。

select_type 的常见取值：

| 取值 | 含义 |
| --- | --- |
| SIMPLE | 不包含子查询或 UNION 的简单查询 |
| PRIMARY | 包含子查询时的最外层查询 |
| SUBQUERY | SELECT 或 WHERE 子句中包含的子查询 |
| DERIVED | FROM 子句中包含的子查询，会生成临时表 |
| UNION | UNION 之后的查询 |
| UNION RESULT | 从 UNION 中获取结果集 |
| MATERIALIZED | 被物化的子查询，用得较少 |

table 列显示表名，用了别名就显示别名（如 u、ur、r），不涉及表操作显示 NULL，`<derived N>` 表示来自 ID 为 N 的查询产生的临时表。把子查询放进 FROM 就能看到 DERIVED：

```sql
EXPLAIN SELECT u.id, u.USER_ACCOUNT, r.ROLE_NAME
FROM s_authority_user u
LEFT JOIN (SELECT USER_ID, role_id FROM s_authority_user_role GROUP BY user_id) ur ON u.id = ur.USER_ID
LEFT JOIN s_authority_role r ON ur.role_id = r.id
WHERE u.USER_ACCOUNT = 'admin';
```

partitions 列显示分区表命中的分区，非分区表该列为空。建一张 `PARTITION BY KEY (id) PARTITIONS 3` 的分区表，explain select * 会输出 p0、p1、p2。

type 列表示查询的连接类型，是判断 SQL 好坏的核心指标，从好到差依次为 system > const > eq_ref > ref > range > index > ALL：

| type | 含义 |
| --- | --- |
| system | 连接类型的特例，查询的表为系统表 |
| const | 使用主键或唯一索引，匹配结果只有一条 |
| eq_ref | join 查询中使用 PRIMARY KEY 或 UNIQUE KEY NOT NULL 索引关联 |
| ref | 使用非唯一索引查找数据（如关联字段未建唯一索引） |
| fulltext / ref_or_null | 使用全文索引 / 对 NULL 做了索引优化的 ref |
| unique_subquery / index_subquery | 子查询中的等值匹配 / 子查询中使用 in |
| range | 索引范围扫描，如按日期范围、ID 范围查找 |
| index | 索引全量扫描，遍历索引从头到尾（不是扫数据文件），常见于只用索引列就能处理的查询 |
| ALL | 扫描全表数据，性能最差，出现时必须检查索引是否生效、SQL 是否有问题 |

possible_keys 是预估可用的索引；key 为 NULL 就该考虑优化。rows 是扫描行数的估算值。

## 小结

本章主线是"规范 + 模型 + 工具 + 调优"：规范层面理解三范式与反范式的权衡及"不在数据库做运算、控制列数量、拒绝 3B"等原则；模型层面掌握三部曲理论基础；工具层面用 PDM 建表、建索引并生成 SQL，注意 DROP INDEX IF EXISTS 的坑；调优层面按业务设计、索引、分库分表、读写分离、SQL 改写、配置参数逐项优化，最后用 explain 验证 type、key、rows 等指标。
