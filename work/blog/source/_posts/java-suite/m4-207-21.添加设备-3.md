# 亿可控设备管理接口集：详情查询与状态、标签、告警、在线状态更新

设备管理的接口全部围绕 ES 的 devices 索引展开。上一节写完 addDevices 的落库逻辑，本篇先把单元测试类搭起来收尾，再补上后面所有逻辑都要复用的按 ID 查详情方法；接着是一组更新接口——设备状态开关、标签、告警信息、在线状态，每个都按 repository、service、controller 三层走完并验证；最后以分页条件查询的需求梳理收尾，为下一篇的实现开篇。

## 先给结论

- 测试类 TestES 用 @SpringBootTest(classes = YkkApplication.class) 指定启动类，再加 @RunWith(SpringRunner.class) 跑起整个上下文，注入 ESRepository 后逐个方法测；每测完一个到 Kibana 查 devices 索引核对数据才算闭环。
- searchDeviceById 用 termQuery 按 ES 主键 _id 查，命中后只取第一条 getSourceAsString 反序列化成 DeviceDTO，并把主键回填进 deviceId——_id 不在 _source 里；查不到或异常一律返回 null。
- 更新统一走 UpdateRequest(索引, 主键) 加 doc(字段, 值)：单字段（status、tag、online）与多字段（alarm、level、alarmName）写法一致，成功返回 true，异常 log.error 后返回 false。
- setStatus 在 service 层先经 findDevice 查存在性，查无此设备直接 false；controller 用 DeviceVO 接请求体，sn 与底层的 deviceId 是同一个东西，只是前后端叫法不同。
- /device/tags 是供外部业务系统调用的接口，不走前端登录，认证过滤器对包含该路径的请求直接放行；controller 测试推荐 VS Code 的 REST Client 插件跑 .http 脚本，接口多时比 Postman 好管理，比 MockMvc 少一堆测试代码。
- 分页查询开篇：设备管理与数据详情两个页面共用一个底层方法，后者多一个 state（0 在线、1 离线、2 一般告警、3 严重告警），设备管理页没有这个条件就传 null，方法内部分支处理。

## 测试类骨架与按 ID 查详情

添加设备的方法写完先过单元测试。在 test 下新建 TestES 类，类上两个注解：@SpringBootTest 指定启动类，@RunWith(SpringRunner.class) 指定测试运行器，测试一跑整个 Spring Boot 上下文就起来了。注入 ESRepository，写 testAdd：new 一个 DeviceDTO，设备编号给 123456，不告警、告警名称空串、级别 0、在线 true、标签空串、开关 true，调 addDevices 落库。

```java
@SpringBootTest(classes = YkkApplication.class)
@RunWith(SpringRunner.class)
public class TestES {

    @Autowired
    private ESRepository esRepository;

    @Test
    public void testAdd() {
        DeviceDTO deviceDTO = new DeviceDTO();
        deviceDTO.setDeviceId("123456");
        deviceDTO.setAlarm(false);
        deviceDTO.setAlarmName("");
        deviceDTO.setLevel(0);
        deviceDTO.setOnline(true);
        deviceDTO.setTag("");
        deviceDTO.setStatus(true);
        esRepository.addDevices(deviceDTO);
    }
}
```

右键运行方法，绿色就表示执行没有错误。验证不止看绿：到 Kibana 里查 devices 索引（查询语句前带上库名），测试数据已经存进来，添加设备的方法才算真正完成。

按 ID 查询设备这个方法后面很多逻辑都要调，先把它写出来并测好。ESRepository 新增 searchDeviceById(String deviceId) 返回 DeviceDTO，用的还是 RestHighLevelClient 高级客户端，查询走它的 search 方法，参数是 SearchRequest 和 RequestOptions.DEFAULT。SearchRequest 指定查 devices 索引；查询条件用 SearchSourceBuilder 构建，query 里放 QueryBuilders.termQuery("_id", deviceId)——注意查的是主键 _id，不是 deviceId 字段。

```java
public DeviceDTO searchDeviceById(String deviceId) {
    SearchRequest searchRequest = new SearchRequest("devices");
    SearchSourceBuilder searchSourceBuilder = new SearchSourceBuilder();
    searchSourceBuilder.query(QueryBuilders.termQuery("_id", deviceId));
    searchRequest.source(searchSourceBuilder);
    try {
        SearchResponse searchResponse = restHighLevelClient.search(searchRequest, RequestOptions.DEFAULT);
        SearchHits hits = searchResponse.getHits();
        long hitCount = hits.getTotalHits().value;
        if (hitCount == 0) return null;
        DeviceDTO deviceDTO = null;
        for (SearchHit hit : hits) {
            String hitResult = hit.getSourceAsString();
            deviceDTO = JsonUtil.getObjByJson(hitResult, DeviceDTO.class);
            deviceDTO.setDeviceId(deviceId);
            break;
        }
        return deviceDTO;
    } catch (IOException e) {
        e.printStackTrace();
        log.error("设备查询异常");
        return null;
    }
}
```

两个细节值得记：结果数量用 hits.getTotalHits().value 拿，等于 0 说明没有查询结果直接返回 null；主键 _id 不在 _source 里，所以反序列化出来的文档缺 deviceId，要手动 setDeviceId 回填一次。主键只可能命中一条，循环里取到第一条就 break。单元测试 testSearchById 调这个方法查 123456，返回后用 JsonUtil.serialize 序列化成 JSON 字符串打出来，控制台能看到完整设备数据，方法没有问题。

## 四个更新方法：一套 UpdateRequest 套路

先看设备状态的业务来源：产品原型的设备列表每行有一个开关，把设备关闭之后，它发上来的报文数据就做忽略处理，不再处理。实现上很轻——索引库里本来就有一列设备状态值，改它的值即可，剩下的逻辑判断真假就行。API 文档要求 PUT 方式提交，参数是设备编号 sn 和状态值，返回 boolean。

ESRepository 里新增 updateStatus，UpdateRequest 两个参数——索引名和要更新的主键，doc 指定要改的字段与值：

```java
public boolean updateStatus(String deviceId, Boolean status) {
    UpdateRequest updateRequest = new UpdateRequest("devices", deviceId);
    updateRequest.doc("status", status);
    try {
        restHighLevelClient.update(updateRequest, RequestOptions.DEFAULT);
        return true;
    } catch (IOException e) {
        e.printStackTrace();
        log.error("更新设备状态出错");
        return false;
    }
}
```

service 层不能拿起来就调——设备存不存在还不一定。先封一个私有方法 findDevice(deviceId)，内部就是调 esRepository.searchDeviceById，类里其它地方要查设备也走它，更简洁。setStatus(deviceId, status) 里先 findDevice，DTO 为 null 直接返回 false，存在才调 updateStatus。controller 这边照 API 文档写：PUT 提交，sn 和 status 在 body 里，是一个对象的两个属性，框架已经提供好 DeviceVO（和前端打交道的实体对象），里面正好有这两个字段：

```java
@PutMapping("/status")
public boolean setStatus(@RequestBody DeviceVO deviceVO) {
    return deviceService.setStatus(deviceVO.getSn(), deviceVO.getStatus());
}
```

sn 就是底层的 deviceId，只是叫法不一样——API 面向前端叫 sn，底层叫 deviceId，用一个 VO 适应这种变化。@PutMapping("/status") 也不是乱写的：类上已有 /device 前缀，拼起来正好对上文档的 /device/status。

| 功能 | 请求 | 路径 | 参数 | 返回 | 底层方法 |
|------|------|------|------|------|----------|
| 设置设备状态 | PUT | /device/status | body：sn、status | boolean | updateStatus |
| 设置设备标签 | PUT | /device/tags | body：sn、tags | boolean | updateDeviceTag |
| 更新设备告警信息 | 内部触发 | — | DeviceDTO | boolean | updateDevicesAlarm |
| 更新在线状态 | 内部触发 | — | deviceId、online | boolean | updateOnline |

设备标签是为检索服务的：给设备打标签，可以是分类（温度计、湿度计）、地理位置（北京、上海），也可以是商圈性质（学校、商场），完全由用户自定义。这个功能在产品原型界面上没有——亿可控不在界面里改标签，而是像微信支付、支付宝那样把接口暴露给外部业务系统，由业务系统调用来管理设备标签，所以只需写底层方法加业务层控制层。updateDeviceTag 和 updateStatus 套路完全一样，doc 里换成 ("tag", tags)，日志改成更新设备标签出错；service 定义 updateTags(deviceId, tags) 一行调用；controller 用 @PutMapping("/tags") 接 DeviceVO 里的 sn 和 tags。这里有个矛盾要处理：接口给外部系统调、不走前端登录，不登录就会被认证过滤器拦住，所以要改写认证过滤器，对包含 /device/tags 的请求直接放行。

告警信息的更新是报文驱动的：设备发来的报文指标达到告警级别时，更新 ES 里存的告警信息——是否告警 alarm、告警级别 level、告警名称 alarmName，前端界面提供按告警筛选的功能，更新最终就是为了搜索。这个方法不会被前端直接调，所以只写 repository 方法并做单元测试。参数不零散传，直接传 DeviceDTO，这些字段它都有；需要改多个字段就在 doc 里接着逗号往下写：

```java
public boolean updateDevicesAlarm(DeviceDTO deviceDTO) {
    UpdateRequest updateRequest = new UpdateRequest("devices", deviceDTO.getDeviceId());
    updateRequest.doc(
        "alarm", deviceDTO.getAlarm(),       // 是否告警
        "level", deviceDTO.getLevel(),       // 告警级别
        "alarmName", deviceDTO.getAlarmName() // 告警名称
    );
    try {
        restHighLevelClient.update(updateRequest, RequestOptions.DEFAULT);
        return true;
    } catch (IOException e) {
        e.printStackTrace();
        log.error("更新设备告警信息出错");
        return false;
    }
}
```

单元测试 testAlarm 构造 123456 这台设备：alarm 设 true、level 给 1、alarmName 给温度过高。执行前 Kibana 里这条数据告警是 false、名称为空、级别 0，跑完再查，三个值都改过来了。在线状态的更新同样简单：设备会断电断网导致离线，信息里要存是否在线，后续很多地方要做统计分析。updateOnline(deviceId, online) 更新一列，doc("online", online) 即可。本节只完成方法本身，怎么判断设备在线还是离线，是后续章节的内容。测试 testOnline 把 123456 的 online 从 true 改成 false，Kibana 里查询验证。

## Controller 测试：REST Client 加 .http 脚本

controller 的测试方法不少。Postman 之前用过，但接口一多，之前测过的接口往往就找不到了，管理起来很不方便；MockMvc 能针对 controller 写单元测试，但会在工程里产生大量测试代码，也不推荐。推荐用 VS Code 的 REST Client 插件：写脚本的方式测 HTTP 接口，写完一遍之后再测也非常方便。资料包里已经提供脚本，在资料的测试文件夹下有个 eco.http，用 VS Code 打开（先把插件装上，才有高亮和发送按钮）。

先把工程启动起来，再到 Kibana 查一眼现有数据：目前只有一条，主键 123456，status 为 true。脚本里找到修改设备状态那段，sn 是 123456 不用改，status 改成 false，点 Send Request，右侧返回 true——方法返回的就是 boolean：

```http
PUT http://(hostname):9083/device/status HTTP/1.1
Content-Type: application/json
Authorization: (Authorization)

{
  "sn": "123456",
  "status": false
}
```

脚本里的主机地址与令牌按资料包原样替换。请求发出去后再到 Kibana 执行一次查询，status 已经变成 false，controller 到 ES 的整条链路就验证完了。

## 分页查询开篇：两个页面共用一个方法

产品原型里有两个页面要用到分页条件查询。第一个是设备管理：按条件查设备列表，条件包括设备编号和标签，结果显然是分页的，非常典型的条件分页查询。第二个是数据详情：显示的内容是设备基本信息加指标信息，条件同样是设备编号和标签，但多了一个设备状态——状态设定了四个值：在线、离线、一般报警、严重报警。

如果两个页面各写一个底层方法，代码冗余比较严重。做法是只写一个方法把条件接过来：设备管理页没有状态条件，就传 null，方法里根据是不是 null 分支跳过即可，很多时候都是这么处理的。本篇把需求梳理到这里，具体实现——布尔查询、通配符、from/size 与 trackTotalHits——留给下一篇展开。

- TestES 是所有 ES 方法的验证场：@SpringBootTest 指定启动类加 @RunWith 起上下文，测完到 Kibana 查数据才算闭环。
- searchDeviceById 按主键 _id 做 termQuery，只取第一条并回填 deviceId，异常与空结果都返回 null，供状态更新等后续逻辑复用。
- 四个更新方法共享一个套路：UpdateRequest(索引, 主键) 加 doc(字段, 值)，单字段多字段一致，异常 log.error 后返回 false。
- 状态更新在 service 层先查存在性；标签接口面向外部系统，认证过滤器放行 /device/tags；告警与在线状态的更新由内部逻辑触发，只做 repository 加单元测试。
- controller 测试用 VS Code REST Client 跑 .http 脚本（资料包 eco.http），改完数据去 Kibana 核对。
- 分页查询需求已就位：设备管理与数据详情两页共用一个底层方法，state 条件（0 在线、1 离线、2 一般告警、3 严重告警）缺省传 null。
