# EMQX ACL安全方案：概述与鉴权链、连接认证、超级用户判断与发布订阅控制

立可得第九章把售货机的「五脏六腑」拆开细看，EMQ 的安全是绕不开的一环。生产环境里 EMQX 必须暴露公网——物联网设备要和后端微服务通信，服务藏不进内网。门一旦敞开，任何终端都能连上来发布、订阅消息，等于谁都随意进出，显然不行。EMQX 给出的解法是 ACL（Access Control List，访问控制列表），课程选择 HTTP 插件方案，把认证和权限逻辑收回到自己写的售货机微服务里。

## 先给结论

- ACL 即访问控制列表：既能控制「谁能连接」，也能控制「连上后能发布、订阅哪些主题」；类比大门安检，名单上的人通过，不在名单上的连连接都不行。
- EMQX 提供三种 ACL 方式：内置 ACL 写配置文件，适合变动小的场景；外部数据库（MySQL、PostgreSQL、Redis、MongoDB 等）动态查库判断；HTTP 方式自己写接口实现复杂规则。除内置外都靠插件支撑，插件不开启就不生效。
- 多个 ACL 插件同时开启会按开启顺序形成鉴权链：匹配到规则即出结果（允许或拒绝）并终止，没匹配走下一个，全部未命中走默认规则（内置 ACL）；实际通常只开一个，开得越多鉴权效率越低。
- ACL 缓存由 etc/emqx.conf 三条配置控制：enable_acl_cache、acl_cache_max_size=32、acl_cache_ttl=1m；TTL 过短数据库压力大，过长则规则变更后实效性差。
- 三段代码实现的分工：/acl/auth 连接认证（mqtt、monitor 开头的 clientid 特权放行，其余查售货机表）；/acl/superuser 超级用户判断（通过即跳过发布订阅控制，相当于王牌）；/acl/pubsub 发布订阅控制（普通售货机只能发 server 加自己编号的主题、订 vm 加自己编号的主题）。
- 联调有套固定节奏：改 emqx_auth_http.conf 后要 emqx restart 才生效；认证回调经网关（192.168.200.1:9007）转发，要在网关忽略鉴权列表里放行；启动顺序必须是先停插件、再起售货机微服务和网关、最后开插件，否则微服务会卡死在启动阶段。

## ACL 是什么：公网暴露后的访问控制

EMQX 在真实生产环境里是公网可访问的，因为物联网设备要和后端微服务通信，它必须暴露出来。可公网可访问意味着任何设备终端都能连上来发布、订阅——相当于把大门敞开还不设门卫。ACL 就是给这扇门装安检：进来的都要核对身份，名单上的人通过，不在名单上的连连接都不行。而且它不只管连接，还能管主题的发布订阅——你能连上来，但可能只被允许订阅某个主题、发布某个主题。

实现方式有三种，适用场景各不相同：

1. **配置文件（内置 ACL）**：EMQX 自带一套规则，直接写进配置文件。简单，适合终端数量少、可预见、变动很小的场景；一旦名单经常变化，改起来就很麻烦。
2. **外部数据库**：MySQL、PostgreSQL、Redis、MongoDB 这些主流数据库都有插件支持，原理是认证时查询数据库来判断终端能否连接。立可得的售货机数量庞大、名单经常变动，每次都改配置文件不现实，需要的正是这种动态方式。
3. **HTTP 方式**：ACL 规则复杂时用它——自己写一套代码，比如在后端微服务里写一个 Controller，把判断逻辑包装进去，实现复杂的 ACL 管理。立可选的就是这条路。

要注意的是，除了内置 ACL，其余方式都靠插件实现：开 MySQL 认证就有 MySQL 的插件，HTTP 认证对应 emqx_auth_http 插件，不开启就不会生效。在 EMQX 控制面板的 Plugins 页能看到这些插件，emqx_auth_http 默认是 Stopped 状态，点 Start 即可启用。

## 鉴权链与缓存：规则怎么走、结果怎么存

如果把这些认证方式同时开启，EMQX 会按插件的开启顺序把它们串成一条鉴权链，链上每个 ACL 就是一条规则。客户端请求进来后逐条匹配：

- 匹配到规则，两种结果二选一：允许——通过鉴权，链条终止；拒绝——同样终止，连接被禁。
- 没匹配到（规则既没允许也没拒绝），继续走下一条规则。
- 走到最后所有规则都没匹配上，落到默认规则，也就是内置 ACL。

实践中通常没必要同时开多个插件：开启得越多，鉴权效率越低，一般只开一个就够。

另一个提升效率的手段是缓存。没有缓存时，每一次认证、每一次发布订阅控制都要查一遍数据库，效率极其低下。etc/emqx.conf 核心配置文件里有三条相关配置：

```ini
# 是否启用 ACL 缓存
enable_acl_cache = on

# 单个客户端最大缓存规则数量
acl_cache_max_size = 32

# 缓存失效时间，超时后缓存将被清除
acl_cache_ttl = 1m
```

1m 即一分钟：第一次匹配经数据库查询得到结果后缓存起来，一分钟内相同的规则再过来就直接取缓存，过期后才重新查库。这个时间不宜过短也不宜过长——过短，数据库压力大；过长，规则已经变了缓存还没过期，控制的实效性就差。

## 连接认证：三段实现的第一道门

代码实现分三块：连接认证、超级用户判断、发布订阅控制。连接认证是第一步——连都连不上，后面的发布订阅无从谈起，它要回答的问题是「当前连接的客户端能否建立连接」。

先看配置。连到部署 EMQX 的宿主机（192.168.200.128），进入 emqx 容器，etc/plugins 目录下每个插件各有一份独立配置，找到并编辑 emqx_auth_http.conf。文件里三段配置用注释线隔开：第一段连接认证，第二段超级用户，第三段发布订阅。

连接认证的默认配置是 http://127.0.0.1:8991/mqtt/auth，请求方式可选 post 或 get——post 更安全；请求参数有三个：clientid、username、password。本方案的判断只依赖 clientid。改完后的三段配置合在一起看（默认地址注释掉，两个井号是这条配置文件的注释符号）：

```ini
# ---- 第一段：连接认证 ----
auth.http.auth_req = http://192.168.200.1:9007/vm-service/acl/auth
auth.http.auth_req_method = post
auth.http.auth_req_param = clientid=%c,username=%u,password=%P

# ---- 第二段：超级用户判断 ----
auth.http.super_req = http://192.168.200.1:9007/vm-service/acl/superuser
auth.http.super_req_method = post
auth.http.super_req_param = clientid=%c,username=%u

# ---- 第三段：发布订阅控制 ----
auth.http.acl_req = http://192.168.200.1:9007/vm-service/acl/pubsub
auth.http.acl_req_method = post
```

地址里的 192.168.200.1 是本机地址（EMQX 跑在 192.168.200.128 那台虚拟机的容器里），9007 是网关端口——认证请求要穿过网关转发到 vm-service。参数里的占位符：%c 会被替换成客户端 clientid，%u 是用户名，%P 是明文密码。

再到售货机微服务里新建 AclController。类上标 @RestController、@RequestMapping("/acl")，注入用构造器方式（lombok 注解加 final 修饰，省掉 @Autowired），日志用 @Slf4j：

```java
@RestController
@RequestMapping("/acl")
@RequiredArgsConstructor
@Slf4j
public class AclController {

    private final VMService vmService;

    // 连接认证：判断当前客户端能否建立连接
    @PostMapping("/auth")
    public ResponseEntity<?> auth(@RequestParam(value = "clientid", defaultValue = "") String clientid,
                                  @RequestParam(value = "username", defaultValue = "") String username,
                                  @RequestParam(value = "password", defaultValue = "") String password) {
        // clientid 为空：400，未通过认证
        if (Strings.isNullOrEmpty(clientid)) {
            return new ResponseEntity<>(null, HttpStatus.BAD_REQUEST);
        }
        // 特权一：websocket 工具等测试客户端，mqtt 开头一律放行
        if (clientid.startsWith("mqtt")) {
            return new ResponseEntity<>(null, HttpStatus.OK);
        }
        // 特权二：所有微服务的连接，monitor 开头一律放行
        if (clientid.startsWith("monitor")) {
            return new ResponseEntity<>(null, HttpStatus.OK);
        }
        // 剩下的可能是互联网终端（一台售货机）：到售货机表里核实
        var qw = new LambdaQueryWrapper<VendingMachineEntity>();
        qw.eq(VendingMachineEntity::getClientId, clientid);
        VendingMachineEntity vm = vmService.getOne(qw);
        if (vm == null) {
            return new ResponseEntity<>(null, HttpStatus.BAD_REQUEST);
        }
        log.info("客户端连接认证 clientid: {} ok", clientid);
        return new ResponseEntity<>(null, HttpStatus.OK);
    }
}
```

username、password 虽然接收了但用不上——判断只看 clientid。返回值约定很直白：ResponseEntity 的状态码 400（BAD_REQUEST）等于「否」，没通过认证；200（OK）等于「通过」。Controller 里 @PostMapping 用了 post，配置文件里 method 也必须是 post，两边要对齐。

配置保存后进入 emqx 的 bin 目录执行 emqx restart，配置才生效。还有一步不能漏：请求要经网关转发，而网关本身加了鉴权，必须把 vm-service/acl/auth 加进网关配置的忽略认证地址列表，否则 EMQX 的认证请求过不了网关这一关。

启动顺序有个「先有鸡还是先有蛋」的坑：插件开着时启动售货机微服务，它启动时要连 EMQX，EMQX 又要通过网关回调 vm-service 认证——此时网关没起、服务也在启动中，回调地址不可用，认证必然失败，服务就一直卡着起不来。正确顺序：先停插件 → 启动售货机微服务 → 启动网关 → 再开启插件。

测试用 EMQX 自带的 websocket 工具，三步验证：

1. clientid 用 mqtt 开头，连接成功，控制台打出「客户端连接认证 clientid ok」，证明请求经过了 AclController；
2. 随便写一个 clientid，连接被拒，提示 bad username or password——这次走的是查库分支，售货机表里没有这个 id；
3. 从数据库 vm 表里复制一个真实存在的 clientid（比如 3775 开头），连接成功。

## 超级用户判断与发布订阅控制

超级用户判断的配置在 emqx_auth_http.conf 第二段：一个请求地址、请求方法（post）、两个参数 clientid 和 username。对应代码同样加在 AclController：

```java
// 超级用户判断：通过后跳过后续的发布订阅控制，相当于王牌
@PostMapping("/superuser")
public ResponseEntity<?> superuser(@RequestParam(value = "clientid", defaultValue = "") String clientid,
                                   @RequestParam(value = "username", defaultValue = "") String username) {
    if (clientid.startsWith("mqtt")) {
        log.info(clientid + "是超级用户");
        return new ResponseEntity<>(null, HttpStatus.OK);
    }
    if (clientid.startsWith("monitor")) {
        log.info(clientid + "是监控用户");
        return new ResponseEntity<>(null, HttpStatus.OK);
    }
    log.info(clientid + "不是超级用户");
    return new ResponseEntity<>(null, HttpStatus.BAD_REQUEST);
}
```

逻辑和连接认证的特权部分一致：mqtt、monitor 开头的直接判为超级用户。配置文件里把 super_req 指到 http://192.168.200.1:9007/vm-service/acl/superuser、方法改 post，网关忽略列表加上 vm-service/acl/superuser，重启流程照旧（先停插件、起服务、开插件）。

测试同样三步：mqtt 开头的 clientid 连接后，控制台先打出连接认证、再打出「是超级用户」——超级用户通过后，后续发布订阅的 ACL 全部跳过；在 mqtt 前面加一个字母，它既不是特权前缀、库里也没有，第一步连接认证就不过，自然到不了超级用户这一层；用数据库里真实的 clientid 连接，能通过连接认证，但不是超级用户——这正是每台真实售货机的常态：它们要受到发布订阅 ACL 的约束，只能发布或订阅被允许的主题，安全控制就落在这里。

发布订阅控制是配置文件的第三段。参数定义了很多（access、clientid、username、ipaddr、topic、mountpoint 等），本方案实际只接收三个必须用的：access（类型，1 代表订阅，2 代表发布）、clientid、topic。

```java
// 发布订阅控制：普通售货机只能发自己的 server 主题、订自己的 vm 主题
@PostMapping("/pubsub")
public ResponseEntity<?> pubsub(@RequestParam(value = "clientid", defaultValue = "") String clientid,
                                @RequestParam(value = "access") int access,
                                @RequestParam(value = "topic", defaultValue = "") String topic) {
    log.info("ACL 发布订阅控制 clientid:" + clientid + " access:" + access + " topic:" + topic);
    if (Strings.isNullOrEmpty(clientid)) {
        return new ResponseEntity<>(null, HttpStatus.BAD_REQUEST);
    }
    var qw = new LambdaQueryWrapper<VendingMachineEntity>();
    qw.eq(VendingMachineEntity::getClientId, clientid);
    VendingMachineEntity vm = vmService.getOne(qw);
    if (vm == null) {
        return new ResponseEntity<>(null, HttpStatus.BAD_REQUEST);
    }
    // access=2 发布：只允许 server + 自己的售货机编号
    if (access == 2 && topic.equals("server" + vm.getInnerCode())) {
        return new ResponseEntity<>(null, HttpStatus.OK);
    }
    // access=1 订阅：只允许 vm + 自己的售货机编号
    if (access == 1 && topic.equals("vm" + vm.getInnerCode())) {
        return new ResponseEntity<>(null, HttpStatus.OK);
    }
    log.info(clientid + "不能发布订阅消息");
    return new ResponseEntity<>(null, HttpStatus.BAD_REQUEST);
}
```

方法里先做非空判断，再查库确认 clientid 是真实设备——理论上走到这一步的请求必然已经通过了连接认证，查不到的情况极少。access 用 int 接收，判断起来比字符串方便。配置文件里把 acl_req 指到 http://192.168.200.1:9007/vm-service/acl/pubsub、方法 post（多出来的参数 EMQX 侧照传，Controller 不接收也没关系），网关忽略列表加 vm-service/acl/pubsub，重启生效。

测试覆盖四种情况：mqtt 开头的超级用户随便发一个主题都能发出去，而且控制台没有任何 pubsub 方法的日志——超级用户根本不经过这段控制；换成数据库里真实的 clientid 随便发消息，websocket 工具上显示发送正常，但对方收不到，控制台打出「不能发布订阅消息」——消息被判定为无效；随便订阅一个主题，订阅直接报错；订阅 vm 加上自己的售货机编号，订阅成功，主题差一点都不行。发布同理，只有 server 加自己编号的主题才是合法目标。

## 小结

ACL 的完整链路是：EMQX 暴露公网后，用 emqx_auth_http 插件把连接认证、超级用户判断、发布订阅控制三个时点的判断请求全部转给售货机微服务的 AclController；clientid 是否真实存在于售货机表，是贯穿三段的判断基准。鉴权链和缓存是 EMQX 提供的两个调节器——前者决定多套规则怎么组合，后者决定查库频率。工程上最容易被忽视的反而是联调细节：配置要 emqx restart 才生效、回调地址要进网关白名单、插件和服务要按先停后起的顺序启动。三段代码都不长，但把「设备是谁、能干什么」这两个问题在消息入口处就回答干净了。
