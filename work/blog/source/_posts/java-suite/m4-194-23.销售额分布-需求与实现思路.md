# 销售额分布：需求思路与 Elasticsearch 区域聚合两段实现

第八章统计分析推进到第六小节"销售额分布"。上一节销售额趋势图沿时间轴看走势，这一节换一个维度：按运营区域看对比。管理后台用柱状图把每个运营区域的销售额放在一起，哪个区域卖得好、哪个区域拖后腿一目了然，为后续经营决策提供依据。本节代码分两段：前半段构建 Elasticsearch 聚合查询，后半段执行查询并把结果封装成柱状图数据。

## 先给结论

- 需求：管理后台按月、年等时间维度查看销售额的区域分布，前端柱状图展示；区域太多展示效果就差，所以先按销售额降序排，只显示销售额最高的 30 个区域。
- 数据源换了：订单汇总表里没有记录运营区域，按区域聚合走不通；改用 Elasticsearch 的订单库统计，比直接对 MySQL 原始订单表聚合效率高得多。
- 接口只有开始日期、截止日期两个参数，没有趋势图那种统计类型参数：不管时间段怎么切，聚合维度始终是区域，传起止日期就够。
- 查询条件两个 filter：create_time 落在 gte(start) 到 lte(end) 区间内，pay_status 为已支付（VmSystem.PAY_STATUS_PAID），已支付的订单才有必要统计。
- 聚合三件套：terms 按 region_name 分组，sum 子聚合对 amount 求和（别名 amount_sum），BucketOrder 按汇总值倒序、size(30) 只留前 30 桶；sourceBuilder.size(0) 不取记录只取聚合，提高效率。
- 结果提取走 ParsedStringTerms、getBuckets、forEach：getKeyAsString 当 X 轴区域名，amount_sum 的 getValue 取整数部分放进 seriesList；Controller 只做一层转发。

## 一、需求与实现思路：为什么换 ES

需求本身很直白：管理后台有一张销售额分布图，把每个运营区域的销售额放在一张柱状图里对比，直观看到哪个区域销售高、哪个区域低，给后续经营决策提供依据。前提是区域不能太多——区域一多柱状图就没法看了，所以按销售额排序之后只显示前 30 个区域的数据。

实现思路的关键在数据源的选择。做销售额趋势图时，直接对订单合并表聚合统计就行；但订单合并表里没有记录运营区域，按区域分组这条聚合路径走不通。改用 Elasticsearch 的订单库来统计：如果对 MySQL 的原始订单表做聚合，效率比较低，ES 天然擅长这类分组聚合，统计效率高得多。

接口设计上有个反直觉的点。销售额趋势图的接口带一个统计类型参数，用来区分按日统计还是按月统计；这里接口文档里"管理后台-工作台-根据地区汇总销售额数据（销售额分布）"这条 API 只有开始日期和截止日期。细想就通了：趋势图的聚合维度随时间类型变化，而分布图不管你按什么时间段查——一周、一月还是一年——聚合维度都是区域，时间只是过滤条件，起止日期两个参数足够。返回数据沿用柱状图、曲线图的封装对象 BarChartCollect，区域名进 X 轴，销售额进数值序列。

## 二、代码实现上半场：查询条件与聚合构建

接口方法定义在订单微服务的 ReportService 中，返回 BarChartCollect，方法名 getCollectByRegion，按区域统计：

```java
BarChartCollect getCollectByRegion(LocalDate start, LocalDate end);
```

实现在 ReportServiceImpl 里，前半部分分四步。

先建查询骨架。SearchRequest 是查询请求对象，要查的索引是订单库 order；SearchSourceBuilder 承载查询与聚合的构建；BoolQueryBuilder 是布尔查询构建器，条件往里装：

```java
SearchRequest searchRequest = new SearchRequest("order");
SearchSourceBuilder sourceBuilder = new SearchSourceBuilder();
BoolQueryBuilder boolQueryBuilder = QueryBuilders.boolQuery();
```

再装两个 filter 条件。第一个是日期区间，rangeQuery 对 create_time 做 gte 大于等于 start、lte 小于等于 end，时间条件就加上了；第二个是支付状态，termQuery 限定 pay_status 为已支付，只有已支付的订单才有必要统计：

```java
boolQueryBuilder.filter(QueryBuilders.rangeQuery("create_time").gte(start).lte(end));
boolQueryBuilder.filter(QueryBuilders.termQuery("pay_status", VmSystem.PAY_STATUS_PAID));
sourceBuilder.query(boolQueryBuilder);
sourceBuilder.size(0);
```

sourceBuilder.size(0) 是一个容易被忽略的细节：这次查询的目的不是取记录，而是聚合统计，把返回文档数设为 0，省掉查询具体数据的开销，效率更高。

然后构建聚合。AggregationBuilders.terms 先起一个自定义的分组名 region，field 指定按区域名称分组；里面嵌套一个 sum 子聚合，别名 amount_sum，聚合字段是 amount——这个别名相当于给聚合结果起的名字，相当于一次 sum 函数调用，后面提取时要靠它。排序用 BucketOrder.aggregation("amount_sum", false)，按统计结果排，false 是倒序（true 才是升序），最后 size(30) 只取聚合结果的前 30 条。注意这个 size 和上面的 size(0) 含义不同：上面管的是返回多少条文档，这里管的是聚合结果保留多少个桶：

```java
AggregationBuilder regionAgg = AggregationBuilders.terms("region")
        .field("region_name")
        .subAggregation(AggregationBuilders.sum("amount_sum").field("amount"))
        .order(BucketOrder.aggregation("amount_sum", false))
        .size(30);

sourceBuilder.aggregation(regionAgg);
searchRequest.source(sourceBuilder);
```

聚合装进 sourceBuilder，sourceBuilder 再装进 searchRequest，前半部分完成。

## 三、代码实现下半场：执行查询、提取结果与测试

后半部分要用 ES 客户端执行查询。注入 RestHighLevelClient：声明为 private final，不再写 @Autowired——Lombok 的 @RequiredArgsConstructor 会自动生成构造器，final 字段随构造器注入：

```java
private final RestHighLevelClient esClient;
```

执行查询、提取结果、封装返回值：

```java
BarChartCollect result = new BarChartCollect();
try {
    SearchResponse searchResponse = esClient.search(searchRequest, RequestOptions.DEFAULT);
    Aggregations aggregations = searchResponse.getAggregations();
    if (aggregations == null) return result;
    ParsedStringTerms term = aggregations.get("region");
    var buckets = term.getBuckets();
    if (buckets.size() <= 0) return result;
    buckets.stream().forEach(b -> {
        result.getXAxisList().add(b.getKeyAsString());
        ParsedSum sumAgg = b.getAggregations().get("amount_sum");
        Double value = sumAgg.getValue();
        result.getSeriesList().add(value.intValue()); // 取整数部分
    });
} catch (IOException e) {
    log.error("根据区域汇总数据出错", e);
}
return result;
```

几个提取要点。记录集部分不用取——前面 size(0)，也取不到，只取分组结果：searchResponse.getAggregations() 拿到 Aggregations，为 null 直接返回 result。aggregations.get("region") 按名称提取分组结果，这个名称必须与定义聚合时的分组名一致；类型转成 ParsedStringTerms，getBuckets 得到桶集合，size 小于等于 0 同样直接返回。有数据就走 stream().forEach 循环每个桶 b：X 轴部分调 getKeyAsString 取出区域名，加进 X 轴数据；数值部分从 b.getAggregations() 里按别名 amount_sum 提取，转成 ParsedSum 类型接收，getValue 得到的是 double 值，用 intValue 取整数部分放进数据序列。查询出错时在 catch 里 log.error 打一条"根据区域汇总数据出错"。

Controller 这一步很简单：把 ReportController 里既有接口的实现拿过来改，直接接收开始日期和截止日期两个参数，调用 reportService.getCollectByRegion 返回即可。

测试流程。启动订单微服务——代码直接对微服务调用，没有经过网关，所以不需要启动网关。服务起来后打开测试脚本"销售和区域分布分析"，这个脚本按刚才的方法编写，统计的是 2021 年整年的数据。测试数据比较少，当前库里只有一条城北街道的数据，图上就展示出一根柱子的数据格式，但整个聚合链路的逻辑是正确的。接口测试完成，销售额分布的功能开发加测试到此收尾。

## 小结

把本篇串起来：需求按区域对比销售额、只留前 30 个区域；数据源从订单合并表换成 ES 订单库，原因就是合并表里没有运营区域字段，而 MySQL 原始订单表聚合效率低；接口只收起止日期两个参数，因为聚合维度恒为区域，时间只是过滤条件；代码前半段 SearchRequest 指定 order 索引，两个 filter 锁定时间区间与已支付状态，terms、sum、BucketOrder、size(30) 完成区域分组求和倒序取前 30，size(0) 省掉文档返回；后半段 RestHighLevelClient 执行 search，ParsedStringTerms 提桶、getKeyAsString 填 X 轴、按 amount_sum 别名取 ParsedSum 的值取整填序列，异常打"根据区域汇总数据出错"；Controller 一层转发，测试脚本按 2021 整年直连订单微服务验证，单条城北街道数据出一根柱子，链路正确。到这里，销售额分布的功能开发与测试都已完成。销售额趋势图沿时间轴看走势，销售额分布按区域横向对比，一纵一横两个视角放在一起，后续的经营决策就有了数据抓手。
