# 售货机端商品与货道数据同步：需求思路、版本信息上报、接收保存、联调测试与商品价格同步

售货机是一台脱离后台界面运行的设备，它卖哪些商品、货道里摆着什么，完全取决于本地数据库里那份"商品 + 货道"配置。这份配置怎么来、怎么保持最新，就是第九章售货机"五脏六腑"里数据同步这一节要解决的问题：售货机端启动时上报本地版本号，服务端比对后决定是否下发最新配置，售货机端先清空再全量插入完成落地，最后联调验证。商品价格变动的推送同步因为实现方式相近，讲完思路留作课后练习。

## 先给结论

- 数据同步分两块：商品与货道数据同步、商品价格变动通知；本篇先走通前者，价格同步讲思路
- 核心机制是版本号：售货机本地维护 tb_version 表，启动时把商品版本、货道版本以 versionCfg 协议上报，服务端比对后决定是否下发
- 服务端下发走两条协议：skuCfg（商品列表）与 channelCfg（货道列表），都携带 versionId 告知售货机最新版本
- 售货机端收到配置采用"先清空、再全量插入"策略，多表操作封装在 @Transactional 的 DataProcessService 里
- 联调用设备 01000001 验证：启动后自动拉取配置，H2 中 tb_sku、tb_channel 落数据，tb_version 版本从 0 变 1
- 价格同步区别于全量替换：按 skuId 逐条 update 价格字段并更新价格版本，代码留作课后完成

## 一、需求与协议：启动上报版本，按版本决定下发

需求分两种场景。第一种：第一次部署售货机时，本地数据是空的，要求售货机在启动的时候能自动获取服务器的最新数据，并保存到本地。第二种：服务端数据发生了变化，但没有及时通知到售货机，这时售货机里是旧数据——解决办法是售货机在每次启动时，把当前的版本信息报送给服务端；服务端接到版本信息后判断这台售货机是不是最新的，是最新的就不处理，不是最新的就把最新的商品数据和货道数据下发给对应的售货机。一个请求、一个下载，流程就这么闭合。

四个协议msgType的分工如下：

| msgType | 方向 | 作用 | 关键数据 |
| --- | --- | --- | --- |
| versionCfg | 售货机 → 服务端 | 上报本地版本 | skucfgVersion、channelCfg 两个版本号 |
| skuCfg | 服务端 → 售货机 | 下发商品配置 | versionId + skus 商品列表 |
| channelCfg | 服务端 → 售货机 | 下发货道配置 | versionId + channels 货道列表 |
| skuPrice | 服务端 → 售货机 | 下发价格变动 | versionId + skuPrice 价格列表 |

售货机启动时发送的请求协议：

```json
{
  "msgType": "versionCfg",
  "sn": 342424343,
  "innerCode": "01000001",
  "needResp": false,
  "data": {
    "skucfgVersion": 0,
    "channelCfg": 0
  }
}
```

第一次出车时两个版本都是 0，之后就是大于 0 的数字。服务端判断不是最新时，以 skuCfg 下发商品信息（有多少商品下发多少条），价格以分为单位：

```json
{
  "msgType": "skuCfg",
  "sn": 342424343,
  "vmId": "01000001",
  "needResp": true,
  "versionId": 1,
  "skus": [
    {
      "skuId": 123,
      "skuName": "可口可乐",
      "image": "http://a.jpg",
      "price": 500,
      "realPrice": 400,
      "classId": 1,
      "className": "饮料",
      "discount": false,
      "unit": "330ml",
      "index": 1
    }
  ]
}
```

货道同理，channelCfg 携带 versionId 和货道列表：

```json
{
  "msgType": "channelCfg",
  "sn": 342424343,
  "vmId": "01000001",
  "needResp": true,
  "versionId": 1,
  "channels": [
    {
      "channelId": "1-1",
      "skuId": 1,
      "capacity": 10
    }
  ]
}
```

设备端收到消息后的处理策略是：把本地数据清掉，根据下发数据重新写入，同时把下发携带的版本号同步写进版本表。落到实现上是四步：售货机启动后连接 EMQ 服务器，读取本地 tb_version 表发送给服务器；在 EmqMsgCallback 的 messageArrived 方法中监听服务器返回信息；同步货道时先删除 tb_channel 旧数据再插入新数据，并修改 tb_version 中的货道版本；同步商品时直接删除 tb_sku 旧数据、插入新数据，并修改 tb_version 中的商品版本。

## 二、向服务器发送版本信息：connectComplete 里发起

协议对应的封装类有两个，都在 emq 的 msg 包下。售货机端发给服务端的协议体统一以 REQ 结尾，版本请求就是 VersionReq，它继承 BaseData，构造函数里直接把 msgType 设成 versionCfg；data 属性是 VersionReqData，装两个版本号：

```java
@Data
public class VersionReq extends BaseData {
    private VersionReqData data = new VersionReqData();
    public VersionReq() {
        this.setMsgType(MsgType.versionCfg.getType());
    }
}

@Data
public class VersionReqData {
    private long skucfgVersion = 0;
    private long channelCfg = 0;
}
```

发送时机放在 EMQ 消息回调类 EmqMsgCallback 的 connectComplete 方法里——这是连接成功的回调，原来只做了订阅主题，现在订阅之后紧接着发送版本信息。版本表只有一条记录且主键为 1，所以 versionMapper.selectById(1) 直接查到版本对象，它就是要发送内容的来源。封装时四个关键点：innerCode 是售货机编号，从配置文件 config 中取出；sn 相当于流水号，用 System.nanoTime() 纳秒值保证唯一性；channelCfg 与 skucfgVersion 分别从版本对象里取；最后用 fastjson 的 JSON.toJSONString 转成 JSON 字符串，通过 emqClient.publish 发出去，msgType 用枚举 MsgType.versionCfg.getType() 取值：

```java
@Override
public void connectComplete(boolean connectComplete, String s) {
    // 订阅服务端Topic
    log.info("connectComplete subscribe {}", config.getSubscribeTopic());
    emqClient.subscribe(config.getSubscribeTopic(), callback);
    // 发送版本信息
    Version version = versionMapper.selectById(1);
    VersionReq versionReq = new VersionReq();
    versionReq.setInnerCode(config.getInnerCode());
    versionReq.setSn(System.nanoTime());
    versionReq.setChannelCfg(version.getChannelVersion());
    versionReq.setSkucfgVersion(version.getSkucfgVersion());
    String msg = JSON.toJSONString(versionReq);
    log.info("请求版本信息 {}", msg);
    emqClient.publish(MsgType.versionCfg.getType(), msg);
}
```

## 三、接收与保存：先清空再插入，事务兜底

接收保存涉及对多张表的操作，所以单独抽一个业务逻辑类。service 包下定义接口 DataProcessService，两个方法分别处理服务端同步商品与同步货道，入参就是两个响应对象 SkuResp 和 ChannelResp：

```java
public interface DataProcessService {
    // 处理服务端同步商品信息
    void syncSku(SkuResp skuResp);
    // 处理服务端同步货道信息
    void syncChannel(ChannelResp channelResp);
}
```

实现类 DataProcessServiceImpl 上加三个注解：@Service 注册为 Spring Bean，@Slf4j 出日志，@Transactional 开事务——因为这两个方法必定要对多张表进行操作。

syncSku 的逻辑分三段。先做防御判断：skus 既不能是 null 也不能是空集合，条件成立才处理。第一步清空本地数据，调 skuMapper.deleteAllSkus()——这是在 Mapper 里扩展的方法，直接清空整张表，而不是逐条 delete，执行效率更高，但这类操作不能回滚。第二步循环 skus 集合，new 一个 Sku 对象，用 BeanUtils.copyProperties 从响应数据拷贝属性，再 insert 插入。第三步更新版本：selectById(1) 取出版本记录，把响应里的 versionId（服务端返回的最新版本）set 到 skuVersion，updateById 存回去：

```java
@Override
public void syncSku(SkuResp skuResp) {
    if (skuResp.getSkus() != null && !skuResp.getSkus().isEmpty()) {
        // 清空本地商品表
        skuMapper.deleteAllSkus();
        skuResp.getSkus().forEach(skuData -> {
            Sku sku = new Sku();
            BeanUtils.copyProperties(skuData, sku);
            skuMapper.insert(sku);
        });
        // 更新版本
        Version version = versionMapper.selectById(1);
        version.setSkuVersion(skuResp.getVersionId());
        versionMapper.updateById(version);
    }
}
```

syncChannel 的思路与它完全相同：注入 ChannelMapper，先 channelMapper.deleteAllChannels() 清空货道表，循环拷贝插入，最后 version.setChannelVersion(channelResp.getVersionId()) 回写货道版本，不再赘述。

业务方法写完，回到回调类 messageArrived 里接入。消息返回来先经过这个方法，这里要判断收到的协议类型是商品的还是货道的。用 msgType 与 MsgType.skuCfg.getType() 做忽略大小写的匹配，命中就是商品同步：用 fastjson 的 JSON.parseObject 把报文按 SkuResp 类型解析成对象，注入 DataProcessService 后调用 syncSku，打一条"同步商品信息"日志。货道同理，匹配 MsgType.channelCfg.getType()，按 ChannelResp 解析后调 syncChannel，日志"同步货道信息"：

```java
String msgType = JSONPath.read(payload, "$.msgType").toString();
if (msgType.equalsIgnoreCase(MsgType.skuCfg.getType())) {
    log.info("同步商品信息");
    SkuResp skuResp = JSON.parseObject(payload, SkuResp.class);
    dataProcessService.syncSku(skuResp);
}
if (msgType.equalsIgnoreCase(MsgType.channelCfg.getType())) {
    log.info("同步货道信息");
    ChannelResp channelResp = JSON.parseObject(payload, ChannelResp.class);
    dataProcessService.syncChannel(channelResp);
}
```

## 四、联调测试与商品价格同步

### 联调：01000001 从空库到版本变 1

先看数据底子：当前配置的设备编号是 01000001，服务端数据库里有这台设备，货道表里也对它做了货道配置，货道关联的商品信息自然能获取到，用它测试没有问题。EMQ 服务已开启，先启动服务端——只开售货机微服务即可，网关不用开。服务端负责通信的是 business 包下 msgHandler 里的 VersionCfgMsgHandler：售货机端启动发出的 versionCfg 请求正好被它接收，process 方法解析报文后按 innerCode 查询服务端版本信息，逐项比较版本号——商品版本、价格版本、货道版本任何一个小于服务端最新版本，就把对应的配置数据通过 MQTT 下发出去，商品配置里自然带着价格。

再启动客户端（售货机端），观察控制台输出：先是初始化，然后订阅主题，接着请求版本信息，随后服务端的数据抓过来了——返回的商品数据、货道数据依次到达，控制台打出"同步商品数据""同步货道数据"，最后是一系列更新操作，数据保存完成。

打开 H2 Console（jdbc:h2:mem://localhost，用户名 root、密码 test）验证：查商品表，数据已经同步过来；查货道表，也已同步；再看版本表，商品版本和货道版本都从原来的 0 变成了 1，价格版本没有变化——与预期完全一致，商品与货道同步的测试完成。

### 价格同步：更新而非替换

价格同步的时机是商品价格变动时，由服务端将价格推送给对应的售货机。最常见的价格变动来自策略设置：对某台售货机做策略调整，9 折变 8 折、7 折再变回 9 折，折后价一变商品价格跟着变，这种变化必须实时通知到售货机做变更。

协议是商品价格变动协议 skuPrice，versionId 是商品价格配置版本号，skuPrice 数组里每一项包含 skuId（哪个商品）、price（原价，分为单位）、realPrice（真实售价，分为单位）、discount（是否打折促销）：

```json
{
  "msgType": "skuPrice",
  "sn": "342424343",
  "innerCode": "8012121",
  "needResp": true,
  "versionId": 1,
  "skuPrice": [
    {
      "skuId": 1,
      "price": 500,
      "realPrice": 480,
      "discount": true
    }
  ]
}
```

实现步骤：先封装 SkuPriceData（对应数组里每一项的字段）和 SkuPriceResp（响应对象，skuPrice 是 SkuPriceData 的集合）；在 DataProcessService 中新增方法定义 syncSkuPrices，实现类里做价格修改。注意它与商品、货道的"全删重插"不同——价格变动做的是更新操作：循环发过来的列表，对每一个商品用 UpdateWrapper 按商品 ID 更新真实价格、价格和折扣三个字段，最后更新版本表的 skuPriceVersion。回调处再判断协议类型，是商品价格变动的协议时调用这段逻辑即可：

```java
public void syncSkuPrices(SkuPriceResp skuPriceResp) {
    if (skuPriceResp.getSkuPrice() != null && !skuPriceResp.getSkuPrice().isEmpty()) {
        skuPriceResp.getSkuPrice().forEach(skuPriceData -> {
            UpdateWrapper<Sku> ew = new UpdateWrapper<>();
            ew.lambda().set(Sku::getRealPrice, skuPriceData.getRealPrice())
                .set(Sku::getPrice, skuPriceData.getPrice())
                .set(Sku::getDiscount, skuPriceData.isDiscount())
                .eq(Sku::getSkuId, skuPriceData.getSkuId());
            this.skuMapper.update(null, ew);
        });
        Version version = versionMapper.selectById(1);
        version.setSkuPriceVersion(skuPriceResp.getVersionId());
        versionMapper.updateById(version);
    }
}
```

这部分代码课后完成，实现方式和上面的商品货道同步基本一致。

## 小结

把整条链路串起来：需求是两个场景——首次部署本地空库要自动拉取、版本落后要重新下发；售货机端在 connectComplete 里读 tb_version（selectById(1)），封装 VersionReq（innerCode 取配置、sn 用纳秒流水号）上报版本；服务端 VersionCfgMsgHandler 比对版本后以 skuCfg、channelCfg 下发商品与货道全量配置；售货机端在 messageArrived 里按忽略大小写的 msgType 分流，DataProcessService 用"先清空再插入"落地并回写版本；联调设备 01000001 验证 tb_sku、tb_channel 落数据、版本 0 变 1。价格同步则换了一种更新姿势：不删数据，按 skuId 逐条 update 价格字段，版本记到 skuPriceVersion，留作课后实现。版本号贯穿始终，它是两端判断"数据新旧"的唯一依据。
