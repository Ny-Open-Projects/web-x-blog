# 智牛股权限接口实战：角色权限四接口、Spring Data REST 高级用法与 Swagger2 启动器

上一章搭好后台管理工程和实体，这一章进入权限模块真正的核心：权限核心逻辑接口实现。复杂权限逻辑用 Spring Data REST 不便处理，要再包一层，由 Spring Boot Controller 提供接口、Service 处理具体逻辑；相对简单的跨表查询仍然交给 Spring Data REST，配合 HQL 和 QueryDSL。最后用自定义 starter 把 Swagger2 封装成可复用组件，为接口文档铺路。

## 先给结论

- 复杂权限逻辑在 Spring Data REST 之上再包一层：Controller 暴露接口、Service 写具体逻辑，两套接口就此互补。
- 保存角色权限接口支持批量：roleAuth 以逗号分隔，M 开头是菜单 ID、O 开头是操作 ID；先删原有关联再存新数据，删除要从最末级的角色操作关联开始。
- 权限数据入库前先去重：前端数据不保证百分之百正确，用 Stream distinct 过滤，同时保证接口处理逻辑简洁。
- 分配用户与角色前必须校验：一个用户可以拥有不同运营身份的角色，但不能拥有相同机构类型的两个角色，违反就抛 ADMIN_USER_INSTITUTION_UNIQUE。
- 按角色查菜单、查菜单操作用 HQL 跨表查询，方法定义在返回实体对应的 Repository 上；权限数据量小且服务于权限判断，不做分页。
- Spring Data REST 三个高级配置：级联映射显示父菜单（VO 不能进 REST 映射）、exposeIdsFor 暴露 ID、QueryDSL 动态条件查询；Swagger2 原生不支持 Spring Data REST，用自定义 starter 封装改造。

## 保存角色权限：外层批量入口与内层解析落库

角色就是由不同权限组合形成的，每个角色有自己的菜单与操作权限，通过后台管理配置。保存角色权限的接口要完成角色和菜单、操作权限信息的关联处理，支持批量：实现一个角色的关联保存，多个角色在外层循环即可。

```java
@Transactional(rollbackFor = Exception.class)
public void savePrivileges(String roleAuth, String... roleIds) {
    log.info("Process in AuthorityLogicServiceImpl.savePrivileges method params, roleAuth: " + roleAuth + ", roleIds: " + Arrays.toString(roleIds));
    // 1. 保存多个角色的权限信息，支持批量方式处理（参数由前端传递）
    for (String roleId : roleIds) {
        // 2. 将roleId信息转换，校验角色信息是否存在
        Long roleIdLong = Long.valueOf(roleId);
        Optional<AuthorityRole> authorityRoleOpt = authorityRoleRepository.findById(roleIdLong);
        if (!authorityRoleOpt.isPresent()) {
            throw new BusinessException(ApplicationErrorCodeEnum.USER_ROLE_NOT_FOUND);
        }
        // 3. 保存角色与权限的关联关系
        saveRolePrivileges(roleIdLong, roleAuth);
    }
}
```

方法上加 @Transactional(rollbackFor = Exception.class)，因为采用 JPA 做数据层操作，JPA 依赖事务才能工作；rollbackFor 标示为所有异常，抛异常时回滚。参数格式要约定清楚：roleAuth 是逗号拼接的字符串，M 开头代表菜单（如 M1001），O 开头代表操作（如 O20001）；roleIds 是数组（如 1001、10002），由此支持多个角色的权限分配。日志用 Lombok 的 @Slf4j 打印入参。

内层私有方法 saveRolePrivileges 负责解析和落库：

```java
private void saveRolePrivileges(Long roleId, String roleAuth) {
    log.info("Process in AuthorityLogicServiceImpl.saveRolePrivileges method. roleId: " + roleId + ", roleAuth: " + roleAuth);
    // 1. 过滤roleAuth参数，以M开头的是菜单ID，以O开头的是操作ID，逗号分隔
    String[] roleAuthArr = roleAuth.replace(" ", "").trim().split(",");
    // 2. 对权限参数信息去重处理
    List<String> roleAuthList = Stream.of(roleAuthArr).distinct().collect(Collectors.toList());
    // 3. 先删除角色原有的菜单和操作权限信息
    authorityRoleOperationRepository.deleteAllByRoleId(roleId);
    authorityRoleMenuRepository.deleteAllByRoleId(roleId);
    // 4. 遍历权限信息，逐个保存
    for (String id : roleAuthList) {
        if (id.contains(MENU_OPT_FLAG)) {
            authorityRoleOperation.setOperationId(Long.parseLong(id.replace(MENU_OPT_FLAG, "").trim()));
            authorityRoleOperation.setRoleId(roleId);
            authorityRoleOperationRepository.save(authorityRoleOperation);
        } else if (id.contains(MENU_FLAG)) {
            authorityRoleMenu.setMenuId(Long.parseLong(id.replace(MENU_FLAG, "").trim()));
            authorityRoleMenu.setRoleId(roleId);
            authorityRoleMenuRepository.save(authorityRoleMenu);
        } else {
            log.warn("unknown menu opt id: " + id);
        }
    }
}
```

几个设计点值得注意。去重是因为不能保证前端传递的数据百分之百正确，重复勾选或前端没控制严格，后台做 distinct 过滤，也保证接口处理逻辑的简洁性。先删后存比跟原有数据比对再添加更直接简单，比对后添加操作麻烦且不易保证数据正确性：先清除原有的操作和菜单，再按新传递的数据保存。删除顺序上，关联的数据放在前面处理，所以先删最末级的角色操作关联数据，避免关联产生的数据问题；deleteAllByRoleId 是自定义 SQL 实现的删除方法，相当于批量删除，没有特殊需求用普通增删改查接口即可。两个常量 public final static String MENU_OPT_FLAG = "O"、MENU_FLAG = "M" 承担类型判断；实体对象定义在循环外，每次循环不用再创建引用，节省资源开销。两类数据最终分别保存到角色和操作关联表、角色和菜单关联表。

Controller 层的 AuthorityLogicController 注入 service、加 @RestController 并定义请求路径 authorityLogic。service 用 IDEA 的 Refactor → Extract → Interface 抽取接口，接口名以 I 开头，实现类移到 implement 子包。

## 分配用户角色与按角色查权限

有了角色权限接口，就可以把角色分配给用户，用户和角色是多对多。userAssignRoles 接收 AuthorityUserRole 和 AuthorityUser 两个参数，实现分五步：查询用户已分配的角色信息、获取需要分配的角色详情、校验、组装关联数据、保存。

```java
// 1. 查询用户已分配的角色信息
List<AuthorityUserRole> authorityUserRoleList = authorityUserRoleRepository.findByUserId(authorityUserRole.getUserId());
// 2. 获取需要分配的角色详情
AuthorityRole authorityRole = authorityRoleRepository.findById(authorityUserRole.getRoleId());
// 3. 校验用户是否存在多个相同机构类型的角色
for (AuthorityUserRole userRole : authorityUserRoleList) {
    if (userRole.getInstitutionTypeId().equals(authorityRole.getInstitutionTypeId())) {
        throw new ComponentException(ApplicationErrorCodeEnum.ADMIN_USER_INSTITUTION_UNIQUE);
    }
}
// 4. 组装并保存用户与角色的关联关系
authorityUserRole.setRoleName(authorityRole.getRoleName());
authorityUserRole.setInstitutionTypeId(authorityRole.getInstitutionTypeId());
authorityUserRole.setInstitutionId(authorityRole.getInstitutionId());
authorityUserRoleRepository.save(authorityUserRole);
```

校验的依据还是那套运营身份规则：平台下面有集团、运营中心、交易商三种运营身份，一个用户可以拥有不同运营身份的角色，但不能拥有相同运营身份的不同角色，也就是说不能拥有不同交易商下面的角色。错误码集中在 ApplicationErrorCodeEnum，比如 USER_ROLE_NOT_FOUND（用户角色未找到，100008）、ADMIN_USER_INSTITUTION_UNIQUE（用户在多个相同机构类型的角色，不能保存，200001）。保存前要完善关联数据：角色名称、机构类型、机构 ID、机构名称这些冗余字段，还有创建人、创建时间、修改人、修改时间。创建人来自当前 session 的操作用户，获取用户信息很多接口都要用，所以把 getUser 封装在 BaseController 父类里：直接从 session 获取 user 对象，不存在就抛异常；AuthorityLogicController 继承 BaseController 即可使用。Controller 上用 @PostMapping 声明 post 方式调用和请求路径，@ApiOperation 是 Swagger 的描述说明。课程演示里常规参数校验交由前端判断控制，实际生产环境后台还是要加非空、合法性这些必要校验，保持代码健壮性。

按角色查权限的两个接口（查菜单操作、查菜单）是前端做权限判断时要调用的，通过 HATEOAS 方式实现。它们不涉及过多业务规则，但需要跨表查询，JPA 接口一般按方法名称做单表 SQL 映射，跨表就得用 @Query 写 HQL：

```java
@Query("select menuOpt from AuthorityMenuOperation menuOpt, AuthorityRoleOperation roleOpt " +
        "where roleOpt.roleId = ?1 and menuOpt.status = 1 " +
        "and roleOpt.operationId = menuOpt.id")
public List<AuthorityMenuOperation> findByRoleId(@Param("roleId") Long roleId);

@Query("select menu from AuthorityMenu menu, AuthorityRoleMenu roleMenu " +
        "where roleMenu.roleId = ?1 and menu.status = 1 " +
        "and roleMenu.menuId = menu.id")
public List<AuthorityMenu> findByRoleId(@Param("roleId") Long roleId);
```

HQL 跟 SQL 语法类似但面向对象，看不到表名、都是对象名称，参数用 ?1 占位（位置从 1 开始），结果集由 JPA 自动映射，不需要再做实体映射。方法放置有个规则：关联查询的返回结果集和哪个实体关联，就把方法定义在对应的数据层接口上，查菜单操作的方法放在 AuthorityMenuOperationRepository 而不是角色的 repository。两个接口都返回集合、不分页：一个系统最多几百个菜单，数据量不大，且这些数据用于权限逻辑的控制处理，并非界面呈现查看；有分页的特殊需求，再通过自定义数据层接口包装一层实现。

## Spring Data REST 的三个高级配置

**级联映射（冗余查询）。** 菜单要显示父菜单的编号和名称，菜单和父菜单都存在菜单表、通过 parentId 映射关联。重新定义接口并封装返回对象可以实现，但麻烦、增加额外代码量；Spring Data REST 支持级联映射，类似 Hibernate 的一对多、多对多级联处理。关键是创建新的 VO 对象，它不能存在于 Spring Data REST 的映射之中，否则返回的对象会自动转换成 REST 地址（响应里只有一个 href）；新 VO 没有关联关系、不做地址映射，就会被自动转换成 JSON 对象返回，里面能带父菜单编号、名称。

```java
@ManyToOne(fetch = FetchType.EAGER)
@JoinColumn(name = "parentId", referencedColumnName = "id",
        insertable = false, updatable = false)
private ParentAuthorityMenuVo parentAuthorityMenu;
```

菜单和父菜单是多对一，用 @ManyToOne；fetchType 选 EAGER（非懒加载，初始化时就加载）还是 LAZY（用到时再加载）按需选。@NotFound 注解建议加上：不加的话，级联关系找不到匹配数据会抛异常，影响正常业务流程；没有特殊要求就让它返回空数据。@JoinColumn 定义映射：父级菜单的 parentId 关联父级菜单数据的 id。insertable 和 updatable 全部关闭，防止保存修改菜单时级联数据被同时改动。一对多同理：一个 User 关联多个角色，AuthorityUser 上用 @OneToMany 配 AuthorityUserRoleVo，通过用户角色表的 userId 和用户表的 id 关联。

**返回 ID 配置。** 实际增删改查需要知道具体 ID 才能操作，但 Spring Data REST 默认将 ID 隐藏不返回，响应报文里没有 ID 信息。两种配置按场景选：暴露所有资源的 ID，配置类里注入 EntityManager，把所有实体遍历后交给 exposeIdsFor；只暴露指定资源的 ID，直接把实体 class 传入。

```java
@Override
public void configureRepositoryRestConfiguration(RepositoryRestConfiguration config) {
    config.exposeIdsFor(entityManager.getMetamodel().getEntities()
            .stream().map(e -> e.getJavaType())
            .collect(Collectors.toList()).toArray(new Class[0]));
}
// 或者只暴露菜单：config.exposeIdsFor(AuthorityMenu.class);
```

**QueryDSL 集成。** 查询经常遇到各种条件组合，每个条件都新增一个接口非常麻烦。比如账户预警通知模板的查询接口，默认支持分页和排序，但不支持按内容、标题过滤，再开接口就很麻烦。QueryDSL 会根据 Spring Data REST 中定义的实体生成 Q 开头的查询类，在 Repository 里继承 QuerydslPredicateExecutor 和 QuerydslBinderCustomizer 后，实体任意属性的单个或多个条件查询都能支持：

```java
@Override
default public void customize(QuerydslBindings bindings, QAuthorityMenu menu) {
    bindings.bind(menu.menuName).first(StringExpression::contains); // 模糊查询
    bindings.bind(menu.menuCode).first(StringExpression::equalsIgnoreCase); // 忽略大小写
}
```

这段配置的含义是菜单名称支持模糊查询、菜单编号完全匹配但忽略大小写；时间范围查询用 path.between 配置。依赖 querydsl-jpa、querydsl-apt 及编译插件加在 stock-entity 工程；对实体的属性做任何增删改（新增删除属性、调整属性名称）之后，不要忘记在 Maven 视图对 stock-entity 重新 clean 打包，重新生成最新的 QueryDSL 映射实体。验证方式：启动服务（端口 10691），不加 QueryDSL 时 URL 后面跟任何查询条件都无法生效；配置后用 Postman 以 menuUri 作为条件发普通参数请求，返回匹配的业务数据，menuName 等其他条件也可以继续拼接。

## Swagger2 自定义启动器

Swagger2 集成这一章有三个目标：掌握自定义启动器的封装与集成配置；让 Swagger2 支持 Spring Data REST（原生并不支持，无法扫描，Swagger 文档呈现不了 Spring Data REST 的实现接口）；与 swagger-bootstrap-ui 第三方 UI 集成（原生界面不直观，换更直观的管理界面）。实现步骤四步：自定义 Swagger2 启动器、后台管理服务集成、与 Spring Data REST 集成支持、集成 swagger-bootstrap-ui 界面。

启动器沿用自定义 starter 的老套路：在 stock-starter 工程下新建模块 bulls-stock-starter-swagger，依赖包括 Gson 工具（谷歌提供）、springfox-swagger2 核心依赖、swagger-ui 界面依赖，以及 spring-boot-starter-data-rest。加后者是因为要做调整修改，让 SpringFox Swagger2 能支持 Data REST 集成，把 Data REST 的接口显示在 Swagger2 文档中。

先写 SwaggerProperties 属性配置类，@ConfigurationProperties(prefix = "swagger")，只记录配置、没有业务逻辑：是否开启 Swagger、要解析的包路径、解析 URL 规则、basePath 基础上需要排除的 URL 规则、标题描述、版本许可、联系人与服务条款、host，以及全局统一鉴权配置：要集成 OAuth2 鉴权时配置 Authorization（name、鉴权 URL 规则、作用域列表、Token URL 历史记录），后面用较简便的方式实现。核心配置类如下：

```java
@Configuration
@EnableSwagger2
@ConditionalOnProperty(name = "swagger.enabled", havingValue = "true")
public class AutoSwaggerConfiguration {
    @Bean
    public Docket api(SwaggerProperties swaggerProperties) {
        return new Docket(DocumentationType.SWAGGER_2)
            .useDefaultResponseMessages(false)
            .host(swaggerProperties.getHost())
            .apiInfo(apiInfo(swaggerProperties))
            .select()
            .apis(RequestHandlerSelectors.withMethodAnnotation(ApiOperation.class))
            .paths(PathSelectors.any())
            .build()
            .securitySchemes(securitySchemes(swaggerProperties))
            .securityContexts(securityContexts(swaggerProperties));
    }
}
```

注解含义要清楚：@Configuration 标注配置类；@EnableSwagger2 开启 Swagger2 功能、生成文档，必须加；@ConditionalOnProperty 是条件化配置，属性项 swagger.enabled 必须配置且值等于 true，下面的配置才生效；配置方法上还有基于属性对象的条件化注解，缺了这个对象整个配置不生效。Docket 内部：先处理 basePath，它配置所有路径相当于通配符，遍历并转换成 Swagger2 能识别的路径格式；再处理排除路径，属性为空时加默认配置，把 error、监控（actuator）相关接口排除掉，不展示在文档中；paths 组合上外层是 AND、内层是 NOT，落在排除路径里的条目不进入文档。apis 用 withMethodAnnotation(ApiOperation.class) 基于注解扫描：方法上加了 @ApiOperation 就纳入 Swagger2 文档管理，比如 AuthorityMenuOperation 数据层接口的方法加了注解就能进文档。securitySchemes 和 securityContexts 是全局统一鉴权配置：全局预制 Authentication 参数，避免每个接口单独配；鉴权策略通过正则表达式匹配，默认匹配所有 URL，defaultAuth 设定关联的认证信息和作用域范围，这套是 OAuth2 集成的铺垫。

最后遵循 SPI 机制，在 Resource 目录下创建 META-INF，新建 spring.factories 指定配置类路径，路径一定要配置正确：

```properties
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
com.itcast.stock.starter.swagger.AutoSwaggerConfiguration
```

到这里，Swagger2 自定义启动器的配置实现就完成了。

## 小结

- 四个核心接口两条实现路线：保存角色权限、分配用户角色走 Controller 加 Service 包装（复杂逻辑）；按角色查菜单、查菜单操作走 Spring Data REST 加 HQL（跨表查询）。
- 保存角色权限的规范：roleAuth 逗号分隔、M 前缀菜单 ID、O 前缀操作 ID；先去重、先删后存、删除从最末级关联开始；方法加 @Transactional 且 rollbackFor 所有异常。
- 用户分配角色的红线：不能拥有相同机构类型的两个角色，违反抛 ADMIN_USER_INSTITUTION_UNIQUE；关联数据要补齐角色名称、机构类型与名称等冗余字段和创建修改信息。
- HQL 面向对象查询：?1 占位、结果自动映射；方法放在返回实体对应的 Repository 上；权限数据不分页，特殊需求再包装一层。
- Spring Data REST 高级三件套：级联映射（新 VO 才能转 JSON，@ManyToOne 加 @JoinColumn 且 insertable/updatable 关闭）、exposeIdsFor 暴露 ID（全量或指定）、QueryDSL 动态条件查询（customize 配模糊与忽略大小写，实体变更后重新 clean package）。
- Swagger2 用自定义 starter 封装：@EnableSwagger2 与 @ConditionalOnProperty 控制开关，Docket 按 @ApiOperation 注解扫描接口、排除默认路径，全局鉴权参数为 OAuth2 集成铺路，最后以 META-INF/spring.factories 注册自动装配。
