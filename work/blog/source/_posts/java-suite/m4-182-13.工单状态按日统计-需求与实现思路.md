# 工单状态按日统计：需求思路、工单定时汇总、无效工单处理与状态统计

运营管理后台需要一个柱状图：选定日期范围，展示每一天工单的完成数和取消数，让管理者看出一段时期内工单量的变化规律。数字是聚合出来的，而工单表是仅次于订单表的大表、每天增长很多，每次查询都实时聚合既慢又压数据库。立可得第八章「统计分析」的这一小节沿用了订单汇总的方案：先建一张按天存储的工单汇总表，用 XXL-JOB 每天凌晨把前一天各状态的工单数算好写进去，图表查询只碰小表；同一任务里还顺带治理了超时未处理的无效工单。这篇按需求思路、定时汇总任务、无效工单处理与统计接口四段讲完。

## 先给结论

- 汇总表 tb_task_collect 一天一条记录：id、finish_count（当日已完成工单数）、progress_count（当日进行中工单数）、cancel_count（当日取消工单数）、collect_date（汇总日期）。
- 图表目前只展示完成和取消两个数，进行中的照样统计入库：它统计的是当天派发给执行人、对方既没完成也没主动取消的超时未处理工单，先存着，给产品后续扩展留数据。
- 统计窗口永远是前一天：任务定在凌晨三点跑（Cron `0 0 3 * * ?`），当天数据还没产生完，前一天才是闭合完整的一天。
- 定时任务可能被重复调度，插入前先按汇总日期删掉旧数据再插入，无论执行多少次每天只有一条记录，天然幂等。
- 无效工单治理挂在同一个任务上：更新时间早于当天、状态仍是创建或进行中的工单，批量改成取消状态并备注「工单超时」。
- 对外查询接口按开始、截止日期从汇总表查列表，按日期升序返回；前端只用完成和取消两个字段，进行中照常返回。

## 需求与思路：为什么要一张汇总表

需求本身不复杂：在运营管理后台查询一定日期范围内每一天的工单完成数和取消数，以柱状图方式展现，示例图里是 1 月 25 日到 29 日每天的完成工单和未完成工单两根柱子。真正要设计的是数据从哪来。

工单数必须经过聚合统计，而工单表是个大表，数据量每天增长很多。如果每次打开图表都对工单表做一遍聚合，效率肯定不高，数据库压力也大。解决方式借鉴了之前对订单表做聚合统计的方案：先设计一张汇总表，以天为单位存储当天的数据，每天执行一个定时任务把数字统计出来插进去，之后图表展示直接从汇总表取数，不再碰工单大表，执行效率非常高。

汇总表 tb_task_collect 的字段就五个：主键 id，三个计数列 finish_count、progress_count、cancel_count，加上汇总日期 collect_date。定时调度继续用 XXL-JOB 来配置任务。

有一个值得琢磨的细节：图表上只有完成和取消两组柱子，为什么汇总表还要统计进行中的工单数？因为「进行中」统计的实际是当天派发给某个人、他既没去做也没主动取消的工单，相当于超时未处理的量。这部分数据当前的产品需求没有展示，但定时任务里照样统计、照样入库。考虑很简单：产品需求随时可能变，哪天要加一条「进行中工单」的曲线，如果现在没存这个数，历史数据就永远补不回来了。做实现方案的时候多想一步扩展，成本几乎为零，收益在未来。

## 定时汇总任务：count、clearData 与 collectTask

代码分四步走。第一步在工单微服务的 pom 里添加 xxl-job-core 依赖；第二步把 xxl-job 相关配置加进 Consul 配置中心里工单微服务的配置文件；第三步从其他微服务把现成的 XxlJobConfig 配置类拷贝过来，放到 job 包下；第四步写任务类 TaskCollectJob，类上加 @Component，方法返回 ReturnT<String>，方法名 collect，带一个 param 参数。

统计逻辑封装成私有方法 count，按日期和工单状态计数：

```java
/**
 * 按日期和状态统计工单数
 */
private Integer count(LocalDate start, Integer taskStatus) {
    var qw = new LambdaQueryWrapper<TaskEntity>();
    qw.lambda()
      .ge(TaskEntity::getUpdateTime, start)
      .lt(TaskEntity::getUpdateTime, start.plusDays(1)) // 小于第二天，即start这一整天
      .eq(TaskEntity::getTaskStatus, taskStatus);
    return taskService.count(qw);
}
```

时间窗是左闭右开：大于等于 start 零点、小于 start 第二天零点。比如 start 是 28 日，查的就是 28 日 0 点到 29 日 0 点之间的全部记录，一天不多一天不少。

任务方法 collectTask 负责把三个数字统计出来落库：

```java
@XxlJob("taskCollectJobHandler")
public ReturnT<String> collectTask(String param) {
    var taskCollectEntity = new TaskCollectEntity();
    // 统计前一天的工单数据
    LocalDate start = LocalDate.now().plusDays(-1);
    taskCollectEntity.setProgressCount(this.count(start, VMSystem.TASK_STATUS_PROGRESS));
    taskCollectEntity.setCancelCount(this.count(start, VMSystem.TASK_STATUS_CANCEL));
    taskCollectEntity.setFinishCount(this.count(start, VMSystem.TASK_STATUS_FINISH));
    taskCollectEntity.setCollectDate(start);
    clearData(start); // 插入前先清理，防止重复
    taskCollectService.save(taskCollectEntity);
    return ReturnT.SUCCESS;
}
```

统计日期取 `LocalDate.now().plusDays(-1)`，也就是昨天。为什么不是当天？任务执行时间应该设在要汇总那天的后一天：当天结束前数据还在持续产生，当天统计出来的数永远不完整；第二天凌晨三点统计前一天，这一天已经闭合，数字才准确。三个 count 调用对应进行中、取消、完成三个状态，状态常量定义在 VMSystem 里，最后把 collect_date 设为 start，保存。

还有一个必须考虑的问题：定时任务有没有可能被重复执行？完全有可能。一旦重复执行，同一天的数据就会插两条，后续的展示会很麻烦。处理办法是插入之前先把这一天的旧数据删掉：

```java
/**
 * 清理某天数据，保证任务重复执行不产生重复记录
 */
private void clearData(LocalDate start) {
    var qw = new LambdaQueryWrapper<TaskCollectEntity>();
    qw.eq(TaskCollectEntity::getCollectDate, start);
    taskCollectService.remove(qw);
}
```

先按 collect_date 删、再插入，无论任务被执行多少次，每天的数据都只有一条。

任务类写完，去 XXL-JOB 调度中心配置。先新建执行器：AppName 必须填 task-service，和配置中心里 executor.appname 保持一致，名称写「立可得工单微服务」。再在这个执行器下新增任务：任务描述「工单汇总」；路由策略选第一个就行，这个任务执行时间比较短；Cron 表达式 `0 0 3 * * ?`，凌晨三点执行；JobHandler 从代码里复制，填 taskCollectJobHandler。任务创建后状态是 stop，可以启动，不过要等凌晨三点才触发，测试时直接用「执行一次」。

测试前先造数据：汇总表里只有历史数据没有当天的，把工单表里部分记录的日期手动改成昨天（28 日），保证统计能算出东西。然后启动工单微服务，调度中心执行一次，到汇总表里看：多了一条记录。重复执行也没问题：第一次插入的记录 ID 是 21，再执行一次后 ID 变成 22，原来的 21 被删掉、重新插了一条新的。这就是 clearData 在起作用，每天的数据保持唯一。

## 无效工单处理与统计查询接口

无效工单的定义：工单创建完成之后，执行者既没有把它完成，也没有手动取消，已经拖过了当天。这部分工单由系统自动改成取消状态，处理操作直接挂到工单定时汇总这个任务上，一起执行。

任务类里再加一个私有方法 cleanTask，做一次批量 update：

```java
/**
 * 无效工单处理：超时未处理的工单自动置为取消
 */
private void cleanTask() {
    var um = new UpdateWrapper<TaskEntity>();
    um.lambda().lt(TaskEntity::getUpdateTime, LocalDate.now())
        .and(w -> w.eq(TaskEntity::getTaskStatus, VMSystem.TASK_STATUS_CREATE)
                  .or()
                  .eq(TaskEntity::getTaskStatus, VMSystem.TASK_STATUS_PROGRESS))
        .set(TaskEntity::getTaskStatus, VMSystem.TASK_STATUS_CANCEL)
        .set(TaskEntity::getDesc, "工单超时");
    taskService.update(um);
}
```

条件有两层。时间条件：更新时间小于当天，也就是昨天及更早的记录。状态条件：创建或进行中两种，它们之间是或的关系，和时间条件之间是且的关系，所以用 `and(w -> w.eq(...).or().eq(...))` 把两个状态包在同一组里，拼出来的条件等价于 `update_time < 今天 AND (状态 = 创建 OR 状态 = 进行中)`。要改的值有两个：状态改成取消（值为 3），备注字段写「工单超时」，相当于记录了取消原因。在 collectTask 的 save 之后调用 cleanTask，汇总和清理一个任务全干完。

测试预期很明确：工单表当前日期之前有很多状态为 1（创建）或 2（进行中）的记录，执行任务后这部分全部变成 3（取消），备注列显示工单超时。启动工单微服务，在调度中心再执行一次工单汇总任务，刷新数据：状态已经按预期批量更新。

汇总数据有了，对外的查询接口跟着做。接口文档定义的地址是 /collectReport，参数是开始日期 start 和截止日期 end，返回列表里带 finishCount、progressCount、cancelCount 三个字段。这个接口不需要单独建控制器类，直接加在 TaskController 里就行。业务方法放在工单汇总的 service 里：

```java
@Override
public List<TaskCollectEntity> getTaskReport(LocalDate start, LocalDate end) {
    var qw = new QueryWrapper<TaskCollectEntity>();
    qw.lambda()
      .ge(TaskCollectEntity::getCollectDate, start)
      .le(TaskCollectEntity::getCollectDate, end)
      .orderByAsc(TaskCollectEntity::getCollectDate);
    return this.list(qw);
}
```

就是一个条件查询：collect_date 大于等于开始日期、小于等于截止日期，按日期升序排好返回。控制器里前端传来的日期是字符串，先转成 LocalDate 再传给业务方法查询。

测试走网关：启动工单微服务和微服务网关，打开 task.http 测试脚本里的「工单状态统计」请求，传一个日期段执行，拿到的查询结果全部来自工单汇总表。到这里，从定时汇总、无效工单治理到图表取数的接口就全部闭环了。

## 小结

这个小节是典型的空间换时间：工单表大、增长快，按日统计就每天算一次存进 tb_task_collect，图表查询只碰小表。实现上三个记忆点：统计窗口永远取前一天，并用左闭右开的时间条件表达；插入前先 clearData，保证任务重复执行不产生重复数据；无效工单的批量取消用 UpdateWrapper 把「时间且（状态或状态）」这种嵌套条件拼清楚。进行中的工单数虽然图表暂时不用，也照存不误，给产品变化留了后路。对外一个 /collectReport 接口按日期段返回汇总列表，前端拿去画柱状图即可。
