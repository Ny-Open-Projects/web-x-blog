# CAT 链路监控全解：Dapper 理论、trace/span 机制、七大报表与单机部署实录

交易平台 Day 2 的课程主题是监控：CAT 链路监控与 Sentinel 限流熔断。本篇覆盖 CAT 这条线——从单体到微服务为什么必须上链路监控，Google Dapper 论文奠定的 trace id + span 关联机制，CAT 的七大优势与丰富报表体系，最后从源码编译到 war 包放进 Tomcat，把 CAT 单机部署完整走一遍。

## 先给结论

- CAT 是美团点评基于 Java 开发的实时应用监控平台，深度集成在 MVC、RPC、数据库、缓存、消息队列、配置系统等中间件框架里，提供多语言客户端（Java、C/C++、Node.js、Python、Go）。
- 实时性是 CAT 的招牌：多数系统做到分钟级统计已经不易，CAT 从数据生成到服务端处理结束做到秒级——48 分 40 秒发起的请求，基本能在 48 分 38 秒看到数据，延迟仅 2-3 秒。
- 链路监控的理论源头是 Google Dapper 论文（2010），Sleuth、Zipkin、SkyWalking 都是基于它衍生开发；核心是 trace id 标识一次请求，span id 标识节点间的调用关联。
- CAT 设计遵循「简单即是最好」，分三个模块：cat-client 埋点 SDK、cat-consumer 实时分析、cat-home 展示控制端；客户端是旁路环节，任何场景下都不能影响业务性能。
- 监控数据全量统计、客户端预计算，链路数据采样计算，服务端压力被前置消化；报表覆盖报错统计、业务统计、LogView 以及 Transaction/Event/Problem/Heartbeat/Metric/Matrix 六类实时报表。
- 单机部署注意三件事：不要在 Windows 下部署（源码读的是不带盘符的绝对路径）；MySQL 建 cat 库用 utf8mb4 字符集；client.xml 与应用程序分离，约定放在 /data/appdisk 下，服务端 TCP 端口 2280、HTTP 端口 8080。

## CAT 是什么：能力与七大优势

微服务架构下，一个请求会流转过几十个分布式节点，逐台机器翻日志已不现实，全局分布式链路监控系统应运而生，这正是 CAT 要解决的监控难题。

CAT 作为服务端项目的基础组件，在美团点评基础架构中间件框架中深度集成，为各业务线提供丰富的性能指标、健康状况与实时告警。它有两个硬指标：其一，报表整体统计粒度是分钟级，而数据从生成到服务端处理结束做到了秒级支持；其二，监控数据全量统计，且客户端做预计算、链路数据走采样计算，把服务端压力分摊到了客户端侧。

具体到设计原则，CAT 的优势可以归纳为七条：

| 优势 | 含义 |
| --- | --- |
| 实时处理 | 信息的价值随时间锐减，事故处理时高延迟的信息只会拖累分析定位排查 |
| 全量采集 | 全量采集指标数据，来源 IP、时间等全面记录，便于深度分析故障案例 |
| 高可用 | 故障还原与问题定位依赖监控组件自身可用，监控服务要保持多节点 |
| 故障容错 | 监控出故障对业务透明，监控与业务服务解耦，采用旁路设计 |
| 高吞吐 | 大型互联网成百上千节点的监控数据上报，服务端必须具备高吞吐能力 |
| 可扩展 | 支持分布式、跨 IDC 机房部署，监控出现瓶颈可水平扩展节点 |
| 报表丰富 | 从各个角度呈现系统整体运行状况，帮助管理人员与运维快速分析 |

其中故障容错值得强调：监控只是公司核心业务流程的旁路环节，辅助服务运行，不能主导服务运转——无论监控自身正常与否，都不允许影响业务服务的正常运行。

## 报表体系：从报错统计到 Matrix

CAT 提供的报表是「报表丰富」这条优势的落地。四个常用报表各有分工：

| 报表 | 作用 |
| --- | --- |
| 报错统计报表 | 列出服务端正常/异常的监测节点，按时间段统计异常最多排行，还有 URL 最多、service 最慢、SQL 最慢等维度；红色区域标出报错数，倒序排列一眼定位问题节点 |
| 业务统计报表 | 按业务维度统计，如支付成功次数；配置项目、负责人、手机号，用曲线图对比当前值与基准限值，偏离过大即存在波动异常，还能在出问题时直接找到首要负责人 |
| LogView 统计日志 | 整个链路请求的日志记录：事务开始/结束、事件、原子性事务，分类统计每层的 GET/POST 方法、请求状态（404/500）与耗时（如 1.06ms、27ms），竖形结构逐层展开 |
| 可视化 LogView | 图形化呈现埋点与各服务节点调用情况，按时间轴画耗时条形；发现某段蓝色条形特别长，就该怀疑这一段调用存在严重问题 |

LogView 的原始日志长这样，每条记录带时间戳与耗时：

```text
14:38:56.595 URL t
14:38:56.595 URL Server cat.dianpingoa.com
14:38:56.595 URL Method HTTP/GET
14:38:56.596 ModelService RemoteTransactionService 1.06ms http://...
14:38:56.596 ModelService CompositeTransactionService 27ms request=...
14:38:56.628 URL t
```

对开发人员 LogView 足够直观，但运营、运维人员看起来吃力，所以另有可视化版本兜底。在这四个报表之外，CAT 还提供六类实时报表：

| 实时报表 | 统计内容 |
| --- | --- |
| Transaction | 一段代码的运行时间、次数、分布：URL、Cache、SQL 的执行次数与响应时间 |
| Event | 事件产生的次数与分布，比如异常 |
| Problem | 基于 Transaction/Event 数据分析得出的异常统计，包括访问较慢的程序 |
| Heartbeat | 不侧重应用逻辑接口，侧重 JVM 内部状态：load、memory、GC、thread 线程使用情况 |
| Metric | 业务指标采集监控，如支付成功/失败次数，可自定义指标实时统计 |
| Matrix | 一次请求的调用分布：调了多少次 SQL、多少次 RPC、多少次缓存，评估应用设计是否合理 |

报错统计的直观性很强：以课程演示数据为例，shop-server 在 16:53 时间段错误次数高达 9236，mobile-web 在 16:48 为 8300，按倒序排列后先看红色区域再钻取节点错误日志，定位效率远高于人工翻日志。

## Dapper 理论：trace id 与 span 的关联设计

Google 在 2010 年 4 月发布了技术报告《Dapper, a Large-Scale Distributed Systems Tracing Infrastructure》，这是一篇大型分布式系统追踪基础设施的设计论文，奠定了分布式链路监控的基础，Sleuth、Zipkin、SkyWalking 都是基于 Dapper 理论衍生开发而来。

Dapper 的部署架构是一条数据流水线：

```mermaid
flowchart LR
    A[生产主机<br/>instrumented binaries] -->|生成二进制 log file| B[Dapper daemon<br/>后台线程]
    B -->|传输监控日志| C[Dapper Collectors<br/>收集器加工组织]
    C -->|写入| D[(Central Bigtable<br/>trace 数据存储)]
```

生产主机上运行被植入监控代码的二进制文件，生成二进制日志文件；Dapper daemon 后台线程把日志传给 Dapper Collectors 收集器；收集器加工、组织这些监控信息后写入中央 Bigtable 存储。存储结构是一张以 trace id 为行键、span 为列键的表：

| trace id | span 12 | span 23 | span 34 | span 45 | span 56 |
| --- | --- | --- | --- | --- | --- |
| 123456 | nil | nil | data | data | nil |
| 246802 | data | nil | nil | nil | data |
| 357913 | nil | data | nil | nil | nil |

trace id 是每次请求的标识：123456 这条请求在 span 34 与 span 45 有数据，说明请求在节点 3-4、4-5 之间流转处理；节点之间一环扣一环，靠 span id 做关联标识——没有它，B 服务的请求根本无法识别是 A 服务转发来的还是外部请求；如果请求只调用了一个节点，就在对应 span 下直接写入数据。所以看一行数据就能还原请求流转了哪些节点，顺着 span id 就能追踪到完整链路。

落到具体的调用场景，四个概念先摆清楚：Trace 是一次分布式调用的链路踪迹；Span 是一个方法（局部或远程）调用的踪迹；Annotation 是附着在 Span 上的日志信息；Sampling 是采样率。以 Service1 → Service2 → Service3 三节点为例，请求进来会分配 TID（即 trace id）和 SID（即 span id）：

| 节点 | Span | pid | 动作 |
| --- | --- | --- | --- |
| Service1 | tid:1, pid:1, sid:1 | - | 请求入口，自身业务 |
| Service1 | tid:1, pid:1, sid:2 | - | 本地数据处理（如 Redis 调用），方法调用中继 |
| Service1 | tid:1, pid:1, sid:3 | - | 调用远程 Service2 |
| Service2 | tid:1, pid:3, sid:4 | 3 | 进入方法逻辑处理 |
| Service2 | tid:1, pid:4, sid:5 | - | 查数据库 |
| Service2 | tid:1, pid:4, sid:6 | - | 调用远程 Service3 |
| Service3 | tid:1, pid:6, sid:7 | 6 | 自身处理 |

规律很清晰：TID 全程保持不变，因为都是同一个请求；每个新的 SID 都在上一个 SID 之后分配，PID（Parent ID）指向上一个 SID，形成父子关联；跨服务远程调用时，下游节点的 pid 记住上游的 sid，调用关系就串起来了。这些数据最终同样经由 daemon → Collectors 写入 Bigtable，链路监控组件就是这样追踪各微服务节点的调用执行情况的。

## 架构设计与单机部署实录

CAT 遵循「简单即是最好」的设计原则，整体分三个模块：

- **cat-client**：提供给业务以及中间层埋点的底层 SDK，收集应用服务的监控埋点信息；
- **cat-consumer**：实时分析从客户端提供的数据；
- **cat-home**：提供给用户的展示控制端，即监控管理后台，可在上面配置与查看整个应用服务的运行信息。

客户端设计是 CAT 系统中最为核心的环节，要求 API 简单、高可靠，且任何场景下都不能影响业务服务性能。工作流程上，HttpThread 在处理业务时会经过 ThreadContext 创建消息树：Call 操作创建 Call 节点，SQL 加入 SQL 节点，Cache 加入 Cache 节点，消息构建结束后放入消息队列，再由 Sender 线程异步发送给服务端——全程不阻塞业务线程。

服务端是单机 cat-consumer 的架构：应用 A、B、C 通过监控线程将消息异步发送给消息消费者，Receiver 用线程池接收后派发给后台分析线程，Analyzer 消费处理消息、转存异步线程并加工统计形成报表，最终写入 HDFS 与 MySQL。当某个报表处理器来不及处理（比如 Transaction 报表处理较慢）时，可通过配置开启多个 Transaction 处理线程并发消费消息，消息接收与分析都有多线程保证。

理解了架构，部署照着做。环境要求：JDK 1.8 以上、Tomcat 8 以上、MySQL 5.7 以上。首先要明确：不建议在 Windows 下部署。CAT 设计上就没考虑 Windows，从源码可以看到读取路径写的是绝对路径，没有跟上盘符，也没有区分操作系统——Windows 的 C/D/E 盘符概念在 Linux 上不存在，Windows 支持不好，容易出各种问题。

部署按六步走：

**第一步，源码编译打 war 包。** 下载 CAT 源码（下载慢可用 Download ZIP 打包下载），用 IDEA 打开，主要源码模块就是之前讲过的 cat-home、cat-client、cat-consumer。建议先把 Maven 加入系统 Path，然后在源码根目录执行（忽略测试用例验证）：

```bash
mvn clean install -Dmaven.test.skip=true
```

也可以在 IDEA 里对 cat-home 根目录运行 clean package，生成的 war 包在 target 目录下。

**第二步，创建数据库。** 用客户端工具连接数据库所在的虚拟机 192.168.19.150，新建名为 cat 的数据库，字符集建议 utf8mb4，排序规则用默认；然后把源码 script 目录下的 SQL 脚本（CatApplication.sql）拷过来执行。

**第三步，目录授权。** CAT 部署在 Linux 虚拟机 10.10.20.10 上，运行所需的配置目录必须具备读写权限：

```bash
chmod -R 777 /data/appdisk
```

`-R` 表示所有目录递归生效，后面跟上要授权的路径。

**第四步，配置客户端与服务端。** CAT 的 client 配置与应用程序是分离的，配置文件约定放在 /data/appdisk 下的 client.xml，指向 CAT 所在虚拟机，TCP 端口 2280，HTTP 端口 8080：

```xml
<?xml version="1.0" encoding="utf-8"?>
<config mode="client">
    <servers>
        <server ip="10.10.20.10" port="2280" http-port="8080"/>
    </servers>
</config>
```

服务端要配置数据库连接，对应 datasources.xml，核心是连接 URL、用户名和密码：

```xml
<?xml version="1.0" encoding="utf-8"?>
<data-sources>
    <data-source id="cat">
        <maximum-pool-size>3</maximum-pool-size>
        <connection-timeout>1s</connection-timeout>
        <idle-timeout>10m</idle-timeout>
        <statement-cache-size>1000</statement-cache-size>
        <properties>
            <driver>com.mysql.jdbc.Driver</driver>
            <url>jdbc:mysql://192.168.19.150:3306/cat</url>
            <user>root</user>
            <password>password</password>
        </properties>
    </data-source>
</data-sources>
```

几个参数的含义：maximum-pool-size 是最大连接池大小，connection-timeout 是连接超时时间，idle-timeout 是闲置回收超时时间；statement-cache-size 默认 1000，如果压力大、要监控的节点比较多，可以改大到 1 万甚至几万。

**第五步，调整 Tomcat。** war 包不能直接运行，必须放进 Tomcat。两处修改：server.xml 里增加 URIEncoding 让它支持 UTF-8；虚拟机内存有限，在 catalina.sh 里调整 JVM 参数——初始化 1G、最大 2G，metaspace 也可指定。然后把 war 包上传到 /usr/local/apache-tomcat/webapps 目录（没有 rz 命令就先安装 lrzsz）。

第六步，启动验证。
```bash
ps -ef | grep tomcat        # 确认没有残留进程
/usr/local/apache-tomcat/bin/startup.sh
tail -f logs/catalina.out   # 观察启动日志，无报错
```

浏览器访问 `http://10.10.20.10:8080/cat/s/config?op=routerConfigUpdate`，用户名 admin、密码 admin 登录，进入 CAT 控制管理后台：能看到基本信息、项目配置信息、应用监控信息、应用高级信息以及客户端路由等系统配置。看到这个页面，CAT 的打包、配置、运行就全部 OK 了。后续章节再讲 CAT 如何与应用服务集成、怎么接入埋点。

## 小结

CAT 的学习路线是一条「由表及里」的路径：先从单体到微服务的架构演变理解为什么需要全局链路监控；再看 CAT 的实时性（秒级处理、分钟级报表）、全量采集、高可用、故障容错、高吞吐、可扩展与报表丰富七大优势；报表侧掌握报错统计、业务统计、LogView 与六类实时报表各自回答什么问题；原理侧抓住 Dapper 论文这条主线——trace id 标记请求、span id 标记调用关联、daemon 采集、Collectors 加工、Bigtable 存储，Service1/2/3 的 tid/pid/sid 传递就是这套理论的具体落地；最后落到 cat-client/consumer/home 三模块的单机部署，环境对齐 JDK 1.8+、Tomcat 8+、MySQL 5.7+，记住不在 Windows 部署、utf8mb4 建库、/data/appdisk 放 client.xml 这几条口径，admin/admin 登进控制台即部署成功。
