# 告警日志查询：InfluxDB 模糊查询、六段封装实现与报文数据模拟

第三章的指标数据已经落进 InfluxDB，本节在存储之上做第一件事：报警日志查询。系统要能按时间段检索发生过报警的记录，报警名称支持模糊匹配，设备编号支持开头匹配，结果分页展示。这一节从 InfluxQL 查询语句一路写到 Controller，末尾还顺手解决了测试数据量不足的问题：用一段模拟代码把整条链路喂饱。

## 先给结论

- 亿可控没有单独的报警日志，报警记录混在指标数据里：报文解析出的指标都存在 quota 表，alarm 字段为 1 的就是报警记录，查询时用 where alarm='1' 把这部分筛出来即可。
- 查询条件四种：时间段（start/end）、报警名称全模糊（包含关键字即命中）、设备编号开头匹配、分页。
- InfluxDB 的模糊查询不是 LIKE，是正则式写法：字段 =~ /条件值/ 做全模糊，条件值前加 ^ 匹配开头，后加 $ 匹配结尾；统计记录数不能用 count(*)，必须指明具体 field 字段，写 count(value)。
- 实现按六段走：InfluxRepository 补通用查询方法 → 定义 QuotaAllInfo、QuotaCount 两个映射类 → AlarmService 拼 WHERE 封装两条语句 → 通用方法执行 → 封装 Pager（含空结果兜底）→ AlarmController 暴露 GET /alarm/log 接口。
- 查出来的 time 是 ISO 格式（带 T），要先用 DateTimeFormatter.ISO_OFFSET_DATE_TIME 解析成 LocalDateTime，再 ofPattern("yyyy-MM-dd HH:mm:ss") 格式化回字符串写回实体。
- 数据量少测不出问题，写 Mock 类模拟 10 台设备发报文：@Scheduled 每 10 秒一轮，随机产生指标值，JSON 序列化后 publish 到 EMQ；发送环节是模拟的，解析、告警判断、落库全走真实链路。

## 需求分析：报警日志藏在指标记录里

界面原型是一个报警日志列表：报警时间、报警级别、设备、指标名称、报警值等列，表格下方是带上一页、下一页的分页控件。对应到功能，就是要按条件检索报警日志并搜索展示。

条件分两类。报警名称做模糊查询：输入"温度"，报警名称中包含"温度"的记录都会被查出来，属于全模糊匹配。设备编号做开头匹配：设备 123456、123457，输入 1234，两台都能查到，只要前缀吻合就命中。

数据从哪来是先要想清楚的问题。亿可控并没有单独的报警日志，只有指标记录：物联网设备发送的报文都会解析成指标存进 InfluxDB，这些指标有的是报警的，有的不是。查询要做的，就是把记录里涉及报警的部分筛出来：记录上有 alarm 字段，alarm 为 1 的就是报警记录。

实现思路三步：第一步编写查询语句，实现分页加模糊条件的查询；第二步编写通用的查询方法，拿着语句就能执行并返回结果；第三步在服务层对查询语句做封装，由 Controller 调用服务层方法把数据返回。整个功能最核心的，就是这条模糊查询语句怎么写。

## InfluxDB 模糊查询：正则式写法与分页语句

MySQL 的模糊搜索用 LIKE 加百分号，InfluxDB 完全不是这套写法，分三种情况：

```sql
-- 全模糊：条件值可以出现在字段的任意位置（前、中、后）
where alarmName=~/温度/
-- 开头匹配：条件值前面加 ^
where deviceId=~/^12/
-- 结尾匹配：条件值后面加 $
where deviceId=~/12$/
```

写在等号后面的是一个波浪线加两条斜杠夹住条件值，本质是正则的思路：^ 锚定开头，$ 锚定结尾，什么都不加就是任意位置。

在命令行里逐步演示。当时库里 quota 表只有 3 条记录，先查报警名称包含"温度"的，再叠加设备编号以 12 开头、alarm 等于 1，加上时间范围，完整的查询语句如下：

```sql
select * from quota
where alarmName=~/温度/ and deviceId=~/^12/ and alarm='1'
and time>='2020-01-01' and time<='2020-12-31'
order by desc limit 10 offset 0
```

order by desc 没有指定字段，默认就按 time 倒序排列，后发生的记录排在前面。limit 10 表示一次查询多少条记录，offset 0 表示从第几条开始查，分页就靠这两个参数。

分页还需要统计符合条件的记录总数。把 order by、limit、offset 这些后缀全去掉，前面的 select 换成 count。注意一个差异：MySQL 支持 count(*)，InfluxDB 不能这么写，必须指明一个具体字段，而且这个字段必须是 field 类型（非索引的值类型字段），这里给 value：

```sql
select count(value) from quota
where alarmName=~/温度/ and deviceId=~/^12/ and alarm='1'
and time>='2020-01-01' and time<='2020-12-31'
```

这两条语句就是后面封装的底稿，先放进记事本备着。

## 六段封装实现：从 Repository 到 Controller

### 通用查询方法

查询需要一个通用方法：接收查询语句，返回查询结果，工程里很多地方都会用到。InfluxRepository 里已经有一个通用的添加数据方法，再补一个查询方法。返回的是列表，元素类型不定，所以写成泛型方法：在返回值前声明类型参数，不必把整个类泛型化：

```java
public <T> List<T> query(String sql, Class<T> clazz) {
    QueryResult queryResult = influxDB.query(new Query(sql, dbName));
    InfluxDBResultMapper resultMapper = new InfluxDBResultMapper();
    influxDB.close();
    return resultMapper.toPOJO(queryResult, clazz);
}
```

influxDB 的 query 方法要传一个 Query 对象，这是 InfluxDB 提供的查询类，有三个构造方法，主要用双参那个：第一个传查询语句，第二个传数据库名，dbName 由配置注入。执行返回的是 QueryResult 查询结果对象，并不是最终要的 List，中间要做一次转换，转换就是映射的过程，用 InfluxDBResultMapper 的 toPOJO 把结果映射成指定的类型。查完之后及时 close，释放资源。

### 两个映射类

告警日志要展示的字段：报警时间、报警名称、级别、指标、数据、设备编号。大部分字段用之前的 QuotaInfo 就能封装，它就是与 quota 表做映射的类，添加指标信息时用的就是它。缺的只有第一个报警时间。

能不能直接在 QuotaInfo 里扩一个 time 字段？没那么简单：time 是添加数据时给的时间，在查询实体上再加一个 time 会造成混乱。做法是不动它，写一个子类继承，多出 time 属性：QuotaInfo 专门用于添加，子类专门用于返回带 time 的结果：

```java
@Data
@Measurement(name = "quota")
public class QuotaAllInfo extends QuotaInfo {
    @Column(name = "time")
    private String time;
}
```

分页查询通常还要统计符合条件的记录总数，这个数字也需要一个类来封装，里面只放一个 count 属性：

```java
@Data
@Measurement(name = "quota")
public class QuotaCount {
    @Column(name = "count")
    private Long count;
}
```

### Service：拼条件、封装两条语句

在 AlarmService 接口里扩展分页查询方法：

```java
/**
 * 告警日志查询
 * @param page     页码
 * @param pageSize 页大小
 * @param start    开始时间
 * @param end      截止时间
 * @param alarmName 告警名称
 * @param deviceId 设备编号
 */
Pager<QuotaAllInfo> queryAlarmLog(Long page, Long pageSize, String start,
        String end, String alarmName, String deviceId);
```

时间用字符串传。实现类里主要做三件事：构建 WHERE 条件、拼查询记录的语句、拼查询记录数的语句。两条语句的 WHERE 条件完全一样，而条件有的存在有的不存在，用户在界面输入了告警名称才有这个条件，设备编号同理，所以要按参数判空拼接；必然存在的条件放前面，可能存在的放后面，一个条件一行，思路更清晰：

```java
StringBuilder whereQl = new StringBuilder("where alarm='1'");
if (!Strings.isNullOrEmpty(start)) {
    whereQl.append(" and time>='").append(start).append("'");
}
if (!Strings.isNullOrEmpty(end)) {
    whereQl.append(" and time<='").append(end).append("'");
}
if (!Strings.isNullOrEmpty(alarmName)) {
    whereQl.append(" and alarmName=~/").append(alarmName).append("/");
}
if (!Strings.isNullOrEmpty(deviceId)) {
    whereQl.append(" and deviceId=~/^").append(deviceId).append("/");
}
```

告警名称是全模糊，deviceId 是开头匹配，所以 deviceId 的正则里带上 ^。接着把两条完整语句拼出来：

```java
// 查询记录的语句
StringBuilder listQl = new StringBuilder("select * from quota ");
listQl.append(whereQl.toString());
listQl.append(" order by desc limit " + pageSize + " offset " + (page - 1) * pageSize);

// 查询记录数的语句
StringBuilder countQl = new StringBuilder("select count(value) from quota ");
countQl.append(whereQl.toString());
```

limit 后面拼的就是 pageSize；offset 是算出来的，公式就是 (page - 1) * pageSize。countQl 拼到 WHERE 条件就结束了，后面没有别的。

### 执行查询与结果封装

注入 InfluxRepository，用通用查询方法执行两条语句：

```java
List<QuotaAllInfo> quotaList = influxRepository.query(listQl.toString(), QuotaAllInfo.class);
List<QuotaCount> quotaCount = influxRepository.query(countQl.toString(), QuotaCount.class);
```

quotaList 就是当前页的查询结果。总记录数要从 quotaCount 集合里取元素的 count 属性，然后构建 Pager 对象，它的双参构造正好接收总记录数和页大小：

```java
Long totalCount = quotaCount.get(0).getCount();
Pager<QuotaAllInfo> pager = new Pager<>(totalCount, pageSize);
pager.setPage(page);
pager.setItems(quotaList);
return pager;
```

这里有个隐患：如果 count 查询返回 null，或者结果集记录数为 0，get(0) 必然报错。为了让逻辑严谨，先做兜底判断，构造一个空的 Pager 返回：

```java
if (quotaCount == null || quotaCount.size() == 0) {
    Pager<QuotaAllInfo> pager = new Pager<>(0L, pageSize);
    pager.setPage(0);
    pager.setItems(new ArrayList<>());
    return pager;
}
```

### Controller 对齐 API 文档

写 Controller 前先看 API 文档：报警日志接口的 path 是 /alarm/log，GET 方式，参数有 page、pageSize、start、end、alarmName、deviceId，返回值是分页结果。参数命名必须与文档严格对应：

```java
@GetMapping("/log")
public Pager<QuotaAllInfo> alarmLog(
        @RequestParam(value = "page", required = false, defaultValue = "1") Long page,
        @RequestParam(value = "pageSize", required = false, defaultValue = "10") Long pageSize,
        String start, String end,
        @RequestParam(value = "alarmName", required = false, defaultValue = "") String alarmName,
        @RequestParam(value = "deviceId", required = false, defaultValue = "") String deviceId) {
    return alarmService.queryAlarmLog(page, pageSize, start, end, alarmName, deviceId);
}
```

page、pageSize 不是必须参数，required 设为 false 并给默认值 1 和 10；start、end 必传，@RequestParam 的 required 默认就是 true，可以省略注解，日期用字符串接收；alarmName、deviceId 可选，默认值给空字符串。

## 时间格式处理与报文数据模拟

代码完成后启动亿可控工程测试。用 VS Code 里的测试脚本调用 /alarm/log，传 start、end、page、pageSize 这几个必须参数，右侧查出了两条记录：设备编号、指标名称、告警级别、告警名称、单位、参考值、值（20.0）、字符串值都对，唯独 time 不对：它是默认的 ISO 格式，中间带着 T，并不是需要的"年月日 小时分秒"。

处理方式是循环结果集，逐条转换时间：

```java
for (QuotaAllInfo quotaAllInfo : quotaList) {
    // 按 ISO 格式解析成 LocalDateTime
    LocalDateTime dateTime = LocalDateTime.parse(quotaAllInfo.getTime(),
            DateTimeFormatter.ISO_OFFSET_DATE_TIME);
    // 再格式化成目标格式的字符串
    quotaAllInfo.setTime(dateTime.format(
            DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss")));
}
```

parse 的第二个参数指定按什么方式解析这个时间串，ISO_OFFSET_DATE_TIME 正对应查询返回的那种格式；目标格式 DateTimeFormatter 没有内置，用 ofPattern 自定义。先转成 LocalDateTime，再转成目标格式的字符串，setTime 写回去。重启后再测，时间就变成了 2020-09-19 09:58:34 这种格式，不再是带 T 的样子。

接口本身没问题，但库里的数据量很少，有些问题测不出来，结果也不够真实。真实场景是设备发报文、经 EMQ、由程序接收解析，总不能为了产生数据真买几台设备。做法是写一段代码模拟实体设备发送报文：发送环节是模拟的，接收之后从 EMQ 接过来、解析、告警判断、状态修改、指标值存储，这些过程与生产环境一模一样。目的有两个：产生大量接近生产的测试数据；把已完成的功能整条链路完整测一遍，看看到底存不存在问题。

Mock 类放在 EMQ 包下，加 @Component 注解，方法挂 @Scheduled 定时任务，cron 表达式让它每间隔 10 秒执行一次，只要工程启动，代码就自动运行：

```java
@Scheduled(cron = "0/10 * * * * ?")
public void addDatas() {
    System.out.println(LocalDateTime.now() + "模拟数据产生");
    // 获取所有报文的指标定义
    List<QuotaEntity> quotaList = quotaService.list();
    for (int i = 1; i <= 10; i++) {           // 模拟 10 台设备
        String deviceId = 100000 + i + "";    // 6 位设备编号
        for (QuotaEntity quotaEntity : quotaList) {
            Map<String, Object> map = Maps.newHashMap();  // 报文
            map.put(quotaEntity.getsKey(), deviceId);     // 设备编号
            Random random = new Random();
            int quotaValue = random.nextInt(48);          // 随机指标值
            map.put(quotaEntity.getValueKey(), quotaValue);
            try {
                String json = JsonUtil.serialize(map);    // 序列化成 JSON
                emqClient.publish(quotaEntity.getSubject(), json);
                Thread.sleep(20);
            } catch (JsonProcessingException e) {
                e.printStackTrace();
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }
    }
}
```

设备编号以 10 万为基数循环递增，拼一个空引号让数字自动转成字符串，得到 100001 到 100010 共 10 台。设备编号的 key（sKey）、指标值的 key（valueKey）、发送的主题（subject）都从指标定义里取，不写死；每台设备把所有指标定义都发一遍。指标值用随机数产生（0 到 47），看起来更接近真实数据。连续发送对 EMQ 本身有压力，产生的数据也不真实，所以每发一条休眠 20 毫秒。真正投入生产时，这段模拟代码注掉即可。

验证时工程一启动，定时任务就开始产数据。VS Code 里再查报警日志，遇到 401 是 token 过期了，先走一遍登录拿新 token 替换脚本里的旧值，再查询就能看到大量数据，"温度过高"这类告警值都出来了，测试就有了真实感。

## 小结

报警日志查询是指标数据落库后的第一个查询功能，核心收获三点：InfluxDB 的模糊查询用正则式写法（=~/值/ 全模糊、^ 开头、$ 结尾），与 MySQL 的 LIKE 完全不同；count 统计必须指明 field 类型的具体字段，不能写 count(*)；动态条件用 StringBuilder 按参数判空拼接，查询记录与查询总数两条语句共享同一段 WHERE。

工程结构上复用了既有套路：Repository 提供通用方法，映射实体按用途拆分（子类 QuotaAllInfo 扩展 time、专用类 QuotaCount 装 count），Service 封装语句并兜底空结果，Controller 严格对齐 API 文档。时间字段的 ISO 格式在返回前用 DateTimeFormatter 转一道。模拟数据的思路是"发送可模拟、链路必须真实"，这个思路在后续功能测试里还能继续复用。
