# 阿里云邮件与短信推送封装接入：注册邮件通知补齐，预警通知章收官

第十八章预警通知的最后一程交给阿里云通信服务。邮件每天免费 200 封，注册个阿里云免费账号就能做实际应用测试；短信没有免费额度，签名与模板审核严格，课程把对接与封装讲透，等签名模板审核下来，不改一行代码就能启用。这一讲完成邮件与短信的配置封装、调度任务接入、用户注册邮件通知，最后整章验证收官。

## 先给结论

- 阿里云邮件后台配置就两步：发信域名（阿里云域名授权快，绿色为可用）+ 发信地址（选域名、填账号名，发信类型选触发邮件，批量场景选批量邮件）；发信地址就是邮件显示的发信人。
- 短信必须先有签名和模板、审核通过才能使用：运营商监管严格、无免费额度；签名跟随短信一起发送（如同不同银行的通知签署不同银行名称），企业资质申请更快，模板申请还要提供业务使用场景说明。
- 封装套路：AliyunSender 抽象类持有公共配置（区域、访问 key、授权密钥、邮箱账号）并负责 initClient 初始化客户端；MailSender、SmsSender 分别实现 IWarnNotifySender 的同步与异步两个发送方法。
- 邮件用 SingleSendMailRequest，正文支持 HTML，多收件人逗号分隔，大批量建议换 BatchSendMailRequest；短信用 CommonRequest，SignName 与 TemplateCode 对应后台的签名名称和模板编码，模板变量组装成 Map 后以 JSON 方式传入模板参数。
- 调度任务里各分支统一走同步发送：发送之后要反写状态，异步会导致发送失败也照常执行更新；注入按属性名称匹配，smsSender、mailSender 名称写错就无法正常注入。
- 验证结果：预警邮件与注册邮件都能正常收到、内容与数据库一致、发送状态 200；短信记录报签名错误属预期——签名模板审核通过后，集成与调用逻辑无需任何更改。

## 阿里云后台：邮件两步、短信两审

邮件推送的入口在阿里云控制台左上角的"产品和服务"里。第一步配发信域名：已有的域名列表里，绿色代表可用；在阿里云上申请的域名，配置和验证起来都比较快。配置新的域名点击新建域名，输入域名名称确定即可；如果是阿里云上的域名，确定之后会弹出授权提示界面，点击同意授权就行。第二步配发信地址：它就是邮件显示的发信人，新建时选择上面配置好的发信域名，填账号名称，发信类型二选一——单发场景选触发邮件，需要批量发送选批量邮件。

短信的监管口径完全不同。短信不同于邮件，运营商监管比较严格，阿里云对短信的使用管理也非常严苛：必须有相应的签名和模板，且都要审核通过之后才能正常使用。入口同样在产品和服务里的短信服务，点开国内消息，完成签名管理与模板管理两项配置。添加模板时，具备企业资质可用的模板类型相对更多一些，整体审核比较严格，申请时还需要提供业务使用场景的说明。签名会跟随短信一起发送——接收到的银行通知里签署着不同银行的名称，就是这个机制。添加签名要填签名名称（要符合相应的规范）、适用场景（选验证码，则验证码类型的模板会附加相应签名）、签名来源与证明文件信息，公司或企业资质申请起来会快很多。

## 封装：抽象类打底，邮件与短信各一个实现类

工程在 bulls-stock-starter 的 sender 模块里加阿里云 SDK 依赖，注意版本号不要配置错误：

```xml
<!-- 阿里云通信组件依赖 -->
<dependency>
    <groupId>com.aliyun</groupId>
    <artifactId>aliyun-java-sdk-core</artifactId>
    <version>4.1.0</version>
</dependency>
<dependency>
    <groupId>com.aliyun</groupId>
    <artifactId>aliyun-java-sdk-dm</artifactId>
    <version>3.1.0</version>
</dependency>
```

base 包下先落一个抽象类，把阿里云推送服务的必要配置收拢——区域、访问 key、授权密钥、邮箱账号等，并提供初始化方法，初始化完成之后才能进行消息的推送：

```java
@Data
public abstract class AliyunSender {
    /** 区域信息 */
    private String regionId;
    /** 访问 key、授权密钥、邮箱账号等配置同理 */
    private String accessKey;
    protected IClientProfile profile;

    /** 初始化阿里云客户端 */
    public void initClient() {
        this.profile = DefaultProfile.getProfile(getRegionId(), getAccessKey(), getSecret());
        this.client = new DefaultAcsClient(profile);
    }
}
```

service 包下的 MailSender 继承 AliyunSender 并实现 IWarnNotifySender：sendSyncMessage 直接调 sendMessage，真正干活的是后者：

```java
@Override
public SenderResult sendMessage(SenderMessage senderMessage) {
    SingleSendMailRequest request = new SingleSendMailRequest();
    SenderResult result = new SenderResult();
    result.setId(senderMessage.getId());
    try {
        request.setAccountName(getMailAccount());              // 发信地址
        request.setFromAlias("mirson.ho");                     // 发信人别名
        request.setAddressType(1);                             // 地址类型，默认 1
        request.setReplyToAddress(true);                       // 回复地址
        request.setToAddress(senderMessage.getReceiver());     // 收件人，多个逗号分隔
        request.setSubject(senderMessage.getSubject());        // 邮件主题
        request.setHtmlBody(senderMessage.getNotifyContent()); // 正文，支持 HTML
        SingleSendMailResponse response = client.getAcsResponse(request);
        result.setSendStatus(GlobalConstants.STATUS_OK);
        return result;
    } catch (ServerException e) {
        log.error("errorCode: " + e.getErrorCode() + ", errorMsg: " + e.getMessage(), e);
        result.setSendStatus(GlobalConstants.STATUS_ERROR);
        result.setMemo(e.getMessage());
        return result;
    } catch (ClientException e) {
        log.error("errorCode: " + e.getErrorCode() + ", errorMsg: " + e.getMessage(), e);
        result.setSendStatus(GlobalConstants.STATUS_ERROR);
        result.setMemo(e.getMessage());
        return result;
    }
}
```

发送失败会进异常分支，异常主要有两类：服务端的 ServerException 与客户端的 ClientException，都把错误码与错误信息记录下来，便于追踪和排查。收件人地址可以给多个收件人发送邮件，之间用逗号分开；大批量发送时，建议把 SingleSendMailRequest 对象更换为 BatchSendMailRequest 对象。

SmsSender 的结构与邮件类似，请求对象换成 CommonRequest，Method、Domain、Version 与 Action（发送短信的 ACTION）按常量默认值设置，再把参数逐个放进去：

```java
@Override
public SenderResult sendMessage(SenderMessage notifyMessage) {
    CommonRequest request = new CommonRequest();
    request.setMethod(MethodType.POST);
    request.setDomain(DOMAIN);
    request.setVersion(VERSION);
    request.setAction(ACTION_SEND_SMS);
    request.putQueryParameter("RegionId", getRegionId());                   // 区域
    request.putQueryParameter("PhoneNumbers", notifyMessage.getReceiver()); // 接收者手机号
    request.putQueryParameter("SignName", getSmsSignName());                // 短信签名
    request.putQueryParameter("TemplateCode", getSmsTemplateCode());        // 模板编码
    // 模板变量：把模板涉及的所有变量组装为 Map，以 JSON 方式放入模板参数
    Map<String, String> params = new HashMap<>();
    params.put("name", "用户");
    params.put("time", "10分钟");
    params.put("price", "100元");
    // 通过阿里云客户端发送，成功则设置对应状态码；
    // 失败捕获 ServerException / ClientException
}
```

签名名称对应后台签名管理里的名称，模板编码对应模板管理下每个模板的编号，这两项需要配置在工程配置里。课程没有验证通过的短信模板，用一个快递通知模板举例：模板里有三个变量，把模板里涉及的所有变量信息组装为一个 Map，放到模板参数下面即可。短信的发送结果与邮件方式不一样：失败时会返回具体的错误码和原因，通过 response 对象的 getData 获取详情——code 返回错误码，message 返回提示消息。

## 配置与自动装配：开箱即用的 sender 组件

调度服务工程配置里补上阿里云通信服务的配置，属性与抽象类里定义的一一对应：

```yaml
# 阿里云通信服务配置
aliyun:
  sender:
    # 服务区域：cn 代表中国，hangzhou 即杭州
    regionId: cn-hangzhou
    # 访问 key
    accessKey: LTAIapcN...XAlA
    # 授权密钥
    secret: ******
    # 发送邮箱账号
    mailAccount: mirson.ho@mail.mirson.cn
    # 短信模板编码
    smsTemplateCode: SMS_173342473
    # 短信签名名称
    smsSignName: 传智汇提醒
```

这些都是必要的配置属性，不要配置错误。为了让应用服务模块开箱即用，sender 模块里再加一个自动化配置类 AutoStockSenderConfiguration：条件化注解根据工程配置当中是否配置了相应的属性来决定是否生效；区域信息、访问 key、授权密钥、邮箱账号、短信模板、签名等通过 @Value 注入进来；然后创建邮件发送实现类与短信发送实现类两个 Bean——各自初始化客户端之后放入 Spring 容器管理，供项目服务使用。最后补 META-INF/spring.factories 指向配置类：

```properties
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
com.icast.bulls.stock.sender.AutoStockSenderConfiguration
```

## 接入调度任务与注册邮件通知

调度服务里改发送预警通知数据的接口。AccountWarnSettingServiceImpl 先注入短信与邮件的实现接口，名称不要写错——注入是按属性名称去匹配相应实现类的，写错了无法正常注入。发送分支按通知类型扩展：

```java
if (GlobalConstants.ACCOUNT_WARN_NOTIFY_TYPE_EMAIL.equals(notifyMessage.getNotifyType())) {
    // 阿里云邮件通知
    result = mailSender.sendSyncMessage(getSenderMessage(notifyMessage));
} else if (GlobalConstants.ACCOUNT_WARN_NOTIFY_TYPE_SMS.equals(notifyMessage.getNotifyType())) {
    // 阿里云短信通知
    result = smsSender.sendSyncMessage(getSenderMessage(notifyMessage));
} else if (GlobalConstants.ACCOUNT_WARN_NOTIFY_TYPE_APP.equals(notifyMessage.getNotifyType())) {
    // APP 站内通知
    result = appSender.sendSyncMessage(getSenderMessage(notifyMessage));
} else {
    log.warn("no support notify type, pls check!");
    notifyMessage.setMemo("no support type!");
}
// 反写发送状态与发送次数
accountWarnNotifyMessageDao.updateNotifyDataSendStatus(result);
```

这里有个明确的选择：通知都用同步方式发送。原因是下面紧接着要进行消息的反写处理——如果采用异步方式，消息发送失败之后，下面的更新还会正常执行，状态就失真了；同步方式发送一旦出现异常，后面的代码就无法正常执行，状态才是可信的。

用户注册侧同样补齐。之前讲解实现了用户注册与开户功能，当时阿里云还没接入，邮件发送是空缺的；现在已经实现，需要在 StockUserService 里重新增加注册邮件通知功能。先把调度任务用的 pom 依赖加到 stock-user 工程，注入邮件发送服务接口，实现 sendEmailMessage：

```java
private void sendEmailMessage(TradeUserVo tradeUser) {
    SenderMessage messages = new SenderMessage();
    messages.setSubject("智牛股注册成功通知");
    messages.setReceiver(tradeUser.getEmail());
    messages.setId(System.nanoTime());   // 当前服务纳秒级时间，作为唯一标识
    messages.setUpdateTime(new Date());
    messages.setNotifyContent("您的帐号注册成功！用户名：" + tradeUser.getName()
            + "，帐号：" + tradeUser.getEmail());
    log.info("send regist email: " + messages);
    mailSender.sendMessage(messages);    // sendMessage 上有 @Async，异步发送
}
```

组装好邮件主题、接收者信息与通知内容后，通过邮件发送接口完成发送，注册接口里调用 sendEmailMessage 即可。异步发送依赖线程池，configure 包下增加 TaskExecutorConfiguration 配置类（线程池配置之前已经讲解过，不再展开），工程配置文件里补两段——线程池与阿里云通信服务：

```yaml
# 线程池配置
task:
  executor:
    corePoolSize: 5
    maxPoolSize: 10
    queueCapacity: 500
    keepAliveSeconds: 60
```

阿里云通信服务配置与调度服务那份相同，regionId、accessKey、secret、mailAccount、smsTemplateCode、smsSignName 一并补齐，这些都是必要属性。

## 验证与章收官

预警邮件验证的前提：通知记录表里存在数据，且要有邮件通知类型的记录。表里当时是三条数据、对应三种通知类型，发送状态与重试次数都为空。启动相关服务（发送账户预警通知的调度任务之前测试时已经添加），在 XXL-JOB 调度管理后台执行发送账户预警通知的任务，数据库里 EMAIL 那条记录的内容会发送至对应的邮箱。登录邮箱刷新，收到一条账户预警通知邮件，邮件通知的具体内容与数据库一致；再刷新数据库，这条 EMAIL 记录的发送状态为 200，发送处理成功。上面那条短信记录提示了短信签名的错误信息——没有审核通过的签名，属预期；开通短信签名与模板之后可以直接再做测试验证，集成和调用处理逻辑不需要做任何更改。

注册邮件验证：启动用户服务，注册接口是开放的，不需要启动 OAUTH 认证服务。用 Postman 调注册接口（http://127.0.0.1:1068/open/register），Body 里填手机号、用户密码、公司 ID、用户姓名与邮箱地址——邮箱地址必须填写正确（这次验证的就是邮件通知），且不能与数据库中其他账号的邮箱地址重复，否则不能正常注册成功。提交后返回注册成功、用户编号 117；登录邮箱刷新，成功收到用户注册的通知邮件，邮件里的用户编号与 Postman 返回的 117 一致。

章末把两条运维要点钉住。其一，发送账户预警通知的调度任务每次抓取要设定一个上限，避免高峰期数据量过大对任务造成阻塞——阻塞量过大会影响调度服务的稳定性。其二，要记录发送状态、反写更新通知数据，避免因为出现的错误反复进行调用，造成额外的系统开销。另外，阿里云的邮件与短信发送功能其实是共用一个 SDK，邮件验证通过基本等于短信链路就绪，差的是签名与模板的资质。预警通知功能无论从技术层面还是业务层面，复杂度并不高，但逻辑思路不清晰、处理不严谨，就容易出现各种问题——做完和做好还是有很大区别，掌握具体的实现思路、对细节充分考虑才是重点。

## 小结

至此第十八章预警通知真正收官。推送矩阵补齐三种方式：APP 在线推送走 gRPC 加 Netty 长连接，邮件与短信走阿里云通信服务，三者共用同一套通知记录表与发送任务，只差 notifyType 分支与各 Sender 实现。落地节奏值得复用：第三方服务先在控制台把资质配齐（发信域名、发信地址、签名、模板），再用抽象类收拢公共配置、实现类只管发送，最后用自动装配加 spring.factories 让业务模块开箱即用；同步发送加状态反写保证数据可信，抓取上限保护调度服务。注册邮件这类"顺手补齐"的功能也验证了封装的价值——依赖一引、接口一注，几行代码就能复用整条发送链路。
