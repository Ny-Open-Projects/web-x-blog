## 纲要

- 问题：点赞评论明细在 MongoDB，但卡片要回显的总数存在 HBase 的 `message` 行；同一条 message 的计数更新会撞上 HBase 行锁，形成热点
- 思路：计数先在 Redis 里累加（快、无锁竞争），再由一个"脉冲"任务延迟批量写回 HBase
- 写回用分布式锁（setNX）串行化，避免多个脉冲任务重复刷同一行
- 关键点：HBase 调用可能失败，锁必须在 `finally` 中释放，否则会死锁
- 效果：把瞬时高并发的计数写，平滑成低频的批量写，行锁压力被打散

## 先准备 HBase 计数写回

不管脉冲怎么做，最终都逃不开两次 HBase 写：把点赞数和评论数更新回 `message` 行。封装两个方法，从连接拿表、构造 Put、写进 `count` 列簇：

```java
public void updateLikeCount(String messageId, int count) throws IOException {
    Table table = hbaseConnection.getTable(TableName.valueOf("message"));
    Put put = new Put(Bytes.toBytes(messageId));
    put.addColumn(Bytes.toBytes("count"), Bytes.toBytes("likeCount"),
            Bytes.toBytes(String.valueOf(count)));
    table.put(put);
    table.close();
}

public void updateRemarkCount(String messageId, int count) throws IOException {
    Table table = hbaseConnection.getTable(TableName.valueOf("message"));
    Put put = new Put(Bytes.toBytes(messageId));
    put.addColumn(Bytes.toBytes("count"), Bytes.toBytes("remarkCount"),
            Bytes.toBytes(String.valueOf(count)));
    table.put(put);
    table.close();
}
```

注意 `count` 是 HBase 里预留的列簇，点赞数和评论数各占一列。这两个方法是"最终落库"，与触发时机解耦。

## 计数先在 Redis 累加

整个体系是异步的，点赞/取消点赞时，不立刻碰 HBase，而是先在 Redis 里做原子自增/自减：

```java
// 点赞 +1 / 取消 -1，评论同理
redisTemplate.opsForValue().increment("message:like:" + messageId, 1);
redisTemplate.opsForValue().increment("message:like:" + messageId, -1);
redisTemplate.opsForValue().increment("message:remark:" + messageId, 1);
redisTemplate.opsForValue().increment("message:remark:" + messageId, -1);
```

这一步极快、无锁竞争，能轻松接住瞬时高并发。真正慢的"写 HBase"被延后了。

## 脉冲：延迟聚合 + 分布式锁写回

所谓"脉冲"，就是另起一个串行任务：拿到锁后，把 Redis 里累计的计数读出来，延迟一小段时间再一次性写回 HBase，然后释放锁。延迟的目的，是让这段时间内的多次自增先在 Redis 里聚成一个值，再写 HBase，从而把行锁冲突平滑掉。

```java
public void flushLikeToHBase(String messageId) {
    // setNX 抢锁，超时 1 分钟，避免脉冲任务并发刷同一行
    Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent("lock:message:like:" + messageId, "1", 1, TimeUnit.MINUTES);
    if (!Boolean.TRUE.equals(locked)) {
        return; // 没抢到锁，本次跳过，下次再刷
    }
    try {
        // 故意延迟（演示用 2 秒，生产可压到毫秒级），让计数先在 Redis 聚合
        Thread.sleep(2000);
        Integer count = (Integer) redisTemplate.opsForValue()
                .get("message:like:" + messageId);
        messageService.updateLikeCount(messageId, count); // 可能抛 IO 异常
    } catch (Exception e) {
        // 记录异常，但不影响释放锁
    } finally {
        // 关键：无论 HBase 是否成功，锁都必须释放，否则会死锁
        redisTemplate.delete("lock:message:like:" + messageId);
    }
}
```

评论计数的脉冲逻辑完全一致，只是 key 换成 `message:remark:*` 和对应的锁。

## 把脉冲接入点赞链路

点赞/取消点赞的服务里，写完 Redis 自增后，触发脉冲任务（可异步）：

```java
// 在 LikeService 的点赞动作中
redisTemplate.opsForValue().increment("message:like:" + likeInfo.getMessageId(), 1);
// 触发脉冲：延迟聚合后写回 HBase
asyncFlushService.flushLikeToHBase(likeInfo.getMessageId());
```

`flushLikeToHBase` 内部自己抢锁、延迟、写回、释放，调用方不必关心细节。

## 实测效果

用 Postman 并发发一批评论请求，`message` 行的 `remarkCount` 都能无缝累加。因为有了 2 秒（可配置）的延迟聚合，HBase 那一行不会被每一次请求都打一次行锁，而是被脉冲"合并"成低频写。延迟时长不是固定的——可以根据系统实际行锁压力调小到毫秒级，目标始终是平滑掉 HBase 的行锁热点。

## 设计要点回顾

| 环节 | 作用 |
| --- | --- |
| Redis 原子自增 | 承接高并发计数，无锁竞争 |
| setNX 分布式锁 | 串行化脉冲任务，避免重复刷行 |
| 延迟聚合 | 把多次自增合并成一次 HBase 写 |
| `finally` 释放锁 | HBase 失败也不能死锁 |
| 可调延迟 | 按行锁压力把延迟压到毫秒级 |
