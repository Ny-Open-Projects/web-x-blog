## 发品链路的前置依赖

商品发布之前，需要先由运营完成类目与品牌的上线，商家再基于运营配置好的类目和品牌去发品。运营在后台的配置内容包括：

- 类目树（如：数码产品 → 3C → 手机）
- 品牌库（如：Apple）
- 属性库（属性名与属性值，供商家发布 SKU 时选择）

本节先完成品牌与类目两张表的建模与发布。

## brand 表：极简的品牌实体

```sql
CREATE TABLE brand (
  id          BIGINT NOT NULL AUTO_INCREMENT,
  create_time DATETIME,
  update_time DATETIME,
  name        VARCHAR(255),
  PRIMARY KEY (id)
);
```

品牌在业务上就是一个名字，字段非常少，这也是"领域职责单一"在表结构上的体现。

## category 表：带层级的类目树

类目与品牌最大的不同是**它有层级关系**，一般设计为三级或四级类目：

```sql
CREATE TABLE category (
  id          BIGINT NOT NULL AUTO_INCREMENT,
  create_time DATETIME,
  update_time DATETIME,
  name        VARCHAR(255),
  level       INT DEFAULT 0,
  parent_id   BIGINT DEFAULT 0,
  PRIMARY KEY (id),
  INDEX parent_id_index (parent_id) USING BTREE
);
```

两个关键字段：

- `level`：类目层级，1 为一级类目，以此类推
- `parent_id`：父节点 ID，根类目的 `parent_id` 为 0，二级类目的 `parent_id` 指向对应的一级类目

### 为什么要提前建 parent_id 索引

**在建表时就需要想清楚后续的查询语句会落在哪些字段上**，并提前把索引结构建好。类目最常见的查询是"查某一个类目下的子类目"，条件就是 `parent_id`，因此这里用 BTREE 索引覆盖它。

等到数据量上来之后再补索引，代价要高得多——不仅要锁表重建，还会经历一段无索引的慢查询窗口。

## 发布接口的实现

品牌与类目的发布逻辑完全一致：接收 JSON 请求体，调用 `save` 落库，再把带自增 ID 的实体返回。

```java
@RestController
@RequestMapping("/brand")
public class BrandController {

    @Autowired
    private BrandService brandService;

    @RequestMapping(value = "create", method = {RequestMethod.POST})
    @ResponseBody
    public JsonReturnType create(@RequestBody Brand brand) {
        brandService.save(brand);
        return JsonReturnType.createType(brand);
    }
}
```

```java
@RestController
@RequestMapping("/category")
public class CategoryController {

    @Autowired
    private CategoryService categoryService;

    @RequestMapping(value = "create", method = {RequestMethod.POST})
    @ResponseBody
    public JsonReturnType create(@RequestBody Category category) {
        categoryService.save(category);
        return JsonReturnType.createType(category);
    }
}
```

两个接口都直接复用 MyBatis-Plus `IService` 提供的 `save` 方法，领域逻辑极简时不需要在 Service 层再包一层。

## 造数据：模拟运营的操作

启动应用（端口 9090），用 Postman 依次发布品牌与三级类目。

发布品牌：

```http
POST http://localhost:9090/brand/create
Content-Type: application/json

{"name": "apple"}
```

发布一级类目：

```http
POST http://localhost:9090/category/create
Content-Type: application/json

{"name": "数码产品", "level": 1, "parentId": 0}
```

发布二、三级类目（注意 `parentId` 指向上一级）：

```http
POST http://localhost:9090/category/create
Content-Type: application/json

{"name": "3c", "level": 2, "parentId": 1}
```

```http
POST http://localhost:9090/category/create
Content-Type: application/json

{"name": "手机", "level": 3, "parentId": 2}
```

最终得到的类目树：

```dir
数码产品 (level=1, parent_id=0)
└── 3c (level=2, parent_id=1)
    └── 手机 (level=3, parent_id=2)
```

**约定：商品默认挂在叶子类目下。** 后续发布 iPhone 这类商品时，`category_id` 应该指向 `手机` 这个 level=3 的叶子节点，而不是中间层节点。这条约定决定了后续商品检索、类目筛选的语义正确性。

## Demo 示例

### 运行说明

1. 在 MySQL 中执行上文的两张建表语句（库名 `socialecom`）
2. 配置 `application.properties` 中的数据源连接
3. 启动 `SocialecomApplication`，服务监听 9090 端口
4. 按"造数据"一节的 HTTP 请求依次调用

### 代码说明

- `Brand` / `Category` 由生成器产出，`@TableId(type = IdType.AUTO)` 声明自增主键，`create_time` / `update_time` 通过 `@TableField(fill = ...)` 交由 `CustomMetaObjectHandler` 自动填充
- Controller 层不写业务逻辑，仅完成参数接收、调用 Service、包装返回三步
- 类目层级由 `level` + `parent_id` 两个字段表达，不引入额外的闭包表或路径字段

### 技术点总结

- 建模时同步规划索引：`parent_id` 承载"查子类目"的高频查询
- 类目树采用邻接表模型（parent_id），写入简单、查询单层子节点高效
- 商品挂叶子类目是一条必须固化的业务约定

## 总结

品牌是极简单实体，类目是带层级的树形实体，二者共同构成商品发布的前置配置。建表时就为 `parent_id` 建索引、约定商品只挂叶子类目，是这一节最值得记住的两点工程经验。配合 MyBatis-Plus Generator，一张新表从建表到具备发布接口的成本被压缩到几分钟，但也需要注意二次生成覆盖文件的风险。
