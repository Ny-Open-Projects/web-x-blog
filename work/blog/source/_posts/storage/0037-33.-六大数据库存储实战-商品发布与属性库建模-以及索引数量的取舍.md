## 纲要

- `item` 表设计：商品只挂叶子类目与品牌
- 索引不是越多越好：单表索引超过五个会拖慢写入
- 领域模型不等于数据模型：给 `Item` 补充 `sellerName` / `brand` / `category` 等富字段
- 属性库建模：`attribute_name` 与 `attribute_value` 的一对多结构
- 给 `attribute_name` 补 `category_id`：用类目收敛可选属性，避免商家发品混乱
- `@TableField(exist = false)` 的正确用法

## item 表：商品的骨架

```sql
CREATE TABLE item (
  id          BIGINT NOT NULL AUTO_INCREMENT,
  create_time DATETIME,
  update_time DATETIME,
  name        VARCHAR(255),
  seller_id   BIGINT,
  category_id BIGINT,
  brand_id    BIGINT,
  PRIMARY KEY (id),
  INDEX name_index (name) USING BTREE,
  INDEX seller_id_index (seller_id) USING BTREE
);
```

字段语义：

- `name`：商品名称，后续要做模糊搜索
- `seller_id`：发布该商品的商家，商家后台发品时由登录态注入
- `category_id`：**叶子级类目** ID，商品只挂在类目树的叶子节点上
- `brand_id`：商品所属品牌

## 索引数量的取舍

`name`、`seller_id`、`category_id`、`brand_id` 四个字段理论上都需要索引，但这里只建了两个。原因是：**MySQL 单表索引超过五个之后，插入效率会明显下降**——每次插入和更新都要同步调整所有索引的 B+ 树结构，索引越多，写放大越严重。

因此只在必要的场景上建索引，本节保留两类查询：

- 按 `name` 做模糊查询（商品搜索）
- 按 `seller_id` 查看某商家下的商品列表（商家后台）

关于 `name` 上的模糊查询，有一条必须遵守的规则：**LIKE 必须走左匹配**，即 `'iphone%'`，不能写成 `'%iphone%'`。左右都加百分号会导致索引完全失效，退化为全表扫描。

## 领域模型的丰富：从外键 ID 到实体对象

生成器产出的 `Item` 只有外键 ID，直接把它返回给前端是不够的——调用方拿到 `seller_id`、`brand_id`、`category_id` 这三个数字，看不到任何可读信息。这就是**领域模型与数据模型的差异**所在：领域模型可以直接把外键背后的实体语义挂进来。

```java
@Data
@EqualsAndHashCode(callSuper = false)
@ApiModel(value = "Item对象", description = "")
public class Item implements Serializable {

    @TableId(value = "id", type = IdType.AUTO)
    private Long id;

    @TableField(fill = FieldFill.INSERT)
    private Date createTime;

    @TableField(fill = FieldFill.INSERT_UPDATE)
    private Date updateTime;

    private String name;

    private Long sellerId;

    @TableField(exist = false)
    private String sellerName;

    private Long categoryId;

    @TableField(exist = false)
    private String category;

    private Long brandId;

    @TableField(exist = false)
    private String brand;

    @TableField(exist = false)
    private List<Sku> skuList = new ArrayList<>();
}
```

关键点在 `@TableField(exist = false)`：它告诉 MyBatis-Plus 这个字段**在数据库表中不存在**，不要在自动生成的 `SELECT` / `INSERT` 语句里拼上它。少了这个注解，`skuList`、`sellerName` 这类非表字段会被当成真实列拼进 SQL，直接导致运行时报错。

`Item` 领域模型的组装发生在商品详情浏览时，由 `ItemServiceImpl.getItem` 完成外键到实体的翻译：

```java
@Override
public Item getItem(Long id, Long shopId) {
    Item item = getById(id);
    if (item == null) {
        return null;
    }
    item.setSellerName(sellerService.getById(item.getSellerId()).getSellerName());
    item.setBrand(brandService.getById(item.getBrandId()).getName());
    item.setCategory(categoryService.getById(item.getCategoryId()).getName());

    QueryWrapper<Sku> skuQueryWrapper = new QueryWrapper<>();
    skuQueryWrapper.eq("item_id", item.getId());
    List<Sku> skuList = skuService.listByShopId(skuQueryWrapper, shopId);
    item.setSkuList(skuList);
    return item;
}
```

## 商品发布接口

```java
@RestController
@RequestMapping("/item")
public class ItemController {

    @Autowired
    private ItemService itemService;

    @RequestMapping(value = "/create", method = {RequestMethod.POST})
    @ResponseBody
    public JsonReturnType create(@RequestBody Item item) {
        itemService.save(item);
        return JsonReturnType.createType(item);
    }
}
```

这里 `categoryId` 取 3，对应前面建好的叶子类目"手机"；`sellerId` 取已入驻的商家 ID。

## 属性库建模：attribute_name 与 attribute_value

商品发布出来还不能售卖——必须基于运营配置的属性库做组合，把 iPhone Xs 具体的颜色与尺寸变成 SKU 才能交易。属性库由两张表构成：

```sql
CREATE TABLE attribute_name (
  id          BIGINT NOT NULL AUTO_INCREMENT,
  create_time DATETIME,
  update_time DATETIME,
  name        VARCHAR(255),
  category_id BIGINT,
  PRIMARY KEY (id)
);

CREATE TABLE attribute_value (
  id                BIGINT NOT NULL AUTO_INCREMENT,
  create_time       DATETIME,
  update_time       DATETIME,
  value             VARCHAR(255),
  attribute_name_id BIGINT,
  PRIMARY KEY (id)
);
```

- `attribute_name`：属性名，如"颜色"、"尺寸"
- `attribute_value`：属性值，如"红色"、"蓝色"、"4 寸"、"5 寸"，通过 `attribute_name_id` 外键归属到某个属性名，是**多对一**关系

对应的领域对象 `AttributeName` 中除了 `name` 还有 `categoryId`：

```java
public class AttributeName implements Serializable {

    @TableId(value = "id", type = IdType.AUTO)
    private Long id;

    private String name;

    private Long categoryId;
}
```

## 给属性名补上类目约束

初版设计漏了 `category_id` 字段。补上它的原因很实际：**不同类目允许使用的属性库是不一样的**。如果不加限制，商家选择"手机"类目发品时，会把大量无关属性（比如衣服的尺码）一起筛出来，发品体验会非常混乱。

加上 `category_id` 后，属性库被限定在特定类目范围内。由于表结构发生了变更，有两种处理方式：

- 重新跑一次 `MybatisPlusGenerator`，代价是已有文件被覆盖
- **手工在 Entity、Mapper XML 中补齐字段映射**（推荐，避免覆盖自定义的领域字段）

手工补齐只需在 `AttributeName` 中加入 `categoryId` 字段及其 getter/setter，保证 ORM 映射与表结构一致即可。

## API 速览

| API | 说明 | 参数 | 返回值 |
| --- | --- | --- | --- |
| `@TableField(exist = false)` | 声明非数据库字段，不参与 SQL 拼接 | `exist` | — |
| `@TableField(fill = FieldFill.INSERT)` | 插入时自动填充（如 create_time） | 填充策略 | — |
| `IService.getById(Serializable id)` | 按主键查询 | 主键值 | 实体对象 |
| `QueryWrapper.eq(column,val)` | 构造等值查询条件 | 列名、值 | `QueryWrapper` |
| `IService.save(T entity)` | 插入记录并回填自增主键 | 实体对象 | `boolean` |

## Demo 示例

### 运行说明

1. 执行 `item`、`attribute_name`、`attribute_value` 三张建表语句
2. 若 `attribute_name` 为已存在的旧表，用 `ALTER TABLE attribute_name ADD COLUMN category_id BIGINT;` 补齐字段，并同步修改 `AttributeName` 实体
3. 启动应用后按上文 HTTP 示例依次发布属性名、属性值与商品

### 代码说明

- 商品发布接口只做 `save`，不含业务校验，实际生产中需要校验 `sellerId` 的有效性、`categoryId` 是否为叶子节点
- 领域模型的富字段（`sellerName` / `brand` / `category` / `skuList`）全部标记 `@TableField(exist = false)`，由 Service 层查询后填充
- 索引只建 `name` 与 `seller_id` 两个，把写入性能留给后续更核心的表

### 技术点总结

- 单表索引控制在五个以内，按"是否高频查询"排序后取舍
- LIKE 模糊查询必须左匹配才能命中索引
- 领域模型可以直接内联关联实体的语义，但必须用 `@TableField(exist = false)` 与数据库解耦
- 表结构变更优先手工补映射，避免生成器覆盖自定义代码

## 总结

商品表是导购链路的骨架，属性库是 SKU 组合的原料。这一节有三条工程结论值得记住：索引数量要与写入性能做交换，超过五个就要重新审视；领域模型可以比数据模型更"胖"，用 `@TableField(exist = false)` 承载外键背后的实体语义；属性库必须绑定类目，否则商家发品时的属性候选项会失控。完成属性库之后，下一步就可以在商品下发布 SKU 并绑定属性值组合了。
