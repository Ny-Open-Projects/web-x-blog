## 有状态与无状态：差异从何而来

判断一个服务是有状态还是无状态，标准很朴素：**同一个服务接收到用户的第一次请求和第二次请求时，是否表现出状态上的差异**。

**无状态服务。** 网络层和应用层本身不具备数据存储能力。无论你是用 Nginx 承接请求，还是用 Java 应用执行业务逻辑，只要同一份代码部署在服务上，用户请求在任何时刻执行的代码逻辑都是不变的。前一次请求不会给后一次请求留下任何痕迹。这类服务就是无状态的。

**有状态服务。** 数据存储涉及数据本身的变更。对数据的操作 A 和操作 B，产生的影响会持续反映到后续请求所看到的数据上。今天写入一条订单，明天还能查到，这就是状态。绝大多数数据库服务都是有状态的。

于是就有了一张清晰的对照表：网络层、应用层基本是无状态的；存储层天然是有状态的。

## CPU 密集与 IO 密集：性能天花板的来源

第二个差异是负载类型的差异。

网络层和应用层本质上是在执行代码逻辑，属于 **CPU 密集型**服务。而存储层的能力集中在数据的读取与写入上，属于 **IO 密集型**服务。

关键的一点在于：**CPU 的运算速度远高于 IO 的读取速度**。二者相差几个数量级。这意味着虽然应用层和网络层的"执行"看起来更复杂，但它跑得快；而存储层看起来只是"取一行数据"，却慢得多。

    DB -.->|"耗时占比最高"| RT["响应返回"]

## 差异叠加产生短板效应

把上面两组差异叠加起来，就产生了架构设计中最常见的**瓶颈与短板效应**。

对于无状态、CPU 密集型的服务，只要堆硬件资源做水平扩容，就能提升整体性能。举个例子：一台 Nginx 只能处理 100 QPS，当流量涨到 200 QPS 时，只需要多部署一台 Nginx，把 DNS 指向分散到两台机器上。因为它无状态，两台机器对外提供的服务能力完全一致——这次扩容是无缝的、无副作用的。

应用层同理。无论是单体还是微服务，只要水平扩展服务器并把 Java 代码部署上去，同样可以做到无瓶颈的平滑扩展。

但存储不一样。它是有状态服务，扩张意味着：

1. **数据搬迁**：新节点不可能空着接流量，必须有数据才有意义。
2. **分片路由**：数据要按某种规则分布到多个节点，请求要能找到正确的节点。
3. **一致性协调**：多副本之间的数据同步、故障切换都需要额外的算力。

再加上 IO 远低于 CPU 的查询能力，短板效应就非常严重：**一次互联网查询请求的最大耗时，往往消耗在最后那次数据库的 IO 读取上**；写操作同样如此。

## 存储层的两大考核指标

正因为上述原因，在架构设计的分层体系里，存储层必须同时扛住两个核心指标：

| 指标 | 含义 | 为什么重要 |
| --- | --- | --- |
| 水平扩展瓶颈 | 存储能否在不显著牺牲正确性与可用性的前提下扩容 | 有状态 + 数据搬迁，扩容成本远高于无状态服务 |
| IO 存取效率 | 单次读写的延迟与吞吐 | IO 速度远低于 CPU，是全链路耗时的短板 |

这两个指标构成了后续所有存储优化的出发点：

- 为了缓解 **IO 效率**，我们引入缓存、引入更合适的存储引擎、做索引优化；
- 为了缓解 **水平扩展**，我们做读写分离、分片、分布式事务以及各类一致性取舍。

后面讨论的六大数据库，本质上都是在这两个指标上做了不同的取舍。理解了这一点，选型时就不再是"Redis 快所以全用 Redis"，而是清楚地知道每一次选择放弃了什么。

## 小结

存储数据库之所以在架构分层中占据核心地位，根源是两个不对称：**无状态可以随便扩、有状态扩不起来**；**CPU 很快、IO 很慢**。这两个不对称相互作用，使得整条请求链路的性能与稳定性最终被最慢、最难扩的那一环锁定——也就是存储层。
