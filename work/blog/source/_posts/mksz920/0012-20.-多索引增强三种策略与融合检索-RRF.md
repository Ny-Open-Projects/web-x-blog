## 纲要

- **多索引增强的定位**：属于**检索前增强**，但从「知识库索引」而非「问题」角度优化。核心思想：对同一文档提供**不同类型的 embedding 索引**，从不同维度匹配用户查询，提升检索性能。
- **为什么有效**：用户查询可能涉及不同层面（具体事实 / 抽象概念 / 简短短语），而知识库文档未必做层次区分。多索引让文档从多角度被匹配。
- **三种多索引策略**（共同模式：检索用「小索引向量」、返回用「对应的大文档」作为上下文）：
 1. **父文档 / 大小文档**：大块拆小块，小块向量化入库（小块语义更聚焦、开源 embedding 对短文本提取更好），检索用小块 embedding，返回其对应大块。
 2. **总结索引**：对大块生成摘要，摘要向量化入库，检索用摘要 embedding，返回对应大块（适合用户要的是经验/抽象信息）。
 3. **假设问题索引**：对大块用 LLM 生成若干「假设性问题」（答案能在该块找到），问题向量化入库，检索用假设问题 embedding（问题↔问题同层匹配），返回对应大块。
- **融合检索（混合检索）**：把**稀疏检索（BM25）**与**稠密检索（embedding）**结果按 **RRF（加权倒数排名）** 融合重排，取 top-n 送大模型。鲁棒性显著优于单形态。
- **RRF 公式**：`score = 1 / (k + rank)`，`k` 经验常数取 60；同文档跨方法分数加权求和，分数越高越靠前。
- 本章按课程口径重构；产品/框架名已规范化（BM25 / embedding / BGE / GTE / RRF）；剥离营销与课程群引流。

## 一、多索引增强的思想

用户问题可能落在不同层次（事实、概念、短语），而原始文档只有一种索引粒度。多索引增强通过对**同一文档**建立不同维度的 embedding 索引，让文档能从多角度匹配问题，从而提升泛化性——无论问题从哪个角度来，都能找到语义更相关的上下文。

它仍在检索前对知识库文档做处理，因此属于检索前增强。

## 二、策略一：父文档 / 大小文档（small-to-big）

- **做法**：给定一个较大的分块（如 300 字符），拆成更小的块（如 3 个 100 字符）；只对**小块**做 embedding，把「小块向量 + 对应大块文本」一起存入向量库。
- **检索/返回**：相似度匹配用的是**小块 embedding**，但返回给大模型做上下文的是**小块对应的那个大块**。
- **为何用小块做 embedding**：研究表明，开源 embedding 模型对短文本提取语义效果更好，更容易和问题语义匹配；匹配到小块后，把包含它的大块整体喂给模型，上下文更完整。

## 三、策略二：总结索引（summary index）

- **做法**：对大块用 LLM 生成**摘要/总结**，对摘要做 embedding，把「摘要向量 + 对应大块文本」入库。
- **检索/返回**：匹配用摘要 embedding，返回的是摘要对应的**大块原文**。
- **适用**：用户问题要的往往是经验或抽象信息而非细节时，摘要索引能更好命中，提高返回上下文的相关度。

## 四、策略三：假设问题索引（hypothetical-questions index）

- **做法**：对大块用 LLM 生成若干**假设性问题**（要求这些问题的答案能在该大块中找到），对问题做 embedding，把「假设问题向量 + 对应大块文本」入库。
- **检索/返回**：匹配用的是假设性问题 embedding，返回的是假设问题对应的**大块原文**。
- **直觉**：输入是问题、索引也是问题，做的是「问题↔问题」同层语义匹配，直观且有效。此思路与 RAG 评估中「由答案生成假设问题判断答案相关性」一脉相承。

> 三种策略差异只在「建立索引的维度」（小块 / 摘要 / 假设问题），**相同点**都是返回对应的大块作为上下文。

## 五、融合检索（混合检索）与 RRF

### 为什么融合
稀疏检索关注关键词精准，稠密检索关注语义泛化；二者互补。融合检索同时吸收两者优点，应对查询与文档的多样性、复杂性、不确定性，显著提升检索模块鲁棒性。

### 流程
1. 对问题做**稠密检索**（embedding）得 top-k 文档；
2. 对问题做**稀疏检索**（BM25）得 top-k 文档；
3. 对每个文档计算**融合分数**；
4. 按融合分数重排，取 **top-n** 作为最终上下文送大模型。

### RRF 加权倒数排名
融合分数与文档的排序位置相关，公式为：

```
RRF_score(d) = 1 / (k + rank(d))
```

- `rank(d)`：文档 d 在某检索方法返回结果中的序号（越小越相关）；
- `k`：经验常数，论文取 **60**，防止分数过大。

**演算示例**：稀疏检索返回 [A,B,C]，稠密检索返回 [C,B,A]；各自 RRF 分数（k=60）：

| 文档 | 稀疏(权重0.3) | 稠密(权重0.7) | 融合分 |
| --- | --- | --- | --- |
| A | 1/61×0.3 | 1/63×0.7 | ≈0.160 |
| B | 1/62×0.3 | 1/62×0.7 | ≈0.161 |
| C | 1/63×0.3 | 1/61×0.7 | ≈0.160 |

B 融合分最高排第一；A、C 相等可随机排。若只取 top-1，则上下文为 B。

> 可对两种检索方法设不同总体权重（如上例稠密 0.7、稀疏 0.3），在融合时乘入汇总。

## 六、FAQ

**Q1：三种多索引策略返回的都是大块，那为什么不一开始就存大块 embedding？**
因为大块语义杂，开源 embedding 对短文本（小块/摘要/假设问题）提取更准；检索用小索引命中后，再返回完整大块给模型，兼顾「匹配准」与「上下文全」。

**Q2：RRF 里 k 为什么取 60？**
论文经验值，目的是让排序序号不主导分数（序号通常 1~几十），避免靠前文档分数爆炸。可按业务微调。

**Q3：融合检索一定要稀疏+稠密吗？**
典型是 BM25 + embedding；也可融合多种稠密检索（不同 embedding 模型），核心是「多路召回 + 倒数排名加权」。

**Q4：多索引会增加存储吗？**
会——同一大块要存多份索引向量（小块/摘要/假设问题），但文本只存一份（对应大块），属可控的向量膨胀换召回提升。

## 七、面试高频问答

**1. 三种多索引增强策略？**
父文档（大小文档）、总结索引、假设问题索引；共同点是检索用小索引、返回对应大块。

**2. 融合检索是什么？为什么用？**
把稀疏(BM25)与稠密(embedding)检索结果用 RRF 融合重排；互补关键词精准与语义泛化，提升鲁棒性。

**3. RRF 公式？k 取多少？**
`1/(k+rank)`，k 经验取 60。

**4. 假设问题索引的匹配逻辑？**
用 LLM 给大块生成假设问题并向量化，检索时是「用户问题 ↔ 假设问题」同层语义匹配，返回对应大块。

## 八、ops 提示（增效）

> **多索引优先试「父文档」**：实现最简（切块即可）、收益明显，是 small-to-big 的标配。
>
> **融合检索是上线标配**：单 embedding 易漏关键词命中，BM25+RRF 几乎零成本把鲁棒性拉满。
>
> **权重可调**：若业务更重语义，稠密权重设高（如 0.7）；更重精确术语，稀疏权重设高。先用等权再调。
