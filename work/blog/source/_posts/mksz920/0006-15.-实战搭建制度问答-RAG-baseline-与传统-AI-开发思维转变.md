## 纲要

- **模块化设计**：`model` 模块（LLM + embedding）+ `DOCpass` 模块（文档解析分块）。
- **model 模块**：LLM 用 OpenAI 兼容接口调用 Ollama 部署的 Qwen2-72B（提示词格式、温度 / top_p / max_tokens / 流式，封装成类）；embedding 用 LangChain 的 `HuggingFaceEmbedding` 调 BGE-M3。
- **DOCpass 模块**：PDF 用 RAGFlow deepDOC（OCR / 布局 / 表格 / 合并）；Excel 用 openpyxl 处理合并单元格——遍历合并区左上到右下、填充同值消除歧义。
- **知识库构建**：递归文本分块（chunk_size=128、overlap=30、中文分隔符）；PDF 经 deepDOC 解析后，文本 >200 字符再递归细分、表格直接入列；Excel 合并单元格拆填后转 markdown 入列；统一封装为 LangChain `Document`（加 `test` 元数据）；`Chroma.from_documents` 向量化入库（集合「制度 DB」）。
- **检索测试**：向量集合 `similarity_search(question,k)` 验证召回。
- **RAG 问答 pipeline**：遍历问题 → 向量检索 k 个上下文 → 拼接 `page_content` 成大上下文 → 填入 prompt 模板（「据上下文作答，无相关信息则答不知道」）→ LLM 流式输出。实测加班 / 出差问题回答准确、有据可查。
- **为何叫 baseline**：未经完备测试、能否上线存疑，需在上面快速迭代。
- **传统 vs AI 软件开发**：传统基于规则、**确定性**（开发前即知结果、一步到位）；AI 基于智能、**不确定性**（用户输入多样、LLM 生成随机，初无法确定是否符合预期）。故 AI 开发要先建**可测试 baseline**，用业务测试集评估后迭代；上线后仍持续收集线上数据迭代（与 ML/DL 训练同理）——这是必须的思维转变。

## 一、模块化：model 与 DOCpass

- **model**：封装 LLM（OpenAI 接口 → Ollama 的 Qwen2-72B）与 embedding（LangChain `HuggingFaceEmbedding` + BGE-M3）。
- **DOCpass**：封装 PDF（deepDOC）与 Excel（openpyxl）解析分块。

## 二、知识库构建实战

1. **分块参数**：递归分块 `chunk_size=128`、`chunk_overlap=30`、加中文分隔符（。，、）。
2. **PDF**：deepDOC 解析 → 文本超 200 字符再递归细分、表格直接入列。
3. **Excel**：openpyxl 读合并单元格（遍历 `merged_cells.ranges`，左上到右下填同值）→ 转 markdown 入列。
4. **封装入库**：所有切片包成 LangChain `Document`（附 `test` 元数据）→ `Chroma.from_documents(documents,embedding,collection_name="制度DB")` 向量化入库。

## 三、检索与 RAG 问答 pipeline

- **向量检索**：`collection.similarity_search(question,k)` 取相关文档。
- **prompt 模板**：任务描述（据上下文作答，无则答「不知道」）+ 问题 + 上下文。
- **拼接生成**：把 k 个 `page_content` 拼成大上下文 → 填入模板 → LLM 流式输出。
- **实测**：加班规定、出差问题均能给出准确且上下文可溯源的回答。

## 四、为什么是 baseline 与思维转变

- **baseline 含义**：未做完备性测试，是否符合上线要求存疑，需在它之上快速迭代。
- **传统 vs AI 软件开发对比**：

| 维度 | 传统软件开发 | AI 应用开发 |
|---|---|---|
| 基础 | 基于规则 | 基于智能 |
| 结果 | 确定性（开发前可知） | 不确定性（输入多样 + 生成随机） |
| 路径 | 设计→开发一步到位 | 先建可测 baseline→评估→迭代 |

- **关键思维**：因 AI 流程处处不确定，必须**先快速建可测试基线**，用业务测试集评估、多轮迭代提升；上线后仍收集线上数据持续迭代（ML/DL 训练同理）。

## 五、FAQ

**Q1：Excel 合并单元格为什么要展开填充？**
合并区只在左上角存值，程序读取易丢信息；展开填同值可保证每行数据完整。

**Q2：为什么 PDF 文本超 200 字符还要再递归分块？**
deepDOC 出的文本块可能过长，超 embedding 上限或稀释语义，故二次细分。

**Q3：为什么说这是 baseline 而非成品？**
缺完备测试，上线质量未验证，需迭代评估。

**Q4：传统与 AI 开发最根本的区别？**
传统确定性、一步到位；AI 不确定性，需 baseline + 迭代。

## 六、面试高频问答

**1. 简述知识库构建的几步。**
解析（deepDOC/openpyxl）→ 分块（递归 128/overlap30）→ 封装 Document → Chroma.from_documents 向量化入库。

**2. RAG 问答 pipeline 流程？**
问题 → 向量检索 k 上下文 → 拼接 page_content → 填入 prompt → LLM 流式生成。

**3. 为什么 AI 应用要先建 baseline？**
因 LLM 生成随机、输入多样，结果不确定，须先有可测基线再评估迭代。

**4. 传统 vs AI 软件开发核心差异？**
确定性 vs 不确定性；一步到位 vs baseline+迭代。

## 七、ops 提示（增效）

> **合并单元格先展开**：Excel 入 RAG 前务必拆填，否则整行缺值。
>
> **长块再细分**：deepDOC 出的大块超 200 字符要二次递归，防截断与语义稀释。
>
> **先基线后迭代**：AI 项目别求一次到位，快速出 baseline 用测试集驱动优化。
