## 纲要

- **如何挑基座 LLM**：从「模型大小对能力的影响」与「特定领域实测」两个角度判断，再落地为 RAG 选型四大步骤。
- **涌现能力（emergent）**：小模型不具备、规模突破临界点后突现的能力；表现一为规模过阈值性能跃升（>100B 质变），表现二为提示词策略对小模型无效、对大模型正向（>100B 生效）。
- **评测三步法**：确定评测维度 → 确定评测数据 → 确定评测指标。
- **主流评测基准**：MMLU（伯克利，57 学科 15908 选择题，准确率 + 概率比较法）、OpenCompass（多语言 / 世界知识 / 推理 / 数学 / 代码 / 长上下文 / agent，29 任务 100 数据集）、FlagEval（理解 / 知识 / 推理 / 数学 / 代码 / 任务解决 / 安全价值观）。
- **刷榜风险**：部分模型训练时泄露评测集，需结合自身场景自建测试集实测。
- **RAG 选型四大步骤**：① 模型大小优先最大最好验证可行性，再评估小模型 / 微调；② 构建业务测试集测信息抽取 / 阅读理解 / 工具调用；③ 核算成本（GPU 部署 + API 调用）；④ 数据安全（上下文暴露第三方 → 本地部署或协商）。
- **项目角色能力差异**：产品经理 / 应用开发工程师 / 部署工程师 / 算法工程师 对大模型「了解深度」要求递减（算法最深、产品最浅）。
- 本章按课程口径重构；基准 / 框架名已规范化（MMLU / OpenCompass / FlagEval / LoRA / QLoRA / vLLM 等）；剥离营销与课程群引流。

## 一、从两个角度分辨模型好坏

- **角度一 · 规模效应**：涌现能力表明「模型越大越好」，但涌现与任务类型相关——简单任务 <100B 已够，复杂任务需 >1000B。
- **角度二 · 领域实测**：针对目标场景实测，比排行榜更可靠。

## 二、评测三步法与主流基准

1. **定维度**：要测哪些能力（知识 / 推理 / 代码 / 长上下文 / agent 等）。
2. **定数据**：在哪些数据集上测。
3. **定指标**：如何定量（准确率、匹配准确性、代码单测通过率等）。
- **MMLU**：伯克利，57 学科共 15908 道选择题；指标为准确率，且用「选项 token 概率最高即判对」规避模型输出的随机性。
- **OpenCompass（司南）**：覆盖多语言 / 世界知识 / 推理 / 数学 / 代码 / 长上下文 / agent 等，拆为 29 任务 100 数据集。
- **FlagEval**：评估简单理解 / 知识运用 / 推理 / 数学 / 代码 / 任务解决 / 安全价值观；代码以单测通过判正确。
- **警惕刷榜**：若模型训练阶段把评测集纳入训练，则榜单失真；关键场景务必自建测试集实测。

## 三、RAG 需要 LLM 具备哪些能力

- **上下文阅读理解**：在较多检索上下文中定位与问题最相关的信息。
- **语义理解生成**：理解检索上下文 + 问题，生成合适答案（基础能力）。
- **工具 / 接口调用**：RAG 常需调用外部工具或接口。

## 四、RAG 选型四大步骤

1. **模型大小**：优先选最大最好的模型验证业务可行性；可行后再评估更小模型，或收集业务数据微调小模型以逼近大模型效果。
2. **能力测试**：构建自己的业务测试集，测试信息抽取、阅读理解、工具调用等。
3. **成本核算**：含 GPU 部署成本与第三方 API 调用成本。
4. **数据安全**：调用第三方 API 会把上下文暴露给厂商；安全严格的企业应部署本地大模型，或在采购 API 时协商安全条款。

## 五、不同项目角色对大模型的要求

- **产品经理（最浅）**：懂大模型基础概念与能力边界、会基础提示词、明确业务数据来源，便于与工程沟通与验收。
- **应用开发工程师（最缺）**：懂技术架构（transformer / embedding）、会调用（GPU / 提示词 / Python / transformers）、能评估能力与构建测试集、判断是否微调、熟练中间件（LangChain / LlamaIndex / RAG / Agent / Embedding / 向量库）、懂选型与开发流程、做容错分析。
- **部署工程师**：熟练推理框架（vLLM / SGLang / TensorRT-LLM / DeepSpeed / TGI）、优化技术（压缩量化 / 解码 / 底层 / 分布式并行）、GPU 优化（编程 / 缓存 / 低比特）、架构耗时分析、性能测试（并发 / 资源 / 吞吐）。
- **算法工程师（稀缺）**：掌握训练微调全流程（数据准备 / 预训练 / 指令微调 / RLHF / 分布式训练）、参数高效微调 PEFT（LoRA / QLoRA / p-tuning）、训练框架（PyTorch / Megatron / DeepSpeed）、跟踪前沿、评测自研模型。

## 六、FAQ

**Q1：涌现能力是什么？对选型有何启示？**
小模型没有、规模过临界点后突现的能力（性能跃升 + 提示词策略生效）；启示是「复杂任务要上更大模型」。

**Q2：为什么不能全信排行榜？**
存在训练集泄露式刷榜；应结合自身场景自建测试集实测。

**Q3：RAG 选型为什么把数据安全单列？**
RAG 要把企业上下文送进模型，用第三方 API 等于把私有数据暴露给厂商；敏感数据应本地部署。

**Q4：算法工程师和应用开发工程师的区别？**
前者负责训练 / 微调自研模型（数据 + 分布式训练 + PEFT），后者负责把现成 / 微调模型集成进应用（调用 + 中间件 + 流程）。

## 七、面试高频问答

**1. 评测大模型的三步法？**
定评测维度 → 定评测数据 → 定评测指标。

**2. 列举 2 个中文大模型评测基准及其特点。**
MMLU（选择题准确率 + 概率比较法）、OpenCompass（29 任务 100 数据集，多能力）、FlagEval（含安全价值观与代码单测）。

**3. RAG 选型四大步骤？**
模型大小验证可行性 → 业务测试集测能力 → 核算 GPU/API 成本 → 考虑数据安全（本地化）。

**4. 部署工程师需掌握哪些推理加速技术？**
推理框架（vLLM / SGLang / TensorRT-LLM / TGI）、量化压缩、分布式并行、GPU 缓存与低比特优化。

## 八、ops 提示（增效）

> **先大后小**：RAG 起步用最大模型验证可行性，再逐步换小模型 / 微调压成本。
>
> **自建测试集**：排行榜仅供参考，关键场景必须用自己的数据实测。
>
> **敏感即本地**：含企业私域上下文的 RAG，默认走本地部署，别把数据喂给第三方 API。
