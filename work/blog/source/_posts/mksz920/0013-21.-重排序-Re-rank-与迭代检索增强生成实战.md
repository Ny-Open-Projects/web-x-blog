## 纲要

- **Re-rank 的定位**：属于**检索后增强**。对检索模块召回的众多文档做**再次筛选/重排**，只挑与问题最相关的送进大模型。
- **为什么必须 Re-rank**：① embedding 相似度高 ≠ 真相关（存在「相似但不相关」假阳性）；② 召回文档太多直接进上下文，会增加大模型答错概率、拖慢速度、引入噪声。Re-rank 让真正相关的文档排更前。
- **主流架构 Cross-Encoder**：不是生成句向量，而是把「查询 + 文档」配对直接送 transformer encoder，输出一个**相关性分数**来排序。常用模型：Cohere（收费 API）、**BGE reranker**（开源本地，可在 HuggingFace / ModelScope 下载）。
- **迭代检索增强生成（系统性增强）**：不是单步增强，而是把 RAG 当模块**多次迭代**——每次迭代把「上一次生成的答案 + 原问题」拼成新问题再去检索，用新答案里的有价值信息召回更准的上下文，最终答案更准确。
- **实战要点**：Re-rank 用 BGE reranker（GPU 推理、构造 query-doc 配对、取分数降序）；迭代检索用两套 prompt（末次用原模板、其余用「允许尝试回答」模板），非末次温度设高（1.1）以生成更多样信息。
- 本章按课程口径重构；代码为知识重构（外部代码卷未挂载），演示基于前述制度问答 baseline 的 RAG pipeline + LangChain；产品名已规范（BGE / BM25 / LangChain / HuggingFace / ModelScope）。

## 一、Re-rank 的动机与本质

检索模块基于相似度召回一批文档，但 embedding 内在特性会导致「相似度高却不相干」。直接把这些文档全送大模型有两个坏处：

1. **假阳性污染**：相似但不相关的文档干扰生成；
2. **长上下文负担**：文档太多 → 大模型答准难度↑、速度↓、噪声↑。

Re-rank 就是对召回文档做**二次排序**，让与问题更相关、更准确的文档块排到最前，方便筛选 top-n。它是检索后增强，也是现代 RAG 流水线必备环节。

## 二、Cross-Encoder 重排架构

- **与 embedding 模型区别**：embedding（Bi-Encoder）把查询和文档各自编码成向量再比相似度；**Cross-Encoder** 直接把「查询 + 文档」配对输入同一个 transformer encoder，末尾加一个分类层，输出**两者的相关性分数**。
- **流程**：准备 query-doc 配对 → 各自 tokenize → 送模型 → 取分数 → 按分数排序。
- **常用模型**：
 - Cohere rerank（API 调用，收费）；
 - **BGE reranker**（开源本地，HuggingFace / ModelScope 可下，本实战演示对象）。

> 推理过程与 LLM / embedding 推理一致（分词 + 模型 + 取分数），只是输入是「配对数据」且输出是单分数。

## 三、迭代检索增强生成（系统性增强）

- **思想**：不是做一次 RAG，而是做多次。每次迭代都是一次完整 RAG，都会产出一个答案；把「上一次答案 + 原问题」拼成新问题再去检索，用新答案里的有价值信息召回更准的上下文。
- **关键依据**：每次迭代生成的答案里可能含回答原问题所需的额外信息（即便不精确），这些信息进入下一轮检索能提高匹配度。
- **示例**：问「赢得 2015 年冠军的队员身高多高」——首次检索只拿到「夺冠」信息，模型勉强给个身高描述（198cm，不精确）；第二次把「问题+198cm 描述」当新查询，更容易命中知识库里真实身高文档，最终答案既含谁夺冠、又含有据可查的准确身高。

## 四、实战：制度问答 Re-rank（BGE reranker）

基于前述 baseline 的 RAG pipeline，复用已建好的 Chroma 制度知识库集合：

1. **准备环境**：指定 GPU 卡号；从 transformers 导入 `AutoModelForSequenceClassification` 与 `AutoTokenizer`。
2. **加载模型**：用本地 BGE reranker 路径初始化 tokenizer 与模型，移入 GPU。
3. **稀疏召回**：用 BM25 检索器对问题重检，得到若干候选文档（如前 3 篇，其中部分不相关）。
4. **构造配对**：遍历候选文档，把「问题 + 文档内容」组成配对列表。
5. **打分**：配对 tokenize（带 padding、最大长度）→ 送模型 → 取 logits 作为重排分数。
6. **排序**：分数转 CPU、转 numpy，乘 -1 后 `argsort` 取降序索引。
7. **精选**：取最相关文档（如排序第一）放回 RAG pipeline 让 LLM 生成。

> 实测：重排后选中的文档，大模型生成的答案不仅说明长期病假，还额外总结了请假 100 天的薪资发放标准——相关性明显提升。

## 五、实战：迭代检索增强生成

1. **函数骨架**：输入 `query`，设定迭代次数（默认 2 次），声明累计答案变量。
2. **拼接新问题**：每次迭代把「原问题 + 上轮答案」拼成 `context_query`；首次无答案则用原问题。
3. **分支 prompt**：非末次用「允许在无相关信息时尝试回答」模板（鼓励生成更丰富多样信息）；末次用原 RAG prompt 模板。
4. **温度策略**：非末次温度设 **1.1**（生成更多样信息，辅助下一轮检索）；末次下调温度保证稳定。
5. **流式输出**：每轮打印中间答案与新一轮检索到的文档，便于观察。

> 实测：首次迭代检索到的文档信息有限；拼接答案后二次检索拿到了更丰富信息，模型据此给出更全面的回答。

## 六、FAQ

**Q1：有了 embedding 相似度，为什么还要 Re-rank？**
相似度是 Bi-Encoder 粗排，存在「相似但不相关」；Re-rank（Cross-Encoder）是细排，对 query-doc 配对精打分，能筛掉假阳性。

**Q2：BGE reranker 和 embedding 模型能共用吗？**
架构同源（都基于 transformer encoder），但任务不同：embedding 出向量、reranker 出分数，不能互相替代，通常串联使用。

**Q3：迭代次数越多越好吗？**
不是。次数多 = 调用 LLM 次数多、延迟高；且答案可能引入噪声。默认 2 次是性价比点，可按业务调。

**Q4：迭代检索非末次温度为什么要高？**
高温让模型生成更多样、更丰富的试探性信息，这些信息进下一轮检索能召回更多潜在相关文档；末次降温保证最终答案稳定。

## 七、面试高频问答

**1. Re-rank 属于哪类增强？为什么需要？**
检索后增强；embedding 相似≠相关，且文档过多污染上下文，Re-rank 二次精排筛选最相关文档。

**2. Cross-Encoder 与 Bi-Encoder 区别？**
Bi-Encoder 各自编码再比相似度（粗排）；Cross-Encoder 把 query+doc 配对同编码输出相关性分数（精排）。

**3. 迭代检索增强生成的核心思路？**
多次迭代，每轮把「上轮答案+问题」拼成新查询再检索，用新信息召回更准上下文。

**4. 迭代非末次温度为何设 1.1？**
高温生成更多样试探信息，辅助下一轮检索；末次降温保稳定。

## 八、ops 提示（增效）

> **Re-rank 是上线必备**：embedding 粗排 + Cross-Encoder 精排，几乎能消除「相似但不相关」的致命假阳性。
>
> **本地优先 BGE reranker**：免费、可离线、数据不出域；Cohere 仅在对效果极致追求且能接受 API 费用时考虑。
>
> **迭代增强慎用**：延迟翻倍起步，只在「单轮召回确实不足」的场景（如多跳推理问题）开启，并固定迭代次数防失控。
