## 纲要

- **目标**：把两份原始数据（IREE 风险事件 JSONL + 企业投资 JSON）解析、预处理、转成三元组，用 `py2neo` 存入 Neo4j，形成「公司/事件类型/投资者/专利」四类实体及三组关系。
- **四类实体**：公司（Company）、事件类型（EventType）、投资者（Investor）、专利（Patent）。
- **三组关系**：公司 -[:HAPPEN]-> 事件类型（关系属性含时间/数值/报道标题/内容）；投资者 -[:INVEST]-> 公司（属性含轮次/时间）；公司 -[:OWN]-> 专利。
- **两大预处理（命门）**：
 1. **id 映射**：投资数据中公司/专利只存 id，需建 `id→对象属性` 字典，把 id 还原成具体实体。
 2. **公司名一致性**：事件数据里的公司主体多为别名/简写（如「格力电器」），投资数据是公司全称（如「珠海格力电器股份有限公司」）→ 用「包含逻辑」建别名↔全称映射（以投资数据全称为准）。
- **入库用 MERGE**：按 `name` 作 key，有则合并无则创建，避免重复节点。
- **实战查询（Cypher）**：按事件类型反查公司、按公司名模糊查事件、投资者→公司→事件多跳。
- 本章按课程口径重构；代码为知识重构（外部代码卷未挂载），演示基于 `py2neo`；产品名已规范（Neo4j / py2neo / IREE / OpenKG）。

## 一、数据解析

### 风险事件数据（JSONL）
每行一个 JSON，事件信息在 `label` 字段（事件类型 + 主体 + 时间/数值等属性）。例：
- 第20条：`label` 含事件类型「裁员」、主体「雪佛龙」、时间属性；
- 第30条：`label` 含「股权质押」、主体、时间、数值（1100万股，2020-05-25）。

> 建模目标：建立「主体(公司) - HAPPEN - 事件类型」，事件属性（时间/数值/报道标题/内容）挂到关系上。

### 投资关系数据（大 JSON）
含三类对象：
- **投资者**：id/名称/投资公司id/轮次/时间（公司只存 id）；
- **公司**：id/名称/别名/经营时间/地址/专利（专利也只存 id）；
- **专利**：名称/类型/id。

> 建「投资者-投资-公司」「公司-拥有-专利」关系时，需把 id 还原成实体。

## 二、两大预处理

### 1. 建立 id 映射字典
遍历数据，把每个对象的 `id` 作 key、对象本身作 value，构建 `id→属性` 字典。后续解析时，将投资关系里的公司 id / 专利 id 映射回完整实体属性。

### 2. 公司名一致性处理（别名↔全称）
- 从事件数据 `label` 的「主体」提取公司名（遍历属性字典，key==主体 即公司名）；过滤脏数据（电器/公司/数值等非真公司名）。
- 从投资数据提取公司全称（type==公司 的 name 字段，数据较干净）。
- 用**包含逻辑**建映射：以投资数据公司全称为准，若事件中的简写名被某全称包含，则建立「简写→全称列表」关系（多为一对一，个别一对多）。例：`小米`→`小米科技有限责任公司`、`格力电器`→`珠海格力电器股份有限公司`、`瑞幸咖啡`→`瑞幸咖啡（北京）有限公司`。

> 这一步是图谱关系不断链的关键，做不好后续查询就找不到节点。

## 三、构建节点与关系（py2neo）

### 实体梳理与关系
四类实体 → 三组关系：
- 公司 发生了 某事件类型（`HAPPEN`）；
- 投资者 投资了 某公司（`INVEST`）；
- 公司 拥有 某些专利（`OWN`）。

### 事件线（公司 + 事件类型 + HAPPEN）
1. 遍历事件数据，建 **EventType** 节点（`MERGE`，以 name 为 key）；
2. 遍历事件属性，把「主体」单独提出作公司名，其余属性暂存；
3. 把简写公司名映射到投资数据全称，建 **Company** 节点（`MERGE`，name=全称）；
4. 用 `Relationship` 建 `公司 -[:HAPPEN {时间/数值/标题/内容}]-> 事件类型`，`graph.create` 入库。

### 投资线（公司 + 专利 + 投资者）
1. type==公司 → 建 Company 节点（属性含地址/创建日），含专利则遍历建 **Patent** 节点 + `公司-[:OWN]->专利`；
2. type==投资者 → 建 Investor 节点；取其 `investCompany` 里的公司 id，经 id 字典还原成公司对象，建 Company 节点（`MERGE` 防重），再建 `投资者-[:INVEST {轮次/时间}]->公司`。

> 因全程 `MERGE`，重复节点不会重复创建。

## 四、实战 Cypher 查询验证

构建完成后用 `MATCH ... RETURN` 验证图谱正确性：

```cypher
// 1. 反查：发生「业绩承诺未达标」事件的公司及报道标题
MATCH (c:Company)-[r:HAPPEN]->(e:EventType {name:'业绩承诺未达标'})
RETURN c.name, r.title

// 2. 模糊查：名称含「比亚迪」的公司发生了哪些事件
MATCH (c:Company)-[r:HAPPEN]->(e:EventType)
WHERE c.name CONTAINS '比亚迪'
RETURN c.name, r.title, e.name
// → 债务增加/产品创新/利润下滑/业务合作/转型

// 3. 单跳：谁投资了「科大讯飞股份有限公司」
MATCH (i:Investor)-[:INVEST]->(c:Company {name:'科大讯飞股份有限公司'})
RETURN i.name

// 4. 多跳：投资者→投资公司→公司发生事件
MATCH (i:Investor {name:'广州基金'})-[:INVEST]->(c:Company)-[r:HAPPEN]->(e:EventType)
RETURN i.name, c.name, e.name
// → 广州基金投了科大讯飞，后者发生裁员/产品创新/股份解禁
```

> 查询结果证明：图谱正确表达了「公司-事件」「投资者-公司」及间接多跳关系。

## 五、FAQ

**Q1：为什么事件数据里的公司名要映射成全称？**
事件数据主体是别名/简写，投资数据是公司全称；不映射则两源节点对不上，关系断链。

**Q2：id 映射解决什么问题？**
投资/专利数据只存 id，需还原成完整实体才能建关系，否则关系指向空壳。

**Q3：为什么入库用 MERGE 而不是 CREATE？**
MERGE 按 name 判重，重复公司/事件节点只保留一份，保证图谱干净可查。

**Q4：HAPPEN 关系的属性为什么挂时间/报道内容？**
把事件上下文（何时发生、数值、原始报道）挂到关系上，查询时可一并取出，丰富上下文。

## 六、面试高频问答

**1. 金融智库图谱有哪四类实体、三组关系？**
实体：公司/事件类型/投资者/专利；关系：HAPPEN(公司-事件)、INVEST(投资者-公司)、OWN(公司-专利)。

**2. 图谱构建两大预处理？**
id 映射（id→实体）、公司名一致性（别名↔全称，以全称准）。

**3. 为什么用 MERGE 入库？**
按 key 判重，防重复节点、保图谱质量。

**4. 多跳查询示例？**
`投资者-[:INVEST]->公司-[:HAPPEN]->事件类型`，一跳查投资、二跳查事件。

## 七、ops 提示（增效）

> **预处理占图谱工程 70% 精力**：id 映射 + 名称一致性做扎实，后面查询才不断链；务必先写断言验证映射覆盖率。
>
> **关系属性别塞太多**：报道 content 很长，查询时可加 `include_content` 开关按需取，避免上下文爆炸。
>
> **先小样本验证再全量**：拿几条事件/投资数据建子图跑通 Cypher，再批量入库，省去全量返工。
