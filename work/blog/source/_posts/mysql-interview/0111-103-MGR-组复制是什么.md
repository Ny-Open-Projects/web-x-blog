> 分类：架构/高可用 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**MGR** / **组复制** / **多数派** / **多写**
> 原文锚点：第 707~711 段「MGR 是 MySQL Group Replication 的缩写，是基于现有 MySQL 复制架构实现的一个插件，最早出现在 5.7」

## 一句话总述
MGR 是 **MySQL Group Replication** 插件（5.7.17 起）：一组 MySQL 实例通过**组通信 + 多数派认证**保持一致，可多节点写入，延迟远小于异步复制。

## 面试官视角
- **考察意图**：对新技术是「听说过」还是「知道它解决什么问题、有什么硬约束」。
- **P5** 知道 MGR 是官方多主方案 / **P6** 能说清组、多数派认证与「基本无延迟」的含义 / **P7** 能列出硬约束：InnoDB、表必须有主键、仅支持 row 格式、推荐奇数节点。
- **红旗**：「MGR 是同步复制，绝对无延迟」；「MGR 能直接提升写性能」；把 MGR 与 NDB Cluster 混为一谈（见 086）。
- **惊艳点**：MGR 各节点**基本无延迟但不保证绝对同步**——事务在本地先应用、冲突在认证阶段裁决，所以原文用词是「基本」而非「完全」 `[经验]`。

## 主问答
**Q：什么是 MGR？它跟传统主从复制比强在哪？**
**A：**
1. **先给结论**：MGR = Group Replication，官方插件，自 **5.7.17** 起提供；一组实例间通过消息通信保持一致性，**每个节点都可独立写入**。
2. **再给机制**：事务在本地执行后进入**组内认证**，由多数派判定是否与并发事务冲突，冲突则回滚；通过后才提交。因此延迟主要来自认证往返，远小于「主库写完再从库慢慢追」的异步链路。
3. **最后给边界**：它**不提升写吞吐**——所有写最终仍要在各节点各应用一次；且硬约束不少：只支持 InnoDB、表必须有主键、binlog 必须是 row 格式、推荐 3/5/9 个奇数节点 `[经验]`。
**加分层**：MGR 解决的是**数据一致性与自动故障转移**，不是写扩展；写扩展要靠分库分表（见 105）。

## ⚠️ 原文纠错
原文称 MGR「最早出现在 MySQL 5.7 版本中」——准确版本是 **5.7.17**，5.7 早期小版本并无 MGR；已按实际发布版本更正。机翻「本科 o 的叉叉 g」还原为 **Percona XtraDB Cluster（基于 Galera）**。
