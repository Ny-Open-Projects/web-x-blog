> 分类：存储引擎 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**pt-online-schema-change** / **触发器** / **分批拷贝** / **表重命名**
> 原文锚点：第 320~345 段「这个工具会先建立一个和要修改的表相同的新表…在分批次把原表中的数据拷贝到新表中…最后把原表和新表进行重命名」

## 一句话总述
pt-online-schema-change **建新结构影子表 → 分批拷贝数据 → 用三个触发器增量同步 → 最后 RENAME 切换**，全程只在重命名瞬间短暂锁表。

## 面试官视角
- **考察意图**：这是"大表 DDL"的标准答案，考你是否理解**触发器增量同步**。
- **P5** 听过工具名 / **P6** 能说出影子表+分批拷贝+重命名 / **P7** 能讲清**三个触发器**的作用与坑（磁盘翻倍、与已有触发器冲突）。
- **红旗**：① 以为它不加任何锁（RENAME 瞬间有锁）；② 不知靠触发器同步增量；③ 忽略磁盘翻倍。
- **惊艳点**：靠**分批（chunk）拷贝**控制锁与复制延迟，比整表 COPY 稳 `[经验]`。验证：执行时看输出的 chunk 进度。

## 主问答
**Q（面试官原话）：** 上千万行的表要加字段，怎么不影业务？

**A：**
1. **先给结论**：用 **pt-online-schema-change**，在**操作系统命令行**跑，不能在 MySQL 客户端里执行。
2. **再给机制**：先按新结构建**影子表**，再**分批**拷原表数据；同时在原表建 **INSERT/UPDATE/DELETE 三个触发器**同步期间增量；拷完 **RENAME 互换表名**，删原表与触发器。只有 RENAME **极短瞬间**锁原表。
3. **最后给边界**：代价是**磁盘翻倍**、拷贝有 IO 压力（故分批控速）；原表**已有触发器**会冲突失败；外键与主键变更需额外评估；老版 PT 对 MySQL 8.0 支持不完整。

**加分层**：先 `--dry-run` 预演，确认无误再用 `--execute`，是上线前标准动作。

## 关键代码
```sql
ALTER TABLE stock ADD COLUMN modified_time TIMESTAMP;   -- 这是要执行的"意图"
```
```bash
# 示意，未验证：--dry-run 预演，确认无误后换 --execute
pt-online-schema-change \
  --alter "ADD COLUMN modified_time TIMESTAMP" \
  D=stock,t=stock,u=dba,p=123456,h=127.0.0.1,P=3306 \
  --charset=utf8mb4 --dry-run
```

## ⚠️ 原文纠错
原文演示中把参数写作 `--execute` 的必要性正确；但原文演示库极小（无必要用工具），且**未提示 PT 对 MySQL 8.0 支持不完整的告警**实为演示环境自身提示，卡面已如实说明。原文"工具在 Linux shell 下运行、不能在 MySQL 客户端执行"正确。机翻「PPonline/PTonline」还原为 pt-online-schema-change。核对范围：第 320~350 段。

## 总结与追问预判
- 影子表 + **三触发器** + 分批拷贝 + RENAME = 大表无损改结构。
- 代价：磁盘翻倍、IO 压力、触发器冲突风险。
