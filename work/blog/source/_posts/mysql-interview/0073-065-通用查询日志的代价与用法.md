> 分类：日志类 | 难度：L2 | 题型：工程题 | 频率：高 | 关键词：**general_log** / **记录所有请求** / **及时关闭**
> 原文锚点：第 157~170 段「客户端从 MySQL 服务器建立连接开始到断开连接这段时间之内，所有的请求信息，无论请求最终是否被成功执行，都会记录…繁忙业务系统中几分钟就可能产生几百兆」

## 一句话总述
通用查询日志记录**连接期间客户端发来的全部请求**（含语法错误的 SQL），是排查"程序到底发了什么"的唯一手段；**默认关闭**，用完必须立刻关并清理。

## 面试官视角
- **考察意图**：看你会不会用日志定位"客户端与数据库不一致"，以及有没有日志成本意识。
- **P5** 知道它记录所有 SQL / **P6** 说清**连失败请求也记**且默认关闭 / **P7** 给出量级代价与"用完即关"纪律。
- **红旗**：① "一直开着方便排查"；② 以为只记成功的 SQL；③ 不知可动态开关。
- **惊艳点**：语法错误的 SQL 在错误日志里可能查不到，在通用日志里**一定在** `[经验]` —— 验证：故意执行一条错误 SQL 后对比两个日志。

## 主问答
**Q（面试官原话）：** 程序改了数据却查不到，怎么定位？

**A：**
1. **先给结论**：临时开启**通用查询日志**，看客户端**实际发来的请求**。
2. **再给机制**：它记录从**建连到断连**期间的全部交互，**无论是否执行成功**——含语法错误 SQL 与连接断开事件，这些慢查询日志不记。
3. **最后给边界**：代价极大，繁忙系统**几分钟几百 MB**，故默认关闭；必须**用完立即关闭并清理**，绝不能长期开。

**加分层**：它和慢查不重叠——慢查只记**执行成功**且超阈值/未走索引的查询，也不记连接事件，做不了行为审计。

## 追问链
| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | 这个日志记什么 | 概念 | 连接期全部请求 | 换题 → 不及格 |
| L2 | 失败的 SQL 记不记 | 机制 | 记，含语法错误 | 判 P5 |
| L3 | 默认开还是关 | 细节 | 默认关闭 | 判 P6 |
| L4 | 开着有什么代价 | 工程判断 | 几分钟几百 MB | 判 P6+ |
| L5 | 能不能长期开 | 架构判断 | 不能，用完即关+清理 | 答上判 P7 |

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| 5.6 / 5.7 | `general_log` 默认 OFF，动态参数 | "默认关，用时再开" |
| 8.0 | 语义不变；仍支持输出到表 `mysql.general_log` | 同上，见 066 卡 |

## 关键代码
```sql
SHOW VARIABLES LIKE 'general_log';
SHOW VARIABLES LIKE 'log_output';       -- FILE / TABLE / NONE

SET GLOBAL general_log = ON;            -- 临时开启，排查完必须关
SET GLOBAL general_log = OFF;
```

## ⚠️ 原文纠错
原文"无论请求最终是否被成功执行都会记录在常规日志中"正确，未发现技术错误。补充原文未提的关键参数：`log_output` 决定日志落到**文件还是表**（`FILE` / `TABLE` / `NONE`），这是启用前的必要确认项 `[经验]`。机翻音译（januarylog、general_log、setgroup、战略vlog）已还原为 general_log、general_log、SET GLOBAL、general_log。

## 总结与追问预判
- 记**全部请求含失败**；默认关；**用完即关 + 清理**。
- 慢查替代不了。
