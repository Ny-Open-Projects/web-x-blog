> 分类：日志类 | 难度：L2 | 题型：工程题 | 频率：中 | 关键词：**binlog_rows_query_log_events** / **原始 SQL** / **ROW**
> 原文锚点：第 393~404 段「我们实际执行的 SQL 和实际所提交的 SQL 完全是两样的…有没有什么办法可以在 ROW 格式中同时记录我们实际提交的 SQL 呢」

## 一句话总述
`binlog_rows_query_log_events=ON` 后，ROW 格式的 binlog 会在行事件**之外额外记一条客户端原始 SQL**，用于排障定位，默认 `OFF`。

## 面试官视角
- **考察意图**：你是否真的用 binlog 排查过问题，而不只是背格式。
- **P5** 知道 ROW 下看到的是行镜像不是原 SQL / **P6** 知道有这个开关 / **P7** 会权衡"可读性 vs 日志量"，并指出**不要为此退回 STATEMENT**。
- **红旗**：① "想看原 SQL 就把格式改成 STATEMENT"；② 以为 ROW 里本来就存 SQL；③ 忽略额外日志量。
- **惊艳点**：开了之后 `mysqlbinlog -vv` 能看到"行镜像 + 原始语句"成对出现 `[实测]`。验证：开启后执行一次 UPDATE 再 `mysqlbinlog -vv` 最新文件。

## 主问答
**Q（面试官原话）：** 线上用 ROW，我想知道程序到底提交了什么 SQL，怎么办？

**A：**
1. **先给结论**：开 `binlog_rows_query_log_events`，不要动 `binlog_format`。
2. **再给机制**：ROW 记录的是**行前后镜像**，`mysqlbinlog` 不加 `-v/-vv` 时是一串不可读编码；即使加 `-v` 转成的 SQL 也**不是客户端原句**。开启该参数后，binlog 会额外写入原始语句事件，排障时可直接对上代码里的 SQL。
3. **最后给边界**：代价是**日志变大**（每条语句多一份文本）。为"看原 SQL"把格式改回 STATEMENT 是**错误解法**——STATEMENT 在主从下有不确定的一致性风险，生产不推荐。

**加分层**：原文演示中先 `FLUSH LOGS` 再执行，正是为了让每条变更落在**新文件**里便于比对，这是读 binlog 的常用手法。

## 关键代码
```sql
SHOW VARIABLES LIKE 'binlog_rows_query_log_events';   -- 默认 OFF
SET GLOBAL binlog_rows_query_log_events = ON;         -- 动态参数，可临时开
FLUSH LOGS;                                           -- 切新文件，便于比对
UPDATE stock SET stock_count = 40 WHERE product_id = 2030 AND warehouse_id = 1;
```

```bash
mysqlbinlog -vv /data/mysqllog/mysql-bin.000005 | grep -n -A2 'stock_count'
```
