> 分类：架构/复制 | 难度：L2 | 题型：工程题 | 频率：高 | 关键词：**拆大事务** / **从库数量** / **并行复制** / **MGR**
> 原文锚点：第 666~696 段「如何尽可能减少这种延迟…最后一个原因无法靠单纯拆分大事务来解决」

## 一句话总述
降延迟按成因对症：大事务**拆小**传输、控制**单主挂载从库数**、从库**并行回放**；前两项改配置即可，第三项要换机制。

## 面试官视角
- **考察意图**：延迟题落到「能不能落地」，而不是背一句「优化 SQL」。
- **P5** 知道要避免大事务 / **P6** 能给出拆事务、限从库数、开并行复制三招 / **P7** 能说出 5.6 库级并行在自己场景无效、必须上 5.7+ 这一关键前提。
- **红旗**：「延迟大就加从库」；「开多线程复制一定有效」；把大表 DDL 也当成能拆的事务。
- **惊艳点**：曾见一主挂**二十多个**从库，业务高峰把主库**网卡带宽打满**——所以从库数量本身是风险项，经验值是**不超过 5 个** `[经验]`。

## 主问答
**Q：主从延迟大，你有哪些办法降下来？**
**A：**
1. **先给结论**：按 100 卡的三段成因对症下药——拆大事务、控从库数、开并行回放。
2. **再给机制**：① 大事务拆小：数百万行 UPDATE 改成循环每次更新几千行；大表 DDL 无法拆，就交给 `pt-online-schema-change` 分批拷贝（见 088）；② 控制一个主库挂载的从库数量，避免主库网卡带宽被 binlog 推送占满；③ 从库启用多线程回放。
3. **最后给边界**：多线程复制在 **5.6 是按库并行**的——若写压力全集中在同一个库，开了也没用；**5.7 起才做到按表/组并行**，所以要用并行复制必须先升到 5.7+（见 102）。
**加分层**：若业务对延迟极敏感，最终手段是换 MGR 组复制，而非继续调异步复制参数（见 103）。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在怎么答 |
|---|---|---|
| 5.6~8.0（验证 8.0.36） | 5.6 库级并行；5.7 起 `LOGICAL_CLOCK` 组并行 | 按三招答，并强调 5.7+ 前提 |

## 关键代码
```sql
-- 5.7+ 开启基于组提交的并行回放（8.0 用 replica 前缀）
SET GLOBAL replica_parallel_type = 'LOGICAL_CLOCK';
SET GLOBAL replica_parallel_workers = 8;   -- 按从库 CPU 与库表分布调整
STOP REPLICA; START REPLICA;               -- 需重启复制线程生效
```

## ⚠️ 原文纠错
原文称 5.7 后「针对表进行多线程复制」，表述偏窄：5.7 的并行依据是 **组提交（LOGICAL_CLOCK）**，同一组提交的事务可并行回放，并非单纯按表 `[经验]`。机翻「大事误/大数」统一还原为**大事务**。
