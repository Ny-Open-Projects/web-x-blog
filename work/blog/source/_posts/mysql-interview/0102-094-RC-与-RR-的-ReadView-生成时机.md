> 分类：事务/隔离级别 | 难度：L4 | 题型：八股题 | 频率：高 | 关键词：**ReadView** / **RC** / **RR** / **可重复读**
> 原文锚点：第 378~379 段「事务的隔离性又分为四个不同的级别，包括读未提交、读已提交、可重复读和串行化」

## 一句话总述
RC 与 RR 共用同一套版本链，差别只在 **ReadView 何时生成**：RC 每条语句生成一次，RR 每个事务只在首次快照读时生成一次并复用。

## 面试官视角
- **考察意图**：隔离级别是背的还是推出来的；能不能顺带说清 RR 下的幻读边界。
- **P5** 背得出四个级别 / **P6** 能说清 ReadView 时机差 / **P7** 能指出 RR 快照读无幻读、当前读仍需间隙锁，并知道 RC 下 binlog 必须用 row 格式。
- **红旗**：「RR 靠加锁实现可重复读」；「RC 与 RR 的差别是锁粒度」；「RR 下不可能有幻读」。
- **惊艳点**：同一事务在 RR 下两次 `SELECT` 结果一致，在 RC 下能看到别的事务刚提交的值 —— 验证：设置会话级别后开事务，中间由另一会话提交一次 UPDATE，对比两次 SELECT（8.0.36 `[经验]`）；另：隔离级别变量在 8.0 名为 `transaction_isolation`，5.7 名为 `tx_isolation`。

## 主问答
**Q：RC 和 RR 在 MVCC 上到底差在哪？**
**A：**
1. **先给结论**：差在 **ReadView 的生成时机**——RC 每条语句新建一次，RR 在事务内首条快照读时建立后一直复用。
2. **再给机制**：ReadView 记录「此刻的活跃事务列表」。RR 复用同一视图，因此之后提交的事务对该视图不可见，读到的始终是事务开始时的版本；RC 每次新建，所以总能看到最新已提交的数据。
3. **最后给边界**：差别**只作用于快照读**，两种级别下当前读都读最新已提交版本。RR 的幻读防护依赖间隙锁，RC 不设间隙锁（外键与唯一键检查除外），这也是 RC 下 `binlog_format` 必须为 ROW 的原因。
**加分层**：RR 复用视图叠加长事务 = 旧版本回收不掉，undo 膨胀（见 091）。

## 关键代码
```sql
-- 会话 A：切换级别后开事务，两次读之间由会话 B 提交一次 UPDATE
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;  -- 换成 REPEATABLE READ 做对照
BEGIN;
SELECT num FROM stock WHERE id = 1;  -- 第 1 次读
-- 此处会话 B 执行 UPDATE 并 COMMIT
SELECT num FROM stock WHERE id = 1;  -- RC：看到新值；RR：仍是旧值
COMMIT;
-- 8.0 用新变量名；5.7 为 tx_isolation
SHOW VARIABLES LIKE 'transaction_isolation';
```

## ⚠️ 原文纠错
原文把四个级别音译为「逐被提交、足以提交、可同复读和串行化」，还原为**读未提交 / 读已提交 / 可重复读 / 串行化**；原文只列出级别名称、未讲 RC 与 RR 的实现差异，本卡实现层结论按 InnoDB 公认行为补充并标 `[经验]`。
