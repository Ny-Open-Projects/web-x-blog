> 分类：架构/复制 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**GTID** / **server_uuid** / **source_id** / **故障转移**
> 原文锚点：第 284~297 段「GTID 由两部分组成，第一部分是执行事务的主机的 UUID，另一部分是该主机上执行过的事务数量」

## 一句话总述
一个 GTID = **`source_id : transaction_id`**（源实例 UUID + 该实例上的递增事务序号），既能标识事务最初在哪提交，也让故障转移变得可计算。

## 面试官视角
- **考察意图**：会不会只看过 `ON`/`OFF` 而没拆过 GTID 结构——拆得开才谈得上排障。
- **P5** 知道 GTID 是全局事务 ID / **P6** 能写出 `uuid:trx_id` 并解释「全局」只在一个复制拓扑内成立 / **P7** 能说出用 `gtid_executed` 集合做差异比对、选出最新从库的迁移步骤。
- **红旗**：「GTID 是全球唯一」；「GTID 就是自增 ID」；「开了 GTID 就不需要 binlog」。
- **惊艳点**：把各从库的 `Executed_Gtid_Set` 做并集，谁包含最多谁就是迁移首选 —— 验证：`SELECT @@gtid_executed` 逐台比对，再用 `GTID_SUBSET()` 判断包含关系（8.0.36 `[经验]`）。

## 主问答
**Q：GTID 长什么样？它解决了什么问题？**
**A：**
1. **先给结论**：形如 `3E11FA47-71CA-11E1-9E33-C80AA9429562:23`，冒号前是**提交它的实例的 UUID**（`source_id`），冒号后是该实例上的**事务序号**，随提交递增。
2. **再给机制**：所谓「全局」**只在一个复制拓扑范围内**成立，不是全宇宙唯一。因为 UUID 能定位最初提交的实例，所以既能追溯来源，又能在换主时直接按 GTID 集合比对差量。
3. **最后给边界**：它只替代「位点定位」这一件事——从库请求增量时告诉主库自己已执行的 GTID 集，主库比对后补齐；**底层仍然依赖 binlog 传输**，不开 binlog 照样玩不转。
**加分层**：换主时挑「已执行 GTID 集最大」的从库当新主，其余从库再指向它即可（见 098）。

## 关键代码
```sql
-- 看本实例已执行的 GTID 集合
SELECT @@gtid_executed;
-- 判断 A 集合是否被 B 集合完全包含（选新主时很有用）
SELECT GTID_SUBSET('aaa:1-10', 'aaa:1-20') AS is_subset;
```

## ⚠️ 原文纠错
原文称「一个一组三层的这种主通复制架构，那么在这四台服务器的范围内」——「一组三从」共 **4 台**，原文先说三台又说四台，属口播口误；按一主三从共四台理解，已统一表述。机翻「GDID/CDID/季节 d」统一还原为 **GTID**。
