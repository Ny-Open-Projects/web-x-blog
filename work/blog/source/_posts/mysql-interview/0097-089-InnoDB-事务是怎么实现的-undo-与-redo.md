> 分类：存储引擎 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**ACID** / **undo log** / **redo log** / **原子性** / **持久性**
> 原文锚点：第 355~390 段「InnoDB 为了实现事务的四个特性，引入了两种日志，一个是 undo log 也就是回滚日志，另一个是 redo log 也就是重做日志」

## 一句话总述
**undo log 记修改前的值 → 保原子性**；**redo log 记修改后的值 → 保持久性**；**隔离性靠锁**；一致性由二者共同保证。事务提交前必须**先把 redo 落盘**。

## 面试官视角
- **考察意图**：ACID 人人会背，这道题考的是**每个字母由什么机制兜底**。
- **P5** 能背 ACID / **P6** 能对应 undo/redo / **P7** 能讲清"数据页不必在提交前落盘，但 redo 必须"这一 WAL 关键点，以及崩溃恢复如何配合两种日志。
- **红旗**：① 说反 undo/redo 记的是前值还是后值；② 认为提交时数据页已写盘；③ 忽略隔离性由锁实现。
- **惊艳点**：**提交前只需 redo 持久化，脏页可以留在缓冲池**——这是 WAL 的核心 `[源码]`。验证：观察 `innodb_flush_log_at_trx_commit` 设置与写入延迟的关系。

## 主问答
**Q（面试官原话）：** InnoDB 事务的 ACID 分别靠什么实现？

**A：**
1. **先给结论**：**原子性 = undo log**，**持久性 = redo log**，**隔离性 = 锁**（共享锁与排他锁互斥），**一致性**由约束与 undo/redo 共同保证。
2. **再给机制**：以转账为例——开始前把 A 账户原值 1000 记入 undo，改后新值 500 记入 redo；B 同理。若中途失败，用 undo 回滚到事务开始前的状态；若提交后崩溃，恢复时用 redo 重做、用 undo 清理未提交部分。
3. **最后给边界**：**必须在事务提交前将 redo 持久化**，而**数据本身不需要在提交前写入磁盘**（可留在内存缓冲池）；这就是为什么 `innodb_flush_log_at_trx_commit` 直接决定"宕机丢不丢数据"。

**加分层**：undo 不只是"回滚用"，它还是 **MVCC 读旧版本的来源**（见 090），这也是为什么长事务会导致 undo 膨胀。

## 关键代码
```sql
START TRANSACTION;
UPDATE account SET balance = balance - 500 WHERE id = 1;  -- 旧值进 undo，新值进 redo
UPDATE account SET balance = balance + 500 WHERE id = 2;
COMMIT;                                                   -- 提交前 redo 已落盘
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';     -- 1 = 每次提交刷盘
```

## ⚠️ 原文纠错
原文"undo 实现原子性、redo 实现持久性、隔离性靠锁、持久性由 redo 与 undo 共同实现"整体正确，但有一处易混：原文的"redo 保证一致性"表述不够严谨——**一致性是约束与两种日志共同作用的结果**，卡面已修正。原文"事务不需要在提交前写入磁盘、只在内存中"应精确为"**数据页**不必在提交前落盘"。核对范围：第 355~395 段。

## 总结与追问预判
- undo=前值=原子性，redo=后值=持久性，锁=隔离性。
- **提交前 redo 必须落盘**，数据页不必。
