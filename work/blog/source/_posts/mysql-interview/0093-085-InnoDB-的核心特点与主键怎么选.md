> 分类：存储引擎 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**聚簇索引** / **行级锁** / **MVCC** / **自增主键** / **自适应哈希**
> 原文锚点：第 216~240 段「InnoDB 是一款事务型的存储引擎…数据逻辑上是按照主键的顺序来进行存储的…支持的是行级锁」

## 一句话总述
InnoDB = **事务 + 聚簇索引（按主键顺序存） + 行级锁 + MVCC**；因为数据按主键排序存储，**主键大小与顺序直接决定索引性能和写入 IO**。

## 面试官视角
- **考察意图**：从"为什么推荐自增 ID 做主键"看你是否真懂聚簇索引。
- **P5** 知道支持事务和行锁 / **P6** 能说清二级索引叶子指向主键（要回表） / **P7** 能解释**主键无序会导致数据迁移与 IO 抖动**，并给出自增 ID 的结论。
- **红旗**：① "用 UUID 当主键更好"；② 不知二级索引存的是主键值；③ 忽略主键长度会放大所有二级索引。
- **惊艳点**：**主键越长，二级索引跟着变大** `[源码]`。验证：INT 与 CHAR(36) 主键对比 .ibd 体积。

## 主问答
**Q（面试官原话）：** InnoDB 表的主键你一般怎么选？为什么？

**A：**
1. **先给结论**：一般用**自增 ID** 列做主键。
2. **再给机制**：InnoDB 是**聚簇索引**组织，数据按主键**逻辑顺序**存放；二级索引叶子节点存的**不是物理地址而是主键值**，所以查询要**回表**一次，主键越大二级索引越大、查找越慢。
3. **最后给边界**：若主键值**无序、随机**（如 UUID），新行要插到已有页中间，会造成**页分裂与数据迁移**，带来随机 IO；自增 ID 则始终追加在末尾，最省 IO。

**加分层**：还有**自适应哈希索引**（按访问统计自动建立，只能等值查找、DBA 无法手工创建）；5.6 起支持全文索引、5.7 起支持空间索引。

| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |

## ⚠️ 原文纠错
原文"InnoDB 数据按主键顺序存储、二级索引叶子指向主键、建议用自增 ID 列作主键"均正确。原文称"InnoDB 支持读未提交、读已提交、可重复读、串行化四种隔离级别，默认级别未明说"——**InnoDB 默认隔离级别是可重复读（REPEATABLE READ）**，卡面补充 `[源码]`。核对范围：第 216~240 段。

## 总结与追问预判
- 聚簇索引 → **主键即数据顺序** → 自增 ID 是最省 IO 的选择。
- 二级索引叶子存主键，所以主键要短。
