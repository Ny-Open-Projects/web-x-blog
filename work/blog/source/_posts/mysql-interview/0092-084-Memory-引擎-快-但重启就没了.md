> 分类：存储引擎 | 难度：L2 | 题型：八股题 | 频率：中 | 关键词：**Memory** / **易失** / **哈希索引** / **固定长度** / **字典表缓存**
> 原文锚点：第 186~215 段「Memory 存储引擎的表数据是存储在内存中的…一旦 MySQL 实例重启，表中的数据就会丢失」

## 一句话总述
Memory 引擎把数据放内存、**默认哈希索引**、读写极快，但**实例重启即丢数据**，字段**定长存储**、**不支持 BLOB/TEXT**，适合缓存**字典映射表**与**周期性统计结果**。

## 面试官视角
- **考察意图**：考"快"的代价是什么，以及你是否知道 MySQL 自己也会用它（内部临时表）。
- **P5** 知道数据在内存、重启丢失 / **P6** 能说清定长存储与不支持大字段 / **P7** 会讲"内存表里必须有一份可重建的持久化副本"，并知道 MySQL 执行 SQL 时会用它存中间结果。
- **红旗**：① 把内存表当持久存储；② VARCHAR 按 CHAR 存导致内存浪费；③ 以为它默认是 B 树索引。
- **惊艳点**：**字段一律定长**，VARCHAR(255) 也按 255 占内存 `[源码]`。验证：建大 VARCHAR 内存表插少量行，看内存占用。

## 主问答
**Q（面试官原话）：** 内存表能用在什么业务上？

**A：**
1. **先给结论**：缓存类场景——**字典映射表**（编码↔说明）和**周期性分析数据**（如当日 Top10 销量）；前提是数据**可重新生成**。
2. **再给机制**：数据在内存，读写远快于磁盘引擎；索引默认用**哈希索引**（等值极快、**不支持范围扫描**），也支持 B 树。MySQL 执行 SQL 需临时存中间结果且满足条件时，也会用它做内部临时表。
3. **最后给边界**：**重启即失**，库里必须另存一份**非易失引擎同构表**用于恢复；字段**定长**存储（VARCHAR 按 CHAR 处理），列别开过大；**不支持 BLOB/TEXT**。

**加分层**：更大规模或要持久化，用 Redis 更合适——内存表定位是库内小表加速。

## ⚠️ 原文纠错
原文"Memory 表不支持 BLOB 或 TEXT 类型""字段固定长度""默认哈希索引"均正确。原文称 MySQL 执行 SQL 时"会把中间结果存到 Memory 引擎表中"——5.7 及以前成立，**8.0 起内部临时表默认使用 TempTable 引擎**，卡面已补版本说明并标 `[经验]`。机翻「漫热/member/mmber」还原为 Memory。核对范围：第 186~215 段。

## 总结与追问预判
- Memory：**快 + 易失 + 定长 + 哈希索引**，只做**可重建**的缓存。
- 8.0 内部临时表已改 TempTable。
