> 分类：服务器配置 | 难度：L2 | 题型：八股题 | 频率：中 | 关键词：**NO_ENGINE_SUBSTITUTION** / **存储引擎** / **静默替换**
> 原文锚点：第 182~186 段「当 CREATE 或 ALTER 语句指定存储引擎不存在或不可用时，严格模式下会报错，宽松模式下则会使用默认的存储引擎代替」

## 一句话总述
`NO_ENGINE_SUBSTITUTION` 决定：**建表/改表指定了一个不存在或不可用的引擎时，是报错还是悄悄换成默认引擎**——默认（5.6 起）是**报错**。

## 面试官视角
- **考察意图**：考"静默降级"意识——你以为建的是 InnoDB，实际可能被换成别的引擎。
- **P5** 知道建表可以指定 `ENGINE=`。
- **P6** 能说出开启后指定不可用引擎会报错、不开启则替换为默认引擎。
- **P7** 能联想到排障场景：引擎被换 → 事务/行锁/崩溃恢复行为全变，且不会有人收到通知。
- **红旗**：① 以为指定了引擎就一定是那个引擎；② 认为"替换成默认引擎"是贴心行为。
- **惊艳点**：被替换后表**仍然建成功**，事务与外键支持可能直接消失 `[经验]` —— 验证：`SHOW TABLE STATUS` 对比 Engine 列，或用 `SHOW CREATE TABLE` 看实际引擎。

## 主问答
**Q（面试官原话）：** 建表时写 `ENGINE=InnoDB`，如果 InnoDB 不可用会怎样？

**A：**
1. **结论**：开启 `NO_ENGINE_SUBSTITUTION` 时**报错拒绝建表**；不开则**静默替换为默认引擎**，表照样建出来。
2. **机制**：这是对"引擎不可用"这一异常的处理策略，属于 sql_mode 对 **DDL 行为**的影响（不只是数据校验）。
3. **边界**：5.6 起该值**默认包含**在 sql_mode 中，所以现代版本默认会报错——这反而是好事，早暴露总比静默降级强。

**加分层**：静默替换的危害在于**事务、行级锁、外键**这些能力可能一起消失，而业务毫不知情，等到故障才发现。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在怎么答 |
|---|---|---|
| 5.6 起 | 该值**默认包含**在 sql_mode | 按"默认报错、不做静默替换"答 |

## 关键代码
```sql
SHOW TABLE STATUS WHERE Name = 't'\G      -- 看实际 Engine
SET SESSION sql_mode = REPLACE(@@sql_mode,'NO_ENGINE_SUBSTITUTION','');
CREATE TABLE t (id INT) ENGINE=NoSuchEngine;  -- 关闭后：静默换成默认引擎
SELECT table_name, engine FROM information_schema.tables WHERE table_schema='appdb';
```

## ⚠️ 原文纠错
原文"严格模式下指定引擎不可用会报错，宽松模式下则使用默认存储引擎代替"——与官方一致，未发现技术错误。补充：5.6 起该值**默认开启**，因此现代版本默认走"报错"路径。机翻音译（noinjuresubstition、super 语句）已还原为 NO_ENGINE_SUBSTITUTION、ALTER 语句。

## 总结与追问预判
- 开启 = **报错**；关闭 = **静默换成默认引擎**（危险）。
- 5.6 起默认开启；静默替换会连事务/行锁/外键一起丢。
