> 分类：服务器配置 | 难度：L2 | 题型：八股题 | 频率：中 | 关键词：**NO_ZERO_DATE** / **NO_ZERO_IN_DATE** / **零日期**
> 原文锚点：第 178~181 段「当设置为 NO_ZERO_DATE 时，日期类型的年数据不能为零，但月和日可以为零；设置为 NO_ZERO_IN_DATE 时，年月日都不能为零」

## 一句话总述
两个值管的是**"零日期"合法性**：`NO_ZERO_DATE` 禁 `0000-00-00` 整值，`NO_ZERO_IN_DATE` 禁年月日中**任意部分**为 0（如 `2026-00-01`）——都是为了让日期检查更严格。

## 面试官视角
- **考察意图**：看你是否能分清这两个名字极像的值，以及它们与严格模式的依赖关系。
- **P5** 知道 MySQL 里存在 `0000-00-00` 这种脏日期。
- **P6** 能说清两者的禁止范围差异（整值 vs 部分为 0）。
- **P7** 能指出**它们只在严格模式下才真正起作用**，并说明 5.7 起两者都进了默认 sql_mode。
- **红旗**：① 把两个值说成同一个；② 以为开了就一定报错误（宽松下可能只是警告）；③ 认为 `0000-00-00` 是合法业务日期。
- **惊艳点**：现实里**不存在 0 年 0 月 0 日**，这类值几乎必然是上游数据错误 `[经验]` —— 验证：`SELECT CAST('0000-00-00' AS DATE);` 与业务表巡检 `WHERE dt = '0000-00-00'`。

## 主问答
**Q（面试官原话）：** 表里出现了 0000-00-00 这种日期，怎么从数据库层面拦住？

**A：**
1. **结论**：用 `NO_ZERO_DATE` 禁止**整值为零**的日期，用 `NO_ZERO_IN_DATE` 禁止**年月任一部分为零**的日期。
2. **机制**：开启后写入这类值会**报错**（严格模式下）或告警（宽松模式下），从而把脏数据挡在库外。
3. **边界**：这两个值**只在严格模式下才真正起作用**；5.7 起它们已包含在默认 sql_mode 中。

**加分层**：根治要往上游走——脏日期多来自外部导入或未校验的默认值，数据库拦截只是最后一道防线。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在怎么答 |
|---|---|---|
| 5.7 / 8.0 | 两者**默认包含**在 sql_mode 中 | 现在按"默认已禁零日期"答；存量库要先清数据再升级 |

## 关键代码
```sql
SET SESSION sql_mode = 'STRICT_TRANS_TABLES,NO_ZERO_DATE,NO_ZERO_IN_DATE';
INSERT INTO t(dt) VALUES('0000-00-00');   -- 报错：Invalid date
INSERT INTO t(dt) VALUES('2026-00-01');   -- 报错：NO_ZERO_IN_DATE 生效
SELECT * FROM t WHERE dt = '0000-00-00';  -- 存量脏数据巡检
```

## ⚠️ 原文纠错
原文"NO_ZERO_DATE 时年不能为零，月和日可以为零；NO_ZERO_IN_DATE 时年月日都不能为零"——与官方定义一致，未发现技术错误。补充原文未强调的：两个值**需与严格模式配合**才产生报错效果。机翻音译（nodesordate、notheserindate）已还原为 NO_ZERO_DATE、NO_ZERO_IN_DATE。

## 总结与追问预判
- `NO_ZERO_DATE` 禁整值零日期，`NO_ZERO_IN_DATE` 禁部分为零；**需严格模式配合**。
- 5.7 起默认包含；存量脏数据要先清再开。
