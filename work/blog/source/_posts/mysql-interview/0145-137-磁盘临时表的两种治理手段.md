> 分类：优化/参数 | 难度：L2 | 题型：工程题 | 频率：高 | 关键词：**tmp_table_size** / **max_heap_table_size** / **慢查询优化**
> 原文锚点：第 64~69 段「找到产生磁盘临时表的 SQL…增大 tmp_table_size 和 max_heap_table_size」

## 一句话总述
磁盘临时表的治理只有两条路：**优化产生它的慢查询**（根治），或**调大内存临时表上限**让它留在内存（缓解）——后者有内存代价。

## 面试官视角
- **考察意图**：会不会把"调参数"当成万能解，而忽略 SQL 本身。
- **P5** 知道调大两个参数 / **P6** 知道**实际生效值是两者的较小值** / **P7** 能指出调大的内存风险与适用边界。
- **红旗**：① 只调参数不提 SQL 优化；② 只调 `tmp_table_size` 忘了 `max_heap_table_size`；③ 说"调大没有代价"。
- **惊艳点**：内存临时表上限取 **min(tmp_table_size, max_heap_table_size)**，只调一个等于没调 `[经验]`。

## 主问答
**Q：磁盘临时表太多导致 IO 高，你怎么处理？**
**A：**
1. **先给结论**：**先治 SQL**（加索引、改写 GROUP BY/ORDER BY、避免大结果集排序），调参只是缓解手段，顺序不能反。
2. **再给机制**：调大 `tmp_table_size` 与 `max_heap_table_size`，让原本落盘的临时表改为内存临时表，从而消除随机写 IO `[经验]`。
3. **最后给边界**：内存临时表上限是**两者取小值**；且该值是**单张表**的上限，并发高时总内存可能成倍放大，盲目调大会引发 OOM。
**加分层**：这两个参数是**会话级**可设的，遇到大查询可在会话内临时调大，不必全局调整——这是最稳的落地姿势。

## 关键代码
```sql
-- 会话级临时调大，只影响当前连接的大查询
SET SESSION tmp_table_size = 256 * 1024 * 1024;
SET SESSION max_heap_table_size = 256 * 1024 * 1024;
```
