> 分类：服务器配置 | 难度：L3 | 题型：事故题 | 频率：中 | 关键词：**5.6 默认严格** / **升级兼容** / **非空列无默认值**
> 原文锚点：第 187~190 段「在 MySQL 5.6 版本之后默认的 sql_mode 值已经变成了严格的事务表模式，所以从 5.5 升级到 5.6 一定要注意这一点」

## 一句话总述
**5.6 起默认 sql_mode 变为 `STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION`**（5.7 再加 `ONLY_FULL_GROUP_BY`、`NO_ZERO_*` 等）——从 5.5 升级上来，**原本能跑的写入会开始报错**。

## 面试官视角
- **考察意图**：这是典型"升级后业务突然报错"的排障题，看你会不会先想到默认配置变了。
- **P5** 知道不同版本配置默认值可能不同。
- **P6** 能说出 5.6 默认变为严格模式，以及非空列无默认值会写不进去。
- **P7** 能给出升级前的完整动作：扫 sql_mode 差异 → 在测试环境用目标版本默认值回归 → 决定改 SQL 还是临时放宽。
- **红旗**：① 升级只看功能不比配置；② 一报错就"把严格模式关掉"了事；③ 不知道 5.7 又加了 ONLY_FULL_GROUP_BY。
- **惊艳点**：升级后最快炸的两类 SQL 是**非空列无默认值**与**非完整 GROUP BY** `[经验]` —— 验证：对比两版本 `SELECT @@global.sql_mode`。

## 主问答
**Q（面试官原话）：** 从 5.5 升到 5.6 之后，原来能插进去的数据现在报错了，可能是什么原因？

**A：**
1. **结论**：**5.6 起默认 sql_mode 变成严格模式**，原宽松模式下被静默截断/转 0 的数据，现在直接报错。
2. **机制**：典型炸点是**非空列没有默认值**——宽松模式会填隐式默认值，严格模式下省略该列写入直接失败。
3. **边界**：5.7 更进一步加入 `ONLY_FULL_GROUP_BY`、`NO_ZERO_DATE`、`NO_ZERO_IN_DATE`、`ERROR_FOR_DIVISION_BY_ZERO`，升级到 5.7/8.0 要再评估一轮。

**加分层**：应急可以在配置文件里**临时放宽**，但这是把问题后推；正解是**升级前用目标版本默认值回归测试**，把不合规 SQL 提前改掉。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在怎么答 |
|---|---|---|
| ≤ 5.5 | 默认**宽松** | 老版本静默吞脏数据 |
| 5.6 | 默认 `STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION` | 升级点一 |
| 5.7 / 8.0 | 再增 `ONLY_FULL_GROUP_BY`、零日期、除零等 | 升级点二，需二次评估 |

## ⚠️ 原文纠错
原文"5.6 之后默认 sql_mode 变成严格的事务表模式"与官方一致；原文举例"非空字段没设默认值就不能再插入空值"表述基本正确，准确说法是**省略该列的写入会失败**，显式插入 NULL 同样失败，卡面已按准确语义表述。

## 总结与追问预判
- 默认 sql_mode 三次收紧：**5.6 严格**、**5.7 加完整分组/零日期**、**8.0 移除 NO_AUTO_CREATE_USER**。
- 升级前必须**比对 sql_mode 并回归测试**，别靠关严格模式应急。
- 下一题：见 039（严格/宽松模式）、036（ONLY_FULL_GROUP_BY）。
