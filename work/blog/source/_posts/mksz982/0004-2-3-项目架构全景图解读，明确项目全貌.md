## 【正文】

### 一、架构全景：三大部分

整张架构图可以分成三大部分来理解：**数据库**、**SpringBoot 子项目** 与 **SpringAI MCP 服务**。数据库是地基，SpringBoot 负责把数据「生产」出来并推给人，SpringAI MCP 负责把数据「暴露」给 AI。下面这张图把文字描述可视化：

```mermaid
flowchart TB
    subgraph EXT[外部数据源]
        RSS[RSS 异动新闻源]
        API[行情 API]
    end
    subgraph SB[SpringBoot 子项目]
        COL[股票定时异动监测模块]
        TR[百度实时翻译模块]
        BOT[钉钉/Telegram 机器人模块]
    end
    subgraph DB[(数据库)]
        MYSQL[(MySQL 持久化)]
        REDIS[(Redis 去重/缓存)]
    end
    subgraph AI[SpringAI MCP 服务]
        MCP[MCP 工具 @McpTool]
        CHAT[ChatClient + @Tool]
    end
    subgraph UX[对外用户端]
        CS[Cherry Studio]
        DIFY[Dify / N8N]
        GRP[钉钉/Telegram 群]
    end

    RSS --> COL
    API --> COL
    COL --> TR --> BOT
    COL --> MYSQL
    COL --> REDIS
    BOT --> GRP
    MYSQL --> MCP
    REDIS --> MCP
    MCP --> CHAT
    CHAT --> CS
    MCP --> DIFY
```

这张图的第一性原理是：**数据只有被「生产」和「消费」两次加工，才产生价值**。生产侧（SpringBoot）解决「数据从哪来、干不干净」，消费侧（MCP + 用户端）解决「人/AI 怎么用」。数据库夹在中间，是二者的契约层。

### 二、数据库：存储与取用的起点

最底层是 **数据库**，负责存储股票相关的信息数据。既然有「存」，就必然有「取」，后续无论是展示、统计还是被 MCP 查询，都要从数据库把数据读出来。存储是这一切的起点。

本项目中数据库采用 **MySQL 主存储 + Redis 辅助**的组合：

- **MySQL** 负责结构化数据的持久化与复杂查询（按代码、按时段、按异动次数聚合）；
- **Redis** 负责分布式去重（避免同一异动事件被重复入库、重复推送）与热点缓存（高频查询的股票概览不必每次打 MySQL）。

这种组合在 `982-demo` 中通过 `application.yml` 配置双源开关，离线 `default` profile 下用 Mock 数据验证主链路，不依赖真实 MySQL/Redis 即可跑通，这正是「工程可本地验证」与「生产可接真实存储」解耦的体现。完整可部署示例见 `982-demo/src/main/resources/application.yml`。

### 三、SpringBoot 子项目：数据采集、翻译与推送

整个大项目由两个子项目组成：SpringBoot 与 SpringAI（下一节讲解）。SpringBoot 内部又包含三个核心模块，它们构成一条完整的数据流水线：

| 模块 | 职责 | 上游 | 下游 | `982-demo` 落点 |
|---|---|---|---|---|
| 股票定时异动监测 | 定时抓取、清洗、入库 | 外部数据源 | 数据库 + 翻译 | `scheduler/RiskScanScheduler`、`provider/` |
| 百度实时翻译 | 英文标题中文化 | 监测模块产出 | 机器人模块 | （Web 服务层翻译适配） |
| 钉钉机器人 | 消息切片、群推送 | 翻译后数据 | 终端群 | `service/RiskEvaluationService` 编排 |

#### 3.1 股票定时异动监测模块

它会定时去抓取股票相关的信息数据，经过数据清洗等一系列处理之后，存入数据库。在 `982-demo` 中，这一职责的物理落点是 `scheduler/RiskScanScheduler`（用 Java 21 虚拟线程做周期扫描）与 `provider/QuoteProvider`（抽象取数接口，`MockQuoteProvider` 提供离线样本、`RealQuoteProvider` 接真实行情）。二者配合，把「何时取、从哪取」与「取到后怎么判定」解耦。完整可部署示例见 `982-demo/src/main/java/com/riskbot/scheduler/RiskScanScheduler.java`。

#### 3.2 百度实时翻译模块

如果目标用户主要用中文交流，而数据源是英文，就需要做翻译。当然，如果项目不需要国际化，直接把原始数据入库即可，所以这块要按实际需求决定是否启用。翻译模块的要点在于**按需启用**与**失败降级**：启用时把英文标题翻成中文提升可读性，失败时保留原文，绝不阻断主链路。

#### 3.3 钉钉机器人模块

抓取并处理好数据之后，通过钉钉机器人把消息推送到钉钉群组。课程让大家在一个群里共同交流，所以需要实现推送功能；而且可以拥有多个群，假设有成千上万个用户，就可以分散到不同的群，直接给对应的群推送，所有群成员都能收到。这正是「系统设计要面向规模」的体现：推送能力从一开始就要支持多群分流，而非写死单群。

**聊天平台对比**（决定以钉钉为主线的现实依据）：

- **Telegram**：开放 Bot API，灵活度高，能做底层二次开发；
- **微信**：底层规则封闭，落地往往依赖第三方 Python 插件方案，稳定性与合规风险更高；
- **钉钉**：企业普及、Webhook 接入简单、群组管理完善，适合作为教学主线。

核心原则始终不变：**无论用哪个平台，核心功能都要我们自己实现**，平台只是通道。

### 四、SpringAI MCP 服务：用自然语言查数据

另一大块是 **SpringAI**，它提供了构建 MCP 服务的方案。我们可以用 MCP 构建各种不同的工具，每个服务都能对外提供能力。这样一来，你就可以通过自然语言跟 AI 系统聊天，直接拿到股票相关的数据，再进一步分析：这只股票有没有可能跌？有没有可能涨？能不能按时段去查，比如某段时间里异动次数比较多的股票，再结合你自己的决策做判断。我们也能做定量分析或二次开发。MCP 服务是后续课程的重点。

在 Spring AI 2.0.1 的语境下，这一块的技术落点非常具体：

- 用 **`@McpTool`** 把「按代码查」「按关键词查」「按异动次数查」等方法标注为 MCP 工具；
- 用 **`ChatClient`** 作为对话入口，配合 **`ToolCallingAdvisor`** 在 Advisor 链里驱动「模型决定调哪个工具」的递归循环；
- 用 **`@Tool`** 让 Agent 具备「查某票风险」的能力（`RiskQueryAgent` 即此范式）。

在 `982-demo` 中，`agent/RiskQueryAgent` 同时扮演「被 MCP 暴露」和「被 ChatClient 驱动」的双重角色，离线时由 `OfflineChatModel` 返回固定 JSON 验证主链路。完整可部署示例见 `982-demo/src/main/java/com/riskbot/agent/RiskQueryAgent.java`。

#### 4.1 为什么 MCP 是「中台」

因为它本身就是我们写代码开发出来的，所以能不能嵌进你自己的项目里？当然可以。你可以把它理解成一个 **中台项目**，并不局限于股票这一个领域：如果你在其他领域提供 MCP 服务，一样可以对接，嵌进自主研发的系统中。例如把 CRM 数据、工单数据、财务数据封装成 MCP 工具，内部 AI 系统就能直接基于私有数据回答，架构完全复用。

### 五、对外用户端：丰富的 AI 工具生态

在用户端，表现形式非常多样。MCP 服务可以作为一个工作流平台来用，比如 **Dify**、**N8N** 这类可以搭建 workflows 的平台（课程里会以 Dify 为例讲解）；此外像 **Coze**、**Cursor**、**Cherry Studio** 等工具也都能继承这种服务能力，接入之后非常灵活方便。

更有价值的是：很多公司内部其实有强烈的 MCP 服务需求。它们自己的数据都存在自己的数据库里，希望通过我们提供的 MCP 服务做一层调用，再配上内部的 AI 聊天系统。把本地工作流定义加上 MCP 服务嵌入自己的系统，这种方式正成为一种趋势，由此构建出来的系统会非常庞大，也是一个「重」的智能体。

### 六、架构的「前后端分离 + 微服务化 + AI 深度集成」本质

整张架构图就是这样一个前后端分离、微服务化、并深度集成 AI 工具的全景：

- **前后端分离**：数据采集/判定（后端）与用户端展示/对话（前端 AI 工具）解耦，通过数据库与 MCP 契约连接；
- **微服务化**：MCP 服务与 Web 服务是两个独立部署单元，共享数据模型但独立演进；
- **AI 深度集成**：AI 不是外挂的「聊天框」，而是贯穿查询、决策、推送闭环的一等公民。

## 【易错点 / 面试题】

1. **面试官问：你的架构里数据库为什么用 MySQL + Redis 两个？**
   答：MySQL 负责持久化与复杂聚合查询（按代码、时段、异动次数），Redis 负责分布式去重与热点缓存。二者职责不同：去重若放 MySQL 靠唯一索引也能做，但在高并发采集下 Redis 原子操作更轻量；热点股票概览用 Redis 缓存可显著降低 MySQL 压力。

2. **易错点：把翻译模块写成阻断式。**
   翻译是付费外部依赖，必须按需启用且失败降级（保留原文），否则一次超时就会卡住整条推送流水线。

3. **易错点：把 MCP 服务与某个具体前端（如 Cherry Studio）强绑定。**
   MCP 是标准化协议，价值在「一次封装、多端复用」。若把逻辑写死进某个前端调用方式，就丧失了中台价值。正确做法是工具逻辑独立于前端，前端只负责接入。

4. **面试题：SpringBoot 子项目和 SpringAI MCP 服务为什么要拆成两个子项目？**
   答：二者变更频率与部署形态不同，采集推送是常驻定时服务，MCP 是对外工具服务。拆分后各自独立构建、独立扩容，共享数据库契约而不共享进程，符合微服务化与故障隔离原则。在 `982-demo` 中虽置于同一工程便于演示，但包边界（provider/engine/service 与 agent）严格分离，生产可进一步拆仓。

## 【小结】

本节把项目全景拆成「数据库地基 + SpringBoot 生产侧 + SpringAI MCP 消费侧 + 丰富用户端」四层，并用架构图固化了数据从「外部源 → 采集清洗 → 存储 → 判定/翻译/推送 / MCP 查询」的完整流向。关键认知是：MCP 服务是脱离股票领域也能复用的「中台」，而拆分两个子项目是为了故障隔离与独立演进。下一节（2-4 如何利用项目进行有效盈利）将切换视角，从技术架构走向商业价值，讲清项目如何通过「信息差」与「会员服务」两条路径产生收益。
