# Go 项目开发: 搜索服务介绍（工程结构与调用链路）

前面把索引、消费、并发、缓存、截断都讲完了，这一节把整个**搜索微服务 `shopsearch`** 摊开看一遍：**目录怎么分、配置怎么加载、前端一个搜索请求是怎么绕一圈回到页面上的**。

## 纲要

- 前端工程：npm 装依赖 + `npm run dev` 起 8080
- 搜索微服务工程目录结构
- config：yaml 配置 → Go 结构体
- global：组件常量 + 索引/业务常量
- internal 分层：pkg / report / server（api、middle、logic）
- `health.go` 用 HEAD 做容器存活检测
- 搜索完整调用链路：web → supermain → shopsearch → ES → 补全 → web
- 为什么 ES 只查命中、商品详情由主服务补全

## 前端启动

前端源码在 `lshop` 工程，根目录两行：

```txt
npm install     # 装依赖
npm run dev     # 起 8080
```
浏览器开 `http://localhost:8080` 就是商城首页。首页搜索框里输「手机」，按 F12 打开 Network，能看到它调的接口是：

```txt
POST http://localhost:8080/api/v1/product/search
```
## 搜索微服务的目录结构

搜索微服务在 `shopsearch` 工程：

```txt
shopsearch/
├── config/
│   ├── config.go        # 把配置解析成 Go 结构体
│   ├── config.yaml      # 项目配置项
│   └── constant.go      # 常量定义
├── global/
│   └── global.go        # 公共常量 + 组件句柄（ES / log / DB）
├── internal/
│   ├── pkg/
│   │   └── error_code.go  # 全局错误码
│   ├── report/
│   │   ├── es/           # 搜索数据模型：product_report.go
│   │   ├── mongo/
│   │   └── mysql/        # 接口层数据模型
│   └── server/
│       ├── api/          # 路由定义
│       │   ├── router.go
│       │   └── health.go
│       ├── middle/       # gin 中间件（鉴权校验）
│       └── logic/        # 接口实现（搜索接口在这里）
├── log/
├── main.go               # 入口
```
几个容易看漏的点：

- **`config.go` + `config.yaml` 是一对**：yaml 管配置，config.go 负责把配置**解析成结构体**（viper + `mapstructure` 标签，**标签名必须和 yaml key 逐字对齐**，错了会静默填零值）
- **`global` 里放两类常量**：一类是**组件常量**（ES、log、DB 这些客户端的名字），一类是**索引相关常量 + 业务常量**
- **`server/api` 只放路由定义，不放实现**；实现类在 `server/logic`（比如搜索接口在 `productSearch`）
- **`health.go` 用 `HEAD` 方法、不返回任何数据**，纯粹给容器做存活探针用
- **`middle` 是 gin 中间件**，主要做 API 层的校验

## 配置项怎么变成结构体

```go
package main

import (
	"fmt"

	"github.com/spf13/viper"
)

// ---------------- config/config.go ----------------

// Config：config.yaml 里 yml 的每一层，都要有一个 mapstructure 标签对应
type Config struct {
	App struct {
		Mode string `mapstructure:"mode"`
		Name string `mapstructure:"name"`
		Port int    `mapstructure:"port"`
	} `mapstructure:"app"`
	Elasticsearch struct {
		Host     string `mapstructure:"host"`
		User     string `mapstructure:"user"`
		Password string `mapstructure:"password"`
	} `mapstructure:"elasticsearch"`
}

var GConfig *Config

func LoadConfig(path string) error {
	fmt.Println("load config from", path)
	v := viper.New()
	v.SetConfigFile(path)
	if err := v.ReadInConfig(); err != nil {
		return err
	}
	cfg := &Config{}
	if err := viper.Unmarshal(cfg); err != nil {
		return err
	}
	GConfig = cfg
	return nil
}

// ---------------- global/global.go ----------------

const (
	// 组件常量：客户端名字要统一，取客户端时按名字取
	ESDefaultClient = "default_client"
	LogDefaultName  = "default_logger"

	// 索引与业务常量
	IndexProduct = "shop_product"
	SearchTopN   = 20
)

func main() {
	_ = LoadConfig
	_ = GConfig
	_ = ESDefaultClient
	_ = IndexProduct
	_ = SearchTopN
	_ = LogDefaultName
}
```
**踩过的坑**：`mapstructure` 标签和 yaml key 对不上时，**不会报错，配置直接是零值**。找这种 bug 要先打印结构体看看哪一层是零。

## 搜索的完整调用链路

在浏览器按 F12 抓到 `POST /api/v1/product/search` 之后，往代码里反查：

```txt
lshop (web, 8080)
  │  POST /api/v1/product/search
  ▼
supermain（商城主服务）
  │  router.go 里匹配到 /api/v1/product/search，调用 goodsSearch
  │  把查询参数组装好，转发给 shopsearch 服务
  ▼
shopsearch（搜索服务，internal/server/api/router.go）
  │  v1.productSearch → logic/productSearch 实现
  ▼
Elasticsearch（shop_product 索引）
  │  返回命中文档
  ▼
supermain 拿到结果 → **补全商品信息** → 返回 lshop
  ▼
页面展示搜索结果
```
关键点在**最后两步**：ES **只负责召回和排序**，返回的是命中文档；**商品详情（价格、库存、标题完整信息）由 `supermain` 从 MySQL/Redis 补全**再返回。

这么做有三个好处：

1. **搜索服务职责单一** —— 它只管查 ES，不碰业务库
2. **搜索结果可以复利用** —— 同一个 ES 结果，前端、App、小程序可以各自按需要补全不同字段
3. **降级空间** —— ES 挂了，主服务还能至少返回骨架数据，不至于全站白屏

路由这一层的定义长这样：

```go

	"github.com/gin-gonic/gin"
```

| --- | --- | --- |
| 配置 | `config/` | yaml 解析成结构体 |

## 注意事项总结

1. 前端 `npm install` + `npm run dev` 起在 **8080**，搜索接口路径是 `/api/v1/product/search`。
2. `config.go` 和 `config.yaml` **成对出现**，配置解析靠 viper + `mapstructure`。
3. **`mapstructure` 标签必须和 yaml key 逐字对齐**，错了是静默零值，不报错。
4. `global` 分两类：**组件常量**（客户端名）和**索引/业务常量**，别混着放。
5. `internal/server/api` 只放**路由定义**，业务逻辑在 `internal/server/logic`。
6. `health.go` 用 **HEAD** 且不返回 body，专门给容器存活探针用。
7. `middle` 放 gin 中间件，做 API 层的**鉴权与参数校验**。
8. 调用链是 **web → supermain → shopsearch → ES → supermain 补全 → web**，链路中间那次转发是**服务间调用**。
9. **ES 只负责召回排序，商品详情由主服务补全** —— 这是搜索服务解耦的关键。
10. `pkg/report` 下 ES / mongo / mysql 三套数据模型分开放，别共用一个结构体。
11. 排查链路时**从 Network 里抓到的 URL 反查 router**，比从页面猜快得多。

## 总结

整个搜索微服务 `shopsearch` 摊开看，目录按 config / global / internal 分层：`config` 用 viper + `mapstructure` 把 yaml 解析成结构体，`global` 放组件常量与索引业务常量，`internal/server/api` 只放路由定义、实现落在 `logic`、`middle` 做鉴权校验，`health.go` 用 HEAD 做容器存活探针。

一次搜索请求的完整链路是 **web → supermain → shopsearch → ES → supermain 补全详情 → web**。关键是 ES **只负责召回和排序**，商品的价格、库存等详情由商城主服务从 MySQL/Redis 补全再返回——搜索服务职责单一、结果可复利用、ES 挂了还能降级返回骨架数据。这套分层是搜索服务解耦的核心。
