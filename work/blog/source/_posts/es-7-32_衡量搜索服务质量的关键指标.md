# 衡量搜索服务质量的关键指标

电商搜索的终极指标是成交率，而搜索召回结果的质量直接影响成交。要优化就得先能量化——本篇讲三类核心指标：**响应时间、首页点击率、MRR（平均倒数排名）**，它们分别对应「快不快」「结果用户点不点」「排得合不合理」。

## 纲要

- 响应时间：一秒响应原则，用 P95/P99 分位数衡量，Prometheus 上报
- 首页点击率：前端埋点 / 后端 requestID 关联点击与请求
- MRR（平均倒数排名）：点击位置的倒数求均值，前三位点击 >30% 即可观
- 输入框自动触发搜索时的「有效请求」过滤

## 响应时间

搜索响应时间直接决定用户愿不愿意用搜索功能。按互联网「一秒响应」原则，从发请求到页面出结果**最多不超过 1 秒**，否则延迟感明显。

```mermaid
flowchart LR
    A["各微服务埋点<br/>记录环节耗时"] --> B["用户级接口汇总"]
    B --> C["Prometheus 上报"]
    C --> D["P95 / P99 分位数看板"]
```

- 在各微服务内埋点记录每个环节耗时，最后在用户级接口统计整体耗时。
- 用 **P95 / P99** 而非平均值衡量，更能反映长尾体验。后续小节会落地商品搜索接口的分位数上报。

## 首页点击率与 MRR

结果是否符合预期，看两点：**首页点击率**和**点击发生的位置靠不靠前**。

```mermaid
flowchart LR
    A["用户发起搜索"] --> B["生成 requestID"]
    B --> C["返回结果列表"]
    C --> D["点击某结果带上 requestID"]
    D --> E["服务端关联: 命中文档+位置"]
    E --> F["计算 首页点击率 / MRR"]
```

**首页点击率** = 单位时间内「发生过首页点击的请求数」/「总请求数」。前端监听点击事件上报即可；后端则给每个请求生成唯一 `requestID`，点击时把 `requestID` 作为请求参数回传，服务端据此关联「被点击文档」。

**MRR（Mean Reciprocal Rank，平均倒数排名）**：取单位时间内被点击文档的位置 `n`，其倒数 `1/n` 即该次 MRR。例如搜出 3 条，点第 1 条 MRR=1，点第 2 条 =1/2，点第 3 条 =1/3。对所有发生点击的请求求平均：

```dir
搜索质量指标体系/
├── 效率指标/
│   └── 响应时间 P95/P99
├── 相关性指标/
│   ├── 首页点击率
│   └── MRR 平均倒数排名
└── 采集方式/
    ├── 前端埋点
    └── 后端 requestID 关联
```

| 指标 | 计算方式 | 健康信号 |
| --- | --- | --- |
| 响应时间 | 用户级接口整体耗时 | P99 ≤ 1s |
| 首页点击率 | 有首页点击请求数 / 总请求数 | 越高越好 |
| MRR | Σ(1/点击位置) / 点击请求数 | 前三位点击 >30% 即可观 |

MRR 最大值不超过 1（用户不可能每次都点第一条）。一般**前三个位置发生点击、MRR 到 30% 以上**，已经是很不错的结果。

## 输入框自动触发场景

为提升体验，用户每输入一个字常自动触发搜索，导致多次请求里只有最后一次有效。统计时需**前端按关键词连续度过滤出「有效搜索请求」**，避免中间无效请求污染指标。

## 总结

衡量搜索服务质量抓住三条主线就够：**响应时间用 P95/P99 守住一秒红线**（后端 Prometheus 上报、各微服务埋点）；**首页点击率与 MRR 量化结果相关性**（前端埋点或后端 requestID 关联点击位置，MRR 前三位 >30% 即健康）；**自动补全场景要过滤有效请求**再统计。指标是优化的依据——点击越靠前、点击率越高，说明排序越合理，后续才能有的放矢地调召回与排序策略。
