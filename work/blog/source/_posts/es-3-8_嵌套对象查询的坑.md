# Go 项目开发: 嵌套对象查询的关系丢失与 nested/join 方案

把一个订单和它的多个商品存成一条文档，商品用对象数组表示 —— 这是最自然的写法，也是最容易查错的写法。本节从"查出来的结果不符合预期"出发，定位根因并给出两种解决方案。

## 纲要

- 问题复现：查"iPhone 且数量 2"为什么查不到却命中了
- 根因：object 数组被扁平化存储，字段间关系丢失
- 方案一：`nested` 类型
- 方案二：`join` 父子文档类型
- 全局序号（global ordinals）：父子文档的性能代价
- nested 与 join 的对比与选型

## 问题复现

订单索引里，`goods` 是对象数组：iPhone 一件、华为两件。

```txt
PUT /order/_doc/1
{
  "id": 1,
  "create_time": 1690000000,
  "pay_amount": 9999.00,
  "goods": [
    { "title": "iphone", "num": 1 },
    { "title": "huawei", "num": 2 }
  ]
}
```

现在查"商品标题为 iphone **且** 数量为 2"的商品 —— 逻辑上它并不存在（iphone 只有 1 件，华为才是 2 件），但查询**命中了这条订单**。

```txt
POST /order/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "goods.title": "iphone" } },
        { "match": { "goods.num": 2 } }
      ]
    }
  }
}
```

## 根因：数组被扁平化

ES 默认把对象数组**打平**存储，上面的文档实际等价于：

```txt
{
  "goods.title": ["iphone", "huawei"],
  "goods.num":  [1, 2]
}
```

于是"iphone"和"2"虽然来自不同的数组元素，在被打平后的字段里却同时满足了条件 —— **数组元素内部的字段对应关系丢失了**。这就是查询结果不符合预期的根因。

## 方案一：nested 类型

把字段类型设为 `nested`，ES 会把数组中的每个对象当作**独立的隐藏文档**索引，字段关系得以保留。

```txt
PUT /order_nested
{
  "mappings": {
    "properties": {
      "id":          { "type": "keyword", "doc_values": false, "index": false },
      "create_time": { "type": "date" },
      "pay_amount":  { "type": "double" },
      "goods": {
        "type": "nested",
        "properties": {
          "title": { "type": "text" },
          "num":   { "type": "integer", "doc_values": false }
        }
      }
    }
  }
}
```

查询必须用 `nested` query：

```txt
POST /order_nested/_search
{
  "query": {
    "nested": {
      "path": "goods",
      "query": {
        "bool": {
          "must": [
            { "match": { "goods.title": "iphone" } },
            { "match": { "goods.num": 1 } }
          ]
        }
      }
    }
  }
}
```

改完之后，"iphone + 数量 2"查不到，"iphone + 数量 1"能查到 —— 结果符合预期了。

## 方案二：join 父子文档

`join` 类型把父子数据存成**不同的 ES 文档**，通过关系字段关联。

```txt
PUT /order_join
{
  "mappings": {
    "properties": {
      "id":          { "type": "keyword" },
      "pay_amount":  { "type": "double" },
      "join_field": {
        "type": "join",
        "relations": { "parent": "child" }
      }
    }
  }
}

# 父文档：订单
PUT /order_join/_doc/1
{
  "id": 1,
  "pay_amount": 9999.00,
  "join_field": { "name": "parent" }
}

# 子文档：商品。必须用父文档 ID 作为 routing
PUT /order_join/_doc/1_1001?routing=1
{
  "title": "iphone",
  "num": 1,
  "join_field": { "name": "child", "parent": 1 }
}
```

两个硬规则：

- 子文档**必须用父文档的 ID 作为 routing**，否则父子不在同一分片，关系查询会失效。
- 父子文档里 `join_field.name` 必须与 mapping 中 `relations` 定义的名字一致（`parent` / `child`）。

查询用 `has_child` / `has_parent` / `parent_id`：

```txt
# 由子文档条件查父文档
POST /order_join/_search
{
  "query": {
    "has_child": {
      "type": "child",
      "query": {
        "bool": {
          "must": [
            { "match": { "title": "iphone" } },
            { "match": { "num": 1 } }
          ]
        }
      }
    }
  }
}

# 由父文档查全部子文档
POST /order_join/_search
{
  "query": {
    "parent_id": { "type": "child", "id": "1" }
  }
}
```

## 全局序号：父子文档的性能代价

`join` 字段在 mapping 里会多出一个 `global_ordinals` 属性，这是理解 join 性能开销的关键。

**全局序号**是建立在 `fielddata` / `doc_values` 之上的数据结构，它为每个不同的 term 按字典序维护一个递增编号。与 fielddata 的序号（只关联单个 segment）不同，全局序号**关联分片中的所有 segment**，因此：

- **每当有新 segment 变为可见（即 refresh 后），全局序号就需要完全重建。**
- 默认策略是**即时构建**，索引变更后作为 refresh 的一部分重建，这会显著增加 refresh 耗时。
- **父 ID 值越多，重建耗时越长** —— 这是不推荐使用父子文档的核心原因。

```mermaid
graph LR
    A[写入/更新文档] --> B[refresh 生成新 segment]
    B --> C[新 segment 可见]
    C --> D[全局序号完全重建]
    D --> E[refresh 耗时增加]
    E --> F[父子查询延迟毛刺]
```

优化思路：**增大 refresh 间隔**能有效减少重建次数；若连接字段不常使用且写入频繁，可以**禁用即时加载**。

## nested 与 join 的对比

| 维度 | `nested` | `join` |
| --- | --- | --- |
| 存储方式 | 父子在同一条 ES 文档中 | 父子是不同文档，独立存储 |
| 读取整份文档 | **更高效**（一次取全） | 需关联查询，性能较差 |
| 更新子文档 | **需整条文档重新索引** | 子文档可单独更新 |
| 额外开销 | 隐藏文档带来的索引膨胀 | 全局序号重建、关系维护开销 |
| 适用场景 | **查多写少**、需要一次取出全部子文档 | **子文档数量多且更新频繁** |

## 实践建议

```dir
├── 推荐：拆分索引
│   ├── order_index（订单维度）
│   └── order_item_index（商品维度，文档 ID = 订单ID_商品ID）
├── 次选：nested（文档体量不大、查多写少）
└── 谨慎：join（子文档多且频繁更新）
```

ES 本身并不擅长处理父子关系文档。**最干净的做法是在建模阶段就绕开它** —— 把订单中的不同商品存成多条文档，用 `订单ID_商品ID` 拼接作为文档 ID。这样既没有扁平化问题，也不需要承担 nested 的重建开销或 join 的全局序号代价。

如果文档体量不大、且希望功能实现简单一些，`nested` 是可接受的折中。`join` 只在子文档数量大且更新频繁的窄场景里才有优势。

## API 速览

| API | 说明 |
| --- | --- |
| `"type": "nested"` | mapping 中把数组字段声明为 nested，保留元素内字段关系 |
| `nested` query | 查询 nested 字段，需指定 `path` |
| `"type": "join"` + `relations` | 定义父子关系字段，如 `{ "parent": "child" }` |
| `routing=<父文档ID>` | 写子文档时必带，保证父子同分片 |
| `has_child` query | 由子文档条件反查父文档，需指定 `type` |
| `has_parent` query | 由父文档条件查子文档 |
| `parent_id` query | 直接按父文档 ID 取全部子文档 |

## 总结

嵌套对象查询的坑，本质是**数组被打平后元素内字段关系丢失**。填坑有两条路：`nested` 保留关系但更新需重建整文档，`join` 支持独立更新但要承担全局序号重建的代价。真正稳妥的做法是在建模阶段就拆分索引，让 ES 只做它擅长的事。
