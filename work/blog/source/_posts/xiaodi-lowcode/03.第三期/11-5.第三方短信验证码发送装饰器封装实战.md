# 第三方短信验证码发送装饰器封装实战

> **导语**：上一节已经能直接调第三方 API 把短信发到手机上，本节把这段调用封装成一个可复用的服务，再由 Controller 注入使用。内容包括：开发者参数如何配置、`fetch` 请求怎么组织 headers 与 JSON body、服务为什么必须在 `providers` 里注册，以及一个很典型的大小写 bug——`appSecret` 属性名写错导致一直返回「不能为空」。最后会说明正式流程里图形验证码 + Redis 防刷的补齐方向。

## 前置知识

建议先看《第三方短信验证码平台接入申请操作指引》完成开通与参数申请，再了解《低代码项目后端接口开发—加密+Redis 模块配置》和《低代码项目后端接口开发—图形验证码接口》，因为正式发送短信前要先用图形验证码做前置校验。本节的 Provider 写法建立在《如何理解Nestjs的提供者Providers》之上。

## 正文

### 先拿到调用资格与参数

课程方提供了免费的短信调用接口，学员不必自己购买第三方套餐。前提是到官网「个人中心 → 开发者」找客服开通短信权限，拿到开发者 ID 与开发者密码；密码会实时更新，练习前记得重新复制一次，粘进本地配置。

把这两个参数抽成一个导出的配置对象（如 `studyClassConfig`），字段是字符串形式的 `appId` 与 `appSecret`。集中放配置而不是散落在请求代码里，后面换账号、换环境只改一处。

### 封装短信发送服务

新建 `utils` 下的文件，导出一个带 `@Injectable()` 的类（如 `TextMessageTwo`）。课程口播里称它为「装饰器」，从代码形态看它其实是一个可被依赖注入复用的 Provider——理解这一点，才知道后面为什么要在模块里注册。

类里定义一个异步方法 `sendMsgCode(form, randomCode)`：

- `form` 是接收短信的手机号，第三方接口要求的属性名就叫 `form`（最终工程封装时该参数改名 `phone`，请求体字段为 `phoneNum`）；
- `randomCode` 是随机生成的验证码（这一版先用四位数字测试），类型为 `number`；
- 因为要发网络请求，方法声明为 `async`。

请求体用 `fetch` 发往课程提供的免费接口：先构造 `headers`，用 `append` 设置 `Content-Type: application/json`；`method` 为 `POST`；`body` 用 JSON 字符串（即 `JSON.stringify`）承载参数。参数来源有三部分——用扩展运算符把 `studyClassConfig` 里的 `appId`、`appSecret` 铺进来，再加上 `code`（验证码）、`form`（手机号），以及固定值的 `templateCode`（模板编号，注意是 `templateCode` 而不是 `templateId`）。第三方 API 要求请求与返回都是 JSON 格式，文档里也列出了成功/失败的响应结构与错误码，联调时可以对照。方法最后把响应以 JSON 形式 `return` 出去。

### 在 Controller 里调用

在 `UserController` 新增一个 POST 接口（路径如 `/user/send_code`），方法声明为 `async`。测试阶段先写死一个手机号和四位验证码，注入刚才的服务后调用 `await this.textMessageTwo.sendMsgCode(form, randomCode)`，用变量接住返回结果并返回给前端；返回里 `code === 0` 代表发送成功。

**别忘了注册 Provider**：这个服务是通过构造函数注入的，必须在 `user.module.ts` 的 `providers` 数组里声明，否则启动时会报依赖解析错误。加上之后注入才生效——这正是「Provider」而不是普通工具函数的区别。

### 联调踩坑：属性名大小写

第一次请求，Node 后端接口本身调用成功了，但返回的 `code` 是 `1`，提示 `appSecret 不能为空`。排查顺序很有代表性：

1. 先看配置对象：`appId`、`appSecret` 都在，值也填了；
2. 再怀疑属性名大小写——一开始写成了首字母大写的 `AppSecret` 之类，与第三方接口文档要求的字段名不一致；
3. 改成 `appSecret`（小写 `a`、大写 `S`）后仍报错，是因为热更新没生效，**重启一次服务**再请求，返回 `code = 0`，手机随即收到四位验证码 `1234`。

两点经验：第三方 API 的字段名大小写敏感，二次封装时务必逐字对齐文档；配置类改动后重启服务再验证，别被旧进程的结果误导。

### 正式流程还差什么

这一版只是把「发短信」跑通，正式接口还要补齐三件事：

- 随机生成四位数验证码，而不是写死 `1234`；
- 手机号 `form` 从前端请求里取，不再写死；
- 把验证码/图形验证码存进 Redis 维护。

正式请求会带 `form`、`captcha`（图形验证码）与类型三个参数：后端先从 Redis 取出图形验证码比对，确认正确且类型匹配，才允许发短信。这一步是为了**防止短信被盗刷**——不做校验，短信套餐很容易被脚本刷爆、成本直线上升。等前端调注册接口时，再拿用户填的手机验证码与 Redis 里的值比对，完成校验闭环。

## 小结

- 先在官网开通短信权限，拿到 `appId`、`appSecret`（密码实时更新），集中放进配置对象。
- 封装带 `@Injectable()` 的 Provider，暴露 `async sendMsgCode(form, randomCode)`；它本质是可注入服务，课程口播称「装饰器」。
- 内部用 `fetch` 发 POST：`Content-Type: application/json`，body 含配置参数、`code`、`form`、固定 `templateCode`，返回 JSON。
- Controller 用 `@Post('send_code')` 注入调用，服务必须在 `user.module.ts` 的 `providers` 注册，`code === 0` 表示成功。
- 属性名大小写敏感（`appSecret`），改配置后要重启服务；正式流程还需随机验证码、前端传 `form`、Redis 存储与图形验证码校验防刷。
