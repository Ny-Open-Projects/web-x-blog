# 项目部署上线—互联公司的DevOps和CI-CD你知道多少？

> **导语**：镜像、容器、Docker-compose 都配好之后，还有个更上层的问题：一套代码从提交到上线，究竟该怎样自动跑完？这一集不写代码，把互联网公司的研发流程、瀑布模型到敏捷开发的演进、DevOps 与 CI/CD 的定义和关系讲清楚，并以阿里云云效为例说明「一次配置、每次自动发布」是怎么落地的。

## 正文

### 一个软件从零到上线要过多少关

先看完整生命周期（省略产品前期调研、竞品分析）：

1. **需求评审**：产品经理确认需求后拉会议，与技术负责人一起判断哪些合理、技术上能否实现、哪些要砍掉；
2. **设计**：产品对接设计，产出设计图；
3. **开发**：前端按设计图、后端按评审时定下的接口与逻辑，前后端同步开发；
4. **测试**：先开测试用例会议确认测试点，再执行测试；
5. **提缺陷与修复**：缺陷提到工单/缺陷管理平台，标注是前端还是后端责任，消息同步到钉钉等 IM；前后端各自修复，测试回归；
6. **验收与上线**：产品确认无误后，先发**预发环境或灰度**验证，再正式上线；
7. **版本迭代**：新版本重新走一遍需求评审，整个流程再来一轮。

这条链路越往后，越依赖「人等人」——一个阶段全部完成才能进下一个。

### 团队演进：从一个人到瀑布模型再到敏捷

讲师用小滴课堂官网产品的成长做了类比：

| 阶段 | 团队形态 | 工作方式 |
| --- | --- | --- |
| 前期 | 功能简单，一个技术员就能搞定 | 一个人包揽所有阶段，谈不上流程 |
| 中期 | 需求变多，新增测试、运维人员 | 不同人做不同阶段，一个阶段做完才进下一个——**瀑布模型**；每次上线靠专人手工操作，效率受限 |
| 后期 | 功能多、项目多、时间少，一人可能同时负责多个项目 | 需要应对快速变化的需求 → **敏捷开发**，并结合 CI / CD |

可以看到，瓶颈不在「写代码」，而在**阶段之间的交接与上线的人工环节**；这正是 DevOps 要解决的地方。

### DevOps：开发运维一体化

DevOps 一词由 **Development（开发）** 与 **Operations（运维）** 组合而成，核心是「开发、测试、运维一体化」：减少部门间沟通成本，实现软件快速、高质量的发布。

具体分工是：运维人员定好规则，搭好**发布平台、监控平台、运维平台**；开发人员基于这些平台和规则，**自主完成发布上线**，不必每次排队等运维。如果开发能自己把这套平台也做出来，那连运维的工作一并包揽了。讲师顺带聊到岗位市场：运维能做的事开发往往也能做，反过来却不成立，这也是运维岗位相对少、待遇偏低的原因之一——理解成「能力边界」的差异即可。

通俗地说，DevOps 就是**开发 + 测试 + 运维**的交集：以前单一职责各管一段，现在一专多能、靠配合提效。

### CI/CD：把流程自动化

CI/CD 指**持续集成（CI）与持续部署（CD）**，是一套实现软件构建、测试、部署自动化的流程。它和 DevOps 紧密相关——DevOps 的「人员一体化、自主发布」，必须借助 CI/CD 工具把整个流程自动化才能落地。

以课程里用的**阿里云云效**为例：

- 本地改完代码，提交到云效的代码仓库；
- 在云效平台里把构建、部署命令**配置一次**（后续除非新增项目才微调）；
- 之后**每次代码改动都自动触发校验**，随时可以发布新版本。

于是「多环境的构建 → 打包 → 测试 → 上线 → 监控」串成一条流水线，产品得以快速迭代。对想去小公司做技术负责人、或整体掌控一条产品线的人来说，开发、测试、运维这几块能力都得具备，而一键发布的 DevOps 实现正是靠 CI/CD 撑起来的。

## 小结

- 完整流程：需求评审 → 设计 → 前后端开发 → 测试 → 缺陷修复 → 预发/灰度 → 上线 → 版本迭代。
- 团队从「一人全包」到瀑布模型，再到多人多项目下的敏捷开发，瓶颈在交接与人工上线。
- DevOps = Development + Operations，强调开发测试运维一体化、减少沟通成本、自主发布。
- CI/CD 是构建/测试/部署的自动化流水线，是 DevOps 落地的技术手段。
- 云效里配置一次构建命令，之后每次代码改动自动触发校验与发布。
