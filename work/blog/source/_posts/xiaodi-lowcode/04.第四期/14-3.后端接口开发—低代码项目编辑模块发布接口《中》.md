# 后端接口开发—低代码项目编辑模块发布接口《中》

## 正文

### 清理模块冗余代码，确定发布接口范围

在 `packages/server` 的 local（低代码）相关模块中，先把上一阶段遗留、暂时用不到的 DTO、Entity 以及控制器里无关接口一并删除，只保留发布接口所需内容。删除 DTO 后依赖会报红，执行依赖安装即可。

### 在 share 子项目统一定义入参类型

请求参数类型统一收敛到 `share` 子项目的 `src/types` 中管理。我们新建 `types/request/low-code.ts`，导出发布请求类型 `PostReleaseRequest`：

```ts
// 代码（已8期）/代码（已8期）/14-3/lowcode/packages/share/src/types/local.ts
import type { IComponent, ILowCode } from '...';

export type PostReleaseRequest = Omit<
  ILowCode,
  'id' | 'account_id' | 'components'
> & {
  components: Omit<IComponent, 'account_id' | 'page_id'>[];
};
```

这里用 TypeScript 内置的 `Omit` 工具类型做了两件事：

1. 从页面实体 `ILowCode` 中排除 `id`、`accountId`、`components`——`id` 由后端生成/查库得到，`accountId`（账号 ID）不应由前端传入，而是从解密后的 Token 中拿当前用户 ID，避免前端伪造 ID 篡改他人页面数据；
2. 单独把 `components` 拼回来，其元素类型为 `IComponent`，但排除前端还不存在的 `configId` 与 `id`，仅由后端在落库时补全。

定义完成后，在 server 端执行构建（如 `npm run build` 或对应 workspace 脚本）让类型可被正常引入。

### 定义控制器与 JWT 鉴权

在 local 控制器中声明发布接口：

```ts
@Controller('local')
export class LocalController {
  constructor(private readonly localService: LocalService) {}

  @Post('release')
  @UseGuards(AuthGuard('jwt')) // 校验 JWT，未登录直接拒绝
  async release(
    @Body() body: PostReleaseRequest,
    @getUserMess() user: Omit<IUser, 'password'>,
  ) {
    return this.localService.release(body, user);
  }
}
```

说明几个关键点：

- 路由为 `POST /low_code/release`，方法名 `release`，入参 `body` 即上面的 `PostReleaseRequest`。
- 用户参数通过上节课封装的 `getUserMess` 装饰器获取，它会把 Token 解密后附加到 `request` 上的用户信息注入进来，且返回结果不含 `password`（`Omit<IUser, 'password'>`）。
- `@UseGuards(AuthGuard('jwt'))` 来自上一节定义的权限校验依赖，确保只有携带合法 JWT 的请求才能进入（最终仓库改为 `APP_GUARD` 全局守卫 + `@Public()` 白名单，接口级写法是教学口径）接口。

### 完善 Module 依赖注入

发布接口会操作多张表（配置表、component 表、component_data 表），因此要在 `local.module.ts` 中通过 `TypeOrmModule.forFeature([...])` 引入对应实体；同时 JWT 的解密策略 `JwtStrategy` 需注册到 `app.module.ts` 的 `providers` 中（全局生效）。注意 `forFeature` 传入实体类数组（如 `[Page, Component, ComponentData]`），与单纯用户表场景区分。

### 用 Apifox 验证鉴权是否生效

启动服务（注意别让其他窗口已占用 3000 端口），用 Apifox 请求 `POST /low_code/release`：

- 不带 Token：返回「没有权限」，鉴权依赖生效；
- 先登录拿到 Token，在请求头 `Authorization` 中加 `Bearer <token>`（注意 `Bearer` 后有一个空格）再请求：接口响应「请求成功」；
- 故意改错 Token：解密失败同样返回「没有权限」。

### 编写服务层发布逻辑（基础方案）

本节先给出**未优化**的第一版实现，后续会用 JMeter 压测其耗时，再引入 Redis 缓存等手段做第二版优化，通过对比体现优化价值。

```ts
async release(body: PostReleaseRequest, user: Omit<IUser, 'password'>) {
  const { components, ...rest } = body;
  const queryRunner = this.dataSource.createQueryRunner();

  let id: number | undefined = undefined;

  try {
    await queryRunner.connect();
    await queryRunner.startTransaction();

    const findLocal = await queryRunner.manager.findBy(Page, {
      accountId: user.id,
    });

    if (findLocal.length > 0) {
      // 已存在 -> 更新
      id = findLocal[0].id;
      await this.updateLocalPage(queryRunner, id, rest, components);
    } else {
      // 不存在 -> 创建
      await this.createPage(queryRunner, user.id, rest, components);
    }

    await queryRunner.commitTransaction();
    return { msg: '发布成功', data: id }（最终仓库口径）;
  } catch (err) {
    await queryRunner.rollbackTransaction();
    console.error(err);
    throw err;
  } finally {
    await queryRunner.release();
  }
}
```

逻辑要点：

1. 用扩展运算符 `...rest` 把 `body` 中除 `components` 外的字段整体提取，便于后续拼装；
2. 通过构造函数注入 `DataSource`，用 `createQueryRunner()` 开启一个数据库事务，保证「查询—更新/创建」多步操作的一致性；
3. `try / catch / finally`：成功提交（`commitTransaction`），异常回滚（`rollbackTransaction`）并打印日志，无论成败都在 `finally` 中 `release()` 释放连接；
4. 先 `findBy(Page, { account_id: user.id })` 判断当前用户是否已有页面：有则走更新、无则走创建，下一节完善 `updateLocalPage` 与 `createPage` 两个方法。

## 小结

- 发布接口入参统一收敛到 `share` 的 `types/local.ts`，用 `Omit` 排除不应由前端传入的 `id`、`accountId`；`accountId` 改由 Token 解密得到的用户 ID 提供，更安全规范。
- 控制器路由 `POST /low_code/release`，通过 `@UseGuards(AuthGuard('jwt'))` 与 `getUserMess` 装饰器完成鉴权与用户信息注入。
- 多表操作必须在 `local.module.ts` 用 `TypeOrmModule.forFeature` 引入实体，JWT 策略全局注册于 `app.module.ts`。
- 发布逻辑用数据库事务保证一致性；先按「页面存在则更新、不存在则创建」分支处理，本版为未优化方案，留待 JMeter 压测后优化。
- 验证顺序：无 Token 拒绝 → 登录拿 Token → `Bearer` 头请求成功。
