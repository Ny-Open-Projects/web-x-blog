# 后端接口开发—低代码项目编辑模块发布接口《下》

> **导语**：发布接口的上篇与中篇搭好了事务骨架，这一篇收尾：把「存在则更新、不存在则创建」两条分支真正实现。重点在多表联动——Page 表置空 `components`、删除旧的 Component 与 ComponentData、插入新组件并回填 ID 数组；最后补上失败时的回滚与服务端异常，让事务真正闭环。

## 正文

### 把两个方法抽到 try 外

更新与创建两个分支逻辑都比较长，抽成独立函数放在 `try` 外；`try` 内只负责三件事：建立数据库连接、开启事务、查询当前页面是否已存在，再按结果调用对应分支。这样主干清晰，两个方法也能被复用。

### 更新分支：先清理，再写入

按笔记里的顺序，一共五步：

1. **置空并更新 Page 表**：`queryRunner.manager.update(Page, id, { ...其他字段, components: [] })`。用展开运算符合并 `page_name`、`desc`、`tdk` 等属性，同时把 `components` 先置为空数组。
2. **删除旧组件**：循环遍历查询结果里的 `components`（一个 ID 数组），逐条 `delete(Component, id)`。特别注意这里删的是**该页面/该用户**的旧数据，不是全表。
3. **组件数据处理**：课程原始实现会按页面 ID 查 `ComponentData` 表并循环删除；最终仓库已修正为**保留问卷数据行**（组件 id 发布后重生成，统计端对失效 id 容错）——原句：有没有数据，有才循环逐条 `delete(ComponentData, id)`，避免残留数据占用存储。
4. **插入新组件**：抽成 `insertComponent(configId)` 方法。循环遍历前端传来的 `components`（先确认它是数组，否则 TypeScript 会报「缺少返回迭代器」），每条执行 `insert(Component, { ...展开字段, page_id, account_id })`，再从返回结果的 `identifiers` 里取出新 ID，`push` 到数组里。
5. **回填 Page 表**：用收集到的组件 ID 数组，再次更新 Page 表的 `components` 字段——前面置空、这里写入，完成整组替换。

### 创建分支：先建页面，再插组件

创建逻辑相对简单：`insert(Page, { ...body, components: [], accountId })`，从 `identifiers[0].id` 拿到新页面 ID，作为 `configId` 传给同一个 `insertComponent` 方法插入组件。`components` 同样先置空、插完再更新。

正因为「更新」和「创建」都要插入组件，才把插入逻辑抽成公共方法——这是本节结构上的关键取舍。

### 事务收尾与返回

成功时给前端返回 `msg` 与 `data`（页面 ID）：更新分支取已存在记录的 ID，创建分支取新插入的 ID。两条分支都要把 ID 正确回传，前端才能跳转到刚发布的页面。

### 联调里的三个坑

用 ApiFox 请求发布接口时，连着踩了三个坑，每一个都值得记下来：

- **body 不传 `components`**：接口返回「发布成功」、页面 ID 为 3，但刷新 Navicat 数据库并没有新增数据——后端其实报错了（`components` 为空导致）。在请求里补齐 `components`（哪怕是空数组）、重启服务后才真正成功。
- **catch 里没有回滚**：失败时事务没有撤销，数据停在半途状态。补上 `await queryRunner.rollbackTransaction()`。
- **失败没有抛出错误**：补 `InternalServerErrorException`，把「发布失败」和具体 `error` 一并返回给前端（教学实现如此；生产上错误详情只进日志，对外固定文案），而不是只打日志。

```ts
} catch (error) {
  await queryRunner.rollbackTransaction();
  throw new InternalServerErrorException('发布失败', error);
}
```

### 为什么同一用户重复发布只更新、不新增

用同一个 token（account ID 为 8）再次发布，把页面名改成「小滴低代码」，返回的页面 ID 仍是 3，数据库里也没有多出一条，但 `pageName` 已经被改过来了。原因正是查询结果长度大于 0 时会走**更新分支**：执行 `update`，把 `components` 置空、替换其它字段。这就是「存在则更新、不存在则创建」的 upsert 语义，也解释了为什么演示里数据始终只有那几条。

## 小结

- 发布接口是「存在则更新、不存在则创建」，由事务里的查询结果决定分支。
- 更新分支依次做：Page 表置空 `components` 并更新其它字段 → 删旧 Component → 组件数据行按最终仓库口径保留（课程原始实现会删，见上文） → 插入新组件 → 回填 ID 数组。
- 插入逻辑被更新与创建共用，因此抽成 `insertComponent(configId)` 方法。
- 删除旧数据要限定到该页面/该用户，不能全表删；`ComponentData` 先查后删。
- `catch` 中必须 `rollbackTransaction()` 并抛出 `InternalServerErrorException`，事务才算闭环。
