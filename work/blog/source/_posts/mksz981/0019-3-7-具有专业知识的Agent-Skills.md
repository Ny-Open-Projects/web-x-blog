【学习目标】

- 说清 MCP 工具调用模式的两个结构性缺陷：上下文膨胀与工具选择困难。
- 理解 Agent Skills 的核心思想：以文件形式为智能体注入领域专业知识。
- 能横向对比三种工具调用形式（Function Tools / MCP / Agent Skills）的适用场景。

【正文】

## 1. 先回顾：MCP 解决了什么

语言大模型要调用外部数据（例如请求第三方软件的 API），早期每个模型都要根据 API 文档自行编写调用方法，且不同模型的调用方法互不兼容。MCP 协议出现后，无论哪个大模型，都可以通过 MCP 提供的工具调用同一个第三方 API：工具由 MCP 服务端统一实现、统一描述，模型侧零适配。

从架构上看，MCP 把一次工具调用拆到三个节点上：MCP Host（大模型端）发起调用需求，MCP 客户端负责与服务端通信，MCP 服务端提供工具并执行。协议内部又分两层：协议层约定工具定义与返回数据的统一格式，传输层按场景选择合适的传输机制（本机文件走 STDIO，远程服务走 SSE 等流式协议）。这套分层设计让「不同公司、不同语言、不同部署位置」的工具能够被同一套标准收敛起来，MCP 因此成为工具供给的行业标准。

但它并非没有代价。

## 2. MCP 的两个结构性缺陷

**缺陷一：工具被「一股脑」全推给智能体。** 一个 MCP 服务器往往挂着十几个甚至更多工具，客户端连接后会把全部工具定义一次性塞进上下文窗口。工具越多，上下文占用越大，成本与延迟同步上升，这就是上下文爆炸。

这笔账可以算得更细。每个工具的定义包含名称、功能描述、入参 JSON Schema，通常要占用几十到上百 token。一个挂载 20 个工具的 MCP 服务器，仅工具清单就接近两千 token；若一个智能体同时挂载五六个 MCP 服务器，工具清单轻松破万。更关键的是，这份清单每一轮对话都要随请求发送，无法摊销，聊得越久，浪费越多。

**缺陷二：智能体面对一堆工具，不知道选哪个。** 好比要挖地，工具包里却有铲子、锄头、扫把，选哪个更合适？智能体本身没有判断力，它的大脑是大模型，于是只能回头问大模型：「我该用哪个工具？」大模型给出工具名称，智能体再去调用。

这一来一回带来两个后果：

- 多轮对话拉长上下文，Token 被反复消耗；
- 遇到需要多个工具组合的任务，还要反复询问，浪费更明显。

以课程里的旅游规划场景为例：一次行程规划可能同时用到地图类工具（地理编码、路线规划、天气查询）与景点类工具（按城市检索、按偏好筛选）。若这些工具全部平铺在上下文里，模型每做一步决策都要在十几个候选里做选择题，选错一个工具，后续链路全部跑偏。

一句话概括：MCP 解决了「工具从哪来」，却没有解决「工具怎么选、怎么用」。

| 维度 | 全量工具注入（MCP 默认形态） | 按需加载（Skills 形态） |
|---|---|---|
| 启动时上下文 | 全部工具定义一次性进入 | 只有元数据与工具索引 |
| 决策方式 | 问大模型「选哪个」 | 智能体凭专业知识自判 |
| 组合任务 | 每步都要重新询问 | 一次判定，组合执行 |
| Token 曲线 | 随工具数量线性增长 | 随任务复杂度增长 |

两个缺陷看似独立，实则同源：都来自「工具定义一次性全量进入上下文」这一设计。上下文里同时塞着全部工具，窗口被挤占（缺陷一），模型也被迫在全集里做选择（缺陷二）。因此解法必然指向同一处，让工具定义按需、分批地进入上下文。这正是 Agent Skills 的出发点。

## 3. Agent Skills：给智能体注入领域知识

换一个思路：如果智能体本身就懂行呢？

给智能体赋予领域能力，例如它是一位种田专家，面对 MCP 返回的一堆种地工具，它自己就知道挖地用铲子、松土用锄头，无需再问大模型。

这样做带来两个直接收益：

1. **省 Token**：不需要为「选哪个工具」反复询问大模型，智能体自己就是最优解的判定者。
2. **省上下文**：不需要 MCP 服务端把所有工具全部返回，按需取用即可，上下文窗口不再被无关工具占满。

实现方式很轻量：**以文件的形式**，把专业知识与工具索引配置在本地。这里的「文件」不是一句比喻，技能在磁盘上是一个目录，里面包含说明文件（描述这项技能做什么、覆盖哪些场景）与元数据（名称、触发条件、工具索引）。智能体启动时只读取元数据；遇到匹配的任务，才把对应技能的说明与工具文档加载进上下文；运行中若还需要脚本、参考数据等辅助资料，再按需读取。智能体调用工具时，直接读取本地配置，无需再向 MCP 服务端全量拉取工具列表。这种调用形式就是 **Agent Skills**。

与「把领域知识直接写进系统提示词」相比，文件化带来三个工程优势：

- **可维护**：知识改动只涉及文件，不牵扯提示词模板代码；
- **可复用**：一份技能文件可被多个智能体挂载，也可在团队间共享；
- **可版本化**：技能目录随代码仓库一起走版本管理，变更历史可追溯。

课程的 10-3、10-5 篇会分别展开「Skills 装载的专业知识形态」与「Skills 的文件结构标准」，本节先建立总体认知。

从提示词工程的视角看，Agent Skills 把「角色设定」从一段系统提示词升级为一组可组合的知识文件：提示词负责「你是谁」，技能文件负责「你懂什么、怎么干」。前者回答人格，后者回答能力，两者互补而非互斥，没有技能文件的提示词是空喊口号的「专家人设」，没有提示词约束的技能文件则是缺乏边界的「资料堆」。

## 4. 三种工具调用形式对比

| 维度 | Function Tools | MCP | Agent Skills |
|---|---|---|---|
| 工具来源 | 自行编写方法 | MCP 服务端统一提供 | 本地文件配置 |
| 跨模型复用 | 差，每个模型各写一套 | 好，协议标准化 | 好，知识沉淀在文件 |
| 工具选择 | 代码写死 | 靠大模型现问 | 智能体凭专业知识自判 |
| 上下文占用 | 小 | 大（全量工具注入） | 小（按需加载） |
| Token 成本 | 低 | 高（反复询问） | 低 |
| 知识沉淀 | 散落在调用代码里 | 工具定义集中在服务端 | 领域知识独立成文件 |

```mermaid
graph LR
    A["Function Tools<br/>手写方法，各模型不通用"] --> B["MCP<br/>协议统一，工具全量返回"]
    B --> C["Agent Skills<br/>专业知识 + 按需取用"]
```

三种形式可以这样定位：第一种是 Function Tools，自己写方法实现工具调用，适合工具数量固定、调用逻辑简单的场景；第二种是通过 MCP 服务器这一共同节点，智能体调用服务端返回的工具，适合工具需要跨模型、跨团队复用的场景；第三种是 Agent Skills，特点是智能体自己拥有专业知识，自己知道哪个工具是最优解，适合工具数量多、任务组合复杂的场景。三者不是替代关系，而是覆盖不同阶段的工具箱。

## 5. 定位辨析

Agent Skills 不是第四种「协议」，而是另一种组织工具调用的形式：MCP 回答「工具从哪来」，Agent Skills 回答「工具怎么用、用哪个」。前者是供给侧的标准，后者是消费侧的智慧。

用一句话概括分工：MCP 让「工具找得到模型」，Agent Skills 让「模型找得到工具」。前者保证任何模型都能零适配接入工具，后者保证智能体在工具变多时依然保持决策质量。这一点在下一篇会进一步展开。

最后说明适用边界：并非所有场景都值得上 Agent Skills。工具数量少于五个、任务路径固定时，全量注入的上下文成本可以忽略，直接用代码写死调用顺序反而更可靠；只有当工具规模上来、任务组合多变时，渐进式加载才能体现收益。技术选型看成本曲线，不看热闹。

【易错点 / 面试题】

1. **MCP 一股脑返回全部工具会带来什么问题？** 上下文窗口被挤占，且智能体不知如何选择，只能反复询问大模型，造成 Token 浪费。这是面试中考察「MCP 局限性」的高频题。答这道题建议给出量化视角：工具清单随请求逐轮发送，20 个工具约两千 token，挂载多个服务端即破万，成本随对话轮次复利式放大。
2. **Agent Skills 为什么省 Token？** 专业知识以文件形式预置在本地，智能体自己知道该用哪个工具，省掉了「问大模型」的来回；工具按需加载，不再全量注入上下文。可以进一步答出「加载曲线」的差异：全量注入的 Token 成本与工具数量挂钩，渐进加载的成本与任务复杂度挂钩。
3. **Function Tools、MCP、Agent Skills 三者是什么关系？** 不是互相替代，是演进与协作：Function Tools 是最早的手写阶段，适合简单固定场景；MCP 统一了工具供给，但把选择难题留给了上下文；Agent Skills 在 MCP 之上补上「会用工具」的能力。终极形态是「MCP 提供工具 + Skills 指导使用」的组合。

【小结】

本节的核心结论：工具调用正在从「模型现问」走向「智能体懂行」。MCP 作为供给侧标准解决了工具的统一接入，但全量返回工具定义导致上下文爆炸，智能体缺乏领域知识导致反复询问、Token 浪费。Agent Skills 以文件形式把领域专业知识与工具索引注入智能体，启动时只加载元数据，遇任务按需加载，从根上同时缓解了两个缺陷。下一篇会讲 Agent Skills 与 MCP 如何组合成「工具调用最强组合」。想对照工程实现的读者，可参阅 `981-demo/src/main/java/com/travel/agent/tool/RouteMakingTools.java` 与 `981-demo/src/main/java/com/travel/agent/tool/AttractionTools.java`：两者分别以 `@Tool` 形式实现 Function Tools 一路的本地工具箱（地图三工具与景点检索），并通过 `981-demo/src/main/java/com/travel/agent/agent/TeamMembers.java` 挂载到各自的 ReActAgent；课程 10-7、12-4 篇则演示 Skills 的装载与渐进式加载，可与工程对照阅读。
