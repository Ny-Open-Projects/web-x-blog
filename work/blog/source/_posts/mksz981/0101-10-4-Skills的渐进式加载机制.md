## 【学习目标】

- 理解「Skills 是个文件夹，一次性全加载会不会占满上下文」这一核心疑问的来由。
- 掌握元数据（索引）机制：先加载目录，不加载内容。
- 掌握三次渐进式加载：元数据索引加载 → 工具按需加载 → 附加资源按需加载。
- 能够把渐进式加载与 MCP 全量返回模式对照，说清各自的上下文代价。

## 【正文】

### 一、两个划时代概念的定位回顾

Cloud Code 提出来的两个概念，MCP 和 Agent Skills，都属于划时代的概念。

MCP 约定了 AI 调用外部工具的连接标准：外部工具只要符合该标准做出一个服务端，大模型去调用该外部工具时只要遵从同一个标准，就能够完成调用，无论你是 DeepSeek 大模型、千问的大模型还是 OpenAI，都可以基于该标准去连接、调用外部的工具，不需要重复造轮子，这就是 MCP 的划时代意义。

Agent Skills 定义的则是另一套标准：**智能体的技能系统**。它不只是一个工具的调用，而是整套的技能系统，包括该领域的专业知识、专业工具的使用逻辑，以及该专业领域的工作流程。所有的专业领域，无论你是产品领域、会计领域还是财务领域，只要按照该标准去制定该领域的技能系统，它就能够赋予给任何一个智能体，让智能体具备该专业领域的知识，这就是 Agent Skills 的划时代意义。

Cloud Code 也讲到，Agent Skills 是一个技能系统，它所包含的工作流程指的是一个固定的流程：我需要做什么工作、我要完成该工作需要经过什么步骤（第一步做什么、第二步做什么、第三步做什么），以及最后以什么形式进行输出，这都是一个固定的模板。只要任何一个智能体继承了该专业领域的 Agent Skills，它都会获得一个固定的流程，并按该固定的流程去完成，不会有其他另外的分支流程。而前面课程讲到的 Workflow 则需要我们人工去封装这些流程的节点，业务逻辑是写在流程节点里面的，有分支、有总结点、有并行。所以 Agent Skills 的工作流程适用于有固定流程的专业领域场景。

到此已经能区分 MCP 与 Agent Skills 的区别：**MCP 只是工具的提供，而 Agent Skills 则不只是使用工具，还包含了整个专业领域的知识，是一个技能的系统。**

### 二、问题的提出：文件夹这么大，会不会占满上下文？

前面讲过，MCP 只是提供工具，它的服务端有多少工具都会一股脑儿地把这些工具返回给 Agent，让智能体自己去挑选工具以及使用工具。而当时没有继承 Agent Skills 的智能体，并不知道完成该任务需要选择什么正确的工具、以及如何去使用工具，所以它要去请教语言大模型，由语言大模型帮它选择工具以及使用工具。这样一来，那些不相关的工具就把上下文窗口给堵塞、给撑满了，这些工具根本用不上，完成该任务也用不到，但 MCP 服务端却一股脑儿地把它返回了过来。Agent Skills 则让智能体知道，它要完成该专业领域的场景需要使用什么样的工具、以及如何去使用该工具，你 MCP 只需要返回对应的工具就可以了。

不过顺着往下想会冒出一个新问题：**Agent Skills 不只是包含工具的使用、不只是包含该说明书，还包含整套的专业领域技能以及整套固定的流程模板，这么一大堆东西都是以一个文件夹的形式加载进去的，那该文件夹不就很大吗？这样不会占满上下文窗口吗？这跟从 MCP 里面把所拥有的工具一股脑儿全部丢回来有什么区别？**

这是个好问题，也是理解渐进式加载的入口。答案是：区别在于加载的内容形态完全不同。

### 三、元数据：先加载索引，而不是加载内容

Agent Skills 加载的是一种叫做元数据的东西。**可以把该元数据理解为索引**，这些专业知识以及工具的调用流程的模板，它只是一个索引，该文件是很小的，这就是元数据。它首先把该元数据、该索引加载到智能体，这样智能体就拥有了该专业领域的知识，却又不会占有太多上下文窗口，因为这只是个很小的元数据文件。

该很小的元数据索引包括了哪些东西？该专业领域的名称、该专业领域的描述，以及一些操作步骤（也就是工具流程）和专业知识的一个索引，它只是一个索引。这是第一个加载。

用日常经验类比：元数据相当于一本书的目录。书架上的全书很厚，直接搬进书桌会把桌面占满；把目录拿进来，只有薄薄一页，却足以知道「哪个主题在哪一章、需要时去哪取」。智能体拿到目录，就拥有了该领域的知识地图，但不必把全书铺在桌面上。

索引与内容分离在软件工程里无处不在：数据库的索引表与数据行、操作系统的目录项与文件块、书籍的目录与正文。共同规律有两条：定位信息的体量远小于内容本身；定位信息被访问的频率远高于内容。Agent Skills 的元数据遵循同一条规律，一次任务中，索引常驻上下文，内容按需取用，上下文预算因此花在「知道去哪取」而不是「把什么都搬进来」。

### 四、三次渐进式加载

```mermaid
flowchart LR
    A["Agent 获得技能文件夹"] --> B["第一次加载\n元数据索引\n（名称/描述/步骤索引/知识索引）"]
    B --> C{"接到匹配任务"}
    C --> D["第二次加载\n工具按需加载\n只让 MCP 返回所需工具"]
    D --> E["执行到具体步骤"]
    E --> F["第三次加载\n附加资源按需加载\n脚本/指令/资源文件"]
```

**第一次加载：元数据索引。** 先加载一个索引，这些资源、代码、脚本、工作流程模板、专业知识的一个目录，只加载这么一个索引，让智能体知道大概要往哪个方向去走、接下来需要怎么做，但是具体的做法等到做到那一步的时候才加载真正的资源。

**第二个加载：工具的按需加载。** 智能体已经加载了元数据，而这里的元数据里包含了在该专业领域里面需要用到哪些工具的名称索引；它就拿着该名称上的索引，知道自己要去完成该专业领域的任务需要用到什么样的工具，因此它会告诉 MCP：你只要返回这两个工具，其他的工具都不需要返回。该就是工具的按需加载。

**第三个加载：附加资源加载。** 工具在使用的过程中可能要调用一些脚本或者指令，这些脚本和指令同样也是存放在该 Agent Skills 的文件夹里面的，但智能体在真正使用该工具的时候，才会调用该工具所需要的脚本或者指令，这就是附加资源的加载。

这三个加载属于渐进式的加载，而非一次性地把所有内容加载到该智能体里面。总结一下：第一个加载是先加载一个索引，这些资源、代码、脚本、工作流程模板、专业知识的一个目录，只加载这么一个索引，让智能体知道大概要往哪个方向去走、接下来需要怎么做，但是具体的做法等到做到那一步的时候才加载真正的资源；第二个加载是对工具的按需加载，不让 MCP 一股脑儿地把所有工具返回过来，只要返回需要的工具就可以了；第三个就是资源的按需加载，无论是调用工具还是其他的一些流程，都需要调用一些资源，而这些资源是在真正执行该步骤、真正需要用到这些附加资源的时候才进行加载。这就是三次渐进式加载。

把三次加载的触发时机归纳成表，机制就完全显形了：

| 加载次序 | 加载内容 | 触发时机 | 上下文占比 |
|----------|----------|----------|------------|
| 第一次 | 元数据索引（领域名称、描述、操作步骤索引、专业知识索引） | 技能赋予智能体时 | 很小，常驻 |
| 第二次 | 所需工具（凭名称索引通知 MCP 只返回这些） | 接到匹配任务、确定工具范围时 | 小，仅相关工具 |
| 第三次 | 附加资源（脚本、指令、资源文件） | 执行到具体步骤、真正需要时 | 按步骤增长 |

三次加载恰好对应任务的三个阶段：技能装载期只付「索引费」，任务匹配期只付「工具费」，步骤执行期才按需付「资源费」。上下文的增长曲线由任务进度决定，而不是由技能包的体积决定，这是渐进式加载区别于一次性全量加载的本质特征。

### 五、两种加载模式的上下文代价对照

| 维度 | MCP 全量返回 | Agent Skills 渐进式加载 |
|------|--------------|--------------------------|
| 首屏进入上下文的内容 | 服务端全部工具的描述与 schema | 仅元数据索引（很小） |
| 工具返回范围 | 全部，与任务无关的也返回 | 按名称索引只返回所需工具 |
| 脚本与资源 | 不涉及（工具即全部） | 执行到具体步骤时才加载 |
| 上下文增长曲线 | 一次性拉满，随工具数线性膨胀 | 按任务进度阶梯式增长 |
| 适用判断 | 工具少、任务杂 | 工具多、领域固定 |

把两种模式放在一起看，渐进式加载的本质是**把「加载」从一次性事件变成按任务进度触发的流水线**：索引先行建立方向感，工具按需保证调用精度，资源后置保证执行深度。三层各自解决一个层面的上下文压力，合起来才敢把「一整个文件夹」交给智能体。

从上下文工程的角度看，渐进式加载把「上下文预算」当成一种需要主动管理的资源：全量加载是预算的超支，渐进式加载是预算的分期。智能体系统的很多失控问题，答案质量随对话变长而下降、token 成本指数上涨，根源都在上下文预算失管。Skills 的三次加载模型提供了一种可复用的管理范式：先建索引，再按需取工具，最后按步取资源，每一层都在为上下文「节流」。

顺带指出框架层的同源实践：Spring AI 2.0.1 提供 `ToolSearchToolCallingAdvisor`，在会话内先对全部工具建立索引、再按需检索，面向大工具集可显著压低 token 占用，这与 Skills 侧「先索引、后按需」的思路完全一致。课程 12-4 篇「Skills实现Agent工具的渐进式加载」会把这套机制落到工程实现上。

课程 12-4 篇与 10-7 篇「SpringAi 1.1.2实现Agent装载Skills」构成同一主题的连续两篇。读到那里时回看本节的三次加载模型，就能把「概念上的渐进式」与「代码里的加载器」逐层对应：元数据文件怎么解析、工具索引怎么查询、附加资源怎么按步取用，都能在 10-5 篇的文件结构标准里找到落点。

## 【易错点 / 面试题】

1. **面试题：为什么 Skills 不把整个文件夹一次性加载进上下文？**
   两个层面。第一，可行性：文件夹包含脚本、资源、完整流程模板，体量远超上下文窗口的合理占用，全量加载会把窗口挤爆；第二，必要性：一次任务通常只用到技能包的一个子集，用不上的内容加载进来只会稀释信噪比。结论：先加载元数据索引建立方向，工具与资源都按需加载。

2. **面试题：三次渐进式加载各自在什么时机触发？**
   第一次在技能赋予时触发，加载元数据索引，获得领域名称、描述、步骤索引与知识索引；第二次在接到匹配任务、确定所需工具时触发，凭索引通知 MCP 只返回对应工具；第三次在执行到具体步骤、真正需要脚本或指令时触发，加载附加资源。答题时按「赋予 → 选工具 → 执行步骤」三个时机串起来讲。

3. **易错点：把元数据理解成「技能的压缩包」。**
   元数据不是压缩后的全量内容，而是索引，它包含名称、描述、步骤索引与知识索引，但恰恰不包含完整正文。压缩包解压后还是全量，索引则永远只指向位置。该区分决定了「按需」是否成立。

## 【小结】

本节回答了「文件夹这么大会不会占满上下文」：不会，因为 Agent Skills 采用三次渐进式加载，元数据索引先行、工具按需返回、附加资源后置加载，上下文随任务进度阶梯式增长而非一次性拉满。下一篇 10-5 落到最具体的文件层：元数据文件 `skill.markdown` 的三段结构，以及技能文件夹里的脚本、指令、资源文件标准。
