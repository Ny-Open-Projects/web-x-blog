## 【学习目标】
学完本节，你将能够：
- 用 `StateGraph.getGraph(Type.PLANTUML)` 把工作流导出为可视化描述，验证拓扑是否符合预期；
- 在 IDEA 安装 PlantUML 插件，把导出的文本渲染成图形；
- 补齐运行所需的依赖（JSON）、配置文件（`application.yml`）与启动入口，真正把工作流跑通。

## 【正文】
工作流需先编译才能运行：`StateGraph.compile()` 产出 `CompiledGraph`，再用其 `invoke()` 或 `stream()` 运行。`CompiledGraph` 的两种运行方式差异在于结果返回时机，`invoke()` 阻塞、一次性返回；`stream()` 非阻塞、逐节点返回：

```java
  // CompiledGraph提供了2种运行工作流的方式:
  * 1. invoke(): 以阻塞的方式运行工作流, 工作流的结果是一次性返回
  * 2. stream(): 以非阻塞, 流式的方式运行工作流,
     执行一个节点, 就返回该节点完成的结果
```

但有个现实问题：怎么确认「我搭的图」和「我想的图」一致？答案是把工作流**图形化打印**出来。

### 用 getGraph 导出图形描述
在 `GraphConfiguration` 的蓝图方法里、返回 `StateGraph` 之前，调用 `getGraph(Type)`。`Type` 是 `StateGraph` 内部的一个枚举，有两种取值：`PLANTUML` 与 `MERMAID`：

```java
  public static enum Type {
      PLANTUML(new PlantUMLGenerator()),
      MERMAID(new MermaidGenerator());
  }
```

本节选 `PLANTUML`，即把工作流以 PlantUML 格式文本导出。`getGraph` 返回 `Graph` 对象，把它打印到日志即可。配置类骨架如下：

```java
  @Configuration
  public class GraphConfiguration {
      @Bean(name = "parallelGraph")
      public StateGraph parallelGraph() throws GraphStateException {
          // 配置链式工作流
      }
  }
```

**为什么用 `getGraph` 做校验**：Graph 工作流的 bug 大多出在「拓扑和预期不符」（漏连线、连反、环）。肉眼读 `addNode`/`addEdge` 代码容易漏，但把图渲染出来一眼就能看出 `START → node1 → node2 → END` 是否齐全。等价于「用单元测试之外再给编排做一次可视化断言」。其拓扑形态等价于下方的 mermaid（与日志里的 PlantUML 描述的是同一张图）：

```mermaid
graph LR
    START["__START__"] --> node1["node1"]
    node1 --> node2["node2"]
    node2 --> END["__END__"]
```

### 运行所需的工程骨架
要把工作流真正跑起来，还需三样东西：

**1. 启动类**：Spring Boot 标准启动类。
**2. 配置文件** `application.yml`：填阿里百炼（DashScope）的 API Key，指定模型（示例用 `deepseek-r1`），并把端口设为 `8081`：

```yaml
  server:
    port: 8081
  spring:
    ai:
      dashscope:
        api-key: 
        chat:
          options:
            model: deepseek-r1 # 指定DeepSeek的模型名称
```

**3. 控制器接口**：接收请求、组装 prompt、调用 `compiledGraph.invoke(map)`：

```java
  @GetMapping(value = "/workflow/parallel")
  public void parallelWorkflow() {
      String prompt = "在咖啡馆里, 想要杯星巴克";
      Map<String, Object> map = new HashMap<>();
      map.put("prompt", "prompt");
      compiledGraph.invoke(map);
  }
```

**为什么还缺一个 JSON 依赖**：工作流内部默认用 Google 的 Gson 做序列化，但运行时需要该依赖在 classpath 中。初次启动常报「找不到 Google 的 JSON 类」，补上 JSON 依赖后即可成功。这是 Graph 工程初次搭建的高频坑，蓝图写对了，却因缺依赖起不来。

**不这么写会怎样**：漏了 `application.yml` 里的 `api-key`，运行到真正调用模型时才报鉴权失败；端口冲突会让服务起不来；缺 JSON 依赖则编译期无事、启动即崩。这些都属于「工程装配」问题，和编排逻辑无关，却是把 Demo 跑通的必要成本。

### 渲染图形：IDEA + PlantUML 插件
IDEA 安装 PlantUML 插件（Plugins 中搜索安装）。运行后，日志里会打印出工作流的 PlantUML 描述，例如：

```
  powered by spring-ai-alibaba
  end footer
  circle start as __START__
  usecase "node1"<<Node>>
  usecase "node2"<<Node>>
  "__START__" -down-> "node1"
  "node1" -down-> "node2"
  "node2" -down-> "__END__"
  @enduml
```

把这段文本贴进 PlantUML 插件的 `.puml` 文件，即可渲染出图形：一个链式工作流，含 `node1`、`node2` 两个节点，入口 `START`、出口 `END`。用 ApiFox 请求 `/workflow/parallel` 返回 200，即代表链路跑通。

**生产经验类比**：把工作流可视化，和微服务里用图表确认调用链、用链路追踪确认执行路径是一个道理。编排类系统「先看见、再相信」，图形校验能挡掉大量拓扑类低级错误。

## 【易错点 / 面试题】
1. **`getGraph(Type.PLANTUML)` 和 `getGraph(Type.MERMAID)` 区别？** 仅导出格式不同，描述同一张拓扑。PlantUML 需 IDEA 插件渲染；Mermaid 可直接在 Markdown/网页渲染，更轻量。
2. **为什么启动报「找不到 Google JSON 类」？** Graph 内部用 Gson 序列化，但需对应 JSON 依赖在 classpath。补依赖即可，属工程装配问题。
3. **图形里只有 node1/node2，能加分支或并行吗？** 本节是线性链；Graph 支持条件边、并行边等更复杂拓扑，后续可在 `Edge` 基础上扩展，但校验「图形化」这一步始终不能省。

## 【小结】
本节给工作流加了「可视化校验」，用 `getGraph(Type.PLANTUML)` 导出拓扑、用 IDEA 插件渲染，确认 `START → node1 → node2 → END` 与设想一致；并补齐了 JSON 依赖、配置文件与启动入口，让工作流能从请求跑到 200。至此第 7 章的 Graph 工作流已完整跑通：记忆中枢（`OverAllState`）→ 蓝图（`StateGraph`）→ 节点（`NodeAction`）→ 连线（`Edge`）→ 编译运行（`CompiledGraph`）→ 可视化校验，形成闭环。

> 技术前瞻：Spring AI 2.1/3.0 的 「Spring AI Agents」 在 Graph 之上抽象出子 Agent 与 Skills 编排，并提供更友好的可观测/可视化能力；但本章建立的「状态 + 节点 + 边 + 编译运行」心智模型，是理解一切上层编排的底座。
