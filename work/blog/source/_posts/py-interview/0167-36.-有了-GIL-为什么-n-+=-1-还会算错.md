> 分类：并发/线程安全 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**读改写** / **原子操作** / **丢更新**
> 原文锚点：第 36~58 段「大部分情况结果是一万，但出现了 9998…说明这个操作并不是线程安全的」

## 一句话总述
GIL 只保证**单条字节码**不被打断，而 `n += 1` 是**读—改—写三步**，中间可能被切走导致**丢更新**——**GIL 不等于线程安全**。

## 面试官视角
- **考察意图**：这是并发题里区分度最高的一问，答"有 GIL 就不用锁"直接判不及格。
- **P5** 知道要加锁 / **P6** 能把 `+=` 拆成三步并指出丢更新的时刻 / **P7** 能说清哪些操作原子、并能用队列等结构从设计上消除竞争。
- **红旗**：①"有 GIL 就不用考虑线程安全"（最经典错误）；② 只说"加锁"却讲不出丢更新发生在哪一步；③ 以为 `list.append` 也不安全。
- **惊艳点**：原文实测 5000 线程 × 2 次累加**多数得到 10000，偶发 9998**——这种"偶尔错"比必错更危险。验证：多次运行下方代码 `[实测]`

## 主问答
**Q：既然同一时刻只有一个线程执行，为什么多线程累加还会算错？**
**A：**
1. **先给结论**：GIL 保证的是**字节码级**互斥，不是语句级；`+=` 由多条字节码组成，**不是原子操作**。
2. **再给机制**：线程 A 取到值、加 1，**尚未写回**时被切走；线程 B 基于旧值加 1 并写回；A 恢复后把自己的结果写回，**覆盖掉 B 的更新**——一次更新丢失。
3. **最后给边界**：单条字节码能完成的（`x = 1`、`list.append`）是原子的；凡是**读-改-写**或**检查再执行**（`if k in d: d[k] += 1`）都必须加锁。
**加分层**：加锁有性能代价，IO 密集场景更推荐把共享状态改成 `queue.Queue` 或线程局部存储，**从设计上消掉竞争**而不是到处加锁。

## 关键代码
```python
import threading
def unsafe():
    n = [0]
    def add():
        for _ in range(10000):
            n[0] += 1                 # 读-改-写，非原子
    ts = [threading.Thread(target=add) for _ in range(8)]
    [t.start() for t in ts]; [t.join() for t in ts]
    print("unsafe:", n[0])            # 偶发 < 80000
def safe():
    n = [0]; lk = threading.Lock()
    def add():
        for _ in range(10000):
            with lk: n[0] += 1
    ts = [threading.Thread(target=add) for _ in range(8)]
    [t.start() for t in ts]; [t.join() for t in ts]
    print("safe:", n[0])              # 恒为 80000
unsafe(); safe()
```

## ⚠️ 原文纠错
原文的结论与实测数据（偶发 9998）正确，是很好的教学材料；需补正一点：**丢失更新的根因是"读-改-写跨多条字节码"，不是"GIL 失效"**。原文中的音译术语已还原。

## 总结与追问预判
- GIL 只管字节码互斥；跨多步的复合操作一律要锁或改设计。
