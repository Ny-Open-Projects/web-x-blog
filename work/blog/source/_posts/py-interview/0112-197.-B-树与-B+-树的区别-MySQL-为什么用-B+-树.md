> 原文锚点：第 23~108 段「B+树是 B树 的变形；两个主要改进：① 只在叶子节点存数据（非叶节点只存 key+孩子指针，增大度）② 叶子节点双向指针相连支持范围查询；阶 m 由磁盘块大小决定」

## 一句话总述
**B 树**是 m 阶**多路平衡查找树**，所有节点（含叶子）都存数据；**B+ 树**是 B 树的变形，两处关键改进——**① 非叶节点只存 key 和孩子指针（不存数据）→ 单页塞更多 key、树更矮**；**② 叶子节点用双向指针串联 → 天然支持范围查询**。MySQL/InnoDB 用 **B+ 树** 而非 B 树。

## 面试官视角
- **考察意图**：能否讲清 B+ 树相对 B 树的两个改进，并解释"为什么阶由磁盘页大小决定"。
- **P5** 能说出"B+ 树叶子存数据、非叶不存、叶子相连" / **P6** 能讲清两个改进各自解决了什么（降树高 / 支持范围查），并解释 B 树不适合范围查 / **P7** 能说清阶 m 由磁盘块/页大小决定、与 IO 的关系，并点出 B+ 树查千万级数据通常只要 3~4 层 IO。
- **红旗**：说"B 树和 B+ 树结构一样"（B 树各节点都存数据，B+ 树只有叶子存）；或认为"阶越大越好"（阶受页大小限制，过大反而跨页）。
- **惊艳点**：B+ 树非叶节点不存数据 → 同样页大小下能存更多 key → **树高更少 → 每次查询磁盘 IO 更少**；这是它压过 B 树、哈希、二叉/平衡树的根本原因 `[源码]`（InnoDB 索引页结构）。

## 主问答
**Q（面试官原话）：** B 树和 B+ 树有什么区别？为什么 MySQL 用 B+ 树？

**A · 标准答案骨架：**
1. **先给结论**：B 树所有节点都存数据；B+ 树**只有叶子节点存数据、非叶节点只存 key+指针**，且**叶子用双向指针相连**。
2. **再给机制**：B+ 树非叶节点腾出数据空间存更多 key → **阶（度）更大、树更矮**；叶子链表让 `WHERE col BETWEEN a AND b` 这类**范围查询**只需顺着指针扫，不必回树上蹿下跳——而 B 树数据散在各层、无法高效范围查。
3. **最后给边界**：**阶 m 由磁盘块/页大小决定**（一页能放多少 key/孩子），目的是让 OS 按页加载缓存友好；阶不是越大越好——受页大小限制，过大反而跨页、缓存命中率下降。

**加分层**：InnoDB 页默认 **16KB**，B+ 树高通常 3~4 层即可索引千万乃至亿级行，一次主键查询约 3~4 次随机 IO（加 buffer pool 后多命中内存）`[经验]`。
