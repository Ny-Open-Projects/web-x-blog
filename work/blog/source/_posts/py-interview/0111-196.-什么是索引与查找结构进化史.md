> 原文锚点：第 1~22 段「索引是数据表一列或多列排序的数据结构，提升检索速度避免全表扫描；回顾查找结构进化：线性→二分→哈希→二叉查找树→平衡树→多路平衡查找树(B树)→B+树」

## 一句话总述
**索引是数据表上一列或多列排序的数据结构**，目的是把"全表逐行扫描"变成"按结构快速定位"；MySQL 用 **B+ 树** 作索引。理解索引要先懂查找结构的**进化史**：线性查找（慢）→ 二分（需有序、插入 O(N)）→ 哈希（查询快但占空间）→ 二叉查找树 BST（logN 但退化成链表）→ 平衡树 AVL（解决退化，但二叉→节点多时树高仍高）→ 多路平衡查找树 **B 树**（一父多子降树高）→ **B+ 树**（MySQL 实际采用）。

## 面试官视角
- **考察意图**：是否知道"为什么 MySQL 选 B+ 树"，而不只是背"B+ 树三层"。
- **P5** 能说出索引是排序数据结构、MySQL 用 B+ 树 / **P6** 能讲清进化史逻辑（二叉→平衡→多路→B+）及每步解决的痛点 / **P7** 能说清 B+ 树相比 B 树的两个改进，并解释"阶(m)由磁盘页大小决定"与 IO 的关系。
- **红旗**：说"B 树和 B+ 树没区别"；或认为哈希索引更适合数据库（忽略哈希不支持范围查询、占空间）；或把 B 树说成二叉搜索树。
- **惊艳点**：B+ 树非叶节点**只存 key 不存数据**→单页能塞更多 key→树更矮→**每次查询的磁盘 IO 次数更少**（InnoDB 页默认 16KB，树高通常 3~4 层即可存千万级数据）`[经验]`。

## 主问答
**Q（面试官原话）：** 什么是索引？为什么 MySQL 用 B+ 树而不是二叉树或哈希？

**A · 标准答案骨架：**
1. **先给结论**：索引是**排好序的数据结构**，让查询从 O(N) 全表扫变成接近 O(logN)；MySQL 选 **B+ 树** 是它在"磁盘 IO 友好 + 支持范围查询"之间的最优解。
2. **再给机制（进化史）**：二叉查找树 BST 会退化成链表（O(N)）；平衡树 AVL 解决了退化但**二叉**导致节点海量时树高仍高；**B 树**让"一父多子"（多路）把树高压下来；但 B 树**各节点都存数据**且不利于范围查；**B+ 树**改进：① 非叶节点只存 key、② 叶子用双向指针相连→既矮又支持范围扫描。
3. **最后给边界**：哈希索引查询 O(1) 但**不支持范围查询、占空间、不适合大规模**；B+ 树虽不是 O(1)，却是兼顾点查与范围查、且 IO 次数最少的折中——**数据库要的是"IO 次数少"而非"单次比较快"**。

**加分层**：B+ 树的"阶 m"由**磁盘块/页大小**决定（一页能放多少 key），让 OS 按页加载缓存更友好；InnoDB 页默认 16KB `[经验]`。
