> 分类：编程范式/装饰器 | 难度：L3 | 题型：事故题 | 频率：高 | 关键词：**functools.wraps** / **__name__** / **元信息** / **签名**
> 原文锚点：第 11~17 段「装饰后返回新函数」→ 反推装饰带来的副作用

## 一句话总述
装饰器返回的是**内层 wrapper**，所以 `func.__name__` 会变成 `wrapper`、`__doc__` 变 `None`，依赖函数名的**日志、文档、框架路由、序列化**全受影响；用 `@functools.wraps(func)` 把元信息**拷贝**回 wrapper 即可。

## 面试官视角
- **考察意图**：区分"会写装饰器"和"写对装饰器"——这是资深与初级的分水岭。
- **P5** 不知道有副作用 / **P6** 知道要用 `@wraps` / **P7** 能说清 `wraps` 拷贝了哪些属性（`__name__`/`__doc__`/`__module__`/`__qualname__`/`__dict__`）以及 `inspect.signature` 为何还能拿到原签名 `[源码]`。
- **红旗**：① 手写装饰器从不加 `@wraps`；② 说"加了 wraps 性能会更好"（它只是拷属性，还**多一层调用开销**）；③ 认为 wraps 能修复 `*args` 吞掉的参数类型。
- **惊艳点**：`wraps` 会把 `__wrapped__` 指向原函数，`inspect.signature()` 正是靠它**穿透**拿到真实签名——**Web 框架的参数注入依赖这条链**。验证：加 wraps 后 `inspect.signature(f)` 还原原始参数表 `[实测]`。

## 主问答
**Q：装饰器会带来什么副作用？怎么解决？**
**A：**
1. **现象**：`@deco` 之后 `f.__name__` 变成内层函数名（如 `wrapper`），`__doc__` 为 `None`，help 与自动生成文档失真。
2. **影响面**：日志里函数名错乱、`sphinx` 文档为空、按函数名做路由/注册/缓存 key 的框架行为异常、单元测试按名字断言失败。
3. **修复**：内层函数上加 `@functools.wraps(func)`，它把 `__name__`/`__doc__`/`__module__`/`__qualname__`/`__dict__` 等从原函数拷过来，并设置 `__wrapped__` 指向原函数。
**加分层**：`wraps` **不改变调用行为**、也不减少一层函数调用开销；它只解决"元信息丢失"，性能问题得另说。

## 关键代码
```python
import functools, inspect

def bad(func):
    def wrapper(*a, **k): return func(*a, **k)
    return wrapper

def good(func):
    @functools.wraps(func)
    def wrapper(*a, **k): return func(*a, **k)
    return wrapper

@bad
def f1(x: int): "doc1"
@good
def f2(x: int): "doc2"

print(f1.__name__, f1.__doc__)              # wrapper None
print(f2.__name__, f2.__doc__)              # f2 doc2
print(inspect.signature(f1), inspect.signature(f2))
```

## 总结与追问预判
- 装饰后 `__name__` 变 wrapper；**`@functools.wraps` 是必选项**；`__wrapped__` 让签名可穿透。
