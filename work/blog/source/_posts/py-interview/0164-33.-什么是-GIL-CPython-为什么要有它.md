> 分类：并发/GIL | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**全局解释器锁** / **引用计数** / **字节码**
> 原文锚点：第 5~11 段「GIL 是 Global Interpreter Lock 的缩写…CPython 的内存管理并不是线程安全的」

## 一句话总述
GIL 是 CPython 解释器上的一把**互斥锁**，同一时刻只允许**一个线程执行字节码**；它的起因是用最省事的办法保护**非线程安全的引用计数内存管理**。

## 面试官视角
- **考察意图**：说得出"是什么"容易，说清"为什么要有"才见功力。
- **P5** 知道同一时刻只有一个线程跑字节码 / **P6** 能说出起因是引用计数非线程安全 / **P7** 能点明它是 **CPython 的实现细节**而非语言规范。
- **红旗**：① 说"Python 语言有 GIL"（那是 CPython 实现）；② 说"有了 GIL 多线程就完全没意义"；③ 说"有 GIL 就不用管线程安全"。
- **惊艳点**：GIL **不是语言规范**——Jython、IronPython 没有；CPython 3.13 起提供实验性的 free-threaded 构建（PEP 703）。验证：3.13 上 `sys._is_gil_enabled()` `[实测]`

## 主问答
**Q：什么是 GIL？为什么 CPython 要引入它？**
**A：**
1. **先给结论**：GIL（Global Interpreter Lock）保证同一时刻只有一个线程执行**字节码**。
2. **再给机制**：CPython 用**引用计数**管理对象生命周期，而计数的增减并非线程安全；多线程同时改同一个对象的计数会导致内存错误。加一把全局大锁是当年最简单、对单线程性能与 C 扩展最友好的选择。
3. **最后给边界**：它只锁**字节码执行**，**不锁你的业务数据**；线程进入阻塞 IO 时会**主动释放** GIL，所以它挡不住数据竞争。
**加分层**：代价是 CPU 密集无法吃满多核，收益是解释器实现简单、C 扩展生态友好——这是明确的工程取舍，不该简单说成"设计缺陷"。

## 关键代码
```python
import sys, threading, time
print("GIL 是否启用:", getattr(sys, "_is_gil_enabled", lambda: "3.13 以下无此接口")())

def burn():
    x = 0
    for _ in range(5_000_000):
        x += 1
t0 = time.perf_counter(); burn(); print("单线程:", round(time.perf_counter() - t0, 2))
ts = [threading.Thread(target=burn) for _ in range(2)]
t0 = time.perf_counter()
[t.start() for t in ts]; [t.join() for t in ts]
print("两线程:", round(time.perf_counter() - t0, 2))   # ≥ 单线程×2，吃不到多核
```

## ⚠️ 原文纠错
原文称"CPython 解释器的内存管理不是线程安全的"，结论正确；更准确的说法是**引用计数的增减不是原子操作**。原文中的音译术语已统一还原为 GIL / CPython。

## 总结与追问预判
- GIL = 保护引用计数的全局字节码锁，是 CPython 实现细节，不保证业务线程安全。
