> 分类：工程化/测试 | 难度：L2 | 题型：工程题 | 频率：中 | 关键词：**mock** / **打桩** / **覆盖率** / **flaky**
> 原文锚点：第 25~28 段「mock 模块用来替换网络请求…coverage 用来统计单元测试的覆盖率」

## 一句话总述
`unittest.mock` 把外部依赖（网络、数据库、时钟）**打桩替换**成可控返回值，让测试保持纯净、快速、可重复；`coverage` 度量覆盖情况，但**覆盖率不是目标**。

## 面试官视角
- **考察意图**：会不会隔离依赖，以及是否清楚 mock 过度使用的反噬。
- **P5** 知道有 mock / **P6** 能 patch 一个函数并写死返回值 / **P7** 能说清"覆盖率高的测试不等于有效的测试"。
- **红旗**：① 单测里发真实网络请求；② 把覆盖率当 KPI（100% 覆盖也可能全是无效断言）；③ mock 掉被测函数本身（等于没测）。
- **惊艳点**：mock 掉太多后**单测全绿、集成即挂**——这是 mock 的主要风险，因此只 mock 边界、不 mock 被测逻辑 `[经验]`

## 主问答
**Q：测试里调用了第三方接口，怎么处理？覆盖率要追求 100% 吗？**
**A：**
1. **先给结论**：外部依赖一律用 mock 打桩隔离；覆盖率用来找盲区，**不是越高越好**。
2. **再给机制**：`unittest.mock.patch` 在指定命名空间**临时替换**对象，可写死 `return_value`，或用 `side_effect` 模拟超时/异常，退出后自动还原。
3. **最后给边界**：只 mock **边界**（HTTP 客户端、时钟、消息队列），**不要** mock 被测函数自己的逻辑；覆盖率要看**关键分支有没有被断言**，不是看行数百分比。
**加分层**：单测必须快（毫秒级）才可能高频跑，这也是必须 mock 掉网络与数据库的现实理由。

## 追问链
| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | 测试里怎么不发真实请求 | 术语 | mock / patch | 换题 → 不及格 |
| L2 | patch 做了什么 | 机制 | 临时替换对象 | 判 P5 |
| L3 | 怎么模拟超时异常 | 边界 | side_effect | 判 P6 |
| L4 | mock 用多了有什么问题 | 反例 | 单测绿、集成挂 | 判 P6+ |
| L5 | 你怎么定覆盖率的口径 | 工程判断 | 关键分支覆盖率 + CI 阈值 | 答上判 P7 |

## 版本与兼容性

|---|---|---|
| Python 3.3+ | `unittest.mock` 于 3.3 进入标准库（此前为第三方 `mock` 包） | 直接用 `unittest.mock`；pytest 生态配 pytest-mock / pytest-cov |

## 关键代码
```python
from unittest.mock import patch
import requests
def fetch_status(url):
    return requests.get(url, timeout=3).status_code
with patch("requests.get") as m:
    m.return_value.status_code = 200
    print(fetch_status("http://x"))          # 200，未发真实请求
with patch("requests.get", side_effect=TimeoutError("timeout")):
    try:
        fetch_status("http://x")
    except TimeoutError as e:
        print("模拟超时:", e)
# 覆盖率：coverage run -m pytest && coverage report -m
```
