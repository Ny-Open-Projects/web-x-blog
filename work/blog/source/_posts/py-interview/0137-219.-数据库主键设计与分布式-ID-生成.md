## 一句话总述
**单库用自增 INT 主键最契合 B+树聚集索引（顺序追加、页分裂少）；UUID 主键随机无序→大量页分裂与碎片**。分布式下自增失效，改用**雪花算法 / 号段 / Redis 自增 / Leaf** 等方案。

## 面试官视角
- **考察意图**：是否把"主键选择"和 B+树/聚集索引机制打通，并能在分布式场景切换思路。
- **P5** 能说出自增主键优于 UUID（有序、省空间） / **P6** 能解释"UUID 无序导致 B+树随机插入、页分裂频繁、碎片多" / **P7** 能给出分布式 ID 的多种方案（Snowflake/号段/Redis/Leaf）并说清取舍。
- **红旗**：认为 UUID 主键"唯一就行没问题"；分不清"数据库自增"与"分布式全局唯一 ID"。
- **惊艳点**：能指出"UUID 作主键还应存为 BINARY(16) 而非 VARCHAR(36) 省空间与比较开销" `[经验]`。

## 主问答
**Q（面试官原话）：** 为什么 MySQL 主键推荐自增整数？UUID 有什么缺陷？分布式系统怎么生成全局 ID？

**A · 标准答案骨架：**
1. **自增 INT 主键好在哪**：InnoDB 主键是聚集索引，数据按主键物理有序；自增写入是**顺序追加在 B+树末尾**，页分裂少、填充率高、索引紧凑。
2. **UUID 的缺陷**：UUID 无序随机，插入点分散在 B+树各处→**频繁页分裂、产生碎片、索引膨胀**；且 VARCHAR(36) 比 BIGINT 占空间、比较更慢。
3. **分布式 ID 生成**：单库自增在分库分表/多实例下会冲突，需全局唯一方案：① **雪花算法 Snowflake**（64bit：时间戳+机器+序列号，趋势递增）；② **号段模式**（DB/Redis 批量取一段号）；③ **Redis INCR**（分布式自增）；④ **Leaf（美团）**等成熟服务。

**加分层**：趋势递增很重要——即使分布式 ID 也尽量保持时间有序，以延续 B+树顺序写的好处；可补"UUID 若要存，用 BINARY(16) 而非 VARCHAR(36)"。

## 关键代码
```python
# 雪花算法最小实现（Python，趋势递增 64bit ID）[实测, python]
import time
def snowflake(node_id, seq=0, epoch=1577836800000):
    t = int(time.time()*1000) - epoch
    return (t << 22) | (node_id << 12) | seq   # 41位时间|10位节点|12位序列
print(snowflake(1, 0))        # 全局趋势递增唯一 ID
```
