## 一句话总述
**缓存击穿 = 某个超热点 key 过期瞬间，海量请求同时穿透到 DB 把它打挂**。解法：分布式锁互斥重建，或后台异步定期刷新热点 key 使其不过期。

## 面试官视角
- **考察意图**：是否分得清击穿（单热点过期）与穿透（不存在数据）、雪崩（大量同时失效）。
- **P5** 能定义击穿（热点 key 过期→大量请求打 DB）并说出"分布式锁"解法 / **P6** 能解释"锁如何限定只有一个线程回源重建，其余等待命中" / **P7** 能补充"后台异步刷新（热点 key 不过期）"作为更简单的替代方案。
- **红旗**：把击穿说成"大量 key 同时失效"（那是雪崩）或"查不存在数据"（那是穿透）。
- **惊艳点**：能点出"热点 key 设逻辑过期 + 异步重建，物理上不失效"的工程套路 `[经验]`。

## 主问答
**Q（面试官原话）：** 什么是缓存击穿？和穿透、雪崩有什么区别？怎么解决？

**A · 标准答案骨架：**
1. **定义**：某些**特别热点**的数据过期了，瞬间大量请求打到后端 DB（如明星离婚相关 key 过期，微博被打挂）——是"单点热点过期"，不同于穿透（数据不存在）和雪崩（大量 key 同时失效）。
2. **解法一（分布式锁）**：用锁限定"只有一个线程负责从 DB 拉数据并重建缓存"，其余线程等待，缓存建好后再从缓存取，从而压住 DB 压力。
3. **解法二（后台异步刷新）**：后台脚本定期刷新快过期的热点 key、重设过期时间，让热点 key **逻辑上不过期**——源文件认为这比加锁实现更简单。

**加分层**：还可采用"逻辑过期"（key 带过期时间戳，过期后由单线程异步重建，物理 key 不删除），兼顾命中率与一致性。

import redis
r = redis.Redis()
def get_hot(key):
    v = r.get(key)
    if v is not None:
        return v
    # 未命中：尝试加锁，只有抢到的线程回源

        finally:
            r.delete(f"lock:{key}")

        v = r.get(key)        # 没抢到锁，稍后从已重建的缓存取
    return v
