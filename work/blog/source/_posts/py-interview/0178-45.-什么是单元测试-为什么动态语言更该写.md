> 原文锚点：第 4~9 段、第 16~22 段「针对程序模块进行正确性检验…防止改一处、另一处就错了」

## 一句话总述
单元测试针对**最小单元**（函数/类）做正确性检验、自底向上保证质量；它的价值有三——**验证底层逻辑、回归防改坏、反过来逼你把设计写简单**。

## 面试官视角
- **考察意图**：是"知道要写测试"，还是理解测试与设计的互动关系。
- **P5** 知道 unittest/pytest / **P6** 能说出"写测试会影响设计"这层 / **P7** 能给出覆盖率与维护成本的取舍判断。
- **红旗**：① 把"我们没时间写测试"当结论；② 靠 print 和日志人工验证正确性；③ 盲目追求 100% 覆盖率。
- **惊艳点**：**越难写测试的代码，设计往往越差**——构造不出依赖就说明耦合过高，"测试写不动"本身就是设计信号 `[经验]`

## 主问答
**Q：什么是单元测试？为什么一定要写？**
**A：**
1. **先给结论**：单元就是**函数或类**，测的是最小粒度的正确性，从最底层自底向上覆盖。
2. **再给机制**：动态语言没有编译期类型保护，重构缺少兜底；有单测之后改动只要跑一遍，就知道有没有把既有逻辑改坏（"改一处、坏另一处"是最典型的遗留代码事故）。
3. **最后给边界**：测试本身也有维护成本，**不是覆盖率越高越好**——应为关键路径和易错逻辑写，不为凑数字写。
**加分层**：最低成本的起步方式，是把调试时的 `print` 改成 `assert` 落到测试文件里。

## 关键代码
```python
def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == target: return mid
        if arr[mid] < target: lo = mid + 1
        else: hi = mid - 1
    return -1

def test_binary_search():
    assert binary_search([1, 3, 5], 3) == 1    # 正常值
    assert binary_search([1, 3, 5], 1) == 0    # 边界值
    assert binary_search([1, 3, 5], 6) == -1   # 异常值
test_binary_search()      # 或：pytest test_search.py -v
```
