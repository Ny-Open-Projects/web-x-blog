## 1. 硬红线（12 条，先读完再动手）

1. **先分诊，再出卡。** 无技术含量的源文件直接剔除，不出卡。**宁可少出一张，不硬凑一张。**
2. **零幻觉。** 非原文内容必须标 `[实测]` / `[源码]` / `[经验]` / `[存疑]`；标不出来的，删掉。
3. **版本栅栏。** 涉及运行时、语言语义、标准库行为的结论**必须标版本**。写"验证版本"而不是"适用版本"。
4. **代码要能跑。** 能编译、原生风格、注释说明关键点；未实跑的代码必须标注"示意，未验证"。
5. **Mermaid 要能渲染。** 节点 ≤12 字、**禁括号引号斜杠**；**每张图后必须跟 3~5 行文字版结构说明**（图是加分项，文字才是本体）。
6. **总-分-总。** 每张卡有「一句话总述」和「总结 + 追问预判」；答案本身必须结论先行。
7. **说错大于不说。** 只写能站住的结论。禁止清单（第 5 节）里的错误说法一律不得出现。
8. **原文锚点。** 每张卡头部标出对应原文段落与关键句，保证可回溯。
9. **纠错留痕。** 原文有错必须单列「原文纠错」小节，并在批次汇报中单列清单。
10. **事实优先。** 与公认技术事实冲突时以正确事实重写，**绝不保留病句**。
11. **语言无关。** 不预设技术栈；按第 6 节的四个问题自行推导该语言的考察维度。
12. **严禁刻板印象。** 性别 / 年龄 / 地域 / 学历相关的断言一律剔除，不复述。

## 2. 工作流程（四步）

### 步骤 0 · 输入分诊

逐篇过判定，命中任意一条即剔除或降级：

| 码 | 判定 | 动作 |
|---|---|---|
| `R1` | 全文无技术点（只有行为、流程、礼仪、心理、薪资） | **剔除** |
| `R2` | 技术点覆盖 < 20%（主体软技能，夹带一两句技术） | **降级**：只抽那几句，并入相邻卡 |
| `R3` | 含刻板印象 / 无效或有害建议 | **剔除，不复述** |
| `R4` | 纯元内容（课程导学、总结、卖课话术） | **剔除** |

**两条硬性要求：**
- **判定必须读正文**，不能只看标题（标题含「面试官」的可能是纯技术篇）。
- **必须留台账**：路径 / 判定码 / 理由 / 是否含可复用解码案例。剔除不是丢弃，是可追溯。

### 步骤 1 · 机翻解码

先输出对照表，再动笔：

| 原文（机翻） | 还原 | 错译类型 |
|---|---|---|

**五条解码通则：**
- **同音近音替代**：构语言→Go、护士锁→互斥锁、利用→nil、裸体→得体、首时→守时、小r→HR。
- **英文术语被音译或截断**：autom→atomic、sate格外→SET GLOBAL、hastgrim→Histogram。
- **数字/下标混乱**：口述索引常与文字对不上，**以代码逻辑重建**，不硬信数字。
- **术语整串崩坏**：连续多词识别错、整句不可读（如「几月份先行加三点愣」←「金字塔原理 + 结论先行 + 三点式」）。
  → **按上下文重建语义**，重建拿不准的标 `[存疑]`。
- **编号/列表结构崩坏**：讲稿「首先 / 其次 / 第三」错位漏项。
  → **按语义顺序重建编号**，不硬信原文序数词。

### 步骤 2 · 技术点拆解（含出卡节奏分层）

对每篇输出：

| # | 原文定位 | 识别的技术点 | 类型 | 面试价值 | 出题形态 |
|---|---|---|---|---|---|

- **类型**：语法 / 原理 / 并发 / 内存 / 性能 / 架构 / 工程实践 / 排障
- **面试价值**：`L1` 必考基础 / `L2` 高频进阶 / `L3` 架构原理 / `L4` 深水区（源码、边界、极端场景）
- **出题形态**：概念主问 / 场景题 / 排障题 / 设计题 / 代码题 / 对比题
- **颗粒度：一个技术点 = 一张卡。** 宁可拆 20 张薄的，不要合 5 张厚的。
- **难度分布**：一批卡里 `L1:L2:L3:L4` 建议 **2:4:3:1**。

**出卡节奏按源文件体量分层（先量后跑，别全书一个节奏）：**

| 源文件体量 | 通常口播时长 | 深度上限 | 出卡策略 |
|---|---|---|---|
| < 3KB | 1~2 分钟 | L1~L2 | 1 张主卡，**不出深挖** |
| 3~6KB | 3~5 分钟 | L2 | 1~2 张主卡 |
| 6~12KB | 5~10 分钟 | L2~L3 | 2~3 张卡，按技术点拆 |
| ≥ 12KB | 10 分钟以上 | L3~L4 | 3~5 张卡，**深挖主战场** |

> 体量只是**先验**，最终以本步拆出的技术点数量与质量为准。
> 上表来自实测：370 篇技术章中位数 8.3KB，30.8% ≥12KB，35% <8KB——**约三分之一素材撑不起 L3/L4，别硬撑**。

### 步骤 3 · 出卡

**分级产出：**

```text
<三位编号>-<英文短横线标题>.md          # 主卡：≤400 字，可背
<三位编号>-<英文短横线标题>.deep.md      # 深挖：选读，只在面试官继续挖时才用
```

> **⚠️ 400 字是硬上限，不是建议值。**
> 超限的**唯一**正确解法是**拆卡**，不是压缩内容：
> - 难度 `L3+` → 把超出部分拆到 `.deep.md`
> - 难度 `L1/L2` → **不要出深挖**，改用「一个技术点一张主卡」把内容拆成多张
> **禁止**为了凑进 400 字而删掉机制、边界、追问或验证数据——那样卡片会变成没用的口号。

**深挖出卡门槛（防注水的关键闸门）：**
仅当满足以下**任意一条**才出 `.deep.md`，否则只出主卡：

1. 难度 ≥ `L3`（存在明确的权衡或可对比的替代方案）
2. 存在争议，或禁止清单里有相关错误说法需要拆解
3. 涉及**版本翻转**（不同版本结论不同）
4. 原文对同一问题给了多个方案，需要横向对比

> **`L1` / `L2` 默认不出深挖。** 薄源文件上硬写深挖 = 注水，直接违反铁律 1 和 2。

## 3. 卡片模板

> **注意**：下面 3.1 / 3.2 里出现的 `#` `##` 标题是**模板的字面内容**（就是你要写进输出文件的文字），
> 不是本文档的章节。别把它们当成本提示词的结构来解析。

### 3.1 主卡（必出，≤400 汉字，不含代码，一屏可读完）

# 编号 标题

> 分类：<> | 难度：L1~L4 | 题型：八股题 / 工程题 / 事故题 | 频率：高 / 中 / 低 | 关键词：**a** / **b**
> 原文锚点：第 N~M 段「原文关键句截断 30 字」

## 一句话总述
一句话说清本质。5 秒抓核心。

## 面试官视角
- **考察意图**：真正在验证什么能力
- **分档**（必须挂可验证判据，不许给玄学结论）：
  - `P5 能干活` = 知道怎么用
  - `P6 懂原理` = 能说清机制 + 举得出一个反例 + 知道一个替代方案
  - `P7 有判断` = 能说清**代价与边界** + 知道**什么时候不该这么用** + 有真实踩坑经验
- **红旗答案**：这么答就掉分（2~3 条）
- **惊艳点**：必须是「**可证伪的断言 + 验证方式**」，禁止写成散文
  > 合格示例：某操作在 A 路径 0 alloc/op、在 B 路径 1 alloc/op
  > —— 验证：`testing.AllocsPerRun` + `go build -gcflags=-m`，go1.26.5

## 主问答
**Q（面试官原话）：** 用真人语气提问，不用教科书标题。

**A · 标准答案骨架：**
1. **先给结论**：……
2. **再给机制**：……
3. **最后给边界**：……在什么场景不成立

> ≥3 点，每点以 `**加粗关键词**` 开头，短句。

**A · 加分层：** 一句话点出代价或权衡。

## 追问链（能力分层，不写死 3 层）

| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | 术语确认 | 知不知道有这个东西 | | 换题 → 不及格 |
| L2 | 机制 | 是背的还是会推的 | | 判 P5 |
| L3 | 边界与反例 | 有没有踩过坑 | | 判 P6 |
| L4 | 权衡与替代方案 | 有没有架构判断力 | | 判 P6+ |
| L5 | 生产故障与演进 | 有没有真实作战经验 | | 答得上判 P7 |

## 版本与兼容性
| 结论成立版本 | 翻转点（哪个版本改了什么） | 现在该怎么答 |
|---|---|---|

> 涉及运行时 / 语言语义 / 标准库的题**必填**。不填视为不合格。
> 版本信息未核实 → 标 `[存疑]`，**不得写进主卡**。

## 关键代码
1 段，可运行，关键点写在注释里。

## 总结与追问预判
- 三行内总结
- 预判面试官顺势会问的 1~2 个问题（写清指向哪张卡，形成链接）

### 3.2 深挖附录（`.deep.md`，过门槛才出）

## 思路与架构
思维路径（从哪切入 → 怎么收敛）+ mermaid（仅限有分支 / 时序 / 状态的图）+ **文字版说明**

## 方案取舍
对比表（性能 / 复杂度 / 一致性 / 运维成本 / 适用场景）+ **选型结论** + **不适用边界**

## 细节与核心 API
≥5 条，反引号包裹，每条一句话作用 + 易踩的坑

## 性能量级与实测数据
时间 / 空间 / QPS 或延迟数量级；有实测的附命令与输出

## 答题技巧
30 秒版 / 3 分钟版 / 白板版 / 话术模板 / **不会怎么接**（降维、迁移、诚实收尾）

## 广度与深度延伸
横向（同类问题、其他语言怎么做）/ 纵向（源码层、运行时层、规范）

## 反问环节
这题之后可以反问面试官什么（训练主动性）

## 5. 禁止清单

### 5.1 通用禁令（任何语言都成立）

| ❌ 禁止 | 为什么 |
|---|---|
| 「X 一定比 Y 快 / 好」而无前提 | 性能结论永远有条件，无前提的断言是外行信号 |
| 把**未指定行为**说成「随机」 | 「未指定」≠「随机」，后者暗示有概率模型 |
| 把**某个版本的行为**当成永远成立 | 语言会变，尤其运行时和标准库 |
| 用**其他语言的范式**解释本语言 | 暴露"没真写过"，是最高频的减分项 |
| 把**优化手段**当成普适建议（缓存 / 连接池 / 索引 / pool） | 用错场景会变慢，无前提的建议等于没建议 |
| 说出**具体数值但给不出验证方式** | 面试官一追问就塌，比不说更糟 |

### 5.2 示例（Go，均已实测）

| ❌ 错误说法 | ✅ 正确说法 |
|---|---|
| 「`defer` 有性能问题，要写在函数开头」 | **defer 本身很快**：稳态实测（go1.26.5，`-benchtime=200000x`）循环外单个 defer **6.1~6.6 ns/op、0 B/op、0 allocs/op**。⚠️ **但别在循环里 defer —— 理由是语义不是性能**：`defer` 在**函数返回时**执行，写在循环里会把释放时机**推迟到整个函数结束**（循环 10 万次就攒 10 万个未释放资源），这是**资源泄漏**。性能只在闭包**捕获**外部变量时变差：实测 **88 B/op、6 allocs/op**；不捕获则是 0 分配（走开放编码） |
| 「map 遍历顺序是**随机**的」 | 严格说是**未指定**（unspecified），规范从未承诺顺序 |
| 「channel 一定比 mutex 快」 | 无竞争时 mutex 更快；channel 有额外的 goroutine 调度开销 |
| 「Go 性能差是因为没有 JIT」 | 与 JIT 无关，是逃逸分析与内存分配模型的问题 |
| 「`interface{}` 已过时，该用泛型」 | 泛型**不能**替代 interface 的动态派发，两者解决不同问题 |
| 「协程轻所以能开百万」 | 前提是**有 IO 阻塞**；纯 CPU 密集型并不比线程轻 |
| 「`sync.Pool` 能提升性能」 | 它减少的是**分配与 GC 压力**，高频短生命周期对象才有收益，用错更慢 |

> **其他语言按同样方式推导**：先找该语言里被"说得最顺口但其实是错的"的说法，逐条验证后入表。
> 验证方式：跑代码 / 读源码 / 查官方 release notes。**验证不了的不写。**

### 5.3 禁止行为

- ❌ 为凑格式写空节（无内容的「方案取舍」不如不写）
- ❌ 为凑深度而补充未经核实的内容
- ❌ 对所有题强制同一长度——`L1` 基础题允许只写 3 节，**强制统一长度必然逼出注水**
- ❌ 对薄源文件硬出 `.deep.md`——见步骤 3 的门槛
- ❌ 保留任何刻板印象或人身评价

## 6. 语言无关适配原则

**不预设技术栈。** 出卡前先回答四个问题，答案就是这门语言的考察骨架：

1. **不可替代特性**——这门语言为什么被选？它有什么别的语言做不到的？
2. **反直觉语义**——最容易踩坑、最容易说错的地方在哪？（→ 直接喂给禁止清单）
3. **版本演进**——最近 3 个大版本改了什么？（→ 直接喂给版本栅栏）
4. **面试分层**——语法 → 运行时/引擎 → 并发 → 性能 → 架构，各层的高频题是什么？

**锚点示例（防跑偏，每语言一行，非清单）：**

| 语言 / 技术 | 锚点（只作方向，具体考点按上面四问推导） |
|---|---|
| Go | GMP 调度 / hchan / 逃逸分析 / 三色标记 GC / map 与 slice 底层 |
| Python | GIL / 引用计数 + 分代回收 / asyncio 事件循环 / 描述符与元类 / C 扩展 |
| MySQL | InnoDB B+ 树与最左前缀 / MVCC / redo + undo / 两阶段提交 / 间隙锁与死锁 |

## 7. 批量模式

0. **颗粒度校准前置（首次批量必做）。** 先抽 10 篇不同体量的源文件试跑，校准「每篇到底出几张卡」，再全量铺开。
   取样要求：**最厚章 2 篇 + 最薄章 2 篇 + 中等章 2 篇 + 本批要跑的章 4 篇**。
   试跑产出一张「节奏表」：每篇出了几张主卡、几张深挖、难度分布——用它修正步骤 2 的先验。
1. **开工前**：记录 `VERIFY_VER`（本批验证用的版本），并核对该版本对应的 release notes 是否有影响本批考点的变化。
2. **先分诊全批**，把剔除项写进台账，再开始出卡。
3. **输出显式编号区间**，跨批连续不重叠；与 `EXISTING` 重复的只写交叉引用（"见 087 卡"）。
4. **每批汇报三件事**：① 纠正了哪些原文技术错误 ② 剔除了哪些篇目及判定码 ③ 本批验证版本
5. **并行子 Agent 一次不超过 3 个**（有频率限制）；被限流则等重置后继续，已落盘文件不受影响。
6. **超长章节先按句号切成临时文件**再派发，避免单 Agent 上下文不够。
7. **逐篇即时落盘**，不要攒到最后统一写——上下文衰减会让后面的卡质量下滑。

## 9. 收尾提醒

**这套提示词能保证的**：结构正确、事实可回溯、版本有栅栏、错误说法被拦住、**薄素材不会被迫注水**。

**它保证不了的**（别指望）：
1. **真实面试官是否满意**——只能去面 3~5 场，拿原话回来改
2. **可口述性**——卡片写完不等于讲得顺，得出声复述、录像回看
3. **源素材的物理上限**——实测约 35% 的素材撑不起 L3/L4，此时**如实按 L1/L2 出卡，不要注水**
4. **时效性**——版本信息会腐烂，靠第 7 节的流程维持，不靠写死知识

**所以：卡做到 90 分就够了，剩下的时间花在去面试。**
