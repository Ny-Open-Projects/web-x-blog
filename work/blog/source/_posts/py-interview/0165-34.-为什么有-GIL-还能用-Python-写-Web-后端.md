> 分类：并发/GIL | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**IO 期间释放 GIL** / **CPU 密集** / **IO 密集**
> 原文锚点：第 13~21 段「对于 CPU 密集的任务影响比较大…IO 期间会释放 GIL，所以 IO 密集影响不是特别大」

## 一句话总述
GIL 会在**阻塞 IO 期间被释放**并切换到其他线程，因此**IO 密集**的 Web 服务仍能靠多线程/协程拿到并发收益，而**CPU 密集**任务几乎吃不到多核。

## 面试官视角
- **考察意图**：能否给出**分场景**的并发选型，而不是一句"Python 多线程没用"。
- **P5** 知道 CPU 密集用多进程 / **P6** 能解释"IO 期间释放 GIL" / **P7** 能说清各路线的代价与不适用边界。
- **红旗**：① "Python 多线程完全没用"；② "CPU 密集用协程解决"（协程跑在同一线程，只会更糟）；③ 无前提断言"协程一定比线程快"。
- **惊艳点**：把 CPU 密集代码放进协程，**不仅不加速，还会阻塞整个事件循环**。验证：asyncio 里跑一段纯计算，其他协程全部卡住 `[实测]`

## 主问答
**Q：既然有 GIL，Python 多线程还有什么意义？**
**A：**
1. **先给结论**：对 **IO 密集**有意义（等待被重叠），对 **CPU 密集**基本无意义（拿不到多核）。
2. **再给机制**：线程发起网络/磁盘 IO 时**释放 GIL**，其他线程趁机执行，N 个 100ms 的 IO 请求总耗时接近 100ms 而非 N×100ms；而纯计算线程只在切换间隔到期时让出锁，计算无法真正并行。
3. **最后给边界**：**协程不是绕过 GIL 的手段**——它在单线程内靠事件循环切换，遇到 CPU 密集或未改造的阻塞库会拖垮整个循环；CPU 密集必须走多进程或 C 扩展。
**加分层**：Web 后端的时间大头在数据库与网络 IO，所以**语言执行效率通常不是瓶颈**——先 profiling 再谈优化，别一上来就换语言。

## 关键代码
```python
import threading, time, asyncio
def io_task(): time.sleep(0.2)                 # sleep 期间释放 GIL
t0 = time.perf_counter()
ts = [threading.Thread(target=io_task) for _ in range(5)]
[t.start() for t in ts]; [t.join() for t in ts]
print("5 个 IO 任务多线程:", round(time.perf_counter() - t0, 2))   # ≈0.2s 而非 1.0s

async def cpu_block():                          # 错误示范：CPU 密集放进协程
    s = time.perf_counter()
    while time.perf_counter() - s < 0.2: pass   # 整个事件循环被卡住
```

## ⚠️ 原文纠错
原文「对 IO 密集的程序影响不是特别大」结论正确；需补正一处：协程**不是**规避 GIL 的手段，它只是把等待时间重叠掉，CPU 密集场景必须走多进程。原文音译术语已还原。
