> 原文锚点：第 7~37 段「从浏览器输入 url 到返回经历哪些过程：DNS→TCP→HTTP→反向代理→WSGI→web 应用→响应→挥手」

## 一句话总述
输入 URL 后宏观链路：**查 DNS 拿 IP → socket 发起 TCP 三次握手 → 发 HTTP 请求 → Nginx 反向代理/负载均衡 → WSGI 适配层（uWSGI/gunicorn）→ Web 框架（Django/Flask/Tornado）处理（查库/发消息）→ 响应经 TCP 返回 → 四次挥手关闭**。

## 面试官视角
- **考察意图**：是否建立"网络分层 + 请求逐跳"的整体心智模型，而非背单点协议。
- **P5** 能说出 DNS→TCP→HTTP→Nginx→WSGI→应用的顺序 / **P6** 能讲清每一跳的角色（Nginx 负载均衡、WSGI 解耦框架与服务器） / **P7** 能下钻到任一层的细节（DNS 递归、TLS 握手、WSGI 协议字段）。
- **红旗**：把流程讲成"浏览器直接连到 Flask"；或在不熟的层硬编细节把自己带坑里。
- **惊艳点**：业务开发者答到 **TCP 层 + Nginx + WSGI** 已够用；再补一句"TLS 在 TCP 之后、HTTP 之前（HTTPS）"即显深度 —— 验证：`curl -v https://example.com` 可见 DNS→TCP→TLS→HTTP 顺序 `[实测]`。

## 主问答
**Q（面试官原话）：** 从浏览器输入一个网址到页面返回，中间经历了什么？

**A · 标准答案骨架：**
1. **先给结论**：按顺序走 **DNS 解析 → TCP 连接 → HTTP 请求 → 反向代理 → WSGI → 应用处理 → 响应返回 → 连接关闭**。
2. **再给机制**：先看本地 DNS 缓存/`hosts`，未命中则**递归查询**本地 DNS→根→权威服务器拿到 IP；`socket` 发起 **TCP 三次握手**；请求打到 **Nginx**（反向代理/负载均衡）再经 **WSGI**（uWSGI/gunicorn）转给 **Web 框架**做业务（查库/消息）；响应原路经 TCP 返回后**四次挥手**。
3. **最后给边界**：对后端岗答到 TCP 层足够；只讲"熟悉到哪一层就说到哪一层"，别在没把握的链路层硬编。

**加分层**：Nginx 与 WSGI 是两个不同职责——前者是**流量入口/负载均衡**，后者是**Python 应用与 Web 服务器的适配协议**，别混为一谈 `[经验]`。
