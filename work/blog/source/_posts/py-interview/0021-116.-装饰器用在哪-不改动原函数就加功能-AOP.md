> 分类：编程范式/装饰器 | 难度：L1 | 题型：八股题 | 频率：高 | 关键词：**AOP** / **装饰器模式** / **日志** / **横切关注点**
> 原文锚点：第 1~8 段「在不修改原来函数的情况下，通过装饰器增加一些功能」

## 一句话总述
装饰器对应设计模式的**装饰器模式**、思想上是**面向切面编程（AOP）**：把**日志、鉴权、限流、缓存、耗时统计、重试、事务**这类**横切关注点**从业务函数里剥出去，**不改原函数一行代码**就加上。

## 面试官视角
- **考察意图**：确认你知道"什么时候该用装饰器"，而不是到处滥用。
- **P5** 能举出打日志 / **P6** 能列出 5 类以上横切场景并说明每类的实现要点 / **P7** 能指出**装饰器不适合承载业务分支**（会破坏可读性）并给出替代（中间件/显式调用） `[经验]`。
- **红旗**：① 把业务逻辑塞进装饰器（难以调试、难测试）；② 认为装饰器能提升性能（它**增加一层调用开销**）；③ 在需要**顺序敏感**的多装饰器场景中随意排列（见 115）。
- **惊艳点**：选装饰器还是中间件——**作用于单个函数用装饰器，作用于整条请求链用中间件**（Flask/Django 的 middleware）。验证：同一段鉴权逻辑，装饰器版只保护被标的视图，中间件版保护全部 `[实测]`。

## 主问答
**Q：装饰器一般用在哪些场景？它解决了什么问题？**
**A：**
1. **定位**：把与业务无关的**横切逻辑**（日志、性能统计、鉴权、限流、缓存、重试、事务）从函数体中剥离，实现**不修改原函数**就增强功能。
2. **典型场景**：① **记录日志/耗时**；② **权限校验**；③ **缓存**（`functools.lru_cache` 就是装饰器）；④ **重试与熔断**；⑤ **注册路由/插件**（框架启动时收集）。
3. **边界**：装饰器适合"通用、可复用、与返回值弱相关"的增强；**业务分支判断**不要塞进去，否则调用方看不到控制流，排查困难。
**加分层**：与继承/组合对比——那是**给类扩展功能**的手段，装饰器是**给函数（或类）扩展功能**且**运行时生效**、可随时摘除，侵入性最低。

## 关键代码
```python
import functools, time

def retry(times=3):                       # 带参装饰器：重试
    def deco(func):
        @functools.wraps(func)
        def w(*a, **k):
            for i in range(times):
                try:
                    return func(*a, **k)
                except Exception:
                    if i == times - 1: raise
        return w
    return deco

@functools.lru_cache(maxsize=128)         # 内置缓存装饰器
def slow(x):
    time.sleep(0.1); return x * 2
```
