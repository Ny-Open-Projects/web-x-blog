> 分类：并发/选型 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**多进程** / **协程** / **Cython** / **序列化代价**
> 原文锚点：第 25~31 段「CPU 密集可以用多进程加进程池…IO 密集可以使用多线程或者协程」

## 一句话总述
先分 **CPU 密集还是 IO 密集**：CPU 走**多进程/进程池**或把热点下沉到 **C 扩展/Cython**，IO 走**多线程或协程**；没有一条路线是免费的。

## 面试官视角
- **考察意图**：能不能给出带**代价**的选型，而不是堆方案名词。
- **P5** 知道 multiprocessing / **P6** 能分场景给出选型 / **P7** 能讲清每条路线的成本（内存、序列化、调试、部署复杂度）。
- **红旗**：① "用协程解决 CPU 密集"；② 无前提说"多进程一定更快"；③ 把 Cython 说成 CPython 解释器（两者完全不同）。
- **惊艳点**：多进程绕开 GIL 的代价是**内存占用 ×N + 参数需 pickle 序列化**；任务太小反而更慢，传大对象常变成新瓶颈。验证：小任务用 `ProcessPoolExecutor` 与串行对比 `[实测]`

## 主问答
**Q：既然 GIL 限制多核，你们怎么解决 CPU 密集场景？**
**A：**
1. **先给结论**：CPU 密集 → `multiprocessing` / `ProcessPoolExecutor` / C 扩展；IO 密集 → `threading` / `asyncio` / `gevent`。
2. **再给机制**：多进程各有独立解释器与 GIL，因此能吃满多核；协程在单线程内靠事件循环切换，只把**等待时间**重叠掉，不产生并行计算。
3. **最后给边界**：进程创建与 pickle 序列化有固定成本，**任务粒度太小不划算**；协程里跑 CPU 密集或未改造的阻塞库，会拖垮整个事件循环。
**加分层**：Cython 是把 Python 代码**编译成 C 扩展**的工具（**不是** CPython 解释器），适合把已定位到的热点函数**局部**加速，性价比通常高于整体换语言。

## 关键代码
```python
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor
import time
def cpu(n): return sum(i * i for i in range(n))
def io(_): time.sleep(0.1); return 1
if __name__ == "__main__":
    t0 = time.perf_counter()
    with ProcessPoolExecutor() as ex: list(ex.map(cpu, [300000] * 4))
    print("CPU 密集用进程池:", round(time.perf_counter() - t0, 2))
    t0 = time.perf_counter()
    with ThreadPoolExecutor(8) as ex: list(ex.map(io, range(8)))
    print("IO 密集用线程池:", round(time.perf_counter() - t0, 2))   # ≈0.1s
```

## ⚠️ 原文纠错
原文「Cython 不是 CPython 解释器，它是把 Python 程序转化成 C 代码的一个扩展」结论正确；补充一点：Cython 生成的扩展**仍受 GIL 约束**，只有在 `with nogil` 块里才真正释放锁 `[经验]`。

- 二分选型 + 明确代价；粒度太小别上进程池，CPU 密集别上协程。
