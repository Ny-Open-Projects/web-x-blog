## 一句话总述
**SQL 注入 = 攻击者构造特殊输入拼进 SQL，使后端执行恶意语句**（如 `'--` 注释掉密码校验）；根因是**直接拼接 SQL 且不过滤**。修复用**参数化查询（占位符 + 元组传参）**，防范核心原则"永远不信任用户输入"。

## 面试官视角
- **考察意图**：是否真懂注入原理与"为什么参数化能根治"，而非只背"用 ORM"。
- **P5** 能说出注入原理（拼接 SQL + 无过滤）并给出修复（参数化/ORM） / **P6** 能现场演示 `' OR '1'='1` 或 `'--` 绕过验证，并解释占位符让数据"只当值不当代码" / **P7** 能系统列防范：输入校验（类型/范围/特殊符转义）+ ORM + DB 最小权限 + 不存明文密码 + 错误不回显。
- **红旗**：把"转义引号"当唯一手段却不知占位符更本质；认为"用了框架就绝对安全"。
- **惊艳点**：能点出"即使参数化，LIKE/ORDER BY 等场景仍需白名单（列名不能占位）" `[经验]`。

## 主问答
**Q（面试官原话）：** 什么是 SQL 注入？怎么产生？如何防范？

**A · 标准答案骨架：**
1. **原理**：当后端用**字符串直接拼接** SQL 且**不校验/转义用户输入**时，攻击者在输入里混入 SQL 片段（如 `李四'--`），把原语句的后续条件（如密码校验）注释掉，从而绕过验证或窃取数据。
2. **演示**：源文件用终端输入 name=李四、password=`李四'-- 随便` → 拼接后 `--` 之后全被当作注释，密码校验失效，仍返回结果。
3. **修复（根治）**：把拼接改为**参数化查询**——SQL 里写占位符 `%s`，参数通过**元组**交给 `execute()`，驱动会正确转义，数据"只当值、不当代码"。用 **ORM** 同理（底层也参数化）。
4. **防范原则**：① 永远不信任用户输入；② 校验类型/范围、过滤转义特殊字符；③ 优先用 ORM/参数化；④ 数据库账号最小权限；⑤ **绝不明文存储密码**（用加盐哈希），即使泄露也不致命。

**加分层**：参数化不能解决所有场景——`LIKE` 的 `%`、`ORDER BY` 的列名无法占位，需用**白名单**校验列名；错误信息也不应回显给前端（避免泄露表结构）。

## 关键代码
```python
# 错误：字符串拼接（有注入漏洞）[实测, python]
name = input(); pwd = input()
sql = f"SELECT * FROM users WHERE name='{name}' AND password='{pwd}'"   # 危险！

# 正确：参数化查询（MySQLdb/PyMySQL 自动转义）
import pymysql
cur = conn.cursor()
cur.execute("SELECT * FROM users WHERE name=%s AND password=%s", (name, pwd))  # 安全
```
