# Go 项目开发: 商城主服务优雅退出

优雅退出不是锦上添花。**异步发 Kafka 时，进程一重启，还压在 Go channel 里的消息就直接没了** —— 商品变更事件一丢，搜索侧索引就和数据库对不上，这种数据不一致往往过很久才被发现。

本节给两种实现：**hook 注册式**（推荐）和**手写 signal 监听式**，本质都是"按正确顺序关组件"。

## 纲要

- 为什么要优雅退出：异步消息会丢在 channel 里
- 退出必须关闭的三个组件与顺序
- HTTP 关闭：带 10 秒超时的 Shutdown
- Kafka 关闭：冲干生产者缓冲区
- MySQL 关闭：关连接池
- hook 注册式实现
- 手写 signal 监听式实现
- 注意事项总结

## 为什么必须优雅退出

```txt
进程退出前没做的事：
  ❌ HTTP server 还在接请求 → 客户端拿到 connection reset
  ❌ Kafka producer 还在 channel 里攒批  → 这批消息直接丢失
  ❌ MySQL 连接池还有活跃连接 → 事务中断、连接泄漏

优雅退出要做的：
  ✅ 停止接收新请求（Shutdown 而非 Close）
  ✅ 等已处理的请求跑完
  ✅ 冲干 Kafka 缓冲区里的消息
  ✅ 关连接池
```

一句话：**`Close` 是立刻拆，`Shutdown` 是请里面的东西先出来。**

## 要关的组件与顺序

关闭顺序不能乱：

```txt
1. HTTP server   ← 先停止收新请求，让在途请求跑完
2. Kafka producer ← 冲干 channel 里没发出的消息
3. MySQL          ← 最后关存储，保证前面两步的日志/状态能落库
```

反过来会出问题：先关 MySQL，Kafka 冲干时写状态就失败了；先关 Kafka，消息还是在 channel 里。

## HTTP + Kafka + MySQL 的关闭函数

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"time"

	"github.com/IBM/sarama"
	"gorm.io/gorm"
)

// Server 主服务持有的资源
type Server struct {
	httpServer *http.Server
	producer   sarama.SyncProducer // 同步生产者，退出前要冲干
	ormDB      *gorm.DB
}

// CloseHTTPServer 关 HTTP：给 10 秒超时，超时就放弃在途请求
func (s *Server) CloseHTTPServer() error {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := s.httpServer.Shutdown(ctx); err != nil {
		return fmt.Errorf("http server close error: %w", err)
	}
	return nil
}

// CloseProducer 关 Kafka 同步生产者，把缓冲区里的消息全部发出去
func (s *Server) CloseProducer() error {
	if err := s.producer.Close(); err != nil {
		return fmt.Errorf("kafka producer close error: %w", err)
	}
	return nil
}

// CloseMysql 关连接池
func (s *Server) CloseMysql() error {
	sqlDB, err := s.ormDB.DB()
	if err != nil {
		return fmt.Errorf("mysql get sqlDB error: %w", err)
	}
	if err := sqlDB.Close(); err != nil {
		return fmt.Errorf("mysql close error: %w", err)
	}
	return nil
}

func main() {
	srv := &Server{}
	// 实际项目里这些字段由初始化流程填充，此处省略
	_ = srv

	// 注册退出钩子，按注册顺序执行
	hooks := []func() error{
		srv.CloseHTTPServer,
		srv.CloseProducer,
		srv.CloseMysql,
	}
	for _, fn := range hooks {
		if err := fn(); err != nil {
			// 单个组件关闭失败不能中断整体退出
			fmt.Println("close hook error:", err)
		}
	}
}
```

三个要点：

- **`Shutdown(ctx)` 而不是 `Close()`**。`Close` 会立刻关闭所有连接，`Shutdown` 会先停止监听、再等活跃连接自然结束；超了 10 秒才强制收尾。
- **Kafka `Close()` 是同步的**，它会等生产者把攒批队列冲干净才返回 —— 这正是"不丢消息"的保障动作。
- **每个 hook 单独判错**。关 Kafka 失败不该阻止你去关 MySQL，最后统一打日志。

## 手写 signal 监听式

不想引入封装包，就自己监听系统信号：

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"

	"github.com/IBM/sarama"
	"gorm.io/gorm"
)

// Server 主服务持有的资源
type Server struct {
	httpServer *http.Server
	producer   sarama.SyncProducer
	ormDB      *gorm.DB
}

// WaitAndShutdown 阻塞等系统信号，收到后按正确顺序关闭资源
func (s *Server) WaitAndShutdown() {
	signals := make(chan os.Signal, 1)
	signal.Notify(signals, syscall.SIGINT, syscall.SIGTERM, syscall.SIGHUP)

	// 没收到信号就一直阻塞在这里
	sig := <-signals
	fmt.Println("received signal:", sig)

	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := s.httpServer.Shutdown(ctx); err != nil {
		fmt.Println("http server close error:", err)
	}

	if err := s.producer.Close(); err != nil {
		fmt.Println("kafka producer close error:", err)
	}

	if sqlDB, err := s.ormDB.DB(); err == nil {
		if err := sqlDB.Close(); err != nil {
			fmt.Println("mysql close error:", err)
		}
	}
}

func main() {
	srv := &Server{}
	// 实际项目里这些字段由初始化流程填充
	srv.WaitAndShutdown()
}
```

几个容易踩的点：

- **要监听的信号不止一个**。`SIGINT`（Ctrl+C）、`SIGTERM`（`kill`）必听，`SIGHUP`（终端断开）也要听 —— 少监听一个，`kill` 就是硬杀，缓存区照样丢。
- **`SIGKILL` 监听不到**，这是设计如此，只能靠容器给 `terminationGracePeriodSeconds` 留时间。
- **channel 给个缓冲**（哪怕 1）。不带缓冲时信号发送会阻塞，快速连按 Ctrl+C 反而出怪问题。

两种方式本质一样，**推荐用 hook 封装**：把关闭函数集中注册，升级顺序只改一行，不用在每个地方重复写关闭逻辑。

| 2 | Kafka producer | `Close()` 冲干 | 不丢 channel 里积压的消息 |

## 注意事项总结

1. **异步发 Kafka 必须优雅退出**，否则 channel 里的消息直接丢。
2. **关闭顺序：HTTP → Kafka → MySQL**，反了会丢状态或丢消息。
3. **`Shutdown` 不是 `Close`**，前者停收新请求并等在途请求，后者硬拆。
4. **HTTP 关闭给超时**（10 秒），避免请求堆积把退出卡死。
5. **Kafka `Close()` 是同步的**，会冲干缓冲区，这是不丢消息的关键。
6. **每个关闭动作单独判错**，一个失败不阻断其余。
7. **信号至少监听 `SIGINT` / `SIGTERM` / `SIGHUP`**，少一个就是硬杀。
8. **`SIGKILL` 收不到**，靠容器预留宽限期兜底。
9. **signal channel 带缓冲**，避免信号发送被阻塞。
10. **hook 式更好维护**，把关闭函数集中注册，升级只改顺序。

## 总结

优雅退出不是锦上添花：**异步发 Kafka 时，进程一重启，压在 channel 里的消息就直接丢了**，商品变更事件一丢，搜索侧索引就和数据库对不上，这种不一致往往过很久才发现。

关闭顺序不能乱——**HTTP → Kafka → MySQL**：先停收新请求让在途跑完，再冲干 Kafka 缓冲区（同步 `Close` 会等攒批队列清空），最后关存储。每个关闭动作单独判错，一个失败不阻断其余；信号至少监听 `SIGINT / SIGTERM / SIGHUP`，`SIGKILL` 收不到只能靠容器宽限期兜底。推荐用 hook 注册式，关闭顺序只改一行。
