> 分类：Elasticsearch | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**scroll、scroll_id、搜索上下文、段合并、max_open_scroll_context**

> 原文锚点：第 42~72 段「通过创建快照保存查询结果…段合并将不会被执行」

## 一句话总述
Scroll 对初始查询结果做**快照**并返回游标 ID，后续每批带上它继续取；适合导出、备份这类**离线全量遍历**，代价是服务端长期持有上下文。

## 面试官视角
P7 必须讲代价，只讲用法会露怯：scroll 上下文占内存；持有期间**它涉及的段不参与合并**，文件句柄与磁盘上涨；默认最多同时打开 500 个上下文；用完必须显式删除 `[经验]`。再补一句语义：取的是快照，**遍历期间的新写入看不到** `[源码]`。

## 主问答
**Q（面试官原话）：** Scroll 怎么用，为什么生产上不敢乱开？

1. **初始化带续期时间**：首个请求是普通查询，额外加 `scroll=5m` 表示上下文存活时长，再加 `size` 定每批条数 `[经验]`。
2. **靠游标滚动**：响应返回游标 ID，后续请求只带游标 ID 与新的续期时间；每次返回的游标 ID 会变，必须**用上一次返回值**继续 `[源码]`。
3. **取空即结束**：原文 20 条数据、每批 5 条，滚动 4 次取完，第 5 次返回空数组即为终止信号 `[实测]`。
4. **四项成本**：上下文占内存；持有期间段不合并、句柄与磁盘上涨；默认上限 500 个；必须显式删除释放 `[经验]`。

## 关键代码
```json
POST /user/_search?scroll=5m
{ "size": 5, "query": { "match_all": {} } }
POST /_search/scroll
{ "scroll": "5m", "scroll_id": "DXF1ZXJ5..." }
DELETE /_search/scroll { "scroll_id": "DXF1ZXJ5..." }
```
```go
// 用完必须显式释放，否则上下文会挂到超时
defer func() {
	_, _ = http.Post(esURL+"/_search/scroll", "application/json",
		strings.NewReader(`{"scroll_id":"`+id+`"}`))
}()
```
> 验证：删除游标后再滚会报上下文找不到；持有期间索引段合并被推迟 `[实测]`。

## 总结与追问预判
**快照换来全量遍历，代价是上下文持有**。面试官下一步会问"实时翻页怎么办"——那是 search_after 的活。

## ⚠️ 原文纠错
1. 事实核校：原文"续期时间只需够处理上一批即可"准确——它是**每次请求刷新**的存活时长，不是整个遍历的总时长，本卡澄清常见误解 `[经验]`。
2. 补充：原文"段合并被推迟"的机制准确；这正是句柄与磁盘上涨的根因，需确保节点文件句柄上限足够 `[源码]`。
3. 崩坏词归一：源码将 Scroll、游标、上下文等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
