> 分类：Go 并发 | 难度：中 | 题型：方法论题 | 频率：中 | 关键词：**WaitGroup、无缓冲 channel、信号量、主协程等待、选型**

> 原文锚点：第 1~50 段「主协程等子协程退出:WaitGroup(Add/Done/Wait,最推荐)/WaitGroup广播通知/无缓冲channel同步/信号量(此场景不推荐,本职限并发)」

## 一句话总述
主协程等待子协程退出有几种同步手段：**WaitGroup（`Add`/`Done`/`Wait`）最推荐、可读性最好**；也可用**无缓冲 channel**（子协程末行写、主读全部值）同步；还能用**信号量**，但信号量本职是**限制并发数**，此"等待退出"场景并不推荐。一句话背法：**「等退出首选 WaitGroup，channel 同步可读但繁琐，信号量是限并发不是等待」**。

## 面试官视角
考官看你对 goroutine 同步手段的体系化认知与正确选型，而非只会一种。能讲清 WaitGroup 最推荐的原因、channel 同步的"读满全部"坑、信号量在此场景不推荐的本质，说明选型成熟；用信号量去"等退出"、或不知 WaitGroup 比 channel 可读性更好，是红旗。
- **P5**：知道 WaitGroup 三件套与 channel 同步。
- **P6**：知道 WaitGroup 最推荐、Done 等价 Add(-1)、多协程需读全 channel 值。
- **P7**：知道信号量在此场景不推荐、其本职是限并发、以及广播通知模式。

## 主问答
**Q（面试官原话）：** 主协程怎么等其他协程都退出？有几种办法？

**先铺垫（由浅入深第 1 层）**：主协程 `main` 一退出，所有子协程都被强杀。要让主协程"等大家都干完再退"，Go 给了几种原语，各有适用面——核心选型原则是"等待退出"和"限制并发"要用对原语。

1. **WaitGroup 最推荐（第 2 层）**：启动前 `Add(1)`，协程内 `defer Done()`（等价于 `Add(-1)`），主协程 `Wait()` 阻塞到全部完成；代码简洁、可读性最佳。
2. **无缓冲 channel 同步（第 3 层）**：子协程把"写 channel"放最后一行，主协程依次读出全部值即表示全完成；多协程需读满全部，否则会漏等。
3. **信号量不推荐（第 4 层·选型）**：信号量（`semaphore` 包，P/V 操作）本职是限制同时执行的协程数、保护资源池，并非"等待退出"的合适原语，此场景应优先 WaitGroup。
4. **广播通知（第 5 层·进阶）**：当协程需等"其他协程准备好数据"再继续，可用第二个 WaitGroup 做通知（见 1023 WaitGroup 广播）。
5. **误用风险（第 6 层）**：`Add` 必须在 `go` 之前调用（或配合锁），否则可能 `Wait` 已返回后还没 Add，导致 panic；这是 WaitGroup 最常见误用。

## 版本与兼容性
| 维度 | 说明 |
|------|------|
| WaitGroup | 标准库 `sync.WaitGroup`，全版本稳定；`Done()` = `Add(-1)` |
| Add 时机 | `Add` 必须在启动 goroutine 前（或持锁）调用，否则 `Wait` 可能提前返回/panic |
| 无缓冲 channel | 子末行写、主读满全部值；可读但繁琐 |
| 信号量 | `golang.org/x/sync/semaphore`，限并发非等待 |
| Go 版本 | 与 Go 版本无关，本项目实测 Go 1.26.5 |

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// WaitGroup：最推荐的主协程等待方式
func main() {
	var wg sync.WaitGroup
	for i := 0; i < 5; i++ {
		wg.Add(1) // go 之前 Add，避免竞态
		go func(id int) {
			defer wg.Done() // 等价 wg.Add(-1)
			time.Sleep(time.Millisecond)
			fmt.Println("worker", id, "done")
		}(i)
	}
	wg.Wait() // 阻塞直到所有 Done
	fmt.Println("全部子协程退出，main 才退")
}
```

## 总结与追问预判
**背这三句就够**：① **等待退出首选 WaitGroup（Add 在 go 前、defer Done、Wait 阻塞）**；② **无缓冲 channel 同步可读但需读满全部值，繁琐**；③ **信号量本职限并发，此场景不推荐**。
**预判追问**：
- 「WaitGroup 最容易踩的坑？」→ `Add` 在 `go` 之后调用会竞态 panic，务必先 Add（见本卡第 5/6 层）。
- 「有没有更优雅的等数据就绪？」→ 双 WG 广播通知（见 1023 WaitGroup 广播）。
- 「信号量到底干嘛用？」→ 限并发数、保护资源池（见 1015 channel 信号量 / 1023 无缓冲 vs 信号量）。
