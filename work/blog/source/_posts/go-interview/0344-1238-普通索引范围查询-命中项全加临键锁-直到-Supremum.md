> 分类：数据库 / MySQL 锁 | 难度：L4 | 题型：原理题 | 频率：高 | 关键词：**范围查询、临键锁、间隙锁、记录锁、Supremum、二级索引**

> 原文锚点：第 33~34 段「我们查询的范围是 name 大于 name2…加锁的规则大致如下，所有命中的这个二级索引的列都被加上了临键锁，直到我们这个最大的虚拟记录行也被加上了临键锁，并且命中记录的主键索引被加上了行锁」

## 一句话总述
普通（非唯一）二级索引做**范围查询**时，所有命中的二级索引记录都会被加上**临键锁**，一直加到 **Supremum 伪记录**为止，同时命中的主键记录被加上**记录锁**。

## 面试官视角
P6 会说「范围查询加行锁」；P7 要讲清**三层锁同时存在**——二级索引上是临键锁（不是记录锁）、扫描终点直达 Supremum、主键上是记录锁，并能画出实际锁住的区间形状。

## 主问答
**Q（面试官原话）：** `WHERE name > 'name2'` 这种范围查询，到底锁了哪些东西？

1. **命中项全加临键锁**：所有满足条件的二级索引记录都被加上**临键锁** `[源码]`。
2. **一直加到伪记录**：加锁**延伸到最大的虚拟记录行（Supremum）**，它同样被加临键锁 `[源码]`。
3. **主键补记录锁**：命中记录的**主键索引上被加上行锁**（记录锁） `[源码]`。
4. **与等值查询的差异**：等值查询的不满足项会退化为间隙锁，而**范围查询不退化** `[经验]`。
5. **锁区间的形状**：临键锁是**左开右闭**区间，逐段覆盖 name1~name2、name2~name3…… 直到 Supremum `[源码]`。
6. **实际效果**：范围内所有间隙与记录都被锁住，其他事务**无法插入命中区间内的值** `[源码]`。

## 关键代码
```sql
-- 表：id 主键，name 普通（非唯一）索引；name 值为 1,2,20,3,4,5,7
BEGIN;
SELECT * FROM t WHERE name > 'name2' LOCK IN SHARE MODE;
-- 加锁结果：
--   二级索引：命中的每条记录加临键锁（左开右闭），一直加到 Supremum 伪记录
--   主键索引：命中的记录加记录锁

-- 验证：MySQL 8.0 可直接观察锁类型与被锁数据
SELECT INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks;
```

## 总结与追问预判
**范围查询 = 一条临键锁链，从命中首项一路锁到 Supremum**。面试官必追问「为什么不退化成记录锁」——因为非唯一索引下记录锁挡不住插入，会幻读，详见同批 1238-range-why-next-key。

## ⚠️ 原文纠错
1. 事实核校：命中项加临键锁、延伸至 Supremum、主键加记录锁、临键锁为左开右闭——均与 InnoDB 范围查询加锁规则一致 `[经验]`。
2. 补充：本卡的结论建立在 **RR（可重复读）隔离级别** 上；若业务使用 RC，间隙锁与临键锁均不生效，只剩记录锁，答题时应先确认隔离级别 `[经验]`。
3. 崩坏词归一：源码将临键锁、间隙锁、记录锁、主键索引、二级索引等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
