## 一句话总述
MySQL 的存储引擎是**可插拔**的：表只是**逻辑概念**，物理上如何表示记录、如何读写磁盘都由存储引擎负责；因此存储引擎本质是**表处理器**，它向上提供统一服务、向下屏蔽底层差异。

## 面试官视角
P6 知道 InnoDB 与 MyISAM；P7 要讲清**逻辑层与物理层的分离**（表是逻辑、引擎管物理）、**可插拔带来的收益**（换引擎不需改应用代码），并能说出存储引擎的两大作用与查看方式。

## 主问答
**Q（面试官原话）：** 什么是可插拔存储引擎？它有什么好处？

1. **可插拔**：MySQL 的存储引擎**可按实际需求以插件形式使用** `[源码]`。
2. **封装存储与提取**：MySQL 把**数据的存储和提取操作**都封装在存储引擎模块中 `[源码]`。
3. **表只是逻辑概念**：表由一行行记录组成是**逻辑上的概念**；**物理上如何表示记录、如何从表取数据、如何写入磁盘**，都由存储引擎负责 `[源码]`。
4. **实现可以不同**：不同存储引擎管理的表，**具体存储结构可能不同**，采取的**存储与查询算法也不同** `[源码]`。
5. **本质是表处理器**：存储引擎**本质上是表处理器**；可插拔引擎提供**一套标准的管理和支持服务**，这些服务在所有底层存储引擎中通用 `[源码]`。
6. **是服务组件**：存储引擎本身是**数据库服务的组件**，实际执行在**物理服务器级别**维护底层数据操作 `[源码]`。
7. **带来定制优势**：为有特定需求（数据仓库、事务处理、高可用性）的用户提供巨大优势，同时支持其利用**独立于任何一个存储引擎的接口和服务** `[源码]`。
8. **交互方式**：应用程序员与 DBA 通过位于存储引擎之上的 **connector API 与服务层**与 MySQL 交互 `[源码]`。
9. **换引擎成本低**：若需求变化要求更换或新增存储引擎，**插件式架构不需要对编码或流程做重大变更** `[源码]`。
10. **查看方式**：通过 **`SHOW ENGINES`** 指令可查看当前 MySQL 服务**支持哪些存储引擎**（默认支持 9 种） `[源码]`。
11. **两大作用**：一是**管理表的创建、数据检索、索引创建**等；二是**支持自定义存储引擎的开发** `[源码]`。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| MySQL 5.5 起 | InnoDB 成为默认引擎 | 取代 MyISAM |
| 8.0 | 数据字典改为 InnoDB | 元数据管理统一 |
| 所有版本 | 引擎可混用 | 同一库中不同表可用不同引擎 |
| 所有版本 | 事务支持 | 取决于引擎，非 MySQL 层提供 |

## 关键代码
```sql
-- 查看当前 MySQL 服务支持的存储引擎
SHOW ENGINES;

-- 建表时显式指定存储引擎
CREATE TABLE t_innodb (id INT PRIMARY KEY) ENGINE=InnoDB;
CREATE TABLE t_memory (id INT PRIMARY KEY) ENGINE=MEMORY;

-- 查看某张表实际使用的引擎
SHOW TABLE STATUS LIKE 't_innodb'\G

-- 修改表的存储引擎（会重建表）
ALTER TABLE t_memory ENGINE=InnoDB;
```

## 总结与追问预判
**「表是逻辑的、引擎管物理的」是本卡题眼**。面试官常追问「为什么现在都用 InnoDB」——因为它支持**事务、行锁与崩溃恢复**，而这些能力**由引擎提供、不由 MySQL 层提供**。系统文件层见同批 1210-file-layer。
