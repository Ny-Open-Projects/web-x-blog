## 一句话总述
熔断是"比降级更不得已"的有损方案：调用持续失败达阈值就**打开**拒绝请求，过段时间**半开**探测，恢复则**关闭**——用主动断流避免慢调用把调用方拖垮（雪崩）。降级则在故障时舍弃非核心功能、保核心可用。

## 面试官视角
- 意图：考察候选人对"熔断三态"与"降级取舍"的掌握，以及雪崩的因果链。
- P5 知道熔断防雪崩、降级保核心；P6 能说清三态（打开/半开/关闭）切换；P7 能讲"熔断是更狠的降级"与典型场景（核心服务调非核心被阻塞）。
- 红旗：把熔断和降级混为一谈；以为熔断打开就永远拒。
- 惊艳点：点出典型链——订单服务调消息服务，消息资源不足→订单请求阻塞→订单被拖垮→依赖订单的全局雪崩。

## 主问答
**Q（面试官原话）：** 熔断和降级有什么区别？熔断怎么工作的？
**A：**
1. **结论**：熔断是"更狠的有损降级"——像保险丝主动断开，避免占用资源；降级是"舍弃非核心保核心"。熔断三态：失败达阈值**打开**拒请求 → 一段时间后**半开**放部分探测 → 成功则**关闭**恢复。
2. **机制**：熔断器统计窗口内错误数/比例，超阈值即打开，快速失败（不真调下游）；半开期放行少量请求探活，恢复则闭合、否则继续打开 `[源码]`。
3. **边界**：雪崩=局部故障引发全局不可用；熔断正为防止此——下游抖动时不让调用方被慢响应长期占用连接/线程。降级常与熔断配合使用：熔断打开即走降级返回简化响应/缓存 `[经验]`。

## 关键代码
```go
// 示意，未验证：熔断器三态骨架
type State int
const (Closed State = iota; Open; HalfOpen)

type Breaker struct {
    mu        sync.Mutex
    state     State
    failures  int
    threshold int
    openedAt  time.Time
}

func (b *Breaker) Allow() bool {
    b.mu.Lock(); defer b.mu.Unlock()
    switch b.state {
    case Open:
        if time.Since(b.openedAt) > 5*time.Second { // 半开探测窗口
            b.state = HalfOpen
            return true
        }
        return false // 仍打开：快速失败
    default:
        return true
    }
}
```
