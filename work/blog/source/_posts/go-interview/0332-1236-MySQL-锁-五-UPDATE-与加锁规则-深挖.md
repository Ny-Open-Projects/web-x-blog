## 思路与架构
InnoDB 加锁规则可拆成三把「锁尺子」：
1. **记录锁（Record Lock）**：锁单行，不含间隙（`REC_NOT_GAP`）。
2. **间隙锁（Gap Lock）**：锁区间，开区间不含边界，防插入。
3. **临键锁（Next-Key Lock）**：记录锁+间隙锁，左开右闭，RR 默认行锁形态。
加锁类型由「索引类型（唯一/普通）× 查询形态（等值/范围）× 记录是否存在」三者共同决定；UPDATE 则先按存储/键值变化归约为 delete/insert 再套上述规则。

## 方案取舍
- **唯一索引等值 + 存在 → 记录锁**：主键唯一性让插入/删除该值不可能，无需间隙，退化。
- **唯一索引等值 + 不存在 → 间隙锁**：值不存在，只能锁其前的间隙防插入，开区间不含边界。
- **范围查询 → 临键锁**：范围无法靠唯一性收敛，必须整段间隙锁防内外插入致幻读。
- **间隙锁不互斥（X/S 共存）**：与记录锁不同，间隙锁只为「防插入」而非「独占行」，故 X/S 可共存；这是 RR 下高并发插入仍能部分并行的关键。

## 答题技巧
- 答「一个 SQL 锁了啥」用**三步法**：① 走哪个索引？② 等值还是范围、记录存不存在？③ 套规则得出记录锁/间隙锁/临键锁及区间。
- 必点「RR 默认 next-key、RC 退化」这一隔离级别前提，避免被追问时漏说。
- 区分「临键锁左开右闭 vs 间隙锁全开」的区间语义，这是 P7 分水岭。
- 被要求证明时，直接给 `performance_schema.data_locks` 的 `lock_mode`（含 `REC_NOT_GAP`/`GAP`/`INSERT_INTENTION`）作为观测证据。

## 细节与核心 API

**三把锁尺子**：

```text
记录锁 REC_NOT_GAP          锁单行，不含间隙
间隙锁 GAP                  开区间不含边界，防插入（仅 RR）
临键锁 next-key             记录锁+间隙锁，左开右闭 [a, b)（RR 默认行锁形态）
加锁 = f(索引类型 × 查询形态 × 记录是否存在)；UPDATE 先归约为 delete/insert 再套规则
```

**规则速记**：唯一索引等值+存在→记录锁；不存在→间隙锁；范围→临键锁；间隙锁 X/S 不互斥（只防插入）。

```sql
-- 观测加锁类型（8.0）
SELECT lock_mode, lock_type, index_name, lock_data
FROM performance_schema.data_locks;
-- lock_mode 含 REC_NOT_GAP / GAP / INSERT_INTENTION / X / S
```
