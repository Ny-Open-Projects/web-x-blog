> 分类：消息队列 / Kafka | 难度：L3 | 题型：方案设计题 | 频率：高 | 关键词：**分区内有序**/**业务 ID 哈希**/**key 路由**/**内存队列**/**全局有序代价**
> 原文锚点：第 1~27 段「短时间内对同一个用户的昵称进行了三次修改，这三条消息可能会被发送到不同的分区，被不同的消费者消费，很容易导致消息乱序…在生产消息的时候将同一个业务 ID 的数据发送到同一个 partition 上…使用数据的唯一 ID 来做哈希…Kafka 只支持分区级别的消息有序性」

## 一句话总述
乱序的根源是「**多实例部署 + 同一业务 ID 的消息散落到不同分区**」；解法是把「需要有序的业务单元」钉进一个分区：**生产端用业务唯一 ID（如用户 ID）作 key 哈希路由**到同一分区（SDK 配置哈希分区器 + 指定 key），消费端天然按分区内顺序消费；若消费后还要**异步处理**，再把同一 key 的消息哈希到**同一个内存队列**串行处理——**Kafka 只保证分区级有序，全局有序等于单分区，性能代价不可接受，工程答案是按业务归类取局部有序**。

## 面试官视角
- 考察意图：从「现象（昵称三次修改乱序）」到「方案（key 路由）」再到「边界（全局有序的代价）」的完整推演——这是消息队列方案设计题的标准范式。
- 分档：P5 知道 Kafka 分区内有序；P6 能给出 key 哈希路由方案并说清消费端内存队列；P7 能分析 key 路由的副作用（数据倾斜、扩容重排）与「局部有序 vs 全局有序」的取舍。
- 红旗答案：「加个时间戳排序就行了」——把一致性问题推给消费端排序，丢消息即永久乱序；「手动指定分区号」——分区数可变，写死即失去扩展性。
- 惊艳点：「**哈希路由用『业务 ID』而不是『消息 ID』**——按消息 ID 哈希等于没用，乱序的正是同一业务 ID 的消息；且 key 要选『冲突少、分布均匀』的字段，否则倾斜让单分区成瓶颈」 [经验]。

## 主问答
**Q（面试官原话）：** Kafka 怎么保证消息的有序性？
**A：**
1. **先说结论与前提**：Kafka **只保证分区内有序**；要有序就把「同一业务单元」的消息路由到同一分区——单分区全有序是理论可行、生产不可用的方案（损失多分区并行与负载均衡） [源码]。
2. **乱序场景还原**：同一用户短时间三次修改昵称，三条消息可能被发到**不同分区**、被**不同消费者**（不同应用实例）并行处理——「先改 A 后改 B」可能被倒序执行。多实例部署 + 无 key 轮询分区是默认行为，乱序是常态 [源码]。
3. **生产端解法：业务 ID 做 key 哈希**。配置 `producer.partitioner` 为哈希模式，发送时指定 key=用户 ID——**相同 ID 的消息哈希到同一分区**，分区内 FIFO + 单分区单消费者串行，顺序天然保证。SDK 原生支持，无需手写分区逻辑 [源码]。
4. **为什么不手动指定分区号**：分区数**支持动态调整**，手写 `partition=3` 这种硬编码，分区扩容后路由关系全变，还得跟着改代码——**key 哈希让路由随分区数自动适配**，扩展性完好 [源码]。
5. **消费后异步的补刀**：消费成功后若交由协程池异步处理，**协程池并行会再次打散顺序**——解法是按 key 再哈希到**固定的内存队列**（队列数 = 处理协程数），同一 key 恒定落同一队列、队列内串行，整条链路有序 [源码]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| 分区内 FIFO | 任何版本恒定 | 方案建立在分区内有序之上 |
| 默认轮询分区器 | 无 key 消息轮询打散 | 要有序必须显式带 key |
| 分区扩容 | 哈希取模基数变化，同 key 可能换分区 | 扩容窗口内业务侧需幂等/版本号兜底 |
| 重度倾斜 | 热点用户把单分区打成瓶颈 | 热点拆二级 key（ID+后缀）+ 业务侧容忍 |

## 关键代码
```go
// 生产端: key = 业务 ID, 走哈希分区器 (sarama 形态 [源码])
config := sarama.NewConfig()
config.Producer.Partitioner = sarama.NewHashPartitioner // 按 key 哈希
producer, _ := sarama.NewSyncProducer(brokers, config)

msg := &sarama.ProducerMessage{
	Topic: "user-profile",
	Key:   sarama.StringEncoder(fmt.Sprintf("user-%d", userID)), // 业务 ID, 不是消息 ID
	Value: sarama.ByteEncoder(payload),
}
producer.SendMessage(msg)
// 消费端: 同一 key 落同一分区 -> 分区内 FIFO -> 单消费者串行, 顺序保证
```

## 总结与追问预判
一句话记忆：**「分区内有序是地基，key 哈希路由是手段，内存队列补消费端，全局有序是陷阱」**。重平衡的触发与治理见 147、`148-rebalance-cost.deep`、`1409-avoid-rebalance` [边界]。常追问「热点用户把分区打满怎么办」——答热点 key 加盐（ID+随机后缀拆到几个分区）+ 业务侧用版本号/时间戳裁决最终态；再追问「扩分区时已有 key 会换分区吗」——会，取模基数变了，扩容窗口内靠幂等消费与上游停写窗口兜底。
