## 思路与架构

按「**为什么要有原则 → 九条原则 → 怎么落地**」三层把握：

1. **为什么需要原则（成本先行）**：**使用索引能提高查询速度、降低服务器负载**；但**建立索引会占用物理空间**，**创建和维护索引的代价也会随着数据量的增大而增大**。因此必须回答两个问题——**在哪些字段上建**、**建什么类型的索引**。
2. **九条原则**：
   - **① 命名规范**：**主键索引用 `pk_` + 字段名**（`pk` 表示 primary key）；**唯一索引用 `uk_` + 字段名**（`uk` 表示 unique key）；**普通索引用 `idx_` + 字段名**（`idx` 是 index 的缩写）`[源码]`。
   - **② 只为搜索、排序、分组的列建索引**：建索引的目的是**快速定位指定数据的位置**，所以要选在 **`WHERE` 子句、`GROUP BY` 子句、`ORDER BY` 子句、以及表与表之间的连接运算中使用频繁的字段**上 `[源码]`。
   - **③ 数字类型的字段更适合建索引**：字段类型会影响查询与连接性能——**数字类型只需比较一次，而字符串需要逐个比较每一个字符**；**字符串的处理时间更长、复杂程度更高**；所以**尽可能选择数字类型的字段建索引**，这也是**设计表时常使用自增整型字段作主键的主要原因** `[源码]`。
   - **④ 存储空间较小的字段更适合建索引**：**占用存储空间越小越合适**；例如**存储大量文本信息的 `TEXT` 类型，与存储指定长度字符串的 `CHAR` 类型相比，`CHAR` 更有利于提高检索效率** `[源码]`。
   - **⑤ 重复度较高的字段不适合建索引**：**如果字段中保存的数据重复度较高，即使该字段在查询时被频繁使用，也不适合建索引** `[源码]`。
   - **⑥ 更新频繁的字段不适合建索引**：**数据更新时为保证索引数据准确，还要同时更新索引**；**字段值频繁更新会造成 IO 访问量增加、加大系统资源消耗、加重存储负载、加大数据维护成本** `[源码]`。
   - **⑦ 尽量使用前缀建索引**：**如果索引的字段值很长，最好使用字段的前缀来建索引**；例如 `TEXT` 和 `BLOB` 类型的字段做全文检索会很浪费时间，**只检索字段的前若干个字符可以提高检索速度** `[源码]`。
   - **⑧ 限制索引的数量**：**索引不是越多越好**——**每个索引都要占用磁盘空间**，**修改数据表时也需要对索引进行维护**，**索引越多，表就要花更多时间去维护**；**如果高频查询是一些组合字段，更推荐为这些字段创建联合索引，而不是每个字段单独建索引** `[源码]`。
   - **⑨ 删除不再使用或很少使用的索引**：**表中的数据被大量更新或使用方式改变后，原来的一些索引可能不再需要**，**需要定期找出这些索引并删除，以减少索引对更新操作的影响** `[源码]`。
3. **落地的态度**：**上面的原则是最基本的准则，但不能拘泥于表面上的准则**，**需要根据应用的实际情况分析和判断，从而选择合适的索引方式** `[源码]`。

## 方案取舍

| 关注点 | 倾向 | 理由 |
|---|---|---|
| 字段类型 | 数字 > 字符串 | 一次比较 vs 逐字符比较 |
| 字段长度 | 越短越好 | 页内能放更多索引项，树更矮 |
| 超长文本 | 前缀索引 | 省空间，代价是选择性下降 |
| 区分度 | 越高越好 | 低区分度优化器会放弃索引 |
| 更新频率 | 越低越好 | 每次更新都要同步维护索引 |
| 索引数量 | 越少越好 | 占空间 + 拖慢写 + 增加维护 |
| 组合查询 | 联合索引 > 多个单列 | 一棵树覆盖多场景，省空间 |
| 存量索引 | 定期清理 | 减少无效维护开销 |

取舍要点：**索引的收益是"读加速"，代价是"写变慢 + 占空间 + 维护成本"**。九条原则本质上都是在这两端之间取平衡——**选更短、更区分、更少更新的列**，**用更少的索引覆盖更多的查询**，**并定期清理失效的索引**。

## 答题技巧

1. **开场先讲成本**：先说"索引提速但有空间与维护代价"，九条原则才有说服力。
2. **命名规范要能背出三个前缀**：**`pk_` / `uk_` / `idx_`**——这是最好拿分的细节。
3. **把③和④合成一条讲**：**"更短 + 更简单"**——数字一次比较、短字段页内密度高、树更矮。
4. **⑤⑥要给出因果**：**重复度高 → 优化器放弃索引**；**更新频繁 → 每次都要同步维护索引，IO 与负载上升**。
5. **⑧⑨是运维视角，容易漏**：**联合索引优于多个单列索引**、**定期删除不再使用的索引**——能答出这两条体现工程经验。
6. **止步档位**：能说出五六条原则即达 L4；能讲全九条并给出每条的因果与取舍，即达 L5。

## 细节与核心 API

**九条原则落地（命名规范 + 类型/长度/区分度/更新/数量/清理）**：

```sql
CREATE TABLE u (
  id    BIGINT AUTO_INCREMENT PRIMARY KEY,        -- ③数字/自增整型主键：短 + 顺序插入少页分裂
  name  VARCHAR(50),
  age   INT,
  email VARCHAR(100),
  KEY pk_id (id),                                 -- ①命名：主键 pk_ / 唯一 uk_ / 普通 idx_
  UNIQUE KEY uk_email (email),                    -- ②只为搜索/排序/分组建
  KEY idx_name_age (name(20), age)               -- ⑦长字段前缀索引 name(20)
);
-- ⑤重复度高/⑥更新频繁字段不宜建；⑧组合查询优先联合索引而非多单列；⑨定期清理无用索引
```

**8.0 不可见索引（先观察再删，比直接 DROP 安全）**：

```sql
ALTER TABLE u ALTER INDEX idx_name_age INVISIBLE;  -- 优化器不再选用，但索引仍维护
ALTER TABLE u ALTER INDEX idx_name_age VISIBLE;    -- 确认无影响后再 DROP
-- DROP INDEX idx_name_age ON u;
```

> 边界：前缀索引长度限制见 1228；联合索引结构见 1217；最左前缀见 1219；本卡只讲建索引九原则与取舍。
