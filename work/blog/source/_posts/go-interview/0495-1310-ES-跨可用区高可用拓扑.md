## 一句话总述
跨可用区 HA 有两条路：**方式一**同集群把节点铺到多个 AZ——资源省（3 数据节点即可），但跨机房分片交互有网络开销、且某 AZ 故障副本乱漂会拖垮健康区；**方式二**每个 AZ 独立建集群、各持一份数据——真 HA、任 AZ 故障其他可顶，但资源翻倍（3 AZ 至少 9 数据节点）。配合 `awareness.force.zone.values` 强制"故障区未恢复前不在其他区分配丢失副本"，防集群过载。

## 面试官视角
- 意图：考察"能否按 SLA/成本选拓扑"，是架构权衡题。
- P5 知道多副本；P6 能讲两种拓扑差异；P7 能讲"方式一跨机房数据交互低效、方式二资源翻倍但真容灾"的 trade-off + force 分配防雪崩。
- 红旗：以为跨 AZ 一定用同集群；不知道 force 分配防止副本乱漂拖垮集群。
- 惊艳点：点出"小集群用方式二比方式一更耗资源（9 vs 3 节点），但换来真正多活容灾"。

## 主问答
**Q：** 跨机房/多可用区 ES 怎么布？
**A：**
1. **方式一（同集群跨 AZ）**：把同一集群节点分布到多个 AZ。优点省资源（3 数据节点即可）；缺点节点间数据跨机房交互、网络低效，且单 AZ 故障时丢失副本被重分配到其他区，可能拖垮健康区。
2. **方式二（多集群各 AZ）**：北京/上海/广州各建独立集群、各持全量数据。任一 AZ 故障，其他 AZ 集群继续服务——真 HA；代价是资源翻倍（3 AZ 至少 9 数据节点）。
3. **强制分配**：设 `cluster.routing.allocation.awareness.force.zone.values=["bj","sh","gz"]`，某 AZ 故障时未恢复前**不**把丢失副本分到其他区，给运维抢修窗口，避免健康区被重分配压垮。

```go
// 强制分配：某可用区故障未恢复前，不在其他区分配丢失副本（防集群过载）
func forceAwareness(base string) error {
    body := `{"persistent":{"cluster":{"routing":{"allocation":{
        "awareness":{"force":{"zone":{"values":"bj,sh,gz"}}}}}}}}`
    req, _ := http.NewRequest(http.MethodPut,
        base+"/_cluster/settings", strings.NewReader(body))
    req.Header.Set("Content-Type", "application/json")
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return err
    }
    defer resp.Body.Close()
    // 配合单集群跨 AZ 节点拓扑，避免副本乱漂把健康区也拖垮
    return nil
}
```
