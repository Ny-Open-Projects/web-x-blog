> 原文锚点：第 11~27 段「缓存缓解DB；命中率反直觉(缓存无权限用户)；本地缓存减RPC；不适合缓存:强一致/频繁改；串行改并行(RPC并行省时=最慢一次)；异步化(MQ解耦非核心)」

## 一句话总述
三组高频杠杆：① **缓存命中率要算清**——应缓存"大概率命中"的数据（如 10 亿用户中仅 10 万有权限，缓存"无权限"者反而命中高），并加本地缓存减远程 RPC；强一致、频繁修改的数据不宜缓存。② **串行改并行**——无依赖的多 RPC 并行，总耗时取决于最慢一次。③ **异步化**——发邮件等非核心逻辑丢进消息队列，缩短主请求。

## 面试官视角
- 意图：考察优化手段是否"算过账"，而非套话；并行与异步的区别是否清楚。
- P5 知缓存/并行/异步三招；P6 知命中率反直觉、并行省时=最慢一次、异步解耦非核心；P7 知本地缓存与 Redis 的取舍、异步后一致性/可靠性如何兜底。
- 红旗：以为"缓存越多越好"；或把并行（同请求内并发）与异步（跨请求解耦）混为一谈。
- 惊艳点：用具体数字讲命中率反直觉（10 万 vs 10 亿），并点出本地缓存减少远程调用 `[边界]` 见 193/1254（缓存模式与一致性）、1828（消息队列异步）、1115-api-perf-overview（总览）。

## 主问答
**Q（面试官原话）：** 缓存和并行、异步在 API 优化里怎么用？
**A：**
1. **缓存命中率反直觉**：缓存应服务于高命中数据。例：10 亿用户仅 10 万有某权限，缓存"无权限"的 10 亿侧反而命中率极低；缓存"有权限"的 10 万反而意义小——应缓存被高频访问的那侧。热点数据再加本地缓存，省去 Redis 远程调用。
2. **不适合缓存的两种数据**：一致性要求极高（缓存与 DB 一致性本就是难题）、修改特别频繁（缓存被反复刷新、命中率反而低）。
3. **串行改并行**：处理请求需调多个无依赖 RPC 时并行执行，整体耗时从"各调用之和"降为"最慢一次"。
4. **异步化解耦**：发通知等非核心、且影响主耗时的逻辑，投到消息队列由其他服务消费，主请求不必等它完成。

## 关键代码
```go
package main

import (
	"golang.org/x/sync/errgroup"
	"time"
)

// 多 RPC 并行：无依赖调用并发，整体耗时≈最慢一次
func loadDashboard(uid int64) (string, error) {
	g := new(errgroup.Group)
	var prof, feed string
	g.Go(func() error { prof, _ = getProfile(uid); return nil })
	g.Go(func() error { feed, _ = getFeed(uid); return nil })
	if err := g.Wait(); err != nil {
		return "", err
	}
	return prof + feed, nil
}

// 异步化：非核心逻辑投 MQ，主请求立即返回
func handleOrder(o Order) {
	_ = publish("notify", o.ID) // 由消费端发邮件，不阻塞主链路
	_ = time.Now()
}
```
