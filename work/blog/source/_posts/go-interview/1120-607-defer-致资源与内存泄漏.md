> 分类：错误处理 | 难度：L3 | 题型：工程题 | 频率：中 | 关键词：**循环 defer** / **大对象** / **延迟释放**
> 原文锚点：第 118~130 段「for 循环 defer 关闭资源致全部打开后才释放」

## 一句话总述
defer 在函数返回时才执行：写在 for 循环里会把释放推迟到整个函数结束，造成资源堆积；引用大对象也会拖慢 GC。

## 面试官视角
- 意图：是否知道 defer 的"函数级"语义，以及循环/大对象场景下的副作用。
- 分档：P5 知别循环 defer / P6 说清封装成函数 / P7 知大对象延迟 GC 可显式置 nil。
- 红旗：以为 defer 出作用域就释放；以为循环里 defer 每轮释放。
- 惊艳点：10 万文件循环 defer 会全打开再逐个关，耗尽句柄 `[经验]` 生产事故。

## 主问答
**Q（面试官原话）：** 为什么不建议在 for 循环里用 defer 关资源？
**A：**
1. **结论**：defer 在**函数返回时**才跑，循环里写 defer 等于把释放攒到函数结束。
2. **机制**：循环 10 万次就压 10 万个未释放资源，文件句柄/内存被占满；defer 引用的大对象在 defer 执行前也一直可达，GC 不回收。
3. **边界**：单文件/单资源用 defer 没问题；只有"循环内反复 defer"和"defer 捕获大对象"才是坑。
**加分层：** 循环内把逻辑包成子函数，在子函数里 defer，做到用完即关。

## 关键代码
```go
// 示意，未验证：循环内 defer 应包进子函数
func bad() {
    for i := 0; i < 1e5; i++ {
        f, _ := os.Open(file(i)) // 全打开后才关，危险
        defer f.Close()
    }
}
func good(i int) { // 子函数内 defer，用完即关
    f, _ := os.Open(file(i))
    defer f.Close()
}
```

## 总结与追问预判
- defer 函数级释放；循环 defer 与大对象捕获是两大泄漏源。
