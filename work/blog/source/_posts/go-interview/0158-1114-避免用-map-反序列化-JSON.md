> 原文锚点：第 32~58 段「map 需 interface{} 类型判断+多分配；结构体更快；个别场景 map+RawMessage 按需解析」

## 一句话总述
反序列化优先用**结构体**而非 `map[string]interface{}`：结构体字段类型确定、无需反射类型判断、内存分配少（基准 结构体 7 次 / map 16 次）；仅需个别 key 时可用 `map[string]json.RawMessage` 只解析 key、忽略值、按需再解析。

## 面试官视角
- 意图：是否理解 map 反序列化的隐藏成本。
- 分档：P5 知结构体更快；P6 能讲 interface{} 反射开销；P7 能讲 RawMessage 按需解析与适用边界。
- 红旗：无脑用 map 接 JSON，不知分配与类型判断代价。
- 惊艳点：点出 `json.RawMessage` 本质是字节切片——先拿 key、值延迟解析，避免一次性全解析。

## 主问答
**Q（面试官原话）：** 反序列化 JSON 用 map 还是 struct？
**A：**
1. **结构体更快**：字段类型编译期确定，反序列化直接填充，无类型判断；`map[string]interface{}` 需对每个值做类型识别并向 interface{} 装箱，产生大量临时分配。
2. **基准差异**：同样数据，结构体反序列化约 7 次内存分配，map 约 16 次，且单次分配量更大——结构体明显更省更快。
3. **RawMessage 折中**：若只需个别 key，用 `map[string]json.RawMessage`，只解析 key、值保留为未解析的字节切片，用到某值再单独 Unmarshal，避免无关字段开销。

## 关键代码
```go
// 示意，未验证：结构体优先；个别 key 用 RawMessage 延迟解析
type Req struct { Field1 int `json:"field1"`; Field2 string `json:"field2"` }
var r Req; json.Unmarshal(b, &r) // 结构体：少分配

// 只取 key、值延迟解析
m := map[string]json.RawMessage{}
json.Unmarshal(b, &m)
var f1 int; json.Unmarshal(m["field1"], &f1) // 用到才解析值
```
