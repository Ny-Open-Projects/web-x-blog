> 分类：分布式 / 高并发 | 难度：L4 | 题型：体系化深挖 | 频率：中 | 关键词：**全链路防超卖** / **方案选型** / **边界到 1013/193/196**

## 思路与架构
防超卖全链路架构是"**请求 → 业务层 → DB 层 → 应用层**"四段：
- **请求入口**：限流/验证码拦掉无效流量（本卡不展开，属接入层）。
- **业务层**：消息队列削峰，请求异步化、不直接打 DB。
- **DB 层（核心）**：库存扣减并发控制三选一/组合——悲观锁 / 乐观锁(version CAS) / Redis 分布式锁(SET NX EX + 唯一 value + Lua 释放)。
- **应用层**：批量写（合并订单扣减）+ singleflight 合并读。

## 方案取舍
| 方案 | 正确性 | 并发度 | 部署要求 | 适用 |
|---|---|---|---|---|
| 悲观锁 | 强（串行） | 低 | 单库事务 | 低并发 |
| 乐观锁 | 强（CAS） | 高 | 单库事务 | 中高并发、冲突少 |
| Redis 分布式锁 | 强（持锁） | 中 | 多实例+Redis | 集群部署 |
| MQ 削峰 | 间接 | 提升 | 需 MQ | 流量整形 |

**组合建议**：高并发秒杀 = MQ 削峰 + 乐观锁/Redis 锁兜底 + 应用层批量/singleflight。纯悲观锁在秒杀下吞吐崩。

## 答题技巧
1. **全链路开口**：先画"请求→MQ→DB锁→应用层"，显出架构思维，别只答 DB 锁。
2. **DB 层三方案对比**：悲观/乐观/Redis 锁，各说一句代价（吞吐/重试/部署）。
3. **Redis 锁三件套必答**：NX EX + 唯一 value + Lua 释放，漏任一项扣分。
4. **缺陷不漏**：超时→看门狗、主从→Redlock，体现工程深度。
5. **边界声明**：本卡聚焦**库存扣减并发层**；Go in-process 锁见 1013、锁分类见 1233、秒杀缓存设计见 193、秒杀高可用见 196，均不重产。

## 细节与核心 API

```lua
-- Redis + Lua 原子扣减库存（不可分割，杜绝“查有货→并发抢光→超卖”）
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock < tonumber(ARGV[1]) then return 0 end  -- 不足，失败
redis.call('DECRBY', KEYS[1], ARGV[1])
return 1  -- 扣减成功
```
```go
ok, _ := rdb.Eval(ctx, deductScript, []string{"stock:"+item}, 1).Int64()
if ok == 0 { return ErrSoldOut }              // 前端提示已售罄
// 落库最终一致：扣成功才发 MQ 创建订单；消费者 INCR DB 库存并校验不为负
// 兜底：DB 层加 `stock = stock - 1 WHERE id=? AND stock >= 1`（条件更新，超卖双保险）
// 回滚：订单超时未支付 -> Lua 把库存加回（INCRBY）+ 取消订单
// 要点：Lua 保证“判断+扣减”原子；DB 条件更新兜底；两道防线缺一不可
```
