> 分类：Elasticsearch · 分布式查询 | 难度：L3 | 题型：现象题 | 频率：中 | 关键词：**主副本 refresh 时机**/**查询结果震荡**/**preference**/**分片级缓存命中**
> 原文锚点：第 27~35 段「主副本 refresh 时机不同，主片已可查副本未 refresh，同查询返回不同结果；用 preference 固定分片避免震荡」

## 一句话总述
主分片与副本分片的 **refresh 时机不一定同步**：主片数据已 refresh 可被搜到、副本还没 refresh 时，同一查询打到主片能命中、打到副本却搜不到——**返回结果发生震荡**。解法是用 `preference`（通常用用户 UID 或时间戳）把同一查询**固定路由到同一个分片**，既消除震荡又提升分片级查询缓存命中率。

## 面试官视角
- 考察意图：是否理解 near-real-time 下"主副本不一致是常态"，以及生产如何规避结果抖动。
- 分档：P5 知主副本都可接查询；P6 知 refresh 时机差异导致震荡；P7 知 preference 固定分片 + 缓存命中收益。
- 红旗：以为主副本永远一致、查询永远稳定；或不知 preference 为何物。
- 惊艳点：点出"preference 顺带提升 shard request cache 命中率"——一举两得，不只是为了稳定。

## 主问答
**Q（面试官原话）：** 为什么同一个搜索请求，有时查得到有时查不到？
**A：**
1. **现象根因**：ES 默认把查询负载均衡到主/副本分片；但各分片 **refresh 是各自触发的**，时点不统一。刚写入的数据在主片已 refresh 可见、副本尚未 refresh 时，**同一查询这次命中主片能搜到、下次命中副本就搜不到**，结果震荡。
2. **preference 固定分片**：在查询后加 `preference=用户UID` 之类的值，ES 会用该值做哈希，**每次把请求打到同一个分片**（主或副本之一），结果稳定。
3. **附加收益**：固定分片后，分片级请求缓存（shard request cache）命中率显著提升——既稳又省。

## 关键代码
```go
// 用用户 UID 作 preference，把同一用户的查询固定到同一分片，消除震荡并命中缓存
q := elastic.NewTermQuery("uid", "u123")
_, _ = cli.Search().
    Index("orders").
    Query(q).
    Preference("u123"). // 关键：固定分片
    Do(ctx)
```

## 总结与追问预判
结果震荡是 near-real-time 的固有现象，preference 是标准解法。追问接"routing 对查询性能的影响"与"bulk 写入路由优化"。
