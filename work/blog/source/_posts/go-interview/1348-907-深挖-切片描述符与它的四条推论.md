> 原文锚点：第 1~90 段「slice 源码定义…切片是数组的描述符…快捷方式类比」

## 思路与架构

切片这一节的所有现象，都可以从**一个结构**推出来：运行时里的切片是三字段描述符——指向底层数组的指针、长度、容量。它描述数组，但不拥有数组。

由这一个结构可以推出四条：

**推论一：传参很便宜。** 数组没有间接部分，传参会复制整个数组的值，大数组代价显著；切片传的只是描述符的副本，64 位平台 24 字节，与元素个数无关。这也解释了那组经典实验：函数内外打印数组地址不同，打印切片地址却相同——不是因为切片"引用传递"（Go 只有值传递），而是因为副本里的指针没变，指向的还是同一块内存。

**推论二：截取零拷贝。** 截取生成的是新描述符，不是新数据。从头截取时首地址不变，从中间截取时首地址向后偏移若干个元素大小——原文用逐元素打印地址证明了这一点。截取后的容量从新起点算到原底层数组末尾，这也是"截取后 append 会覆盖别人数据"的根因。

**推论三：描述符独立、内存共享。** 赋值拷贝的是描述符，从此两份描述符各自演进：改一方的长度或容量不会影响另一方。但它们指向的内存是同一块，所以改元素会互相看见。分道扬镳只发生在一个时刻——某方扩容换了底层数组，指针不再相同。

**推论四：改元素与改指向是两回事。** 在函数里给切片参数整体重新赋值，改变的是局部描述符的指针，等于与原切片解除引用关系，外层毫发无损。原文的类比很准：快捷方式原本指向文件 A，重新赋值后指向文件 B，文件 A 只是少了一个引用，内容没变。想要外层也变，只有两条路——传指针，或者把结果返回去。

**设计动机。** 切片之所以这样设计，是为了补数组的两个缺陷：元素个数不可变、传值开销大。切片元素可变，并引入容量属性在追加时预留空间（例如 4 追加后容量变 8），从而减少内存申请次数。

## 方案取舍

| 场景 | 做法 | 理由 |
|---|---|---|
| 大数组入参 | 改传切片或指针 | 避免整块拷贝 |
| 需要独立副本 | 显式复制 | 共享底层会互相影响 |
| 截取后长期持有 | 复制出来再持有 | 否则大数组无法回收 |
| 需要限制容量 | 三索引截取 | 防止越界写入影响他人 |
| 函数内要影响外层 | 传指针或返回 | 重新赋值只改局部描述符 |

取舍要点：

- **"引用传递"是个坏词。** Go 只有值传递，切片传的是描述符副本；用错词汇会让人误以为语义特殊。
- **共享是内存层面的，独立是描述符层面的。** 所有"改了没改"的问题，都可以用这条分界一刀切开。
- **零拷贝不总是好事。** 截取不拷贝意味着底层大数组会一直被小切片钉住，长生命周期场景要显式复制。
- **容量是性能设计，不是容量保证。** 它的存在是为了减少内存申请次数，不代表可以无脑追加。

## 答题技巧

1. **从结构推出结论，不要背结论。** 先画三字段描述符，再推传参、截取、赋值三种行为，逻辑链最稳。
2. **主动纠正"引用传递"。** 说"Go 只有值传递，切片传的是描述符副本"，一句话就能拉开差距 `[经验]`。
3. **用那组地址实验说话。** 数组内外地址不同、切片相同、中间截取偏移一个元素大小，报出这三个数字很有说服力 `[源码]`。
4. **把改元素与改指向并列。** 两者结果相反，能并列讲清说明真懂了 `[经验]`。
5. **提一句回收陷阱。** 小切片长期持有导致大数组无法释放，是工程经验的自然延伸，很适合做加分收尾。

## 细节与核心 API

```go
// 推论 1：reslice 共享底层数组，修改互相可见
a := []int{1, 2, 3, 4}
b := a[1:3]            // b=[2,3]，指向 a 的底层数组
b[0] = 99             // a 也变成 [1,99,3,4]
// 推论 2：cap 从当前位置算到原数组末尾
fmt.Println(cap(b))   // 3（从索引1到末尾4）
// 推论 3：append 超出 cap 会分配新数组，之后与原数组解耦
b = append(b, 5, 6)   // 超出 cap，可能搬移；a 不再受影响
// 推论 4：函数传 slice 拷贝描述符，仍共享底层数组（除非 append 触发扩容）
func f(s []int) { s[0] = -1 } // 影响调用方
```
