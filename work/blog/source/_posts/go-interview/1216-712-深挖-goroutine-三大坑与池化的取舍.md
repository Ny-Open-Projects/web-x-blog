## 思路与架构

这一节的三个坑，表面是三种写法，根子是**同一条主线**：goroutine 把"读值"推迟到了"执行"，而循环体在这段时间里从没停止改写数据。

**第一层：估值时机。** `go f(i)` 的参数在 go 语句执行那一刻就求值完毕；`go func(){ f(i) }()` 的函数体要等调度器把它排上 CPU 才读 i。前者拿到的是当时的快照，后者拿到的是执行瞬间的现场。Go 1.22 把循环变量改成每轮独立后，后者也能拿到正确的值——但前提是 go.mod 声明了对应语言版本，这点常被忽略。

**第二层：共享内存。** 复制变量能救循环变量，救不了指针。把一个结构体指针交给 goroutine，主协程还在同一块内存上反复赋值，这是典型的一写多读无同步，属于数据竞争而非"时序不巧"。判断标准很简单：**有没有两个 goroutine 同时访问同一地址、且至少一个是写**。race detector 就是按这个判据工作的。

**第三层：数量失控。** 前两层是正确性问题，这一层是资源问题。goroutine 再轻量也有栈与调度成本，批量任务无节制地起，耗尽的是文件句柄与内存。池化的价值就在这里：给并发度设上限、复用 worker、把峰值削平。

**观测与同步的分界。** 很多人顺手用 `runtime.NumGoroutine()` 或池的运行计数做"跑完没有"的判断。这是把观测指标当同步原语用：数值回落可能是别的组件收尾导致的，语义上并不等价于"我提交的任务已完成"。观测归监控看板，同步归等待组，两者各司其职。

## 方案取舍

| 场景 | 常见写法 | 问题 | 推荐 |
|---|---|---|---|
| 循环里起 goroutine | 闭包直接引用 i | 读到末值 | 复制变量 / 传参 / 1.22 语义 |
| 传结构体给 goroutine | 复用同一指针 | 数据竞争 | 每轮新对象或值拷贝 |
| 批量异步任务 | 无脑 go 关键字 | 资源耗尽 | 协程池限并发 |
| 判断任务结束 | 轮询计数 + sleep | 忙等、语义不可靠 | 等待组 / 池等待能力 |
| 线上观测 | 本地打印 | 无人看、无告警 | 上报监控 + 阈值告警 |

取舍要点：

- **正确性优先于性能。** 池化解决的是资源问题，它不会自动修复闭包捕获与数据竞争；顺序应是先写对，再调优。
- **别过度防御。** 同步执行完的闭包不需要复制变量，无脑 `i := i` 只会制造噪音。判据是"闭包会不会活过当前轮"。
- **池不是越大约好。** size 的意义是并发度上限，它取决于下游资源承载力（句柄、连接数、CPU），通常不是机器核数。
- **释放时机跟着生命周期走。** 演示代码里 `defer Release()` 是对的，但常驻服务的池应当跟进程生命周期一致，函数级释放反而会造成反复建池。

## 答题技巧

1. **按"估值时机—共享内存—资源上限"三层答。** 有层次的回答比罗列要点更能体现体系感。
2. **主动报出 Go 版本边界。** 说到循环变量陷阱时补一句"Go 1.22 起每轮独立、需 go.mod 声明"，这一句就能和只背结论的人拉开差距 `[经验]`。
3. **把"时序问题"纠正成"数据竞争"。** 用词准确是 P7 的直接信号，顺带提 `-race` 能在 CI 拦住 `[源码]`。
4. **池化题要谈释放与满池行为。** 只会 `Submit` 是使用经验，讲得出 Release 时机与池满策略才是工程经验 `[经验]`。
5. **分界要讲死。** "NumGoroutine 用于观测、等待组用于同步"这句话背下来，几乎能接住所有追问。

## 细节与核心 API

```go
// 坑1 泄漏：goroutine 永久阻塞（无退出条件）
done := make(chan struct{})
go func() { <-done }() // 若无人 close(done) 则泄漏
// 修复：用 context 取消
ctx, cancel := context.WithCancel(context.Background())
go func(ctx context.Context) { for { select { case <-ctx.Done(): return; default: work() } } }(ctx)
// 坑2 panic：goroutine 内 panic 不被外层 recover 捕获，会崩进程
go func() { defer func() { _ = recover() }(); mayPanic() }()
// 坑3 竞态：共享变量未同步
var mu sync.Mutex
go func() { mu.Lock(); counter++; mu.Unlock() }()
// 池化取舍：短任务用 worker pool 复用 G 省创建成本；长任务/阻塞型不宜池化
```
