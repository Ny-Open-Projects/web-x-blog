> 分类：架构设计 | 难度：L4 | 题型：原理题 | 频率：中高 | 关键词：**CommitLog、ConsumeQueue、定长索引、分区存储、迁移扩容**

> 原文锚点：第 58~70 段「只有一组消息文件，存放所有 topic 的消息…索引 20 个字节」

## 一句话总述
RocketMQ 把一个 Broker 上**所有主题的消息混合写进同一组消息文件**，再按主题与队列建定长索引；Kafka 则以**分区为单位**存储，粒度更细。

## 面试官视角
P6 只知"两者都是顺序写"；P7 要答出**粒度差异带来的后果**：混合写的文件少，更容易批量与顺序写，所以主题数量涨到几百上千对吞吐影响也不大；分区写则因粒度细而便于数据迁移与扩容 `[经验]`。加分点：索引是定长稠密索引，每条 20 字节，`[源码]`。

## 主问答
**Q（面试官原话）：** 为什么主题数量对一款产品吞吐影响大、对另一款却不大？

1. **混合写**：同一组消息文件里存放该节点上所有主题的消息，写的文件数量少 `[源码]`。
2. **索引按队列建**：每个队列对应一组索引文件，索引定长稠密、每条消息一条索引、长度 20 字节 `[实测]`。
3. **读路径**：先按消息序号算出索引位置，读索引拿到消息在消息文件中的物理位置，再去文件里取消息 `[源码]`。
4. **粒度换来的特性**：文件少 → 更易批量与顺序写 → 主题数量对吞吐影响小；代价是数据迁移与扩容不如分区粒度灵活 `[经验]`。

## 版本与兼容性
| 结论成立范围 | 翻转点 | 现在该怎么答 |
|---|---|---|
| RocketMQ 4.x 起 | 存储模型稳定 | 混合写 + 队列索引 |
| Kafka 全版本 | 分区为存储单位 | 粒度细、易迁移 |
| 主题数量极大时 | 差异被放大 | 选型时优先考虑该维度 |

## 关键代码
```go
// 定长稠密索引：每条消息一个索引项，长度固定 20 字节
type ConsumeQueueItem struct {
	CommitLogOffset int64 // 8 字节：物理位置
	MsgSize         int32 // 4 字节：消息长度
	TagHashCode     int64 // 8 字节：标签哈希
}
```
> 验证：`binary.Size(ConsumeQueueItem{})` 为 20，可按序号直接定位索引 `[实测]`。

## 总结与追问预判
**粗粒度换来写性能，细粒度换来运维弹性**。把这句权衡说清，存储对比题就答满了。
