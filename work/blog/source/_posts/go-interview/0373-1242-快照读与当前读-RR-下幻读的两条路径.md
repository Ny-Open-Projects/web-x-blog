> 分类：MySQL 事务 | 难度：L3 | 题型：机制题 | 频率：高 | 关键词：**快照读**/**当前读**/**ReadView**/**FOR UPDATE**/**FOR SHARE**/**间隙锁**

> 原文锚点：第 8~22 段「快照读如何避免幻读 / 哪些属于当前读」

## 一句话总述
RR 下普通 SELECT 是**快照读**（基于事务开启时的 ReadView，沿 undo log 版本链读到启动时刻的数据），能避开别事务新增/删除的行；而**当前读**（加锁读、写操作、串行化下的普通读）读的是最新已提交数据，**仍可能看到别事务插入的行**，从而发生幻读。锁语法：MySQL 8.0 用 `SELECT ... FOR SHARE`，旧版用 `FOR SHARE MODE`，`FOR UPDATE` 通用。

## 面试官视角
这题是幻读机制的「分水岭」。能分清快照读/当前读，并说清「快照读靠版本链、当前读靠锁」，再补一句「当前读在 RR 下仍可能幻读」的，已经超出背定义的水平。锁语法版本差异（FOR SHARE vs FOR SHARE MODE）是加分细节。

## 主问答
**Q（面试官原话）：** RR 下快照读和当前读分别怎么影响幻读？

1. **快照读靠 ReadView 隔离**：RR 下第一条查询建立事务级快照，后续普通 SELECT 都沿 undo log 版本链回到该快照，别事务提交的新增/删除对本事务不可见——这是 RR「大部分避免幻读」的根因。
2. **当前读读最新数据**：`SELECT ... FOR UPDATE` / `SELECT ... FOR SHARE`、所有 INSERT/UPDATE/DELETE、以及串行化下的普通读，都按最新已提交数据操作，会**看到别事务已提交的插入行**，因此仍可能发生幻读。
3. **锁语法有版本差异**：加读锁的共享当前读，MySQL 8.0 及以后用 `SELECT ... FOR SHARE`，8.0 以下用 `SELECT ... LOCK IN SHARE MODE`；`FOR UPDATE` 各版本通用。
4. **串行化强制当前读**：串行化级别下普通 SELECT 也会加共享读锁，退化为当前读，从根本上杜绝幻读但并发度骤降。
5. **结论**：快照读「很大程度上」避免幻读而非「完全」避免；彻底挡住插入型幻读要靠当前读下的**间隙锁 / Next-Key 锁**（锁住间隙阻止插入）。

## 版本与兼容性
| 语法 | 适用版本 | 读类型 |
|------|----------|--------|
| `SELECT ... FOR UPDATE` | 全版本 | 当前读（排他锁） |
| `SELECT ... FOR SHARE` | MySQL 8.0+ | 当前读（共享锁） |
| `SELECT ... LOCK IN SHARE MODE` | 8.0 以下 | 当前读（共享锁，旧写法） |
| 串行化下普通 SELECT | 全版本 | 自动当前读（共享锁） |

## 关键代码
```sql
-- 快照读：RR 下普通 SELECT，看不到别事务新插入的行
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM t WHERE id = 12;   -- 空（快照建立时本就无此行）

-- 会话 B 插入 id=12 并提交
INSERT INTO t(id) VALUES (12); COMMIT;

SELECT * FROM t WHERE id = 12;   -- 仍为空（快照读，B 的插入不可见）

-- 当前读：加锁读会看到 B 已提交的行 → 出现幻读
SELECT * FROM t WHERE id = 12 FOR UPDATE;  -- 查出 B 插入的 id=12（幻读）
```

## 总结与追问预判
核心：**快照读沿版本链隔离、当前读读最新；RR 下当前读仍可能幻读，靠间隙锁兜底**。追问常拐向「间隙锁怎么挡插入」——备好「Next-Key 锁 = 记录锁 + 间隙锁，锁住间隙阻止插入」（见锁专题卡）。
