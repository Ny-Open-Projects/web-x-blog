> 原文锚点：第 1~16 段「.bash_profile 登录时读…bash 子 shell 读 .bashrc…etc 全局与家目录用户级…顺序…echo $0 验证」

## 一句话总述
用户环境脚本分**两条链**：**profile 链**（登录 shell 触发：/etc/profile → /etc/profile.d/*.sh → ~/.bash_profile）与 **bashrc 链**（子 shell/交互非登录触发：/etc/bashrc → ~/.bashrc）；另有 /etc/environment 最先加载全局环境。**同名变量后执行的覆盖先执行的**。发行版差异：RHEL/CentOS 用户级用 `~/.bash_profile`，Debian/Ubuntu 用 `~/.profile`。

## 面试官视角
- 意图：Linux 日常题——环境变量「配了不生效/重复生效」的排查能力，靠的就是两链模型。
- 分档：P5 报出主要文件；P6 说清登录 shell 与子 shell 触发差异、覆盖顺序；P7 能讲「.bash_profile 里统一 source .bashrc」惯例的由来与验证手段。
- 红旗答案：以为 .bashrc 每次登录都读（登录 shell 默认不读它）；说不清 profile 与 bashrc 分工。
- 惊艳点：给出 `echo $0` 埋点验证法——每个脚本末行加 `echo $0`，登录/切换 shell 观察输出顺序 [经验]。

## 主问答
**Q（面试官原话）：** Linux 用户环境配置脚本的执行顺序是怎样的？

**A：**
1. **两条链的分工**：登录系统 → **profile 链**（/etc/profile 全局 → ~/.bash_profile 用户级，登录时执行）；在 shell 里再开一个 bash（子 shell）→ **bashrc 链**（/etc/bashrc 全局 → ~/.bashrc 用户级）。机制目的是**分离登录环境与子 shell 环境**。
2. **惯例**：通常在 `~/.bash_profile` 里 source `~/.bashrc`，统一配置入口——否则交互子 shell 里 alias/函数不生效。
3. **完整顺序**：/etc/environment → /etc/profile → /etc/bashrc → /etc/profile.d/*.sh → ~/.bash_profile（或 ~/.profile）→ ~/.bashrc。
4. **覆盖规则**：同名环境变量在多个脚本中配置时，**后执行者覆盖先执行者**——排「配了不生效」时先查最后加载的文件。
5. **验证法**：每个脚本末行加 `echo $0`（输出当前脚本路径与文件名），登录一次、su 切换一次，按打印顺序即得真实链条。

## 关键代码
[实测] 两链分离（fake HOME，不污染真实环境）：`HOME=/tmp/fakehome` 下放 `.bash_profile`（echo 标记 A）与 `.bashrc`（echo 标记 B）——`env -i HOME=/tmp/fakehome bash --login -c true` 输出**仅 A**（登录 shell 走 profile 链）；`env -i HOME=/tmp/fakehome bash -i -c true` 输出**仅 B**（交互非登录走 bashrc 链）。登录与子 shell 各读各的链、互不串；`.bash_profile` 里不 source `.bashrc` 时，子 shell 中 alias 失效即由此而来。

```python
# 覆盖规则模拟器：按真实加载顺序应用同名变量，后者覆盖前者
order = ["/etc/environment", "/etc/profile", "/etc/bashrc",
         "/etc/profile.d/demo.sh", "~/.bash_profile", "~/.bashrc"]
defs = {
    "/etc/environment":       {"JAVA_HOME": "/usr/lib/jvm-11"},
    "/etc/profile":           {"JAVA_HOME": "/usr/lib/jvm-17"},
    "/etc/profile.d/demo.sh": {"MAVEN_OPTS": "-Xmx512m"},
    "~/.bash_profile":        {"JAVA_HOME": "~/sdk/21"},
}
env = {}
for f in order:                      # 按顺序加载
    for k, v in defs.get(f, {}).items():
        env[k] = (v, f)              # 后写覆盖先写
for k, (v, src) in sorted(env.items()):
    print(f"{k}={v}   # 生效于 {src}")
```

[实测] 输出：`JAVA_HOME=~/sdk/21  # 生效于 ~/.bash_profile`、`MAVEN_OPTS=-Xmx512m  # 生效于 /etc/profile.d/demo.sh`——etc 层两次定义的 JAVA_HOME 均被后加载的用户级覆盖，即「配了不生效先查最后加载的文件」。

## 总结与追问预判
核心：**两链模型（登录=profile 链、子 shell=bashrc 链）+ 覆盖规则（后者赢）+ echo $0 埋点验证**三件套。追问接实战：环境变量配错导致服务异常的排查见 410 与 `410-os-args-path`、crontab 不生效的经典成因（cron 环境不读 profile 链）见 1816、sudo 环境差异见 1817。

## ⚠️ 原文纠错
1. 术语核校： [经验] 原文将 bash_profile/bashrc/profile 音转为多个崩坏串（败写点写barc 等）、`echo $0` 音转为「口多乐零」、Linux/Debian 亦有音转，本卡统一为规范术语，不列举原词。
2. 事实核校： [经验] 原文「.bash_profile 是在 bash 子 shell 调用另一个 bash 时读取」张冠李戴——子 shell 触发读的是 **.bashrc 链**；.bash_profile 是**登录 shell** 读取 [实测]。
3. 补充核校： [经验] 顺序清单中 /etc/environment 由 pam/env 模块在会话建立时加载，严格说早于任何 shell 脚本执行，与脚本链分层。
