## 思路与架构

```text
淘汰度量演进
├─ 传统 LRU(链表): 命中→移到头 / 满→淘汰尾
│     成本: 所有 key 一个 node(额外空间) + 每次命中一次移动(额外操作)
├─ 近似 LRU(Redis): 对象内 24bits 存"最后访问时间" + 随机采样 N 个取最久
│     省掉空间与移动, 代价=精度损失 + 批量读刷新导致缓存污染
└─ LFU(Redis 4.0+): 同一 24bits 拆 16bits(分钟级时间) + 8bits(计数,初值5)
      每次访问: 先按时间差衰减 → 再按概率增长(当前值越大概率越低)
      目的: 挤出"曾经热、如今冷"的 key, 抵挡缓存污染
```

## 方案取舍
- **为什么 Redis 宁要精度换成本**：Redis 的核心竞争力是**单线程下的极致吞吐与可预测延迟**，任何引入到每个 key 上的额外内存或每次命中上的额外写操作都会被放大成全局性能问题。链表方案的问题是**每个 key 都要多一个节点指针、每次读都要一次移动**；改成"对象内字段 + 淘汰时临时采样"，把**常态成本降为零**，只在真正需要淘汰时才付代价。这是典型的"**把成本从热路径挪到冷路径**" [经验]。
- **为什么 LFU 一定要衰减**：如果只记纯访问次数，一个上线初期被狂刷、之后再无人问津的 key，计数会永远压在最高位，谁也挤不走它——这就从"缓存污染"变成了"**缓存固化**"。加入**按距上次访问时长的衰减**之后，频次具备时间局部性：**最近还在被访问的才维持高值，停下来就自然冷却**。所以准确的说法是 Redis 用的是"**带衰减的访问频率**"，而不是简单的访问次数 [经验]。
- **为什么增长要用概率而不是加一**：计数器只有 **8 位（0~255）**，如果直接累加，一个热点 key 几百万次访问会瞬间打满到 255，之后所有热点都变成同一个值，**区分度彻底消失**。用概率增长（当前值越大，增长率越低）相当于做了**对数压缩**——越往上越难涨，于是 8 位空间能被拉开成一条长尾，足以区分"很热"和"极热" [经验]。
- **采样数怎么调**：`maxmemory-samples` 越大、越接近真实 LRU，命中率越好，但每次淘汰要比较的候选越多、**CPU 开销越大**。默认 5 是"够准又够快"的折中。调完之后**必须用 `evicted_keys` 与命中率验收**，而不是凭感觉调完就走 [经验]。
- **本地缓存 vs 分布式缓存的取舍不同**：在你自己进程内（如 Go 里手写的 map + list），链表移动只是几条指针赋值，空间也不是稀缺资源——所以**本地缓存用严格 LRU 完全合理**。真正的差别在于 Redis 面对的是**千万级 key 与极致延迟要求**，才必须做近似。**面试时把这条说出来，证明你理解的是"约束决定方案"，而不是背 Redis 的实现细节** [经验]。

## 答题技巧
- 先给全称再说度量维度：**LRU 看时间、LFU 看次数**，一句话把地基打稳 [经验]。
- 讲 Redis 为什么不用原生链表时，**两个成本都要给**（额外空间 + 移动开销），只给一个是常见的失分点 [经验]。
- 主动纠正"24 字节 vs 24 位"——这是极其常见的口误，纠正它是廉价的高分点 [经验]。
- 被问「LFU 就只是记次数吗」→ 立刻答**不是**，要讲**先衰减后按概率增长**，`lfu-decay-time` 越大衰减越慢、`lfu-log-factor` 越大增长越慢 [经验]。
- 收尾给选材建议：**访问模式稳定且局部性强 → LRU；存在偶发批量扫描、容易造成污染 → LFU**，并补一句"LFU 需 Redis 4.0+" [经验]。
- 主动边界到本库 MySQL 缓冲池相关卡片（InnoDB LRU 变体与中点插入策略），构成本地—分布式缓存对照 [边界]。

## 细节与核心 API

**Redis 对象内 24 bits 字段布局（LRU 与 LFU 共用同一空间）：**

```go
// 近似 LRU：24 bits 存「最后访问时间戳」，淘汰时随机采样 N 个取最久未访问
// LFU(4.0+)：同一 24 bits 拆 16 bits(分钟级时间) + 8 bits(计数, 初值 5)
type redisObject struct {
    lru uint32 // 实际只用 24 bit：LRU 模式存时间戳；LFU 模式存 (time16 | counter8)
}
// 每次访问(LFU)：先按时间差衰减 → 再按概率增长（当前值越大概率越低，对数压缩 0~255）
```

**本地缓存用严格 LRU 完全合理（Go 进程内，移动只是指针赋值）：**

```go
type LRU struct {
    ll *list.List
    m  map[string]*list.Element
}
func (c *LRU) Get(k string) (any, bool) {
    if e, ok := c.m[k]; ok {
        c.ll.MoveToFront(e) // 命中移到头；本地场景成本低，与 Redis 约束不同
        return e.Value, true
    }
    return nil, false
}
```

**LFU 调优三项：**

```conf
maxmemory-samples 5   # 采样数：越大越接近真实 LRU/LFU，CPU 越高
lfu-log-factor 10     # 增长概率对数因子，越大增长越慢（8 位计数器区分度拉长）
lfu-decay-time 1      # 衰减分钟数，越大衰减越慢；停访问的 key 自然冷却
```
