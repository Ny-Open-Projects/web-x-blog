> 分类：MySQL 锁 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**MDL**/**元数据锁**/**Waiting for table metadata lock**
> 原文锚点：第 80~91 段「元数据锁 MDL」

## 一句话总述
MDL 是 server 层**自动加**的表级锁，保证读写期间表结构不被并发 DDL 改掉；增删改查加读锁、DDL 加写锁。

## 面试官视角
- 考察意图：高频——"为什么一条慢查询能卡死整个表""DDL 为什么等很久"。
- 分档：P5 知 MDL 自动加；P6 知增删改查加读锁、DDL 加写锁；P7 知 5.5 引入与雪崩坑。
- 红旗答案：以为 DDL 不会因查询被阻塞。
- 惊艳点：点出 MDL 等待雪崩——长事务持读锁挡 DDL，DDL 挡后续读。

## 主问答
**Q（面试官原话）：** 为什么对一张热点表执行 ALTER 会卡很久？
**A：**
1. **自动加、无需显式**：访问表时自动加 MDL；增删改查 → MDL **读锁（共享）**，变更表结构（ALTER/DROP）→ MDL **写锁（排他）**。
2. **引入版本**：MySQL **5.5** 引入，解决"查询遍历中表结构被改导致结果错乱"。
3. **互斥规则**：读-读不互斥（可并发查），读-写、写-写互斥——保证改结构时安全。
4. **经典坑（雪崩）**：长事务/慢查询持 MDL 读锁 → 后续 DDL 等写锁被阻塞 → 再后续普通查询等读锁也被阻塞，**全表堆积 Waiting for table metadata lock**；排查看 `performance_schema.metadata_locks`。

```sql

```

## 总结与追问预判
MDL 自动保护表结构一致性；读共享、写排他；长事务持读锁会挡 DDL 进而引发 MDL 等待雪崩，是线上常见故障源。

## ⚠️ 原文纠错
1. 事实核校： [经验]MDL 自动加、增删改查→读锁、DDL→写锁、5.5 引入、读读不互斥读写互斥，正确。
2. **补正**：原文"变更表结构时将 MDL 解锁"为口播错误，应为"加 MDL **写锁**"（解锁=释放，语义相反）。
3. 崩坏词归一：原数据组/MATDAAA/MADAAAOS/mcdataloks→元数据锁 MDL、innerDB/英LDB→InnoDB、事物→事务、解组→锁、场锁→行锁、原数据表→metadata_locks 表。
