## 思路与架构

把"本地联调私有包"的三条路摆在同一张表里看：

```text
方案           改动位置          是否污染 go.mod   是否需要远端   适合场景
──────────────────────────────────────────────────────────────────────
replace        改 go.mod         是（高风险）       不需要        临时验证单个包
推送远端        改 go.mod(require) 否               需要          已定版、要共享
go.work        新增独立文件      否                不需要        多模块并行开发  ← 推荐
```

三条推导链：

1. **为什么 `replace` 是高风险动作**：它写在 **`go.mod`** 里，而 `go.mod` 是**要入库的**。一旦忘记删除就提交，CI 上会去找一个别人机器上才存在的本地路径，直接构建失败。**风险来自"联调产物混进了交付物"**。
2. **为什么 `go.work` 能绕开这个风险**：它是**独立文件**、**位于所有模块的共同父目录**、**默认不入库**。构建时 Go 通过 `GOWORK` 环境变量发现它，把 `use` 列表里的模块当作**根模块**——**优先级高于 `go.mod` 中的 require**，但**不修改 `go.mod` 一个字**。
3. **为什么还需要 `go work sync`**：工作区解析出的是一个**跨模块的统一构建列表**，与各模块自己 `go.mod` 里记录的可能不一致。`sync` 把这统一结果**回写**到各模块的 `go.mod`，让**单模块脱离工作区也能复现同一版本**。这是"联调完要交付"时最关键的一步。

## 方案取舍

```text
什么时候该用哪个？
─────────────────────────────
只要改一个私有库、且改动一次性
    └─ replace 最快，但**提交前必须 diff go.mod**

私有库已稳定、需要团队共享
    └─ 打 tag 推远端，老老实实 require

同时改 2 个以上模块（典型：公共库 + N 个下游服务）
    └─ go.work 唯一正解，replace 会变成 N 份重复配置

要验证"去掉工作区后还能不能构建"
    └─ GOWORK=off 跑一遍 build / test，这是发布前自检动作
```

- **`go.work` 的代价**：① 每个人本地目录布局不同，`go.work` **天然不可共享**；② IDE 与 LSP 需要识别工作区，老工具链（< 1.18）完全不认；③ **CI 里没有 `go.work`**，所以**"工作区能过、CI 挂了"**是常见故障——根因是忘了 `go work sync` 或忘了推某个模块的新版本。
- **`replace` 的代价**：除了误提交，还有**"多模块组合爆炸"**——N 个下游服务都要写同一条 replace，改一次路径要动 N 处。
- **推送远端的代价**：**反馈周期长**（改一行要 commit + push + `go get`），且**污染提交历史**（为调试产生一堆无意义 commit）。
- **共同前提**：三者都**绕不开 `GOPRIVATE` / `GONOPROXY`**——只要模块路径不在公开代理白名单内，就仍需配置私有仓库变量（见 407）。**工作区模式解决的是"路径解析"，不是"鉴权与代理"**。

## 答题技巧

- **开口先摆三条路**，再说推荐。直接抛"用 go.work"会让面试官觉得你只会一条命令；摆出对比表再选，才像做过决策。
- **一定要点出"污染 `go.mod`"这个关键词**——这是 replace 与 go.work 的**根本分野**，也是面试官最想听的那句。
- **把 `go work sync` 讲成"交付前动作"**：它的价值在于**让工作区的构建结果可复现**，是联调与发布之间的桥梁。只说"同步依赖"太浅。
- **主动交代 `GOWORK=off`**：这是**发布前自检**手段，也是证明"工作区确实在生效"的最干净反证（实测：关掉后立刻报 `no required module provides package`）。
- **别踩的坑**：不要说"go.work 提交到仓库大家一起用"。**工作区文件是本地的、个人的**，团队共享的正解是**推 tag + require**。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Go 1.18 起 | 工作区模式引入 | 之前只能用 replace |
| 实测 go1.26.5 | `go work init` 写 `go 1.26.5` | `go` 指令随工具链 [实测] |
| 全版本（1.18+） | 子命令仅 init / sync / edit | 别臆造 [实测] |
| `GOWORK=off` | 完全忽略工作区 | 发布前自检手段 [实测] |
| 老工具链 < 1.18 | 不识别 `go.work` | 会直接忽略，退化为 require |
| CI 环境 | 通常**无** `go.work` | 必须先 `go work sync` 再交付 |

## 细节与核心 API

```bash
# 路1：go run 直接跑（最快，无构建产物）
go run ./cmd/server
# 路2：delve 调试（断点/变量/单步）
dlv debug ./cmd/server -- -port 8080      # 或 dlv test / dlv attach <pid>
# 路3：热重载（改码自动重启，开发体验好）
air -c .air.toml                          # air 监听变更重建；或 fresh/gin
# 远程/容器联调：
#  - 端口转发 kubectl port-forward svc 8080:8080
#  - 远程 delve：dlv --listen=:2345 --headless exec ./bin（IDE 远程 attach）
# mock 依赖：接口注入假实现（见策略注入卡），或 go test 用 httptest 起本地服务
# 注意：联调前确保 GOPROXY 可拉私有依赖；IDE 调试以 dlv 为准，别用 print 大法
```
