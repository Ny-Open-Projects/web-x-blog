> 分类：缓存 / Redis | 难度：L4 | 题型：方案题 | 频率：高 | 关键词：**延迟双删、休眠、经验值、最终一致、尽力保证**

> 原文锚点：第 48~53 段「既然出问题的原因是先删缓存之后依然可能读到旧值，那我们在这里就可以执行多次删除…我们在更新数据库之前去删一次缓存，然后更新完数据库之后再休眠一段时间再去删除一次缓存…这里面的休眠时间是没办法确定的，只能给个经验值…这种方案只能在最大程度上去保证一致性…这种方案我们称之为延迟双删」

## 一句话总述
延迟双删就是在**更新数据库前删一次缓存、更新后休眠一小段再删一次**，用第二次删除清掉并发读请求写回的旧值；但它**只能最大程度保证一致性**，因为休眠时长无法精确确定。

## 面试官视角
P6 会说「双删能解决一致性」；P7 必须讲清**它解决的具体是什么**（清掉被并发读回写的脏值）、**为什么只是尽力而为**（休眠时长是经验值，无法证明覆盖所有并发窗口），以及它对吞吐的副作用。

## 主问答
**Q（面试官原话）：** 延迟双删能彻底解决一致性问题吗？

1. **要解决的问题**：出问题的原因是**先删缓存之后依然可能读到旧值**并被写回缓存 `[源码]`。
2. **做法一**：**更新数据库之前先删一次缓存** `[源码]`。
3. **做法二**：**更新完数据库之后休眠一段时间，再删除一次缓存** `[源码]`。
4. **作用机理**：第二次删除用于**清掉并发读请求在窗口期内写回的旧值** `[经验]`。
5. **效果有限**：这种方式**只能最大程度减少不一致**，不能彻底消除 `[源码]`。
6. **根本原因**：**休眠时间没办法确定，只能给一个经验值** `[源码]`。
7. **名称**：先删缓存 → 更新数据库 → 再删缓存，这一方案称为**延迟双删** `[源码]`。
8. **副作用**：休眠会拉长请求耗时，高吞吐场景需权衡 `[经验]`。

## 关键代码
```go
// 延迟双删：更新前删一次，更新后休眠再删一次
func delayedDoubleDelete(id int64, age int) error {
	// 1) 第一次删除：更新数据库之前
	_ = rdb.Del(ctx, cacheKey(id)).Err()

	// 2) 更新数据库
	if err := db.Exec("UPDATE user SET age=? WHERE id=?", age, id).Error; err != nil {
		return err
	}

	// 3) 休眠一段时间后第二次删除（时长为经验值，无法精确确定）
	time.Sleep(500 * time.Millisecond)
	return rdb.Del(ctx, cacheKey(id)).Err()
}

// 生产优化：把第二次删除异步化，避免 sleep 阻塞主流程
func delayedDoubleDeleteAsync(id int64, age int) error {
	_ = rdb.Del(ctx, cacheKey(id)).Err()
	if err := db.Exec("UPDATE user SET age=? WHERE id=?", age, id).Error; err != nil {
		return err
	}
	go func() {
		time.Sleep(500 * time.Millisecond)
		_ = rdb.Del(context.Background(), cacheKey(id)).Err()
	}()
	return nil
}
```

## 总结与追问预判
**双删的价值是「把不一致窗口压到很小」，不是「消灭不一致」**——答题时务必说清这点，否则会被追问到答不上来。真正兜底的是**删除失败补偿**与**缓存过期时间**，见同批 1261-delete-retry-binlog。

1. 事实核校：出问题源于删后仍读到旧值、更新前后各删一次、休眠时长为经验值、只能在最大程度保证一致性、命名为延迟双删——均准确 `[经验]`。
2. 补充：原文未展开的实用做法是**把第二次删除异步化**（或投递到延时消息队列），避免 `sleep` 阻塞主流程拖慢接口；答题时补上这条更贴近生产 `[经验]`。
