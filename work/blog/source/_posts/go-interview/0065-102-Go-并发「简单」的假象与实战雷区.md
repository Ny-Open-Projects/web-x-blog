# 102 Go 并发"简单"的假象与实战雷区

> 分类：Go 并发模型 | 难度：中 | 题型：认知题 | 频率：高 | 关键词：**go 关键字、资源耗尽、死锁、并发 bug 难定位、脏数据**

> 原文锚点：第 16~24,30~49 段「go 一行启动≠写好；需考虑协程数/上下文切换/死锁/资源/选型；并发 bug 需并发量触发、脏数据」

## 一句话总述
`go` 关键字一行启动协程、屏蔽调度底层，让"写并发"很容易，但"写好并发"很难：要兼顾**协程数控制（资源耗尽）/上下文切换/死锁/软硬件资源/原语选型**，且并发 bug 需一定并发量才触发、难定位，还产生脏数据影响业务。一句话背法：**「go 一行易写难写好：要管协程数/死锁/选型，且 bug 只在并发量下触发、出脏数据」**。

## 面试官视角
考官看你是否意识到并发的隐蔽成本，而非停在"go 很方便"。能讲清雷区清单、并指出"并发 bug 只在特定并发量下触发、难复现且出脏数据"，说明有实战血泪；以为"加个 go 就行"、对资源与死锁毫无概念，是红旗。
- **P5**：知道并发有坑。
- **P6**：能列雷区（资源/死锁/选型）。
- **P7**：能讲并发 bug 特性（难复现/脏数据）并给规避。

## 主问答
**Q（面试官原话）：** 都说 Go 并发简单，难在哪？

**先铺垫（由浅入深第 1 层）**：`go` 把"怎么调度、怎么切换"全藏起来了，所以写起来像"加个前缀就并行了"。但并发的难不在"起协程"，在"起完之后怎么不出事"——资源、死锁、选型、脏数据，哪一个都能让线上半夜告警。

1. **易写难好（第 2 层）**：`go` 屏蔽调度，一行起协程；但需自己控协程数（防资源耗尽）、防上下文切换开销、防死锁、受软硬件资源约束、做原语选型。
2. **bug 特性（第 3 层·最难）**：并发 bug 只在**一定并发请求下才触发**→难以稳定复现与定位；更严重的是会产生**脏数据**，直接冲击业务正确性。
3. **典型实例（第 4 层·实战）**：并发写 DB 时 for 循环迭代器元素是指针移动 + 闭包取值时刻问题，闭包最终大概率拿到最后一个 user，结果重复错乱。
4. **规避手段（第 5 层）**：把循环变量以参数传值进闭包 / 循环内 `tmp := u` 拷贝 / 不用闭包直接传参；具体三修法见 1017。
5. **误用风险（第 6 层）**：无脑 `go` 还容易滚雪球——协程数失控 → 资源耗尽 + 切换暴涨（见 108 何时控并发 / 101 上下文切换代价）。

## 版本与兼容性
| 维度 | 说明 |
|------|------|
| 通用事实 | 并发雷区与 bug 特性长期成立，不依赖 Go 版本 |
| 闭包陷阱 | Go < 1.22 循环变量按引用共享；Go 1.22+ 改为每轮新变量（见 1017） |
| 脏数据 | 并发写共享状态未保护 → 数据错乱，比崩溃更隐蔽 |
| 规避 | 控并发数 + 选对原语 + 闭包传值（见 108/1017） |
| Go 版本 | 闭包语义边界见 1017（Go 1.22 per-iteration），本项目实测 Go 1.26.5 |

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
)

type User struct{ ID int }

func main() {
	users := []User{{1}, {2}, {3}}

	// ❌ 坏：Go<1.22 下 u 是同一变量，闭包最终大概率拿到最后一个 user
	var wgBad sync.WaitGroup
	for _, u := range users {
		wgBad.Add(1)
		go func() {
			defer wgBad.Done()
			writeDB(u) // 可能全是 User{3}
		}()
	}
	wgBad.Wait()

	// ✅ 修法：把循环变量以参数传值进闭包（Go 全版本安全）
	var wg sync.WaitGroup
	for _, u := range users {
		wg.Add(1)
		go func(u User) {
			defer wg.Done()
			writeDB(u) // 各自拿到正确的 user
		}(u)
	}
	wg.Wait()
}

func writeDB(u User) { fmt.Println("write", u.ID) }
```

## 总结与追问预判
**背这三句就够**：① **`go` 易写难写好：要管协程数/上下文切换/死锁/资源/原语选型**；② **并发 bug 只在特定并发量下触发、难复现，还会出脏数据**；③ **闭包捕获循环变量是大坑，修法是传值/拷贝/不用闭包**。
**预判追问**：
- 「闭包循环变量怎么修？」→ 参数传值或循环内 tmp 拷贝（见 1017 goroutine 循环变量）。
- 「协程数怎么控？」→ 协程池 / channel 信号量限并发（见 108 何时控并发 / 1015 信号量）。
- 「原语怎么选型？」→ 见 102 并发原语选型大方向（channel 编排、锁保护、原子）。

## ⚠️ 原文纠错
1. 事实核校：go 易写难好、雷区清单、并发 bug 需并发量触发且出脏数据——均正确，本卡为准。
2. 崩坏词归一：源码将 goroutine/协程/闭包等音译为崩坏词；本卡统一为规范术语。
3. 补强：本卡在版本表补「Go 1.22 起循环变量改为 per-iteration 语义」的边界（旧版闭包陷阱在 1.22+ 自然消失，但传值写法全版本安全），原卡未点明版本差异。
