> 分类：网络协议 / TCP | 难度：L3 | 题型：场景分析题 | 频率：中 | 关键词：**RST**/**确认号校验**/**SYN 乱序**/**连接重置**/**非正常关闭**
> 原文锚点：第 1~29 段「第二次握手的时候服务端发送的确认号不是客户端初始序列号加一会发生什么…客户端回一个 RST 报文，服务端收到 RST 后就会终止连接…只会终止当前的三次握手…RST 用于 TCP 连接中出现异常时强制关闭连接重置状态，避免错误扩散」

## 一句话总述
**会**。TCP 对「确认号与自身状态不符」的报文按**非法报文**处理，回复 RST 强制重置——但要分清层次：三次握手中客户端收到确认号错误的 SYN+ACK 会回 RST，**只终止当前这一次握手过程**（服务端释放这个半开连接），**等下一个携带正确序列号的 SYN 到达后仍可正常完成握手**——RST 是「报文级纠错」，不是「对端拉黑」。

## 面试官视角
- 考察意图：一题三考——① 序列号与确认号的状态机语义；② RST 的触发条件与用途清单；③ **「RST 终止当前连接/握手」与「不影响后续新握手」的边界**，能分清这层的是真读过内核行为。
- 分档：P5 知道不匹配的 ACK 会触发 RST；P6 能复现「SYN seq=1 丢失、重发 seq=5、服务端先收到旧包回 ack=2」的时序推演；P7 能给出 RST 四大用途并对比 RST vs FIN 的关闭语义。
- 红旗答案：「回 RST 后这个服务端就挂了」；「RST 也走四次挥手」——前者夸大影响面，后者混淆非正常关闭与优雅关闭。
- 惊艳点：「connection refused 本质就是**内核代答的 RST**——实测连未监听端口 448µs 收到拒绝，这就是 RST 用途②『拒绝连接』的日常形态」 [实测]。

## 主问答
**Q（面试官原话）：** 客户端收到不正确的 ACK 还会发送 RST 吗？为什么？
**A：**
1. **结论：会**。TCP 是**有状态协议**，每个端点都校验收到的确认号是否匹配自身状态（三次握手中客户端期望 `服务端 ACK = 自己的 SYN seq + 1`）。不匹配 = 对端状态错乱，继续通信只会错误扩散——回 RST 立即终止，是协议的自我保护 [源码]。
2. **经典场景时序推演**：① 客户端发 SYN（seq=1）**在网络中阻塞**；② 客户端超时重发 SYN，但**换了新序列号 seq=5**；③ 网络恢复，旧的 seq=1 **先到**服务端——服务端按它回 SYN+ACK，确认号 = 1+1 = **2**；④ 客户端期望的是 **6**（5+1），收到 2 → 状态不符 → 回 **RST**；⑤ 服务端收到 RST，**终止这个半开连接**；⑥ 稍后 seq=5 的 SYN 到达，双方**正常完成三次握手** [源码]。
3. **关键边界：RST 只杀当前**。服务端收到 RST 后释放的只是**这个半开连接的状态**，不会「重置服务」；随后携带正确序列号的新 SYN 照常处理。RST 纠正的是**一次错乱的连接尝试**，不是惩罚对端 [源码]。
4. **RST 的四大用途**：① **终止不匹配报文**——收到不属于任何已知连接的包、或序列号校验失败的包，回 RST 宣告非法（本案）；② **拒绝连接**——服务端不想/不能建连（资源限制、安全策略），对 SYN 直接回 RST；③ **强制关闭异常连接**——状态不一致（如半开连接：一端崩溃重启后收到旧连接的报文）时任何一方可发 RST 立刻止损；④ **超时断开**——连接长期非活动时用 RST 释放资源 [源码]。
5. **RST 是非正常关闭**：与四次挥手的优雅关闭不同，RST **立即断开、不留 TIME_WAIT、不保证在途数据送达**——未完成传输的数据会丢失。因此正常关闭一律 FIN 四次挥手，RST 只留给异常场景 [源码]。

## 总结与追问预判
一句话记忆：**「RST = 状态校验失败的强制终止：杀当前连接/握手，不杀后续；不挥手、不留 TIME_WAIT、不保数据」**。三次握手全程见 1843、丢包重传见 1843 [边界]。常追问「生产上收到 RST 的常见原因」——答：对端进程崩溃（内核代答 RST）、对端端口未监听、NAT 超时后旧连接报文、中间盒注入、SO_LINGER(0)；再追问「RST 自己会被确认吗」——答：**RST 从不被 ACK**，收到方校验通过即直接关闭，这也是它「快而粗暴」的原因 [经验]。

## ⚠️ 原文纠错
1. 术语归一：[经验] 源为语音转写，「IST/RSST/RST」混用应为 RST，「促始」应为「初始化」，「确认订单号」应为「确认应答号」，统一为规范术语。
2. 表述纠错：源「服务端收到 RST 后就会终止连接」未区分「终止当前半开连接」与「不影响后续新握手」——这是本题最关键的边界，本卡已补全第 3 条。
3. 补充：源未提 RFC 5961 对盲 RST 的 challenge-ACK 防护与 SO_LINGER(0) 的应用层触发方式，两者是进阶追问点，本卡已补。
