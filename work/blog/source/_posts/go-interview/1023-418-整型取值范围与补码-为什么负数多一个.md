## 一句话总述
`int16` 的范围是 **-32768 ~ 32767**：按原码推导只能得到 -32767 ~ 32767，但计算机用**补码**存储，负零的补码 `1000...0` 没有任何原码能映射过去，于是被人为规定为 -32768，负数因此比正数多一个。

## 面试官视角
考官要的是「为什么不是对称的」。能把「原码 ±0 重复 → 补码释放出一个编码 → 规定给最小负数」这条链路讲顺，比背范围有意义得多。顺带说出 `math.MinInt16` 这类常量，说明你写过边界测试。

## 主问答
**Q（面试官原话）：** int16 的范围是多少？为什么负数比正数多一个？

1. **先看原码**：最高位是符号位，最大数符号位为 0 且其余全 1，最小数符号位为 1 且其余全 1。
2. **零重复**：原码里「全 0」表示正零、「符号位为 1 其余为 0」表示负零，两者数值相等，浪费了一个编码。
3. **补码规则**：正数补码不变；负数补码为**符号位不变、其余位取反后加一**。
4. **负零归并**：负零取反加一后连续进位，结果与正零的补码完全相同，因此补码中零只占一个编码。
5. **多出的编码**：补码比原码多出一个编码，且任何原码都不可能转成补码后得到「1 后面全 0」，于是人为规定它等于最小负数，范围由此变成 -32768 ~ 32767。

## 关键代码
```go
package main

import (
	"fmt"
	"math"
)

func main() {
	fmt.Println(math.MinInt16, math.MaxInt16) // -32768 32767
	fmt.Println(math.MinInt8, math.MaxInt8)   // -128 127
	// 最小值的二进制：1 后面全 0，正是补码多出的那个编码
	fmt.Printf("%016b\n", int16(math.MinInt16))
}
```

## 总结与追问预判
核心：**补码归并正负零 → 多出一个编码 → 归给最小负数**。追问常拐向「为什么 `math.MinInt64` 取绝对值会溢出」，备好「最小值取负仍是自身」这个经典陷阱。

## ⚠️ 原文纠错
1. 事实核校： [经验] 原文中间推导「负的 2^15 减一到正的 2^15 减一」即 -32767 ~ 32767，那是**原码**情形的结论；采用补码存储后最小值多出一个，最终为 -32768 ~ 32767，原文后段已自行修正，本卡明确区分两阶段。
2. 事实核校： [经验] 原文称「补码中会比原码多出一个编码」表述正确，但更准确的说法是：补码消除了 ±0 的重复表示，从而比原码多容纳一个有效数值编码。
3. 崩坏词归一：源码将 int16 / 补码 / 二进制 等音译为多组崩坏词，本卡统一为规范术语。
