## 一句话总述
大文本场景的写入负载靠"减写次数 + 缓刷新 + 分集群"三段治理：合并写操作、调大 refresh_interval、按用户热度做冷热与读写分离，低频用户按 TTL 淘汰。

## 面试官视角
- 意图：考察候选人对 ES 写入链路的链路级理解（buffer→refresh→segment merge）与架构权衡能力。
- P5 知道 refresh_interval 默认 1s 可调大；P6 能说清业务层合并写入省的是什么；P7 能把冷热分离抽象成"二八法则分集群"。
- 红旗：以为调 refresh_interval 是治本；把读写分离和冷热分离混为一谈。
- 惊艳点：指出 refresh 是 ES 内部 IO 合并、业务层合并是应用层 IO 合并，两层可叠加。

## 主问答
**Q（面试官原话）：** 大文本索引写入把集群压垮了，怎么优化？
**A：**
1. **结论**：三层——业务层合并多次写操作（上传又删则直接不写）、调大 refresh_interval（大文本建议 >5s）、架构上冷热/读写分离并按 TTL 淘冷。
2. **机制**：refresh 把 in-memory buffer 的文档变成可搜索段，默认 1s 一次，本质是 ES 内部 IO 合并；业务侧把同文档的增删改合并成最终态再写，减少无效写入 `[源码]`。
3. **边界**：冷热分离把 20% 高频用户拆到高配独立集群；读写分离把新用户先写临时集群、夜间闲时迁移全量；僵尸用户按可配置 TTL（如 100 天）淘汰，重搜时重建 `[经验]`。

## 关键代码
```go
// 示意，未验证：业务层合并同一文档的多次操作——上传后又删除则直接丢弃，不写 ES
type OpType int
const (OpUpsert OpType = iota; OpDelete)

type Op struct{ DocID string; Type OpType }

func mergeOps(ops []Op) []Op {
    last := map[string]Op{}
    order := []string{}
    for _, o := range ops {
        if _, ok := last[o.DocID]; !ok {
            order = append(order, o.DocID)
        }
        last[o.DocID] = o // 后写覆盖前写
    }
    out := make([]Op, 0, len(order))
    for _, id := range order {
        if last[id].Type != OpDelete { // 最终态是删除则不写
            out = append(out, last[id])
        }
    }
    return out
}
```
