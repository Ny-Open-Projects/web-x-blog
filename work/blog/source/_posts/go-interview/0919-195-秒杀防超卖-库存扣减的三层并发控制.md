> 原文锚点：第 9~25 段「DB 层三种方案：①悲观锁(查库存>0 加锁更新) ②乐观锁(version 字段 CAS 更新,WHERE version=旧值) ③Redis 分布式锁(SET NX EX + 唯一 value + Lua 释放)」

## 一句话总述
秒杀防超卖的核心是**库存扣减的并发正确性**。数据库层有三套典型方案：**① 悲观锁**（查询即加锁，库存>0 才更新，串行化）；**② 乐观锁**（表加 version 字段，UPDATE 时 `WHERE version=旧值 AND stock>0` 带版本 CAS，失败重试）；**③ Redis 分布式锁**（SET NX EX 抢占锁，持锁扣库存）。三者按"并发度/正确性/部署复杂度"取舍。

## 面试官视角
- 意图：考察能否把"防超卖"落到**具体的并发控制手段**，而不是空谈"用锁"。
- P6 能说出三种方案名字与大致做法；P7 能讲清乐观锁 version CAS 的原子更新 SQL、以及 Redis 锁的"原子加锁+唯一 value+Lua 释放"三要素。
- 红旗：以为乐观锁不加条件（实际必须 `WHERE version=旧值` 才 CAS）；把 Redis 分布式锁说成"SET 一下就行"（漏掉原子性/唯一值/过期）。
- 惊艳点：点出"无论业务层怎么优化，最终库存扣减仍可能并发，所以 DB 层必须兜底"——自然引出 Redis 锁细节（见 195）和 MQ 削峰（见 195）。

## 主问答
**Q（面试官原话）：** 电商秒杀怎么防止超卖？数据库层怎么做？
**A：**
1. **结论**：防超卖 = 保证库存扣减的并发正确性。数据库层三方案：悲观锁、乐观锁、Redis 分布式锁。
2. **机制① 悲观锁**：查库存前加锁（`SELECT ... FOR UPDATE`），确认 stock>0 再 UPDATE，提交后其他线程才能操作——**串行化、绝对正确但吞吐低**，高并发下成瓶颈。
3. **机制② 乐观锁**：库存表加 `version` 字段；查时读出 stock 和 version；更新时
   `UPDATE stock SET stock=stock-1, version=version+1 WHERE id=? AND version=旧值 AND stock>0`。
   若 version 已被别人改过，影响行数=0 → 重试直至成功。**无锁、高并发，但高冲突时重试多**。
4. **机制③ Redis 分布式锁**：用 `SET lock NX EX` 原子抢占锁，持锁期间扣库存，释放用 Lua 保证"判断+删除"原子——适合多实例部署（见 195）`[经验]`。

## 关键代码
```sql
-- ① 悲观锁：查询即加行锁，提交前其他事务阻塞
START TRANSACTION;
SELECT stock FROM goods WHERE id = 100 FOR UPDATE; -- 加锁
-- 应用判断 stock > 0 后更新
UPDATE goods SET stock = stock - 1 WHERE id = 100;
COMMIT;

-- ② 乐观锁：version CAS，原子更新+防超卖双重条件
UPDATE goods
   SET stock = stock - 1, version = version + 1
 WHERE id = 100
   AND version = 5        -- 旧版本值（CAS）
   AND stock > 0;         -- 防超卖：库存不足直接失败
-- 影响行数=0 表示被他人抢先，应用层重试
```

## 总结与追问预判
- DB 层三方案：悲观锁(FOR UPDATE 串行)/乐观锁(version CAS 重试)/Redis 分布式锁(NX EX)。
- 预判：Redis 锁细节 → 见 195；MQ 削峰+应用层 → 见 195；通用锁分类 → 见 1013（本卡聚焦 DB/Redis 库存扣减层）。
