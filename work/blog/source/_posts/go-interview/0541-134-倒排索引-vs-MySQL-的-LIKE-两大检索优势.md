> 分类：Elasticsearch 查询 | 难度：L3 | 题型：对比题 | 频率：高 | 关键词：**LIKE、左前缀、全表扫描、分词、match、相邻文本、全文检索**

> 原文锚点：第 18~29 段「MySQL 的索引是 B+树的结构，它在这个字段上建索引的时候，是按照从左到右的顺序建索引的，所以使用 like 做模糊匹配的时候，只能在包含左前缀的情况下才能使用到索引…而一旦百分号出现在开头，那么就会走全表扫描…MySQL 的模糊匹配只能用来匹配相邻的连续文本…Elasticsearch 还支持多种查询方式，我们既可以按照查询关键词的顺序匹配，也可以查询关键词的部分」

## 一句话总述
倒排索引相对 MySQL `LIKE` 有**两大优势**：**①查询效率**——B+树按**从左到右**建索引，`LIKE` 只有**左前缀**能用上索引，**`%` 出现在开头就必然全表扫描**；倒排索引建立的是**单词 → 文档 ID** 的映射，可**按词直接定位文档**。②**分词**——MySQL 模糊匹配只能匹配**相邻的连续文本**，ES 支持多种查询方式，既可**按关键词顺序匹配**，也可只匹配**关键词的一部分**（如 `match` and / `match` or）。

## 面试官视角
- 考察意图：能否把"为什么 ES 全文检索比 MySQL LIKE 快"讲成**结构性原因**，而不是"ES 快"三个字。
- 分档：P5 知道 `LIKE '%x%'` 用不上索引；P6 能说清**左前缀原则**与全表扫描；P7 能补上**分词维度**的差异——**MySQL 只能匹配相邻连续文本**，ES 可做词序/部分匹配。
- 红旗答案：以为给字段建了索引 `LIKE '%x%'` 就能走索引——**`%` 在开头一律全表扫描**。
- 惊艳点：**两类"全表扫描"都会发生**：`LIKE '%x'` 既可能走**二级索引的全表扫描**，也可能走**主键索引的全表扫描**，两种都很慢 `[源码]`。

## 主问答
**Q（面试官原话）：** 为什么全文检索要用 ES 而不是 MySQL 的 LIKE？

1. **结论**：两条硬优势——**查询效率**（倒排按词直查，避免全表扫描）与**分词能力**（ES 支持多种匹配方式，MySQL 只匹配相邻连续文本）`[源码]`。
2. **效率 · B+树的建索引顺序**：MySQL 的索引是 **B+树**结构，**在字段上建索引时是按照从左到右的顺序**建的 `[源码]`。
3. **效率 · 左前缀原则**：因此用 `LIKE` 做模糊匹配时，**只有在包含左前缀的情况下才能使用到索引**，也就是**通配符 `%` 不出现在开头的位置**才能用到索引 `[源码]`。
4. **效率 · `%` 在开头即失效**：**一旦 `%` 出现在开头，就会走全表扫描**；**不管是走二级索引树的全表扫描，还是走主键索引的全表扫描，这种查询方式都会变得很慢** `[源码]`。
5. **效率 · 倒排的做法**：ES 的全文检索使用**倒排索引**结构，**建立的是单词到文档 ID 的对应关系**，**根据单词可以快速定位到文档**——**就像汉语词典里的索引一样，根据关键词快速定位到关键词出现在哪一页**；所以**相同数量级下的数据，ES 有更出色的全文检索性能** `[源码]`。
6. **分词 · MySQL 的限制**：**MySQL 的模糊匹配只能用来匹配相邻的连续文本** `[源码]`。
7. **分词 · ES 的多样**：ES **还支持多种查询方式**，**可以根据具体业务场景选择不同的匹配方式**；既**可以按查询关键词的顺序匹配**，也**可以只查询关键词的一部分**（如 `match` and / `match` or）`[源码]`。

**加分层：** 判断 MySQL 能否用索引，只看一条——**`%` 是不是在最左边**。最左前缀是 B+树索引的天然约束，与字段有没有索引无关。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| MySQL 全版本 | B+树左前缀 | `LIKE '%x'` 不走索引 |
| MySQL 5.6+ | InnoDB 支持全文索引 | 可用 FULLTEXT，但能力弱于 ES |
| MySQL 5.7+ | 内置 ngram 解析器 | 支持中文全文，但仍非检索引擎 |
| ES 全版本 | 倒排结构 | 按词直查，与版本无关 |

## 关键代码
```go
// 用 Go 对比两条路径：MySQL LIKE 全表扫描 vs ES 倒排直查
package main

import (
	"context"
	"fmt"
	"strings"

	"github.com/olivere/elastic/v7"
)

// simulateMySQLLike 模拟 MySQL：B+树按左前缀建索引，'%x' 开头只能逐行扫
func simulateMySQLLike(docs map[int]string, kw string) []int {
	var hit []int
	for id, text := range docs { // 全表扫描：每行都要比对
		if strings.Contains(text, kw) {
			hit = append(hit, id)
		}
	}
	return hit
}

func main() {
	// 1) MySQL 侧：LIKE '%红%' -> 全表扫描
	docs := map[int]string{1: "小明", 2: "小红", 3: "小强"}
	fmt.Println("MySQL LIKE '%红%' 命中:", simulateMySQLLike(docs, "红"))

	// 2) ES 侧：倒排索引按 term 直查，复杂度与文档总数无关
	ctx := context.Background()
	client, _ := elastic.NewClient(elastic.SetURL("http://127.0.0.1:9200"), elastic.SetSniff(false))
	q := elastic.NewMatchQuery("name", "红") // match：先分词，再查倒排列表
	res, _ := client.Search().Index("user").Query(q).Size(10).Do(context.WithValue(ctx, struct{}{}, nil))
	fmt.Println("ES match 查询完成，命中数:", res.TotalHits())
}
```

## 总结与追问预判
**最常见追问是"那我把 `%` 放后面不就行了"**——`LIKE 'x%'` **确实可以走索引**（符合左前缀），但它解决的只是"前缀匹配"，解决不了"**包含**"和"**任意位置**"的检索，而这正是全文检索的核心诉求。追问常接"MySQL 的 FULLTEXT 能不能替代 ES"——**5.6 起 InnoDB 支持全文索引、5.7 起有 ngram 中文解析器**，但它们缺少**分片、近实时、相关性评分、聚合**等检索系统能力，定位不同，不能等同替换。

## ⚠️ 原文纠错
1. 事实核校：B+树按从左到右建索引、`LIKE` 仅在左前缀时用索引、`%` 开头走全表扫描（二级索引全扫或主键索引全扫）、倒排为单词到文档 ID 映射因而可按词直查、MySQL 模糊匹配只匹配相邻连续文本、ES 支持按词序或部分匹配——均与 MySQL/ES 实现一致 `[经验]`。
2. 补充：原文把 ES 的多种匹配方式概括为 `match` and / `match` or，准确术语是 **`match` 查询的 `operator` 参数**（`and` / `or`）以及 `match_phrase`（短语查询，要求词序与间距）；面试中应报出 `match_phrase` 这个术语 `[经验]`。
3. 崩坏词归一：源码将 Elasticsearch、B+树、倒排索引、分词、match 查询等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
