> 分类：消息队列 / Kafka | 难度：L4 | 题型：流程题 | 频率：高 | 关键词：**写入流程、活跃日志段、页缓存、数据文件、索引文件、副本同步、应答确认**

> 原文锚点：第 23~49 段「producer 发送消息，应用程序中的 producer 通过 Kafka 提供的 API 将消息发送到指定的 topic 上…每个分区对应的日志对象管理分区中所有的日志分段，新发送的消息会追加到当前活跃的日志分段，任何时刻都只有一个活跃的日志分段…消息内容会追加到数据文件当中，追加的过程中文件是先被写入到操作系统的内存缓冲区，然后同步到磁盘中的数据文件…消息写入之后还需要进行副本的同步…当生产者的消息被成功写入提交，Kafka 的 broker 会响应生产者写入结果」

## 一句话总述
写入链路是：**producer 按分区策略选分区 → 消息追加到该分区唯一的活跃日志分段 → 先落操作系统内存缓冲区再同步到磁盘数据文件 → 同步到副本分区 → 全部 ISR 副本写入后 broker 应答生产者**。

## 面试官视角
P6 会说「写到分区文件里」；P7 要讲清**活跃日志段的唯一性**、**先内存缓冲后刷盘的两段式**、**每个日志段对应一个数据文件加一个索引文件**，以及**应答时机取决于副本同步结果**——后者是可靠性配置的入口。

## 主问答
**Q（面试官原话）：** 一条消息从生产者发出到落盘，中间经历了什么？

1. **producer 发送**：应用程序中的 producer 通过 Kafka API **将消息发送到指定 topic** `[源码]`。
2. **选分区**：producer 通过**指定不同的分区策略**决定消息存到哪个具体分区 `[源码]`。
3. **定位日志对象**：每个分区对应一个**日志对象**，它管理该分区中**所有的日志分段** `[源码]`。
4. **追加到活跃段**：新发送的消息**追加到当前活跃的日志分段**；**任何时刻都只有一个活跃的日志分段** `[源码]`。
5. **段与文件对应**：每个日志分段对应**一个数据文件和一个索引文件**；消息内容**追加到数据文件** `[源码]`。
6. **两段式落盘**：追加过程中，文件**先被写入操作系统的内存缓冲区**，**然后同步到磁盘中的数据文件** `[源码]`。
7. **副本同步**：消息写入后还需**同步到副本分区**，这一环节保障数据可靠性 `[源码]`。
8. **应答确认**：当消息被成功写入提交后，**broker 响应生产者写入结果** `[源码]`。
9. **性能关键**：依赖**操作系统页缓存**而不是应用层自己缓存，是 Kafka 高吞吐的重要原因之一 `[经验]`。

## 关键代码
```go
package main

import (
	"fmt"

	"github.com/IBM/sarama"
)

func main() {
	cfg := sarama.NewConfig()
	cfg.Producer.RequiredAcks = sarama.WaitForAll // 等所有 ISR 副本写入后才应答
	cfg.Producer.Return.Successes = true
	cfg.Producer.Partitioner = sarama.NewHashPartitioner

	producer, _ := sarama.NewSyncProducer([]string{"127.0.0.1:9092"}, cfg)
	defer producer.Close()

	msg := &sarama.ProducerMessage{
		Topic: "orders",
		Key:   sarama.StringEncoder("order-10086"),
		Value: sarama.StringEncoder("paid"),
	}
	partition, offset, err := producer.SendMessage(msg)
	if err != nil {
		panic(err)
	}
	// 返回的 offset 即该消息在分区日志段中的位置
	fmt.Printf("partition=%d offset=%d\n", partition, offset)
}
```

## 总结与追问预判
**「顺序追加 + 页缓存 + 单活跃段」是 Kafka 写入高性能的三件套**。追问常是「什么时候才算写入成功」——这由 acks 与 ISR 共同决定，详见同批 147-isr-replication（146-* 那批已讲存储模型与日志分段细节，本卡聚焦端到端链路）。
