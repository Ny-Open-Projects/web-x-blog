> 原文锚点：第 99~106 段「自增值持久化、原子 DDL 与 doublewrite 文件分离」

## 一句话总述
MySQL 8.0 起自增值经 redo log + 数据字典表持久化，重启不再从 max(ID) 反推、避免 ID 复用；8.0.20 起 doublewrite 独立成文件；字典下沉到 InnoDB 事务引擎系统表，DDL 变为系统表 DML，具备原子性。

## 面试官视角
这道题考的是候选人对 8.0 内核改进的真实了解而非背概念。8.0 之前「重启后自增值复用」是经典坑，能讲清「为什么复用、8.0 怎么解决」的人通常真被坑过。doublewrite 分离与原子 DDL 是加分项。

## 主问答
**Q（面试官原话）：** MySQL 8.0 对自增值和 doublewrite 做了哪些改动？为什么 8.0 之前自增值会重复利用？

1. **自增值持久化（8.0 起）**：8.0 之前自增值只在内存、不落盘；重启后 InnoDB 用 `SELECT MAX(id)` 反推，若最大 ID 已删则自增值可能复用、引发主键冲突。8.0 起改为持久化：每次 `INSERT`/`UPDATE` 改动自增值先写 redo log，checkpoint 再刷入 `mysql.innodb_dynamic_metadata`；crash 重启先读该字典表持久化值、再从 redo 取最新值，保证序列连续不回退。

2. **doublewrite 文件分离（8.0.20 起）**：8.0.20 前 doublewrite buffer 在系统表空间（ibdata），所有表共享、易成写瓶颈；8.0.20 起拆成独立文件（如 `#ib_16384_0.dblwr`），与系统表空间解耦，降写放大、提并发吞吐。

3. **原子 DDL 兜底**：8.0 把数据字典迁移到 InnoDB 事务引擎托管的系统表，DDL 变成「对系统表的一组 DML」，失败可借事务引擎回滚，保证字典原子性——不出现「表建了字典没记」的中间态。

## 版本与兼容性
| 版本 | 自增值行为 | doublewrite | DDL 原子性 |
|------|------------|-------------|------------|
| < 8.0 | 内存态、重启从 max(ID) 反推，可能复用 | 在系统表空间共享 | 非原子，可能留中间态 |
| 8.0 ~ 8.0.19 | redo + 字典表持久化 | 仍在系统表空间 | 原子 DDL（字典下沉事务引擎） |
| >= 8.0.20 | redo + 字典表持久化 | 独立 doublewrite 文件 | 原子 DDL |

## 总结与追问预判
核心：**8.0 把自增值从「重启靠猜」变成「重启靠 redo + 字典表」**。追问多拐向「自增主键用完」「UUID vs 自增主键的碎片率」，提前备好 B+树页分裂对比。doublewrite 分离是 8.0.20 才有，务必带版本边界。
