> 原文锚点：第 36~42 段「自动提交默认开启，需设为 false 改手动位移提交」

## 一句话总述
自动提交**默认开启**但会带来重复消费与消息丢失；高可靠场景应关掉它改为**手动提交**，并遵守"**没消费成功就不提交位移**"。

## 面试官视角
P6 知道"手动提交更稳"；P7 要说出**自动提交为什么会丢**——位移先于业务处理提交，失败后再不投递 `[源码]`。加分点：**宁可重复消费也不丢消息**，消费端须幂等 `[经验]`。

## 主问答
**Q（面试官原话）：** 消费位移什么时候提交？自动提交有什么问题？

1. **两种提交方式**：位移提交分自动提交与手动提交；消费端配置项默认值为 **true**，即默认开启自动提交 `[源码]`。
2. **自动提交的双风险**：提交时机由客户端周期驱动，与业务处理不同步，会带来**重复消费**与**消息丢失**两类问题 `[经验]`。
3. **高可靠要关掉它**：把该配置项设为 **false**，改为手动提交位移 `[实测]`。
4. **铁律：没成功就别提交**：消息没有被成功消费时，**不能提交对应的消费位移**，否则这条消息等于被永久跳过 `[源码]`。
5. **取舍原则**：对高可靠应用，**宁可重复消费，也不应因消费异常导致消息丢失**——所以消费端必须做幂等 `[经验]`。
6. **毒药消息要隔离**：解析异常的消息会一直消费失败、卡住进度，应投递到专门队列待排障 `[经验]`。

## 关键代码
```go
for {
    m, err := r.FetchMessage(ctx)        // 手动模式：先取消息
    if err != nil { break }
    if err := handle(m); err != nil {    // 业务处理失败
        continue                         // 不提交位移，消息稍后重新投递
    }
    r.CommitMessages(ctx, m)             // 成功后才提交
}
```
> 验证：把提交放在业务处理之前重跑，宕机后该消息不再出现，即"静默丢失"现场 `[实测]`。

## 总结与追问预判
**位移提交是消费端唯一的所有权确认动作**。下一步常问：那投递失败的消息放哪——见同批深卡的重试与死信队列。

## ⚠️ 原文纠错
1. 事实核校：原文"默认开启自动提交、高可靠应改手动"准确；补充——手动提交的落点是**业务处理成功之后**，不是拉取之后 `[源码]`。
2. 补充：原文"宁可重复消费不应丢失"是正确取舍，但需配套**消费端幂等**（唯一键去重或幂等写入），否则重复消费会变成数据错误 `[经验]`。
