> 分类：Go 工程 | 难度：中高 | 题型：原理深挖 | 频率：中高 | 关键词：**可见性、internal、replace、exclude、GOPRIVATE、主模块**

> 原文锚点：第 1~103 段「两种内部包理解、可见性、internal 目录、私有包 replace 导入、go.mod 指令」

## 思路与架构
「如何使用内部包」有两层含义，需先与面试官对齐：
- **语言/目录层**：`internal` 目录 = 包级可见性控制。Go 1.4 引入，编译期强制：`internal` 下包只能被其**父目录及子目录**引用。
- **工程/依赖层**：公司内部私有包 = 依赖获取问题。包在内网 git 平台，本地未上传时用 `replace` 映射到本地目录。
- 底层基础是**标识符可见性**：首字母大小写决定跨包可访问性，字段与方法同样受限。

## 方案取舍
- 用 `internal` 而非仅靠大小写：大小写只能控制标识符，控制不了「整个包被别的工程 import」；internal 提供目录级硬约束。
- 用 internal 而非口头约定：约定会腐化，编译期报错才是可执行的架构边界。
- 私有包本地调试用 `replace` 而非发版：避免为调试反复推 tag；但 replace 只在主模块生效，交付前记得清理或提交正式版本。
- `exclude` 是最后手段：只在明确某版本有严重 Bug 时用，日常几乎不用；优先升级到修复版本。

## 答题技巧
1. 先澄清歧义：「内部包」可能指 `internal` 目录，也可能指公司私有包——反问确认是专业表现。
2. 讲可见性打底：大小写决定标识符跨包，字段方法同规则。
3. 讲 internal 规则：Go 1.4+、父目录及子目录可用、越级编译报错；意义是防高权限后台包被误导入。
4. 讲私有包实战：GOPRIVATE 绕代理→未上传报 404→replace 映射本地→require 生成伪版本号。
5. 收尾补限制：replace/exclude **仅主模块生效**；实战话术「业务代码放 internal，公共包放外面；本地调试用 replace，上线前换成正式版本」。

## 细节与核心 API

```bash
# internal 目录规则：名为 internal 的包，只能被“以 internal 父目录为根”的导入路径引用
# 例：模块 example.com/app，目录 app/internal/auth
#   允许：example.com/app/internal/auth
#        example.com/app/server（server 在 internal 的祖先路径内）
#   禁止：example.com/other/pkg 导入 example.com/app/internal/auth（编译报错）
# 用途：强制封装，防止外部模块依赖“本不该公开”的实现细节
# 私有包（企业内）：用 internal/ 控制可见性，或放独立私有模块 + GOPRIVATE（见私有模块卡）
# 对比：internal 是“同一模块内可见性边界”；私有模块是“跨模块但不公开”
# 经验：先把易变实现放 internal，稳定了再考虑提升为公开 API
```
