> 原文锚点：第 1~12 段「查询根本不存在的数据，缓存与 DB 都没有，请求每次穿透缓存打 DB；用空值缓存 / 布隆过滤器 / 接口校验规避」

## 一句话总述
**缓存穿透** = 查询**根本不存在**的数据（如非法 ID），缓存和 DB 都没有，请求**每次都绕过缓存直击数据库**，高并发下把 DB 打挂。解法三类：**缓存空值**（不存在的 key 也存个 null+短 TTL）、**布隆过滤器**（拦截肯定不存在的 key）、**接口/参数校验**（非法 ID 直接拒）。

## 面试官视角
- 考察意图：能否区分"穿透（查不存在）/ 雪崩（大量同时失效）/ 击穿（热点 key 失效）"三兄弟，并给出对应解法。
- 分档：P5 知穿透=查不存在打 DB；P6 能给空值缓存 + 布隆过滤器；P7 能讲清布隆过滤器的误判与空值缓存的 TTL 陷阱。
- 红旗：把穿透说成"key 同时失效"（那是雪崩）；或只说布隆过滤器不知空值缓存。
- 惊艳点：点出"空值缓存要设**短 TTL** 且注意与正常空结果区分，否则脏数据常驻"；布隆过滤器**有误判率**（说不存在必不存在，说存在可能误判）。

## 主问答
**Q（面试官原话）：** 怎么防止缓存穿透？
**A：**
1. **缓存空值**：查 DB 发现不存在，也往缓存写个 `null`（或特殊标记）+ **短 TTL**。后续同 key 直接命中空值，不再打 DB。注意 TTL 要短，避免真有数据时读到脏空值 `[经验]`。
2. **布隆过滤器**：在缓存前加布隆过滤器，所有合法 key 预先放入；查询先过过滤器，**肯定不存在的 key 直接拦截**，不会打到缓存/DB。代价是有**误判率**（说存在可能实际无，但说不存在一定无）。
3. **接口/参数校验**：入口层校验 ID 合法性（格式、范围），非法请求直接拒，从源头减少穿透。

## 关键代码
```go
// 缓存空值防穿透（设短 TTL，与正常空结果区分）
val, err := rdb.Get(ctx, key).Result()
if err == redis.Nil {
    // DB 也没有 → 写空值 + 短 TTL，避免反复打 DB
    if !existsInDB(key) {
        rdb.Set(ctx, key, "NULL", 2*time.Minute) // 短 TTL
        return nil, nil
    }
}
```

## 总结与追问预判
穿透是"查不存在"，核心是"让不存在的 key 也别打 DB"。另两兄弟——雪崩（大量 key 同时失效，见 1254）、击穿（单热点 key 失效，见 1254）。缓存一致性见 1261-*。
