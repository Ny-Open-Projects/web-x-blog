> 分类：容器与编排 / K8s | 难度：L2 | 题型：原理题 | 频率：高 | 关键词：**Pod 创建流程**/**apiserver**/**etcd**/**scheduler 绑定**/**kubelet**/**控制循环**

> 原文锚点：第 6~17 段「创建应用 → 提交 apiserver → 调度 → kubelet 接管」

## 一句话总述
K8s 创建 Pod 是**声明式 + 控制循环**的接力：`kubectl` 把 PodSpec 提交给 **kube-apiserver**，apiserver 校验后存入 **etcd**；**kube-scheduler** 监听到未绑定节点的 Pod，用调度算法选出节点并**把节点名写进 `spec.nodeName`**（binding）回写 etcd；对应节点上的 **kubelet** 感知到绑定，接管镜像拉取与容器创建，并把运行状态持续回写 apiserver。

## 面试官视角
这是 K8s 原理题的第一道分水岭。背组件名不值钱，考官要看三处：① **为什么所有组件都不直接读写 etcd**（只有 apiserver 碰 etcd，其余组件通过 API Server 的 list-watch 协作）；② **调度完成的标志是什么**（`spec.nodeName` 被写入，而不是容器跑起来）；③ **声明式语义**（kubectl 提交的是期望状态，控制循环负责收敛）。三处答清即是「用过 K8s」和「理解 K8s」的差距。

## 主问答
**Q（面试官原话）：** 简述 K8s 创建一个 Pod 的主要流程？

1. **提交**：`kubectl apply -f pod.yaml`（描述 Pod 的名称、命名空间、容器镜像、端口等）或 `kubectl create deployment`，请求到达 kube-apiserver。
2. **落库**：apiserver 做**认证 → 鉴权 → 准入控制 → 校验**，把 Pod 对象以 API 对象形式写入 **etcd**，此时 Pod 处于 Pending、无节点。
3. **调度**：kube-scheduler 通过 list-watch 监听到 `spec.nodeName` 为空的 Pod，运行**调度算法**（先过滤不可用节点、再对可用节点打分），选出最佳节点，执行 **binding**——把节点名写入 Pod 的 `spec.nodeName` 字段并回写（经 apiserver）到 etcd。这一步即「binding the pod to node」。
4. **kubelet 接管**：节点上的 kubelet 同样经 list-watch 感知到「绑定到本节点的 Pod」，按 PodSpec 依次**创建 Pod 沙箱（pause 容器）→ 拉取镜像 → 创建并启动业务容器**。
5. **状态回写与守护**：kubelet 持续上报容器状态（经 apiserver 写回 etcd），Pod 从 Pending 转 Running；此后 kubelet 按**期望状态持续收敛**——容器挂了重启、Pod 被删则按其上层控制器（Deployment/ReplicaSet）的期望重建 [实测]。
   - 实测佐证（k3d 单节点 v1.35.5）：`kubectl apply` 后 `spec.nodeName=k3d-wave158-server-0` 立即可查、`Scheduled` 事件先于容器创建出现；**镜像不可达时 Pod 长期 Pending 但调度早已成功**（事件 `Successfully assigned` 与 `FailedCreatePodSandBox` 并存）——「调度完成」与「容器运行」是两个独立阶段；修复镜像源后 apply→Running 仅 **2.4s**，事件链 Pulled→Created→Started，conditions 时间线 PodScheduled→Ready 全程 1s 内。

## 版本与兼容性
| 主题 | 说明 |
|------|------|
| Pod 分阶段 | Pending（已落库/已调度未起容器）→ Running → Succeeded/Failed |
| kubectl create vs apply | create 命令式一次创建；apply 声明式可重复执行、支持后续变更收敛 |
| list-watch | 组件间感知机制自 1.0 起未变；注意 kubelet/scheduler **不直接读 etcd** |
| Pause 沙箱 | 每个 Pod 先起 pause 容器_hold 网络命名空间，业务容器共享其 net/ipc |

## 关键代码
```go
package main

import (
	"encoding/json"
	"fmt"
)

// Pod 结构只取关键字段：调度完成的标志就是 spec.nodeName 被写入
type Pod struct {
	Metadata struct {
		Name string `json:"name"`
	} `json:"metadata"`
	Spec struct {
		NodeName string `json:"nodeName"`
	} `json:"spec"`
	Status struct {
		Phase string `json:"phase"`
	} `json:"status"`
}

func main() {
	// Pending（调度前）与已调度两个阶段的对象快照
	pending := `{"metadata":{"name":"demo-pod"},"spec":{"nodeName":""},"status":{"phase":"Pending"}}`
	bound := `{"metadata":{"name":"demo-pod"},"spec":{"nodeName":"k3d-wave158-server-0"},"status":{"phase":"Pending"}}`

	for _, raw := range []string{pending, bound} {
		var p Pod
		if err := json.Unmarshal([]byte(raw), &p); err != nil {
			panic(err)
		}
		if p.Spec.NodeName == "" {
			fmt.Printf("%s: phase=%s nodeName 为空 -> 等待调度器 binding\n", p.Metadata.Name, p.Status.Phase)
		} else {
			fmt.Printf("%s: phase=%s nodeName=%s -> 已绑定, 待 kubelet 接管\n", p.Metadata.Name, p.Status.Phase, p.Spec.NodeName)
		}
	}
}
```

[实测] 输出：nodeName 为空 -> 等待调度器 binding / nodeName=k3d-wave158-server-0 -> 已绑定。

## 总结与追问预判
核心：**四棒接力 apiserver 落库 → scheduler 写 nodeName → kubelet 拉镜像建容器 → 状态回写收敛；只有 apiserver 碰 etcd，其余组件 list-watch**。追问常拐向「调度算法细节」「Pod 卡在 Pending 怎么排查」（`kubectl describe` 看事件即可定位是调度失败还是镜像拉取失败，实测 FailedCreatePodSandBox 即镜像侧问题）——组件角色分工见 1515.md`，深挖见 1516.md`。

## ⚠️ 原文纠错
1. 事实核校： [经验] 原文两处说「调度器监听 etcd 中新 pod 的变化」「kubelet 进程会监听 etcd 中 pod 的变化」——**不准确**：scheduler/kubelet 均通过 API Server 的 list-watch 机制感知变更，**不直接读写 etcd**；etcd 只有 apiserver 一个读写方，这是 K8s 安全与一致性的根基。本卡已按正确架构改写。
2. 术语归一：源文将「节点」音转为 load（load 节点、loadName），实为 node 与 `spec.nodeName`；组件名 KBAPSover/cabschedule 转写为 kube-apiserver/kube-scheduler。
