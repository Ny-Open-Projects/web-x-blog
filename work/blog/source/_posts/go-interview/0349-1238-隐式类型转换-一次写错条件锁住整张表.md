> 分类：数据库 / MySQL 锁 | 难度：L4 | 题型：排错题 | 频率：高 | 关键词：**隐式类型转换、索引失效、全表扫描、行锁升级、EXPLAIN type=index**

> 原文锚点：第 53~67 段「查询 name 大于等于 10 并且小于等于 15 的时候，我们整表的数据全部都被加锁了…它并不是加了表锁，而是加的是临键锁和行锁，只不过它把数据表里面的所有数据都加了行锁…这里面是走了二级索引的全表扫描…它的 type 是 index，也就是它走了二级索引的全表扫描…类目列是字符串类型，而我们用的条件是数字类型，也就是查询条件发生了类型的强制转换，所以会走全表扫描」

## 一句话总述
当查询条件的**类型与索引列不一致**时会发生**隐式类型转换**，导致索引失效、退化为**二级索引全表扫描**；结果是**表中所有记录都被加上行锁**（不是表锁），整表的插入、删除、修改全部被阻塞。

## 面试官视角
P6 知道「类型要写对」；P7 必须讲清**从类型错误到锁全表的完整因果链**、**「全表行锁 ≠ 表锁」这个判据**，以及用 **EXPLAIN 的 type=index** 定位该问题的方法——这是线上重大事故的典型成因。

## 主问答
**Q（面试官原话）：** 一条范围查询把整张表锁死了，可能是什么原因？

1. **现象**：查询区间明明没命中任何记录，**整表数据却全部被加锁** `[源码]`。
2. **锁的范围**：表中所有记录、主键索引上的所有数据行、**包括最大虚拟记录行**都被加锁 `[源码]`。
3. **关键判据**：此时**并不是加了表锁**，而是**临键锁与行锁**——只是把表里所有数据都加了行锁 `[源码]`。
4. **后果**：这张表**所有的插入、删除、修改操作都会被阻塞** `[源码]`。
5. **根因**：该查询**走了二级索引的全表扫描** `[源码]`。
6. **定位方法**：用 `EXPLAIN` 分析，其 **type 为 index**，表示走了二级索引的全表扫描 `[源码]`。
7. **为什么会全表扫描**：索引列是**字符串类型**，而查询条件给的是**数字类型**，发生了**类型的强制转换（隐式类型转换）**，导致索引失效 `[源码]`。
8. **修正方法**：把条件改回**字符串类型**即可重新走索引的范围扫描 `[源码]`。

## 关键代码
```sql
-- ❌ 错误：name 是 VARCHAR，却用数字比较 -> 隐式类型转换 -> 索引失效
BEGIN;
SELECT * FROM t WHERE name >= 10 AND name <= 15 LOCK IN SHARE MODE;
-- EXPLAIN 显示 type=index（二级索引全表扫描）
-- 后果：全表所有记录被加行锁，整表写入被阻塞

EXPLAIN SELECT * FROM t WHERE name >= 10 AND name <= 15;

-- ✅ 正确：条件写成字符串，走索引范围扫描，只锁扫过的少量记录
BEGIN;
SELECT * FROM t WHERE name > 'name10' AND name < 'name15' LOCK IN SHARE MODE;

EXPLAIN SELECT * FROM t WHERE name > 'name10' AND name < 'name15';
-- type=range，仅扫描并锁定必要的索引区间
```

## 总结与追问预判
**「锁全表但 EXPLAIN 不出来」时先查条件类型**——这是最高频的线上锁表事故根因。答题务必强调**「全表行锁 ≠ 表锁」**：前者是每条记录各加行锁，后者是单个表级锁，二者在锁视图中表现完全不同。修正后最小加锁范围见同批 1238-range-empty-lock。

## ⚠️ 原文纠错
1. 事实核校：整表被锁但非表锁、锁型为临键锁与行锁、包含最大虚拟记录行、EXPLAIN type=index 表示全索引扫描、字符串列遇数字条件发生隐式转换——均与 MySQL 行为一致 `[经验]`。
2. 补充：隐式类型转换具有**方向性**——字符串列用数字比较会失效（需对列做转换），而数字列用字符串比较通常仍可用索引；答题时说明方向更严谨 `[经验]`。
3. 崩坏词归一：源码将索引、全表扫描、临键锁、字符串、类型转换等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
