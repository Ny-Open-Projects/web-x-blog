> 分类：Go 并发/sync | 难度：L3 | 题型：陷阱题 | 频率：高 | 关键词：**禁止值复制** / **Mutex 字段被复制** / **锁状态不共享** / **noCopy**
> 原文锚点：第 3~16 段「sync 包装类型（Mutex/RWMutex/Cond）传值会复制锁，含作为结构体字段被值传递→计数归零」

## 一句话总述
sync.Mutex / RWMutex / Cond 等**禁止值复制**：当计数器这类结构体（含 Mutex 字段）以值传递方式被复制，副本与原对象的锁状态各自独立、互不共享，并发自增实际作用于不同副本，最终读出默认值 0——锁"看起来加了"却毫无保护作用。必须用指针 / `*sync.Mutex` 接收者。

## 面试官视角
- 考察意图：是否真理解 Mutex 是"带状态的值"、值复制会破坏并发保护
- P5 知 Mutex 不能值复制；P6 能讲清"复制后锁状态独立→计数归零"机理；P7 能讲 noCopy 检测与修复（传指针）
- 红旗：以为"结构体复制只是浅拷字段、锁还生效"；在方法里用值接收者操作含 Mutex 的结构体
- 惊艳点：用"counter 读出 0 而非 1000"的最小反例现场证伪值复制 [源码]

## 主问答
**Q（面试官原话）：** 为什么 sync.Mutex 这类类型不能值复制？
**A：**
1. **锁是有状态的值**：Mutex 内部记录持有者/状态，值复制会得到一份**全新的锁状态**，副本与原对象各自独立，互斥保护失效 [源码]。
2. **字段被值传递同样中招**：含 Mutex 的结构体（如计数器）一旦以值传给方法，整个结构体（含锁和计数）被复制，方法里加的是副本的锁、改的是副本的计数，原对象毫无变化——1000 次自增后原 counter 仍读 0 [源码]。
3. **修复=传指针**：结构体用 `*Counter`、Mutex 用 `*sync.Mutex` 作接收者/参数，保证所有 goroutine 共享同一把锁与同一份计数 [经验]。

## 关键代码
```go
type Counter struct {
    mu sync.Mutex
    n  int
}
// ❌ 值接收者：c 是副本，锁和 n 都不共享，自增 1000 次后仍读 0
func (c Counter) Inc()  { c.mu.Lock(); c.n++; c.mu.Unlock() }
func (c Counter) Get() int { return c.n }

// ✅ 指针接收者：共享同一把锁与同一份 n
func (c *Counter) IncP()  { c.mu.Lock(); c.n++; c.mu.Unlock() }
func (c *Counter) GetP() int { return c.n }
```

## ⚠️ 原文纠错
源码将若干术语音译为崩坏词，本卡统一为规范术语（SYNC→sync、勾浪→Go、购入t→goroutine、主学程→主协程、计术→计数、引的值→原值等）；技术结论未做事实性更正 [经验]。

## 总结与追问预判
- 含 sync 类型的结构体，永远传指针、用指针接收者；`go vet` 的 copylocks 能拦大部分值复制。
- WaitGroup 也有同样禁复制规则（noCopy），见 913；通用值/指针取舍见 508（只引不重述）。
