## 思路与架构
MySQL 锁服务于「多事务并发改同一行」的并发控制。整体架构分两层：隔离级别层（决定何时加锁）与引擎层（决定锁粒度）。串行化最简单——读写都加锁（S/X 记录锁 + 表级意向锁 IS/IX），但锁竞争最重。更优解是 InnoDB 的「读用 MVCC 快照、写加锁」：快照读走 undo log 构建的历史版本，不阻塞写；当前读（for update）才加锁。锁本身是内存结构，事务改数据时才与记录绑定，靠锁状态（持有/等待）实现写写排队，杜绝脏写。

## 方案取舍
- **串行化 vs MVCC+锁**：串行化绝对安全但并发极差；MVCC+写锁在保住「避免脏写」前提下放开读写并发，是默认选择。
- **表锁 vs 行锁 vs 页锁**：行锁冲突少并发高（InnoDB 默认），表锁开销小但串行（MyISAM），页锁居中（BDB，已罕见）。
- **RC vs RR**：RC 每次查询建 readview（不可重复读），RR 复用首次 readview（可重复读），RR 更常用。
- **快照读 vs 当前读**：普通 select 不阻塞写；for update 当前读加锁，用于强一致与防幻读。

## 答题技巧
答锁题先定调「并发控制需要锁」，再分三异常（脏读/不可重复读/幻读源于读写，脏写源于写写且全级别禁）。必点：InnoDB 默认行锁 + MVCC 读写不冲突；readview 时机是 RC/RR 分界；串行化靠 S/X + 意向锁但并发差；锁是内存结构、改数据才绑、靠状态机排队。追问架构时，用「隔离级别层 + 引擎层 + 快照/当前读」收尾，并点出无索引改全表会升级表锁的坑。

## 细节与核心 API

**锁粒度与意向锁**：

```text
行锁(InnoDB 默认) > 页锁(BDB,罕见) > 表锁(MyISAM,串行)
意向锁 IS/IX 表级：快速判断表内是否有行锁冲突，避免逐行扫
```

```sql
LOCK TABLES t WRITE;     -- 表锁（MyISAM 风格，串行）
-- InnoDB 行锁靠索引；无索引/索引失效的 UPDATE 会升级为全表锁（高频坑）
UPDATE t SET a=1 WHERE name='x';   -- name 无索引 → 锁全表！WHERE 必须走索引
```

**快照读 vs 当前读**：

```sql
SELECT * FROM t WHERE id=1;            -- 快照读，不阻塞写（MVCC）
SELECT * FROM t WHERE id=1 FOR UPDATE;-- 当前读，加 X 记录锁（防幻读）
-- 串行化：普通 select 也变加锁读（S 锁），并发最差
```
