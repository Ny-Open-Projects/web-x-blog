## 一句话总述
秒杀是**瞬时流量突增、抢完即回落**，硬扛加机器不现实（库存行锁限制并发）；正解是**异步削峰**——请求入队、后端按能力消费、实时反馈进度，把高并发下单转成有序队列。

## 面试官视角
- 考察意图：是否理解「流量整形/削峰」而非「堆机器」，能否讲清异步排队的全链路与适用边界。
- 分档：P5 知请求入队、后端消费；P6 能讲端到端流程（预订单→排队编号→等待页→多消费者→完成页）；P7 知异步削峰只适合瞬时高峰、持续高峰要水平扩展+弹性伸缩。
- 红旗答案：说「加机器硬扛」；或把异步削峰套到持续高峰场景（如外卖午高峰）。
- 惊艳点：点出「库存扣减需锁记录、单品加机器难根治」，以及「实时进度反馈缓解焦虑、提升信任」 [经验]。

## 主问答
**Q（面试官原话）：** 电商秒杀瞬时流量怎么应对？整套下单流程是怎样的？
**A：**
1. **异步削峰核心思路**：前端接请求**不立即生成订单、而是放入队列**，后端按实际处理能力逐步消费；同时实时反馈进度（排队人数、预计等待）缓解用户焦虑。这样把高并发下单转成**有序队列**，既保购买公平又减压 [经验]。
2. **端到端下单流程**：①用户提交→**预订单入排队区 + 分配排队编号**；②引导等待页，按编号定时查排队位置（前方待处理数 + 预计时间）；③订单服务**多消费者按序取预订单调后台生成真实订单**；④预订单出队→等待页感知并跳完成页→走常规支付 [经验]。
3. **适用边界（瞬时 vs 持续）**：异步消峰**只适合瞬时高并发**（秒杀峰值短）；若高峰持续长且时效要求高（外卖午高峰 2h、半小时送达）则**不适用**，须水平扩展 + 弹性伸缩直面高峰。单加机器难根治（库存扣减需锁记录限制并发）[经验]。

// 端到端排队（Go 侧视角）：请求入队、多消费者按序出库、进度可查
func enqueue(q redis.Client, sku string, order PreOrder) (pos int64, err error) {
    key := "seckill:queue:" + sku            // 每商品独立队列（拆分见 194）
    pos, err = q.RPush(ctx, key, order.ID).Result()
    return pos, err                            // 返回排队位置，供等待页轮询
}
func consume(q redis.Client, sku string, handle func(PreOrder)) {
    key := "seckill:queue:" + sku
    for {                                      // 多消费者按序取预订单
        id, err := q.LPop(ctx, key).Result()
        if err == redis.Nil { time.Sleep(50 * time.Millisecond); continue }
        handle(loadPreOrder(id))               // 调后台生成真实订单
    }
}
