## 一句话总述
验证隔离级别的标准手法是开两个会话分别设置隔离级别后交叉观察；运行中事务可用 `information_schema.INNODB_TRX` 查看，锁等待时长由 `innodb_lock_wait_timeout` 控制（**默认 50 秒**）。读已提交下能看到「避免脏读但仍不可重复读」的完整对照。

## 面试官视角
考官不一定要求你背命令，但**说得出来命令名**就是区分度。能讲清「设置隔离级别只对后续事务生效」「锁等待超时默认 50 秒」「运行中事务去哪张表看」，说明你真在终端上验证过而不是只看过博客。

## 主问答
**Q（面试官原话）：** 你怎么在 MySQL 上验证隔离级别的差异？

1. **会话级设置**：用会话级语句设置隔离级别，**只对设置之后开启的事务生效**，已在运行的事务不受影响。
2. **开两个会话对照**：两个终端各自开启事务，一个修改不提交，另一个观察能否看到未提交的修改——这就是脏读的复现路径。
3. **调锁等待便于观察**：演示时可调大锁等待超时；该参数默认 **50 秒**，生产不应调大，否则会长时间占用连接。
4. **查看运行中事务**：查询系统表可看到当前仍在运行的事务，事务提交后再查就为空——用它判断是否有长事务未提交。
5. **锁保证并发安全**：两个事务更新同一行时后者会阻塞，前者回滚或提交后阻塞才释放；若业务是「先读后改」，应显式加锁读以保证原子。

## 关键代码
```sql
-- 会话 A：读已提交下修改，未提交前对 B 不可见
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
UPDATE t SET a = a + 1 WHERE id = 1;   -- 未提交，B 仍读到旧值

-- 会话 B：验证避免脏读
SELECT a FROM t WHERE id = 1;          -- 读不到 A 的未提交修改
-- A 执行 COMMIT 后，B 再查才看到新值（同一事务内即不可重复读）

-- 查看仍在运行的事务
SELECT trx_id, trx_state, trx_started FROM information_schema.INNODB_TRX;
```

## 总结与追问预判
核心：**会话级设置 + 双会话对照 + 系统表查事务 + 锁等待 50 秒**。追问常拐向「长事务怎么排查」，备好「按启动时间排序找最老事务」这条。

## ⚠️ 原文纠错
1. 事实核校： [经验] 原文在两个终端分别设置锁等待时间再开启事务——需明确 `innodb_lock_wait_timeout` 为**会话级可设**变量，且隔离级别语句**仅对设置之后开启的事务生效**，本卡补出该前提。
2. 事实核校： [经验] 原文演示「事务 A 更新后 B 更新同一行会阻塞，A 回滚后 B 才继续提交，最终值正确」——现象正确，说明行锁保障了同一行的并发安全；但需补充：若业务是「先读值再改」，普通读不加锁，应使用 `SELECT ... FOR UPDATE` 保证读改原子。
3. 事实核校： [经验] 原文称提交后查询系统表「就没有正在运行的事务了」——准确；补充该表仅记录 **InnoDB 引擎层**的事务，只读事务在某些版本下不一定体现。
4. 崩坏词归一：源码将事务 / 隔离级别 / 会话 / 提交 等音译为多组崩坏词，本卡统一为规范术语。
