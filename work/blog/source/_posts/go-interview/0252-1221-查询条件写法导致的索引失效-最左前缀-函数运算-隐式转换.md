> 分类：数据库 / MySQL 索引 | 难度：L3 | 题型：排错题 | 频率：高 | 关键词：**最左前缀、联合索引、函数、表达式、隐式类型转换、索引失效**

> 原文锚点：第 6~18 段「在某些情况下，查询优化器可能无法使用到索引，从而导致索引失效。例如我们的查询条件不满足最左前缀原则，对于联合索引，如果查询条件中没有包含索引最左边的列，或者是没有连续使用索引列，那么索引就可能无法使用…如果查询条件中使用了函数或者是运算符，那么查询优化器就可能无法对这个列使用索引…如果查询条件里面的数据类型和索引列的数据类型不匹配，那么数据库可能需要进行隐式的类型转换，这种情况可能会导致索引失效」

## 一句话总述
B+树适用于**全值匹配、最左前缀匹配、范围匹配、排序、分组**五类场景；而**查询条件写法**是最常见的失效来源，典型三种：**①不满足最左前缀原则**（联合索引 `abc`，条件只含 `b` 或只含 `b+c`）、**②对索引列使用函数或运算**（`UPPER(name)='JOHN'`、`age+1=30`）、**③隐式类型转换**（`int` 列与字符串 `'18'` 比较）。

## 面试官视角
- 考察意图：能否把"索引失效"从背清单升级为**按成因分类**，并给出**改写建议**。
- 分档：P5 知道函数会让索引失效；P6 能说全三种写法类失效；P7 能给出**每一种的改写方案**，并指出 **`!=` / `NOT IN` 一般不走索引**这一原文遗漏点。
- 红旗答案：把"最左前缀"只理解成 LIKE；或以为联合索引只要包含任意一列就有效。
- 惊艳点：**联合索引 `(a,b,c)` 下，条件只有 `b`、`c` 时索引失效**——因为 B+树是**先按 a、再按 b、再按 c** 排序的，跳过 a 就失去了有序性 `[源码]`。

## 主问答
**Q（面试官原话）：** 哪些写法会让索引失效？

1. **结论**：三类写法问题会让优化器用不上索引——**不满足最左前缀原则**、**对索引列使用函数或运算**、**查询条件发生隐式类型转换** `[源码]`。
2. **背景 · B+树适用五场景**：**匹配全值**（如 `=`、`IN` 这类条件）、**匹配左边的列**（`LIKE` 前缀匹配，以及**联合索引必须从第一个索引字段开始匹配**，一旦索引字段出现断层就会导致索引失效）、**匹配范围值**（`>`、`<`、`BETWEEN` 等）、**用于排序**、**用于分组** `[源码]`。
3. **失效一 · 最左前缀**：对于联合索引，**如果查询条件中没有包含索引最左边的列，或者没有连续使用索引列，索引就可能无法使用**；例如联合索引 `abc`，**查询条件只包含 `b`，或同时包含 `b`、`c` 两个字段时，索引就会失效** `[源码]`。
4. **失效二 · 函数或运算**：**如果查询条件中使用了函数或运算符，优化器就可能无法对这个列使用索引**；例如 `UPPER(name)='JOHN'` 用了 `UPPER` 函数，**name 列就无法使用索引**；再如 `age+1=30`，**age 字段带了表达式，同样用不到索引** `[源码]`。
5. **失效三 · 隐式类型转换**：**如果查询条件的数据类型与索引列的数据类型不匹配，数据库可能需要进行隐式类型转换**，这种情况可能导致索引失效；例如 **`age` 是 `int` 类型，而查询条件写成 `age = '18'`（字符串 18）**，就可能发生类型转换并导致失效 `[源码]`。
6. **改写建议**：函数改写成**对常量做变换**（`name = 'john'` 并让比较走原列）、表达式改写成**把运算移到常量侧**（`age = 29` 而非 `age + 1 = 30`）、类型**与列定义保持一致**（去掉引号）`[经验]`。

**加分层：** 判断口诀——**索引列必须"裸着"出现在比较符的一侧**：一旦被函数包裹、参与运算、或类型被转换，B+树的有序性就用不上了。

## 关键代码
```sql
-- 联合索引 (a, b, c)：只有从最左列连续匹配才能用上
ALTER TABLE t ADD INDEX idx_abc (a, b, c);

-- 1) 生效：命中最左列 a
EXPLAIN SELECT * FROM t WHERE a = 1 AND b = 2;

-- 2) 失效：跳过 a，只用 b / b+c
EXPLAIN SELECT * FROM t WHERE b = 2;
EXPLAIN SELECT * FROM t WHERE b = 2 AND c = 3;

-- 3) 失效：对索引列用函数 / 参与运算
EXPLAIN SELECT * FROM t WHERE UPPER(name) = 'JOHN';
EXPLAIN SELECT * FROM t WHERE age + 1 = 30;
-- 改写：把变换移到常量侧
EXPLAIN SELECT * FROM t WHERE name = 'john';
EXPLAIN SELECT * FROM t WHERE age = 29;

-- 4) 失效：int 列与字符串比较触发隐式转换
EXPLAIN SELECT * FROM t WHERE age = '18';
-- 改写：类型与列定义一致
EXPLAIN SELECT * FROM t WHERE age = 18;

-- 5) 8.0 可用函数索引兜底（无法改写 SQL 时）
CREATE INDEX idx_upper_name ON t ((UPPER(name)));
```

## 总结与追问预判
**最爱追问的是"联合索引 `(a,b,c)` 查 `a` 和 `c` 能不能用"**——**能用 a 部分**（`a` 命中后 `c` 只能在索引内做过滤，Extra 可能出现 `Using index condition`），但**跳过了 `b`，`c` 无法用于定位**。追问常接"那 `!=` 呢"——**`!=` / `NOT IN` 通常选择性差，优化器多走全表扫描**，这一点原文把它归入"匹配全值"是不准确的（见纠错节）。

## ⚠️ 原文纠错
1. 事实核校：B+树适用全值/最左前缀/范围/排序/分组五类、联合索引跳过最左列或断层会失效、对索引列用函数或表达式会失效、类型不匹配触发隐式转换导致失效——均与 MySQL 优化器行为一致 `[经验]`。
2. 补充：**原文把"不等于号（!=）"归入"匹配全值"，不准确**——`!=` / `NOT IN` 通常选择性差，**一般不走索引**；另外 **8.0 起支持函数索引**，可为 `UPPER(name)` 这类表达式建索引来绕过失效 `[经验]`。
3. 崩坏词归一：源码将联合索引、最左前缀、隐式类型转换、优化器等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
