> 覆盖源 12-56 全文：activeExpireCycle「随机 20 + 25% 阈值」的统计学直觉、为什么不遍历过期字典的两难、HZ 调优的收益与代价账本、dynamic-hz 自适应、与「比例驱动加压」模式族的关系。主卡已给结论与单轮算法，本附录做参数推导与调优决策四层深挖。

## 思路与架构

```text
周期删除 = 时间维度(HZ) × 空间维度(抽样算法) 两个独立旋钮
├─ HZ 旋钮: 每秒启动多少轮周期任务
│   ├─ 默认 10 (100ms/轮)
│   ├─ 范围 1~500, 作者建议 <=100
│   └─ 5.0+ dynamic-hz 默认开: 按负载自适应
└─ 抽样旋钮: 每轮花多少 CPU
    ├─ 每个 DB 随机抽 20 个 (成本恒定 O(20))
    ├─ 过期比例 >25% -> 续扫 (过期密度高, 边际收益仍大)
    ├─ <=25% -> 转下一个 DB / 收手
    └─ 期望删除量/轮 = 20 × 过期比例 p
```

## 方案取舍
- **20 / 25% 两个数字的统计学直觉**：每轮成本固定（20 次 O(1) 判断 + 若干次删除）；设全局过期比例为 p，则一轮期望删除 `20p` 个。**25% 是「边际收益是否值得继续」的分界**：本批命中率 >1/4 说明抽样落点附近过期密度高，继续扫的期望收益仍大；≤1/4 说明已接近均匀背景噪声，继续扫性价比骤降。这本质是**用「本批命中率」作全局密度的无偏估计**，以 O(1) 信息量驱动加压——与 429 指数退避（连续失败才升级冷却）、TCP 拥塞控制（丢包才降窗）同构：**都是用局部观测信号调节全局投入** [经验]。
- **为什么不遍历过期字典——真正的两难**：遍历全字典一遍的成本随 TTL key 数线性增长（百万级 key 意味着百毫秒级阻塞主线程）；而「把遍历拆到多个周期」又引入频率设置难题——**频率设低，过期 key 积压；设高，上一轮没结束下一轮就开始，任务堆积拖垮 CPU**。随机抽 20 把每轮成本从 O(N) 压到 O(20)，且**无状态**（不用维护「扫到哪了」的游标），彻底绕开两难。代价是单轮覆盖率的期望只有 20/N——这正是「过期数据不会立马删」的算法根源 [源码]。
- **HZ 调优账本**：把 HZ 从 10 调到 100，清理及时性提升约 10 倍（100ms→10ms 粒度），但周期任务 CPU 占比同步 ×10——Redis 的周期任务不止过期清理（还有集群心跳、超时检测等），HZ 调大是**全局**放大。作者建议 ≤100 的原因：100 以上清理收益边际递减（抽样算法本身限制了单轮吞吐），而 CPU 代价线性增长。**正确姿势是先量化**：`INFO` 看 expired keys 速率与内存中带 TTL key 的积压量，确认真积压再动 [经验]。
- **dynamic-hz（5.0+ 默认开）**：配置文件里的 `hz 10` 变成「基准值」，实际频率在 [hz/2, 5×hz] 区间内按「过期 key 积压程度」自适应——积压多自动加速、空闲时回落省 CPU。**这解释了「调大 HZ」在现代版本边际收益变小**：自适应机制已经把「常态积压」吃掉了，只有突发性大批量过期（如批量写入了同秒过期的会话）才需要人工干预 [经验]。
- **突发大批量过期的专项方案**：活动结束时刻成千上万会话同时过期，是抽样算法最坏情况（过期密度高会触发大量续扫轮）。工程上三条路：① 把过期时间**加随机抖动**（TTL ± 随机几分钟）摊平峰值；② 4.0+ 开 `lazyfree-lazy-expire` 让释放走后台线程；③ 业务侧改用主动删除（SCAN + 批量 DEL）接管已知批量场景。**抽样兜底 + 业务避峰**双管齐下才是完整答案 [经验]。

## 答题技巧
- 答完「不会立马删」主动报数字：**HZ 默认 10、随机 20 个、25% 阈值**——三个数字齐报，直接与背概念的人拉开身位 [源码]。
- 用「零散 + 集中」这对词概括两种策略的互补关系，比罗列方案更显理解 [经验]。
- 被问「为什么不遍历」→ 讲两难（遍历太长 vs 频率难设任务堆积）再落到「抽样成本恒定 O(20)」，展示推导而非结论 [经验]。
- 被问「积压怎么办」→ 先反问「常态积压还是突发批量」，常态调 HZ/dynamic-hz，突发上抖动 + lazyfree，一问一档 [经验]。
- 主动边界到 `1255-expire-deletion-choices.deep`（三方案取舍与主从语义）、`1257-eviction-policies`（内存淘汰另一套）、`709-cron-overlap-recover`（应用层错峰补偿同构思路），构成过期数据全链 [边界]。

## 细节与核心 API

**周期删除两个旋钮（时间维度 HZ × 空间维度抽样）：**

```conf
hz 10            # 默认 100ms/轮，范围 1~500，作者建议 <=100
dynamic-hz yes   # 5.0+ 默认开，实际频率在 [hz/2, 5×hz] 按积压自适应
```

**单轮算法（activeExpireCycle）速记：**

```text
每个 DB 随机抽 20 个带 TTL 的 key
过期比例 > 25% → 立刻再扫一轮（比例驱动加压，期望删除/轮 = 20 × 全局过期比例 p）
<= 25%        → 转下一个 DB / 收手
成本恒定 O(20)，无状态（不维护游标），单轮覆盖率期望仅 20/N
```

**观测与决策：**

```bash
redis-cli INFO stats | grep expired_keys   # 过期删除速率
redis-cli INFO memory                      # 带 TTL key 的积压量
# 先量化确认真积压，再动 HZ；突发大批量过期上 TTL 随机抖动 + lazyfree
```
