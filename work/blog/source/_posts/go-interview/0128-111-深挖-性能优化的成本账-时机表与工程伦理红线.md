> 原文锚点：第 5~30 段「性能优化不一定能降低成本，很多时候还可能会增加成本…重构也可以算是代码性能优化的一种…把握好优化的时机…扁鹊三兄弟…有些程序员在写代码时故意通过 sleep 休眠一段时间，等到后续减少这个 sleep 时间…这种做法肯定是不值得推荐的」
> [边界] 本文只讲**成本账、时机判断表与伦理底线**：如何定位瓶颈见 112、如何讲优化故事见 112、工具链见 113 与 `1114-pprof-overview`，均不重述。

## 思路与架构

把"要不要优化"变成一道**可计算的题**，而不是靠感觉：

```text
优化 ROI = 预期收益 / (实施成本 + 维护成本 + 风险成本)

收益侧（可量化）
  吞吐提升 QPS、延迟 P99 下降、内存/机器数下降、能耗下降、SLA 达标
成本侧（常被低估）
  开发工时、复杂度上升（更难维护）、新引入的组件与运维负担
  回归风险（优化往往动到核心路径）
  机会成本（这段时间本可以做别的需求）

判据：
  ROI > 3  ->  马上做
  ROI 1~3  ->  排进迭代，随需求顺带做
  ROI < 1  ->  不做，写个 ADR 记录"为什么不优化"
```

**一张时机表**（把扁鹊三兄弟翻译成工程动作）：

```text
阶段                   对应扁鹊      该做什么                    不该做什么
──────────────────────────────────────────────────────────────────────
设计/选型              大哥(治未病)  选对数据结构与算法           为"极致性能"过度设计
                                    定下 SLO 与容量模型         把架构设计到完美才开工
编码/Code Review       大哥          挡掉 N+1、循环内分配        微优化单个函数
                                    挡掉明显的锁竞争
提测/压测              二哥(初起)    基准测试 + pprof 定位       凭直觉改代码
                                    针对性优化热点
上线后/有监控          二哥          看 P99/CPU/GC 趋势         等用户投诉才动手
故障/体验受损          扁鹊(重症)    立即定位、止血、复盘        只做止血不复盘
──────────────────────────────────────────────────────────────────────
核心洞察：最高明的是"大哥"——让优化这件事根本不必发生。
```

## 方案取舍

```text
方案 A：设计阶段就把性能做对（治未病）
  + 成本最低，收益最大；复杂度可控
  - 需要经验，且要求"知道瓶颈通常在哪"
  适用：所有项目。选对数据结构/算法 > 事后调优 100 倍

方案 B：先交付、后按数据优化（敏捷默认）
  + 交付快，优化投入有真实数据支撑
  - 可能留下架构级债，后期改动面大
  适用：需求变化快、瓶颈不明确的业务

方案 C：一开始就追求极致性能（反模式）
  + 理论上限最高
  - 交付周期拉长、产出效率降低、复杂度爆炸
  判定：明确不推荐，除非是数据库/中间件这类产品本身

方案 D：等出问题再优化（救火）
  + 不用提前投入
  - 故障成本、口碑损失、时间压力下的低质量改动
  判定：不应作为策略，只能作为兜底
```

**三条伦理红线**（本卡最有价值的部分）：

```text
红线 1：绝不人为制造基线
   典型案例：先故意加 sleep，之后逐步删掉，制造"性能提升 xx%"的假象。
   这是数据造假，不是优化。一经发现，技术信用归零。

红线 2：优化成果必须可复现
   汇报要给出：测试环境、数据量、并发度、命令、前后数字。
   别人照着跑能得出相同结论，才算数。

红线 3：不许只报好消息
   优化常常有副作用（内存换时间、一致性降级、可维护性下降）。
   必须同时说明代价，让决策者完整判断。
```

## 答题技巧

```text
1. 先给成本观，再给方法论（区分度最高）
   「优化不一定降本，很多时候反而增加成本 ——
     所以真正的功夫在判断'值不值得'。」

2. 把"不要过早优化"说成可执行的判据
   「不是'别优化'，是'没有数据就别优化'。
     有实测数字支撑的优化，任何时候都不算早。」

3. 讲扁鹊故事时一定要落到"治未病"
   「大哥最厉害因为治病于发作之前；
     工程上就是设计阶段选对数据结构、review 时挡掉 N+1。
     最高明的优化是让优化不必要。」

4. 主动提 ROI 公式（显得体系化）
   「收益/(实施+维护+风险)；ROI<1 就写 ADR 记录为什么不优化，
     而不是闷头做。」

5. 一定要踩住伦理红线
   「故意加 sleep 再删掉制造提升，这是造假。
     优化成果必须可复现：环境、数据量、命令、前后数字四件套。」

6. 收尾拔高
   「性能优化的成熟度，体现在'能说清楚为什么现在不改它'。」
```

**面试官可能的追问**：

```text
Q：老板只看得到"救火英雄"，怎么办？
A：把"治未病"的成果指标化 —— 例如本季度通过 review 拦截了多少
   性能隐患、P99 趋势是否平稳、机器成本是否下降。
   看不见的贡献，要想办法让它可见，而不是等事故发生。

Q：怎么证明优化真的有效，而不是波动？
A：多轮 benchmark 取中位数，用 benchstat 做统计检验；
   同时看 P99 而不只是平均值；上线后看监控曲线而非单次测试。

Q：优化完怎么防止回退？
A：把关键基准纳入 CI（阈值告警）、把核心指标做成常驻监控、
   并在 PR 模板里要求"是否影响性能"的自查项。
```
