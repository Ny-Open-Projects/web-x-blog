> 原文锚点：第 1~4、34~51 段「第四个特性是它是提交日志的，这个特性指的是新的消息总是以追加的方式进行写入，也就是顺序IO…操作系统每次从磁盘中读写数据的时候，都需要先寻址，也就是先要找到数据在磁盘上的物理位置，然后再进行数据读写…顺序读写相比随机读写省去了大部分的寻址时间，它只需要寻址一次就可以连续地读写下去…Kafka 利用操作系统的页缓存机制，将磁盘中的数据缓存在内存中…调用系统的 API 读写文件的时候，并不是直接去读写磁盘上的文件，应用程序实际操作的是页缓存，也就是文件在内存中的缓存副本」

## 一句话总述
Kafka 高吞吐的存储层靠两条：**①顺序写磁盘**——消息只以**追加**方式写入分区日志尾部（"提交日志"特性），**相比随机读写省去大部分寻址时间**（SSD 快好几倍，**机械磁盘差距达几十倍**）；**②页缓存**——应用程序操作的其实是**文件在内存中的缓存副本**，操作系统用完页缓存**不会立刻清除**而是尽量利用空闲内存保存，消息系统"刚生产就被消费"的特点让页缓存命中率极高。

## 面试官视角
- 考察意图：能否把"Kafka 快"落到**磁盘特性与操作系统机制**上，而不是停在使用层面上。
- 分档：P5 知道 Kafka 顺序写；P6 能说"寻址一次 vs 反复寻址"；P7 能补上**页缓存的三条行为**（不立即回收、尽量利用空闲内存、LRU 淘汰）以及**对 Java 程序避免堆内存 GC 的额外收益**。
- 红旗答案：以为"Kafka 快是因为用了内存"——它其实是**靠磁盘顺序写 + 操作系统页缓存**，自己并不在 JVM 堆里缓存消息。
- 惊艳点：**无论用什么编程语言，调用系统 API 读写文件都不是直接读写磁盘**，应用程序真正操作的一直是**页缓存** `[源码]`。

## 主问答
**Q（面试官原话）：** Kafka 写磁盘为什么还能这么快？

1. **结论**：两条支柱——**顺序写磁盘**（省寻址）与**页缓存**（大部分读写实际在内存中完成）`[源码]`。
2. **顺序 IO 的来源**：Kafka 的特性之一是**提交日志**——**新的消息总是以追加的方式进行写入，也就是顺序 IO**；分区可做到**线性扩展与负载均衡**，副本可做到**故障容错**，而**提交日志是一种高效的写入方式** `[源码]`。
3. **为什么顺序比随机快**：**操作系统每次从磁盘读写数据都要先寻址**，即**先找到数据在磁盘上的物理位置再读写**；**机械硬盘寻址需要移动磁头，这是机械运动**（工作时发出的咔咔声就是移动磁头的声音），耗时较长。因此 **SSD 上顺序读写比随机快好几倍**，**机械磁盘上这个差距会达到几十倍** `[源码]`。
4. **核心机理**：**顺序读写相比随机读写省去了大部分寻址时间，只需要寻址一次就可以连续地读写下去** `[源码]`。
5. **Kafka 怎么用**：**消息按照 topic 与 partition 组织**，**每个 topic 的消息分布在多个 partition 上**，而**这些 partition 又分布在不同节点上**；**每个 partition 对应一个日志文件**，**客户端发来的消息会顺序追加到日志文件的尾部**，**消费的时候也从日志文件的指定位置开始顺序地把消息读出来** `[源码]`。
6. **页缓存的工作方式**：Kafka **利用操作系统的页缓存机制把磁盘中的数据缓存在内存中**；**应用程序写入文件时，操作系统先把数据写入页缓存，再一批一批写到磁盘**；**应用程序用完某一块页缓存后，操作系统并不会立刻清除这块内存，而是尽可能利用空闲物理内存来保存这些缓存**，**除非内存不够才会清理一部分** `[源码]`。
7. **为什么命中率高**：**当消费者读取数据时，如果数据已在页缓存中，就可以直接从内存读取而无需访问磁盘**；**对消息系统而言，刚生产的消息通常在短时间内被消费**，所以**按 LRU 策略，刚写入的页缓存命中几率非常高** `[源码]`。
8. **额外收益**：**直接使用操作系统的页缓存（即堆外内存），对 Java 程序而言还可以避免对堆内存的管理开销** `[源码]`。

**加分层：** 这两条是**叠加关系**——顺序写让每次 I/O 都便宜，页缓存让大部分 I/O 干脆不发生。Kafka 的高吞吐不靠"自己实现一个缓存"，而靠**把缓存交给操作系统**。

## 关键代码
```go
// 用 Go 感受"顺序写"与"随机写"的差距（同一块盘上的写入耗时对比）
package main

import (
	"fmt"
	"os"
	"time"
)

func main() {
	const n = 20000
	const size = 4096
	buf := make([]byte, size)

	// 1) 顺序写：只寻址一次，连续往下写 —— Kafka 分区日志的写入模型
	f1, _ := os.CreateTemp("", "seq")
	t0 := time.Now()
	for i := 0; i < n; i++ {
		f1.Write(buf) // 追加到文件尾部
	}
	fmt.Println("顺序写耗时:", time.Since(t0))

	// 2) 随机写：每次都重新寻址到不同偏移 —— 传统随机落盘模型
	f2, _ := os.CreateTemp("", "rand")
	t1 := time.Now()
	for i := 0; i < n; i++ {
		f2.WriteAt(buf, int64(i*size%n*size)) // 偏移跳来跳去，反复寻址
	}
	fmt.Println("随机写耗时:", time.Since(t1))

	// 3) 写入后 OS 数据仍在页缓存中，消费方紧接着读几乎不碰磁盘
	//    Kafka 依赖的正是这一层的"读多写快的窗口"
	f1.Sync() // 真正刷盘（Kafka 默认不主动调，交给 OS）
}
```

## 总结与追问预判
**最爱追问的是"顺序写这么快，Kafka 为什么还要分区"**——因为**单个 topic 若只对应一个文件，这台机器的 IO 就会成为该 topic 的性能瓶颈**，分区把这个瓶颈打散到多台机器上；再加多副本做容错。**顺序写解决"单盘怎么写最快"，分区解决"怎么横向摊开"**，两者是不同层次。追问常接"那消息会不会丢"——**可靠性不该由同步刷盘保障，而应由多副本机制保障**（见 1417）。
