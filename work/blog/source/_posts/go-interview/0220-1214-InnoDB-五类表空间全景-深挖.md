> 原文锚点：第 1~57 段「五类表空间类型」全景

## 思路与架构
本卡把 InnoDB 的五类表空间按「**共享型 vs 独立型**」与「**版本起点**」两个维度串起 `1214-file-per-table`、`1214-shared-general-tablespace`、`1214-temp-undo-tablespace` 三张主卡，并显式划边界。

- **独立型**：file-per-table（每表 .ibd，默认 ON，删数据回收，单表 64TB）。
- **共享型**：① 系统表空间/共享表空间（IBdata，多表共用，删数据不回收，64TB 共享）；② 通用表空间（5.7+，共享型但内存更省、可挪目录）。
- **辅助型**：③ 临时表空间（5.7.2+，ibtmp 重启重建）；④ undo 表空间（5.6+，默认 2 文件，可 truncate 不可 drop）。

## 方案取舍
| 类型 | 版本起点 | 空间回收 | 关键取舍 |
| --- | --- | --- | --- |
| file-per-table | 默认 | 删即回收 | fd 占用高、fsync 分散 |
| 共享/系统 | 古老 | 不回收只复用 | 64TB 被分摊、省元数据内存 |
| 通用 | 5.7 | 取决于挪动 | 内存更省、可 IO 隔离 |
| 临时 | 5.7.2 | 重启重建 | 存临时表/未提交回滚 |
| undo | 5.6 | truncate | 拆出系统表空间便于运维 |

- 选型主线：默认 file-per-table 够用；要省元数据内存或 IO 隔离用通用；undo 必须独立才能 truncate。

## 答题技巧
- **版本红线**：通用 5.7、临时 5.7.2、undo 5.6——面试官爱问「哪版才有」。
- **回收对比**：file-per-table 删即回收 vs 共享表空间只复用不回收，是经典送分题。
- **undo 陷阱**：可 TRUNCATE 不可 DROP；只有独立于系统表空间才支持 truncate。
- **显式边界**：表空间「定义 + 共享/独立二分 + 系统表空间含双写/更改缓冲/undo」见 1211；8.0 单 .ibd + SDI 布局见 1211；本卡不重画这两张已覆盖的底层，只补「五类类型的优缺点与版本演进」这一真 gap。

## 细节与核心 API

**五类表空间与版本起点**：

```sql
独立型   file-per-table :  CREATE TABLE t(...) /* 默认 innodb_file_per_table=ON，删即回收 */
共享型   系统表空间     :  ibdata1（多表共用，删不回收只复用，64TB 共享）
通用     通用表空间     :  CREATE TABLESPACE ts ADD DATAFILE 'ts.ibd'（5.7+，内存更省/可 IO 隔离）
临时     临时表空间     :  ibtmp1（5.7.2+，重启重建，存临时表/未提交回滚）
undo     undo 表空间    :  undo_001/undo_002（5.6+，默认 2 文件，可 TRUNCATE 不可 DROP）
```

```ini
# 关键配置与版本边界（P7 硬证据）
innodb_file_per_table = ON        # 默认独立 .ibd，删表回收空间
innodb_undo_tablespaces = 2       # 5.6+ 默认 2 个 undo 文件
# 通用 5.7 起 / 临时 5.7.2 起 / undo 独立 5.6 起
```

> 边界：.ibd 内嵌 SDI 见 1211；双写/更改缓冲在系统表空间见 1212；本卡只讲五类表空间优缺点与版本演进。
