> 分类：MySQL/分库分表 | 难度：L3 | 题型：八股题 | 频率：中 | 关键词：**分库分表**/**B+树高度**/**SMO**/**并发**/**负载均衡**

> 原文锚点：第 3~14 段「那第三…分库分表…yeloDB 存储引擎的 b 加树…SMO 全称 structure modification operation…需要受 SMO 影响的节点加锁…限制并发能力…提高并行处理能力…负载均衡」（分库分表提升性能的四大理由：B+树高度/SMO 锁/并行/负载均衡）

## 一句话总述
分库分表之所以能提升查询性能，根源在四点：**单表数据量降 → B+树高度降 → IO 减**；**页分裂/合并（SMO）频率降 → 加锁范围小 → 并发升**；**数据分散 → 多实例并行查询**；**读写负载被打散 → 避免单点瓶颈**。其中「SMO 加锁限制并发」是最常被忽略、也最显深度的动机。

## 面试官视角
这题考「为什么分库分表」的底层机理，而不是背「为了扩容」。考点：① B+树高度与数据量的关系；② **SMO（页分裂/合并）为何要加锁、如何限制并发**——这是高阶分水岭；③ 分库分表的四个收益能否系统列出。能讲清 SMO，直接拉开与只背「分摊压力」的人。

## 主问答
**Q（面试官原话）：** 分库分表为什么能提升数据库性能？具体机制是什么？

**A：**
1. **B+树高度降低，减少 IO**：InnoDB 聚簇索引是 B+树，单表数据量越大树越高（3 层约存千万级、4 层到亿级）。高度 +1 意味着每次索引查找多一次磁盘/缓冲页访问；分表后单表变小，树高回落，查询路径更短。在内存小或机械盘场景，这一项影响极明显。
2. **SMO 频率下降 → 并发能力提升（核心）**：向页插入超过容量会触发**页分裂**、删除使页过空会触发**页合并**，这类**结构修改操作（SMO, Structure Modification Operation）**需要对受影响的索引页（可能向上传播到根）加锁。单表越大、写入越密，SMO 越频繁、加锁范围越广，**直接限制该表的并发写入能力**；分表把数据分散，单表 SMO 频率降低，且不同表可并行做 SMO，整体并发上升。
3. **并行处理能力**：数据分散到多个库/表后，一个分析型查询可拆到各分片**并行执行**，再汇聚结果，吞吐随分片数近似线性提升。
4. **负载均衡**：读写流量被均摊到不同实例/表，避免单一大表成为 CPU、连接数、缓冲池的瓶颈点。

## 版本与兼容性
- SMO/页分裂合并是 InnoDB 通用机制；**MySQL 5.6+ 支持 Online DDL**，很多 DDL 可在线做而不长时间锁全表（见 1221.md`），但**普通 DML 触发的 SMO 加锁仍在**，这才是「写并发受限」的日常来源。
- 分片键（路由键）选择决定并行度与热点：选错会出现「热点分片」，并行收益被抵消。
- 分库分表不是银弹：跨分片 join、分布式事务、全局唯一 ID 都会变复杂，需配合中间件（如 MyCat/ShardingSphere）。

## 关键代码

```sql
-- 按 user_id 取模分 16 个分片：单表变小→B+树高度降、SMO 频率降
-- 查询时按路由键定位分片，多分片可并行执行后汇聚
SELECT * FROM orders_00 WHERE user_id = 100 AND ...
UNION ALL
SELECT * FROM orders_01 WHERE user_id = 100 AND ...
-- ...（应用层/中间件按 user_id % 16 路由，仅打中一个分片时无需 UNION）
-- 全局汇聚示例（跨分片统计）：各分片并行算局部和，应用层求和
SELECT SUM(cnt) FROM (
  SELECT COUNT(*) cnt FROM orders_00 WHERE status=1
  UNION ALL SELECT COUNT(*) FROM orders_01 WHERE status=1
  -- ... 其余分片
) t;
```

## 总结与追问预判
收口：**分库分表 = 降树高(减IO) + 降 SMO(升并发) + 并行查询 + 负载均衡**，其中 SMO 加锁限制并发是最深的一层。预判追问：① SMO 与日常 DDL 锁的区别 → 见 `1221`；② 表结构层更轻量的优化（动静分离，见 1249.md`）；③ 单 SQL 内的降本（小表驱动，见 1249.md`）。回答时把「SMO 加锁会向上传播到根」这句抛出来，是高阶加分。
