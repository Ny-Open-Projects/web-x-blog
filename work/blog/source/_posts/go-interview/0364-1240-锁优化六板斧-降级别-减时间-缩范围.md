## 一句话总述
锁优化的本质是**降低锁竞争概率**：选隔离级别、冲突少换乐观锁、缩短持锁时间、缩小锁范围、大查询分页、合并 SQL。

## 面试官视角
P6 能说「加索引、缩短事务」；P7 要给出**结构化六条**，并指出降隔离级别是双刃剑，会引入脏读与不可重复读。

## 主问答
**Q（面试官原话）：** 线上锁冲突严重，你从哪几个方向优化？

1. **选合适隔离级别**：降低隔离级别可降低锁竞争、提高并发，但可能引入脏读与不可重复读，需按业务权衡 `[源码]`。
2. **冲突少用乐观锁**：无锁设计，只在数据修改时检查并发冲突，减少锁开销 `[源码]`。
3. **缩短持锁时间**：事务中先做不涉锁操作，**加锁操作放最后** `[源码]`。
4. **缩小锁定范围**：避免表锁、优先行锁；WHERE/JOIN 用索引，避免全表扫描 `[源码]`。
5. **分页处理**：大数据量查询改用分页，减少单次锁定数据量 `[源码]`。
6. **优化 SQL**：多个查询合并为一个，减少加锁次数 `[源码]`。

## 关键代码
```sql
-- 1) 按业务需要选择隔离级别（示例：会话级降为读已提交以降低锁竞争）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 2) 乐观锁：以版本号字段做条件更新，避免显式加锁
UPDATE goods
   SET stock = stock - 1, version = version + 1
 WHERE id = 1001 AND version = 7;
-- 影响行数为 0 即表示发生并发冲突，由应用层重试

-- 3) 缩短持锁时间：事务内先做无锁准备操作，最后再执行加锁写入
START TRANSACTION;
SELECT price FROM goods WHERE id = 1001;   -- 不涉锁操作在前
UPDATE goods SET stock = stock - 1 WHERE id = 1001; -- 加锁操作在后
COMMIT;

-- 4) 缩小锁范围：确保 WHERE 条件命中索引，避免全表扫描加锁
EXPLAIN SELECT * FROM orders WHERE user_id = 88 AND status = 1;
```

## 总结与追问预判
**六条本质都是降低锁竞争概率，「加锁操作放事务最后」最易被忽略也最立竿见影**。追问常是「降了隔离级别会不会出问题」——会，需用业务可接受性兜底。死锁与超时配置见同批 1240-deadlock-timeout。
