> 原文锚点：第 1~70 段「为什么需要缓冲池…传统 LRU 的两个缺陷…冷热分区与预读失效」

## 思路与架构

这一节的知识可以拆成**一条主线的两次进化**：先有缓冲池解决"磁盘太慢"，再有冷热分区解决"缓冲池被冲垮"。

**基线：为什么必须有缓冲池。** 数据在磁盘上，每次直接读盘效率极低。于是向操作系统申请一片连续内存，按默认 16KB 切成一个个缓存页，再给每个缓存页配一个**控制块**记录表号、页号、页地址与链表指针。读命中直接取内存，未命中才读盘并把整页载入——注意是**整页**，因为索引只能定位到页、定位不到页内的行，行要靠页目录二次定位。写则先改内存页并标脏，由后台线程异步落盘。

**第一次进化：朴素 LRU 不够用。** 传统 LRU 把新页插在链表头部、从尾部淘汰，热点数据确实能留在表头，但有两个硬伤。其一是**缓冲池污染**：一次大范围扫描会把池里所有页替换出去，即使 SQL 最终只返回一条，执行过程中扫描过的大量页也都进了池，热数据被冲掉后再次访问就是大量磁盘 IO。其二是**预读失效**：为利用局部性而预加载的相邻页，若后续没被访问，反而占住链表前排，把真正的热点挤到尾部被淘汰。

**第二次进化：冷热分区 + 延迟晋升。** 解法不是抛弃 LRU，而是**给新页设观察期**。链表切成 young 与 old 两段，新页插在 old 区头部（即整个链表中后部）；old 区页首次被访问时记录时间戳，只有间隔超过 `innodb_old_blocks_time`（默认 1000 毫秒）的再次访问才晋升到链表头部。短命的扫描页与预读页活不过这一秒，自然被淘汰；真正的热点则稳定留在 young 区。old 区占比由 `innodb_old_blocks_pct` 控制，默认 37，冷区刻意小于热区。再加一条防抖：young 区**前 1/4** 的页被访问时不挪动，只有后 3/4 才移到头部，避免热点页反复搬动链表节点。

这三层的递进关系是回答的骨架：**缓存页解决读写慢 → 链表解决查找慢 → 冷热分区解决淘汰不准**。

## 方案取舍

| 决策 | 选项 | 取舍 |
|---|---|---|
| 淘汰策略 | 朴素 LRU / 冷热分区 | 分区多一次时间判断，换来抗扫描能力 |
| 冷区占比 | 默认 37 / 调小 | 调小让热区更大，但抗冲击余量变薄 |
| 晋升窗口 | 默认 1000ms / 调大 | 调大更严格，真热点晋升也变慢 |
| 缓冲池容量 | 128MB / 60%~80% 内存 | 容量提命中率，但要给系统与其他进程留余量 |
| 实例个数 | 1 / 多实例 | 多实例降锁竞争，池太小时反而浪费 |
| 预读 | 开 / 关 | 顺序扫描受益，随机负载可能只是白白占缓存 |

取舍要点：

- **冷热分区的代价是一次时间比较 + 一次可能的节点搬动**，收益是缓存命中率在扫描型负载下不崩。这是本设计成立的前提。
- **容量与算法不能互相替代。** 池太小，再好的淘汰算法也留不住工作集；池够大，冷区参数就不必过度调优。
- **参数是全局的。** 调 `innodb_old_blocks_pct` 会影响所有查询，混合负载下要按最坏的那个场景配，而不是按平均值。
- **别把默认值当结论。** 37 与 1000ms 是通用起点，扫描型与分析型负载的合适取值往往不同 `[经验]`。

## 答题技巧

1. **按"缓存页 → 链表 → 冷热分区"三层递进开场。** 有骨架比背参数强，也能自然引出为什么要分区。
2. **把"延迟晋升"这四个字说在前面。** 一句话概括机制，再展开参数，听感上是理解而非背诵 `[经验]`。
3. **两个默认值要顺口报出**：old 区 37、时间窗 1000 毫秒；再补 young 区前 1/4 不移动，这是区分度 `[源码]`。
4. **主动区分服务崩溃与系统崩溃的口径**，说明刷盘参数的丢数据边界，体现工程判断而非背书 `[源码]`。
5. **问到调优必给代价。** 调小冷区换来抗冲击变弱，调大日志换来恢复变慢——每提一个优化都补一句它换走了什么 `[经验]`。

## 细节与核心 API

**冷热分区两个默认参数（全局，混合负载需按最坏场景配）：**

```sql
SHOW VARIABLES LIKE 'innodb_old_blocks_pct';    -- 默认 37（冷区占缓冲池比例 %）
SHOW VARIABLES LIKE 'innodb_old_blocks_time';   -- 默认 1000（晋升时间窗，毫秒）

SET GLOBAL innodb_old_blocks_pct  = 37;   -- 冷区刻意小于热区
SET GLOBAL innodb_old_blocks_time = 1000; -- 间隔超过此值才晋升 young 区头
```

**页控制块与延迟晋升判据（简化 Go 模型，对应于 InnoDB buf_block_t）：**

```go
type bufBlock struct {
    tableID      uint32
    pageNo       uint32
    pageAddr     unsafe.Pointer
    prev, next   *bufBlock
    firstAccessTS int64 // 首次访问时间戳（纳秒）
    inYoung      bool   // 是否位于 young 区
}

// 延迟晋升：冷区页间隔 > innodb_old_blocks_time 才移到 young 区头；
// young 区前 1/4 被访问不移动，避免热点页反复搬动链表节点。
func (p *bufPool) maybePromote(blk *bufBlock, now int64) {
    if !blk.inYoung {
        if now-blk.firstAccessTS > int64(1000*time.Millisecond) {
            p.moveToYoungHead(blk)
        }
        return
    }
    if p.youngPos(blk) > p.youngLen/4 { // 仅 young 区后 3/4 才挪动
        p.moveToYoungHead(blk)
    }
}
```

**查看缓冲池命中与晋升状态（定位扫描型污染）：**

```sql
SHOW ENGINE INNODB STATUS\G
-- 关注 BUFFER POOL AND MEMORY 段：
--   youngs/s      —— 晋升到 young 区的速率
--   non-youngs/s  —— 未过时间窗即淘汰的速率（扫描型负载会飙升）
--   Buffer pool hit rate —— 命中率，低于 95% 需警惕容量/污染
```
