## 一句话总述
标准库 `encoding/json` 靠反射、内存分配多、性能差；换 **jsoniter**（用法 100% 兼容、反序列化性能与内存分配大幅优于标准库）、**easyjson**（预编译生成代码最快但结构变更需重编译）、**ffjson**；跨服务调用改 **RPC + protobuf** 也能提性能。

## 面试官视角
- 意图：是否知道标准库 JSON 是性能热点，且有可替换方案。
- 分档：P5 知标准库慢；P6 能说 jsoniter 兼容+快；P7 能讲 easyjson 预编译取舍与 protobuf 适用场景。
- 红旗：以为 JSON 序列化无优化空间，或盲目上 easyjson 不顾维护成本。
- 惊艳点：点出基准差异主要在**反序列化**与**内存分配**——标准库反序列化约 6 次分配，jsoniter 仅 1 次。

## 主问答
**Q（面试官原话）：** Go 里 JSON 序列化怎么优化？
**A：**
1. **标准库瓶颈**：`encoding/json` 依赖反射，序列化/反序列化都产生多次内存分配，性能偏低。
2. **jsoniter**（推荐）：API 与标准库 100% 兼容，反序列化性能明显更优、内存分配更少（标准库反序列化约 6 次分配，jsoniter 约 1 次），迁移成本最低。
3. **easyjson / ffjson**：通过**预编译**为结构体生成序列化代码，省去反射、性能最高；代价是结构变更需重新生成、可读性/维护性差。
4. **protobuf**：跨服务调用若改用 RPC + protobuf，二进制编码比 JSON 文本更小更快，整体序列化性能进一步提升。
