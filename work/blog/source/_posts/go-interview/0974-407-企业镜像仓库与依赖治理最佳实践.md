## 一句话总述
公开平台上的包由个人或组织维护，**tag 有被删除的风险**，直连源码站随时可能拉不到版本；所以企业一般自建 Go 镜像仓库，把内部用到的版本同步进去并做安全审计，而内部开发的公共包不走镜像，直接到企业内部 Git 仓库取。

## 面试官视角
这题区分「用过 Go」和「管过 Go 依赖」。能说出镜像仓库存在的两个理由（**可用性**：防止上游删 tag；**安全性**：拦截有漏洞的版本），并且区分第三方包与内部包的取用路径，就是工程级答案。

## 主问答
**Q（面试官原话）：** 公司的 Go 依赖是怎么管理的？为什么要自建镜像？

1. **可用性风险**：公开平台上的版本 tag 可能被维护者删除，一旦代码直接从源码站拉取，就会面临版本拉不到的风险甚至构建中断。
2. **自建镜像**：企业把内部使用到的第三方包版本全部同步到自己的镜像仓库，构建时从镜像取，摆脱对上游可用性的依赖。
3. **安全审核**：镜像仓库可对同步进来的版本做安全扫描，避免使用存在重大安全漏洞的依赖。
4. **内部包直取**：企业内部开发的公共包一般**不走镜像代理**，直接到企业内部 Git 仓库拉取，配合私有源配置绕过代理与校验。
5. **配套动作**：对外网代理、私有域名、校验策略统一用配置固化，并在 CI 中校验，避免依赖开发者本机环境。

## 关键代码
```go
// Go 侧视角：CI 中校验依赖来源，禁止内部模块被意外指向公网
package main

import (
	"fmt"
	"os/exec"
	"strings"
)

func main() {
	out, _ := exec.Command("go", "list", "-m", "all").Output()
	for _, line := range strings.Split(string(out), "\n") {
		if strings.Contains(line, "corp.example.com") && !strings.Contains(line, "git.corp") {
			fmt.Println("可疑依赖来源:", line)
		}
	}
}
```

## 总结与追问预判
核心：**镜像仓库解决可用性与安全性，内部包直连内部 Git**。追问常拐向「镜像和私有源怎么共存」，备好「第三方走代理、内部域名配私有源」这条分流规则。
