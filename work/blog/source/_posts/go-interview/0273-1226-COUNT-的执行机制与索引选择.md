> 分类：数据库 / MySQL | 难度：L3 | 题型：机制题 | 频率：高 | 关键词：**Server 层计数变量** / **聚簇索引** / **二级索引** / **key_len 最小优先**
> 原文锚点：第 7~40 段「server 层为每条 count 维护变量、循环读 InnoDB 记录；聚簇索引叶子存全字段、二级索引叶子只存主键+字段值、体积小；优先用二级索引、无则主键；多个二级索引选 key_len 最小」

## 一句话总述
`COUNT` 的执行在 **Server 层**循环读 InnoDB 记录、累加"参数非 NULL"的计数。关键优化是**索引选择**：InnoDB 的**二级索引叶子只存主键值+索引字段值**，比聚簇索引（存全字段）体积小，所以 `COUNT(*)`/`COUNT(1)` 有二级索引时**优先扫二级索引**；多个二级索引时选 **key_len 最小**的那个；没有二级索引才退化到聚簇索引（主键）。

## 面试官视角
- 意图：考察能否从"执行机制 + 索引物理结构"解释 `COUNT` 为什么快、为什么选某个索引。
- P6 能讲清"Server 层维护计数变量 + 优先二级索引"；P7 能点出"二级索引叶子只存主键+字段、IO 更小"以及"key_len 最小优先"的细节。
- 红旗：以为 `COUNT(*)` 会扫全表所有列（实际走最小二级索引，只扫索引树）；把"优先二级索引"说成"一定走主键"。
- 惊艳点：结合 1216 InnoDB 数据页 / 1217 MyISAM 布局，说明"聚簇索引 vs 二级索引叶子内容差异"是索引选择的物理根因。

## 主问答
**Q（面试官原话）：** `COUNT(*)` 执行时 MySQL 是怎么统计的？为什么有时走二级索引？
**A：**
1. **结论**：`COUNT` 由 **Server 层**为每条计数维护一个变量，循环向 InnoDB 取记录，参数非 NULL 就 +1，取完返回总数。索引选择上**优先二级索引、无则主键、多二级索引选 key_len 最小**。
2. **机制（Server/存储分层）**：MySQL 分 Server 层和存储引擎层。`COUNT` 的累加逻辑在 Server 层；InnoDB 按 B+ 树存记录，分**聚簇索引**（叶子存完整记录）和**二级索引**（叶子只存主键值 + 索引字段值，不含全字段）。
3. **机制（为什么选二级索引）**：二级索引叶子比聚簇索引**占用空间小**，遍历的 IO 成本更低。因此 `COUNT(*)`/`COUNT(1)` 表上有二级索引时，优化器**优先用二级索引**；没有二级索引才退化到聚簇索引（主键）。
4. **边界（key_len 最小）**：若有多个二级索引，优化器选 **key_len 最小**的（如 `INT` 索引比 `VARCHAR` 索引短）。`COUNT(索引字段)` 也走二级索引，但**还要读字段值判 NULL**，略慢于 `COUNT(*)`/`COUNT(1)`（见 1226）`[经验]`。

## 关键代码
```sql
-- 表 cnt_test1(id 主键, name, age 非索引)；cnt_test2(id 主键, name, age 各有单列索引)
-- 1) 有二级索引时，COUNT(*) 选 key_len 最小的二级索引（age 为 INT，比 name VARCHAR 短）
EXPLAIN SELECT COUNT(*)  FROM cnt_test2; -- key=idx_age
-- 2) 无二级索引时，退化到主键（聚簇索引）
EXPLAIN SELECT COUNT(id) FROM cnt_test1; -- key=PRIMARY
-- 3) COUNT(索引字段) 也走二级索引，但需读字段值判 NULL
EXPLAIN SELECT COUNT(age)  FROM cnt_test2; -- key=idx_age
EXPLAIN SELECT COUNT(name) FROM cnt_test2; -- key=idx_name（key_len 更大的被选去做 name 统计）
```

## 总结与追问预判
- 执行：Server 层循环累加；索引选择：二级索引优先（叶子小）、无则主键、多二级索引用 key_len 最小。
- 预判：性能排序与 MyISAM → 见 1226；InnoDB 页结构 → 见 1216；MyISAM 布局 → 见 1217（不冲突，本卡讲 count 执行机制）。
