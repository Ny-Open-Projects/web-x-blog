> 分类：数据库 / MySQL 存储 | 难度：L4 | 题型：原理题 | 频率：高 | 关键词：**change buffer、insert buffer、非唯一索引、随机读、merge、软删除、purge、innodb_change_buffer_max_size**

> 原文锚点：第 46~77 段「如果要修改的数据不在 buffer pool 当中，就需要先把要更改的数据从磁盘加载到内存中的 buffer pool，然后修改缓存页中的数据再写 redo log，这个过程中会产生一次随机读的操作…对于非唯一普通索引页，如果它的数据不在缓冲池当中，就不会立刻将磁盘上的数据加载到 buffer pool 里面，而仅仅是将数据修改记录到更改缓冲区当中，当后面这个数据被读取的时候，再将数据合并进缓冲池…为什么写缓冲的优化仅仅适用于非唯一普通索引页呢？如果索引页设置了唯一属性，InnoDB 就必须检查数据的唯一性，而唯一性的检查就必须要从磁盘上去读取数据」

## 一句话总述
**更改缓冲区（change buffer）** 是 InnoDB 对**非唯一普通索引页**的写优化：当目标索引页**不在 buffer pool** 时，**不立即从磁盘加载该页**，而是**只把这次修改记录在 change buffer 里**，**等后续该数据被读取时再合并（merge）进 buffer pool**，从而**大幅减少磁盘随机读**。它**只对非唯一索引生效**——**唯一索引必须做唯一性检查，而检查就必须读盘**，这次随机读省不掉。

## 面试官视角
- 考察意图：能否把 change buffer 从"一个缓存"讲成"**用延迟合并换掉随机读**"的机制，并说清**为什么唯一索引不适用**。
- 分档：P5 知道有 insert buffer；P6 能说"5.5 起改名 change buffer、覆盖 delete/update"；P7 能讲清**唯一性检查必须读盘**这一限制，并推出"**更新频繁的字段谨慎加唯一索引**"的工程结论。
- 红旗答案：以为 change buffer 对主键/唯一索引也生效；或以为它能减少写 IO（它减的是**读 IO**）。
- 惊艳点：**change buffer 优化的是"读"而不是"写"**——它把"改之前必须先读进来"这次**随机读**推迟到真正被读时才执行 `[源码]`。

## 主问答
**Q（面试官原话）：** change buffer 是什么？为什么唯一索引用不了？

1. **结论**：change buffer 是**写缓冲/更改缓冲区**，对**不在 buffer pool 中的非唯一普通索引页**，**不立即加载磁盘数据，只把修改记进 change buffer**，**读取时再合并**，`[源码]` 从而减少磁盘随机读。
2. **背景 · 两种修改路径**：
   - **页在 buffer pool 中**：**直接修改缓冲池中的数据页，再写 redo log**，**只需一次内存操作和一次顺序写操作** `[源码]`。
   - **页不在 buffer pool 中**：**需要先把要更改的数据从磁盘加载到内存的缓冲池**，再改缓存页、再写 redo log；这个过程中**会产生一次随机读操作**，外加一次内存操作和一次写 redo log 的顺序磁盘操作 `[源码]`。
3. **机制**：引入更改缓冲区后，对**非唯一普通索引页**，若其数据不在缓冲池中，**就不会立刻将磁盘上的数据加载到缓冲池**，**而仅仅是将这次数据修改记录到更改缓冲区当中**；**当后面这个数据被读取的时候，再将数据合并进缓冲池**，**在很大程度上减少了磁盘的随机读操作**；**写缓冲的数据也会定期刷到系统表空间的文件里面** `[源码]`。
4. **历史演进**：**MySQL 5.5 之前叫插入缓冲（insert buffer），只针对 insert 做优化**；**从 5.5 版本开始，不仅针对 insert，对 delete 和 update 也有效**，这个机制改称**写缓冲 / 更改缓冲区（change buffer）** `[源码]`。
5. **为什么只适用于非唯一普通索引页**：**如果索引页设置了唯一（unique）属性，在进行修改操作时 InnoDB 就必须检查数据的唯一性**；**而唯一性的检查就必须要从磁盘上去读取数据**，**所以对于唯一属性的字段，没办法避免修改和新增数据时这一次随机读操作** `[源码]`。
6. **工程结论**：**对于更新比较频繁的字段，要谨慎加唯一索引**——**加了唯一索引之后，数据的修改效率可能反而更低** `[源码]`。
7. **两个重要配置**：
   - **`innodb_change_buffer_max_size`**：默认值是 **25**，表示**更改缓冲区占整个缓冲池的 25%**；它也有最大空间限制，**最大不能超过缓冲池的 50%**，**设置 50 以上的值没有效果** `[源码]`。
   - **`innodb_change_buffering`**：控制缓冲哪些操作，可选 **inserts（只缓冲插入）、deletes（只缓冲删除）、changes（只缓冲插入和删除）、purges（只缓冲清除）**，以及 **none（不缓冲任何操作，相当于关闭）**；**默认值为 `all`，即缓冲所有操作** `[源码]`。
8. **delete 与 purge 的区别**：**InnoDB 删除数据时，磁盘空间并不会立刻被回收**；为减少磁盘 IO，做法是**先把这条记录标记为删除，也就是修改这条记录的一个字段属性，即常说的软删除**，**然后通过后台的 purge 线程定期进行回收**；**被删除数据部分对应的磁盘空间会被标记为可用，可被后续写入使用，但磁盘文件的大小不会改变** `[源码]`。

**加分层：** change buffer 最适合的负载是**写多读少**——写的时候先记账、读的时候才合并；如果写完之后立刻读，合并马上发生，优化收益就没了。

## 总结与追问预判
**最爱追问的是"change buffer 会不会丢数据"**——不会：修改**同时会写 redo log**，change buffer 本身也会**定期刷到系统表空间**；崩溃后可从 redo 与系统表空间恢复。追问常接"那我是不是该把唯一索引都改成普通索引"——**不行**，唯一性是**业务约束**，不能为了写性能牺牲正确性；正确做法是**在更新频繁的字段上谨慎加唯一索引**，或改用业务层去重 + 普通索引。

## ⚠️ 原文纠错
1. 事实核校：页在缓冲池时只需内存操作 + 顺序写 redo、页不在时需一次随机读、change buffer 只对非唯一普通索引页生效且读取时合并、5.5 前为 insert buffer 且 5.5 起覆盖 delete/update、唯一索引因唯一性检查必须读盘故不适用、更新频繁字段慎加唯一索引、max_size 默认 25 且上限 50、change_buffering 可选四类操作值、delete 为软删除且由后台 purge 线程回收、磁盘文件大小不变——均与 InnoDB 实现一致 `[经验]`。
2. 补充：**原文称 `innodb_change_buffering` 默认值"表示全部不进行缓冲"，自相矛盾**——**默认值为 `all`（缓冲所有操作）**，**none 才是关闭**；且 change buffer **不作用于主键，只作用于非唯一的二级索引页** `[经验]`。
3. 崩坏词归一：源码将 change buffer、insert buffer、buffer pool、唯一索引、软删除、purge、InnoDB 等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
