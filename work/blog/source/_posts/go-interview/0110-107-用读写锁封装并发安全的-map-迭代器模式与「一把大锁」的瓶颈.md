# 107 用读写锁封装并发安全的 map：迭代器模式与"一把大锁"的瓶颈

> 分类：Go 并发 | 难度：中 | 题型：实现题 | 频率：高 | 关键词：**RWMutex、读写锁、读锁、写锁、迭代器、匿名函数、锁粒度**

> 原文锚点：第 1~23 段「map 是非并发安全的，底层有强制校验，并发写导致程序崩溃…结构体两字段(读写锁+map[any]any)…get 读锁/set·delete 写锁…range 入参匿名函数返回 bool，遍历只加读锁…整 map 一把大锁粒度集中」

## 一句话总述
用 **`sync.RWMutex` + 原生 map** 封装并发安全容器：**结构体只有两个字段**（读写锁 + `map[any]any`），**`get` 加读锁、`set`/`delete` 加写锁**，**`range` 用"匿名函数作入参"实现迭代器**（回调返回 `true` 继续、`false` 终止，遍历属读操作故只加读锁）。读锁提升了并发读性能，但**整个 map 仍是一把大锁，粒度过于集中**。一句话背法：**「RWMutex 包原生 map：get 读锁/set·delete 写锁/range 读锁迭代器；但整 map 一把大锁，优化靠分片」**。

## 面试官视角
考官考察能否把"加锁"从会调 `Lock()` 升级为**按操作性质选锁 + 封装成可用 API**。能补上迭代器模式（回调 bool 控制终止）、读锁只用于遍历、以及"一把大锁"瓶颈与分片优化方向，说明成熟；遍历时也加写锁、或不知原生 map 并发写会直接崩溃（底层有强制校验），是红旗。

## 主问答
**Q（面试官原话）：** 怎么用锁实现一个并发安全的 map？

**先铺垫（由浅入深第 1 层）**：原生 map 不是"并发写会数据错乱"，而是**直接崩溃**——它底层有并发写校验，检测到就抛异常。所以并发用 map 第一件事就是加锁。最朴素的做法是整个 map 配一把读写锁，再按操作性质选读锁/写锁。

1. **结论（第 2 层）**：用 `sync.RWMutex` 保护原生 map 并封装操作方法：读加读锁、写与删除加写锁、遍历加读锁并用迭代器回调。
2. **为什么必须做（第 3 层）**：map 非并发安全，底层有强制校验，并发写直接崩溃（非数据错乱）。
3. **结构体（第 4 层）**：只有两个字段——读写锁 + `map[any]any`。
4. **锁选择（第 5 层）**：`get` 读锁；`set`/`delete` 写锁（map 的 delete 也是写）。
5. **range 与迭代器（第 6 层）**：`range` 入参是返回 bool 的匿名函数，遍历是读操作只加读锁；回调返回 true 继续、false 终止——这是 Go 常见迭代器写法。加分层：读写锁只在"读远多于写"时有意义；写占比高直接用 `sync.Mutex` 更省心。整 map 仍是一把大锁，优化靠分片。

## 关键代码
```go
package main

import "sync"

// SafeMap：读写锁 + 原生 map，两个字段即全部状态
type SafeMap struct {
	mu sync.RWMutex
	m  map[any]any
}

func NewSafeMap() *SafeMap { return &SafeMap{m: make(map[any]any)} }

func (s *SafeMap) Get(k any) any { // 读 -> 读锁
	s.mu.RLock()
	defer s.mu.RUnlock()
	return s.m[k]
}

func (s *SafeMap) Set(k, v any) { // 写 -> 写锁
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[k] = v
}

func (s *SafeMap) Delete(k any) { // 删 -> 写锁
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.m, k)
}

// Range：遍历是读操作 -> 只加读锁；匿名函数作迭代器，返回 false 终止
func (s *SafeMap) Range(f func(k, v any) bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	for k, v := range s.m {
		if !f(k, v) {
			return
		}
	}
}

func main() {
	sm := NewSafeMap()
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ { // 并发写：原生 map 会崩，这里安全
		wg.Add(1)
		go func(i int) { defer wg.Done(); sm.Set(i, i) }(i)
	}
	wg.Wait()
	sm.Range(func(k, v any) bool { return true })
}
```

## 总结与追问预判
**背这三句就够**：① **RWMutex 包原生 map：get 读锁、set/delete 写锁、range 读锁+迭代器回调**；② **原生 map 并发写直接崩溃（底层校验），不是数据错乱**；③ **整 map 一把大锁粒度集中，优化靠分片；读多写少才用 RWMutex**。
**预判追问**：
- 「这把大锁怎么优化？」→ 分片，把锁粒度降到分片级（见 107 分片 map）。
- 「还要自己写吗？」→ 多数场景直接用 `sync.Map`（见 922）；自写用于类型安全/自定义遍历。
- 「channel 串行化呢？」→ 并发度恒 1，通常不如分片（见 107 用 channel 串行化）。

## ⚠️ 原文纠错
1. 事实核校：原生 map 非并发安全且底层强制校验、并发写崩溃、结构体两字段、get 读锁/set·delete 写锁、range 匿名函数迭代器且只加读锁、读锁提升并发读但整 map 一把大锁——均与 Go 语义一致。
2. 补充：迭代期间持锁会阻塞所有写；生产实现应先持锁拷贝快照、出锁后再遍历回调（避免回调里做网络 IO 拖慢写入）。
3. 崩坏词归一：源码将读写锁/迭代器/匿名函数/锁粒度等音译为崩坏词；本卡统一为规范术语。
