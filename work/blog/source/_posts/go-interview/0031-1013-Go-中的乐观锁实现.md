> 分类：Go/并发 | 难度：L3 | 题型：设计题 | 频率：中 | 关键词：**乐观锁** / **CAS** / **atomic.CompareAndSwap** / **版本号机制**

> 原文锚点：第 6~26 段「乐观锁两实现：CAS(atomic.CompareAndSwap自旋,冲突多CPU开销大,适合冲突少持锁短) + 版本号机制(加version字段,更新where version=旧值自增)」

## 一句话总述
Go 没有内置"乐观锁"类型，乐观锁靠两种模式实现：**CAS**（用 `sync/atomic` 的 `CompareAndSwap` 自旋重试，冲突多时 CPU 开销大，适合冲突少、持锁短）与**版本号机制**（给数据加 version 字段，更新时 `where version=旧值` 并自增，不一致则失败重试）。二者都是"先改、提交时校验"。一句话背法：**「Go 乐观锁两实现：CAS(atomic.CompareAndSwap 自旋重试，冲突少时优、冲突多 CPU 飙升) + 版本号机制(where version=旧值)；先改后校验」**。

## 面试官视角
这是考察乐观锁在 Go 里落地能力的题，不是背概念。
- **P5**：知道 CAS 是乐观锁。
- **P6**：能写出 `atomic.CompareAndSwap` 自旋循环。
- **P7**：能讲清 CAS 的 CPU 开销缺陷与版本号机制适用场景。
- **红旗**：以为乐观锁在 Go 里有现成类型；CAS 失败后不重试或无限自旋不退出。
- **惊艳点**：点出"CAS 冲突多时一直重试→CPU 飙升"，所以适合冲突少；版本号机制天然适合 DB/有状态存储。

## 主问答
**Q（面试官原话）：** Go 里怎么实现乐观锁？

**先铺垫（由浅入深第 1 层）**："乐观锁"是一种**策略**不是一种类型——它假设冲突很少，于是"先改、提交时再校验版本/值"，校验失败才重试。Go 里把它落地有两套武器。

1. **结论（第 2 层·机制）**：Go 乐观锁两种实现——① **CAS**：`atomic.CompareAndSwapXxx(addr, old, new)` 在 `for` 里自旋，期望值与当前一致才更新、否则重试；② **版本号**：数据带 `version` 字段，更新语句带 `where version=读取时的值` 并 `version+1`，被别人改过则 version 不匹配、更新失败可重试 `[源码]` sync/atomic。
2. **机制（第 3 层·CAS 取舍）**：CAS 是"乐观"的——不先加锁，提交时校验。但**冲突概率大时 CAS 一直失败、不断重试**，空耗 CPU，所以只适合**冲突少、临界区极短**的场景（如计数器）`[实测]`。
3. **边界（第 4 层·版本号）**：版本号机制把"校验"下沉到数据行（DB 或带版本的结构体），适合有持久化/状态的场景；数据库里常 `update ... set status=?, version=version+1 where id=? and version=?` 实现 `[经验]`。
4. **对比（第 5 层）**：冲突多用 CAS 会 CPU 飙升，应退回悲观锁 Mutex；版本号机制天然适合跨请求/DB 场景 `[经验]`。
5. **写法（第 6 层）**：CAS 自旋必须带退出/上限，否则活锁；Go 1.19 起泛型 `atomic.CompareAndSwap` 更顺手 `[源码]`。

## 关键代码
```go
package main

import (
	"fmt"
	"sync/atomic"
)

// 乐观锁实现一：CAS 自旋（冲突少、临界区短时合适）
func incr(addr *int64) {
	for {
		old := atomic.LoadInt64(addr)
		if atomic.CompareAndSwapInt64(addr, old, old+1) {
			return // 期望值未变才更新成功，否则重试
		}
		// 冲突多时这里会一直重试 → CPU 开销大
	}
}

func main() {
	var counter int64
	for i := 0; i < 100; i++ {
		incr(&counter)
	}
	fmt.Println("cas counter =", counter) // 100

	// 乐观锁实现二：版本号机制（伪 SQL，适合 DB/有状态场景）
	// UPDATE t SET status=?, version=version+1 WHERE id=? AND version=?
	// version 不匹配 → 影响行数 0 → 业务重试
}
```

## 总结与追问预判
**背这三句就够**：① **Go 乐观锁=CAS(atomic) + 版本号**；② **CAS 自旋重试，冲突少时优、冲突多 CPU 飙升**；③ **版本号适合 DB/有状态场景**。
**预判追问**：
- 「CAS 和 Mutex 怎么取舍？」→ 冲突少用 CAS，冲突多/长用 Mutex（见 105）。
- 「悲观锁是什么？」→ 先加锁再改，见 1013 Mutex 悲观锁。
- 「CAS 死循环风险？」→ 必须带重试上限，否则活锁。
