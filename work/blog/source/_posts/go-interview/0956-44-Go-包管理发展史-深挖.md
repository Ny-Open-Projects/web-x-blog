> 原文锚点：第 1~115 段「Go 包管理的方式有哪些（一）全貌」

## 思路与架构
Go 包管理的核心矛盾是「依赖版本控制」：
1. **GOPATH 阶段（无版本）**：全局 src 平铺，导入路径即身份，无法并存多版本——这是所有痛点的根源。
2. **社区阶段（补版本）**：godep 用 workspace 快照、glide 用 lock 文件、govendor 用 vendor 目录——各自用不同手段给 GOPATH 补上「版本锚点」。
3. **Modules 阶段（终局）**：以 go.mod 声明语义化版本、go.sum 做内容哈希校验，彻底脱离 GOPATH 全局约束，支持多版本并存与可复现构建。

## 方案取舍
- **GOPATH vs Modules**：GOPATH 简单但无版本、必须放 src 下；Modules 有版本/可复现，但引入 proxy/校验等复杂度。
- **godep 快照 vs glide 声明式**：快照笨重但直观；声明式更贴合现代包管理，但需维护 yaml/lock 两份。
- **govendor vendor 目录 vs Modules vendor/**：govendor 把依赖拷进工程、CICD 快但冗余；Modules 用 cache + go.sum，按需拉取，更省空间。
- **GO111MODULE=auto/on/off**：迁移期用 auto 平滑过渡；新项目直接 on（1.16+ 已不可关 off）。

## 答题技巧
- 答「Go 包管理」用**时间线法**：2009 GOPATH → 2013 godep → 2014 glide → 2015 govendor → 2018 Modules，年份一抛就显功底。
- 必点「GOPATH 无版本控制」这个根本缺陷，再讲社区怎么补、Modules 怎么根治。
- 被追问细节时，主动区分 GOPATH 模式（管理方式）与 GOPATH 路径（环境变量值）两个概念。
- 收尾补一句「Modules 用 go.sum 哈希校验防篡改、支持多版本并存」——这是区分 P6/P7 的关键。

## 细节与核心 API

```bash
go mod init example.com/app     # 初始化 go.mod
go mod tidy                      # 增删依赖，使 go.mod/go.sum 与代码一致
go get github.com/gin-gonic/gin@v1.9.1   # 加/升级指定版本
go mod download                  # 下载到模块缓存（GOMODCACHE）
go mod verify                    # 校验已下载模块未被篡改（对照 go.sum）
go list -m all                   # 查看依赖树与版本
go list -u -m all                # 查看可升级版本
# 锁文件：go.mod（声明） + go.sum（哈希校验）；CI 用 -mod=readonly 防意外变更
# 可重现构建：go.sum 提交仓库；GOFLAGS=-mod=mod 才允许自动改
# vendor：go mod vendor 把依赖打入 vendor/（离线/审计场景）
```
