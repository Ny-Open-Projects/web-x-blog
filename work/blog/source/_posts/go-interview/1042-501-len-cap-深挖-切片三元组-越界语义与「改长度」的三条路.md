# 501 len/cap 深挖：切片三元组、越界语义与"改长度"的三条路

> 深挖卡：从「哪些类型能用 len/cap」推进到「len 与 cap 到底描述谁」以及修改它们的三种手段与风险。

## 思路与架构

切片的 len/cap 不是切片自己的属性，而是**头部三元组**（`SliceHeader`）里两个字段对外呈现的视图：

```text
type SliceHeader struct {          // 24 字节（64 位）
    Data uintptr  // 指向底层数组首个可访问元素
    Len  int      // 可访问元素个数  → len(s)
    Cap  int      // 从 Data 起底层数组剩余容量 → cap(s)
}

底层数组  [_ _ _ _ _ _]   cap=6
           ↑
          Data
s := make([]int, 1, 6)  →  len=1 cap=6   可见 [_]
s = s[:4]               →  len=4 cap=6   可见 [_ _ _ _]  合法（上限是 cap）
s = s[:8]               →  panic: slice bounds out of range [:8] with capacity 6
```

三条铁律：

1. **`len` 是安全边界，`cap` 是可扩展余量**。索引 `s[i]` 受 `len` 约束（`i >= len` 即 panic），切片表达式 `s[i:j]` 的上界受 `cap` 约束（`j <= cap` 才合法）。**这就是为什么 `s = s[:cap(s)]` 是合法的"撑满"写法，而 `s[0]` 在 `len=0` 时 panic。**
2. **共享底层数组 = 修改互相可见**。`s2 := s1[2:4]` 后改 `s2[0]` 等于改 `s1[2]`；`append` 时若 `len < cap` 会**原地写入**覆盖后面元素，若 `len == cap` 才分配新数组（此时两者分道扬镳）。这条是 Go 切片最经典的坑。
3. **len/cap 只能"缩小视图"，不能"凭空增大"**。想让 `len` 变大只有三条路：`append`（安全）、`s[:n]` 在 cap 范围内重切（安全）、`reflect.SetLen` / `unsafe.Slice`（**绕过保护，危险**）。

## 方案取舍

| 目标 | 手段 | 是否安全 | 代价 / 风险 |
|---|---|---|---|
| 只想要前 n 个元素 | `s = s[:n]`（n ≤ len） | 安全 | 底层数组仍被引用，可能拖住大内存不释放 |
| 想撑到 cap | `s = s[:cap(s)]` | 安全（语法允许） | 读到的后半段是"旧值/零值"，语义上通常无意义 |
| 断开与原数组的共享 | `s = s[:n:n]`（三索引切片） | 安全 | 把新切片 cap 锁成 n，后续 append 必分配新数组 |
| 缩容释放内存 | `s = append([]T(nil), s...)` | 安全 | 一次拷贝，换来原数组可被 GC |
| 预分配避免扩容 | `make([]T, 0, n)` | 安全 | 一次分配，后续 append 不搬迁 |
| 正规调 cap | `slices.Clip` / `slices.Grow`（Go 1.21+） | 安全 | 标准库封装，推荐 |
| 反射改 len/cap | `reflect.Value.SetLen/SetCap` | **不安全** | 越过 append 的写入语义，`SetCap` 越界 panic |
| unsafe 重制 | `unsafe.Slice(data, n)` | **极不安全** | 完全绕过边界检查，越界直接踩邻居内存 |

取舍原则：**凡是需要"改 len/cap"的需求，99% 应该用 `append` 或 `s[:n]` 表达**；反射与 unsafe 那两条路只在极少数零拷贝场景（如 mmap 出来的大块内存、网络包解析）由标准库或成熟库内部使用，业务代码一律禁止。

## 答题技巧

1. **把 len/cap 讲成"视图 vs 余量"，不要讲成"长度和容量"**：视图决定你现在**能看**多少，余量决定你**不用搬**还能长多少。这个表述一旦给出，后面所有边界问题都能自洽推导。
2. **主动报三索引切片 `s[low:high:max]`**：这是"改 cap"的唯一语法级手段，很多人不知道它能把 cap 锁死从而**切断共享**，答出来立刻拉开差距。
3. **unsafe 那条路要同时给出反例**：`unsafe.Slice(unsafe.SliceData(s), 6)` 把 `len` 从 1 改成 6 后，`s[3]` 读到的可能是别的对象的内存，写进去就是数据破坏——**说得出"能给数字但生产不能用"，比只会背 API 强**。
4. **把 string 的 len 争议一次讲清**：`len` 是字节数、`utf8.RuneCountInString` 才是字符数、转 `[]rune` 有 O(n) 拷贝所以只适合一次性统计。**三句话覆盖全部追问**。
5. **带版本栅栏**：`unsafe.Slice` / `unsafe.SliceData` 是 Go 1.17+（SliceData 是 1.20+）；`slices` 包的 `Clip` / `Grow` 是 Go 1.21+。老项目只能手写 `make` + `copy`。

## 细节与核心 API

```go
s := []int{1, 2, 3}
fmt.Println(len(s), cap(s))   // 3 3
a := [4]int{1, 2, 3, 4}
fmt.Println(len(a), cap(a))   // 4 4（数组 len==cap）
m := map[string]int{"a": 1}
fmt.Println(len(m))           // 1（map 无 cap）
ch := make(chan int, 2)
fmt.Println(cap(ch))          // 2（仅 slice/array/chan 有 cap）
// len 是 O(1) 读取描述符字段；nil slice len==0；nil map len==0 可安全读
var ns []int
fmt.Println(len(ns), ns == nil) // 0 true
```
