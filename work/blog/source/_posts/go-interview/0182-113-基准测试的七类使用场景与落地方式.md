> 原文锚点：第 5~17 段「基准测试的七类使用场景」

## 一句话总述
基准测试的典型场景有七类：优化度量、库与框架选型、硬件调优、算法比较、集成到 CI 防止性能回退、迭代开发中做回归、以及模拟不同负载做容量规划——核心都是**用可复现的数字替代拍脑袋的判断**。

## 面试官视角
考官不只想听清单，更想听「你怎么用」。能说出 CI 里跑基准的**现实坑**（共享机器噪声大、要固定机型取中位数设阈值），比列七个名词有说服力得多。

## 主问答
**Q（面试官原话）：** 基准测试一般用在哪些场景？

1. **性能优化**：度量和比较不同实现的性能，定位代码中的性能瓶颈并尝试不同优化策略，用数据判断优化是否有效。
2. **库与框架选型**：选型时通过运行基准比较不同库或框架的性能，选择更优者，避免只看文档和口碑。
3. **硬件调优**：在不同硬件平台上运行同一套基准，判断哪些硬件配置对系统性能影响更大，指导硬件选型。
4. **算法比较**：对完成同一任务的不同算法跑基准，选出最适合特定问题规模的算法。
5. **CI 与迭代**：集成到持续集成流程，确保提交不引入性能下降；迭代期定期运行，在开发早期发现潜在问题。

## 关键代码

package demo

import (
	"strconv"
	"testing"
)

// 同一任务的两种实现，用基准决定选哪个
func concatPlus(n int) string {
	s := ""
	for i := 0; i < n; i++ {
		s += strconv.Itoa(i)
	}
	return s
}

func BenchmarkConcat(b *testing.B) {
	for i := 0; i < b.N; i++ {
		_ = concatPlus(100)
	}
}

## 总结与追问预判
核心：**七类场景归根到底是「用数字决策」**。追问常拐向「CI 上怎么判定性能回退」，备好「固定机器 + 多次取中位数 + 设阈值告警」这条落地方案。

## ⚠️ 原文纠错
1. 事实核校： [经验] 原文把「负载测试」也归入基准测试场景——需澄清边界：基准测试测的是**单个代码路径的稳定开销与吞吐**，负载/压力测试面向**整体系统在特定并发下的表现**；后者应使用专门的压测工具，基准只能做粗粒度预测。
2. 事实核校： [经验] 原文建议「每次 CI 构建都运行基准测试」——方向正确，但共享 CI 机器上结果噪声很大；工程实践是**固定机型、多轮取中位数、设置阈值告警**，而不是用单次结果直接判红。
3. 崩坏词归一：源码将基准测试 / 持续集成 / 负载 等音译为多组崩坏词，本卡统一为规范术语。
