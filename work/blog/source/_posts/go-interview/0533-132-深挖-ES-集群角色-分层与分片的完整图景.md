> 分类：Elasticsearch | 难度：L4 | 题型：架构题 | 频率：高 | 关键词：**角色隔离、数据分层、分片分配、副本提升、容量规划**

> 原文锚点：第 6~97 段「集群由多个节点构成…节点角色…分片分配…副本升级为主」

## 思路与架构

理解 ES 集群，可以按**三层递进**建立模型：节点角色 → 数据分层 → 分片分布。每一层解决一个不同量级的问题。

**第一层：角色划分解决职责与资源问题。** 集群由多个节点构成，自动选出一个主节点负责管理与协调——创建删除索引、分片分配、配置变更。其余角色各司其职：数据节点存数据并处理读写与聚合；协调节点只做路由与结果汇总、不存数据；摄取节点在写入前做预处理；机器学习节点跑相关模块。角色隔离的意义有两条：**按任务特点配硬件**，以及**避免相互抢占**。所以生产上建议一台机器只跑一个实例，大型集群还会单独部署协调节点作为业务连接入口。

这里有个高频误区：配置里打开主节点角色，得到的只是**候选资格**，不是任命。谁是主节点由集群启动后的投票决定，而集群中**有且只有一个**。看监控时也一样，角色列里的字母只表示"有资格"，要看主节点列的星号才知道现任是谁。

**第二层：数据分层解决成本问题。** 数据有强时效性——越近生成的数据访问频率越高，日志类尤其典型。用同一套高配硬件承载冷数据，是纯粹的浪费。于是数据节点再切成五档：热（最近写入、访问最高）、温（较高但次之）、冷（很少访问或已过期）、冻结（几乎不访问、可压缩放归档）、内容（全文检索业务数据）。硬件随档递减：热层高速固态加大内存 CPU，冷层低速磁盘少量资源，冻结层甚至可以放网络存储、查询前先解压加载。

**第三层：分片分布解决可用性与扩展问题。** 索引由主分片与副本分片构成，总分片数 = 主分片数 ×（1 + 副本数）。分配上有一条硬约束：**同一分片的副本绝不与它的主分片落在同一节点**。理由是反证式的——若同节点，该节点宕机后主副本同时丢失，容灾能力归零。写入路径是先落主分片、再同步副本；副本既能提升读吞吐，也能在主分片故障时自动升主。

副本上位有两条自动路径（节点宕机失联、集群重平衡）与一条手动路径（集群路由 API 强制分配）。兜底规则是：若所有副本都不如原主完整，ES **默认拒绝**提升不完整的副本，因为那等于主动丢数据；确需强升必须显式声明接受数据丢失。

## 方案取舍

| 决策点 | 选项 | 取舍 |
|---|---|---|
| 节点部署 | 单机多实例 vs 单实例 | 生产选单实例，避免故障域耦合与资源争抢 |
| 角色配置 | 全角色 vs 专用角色 | 小集群可全角色，大集群必须拆 |
| 硬件投入 | 统一高配 vs 分层配置 | 有时效性数据必选分层，冷数据下沉即省钱 |
| 副本数 | 0 / 1 / 多 | 0 无容灾；1 是常规起点；多副本换读吞吐 |
| 强制升主 | 拒绝 vs 接受丢失 | 默认拒绝；强升是最后手段且要留痕 |

取舍要点：

- **角色隔离不是形式主义。** 它的收益体现在故障域与硬件匹配上，是容量规划的前置动作。
- **分层的前提是认清访问模式。** 没有时效性的数据强行分层只会增加运维复杂度。
- **副本数决定容灾级别，主分片数决定写入并行度。** 前者可动态调整，后者建索引后不可改——这是规划期最容易埋雷的地方。
- **默认拒绝不完整副本上位，是保护而非缺陷。** 面试里把它讲成"集群很保守"，不如讲成"它把数据丢失的决策权交还给人"。

## 答题技巧

1. **用三层模型开场。** "角色、分层、分片"这三个词一出口，回答的骨架就立住了，比散点罗列强得多。
2. **抢答候选与主节点的区别。** 主动区分"资格"与"结果"、"角色列"与"主节点列"，是这章最值钱的区分度。
3. **报数字。** 三主一副本等于六个分片，这种实算能立刻建立可信度 `[经验]`。
4. **纠正缩写误记。** 角色缩写里"机器学习"与"远程连接"两个字母常被记反，答对这一处很加分 `[源码]`。
5. **落到运维动作。** 提一句用 `_cat/nodes` 和 `_cat/shards` 做核验，比纯讲理论更像做过线上 `[经验]`。

## 细节与核心 API

**角色配置与核验（es 角色列表，l=机器学习 r=远程连接，勿记反）：**

```yaml
# elasticsearch.yml
node.roles: [ master, data_hot, data_warm, ingest ]  # 候选主节点只是"资格"，选举后才有且只有一个主
# 生产：一台机器只跑一个实例；大集群单独部署协调节点作连接入口
```

```bash
GET _cat/nodes?v&h=name,node.role,master   # 主节点列星号才是现任，角色列只表资格
GET _cat/shards/idx?v                      # 核验分片分配
```

**总分片数 = 主分片数 × (1 + 副本数)；同分片主副不落同节点：**

```json
PUT /idx { "settings": { "number_of_shards": 3, "number_of_replicas": 1 } }  // 共 6 个分片
// 强制升主（接受数据丢失才用，默认拒绝不完整副本上位）
POST /_cluster/reroute?retry_failed
{
  "commands": [ { "allocate_stale_primary": { "index": "idx", "shard": 0, "node": "node-x", "accept_data_loss": true } } ]
}
```
