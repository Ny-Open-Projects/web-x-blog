> 分类：消息队列 / Kafka | 难度：L4 | 题型：配置题 | 频率：高 | 关键词：**Version、MaxMessageBytes、message.max.bytes、重试、LZ4、压缩**

> 原文锚点：第 17~25 段「需要设置一个客户端的版本号，这个版本号需要跟服务端的版本号一致…虽然不一致也可以使用，但在某些情况下可能会出现问题或者影响生产或消费的性能…配置的这个参数要比 broker 端配置的 message.max.bytes 要小，我们这个配置才会生效…压缩的配置我们使用的是压缩率比较高的 LZ4…性能表现上 LZ4 是最高的，而压缩比是 zstd 最高，其次是 LZ4，所以综合考虑 LZ4 的性价比最高」

## 一句话总述
Kafka 生产者配置的三个高频坑：**客户端 Version 必须与服务端对齐**、**MaxMessageBytes 必须小于 broker 的 message.max.bytes 才生效**、**压缩算法综合性价比首选 LZ4**。

## 面试官视角
P6 知道要配 broker 地址；P7 必须说清这三个参数的**生效条件与因果**——版本号不一致「能用但不保证」、消息上限是「小于等于才生效」、压缩是「吞吐与压缩比的权衡」，并给出具体数字判据。

## 主问答
**Q（面试官原话）：** Kafka 生产者有哪些配置是你一定会显式设置的？

1. **客户端版本号（Version）**：应与**服务端 Kafka 版本号保持一致** `[源码]`。
2. **不对齐的后果**：版本号不一致虽然仍可使用，但**某些情况下会出现问题，或影响生产/消费性能** `[源码]`。
3. **网络超时**：需显式配置网络超时相关参数，避免默认超时在跨机房场景下过短 `[源码]`。
4. **重试策略**：配置**重试间隔时间与最大重试次数**，应对瞬时抖动 `[源码]`。
5. **单条消息上限（MaxMessageBytes）**：必须**小于 broker 端 message.max.bytes**，否则该配置不生效 `[源码]`。
6. **压缩算法**：可选 LZ4 与 zstd 等；**性能（吞吐）上 LZ4 最高**，**压缩比是 zstd 最高、其次 LZ4** `[源码]`。
7. **综合结论**：考虑吞吐与压缩比的平衡，**LZ4 性价比最高，通常选 LZ4** `[源码]`。
8. **Acks 与 Partitioner**：与可靠性、分区路由相关，应按业务语义配置 `[源码]`。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Kafka 全版本 | Version 需显式指定 | 与 broker 版本对齐 |
| 全版本 | 消息大小双端约束 | 客户端 ≤ broker |
| 各版本支持不同 | 压缩算法可用性 | LZ4 广泛支持，zstd 需较新版本 |
| 长期有效 | 吞吐 vs 压缩比 | 综合选 LZ4 |

## 关键代码
```go
package main

import (
	"time"

	"github.com/IBM/sarama"
)

func newConfig(brokerVersion string) *sarama.Config {
	cfg := sarama.NewConfig()

	// 1) 客户端版本必须与服务端一致，否则某些特性与性能表现不可预期
	v, err := sarama.ParseKafkaVersion(brokerVersion) // 如 "3.6.0"
	if err != nil {
		panic(err)
	}
	cfg.Version = v

	// 2) 网络超时
	cfg.Net.DialTimeout = 10 * time.Second
	cfg.Net.WriteTimeout = 10 * time.Second
	cfg.Net.ReadTimeout = 10 * time.Second

	// 3) 重试：间隔 + 最大次数
	cfg.Producer.Retry.Max = 3
	cfg.Producer.Retry.Backoff = 100 * time.Millisecond

	// 4) 单条消息上限：必须小于 broker 端 message.max.bytes，本配置才生效
	cfg.Producer.MaxMessageBytes = 1000000 // 例：broker 配 1048588，此处取更小值

	// 5) 压缩：综合吞吐与压缩比，LZ4 性价比最高
	cfg.Producer.Compression = sarama.CompressionLZ4

	// 6) 可靠性与分区路由
	cfg.Producer.RequiredAcks = sarama.WaitForAll
	cfg.Producer.Partitioner = sarama.NewHashPartitioner
	cfg.Producer.Return.Successes = true // 同步发送必须开启

	return cfg
}
```

## 总结与追问预判
**三个参数的共同点：都不是「配了就生效」，都有生效前提**（版本对齐、小于等于 broker、算法版本支持）。面试官爱追问「为什么配了 MaxMessageBytes 还是报消息过大」——答案就是它大于了 broker 端的 `message.max.bytes`。重连机制见同批 1420-producer-reconnect。

## ⚠️ 原文纠错
1. 事实核校：版本需与服务端一致、不一致可能影响性能、MaxMessageBytes 需小于 broker 端配置才生效、LZ4 吞吐最高、zstd 压缩比最高、综合选 LZ4——均与 Kafka 官方与 sarama 文档一致 `[经验]`。
2. 补充：原文说「生产者参数要比 broker 小才生效」是准确的，应理解为**两道防线**——客户端先拦一道（快速失败省网络），broker 再拦一道（兜底），两者取小者实际生效 `[经验]`。
3. 崩坏词归一：源码将 Kafka、broker、版本号、压缩算法名等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
