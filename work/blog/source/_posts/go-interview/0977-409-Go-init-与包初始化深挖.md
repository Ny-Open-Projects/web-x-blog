## 思路与架构
把初始化想成**「一张有向图的一次后序遍历」**，所有顺序问题都能推导出来：

- **图的构成**：节点是包，边是 import 关系（A → B 表示 A 依赖 B）。
- **遍历规则**：对 import 图做**深度优先后序遍历**——先递归处理所有依赖，依赖全部就绪后，才处理当前节点自己。
- **单节点内部顺序**：`常量 → 包级变量（按依赖顺序求值）→ init 函数（同文件按定义序、跨文件按文件名序）`。
- **全局收尾**：全图遍历完成（所有包 init 执行完）→ main 包的 init → main 函数。

记住这四层，**任何依赖图都能手排出顺序**，不需要背「最后被依赖最先初始化」这类容易记反的口诀。同时记住两条不变式：**每个包只初始化一次**（图遍历天然去重）、**全部在同一个 goroutine 串行**（没有并发初始化这回事）。

## 方案取舍
- **用 init 隐式注册 vs 显式初始化函数**：init 里做注册（如数据库驱动、插件）简洁、调用方无感，代价是**副作用不可见、无法传参、无法返回错误**。库代码适合隐式注册，业务代码更推荐显式初始化并显式传依赖。
- **init 里做外部 I/O vs 启动后做**：init 无法返回 error，连接失败只能 panic 或静默失败，且会拖慢启动、测试时被强制触发。**规则：init 只做纯内存副作用，外部连接交给显式初始化。**
- **依赖文件名顺序 vs 显式排序**：依赖文件名字典序的隐式顺序非常脆弱（换构建方式、换文件名就变）。**需要先后时，在同一个 init 内显式按序调用**，把隐式约定变成显式代码。
- **包级变量初始化 vs init 里赋值**：包级变量初始化表达式在 init 之前执行，适合无副作用的计算；需要多行逻辑、错误处理或依赖其他包的运行时状态时，放进 init 更清晰。
- **懒加载 vs init 预加载**：init 预加载省去首次调用的延迟，但无论用不用都要付出代价；懒加载（`sync.Once`）把成本推迟到真正需要时，也更容易处理错误。

## 答题技巧
- **开口给模型**：「把 import 关系看成有向图，按深度优先后序遍历」——一句话胜过背五条规则。
- **背下四个字：变 → init**：单包内部永远是「变量 → init」，很多人会答反，这一句是分水岭。
- **主动纠正诱导题**：考官常问「包级变量和 init 谁先」，答案**变量先**；若变量初始化表达式依赖了另一个包，那个包必须已经完整初始化完。
- **说出两条不变式**：「每个包只初始化一次」「全部在同一 goroutine 串行」——第二条能自然推出「init 阻塞会卡死启动」，是加分推论。
- **收尾给工程建议**：init 只做纯内存副作用，外部连接用显式初始化并显式传依赖；需要先后顺序就在同一个 init 里显式调用。这样既展示语言功底，也展示工程判断。

## 细节与核心 API

```go
// 初始化顺序（重要，面试常问）：
// 1) 依赖包先初始化（被 import 的包，递归；每个包只初始化一次）
// 2) 包内：先按依赖顺序初始化包级变量（含依赖包的变量），再执行 init()
// 3) 一个包可有多个 init()，按文件名字典序、文件内出现顺序执行
// 4) 最后 main 包的变量 -> main.init -> main()
var x = compute()         // 包级变量初始化先于 init
func init() { fmt.Println("init") }
// 用途：注册驱动/校验配置/建连接池（如 sql.Register、prometheus 注册）
// 陷阱：
//  - init 无法传参、无法控制时机、（panic 即崩溃进程）
//  - 循环 import 编译报错；init 副作用难测试（建议重资源放懒加载，见 init 懒加载卡）
//  - 包级变量初始化 panic 不会执行 init，顺序问题难排查
```
