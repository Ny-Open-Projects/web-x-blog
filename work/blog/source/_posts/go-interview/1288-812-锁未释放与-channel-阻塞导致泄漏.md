> 分类：Go 并发 | 难度：L3 | 题型：八股题 | 频率：中 | 关键词：**互斥锁**/**channel 阻塞**/**nil channel**
> 原文锚点：第 77~92 段「没正确释放锁…向未初始化/已关闭 channel 收发」

## 一句话总述
两类"**阻塞型**"泄漏：① 互斥锁拿了不释放，其他协程永久拿锁阻塞；② 向**未初始化（nil）或已关闭的 channel** 收发，协程永久阻塞——被阻塞的协程及其引用对象都无法回收。

## 面试官视角
- 考察意图：是否区分"内存泄漏"与"协程阻塞泄漏"的同一根因——协程卡死。
- 分档：P5 知锁要 Unlock；P6 知 nil channel 收发永久阻塞；P7 能讲 defer Unlock 与 channel 生命周期管理。
- 红旗答案：以为 channel 发了就完事、不清楚 nil channel 读写的特殊性。
- 惊艳点：指出 **nil channel 的收发操作永远阻塞**（select 中可用作"关闭分支"技巧）`[经验]`。

## 主问答
**Q（面试官原话）：** 锁和 channel 使用不当也会泄漏？怎么理解？
**A：**
1. **结论**：锁未释放→等待锁的协程永久阻塞；向 nil/已关闭 channel 收发→协程永久阻塞；两者都让协程卡死、内存泄漏。
2. **机制**：锁场景中，若持锁协程在 Unlock 前 panic 或逻辑跳过，后续所有 `Lock()` 者排队阻塞；若持锁前还把大对象载入内存，堆积数据会撑爆。channel 场景中，`make(chan T)` 才是有效 channel，**没 make 的是 nil channel，读写永远阻塞**。
3. **边界**：`defer mu.Unlock()` 确保解锁；channel 关闭后**不能再向它发送**（会 panic），但可继续接收（读到零值+ok=false）。

**加分层：** 用 `select` + `default` 或 `time.After` 给 channel 操作加超时，避免永久阻塞。

## 关键代码
```go
// ① 锁未释放 → 后续 Lock 永久阻塞
mu.Lock()
// 缺少 defer mu.Unlock()，异常路径跳过 → 死锁式泄漏
doWork() // 若此处 panic，锁永远不释放

// ② nil channel 收发永久阻塞
var ch chan int      // 未 make，是 nil
ch <- 1              // 永远阻塞（编译通过，运行卡死）
<-ch                 // 同样永远阻塞

// 正确：用 select + 超时避免永久阻塞
select {
case ch <- 1:
case <-time.After(time.Second):
    // 超时退出，不卡死
}
```

## 总结与追问预判
锁与 channel 的"阻塞"本质是协程卡死，和 goroutine 泄漏同源。防御：`defer Unlock`、正确初始化 channel、收发加超时。追问接"goroutine 泄漏"与"cgo 泄漏"。

## ⚠️ 原文纠错
1. 机翻崩坏词归一：`复释锁锁/复释锁`→**互斥锁（mutex）**；`过入/购入进`→**goroutine（协程）**；`deffor循环`→**for 循环**；`maate`→**make**（channel 初始化）。事实正确，仅术语崩坏，本卡已归一 `[经验]`。
2. 原文"向未正确初始化或已关闭的 channel 收发会阻塞"——准确：未初始化即 nil channel，收发永久阻塞；已关闭 channel 发送会 panic（原文未细拆"关闭后发送 panic、接收得零值"，本卡已补全这一精度点）。
