> 原文锚点：第 5~28 段、第 65~77 段「user2/user3 联合索引顺序不同、非前缀 LIKE 仍走索引、顺序无关」

## 一句话总述
对联合索引做非前缀 LIKE 时，若查询「只取联合索引包含的列」，同样满足覆盖，优化器会遍历二级索引树（type=index），此时**列顺序无关紧要**——因为反正要全扫整棵二级索引树，左前缀原则不再起作用。user2（age+name）与 user3（name+age）两类顺序下，非前缀 LIKE 都能用到索引。但若查全部字段（含非索引列），需回表，优化器改扫聚簇索引。

## 面试官视角
这是「覆盖索引破例」在联合索引上的延伸。考官想听你点破：① 非前缀 LIKE 在联合索引上走的是「全扫二级索引」，不是「按前缀定位」；② 既然全扫，列先后顺序就不影响；③ 一旦 SELECT 带了非索引列导致回表，优化器就放弃二级索引改扫聚簇。能结合 user2/user3 对比举例最稳。

## 主问答
**Q（面试官原话）：** 联合索引（age,name）上查 name 用 '%x%'，为什么还能用索引？

1. **覆盖判定**：只要查的列都在联合索引内（age、name），无需回表，即满足覆盖。
2. **全扫二级索引**：非前缀 LIKE 无法定位，优化器遍历整棵联合索引的二级索引树（type=index）。
3. **顺序无关**：全扫意味着逐叶子读取，左前缀原则失效，故（age,name）与（name,age）两种顺序结果一致。
4. **回表则弃**：若 SELECT 含非索引列（如 user1 的 age 无索引时查全部），每行都需回表，成本高于扫聚簇，优化器改走 ALL。

## 总结与追问预判
核心：**联合索引非前缀 LIKE，覆盖时全扫二级索引且列序无关；带非索引列回表则改扫聚簇**。追问常接「三种例外情形汇总」（见 1222）。
