> 分类：消息中间件 / Kafka | 难度：L3 | 题型：对比选型题 | 频率：中 | 关键词：**单分区单会话** / **跨分区跨会话** / **性能代价** / **exactly-once** / **选型**
> 原文锚点：第 34~44 段「幂等=重试不影响数据、broker去重consumer不变；事务=多步原子；幂等仅单分区单会话，事务跨分区跨会话跨topic；事务性能更差，非必要不开；consumer端仍可能重投」

## 一句话总述
二者都是 Kafka 实现**精确一次（exactly-once）发送**的工具，作用范围不同：**幂等生产者**只保证**单分区单会话**内不重发；**事务生产者**在幂等基础上支持**跨分区、跨会话、跨 topic** 原子写。事务性能更差、开销更大，**非必要不开**。且二者都只去重 producer 端，consumer 端精确一次仍需额外机制。

## 面试官视角
- 意图：是否能在"范围/性能/必要度"三维上做选型，而非背定义。
- P5 知二者都去重；P6 知幂等单分区、事务跨分区跨会话；P7 知"事务性能差、按需启用、consumer 端仍是精确一次短板" `[边界]` 见 1418。
- 红旗：以为事务一定优于幂等；忽略 consumer 端重复消费的盲区。
- 惊艳点：点出"事务支持跨 topic（一个 producer 向多个 topic 发消息纳入同一事务）"，这是幂等做不到的 `[经验]`。

## 主问答
**Q（面试官原话）：** 幂等生产者和事务生产者怎么选？
**A：**
1. **作用范围**：幂等生产者只保证同一分区、同一会话内消息不重复；事务生产者在幂等之上扩展到跨分区、跨会话、甚至跨 topic（多 topic 写入进同一事务）。
2. **性能与代价**：事务需维护 `transactional.id`、做两阶段提交式协调，性能明显差于幂等；除非确实需要"多步原子/跨 topic 原子"，否则不启用事务。
3. **共同盲区**：二者都只在 producer→broker 去重；consumer 因 offset 提交与处理顺序错位，仍可能重复消费或丢失——端到端精确一次还需消费逻辑幂等（如按业务主键去重）。

## 关键代码
```go
// 示意：选型决策辅助（按需求判断是否启用事务），未做端到端验证
func needTransaction(crossPartition, crossTopic, consumeTransform bool) bool {
    // 仅单分区单会话去重 → 只开幂等即可
    if !crossPartition && !crossTopic && !consumeTransform {
        return false // 幂等生产者足够
    }
    // 跨分区/跨 topic/消费转换写回 → 必须事务
    return true // 幂等 + transactional.id
}
```

## 总结与追问预判
- 幂等=单分区单会话去重；事务=跨分区/会话/topic 原子，性能更差，按需启用。
