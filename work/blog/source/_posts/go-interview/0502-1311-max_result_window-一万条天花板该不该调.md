> 分类：Elasticsearch | 难度：L2 | 题型：场景题 | 频率：中高 | 关键词：**max_result_window、结果窗口、相关性、settings**

> 原文锚点：第 9~16 段「默认只支持取索引的前一万条记录…通常不建议调整这个值」

## 一句话总述
ES 默认 `max_result_window = 10000`，`from + size` 超过它就抛结果窗口过大异常；参数可调大但**官方不推荐**——它是集群保护线，不是要跨越的障碍。

## 面试官视角
P6 答"把参数调大就行"；P7 要说清**为什么不该调**：限制初衷是集群性能，而前一万条都找不到目标，说明**相关性做得不够好**，该优化查询与排序 `[经验]`。调参数只是把 OOM 的时间点往后推，单次请求的资源放大一点没变。

## 主问答
**Q（面试官原话）：** 深分页报结果窗口过大，怎么解决？

1. **判定式是 from+size**：条件是 `from + size > max_result_window`；from=9995、size=10 同样报错 `[经验]`。
2. **索引级参数**：它写在索引 settings 里，可动态更新，但只对该索引生效 `[源码]`。
3. **为什么不建议调**：护栏是为性能设的；调大后 `(from+size)×分片数` 的读取量分毫未减，只是延后崩溃 `[经验]`。
4. **正解在业务侧**：加过滤条件缩小结果集、用聚合代替翻页、优化相关性；真要全量遍历就换游标方案 `[实测]`。

// 正解：不抬天花板，把深翻页换成游标迭代
func scan(ctx context.Context, size int) error {
	var last []any // 上一页末尾排序值
	for {
		page, err := queryPage(ctx, size, last) // search_after 走游标
		if err != nil || len(page.Hits) == 0 {
			return err
		}
		last = page.Hits[len(page.Hits)-1].Sort
	}
}

## ⚠️ 原文纠错
1. 事实核校：原文"从一万往后取十条所以超过一万"结论对，但判定式是 `from + size > 10000` 而非 `from > 10000`，本卡补全边界 `[经验]`。
2. 补充：原文"可以通过索引 settings 修改"准确；该设置是索引级、可动态更新，不影响已落盘数据 `[源码]`。
3. 崩坏词归一：源码将 Elasticsearch、索引、设置等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
