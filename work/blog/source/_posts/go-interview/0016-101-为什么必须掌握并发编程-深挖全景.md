## 思路与架构
本卡把「为什么必须掌握并发编程」拆成**动机层 → 概念层 → 代价层 → 优化层**四层，串起 `101-concurrency-vs-parallel`（并发并行+单核机制）、`101-context-switch-cost`（切换代价）、`101-reduce-context-switch`（四法）三张主卡，并显式划出边界。

- **动机层**：① 多核 CPU 打破单核效能上限，并发成刚需；② 高并发业务（百万级 QPS）使中间件不足以兜底；③ Go 语言以并发为第一公民，重构 PHP 后端看重其并发性能。
- **概念层**：并发=同时间段交替、并行=单位时间同时；单核靠时间片轮转伪造并发。
- **代价层**：切换 = 寄存器保存 + CPU 缓存失效 + 内核态切换，缓存失效是主损耗。
- **优化层**：减锁分段 / CAS / 减线程 / 协程（M:N 用户态）。

## 方案取舍
- 为什么不用「一味加线程」：线程切换本身有成本，线程数过多反而因抢占 CPU 使每线程时间片变短、执行变长——与「减线程」原则矛盾。
- 为什么协程优于纯多线程：把调度从内核搬到用户空间，单线程当多线程用，既减线程数又免内核切换，是 Go 高并发的根基。
- 与「减锁」的取舍：CAS 自旋在长临界区会空转浪费 CPU，短临界区才划算；sync.Map 读写分离适合读多写少。

## 答题技巧
- **必背三动机**：多核刚需 / 高并发业务 / Go 特性，三选一都能开口，三者齐说显体系。
- **辨析模板**：先给定义（并发交替 vs 并行同时），再补「并发可能并行也可能不」，最后落「单核靠时间片」。
- **代价落到缓存**：被追问「为什么慢」时，不要只说保存寄存器，要强调「CPU 比内存快几个数量级，缓存失效后从内存重载」才是大头。
- **显式边界**：CAS 内部实现见 104（原子卡）、sync.Map 见 922（并发 map 卡）、并发陷阱见 102；本卡不重画这些专项，只串动机与框架。
