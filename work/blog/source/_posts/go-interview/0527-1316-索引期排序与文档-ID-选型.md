> 分类：Elasticsearch | 难度：L3 | 题型：八股题 | 频率：中 | 关键词：**index.sort**/**自定义 ID**/**写入延迟**
> 原文锚点：第 14~23 段「写入即排序…自定义 ID vs 自动生成」

## 一句话总述
ES 可在索引期按字段排序（`index.sort.field`）让查询省去排序耗时；文档 ID 选型上，需更新/删除的业务必须用**自定义业务 ID**（避免"先查 ID 再改"的十~百倍延迟），仅追加的日志场景用自动生成 ID 反而更快。

## 面试官视角
- 考察意图：是否理解"写入期付出"换"查询期收益"，以及 ID 策略对增删改的影响。
- 分档：P5 知日志用自动 ID；P6 懂业务要自定义 ID；P7 能讲清 index.sort 机制与"查 ID 再改"延迟来源。
- 红旗答案：以为所有场景都该用自动 ID；以为 index.sort 是查询时排序。
- 惊艳点：**自动生成 ID 的文档反而写入更快（无需检查是否存在），所以仅追加的日志场景应交给 ES 自动生成；需要更新的业务才必须自定义 ID** `[经验]`。

## 主问答
**Q（面试官原话）：** 什么时候该自定义文档 ID？索引期排序有什么用？
**A：**
1. **结论**：有更新/删除需求的业务把文档 ID 设为业务主键（如 DB 行 ID），避免"先查 ES 拿 ID 再更新"的链路放大；仅追加日志用自动 ID 提速。
2. **机制**：`index.sort.field` 在段内按字段预排序，查询排序时直接利用、省去收集后排序；自定义 ID 让 update/delete 凭 ID 直达，跳过查询环节 `[经验]`。
3. **边界**：索引期排序增加写入成本、且只对一个字段有效；它优化的是"按该字段排序的查询"，不是所有查询。

**加分层：** "查 ID 再改"之所以慢，是因为多一次检索来回 + 批量场景下放大成 N 次，对写入链路是十倍到百倍延迟。

## 关键代码
```json
// 索引期排序 + 自定义 ID 的场景
PUT /orders
{ "settings": { "index.sort.field": ["logtime"], "index.sort.order": ["desc"] },
  "mappings": { "properties": { "logtime": { "type": "date" } } } }
// 写入时指定业务 ID：PUT /orders/_doc/<业务主键>
```

## 总结与追问预判
ID 选型=按需自定义；index.sort 把排序代价前移到写入。追问接"refresh/translog 调优"。
