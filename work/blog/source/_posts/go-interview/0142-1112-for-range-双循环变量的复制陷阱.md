> 原文锚点：第 40~63 段「避免 for-range 双循环变量遍历大元素 array/slice；每元素复制给第二循环变量；基准三方式(for下标≈forrange单变量≫forrange双变量)；双变量最慢因每次复制元素值部」

## 一句话总述
用 `for range` 遍历**大元素类型**的 array/slice 时，若用**双循环变量**（`for _, v := range s`），每次迭代都会把元素**复制**给 `v`，代价 = 元素值尺寸 × 元素数；改用单循环变量 + 下标取值（`s[i]`）或普通 `for` 下标遍历，可避免这次复制，基准测试差距可达数量级。

## 面试官视角
- 意图：考察对 for-range 复制语义的敏感度和"用 benchmark 说话"的习惯。
- P5 知道 for-range 有副本；P6 能说清双变量每次复制元素、单变量不复制；P7 能给出基准对比并讲清"代价 = 元素尺寸 × 次数"。
- 红旗：在大 struct 数组上无脑用 `for _, v := range`；凭感觉优化不测。
- 惊艳点：点出"单循环变量 + s[i] 取值"与"普通 for 下标"都避开了元素复制，且用 `go test -bench` 量化差距。

## 主问答
**Q（面试官原话）：** for-range 遍历大结构体切片，为什么用双变量慢？
**A：**
1. **结论**：`for _, v := range s` 中，每次迭代 Go 会把当前元素**复制**到 `v`（复制量 = 元素直接值部）；若元素是 1024×int 的大数组，每次复制 4KB（32位），1000 元素就是 4MB 无效复制 → 慢一两个数量级。
2. **机制（避复制）**：用**单循环变量** `for i := range s` 后 `s[i]` 取值，或普通 `for i:=0;...` 下标遍历，都**不复制元素**，直接按索引访问底层——基准显示这两种与前一种不在一个量级。
3. **边界**：陷阱只在**元素类型是大尺寸**（大 struct/大 array）时显著；元素是小 header 类型（slice/string/接口，十几个字节）时复制代价可忽略，不必刻意规避 `[经验]`。

## 关键代码
```go
// 三种遍历方式的基准对比（元素为大数组时差距显著）
type Big [1024]int64

func byForIndex(s []Big) int64 { // for 下标：不复制元素
    var sum int64
    for i := 0; i < len(s); i++ {
        sum += s[i][0]
    }
    return sum
}
func byRangeOne(s []Big) int64 { // for range 单变量 + s[i]：不复制元素
    var sum int64
    for i := range s {
        sum += s[i][0]
    }
    return sum
}
func byRangeTwo(s []Big) int64 { // for range 双变量：每次复制元素！
    var sum int64
    for _, v := range s { // v 是元素的副本，1000 次 = 4MB 复制（32位）
        sum += v[0]
    }
    return sum
}
// go test -bench=.  预期：byRangeTwo 远慢于前两者
```
