> 原文锚点：第 50~72 段「sync.Map 的删除是通过标记来延迟删除的，删除的过程同样也是先从 read 里面查找，如果在 read 里面，它就会调用 delete 函数，这个 delete 函数会将 key 所指向的值的指针设置为 nil…当 read 和 dirty 一致的时候触发重整的过程，重整会将 nil 状态的键值全部置到 expunged 状态，同时将没有删除的键值拷贝到 dirty 当中…所谓浅拷贝其实就是指针操作，并不会复制真实的数据…当指针为 nil 时表示已删除，不过此时还没有经过 read 到 dirty 的重整，它仍然属于 dirty；当值等于 expunged 时表示已删除且已经过重整，它不属于 dirty、仅属于 read，下一次从 read 升级到 dirty 时会彻底删除该 entry」

## 一句话总述
`sync.Map` 的删除是**标记式延迟删除**：删除时**先把 entry（指向值的指针）置为 `nil`**，而不是立即摘除；**当 read 与 dirty 一致时触发"重整"**——把 **nil 状态的 entry 置为 `expunged`**，并**把未删除的键值浅拷贝到 dirty**（只做指针操作、不复制真实数据）。**entry 指针有三态**：**nil**（已删，尚未重整，仍属于 dirty）、**expunged**（已删且已重整，只属于 read，下次升级时彻底删除）、**既非 nil 也非 expunged**（正常数据，read 与 dirty 可共享同一个 entry）。

## 面试官视角
- 考察意图：这是 `sync.Map` 最细的一层，能否讲清 **nil 与 expunged 的区别**基本决定了对实现的理解深度。
- 分档：P5 知道删除是延迟的；P6 能说"删除先把指针置 nil"；P7 能讲清 **三态含义**、**为什么需要 expunged**（防止并发下脏读）、以及**重整是浅拷贝**。
- 红旗答案：说不清 `nil` 和 `expunged` 到底差在哪；或以为删除会立刻释放内存。
- 惊艳点：**`expunged` 这个第三态的存在，是为了解决"把 read 拷进 dirty 时的并发正确性"**——拷贝瞬间若只把指针置 nil，并发的读写会让 dirty 里的值不确定 `[源码]`。

## 主问答
**Q（面试官原话）：** `sync.Map` 删除一个 key 之后，内存立刻释放了吗？

1. **结论**：**不会立刻释放**——删除是**通过标记来延迟删除**的：先找到 entry，**把该 key 所指向的值的指针设置为 `nil`**，真正摘除要等到**重整** `[源码]`。
2. **删除路径**：**删除同样先从 read 里查找**；**如果在 read 里，就调用 delete 函数，把该 key 指向的值的指针置为 `nil`** `[源码]`。
3. **重整的触发时机**：**延迟体现在当 read 和 dirty 一致的时候会触发重整过程** `[源码]`。
4. **重整做什么**：**把 nil 状态的键值全部置到 `expunged` 状态**，**同时把没有删除的键值拷贝到 dirty 当中**；**所谓浅拷贝，其实就是指针操作，并不会复制真实的数据** `[源码]`。
5. **为什么需要重整**：**避免 read 里的 key 无限膨胀**——**存在大量删除逻辑时，这些 key 不会被回收**；**当 key 升级到 read 时，这些逻辑删除的 key 才能被释放** `[源码]`。
6. **entry 三态**：
   - **`nil`**：**entry 已删除，但还没有经过 read → dirty 的重整**；**此时它仍然属于 dirty**（若 dirty 不为 nil）`[源码]`。
   - **`expunged`**：**entry 已删除，且已经过 read → dirty 的重整**；**它不属于 dirty、仅属于 read**；**下一次从 read 升级到 dirty 时会彻底删除这个 entry** `[源码]`。
   - **既非 `nil` 也不是 `expunged`**：**存储的是普通的键值对（真正的数据）**；**因为它是指针，read 和 dirty 里的 entry 都可能指向它** `[源码]`。
7. **`expunged` 的必要性**：**从 read 拷贝到 dirty 的过程中**，若删除只是把指针置 nil，**并发问题会导致拷贝后 dirty 里值的正确性受影响**；因此**用 `expunged` 状态标记 read 里的 entry 是否已被删除**——**复制时把 read 中 nil 状态的实体标记为 `expunged`，并且不把它复制到 dirty 里** `[源码]`。

**加分层：** 记法——**`nil` 是"刚删、还没清理"，`expunged` 是"已清理过、只留个墓碑在 read 里"**；墓碑会在下一次 dirty 提升时被彻底清扫。

## 关键代码
```go
package main

import "sync"

// entry 的三态：正常指针 / nil(刚删) / expunged(已重整的墓碑)
// 真实源码中 expunged 是一个 unsafe.Pointer 哨兵值
var expunged = new(any)

type entry struct{ p any }

func main() {
	// 1) 正常态：read 与 dirty 可共享同一个 entry 指针
	e := &entry{p: "value"}

	// 2) 删除：先把 p 置为 nil —— 只是标记，内存尚未释放
	e.p = nil

	// 3) 重整（read -> dirty 拷贝）时：nil 的 entry 被标记为 expunged，且不拷进 dirty
	e.p = expunged

	// 4) 下一次 dirty 提升时，expunged 的墓碑被彻底删除，内存才真正回收
	var _ = e

	// 真实使用：删除后再 Load 拿不到值，但底层 entry 可能仍在 read 中占位
	var m sync.Map
	m.Store("k", "v")
	m.Delete("k")
	if _, ok := m.Load("k"); !ok {
		// ok == false：逻辑上已删除
	}
}
```

## 总结与追问预判
**最爱追问的是"`nil` 和 `expunged` 到底差在哪"**——一句话：**`nil` 还属于 dirty（可能被拷回去，所以不能当真删掉），`expunged` 已经脱离 dirty、只留墓碑在 read 里，下次提升时彻底清除**。追问常接"为什么不能直接置 nil 就完事"——因为 **read → dirty 的拷贝是并发进行的**，若只用 nil 表示删除，拷过去的瞬间可能有其他 goroutine 正在写同一个 entry，导致 dirty 拿到错误的值；`expunged` 是一个**不可变哨兵**，能安全地表达"此项已废弃、不参与拷贝"。

## ⚠️ 原文纠错
1. 事实核校：删除为标记式延迟删除、先从 read 查找并把 entry 指针置 nil、read 与 dirty 一致时触发重整、重整把 nil 置为 expunged 并把未删除项拷入 dirty、拷贝为浅拷贝（只动指针）、重整用于避免 read 无限膨胀、entry 三态含义与归属、`expunged` 用于保证拷贝时的并发正确性——均与 Go 标准库实现一致 `[经验]`。
2. 补充：原文"当 read 和 dirty 一致时触发重整"应精确为——**`misses` 累积超过 `len(dirty)` 时执行提升，提升过程中完成 nil → expunged 的标记与 dirty 重建**；另外**删除一个已存在于 dirty 的 key 时，会直接从 dirty 中摘除**，并非一律走标记路径 `[经验]`。
