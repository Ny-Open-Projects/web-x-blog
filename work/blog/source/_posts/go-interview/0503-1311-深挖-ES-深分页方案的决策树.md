> 分类：Elasticsearch | 难度：L4 | 题型：架构题 | 频率：高 | 关键词：**方案选型、游标、快照、一致性、成本模型**

> 原文锚点：第 23~33 段「避免深度分页…用游标查询…用 search_after…分层结果」

## 思路与架构

把深分页拆成**三层决策**，自上而下收敛：

1. **第一层：能不能不做深分页。** 解决问题的最高境界是让问题不成立。ES 把默认上限定在一万条，本身就是产品信号——前一万条都找不到，说明查询相关性有问题。业务侧手段有四种：收紧过滤条件缩小结果集、用聚合代替逐条翻页、改排序让目标前移、把结果**分层**（先分页主体，再对每层内的聚合结果单独分页）。
2. **第二层：离线全量遍历。** 导出、备份、离线计算这类任务，用快照型游标（scroll）。它把初始查询的结果集冻住，后续按批拉取，规避偏移量放大。代价是服务端上下文：占内存、持有期间段不合并、文件句柄与磁盘上涨、默认并发上限 500、必须显式释放。
3. **第三层：实时连续翻页。** 用户交互型分页用排序值游标（search_after）。无快照、读实时，代价是不能跳页，且排序值必须唯一。若要一致性保证，配 PIT（Point In Time）构成完整解。

三层的判据只有一句话：**看是否需要随机跳页、是否允许读到遍历期间的写入**。

## 方案取舍

| 维度 | from+size | 快照型游标 | 排序值游标 |
|---|---|---|---|
| 读取量 | (from+size)×分片数 | 与总量线性、无放大 | 每页固定、无放大 |
| 随机跳页 | 支持 | 不支持 | 不支持 |
| 数据视图 | 实时 | 快照 | 实时（配 PIT 则快照） |
| 服务端持有 | 无 | 有上下文 | 配 PIT 时轻量持有 |
| 适用 | 前 1 万条浅翻页 | 导出 / 备份 | 用户端连续翻页 |

取舍要点：

- **别把护栏当旋钮。** 调大结果窗口上限是最常见的错误答案，它不改变 `(from+size)×分片数` 的放大，只是把崩溃时间推后。
- **游标不是免费的。** 快照型游标的成本在服务端常驻，是"用集群资源换客户端便利"；并发一大先压垮的是节点句柄与堆。
- **排序值是分页的命门。** 排序键不唯一，边界就会漂移，出现漏页或重页；用唯一键做次级排序键是标配动作。
- **映射决定上限。** 排序字段有没有列式结构，决定了方案能不能落地；这条在面试里常被跳过，却是真实线上故障的高发点。

## 答题技巧

1. **先给判据再给方案。** 开口不要背 API，先问清"要跳页吗？要实时吗？数据量多大？"——判据先行本身就是 P7 信号。
2. **报数字。** "(from+size)×分片数" 这个公式要能脱口而出，配合 10 分片 / offset 一万 / 10 万条的实算，比任何形容词都有说服力。
3. **主动交代代价。** 每推一个方案就顺手说它的成本（上下文、不可跳页、堆内存），这是区分 P6 与 P7 的分水岭。
4. **把规避放在第一位。** "能不能不深分页"是最高分的回答，因为它把技术题拉回了业务判断。
5. **落到 Go 侧。** 面试官若是 Go 岗，补一句客户端实现：游标迭代要用 `for` 循环推进末条排序值、`defer` 释放服务端上下文、`context` 贯穿整轮遍历以便中途取消 `[经验]`。

## 细节与核心 API

**三层决策对应 API：**

```json
// ① 浅翻页 from+size（默认上限 10000，调大只是推后崩溃）
{ "from": 0, "size": 10, "query": { "match_all": {} } }

// ② 快照型游标 scroll（导出/备份，服务端持上下文，必须释放）
GET /idx/_search?scroll=1m { "size": 1000, "query": { "match_all": {} } }
POST /_search/scroll { "scroll": "1m", "scroll_id": "<上一轮返回的_id>" }

// ③ 实时连续翻页 search_after（排序值必须唯一，加 _id 做次级排序键）
{ "size": 1000, "query": { "match_all": {} },
  "sort": [ { "ts": "asc" }, { "_id": "asc" } ],
  "search_after": [ 1700000000, "doc-998" ] }

// 一致性：PIT 冻结数据视图
POST /idx/_pit?keep_alive=1m
{ "size": 1000, "query": {...}, "pit": { "id": "<pit_id>" }, "sort": [...] }
```

**放大公式（必报数字）：**

```text
from+size 读取量 = (from + size) × 分片数
例：10 分片 / offset 10000 / size 10 → 每分片拉 10010 条、协调节点合 100100 条
```

**Go 侧实现纪律：**

```go
// for 循环推进末条排序值；defer clearScroll / 关闭 PIT；context 贯穿整轮遍历以便中途取消
for {
    res, _ := es.Search(es.Search.WithScroll(time.Minute), es.Search.WithContext(ctx))
    // 推进 search_after = 最后一条的 [ts, _id]
    if lastBatchEmpty { break }
}
```

2. 补充：原文列举的"分层结果"思路（先分页、再对聚合结果分页）是有效的降载手段，本卡把它归入第一层规避策略 `[经验]`。
