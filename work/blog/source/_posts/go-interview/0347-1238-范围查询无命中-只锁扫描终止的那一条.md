> 分类：数据库 / MySQL 锁 | 难度：L4 | 题型：原理题 | 频率：中 | 关键词：**扫描终止、临键锁、记录锁、空区间、最小加锁**

> 原文锚点：第 68~75 段「查询区间是 name 大于 name10 并且 name 小于 name15，当然这个区间当前也是没有命中任何数据的…由于它要扫描到第一条不满足条件的索引记录之后，就不再进行扫描了，所以加锁的记录只有一条，也就是 name 等于 name2 这条记录…它加的是一个临键锁…它还对 id 等于 2 的这条记录加了一个单纯的记录锁，并且是在主键索引上进行加锁的」

## 一句话总述
范围查询即使**一个记录都没命中**，也至少要锁**扫描终止处的那一条**索引记录：二级索引上加**临键锁**，对应的主键行加**记录锁**——扫描一旦遇到第一条不满足条件的记录就立即停止。

## 面试官视角
P6 会以为「没查到数据就不加锁」；P7 必须纠正：**没有命中不代表没有锁**。只要走了加锁读，扫描经过的索引记录就会被加锁，最小范围就是终止处的那一条，这是判断并发阻塞的关键。

## 主问答
**Q（面试官原话）：** 查询一个不存在的数据区间，会加锁吗？

1. **会加锁**：即便区间**未命中任何数据**，加锁读仍会对扫描过的索引记录加锁 `[源码]`。
2. **扫描提前终止**：扫描到**第一条不满足条件的索引记录后即停止**，不再继续 `[源码]`。
3. **本例只锁一条**：扫描到 `name = 'name2'` 时发现区间内没有对应值，因此**只有这一条被加锁** `[源码]`。
4. **锁型是临键锁**：该二级索引记录上加的是**临键锁** `[源码]`。
5. **主键补记录锁**：同时对 **id = 2** 这条记录加了**单纯的记录锁**，加在主键索引上 `[源码]`。
6. **与全表扫描的区别**：走索引范围扫描时锁范围极小，而类型写错导致全表扫描时会锁全表 `[经验]`。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| MySQL 5.7 / 8.0 RR | 扫描终止规则一致 | 未命中也锁终止项 |
| RC 隔离级别 | 无间隙锁 | 只保留记录锁 |

## 关键代码
```sql
-- name 字符串列，值为 1,2,20,3,4,5,7；区间 name10~name15 无数据
BEGIN;
SELECT * FROM t WHERE name > 'name10' AND name < 'name15' LOCK IN SHARE MODE;
-- 扫描：在 name='name2' 处判定区间无值 -> 立即终止
-- 加锁：
--   二级索引 name='name2' -> 临键锁
--   主键 id=2            -> 记录锁

-- 对比：条件写成数字会触发隐式转换 -> 全表扫描 -> 全表行锁
SELECT * FROM t WHERE name >= 10 AND name <= 15 LOCK IN SHARE MODE;

-- 验证（MySQL 8.0）
SELECT INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks;
```

## 总结与追问预判
**「没查到 ≠ 没加锁」**——这句话是本卡的题眼。面试官常把它与「类型写错锁全表」对比着问，用来考察你是否真的理解**扫描范围决定锁范围**。两者对比见同批 1238-type-conversion-lock。

## ⚠️ 原文纠错
1. 事实核校：未命中仍加锁、扫描到第一条不满足项即停、只锁一条、二级索引加临键锁、主键加记录锁——均与 InnoDB 行为一致 `[经验]`。
2. 补充：需强调本结论的前提是**当前读（加锁读）**；若是普通 `SELECT`（快照读），在 RR 下走 MVCC 不加任何锁，答题时应先区分读的类型 `[经验]`。
3. 崩坏词归一：源码将临键锁、记录锁、主键索引、扫描等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
