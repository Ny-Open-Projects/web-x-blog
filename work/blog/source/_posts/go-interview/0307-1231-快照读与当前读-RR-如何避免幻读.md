> 原文锚点：第 1~7 段、第 79~85 段「两种避免幻读机制、快照读MVCC、当前读FOR UPDATE、隔离级别与问题对照」

## 一句话总述
InnoDB 默认隔离级别是可重复读（RR），它**在很大程度上**能避免幻读，靠两种机制：① **快照读**——普通 SELECT 走 MVCC，事务内始终看到启动时的数据，别的事务新插入读不到；② **当前读**——`SELECT ... FOR UPDATE` 加 next-key 锁（记录锁+间隙锁），别的事务在锁范围内插入会被阻塞。但仍有极个别场景无法完全避免。

## 面试官视角
「RR 下幻读解决了吗」是经典追问，答案是「很大程度上解决，靠快照读+当前读双机制，但非 100%」。考官还期待你能背出隔离级别与问题的对照：脏读→读已提交以上解决；不可重复读→可重复读以上解决；级别越高隔离越强、性能越差。

## 主问答
**Q（面试官原话）：** RR 隔离级别下幻读是怎么解决的？

1. **快照读（MVCC）**：普通 SELECT 默认快照读；RR 下事务执行过程中看到的数据始终与启动时一致，其他事务中途插入的数据读不到，从而避免幻读。
2. **当前读（加锁）**：`SELECT ... FOR UPDATE` 会给记录加 **next-key 锁**（记录锁 + 间隙锁）；其他事务若在该锁范围内插入记录，插入语句会被阻塞。
3. **注意边界**：两种机制是「在很大程度上」避免幻读，仍有极个别情况无法解决（如快照读后又发生当前读）。
4. **级别对照**：读未提交/读已提交/可重复读/串行化，从左到右隔离级别递增、性能递减；解决脏读需读已提交以上，解决不可重复读需可重复读以上。

## 关键代码
```sql
SELECT * FROM t WHERE id > 10 FOR UPDATE;  -- 当前读，加 next-key 锁阻塞插入
```

## 总结与追问预判
核心：**RR 靠快照读(MVCC) + 当前读(next-key 锁) 很大程度上避免幻读；隔离级别越高性能越差**。追问可回「MVCC 原理」（见 1231）或「ReadView 时机」（见 1231）。
