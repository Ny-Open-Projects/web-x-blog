## 一句话总述
本源把锁按"对冲突的预测"分类：**悲观锁（Mutex）先加锁后访问**，**乐观锁（CAS/版本号）先访问、提交时校验**。面试按"分类→Go 落地→故障规避"三步走，并明确与既有卡的边界：Mutex 用法见 925、CAS vs Mutex 取舍见 105、DB 层乐观悲观见 1233、channel 死锁见 1019。

## 思路与架构
- **概念层**：悲观（假设冲突必发生，先锁）/乐观（假设无冲突，提交校验）。这是认知框架。
- **Go 落地层**：Mutex=悲观（sync.Mutex）；乐观无内置类型，靠 atomic CAS 或版本号。二者分别解决"冲突多/冲突少"两端。
- **故障层**：死锁（互等锁，fatal error 不可 recover，六法避免）/活锁（谦让空转）。是锁使用的反面教材。
- **边界层**：与 925（Mutex 调用）、105（atomic vs lock 取舍）、1233（DB 乐观悲观）、1019（channel 死锁）互补，本卡只讲"分类+Go 乐观实现+死锁活锁概念"。

## 方案取舍
- **为何 Mutex 是悲观**：它不预判实际冲突，一律先 Lock——简单但冲突少时有不必要阻塞；此时乐观(CAS)更轻。
- **CAS 的代价**：自旋重试在冲突多时 CPU 飙升，故仅适合极短临界区/低冲突；高冲突退回 Mutex。
- **死锁为何不可 recover**：Go 的死锁是运行时 fatal error，不是普通 panic，`recover` 拦截不住，必须靠设计避免（同序取锁/TryLock/超时）。

## 细节与核心 API

**① 悲观锁：`sync.Mutex`——先加锁，再访问**

```go
var mu sync.Mutex
var balance int

func withdraw(n int) {
	mu.Lock()         // 假设冲突必发生：先锁
	defer mu.Unlock()
	balance -= n      // 临界区
}
// 代价：无论是否真冲突都要走加锁/解锁，冲突少时有不必要的阻塞
```

**② 乐观锁：CAS（`atomic.CompareAndSwap`）——先算，提交时校验**

```go
var balance int64 = 100

// CAS 自旋：乐观地改，失败就重来
func withdrawCAS(n int64) bool {
	for {
		old := atomic.LoadInt64(&balance)
		if old < n {
			return false // 余额不足，直接失败
		}
		newV := old - n
		// 提交时校验：这期间没人改过才写成
		if atomic.CompareAndSwapInt64(&balance, old, newV) {
			return true // 成功
		}
		// 失败 = 有人抢先改了 → 重新读、重新算、再试
	}
}
// 冲突少：一次成功，比 Mutex 轻
// 冲突多：长时间自旋 → CPU 飙升，此时应退回 Mutex
```

**③ 乐观锁：版本号（适合"读多写少 + 需要多次校验"）**

```go
type Versioned struct {
	mu   sync.Mutex
	val  int
	ver  uint64 // 版本号，每次写入 +1
}

// 乐观读：先取快照，用完回校版本号
func (v *Versioned) OptimisticUpdate(fn func(int) int) bool {
	v.mu.Lock()
	defer v.mu.Unlock()
	oldVer := v.ver
	oldVal := v.val
	newVal := fn(oldVal) // 基于快照计算（假设无冲突）
	if v.ver != oldVer { // 提交时校验版本号
		return false      // 被别人改过，本次作废
	}
	v.val = newVal
	v.ver++
	return true
}
```

**④ 死锁：Go 的死锁是运行时 fatal error，`recover` 拦不住**

```go
func deadlockDemo() {
	var a, b sync.Mutex
	// 协程 1：先 a 后 b；协程 2：先 b 后 a → 互等
	go func() {
		a.Lock(); time.Sleep(10 * time.Millisecond)
		b.Lock(); defer b.Unlock(); defer a.Unlock()
	}()
	b.Lock(); time.Sleep(10 * time.Millisecond)
	a.Lock() // 卡死
	defer a.Unlock(); defer b.Unlock()
}
// fatal error: all goroutines are asleep - deadlock!
// 注意：这是 fatal error，不是 panic，recover() 无效
```

**⑤ 用 `TryLock`（Go 1.18+）避免死等**

```go
func tryBoth(a, b *sync.Mutex) bool {
	if !a.TryLock() { // 拿不到就立刻返回，不阻塞
		return false
	}
	defer a.Unlock()
	if !b.TryLock() {
		return false
	}
	defer b.Unlock()
	// 两把锁都拿到，做临界区操作
	return true
}
```

> API 速记：`sync.Mutex`（悲观）/ `atomic.CompareAndSwap*`（乐观 CAS）/ `Mutex.TryLock`（Go 1.18+，防死等）/ 版本号（乐观，适合复杂结构）。

1. **开口定调**："锁分悲观/乐观，Go 的 Mutex 是悲观锁"。
2. **给落地**：乐观锁在 Go 用 CAS(atomic) 或版本号，无内置类型。
3. **讲故障**：死锁 fatal error 不可 recover + 避免六法 + 活锁辨析。
4. **关联延展**：提 925/105/1233/1019，显示体系化与边界意识。
