> 原文锚点：第 42~60 段「for 循环内 goroutine 读主循环正在修改的变量/字段，结果取决于调度时机」

## 一句话总述
for 循环里 goroutine 读共享/循环变量，绝大多数情况是**数据竞争**（未定义行为）。别靠"多跑几次看着对"判断，用 `go run -race` / `go test -race` 在竞态发生时直接报冲突位置，再按 1018 系列修法根治。一句话背法：**「for 循环 goroutine 读共享变量多为数据竞争（UB）；用 go run -race / go test -race 抓冲突栈，开销 2~10x 仅 CI 开，不能靠肉眼/运气」**。

## 面试官视角
这是工程素养题。考官看你会不会"用工具证伪竞态"，而不是靠运气或肉眼分析调度。
- **P5**：知道 -race 能检测。
- **P6**：能说清数据竞争是 UB、不加锁的"偶尔正确"不可信。
- **P7**：能讲 -race 的原理（影子内存/happens-before）与开销。
- **红旗**：以为"我跑过好几次都对就没问题"；以为竞态一定会 panic。
- **惊艳点**：指出 -race 有运行时开销（约 2~10x 内存/时间），只在测试与 CI 开，不在生产常驻。

## 主问答
**Q（面试官原话）：** 怎么确认 for 循环里的 goroutine 是不是有数据竞争？

**先铺垫（由浅入深第 1 层）**：并发 bug 最骗人的地方是"看着对"。数据竞争是未定义行为——它不保证 panic、不保证崩溃，可能只是偶尔算错。所以"我对着跑了几次都没问题"在并发里等于零证据。

1. **结论（第 2 层·机制）**：用竞态检测器 `go run -race main.go` 或 `go test -race ./...`，它会报告每处"写-读无同步"的冲突调用栈；有冲突即存在数据竞争，必须修 `[源码]` race detector。
2. **机制（第 3 层）**：-race 给每个内存访问维护影子状态、跟踪 happens-before，发现无同步的并发访问对就告警；直接定位到具体行，比肉眼分析调度可靠 `[源码]`。
3. **边界（第 4 层）**：数据竞争是**未定义行为**——不报 panic、不崩溃都可能，运行期偶发错乱最难查；所以"看着对"不等于"对"，靠 -race 证明无竞争才算过关 `[经验]`。
4. **原理（第 5 层）**：核心是"影子内存"记录每次访问的 happens-before 关系，代价是内存/时间开销约 2~10x `[源码]` race detector。
5. **实践（第 6 层）**：CI 常开 -race，本地复现用 `go run -race`；修完再跑 -race 确认零冲突 `[经验]`。

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
)

// 运行：go run -race main.go
// 无同步的并发自增会被 -race 直接报 WARNING: DATA RACE 并定位调用栈
func main() {
	var x int
	var wg sync.WaitGroup
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			x++ // 写-读无同步 -> 数据竞争
		}()
	}
	wg.Wait()
	fmt.Println("x =", x) // 值不确定，且 -race 会告警
}
```

## 总结与追问预判
**背这三句就够**：① **for 循环 goroutine 读共享变量多为数据竞争（UB）**；② **用 go run -race / go test -race 抓冲突栈**；③ **开销 2~10x 仅 CI 开，不能靠肉眼/运气**。
**预判追问**：
- 「偶尔跑对能证明无竞争吗？」→ 不能，UB 不保证崩；必须用 -race 证明。
- 「修完怎么验证？」→ 再跑 -race 确认零 WARNING（见 1018 修法总览）。
- 「循环变量捕获也是竞争？」→ 旧版共享变量读终值属竞争，1.22+ 自愈（见 1017）。
