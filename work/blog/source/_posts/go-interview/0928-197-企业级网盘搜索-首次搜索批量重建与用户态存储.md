## 一句话总述
搜索服务常晚于网盘其他功能上线，且并非所有用户都用搜索（内容搜索更是会员权益），故**只存用过搜索的用户数据**省成本。用户首次搜索时：先查 **Redis 缓存 / MongoDB** 有无该用户，无则判定为首次、异步批量重建其全量索引；重建完成前该用户只能搜到已索引的部分文件。文件名变更同样靠事件推送增量更新索引。

## 面试官视角
- 考察意图：能否解释「为何不全量建索引」与「首次搜索懒重建」的成本权衡，以及用户态用什么存。
- 分档：P5 知搜索要建索引；P6 能说首次重建+缓存/DB；P7 知存量/会员权益驱动的部分索引、异步与最终一致。
- 红旗答案：认为上线即全量索引所有用户（浪费巨大）；忽略「重建完成前只搜部分」的最终一致窗口。
- 惊艳点：点出「内容搜索是会员权益、只对用过搜索的付费用户建内容索引」，以及「Redis+Mongo 双层存用户态、首次触发异步重建」 [经验]。

## 主问答
**Q（面试官原话）：** 为什么不全量建索引？用户首次搜索怎么办？
**A：**
1. **不全量原因**：搜索服务上线晚、存量未写、且非全员用搜索（内容搜索是会员权益），全量建索引浪费巨大计算/存储 [经验]。
2. **首次懒重建**：用户发起搜索先查 Redis/Mongo 有无记录，无则判首次、异步批量重建其全量索引 [经验]。
3. **最终一致窗口**：重建完成前该用户只搜到已索引的部分文件；文件名变更靠事件推送增量更新，不涉强事务 [经验]。

## 关键代码

```go
// 首次搜索懒重建：Redis+Mongo 双层用户态，命中则直查 ES，未命中异步重建
func Search(userID string, q string) ([]EsFileDoc, error) {
    if !userStore.Exists(userID) { // Redis 未命中再查 Mongo，都没有=首次
        go rebuildUserIndexAsync(userID) // 异步批量重建全量索引
        // 重建完成前只搜到已索引的部分文件（最终一致）
    }
    return es.Search("netdisk_filename", q, userID)
}
// 文件名变更：事件推送增量更新索引（不涉强事务）
func onNameChange(evt FileEvent) { es.Update("netdisk_filename", evt.FileID, map[string]any{"name": evt.Name}) }
// 内容索引：仅会员且用过搜索的用户才建（权益+成本）
```

## 总结与追问预判
「按实际使用情况懒建索引」是成本敏感系统的常态。Redis+Mongo 双层用户态 + 异步重建，是搜索系统兼顾成本与体验的标准做法。
