> 原文锚点：第 38~61 段「多组件关闭顺序 / 启动与关闭相反」

## 一句话总述
多组件服务关闭顺序与**启动顺序相反**：启动时「**最后被依赖的组件最先初始化**」，关闭时「先停最外层的入口流量，再关下游依赖」。例：HTTP 收请求→写 Redis 缓存→发 Kafka：启动先 Kafka→Redis→最后 HTTP；关闭先 **HTTP**（拒新流量）→Redis→Kafka。若「消费 Kafka 写 DB」，则先关 **Kafka 消费者**再关 DB。异步生产者未 flush 会丢消息（见 1420.md`）。

## 面试官视角
关闭顺序是架构题，考「依赖方向」而非背清单。能讲出「启动最后依赖先 init、关闭相反」这条总原则，并举一两个正确反例（先关 DB 会导致在途请求写库失败），就是合格；只说「都 Close 一下」不及格。

## 主问答
**Q（面试官原话）：** 服务里同时有 HTTP、Redis、Kafka、DB，怎么排序关闭？

1. **总原则**：启动「最后被依赖的先 init」，关闭**严格相反**——先停入口、后关底层。
2. **入口最先关**：先关 HTTP server（Shutdown 拒新请求），让外部流量进不来，再进行下游清理，避免「下游已关、在途请求还来写」。
3. **按依赖反向关**：上例链路 HTTP→Redis(缓存)→Kafka(发消息)→DB(落库)：关闭顺序 HTTP → Redis → Kafka → DB；若链路是「消费 Kafka 写 DB」，则先关 Kafka 消费者（不再拉新消息）再关 DB。
4. **异步组件必须 flush**：Kafka 异步生产者把消息放 SDK channel 由后台提交，退出前**必须等 channel 积压提交完**（Close 而非 AsyncClose），否则丢消息——见 1420.md`。
5. **资源型收尾**：db/redis 连接调 `Close()`、文件句柄 `defer` 释放，确保不泄漏；用 registry/hook 把各组件 Close 串成有序列表统一执行。

## 版本与兼容性
| 链路 | 启动顺序 | 关闭顺序 |
|------|----------|----------|
| HTTP→Redis→Kafka | Kafka→Redis→HTTP | HTTP→Redis→Kafka |
| 消费 Kafka→DB | DB→Kafka(消费) | Kafka(停消费)→DB |

## 关键代码
```go
// 用 hook 列表按依赖反向关闭（先注册=后关；或显式倒序）
closers := []func() error{
    redis.Close, // 后启动的依赖
    kafka.Close, // 先启动的依赖
}
// HTTP 已在最前 Shutdown 拒流；其余按依赖反向 Close
for _, c := range closers {
    _ = c() // 实际应收集 error 并做超时控制
}
// Kafka 异步生产者务必先 Flush/等待 channel 提交完再 Close（见 1420）
```

## 总结与追问预判
核心：**关闭 = 启动反向；先停入口流量再关依赖；异步生产者须 flush**。追问拐向「单组件关闭机制」——备好 `http.Server.Shutdown`（见 713.md`）；Kafka flush 见 1420.md`。
