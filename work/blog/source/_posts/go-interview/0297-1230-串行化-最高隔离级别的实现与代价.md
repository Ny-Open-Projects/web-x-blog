> 原文锚点：第 76~89 段「串行化机制 / 排队等待 / 选型权衡」

## 一句话总述
串行化是最高隔离级别：InnoDB 会把普通 SELECT **隐式转为加共享锁的锁定读**，读写冲突时后访问的事务必须等前一个事务完成，从而杜绝脏读、不可重复读与幻读；代价是读写并发能力大幅下降，生产一般不建议使用。

## 面试官视角
考官想纠正两个常见误解：「串行化 = 全库单线程」和「串行化就是加读写锁」。能说出**隐式 FOR SHARE** 这个实现细节、并指出**读读仍可并行**，说明你读过官方文档而不是凭字面想象。

## 主问答
**Q（面试官原话）：** 串行化是怎么实现的？为什么不建议用？

1. **最高级别**：串行化提供最高级别的隔离，脏读、不可重复读、幻读**都不会出现**。
2. **隐式加共享锁**：实现上类似可重复读，但 InnoDB 会把普通 SELECT **隐式转换**为加共享锁的锁定读，从而让读写之间产生冲突。
3. **冲突即排队**：多个事务对同一条记录读写冲突时，后访问的事务必须等待前一个事务执行完成才能继续。
4. **读读不冲突**：并非同一时刻只能有一个事务在执行——**读与读之间共享锁互相兼容**，可以并行，只有读写、写写才排队。
5. **代价明显**：事务需要排队等待，严重影响数据库并发性能，因此生产上通常不把隔离级别设为串行化。

| 级别 | 普通 SELECT | 并发表现 |

| 可重复读 | 快照读，不加锁 | 读写不阻塞 |

## 关键代码
```sql
-- 串行化下的普通 SELECT，效果等价于显式加共享锁
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
START TRANSACTION;
SELECT a FROM t WHERE id = 1;        -- 隐式转为 SELECT ... FOR SHARE
-- 另一事务此时 UPDATE 同一行会被阻塞，直到本事务提交
COMMIT;
```

## 总结与追问预判
核心：**隐式共享锁 → 读写排队 → 三类问题全无，但并发崩塌**。追问常拐向「那怎么既保证一致又不串行」，备好「可重复读 + 显式 FOR UPDATE 锁定关键读」这条折中。

## ⚠️ 原文纠错
1. 事实核校： [经验] 原文称串行化「同一时刻只能有一个事务在执行」——过于绝对。读读之间共享锁兼容可以并行，只有读写、写写冲突才排队，且排队范围限于**冲突的记录**，并非全库串行。
2. 事实核校： [经验] 原文称串行化「对记录加上读写锁」——官方表述为：串行化类似可重复读，但 InnoDB 会**隐式把普通 SELECT 转为加共享锁的锁定读**；8.0 起对应语法为 `SELECT ... FOR SHARE`（旧写法为 LOCK IN SHARE MODE）。
3. 崩坏词归一：源码将事务 / 串行化 / 共享锁 / 幻读 等音译为多组崩坏词，本卡统一为规范术语。
