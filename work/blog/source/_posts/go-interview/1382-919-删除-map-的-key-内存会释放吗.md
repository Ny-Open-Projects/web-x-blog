> 分类：Go 语言基础 / map 进阶 | 难度：L1~L2 | 题型：机制题 | 频率：高 | 关键词：**delete**/**不缩容**/**渐进式扩容**/**装填因子**/**懒迁移**

> 原文锚点：第 1~14 段「追加 10 万键值对…强制 GC 打印内存…删除后内存不变…map 置 nil 后明显变少…渐进式扩容/装填因子/懒迁移」

## 一句话总述
**不会释放**。delete 只标记槽位、`len` 变小，但哈希表**只增不减**——因为 Go map 的扩容是**渐进式**的：只在**插入**时按装填因子触发、搬迁分批进行（懒迁移），设计上根本没有「缩容」路径。想真正释放只能整体重建（见 920）。[实测] 10 万键值对 2.5MB，全删后仍 2.5MB，置 nil + GC 后才回落。

## 面试官视角
- 意图：高频追问题——「删了 key 内存降不降」背后考的是对扩容机制的理解深度。
- 分档：P5 答不会；P6 能用 MemStats 验证并讲标记删除；P7 能把「为什么不缩容」接到渐进式扩容的设计动机（分摊搬迁成本、避免长尾延迟）。
- 红旗答案：以为 delete 后 GC 会回收桶；说「len 变 0 就是空 map 占 0 内存」。
- 惊艳点：讲清设计取舍——缩容会引入不可预期的长暂停，与 Go「低延迟 GC」目标冲突，所以宁可费内存也要保延迟平稳；再给治理方案引用 [经验]。

## 主问答
**Q（面试官原话）：** map 中删除一个 key，它的内存会释放吗？

**A：** 三段实验 + 机制解释 [实测]：

1. **实验**：插入 10 万键值对 → 强制 GC → `HeapAlloc ≈ 2.5MB`；遍历 **delete 全部 key** → 再 GC → **仍 2.5MB**（桶不归还）；`m = nil` → GC → 内存**明显回落**——释放的时机是 map 本身不可达，不是 delete。
2. **为什么不缩容**：Go map 用**渐进式扩容**（incremental）——只在**插入新元素**时按**装填因子**（>6.5 触发翻倍扩容；溢出桶过多触发等量扩容）判断是否扩容，搬迁**分批**进行（懒迁移，每次写入顺带搬一点）。这套机制里**只有「长」没有「缩」**：删除不触发任何搬迁，空桶原样保留。
3. **设计动机**：缩容/整表整理会造成单次长延迟，与 Go 运行时「低延迟优先」的目标冲突；map 的容量按峰值预留，是拿内存换平滑。
4. **怎么办**：峰值后长期低量的场景，重建 map 迁移存活数据强制回收——方案与数字见 920（2.5MB → 0.3MB 实测）。

## 关键代码
```go
package main

import (
	"fmt"
	"runtime"
)

func memMB() float64 {
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return float64(m.HeapAlloc) / 1024 / 1024
}

func main() {
	m := make(map[int]int)
	for i := 0; i < 100000; i++ {
		m[i] = i
	}
	fmt.Printf("insert 10w : %.1f MB, len=%d\n", memMB(), len(m))
	for k := range m {
		delete(m, k)
	}
	fmt.Printf("delete all : %.1f MB, len=%d  ← len 归零内存不动\n",
		memMB(), len(m))
	m = nil
	runtime.GC()
	fmt.Println("m = nil    : heap released")
}
```

[实测] 输出：`insert 10w: 2.5 MB, len=100000` → `delete all: 2.5 MB, len=0`（**len 归零、内存纹丝不动**）→ `m = nil: heap released`——「delete ≠ 释放」的铁证；完整重整方案与 0.3MB 对比数据见 920。

## ⚠️ 原文纠错
1. 术语核校： [经验] 原文将 Go 语言与 GC 音转为多组同源崩坏串、nil 音转为「leo/neo」、键值对音转为「建值队/建置队」、ReadMemStats 音转为「readmemorystate」、遍历音转为「便利」，本卡统一为规范术语，不列举原词。
2. 事实核校： [经验] 原文「因为扩容机制所以删除不回收空间」的因果要讲准——不是「扩容机制顺带导致不缩容」，而是设计上**只实现增长路径**：渐进式搬迁把成本分摊到写操作上，删除没有对应的反向分摊机制；「懒迁移」即增量搬迁，术语已归一。
3. 补充核校： [经验] 实验中 delete 后需强制 `runtime.GC()` 才能对比——否则上轮未回收的垃圾会干扰读数；`len(map)` 归零但 `HeapAlloc` 不变是最直观的演示点。
