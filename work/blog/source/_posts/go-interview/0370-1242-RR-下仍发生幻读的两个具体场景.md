> 分类：MySQL 事务 | 难度：L4 | 题型：场景题 | 频率：中 | 关键词：**RR 幻读**/**更新带出**/**当前读可见**/**快照读局限**/**很大程度避免**

> 原文锚点：第 37~55 段「RR 下仍发生幻读的两类演示」

## 一句话总述
RR 靠快照读「**很大程度上**避免」幻读，但**不是完全避免**。两个具体陷阱：① 本事务对别事务**新插入且已提交**的行执行了 UPDATE/DELETE（当前读），该行被拉进本事务后，再查就能看到它；② 本事务用**当前读**（`FOR UPDATE`/`FOR SHARE`）去查，直接看到别事务已插入的行。两者都让 RR 下的幻读「复现」。

## 面试官视角
这是幻读里最容易被忽略的进阶点。背「RR 避免幻读」的人九成答不出「那为什么还会发生」。能说出「更新把新插入行拉进本事务」和「当前读绕过快照」两个机制，并强调「很大程度上而非完全」，面试立刻分层。

## 主问答
**Q（面试官原话）：** 不是说 RR 避免幻读吗，为什么还会发生？

1. **RR 只「很大程度」避免**：快照读隔离了别事务的增删，但一旦本事务自己发起当前读，隔离就被打破——所以官方口径是「很大程度上避免」，绝非 100%。
2. **场景一·更新带出**：RR 下本事务快照读查不到别事务插入的 id=12；但若本事务**对该 id=12 执行 UPDATE**（当前读），这行最新数据被读入并锁定，随后再查就能看到它——幻读出现。本质是当前读打破了快照隔离。
3. **场景二·当前读直接可见**：RR 下本事务用 `SELECT ... FOR UPDATE` / `FOR SHARE` 去查别事务已插入的行，走的是最新已提交数据，直接看到那行——幻读出现。
4. **根因统一**：两类场景的根因都是「本事务脱离了快照读、改用当前读」，于是别事务已提交的插入对它就可见了。
5. **彻底解法**：要消除这两类幻读，得让当前读也拦住插入——即依赖间隙锁/Next-Key 锁锁住查询范围内的间隙，使别事务的 INSERT 被阻塞而非「插入后本事务当前读才看到」。

## 版本与兼容性
| 场景 | 隔离级别 | 是否幻读 | 根因 |
|------|----------|----------|------|
| 快照读查新插入行 | RR | 否 | 快照隔离 |
| 对本事务 UPDATE 新插入行后查 | RR | 是 | 当前读拉入 |
| `FOR UPDATE` 查新插入行 | RR | 是 | 当前读读最新 |
| 串行化 | SERIALIZABLE | 否 | 锁已挡插入 |

## 关键代码
```sql
-- 场景一：RR 下 UPDATE 把别事务插入的行拉进本事务
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM t WHERE id = 12;        -- 空（快照无此行）

-- 会话 B 插入并提交
INSERT INTO t(id) VALUES (12); COMMIT;

SELECT * FROM t WHERE id = 12;        -- 仍空（快照读）
UPDATE t SET a = 1 WHERE id = 12;     -- 当前读：把该行最新版本拉入本事务
SELECT * FROM t WHERE id = 12;        -- 此刻查得到 id=12（幻读复现）
```

## 总结与追问预判
核心：**RR 幻读的两个复现口子都是「脱离快照读改用当前读」**。追问拐向「间隙锁到底怎么锁」——备好「Next-Key 锁 = 记录锁 + 间隙锁，插入落在间隙则阻塞」（见 1235/1236 锁专题卡）。
