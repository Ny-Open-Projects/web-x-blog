> 分类：Go 并发 | 难度：L2 | 题型：细节题 | 频率：中 | 关键词：**close、残留数据、不阻塞、零值、无缓冲、跨协程关闭**

> 原文锚点：第 15~22、49~51 段「从一个关闭的channel里面读取数据是不会发生阻塞的，即使这个channel是一个无缓冲的channel…如果关闭动作发生在一个新的协程中呢，那这个读取操作也是不会被阻塞的…当我们关闭channel之后，channel中的数据依然是可以读取到的…我们再读取这个数据，最终呢我们也是可以正常读取到channel里面写入的这条数据的」

## 一句话总述
`close` 的语义是"**关门**"而不是"**清空**"：关闭后**缓冲区里已有的数据依然可以被正常读完**，读完（或无残留）之后才开始反复返回**类型零值**；并且**读一个已关闭的 channel 永远不会阻塞**，即使它是无缓冲 channel，即使关闭动作发生在另一个 goroutine 里。

## 面试官视角
- 考察意图：是否把"关闭"误解成"丢弃数据"，以及是否知道读已关闭 channel 的阻塞性质。
- 分档：P5 知道关闭后读得到零值；P6 知道**残留数据先被读完**；P7 能补上"**无缓冲也不阻塞**"与"**关闭在别的 goroutine 中同样不阻塞**"。
- 红旗答案：以为 `close` 会把缓冲区数据丢掉、或以为读已关闭 channel 会 panic（`panic` 只发生在**写**和**重复关闭**上）。
- 惊艳点：**无缓冲 channel 关闭后读也不阻塞**——因为关闭状态本身就是一个"立即可得"的就绪条件，不需要等对端 `[源码]`。

## 主问答
**Q（面试官原话）：** channel 关了以后还能读到里面的数据吗？会阻塞吗？

1. **结论**：能读到。**关闭不等于清空**——关闭前已经写入、尚未被取走的数据**依然可以正常读取**，读完之后才开始反复返回**该 channel 元素类型的零值** `[源码]`。
2. **残留先读完**：示例里先写入一条数据再 `close`，随后读取**仍然能正常拿到这条数据** `[源码]`。所以正确心智模型是：`close` 只是**禁止再写入**，并把"读完"标记为"返回零值 + ok=false"。
3. **读永不阻塞**：从一个**已关闭**的 channel 里读取**不会发生阻塞**，**即使它是无缓冲 channel**，程序也能正常输出 `[源码]`。
4. **跨 goroutine 同样成立**：即使 `close` 发生在**另一个新起的协程**中，外面的读取操作**同样不会被阻塞**，程序可以正常执行到最后 `[源码]`。
5. **可以一直读**：实际上可以**一直**从已关闭 channel 中读出零值——示例里循环每隔一秒读一次，都会读到值（零值） `[源码]`。
6. **边界**：与之相对，**向已关闭 channel 发送数据会 panic**；关闭一个 `nil` channel 或**重复关闭**也会 panic `[源码]`。

**加分层：** 正因为"残留先读完 + 之后零值不阻塞"，`close` 才能被当作**广播通知**用：发送方写完再关门，接收方把活干完自然退出，不会因为读不到数据而卡死。

## 关键代码
```go
// 1) 关闭后残留数据仍可读完 —— close 是"关门"不是"清空"
ch := make(chan int, 2)
ch <- 100
ch <- 200
close(ch)
fmt.Println(<-ch) // 100 —— 残留照常读到
fmt.Println(<-ch) // 200
fmt.Println(<-ch) // 0   —— 读完之后才是零值

// 2) 读已关闭 channel 永不阻塞，即使是无缓冲的
uch := make(chan int) // 无缓冲
close(uch)
v, ok := <-uch // 立即返回 0, false，不阻塞
fmt.Println(v, ok)

// 3) 关闭动作在别的 goroutine 中，外面读同样不阻塞
ch2 := make(chan int)
go func() { close(ch2) }()
fmt.Println(<-ch2) // 0，不阻塞

// 4) 反例：向已关闭 channel 发送会 panic（注释掉才不崩）
// ch <- 1 // panic: send on closed channel
```

## 总结与追问预判
**最常见的追问是"那 for-range 呢"**——`for range` 遍历 channel 时，会把残留数据**全部读完**，读到关闭后才结束循环；所以 `for-range` 天然配合"写完后关闭"的模式。注意它**不能用来判断 channel 是否已关闭**（循环退出时只说明"已关闭且已读完"，且退出后无法再观察），判断关闭要用 `v, ok := <-ch` 的 `ok`。

## ⚠️ 原文纠错
1. 事实核校：关闭后残留数据可读、读完返回类型零值、读已关闭 channel 不阻塞（含无缓冲与跨协程关闭场景）、写已关闭 channel 与重复关闭 panic——均与 Go 语言规范一致 `[经验]`。
2. 补充：原文示例对"可以一直读下去"表述为"每读取一次休眠一秒仍读到值"，容易被误读成"一直读到真实数据"；准确说法是**残留读完后返回的是零值**，读到的是零值而非原数据 `[经验]`。
