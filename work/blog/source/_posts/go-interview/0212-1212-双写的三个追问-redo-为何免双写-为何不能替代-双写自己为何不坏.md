> 分类：数据库 / MySQL 存储 | 难度：L5 | 题型：追问题 | 频率：中 | 关键词：**512字节、block、扇区、原子写、物理日志、逻辑日志、undo、2MB连续空间、校验值**

> 原文锚点：第 27~45 段「为什么 redo log 不需要使用 doublewrite 的方式来保障写入磁盘的可靠性？主要原因是 redo log buffer 在内存中存储的方式是以 block 为单位进行存储的，每个 block 的大小是 512 字节，它和磁盘的扇区大小是一致的，这样的设计可以保证后续的写入都是原子性的，所以 redo log 是不存在部分写失败的情况…为什么 doublewrite buffer 持久化到磁盘的过程，就不会出现数据页损坏的情况？首先脏页的落盘是随机IO，而 doublewrite buffer 的落盘是顺序IO…它会在 IBdata 上划分出两兆b的连续空间…会在每个数据页结束的位置写入这个页的校验值，在进行数据恢复的时候会通过校验值跟页的数据进行对比，判断这个页数据是否完整」

## 一句话总述
三个追问的答案分别是：**① redo log 不需要双写**——它在内存里**以 512 字节的 block 为单位存储**，与**磁盘扇区大小一致**，因此**写入天然是原子的**，不存在部分写失败；**② redo log 不能替代 doublewrite**——它记录的是"**在某个数据页上做了什么修改**"，**页本身损坏时重做依然得到损坏的页**，必须有**完整页的副本**；**③ doublewrite 自己不易坏**——它是**顺序 IO**、写在 **IBdata 上划分出的 2MB 连续空间**、**每次 1MB 且在脏页落盘之前完成**，且**每个数据页结束位置会写入该页的校验值**，恢复时用校验值判断页是否完整。

## 面试官视角
- 考察意图：这三个问题是双写机制的"压力测试"，能全答出来基本可以判定为真正读过实现。
- 分档：P5 只答得出"redo log 也可靠"；P6 能答出 **512 字节对齐扇区**；P7 能三个全答，并**主动纠正"redo log 是逻辑日志"这一常见混淆**（那是 **undo log** 的特性）。
- 红旗答案：把 **undo log 的"逻辑日志 + 执行逆向操作回滚"** 说成 redo log 的特性。
- 惊艳点：**doublewrite 的可靠性不是靠"再双写一层"，而是靠"顺序写 + 校验值 + 时序保证"三件套**——写完双写才允许写数据页，双写没成功磁盘数据就不变 `[源码]`。

## 主问答
**Q（面试官原话）：** redo log 为什么不需要双写？能不能用它替代双写？

1. **结论**：redo log **不需要双写**（512 字节 block 对齐扇区，写入本身原子）；**也不能替代双写**（它记录页上的修改动作，页坏了重做无效，必须有页副本）`[源码]`。
2. **问题一 · redo log 为何免双写**：**redo log buffer 在内存中是以 block 为单位存储的**，**每个 block 的大小是 512 字节**，**它与磁盘扇区的大小一致**；**这样的设计可以保证后续的写入都是原子性的**，所以 **redo log 不存在部分写失败的情况** `[源码]`。
3. **问题二 · 为何不能互相替代**：**doublewrite 记录的是物理数据，也就是实际的数据页的数据**；**redo log 记录的是"在某个数据页上做了什么修改"**，**如果数据页本身发生了损坏，用 redo log 恢复已经损坏的数据块是无效的**——**数据页本身已经损坏，再次重做依然是一个损坏的页**。因此**当出现损坏的数据页时，就需要一个数据页的副本来还原** `[源码]`。
4. **问题二 · 顺带厘清 undo**：**回滚日志记录的是逻辑日志**，**回滚的时候是通过执行操作的逆向操作来实现的** `[源码]`——这是 **undo log** 的特性，不要与 redo log 混为一谈（详见纠错节）。
5. **问题三 · 双写为何自己不易损坏（原因一）**：**脏页的落盘是随机 IO，而 doublewrite buffer 的落盘是顺序 IO**，**写入效率非常高** `[源码]`。
6. **问题三 · 原因二（空间与时序）**：**doublewrite 和 redo log 一样存放在共享表空间当中**，**它会在 IBdata 上划分出 2MB 的连续空间**；**内存里的 doublewrite buffer 大小也是 2MB**，**落盘时每次写 1MB**，**并且这个动作发生在脏页持久化到数据表之前**——**只有 doublewrite buffer 成功写到磁盘之后，才会将脏页数据固化到磁盘；如果 doublewrite buffer 没有写成功，磁盘上的数据也就不会发生改变** `[源码]`。
7. **问题三 · 原因三（校验值）**：**doublewrite buffer 里面的数据页在持久化到磁盘时，会在每个数据页结束的位置写入该页的校验值**；**进行数据恢复的时候，会通过校验值与页数据进行对比，判断这个页数据是否完整** `[源码]`。

**加分层：** 把 doublewrite 的可靠性归纳为"**顺序写（不易撕裂）+ 时序保证（先副本后数据）+ 校验值（可判定）**"三条，比单纯说"它也在磁盘上"有说服力得多。

## 关键代码
```go
// Go 侧核对：redo block 大小、双写区位置与校验相关状态
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/go-sql-driver/mysql"
)

func main() {
	db, _ := sql.Open("mysql", "root:pass@tcp(127.0.0.1:3306)/mysql")
	defer db.Close()

	var name, value string

	// 1) redo log buffer 大小（内部按 512 字节 block 组织，与扇区对齐）
	db.QueryRow("SHOW VARIABLES LIKE 'innodb_log_buffer_size'").Scan(&name, &value)
	fmt.Println("innodb_log_buffer_size =", value)

	// 2) 双写开关
	db.QueryRow("SHOW VARIABLES LIKE 'innodb_doublewrite'").Scan(&name, &value)
	fmt.Println("innodb_doublewrite =", value)

	// 3) 双写写入页数与批次，用于观察"先副本后数据"的时序
	rows, _ := db.Query("SHOW GLOBAL STATUS LIKE 'Innodb_dblwr%'")
	for rows.Next() {
		rows.Scan(&name, &value)
		fmt.Printf("%s = %s\n", name, value)
	}

	// 4) 崩溃恢复时由校验值判定页完整性，再由 redo log 前滚
	// 可通过错误日志中的 "Database page corruption" / "dblwr" 关键字定位
}
```

## 总结与追问预判
**这三个追问几乎一定会连着问**，建议按"**对齐 → 补副本 → 怎么保证副本不坏**"的顺序一口气答完。最容易被追问到底的是第二条——**"redo log 到底记了什么"**：它记的是**页号 + 页内偏移上的物理修改**，前提是**页本身完好**；所以**坏页必须先靠副本还原，再重做**。若面试官继续问 undo，就答 **undo 是逻辑日志，回滚靠执行逆向操作**。

## ⚠️ 原文纠错
1. 事实核校：redo log buffer 按 512 字节 block 存储且与磁盘扇区一致、写入原子故无部分写失败、doublewrite 记录实际数据页的物理数据、redo log 记录页上的修改动作且页损坏时重做无效、坏页需副本还原、双写落盘为顺序 IO 而脏页落盘为随机 IO、双写占 2MB 连续空间且每次写 1MB、双写先于脏页落盘且失败则数据不变、每页结束位置写入校验值供恢复比对——均与 InnoDB 实现一致 `[经验]`。
2. 补充：**原文把"记录逻辑日志、回滚靠执行逆向操作"说成了 redo log，实际描述的是 undo log**；redo log 记录的是**到页的物理修改**，用于**崩溃恢复前滚**，两者不可混淆 `[经验]`。
3. 崩坏词归一：源码将 redo log、undo log、doublewrite、block、扇区、校验值、IBdata 等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
