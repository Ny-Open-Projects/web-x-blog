## 一句话总述
大 Key 的危害沿六条线扩散：**占内存**（碎片）、**拖单线程性能**（Redis 命令单线程，大值读写删都占 CPU）、**堵网络**（大流量打满带宽）、**伤持久化**（AOF always 阻塞主线程；AOF 重写/RDB 快照 fork 时复制页表、写时复制拷贝物理内存，大 Key 让二者极耗时）、**延主从同步**、**致集群倾斜**（单分片内存远超其他）。其中"写时复制 + 内存大页"是高频深挖点。

## 面试官视角
- 意图：考察"大 Key 为什么可怕"，能否讲清机制而非罗列现象。
- P5 知道大 Key 慢；P6 能讲单线程阻塞、网络、持久化三条；P7 能讲清 **fork 复制页表 + 写时复制物理内存 + 内存大页(2MB)放大拷贝量** 这一底层链路。
- 红旗：以为大 Key 只是"占内存"；不知道 AOF always 与 fork 写时复制的差别。
- 惊艳点：点出"内存大页让写时复制从拷贝 4KB 变成拷贝 2MB，哪怕只改 1 字节"。

## 主问答
**Q：** 大 Key 有哪些具体影响？
**A：**
1. **内存**：占内存多；过期大 Key 低频访问难被定期删除及时清，产生内存碎片。
2. **性能**：Redis 命令单线程执行，大 Key 的读/写/删都耗更多 CPU 与内存，拉低吞吐、延长响应。
3. **网络**：大值流量大，易打满局域网带宽，殃及同网其他服务（10MB×1000/s 即 10GB/s）。
4. **持久化**：AOF `always` 策略下大 Key 写入让主线程 `fsync` 阻塞很久；AOF 重写/RDB 快照 `fork` 时内核把父进程**页表复制**给子进程（不拷物理内存），但若子进程改了大 Key，**写时复制**会拷贝其物理内存——大 Key 让两步都极耗时、阻塞主进程。
5. **主从**：大 Key 传输/处理更久，易致主从同步延迟、数据不一致。
6. **集群**：大 Key 分片内存远超其他，造成集群数据倾斜。

## 关键代码
```go
// 大 Key 删除务必异步：UNLINK 后台回收，不阻塞主线程（对比 DEL 同步阻塞）
func safeDelBigKey(rdb *redis.Client, key string) error {
    // UNLINK：把回收工作交给后台线程，主线程立即返回
    return rdb.Unlink(ctx, key).Err()
    // 切忌 rdb.Del(ctx, key) —— 大 Key 同步释放会长时间阻塞单线程
}

// 线上曾遇 15GB+ hash 在集群 slot 迁移时阻塞，即大 Key 迁移风险
```
