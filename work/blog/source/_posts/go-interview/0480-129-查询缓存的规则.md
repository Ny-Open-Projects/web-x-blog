> 分类：MySQL 内核 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**查询缓存**/**SQL 哈希**/**命中条件**/**失效粒度**
> 原文锚点：第 3~16 段「查询缓存规则…k 是 SQL 哈希值」

## 一句话总述
查询缓存以 **SQL 语句的哈希值**为 key：只有 SQL **完全一致**（大小写/空格/注释/库/协议/字符集）才命中；不缓存子查询结果、不确定函数（`NOW()`/`RAND()`/`UUID()` 等）、警告查询、超大结果集、含自定义函数/存储函数/用户变量/临时表/系统表的查询、`SQL_NO_CACHE`、分区表（自动禁用）；结果集存于引擎层缓冲（MyISAM 在 OS cache、InnoDB 在 buffer pool）。

## 面试官视角
- 考察意图：是否理解"查询缓存命中条件极苛刻"这一设计软肋。
- 分档：P5 知缓存靠 SQL 哈希；P6 能列举不缓存的几类；P7 能讲清"分区表自动禁用"与"结果集存引擎层"等细节。
- 红旗答案：以为"只要查同样数据就能命中"——实际 SQL 文本有一点不同都不行。
- 惊艳点：点出 **key 是"SQL 文本的哈希"而非"查询结果"，所以注释不同都不命中** `[经验]`。

## 主问答
**Q（面试官原话）：** 查询缓存的命中规则是什么？
**A：**
1. **结论**：key = SQL 语句哈希，文本完全一致才命中；多类场景明确不缓存。
2. **机制**：Server 层拿到 SQL 后**不做任何改写**直接算哈希；子查询中间结果不缓存（只缓存最终集）；不确定函数因结果会变而不缓存；结果集超过 `query_cache_limit` 不缓存；含用户函数/临时表/系统表不缓存；显式 `SQL_NO_CACHE` 跳过；**分区表自动禁用查询缓存**。
3. **边界**：命中后甚至跳过解析/优化器/引擎交互，直接从内存返回，所以单次命中极快——但"命中难、易失效"使得这个收益常常得不偿失（见后续卡）。

**加分层：** 不同引擎缓存落点不同（MyISAM→OS cache，InnoDB→buffer pool），说明查询缓存是"叠加"在引擎缓冲之上的 Server 层缓存。

## 关键代码
```sql
SELECT SQL_CACHE * FROM t WHERE id=1;   -- 显式使用（旧版）
SELECT SQL_NO_CACHE * FROM t WHERE id=1;-- 显式跳过
SHOW VARIABLES LIKE 'query_cache_size';  -- 0 表示已关闭
```

## 总结与追问预判
查询缓存 key=SQL 文本哈希，命中条件极苛刻、易失效。追问接"为什么 8.0 移除它"的五大动因。
