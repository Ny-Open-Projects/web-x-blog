## 一句话总述
五种典型的不优雅错误处理：**① 记了日志又 return error（被处理两次）；② 日志缺上下文；③ 先判正常分支再处理 error（缩进爆炸）；④ 该直接 `return f()` 却多写一层 `err != nil`；⑤ 出错只 log 不 return（导致非法数据入库、返回 nil 假成功）**。优雅写法的核心是「错误只在一处决断」。

## 面试官视角
这题考「代码品味」和实战踩坑。考点：① 能否一眼看出五种反模式；② 优化后的写法为何好（缩进/单一职责/不丢错误）；③ 上下文怎么带（wrap）。能举出「序列化失败不 return」这种线上事故级反例，非常加分。

## 主问答
**Q（面试官原话）：** 有哪些不优雅的错误处理写法？怎么改？

**A：**
1. **记日志又 return error（处理两次）**：函数内 `log.Error` 后又 `return err`，调用方拿到 err 再记一次——日志重复、且「到底谁负责处理」模糊。优雅做法：**谁处理谁记日志**，中间层只 `return` 传递，最外层统一记。
2. **日志缺上下文**：只记「open failed」不知是哪个请求/ID。应用 `pkg/errors.Wrap`/`fmt.Errorf("%w")` 把 `teid` 等上下文包进错误链，外层一次拿到完整链路。
3. **先判正常再处理 error（缩进爆炸）**：`if ok { ...长业务逻辑... } else { return err }` 让正常逻辑嵌套多层。优雅写法**先 `if err != nil { return err }` 提前返回**，正常逻辑顶格写——「代码写给人看」。
4. **多余的 err != nil 判断**：`err := f(); if err != nil { return err }` 可化简为一行 `return f()`（当返回值就是 error 时），减少噪音。
5. **出错只 log 不 return（最危险）**：序列化失败后 `log.Error` 却没 `return`，函数最终返回 `nil`——非法数据被当成功写入 DB，引发脏数据/线上事故。优雅做法：**任何错误分支必须 return，绝不「记而不返」**。

## 版本与兼容性
- 上下文包装：`github.com/pkg/errors` 的 `errors.Wrap/Wrapf`（历史惯用法），或 **Go 1.13+** 的 `fmt.Errorf("...%s...: %w", id, err)`（标准库，推荐）。两者都让 `errors.Is` 可穿透。
- 「早返回 / 快乐路径顶格」是 Go 社区共识风格（Effective Go / Uber Go Style 均提倡）。
- 注意与 `123-error-log.md`（错误日志规范）互补：那张讲「日志怎么记」，本卡讲「错误在调用链中怎么流转不丢」。

## 关键代码

```go
// 片段：五种不优雅模式对比（pkg/errors 示意，讲解用）

import (
	"encoding/json"
	"errors"
	"fmt"
	"github.com/pkg/errors" // 或 Go1.13+ 用 fmt.Errorf("%w")
)

// ❌ 反模式 1+2+5：记日志又返回(双记)、缺上下文、序列化失败只 log 不 return(假成功)
func bad(id string, b []byte) error {
	var v Config
	if err := json.Unmarshal(b, &v); err != nil {
		fmt.Printf("unmarshal fail\n") // 没带 id 上下文，且没 return！
		// return err  ← 漏了这行，函数最终返回 nil，脏数据被当成功
	}
	save(v) // 用未初始化的 v，写入脏数据
	return nil
}

// ✅ 优雅：早返回 + wrap 带上下文 + 只 return 不在此层记日志
func good(id string, b []byte) error {
	var v Config
	if err := json.Unmarshal(b, &v); err != nil {
		return errors.Wrapf(err, "unmarshal config id=%s", id) // 带上下文，穿透 Is
	}
	return save(v)
}
```

## 总结与追问预判
收口：**错误只在一处决断——中间层 wrap+return，最外层记日志；任何错误分支必须 return；正常逻辑早返回顶格**。预判追问：① error 本质与类型断言（见 513.md`）；② 标准 wrap 实践（见 513.md`）。回答时把「记日志又 return = 处理两次」和「只 log 不 return = 假成功」两个坑点名，最显实战经验。

## ⚠️ 原文纠错
源视频转写将 error 处理相关术语（日志 / 包装 / 上下文 / 返回 等）音译为若干崩坏词，本卡已统一还原为规范术语（error / 日志 / errors.Wrap / fmt.Errorf / 返回 等）。交付卡禁止保留任何原词崩坏写法。

> **[经验]** 五反模式中**「只 log 不 return」最危险**——它制造「返回 nil 的假成功」，让非法数据静默入库，是真实线上事故源头。面试把它作为「最高危反模式」点出，比泛泛说「代码风格差」更有说服力；再补「记日志又 return 是处理两次」即满分。
