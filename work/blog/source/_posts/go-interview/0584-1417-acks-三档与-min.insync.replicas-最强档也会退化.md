> 分类：消息中间件 / Kafka | 难度：L3~L4 | 题型：陷阱题 | 频率：极高 | 关键词：**acks、0/1/all、min.insync.replicas、ISR、可靠性与吞吐**

> 原文锚点：第 11~24 段「ACKS 的默认值是一…设置为负一可以达到最强的可靠性，但是这并不意味着消息就可靠，因为 ISR 中可能只有 leader 副本」

## 一句话总述
`acks` 决定生产者等几个副本确认：**0 不等、1 等 leader（默认）、-1/all 等全部同步副本**；最强档会**因 ISR 只剩 leader 而退化**，必须靠 `min.insync.replicas` 兜底。

## 面试官视角
P6 背"all 最可靠"；P7 要说出**all 会退化**这个陷阱——追随者同步慢被踢出 ISR 后，ISR 只剩 leader，acks=all 就等同于 acks=1 `[源码]`。加分点：给出典型配置——副本 3、`min.insync.replicas=2` `[经验]`。

## 主问答
**Q（面试官原话）：** acks 设成 all 就一定不丢消息吗？

1. **默认档是 1**：默认值 1 表示只要分区 leader 写入成功就返回成功响应；若 leader 写入后还没被追随者拉取就宕机，**新选出的 leader 没有这条消息，消息丢失** `[源码]`。
2. **0 是吞吐优先**：设为 0 时生产者不等任何服务端响应，异常导致的丢失**生产者无从得知**；相同配置下吞吐量最大、可靠性最差 `[经验]`。
3. **-1 或 all 是可靠优先**：需等待同步副本集合中所有副本写入成功才返回；相同配置下可靠性最强 `[源码]`。
4. **但 all 会退化**：若 ISR 中只剩 leader 副本，acks=all 就演变成 acks=1，丢消息风险随之上升 `[实测]`。
5. **用最小同步副本数兜底**：`min.insync.replicas` 指定 ISR 中最小副本数（默认 1），不满足则写入抛异常；典型配法是**副本数 3、该值配 2** `[源码]`。
6. **可靠性换可用性**：该值抬高后，若 ISR 中副本不足，消息将无法写入——**宁可拒绝写入，也不要静默丢数据** `[经验]`。

## 关键代码
```go
// 高可靠组合：等全部同步副本 + 失败可重试 + 同步发送拿 error
w := kafka.Writer{
    RequiredAcks: kafka.RequireAll,   // 等价于 acks=-1/all
    Async:        false,              // 同步发送，异常直接返回
    MaxAttempts:  3,                  // 可重试异常自动重试
}
```
> 验证：`kafka-configs.sh --describe --entity-type topics` 核对 `min.insync.replicas=2` 且副本数为 3 `[实测]`。

## 总结与追问预判
**acks 管"等谁"，min.insync 管"至少有几个"**——两个参数必须配套。下一步必问未同步副本能否当 leader——接同批第 3 张卡。
