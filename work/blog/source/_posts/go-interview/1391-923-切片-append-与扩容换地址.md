> 分类：Go 语言基础 | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**append**/**扩容**/**底层数组替换**
> 原文锚点：第 32~74 段「函数内 append…扩容后地址改变、修改不反映外层」

## 一句话总述
切片 append 时：若 **cap 足够不扩容**，底层数组不变（新元素因外层 len 独立而对外层不可见）；若 **cap 不足触发扩容**，底层数组被拷贝到新地址，函数内切片指向新数组，此后任何修改/append 都不再影响外层。

## 面试官视角
- 考察意图：是否理解 append 的"扩容换地址"是切片传参陷阱的核心。
- 分档：P5 知 append 可能改变切片；P6 知扩容后函数内修改不影响外层；P7 能讲清"len 独立导致不可见"与"换地址"两层原因。
- 红旗答案：以为"只要共享底层数组，append 就一定反映到外层"。
- 惊艳点：拆成两个独立原因——① 不扩容时**外层 len 独立**使新元素不可见；② 扩容时**换底层地址**使后续修改不反映 `[经验]`。

## 主问答
**Q（面试官原话）：** 在函数里给切片 append，外面为什么有时候看不到？
**A：**
1. **结论**：append 是否反映到外层，取决于**有没有扩容**：不扩容→底层共享但外层 len 没变（看不见新元素）；扩容→底层数组换新地址，函数内此后修改与外层彻底无关。
2. **机制**：传参时 `len` 是直接部分、各自独立。不扩容时新元素写入共享数组，外层因自己的 len 仍是旧值而"看不见"（除非反射强改 len）；扩容时 Go 分配新数组、拷贝旧数据、函数内 ptr 指向新地址，外层 ptr 仍指旧数组。
3. **边界**：原函数内 append 后再改元素，若已扩容则改的是新数组，外层不变；若未扩容则改的是共享数组，外层可见（但新增元素仍因 len 不可见）。

**加分层：** 真实工程中"大切片 append 小数据"会意外长期持有大底层数组（内存 retention），可用 `s[len(s):cap(s):cap(s)]` 或 `append([]T{}, s...)` 切断。

## 关键代码
```go
func appendIn(s []int) {
    s = append(s, 5) // cap 够→共享底层；cap 不够→换地址
    s[0] = 6         // 若已扩容，改的是新数组，外层 a 不变
}
func main() {
    a := make([]int, 3, 3) // len=3,cap=3 → append 必扩容
    appendIn(a)
    fmt.Println(a) // [1 2 3]：扩容换地址，修改不反映
}
```

## 总结与追问预判
append 陷阱两层：len 独立导致不可见、扩容换地址导致不反映。工程上警惕大切片被小 append 长期持有。追问接"切片传参模型"与"map 为何不会这样"。

## ⚠️ 原文纠错
1. 机翻崩坏词归一：`耳pad`/`耳pend`→**append**；`速组`→**数组**；`类n`→**新（new）**；`排wergram`/`paragram`→**parameter（参数）**；`构`→**Go**。事实推理正确，仅术语崩坏，本卡已归一 `[经验]`。
2. 原文演示"反射强行把外层 len 改成 4 使不可见元素可见"——这是说明 len 独立的教具代码，生产勿用；本卡保留其原理说明但点明非生产用法。
3. 原文"假设函数中 append 很多元素导致扩容"追问是否会内存泄漏——原文结论"不会，函数内切片换地址后随 GC 回收"准确，本卡沿用并补充真实 retention 陷阱。
