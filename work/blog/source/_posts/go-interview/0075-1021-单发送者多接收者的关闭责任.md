> 分类：并发模型 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**fan-out** / **发送方关闭** / **WaitGroup**

> 原文锚点：第 56~77 段「一个发送者多个接收者：由发送者关闭 channel 并退出发送」

## 一句话总述
一个发送者、多个接收者（fan-out）时，关闭责任归**唯一发送者**：它在发完数据后 close，多个接收者 for-range 检测到关闭态即全部退出，干净无 panic。一句话背法：**「单发送者多接收者(fan-out)：关闭责任归唯一发送方，发完 close，接收方 for-range 自动退出；前提发送者唯一」**。

## 面试官视角
这是考察"关闭责任唯一"这一核心约定的题。
- **P5**：知道发送方关。
- **P6**：说清为何接收方不能关（会触发已关还写）。
- **P7**：知道多发送者要升级方案。
- **红旗**：让接收方去 close 数据 channel；多发送者也照搬此方案。
- **惊艳点**：发送方唯一 → close 必然只一次，且 close 时机在发送结束后，杜绝"向已关写" `[源码]`。

## 主问答
**Q（面试官原话）：** 一个 goroutine 发、五个 goroutine 收，谁关 channel？

**先铺垫（由浅入深第 1 层）**：channel 关闭最大的坑就是"谁来关"。一句话原则——**关闭责任唯一**。单发送者场景最简单：只有它有写的资格，自然也只有它来关，且关在发完之后。

1. **结论（第 2 层·机制）**：由**发送方**关闭；它在 for 循环发送完毕后再 close，接收方一律 for-range 读取 `[源码]`。
2. **机制（第 3 层）**：发送方唯一，close 只发生一次且位于发送之后；接收方读到关闭态自动退出，主协程用 WaitGroup 等齐 `[源码]`。
3. **边界（第 4 层）**：此方案前提是**发送者只有一个**；一旦多个发送者，接收方关数据 channel 会让别的发送方写已关 channel 而 panic `[源码]`。
4. **顺序（第 5 层）**：关闭前必须保证"不再发送"，close 时机在发送循环之后，顺序错就前功尽弃 `[经验]`。
5. **升级（第 6 层）**：多发送者必须换 stop channel 协调方案（见 1021 多发送者）`[边界]`。

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	ch := make(chan int)
	var receivers sync.WaitGroup

	// 5 个接收者：for-range 读到关闭态自动退出
	for i := 0; i < 5; i++ {
		receivers.Add(1)
		go func(id int) {
			defer receivers.Done()
			for v := range ch {
				_ = v
			}
			fmt.Println("receiver", id, "exited")
		}(i)
	}

	// 唯一发送方：发完后关闭（关闭责任归发送方）
	go func() {
		for i := 0; i < 10; i++ {
			ch <- i
		}
		close(ch) // 发送结束后关闭，接收方 range 自动收尾
	}()

	receivers.Wait()
	fmt.Println("all receivers done")
}
```

## 总结与追问预判
**背这三句就够**：① **关闭责任归唯一发送方**；② **发完 close，接收方 for-range 自动退出**；③ **前提发送者唯一，否则换方案**。
**预判追问**：
- 「多发送者怎么办？」→ stop channel 广播停发 + 协调者关闭（见 1021 多发送者）。
- 「关闭后读会怎样？」→ 得零值 ok=false，安全（见 1021 四条特性）。
- 「重复关闭？」→ panic（见 1019 重复关闭）。
