> 覆盖源 14-10 全文：删除脚本与控制器六步链路、手动删文件的野路子、`delete.topic.enable` 开关、磁盘 IO 影响，以及拓展问「为什么 topic 只支持加分区、不支持减分区」。主卡已给六步流程与命令，本附录做「删除为什么是异步状态机」「手动清理的三处落点」「缩容为何被放弃」「替代方案怎么落地」四层深挖。

## 思路与架构

```text
删除请求
├─ 阶段一(同步): 管理脚本写入待删除节点 → 客户端立刻返回
├─ 阶段二(异步/控制器):
│   ├─ 扫描待删除节点
│   ├─ 向各 broker 发 StopReplicaRequest(deleteFlag=true)
│   ├─ broker 停副本 + 清内存/磁盘
│   ├─ 清理副本后回写集群元数据
│   ├─ 移除 /config/topics 配置 + broker 本地配置
│   └─ 摘掉待删除节点 = 流程终态
└─ 兜底(手动): 元数据两处路径 + log.dirs 目录三处同时清
```

## 方案取舍
- **为什么不做成同步删除**：删除要动多个 broker 上的磁盘文件，动辄几十 GB、分钟级；若命令同步阻塞，客户端要么超时、要么长连接挂死。做成「标记 + 控制器异步推进」既让客户端立刻返回，又能失败后由控制器重试到终态 [经验]。
- **为什么不建议手动删文件**：手动要同时命中**三处**落点——元数据的 topics 路径、config 路径，以及 `log.dir`/`log.dirs` 下的数据目录。**漏一处就留下幽灵状态**：元数据还在但数据没了（broker 启动时可能报错），或数据还在但元数据没了（磁盘永远不释放）。脚本删除能保证三处原子推进，所以生产一律用脚本 [经验]。
- **缩容为何被放弃（核心是时间戳语义）**：分区一旦减少，老数据必须有归宿。① 随分区一起删除 → **消息直接丢失，可靠性不可接受**；② 追加到现有分区尾部 → 新消息时间戳反而小于旧消息，**分区内时间戳不再单调递增**，Spark/Flink 这类按时间戳做窗口与水位线的组件直接受影响；③ 分散插入现有分区 → 需要大规模内部数据复制，消息量大时占满带宽与磁盘，复制期间还要保证可用性 [经验]。
- **还要叠加的复杂度**：除了数据去向，缩容还要同时处理**消息顺序性**（重分布后同 key 不再落在同一分区）、**事务性**（跨分区事务状态）、以及**分区与副本的状态切换**。收益（少见的需求）远小于成本，官方直接不做 [经验]。
- **替代方案才是标准答案**：新开一个分区数更少的 topic，业务层双写一段时间后切消费端再切生产端，老 topic 走正常删除流程下线。这也是"缩容"在工程上唯一可行形态 [经验]。

## 答题技巧
- 被问「删除流程」先给结论句——**同步打标记、异步真删除**，再展开六步；只背命令会停在 P5 [经验]。
- 追问「能手动删吗」→ 答「能，但要同时清三处，漏一处留幽灵，所以只在脚本删不动的兜底场景用」[经验]。
- 追问「为什么不能减少分区」→ 按**丢数据 / 时间戳乱序 / 复制开销**三选一必踩的坑展开，再补顺序性、事务性、状态切换 [经验]。
- 主动给工程收口：「真要缩就新开 topic 切流」，这是面试官想听的落地动作 [经验]。
- 主动边界到 `1419-log-cleanup-policy`（日志段清理策略，是"段"级回收而非"主题"级删除）、`1419-partition-strategy`（分区数取值与 key 哈希），构成本地生命周期全栈 [边界]。

## 细节与核心 API

**删除是状态机：同步打标记、异步真删除：**

```bash
kafka-topics.sh --bootstrap-server b:9092 --delete --topic old_topic   # 客户端立即返回，控制器异步推进
# 手动清理三处落点（兜底，漏一处留幽灵状态）：
#   ① 元数据 topics 路径  ② 元数据 config 路径  ③ log.dirs 下数据目录
# 生产一律用脚本，保证三处原子推进
```

**缩容不支持，替代=新开 topic 切流：**

```bash
# 新开分区数更少的 topic，业务双写 → 切消费端 → 切生产端 → 老 topic 走删除流程下线
kafka-topics.sh --bootstrap-server b:9092 --create --topic new_topic \
  --partitions 6 --replication-factor 3
# 核心约束：分区一旦减少，老数据时间戳乱序 / 顺序性破坏 / 跨分区事务，收益远小于成本
```
