> 分类：并发模型 | 难度：L3 | 题型：工程题 | 频率：中高 | 关键词：**NumGoroutine、监控、WaitGroup、忙等**

> 原文锚点：第 85~97 段「打印当前携程数量…判断正在执行的任务数，没执行完就休眠等待」

## 一句话总述
`runtime.NumGoroutine()` 返回当前活跃的 goroutine 数，适合做**观测与告警**；但拿它轮询判断"任务跑完没有"是忙等，正确做法是等待组。

## 面试官视角
P6 说"用 NumGoroutine 判断结束"；P7 要划清界限——它是**计数器不是同步原语**：读到 0 不代表你的任务完成，别的组件也可能在起 goroutine `[经验]`。线上更该把它接进监控（配合 pprof 上报），而不是写在循环里 sleep 轮询 `[源码]`。

## 主问答
**Q（面试官原话）：** 怎么知道池里的任务都跑完了？

1. **观测用 NumGoroutine**：它返回进程中活跃 goroutine 总数，含运行时自身的，原文打印出 12 与 7 的对比 `[实测]`。
2. **它不是同步原语**：数值回落并不等于"我提交的任务已完成"，用它轮询是忙等且语义不可靠 `[源码]`。
3. **正确姿势是等待组**：提交前 `Add`、任务内 `Done`、主协程 `Wait`，或用池自带的等待能力 `[经验]`。
4. **线上要接监控**：把 goroutine 数通过监控组件上报，配合看板与阈值告警，而不是本地打印 `[源码]`。

## 关键代码
```go
var wg sync.WaitGroup
for i := 0; i < 100; i++ {
	wg.Add(1)
	_ = p.Submit(func() {
		defer wg.Done()
		time.Sleep(100 * time.Millisecond)
	})
}
wg.Wait() // 正确：等待全部完成
fmt.Println("goroutines:", runtime.NumGoroutine()) // 仅观测
```
> 验证：wg.Wait() 返回后 counter 必为 100；NumGoroutine 仅作打印佐证 `[实测]`。

## 总结与追问预判
**计数器归观测、等待组归同步**，两者别混用。这是并发工程里最容易被问穿的一条分界。

1. 事实核校：原文"循环判断正在执行的任务数、不为零就休眠等待"能让结果正确，但属**忙等**，本卡指出其局限并给出等待组正解 `[经验]`。
