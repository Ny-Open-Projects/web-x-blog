> 覆盖源 6-6 全文：从「循环 defer」到「有界并发池」的每一步动机与代价、句柄配额的完整体系（soft/hard/systemd/cgroup 四层）、WaitGroup 的正确使用细节、goroutine 池的三种实现取舍、大文件场景的内存维度。主卡已给四步演进与实测，本附录做配额体系与并发控制四层深挖。

## 思路与架构

```text
海量文件处理的四步演进 (每步解决上一步的一个具体死法)
├─ 1. 循环 defer          -> 死法: 句柄耗尽 (10 万 > soft 1024)
├─ 2. 封装函数用完即关     -> 死法: 串行太慢 (IO 是大头)
├─ 3. WaitGroup + go 无界 -> 死法: 协程堆积 (10 万 goroutine 栈) / 大文件内存
└─ 4. 信号量/池 有界并发   -> 终态: 并发度 = f(磁盘/网络/内存), 压测定档
句柄配额四层 (从外到内取最小)
├─ hard limit (root 可调)
├─ soft limit (ulimit -n, 进程生效)
├─ systemd LimitNOFILE (服务场景覆盖 shell)
└─ 容器 cgroup / k8s limits + 宿主 ulimit
```

## 方案取舍
- **每一步演进都在换约束**：第 1 步的死因是**句柄配额**（OS 层），第 2 步直接解决；第 3 步引入并发后，死因从「句柄」变成「**内存与调度**」（goroutine 初始栈 2KB，10 万个约 200MB 起步，还不算大文件 buffer）；第 4 步的池化是把「无界资源」换成「有界等待」——**排队在 channel 上，成本从内存变为延迟**。演进链的通用性在于：任何「批量稀缺资源」场景（连接、临时文件、内存块）都走同样的四步 [经验]。
- **句柄配额是四层不是一层**：shell 里 `ulimit -n` 看到的只是 **soft limit**（hard 通常 1048576）；**systemd 托管的服务**读的是 Unit 里的 `LimitNOFILE`（很多发行版默认也可能是 1024 级别，这就是「手动跑没问题、上服务就报错」的经典谜案）；**容器**里还有 cgroup 的 fd 配额与宿主 ulimit 叠加，取的是最紧的一层。排查口诀：**容器里进 Pod `ulimit -n` + `cat /proc/1/limits` 双查**，看到什么才算什么 [经验]。
- **WaitGroup 三个必踩细节**：① `Add(1)` 必须在 `go` 语句**之前**（放协程里会存在 Wait 提前通过、协程成孤儿的竞态）；② `Done` 用 `defer` 保证 panic 路径也执行；③ Go 1.25 起 `WaitGroup.Go(fn)` 内置了 Add+go+Done 的封装，但旧版本仍要手写三件套 [源码]。
- **goroutine 池三种实现的取舍**：① **信号量 channel**（`make(chan struct{},N)` 拿放令牌）——最少代码，协程还是每任务一个，只是同时活跃的有界；② **固定 worker 池**（N 个 worker 从 tasks channel 消费）——协程数恒定 N，任务队列天然缓冲，调度开销最小；③ **第三方池库**（ants 等）——带回收、监控、panic 处理。10 万级任务的基准选择是 ②，实现 20 行且无依赖；① 适合偶发的批量段 [经验]。
- **大文件场景的第二个维度**：并发度即便限到 10，若单文件 1GB 且 `os.ReadFile` 全量载入，内存峰值仍 10GB——**并发控制只管「同时几个」，不管「每个多大」**。解法是流式处理（`bufio.Scanner` 按行/块读，处理完即释放）+ 必要时对「同时载入内存的字节数」单独设限。池化限流与流式读取是**正交的两道闸**，缺一不可 [经验]。

## 答题技巧
- 用「四步演进」答题，每步说清「上一步会怎么死」——链式推演比直接报终态答案高一个档次 [经验]。
- 句柄上限主动报平台差异：Linux soft 1024 / 实测 macOS 1048575 / systemd 与容器另有覆盖层，显示踩过生产坑 [实测]。
- 被问「并发度怎么定」→ 别报数字，答「按 IO 类型分域 + 压测定档」：本地 NVMe 可几十、NFS/对象存储看远端、内存敏感场景还要乘上单任务内存 [经验]。
- 被问「为什么不直接调大 ulimit 到 10 万」→ 答 ulimit 只解决句柄层，协程堆积与大文件内存两层问题原样还在——**调配额不替代池化** [经验]。
- 主动边界到 `607-defer-mem-leak`（循环 defer 机制）、`604-defer-runtime.deep`（_defer 结构与性能）、`912-goroutine-scheduling.deep`（goroutine 栈与调度成本）、`820-sleep-vs-after`（定时资源），构成资源管理专题 [边界]。

## 细节与核心 API

```go
// 文件/连接：defer Close 释放句柄（fd 是有限资源，泄漏会 EMFILE）
f, _ := os.Open("x")
defer f.Close() // 务必检查 err：defer f.Close() 吞错，应 defer func(){ _ = f.Close() }()
// 句柄上限
//   ulimit -n / /proc/sys/fs/file-max
//   进程内：runtime/debug.SetMaxThreads 间接相关；fd 由 OS 限制
// 连接池：database/sql 自带 SetMaxOpenConns/SetMaxIdleConns，避免无限制开连接
db.SetMaxOpenConns(50)
db.SetMaxIdleConns(10)
// 终结器兜底（不推荐为主，仅兜底）：runtime.SetFinalizer(obj, cleanup)
```
