> 原文锚点：第 1~29 段「通过 switch 这种类型转化的方式对 interface 的具体类型进行断言…在转化过程中需要考虑溢出问题…通过 IntSize 拿到当前操作系统支持的 int 是 32 位还是 64 位…将 1 左移位数减一位…浮点型还应考虑精度问题」

## 一句话总述
把 `interface{}` 里任意宽度的数值类型安全地转成当前平台的 `int`，本质是两件事：**switch 类型断言**分派具体类型 + **逐类型做溢出防护**——先算出当前平台 int 的上下界（`strconv.IntSize` + 位运算），窄类型（int8/16/32）不可能溢出可直接转，宽类型（int64/uint32/uint64/string）必须先比对边界，**无符号类型范围比有符号宽，只可能超上界**。

## 面试官视角
- 考察意图：表面考 strconv 与断言语法，实际考**对「平台相关 int 宽度」的敏感度**——同一份代码在 32/64 位编译目标下行为不同，这是 Go 面试的隐藏分水岭。
- 分档：P5 会 `v.(int)` 断言和强制转换；P6 知道 `strconv.IntSize` 并能写出上下界判断；P7 能推导位运算边界的来历、指出 uint 只需判上界、并主动提浮点精度。
- 红旗答案：`v.(int)` 一把梭不处理 int64/uint64；认为「强转溢出会 panic」——Go 整数强转**截断不报错**，必须自己判断。
- 惊艳点：「uint64 的 `1<<63` 强转 int 会变成**负的最小值**，符号位被重新解释——实测验证过」 [实测]。

## 主问答
**Q（面试官原话）：** 写一个函数，把 interface{} 里的任意数值安全地转成 int，失败返回 error。
**A：**
1. **函数签名与分派**：`func ToInt(v interface{}) (int, error)`，用 **switch 类型断言**（`switch x := v.(type)`）分派到 int/int8/int32/int64/uint 系/string 各分支；不匹配的类型返回 error——这正是「类型断言 + 溢出防护」两个考点的合体 [源码]。
2. **先算平台边界**：`strconv.IntSize` 返回当前平台 int 位宽（32 或 64）。最大值 = `1<<(bits-1) - 1`，最小值 = `-1<<(bits-1)`（补码表示下负数比正数多一个）。实测 64 位平台：max=**9223372036854775807**、min=**-9223372036854775808** [实测]。
3. **窄类型直接转**：int8/int16/int32 的取值范围是 int 的**子集**（64 位平台），强转不可能溢出，直接转；int64 在 **64 位平台**也直接转，但在 **32 位平台**必须先比对上下界——这就是「同一份代码跨编译目标行为不同」的根源 [源码]。
4. **无符号类型只判上界**：uint 系没有负数、**表示范围比同宽度有符号宽一倍**，所以只有「超过 int 最大值」一种溢出方式。uint8/uint16 在 64 位平台安全；uint32/uint64 必须判 `value > maxInt`。经典坑：`uint64(1<<63)` 强转 int 得到 **-9223372036854775808**——符号位被重新解释，Go 不报错 [实测]。
5. **string 分支**：`strconv.ParseInt(s, 10, 64)` 转成 int64，出错原样返回 error；成功后仍要按平台位宽判断是否溢出 int（32 位平台下 `"9223372036854775807"` ParseInt 成功但转 int 会截断） [实测]。
6. **浮点是另一个维度**：浮点转整型考的是**精度**不是溢出——`int(3.99)` 直接截断为 3，`math.MaxInt64` 级别的 float64 已无法精确表示整数，先想清楚要不要 `math.Round` [经验]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Go 1.16 及以前 | `math.MaxInt` 常量不存在，需自己用位运算算 | 手算边界通用，兼容老版本 |
| Go 1.17+ | `math.MaxInt/MinInt` 常量内置，随平台位宽自动适配 | 新代码优先用常量，仍要懂位运算来历 |
| Go 1.18+ | 泛型 + `constraints.Integer` 可收敛重复分支 | 面试手写仍用 switch 断言版 |
| 32 位编译目标（GOARCH=386/arm） | int=int32，int64/uint64 全部要判溢出 | 判断逻辑不能写死 64 位假设 |

## 关键代码
```go
// 平台边界 + 溢出行为的实测验证
package main

import (
	"fmt"
	"strconv"
)

func main() {
	fmt.Println("strconv.IntSize =", strconv.IntSize)
	maxInt := int(^uint(0) >> 1) // 等价 1<<(bits-1)-1
	minInt := -maxInt - 1        // 等价 -1<<(bits-1)
	fmt.Println("int 最大值 =", maxInt)
	fmt.Println("int 最小值 =", minInt)
	_, err := strconv.ParseInt("9223372036854775808", 10, 64)
	fmt.Println("ParseInt 超范围 err =", err)
	var u uint64 = 1 << 63
	fmt.Printf("uint64 %d 强转 int = %d\n", u, int(u))
}
// [实测] 输出：IntSize=64；max=9223372036854775807；min=-9223372036854775808；
// ParseInt err = value out of range；uint64 9223372036854775808 强转 int = -9223372036854775808
```

## 总结与追问预判
一句话记忆：**「断言分派类型，边界只算一次；窄类型白送，宽类型必查，uint 只查上界，强转是截断不是报错」**。string/[]byte 零拷贝转换与版本演进见 906、`1113-string-byteslice-zerocopy.deep` [边界]。常追问「为什么不直接全部强转」——答 Go 整数强转是**静默截断**，测试环境 64 位跑不出问题、32 位嵌入式/老机器上才爆，属最难复现的一类线上事故；再追问「float 呢」——按主问答第 6 条答精度与截断。
