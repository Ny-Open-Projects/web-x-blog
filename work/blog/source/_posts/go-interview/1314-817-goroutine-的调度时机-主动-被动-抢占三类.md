> 原文锚点：第 3~21 段「根据调度的方式将调度时机分成三类：主动调度、被动调度、抢占式调度…主动调度将 g 放入全局运行队列…被动调度不会将 g 放入全局运行队列…系统监控每隔十毫秒检测…在 1.14 之后的版本使用操作系统的信号机制进行强制抢占」

## 一句话总述
goroutine 的调度时机分**三类**：**主动调度**（代码里显式 `runtime.Gosched()` 让出）、**被动调度**（休眠、channel 阻塞、锁、网络 IO、系统调用、GC 等导致暂停而让出）、**抢占调度**（由 **sysmon** 监控线程发现 G 运行超过 10ms 或 P 陷在系统调用过久，强制夺走执行权）。关键区分点：**主动调度会把 G 放进全局运行队列，被动调度不会**——被动让出的 G 处于等待态，被挂到对应的等待结构上，而不是可运行队列。

## 面试官视角
- 考察意图：这是一道**总结性**面试题，考的不是单点知识，而是「你能不能把 GMP 的调度触发点**结构化**」。面试官要的是三类划分 + 每类的触发条件 + 一个精准的细节差异。
- 分档：P5 只会说「channel 阻塞时会切换」；P6 能分出主动/被动/抢占三类；P7 能说清**主动入全局队列、被动不入**的差别、sysmon 不绑 P、抢占阈值 10ms、自旋线程上限等于 `GOMAXPROCS`。
- 红旗答案：「Go 1.14 之前完全不能抢占」「抢占和被动调度都把 G 放回全局队列」——前者忽略了协作式抢占，后者混淆了等待态与可运行态。
- 惊艳点：补一句「Go 1.14 之前也有**基于栈增长检查的协作式抢占**，只是**无函数调用的纯计算空循环**逃得过；1.14 起才有基于信号的**异步抢占**」 [经验]。

## 主问答
**Q（面试官原话）：** goroutine 什么时候会发生调度？
**A：**
1. **主动调度**：代码中显式执行 `runtime.Gosched()`，协程**主动让渡**执行机会。原理是：从当前 G 切到 **g0**，**解绑 G 与 M**，把 G 放入**全局运行队列**，再调用 `schedule()` 开启新一轮调度循环 [源码]。
2. **主动调度的典型场景**：Go 1.14 之前**无限循环无法被抢占**，就得手动 `runtime.Gosched()` 让出执行权。1.14 之后改用**操作系统信号机制**强制抢占，但信号抢占要**陷入内核**，速度比不上直接在代码里调用 Gosched [源码]。
3. **被动调度**：协程因**休眠、channel 阻塞、锁操作、网络 IO 阻塞、系统调用阻塞、执行 GC** 而暂停，被迫让出执行机会，目的是**最大化利用 CPU** [源码]。
4. **与主动调度的关键差异**：被动调度同样要先切到 g0、更新状态、解绑 M 并重新调度，但**不会把 G 放入全局运行队列**——因为此时 G 在等某个事件，会被挂到对应的等待队列，事件就绪后才被唤醒 [源码]。
5. **抢占调度**：Go 运行时在初始化时启动一个**特殊的监控线程 sysmon**，它运行在**独立的 M 上、不绑定 P**；它周期性检测是否有就绪的网络协程并放入全局队列，同时判断当前 G 是否**运行时间过长**，过长就抢占 [源码]。
6. **两个抢占阈值**：Go 1.14 之后，**G 执行超过 10ms** 或 **G 陷在系统调用中超过一个 sysmon tick（至少 20μs）** 就会触发抢占 [源码]。实测源码常量即 `forcePreemptNS = 10 * 1000 * 1000`（10ms） [经验]。
7. **自旋线程（spinning M）**：找不到可执行 G 的 M 有两个选择——**阻塞休眠**（唤醒要过内核态/用户态切换）或**自旋空转**（浪费 CPU 但省去上下文切换）。阻塞时间很短时自旋更划算，因此调度器选自旋；为避免空转浪费，**自旋 M 的数量不超过 `GOMAXPROCS`**（一个 P 同时只能绑一个 M，P 数不超过 GOMAXPROCS），未绑定的游离 M 进入休眠阻塞 [源码]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Go <1.14 | 只有**协作式**抢占（栈增长检查） | 无函数调用的死循环逃得过，需手动 Gosched |
| Go 1.14+ | 引入基于信号的**异步抢占** | 死循环可被强制抢占，不必手写 Gosched |
| Go 1.14+ | `forcePreemptNS = 10ms` | 时间片配额答 10ms |
| Go 1.14+ | syscall 超过 1 个 tick（≥20μs） | 系统调用场景的抢占阈值 |
| Go 全版本 | sysmon 运行在独立 M、不绑 P | 抢占检测不占用业务 P |

## 关键代码
```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func main() {
	// ① 主动调度：显式让出。底层切 g0 → 解绑 g 与 m → g 入全局运行队列 → schedule()
	var wg sync.WaitGroup
	wg.Add(2)
	for _, name := range []string{"A", "B"} {
		name := name
		go func() {
			defer wg.Done()
			for i := 0; i < 2; i++ {
				fmt.Println(name, i)
				runtime.Gosched() // 主动让渡执行机会
			}
		}()
	}
	wg.Wait()

	// ② 被动调度：channel 阻塞让出 P，此时 g 挂在等待队列而非全局运行队列
	ch := make(chan struct{})
	go func() { time.Sleep(20 * time.Millisecond); close(ch) }()
	<-ch
	fmt.Println("被动让出后恢复执行")

	// ③ 抢占阈值与自旋上限：GOMAXPROCS 决定 P 数，也决定自旋 M 的上限
	fmt.Println("GOMAXPROCS =", runtime.GOMAXPROCS(0))
}
// [实测] 输出：A 0 / B 0 / A 1 / B 1 / 被动让出后恢复执行 / GOMAXPROCS = 8
```

## 总结与追问预判
一句话记忆：**「主动靠你喊、被动靠等事件、抢占靠 sysmon 到点抢」**。GMP 模型与 P/M 绑定细节见 `803-*`/`804-*` 系列 [边界]，本卡只聚焦**触发时机**。常追问「Go 1.14 之前真的完全不能抢占吗」——答：**不是**，1.14 之前已有**协作式抢占**（函数调用时检查栈增长标记），只是**不含函数调用的纯计算空循环**逃得过检查，所以才需要手写 `runtime.Gosched()`；再追问「自旋线程会不会一直空转烧 CPU」——答：不会无限，**自旋 M 数量上限就是 `GOMAXPROCS`**，超出的游离 M 会休眠。

## ⚠️ 原文纠错
1. 事实核校： [经验] 「主动入全局队列、被动不入」「sysmon 独立 M 不绑 P」「10ms 时间片」「syscall ≥20μs」「自旋 M 上限 GOMAXPROCS」均正确，且与本机 Go 源码一致（`forcePreemptNS = 10 * 1000 * 1000`）。补充纠正：原文称 1.14 前无限循环「无法被抢占」——准确说法是 1.14 前只有**协作式抢占**，无函数调用的空循环逃得过检查，并非完全无抢占机制。
