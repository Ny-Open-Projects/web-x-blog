## 一句话总述
大 Key 处理六法：**拆**（string 拆多 key 或 hash field 拆分，集合按 field 取模分多 key）、**删**（UNLINK 异步删）、**短过期**（更小 TTL 让它快失效）、**淘汰**（开 LRU/LFU 优先逐出大 Key）、**扫**（低峰期 HSCAN/redis-cli --bigkeys/RDB 扫描定位）、**压**（响应数据 gzip 压缩后存，命中直接作 HTTP gzip 流返回）。

## 面试官视角
- 意图：考察"给出可落地的治理手段"，而非只会说"别用大 Key"。
- P5 知道拆分；P6 能说出 UNLINK 异步、LRU/LFU、scan 定位；P7 能讲"集合取模分片 + gzip 压缩 + 定时 UNLINK 清理"的组合拳。
- 红旗：用 DEL 删大 Key；用 SCAN 一次拉太多条数打爆服务。
- 惊艳点：点出"gzip 压缩后直接作 HTTP GZIP 流响应，服务端免二次解压"。

## 主问答
**Q：** 大 Key 怎么处理？
**A：**
1. **拆分**：string 拆成多个小 key（MGET 取回）；或存成 hash，各属性为 field（HGET/HMGET）。集合按 field 取模分多 key（如 100 万元素取模 100 分成 100 个小 key）。
2. **异步删**：用 **UNLINK** 异步回收，不阻塞主线程；绝不用 DEL 同步删大 Key。
3. **短过期**：值过大时设更小 TTL，到时主动 UNLINK 清理。
4. **淘汰**：开内存淘汰策略，用 **LRU/LFU** 在内存触顶后优先逐出低频大 Key。
5. **扫描定位**：低峰期用 HSCAN/LLEN/HLEN 控制每次条数遍历；或用 `redis-cli --bigkeys`、RDB 文件扫描定位大 Key。
6. **压缩存储**：响应数据先 gzip 压缩再存，命中时直接作 HTTP GZIP 流返回，服务端免二次解压。

// 集合大 Key 拆分：按 field 取模分成 N 个小 key
func splitBigHash(rdb *redis.Client, base string, fields map[string]string, n int) {
    for f, v := range fields {
        shard := fmt.Sprintf("%s:%d", base, hashField(f)%n) // 取模分片
        rdb.HSet(ctx, shard, f, v)
    }
}
// 定位：redis-cli --bigkeys（或低峰 HSCAN，控制 COUNT 避免打爆）
