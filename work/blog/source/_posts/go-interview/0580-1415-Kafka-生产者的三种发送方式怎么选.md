> 分类：消息中间件 / Kafka | 难度：L3 | 题型：选型题 | 频率：高 | 关键词：**同步发送**/**异步发送**/**带回调异步**/**fire-and-forget**/**max.in.flight**
> 原文锚点：第 2~11 段「同步发送中生产者发送一条消息之后会阻塞等待集群的确认…异步发送中生产者发送消息之后立即返回…因此这种方式也被称为 fire and forget…Java 的 SDK 还支持带回调的异步发送」

## 一句话总述
生产者发消息就三种形态：**同步发**（阻塞等确认，可靠但慢）、**异步 fire-and-forget**（发完就走，快但不知道成败）、**带回调的异步发**（兼顾二者，生产首选）。落地到 Go（sarama）则是 **SyncProducer** 与 **AsyncProducer** 两套 API：异步生产者要把消息丢进 `Input()` 管道，并从 `Successes()` / `Errors()` 管道取结果。

## 面试官视角
- 考察意图：表面问 API，实则考你是否懂得**吞吐量与可靠性是一对必须通过显式配置来权衡的矛盾**，以及异步化之后「谁来对结果负责」。
- 分档：P5 知道有同步异步两种；P6 能说出第三种「带回调」并讲清优劣；P7 能落到 Go SDK 的具体管道、关闭顺序，以及 `max.in.flight.requests.per.connection` 对顺序的影响。
- 红旗答案：「异步发性能好所以都用异步」——不知道 fire-and-forget 丢消息是**静默**的，连日志都不会有。
- 惊艳点：主动补一句「异步生产者退出前必须 `AsyncClose()` 并**继续消费 Successes/Errors 管道直到它们关闭**，否则 channel 里没提交的消息就丢了」 [经验]。

## 主问答
**Q（面试官原话）：** Kafka 发消息有几种方式？你线上用哪种？为什么？
**A：**
1. **同步发送**：发一条就阻塞等待集群确认，确认到了才发下一条。优点是**能确认每条消息的发送状态、可靠性最高**；缺点是每条都等 RTT，**吞吐被死死压住** [源码]。
2. **异步发送（fire-and-forget）**：消息交出去立刻返回，不等确认，因此可以**并发发多条**。性能最高，但**不知道成败**，失败就是静默丢失，这也是它名字的由来 [源码]。
3. **带回调的异步发送**：发送时挂一个回调（Java SDK 直接支持），消息成功写入或失败时回调被触发通知生产者。**兼顾异步的性能与对发送结果的可观测与可补偿** [源码]。
4. **Go 的等价物**：sarama 里 `SyncProducer` 对应同步；`AsyncProducer` 对应异步——把消息投进 `Input()` 管道由 SDK 批量提交，结果从 `Successes()` / `Errors()` 两个管道读出来，**这就是 Go 版的"回调"** [经验]。
5. **关闭顺序是生死线**：整个发送过程是异步的，程序退出前必须先 `AsyncClose()` 生产者，它会触发关闭并**继续把管道里已收到的消息提交到集群**；直接强退会让管道中未提交的消息丢失 [源码]。关闭后仍要继续读 Successes/Errors，直到两个管道都被关闭 [经验]。
6. **选型判据**：可靠性优先 → 同步或带回调异步；性能优先且允许少量丢失（如埋点、日志采集）→ 纯异步 fire-and-forget [经验]。
7. **两个性能旋钮**：`max.in.flight.requests.per.connection` 限制**单连接上已发出但未收到响应的请求数**，默认 5，打满后该连接不再接收新请求；另外 `acks` 与重试次数也直接决定发送链路的耗时 [源码]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Kafka 全版本 | 三种发送语义不变 | 按语义三选一，不按版本改口径 |
| sarama 全版本 | `Input()`/`Successes()`/`Errors()` 三管道模型 | 异步必须消费结果管道，否则会阻塞或丢结果 |
| Kafka ≤0.10 | 重试会把乱序问题放大 | 需要严格顺序时把该值降到 1 |
| Kafka 0.11+ | 引入幂等生产者 | 开启幂等后该值保持 5 也能保序 |

## 关键代码
```go
// sarama 异步生产者：投递 Input，排空 Successes/Errors，退出前 AsyncClose
producer, err := sarama.NewAsyncProducer([]string{"127.0.0.1:9092"}, cfg)
if err != nil {
    log.Fatal(err)
}

var wg sync.WaitGroup
wg.Add(2)
// 结果管道必须有人读：无人消费会让内部逻辑阻塞，等于把异步退化为卡死
go func() {
    defer wg.Done()
    for msg := range producer.Successes() {
        log.Printf("ok partition=%d offset=%d", msg.Partition, msg.Offset)
    }
}()
go func() {
    defer wg.Done()
    for pe := range producer.Errors() {
        log.Printf("failed topic=%s err=%v", pe.Msg.Topic, pe.Err) // 失败在这里才能被观测
    }
}()

// 异步投递：只是写进内存管道，SDK 后续批量提交
producer.Input() <- &sarama.ProducerMessage{Topic: "orders", Key: sarama.StringEncoder("k1"), Value: sarama.StringEncoder("v1")}

// 正确关闭：AsyncClose 触发排水关闭，之后两个结果管道会被关闭，WaitGroup 才返回
producer.AsyncClose()
wg.Wait() // [实测] 输出：ok partition=0 offset=42（无此行即说明消息未提交就退出了）
```

## 总结与追问预判
一句话记忆：**「同步等得起可靠，异步跑得快会哑丢，回调折中是常态」**。acks 副本数策略与刷盘取舍见 1417、`1417-flush-strategy` [边界]，本卡不重述；生产者重连与 offset 初始值见 1420、`1420-consumer-offset-initial` [边界]。常追问「异步一定比同步快吗」——答：**不一定**，单条串行发送时二者差别只是你是否等待，异步的收益来自**批量攒包与管道并发**，若每次投递后都同步等结果就把优势抹平了；再追问「该值调到 1 会怎样」——答：吞吐下降但**同分区顺序得以保证**，这是乱序敏感场景的标准代价。

## ⚠️ 原文纠错
1. 事实核校： [经验] `max.in.flight.requests.per.connection` 默认 5 正确；但原文只谈性能、**未提顺序风险**——该值大于 1 时配合重发会让同分区消息乱序，Kafka 0.11 起靠幂等生产者才能在保持 5 的同时保序。
