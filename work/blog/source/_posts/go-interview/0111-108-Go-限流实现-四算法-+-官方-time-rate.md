## 一句话总述
访问外部服务需限流防过载，常见四算法**固定窗口/滑动窗口/漏桶/令牌桶**；Go 官方 `golang.org/x/time/rate` 提供令牌桶：`rate.Limit` 设速率、`burst` 设桶容量、`Wait(ctx)` 在速率超限时阻塞（可超时放行）。一句话背法：**「限流四算法：固定/滑动窗口、漏桶、令牌桶；Go 官方 time/rate 令牌桶一行接入」**。

## 主问答
**Q（面试官原话）：** Go 里怎么给请求做限流？

**先铺垫（由浅入深第 1 层）**：限流和控并发数不是一回事——控并发数是"同时跑几个"，限流是"每秒放行几个"。目的都是保护下游，但限流关注的是时间维度上的速率。四算法解决的就是"怎么平滑地卡住速率"。

1. **四算法对比（第 2 层）**：
   - 固定窗口：按时间片计数，简单但有窗口临界突刺（两窗口交界可双倍放行）。
   - 滑动窗口：细分时间片平滑临界，精度高、内存略增。
   - 漏桶：恒定速率出水，强制平滑、突发被削平，但无法应对合法突发。
   - 令牌桶：恒定速率放令牌、桶可积攒，能吸收短时突发——最常用。
2. **官方库（第 3 层）**：`lim := rate.NewLimiter(rate.Limit(1), 3)` 表示每秒 1 个、桶容量 3（可突发 3）；`lim.Wait(ctx)` 超限时阻塞，`ctx` 设超时则超时放行。
3. **自实现（第 4 层）**：用 `time.Ticker` 按速率往带缓冲 `chan time.Time` 放令牌，请求侧从 channel 取令牌，取不到即受限。
4. **加分层（第 5 层）**：`burst` 即桶容量，等价于信号量的权重——允许短时突发；这是令牌桶相比漏桶的最大优势。
5. **误用风险（第 6 层）**：别把限流当控并发数用（二者目标不同）；`Wait` 不加超时可能无限阻塞；分布式场景单机限流不精准（见 108 分布式限流）。

## 关键代码
```go
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/time/rate"
)

// 官方令牌桶：每秒 1 个令牌，桶容量 3（允许短时突发 3）
func main() {
	lim := rate.NewLimiter(rate.Limit(1), 3)

	for i := 0; i < 6; i++ {
		ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
		start := time.Now()
		if err := lim.Wait(ctx); err != nil {
			fmt.Println(i, "超时放行:", err)
		} else {
			fmt.Printf("%d 放行，等待 %v\n", i, time.Since(start))
		}
		cancel()
	}
	// 前 3 个瞬时放行（桶里有 3 令牌），之后每 ~1s 放 1 个
}
```

## 总结与追问预判
**背这三句就够**：① **限流四算法：固定/滑动窗口、漏桶、令牌桶（最常用，吸收突发）**；② **官方 `rate.NewLimiter(rate.Limit(r), burst)` + `Wait(ctx)` 一行接入**；③ **`burst`=桶容量=允许短时突发；限流≠控并发数，Wait 要设超时**。
**预判追问**：
- 「限流和控并发数区别？」→ 限流卡速率、控并发卡同时数（见 108 何时控并发）。
- 「分布式怎么限流？」→ 令牌外置 Redis + Lua 原子（见 108 分布式限流）。
- 「漏桶和令牌桶区别？」→ 漏桶削平突发强制平滑，令牌桶允许突发（见本卡第 2 层）。
