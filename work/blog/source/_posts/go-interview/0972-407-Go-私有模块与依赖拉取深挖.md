## 思路与架构
把「Go 去哪儿拿代码」拆成**三条路径 + 三道校验**，所有配置变量都能对号入座：

- **三条拉取路径**：
  1. **代理路径** —— 走 `GOPROXY` 指定的模块代理，快、可缓存、可审计，是第三方依赖的默认通道。
  2. **回源路径** —— `direct` 或匹配 `GONOPROXY` 的模块，直接按模块路径连到版本控制系统（Git 等）拉取。
  3. **本地路径** —— `replace` 指向本机目录，只用于调试，不进入协作链路。
- **三道校验**：
  1. **校验和数据库**（`GOSUMDB`）比对 —— 防篡改，由 `GONOSUMDB` / `GOPRIVATE` 关闭。
  2. **go.sum 本地锁定** —— 记录模块哈希，二次构建时校验一致性。
  3. **vendor 目录** —— 把源码直接入库，彻底离线，代价是仓库膨胀与升级负担。

`GOPRIVATE` 之所以方便，是因为它同时把域名写进了「不走代理」与「不校验」两处——**一条配置切换两条路径 + 关闭一道校验**。理解这张图，就不必死记三个变量。

## 方案取舍
- **replace vs 远程仓库**：replace 改本地代码即时生效、调试效率最高，但把路径绑死在本机，协作者必须还原同样的目录结构；远程仓是唯一可持续的协作形态。**结论：调试用 replace，合入前必须切回远程。**
- **公网代理 vs 企业镜像**：公网代理零维护但受境外网络与上游可用性影响；企业镜像有运维成本，换来的是不被上游删 tag 拖垮 + 可插安全扫描。团队规模上来了就该建。
- **GOPRIVATE vs GONOPROXY + GONOSUMDB**：前者一条搞定，语义清晰；后者粒度更细，适合「要走内部代理但仍需免校验」这类混合场景。默认选前者。
- **GOINSECURE vs GOPRIVATE**：前者只放开 HTTP 与自签证书，**不关闭校验**；两者正交，自签证书的私有 Git 往往需要**同时**配置。这是最容易踩的坑。
- **vendor vs 模块缓存**：vendor 保证完全离线与可复现，适合交付给客户或高合规场景；日常用模块缓存 + go.sum 更轻。
- **伪版本号 vs 语义化 tag**：伪版本号能拉到任意提交，但不表达兼容性；对外发布的模块应打 tag，否则下游无法做版本约束。

## 答题技巧
- **先画路径再谈变量**：开口讲「代理 / 回源 / 本地三条路」，考官立刻知道你建立了模型，而不是背了几个变量名。
- **精准说清 GOPRIVATE 的两个作用**：「不走代理 **且** 不校验」——只说一半是最常见的失分点。
- **被问「拉不下来怎么办」按层排查**：模块路径是否与仓库地址一致 → 私有变量是否覆盖该域名 → Git 鉴权与 known_hosts → 自签证书是否需放开 → 代理是否可达。给出排查顺序比给结论更像做过。
- **主动补一个反常识点**：`GOINSECURE` 不关校验；`replace` 不会传递给下游模块（只有主模块的 replace 生效）。这两句能显著提升可信度。
- **收尾给可验证动作**：`go env` 打印变量、`go list -m all` 核对来源、CI 中固化 `go env -w` 并校验——有动作才像落地过。

## 细节与核心 API

```bash
# 私有模块：不走公共 proxy / 不做 checksum 校验
go env -w GOPRIVATE="git.company.com,github.com/org/private"
# 等价：GONOSUMDB / GONOSUMCHECK（旧）；GOPRIVATE 同时跳过 proxy 与 sumdb
go env -w GONOSUMDB="git.company.com"
# 拉取：需认证，配 git 凭证（SSH key 或 token）
git config --global url."git@github.com:".insteadOf "https://github.com/"
# 本地/未发布版本：用 replace 指向本地或特定分支（临时）
#   require github.com/x/y v0.0.0
#   replace github.com/x/y => ../y   （开发期）
# 注意：replace 仅本机/本模块生效，提交后他人需同样路径；发布前移除临时 replace
# 代理链路：GOPROXY（默认 proxy.golang.org,direct）；私有域经 GOPRIVATE 直连 git
```
