> 分类：并发模型 | 难度：中 | 题型：工程题 | 频率：高 | 关键词：**乐观锁、悲观锁、复合临界区、选型**

> 原文锚点：第 13~16 段「只需对某一变量并发读写用原子…多个变量用互斥锁」

## 一句话总述
单变量并发计数/状态切换用原子（**乐观、无锁**）；涉及多变量一致或带条件的复合操作必须用互斥锁（**悲观、护临界区**）。一句话背法：**「单变量无复合用原子（乐观），多变量一致/读判写用锁（悲观）」**。

## 面试官视角
考官考察"按场景选型"的判断力。能讲清单变量用原子、多变量/复合用锁、并点出"高竞争下需实测、原子并非银弹"，说明成熟；"原子永远比锁快"、所有并发无脑上锁，是红旗。
- **P5**：知道单变量用原子。
- **P6**：能讲多变量需锁。
- **P7**：知道高竞争下需实测选型，原子并非银弹。

## 主问答
**Q（面试官原话）：** 到底什么时候该用原子，什么时候该上锁？

**先铺垫（由浅入深第 1 层）**：选型和看病一样——先看"病灶"多大。如果只是"一个计数器 +1"这种单点操作，原子一个 CPU 指令就搞定，没必要请锁这个"重武器"；但凡是"先看后改、还要保持多个变量一致"的复合动作，原子就力不从心了，必须把整段护起来。

1. **结论（第 2 层）**：单变量、无复合条件的并发读写用原子；多变量一致或"读-判断-写"复合逻辑用锁。
2. **机制（第 3 层）**：原子是**乐观无锁**（假设冲突少、失败 CAS 重试），锁是**悲观**（进临界区前先独占），二者解决不同问题。
3. **边界（第 4 层）**：原子无法表达"多个变量要么都改要么都不改"的事务语义，这种必须用锁（如转账 A-1 且 B+1）。
4. **加分层（第 5 层）**：高竞争场景下锁一次独占可能优于原子反复重试，选型要**压测**而非凭感觉——`go test -bench` 看竞争曲线。
5. **误用风险（第 6 层）**：无脑原子去护复合逻辑会留竞态；无脑上锁去护单计数器则牺牲性能——按"变量数 + 是否复合"决策。

## 版本与兼容性
| 维度 | 说明 |
|------|------|
| 单变量 | 计数/状态位/标志 → atomic（乐观无锁） |
| 多变量/复合 | 读-判-写、事务一致性 → sync.Mutex（悲观） |
| 高竞争 | 锁一次独占可能优于原子重试，压测为准 |
| 类型化 | Go 1.19+ atomic.Int64 等免指针 |
| Go 版本 | 选型原则长期成立，本项目实测 Go 1.26.5 |

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	// ✅ 单变量无复合：原子足矣（乐观、无锁）
	var total atomic.Int64
	for i := 0; i < 1000; i++ {
		total.Add(1)
	}
	fmt.Println("total =", total.Load()) // 1000

	// ✅ 多变量一致 / 读-判-写 复合：必须锁（悲观、护临界区）
	var mu sync.Mutex
	balance := 100
	cost := 30
	mu.Lock()
	if balance >= cost { // 读-判断-写 是复合逻辑，原子表达不了
		balance -= cost
	}
	mu.Unlock()
	fmt.Println("balance =", balance) // 70
}
```

## 总结与追问预判
**背这三句就够**：① **单变量、无复合条件 → 原子（乐观无锁）**；② **多变量一致 / 读-判-写 → 锁（悲观护临界区）**；③ **高竞争下锁可能优于原子反复重试，选型要压测**。
**预判追问**：
- 「原子和锁性能差多少？」→ 单变量低竞争原子更轻，高竞争 CAS 自旋可能反超（见 104 原子陷阱 / 105 无锁原理）。
- 「读-判-写 能用 CAS 吗？」→ 能，但要 CAS 循环且小心 ABA（见 105 无锁原理 / 104 原子陷阱）。
- 「类型化原子有啥好？」→ Go 1.19+ atomic.Int64 免手写指针、编译期防类型错（见 104 原子本质）。
