> 分类：Go 并发缺陷 | 难度：中高 | 题型：工程题 | 频率：高 | 关键词：**context 取消、超时控制、协程池、channel 信号量、大文件分治、NumGoroutine 监控**

> 原文锚点：第 40~63 段「无退出机制→context 取消；无超时→设超时/协程池；占内存多→分而治之/文件流/协程池控并发」

## 一句话总述
防协程泄露本质是一个工程问题：**让每个协程都有确定的退出路径，并给并发数设上限**。`context` 取消给协程退出信号、超时防止长任务堆积、协程池/channel 信号量限制同时运行的协程数、大文件分而治之/流式处理避免单协程吃光内存；线上用 `runtime.NumGoroutine()` 看趋势、pprof 的 goroutine profile 定位。一句话背法：**「每个协程有退出路径 + 并发有上限 + 资源有分治 + 有监控，四件套防泄露」**。

## 面试官视角
考官看你能不能从「背坑」升级到「建防护体系」，给出可落地的治理手段。有体系（取消+超时+池化+分治+监控五连）说明你管过生产；只说「用完关掉」说明没真做过并发治理。
- **P5**：知道用 context 取消让协程退出。
- **P6**：知道超时 + 协程池/信号量控制并发上限。
- **P7**：知道大文件分治/流式处理 + 监控闭环（NumGoroutine 趋势 + pprof 定位）。

## 主问答
**Q（面试官原话）：** 生产上怎么系统地防协程泄露？别只说概念。

**先铺垫（由浅入深第 1 层）**：协程泄露的根源就一句话——协程被 `go` 出来了，却因为「没人通知它退」「没超时兜底」「并发无上限」而永远卡着。治理就是针对这三根因分别下药：给退出信号、给超时、给并发上限，再加监控把泄露暴露在爆炸前。

1. **context 取消（第 2 层·退出信号）**：for 循环读 channel 的协程必须监听 `ctx.Done()`，业务逻辑检测到完成/超时/不需执行时调 `cancel()`，子协程 `select` 到后 `return` 退出。
2. **超时控制（第 3 层·防堆积）**：访问外部子系统必须设超时（context 超时 / `http.Client.Timeout`）；无超时 + 下游故障 = 请求堆积、协程失控。
3. **并发上限（第 4 层·源头杜绝）**：用**协程池**或带缓冲的 **channel 信号量**限制同时运行的协程数，杜绝无界 `go func()`。协程池的本职就是给并发数设上限。
4. **大资源分治（第 5 层·防 OOM）**：读大文件/处理海量数据，拆成小段流式处理，避免单协程把内存吃满 OOM。
5. **监控闭环（第 6 层·第一现场）**：`runtime.NumGoroutine()` 打印趋势，数量只增不减就是泄露信号；pprof goroutine profile 抓现场栈。监控是第一现场，能先于 OOM 报警。

## 版本与兼容性
| 维度 | 说明 |
|------|------|
| context 标准库 | Go 1.7+ 引入 `context`，取消语义稳定至今 |
| 信号量写法 | 带缓冲 channel `sem := make(chan struct{}, N)` 是最轻量的并发上限实现（亦可用 `golang.org/x/sync/semaphore`） |
| 监控 API | `runtime.NumGoroutine()` 全版本可用；pprof `goroutine` profile 全版本可用 |
| 协程池 | 标准库无内置池，常用 `ants` 等三方库，或自行 channel 信号量实现 |
| Go 版本 | 治理手段与 Go 版本无关，本项目实测 Go 1.26.5 |

## 关键代码
```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"time"
)

func main() {
	// ① context 取消：子协程监听 Done 主动退出
	ctx, cancel := context.WithCancel(context.Background())
	go func() {
		for {
			select {
			case <-ctx.Done():
				fmt.Println("worker exit:", ctx.Err())
				return
			// case v := <-ch: handle(v)
			}
		}
	}()
	cancel() // 业务完成/超时 → 通知退出

	// ② 协程池式信号量：限制同时最多 10 个协程，从源头杜绝无界创建
	sem := make(chan struct{}, 10)
	tasks := make([]int, 100)
	for _, t := range tasks {
		sem <- struct{}{} // 占坑，满了就等
		go func(task int) {
			defer func() { <-sem }() // 退出还坑
			time.Sleep(10 * time.Millisecond)
			_ = task
		}(t)
	}

	// ③ 监控闭环：NumGoroutine 只增不减就是泄露信号
	fmt.Println("current goroutines:", runtime.NumGoroutine())
}
```

## 总结与追问预判
**背这三句就够**：① **每个协程都要有退出路径（ctx 取消 + 超时兜底）**；② **用协程池/channel 信号量给并发数设上限，杜绝无界 go**；③ **大文件分治/流式 + NumGoroutine/pprof 监控闭环**。
**预判追问**：
- 「context 是怎么传播的？」→ 沿调用链往下传，cancel 时整条链收到信号（见 602 context 传播）。
- 「channel 信号量和协程池区别？」→ 信号量是并发上限原语，协程池还管复用与队列（见 1016 令牌桶 vs 信号量）。
- 「具体有哪些代码写法会泄露？」→ 见 1022 触发场景（defer 误用/nil channel/空 select）与 1019（channel 三形态）。
