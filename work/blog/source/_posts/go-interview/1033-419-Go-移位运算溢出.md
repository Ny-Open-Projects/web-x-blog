> 原文锚点：第 1~20 段「uint16 移位溢出与类型推断」

## 一句话总述
Go 的移位/算术运算**按操作数类型**推断结果类型：把 `uint16` 的变量左移超过其位宽，常量 `1` 也被当 `uint16` 处理，结果溢出归零——比较因此得出错误结论，需显式转 `uint32` 修复。

## 面试官视角
- 考察意图：常考"为什么 1<<16 在 uint16 下没报意料结果"——类型推断导致的静默溢出。
- 分档：P5 知移位会溢出；P6 知 Go 按操作数类型推断；P7 知溢出归零 + 显式转型修复。
- 红旗答案：以为 `1` 永远按 int 算、移位不会悄悄溢出。
- 惊艳点：点出"无类型常量按上下文操作数类型确定类型"这一底层规则。

## 主问答
**Q（面试官原话）：** 下面这段 Go 为什么移位后结果不对？
**A：**
1. **类型推断**：`s` 是 `uint16`，无类型常量 `1` 在 `s << 16` 中按 `uint16` 处理——所以 `1<<16` 在 uint16 域里**溢出归零**，不是算术 65536。
2. **错误比较**：`s=65535 > (1<<16 按uint16=0)` → `65535>0` 为真 → 误判"未溢出"(shiftOK)；而期望是 `s > 65536` 才该 shiftNotOK。
3. **修复**：先 `uint32(s)`，再用 `uint32(1) << 16`，结果在 uint32 域正确为 65536，比较 `65535 > 65536` 为假 → shiftNotOK。
4. **本质**：Go 不会隐式把结果提升到更大类型；溢出是"模 2^N 回绕"（uint16 下 65536 mod 65536 = 0）。

## 关键代码
```go

// 错误：1 按 uint16 处理，1<<16 溢出为 0
if s > (1 << 16) { /* 误判 */ }
// 正确：显式转 uint32
if uint32(s) > (uint32(1) << 16) { /* 正确 */ }
```

## 总结与追问预判
Go 移位/运算按操作数类型定结果类型，无类型常量跟随上下文；uint16 下 1<<16 溢出归零导致误判，修复是显式转更大宽度类型。溢出本质是模 2^N 回绕，非报错。
