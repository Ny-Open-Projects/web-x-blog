> 分类：Elasticsearch · 分布式写入 | 难度：L3 | 题型：架构题 | 频率：高 | 关键词：**协调节点**/**routing 哈希**/**主分片取余**/**分片位置**/**主分片数不可改**
> 原文锚点：第 2~9 段「集群任意节点可接收请求并转发，承担转发者即协调节点；协调节点用 routing 哈希后对主分片数取余定位目标分片」

## 一句话总述
ES 集群中**任意节点都能接收读写请求**，承担"接收并转发"角色的节点叫**协调节点**（coordinating node）；它用 `hash(routing) % 主分片数` 定位文档所属分片，而**全节点都缓存分片→节点位置表**（仅主节点可更新）——正因主分片数参与路由计算，**主分片数一旦设定不可修改**，且分片数须 > 节点数并预留扩展位。

## 面试官视角
- 考察意图：是否理解 ES 请求从"客户端"到"目标分片"的寻址链路，以及"主分片数为何不可改"。
- 分档：P5 知协调节点转发；P6 知 routing 取余定位、全节点缓存分片位置；P7 能推导"主分片数不可改 + 分片数>节点数"的工程结论。
- 红旗：以为请求直达目标分片；或以为副本数参与路由；或以为改主分片数不影响存量数据。
- 惊艳点：点出"主分片数参与 hash 取余 → 改主分片数会让既有 routing 全部错位 → 故不可改"，以及"分片数须 > 节点数 + 预留，才能水平扩展新节点"。

## 主问答
**Q（面试官原话）：** 一个写请求从客户端发到 ES，是怎么找到目标分片的？
**A：**
1. **协调节点**：客户端请求落到哪个节点，哪个节点就临时充当协调节点——负责按 routing 算分片、把请求转发到持有该分片的数据节点、汇总返回。生产上常**关掉其他角色、专设协调节点**保角色独立 `[经验]`。
2. **routing 取余定位**：`routing` 默认是文档 `_id`；算法为 `hash(routing) % 主分片数` 得到分片编号。写入未指定 ID 时 ES 自动生成；指定 ID 时还要先查目标分片有无同 ID（多一次磁盘 IO）。
3. **分片位置**：集群**每个节点都保存全量分片位置表**，但**只有主节点能更新**它；协调节点查本地缓存即可知"分片在哪台节点"，无需问主节点。因为主分片数参与路由计算，**主分片数设定后不可改**（改了存量文档 routing 全部错位）。

## 关键代码
```go
// Go 侧：写文档时显式带 routing，让同维度数据落到同一分片
_, err := cli.Index().
    Index("orders").
    Id("o-1001").
    Routing("u123"). // 用 UID 作 routing
    BodyJson(order).
    Do(ctx)
// 查询同一用户订单时也带相同 routing，请求只打到固定分片，避免全分片广播
_, _ = cli.Search().Index("orders").Routing("u123").Query(termQ).Do(ctx)
```

## 总结与追问预判
协调节点 + routing 取余 + 全节点缓存位置，是 ES 分布式写入寻址的三件套；主分片数不可改是其直接推论。追问常接"routing 对写入/删除的影响"与"主副本 refresh 时机不同导致查询结果震荡"。
