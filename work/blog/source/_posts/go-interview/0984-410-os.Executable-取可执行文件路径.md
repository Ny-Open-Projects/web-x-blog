## 一句话总述
`os.Executable()`（go1.8+）返回当前进程 exe 的绝对路径；`go run` 时仍是临时文件不可用，`go build` 后可靠；部署用软链时需 `filepath.EvalSymlinks` 还原真实目录。

## 面试官视角
- 意图：是否知道该 API 的版本与 go run 陷阱，及软链处理。
- P5 知 Executable 取 exe 路径 / P6 知 go1.8 引入 + 软链需 EvalSymlinks / P7 知生产用 build 产物。
- 红旗：以为 go run 下 Executable 可用；以为返回的是源码目录。
- 惊艳点：Executable 不自动 Abs 转换，`go run` 临时路径已绝对，Abs 也救不了 `[源码]` os 包。

## 主问答
**Q（面试官原话）：** 除了 Args[0]，还有别的方式拿 exe 路径吗？
**A：**
1. **结论**：`os.Executable()` 直接返回当前 exe 绝对路径，比 Args0 语义更清晰。
2. **机制**：go1.8 引入；`go run` 内部仍生成临时 exe，故此时返回临时路径，`go build` 后才是真实路径。
3. **边界**：它不做软链解析；部署用软链指向 exe 时，要用 `filepath.EvalSymlinks` 取真实目录 `[源码]`。
**加分层：** 比 Args0 更稳，因为不依赖命令行如何调用，但仍受 go run 临时文件影响。
