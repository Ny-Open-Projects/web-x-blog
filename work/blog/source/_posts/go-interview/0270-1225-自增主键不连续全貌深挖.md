## 思路与架构
自增主键由存储引擎（InnoDB）维护一个**计数器**，插入时原子地"取当前值+1 并分配"，分配与唯一性校验、事务提交解耦，因此失败/回滚都不回收——这是"递增不连续"的根本设计取舍。

## 方案取舍
- **为何不回收洞**：回收需加锁查 `MAX(id)` 并串行化自增申请，直接牺牲高并发写入吞吐；MySQL 选择"宁可留洞"换并发。代价是 ID 空间浪费，但 ID 本就不该承载业务连续性语义。
- **8.0 持久化 vs 之前**：8.0 前计数器在内存，重启依 `SELECT MAX(id)+1` 重建→洞会被复用（看似"恢复连续"却破坏预期）；8.0 存入数据字典（redo 保护）后重启仍从原值续，行为可预期。
- **offset/increment 双主法 vs 现代 GTID**：双主奇偶分流是经典但要求双写、运维复杂；现代多单写+GTID 复制，自增冲突问题自然消失。
- **INT vs BIGINT**：有符号 21 亿、无符号 42 亿在高速写入下很快触顶；新表直接 BIGINT 或业务层雪花 ID 是更省心的选择。

## 答题技巧
1. **先给总括**：自增=递增非连续，6 类原因（回滚/唯一冲突/删除/显式ID/offset-increment/手动ALTER）张口即列。
2. **抓分水岭**：8.0 持久化是必考题，一句话点出"内存重建→洞复用"与"字典持久化→洞永久"的翻转。
3. **对比记忆**：唯一索引冲突**留洞**、主键显式冲突**不留洞**——同一"冲突"二字结果相反，最易被追问。
4. **落到工程**：业务绝不能依赖自增连续性；大表用 BIGINT/雪花；双主用 offset+increment 奇偶分流（或干脆单写+GTID）。
5. **反直觉点**：① TRUNCATE 不可回滚且归零；② 溢出是硬错误不覆盖、且删低值也救不回（只增不减）；③ ALTER AUTO_INCREMENT 只能调大。

## 细节与核心 API

**自增计数器由 InnoDB 维护，分配与事务提交解耦 → 回滚/失败不回收（递增不连续）**：

```sql
SHOW VARIABLES LIKE 'auto_increment%';
-- auto_increment_offset / auto_increment_increment（双主奇偶分流）

-- 8.0 前：计数器在内存，重启依 MAX(id)+1 重建 → 洞复用
-- 8.0  ：计数器存入数据字典（redo 保护），重启仍从原值续 → 洞永久
```

```text
INT 有符号 21 亿 / 无符号 42 亿上限；大表直接 BIGINT 或业务层雪花 ID
反直觉：TRUNCATE 不可回滚且归零；溢出是硬错误；ALTER AUTO_INCREMENT 只能调大
唯一索引冲突 → 留洞；主键显式冲突 → 不留洞（同一"冲突"二字结果相反）
业务绝不能依赖自增连续性
```
