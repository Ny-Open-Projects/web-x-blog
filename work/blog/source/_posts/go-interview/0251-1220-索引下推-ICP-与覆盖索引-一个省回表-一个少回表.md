> 分类：MySQL / 索引优化 | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**ICP**/**索引下推**/**覆盖索引**/**回表**/**Using index condition**
> 原文锚点：第 1~27 段「查询只获取索引字段的值就不需要回表，这种查询方式称为索引覆盖…name LIKE '%b' 无法用到索引列的范围区间，但毕竟只涉及 name 列…MySQL 5.6 之后先不急着回表，先检测这条记录是否满足 LIKE 条件，不满足就没有必要回表了…把这个改进称为索引条件下推」

## 一句话总述
两者都是「少回表」的优化，但**砍的位置不同**：**覆盖索引**——查询所需列全在二级索引里，**彻底不回表**（EXPLAIN：`Using index`）；**索引下推 ICP**——WHERE 里的**非范围条件**（如 `name LIKE '%b'`）**下沉到存储引擎层**，在二级索引扫描时就地过滤，**不满足的直接跳过回表**——回表次数从「范围内全部」降到「过滤后剩余」（EXPLAIN：`Using index condition`）。ICP 是 MySQL 5.6 引入的优化。

## 面试官视角
- 考察意图：一句话题目两层考——① 能否各自讲清机制（多数人只背「覆盖索引免回表」）；② 能否说准**区别**（覆盖=不回表，下推=回表前先过滤）并落到 EXPLAIN 标志。
- 分档：P5 知道覆盖索引免回表；P6 能完整复述 ICP 场景（范围条件+无法入区间的同列条件）与回表次数下降的账；P7 能给出 EXPLAIN 两标志对比、ICP 的适用/失效边界（跨列、函数）。
- 红旗答案：「索引下推就是把索引推到磁盘上」；以为下推和覆盖互斥——同一查询里二者可同时不出现/只出现其一。
- 惊艳点：「**回表是随机 IO**——主键值不连续，每次回表一次随机读；ICP 把过滤提前到索引层，等于用『顺序扫索引的便宜』替代『多次随机回表的昂贵』」 [经验]。

## 主问答
**Q（面试官原话）：** 索引覆盖和索引下推有什么区别？
**A：**
1. **背景：回表为什么贵**。二级索引叶子只存**索引列 + 主键值**；查非索引列就要拿主键回聚簇索引取整行——且二级索引返回的主键**不连续**，每次回表都是**随机 IO**，是二级索引查询的最大开销 [源码]。
2. **索引覆盖：彻底免回表**。查询所需**所有列都包含在索引中**（如只在 name 列有索引、只查 name），直接从二级索引叶子取值返回，**全程不碰聚簇索引**——EXPLAIN Extra 显示 `Using index`。这也是不鼓励 `SELECT *` 的原因之一：星号让覆盖失效 [源码]。
3. **索引下推的场景**：条件里**混着能走范围与不能走范围的条件**——`WHERE name > 'c' AND name LIKE '%b'`：`name > 'c'` 能构造范围区间定位二级索引；`LIKE '%b'` 无法构成区间。**没有 ICP 时**：按 `name > 'c'` 拿到范围内所有二级索引记录 → **逐条回表**取整行 → 再在 server 层过滤 `LIKE '%b'`——大量回表白白浪费在最终被过滤的行上 [源码]。
4. **ICP 的改进（5.6+）**：把 `LIKE '%b'` 条件**下推到存储引擎层**——二级索引扫描时**先就地检测**该记录是否满足；不满足的直接跳过，**不执行回表**。由于二级索引叶子本来就有 name 列的值，这个检测是零成本的。回表次数 = 范围命中数 × LIKE 命中率，大幅减少 [源码]。
5. **区别一句话**：**覆盖索引 = 所需列全在索引 → 不回表**；**索引下推 = 条件列在索引里 → 回表前先过滤、少回表**。前者砍的是「要不要回表」，后者砍的是「回表多少次」。EXPLAIN 上分别对应 `Using index` 与 `Using index condition` [经验]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| MySQL < 5.6 | **无 ICP**：全部二级索引记录回表后 server 层过滤 | 老版本答不出 Using index condition |
| MySQL 5.6+ | ICP 引入，默认开启（optimizer_switch index_condition_pushdown=on） | 按本卡机制答 |

## 关键代码
```sql
-- 表: idx_name (name);  联合场景: idx_abc(a,b,c)
-- 场景1: 覆盖索引 (所需列全在索引 -> Using index, 零回表)
EXPLAIN SELECT name FROM t WHERE name > 'c';
-- Extra: Using where; Using index  <- 覆盖

-- 场景2: 索引下推 (范围+非范围同列条件 -> Using index condition)
-- name>'c' 可定范围; name LIKE '%b' 无法入区间, 但列在索引里可就地过滤
EXPLAIN SELECT * FROM t WHERE name > 'c' AND name LIKE '%b';
-- MySQL<5.6: 回表全部范围命中后 server 过滤
-- MySQL5.6+: Extra: Using index condition <- ICP, 回表次数=范围命中×命中率

-- 场景3: ICP 失效 (条件涉及索引外的列)
EXPLAIN SELECT * FROM t WHERE name > 'c' AND age = 20;
-- age 不在 idx_name 里, 索引层无值可判 -> 只能回表后过滤
-- [经验] 验证路径: EXPLAIN 看 Extra 标志; 开关对照: SET optimizer_switch='index_condition_pushdown=off' 对比
```

## 总结与追问预判
一句话记忆：**「覆盖=不回表（Using index）；下推=回表前先过滤（Using index condition，5.6+）；回表是随机 IO，能省则省」**。覆盖索引的设计手法与星号问题见 1222、`1246-covering-index`、`1239-select-star-vs-covering`、`1247-covering-index-split` [边界]。常追问「ICP 对联合索引的意义」——答联合索引 (a,b) 中 `a=1 AND b LIKE '%x'`：b 不能入区间但列在索引里，ICP 就地下推过滤，联合索引的后缀列价值大增；再追问「下推后还需要覆盖索引吗」——两者正交：ICP 减回表次数，覆盖消除回表本身，能覆盖优先覆盖。
