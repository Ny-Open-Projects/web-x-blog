> 分类：Go/运行时 | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**负载因子、翻倍扩容、等量重建、渐进迁移、不缩容**

> 原文锚点：第 5~31 段「元素达阈值触发扩容；overflow 过多但元素少触发数据重整；Go 不会一次性迁移完而是懒迁移；扩容后大小恒为 2 的幂」

## 一句话总述
map 扩容有**两个触发条件**：① 元素数超过「负载因子 × 桶数」→ **翻倍扩容**（桶数 ×2）；② 溢出桶/墓碑过多但元素很少（大量增删导致）→ **等量重建**（桶数不变，只整理回收碎片）。两种都不一次性搬完，而是**渐进迁移**：写操作顺带搬少量桶，迁移期间查找要同时查新旧两张表，搬完才释放旧表。**map 只增不缩**——删除元素不会归还内存。

## 面试官视角
P5 答「装不下了就扩容」；P6 要说出**负载因子**和**两个触发条件**；P7 必须补三件事：**渐进迁移**（避免一次性 STW 式抖动）、**删除不缩容**（生产内存只涨不跌的真凶）、以及**版本栅栏**（Go 1.24 起底层从 hmap/bmap 换成了 Swiss Table，负载因子由 6.5 变成 7/8）。能说出后两条的人很少，说出来就是加分项。

## 主问答
**Q（面试官原话）：** Go 的 map 什么时候扩容？扩容的时候数据是怎么搬的？

1. **触发条件一（翻倍扩容）**：元素数超过「负载因子 × 桶数」时触发。负载因子是**编译期常量、不随规模变化**：Go ≤1.23 为 `loadFactorNum/loadFactorDen = 13/2 = 6.5`；**Go 1.24+ 为 `maxAvgGroupLoad/MapGroupSlots = 7/8 = 0.875`** `[源码]`——超过就翻倍开新表，把元素重新分布到 2 倍空间。
2. **触发条件二（等量重建 / 同容量整理）**：桶数不变，只把散落的溢出桶/墓碑整理回收。产生原因是**大量插入 + 删除**留下空洞或被标记删除的槽位，元素数不多但空间已被占满 `[经验]`。Go 1.24+ 对应 `pruneTombstones`：墓碑数超过容量 **10%** 才值得原地清理 `[源码]`。
3. **渐进迁移（核心）**：Go **不会**一次性把全部键值搬完，而是**懒迁移**——每次写操作顺带迁移少量桶（经典实现里一次搬当前桶 + 进度桶两个），其余等用到时再搬 `[源码]`。这样把一次性的大块内存分配与拷贝摊平成 O(1) 增量，**避免扩容瞬间的耗时尖刺**。
4. **迁移期间读写**：新表写入，查找要**同时在新旧两张表**里找；搬完后旧表被丢弃、内存释放 `[经验]`。**正因为数据会在新旧表间重新分布，加上遍历起点本身随机，map 才是无序的**。
5. **删除不缩容（重要且常被说错）**：`delete` 只是把槽位标记为已删除（墓碑）、`len` 减一，**桶内存不归还** `[实测]`。本机 Go 1.26.5 实测：插入 100 万个 int→int 后 `HeapAlloc = 36.34 MB`，**逐个 delete 清空后仍是 36.34 MB**（`len=0`），再调 `clear(m)` 还是 **36.34 MB**——**map 只会变大不会变小**，想真正释放只能 `m = nil` 或重建一个新 map 让旧表被 GC。
6. **小 map 免建表优化**：Go 1.24+ 元素 ≤8 时直接装在单个 group 里，不分配完整表 `[实测]`——本机实测每 map 装 **8 个元素平均 200 字节**，装 **9 个就跳到 385 字节**（约 +93%），第 9 个元素触发 `growToTable` 分配容量为 16 的表。

## 追问链
| 层级 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | 什么时候扩容？ | 触发条件 | 元素数超过 负载因子×桶数 | 只说"满了就扩"，停在 L1 |
| L2 | 扩容有几种？ | 机制完整度 | 翻倍扩容 + 等量重建（整理碎片）两种 | 只知道翻倍，停在 L2 |
| L3 | 数据是一次搬完吗？ | 渐进迁移 | 不是，懒迁移，写时顺带搬，查找查新旧两表 | 以为一次性复制，停在 L3 |
| L4 | 删掉大量元素内存会降吗？ | 缩容认知 | 不会，delete 只留墓碑，实测 HeapAlloc 不变 | 以为会缩容，停在 L4 |
| L5 | Go 1.24 之后底层变了什么？ | 版本敏感度 | 换成 Swiss Table，负载因子 6.5 → 7/8，加小 map 优化 | 不知道版本差异，停在 L5 |

## 版本与兼容性
| 版本 | 行为 | 现在该怎么答 |
|---|---|---|
| **Go ≤ 1.23** | `hmap` + `bmap` 桶数组、桶内 8 对、溢出桶链表；`loadFactorNum=13 / loadFactorDen=2` → **6.5** | 结构细节见 914 |
| **Go 1.24+** | 底层换成 **Swiss Table**（`internal/runtime/maps`）：`Map{used, seed, dirPtr, dirLen, globalDepth…}` + 多个 `table`，`maxAvgGroupLoad=7`、`MapGroupSlots=8` → **0.875** | **按 Swiss Table 答**，并补可扩展哈希（一次只分裂一个 table，天然增量） |
| Go 1.23+ | 新增 `clear(m)` 内置 | 只清槽位，同样不释放底层内存 |
| 全版本 | 删除不缩容 | 释放内存靠重建 map |

## 关键代码
```go
// ① 预分配容量：避免反复扩容搬迁（已知规模时必写）
m := make(map[int]int, 1_000_000)

// ② 删除不缩容的实测形态：len 归零，堆内存纹丝不动
for i := 0; i < 1_000_000; i++ {
    m[i] = i
}
for i := 0; i < 1_000_000; i++ {
    delete(m, i) // len(m)==0，但桶内存不归还
}
clear(m) // Go 1.23+：清空元素，同样不释放底层内存

// 真正释放的唯一办法：让旧表整体可被 GC
m = nil
// 或 m = make(map[int]int) 重新分配
```

## 总结与追问预判
背这三句：**「两个触发条件（翻倍 / 等量）、渐进迁移而非一次性搬、只增不缩」**。面试官下一步常追问：①「为什么 map 遍历无序」——答遍历起点随机（实测同一 map 三次 range 的首个 key 分别是 **13 / 149 / 184**）+ 扩容重分布；②「slice 扩容和 map 扩容有什么不同」——slice 是整体搬一次、map 是渐进搬；③「线上 map 内存只涨不跌怎么排查」——答删除不缩容 + 重建或分片。

`[边界]` 本卡只讲**扩容触发、迁移方式与不缩容**，**不重述** hmap/bmap 的字段结构（见 914）、key 的定位算法（见 914）、map 并发写 panic 与浮点 key（见 914）、nil map 与空 map 的区别（见 918）、slice 的扩容策略（见 908）。

## ⚠️ 原文纠错
1. 纠正：原文称 map 会随删除「触发缩容、动态伸缩」——**Go map 只增不缩**，实测删除后堆内存不变 `[实测]`。
2. 纠正：原文称「扩容因子随 B 增大而变大」——负载因子是**常量**（6.5 或 0.875），变的是阈值 `[经验]`。
3. 补充：原文未提「等量重建/整理碎片」的触发比例，Go 1.24+ 为墓碑超容量 10% `[源码]`。
4. 纠正：原文把 map 无序归因于迁移——主因是**遍历起点随机**，实测三次首 key 各不相同 `[实测]`。
5. 补充：原文未提高版本差异，Go 1.24+ 底层已换成 Swiss Table `[源码]`。
6. 崩坏词归一：源码将若干术语音译为崩坏词，本卡统一为规范术语 `[经验]`。
