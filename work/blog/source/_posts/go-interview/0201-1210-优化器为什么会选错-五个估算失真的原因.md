> 分类：数据库 / MySQL 优化器 | 难度：L4 | 题型：原理题 | 频率：高 | 关键词：**统计信息、采样、成本估算、缓冲池、执行计划**

> 原文锚点：第 1~13 段「统计信息不一定准确，MySQL 依赖的是存储引擎提供的统计信息来评估成本…InnoDB 因为它有 MVCC 多版本并发控制的架构，它并不能维护一个数据表行数的精确统计信息，而且 InnoDB 采用了随机取八个数据页的样本进行计算整体的数据…最小的执行成本不代表最快的执行速度…IO 的估算成本没有考虑到缓存的情况…当可能的执行计划非常多的时候，优化器不会去估算全部可能的执行计划」

## 一句话总述
优化器会选错计划，根因是**成本估算本身不精确**：统计信息靠采样、成本模型只看 CPU 与 IO、估算不考虑缓存、计划空间被截断、存储过程与自定义函数无法估算。

## 面试官视角
P6 会说「统计信息不准」；P7 要能**列出五条并给出机制层面的解释**——尤其「InnoDB 因 MVCC 无法维护精确行数、改用随机 8 个数据页采样」这一条，能报出具体数字的答案是高分答案。

## 主问答
**Q（面试官原话）：** 优化器选的执行计划为什么有时候不是最优的？

1. **统计信息不准**：MySQL 依赖**存储引擎提供的统计信息**评估成本，但有的引擎偏差较大 `[源码]`。
2. **InnoDB 的先天限制**：因 **MVCC（多版本并发控制）架构**，InnoDB **不能维护数据表行数的精确统计信息** `[源码]`。
3. **改用采样估算**：InnoDB 采用**随机取 8 个数据页**的样本计算整体数据 `[源码]`。
4. **采样的取舍**：虽不精确，但**在很大程度上减少了计算统计信息带来的时间消耗** `[源码]`。
5. **成本不等于速度**：优化器只能通过 **CPU 成本和 IO 成本**评估执行成本；多数情况下成本越低越快，但**并非绝对** `[源码]`。
6. **IO 估算忽略缓存**：优化器按**真实物理 IO** 估算，但查询的页可能已在 **InnoDB 缓冲池（buffer pool）** 中，实际成本更低 `[源码]`。
7. **计划空间被截断**：成本估算本身耗时，当可能的执行计划非常多时，优化器**不会估算全部**，可能错过最佳计划 `[源码]`。
8. **部分成本无法估算**：如 **存储过程、用户自定义函数** 的执行成本，优化器无法估算 `[源码]`。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| MySQL 5.x / 8.0 | 采样机制一致 | 8 页采样是经典值 |
| 8.0 起 | 统计信息可持久化 | 仍为采样，非精确值 |
| 所有版本 | 直方图 | 8.0 可用直方图改善倾斜分布 |
| 所有版本 | 干预手段 | 用 FORCE INDEX 或 hint 纠正 |

## 关键代码
```sql
-- 查看表的统计信息（注意 row 数为估算值，非精确值）
SHOW TABLE STATUS LIKE 'userbig'\G

-- 查看索引的基数（Cardinality），同样是采样估算
SHOW INDEX FROM userbig;

-- 重新采样以刷新统计信息
ANALYZE TABLE userbig;

-- 确认优化器最终选择的计划（成本是估算值，非真实耗时）
EXPLAIN FORMAT=JSON SELECT * FROM userbig WHERE name > 'name10'\G
```

## 总结与追问预判
**「MVCC → 无法精确计数 → 8 页采样」是本卡最有说服力的一条**。面试官常追问「怎么纠正」——可刷新统计信息、建直方图（8.0），或在确认优化器误判时用索引提示干预。优化器自身能做哪些优化见同批 1210-optimizer-optimizations。

## ⚠️ 原文纠错
1. 事实核校：依赖引擎统计信息、InnoDB 因 MVCC 无法精确计数、随机 8 页采样、成本≠速度、IO 估算忽略缓冲池、计划空间截断、存储过程与 UDF 无法估算——均与 MySQL 优化器行为一致 `[经验]`。
2. 补充：原文「随机取八个数据页」是 MySQL 的经典采样基数；实际采样页数受 `innodb_stats_persistent_sample_pages` 等参数控制，可调大以提升准确度（代价是统计耗时增加） `[经验]`。
3. 崩坏词归一：源码将 InnoDB、MVCC、缓冲池、索引、存储过程等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
