## 一句话总述
Redis 分布式锁要保证正确，必须满足：**① 原子加锁**（`SET lock NX EX`，不存在才插入+设过期一步完成）；**② 唯一 value**（每个客户端不同，防误删别人的锁）；**③ 原子释放**（Lua 脚本判断 value 相等再删除）。两大缺陷：**超时难设**（用看门狗守护线程续约）和**主从异步复制不可靠**（用 Redlock 红锁：≥5 独立节点、过半加锁成功）。

## 面试官视角
- 意图：考察 Redis 分布式锁的**工程正确性细节**——多数人只写 `SET NX`，漏掉原子性/唯一值/Lua 释放三件套。
- P6 能说出 SET NX EX + 唯一 value + Lua 释放；P7 能讲清两个缺陷的解决方案（看门狗续约、Redlock 过半）及其代价。
- 红旗：加锁和设过期分两步（非原子，崩溃会死锁）；释放锁直接 DEL（可能删掉别人的锁）。
- 惊艳点：点出"Redlock 是 Redis 官方为集群可靠性设计的算法，但实现复杂、有争议"，显出对分布式锁陷阱的深度认知。

## 主问答
**Q（面试官原话）：** Redis 分布式锁怎么实现才安全？有什么缺陷？
**A：**
1. **结论**：安全分布式锁 = 原子加锁 + 唯一 value + 原子释放三件套；并用看门狗/Redlock 补两个固有缺陷。
2. **机制① 原子加锁**：`SET lock <uniqueValue> NX EX 10`——只有 key 不存在才设值，并一步设 10s 过期（避免"加锁后崩溃、锁永不释放"）。
3. **机制② 唯一 value**：每个客户端用唯一标识（如 UUID）作 value，释放时先比对 value 再删，防止**误删其他客户端的锁**。
4. **机制③ 原子释放**：用 **Lua 脚本**把"判断 value 相等 + 删除"合成原子操作（Redis 单线程执行 Lua 天然原子），避免"比对完锁过期、删了别人的锁"。
5. **缺陷与补法**：
   - **超时难设**：设长影响性能、设短业务没跑完锁就失效（线程 A 没跑完 B 又拿到锁）→ 用**看门狗**守护线程定时续约。
   - **主从异步**：主节点加锁后未同步就宕机，从节点升主可再被加锁 → 用 **Redlock**：≥5 个独立主节点、向多数（≥3）成功加锁才算获取，单点故障仍可锁 `[经验]`。

## 关键代码
```go
// 原子加锁：只有 key 不存在才设置，并一步设过期（Go + go-redis）
ok, err := rdb.SetNX(ctx, "lock:stock:100", uniqueValue, 10*time.Second).Result()
if err != nil || !ok {
    return errors.New("获取锁失败，稍后重试")
}
// 业务：扣减库存 ...
// 原子释放：Lua 判断 value 相等再删除，防误删他人锁
const script = `
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end`
rdb.Eval(ctx, script, []string{"lock:stock:100"}, uniqueValue)

// 看门狗：守护线程在锁到期前定时续约（EXPIRE key 10s），主线程结束销毁
```

- 三件套：SET NX EX 原子加锁 + 唯一 value 防误删 + Lua 原子释放；缺陷：超时→看门狗、主从→Redlock。
