## 思路与架构
```text
答题架构：先抛"Mutex 有两模式，本质吞吐vs公平"总纲，再分三块：
1. 正常模式行为：FIFO排队 + 唤醒者与新请求竞争(新请求占优) + 连续获取高吞吐
2. 饥饿模式行为：handoff直交队首 + 新来者入尾不抢 + 公平保先等者
3. 切换：等>1ms 或 队剩1人 → 饥饿；平衡回正常
底层实现(state位/CAS/sema)交给 925，本波只讲可观察行为
```

## 方案取舍
```text
面试取舍：被问"两种模式区别"直接上对照表(排队/竞争/吞吐/公平)，比背实现更利落。
必提两个切换触发条件(1ms/队空)——这是区分"懂行为"和"只会背实现"的分水岭。
避免：不要重写 state/sema 位布局(那是 925 的地盘)，聚焦行为对比。
```

## 答题技巧
```text
技巧1：用一句话封口——"正常求吞吐(新请求占优)、饥饿求公平(handoff队首)，按1ms/队空切换"。
技巧2：举"新请求在CPU上缓存热度高故抢赢"解释为何正常模式新请求占优，显深度。
技巧3：收尾点 go1.9 引入饥饿模式(修复写者饿死)，显版本意识(引 925)。
```

## 细节与核心 API

**模式切换由运行时自动完成**，面试只需能说清"可观察行为"，不重写 state/sema 位布局：

```go
var mu sync.Mutex
mu.Lock()
defer mu.Unlock() // 临界区

// TryLock：仅正常模式可成功；饥饿模式或被占用时直接返回 false（非阻塞快速路径）
if mu.TryLock() {
    defer mu.Unlock()
    // 抢到才进
}
```

**两种模式的可观察行为对照（答题要点）**：

```text
维度           正常模式                    饥饿模式
------------------------------------------------------------------
排队           FIFO 等待队列                FIFO，但 handoff 直交队首
竞争           唤醒者 vs 新请求（新请求占优） 新来者直接入尾，不参与竞争
吞吐           高（连续获取，缓存热）        中（保证等待者先拿）
公平           弱（可能饿死写者）            强（先等先拿）
切换触发       等待 > 1ms 或 队空剩自己 → 饥饿
回正常         饥饿者拿到锁且等待 ≤ 1ms，或队列清空
```

```go
// 关键事实：go1.9 引入饥饿模式，修复"写者饿死"
// 正常模式新请求占优的根因：新请求在 CPU 上缓存热度更高，CAS 更易成功
```

> 边界：Mutex 实现见 925；本深卡只讲"如何答好两种模式对比题"。
