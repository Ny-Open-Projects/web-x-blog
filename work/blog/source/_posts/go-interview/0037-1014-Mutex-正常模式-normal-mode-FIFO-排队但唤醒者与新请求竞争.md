> 分类：Go / 并发 / 锁 | 难度：L3 | 题型：原理题 | 频率：中高 | 关键词：**正常模式** / **FIFO** / **唤醒竞争** / **吞吐** / **饥饿**

> 原文锚点：第 28~31 段「正常模式：等待者按FIFO排队…唤醒的goroutine不直接持锁而与新请求竞争…新请求(在CPU上)更易抢到…刚唤醒的常失败加入队列前面…可连续多次获取锁(吞吐好)」

## 一句话总述
sync.Mutex **正常模式（normal mode）**下，等待者按 **FIFO** 排队，但被唤醒的等待者**不会直接拿到锁**，而是和刚到来的新请求者**竞争**；由于新请求者正跑在 CPU 上、有缓存热度，**更容易抢到锁**，导致刚唤醒者常失败并插到队列前端。这种"新来者优先"换来**更高吞吐**（同一 goroutine 可连续多次获取锁），但可能让队尾等待者饥饿。一句话背法：**「Mutex 正常模式：等待者 FIFO 排队，但唤醒者与新请求竞争、新请求(在CPU上)占优→同g可连拿高吞吐，代价队尾可能饥饿」**。

## 面试官视角
互斥锁两种模式是并发高频题。面试官想看你能否说清正常模式"为何吞吐高却可能不公平"——即唤醒者与新请求竞争、新请求占优这一反直觉点，而非只背"FIFO"。
- **P5**：知道等待者 FIFO 排队。
- **P6**：知道唤醒者不直接持锁、要和新请求竞争。
- **P7**：知道新请求占优致高吞吐、但队尾可能饥饿，并引出自饿模式（Go 1.9+）作解药。
- **红旗**：以为 FIFO 就保证先来先拿；以为唤醒者一定优先。
- **惊艳点**：点出"连续多次获取"是吞吐高的来源，也是饥饿隐患的根源。

## 主问答
**Q（面试官原话）：** Mutex 的正常模式是怎么回事？

**先铺垫（由浅入深第 1 层）**：很多人以为 Mutex 的等待队列"FIFO = 先来先拿锁"。正常模式下 FIFO 只管"排队秩序"，不管"谁先抢到"——锁一释放，队首的唤醒者和刚到的请求者要**现场抢**。

1. **FIFO 等待队列（第 2 层·机制）**：拿不到锁的 goroutine 按到达顺序排进等待队列，保证"先来先等"的秩序 `[源码]`。
2. **唤醒者与新请求竞争（第 3 层）**：锁释放时，被唤醒的等待者**不自动持锁**，要和此时新来的 `Lock()` 请求者抢；新请求者正在 CPU 上跑、局部性更好，所以**抢赢概率更高** `[源码]`。
3. **唤醒失败插队头（第 4 层）**：抢输的唤醒者退回队列**前端**（不是队尾），避免反复唤醒-失败的抖动 `[源码]`。
4. **连续多次获取 = 高吞吐（第 5 层）**：因为新请求常赢，同一个 goroutine 可连续多次拿到锁，减少上下文切换，吞吐最好——代价是队尾老等待者可能长时间拿不到（饥饿隐患）`[实测]`。
5. **解药（第 6 层）**：Go 1.9 引入饥饿模式——等待超 1ms 或队列空即切换，保证队尾最终能拿锁 `[源码]` 见 1014 饥饿模式卡。

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
)

// sync.Mutex 默认正常模式：等待者 FIFO 排队，但唤醒者需与新请求竞争
func main() {
	var mu sync.Mutex
	var order []int
	var wg sync.WaitGroup

	// 10 个 goroutine 依次抢锁，正常模式下唤醒者可能与新请求竞争，
	// 新到达且在 CPU 上的请求者常抢赢 → 同一 goroutine 可连续获取（高吞吐）
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			mu.Lock()
			order = append(order, id) // 临界区极短
			mu.Unlock()
		}(i)
	}
	wg.Wait()
	fmt.Println("acquired order (非确定，取决于调度):", order)
}
```

## 总结与追问预判
**背这三句就够**：① **正常模式：等待者 FIFO 排队**；② **唤醒者不自动持锁，与新请求竞争、新请求占优**；③ **同 g 可连续拿锁→高吞吐，但队尾可能饥饿**。
**预判追问**：
- 「怎么解决饥饿？」→ 饥饿模式（Go 1.9+），等待超 1ms 或队列空切换（见 1014 饥饿模式卡）。
- 「Mutex 底层？」→ state/CAS/sema 见 925。
- 「正常 vs 饥饿怎么切换？」→ 等待时长 + 队列是否为空触发（见 1014 mutex-mode-switch）。
