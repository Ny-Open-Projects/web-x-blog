> 分类：Go 并发缺陷 | 难度：中高 | 题型：事故题 | 频率：中 | 关键词：**端口耗尽、内存 OOM、长任务堆积、下游故障放大、资源维度**

> 原文锚点：第 4~6 段、56~63 段「协程占端口/内存；长任务无超时堆积；大文件占内存 OOM」

## 一句话总述
协程泄露不只「内存涨」一种表现，按**耗尽资源**可分三类：**端口/句柄耗尽**（协程发起网络请求占本地端口，堆积到端口用完）、**内存 OOM**（协程读大文件/处理大数据，同时运行太多把内存吃满）、**长任务堆积**（并发大 + 下游慢且无超时，协程数失控）。三者根因都是「无界创建 + 无退出」，解法见 1022 预防体系。一句话背法：**「泄露三破坏面：占端口、吃内存、堆长任务；根因都是无界创建无退出」**。

## 面试官视角
考官看你能不能从「资源视角」理解泄露的破坏面，而非只盯着内存。能从端口/内存/长任务三个维度展开，并点出「下游故障 + 无超时 = 雪崩式堆积」的放大效应，说明你见过生产事故；以为泄露只表现为 OOM、没意识到网络协程会耗尽本地端口，是红旗。
- **P5**：知道泄露会涨内存。
- **P6**：知道端口/句柄、内存 OOM、长任务三类资源维度。
- **P7**：能点出「下游故障 + 无超时 = 雪崩式堆积」的放大效应，并给出超时+池化+分治的化解。

## 主问答
**Q（面试官原话）：** 协程泄露除了 OOM 还会怎样？破坏面有多大？

**先铺垫（由浅入深第 1 层）**：很多人以为协程泄露就是「内存慢慢涨直到 OOM」。其实协程不只是一个 goroutine 结构体，它往往**持有端口、句柄、正在处理的大块数据**。协程堆积，它持有的资源也跟着堆积，破坏面是多维的。

1. **端口/句柄耗尽（第 2 层）**：协程常用来发网络请求，每个占用一个本地端口/文件句柄；无界创建 → 端口或句柄耗尽，新连接全失败。
2. **内存 OOM（第 3 层）**：协程读大文件/处理海量数据，同时跑太多 → 内存被吃满 → OOM 被 kill。
3. **长任务堆积（第 4 层·最隐蔽）**：高并发服务访问慢下游，又**没设超时** → 请求协程越积越多，最终服务崩溃。
4. **放大效应（第 5 层·深度）**：一个无限创建协程去调下游的服务，下游一抖 → 端口/协程双耗尽，下游故障被无超时放大成雪崩。这是生产最常见、最隐蔽的泄露放大链。
5. **治理指向（第 6 层）**：三类都靠「超时 + 协程池/信号量限并发 + 大文件分而治之」化解（详见 1022 预防体系）。

## 版本与兼容性
| 维度 | 说明 |
|------|------|
| 端口耗尽 | 每个 outbound TCP 连接占一个本地 ephemeral 端口；协程无界发请求 → 端口用尽（典型 `address already in use` / 连接失败） |
| 内存 OOM | 协程持有大块数据且同时运行过多 → RSS 涨满被 OOM-killer 杀 |
| 长任务堆积 | 无 `context` 超时 + 下游 P99 抖动 → 在途请求协程数失控 |
| 化解手段 | `context.WithTimeout` + channel 信号量/协程池限并发 + 大文件分治流式（见 1022） |
| Go 版本 | 与 Go 版本无关，本项目实测 Go 1.26.5 |

## 关键代码
```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// 模拟一个慢下游：耗时 500ms，可能抖动
func callSlowDownstream(r int) {
	time.Sleep(500 * time.Millisecond)
	_ = r
}

func main() {
	// ❌ 坏例子：无超时 + 无并发上限，下游一慢协程就堆积（端口/协程双耗尽）
	hugeBatch := make([]int, 1000)
	var wgBad sync.WaitGroup
	for _, req := range hugeBatch {
		wgBad.Add(1)
		go func(r int) { // 无限创建，下游抖一次全卡在这
			defer wgBad.Done()
			callSlowDownstream(r)
		}(req)
	}

	// ✅ 修法：带超时 + 信号量限并发，下游抖动也不雪崩
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	sem := make(chan struct{}, 20) // 同时最多 20 个
	var wg sync.WaitGroup
	for _, req := range hugeBatch {
		sem <- struct{}{}
		wg.Add(1)
		go func(r int) {
			defer wg.Done()
			defer func() { <-sem }()
			done := make(chan struct{})
			go func() { callSlowDownstream(r); close(done) }()
			select {
			case <-done:
			case <-ctx.Done():
				fmt.Println("超时退出，避免堆积:", ctx.Err())
			}
		}(req)
	}
	wg.Wait()
}
```

## 总结与追问预判
**背这三句就够**：① **泄露按资源分三类：端口/句柄耗尽、内存 OOM、长任务堆积**；② **根因都是无界创建 + 无退出**；③ **化解靠超时 + 协程池/信号量限并发 + 大文件分治**。
**预判追问**：
- 「网络协程怎么会耗尽端口？」→ 每个 outbound 连接占一个本地 ephemeral 端口，无界创建就耗尽（见本卡第 2 层）。
- 「下游故障怎么放大？」→ 无超时 + 下游慢 → 在途协程越积越多 → 端口/协程双耗尽雪崩（见本卡第 4/5 层）。
- 「怎么从源头防？」→ 见 1022 预防体系（ctx 取消 + 超时 + 池化 + 分治 + 监控）。
