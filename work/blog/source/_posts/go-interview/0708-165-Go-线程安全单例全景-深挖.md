## 一句话总述
本源把 Go 线程安全单例串成**四方案**：裸懒汉(竞态)/加锁(正确但每次锁)/DCL(缩锁范围但有可见性 race)/sync.Once(官方推荐)/原子+Mutex(=Once 源码)。面试按"问题→四方案→内存模型陷阱→Once 本质"四步走，并明确与既有卡边界：单例概念 162、Once 关闭 1021、Mutex 925、atomic 105。

## 思路与架构
- **问题层**：懒汉式 check-then-act 竞态，多 goroutine 多次建实例。
- **方案层**：加锁(全量互斥)→DCL(无锁快路径+持锁双检)→Once(封装双检)→原子(手写 Once)。
- **陷阱层**：Go 内存模型下，裸 DCL 的外层无锁读与持锁写存在数据竞争，必须 atomic 或 Once 保护。
- **本质层**：Once.doSlow = atomic 标志 + Mutex 双检，原子方案即其展开。
- **边界**：与 162(单例概念)/1021(Once 关闭)/925(Mutex)/105(atomic) 互补，本卡只讲线程安全实现。

## 方案取舍
- **裸懒汉**：不可用（竞态）。
- **加锁**：正确但每次访问加锁，实例已建仍付锁开销——简单场景可接受。
- **DCL**：省已建后锁开销，但裸写有可见性 race；要安全须配 atomic 标志，等于退化成原子方案。
- **Once**：语义最直白、无 race、零手写锁——Go 单例首选。
- **原子+Mutex**：理解 Once 底层用；实战不如直接 Once（重复造轮子）。

## 答题技巧
1. **开口定调**："懒汉式有竞态，Go 单例用 sync.Once 最稳"。
2. **展方案**：加锁正确但贵 → DCL 省锁但有 race → Once 封装修正。
3. **挖本质**：Once 内部 = atomic + Mutex 双检，原子方案即其展开。
4. **补陷阱**：裸 DCL 外层读是 race，内存模型要求同步。
5. **关联延展**：提 162/1021/925/105，显示体系化与边界意识。

## 细节与核心 API

```go
// 推荐：sync.Once（最简洁、无锁竞争、Go 官方保证只执行一次）
type Singleton struct{ cfg string }
var (
    inst *Singleton
    once sync.Once
)
func Get() *Singleton {
    once.Do(func() { inst = &Singleton{cfg: loadCfg()} })
    return inst
}
// 双重检查（无需 Once，但要 atomic + 内存屏障，易写错，不推荐）
// 错误示范：if inst == nil { inst = &Singleton{} } // 非原子，可能建多次
// 注意：单例若持可变状态要自身加锁；单例构造函数 panic 会导致 once 已标记为“完成”而无法重试
// 选型：单例只读配置/连接池用 sync.Once；需多实例用工厂；测试要可替换用依赖注入而非全局单例
```
