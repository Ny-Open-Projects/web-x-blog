> 原文锚点：第 32~35 段「饥饿模式解决等待队列长尾…解锁直接把锁交队头…新来者不竞争不自旋直接入队尾…解决旧goroutine一直拿不到锁」

## 一句话总述
sync.Mutex **饥饿模式（starvation mode）**为消除"队尾老等待者拿不到锁"的长尾问题：锁释放时**直接把锁交给等待队列队首**，且新来的 goroutine **不参与竞争、不自旋**，直接排到队尾。这样保证先等者先得，牺牲吞吐换**公平**。一句话背法：**「Mutex 饥饿模式：解锁 handoff 直交队首、新来者不自旋排尾，先等先得保公平，代价吞吐降；Go 1.9 引入」**。

## 面试官视角
与正常模式对照。面试官想看你是否懂饥饿模式"如何保证公平"——handoff 直交队首 + 新来者入尾不抢，以及它和正常模式的吞吐/公平取舍。
- **P5**：知道饥饿模式保证先等先得。
- **P6**：知道解锁 handoff 直交队首、新来者排尾不抢。
- **P7**：知道代价是吞吐下降，且 Go 1.9 引入作公平性修复。
- **红旗**：以为饥饿模式吞吐更高；以为新请求在饥饿模式还能抢锁。
- **惊艳点**：点出 handoff 经 `runtime_Semrelease(handoff=true)` 实现，饥饿位 `mutexStarving` 标记当前模式。

## 主问答
**Q（面试官原话）：** 饥饿模式又是什么？怎么保证公平？

**先铺垫（由浅入深第 1 层）**：正常模式为了吞吐让"新请求占优"，代价是队尾老等待者可能一直拿不到锁。饥饿模式就是针对这个长尾问题的补丁——把"谁先等"变成硬规则。

1. **解锁 handoff 直交队首（第 2 层·机制）**：进入饥饿模式后，释放锁不再"唤醒一个去竞争"，而是把锁**直接交给**等待队列最前面的 goroutine（handoff），队首立即持锁 `[源码]`。
2. **新来者不抢、排队尾（第 3 层）**：饥饿模式下新 `Lock()` 请求者**不自旋、不参与竞争**，直接挂到等待队列尾部——避免出现"刚释放又被新请求抢走"导致老等待者永远拿不到 `[源码]`。
3. **解决长尾饥饿（第 4 层）**：先到先得，最长的等待者必然在队首被优先满足，彻底消除正常模式下"新请求占优"带来的饥饿隐患；代价是吞吐下降（少了连续获取、多了排队切换）`[实测]`。
4. **实现（第 5 层）**：handoff 经 `runtime_Semrelease(handoff=true)` 实现，state 第 3 位 `mutexStarving` 标记当前是否饥饿模式 `[源码]`。
5. **版本（第 6 层）**：饥饿模式 Go 1.9 引入，修复此前写者可能饿死的缺陷 `[源码]`。

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// 饥饿模式示意：高竞争下，runtime 自动切换饥饿模式，
// 让长时间等待的 goroutine 通过 handoff 优先拿到锁（公平），而非永远被新请求抢占
func main() {
	var mu sync.Mutex
	done := make(chan int, 2)

	for id := 0; id < 2; id++ {
		go func(id int) {
			mu.Lock()
			time.Sleep(2 * time.Millisecond) // 持有较久，制造竞争窗口
			mu.Unlock()
			done <- id
		}(id)
	}
	for i := 0; i < 2; i++ {
		fmt.Println("released to goroutine", <-done)
	}
}
```
