> 深挖卡：把「表单防重」抽象成「任意写接口的幂等性」，覆盖幂等键、状态机、乐观锁、唯一索引四条落地路径。

## 思路与架构

表单防重只是幂等的一个特例。通用模型是：**客户端为一次业务意图生成唯一幂等键（Idempotency-Key），服务端以该键为唯一约束做「首次执行、重放返回」**。

```text
请求 → ① 取幂等键 K（客户端 Idempotency-Key 头 / 服务端下发 token / 业务天然键）
     → ② 原子占位：INSERT INTO idempotent(K, state) VALUES(?, 'RUNNING')
          命中唯一约束 → 说明有请求在处理或已完成
     → ③ 分支：
          占位成功        → 执行业务 → 更新为 SUCCESS 并缓存响应
          已有 SUCCESS    → 直接回放上次的响应（不重复执行）
          已有 RUNNING    → 返回 409 冲突 / 让客户端稍后重试
     → ④ 兜底：业务表自身的唯一索引（订单号、流水号）防住幂等键失效的场景
```

三条架构铁律：

1. **幂等键的作用域要带业务身份**：只用一个 UUID 做键，攻击者可以用别人的 key；正确做法是 `(user_id, key)` 联合唯一，或干脆用业务天然键（订单号、转账流水号）。
2. **必须记录「执行结果」而不只是「执行过」**：只记 `done=1` 的话，重放请求无法返回与首次一致的响应体；应缓存首次的响应（或至少状态码 + 资源 ID），保证**重放语义一致**。
3. **并发态要显式区分**：`RUNNING` 与 `SUCCESS` 是两种状态，不能合并。并发的第 2 个请求撞上 `RUNNING` 时要返回 409 让客户端重试，而不是返回"成功"（业务还没落库）。

## 方案取舍

| 方案 | 幂等粒度 | 代价 | 适用 |
|---|---|---|---|
| 前端禁用按钮 | 单次点击 | 零 | **不能单独用**，纯体验优化 |
| PRG 重定向 | 刷新重放 | 零，多一次 303 | 所有 POST→页面场景，**必配** |
| 服务端一次性 token | 单次表单 | 一次 Redis 往返 + TTL 管理 | 表单、支付页 |
| **幂等键 + 去重表** | 任意接口 | 一张表 + 唯一索引 | **通用写接口首选** |
| 业务唯一索引 | 天然业务键 | 无额外表，需业务有天然键 | 订单/流水/评论去重，**最强兜底** |
| 乐观锁（version） | 更新操作 | 表加 version 字段 | 余额扣减、状态流转 |
| 状态机校验 | 流转操作 | 状态字段 + 前置校验 | 订单 待支付→已支付 只能转一次 |
| 分布式锁 | 临界区 | 锁服务可靠性、超时难定 | 不推荐单独做幂等，只做并发互斥 |

取舍原则：**能用业务唯一索引就用（成本最低且最硬），没有天然键再上幂等键表，PRG 与 token 解决的是「用户行为层」，不能替代存储层约束。** 另外注意：分布式锁**不是**幂等方案——它只保证互斥，锁释放后重复请求照样能进来。

## 答题技巧

1. **开口先分类，别直接给方案**：先说「重复提交有三类来源（刷新重放、双击、脚本重放），对应三层防御（PRG、token、幂等键/唯一索引）」——结构感立刻拉满，面试官会顺着你的分类追问而不是乱枪打鸟。
2. **把"原子性"当成加分点主动抛**：说完 token 立刻补一句「校验和消费必须是一个原子操作，生产用 Redis `GETDEL`，先 GET 再 DEL 有并发窗口」——这句话是 P6 与 P7 的分水岭。
3. **主动交代失败分支**：不要只讲成功路径。要说明「幂等键撞上 RUNNING 时返回 409 让客户端重试，撞上 SUCCESS 时回放首次响应」，并补「响应要缓存多久」——这是面试官最爱挖的坑。
4. **带上可观测与清理**：幂等表会无限膨胀，答出「按 TTL 归档 / 只保留 24~72 小时 + 超过业务最长重试窗口即可删除」，再补「幂等命中率要打点，命中率突增通常意味着客户端在疯狂重试」。
5. **版本与组件栅栏要说清**：Redis `GETDEL` 是 6.2+ 才有的原子命令，低版本要用 `SETNX` + TTL 或 Lua 脚本；Go 侧 1.22+ 的 `ServeMux` 支持 `POST /path` 方法路由，把提交与结果页拆成两条路由比在 Handler 里 `if r.Method` 分支更干净。

## 细节与核心 API

```go
// 幂等键 + Redis：同一请求号只落地一次
func handle(w http.ResponseWriter, r *http.Request) {
    idem := r.Header.Get("Idempotency-Key")
    if idem == "" { http.Error(w, "missing key", 400); return }
    // SET NX：首次写入成功，重复请求返回已存在
    ok, _ := rdb.SetNX(ctx, "idem:"+idem, "processing", 30*time.Minute).Result()
    if !ok { http.Error(w, "duplicate", 409); return }
    result := doBusiness(r)
    rdb.Set(ctx, "idem:"+idem, result, 30*time.Minute)
    json.NewEncoder(w).Encode(result)
}
// 其他手段：DB 唯一索引/去重表、乐观锁 version、状态机（已处理则直接返回）
// 选型：客户端重试 + 服务端幂等键最常用；DB 唯一约束作最终兜底
```
