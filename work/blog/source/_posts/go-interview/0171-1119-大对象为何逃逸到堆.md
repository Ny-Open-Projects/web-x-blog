> 分类：Go 编译器 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**逃逸分析**/**64KB 阈值**/**堆分配**
> 原文锚点：第 1~29 段「对象超过六十四 KB 直接分配到堆栈…大于六十四 KB 通常发生逃逸」

## 一句话总述
超过约 **64 KB** 的局部对象通常会被编译器判定逃逸到堆；但 64KB 是**按类型的经验阈值**而非铁律，且逃逸分析只判断**初始化时**的分配，运行期 `append` 撑大切片编译器无法预知。

## 面试官视角
- 考察意图：是否真懂逃逸分析的判定边界，还是背了"64KB 必逃逸"的口诀。
- 分档：P5 知道"大对象上堆"；P6 知 64KB 是启发式、按类型不同；P7 能说明"运行期扩容不进静态分析"。
- 红旗答案："超过 64KB 一定逃逸"；把"堆"和"栈"混称为"堆栈"。
- 惊艳点：**64KB 阈值因类型而异**（数组/切片/string 上限不同），且 `make([]T, n)` 长度来自变量也必逃逸 `[源码]`。

## 主问答
**Q（面试官原话）：** 多大会导致 Go 对象逃逸到堆上？
**A：**
1. **结论**：经验上局部对象超过约 64KB 大多逃逸，但是**类型相关**的启发式，不是硬限。
2. **机制**：编译器在 SSA 阶段做逃逸分析，对象若"栈帧放不下或生命周期超出函数"就移到堆；64KB 是触发该启发式的常见体量边界 `[源码]`。
3. **边界**：逃逸分析是**编译期静态**的，只能看初始化形状——`make([]int, 1024*65)` 静态可见会逃逸，但先小后 `append` 撑过 64KB 的过程编译器看不出来，那时是否上堆由运行期分配器决定。

**加分层：** 长度来自变量的切片 `make([]T, n)`（n 是变量）必然逃逸，因为编译器无法确定其大小。

## 关键代码
```go
func f() {
    s64 := make([]byte, 64*1024) // 64KB：通常不逃逸
    s65 := make([]byte, 65*1024) // 65KB：通常 moved to heap
    n := 65 * 1024
    sv := make([]byte, n) // 长度来自变量：必逃逸
    _ = s64
    _ = s65
    _ = sv
}
// go build -gcflags='-m' 可见 s65/sv "escapes to heap"
```

## 总结与追问预判
64KB 是经验阈值不是铁律；逃逸分析只管"出生"，不管"成长"。追问常接"接口类型怎么导致逃逸"，是下一张卡。

## ⚠️ 原文纠错
1. 原文"对象超过 64KB **直接分配到堆栈**"术语混用——应明确是"逃逸到**堆**（heap）"，栈（stack）与堆是不同区域，无"堆栈"这一统一分配去向 `[经验]`。
2. 原文"大于 64KB 之后**通常**发生逃逸"表述偏绝对：64KB 是按**类型**不同的启发式，且原文后文自己举例"1024×65 的数组未逃逸"已自相矛盾；应表述为"经验阈值、因类型而异" `[源码]`。
