## 思路与架构

```mermaid
graph TD
A[struct 内存对齐] --> B[动机:CPU 按字长读/减字数]
A --> C[规则:字段对齐=min类型,机器字节]
C --> C1[结构体对齐=字段最大对齐]
C --> C2[size=累加+填充]
C --> C3[对齐值=1 无填充]
A --> D[平台:32位4B/64位8B]
A --> E[特例:空结构体末位需对齐]
E --> E1[动机:防取地址越界/泄露]
```

## 方案取舍
- **空间 vs 访问效率**：对齐用 padding 换「CPU 少读几次」，通常值得；极密内存场景才手动重排字段压 padding。
- **排字段口诀**：同对齐值字段聚一起、大字段靠后，减少跨对齐边界的 padding。
- **末位空字段**：宁可多几个字节也要对齐，安全优先于省空间。

## 答题技巧
- 被问 size 时，先算各字段对齐值 → 结构体最大对齐 → 累加+填充，当场推出数字显专业 [经验]。
- 主动补「末位空结构体对齐」特例，区分于普通零尺寸值，是 P7 加分项 [经验]。
- 与 1112（struct 含 padding/零尺寸值用途）互为引用不重述 [边界]。

## 细节与核心 API

```go
type S struct {
    a bool  // 1B，对齐到 1
    _ [7]byte // 填充到 8，使 b 对齐 8
    b int64 // 8B
    c bool  // 1B
    // 尾部补 7B 使整体是 8 的倍数 -> 24B
}
fmt.Println(unsafe.Sizeof(S{})) // 24
// 优化：按字段大小降序排列消除填充
type Opt struct { b int64; a bool; c bool } // 16B
// 工具：fieldalignment（govet 子集）可自动发现可压缩的结构体
// 对齐受目标架构影响（64 位 8 字节，32 位 4 字节）；Wire/DB 布局需手动序列化避免依赖
```
