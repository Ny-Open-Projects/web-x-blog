> 分类：网络协议 / TCP | 难度：L2 | 题型：场景枚举题 | 频率：中 | 关键词：**错误 ACK、SYN 重传换序、中间人攻击、实现 bug、RST 自我保护**

> 原文锚点：第 1~11 段「什么情况下三次握手客户端会收到不正确的 ACK：网络延迟或数据包重复、中间人攻击伪造、客户端或服务端程序实现错误三类」

## 一句话总述
三次握手中客户端收到「不正确 ACK」——即**服务端回的 SYN+ACK 确认号与自己期望的不符**——根因有三类：**① 网络延迟/丢包导致旧 SYN 重传换序、旧包先到**；**② 中间人攻击拦截伪造 ACK**；**③ 通信双方程序实现 bug 算错序列号**。无论哪种，后果都一致（见 1844）：客户端按非法报文处理、回 **RST** 终止这次握手——这是 TCP 有状态校验的自我保护，不是连接被拉黑。

## 面试官视角
P5 能答「收到错的 ACK 会 RST」；P6 要**枚举出三类成因**并说清第 ① 类的时序（SYN 重传换了新序列号、旧 SYN 先到使确认号错位）；P7 会补「程序 bug 类虽然少见但真实存在」，并点出**内核代答 RST 是协议通用自我保护机制**（连未监听端口也是 RST，见 `1844`）。

## 主问答
**Q（面试官原话）：** 什么情况下三次握手过程中，客户端会收到不正确的 ACK？

1. **成因①：网络延迟 / 丢包重传换序** `[经验]`：客户端先发 `SYN(seq=1)` 在网中阻塞，超时**重发时换了新序列号 `seq=5`**；旧包恢复后**先到**服务端，服务端按旧 seq 回 `SYN+ACK，ack=2`；客户端期望的是 `5+1=6`，收到 `2` → **确认号不符 → 判定为不正确 ACK**。（后果与时序推演详见 1844 第 2 条。）
2. **成因②：中间人攻击（MITM）伪造** `[经验]`：攻击者拦截并篡改/伪造数据包，主动向客户端发送一个**伪造的 ACK**，其确认号与客户端当前状态不匹配，客户端据此判定为不正确 ACK。这类属于**恶意注入**，正常网络不会出现。
3. **成因③：通信双方程序实现 bug** `[经验]`：客户端或服务端在**计算/校验序列号**时出现实现错误，导致一方发出的确认号对不上另一方的状态。原文也承认「比较少见，但可能发生」——多见于自定义协议栈、老旧的嵌入式 TCP 实现、或 NAT/中间件改写序列号出错。
4. **共同后果：RST 自我保护** `[源码]`：TCP 是**有状态协议**，端点逐包校验确认号是否匹配自身状态；一旦不匹配即按非法报文处理，**回 RST 立即终止当前这次握手**。内核的「连接被拒（connection refused）」本质也是它**代答的 RST**——这证明「校验失败即 RST」是 TCP 的通用机制，不只是握手场景（实测见 `1844`，连未监听端口 448µs 内收到内核 RST）。
5. **边界（避免夸张）** `[源码]`：RST **只终止当前这一次握手/半开连接**，不影响后续携带正确序列号的新 SYN；更不是「服务端挂了」。收到 RST 方校验通过即直接关闭，**RST 本身从不被 ACK**。

## 追问链
| 层级 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | 收到错误 ACK 会怎样？ | 后果 | 客户端回 RST 终止握手 | 答不出 RST，停在 L1 |
| L2 | 错误 ACK 哪来的？ | 成因枚举 | 网络延迟重传 / MITM 伪造 / 程序 bug 三类 | 只答网络，停在 L2 |
| L3 | 重传换序怎么错位？ | 时序 | 旧 SYN 先到→ack 用旧 seq→与期望不符 | 推不出时序，停在 L3 |
| L4 | 程序 bug 现实吗？ | 严谨 | 少见但真实，多见于自定义栈/NAT 改写 | 说"不可能"，停在 L4 |
| L5 | RST 会影响后续握手吗？ | 边界 | 只杀当前，新 SYN 照常 | 以为对端被拉黑，停在 L5 |

## 版本与兼容性
| 版本 / 规范 | 行为 | 现在该怎么答 |
|---|---|---|
| RFC 793 | 确认号校验失败 → RST，恒定 | 基础语义 |
| RFC 5961 | 盲 RST 防护：challenge-ACK，非法 RST 不直接生效 | 被问「伪造 RST」时提 |
| NAT / 中间件 | 改写序列号可能导致一端确认号错位 | 成因③的现实变体 |
| 应用层 | `SO_LINGER(0)` 可主动发 RST 放弃数据 | 程序可控触发 RST |

## 总结与追问预判
答题骨架：**「三类成因（网络重传换序 / MITM 伪造 / 程序 bug）→ 后果都是客户端回 RST 终止当前握手 → 只杀当前不影响后续」**。这是 `1844-rst-incorrect-ack`（**后果与机制**）的**前因篇**——两卡配套看才完整：本题讲"**为什么会收到错误 ACK**"，1844 讲"**收到后发生什么**"。
