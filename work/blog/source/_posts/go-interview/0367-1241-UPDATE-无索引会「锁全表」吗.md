# 1241 UPDATE 无索引会"锁全表"吗

> 分类：MySQL 锁 | 难度：L3 | 题型：FAQ 题 | 频率：高 | 关键词：**UPDATE 全表扫描** / **next-key X 锁** / **全表行锁≠表锁** / **阻塞增删改** / **RR**
> 原文锚点：第 1~8 段「更新无索引…全表扫描…表中全部记录被零件锁(临键锁)覆盖…不是表锁…全表扫描期间其他事务增删被阻塞」

## 一句话总述
`UPDATE` 的 `WHERE` 没有可用索引时，InnoDB 只能全表扫描，于是**每一行都被加上 next-key 排他锁（X）**，锁的范围扩大到整张表——但这叫"全表行锁"而非"表锁"：它阻塞其他事务的增删改，是线上灾难，却与 `LOCK TABLES` 的表锁在锁视图上完全不同。

## 面试官视角
- 意图：是否分得清"全表行锁"与"表锁"，以及 UPDATE 无索引为何会放大到锁全行。
- P5 知无索引→全表扫→锁多行；P6 说清是 next-key X 锁、非表锁、事务提交才释放；P7 知 Supremum 伪记录也被锁、RR 下才显著。
- 红旗：直接答"会锁表"；混淆全表行锁与表锁。
- 惊艳点：UPDATE 加的是 **X 锁**（排他），而 `SELECT ... LOCK IN SHARE MODE` 加的是 S 锁——同是全表扫描，锁模式不同 `[经验]`。

## 主问答
**Q（面试官原话）：** 更新数据的时候没加索引，会不会锁全表？
**A：**
1. **锁的是行不是表**：InnoDB 以 next-key 锁为基本加锁单位，无索引→全表扫描→所有记录加 X 锁（含 Supremum 伪记录），是"全表行锁"而非"表锁" `[源码]`。
2. **释放时机**：写锁在事务提交/回滚后才释放；全表扫描耗时长，锁持有时间也长。
3. **阻塞范围**：扫描期间其他事务对该表的插入、删除、修改都会被阻塞，线上影响面极大。
4. **与表锁区别**：表锁是单表级锁（开销小、并发低），全表行锁是逐行加锁——二者锁视图表现不同，根因是"全表扫描"而非"显式锁表" `[边界]` 见 1233。

| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| InnoDB RR（默认） | 行级默认 next-key 锁 | 全表行锁在此级别显著；RC 下退化为记录锁，不锁间隙 |
| 所有版本 | 意向锁不阻塞行 | 全表行锁靠 next-key 实现，非表级锁 |

## 关键代码
```sql
-- 表 t：id 主键自增，age 字段无索引
BEGIN;
UPDATE t SET name='x' WHERE age = 2;   -- age 无索引 → 全表扫描
-- 观察：所有记录（含 Supremum）被加 X, next-key 锁
SELECT INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks WHERE OBJECT_NAME='t'\G
-- 另一事务对任一行 INSERT/DELETE/UPDATE 均被阻塞，直到本事务提交
COMMIT;
```

## 总结与追问预判
- 无索引 UPDATE = 全表扫描 = 全表行锁（X），非表锁；事务提交才放。
- 预判：SELECT 侧同类事故 → 见 1238；UPDATE 底层加锁 → 见 1236；表锁本身 → 见 1233。
