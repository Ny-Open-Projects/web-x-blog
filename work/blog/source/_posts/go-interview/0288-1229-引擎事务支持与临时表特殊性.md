> 分类：MySQL 事务 | 难度：L3 | 题型：八股题 | 频率：中 | 关键词：**InnoDB** / **NDB** / **临时表** / **Using temporary** / **EXPLAIN**
> 原文锚点：第 1~13 段「仅 InnoDB/NDB 支持事务；非事务引擎改动无法回滚；内部临时表不分配事务 ID；EXPLAIN Extra 判断」

## 一句话总述
MySQL 只有 InnoDB（主力）和 NDB 支持事务，非事务引擎（如 MyISAM）的修改无法回滚；临时表分"用户临时表"和"内部临时表"两种，内部临时表（`EXPLAIN Extra: Using temporary`）不参与事务、不分配事务 ID。

## 面试官视角
- 意图：考察候选人对"事务到底挂在哪个对象上"的理解，而非只会背 ACID。
- P5 知道 InnoDB 才支持事务；P6 能区分用户临时表与内部临时表；P7 能说出 EXPLAIN 怎么判断一条查询是否用到内部临时表。
- 红旗：以为所有表都支持事务；以为临时表也走完整事务。
- 惊艳点：指出内部临时表（排序/分组中间结果）是会话级、不分配 trx_id，所以查询操作永不产生事务 ID。

## 主问答
**Q（面试官原话）：** 怎么判断一条 SQL 用到的表是不是事务表？临时表算事务吗？
**A：**
1. **结论**：只有 InnoDB/NDB 表是事务表，非事务引擎（MyISAM 等）的写无法回滚；用户临时表（`CREATE TEMPORARY TABLE`）可参与事务，内部临时表（优化器生成的 `Using temporary`）不参与、不分配事务 ID。
2. **机制**：`EXPLAIN` 的 `Extra` 列出现 `Using temporary` 表示优化器用了内部临时表，它不属于事务表、无 trx_id；用户临时表在只读事务里也能增删改，但只有首次改它才分配事务 ID `[源码]`。
3. **边界**：非事务引擎的表即使执行了 UPDATE，出错也无法回滚——因为根本没产生 undo/事务上下文，落库即永久 `[经验]`。

## 关键代码
```sql
-- 用 EXPLAIN 看是否触发内部临时表（不参与事务、不分配 trx_id）
EXPLAIN SELECT department, COUNT(*) FROM emp GROUP BY department;
-- 若 Extra 出现 Using temporary，说明优化器建了内部临时表，该表不分配事务 ID
```
