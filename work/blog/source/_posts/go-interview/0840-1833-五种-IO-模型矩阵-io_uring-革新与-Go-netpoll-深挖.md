> 覆盖源 18-33 全文：阻塞/非阻塞/多路复用/信号驱动/异步五模型的全维度矩阵、「两次操作」缺陷的精确定位、AIO 的内核-应用契约、Linux AIO 之败与 io_uring 之成、Go「同步风格 API + 异步运行时」的架构本质。主卡已给同步异步判据与演进主线，本附录做模型矩阵与落地四层深挖。

## 思路与架构

```text
五种 IO 模型 × 两个阶段 (阶段1: 等数据就绪; 阶段2: 拷贝到用户态)
├─ 阻塞 IO     : 阶段1阻塞等待    | 阶段2自己拷 (同步)
├─ 非阻塞 IO   : 阶段1轮询        | 阶段2自己拷 (同步)
├─ IO 多路复用 : 阶段1 select/epoll 统一等 | 阶段2自己拷 (同步)
├─ 信号驱动    : 阶段1 SIGIO 通知就绪 | 阶段2自己拷 (同步)
└─ 异步 IO     : 阶段1+2 全由内核完成, 完成后通知 (异步)
判据: 只要阶段2 (拷贝) 由调用线程参与 -> 同步 IO
└─ Linux AIO(libaio): 仅 O_DIRECT 好 -> io_uring: 提交/完成双队列重构
```

## 方案取舍
- **五模型矩阵是记忆骨架**：把「等就绪」与「拷贝」拆成两个阶段填表，同步/异步的判据立刻清晰——**前四个模型的阶段 2 都是应用自己做**（recvfrom 阻塞拷贝），所以全部是同步 IO；只有 AIO 两个阶段都由内核承包。多路复用的价值不在「异步化」而在**把阶段 1 从「每连接一次等待」合并为「一次等待看全部 fd」**——省的是线程/进程数量，不是拷贝阶段。信号驱动（SIGIO）在 TCP 上语义含糊（信号不带 fd 信息、可能风暴）几乎没人用，知道存在即可 [经验]。
- **Linux AIO 为什么失败**：设计缺陷三连——仅对 **O_DIRECT** 打开的文件表现正常（绕过页缓存，与常规读路径互斥）；很多场景内核**偷偷退化为同步**；接口与 fd 集成差（网络 socket 支持残缺）。结果是十几年来 Linux 高性能 IO 都在「同步非阻塞 + epoll」这条路内卷。**io_uring 重做的核心**：用户态与内核共享两个环形队列（提交 SQ / 完成 CQ），**一次系统调用可批量提交多个 IO**，且覆盖文件与网络、支持注册缓冲与注册 fd——系统调用次数从「每 IO 一次」降到「每批一次」，这才是把「减少上下文切换」做进协议层 [经验]。
- **Go 的架构本质是「把异步藏起来」**：用户写 `conn.Read()` 这种同步阻塞代码；runtime 把 fd 全部设为非阻塞并注册进 netpoll（Linux 上是 epoll），Read 无数据时 `gopark` 挂起 goroutine、M 线程去跑别的任务，事件到达后 `goready` 唤醒。**效果**：以「单进程 + 万级 goroutine」实现了 AIO 级的并发能力，且免掉回调地狱——代价是 runtime 复杂度与少量调度开销。对比 C++/Java NIO 的显式回调/Selector 编程，Go 的选型是**用运行时复杂度换应用简洁性**。io_uring 对 Go 的潜在增益（减少系统调用）目前收益有限：netpoll 已把等待阶段批量化，剩余的拷贝阶段本来就不在用户态路径上 [源码]。
- **「异步常与非阻塞结合」的工程含义**：源文这句落地就是——非阻塞保证「发起 IO 的瞬间不会卡死」，异步/多路复用保证「等待期间能干别的」；两者组合后单线程也能管理海量连接（nginx/redis 的模型）。反例是「阻塞 IO + 多线程」：每连接一线程，万级连接就是万级线程——栈内存（每线程兆级）与调度开销都不可接受，这就是 C10K 问题催生非阻塞+多路复用生态的历史动因 [经验]。
- **选型收束**：单机小服务、连接少 → 阻塞 IO + 线程池最简单；海量连接 → 非阻塞 + 多路复用（或 Go/erlang 这类自带 netpoll 的语言）；极端吞吐 → io_uring。**同步异步不是好与坏，是「控制流复杂度」与「并发能力」的交易** [经验]。

## 答题技巧
- 先给判据（拷贝阶段谁做），再填五模型矩阵表格，最后落「多路复用仍是同步」——层次比名词重要 [经验]。
- 主动纠偏「线程同步 ≠ IO 同步」，这是题目埋的显式陷阱，当场点破即加分 [源码]。
- 被问「io_uring 好在哪」→ 双队列共享内存 + 批量提交 + 全域覆盖（文件/网络），对比 AIO 的三宗罪 [经验]。
- 被问「Go 为什么不用回调」→ netpoll + gopark/goready 把异步封装进调度器，同步 API + 异步运行时 [源码]。
- 主动边界到 `1834-io-multiplexing-select-poll-epoll`（select/poll/epoll 机制）、`1834-epoll-level-edge`（触发模式）、`1836-zero-copy-path`（拷贝阶段的优化另一翼），构成高性能 IO 双翼（等待翼 + 拷贝翼）[边界]。

## 细节与核心 API

```go
// epoll（Linux 主流多路复用，Go netpoller 默认后端）：
//   epoll_create1 -> epoll_ctl(ADD) -> epoll_wait 拿就绪事件
//   边沿(ET) vs 水平触发(LT)：ET 仅状态变化时通知一次，须一次读尽；LT 没读尽会再通知
// io_uring（新一代，真正异步）：提交/完成两个 ring，系统调用近乎零开销
//   提交 SQE -> 内核异步执行（含文件 IO） -> 完成 CQE 回填，支持轮询免 syscall
// Go 现状：netpoller 仍基于 epoll/kqueue（非 io_uring），但收发走 runtime 托管
// 选型：高并发网络 epoll 足够；高 IOPS 本地磁盘随机 IO 用 io_uring 收益明显
// 矩阵：模型3（epoll）覆盖 99% 网络场景；模型5（io_uring）补齐“网络+磁盘统一异步”
```
