> 分类：MySQL 锁 | 难度：L2 | 题型：概念题 | 频率：中 | 关键词：**乐观锁**/**悲观锁**/**version 字段**/**FOR UPDATE**
> 原文锚点：第 16~40 段「乐观锁与悲观锁」

## 一句话总述
乐观锁与悲观锁是**并发控制思想**而非某把具体锁：乐观锁提交时检测冲突（版本机制），悲观锁修改前先加锁（DB 的 S/X 即其实现）。

## 面试官视角
- 考察意图：常混淆"乐观锁是 MySQL 锁吗"——它多为应用层方案，需讲清边界。
- 分档：P5 知乐观锁靠版本；P6 知悲观锁=先加锁；P7 知库/表/MDL/行锁都属悲观。
- 红旗答案：把乐观锁说成数据库提供的一把锁。
- 惊艳点：点出"乐观/悲观是思想，DB 各类锁归悲观阵营"。

## 主问答
**Q（面试官原话）：** 乐观锁和悲观锁有什么区别？
**A：**
1. **乐观锁（版本机制）**：表加 `version` 字段，读时带出版本；更新时 `WHERE version=旧值` 并 `version+1`，若已被他人改过则条件不满足、更新 0 行，应用读取后重试。适合**读多写少**。
2. **写多场景代价**：大量写时冲突频繁，业务层不断重试，反而拉低性能——此时乐观锁不划算。
3. **悲观锁（先加锁）**：修改前先 `SELECT ... FOR UPDATE` 等加 X 锁，阻止他人读写，直至事务提交；S/X 锁即悲观锁的实现。
4. **边界澄清**：库级全局锁、表锁、MDL、页锁、行锁都属**悲观锁**范畴；乐观锁通常是**应用层 version 字段**，非 DB 内置锁。

## 关键代码
```sql
-- 乐观锁：更新带版本条件
UPDATE orders SET status=1, version=version+1
WHERE id=10 AND version=1;
-- 悲观锁：
SELECT * FROM orders WHERE id=10 FOR UPDATE;
```

## 总结与追问预判
乐观锁=应用层版本冲突检测（读多写少佳），悲观锁=DB 的 S/X 先加锁（写冲突多时稳）；二者是思想，DB 各类锁归悲观阵营。

## ⚠️ 原文纠错
1. 事实核校： [经验]乐观锁版本机制、WHERE version=旧值+自增、写多则重试降级、悲观锁=修改前加锁(S/X 即实现)、库/表/MDL/行锁属悲观，均正确。
2. **补正**：乐观锁/悲观锁是并发控制**思想**，非 MySQL 内置锁类型；乐观锁一般为应用层 version 字段（原文归入"按锁性能分"易误解为 DB 锁）。
3. 崩坏词归一：漏关锁→乐观锁、被关锁→悲观锁、rgin/verging/verid/worgin/wordgin/进值→version（版本号）、事物→事务。
