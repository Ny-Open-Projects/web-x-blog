> 原文锚点：第 26~28 段「m 最多可以持有十个锁……lose 长度是十的一个数组」
> 主卡见 821-静态锁分级与m持锁上限。

## 思路与架构

要防的 bug 不是「死锁」，而是**锁序倒置**：A 持锁 1 等锁 2，B 持锁 2 等锁 1。静态检测靠**预先给每把锁一个 rank**。流程（`lockrank_on.go`）：

```text
lockWithRank(l, rank)
  └─ systemstack                       # 要访问 g.m.locksHeld 并可能 print/throw，用户栈上不安全
       └─ i 等于 locksHeldLen?
            ├─ i > 10 → throw("too many locks held concurrently for rank checking")
            └─ 正常 → 记入 {lockAddr, rank}
                 └─ i > 0 → checkRanks(locksHeld[i-1], 当前 rank)
                      ├─ 倒序 → fatal error: lock ordering problem
                      └─ 正常 → lock2 真正加锁
```

1. 入口 `lockWithRank` **必须切到 systemstack**——它要访问 `g.m.locksHeld` 并可能 `print`/`throw`，这些在用户栈上不安全。
2. 「第 11 把」的检查在**记录之前**：先判 `i >= len(locksHeld)` 再 `throw`。
3. `checkRanks` 只跟**前一把**（`locksHeld[i-1]`）比——因为**锁必须按 rank 单调获取**，只比相邻的就够。
4. `lockrank_off.go` 是同一套逻辑的空壳：`getLockRank` 返回 0、`lockWithRank` 直接转 `lock2`——**整个 rank 机制编译后为空**。

## 方案取舍

| 维度 | 方案 | 代价 | Go 选谁 |
|---|---|---|---|
| 检测时机 | 运行时动态推断 rank | 要维护全局锁持有图，**热路径开销大** | 否 |
| 检测时机 | **编译期静态 rank** | 新增锁必须手工配 rank，**漏配即误报** | **是** |
| 粒度 | 记录所有持锁 | 需 per-M 数组，有上限 | 部分（只记 m 当前持有） |
| 上限行为 | 第 11 把**等待/拒绝** | runtime mutex 不能失败返回 | 否 |
| 上限行为 | **`throw`** | 进程立刻死 | **是** |
| 错误类型 | `panic` | 可 recover，掩盖问题 | 否 |
| 错误类型 | **`throw` → `fatal error`** | 立刻暴露，不给误操作空间 | **是** |
| 默认状态 | 默认开启 | 误报风险高，production 易崩 | 否 |
| 默认状态 | **默认关闭（GOEXPERIMENT）** | 默认无检测 | **是** |

选型结论：Go 把它做成**默认关闭的编译期实验**——「宁可默认无保护，也不让用户被误报拦住」。**不适用边界：不要在生产环境开这个实验**（见下方实测）。

## 细节与核心 API

- `heldLockInfo{lockAddr uintptr; rank lockRank}`（`runtime2.go:467-471`）——**存地址不只存数量**，因为 rank 检查要按**同一把锁**配对（`releaseLockRankAndM` 靠地址找并 `copy` 压缩数组）。
- `m.locksHeldLen int` + `m.locksHeld [10]heldLockInfo`（`runtime2.go:722-723`）——注释明写「Up to 10 locks held by this m, **maintained by the lock ranking code**」，"maintained by" 就是「只有那套代码在写」的提示。
- `m.locks int32` 是**另一回事**：`lock2` 里 `gp.m.locks++`，`unlock2` 里 `gp.m.locks--`，负数则 `throw("runtime·lock: lock count")`——**纯粹防计数下溢**（比如漏配的 unlock）。
- `lockRankLeafRank` 是给「未指定 rank 的锁」的兜底值（`lockrank_on.go:71-73`）。
- `acquireLockRankAndM` / `releaseLockRankAndM` 是给**非 mutex 场景**（如 `cgoCheck`）用的无锁 rank 声明。
- `checkRanks` 只比较 `locksHeld[i-1]` 与当前 rank——**不做全序检查**，靠「获取时必须单调」这个不变式。

## 性能量级与实测数据

复现（go1.26.5 darwin/amd64）[实测]：

```text
$ go run .                                    # 默认构建
200 个 goroutine 竞争 sync.Mutex：正常结束

$ GOEXPERIMENT=staticlockranking go run .
fatal error: lock ordering problem
panic during panic
runtime.throw(...)                  runtime/panic.go:1229
runtime.checkRanks(...)             runtime/lockrank_on.go:166
runtime.acquireLockRankAndM(...)    runtime/lockrank_on.go:119
runtime.(*rwmutex).rlock(...)       runtime/rwmutex.go:75
runtime.preemptM(...)
$ echo $?
1
```

两个关键观察（本题最有价值的部分）：

1. **失败的不是用户的 `sync.Mutex`，而是 runtime 自己的 `rwmutex.rlock`**——`preemptM` 里要给 `allp` 加读锁。**这说明该实验在 go1.26.5 上已经与 runtime 状态不同步**：`preemptM` 的加锁顺序违反了它自己声明的 rank [实测]。
2. 报的是 **`lock ordering problem`，不是 `too many locks held concurrently`**——**两条不同的 throw 路径**。本例根本没到 10 把（只持有 1~2 把），是**序错了**。原文只提前者，等于把两种失败模式混成一个。

**为什么出现 `panic during panic`**：`checkRanks` 在 `systemstack` 上 `throw`，而此时可能已在 panic 处理中（`preemptM` 被异步抢占信号打断的路径），于是二次 panic——fatal 路径的常见二次故障。

**默认构建的零成本**：`lockrank_off.go` 里 `getLockRank` 是 `return 0`、`lockWithRank` 是 `lock2(l)`——内联后等于零；`locksHeld` 数组占的 80 字节（`runtime2.go:723`）纯属「为实验预留」。

## 答题技巧

```text
30 秒版：m.locks 是计数器防下溢；locksHeld [10] 只在 GOEXPERIMENT=staticlockranking
        下维护，超了是 throw 而非拒绝。默认构建没这个限制。

3 分钟版：先讲「防的是锁序倒置不是死锁」，再讲两个字段的分工，
         再讲两种失败模式（lock ordering problem vs too many locks），
         最后讲默认关闭的理由（新增锁漏配 rank 即误报 fatal，且实测已与 runtime 不同步）。

白板版：画主卡那张流程，写 lockrank_on.go / lockrank_off.go 这对文件名——
       「同一个机制的两个实现靠 build tag 二选一」本身就是高分点。

话术模板：「这题的关键是分清三个东西：计数器 m.locks、实验数组 locksHeld、
         以及它们只在实验下生效这件事。」

不会怎么接：被问「怎么给新的锁配 rank」——诚实收尾：在 lockrank_on.go 里用
          lockInit(&var, rank) 或 lockWithRankMayAcquire(&var, rank)，
          rank 值由 runtime 团队按全局锁序约定分配，不是使用者自己能定的。
```

## 广度与深度延伸

- 横向：Java 有类似的 lock-rank 调试选项；Go 的方案更激进——**直接 throw**。
- 纵向：`m.locksHeld` 与 `m.locks` 的分裂，类似于 per-M/per-P 字段的普遍模式（P 的本地缓存见 815-p的内存缓存）——「per-M 的东西其实常挂在 P 上」在 runtime 里反复出现。
- 规范：`GOEXPERIMENT` 是官方实验开关机制，`go env GOEXPERIMENT` 可查当前值；**实验不等于稳定 API**。

## 补充纠错（deep 级）

| 原文说 | 实际是 | 依据 |
|---|---|---|
| 「m 最多能持有的锁的数量是十个」 | **两个错误叠加**：① 默认构建**无此限制**；② 即使开实验，也不是「最多持有 10 把」而是「**第 11 把直接 throw**」 | `lockrank_off.go`；`lockrank_on.go:78-80` |
| 「lose 是长度 10 的数组，它存储的是当前 m 持有锁的信息」 | 真名 `m.locksHeld`；但「存储持有锁信息」的**只有实验构建**在写，默认构建**从不写它** | `runtime2.go:722-723` 注释 "maintained by the lock ranking code" |
| 「loks 字段表示 m 持有的锁的数量」 | 方向对，但它**不是"持有的锁"的记录**（那个在 `locksHeld`），只是**加锁计数器**，用途是检测 `unlock` 次数不匹配 | `lock_spinbit.go`（`if gp.m.locks < 0 { throw }`） |
| 「blocking 字段表示当前 m 是否被阻塞在一个 note 上」 | 描述基本正确但**因果讲反**：不是「goroutine 阻塞在 note 上」，而是 **m 在 `stopm`/`notesleep` 时挂在 `mp.park` 这个 note 上**——**g 阻塞挂的是 sudog**（见 814-g的调度上下文与阻塞等待字段） | `runtime2.go` `park note` / `blocked bool` |
