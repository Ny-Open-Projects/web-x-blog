> 分类：Go/并发 | 难度：L2 | 题型：概念题 | 频率：中 | 关键词：**Mutex** / **悲观锁** / **乐观锁** / **sync.Mutex**

> 原文锚点：第 1~5 段「悲观锁认为冲突总发生、访问前加锁；乐观锁假设无冲突、更新时校验；Go 的 sync.Mutex 属悲观锁(访问前加锁保护)」

## 一句话总述
`sync.Mutex` 属于**悲观锁**——它假设并发冲突总会发生，因此在对共享资源访问**之前**就加锁，保证同一时刻只有一个 goroutine 能进入临界区。与之相对的**乐观锁**假设冲突不发生，修改时不先加锁、而在更新时校验期间是否被别的 goroutine 改过（被改则放弃重试）。一句话背法：**「sync.Mutex 是悲观锁：访问临界区前先 Lock，假设冲突必发生；乐观锁先访问、更新时校验(被改则重试)，Go 乐观锁靠 CAS/版本号」**。

## 面试官视角
这是考察"是否理解锁的分类"的题，常用来区分只会调 Lock 的人和懂并发模型的人。
- **P5**：知道 Mutex 是用来加锁的。
- **P6**：能说出"Mutex 是悲观锁"并解释悲观/乐观区别。
- **P7**：能讲清 Go 没有内置乐观锁、乐观锁在 Go 里靠 CAS/版本号实现。
- **红旗**：以为 Mutex 是乐观锁；以为 Go 有内置的"乐观锁"类型。
- **惊艳点**：点出"悲观=先加锁再访问、乐观=先访问更新时校验"的本质差异，并预告 Go 乐观锁用 atomic CAS。

## 主问答
**Q（面试官原话）：** Mutex 到底是悲观锁还是乐观锁？

**先铺垫（由浅入深第 1 层）**："悲观/乐观"描述的是锁对"冲突会不会发生"的**预设**。预设不同，动作顺序就不同：一个先上锁再干活，一个先干活再校验。

1. **结论（第 2 层·机制）**：`sync.Mutex` 是**悲观锁**——核心假设是"并发冲突一定会发生"，所以进入临界区前必须先 `Lock()`，拿到锁才执行，出临界区 `Unlock()`，期间别的 goroutine 阻塞等待 `[源码]`。
2. **机制（第 3 层·与乐观对比）**：**乐观锁**假设"冲突大概率不发生"，因此修改共享资源时**不先加锁**，而是在真正提交更新时校验"这段时间内有没有别的 goroutine 改过"——没改就提交，改了就放弃/重试。乐观锁在 Go 里没有专门类型，通常用 `sync/atomic` 的 CAS 或版本号实现（见 1013 乐观锁）`[源码]`。
3. **边界（第 4 层）**：Mutex 的"悲观"体现在**加锁动作发生在临界区之前**；它不关心实际有没有冲突，一律先锁——冲突少时这会带来不必要的阻塞开销，此时乐观锁（CAS）更轻 `[经验]`。
4. **取舍（第 5 层）**：冲突少/临界区极短 → 乐观锁 CAS 更轻；冲突多/不确定 → 悲观锁 Mutex 更稳 `[经验]`。
5. **进阶（第 6 层）**：DB 层乐观/悲观锁见 1233；Go 层 Mutex 内部实现（CAS 快路径 + sema 睡眠）见 925 `[边界]`。

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
)

// 悲观锁：访问临界区"之前"就加锁，假设冲突必发生
var mu sync.Mutex
var balance int

func withdraw(n int) {
	mu.Lock()         // 进入前加锁（悲观：假设会有冲突）
	defer mu.Unlock() // 退出解锁
	balance -= n      // 临界区：同一时刻仅一个 goroutine 可达
}

func main() {
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			withdraw(1)
		}()
	}
	wg.Wait()
	fmt.Println("balance =", balance) // -100（并发自减安全）
}
```

## 总结与追问预判
**背这三句就够**：① **sync.Mutex 是悲观锁（访问前先 Lock）**；② **乐观锁先访问、更新时校验、被改则重试**；③ **Go 乐观锁靠 CAS/版本号，无内置类型**。
