## 思路与架构

```text
生产环境收到/发出 RST 的常见原因图谱
├─ 对端发出
│   ├─ 端口未监听 -> 内核代答 RST (connection refused)
│   ├─ 进程崩溃/被 kill -> 内核清算半开连接回 RST
│   ├─ 应用读缓冲溢出/对端主动 SO_LINGER(0) 关闭
│   └─ 对端 TCP 状态机校验失败(陈旧报文)
├─ 中间设备发出
│   ├─ 防火墙策略阻断注入 RST
│   ├─ NAT 表项超时后旧连接报文触发
│   └─ 负载均衡健康检查剔除
└─ 本端发出: SO_LINGER(0)/强制 Close/状态校验失败
排查顺序: 抓包看 RST 方向 -> 定位两端进程存活 -> 查中间盒策略
```

## 方案取舍
- **RST vs FIN 的完整对比**：① **优雅度**——FIN 走四次挥手，双方把在途数据发完才关；RST 立即弃连接，**在途数据直接丢**。② **TIME_WAIT**——主动 FIN 方进入 TIME_WAIT 等 2MSL；RST 关闭**不产生 TIME_WAIT**（这既是优点——排查端口耗尽时更利落，也是危险——失去 TIME_WAIT 对旧报文的吸收保护）。③ **半关闭**——FIN 支持半关闭（一方 shutdown(WR) 后仍可读对方数据）；RST 无半关闭，双向立刻作废。④ **确认机制**——FIN 有对应 ACK 计入序列号；**RST 从不被 ACK、也不占序列号**，收到方校验（序列号窗口内）通过即直接关闭 [源码]。
- **RST 不被 ACK 的深层含义**：因为 RST 本身可能来自「对端早已不存在的连接」，若要求 ACK 会陷入「给不存在连接确认」的死循环。代价是 **RST 可能丢失且无人重发**——发送方发完即认为对方会关，接收方没收到就继续挂在旧状态。这就是半开连接（一端以为活着、另一端已死）的成因之一，也是 keepalive/心跳存在的理由（`1849-http-vs-tcp-keepalive` [边界]）。
- **「connection refused」的内核代答机制**：客户端 SYN 到达但目标端口无监听时，**目标主机内核**（不是任何进程）回 RST——应用层表现为 `connect: connection refused`（实测 448µs）。这是 RST 用途②的日常形态，也是最快的失败模式：**比连接超时（黑洞丢包）快几个数量级**，所以排障时「秒拒」与「超时」指向完全不同的病因——秒拒查端口/防火墙 REJECT，超时查路由/DROP [实测]。
- **半开连接与探活**：一端崩溃重启后，另一端仍持有旧连接状态；重启方收到旧连接报文 → 状态不匹配 → 回 RST（用途③）。这解释了两个生产现象：① 重启后的服务收到「幽灵报文」并打出 RST；② 长空闲连接的死活探测不能靠 TCP 自身（默认 keepalive 2 小时+），应用层心跳才是及时方案 [经验]。
- **RFC 5961 与伪造 RST 防护**：早期 TCP 对「落在窗口外的 RST」直接接受，催生了盲 RST 攻击（猜测四元组+序列号即可掐断连接）。RFC 5961 引入 **challenge-ACK**：收到可疑 RST 时不直接关闭，而是回一个 challenge ACK 要求对方证明身份；真实对端会再发 RST（带正确序列号），伪造者则沉默。现代内核已默认开启，排查「RST 没生效」时要想到这一层 [经验]。

## 答题技巧
- 答完「会回 RST」立刻补边界「只终止当前握手，新 SYN 照常」——这句话是本题的分水岭 [经验]。
- 时序推演画在嘴上：seq=1 阻塞 → 重发 seq=5 → 旧包先到 → ack=2≠6 → RST，一步步说 [源码]。
- 被问「RST 和 FIN 区别」→ 四维对比（优雅度/TIME_WAIT/半关闭/ACK 机制）一口气报完 [经验]。
- 被问「生产上 RST 从哪来」→ 按图谱三分类（对端/中间盒/本端）+「秒拒查 REJECT、超时查 DROP」的排查口诀 [经验]。
- 主动边界到 `1843-tcp-handshake-recap`（握手状态机）、`1843-handshake-loss-first`（握手丢包重传）、`1849-http-vs-tcp-keepalive`（保活与心跳），构成 TCP 连接管理专题 [边界]。

## 细节与核心 API

```bash
# RST（复位）触发场景：
#  - 端口无监听进程：连接被拒，对端收 RST
#  - 已关闭 socket 仍收到数据（半打开连接）：RST
#  - recv buffer 满且对端硬塞（向已关闭方向写）：RST
#  - SO_LINGER 设 l_onoff=1,l_linger=0：close 直接 RST（不进 TIME_WAIT，但丢弃未发数据）
# 抓 RST：tcpdump 'tcp[tcpflags] & (tcp-rst) != 0'
# RST vs FIN：
#  FIN = 正常优雅关闭（我只不发数据了，仍收你的）；双向 FIN 才全关
#  RST = 异常立即终止（连接作废，不保证数据送达，无四次挥手）
# 生产：大量 RST 多指向“服务挂了/端口错/半打开/优雅关闭没做好/防火墙拦截”
```
