## 【学习目标】

- 说清 AutoDL 不同区域在公网接入策略上的差异，以及两种接入方式各自的配置写法。
- 独立完成「魔搭社区下载模型 → vllm serve 启动 → 日志判活 → 应用侧三项配置」的全过程。
- 理解模型体积、下载耗时、租用计费三者的成本关系，以及 api-key 在私有化场景下的真实地位。

## 【正文】

模型下载耗时较长，动辄几个 G 的体积不适合现场等待，所以这一步已经提前执行完，这里直接看结果。

先补充一个前置说明。此前采购的 AutoDL 机器都在西北 B 区，这类机器会在「自定义服务」里直接把 6006 和 6008 的公网 IP 暴露出来。但 AutoDL 各区域的策略并不一致：内蒙区域的服务器在「自定义服务」中看不到任何公网 IP，只给出一条 SSH 命令，让你通过 `ssh` 连接到这台服务器的 6006 端口。

为了把两种接入方式都演示到，又在内蒙 B 区加购了一台配置相同的服务器，之后的操作与之前完全一致：更新软件包、升级 Python、安装 `python3-pip` 与 Python3 虚拟环境，再把镜像源换成清华源。

## 一、建目录、装依赖、下载 Qwen3-4B

环境就绪后开始建目录：进入 root 下的目标文件夹，在其中创建 `vllm_deploy` 目录，进入该目录后创建并激活虚拟环境，再按文档把依赖装上。

依赖装完后，Qwen3-4B 已经成功下载到本地。原本计划装的是 Qwen3-8B，但它的体积有 16 个 G，遇上 AutoDL 网速只有几百 K 的时间段，下载要耗上好几个小时，而服务器在下载期间同样按时间计费，来回折腾会多出不少成本，所以换成了小一些的 Qwen3-4B。对比很直观：8B 是 16 个 GB，4B 只有 8.06G，下载快得多，因此最终使用的是下载 Qwen3-4B 的命令。

这笔账值得算细一点：下载耗时乘以每小时租用价格，就是模型的「落地成本」。16G 的模型在几百 K 的网速下要几个小时，费用远超模型本身的价值；换 8.06G 的 4B 后下载时间大幅缩短，费用随之下降。4B 与 8B 的能力差距在验证阶段可以接受，等链路跑通、确有必要再升级模型，先用最小可用模型把流程跑起来，是控制试错成本的通用策略。

下载命令可以在魔搭社区的模型页上取：页面上有一个「下载模型」按钮，点开后右侧就给出对应的下载命令，直接复制即可。命令中的 `--local_dir` 用来指定大模型落盘的目录，这里就是把它下载到当前文件夹下的 `Qwen3-4B`。

这里有个必须注意的点：文件夹名字要和模型名字完全一致，否则后面启动会报错，`--local_dir` 必须与模型名称保持一致。

「目录名与模型名一致」不是玄学，是 vLLM 定位模型的方式：启动命令里的模型名要在本地目录中找到对应结构，名字对不上就直接报模型不存在。魔搭模型页给出的命令本身自带正确的 `--local_dir` 值，直接复制即可规避该问题；手动改目录名是新手最常踩的坑。

## 二、vllm serve 启动模型

下载完成后，用 `vllm serve` 启动模型：后面跟上模型名字，再指定启动参数，把监听主机设为 `0.0.0.0`、端口设为 `6006`，同时指定最大模型长度为 4k。

三个启动参数各有目的。监听主机 `0.0.0.0` 绑定所有网卡，平台的端口映射才能把流量转进容器，与 12-3 里 Ollama 的 `OLLAMA_HOST` 是同一道理。端口选 6006 是因为 AutoDL 在未做企业认证的情况下默认只开放 6006，把模型服务部署在该端口上可以直接访问，不需要再到防火墙里单独放端口。最大模型长度 4k 限制上下文窗口，长度越短占用的显存越少，对 24G 显存的 4090 来说，4k 长度给权重和激活值留出了充足余量；后续业务上下文变长时再调高该参数。

回到浏览器验证启动结果，正常启动后日志里会出现 `Starting vLLM API server`，监听在 `0.0.0.0:6006` 上，与启动命令里指定的主机和端口一致，看到这一行即代表启动成功。

判活看日志是推理服务的通用技能：`Starting vLLM API server` 这行出现，说明权重加载、显存分配、端口绑定全部完成，服务进入可接受请求的状态。在这行出现之前发请求只会得到连接拒绝。启动过程要等模型权重从数据盘读进显存，小模型也要几十秒，耐心看日志比反复刷新浏览器更可靠。

## 三、两种接入方式：公网直连与 SSH 隧道

模型跑起来后，就回到代码里调整 OpenAI 相关配置：`base-url`、模型名称、`api-key` 都要改。下面以 BI 报表问答系统为例演示整个过程。

先看 YAML 配置文件，先把项目停掉。文件中原本有一份 OpenAI 配置，`chat` 的 `model` 之前用的是 `Challenge3 Max`，现在要换成 `vllm serve` 启动时指定的模型名字，直接粘过来即为本地部署的模型。

接着是 `base-url`。它与此前西北区 AutoDL 上部署 Ollama 的写法不同：西北区那台机器在「自定义服务」里已经把公网地址映射好了，代码里（智能调拨那部分）直接写公网地址即可。而内蒙区的机器根本没有公网地址，处理方式反而更简单，平台既然提供了 SSH 命令，就在业务服务器上通过这条命令与 AutoDL 建立隧道，之后用本机 `localhost` 访问即可。演示时用的是 Windows 机器，真实环境中 BI 报表问答系统会部署在独立的一台业务机器上，做法相同。

```mermaid
flowchart LR
    subgraph 方式一：公网直连（西北 B 区）
        A1[业务服务器] -->|https 公网地址:8443| B1[AutoDL 容器 6006]
    end
    subgraph 方式二：SSH 隧道（内蒙 B 区）
        A2[业务服务器 localhost:6006] -->|ssh 端口转发| B2[AutoDL 容器 6006]
    end
    B1 --> C[vLLM + Qwen 模型]
    B2 --> C
```

| 对比项 | 西北 B 区 | 内蒙 B 区 |
|---|---|---|
| 自定义服务 | 暴露 6006/6008 公网 IP | 不暴露公网 IP |
| 接入凭证 | 公网地址 | 一条 SSH 命令 |
| 应用侧 base-url | 公网映射地址 | `http://localhost:6006` |
| 前置动作 | 无 | 业务服务器上先建 SSH 隧道 |
| 适用判断 | 平台给了公网地址就用 | 平台只给 SSH 命令就建隧道 |

以平台给出的 SSH 命令为例：在本地开一个命令行窗口，把命令粘进去，可以看到它就是通过 `ssh` 连接 AutoDL 服务器的 6006 端口。回车后提示输入密码，密码粘贴进去再回车，光标停在原地不动、没有任何报错，就说明隧道建立成功，本地的 6006 端口已经和远端 AutoDL 服务器的 6006 端口打通。

「光标停住不动」是 SSH 隧道建立成功的标志，不是卡死：隧道以前台进程的方式保持连接，窗口不能关，关了隧道就断。生产环境会将该进程交给 systemd 或 autossh 托管，保证断线重连。

于是 `base-url` 可以直接写成 `http://localhost:6006`：访问本机 6006 的流量经由 SSH 隧道抵达 AutoDL 的 6006，而该端口上运行着 vLLM，vLLM 又加载着 Qwen 模型，链路就此打通。

再来看 `api-key`。vLLM 启动模型时并不会生成 `api-key`，换句话说私有化部署场景下根本用不到它。

该现象正好呼应前面提过的现象：不少课程会强调要把 `api-key` 放进环境变量再从环境变量读取，于是容易形成固化思维，认为把 `api-key` 直接写在配置里就是「不规范、太 low」。实际上私有化部署时该字段没有任何作用，这里可以直接写一个 `EMPTY`。

但不能将该 `api-key` 配置项删掉。OpenAI 协议要求请求中必须携带该属性，即便没有值也必须存在，所以不能直接注释掉，要保持开启，值随便填即可。

三个配置项在私有化场景下的正确姿势可以归成一句话：base-url 指向自己的服务，model 用服务器上真实启动的模型名，api-key 保留配置项但值随意。前两项决定「连得上、调对模型」，第三项决定「协议合法」。把 api-key 删掉导致请求体缺字段，是私有化接入期最典型的低级错误，错不在「写死在配置里」，而在「根本不该删」。安全实践要分场景看：公有云 API 的 key 必须进环境变量或密钥管理，因为 key 本身就是钱；私有化内网端点没有鉴权，key 只是个占位符，为它设计环境变量属于仪式感。

最后提醒一点：学习某项技术时不要被别人的说法固化成思维定式，别的老师这么教就照搬，别人说没把 `api-key` 放进环境变量就是不规范，你也跟着这么认为。学得越深越会发现，同样的做法在不同场景下会有完全不同的解读。

## 【易错点 / 面试题】

1. **面试题：私有化部署后，应用侧连接模型服务要改哪三个配置？各有什么注意点？** 答：base-url 指向模型服务地址（有公网映射写公网地址，只有 SSH 命令就先建隧道再写 localhost）；model 必须与 `vllm serve` 启动时的模型名一致；api-key 配置项必须保留但值可随意（如 `EMPTY`），因为 OpenAI 协议要求请求必须携带该字段。
2. **易错点：`--local_dir` 目录名与模型名不一致。** 表现为 vLLM 启动时报找不到模型。直接复制魔搭模型页给出的下载命令，不要手动改目录名。
3. **易错点：用模型体积赌网速。** 下载期间服务器照常计费，大模型遇上网速低谷，费用可能远超预期。先算「体积 ÷ 网速 × 时价」再决定模型规格，验证阶段优先小模型。

## 【小结】

本节完成 vLLM 部署的落地动作：魔搭社区下载 Qwen3-4B、`vllm serve` 以 `0.0.0.0:6006` 加 4k 上下文启动、按日志判活、应用侧改好三项配置。两种接入方式的取舍可以固化为判断规则：平台给了公网地址就直连，只给 SSH 命令就建隧道，应用侧 base-url 相应写公网地址或 localhost。

配套工程 `980-demo` 把这三项配置抽象成了与部署方式无关的形式：`980-demo/src/main/java/com/carl/ai/transfer/config/ChatModelConfig.java` 通过 `transfer.llm.base-url`、`transfer.llm.model`、`transfer.llm.api-key` 三个属性装配 `OpenAiChatModel`，Ollama 与 vLLM 共用同一份代码，换端点只换配置值；没有 GPU 环境时 `transfer.offline=true` 切到 `OfflineChatModel` 返回固定 JSON，主链路不依赖任何外部服务。
