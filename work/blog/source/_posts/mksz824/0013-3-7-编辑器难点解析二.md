上节课介绍了编辑器整体的状态设计和几个典型场景的实现。大家应该发现其实没那么复杂，要做的就是对全局状态 components 字段进行修改而已。现在用一张更大的图描述应用的整个流程：完成了数据到画布渲染的第一步，有这样的数据就能渲染出对应的画布，text 是 hello，字体和颜色也有对应值。

接下来要完成的是：点击画布中的某个组件，需要将元素的属性以不同表单的形式展现到右侧。属性和组件的对应关系都有定义，最终的实现还有属性分组等，这里暂不考虑。

## 方案一：表单写死在页面

先看数据流。点击选中组件后，可以筛选出所选组件里有什么值，比如 text: 'hello'、font family、color: purple。

很容易想到的做法是把这些表单组件写死到页面中：拿到 current component 的 props，假设有 text 和 color 两个值，就顺序写下去，第一个用 input，value 等于 text 的值；处理 color 时用一个叫 Color Picker 的特殊组件，也接受一个值。属性非常多的话，就一个一个继续写下去。

这样写非常简单，但后期问题也很多。第一，代码非常冗长，属性多就要一直写，一百个属性就得写一百个对应组件。第二，对不同类型的业务组件都要做判断：text 组件渲染这些表单，else if 判断是 image 就渲染和 image 相关的组件，要写一大堆特别长的逻辑。第三，可扩展性非常差，添加新业务组件时又要在后面加一大堆 if else。这是一个很差的实现方案。

## 方案二：Props Map 数据驱动

看到界面展示应该想到另一个维度：界面 UI 其实就是数据的抽象。所以自然想到用特定的数据结构把它渲染成界面。给这个数据结构起个名字，叫 Props Map。

它把元素中的每个属性和一系列值相对应，值里有一个 component 字段，指明用什么组件去处理它。比如 text 需要 input，font family 用 drop down，color 使用 color picker。

```ts
const propsMap = {
  text: { component: 'input' },
  fontFamily: { component: 'dropdown' },
  color: { component: 'color-picker' },
}
```

渲染时循环这个 object 的 map，拿到 key 和 value：key 用来从 propsMap 中取出 component，就是要渲染的组件；再把对应的 value 传进去，就能渲染出对应的表单。比如 text 是 input，就把 hello 作为它的 value 灌进去；font family 是 drop down，value 是黑体，传进去显示对应值。

遇到没有类似表单组件的情况，还可以二次开发，只要这个组件有 value 属性就可以了。比如 color 等于 purple 没有现成组件，就自己开发或二次封装一个取色器，传入 value 即可。这在一定程度上满足了可扩展性这个命题：组件的属性可以扩展。

组件类型同样可以扩展。简单组件有这些属性；复杂组件比如幻灯片，只有一个属性 pictures，是一个数组，里面有一系列图片。可以给它定义对应的处理组件 picsProcessor，value 传入一个图片数组，内部自己去实现，比如渲染出两张图片和传入的图片一一对应。组件的可扩展性问题就完成了。

## 组件的更新

说完展示再说更新。数据流始终保持自上而下的顺序：表单更新最终要反射回到总体的 store 中。做法是在对应组件中发射一个 change 事件，change 发生时我们能知道是哪个元素的哪个属性以及新的值是什么，就用这个信息在全局 store 中更新这个值。

比如把 hello 改成 hello2，发射一个事件出去，事件详情包含：是哪个元素在更新（id 等于 1）、更新的属性是 text、新的值是 hello2。store 拿到这些值来更新，再自上而下传递，最终画布上的值被更新，数据流动就完成了。

```ts
function handleChange(propKey, newValue, id) {
  const component = store.components.find(c => c.id === id)
  component.props[propKey] = newValue
}
```

handlechange 要传出去的有 propKey（哪个属性）、newValue（新值）和 id。首先找到更新的是哪个 component，然后 update component 的 props：propKey 等于 newValue，整个过程就完成了。

除了表单更新，画布的更新也采用发射事件的方式对 store 的某些值进行更新。比如在画布上拖动改变位置，拖动过程触发对应的 change 事件，用相同的逻辑更新值：拖动其实就是改变了 left 和 top 这两个 position，最终位置发生改变。注意要在业务组件外层添加一个 wrapper 包裹，做成透明的，各种事件都放在这个 wrapper 上，比如拖动就在上面发送 change 事件。

复杂组件也是如此。不管内部逻辑多复杂，比如幻灯片里有上传图片、删除、编辑等操作，最终发出来的值就是对 picture 这个值的变化：多加了一张照片，数组里的值从两项变成三项，就是这么简单。

## 画布操作的插件化

最后一个问题是画布操作的插件化。比如快捷键：选中后按 Delete 可以删除元素。这些快捷键可以写成普通的可重用函数，比如 useHotKey，提供一系列回调：第一个值是 delete，点击 delete 时触发对应的事件，回调写在这里。这些函数都提供回调，在回调中对全局 store 进行一系列改写。而快捷键功能和编辑器本身没有任何关系，这就做到了解耦。

## 一个延伸问题

这节课想讲的道理是：界面是数据的反应。看到复杂的界面，首先想想能否用数据来代替它，就像我们用的小数据结构 Props Map，用了它就发生了翻天覆地的变化。

也许有人有疑问：假如表单组件传入的属性不叫 value，变化的事件不叫 change，怎么办？其实这里只定义了最简单的 component 结构，还可以丰富地扩展它。比如定义 valueKey，你就可以用 value2 这个属性传入值；再添加 eventKey，不用 change 事件而用 input 事件来更新，都可以自定义化，甚至可以添加更多属性来完成更多功能。
