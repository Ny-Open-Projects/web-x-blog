选好 MongoDB 作为数据库、完成基础知识学习后，接下来就是数据库设计。关系型数据库有各种冗长的设计原则，而 MongoDB 是以文档（或者说 JSON）为根本的非关系型数据库，学习过程中大家应该深刻体会到：JSON 格式的数据结构要简单很多。

官方文档里有一篇 MongoDB Schema Design Best Practices，是我最近看过的关于 MongoDB 最好的一篇文章。这里抽取它的精华作为脉络，结合我们的应用聊最佳设计实践。请大家把这篇文章收藏一下，有需求时拿出来看看，属于常看常新的指南。

首先要注意一件事：做 MongoDB 数据库结构设计时，千万不要把关系型数据库的条条框框照搬过来。比如一想"我要创建几个表、表之间什么关系"，就要把这些表和表间联系从脑子里抛掉。文档里特别谈到几点：no formal process，没有特定的流程；no algorithm，没有特定的算法；no rules，没有特定的规则。它是非常自由的设计形式，唯一的要点是针对你要实现的应用进行设计、对症下药。两个目的不同的应用，即使数据相同，也可能设计出完全不同的两套方案。

所以开始设计前要再次弄清需求：应用要存储什么数据、它们的关系怎样。大家可以翻看之前的需求文档，我不再一条条回顾。我们的应用有几个实体？第一个肯定是用户 user，用户承担了很重要的角色：注册、登录、修改用户信息等，很多其他数据都围绕它展开。第二个是 work 作品，应用的核心，就是一张张海报，里面包含海报的一系列信息。用户和作品的联系：一个作者可以有多个作品，一对多关系。第三个是渠道 channel，作品展示海报的不同途径，用户可以将一个作品在多个渠道推广，每个渠道都有一个特殊的 URL，所以作品和渠道也是一对多。应用主要由这三个实体组成，后期功能成长可能还有更多，先归纳为这三个。MongoDB 的好处之前也说过：不需要预先把结构设计得多么完美，可以根据需求不断进化数据库结构。

用 JSON 描述一下，不难发现有可能是这样的结构：最外层是 user 信息，user 有多个 works，所以里面是个数组；作品里因为渠道和它一对多，也有个渠道数组。

用 JSON 描述完就会发现，MongoDB 数据库设计的关键我认为只有一个问题，文章也是这么写的：当两个实体产生联系时，选哪种方案实现对应关系。这是唯一要设计和选择的问题。方案一是内嵌（embedding）：数据直接保存在一个对象（数组）中，就像我们的 hobbies 那种形式。方案二是引用（referencing）：数据存储在另一个集合中，保存和当前数据产生关系的内容，使用 $lookup 做跨集合查询。比如把 user 单独存一个 collection，works 存另一个集合，works 用一个特殊字段（比如 userId）保持两者的关系。

两种形式有利有弊，要根据特点选型。先看内嵌的优势：数据都写在一个结构里，一次查询就能获取全部信息；避免多集合查询；操作是原子性的，一个操作就能更新多个信息，比如 user、works、channels 三个实体的信息都可以通过一个操作更新。劣势也有：单个文档可能特别大，查询更耗时，获得无关信息的概率增大，比如取一个 user 时，里面 works 的信息会非常繁杂；更要特别注意的是，MongoDB 对单个文档（collection 中的一条 record）有 16 兆的最大限制，内嵌非常多数据时可能超过限制导致出错。

再分析引用的优势：数据分散到不同文档，单个文档数据量变小；不太会触及 16 兆限制；每次查询取得不必要数据的概率降低，查一个 user 时不会带出 works 的信息。劣势自然就是内嵌的优势反过来：可能需要多次查询或使用 $lookup 才能获得最终数据，比较繁琐。

分析完这个关键问题的细节，对不同关系就要按实际情况分析，在两种方式中做取舍。下节课结合数据量的多少和我们的应用特点，完成数据库的具体设计。
