## uploadToOSS

创建一个方法，称之为 uploadToOSS。先从 this 上解构出 ctx 和 app，因为使用 stream 还要把 stream 也拿过来，仍然用之前的 `this.ctx.getFileStream()` 拿到一个读流（readStream）。

接着确定上传的位置。bucket 已经固定为之前创建的 OpsFlow-backend，bucket 里还可以再建子文件夹。我们的路径设计是：bucket 下的子文件夹 imtest，再是文件名。文件名和之前一样生成一个六位随机字符串，加上扩展名 ext。这个大家已经很熟悉了，创建一个 path 变量 savedOssPath：`join('imtest', nanoid(6) + extname(stream.filename))`，扩展名从 stream 的 filename 上拿。

## 上传：ctx.oss.put

上传用 ctx.oss 实例上的 put 方法。外面套一个 try/catch：`const result = await ctx.oss.put(savedOssPath, stream)`。put 的第一个参数 name 是要上传的文件地址，第二个参数 file 的类型是 any，可以适配多种文件类型：可以是一个 string（文件地址）、一个 buffer，也可以是一个 stream。这里直接把 stream 传进去。

还可以用另一个方法 `ctx.oss.putStream`，它只能上传 stream，第二个参数就是流。这里选 put，适用性更广。

拿到 result 后看一下它的类型：PutObjectResult 里有 name、url 等一系列数据，还有 response，response 里包含 status、headers、size 等详细信息。我们最关心的是 name 和 url 两个属性，可以先用 `app.logger.info(result)` 打印出来观察。既然拿到了 name 和 url，就可以直接返回：用 `ctx.helper.success` 返回，只需要 name 和 url 两项。

## 失败逻辑：必须消费掉流

catch 里的失败逻辑有一个特别注意点：在返回之前，必须把上传的文件流消费掉，否则浏览器的响应就会卡死。egg 团队提供了一个特殊的库 stream-wormhole（wormhole 是虫洞的意思，把 stream 放进虫洞消费掉）。用法很简单：`await sendToWormhole(stream)`，它是一个 promise。自行安装后 import 出来直接用。

流被消耗掉之后，返回之前添加过的错误信息：`ctx.helper.error(ctx, 'imageUploadFail')`，错误 type 是 imageUploadFail。失败情况大家可以自己测试，这里测正确的。

## 测试

把 router 中 upload 的处理换成 uploadToOSS，保存。用之前那张 bubble 的 png 做测试，点击 Send。成功的话应该返回两个值：url 和 name。可以看到成功返回了 name 和 url，url 应该可以直接访问到图片。也可以到 OSS 管理控制台验证：bucket 下面进入文件管理的 imtest，能看到刚上传的图片，点击详情复制 URL，下载下来查看，就是上传的那张图片，说明整个流程没问题。日志里除了 name、url，还有 response 里的 status、statusCode 等详细信息。

## file 模式与 stream 模式对比

这节课用阿里云完成了单文件上传，用的是流（stream）模式。用 file 模式的话会更简单，put 的数据换成 `ctx.request.files` 对应的第一个 files 即可。但特别注意一点：file 模式下文件已经被保存在本地某处，上传到云服务之后，还需要用 fs 把本地文件删除，因为最终保存目的地是云服务，不需要保留本地文件。

这也是 stream 模式对 file 模式的优势：虽然 stream 更难理解，但效率更高。对比一下两种模式的步骤：

- file 模式要三步：getStream 保存到本地文件（save to local file），然后把 file 上传到 OSS，最后 finally 里 delete 本地文件；
- stream 模式只有一步：getStream 直接拿到 stream，然后 upload to OSS，其他操作都不需要，因为没有本地文件。

到这里就总结完了 file 模式和 stream 模式的异同与优劣。
