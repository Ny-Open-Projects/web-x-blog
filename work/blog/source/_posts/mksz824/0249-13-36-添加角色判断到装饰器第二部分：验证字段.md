上节课我们添加了对应的权限判断，但在权限判断中还需要考虑 fields 的有效性：更新或者创建对应实体的时候，只能限定到特定的属性。在 work 中表现为这些对应的字段，而另外一些字段，比如 work 中的 isTemplate 属性，普通用户是无法创建或更新的。这节课就来添加这部分代码。

来到 checkPermission 对应的 decorator，添加一系列逻辑。之前我们使用 rule && rule.conditions 判断了是否有 condition，自然也可以使用 rule 上的一个属性判断它是否有 fields。先加一行注释：判断 rule 中是否有对应的受限字段（fields）。然后判断 rule && rule.fields，假如有的话，把 fields 先取出来，跟 body 中的数据进行比对。类似的工作之前做过，大家应该都很清楚。

需要的第一个东西是 CASL 中的一个 function：from '@casl/ability' 的 permittedFieldsOf。拿到它以后就可以进行获取了。这里特别注意，上面的分支经过了一次数据查询，而这里不需要查询特定的记录。看 rules 可以发现，虽然规则里有 condition，但要拿 fields 不需要经过查询也能拿到结果，和查询的结果无关，所以直接获取就好。

第一步获取对应的 fields：`const fields = permittedFieldsOf(ability, action, modelName, options)`。第一个参数传入 ability，第二个是 action，第三个是 modelName。注意这里不需要查询，直接传字符串就好。第四个是 options，这个是必填项，必须写。在最上面把它添加一下，复制过来即可，跟之前基础知识的写法一样。写完以后大家对 options 就清楚了：options 其实就是我们使用这个方法调用得到的最后结果。另外要注意，这里并没有像原来那样在 rule.fields 不存在时直接设置所有字段，现在我们知道，假如没有 rule.fields，就说明没有具体的受限条件，所以直接给它设置一个空数组，再把 options 传入过来。

拿到 fields 后会获得一个数组，但最好先判断数组里面是否有值再进行判断：if (fields.length > 0)。大于零就可以做比较了。这里有两种解决方式。之前使用的方式是 lodash 的 pick，把 requestBody 做一个过滤。第一种思路就是过滤 request body，我们不想采用这种方式，加一个星号标记代表不采用。我想采用另外的方式：判断 fields 和 requestBody 的值的关系。假如 fields 对 payload keys 的关系是全部包含，说明没问题；假如 payload 里有一些不包含的字段，直接输出错误。这样我们就不需要过滤 body，而是返回一个 true 或 false 的结果。

第二种方式的第一步是获取 payload 的 keys 来做比较，也就是 payload keys 对 fields 应该是全部包含的关系。确定了使用第二种方式，返回一个最终成功或者失败的结果。使用 Object.keys 拿到 requestBody 的一系列 keys，然后判断是否是全包围的关系。这里可以借助 lodash 的一个方法 difference，文档里写：create an array of array values not included in the other given arrays，可以解决我们的问题。假如 payload keys 全都包含在 fields 里，它会返回一个空数组；假如 body 有 fields 没有包含的字段，它会返回一个拥有这些字段的数组，我们可以用这个数组的值进行判断。lodash 已经安装完毕（大家自己去安装，说过多次了），从中导出 difference。

进行计算，称之为 diffKeys：difference(payloadKeys, fields)。第一个参数是要判断的 payload keys，第二个是你想拥有的所有字段，也就是 fields。这样就能拿到有区别的 keys。假如它的 length 不等于零，说明 payload keys 有不存在于 fields 里面的字段，要返回 false。

所以添加一个新的变量。原来的 permission 是判断其他权限的，这里再加一个 keyPermission，一开始应该是 true，因为假如没有对应的 rule，我们希望它是通过的。keyPermission 等于 diffKeys.length === 0，等于零时是合法的。最后把判断添加上去：除了 permission，还要满足 keyPermission。

现在这个过程就写完了，大家可以回顾一下。关键是这两个思路：第一种是过滤，第二种是判断是否通过，其实一个意思，但我们这里想返回一个 true false 的结果。

可以进行测试了，测试 create work 和 update work。updateWork 还没有添加对应的 permission，我给大家添加一下，复制一份 checkPermission。添加后 update 就已经有对应的权限管理了。我这里把 diffKeys 打出来，看得更清楚一些。

登录一下，还是用户 123，把 token 复制。第一步来到 create empty work，把 bearer 添加进去。body 现在是合法的，我们给它添加一个不合法的数据 isTemplate: true，点击 send 应该返回错误。可以看到它显示"没有权限完成操作"，看一下 diffKeys，多了一项 isTemplate，所以不合法。把 isTemplate 删掉再创建，应该没有问题，返回了正确的结果。
