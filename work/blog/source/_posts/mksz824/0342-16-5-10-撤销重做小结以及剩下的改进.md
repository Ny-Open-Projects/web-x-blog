撤销重做功能到这里已经完成。它是本周的难点，开发周期也比较长，所以用一小节做个回顾，并留几个可以继续优化的点。

## 开发演化过程回顾

**第一步：需求分析。** 最简单的方案是全量保存，每次修改都把完整数据存下来，但缺点很明显：数据大量冗余，需要很大的空间。优化方案是只保存修改相关的数据。操作分为三种类型：新增、删除、修改，于是确定了 `HistoryProps` 的结构：type（add/delete/modify）、componentId、data、index 等字段。

**第二步：记录操作。** 在 state 里添加 histories 数组和相关 key，每次操作后把对应类型的历史记录 push 进去。

**第三步：数据指针与反向操作。** 确定 `historyIndex` 作为当前操作位置的指针；undo 时往前移动，并对不同类型的记录做相反的操作，add 反向是删除、delete 反向是恢复原位、modify 反向是恢复旧值。

**第四步：单元测试。** 先写基本的 case 验证核心逻辑。

**第五步：界面测试并提出改进。** 界面测试暴露出很多测试用例覆盖不到的场景，由此引出一系列进阶改进：

1. **一次操作回退多个值**，针对移动和修改大小。改进 `updateComponent`，参数变成 `UpdateComponentData`：key 是 `keyof AllComponentProps` 或其数组，value 是 string 或 string 数组，一次更新多个键。undo 里把这段处理抽成了独立的 `modifyHistory` 函数，用 `Array.isArray(newKey)` 判断，数组就循环逐项回滚。
2. **记录防抖**，input 输入这类快速连续操作只记最后一次。实现了一个简单的 `debounceChange`（闭包 + 清除 timer 的常规做法，lodash 的 debounce 复杂得多），再用它包裹出一个防抖版的 pushHistory。
3. **缓存最初的旧值**，防抖后回滚要回到动作开始时的值，所以在 state 里加了 `cacheOldValue`：操作开始时缓存旧值，push 后用缓存值记录，最后恢复成 null。
4. **最大条目数 + 回滚中途编辑**，用一个统一的 `pushHistory` 函数处理：超过上限就 shift 第一项再 push；如果 `historyIndex` 不等于 -1，先把之后的所有记录一次性删除，添加新记录，最后把 historyIndex 重置为 -1。

## 留给大家的优化点

以下几个方向大家可以酌情自己完成，代码中不做具体实现：

1. **state 结构优化**：现在历史记录相关的字段都直接平铺在 `EditorProps` 里，可以把它们往下嵌套一层，比如收进一个 `history` 键中，更清楚地表达「这些都是 history 相关操作」。
2. **帮助函数外迁**：editor.ts 这个文件确实有点长了，`debounceChange`、`pushHistory`、`modifyHistory` 这些帮助函数可以移动到单独的文件中去，不挂 tag 的话要滚很久才能找到。
3. **补全单元测试**：根据这些 case 把剩下的单元测试补全，保证功能正常运行。
4. **快捷键**：hotkeys 里还没有添加 Ctrl+Z 和 Ctrl+Shift+Z 这两个回滚和重做的组合键，添加起来应该很简单。
5. **页面设置的回滚**：修改页面背景颜色、背景图片目前没有对应的回滚功能，可以在记录里标明这次修改是页面级还是组件级的，然后补上。

最后希望大家多测试几遍，这个功能比较复杂，实现过程中可能还有大大小小的 bug，可以尝试修复。

## 两道思考题

围绕 undo/redo 在不同情景下的实现留两道思考题：

1. 一个简单的编辑器（比如我们这个），它的回滚和重做是怎么实现的？相对简单，结合本周的内容想一想。
2. 一个复杂的编辑器（比如 VS Code）也支持回滚和重做，它又是怎么实现的？

对照这两个场景，看看能不能形成自己的想法。这节课的回顾就到这里，整体实现、可能的优化和思考题都梳理了一遍，希望课下好好消化。
