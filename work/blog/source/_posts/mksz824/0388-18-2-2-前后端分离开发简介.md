前面的内容一直在和编辑器交互与功能打交道，现在编辑器已初具规模，是时候把后端环境请出来了。上一阶段已经介绍了后端 API 开发的过程，现在要把两者结合起来。

现代应用开发自 SPA 单页应用出现以后，前端和后端可以并行工作，最后再做接口联调和整合，这就是前后端分离的开发方式。大家对它应该已经很熟悉了，这节只简单描述流程，并讲几个比较特殊的点。

## 流程中的三个要点

**第一，定制接口。** 双方在最初按照需求讨论并定制接口、参数和返回数据，一般采用 RESTful 协议。课程里也模拟了这个流程，真的是开过会讨论的。

**第二，文档化并做好版本管理。** 开会完毕要把结论文档化，记录在某处方便其他工程师查询。我们在语雀里记录了 "B端 server 主要接口" 文档，把接口划分成系列条目，还提供了 Postman 文件下载。另一个属于定制规范（也是 RESTful 的规范）的要点是 API 版本化：每次升级后能清楚查看变动和修改，这是 best practice。可以看 Shopify 的 API version release notes，每次 release 都列出新添加的接口和旧的 breaking change，方便回溯参考。

**第三，用工具实时查看和运行。** 前后端分离时，双方要维护一份共同文档规定相同的响应格式。对一个 RESTful API 我们要了解四件事：

1. endpoint，具体路径（URL）；
2. method，get、post、patch 还是 delete；
3. 参数在 URL 的 query 还是 body 里，比如 parameters 里的 id（string 类型，指当前资源）；
4. 最关心的：返回格式，比如一段 JSON data 里有哪些 key，失败时是否有 401 这样的响应。

纯文档维护起来繁琐，也没有归类、筛选、调试等基本功能，想真实调试还得写代码。于是专用的分类管理和调试工具出现了：

- **Postman**：客户端工具，从官网下载；把课程提供的 JSON 文件导入后，接口会自动分类（用户、作品、工具、渠道）。随便点开"获取短信验证码"，URL、方法、header、body（发送 JSON 格式的 phoneNumber）、响应示例一目了然，后面会一直用它。
- **Swagger**：在线工具，和 Postman 类似，区别是它可以根据代码注释直接生成一个 web 网站。同样提供分类、参数说明和响应格式，还支持实时调用：点 Try It Out、输入参数、点 Execute，就能实时返回 Response Body。

建议在真实项目中一定要用这类工具做 API 的管理、查看和运行。

## 开发与联调

完成定制规范后进入开发阶段。接口规范上双方使用 RESTful 协议；前端还可以借助 Node 生态现成的工具给自己提供一个 Mock Server，顾名思义是假的 Server，但接口规范和后端真 Server 完全一致，后面会介绍这样一个工具供真实工作环境使用。课程后续开发会直接用真实接口，因为录制时接口已经全部开发完毕。这样前端与后端就能并行开发，极大提高效率，分工也更明确。

最后是联调阶段：前端切换成后端接口，进行功能校验即可，然后提测。

## 这种方式的优点

1. **打造精益团队**：分离后前后端工程师只专注各自的开发工作，实现自治，能培养独特的技术特性；
2. **提升开发效率**：代码解耦，只需要约定接口参数就可以并行开发，不是串行等待，整个应用的开发效率有质的提升；
3. **增强代码可维护性**：应用代码不再混为一谈，只有运行时才存在调用关系。
