上节课完成了界面的自定义显示，我没有在界面里进行测试，因为对测试用例比较有信心；课下在界面中验证了一下，没有问题。测试带来的这种不使用界面的开发方式，我觉得非常有趣。这节课完成下一步工作：生命周期函数，和大家一起完成 before-upload，也就是上传之前的验证。

## 需求分析

对使用者来说这个功能比较重要。有了这个生命周期函数，用户可以完成上传之前的验证，验证上传文件的大小或类型，返回布尔值；还可以完成结果的转换，比如想上传一种类型的文件，需要经过另外一个 API 处理，处理完后返回另外一个结果再去上传。验证很简单，用布尔值代表；转换结果则可能请求某个接口拿到一些属性，将文件转换后再进行下一步工作。

这节课还是采用 TDD 的写法，会学到一点新的关于测试的东西。先说结论：好的测试有时要比代码实现写得多很多，测试越详细，出错的概率就越低，这就是测试代码覆盖率的问题。

case 我已经写好了，不从头写，因为大家已经比较熟悉。特别注意，我把 mockedAxios 的 post 在每个例子的 afterEach 里做了 mockReset。写好了两个 case：

第一个 case 是 beforeUploadCheck。里面定义了一个函数 checkFileSize，判断 file size 大于 2 就返回 false。测试里 file size 是 2，也就是大于 2，所以应该返回 false，即上传不成功。通过把函数以 beforeUpload prop 的形式传入 wrapper，然后用三个断言验证是否符合预期：post 不会被调用（在 post 之前就直接 return false 了）；界面上的 li 长度等于 0（没有上传任何文件）；另外添加了一个 jest.fn() 作为 callback 传入 checkFileSize，验证里面的 if 逻辑有没有被调用过。

第二个 case 测试 promise 的返回。添加了一个 failedPromise，同样以 beforeUpload prop 传入 wrapper，检查上述两条是否符合预期。由于它是 promise，需要 flushPromises 让 promise 变成结束状态。

有了这两条测试，就可以开始写代码了。

## 实现 beforeUpload

来到代码，我先把代码结构稍稍调整了一下：把上传文件的过程单独放在一个函数 postFile 中，它就是之前那一整套逻辑，把 uploadedFile 传进去完成上传。

先确定 beforeUpload 属性的类型，它应该是一个函数。在最上面添加一个 type，称为 CheckUpload：参数是 file，返回布尔值，或者是 Promise，Promise 的参数也是 file。

写完后把它放到 props 中：beforeUpload，type 是 Function。记得用 as 把它断言成给定的类型，用 PropType 传入泛型 CheckUpload。

然后是判断逻辑，在 postFile 之前进行，此时已经拿到文件了。因为 beforeUpload 是可选的，先判断 props.beforeUpload 是否存在：存在则 `const result = props.beforeUpload(uploadedFile)`；不存在就直接调用 postFile。

result 有两种类型。第一种是 Promise：用 `result instanceof Promise` 判断。是 Promise 就 `result.then()`，拿到处理后的新文件 processedFile，然后调用 postFile(processedFile) 开始真正的上传。再 catch 一下出错的情况，把错误 console 出来。

第二种是布尔值：`else if (result === true)` 时直接 postFile(uploadedFile)。剩下的 result 为 false 的情况什么都不写，直接 return，后面的流程就不会继续了。

保存后运行测试：全部通过。

## 让测试更详细

但是我们的 case 是否详尽呢？failedPromise 只测试了 reject 的情况，resolve 的情况是否详尽？resolve 的时候真正的实现可能有另外一番光景，还需要测试一下。

添加一个 successPromise，resolve 一个 new file，文件名是 new-name.docx，相当于把一个文件转换成了另一个文件。可以继续在同一个 case 里写（不想新开 case 的话）：使用 setProps 重新设置 wrapper 的 props，把 beforeUpload 改成 successPromise，然后 `await` trigger change 让它重新上传。promise 结束后，和之前的测试一样：断言 axios 的 post 已被调用；拿到 first item（li 的第一项），断言上传成功，并且 file name 等于 new-name.docx，也就是转换后的文件。保存运行，测试通过，又多检查了一种用例。

代码是否完备了？我们要求 promise 返回必须是一个 File 对象：successPromise resolve 的是 new File。但如果随便返回一个字符串，应该上传失败，因为我们要处理并上传的是 file。所以再测试这种情况：添加一个 successPromiseWithWrongType，resolve 直接是一个字符串 'abcd'。加注释把三段测试分割开：failedPromise、successPromise with file、successPromise with wrong file。这里同样 setProps、trigger change，期望是 post 没有被调用（not.toHaveBeenCalled）。

结果测试没有通过，测试帮我们找到了第一个问题，说明代码中有缺陷。代码里的 processedFile 并没有判断它是不是一个 File，就直接进行了下一步处理。为了适应这个测试，修改逻辑：判断 processedFile 是否 `instanceof File`，只有是 File 时才进行下一步处理；不是就 throw 一个 error：'beforeUpload promise should return File object'，写清楚一点，大家都知道为什么出错。再补上 post 不被调用的断言，运行后 pass 全部变绿。

从编码过程可以看出测试的好处，再强调一遍：测试写得越详细，就越能发现代码中的问题，这就是测试驱动开发。写测试用例有时比写实现更繁琐，但记住，这样繁琐的过程最终肯定会帮助到你。这节课就是过程的体现：实现只有寥寥几行代码，测试却补充了这么多。这节课到这里，谢谢大家。
