从这节课开始接触新内容：文件上传。这是 Web 应用非常常见的需求，也是必须掌握的内容。之前在开发前端上传组件时从前端角度简单介绍过（第十二周 2-2 小节），淡忘的话可以回看。现在到了后端实现，先温故知新，复习这部分内容，并补充一些和上传相关的新知识。

## enctype 决定数据格式

最重要的知识点：要根据不同的需求选取 form 的 enctype 值。默认值是 `application/x-www-form-urlencoded`，比较长。用人话讲：表单里的数据在传输时会被编码到 body 或 URL 中。

看一个简单的表单例子：有两个 input，一个是 `type="text"`、name 为 textOne，另一个是 `type="file"`、name 为 fileOne。不设置 enctype（用默认值），点击 submit 时发送请求。抓取请求内容：POST 方法，Content-Type 是默认值，Content-Length 是传输大小。关键在这一行，两个值以 key=value 的形式发送：`textOne=textDefault`，不同的值之间用 & 符号连接。

这种方式没法实现文件上传。可以看到 file 类型的 input 被解析成 `fileOne=a.txt`，只包含了文件名，没有包含文件内容。所以要发送大量二进制数据，必须使用 form 的另一种 enctype：`multipart/form-data`。

## multipart/form-data 的请求长什么样

设置 enctype 后再看发送的数据，和之前完全不一样了。Content-Type 变成 `multipart/form-data`，特别注意：满足这个条件的提交，浏览器会自动创建一个 boundary 值，形如一堆中竖线加一串随机数字，它代表一个固定的分割符，是随机生成的。

请求体按这个 boundary 分割成多个部分。第一个分割之后，代表要开始传送一个值：`Content-Disposition: form-data; name="textOne"`，name 和 input 的 name 一样，真正的值换一行写在下面。然后第二个值开始传输，仍用相同的 boundary 分割。

第二个值的 `Content-Disposition` 同样是 form-data、name 等于 fileOne。特别注意：file 类型会多一个 `filename=a.txt`，还多一个 Content-Type，表示文件的类型，这里是 text/plain 普通文本。再往后，value 就映射出 a.txt 里面的内容，一般以二进制文件的格式传输。

两部分传输完毕后，用 boundary 加两个横线的特殊形式表示请求体结束。对比可见，multipart/form-data 发送的数据比默认类型多得多。所以要按需选取正确的 enctype，只有传文件时才应该用 multipart/form-data。

另外，前端一直采用的 JSON 方式在这两者之外：把 Content-Type 设为 `application/json`，直接发送 JSON 数据。它和默认类型很相似，只是格式不同，同样不能发送复杂的文件数据。

## egg 的处理机制

axios 发送的普通文本数据，egg 用 bodyparser 中间件处理。它是一个 koa 的中间件，GitHub 描述是"a body parser for koa, support json, form and text type body"，支持多种普通文本。

解析规则按 Content-Type 判断：为 `application/json` 及一系列 JSON 类型时，按 JSON 格式解析请求 body，把 JSON 值挂到对应的 body 上；为默认的表单类型时，按 form 格式解析，把信息以 key-value 的形式存放到 `ctx.request.body` 上。它的源码值得一看，其实很简单，就是根据不同的格式类型转换成 JSON 对象。

如果要实现 multipart 上传，就要借助另一个内置的 egg 插件 egg-multipart。它的原理之后会详细介绍。看 multipart 的数据格式可以想象：实现过程应该是根据 boundary 把数据分割开来再分类，文件类型就把文件内容写到服务器的某个文件中，普通字符串类型就直接写到 ctx.request.body 里。原理大致如此，内部会有更多逻辑。

这节课把 form 表单提交的两种形式、它们提交的数据格式，以及 egg 用什么机制处理它们一一解释了一遍，让大家有一个初步认识。接下来就可以进入代码，看看文件上传是怎样实现的。
