上节加了整体 loading，现在能知道页面是否有请求在发送。这节更进一步：搞清楚具体是哪个请求在发送，这需要一个特殊的数据结构。最简单的方案是创建一个 object，比如叫 `optNames`：key 是请求名称，值为 true 表示该请求正在进行。数据加载完毕直接删掉 key（`delete optNames.login`）。想判断某个特定请求是否在加载，只需检查对应 key 是否存在，也可以封装成 getter，比如 `state.getters.isUploading('login')` 传进要检查的名称。

## 改造 state 与 mutation

到 `global.ts`，state 里新增 `optNames`，类型是 `{ [key: string]: boolean }`，默认值为空 object。两个 mutation 都加一个可选参数 opName：`startLoading` 里判断 opName 存在时执行 `state.optNames[opName] = true`；`finishLoading` 做相反操作 `delete state.optNames[opName]`。

getter 创建 `isOpLoading`，因为要传参，所以返回一个函数：第一个参数是 state，再返回一个接受 opName（string）的函数，内部 `return state.optNames[opName]`。

## 让拦截器拿到请求名

问题来了：opName 参数怎么传进来？调用这两个 mutation 的地方在 `main.ts` 的拦截器里，而拦截器只能拿到 config；同时使用 actionWrapper 包裹请求后，所有异步逻辑都在那里发起。所以合理的做法是在 actionWrapper 里把请求名写进 config，actionWrapper 已经移到了 `index.ts`，模板等其他异步请求也都用它包裹。

在 actionWrapper 构造 newConfig 时多加一个属性 opName，取什么值？现成的选择就是 commitName，它本来就是 mutation 的名称，语义上正好对应。

但 config 的类型是 `AxiosRequestConfig`，没有 opName 这个属性，点不出来。需要自定义一个类型做交叉扩展，再做类型断言：

```ts
interface ICustomAxiosConfig extends AxiosRequestConfig {
  opName?: string
}
const newConfig = config as ICustomAxiosConfig
newConfig.opName = commitName
```

request 拦截器这边完成后，response 侧做同样的处理。response 对象上带着 config 属性，请求时传的 config 会随响应一起传回来，所以同样能拿到 opName，再做一次类型断言即可。

## 页面验证

到 LoginView 感受效果。创建变量 `isLoginLoading`，调用 getters 的 isOpLoading 并传入 'login'，这个键与 login action 的名称完全一致；然后把返回值绑到登录 AButton 的 loading 属性上，AButton 原生支持这个属性，loading 为 true 时按钮会出现转圈效果。

测试：获取验证码、填入后点击登录，登录按钮出现转圈状态，随后跳转到首页，功能实现。再到 HomeView 验证另一处：添加 isLoading，取 fetchTemplates 是否在 loading，页面上显示一行大字，刷新页面能看到 "template is loading" 出现。

两个页面都能用 isOpLoading 拿到非常精确的 loading 状态。至此全局 loading 全部完成：既有"是否正在 loading"的笼统全局状态，也有"具体哪个请求在 loading"的精细局部状态。
