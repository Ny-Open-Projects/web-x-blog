这节课继续进行优化。前面我们一直针对的是由第三方脚本组成的 chunk-vendors.js 进行优化，它的体积已经大幅下降，从最初的 2.25MB 下降到了 1.26MB，这是一个伟大的成果。但还不满足，我们希望从另外一个维度来优化。

## 为什么要拆分 vendors

Vue CLI 在打包时，webpack 配置已经默认使用了 Code Split：将应用的主要代码和 chunk-vendors（第三方库的一系列代码）打成了两个文件。为什么这么做？都是从浏览器缓存考虑的。那么对于第三方库，我们是否要将一个大的 vendors 文件，按照第三方库继续拆分成更多比较小的文件呢？这样做有什么好处？

举一个非常形象的例子。假设我们的应用有一系列 JS 文件：主程序 App 占 250KB，两个依赖 Vue 和 jQuery 分别是 150KB 和 100KB，加起来 500KB。有一个用户从周一到周四每天访问我们的网站，看一下总共耗费多少流量（当然越少越好）。

方案一：只有一个文件，三个库都打包到 main.js 中，大小 500KB。周一第一次访问，花费 500KB；周二没有任何新功能上线，可以享受浏览器缓存，零 KB；周三我们对 App 做了一个简单修改，main.js 的哈希值发生了改变，要重新下载，500KB；周四我们对第三方库进行修改，添加一个 100KB 的 lodash，新的 main.js 又被打包生成，变成 600KB，发生修改就要重新下载，耗费 600KB。加起来是 1600KB，这当然是一个很不好的设计方案。

方案二：两个文件，App 主程序一个文件，vendors 另外一个文件。周一样样都要下载，500KB；周二零 KB；周三只有 App 更新了，只需下载它，节省了一半空间，250KB；周四第三方库 vendors 发生了更新，从 250KB 变成 350KB，耗费 350KB。加起来是 1100KB，比原来有所下降。

方案三：继续拆分下去，250KB 的 App、Vue 和 jQuery 分别打成 150KB 和 100KB 的文件。周一样样都要下载；周二零 KB；周三只有 App 更新，下载 250KB；周四添加了新的第三方库 lodash（100KB），已有的三个文件都没有发生变化，都不用下载，只要重新下载新的 100KB 文件。总计耗费 850KB。

从这个例子可以看出：部分的修改意味着重新下载所有的文件，而我们的修改方案正好反其道而行。将一个比较大的第三方库拆分成几个小的文件，对于以后的更新大有裨益，可以充分享受浏览器的缓存。

## 第二个优点：并行加载

第二个优点是：浏览器天生支持平行加载多个文件，将大的文件分割成小的文件，比大文件有更快的加载速度。很多同学可能都知道，传说中浏览器对同一个域名有最多的并行加载个数限制。我看到一个帖子，它说针对不同协议有不同的处理：HTTP 1.1 时不同浏览器有限制，对 Chrome 来说是 6。

做一个形象的实验。test 文件里有一系列脚本：一组来自一个很老旧、几乎已经不维护的服务，也就是新浪的 App Engine（SAE），这些都是很老旧的第三方库，采用的是 HTTP 1.1 协议。打开 Network 面板刷新一下，可以清楚地看到：前面几个加载得比较快，到后面的文件，灰色的一段都非常非常长。灰色代表它是在等待阶段，等待说明前面已经被完全占用满了，前面的文件已经达到了六七个，也就是达到了上限，所以它必须等待这些都加载完，再重新建立连接下载。这就是 HTTP 1.1 的弊端。

再看 HTTP 2 解决了怎样的问题。把刚才的脚本注释掉，打开 CDNJS 也就是 Cloudflare 的一系列 CDN，刷新。可以看到一瞬间它们都完成了加载，并且是齐头并进的：虽然有七八个文件，但没有因为连接限制而进行过长的等待，而是一起完成了加载。文档也是这么说的：HTTP 1.1 有这样的限制，到 HTTP 2 这个限制就完全不存在了，one single TCP connection for all requests，一个 TCP connection 处理所有的请求。

还可以看到它的 protocol 使用的是 h3-29，这是最新的 HTTP 3 协议，所以 Cloudflare 这个 CDN 做得非常好，采用的技术也很新。

所以在现代浏览器和 HTTP 2 普及的时代，并发数量的限制已经不是瓶颈了，将一个大的第三方文件分割成多个是有现实意义的。下节课我们来看 Webpack 的一个内置插件 SplitChunksPlugin，怎样来完成这个任务。
