这节课到界面上测试 undo/redo 的效果。单元测试这边，我把最常用的三个断言封装成了三个函数：获取 components 的 length、拿到最后一项并判断 id 是否等于目标 id、拿到当前元素并判断它的 text。测试用例立刻变得非常简约。把 redo 的测试也补上之后，全部通过。

有了这层保证，再到界面上测。

## 界面搭建

界面需要一个撤销按钮和一个重做按钮。我新建了一个 `HistoryArea` 组件来放这两个按钮：用 `a-tooltip` 和 `a-button` 配合 undo 和 redo 两个图标，点击时分别 `store.commit('undo')` 和 `store.commit('redo')`。

因为这个组件会调用 store 的方法、又属于 Editor 的一部分，我把它放到了 views 下单独的 Editor 子文件夹，和 Editor 相关的 view 都收在这里，管理起来更方便。你也可以直接写进 editor.vue，效果一样。

为了方便调试，组件里还会循环输出一个历史记录列表（`li v-for="(item, index) in histories"`），并判断 `index` 是否等于当前的 `historyIndex`，相等就显示为粗体。这样能直观看到接口里有多少条数据、当前走到了哪条。界面测试时把数据简单可视化是调试的重要手段，比 console.log 更直观，一会儿大家就能体会到好处。

## 按钮 disabled 状态

界面上两个按钮一开始都是可点击的，这不符合需求，特定条件下它们应该是 disabled 的，比如没有历史记录时。这两个状态要从 store 派生，加到 editor.ts 的 getters 里。

第一个 getter `checkUndoDisable`，undo 应该禁用的条件有两个：一是没有任何历史记录（no history item）；二是已经走到最前面，不能再往前回退（move to the first item）：

```ts
checkUndoDisable(state) {
  const { histories, historyIndex } = state
  if (histories.length === 0 || historyIndex <= 0) {
    return true
  }
  return false
}
```

第二个 getter `checkRedoDisable`，条件类似但有差异：没有历史记录一条相同；第二条是走到了最后一项（move to the last）。另外还有一个容易想不到的条件：从来没有 undo 过（never undo before，`historyIndex === -1`），这时 redo 肯定不能点，要多加这条判断。

注意 redo 的实现里 `historyIndex++` 是在操作之后做的，和 undo 的先减减不同，所以判断最后一项时要往后看一项。把两个 getter 拿到 `HistoryArea` 中，新建两个 computed，`undoDisabled` 和 `redoDisabled`，手动指定为布尔类型（getters 返回默认是 any）。按钮的 `disabled` 属性分别绑上去。

再上界面：没有任何操作时两个按钮都是禁用状态。按测试用例同样的规则操作一遍：添加大标题、删掉、再更新一个值（fontSize 改成 bold），出现三条历史记录 add、delete、modify。点回滚逐条撤销，回退到 add 时对应记录被删除，回到最初 index 后按钮自动 disable。再测重做，逐条恢复：add 恢复组件、delete 执行删除、modify 切回 bold，全程没问题。

## 发现的五个可优化点

多操作几次就暴露出问题了。以下是我试用后发现的可优化点：

1. **拖动会写入多条记录**：拖动一次元素，会 modify 两条（left 和 top），放大后再拖甚至写入四条，回滚时一条一条滚。我们希望一次操作只产生一条记录。
2. **快速修改文本会保存多条记录**：在文本框里快速改动（比如把 hello 改成 sdf），会写入多条记录。希望快速修改只保存一条，回滚时一次回到最初位置。
3. **回滚中途继续编辑的处理不对**：回滚到中间某个状态后继续修改，新记录直接追加在 history 末尾。实际上回滚点之后的历史记录应该被清掉，新操作从当前指针位置开始。
4. **页面设置没有历史记录**：修改页面背景颜色、高度、上传图片等操作，完全没有产生历史记录，也应该纳入。
5. **历史记录没有上限**：可以无限保存，需要设置一个保存的最大条目数。

这几个问题不是代码 bug，而是从易用性角度出发的优化，想把撤销重做做得更好用、更完美，就要解决它们。下节课着手解决。
