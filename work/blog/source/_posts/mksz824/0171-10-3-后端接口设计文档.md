上节课完成了需求分析，这节课的任务是把需求转化为接口。后端接口比较明晰，和需求几乎一一对应。

在提取接口之前先明确一点：项目开始时我们已经确定了使用前后端分离开发的架构体系，后端以 RESTful API 的形式给前端提供接口，这样双方可以并行开发，大大提高开发效率。RESTful API 大家多少都有了解，这里不展开详细解释。

完成接口文档的第一步，是把之前分析出来的需求创建一个文档粘贴进去，然后对接口进行一一设计。设计过程中主要聚焦 RESTful 的几大特性。第一是路径，也叫 endpoint，表示 API 的具体网址。在 RESTful 架构中每个网址代表一种资源，比如我们写 `/works`，这个网址就代表一种资源，正好可以和需求分类的几种实体对应，比如 users、works、templates 等等。

第二个特性是 verb，动词，表示对资源的具体操作类型，由 HTTP 动词表示。常见的动词有五种：get、post、put、patch、delete，对应增删改查。特别注意这里有 put 和 patch 两种更新方式，它们的区别是什么是面试常问的问题，课下要搞清楚。在我们这里，更新都使用 patch 方法。

有了这两个原则，就可以设计接口了。比如创建一个空白作品，自然是使用 post 方法，endpoint 写 `/works`，这样一个 endpoint 就设计完成了。还有一个相同功能不同途径的实现方式：可以在资源后面再加一个动词加以区分。比如登录有邮箱密码登录，我们写 `post /users/loginByEmail`，实体名称 users 加一个动词 loginByEmail，很清楚地说了要使用邮箱密码登录。手机验证码登录方式也是 post，写 `users/loginByPhoneNumber`，这样就做了区分。

第三个特性是 RESTful API 可以通过参数的形式完成信息的过滤，这在展示信息列表的时候非常常用。文档上说的是：假如数量众多，服务器不可能将所有结果都返回给用户，API 可以提供参数过滤返回结果，比如 `limit=10`、`offset=10`。对应到我们的需求：查询自己的作品列表，实体是 works，自然是 get 方法，加参数。比如搜索的名称，我们称之为 `title=xxx`；还有分页：第几页用 pageIndex 表示，等于 0 就是第一页；每页多少用 pageSize 表示，等于 5。这样作品列表的过滤过程就完成了。剩下的接口都大同小异，大家可以自己完成。

还需要明确一个信息：请求参数。刚才介绍了可以在 query 中发送参数，但很多情况下参数是放在 body 中传递复杂信息的，是 JSON 格式。不过现在考虑请求参数为时尚早，有些字段可能和数据库设计的字段相关，可以在实现具体接口的时候再补充。这些信息甚至不需要手动编写，可以通过 Swagger 等自动化工具生成。

说完请求参数，最后相对应的自然是返回格式。对于返回格式，除了数据本身，还需要一些特殊信息来表示请求的状态。大家肯定会想到 HTTP 状态码，二百、三百、四百、五百这一系列，这是基础知识，含义可以自行查阅文档。为了让错误更加明晰，我们还需要加入一个错误码信息，用一个特殊字段告诉用户到底出现了什么错误。这里我们采用一个数字，称之为 errorNumber：0 代表没有错误，其他数字各有含义，可以在编码时进行设计。去查看任何一个比较出名的 Open API 的设计，都能看到类似的错误码。比如微信支付的设计，文档里有错误码说明，它使用字符串来表示，其实跟我们的数字是同一个意思。

于是可以得出一个通用的返回格式：errorNumber 代表错误码，表示成功或失败；data 包括真正需要返回的信息，可以是数组或者普通 object；最后还有一个 message，是具体的报错信息。经过这个过程，我们就可以得到后端接口的设计文档。我最终设计生成的文档里有一系列的接口设计，最后还有统一的返回格式，我把不同的实体做了分类，大家可以对应参考。

特别注意，这个接口设计文档完全是以开发为目的的，是为自己后面开发时梳理思路用的，还没达到给前端人员使用或者公开成为 Open API 的程度。开发过程中我们会不断丰富这个文档。最后的成果不仅会有自动生成的 API 文档，比如微信支付那种，还要有提供给开发者可以直接调用的 Postman 文件。有 Postman 就方便很多：我最终生成的一系列 Postman 文件，把不同的实体分类，每个接口的参数、headers 有什么、body 有什么、返回应该是什么样，都写得很清楚，开发者一看就明白。

我们目前的任务已经达成：根据需求梳理出要完成的接口文档列表。有了这个列表作为指导，就可以把文档作为开发的纲领开始开发了。希望大家课后也根据这个指导思想生成一个自己的接口设计文档。
