上节课简介了 ESLint 的功能和相关编辑器插件的安装，现在深入到 ESLint 配置内部，看看它是怎样组织验证选项的。ESLint 默认不包含任何规则，行为完全由一个配置文件控制。这个配置文件在项目根目录下，叫 .eslintrc.js，也可以写成 JSON 格式。

配置文件里有一系列选项。其中三项不是很重要，也很好理解：root、env 和 parserOptions，可以去文档里自己了解。要特别掌握的是另外两个。第一个是 rules，从名字就能看出是规则。可以在 rules 这个 object 里添加一系列单条规则，内置规则可以到 ESLint 官网的 rules 页面查看，默认的规则非常多，每一条对应不同的规则。

现在添加一条必须加分号的规则。找到它的名称 semi（就是分号），在 rules 里新建一项 semi。规则有三个等级：0 代表关闭，1 代表 warning 输出警告但不是错误，2 代表错误。先改成 1，回到 App.vue，没加分号的地方都变成黄色预警，是 Warning 但不是错误；改成 2，它就变成错误，告诉你这里有问题。除了用数字，也可以用三个字母的单词：off 是关闭，warn 等于 1，error 等于 2，换成 error 效果一样。

一个 rule 在某些情况下还有配置选项。拿分号来说，可以选择"必须加"，也可以选择"必须不加"，而"不加"这个分支同样有三种选项：必须加、必须不加、加不加都无所谓。文档里对应 string option：always 表示必须加（默认值），never 表示不加。可以用数组形式配置：数组第一项是等级，第二项是配置。把 error 变成数组 `["error", "never"]`，再看效果，错误换了个位置：因为这行代码加了分号，而现在的规则是必须不加，所以在这里报错。这样分号规则就确定了。

但我们发现还有很多格式需要讨论：单引号还是双引号、Tab 还是空格等等。于是陷入沉思：不可能针对每种格式都和大家讨论决定。打开 Google 一搜，发现很多公司都有一样的问题，于是不少大公司提出了自己的一套标准，经过讨论公开了一系列规则，作为一组供大家直接用到自己的项目里。这就是 extends 字段。它是一个数组，数组里的每一项就是一组规则。比如其中的 vue/essential，来自 eslint-plugin-vue，是一系列规则的合体。到 eslint-plugin-vue 官网可以看到它的所有规则，点进每一项还有详细说明。

比如其中一条规则：不能在正常的 HTML 元素上使用 is 特性，只能用在自定义 component 上。我们实际测试一下，给 h1 上面加一个 is，立刻报错了，错误信息正好对应这条规则，说明这一组规则已经加载成功。所以 extends 就是把知名组织整理好的规则合集拿来就用，不用自己一条一条规定。

介绍完配置文件，再说说出现错误后有没有自动解决的办法。ESLint 在命令行中有一个 --fix 选项，可以帮我们自动完成修改。VS Code 里同样可以通过运行命令来完成：比如文件里有几个错误，想自动修复时，按住 Command Shift P 弹出命令窗口，输入 ESLint，出现所有 ESLint 相关的选项，选 Fix All Auto-fixable Problems（自动修复所有可修复问题），回车之后错误就被修复了。也可以给这个操作绑定一个快捷键，比较好用。

除了用命令，还可以在配置文件里写入一项配置，让每次保存时自动修正。打开之前说过的 settings.json，所有编辑器配置都可以写在这里。之前我们添加过 eslint.validate，给 TypeScript 文件加上了 ESLint 验证；现在添加另一个选项 editor.codeActionsOnSave，让保存的时候执行 source.fixAll.eslint。配置好后，文件里有两个错误，按 Command S 保存，神奇的事情发生了：保存的瞬间两个错误就消失了。但注意，不是每一个错误都有对应的修复规则，比如上面那个 is 的问题就没有修复规则，所以它仍然留在那里。

对于自动修复功能，我本人一般不添加，更希望靠自己养成符合规范的写法，不过大家可以按自己的喜好决定。这节课到这里。这节课学习了 ESLint 配置文件的内容，并给编辑器添加了自动修复代码的功能。谢谢大家。
