这节课继续改造上节课完成的中间件。上节课我们用了多种方式完成类似中间件的需求，到后来它已经不是中间件了，只是一个普通函数。所以不需要特别拘泥于概念，可以用多种方式完成任务。这节课再接触一种新方式，同时学习一个新概念。

之前讲过 Nuxt 有一系列特殊文件夹，比如 components 和 composables，它们共同的特点是 auto-imports：在里面写的组件或函数都会被自动导入、直接使用。其实还有一个特殊文件夹叫 utils，同样支持自动导入，里面一般放置各种帮助函数。它和 composables 的区别在于：utils 放的是和 Vue 3 响应式数据无关的普通函数，composables 放的是组合式函数。

server 端也支持这个特性：在 server 文件夹下新建 utils 文件夹（注意名字不要写错），里面的文件同样会被自动导入。于是想到一个最简单的方法：定义一个高阶函数。我们之前一直使用 defineEventHandler 来生成 event handler，它的返回就是一个普通的 event handler 类型。所以可以定义一个高阶函数，把其中的 handler 作为参数传进来，返回一个新的 defineEventHandler，并在前后做一系列想要的操作，从而实现比 middleware 更灵活的方案：可以在响应的前后都添加额外处理，还不需经过一次导入来处理。

在 server/utils 下创建函数。注意 utils 下面接受两种命名：named export（具名导出）和 default export。区别是具名导出可以直接使用函数名，默认导出的函数名跟文件名相关。这里采用第一种：

```ts
export const defineAuthResponseHandler = (handler: EventHandler) => {
  return defineEventHandler(async (event) => {
    // before the route handler
    const response = await handler(event)
    // after the route handler
    return response
  })
}
```

参数 handler 是用户想要的最终处理逻辑，类型使用 H3 提供的 EventHandler。函数返回一个 defineEventHandler 的调用，通过这种方式就能返回一个和直接用 defineEventHandler 完全一样的结果。它的参数同样是 event，在里面先 `await handler(event)`（handler 基于 Promise），把返回值接住并 return 出去，原始逻辑就完整保留了下来。

关键是这个结构：在调用 handler 之前的位置可以放 before the route handler 的逻辑，在之后可以放 after the route handler 的逻辑。上节课的鉴权逻辑是在调用前处理的，直接把原来的判断复制到这里即可。想复用的逻辑就写在 handler 之前，想在响应之后处理的写在后面。这个写法比较难理解的地方就是"传入一个函数，返回 defineEventHandler 并让 handler 运行"，本质上就是一个高阶函数。

升级版写好之后，使用起来非常简单：把原来代码里那些零碎的东西都删掉，只需把函数名从 defineEventHandler 换成 defineAuthResponseHandler，它就会在前后加上我们想要的鉴权处理。

保存后验证：刷新 users/1，显示出 401；而其他普通 URL 不受影响。把假数据里的 isLogin 改成 true，再访问受保护的路由，就能直接拿到后面的响应。整个开发过程完成。

这种方式有点像我们在 Nest.js 中重度使用的 decorator（装饰器），但相比之下好懂很多。如果你要在请求前后重复添加一些逻辑，比如鉴权验证，使用这种方式不失为一种很棒的手段。

这节课的任务完成了：又用一种新方式完成了 AuthHandler 的编写，同时了解到 utils 文件夹的特性，它在 server 端和前端都可以被自动导入。
