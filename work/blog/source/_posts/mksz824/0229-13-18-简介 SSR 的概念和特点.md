这节课进入新内容：在后端渲染前端特定的作品。先看对应的接口：展示 H5 页面。访问这个接口时，应该展示出我们在编辑器里创建的页面。接口的参数是 id 和 uuid，通过这两个参数从数据库拿到对应的数据，再用数据里的作品信息渲染出特定页面。

## 数据结构

先观测一下数据结构。从数据中取出的 content 是最重要的，我们需要的信息都在里面，可以帮我们完成渲染。它包含两部分信息：第一部分是页面上各种各样的元素，称为 components，其中 name 是组件的名称，props 是一系列对应的属性；除 components 外，还有一个通用的 props 属性，代表整个页面的一系列 CSS 属性，目前有 backgroundColor、backgroundImage 等背景相关的属性。

## 用什么渲染

用什么渲染这个问题之前已经多次解释过，我们早就未雨绸缪：一个通用组件库在前面阶段就建立好了。之前分析过，创建的 OpsFlow 组件库可以供 B 端编辑器和 H5 端共同使用。

特别说明一下：之前那个库叫 OpsFlow 组件库，这里又新建了一个库，也叫 OpsFlow 组件库。两个库基本一样，区别是新库多了一个组件，叫 FinalPage。这个 FinalPage 用于直接渲染出编辑器中页面的最终效果。它接受一个属性 components，就是页面上一个个组件的配置，和数据里的内容完全一致。传入后它就会渲染出对应的页面。

同学们可以直接使用这个组件库，也可以在原有组件库的基础上新建一个简单的 FinalPage 组件。它做的任务很简单：循环传入的数组，拿到每一项的 name（组件名称）和 props，循环渲染就可以了。

## 怎么渲染：SPA vs 后端渲染

解决了"用什么渲染"，最重要的是"怎么渲染"。讲这个之前要先分清前端和后端不同的渲染方式和需求。

前端我们都知道是 SPA 应用：运行对应的 JavaScript 代码，把 Vue 的实例渲染到 DOM 节点上。后端当然也可以用这种方式，但有一个重大区别：后端只是简单展示页面，页面就是一个静态的 HTML，没有任何交互。所以不应该使用比较重的 SPA，而应该直接生成对应的字符串，通过 ctx.render 直接渲染页面，这是最简单也是最好的方式。

于是问题变成：怎样把组件数据在后端渲染并生成字符串？这就是一个新话题：SSR，全称 Server Side Rendering，服务器端渲染。Vue 有专门的章节介绍服务器端渲染，这里简单总结一下它的优缺点。

## SSR 的优点

第一，更好的 SEO。搜索引擎的 SEO 是通过爬虫对渲染后的页面进行爬取的。前端如果用 SPA，页面里只有 JavaScript 代码，DOM 节点在 JS 运行之前完全为空，对 SEO 不利。后端直接渲染字符串、直接生成 HTML 模板数据，对 SEO 更好。

第二，更快的渲染时间，也叫 Time to Content。SPA 的渲染方式需要等待所有 JavaScript 完成下载并执行后才能显示页面；SSR 不需要 JS 运行的过程，直接展示数据和页面，可能更快。

## SSR 的缺点

第一，开发的限制。很多 Vue 生态的库都和浏览器相关操作有关，可能遇到不兼容，浏览器相关的操作有可能只能在特定的钩子函数中运行。

第二，部署更复杂。SPA 应用是完全静态化的，最终打包出来就是几个静态 JS 文件，放在哪里都可以；而 SSR 应用需要特定的 Node.js server 才可以运行，配置和部署要更复杂一点。

第三，占用更多服务器端负载。Node.js 需要渲染完整的应用程序，显然会比仅提供静态文件的 server 占用更多的 CPU 资源，要做好这方面的准备。

所以使用 SSR 之前要问自己的第一个问题就是：我们是否真的需要它？取决于 SEO 和 Time to Content 对你的应用有多大的需求。根据不同的需求选择最佳的方法和工具，是重要的考量元素。

## 实现方式

SSR 的实现基本原理文档里都有：它来自 Vue 旗下的一个叫 server-renderer 的库，提供一系列方法帮我们完成任务。之后我们会使用 createSSRApp（注意是 SSR App），配合 renderToString 或 renderToStream，把对应的组件直接渲染成字符串或流。基本原理就是这些，非常重要，下节课会简介。

关于 SSR 实现还想提一个话题：Vue 和 React 都有针对 SSR 的"大而全"的通用开发框架，Vue 的叫 Nuxt.js，React 的叫 Next.js，很多同学都听过。特别注意：虽然它们号称 SSR 框架，但我更愿意称之为通用框架，它们的功能远不止 SSR。简单浏览一下文档就会发现各种功能，Rendering Mode（也就是 SSR）只是其中一个小功能。这类框架的目的是做一个大而全、同时适配前端和后端的通用框架，感兴趣可以去深入了解。

但我们这里不会选用这类框架，因为任务很明确：只在服务器端渲染成对应的 HTML 字符串，不需要那么多功能。按照最小化原则，切记选择适合自己需求的工具，不要杀鸡焉用牛刀。
