这节课我们将定义的不同角色权限添加到对应的代码中。这个逻辑应该放在哪个位置呢？最好在一个统一的地方一劳永逸地添加，不用在每个 controller 中填写重复的逻辑。我能想到两个地点：一个是 middleware 中间件，另一个是 decorator 装饰器。

我觉得装饰器是更好的选项。第一，装饰器可以添加多个参数，比较方便；第二，调用起来很明晰，在哪使用就在哪调用，代码更容易读懂。所以我们的任务是来到 checkPermission 这个装饰器，在这里完成改造。

先看之前的逻辑：获得当前 user 的 id，然后使用 params 上的 id 进行查询，判断两者是否相等。假如改成对应的权限判断，这些逻辑都不复存在了。来看改造需要什么信息。回顾之前学的 roles 定义：第一个需要 user，也就是获得当前用户。这个是有的，可以在 ctx.state.user 中获得，没问题。第二个需要实体信息，也就是你在操作哪个实体。checkPermission 中已经有了对应的 modelName，它跟 MongoDB 对应的 model 正好一一对应，也不成问题。第三个需要执行什么样的操作，也就是 action，我们定义的是 read、update、create 和 delete。

观察发现，这个操作跟 HTTP verb 是一一对应的：router 中的 POST、GET、PATCH、DELETE 当然都有（可能还有更多，特殊的情况之后再讲解），所以可以先做一一对应。这样我们不需要传入任何参数，直接从 ctx 上获取对应的 HTTP 操作方法即可。

这里特别说明一点，还有一个特殊的实体 channel。channel 的操作暂且不管，因为它很特殊：它的 model 名称虽然是 channel，但我们操作它应该在 work 上获取对应的信息，因为它是属于 work 的。

动手改造。第一步把定义好的 roles 拿过来：import defineRoles from 上一级的 roles。然后创建一个 mapping，把 HTTP 方法跟 rules 里对应的 action 一一对应。我称之为 caslMethodMapping，类型是 Record<string, string>，key 和 value 都是 string。写的时候注意 HTTP verb 是大写的：GET 对应 read，其他的照着对应关系写就好。

有了对应关系就可以在装饰器里操作了。第一步拿到 method，来自 ctx.request.method。有了 method 就能拿到对应的 action：action = caslMethodMapping[method]。拿到 action 后做一个特殊状态的判断：假如没有 ctx.state.user，其实是进行不下去的，直接抛出异常即可，这里只要判断一下就行。

预先的情况处理完毕，接下来定义 ability：const ability = defineRoles(ctx.state.user)，把 user 传进去，就获得了 ability。然后按照之前学的规则继续。

这里特别注意有一个条件分支。rules 中有一些 condition，比如 work 只有本人才能读取，这涉及到一次查询。所以要先获得 rule 来判断一下它是否存在对应的 condition：有 condition 就要做一次查询，没有就可以直接判断。这里有一个特殊的方法：ability 上的 relevantRuleFor，它接收两个参数，第一个是 action（哪个操作），第二个是实体 modelName。拿到 rule 后就可以用它判断：假如 rule 存在，并且 rule 上面有 conditions（rule 对象上有一系列属性和方法，conditions 对应的就是我们设置的一系列条件），那就需要进行一次查询。加一个注释让大家看清楚一些。

查询可以叫 certainRecord，await ctx.model[modelName].findOne(...)，并且调用 .lean() 把它转换成一个普通的 JavaScript object。再加一个注释：假如存在 condition，就进行查询获取对应的数据。

有了数据以后，就可以获得最后的 permission（true 或 false）。因为这里有个 if else，在外层先定义 permission 等于 false，然后分别取得结果。permission = ability.can(action, subject(modelName, certainRecord))。这里要注意，我们要跟对应的实体进行对应：之前可以直接根据 constructor 的 name 来对应，这里要手动完成对应。CASL 提供了一个内置的方法，从 @casl/ability 导入一个叫 subject 的 function 来完成对应：第一个参数是 model 的名称 modelName，第二个参数是查询到的 object，也就是 certainRecord。这样就完成了绑定。

当然还有一种情况不需要查询，比如 create work。放在 else 里，很简单：permission = ability.can(action, modelName)。

完成以后，后面原来那一长串判断就都可以注释删掉了，直接判断有没有 permission 就可以。再看一遍代码加深印象，特别是新的内容：先获得 rule，rule 是定义的一系列对象，看它有没有 condition；有对应的 condition 就进行一次查询，把查询的对象和 modelName 用 subject function 绑定；没有的话直接调用 ability.can(action, modelName)。

保存后打印几个值验证结果：打印 permission，再打印 rule，前面加个前缀看得更清楚。测试一下方法是否好用。controller 中不需要替换任何参数，因为装饰器的参数跟现有完全吻合。

第一个测试 work 的获取，这个只能获取本人的作品。先 loginByEmail 拿 token，复制下来，到 get single work 里把 token 贴上。现在拿的是 32 这个作品，不属于这个作者，应该返回没有权限。点击 send，确实显示没有权限。看输出：permission 是 false，rule 里面有一系列定义好的内容，action 和 subject 是我们最关心的，这里出现了对应的 conditions，这正是要满足的条件，它不满足，所以结果是 false。

再看一个满足的条件：换成 30，点击 send，返回了对应的作品，permission 变成了 true，condition 跟刚才一样。

这样这部分编码就完成了。当然我们只判断了 rule 上的 conditions，还有一个特殊情况：还有一系列的 body 值。所以下节课要判断这些 body 值是否在约定的数据范围之内。
