上节课讲到过组件和模块的发展历程：之前使用的是全局 namespace 的挂载方式，随着 AMD、CommonJS、ES6 Modules 的陆续出现，模块化开发有了更多的实践。由于浏览器环境的特殊性，ES6 Modules 中 import export 这种同步加载的方式无法在大多数浏览器中直接使用。所以工程师们又想了一些办法，一些工具的出现改变了这种现状：它们将浏览器不支持的模块进行编译、转换、合并，最后生成可以在浏览器端良好运行的代码。这种工具我们称为 Bundler，打包工具。

Bundler 是社区产物，自然呈现出百花齐放的景象。首先说说所有人都清楚或听说过的 Webpack。我相信所有前端工程师就算没有用到过，也肯定听说过。它是 create-react-app 和 vue-cli 这类脚手架工具内部的工具。从官网的这张图可以看到，它允许我们将各种类型的资源视作与 JavaScript 平等的模块，以一致的方式加载进来。我们的组件所有依赖都可以在自己的实现中声明，对外只暴露出一个 JavaScript 模块作为入口，这是一种单 JavaScript 入口文件的模式，也是目前较为主流的前端组件化方案。对我们的应用而言，比如 OpsFlow 的 B 端应用，它的入口文件就是之前说的 main.js，就是单 JavaScript 入口文件。

Webpack 构建的产物是什么呢？做一个最简单的实验看一下。我创建了一个最简单的项目，有两个文件：main.js 是入口文件，hello.js 是另一个模块，使用 export 导出两个 function。main 中 import 它们并调用，最终效果是在 root 节点中把 innerHTML 改成 hello 返回的值，也就是 hello Viking。然后把这个 js 资源直接引入 index.html，看看会怎么样。当然是直接报错：cannot use import statement outside a module，浏览器没法直接使用。

这时候用 Webpack 来帮个忙。它是一个命令行工具，我们已经安装了 webpack，直接输入 `npm webpack`，第一个参数是你想打包的入口文件 main.js，这样就够了。运行后它会生成一个 dist 文件夹下的同名文件，里面是压缩以后的代码，格式被混淆了，有点看不懂。现在把它引入 index.html，地址改成 ./dist/main.js，保存刷新，代码就能良好地运作了。

现在至少清楚了一件事：Webpack 帮我们做了一些事情，它分析得到所有必须的模块，提供让这些模块有序正常执行的环境，最终生成的文件可以良好地在浏览器中执行。我们在开发阶段就可以轻松惬意地使用 ES6 modules。它还有很多高级功能，比如加载多种文件类型、代码分割、Tree Shaking 等，之后会讲。只要记住一个基本规律：有了 bundler，我们就可以直接使用 ES6 模块系统来开发项目。这就是所有 bundler 的基本工作原理。

当然，还包括接下来要使用的打包组件库的工具 Rollup。它完成的任务和 Webpack 是一样的，是另外一个打包工具。概念之后要用的时候再简介，这里先在本地试一试。两者在使用上有一些明显的差别：同样是命令行工具，可以在本地安装。安装完毕后运行命令，看看它生成什么样的代码。在项目根目录输入 `npx rollup main.js --file dist/bundle.js --format iife`，main.js 是入口文件，--file 指定输出文件为 dist/bundle.js，最后一个参数可加可不加，指定生成什么格式的代码。这里输入 iife，上节课讲过，iife 是自执行函数，更适合浏览器使用，可以防止全局变量污染。

运行后生成了文件，cat 一下 dist/bundle.js 看看生成的代码：它比 Webpack 生成的代码清晰易懂很多。首先可以看到，它把 hello 的实现单独取出来放在前面，后面是 main.js 真正的实现，然后用一个自执行函数把整体包裹起来，防止全局变量污染。现在把它替换到 index.html 里，地址改成 bundle.js，保存查看，自然而然可以良好运作。

不难看出，各种 Bundler 虽然有不同的用法和 API，但本质应该都是一样的：帮我们处理 ES6 的模块代码，生成浏览器可以直接运行的格式的文件。这节课就先讲到这里。下节课我们来看一看 Webpack 和 Rollup 的几个特点，以及为什么选择 Rollup 当作我们的组件库打包工具。到这里，谢谢大家，再见。
