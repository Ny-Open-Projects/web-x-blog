到目前为止，我们能够成功地将应用部署到服务器中并运行起来。但这不是我们最终的解决方案，而是一个传统后端部署的解决方案。如果你部署的是一个小型项目，比如个人学习项目、小公司的项目，这样做完全可以胜任。但我们还是不难发现，这种方式有可能遇到几个比较棘手的问题，需要在后面的内容中找一个更好的解决方案。

首先梳理一下本章传统部署学到的大体内容。一开始我们讲了 egg 针对开发环境以及生产环境启动应用的不同方式，基本就是使用不同的脚本完成启动以及停止，为不同的目的服务。开发环境我们都知道使用的是 egg-bin，它会自动 watch 文件的改变，有对应的修改时会重启服务器。而生产环境我们使用的是 egg-script，内部大家都知道了，依赖的是 egg-cluster。

提到 cluster，我们学习了 Node.js cluster 的简单使用以及原理。大家在基础课程中一般不会接触到 cluster，但在生产上它非常有用。根据这个原理我们了解到，egg-script 启动的时候会启动多个进程：第一个是一个 master 进程，类似于我们说的 PM2 这样的守护工具，管理其他进程的启动、关闭以及相互通信；然后有一个 agent 进程，agent 作为 master 的秘书，会协调处理一些后台任务，比如命令或指派只需要一个 worker 处理的特殊任务；最后还有和 CPU 核数一样的 worker 进程，它们是真正运行对应业务代码的一系列进程。

了解了 cluster 启动的原理以后，我们来到了要部署到的位置，也就是云服务器。它是抛开本机以外的另外一个实体机器。首先我们简单调研了目前国内比较大的云服务器商，发现很多云服务器商都有对应的 promotion 或者叫优惠，价格一年还是比较低廉的，推荐大家去购买一个。然后针对一个新的 Linux 机器，为了保证安全，它有一些必要的配置，我们完成了对应的配置：第一步创建一个新用户，然后给新用户赋予 sudo 权限，因为它有时候还是要切换到 sudo 去完成对应的操作；接着禁止 root 登录，保护服务器的安全；最后使用 SSH key 免密登录，你也可以设置直接禁止使用密码登录等一系列配置。

之后我们在服务器中安装了一些运行必备的软件，比如 Node.js、MongoDB、Redis 等等。然后代码针对生产环境做了对应的配置修改。最后在服务器端完成了部署，并且将应用成功地运行起来。

这就是本章大体的知识脉络。在这个过程中，我们会发现有几个问题很棘手。

第一个问题是前置软件的安装。刚才说的 Node.js、MongoDB 和 Redis，假如应用要启动，这几个软件是必须被安装的。它们在不同的操作系统中有着不同的安装方式、启动脚本或者预设初始的方式，有可能都不相同。这就给我们造成了很大的困扰：假如需要在多台机器上部署，可能会遇到各种各样不同的问题，而且以后我们有可能会安装更多的软件。所以能否有一个统一的方式可以处理这些项目的依赖？我认为这是一个非常现实并且迫在眉睫要解决的问题。

第二个问题是，项目需要运行一系列命令以后才能启动。这些命令有可能包括：第一步安装依赖 npm install，然后有一个编译的过程（因为我们使用 TypeScript 书写，需要编译），接下来还有可能要使用 webpack 生成对应的静态文件供 H5 页面使用，最后还有 npm start 启动对应的应用。所以能否将这些命令浓缩到一起？

第三个问题也很重要，就是项目更新的问题。目前当项目有更新的时候，需要一系列手动步骤：有可能需要登录到服务器上，首先停止服务，然后拷贝对应的代码；假如依赖有更新，可能还需要重新安装依赖，然后再启动服务。这是一个非常繁琐而且容易出错的步骤。有没有更方便的方式可以完成这个过程？这是我们的第三个问题。

当然，第三个问题其实可以分成两个问题：第一，我们需要一个命令完成更新代码、安装依赖、启动应用的整个过程；第二，我们要在特定的提交（比如一次 git commit）中自动触发整个流程。

这三个问题就是接下来一系列内容要尝试解决的问题，主要使用 Docker 以及 GitHub Actions 来完成。这节课我们对之前的知识做了简单的回顾，并提出了三个问题。接下来看看使用特定的工具能否良好地解决对应的问题。
