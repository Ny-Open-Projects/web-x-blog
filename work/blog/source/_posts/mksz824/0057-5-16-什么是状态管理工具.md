上节课使用 Vue Router 添加了一系列功能。现在来到路由以外的另一个 SPA 重要课题：状态管理。学 Vue 或 React 时，经常看到同学被状态管理工具搞得一头雾水，根本不知道它解决什么问题就拿来使用，跟着教程写了一大堆不知所云的代码。这是我们应该极力避免的学习途径。使用任何工具之前，首先要弄懂它到底解决什么问题，项目中是否真的需要它。小规模的项目也许根本不需要全局状态管理，用了就是画蛇添足。

## 全局状态从何而来

和路由工具一样，先弄懂起因：为什么会有状态管理工具？整个应用共享同一份状态，是从 SPA 开始出现的。没有 SPA 的世界，每次访问 URL 页面都会完全刷新，数据往往来自后端的直接渲染，根本就没有全局状态的概念。SPA 诞生以后，前后端分离开始大规模实践，整个应用在不跳转 URL 的基础上通过 JS 渲染界面，状态管理工具才不断出现。

现在有首页、template detail、编辑器三个分离的静态页面。从需求上看，这几个页面应该都有一些共同的数据要获取和处理，这些数据称为全局数据：多个组件需要共享的一系列数据。最简单的例子：template 信息，首页和详情页可能都要用；user 信息，当前用户是否登录、登录后展示的一系列信息，三个页面都会用。随着应用扩展，还有更多全局状态：是否在读取、是否有网络错误、用户自己创建的模板信息、编辑器的复杂状态等等。处理这个问题时必须把眼光放长远，把问题想象得比现在更复杂。

## 解决方案一：根组件集中管理

React 和 Vue 共享一个重要思想：单向数据流。数据从父组件通过 props 流动到子组件；子组件本身不修改数据，而是通过回调或发送事件的方式回到数据源头修改，修改完毕后再往下流动。

第一个方案自然诞生了：把所有全局状态存在根组件中，然后向下传递，哪里需要传到哪里。没问题，但麻烦不少：第一，组件如果有十几层，底层组件想获得某一项全局数据，就要一层一层传递下去，非常繁琐；第二，中间传递层可能根本不需要这个数据，但为了带下去还是要传一下；第三，根组件压力太大，所有的数据处理方法、数据分类归类都放在这里，逻辑非常繁杂。复杂情况下这个方案不好用。

## 解决方案二：全局对象

第二个方案抛开框架，从 JavaScript 语言本身出发：想共享数据时，创建一个文件，里面包含一个对象，放全局数据和一系列操作，用的时候把这个文件 import 进去，调用方法或直接修改数据。这是最浅显易懂的方案，但它真的完美吗？分析一下缺点：

1. 全局对象里的数据是普通 JavaScript 类型，不是响应式的。第一次读取渲染没问题，但修改数据以后，界面没法做出对应的更新，这是很大的问题。
2. 全局对象的修改无法追踪。应用中任何一处代码都有机会 import 它并做出修改，但你根本没法搞清楚是哪行代码哪个文件改了全局数据，非常容易产生难以追踪的 bug。
3. Vue 是组件化的世界，组件像一棵树，全局数据一般走单向数据流从父组件传给子组件。直接从组件中获取全局数据被认为是一种反模式，很容易造成数据混乱。

## 状态管理工具

这种情况下，状态管理工具出现了。按框架适配分，最出名的有三个：针对 Vue 的 Vuex；更适配 React 的 Redux（但它不与框架强绑定，其他框架也能用）；还有设计理念独到的 MobX，它把响应式编程的思想带到 React 中去。

别被这些高级的单词吓坏，这些工具内部的设计理念大同小异。首先，它们都有一个类似 object 的数据类型，但不同于简单的 object，称为 store，也叫 single source of truth（唯一的真实数据来源），整个应用全局就用这一种数据结构来管理状态。其次，里面的数据不能随意修改，不能像普通对象一样随意操作，只能调用特殊的方法来实现修改。

正因如此，store 中状态的变化完全可追溯、可控制，称为 predictable（可预测的）。借助特殊的工具，我们甚至能清楚地观察到数据的变化，并且在变化中来回漫游，这个功能叫 time travel（时间漫游）。

状态管理工具的核心概念就讲完了：一个特殊的全局数据结构，里面的数据不能随意修改，只能调用特殊的方法进行变更。三个工具各自衍生出一些特色，但核心理念不变。用图描述新架构：global.js 被打入冷宫，取而代之的是神奇的 store，内部包含需要的所有数据。数据不能随意修改，必须调用称为 action 的方法才能修改；修改成功后 store 更新数据，并通知界面做出对应的更新，页面更新到最新状态。

这节课介绍了状态管理工具是什么、要解决什么问题。下节课了解 Vuex 作为这样一款工具有什么神奇和奥妙之处。
