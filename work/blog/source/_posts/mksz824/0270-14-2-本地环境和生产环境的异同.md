应用开发完毕之后，就正式进入上线（部署）环节。本周开头先介绍一种传统的部署模式：这部分不会特别深入，因为它不是我们最终采用的方式，只是演示流程，总结它的优势和劣势。本节课先回顾一下本地开发与生产环境的几个异同点。

## 本地开发环境

本地开发我们已经很熟悉了。框架提供了一个内置工具 egg-bin，为了提升研发体验，它提供了在本地运行开发调试和单元测试的便捷方式：能自动监控文件修改，然后重新运行对应的命令。它使用的配置文件是 `config/config.default.ts`，启动开发环境的命令是 `egg-bin dev`，看一眼 package.json 就清楚了。

类似的还有 `egg-bin debug` 进入 debug 模式，以及 test-local、coverage 等一系列本地开发的环节，都由 egg-bin 完成。

## 生产环境：PM2 与 egg-script

部署应用时不能再用 egg-bin，因为它针对本地开发做了很多处理，而生产环境需要一个更简单稳定的方式，需要一个新的工具来管理应用的启动、停止等。在生产环境运行过 Node.js 应用的都知道 PM2 这款工具。它叫 Process Manager，作用就是管理所有的 Node.js 进程。比如最基础的直接运行方式 `node script.js`，换成 PM2 就是 `pm2 start script.js`，还能带来更多面向生产环境的优势。

去它的官网可以看到一系列 features，这里介绍几个最基本的：

- 支持 cluster 模式运行（cluster 是 Node.js 中的概念，下节课会讲）；
- 自动重启 auto reload，代码发生任何改变都能监控到并重启；
- hot reload；
- 性能监控工具：所有运行中的进程都能在界面上查看状态、CPU 和内存占用。

不过针对本项目的框架，不需要用 PM2 这类进程管理工具。框架有自己的模块 egg-script，它建立在 egg-cluster 之上。egg-cluster 支持启动多进程，稳定性极高，下节课会专门讲这个特殊的 Cluster 模式。

生产环境下，我们用 egg-script start 和 egg-script stop 来完成启动和关闭。注意它的配置文件是 `config/config.prod.ts` 与 `config/config.default.ts` 合并后的结果，用的是 deep merge，prod 会覆盖 default 里的同名配置。生产相关的配置都可以写在 prod 文件中。

## 编译 TS 为 JS

用 egg-script 启动的是 JS 文件，所以生产环境运行之前要先手动编译，把 TS 转换为 JS。这个命令在 package.json 里，叫 tsc：

```bash
npm run tsc
```

它实际执行的是 `ets tsc -p .`。这个 ets 是什么？它对应一个 egg Helper 代码库，提供一系列与 TypeScript 相关的帮助，用来 Generate TypeScript Definition（`.d.ts` 文件）for egg。之前说过框架会自动生成一系列 `.d.ts` 类型文件供我们使用，原理就是用到了这个 Helper，而它内置在 egg-bin 里，可以直接使用。

运行之前特别注意：先升级 TypeScript 版本。原来项目用的是 3.0.0，由于后面的逻辑加入了 SSR 功能、引入了 Vue 3 依赖，而 Vue 3 需要 TS 4 以上版本才能编译，所以要改成 4.4.3：

```bash
npm install typescript@4.4.3 --save-dev
```

没升级就运行 tsc 是会报错的。运行后可以看到生成了一系列 `.d.ts` 和 `.js` 文件，每个 TS 文件都有对应的 JS 文件。`.gitignore` 里写了规则，这些文件在 Git 中都被忽略。

## 启动与清理

生成了 JS 之后就可以运行 `npm run start` 开启服务。稍等片刻，服务会在对应的 IP 和端口启动成功，刷新页面可以访问，说明启动成功。关闭进程用 `npm run stop`，稍等一会儿就关闭完毕。

再介绍一个小命令。package.json 里有一个 `npm run clean`，它运行的是 egg-script 的子命令 `ets clean`，会把生成的 JS 文件全部删除。运行之后，这些编译产物就都清掉了。

这节课回顾了本地开发环境和生产环境的概念与异同，以及在不同环境中怎样启动应用。下节课深入看一下 Cluster，看看它是怎样在生产环境大显神威的。
