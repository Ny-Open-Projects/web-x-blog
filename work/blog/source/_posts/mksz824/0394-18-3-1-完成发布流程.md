上节成功拿到了截图，这节完成截图之后的发布。发布本身和截图没有直接关系，截图是为了把 coverImage 字段保存到数据库。为什么只在发布时截图？因为截图并上传是一个耗时的过程，每次保存都截图势必造成大量浪费，所以设计成只有发布时才走一遍完整流程。

## 四个步骤

用注释把步骤写清楚，然后逐步编码：

1. **截图并上传**：takeScreenshotAndUpload，已经完成；
2. **更新 store 中配置的 coverImage**：`store.commit('updatePage', { key: 'coverImage', value: resp.data.urls[0], isRoot: true })`，value 能自动联想出来，resp.data.urls[0] 就是上传后真正的 URL；因为要修改根属性，isRoot 为 true；
3. **保存作品**：有了更新后的值，直接 `await saveWork()`。不过要看一下 useSaveWork 里的 saveWork 函数，它目前没有取得 coverImage，所以要补上一起保存；
4. **发布作品**：添加 publishWork action，用 actionWrapper 包裹，URL 是 `works/publish/:id`（没有 body 数据），mutation name 同名，method 设为 post。暂且不添加对应的 mutation，因为发布完成后界面还没有任何呼应。调用时 `await store.dispatch('publishWork', { urlParameters: { id: currentWorkId } })`，注意要传 id。

## 错误处理：finally

看起来四个步骤完成了，但要特别注意出错处理：假如发布不成功，界面上的一些元素需要复原，比如 `canvasFix.value = false`。如果中途出错，最后这行是执行不到的。async 的错误处理我们已经很熟悉：try/catch，catch 里先 `console.error(e)` 打印出来。这里还要用上 try/catch 之后的 **finally** 关键字，不管 try/catch 发生什么情况，finally 里的代码都会执行。把 `canvasFix.value = false` 放进 finally，整个发布过程的错误处理就完成了。

## 发布的 loading

页面实测：点击发布，先 upload-image 成功返回 URL，接着 saveWork 的 patch 请求带上了最新的封面图，最后 publish 的 POST 也成功，返回了一个 URL，这个 URL 后面可以继续使用。

但发布时没有任何 loading 效果，最好像保存一样加上。由于点击发布是好几个请求的混合状态，不适合用全局状态中的 loading（它没法描述组合状态），所以简单一点：在 editor 中添加响应式对象 isPublishing，初始 false；点击 publish 时先置 true，在 finally 里置回 false，然后把 isPublishing 返回出去绑到按钮上。再点发布，loading 效果出现了，直到全部结束才消失。

发布流程完成。下节让发布成功后弹出浮层，继续下一步处理。
