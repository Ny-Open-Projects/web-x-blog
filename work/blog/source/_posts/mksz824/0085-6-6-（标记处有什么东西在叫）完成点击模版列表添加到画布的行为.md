前几节课我们成功编写并且在编辑器中央循环展示了第一个组件 LText，现在来完成第一个行为：点击左侧模板，添加到编辑器中央。这个任务对大家来说应该没什么难度。技术实现文档中已经描述了它的过程：渲染左侧预设组件模板，数据是预设的，可以写死在本地，也可以从服务器端获得。

但文档里是在没有代码实现的情况下高度抽象的过程，现在有了业务代码，再用图来分析一下怎样完成这个任务。图应该从左边开始看，还是从最简单的 case 考虑：因为我们现在只实现了 LText，所以模板暂定只渲染一系列 LText 模板。模板的数据就是我们之前确定的 LText 的各种属性，传入 LText 组件渲染即可。

首先要搜集模板数据。技术方案里说过可以写死在本地或者从服务器端获得，这里采用第一种，简单地写死在本地。我在 src 下面创建了一个文件 DefaultTemplates.ts，里面暂定了一个变量 DefaultTextTemplates。看这些属性很熟悉，就是我们分析得到的 LText 接受的一系列属性，它们可以渲染出不同的文本效果。

接下来创建一个组件来循环渲染这些测试数据。这个组件有一个 list 属性，传入后就可以循环渲染这些数据，生成一系列 LText。做法和中间画布的渲染逻辑是一样的。我已经建立了 components-list 组件，一些代码都预设好了，只要在模板中渲染出来。很自然地写 LText，加 v-for 循环展示：item in list，key 等于 index，然后用 v-bind 把属性一个一个绑上去，把 item 传过去。保存后看页面，预设的模板都展示出来了。

在 components-list 组件中唯一的区别是给 LText 添加点击事件，所以要把这些 LText 一一包裹在一个 wrapper 中，可以设置成 div 标签，起到隔离的作用：在 wrapper 上添加点击事件，往外发送一个事件，称之为 on-item-click，我们不希望它影响到组件本身的点击事件。修改很简单：创建一个 div 加 class="component-item"，内部就是 LText 组件，把原来的代码拷贝进来。

接下来添加点击事件。先添加 emits 数组，事件名 on-item-click；然后建立 setup，取出两个参数：props 和 context。在 setup 中创建函数 onItemClick，data 是要发射出去的属性，暂定为 any；里面发射事件：emit('on-item-click', data)。最后把 onItemClick return 出去。把这个事件添加到外层 wrapper 上：@click="() => onItemClick(item)"，注意要用调用的方式，调用的参数是 item，也就是循环的这一项属性。保存，任务完成。

看图，现在走到发送出事件这一步了。这时也许有同学会问：不如在这个组件中直接调用 useStore 然后 commit 发送变化，而不是把事件发送到父组件、由 editor.vue 处理，走一道捷径直接过去不就完了？为什么还要经过一个中间层？我是这样认为的：未来这个行为可能不只是添加到中间编辑器，点击以后可能有很多新的变化。所以作为一个展示型组件，最好不要和 store 的行为强绑定，而应该以事件的形式提供一个回调，要做什么事情，由接受事件的容器型组件做决定。

事件已经发送出去，现在处理 editor.vue，接收事件并添加对应的处理。在 setup 中添加 addItem 函数并返回出去，然后在模板上接收：@on-item-click="addItem"。这时就可以用 store 来进行 state 的更新了：store.commit('addComponent', props)，mutation 的方法叫 addComponent，把这一系列属性传过去。

有了这个，就可以在 store 中做文章了。到 editorStore 添加 mutations，刚才事件名称叫 addComponent，第一个参数是 state，第二个是 props。看图，现在走到真正的处理这一步。创建一个 newComponent 作为最终的数据，它应该是 ComponentData 类型的：id 用 uuidv4 创建，name 是 LText，props 就是传过来的 props。有了新的 component 数据后，把它 push 进去：state.components.push(newComponent)，整个修改完成。

来感受一下好不好用。来到页面，模板都显示在这里了，点击其中一个，它被添加到了中间编辑的部分。因为中间是响应式的数据，当我们更新 state 时，这部分响应式的内容就发生了更新。

整个添加的过程完毕了。通过图的方式，大家是不是可以更好地了解整个过程？虽然完成了逻辑，但我又发现了一个不爽的地方：props 或者 editor 中的 props 都设置成了 any 类型。这就是我说的渐进式开发：在开发过程中发现问题，发现不对的苗头就要分析现在的做法是否得当，不要让问题越积越多。props 一开始是用 indexable type 描述的，但其实 ComponentData 的 props 就是业务组件的一系列属性，大部分已经确定：由通用属性和特有属性组成，而不是一系列不确定的状态。当然这些属性可能比较多，用 interface 描述可能写比较长。改成确定的 interface 到底值不值得，下节课来讨论。
