现在开始做登录功能，首先遇到的就是表单处理，而表单处理的第一个基本问题是验证。记住一句话：永远不要相信用户的输入。所以我们现在学的不是单纯的登录问题，而是一套与数据验证相关的通用方案。数据验证的范围比表单更大，定义 schema、数据类型时同样会遇到验证需求。

## 旧方案的痛点

数据验证在前端和后端都需要做。前端约束用户输入，让用户填入符合规则的字符，不合规时给出提示；后端则要再次保证传入 API 的数据是合理的。

之前我们前后端用的是不同的方案。前端靠框架能力，框架提供了一批表单组件，按它的规则写就能完成验证。但这种方式对我们不透明，和框架深度绑定，自定义不方便；换一个框架就要重新学一套用法。比如用 `AForm` 时，它提供好了一系列组件要按它的方式写，想给组件添加属性、改样式都不方便。后端用的则是 `ajv-validate`。

于是一个自然的想法是：有没有前后端通用的方案？学一套 API、写一套规则，前端后端一起用。

第二个问题在 TypeScript 身上。TS 一定程度上约束了数据类型，但它没法用于运行时验证，因为 TS 是静态类型检查，只检查代码中的类型，到 runtime 就不起作用了。结果我们经常要写两套代码做同一件事：一个验证 schema，规定 email 是 string、password 是 string；再写一个 TS 类型，内容和 schema 完全一致，只是应用场景不同，却必须写两遍。定义 user 的 schema 时也一样：interface 已经写了一遍，schema 里还要把类似的内容重新写一遍。

如果有一种方式，先定义 schema，再通过特殊手段把 `UserProps` 这样的类型直接推断出来，就非常理想了。

## Zod 登场

解决这两个问题的工具就是现在非常流行的 Zod（zod.dev），GitHub Stars 高达 29.1k。它以声明式的方式定义和验证数据的结构与约束，可以用于验证前端用户输入、后端 API 响应、数据库查询等各种数据。两个我很喜欢的特点：

1. 验证器只需声明一次，Zod 就能自动推断出静态 TS 类型，还能把简单类型组成复杂的数据结构，正好解决第二个问题。
2. 支持链式调用和组合验证规则，可以灵活定义复杂验证逻辑，API 友好、易读。

Nuxt 是全栈框架，正好是让前后端共用一套规则的绝佳位置，第一个问题也解决了。

## 安装与基本用法

安装很简单，先确认 TypeScript 版本在 4.5 以上（Nuxt 3 新建的项目都满足），然后 `npm install zod`。装好后拿 `index.vue` 举几个例子。

所有功能都从 `zod` 导入的 `z` 对象上完成。先定义一个最简单的规则：

```ts
import { z } from 'zod'

const mySchema = z.string()
```

这个 schema 要求内容是 string。用它调用 `parse` 方法来验证任何值：传入正确的类型 `'Viking'`，打印 result 会直接输出这个字符串，说明没问题；传入错误类型比如数字 12，就会抛出一个特殊的 `ZodError`。

还有一种安全解析方式，验证失败但不抛错，也是我经常用的，叫 `safeParse`。传 12 进去不会有任何异常，它返回一个对象：`success` 为 false 表示失败，另有一个 `error` 属性，上面的 `issues` 里是各种错误详情。

这里有个非常好的设计：不能直接打印错误，要先判断 `if (!result.success)` 再打印，它使用了 type guard 的形式，让代码更容易获取类型，这一点做得很好。

## 链式调用扩展规则

在 string 上还能用链式调用添加更多规则。比如要求它是邮箱，直接接 `.email()`。传入一个普通字符串验证就会报错：invalid string，message 说明 invalid email，不是合法邮箱。

还可以设置最小长度，比如 `.min(5)`，字符串至少 5 个字符，不满足时报 too small。自定义错误信息也很方便：在链式方法里接收一个 object，传 `message` 字段即可，比如 email 规则上传 `message: 'should be email'`，报错时就会显示这条自定义信息。链式写起来非常顺手。

Zod 几乎覆盖所有类型的数据验证：原始数据类型、空类型、各种字面量，字符串上除了演示的还有 UUID、URL、startsWith 等等，Numbers 也有，大家可以到官网探索。

## 对象 schema 与类型推断

最后定义一个和登录契合的 object schema：

```ts
const loginSchema = z.object({
  email: z.string().email(),
  password: z.string().min(6)
})
```

它完全可以嵌套：email 属性是 `z.string().email()`，password 是 `z.string().min(6)`。这种写法非常形象，看一眼就知道数据规则是什么样。

再展示它最强大的特性，从 schema 推断静态类型：

```ts
type LoginData = z.infer<typeof loginSchema>
```

打开 `LoginData` 这个类型看一下，非常完美：生成了 email 和 password 两个都是 string 的类型。这解决了开头说的第二个问题。
