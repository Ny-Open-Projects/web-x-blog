上一章我们明确了有什么样的模块类型、用什么工具打包成什么样的模块类型。这一章就可以正式把业务组件库和 OpsFlow 项目（也就是 B 端项目）进行分家了。像最早分析的那样，业务组件库作为一个在 B 端和 H5 端都要使用、或者说是共享的项目，需要单独拆分出来，也就是新建一个单独的项目。

CLI 里已经有了一个最终成品的模板。在 CLI init 之后可以看到两个选项：Vue3 标准组件模板和 OpsFlow 组件库模板。这里请大家和我一样，不要选择 OpsFlow 组件库模板，因为它是最终成品的结果。我们要做的是把它一步一步进化到最后的成品模板，这个过程还是非常有意思的，能学到很多知识。所以再强调一遍：不要使用直接已经完成的成品模板。正确做法是在 test 文件夹下新建一个文件夹，执行 init，还是选择同一个 CLI，然后选第一个 OpsFlow 标准项目模板来新建。

这个项目使用的基础技术和 B 端完全一致，也是 TypeScript 加 Vue。由于 OpsFlow 组件库这个名字在做项目时就已经采用并发布到了 npm，我这里起了个新的名字来演示。

这个项目就是用 OpsFlow 标准模板创建的。我把一些跟组件库相关的代码挪了进来，暂时采用这样的文件结构，其实就是把 B 端里的一些文件直接挪过来。下面重温一下这个结构，温故而知新。对业务组件库来说，最重要的当然是组件：我们有三个基本组件，LText 文本、LImage 图片和 LShape 图形。这里暂时只挪过来一个 LText，因为之后要修改文件的结构，如果三个都挪过来就要改三遍，很麻烦。

然后挪过来一个通用的 hooks，也就是最关键的 useComponentCommon。它对外暴露两个方法：一个是 styleProps，负责样式的提取；另一个是 handleClick，处理点击以后的事件。最后是 defaultProps 这个数据文件。defaultProps 有几部分内容：首先比较重要的是组件属性的 interface。通用属性的 interface 叫 CommonComponentProps，后面是两个独特的属性，TextComponentProps 和 ImageComponentProps。对应到图上就是通用的共有属性，加上不同组件各自的独有属性。

定义了 interface 之后，就可以创建对应的默认值，比如 textDefaultProps 和 imageDefaultProps。除了这两部分数据，还有一些更加细化的数据：比如把属性过滤以后，生成对应要用在组件样式上的属性名称 stylePropsNames，用 `without` 做处理。每个组件都要做一次单独的处理，因为每个组件不一样，你不知道哪个属性会被去掉。最后是一个 transformToComponentProps 函数，把属性转换成对应的 Vue props。

这里要特别提一下之前留的作业：怎样防止在编辑器中的点击事件被触发？我在这里添加了一个 isEditing 属性，是个布尔类型，可以传 true 或 false。当 isEditing 为 true 时，useComponentCommon 里会做判断，最终 window.location.href 的跳转就不会执行。

这就是业务组件库的一个简单基本结构。可以看到它很简单，基本就是把原来的文件挪过来就好。当然它和 B 端项目肯定是有差别的，因为我们最终生成的文件类型完全不一样。下节课开始对它做一步步的改造，为生成组件库继续奋斗。
