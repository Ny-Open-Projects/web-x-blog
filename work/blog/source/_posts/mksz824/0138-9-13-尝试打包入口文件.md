上节课我们其实已经明白了整个 Rollup 的处理过程：先添加 TypeScript plugin，对 TS 文件使用 tsc 做转换；再添加 Vue plugin，把 Vue 文件转换成对应的 js 对象；最后使用 css-only 对剩下的 CSS 文件做处理，单独生成一个样式文件。这样的处理流程对我们的入口文件 src/index.ts 应该没有问题。现在直接把入口替换为 index.ts，看看有什么问题。

修改了入口文件，同时修改了一些 overrides：exclude 多加了两项，把 src/App.vue 和 src/main.ts 加进去，不需要处理。当然这两个文件后期是要删除的，作为组件库我们已经不需要和网页应用相关的这两个文件了。添加完毕后直接试一下 `npm run build:esm`，最后生成了 breaks.esm.js 文件，生成没问题。但出现了一系列警告：unresolved dependencies。这个警告之前其实就出现过，我们一直没有管它。它贴心地提供了文档，在 Trouble shooting 的 Treating module as external dependency 一节，大意是：Rollup 默认只解析相对路径的模块 ID。对于绝对路径的模块，比如 `import moment from 'moment'`，它处理不了，只会保留 import 语句不做任何处理。

所以如果你想将 node_modules 里的文件都打包进最终的文件，比如我们 dependencies 里有 Vue 和 lodash，想把它们的实现打包进去，可以使用一个单独的插件完成这个任务。它是官方插件，叫 rollup-plugin-node-resolve，大家可以去安装。它可以处理 node_modules 中的第三方模块，并把它们打包进最终生成的内容中。我这里已经安装完毕，import 进来，添加到 plugins 最前面。有了它之后，再打包一次，警告消失了。

看一下 dist 中的代码：生成了一系列 index.d.ts 声明文件，bundle.css 生成了，主要的 ESM 也生成了。打开 OpsFlow 组件库的代码看看，生成了非常多的内容，大约五千多行。为什么呢？因为刚才我们把第三方模块，也就是 lodash 和 Vue 的实现都加载了进来。它虽然是 Tree shaking 的，只把需要的几部分代码拿进来，但实现还是很长，能看到一系列第三方库的实现。

这时候扪心自问一下：这真是我们想要的结果吗？先岔开聊一句，审视一下项目的依赖。package.json 里的 dependencies 分几类。第一类就叫 dependencies：这类依赖一般是运行项目业务逻辑需要的第三方库。当别人运行 `npm install OpsFlow-components` 时，这些依赖默认会被解析并下载到 node_modules。第二类是 devDependencies：开发模式工作流下需要依赖的第三方库都声明到这个类型下。什么是开发模式工作流呢？我大致的理解是：与核心业务逻辑和最终生成的模块无关的任务，而这些任务又支持着核心业务的开发过程，以及程序从开发环境到生产环境的过程。比如单元测试、语法转换、Lint 工具、CSS 预处理器、程序构建等等。

还有一种类型的依赖，用我们的项目举例：大家都知道我们组件库赖以生存的库是 Vue，没有 Vue，这个 Vue 组件库就毫无意义。类似场景还有很多，比如 React 组件库、Webpack 插件，都是以 React 或 Webpack 为核心开发的库。这些插件或组件库运行都有一个前提：核心依赖库必须先下载安装，它不能脱离核心依赖库而被单独依赖并引用。所以 npm 的 package.json 中还有一个字段提供这样的信息，告诉用户：你要使用我的库或插件，需要安装这些依赖。这个字段称为 peerDependencies。当你在一个项目中用 npm install 安装库的时候，peerDependencies 中声明的依赖不会被 npm 安装，转而输出 warning 日志。

我们这里是创建一个 Vue 组件库，所以需要把 Vue 这个依赖挪到 peerDependencies，告诉用户使用之前一定要安装 Vue。挪动一下：把 Vue 从 dependencies 移到 peerDependencies。但还有一个问题：开发的时候我们需要这个库。开发过程中如果没有这个依赖，而 npm install 不会安装 peerDependencies 里的内容，不就直接报错了吗？很简单，把这个依赖同时挪到 devDependencies 里，这样 npm install 的时候就有这个依赖了。放到最下面，我们就完成了这个改动。

描述完 npm 中的依赖关系，回到打包。当用户使用 npm 安装最终的组件库时，外部环境会提供我们需要的 Vue，而用户本地的依赖会提供 lodash-es。所以最终代码中其实不需要 Vue 和 lodash 这两个模块。我们的任务回到原点：对于源代码中使用的 Vue 和 lodash 这些模块，不进行打包。Rollup 提供了一个字段完成这个任务，称为 external。文档的 Core functionality 里可以看到，external 规定哪些是打包过程中的外部引用模块，在打包过程中将其省略。它最简单支持数组的写法，把想省略的模块写到数组中即可，可以微调哪些导入想打包、哪些是外部引用。

写一下：在配置最下面加 `external: ['vue', 'lodash-es']`，把这两个去掉。再运行一次 `npm run build:esm`，成功了。再看里面的实现：往上滑，原来那些第三方引用的内容都消失了，Vue 的实现和 lodash 的实现都没有打包进代码中。

它还支持更丰富的写法，可以写成函数。函数有个参数 id，代表模块名称。返回 true 代表省略，false 代表不省略。假如只想省略 Vue，可以这么写：`return /vue/.test(id)`，用正则判断 id 是否以 vue 开头，为真时省略。重新打包一次试试：往上翻会发现 Vue 的实现没有了，但 lodash 的代码被打包了进去，能看到 basePick、basePickBy 这些方法，都是因为我们在里面使用了 pick，这些是它的一系列依赖。大家可以想想：如果用 external 的函数写法，想忽略掉 node_modules 中的所有模块，应该怎么写？

到这里，我们就完成了对最终代码生成格式的调整，现在的 ESM 模块看起来没有什么问题了。这节课就到这里，谢谢大家，再见。
