数据获取的最后一节，探讨发送请求的时机问题。

先看默认情况。比如现在在首页，要跳转到 user one 或 user two 这两个需要发异步请求的页面，点击后会先发送请求，页面等到数据获取完毕后再渲染跳转，这是通过 Vue 内置组件 Suspense 完成的。用上次的页面做个实验：为了效果更明显，把 DevTools 里的网络调成 Slow 3G，同时简化代码，只留下一段使用 `useFetch` 发请求的逻辑。

点击 user one，可以看到页面此时并没有跳转，请求发送完毕后才完成跳转；回到 home 再试，点击 user two 也是同样的流程。

这里可以介绍一个内置的全局组件，用来显示网络请求的状况：`NuxtLoadingIndicator`。把它放在根组件（最外层）上，任何异步请求的状态都会在里面显示。依然把网速调慢，从 home 点击 user one，页面顶部会出现一个一直在动的绿色进度条，请求结束、页面跳转后条就消失。

这就是默认的请求时机和方式。当然，我们可以通过组合式函数的参数手动修改请求时机，让请求在路由跳转结束后再开始，而不是等请求结束才跳转页面，这更像传统的 SPA 项目：一般在 onMounted 时再发异步请求。

参数很简单，叫 `lazy`（懒加载），默认 false，设为 true 即可。使用这种方式就要手动处理请求状态，比如要显示 loading，就需要拿到之前用过的 `pending` 参数，通过判断它来渲染。另外注意，lazy 模式下 `NuxtLoadingIndicator` 不起作用，需要手动用 `v-if` 配合 pending 来完成 loading 效果。

修改完请求方式后看效果：刷新首页，调成 Slow 3G，点击 user one，页面立刻跳转完毕并显示 loading，loading 结束后数据才显示出来，和之前完全不一样，顶部也没有进度条了。

除了传 lazy 参数，还有两个快捷方式可以完成同样的效果：`useLazyFetch` 和 `useLazyAsyncData`，它们和前两个函数一一对应，只是自带 lazy 效果。喜欢这种渲染方式可以直接用这两个快捷函数。

最后介绍 client-only fetching。众所周知，首次页面渲染的数据请求是在后端发起的，这是 Nuxt 作为 SSR 框架的一大特点。先复习一下：直接在 user one 路由上刷新，前端不会发出任何异步请求，页面是直接渲染出来的；查看页面源代码，这些 HTML 是直接输出在源代码里的，搜索用户名称就能找到对应字段。

如果想让行为和普通 SPA 一样，在页面渲染完毕、hydration 结束后再发请求，只需加一个参数，把 `server` 设为 false。修改后刷新页面验证：network 里可以看到请求是由前端发起的，页面上也有 loading 状态；再看页面源代码，搜索 loading 只能找到 loading 字样，其他数据都没有，它们是通过 JS 动态添加的，而不是直接输出到 HTML 中。

不过我不推荐这种数据获取方式，等于把 Nuxt 带来的 SSR 优势都抹掉了，使用默认形式就挺好。如果想让页面出现骨架屏，加个 lazy 完全可以。

到此为止，Nuxt 数据获取的知识告一段落。大家要掌握三种数据获取方式的不同，以及请求时机的问题，对整体流程更加成竹在胸。
