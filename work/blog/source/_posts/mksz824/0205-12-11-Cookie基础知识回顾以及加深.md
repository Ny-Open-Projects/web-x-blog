从这一节开始进入认证的内容。认证是系统里最基础的安全设计，再简陋的信息系统也不会忽略用户登录这个功能。系统要为用户提供服务之前，总得先弄清楚"你是谁、能不能用某个功能"。要完成这个任务，先要理解一个核心概念：Cookie。

HTTP 请求本身是无状态的，但 Web 应用通常需要知道发起请求的人是谁。为了解决这个矛盾，HTTP 协议设计了一个特殊的请求头，也就是 Cookie。这部分内容看起来很常规，不少同学觉得自己都懂了，但真去翻文档细看，会发现很多模棱两可的细节。所以值得花不到十分钟把 Cookie 的关键属性系统回顾一遍。

## 创建与回传

服务器用 `Set-Cookie` 这个响应头向用户代理（浏览器）发送 Cookie 信息，格式是 key=value，比如 `yummy_cookie=chocolate`。想设置多个 Cookie，就在响应里带多个 `Set-Cookie` 头，比如再加一个 `tasty_cookie=strawberry`。

之后浏览器对同一台服务器发起新请求时，会把之前保存的 Cookie 通过一个请求头自动带回去，这个请求头的名字就是 `Cookie`，内容同样以 key=value 的形式列出之前设置的值。整个过程完全自动，客户端不需要做任何额外设置。

## 生命周期

生命周期靠 `Expires` 属性控制，它指定一个过期时间，超过这个时间 Cookie 就失效。要注意的一点是：过期时间的判断只和客户端（浏览器）相关，跟服务器端没有关系。

## 安全属性

Cookie 里经常存着比较隐私的信息，所以协议提供了两个安全相关的属性。

第一个是 `Secure`。激活方式很直接，在 Cookie 定义后面加上 `Secure` 即可。它表示 Cookie 只能通过 HTTPS 协议加密过的请求发送给服务端，如果没有使用 HTTPS，这个 Cookie 就不会被发送。

第二个是 `HttpOnly`，这是一个非常有用的属性。设置之后，JavaScript 无法访问该 Cookie，页面里任何 JS 文件中调用 `document.cookie` 都拿不到它的数据，可以有效缓解 XSS 攻击。

## 作用域：Domain 与 Path

作用域决定 Cookie 在哪些主机、哪些路径下生效。

`Domain` 指定哪些主机可以接受这个 Cookie。特别注意：不指定时默认为 Origin，且 Origin 不包含子域名。举个例子，访问 test.com 时服务器返回 `Set-Cookie: id=xxx` 而没有设置 Domain，那么只有完全同源的 test.com 请求能带上这个 Cookie，访问 api.test.com 这样的二级域名时是不可访问、不会携带的。

但如果显式设置了 `Domain=test.com`，那么 test.com 以及 api.test.com 等一系列子域名下的访问就都能拿到这个 Cookie 的值。这一点是实践中容易踩坑的地方。

`Path` 更简单，它指定了主机下的哪些路径可以接受 Cookie，默认所有路径都可以，也可以限定为某一个具体路径。

## SameSite 与 CSRF 防御

`SameSite` 是一个较新的属性，目前所有主流浏览器都已支持。官方的描述是：SameSite Cookie 允许服务器要求某个 Cookie 在跨站请求时不会被发送，通过这种方式可以有效阻止跨站请求伪造攻击（CSRF）。光看描述容易困惑，放进场景里理解会更清楚。

场景一：登录银行网站 bank.com，登录后它返回 `Set-Cookie: id=xxx`，此后银行靠这个 Cookie 验证已登录用户。这时你访问了黑客搭建的 evil.com，页面诱导你点击一个表单，表单的 action 指向银行的转账操作。提交时由于你登录过银行、Cookie 已存在，银行验证这是一次合法操作，钱就被转走了。

场景二更隐蔽：evil2.com 的首页直接插入一张图片，`<img src="bank.com/transfer?...">`，通过 GET 请求完成转账。你访问这个页面时图片请求自动发出，同样因为带着登录 Cookie 而被银行判定为合法交易。

SameSite 就是为了解决这类问题而出现的，它有三个选项。

- `None`：不做任何限制，行为和默认情况一样。
- `Strict`：最为严格，完全禁止第三方 Cookie。跨站点时（比如 evil.com 和 evil2.com），任何情况下都不发送 Cookie；只有在 bank.com 内、请求目标与当前网页一致时才携带。副作用是体验很差：比如第三方网页里有一个 GitHub 链接，用户点击跳转后不带 GitHub 的 Cookie，直接变成未登录状态。
- `Lax`：稍作放宽。大多数情况下仍不发送第三方 Cookie，但导航到目标网址的 GET 请求除外。

对照规则表：在第三方网页里点击 `<a href>` 跳转，Lax 下会发送 Cookie；预加载会发送；GET 表单提交（本质上和链接一样）也会发送。但 POST 表单不发送，iframe 不发送，通过 JavaScript 发起的 AJAX 异步请求不发送，前面场景里用来搞事的 image 请求同样不发送。所以刚才银行转账的两种攻击方式，用 Lax 就能防住。

以上就是 Cookie 基础知识的回顾，其中和安全相关的几个属性，尤其是 SameSite，以及 Secure、HttpOnly，后面的章节都会实际用到。课下可以再对照文档加深一遍印象。
