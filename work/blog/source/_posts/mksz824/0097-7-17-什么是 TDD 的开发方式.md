前面已经讲了 Jest 和 Vue 组件测试的大部分内容，有了这些基础，大家对一般组件的流程和测试的书写应该都没有问题了。有了这些实践之后，再补充一个非常有意思的测试概念，既拓宽知识面，也带大家体验一种很有意思的开发方式。

进入一个实际场景：拿我们要做的第一个自研表单组件来说，就是 ColorPicker 组件。很多地方的属性都需要进行颜色选择，比如背景颜色、字体颜色等等。产品经理提供了一份简单的原型图，分两张：点击颜色框之前，可点击的部分显示成一种样子；点击之后弹出一个框，是另一种样子。

通过这两张图可以分析出需求。先看显示部分：左侧显示当前传入的颜色，传入白色、黑色或任何十六进制的颜色值，就显示出来；右侧显示十种默认的常用颜色；默认情况下右侧最后一个是透明的框，点击它可以清除颜色效果。

再看点击交互：点击左侧这一块，会显示一个颜色选择框；在颜色选择框中，无论点击色块还是在 input 窗中修改值，都会把新的十六进制颜色值以事件的形式发射出去；点击右侧任何一个默认颜色框，也会把新的值以事件形式发射出去。

需求看完，有两点要特别注意。第一，这个颜色选择框如果要自己实现，是非常复杂和困难的事情，所以可以直接使用 HTML5 自带的 input color 标签：把 input 的 type 设置成 color，浏览器就会自动渲染出一个类似我们结构的表单，初始渲染一个色块，点击后弹出颜色选择器。第二，它的属性和普通 input 非常相似：用 value 指定选择器默认的颜色，使用十六进制格式；监听变化可以用 input 或 change 事件，input 事件在每次颜色变更时都会触发，change 事件则是用户关闭选择器之后才触发。

需求分析到这里，不禁陷入一种思考：可不可以把这些需求直接写下来？这些需求正是 PM 让我们完成的功能，然后根据需求写代码，让代码一个个地把这些测试用例、也就是需求完成。这种想法其实早就存在了，它叫 TDD，Test Driven Development，测试驱动开发，维基百科上有完整介绍。

所以在这个章节里，我不再按部就班地分析完需求就立马写代码。这个组件足够简单，那样写对技术水平没什么提高，不如尝试一把 TDD 的开发流程。之前的做法是先写好代码，再把测试一个个补上去，TDD 正好相反：先把分析出的需求以测试用例的方式添加到测试代码中，这时测试肯定是全部 fail 的，因为还没有任何实现；然后根据一个个测试去完成代码实现，让一个个失败的测试经过代码的洗礼变成一系列的通过。

和日常开发方式相比，这种方式有什么优势和劣势，正好在这一章里尝个鲜。TDD 的简介就到这里，下节课开始写代码。谢谢大家，再见。
