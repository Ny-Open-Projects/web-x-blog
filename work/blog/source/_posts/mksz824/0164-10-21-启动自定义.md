上节课我们描述了 Egg.js 扩展的概念，这里最后描述一个 Egg.js 的概念，称之为启动自定义。我们都知道，每次运行 npm run dev 或者 start 的时候，Egg 程序的启动需要花费一些时间，也就是说在这期间它会进行一系列的工作，比如初始化等。初始化完成以后，应用才可以启动成功，并开始对外提供服务，这是 Egg.js 一个很重要的过程。

对新手来说它是完全黑盒的，一般不用操心里面会有怎样的过程。但当你从新手成长为一个老手，就会发现有很多需求是需要启动的时候进行自定义的。比如要添加数据库以及其他类型的服务，需要在应用启动的时候把这些服务进行初始化，后面的逻辑中才能成功使用它们。Egg.js 为我们提供了一个入口文件来完成对应的任务。这个文件必须在根目录下，命名应该是 app.ts。它以生命周期这种大家很熟悉的方式，提供了各种不同阶段的回调函数，供用户进行自定义。这节课就简单了解一下这个文件以及不同的生命周期，后期我们自己开发插件的时候，很可能会深入对这个文件进行修改。

注意刚才说的位置：app.ts 必须在根目录下，不是在 app 文件夹中，而是在 app 的上一层。这个文件需要返回一个特殊的类，叫 Boot 类。我们可以通过定义 Boot 类中的生命周期方法来执行启动应用过程中的初始化工作。首先把一个依赖导进来，它是一个特殊的 interface，叫 IBoot。然后导出一个 class，这里称之为 AppBoot，使用 implements 实现 IBoot 中的一系列方法。在构造函数中可以设置 this.app 的值，类型是 Application，也就是我们非常熟悉的 app。先创建一个 private readonly 的 app，类型是 Application，然后在 constructor 中传入一个 app 参数，`this.app = app`，完成了初始化。

有了 TS 的帮助，可以点这个类型进去看一下定义文件：IBoot 是一个 interface，上面有一系列的方法，每个方法都有注释解释这个生命周期在干什么。

前面两个生命周期是跟 config 相关的。第一个称之为 configWillLoad，是最开始的生命周期。此时 config 文件已经被读取并且合并，但还没有生效，所以这是应用层修改配置的最后时机。特别注意这个函数只支持同步的调用，它返回的不是 Promise。在这里可以对配置做一些处理，比如配置中有加密的内容（像密码之类的），可以在这里做解密等操作。我们 console.log 一下：这里是 config，能拿到 this.app.config 中的 baseURL，等会儿打印出来看。

除了 config，在这里还可以通过一个特殊属性查看即将被添加的中间件，称之为 coreMiddleware，也是 this.app 上的属性。我不知道为什么它的定义文件中没有提供这个对应的属性，打的时候注意不要把单词打错。它是内置的一系列中间件，在 configWillLoad 里可以对它进行修改。这其实是中间件的第三种添加方式，也是插件编写过程中、插件源代码中采用的添加中间件的方式：因为插件不支持在 config.default.ts 里添加，也没有 router 的概念，所以只能在生命周期里添加。现在我们还没有启用 myLogger，可以在 coreMiddleware 里添加一下：直接把 myLogger 复制过来，coreMiddleware 是一个数组，使用 unshift 把它添加到第一项，注意名称不要打错。

启动看一下：config 已经被合并，打印的是 localUrl。coreMiddleware 里已经启动了一些内置的中间件，比如 notfound、bodyParser、overrideMethod 等等。现在自定义的 myLogger 也添加进去了，应该会生效。发一个请求（用 curl），请求成功后看 log 文件，里面成功添加了一条带时间的记录，说明使用生命周期添加中间件的方式已经生效了，这是一种新的方式。

下一个是 configDidLoad，不做演示了，顾名思义：config 文件加载完毕，插件这个时候也加载完毕了。再下一个是 async didLoad，是异步方法，表示除了配置和插件，其他的文件也都加载完毕了。在 didLoad 生命周期中可以加载一些应用的自定义文件、启动一些自定义的服务，比如你有一个数据库服务要启动，就可以写在这里。

到这里加载已经全部完毕，下一步是插件要先启动，对应 willReady。willReady 代表所有的插件都已启动完毕，但应用整体还没有 ready。这里面有个很有趣的现象：willReady 是 async 的，我们在里面打印 app.middleware（这里用 enableWillReady 之类的方式区分一下）。重启 npm run dev 对比：configWillLoad 时 middleware 有那几个内置项，但到了 willReady，除了 unshift 添加的第一个中间件，后面还多出了 session、security、i18n、egg-loader、tracer 这几个。它们从哪里来？因为中间有个插件加载的过程，插件也是包括中间件的，插件加载的过程中不知不觉添加了一些中间件，这就是插件的力量。这解释了为什么 willReady 比 configWillLoad 多这么多项。

倒数第二个是 didReady，也就是应用已经启动完毕了，也是异步的。在这里可以访问应用上面的一系列属性，甚至能拿到 ctx。特别注意它是异步的方法：`await this.app.createAnonymousContext()` 可以创建一个匿名的上下文对象。有了上下文对象，就可以在上面调用一系列的方法，比如调用 service.test.sayHi，都能自动联想出来。这说明在 didReady 中可以调用和应用相关的一系列方法，应用已经启动成功。console.log 打印 didReady response 验证一下。

还可以看一下最终启用的所有中间件：console.log final middlewares，即 this.app.middleware。注意区别：coreMiddleware 是一个数组（字符串），而 this.app.middleware 是应用真正启动后所有的中间件，并且它已经把数组里的字符串转化成了一系列的 function，真正的 middleware 代码。重新启动看效果：最后面是 didReady 里的代码，调用 ctx 上 service 的方法完全成功；final middlewares 把数组里的字符串转换成了真正的 async function，和配置一一对应。

这样我们就了解了这些生命周期的用途。这节课是简单的了解，完成启动的自定义，以及整个应用的生命周期。后面编写插件的时候，可能会和这些生命周期进行密切的接触。给大家一个大体的印象就可以了。
