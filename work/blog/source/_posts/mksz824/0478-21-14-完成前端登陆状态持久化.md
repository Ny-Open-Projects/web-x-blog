这节课完成前端持久化的任务。为此需要一个额外的接口：JWT 里只保存了用户的关键信息（username 和 userId 这两个区分用户的关键特征），解密后也只能得到这两个信息；而我们需要把用户方方面面的信息都返回给前端。添加一个接口是常规做法，login 里其实就是把 user 的所有信息都反馈给了用户。

## 新增 current 接口

创建接口文件 `current.get.ts`，即 `api/users/current`，从这里发起一次查询：

```ts
const currentUserData = await UserSchema
  .findOne({ username: event.context.user.username })
  .exec()

return currentUserData?.toJSON()
```

查找的关键信息是 username，它从哪里来？记得在 auth.ts 中间件里，我们把它存到了一个特殊的地方：event.context.user。中间件先运行，解密成功后就把关键信息放到了事件对象上，供之后使用，这就是保存信息的奥秘。拿过来后调用 exec，最后照旧 toJSON 返回，隐藏掉 password 等关键信息。

接口开发完毕，测试一下：先登录拿到返回信息，再请求 `api/users/current`，能返回和 login 同样的详情。然后把 cookie 稍作修改（随便删一点）再发送，弹出 400 错误，这就是中间件验证不通过直接抛出的错误。任务完成。

## 前端中间件逻辑

接下来在前端中间件中添加逻辑，让用户第一次进入系统时获取持久化的信息。现在已能拿到 currentUser，之后的逻辑从这里开始。先拿 token，从 cookie 上获取，有现成的全局方法 `useCookie`，key 叫 token：

```ts
const token = useCookie('token')
```

两种情况需要处理：

**第一种：没有 token**，说明没有登录，直接跳到 login 页面。注意 useCookie 返回的是响应式对象，取值要调用 `.value`：

```ts
if (!token.value) {
  return navigateTo('/login')
}
```

**第二种**比较难理解，需要两个判断条件：token 存在，且用户状态是未登录。这种情况就是第一次进入应用时触发的：需要检查 token 是否正确，直接向 current 接口发请求，成功就赋予用户登录状态，之后的交互就不需要再走一遍这个逻辑，做到只在第一次进入界面时运行一次：

```ts
if (token.value && !currentUser.value?.isLogin) {
  // 检查 token 并完成自动登录
}
```

发送请求选择 `useFetch`。它有个聪明之处：在 SSR 初次渲染运行时不会额外发送一次请求，而是直接调用后端路由里的逻辑，相当于把接口代码直接替换到调用处，速度更快。函数改成 async，用 await 调用 useFetch 请求 `/api/users/current`。

## SSR 下手动传 header

有个小问题要特别注意：SSR 初次运行时用 useFetch 发请求不会带任何 headers，因为这时浏览器渲染还没开始，需要手动设置。先用全局函数 `useRequestHeader` 拿到 header（注意还有一个 `useRequestHeaders` 是获取多个的，这里只需要 cookie 一个就够了），它的返回有可能是 undefined，用 `as string` 做类型断言。

请求时把 headers 加上去，需要 cookie；另外还要加一个 `accept: application/json`。因为不加的话 useFetch 默认是要接收 HTML 的，我们希望返回 JSON。不加的话大家可以试一下，会把整个 HTML 页面都返回出来。

## 处理结果

useFetch 返回的两个值：data 是真正的数据，error 是错误。为了看得清楚，先把两个都打印出来，再进行判断：

```ts
if (!error.value) {
  currentUser.value.isLogin = true
  currentUser.value.data = data.value
} else {
  currentUser.value.isLogin = false
  token.value = null
  return navigateTo('/login')
}
```

验证成功（error 为空）就赋予登录状态，isLogin 设为 true，同时把 data.value 赋给 currentUser 的 data。另一种情况是验证失败，说明 token 有问题或已过期：isLogin 设为 false，并把 cookie 清除。后端清除 cookie 要调 deleteCookie，前端不用，直接把 token.value 设为 null 即可。最后 navigateTo 到 login。

## 验证效果

整个逻辑开发完毕，验证一下。先完成一次成功登录进入首页，然后刷新：状态被持久化保存了，自动登录成功。查看数据：error 是 undefined，data 是请求返回的用户信息。

这里特别注意一个概念差异：Nuxt 3 是全栈框架。在只有前端的 SPA 世界里，很多逻辑都是页面 mount 完毕后才发送异步请求；而 Nuxt 3 的 SSR 过程中，第一次渲染时很多逻辑是在服务器端运行的，渲染到前端时登录已经完成了，并没有发送异步请求的过程。可以看到 current 的请求不是在浏览器里发出的。

最后做个反向测试：修改 token 的三个值再刷新，就会跳转到 login，数据里 error 弹出，显示请求 `api/users/current` 的结果"token 已经过期"，data 是 null，最终完成跳转。

到这里，全栈用户验证的代码编写就完成了。这是一段非常有趣的中间件代码，也是本章的难点之一，请课下好好理解，也可以想一想 OpsFlow 里类似功能是怎样完成的，不难得出全栈框架和纯 SPA 项目实现的异同。
