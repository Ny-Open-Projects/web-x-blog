上节课完成了技术架构，分析出需要几个项目以及它们之间的关系。现在要下沉到一个具体的细节，搞清楚这个细节，整个系统才能良好运作。

首先要找到核心问题或难点。仔细观察需求就不难发现，整个系统的核心是围绕编辑器制作的海报展开的，这个海报作品对整个系统最为关键。那么要想一想：海报应该由怎样的数据结构生成？

## 海报的数据结构

关注海报的本质，它应该由两部分组成。第一部分是背景，可能是图片或纯色等一系列属性；第二部分是由不同的元素组成，海报上布满大大小小的元素，元素和组件是对应的，比如图片、文字或形状。

元素内部有一系列属性，可以简单分成两类：一类是界定位置的属性，确定 position 放在哪里。元素都分布在画布上，可以想象它们对应 `position: absolute`，用 left 和 top 界定具体位置。另一类是界定展示的属性，也就是它长什么样子，多大、多宽、有怎样的文字等等。

由此可以得出一个可能的数据结构：

```json
{
  "id": 1,
  "title": "作品标题",
  "props": {
    "background-image": "url(...)",
    "background-position": "center"
  },
  "components": [
    {
      "id": 101,
      "name": "text",
      "props": {
        "left": 10,
        "top": 20,
        "text": "示例文字",
        "fontSize": "16px"
      }
    },
    {
      "id": 102,
      "name": "image",
      "props": {
        "left": 30,
        "top": 40,
        "src": "url(...)"
      }
    }
  ]
}
```

第一部分和背景相关，也就是和整个页面相关，称之为配置，里面有作品的信息，比如 title 等。第二部分 props 界定了整个页面的属性，和配置相对，这里简单列了两个 CSS 属性，比如 background-image、background-position 等。

## 组件用什么容器：数组

说完页面的设置，再说最重要的元素。面对的第一个问题是：保存这一系列元素（components）时，该用对象还是数组？

数组和对象的区别在于数组是有序的。回头看需求，里面有一个图层设置，图层可以来回拖拽，所以它是有序的，自然要采用数组，数组中是一系列的 object。每个 object 对应刚才分析出的属性：

1. **name**：指代它是什么类型的组件，比如 `name: 'text'` 就是文本组件，这个命名要和公共组件库 OpsFlow 组件库的组件命名对应起来。
2. **id**：一个特殊的 ID，每个组件都是独特的，可能需要用 ID 把对应组件筛选出来。
3. **props**：已经分好类了。一部分是位置属性，比如 left、top；另一部分是展示属性，比如文本组件有它内部的文本、字体大小等。

看完 text，image 大同小异，唯一不一样的是展示属性换成和图片相关的属性。

## 数据流转

有了数据结构，用图的方式看一下整体数据的流转情况，并通过场景分析测试这个数据结构的可用性。

在 B 端 editor 上，其实就是完成对作品信息的一系列操作：添加组件或删除组件，就是向 components 数组添加或删除对应的元素；更新组件的某个属性，就是找到数组中对应的 component，更新它的 props。操作完成后，把 JSON 数据发给 OpsFlow 后端的 RESTful API，后端根据 method 完成保存，把这一串 JSON 数据整体存入数据库，创建过程就完成了。

有了创建还要有展示，展示分两部分。第一部分是 OpsFlow 后端中的 H5 SSR 页面，直接根据 ID 把 JSON 数据获取过来，做 SSR 渲染。第二部分是在画布上展示，本质上一样，只不过通过 RESTful API 包了一层，拿到 JSON 数据后用同样的方式展示。

## 扩展性验证

分析完基本场景，还要考虑一个重要问题：扩展性。前期做技术方案设计时要特别注意这一点，不要让前期设计的局限变成后面整个项目的瓶颈。针对扩展性，可以用场景设计的方式验证，想象两个场景，看看目前的设计能否完成。

**场景一：海报添加背景音乐。** 背景音乐属于整个页面的设置，自然可以在 props 中添加属性：一个是 background music，是音乐文件的地址；另一个是是否自动播放。渲染时对这两个属性进行甄别，加载对应的文件即可。这个场景完全适用。

**场景二：新增组件类型。** 这个很重要。现在只有 text 和 image，假设要加一个稍复杂的组件，比如"当前日期"，组件添加后直接生成对应内容。做法是给业务组件库添加一个 date 组件，它的 props 分三部分：位置属性大家都一样；date 指定要渲染什么时间，默认是 now（渲染当前时间），也可以传入不同的时间；还有 style，因为日期的展示可以有各种不同的样式，可以预定义很多种样式供选择。可见目前的数据结构是能满足扩展性需求的。

这节课的下沉式设计就结束了，我们对系统最核心的问题有了一个答案。注意我们关注的仍然是宏观的整体设计，也就是技术方案的初步设计。初步设计是为了寻找方向，论证几个问题：可行性、扩展性、复杂度高低，解决这几个问题就够了。
