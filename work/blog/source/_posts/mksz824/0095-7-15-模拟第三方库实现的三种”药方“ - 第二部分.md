这节课继续完成 UserProfile 的测试，做完最后一个 case 就大功告成了：模拟 vue-router 的实现。vue-router 最终调用的 push 方法也是两层结构，中间用 useRouter 函数过渡。

目前已经通过两个途径完成了一真一假的模拟：一个是把 main.ts 的整个实现用 jest.mock 真实地模拟出来，另一个是用 global.provide 传递真实的 store，测试状态是否改变。现在新创建一个 case：完成登录之后点击登出按钮，要触发一系列事件，依次验证 logout 的 commit、message.success 是否被调用，最后看 router.push 是否被调用。

对于模拟 push，再来一点不一样的，让大家充分感受测试一个功能可以有很多手段。这次采用半真半假的方式。首先还是用全局模拟的方式：`jest.mock('vue-router', ...)` 返回一个 object，和第一种方式类似。但注意 useRouter 是一个 function 而不是对象，这里要做区别对待：这个 function 被调用后返回一个对象，对象上有 push 属性，它是一个 function。

push 的实现可以这样设计：在 SPA 路由的实现方式里我们介绍过 history API，其中 pushState 可以在不引起刷新的情况下改变 URL，操作非常类似数组。所以是否可以用一个数组来代替它完成这个操作？之后只要检查数组中是否有对应的路由就可以了。创建一个数组，称为 mockedRoutes，它是一个 string 数组。push 接受一个参数 url，实现就一句话：`mockedRoutes.push(url)`。检查时看 mockedRoutes 里有没有对应的路由，就知道这个函数是否调用成功。这就是第三种方式，和前两种都有区别，是一个新思路。

接下来完成这个测试。首先点击，这一步大家已经很熟悉了：async await，`wrapper.get('.user-profile-dropdown')`，再往下找到里面的 div，然后 trigger 一个 click。trigger 之后，先判断 commit 是否被调用。和前面的逻辑一样，判断 store 中的一个属性：`expect(store.state.user.isLoggedIn).toBeFalsy()`。

然后测 message.success 是否被调用。这里说过，为了避免多个 case 之间互相影响，最好先把 mock reset 一下。因为前面的 case 里已经用过 toHaveBeenCalled，如果不清空，调用次数会累加，造成计算混乱。reset 的位置放在 afterEach 里：拿到 message，注意它现在已经是 mock 对象了，之前也写过怎么声明，用 jest.Mocked 传入泛型 `typeof message`，然后取 success 方法调用 mockReset。这样各 case 之间就没有影响了。之后在当前 case 里判断 `expect(message.success).toHaveBeenCalledTimes(1)`。跑一下，测试完美通过。

最后判断 router 的调用。中间还有一个拦路虎，setTimeout：源代码里设定两秒后才执行 push。经过前面的历练，对付它的方法大家应该很轻松就能掌握了：在 beforeAll 里写 `jest.useFakeTimers()`，用假的 timer 实现；然后在断言前执行 `jest.runAllTimers()`，让 timer 跑完。run 完之后就可以断言了：push 被调用后，mockedRoutes 数组里应该有一项记录，值是斜杠。用 toEqual 比较数组：`expect(mockedRoutes).toEqual(['/'])`。跑一下，完美通过。

到这一步，UserProfile 的测试就全部完成了。这个组件本身可以说毫无难度，它的测试其实也不是那么重要，但我想通过它让大家掌握模拟第三方库的三种不同药方，感受测试的花样和玩法。请大家课后回顾这三种方法。这节课就到这里，谢谢大家，再见。
