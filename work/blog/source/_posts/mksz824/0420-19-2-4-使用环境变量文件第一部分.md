上节课简单了解了 Vue CLI 中模式的概念。所谓模式，就是在运行 vue-cli-service 命令时设定不同的环境变量 NODE_ENV，然后 Webpack 会根据这个环境变量使用不同的配置文件，打包出为不同目的服务的静态文件。前面介绍了两种设定模式的方式：一是运行不同命令时默认帮你设定，比如 serve 就是 development；二是使用 cross-env 在运行 npm script 时强行设定。这节课学习第三种方式，最终来解决我们的问题。

## 问题回顾

目前只有一个环境变量 NODE_ENV 来区分是什么环境，但我们有一个特殊的 staging 预发布环境：它本身是 production 环境，分支会走 production，但它的 URL 需要使用测试后端的地址。所以我们可能需要另外添加一个环境变量，再次区分是不是 staging 环境。这种情况下，就需要一个特殊的文件，称之为 .env。

## 环境变量文件的加载规则

在项目根目录中放置这种类型的文件，可以指定环境变量。文档写得比较细致，按从笼统到细分：

- `.env`：在所有环境下，也就是运行任何 vue-cli-service 命令时都会被载入；
- `.env.local`：同样在所有环境被载入，但会被 git 忽略，不会提交到仓库；
- `.env.[mode]`：只在指定的模式中被载入；
- `.env.[mode].local`：同上，但也会被 git 忽略。

一个环境文件中应该只包含环境变量的键值对，比如 `foo=bar`，前面是变量名称，后面是值。特别注意：不要在应用程序中储存任何机密信息，比如私有的 API 密钥，这是为了安全性考虑，因为这个文件有可能是对外可见的。

## 实践：在 development 模式中注入变量

我创建了一个 .env.development 文件，根据文档，它只在 development 模式中加载，也就是运行 npm run serve 时注入。添加两个变量：一个是 NODE_ENV，故意设置为 production，来做一次乱点鸳鸯谱的测试；另一个是自定义变量 VUE_APP_FOO，值设置为 hello。

```ini
NODE_ENV=production
VUE_APP_FOO=hello
```

然后在 main.ts 中添加对应的 console，自定义变量同样在 process.env 上。特别注意：修改完任何环境变量之后，需要重新执行命令（比如 npm run serve），才会拿到最新的结果。

重启之后可以看到，check 打出 production，说明 NODE_ENV 变成了 production；另一个环境变量 foo 也完美显示出来。同时页面会报一个服务器的错误，因为我们把它设置成 production，它就使用了正式地址 api.opsflow.com，而这个正式服务器地址不支持跨域访问，所以出现错误，符合预期。

## 环境变量的优先级

现在有三种定义环境变量的方式，它们的优先级是怎样的？再来做一个实验：在 package.json 的测试命令里用 cross-env 直接把 NODE_ENV 设置成 development，和 .env.development 里的 production 对比，看谁覆盖谁。

修改完毕重新启动，check 变成了 development，foo 还能打出来，值是 hello。从这个例子不难分析出环境变量的优先级：最高的是命令行上用 cross-env 直接设定的环境变量；第二是 .env.[mode] 环境变量文件中设定的；最低是运行命令时默认的 mode。

照这么分析，我们离最终目的已经不远了：既然可以拿到除 NODE_ENV 以外的任何环境变量，就可以在 staging 环境中给它设置一个独特的环境变量，和正式的生产环境加以区分。

## 一个神奇的现象

那么在 .env 这种所有模式都载入的文件里添加的变量，是否都可以使用呢？随便添加一个变量试试：在 .env 里添加 `bar=bar`，并在 main.ts 里添加新的 console 输出。重启应用后，神奇的现象发生了：check 和 foo 都有值，而 bar 的值变成了 undefined，没法在客户端代码中使用和显示。
