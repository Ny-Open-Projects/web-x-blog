上节课总览了本周的内容和知识点，这节课正式进入后端世界，开始服务器端的开发。在开始写代码之前，和前端开始时的流程一样，需要有一个技术方案设计的过程，流程和之前遵循的一致。

再次强调一下技术方案的重要性。第一，它是架构师的必备能力，是区分基础程序员和架构师的重要指标。同时从实用角度讲，技术设计不会浪费你的时间，只能为你节省时间，所以必须正视它。另外，技术方案设计需要从宏观角度把控，从整体出发，没必要下探到细枝末节。比如一个具体的需求到底要不要使用第三方库、要不要使用 Lodash，这些不需要在技术方案设计中体现。

从哪里开始？前后端分离项目的后端，任务是提供 RESTful API 供前端使用。所以第一步要知道要完成哪些接口，也就是一个接口设计文档。有了这个文档，我们才有可以提供给其他应用使用的最终产出。这节课的概念会比较多，我会尽量从简地讲解，因为大家更喜欢真刀实枪地写代码，对设计和文档普遍感觉弱一些。

完成接口文档的第一步是做需求分析。需求分析在第二阶段前端开始的部分已经用 OpsFlow 主站做过具体的分析，得出了的一系列实体的需求。不过前端是从 UI 和交互进行分析，到了服务器端要抛开 UI 交互，从数据的实体出发来分析。这里我直接给大家下结论，大家去使用这个系统也能得出类似的需求，或者看我们的需求文档都可以。相对于前端，后端的复杂度并不高，都是比较常规的内容。这里从实体出发，实体之间的相互关系也比较明晰。不过在内容设计中我会故意添加一些知识点，把整个项目的覆盖度在广度和深度上提到新的水平，来匹配复杂项目这个概念。

简单过一下需求。第一个拆分出来的需求是用户。用户系统第一个就是创建用户，也就是注册。最简单的是邮箱和密码注册，然后做扩展，希望用多种方法完成注册，常用的还有手机加验证码，自然还有一个验证码获取的过程。除了这两种，还有一种很流行的注册方式是 OAuth，比如用微信注册、用 GitHub 注册，可以很快捷地获取用户信息，这里我们选择 GitHub 来完成 OAuth 注册。特别注意：手机验证码和 OAuth 方式都是注册即登录，使用注册的过程也就完成了登录；而邮箱密码需要一个单独的登录过程，所以登录部分要有邮箱密码登录的步骤。注册登录完毕之后，首先是获取用户信息，注册完应该有一个接口提供获取用户信息，然后是修改用户。

接下来是最重要的作品。作品首先是创建，一开始是创建空白作品，还可以复制作品，也就是使用模板进行创建，直接获取模板中的数据。创建完毕后，可以查询自己的作品列表，可以查询单个作品，还可以保存作品、删除作品。然后有两个发布：发布作品指的是当作品修改完毕、觉得比较完美以后，可以发布成一个作品，供大家通过 H5 server 进行浏览；还可以发布为模板。模板和作品的区别在于同一个实体，只有一个 flag 做区分。变成模板以后，可以添加到模板列表，供别人使用和展示。所以模板这里很简单：一个是首页的模板列表接口，一个是单个模板信息，点击进去会到单个模板页。

再接下来是渠道，更简单。渠道是依附于作品的一个特殊信息，一个作品可以有多个渠道，每个渠道可以创建一个单独的链接供用户分享，比如微信渠道分享到微信、支付宝渠道分享到支付宝。接口就四个：创建、删除、修改，还有获取单个作品的所有渠道，因为它是一对多的。

最后是工具类。第一个是上传文件，主要是照片。为了扩展大家的知识面，我们会讲本地上传，还可以使用 OSS 做云服务上传。上传完还要讲图片处理，这是很常见的需求，比如裁剪、缩放等。另外有一个暂不考虑的部分：后端有一个接口提供预览以及直接展示作品的功能，但它不是一个标准的 RESTful 接口，而是直接展示一段 HTML 代码，这里还涉及 SSR 的知识，后面再讲解。通过这个列表，我们就把所有功能点进行了拆分。

接下来有一个要特别注意的点：在接口分析中需要提前预知一个问题，就是权限设置。对一个复杂的后端系统，权限控制必不可少，这在课程中也是比较有亮点的知识点，后面会着重笔墨解释它的实现手段。权限简单来说，就是一个用户能看到哪些数据、能操作哪些功能。在一开始的编码过程中权限先暂不考虑，随着课程的推移慢慢加上，这里预先提出来是让大家对它有预先的认知。

我们把权限划分为几个层级。第一层级：有些接口只有登录用户才能访问。比如注册、登录这些接口不需要登录就可以访问，而修改、获取用户信息需要登录才可访问。第二层级：有些接口只允许登录用户更新或删除自己的资源。比如删除作品，请求里带着一个作品 ID，但你不可能去删别人的作品，所以这里要有权限控制，预先判断当前用户是否有权限。第三层级更细：只能更新特定的字段。比如修改用户信息，里面有很多字段，但我们可能只想让它修改 username，密码不能直接修改，role 角色可能也不能直接修改。第四层级是管理员，最强的权限，可能可以获得所有接口的操作权。

这节课我们完成了需求分析，把需求拆分成了系列需求点。后端的需求和前端相比要稍微简单一些，并且更明晰，每个需求几乎和一个接口一一对应。完成需求分析后，下节课开始接口设计的下半部分，同时完成整个接口文档的内容。
