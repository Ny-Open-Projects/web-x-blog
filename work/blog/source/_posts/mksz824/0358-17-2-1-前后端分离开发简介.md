前面的内容一直在和编辑器的交互、功能打交道，现在编辑器已经初具规模，是时候把后端环境请出来了。上一阶段介绍了后端 API 开发的过程，现在要把两者结合起来。

SPA（单页应用）出现以后，前端和后端可以平行工作，最后再进行接口联调和整合，这种工作方式就是前后端分离开发。大家对它应该非常熟悉了，工作中可能一直在用，所以这里只用一节简单描述，并说几个比较特殊的点。

## 前后端分离的流程

**第一步：定制接口。** 双方在最初按照需求讨论并定制接口、参数和返回数据，一般采用 RESTful 协议。本课程模拟了这个流程，我和后端老师真的开会讨论过。

**第二步：文档化。** 开会完毕后要把它文档化，记录在某个地方，方便其他工程师查询。在语雀中我们记录了「B端 server 主要接口」的文档，划分成一系列接口，还提供了 Postman 文件下载（Postman 一会儿介绍）。

**第三点要注意的：接口版本化。** 这也算 RESTful 协议的规范，每次升级后可以清楚查看变动和修改，这是 best practice。可以参考 Shopify 的 API version release notes，点进每个版本都能看到详细的发布信息：新增了什么接口、有哪些 breaking changes、修改了什么接口，方便回溯和参考。

**第四点很重要：使用工具实时查看和运行。** 前后端分离开发时，双方需要维护一份共同的文档来规定格式。对一个 RESTful API，我们要知道四件事：

1. **endpoints**：具体的路径或网址，比如一个获取球队信息的 URL；
2. **method**：用 GET、POST、PATCH 还是 DELETE；
3. **参数**：发送请求时参数在哪，URL 上的 query 还是 body 里的复杂信息。比如 parameters 里的 id，指当前球队的信息，string 类型；
4. **返回格式**：这是最关心的。成功时返回什么样的 JSON、key 有哪些；失败时比如 401 的响应长什么样。

光看文档维护起来繁琐、使用也不方便，没有归类、筛选、调试这些基本功能；想真实调试某个接口还得写代码或找别的工具。于是直接调试和分类管理的工具就出现了。

## 两个工具

**Postman**：很多人都在用，可以在官网下载。我们的文档也提供了对应的 JSON 文件，下载导入后可以看到按用户、作品、工具和渠道分类的 API。随便点开一个，比如「获取短信验证码」，可以清楚看到 URL 是什么、用什么方法、Header 和 Body 是什么，Body 里发送 JSON 格式、传一个 `phone_number` 参数，以及对应的响应内容。这是后面课程会持续使用的工具。

**Swagger**：一个在线工具。它和 Postman 很类似，区别是 Postman 偏客户端工具，而 Swagger 能根据代码里的注释直接生成一个 Web 应用（网站）。它同样提供分类功能，清楚展示请求 URL、需要的参数、参数的响应格式，并且支持实时调用：点击某个接口、Try it out、输入参数、点 Execute，实时的 Response Body 就返回了。

我建议在真实项目中一定要使用这一类工具来管理和查看、运行你的 API，就是 Postman 和 Swagger。

## 开发与联调

完成定制规范之后进入开发阶段。接口规范上双方使用 RESTful 协议；前端可以借助 Node 上现成的工具给自己提供 mock server。顾名思义，mock server 是假的 server，但它的接口规范、方法和最后后端真正的 server 完全一致。后面的课程会介绍这样一个工具，供大家在真实工作环境中使用。开发阶段我会直接使用真实接口，因为录制课程时后端已经全部开发完毕。

通过这种方式前端与后端可以并行开发，极大提高效率，分工也更明确。最后是联调阶段：前端切换成后端接口，进行功能校验就完成了联调，接着提测。

## 前后端分离的优点

1. **打造精益团队**：分离后前后端工程师只需专注各自的工作，可以培养独特的技术特性，构建全栈式的精益开发团队；
2. **提升开发效率**：前后端代码解耦，只需提供对应的接口参数就可以并行开发，不用串行等待，整个应用的开发效率会有质的提升；
3. **增强代码可维护性**：代码分离后不再混为一谈，只在运行时才产生调用关系。
