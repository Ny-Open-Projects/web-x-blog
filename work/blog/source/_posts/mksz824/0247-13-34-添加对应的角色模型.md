学习完 CASL 的基础知识后，这节课给 OpsFlow 后端项目添加关于 RBAC 的权限控制。第一步来到 User 用户模型，添加一个字段指示当前用户是什么样的角色。字段自然称为 role，类型确定成一个字符串字面量的联合类型：一种 role 是 admin，另外一种是 normal。暂定先有两种角色，以后有特殊需求再扩充。有了这个属性，在对应的 schema 中也要添加：role 的 type 是 string，default 默认当然是 normal。

确定完模型，新建一个文件，把所有和用户权限相关的界定都放在里面。我在 app/rules 文件夹下添加了 rules.ts，在这里面界定所有用户的权限和相关功能。照着上节课的例子，我们应该返回一个 defineRules 这样的函数。

首先把需要的内容拿过来，import { AbilityBuilder, Ability } from '@casl/ability'（这个包大家自己去安装）。然后需要拿到用户的 props 类型，因为函数中要传入这个类型，从上一层的 model/user 引入 UserProps。接着定义 export default function defineRoles，传入一个参数 user，类型是 UserProps。

第一步还是新建 AbilityBuilder：const { can, build } = new AbilityBuilder(Ability)，上面几节课已经讲过这段代码了。拿到 can 和 build 这两个方法后就可以添加逻辑。一开始要判断 user 存在，这是在登录用户那里才能使用的，所以它应该在 JWT 中间件之后使用，user 应该存在。user.role 等于 admin 的时候，就是系统管理员，写 can('manage', 'all')，所有资源都可以管理。

剩下的就是普通用户，写一个 else。假如日后扩展更多权限，这是一个完全可扩展的结构。现在只有 admin 和 normal user，这里称之为 normal login user。

第一个要确定的实体是 user。普通用户只能读取自己的信息以及更新特殊字段。can('read', 'user', { id: user._id })，condition 是 id 等于 user 的 _id，也就是说只能读取自己的信息。

写到这里我们发现 UserProps 并没有定义 id 字段，所以会报错。因为传入的不仅仅是 UserProps，它是一个 document，MongoDB 会在上面包装一系列的属性。所以假如想要类型完美的话，给它再添加一个类型，从 mongoose 中拿 Document，做一个交叉类型 `UserProps & Document`。Document 有三个泛型，前两个传入 any，第三个传入 UserProps。现在 id 就存在了，而且 user 作为一个 Document 上面还有一系列的方法。

说完读取，再说更新。它还可以 update，实体名称是 user，更新哪些字段就有意思了：这里只能界定它更新某些特殊字段，包括 nickname 和 picture。写法是 can('update', 'user', ['nickname', 'picture'], { _id: user._id })，也就是它只能更新自己的昵称和头像，其他的都不让更新。比如 password 肯定不能更新，type 和 role 等等也不能更新。condition 的 _id 表示只能更新自己的。

完成 user 的定义后，第二个实体是使用最多的 work。普通用户可以创建、更新和删除自己的 work。首先是 create：can('create', 'work', [...])。这里给 create 添加字段限制，是因为只能创建这几个字段，其他的字段不能进行创建；它不需要根据用户来界定，所以没有 condition。我直接复制字段列表过来。

然后是 read：can('read', 'work', { user: user._id })。它的外键，或者说指向 user 的引用属性叫 user，大家不要写错了。可以在 work model 上看一下，user 对应的就是我们的 user id，所以属性名称是 user。

update 除了只能操作自己的，还有字段的限制，把这些条件复制过来：can('update', 'work', [...字段], { user: user._id })，condition 也是自己的作品。最后 delete 很简单，不再重复写，复制过来，只能删除自己的作品。

还有一个 channels。channels 是一个比较特殊的数据结构，它其实是隶属于 work 的一个字段，但这里先不考虑其特殊性，按照规则把内容写在这里。规则跟之前一样，创建、更新、删除属于自己的 channel，直接把规则复制过来，不再重复写一遍。看一下它的规则：特别注意创建的时候有一个对应的 condition，因为 channels 隶属于 work，之前要检查 work 的信息。read 只能是自己的 channel，update 和 delete 也只能操作自己的 channel。

最后别忘了 return build()，整个 function 就书写完毕了。

这节课我们成功定义了对应的角色模型。把所有的角色信息汇总在这里非常方便而且明晰，角色的信息如果哪里出现问题，就可以在这里查找并归类。下节课看看怎样将对应的规则添加到代码中去。
