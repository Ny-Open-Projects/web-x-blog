## 纲要

- **指令生成器让你不用死记硬背**：超时、参数、丢弃旧构建这些配置，在页面上点选即可自动生成语法，粘贴即用
- **两个生成器分工不同**：**声明式指令生成器**生成块级配置（`environment`/`options`/`parameters`/`triggers`），**片段生成器**生成步骤级代码（`checkout`/`sh`/`sleep`/`cleanWs`）
- **正确用法是"看懂而非记住"**：生成后理解每行含义即可，新项目把脚本复制过去改 URL 和变量就能用
- **`triggers { cron(...) }` 是计划任务入口**：语法与 Linux crontab 完全一致——分 时 日 月 周
- **`H` 是 Jenkins 的哈希随机值**：让同一时刻的多个构建**错开分钟执行**，避免整点集中爆发压垮节点
- **不写 `H` 的后果很具体**：十个构建都配"每 15 分钟"，会全部在 0/15/30/45 分并行执行
- **自动触发的构建用户显示"自动触发"**：这是判断构建来源的重要标志

## 一、声明式指令生成器：不用背语法的底气

### 1.1 它解决什么问题

编写流水线脚本时，你要配超时、配参数、配丢弃旧构建……这些配置项参数繁多，**之前写的时候配置了超时、配置了重试，都可以通过在页面上进行指定生成**。

> 课件原话：**所以我们不需要去死记硬背这些。我们只需要根据我们想要的功能，在页面上直接手动操作，生成就可以。**

这是 Jenkins 对新手最友好的功能之一——**把"记忆语法"变成"点选配置"**。

### 1.2 怎么用

**页面点击「生成流水线（Pipeline Syntax / 流水线语法）」→ 选中你要生成的配置 → 点击「自动生成」**。

可生成的配置覆盖几乎所有声明式块：

| 可生成项 | 对应配置 |
|---|---|
| `environment` | 环境变量 |
| `options` | 全局行为（丢弃旧构建、禁用并发等） |
| `parameters` | 构建参数 |
| `triggers` | 触发器（含 cron 计划任务） |
| `tools` | 工具（JDK、Maven 等） |
| `steps`（片段生成器） | 具体步骤（checkout、sh、sleep） |

### 1.3 实战一：生成一个环境变量

1. 生成器里选 `environment`；
2. 填变量名 `name`、值 `中`；
3. 点生成 → 得到：

```groovy
environment {
    name = '中'
}
```

4. 复制到 `pipeline { }` 或 `stage { }` 里即可。

### 1.4 实战二：生成 options 的丢弃旧构建

这是最实用的一个。手工写 `buildDiscarder(logRotator(...))` 参数容易记错，生成器点选即可：

1. 生成器里选 `options` → **丢弃旧的构建（Build Discarder）**；
2. 勾选 **保持构建天数为 7 天**、**保持最大的构建数为 20**；
3. 点生成 → 得到：

```groovy
options {
    buildDiscarder(logRotator(numToKeepStr: '20', daysToKeepStr: '7'))
}
```

4. 粘贴到流水线里——**只保留 7 天的构建日志，最多保留 20 个**。

> 课件强调的用法：**我们大概能看懂它是什么意思就可以。** 比如看到 `logRotator(numToKeepStr: '20',daysToKeepStr: '7')` 就知道是"保留旧构建日志"，不需要记参数名。

### 1.5 片段生成器：步骤级代码一键生成

除了声明式指令生成器，还有**片段生成器（Snippet Generator）**，专门生成具体步骤。可生成的操作包括：

- **拉取代码**（`checkout` / `git`）
- **执行命令**（`sh`）
- **睡眠**（`sleep`）
- **清理工作空间**（`cleanWs`）
- **报错处理**等

**实战：生成拉取代码**

```groovy
// 生成器产物，改 URL 即可复用
checkout([$class: 'GitSCM', branches: [[name: '*/main']],
          extensions: [],
          userRemoteConfigs: [[url: 'http://gitlab.example.com/golang/go.git']]])
```

**实战：生成 sleep**

```groovy
sleep 10          // 睡 10 秒
// 或
sleep(time: 10, unit: 'MINUTES')   // 睡 10 分钟
```

**实战：生成清理工作空间**

```groovy
cleanWs()
```

### 1.6 真正的价值：新项目快速复制

课点破了这个功能的终极用法：

> 如果我们有新的项目、新的构建项目的话，**我们只需要把这个流水线脚本复制过去，然后再稍微改动一下就可以。**

具体做法：

1. 老项目的 `Jenkinsfile` 整份复制到新项目；
2. 用片段生成器重新生成 `checkout`，**把 URL 改成新仓库**；
3. 用指令生成器调整 `options` / `parameters`；
4. 完成。

**不用从零写，也不用背语法。** 这就是生产环境里流水线模板化的标准做法——一个基础模板 + 每项目改几个变量。

## 二、计划任务：triggers + cron

### 2.1 语法与 Linux crontab 完全一样

流水线的计划任务通过 `triggers` 方法定义：

```groovy
pipeline {
    agent any
    triggers {
        cron('* * * * *')        // 示例：每分钟
    }
    stages {
        ...
    }
}
```

**五个字段的含义与 Linux 计划任务一致**：

| 字段 | 取值范围 | 含义 |
|---|---|---|
| 分 | 0 ~ 59 | 分钟 |
| 时 | 0 ~ 23 | 小时 |
| 日 | 1 ~ 31 | 一个月中的第几天 |
| 月 | 1 ~ 12 | 月份 |
| 周 | 0 ~ 7 | **0 和 7 都代表星期天** |

### 2.2 `H`：Jenkins 独有的哈希随机值

`cron` 里有一个 Linux crontab **没有**的符号——**`H`**。

> 课件解释：**`H` 就代表哈希值（hash）。哈希值就代表可能你是在不同的时间来进行执行，它是随机的。**

**它解决什么问题？**

假设你有**十个构建**，都配置了"每 15 分钟执行一次"：

- **不写 `H`**：全部默认从 **0 分、15 分、30 分、45 分**开始执行 → **十个构建在同一分钟并行爆发，加大服务器负载**；
- **写了 `H`**：构建 A 可能在 1 分、22 分、37 分、52 分；构建 B 可能在 6 分、21 分、36 分、51 分……**每个构建的起始分钟被哈希打散**，不会都挤在同一分钟。

> **一句话：`H` 是 Jenkins 给批量定时任务提供的负载均衡手段。项目一多，它是必选项。**

### 2.3 五个实战配置逐条拆

**① 随机分钟，每 15 分钟一次**

```groovy
cron('H/15 * * * *')
```

含义：每隔 15 分钟执行一次，但**起始分钟随机**（不是固定从 0 分开始）。

**② 随机分钟，每 10 分钟一次（仅前半小时）**

```groovy
cron('H H(0-29) * * *')
```

含义：分钟的 0~29 范围内，每隔 10 分钟执行一次。因为小时限定了 `0-29`，所以是**前半个钟每 10 分钟一次**，起始时间随机（可能从 4 分开始，也可能从 24 分开始）。

**③ 工作日固定时段，每 2 小时一次**

```groovy
cron('45 9-16/2 * * 1-5')
```

含义：**周一至周五，9:45 到 16:45，每隔 2 小时执行一次**。

推算执行时间：9:45 → 11:45 → 13:45 → 15:45，**一共四次**。

**④ 工作日，每 2 小时一次，时间随机**

```groovy
cron('H H(9-16)/2 * * 1-5')
```

含义：**周一至周五，9 点到 16 点，每隔 2 小时执行一次**，但**起始时间不固定**（可能从 9 点多开始，也可能从 10 点多开始）。

**⑤ 每月 1 号和 15 号，随机时分**

```groovy
cron('H H 1,15 1-11 *')
```

含义：**每月 1 号和 15 号执行，随机分钟、随机小时**，月份范围 1~11 月。

### 2.4 五种配置对照表

| 表达式 | 语义 | `H` 的作用 |
|---|---|---|
| `H/15 * * * *` | 每 15 分钟 | 打散起始分钟 |
| `H H(0-29) * * *` | 前半小时每 10 分钟 | 打散起始分钟 |
| `45 9-16/2 * * 1-5` | 工作日 9:45-16:45 每 2 小时 | 无 `H`，时间固定 |
| `H H(9-16)/2 * * 1-5` | 工作日 9-16 点每 2 小时 | 打散小时 |
| `H H 1,15 1-11 *` | 每月 1/15 号 | 打散时分 |

### 2.5 实操验证

```groovy
pipeline {
    agent any
    triggers {
        cron('* * * * *')          // 每分钟执行一次（仅为演示）
    }
    stages {
        stage('Demo') {
            steps {
                sh 'date'
            }
        }
    }
}
```

课件实操：保存后**等待一分钟，下一分钟自动执行**。点进去看构建详情，可以看到**构建用户显示"自动触发"**。

> **这个细节很有用**：看到"自动触发"就知道这次构建来自 cron/ webhook，而不是某人手动点的——排查"谁动了线上"时这是第一手线索。

## 三、常见报错与排查

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 定时构建不执行 | `cron` 写错，或 Jenkins 时区不对 | 检查五字段；系统配置里校时区 |
| 多个构建同一分钟爆发 | cron 没写 `H` | 起始字段改 `H` 或 `H/interval` |
| `H(0-29)` 不生效 | 语法写错 | 必须是 `H(范围)` 形式 |
| 生成的语法粘贴后报错 | 复制不完整或位置错 | `options`/`triggers` 放 `pipeline` 层，`environment` 可放两层 |
| 自动触发看不出是谁 | 未记录触发源 | 报警里带 `BUILD_URL` + `GIT_COMMIT`；必要时装 Build User |
| `sleep` 参数不识别 | 用了错误形式 | `sleep 10` 或 `sleep(time:10,unit:'MINUTES')` |

## 四、面试考点与追问

**Q1：Jenkins 的 `cron` 与 Linux crontab 有什么区别？**
五个字段（分时日周）语义完全一致，但 Jenkins 多一个 **`H`（哈希值）**符号，表示在该字段取值范围内随机取一个值，用于把多个构建的执行时刻打散，避免同一时刻集中爆发。

**Q2：`H/15 * * * *` 与 `*/15 * * * *` 的差别？**
`*/15` 固定从 0 分开始，每 15 分钟一次（0/15/30/45）；`H/15` 的起始分钟由 Jenkins 哈希决定，随机打散。项目少时无差别，项目多时 `H` 能显著降低整点负载峰值。

**Q3：如果有 10 个构建都配了每 15 分钟一次，不写 `H` 会怎样？**
十个构建会在 0/15/30/45 四个时刻同时启动，十份构建并行争抢 executor 与节点资源，可能导致全部变慢、排队甚至 OOM。写 `H` 后每个构建的起始分钟不同，负载被摊平。

**Q4：声明式指令生成器和片段生成器的区别？**
**声明式指令生成器**生成块级声明式配置（`environment`、`options`、`parameters`、`triggers`、`tools`）；**片段生成器**生成步骤级代码（`checkout`、`sh`、`sleep`、`cleanWs`）。前者配"结构"，后者配"动作"。

**Q5：新项目搭建流水线时，怎么用生成器提高效率？**
复制老项目 `Jenkinsfile` 作模板 → 用片段生成器重新生成 `checkout` 并改 URL → 用指令生成器调整 `options`/`parameters` → 通读一遍理解每行含义。不需要从零写，也不需要背语法。

**Q6：怎么区分一次构建是手动触发还是自动触发？**
看构建详情里的"构建用户"——自动触发（cron/webhook）显示"**自动触发**"，手动触发显示操作人。报警里带上 `BUILD_URL` 与 `GIT_COMMIT` 可以进一步定位来源。
