# 1247 深度分页问题总览：为什么 LIMIT m,n 在大 m 时慢

> 分类：MySQL/分页 | 难度：L2 | 题型：概念题 | 频率：高 | 关键词：**深度分页**/**LIMIT m,n**/**OFFSET 放大**/**回表**/**游标分页**/**覆盖索引**
> 原文锚点：第 49~56 段「深翻页主要代价在回表、按主键与按二级索引两类优化收口」

## 一句话总述
**深度分页**指翻到很靠后的页（`LIMIT m, n` 中 m 很大）。其性能瓶颈不在 n（取几行），而在「引擎要先定位/跳过前 m 行」——若排序无法索引内完成则需 filesort，且每行常要回表取全字段，m 越大 IO 放大越严重。优化方向只有两条：**按主键游标分页**或**按二级索引覆盖索引两查询拆分**。

## 面试官视角
- 考察意图：能否说清深翻页慢的根因，并据此推导两类优化，而非背「用 id 代替 LIMIT」。
- 分档：P5 知 `LIMIT m,n` 大 m 慢；P6 能量化「跳过 m 行 + 回表」两步代价；P7 能按排序键类型分流到两种解法并讲边界。
- 红旗答案：把慢因只归为「扫描行多」不提回表/排序；把游标分页当成万能、不知非主键排序退化。
- 惊艳点：点出「代价主体在前 m 行的回表而非最后的 n 行」，以及「解法选择由排序键是否为主键决定」 [经验]。

## 主问答
**Q（面试官原话）：** 什么是深度分页？为什么越翻越慢？
**A：**
1. **定义**：`LIMIT m, n` 中 m（跳过的行数）很大即为深度分页，常见于「跳到第 100 万页」或全表批量导出 [经验]。
2. **慢因两步**：① 引擎需先定位并跳过前 m 行，若 ORDER BY 无合适索引要走 filesort；② 每行要回表取 SELECT 全字段，m 越大回表行数越多，IO 近似 O(m+n) [经验]。
3. **两类解法**：排序键是**主键**→游标分页 `WHERE id > miniID`（见 1247）；排序键是**二级索引**→覆盖索引两查询拆分（见 1247）[经验]。

## 关键代码

```sql
-- 深翻页慢因对比（m 越大差距越大）
-- 慢：前 m 行全回表取全字段，m 接近全表时近乎扫全表
SELECT * FROM user ORDER BY name LIMIT 1000000, 10;

-- 快（按主键游标）：无 OFFSET，顺序扫 + 只回查本批 k 行
SELECT * FROM user WHERE id > :miniID ORDER BY id LIMIT 10;

-- 快（按二级索引）：第一查询只取 id 走覆盖索引，第二查询 IN 回查全字段
SELECT id FROM user ORDER BY name, id LIMIT 1000010;
SELECT * FROM user WHERE id IN (?,?,?,?,?,?,?,?,?,?);
```

## 总结与追问预判
深度分页的核心是「前 m 行的跳过 + 回表」而非末 n 行。优化本质是把 O(m+n) 回表降为 O(索引扫 m + k 回查)。前端「任意跳第 N 页」需求与游标分页冲突，需额外书签/预计算，是常见追问点。
