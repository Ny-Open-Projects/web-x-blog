# 1237 Supremum 伪记录：被忽略的最大区间

> 分类：MySQL / InnoDB | 难度：L4 | 题型：陷阱题 | 频率：中高 | 关键词：**Supremum、虚拟记录行、插入意向锁、字符串序**

> 原文锚点：第 48~92 段「最大的虚拟记录行也被加了临键锁…为什么插入 id=22 能成功」

## 一句话总述
每个索引页末尾有一条虚拟的最大记录（Supremum），等值命中最大值时它同样被加临键锁，锁住 `(最大索引值, +∞)`；注意这个"最大"是**该索引列的值**，与主键 ID 毫无关系。

## 面试官视角
P6 会答"最大虚拟行锁住整张表后半段"；P7 要立刻纠正：锁区间是建在**二级索引**上的，判断插入能否成功要看插入行的**索引列值**落在哪 `[经验]`。原文那个反直觉实验——自增 ID 已到 22，插入 id=22 竟然成功——就是这条判据的最好佐证 `[源码]`。

## 主问答
**Q（面试官原话）：** 最大虚拟行都加锁了，为什么还能插进去一条数据？

1. **区间在索引列上**：锁住的是 `(name=7, +∞)`，用**索引列的值**比较，不是主键 ID `[源码]`。
2. **字符串按编码序排**：原文 name 为 1、2、20、3、4、5、7，按编码序 22 落在 20 与 3 之间，**小于 5**，落在锁定区间左侧 `[实测]`。
3. **所以 id=22 插得进**：虽然主键值很大，但索引列值 22 不在锁定区间内，插入直接成功 `[经验]`。
4. **改成就插不进**：把索引列改成 9（编码序大于 7）即落入锁定区间被阻塞，锁视图中随即出现**插入意向锁** `[实测]`。

## 关键代码
```sql
-- 事务 A 持有 name=7 的临键锁（含 Supremum）
BEGIN; SELECT * FROM t WHERE name='7' LOCK IN SHARE MODE;
-- 事务 B：索引列值 22 < 5，成功
INSERT INTO t(id, name) VALUES (22, '22');
-- 事务 B：索引列值 9 > 7，阻塞，出现插入意向锁
INSERT INTO t(id, name) VALUES (23, '9');
```
```go
// 判据只看索引列，不看主键
locked := strings.Compare(insertName, "7") > 0 // 用列排序规则比较
```

## 总结与追问预判
**加锁区间建在哪个索引上，就用哪个索引的列值比较**。把这条说清，等值加锁这一章就通了。
