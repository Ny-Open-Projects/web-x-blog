# 129 移除查询缓存（一）：命中率低

> 分类：MySQL 内核 | 难度：L3 | 题型：分析题 | 频率：中 | 关键词：**命中率**/**SQL 哈希**/**空间固定**
> 原文锚点：第 22~27 段「第一个原因：命中率不高…空间固定、相同语句概率低」

## 一句话总述
移除原因①**命中率低**：缓存 key 是 SQL 哈希，大小写/空格/注释任一不同即视为不同查询；缓存空间固定、高并发下很快因空间不足而淘汰；用户短期内执行**完全相同**语句的概率本就不高；大结果集、自定义函数等场景还压根不缓存——三重叠加，命中率天然偏低。

## 面试官视角
- 考察意图：能否从"key 设计 + 容量 + 使用模式"三个角度论证命中率必然低。
- 分档：P5 知命中率不高；P6 能讲出 key 苛刻 + 空间固定；P7 能结合"相同语句概率低"做定量直觉。
- 红旗答案：只说"命中率低"却不解释为什么低。
- 惊艳点：点出 **"完全相同 SQL 的概率低"是统计事实**——业务里参数、注释、空格稍有差异就 miss `[经验]`。

## 主问答
**Q（面试官原话）：** 为什么查询缓存命中率不高？
**A：**
1. **结论**：key 苛刻 + 容量固定 + 重复概率低，三者共同压低命中率。
2. **机制**：① key=SQL 文本哈希，任何字符差异都 miss；② 缓存区（`query_cache_size`）固定，高 QPS 下迅速被填满并淘汰旧项；③ 真实业务很少短时间内发两条**逐字符相同**的 SQL，且大结果集/自定义函数等本就不缓存。
3. **边界**：只有"读多写少、且 SQL 模板高度固定"的场景（如极少变更的配置表）命中率才划算——但这类场景本就少。

**加分层：** 低命中率意味着"为少数命中付出全量管理成本"，是投入产出比问题。

## 关键代码
```sql
-- 两条"语义相同但文本不同"的语句，缓存视为两次不同查询
SELECT * FROM t WHERE id = 1;
select  *  from  t  where  id = 1;  -- 空格/大小写不同 → 不同 key
```

## 总结与追问预判
低命中率 = key 苛刻 × 容量固定 × 重复概率低。追问接"更易失效的表级失效"与"管理开销/性能不可预测"。
