# 418 有符号整型溢出：反转成最大负数与四类判据

> 分类：Go 数值类型 | 难度：L3 | 题型：陷阱题 | 频率：高 | 关键词：**符号反转**/**MaxInt64+1**/**MinInt64**/**溢出判据**/**资损风险**

> 原文锚点：第 53~70 段「有符号溢出反转 / 四类判断条件 / 业务风险」

## 一句话总述
有符号整型溢出会**符号反转**：`math.MaxInt64 + 1` 变成 `math.MinInt64`。因为补码下负数比正数多一个，最大值再进一位就落到最小负数。金融、积分、金币场景里这会让「应扣减」变成「加上一个大值」，必须在运算前拦截。

## 面试官视角
这题的落点不是「结果是负数」，而是**你能不能写出不溢出的判据**。考官会盯着你写 `x+y > MaxInt64`——那是错的。正确写法是把加法改写成减法：`y > 0 && x > math.MaxInt64-y`。

## 主问答
**Q（面试官原话）：** int64 最大值加 1 会怎样？怎么判断会不会溢出？

1. **结果是最小负数**：`math.MaxInt64 + 1` 溢出后变成 `math.MinInt64`，符号发生反转，而不是报错。
2. **反转有据**：补码下负数范围比正数多一个，最大值继续进位正好落到最小负数的编码上。
3. **判据一（加正数）**：当 y > 0 时，若 `x > math.MaxInt64 - y`，则 x+y 必然溢出上界。
4. **判据二（加负数）**：当 y < 0 时，若 `x < math.MinInt64 - y`，则 x+y 必然溢出下界。
5. **业务后果**：不做校验时，本该扣减的积分或金币可能变成加上一个大值，直接造成资损，因此必须先判后算。

## 关键代码
```go
package main

import (
	"errors"
	"fmt"
	"math"
)

func addInt64(x, y int64) (int64, error) {
	if y > 0 && x > math.MaxInt64-y {
		return 0, errors.New("int64 overflow")
	}
	if y < 0 && x < math.MinInt64-y {
		return 0, errors.New("int64 underflow")
	}
	return x + y, nil
}

func main() {
	v, err := addInt64(math.MaxInt64, 1)
	fmt.Println(v, err) // 0 int64 overflow

	x := int64(math.MaxInt64)
	fmt.Println(x+1, x+1 == math.MinInt64) // [实测] 输出：-9223372036854775808 true
}
```

## 总结与追问预判
核心：**反转不报错，先判后算；判据用减法写**。追问常拐向「原文说的四个条件怎么化简」「乘法怎么办」，备好「四条实为按 y 正负对称展开，保留两条即可」与除法判据。

## ⚠️ 原文纠错
1. 事实核校： [经验] 原文列举的四个判断条件本质上只有两类，是按 y 的正负做的对称展开；实现时保留 `y>0` 与 `y<0` 两条即可覆盖，四条反而易漏写。
2. 事实核校： [经验] 原文称反转会造成「更大的安全漏洞」——更准确的定性是**资损风险**：本应扣减的金额或积分反向变成大额增加，属业务事故而非内存安全问题。
3. 崩坏词归一：源码将 int64 / MaxInt64 / 溢出 等音译为多组崩坏词，本卡统一为规范术语。
