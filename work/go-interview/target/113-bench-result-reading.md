# 113 基准结果怎么读：ns/op、B/op 与 allocs/op

> 分类：Go 测试 | 难度：L3 | 题型：实操题 | 频率：高 | 关键词：**ns/op**/**B/op**/**allocs/op**/**b.N 自动校准**/**-8 后缀**

> 原文锚点：第 31~43 段「结果字段与执行次数」、第 50~53 段「内存分配指标」

## 一句话总述
输出形如 `BenchmarkF1-8  76  15123456 ns/op`：后缀 `-8` 是**逻辑 CPU 数**，76 是本次的 `b.N`，`ns/op` 是每次操作耗时；加 `-benchmem` 后多出 `B/op`（每次分配字节数）与 `allocs/op`（分配次数）。默认跑满 1 秒，函数越快则次数越多。

## 面试官视角
考官要的是「你能不能看着输出说出结论」。能解释后缀数字、知道 b.N 由框架自动校准、**并且指出手动改 b.N 是反模式**，这题就完整了。内存两列常被忽略，主动讲是加分。

## 主问答
**Q（面试官原话）：** 基准测试的输出每一项是什么意思？

1. **后缀是核数**：`BenchmarkF1-8` 中的 8 表示运行环境有 8 个逻辑 CPU，即本次的 GOMAXPROCS。
2. **次数是 b.N**：第二个数字是循环执行的次数，也就是 b.N 的值；由框架自动决定。
3. **每次耗时**：`ns/op` 是每执行一次被测函数平均花费的纳秒数，是横向对比的核心指标。
4. **自动校准**：默认每个基准函数执行 1 秒，函数越快则次数越多；指定更长时间会得到更多样本。
5. **内存两列**：加 `-benchmem` 后输出每次操作分配的字节数与内存分配次数；纯休眠类函数这两项接近 0。

## 关键代码
```go
package demo

import (
	"testing"
	"time"
)

func F1() { time.Sleep(10 * time.Millisecond) }
func F2() { time.Sleep(20 * time.Millisecond) }

// go test -bench=. -benchmem
// 期望：F1 的 ns/op 约为 F2 的一半，两者 B/op 都接近 0
func BenchmarkF1(b *testing.B) {
	for i := 0; i < b.N; i++ {
		F1()
	}
}
```

## 总结与追问预判
核心：**ns/op 比快慢、B/op 与 allocs/op 看内存、后缀看核数**。追问常拐向「怎么让结果更可信」，备好「加长 -benchtime、多跑几次取中位数、固定机器」三条。

## ⚠️ 原文纠错
1. 事实核校： [经验] 原文演示「把 b.N 改成 100 强制两个函数各跑 100 次」——**能跑但属反模式**。b.N 由 testing 框架根据 -benchtime 自动校准（先小样本试跑再倍增），手动写死会破坏校准，使不同函数、不同机器之间的结果失去可比性；正确做法是用 `-benchtime` 控制时长。
2. 事实核校： [经验] 原文示例 f1 只休眠 10 毫秒，实测却约 15 毫秒每次、1 秒约 76 次——差值来自调度与计时开销，属正常；可借此说明 ns/op 包含真实运行开销，不等同于纯逻辑耗时。
3. 崩坏词归一：源码将基准测试 / ns/op / 内存分配 等音译为多组崩坏词，本卡统一为规范术语。
