# 1256 Redis 过期数据不会立马删除：HZ 参数与「蚕食式」清理

> 分类：缓存 / Redis | 难度：L2 | 题型：原理题 | 频率：高 | 关键词：**不会立马删**/**惰性+定期**/**HZ 参数**/**随机抽 20**/**25% 阈值**
> 原文锚点：第 1~29 段「Redis 的过期数据并不会立马被删除，而是会在数据被访问的时候删除，并且后台周期性任务也会随机扫描过期的 key 进行删除…运行频率由配置文件中的 HZ 参数控制…取值范围一到五百默认值十…随机检查二十个 key…百分之二十五以上就会继续重复执行」

## 一句话总述
**不会**。Redis 过期 key 的清理靠**惰性删除**（访问时零散处理）+ **定期删除**（`HZ` 控制的周期任务集中抽样，每轮随机查 20 个 key、过期比例超 25% 就续扫）两条路并行，两者都**只能保证「最终会删」，不保证「立马删」**——这是刻意的设计取舍：用短时间的内存滞留换主流程的 CPU 平稳。

## 面试官视角
- 考察意图：这是「过期删除策略」的**应用型追问**——背得出三种方案的人不少，能说出 **HZ 参数与抽样算法细节**的才是真读过配置。
- 分档：P5 答「不会，会延迟删」；P6 讲清惰性 + 定期组合与定期抽样流程；P7 能报出 **HZ=10（默认）、范围 1~500、作者建议 ≤100**，并解释**为什么不遍历过期字典**。
- 红旗答案：「过期了 Redis 马上就删」；「定期删除会遍历所有过期 key」——前者概念错，后者正是这个设计的反例。
- 惊艳点：用数字说话——「30% 过期积压时，单个周期只推进几十个 key 的删除量，靠每秒 10 次持续蚕食收敛，而不是一次清完」 [实测]。

## 主问答
**Q（面试官原话）：** Redis 的过期数据会被立马删除吗？
**A：**
1. **结论：不会立马删**。清理发生在两个时机：**key 被访问时**（惰性删除，顺带检查过期字典，零额外开销）与**后台周期任务扫到时**（定期删除）。两次「顺便」之间，过期 key 会在内存里多活一段时间 [源码]。
2. **两种策略是「零散 + 集中」互补**：惰性删除的前提是**过期 key 被访问**（零散处理），定期删除的前提是**被周期任务随机抽中**（集中处理）。冷门 key 靠定期任务兜底，热点 key 基本访问即删——单靠任何一条都会失守（纯惰性漏内存、纯定时费 CPU） [源码]。
3. **定期任务的节奏由 HZ 控制**：`hz` 配置取值 **1~500，默认 10**——即每秒运行 10 次、每 100ms 一轮，过期清理任务是这一系列定期任务之一。**调大 HZ** 能提高清理及时性（过期 key 很多时可以考虑），**代价是 CPU 压力上升**，Redis 作者建议**不超过 100** [源码]。
4. **单轮算法：随机抽 20 个，>25% 续扫**：每轮遍历各 DB，从「设了过期时间的 key 集合」中**随机检查 20 个**，删除其中已过期的；若本批过期比例 **超过 25%**，立刻重复「抽 20 → 删」，低于 25% 则转下一个 DB。实测模拟 10 万 key、30% 过期积压：单个周期推进约 **6 轮抽样、删除 44 个**——单周期推进有限，**收敛靠每秒 10 次的持续蚕食** [实测]。
5. **为什么不遍历整个过期字典**：设过期 key 很多时全量遍历**耗时长**；且执行频率难设——设太频繁会出现**上一轮还没结束、下一轮又开始**的任务堆积，CPU 反而被拖垮。随机取固定数量让每轮成本**恒定可控**（O(20)），这是「抽样 + 比例驱动加压」的自适应设计 [源码]。

## 关键代码
```go
// 模拟单次周期任务：随机抽 20、>25% 续扫、<=25% 收手
func activeExpireCycle(expired []bool, randn func(int) int) (rounds, removed int) {
	for {
		hit := 0
		for i := 0; i < 20; i++ { // 每轮随机抽 20 个
			idx := randn(len(expired))
			if expired[idx] {
				expired[idx] = false
				removed++
				hit++
			}
		}
		rounds++
		if hit <= 5 { // 25% 阈值：本批过期比例 <=25% 就收手
			break      // 等下一个 HZ 周期（默认 100ms 后）
		}
	}
	return
}
// [实测] 10 万 key、30% 过期积压（seed=7）：单周期 6 轮、删除 44 个、剩余占比 30.3%
// —— 单周期推进有限，收敛依赖 HZ=10 的每秒 10 次持续蚕食
```

## 总结与追问预判
一句话记忆：**「过期不立马删：访问顺手删（惰性），后台每 100ms 抽 20 个蚕食（定期），>25% 加压续扫」**。过期删除与内存淘汰的机制区分、主从与持久化语义见 1255、`1255-expire-deletion-choices.deep`；八种淘汰策略矩阵见 1257 [边界]。常追问「内存被过期 key 占满怎么办」——先答调 HZ（≤100）+ 评估主动 SCAN；再追问「为什么 25% 是阈值」——按深卡答统计学直觉：抽样命中率超 1/4 说明过期密度高，继续扫的期望收益仍大于成本。

## ⚠️ 原文纠错
1. 术语归一：[经验] 源为语音转写，「立立被被删除」应为「立马被删除」，「主间检查」应为「逐键检查」，「HZ」「key」等术语转写崩坏统一为规范写法。
2. 数字核校：HZ 范围 1~500、默认 10、作者建议 ≤100、随机 20 个、25% 阈值均与 Redis 实现一致 [源码]。
3. 补充：源未提 `dynamic-hz`（5.0+ 默认开启的自适应频率）与 4.0+ 异步释放，两者是调优追问的高频点，本卡已补。
