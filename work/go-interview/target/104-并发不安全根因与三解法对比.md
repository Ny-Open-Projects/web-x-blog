# 104 并发不安全根因与三解法对比

> 分类：Go/并发 | 难度：L2 | 题型：案例题 | 频率：高 | 关键词：**CNT++ 三指令竞争** / **锁** / **通道** / **原子操作**
> 原文锚点：第 4~56 段「并发不安全=CNT++ 拆 load/add/store 三指令多核竞争得 987≠1000、单核不出现；三解法(锁/通道缓冲1/原子 AddInt64)对比，原子最简洁高效」

## 一句话总述
`count++` 在机器层被拆成 **load（读内存到寄存器）→ add（加一）→ store（写回内存）** 三条指令；多核下多个 goroutine 同时 load 到相同旧值，各自加一写回，结果相互覆盖，最终 ≠ 期望（demo 得 987 而非 1000）。三种修法：① `sync.Mutex` 加锁（正确但每次锁）；② 缓冲为 1 的 channel（写入即占坑、等效锁）；③ `atomic.AddInt64`（CPU 原子指令，最简洁高效）。单核（GOMAXPROCS=1）串行调度下不出现——但生产永远多核，必须保护。

## 面试官视角
- 意图：考察"能否用一个最小例子讲清数据竞争的来源与解法光谱"。
- P5 知 count++ 有并发问题；P6 能拆三指令讲竞争、能列三种解法；P7 能讲"channel 缓冲1 本质就是把写入当锁、原子靠硬件指令最轻"并点出单核不出现但不可依赖。
- 红旗：以为 count++ 是一条原子指令；以为单核安全就可不保护。
- 惊艳点：点出"channel 缓冲=1 在这里等价于一把锁，原子操作才是变量级互斥的最轻实现"。

## 主问答
**Q：** 为什么 `count++` 并发会出错？怎么修？
**A：**
1. **根因**：`count++` 不是单指令，而是 load→add→store 三步。多核下 goroutine A、B 同时 load 到相同旧值 v，各加一得 v+1，先后 store 回——本应 +2 却只 +1，多次叠加后离 1000 差一截（demo 987）。
2. **解法一 锁**：`mu.Lock()` 包住 `count++`，保证同时只有一个 goroutine 进临界区——正确，但已建好后每次仍加锁。
3. **解法二 通道**：用缓冲 1 的 channel，写前 `<-ch` 占坑、写完 `ch <- struct{}{}` 释放，等价于一把锁保护该行。
4. **解法三 原子**：`atomic.AddInt64(&count, 1)`，底层 CPU 原子指令，同刻只允许一个 goroutine 对该地址加一——最简洁、最高效，是计数器首选。

## 关键代码
```go
var count int64
// 错误：多核下 count++ 被拆成 load/add/store，结果相互覆盖
for i := 0; i < 1000; i++ {
    go func() { count++ }() // demo 得 987 而非 1000
}

// 正确且最简：原子操作（底层 CPU 原子指令，变量级互斥）
for i := 0; i < 1000; i++ {
    go func() { atomic.AddInt64(&count, 1) }() // 终值稳定 1000
}
// 单核 GOMAXPROCS=1 时调度串行，count++ 不交错，但生产永远多核必须保护
```
