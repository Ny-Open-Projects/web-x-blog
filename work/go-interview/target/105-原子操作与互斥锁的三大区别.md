# 105 原子操作与互斥锁的三大区别

> 分类：并发模型 | 难度：中 | 题型：对比题 | 频率：高 | 关键词：**原子操作、互斥锁、实现方式、保护范围、性能**

> 原文锚点：第 3~15 段「原子操作由底层 CPU 指令实现…锁在软件层…保护范围与性能差异」

## 一句话总述
原子操作与互斥锁核心三点差异——**实现**（CPU 指令 vs 软件）、**保护范围**（单个变量 vs 代码块）、**性能**（小范围原子更快，但有前提）。一句话背法：**「原子与锁三区别：硬件指令 vs 软件、单变量 vs 临界区、小范围原子快但有前提」**。

## 面试官视角
考官考察能否讲清两者本质区别而非背结论。能讲清 CPU 指令 vs 软件实现、变量 vs 代码块保护范围、并点出"原子并非永远更快、激烈竞争时锁结构更清晰"，说明成熟；"原子一定比锁快"无前提、以为锁只能保护单个变量，是红旗。
- **P5**：知道原子保护变量、锁保护代码块。
- **P6**：能说 CPU 指令 vs 软件实现及性能前提。
- **P7**：知道何时该用锁、原子并非总是更快。

## 主问答
**Q（面试官原话）：** 原子操作和锁有什么区别？

**先铺垫（由浅入深第 1 层）**：两者都解决并发安全，但解决问题的"层级"不同。锁是在软件层把一段代码"圈起来"独占；原子是在硬件层把"一个变量的读-改-写"做成一条不可分割的指令。看清这个层级差，三区别就顺了。

1. **结论（第 2 层）**：实现上原子靠 CPU 原子指令（硬件），锁在软件层（mutex 内部也用原子 + 调度）；保护范围原子是单个变量，锁是临界区代码块。
2. **机制（第 3 层）**：原子指令执行期间不可被其他核中断观察，无需上下文切换；锁在竞争时要挂起/唤醒 goroutine（涉及调度，更重）。
3. **边界（第 4 层）**：原子只在"单变量读写/计数"场景占优，涉及多变量一致或复合操作必须上锁。
4. **加分层（第 5 层）**：原子不是"永远更快"——竞争激烈、临界区偏大时，锁一次独占反而结构更清晰、重试开销更小；选型以压测为准。
5. **误用风险（第 6 层）**：以为"原子=all-or-nothing 事务回滚"是错的——原子是**不可分性（indivisibility）**，单个原子操作不存在"回滚"，只是不被观察到中间态。

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	// 原子：硬件指令，保护单个变量
	var c atomic.Int64
	c.Add(1)
	fmt.Println("atomic:", c.Load())

	// 锁：软件层，保护临界区代码块（多步操作）
	var mu sync.Mutex
	var x, y int
	mu.Lock()
	x++ // 多变量组合一致性，原子表达不了，必须锁
	y++
	mu.Unlock()
	fmt.Println("mutex:", x, y)
}
```

## 总结与追问预判
**背这三句就够**：① **实现不同：原子靠 CPU 指令（硬件），锁在软件层（原子+调度）**；② **保护范围不同：原子护单变量，锁护临界区代码块**；③ **性能有前提：小范围低竞争原子更快，高竞争/复合锁更清晰，实测选型**。
**预判追问**：
- 「原子是事务回滚吗？」→ 不是，是"不可分"（indivisibility），无回滚（见本卡第 6 层纠错）。
- 「什么时候该用锁？」→ 多变量一致/读-判-写复合（见 105 何时用原子）。
- 「底层怎么无锁？」→ LOCK 前缀锁 cache line + MESI（见 105 无锁原理）。

## ⚠️ 原文纠错
原文第 3 段称原子操作"要么全部执行成功，要么全部不执行"。这是事务回滚（all-or-nothing）语义；原子操作的准确含义是**不可分性（indivisibility）**——执行期间其他 goroutine 不会观察到中间状态，单个原子读/写/CAS 不存在"回滚"。应表述为"不可被中断地整体生效"。本卡已修正此表述。其余事实（CPU 指令实现、保护范围、性能前提）均正确。
