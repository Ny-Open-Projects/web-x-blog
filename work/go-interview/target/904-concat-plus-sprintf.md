# 904 加号拼接与 fmt 格式化：为什么这两种方式最慢

> 分类：Go 基础 / string | 难度：L2 | 题型：原理题 | 频率：高 | 关键词：**字符串不可变、加号拼接、fmt.Sprintf、对象创建、强转、GC、对象池**

> 原文锚点：第 6~11 段「字符串是不可变的，所以使用加号去拼接两个字符串的时候会生成一个新的字符串，这个操作就需要开辟一段新的空间，那么每拼接一次都需要开辟一次空间，所以使用这种方式来拼接大量的字符串就会导致频繁的对象创建，同时旧对象也需要被 GC 回收，从而导致了拼接大量字符串的时候效率会很低…格式化函数在对字符串进行操作的过程中，它会创建新的对象，这里它还使用了 buffer，也就是对象池，并且每次拼接的时候都会对字符串进行强制的转化…每次拼接操作都需要经历对象创建、字符串的格式化、string 的转化以及对象的释放操作，所以它的整体性能也是比较差的」

## 一句话总述
字符串常见的拼接方式有**六种**：**加号连接符**、**格式化函数**、**bytes.Buffer**、**strings.Builder**、**字节切片**、**strings.Join**。其中**加号**与 **fmt 格式化**最慢：**加号**因为**字符串不可变**，**每拼接一次都生成一个新字符串、开辟一段新空间**，导致**频繁对象创建**并**让旧对象等待 GC**；**fmt** 则不仅**创建新对象**，**每次拼接还要对字符串做强制转化**，全流程是**对象创建 → 格式化 → string 转化 → 对象释放**，整体性能很差。

## 面试官视角
- 考察意图：能否把"加号慢"从结论升级为**因果链**（不可变 → 每次新对象 → 频繁分配 + GC）。
- 分档：P5 知道加号拼接慢；P6 能说"字符串不可变、每次生成新串"；P7 能补上 **fmt 的四步开销**（创建 → 格式化 → 强转 → 释放）与**基准测试里 fmt 与加号效率接近**这一实测结论。
- 红旗答案：以为 `fmt.Sprintf` 因为用了对象池所以快——**对象池省的是 `pp` 结构的复用，省不掉格式化与类型转换的开销**。
- 惊艳点：**`fmt` 与加号在基准测试里效率接近**——很多人以为 `fmt` 会明显更慢，实测两者是同一量级的低效 `[源码]`。

## 主问答
**Q（面试官原话）：** 用 `+` 拼接大量字符串为什么慢？`fmt.Sprintf` 呢？

1. **结论**：**字符串不可变 + 每次拼接都产生新对象**是加号慢的根因；**fmt 在此基础上还要做格式化与强制转化**，两者都很慢，且**基准测试显示 fmt 与加号的效率比较接近** `[源码]`。
2. **六种方式全景**：**① 加号连接符；② 格式化函数；③ bytes.Buffer；④ strings.Builder；⑤ 字节切片；⑥ strings.Join** `[源码]`。
3. **加号 · 不可变是根因**：**字符串是不可变的**，**使用加号拼接两个字符串时会生成一个新的字符串** `[源码]`。
4. **加号 · 每次都要新空间**：**这个操作需要开辟一段新的空间**，**每拼接一次都需要开辟一次空间**，所以**拼接大量字符串会导致频繁的对象创建** `[源码]`。
5. **加号 · 双重代价**：**同时旧对象也需要被 GC 回收**，**从而导致拼接大量字符串时效率很低** `[源码]`。
6. **fmt · 创建新对象**：**格式化函数在对字符串进行操作的过程中会创建新的对象** `[源码]`。
7. **fmt · 对象池与强转**：**它还使用了 buffer，也就是对象池**，**并且每次拼接的时候都会对字符串进行强制的转化**（源码里进行了一次强转）`[源码]`。
8. **fmt · 四步开销**：**每次拼接操作都要经历对象创建 → 字符串的格式化 → string 的转化 → 对象的释放**，**所以整体性能也比较差** `[源码]`。

**加分层：** 记法——**加号是"分配 + GC"两份代价，fmt 是"分配 + 格式化 + 转换 + 释放"四份代价**；两者都慢，但慢的原因不同，面试里要分开说。

## 关键代码
```go
package main

import (
	"fmt"
	"testing"
)

// 加号：每次都生成新字符串 -> 频繁分配 + 旧对象待 GC
func concatPlus(n int) string {
	s := ""
	for i := 0; i < n; i++ {
		s += "abcd" // 每次重新分配一段空间
	}
	return s
}

// fmt.Sprintf：创建 pp 对象 -> 格式化 -> string 转化 -> 释放
func concatFmt(n int) string {
	s := ""
	for i := 0; i < n; i++ {
		s = fmt.Sprintf("%s%s", s, "abcd")
	}
	return s
}

// 基准测试：go test -bench='Benchmark' -benchmem -benchtime=3s
func BenchmarkPlus(b *testing.B)   { for i := 0; i < b.N; i++ { concatPlus(1000) } }
func BenchmarkFmt(b *testing.B)    { for i := 0; i < b.N; i++ { concatFmt(1000) } }
```

## 总结与追问预判
**最爱追问的是"那少量拼接用哪个"**——**用加号没问题**：少量拼接的可读性价值远大于性能差异，原文也强调**日常使用不必过于纠结，更应关注代码风格与可读性**，**代码简洁本身也是生产力**。追问常接"什么才算大量"——一般是**循环里成百上千次拼接**，或**高并发热路径**；这时才该换 `strings.Builder`（见 `904-builder-vs-buffer`）。

## ⚠️ 原文纠错
1. 事实核校：六种拼接方式、字符串不可变故加号生成新串、每次开辟新空间、大量拼接导致频繁对象创建、旧对象需 GC 回收故效率低、fmt 会创建新对象、使用了对象池、每次拼接都会强转、每次经历创建→格式化→转化→释放四步、整体性能差——均与 Go 语义一致 `[经验]`。
2. 补充：**原文说 fmt "使用了 buffer，也就是对象池"，准确说法是 `fmt` 用 `sync.Pool` 复用的是内部的 `pp` 结构体**，它**不消除格式化与类型转换的开销**；另外 `fmt.Sprintf` 涉及**反射解析格式串**，这才是它慢的主因之一 `[经验]`。
3. 崩坏词归一：源码将格式化函数、对象池、强转、垃圾回收、buffer 等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
