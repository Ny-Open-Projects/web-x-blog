# 134 深挖：倒排索引的构建、index_options 四档与检索四步

> 分类：Elasticsearch 存储 | 难度：L4 | 题型：综合题 | 频率：高 | 关键词：**文档预处理、停用词、词干提取、index_options、docs/freqs/positions/offsets、交集并集、相关性评分**

> 原文锚点：第 30~34、52~76 段「倒排索引的构建过程一般包括下面这几个步骤：首先是文档的预处理，它会将文档集中的每一个文档进行预处理，这个预处理的过程包括分词、去掉停用词等等，当然还有一些情况会进行词干提取…index_options 有四个值：docs 表示只有文档ID被存储，freqs 表示文档ID和 term 的词频会被存储，positions 是默认值，offsets 表示还会存储 term 的起始和结束字符偏移量…使用倒排索引进行搜索的过程：先对查询进行预处理，然后查找倒排列表，再进行结果合并，最后排序和返回结果」

## 思路与架构

按「**构建三步 → 存多少信息 → 检索四步**」三层把握：

1. **构建过程（三步）**：
   - **① 文档预处理**：**对文档集中的每一个文档进行预处理**，包括**分词**、**去掉停用词**等；**有些情况还会进行词干提取** `[源码]`。
   - **② 生成倒排列表**：**对文档集中的每一个关键词，创建一个包含这个关键词的文档列表**，这个列表称为**倒排列表** `[源码]`。
   - **③ 构建倒排索引**：**把所有关键词的倒排索引组成一个倒排索引**；**倒排索引可以看作是一个映射——键是关键词，值是倒排列表** `[源码]`。
2. **index_options 四档（控制 posting list 存多少信息）** `[源码]`：
   - **`docs`**：**只有文档 ID 被存储**，也是倒排索引存储的**最小单位**——据此可知道查询词在哪些文档中出现过。
   - **`freqs`**：**文档 ID 和 term 的词频会被存储**；**词频即 term 出现的频率，用于搜索评分**，**重复出现的 term 评分高于只出现一次的 term**。
   - **`positions`（默认值）**：**文档 ID、词频以及词条的位置信息都会被存储**；**一旦存了这三项，就可以使用临近查询以及短语查询**。
   - **`offsets`**：**文档 ID、词频、位置，再加上 term 的起始和结束字符偏移量都会被存储**；**存储这些信息后可以做高亮相关功能**。
   - **取舍**：**存储的信息越多，占用的磁盘空间就越大，需要根据具体业务需求合理评估**。
3. **检索过程（四步）** `[源码]`：
   - **① 查询预处理**：**先对用户输入的关键词进行预处理，对查询关键词进行分词**。
   - **② 查找倒排列表**：**根据查询中的关键词，在倒排索引的字典中查找对应的倒排列表**。
   - **③ 结果合并**：**把多个关键词的倒排列表进行合并**，得到包含所有关键词的文档集合；**涉及集合的交集、并集操作，取决于查询类型**——**用 `match` and 需要取交集，用 `match` or 需要取并集**。
   - **④ 排序与返回**：**按一定排序规则排序后返回**，规则如**相关性评分、文档的更新时间**等，**可在查询语句中自行指定**。
4. **维护要点**：**倒排索引在构建过程中需要考虑权重、分词、去除停用词等一系列技术来提高搜索效果与准确性**；**为保证倒排索引的实时性，还需要定期更新索引以反映文档的变化** `[源码]`。

## 方案取舍

| 关注点 | 选项 | 代价 / 收益 |
|---|---|---|
| `docs` | 只存文档 ID | 空间最小；只能回答"哪些文档含该词" |
| `freqs` | + 词频 | 多占空间；换来**评分能力**（词频越高分越高） |
| `positions` | + 位置（默认） | 再占空间；换来**短语查询与临近查询** |
| `offsets` | + 字符偏移 | 空间最大；换来**高亮** |
| 多词合并 | 交集（and） | 结果更精确，召回低 |
| 多词合并 | 并集（or） | 召回高，精确度下降 |
| 预处理 | 去停用词 | 降噪 + 省空间，但可能误删有意义的词 |
| 索引更新 | 定期重建 | 保实时性，代价是构建开销 |

取舍要点：**`index_options` 是一条清晰的"空间换能力"阶梯**——每多存一档信息，就多解锁一类查询能力（评分 → 短语 → 高亮），代价是磁盘占用上升。工程上**默认值 `positions` 已覆盖绝大多数场景**，只在确实需要高亮时才上 `offsets`；反过来，若只要"有没有"的判定（如过滤、存在性判断），降到 `docs` 能显著省空间。

## 答题技巧

1. **构建三步要按"预处理 → 列表 → 索引"的顺序讲**：先去停用词再生成列表，顺序反了会被追问。
2. **`index_options` 四档要能一口气背出并各配一句用途**：`docs`（最小）/ `freqs`（评分）/ `positions`（默认，短语查询）/ `offsets`（高亮）。**报出默认值 `positions` 是 P7 硬证据**。
3. **检索四步里"合并"要带 and/or**：`match` 用 **and 取交集**、**or 取并集**，这是最常被追问的一步。
4. **主动补两条维护项**：**权重/分词/停用词**影响效果与准确性，**定期更新索引**保证实时性——这两条原文有、但候选人常漏。
5. **止步档位**：能讲清构建三步与检索四步即达 L4；能补上 `index_options` 四档及其解锁的能力、and/or 合并语义与维护要点，即达 L5。

## ⚠️ 原文纠错
1. 事实核校：构建三步（预处理含分词/去停用词/词干提取、生成倒排列表、汇总为映射）、`index_options` 四档含义与 `positions` 为默认值、检索四步（查询预处理/查倒排列表/合并/排序返回）、and 取交集 or 取并集、权重分词停用词影响效果、需定期更新索引——均与 ES 实现一致 `[经验]`。
2. 补充：原文未提 **ES 的近实时（NRT）机制**——倒排索引并不是"定期重建"，而是**新文档先写入内存 buffer 与 translog，经 refresh（默认 1 秒）生成新段后才可被检索**，段再通过后台 merge 合并；面试中把"定期更新"改述为 **refresh + merge 的近实时模型**更准确 `[经验]`。
3. 崩坏词归一：源码将倒排索引、倒排列表、停用词、词干提取、index_options、偏移量、高亮等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。

## 细节与核心 API

**index_options 四档（默认 positions，控制 posting list 存多少信息）：**

```json
PUT /my_idx {
  "mappings": { "properties": {
    "title":    { "type": "text", "index_options": "docs" },     // 只存文档 ID
    "content":  { "type": "text", "index_options": "freqs" },    // + 词频（评分）
    "body":     { "type": "text", "index_options": "positions" },// 默认：+位置（短语查询）
    "comment":  { "type": "text", "index_options": "offsets" }   // +字符偏移（高亮）
  } }
}
```

**检索四步里的合并语义（and 交集 / or 并集）：**

```json
// match + operator=and → 取多个 term 倒排列表的交集
{ "query": { "match": { "body": { "query": "go 并发", "operator": "and" } } } }
// bool.must 等价于 and；bool.should 等价于 or（取并集）
{ "query": { "bool": { "must": [ {"term":{"f":"a"}}, {"term":{"f":"b"}} ] } } }
```

**近实时模型（纠错 2 的落地）：**

```text
新文档 → 内存 buffer + translog → refresh(默认 1s) 生成新段(OS cache) 才可搜
段经后台 merge 合并；不是"定期重建索引"，而是 refresh + merge 的 NRT 模型
```
