# 1022 协程泄露全景（深卡）

> 分类：Go 运行时 · 并发缺陷 | 难度：L3 | 题型：综合题 | 频率：高 | 关键词：**泄露本质**/**场景枚举**/**预防体系**/**监控定位**
> 原文锚点：第 1~66 段「协程泄露定义、三类易发场景(defer/nil/空select/无退出)、预防(context/超时/池化/分治)、监控」

## 思路与架构
把"协程泄露"从本质到落地串成一条线：

1. **本质**：协程被创建却永不退出（阻塞在 channel / 死循环 / 等永不发生的事件），其栈与引用对象一直可达，GC 不敢回收；持续创建 → 堆积 → 内存/端口/句柄耗尽 → OOM 或服务崩溃。
2. **场景枚举（两组互补）**：
   - **本卡组**（1022-leak-trigger-scenarios）：defer 误用（文件句柄堆积）、nil channel 读写、空 `select{}`、channel 收发不匹配的延伸。
   - **1019 组**：for-select 不判 ok 空转、发送超缓冲永久阻塞、ticker 不 Stop。
3. **预防体系**（1022-leak-prevention）：context 取消 + 超时 + 协程池/信号量控并发 + 大文件分治/文件流 + 监控。
4. **监控定位**：`runtime.NumGoroutine()` 看趋势、pprof goroutine profile 抓现场。

## 方案取舍
| 治理手段 | 防什么 | 代价/注意 |
| --- | --- | --- |
| context 取消 | 无退出机制的协程 | 每个协程都要接 Done |
| 超时 | 长任务/下游故障堆积 | 需业务可接受中断 |
| 协程池/信号量 | 无界并发创建 | 需估并发上限 |
| 大文件分治 | 单协程吃光内存 | 代码稍复杂 |
| NumGoroutine/pprof | 发现泄露 | 线上常态化观测 |

**取舍总纲**：泄露的"发现"靠监控、"根治"靠给每个协程确定性退出路径 + 并发上限；不能依赖"函数返回协程就自动没" `[经验]`。

## 答题技巧
- 被问"协程泄露"，先抛本质（不退出→不可回收→堆积），再枚举两组场景，最后给预防体系 + 监控，结构最完整。
- 被问具体某坑：用对应专项卡（defer/nil/空select → 1022；channel 三形态 → 1019；概念与监控 → 812）。
