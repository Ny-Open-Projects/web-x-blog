# 108 何时需要控制并发数（资源预算三约束）

> 分类：Go 并发模型 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**资源预算** / **goroutine 内存** / **端口上限** / **文件描述符**
> 原文锚点：第 1~10 段「启动携程消耗资源：内存/端口/文件描述符；过多携程→内存暴涨/连接耗尽」

## 一句话总述
控制并发数不是"越并发越快"，而是受三类硬资源约束：**单个 goroutine 实际占用内存（大对象可达数十~数百 MB）**、**本地端口上限 65535**、**内核文件描述符上限**；任一逼近红线就必须用协程池/信号量/限流卡住并发。

## 面试官视角
- 意图：考察是否理解"无界 goroutine"背后的资源账，而非只会背 `go func()`。
- 分档：P5 知协程吃内存；P6 能说出端口 65535 / fd 上限；P7 能据此给出"何时该池化/限流"的决策框架。
- 红旗：以为 goroutine 轻量就可以无限开；或只说 OOM 不提端口/fd。
- 惊艳点：点出"goroutine 本身约 2KB 栈，但业务里加载大文件/大对象时单协程实际占用可达数百 MB——约束的是它引用的资源，不是栈"。

## 主问答
**Q（面试官原话）：** 都说 goroutine 轻量，那为什么还要控制并发数？
**A：**
1. **内存约束**：空 goroutine 只占约 2KB 栈，但业务协程常加载文件、缓存大对象，单个协程实际持有内存可达数十~数百 MB；同时开成千上万个→总内存爆炸 OOM。
2. **端口约束**：用 goroutine 发起大量网络请求时，每个连接占用一个本地端口，而本地端口上限约 **65535**；耗尽后无法建立新 TCP 连接。
3. **文件描述符约束**：同时打开的文件/连接数受内核 `fs.file-max` 与进程 `ulimit -n` 限制，超限后 `open`/建连失败。
4. **决策**：出现上述任一类风险→用协程池（上限 N 个 worker）或信号量卡并发，调用外部服务再叠加限流避免打垮下游。

## 关键代码
```go
// 示意，未验证：按端口预算反推并发上限
const maxConns = 60000 // 留余量，避开 65535 硬上限
sem := make(chan struct{}, maxConns)
for _, url := range urls {
    sem <- struct{}{}
    go func(u string) {
        defer func() { <-sem }()
        http.Get(u) // 每个连接占一个本地端口
    }(url)
}
```

## 总结与追问预判
- 控制并发数 = 给"内存/端口/fd"三类资源设预算上限，再选池化或限流手段。
