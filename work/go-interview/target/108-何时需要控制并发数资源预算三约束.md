# 108 何时需要控制并发数（资源预算三约束）

> 分类：Go 并发模型 | 难度：中 | 题型：工程题 | 频率：高 | 关键词：**资源预算、goroutine 内存、端口上限、文件描述符**

> 原文锚点：第 1~10 段「启动携程消耗资源：内存/端口/文件描述符；过多携程→内存暴涨/连接耗尽」

## 一句话总述
控制并发数不是"越并发越快"，而是受三类硬资源约束：**单个 goroutine 实际占用内存（大对象可达数十~数百 MB）**、**本地端口上限 65535**、**内核文件描述符上限**；任一逼近红线就必须用协程池/信号量/限流卡住并发。一句话背法：**「控并发数=给内存/端口(65535)/fd 三类资源设预算上限，逼近即池化/限流」**。

## 面试官视角

## 主问答
**Q（面试官原话）：** 都说 goroutine 轻量，那为什么还要控制并发数？

**先铺垫（由浅入深第 1 层）**："goroutine 轻量"指的是栈只有约 2KB，但一个业务协程往往还持有它加载的文件、缓存的大对象、占用的 TCP 连接——这些才是真正吃资源的。无界 `go func()` 把成千上万个协程撒出去，不是栈爆炸，是它背后的内存/端口/fd 同时爆。控并发数本质是给这三类资源设预算。

1. **内存约束（第 2 层）**：空 goroutine 只占约 2KB 栈，但业务协程常加载文件、缓存大对象，单个协程实际持有内存可达数十~数百 MB；同时开成千上万个→总内存爆炸 OOM。
2. **端口约束（第 3 层）**：用 goroutine 发起大量网络请求时，每个连接占用一个本地端口，本地端口上限约 **65535**；耗尽后无法建立新 TCP 连接。
3. **文件描述符约束（第 4 层）**：同时打开的文件/连接数受内核 `fs.file-max` 与进程 `ulimit -n` 限制，超限后 `open`/建连失败。
4. **决策（第 5 层）**：出现上述任一类风险→用协程池（上限 N 个 worker）或信号量卡并发，调用外部服务再叠加限流避免打垮下游。
5. **误用风险（第 6 层）**：并发上限 N 不是拍脑袋——按"内存预算/端口预算"反推（如留余量避开 65535）；限流（速率）与控并发（同时数）要叠加使用，不是二选一。

## 关键代码
```go
package main

import (
	"fmt"
	"net/http"
	"sync"
)

// 按端口预算反推并发上限：留余量，避开 65535 硬上限
func main() {
	const maxConns = 60000 // 远小于 65535，留系统与其他进程余量
	sem := make(chan struct{}, maxConns)

	urls := []string{"http://a", "http://b", "http://c"}
	var wg sync.WaitGroup
	for _, u := range urls {
		sem <- struct{}{} // 占坑，满则等（控并发=同时建连数）
		wg.Add(1)
		go func(url string) {
			defer wg.Done()
			defer func() { <-sem }() // 还坑
			resp, err := http.Get(url)
			if err != nil {
				fmt.Println("err:", err)
				return
			}
			_ = resp.Body.Close()
		}(u)
	}
	wg.Wait()
}
```

## 总结与追问预判
**背这三句就够**：① **goroutine 栈仅 2KB，但业务持有大对象/连接使单协程实际占数十~数百 MB**；② **三类硬约束：内存 OOM、本地端口约 65535、内核 fd 上限**；③ **任一逼近红线→协程池/信号量卡并发，调外部再叠加限流，N 按资源预算反推**。
**预判追问**：
- 「限流和控并发区别？」→ 限流卡速率、控并发卡同时数，二者叠加（见 108 四算法）。
- 「信号量怎么写？」→ channel 缓冲 N 当作信号量（见 1015 channel 信号量）。
- 「端口耗尽怎么治？」→ 协程池限并发 + 连接复用（见 1022 资源耗尽维度）。
