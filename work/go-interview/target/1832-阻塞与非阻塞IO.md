# 1832 阻塞与非阻塞 IO：判定轴只看"第一个阶段"

> 分类：操作系统 / 网络 | 难度：L3 | 题型：原理题 | 频率：极高 | 关键词：**阻塞IO**/**非阻塞IO**/**等待加拷贝**/**内核缓冲区**/**EAGAIN**/**轮询**/**同步异步**
> 原文锚点：第 5~13 段「一个应用想进行一次 IO 会分为两个阶段…操作系统完成一次 IO 操作，它也包含两个过程，第一个是准备数据阶段，第二个是拷贝数据阶段…一次 IO 本质上其实就是等待加拷贝」
> [边界] 本文只讲**阻塞 / 非阻塞这对概念的判定轴与代价**：三种多路复用系统调用的机制对比见 1834，写路径与页缓存见 1835，文件描述符语义见 1813，均不重述。

## 一句话总述
一次 IO 拆成**两个阶段**——**① 等数据准备好（等待）+ ② 把数据从内核缓冲区拷到用户缓冲区（拷贝）**。所谓"阻塞 / 非阻塞"，判定的**只有第一个阶段**：数据没准备好时，调用是**把线程挂起**还是**立刻返回**。第二条判定轴是"同步 / 异步"，它看的是**第二个阶段**——拷贝到底由谁阻塞完成。两条轴交叉，才撑得起五种 IO 模型。

## 面试官视角
- 考察意图：这是**IO 题的公理层**。后面所有网络题（多路复用、netpoll、零拷贝）都长在它上面。能一开口就拆出"等待 + 拷贝"两阶段，后面的回答会自动变清晰。
- 分档：P5 只能背"阻塞就是卡住"；P6 知道非阻塞会立刻返回、要配合循环；P7 能讲出**两条判定轴的分工**、**"非阻塞在第二阶段仍是同步阻塞"**这个反直觉点，以及**非阻塞单独用反而更费 CPU**。
- 红旗答案：「非阻塞 IO 性能更好」——**孤立使用是更差的**。线程不挂起换来的是 CPU 空转，只有和多路复用配合才有意义。
- 惊艳点：补一句「Go 里 `os.File` 就算你手动 `SetNonblock`，`Read` 依然会被运行时网络轮询器接管而阻塞——**想拿到真正的 `EAGAIN`，必须走裸 `syscall`**」[实测]。

## 主问答
**Q（面试官原话）：** 说说阻塞 IO 和非阻塞 IO 的区别，为什么说一次 IO 本质是"等待加拷贝"？

**A：**
1. **先立两阶段模型**：应用程序不能直接碰硬件，读写磁盘/网络必须走系统调用，所以一次 IO 天然分两步——**内核先等外部设备把数据准备好**，再**把数据从内核缓冲区拷进用户进程的缓冲区** [经验]。
2. **拆成三个动作更好背**：① 应用向内核发起 IO 调用；② 内核等待设备就绪、把数据搬进内核缓冲区；③ 内核把数据从内核缓冲区拷到用户缓冲区 [经验]。第 ②③ 步就是"等待 + 拷贝"。
3. **阻塞 IO 的行为**：数据没准备好时，应用进程**一直阻塞等待**，被挂起、不占 CPU，直到数据就绪并完成拷贝，系统调用才返回。**代价是线程被占死**，一个线程只能盯一个 fd [经验]。
4. **非阻塞 IO 的行为**：数据没准备好时**不挂起，立即返回**，Go/Unix 下表现为 `syscall.EAGAIN`（macOS/Linux 文本均为 `resource temporarily unavailable`），应用靠**反复尝试读写**的方式去问，这个过程叫**轮询** [实测]。
5. **非阻塞的真实代价**：轮询对 CPU 是**较大的浪费**，空转 200ms 能跑掉 **413 万次**循环；实测为了等 100ms 后的一字节数据，一共调了 **106876 次** `read` 才成功 [实测]。所以它**只在特定场景下单独使用** [经验]。
6. **反直觉的关键点**：非阻塞**只在第一阶段不阻塞**。数据就绪后真正 `read` 拷贝的那一步，应用**仍然要等拷贝完成**——所以它依旧属于**同步 IO** [经验]。
7. **两条判定轴要分清**：**阻塞 / 非阻塞**看"**等数据**时线程是否被挂起"；**同步 / 异步**看"**拷贝**是否由应用自己阻塞完成、还是内核做完再通知"。**异步 IO 才是两阶段都不阻塞** [经验]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| POSIX 全平台 | 两阶段模型与阻塞语义恒定 | 通用基础答案 |
| Linux / macOS 实测 | `EAGAIN` 与 `EWOULDBLOCK` **同值** | `errors.Is` 两个都判为 true [实测] |
| Linux 2.6+ | epoll 成熟 | 非阻塞 fd + 多路复用才是正解 |
| Linux 5.1+ | `io_uring` 引入 | 真异步 IO 有了生产级选项 |
| macOS / BSD | **无 epoll、无 io_uring** | 对应机制是 kqueue |
| Go 全版本 | netpoll 封装底层 | 业务代码不手写非阻塞 fd [实测] |

## 关键代码
```go
package main

import (
	"errors"
	"fmt"
	"syscall"
	"time"
)

func main() {
	var p [2]int
	if err := syscall.Pipe(p[:]); err != nil {
		panic(err)
	}
	rfd, wfd := p[0], p[1]
	// 关键：必须直接对 fd 设 O_NONBLOCK。
	// 若用 os.Pipe() 得到 *os.File，Go 运行时已把 fd 交给网络轮询器接管，
	// 再 SetNonblock 后调用 Read 依然会挂起 goroutine，拿不到 EAGAIN。
	syscall.SetNonblock(rfd, true)

	buf := make([]byte, 8)
	start := time.Now()
	n, err := syscall.Read(rfd, buf)
	fmt.Printf("非阻塞读(无数据) n=%d err=%v 耗时=%v\n", n, err, time.Since(start).Round(time.Microsecond))
	fmt.Printf("errors.Is(EAGAIN)=%v errors.Is(EWOULDBLOCK)=%v\n",
		errors.Is(err, syscall.EAGAIN), errors.Is(err, syscall.EWOULDBLOCK))

	syscall.Write(wfd, []byte("hi"))
	n2, err2 := syscall.Read(rfd, buf)
	fmt.Printf("非阻塞读(有数据) n=%d err=%v 数据=%q\n", n2, err2, buf[:n2])
	syscall.Close(rfd)
	syscall.Close(wfd)
}
```

> 验证（`[实测]` 输出，macOS / go1.26.5）：非阻塞读无数据 `n=-1 err=resource temporarily unavailable 耗时=5µs`——**立刻返回**，`errors.Is(err, syscall.EAGAIN)` 与 `errors.Is(err, syscall.EWOULDBLOCK)` 均输出 `true`；写入后 `非阻塞读(有数据) n=2 err=<nil> 数据="hi"`。对照组：用 `os.Pipe()` + `SetNonblock` 的阻塞读，写端延迟 100ms 写入时，读端实测 `耗时=102ms` 才返回——即**挂起了 100ms**；轮询等 100ms 的一字节数据共触发 `106876` 次 `read` 调用；纯空转循环 200ms 计得 `4133389` 次。

## 总结与追问预判
- 一句话收尾：**"阻塞非阻塞看等不等，同步异步看拷不拷"**——两阶段拆开，五种模型就不会混。
- 大概率被追的三问：① 非阻塞单独用为什么不划算（空转烧 CPU，413 万次/200ms 是硬证据）；② 为什么多路复用是正解（把轮询交给内核，一次调用盯多个 fd）；③ Go 里为什么从没写过非阻塞 fd（netpoll 已封装，Linux 走 epoll、darwin 走 kqueue）。
- 反向加分：主动指出**"非阻塞 IO 也是同步 IO"**，并补 `io_uring` 才是 Linux 上真正的异步路径。

## ⚠️ 原文纠错
1. 源码称非阻塞「大幅提升了性能」——它只让线程不挂起，孤立轮询反而更费 CPU [经验]。
2. 源码称应用访问硬件「只能」通过系统 API——`mmap`、`io_uring` 可绕开或减少系统调用 [经验]。
3. 源码未区分「阻塞/非阻塞」与「同步/异步」——二者是两条判定轴，不可混用 [经验]。
4. 源码说 IO 以「某一个核心」为主体——应是**主机（CPU+内存）与外部设备**间的数据迁移 [经验]。
5. 源码未提 Linux 原生 AIO 长期只对 `O_DIRECT` 有效，`io_uring`（5.1 起）才补齐 [经验]。
6. 源码把五个模型并列——实则**前四种都是同步 IO**，仅异步 IO 第二阶段不阻塞 [经验]。
