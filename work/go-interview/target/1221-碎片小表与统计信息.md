# 1221 碎片、小表与统计信息：优化器"有索引却不用"的三种情形

> 分类：数据库 / MySQL 索引 | 难度：L4 | 题型：排错题 | 频率：中 | 关键词：**索引碎片、重建索引、小表全扫、统计信息、成本估算、ANALYZE**

> 原文锚点：第 43~51 段「索引在经过大量的插入删除和更新操作之后，就可能产生碎片，会导致索引结构不再连续，这种情况下查询优化器可能认为全表扫描比使用碎片化的索引更有效，所以定期对索引进行优化，比如重建索引可以解决这个问题…如果数据表的数据量很小，查询优化器可能认为全表扫描要比使用索引更有效，这是因为全表扫描可以避免索引的查找和回表操作…查询优化器在选择执行计划的时候会基于统计信息来估算各个操作的代价，在某些情况下可能会因为统计信息不准确或者是统计信息过时而选择错误的执行计划，从而导致索引失效，这种情况下就需要我们定期去更新统计信息」

## 一句话总述
除了条件写法，**物理状态与估算输入**也会让优化器放弃索引：**①索引碎片过多**——大量增删改后索引结构不再连续，优化器认为全表扫描比扫碎片化索引更有效，**重建索引可解决**；**②数据表太小**——全表扫描能**避免索引查找与回表**，小数据量下损失不严重；**③优化器估算错误**——执行计划基于**统计信息**估算代价，**统计信息不准确或过时**会导致选错计划，**需定期更新统计信息**。

## 面试官视角
- 考察意图：能否识别"**有索引、写法也对，但优化器就是不用**"这一类最难的失效场景。
- 分档：P5 只会改 SQL 写法；P6 能想到统计信息过时；P7 能三情形全答，并给出**对应的处置动作**（重建索引 / 更新统计信息 / 接受小表全扫）。
- 红旗答案：一见索引失效就只会在 SQL 上找原因；不知道 **`ANALYZE TABLE`** 与**重建索引**这两个运维手段。
- 惊艳点：**小表全表扫描往往是"正确选择"而不是"失效"**——它省掉了索引查找与回表的双重开销，数据量小时这是优化器的理性决策 `[源码]`。

## 主问答
**Q（面试官原话）：** SQL 写法没问题，为什么优化器还是不用索引？

1. **结论**：三类非写法因素——**索引碎片过多**、**数据表太小**、**优化器估算错误（统计信息不准或过时）** `[源码]`。
2. **失效六 · 索引碎片过多**：**索引在经过大量的插入、删除和更新操作之后就可能产生碎片**，**会导致索引结构不再连续**；这种情况下**查询优化器可能认为全表扫描比使用碎片化的索引更有效**；**定期对索引进行优化，比如重建索引，可以解决这个问题** `[源码]`。
3. **失效七 · 数据表太小**：**如果数据表的数据量很小，查询优化器可能认为全表扫描要比使用索引更有效**；原因是**全表扫描可以避免索引的查找和回表操作**，**而且在数据量较小的情况下，全表扫描的性能损失并不严重** `[源码]`。
4. **失效八 · 优化器估算错误**：**查询优化器在选择执行计划时，会基于统计信息来估算各个操作的代价**；**某些情况下可能因统计信息不准确或统计信息过时而选择错误的执行计划**，从而导致索引失效；**这种情况下需要定期更新统计信息** `[源码]`。
5. **处置动作**：
   - **碎片** → **重建索引**（`OPTIMIZE TABLE` 或 `ALTER TABLE ... ENGINE=InnoDB`）`[经验]`。
   - **统计信息** → **`ANALYZE TABLE` 重新采样**，必要时调大采样页数 `[经验]`。
   - **小表** → **不必干预**，甚至应考虑**删掉该表上的多余索引**以减少维护成本 `[经验]`。
6. **边界**：这三类都属于**优化器的成本择优结果**而非语法错误——**"用不用索引"的最终裁判是成本估算，不是索引是否存在** `[经验]`。

**加分层：** 排查顺序建议——**先看 `EXPLAIN`（是否用索引）→ 再看 `rows` 与实际行数是否偏差大（统计信息是否过时）→ 最后看表是否有大量增删改历史（碎片）**。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| InnoDB 全版本 | 碎片随增删改累积 | 定期重建 |
| 5.6 起 | 持久化统计信息 | `innodb_stats_persistent` 默认 on |
| 8.0 起 | 直方图统计 | `ANALYZE ... UPDATE HISTOGRAM` |
| 全版本 | 小表全扫 | 属正常择优，不必干预 |

## 关键代码
```sql
-- 1) 查看表的数据量与碎片情况（Data_free 偏高提示碎片）
SELECT table_name, table_rows, data_length, index_length, data_free
FROM information_schema.tables
WHERE table_schema = DATABASE() AND table_name = 'user1';

-- 2) 重建索引：回收碎片、让索引结构重新连续
OPTIMIZE TABLE user1;
-- 或：ALTER TABLE user1 ENGINE=InnoDB;

-- 3) 更新统计信息（统计信息过时时优化器会选错计划）
ANALYZE TABLE user1;

-- 4) 确认是否启用持久化统计信息（5.6 起默认 on）
SELECT @@innodb_stats_persistent;

-- 5) 8.0 可为低区分度列收集直方图，改善选择性估算
ANALYZE TABLE user1 UPDATE HISTOGRAM ON age WITH 100 BUCKETS;

-- 6) 对比 EXPLAIN 的 rows 与实际 COUNT，判断是否估算失真
EXPLAIN SELECT * FROM user1 WHERE name = 'name3';
SELECT COUNT(*) FROM user1 WHERE name = 'name3';
```

## 总结与追问预判
**最爱追问的是"重建索引会不会锁表"**——`OPTIMIZE TABLE` 在 5.6 之前会**重建整表并长时间锁表**；**5.6 起 InnoDB 支持 Online DDL**，`ALTER TABLE ... ENGINE=InnoDB` 可在线执行，但仍会占用 IO 与临时空间，**需在低峰期做**。追问常接"小表要不要建索引"——**一般不要**：小表全扫更快，索引只会增加维护成本；**只有当该表预期会快速增长时**才提前规划。

## ⚠️ 原文纠错
1. 事实核校：大量增删改产生碎片并使索引结构不再连续、优化器可能改走全表扫描、重建索引可解决、小表因可省去索引查找与回表而优选全扫且损失不严重、优化器基于统计信息估算代价、统计信息不准或过时导致选错计划、需定期更新统计信息——均与 MySQL 优化器行为一致 `[经验]`。
2. 补充：原文只说"定期更新统计信息"，**具体动作是 `ANALYZE TABLE`**；5.6 起 InnoDB **默认开启持久化统计信息**，8.0 还支持**直方图**以改善低区分度列的估算；另外"小表全扫"**不是故障而是择优结果**，不应强行用索引提示干预 `[经验]`。
3. 崩坏词归一：源码将索引碎片、重建索引、统计信息、回表、优化器等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
