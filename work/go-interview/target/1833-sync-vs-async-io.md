# 1833 同步 IO 与异步 IO：关注的是「通知机制」，不是等待姿态

> 分类：操作系统 / IO 模型 | 难度：L3 | 题型：概念辨析题 | 频率：高 | 关键词：**同步/异步**/**通知机制**/**AIO**/**两次操作**/**信号驱动**
> 原文锚点：第 1~29 段「同步和异步关注的是消息通知的机制…同步就是发出一个调用的时候自己需要参与等待结果的过程…异步 IO 只需要向内核发送一次请求，就可以完成状态询问和数据拷贝的所有操作…多线程的同步异步与 IO 的同步异步是不同的概念不能混淆」

## 一句话总述
同步/异步的判据是「**谁来做数据拷贝、怎么通知完成**」：**同步 IO** 中调用者要亲自参与（发起 read 等待→自己 recvfrom 拷贝），数据从内核到用户空间这一步由调用方完成；**异步 IO（AIO）** 一次请求全包——内核收请求后自行完成「等待数据就绪 + 拷贝到用户空间」，完成后回调/信号/事件通知。**多路复用与信号驱动本质仍是同步 IO**（都有「先 select 询问、再 recvfrom 拷贝」两次操作），AIO 才把两个阶段合成一次。

## 面试官视角
- 考察意图：双重陷阱题——① 「select/epoll 是异步 IO 吗」→ 不是，它们只做了「通知就绪」，拷贝还是同步的；② 「线程同步和 IO 同步是一回事吗」→ 完全不同概念。
- 分档：P5 能区分同步阻塞/同步非阻塞；P6 说清「异步=内核代拷贝+主动通知」、多路复用仍是同步；P7 能讲 Linux AIO 的局限与 io_uring 的革新、Go netpoll 的本质。
- 红旗答案：「epoll 就是异步 IO」——epoll 只替代「等待就绪」阶段；「同步 IO 就是阻塞 IO」——非阻塞轮询也是同步。
- 惊艳点：「**POSIX 定义的判据：同步 IO 在 io_operation 期间会阻塞进程（含拷贝阶段），AIO 在全过程不阻塞**——多路复用卡在『拷贝阶段仍在调用线程完成』，所以是同步」 [源码]。

## 主问答
**Q（面试官原话）：** 同步 IO 和异步 IO 的区别是什么？
**A：**
1. **概念判据：通知机制与参与度**。**同步**——调用发出后，调用者**亲自参与等待结果的过程**（数据准备就绪后，还要自己发起拷贝）；**异步**——发出调用后到数据准备完成，**全程不参与**，内核主动把数据从内核空间复制到用户空间，完成后通过回调/信号/事件通知应用 [源码]。
2. **概念纠偏：两对「同步」不是一回事**。IO 的同步/异步描述**调用者与 IO 操作的控制流**；进程/线程语境的同步/互斥描述**多执行流协调工作次序的制约关系**（尤其访问临界资源）。字面相同、领域不同，面试混用直接暴露基础不牢 [源码]。
3. **演进视角：AIO 解决「两次操作」问题**。IO 多路复用（select/poll/epoll）与信号驱动 IO 虽比阻塞/非阻塞高效，但都需要**两步**——先 select 等待就绪、再 recvfrom 拷贝数据，**两次调用之间数据拷贝仍由应用完成**，本质是同步 IO。**AIO 一次请求全包**：发起读取请求即返回，内核完成「等数据 + 拷到用户空间」全部工作后发通知 [源码]。
4. **同步 IO 的合理存在**：简单直观，控制流与 IO 完成紧密相关；适用于单线程/IO 不频繁/可容忍等待的程序。**多线程环境下同步 IO 也能并发**——每个连接一个线程阻塞处理（线程池模式），代价是线程数随连接数增长 [源码]。
5. **异步 IO 的收益与代价**：等待 IO 期间继续执行其他任务，高并发/高响应性场景（服务器）受益；**代价是额外的完成通知代码与更复杂的控制流**。工程上常**异步 + 非阻塞结合**，单进程同时管理大量连接 [源码]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| POSIX 定义 | 同步 IO 的拷贝阶段阻塞调用线程 | 以「拷贝谁做」判同步异步 |
| Linux 原生 AIO (libaio) | 仅 O_DIRECT 支持好，生态差 | 老 AIO 是半成品，别吹成通用方案 |
| io_uring (5.1+) | 真正高性能的异步接口：提交/完成两队列 | 现代 Linux 异步 IO 的事实标准 |
| Windows IOCP | 成熟的 AIO 实现 | 跨平台对比可提 |
| Go runtime | 同步风格 API + 内核非阻塞/epoll（netpoll） | 用户写同步代码，runtime 干异步的活 |

## 关键代码
```go
// Go: 同步风格 API + runtime netpoll 化 —— 用户不写回调也享受异步机制
// 每个 goroutine 里"阻塞"读, 实际 fd 是非阻塞的, 阻塞感由 netpoll+调度器消化
func handle(conn net.Conn) {
	buf := make([]byte, 4096)
	n, _ := conn.Read(buf) // 表面同步阻塞; 底层: fd 已非阻塞, 无数据时
	// 该 goroutine 被 gopark 挂起, M 去跑别的 goroutine; 数据到达 epoll 唤醒
	fmt.Println(string(buf[:n]))
}
// [源码] runtime/netpoll.go: netpollblock 状态机把 epoll_wait 事件映射回 gopark/goready
// 结论: Go 用户写的是"同步 IO"代码, 内核态走的是"非阻塞+多路复用", AIO(如 io_uring) 尚未成为默认路径
```

## 总结与追问预判
一句话记忆：**「同步=自己等+自己拷，异步=内核全包+通知你；epoll 只管就绪通知，拷贝仍同步；线程同步与 IO 同步重名不同义」**。epoll/select 的机制细节见 `1834-io-multiplexing-select-poll-epoll`、`1834-epoll-level-edge` [边界]。常追问「io_uring 为什么快」——答提交/完成两队列共享内存、批量提交减少系统调用、零拷贝注册缓冲；再追问「异步 IO 为何在 Linux 起步晚」——原生 AIO 设计缺陷（仅 O_DIRECT、无文件缓存集成），直到 io_uring 重做 [经验]。

## ⚠️ 原文纠错
1. 术语归一：[经验] 源为语音转写，「slack」应为 select，「receive/recvfrom」混用应为 recvfrom，「l操作」应为 IO 操作，统一为规范术语。
2. 表述纠错：源「多路复用…需要能群全部的文件描述符」描述的是 select 的 fd 全量遍历特性，epoll 已用就绪列表解决——源把 select 与 epoll 混述，本卡已按模型分层（多路复用整体仍是同步 IO 这一定性不变）。
3. 补充：源未提 POSIX 判据、io_uring 与 Go netpoll 本质，均为高频深挖点，本卡已补 [源码]。
