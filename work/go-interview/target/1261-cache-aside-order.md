# 1261 先删缓存还是先更新库：两种顺序都有窗口，后者更安全

> 分类：缓存 / Redis | 难度：L4 | 题型：对比题 | 频率：高 | 关键词：**删除顺序、先删缓存、先更新库、不一致窗口、缓存更快**

> 原文锚点：第 39~67 段「先删缓存还是先更新数据库的问题…假设我们先删缓存再更新数据库…请求二查询到这条数据之后会将读取到的值写入到缓存，缓存里面的值就被修改成十六，而数据库最终是十七，从而又不一致…先更新数据库再删除缓存在并发场景下也并不是万无一失的…但是先更新数据库再删缓存出现问题的条件更加苛刻，也就是会更加安全」

## 一句话总述
两种顺序都有一致性窗口：**先删缓存**时读请求可能把旧值写回缓存；**先更新库**时读请求可能在删除前读到旧值再回写。但后者触发条件更苛刻（需读请求恰好未命中且写缓存发生在删除之后），因此**更安全**。

## 面试官视角
P6 只记「先更新数据库再删除缓存」；P7 要能**画出两种顺序的异常时序**，并解释为什么后者的条件更苛刻——**缓存操作通常比数据库快**，很难出现「写完库、删完缓存之后，读请求才把旧值写进缓存」。

## 主问答
**Q（面试官原话）：** Cache Aside 里，先删缓存还是先更新数据库？

1. **先删缓存再更新库（异常时序）**：请求一删除缓存后尚未更新库 → 请求二读缓存未命中、从库读到旧值 → 请求二把旧值写回缓存 → 请求一才把库更新 → **库新缓存旧** `[源码]`。
2. **此方案的根源**：删完缓存后到更新库之间，仍可能被读到旧值并回写 `[源码]`。
3. **先更新库再删缓存（异常时序）**：请求二读时无缓存、从库读到旧值 → 请求一更新库并删除缓存 → 请求二才把旧值写入缓存 → **同样不一致** `[源码]`。
4. **并非万无一失**：先更新库再删缓存在并发场景下**也不是绝对安全** `[源码]`。
5. **为何更安全**：它出问题的**条件更加苛刻**——需要写库时另一个读请求**刚好没命中缓存**、且在前一个请求改库前完成查库、且请求二写缓存发生在请求一删缓存之后 `[源码]`。
6. **苛刻的物理原因**：**缓存操作通常比数据库更快**，很难出现请求一写完数据并删完缓存之后，请求二才更新缓存的情况 `[源码]`。
7. **根本判断**：只要同一条数据的**缓存操作与数据库操作可能在多个线程中执行**，就有可能出现并发安全问题 `[源码]`。

## 关键代码
```go
// 方案 A：先删缓存再更新库 —— 窗口较大
//   T1: DEL cache;  T2: GET miss -> DB(旧值) -> SET cache(旧值);  T1: UPDATE DB(新值)
//   结果：DB=新值，cache=旧值
func delThenUpdate(id int64, age int) error {
	_ = rdb.Del(ctx, cacheKey(id)).Err()
	return db.Exec("UPDATE user SET age=? WHERE id=?", age, id).Error
}

// 方案 B：先更新库再删缓存 —— 触发条件更苛刻，推荐
//   需同时满足：读请求未命中缓存 + 查库发生在改库前 + 写缓存发生在删缓存后
func updateThenDel(id int64, age int) error {
	if err := db.Exec("UPDATE user SET age=? WHERE id=?", age, id).Error; err != nil {
		return err
	}
	return rdb.Del(ctx, cacheKey(id)).Err()
}
```

## 总结与追问预判
**标准答案是「先更新数据库，再删除缓存」**，但必须补一句「它也不是绝对安全，只是窗口更小」。面试官若继续追问「那怎么缩小窗口」，答案就是**延迟双删**（见同批 1261-delayed-double-delete）与**删除失败补偿**（见 1261-delete-retry-binlog）。

## ⚠️ 原文纠错
1. 事实核校：两种顺序的异常时序、先更新库条件更苛刻、缓存操作快于数据库、多线程执行即可能并发不安全——分析均正确 `[经验]`。
2. 补充：严格来说，「先更新库再删缓存」的不一致窗口还需满足**读请求在写缓存前发生了较长停顿**（如 GC、网络延迟）；正因为缓存写通常远快于数据库写，这个窗口才极小 `[经验]`。
3. 崩坏词归一：源码将 Redis、缓存、并发、线程等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
