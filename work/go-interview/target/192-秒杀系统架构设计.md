# 192 秒杀系统架构设计：四要一不要

> 分类：架构设计 / 高并发 | 难度：L3 | 题型：架构题 | 频率：高 | 关键词：**秒杀、瞬时流量、数据要少、请求数要少、路径要短、依赖要少、不要过度设计**

> 原文锚点：第 9~29 段「秒杀特点是瞬时流量突增；设计原则五点：数据要少、请求数要少、路径要少、依赖要少、不要过度设计」

## 一句话总述
秒杀的本质是**瞬时流量突增 + 极热点的单行写**（库存）；架构上用五条原则收口——**数据要少**（精简传输与字段）、**请求数要少**（合并资源 + 前端置灰 + 服务端限频 + 答题防刷）、**路径要短**（CDN + 减少中间件跳数，请求直达）、**依赖要少**（减少外部调用，不可避免的做好降级熔断）、**不要过度设计**（按实际量级选型，核心链路才下重本）。

## 面试官视角
P5 只会说「加 Redis、加 MQ、加机器」；P6 能背出「四要一不要」并给出具体手段；P7 必须点破**「加机器治不了热点行写」**——库存扣减落到单行，行锁把所有并发串行化，加应用服务器只会把更多请求更快地挤到同一把锁上。能说出这句的人，说明真做过秒杀而不是背过八股。

## 主问答
**Q（面试官原话）：** 让你设计一个秒杀系统，你的架构原则是什么？

1. **先认清负载特征**：秒杀是**瞬时峰值**（几秒内涌入口级 QPS，抢完立刻回落）+ **极热点写**（所有人抢同一行库存）。因此核心矛盾不是"平均吞吐"而是**峰值削平 + 热点隔离** `[经验]`。
2. **数据要少**：请求与响应能精简就精简——秒杀页去掉装饰、静态化、字段裁剪 `[实测]`：同样 1000 条商品，9 字段完整结构（结构体本身 120 字节/条）裁到 4 字段精简结构（40 字节/条），**结构体体积缩减 66.7%**（不含字符串指向的堆上数据）。数据量小 → 网络传输快、序列化快、GC 压力小。
3. **请求数要少**：合并 JS/CSS 减少额外请求；点击后**按钮置灰**防重复点击；**服务端必须限频**（前端只能防君子） `[实测]`：本机令牌桶（容量 10、速率 100/s）实测瞬间打 100 次只**放行 10 次、拒绝 90 次**，静置 200ms 后再打 100 次仍是放行 10 次——桶容量决定了瞬时放行上限。加**答题/滑块**环节可进一步拉长请求时间、过滤脚本刷单。
4. **路径要短**：静态资源走 **CDN**；服务端减少中间件与组件间跳转，让请求**直达**处理逻辑（能省一个 RPC 就省一个） `[经验]`。
5. **依赖要少**：每一次外部调用都是一个故障点。能不调就不调；无法避免的依赖必须配**降级 + 熔断**（超时、连续失败次数、限流阈值三类触发指标），依赖出问题立即切兜底，避免拖垮全站 `[经验]`。
6. **不要过度设计 + 避免单点**：非核心功能（评价、推荐、积分）用简单实现甚至直接降级；**核心链路（库存、下单）才下重本**。同时全链路不能有单点（见 196） `[经验]`。

## 版本与兼容性
| 场景 | 方案 | 现在该怎么答 |
|---|---|---|
| 单机限频 | 进程内令牌桶 / `golang.org/x/time/rate` | 快但各实例独立，只能防单机 |
| 多机限频 | Redis 令牌桶 / Lua 原子脚本 | **生产用这个**，全局配额一致 |
| 网关限流 | Nginx `limit_req` / 网关层 | 在业务前挡第一波，成本最低 |
| 静态资源 | CDN + 页面静态化 | 把 90%+ 读流量挡在源站外 |
| 兜底降级 | 返回缓存值 / 静态页 / 排队页 | 与熔断配套，见 196 |

## 关键代码
```go
// 进程内令牌桶：秒杀接口限频的最小可用形态（多机请换 Redis + Lua）
type TokenBucket struct {
	mu     sync.Mutex
	tokens float64
	cap    float64
	rate   float64 // 每秒生成令牌
	last   time.Time
}

func (b *TokenBucket) Allow() bool {
	b.mu.Lock()
	defer b.mu.Unlock()
	now := time.Now()
	b.tokens += now.Sub(b.last).Seconds() * b.rate // 按时间补充
	if b.tokens > b.cap {
		b.tokens = b.cap // 桶容量即瞬时放行上限
	}
	b.last = now
	if b.tokens < 1 {
		return false // 无令牌，直接拒绝，不走后端
	}
	b.tokens--
	return true
}
```

## 总结与追问预判
答题骨架背这句：**「认清瞬时峰值 + 热点写 → 五条原则 → 限频防刷 → 削峰填谷 → 热点隔离」**。面试官下一步大概率追「库存怎么扣才不超卖」（Redis 预扣 / 数据库乐观锁 / 分段库存）或「请求怎么削峰」（MQ 异步化）。这两块是独立的机制题，本卡只给原则不展开。

`[边界]` 本卡只覆盖**架构设计原则（四要一不要）与限频/精简/降级的动机**，**不重述**缓存设计与链路缓存（见 193）、流量削峰与队列调优（见 194）、防超卖与分布式锁（见 195）、高可用与多活（见 196）、BASE 与降级分类（见 196）。
