# 609 channel 的设计哲学

> 分类：Go 并发 | 难度：L2 | 题型：概念题 | 频率：高 | 关键词：**CSP**/**通信共享内存**/**不要通过共享内存通信**
> 原文锚点：第 1~5 段「不要通过共享内存来通信，而是通过通讯来共享内存…设计哲学」

## 一句话总述
Go 的并发哲学是 **"不要通过共享内存来通信，而要通过通信来共享内存"**（CSP 模型）——channel 就是这一理念的原语：用发送/接收代替"锁 + 共享变量"，谁持有 channel 谁就临时拥有数据。

## 面试官视角
- 考察意图：是否理解 Go 并发的"通信优先"取向，而非只会加锁。
- 分档：P5 能背这句名言；P6 能讲清"通信共享内存 vs 共享内存通信"的区别；P7 能对比 channel 与 mutex/atomic 的取舍。
- 红旗答案：把 channel 和 mutex 当成完全等价、随手选其一。
- 惊艳点：点出 **channel 传递的是"数据所有权"，天然规避竞态**；并补充"高频小数据用 atomic/mutex 更轻" `[经验]`。

## 主问答
**Q（面试官原话）：** Go 为什么说"不要通过共享内存通信"？
**A：**
1. **结论**：CSP 取向——用通信（channel）共享内存，优于用锁保护共享内存。
2. **机制**：传统共享内存靠 mutex/atomic 防竞争，易死锁/漏锁；Go 主张把数据通过 channel 传递，接收方拿到后才操作，临界区被"传递"本身消解。
3. **边界**：channel 非银弹——**高频计数器/标志位用 atomic 或 mutex 更低开销**；channel 适合"传递所有权、协调协程生命周期、流水线"。

**加分层：** 这是 Rob Pike 名言，与 Erlang 的 actor 模型（发消息而非共享）思想同源。

## 关键代码
```go
ch := make(chan int)
go func() { ch <- 1 }() // 发送方把值"交付"出去
v := <-ch              // 接收方拿到后才拥有该值
```

## 总结与追问预判
channel 是 CSP 哲学的实现：用通信代替共享锁。追问接"channel 底层 hchan 结构"与"无缓冲 vs 有缓冲"。
