# 1221 选择性差与 OR 条件：为什么 OR 会让索引失效

> 分类：数据库 / MySQL 索引 | 难度：L4 | 题型：排错题 | 频率：高 | 关键词：**选择性、区分度、OR、AND、index_merge、index_merge_union、回表**

> 原文锚点：第 19~42 段「索引选择性很差的列就是指某个列上的重复值很多，那么查询优化器可能认为使用全表扫描比使用索引更有效…如果我们的查询里面使用了 or 条件，如果其中一个字段不是索引列，那么一定是无法使用索引的。因为 or 的含义就是两个条件里面只需要满足一个就可以了…在 user1 里面我们使用 or 条件，由于 name 列有索引而 age 列没有索引，所以 name 列是没有办法用到索引的。但是如果我们把这个 or 换成 and，这个时候它是可以用到索引的…我们需要确保 index_merge 和 index_merge_union 是 on 的状态」

## 一句话总述
两类失效：**①选择性差**——列上重复值很多（如性别只有男/女），优化器可能认为**全表扫描比走索引更有效**而放弃索引；**②OR 条件中存在非索引字段**——`OR` 只需满足其一，若只有一侧是索引列，另一侧非索引列**仍需全表扫描**，索引就失去意义；**换成 `AND` 则可以用到索引**（先用索引匹配，再对另一列过滤）。两侧都有索引时，靠 **`index_merge`（union）** 合并，需确保 **`index_merge` 与 `index_merge_union` 处于 `on`**。

## 面试官视角
- 考察意图：能否解释"为什么 OR 比 AND 更容易失效"，以及"有索引却不用"背后的**成本估算**逻辑。
- 分档：P5 知道低区分度列不适合建索引；P6 能说 OR 一侧无索引则整体失效；P7 能补上 **`index_merge` / `index_merge_union` 开关**、**换成 AND 可用索引**的原因，以及 **8.0 中 OR 两列可分别建单列索引**。
- 红旗答案：以为"只要 WHERE 里出现索引列就会用索引"；忽略优化器的**成本择优**。
- 惊艳点：**`OR` 与 `AND` 的差别在于过滤次序**——`AND` 可以**先用索引缩小范围再对另一列过滤**，而 `OR` 无法这样做，因为不满足索引条件的行**仍可能满足另一个条件** `[源码]`。

## 主问答
**Q（面试官原话）：** 为什么 `WHERE a=1 OR b=2` 用不到索引，换成 `AND` 就行？

1. **结论**：`OR` 要求"**两个条件满足其一即可**"，**若其中一个是非索引列，另一个索引列就失去意义**——因为不满足索引条件的行仍可能满足另一个条件，**必须对另一列做全表扫描**；而 `AND` 可以**先用索引列缩小范围，再对另一列过滤** `[源码]`。
2. **失效四 · 选择性差**：**索引选择性很差的列，是指某个列上的重复值很多**；此时**查询优化器可能认为使用全表扫描比使用索引更有效**，索引就可能失效；典型如**在性别列上建索引**——**性别只有男和女两个值，选择性很差**，**经优化器分析后索引可能不会被使用** `[源码]`。
3. **失效五 · OR 含非索引字段**：**如果查询使用了 `OR` 条件，且其中一个字段不是索引列，那么一定无法使用索引**；因为 **`OR` 的含义是两个条件里只需满足一个**，**只有一个条件列是索引列是没有意义的**——**若先按索引列过滤，就无法确定被过滤掉的行是否满足 `OR` 的另一条件**，所以**对另一个非索引字段依然需要全表扫描** `[源码]`。
4. **实测对照**：在 `user1` 表（**name 有索引、age 无索引**）上执行 `name='name3' OR age=4`，**查询分析显示没有用到索引**；在 `user3` 表（**name 与 age 组成联合索引**）上执行同样语句，**则用到了索引** `[源码]`。
5. **换成 AND 即可用索引**：**把 `OR` 换成 `AND` 时可以用到索引**——因为是 `AND` 条件，**可以先从索引树上匹配 name 字段的条件，匹配完成后再对 age 进行过滤**，所以 **`AND` 时能用上 name 列的索引** `[源码]`。
6. **两侧都有索引时的做法**：**OR 条件连接的两个列可以分别建立单列索引，也可以是联合索引**；同时必须确保 **MySQL 版本在 5.0 以上**，并且**查询优化器相关配置 `index_merge` 与 `index_merge_union` 处于 `on` 状态**——**只有这两个配置打开，多个字段的 `OR` 条件才会使用到索引** `[源码]`。

**加分层：** 判断顺序——**先看 OR 两侧是否都有索引**；都有才谈 `index_merge`，只有一侧就直接判定失效。工程改写常用 **`UNION ALL` 拆分两个条件**，各自走各自的索引。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| MySQL 5.0+ | 引入 `index_merge` | OR 两侧均有单列索引时可合并 |
| 全版本 | 开关 `index_merge` | 关闭则 OR 合并失效 |
| 全版本 | `index_merge_union` | 控制 union 型合并 |

## 关键代码
```sql
-- 场景：user1 表 name 有索引、age 无索引
CREATE TABLE user1 (id INT PRIMARY KEY, name VARCHAR(20), age INT, KEY idx_name (name));

-- 1) OR 一侧无索引 -> 用不上索引
EXPLAIN SELECT * FROM user1 WHERE name = 'name3' OR age = 4;

-- 2) 换成 AND -> 可以用 idx_name（先按 name 定位，再过滤 age）
EXPLAIN SELECT * FROM user1 WHERE name = 'name3' AND age = 4;

-- 3) 两侧都建单列索引 -> 走 index_merge（union）
ALTER TABLE user1 ADD INDEX idx_age (age);
EXPLAIN SELECT * FROM user1 WHERE name = 'name3' OR age = 4;
-- 观察 Extra：Using union(idx_name, idx_age)

-- 4) 确认优化器开关处于 on
SELECT @@optimizer_switch LIKE '%index_merge=on%'      AS merge_on,
       @@optimizer_switch LIKE '%index_merge_union=on%' AS union_on;

-- 5) 工程改写：用 UNION ALL 拆分，各自走各自索引
SELECT * FROM user1 WHERE name = 'name3'
UNION ALL
SELECT * FROM user1 WHERE age = 4 AND name <> 'name3';
```

## 总结与追问预判
**最爱追问的是"那我给 OR 两侧都建索引就一定能用吗"**——**不一定**：一是**优化器仍按成本择优**（任一侧选择性太差就可能直接全表扫），二是 **`index_merge` 开关必须打开**，三是 **`index_merge` 的合并本身有额外代价**，有时反而不如拆分写法。追问常接"低区分度列到底该不该建索引"——**一般不该单独建**；若查询确实高频，可把它作为**联合索引的后缀列**或依赖**索引下推**来发挥作用。

## ⚠️ 原文纠错
1. 事实核校：选择性差即重复值多且优化器可能改走全表扫描、OR 一侧为非索引列则整体失效、AND 可先用索引再过滤、两侧均建索引时依赖 `index_merge`、需 5.0 以上且 `index_merge` 与 `index_merge_union` 为 on——均与 MySQL 优化器行为一致 `[经验]`。
2. 补充：**原文称"OR 连接的两个列可以是联合索引"，需谨慎**——联合索引 `(name, age)` 中 `age` 不是最左列，`name=X OR age=Y` 实际多走**联合索引的全索引扫描**，而非高效定位；**`index_merge` 的 union 合并需要的是两个各自独立的单列索引** `[经验]`。
