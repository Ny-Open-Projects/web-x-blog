# 1835 写文件可靠性深挖

> 分类：内存与 OS / 文件系统 | 难度：L3 | 题型：深挖 | 频率：中 | 关键词：**可靠性层次** / **page cache** / **fsync** / **O_DIRECT** / **多副本**
> 原文锚点：第 1~50 段「缓冲IO写路径…进程崩溃不丢/系统崩溃才丢…fsync强制落盘…通用数据块层/IO调度器」

## 思路与架构
写文件的"不丢"是一条可靠性光谱，从弱到强：
- **page cache（默认）**：进程崩溃不丢，系统崩溃可能丢；吞吐最高。
- **fsync/fdatasync**：强制落盘，消除系统崩溃窗口；代价是磁盘 IO。
- **O_DIRECT / 直写**：绕过 page cache 直接写设备，避免双份缓存但需自管对齐。
- **应用层多副本**：数据库 WAL + 副本（如 Kafka 多副本），不靠单次 fsync 保命。

## 方案取舍
```text
写文件可靠性取舍（按需求取层）：
──────────────────────────────────────────────────
需求                      方案                  丢数据窗口
普通日志/可重建数据       page cache 延迟写回    系统崩溃丢未写回部分
必须落盘(事务提交/WAL)    fsync/fdatasync        无(调用后持久)
绕过缓存/特殊 IO          O_DIRECT              自管对齐，仍可选 fsync
高可用关键数据            多副本+WAL            单盘故障由副本兜底
→ 耐久性与性能反相关：越耐久越慢；按数据重要性分级，不无脑 fsync
```

## 答题技巧
```text
面试话术（先答 FAQ 再展开）：
1. 直接答：进程崩溃不丢(数据在 page cache 由内核托管)，系统崩溃且未写回才丢
2. 写路径：用户缓冲→page cache→延迟写回磁盘，write 返回≠落盘
3. 强制落盘：fsync 阻塞到完成、fdatasync 更轻(不同步元数据)
4. 权衡：fsync 代价是磁盘 IO，仅关键路径用；普通写靠 page cache
5. 进阶：真正高可用靠应用层多副本(如 WAL+副本)，不只依赖单次 fsync
```
