# 1119 fmt/反射/日志触发的逃逸

> 分类：Go 编译器/标准库 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**fmt**/**reflect**/**逃逸**/**GC**
> 原文锚点：第 85~104 段「string 作为 FMT 入参导致逃逸…日志打印都导致对象逃逸」

## 一句话总述
传给 `fmt` 系列、日志库（多调 fmt）、以及 `reflect.ValueOf` 的取值操作，入参几乎必然逃逸到堆——因为底层靠反射取值，反射需要值的稳定地址。原文"堆分配比栈分配开销大很多"表述过笼统，应落到 GC 成本。

## 面试官视角
- 考察意图：能否把"为什么 fmt 入参逃逸"讲到底（反射取值），并给出性能权衡而非死记结论。
- 分档：P5 知"fmt 参数会逃逸"；P6 懂反射取值是根因、日志库同理；P7 能权衡"大对象传指针减拷贝 vs 增加逃逸/GC 扫描"。
- 红旗答案："所有 fmt 调用都慢"（错，逃逸本身零运行期开销，慢在堆分配+GC）；"用指针一定更好"。
- 惊艳点：**`reflect.ValueOf(x)` 逃逸而 `reflect.TypeOf(x)` 不逃逸**——取"值"要地址、取"类型"不需要 `[源码]`。

## 主问答
**Q（面试官原话）：** 为什么日志打印会让对象逃逸到堆？
**A：**
1. **结论**：fmt/日志库通过反射取参数值，反射要求参数有稳定堆地址，故入参逃逸；`reflect.ValueOf` 同理，`reflect.TypeOf` 则不然。
2. **机制**：fmt 的 `Print*` 内部用 `reflect.ValueOf` 拆参，被拆的具体值必须搬到堆上让反射句柄持有；多数日志库底层调 fmt，所以日志参数也逃逸 `[源码]`。
3. **边界**：逃逸分析本身**零运行期开销**，开销在"堆分配走 mcache/mcentral/mheap + 后续 GC 标记清扫 + 增加 GC 扫描工作量"，并非"所有堆分配都慢"。

**加分层：** 大对象传参用指针可减一次大拷贝，但指针本身更易触发逃逸、增加 GC 扫描面；小对象反而应传值以减少逃逸与 GC 负担——这是 trade-off 而非铁律。

## 关键代码
```go
func f22(s string) {
    fmt.Println(s) // s 作为 fmt 入参 → 经反射取值 → 逃逸
}
func f21() {
    var x int = 5
    _ = reflect.TypeOf(x)  // 取类型：通常不逃逸
    _ = reflect.ValueOf(x) // 取值：需地址 → 逃逸
}
// go build -gcflags='-m'：f22 中 s "escapes to heap"，f21 中 ValueOf 参数 moved to heap
```

## 总结与追问预判
fmt/日志/反射的逃逸根因是"反射取值要地址"，性能代价落在 GC；优化是 trade-off。至此逃逸分析全貌已铺开，深挖卡收口。

## ⚠️ 原文纠错
1. 原文"**堆上动态分配的内存比栈上静态分配的开销大很多**"表述过笼统：准确说法是堆分配需经内存分配器（mcache/mcentral/mheap）且对象长期占用堆、增加 GC 标记清扫与扫描工作量；逃逸分析本身是**编译期零开销**的优化，不能说"所有堆分配都慢" `[源码]`。
2. 原文优化建议"大对象用指针减内存占用、小对象避免指针"方向正确，但漏了代价：**指针更易触发逃逸并增加 GC 扫描面**，应作为 trade-off 表述而非单向建议 `[经验]`。
