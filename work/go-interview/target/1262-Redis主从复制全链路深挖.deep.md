# 1262 Redis 主从复制全链路深挖

## 思路与架构
把主从复制拆成**「一条链路 + 两个缓冲区 + 三份状态」**，所有细节都能挂上去：

- **一条链路**：`slaveof 保存信息 → 定时任务建 socket → PING 探活 → 鉴权 → PSYNC 协商 → 全量(或增量) → 命令传播常态化`。
- **两个缓冲区**：
  1. **客户端输出缓冲区**（全量期间新写命令的暂存处）——满了会导致全量失败重来。
  2. **复制积压缓冲区**（主节点上的环形队列）——常态存放近期写命令，决定断连后能否续传。两者都「写满即失效」，但失效后果不同。
- **三份状态**：`runID`（节点身份，重启即变）、`复制偏移量`（按字节累加的进度）、`主从拓扑`（谁是谁的从库）。

判断一次重连走全量还是增量，只需问三个问题：**runID 变了吗？offset 之后的数据还在积压缓冲区里吗？主库有足够资源做全量吗？**——三者都决定最终路径。

## 方案取舍
- **全量 vs 增量**：全量简单可靠但代价高（BGSAVE 消耗 CPU 与内存、RDB 传输吃带宽、从库清空期间无法服务）；增量轻量但依赖积压缓冲区未被覆盖。**工程目标就是把重连尽量收敛到增量。**
- **积压缓冲区调大 vs 接受偶尔全量**：调大能显著延长可容忍的断连窗口，代价是主节点常驻内存；估算应为「写速率 × 断连时长 × 2」，而不是拍一个固定值。
- **从库全量期间继续服务 vs 阻塞**：继续服务（默认）保证可用性但可能返回陈旧数据；阻塞则把压力推给主库或让调用方感知。**读多写少的缓存场景通常选继续服务，强一致读应改走主库。**
- **异步复制 vs 强一致**：Redis 复制是异步的，主库写成功即返回，从库可能落后；这换来低延迟，代价是主库宕机时可能丢最后一段写入。**需要强一致就不要用原生复制兜底。**
- **主从复制 vs 哨兵 vs 集群**：复制解决数据冗余，哨兵解决自动故障转移，集群解决容量与分片。三者是叠加关系，不是替代关系——这是面试里被问混最多的地方。
- **多从库 vs 单从库**：多从提升读扩展与容灾，但主库要把写命令复制给所有从库，复制扇出本身也是主库负担。

## 答题技巧
- **开口区分「复制」与「故障转移」**：一句话「主从复制只管数据，自动切换靠哨兵」能立刻纠正考官最常见的诱导。
- **背下三个硬数字**：积压缓冲区默认 **1MB**；复制超时默认 **60 秒**；runID **40 位**。这三个数字是这块的锚点。
- **被问「断连后为什么全量」按序排查**：runID 是否变了 → offset 是否已被覆盖 → 积压缓冲是否太小。给出排查顺序比猜原因可信得多。
- **主动补一个反常识点**：积压缓冲区是**环形**的，写满**直接覆盖**而不是阻塞；所以「主库写太快」会让从库重连必走全量，形成雪崩式的复制风暴。
- **收尾给可验证动作**：`INFO replication` 看 `master_link_status` 与两个 offset 差值、`INFO server` 比对 runID、压测期监控 `rdb_bgsave_in_progress`——能讲出观测方式最加分。

## 细节与核心 API

**主从复制关键配置（两缓冲区 + 超时）：**

```conf
repl-backlog-size 1mb   # 复制积压缓冲区默认 1MB，环形；估算 = 写速率 × 断连时长 × 2
repl-timeout 60         # 复制超时默认 60s
repl-backlog-ttl 3600   # 从库全掉后积压缓冲区保留时长
```

**全量 vs 增量判定（重连先问三问）：**

```text
runID 变了吗？ → 变了必走全量
offset 之后的数据还在积压缓冲区吗？ → 被覆盖则全量
主库有足够资源做全量(BGSAVE)吗？ → 否则失败重来
```

**观测命令：**

```bash
redis-cli INFO replication   # master_link_status / master_repl_offset / slave_repl_offset / connected_slaves
redis-cli INFO server         # run_id（40 位，重启即变）
redis-cli INFO persistence    # rdb_bgsave_in_progress（全量期间监控）
```
