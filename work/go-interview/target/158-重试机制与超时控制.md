# 158 重试机制与超时控制

> 分类：微服务/高可用 | 难度：L3 | 题型：设计题 | 频率：高 | 关键词：**重试** / **指数退避** / **超时** / **重试风暴**
> 原文锚点：第 21~38 段「失败重试限次；非幂等谨慎；指数退避+超时上限；客户端传重试次；服务端反向抑制；每调用设超时防雪崩」

## 一句话总述
重试与超时是微服务容错的第一道防线：重试要"限次 + 指数退避 + 超时上限 + 防风暴"，超时是给每个调用设上限、避免资源被慢调用拖死——二者都为防止局部抖动演成雪崩。

## 面试官视角
- 意图：考察候选人对重试的"副作用"意识（重试风暴），而非只会"失败就重发"。
- P5 知道重试要限次；P6 能说清指数退避与超时上限；P7 能讲"服务端反向抑制重试"与"非幂等谨慎"。
- 红旗：以为重试越多越稳；对写操作（非幂等）也盲目重试。
- 惊艳点：指出"多层重试传递"会放大流量（客户端重试→服务端又重试→雪崩），服务端可用错误码/标志反向告知"别重试"。

## 主问答
**Q（面试官原话）：** 微服务调用失败，重试该怎么设计才不翻车？
**A：**
1. **结论**：重试必须限次（只核心调用重、控次数或按比例），配**指数退避**（1/2/4/8s）与**总超时上限**（如 >10s 停），非幂等操作慎用。
2. **机制**：退避给对端恢复窗口；客户端可把"已重试次数"传给服务端，服务端过载时直接拒绝超次请求避免放大；超时给单次调用设上限，超时就终止，防资源被慢调用长期占用 `[源码]`。
3. **边界**：重试是"放大流量"的操作——多层传递（客户端+服务端都重试）易雪崩；服务端可用约定错误码/响应头告诉客户端"无需重试"，从源头抑制 `[经验]`。

## 关键代码

```go
// 示意，未验证：指数退避重试（带总超时与次数上限）
func callWithRetry(ctx context.Context, tries int) error {
    var err error
    backoff := time.Second
    deadline := time.Now().Add(10 * time.Second) // 总超时上限
    for i := 0; i < tries; i++ {
        if time.Now().After(deadline) {
            return errors.New("retry timeout")
        }
        if err = doCall(ctx); err == nil {
            return nil
        }
        time.Sleep(backoff)
        backoff *= 2 // 1s,2s,4s,8s...
    }
    return err
}
```
