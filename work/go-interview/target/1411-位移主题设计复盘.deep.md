# 1411·深 位移主题设计复盘：把元数据存进自己的 topic，Kafka 到底赢在哪？

> 分类：消息中间件 / Kafka | 难度：L4 | 题型：架构题 | 频率：中 | 关键词：**__consumer_offsets**/**元数据自托管**/**日志压实**/**哈希分桶**/**副本因子**/**ZooKeeper**
> 原文锚点：第 5~16、24~31 段「在旧的消费者客户端当中，消费位移是存储在 ZooKeeper 当中…由于 ZooKeeper 在性能和扩展方面逐渐暴露出的一些问题…将位移存储在 Kafka 的 topic 中，可以提高系统的性能和可靠性，同时减少对 ZooKeeper 的依赖」
> [边界] 本文是 `1411-offset-topic` 的设计层深挖，主卡已讲的结构与常数此处不重述；提交策略与重复消费见 1417，重平衡流程见 147。

## 思路与架构

位移主题的本质，是 Kafka 把**自己的元数据**托管给了**自己的存储引擎**。把这条主线拆开看：

```text
演进主线：外部协调器 → 自托管
─────────────────────────────────────────────────────
0.8.x   消费位移 ──> ZooKeeper
        问题：ZK 是"低频元数据"的设计，写放大扛不住高频位移提交；
              强依赖外部组件，ZK 抖动直接拖垮消费侧

0.9+    消费位移 ──> 内部 topic __consumer_offsets
        收益：① 复用 topic 的分区/副本/自动扩展能力，天然水平扩展
              ② 写入路径与普通消息完全一致，无需维护第二套存储
              ③ 去掉对 ZooKeeper 的强依赖，运维面收敛

2.x+    __consumer_offsets 兼存 GroupMetadata（成员 / generation / leader）
        收益：消费组协调状态与位移同处一处，重平衡时无需跨系统读
```

三个关键设计决策：

1. **为什么是 50 个分区而不是 1 个**：位移提交的 QPS 与"消费组数 × 分区数"成正比，单分区必然成为写入热点。50 是个**经验折中**——足够分散常见规模的压力，又不至于因分区过多拖慢日志压实与 leader 选举。
2. **为什么用哈希取模而不是范围划分**：`groupID` 是字符串，没有天然顺序；哈希能保证**同一个组的位移永远落在同一个分区**，这对"按 key 有序"和"日志压实"都是必需的——同组的历史位移必须串行可比。
3. **为什么必须开日志压实**：位移是**状态**不是**事件**。一个三元组只需要最新值，历史版本毫无价值。用 `cleanup.policy=compact` 按 key 去重，既控制了存储膨胀，又让消费者重启时能直接读到最新位移。

## 方案取舍

```text
方案 A：位移存 ZooKeeper（0.8.x 老方案）
  优：实现简单，天然强一致
  劣：ZK 写性能低、扩容难；高频提交会把 ZK 打爆；多一套运维组件

方案 B：位移存外部 KV（Redis / MySQL）
  优：读写快
  劣：引入外部依赖的一致性与可用性问题；等于把 Kafka 的可靠性降到外部存储的可靠性

方案 C：位移存自己的内部 topic（0.9+ 现行方案）  ← 选中
  优：零外部依赖；复用分区/副本/压实全部能力；写入路径与数据面统一
  劣：有"自举"问题——Broker 启动时该 topic 尚不存在，需首次消费时自动创建；
      副本因子默认 3，单 broker 环境会创建失败，需手动下调
```

- **自举问题的处理**：`__consumer_offsets` 由 Broker 在**集群中第一次有消费者消费时自动创建**，用户无需手动建。但这也意味着**第一次消费会有一段创建延迟**，生产上更稳妥的做法是**提前手动建好并指定分区数与副本因子**。
- **副本因子 3 的隐性约束**：副本数不能超过 broker 数。3 副本在**单节点开发环境会直接创建失败**，这是新手最常见的踩坑点——要么起 3 个 broker，要么把 `offsets.topic.replication.factor` 调成 1。
- **分区数改不动的代价**：topic 一旦创建，`offsets.topic.num.partitions` 再改**不生效**。若集群后期消费组规模暴涨，50 个分区可能不够，只能重建 topic 或手工扩容——**建集群时就应该按未来规模预设**。

## 答题技巧

- **先讲"为什么换"，再讲"怎么存"**。面试官问位移主题，真正想听的是**从 ZooKeeper 迁出来的动机**，不是背几个常数。
- **准备一句"自托管"总结**：「Kafka 把元数据交给自己的存储引擎，换来的是**零外部依赖 + 水平扩展 + 写入路径统一**。」这句话能直接拉到架构视角。
- **数字要报得准**：**0.9 起**、**50 分区**、**副本因子 3**、**KV 三元组**、**记录下一条位移**。这五个点缺一个就会被追问。
- **主动踩刹车的地方**：说"每个消费组一个位移主题"是**最常见误解**，正确说法是全集群共用一个 topic、组按哈希落分区。主动澄清反而加分。
- **别踩的坑**：不要把位移主题和"提交策略"混为一谈——**它只负责存，不负责决定何时提交**；提交时机是 `enable.auto.commit` 与手动提交的事。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Kafka 0.8.x | 位移存 ZooKeeper | 仅老集群 |
| Kafka 0.9.0 起 | 引入新消费者 + 内部 topic | **现行方案起点** |
| Kafka 2.x 起 | 兼存 `GroupMetadata` | 不只存位移 |
| Kafka 3.x 起 | KRaft 模式可脱离 ZooKeeper | 位移仍在内部 topic，未变 |
| 默认配置 | 50 分区 / 副本 3 / 压实 | 建集群时按规模预设 |

## 细节与核心 API

**内部 topic `__consumer_offsets` 的关键配置（建集群时预设，改了不生效）：**

```bash
# 0.9+ 引入，全集群共用一个 topic；group 按 hash(groupID) % 50 落分区
kafka-topics.sh --bootstrap-server b:9092 --describe --topic __consumer_offsets
```

```properties
offsets.topic.num.partitions=50            # 经验折中：分散常见规模压力，又不拖慢压实/选举
offsets.topic.replication.factor=3        # 副本数不能超过 broker 数；单 broker 开发需调成 1
log.cleanup.policy=compact                 # 位移是状态不是事件，按 key 压实，控存储膨胀
```

**自举与坑：**

```text
- 第一次消费由 Broker 自动创建（有创建延迟）；生产更稳妥是提前手动建好
- 副本因子 3 在单节点开发环境会创建失败 → 起 3 broker 或调 offsets.topic.replication.factor=1
- 兼存 GroupMetadata（成员/generation/leader），重平衡无需跨系统读
```
