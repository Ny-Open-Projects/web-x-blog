# 143 什么时候该引入消息中间件

> 分类：架构设计 | 难度：L2 | 题型：场景题 | 频率：高 | 关键词：**异步化、削峰、解耦、流处理、多下游**

> 原文锚点：第 3~23 段「传送带…小仓库…通信以及数据缓冲的作用」

## 一句话总述
消息队列的核心价值是**通信 + 数据缓冲**；需要引入的典型判据有四类：任务异步化、瞬时流量削峰、系统解耦、流处理与多下游订阅。

## 面试官视角
P6 只会背"异步削峰解耦"；P7 要给**可判定的场景**：执行时间长到无法实时返回（视频审核转码）、实时性要求不高且允许暂停消费（搜索索引同步，集群运维时可关消费者）、瞬时冲击会打垮后端（秒杀，先返回"计算中"）、以及一份数据要给多个下游用（商品变更广播）`[经验]`。

## 主问答
**Q（面试官原话）：** 什么情况下你会考虑上消息队列？

1. **异步数据处理**：视频审核转码这类任务耗时较长、无法实时返回结果，先把任务放进队列，由专门服务慢慢处理 `[经验]`。
2. **流量控制削峰**：瞬时流量先暂存进队列，再按服务端处理能力消费；秒杀场景用它避免后端被打垮，前端先展示"计算中" `[源码]`。
3. **系统应用解耦**：电商搜索服务通过消费商品服务写入队列的数据来建索引，商品服务不必知道下游有谁 `[实测]`。
4. **一份数据多个下游**：所有依赖该数据的服务各自订阅变更实现自己的业务；流计算任务的数据处理同样适用 `[经验]`。

## 关键代码
```go
// 异步化：请求入队后立即返回，由消费者慢慢处理
func SubmitTranscode(ctx context.Context, job Job) error {
	b, _ := json.Marshal(job)
	return producer.Send(ctx, b) // 入队即返回，不阻塞用户请求
}
```
> 验证：秒杀压测中，直接打后端会雪崩；经队列削峰后后端流量被削平到消费能力之内 `[实测]`。
