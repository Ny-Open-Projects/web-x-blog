# 1239 深挖：InnoDB 行锁本质、死锁成因与锁事故排查四步

> 分类：数据库 / MySQL 锁 | 难度：L5 | 题型：综合题 | 频率：高 | 关键词：**行锁本质、加锁对象是索引、三种行锁、RR 默认临键、死锁检测、锁等待、blocking_pid、INNODB_TRX**

> 原文锚点：第 26~40、50~70 段「InnoDB 行锁是通过对被索引数据页上的记录加锁实现的，它加锁的对象是索引…主要有三种类型的锁…临键锁是 InnoDB 最基本的加锁单位…只有通过索引条件检索数据，InnoDB 才能使用行级锁…死锁是指两个或多个事务之间相互持有和请求相同资源上的锁，从而产生了循环依赖…锁等待时间长和死锁不是一回事…MySQL 支持死锁检测和锁的超时机制…大多数情况下只需要重新从头开始执行被回滚的事务就可以了」

## 思路与架构

按「**行锁本质 → 死锁 → 排查**」三层把握：

1. **行锁本质（加锁对象是索引）**：
   - InnoDB 行锁是**通过对被索引数据页上的记录加锁实现的**，**加锁的对象是索引**（不是数据行本身） `[源码]`。
   - **三种行锁**：
     - **记录锁（Record Lock）**：锁定**单个记录**，**读已提交（RC）与可重复读（RR）都支持** `[源码]`。
     - **间隙锁（Gap Lock）**：锁定**索引记录之间的间隙**，确保**间隙不变**，**只在 RR 下支持** `[源码]`。
     - **临键锁（Next-Key Lock）**：**记录锁与间隙锁的组合**，锁住记录行的同时锁住数据前后的范围；**是 InnoDB 最基本的加锁单位**，**只在 RR 下支持** `[源码]`。
   - **推论**：正因为加锁对象是索引，**只有通过索引条件检索数据，InnoDB 才能使用行级锁**；否则退化为全表的行锁（见 `1239-select-star-vs-covering`）。
   - **RR 下的默认行为**：**RR 下 InnoDB 对记录的加锁默认都是临键锁**；**当操作含有唯一索引时，会对临键锁优化降级为记录锁**——只锁索引记录本身，而非一个范围 `[源码]`。
   - **无主键表**：即使表**没有主键、也没有任何索引**，InnoDB 仍会扫描聚簇索引并给**它自己维护的隐藏 ID** 加锁——加锁行为不变，只是看不到具体 id `[源码]`。
2. **死锁（定义、成因、处理）**：
   - **定义**：**两个或多个事务之间相互持有和请求相同资源上的锁，从而产生循环依赖** `[源码]`。
   - **三个成因**：以**不同的顺序**锁定资源；多个事务**锁定相同的资源**；本质都是**循环依赖** `[源码]`。
   - **与锁等待的区别**：**锁等待时间长和死锁不是一回事，不能混为一谈**——锁等待只是"排队"，死锁是"成环且无人能让步" `[源码]`。
   - **检测与回滚**：MySQL **支持死锁检测与锁超时机制**；InnoDB 检测到循环依赖后**立即返回错误信息**；开启默认死锁检测后，死锁出现时**事务会自动回滚**（实测两个事务只剩一个存活） `[源码]`。
   - **应用侧应对**：**事务型系统的死锁无法避免**，所以**应用设计时必须考虑如何处理死锁**；**大多数情况下只需从头重新执行被回滚的事务**，除非又遇到另一个死锁 `[源码]`。
3. **排查四步（事故处理流程）**：
   - **① 看有无等待的锁**：执行 `SHOW ENGINE INNODB STATUS`，查看 InnoDB **当前有没有等待的锁**（等待数为 0 说明无等待） `[源码]`。
   - **② 看活跃事务**：查 `information_schema.INNODB_TRX`，看**当前运行中的事务** `[源码]`。
   - **③ 看锁等待明细**：查 `sys` 库下的 **`sys.innodb_lock_waits`**，得到**锁等待的详细信息** `[源码]`。
   - **④ 取三个关键字段**：`blocking_pid`（**当前正在阻塞的 PID**）、`blocking_trx_id`（**当前正在阻塞的事务 ID**）、`blocking_query`（**正在阻塞的查询语句**） `[源码]`。

## 方案取舍

| 关注点 | 方案 | 代价 / 收益 |
|---|---|---|
| 加锁粒度 | 行锁（锁索引记录） | 并发高；无索引则退化为全表行锁 |
| RR 默认临键锁 | 顺带锁间隙，杜绝幻读 | 并发度下降、死锁概率上升 |
| 唯一索引降级 | 只锁记录本身 | 锁范围最小，代价是需要唯一索引 |
| 死锁检测 | 自动检测 + 回滚一方 | 立即报错，但检测本身有 CPU 开销 |
| 锁等待超时 | 超时自动放弃 | 只解决"等太久"，不解决成环 |
| 应用侧重试 | 重跑被回滚事务 | 简单有效，需保证事务幂等 |

取舍要点：**临键锁是 InnoDB 用"更大的锁范围"换取"RR 下无幻读"**；代价是并发度下降与死锁概率上升。因此写密集且能容忍幻读的场景常改用 **RC + 显式唯一约束**，把间隙锁整体去掉。死锁层面，**检测 + 回滚 + 应用重试**是唯一可行解——死锁无法避免，只能"快速失败并重试"。

## 答题技巧

1. **先立"加锁对象是索引"这个纲**：所有加锁规则都是这一句的推论（无索引→全表行锁；选哪棵树→锁哪些记录）。
2. **三种锁要带隔离级别**：记录锁 **RC/RR 都支持**，间隙锁与临键锁**只在 RR 支持**——只报锁类型不报级别会被扣分。
3. **必须说"临键锁是最基本的加锁单位"**：这句话是原文的原话，也是理解所有退化规则的起点。
4. **死锁与锁等待要主动区分**：**锁等待长 ≠ 死锁**；死锁是循环依赖，靠检测 + 回滚解决。
5. **排查要落到三个字段**：`blocking_pid` / `blocking_trx_id` / `blocking_query`——报出字段名比泛泛说"查锁表"更有说服力（视图清单与版本迁移见 `1240-lock-views`）。
6. **止步档位**：能讲清三种锁与 RR 默认行为即达 L4；能补上死锁三成因、"锁等待 ≠ 死锁"、排查四步与三个关键字段，即达 L5。

## ⚠️ 原文纠错
1. 事实核校：行锁通过对索引记录加锁实现、三种锁类型及其隔离级别支持、临键锁为最基本加锁单位、RR 下默认临键锁且遇唯一索引降级、无主键表仍对隐藏 ID 加锁、死锁为循环依赖且与锁等待不同、死锁检测后自动回滚、应用应重试被回滚事务、排查四步与三个关键字段——均与 InnoDB 实现一致 `[经验]`。
2. 补充：原文未提**间隙锁与临键锁在 RC 下不生效**，也未提**死锁检测可通过 `innodb_deadlock_detect` 关闭**（高并发热点更新场景下关掉检测、改用锁等待超时是常见调优手段）；另外 `sys.innodb_lock_waits` 在 8.0 中底层已改读 `performance_schema.data_lock_waits` `[经验]`。
3. 崩坏词归一：源码将 InnoDB、临键锁、间隙锁、记录锁、死锁、意向锁、information_schema 等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
