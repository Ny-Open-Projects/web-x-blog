# 715 动态配置的事故红线：连接配置绝不热更

> 分类：配置中心 / 稳定性 | 难度：L4 | 题型：经验题 | 频率：高 | 关键词：**动态配置风险、连接配置、发版流程、健康检测、线上事故**

> 原文锚点：第 6~17 段「应尽量避免动态更新配置…数据库连接等访问配置避免动态更新…走配置审核与发版流程；测试误调线上接口开启迁移开关致事故」

## 一句话总述
动态更新配置是把双刃剑：应**尽量避免**用，尤其数据库/连接类配置绝不热更——配错 IP/密码会直接打挂线上。安全做法是走配置审核与发版流程，靠健康检测兜底。

## 面试官视角
P6 知道动态配置有风险；P7 能讲出事故案例根因（测试 DNS 缓存误调线上 API 开迁移开关），并指出「动态开关应走完整发版而非暴露 API 随意改」。

## 主问答
**Q（面试官原话）：** 动态配置有什么坑？哪些配置不能热更？

1. **尽量少用**：动态更新配置非万能，许多事故源于配置使用不当，优先静态配置 `[经验]`。
2. **连接配置禁热更**：数据库 IP/密码等访问配置一旦动态改错，服务直接连不上，瞬时打挂线上 `[源码]`。
3. **走发版流程**：线上配置变更应审核后随发版走；新应用健康检测不通过就不启动，对线上近乎零影响 `[经验]`。
4. **事故案例**：测试环境因 DNS 缓存误调线上 API，打开了本应夜间执行的迁移开关，引发大量数据迁移 `[经验]`。
5. **开关别暴露 API**：控制迁移等高风险逻辑的配置，应走应用配置完整发版，而非暴露接口随意改 `[经验]`。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| 任意版本 | 动态配置非标配 | 默认静态+发版 |
| 云原生时代 | k8s 健康检测兜底 | 新版本不启动即回滚 |
| 任意版本 | API 随意改=风险 | 高风险开关收回归发版 |

```go
if err != nil { log.Fatal(err) } // 连不上直接失败，由健康检测拦截
// 动态开关改走 ConfigMap + 滚动发版，而非 HTTP API 热改
```
