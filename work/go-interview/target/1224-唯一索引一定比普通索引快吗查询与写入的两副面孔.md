# 1224 唯一索引一定比普通索引快吗？查询与写入的两副面孔

> 分类：数据库 / MySQL 索引 | 难度：L3 | 题型：辨析题 | 频率：高 | 关键词：**唯一索引、普通索引、查询性能、change buffer、随机读、写多读少、业务层去重**

> 原文锚点：第 1~29 段「两个隐藏前提：相同索引结构（默认 B+ 树）、相同数据集；查询效率几乎相同；写入效率差异很大，因为唯一索引无法使用 change buffer」

## 一句话总述
**查询上几乎一样快，写入上普通索引明显更快。** 两者都是 B+ 树，在「字段值本身具备唯一性 + 数据集相同」两个前提下，普通索引最多比唯一索引**多探一次**（无 `LIMIT 1` 时）；但写入时**唯一索引必须做唯一性校验、必须把索引页读进内存，因此用不上 change buffer**，写多读少场景下会产生大量随机读 IO，性能差距显著。

## 面试官视角
P5 答"唯一索引更快因为有唯一约束"；P6 能说出「查询差不多、写入差很多」并提到 change buffer；P7 必须补上**两个隐藏前提**（相同索引结构 + 相同数据集），并给出工程结论：**写多读少的字段慎用唯一索引，唯一性可以放到业务层或 Redis `SETNX` 兜底**。能主动指出"题目本身藏了前提"是加分项。

## 主问答
**Q（面试官原话）：** 唯一索引一定比普通索引快吗？

1. **先拆两个隐藏前提** `[经验]`：① **相同的索引结构**——若引擎支持哈希索引，则两者查询都是 O(1)、无差异，但唯一索引写入要做唯一校验仍更慢；默认按 **B+ 树**比较。② **相同的数据集**——字段值本身要具备唯一性，且字段大小、值稀疏程度一致，否则没有可比性。
2. **查询性能：几乎相同，差距只有"多探一次"** `[经验]`：两者都基于 B+ 树定位。唯一索引命中第一条即停（有唯一保证）；普通索引在没有 `LIMIT 1` 时，找到一条后**还会继续往下探一次**确认是否还有相同值。**在字段值本就唯一的前提下，普通索引只比唯一索引多一次查找**。
3. **这一点差距为什么可以忽略** `[源码]`：MySQL 一个数据页 **16KB**，能装大量索引项，"多探一次"绝大多数情况下**还在同一个页内**，且读取时有预读机制会顺带加载相邻页。因此两者查询效率**微乎其微**。
4. **写入性能：差距巨大，根因是 change buffer** `[源码]`：普通（非唯一）索引的写入可以走 **change buffer**——目标索引页不在 buffer pool 时，**不立即从磁盘加载**，只把修改记进 change buffer，等该页被读到时再合并，**省掉一次随机读**。唯一索引**必须校验唯一性，而校验就必须把页读进来**，这次随机读省不掉，**所以用不了 change buffer**（详见 1212）。
5. **工程结论** `[经验]`：**写多读少**的字段要慎用唯一索引——大量磁盘随机读会占用 IO 资源，甚至拖垮整个实例。此时应改用**业务层保证唯一性**（如 Redis `SETNX`、幂等表 + 普通索引，见 1223、`1223-unique-ensure-methods.deep`）。
6. **change buffer 生效还有前提** `[经验]`：**写入的数据短时间内不被读取**才划算；如果写完立刻读，合并马上触发，优化收益归零——**这种"写完即读"的场景反而可以放心用唯一索引**。

## 追问链
| 层级 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | 唯一索引查询更快吗？ | 破除直觉 | 几乎一样快，不是"更快" | 笃定更快，停在 L1 |
| L2 | 比较的前提是什么？ | 严谨性 | 相同索引结构 + 相同数据集且字段唯一 | 不提前提，停在 L2 |
| L3 | 普通索引为什么只慢一点？ | 机制 | 无 LIMIT 1 时多探一次，且多在同一页内 | 说不清多探一次，停在 L3 |
| L4 | 写入为什么差很多？ | 核心 | 唯一索引要校验唯一性必须读盘，用不了 change buffer | 不知道 change buffer，停在 L4 |
| L5 | 什么时候该用唯一索引？ | 工程判断 | 写完立刻读、或更新很少时可用；写多读少走业务层去重 | 一律"都用唯一索引"，停在 L5 |

## 版本与兼容性
| 版本 | 行为 | 现在该怎么答 |
|---|---|---|
| MySQL 5.5 之前 | 只有 insert buffer，仅优化 insert | 老版本收益更小 |
| MySQL 5.5 起 | 改名 **change buffer**，覆盖 insert/delete/update | 按 change buffer 答 |
| 全版本 | `innodb_change_buffer_max_size` 默认 **25**，上限 50 | 写多读少可调大 |
| 全版本 | `innodb_change_buffering` 默认 `all` | `none` 才是关闭 |
| 8.0 | 索引结构未变 | B+ 树结论不变 |

## 关键代码
```sql
-- ① 观察 change buffer 是否在工作（唯一索引写入时这里的 merges 不会增长）
SHOW GLOBAL STATUS LIKE 'Innodb_ibuf%';

-- ② 两个关键配置
SHOW VARIABLES LIKE 'innodb_change_buffer_max_size';   -- 默认 25，上限 50
SHOW VARIABLES LIKE 'innodb_change_buffering';         -- 默认 all

-- ③ 查询侧：普通索引加 LIMIT 1 可抹平"多探一次"的差距
SELECT id FROM t WHERE uk_col = ? LIMIT 1;   -- 与唯一索引等效，命中即停

-- ④ 写多读少时改用业务层去重：普通索引 + 幂等表唯一键兜底
CREATE TABLE t (
  id     BIGINT PRIMARY KEY AUTO_INCREMENT,
  biz_key VARCHAR(64) NOT NULL,
  KEY idx_biz_key (biz_key)          -- 普通索引，写入走 change buffer
);
CREATE TABLE t_uniq (
  biz_key VARCHAR(64) PRIMARY KEY    -- 唯一性由这张小表的主键兜底
);
```

## 总结与追问预判
答题骨架：**「两个前提 → 查询几乎相同（多探一次可忽略）→ 写入差很多（change buffer 用不了）→ 写多读少走业务层去重」**。面试官下一步常追「change buffer 会不会丢数据」（不会，同时写 redo log 并定期刷系统表空间）、「那能不能把唯一索引都改成普通索引」（**不能**，唯一性是业务约束，不能为性能牺牲正确性）。

`[边界]` 本卡只做**唯一索引 vs 普通索引的查询/写入性能对比与选型建议**，**不重述** change buffer 的完整机制与配置项（见 1212）、B+ 树结构本身（见 1217）、唯一性的多种保证方式（见 1223、`1223-unique-ensure-methods.deep`）、索引设计通则（见 1221）。
