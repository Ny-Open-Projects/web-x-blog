# 1215 REDUNDANT vs COMPACT：偏移列表 vs 长度列表

> 分类：MySQL 存储 | 难度：中高 | 题型：对比 | 频率：中 | 关键词：**REDUNDANT、字段长度偏移列表、NULL 比特位、COMPACT、空间浪费**

> 原文锚点：第 74~84 段「REDUNDANT 为 5.0 前格式、偏移列表逆序、靠相邻差值算长度、NULL 比特位」

## 一句话总述
REDUNDANT 是 MySQL 5.0 之前的旧行格式，其首部是「**字段长度偏移列表**」（所有列含隐藏列的长度偏移量，逆序存放，靠相邻两值之差算出各列长度），且**没有独立的 NULL 列表**——把「是否为 NULL」编码进偏移量第一个比特位（NULL 比特位）。COMPACT 改为「变长字段长度列表 + 独立 NULL 值列表」，更省空间，故 5.1 起取代 REDUNDANT 成为默认。

## 面试官视角
对比题考「为什么 COMPACT 更省」。考官期待你说清：REDUNDANT 对所有列（含隐藏列、NULL 列）都存偏移量、且把 NULL 判断塞进比特位，冗余大；COMPACT 只存变长非 NULL 列的长度 + 独立位图，数据量大时磁盘占用明显更少。

## 主问答
**Q（面试官原话）：** REDUNDANT 和 COMPACT 行格式有什么区别？

1. **首部结构不同**：REDUNDANT 首部是「字段长度偏移列表」，COMPACT 首部是「变长字段长度列表」+「NULL 值列表」两部分。
2. **长度算法不同**：REDUNDANT 存的是每个字段的**偏移量**，靠两个相邻数值的**差值**计算各列长度；COMPACT 直接存各变长字段的字节长度。
3. **NULL 处理不同**：REDUNDANT 无独立 NULL 列表，把每个列偏移量**第一个比特位**作为 NULL 比特位（为 1 则该列值为 NULL）；COMPACT 用独立的 NULL 值列表按位标记。
4. **空间与现状**：REDUNDANT 冗余浪费、数据量大时磁盘占用更多，5.0 后被 COMPACT 取代，现版本基本不再使用。

## 总结与追问预判
核心：**REDUNDANT 用偏移列表+NULL 比特位（冗余），COMPACT 用长度列表+独立 NULL 位图（省空间）**。追问常接「DYNAMIC 又改了什么」（见 1215-row-overflow）。
