# 137 为什么需要段合并（segment merge）

> 分类：Elasticsearch 存储 | 难度：L4 | 题型：原理题 | 频率：中 | 关键词：**段合并**/**段数量**/**文件描述符**/**物理删除**/**压缩比**
> 原文锚点：第 35~37 段「段合并的目的与触发背景」

## 一句话总述
每次增删改都会产生新段，积累后段数过多会消耗文件描述符、增加检索时需扫描的段数，拖累速度；段合并（merge）的核心目的是**减少段数量**、在合并中**物理删除标记文档**、并**提升压缩比**（小段压缩比低，合并后更高）。

## 面试官视角
- 考察意图：是否理解 merge 既是「清理」也是「优化」，以及触发 merge 的多种时机。
- 分档：P5 知 merge 减少段数；P6 知 merge 物理删标记文档、提压缩比；P7 知多种触发时机与自然/API 触发的差异。
- 红旗答案：以为 merge 只是为了合并小文件；或不知道 force merge 的代价。
- 惊艳点：点出「自然写入只合小段，force merge API 会合大段、负载显著更大」。

## 主问答
**Q（面试官原话）：** ES 为什么要做段合并？什么时候触发？
**A：**
1. **段膨胀问题**：每次操作都生成小段，随时间积累段数爆炸，过多段消耗文件描述符与内存/CPU，并增加检索扫描段数。
2. **merge 三作用**：① 减少段数量；② 合并中物理删除打了删除标记的文档（回收空间，利于频繁更新删除场景）；③ 提升压缩比（小段压缩比小，合并后更大）。
3. **触发时机一（自然写入）**：数据写入 flush 落盘形成新段后，判断是否需要 merge。
4. **触发时机二（commit）**：flush 线程调用 Lucene commit，强制内存中段落盘并触发 merge。
5. **触发时机三/四（API/关闭）**：显式调用 force merge API（可指定最终段数）；索引关闭时落盘并检查待合并段。
