# 1237 隐式锁：插入未提交，别人为什么读就被卡

> 分类：MySQL / InnoDB | 难度：L4 | 题型：原理题 | 频率：中高 | 关键词：**隐式锁、延迟加锁、锁转换、意向锁**

> 原文锚点：第 1~16 段「插入操作只加意向排他锁，记录行没有加任何锁…获取读锁被阻塞」

## 一句话总述
InnoDB 对新插入的记录**默认不建锁结构**，只靠记录里的事务标识形成一把隐式锁；直到别的事务真来抢，才由**抢锁方**把隐式锁转成显式锁、替原事务加上，然后自己阻塞。

## 面试官视角
P6 只知道"插入会加排他锁"；P7 要指出插入瞬间**行上没有锁对象**，加锁动作被推迟到冲突发生，即延迟加锁 `[经验]`。还要说清两个反直觉点：替原事务补的是**排他型记录锁**，且补完之后**抢锁方自己进入等待** `[源码]`。

## 主问答
**Q（面试官原话）：** 我插入一条没提交的记录，另一个事务读它为什么会被卡住？

1. **插入只加表级意向锁**：原文实测，事务 A 插入 id=7 后锁视图里只有表上的意向排他锁，**新行上没有锁** `[实测]`。
2. **靠隐藏列撑起隐式锁**：记录带一个隐藏的事务标识列，写着最后改动它的事务；该事务仍活跃，就等价于这行被它锁着 `[源码]`。
3. **冲突时才转显式锁**：事务 B 申请该行的共享锁时，先给表加意向共享锁，再替事务 A 在这行**补一把排他记录锁**，最后自己排队 `[经验]`。
4. **收益是省锁对象**：批量插入大量新行时不必逐行建锁结构，锁内存与申请开销都省下来 `[经验]`。

## 关键代码
```sql
-- 会话 A
BEGIN;
INSERT INTO t (id, name) VALUES (7, '7');   -- 只加表级意向排他锁
-- 会话 B：被阻塞
BEGIN;
SELECT * FROM t WHERE id = 7 LOCK IN SHARE MODE;  -- 触发隐式锁转显式
```
```go
rows, _ := db.Query(`SELECT LOCK_TYPE, LOCK_MODE, LOCK_STATUS
                     FROM performance_schema.data_locks WHERE OBJECT_NAME = 't'`)
```
> 验证：A 未提交时 B 的加读锁语句挂起，此时锁视图中该行出现记录锁 `[实测]`。
