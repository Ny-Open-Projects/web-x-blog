# 405 go.mod 结构与伪版本号

> 分类：工程化与测试 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**go.mod** / **module/require** / **直接/间接依赖** / **伪版本**
> 原文锚点：第 70~92 段「module name…go版本…require 直接+间接…伪版本三部分」

## 一句话总述
go.mod 记录模块路径、最低 Go 版本与依赖：require 列出直接依赖，间接依赖仅当其自身无 go.mod 时才写入并生成伪版本号（版本+提交时间+commit 前缀）。

## 面试官视角
- 考察意图：是否读得懂 go.mod 各指令，尤其伪版本构成与间接依赖的写入规则。
- P5 知 module/require / P6 能讲伪版本三段与间接依赖条件 / P7 知 go 指令的真实语义与依赖图修剪。
- 红旗：以为 go.mod 列出全部间接依赖；以为伪版本号是随意生成的。
- 惊艳点：间接依赖只在"它自己没有 go.mod"时才写进本模块 go.mod，否则由它的 go.mod 自管 `[源码]`。

## 主问答
**Q（面试官原话）：** go.mod 里面都写了些什么，伪版本号是怎么来的？
**A：**
1. **结论**：含 module 名、go 指令（最低版本）、require 块（直接+部分间接依赖）。
2. **机制**：伪版本形如 v0.0.0-20190725-abcdef123，三段=基础版本+提交时间+commit 哈希前缀，用于标记无 tag 的提交 `[源码]`。
3. **边界**：仅当依赖包自身无 go.mod 时，其版本才以伪版本形式原样写进本模块 go.mod；有 go.mod 的由它自己管理。
**加分层：** go 指令是"最低要求版本"而非"当前环境版本快照"，工具链会据此拒绝过低版本并（≥1.21）选择工具链。

## ⚠️ 原文纠错
发现 1 处表述不严谨。
- 原文第 78~82 段称 go.mod 的 `go 1.20` 指令"只是获取当前环境里面的 go 版本的信息"。**纠正**：该指令的官方语义是「当前模块要求的最低 Go 版本」（minimum required version），工具链会据此拒绝用过低版本构建；自 go1.21 起它还会驱动工具链自动选择（toolchain）。"只是当前环境版本快照"的说法掩盖了它的约束与选择作用 `[源码] src/cmd/go/internal/modload`。
