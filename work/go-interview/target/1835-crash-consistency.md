# 1835 写文件崩溃：已写入数据会丢吗

> 分类：内存与 OS / 文件系统 | 难度：L3 | 题型：FAQ 题 | 频率：高 | 关键词：**进程崩溃** / **系统崩溃** / **page cache 保留** / **崩溃一致性** / **不丢条件**
> 原文锚点：第 17~25 段「进程崩溃…数据仍在page cache由内核管理…仍可读…若OS崩溃/宕机在写回前才丢」

## 一句话总述
进程写文件过程中**崩溃——已写入的数据不会丢**：数据在 page cache 中、由内核管理，与进程生命周期无关，其他进程仍能读到；**只有在脏页写回磁盘之前发生系统/OS 崩溃或服务器宕机**，这部分数据才会丢失。

## 面试官视角
- 意图：能否区分"进程崩溃"与"系统崩溃"两种崩溃边界，给出精确结论。
- P5 知进程崩溃数据不丢；P6 说清 page cache 属内核、跨进程可读；P7 知系统崩溃且未写回才丢、根治靠 fsync。
- 红旗：把"进程崩溃"和"机器宕机"混为一谈；忽略 page cache 是内核资源。
- 惊艳点：崩溃一致性（crash consistency）的边界就在"进程级 vs 系统级"——前者数据在内存由内核托管，后者内存也随断电丢失 `[经验]`。

## 主问答
**Q（面试官原话）：** 进程写文件的过程中崩溃了，已写入的数据会丢失吗？
**A：**
1. **进程崩溃不丢**：数据已进入 page cache，page cache 由内核管理、不随进程退出消失；其他进程读取仍拿到崩溃前写入的数据 `[源码]`。
2. **系统崩溃才丢**：若内核把 page cache 写回磁盘之前，操作系统崩溃或服务器宕机（断电），这部分脏页随内存丢失。
3. **结论**：进程崩溃已写入数据不丢；除非数据在刷盘前遭遇系统级崩溃/宕机才可能丢失。
4. **根治**：在写入关键数据后显式调用 `fsync`/`fdatasync` 强制落盘，消除该窗口 `[边界]` 见 1835-fsync-durability。

## 关键代码
```go
// 示意，未验证：进程 A 写入（仅入 page cache），进程崩溃后进程 B 仍能读到
package main
import ("os"; "fmt")
func main() {
    f, _ := os.CreateTemp("", "crash")
    f.Write([]byte("committed-in-cache"))
    // 此刻进程崩溃：数据在 page cache，内核仍托管，另一进程可读取如下
    b, _ := os.ReadFile(f.Name())
    fmt.Println("另一进程读到:", string(b)) // 进程崩溃不丢
    // 若此处未 fsync 且机器宕机 → 数据丢失
}
```

## 总结与追问预判
- 进程崩溃不丢（cache 属内核）；系统崩溃且未写回才丢；fsync 根治。
- 预判：写路径 → 见 1835-write-path-pagecache；强制落盘 → 见 1835-fsync-durability；page cache 通用行为 → 见 144-seqwrite-pagecache。
