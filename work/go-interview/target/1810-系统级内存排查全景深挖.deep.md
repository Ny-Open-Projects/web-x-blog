# 1810 系统级内存排查全景（深挖）

> 分类：Linux/内存排查 | 难度：L3 | 题型：综合题 | 频率：中 | 关键词：**系统级排查** / **工具链** / **与应用层互补**
> 原文锚点：第 1~75 段「free/top 指标；buffer/cache；vmstat/slabtop/pmap；排查决策树；内存不足信号；ES 关 swap」

## 一句话总述
本源讲的是**操作系统层**内存排查（free/top/vmstat/slabtop/pmap + 指标解读 + 决策树），与已有的 **Go 应用层**排查卡（812-* pprof 诊断、1114-* pprof 工具）是上下游关系：应用层用 pprof 看 Go 堆，系统层用上述工具看整机与进程。面试按"先系统后应用"两层串联。

## 思路与架构
- **指标层**：free 的 available/free/buffer/cache；top 的 VIRT/RES/SHR；vmstat 的 si/so/wa/b——三层指标各看不同粒度（系统/进程/趋势）。
- **工具层**：free/top 静态快照 → vmstat 趋势 → slabtop/pmap 下钻归属（cache 谁占 / 进程地址空间谁占）。
- **决策层**：可用内存低 / swap 占用 / buffer cache 高 三型分流，各有下钻工具。
- **与应用层边界**：本卡是 OS 视角；Go 堆问题用 runtime/pprof（见 812、812-pprof-diagnosis、1114-pprof-analysis），二者互补——系统层确认"机器内存异常"后，再用 pprof 定位"哪个 Go 对象"。

## 方案取舍
- **为何先系统后应用**：机器内存报警可能是 cache 占着（非问题）或别进程占着（非本服务），先 system 层排除再下钻应用，避免一头扎进 pprof 浪费时间。
- **buffer vs cache 为何重要**：二者都可回收，cache 高不一定是泄漏；真泄漏看 available 持续低 + swap 启用。
- **swap 的取舍**：swap 保命但极慢，延迟敏感服务（如 ES）常关 swap 换可预测性，属"用 OOM 风险换确定性"。

## 答题技巧
1. **开口定调**："内存排查我分系统层和应用层，先系统确认现象"。
2. **工具递进**：free→top(RES)→vmstat(趋势,看 si/so/wa/b)→slabtop/pmap(下钻)。
3. **给信号集**：内存不足 = free↓+si/so↑+bi/bo↑+缺页中断↑+cs↑+b↑+wa↑ 同时出现。
4. **关联延展**：补一句"Go 应用层用 pprof 看堆，见 812/1114"，显示两层联动。

## 细节与核心 API

```bash
free -h                       # 总览：used/buff/cache/available（看 available 而非 free）
top -p <PID> -H               # 按进程/线程看 RES（常驻）、VIRT（虚拟）、SHR（共享）
pmap -x <PID> | tail -1       # 进程内存映射明细与总和
cat /proc/<PID>/status | grep -E 'Vm|Rss'   # VmRSS/VmSize/VmSwap
cat /proc/<PID>/smaps         # 每段匿名/文件映射的 PSS/USS（精确算常驻）
smem -t -p                    # 按 PSS 排序（USS 才是进程独占）
# 内存泄漏定位：对比两次 smaps 的 Rss 增长；配合 pprof（Go）看堆
# 注意：cache 可被动回收，不能算“真用掉”；available 才是可立即分配量
```
