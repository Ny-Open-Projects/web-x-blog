# 925 sync.RWMutex 读写锁的使用规则

> 分类：并发模型 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**读锁不阻塞读** / **读多写少** / **锁须传指针**
> 原文锚点：第 23~98 段「读锁并不会堵塞读锁…读写锁适用于读多写少…锁需传指针类型」

## 一句话总述
RWMutex 是多读单写锁：多个 goroutine 可同时持读锁，读锁互不阻塞；写锁独占；读多写少场景用读锁比用写锁/互斥锁更高效，且锁必须传指针。

## 面试官视角
- 考察意图：是否理解读写分离收益 + 锁传参陷阱
- P5 知"读多写少用 RWMutex" / P6 知读锁不阻塞读 + 计数器示例量级 / P7 知锁拷贝导致失效
- 红旗：说"读锁比互斥锁一定快"无前提；把锁当值传参
- 惊艳点：纯读场景 RWMutex.RLock 成本仅 1 次原子加（readerCount+1），无竞争即返回 `[源码]`

## 主问答
**Q：** 什么时候用读写锁、怎么用才对？
**A：**
1. **读锁并发**：多个读锁可同时持有，互不阻塞，适合读多写少 `[源码]`。
2. **写锁独占**：写锁未释放时，后续读、写都阻塞，整把锁被独占 `[源码]`。
3. **须传指针**：锁含内部状态，必须传 `*RWMutex`，拷贝会让锁失效 `[源码]`。
**加分层：** 锁控制的是"逻辑代码段的执行顺序"，多核上两协程仍可能同时被调度，只是其一在等锁——故加 sleep 才保证打印顺序稳定。

// 示意，未验证：读多写少计数器，读用 RLock、写用 Lock
type Counter struct { mu sync.RWMutex; n int }
func (c *Counter) Get() int  { c.mu.RLock(); defer c.mu.RUnlock(); return c.n }
func (c *Counter) Add(v int) { c.mu.Lock(); c.n += v; c.mu.Unlock() }
// 注意：必须传 *Counter（指针），mu 不能被值拷贝
