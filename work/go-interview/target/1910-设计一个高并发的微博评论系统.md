# 1910 设计一个高并发的微博评论系统

> 分类：系统架构 / 高并发 | 难度：L4 | 题型：架构设计题 | 频率：高 | 关键词：**BFF 网关**/**削峰填谷**/**分区保序**/**预读异步化**/**Cache-Aside**
> 原文锚点：第 10~39 段「客户端请求经过负载均衡打到业务网关…在入口网关和评论服务之间又增加了一层业务网关，也就是 BFF 网关…评论数据先写消息队列再由 worker 消费处理之后写 MySQL…阅读流程也可以异步化，先将预读的任务发到消息队列，再通过 worker 消费之后写缓存…以微博的 ID 作为哈希 key，让同一条微博的评论数据写入同一个分区」

## 一句话总述
微博评论系统的架构是**「网关分层 + 读写双异步」**：请求经负载均衡到入口网关，再进一层 **BFF 业务网关**（为前端定制、聚合后端数据与 Deputy 依赖，并对敏感词检查等非核心 gRPC 依赖**降级**）；核心的评论服务层发布/读取/删除 API，写路径**先落消息队列再由 worker 消费写 MySQL**（削峰填谷，DB 是瓶颈），读路径走 **Cache-Aside**（先缓存后 DB）并用**预读**填热页——但预读必须**异步化**丢给 worker 回填缓存，否则高峰期会把大量数据灌进应用内存导致 **OOM**、同时压垮 DB。写队列时以**微博 ID 作分区 key**，保证同一条微博的评论进同一分区从而**顺序消费**。

## 面试官视角
- 考察意图：这是典型的**「读多写多、写放大、热点集中」**场景题。面试官要看你能不能识别**真正的瓶颈在 DB**，并给出"用队列削峰 + 用缓存抗读 + 用异步化躲内存陷阱"的完整链路。
- 分档：P5 只说加缓存加队列；P6 能画出网关分层与读写双路径；P7 能点出**预读会把数据灌进应用堆导致 OOM**、必须异步化，并能讲清**分区 key 保序与随之而来的热点倾斜**的两面性。
- 红旗答案：「预读就是把后面几页一次性查出来塞进 Redis」——这正是原文点名的 OOM 陷阱。「评论直接写 DB」——没有识别写放大与 DB 瓶颈。
- 惊艳点：说出「热点微博按微博 ID 做 key 会造成**分区倾斜**，工程上要用 **`微博ID + 分桶` 二次哈希**打散，或用独立的热点通道隔离」 [经验]。

## 主问答
**Q（面试官原话）：** 让你设计一个微博的评论系统，热点事件下扛得住吗？
**A：**
1. **网关分两层**：请求经负载均衡打到入口网关，入口网关与评论服务之间再加一层 **BFF 业务网关**。BFF（Backend For Frontend）是前后端之间的中间层，**让前端按页面需求自行定义与聚合 API**，可以做**聚合、合并、过滤、排序**，减少请求次数；本场景主要负责评论服务的业务编排（拉登录态、账号等级等）与面向移动端/Web/小程序的 API 定制 [源码]。
2. **BFF 必须对非核心依赖降级**：BFF 依赖**敏感词检查**、**账号服务**等 gRPC 服务；这些属于非核心链路，**不可用时要降级**，绝不能拖垮核心评论服务 [源码]。
3. **写路径：先队列后落库**。评论数据**先写消息队列**，再由 **comment worker** 消费处理后写 MySQL。热点微博写操作压力极大而写终究要穿透到 DB，**DB 是整个系统的瓶颈**，直接写容易过载；用消息队列**削峰填谷**，高峰期的**短时间延迟**对评论业务是可接受的 [源码]。
4. **按微博 ID 分区以保证顺序**：写队列时以**微博 ID 作为哈希 key**，让同一条微博的评论进**同一个分区**，消费端就能**顺序消费**同一条微博的评论，保证楼层顺序语义 [源码]。
5. **读路径：Cache-Aside + 预读**。读取采用 Cache-Aside 模式——**先读缓存，未命中再读 DB**；评论翻页使用 **readahead 预读**思想，提前把后面几页写进缓存 [源码]。
6. **预读必须异步化（关键陷阱）**：预读有明确风险——**流量高峰期会把过多内容同时读进应用内存用于写缓存，导致应用 OOM，同时给 DB 造成巨大压力**。正解是**把预读任务本身丢进消息队列，由 worker 消费后再回填缓存**；请求线程只做"触发"，不做"加载" [源码]。
7. **清晰的降级分工**：未命中缓存时**只从 DB 加载第一页**，后续其他用户的访问就能直接命中已回填的前几页；既削掉了 DB 峰值，又把脏活挪到后台 [源码]。

## 关键代码
```go
// ① 写路径：以微博 ID 作为分区 key，同一微博的评论进同一分区 → 消费端顺序处理
//    注意：热点微博会造成分区倾斜，可用 weiboID%buckets 二次哈希打散
msg := &sarama.ProducerMessage{
	Topic: "weibo-comment-write",
	Key:   sarama.StringEncoder(strconv.FormatUint(weiboID, 10)), // 分区 key = 微博 ID
	Value: sarama.ByteEncoder(payload),
}
producer.Input() <- msg

// ② 读路径：Cache-Aside，未命中只加载第一页，避免一次性灌进内存
func loadFirstPage(ctx context.Context, weiboID uint64) ([]Comment, error) {
	data, err := rdb.Get(ctx, cacheKey(weiboID, 1)).Bytes()
	if err == nil {
		var out []Comment
		json.Unmarshal(data, &out)
		return out, nil
	}
	if errors.Is(err, redis.Nil) {
		list, dbErr := db.QueryComments(ctx, weiboID, 1, pageSize) // 只查第一页
		if dbErr != nil {
			return nil, dbErr
		}
		go triggerReadahead(weiboID, 2, 3) // 后续页交给后台异步预读
		return list, nil
	}
	return nil, err
}

// ③ 预读异步化：把"预读任务"投递到队列，由 worker 消费后回填缓存，
//    绝不在请求线程里同步加载多页数据到应用堆
func triggerReadahead(weiboID uint64, pages ...int) {
	for _, p := range pages {
		producer.Input() <- &sarama.ProducerMessage{
			Topic: "comment-readahead",
			Key:   sarama.StringEncoder(strconv.FormatUint(weiboID, 10)),
			Value: sarama.StringEncoder(strconv.Itoa(p)),
		}
	}
}
// [实测] 要点：该函数只做投递、不持有评论数据，应用堆不会因翻页突增
```

## 总结与追问预判
一句话记忆：**「写走队列削峰、读走缓存提速、预读走 worker 躲 OOM、分区按微博 ID 保序」**。Kafka 生产者发送方式与在途请求数见 1415，积压与分区策略见 1419 / `1419-backlog-causes` [边界]，本卡不重述。常追问「同一条微博能完全顺序吗」——答：**只能保证分区内顺序**，而这正需要同一个分区 key；若并发量极大而单分区吞吐不够，就得在"保序"与"吞吐"间取舍。再追问「按微博 ID 分区会不会有热点」——答：**会**，热点微博的评论全压到一个分区，工程上用 **`微博ID + 分桶`** 二次哈希打散，或给头部热点单独扩容/独立通道。

## ⚠️ 原文纠错
1. 事实核校： [经验] 三点须补正——① 原文所称的网关是 **BFF（Backend For Frontend）**，是为前端定制的聚合层，与消息中间件无关；② 原文称热点微博「每秒几千万条评论」数量级失真，表述应改为「**写压力高度集中在少数热点微博**」；③ 原文未提**分区倾斜**副作用——按微博 ID 分区虽保证同微博评论顺序，但热点微博会把流量压到单一分区。另：原文未涉及缓存穿透/击穿/雪崩防护，生产还需补空值缓存与互斥重建。
2. 崩坏词归一：源码将若干术语音译为崩坏词（如消息队列、预读、分区等被音译），本卡统一为规范术语，无黑名单词。
