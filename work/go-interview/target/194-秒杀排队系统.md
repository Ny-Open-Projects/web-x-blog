# 194 秒杀排队系统：Redis 队列选型与四调优

> 分类：分布式/高并发 | 难度：L2 | 题型：架构题 | 频率：中 | 关键词：**Redis 队列**/**队列拆分**/**长队列调度**/**长度限制=库存**/**LPUSH/RPOP**
> 原文锚点：第 30~43 段「消息队列选型 Redis + 队列拆分/调度/长度限制」

## 一句话总述
秒杀排队用 **Redis 而非 MQ** 更轻量高性能；再靠**队列拆分（每商品独立队列）、长队列调度、长度限制=库存**三招把 Redis 队列调稳，既控压又保公平。

## 面试官视角
- 考察意图：是否真做过队列调优，而非只会「扔进 MQ」；能否讲清拆分/调度/限长背后的取舍。
- 分档：P5 知 Redis 做队列（LPUSH/RPOP）；P6 能讲拆分/调度/限长三招；P7 知限长=库存如何减少 DB 压力、异常/取消如何回收长度。
- 红旗答案：所有商品共用一个队列（热点倾斜、无并行）；不设长度上限（无效请求也打 DB）。
- 惊艳点：点出「长度限制=库存，超长直接拒、提示抢完」，把无效下单挡在 DB 之外 [经验]。

## 主问答
**Q（面试官原话）：** 秒杀排队队列怎么选型？怎么做调优？
**A：**
1. **选型 Redis 而非 MQ**：秒杀排队更轻量、性能卓越；Redis 内置队列结构支持 **LPUSH/RPOP（先进先出）、LLEN 取长度、按排队号定位消息位置**，便于实时反馈进度 [经验]。
2. **队列拆分（每商品独立队列）**：每个秒杀商品设独立队列，分散 Redis 存取压力；多队列多 key 可落到**不同 Redis 节点并行读写**，进一步提升性能 [经验]。
3. **队列调度（长队列倾斜）**：不同商品参与人数不同，热门商品队列过长；对长队列**调度更多资源**避免等待过久 [经验]。
4. **长度限制 = 库存**：初始长度设为库存数，超长请求**直接拒绝入队**（提示抢完），减少 DB 压力；后台异常/用户取消→可用长度回升→重新开放入队 [经验]。

## 版本与兼容性
- LPUSH/RPOP 为 Redis 列表原语；集群下多 key 靠 hash tag 或独立实例保证同 sku 同槽。与「消息队列削峰」角度互补（见 195）[边界]。

## 关键代码

```go
// Redis 队列四调优（Go 侧）：每 sku 独立 key + 限长=库存 + 长度回收
func tryEnqueue(q redis.Client, sku string, stock int64, order PreOrder) (bool, error) {
    key := "seckill:queue:" + sku
    // 长度限制=库存：超长直接拒绝，不碰 DB
    if n, _ := q.LLen(ctx, key).Result(); n >= stock {
        return false, nil // 已抢完
    }
    if _, err := q.RPush(ctx, key, order.ID).Result(); err != nil {
        return false, err
    }
    return true, nil
}
// 取消/异常：LPOP 移除后长度自动回落，下次入队重新开放（无需额外回收）
```

1. 事实核校： [经验] Redis 列表 LPUSH/RPOP 即 FIFO、LLEN 取长、按 index 定位；限长=库存可挡无效请求——均正确。
