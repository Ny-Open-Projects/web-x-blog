# 1115 减少锁粒度 + 批量获取 + 服务扩展

> 分类：性能优化 / API | 难度：L3 | 题型：技巧题 | 频率：中 | 关键词：**锁粒度** / **分段锁** / **批量获取** / **IN 语句** / **水平扩展**
> 原文锚点：第 28~43 段「减少锁粒度(只锁必要/分段锁hash/读写分离)；批量获取(合并远程调用/IN/mget,控条数)；服务扩展(水平扩/垂直扩容,IO或计算密集)」

## 一句话总述
另三组杠杆：① **减少锁粒度**——只在必要代码加锁，用哈希分片或读写分离把全局锁拆细，避免"全函数加锁"把可并行数据串行化。② **批量获取**——合并多次远程调用（IN 语句 / mget），减网络往返，但单次条数要控。③ **服务扩展**——资源不足（CPU/内存）时水平扩更多实例，或垂直升级单机配置，前提是自身 IO/计算已到瓶颈。

## 面试官视角
- 意图：考察锁粒度细化与批量/扩展的实操理解，以及"何时该加锁、加多细"。
- P5 知锁粒度/批量/扩展三招；P6 知分段锁与读写分离、IN 合并查询、水平 vs 垂直扩容；P7 知批量条数上限、水平扩展的前提（无状态/共享存储）。
- 红旗：对整个写函数加锁导致多文件写入互相阻塞；或盲目扩容却不先定位瓶颈。
- 惊艳点：点出"多文件数据独立本可并行，全局锁反而串行"的代价 `[边界]` 见 925（Mutex/读写锁实现）、165（单例锁）、136（ES 批量）、112-bottleneck-first（先定位再扩）。

## 主问答
**Q（面试官原话）：** 锁粒度、批量、扩展在优化里怎么落地？
**A：**
1. **只锁必要代码**：写文件只需锁当前文件的写入（甚至某行），不必锁整个写函数——否则多文件互相独立的数据被迫串行，吞吐骤降。
2. **分段锁 + 读写分离**：用哈希把数据分片、每片一把锁（参考并发 map、读写锁源码的分段/读写字段），把全局竞争打散，核心目标是细化粒度、避免全局锁。
3. **批量获取减调用**：循环逐条 get 改为一次 mget / 一次 `IN` 查询，减少远程调用网络消耗；但单次批量条数过多也会拖慢，需控制。
4. **服务扩展**：高 IO 或计算密集且资源不足时，水平启多实例或垂直升配；前提是该服务自身 IO/计算已达瓶颈（否则先定位）。

## 关键代码
```go
package main

import "sync"

// 减少锁粒度：按 key 分片加锁，而非全局一把锁
type ShardedCache struct {
	shards []struct {
		mu sync.Mutex
		m  map[string]int
	}
}

func (c *ShardedCache) Add(key string, v int) {
	s := &c.shards[hash(key)%len(c.shards)]
	s.mu.Lock()
	s.m[key] = v
	s.mu.Unlock()
}
```
