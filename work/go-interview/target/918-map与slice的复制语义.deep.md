# 918·深 map 与 slice 的复制语义：为什么一个共享、一个独立？

> 分类：Go 基础 / 数据结构 | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**引用语义**/**描述符拷贝**/**hmap**/**SliceHeader**/**len cap 独立**/**扩容分家**
> 原文锚点：第 16~34 段「切片和 map 在赋值的表现上是有差异的…当我们往复制后的这个 map 里面增加键值对的时候，我们这个原始的 map 也有这个键值对…对于切片…只有新的切片里面有新的元素，原始的切片里面是没有新的元素的」
> [边界] 本文是 `918-nil-vs-empty-map` 的深挖，主卡已讲的 nil/空 map 行为矩阵此处不重述；slice 头部结构与截取共享见 907 / `907-slice-desc-independent`，map 底层 `hmap`/`bmap` 见 914。

## 思路与架构

一句话抓本质：**map 变量里装的是"指针"，slice 变量里装的是"描述符"**。

```text
map[string]int        slice（[]int）
┌──────────┐         ┌──────────────────────────┐
│ *hmap ───┼───┐     │ Data ptr ───┐  len  cap  │   ← 三个字段都拷走
└──────────┘   │     └─────────────┼───────────┘
               ▼                   ▼
        ┌─────────────┐     ┌──────────────────┐
        │  hmap 结构  │     │   底层数组        │
        │  buckets…   │     └──────────────────┘
        └─────────────┘        ↑            ↑
                            s1.Data      s2.Data  （指向同一块）

赋值 m2 := m1  →  只拷一个指针，两者指向同一个 hmap
     ⇒ 任一方的增删改，另一方全部可见

赋值 s2 := s1  →  拷三个字段（Data/len/cap），Data 指向同一数组，
                  但 len/cap 是各自的副本
     ⇒ 改元素（s2[0]=x）互相可见
     ⇒ append 只改自己的 len，原切片 len 不变 ⇒ 新元素对原切片不可见
```

三条推导链：

1. **为什么 map 必须是指针语义**：map 要支持扩容、搬迁（`growing`/`evacuate`），桶数组地址会变。若按值拷贝，扩容后副本就指向旧桶，语义崩坏。所以 map 变量本质上是一个 `*hmap`。
2. **为什么 slice 要带 len/cap 两个字段**：切片是"数组的窗口"。**底层数组存的元素**与**切片可见的元素**是两个概念——底层有，不代表这个窗口能访问。正是因为 `len` 是副本，`append` 才只影响一方。
3. **什么时候 slice 会"看起来共享"**：只要 `cap` 够、`append` 不扩容，新元素**确实写进了同一块数组**。此时通过**指针或重新截取**仍能看见——**共享的是空间，独立的是可见范围**。

## 方案取舍

```text
需要"传进去让函数填充"时怎么选？
──────────────────────────────────
map：  直接传值即可，函数内 m[k]=v 调用方可见（因为共享 hmap）
       但"替换整个 map"（m = 新map）不可见 —— 要传 *map 或返回新值

slice：直接传值，append 的结果**必须返回**并接回
       经典坑：func f(s []int){ s = append(s, 1) } 调用方完全无感
       想原地改就用 *[]int，或明确返回新切片

想拿到独立副本时：
       map：没有内置 copy，只能手工遍历；或用 maps.Clone（Go 1.21+）
       slice：用 copy(dst, src) 或 s2 := append([]T(nil), s1...)
              注意 append 写法要传 nil，否则可能复用原底层数组
```

- **map 的取舍**：换来**传递零成本、天然共享**，付出**并发不安全**——多个 goroutine 同时写会直接 `fatal error: concurrent map writes`（不是 panic，无法 `recover`）；需要并发就用 `sync.Map`（见 922*`）或加锁。
- **slice 的取舍**：换来**零拷贝的窗口能力**（截取、传参极廉价），付出**"改了看不见 / 看见了没改"的心智负担**，以及**截取大切片导致底层数组无法回收的内存泄漏**风险（见 905）。
- **两者共同的坑**：都**不能**用 `==` 比较内容（map 只能与 `nil` 比，slice 连编译都过不了），要比较得遍历或用 `slices.Equal` / `maps.Equal`（Go 1.21+）。

## 答题技巧

- **开口先给结论**：「map 是指针语义，slice 是描述符语义。」先把两个名词摆出来，再展开，面试官立刻知道你分清了。
- **一定要补的实测证据**：`&s1[0] == &s2[0]` 输出 **`true`**——这句话能挡掉"切片赋值是完全独立的"这个常见错误认知。
- **把"扩容分家"作为压轴**：`append` 一旦超过 `cap`，会分配新数组并拷贝，此时两个切片**彻底无关**。演示代码里要显式用 `make([]int, 2, 10)` 预留容量，否则结论不稳定。
- **主动划边界**：提到共享时补一句"共享的是**底层空间**，独立的是**可见范围**（`len`）"，这句话是本题的最高分答案。
- **别踩的坑**：不要说"slice 是值类型、map 是引用类型"然后停住——**两者都是值传递**，区别只在于**值里面装的是什么**（指针 vs 描述符）。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Go 全版本 | map 变量实为 `*hmap` | 赋值共享，改一方另一方可见 |
| Go 全版本 | slice 三字段描述符 | `len`/`cap` 独立，`Data` 共享 |
| Go 全版本 | `append` 超 `cap` 才分配新数组 | 演示须预留 `cap` [实测] |
| Go 1.21+ | `maps.Clone` / `slices.Clone` | 深拷贝不必手写循环 |
| Go 1.21+ | `maps.Equal` / `slices.Equal` | 内容比较有了标准做法 |
| Go 全版本 | 并发写 map 是 `fatal` 非 `panic` | 无法 `recover`，只能避免 [经验] |
