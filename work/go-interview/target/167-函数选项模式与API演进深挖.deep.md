# 167 函数选项模式与 API 演进 深挖

> 覆盖源 16-7 全文：参数不断扩展导致所有调用点都要改的痛点、函数选项模式的定义（配置对象 + 函数类型 + 一串 With 返回函数 + 变长参数接收并遍历应用）、不在二十三种设计模式之列但 Go 中极实用、以 ES 客户端初始化为例（必传：名称/地址/用户名/密码；可选：查询日志开关、慢查阈值、连接 schema）。主卡已给四步实现与可运行代码，本附录做「它到底解决了什么问题」「与配置结构体 / Builder 的三方取舍」「什么时候不该用它」「工程上的六个细节」四层深挖。

## 思路与架构

```text
API 演进的三条路
├─ 直接加形参:        老调用点全部编译失败(破坏性)
├─ 传一个配置结构体:   调用点要写 Config{...}, 新增字段要考虑零值兼容
└─ 函数选项模式:       必传形参 + opts ...Option, 新增只加 WithXxx, 老调用点零改动
     实现: type Option func(*options) → func WithXxx(v) Option { return func(o *options){...} }
     应用: o := 默认值; for _, opt := range opts { opt(o) }
```

## 方案取舍
- **它解决的不是"参数多"，而是"参数会变"**：参数多本身不是问题，问题是**每次加参数都要改所有调用点**。函数选项模式把"签名演进"变成"**新增一个函数**"，这是**向后兼容**的关键——老代码编译期零改动，新代码想要新配置就多传一个 `With`。所以判断要不要上这套模式的依据是「**这个 API 未来会不会频繁加可选配置**」，而不是「当前有多少个参数」 [经验]。
- **为什么不干脆传配置结构体**：配置结构体的问题不在功能而在**摩擦**——调用方即便全用默认值也必须写一个 `Config{}`（或者在加字段后被迫补字段），而且一旦字段导出，将来**重命名、加校验、换语义都会破坏兼容**。函数选项把字段藏在不导出的 `options` 里，对外只暴露 `WithXxx` 函数，等于给自己留了一条**可演进的私有面** [经验]。
- **为什么不选 Builder**：Builder 适合"构造过程有**多步依赖、需要分步校验、最终一次性 Build**"的场景（例如 SQL 构造器）。而初始化客户端这类场景只是"**给一堆独立字段赋可选值**"，用 Builder 要多一个类型和一次 `Build()` 调用，语义负担更重。**函数选项 = 轻量版 Builder**，Go 社区几乎一致地在客户端初始化上选它 [经验]。
- **什么时候不该用**：① **必传参数不要塞进 Option**——必传就应该在签名里显式体现，否则调用方漏传只能在运行期才发现，把编译期错误推成了运行期错误；② **只有一两个可选字段且几乎不会变**时，直接加形参或传配置结构体更直白；③ **需要整体序列化/反序列化配置**（如把配置写进 YAML）时，结构体更合适，因为 `With` 函数无法被序列化 [经验]。
- **六个工程细节**：① 变长参数 `...Option` **只能放参数列表最后**；② `options` 字段**不导出**，对外只给 `With`；③ 构造函数里**先填默认值**再应用 Option，保证"不传也能用"；④ `WithXxx` 内部可以做**参数校验**（返回 error 的版本是 `func WithXxx(v) (Option, error)`，或 panic 式为 `MustWithXxx`）；⑤ 命名惯例统一 `With` 前缀；⑥ 需要整体注入时提供 `WithOptions(opts options)` 之类的逃生舱 [经验]。

## 答题技巧
- 开口先把痛点讲清楚：**「直接加形参会让所有调用点都改」**，再引出模式——先讲问题再给方案，比直接背实现更有说服力 [经验]。
- 被问「Option 是什么」→ 一句话答 `type Option func(*options)`，并强调**返回函数**的 `WithXxx` 形态是这套模式的识别特征 [经验]。
- 被追问「为什么不用配置结构体」→ 答**零值友好 + 字段不导出 + 加项不破坏兼容**三点，而不是"大家都在用" [经验]。
- 主动纠偏：**「必传参数不能走 Option，任意数量不等于任意位置」**——这是本题最容易踩的表述坑，主动说能加分 [经验]。
- 收尾给选型：可选配置多且会演进 → 函数选项；需要序列化或整体校验 → 配置结构体；构造有步骤依赖 → Builder [经验]。
- 主动边界到本库 ES 客户端与接口设计相关卡片，构成 Go API 设计全栈 [边界]。

## 细节与核心 API

```go
// 函数选项（Functional Options）：用可变数量的「选项函数」扩展配置，向后兼容
type Option func(*Server)
func WithPort(p int) Option           { return func(s *Server) { s.port = p } }
func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func New(opts ...Option) *Server {
    s := &Server{port: 8080, timeout: 30 * time.Second} // 默认值
    for _, o := range opts { o(s) }                     // 逐个应用
    return s
}
s := New(WithPort(9000), WithTimeout(5*time.Second))
// 收益：新增选项不破坏旧调用（不用改函数签名）；可读性强；可组合
// 对比：结构体配置需每次传全量、易漏字段；多构造函数爆炸
// 取舍：选项过多时考虑显式 Config 结构体 + 校验；超 5 个选项仍用 Options 更灵活
```
