# 1021 多发送者的通道关闭方案

> 分类：并发模型 | 难度：L4 | 题型：工程题 | 频率：高 | 关键词：**stop channel** / **广播退出** / **WaitGroup 收口**
> 原文锚点：第 77~112 段「多发送者单接收者、或多对多：用额外 stop channel 通知停发，协调者收口后关数据 channel」

## 一句话总述
多发送者场景不能让任何一方直接关数据 channel。做法是引入一个 stop channel 广播"停止发送"信号：发送者收到后退出，协调者（WaitGroup 收齐或独立 goroutine）确认无发送者后再关数据 channel。

## 面试官视角
- 意图：能否在 N 个发送者下既防"向已关写 panic"又防"重复 close"。
- P5 知 stop channel 思路 / P6 说清"先停发再关数据"顺序 / P7 知 N:N 必须独立协调者关、关前确无写入。
- 红旗：让接收方直接 close 数据 channel（其余发送方还在写 → panic）；多发送者各自 close。
- 惊艳点：stop 关闭后所有发送者都能读到零值退出（广播），但数据 channel 只能在"零发送者"后由唯一协调者关 `[源码]`。

## 主问答
**Q（面试官原话）：** 多个 goroutine 往一个 channel 发，怎么安全关？
**A：**
1. **结论**：数据 channel 谁都不能随意关；用独立 stop channel 通知所有发送者停发。
2. **机制**：接收（或协调者）close(stop) → 各发送者 `select` 收到零值退出；WaitGroup 等全部发送者结束后，由协调者 close 数据 channel。
3. **边界**：N:N 时关闭既不在发送方也不在接收方，而在独立 goroutine/main；关前必须保证不再有发送者写入，否则 panic。
**加分层：** "先停发、后关数据"的顺序是铁律，顺序反了就 panic。

## 关键代码
```go
// 示意，未验证：多发送者，协调者收口后关数据 channel
stop := make(chan struct{})
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    wg.Add(1)
    go func() { defer wg.Done(); for { select { case <-stop: return; default: /* 发送 */ } } }()
}
close(stop) // 广播停发
wg.Wait()   // 所有发送者已退出
close(data) // 此刻再关数据 channel，安全
```

- 多发送者禁止任一方关数据 channel；stop 广播停发，协调者等齐后关闭。
