# 819 GMP 调度中的阻塞场景全景

> 分类：Go 底层 / 调度 | 难度：L2 | 题型：原理题 | 频率：高 | 关键词：**GMP 阻塞**/**系统调用**/**channel 阻塞**/**waitreason**/**M 与 P 解绑**

> 原文锚点：第 2~11 段「g.waitreason 字段 → 系统调用/内存同步/GC/Sleep 四类阻塞」

## 一句话总述
GMP 调度中的阻塞可从 `g.waitreason` 字段的枚举总览，归为四类：① **系统调用/IO**（读写文件、网络操作——M 释放或移交 P，调度其他 G 上 CPU）；② **内存同步**（channel 收发、互斥锁/读写锁、select 空等、WaitGroup/Cond 等同步原语）；③ **垃圾回收**（1.8 前无混合写屏障时标记/STW 阻塞更重）；④ **time.Sleep**。核心机制：G 阻塞时**工作线程 M 与 P 解绑**，让 P 去跑队列里其他 G，保住 CPU 利用率。

## 面试官视角
GMP 阻塞题是调度器的「应用层考点」——不考数据结构细节，考「**G 睡了之后谁干活**」的机制直觉。三个采分点：① 四类阻塞**报全**（漏 GC 和 Sleep 的占多数）；② **阻塞与阻塞不同**——channel 阻塞 G 换走、syscall 阻塞 M 换 P、两者处理路径不同；③ 会用 `waitreason`（gdb/pprof blocked/trace 可见）排查线上阻塞——答到工具层即 senior。

## 主问答
**Q（面试官原话）：** GMP 调度过程中哪些情况会出现阻塞？

1. **系统调用/耗时 IO**：G 执行读写文件、网络操作等 syscall 时阻塞——此时 **M 会释放/移交 P** 并尝试获取新 P 继续执行其他 G（网络 IO 更优：netpoller 感知后 G 直接让出，M 不阻塞）。
2. **内存同步访问**：① **channel**——从空 channel 收、向满 channel 发即阻塞，直到可收/可发；② **互斥锁/读写锁**——锁被他人持有时阻塞等待；③ **select**——所有 case 均不可执行且无 default 时阻塞，直到某 case 就绪；④ **同步原语**——WaitGroup.Wait、sync.Cond.Wait 等。
3. **垃圾回收**：标记阶段的辅助标记（mark assist）、STW 阶段都会阻塞用户 G——**1.8 前无混合写屏障，re-scan 需要更长 STW**，阻塞感受更重；之后 STW 缩到亚毫秒级。
4. **time.Sleep**：G 睡眠等待定时器到期——不占 M（M 被释放去跑别的 G），到期后 G 重新入队。
5. **统一应对机制**：无论哪类阻塞，调度的核心动作都是 **G 与 M 解绑等待、M 手里的 P 交出（或转交）去跑其他可运行 G**——等待结束后 G 重新进队列（可能被别的 M 捡走），这就是 Go 高 CPU 利用率的调度底盘。[经验] 补全：阻塞原因在 `g.waitreason` 有完整枚举（runtime/runtime2.go），线上可用 blocked profile / trace 定位「G 都睡在什么上」。

## 版本与兼容性
| 主题 | 说明 |
|------|------|
| syscall 阻塞 | M 进入 syscall；超时未返由 sysmon 移交 P 给其他 M |
| 网络阻塞 | netpoller 托管, G 挂起但 M 不阻塞（与文件 IO 不同） |

## 关键代码
```go
func main() {
	ch := make(chan int)
	runtime.GOMAXPROCS(1) // 单 P: 证明阻塞 G 不占 CPU, 其他 G 照常跑

	for i := 0; i < 4; i++ { // 4 个 G 睡在 chan receive (内存同步阻塞)
		go func(id int) {
			<-ch // G 挂起, M 转身跑别的 G
		}(i)
	}
	// 阻塞中的 4 个 G 不吃 CPU: 主 G 照常完成 100 万次计数
	sum := 0
	for i := 0; i < 1_000_000; i++ {
		sum += i
	}
	fmt.Println("sum =", sum)
	fmt.Println("NumGoroutine =", runtime.NumGoroutine()) // 5 = 1 主 + 4 睡

	close(ch) // close 使所有 <-ch 立即返回零值 -> 全部唤醒
}
```

[实测] 输出（GOMAXPROCS=1）：`sum = 499999500000`、`NumGoroutine = 5`——4 个 G 阻塞在 chan receive 期间主 G 单 P 照常跑完百万计数，close 全部唤醒。

四类阻塞的调度应对：
```text
四类阻塞的调度应对 (谁睡、谁走、谁顶上)
├─ syscall (文件/重 IO)
│   └─ M 陷进内核 -> P 被移交/释放 -> 其他 M 用 P 跑 G
├─ 内存同步 (channel/锁/select/WG/Cond)
│   └─ G 挂到等待队列 -> M 不睡 -> 立刻跑下一批 G
├─ GC (mark assist / STW)
│   └─ 1.8 前重 STW; 1.8+ 混合写屏障, STW 亚毫秒
└─ time.Sleep
    └─ G 挂定时器堆 -> M 跑别的 G -> 到期重新入队
└─ 排查: g.waitreason 枚举 + pprof block + trace
```

## 总结与追问预判
核心：**四类阻塞（syscall/内存同步/GC/Sleep）+ 统一应对（M-P 解绑、P 不闲着）+ waitreason 排查入口**。追问常拐向细节——syscall 超时移交由 sysmon 执行、netpoller 让网络 IO 不占 M（见 1833.md` 的 Go 网络模型）、阻塞分类学源码定位见 819.md`、调度器调参与资源上限见 1006.md`、waitreason 在诊断中的用法另见 116.md`。

## ⚠️ 原文纠错
1. 事实核校： [经验] 原文「系统调用时 M 可以释放 P」表述正确但过程不完整——进入 syscall 前 M 会**先尝试解绑 P 交给其他 M**，syscall 返回后优先找回原 P、找不到则 G 进全局队列；超时接管由 **sysmon** 执行，原文缺这一环。
2. 术语核校： [经验] 原文「购入team/勾入ting」=goroutine、「批」=P、「slack 语句」=select 语句、「waitergroup」=WaitGroup，已归一。
