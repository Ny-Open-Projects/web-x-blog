# 804 Go 编译全流水线

> 分类：工程化与编译 | 难度：L3 | 题型：原理题 | 频率：中 | 关键词：**编译流水线** / **SSA** / **cmd/link**
> 原文锚点：第 1~121 段「从 main.go 到可执行文件经历的步骤总览」

## 一句话总述
`go build` 内部是一条「前端(parse+typecheck) → 中端(ir→ssa 优化) → 后端(各 arch 生成 obj) → 链接(cmd/link)」的流水线，每阶段产物明确，不可颠倒。

## 面试官视角
- 意图：是否真正理解源码到二进制的全链路，而非只背"编译分三步"。
- P5 能列阶段名 / P6 说清每个阶段产物 / P7 知阶段为何这样切分、build cache 在哪层生效。
- 红旗：把链接说成编译一部分不分清；以为 SSA 在类型检查之前；以为 GC 在编译期。
- 惊艳点：现代 Go(1.18+) 类型检查用 `cmd/compile/internal/types2`（go/types 的 fork），与前端语法树分离 —— 验证 `go/src/cmd/compile/internal/types2` `[源码]`。

## 主问答
**Q（面试官原话）：** 你写 `go build`，背后到底经历了哪些阶段？每阶段产出什么？
**A：**
1. **结论**：parser → typecheck(noder→ir) → SSA 中端优化 → 后端按 arch 生成 obj → `cmd/link` 链接成可执行。
2. **机制**：`syntax` 包把词法/语法分析成 AST；`noder` 把 AST 转成 `ir`(中间表示) 并借 `types2` 做类型检查；`ssa` 包把 ir 降级成 SSA 并做中端优化；各 arch 后端(`amd64`/`arm64`)把 SSA 转成机器码写入 `obj`；最后 `cmd/link` 链接 `[源码]`。
3. **边界**：解析/类型检查属"前端"与 CPU 架构无关；SSA 优化是架构无关中端；机器码生成与链接才是架构相关后端。
**加分层：** 这种切分让加新语言特性只动前端、加新架构只动后端，互不影响。
