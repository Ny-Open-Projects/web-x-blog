# 1239 唯一索引与普通索引的加锁退化规则

> 分类：数据库 / MySQL 锁 | 难度：L4 | 题型：规则题 | 频率：高 | 关键词：**唯一索引、普通索引、等值查询、范围查询、记录锁、间隙锁、临键锁、退化**

> 原文锚点：第 15~25 段「唯一索引等值查询，如果记录存在，那唯一索引的临键锁就会退化成记录锁。如果唯一索引的等值查询记录不存在的时候，那唯一索引的临键锁会退化成间隙锁，它会锁定不存在记录所在的间隙。那当查询的范围超过最大的主键ID值的时候，它会在当前索引的最大值和当前索引的最大索引行之间增加临键锁。注意这里面的最大值是相对于我们当前扫描的这个索引列的最大值而言，而不是主键索引的最大值」

## 一句话总述
InnoDB 在 RR 下**默认加临键锁**，但会按"索引是否唯一 + 记录是否存在 + 是否越过索引边界"**三级退化**：唯一索引等值命中 → **记录锁**；唯一索引等值未命中 → **间隙锁**；查询范围超过当前索引最大值 → 在**该索引最大值与最大索引行之间**加**临键锁**（注意"最大值"是相对**当前扫描的索引列**，不是主键索引的最大值）。普通二级索引更复杂：扫描到的二级索引加**临键锁**，**第一条不满足条件的记录退化为间隙锁**，符合条件记录的主键加**记录锁**。

## 面试官视角
- 考察意图：能否把"加什么锁"从背结论升级为**按条件推导**。
- 分档：P5 知道 RR 下默认临键锁；P6 能说"唯一索引等值命中退化成记录锁"；P7 能补上"**等值未命中退化成间隙锁**"、"**越过索引最大值加临键锁**"以及"**最大值是相对当前扫描的索引列**"这个易错点。
- 红旗答案：把"超过最大值"里的最大值理解成**主键索引的最大值**——原文明确强调是**当前扫描索引列的最大值**。
- 惊艳点：**"扫描到第一条不满足条件的记录"是加锁边界的关键**——普通索引必须多扫一条才能确认范围结束，这多扫的一条就被锁住（并退化为间隙锁）`[源码]`。

## 主问答
**Q（面试官原话）：** 唯一索引等值查询加什么锁？记录不存在呢？

1. **结论**：RR 下默认加**临键锁**，但会按条件退化——**唯一索引等值命中 → 记录锁**；**唯一索引等值未命中 → 间隙锁**；**越过索引最大值 → 临键锁** `[源码]`。
2. **唯一索引等值 · 记录存在**：**临键锁退化成记录锁**，仅锁住索引记录本身 `[源码]`。（退化原因见 `1236-unique-equality-exists`：唯一性杜绝了该行的插入/删除，不会产生幻读。）
3. **唯一索引等值 · 记录不存在**：**临键锁退化成间隙锁**，**锁定该不存在记录所在的间隙** `[源码]`。
4. **唯一索引范围 · 越过最大值**：当查询范围**超过最大的主键 ID 值**时，会在**当前索引的最大值与当前索引的最大索引行之间**增加**临键锁**；**这里的最大值是相对于当前扫描的这个索引列而言，而不是主键索引的最大值** `[源码]`——这是本条最易错的细节。
5. **普通索引（二级索引）· 等值**：首先对**扫描到的二级索引加临键锁**；由于二级索引**需要扫描到第一个不满足条件的记录**才能确认范围结束，**这条被扫描的记录会退化成间隙锁**；随后**把符合查询条件的记录的主键加记录锁** `[源码]`。
6. **普通索引 · 边界与范围**：查询的是**当前最大的索引值**时，会给**最大的虚拟记录行加临键锁**；**二级索引记录不存在时，二级索引的临键锁退化成间隙锁**；**范围查询记录存在**时，二级索引记录加临键锁、符合条件记录的主键加记录锁；**范围查询记录不存在**时，因会扫描到第一条不满足条件的记录，**该记录会加临键锁和记录锁**；**范围超过索引最大记录**时，在**最大记录与最大索引行之间**加临键锁 `[源码]`。

**加分层：** 判断顺序可记为"**先定索引树（唯一/普通）→ 再看命中与否 → 最后看是否越过索引边界**"，三步走完就能推出锁类型。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| RR（默认） | 间隙锁/临键锁生效 | 按本卡退化规则推导 |
| RC | **无间隙锁** | 只有记录锁，退化规则不适用 |
| 8.0 起 | `data_locks` 视图 | 用 `lock_mode` 可直读锁类型 |
| 5.7 及之前 | `innodb_locks` | 视图名不同，规则一致 |

## 关键代码
```sql
-- 1) 唯一索引等值命中：临键锁退化为记录锁
START TRANSACTION;
SELECT * FROM userbig WHERE id = 10 FOR UPDATE;
SELECT lock_mode FROM performance_schema.data_locks
WHERE object_name = 'userbig'\G   -- 期望 X, REC_NOT_GAP

-- 2) 唯一索引等值未命中：退化为间隙锁，锁住不存在记录所在的间隙
START TRANSACTION;
SELECT * FROM userbig WHERE id = 999999 FOR UPDATE;
-- 期望 X, GAP

-- 3) 范围超过当前索引最大值：在该索引最大值与最大索引行之间加临键锁
START TRANSACTION;
SELECT * FROM userbig WHERE id > 900000 FOR UPDATE;

-- 4) 普通索引：多扫一条不满足条件的记录，该记录退化成间隙锁
ALTER TABLE userbig ADD INDEX idx_name (name);
START TRANSACTION;
SELECT * FROM userbig WHERE name = 'name10' FOR UPDATE;
SELECT index_name, lock_mode, lock_data
FROM performance_schema.data_locks WHERE object_name = 'userbig'\G
```

## 总结与追问预判
**"最大值是相对当前扫描的索引列，不是主键索引最大值"是本节能拉开差距的一句**——很多候选人会下意识答成主键最大值。追问常接"RC 下呢"——**RC 没有间隙锁**，全部退化规则只剩记录锁，这也是"RR 更容易死锁、RC 并发更高"的原因之一。再往下会接"怎么验证"——8.0 查 `performance_schema.data_locks` 的 `lock_mode` 字段（`REC_NOT_GAP` / `GAP` / 普通即为临键锁）。

## ⚠️ 原文纠错
1. 事实核校：唯一索引等值命中退化为记录锁、未命中退化为间隙锁、越过索引最大值加临键锁且最大值取当前扫描索引列、普通索引扫描第一条不满足条件的记录并退化为间隙锁、符合条件记录主键加记录锁、最大虚拟记录行加临键锁——均与 InnoDB 加锁规则一致 `[经验]`。
2. 补充：原文把这些规则笼统陈述为"加锁情况"，未点明**这些退化只在 RR 下成立**——**RC 隔离级别下不存在间隙锁**，退化规则不适用；面试中必须补上隔离级别前提 `[经验]`。
3. 崩坏词归一：源码将临键锁、间隙锁、记录锁、唯一索引、二级索引、主键等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
