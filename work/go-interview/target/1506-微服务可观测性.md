# 1506 微服务可观测性：监控与链路追踪

> 分类：架构设计 / 微服务 | 难度：L3 | 题型：实战题 | 频率：高 | 关键词：**链路追踪** / **traceID** / **serviceID** / **可观测性** / **监控**
> 原文锚点：第 16~21 段「服务监控和链路追踪…traceID透传下游…serviceID定位节点」

## 一句话总述
微服务可观测性 = 监控（健康检查/性能/日志/告警）+ 链路追踪（全局 traceID 透传串联各节点、每节点 serviceID 定位归属）；没有它，分布式调用链排障寸步难行。容错（158）管"故障怎么办"，可观测性管"故障在哪"。

## 面试官视角
- 意图：是否把"可观测性"当成独立命题，而非与容错混为一谈；能否讲清 traceID 串联机制。
- P5 知要监控+日志；P6 说清 traceID 透传与 serviceID 定位；P7 知采样率/存储选型（如 OpenTelemetry/Jaeger）。
- 红旗：以为有日志就够了；把链路追踪等同于监控告警。
- 惊艳点：traceID 全局唯一、随请求透传所有下游调用，方能把跨服务的异常日志串成一条完整链路 `[经验]`。

## 主问答
**Q（面试官原话）：** 微服务出问题怎么排查？链路追踪怎么实现？
**A：**
1. **监控全覆盖**：健康检查、性能监控、日志采集、异常告警四件套，确保系统稳定可观测 `[源码]`。
2. **链路追踪机制**：每个请求生成全局 `traceID`，透传到下游全部调用；每个调用节点自身生成 `serviceID`（标识哪个服务）。
3. **串联与定位**：用 `traceID` 把各微服务中的异常日志串成完整调用链，追溯请求在哪一环出错；`serviceID` 定位异常归属、判断上下游关系。
4. **与容错边界**：容错（隔离/超时/限流/熔断/降级，见 158）管"故障如何兜底"，可观测性管"故障在哪里发生"，二者互补非替代 `[边界]`。

## 关键代码
```go
// 示意，未验证：用 context 透传 traceID，下游调用携带同一 traceID 实现串联
package main
import ("context"; "fmt")
type ctxKey string
func withTrace(ctx context.Context, traceID string) context.Context {
    return context.WithValue(ctx, ctxKey("trace"), traceID)
}
func callDownstream(ctx context.Context, svc string) {
    traceID, _ := ctx.Value(ctxKey("trace")).(string)
    // 请求带上 traceID 与自身 serviceID，下游继续透传
    fmt.Printf("svc=%s traceID=%s -> 调用下游\n", svc, traceID)
}
func main() {
    ctx := withTrace(context.Background(), "trace-abc123")
    callDownstream(ctx, "order-svc") // 全链路同一 traceID
}
```

## 总结与追问预判
- 可观测性 = 监控 + 链路追踪；traceID 串联、serviceID 定位；与容错互补。
- 预判：容错策略 → 见 158 系列；治理总览 → 见 157；指标监控 → 见 1511。
