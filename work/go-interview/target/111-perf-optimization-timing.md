# 111 性能优化的时机：什么时候该优化，什么时候不该

> 分类：工程实践 / 性能 | 难度：L3 | 题型：方法论题 | 频率：高 | 关键词：**优化时机**/**过程指标**/**吞吐**/**延迟**/**内存占用**/**扁鹊三兄弟**/**敏捷冲刺**
> 原文锚点：第 4~30 段「性能优化的目的是满足客户对处理速度、吞吐量、内存占用以及能耗等过程指标的需求…性能优化不一定能降低成本，很多时候还可能会增加成本…需要把握好优化的时机…很多开发人员倾向于一开始就追求完美的架构、高性能的算法，最终导致交付周期变长」
> [边界] 本文只讲**"要不要优化、什么时候优化"的时机判断**：定位瓶颈的方法见 `112-bottleneck-first`、面试叙述法见 `112-star-answer`、基准测试与 pprof 工具链见 `113-benchmark-basics` 与 `1114-pprof-overview`，均不重述。

## 一句话总述
性能优化的**目的**是满足用户对**处理速度、吞吐量、内存占用、能耗**等指标的需求；它**不一定降本、常常反而增加成本**，所以真正的功夫不在"怎么优化"，而在**"什么时候优化"**——**先交付、先度量，等瓶颈暴露出来再针对性下手**，既不能一开始就把架构和算法设计到极致（拖长交付周期），也不能等火烧到用户才救火。

## 面试官视角
- 考察意图：这题几乎必问，因为**它直接暴露你的工程成熟度**。只会讲"加缓存加索引"的是初级；能讲清"**为什么现在不动它**"的才是高级。
- 分档：P5 说"有瓶颈就优化"；P6 能说出"先度量再优化、不要过早优化"；P7 能补上**成本观**（优化常增加成本，收益必须大于投入）、**时机论**（扁鹊三兄弟：防患未然 > 初起时治 > 病入膏肓），以及**"优化成果必须可复现、可度量"**这条底线。
- 红旗答案：「我写代码就直接用最优算法和最高性能架构」——这会让**交付周期变长、产出效率变低**，在敏捷里是明确反模式。
- 惊艳点：主动说「**扁鹊大哥最厉害，因为他治病于发作之前**；对应到工程上，是**在设计和 code review 阶段就把明显的坑挡掉**，而不是等线上告警再去当"救火英雄"」[经验]。

## 主问答
**Q（面试官原话）：** 你觉得性能优化该在什么时候做？项目一开始就追求高性能好吗？

**A：**
1. **先说目的是什么**：性能优化是为了满足客户对**处理速度、吞吐量、内存占用、能耗**等指标的需求，它和编码在开发过程中**同等重要**——因为**性能问题严重影响体验、甚至导致功能不可用，其严重程度等同于 Bug** [源码]。
2. **再说成本观（很多人忽略）**：性能优化**不一定能降低成本**，很多时候**反而会增加成本**（更多机器、更复杂的架构、更长的工期）。但这个成本**是必要的**，因为软件服务于用户 [源码]。
3. **什么时候不该优化**：一开始就追求"完美架构 + 高性能算法"，会把**交付周期拉长、产出效率降低**，这在敏捷开发中**不合适**。正确顺序是**先正确、再快速** [源码]。
4. **什么时候该优化**：性能问题一旦**影响使用体验或导致功能不可用**，其严重程度**与 Bug 相同**，必须立刻处理。此外，同一个功能用**不同组件、不同算法**实现，对机器资源的占用**通常有差异**，这种差异就是优化空间 [源码]。
5. **用一个故事讲时机（扁鹊三兄弟）**：魏文王问扁鹊兄弟三人谁医术最好，扁鹊答"**大哥最好、二哥次之、我最差**"——因为大哥治病于**病情发作之前**，二哥治于**病情初起之时**，而扁鹊治于**病情严重之时**，所以只有他名声最大 [源码]。
6. **这个故事的工程翻译**：**防患于未然才是最高明的**——正如"不见防火英雄，只有救火英雄"。但在实际工作中，**问题要被看见**才有资源投入，所以也要学会在**合适的时机**把性能问题解决掉 [经验]。
7. **敏捷里怎么安排**：一般会在敏捷开发中**单独安排时间做性能优化冲刺**，把优化当成一个**有计划的迭代项**，而不是随手的临时改动 [源码]。
8. **重构与优化的关系**：重构**可能**提升性能，但它的首要价值是**降低维护成本**；把重构直接等同于性能优化**并不严谨**，准确说是"重构为后续优化创造了条件" [经验]。
9. **优化的收益空间**：即使是经验丰富的团队、时间充裕地写出的代码，**运行速度通常仍可提升 30%~100%**——但这是**经验估计值，不是普适定律**，具体能提多少**必须实测** [经验]。
10. **一条底线**：优化成果必须**可度量、可复现**。靠 benchmark 和 profile 数据说话，**绝不能靠人为制造基线**（详见「原文纠错」第 3 条）[经验]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| 任意项目 | 「先正确、再快速」不变 | 过早优化是反模式 |
| 敏捷团队 | 优化作为**独立冲刺**安排 | 有预算、有目标、有验收 |
| 有 SLA/SLO 的系统 | 性能即功能 | 不达标等同故障 |

## 关键代码
```go
// 时机论落到 Go 工程：优化前先有可复现的基线，优化后用同一基准验证
package main

import (
	"fmt"
	"strings"
	"testing"
	"time"
)

// 被测函数：字符串拼接（便于展示"优化前后同一基准对比"）
func concatPlus(n int) string {
	s := ""
	for i := 0; i < n; i++ {
		s += "x"
	}
	return s
}

func concatBuilder(n int) string {
	var b strings.Builder
	b.Grow(n) // 关键：预分配，避免多次扩容
	for i := 0; i < n; i++ {
		b.WriteByte('x')
	}
	return b.String()
}

// 基准测试基线：go test -bench . -benchmem
func BenchmarkConcatPlus(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_ = concatPlus(1000)
	}
}

func BenchmarkConcatBuilder(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_ = concatBuilder(1000)
	}
}

func main() {
	// 没有 go test 环境时的最小对照：直接计时
	start := time.Now()
	_ = concatPlus(200000)
	d1 := time.Since(start)

	start = time.Now()
	_ = concatBuilder(200000)
	d2 := time.Since(start)

	fmt.Printf("+= 拼接      : %v\n", d1)
	fmt.Printf("Builder 预分配: %v\n", d2)
	fmt.Printf("倍数         : %.1fx\n", float64(d1)/float64(d2))
}
```

> 验证（`[实测]` 输出，macOS / go1.26.5，20 万次单字符拼接）：
> ```text
> += 拼接      : 2.747641878s
> Builder 预分配: 405.468µs
> 倍数         : 6776.5x
> ```
> 说明：**"该不该优化"要先用数字回答**——这里差距达 **6776 倍**，属于"必须立刻优化"；而如果实测差距只有 3%，它就属于"现在不该动"。**结论：优化与否由实测数据决定，不由直觉决定**（基准测试写法见 `113-benchmark-basics`）。

## 总结与追问预判
- 一句话收尾：**优化的目标是达标，不是极致；时机由数据决定，不由焦虑决定**。
- 大概率被追的三问：① 老板要性能你怎么办（先量化现状→定目标→定位瓶颈→小步验证→固化进监控）；② 优化和功能冲突怎么取舍（功能正确优先，性能不达标等同故障时才升级为最高优先级）；③ 怎么防止性能回退（把基准测试与关键指标**纳入 CI 或常驻监控**）。
- 反向加分：主动说「**最高明的优化是让优化不必要**——设计阶段选对数据结构与算法，比事后调优便宜一个数量级」。

## ⚠️ 原文纠错
1. 源码称「重构也算性能优化」——不严谨：重构首要目标是**降维护成本**，非性能 [经验]。
2. 源码称速度「可提高 30%~100%」——**无来源的经验估计**，幅度须实测 [经验]。
3. 源码提到**故意加 sleep 再删掉**制造优化成果——**数据造假，伦理红线** [经验]。
4. 源码主张「让老板看到能力」——正道是**可复现数据 + 沉淀监控**，非挑时机 [经验]。
5. 源码称专家「能解决别人解决不了的问题」——**过窄**，更贵在**建立不发生的机制** [经验]。
6. 源码称「过程指标」——规范表述是**服务质量指标** [经验]。
