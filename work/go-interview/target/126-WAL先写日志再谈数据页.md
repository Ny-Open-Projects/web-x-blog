# 126 WAL：先写日志，再谈数据页

> 分类：MySQL / InnoDB | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**WAL、预写日志、redo log、log buffer、持久性**

> 原文锚点：第 11~29 段「写数据前先写事务日志，再一步刷盘…WAL…保证持久性」

## 一句话总述
WAL（预写日志）要求**修改先落日志再落数据页**：事务提交时数据页往往还在内存，持久性由已持久化的重做日志担保，崩溃后靠重放恢复。

## 面试官视角
P6 说"先写日志"；P7 要给出**四步流程**：分配事务 ID 并记开始 → 改内存数据页同时把重做日志写进日志缓冲 → 日志缓冲刷到磁盘日志文件（顺序 IO）→ 提交时再记提交信息并刷盘 `[源码]`。加分点：WAL 的三个价值——保持久性、保一致性、让多事务并发不必争抢同一数据文件 `[经验]`。

## 主问答
**Q（面试官原话）：** 事务提交了，数据到底写没写到磁盘？

1. **提交时数据页通常没落盘**：被持久化的只是重做日志，数据页由后台线程异步刷，两者是**独立操作** `[经验]`。
2. **日志是顺序写**：重做日志按顺序追加，属顺序 IO，性能远高于随机写数据页 `[源码]`。
3. **日志里记什么**：事务 ID、操作类型、数据页位置、修改后的值，足够重放 `[源码]`。
4. **崩溃后怎么办**：未刷盘的数据页靠重放重做日志恢复到正确状态，这正是持久性的来源 `[实测]`。

## 关键代码
```sql
BEGIN;
UPDATE user_balance SET balance = balance + 1 WHERE id = 1;  -- 改内存页 + 写日志缓冲
COMMIT;                                                      -- 日志刷盘即算持久化
```
> 验证：提交后立即 `SHOW ENGINE INNODB STATUS`，可见日志序列号前进，而脏页数尚未归零 `[实测]`。

## 总结与追问预判
**持久性由日志担保，不由数据页担保**。下一步必问：日志到底在哪些时刻被刷盘。
