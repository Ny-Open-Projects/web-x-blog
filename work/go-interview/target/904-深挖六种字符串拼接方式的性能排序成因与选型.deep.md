# 904 深挖：六种字符串拼接方式的性能排序、成因与选型

> 分类：Go 基础 / string | 难度：L4 | 题型：综合题 | 频率：高 | 关键词：**六种方式、不可变、预分配、Grow、零拷贝、编译期常量、strings.Builder、strings.Join**

> 原文锚点：第 1~74 段「字符串常见的拼接方式有六种：通过加号连接符进行拼接、通过格式化函数进行拼接、通过 bytes.Buffer、通过 strings.Builder、直接通过字节切片进行拼接、通过 strings.Join 函数进行拼接…strings.Builder 在大量字符串拼接的场景下性能表现比较出众，这种方式也是官方推荐的字符串拼接方式…日常使用呢不必过于纠结，更多的应该关注代码的风格和可读性，因为代码的简洁本身也是一种生产力」

## 思路与架构

按「**六种方式 → 两条性能主线 → 选型**」三层把握：

1. **六种方式**：**① 加号连接符；② 格式化函数（`fmt`）；③ bytes.Buffer；④ strings.Builder；⑤ 字节切片；⑥ strings.Join**。
2. **两条决定性能的主线**：
   - **主线一 · 有没有预分配**：低效方式（加号、`fmt`）**每次拼接都要开辟新空间**——**字符串不可变，加号每拼一次就生成一个新字符串**，于是**频繁对象创建 + 旧对象等待 GC**；`fmt` 更甚，还要走**对象创建 → 格式化 → string 转化 → 对象释放**四步。高效方式（Buffer / Builder / 预分配切片 / Join）都用**预分配**：**`Grow` 提前申请空间**，**追加时预申请更多空间**，从而**避免后续频繁的空间申请**；实测**不预分配会不断扩容，`Grow` 之后不再扩容**。
   - **主线二 · 最后一步转字符串是否拷贝**：`bytes.Buffer` **强转、要重新申请内存**；`strings.Builder` **零拷贝、直接把底层 `[]byte` 转成字符串返回**。这一条让 **Builder 整体性能略高于 Buffer**。
3. **扩容规则（两者共有）**：**当 buffer 的容量减去 buffer 的长度，小于当前需要追加的字符串的长度时才触发扩容**；**扩容到两倍的当前 buffer，再加上当前需要追加的字符串的长度**（Go 1.20 起改为更平滑的 `slices.Grow` 策略）。
4. **两个易被忽略的高效点**：**`strings.Join` 底层就是 `strings.Builder` + 内部 `Grow`**，且**入参切片长度固定**所以预分配很准；**两个常量字符串拼接由编译期预分配**，几乎零运行时成本。

## 方案取舍

| 方式 | 是否预分配 | 转字符串 | 适用 |
|---|---|---|---|
| 加号 `+` | 否 | 每次生成新串 | 少量拼接、常量拼接 |
| `fmt.Sprintf` | 否 | 强转 + 反射解析 | 需要格式化，不在热路径 |
| `bytes.Buffer` | `Grow` | **强转（拷贝）** | 需要字节级读写/`io.Reader` |
| `strings.Builder` | `Grow` | **零拷贝** | 大量拼接、高并发（推荐） |
| 预分配字节切片 | `make(cap)` | 强转（可 unsafe 规避） | 已知总长、追求极致 |
| `strings.Join` | 内部 `Grow` | 零拷贝 | 已有字符串切片，最省心 |

取舍要点：**快与慢的分水岭是"能不能少分配"**，而**Builder 与 Buffer 的分水岭是"最后一步要不要拷贝"**。原文给的工程建议很中肯——**日常使用不必过于纠结，更应关注代码风格与可读性，代码简洁本身也是生产力**；**只有在极少数需要极致性能的场景下，才需要慎重选择性能更高的拼接方式**。

## 答题技巧

1. **开口先列六种**：加号 / `fmt` / Buffer / Builder / 字节切片 / `strings.Join`——能列全就已经领先多数候选人。
2. **慢的两条要给因果**：**加号 = 不可变 → 每次新串 → 频繁分配 + GC**；**`fmt` = 创建 → 格式化 → 强转 → 释放**。
3. **快的四条要说"预分配"**：核心是 **`Grow` 提前申请空间，追加时再预申请更多**。
4. **Builder 胜出的根因必须答准**：**`String()` 零拷贝 vs `Buffer` 强转拷贝**——这是本题的灵魂。
5. **主动补两条加分项**：**`strings.Join` 底层就是 Builder + Grow**；**常量拼接在编译期完成**，所以两个常量拼接几乎不耗时。
6. **止步档位**：能说清"加号慢、Builder 快"即达 L4；能列全六种、讲清扩容规则、零拷贝差异、Join 实现与常量优化，并给出"可读性优先"的选型态度，即达 L5。

## ⚠️ 原文纠错
1. 事实核校：六种拼接方式、加号因字符串不可变每次生成新串并开辟空间、大量拼接导致频繁对象创建与 GC 负担、`fmt` 创建对象并使用对象池且每次强转、Buffer 与 Builder 均有 `Grow` 预分配、扩容触发条件与 `2*cap+n` 公式、Builder 零拷贝而 Buffer 强转、Join 底层为 Builder 且内部 `Grow`、常量在编译期预分配故拼接更快更省内存——均与 Go 语义一致 `[经验]`。
2. 补充：**`2*cap + n` 为 Go 1.10~1.19 实现，1.20 起改用 `slices.Grow`**；**`Builder.String()` 零拷贝后不可再写入**；**`unsafe` 零拷贝转换在 Go 1.20+ 应改用 `unsafe.String`** `[经验]`。
3. 崩坏词归一：源码将 bytes.Buffer、strings.Builder、strings.Join、Grow、预分配、扩容、零拷贝等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
