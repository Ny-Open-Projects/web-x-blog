# 922 深挖：sync.Map 的整体设计、代价边界与选型

> 分类：Go 并发 | 难度：L5 | 题型：综合题 | 频率：高 | 关键词：**读写分离、原子操作、加锁、读多写少、misses、延迟删除、选型**

> 原文锚点：第 38~77 段「sync.Map 是通过 read 和 dirty 两个字段将读写分离，从而尽可能减少锁的操作。需要注意的是，sync.Map 并不是适用于所有场景的解决方案，它主要是用于读多写少的场景。对于写操作非常频繁的场景，需要其他更加高级的并发控制机制…map 并发安全的实现有两个思路，是原子操作和加锁…基本思路就是尽可能多地使用原子操作，直到迫不得已才会使用锁机制」

## 思路与架构

按「**设计原则 → 结构 → 代价与边界**」三层把握：

1. **设计原则：原子优先，锁兜底**：
   - 并发安全只有两条路——**原子操作**与**加锁**。
   - **原子操作是直接面向硬件的一组不可分割的指令**，**效率比加锁高很多**。
   - 因此 `sync.Map` 的基本思路是：**尽可能多地使用原子操作，直到迫不得已才使用锁机制**。
   - 落到结构上：**read 用原子操作读（无锁）**，**dirty 用锁保护（有锁）**。
2. **结构：双 map + 计数器 + 三态指针**：
   - **read / dirty 双 map 读写分离**：读先 read、后 dirty；写只写 dirty。
   - **misses 计数器**：统计 read 被穿透的次数，**超过 `len(dirty)` 就把 dirty 提升为 read**，让后续读重新回到无锁路径。
   - **entry 三态**：正常指针 / `nil`（刚标记删除，仍属 dirty）/ `expunged`（已重整，只属 read，下次提升时彻底删除）。
   - **延迟删除 + 浅拷贝重整**：避免 read 无限膨胀，拷贝只动指针。
3. **代价与边界**：
   - **写密集会退化**：新 key 只进 dirty，读新 key 必然穿透加锁，misses 快速累积 → 频繁提升 → 开销接近甚至超过"普通 map + 锁"。
   - **删除不是即时释放**：标记删除后内存要等重整才回收，大量删除的 key 会阶段性占位。
   - **类型安全缺失**：键值为 `any`，编译期无类型检查，还有装箱开销。
   - **一致性语义**：read 是快照，读路径不保证严格的线性一致。

## 方案取舍

| 关注点 | `sync.Map` | 普通 map + `sync.RWMutex` |
|---|---|---|
| 读性能 | 命中 read 时**无锁**，极高 | 需读锁，有原子开销 |
| 写性能 | 只写 dirty，写密集时退化 | 写锁独占，稳定 |
| 类型安全 | `any`，无编译期检查 | 可配合泛型，类型安全 |
| 遍历 | `Range` + 回调，快照语义 | 自行加锁遍历 |
| 内存 | 双 map + 延迟删除，占用偏高 | 单 map，占用低 |
| 适用 | **读多写少**、写一次读多次 | 读写比例接近、或需类型安全 |

取舍要点：**`sync.Map` 用"双份结构 + 延迟删除 + 快照语义"换"读路径无锁"**。这份交易只在**读远多于写**时才划算；一旦写占比上升，misses 触发的提升与 dirty 重建会吃掉全部收益。因此 **Go 官方文档也只推荐两类场景**：**① 写一次读很多次（如缓存）；② 多个 goroutine 各写各的不相交的 key 集合**。

## 答题技巧

1. **开场先给设计原则**：**原子优先、锁兜底**——这一句能把后面所有结构选择串起来。
2. **结构上讲三条就够**：**read/dirty 读写分离**、**misses 触发提升**、**entry 三态 + 延迟删除**。少一条都会被追问。
3. **必须主动说适用边界**：**读多写少**；**写操作非常频繁的场景需要更高级的并发控制机制**——能主动说出边界，比多背一条细节更值钱。
4. **给出替代方案**：写密集用**分片 map（sharding）+ 互斥锁**；需要类型安全用**泛型 + `RWMutex`**；缓存场景用 `sync.Map` 或 `singleflight`。
5. **纠正一个常见误传**：**dirty 是互斥锁保护，不是自旋锁；CAS 用在 entry 状态变更上**。
6. **止步档位**：能讲清双 map 与读写分离即达 L4；能补上 misses 提升、entry 三态、延迟删除与适用边界，即达 L5。

## 细节与核心 API

```go
// 内部：read（atomic.Load 的只读 map，无锁快路径）+ dirty（含新写入，需锁）
// 适合：读多写少、key 集合相对稳定；不适合频繁写或需遍历一致
var m sync.Map
m.Store("a", 1)
m.LoadOrStore("b", 2)        // 不存在才存
if v, ok := m.Load("a"); ok { _ = v }
m.Delete("a")
m.LoadAndDelete("b")
// 代价：miss 频繁会升 dirty、双份存储；value 是 interface{} 有装箱/类型断言开销
// 选型：通用并发 map 用 map+RWMutex；仅热点只读+偶发写用 sync.Map
// 不要对 sync.Map 做范围遍历做强一致快照（Load 与 Range 不保证同一瞬间视图）
```

## ⚠️ 原文纠错
1. 事实核校：读写分离以减少锁操作、原子操作面向硬件且效率高于加锁、原子优先锁兜底、read/dirty 双 map、misses 触发提升、entry 三态与延迟删除、适用读多写少且写密集需其他并发控制机制——均与 Go 标准库实现一致 `[经验]`。
2. 补充：**原文称对 dirty 的写入使用"自旋锁 + CAS"，实际是互斥锁 `mu sync.Mutex` 保护 dirty，CAS 用于 entry 指针状态变更**；另 `sync.Map` 的官方推荐场景是**写一次读多次**与**不相交 key 集合的并发写**，不只是笼统的"读多写少" `[经验]`。
3. 崩坏词归一：源码将 sync.Map、原子操作、加锁、自旋锁、读多写少、entry 等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
