# 163 观察者模式：用 channel 做发布订阅

> 分类：设计模式/行为型 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**发布订阅** / **channel** / **解耦**
> 原文锚点：第 17~25 段「观察者定义一对多依赖，主题变动自动通知所有观察者」

## 一句话总述
观察者让一个主题被多个观察者监听，主题状态变化自动广播通知；Go 里用 channel + goroutine 实现最地道，比回调接口更契合并发模型。

## 面试官视角
- 意图：能否区分观察者（松耦合通知）与中介者（集中调度），并说清 Go 的 channel 实现与泄漏风险。
- P5 知用 channel 广播 / P6 说清同步 vs 异步通知、慢消费者阻塞 / P7 知退订、背压、goroutine 泄漏治理。
- 红旗：观察者 handler 抛 panic 拖垮主题；忘了退订导致泄漏；用共享变量代替 channel。
- 惊艳点：慢消费者会反向阻塞发布者（无缓冲 channel 同步传递），高并发下需用带缓冲+select default 或独立收件箱 —— 验证：写个慢订阅者看发布 goroutine 卡住，go1.26.5 `[经验]`。

## 主问答
**Q（面试官原话）：** 怎么实现事件通知，一个变化通知多处？
**A：**
1. **结论**：主题维护订阅者 channel 列表，发布时向各 channel 发消息；订阅者各自 range 接收。
2. **机制**：无缓冲 channel 是同步的——某个慢订阅者不接收会阻塞发布循环；用缓冲或 select+default 解耦 `[经验]`。
3. **边界**：必须提供 Unsubscribe 并退出 goroutine，否则订阅者 goroutine 泄漏；handler 内 recover 防 panic 扩散。
**加分层：** 高频事件用"每个订阅者独立收件箱 goroutine + 缓冲 channel"做背压隔离，互不拖累。

## 关键代码
```go
// 示意，未验证：channel 发布订阅
type Hub struct{ mu sync.Mutex; subs []chan string }

func (h *Hub) Publish(msg string) {
	h.mu.Lock(); defer h.mu.Unlock()
	for _, c := range h.subs { c <- msg } // 慢订阅者会阻塞此处
}
```
