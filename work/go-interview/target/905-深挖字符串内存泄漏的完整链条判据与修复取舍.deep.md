# 905 深挖：字符串内存泄漏的完整链条、判据与修复取舍

> 分类：Go 基础 / string | 难度：L4 | 题型：综合题 | 频率：中 | 关键词：**共享底层、截取泄漏、赋值传参不拷贝、地址改变、拷贝切断、strings.Clone、strings.Builder**

> 原文锚点：第 1~6、26~33、73~75 段「字符串底层存储实际上是指向的一个字节切片的指针…截取后的字符串引用了原始的字符串的地址…即使不再需要这个切片，原始字符串的内存也是无法释放的，从而导致了内存泄露…第一种方式是将截取后的子字符串转成字节切片，然后再转成 string 类型；第二种方法是截取完子字符串之后，在它的前面拼接上一个新的字符串，然后再截掉这个新的字符串；最后一种方式是使用 strings.Builder 方法对新的字符串进行重新构造」

## 思路与架构

按「**为什么会泄漏 → 怎么判断 → 怎么修**」三层把握：

1. **为什么会泄漏（一根链条）**：
   - `string` 是**描述符**：**底层存储实际上是指向的一个字节切片的指针**（指针 + 长度）。
   - **赋值、按值传参、按指针传参都不拷贝数据**，得到的变量与原始字符串**指向同一块内存**；把原串置空也只是让它的指针改指别处，**原字节数组若仍被引用就不会释放**。
   - **截取**更进一步：**截取后的字符串引用了原始字符串的地址**，两者**起始地址相同**，于是**子串持有原始字符串的内存**——**即使不再需要这个子串，原始字符串的内存也无法释放**，这就是内存泄漏。
   - **典型场景**：**一个大字符串只取前二十个字符**，只要这个子串还活着，整块大内存就一直不会被回收；**大量子串截取同一超长字符串时**，泄漏会被显著放大。
2. **怎么判断（唯一判据）**：
   - **看地址是否改变**。地址不变 = 仍共享原串；地址改变 = 已发生拷贝、成为独立副本。
   - 已验证的三种"不变"情形：**赋值**、**按值/按指针传参**、**截取**。
   - 已验证的两种"改变"情形：**`string` 与 `[]byte` 互转**（强转必拷贝）、**追加操作**（拼接会触发拷贝，这也是"前拼空串再截掉"能生效的原因）。
   - 特殊对照：**`strings.Repeat(s, 1)` 地址不变**（源码直接把入参 return 回去）；**`Repeat(s, n>1)` 地址改变**（走 `strings.Builder` 预分配并在重复过程中扩容）。
3. **怎么修（三 + 一条官方答案）**：
   - **① `[]byte` 中转**：截取 → 转 `[]byte` → 转回 `string`。
   - **② 前拼新串再截掉**：截取 → 前拼一个新串 → 截掉新串。
   - **③ `strings.Builder`**：预分配截取空间 → 写入 → 取出；**因为是新申请的内存空间，这种方式最安全**。
   - **官方答案**：**Go 1.18+ 用 `strings.Clone`**，语义清晰、一行搞定。

## 方案取舍

| 关注点 | 结论 | 影响 |
|---|---|---|
| 描述符模型 | 指针 + 长度 | 复制成本低，但共享数据 |
| 赋值 / 传参 | 不拷贝 | 与原串共享同一地址 |
| 截取 | 不拷贝、共享起始地址 | **子串钉住整块大内存** |
| 置空原串 | 只改指针指向 | **有引用就不释放** |
| 强转 `string ↔ []byte` | 必拷贝 | 可作为切断手段 |
| 追加 / 拼接 | 触发拷贝 | "前拼再截"因此有效 |
| `strings.Builder` | 新申请内存 | 最安全、可读性最好 |
| `strings.Clone` | 官方语义化 API | Go 1.18+ 首选 |

取舍要点：**这一节的所有取舍都围绕一条——"共享"换来的是低复制成本，"独立"付出的是一次分配与拷贝**。**不要在热路径上无差别 `Clone`**；正确姿势是**按生命周期决策**：子串只是函数内短用就保持共享，子串要长期保存（进缓存、进结构体、跨请求传递）就必须切断。

## 细节与核心 API

**① 泄漏现场 + 地址判据（一套可背的代码）**

```go
package main

import (
	"fmt"
	"strings"
	"unsafe"
)

// 取 string 底层字节数组的起始地址（判据工具）
func addr(s string) uintptr {
	return (*(*[2]uintptr)(unsafe.Pointer(&s)))[0]
}

func main() {
	big := strings.Repeat("A", 1<<20) // 1MB 大串

	// ① 截取：地址不变 → 共享原串 → 子串钉住 1MB
	sub := big[:20]
	fmt.Println(addr(big) == addr(sub)) // true ← 子串持有整块大内存

	// ② 赋值 / 传参：也不拷贝，地址同样不变
	cp := big
	fmt.Println(addr(big) == addr(cp)) // true

	// ③ 置空原串没用：指针改指别处，但只要 sub 活着，原字节数组就不会释放
	big = ""
	_ = sub // 此时 1MB 仍被 sub 钉住
}
```

**② 三种修复写法 + 官方答案**

```go
// 修复①：[]byte 中转（强转必拷贝）
sub1 := string([]byte(big[:20]))

// 修复②：前拼新串再截掉（拼接触发拷贝）
sub2 := ("" + big[:20])[0:] // 拼空串会触发拷贝，地址改变

// 修复③：strings.Builder（新申请内存，最安全）
var b strings.Builder
b.Grow(20)
b.WriteString(big[:20])
sub3 := b.String()

// ✅ 官方答案（Go 1.18+）：strings.Clone，语义清晰、一行搞定
sub4 := strings.Clone(big[:20])

// 验证：以上四种地址都与 big 不同
fmt.Println(addr(sub1) != addr(big), addr(sub4) != addr(big)) // true true
```

**③ `strings.Repeat` 的源码对照（证明读过源码的加分点）**

```go
r1 := strings.Repeat(big, 1) // 源码直接 return s → 地址不变
r2 := strings.Repeat(big, 2) // 走 strings.Builder 预分配+扩容 → 地址改变
fmt.Println(addr(r1) == addr(big)) // true
fmt.Println(addr(r2) == addr(big)) // false
```

**④ 真实泄漏场景（背这个例子）**

```go
// 读大文件/大响应体后只取前若干字节做日志或校验 → 子串把整块钉住
func fingerprint(path string) (string, error) {
	data, err := os.ReadFile(path) // 假设 100MB
	if err != nil {
		return "", err
	}
	// ✗ 直接截取：返回的 20B 子串钉住 100MB
	// return string(data[:20]), nil

	// ✓ 切断共享：只留 20B
	return strings.Clone(string(data[:20])), nil
}
```

> 判据一句话：**看地址变没变**。地址不变 = 仍共享；地址改变 = 已拷贝成独立副本。
> 取舍提醒：**别在热路径上无差别 `Clone`**——按生命周期决策：
> 函数内短用就保持共享（省一次分配），要长期保存（进缓存/结构体/跨请求）才切断。

## 答题技巧

1. **先把泄漏链条讲完整**：**描述符共享 → 截取同址 → 子串钉住整块 → 原串不可回收**，四步缺一会被追问。
2. **给出唯一判据**：**"看地址变没变"**。这句话能把后面所有现象和修复手法统一起来，是最漂亮的答题骨架。
3. **务必举出真实场景**：**读大文件 / 大响应体后取前若干字节做校验或日志**——这类例子最能证明不是背结论。
4. **`Repeat` 的对照很好用**：**参数 1 地址不变、大于 1 地址改变**，因为它分别走了"直接 return"与"`Builder` 扩容"两条路径，可以顺带证明你读过源码。
5. **主动补 `strings.Clone`**：原文成文时尚无此 API，**补上它（Go 1.18+）是明显的加分项**。
6. **止步档位**：能讲清泄漏原因并写出一种修复即达 L4；能给出完整链条、三种写法、`Repeat` 对照与官方 API，即达 L5。
