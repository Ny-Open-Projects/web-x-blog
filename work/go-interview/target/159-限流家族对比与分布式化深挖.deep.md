# 159 限流家族对比与分布式化深挖

> 覆盖源 15-9 的工程延伸：四算法的判读矩阵与选择流程、滑动窗口的环形数组实现、令牌桶/漏桶在网关与客户端的落位、分布式限流的原子化与协调语义。主卡已给算法与形态，本附录做选型与落地深挖。

## 思路与架构

```text
限流选型决策树
├─ 保护谁?
│   ├─ 保护脆弱下游(只吃固定速率) -> 漏桶 / 固定速率消费
│   ├─ 控制调用方平均用量 -> 令牌桶 (留突发余量)
│   └─ API 计数配额 -> 滑动窗口 / 固定窗口(粗)
├─ 突发要不要放行?
│   ├─ 要 -> 令牌桶 (桶容量=突发上限)
│   └─ 不要 -> 漏桶 / 滑动窗口
├─ 单机 or 全局?
│   ├─ 单机: 内存计数 (注意多实例配额=N/实例数)
│   └─ 全局: Redis+Lua 原子化 / 网关集中
└─ 满了怎么办?
    ├─ 直接拒 (429/快速失败) -> 上游可重试
    └─ 排队 (延迟队列) -> 延迟换成功率, 队长要限
```

## 方案取舍
- **固定窗口边界突刺的修复阶梯**：[实测] 配额 10/窗，跨边界 20 连发全放行（2 倍）。修复阶梯：① **滑动窗口**——把 1 窗切 N 子窗，按子窗滑动求和，内存 O(N)；② **精确滑动窗口**——记录时间戳队列（或环形数组），窗口外过期出队，最准但最贵；③ **令牌桶**——干脆按速率发牌，边界问题不存在。选哪档看业务对突刺的敏感度，粗限流用固定窗 + 上游退避也够用 [经验]。
- **令牌桶 vs 漏桶的角色差异最易混**：令牌桶约束的是**调用方平均速率**（攒令牌=攒突发额度，鼓励错峰）；漏桶约束的是**被调方承受速率**（出口恒速，削平一切）。同一系统里两者可共存——客户端用令牌桶自限、服务端用漏桶/队列兜底；方向不同，不是二选一 [经验]。
- **分布式限流的原子化要点**：多实例共享计数必须**判定与自增原子化**——Redis 侧用 Lua 脚本（GET+INCR+EXPIRE 合一，防竞态双计），或 Redis 模块的速率限流命令。中心化的代价：Redis 成为限流链路的可用性单点（Redis 抖动时策略要「fail-open 放行」还是「fail-close 拒绝」必须提前拍板——多数业务 fail-open，交易类 fail-close）[经验]。
- **拒绝后果与上游协议**：限流不是终点——被拒请求的上游行为决定系统韧性：HTTP 429 + Retry-After、客户端指数退避（「抽样反馈驱动加压」的同构：429 比例是限流效果的观测信号）、队列式则要设**最大排队时长**防延迟雪崩。**限流策略必须和上游的退避策略成对设计**，只配服务端不谈客户端是半套方案 [经验]。

## 答题技巧
- 用 [实测] 数字开题：「固定窗口跨边界 20 连发全放行，2 倍突刺」——一句话钉死固定窗口的缺陷 [实测]。
- 按「保护谁→突发→单机全局→满了怎么办」决策树答选型，展示流程而非背名单 [经验]。
- 被问「分布式怎么做」→ Redis+Lua 原子化 + fail-open/fail-close 拍板——落到工程决策层 [经验]。
- 被问「ES 怎么限流」→ 读写线程池固定容量+满则拒（延迟队列式），拒绝异常即背压信号 [源码]。
- 主动边界到 `159-rate-limit-algorithms`（算法与形态主线）、`108-rate-limiter-go`（Go 实现体）、`1016-channel-ratelimiter`（channel 版）、`1016-ratelimit-vs-semaphore`（限流 vs 信号量语义差），构成「限流」专题 [边界]。
