# 164 懒汉 vs 饿汉单例：选型对比与 Go 的 init 饿汉

> 分类：设计模式 / 创建型 | 难度：L2 | 题型：手写题 | 频率：中 | 关键词：**懒汉式**/**饿汉式**/**init 函数**/**并发安全**/**选型倾向**
> 原文锚点：第 1~27 段「懒汉式在使用的时候才进行初始化，实例化的过程是懒加载的，一定程度上节省资源，最大问题是需要考虑并发安全…饿汉式在程序初始化的时候就已创建好，加载速度快、实现简单、线程安全…大多数情况下我们通常更多使用饿汉模式」

## 一句话总述
懒汉 vs 饿汉的本质分歧是「**实例化时机**」：**懒汉**首次使用才创建——省资源但首载慢、**必须处理并发安全**（否则竞态多次创建）；**饿汉**在包 `init`/变量初始化时创建——Go 的 init 每程序启动只执行一次，**天然线程安全、实现零成本**；作者结论：**大多数场景倾向饿汉**——单例迟早要用，懒加载意义不大，同步开销反是负担。

## 面试官视角
- 考察意图：手写两种实现只是及格线，真正考察**选型推理**——「为什么实际倾向饿汉」能讲出「懒加载的意义 + 同步的代价」才是理解。
- 分档：P5 能手写两种雏形；P6 讲清两者的优缺点对照与 init 的单次语义；P7 能给「何时才真正需要懒汉」（初始化昂贵/有副作用/可能永远不用）与 sync.Once 的官方答案。
- 红旗答案：懒汉裸写 `if instance == nil` 就交付（并发多次创建）；说「饿汉线程安全是因为 Go 的 init 有锁」——init 的串行性来自**包初始化机制**（单 goroutine 顺序执行依赖链），不是锁。
- 惊艳点：「**饿汉把『线程安全』从运行时问题变成了初始化时序问题**——init 在任何用户 goroutine 之前串行完成，天然没有竞态窗口」 [经验]。

## 主问答
**Q（面试官原话）：** 分别用懒汉式和饿汉式实现单例，说说区别。
**A：**
1. **懒汉式：使用时才实例化**。定义 `var lazyInstance *instance`，访问入口 `GetInstance()` 里判 `nil` 才创建。优点：首用才建，**一定程度节省资源**（含初始化开销大的对象）；缺点：**第一次加载变慢**，且最大问题是**并发安全**——多个 goroutine 同时判 nil 会竞态多次创建 [源码]。
2. **懒汉的并发补丁**：裸判 nil 不可交付——工程答案按序是 **Mutex 加锁 → 双重检查（DCL）→ sync.Once**（官方推荐，内部即 atomic+Mutex 双检），完整链路见 `165-singleton-mutex-dcl`、`165-singleton-atomic`、`165-singleton-once` [边界]，本卡不重述实现细节。
3. **饿汉式：初始化即创建**。Go 的做法：包级变量 `var eager = &instance{n: 1}` 或在 **`init()` 函数**里实例化——**Go 保证程序启动时 init 只执行一次**（且依赖链串行），后续访问入口直接返回已建实例，无需任何判空与加锁 [源码]。
4. **优缺点对照**：饿汉优点——实现简单、执行效率高、**天然线程安全**；缺点——若实例整个生命周期从未被使用，**白占内存**。懒汉优点——延迟到需要时；缺点——首载慢 + 并发安全成本 [源码]。
5. **选型结论：默认倾向饿汉**。推理链：① 单例通常**迟早要被实例化**——延迟创建的意义本就不大；② 懒汉的加锁/解锁是**运行时持续开销**，同步操作降低 CPU 利用率，使用不当还引入风险；③ 饿汉把安全交给初始化时序，运行时零成本。**只有「初始化昂贵、有副作用、或可能永远不用」的对象才值得懒汉**（如重连接、按配置懒加载） [源码]。

## 关键代码
```go
// 懒汉(sync.Once 官方版) + 饿汉(包级变量) 实测对比
type instance struct{ n int }

var (
	lazy  *instance
	once  sync.Once
	eager = &instance{n: 1} // 饿汉: 包变量初始化, 启动即建
)

func GetLazy() *instance {
	once.Do(func() { lazy = &instance{n: 42} }) // 只执行一次
	return lazy
}
func GetEager() *instance { return eager } // 无判空无锁

func main() {
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() { defer wg.Done(); GetLazy() }()
	}
	wg.Wait()
	// [实测] -race 下 100 并发: once.Do 恰好执行 1 次, lazy.n=42, eager.n=1
	// 数据竞争 0 —— Once 懒汉安全, 饿汉天然无竞态窗口
}
```

## 总结与追问预判
一句话记忆：**「懒汉省资源但欠并发债，饿汉零运行时成本但可能白占内存；Go 里饿汉靠 init 单次语义白嫖线程安全——默认饿汉，昂贵初始化才 sync.Once 懒汉」**。并发安全的懒汉全家族（DCL/atomic/Once 源码同源性）见 `165-singleton-mutex-dcl`、`165-singleton-atomic`、`165-singleton-once`、`165-thread-safe-singleton.deep` [边界]。常追问「init 里做重活有什么问题」——答拖慢启动、隐式依赖链难排查、失败难处理（init panic 直接崩），重初始化更宜显式 `Init(ctx)` 或懒加载；再追问「init 会并发执行吗」——不会，单 goroutine 按依赖序串行，这正是饿汉安全的来源。

## ⚠️ 原文纠错
1. 术语归一：[经验] 源为语音转写，「揽汉式/揽函式」应为「懒汉式」，「二函式/恶焊模式」应为「饿汉式」，「neo」应为 nil，「NNIT函」应为 init 函数，统一为规范术语。
2. 表述纠错：源说 init「只会执行一次」需精确为「每个包的 init 按依赖序**串行**执行一次」——串行性才是饿汉线程安全的真正来源，本卡已补全。
3. 补充：源未提 sync.Once 与 OnceFunc/OnceValue 泛型演进，以及 init 重活反模式，本卡已补 [经验]。
