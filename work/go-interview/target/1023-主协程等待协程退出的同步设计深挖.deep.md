# 1023 主协程等待协程退出的同步设计深挖

> 分类：Go 并发 / 同步 | 难度：L3 | 题型：深挖 | 频率：中 | 关键词：**WaitGroup** / **广播** / **channel 同步** / **信号量** / **选型边界**
> 原文锚点：第 1~50 段「WaitGroup三件套/广播通知/无缓冲channel同步/信号量限并发(不推荐等待)」

## 思路与架构
"主协程等子协程退出"本质是**完成计数**问题，WaitGroup 是为此而生的原语；channel 同步是"用通信模拟计数"，可读但繁琐；信号量是"资源池/并发度"原语，被误用时才去等退出。回答时先定诉求（等完成 vs 限并发），再选原语，最后谈进阶（广播通知、数据依赖）。

## 方案取舍
```text
等待/同步原语取舍矩阵：
──────────────────────────────────────────────────────────────
原语            本职语义        适用诉求          本场景推荐度
WaitGroup       完成计数        等全部退出        最推荐(可读性好)
无缓冲 channel  通信模拟计数    等全部退出        可用(需读满)
信号量          资源池/限并发   限同时执行数      不推荐(语义错位)
双 WG 广播     一次性就绪通知   协程间数据依赖    进阶(妙用)

设计法则：
- 等退出 → WaitGroup 首选；需要"数据就绪再继续" → 双 WG 广播
- channel 同步务必读满全部值，否则漏等
- 信号量只用于限并发，别拿去当完成计数
- Done 即 Add(-1)，广播里把 WG 当条件变量用
```

## 答题技巧
```text
面试话术（先诉求后选型，再进阶）：
1. 诉求：等全部退出 → WaitGroup(Add/Done/Wait)，可读性最佳
2. 替代：无缓冲 channel（子末行写、主读满）；信号量限并发不推荐
3. 进阶：协程间数据依赖 → 双 WG 广播（ready.Wait 阻塞、Done 通知）
4. 避坑：channel 需读满；信号量误用=语义错位
5. 收尾：WaitGroup 是完成计数原语，信号量是资源池原语，职责不同
```

> 边界：WaitGroup 用法与坑见 913；无缓冲 channel 阻塞 main 见 1024；信号量限并发见 1015；信号通知对照见 1024。本卡只深挖"等待退出同步设计"不重述 WaitGroup 实现原理。
