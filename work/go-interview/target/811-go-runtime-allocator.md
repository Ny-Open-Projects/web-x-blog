# 811 Go runtime 内存分配：tcmalloc 思想

> 分类：内存与 GC | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**runtime 自主管理** / **降低锁粒度** / **内存池**
> 原文锚点：第 109~122 段「runtime 抛弃传统分配…源于 tcmalloc…二级分配…线程内存池…池化」

## 一句话总述
Go runtime 不每次走系统调用，而是借鉴 tcmalloc 做多级缓存分配：本地小对象缓存优先、不足再向中心/全局池要，以降低锁竞争、减少用户态/内核态切换。

## 面试官视角
- 意图：是否理解 Go 为何自己管内存、怎么兼顾性能与并发。
- P5 知内存池减少 syscall / P6 说清多级缓存与降锁 / P7 知 mcache/mcentral/mheap 结构。
- 红旗：以为 Go 每次分配都 mmap；以为「线程池」即 OS 线程。
- 惊艳点：本地缓存命中几乎无锁，竞争才走中心池 —— 验证 `GODEBUG=allocfreetrace=1` `[经验]`。

## 主问答
**Q（面试官原话）：** Go 的内存管理是怎么实现的？为什么不用系统调用？
**A：**
1. **结论**：runtime 自管堆，借鉴 tcmalloc 多级分配，本地缓存优先、全局兜底，减少 syscall 与锁竞争 `[源码]`。
2. **机制**：小对象走处理器本地缓存，不足向中心缓存、再向堆（全局）申请；大对象直连堆。
3. **边界**：本地缓存不是 OS 线程私有——Go 中挂在 P（处理器）上（mcache），随 GMP 调度迁移。
**加分层：** 池化把频繁小分配变成复用，但池过大反而浪费物理内存。

- 预判：GC → 见 811-go-gc-tricolor；逃逸 → 见 811-go-escape-analysis。

## ⚠️ 原文纠错
原文第 113 段称 Go「每个线程都会自行维护一个独立的内存池」。该说法沿用了 tcmalloc 的线程本地缓存表述，但对 Go 不够精确：Go 的 GMP 模型下小对象本地缓存是挂在 P（处理器，mcache）而非 OS 线程（M）上，随调度在 P 间迁移，并非每线程私有。其余「二级分配、不足再向全局池申请、以降低锁粒度」的核心思想与 Go 实现一致。机翻解码：勾浪→Go、tmalloc→tcmalloc、mloc→malloc。
