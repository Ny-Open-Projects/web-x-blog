# 1018 goroutine 的「估值时刻 vs 执行时刻」

> 分类：并发模型 | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**go 语句估值** / **调度时机** / **GOMAXPROCS** / **非确定性**
> 原文锚点：第 16~29 段「go 声明时变量即估值、调度执行时机不定；sleep(1s) 恰能看到正确值；GOMAXPROCS=1 只是巧合非保证」

## 一句话总述
`go f(args)` 在**声明那一刻**就对参数求值，而 goroutine 的**执行**是异步调度、时机不定——这是 for 循环里 goroutine 读到"奇怪值"的根因：你以为读的是当时的值，实际读的是调度到时才看到的值。

## 面试官视角
- 意图：考察候选人是否建立"声明求值 / 执行调度"两阶段心智模型，而非只背"传参能修"。
- P5 知道 goroutine 异步、读到的值不确定；P6 能说清"声明即估值、执行才调度"；P7 能指出 GOMAXPROCS=1 或 sleep 只是巧合、非语义保证。
- 红旗：以为 sleep(1s) 能"保证"读到正确值；以为 GOMAXPROCS=1 就安全。
- 惊艳点：用"估值时刻 vs 执行时刻"一句话解释所有 for+goroutine 坑，而非逐例记。

## 主问答
**Q（面试官原话）：** 为什么 for 里 go 打印变量，有时 sleep 一下又对了？
**A：**
1. **结论**：`go` 语句在声明处就对实参求值，但函数体在调度到时才跑；for 循环里主协程还在继续改循环变量，goroutine 执行时读到的已是新值。
2. **机制**：`go f(v)` 中 `v` 在 go 语句那一行就已定格（值或地址），但 `f` 的体要等调度；sleep(1s) 只是给主协程足够时间把循环跑完、goroutine 得以调度，是"调度巧合"不是保证 `[源码]`。
3. **边界**：GOMAXPROCS=1 同样非保证——单核下主协程不主动让出时子 goroutine 仍可能迟迟不调度；真正的解法是传值/重赋值制造独立存储，而非依赖时序 `[经验]`。

## 关键代码
```go
// 示意，未验证：声明即估值，执行才调度
for i := 0; i < 3; i++ {
    v := i                 // 声明处 v 已定格为本轮值
    go func() { println(v) }() // v 是值拷贝，执行时读到定格值
}
// 若不重赋值直接 go func(){println(i)}()：i 是共享变量，执行时读到终值
```
