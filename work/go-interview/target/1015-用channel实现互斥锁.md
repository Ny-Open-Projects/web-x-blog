# 1015 用 channel 实现互斥锁：容量必须是 1

> 分类：并发模型 | 难度：L3 | 题型：编码题 | 频率：中高 | 关键词：**channel 锁、容量 1、空结构体、加锁即写入、解锁即读出**

> 原文锚点：第 1~17 段「我们定义了一个 channel，它的缓冲大小为一，这里缓冲容量大小必须是一…写入的动作是加锁，读取的动作是解锁」

## 一句话总述
用**容量为 1 的缓冲 channel** 当锁：往里写一个空结构体等于加锁，从中读出等于解锁；容量被占时其他写入方阻塞，互斥就此成立。一句话背法：**「channel 锁 = 容量 1 的二值信号量，写入即加锁、读出即解锁」**。

## 面试官视角
- **P6**：知道"channel 能当锁"，写出容量 1 + 写入加锁/读出解锁。
- **P7**：要说出**容量必须是 1 的原因**——容量大于 1 时多个 goroutine 都能写入，互斥失效；加分点：用 `struct{}{}` 而非 bool，因为**空结构体不占内存**，传的是信号不是数据。
- 红旗：忘记 `defer Unlock` 导致临界区 panic 后永久阻塞。

## 主问答
**Q（面试官原话）：** 怎么用 channel 写一个互斥锁？为什么缓冲要设成 1？

**先铺垫（由浅入深第 1 层）**：互斥的本质是「同一时刻只允许一个 goroutine 进临界区」。channel 的缓冲容量天然能充当「准入计数」——容量为 1 时就像一个占位的令牌。

1. **定义容量 1 的 channel（第 2 层）**：声明缓冲容量为 1 的通道，元素类型用 `struct{}{}`，避免承载无意义的数据（零内存开销）。
2. **写入即加锁（第 3 层）**：访问共享变量前先向 channel 写入一个元素；此时通道容量被占，其他 goroutine 再写入就阻塞在写这一行。
3. **读出即解锁（第 4 层）**：操作完成后从 channel 读出该元素，容量释放，被阻塞的下一个写入方才被唤醒并成功写入。
4. **容量为什么是 1（第 5 层·最常考）**：容量为 1 时同时只有一方能写入；若容量大于 1，多个 goroutine 都能写进去，**互斥直接失效**。
5. **工程细节（第 6 层）**：解锁必须 `defer`，否则临界区 panic 会让「读出」永不执行，造成**永久阻塞**；且这是教学演示，生产仍推荐 `sync.Mutex`（有 `TryLock`、经充分优化）。

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
)

// ChanMutex：用容量 1 的 channel 当互斥锁
type ChanMutex struct{ ch chan struct{} }

func NewChanMutex() *ChanMutex { return &ChanMutex{ch: make(chan struct{}, 1)} }
func (m *ChanMutex) Lock()     { m.ch <- struct{}{} } // 容量被占则阻塞
func (m *ChanMutex) Unlock()   { <-m.ch }              // 释放后唤醒下一个写入方

func main() {
	var mu ChanMutex = *NewChanMutex()
	var counter int
	var wg sync.WaitGroup

	// 1000 个 goroutine 各自自增，靠 channel 锁保护
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			mu.Lock()
			defer mu.Unlock() // 必须 defer，否则 panic 会永久阻塞
			counter++
		}()
	}
	wg.Wait()
	fmt.Println("counter =", counter) // 1000（互斥生效）
}
```

## 总结与追问预判
**背这三句就够**：① **channel 锁 = 容量 1 的二值信号量**；② **写入即加锁、读出即解锁**；③ **容量必须是 1，否则互斥失效**。
**预判追问**：
- 「它和标准库 Mutex 谁快？」→ `sync.Mutex` 更快更优，channel 锁仅用于理解原理（见 1015 互斥锁 vs channel 锁）。
- 「能不能当计数信号量？」→ 能，把容量设成 N 即可限制 N 个并发（见 1015 计数信号量）。
- 「忘了 Unlock 呢？」→ 后续写入永久阻塞（死锁），故必须 `defer`。

## ⚠️ 原文纠错
1. 事实核校：原文"写入是加锁、读出是解锁"准确；补充——**容量必须为 1**，这是互斥成立的前提，原文虽提到但容易被当成可选细节。
2. 补充：原文示例未处理异常路径，工程上应把解锁放进 `defer`，否则临界区 panic 会造成**永久阻塞**。
3. 崩坏词归一：源码将 channel、goroutine、互斥锁、等待组等术语音译为多组崩坏词，本卡统一为规范术语。
