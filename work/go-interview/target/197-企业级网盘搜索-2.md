# 197 企业级网盘搜索：文件名/内容索引分离与大文件隔离

> 分类：架构/搜索 | 难度：L3 | 题型：设计题 | 频率：中 | 关键词：**索引分离**/**segment merge**/**大文件隔离**/**独立队列**/**截断超大文件**
> 原文锚点：第 15~35 段「文件名/内容分离三因(性能/成本副本/重建代价+ES segment merge压力) + 大文件走独立MQ/解析服务/索引服务 + 过滤截断超大文件」

## 一句话总述
文件名与内容索引**必须分离存储**，三原因：① 文件名搜索频率远高于内容、需保性能；② 内容体量大、副本数与成本不同；③ 索引结构变更需全量重建，内容耦合会放大重建成本（ES 底层 segment 更新整份重写+标记删除、大文本 merge 压力巨大甚至需低峰手动触发）。大文件解析耗时长，须走**独立 MQ/解析服务/索引服务**隔离，避免拖垮小文件；超大型文件直接过滤/截断以保稳定。

## 面试官视角
- 考察意图：能否从性能/成本/运维三角度论证「为何分索引」，以及大文件如何隔离。
- 分档：P5 知内容搜索慢；P6 能列分离三因；P7 知 ES segment merge 代价、大文件隔离与截断策略。
- 红旗答案：把文件名与内容放同一索引（性能被内容拖垮）；忽略大文件对小文件的影响。
- 惊艳点：点出「ES 更新是整份重写+标记删除、merge 压力大、大文本甚至需低峰手动触发」，以及「大文件独立队列/服务做背压隔离」 [经验]。

## 主问答
**Q（面试官原话）：** 为什么文件名和内容索引要分开？大文件怎么处理？
**A：**
1. **分离三因**：① 文件名搜索频率高、需保性能；② 内容体量大、副本数与成本不同；③ 结构变更需全量重建，内容耦合放大重建成本 [经验]。
2. **ES 底层代价**：更新是整份重写+标记删除、merge 时清理；大文本 merge 压力巨大、常需低峰手动触发——耦合会拖累文件名索引 [经验]。
3. **大文件隔离**：解析耗时随大小变，大文件走**独立 MQ/解析服务/索引服务**，避免影响小文件；超大型直接过滤或截断保稳定 [经验]。

// 大文件隔离：按大小路由到不同 MQ/解析服务，做背压隔离
func routeParseTask(f FileMeta) {
    if f.Size > bigFileThreshold { // 大文件走独立队列，避免拖垮小文件
        bigFileMQ.Publish(ParseTask{URL: f.ObjAddr})
    } else {
        smallFileMQ.Publish(ParseTask{URL: f.ObjAddr})
    }
}
// 超大型文件：截断或放弃索引，保护 ES 存储与查询性能
func indexableContent(text string) string {
    if len(text) > maxIndexBytes {
        return text[:maxIndexBytes] // 截断后再索引
    }
    return text
}

## 总结与追问预判
「按访问频率与成本拆分索引」是搜索系统的通用设计原则。大文件隔离本质是背压与资源配额，防长尾拖垮整体 SLA。
