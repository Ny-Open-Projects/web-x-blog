# 1418 业务层幂等消费实现（应用侧去重）

> 分类：消息中间件 / Kafka | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**幂等消费** / **唯一索引** / **去重表** / **Redis 去重缓存** / **ES 文档ID**
> 原文锚点：第 29~55 段「业务层幂等：幂等/事务生产者、手动提交、业务主键唯一索引、去重表/全局ID、Redis 去重缓存」

## 一句话总述
Kafka 自身机制（幂等/事务生产者、手动提交）只能减少重复，**彻底去重要靠消费端业务逻辑幂等**：用**数据库主键/唯一索引**、**ES 文档ID 用业务 ID**、**去重表/全局唯一 ID**，或 **Redis 去重缓存**——同一消息多次消费结果一致。

## 面试官视角
- 意图：是否掌握"应用侧幂等"这一最根本的重复消费解法。
- 分档：P5 知 DB 唯一索引；P6 能讲 ES 文档ID/去重表；P7 能对比各方案代价与分布式原子难点。
- 红旗：以为开了幂等生产者就万事大吉（仅去重 producer 端，consumer 端仍可能重复）。
- 惊艳点：点出"幂等生产者只保证 producer 不重发，consumer 因 offset 问题仍可能重投——端到端去重必须在消费逻辑"。

## 主问答
**Q（面试官原话）：** 除了 Kafka 自带幂等，业务上怎么保证不重复处理？
**A：**
1. **Kafka 自身（减少非根治）**：幂等生产者（0.11+，每条消息唯一标识，已收丢弃）+ 事务生产者（0.14+）；手动提交 offset（边界见 1417）。
2. **业务主键 / 唯一索引**：消费写入时用业务主键（如订单 ID）作 DB 主键或唯一索引；插入成功=首次，冲突=已处理→丢弃。MySQL、MongoDB 均适用。
3. **ES 文档 ID 用业务 ID**：消费写 ES 时以订单 ID 作文档 ID，新增/删除直接按 ID upsert，最小代价实现幂等。
4. **去重表 / 全局唯一 ID**：建消费状态表，消息带全局唯一 ID；消费前查状态，未消费则处理并写状态，已消费则跳过——需保证"查状态→消费→提交状态"原子。
5. **Redis 去重缓存**：维护已处理消息 ID 集合，处理前查缓存，存在则跳过；本质与去重表同，只是存储位置不同，代价是 Redis 可用性。
