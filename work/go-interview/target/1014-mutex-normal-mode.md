> 原文锚点：第 28~31 段「正常模式：等待者按FIFO排队…唤醒的goroutine不直接持锁而与新请求竞争…新请求(在CPU上)更易抢到…刚唤醒的常失败加入队列前面…可连续多次获取锁(吞吐好)」

## 一句话总述
sync.Mutex **正常模式（normal mode）**下，等待者按 **FIFO** 排队，但被唤醒的等待者**不会直接拿到锁**，而是和刚到来的新请求者**竞争**；由于新请求者正跑在 CPU 上、有缓存热度，**更容易抢到锁**，导致刚唤醒者常失败并插到队列前端。这种"新来者优先"换来**更高吞吐**（同一 goroutine 可连续多次获取锁），但可能让队尾等待者饥饿。

## 面试官视角
互斥锁两种模式是并发高频题。面试官想看你能否说清正常模式"为何吞吐高却可能不公平"——即唤醒者与新请求竞争、新请求占优这一反直觉点，而非只背"FIFO"。

## 主问答
**Q（面试官原话）：** Mutex 的正常模式是怎么回事？

**A：**

1. **FIFO 等待队列**：拿不到锁的 goroutine 按到达顺序排进等待队列，保证"先来先等"的秩序。
2. **唤醒者与新请求竞争**：锁释放时，被唤醒的等待者**不自动持锁**，要和此时新来的 `Lock()` 请求者抢；新请求者正在 CPU 上跑、局部性更好，所以**抢赢概率更高**。
3. **唤醒失败插队头**：抢输的唤醒者退回队列**前端**（不是队尾），避免反复唤醒-失败的抖动。
4. **连续多次获取 = 高吞吐**：因为新请求常赢，同一个 goroutine 可连续多次拿到锁，减少上下文切换，吞吐最好——代价是队尾老等待者可能长时间拿不到（饥饿隐患）。

## 关键代码
```go
// 正常模式示意：释放锁后，被唤醒等待者与新 Lock 请求者竞争
func illustrateNormalMode() {
    var mu sync.Mutex
    // 多个 goroutine 竞争：新到达且在 CPU 上的请求者常抢赢（缓存热度）
    // 被 runtime_Semrelease 唤醒的等待者需重新 CAS，失败则回插队头
    mu.Lock()
    defer mu.Unlock()
    // 同一 goroutine 若持续请求可连续获取 → 吞吐高
}
```

- 口诀：**正常模式=FIFO排队+唤醒者竞争+新请求占优+高吞吐(藏饥饿)**。
