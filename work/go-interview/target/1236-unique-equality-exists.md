# 1236 唯一索引等值查询（记录存在）→ 记录锁

> 分类：MySQL 锁 | 难度：L4 | 题型：规则题 | 频率：高 | 关键词：**唯一索引**/**等值查询**/**记录存在**/**记录锁退化**/**REC_NOT_GAP**
> 原文锚点：第 14~26 段「唯一索引等值查询且记录存在的加锁」

## 一句话总述
唯一索引（含主键）等值查询、且记录存在时，InnoDB 加的是**记录锁**（临键锁退化），锁模式 `X, REC_NOT_GAP`——只锁这一行、不含间隙。退化原因是主键唯一性使其他事务无法插入/删除该 id，故不可能产生幻读。

## 面试官视角
- 考察意图：是否理解「为什么唯一索引等值命中能降级为纯记录锁」，这是 InnoDB 锁优化常考点。
- 分档：P5 知唯一索引等值加记录锁；P6 知不含间隙（REC_NOT_GAP）；P7 知退化原因（唯一性杜绝幻读）。
- 红旗答案：以为唯一索引等值也加间隙锁；或说不清为什么能退化。
- 惊艳点：点出 `locks rec but not gap` 这个具体锁模式，以及「加锁单位是记录锁，只是经优化退化」。

## 主问答
**Q（面试官原话）：** 主键等值查询命中一条记录，加的是什么锁？
**A：**
1. **加锁对象**：扫描的是哪个索引（如主键索引），就对该索引加锁；锁类型是记录上的**排他锁（X）**。
2. **锁模式**：`X, REC_NOT_GAP`（即 `locks rec but not gap`）——**纯记录锁，不含间隙**。
3. **退化来源**：底层单位本是临键锁（next-key lock），但经 MySQL 优化退化成记录锁。
4. **退化原因**：主键具有唯一性——其他事务插入该 id 会因主键冲突失败，删除该 id 会被记录锁阻塞，故不可能产生幻读，无需间隙锁。
5. **效果**：只锁住这一行，其他事务无法删除/修改该记录，但可自由插入/修改其他 id。

## 总结与追问预判
唯一索引等值命中的核心是「记录锁退化、无间隙」。与之对照的是「记录不存在」会退化为间隙锁——那是下一个常问分支。

## ⚠️ 原文纠错
1. 事实核校： [经验] 唯一索引等值命中加记录锁(REC_NOT_GAP)、临键锁退化、退化因主键唯一杜绝幻读——均正确；源码口播「加锁单位依然是零件锁只不过退化成记录锁」表述绕，已理顺为「底层单位是临键锁、优化退化为记录锁」。
2. 崩坏词归一：源码将 临键锁 音译为 零件锁、记录锁 正确保留、间隙锁 正确保留、意向排他锁 音译为 意向排发组、写锁 音译为 协索/解索、终端 音译为 终态；MySQL 音译为崩坏词（本卡统一为 MySQL）。
