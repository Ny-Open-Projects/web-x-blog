# 418 Go 整型溢出与边界防御深挖

## 思路与架构
把整型问题归纳成**「三态两域」**，回答任何边界题都能对号入座：

- **三态**：
  1. **常量** —— 任意精度、编译期求值，溢出直接编译失败，是最安全的形态。
  2. **变量运算** —— 定宽、运行期求值，溢出静默回绕（无符号模 2^n、有符号符号反转），是最危险的形态。
  3. **类型转换** —— 定宽之间按位重解释，高位截断或符号位重解释，同样静默。
- **两域**：
  - **语言层规则**：无符号回绕是规范定义的确定行为，不是未定义行为；有符号溢出同样不 panic，只是结果反转。
  - **业务层规则**：语言允许 ≠ 业务可接受。金额、积分、库存这类场景必须**先判后算**。

所有防御手段都围绕一个原则：**把「先算后判」改写成「先判后算」，并把加法比较改写成减法比较**，因为比较本身不能溢出。

## 方案取舍
- **事前校验 vs 事后检测**：事后检测（`x+y < x`）依赖已发生的溢出，且编译器可能优化掉这类判断；事前校验把加法改写成减法，语义清晰且不溢出。**唯一正确选项是事前校验。**
- **自己写判据 vs 用标准库**：标准库长期缺少通用安全加法；可用 `math/bits` 的 `Add64`/`Mul64` 拿到进位标志，比手写判据更不易错，可读性也更好。
- **int vs int64 存金额**：`int` 位宽随架构变化（32 位机器上仅 ±21 亿），跨端行为不一致；金额建议显式用 `int64` 表示最小单位（分），或直接上定点数/大数库。
- **浮点表示金额 vs 整数表示**：浮点有精度损失，绝不可用于金额；用整数分 + 整数运算是金融场景的通行做法。
- **溢出即报错 vs 饱和截断**：报错（fail fast）适合交易类，能立刻暴露问题；饱和到边界值适合展示类指标，避免一个异常值污染整张报表。二者按场景选，不要混用。
- **panic vs 返回 error**：库函数应返回 error 交由调用方决策；仅在「不可能发生」的内部不变量处使用 panic。

## 答题技巧
- **开口先分三态**：「常量编译期报错、变量运行期静默回绕、转换按位截断」——这一句就能把答案立住。
- **把关键数字背下来**：int8 → -128~127；int16 → -32768~32767；int32 → ±2147483647/-2147483648；int64 → ±9223372036854775807。补码决定了负数总比正数多一个。
- **被问「怎么防」立刻写减法判据**：`y > 0 && x > math.MaxInt64-y`。写成 `x+y > max` 是这题最常见的失分点，务必回避。
- **主动补一个反常识点**：`math.MinInt64` 取绝对值（或取负）**结果仍是自身**，因为最小值没有对应的正数——这是边界测试的经典用例。
- **收尾落到业务**：讲一句「金融/积分场景先判后算，否则扣减变大额增加」，把语言知识转成工程价值，这类收尾最讨喜。

## 细节与核心 API

无符号类型溢出是取模回绕（定义良好）；有符号溢出是未定义行为（release 下不 panic 但结果错）：

```go
var u uint8 = 255
u++                     // 0（回绕，定义良好）
var i int8 = 127
// i++                // 有符号溢出 UB，避免依赖
// 安全加法：先判上界
func addInt64(a, b int64) (int64, bool) {
    if b > 0 && a > math.MaxInt64-b { return 0, false }
    if b < 0 && a < math.MinInt64-b { return 0, false }
    return a + b, true
}
```
