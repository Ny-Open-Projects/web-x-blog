## 思路与架构
Go 没有异常，错误是**显式返回值**——这决定了「优雅」的本质是**在调用链上对错误做单一、明确的决断**：要么附加上下文继续上抛，要么就地消化返回 nil，绝不在中间层既记日志又返回（处理两次）或只记不返（假成功）。

```text
错误在调用链上的生命周期
  产生 err ──► 中间层 A：不处理 → wrap(加上下文) 继续 return
            ──► 中间层 B：不处理 → wrap 继续 return
            ──► 某层 C：能消化(降级/默认) → 返回 nil（错误消失）
            ──► 最外层：记日志一次 / 转 HTTP 500 / os.Exit
  判定标准：是否真解决了错误？解决了→nil；没解决→继续 wrap+return
```

## 方案取舍
| 做法 | 适用 | 代价 | 反模式对照 |
| --- | --- | --- | --- |
| `errors.New`/哨兵 | 简单固定错误 | 不可附上下文 | 用文本断言（`Contains`） |
| `fmt.Errorf("%w")` | Go1.13+ 包装 | 标准库、Is 穿透 | pkg/errors（历史，仍可用） |
| 自定义类型+code | 需分类/国际化 | 需定义类型 | 靠字符串分类 |
| 降级返回 nil | 真消化错误 | 需确认已解决 | 只 log 不 return（假成功） |

**取舍结论**：包装用标准库 `fmt.Errorf("%w")`（Go 1.13+），分类用自定义类型+`errors.Is/As`；**绝不**用字符串断言、**绝不**只记不返、**绝不**每层记日志。

**纪律边界**（必须记牢）：
- wrap ≠ 吞错：wrap 是「附加信息上抛」，return nil 才是「消化」。
- 确定处理（降级/默认/重试成功）→ 返回 nil；仅记日志未解决 → 必须继续 return。
- 日志只在最外层（main/handler/goroutine 顶层）一次。

## 答题技巧
1. **先讲模型再讲纪律**：开口「Go error 是接口、显式返回，优雅=调用链上单一决断」，再列三条纪律——显体系。
2. **三个反模式点名**：① 记日志又 return（处理两次）；② 只 log 不 return（假成功，最危险）；③ 先判正常增缩进（应早返回）。
3. **版本演进加分**：明确「Go 1.13+ 用 `fmt.Errorf("%w")` + `errors.Is/As`，pkg/errors 是历史惯用法」——显你跟版本。
4. **反直觉点收尾**：「降级成功返回 nil」——多数人以为错误必须一路上抛，讲清「被消化即消失」直接封神。
5. **避坑**：不说「Go 没有错误处理」（它有，只是不用异常）；不把 `==` 当万能判断（wrap 后失效）；不混淆 `errors.New` 与 `fmt.Errorf("%w")` 的穿透性。
