# 1817 su、su -、sudo -i、sudo -s：四个命令只差两条轴——密码是谁的、环境加载谁的

> 分类：操作系统 / Linux | 难度：L2 | 题型：对比题 | 频率：高 | 关键词：**su**/**su -**/**sudo -i**/**sudo -s**/**登录环境**/**sudoers**/**环境变量**/**审计**
> 原文锚点：第 3~31 段「su 命令用于切换到另一个用户，如果不指定用户名，它默认会切到 root 用户下…su 切换用户的时候，它会保留当前用户的环境变量，也就是只切换用户的身份，而不会去切换用户的登录环境…su 中横线除了切换用户身份之外，它还会加载目标用户的登录环境…sudo -i 和 sudo -s 都使用 root 权限，它们之间的区别也在于是否加载 root 用户的登录环境」
> [边界] 本文只讲**四个提权/切换命令的语义对比**：文件描述符与重定向见 `1813-fd-stdin-out-err`，进程状态与后台执行见 `187-process-states`，inode 与权限位见 `1814-inode-basics`，均不重述。

## 一句话总述
这四个命令的差异**只落在两条轴上**：**① 要输谁的密码**——`su` 系列要**目标用户**的密码，`sudo` 系列要**当前用户自己**的密码（且该用户必须在 `/etc/sudoers` 或 admin/sudo 组里）；**② 加载谁的登录环境**——**带 `-` 的**（`su -`、`sudo -i`）**加载目标用户的登录环境**（模拟完整登录），**不带 `-` 的**（`su`、`sudo -s`）**保留当前用户的环境变量**。一句话背法：**"横杠 = 换环境"**。

## 面试官视角
- 考察意图：这是**运维基本功的听诊器**。面试官不是要你背命令，而是看你能不能**抓住"密码归属"和"环境加载"这两条区分轴**——抓不住的人，现场排障时连"为什么我的 `JAVA_HOME` 没了"都解释不清。
- 分档：P5 只会用 `su`；P6 知道 `su -` 会加载环境；P7 能说清**四个命令两两成组**（`su`/`su -` 一组、`sudo -i`/`sudo -s` 一组，组内差异都是"加不加横杠"）、**`sudo` 用的是当前用户密码**、**`/etc/sudoers` 与用户组的授权关系**，以及 **`sudo -i` 可审计**这个加分点。
- 红旗答案：「`sudo` 要输入 root 密码」——**错**。`sudo` 验证的是**当前用户自己的密码**，这正是它比 `su` 更安全的原因（**不需要散播 root 密码**）。
- 惊艳点：主动补「`sudo -i` 会把 `sudo` 执行过的命令**记录下来以便审计**，这是生产环境推荐它的核心理由」[经验]。

## 主问答
**Q（面试官原话）：** `su`、`su -`、`sudo -i`、`sudo -s` 有什么区别？

**A：**
1. **`su`（不带横杠）**：用于**切换到另一个用户**，不指定用户名则**默认切到 root**。切换时需要输入**目标用户的密码**。它**保留当前用户的环境变量**——**只切换用户身份，不切换登录环境** [经验]。
2. **`su -`（带横杠）**：功能与 `su` 类似，差别在于它**除了切换身份，还会加载目标用户的登录环境**，包括**环境变量、用户配置文件**等；**本质上它模拟了一次完整的登录过程**，就像直接登录到目标用户一样 [经验]。
3. **什么时候必须带横杠**：当你要**以 root 身份运行命令**时，建议用 `su -`，**以确保环境设置是正确的** [经验]。
4. **`sudo -i`**：以 **root 身份启动一个新的交互式 shell**。这里要输入的是**当前登录用户的密码**，而**不是 root 用户的密码**；前提是**当前用户在 `/etc/sudoers` 中有配置**，或者**属于 admin / sudo 用户组** [经验]。
5. **`sudo -i` 与 `su -` 类似**：它**会加载 root 用户的登录环境**。它还有一个额外优点——**可以记录使用 `sudo` 执行的所有命令，便于在需要时审计** [经验]。
6. **`sudo -s`**：与 `sudo -i` 类似，但**不加载目标用户（root）的登录环境**；相反，它**保留当前用户的环境变量**。从普通用户切到 root 后，**用的仍然是原来那个用户的环境变量**——**只是在新的 shell 里获得了 root 权限** [经验]。
7. **`sudo -s` 的典型用途**：在**当前非 root 环境**下，执行**一些需要 root 权限的操作** [经验]。
8. **怎么授权**：是否能执行 `sudo`，取决于 `/etc/sudoers` 的配置或用户所属的用户组；用户组信息在 **`/etc/group`** 里，可用 `groups` 查看某用户属于哪些组 [经验]。
9. **一张表收口**：`su` / `su -` 用于**切换到其他用户**（默认 root），差异是**是否加载目标用户登录环境**；`sudo -i` / `sudo -s` 默认获得 **root 权限**，差异同样是**是否加载 root 登录环境**；**两个 sudo 变体都要求当前用户具备 sudo 权限，并用当前用户的密码验证** [经验]。

## 关键代码
```go
// 用 Go 复刻"是否加载登录环境"的判定，演示 su 与 su - 的底层机制差异：
// 登录 shell 会读取目标用户的 profile，非登录 shell 不会。
package main

import (
	"fmt"
	"os"
	"os/exec"
)

func run(login bool, home string) string {
	args := []string{"-c", "echo $MYENV"}
	if login {
		args = []string{"-lc", "echo $MYENV"} // -l = login shell
	}
	cmd := exec.Command("sh", args...)
	cmd.Env = []string{"HOME=" + home, "PATH=" + os.Getenv("PATH")}
	out, err := cmd.CombinedOutput()
	if err != nil {
		return "err: " + err.Error()
	}
	return string(out)
}

func main() {
	const home = "/tmp/fakehome" // 该 HOME 的 .profile 里写了 export MYENV=from-profile
	fmt.Printf("非登录 shell (对应 su 保留环境): MYENV=%s", run(false, home))
	fmt.Printf("登录 shell   (对应 su - 加载环境): MYENV=%s", run(true, home))
}
```

> 验证（`[实测]` 输出，macOS / go1.26.5，先在 `/tmp/fakehome/.profile` 写入 `export MYENV=from-profile`）：`HOME=/tmp/fakehome sh -c 'echo $MYENV'` 输出 **`MYENV=[]`**（空，未加载）；`HOME=/tmp/fakehome sh -lc 'echo $MYENV'` 输出 **`MYENV=[from-profile]`**。这正是 `su` 与 `su -` 的底层机制——**加横杠 = 启动登录 shell = 读取目标用户的 profile**。另实测本机：`/etc/sudoers` 为 `-r--r----- 1 root wheel 1563`（0440，root 只读，应通过 `visudo` 修改）；`id -Gn` 显示当前用户所属组含 **`admin`**（macOS 上对应 sudo 授权组，Linux 上通常名为 `sudo` 或 `wheel`）；`sudo --version` 输出 **`Sudo version 1.9.13p2`**。

## 总结与追问预判
- 一句话收尾：**"横杠换环境，sudo 用自己的密码"**——这两句能推出全部四个命令。
- 大概率被追的三问：① 为什么 `sudo` 比 `su` 安全（**不用散播 root 密码** + **可审计**）；② 为什么切过去后命令找不到（**没加横杠，`PATH` 还是原用户的**）；③ 怎么给一个用户 sudo 权限（加进 `sudo`/`admin` 组，或在 `/etc/sudoers` 里配置，**必须用 `visudo`**）。
- 反向加分：主动指出 **`sudo -i` 可记录命令便于审计**，这是生产环境优先它的硬理由；再补一句 **Ubuntu 默认锁 root 密码，`su` 根本用不了**。

## ⚠️ 原文纠错
1. 源码称 `su` 「保留当前用户的环境变量」——准确说是**不加载目标用户的 profile**，原环境随 shell 继承 [实测]。
2. 源码未提**底层机制**：带横杠即**启动登录 shell**并读取目标用户 profile，实测可复现 [实测]。
3. 源码未提 **Ubuntu/Debian 默认锁 root 密码**，那些系统上**只能用 `sudo`** [经验]。
4. 源码把授权组只说成「admin 或 sudo 组」——**组名随发行版而异**，RHEL 系常用 `wheel` [实测]。
5. 源码未强调 `sudo` **验证的是当前用户自己的密码**，这正是它不必散播 root 密码的原因 [经验]。
6. 源码未提醒 `/etc/sudoers` 为 **0440 只读**，直接编辑会破坏权限，须用 **`visudo`** [实测]。
