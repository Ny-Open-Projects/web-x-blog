> 原文锚点：第 1~12 段「计数器存储 k=前缀+微博ID v=长整型…缓存+数据库结合…更新先DB再缓存(moaa/memcached)…高并发DB成瓶颈(TPS 3000~6000)…单请求多计数缓存失效穿透DB…仅适用中小规模」

## 一句话总述
海量计数器（粉丝数/评论数/点赞数）最朴素的做法是**缓存（Redis/memcached）+ 数据库**：更新时先写 DB 再写缓存。但在日活过亿、百万 QPS 的场景下，DB 的 TPS（约 3000~6000）成为写入瓶颈，且单请求聚合多计数、缓存失效即穿透到 DB，该方案**仅适合中小规模**。

## 面试官视角
计数器是典型高并发写场景。面试官想看你能否指出"缓存+DB"的天花板，并自然引出后续的 Redis 全量 / 磁盘型存储方案。

## 主问答
**Q（面试官原话）：** 海量微博计数器，用缓存加数据库怎么存？有什么问题？

**A：**

1. **存储模型**：计数器的 key 通常是「业务前缀 + 对象 ID」（如 `count:weibo:{id}`），value 为长整型；读时聚合多个对象的计数，写时递增。
2. **更新顺序**：先更新数据库计数 +1，再更新缓存（Redis/memcached）。读优先走缓存，未命中回源 DB。
3. **瓶颈一·DB TPS**：数据库事务 TPS 约 3000~6000，远不能满足百万级 QPS；即便合并更新，总量过大且请求分散在多业务端，DB 仍无法承受写入压力。
4. **瓶颈二·缓存穿透**：单请求往往一次性拉多个计数（用户信息页含关注/粉丝/微博数；微博列表含转发/评论/点赞/阅读数），一旦缓存失效，穿透到 DB 的读也成瓶颈。结论：该架构**仅适用于中小规模计数器**。

## 关键代码

```go
// 缓存 + 数据库 计数器更新（先 DB 后缓存）
func IncrCounter(ctx context.Context, objID string, delta int64) error {
    // 1) 先更新数据库
    if _, err := db.ExecContext(ctx,
        "UPDATE counters SET cnt = cnt + ? WHERE obj_id = ?", delta, objID); err != nil {
        return err
    }
    // 2) 再更新缓存
    return rdb.IncrBy(ctx, "count:"+objID, delta).Err()
}
```

## 总结与追问预判
- 口诀：**先 DB 后缓存；DB TPS 是天花板；聚合多计数放大穿透**。
- 预判追问："那大厂怎么扛百万 QPS？"答：缓存+DB 不够 → Redis 全量（见边界卡）或更彻底的磁盘型存储（Pika/RocksDB）。
