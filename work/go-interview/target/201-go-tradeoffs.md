## 一句话总述
Go 最适合**网络 IO 并发、微服务、CLI、云原生基础设施**；但它**不是万能语言**——GUI/桌面、操作系统/驱动等系统底层、硬实时、纯 CPU 密集无并发收益的场景，Go 优势不大甚至不如 C/Rust；且早期（1.18 前）泛型缺失导致部分数据结构生态偏弱（已改善）。选型要按「并发密度 + 部署形态 + 生态成熟度」判断。

## 面试官视角
这题考「选型的诚实度与边界判断」——很多人只会鼓吹。考点：① 能否说出 Go 的适用边界（不止优势）；② 能否区分「Go 强在并发编排，不擅长系统底层/硬实时」；③ 是否知道泛型演进。能讲「什么时候不选 Go」，直接显 senior 工程成熟度（源本身只讲优势，补边界是加分）。

## 主问答
**Q（面试官原话）：** 那还有理由不选择 Go 吗？什么场景不该用 Go？

**A：**
1. **GUI / 桌面应用**：Go 缺乏成熟原生 GUI 生态（相比 C#/Java/Swift/Electron），写桌面客户端体验差、库少——这类场景不该选 Go。
2. **系统底层 / 操作系统 / 驱动**：Go 带 GC、运行时，不适合写内核、驱动、对内存布局/时序极度敏感的系统程序——这些仍是 C/Rust 的领地（Go 初衷是「替代 C 的应用层」，不是内核层）。
3. **硬实时（RTOS）**：GC 的停顿（即便亚毫秒）无法满足硬实时 deadline；实时控制/嵌入式固件用 C/Rust/专用 RTOS。
4. **纯 CPU 密集且无并发收益**：Go 的优势在「并发编排 IO」，单任务纯计算不比同优化 C/Rust 快，反而因 GC 略吃亏——此时应靠多进程/外部算力，或换语言。
5. **历史短板已改善**：1.18 前无泛型，部分容器/算法库靠 `interface{}`+反射，类型安全与性能受损；1.18+ 泛型落地，生态迅速补齐。这是「曾经不选 Go」的理由，现已弱化。

## 版本与兼容性
- 泛型：Go 1.18（2022）引入，此前是「不选 Go」的常见理由；现 `map`/切片/容器泛型化，短板基本补齐。
- GC 停顿：1.5 并发标记清除、1.8 亚毫秒级典型停顿；非硬实时但仍优于早期。
- 与「Go 成功因素」（`201-go-success-factors.md`）互补：优势讲「为什么选」，本卡讲「为什么有时不选」——完整选型观。

## 总结与追问预判
收口：**Go 强在并发/云原生/CLI，弱在 GUI/系统底层/硬实时/纯 CPU 密集；泛型短板（1.18 前）已补**。预判追问：① 用在哪（见 `201-go-adoption-landscape.md`）；② 为何成功（见 `201-go-success-factors.md`）。回答时把「源只讲优势，工程上需补边界：GUI/底层/硬实时不选 Go」点出，最显选型诚实度——面试官最防「只背优点」的候选。

```go
// Go 之长：IO 并发编排（每请求一 goroutine，万级无压）
func handle(conns []net.Conn) {
    for _, c := range conns {
        go func(c net.Conn) { // IO 等待时不占系统线程，并发密度极高
            io.Copy(c, c)
        }(c)
    }
}

// Go 之弱：纯 CPU 密集无并发收益时，优势不显（GC + 抽象略慢于手调 C/Rust）
// 此时应靠多进程分摊，或把热点用 C/Rust 写、Go 调（cgo/独立服务）
func cpuBound(n int) int { // 单任务重计算：Go 不比同优化 C 快
    s := 0
    for i := 0; i < n; i++ {
        s += i * i
    }
    return s
}
```
