# 1850 拔网线后 TCP 连接还在吗

> 分类：网络 / TCP 进阶 | 难度：L1~L2 | 题型：场景推演题 | 频率：中 | 关键词：**半开连接**/**tcp_retries2**/**超时重传**/**RST**/**连接本质**

> 原文锚点：第 1~14 段「TCP 连接是内存中的结构体…拔网线不变更状态…重传期内插回则连接保住…超阈值断开…插回后发数据被 RST」

## 一句话总述
**TCP 连接 = 内核内存里的一个结构体**（四元组 + 状态机），拔网线不会改它——连接在两端依然「存在」。后续分两支：**重传窗口内插回网线** → 数据报文送达、ACK 归位，连接毫发无损；**超时重传耗尽**（`tcp_retries2`，默认 15 次）→ 内核判定连接异常断开；之后客户端再发数据，服务端无此连接 → 回 **RST**，彻底终结。

## 面试官视角
- 意图：又一道「理解 TCP 本质」的变式题——考「连接是逻辑态不是物理线」的认知与内核参数意识。
- 分档：P5 答拔了还在/断了（二选一）；P6 能分「插回时机」两种情况并提到超时重传；P7 能报 tcp_retries2 等内核参数与 keepalive 对比、半开连接的清理链。
- 红旗答案：说「拔网线立刻断开」（物理断≠逻辑断）；说「连接永远存在」（重传耗尽会清）。
- 惊艳点：与 1846 呼应——「拔网线」和「宕机重启」是半开连接的两种成因，收尾都靠 RST 或 keepalive；内核参数报得出 `tcp_retries2=15`（约 15~16 分钟） [经验]。

## 主问答
**Q（面试官原话）：** 拔掉网线后原本的 TCP 连接还会存在吗？

**A：** 先破题：TCP 是协议，连接在代码层是**内存中的结构体**（状态、序列号、四元组）——拔网线这个物理动作**不会变更**它 [经验]：

1. **重传窗口内插回网线**：服务端发的数据报文得不到 ACK，触发**超时重传**（次数由内核参数 `net.ipv4.tcp_retries2` 控制，默认 15）；网线插回后客户端处于 ESTABLISHED（状态没变过），正常收报文回 ACK——**连接保住，数据继续传，无感恢复**。
2. **一直不插回**：重传次数耗尽 → 内核判定连接异常 → 通过 socket 通知应用「连接有问题」→ 服务端断开本地连接。
3. **之后的复活尝试**：客户端再插回网线并发数据——服务端已没有同四元组的连接 → 内核回 **RST** → 客户端收到后关闭自己的连接。两端至此才真正断开。
4. **本质一句**：物理断开 ≠ 逻辑断开；TCP 连接的生命周期由状态机 + 重传/保活定时器决定，不由网线决定。

## 关键代码
```python
# 场景推演器：插回网线的时机决定连接命运
def fate(replug_in_window: bool):
    if replug_in_window:
        return ["服务端数据报文重传中…", "网线插回：客户端仍 ESTABLISHED",
                "报文送达 → ACK 回归 → 连接保住，无感恢复"]
    return ["重传次数耗尽（tcp_retries2=15）",
            "内核通知应用连接异常 → 服务端断开本地连接",
            "客户端插回后再发数据 → 服务端无此连接 → 回 RST",
            "客户端收到 RST → 连接终结"]

for case in (True, False):
    print("窗口内插回:" if case else "一直没插回:")
    for s in fate(case):
        print("  ", s)
```

[实测] 输出两分支共 7 步——按「时机决定命运」的链路口述即可覆盖全部得分点。

## 总结与追问预判
核心：**「连接=内存结构体」破题 → 重传窗口二分 → RST/keepalive 收尾**。追问接半开连接族：宕机重启再收 SYN 的 Challenge ACK 分支见 1846（同一底座的不同分支）、RST 生产现场见 1844、2MSL 见 `1847-2msl-timewait`、keepalive 与应用心跳见 1849 与 `1849-keepalive-pitfalls.deep`。

## ⚠️ 原文纠错
1. 术语核校： [经验] 原文将 socket 音转为「搜口」类崩坏串、四元组音转为「端t资源组」、RST 音转为「IST」，本卡统一为规范术语，不列举原词。
2. 事实核校： [经验] 原文称 `tcp_retries2` 默认值为 5——**实际默认 15**（约 924 秒重传窗口）；重传间隔按指数退避，15 次耗尽约 15~16 分钟，时间量级要答对。
3. 补充核校： [经验] 「内核通过 socket 接口告知应用」的具体形态是——后续读写返回错误（ETIMEDOUT/「Connection timed out」），应用层捕获后自行处理；内核不会主动回调应用，这句要答实。
