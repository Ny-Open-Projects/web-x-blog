# 1262 Redis 全量同步完整流程

> 分类：Redis | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**全量同步**/**slaveof**/**BGSAVE**/**RDB**/**清空加载**

> 原文锚点：第 10~18 段「全量同步触发与建连」、第 32~47 段「生成快照与从节点加载」

## 一句话总述
全量同步用于从节点**首次连接**主节点或增量同步失败时：保存主节点信息 → 建 socket 连接 → PING 探活 → 密码校验 → 触发全量 → 主节点 BGSAVE 生成 RDB 发给从节点 → 从节点**先清空旧数据**再加载 RDB；期间新到的写命令先缓存，RDB 传完再补发。

## 面试官视角
考官要的是顺序与两个细节：为什么从节点要**先清空**数据，以及 RDB 生成期间的新写命令去哪了。答出「主节点侧的写命令缓冲区补发」，说明你理解了全量同步不是简单的文件拷贝。

## 主问答
**Q（面试官原话）：** Redis 全量同步是怎么做的？

1. **保存信息**：从节点执行 `slaveof` 保存主节点信息，**不会立即发起复制**，实际连接由从节点的定时任务发起。
2. **建连与探活**：定时任务发现主节点信息后用 socket 连接，成功后发送 PING；得不到响应就重连。
3. **权限校验**：主节点若设置了密码，连接过程需要权限校验，验证失败则同步终止。
4. **生成快照**：首次建连必然全量；主节点执行 BGSAVE 生成 RDB 快照文件并发送给从节点。
5. **清空并加载**：从节点收到 RDB 后**先清空自身数据**再加载；RDB 生成期间的新写命令先缓存到主节点内存缓冲区，快照传完后再补发给从节点，保证一致。

## 追问链
| 档位 | 追问 | 答不出停在哪档 |
|------|------|----------------|
| L1 | slaveof 之后立刻复制吗？ | 误以为立即复制 |
| L2 | 从节点收到 RDB 先做什么？ | 说不清先清空 |
| L3 | 快照期间新写命令怎么办？ | 说不清缓冲区补发 |
| L4 | 全量复制会超时吗？ | 说不清超时参数 |
| L5 | 缓冲区写满会怎样？ | 说不清复制失败重来 |

## 版本与兼容性
| 环节 | 关键点 |
|------|--------|
| 建连 | 定时任务发起，非立即 |
| 探活 | PING，失败重连 |
| 校验 | 主节点密码 |
| 传输 | RDB 快照 + 缓冲区补发 |

## 关键代码
```go
// Go 侧视角：从库加载 RDB 期间要避免把流量切过去，先探测再放行
package main

import (
	"fmt"
	"os/exec"
	"strings"
)

func main() {
	out, _ := exec.Command("redis-cli", "INFO", "persistence").Output()
	for _, l := range strings.Split(string(out), "\n") {
		if strings.Contains(l, "rdb_bgsave_in_progress") {
			fmt.Println(l) // 为 1 表示主库正在生成快照，此刻勿摘流
		}
	}
}
```

## 总结与追问预判
核心：**信息保存 → 建连 → 探活 → 校验 → BGSAVE → 清空加载 → 补发缓冲**。追问常拐向「全量复制期间从节点能否读」「超时怎么办」，备好「由配置决定是否继续服务」与「超时默认 60 秒」。

## ⚠️ 原文纠错
1. 事实核校： [经验] 原文称执行 `slaveof` 后「并不会立即发起复制」——正确，它只保存主节点信息，实际连接由从节点内部定时任务发起，本卡保留这一易错细节。
2. 事实核校： [经验] 原文描述主节点响应时只说「带上自己写入的偏移量」——完整形式为 `+FULLRESYNC <runid> <offset>`，**运行 ID 与偏移量两个字段缺一不可**，从节点据此更新主节点身份。
3. 崩坏词归一：源码将 Redis / slaveof / BGSAVE / RDB 等音译为多组崩坏词，本卡统一为规范术语。
