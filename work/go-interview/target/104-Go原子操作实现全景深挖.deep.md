## 一句话总述
本源把"Go 怎么实现原子操作"拆三层：**根因层**（count++ 拆 load/add/store 三指令、多核竞争、三解法锁/通道/原子）、**本质层**（原子=不可中断的变量级互斥，Go 靠 LOCK 前缀 CPU 指令锁总线、跨架构封装 sync/atomic）、**陷阱层**（struct 不直接原子、不保复合逻辑、高竞争不如锁、单核也需保护、Value 同类型）。本波（10-4）与 105-atomic-* 重叠，只补**根因 worked example + 本质定义 + 实战陷阱**三块，底层指令细节见 105。

## 思路与架构
- **根因层**：数据竞争来自"非原子的读-改-写"，最小例子 count++；解法光谱 锁/通道/原子——与 104-concurrency-race-demo 一致，本波主卡。
- **本质层**：原子=变量级互斥锁、硬件指令保证不可分——动机定义，与 104-atomic-essence 一致；底层 LOCK 前缀/缓存一致性细节见 105（不重复）。
- **陷阱层**：使用边界与踩坑——与 104-atomic-pitfalls 一致；正式选型（原子 vs 锁）见 105（不重复）。
- **边界**：与 105-atomic-implementation（无锁底层原理）/105-atomic-types-scope（类型范围）/105-atomic-vs-lock-when（选型）/105-atomic-vs-mutex-core（原子 vs Mutex 核心）/165-singleton-atomic（原子实现单例）互补，本波只补 additive 三块。

## 方案取舍
- **原子 vs 锁 vs 通道**：单变量计数/状态位 → 原子最轻；复合临界区（多变量+条件）→ Mutex；goroutine 编排/流水线 → channel（别把 channel 当纯锁用）。
- **原子 vs 锁性能**：低中竞争原子胜；极高竞争 CAS 自旋重试的 CPU 开销可能反超一把锁——以 `go test -bench` 实测为准，不拍脑袋。
- **struct 一致性**：要么整体塞 atomic.Value（同类型），要么上锁；不要对 struct 字段逐个原子幻想"整体一致"。

## 答题技巧
1. **开口定调**："原子是变量级互斥、硬件保证不可分，是并发原语里唯一真原子性"。
2. **给根因**：count++ 三指令竞争，三解法对比（锁/通道/原子）。
3. **讲本质**：不可中断 + LOCK 前缀指令锁总线 + sync/atomic 跨架构封装。
4. **列陷阱**：struct 不直接原子、不保复合逻辑、高竞争不如锁、单核也需保护、Value 同类型。
5. **关联延展**：提 105-atomic-* / 165 / 925，显示体系化与边界意识（本源是 10-4，补 additive 不重复）。
