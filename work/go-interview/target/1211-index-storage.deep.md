# 1211 深挖：索引的底层物理存储全链路

> 分类：数据库内核 | 难度：高 | 题型：深挖 | 频率：中 | 关键词：**B+树页、表空间、段/区、SDI、原子 DDL、自增值持久化**
> 原文锚点：第 1~106 段「索引底层存储全链路」

## 思路与架构
把「一张表的索引怎么落到磁盘」串成一条自上而下的链：
1. **逻辑层**：索引本质是有序数据结构（InnoDB 为 B+树），按列建立、加速查询、带来写入与存储代价。
2. **页层（16KB）**：B+树由「页」组成，叶子页存聚簇索引的完整行或二级索引的「键值+主键」；非叶子页只存路由键。
3. **区/段层**：页聚成「区（extent，64 个连续页）」，区聚成「段（segment，叶子段/非叶子段）」，段是空间分配的基本单位。
4. **表空间层**：段归属表空间（系统表空间 / 独立表空间 `.ibd` / 通用表空间），`.ibd` 内用「空间 ID + 页号」寻址。
5. **文件层**：`.ibd` 文件除数据页外，还内嵌 SDI（Serialized Dictionary Information）二进制，存表结构；可用 `ibd2sdi` 抽出为 JSON。
6. **字典层**：8.0 起数据字典下沉到 InnoDB 事务引擎系统表，DDL 变成对系统表的 DML，具备原子性；自增值经 redo + `mysql.innodb_dynamic_metadata` 持久化；8.0.20 起 doublewrite 独立成文件。

## 方案取舍
- **聚簇索引 vs 二级索引**：聚簇索引叶子直接存行、回表为零；二级索引叶子存「键+主键」，需回表。取舍点是「覆盖索引能否命中」决定要不要冗余列。
- **独立表空间 vs 系统表空间**：独立 `.ibd` 便于单表维护/迁移、碎片可控；系统表空间省元数据开销但易膨胀难回收。
- **8.0 字典重构取舍**：把 `.frm` 扔掉、字典入事务引擎，换来原子 DDL 与崩溃一致性，代价是升级路径与运维工具需适配新系统表。
- **doublewrite 分离取舍（8.0.20）**：独立文件降低写放大、提升并发，但多一份文件要纳入备份与监控。

## 答题技巧
- 答「索引怎么存」用**自顶向下四层法**：逻辑（B+树）→ 页（16KB）→ 区/段 → 表空间/文件，逐层对应一个工程含义。
- 必点「InnoDB 是聚簇索引、叶子存整行；二级索引靠主键回表」——区分 P6/P7 的关键。
- 被追问 8.0 改进时，直接抛「原子 DDL（字典下沉事务引擎）+ 自增值持久化（redo + 字典表）」两条，并带版本边界。
- 收尾补一句「`.ibd` 里内嵌 SDI、可用 `ibd2sdi` 导出」，展示对物理文件的可观测性，避免被追问时只停在概念层。
