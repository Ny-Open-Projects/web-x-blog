# 186 深挖：大日志检索的四层工具箱与线上红线

> 分类：操作系统 / Linux | 难度：L4 | 题型：排查题 | 频率：中 | 关键词：**检索策略**/**流式**/**切片**/**并行度**/**IO 打满**/**日志治理**
> 原文锚点：第 13~32 段「sed 指令在执行的时候会从第一行进行扫描，一直扫描到我们指定的行…因此还有一种方式，就是对这个文件进行分段处理…通过多 CPU 进行查找，速度会更快…线上要谨慎使用」
> [边界] 本文只讲**检索策略与风险控制**：单文件查看基础命令见 `186-big-log-viewing`，fd 与磁盘空间类排查见 `1313-os-virtual-fd`、`1815-file-deleted-space-held`，均不重述。

## 思路与架构

把「查大日志」按**代价从低到高**排成四层，永远从最低层开始试，试不上去再升层：

```text
第 1 层：不扫描（代价 O(1)）
  tail -n 200 app.log        末尾 seek，代价与总量无关
  head -n 200 app.log        从头读一点就停
  tail -f / tail -F          实时跟随（-F 能跟上轮转重建的文件）

第 2 层：窄区间扫描（代价 O(N)，N = 区间长度）
  sed -n '100000,100200p'    注意：仍要从首行顺序扫到 10 万行
  awk 'NR>=a && NR<=b'       同上，语义更清晰
  ↓ 判断依据：已知错误大概发生在什么时间段 → 先按时间定位偏移

第 3 层：切分 + 多文件检索（代价 O(总量)，但可并发）
  split -l 200000 big.log seg_        （GNU 可用 -n 按份数均分）
  grep -Hnw 'PATTERN' seg_*           -H 文件名 / -n 行号 / -w 全词

第 4 层：并行检索（代价 O(总量)/P，但风险最高）
  ls seg_* | xargs -P 8 -I{} grep -Hnw 'PATTERN' {}
  for f in seg_*; do grep ... "$f" & done; wait
  ⚠ 并行度必须限流，且只应在归档机/从库执行
```

**升层的判据**——每一层都要回答"我凭什么跳到下一层"：

```text
能定位到头尾?        → 停在第 1 层，不要升
能定位到时间段/行号? → 停在第 2 层
只知道内容不知道位置? → 升到第 3 层（切片是默认正解）
切片后仍然慢且紧急?  → 才考虑第 4 层，且必须限流 + 错峰
```

## 方案取舍

```text
方案 A：裸 grep 整个大文件
  + 一条命令，零准备
  - 全量顺序读，IO 打满，耗时线性于总量
  判定：仅在文件 < 几百 MB 且机器空闲时使用

方案 B：切分后串行 grep 各片
  + 总量不变，但单个 grep 失败可重来，能中途看进度
  - 总耗时没省，只是更可控
  判定：默认选择，风险最低

方案 C：切分后 xargs -P 并行
  + 多核机器上明显更快
  - 吃 CPU 与 IO；机械盘上并行度收益会被 IOPS 吃回去
  判定：SSD + 核数有余量 + 非高峰时才用

方案 D：预先建索引（采集进 ES / ClickHouse / 对象存储）
  + 检索从分钟级降到毫秒级，可聚合、可画图
  - 要投入采集链路与存储成本
  判定：这是**唯一的正解**，前三种都是救火
```

**线上四条红线**：

```text
1. 绝不 vim 打开大文件 —— 全量进内存，直接把机器拖垮
2. 绝不在业务高峰做全量/并行检索
3. 并行度上限 ≈ CPU 核数，且要观察 IO wait 是否飙升
4. 检索完记得清理临时切片（split 产物常常忘了删，反而占满磁盘）
```

## 答题技巧

```text
1. 开场先给分层，不报命令
   「我一般按代价分四层：不扫描 → 窄区间 → 切片 → 并行，
     能停在上层就绝不往下降。」
   有分层意识的回答，面试官会自动加分。

2. 背三条"为什么"，而不是三条命令
   - head/tail 为什么快？  定位头尾不需要读全文（tail 走末尾 seek）
   - sed 取区间为什么慢？  它必须从首行顺序扫到目标行
   - 并行为什么不一定快？  机械盘的瓶颈在 IOPS 不在 CPU

3. 主动点出两个高频翻车点
   - GNU split 的 -n/-d/--additional-suffix 在 macOS 上不通用
     （实测报 illegal option -- -，要改用 -l）
   - -w 是词边界不是空格，'503' 不会误命中 5030

4. 一定要落到"根本解法"
   「检索手法都是救火，正解是日志滚动切分 + 采集进检索系统，
     让'查 20G 日志'这件事根本不发生。」

5. 收尾一句拔高
   「排障的第一性问题不是'怎么查'，而是'为什么会有 20G 的日志'——
     日志治理缺失才是根因。」
```

**面试官可能追问的边界问题**：

```text
Q：tail -f 和 tail -F 区别？
A：-f 按文件描述符跟随，日志轮转后新文件它跟不住；
   -F 会按文件名重试打开，能跟上 logrotate 重建的文件。

Q：grep -H 单文件时为什么不显示文件名？
A：单文件检索是默认行为；多文件才自动带文件名，
   但为了脚本一致建议显式写 -H。

Q：切完片忘了删怎么办？
A：split 前应 mkdir 到独立临时目录，用完整个目录删掉；
   最好放在有定期清理的临时盘而非数据盘。
```
