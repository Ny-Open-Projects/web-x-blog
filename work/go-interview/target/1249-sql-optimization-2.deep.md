## 思路与架构
「SQL 优化经验」不是零散技巧，而是**分层体系**——从 SQL 写法到表结构到架构，每一层解决不同量级的问题。本波（12-49）覆盖的三个点正好落在不同层：

```text
SQL 优化分层体系
├─ L1 写法层：小表驱动大表（join 顺序），见 1249-small-table-drive
├─ L2 索引层：覆盖索引避免回表 / 深度分页（本波综合案例，边界见 1247/1239）
├─ L3 表结构层：动静分离（热列垂直拆表），见 1249-hot-cold-column-split
└─ L4 架构层：分库分表（降树高/降SMO/并行/负载均衡），见 1249-smo-sharding
```

排查顺序建议：**先写法层（最低成本）→ 再索引层（加覆盖索引）→ 再结构层（拆列）→ 最后架构层（分库分表，成本最高）**。能不加索引/不分表解决的问题，绝不往上推。

## 方案取舍
| 优化手段 | 解决什么 | 成本 | 适用边界 | 不该用的场景 |
| --- | --- | --- | --- | --- |
| 小表驱动大表 | join 内层探测次数 | 极低（改 SQL/加索引） | 有索引的 NLJ | 内层无连接索引 |
| 覆盖索引 | 回表 IO | 低（建联合索引） | 高频窄查询 | 列频繁更新（见动静分离） |
| 动静分离 | 缓冲页失效 | 中（拆表+JOIN） | 热列≫冷列更新频率 | 热冷总一起读 |
| 分库分表 | 树高/SMO/并行 | 高（中间件+分布式事务） | 单实例已到瓶颈 | 数据量未到亿级/可加索引解决 |

**取舍结论**：优化遵循「由廉价的写法/索引层优先，昂贵的架构层兜底」。分库分表是最后手段，不是首选；很多「慢」其实靠覆盖索引 + 小表驱动就能解决（本波综合案例中的 name 列导致回表 5 万行，正是靠「把 name 纳入联合索引末列」或「只取 ID 再查」在索引层解决，无需分表）。

**边界纪律**：综合案例中「联合索引 + 覆盖索引避免回表 + 深度分页用 where 缩范围 + order by 索引首列」属索引层，已被 `1246/1247/1239` 充分覆盖，本批**不重复**主卡，仅在边界引用。

## 答题技巧
1. **分层作答显体系**：开口就「SQL 优化我按写法→索引→结构→架构四层看」，比罗列技巧专业。
2. **数字与机制**：B+树 3 层≈千万、4 层≈亿；SMO 加锁会向上传播到根；缓冲池默认 16KB 页——这些数字让答案可信。
3. **讲清因果链**：动静分离不是「减少 IO」而是「切断热列更新→同页冷列缓存失效」；分库分表不是「分摊压力」而是「降 SMO 加锁范围+降树高」。
4. **避坑**：① 不把「小表全扫」（优化器择优，见 `1221`）与「小表驱动大表」（join 顺序）混为一谈；② 高频更新列不进联合索引；③ 分库分表是兜底手段，别张口就分。
5. **收尾落到边界**：被问「还能怎么优化」时，按 L1→L4 顺序给出下一层方案，体现工程权衡。
