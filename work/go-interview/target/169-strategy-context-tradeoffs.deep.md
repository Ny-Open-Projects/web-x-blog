# 169 策略注入方式与上下文取舍深挖

> 覆盖源 16-9 的工程延伸：setter/构造/函数类型三种注入的取舍、策略并发切换的坑、注册表收敛策略族、与 switch/map 分发的对比实测思路。主卡已给购物车主线，本附录做注入与演进深挖。

## 思路与架构

```text
策略到达上下文的四条路
├─ setter 注入 (源文 SetPayStrategy)
│   ├─ 运行期可换, 灵活
│   └─ 代价: 状态可变 -> 并发切换要锁; nil 窗口期
├─ 构造注入 (NewCart(strategy))
│   ├─ 生命周期内不变, 免锁
│   └─ 代价: 换策略要换整个上下文
├─ 函数类型注入 (type Pay func(int) string)
│   ├─ 单方法策略的最轻形态, 无需定义接口
│   └─ 代价: 多方法契约表达不了
└─ 注册表 (map[string]PayStrategy + Register)
    └─ 策略多时收敛选择逻辑, 按名取用
```

## 方案取舍
- **setter 注入的三个隐雷**：① **nil 窗口**——构造后到 Set 前的调用会 panic（主卡已防御）；② **并发切换**——两个字 goroutine 同时 Set/Checkout 读写字段是数据竞争，`go test -race` 必爆，要么加锁要么保证策略在启动期配置完毕；③ **可变状态传染**——上下文不再「构造即完备」，测试要额外 SETUP。若策略生命周期内不变，**构造注入是更稳的默认** [经验]。
- **单方法接口可以再瘦身**：策略只有一个方法时，接口可以整个消失——`cart.pay = func(amount int) string {...}`，函数类型就是策略。Go 的隐式接口已经够轻，「一个方法一个接口」的仪式感在函数类型面前是多余的；**方法数 ≥2 或需要状态时才立接口** [经验]。
- **策略多了以后：注册表收敛**：支付方式 10+ 种时，调用方的 `switch kind { ... }` 会把开闭收益吐回去——用 `map[string]PayStrategy` 注册表 + `Register(name, s)`，新增方式=注册一行，选择逻辑统一收口。与工厂模式的边界：工厂管「创建」，注册表管「查找」，策略管「行为」，三者常叠用而不冲突（模式全景见 `163-design-patterns.deep.md`）[经验]。
- **和 map 分发函数的对比**：不定义任何类型、`map[string]func(int) string` 也能消除 switch——但失去的是：① 无状态封装（策略的配置字段如卡号/CVV 没地方放）；② 无接口约束（漏实现无编译期检查）。**判断标准：策略有没有自己的配置状态**。有 → 接口+结构体；纯无状态 → map+函数足够 [经验]。

## 答题技巧
- 主线答四步实现后，主动报 nil 防御与并发切换两个工程雷——把「会写模式」升级为「用过模式」[经验]。
- 用「策略有没有配置状态」给 map+函数 vs 接口划界——展示选型判断而非模式崇拜 [经验]。
- 被问「策略太多怎么办」→ 注册表 + Register 收口，并区分工厂/注册表/策略三者的职责 [经验]。
- 被问「和状态模式区别」→ 「策略由调用方主动选、状态由内部流转被动变」（详见 `163-strategy.md` 的立论，不重述）[边界]。
- 主动边界到 `169-pay-strategy-cart`（购物车主线）、`163-strategy`（模式立论与函数类型形态）、`163-design-patterns.deep`（模式全景）、`168-builder-pattern-roles`（创建型对照），构成「设计模式实战」专题 [边界]。
