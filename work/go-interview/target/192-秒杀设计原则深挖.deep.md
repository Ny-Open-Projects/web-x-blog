# 192 秒杀设计原则深挖：五条原则的落地手段与代价

> 深挖卡：把「四要一不要」从口号落成可执行的手段清单，并给出每条的代价与边界。

## 思路与架构

五条原则不是并列关系，而是**一条递进的成本漏斗**——每往上一层，被拦掉的请求越多、落到数据库的越少：

```text
用户点击
  ↓ 【请求数要少】按钮置灰 + 合并静态资源 + 答题/滑块
  ↓ 【数据要少】  页面静态化 + 字段裁剪 + 压缩
  ↓ 【路径要短】  CDN 承载静态 → 网关限流 → 直达业务，少跳中间件
  ↓ 【依赖要少】  去掉非必要 RPC，剩余依赖配熔断降级
  ↓ 【不要过度设计】非核心功能可砍可降级，核心链路才做足
DB（只剩极少数真实请求）
```

每一层对应的一组具体手段：

| 原则 | 手段 | 拦掉什么 | 代价 |
|---|---|---|---|
| 请求数要少 | 静态资源合并、按钮置灰、答题/滑块、验证码 | 重复点击、脚本刷单 | 用户体验略降（答题） |
| 数据要少 | 页面静态化、字段裁剪、gzip/br、protobuf | 序列化与带宽成本 | 前端要配合改造 |
| 路径要短 | CDN、网关限流、减少中间件与 RPC 跳数 | 网络 RTT 与排队 | CDN 回源一致性要处理 |
| 依赖要少 | 去除非必要调用、本地缓存兜底 | 故障传播面 | 需要梳理依赖拓扑 |
| 不过度设计 | 非核心降级、核心做足 | 研发成本 | 需要明确核心链路边界 |

**关键认知：这五条原则本质都是在做「减法」**，而多数候选人上来就做加法（加缓存、加 MQ、加机器）。秒杀题的正确答案方向是**先减后加**——能不发的请求不发、能不传的数据不传、能不跳的节点不跳，剩下的才用缓存/MQ/锁去扛。

## 方案取舍

| 决策点 | 选项 A | 选项 B | 怎么选 |
|---|---|---|---|
| 限频位置 | 前端置灰 | 服务端令牌桶 | **都要**，前端体验、后端防守 |
| 限频粒度 | 单机进程内 | Redis + Lua 全局 | 单机快但不准；生产用 Redis 全局配额 |
| 削峰方式 | 同步直接扣库 | MQ 异步下单 | 秒杀必须异步，同步会打穿 DB |
| 库存扣减 | 数据库乐观锁 | Redis 预扣 + 异步落库 | Redis 预扣扛住峰值，DB 做最终一致 |
| 热点打散 | 单行库存 | 分段库存（拆 N 个子库存） | 分段把行锁冲突降为 1/N，需处理"某段售罄、总量有余" |
| 静态化 | 服务端渲染 | CDN + 纯静态页 | 秒杀页必须静态化，动态数据用独立小接口 |
| 降级范围 | 全站降级 | 只降非核心 | **只降非核心**（评价/推荐/积分），核心下单不降 |

取舍原则：**先判断这条路径在不在核心链路上**。核心链路（浏览秒杀页 → 下单 → 扣库存 → 支付）允许复杂、允许重投入；非核心链路（评论、推荐、排行榜）一律可降级、可简化、可异步。这条判据能一次性回答"要不要上某某组件"。

## 答题技巧

1. **开口先定性再列原则**：先说「秒杀 = 瞬时峰值 + 热点单行写」，再抛五条原则。定性错了（比如当成普通高并发读），后面答得再全也是偏的。
2. **主动抛那句最有区分度的话**：「**加机器解决不了热点行写，因为库存是一行，行锁把并发串行化了**」。这句话一出口，面试官基本会跳过基础追问直奔深水区。
3. **用实测数字代替形容词**：不要说"限频能挡掉很多请求"，要说「令牌桶容量 10、速率 100/s，瞬间打 100 次只放行 10 次」——**桶容量 = 瞬时放行上限**，这个结论是从数字里长出来的。
4. **把"不要过度设计"讲成有边界的纪律**：很多人答成"能简单就简单"，会被追问死。正确表述是「**核心链路做足、非核心可降级**，判断标准是这条路径断掉会不会影响成交」。
5. **收尾主动串到同批卡**：秒杀是个题族，一张卡答不完。主动说「缓存链路、削峰、防超卖、高可用分别是另外四张卡的内容」——展示的是体系感，而不是在回避。（对应 `193-seckill-link-cache`、`194-seckill-traffic.deep`、`195-prevent-oversell.deep`、`196-seckill-ha.deep`。）

## 细节与核心 API

```go
// 五原则：限流（挡住多余请求）/ 削峰（MQ 排队）/ 异步（下单与支付解耦）
//        / 库存预热（Redis 放库存，不直打 DB）/ 防超卖（原子扣减）
// 1) 库存预热：活动前把库存载入 Redis
rdb.Set(ctx, "stock:"+itemID, total, 0)
// 2) 入口限流：网关层令牌桶 + 答题/验证码防脚本
// 3) 下单：Lua 原子扣库存（见防超卖卡）
ok, _ := rdb.Eval(ctx, deductScript, []string{"stock:"+itemID}, 1).Int64()
if ok == 0 { return ErrSoldOut }
// 4) 异步创建订单：扣减成功才发 MQ，消费者落 DB + 支付
producer.Publish("orders", orderID, payload)
// 要点：能前置拦截的别放后端；任何“查库存+扣库存”两段必须原子，否则超卖
```
