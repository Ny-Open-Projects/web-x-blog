# 925 锁的不可重入与顺序控制陷阱

> 分类：并发模型 | 难度：L2 | 题型：八股题 | 频率：中 | 关键词：**不可重入 fatal error** / **控制逻辑顺序** / **多核非严格调度**
> 原文锚点：第 7~17 段、第 90~98 段「读锁后再获取写锁 Go 抛 fatal error…锁控制的是逻辑代码段顺序」

## 一句话总述
Go 的 Mutex/RWMutex 都不可重入：读锁未解再取写锁在 Go 直接 fatal error 终止程序（Java 才会死锁挂起）；锁锁住的是"逻辑代码段的执行顺序"，多核下协程仍可能同时被调度，只是其一在等锁。

## 面试官视角
- 考察意图：是否真踩过重入坑、是否理解锁的语义边界
- P5 知"不可重入" / P6 能讲 Go fatal error vs Java 死锁差异 / P7 能讲多核下加 sleep 才保证打印顺序
- 红旗：说 Go 重入会死锁（实际是 fatal error 崩溃）；说锁能严格控协程调度顺序
- 惊艳点：Go 重入不是死锁挂起，而是 runtime 检测到"所有协程休眠"直接 fatal error 退出进程 `[源码]`

## 主问答
**Q：** 读锁里再取写锁会怎样？锁能保证执行顺序吗？
**A：**
1. **不可重入崩溃**：RWMutex 持读锁再 Lock，Go 检测死锁直接抛 fatal error 终止程序（非挂起）`[源码]`。
2. **只控逻辑顺序**：锁保证的是"被锁代码段的先后"，不是协程调度顺序；多核下两协程可同时跑，其一在 Lock 处阻塞 `[源码]`。
3. **顺序需 sleep**：要稳定观测"先二后一"的打印，需让先持锁的协程 sleep，否则调度不确定 `[经验]`。
**加分层：** 与 Java 不同，Java 重入锁会死锁挂起、Go 直接崩溃——Go 没有可重入锁类型。
