# 908 扩容按元素 size 优化与时间/空间权衡

> 分类：Go / 切片 | 难度：L3 | 题型：原理题 | 频率：中 | 关键词：**元素 size 优化** / **位运算微调** / **时间空间权衡** / **大切片不双倍** / **小步长防频繁拷贝**
> 原文锚点：第 28~34 段「growslice 对 elemsize 位运算优化；基于时间复杂度与空间复杂度权衡；大切片双倍浪费内存、小步长频繁拷贝，故按 size 微调」

## 一句话总述
`growslice` 算出基础新容量后，还会**按元素 size（elemsize）做位运算微调**——这是 runtime 在"内存占用"与"扩容次数（拷贝开销）"之间的权衡：大切片若再翻倍会浪费大量内存，故因子更低；小切片若每次只涨一点又会频繁触发拷贝，故更激进。最终容量是这套权衡的结果，并非简单 2x/1.25x。

## 面试官视角
- 意图：能否讲清"扩容因子为什么不是固定值"，理解 runtime 的权衡。
- P5 知扩容会预留 buffer；P6 知按 elemsize 优化；P7 知"权衡本质：大切片省内存、小切片降拷贝频率"。
- 红旗：以为扩容因子是写死的常数；或以为每次都精确 1.25 倍。
- 惊艳点：点出"预留 buffer 是为减少 future 扩容拷贝，但预留过多又浪费——runtime 按 size 动态平衡" `[边界]` 见 923（扩容换地址）、909-slice-header（slice 头结构）。

## 主问答
**Q（面试官原话）：** 为什么扩容因子会按元素大小变化，不是固定值？
**A：**
1. **size 微调**：growslice 在基础容量上按 `elemsize` 做位运算微调，不同元素类型得到略不同的新容量。
2. **空间侧**：切片很大时若再翻倍，未继续追加就会空占大量内存——所以大切片因子更低（趋近 1.25）。
3. **时间侧**：若每次只涨一点点，频繁 append 会反复触发拷贝——所以小切片因子更激进（翻倍）。
4. **本质**：runtime 在"内存分配次数"与"内存空间占用"间求平衡，最终容量是权衡结果。
