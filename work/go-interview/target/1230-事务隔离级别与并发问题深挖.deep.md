# 1230 事务隔离级别与并发问题深挖

## 思路与架构
用**「三种现象 × 四种级别」的矩阵**统领全部内容，再补一层「实现机制」就能回答所有追问：

- **现象层**（要防什么）：
  - **脏读** —— 读到别人未提交的修改，值可能根本不存在过。
  - **不可重复读** —— 同一行、两次读，值变了（别人 UPDATE 并提交）。
  - **幻读** —— 同条件、两次查，行数变了（别人 INSERT/DELETE 并提交）。
- **级别层**（防到哪一步）：读未提交 → 读已提交 → 可重复读 → 串行化，逐档多挡一种现象。
- **实现层**（靠什么防）：
  - 读已提交：**每条语句**生成一次快照，所以能挡脏读、挡不住不可重复读。
  - 可重复读：**事务开始**时生成一次快照，全程复用，所以挡住不可重复读。
  - 串行化：把普通读也变成加锁读，用冲突排队换绝对一致。

记住「**快照生成的时机**决定能挡住什么」，矩阵就不再是死记硬背，而是一条可推导的链。

## 方案取舍
- **读已提交 vs 可重复读**：前者每条语句新鲜快照，一致性弱但锁与回滚段压力小、主从复制下 binlog 必须用 `ROW` 格式才安全；后者事务级快照，一致性好、是 InnoDB 默认。绝大多数业务直接用默认即可。
- **可重复读 vs 串行化**：串行化把所有读都加锁，一致性拉满但读写互相阻塞，吞吐断崖式下降。真需要强一致时，更划算的做法是**保持可重复读 + 对关键读显式 `SELECT ... FOR UPDATE`**，把锁的范围收窄到必要的那几行。
- **提高隔离级别 vs 改应用逻辑**：很多不一致其实靠「把读改写进一条原子 SQL」（`UPDATE t SET a = a + 1`）就能消除，无需升级隔离级别。**能用一条原子语句解决的，不要动隔离级别。**
- **长事务 vs 一致性**：可重复读下事务越久，快照越老、回滚段越大、锁持有越久。**宁可拆成短事务，也不要靠长事务换"读到稳定视图"。**
- **默认级别 vs 业务定制**：全局改隔离级别影响所有连接，风险面大；更稳妥是**会话级**对特定业务调整，并写进连接池初始化语句里。

## 答题技巧
- **开口先给矩阵**：三行四列的「脏读/不可重复读/幻读 × 各级别」是所有后续追问的锚点，先立住再展开。
- **主动纠正诱导题**：考官常问「读未提交能避免什么」，正确回答是「什么都避免不了」。答错这一句基本判负。
- **用一句话点出本质**：「**快照生成的时机**决定能挡住什么」——这句能把死记硬背的人甩开。
- **被问默认级别要带版本号**：MySQL InnoDB 默认**可重复读**；并顺带说明这比 SQL 标准要求更强（快照读下几乎无幻读），这是高频加分点。
- **收尾给可验证动作**：`SELECT @@transaction_isolation` 查当前级别、`information_schema.INNODB_TRX` 找长事务、双会话交叉验证——会动手的人最有说服力。

## 细节与核心 API

**现象 × 级别矩阵（✓ 会出现 / ✗ 被挡 / △ 快照读几乎无、当前读有）**：

```text
            脏读    不可重复读   幻读
读未提交      ✓        ✓         ✓
读已提交      ✗        ✓         ✓
可重复读      ✗        ✗         △(快照读几乎无，当前读有)
串行化        ✗        ✗         ✗
实现：RC 每条语句建快照 / RR 事务启动建一次快照 / 串行化普通读也加锁
```

```sql
SELECT @@transaction_isolation;                      -- InnoDB 默认 REPEATABLE-READ
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;  -- 会话级改，风险面小
SELECT * FROM information_schema.INNODB_TRX\G       -- 找长事务（trx_started 早）
-- 强一致关键读：保持 RR + 显式加锁，避免升级到串行化
SELECT * FROM t WHERE id=1 FOR UPDATE;
```

> 边界：MVCC/ReadView 见 1231；锁机制见 1232；本卡只讲隔离级别与并发现象。
