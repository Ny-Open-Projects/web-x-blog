# 155 微服务垂直/水平拆分与自动化落地 深挖

> 覆盖源 15-5 全文：垂直拆分优先 + 服务自治接口隔离 + 自动化驱动。主卡已给三原则总览，本附录做"垂直 vs 水平两种拆法对比"与"自动化驱动的落地前提"。

## 思路与架构

```text
微服务设计原则落地
├─ 拆分方向: 先垂直(按业务线) → 再水平(按处理流程分层)
├─ 自治边界: 标准接口隔离 + 禁止跨团队直连 DB
└─ 自动化前提: 工具链先行 → 流水线串联 DevOps → 交付周期 月 → 天
```

## 方案取舍
- **垂直 vs 水平**：垂直按业务线切（服装/家电/食品，业务线再细分），各业务闭环、团队端到端负责、职责边界清晰；水平按流程分层（UI/业务/数据），职责明确但**调用链路变长导致性能下降**、同一个需求跨多个服务使**沟通成本抬升**。综合利弊所以**先垂直后水平** [经验]。
- **性能/成本的反向验证**：水平拆分把一次本地调用变成多次远程调用，RT 叠加且故障点增多；垂直拆分的跨服务调用多发生在业务线边界，频率相对低 [经验]。
- **自治的代价与底线**：自治提升稳定性，但需要额外的接口契约治理；底线是**数据私有**——直接连对方库等于把对方的表结构变成自己的隐式依赖 [经验]。
- **工具链必须先行**：运维成本随服务数量指数增长(M×N 效应)，若先拆服务再补自动化，会被部署/监控/日志的重复劳动拖垮；应先用工具收敛创建/开发/测试/部署/运维的重复工作 [经验]。

## 答题技巧
- 被问"怎么拆"先答方向（垂直优先），再补"再按流程水平分层"，最后落到"拆分前先把自动化工具建起来" [经验]。
- 提到自治务必补"禁止跨团队直连对方数据库"，这是面试官最爱听的工程红线 [经验]。
- 主动边界到 `152-*`(选型权衡)、`154-*`(拆分执行)、`157-*`/`158-*`(治理与容错)，构成微服务全栈 [边界]。

## 细节与核心 API

**拆分方向 + 自治红线：**

```text
先垂直(按业务线：服装/家电/食品，各业务闭环、团队端到端负责)
→ 再水平(按流程分层：UI/业务/数据，调用链变长 RT 叠加、故障点增多)
```

**性能反向验证 + 自动化前提：**

```text
水平拆分把一次本地调用变多次远程调用，RT 叠加 + 故障点增多；垂直跨服务调用多在业务线边界，频率低
自治底线：数据私有 — 直连对方库 = 把对方表结构变自己隐式依赖（工程红线）
工具链先行：运维成本随服务数指数增长(M×N)，先建自动化(创建/开发/测试/部署/运维)再拆
```
