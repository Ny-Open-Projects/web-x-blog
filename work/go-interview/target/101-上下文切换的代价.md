# 101 上下文切换的代价

> 分类：并发基础 | 难度：L3 | 题型：机制题 | 频率：中 | 关键词：**上下文切换**/**寄存器**/**CPU缓存失效**/**内核切换**/**时间片**
> 原文锚点：第 31~39 段「上下文切换的定义与代价」

## 一句话总述
上下文切换是「保存当前任务状态 → 加载下一任务状态」的过程。代价来自两方面：**寄存器现场保存**与 **CPU 高速缓存失效**；切换还涉及硬件上下文与内核态的切换，是并发程序性能隐性杀手。

## 面试官视角
- 考察意图：是否理解并发并非免费——频繁切换会吃掉吞吐，是否能说出具体成本项。
- 分档：P5 知切换要保存状态；P6 知寄存器+缓存失效；P7 知还涉及内核/硬件切换、缓存失效是主要性能损耗。
- 红旗答案：以为切换只是「改个指针」，没有成本。
- 惊艳点：点出「CPU 比内存/IO 快几个数量级，缓存失效后要从内存重新加载，代价远高于切换本身」。

## 主问答
**Q（面试官原话）：** 什么是上下文切换？它有什么代价？
**A：**
1. **定义**：任务没在一个时间片内跑完就需让出 CPU，必须先保存当前执行状态（程序计数器、寄存器等），下次获得时间片时再加载，这一存一取就是一次上下文切换。
2. **寄存器现场保存**：切换前要保存执行流程状态到寄存器（保存/恢复寄存器现场），这是硬件级上下文切换的固定开销。
3. **CPU 高速缓存失效**：切换后新任务的数据不在当前 CPU 缓存中，缓存行失效，需从内存重新加载，而内存比 CPU 慢几个数量级——这是切换的主要性能损耗。
4. **内核态切换**：进程/线程切换需陷入内核，保存/恢复内核调度结构，比纯用户态切换更重。

## 关键代码
```go
// 频繁切换的代价直观对照：大量 goroutine 创建+调度切换会拉高 P99 延迟
func switchCostDemo() {
	var wg sync.WaitGroup
	for i := 0; i < 100000; i++ { // 10w 次创建+调度切换
		wg.Add(1)
		go func() {
			wg.Done()
		}()
	}
	wg.Wait() // 应复用 goroutine 或用协程池，避免无脑海量创建
}
```

## 总结与追问预判
切换成本主要在缓存失效与内核态切换。既然切换有代价，下一招就是「减少切换」——四类优化手段。
