# 101 上下文切换的代价

> 分类：并发基础 | 难度：中 | 题型：机制题 | 频率：中 | 关键词：**上下文切换、寄存器、CPU 缓存失效、内核切换、时间片**

> 原文锚点：第 31~39 段「上下文切换的定义与代价」

## 一句话总述
上下文切换是「保存当前任务状态 → 加载下一任务状态」的过程。代价来自两方面：**寄存器现场保存**与 **CPU 高速缓存失效**；切换还涉及硬件上下文与内核态的切换，是并发程序性能隐性杀手。一句话背法：**「上下文切换的代价主要在 CPU 缓存失效，其次才是寄存器保存与内核态切换」**。

## 面试官视角
考官看你是否理解并发并非免费——频繁切换会吃掉吞吐，能否说出具体成本项。能讲清"缓存失效是主要损耗、内存比 CPU 慢几个数量级"说明有底层视角；以为切换只是「改个指针」没成本，是红旗。
- **P5**：知道切换要保存/加载任务状态。
- **P6**：知道寄存器现场保存 + CPU 缓存失效两项成本。
- **P7**：知道还涉及内核/硬件切换、缓存失效是主要性能损耗。

## 主问答
**Q（面试官原话）：** 什么是上下文切换？它有什么代价？

**先铺垫（由浅入深第 1 层）**：一个核同一时刻只能跑一个任务的指令。任务没在一个时间片内跑完就得让出 CPU，让给别人跑——但下次轮到它时，得从它上次停的地方接着跑。这就得把"上次跑到哪、手里攒了啥"记下来，再加载别人的。这一存一取就是上下文切换。

1. **定义（第 2 层）**：任务没在一个时间片内跑完就需让出 CPU，必须先保存当前执行状态（程序计数器、寄存器等），下次获得时间片时再加载，这一存一取就是一次上下文切换。
2. **寄存器现场保存（第 3 层）**：切换前要保存执行流程状态到寄存器（保存/恢复寄存器现场），这是硬件级上下文切换的固定开销。
3. **CPU 高速缓存失效（第 4 层·主要损耗）**：切换后新任务的数据不在当前 CPU 缓存中，缓存行失效，需从内存重新加载，而内存比 CPU 慢几个数量级——这是切换的主要性能损耗。
4. **内核态切换（第 5 层）**：进程/线程切换需陷入内核，保存/恢复内核调度结构，比纯用户态切换更重；goroutine 的 M:N 调度把部分切换留在用户态，正是为了减轻这一点。
5. **误用风险（第 6 层）**：无脑海量创建 goroutine/线程会让切换次数暴涨，P99 延迟被切换成本吃掉；应复用协程池、控制并发数（见 108/102）。

## 版本与兼容性
| 维度 | 说明 |

| 通用事实 | 上下文切换成本是任何 OS/语言下都成立，不依赖 Go 版本 |

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// 直观对照：10w 次 goroutine 创建+调度切换，切换成本会拉高实际耗时
// 生产应复用 goroutine 或用协程池，避免无脑海量创建（见 108 何时控并发）
func main() {
	const n = 100000
	start := time.Now()
	var wg sync.WaitGroup
	for i := 0; i < n; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
		}()
	}
	wg.Wait()
	fmt.Printf("%d 次 goroutine 创建+调度切换耗时: %v\n", n, time.Since(start))
}
```

## 总结与追问预判
**背这三句就够**：① **上下文切换 = 保存现场 + 加载现场，让任务交替执行**；② **主要代价是 CPU 缓存失效（从内存重加载），其次是寄存器保存与内核态切换**；③ **海量创建协程会让切换暴涨、吃掉吞吐，要控并发/用池**。
**预判追问**：
- 「并发一定比串行快吗？」→ 不一定，切换成本 + 竞争会反噬（见 101 并发与并行）。
- 「怎么减少切换？」→ 减锁/数据分段、CAS、减线程数、协程 M:N（见 101 减少切换四类方法）。
- 「goroutine 切换比线程轻在哪？」→ M:N 把部分切换留在用户态（见 815 GMP 调度）。
