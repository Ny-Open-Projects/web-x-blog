# 1235 深挖：MySQL 锁机制与排查思路

> 分类：MySQL 锁 | 难度：高 | 题型：深挖 | 频率：高 | 关键词：**加锁单位、索引、RR/RC、死锁、观测**
> 原文锚点：第 1~111 段「MySQL 锁全景（四）」

## 思路与架构
把「一条 SQL 怎么加锁」串成一条链：
1. **隔离级别定基调**：RR 默认 next-key 防幻读；RC 退化为记录锁。
2. **索引定加锁对象**：锁永远加在索引上——命中主键锁主键，命中二级索引锁二级索引及其对应主键。
3. **语句定锁类型**：INSERT 走插入意向锁 + 表 IS；DELETE/UPDATE 先定位加 X 记录锁；`for update` 当前读按 next-key。
4. **冲突定阻塞**：唯一键冲突、supremum X 锁、next-key 间隙重叠 → 阻塞或死锁。
5. **观测定排查**：`performance_schema.data_locks` 看锁，`information_schema.innodb_trx` 看活跃事务。

## 方案取舍
- **RR vs RC**：RR 用 next-key 防幻读但锁粒度大、易阻塞；RC 无间隙锁、并发高但可能幻读——金融一致性选 RR，高并发读多写少可评估 RC。
- **唯一索引等值**：优化退化为记录锁，减少间隙争用——设计时应尽量用唯一键/主键定位，缩小锁范围。
- **批量删除**：大表 DELETE 走 next-key + purge 异步，宜分批/限行数，避免长事务持锁。

## 答题技巧
- 答「为什么 RR 不幻读」用**一句话**：RR 默认 next-key 锁锁间隙，RC 退化记录锁不锁间隙。
- 必点 **「锁在索引上」**——这是区分 P6/P7 的关键，很多人误以为锁在行数据上。
- 被追问死锁：直接说「next-key 间隙重叠 + 两事务加锁顺序相反」，并抛 `data_locks` 观测手段。
- 收尾强调「加锁单位默认是 next-key 锁、唯一等值会退化」，展示对默认行为的掌握。
