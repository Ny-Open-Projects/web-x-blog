# 602 Context 使用的最佳实践与反模式

> 分类：工程实践 | 难度：L2 | 题型：工程题 | 频率：高 | 关键词：**函数签名传递** / **第一参数** / **不在内层创建** / **及时 cancel**
> 原文锚点：第 105~132 段「作为参数而非结构体字段/全局变量…第一参数…不在内层创建…及时取消」

## 一句话总述
context 应作为函数第一个参数显式透传，在上层（请求入口）创建并向下传播；错误时及时 cancel；禁止塞进 struct、全局变量或在内层函数私自创建。

## 面试官视角
- 考察意图：能否把"参数传递 / 入口创建 / 及时取消"三条铁律讲成工程纪律。
- P5 知 context 放第一参数 / P6 能说清为何不放 struct、为何在上层创建 / P7 知不 cancel 的泄漏代价与排查。
- 红旗：把 context 存进 struct 字段；在内层函数新建 context 切断取消链。
- 惊艳点：在内层函数自建 context 会让其脱离父链，父 cancel 无法传递到该层，造成取消失效与泄漏 `[经验]`。

## 主问答
**Q（面试官原话）：** 你们项目里 context 一般怎么传，有什么坑？
**A：**
1. **结论**：context 永远作为函数第一个参数显式传入，不在 struct/全局变量里保存。
2. **机制**：在请求最外层（如 handler）创建，沿调用链一层层透传，保证父 cancel 能逐层到达。
3. **边界**：不在内层函数新建 context，否则脱离父链、取消信号断流；出错路径要立即 cancel 释放资源。
**加分层：** 即便逻辑不会超时，也建议入口统一 WithCancel 并在错误分支 cancel，养成确定性生命周期习惯。

## 关键代码
```go
// 示意，未验证：入口创建、错误即取消
func handler(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 5*time.Second)
	defer cancel()
	if err := do(ctx); err != nil {
		cancel() // 提前释放
		return
	}
}
```

- 第一参数传入、入口创建、错误即 cancel；禁 struct/全局/内层自建。
