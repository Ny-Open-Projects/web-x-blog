# 1019 忽视数据竞争

> 分类：并发模型 | 难度：L2 | 题型：事故题 | 频率：高 | 关键词：**data race** / **-race** / **共享内存**

> 原文锚点：第 3~32 段「多个 goroutine 访问同一内存且至少一个写，即数据竞争；可用 go run -race 检测」

## 一句话总述
当≥2 个 goroutine 访问同一块内存（全局变量、闭包捕获变量）且至少一个写时，就产生数据竞争，结果不可预期；用 `go run -race` 能在同进程内抓出调用栈。一句话背法：**「≥2 goroutine 访问同一内存且至少一个写 = 数据竞争（未定义行为）；go run -race 抓同进程竞态，跨请求写冲突查不到」**。

## 面试官视角
这是并发正确性的底线题。考官看你会不会用工具证明"无竞争"，而不是靠肉眼瞎看。
- **P5**：知道多写共享变量会乱。
- **P6**：说清判定条件 + 会用 -race。
- **P7**：知道 -race 抓不到跨进程/跨请求冲突。
- **红旗**：以为加锁就一定对；以为 -race 能查出所有并发问题。
- **惊艳点**：`-race` 只检测**同进程内** goroutine 的内存竞争，检测不到需靠锁/事务解决的跨请求写冲突 `[源码]` race detector。

## 主问答
**Q（面试官原话）：** 你写的并发代码怎么确认没有数据竞争？

**先铺垫（由浅入深第 1 层）**："看起来跑对了"在并发里毫无意义。数据竞争是未定义行为——它可能这次对、下次错，也可能永远不崩但悄悄算错。判定它只有一条硬规则：是否有"无同步的并发访问对"。

1. **结论（第 2 层·机制）**：多个 goroutine 同时访问同一变量且至少一方写，就存在竞争；用 `-race` 跑一遍定位调用栈 `[源码]`。
2. **机制（第 3 层）**：-race 在编译插桩，记录每处内存访问的 happens-before，冲突即报调用栈（main→increase→add→plus）`[源码]` race detector。
3. **边界（第 4 层）**：除 `atomic` 与 `sync.Map` 外，内置类型都非并发安全；**跨进程/跨 HTTP 请求的写冲突不是 data race**，-race 查不到，要事务或锁 `[源码]`。
4. **开销（第 5 层）**：-race 有运行时开销（约 2~10x），只用于测试/CI，不上生产；它会漏报依赖外部时序的竞态 `[经验]`。
5. **修法（第 6 层）**：用 Mutex/atomic/channel 建立 happens-before；修完再跑 -race 确认无冲突 `[经验]`。

## 关键代码
```go
package main

import "sync"

func main() {
	var cnt int
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			cnt++ // 无同步：多 goroutine 并发写同一变量 -> data race
		}()
	}
	wg.Wait()
	// 用 go run -race main.go 跑，会报 WARNING: DATA RACE 并定位调用栈
}
```

## 总结与追问预判
**背这三句就够**：① **共享内存 + 并发写 = 数据竞争（UB）**；② **go run -race 抓同进程竞态**；③ **跨请求写冲突 -race 查不到，要锁/事务**。
**预判追问**：
- 「-race 能查所有并发问题吗？」→ 不能，只同进程内存竞争；跨请求需事务/分布式锁。
- 「怎么修？」→ Mutex/atomic/channel 建 happens-before（见 1018 修法）。
- 「忘了等 goroutine 也会竞态？」→ 漏等导致计数偏小，见 1019 不等待。

## ⚠️ 原文纠错
原文把"多个 HTTP 请求并发修改同一行数据"也称作数据竞争。纠正：跨请求/跨进程的写冲突属于资源争用，**不是** Go 内存模型层面的 data race，`go run -race` 也检测不到，需靠数据库事务、行锁或分布式锁解决；data race 专指同进程内 goroutine 对共享内存的无同步并发访问。
