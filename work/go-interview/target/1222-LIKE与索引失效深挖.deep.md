# 1222 LIKE 与索引失效（深挖）

> 分类：MySQL 索引 | 难度：中高 | 题型：原理深挖 | 频率：高 | 关键词：**LIKE、最左前缀、覆盖索引、聚簇索引、二级索引、回表**

> 原文锚点：第 1~93 段「最左前缀原则、四种表实验、覆盖索引破例、聚簇vs二级索引成本」

## 思路与架构
LIKE 与索引的关系可拆成两条轴：
- 能否「定位」：前缀 LIKE（'x%'）利用 B+ 树有序性做范围定位 → type=range；非前缀（'%x%'）无法定位，只能全扫。
- 全扫「哪棵树」：覆盖时扫二级索引树（小、免回表）→ type=index；需回表时扫聚簇索引树（大）→ type=ALL。
覆盖索引是连接两条轴的关键：它不改变「非前缀无法定位」的事实，但改变了「全扫成本」，从而让二级索引被选用。

## 方案取舍
- 写 `'x%'` 而非 `'%x%'`：能用 range 就别用 index，前缀匹配效率更高。
- 用覆盖索引兜底模糊查询：对高频模糊列建索引，并让 SELECT 只取索引列，避免回表。
- 联合索引列序：对非前缀 LIKE 场景列序无关（反正全扫）；但对前缀/等值场景列序决定最左前缀命中，仍需把高区分度列放左。
- 不盲目加索引：索引增多拖慢写入与优化器选型；覆盖需求优先用「联合索引包含查询列」。

## 答题技巧
1. 先给铁律：LIKE 必须前缀匹配（'x%'）才能用索引有序性；'%x%' 常规失效。
2. 立刻抛破例：覆盖索引下非前缀 LIKE 走 type=index（全扫二级索引），三种例外本质都是覆盖。
3. 解释「为什么二级索引」：二级索引树只含索引列+主键、体积小于聚簇（含事务ID/回滚指针），覆盖免回表。
4. 收尾对比：type=range（定位）效率 > type=index（全扫）；回表与否决定优化器选树。
5. 实战话术：「模糊查询优先前缀；若必须中间匹配，建索引并只查索引列走覆盖，避免回表全扫聚簇。」

## 细节与核心 API

**两条轴：能否「定位」+ 全扫「哪棵树」**：

```sql
EXPLAIN SELECT * FROM t WHERE name LIKE 'x%';   -- type=range（前缀有序，B+树定位）
EXPLAIN SELECT * FROM t WHERE name LIKE '%x%';  -- 常规 type=ALL（非前缀无法定位）
```

**破例：覆盖索引下非前缀 LIKE 走 `type=index`（全扫二级索引树，免回表）**：

```sql
CREATE INDEX idx_name ON t(name);
SELECT name FROM t WHERE name LIKE '%x%';  -- 只取索引列 → 扫二级索引，type=index（非 ALL）
```

**全扫哪棵树**：覆盖扫二级索引（只含 索引列+主键，体积小，免回表）vs 需回表扫聚簇（含 `DB_TRX_ID`/`DB_ROLL_PTR`，体积大，type=ALL）。
