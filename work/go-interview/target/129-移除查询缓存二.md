# 129 移除查询缓存（二）：极易失效

> 分类：MySQL 内核 | 难度：L3 | 题型：分析题 | 频率：中 | 关键词：**表级失效**/**写放大**/**读远大于写**
> 原文锚点：第 28~34 段「第二个原因：容易失效…表变更全失效」

## 一句话总述
移除原因②**极易失效**：MySQL 不逐行维护缓存，而是**"某张表一变，所有关联该表的缓存全部失效"**——任何 `INSERT/UPDATE/DELETE/TRUNCATE/ALTER TABLE/DROP` 都让相关查询缓存作废，所以**只对"读远大于写"的表才划算**，读写均多的场景基本无效；逐条维护缓存的加锁+重算代价又太大，干脆全失效。

## 面试官视角
- 考察意图：是否抓住"失效粒度是表级"这一致命伤。
- 分档：P5 知写操作会让缓存失效；P6 知"表级全失效"；P7 能讲清"为什么不用行级失效（维护代价高）"与适用边界。
- 红旗答案：以为"只失效那一行对应的缓存"——实际是整表缓存清空。
- 惊艳点：点出 **失效粒度=表，是查询缓存被业务缓存(Redis)取代的根本原因** `[经验]`。

## 主问答
**Q（面试官原话）：** 为什么说查询缓存容易失效？
**A：**
1. **结论**：失效粒度是**表级**——表一变，相关所有缓存全废。
2. **机制**：MySQL 记录"每条缓存涉及哪些表"，一旦这些表发生写（DML/DDL），关联缓存全部标记失效。若想改为"只失效受影响数据"，需逐条检查+加锁+可能重跑 SQL，代价远超收益，故采用粗粒度全失效。
3. **边界**：因此**只有读远多于写的表**（如配置表、字典表）才适合查询缓存；写频繁的表缓存几乎一写就空，纯属开销。

**加分层：** 这与 CPU 缓存的"写回/写直达"是两码事——查询缓存没有行级/块级失效，粗粒度是设计妥协。

## 关键代码
```sql
-- 任意写操作都会清空 t 相关的全部查询缓存
UPDATE t SET col = col + 1 WHERE id = 8;   -- t 的所有 SELECT 缓存立即失效
-- 即便是和刚改那行无关的结果集，也一并作废
```

## 总结与追问预判
表级失效是查询缓存最大硬伤，只适合读多写少。追问接"管理开销与性能不可预测"以及"8.0 的替代方案"。
