# 923 切片与 map 传参深挖

## 思路与架构
切片与 map 的传参表现，统一由 **"一切传值 + 直接部分/间接部分"** 模型解释，无需分开记两套规则。
- **底层表示**：切片 = `(ptr→底层数组, len, cap)` 三字段 header；map = `*hmap` 指针的 header。两者 header 都是"直接部分"，底层数据都是"间接部分"。
- **传参统一行为**：拷贝 header（直接部分）→ 各自独立；共享底层（间接部分）→ 改内容互见。于是"下标改元素 / key 改键值"都反映外层，"对参数重新赋值"都不影响外层——切片与 map **完全一致**。
- **唯一差异在 append**：切片 `append` 在 cap 不足时**分配新底层数组、拷贝数据、换 ptr**；map 增长是 hmap **原地桶扩容/渐进搬迁**，**header 指向不变**。这就是"切片 append 有时外层看不到，map 新增一定看得到"的根因。
- **len 语义差异**：切片 len 是 header 里的独立字段，拷贝后外层 len 不随函数内 append 自增，故有"底层有数据但不可见"的窗口；map len 由 hmap 的 count 实时给出，新增即反映，无此歧义。

## 方案取舍
- **"传切片还是传指针"**：多数场景传切片本身即可（header 轻量、共享底层）；若需函数内改变外层 len/cap（如必须让 append 结果回传），应传 `*[]T` 或返回新切片重新赋值。
- **避免大切片 retention**：`big[2:3]` 这样的小切片会长期持有整个 big 的底层数组；用 `append([]T{}, big[2:3]...)` 或 `copy` 到新切片切断引用，及时释放大内存。
- **map 并发安全**：共享 hmap 在并发读写会 fatal（`concurrent map writes`）；需加锁或用 `sync.Map`，这与"传参共享"是同一底层事实的两面。

## 答题技巧
1. **一句话统一**：开场即"Go 都是值传递，拷贝直接部分、共享间接部分"，把切片/map/string/chan 全收进一个模型。
2. **对比表收尾**：用"改内容 vs 重新赋值""切片 len 独立 vs map len 实时"两行对比，凸显差异点。
3. **反直觉点**：① 切片 append 不扩容时新元素因**外层 len 独立**而不可见（不是没写进去）；② 切片 append 扩容后**换底层地址**，后续修改与外层无关；③ map 无扩容换地址，新增必反映；④ 反射强改 len 是教具非生产代码。
4. **验证手段**：打印 `%p` 首元素地址证"共享底层"；打印 len 证"直接部分独立"。
5. **版本锚点**：此行为自 Go 1.0 起稳定；hmap 渐进式扩容（非完全重建）是 Go 运行时的经典设计，可顺带展示深度。
