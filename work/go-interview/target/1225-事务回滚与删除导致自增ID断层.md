# 1225 事务回滚与删除导致自增 ID 断层

> 分类：MySQL 内核 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**自增主键**/**事务回滚**/**8.0 持久化**
> 原文锚点：第 1~16、43~48 段「回滚/删除造成断层…8.0 前后复用差异」

## 一句话总述
自增主键只保证**递增**不保证**连续**：事务回滚、记录被删除都不会把已分配的自增值"还回去"，后续插入从当前最大值+1 继续；MySQL 8.0 之前计数器在内存、重启按 MAX(id)+1 重建会复用，8.0+ 持久化到数据字典（redo 保护）后不再复用。

## 面试官视角
- 考察意图：是否真懂"自增连续 vs 递增"的语义与 8.0 行为翻转。
- 分档：P5 知回滚会留洞；P6 懂删除/回滚都不回收；P7 能讲清 8.0 前后重启复用差异与数据字典持久化。
- 红旗答案：以为回滚后 ID 会回填；以为 8.0 之前也持久化。
- 惊艳点：**8.0 把自增计数器放进数据字典并由 redo 保护，重启不再 SELECT MAX+1 重建，所以洞永久保留** `[经验]`。

## 主问答
**Q（面试官原话）：** 什么情况下自增主键会不连续？回滚后 ID 会回来吗？
**A：**
1. **结论**：事务回滚、记录删除、唯一索引冲突、显式指定 ID、改 offset/increment、手动 ALTER AUTO_INCREMENT 都会造成断层；回滚/删除**不会回收**已分配值。
2. **机制**：自增值在语句执行前分配，失败/回滚都不回退（回退需加锁查最大值，损害并发性能）；8.0 前计数器在内存，重启从 `MAX(id)+1` 重建故会复用洞，8.0+ 持久化到数据字典（redo 保护）不再复用 `[经验]`。
3. **边界**：指定了洞里的 ID 再插入仍能成功（显式值绕过自增分配）；但依赖连续性做业务判断是反模式。

**加分层：** 想彻底重置用 `TRUNCATE TABLE`（DDL、隐式提交、不可回滚、自增归位），`DELETE` 不行。

## 总结与追问预判
自增=递增非连续；回滚/删除不回收；8.0 持久化是分水岭。追问接"唯一索引冲突为何也留洞"。
