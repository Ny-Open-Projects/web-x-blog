# 1022 协程泄露的预防与治理体系

> 分类：Go 运行时 · 并发缺陷 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**context 取消**/**超时**/**协程池**/**channel 控并发**/**大文件分治**/**NumGoroutine 监控**
> 原文锚点：第 40~63 段「无退出机制→context 取消；无超时→设超时/协程池；占内存多→分而治之/文件流/协程池控并发」

## 一句话总述
防协程泄露是"让每个协程都有确定的退出路径"的工程问题：**context 取消**给协程退出信号、**超时**防止长任务堆积、**协程池/channel** 控制同时运行的协程数、**大文件分而治之/文件流**避免单协程吃光内存；线上用 `runtime.NumGoroutine()` 看趋势、pprof 的 goroutine profile 定位 `[经验]`。

## 面试官视角
- 考察意图：能否从"背坑"升级到"建防护体系"，给出可落地的治理手段。
- 分档：P5 知 context 取消；P6 知超时 + 协程池控并发；P7 知大文件分治/文件流 + 监控闭环（NumGoroutine/pprof）。
- 红旗：只说"用完关掉"，拿不出 context/超时/池化任一具体手段；或不知怎么"发现"泄露。
- 惊艳点：点出"协程池的本职就是给并发数设上限，从源头杜绝无界创建"；以及"监控是第一现场——NumGoroutine 只增不减就是泄露信号"。

## 主问答
**Q（面试官原话）：** 生产上怎么系统地防协程泄露？
**A：**
1. **context 取消**：for 循环读 channel 的协程必须监听 `ctx.Done()`，业务逻辑检测到完成/超时/不需执行时调用 cancel，子协程 `select` 到后 `return` 退出 `[经验]`。
2. **超时控制**：访问外部子系统必须设超时（context 超时 / `http.Timeout`）；无超时 + 下游故障 = 请求堆积协程失控。
3. **并发上限**：用**协程池**或带缓冲的**channel 信号量**限制同时运行的协程数，杜绝无界 `go func()`。
4. **大资源分治**：读大文件/处理海量数据，拆成小段流式处理，避免单协程把内存吃满 OOM。
5. **监控闭环**：`runtime.NumGoroutine()` 打印趋势，pprof goroutine profile 抓现场。

## 关键代码
```go
// 1) context 取消：子协程监听 Done 主动退出
ctx, cancel := context.WithCancel(context.Background())
go func() {
    for {
        select {
        case <-ctx.Done():
            return // 收到取消信号，退出
        case v := <-ch:
            handle(v)
        }
    }
}()
// 业务完成/超时：cancel()

// 2) 协程池式信号量：限制同时 10 个协程
sem := make(chan struct{}, 10)
for _, task := range tasks {
    sem <- struct{}{} // 占坑，满则等
    go func(t Task) {
        defer func() { <-sem }()
        do(t)
    }(task)
}
```
