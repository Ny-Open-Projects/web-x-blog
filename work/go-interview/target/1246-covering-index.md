# 1246 优化一：覆盖索引消掉百万次回表

> 分类：数据库 / MySQL 索引 | 难度：L4 | 题型：优化题 | 频率：高 | 关键词：**覆盖索引、回表、二级索引、SELECT 字段裁剪、Using index**

> 原文锚点：第 20~23 段「我们怎么去避免第二个查询的回表呢？这里我们可以使用覆盖索引，比如把 SELECT * 改成 SELECT name，由于我们获取的全部都是索引字段，所以这里它直接扫描二级索引树就可以了，它就不需要到主键索引上进行回表…只花费了二百六十八毫秒，比一秒零六百五十毫秒已经快了很多…覆盖索引确实可以减少过多的回表次数带来的性能消耗」

## 一句话总述
把 `SELECT *` 改为**只查询索引已覆盖的字段**，使扫描二级索引树即可拿到全部所需列，从而**免除百万次回表**；实测耗时从 1650 毫秒降到 **268 毫秒**。

## 面试官视角
P6 知道「覆盖索引能加速」；P7 要讲清**判定条件**（查询列全部落在索引里，执行计划出现 `Using index`）、**收益来源**（省掉回表而非省掉扫描），以及**它的局限**（业务确实只要索引列时才可用）。

## 主问答
**Q（面试官原话）：** 这个深度分页怎么优化？覆盖索引能解决什么问题？

1. **回表是主要开销**：深度分页的两块耗时中，**回表是更容易被优化掉的一块** `[源码]`。
2. **覆盖索引做法**：把 `SELECT *` 改成**只取索引字段**（如 `SELECT name`） `[源码]`。
3. **生效原理**：所取列**全部是索引字段**，因此**直接扫描二级索引树即可**，无需再到主键索引树回表 `[源码]`。
4. **实测收益**：耗时从 **1650 毫秒降到 268 毫秒**，提升显著 `[源码]`。
5. **结论**：覆盖索引确实能**减少过多回表次数带来的性能消耗** `[源码]`。
6. **适用条件**：业务**确实只需要索引列**时才成立；若要全字段则仍需回表 `[经验]`。
7. **判定方法**：用执行计划确认，覆盖索引时额外信息中会出现 **Using index** `[经验]`。

## 关键代码
```sql
-- 原查询：SELECT * 需要全部字段 -> 每条都要回表
SELECT * FROM userbig WHERE name LIKE 'name%' LIMIT 1000000, 10;   -- 约 1650 ms

-- 覆盖索引：只取索引列 name，二级索引树即可满足，无需回表
SELECT name FROM userbig WHERE name LIKE 'name%' LIMIT 1000000, 10; -- 约 268 ms

-- 确认是否命中覆盖索引：Extra 出现 Using index 即表示无需回表
EXPLAIN SELECT name FROM userbig WHERE name LIKE 'name%' LIMIT 1000000, 10;

-- 若要全字段且想少回表：先用覆盖索引拿到主键，再回表少量记录（延迟关联）
SELECT u.* FROM userbig u
  JOIN (SELECT id FROM userbig WHERE name LIKE 'name%' LIMIT 1000000, 10) t
    ON u.id = t.id;
```

## 总结与追问预判
**覆盖索引省的是回表，不是扫描**——扫描百万行依然存在，所以它只治「一半」。若业务必须要全字段，追问方向是**延迟关联**（先覆盖索引取主键再回表少量行）或**游标法**（见 1246-id-cursor）。

## ⚠️ 原文纠错
1. 事实核校：只取索引字段即可免回表、实测 1650→268 ms、覆盖索引减少回表开销——均与 InnoDB 覆盖索引机制一致 `[经验]`。
2. 补充：原文把 `SELECT *` 改成只查索引列的思路正确，但在真实业务中往往需要全字段，此时更通用的做法是**延迟关联**（子查询用覆盖索引取主键、外层再按主键回表），答题时补上这条会更完整 `[经验]`。
