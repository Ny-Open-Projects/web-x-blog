# 1811 IO 指标判读的优先级与假饱和深挖

> 覆盖源 18-11 的机制延伸：%util 与 await 的判读优先级、RAID/SSD/NVMe 时代的 %util 失真、异步 IO 与 page cache 的屏蔽效应、iostat 观测方法论的基线对照。主卡已给两步链，本附录做判读深挖。

## 思路与架构

```text
IO 指标判读的优先级账本
├─ 第一判据: 应用延迟 (最终裁判)
│   └─ 应用响应变慢/超时 = 有问题的必要条件
├─ 第二判据: await (r_await/w_await)
│   └─ 应用视角等待 ms (含排队) -> 超设备正常值 = 饱和/故障
├─ 第三判据: aqu-sz
│   └─ 队列深度持续 >1 = 请求在积压
├─ 参考项: %util (最易误读)
│   ├─ 含义: 设备"有 IO 在处理"的时间占比
│   ├─ 失真1: RAID/多路径逻辑设备 100% != 物理盘极限
│   └─ 失真2: 并行能力强的设备 (NVMe) %util 高不必慢
└─ 方法论: 基线 -> 负载 -> 对照
    [实测] tps 132->7788, 3.09->264 MB/s (dd 512MB 期间)
```

## 方案取舍
- **%util 为什么退居参考项**：%util 的原始语义是「采样周期内设备有至少一个 IO 在处理的时间比例」，隐含假设是**设备串行处理**——机械单盘时代成立；RAID 阵列、多队列 NVMe 可并行处理多请求，%util=100% 只说明「每刻都有活」，吞吐与延迟可能还有大量余量。现代 Linux 的 iostat 甚至标注 %util 对并行设备无意义。**判读顺序应是 应用延迟 → await → aqu-sz → %util**，把最易失真的放最后 [经验]。
- **await 的「含排队」特性是双刃剑**：它反映应用真实感受，但把「设备慢」与「请求发太多」混在一起——await 高时先看 r/s+w/s 是否异常放大（业务风暴/日志狂写），再下结论设备故障。归因顺序：**先查量、再查速**——量没涨而 await 涨才是设备侧问题 [经验]。
- **磁盘忙而应用无感的三个屏蔽器**：① **异步 IO**——应用提交后不等待，延迟不落在调用线程；② **预读（readahead）**——顺序读由内核提前拉取，命中时应用零等待；③ **page cache**——写先落缓存异步刷盘（见 1835.md` 的落盘语义）。推论：**排查 IO 问题永远从应用症状出发**，无症状的磁盘忙只是「设备在干活」，不是事故 [经验]。
- **观测方法论：基线对照压过单点快照**：单次 iostat 只给瞬时值，无法区分「一直这样」与「刚变坏」。标准动作是**采基线 → 复现负载 → 对照**——[实测] 本机演示：空闲时 disk0 tps=132/3.09MB/s，dd 写 512MB 期间 tps=7788/264MB/s，负载特征（顺序大块写）从 tps 与 MB/s 的比例关系直接可读（大 tps 低 KB/t 为随机小 IO，反之顺序大块）。pidstat 的滚动输出正是为这种时间维观测设计，比 top 的清屏模式更适合留痕 [实测]。

## 答题技巧
- 回答按「设备层 → 进程层」两步链组织，先报工具与指标族再报判读——结构即得分 [经验]。
- 主动纠偏 %util：「RAID 逻辑设备 100% 是假饱和，判读优先级 await > aqu-sz > %util」——一句话甩开背工具名的人群 [经验]。
- 报实测对照：「基线 132 tps，负载下 7788 tps，267MB/s——顺序写特征明显」——用数字证明做过，不只是听过 [实测]。
- 被问「磁盘忙应用不卡要不要管」→ 报三个屏蔽器，结论「以应用延迟为最终判据，但持续满载要预警容量」[经验]。
- 主动边界到 `1811-io-troubleshoot`（两步链主线）、`1833-sync-vs-async-io`（同步异步判据）、`1836-zero-copy-path`（零拷贝减负）、`188-load-diagnosis`（平均负载归因）、`1818-raid-basics`/`1818-raid-selection`（RAID 并行能力来源），构成「性能排查」专题 [边界]。

## 细节与核心 API

```bash
iostat -x 1                   # -x 看扩展指标
# 关键列：
#   r/s, w/s        每秒读写次数
#   rkB/s, wkB/s    吞吐
#   await           单 IO 平均等待（队列+服务），>20ms 偏慢
#   svctm           设备服务时间（新内核已弃，近似）
#   %util           设备忙闲比，100% 表示设备满负荷（但 SSD 可并行，未必瓶颈）
#   aqu-sz          平均队列深度
# 判读优先级：await 突增 + aqu-sz 堆积 -> 真实阻塞；%util=100 但 await 低 -> 吞吐打满但未见延迟，未必瓶颈
fio --name=t --rw=randrw --bs=4k --iodepth=32 --runtime=60  # 压测验证真实上限
# 假饱和：RAID/多队列设备 %util 是各盘聚合，单盘没满也可能显示 100%；看 await 而非 util
```
