# 134 正排索引与倒排索引：从「文档 → 词」到「词 → 文档」

> 分类：Elasticsearch 存储 | 难度：L2 | 题型：概念题 | 频率：高 | 关键词：**正排索引、倒排索引、文档ID、分词、B+树、词项**

> 原文锚点：第 1~17 段「正排索引记录的是文档ID到字段或者是关键词的对应关系的集合…在 MySQL 中一个数据行，我们就可以看作是一个文档…倒排索引则刚好相反，它记录的是某个字段值或者是某个字段中每一个词跟文档ID的对应关系，通俗来说就是包含某个词的文档ID的集合」

## 一句话总述
**正排索引**记录的是"**文档 ID → 字段/关键词**"的对应关系（MySQL 除全文索引外都属于正排，靠 **B+树**构建）；**倒排索引**刚好**反过来**，记录的是"**词 → 包含该词的文档 ID 集合**"。检索时先用分词器把字段值切成词，再为每个词记录它出现在哪些文档里。

## 面试官视角
- 考察意图：能否用一句话说清"正排/倒排到底谁映射到谁"，这是全文检索的入门分界。
- 分档：P5 知道倒排索引是"词找文档"；P6 能举出**分词后每个词对应一个文档 ID 集合**的具体例子；P7 能补上"**MySQL 的二级索引本质也是正排**"这一对照。
- 红旗答案：说倒排索引是"把索引倒过来排序"；或把两者方向说反。
- 惊艳点：**MySQL 里"一个数据行 = 一个文档"**，给 `name` 建普通索引就是记录"**主键 ID → name 字段**"的对应关系——**这就是正排**，只不过它是用 B+树构建的 `[源码]`。

## 主问答
**Q（面试官原话）：** 什么是倒排索引？

1. **结论**：**正排索引**记录"**文档 ID → 字段或关键词**"的对应关系集合；**倒排索引**记录"**字段值或字段中每一个词 → 文档 ID**"的对应关系，**通俗说就是包含这个词的文档 ID 的集合** `[源码]`。
2. **正排索引侧**：在 MySQL 中**一个数据行可以看作是一个文档**；给 `user` 表的 `name` 字段加一个普通索引，就意味着记录了"**文档 ID（即主键 ID）→ name 字段**"的对应关系；**MySQL 的这个对应关系是通过 B+树来构建的** `[源码]`。
3. **倒排索引侧**：倒排索引**刚好相反**，记录"某个字段值，或某个字段中的每一个词 → 文档 ID"；**MySQL 中除全文索引外都属于正排索引** `[源码]`。
4. **分词是前置步骤**：建立倒排索引**首先要对字段值进行分词**；假设按单词分词，"**小明**"会被切成"**小**"和"**明**"两个词 `[源码]`。
5. **形成词 → 文档集合**：分词后，"小"这个词出现在文档 1、2、3 中，于是**"小"的倒排索引记录的文档集合就是 1、2、3**；"明"只出现在文档 1，其集合只有 1；"红"只在文档 2；"强"只在文档 3 `[源码]`。
6. **收益的直接来源**：因为"包含某个词的文档 ID"已经**预先记录**下来了，要在几千亿数据中查找包含"红"字的文档时，**很快就能定位到它出现在 2 号文档** `[源码]`。

**加分层：** 正排解决"**给我一个文档，它有哪些内容**"（适合按主键取行）；倒排解决"**给我一个词，哪些文档含它**"（适合全文检索）。两者不是替代关系，ES 里**同时存在**——倒排用于检索，正排（stored field / doc_values）用于取原值与聚合。

## 关键代码
```go
// 用 Go 直观对比"正排"与"倒排"的映射方向
package main

import (
	"fmt"
	"sort"
	"strings"
)

func main() {
	// 文档集：docID -> 原文
	docs := map[int]string{
		1: "小明",
		2: "小红",
		3: "小强",
	}

	// 正排索引：文档ID -> 字段值（等价于 MySQL 二级索引按主键找值）
	forward := map[int]string{}
	for id, text := range docs {
		forward[id] = text
	}
	fmt.Println("正排（文档->内容）:", forward)

	// 倒排索引：词 -> 包含该词的文档ID集合
	inverted := map[string][]int{}
	for id, text := range docs {
		for _, term := range strings.Split(text, "") { // 按单字分词
			inverted[term] = append(inverted[term], id)
		}
	}
	for _, ids := range inverted {
		sort.Ints(ids)
	}
	fmt.Println("倒排（词->文档ID集合）:", inverted)

	// 检索"包含'红'字的文档"：直接取倒排列表，无需扫全量
	fmt.Println("查询'红'命中文档:", inverted["红"])
}
```

## 总结与追问预判
**最爱追问的是"MySQL 的索引算不算倒排"**——**不算**，MySQL 除全文索引外都是**正排**（文档 ID → 字段值），只是用 B+树组织；倒排的关键词是"**先分词、再建词到文档的映射**"。追问常接"那倒排索引的检索优势具体在哪"——见 134：核心是 **LIKE '%x%' 必然全表扫描**，而倒排索引可以**直接取词的文档列表**。

## ⚠️ 原文纠错
1. 事实核校：正排为"文档 ID → 字段/关键词"、MySQL 一个数据行可视为一个文档、MySQL 普通索引为正排且由 B+树构建、倒排为"词 → 文档 ID 集合"、建倒排需先分词——均与检索系统基本原理一致 `[经验]`。
2. 补充：原文的示例按**单字**分词（"小明" → "小" / "明"），真实场景多用 **IK 等中文分词器**按词切分；另外倒排索引记录的通常不只是文档 ID，还包括**词频与位置信息**（见 134）`[经验]`。
3. 崩坏词归一：源码将倒排索引、正排索引、文档 ID、分词、B+树、Elasticsearch 等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
