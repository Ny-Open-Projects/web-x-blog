# 1015 channel 锁的四道坑：不可重入、无 TryLock、panic 与误用

> 分类：并发模型 | 难度：L3 | 题型：陷阱题 | 频率：中高 | 关键词：**不可重入、TryLock、defer 解锁、死锁、通信共享内存**

> 原文锚点：第 31~36 段「推荐使用 channel 并不是因为 channel 的性能有多高，主要是它符合不要通过共享内存来通信，而是通过通信来共享内存的设计哲学」

## 一句话总述
推崇 channel 是因为它契合**用通信共享内存**的设计哲学，不代表性能更高；当锁用它时会踩到**不可重入、无原生 TryLock、漏解锁即死锁**三道坑。

## 面试官视角
P6 会说"官方推荐用 channel"；P7 要能纠正为**推荐的是通信模型，不是把通道当锁用** `[经验]`。加分点：指出同一 goroutine 二次加锁会**永久阻塞**，且通道锁没有标准库那样的 TryLock `[源码]`。

## 主问答
**Q（面试官原话）：** 既然官方推崇 channel，是不是该处处用它替代锁？

1. **推荐的是模型不是性能**：选择通道是因为它符合"**不要通过共享内存来通信，而要通过通信来共享内存**"，能更简单解决复杂协作问题 `[源码]`。
2. **不是每种场景都合适**：在互斥锁这个场景上，标准库的互斥锁**既简单又快**，通道实现的锁并没有优势 `[实测]`。
3. **不可重入**：同一 goroutine 连续加锁两次会阻塞在第二次写入上；实测 200 毫秒仍未完成，等价于自锁 `[实测]`。
4. **没有原生 TryLock**：标准库互斥锁提供尝试加锁，通道锁要自己写 `select` 加 `default` 才能模拟，语义还不完全一致 `[经验]`。
5. **漏解锁即死锁**：解锁动作是"从通道读出"，一旦临界区 panic 或提前 return 而没读出，后续所有加锁方永久阻塞；必须 `defer` 解锁 `[源码]`。

## 关键代码
```go
// 模拟 TryLock：用 select + default 非阻塞写入
select {
case m.ch <- struct{}{}:
    // 拿到锁，记得 defer m.Unlock()
    defer func() { <-m.ch }()
    doSomething()
default:
    // 拿不到锁，直接返回，不阻塞
}
```
> 验证：同一 goroutine 内连续两次 `m.Lock()`，200ms 超时仍未返回，确认不可重入 `[实测]`。

## ⚠️ 原文纠错
1. 事实核校：原文"推荐 channel 不是因为性能"准确；补充——这也是**通道锁性能更差却不推荐替换互斥锁**的完整理由，两句要连起来答 `[经验]`。
2. 补充：原文未提重入与异常路径风险；通道锁与互斥锁同样**不可重入**，且必须 `defer` 解锁，否则一次 panic 就会拖垮全部等待方 `[源码]`。
