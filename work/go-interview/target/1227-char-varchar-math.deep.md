# 1227 深挖：字符类型的空间账本

> 分类：MySQL / 数据类型 | 难度：L4 | 题型：架构题 | 频率：中高 | 关键词：**定长变长、行长度上限、字符集字节、TEXT 溢出、容量规划**

> 原文锚点：第 1~94 段「char 与 varchar 的区别…长度怎么设置…行大小限制」

## 思路与架构

这一节的全部内容可以归到**同一个问题**：一个字符字段到底占多少空间，以及上限是怎么被算出来的。

**第一层：定长与变长的取舍。** 变长字段必须额外记录"这一段实际有多长"，代价是 1~2 字节；定长字段不需要，但不足长度时用空格补齐。所以判断依据只有一条：**长度是否真的固定**。固定就选定长，省下记账字节——别小看这 1 字节，一千万行约 10MB，十个这样的字段一千万行就是百兆级别。反过来，把真正变长的数据塞进定长字段，填充造成的浪费远大于省下的 1 字节。

**第二层：字符数与字节数。** 字段声明的长度是**字符数**，实际占用的是**字节数**，两者之间的换算系数由字符集决定。utf8mb4 下一个汉字 3 字节、英文与数字 1 字节、表情符号 4 字节；GBK 下汉字 2 字节；latin1 是单字节编码，只覆盖西欧语言。这里要记住两个函数：`LENGTH()` 取字节数、`CHAR_LENGTH()` 取字符数。另外，MySQL 里旧称的 utf8 实为最大 3 字节的 utf8mb3，与 utf8mb4 的实质差别就是能不能存 4 字节的表情符号。

**第三层：上限从哪来。** 一条记录全部字段的字节总和不能超过 65535 字节。注意报错信息的措辞是"行大小过大"而不是"字段过长"——这提示约束对象是整行。于是 varchar 的可用长度是一个四步扣减：

1. 从 65535 起步；
2. 减去长度信息：字段字节数超过 255 用 2 字节，否则 1 字节；
3. 减去可为 NULL 列的标志位（每列 1 字节），NOT NULL 则省下；
4. 减去同表其他字段（如 INT 主键 4 字节）；
5. 最后除以字符集的单字符最大字节数，向下取整。

几个对照结果：utf8mb4 + INT 主键 + 可为 NULL → 16382；改用 utf8mb3 且可为 NULL → 21842；再改成 NOT NULL → 21843；latin1 单字段 → 65533。

**第四层：TEXT 与 BLOB 的特殊性。** 它们的内容存在行外，**不计入** 65535 的行长度限制，但行内仍要留几个字节记录长度与溢出指针——官方口径 9~12 字节，原文实测 10 字节，且可为 NULL 时还要再占一个标志位。容量量级上，TEXT 最大 65535 字节，MEDIUMTEXT 可达 16MB，LONGTEXT 可达 4GB。

## 方案取舍

| 场景 | 选择 | 理由 |
|---|---|---|
| 长度固定（如定长编码） | 定长类型 | 省下长度信息字节 |
| 长度可变 | 变长类型 | 避免空格填充浪费 |
| 需要存表情符号 | utf8mb4 | 旧 utf8 最大 3 字节放不下 |
| 纯西欧语言 | latin1 | 单字节，可用长度最大 |
| 大段文本 | TEXT / BLOB | 内容不计入行长度 |

取舍要点：

- **省字节的前提是长度真固定。** 拿变长数据用定长字段，是拿小钱换大亏。
- **超长报错还是截断，取决于模式。** 严格模式是默认行为，别按"会截断"来设计。
- **上限推导要扣到整行。** 只盯着单个字段算，一定算不对。
- **TEXT 不是免费的。** 内容豁免但指针照占，设计宽表时这点会被放大。

## 答题技巧

1. **先说"声明按字符、存储按字节"。** 这一句是整个字符类型章节的钥匙。
2. **算题当场推，不要背数。** 把四步扣减写在纸上逐步减，比报一个记错的数字可信得多 `[经验]`。
3. **报错措辞当线索用。** 提示"行大小过大"就说明约束在整行，顺着这条线推导不会偏 `[源码]`。
4. **把量级记全。** 65535 字节的行上限、9~12 字节的 TEXT 行内开销、16MB 与 4GB 两个 TEXT 档位，报得出来很加分 `[经验]`。
5. **区分函数。** 被问"这个字段多长"时主动说明你取的是字节还是字符，细节分就到手了。
