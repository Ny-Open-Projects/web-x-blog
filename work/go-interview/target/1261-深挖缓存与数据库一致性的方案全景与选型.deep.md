# 1261 深挖：缓存与数据库一致性的方案全景与选型

> 分类：缓存 / Redis | 难度：L4 | 题型：综合题 | 频率：高 | 关键词：**双写一致性、Cache Aside、延迟双删、MQ 重试、binlog 订阅、过期时间**

> 原文锚点：第 1~86 段「使用缓存最大的挑战是如何保证 Redis 与数据库的双写一致性问题…并发问题并不是 Redis 内部执行机制导致的，而是业务层发起了并发请求导致的…当数据更新的时候删除缓存，当读取缓存的时候如果没有命中缓存，再从数据库中读取数据然后回写到缓存当中，这个策略就是 Cache Aside…先更新数据库再删缓存出现问题的条件更加苛刻…订阅 binlog 进行异步删除…给缓存设计一个较短的过期时间」

## 思路与架构

把双写一致性问题拆成**五层递进**，面试时按此链路作答：

1. **认清问题**：引入缓存后更新数据要同时改库与改缓存，产生顺序问题。**先更新缓存**时库失败即不一致；**先更新库**时并发更新会因到达顺序颠倒而不一致。**关键认知：并发来自业务层的并发请求，Redis 单线程并不解决这个问题。**
2. **换思路——避免问题产生**：与其更新缓存，不如**删除缓存**。理由是操作路径更短、避免无效查询与写入、与 MySQL 被废弃的查询缓存同构，且**更新频繁的数据本就不适合缓存**。
3. **定策略——Cache Aside**：更新时删除缓存，读取未命中时从库加载并回写（**懒加载**）。这是业界默认解法。
4. **选顺序——先更新库再删缓存**：两种顺序都有异常窗口，但「先更新库」的条件更苛刻（读请求需恰好未命中、查库发生在改库前、写缓存发生在删缓存后），且**缓存操作通常快于数据库**，故更安全。
5. **补兜底——窗口与失败都要处理**：窗口用**延迟双删**压缩（休眠时长为经验值，只是尽力而为）；删除失败用**同步重试 / MQ 异步重试 / 订阅 binlog 异步删除**补偿；最后用**较短的缓存过期时间**收尾。

## 方案取舍

| 方案 | 解决什么 | 代价 | 适用 |
|---|---|---|---|
| 更新缓存 | — | 并发乱序留旧值、无效查询 | 不推荐 |
| 删除缓存（Cache Aside） | 并发乱序与无效写入 | 一次缓存缺失 | 默认方案 |
| 先删缓存后更库 | 实现简单 | 窗口较大，脏值易回写 | 一致性要求低 |
| 先更库后删缓存 | 压缩窗口 | 仍有极小窗口 | **推荐** |
| 延迟双删 | 清掉回写的脏值 | 休眠耗时、时长凭经验 | 中等一致要求 |
| 同步重试 | 删除失败 | 占用请求时间 | 低频场景 |
| MQ 异步重试 | 删除失败且要解耦 | 引入消息中间件 | 通用 |
| binlog 订阅（Canal） | 删除失败且零侵入 | 需开 row 格式 binlog、运维成本 | 大型系统 |
| 短过期时间 | 兜底 | 命中率下降 | **必配** |

取舍要点：**没有一种方案能给出强一致**。工程上的正确姿势是「Cache Aside + 先更库后删缓存 + 删除失败补偿 + 短过期时间」四件套；追求强一致则必须引入分布式锁或串行化，付出性能代价。

## 答题技巧

1. **先破后立**：先说明「更新缓存这条路走不通」（并发乱序），再引出删除缓存，逻辑最有说服力。
2. **带上物理直觉**：「缓存操作比数据库快，所以先更库后删缓存的窗口极小」——这句话能让面试官相信你是推理而非背诵。
3. **诚实交代局限**：主动说「延迟双删只是尽力而为，休眠时长是经验值」，比吹嘘方案完美更可信。
4. **报出 Canal 原理**：伪装从节点 → dump 请求 → 接收 binlog → 解析结构化数据，这是加分硬证据。
5. **别忘了兜底**：结尾补一句「缓存设置较短过期时间作为最后防线」，体现闭环思维。
6. **止步档位**：能讲清 Cache Aside 与删除顺序即达 L4；能完整讲出窗口分析、延迟双删、MQ/binlog 补偿与过期兜底，并说明「没有强一致」，即达 L5。

## 细节与核心 API

**Cache Aside 标准实现（先更库、再删缓存，窗口最小）：**

```go
func Update(ctx context.Context, key string, val *Order) error {
    if err := db.Update(val); err != nil { // 1. 先更新数据库
        return err
    }
    cache.Delete(key) // 2. 再删除缓存（读未命中时懒加载回写）
    return nil
}
```

**延迟双删（尽力而为，清掉并发回写的脏值）+ 删除失败补偿：**

```go
cache.Delete(key)
time.Sleep(500 * time.Millisecond) // 休眠时长凭经验，仅尽力压缩窗口
cache.Delete(key)
// 删除失败补偿三选一：
// ① 同步重试（低频）② MQ 异步重试（解耦）③ 订阅 binlog 异步删（零侵入）
```

**Canal 订阅 binlog 异步删除（大型系统推荐）：**

```text
原理：伪装 MySQL 从节点 → 发 dump 请求 → 接收 row 格式 binlog
     → 解析为结构化数据 → 投递 MQ / 直连删除 Redis
前提：MySQL 开启 binlog 且为 ROW 格式；运维侧引入 Canal 组件
```

**兜底必须配：**

```go
cache.Set(key, v, shortTTL) // 较短的缓存过期时间，作为最后一道防线
```
