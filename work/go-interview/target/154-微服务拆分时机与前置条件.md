# 154 微服务拆分时机与前置条件

> 分类：架构设计 / 微服务 | 难度：L3 | 题型：决策题 | 频率：高 | 关键词：**单体优先** / **演进式拆分** / **被迫拆分** / **基础设施就绪** / **康威定律**
> 原文锚点：第 6~14 段「产品初期单体；业务不清单体更简单；资源受限风险大；单体过大被迫拆；拆前基础设施就绪」

## 一句话总述
微服务化是**业务发展到一定阶段被迫做**的事：产品初期/业务理解不清/资源受限时选**单体**更稳；当单体过于庞大不得不拆时才微服务化，且拆分前需基础设施就绪（监控/自动化部署/服务化框架/灰度发布/资源调度/弹性伸缩）。

## 面试官视角
- 意图：考察是否把微服务当银弹，还是懂"单体→演进"边界。
- 分档：P5 知小项目用单体；P6 知被迫拆分时机；P7 能列拆前基础设施清单与运维前置成本。
- 红旗：上来就微服务，不知分布式运维成本。
- 惊艳点：点出"从已有单体逐步划服务比一开始微服务简单"——演进式优于推倒重来。

## 主问答
**Q（面试官原话）：** 什么时候该做微服务拆分？
**A：**
1. **先单体**：新领域业务理解不清、资源受限时，单体复杂度可控、交付快、风险低。
2. **被迫拆**：当单体过于庞大、发布慢/故障面大，才微服务化——是业务阶段产物，非起点。
3. **前置条件**：拆分前保证基础设施与公共基础服务就绪：监控快速定位故障、工具自动化部署、服务化框架降开发复杂度、灰度发布提可用、资源调度/弹性伸缩。
4. **演进式**：从单体中按业务能力逐步划服务，比"上来就微服务"风险低得多（边界见 152 选型权衡）。
