# 108 控制并发数全景（资源预算 → 池化 → 信号量 → 限流 → 分布式）

> 分类：Go 并发模型 · 全景 | 难度：L3 | 题型：深挖 | 关键词：**资源预算** / **协程池** / **信号量** / **限流** / **分布式限流**
> 原文锚点：第 1~67 段「为什么控并发 + 协程池 + 限流 + 分布式限流」

## 思路与架构
"如何控制并发数"本质是**资源预算 + 手段选型**两层问题：
1. **资源预算层**（本卡组 108-资源预算）：内存（大对象使单协程达数百 MB）/ 端口 65535 / fd 上限三类硬约束决定"必须控"。
2. **手段选型层**：
   - 控制"同时跑的协程数" → 协程池（ants 等，见 711/712）/ 信号量（chan struct{}，见 1015/105）。
   - 控制"打下游的速率" → 限流（令牌桶，见 108-rate-limiter-go）。
   - 多副本全局精准 → 分布式限流（Redis，见 108-distributed-ratelimit）。
3. 泄露预防维度见 1022（context 取消 + 超时 + 池化 + 监控）。

## 方案取舍
| 手段 | 控什么 | 适用 | 边界 |
|---|---|---|---|
| 协程池 | 同时运行协程数 | CPU/内存密集型任务 | 见 711/712（ants 实现） |
| 信号量 | 并发度（in-flight） | 轻量限流 | 见 1015/105 |
| 限流 | 请求速率 | 保护下游服务 | 见 158（架构级） |
| 分布式限流 | 全局速率 | 多副本部署 | 引入 Redis 依赖 |

## 答题技巧
- 先讲"为什么控"（资源预算三约束），再讲"控什么"（协程数 vs 请求速率），最后讲"分布式怎么办"。
- 口诀：**预算定上限、池化控并发、限流护下游、Redis 管全局**。
- 易混点：控制并发数（池化/信号量）≠ 限流（控速率）；前者管"自己开多少"，后者管"打别人多快"。
