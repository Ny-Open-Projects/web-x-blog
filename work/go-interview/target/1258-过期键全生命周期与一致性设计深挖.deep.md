# 1258 过期键全生命周期与一致性设计深挖

> 覆盖源 12-58 的延伸：过期键从「判定→删除→持久化→复制」的全生命周期状态机、主从时钟差异的冲突场景推演、Redis 为何选「主库唯一决策点」、与网关缓存 TTL 的设计对照。主卡已给规则矩阵，本附录做设计动机深挖。

## 思路与架构

```text
一个键的过期全生命周期
├─ 判定层 (主库)
│   ├─ 惰性: 访问时查 TTL, 过期才删 (省 CPU, 欠及时)
│   └─ 周期: 每 100ms 抽样 20, 过期>25% 续扫 (1256)
├─ 删除动作
│   ├─ 内存移除 + AOF 追加 DEL + 主->从广播 DEL
├─ 持久化层
│   ├─ RDB: 生成过滤 / 主库载入过滤 / 从库载入全量
│   └─ AOF: DEL 已记录 / 重写过滤过期键
└─ 复制层
    ├─ 从库: TTL 到期不删, 读 3.2+ 返回 nil
    └─ 主库 DEL 到达才物理删除 (一致性锚点)
```

## 方案取舍
- **为什么删除决策权只给主库**：TTL 判定依赖**时钟**——主从机器时钟哪怕差几百毫秒，主库判「未过期」而从库判「已过期」，两边数据视图就分叉。**把判定权收敛到主库**，从库只执行命令流（DEL 广播），复制语义退化为「命令重放」，无需任何时钟同步假设——这是用「简单一致」换「本地及时」的经典取舍。代价：从库的过期键物理残留，靠主库 DEL 或主从切换后的重新判定清理 [经验]。
- **从库读过期键的版本演变是「语义与物理分离」**：3.2 前从库返回真实值（客户端可能读到已过期数据，主从间短暂不一致可见）；3.2 起从库**读时检查 TTL，过期返回 nil**——但物理不删。**「可见性」交给读路径，「物理删除」留给主库**——两层分离后既保一致又保语义正确，是理解 Redis 主从设计的点睛案例 [经验]。
- **RDB 载入主从不对称的同一逻辑**：主库载入要「对客户端负责」，过期键必须拦；从库载入后马上被主从同步覆盖，本地判断不仅无用还可能与主库结论冲突（又是时钟差异）——**「即将被覆盖的数据不值得精确」**，全量载入反而是最优解 [经验]。
- **AOF 的 DEL 追加与重写过滤是一对闭环**：DEL 追加保证「重放 AOF 能重现删除」——否则恢复后死键复活；重写过滤保证「AOF 不为已死数据陪葬」——体积收敛。两招合起来：**历史命令流完整 + 当前状态精简**。设计上「记录动作」与「记录状态」各取所长，与 binlog 的 STATEMENT/ROW 之争同构（MySQL 视角见 123.md` 的复制过滤对照）[经验]。

## 答题技巧
- 用「生命周期状态机」开答：判定→删除→持久化→复制四段，每段一句规则——比按 RDB/AOF 平铺更有结构 [经验]。
- 杀招题「从库为什么不删」→ 主时钟唯一决策点 + 时钟差异冲突推演——设计动机层回答 [经验]。
- 主动报版本边界：3.2 前后从库读行为的差异——版本意识是 senior 信号 [经验]。
- 用类比收束：「记录动作（AOF DEL）与记录状态（重写）各取所长」——与 binlog 同构，跨域类比加分 [经验]。
- 主动边界到 `1258-redis-expire-persistence`（规则矩阵主线）、`1255-expire-deletion-choices.deep`（删除策略与从库读 3.2 边界）、`1256-periodic-scan-internals.deep`（周期扫描机制）、`1253-hybrid`（混合持久化）、`1253-aof-rewrite`（重写本体），构成「过期与持久化」专题 [边界]。
