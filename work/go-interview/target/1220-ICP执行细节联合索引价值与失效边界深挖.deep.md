# 1220 ICP 执行细节、联合索引价值与失效边界 深挖

> 覆盖源 12-20 全文：ICP 在执行器与存储层之间的交互时序、适用条件的精确清单（同索引列/无函数/非主键索引）、联合索引后缀列的价值重估、与 MRR 的配合、EXPLAIN 之外的验证手段。主卡已给机制主线与 SQL 对照，本附录做执行细节与边界四层深挖。

## 思路与架构

```text
ICP 前后的回表账本 (WHERE name > 'c' AND name LIKE '%b')
├─ 无 ICP (5.6 前)
│   ├─ 存储层: 二级索引扫描 name>'c' 全部命中 -> 逐条返回主键
│   ├─ 回表: 每条主键一次随机 IO (命中率无关, 全回)
│   └─ server 层: 逐行过滤 LIKE '%b' (大部分白回)
├─ 有 ICP (5.6+)
│   ├─ 执行器把 LIKE 条件下推给 InnoDB
│   ├─ 存储层: 索引扫描时就地用叶子的 name 值判 LIKE
│   ├─ 只对满足者回表 -> 回表数 = 范围命中 × LIKE 命中率
│   └─ EXPLAIN Extra: Using index condition
└─ 适用前提: 条件列 ∈ 当前二级索引 且 无函数/类型转换
```

## 方案取舍
- **执行器与存储层的接口视角**：MySQL 分 server 层与存储引擎层，条件过滤默认在 server 层——这要求存储层**先返回整行**（回表）。ICP 的本质是**把谓词求值的边界下沉**：执行器把「能在索引列上判定的条件」编码后传给 InnoDB，存储层在扫描二级索引时逐条求值，只回传通过者。**理解成「过滤下推到数据所在处」**——与分布式系统的「计算靠近存储」是同一设计哲学，与 HBase 谓词下推、ES query DSL 下推同构 [经验]。
- **ICP 适用的精确清单**：① 条件列必须**属于当前使用的二级索引**（索引叶子有值可判）；② 通常是**无法用于构造扫描区间的条件**（LIKE '%x'、!=、无法入区间的范围）——能入区间的条件本来就用于定位了；③ **不能跨函数/表达式**（`UPPER(name) LIKE ...` 无法下推，索引值与函数结果无关）；④ 只对**二级索引**有意义——聚簇索引本身含整行，无「回表」可省。不满足清单即失效，EXPLAIN 退化为 Using where [源码]。
- **联合索引后缀列的价值被 ICP 重估**：联合索引 (a,b) 中，`WHERE a=1 AND b LIKE '%x'` 的 b 无法参与定位（前缀等值后 b 才有序；此处 b 的 LIKE 非前缀）——**没有 ICP 时 b 列在索引里纯粹「搭车」**，还是要回表过滤；**有 ICP 后 b 的过滤在索引层完成**。推论：设计联合索引时，「虽不能参与定位但能参与过滤」的列值得放入索引尾部——ICP 让「过滤列」与「定位列」都可以在索引里发光 [经验]。
- **与 MRR（Multi-Range Read）的配合**：ICP 减少回表次数，MRR 优化剩余回表的**模式**——把二级索引扫出的主键**排序缓冲后按主键序回表**，随机 IO 变顺序 IO。两者可叠加：ICP 砍数量、MRR 改顺序，EXPLAIN 出现 `Using MRR`。**先 ICP 后 MRR** 是「减少次数 → 优化剩余次数的访问模式」的递进优化链 [经验]。
- **验证与调试手段**：① EXPLAIN 看 Extra 标志（`Using index condition` = ICP 生效；同时有 `Using index` 时说明覆盖优先）；② **开关对照实验**——`SET optimizer_switch='index_condition_pushdown=off'` 后重跑，对比 Handler 状态变量（`Handler_read_next` 与回表相关计数）量化收益；③ 大结果集才显著——命中率越高（LIKE 命中多），ICP 收益越小；命中率低时收益最大 [经验]。

- 用场景 SQL 落地：`name > 'c' AND name LIKE '%b'`，两条件一能一不能，正是 ICP 的标准戏台 [源码]。

## 细节与核心 API

**ICP 生效标志与回表账本**：

```sql
EXPLAIN SELECT * FROM t WHERE name > 'c' AND name LIKE '%b'\G
-- Extra: Using index condition  ← ICP 生效
-- 无 ICP(5.6前)：二级索引全扫逐条回表，server 层逐行过滤（大量白回）
-- 有 ICP(5.6+)：执行器把 LIKE 下推 InnoDB，索引层就地过滤，只对满足者回表
```

**开关对照实验量化收益**：

```sql
SET optimizer_switch='index_condition_pushdown=off';  -- 关闭重跑，对比 Handler_read_* 计数
SET optimizer_switch='index_condition_pushdown=on';
```

**联合索引后缀列价值重估**：`(a,b)` 中 `a=1 AND b LIKE '%x'` 的 b 无法参与定位，但 ICP 让 b 的过滤在索引层完成 → "定位列 + 过滤列"都可入索引尾部。

**与 MRR 叠加**：ICP 砍回表数量，MRR 把剩余主键排序后按序回表（随机 IO → 顺序 IO）；Extra 同时出现 `Using index condition` / `Using MRR`。

**ICP 精确适用清单**：条件列 ∈ 当前二级索引 且 无函数/类型转换 且 非聚簇索引（聚簇本身含整行无回表可省）。

> 边界：覆盖索引与 LIKE 例外见 1222；最左前缀见 1219；本卡只讲 ICP 执行细节与失效边界。
