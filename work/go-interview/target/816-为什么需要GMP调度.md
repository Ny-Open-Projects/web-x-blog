# 816 为什么需要 GMP 调度

> 分类：并发模型 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**单进程阻塞** / **N:M** / **用户态协程**
> 原文锚点：第 1~57 段「单进程阻塞浪费 CPU…携程解决内存占用与切换开销」

## 一句话总述
GMP 是为解决"单进程阻塞浪费 CPU、多线程切换/内存开销大"而生的 N:M 协程调度模型：用户态 g 多路复用到内核线程 m 上。

## 面试官视角
- 考察意图：是否理解调度模型演进的动机，而非背结论
- P5 能讲单进程→多线程→协程主线 / P6 能讲 N:M 与 1:1 的取舍 / P7 能讲 IO 密集型为何 g 更优
- 红旗：把协程说成"免费"；认为线程和 g 是同一层概念
- 惊艳点：g 初始栈仅 2KB、线程默认 ~1MB（Java），故可开百万级 g `[经验]`

## 主问答
**Q：** 为什么 Go 要搞一套 GMP，而不是直接用系统线程？
**A：**
1. **单进程痛点**：阻塞（如磁盘 IO）时 CPU 空等，利用率低 `[经验]`。
2. **多线程痛点**：每线程 ~MB 级内存、上下文切换与态切换开销大 `[经验]`。
3. **协程解法**：g 默认 2KB 栈，N:M 复用到 m，用户态切换免内核介入 `[源码]`。
**加分层：** 协程由 runtime 调度（协作），线程由 OS 抢占调度，二者不在同一层。
