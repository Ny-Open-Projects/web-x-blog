# 102 Go 并发"简单"的假象与实战雷区

> 分类：Go 并发模型 | 难度：L3 | 题型：认知题 | 频率：高 | 关键词：**go 关键字** / **资源耗尽** / **死锁** / **并发 bug 难定位** / **脏数据**
> 原文锚点：第 16~24,30~49 段「go 一行启动≠写好；需考虑协程数/上下文切换/死锁/资源/选型；并发 bug 需并发量触发、脏数据」

## 一句话总述
`go` 关键字一行启动协程、屏蔽调度底层，让"写并发"很容易，但"写好并发"很难：要兼顾**协程数控制（资源耗尽）/上下文切换/死锁/软硬件资源/原语选型**，且并发 bug 需一定并发量才触发、难定位，还产生脏数据影响业务。

## 面试官视角
- 意图：考察是否意识到并发的隐蔽成本，而非停在"go 很方便"。
- 分档：P5 知并发有坑；P6 能列雷区；P7 能讲并发 bug 特性（难复现/脏数据）并给规避。
- 红旗：以为"加个 go 就行"，对资源与死锁毫无概念。
- 惊艳点：点出"并发 bug 只在特定并发量下触发"——这是它比普通 bug 更难查的根因；实例见 1017（闭包捕获循环变量致数据错乱）。

## 主问答
**Q（面试官原话）：** 都说 Go 并发简单，难在哪？
**A：**
1. **易写难好**：`go` 屏蔽调度，一行起协程；但需自己控协程数（防资源耗尽）、防上下文切换开销、防死锁、受软硬件资源约束、做原语选型。
2. **bug 特性**：并发问题导致的 bug 只在**一定并发请求下才触发**→难以稳定复现与定位；更严重的是会产生**脏数据**，直接冲击业务。
3. **典型实例**：并发写 DB 时 for 循环迭代器元素是指针移动 + 闭包取值时刻问题，闭包最终大概率拿到最后一个 user，结果重复错乱——修复见 1017（tmp 拷贝 / 参数传值 / 不用闭包）。

## 关键代码
```go
// 示意，未验证：闭包捕获循环变量→数据错乱（详情与修法见 1017）
for _, u := range users {
    go func() { writeDB(u) }() // u 是同一变量，最终多拿到最后一个
}
// 修法：参数传值
for _, u := range users {
    go func(u User) { writeDB(u) }(u)
}
```
