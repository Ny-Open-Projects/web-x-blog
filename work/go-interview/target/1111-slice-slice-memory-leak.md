# 1111 切片截取导致的内存泄漏

> 分类：内存与 GC | 难度：L3 | 题型：事故题 | 频率：高 | 关键词：**底层数组共享** / **引用类型** / **置 nil**
> 原文锚点：第 3~20 段「截取造成内存泄漏：指针切片截取后底层不释放，需把丢失元素置 nil」

## 一句话总述
截取大切片得到小子切片时，两者**共享底层数组**；若子切片仍被引用，整块底层数组（含已"丢弃"的元素）无法被 GC 回收。对引用类型（指针/string/切片）元素，应主动把不再用到的槽位置 `nil` 以释放 `[源码]`。

## 面试官视角
- 意图：是否真懂切片"引用语义"导致的内存泄漏陷阱。
- P5 知截取共享底层数组 / P6 说清为何不释放 + 置 nil 解法 / P7 知 string 截取同样泄漏、用 `strings.Clone` 切断。
- 红旗：以为截取后就和原数组无关；以为 len 变小内存就释放。
- 惊艳点：子切片持有一处引用即可保住整块底层数组 —— 验证 `go build -gcflags=-m` go1.26.5 `[源码]`。

## 主问答
**Q（面试官原话）：** 切片截取也会导致内存泄漏？说说看。
**A：**
1. **结论**：截取产生的子切片与原切片共享底层数组；只要子切片活着，整块数组（含丢弃元素）都不回收 `[源码]`。
2. **机制**：slice header 的 `ptr` 仍指向原数组起点附近，GC 按"是否可达"判定，不按 len 裁剪。
3. **边界**：元素是**指针/string/切片**等引用时才真泄漏；值类型（int）只是浪费不泄露。解法：把不再需要的槽位置 `nil`（指针）或 `copy` 到新小数组切断引用。
**加分层：** `s = append([]T(nil), s...)` 或 `strings.Clone` 可显式断开与原大数组的共享。

## 关键代码
```go
// 示意，未验证：指针切片截取后泄漏 + 置 nil 修复
type Big struct{ data [1 << 20]byte }
src := make([]*Big, 1000) // 大底层数组
sub := src[1:3]           // 共享底层数组，整块不回收
// 修复：丢弃的元素置 nil，并切到独立小数组
sub[0], sub[1] = nil, nil
sub = append([]*Big(nil), sub...)
```

## 总结与追问预判
- 截取共享底层数组，引用类型元素需置 nil 或克隆切断。
