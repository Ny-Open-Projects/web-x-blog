# 1224 唯一性深挖：什么时候该把唯一约束从数据库挪走

> 深挖卡：从「唯一索引 vs 普通索引」推进到「唯一性该由谁保证」的架构决策。

## 思路与架构

唯一性约束可以落在四个层次，每一层的**强度与代价**不同：

```text
层 1  数据库唯一索引       强一致、绝对不重复；写入必须读盘校验（change buffer 失效）
层 2  独立幂等/去重表      强一致；把冲突检测从大表挪到一张窄表，随机读范围小得多
层 3  分布式锁 / Redis SETNX  最终一致窗口内可靠；依赖外部组件，需处理锁超时与续约
层 4  应用层先查后插      最弱（并发下有窗口）；只适合低并发或已在上游串行化的场景
```

**为什么"层 1 → 层 2"这个挪动能提性能**：唯一索引的代价不在"判重"本身，而在**判重必须命中那张又宽又大的主表/二级索引页**。把它挪到一张只有业务键的窄表后：

- 单个页能装下**几十倍**的键，buffer pool 命中率大幅提升，随机读次数骤降；
- 主表上的索引退化成**普通索引**，写入重新走 change buffer；
- 窄表本身可以用**主键**（而非二级唯一索引）承载唯一性，省掉一次回表。

代价是**多一次写入、多一个组件/表要维护**，且要保证两张表的写入在同一事务里（否则不一致）。

**为什么不能简单地"都改成普通索引"**：唯一性是**业务正确性约束**，不是性能优化项。放着不管会出现重复订单、重复券、重复账号，事后清理成本远高于一点写性能。挪动的前提是**必须有等价的兜底机制**，而不是直接删掉约束。

## 方案取舍

| 场景 | 推荐 | 理由 |
|---|---|---|
| 低频写入、写完常读（账号、手机号、邮箱） | **数据库唯一索引** | 写少读多，change buffer 本来也无收益，正确性优先 |
| 高频写入、写完很少读（流水、埋点、消息） | **普通索引 + 幂等表去重** | 避开 change buffer 失效带来的随机读风暴 |
| 跨库 / 分库分表 | **业务层全局 ID + 幂等表** | 单库唯一索引跨片无效，必须用全局唯一键 |
| 已引入 Redis 且能接受最终一致 | **SETNX / 幂等键** | 一次内存操作，注意设置过期与误删（见 `704-idempotency-design.deep`） |
| 峰值极高的唯一资源争抢（秒杀库存、限量券） | **Redis 预扣 + 异步落库** | 数据库唯一索引会成为热点瓶颈（见 `195-prevent-oversell.deep`） |
| 数据修复期、历史脏数据未清 | **先普通索引 + 后台任务去重，清完再加唯一** | 直接加唯一索引会因重复值建不起来 |

取舍原则：**唯一性约束往哪放，取决于"写入频次 × 写完是否立刻读 × 是否需要跨片"三件事**。三件事都指向数据库以外的，才值得挪走；否则一律留在数据库——**最强的正确性保障永远是最便宜的那一个**。

## 答题技巧

1. **开口先拆题，指出题目藏了前提**：「这题有两个隐藏前提——相同索引结构、相同数据集；默认都是 B+ 树，且字段值本身唯一」。先拆题再作答，展示的是严谨性，面试官会立刻提高对你的评价基线。
2. **把"查询差距"量化到可忽略**：不要说"差不多"，要说「普通索引只是**多探一次**，而一个数据页 16KB 能装大量索引项，这次探查大概率还在同一页内，加上预读，差距微乎其微」——**给出量级才是 P7 的说法**。
3. **写入差距要落到机制名**：「唯一索引**必须校验唯一性，校验必须读盘**，所以用不了 **change buffer**；普通索引可以把这次随机读推迟到真正被读时才发生」。机制名一出来，追问空间就被你占满了。
4. **工程结论要给边界**：「**写多读少**的字段慎用唯一索引」——同时必须补一句「但 change buffer 生效还要求**写完不立刻读**；写完立刻读的场景反而可以放心用唯一索引」。只说一半会被追问死。
5. **收尾给"挪走唯一性"的完整清单**：数据库唯一索引 → 幂等窄表 → Redis SETNX → 应用层先查后插，并强调**挪走的前提是必须有等价兜底，不能为了性能牺牲正确性**。这句是整道题的价值落点。
