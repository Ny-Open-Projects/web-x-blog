# 112 性能优化第一步：先定位瓶颈，再动手

> 分类：面试策略 | 难度：L2 | 题型：方法论题 | 频率：高 | 关键词：**瓶颈优先**/**慢查询**/**缓存**/**代码重构**/**并行**
> 原文锚点：第 18~30 段「定位瓶颈优先 + 慢查询优化 + 缓存 + 代码重构/并行」

## 一句话总述
性能优化的铁律是**先定位瓶颈、绝不盲试**：靠监控/慢查询日志锁定 CPU、IO、DB 等热点，再做索引/缓存/重构等针对性优化，否则方向错了白忙。

## 面试官视角
- 考察意图：是否具备「测量驱动」的工程素养，而非一上来乱加索引、乱加缓存。
- 分档：P5 知先看监控定位瓶颈；P6 能展开 DB 慢查询日志→加索引+改写、缓存热点、代码重构；P7 知常见瓶颈分类（CPU/IO/锁/内存）、知无关串行可并行化。
- 红旗答案：上来就说「加缓存、加索引」却说不清瓶颈在哪；把串行改并行却不判断是否有依赖。
- 惊艳点：强调「先让面试官认可方向对」——定位优先于手段；点出重构时**低成本条件前置、提前返回**细活 [经验]。

## 主问答
**Q（面试官原话）：** 性能优化第一步该做什么？具体有哪些手段？
**A：**
1. **第一步永远是定位，不是试**：先**用监控/火焰图锁定瓶颈**（CPU 密集、IO 密集、锁竞争等），让面试官先认可方向对再谈手段；盲试既低效又显得没章法 [经验]。
2. **DB 侧：慢查询日志 → 定位 → 改写**：通过慢查询日志**定位慢 SQL**，再用**加索引 + 改写语句**优化（避免对索引列做函数运算、减少回表）；面试官常追问 MySQL 索引与改写细节，需提前准备 [经验]。
3. **代码侧：重构 + 并行**：**多个条件时先判代价低的、不满足就提前返回**；消除不必要的循环/判断；**无相互依赖的串行操作改成并行**（多路独立 IO 用 goroutine）。缓存层对热点数据加缓存避免重复计算、减负底层（如 MySQL）[经验]。

| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
| --- | --- | --- | --- | --- |

## 版本与兼容性
- 并行化示例基于 Go 原生 `sync`/`context`，各版本通用；慢查询日志与 EXPLAIN 为 MySQL 通用能力。

## 总结与追问预判
瓶颈优先是性能题的「元方法」，和 STAR、QoS 指标组成完整回答。面试官可能把话题引向具体语言优化（Go 逃逸分析、锁优化）——可用库中 1240/1118 等卡衔接。

## ⚠️ 原文纠错
1. 事实核校： [经验] 重构里的「并行」仅适用于**无相互依赖**的操作，有依赖的串行改并行会引入竞态——正确，须谨慎。
2. 崩坏词归一：源码将若干术语音译为崩坏词，本卡统一为规范术语（瓶颈、慢查询日志、回表、提前返回、并行等）。

```go
// 低成本条件前置 + 提前返回：先排除不可能命中的情况，省后续计算
func match(u User, cond Condition) bool {
    if cond.MinAge > 0 && u.Age < cond.MinAge { // 便宜的过滤先跑
        return false
    }
    if !u.Active { // 不满足直接返回，不再进入重逻辑
        return false
    }
    return expensiveCheck(u, cond) // 仅对少量候选做重活
}

// 无依赖的串行改并行：两路独立 IO 并发拉取
func fetchBoth(ctx context.Context) (A, B, error) {
    var a A
    var b B
    var wg sync.WaitGroup
    var errA, errB error
    wg.Add(2)
    go func() { defer wg.Done(); a, errA = getA(ctx) }()
    go func() { defer wg.Done(); b, errB = getB(ctx) }()
    wg.Wait()
    return a, b, errors.Join(errA, errB)
}
```
