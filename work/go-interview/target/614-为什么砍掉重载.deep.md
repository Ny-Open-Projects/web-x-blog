# 614 为什么砍掉重载：替代方案与遮蔽语义深挖

> 覆盖源 6-14 的工程延伸：重载被拒的完整代价账、可变参数/泛型/命名分化三条替代路、嵌入遮蔽与接口分派的语义鸿沟、main 函数多态验证。主卡已给结论与两层重写，本附录做「为什么」与「怎么办」深挖。

## 思路与架构

```text
同名方法在 Go 里的三种命运
├─ 同一结构体定义两次 → 编译错误 (method redeclared)
├─ 结构体嵌入同名方法
│   ├─ 外层有实现 -> 外层遮蔽内层 (静态, 编译期)
│   ├─ 外层无实现 -> 方法提升, 走内层
│   └─ 都要触达内层 -> 显式外层.内层.方法()
├─ 接口 + 多实现
│   ├─ 各类型实现同一签名
│   └─ 经接口变量调用 -> itab 运行期分派 (真多态)
└─ 参数差异表达 (替代重载)
    ├─ 个数不同 -> 可变参数 ...T
    ├─ 类型不同 -> 泛型 [T ...] (1.18+) 或命名分化
    └─ 语义不同 -> 拆成不同方法名 (最 Go 风格)
```

## 方案取舍
- **重载的真实代价**：支持重载的语言要解决「同名多义时的最佳匹配」——重载决议规则（精确匹配 > 拓宽转换 > 装箱 > 可变参数）本身是招聘面试的坑源地，且**只看静态类型不看运行期类型**的决议常出反直觉结果。Go 的取舍是「一个名字一种行为」，把分歧暴露在方法名或类型参数上，换来的可读性收益是 grep 友好、IDE 跳转唯一 [经验]。
- **三条替代路怎么选**：**个数不同**——可变参数最自然（如 `Add(1,2,3)`），但要警惕「空参调用」与切片展开 `nums...` 的边界；**类型不同**——1.18 前只能命名分化（`AddInt/AddFloat`）或收 `interface{}`（丢失类型安全），1.18 后泛型正解；**语义不同**——果断拆名（`ParseInt` 与 `ParseFloat` 而非重载 `Parse`），标准库正是这么做的 [经验]。
- **遮蔽 vs 多态的语义鸿沟**（最容易答错的点）：嵌入遮蔽是**编译期静态分派**——`Cat{Animal{}}` 变量调 `Eat()` 永远走 Cat 版；把 Cat 以 `Animal` 身份传出（函数参数 `func f(a Animal)`），调 `a.Eat()` 走的是**被遮蔽的 Animal 版**——因为 Animal 值里根本没有 Cat 的信息。接口分派则相反：itab 记住动态类型，`Eater` 接口变量调 `Eat()` 走实际类型的版本。**「嵌入改写行为但不改写身份；接口连身份一起抽象」**一句话钉死区别 [源码]。
- **重写的正确姿势清单**：① 要多态——定义接口、各类型各自实现、经接口变量调用；② 只想复用 + 定制——嵌入遮蔽，但记住对外暴露的身份仍是各自类型；③ 想在遮蔽版本里复用内层逻辑——`c.Animal.Eat()` 显式触达后再加工。用错场景（如指望嵌入产生运行期分派）是线上「明明重写了怎么没生效」的常见根源 [经验]。

## 答题技巧
- 先用一句话立结论「不支持重载、两层支持重写」，再主动讲为什么砍——「砍掉的语法 + 保住的简单性」两面一起说 [经验]。
- 用编译错误落地：「同一结构体写两个 Add，报 method redeclared」——一句话证明不是「不建议」而是「不允许」[源码]。
- 被问「遮蔽算多态吗」→ 用「Cat 传成 Animal 调用走旧版」的反例打穿，比背定义有力 [源码]。
- 被问「没有重载难受吗」→ 报三条替代路 + 标准库 ParseInt/ParseFloat 命名分化实例，从辩护升级为方案输出 [经验]。
- 主动边界到 `615-embedding-inheritance`（嵌入与继承全景）、`615-go-oop`（Go 面向对象哲学）、`613-duck-typing-interface`（接口的鸭子类型语义），构成「Go 面向对象取舍」专题 [边界]。
