# 1238 范围查询的扫描终点：不满足条件的记录也要加锁

> 分类：数据库 / MySQL 锁 | 难度：L4 | 题型：原理题 | 频率：中 | 关键词：**扫描终止、临键锁、左开右闭、回表加锁、二级索引**

> 原文锚点：第 45~52 段「我们把条件改成 name 小于等于 name2…它命中的记录是 name1、name2…由于 name20 也被扫描到了，在进行索引扫描的时候，它会扫描到最后一条不满足条件的记录…它扫描了三条记录，其中 name1 和 name2 是命中的记录…对于这两个命中的记录，它还加了一个单纯的行锁，而且这个行锁是在主键索引上加的，而 name1 和 name2 的临键锁是在二级索引树上加的，同时也会给 name20 加一个临键锁」

## 一句话总述
范围查询的扫描会**多走一条**——一直扫到第一条不满足条件的记录才停；命中记录加二级索引临键锁 + 主键记录锁，**那条不满足条件的记录也会被加临键锁**。

## 面试官视角
P6 以为只锁命中的行；P7 必须指出**「扫描终点那条不满足条件的记录同样被加锁」**，且它被加的是临键锁（左开右闭，包含它自己的索引值），这是很多人算错锁区间的原因。

## 主问答
**Q（面试官原话）：** `WHERE name <= 'name2'` 明明只命中两条，为什么锁了三条？

1. **扫描多走一条**：索引扫描会**一直扫到最后一条不满足条件的记录**才停止 `[源码]`。
2. **本例扫描三条**：命中 name1、name2，但**还扫描了 name20**（它不满足条件） `[源码]`。
3. **命中项加两类锁**：命中的记录**在二级索引树上加临键锁**，同时**在主键索引上加单纯的行锁（记录锁）** `[源码]`。
4. **不满足项也加锁**：扫描终点的 name20 **同样被加上临键锁** `[源码]`。
5. **区间含右边界**：临键锁是**左开右闭**区间，因此该锁**包含 name20 这个索引值本身** `[源码]`。
6. **判断依据**：之所以扫到 name20 才停，是因为 name20 已不满足 `<= name2`，扫描到此终止 `[源码]`。

## 关键代码
```sql
-- name 值为 1,2,20,3,4,5,7（字符串按编码序排列）
BEGIN;
SELECT * FROM t WHERE name <= 'name2' LOCK IN SHARE MODE;
-- 扫描：name1（命中）、name2（命中）、name20（不满足，扫描到此终止）
-- 加锁：
--   二级索引 name1、name2  -> 临键锁
--   二级索引 name20        -> 临键锁（左开右闭，区间包含 name20 自身）
--   主键 id 对应命中行      -> 记录锁

-- 验证锁范围（MySQL 8.0）
SELECT INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks;
```

## 总结与追问预判
**「命中 N 条却锁了 N+1 条」是本源的经典实验**。答题时主动点出扫描终点那条记录也被锁，能直接拉开与泛泛而谈者的差距。若条件类型写错导致全表扫描，后果见同批 1238-type-conversion-lock。

## ⚠️ 原文纠错
1. 事实核校：扫描到最后一条不满足条件的记录才停、命中项二级索引加临键锁且主键加记录锁、不满足项同样加临键锁且含右边界——均与 InnoDB 行为一致 `[经验]`。
2. 补充：示例中 name 值为 1、2、20、3、4、5、7，按**字符编码序**排列，故 20 紧随 2 之后；判断「下一个值」必须按索引列的排序规则而非数值大小 `[经验]`。
3. 崩坏词归一：源码将临键锁、记录锁、主键索引、扫描等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
