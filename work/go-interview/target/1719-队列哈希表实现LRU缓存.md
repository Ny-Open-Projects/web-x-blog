# 1719 队列+哈希表实现 LRU 缓存

> 分类：算法 / 设计题 | 难度：L1~L2 | 题型：设计题 | 频率：高 | 关键词：**LRU**/**双向链表**/**哈希表**/**O(1) get/put**/**淘汰队尾**

> 原文锚点：第 1~16 段「最近最少使用…队列最大容量=缓存大小…最近访问移到队头…哈希表存键值…满了删队尾+删哈希表」

## 一句话总述
LRU = 最近最少使用淘汰：**哈希表管「找得到」（O(1) 定位）+ 双向链表管「排得出」（O(1) 移动）**。访问/写入就提到链表头，容量满时淘汰链表尾；get/put 都是 O(1)。两个动作记牢：**命中提头、满删队尾**——删尾时必须同步删哈希表，否则出现「幽灵键」。

## 面试官视角
- 意图：数据结构组合设计的第一名题——考哈希表与链表互补的直觉，以及淘汰时**双结构同步**的严谨性。
- 分档：P5 说清两结构分工；P6 写对 get/put 流程与淘汰同步；P7 能论证为什么必须双向链表（O(1) 删中间节点需要前驱指针）、对比 LFU 与 Redis 近似 LRU。
- 红旗答案：用数组/单链表实现还说 O(1)（移头是 O(n)）；淘汰队尾忘了删哈希表。
- 惊艳点：点破源实现的升级点——数组队列「移到队头」是 O(n)，生产级用 `container/list` 双向链表把移动降到 O(1)；sync.Map 用在单协程场景反而不必要 [经验]。

## 主问答
**Q（面试官原话）：** 如何使用队列和哈希表实现一个 LRU 缓存？

**A：** LRU：缓存满后淘汰「最久未被访问」的数据。结构与流程 [实测]：

1. **双结构分工**：队列（双向链表语义）容量=缓存大小，**队头=最近使用、队尾=最旧**；哈希表存 key → 节点位置，让「是否在缓存/在哪」一次定位。
2. **Put**：key 已存在 → 更新值并提到队头；不存在且已满 → **删队尾元素 + 同步删哈希表**，再把新键值对插队头并登记哈希表。
3. **Get**：哈希表查 key；未命中返回 miss；命中且不在队头 → 从队列摘下重插队头，返回值。
4. **复杂度账**：哈希定位 O(1)；**双向链表**摘除/插头 O(1)（有前驱指针），所以整体 O(1)；若用数组或单链表，移动节点要 O(n)——这是「必须双向」的根本原因。
5. **边界**：删除队尾时哈希表不同步删除，会让幽灵键永远查得到——双结构一致性是本题第一坑。

## 关键代码
```go
package main

import "fmt"

type entry struct{ key, val int }

type LRUCache struct {
	cap   int
	list  []entry      // 队头=最新、队尾=最旧（示意；生产用 container/list 双向链表）
	index map[int]int  // key → 队列下标
}

func New(capacity int) *LRUCache {
	return &LRUCache{cap: capacity, index: map[int]int{}}
}

func (c *LRUCache) Get(key int) (int, bool) {
	i, ok := c.index[key]
	if !ok {
		return -1, false
	}
	e := c.list[i] // 命中提头
	c.list = append(c.list[:i], c.list[i+1:]...)
	c.list = append([]entry{e}, c.list...)
	for j, x := range c.list {
		c.index[x.key] = j
	}
	return e.val, true
}

func (c *LRUCache) Put(key, val int) {
	if i, ok := c.index[key]; ok {
		c.list[i].val = val
		c.Get(key) // 更新后提头
		return
	}
	if len(c.list) == c.cap { // 满：淘汰队尾 + 同步删哈希表
		delete(c.index, c.list[len(c.list)-1].key)
		c.list = c.list[:len(c.list)-1]
	}
	c.list = append([]entry{{key, val}}, c.list...)
	c.index[key] = 0
	for j, x := range c.list {
		c.index[x.key] = j
	}
}

func main() {
	c := New(2)
	c.Put(1, 1)
	c.Put(2, 2)
	v, _ := c.Get(1)
	fmt.Println(v)
	c.Put(3, 3)          // 淘汰 2
	v, ok := c.Get(2)
	fmt.Println(v, ok)
	c.Put(4, 4)          // 淘汰 1
	v, _ = c.Get(1)
	fmt.Println(v)
	v, _ = c.Get(3)
	fmt.Println(v)
}
```

[实测] 输出：`1` / `-1 false` / `-1` / `3`——Get(1) 把 1 提头致 2 变最旧被 3 淘汰，Put(4) 再淘汰 1，淘汰顺序与 LRU 语义一致。

## 总结与追问预判
核心：**「命中提头、满删队尾、删尾同步删表」三句口诀 + 为什么双向链表的 O(1) 论证**。追问往对比与生产走：LRU 与 LFU 淘汰语义对比见 1259、Redis 实际用近似 LRU（采样）见 1257、MySQL Buffer Pool 的 LRU 变体（young/old 分区防全表扫污染）见 125 与 `126-buffer-pool-lists`；队列基础结构见 176、链表变体见 172。

## ⚠️ 原文纠错
1. 术语核校： [经验] 原文「latest 的 recentlyuse」应完整为 Least Recently Used（最久未使用）、LRU 音转「最新最少使用」，已归一；「双线链表」=双向链表；「QY六键值队/SYCmap」=键值对/sync.Map，不列举原词。
2. 事实核校： [经验] 原文用「sync.Map」存键值对没有必要——缓存通常在单协程或已外置锁的场景访问，普通 map 更快；sync.Map 适合读多写少的特定并发形态，选用前应说明理由。
3. 事实核校： [经验] 原文「数组实现的队列……移动到队列头部」在数组上移头是 O(n)，与「LRU 各操作 O(1)」的经典标准不符；正式答法应升级为双向链表（`container/list`），数组版只配作教学示意。
