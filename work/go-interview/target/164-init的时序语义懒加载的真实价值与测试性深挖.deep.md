# 164 init 的时序语义、懒加载的真实价值与测试性 深挖

> 覆盖源 16-4 全文：Go 包初始化的完整时序（依赖序/变量初始化/init 链）、饿汉「白占内存」的量化视角、懒汉在什么条件下才回本、单例的测试与 mock 难题、sync.Once 家族的现代形态。主卡已给选型结论与实测，本附录做初始化语义与工程决策四层深挖。

## 思路与架构

```text
Go 包初始化时序 (饿汉安全的来源)
├─ 1. 按依赖序: 被依赖包先完成全部初始化
├─ 2. 包内: 变量初始化(按依赖序) -> 各文件 init() 按文件名序
├─ 3. 全程单 goroutine 串行 -> 无竞态窗口
└─ main 之前一切就绪
懒汉回本的条件 (三者满足才值得):
├─ 初始化昂贵 (重连接/大索引构建 > 100ms 级)
├─ 有副作用 (建连接占句柄/写外部状态)
└─ 可能永不用 (可选功能路径)
否则: 默认饿汉 (包变量/init), 运行时零成本
```

## 方案取舍
- **init 时序的完整规则比「只执行一次」更细**：① **依赖序**——import 图决定包初始化顺序，被依赖者先完成；② 包内先做**变量初始化**（且按依赖关系排序，非声明序），再跑各文件的 `init()`（同包按**文件名顺序**）；③ 全程**单 goroutine 串行**——没有并发窗口，这就是饿汉「天然线程安全」的准确机制。推论：init 里 import 某包就把它的初始化成本拉进了自己的启动路径，**init 链是启动时间的隐形账本**——大量库各自 init 干重活（注册、探测、预建连接）会拖慢所有使用者 [源码]。
- **「白占内存」要算的是启动账不是内存账**：饿汉缺点常被表述为内存浪费，但单例对象本身通常不大；真正的代价是**启动时间**——初始化贵的对象在 main 之前就同步构建，拉长服务冷启动（发布/扩容/重启的恢复时间都受影响）。所以「饿汉 vs 懒汉」在高阶视角是**启动延迟 vs 首次访问延迟**的转移：饿汉把延迟付在启动，懒汉付在第一个请求——**延迟敏感的冷启动场景（FaaS/频繁扩容）偏好懒汉，常驻服务偏好饿汉** [经验]。
- **懒汉回本的三条件缺一不可**：① 初始化昂贵（毫秒到秒级）；② 有副作用（连接、句柄、外部状态——不使用就不该发生）；③ 存在「永远不用」的真实概率（可选功能）。三者全满足才值得为此引入 Once 与访问延迟。反例：普通配置对象、轻量结构体——饿汉直接建，Once 的判定位检查虽小，**认知成本与代码复杂度是真实代价** [经验]。
- **单例与测试性的冲突及出路**：全局单例天然抗拒测试——状态跨测试用例泄漏、无法注入 mock。出路按代价排序：① 接口化 + 构造注入（最干净，但偏离「单例」初衷）；② 包级变量 + 测试内替换（`var impl = realImpl`，测试里 `impl = mockImpl`，配合 t.Cleanup 还原）——Go 惯用折中；③ sync.Once 容器保留全局访问点但允许 `Once.Reset`（测试专用，慎用）。**单例的正确用法是「一个进程一份的无状态服务实例」**，一旦装了可变状态就要警惕测试与并发的双重压力 [经验]。
- **Once 家族的现代形态**：Go 1.21 起 `sync.OnceFunc(f)`、`sync.OnceValue(func() T)` 把「once + 存结果」封装成函数——懒汉单例一行搞定 `getCfg := sync.OnceValue(loadCfg)`，并发安全且类型推断自然；对比手写 `once.Do + 局部变量`，少了两个变量声明与错误传播样板。**新代码直接用 OnceValue 家族**，手写 Once 留给需要 Reset 语义的场景 [经验]。
