# 1247 深度分页优化：二级索引排序用覆盖索引两查询拆分

> 分类：MySQL/分页 | 难度：L3 | 题型：方案题 | 频率：高 | 关键词：**覆盖索引**/**两查询拆分**/**二级索引排序**/**避免回表**/**IN 主键回查**
> 原文锚点：第 49~55 段「按 name 排序用覆盖索引、第一查询只取 id、第二查询 IN 主键取全字段」

## 一句话总述
当排序键是**二级索引/类目字段**（如 `name`）而非主键时，无法用 `id > miniID` 游标，改用**覆盖索引两查询拆分**：第一查询只走覆盖索引取「排序后的前 k 个 id」（不回表），第二查询 `WHERE id IN (...)` 按主键精准回查全字段，把一次大 OFFSET 回表拆成「小覆盖 + 小回查」。

## 面试官视角
- 考察意图：是否懂覆盖索引省回表的原理，能否把「深翻页大回表」拆成两步化解 IO 放大。
- 分档：P5 知「先查 id 再查全字段」；P6 能讲清「第一查询走覆盖索引不回表、第二查询按主键 IN 回查」；P7 能量化两查询各自代价与适用边界。
- 红旗答案：把覆盖索引说成「建个索引就快」；忽略第一查询仍需 `OFFSET` 大值、只是它现在只扫索引不回表。
- 惊艳点：点出「深翻页 90% 代价在回表，拆出仅取 id 的覆盖查询后，第二查询只回查 k 行、代价恒定」 [经验]。

## 主问答
**Q（面试官原话）：** 排序不是按 id 而是按 name，深度分页怎么优化？
**A：**
1. **根因同构**：深翻页主要慢在「前 m 行都要回表取全字段」，排序键为二级索引时同样成立，只是不能再靠 `id > miniID` 游标 [经验]。
2. **覆盖索引取 id**：第一查询只 `SELECT id`，排序/过滤走二级索引（覆盖索引）直接出「排序后前 k 个 id」，**全程不回表**，把最大头的回表 IO 砍掉 [经验]。
3. **IN 主键回查全字段**：拿到的 k 个 id 用 `WHERE id IN (...)` 按主键精准回查全字段，第二查询只回查 k 行、代价恒定，与翻页深度无关 [经验]。

## 总结与追问预判
两查询拆分的本质是「把一次深 OFFSET 的全字段回表，拆成一次只取 id 的覆盖索引扫描 + 一次 k 行主键回查」。代价从 O(m+n) 回表降到 O(索引扫 m + k 回查)。注意第一查询仍需大 OFFSET（只扫索引），若需极致可叠加「上一页末 name+id 复合游标」进一步去 OFFSET。

## ⚠️ 原文纠错
1. 事实核校： [经验] 深翻页主要代价在回表、覆盖索引只取 id 不回表、IN 主键回查全字段——均正确。
2. 崩坏词归一：源码将若干术语音译为崩坏词，本卡统一为规范术语（覆盖索引、二级索引、回表、主键、排序键等）。

```sql
-- 场景：按 name 排序的深翻页（LIMIT m, n，m 很大）
-- 原慢 SQL：SELECT * FROM user ORDER BY name LIMIT 1000000, 10;  -- 前 100 万行全回表

-- ① 第一查询：只走覆盖索引取「排序后前 k 个 id」，不回表
SELECT id
FROM   user
ORDER  BY name, id          -- 二级索引 + 主键保稳定序
LIMIT  1000010;             -- 仍要 OFFSET，但只扫索引、不回表取全字段

-- ② 第二查询：用上游 k 个 id 按主键精准回查全字段，只回查 k 行
SELECT id, name, age, addr
FROM   user
WHERE  id IN (?, ?, ?, ?, ?, ?, ?, ?, ?, ?);  -- 上一步得到的 k 个 id
```
