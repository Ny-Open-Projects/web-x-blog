# 129 查询缓存与 MySQL 架构深挖

## 思路与架构
- **查询缓存全生命周期**：以 SQL 文本哈希为 key → 查找 → 命中直返（跳过解析/优化/引擎）/ 未命中走执行 → 回填缓存 → **表级失效**（该表任何写清空全部关联缓存）。它是叠加在引擎缓冲之上的 **Server 层缓存**，落点随引擎而异（MyISAM→OS cache，InnoDB→buffer pool）。
- **8.0 移除的五大动因**：① 命中率低（key=文本哈希、空间固定、重复概率低）；② 极易失效（表级失效、只适合读多写少）；③ 管理开销（未命中仍写缓存，最坏 +13%）；④ 性能不可预测（延迟方差大，稳定比峰值重要，类比 B+ 树选型）；⑤ 业务级缓存（Redis/memcached/本地）更灵活且不占 MySQL 资源。5.7.20 默认禁用、8.0 彻底移除。
- **MySQL 四层架构**：网络连接层（连接器/连接池，连接池在客户端）、服务层（NoSQL/SQL 接口、解析器、优化器、缓存）、存储引擎层、文件系统层。长连接省建连但临时内存挂在连接对象上、断开才释放 → 涨内存；解法：定期重连或 5.7+ `mysql_reset_connection`。
- **服务层优化器职责**：解析 SQL → 应用重写（子查询/连接重排）→ 选索引（评估代价）→ 定多表连接顺序 → 生成并评估执行计划；统计信息（页数/基数/索引分布）由**引擎层**提供。

## 方案取舍
- **查询缓存 vs 业务缓存**：查询缓存粒度=表，失效粗暴、收益不确定；业务缓存粒度=key、可按热点精准控制、不挤占 MySQL——后者全面胜出。
- **长连接 vs 短连接**：长连接省建连但占内存，短连接干净但建连贵；折中是"长连接 + 定期 reset_connection"。

## 答题技巧
1. **先答"为什么移除"五点**，用"命中率低/表级失效/开销/抖动/有替代"串成一条因果链。
2. **强调表级失效是致命伤**——这是它区别于 Redis 的根本。
3. **反直觉点**：① key 是 SQL 文本哈希（注释不同都不命中）；② 分区表自动禁用查询缓存；③ `query_cache_type=0` 不释放已分配缓冲；④ 未命中也要付写缓存成本。
4. **架构四层张口即来**，并澄清"连接池在客户端、连接器在服务端"。
5. **版本锚点**：5.7.20 默认禁用、8.0 彻底移除；`mysql_reset_connection` 自 5.7.3；优化器统计信息始终来自引擎层。

## 细节与核心 API

**查询缓存相关变量（8.0 已彻底移除，仅 5.7 及更早可见）：**

```sql
SHOW VARIABLES LIKE 'query_cache_type';  -- 0=OFF 1=ON 2=DEMAND
SHOW VARIABLES LIKE 'query_cache_size';  -- 固定分配，type=0 也不释放
-- 8.0 直接报 Unknown system variable：query cache 已从代码树删除
```

**长连接内存治理（连接池在客户端，临时内存挂在连接对象上断开才释放）：**

```sql
-- 5.7.3+ 重置连接：释放临时内存/回滚事务，但保留连接与认证，不重建握手
mysql_reset_connection();
```

```go
// Go 侧用连接池复用长连接，避免频繁建连；但需设存活上限防内存堆积
db.SetMaxOpenConns(50)
db.SetMaxIdleConns(10)
db.SetConnMaxLifetime(time.Minute * 30) // 到期回收，等价于被动 reset_connection
```

**四层架构落点速记**：网络连接层（连接器/连接池，**连接池在客户端**) → 服务层（SQL 接口/解析器/优化器/查询缓存，缓存在 Server 层）→ 存储引擎层（InnoDB buffer pool）→ 文件系统层。优化器所需统计信息（页数/基数/索引分布）由**引擎层**提供。
