# 1015 互斥锁 vs channel 锁：基准测试差 3 倍

> 分类：并发模型 | 难度：L3~L4 | 题型：性能题 | 频率：高 | 关键词：**基准测试、ns/op、快速路径、CAS、自旋、饥饿模式**

> 原文锚点：第 18~30 段「使用 Go 自带的互斥锁实现，耗时是平均每次操作二十四纳秒，而使用 channel 实现的互斥锁，平均每次操作是七十六纳秒」

## 一句话总述
同样的自增临界区，**标准库互斥锁约 19 纳秒、channel 锁约 62 纳秒**，差约 **3 倍**；因为通道内部本身也要加锁，而互斥锁有 CAS 快速路径与自旋/饥饿模式优化。

## 面试官视角
P6 答"互斥锁更快"；P7 要给出**数量级**并说清原因：通道是通用通信结构、**内部自带锁与队列**，用它当锁等于绕一层 `[源码]`。加分点：互斥锁的快路径只需一次 CAS 成功即拿到锁，还有正常/饥饿两种模式控制是否自旋 `[经验]`。

## 主问答
**Q（面试官原话）：** 用 channel 当锁性能怎么样？和标准库互斥锁比呢？

1. **实测结论**：本机 12 逻辑 CPU、`go test -bench` 跑同一段自增，互斥锁 **19.48 ns/op**、channel 锁 **62.00 ns/op**，后者约为前者的 **3.2 倍** `[实测]`。
2. **两者都零分配**：两种实现的内存分配均为 0 B/op、0 allocs/op，差距纯粹来自**执行路径**而非内存分配 `[实测]`。
3. **通道自带锁**：channel 本身的实现就需要加锁，还要维护发送/接收等待队列，用它当锁等于在锁外面再套一层 `[源码]`。
4. **互斥锁有快路径**：加锁先尝试一次 CAS，成功就直接拿到锁；失败才进入慢路径，按正常模式自旋或在饥饿模式下排队 `[源码]`。
5. **模式切换是关键**：标准库会依据等待时长在正常模式与饥饿模式之间切换，并对自旋次数做限制，这些优化都是为锁场景专门做的 `[经验]`。

## 关键代码
```go
func BenchmarkMutex(b *testing.B) {          // 19.48 ns/op  0 B/op  0 allocs/op
	var mu sync.Mutex
	for i := 0; i < b.N; i++ {
		mu.Lock()
		counter++
		mu.Unlock()
	}
}

func BenchmarkChanLock(b *testing.B) {       // 62.00 ns/op  0 B/op  0 allocs/op
	m := NewChanMutex()                      // 容量 1 的 channel 当锁
	for i := 0; i < b.N; i++ {
		m.Lock()
		counter++
		m.Unlock()
	}
}
```
> 验证：`go test -bench=. -benchmem` 在同机输出上述两组数字，比值约 3.2 `[实测]`。

## ⚠️ 原文纠错
1. 事实核校：原文"互斥锁 24 纳秒、通道锁 76 纳秒"方向正确；本机实测为 **19.48 / 62.00 ns/op**（12 核、Go 1.26.5），比值同样约 3 倍，**结论可复用但数字随机器变化** `[实测]`。
2. 易混点：原文"通道锁性能更差"的原因说成"实现复杂"不够具体，准确原因是**通道内部本身要加锁且要维护等待队列** `[源码]`。
