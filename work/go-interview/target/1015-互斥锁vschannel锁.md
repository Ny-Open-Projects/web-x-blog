# 1015 互斥锁 vs channel 锁：基准测试差 3 倍

> 分类：并发模型 | 难度：L3~L4 | 题型：性能题 | 频率：高 | 关键词：**基准测试、ns/op、快速路径、CAS、自旋、饥饿模式**

> 原文锚点：第 18~30 段「使用 Go 自带的互斥锁实现，耗时是平均每次操作二十四纳秒，而使用 channel 实现的互斥锁，平均每次操作是七十六纳秒」

## 一句话总述
同样的自增临界区，**标准库互斥锁约 19 纳秒、channel 锁约 62 纳秒**，差约 **3 倍**；因为通道内部本身也要加锁，而互斥锁有 CAS 快速路径与自旋/饥饿模式优化。一句话背法：**「互斥锁比 channel 锁快约 3 倍，因 channel 内部自带锁与队列」**。

## 面试官视角
- **P6**：答"互斥锁更快"。
- **P7**：要给出**数量级**并说清原因：通道是通用通信结构、**内部自带锁与队列**，用它当锁等于绕一层。加分点：互斥锁的快路径只需一次 CAS 成功即拿到锁，还有正常/饥饿两种模式控制是否自旋。

## 主问答
**Q（面试官原话）：** 用 channel 当锁性能怎么样？和标准库互斥锁比呢？

**先铺垫（由浅入深第 1 层）**：两者都能保护临界区实现互斥，但"能不能用"和"快不快"是两问；要回答性能必须上基准测试。

1. **实测结论（第 2 层）**：本机 12 逻辑 CPU、`go test -bench` 跑同一段自增，互斥锁 **19.48 ns/op**、channel 锁 **62.00 ns/op**，后者约为前者的 **3.2 倍**。
2. **两者都零分配（第 3 层）**：内存分配均为 0 B/op、0 allocs/op，差距纯粹来自**执行路径**而非分配。
3. **通道自带锁（第 4 层）**：channel 实现本身就需要加锁，还要维护发送/接收等待队列，用它当锁等于在锁外面再套一层。
4. **互斥锁有快路径（第 5 层）**：加锁先尝试一次 CAS，成功就直接拿到；失败才进慢路径，按正常模式自旋或在饥饿模式排队。
5. **模式切换（第 6 层）**：标准库据等待时长在正常/饥饿模式间切换，并限制自旋次数——这些优化都是为锁场景专门做的。

## 关键代码
```go
package bench

import (
	"sync"
	"testing"
)

var counter int64

func BenchmarkMutex(b *testing.B) { // 约 19.48 ns/op  0 B/op  0 allocs/op
	var mu sync.Mutex
	for i := 0; i < b.N; i++ {
		mu.Lock()
		counter++
		mu.Unlock()
	}
}

func BenchmarkChanLock(b *testing.B) { // 约 62.00 ns/op  0 B/op  0 allocs/op
	m := NewChanMutex() // 容量 1 的 channel 当锁（见 1015 channel 互斥锁）
	for i := 0; i < b.N; i++ {
		m.Lock()
		counter++
		m.Unlock()
	}
}
```
> 运行：`go test -bench=. -benchmem`。同机输出上述两组数字，比值约 3.2。

## 总结与追问预判
**背这三句就够**：① **互斥锁比 channel 锁快约 3 倍**；② **channel 内部自带锁与队列**；③ **互斥锁有 CAS 快路径 + 正常/饥饿模式**。
**预判追问**：
- 「那什么时候仍该用通道？」→ 需要"传递数据/所有权"或扇出扇入时，channel 是语义正确的选择，仅为互斥才选锁（见 1015 互斥锁 vs channel 锁）。
- 「饥饿模式干嘛的？」→ 防止尾部 goroutine 长期拿不到锁，等待超阈值后转排队模式保证公平。
- 「CAS 失败呢？」→ 进入慢路径，按模式自旋或排队，不忙等死循环。

## ⚠️ 原文纠错
1. 事实核校：原文"互斥锁 24 纳秒、通道锁 76 纳秒"方向正确；本机实测 **19.48 / 62.00 ns/op**（12 核、Go 1.26.5），比值同样约 3 倍，**结论可复用但数字随机器变化**。
2. 易混点：原文"通道锁性能更差"的原因说成"实现复杂"不够具体，准确原因是**通道内部本身要加锁且要维护等待队列**。
3. 崩坏词归一：源码将 channel、goroutine、互斥锁、基准测试等术语音译为多组崩坏词，本卡统一为规范术语。
