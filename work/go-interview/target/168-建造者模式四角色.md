# 168 建造者模式四角色：指挥者、构建验证与经典实现

> 分类：设计模式 / 创建型 | 难度：L2 | 题型：原理题 | 频率：中 | 关键词：**分步构建**/**四角色**/**指挥者**/**构建验证**/**链式调用**
> 原文锚点：第 1~27 段「建造者模式主要用于解决复杂对象的构建问题…将对象的构建过程和它的表示进行分离，同样的构建过程可以创建不同的表示…基本结构包括产品、抽象的建造者、具体的建造者、指挥者四个角色…可以在构建过程中添加验证逻辑」

## 一句话总述
建造者模式解决的是「**复杂对象的分步构建**」：把多步骤、多可选件、有依赖关系的构建过程从构造函数里拆出来——**四角色**（Product 产品 / Builder 抽象接口 / ConcreteBuilder 具体实现 / **Director 指挥者**定构建顺序）各司其职；Go 里的地道形态是**链式调用 + `Build()` 收口验证**，让非法配置在构建完成时才被拦截并返回明确错误。

## 面试官视角
- 考察意图：不只问「什么是建造者」，而是看你是否理解**每个角色为什么存在**——尤其指挥者（定流程）与构建验证（不变量守门）这两处，多数候选人只会背「分步构建」。
- 分档：P5 能说出「参数多用建造者」；P6 讲清四角色与「同样构建过程创建不同表示」；P7 能对比经典 Builder 与函数式 Options 的适用边界、并强调 Build 时校验不变量。
- 红旗答案：把建造者说成「就是链式调用语法糖」；四角色背得出但说不清指挥者存在的意义。
- 惊艳点：「**Builder 的隐藏价值是把校验时机从『构造瞬间』推迟到『构建完成』**——分步设置过程中的中间态允许暂时非法，`Build()` 收口时一次性校验不变量」，配实测 [实测]。

## 主问答
**Q（面试官原话）：** 建造者模式主要用来解决什么问题？
**A：**
1. **复杂构建的分解**：对象包含多个部件（如 partA/partB/partC）、多步骤设置时，建造者把构建过程**分解成清晰的步骤方法**，代码更易读易维护——这是「分离构建过程与表示」的第一层含义 [源码]。
2. **灵活性与选择性设置**：调用方只设置关心的参数，其余走默认；新增配置不破坏既有调用——与函数式 Options 解决的是同一类「参数爆炸」问题（Options 形态见 162 [边界]） [源码]。
3. **参数列表与复用**：避免构造函数十几连参数；**同一建造者可复用于构建多个同类型产品**，构建流程沉淀在建造者里而非散落各调用点 [源码]。
4. **四角色结构**：① **Product**——被构建的复杂对象；② **抽象 Builder**——定义构建各部件的接口；③ **具体 Builder**——实现接口、持有半成品、提供取产品方法；④ **指挥者 Director**——用 Builder 接口**定构建顺序与流程**（如「必须先建 A 再建 B」）。「同样过程建不同表示」正是靠 Director 复用流程、换 ConcreteBuilder 实现达成的 [源码]。
5. **构建验证是隐藏考点**：允许在构建过程中**添加验证逻辑，确保对象构建完成时处于有效状态**——Go 里的地道实现是链式方法返回 `*Builder`、`Build()` 收口时校验不变量（端口范围、必填项），非法即返回 error。实测：`Port(70000)` 的非法构建被 `Build()` 拦截，报 `invalid port 70000` [实测]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |

| 函数式 Options | `func(*T)` 闭包合并配置（见 162 [边界]） | 轻量配置首选，代价是闭包分配与无必填校验 |

## 关键代码
```go
// Go 地道 Builder: 链式调用 + Build() 收口校验不变量
type Builder struct{ s Server }

func NewBuilder() *Builder { // 默认值先行
	return &Builder{s: Server{host: "0.0.0.0", port: 8080, maxConn: 100}}
}
func (b *Builder) Host(h string) *Builder { b.s.host = h; return b }
func (b *Builder) Port(p int) *Builder    { b.s.port = p; return b }
func (b *Builder) TLS() *Builder          { b.s.tls = true; return b }

func (b *Builder) Build() (Server, error) { // 构建完成时统一校验
	if b.s.port <= 0 || b.s.port > 65535 {
		return Server{}, fmt.Errorf("invalid port %d", b.s.port)
	}
	return b.s, nil
}
// [实测] 合法构建: {host:10.0.0.1 port:9090 maxConn:100 tls:true} err=<nil>
//        非法构建: err = invalid port 70000 —— 中间态自由, 收口拦截
```

## 总结与追问预判
一句话记忆：**「分步构建、收口验证：四角色分工，指挥者定流程，Build() 守不变量」**。函数式 Options 的工程化形态与代价见 162；strings.Builder 的性能场景（名字相似、动机不同）见 904 [边界]。常追问「指挥者在 Go 里还要不要」——答：Go 少用抽象接口体系，Director 的「流程固化」价值常由封装函数承担；再追问「Builder 和 Options 何时互斥」——答配置少且无强校验用 Options，配置多、有依赖约束、需要 Build 校验时上 Builder，两者可共存（Options 设值 + Build 校验）。

## ⚠️ 原文纠错
1. 术语归一：[经验] 源为语音转写，「非常复杂和构易管理」应为「复杂和难以管理」，「建造者结口」应为「建造者接口」，其余术语音译崩坏词统一为规范术语。
