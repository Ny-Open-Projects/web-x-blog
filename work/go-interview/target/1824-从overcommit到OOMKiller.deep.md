# 1824·深 从 overcommit 到 OOM Killer：超额申请这台机器是怎么算账的？

> 分类：操作系统 / 内存管理 | 难度：L4 | 题型：原理题 | 频率：中 | 关键词：**overcommit**/**OOM Killer**/**oom_score**/**swap**/**cgroup**/**惰性分配**/**RSS vs VSZ**
> 原文锚点：第 26~32 段「物理内存是否充足，会不会影响进程的内存申请，需要根据实际的条件具体来看…假设这 8G 的虚拟内存被访问了，就要看系统有没有 swap 分区，如果系统没有 swap 分区，就会因为物理内存不够，进程会被操作系统杀掉，也就是出现了内存溢出 OOM」
> [边界] 本文是 `1824-alloc-8g-on-4g-machine` 的深挖，主卡已讲的三层判定链此处不重述；页表与地址转换见 811，排查工具见 1810。

## 思路与架构

把"4G 机器申请 8G"拆成**三个独立的账本**：

```text
账本一：地址空间账（虚拟层）
    32 位 x86    用户态 ~3G    → 申请 8G 根本开不出这张票，直接失败
    64 位 x86-64 用户态 ~128TB → 开得出票，申请必然成功
    判据：只看位数与内核划分，与物理内存无关

账本二：承诺账（overcommit 策略层）
    内核要不要"允许承诺超过实际拥有"？
    启发式（默认）：明显离谱的申请才拒绝，其余放行
    总是允许：一律放行，风险后置到访问阶段
    严格：承诺量 ≤ swap + 可分配物理内存，超额即拒绝
    ⇒ 这一层决定"申请那一刻会不会被拒"

账本三：兑现账（访问层）
    缺页异常 → 内核必须此刻拿出物理页框
    拿得出：分配、建映射、继续跑
    拿不出：先换页到 swap；swap 也没有 → OOM Killer 介入选进程杀掉
    ⇒ 这一层决定"跑起来之后会不会死"
```

三条推导链：

1. **为什么内核敢超额承诺**：统计上**大多数程序申请了不用**（预留缓冲、稀疏数据结构）。允许 overcommit 能显著提高内存利用率——代价是**把"分配失败"这个可预期错误，变成了"运行中被杀"这个不可预期故障**。
2. **为什么 OOM 不是"申请者死"**：OOM Killer 按 **`oom_score`** 打分选人——**占用内存越多分越高**，但**关键系统进程与管理进程会被保护**，还可以通过 `oom_score_adj` 手工调整。所以"谁申请得多谁死"只是粗略直觉，真实策略是**牺牲最"划算"的那个进程来保住整机**。
3. **为什么容器里行为不一样**：cgroup 有**自己的内存 limit**，它**独立于宿主机的 swap 与总量**。容器进程超限会被 cgroup 层面的 OOM 杀掉，**哪怕宿主机还有大把空闲内存**——这是 K8s 上最常见的"明明机器很空却 OOM"的根因。

## 方案取舍

```text
要不要开 swap？
──────────────────────
开 swap
  优：给超额使用留缓冲；让"冷页"有地方去，反而提升热数据命中率
  劣：一旦开始换页，延迟从百纳秒级掉到毫秒级（数量级退化）
  结论：桌面/通用服务器**建议开**；延迟敏感的数据库、缓存节点**建议关或极小**

不开 swap
  优：内存压力立刻暴露为 OOM，故障信号清晰，不会"活着但慢死"
  劣：没有缓冲余量，瞬时峰值直接杀进程
  结论：对延迟 SLA 严格的服务（Redis / ES / MySQL）常见选择

调 overcommit 策略
  严格模式：适合"宁可申请失败也不要运行中被杀"的场景（金融、数据库）
  启发式（默认）：通用服务器的最佳平衡
```

- **"有 swap 就能用 8G"的隐性代价**：源码这句话没错，但**没说速度**。8G 里若只有 2G 是热数据、6G 被换到磁盘，程序**能跑但每访问一次冷页就是一次磁盘 IO**——**"能正常运行"和"能正常服务"是两回事**。
- **观测口径要分清**：`VSZ`/`VIRT` 是**虚拟地址空间**（含未兑现的承诺），`RSS`/`RES` 才是**当前真正占用的物理内存**。**判断内存压力只能看 RSS**，看 VSZ 会被 overcommit 严重误导。
- **Go 程序的特殊之处**：`make([]byte, N)` 会**立即清零**，等于**立刻触碰所有页**——所以 Go 里你**看不到 C 那种"申请免费"的假象**，RSS 会同步涨上去（实测 `HeapSys` 立刻到 1056384 KB）。**这既是好事（故障早暴露），也意味着 Go 程序更容易在申请瞬间就把 RSS 顶高**。

## 答题技巧

- **开口先分三个账本**，再逐个判定。这个框架能让你在追问中不乱阵脚。
- **一定要带 RSS 实测**：`mmap` 后 **2716 KB** → 写遍后 **1051476 KB** → `munmap` 后 **3188 KB**。三组数字是"惰性分配"最干净的证据，比任何比喻都有力。
- **主动点出 Go 与 C 的差异**：「Go 的 `make` 会清零，所以看不到惰性；要演示必须用裸 `mmap`。」——这句话能证明你真的跑过。
- **把容器场景补上**：K8s 上"宿主机很空却 OOM"是高频故障，根因是 **cgroup limit 独立于 swap**。主动讲这个，直接体现生产经验。
- **别踩的坑**：① 别只说"会 OOM"——64 位下申请一定成功；② 别把 VSZ 当真实占用；③ 别忽略 `oom_score` 的选人逻辑，被杀的不一定是申请最多的那个。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Linux 2.6+ | overcommit 三档策略可用 | 默认启发式 |
| Linux 全版本 | OOM Killer 按 `oom_score` 选人 | 可用 `oom_score_adj` 保护关键进程 |
| cgroup v1 / v2 | 容器内存 limit 独立 | 超限即 OOM，与宿主机无关 |
| 32 位 / 64 位 | 用户态上限 ~3G / ~128TB | 申请阶段的判定依据 |
| 实测 macOS / go1.26.5 | `mmap` 惰性、Go `make` 立即清零 | 演示须用裸 `mmap` [实测] |

## 细节与核心 API

```bash
cat /proc/sys/vm/overcommit_memory
#  0 = 启发式（默认，允许适度超卖）
#  1 = 总是允许（危险，易触发 OOM）
#  2 = 严格：提交总量不超过 swap+RAM*overcommit_ratio
cat /proc/sys/vm/overcommit_ratio
dmesg | grep -i "killed process"   # OOM 发生时记录被杀进程与内存快照
# 调优：关键服务加 oom_score_adj（-1000 几乎不被杀）
echo -500 > /proc/<PID>/oom_score_adj
# 现象：malloc 成功但访问时触发 OOM Killer（因 overcommit，物理页真的不够才杀）
# 防护：设 overcommit_memory=2 + swap + 限制 cgroup 内存，避免整机雪崩
```
