# 705 Web 框架选型三原则

> 分类：Go Web 生态 | 难度：L3 | 题型：设计题 | 频率：中 | 关键词：**业务优先** / **团队储备** / **交付时间** / **先上线再迭代**
> 原文锚点：第 44~53 段「选型三原则：满足业务需求为前提、考虑团队人力资源、考虑交付时间」

## 一句话总述
框架选型三原则优先级：**业务需求 > 团队技术储备 > 交付时间**。先满足业务再谈性能/成本/安全；优先选团队有储备的；互联网项目周期短就选上手快、能先上线的，再逐步迭代。Beego 这类全功能、门槛低的框架适合紧急项目。

## 面试官视角
- 考察意图：会不会"为技术而技术"、能不能结合团队与排期做务实选型
- P5 能说"看业务"；P6 能列三原则并排优先级；P7 能结合具体场景（紧急项目选 Beego、高并发选 Gin/Fiber）给理由
- 红旗：只比性能参数、不顾团队是否会用；说"性能最高就是最好"
- 惊艳点：点出"先快速上线再迭代优化"的互联网节奏，以及"选型要兼顾团队储备缩短周期" [经验]

## 主问答
**Q（面试官原话）：** 实际项目里怎么选 Web 框架？
**A：**
1. **第一原则·业务优先**：先确认框架能否满足当前业务需求，在此前提下才考虑性能、成本、安全、稳定性；有些选型诉求本身就是降本/提性能/安全驱动 [经验]。
2. **第二原则·团队储备**：优先选团队**已有经验**的框架，缩短开发周期、保障运维稳定——这是隐性成本大头 [经验]。
3. **第三原则·交付时间**：互联网项目交付周期短、要快速验证市场；没时间慢慢学就选实现周期最短的，**先快速上线再逐步迭代**；Beego 全功能、入门低，紧急项目优先 [经验]。

## 关键代码
```go
// 选型落地示例：用 Gin 快速起一个业务 handler（团队有 Gin 储备时优先）
func RegisterUser(r *gin.Engine, svc UserService) {
    r.POST("/users", func(c *gin.Context) {
        var req CreateUserReq
        if err := c.ShouldBindJSON(&req); err != nil { // Gin 绑定，储备够则快
            c.JSON(400, gin.H{"err": err.Error()}); return
        }
        c.JSON(200, svc.Create(req))
    })
}
```

## ⚠️ 原文纠错
源码将若干术语音译为崩坏词，本卡统一为规范术语（外部框架→Web 框架、技术站→技术栈、全占→抢占/验证市场等）；技术结论未做事实性更正 [经验]。
