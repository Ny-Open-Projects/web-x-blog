# 1414 有序性方案的倾斜、扩容与端到端幂等 深挖

> 覆盖源 14-14 全文：key 路由方案的三类副作用（倾斜/扩容重排/分区数上限）、热点加盐的正确姿势、内存队列模型的容量与丢失风险、有序性与幂等的配套关系。主卡已给方案主线与代码，本附录做边界与配套四层深挖。

## 思路与架构

```text
端到端有序链路 + 各环节风险
├─ 生产端: key=业务ID -> 哈希分区
│   ├─ 风险1: 热点 key 倾斜 -> 单分区瓶颈
│   └─ 风险2: 扩分区 -> 取模基数变 -> 同 key 换分区
├─ Broker: 分区内 FIFO (恒定保证)
├─ 消费端: 分区 -> 消费者 一对一 (见 147)
└─ 异步处理: key 二次哈希 -> 固定内存队列 -> 串行
    ├─ 风险3: 队列内存无界 -> 背压/限流
    └─ 风险4: 进程崩溃队列丢失 -> 需幂等兜底
配套: 任何「换分区/换队列/重试」扰动都靠消费幂等收尾
```

## 方案取舍
- **倾斜是哈希路由的阿喀琉斯之踵**：按用户 ID 哈希在用户量均匀时表现良好，但**热点用户/大商户**会把单分区打成瓶颈——分区再多也无用（同一 key 恒落同一分区）。缓解：① **加盐拆分**——key = ID + 随机后缀（0~N-1），把热点拆到 N 个分区，有序性在「ID+后缀」粒度保证，最终态由业务用**版本号/时间戳**裁决；② 路由前做 key 统计预热，显式热 key 表定向调度。没有免费午餐——**加加盐牺牲的就是局部有序**，要靠业务语义补 [经验]。
- **扩分区是有序性的隐形杀手**：`hash(key) % partitionCount` 的基数一变，**绝大多数 key 会被重新映射到新分区**——扩容瞬间，「同一 ID 的历史消息在旧分区、新消息在新分区」跨分区错位，局部有序被打破。工程对策：① 扩容前**停写窗口**或双写过渡，等旧分区消费完再切；② 上游消息带**单调版本号/时间戳**，消费端幂等裁决——这把「传输层保序」降级为「应用层去重」，是扩容窗口的兜底保险 [经验]。
- **内存队列模型的两笔账**：**容量账**——固定队列数 = 处理协程数，同一 key 恒进同一队列，但队列长度无界时内存膨胀，要配**背压**（队列满阻塞 poll 或限流）；**丢失账**——进程崩溃时队列内未处理消息丢失，等下次重平衡重新分配分区后从位移重拉，所以**队列只是重排器不是存储**，可靠性完全依赖位移提交与幂等消费。这两笔账决定：内存队列适合「处理快于生产」的场景，慢消费场景要先扩分区而不是堆队列 [经验]。
- **有序与幂等是配套而不是替代**：很多人把「上幂等」当有序性的替代品——错了。**幂等解决「重复执行」，保序解决「乱序执行」**，同一 ID 的「删除」先于「更新」到达时，幂等救不了最终态。正确组合：传输层尽力保序（key 路由）+ 应用层幂等兜底（重复/重排后的最终态裁决，用版本号单调性判断）。**「带版本号的事件」是分布式消息的终极防御**，成本是业务消息结构化 [经验]。
- **全局有序的真实代价**：单分区方案唯一的优点是「绝对有序」，代价是：① 吞吐上限 = 单分区单消费者的处理能力；② 无并行冗余，消费者挂了整条链路停摆（重平衡也救不了单分区单实例的容量）；③ 水平扩展失效。真实系统几乎总是「按业务维度局部有序」——订单按订单 ID、用户按用户 ID、账户按账户 ID，**有序的粒度跟着业务一致性边界走**，而不是跟着技术手段走 [经验]。

## 答题技巧
- 先还原乱序现象（昵称三次修改），再给方案主线（key 路由 → 分区有序 → 内存队列），最后主动抛副作用（倾斜/扩容）——现象→方案→代价的三段式 [经验]。
- 强调 key 的选择：「业务 ID 不是消息 ID」，一句话区分「有用路由」与「无效路由」 [经验]。
- 被问「热点怎么办」→ 加盐拆分 + 版本号裁决，说清「拆了就丢局部有序」的代价 [经验]。
- 被问「为什么不直接全局有序」→ 单分区的三个代价 + 「有序粒度跟业务一致性边界走」 [经验]。
- 主动边界到 `147-consumer-rebalance`（分区-消费者映射）、`1409-avoid-rebalance`（重平衡扰动期间的顺序风险）、`1417-producer-acks`（可靠性与顺序的叠加配置），构成消息可靠性专题 [边界]。
