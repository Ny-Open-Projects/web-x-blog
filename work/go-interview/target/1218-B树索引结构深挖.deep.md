# 1218 B+ 树索引结构（深挖）

> 分类：MySQL 索引 | 难度：中高 | 题型：原理深挖 | 频率：高 | 关键词：**B+树、聚簇索引、非聚簇索引、页、磁盘IO、范围查询**

> 原文锚点：第 1~98 段「索引磁盘本质、各结构对比、B+ 树优势、AHI」

## 思路与架构
理解 B+ 树要分三层：
- 物理层：数据按「页」（默认 16KB）存磁盘，IO 以页为单位，一次读一页及其相邻页进内存。
- 结构层：B+ 树非叶只存「目录项（键值 + 子页指针）」，叶子存「真实记录页」并用双向链表相连；同页能放更多目录项 → 树矮胖 → 层数少 → IO 少。
- 查询层：单点查从根逐层下行到叶子（层数 = IO 次数）；范围查在叶子链表上顺序扫，无需回退。

## 方案取舍
- 选 B+ 而非哈希：哈希等值快但无范围/排序，索引场景范围查是刚需。
- 选 B+ 而非 B 树：B 树非叶也存数据，目录稀疏、树更高、范围查中序遍历跨节点 IO 多。
- 选 B+ 而非 AVL/二叉：二叉树高度随节点线性增长，层数 = IO 数，大表不可接受。
- AHI 是补丁而非替代：只对高频等值列在内存建哈希，主结构仍是 B+ 树。

## 答题技巧

## 细节与核心 API

**① 页与树高的量化关系（面试最爱的算术题）**

```text
InnoDB 默认页 = 16KB
假设：主键 BIGINT 8B + 子页指针 6B ≈ 14B/目录项
非叶节点一页能放：16KB / 14B ≈ 1170 个目录项（扇出）

树高 2 层：1170 × 16（每叶约 16 行）=   18,720 行
树高 3 层：1170 × 1170 × 16        ≈ 21,902,400 行（约 2000 万）
树高 4 层：                         ≈ 256 亿行
```

> 结论锚点：**千万级大表的 B+ 树高度只有 3 层**，单点查询最多 3 次磁盘 IO
> （且非叶节点几乎全被 Buffer Pool 缓存，实际 IO 更少）。这正是不用二叉树的根本原因——
> 二叉树 2000 万行要 24 层 = 24 次 IO。

**② 结构对照（背这张表）**

| 结构 | 非叶存什么 | 范围查询 | 树高 |
|---|---|---|---|
| B 树 | 键值 **+ 数据** | 中序遍历，跨节点回退 | 高（目录稀疏） |
| **B+ 树** | **只存目录项** | **叶子双向链表顺序扫** | **矮胖** |
| 哈希 | 桶 + 链表 | ❌ 不支持范围 | — |
| 二叉/AVL | 键值 + 数据 | 中序遍历 | 极高，不可用 |

**③ 现场验证**

```sql
-- 看索引树的高度（Information Schema，MySQL 8.0）
SELECT index_name, page_no, level
FROM information_schema.innodb_indexes;

-- 用 EXPLAIN 验证走索引（key 非空 + rows 大幅下降）
EXPLAIN SELECT * FROM t WHERE id = 12345;

-- 范围查询：B+ 树叶子链表顺序扫，Extra 不会出现 Using filesort
EXPLAIN SELECT * FROM t WHERE id BETWEEN 100 AND 200;

-- 看页大小（默认 16384 = 16KB）
SHOW VARIABLES LIKE 'innodb_page_size';
```

**④ InnoDB 的配套补丁（收尾加分项）**

- **AHI（自适应哈希索引）**：对高频等值列在内存建哈希，**只对等值有效**，主结构仍是 B+ 树；
- **Buffer Pool**：缓存数据页，让"3 次 IO"进一步降到 0~1 次；
- **Change Buffer**：非唯一二级索引的写缓冲，减少随机 IO。

> 一句话话术："索引在磁盘、IO 是瓶颈、还要支持范围查——这三条约束决定了只能是 B+ 树。"

1. 开口先给约束：「索引在磁盘、IO 是瓶颈、要支持范围查」——这是所有结论的根。
2. 用排除法展开：哈希（无范围）→ 数组二分（插入贵）→ 二叉搜索树（退化+高）→ AVL（仍高）→ B 树（范围遍历贵）→ B+ 树（全补）。
3. 对比 B/B+ 用一个表：数据位置、范围查方式、树高。
4. 收尾补 InnoDB 特性：AHI / Buffer Pool / 双写缓冲，显示体系化。
5. 实战话术：「B+ 树让索引树更矮胖，一次查询只需 3~4 次磁盘 IO，且范围查可顺序扫叶子链表。」
