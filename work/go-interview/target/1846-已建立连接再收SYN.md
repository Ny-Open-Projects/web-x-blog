# 1846 已建立连接再收 SYN：Challenge ACK 分水岭

> 分类：网络 / TCP 进阶 | 难度：L1~L2 | 题型：场景推演题 | 频率：中 | 关键词：**Challenge ACK**/**半开连接**/**源端口**/**RST**/**keepalive**

> 原文锚点：第 1~17 段「客户端宕机恢复再连…服务端再次收到 SYN…源端口相同→回 Challenge ACK→客户端回 RST 关旧连接…不同→三次握手建新连接」

## 一句话总述
已 ESTABLISHED 的连接再次收到 SYN（典型场景：客户端宕机重启后重连），服务端如何反应**取决于新 SYN 的源端口是否与旧连接相同**：**相同** → 服务端当它是旧连接上的乱序报文，回 **Challenge ACK**（携带正确序列号），客户端发现序列号对不上 → 回 **RST** → 服务端释放旧连接；**不同** → 走三次握手建新连接，旧连接靠「发数据被 RST」或 keepalive 超时收尾。

## 面试官视角
- 意图：三次握手细节的刁钻变式（正是「基础题越考越深」的样板）——考你能否推演内核行为而非背流程图。
- 分档：P5 只会答「重新握手」；P6 能分出源端口两种情况；P7 能讲 Challenge ACK 的 RFC 5961 来源、半开连接与 keepalive 收尾链。
- 红旗答案：不分类直接说「服务端重新握手」；不知道旧连接不会自己立刻消失。
- 惊艳点：点破「SYN 的初始序列号是随机的 → 对旧连接来说它必然『乱序』」这一步因果，以及四元组三元未变、唯一变量是源端口 [经验]。

## 主问答
**Q（面试官原话）：** 如果 TCP 已建立连接，再次收到 SYN 会发生什么？

**A：** 场景先行：客户端中途宕机，服务端无数据可发——双方都停在 ESTABLISHED（**半开连接**：一方已失联，另一方不知情）。客户端恢复后重连，IP 与目标端口都没变，**唯一变量是源端口** [经验]：

1. **源端口相同**：服务端把新 SYN 当作旧连接里的**乱序报文**（SYN 的初始序列号是随机数，几乎不可能等于当前期望序列号）→ 不重握手，回 **Challenge ACK**（携带正确的序列号与确认号）→ 客户端核对发现「这不是我要的」→ 回 **RST** → 服务端收到 RST，释放旧连接。
2. **源端口不同**：四元组全新 → 服务端按新连接走**三次握手**；旧连接不会被立刻感知：
   - 服务端若发数据 → 客户端连接已不存在，内核回 **RST** → 服务端关闭旧连接；
   - 服务端一直不发数据 → **TCP keepalive** 保活机制探测到对端无存活 → 超时后释放连接。
3. **一层升华**：Challenge ACK 是 RFC 5961 的防护设计——让「来路不明的 SYN」温和地暴露身份，而不是粗暴重启或直接 RST（防 RST 盲打攻击）。

## 关键代码
```python
# 场景推演器：输入新 SYN 的源端口是否与旧连接相同 → 输出报文链
def on_syn(same_port: bool):
    if same_port:
        return [
            "SYN(乱序: ISN 随机≠期望 seq) 到达 ESTABLISHED 服务端",
            "服务端 → Challenge ACK(携带正确 seq/ack)",
            "客户端发现 seq 不符 → 回 RST",
            "服务端收到 RST → 释放旧连接",
        ]
    return [
        "四元组全新 → 服务端走三次握手建新连接",
        "旧连接① 服务端发数据 → 客户端内核回 RST → 关闭",
        "旧连接② 一直不发数据 → keepalive 超时探测 → 释放",
    ]

for case in (True, False):
    print("源端口相同:" if case else "源端口不同:")
    for step in on_syn(case):
        print("  ", step)
```

[实测] 输出两分支共 7 步推演链，与主问答逐条对应——面试时按这条链口述即可拿满分。

## ⚠️ 原文纠错
1. 术语核校： [经验] 原文将 Challenge ACK 音转为「级 chal­len SCK」类崩坏串、RST 音转为「IST」、SYN 音转为「SNN」，本卡统一为规范术语，不列举原词。
2. 事实核校： [经验] 原文「客户端收到 Challenge ACK 发现序列号并不是自己期望的」表述需精确——客户端正处于 SYN_SENT（三次握手进行中），它期望的是 SYN+ACK，收到纯 ACK 不符即回 RST；「序列号是随机数所以旧连接视为乱序」是服务端侧的因果，两侧视角勿混。
3. 补充核校： [经验] 「客户端宕机恢复后一定用新源端口」不成立——内核重启用临时端口池，新旧源端口相同与否是随机的，所以才需要两分支都答。
