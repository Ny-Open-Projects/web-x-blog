# 157 微服务治理：节点管理（故障摘除）

> 分类：微服务/治理 | 难度：L2 | 题型：概念题 | 频率：中 | 关键词：**节点摘除**/**注册中心主动摘除**/**心跳**/**消费者存活探测**/**故障扩散**
> 原文锚点：第 6~18 段「节点管理：注册中心主动摘除(心跳超时) + 服务消费者摘除(存活探测下移到消费者)」

## 一句话总述
微服务任意一方（提供者/消费者/注册中心）出问题都会调用失败，须**及时摘除故障节点防局部扩散**；两种机制——**注册中心主动摘除**（心跳超时）与**服务消费者摘除**（存活探测下移到消费者更抗误判）。

## 面试官视角
- 考察意图：是否理解「故障节点怎么被摘掉」，以及两种摘除机制的取舍。
- 分档：P5 知心跳超时摘除；P6 知两种机制区别、消费者摘除更抗注册中心误判；P7 知「防故障扩散」是治理第一目标。
- 红旗答案：以为只有注册中心一种摘除；不知注册中心自身网络问题会误删全部。
- 惊艳点：点出「注册中心与提供者网络隔离时，注册中心可能误删所有节点，故存活探测下放到消费者更稳」 [经验]。

## 主问答
**Q（面试官原话）：** 微服务里故障节点怎么摘除？
**A：**
1. **注册中心主动摘除（心跳）**：提供者周期性向注册中心发**心跳**；超过指定时间未收到→注册中心判定故障、将该节点移出服务列表，并把最新可用节点**推送**给消费者 [经验]。
2. **服务消费者摘除（存活探测下移）**：注册中心也可能因自身与提供者网络问题**误删全部节点**（提供者其实正常）；把存活探测下放到消费者更合理——消费者发现某节点不可用就**本地移除**，避免「注册中心误判导致全摘」[经验]。
3. **目标：防故障扩散**：任意一方出问题都可能导致调用失败；及时摘除，避免**局部故障扩散成整体故障** [经验]。

## ⚠️ 原文纠错
1. 事实核校： [经验] 心跳超时注册中心摘除、消费者存活探测更抗误判、防故障扩散——均正确。
2. 崩坏词归一：源码将若干术语音译为崩坏词，本卡统一为规范术语（服务提供者、注册中心、心跳、摘除、故障扩散等）。

```go
// 消费者侧存活探测：本地摘除不可用节点（避免注册中心误判全摘）
type Registry struct {
    mu      sync.RWMutex
    healthy map[string]bool // addr -> 是否可用
}
func (r *Registry) Call(addr string, req Req) (Resp, error) {
    r.mu.RLock(); ok := r.healthy[addr]; r.mu.RUnlock()
    if !ok {
        return Resp{}, ErrUnhealthy // 本地已摘除，不再发请求
    }
    resp, err := doCall(addr, req)
    if isConnFailure(err) { // 存活探测失败
        r.mu.Lock(); r.healthy[addr] = false; r.mu.Unlock()
    }
    return resp, err
}
// 提供者侧：周期性向注册中心发心跳，超时未发→注册中心主动摘除
```
