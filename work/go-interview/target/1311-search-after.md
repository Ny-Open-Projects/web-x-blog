# 1311 Search After：实时游标与它的三个硬约束

> 分类：Elasticsearch | 难度：L3 | 题型：场景题 | 频率：高 | 关键词：**search_after、排序值游标、实时、跳页、PIT**

> 原文锚点：第 73~96 段「不会创建快照…取上一次排序值作为游标获取下一页」

## 一句话总述
Search After 用**上一页最后一条的排序值**当游标取下一页，不建快照、每次读实时数据，是实时连续翻页的首选方案。

## 面试官视角
P6 会说"换成 search_after 就行"；P7 要主动抛出**三个硬约束**：排序值必须唯一（否则同值会漏页重页，通常用唯一键兜底）、排序字段必须可列式读取、**不支持随机跳页** `[经验]`。再补一句：裸用会因查询期间数据变动而不一致，配 PIT 才是完整解 `[源码]`。

## 主问答
**Q（面试官原话）：** 实时分页场景你用 search_after，它有什么限制？

1. **游标是排序值**：首个请求要显式指定排序字段与每页条数；之后把上一页**末条**的排序值数组原样传回 `[经验]`。
2. **无快照、读实时**：与快照型游标相反，每次请求都走当前数据，因此能看到期间的新写入，也就会看到不一致 `[源码]`。
3. **不能跳页**：没有页码概念，只能顺序往下翻；想跳到第 N 页只能一路翻过去，这是它换性能的代价 `[实测]`。
4. **排序值要唯一**：排序键有重复值时分页边界会漂移，必须追加唯一字段做次级排序键 `[经验]`。

## 关键代码
```json
POST /user/_search
{ "size": 5, "sort": [{"id":"asc"},{"_id":"asc"}], "search_after": [13, "13"] }
```
```go
// 顺序推进：无页码概念，只能一路往下翻
for len(hits) > 0 {
	hits, _ = query(ctx, size, lastSort)
	if len(hits) > 0 {
		lastSort = hits[len(hits)-1].Sort // 末尾排序值即下一页游标
	}
}
```
> 验证：原文 20 条数据每页 5 条，逐页回传末条排序值可翻到返回空数组为止 `[实测]`。
