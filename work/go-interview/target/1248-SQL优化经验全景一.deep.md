## 思路与架构
SQL 优化分四层，本波聚焦前三层未被覆盖的真 gap，编写习惯层与既有卡互补：
1. **设计层（本卡组 1248-主1）**：类型恰当 / NOT NULL / 默认值 / date→int。既有 1215 讲 compact 行格式 NULL 存储，本卡讲"设计建议 why"。
2. **查询层索引失效（1248-主2）**：隐式类型转换 + OR 规则。既有 1221/1222 汇总了函数/最左前缀/覆盖索引，本卡补"隐式转换"与"OR 两字段都索引"两个具体坑。
3. **版本细节（1248-主3）**：8.0 范围列后索引仍有效 + IS NULL/IS NOT NULL/NOT IN 规则。既有 1222 讲最左前缀基础，本卡补版本例外。
4. **编写习惯层（互补不重产）**：长连接（见 129）、TRUNCATE vs DELETE（见 1225）、深度分页改造（见 1246）。

## 答题技巧
- 答 SQL 优化按"设计→索引→版本→习惯"四层递进，先说设计前移最省力。
- 易混点：范围列后失效是**老版本**经验，8.0 以 EXPLAIN 为准；隐式转换本质是对列套函数。
- 口诀收尾：全值匹配我最爱，最左前缀要遵守；索引列上少计算，字符引号不能丢；不等空值还有 OR，索引失效要注意。

## 细节与核心 API

**查询层索引失效两坑（隐式转换 / OR 规则）：**

```sql
-- 隐式类型转换：varchar 列被传数字 → 优化器对列套 CAST 函数 → 索引失效
SELECT * FROM user WHERE phone = 13800000000;   -- 失效（phone 是 varchar）
SELECT * FROM user WHERE phone = '13800000000'; -- 走索引（类型匹配）

-- OR 两侧：仅一侧有索引 → 优化器放弃索引走全表
SELECT * FROM t WHERE a = 1 OR b = 2; -- a 有索引、b 无 → 整句失效
-- 改写为 UNION 才能各自走索引
SELECT * FROM t WHERE a = 1 UNION SELECT * FROM t WHERE b = 2;
```

**版本细节（8.0 已推翻"范围列后全失效"老经验）：**

```sql
-- 8.0 下联合索引 (a,b)，a 走范围后 b 仍可能参与索引过滤（以 EXPLAIN 为准）
SELECT * FROM t WHERE a > 10 AND b = 1;

-- IS NULL / IS NOT NULL / NOT IN 在 8.0 对 NULL 友好的联合索引上可用到索引
SELECT * FROM t WHERE b IS NULL;        -- 8.0 可走 (a,b) 索引
SELECT * FROM t WHERE b NOT IN (1,2,3); -- 注意 NOT IN 含 NULL 时整集为 NULL
```

**设计层（类型恰当 / NOT NULL / date→int 映射）：**

```sql
-- 日期存 int(秒/毫秒时间戳) 比 date/datetime 省空间且范围查询快
CREATE TABLE evt (
  id      BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  etime   INT    NOT NULL DEFAULT 0,  -- 存 unix 秒，而非 DATETIME
  status  TINYINT NOT NULL DEFAULT 0, -- NOT NULL + 默认值，避免 NULL 占额外位
  PRIMARY KEY (id),
  KEY idx_etime (etime)
);
```
