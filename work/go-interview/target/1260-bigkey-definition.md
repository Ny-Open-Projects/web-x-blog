# 1260 Redis 大 Key 的定义与判定阈值

> 分类：Redis/运维 | 难度：L2 | 题型：概念题 | 频率：中 | 关键词：**大 Key** / **阈值** / **value>1MB** / **集合>1万**
> 原文锚点：第 3~7 段「无统一标准；value>1MB 或集合>1万 视为大Key；低延迟高并发场景 10KB 即大Key；按耗时上报定义」

## 一句话总述
Redis 大 Key 没有统一硬标准，**通用经验线**是单个 value 占用 >1MB 或集合元素 >1 万个；但在高并发、低延迟容忍度差的场景，**10KB 就可能算大 Key**。工程上应按业务实际：统计 value 大小分布与不同区间的访问耗时，用数据自己定义"业务大 Key"。

## 面试官视角
- 意图：考察"会不会量化大 Key"，而非背一个死数字。
- P5 知道大 Key 不好；P6 能说出 1MB/1万 经验线与 10KB 场景线；P7 能讲"按耗时上报、按业务定义"的量化方法。
- 红旗：以为大 Key 有全球统一阈值；把所有 key 一律等同看待。
- 惊艳点：点出"大 Key 是相对概念，取决于业务延迟容忍度与访问频率"。

## 主问答
**Q：** 多大算 Redis 大 Key？
**A：**
1. **通用经验线**：单个字符串 value 占用空间很大（上百 MB 级）或集合类型存了几千万元素，显然是大 Key；实践中常以 **value > 1MB 或集合元素 > 1 万** 作为处理阈值。
2. **场景线**：对于并发高、延迟容忍度极低的响应链路，**10KB 的 value 就可能算大 Key**——因为一次大值网络传输就拖垮 P99 延迟。
3. **量化定义**：在代码里对 value 的访问耗时做上报，统计业务中 value 大小分布与不同大小区间的耗时，据此定出自己业务的大 Key 线。

## 关键代码
```go
// 量化大 Key：上报每次 GET 的 value 大小与耗时，按分桶统计
func observeGet(rdb *redis.Client, key string) {
    start := time.Now()
    size, _ := rdb.StrLen(ctx, key).Result() // 先取长度，避免拉全量
    _ = rdb.Get(ctx, key).Err()
    cost := time.Since(start)
    // 按 size 分桶(1KB/10KB/1MB...)记录耗时直方图
    metrics.Observe("redis_get_cost", float64(cost.Microseconds()),
        "bucket", bucketOf(size))
    if size > 10*1024 { // 低延迟场景 10KB 即预警
        log.Warnf("possible bigkey %s size=%d cost=%v", key, size, cost)
    }
}
```
