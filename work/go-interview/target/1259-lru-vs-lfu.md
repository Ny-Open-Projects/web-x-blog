# 1259 LRU 与 LFU 的差别，以及 Redis 为什么不用传统 LRU

> 分类：缓存 / 淘汰算法 | 难度：L4 | 题型：原理题 | 频率：高 | 关键词：**LRU**/**LFU**/**近似采样**/**缓存污染**/**衰减计数**
> 原文锚点：第 3~36 段「传统的 LRU 算法基于链表结构…Redis 并没有使用传统的 LRU 算法…使用红近似的 LRU 算法…在对象结构中添加一个额外的字段记录最后一次访问时间…随机采样默认五个值…将访问时间改成访问次数…访问频次初始值是五…高十六位记录访问时间戳，低八位记录访问频次」

## 一句话总述
**LRU**（Least Recently Used）按**最近访问时间**淘汰，**LFU**（Least Frequently Used）按**访问频次**淘汰。传统 LRU 用链表维护访问顺序（命中就移到头部、淘汰尾部），但 Redis 嫌它**吃内存 + 大量链表移动伤性能**，于是改成**近似 LRU**：在对象结构里塞一个额外字段记录最后访问时间，淘汰时**随机采样若干个、丢掉其中最久未用的那个**。这套近似方案的问题是会被**一次性批量读取**污染；把度量从"访问时间"换成"访问频次"就成了 LFU，**再给频次加上随时间衰减**，才是 Redis 里那个真正好用的 LFU。

## 面试官视角
- 考察意图：表面考算法，实则考**工程取舍**——你知不知道"教科书算法"落到生产时要为**内存开销**和**操作开销**让路，以及分布式缓存里只有淘汰 algo 没有护城河，**缓存污染**才是真正的敌人。
- 分档：P5 只会背 LRU 全称；P6 能讲清链表实现与 Redis 改用近似采样的两个理由；P7 能一路说到**24 位字段的位布局（16 位时间 + 8 位计数）、初值 5、概率增长、衰减参数**，并主动点出缓存污染与两种缓解路径。
- 红旗答案：「Redis 的 LRU 就是链表那条 LRU」「LFU 就是记个访问次数」——前者不知道近似采样，后者不知道**频次会衰减**，而衰减恰恰是 LFU 的灵魂。
- 惊艳点：「LFU 里那个 24 位字段是 **24 bits 不是 24 字节**」——这是面试里极其常见的一句口误纠正 [经验]。

## 主问答
**Q（面试官原话）：** LRU 和 LFU 有什么区别？Redis 里是怎么实现的？
**A：**
1. **LRU 的思路**：全称 Least Recently Used（**最近最少使用**），传统实现维护一条**访问顺序链表**，最近访问的数据移到**链表头部**，最久未访问的自然沉到**链表尾部**，淘汰时拿尾部即可。优点是**易实现**，对**局部性好**的访问模式有不错的命中率 [源码]。
2. **Redis 为什么不用传统 LRU——两个硬伤**：① 用链表管理**所有**缓存数据，会占用**额外的缓存空间**；② 每次访问都要把节点**移到链表头部**，海量访问会带来大量链表移动操作，**直接影响 Redis 性能** [源码]。
3. **近似 LRU**：Redis 改为在**对象结构**中增加一个额外字段记录**最后一次访问时间**，淘汰时 **随机采样**（默认 5 个，由 `maxmemory-samples` 配置），丢掉采样里**最久未使用**的那个。这样既省内存又无链表移动开销 [源码]。
4. **近似方案的代价——缓存污染**：如果应用**一次性读取大量数据**，这些数据的最后访问时间会被集体刷新，导致它们迟迟不能被清理，把真正的热数据挤出缓存 [源码]。
5. **把度量从"时间"换成"次数"→ LFU**：LFU 全称 Least Frequently Used（**最不经常使用**），维护每个数据项的访问频次，淘汰**频次最低**者。它能适应更多样的访问模式，尤其解决"偶尔被访问一次就在缓存里赖很久"的问题；代价是**实现更复杂**，要维护频次信息 [源码]。
6. **Redis 的 LFU 位布局**：对象结构的同一个字段里同时记录时间戳与频次——**高 16 位**记录访问时间戳，**低 8 位**记录访问频次，**频次初值是 5** [源码]。注意这个字段是 **24 位（bits）而非 24 字节** [经验]。
7. **频次会衰减才会过期**：访问**次数** ≠ 访问**频率**。Redis 在每次被访问时**先按距上次访问的时长做衰减**（`lfu-decay-time`，单位分钟，默认 1，值越大衰减越慢），再按概率增加频次——**当前频次越高，增长概率越低**（由 `lfu-log-factor` 调节，值越大增长越慢）。这样早年很热、如今无人问津的 key 会自然冷却并被淘汰 [源码]。

## 关键代码
```go
// 手写一个最小 LRU：哈希表 + 双向链表，命中移到头、满则淘汰尾
type entry struct{ key, val int }

type LRU struct {
	cap   int
	ll    *list.List            // 按访问顺序：最近访问在表头
	items map[int]*list.Element // key -> 链表节点，O(1) 定位
}

func NewLRU(cap int) *LRU { return &LRU{cap: cap, ll: list.New(), items: map[int]*list.Element{}} }

func (c *LRU) Get(key int) (int, bool) {
	if e, ok := c.items[key]; ok {
		c.ll.MoveToFront(e) // 命中即"最近使用"
		return e.Value.(entry).val, true
	}
	return 0, false
}

func (c *LRU) Put(key, val int) {
	if e, ok := c.items[key]; ok {
		c.ll.MoveToFront(e)
		e.Value = entry{key, val}
		return
	}
	c.items[key] = c.ll.PushFront(entry{key, val})
	if c.ll.Len() > c.cap { // 超出容量：淘汰链表尾部 = 最久未使用
		tail := c.ll.Back()
		delete(c.items, tail.Value.(entry).key)
		c.ll.Remove(tail)
	}
}
// [实测] 要点：Get 的 MoveToFront 就是 Redis 嫌贵而改用采样淘汰的那个动作
```

## 总结与追问预判
一句话记忆：**「LRU 看最后一次什么时候来，LFU 看来过多少次还要按时间打折」**。MySQL 缓冲池里的 LRU 变体见 `1262-*`/`1264-*` 系列 [边界]，本卡聚焦 Redis 侧实现。常追问「那 24 位会不会溢出」——答：LFU 的高 16 位存的是**分钟级**时间戳（会回绕，实现上通过比较相对时间处理），低 8 位频次上限 **255**，这也是为什么要靠 `lfu-log-factor` 概率增长去压住增长速度；再追问「近似 LRU 采样数调大有用吗」——答：**有，且是纯取舍**：采样数越大越接近真实 LRU、命中率越好，但**每次淘汰的 CPU 开销越大**，默认值是在"够准"和"够快"之间的折中。

## ⚠️ 原文纠错
1. 事实核校： [经验] 三处需纠正/补全——① 原文所称"二十四**字节**"字段实为 **24 位（bits）**：高 16 位时间戳 + 低 8 位访问频次，合计 24 bits；② LFU 全称 Least Frequently Used，含义是"**最不经常使用**"，原文"最近不常用"表述不准；③ 原文未给 `lfu-log-factor` 默认值（**10**），已补。采样默认 5、频次初值 5、16+8 位布局、随机采样淘汰均已核校正确。
