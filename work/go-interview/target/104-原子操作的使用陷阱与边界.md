# 104 原子操作的使用陷阱与边界

> 分类：Go/并发 | 难度：L3 | 题型：陷阱题 | 频率：中 | 关键词：**不对 struct 直接原子** / **原子不保复合逻辑** / **高竞争不如锁** / **atomic.Value 同类型**
> 原文锚点：第 57~66 段引申「原子=变量级互斥；Go 封装 sync/atomic 通用 API；支持类型有限」+ 标准实战陷阱归纳

## 一句话总述
原子操作虽轻，但有清晰边界：**① 不能对 struct 直接原子**（只支持基础标量/unsafe.Pointer，多字段要上锁或聚合进 atomic.Value）；**② 不保证复合逻辑**（"读—判断—写"仍要 CAS 循环或锁）；**③ 高竞争下原子反复重试可能不如一把锁**（锁 cache line 有开销）；**④ 单核也要原子**（编译重排 + 调度抢占仍会交错，不能靠 GOMAXPROCS=1 偷懒）；**⑤ atomic.Value 必须存同类型**否则 panic。选型：单变量计数/状态位用原子，复合临界区上锁。

## 面试官视角
- 意图：考察"会不会在真实代码里用错原子"，是踩坑题。
- P5 知计数器用原子；P6 能列 3+ 陷阱；P7 能讲"原子只保单变量、复合逻辑需 CAS/锁、高竞争实测可能不如锁、单核也需保护"。
- 红旗：对 struct 直接 `atomic.Load`；以为原子能保护一段逻辑；靠单核省掉原子。
- 惊艳点：点出"高竞争下 CAS 自旋重试的 CPU 开销可能反超一把锁"——选型要实测。

## 主问答
**Q：** 用原子操作有哪些常见陷阱？
**A：**
1. **类型限制**：原子只支持 int32/64/uint32/64/uintptr/unsafe.Pointer 与 atomic.Value；对 struct 直接 `atomic.Load(&s)` 编译不过——多字段一致性要上锁，或把整个值塞进 `atomic.Value`（存入类型须一致）。
2. **不保复合逻辑**：`if atomic.Load(&f)==0 { ... } atomic.Store(&f,1)` 这种"读—判—写"不是原子整体，仍竞态；要 `CompareAndSwap` 循环或上锁。
3. **高竞争代价**：原子指令锁 cache line，极高竞争下 CAS 自旋重试的 CPU 开销可能超过一把锁——选型以实测为准。
4. **单核也需保护**：单核下编译重排与调度抢占仍会让 load/add/store 交错（见 104），不能靠 GOMAXPROCS=1 省原子。
5. **atomic.Value 同类型**：`Store` 后必须存同一动态类型，否则下次 `Store` 直接 panic。

## 关键代码
```go
// 陷阱①：struct 不能直接原子
type S struct{ A, B int }
// atomic.LoadInt64(&s.A) 合法，但对整个 S 原子非法——多字段需 Mutex

// 陷阱②：读-判-写不是原子整体，仍需 CAS
for {
    old := atomic.LoadInt64(&flag)
    if old != 0 {
        break
    }
    if atomic.CompareAndSwapInt64(&flag, 0, 1) { // 用 CAS 替代"读-判-写"
        break
    }
}

// 陷阱⑤：atomic.Value 必须同类型
var v atomic.Value
v.Store("a")
v.Store(42) // panic：与首次存入类型不一致
```
