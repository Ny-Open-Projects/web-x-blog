# 1506 微服务避免过度设计：二八定律

> 分类：架构设计 / 微服务 | 难度：L2 | 题型：原则题 | 频率：中 | 关键词：**过度设计** / **二八定律** / **单体优先** / **收益评估**
> 原文锚点：第 29~30 段「避免过度设计…二八定律…80%产出来自20%投入…简化范围」

## 一句话总述
微服务不是越细越好——用二八定律简化范围，先把 20% 核心投入做扎实，避免过度设计抬高复杂度与交付周期、徒增成本；边界不清时先不拆（见 154）。

## 面试官视角
- 意图：是否把微服务当银弹，还是懂"为未来预设架构"本身就是负债。
- P5 知别过度拆；P6 说清二八定律与简化范围；P7 能量化"拆分收益 vs 运维成本"。
- 红旗：一上来就按部门/人员粒度拆成几十个服务；为"可能将来要"预留复杂抽象。
- 惊艳点：80% 价值来自 20% 投入——先聚焦那 20% 核心，其余按需演进，比一步到位省成本 `[经验]`。

## 主问答
**Q（面试官原话）：** 微服务化要避免什么坑？
**A：**
1. **避免过度设计**：不为"未来可能"预设超出当前需求的架构，否则复杂度↑、交付周期↑、成本↑ `[源码]`。
2. **二八定律**：80% 产出源自 20% 投入，先简化范围、聚焦核心 20% 扎实做，再按需扩展。
3. **先单体后演进**：边界不清时先不拆，等业务发展出清晰界限再演进式拆分（见 154）`[边界]`。
4. **收益评估**：拆分前确认真有收益，不为微服务而微服务——否则一致性/延迟/运维成本反噬。

## 关键代码
```go
// 示意，未验证：单体直接调用 vs 微服务 RPC 的额外开销对比——过度拆分的代价
package main
import ("context"; "fmt"; "time")
// 单体：进程内直接调用，无网络开销
func inProcess(a, b int) int { return a + b }
// 微服务：跨网络调用，多了超时/序列化/重试（过早拆分的成本）
func overRPC(ctx context.Context, a, b int) (int, error) {
    _ = time.Sleep(2 * time.Millisecond) // 网络+序列化开销
    return a + b, nil
}
func main() {
    fmt.Println("单体:", inProcess(1, 2))
    r, _ := overRPC(context.Background(), 1, 2)
    fmt.Println("微服务RPC:", r, "(多一次网络往返)")
}
```
