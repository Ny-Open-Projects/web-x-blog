## 一句话总述
`df` 空间没降的另一类原因：**`rm` 被运维别名/函数覆盖成了 `mv` 到 `/tmp`**——看似删了，文件其实被移到临时目录，仍在原文件系统占用空间，且要等机器重启 `/tmp` 清理才真正释放（或手动清 `/tmp`）。

## 面试官视角
偏运维实战的"坑"。面试官想看你是否知道生产环境 `rm` 常被加固为"伪删除"，以及这如何误导磁盘排查，能否点出"看当前目录没了 ≠ 空间释放了"。

## 主问答
**Q（面试官原话）：** 我 rm 删了文件，当前目录看不到了，可磁盘还是满的，怎么回事？

**A：**

1. **`rm` 被覆盖成 `mv`**：很多运维为防误删，在 `~/.bashrc` 里定义同名 shell 函数 `rm() { mv "$@" /tmp/; }`，覆盖系统 `rm`；执行 `rm file` 实际是把文件移动到 `/tmp`，当前目录消失但**原文件系统占用不变**（/tmp 多在同一分区）。
2. **回收机制**：移到 `/tmp` 的文件要等机器重启（或 tmpwatch 定时清理）才删除；期间空间不释放，且"误删可找回"正是该机制的初衷。
3. **排查**：`df` 仍满时，查 `/tmp` 是否有刚移入的大文件；用 `alias rm` / `type rm` 确认 `rm` 是否已被函数覆盖；真要立刻释放需手动 `rm -rf /tmp/<file>`（走真正的 unlink）或清 `/tmp`。

## 版本与兼容性
- 该加固是运维约定（写 `~/.bashrc`/`~/.zshrc`），非系统默认；不同发行版默认 `rm` 即 `rm`，无回收站。
- `/tmp` 清理策略：systemd `tmpfiles.d` 或 `tmpwatch`/`tmpreaper`，通常按 mtime 超时清理，重启亦会清。

```go
// 复现"安全删除"：把待删文件移动到 /tmp 回收站（等价 rm 别名成 mv 的思路）
func safeDelete(path string) error {
    name := filepath.Base(path)
    dst := filepath.Join("/tmp", ".trash_"+name)
    // 移到回收站而非直接 unlink，误删可找回；空间仍占原分区直到 /tmp 清理
    if err := os.Rename(path, dst); err != nil {
        return err // 跨分区需 cp+rm，此处同分区 rename 即可
    }
    return nil
}
```
