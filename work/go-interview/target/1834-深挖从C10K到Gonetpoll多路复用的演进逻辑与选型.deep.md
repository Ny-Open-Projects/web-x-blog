# 1834 深挖：从 C10K 到 Go netpoll——多路复用的演进逻辑与选型

> 分类：操作系统 / 网络 | 难度：L4 | 题型：设计题 | 频率：中 | 关键词：**C10K**/**netpoll**/**红黑树**/**就绪链表**/**ET 非阻塞**/**事件循环**/**跨平台**
> 原文锚点：第 22~33 段「epoll 是为解决 select 和 poll 的性能问题而设计的…只返回有事件发生的文件描述符的个数，不需要扫描整个集合…epoll 支持边缘触发和水平触发两种模式…epoll 可能不是在所有的操作系统上都支持」
> [边界] 本文只讲**演进逻辑、内部结构与工程选型**：三者的字段级对比见 1834，Go `select` 语句见 909，均不重述。

## 思路与架构

用一个**不变的矛盾**串起三代机制：

```text
矛盾：连接数 N 持续增长，但"找出谁就绪"的成本随 N 线性上涨

第一代 select —— 位图 + 全量往返
  用户态 fd_set(1024 位图) --拷贝--> 内核遍历 --标记--> 拷回用户态 --> 用户态再遍历
  成本 = 2 次拷贝 + 2 次 O(N) 遍历 + 硬上限 1024

第二代 poll —— 数组化，只拆掉了上限
  struct pollfd[] 取代位图  ⇒ 数量不再受 1024 限制
  但 拷贝 + O(N) 遍历 一个没少  ⇒ 复杂度代际未变

第三代 epoll —— 把"集合"搬进内核长期持有
  红黑树    : 存全部监听 fd，支持 O(log N) 增/删/改
  就绪链表  : 事件发生时由回调把 fd 挂进来
  epoll_wait: 只把就绪链表交回用户态
  成本 = O(就绪数)，与总连接数 N 解耦
```

**为什么红黑树 + 链表是必需的双结构**（面试高频追问）：

```text
只留链表？    -> 每次增删监听项要遍历，O(N)
只留红黑树？  -> 找就绪项要遍历整棵树，退化成 O(N)
两者配合：
  增/删/改监听  -> 红黑树 O(log N)
  取就绪        -> 直接摘就绪链表 O(就绪数)
这就是 epoll 的精髓：把两种不同访问模式拆到两种数据结构上
```

## 方案取舍

```text
维度          select              poll              epoll
─────────────────────────────────────────────────────────────
fd 上限       1024 硬限制         无硬限制           无位图限制
数据结构      位图                结构体数组         红黑树 + 就绪链表
每次调用拷贝  是（两次）          是（两次）         否（集合常驻内核）
查找复杂度    O(N)                O(N)              O(就绪数)
触发模式      仅 LT               仅 LT             LT + ET
跨平台        全平台              全平台            Linux 专有
─────────────────────────────────────────────────────────────
适用          教学 / 极小规模     中等规模且跨平台    Linux 高并发
```

**ET 与 LT 的取舍**（这是 epoll 独有的决策点）：

```text
LT（水平触发，默认）
  + 语义简单：没读完会一直通知，不容易漏事件
  - 同一事件可能被重复投递，要注意去重
  适用：大多数业务，推荐默认

ET（边缘触发）
  + 每个事件只通知一次，投递次数最少
  - 必须配非阻塞 IO，并循环读/写到 EAGAIN
    漏读一次 = 这个连接从此再无事件 = 永久卡死
  适用：极致性能优化，且团队能hold住非阻塞状态机
```

**跨平台选型的三条纪律**：

```text
1. 不要直接调 epoll —— 用 libevent / libuv / netty / Go net 包
   它们把 epoll / kqueue / IOCP 抽象成统一接口
2. Go 更彻底：运行时自带 netpoll，按平台编译不同后端
   Linux -> netpoll_epoll.go   darwin/BSD -> netpoll_kqueue.go
   业务代码完全无感
3. 面试说"我们用 epoll"时，要能补一句
   "跨平台场景要抽象，macOS 是 kqueue、Windows 是 IOCP"
```

## 答题技巧

```text
1. 用一条主线讲完三代，不要罗列字段
   「核心矛盾是'找就绪'的成本随连接数线性涨：
     select 全量往返、poll 只拆上限、epoll 把集合常驻内核只回传就绪。」

2. 主动纠正一个大众误区（极大加分）
   「poll 并不比 select 快，它只是去掉了 1024 上限；
     真正的代际差在 epoll。」

3. epoll 内部结构要答"两个结构"
   「红黑树管增删、就绪链表管取就绪——
     单说链表或单说红黑树都是不完整的。」

4. 被问 ET 时一定补风险
   「ET 必须一次读到 EAGAIN，否则漏事件导致连接永久卡死；
     所以 ET 一定要配非阻塞 socket。」

5. 收尾拔高到语言层
   「Go 把这套复杂度收进 runtime：goroutine 阻塞在网络 IO 时
     由 netpoll 接管，M 不会被占住，这就是 Go 能'写得像同步、
     跑得像异步'的原因——也是 GMP 存在的意义之一。」
```

**可能被追问的深水区**：

```text
Q：epoll 一定比 select 快吗？
A：不一定。连接数很少（几十个）且全部活跃时，
   select 的简单性反而占优，epoll 的红黑树与回调有额外常数开销。
   优势要到"大量连接、少量活跃"的场景才显现——这正是网络服务的常态。

Q：为什么网络服务多是"大量连接、少量活跃"？
A：长连接大部分时间在等请求。select/poll 每次都要扫全部连接，
   其中绝大多数根本没数据；epoll 只处理真正有事件的那几个。

Q：Go 里一个连接一个 goroutine 不会爆吗？
A：阻塞在 IO 上的 goroutine 会被 netpoll 接管，不占 OS 线程；
   初始栈仅 2KB 量级，十万级连接在内存上是可承受的。
   但每个连接一个 goroutine 不代表可以不管超时与限流。
```

## 细节与核心 API

```go
// C10K 问题：1 万并发连接，每连接一线程 -> 上下文切换/内存爆炸
// 演进：select(poll 集 fd 数组，O(n) 轮询) -> epoll(就绪事件回调，O(1)) -> Go netpoller
// Go 做法：每个 conn 一个 goroutine，写法像阻塞，实际由 netpoller 托管
ln, _ := net.Listen("tcp", ":8080")
for {
    c, _ := ln.Accept()
    go func(conn net.Conn) {        // 一个 G 处理一个连接（M 不阻塞）
        buf := make([]byte, 4096)
        for { n, err := conn.Read(buf); if err != nil { return }; handle(buf[:n]) }
    }(c)
}
// 十万连接只需少量 M（=GOMAXPROCS + 少量 syscall 线程），靠 epoll 唤醒就绪 G
// 选型：写业务用 Go 原生 net（省心）；要极致 control（自定义事件循环）才用 epoll 直接写
// 陷阱：netpoller 只管“网络 fd”，本地大文件 read 仍阻塞 M（必要时用 goroutine 池隔离）
```
