# 1222 LIKE 索引失效：三种例外与效率对比

> 分类：MySQL 索引 | 难度：中高 | 题型：总结 | 频率：高 | 关键词：**覆盖索引、三种例外、type=index、type=range、效率**

> 原文锚点：第 70~93 段「三种违反最左前缀仍用索引的情形、range 优于 index」

## 一句话总述
结论：LIKE 非前缀（`'%x%'`）**并非一定失效**。三种例外（均因覆盖索引）：① 表只有「主键+一个索引列」，SELECT * 也覆盖；② 多列表中只查该索引列；③ 联合索引上只查联合索引列（顺序无关）。覆盖下走 type=index（全扫二级索引树）。注意 type=range（利用有序性快速定位）效率高于 type=index（全扫），前缀 LIKE 才是 range。

## 面试官视角
这是整套 LIKE 题的收口。考官看你能用「覆盖索引」一条线串起所有例外，并强调「用索引 ≠ 高效」——type=index 虽用了二级索引，但是全扫，效率低于 type=range。能补一句「是否回表决定优化器选哪棵树」就是满分回答。

## 主问答
**Q（面试官原话）：** 总结一下 LIKE 索引失效的例外与效率。

1. **例外一（两列表）**：表仅主键+一个索引列，非前缀 LIKE 的 SELECT * 仍覆盖 → 走二级索引。
2. **例外二（多列只查索引列）**：只取索引列即覆盖 → 走二级索引（type=index）。
3. **例外三（联合索引只查其列）**：覆盖且顺序无关 → 全扫二级索引树。
4. **效率对比**：type=range（前缀 LIKE，利用有序性定位）> type=index（非前缀，全扫二级索引）；两者都「用了索引」，但 range 更快。是否回表决定优化器在「二级树 / 聚簇树」间选型。

## 版本与兼容性
| 写法 | type | 用索引? | 效率 |
|------|------|---------|------|
| 'x%' | range | 是 | 高 |
| '%x%' + 覆盖 | index | 是 | 中（全扫） |
| '%x%' + 回表 | ALL | 否 | 低 |

## 关键代码
```sql
-- 实战：建覆盖索引让模糊查询尽量走索引
ALTER TABLE user ADD INDEX idx_name (name);
SELECT name FROM user WHERE name LIKE '%张%';  -- type=index
```

## 总结与追问预判
核心：**非前缀 LIKE 在覆盖索引下可走 type=index（全扫二级索引），三种例外本质都是覆盖；range > index 效率**。追问可回各情形细节（见 1222-covering-index / 1222-composite-exceptions）。
