# 604 开放编码 defer（open-coded defer）

> 分类：Go 运行时 | 难度：L3 | 题型：原理题 | 频率：中 | 关键词：**open-coded defer** / **Go 1.14** / **零分配** / **编译期内联**
> 原文锚点：第 26~28 段「开放式编码 defer：编译期确定数量与位置的 defer 直接内联，不需运行时记录，一个帧只有一个 _defer 记录所有」

## 一句话总述
Go 1.14 起引入**开放编码 defer（open-coded defer）**：当函数内 defer 数量少且位置在编译期可确定时，编译器直接把 defer 调用内联到函数返回前，跳过 `deferproc` 的堆分配与链表操作，几乎零开销。

## 面试官视角
- 意图：考察候选人对 defer 性能优化的了解（红旗：以为所有 defer 都有运行时开销）。
- P5 知道 defer 有开放编码优化；P6 能说清"编译期内联、跳过 deferproc"；P7 能指出限制（循环内 defer、数量过多则退化为普通 defer）。
- 红旗：以为 defer 一定堆分配；以为循环里的 defer 也能开放编码。
- 惊艳点：点出开放编码后 defer 与直接函数调用性能接近，所以"defer 慢"在多数场景是误区。

## 主问答
**Q（面试官原话）：** defer 有性能优化吗？为什么有人说 defer 几乎零开销？
**A：**
1. **结论**：Go 1.14 的开放编码 defer 把"数量少、位置固定"的 defer 在编译期直接内联到函数返回前，不再走 `deferproc` 堆分配与链表头插，开销接近普通调用。
2. **机制**：开放编码要求 defer 出现在函数顶层（非循环内）、数量不超过阈值（默认 8）；编译器为每个 defer 生成对应的清理代码，函数 return 前顺序执行；一个栈帧只用一个 `_defer` 记录描述整组开放编码 defer `[源码]`。
3. **边界**：循环内 defer、defer 数量超阈值、或无法在编译期确定数量时，退化回普通 `deferproc` 路径（有堆分配与链表开销）——所以"循环里 defer"慢且泄漏，与开放编码无关 `[经验]`。

## 关键代码
```go
// 示意，未验证：开放编码——编译期内联，无需 deferproc 堆分配
func openCoded() error {
    f, e := os.Open("x")
    if e != nil {
        return e
    }
    defer f.Close() // 数量少且位置固定 → 编译期内联到返回前
    // ... 返回前编译器直接插入 f.Close() 调用
    return nil
}
```
