# 199 大文本高亮的四种提速方案

> 分类：搜索引擎/ES 调优 | 难度：L3 | 题型：场景题 | 频率：中 | 关键词：**高亮** / **流式读取** / **外部存储高亮** / **化整为零**
> 原文锚点：第 25~42 段「大文本高亮性能差；定制插件流式停读、外部存储并发高亮、按段落拆分、评估是否真需高亮四种方案」

## 一句话总述
大文本高亮慢的根因是"全量匹配+全局最优片段计算"，四方案按"改 ES / 绕开 ES / 拆小 / 不要高亮"递进，越往后研发成本越低、越贴近业务。

## 面试官视角
- 意图：考察候选人能否把"性能问题"拆成多条可落地的技术路线，并说清各自代价。
- P5 能列两种方案；P6 能对比插件 vs 外部存储的复杂度；P7 能指出"网盘场景靠文件名辨识度可不要高亮"这种业务级取舍。
- 红旗：只会说"加机器"；把四种方案当成互斥而非可组合。
- 惊艳点：点出原生高亮"找全部匹配再算最优片段"才是慢因，而非单纯 IO。

## 主问答
**Q（面试官原话）：** ES 大文本高亮很慢，有什么优化思路？
**A：**
1. **结论**：四方案——定制高亮插件（流式读、命中即停）、外部存储并发高亮、按段落拆分文档、或直接评估不要高亮，研发成本与收益递减。
2. **机制**：插件在 ES 内改高亮逻辑，流式读原文、首段命中即停并并发处理多匹配；外部存储把原文放外面，按 docID 并发取、业务侧高亮再回填 ES 结果。
3. **边界**：拆分文档会带来分页去重复杂度；业务可接受"仅提示含关键词"时直接去掉高亮，成本最低 `[经验]`。

## 关键代码
```go
// 示意，未验证：外部存储并发高亮——按 docID 批量取原文，多 worker 并行高亮后回填
type Doc struct{ Content string }

func highlightExternal(docs []Doc, kw string) []string {
    out := make([]string, len(docs))
    var wg sync.WaitGroup
    for i, d := range docs {
        wg.Add(1)
        go func(i int, d Doc) {
            defer wg.Done()
            out[i] = strings.ReplaceAll(d.Content, kw, "**"+kw+"**")
        }(i, d)
    }
    wg.Wait()
    return out
}
```
