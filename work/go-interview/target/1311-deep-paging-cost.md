# 1311 ES 深分页：from+size 的分布式放大

> 分类：Elasticsearch | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**深度分页、from+size、分片、协调节点、放大倍数**

> 原文锚点：第 2~8 段「查询偏移量等于一万…从每个分片取一万零一十条」

## 一句话总述
ES 的 `from + size` 分页在分布式下会被**分片数放大**：每个分片都先各取 `from + size` 条，再由协调节点全局排序后截取，代价随偏移量线性增长。

## 面试官视角
P6 只答"ES 分页慢"；P7 要给出**量化口径**：全集群读取量 = `(from + size) × 分片数`。原文 10 分片、offset=10000、size=10 即 100100 条 `[经验]`。再补一句减负细节：分片回传的只有**文档 ID 与排序字段**，完整文档由协调节点二次拉取，否则更早打爆网络 `[源码]`。

## 主问答
**Q（面试官原话）：** ES 为什么深分页特别慢？

1. **两段式执行**：scatter 阶段每个分片各取 `from + size` 条本地结果，gather 阶段协调节点归并排序，最后丢掉前 `from` 条只留 `size` 条 `[经验]`。
2. **放大倍数是分片数**：读取量 = `(from + size) × 分片数`；offset=10000、size=10、10 分片 → 100100 条 `[实测]`。
3. **回传最小列**：分片只给协调节点文档 ID 与排序字段，不含完整文档；但协调节点仍要在内存里持有十万条排序键 `[源码]`。
4. **五个后果成链**：性能退化 → 默认 1 万条上限 → 内存 CPU 暴涨 → 集群稳定性受损 → 查询期间数据变动导致分页结果不一致 `[经验]`。

## 关键代码
```json
POST /user/_search
{ "from": 10000, "size": 10, "query": { "match_all": {} } }
```
```go
// 放大倍数 = 分片数，与 size 无关地随 from 线性增长
func readAmplification(from, size, shards int) int { return (from + size) * shards }
```
> 验证：10 分片下 readAmplification(10000, 10, 10) = 100100，即"取 10 条"的一万倍 `[实测]`。

## 总结与追问预判
**放大倍数是分片数**，这是 from+size 的原罪；面试官下一步必问"那怎么办"，接 scroll 与 search_after 两张卡。
