# 1013 悲观锁 vs 乐观锁（Go 语言层，深挖）

> 分类：Go/并发 | 难度：L3 | 题型：综合题 | 频率：中 | 关键词：**锁分类** / **Mutex 悲观** / **CAS 乐观** / **死锁活锁**
> 原文锚点：第 1~73 段「悲观/乐观定义；Mutex 悲观；乐观两实现(CAS/版本号)；死锁+避免六法+TryLock；活锁」

## 一句话总述
本源把锁按"对冲突的预测"分类：**悲观锁（Mutex）先加锁后访问**，**乐观锁（CAS/版本号）先访问、提交时校验**。面试按"分类→Go 落地→故障规避"三步走，并明确与既有卡的边界：Mutex 用法见 925、CAS vs Mutex 取舍见 105、DB 层乐观悲观见 1233、channel 死锁见 1019。

## 思路与架构
- **概念层**：悲观（假设冲突必发生，先锁）/乐观（假设无冲突，提交校验）。这是认知框架。
- **Go 落地层**：Mutex=悲观（sync.Mutex）；乐观无内置类型，靠 atomic CAS 或版本号。二者分别解决"冲突多/冲突少"两端。
- **故障层**：死锁（互等锁，fatal error 不可 recover，六法避免）/活锁（谦让空转）。是锁使用的反面教材。
- **边界层**：与 925（Mutex 调用）、105（atomic vs lock 取舍）、1233（DB 乐观悲观）、1019（channel 死锁）互补，本卡只讲"分类+Go 乐观实现+死锁活锁概念"。

## 方案取舍
- **为何 Mutex 是悲观**：它不预判实际冲突，一律先 Lock——简单但冲突少时有不必要阻塞；此时乐观(CAS)更轻。
- **CAS 的代价**：自旋重试在冲突多时 CPU 飙升，故仅适合极短临界区/低冲突；高冲突退回 Mutex。
- **死锁为何不可 recover**：Go 的死锁是运行时 fatal error，不是普通 panic，`recover` 拦截不住，必须靠设计避免（同序取锁/TryLock/超时）。

## 答题技巧
1. **开口定调**："锁分悲观/乐观，Go 的 Mutex 是悲观锁"。
2. **给落地**：乐观锁在 Go 用 CAS(atomic) 或版本号，无内置类型。
3. **讲故障**：死锁 fatal error 不可 recover + 避免六法 + 活锁辨析。
4. **关联延展**：提 925/105/1233/1019，显示体系化与边界意识。
