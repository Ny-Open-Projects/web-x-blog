# 1255 Redis 过期删除与内存淘汰：两套正交机制，别再混淆

> 分类：缓存 / Redis | 难度：L2 | 题型：概念辨析题 | 频率：高 | 关键词：**过期删除**/**内存淘汰**/**过期字典**/**惰性+周期**/**maxmemory**
> 原文锚点：第 1~35 段「过期删除策略主要是针对设置了过期时间的键值对…如果想实现对过期 key 的删除至少有三种方案…Redis 基于性能和过期数据淘汰的实时性上综合考虑，最终结合使用了惰性删除和周期性删除策略…内存淘汰策略主要是针对 Redis 内存使用达到最大限制的情况」

## 一句话总述
**过期删除**与**内存淘汰**是两套**触发条件正交**的机制：过期删除处理「**key 到了 TTL**」——目的是清理已死数据，方案有惰性/定时/周期三种，**Redis 组合了惰性 + 周期**；内存淘汰处理「**内存达到 maxmemory**」——目的是腾地方给新写入，才有那 8 种 `maxmemory-policy`。前者看**时间**，后者看**空间**，任何「Redis 怎么删数据」的问题都要先问清是哪一种。

## 面试官视角
- 考察意图：这是 Redis 高频混淆题。面试官想看你是否能先把两个概念切开，再分别讲清各自的方案取舍。
- 分档：P5 能说出「一个是过期、一个是内存满」；P6 讲清惰性/定时/周期三方案与 Redis 的组合选择、过期字典 O(1) 判断；P7 能解释**为什么不用定时删除**、主动对比 8 种淘汰策略（另题）并给出主从场景的过期语义。
- 红旗答案：把 `noeviction` 说成「过期了不删」；认为过期 key 是「时间到了立刻消失」——实际上惰性 + 周期组合下，**过期 key 会在内存里多活一小段时间**。
- 惊艳点：「**为什么 Redis 不用定时删除**——每个 key 挂一个 timer，CPU 用来创建/销毁大量定时器，还要维护 timer 结构，对内存主数据库得不偿失」 [经验]。

## 主问答
**Q（面试官原话）：** Redis 的过期删除策略和内存淘汰策略有什么区别？
**A：**
1. **触发条件正交，先切开**：**过期删除**针对**设置了过期时间且到达过期时间**的 key——是「数据生命周期」问题；**内存淘汰**针对**内存使用达到 maxmemory**——是「资源不足」问题。没有 TTL 的 key 永远不会被过期删除，但可能被内存淘汰；内存没满时淘汰策略一个字节都不会动 [源码]。
2. **过期删除的三种候选方案**：① **惰性删除**——客户端访问该 key 时才检查并删除，CPU 零额外开销，但过期 key 若再无人访问就**一直占着内存**；② **定时删除**——每个 key 设过期时间时挂一个 timer，到点立刻删，内存最友好但 **CPU 代价大**（海量 timer 的创建销毁与调度）；③ **周期删除**——每隔一段时间**随机抽一批设了 TTL 的 key** 检查并删除其中过期的，CPU 与内存的折中 [源码]。
3. **Redis 的选择：惰性 + 周期组合**：纯惰性会让冷门过期 key 内存泄漏，纯定时 CPU 扛不住，两者结合——访问兜底、周期抽样主动清，在性能与内存占用之间取得平衡 [源码]。
4. **过期判断的数据结构——过期字典**：设置 TTL 时，Redis 把 key 与其**过期时间戳**存进一张**过期字典（哈希表）**。读 key 时先查过期字典（O(1)）拿到过期时间，与当前系统时间比较：大于当前时间未过期、否则判定过期（惰性删除路径）；不在过期字典里则直接读值。哈希表保证这一步**不随 key 数量增长变慢** [源码]。
5. **内存淘汰是另一套机制**：内存达到 maxmemory 后按 `maxmemory-policy` 淘汰数据腾空间。八种策略 = 范围（allkeys 全部 / volatile 仅过期 key）× 算法（LRU / LFU / random / ttl）+ noeviction；**默认 noeviction（3.0+），内存满即拒写**。策略矩阵与版本细节是另一道题，见 `1257-eviction-policies` [边界]，本卡不重述。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Redis 全版本 | 两套机制正交这个结论恒定 | 概念切割永远第一句 |
| 3.0 前后 | 淘汰默认策略 volatile-lru → noeviction | 版本题归 1257 [边界] |
| 4.0 | 新增 LFU 两策略；`lazyfree` 异步删除 | 大 key 过期删除可配 `lazyfree-lazy-expire` 防阻塞 |
| 主从架构 | **从库不主动做过期删除**，过期由主库删除并同步 DEL | 读从库可能短暂读到已过期数据（3.2+ 对本库读返回 nil 但不删） |
| 持久化 | RDB/AOF 对过期 key 的处理不同（AOF 重写时丢弃已过期 key） | 恢复后已过期 key 不会复活 |

## 关键代码
```go
// 模拟 Redis「惰性删除 + 过期字典」的判断语义（周期扫描同理可扩展）
package main

import (
	"fmt"
	"time"
)

type Store struct {
	data   map[string]string
	expire map[string]int64 // 过期字典：key -> 过期时间戳(纳秒)
}

func (s *Store) Get(k string) (string, bool) {
	if ts, ok := s.expire[k]; ok { // 先查过期字典 O(1)
		if ts <= time.Now().UnixNano() { // 已过期：惰性删除
			delete(s.data, k)
			delete(s.expire, k)
			return "", false
		}
	}
	v, ok := s.data[k]
	return v, ok
}

func main() {
	s := &Store{data: map[string]string{}, expire: map[string]int64{}}
	s.data["k1"] = "v1"
	s.expire["k1"] = time.Now().Add(-time.Second).UnixNano() // 已过期
	_, ok := s.Get("k1")
	fmt.Println("读已过期 key：", ok) // [经验] 输出 false —— 访问触发惰性删除
}
```

## 总结与追问预判
一句话记忆：**「过期删除看时间（TTL 到没到），内存淘汰看空间（maxmemory 满没满），Redis 过期删除 = 惰性 + 周期」**。八种淘汰策略的矩阵与版本默认见 `1257-eviction-policies`；LRU/LFU 的实现取舍见 `1259-lru-vs-lfu` [边界]。常追问「为什么不用定时删除」——按主问答第 2/3 条答 CPU 代价；再追问「过期 key 会不会一直占内存」——答：无人访问时靠周期抽样兜底清掉，若设置了 TTL 的冷 key 极多且周期抽样赶不上，内存可能被过期 key 占满（此时该用 `scan` 主动清理或评估淘汰策略），这是惰性 + 周期组合的已知残余风险 [经验]。
