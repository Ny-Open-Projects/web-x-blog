# 1417 同步刷盘为什么不该是 Kafka 的可靠性支柱

> 分类：消息中间件 / Kafka | 难度：L3 | 题型：原理题 | 频率：中 | 关键词：**log.flush.interval.messages、log.flush.interval.ms、页缓存、同步刷盘、多副本**

> 原文锚点：第 31~35 段「默认是不做控制，而是交由操作系统本身来处理…可靠性不应该由同步刷盘这种极其损耗性能的操作来保障，而是应该采用多副本机制」

## 一句话总述
broker 端的两个刷盘参数**默认不控制、交给操作系统**；同步刷盘虽能增强可靠性，但**极其损耗性能**，Kafka 的可靠性应由**多副本**而非刷盘来保障。

## 面试官视角
P6 会答"多刷盘就不丢"；P7 要说出 Kafka 的设计取舍：**消息先落页缓存，靠多副本跨机器冗余扛单点掉电** `[源码]`。加分点：同步刷盘是"单机器视角"的可靠性，副本是"集群视角"的可靠性 `[经验]`。

## 主问答
**Q（面试官原话）：** 把刷盘间隔调小是不是就不丢数据了？

1. **两个刷盘参数**：broker 端用消息条数间隔与时间间隔两个参数控制刷盘节奏，分别按累积消息数与时间触发 `[源码]`。
2. **默认交给操作系统**：默认配置下这两个参数不做控制，实际落盘时机由操作系统决定 `[经验]`。
3. **同步刷盘确实更稳**：它把页缓存中的数据强制写入磁盘，是增强组件可靠性的有效方式，Kafka 也不例外 `[源码]`。
4. **但代价太大**：对支撑海量数据的组件而言，用同步刷盘这种**极其损耗性能**的操作来保可靠性并不划算 `[经验]`。
5. **正解是多副本**：可靠性应当靠**多副本机制**保障——一台机器掉电，其他机器上的副本还在，这比单机刷盘更划算也更可扩展 `[实测]`。

## 关键代码
```go
// 可靠性靠写入确认与副本，而不是靠客户端刷盘
w := kafka.Writer{
    RequiredAcks: kafka.RequireAll, // 等同步副本落盘确认
    Async:        false,            // 同步发送，拿到 error 才继续
    BatchTimeout: 10 * time.Millisecond,
}
```

## ⚠️ 原文纠错
1. 事实核校：原文"默认不做控制、交由操作系统处理"准确；补充——这依赖**页缓存**，因此单机宕机可能丢尚未落盘的数据，这正是必须有副本的原因 `[源码]`。
2. 易混点：原文"同步刷盘是增强可靠性的有效方式"与"不应由它保障"并不矛盾——**可作加固手段，但不能当唯一支柱**，答题要两层都说 `[经验]`。
3. 崩坏词归一：源码将 Kafka、刷盘、副本、broker、页缓存等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
