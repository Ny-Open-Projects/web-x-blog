# 1312 ES 并发冲突控制深挖

> 分类：Elasticsearch / 并发控制 | 难度：L3 | 题型：深挖 | 频率：中 | 关键词：**乐观并发** / **版本号** / **_seq_no** / **重试** / **实战**
> 原文锚点：第 1~52 段「悲观vs乐观；ES 版本号乐观控制；internal/external/external_GT；_seq_no+_primary_term 7.0 默认」

## 思路与架构
ES 并发控制主线：用"版本/序列号"在**更新提交点**检测冲突，而非在读取点加锁，从而不阻塞并发读：
- 悲观阵营（MySQL 表/行锁）先加锁再访问，冲突被"挡在门外"但牺牲并发。
- 乐观阵营（ES）假定无冲突、读写不阻塞，冲突在更新时被版本校验拦下、交由应用重试。
- 版本依据演进：internal/external（版本号）→ 6.6 起 _seq_no + _primary_term（序列号+代次）→ 7.0 默认。

## 方案取舍
```text
ES 并发控制三依据对比：
──────────────────────────────────────────────────────
依据                  引入/默认        匹配规则              适用
internal              默认             version == 当前       纯 ES 内部
external              全版本           version  > 当前       外部系统按版本同步(客户端自管)
external_GT           全版本           version >= 当前       放宽等号场景
_seq_no+_primary_term 6.6/7.0默认      seq_no 且 primary_term 均匹配  高版本推荐、主分片切换安全

选型要点：
- 新项目直接 if_seq_no/if_primary_term（7.0 默认）
- external 系列需客户端保证版本单调，否则丢更新
- 乐观控制不阻塞读，冲突代价转嫁到"应用重试"
```

## 答题技巧
```text
面试话术（先答思想，再答机制，最后给实战）：
1. 总述：并发控制两思想——悲观(加锁阻塞)、乐观(版本校验+重试)；ES 选乐观
2. 机制一：版本号三类型 internal(等)/external(大于)/external_GT(大于等于)
3. 机制二：6.6 起 _seq_no(序列号)+_primary_term(代次)，7.0 默认；二者均匹配才更新
4. 为什么两个：主分片换代会复用 seq_no，primary_term 区分代次防恢复取错
5. 实战：GET 取版本/seq_no → 带 version/if_seq_no+if_primary_term 更新 → 409 则重取重试
6. 收尾：乐观不阻塞读，冲突代价在应用重试；外部同步务必版本单调
```

> 边界：通用锁理论见 1233（MySQL）、1013-mutex-pessimistic（Go Mutex 属悲观）；ES 文档写入链路见 1314（其提及 version 乐观锁为旁枝）；本卡只深挖"ES 并发冲突控制"不重述各通用机制。
