# 107 分片 map：用 FNV 哈希取模把一把大锁打散成 32 把

> 分类：Go 并发 | 难度：L4 | 题型：实现题 | 频率：中 | 关键词：**分片、sharding、FNV 哈希、取模、锁粒度、两次遍历、return 前解锁**

> 原文锚点：第 24~51 段「为了分散锁的力度，我们可以对 map 的元素进行分片存储，这样锁的力度就会被分散到各个分片，而不是整个 map…我们通过切片来存放这个 map，这样就可以对每个切片的元素进行加锁。切片的大小我们设置为三十二个，也就是把这个 map 分成了三十二个分片…分片下标是通过 key 对分片数量取模来计算的，key 一般是字符串类型，所以需要把字符串映射成一个 int 类型来方便进行取模运算，这里提供了 FNV 的哈希算法，它是一种简单并且快速的哈希算法，特别适合对字符串进行哈希计算」

## 一句话总述
分片 map 把**一个 map 拆成 32 个分片**（用**切片**存放 32 个 map），**每个分片配一把独立的读写锁**，于是**锁的粒度从"整个 map"降到"分片级"**；分片号由 **key 经 FNV 哈希映射成整数后对分片数量取余**得到，**相同 key 必落同一分片、不同 key 被打散到不同分片**，从而获得更高并发性能。遍历则要**两层循环**（先遍历分片、再遍历分片内键值），且**锁必须加在循环内部**。

## 面试官视角
- 考察意图：能否把"降低锁粒度"落成**一个可运行的具体方案**，并说清**哈希选型的理由**与**遍历时的加锁陷阱**。
- 分档：P5 知道可以分片；P6 能说"多个 map + 多把锁"；P7 能补上 **FNV 哈希适合字符串**、**取余即分片下标**、**不同 key 打散**的因果链，以及**遍历必须两层循环、锁在循环内、提前 return 前要显式解锁**这三个工程细节。
- 红旗答案：以为分片数越大越好（**分片多则内存与遍历开销上升**）；或在遍历时把锁加在循环外（等于退化为大锁）。
- 惊艳点：**遍历时的终止语义有两种**——`break` 只跳出当前分片，`return` 才终止全部；而 **`return` 会导致锁得不到释放，所以必须在 return 前再解锁一次** `[源码]`。

## 主问答
**Q（面试官原话）：** 一把大锁太粗，怎么把锁粒度降下来？

1. **结论**：**对 map 的元素进行分片存储**，**用一个切片存放多个 map**，**对每个切片的元素加锁**，**锁的粒度就被分散到各个分片而不是整个 map** `[源码]`。
2. **分片数量**：**切片大小设置为 32**，也就是**把这个 map 分成了 32 个分片**；初始化时**先初始化长度为 32 的切片**，**再通过循环把这 32 个 map 提前声明好**，然后返回分片 map 对象 `[源码]`。
3. **定位分片 · FNV 哈希**：**分片下标通过 key 对分片数量取模计算**；**key 一般是字符串类型，所以需要把字符串映射成一个 int 类型以便取模**；这里使用 **FNV 哈希算法**——**它是一种简单并且快速的哈希算法，特别适合对字符串进行哈希计算**；**本质上就是把字符串映射成一个整数，并且越分散越好** `[源码]`。
4. **定位分片 · 取余**：**把 key 通过 FNV 映射成整数后，对分片数量取余**，**取余的结果就是切片的下标，也就是分片的编号**，据此返回该分片 `[源码]`。
5. **同 key 同分片、异 key 打散**：**由于 key 做的是取余运算，相同 key 经过哈希算法得到的 int 值也相同，最终得到的分片也是同一个**；**而对于不同 key 的操作，就可以把它们打散到不同的分片上**，**这样锁的粒度就被分散，从而获得更高的性能** `[源码]`。
6. **读写锁位置**：**读操作先根据 key 获取对应分片，再从该分片上取 key 对应的值**，**读取加读锁**；**写入操作使用写锁** `[源码]`。
7. **遍历 · 两层循环 + 锁在内部**：**遍历需要两次遍历**——**先遍历全部分片，再遍历这些分片上的全部键值对**；**由于加锁是在分片级别，锁需要放到 for 循环内部实现，而不是在循环外面加锁**，**每操作完一个分片就把该分片级别的锁释放掉** `[源码]`。
8. **终止语义与解锁陷阱**：**如果只是提前终止当前分片上的迭代，用 `break` 跳出对当前分片的迭代**；**如果要终止全部迭代器则需要 `return`**，**但 `return` 之后加锁操作就得不到解锁，所以必须在 `return` 之前再进行一次解锁操作，防止锁得不到释放** `[源码]`。

**加分层：** 分片数通常取 **2 的幂**（如 32），这样"取余"可用位运算 `hash & (n-1)` 替代，比 `%` 更快；这也是工程实现里几乎都选 32/64/128 的原因。

## 关键代码
```go
package main

import (
	"hash/fnv"
	"sync"
)

const shardCount = 32 // 分片数取 2 的幂，可用位运算替代取余

type shard struct {
	mu sync.RWMutex
	m  map[string]any
}

type ShardedMap []*shard

func NewShardedMap() ShardedMap {
	s := make(ShardedMap, shardCount)
	for i := range s {
		s[i] = &shard{m: make(map[string]any)}
	}
	return s
}

// getShard：FNV 把字符串映射成整数，再对分片数取余得到分片编号
func (s ShardedMap) getShard(key string) *shard {
	h := fnv.New32a()
	h.Write([]byte(key))
	return s[uint(h.Sum32())%shardCount]
}

func (s ShardedMap) Set(k string, v any) { // 写 -> 分片级写锁
	sh := s.getShard(k)
	sh.mu.Lock()
	defer sh.mu.Unlock()
	sh.m[k] = v
}

func (s ShardedMap) Get(k string) any { // 读 -> 分片级读锁
	sh := s.getShard(k)
	sh.mu.RLock()
	defer sh.mu.RUnlock()
	return sh.m[k]
}

// Range：两层遍历；锁必须在循环内部，每个分片操作完即释放
func (s ShardedMap) Range(f func(k string, v any) bool) {
	for _, sh := range s {
		sh.mu.RLock()
		stopped := false
		for k, v := range sh.m {
			if !f(k, v) {
				stopped = true
				break // 只跳出当前分片
			}
		}
		sh.mu.RUnlock()
		if stopped {
			return // 终止全部迭代（锁已在上面释放，安全）
		}
	}
}
```

## 总结与追问预判
**最爱追问的是"分片数选多少"**——**没有固定答案**，常见 32/64/128：太少则锁竞争仍明显，太多则**内存占用与遍历开销上升**（遍历要遍历全部分片）。追问常接"和 `sync.Map` 比呢"——`sync.Map` 是**读多写少 + 写一次读多次**的最优解，且内部已用类似分片思想；分片 map 的优势是**类型安全（配泛型）与可预测的写性能**，劣势是**遍历要扫全部分片、且分片数固定后不易调整**。
