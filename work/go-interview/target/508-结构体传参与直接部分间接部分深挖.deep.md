# 508 结构体传参与直接部分/间接部分（深挖）

> 分类：Go 语言基础 | 难度：L3 | 题型：原理深挖 | 频率：高 | 关键词：**值传递、直接部分、间接部分、逃逸分析、方法集、copylocks**

> 原文锚点：第 1~94 段「从切片、map、string 到结构体，统一由直接部分与间接部分解释」

## 思路与架构

一个模型打天下：Go 的**赋值与传参都只拷贝直接部分**，含指针的类型在拷贝后**共享间接部分**。按"变量的头部里有没有指针"给类型归类：

- **纯值类**：int、float、bool、数组、不含指针字段的结构体 —— 拷贝即隔离，函数内怎么改都出不去。
- **头部类**：slice（ptr/len/cap）、string（ptr/len）、interface（类型指针 + 数据指针）—— 拷头部，共享底层。
- **纯指针类**：map（指向 hmap 的指针）、chan、func、`*T` —— 拷的就是指针本身，改内容必然外可见。

结构体是**复合体**：对它的拷贝是逐字段的浅拷贝，**字段的类型决定它有没有间接部分**。于是同一个结构体里三种现象并存且互不矛盾：`Name string` 赋新值改不到外面；`Names []string` 通过下标改元素能改到外面；`Names` 整体赋新切片又改不到外面。答题时把这三种情况串成一条规则讲，比背结论有说服力。

## 方案取舍

- **传值**：适合小结构体（约三到四个机器字以内）、只读语义、希望参数**不逃逸**到堆上（省一次分配、少一轮 GC 扫描）。代价是大结构体逐字段拷贝的成本随字段数线性上升。
- **传指针**：适合要改调用方、结构体大、含不可拷贝字段（锁）的场景。代价是逃逸到堆带来的分配与 GC 压力、可能的 nil 解引用、以及"远距离副作用"造成的可读性损失。
- **不要为省拷贝过早传指针**：很多几个字段的值对象传值反而更快，因为省掉了逃逸与 GC；只有 `go test -bench` 加 `-benchmem` 显示拷贝确实是热点时才值得换，避免凭直觉优化。
- **隔离共享**：不想让函数污染调用方的切片字段，传参前 `slices.Clone`；反过来，想让结构体"真深拷贝"必须逐字段处理指针字段，一次赋值只是浅拷贝。
- **含锁结构体**：一律以 `*T` 传递并禁用值接收者，靠 `go vet` 的 copylocks 静态兜底，别依赖人工 review。

## 答题技巧

1. **开场定调**：先说"Go 只有值传递，拷贝直接部分、共享间接部分"，一句话把题目收进模型。
2. **分类给证据**：用纯值类 / 头部类 / 纯指针类三类举例，说明"共享且可写"与"共享但只读"的差别，string 与 slice 的对比最有说服力。
3. **反直觉三连**：结构体整体赋值改不到外面；改切片元素能改到外面；扩容之后连拷贝双方都分家。三句话覆盖绝大多数追问。
4. **落到工程**：提到 `strings.Builder`、append 这类"看着像改、其实是换地址"的操作，展示真实编码经验。
5. **版本锚点**：语义自 Go 1.0 起稳定；Go 1.21 起有 `slices.Clone`，隔离切片优先用它；含锁结构体从 Go 1.7 起由 `go vet` 的 copylocks 检查。
6. **收尾话术**："先问要不要改调用方，再看结构体大不大，含锁字段一票否决，其余交给 benchmark 数据决定"——把判据压缩成一句可背的话。

## 细节与核心 API

```go
type Big struct{ data [1024]byte }
func byVal(b Big)   {} // 整体拷贝 1KB
func byPtr(b *Big)  {} // 仅拷贝指针 8 字节
// 经验：> 几字节省份不划算就用指针；需“修改调用方”必须用指针
// 直接部分（直接字段）vs 间接部分（指针/切片指向的底层数据）
type Node struct {
    Val  int        // 直接部分，拷贝即复制
    Next *Node     // 间接部分，拷贝后新旧节点共享同一 Next 指向的对象
}
// 因此按值拷贝结构体不等于深拷贝其指针指向的数据
```
