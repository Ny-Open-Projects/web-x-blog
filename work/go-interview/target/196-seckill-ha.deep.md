# 196 秒杀高可用设计权衡（深挖）

> 分类：架构设计 | 难度：L3 | 题型：设计题 | 频率：中 | 关键词：**异地多活成本** / **降级指标体系** / **过载保护**
> 原文锚点：第 102~145 段「实现基本可用要简单很多…手动降级自动降级…过载保护直接拒绝」

## 思路与架构
秒杀高可用的主线是「保核心下单链路、牺牲非核心与强一致」：流量层削峰（MQ 排队）→ 接入层限流/过载拒绝 → 应用层降级非核心 → 数据层异地多活兜底灾难。CAP 决定走 AP，BASE 给出落地姿态。

```mermaid
flowchart LR
    A[流量洪峰] --> B[消息队列削峰]
    B --> C[网关限流过载拒绝]
    C --> D[应用降级非核心]
    D --> E[核心下单 AP]
    E --> F[异地多活兜底]
```

- 削峰：把同步下单转异步排队，瞬时流量被「拉平」。
- 限流/过载：令牌桶/漏桶在入口拒绝超额请求，避免雪崩。
- 降级：超时/失败数/故障/限流四类触发，关广告/审计/风控等非核心。
- 多活：机房级灾难时切流，代价是 RTT 与一致性。

## 方案取舍
| 策略 | 收益 | 代价 | 适用 |
|---|---|---|---|
| 异地多活 | 抗机房级灾难 | 成本高×N、RTT 升、强一致难 | 核心业务容灾 |
| MQ 削峰 | 拉平瞬时流量 | 增加延迟、需保证不丢 | 秒杀预订单 |
| 手动降级 | 人工精准可控 | 响应慢、依赖人 | 已知大促预案 |
| 自动降级 | 实时、免值守 | 阈值难调、可能误伤 | 7×24 系统 |
| 过载拒绝 | 防雪崩保核心 | 部分用户被拒 | 极限峰值 |

选型结论：**先保核心下单（AP+最终一致），再逐级加容灾**。异地多活是「灾难兜底」而非日常手段，成本与一致性代价决定它只给核心业务。**不适用边界**：金融强一致场景不宜多活，应优先 CP。

## 细节与核心 API
- `令牌桶/漏桶`：限流算法，前者允许突发、后者平滑。
- `配置中心`：手动降级的开关载体（如 Nacos/Apollo），改后推送或定时拉取生效。
- `超时降级`：RT 超阈值且非核心即降级。
- `失败次数降级`：连续失败达阈值触发，异步线程监控恢复后撤销。
- `限流降级`：访问达阈值直接降级，返回排队/错误页。
- `软状态`：容忍节点间短暂不一致的中间态，是 BASE 的关键。

## 答题技巧
- 30 秒版：秒杀高可用=保核心、牺牲非核心与强一致；削峰+限流+降级+多活。
- 3 分钟版：CAP 选 AP → BASE 三要素 → 四类基本可用策略 → 异地多活兜底灾难。
- 白板版：画上面 flowchart，每层标一个手段。
- 话术模板：「先问核心链路是什么，再谈怎么保它、怎么舍非核心。」
- 不会怎么接：诚实说「具体阈值我们压测得出，思路是分层降级 + 容灾兜底」。
