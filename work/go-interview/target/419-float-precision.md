# 419 Go 浮点精度损失

> 分类：Go 数值类型 | 难度：L3 | 题型：陷阱题 | 频率：高 | 关键词：**IEEE754**/**0.1+0.2**/**结合律**/**float32/float64**
> 原文锚点：第 27~67 段「浮点精度、结合律与位数」

## 一句话总述
浮点遵循 IEEE754，**很多十进制小数无法精确表示**，导致 `0.1+0.2≠0.3`、不满足结合律、且 `float32` 仅约 6~7 位十进制有效——这些都是表示精度问题，不是独立舍入规则。

## 面试官视角
- 考察意图：经典 `0.1+0.2` 陷阱 + 精度位数 + "四舍不一定五入"的本质。
- 分档：P5 知 0.1+0.2≠0.3；P6 知 float32 位数少；P7 知不满足结合律、舍入本质。
- 红旗答案：以为浮点运算"和数学一样精确"，或以为"四舍不五入"是独立规则。
- 惊艳点：点出"四舍不五入"其实是 float32 存储值偏差导致的边界表现，非规则。

## 主问答
**Q（面试官原话）：** 为什么 0.1 加 0.2 不等于 0.3？
**A：**
1. **不可精确表示**：0.3 等很多小数用二进制科学计数法无法精确凑出，float32 只有 2^32 个状态（约 40 亿），远不够覆盖所有小数 → 必有精度损失。
2. **常量 vs 变量**：常量在**编译期**求值（如 `0.3` 常量相加可能被精确折叠），变量走 IEEE754 运行时转换 → 变量相加才有损失。
3. **不满足结合律**：`(a+b)+c` 与 `a+(b+c)` 因精度损失顺序不同结果可能不同。
4. **位数差异**：float32 有效数字 23 位 → 约 6~7 位十进制准确；float64 52 位 → 约 15~17 位。`%f` 默认打印 float32 仅 6 位小数可靠。

## 关键代码
```go
fmt.Println(0.1 + 0.2 == 0.3) // false
fmt.Println(float32(0.1) + float32(0.2) == float32(0.3)) // false
```

## 总结与追问预判
浮点精度损失源于二进制无法精确表示多数小数；0.1+0.2≠0.3、不满足结合律都是此因；float32 仅 ~6-7 位有效。金额等场景用整数分或 decimal，别用 float 比较相等。

## ⚠️ 原文纠错
1. 事实核校： [经验] 0.1+0.2≠0.3、常量编译期求值无损失、变量有损失、不满足结合律、float32 ~6-7 位/float64 ~15-17 位，正确。
2. **补正**：原文"四舍但不一定五入"表述误导——本质仍是 float 存储值偏差导致四舍五入边界异常（且 Go 用 round-half-to-even），并非独立舍入规则。
