# 161 依赖倒置原则 DIP

> 分类：设计模式/原则 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**依赖抽象** / **面向接口** / **高层低层解耦**
> 原文锚点：第 97~100 段「高层模块和低层模块都依赖于抽象接口…不依赖具体实现，降低耦合」

## 一句话总述
依赖倒置原则（DIP）：高层与低层模块都依赖**抽象接口**，而非彼此依赖具体实现；调用方面向接口编程，具体实现可热插拔。

## 面试官视角
- **意图**：是否真用接口解耦过模块，而非只背「依赖抽象」。
- **P5** 能说「面向接口而非实现」 / **P6** 能举 DB 访问依赖抽象接口、换驱动不改高层的例子 / **P7** 知倒置是「调用方定义接口」而非实现方定义。
- **红旗**：以为「用了 interface 关键字就是 DIP」；在高层和具体实现间直接 new。
- **惊艳点**：DIP 的接口由**调用方**定义（Go 的「消费端接口」），实现方被动满足——验证：`go doc` 惯例 go1.26.5 `[经验]`。

## 主问答
**Q（面试官原话）：** 依赖倒置原则怎么落地？
**A：**
1. **结论**：高层模块定义它需要的抽象接口，低层实现该接口；二者都依赖接口，不互相依赖具体类型。
2. **机制**：抽象层把易变的具体实现（如某数据库驱动）隔离在边界后，换实现时高层零改动 `[源码]`。
3. **边界**：别为简单、稳定的依赖也强加一层接口，否则只是增加间接层而无收益。
**加分层：** DIP 与 OCP 合力——抽象稳定即可扩展、可替换，是框架与插件化的地基。

## 总结与追问预判
- DIP = 高层低层同依赖抽象；接口由消费端定义。
- 预判：接口隔离 → 见 161-isp；开闭原则 → 见 161-ocp。
