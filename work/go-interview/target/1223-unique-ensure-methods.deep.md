# 1223 唯一索引设计 深挖

> 覆盖源 12-23 全文：NULL 例外 + 逻辑删除联合唯一 / deleteID + 大字段 MD5 哈希。主卡已给三类场景与 SQL 模板，本附录做方案取舍与索引长度限制推算。

## 思路与架构

```text
唯一性保障路径
├─ NULL 例外 → 字段 NOT NULL
├─ 逻辑删除 → email+deleteID 联合唯一(可反复删) 优于 email+status(只能删一次)
└─ 大字段 → 取 MD5/SHA 存哈希列建唯一索引(绕开长度限制 + 省磁盘)
```

## 方案取舍
- **status vs deleteID**：`status` 只有 0/1 两态，`email+status` 联合唯一后同一 email 最多删一次，再次删除仍冲突；`deleteID` 用被删行主键填充，每次删除取值必然不同，天然满足联合唯一且支持反复删除——逻辑删除场景优先选 `deleteID` [经验]。
- **直接建索引 vs 哈希列**：大字段直接建唯一索引受索引长度 **3072 字节**限制，utf8mb4 每字符 4 字节 → 上限 **768 字符**（3072÷4），超出即报错；且长索引本身占大量磁盘。存哈希列既绕开长度限制又省空间，代价是需知晓哈希碰撞概率极低但理论存在 [经验]。
- **UNIQUE KEY vs PRIMARY KEY**：主键也具唯一性且不允许 NULL，但一表只能有一个，业务唯一性通常用 UNIQUE KEY 承载而非挤占主键。

## 答题技巧
- 被问「唯一索引还会重复吗」先给结论**不一定**，再按 NULL / 逻辑删除 / 大字段三类展开，显结构化 [经验]。
- 长度限制要会心算：3072 字节 ÷ 单字符字节数（utf8mb4 为 4）= 768 字符 [经验]。
- 主动边界到 `1236`(唯一索引加锁)、`1211`/`1221`(索引原理与设计)，构成索引全栈 [边界]。
