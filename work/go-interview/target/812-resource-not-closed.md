# 812 资源未关闭导致内存泄漏

> 分类：Go 运行时 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**资源泄漏**/**defer 时机**/**文件句柄**
> 原文锚点：第 64~76 段「打开文件资源而不释放…for 循环内 defer 关闭」

## 一句话总述
打开的文件、连接、句柄若不及时 `Close`，底层资源会一直占用；尤其在 **for 循环内用 `defer` 关闭**时，`defer` 要等函数结束才执行，导致资源在函数返回前大量堆积。

## 面试官视角
- 考察意图：是否理解 `defer` 的"函数级"执行时机，以及资源句柄本质有限。
- 分档：P5 知"开文件要 Close"；P6 知"for 内 defer 会堆积"；P7 能把处理封装成函数让 defer 立即生效。
- 红旗答案：认为"for 里写 defer 每次循环都会关"、以为 defer 是块级作用域。
- 惊艳点：指出 **`defer` 绑定的是函数而非循环块**——这是 for 内 defer 失效的根因 `[经验]`。

## 主问答
**Q（面试官原话）：** for 循环里反复打开资源，怎么就泄漏了？
**A：**
1. **结论**：资源句柄数量有限；不关闭会堆积，且 **`defer Close()` 要等外层函数返回才执行**，不是每次循环结束。
2. **机制**：在 for 里 `f, _ := os.Open(...); defer f.Close()`，所有 `defer` 都排到函数退出时才统一执行，十万个文件句柄在函数结束前一直敞着。
3. **边界**：把"打开+处理+关闭"封进一个函数，函数返回即触发 `defer`，句柄随循环迭代即时释放，不再堆积。

**加分层：** 除文件外，数据库连接、HTTP response.Body、`rows` 结果集、临时文件都需显式 Close，否则同样泄漏。

## 关键代码
```go
// 错误：for 内 defer，十万个句柄等到函数结束才关
func bad() {
    for i := 0; i < 100000; i++ {
        f, _ := os.Open(fmt.Sprintf("file%d", i))
        defer f.Close() // 全部排队到 bad() 返回
    }
}

// 正确：封装成函数，每次迭代结束即 Close
func good() {
    for i := 0; i < 100000; i++ {
        process(fmt.Sprintf("file%d", i))
    }
}
func process(name string) {
    f, _ := os.Open(name)
    defer f.Close() // 函数返回立即执行
    // ... 处理 ...
}
```

## 总结与追问预判
`defer` 是函数级而非块级，for 内直接 defer 会堆积资源。修法是把"开-用-关"封进函数。追问接"goroutine 泄漏"与"pprof 定位"。
