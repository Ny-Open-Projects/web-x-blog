# 188 平均负载归因与容器环境陷阱 深挖

> 覆盖源 18-8 全文：平均负载的严格定义（R 态 + D 态的指数衰减平均）、与 CPU 使用率的非一一对应关系、用核数折算判断是否过载、1/5/15 分钟三值的趋势读法、以及 CPU 密集与 IO 密集两类负载的分野。主卡已给定义、判据与巡检示例，本附录做「三种负载形态的归因矩阵」「为什么包含 D 状态」「指数衰减的工程含义」「容器里的失效点」「排查顺序」五层深挖。

## 思路与架构

```text
load 高
├─ 先归一化: ratio = load1 / 有效核数
│   ├─ ratio < 0.7  观察
│   ├─ 0.7~1.0      接近满载, 看趋势
│   └─ >= 1.0       过载
├─ 再看 CPU 使用率做归因
│   ├─ CPU 高 + load 高 → CPU 密集: 算力瓶颈, 优化算法/扩容/限流
│   ├─ CPU 低 + load 高 → IO 密集/锁竞争: D 状态堆积, 查磁盘与存储
│   └─ CPU 高 + load 高 + 运行队列长 → 调度饱和: 并发度过高
└─ 最后看 1/5/15 趋势
    ├─ 三者接近 → 平稳
    ├─ 1min << 15min → 高峰已过
    └─ 1min >> 15min → 正在恶化, 持续观察
```

## 方案取舍
- **为什么负载要算进 D 状态**：不可中断状态是内核为保证「进程数据」与「落盘数据」一致性而设的保护机制，最典型场景就是等硬件设备的 IO 响应。如果把它排除在外，磁盘已经堵死、一堆任务卡在数据一致性关键路径上的情况，在负载指标上却毫无体现——**这个指标就失去了最有用的报警能力**。所以「包含 D 状态」是刻意设计，不是缺陷 [经验]。
- **为什么用指数衰减而不是滑动窗口**：滑动窗口要给每个样本留位置，开销与内存随窗口增长；指数衰减只需保留**上一个平均值**，新值按常数加权叠加即可，O(1) 空间。工程含义很重要：**越靠近当下权重越高，所以 1 分钟值对突发敏感、15 分钟值抹平抖动**。判断趋势时必须三值同看，单看 1 分钟容易被瞬时抖动骗，单看 15 分钟又会漏掉刚开始的恶化 [经验]。
- **归因不能只看两个指标**：`load + CPU 使用率` 只能粗分三类。真正定位需要再加 **`wa`（IOwait）、运行队列长度、D 状态任务数、上下文切换频率**——CPU 低而 load 高时，如果 `wa` 也高就是存储瓶颈，如果 `wa` 不高却在大量 D 状态，就要怀疑**锁竞争、网络存储、NFS 挂载卡住**这类更隐蔽的原因 [经验]。
- **容器里的两处失效**：其一，`/proc/cpuinfo` 在多数容器中对 `/proc` 未做隔离，读出来的是**宿主机核数**，据此判断「未过载」会严重误判；其二，容器内看到的 load average 往往也是**宿主机的**。正解是取 **cgroup 的 CPU 配额**（cpu.max / cpu.cfs_quota_us ÷ period）折算成有效核数，再拿它去比 load [经验]。
- **排查顺序建议**：① 归一化判真过载 → ② 看 CPU 使用率粗分 CPU 密集 / IO 密集 → ③ 用 `wa` 与 D 状态数收敛域 → ④ 落到进程/线程级（谁在跑、谁在等）→ ⑤ 再谈扩容或优化。**跳过前三步直接扩容是最常见的浪费** [经验]。

## 答题技巧
- 开口先纠偏：「load 不是 CPU 使用率」，一句话把概念地基打稳，这是这道题最大的分水岭 [经验]。
- 把定义说精确：**「单位时间内可运行 + 不可中断的活跃任务数的指数衰减平均」**，三个定语缺一个都显出背得不牢 [经验]。
- 被追问「为什么包含不可中断」→ 答「为了不漏报 IO 堵死这类最需要报警的情况，这是刻意设计」 [经验]。
- 被追问「负载多高算高」→ 别报绝对值，答「**看与核数的比值**」并举例：负载 3 在 3 核满载、6 核半闲、1 核则 2/3 任务抢不到 [经验]。
- 主动边界到 `187-process-states`（R/D/S/Z 状态机，本卡不重述 D 状态的转换细节）、`1820-user-kernel-space`（陷入内核的代价）、`1829-scheduling-overview.deep`（调度器与运行队列），构成 Linux 性能排查全栈 [边界]。
