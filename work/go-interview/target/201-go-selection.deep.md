## 思路与架构
「为什么选/不选 Go」本质是**技术选型权衡**：把语言特性（并发/GC/部署/构建）映射到问题域（云原生/IO 并发/微服务），同时诚实标注不适域（GUI/系统底层/硬实时/纯 CPU）。

```text
Go 选型决策框架
  问题域 ───────────────► 语言特性匹配度 ───────────► 选/不选
  微服务/API/网关         goroutine+单二进制+低开销    ✅ 首选
  云原生基础设施          Docker/K8s 生态同源         ✅ 首选
  CLI/ DevOps 工具        单二进制跨平台分发           ✅ 首选
  GUI/桌面               生态缺失                     ❌ 不选
  操作系统/驱动/内核      GC+运行时不适合             ❌ 不选
  硬实时                  GC 停顿破 deadline          ❌ 不选
  纯 CPU 密集(无并发)    优势不显(逊于 C/Rust)        ⚠️ 慎选
```

## 方案取舍
| 维度 | Go 表现 | 对比 | 结论 |
| --- | --- | --- | --- |
| 并发模型 | goroutine 原生、轻量 | vs Java 线程重、C 手写难 | **强项** |
| 部署 | 单静态二进制 | vs JVM 需运行时、Python 需解释器 | **强项** |
| 内存管理 | 带 GC | vs C/Rust 手动/所有权 | 效率换简单 |
| 执行效率 | 接近 C | vs C/Rust 略慢（GC/抽象） | 够用 |
| 生态成熟度 | 云原生/后端强 | vs Java 企业库更全 | 领域偏 |
| 泛型 | 1.18+ 完备 | vs Java/C++ 早有 | 已补齐 |

**取舍结论**：Go 是「**并发密度高 + 部署简单 + 团队迭代快**」场景的最优解之一；在这些维度不重要的场景，它的相对优势消失，应按上表慎选。

**诚实边界**（关键）：源只讲优势，工程选型必须补「不适用域」——GUI/系统底层/硬实时/纯 CPU 密集非 Go 强项；1.18 前泛型短板已补。完整选型观 = 优势 + 边界。

## 答题技巧
1. **优势三维 + 边界三维**：开口「强在并发/部署/构建，弱在 GUI/底层/硬实时」，平衡立现，胜过单向鼓吹。
2. **甩基座项目**：Docker/K8s/etcd/TiDB/Prometheus 全是 Go——证明生态非蹭热度。
3. **定位金句**：「Go = C 性能 + Python 效率，互联网时代的 C，替代 C 不是 Java」。
4. **版本演进加分**：泛型 1.18 落地补齐短板；GC 停顿从 STW 优化到亚毫秒（1.5/1.8）。
5. **避坑**：不说「Go 最快」（纯 CPU 不比 C/Rust）；不说「Go 万能」（GUI/底层非其域）；不把「云原生语言」说成「只能写云原生」（CLI/工具同样是强项）。
