# 1911·深 垂直拆表的三条动机：从"表太大"到"页缓存命中率"

> 分类：数据库 / 表设计 | 难度：L4 | 题型：设计题 | 频率：中 | 关键词：**垂直拆分**/**冷热分离**/**页缓存**/**数据页密度**/**写放大**/**二次回查**/**大字段外置**
> 原文锚点：第 14~27 段「在业务上我们打开这个评论页面的时候，我们会先去展示评论列表，因此查询频率最高的就是评论列表了…如果楼层深度不可控，就会导致慢查…表数据的频繁更新会使得页缓存失效的概率变高，从而降低了缓存的命中率…让 MySQL 的一个数据页上可以缓存更多的数据行，而且大字段带来的大 IO 会拖慢评论和回复元数据的获取」

## 思路与架构

垂直拆分不是"表宽了就砍一刀"，而是**按访问特征把列分成三类**：

```text
按访问特征给列分类
─────────────────────────────────────────────────────
A 类：高频读 + 低频写    → 留在主表
      （id / weibo_id / user_id / status / top_flag / 时间）
      理由：这些是列表页每刷一次都要读的，且几乎不更新
      ⇒ 数据页长期干净，页缓存命中率极高

B 类：高频写（计数器）   → 拆到汇总表
      （first_floor_cnt / total_reply_cnt）
      理由：每来一条回复就 +1，是纯写放大源
      ⇒ 留在主表会让主表页持续变脏，把 A 类的缓存收益一起赔掉

C 类：低频读 + 大体积     → 拆到内容表（甚至 KV 库）
      （content TEXT）
      理由：只有展开时才读，但体积大
      ⇒ 留在主表会压低 16KB 数据页的行密度，让 A 类查询多花 IO
```

三条动机的**量化说法**（面试里说出来就是加分）：

1. **数据页密度**：InnoDB 数据页默认 **16KB**。一条评论的元数据约几十字节，而内容动辄数百字节甚至数 KB。把 `TEXT` 留在主表，单页行数可能从**数百行掉到十几行**——同样的列表查询，缓存页要多一个数量级。
2. **页缓存命中率**：MySQL 依赖**操作系统页缓存**加速读。页一旦被写脏，缓存收益下降。计数器每来一条回复就 `+1`，若与主表同页，等于**用最高频的写去污染最高频的读**。
3. **查询路径简化**：评论列表查询是 `WHERE weibo_id = ? ORDER BY ... LIMIT n`。如果回复混在同表，就必须额外过滤 `parent_id = 0`，**索引设计与执行计划都变复杂**，而且**混表后行数翻几倍**，即使走索引代价也更高。

## 方案取舍

```text
方案 A：单表宽表（含 content、含计数）
  优：一次查询拿到全部，无二次回查；开发最简单
  劣：页密度低、缓存命中差、写读互相污染；行数膨胀后索引代价高

方案 B：垂直拆成 5 张（本设计）  ← 选中
  优：三类访问特征各自最优化；列表查询走最窄的页
  劣：取内容要二次回查（用 IN 批量化压成一次往返）；
      JOIN 变多，事务边界要重新设计

方案 C：主表 + 内容直接进 KV（Redis / RocksDB）
  优：MySQL 只承担结构化元数据，容量与 IO 压力最小；KV 天然适合内容
  劣：多一套存储的一致性与运维；内容无法参与 SQL 查询（如全文检索）
```

- **拆表后事务边界怎么处理**：跨表写入要么用**本地事务**（同库，5 张表可放一个事务），要么**异步化**。评论系统通常选择**先写主表、内容异步补**，但要接受"元数据已可见、内容短暂为空"的最终一致——需前端容错。
- **二次回查怎么优化**：分页拿到 10 条评论 id 后，**用一次 `IN` 批量取内容**，把 10 次往返压成 1 次。这是拆表设计的**标准配套动作**，忘了讲会被追问。
- **什么时候不该拆**：如果**内容总是和元数据一起被读**（比如详情页必须展示正文），且体量不大（几百字节以内），拆出去反而多一次 IO。**拆的判据是"是否被同频访问"，不是"是否大"**。
- **楼层折叠的取舍**：换来**可控的查询深度**（一次索引范围扫描），付出**用户需手动展开**。这个取舍在微博、朋友圈、视频号评论里已被普遍验证——**没人会真的展开到第 50 层**。

## 答题技巧

- **开口先分类，再讲表**。按"A 高频读 / B 高频写 / C 大体积"给列分类，再对应到具体表名，结构立刻清晰。
- **把"16KB 数据页"和"页缓存命中率"两个词说出口**。绝大多数候选人只会说"大字段影响性能"，说不出**机制**，这就是差距。
- **主动交代代价**：拆表不是免费午餐，要说清"**取内容变成二次查询，用 `IN` 批量化压成一次往返**"。只讲收益不讲代价的设计题答案，面试官一定会追。
- **用"访问特征"而非"表的宽窄"作为判据**：一句「**拆的依据是列是否被同频访问，不是它大不大**」能直接拉到设计层。
- **别踩的坑**：不要把垂直拆分和分库分表混为一谈——**垂直拆解决"一行太宽/读写互相污染"，水平拆解决"行数太多"**，两者动机完全不同。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| MySQL 5.7 / 8.0（InnoDB） | 数据页 **16KB**，行溢出阈值约页的一半 | 大字段触发溢出页，更慢 |
| MySQL 8.0 起 | `JSON` + 函数索引可用 | 楼层树可换闭包表 |
| 使用独立表空间（`innodb_file_per_table`） | 默认开启 | 单表单独文件，拆表收益更直观 |
| 内容量达 TB 级 | MySQL 不再经济 | 迁 KV / 对象存储 |
| 分库分表引入后 | 跨片 JOIN 不可用 | 垂直拆表需在**同一片内**完成 |
