# 821 静态锁分级与 m 持锁上限

> 分类：并发模型 / runtime | 难度：L4 | 题型：八股题 | 频率：低 | 关键词：**m.locks 计数器**/**locksHeld 数组**/**staticlockranking**/**throw 而非 panic**
> 原文锚点：第 26~28 段「m 最多可以持有十个锁……lose 长度是十的一个数组」
> 边界：本卡管「上限 10」的真相与两种失败模式；m.locks 计数器与自旋/note 的基础版见 815。

## 一句话总述
`m.locks` 只是**一个 `int32` 计数器**（防下溢）；`m.locksHeld [10]heldLockInfo` 才是「10 把锁」的真相，但**它只在 `GOEXPERIMENT=staticlockranking` 下被维护**——超 10 把不是「装不下」，是直接 `throw`（`fatal error`，`recover` 无效）；**默认构建没有这个限制**。原文「m 最多持有十个锁」缺了这个前提。

## 面试官视角
- 考察意图：考「有没有数过字段」。多数人答不出 `m.locksHeld` 这个名字，也答不出它由**编译期实验开关**控制。
- 分档：P5 知道 runtime mutex 有「最多 10 把锁」的说法；P6 说清 `m.locks` 是计数器（`lock2` 加一、`unlock2` 减一），`locksHeld` 记**锁地址 + rank**；P7 知道这依赖 `GOEXPERIMENT=staticlockranking`，默认构建下 `getLockRank` 直接 `return 0`。
- 红旗答案：「超了会拒绝/阻塞」——因果半错，默认构建**没这个限制**，开了实验是 `throw`（fatal，**recover 无效**）；「lose 是长度 10 的数组」——字段名错，真名 `locksHeld`。
- 惊艳点：`GOEXPERIMENT=staticlockranking go run` 一个**只做 `sync.Mutex` 加解锁**的程序，直接 `fatal error: lock ordering problem` [实测]。

## 主问答
**Q（面试官原话）：** 你说 M 最多能持有十个锁，超了会怎样？
**A：**
1. **先纠偏**：**方向对、机制错**。默认构建**没有这个限制**；`m.locks` 只是 `int32` 计数器。10 把上限来自 `m.locksHeld [10]heldLockInfo`，**但它只在 `GOEXPERIMENT=staticlockranking` 下维护** [源码]。
2. **再给机制**：`lock2` 里 `gp.m.locks++`，并检查 `if gp.m.locks < 0 { throw("runtime·lock: lock count") }`——**防计数下溢**，不是上限。开了实验才走 `systemstack`，第 11 把 `throw("too many locks held concurrently for rank checking")`（`lockrank_on.go:77-83`）[源码]。
3. **最后给边界**：该实验**默认关闭**（`lockrank_off.go`）；关掉时 `getLockRank` 直接 `return 0`，检查路径被编译器消掉。**为什么默认关闭**：静态锁排名要给每把 runtime 锁**硬编码 rank**，漏配就误报 fatal；实测开实验后连 `sync.Mutex` 内部的 `rwmutex.rlock` 都被判倒序——**该实验与当前 runtime 不同步，不适合生产** [实测]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| `locksHeld [10]` 存在但**默认不维护** | Go 1.x 长期 | 逻辑在 `lockrank_on.go` / `lockrank_off.go` 二选一（build tag） |
| `staticlockranking` 非默认 | Go 1.x 长期 | 讲「10 把上限」**必须带这个前提** |

| `m.locks` 防的是**负数** | Go 1.x 长期 | `lock2` 判 `locks < 0` 抛 `lock count` |

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	var wg sync.WaitGroup
	for i := 0; i < 200; i++ {
		wg.Add(1)
		go func() { defer wg.Done(); mu.Lock(); mu.Unlock() }()
	}
	wg.Wait()
	fmt.Println("200 个 goroutine 竞争 sync.Mutex：正常结束")
}
```

实测输出（go1.26.5 darwin/amd64）[实测]：

```text
$ go run .                                    # 默认构建
200 个 goroutine 竞争 sync.Mutex：正常结束

$ GOEXPERIMENT=staticlockranking go run .
fatal error: lock ordering problem
panic during panic
runtime.checkRanks(...)             lockrank_on.go:166
runtime.acquireLockRankAndM(...)    lockrank_on.go:119
runtime.(*rwmutex).rlock(...)       rwmutex.go:75
runtime.preemptM(...)
$ echo $?
1
```

这是「10 把锁」机制最硬的证据：一个**只做 `sync.Mutex` 加解锁**的普通程序，在该实验下直接 fatal error，栈顶是 `preemptM → rwmutex.rlock → checkRanks`——是 **runtime 自身内部锁**被判倒序 [实测]。注意：报的**不是** `too many locks held`（第 11 把），而是 `lock ordering problem`（序错了）——**两种失败模式**，原文只提前者。

## 总结与追问预判
一句话记忆：**「`m.locks` 防下溢，`locksHeld` 防（实验下的）锁序倒置，默认构建两者只有一个」**。追问预判：per-P 缓存挂在谁身上见 815-p的内存缓存；P 状态机见 815-p的标识与状态机；两种失败模式的完整对照见本卡深挖 [边界]。

## ⚠️ 原文纠错
1. 「lose 是长度 10 的数组，存储 m 持有的锁信息」→ 真名 **`m.locksHeld [10]heldLockInfo`**，元素是 `{lockAddr uintptr; rank lockRank}`，**不是只存数量**。
2. 「m 最多能持有的锁的数量是十个」→ **缺前提**：仅 `GOEXPERIMENT=staticlockranking` 下成立；默认构建**无此限制**。
3. 「preemptGen 记录对 m 完成信号抢占的次数」→ 方向对，但**没说清它的用途**是「检测抢占请求**失败**」而非统计次数。
