# 147 为什么分区存储：打破单机 IO 瓶颈，换取水平扩展

> 分类：消息队列 / Kafka | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**分区、IO 瓶颈、水平扩展、负载均衡、高伸缩性、分片**

> 原文锚点：第 1~10 段「同一个 topic 的消息是分散存储到不同的分区的…如果一个 topic 只对应一个文件，那么这个文件所在的机器 IO 就会成为这个 topic 的性能瓶颈，而分区解决了这个问题…通过增加分区的数量可以实现水平扩展，分区的作用其实是提供负载均衡的能力，或者说是为了实现系统的高伸缩性…MongoDB 和 Elasticsearch 中的分片、HBase 中的 region 等等，本质上都是对数据进行分区」

## 一句话总述
分区把 topic 的数据打散到多个物理单元：若只有一个文件，**所在机器的 IO 会成为整个 topic 的性能瓶颈**；分区后读写按**分区粒度**进行、可分布到不同节点，从而实现**负载均衡、水平扩展与高伸缩性**。

## 面试官视角
P6 会说「分区提高并发」；P7 要讲清**瓶颈的物理来源**（单机 IO）、**扩展的方式**（加分区 + 加节点）、**读写粒度**（按分区而非按 topic），并把它与 MongoDB/ES 的分片、HBase 的 region 联系起来——说明你理解的是**通用分布式数据分区思想**而非 Kafka 专有技巧。

## 主问答
**Q（面试官原话）：** Kafka 为什么要把一个 topic 拆成多个分区？

1. **分散存储**：同一个 topic 的消息**分散存储到不同分区**；消息发往 broker 前会**根据分区规则选择具体分区** `[源码]`。
2. **均匀分布**：分区规则设置合理时，**所有消息可均匀分配到不同分区** `[源码]`。
3. **瓶颈来源**：若一个 topic 只对应一个文件，**该文件所在机器的 IO 会成为整个 topic 的性能瓶颈**；分区正是为解决这个问题 `[源码]`。
4. **可动态调整**：创建 topic 时可通过参数**指定分区个数**，也**可在创建完成后修改分区数量** `[源码]`。
5. **水平扩展**：通过**增加分区数量实现水平扩展** `[源码]`。
6. **作用定位**：分区提供**负载均衡能力**，或者说用于实现系统的**高伸缩性** `[源码]`。
7. **跨节点分布**：不同分区可**放置到不同节点的机器上**；**数据读写针对分区粒度进行**，每个节点可**独立执行各自分区的读写请求** `[源码]`。
8. **加机器即加吞吐**：可通过**添加新的机器节点**来增加整体系统吞吐量 `[源码]`。
9. **通用思想**：分区广泛用于分布式系统——**MongoDB 与 Elasticsearch 的分片、HBase 的 region**，本质上都是对数据进行分区 `[源码]`。

## 关键代码
```go
package main

import (
	"fmt"

	"github.com/IBM/sarama"
)

func main() {
	cfg := sarama.NewConfig()
	cfg.Producer.Partitioner = sarama.NewHashPartitioner // 或 NewRoundRobinPartitioner

	producer, _ := sarama.NewSyncProducer([]string{"127.0.0.1:9092"}, cfg)
	defer producer.Close()

	// 分区的意义：同一 topic 的消息被打散，读写按分区粒度并行到不同节点
	for i := 0; i < 10; i++ {
		msg := &sarama.ProducerMessage{Topic: "orders", Value: sarama.StringEncoder(fmt.Sprint(i))}
		partition, offset, err := producer.SendMessage(msg)
		if err != nil {
			panic(err)
		}
		fmt.Printf("partition=%d offset=%d\n", partition, offset)
	}
}
```

## 总结与追问预判
**「单机 IO 瓶颈 → 分区 → 水平扩展」是完整因果链**。追问常是「分区数是不是越多越好」——不是：分区过多会导致文件句柄与副本同步开销上升，且**分区只能增不能减**，需提前规划。具体路由规则见同批 147-partition-strategy。
