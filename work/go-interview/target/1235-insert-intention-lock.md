# 1235 插入意向锁与 supremum 加锁

> 分类：MySQL 锁 | 难度：高 | 题型：实验/原理 | 频率：高 | 关键词：**插入意向锁、IS 锁、supremum、唯一键冲突、RR**

> 原文锚点：第 1~51 段「插入阻塞实验与插入意向锁/supremum」

## 一句话总述
在可重复读（RR）下，插入操作会先加表级 IS 锁，再申请插入意向锁（一种特殊的间隙锁，多个之间不互斥）；唯一键冲突时第二个插入被阻塞。若 `select ... for update` 查一个不存在的记录，InnoDB 会对页内最大虚拟记录 supremum 加 X 锁，从而阻塞一切更大的插入。

## 面试官视角
插入意向锁是 MySQL 锁里最易踩坑的点。考官看你能不能讲清「为什么并发插入一般不互斥、唯独唯一键冲突才阻塞」，以及 supremum 这个虚拟记录的角色。能答出这两点就是 P7。

## 主问答
**Q（面试官原话）：** 插入意向锁是什么？为什么插入相同键值会阻塞？

1. **插入先加 IS 锁**：插入属写入，获取行锁前先在表级加意向共享锁（IS）。
2. **插入意向锁不互斥**：它是特殊的间隙锁，仅标记「要插入的位置」；不同事务的插入意向锁之间不互斥，所以普通并发插入互不阻塞。
3. **唯一键冲突阻塞**：第一个事务插入未提交，该记录加记录锁（REC_NOT_GAP，锁住这一行）；第二个插入相同唯一键值与之冲突 → 被阻塞。
4. **supremum 的 X 锁**：`for update` 查不存在记录时，InnoDB 对页内最大虚拟记录 supremum 加 X 锁，凡插入比它小的区间都被阻塞，此时加锁类型显示为 insert intention（标记被阻塞的插入）。

## 关键代码
```sql
-- 会话A
BEGIN; INSERT INTO t(id,a) VALUES(10,10);  -- 不提交
-- 会话B（插入同 id=10）被阻塞
INSERT INTO t(id,a) VALUES(10,10);
```

## 总结与追问预判
核心：**插入意向锁不互斥，冲突在唯一键记录锁与 supremum X 锁**。追问常拐向「意向锁本身是什么」（见 1235-intention-lock）或「next-key 怎么来的」（见 1235-next-key-lock）。
