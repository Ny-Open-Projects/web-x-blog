# 1239 SELECT * 与覆盖索引：同一个查询为何加锁对象完全不同

> 分类：数据库 / MySQL 锁 | 难度：L4 | 题型：排错题 | 频率：高 | 关键词：**SELECT \***、**覆盖索引、回表、优化器选树、加锁对象、临键锁、二级索引**

> 原文锚点：第 5~14 段「我们把这个 select name 改成 select *，我们再来执行一下这个事务…我们可以看到这个时候呢，我们表中所有的主键记录呢都被加上了临键锁…只查询 name 字段的时候，它扫描的是 name 列的二级索引树，也就是这里使用到了索引覆盖。但是如果我们使用 select * 的话，那为了避免大量的回表操作，查询优化器是没有使用任何索引列的，也就是它会扫描聚簇索引…加锁的对象自然而然也就变成了对主键索引加行锁」

## 一句话总述
同一条锁定读，**`SELECT name` 与 `SELECT *` 的加锁对象完全不同**：`SELECT name` 走**二级索引覆盖** → 对扫描到的**二级索引记录**加锁、再对主键加行锁；`SELECT *` 因**要回表取全字段**，优化器干脆**不用二级索引**而直接扫**聚簇索引** → 只对**主键索引加临键锁**。核心链路是：**结果集 → 优化器选哪棵树 → 加锁对象**。

## 面试官视角
- 考察意图：是否知道"加锁对象不是由 WHERE 条件单独决定的"，而是**由优化器实际选择的那棵索引树**决定的。
- 分档：P5 知道加锁加在索引上；P6 知道覆盖索引能少回表；P7 能推出"**`SELECT *` 会改变加锁范围**"这一反直觉结论，并解释优化器为何弃用二级索引。
- 红旗答案：以为 `WHERE name > 'a'` 一定在 `name` 索引上加锁；不知道 **`SELECT *` 会让优化器改用聚簇索引**。
- 惊艳点：**把 `SELECT *` 改成只查索引列，不只是"少回表提速"，而是**改变了加锁的索引树**，从而影响并发阻塞范围 `[源码]`。

## 主问答
**Q（面试官原话）：** 同样的 WHERE 条件，`SELECT name` 和 `SELECT *` 加锁一样吗？

1. **结论**：不一样。`SELECT name` 扫**二级索引树**并**在二级索引记录上加锁**、再到主键加行锁；`SELECT *` 扫**聚簇索引**并**只对主键索引加临键锁** `[源码]`。
2. **`SELECT name` 的路径**：只查 `name` 字段时，扫描的是 **`name` 列的二级索引树**，此时**使用到了索引覆盖**（要的列都在索引里，无需回表）；于是**被扫描到的二级索引记录会全部加锁**，**再给对应的主键加行锁** `[源码]`。
3. **`SELECT *` 的路径**：使用 `SELECT *` 时，要取全字段，**若走二级索引就要大量回表**；为了**避免大量的回表操作**，查询优化器**不使用任何索引列**，改为**扫描聚簇索引** `[源码]`。
4. **加锁对象的差异**：因为扫的是聚簇索引，**加锁对象自然变成对主键索引加行锁**；实测可见**表中所有主键记录都被加上了临键锁** `[源码]`。
5. **对照**：`SELECT name` 是"**二级索引加锁 + 主键加行锁**"两级；`SELECT *` 是"**主键索引直接加临键锁**"一级——两者锁住的记录集合与阻塞面都不同 `[源码]`。
6. **边界（无索引场景）**：若扫描的记录**没有索引或未使用索引**，就会**全表扫描**，导致**每条记录都被加上临键锁**（相当于锁住全表），其他事务对该表的增删改查**全部被阻塞**；注意它**不是表锁，是行锁锁满了全表** `[源码]`。

**加分层：** 工程结论——**锁定读（`FOR UPDATE` / `LOCK IN SHARE MODE`）里禁止写 `SELECT *`**。只查需要的列，既可能走覆盖索引少回表，也能**把加锁面限制在必要的索引记录上**。

## 关键代码
```sql
-- 前提：name 上有二级索引 idx_name
ALTER TABLE userbig ADD INDEX idx_name (name);

-- 1) SELECT name：走覆盖索引，二级索引加锁 + 主键加行锁
START TRANSACTION;
SELECT name FROM userbig WHERE name > 'name10' AND name <= 'name15' FOR UPDATE;
-- 观察锁：二级索引记录上有锁，主键上有行锁

-- 2) SELECT *：优化器弃用二级索引，改扫聚簇索引，只对主键加临键锁
START TRANSACTION;
SELECT * FROM userbig WHERE name > 'name10' AND name <= 'name15' FOR UPDATE;
-- 观察锁：表中所有主键记录都被加上临键锁

-- 3) 8.0 观察实际加锁
SELECT index_name, lock_type, lock_mode, lock_data
FROM performance_schema.data_locks WHERE object_name = 'userbig'\G

-- 4) 用 EXPLAIN 验证优化器到底选了哪棵树
EXPLAIN SELECT name FROM userbig WHERE name > 'name10' FOR UPDATE;
EXPLAIN SELECT *    FROM userbig WHERE name > 'name10' FOR UPDATE;
```

## 总结与追问预判
**最爱追问的是"为什么 `SELECT *` 反而锁得更多"**——因为优化器为了避免回表直接扫聚簇索引，把**临键锁打在了主键记录上**，锁的就是"整段主键区间"。追问常接"怎么避免"——**锁定读只查必要列、让查询走覆盖索引**，或**先用主键/唯一索引查出 id 集合，再用主键锁定**（把大范围锁拆成精确行锁）。另注意与 `1238-type-conversion-lock` 的联动：隐式类型转换导致的**全表扫描加锁**是同一因果链的另一种触发方式。

## ⚠️ 原文纠错
1. 事实核校：`SELECT name` 走覆盖索引并在二级索引记录加锁、`SELECT *` 因避免回表而扫聚簇索引、加锁对象随之变为主键索引、无索引时全表记录加临键锁（行锁而非表锁）——均与 InnoDB 加锁实现一致 `[经验]`。
2. 补充：原文此处与"隐式类型转换导致索引失效"混在同一节讲述，二者**成因不同**——本卡的选树变化源于**结果集需要回表**，类型转换那类源于**查询条件与索引列类型不匹配**；面试中应分开表述 `[经验]`。
3. 崩坏词归一：源码将临键锁、聚簇索引、二级索引、覆盖索引、优化器等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
