# 806 GC 两大门派：追踪式 vs 引用计数式

> 分类：Go/运行时 | 难度：L2 | 题型：综述题 | 频率：高 | 关键词：**追踪式 GC** / **引用计数式 GC** / **根对象** / **循环引用**
> 原文锚点：第 6~26、41~47 段「GC 本质=找死亡对象回收；自动/手动 GC；实现方式分追踪式(tracing)与引用计数式(reference counting)；根对象=全局变量/执行栈/寄存器；引用计数优=实现简单回收及时，缺=额外开销+无法回收循环引用」

## 一句话总述
GC 实现方式从**方法论**上只分两派：**追踪式（tracing）** 从根对象出发扫描整堆、标记存活；**引用计数式（reference counting）** 给每个对象挂计数器、归零即回收。追踪式是 Java/Go 的选择，引用计数式以 Python/ObjC 为代表；**循环引用是引用计数的死穴**，也是 Go 选追踪式的根因之一。

## 面试官视角

- P5 能说出两派名字；P6 能讲清追踪式"从根对象扫堆"与引用计数"归零即回收"的本质差异；P7 能点出循环引用无法回收、追踪式需要 STW 或写屏障保证正确性。
- 红旗：把引用计数当万能（忽略循环引用）；把"GC"等同于"只有 Java 的 JVM 那一套"。

## 主问答
**Q（面试官原话）：** GC 的实现方式有哪些？两派各有什么优劣？
**A：**
1. **结论**：GC 本质是**找出不再被引用的"死亡对象"并回收**。实现方式只有两大类——**追踪式（tracing）** 和 **引用计数式（reference counting）**。
2. **追踪式**：从**根对象**（全局变量、执行栈上的变量/指针、寄存器中的指针）出发，沿引用关系一步步扫描整个堆，标记存活对象，回收未标记对象。Java、Go、Lua 都属此类。缺点是"扫整堆"代价随堆增大而上升，需 STW 或写屏障保护并发正确性。
3. **引用计数式**：给每个对象维护一个计数器，被引用 +1、失去引用 -1，**归零立即回收**。优点是**实现简单、回收及时**（对象死即收，内存不积压）；缺点是**额外空间/时间维护计数器**，且**无法回收循环引用**（A↔B 互相引用，计数永远不为 0）。Python、ObjC 属此类（Python 另配标记清除兜底循环引用）。
4. **自动 vs 手动**：绝大多数语言（Go/Java/Python）走自动 GC，开发省心、避免漏释放；C/C++ 是手动 GC（malloc/free、new/delete），可极致控性能但易出错。自动 GC 的唯一代价是额外性能开销 `[经验]`。

## 关键代码
```go
// 引用计数式 GC 的核心结构：对象挂计数器，归零即回收
type rcObj struct {
    refs int64 // 引用计数
    data interface{}
}
func retain(o *rcObj)  { atomic.AddInt64(&o.refs, 1) }
func release(o *rcObj) {
    // 计数归零立即回收；但若 A、B 互相引用，计数永远 >0 → 循环引用泄漏
    if atomic.AddInt64(&o.refs, -1) == 0 {
        free(o)
    }
}
// 追踪式不需要计数器：GC 从 roots 出发遍历对象图，未达对象即垃圾
var roots = []*rcObj{globalA, stackB} // 根对象集合
```

## 总结与追问预判
- 两派：追踪式（扫堆标记存活）vs 引用计数式（归零即收）；循环引用是引用计数死穴。
- 预判：追踪式怎么细分 → 见 806-tracing-variants；Go 选追踪式且不用分代 → 见 806-go-why-no-generational；三色标记法 → 见 807-gc-tricolor。
