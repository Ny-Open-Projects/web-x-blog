# 1255 过期删除三方案取舍与主从过期语义 深挖

> 覆盖源 12-55 全文：惰性/定时/周期三种过期删除方案的完整取舍矩阵、Redis 为什么不用定时删除、周期抽样扫描的节奏与「过期比例续扫」、主从复制与持久化视角下的过期语义、大 key 过期删除的阻塞风险与异步化。主卡已给两机制区分与惰性 + 周期组合，本附录做决策树与边界场景四层深挖。

## 思路与架构

```text
「Redis 怎么删数据」先分诊
├─ key 有 TTL 且时间到了? -> 过期删除(本卡主线)
│   ├─ 惰性: 访问时查过期字典 -> 过期则删 (CPU 0 开销, 冷 key 漏删)
│   ├─ 定时: 每 key 一个 timer (内存最及时, CPU 大户 -> Redis 弃用)
│   └─ 周期: 后台周期性随机抽样 (折中, Redis 采用)
│       └─ 每次抽样 N 个设 TTL 的 key, 过期比例过高则立刻再扫一轮
├─ 内存到 maxmemory? -> 内存淘汰(另一套, 策略见 1257)
│   └─ noeviction 拒写 / allkeys-* / volatile-*
└─ 交叉区: volatile-* 淘汰只作用于有 TTL 的 key
    └─ 无任何过期 key 时 volatile-* 退化为拒写
```

## 方案取舍
- **为什么定时删除被弃用**：设 TTL 的 key 通常以百万计，每个挂一个精确 timer 意味着 ① 海量 timer 数据结构的**内存开销**（本身就是省内存的数据库，倒被 timer 吃了）；② 到期时刻集中时**CPU 被删除风暴打满**，主流程（命令处理）被挤压；③ timer 的创建/销毁/管理本身是纯开销。三笔账算下来，「到期即删」的实时性收益完全抵不过成本——这是**用错过一次及时性，换整体吞吐**的经典取舍 [经验]。
- **惰性删除的残余风险与周期兜底**：惰性路径只在 key 被访问时触发，**再也没人读的过期 key 会一直占内存**。周期删除的兜底节奏：后台任务周期性运行，每轮**随机抽样**一批设了 TTL 的 key 检查删除；若本轮过期比例过高（说明过期 key 积压），**不等下一周期立刻再扫一轮**，形成自适应强度。这是「抽样 + 比例驱动加压」的通用模式，与自旋重试、TCP 拥退避同构 [源码]。
- **主从架构的过期语义是隐藏追问点**：过期删除由**主库**执行（惰性 + 周期都在主库），从库**不主动删**过期 key，而是等主库删了之后**同步 DEL 命令**过来。后果：主库 key 刚过期、DEL 还没同步的窗口内，读从库可能拿到**已过期数据**；Redis 3.2+ 对从库读做了修补——**读到逻辑已过期的 key 时返回 nil 但不删除**，数据一致性窗口收窄，但删除仍由主库统一负责（保证主从删除顺序一致，避免从库先删导致 DEL 同步丢失语义） [经验]。
- **持久化视角**：RDB 快照时已过期的 key 不写入；加载 RDB 时对每个 key 再查一次系统时间，已过期的不恢复。AOF 则把过期删除作为显式 DEL 记录，**AOF 重写时直接丢弃已过期 key**。结论：**过期数据不会在重启后复活**——面试里「Redis 重启后过期 key 还在吗」这题的完整答案就在这三处 [经验]。
- **大 key 的过期删除阻塞**：周期/惰性删除碰到百 MB 级 hash/zset 时，同步释放可能造成主线程长尾毛刺。4.0+ 的 `lazyfree-lazy-expire` 让过期删除走**异步线程**（引用计数 + 后台 unlink），代价是内存释放有延迟。这与「惰性 + 周期」正交：组合拳是惰性判断在主线程（O(1)），真正释放到后台 [经验]。

## 答题技巧
- 第一句永远先切概念：「过期删除和内存淘汰是两套正交机制」，然后按面试官追问的分支走 [经验]。
- 被问「为什么不用定时删除」→ 用三笔账答：timer 内存开销、删除风暴打满 CPU、管理本身是纯开销 [经验]。
- 被问「冷门过期 key 占内存怎么办」→ 先答周期抽样兜底 + 比例驱动续扫，再补「极端积压时主动 SCAN 清理」，显示知道残余风险 [经验]。
- 主从题主动上：「从库不主动删，等主库 DEL 同步；3.2+ 读从库对逻辑过期 key 返回 nil」——一个追问点拆两层，直接到 P7 档 [经验]。
- 主动边界到 `1257-eviction-policies`（八种淘汰策略矩阵与版本默认）、`1259-lru-vs-lfu`（LRU/LFU 实现取舍）、`194-redis-queue-tuning`（生产调优），构成 Redis 内存管理全链 [边界]。
