# 113 Go 基准测试深挖

## 思路与架构
把基准测试拆成**「一条循环 + 两个可调 + 三类指标」**，所有参数和方法都能对号入座：

- **一条循环**：`for i := 0; i < b.N; i++ { 被测代码 }`。b.N 不是常量，而是框架为达到 `-benchtime` 目标时长而**自动校准**出来的样本量——先小样本试跑，再按倍数增长直到耗时达标。理解了这一点，就知道为什么不该手动改 b.N。
- **两个可调**：
  1. **时长**（`-benchtime`）—— 决定样本量与统计置信度。
  2. **并发度**（`-cpu`，即 GOMAXPROCS）—— 决定在多核下的可伸缩性表现。
- **三类指标**：`ns/op`（时间）、`B/op`（每次分配字节）、`allocs/op`（分配次数）。**只看时间会漏掉 GC 压力**，这三类要一起看。

再加一层「干扰排除」：`ResetTimer` 管一次性前置，`StopTimer/StartTimer` 管循环内间歇。基准测试的可信度 = 足够的样本量 × 干净的计时区间。

## 方案取舍
- **-benchtime 加长 vs 默认 1 秒**：默认够快但样本少、抖动大；加长到 3~10 秒能压掉噪声，代价是 CI 时间变长。**本地调优用 3~5 秒，CI 用 1~2 秒并靠多轮取中位数。**
- **-benchmem 常开 vs 按需开**：内存指标几乎零成本，优化阶段应常开；只看吞吐的选型对比可不开。
- **手动设 b.N vs 交给框架**：手动写死会让不同函数、不同机器的结果失去可比性，**永远交给框架校准**，需要更多样本就调 -benchtime。
- **单次结果 vs 多轮取中位数**：单次结果受调度、发热、邻居进程影响极大；严肃对比应使用 `benchstat` 之类的工具对多轮结果做统计比较。
- **微基准 vs 端到端基准**：微基准（单个函数）定位明确但容易脱离真实场景；端到端基准贴近实际但归因困难。**先用端到端找瓶颈，再用微基准验证优化。**
- **ResetTimer vs Stop/Start**：一次性构造测试数据用 Reset 最干净；需要在每轮之间重置状态的场景才用 Stop/Start，滥用会让计时区间碎片化。

## 答题技巧
- **开口给框架**：「文件名 `_test.go`、函数名 `Benchmark` 大写前缀、参数 `*testing.B`」——这三句是地基，先立住。
- **主动说一个反模式**：「不要手动改 b.N」——这是区分背答案与真用过的分水岭，考官很吃这一套。
- **把指标讲全**：ns/op 之外还有 B/op 与 allocs/op，能说全三列的人不多。
- **被问「-bench 怎么筛选」要纠正通配符**：明确它是**正则表达式**，`-bench=.` 的 `.` 匹配任意字符；按通配符写 `-bench=Benchmark*` 语义全错。
- **收尾给可验证动作**：`-bench=. -benchmem -benchtime=3s -cpu=1,4,8` 一条命令覆盖时间、内存、多核三个维度——能报出这条命令最有说服力。
