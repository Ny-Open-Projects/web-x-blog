# 1219 最左前缀原则的底层原理（B+树有序性 + 逆序后缀匹配）

> 分类：MySQL 索引 | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**最左前缀** / **B+树有序性** / **字符串逐字符比较** / **逆序存储** / **后缀匹配**
> 原文锚点：第 1~22 段「B+树按列值排序；字符串逐字符比较、前缀有序；前缀匹配可用索引、中间/后缀不可用；逆序存储字符串实现变相后缀匹配」

## 一句话总述
最左前缀原则的根因是 **B+树按列值有序排列**：字符串索引按"逐字符比较"（首字符→次字符→…）排序，因此**前缀是有序的**，可从索引树前缀/范围定位；**中间或后缀无序**，无法直接定位。需要后缀匹配时，可把字段**逆序存储**、查询串也逆序，把"后缀匹配"转成"前缀匹配"。

## 面试官视角
- 意图：是否理解"最左前缀"是 B+树有序性的必然结果，而非死记规则。
- P5 知 LIKE 'x%' 用索引、'%x%' 不用；P6 知"前缀有序可定位、后缀无序不可定位"的原理；P7 知逆序存储实现后缀匹配的变通技巧。
- 红旗：以为最左前缀是人为规定；或以为 '%x%' 永远全表扫（忽略覆盖索引例外，见 1222）。
- 惊艳点：点出"范围查找本质也是前缀/范围定位，所以能用索引；后缀匹配因破坏有序性才失效" `[边界]` 见 1222（规则与覆盖例外）、1217（B+树结构）、1211（前缀索引）。

## 主问答
**Q（面试官原话）：** 为什么索引是最左前缀原则、后缀匹配用不上索引？
**A：**
1. **B+树有序性**：索引按列值排序，字符串比较是逐字符的（首字符小则整体小，相同再比次字符），所以**前缀段是有序的**——`LIKE 'AB%'` 能沿树前缀定位。
2. **中间/后缀无序**：`'%BC'`/`'%BC%'` 不是从头比较，B+树无法从中间/末尾反推位置，常规只能全表扫（覆盖索引例外见 1222）。
3. **范围同属前缀定位**：`> 'AAR'` 这类范围也是"从某一前缀起向后扫"，故能用索引——本质都依赖前缀有序。
4. **逆序存储变通**：要按后缀搜（如搜 `LON`），把字段逆序存成 `NOL`、查询串也逆序，后缀匹配就变成了前缀匹配，照样走索引。

## 关键代码
```sql
-- 前缀匹配：有序，走 range
SELECT * FROM user WHERE name LIKE 'AB%';
-- 后缀匹配常规失效；逆序存储后转为前缀匹配
ALTER TABLE user ADD COLUMN name_rev VARCHAR(64);
UPDATE user SET name_rev = REVERSE(name);
-- 搜后缀 'LON' → 查逆序字段的前缀 'NOL'
SELECT * FROM user WHERE name_rev LIKE 'NOL%';
```

## 总结与追问预判
- 最左前缀 = B+树前缀有序的必然；后缀无序需逆序存储变通。
