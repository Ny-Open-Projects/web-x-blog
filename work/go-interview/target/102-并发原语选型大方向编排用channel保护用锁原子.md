# 102 并发原语选型大方向（编排用 channel、保护用锁/原子）

> 分类：Go 并发模型 | 难度：中 | 题型：决策题 | 频率：高 | 关键词：**选型大方向、channel 编排、锁保护共享、sync.Map、灵活组合**

> 原文锚点：第 50~58 段「新手误区；大方向：任务编排用 channel、共享保护用锁；复杂场景灵活组合（sync.Map 读写分离）」

## 一句话总述
并发原语选型有**大方向**：**任务编排（协程间协作流程）用 channel**，**共享资源保护用传统并发原语（锁/原子）**；复杂场景灵活组合，如 sync.Map 用读写分离分散锁粒度降竞争——二者不是二选一。一句话背法：**「编排用 channel，保护用锁/原子，复杂场景灵活组合非二选一」**。

## 面试官视角
考官考察"何时用 channel、何时用锁"的判断力，而非死记。能讲清大方向、并举灵活组合（sync.Map 降锁竞争）与边界，说明成熟；所有场景无脑 channel 或全上锁、不知锁 vs 原子差异，是红旗。
- **P5**：知道锁和 channel 都能同步。
- **P6**：能讲清大方向（编排 vs 保护）。
- **P7**：能举灵活组合（sync.Map 降竞争）并知边界。

## 主问答
**Q（面试官原话）：** 锁和 channel 都能解决并发，怎么选？

**先铺垫（由浅入深第 1 层）**：新手最容易陷的坑是"学了一个原语就处处用"。但 channel 和锁解决的是不同层面的问题——channel 管"流程怎么协作"，锁管"状态怎么不被同时改"。先想清楚你要解决的是哪类，选型就自然了。

1. **大方向（第 2 层）**：任务编排（谁先谁后、流水线、扇出扇入）用 **channel**；保护共享变量/临界区用 **锁/原子**（互斥锁或原子操作）。
2. **为何分（第 3 层）**：channel 擅长表达"数据流动与协作"，锁/原子擅长"护住一个状态"，混用会写复杂。
3. **灵活组合（第 4 层·实战）**：复杂场景不互斥——如 `sync.Map` 用**读写分离**把一把大锁拆成多 shard 降锁竞争（原理见 922）；高竞争下锁未必慢于原子，需实测（见 105）。
4. **新手三误区（第 5 层）**：①不知怎么拆分编排并发任务；②不知用哪个原语；③把并发写复杂引入死锁。
5. **误用风险（第 6 层）**：大方向是经验法则不是铁律——单纯护一个变量用原子比 channel 轻得多；数据传递/流水线才上 channel，别反过来。

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
)

// 编排用 channel（任务流转），保护用锁（护住共享 sum）——各司其职、灵活组合
func main() {
	ch := make(chan int, 10) // 编排：任务流转
	var mu sync.Mutex
	var sum int64

	var wg sync.WaitGroup
	wg.Add(1)
	go func() {
		defer wg.Done()
		for v := range ch {
			mu.Lock()
			sum += int64(v) // 保护：锁护住共享状态
			mu.Unlock()
		}
	}()

	for i := 1; i <= 5; i++ {
		ch <- i
	}
	close(ch)
	wg.Wait()
	fmt.Println("sum =", sum) // 15
}
```

## 总结与追问预判
**背这三句就够**：① **任务编排（流水线/扇出扇入）用 channel，保护共享状态用锁/原子**；② **二者灵活组合非二选一（如 sync.Map 读写分离降竞争）**；③ **大方向是经验法则：单纯护变量用原子更轻，别无脑 channel**。
**预判追问**：
- 「锁和原子怎么选？」→ 单变量计数/状态位用原子，复合临界区上锁（见 105 何时用原子）。
- 「锁和 channel 性能差？」→ 见 1015 channel 互斥锁对比；sync.Map 见 107/922。
- 「怎么避免死锁？」→ 锁序一致、加超时、缩小临界区（见 1014 Mutex）。
