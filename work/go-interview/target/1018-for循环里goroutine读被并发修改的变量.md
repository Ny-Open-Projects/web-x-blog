# 1018 for 循环里 goroutine 读"被并发修改"的变量

> 分类：并发模型 | 难度：L3 | 题型：事故题 | 频率：高 | 关键词：**数据竞争** / **字段级并发** / **只读拷贝** / **sync**
> 原文锚点：第 42~60 段「主循环边改 s2.f3 字段边启 goroutine 读该字段；读到的取值取决于调度时机，属真正的读写数据竞争」

## 一句话总述
比"循环变量捕获"更隐蔽的一类坑：for 循环里**主协程正在修改某变量/字段，同时启动的 goroutine 去读它**——这是读写两端的真数据竞争（非单纯读终值），结果非确定性，必须用同步或只读拷贝隔离。

## 面试官视角
- 意图：区分"读循环索引"与"读写共享变量"两类竞态，后者危害更大（未定义行为）。
- P5 知道这种写法结果不定；P6 能说清这是读写两端的数据竞争；P7 能给出修法（传值拷贝/锁/chan）并用 -race 验证。
- 红旗：以为"只是读到旧值"没事；以为不加锁偶尔正确就安全。
- 惊艳点：指出数据竞争是**未定义行为**——不是"偶尔错"，而是编译器/运行时可任意重排，必须修。

## 主问答
**Q（面试官原话）：** 主循环改一个字段、goroutine 里读它，为什么读到的不对？
**A：**
1. **结论**：主协程写、goroutine 读同一块内存且无同步 → 数据竞争（data race），读到的值取决于调度时机，且属未定义行为。
2. **机制**：源中 `s2.f3` 在主循环每轮被赋值、goroutine 通过指针读 `f3`；两端无 happens-before 关系，读可能拿到修改前、修改中或修改后的任意值 `[源码]`。
3. **边界**：修法三选：① 传值拷贝（把字段值当参数传，断开心地址共享）；② 用 `sync.Mutex`/`atomic` 保护读写；③ 用 channel 传递值。不要靠"大概率读到对的值"侥幸 `[经验]`。

## 关键代码
```go
// 示意，未验证：字段级读写竞争，用传值拷贝隔离
type S struct{ F3 int }
for i := 0; i < n; i++ {
    s2 := S{F3: i}            // 每轮新结构体
    v := s2.F3                // 取出字段值做值拷贝
    go func(f3 int) { readData(f3) }(v) // 传值：goroutine 不再读主循环变量
}
// 反例：go func(){ readData(s2.F3) }() 仍共享 s2 地址 → 竞争
```

## 总结与追问预判
- 读写竞争 > 读终值：必须同步或拷贝，不是"偶尔对"。
- 预判：检测手段 → 见 1018；循环变量捕获 → 见 1017。
