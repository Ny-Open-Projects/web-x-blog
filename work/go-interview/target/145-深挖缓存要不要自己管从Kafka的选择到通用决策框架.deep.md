# 145 深挖：缓存要不要自己管——从 Kafka 的选择到通用决策框架

> 分类：架构设计 / 存储 | 难度：L4 | 题型：设计题 | 频率：中 | 关键词：**自管缓存 vs OS 缓存**/**直写 vs 只读缓存**/**一致性双写**/**GC 压力**/**对象开销**/**决策框架**
> 原文锚点：第 5~37 段「消息系统的业务特性决定了它很适合使用 page cache…平时遇到的大部分服务都是读多写少的场景，这种场景适合使用只读缓存…命中率最高的置换策略一定是根据业务逻辑定制化的策略…另外还需要避免 GC 带来的性能影响」
> [边界] 本文只讲**决策框架与取舍**：Kafka 四条理由的逐条展开见 145，页缓存机制见 144，LRU/LFU 算法细节见 1259，均不重述。

## 思路与架构

「要不要自己管缓存」不是偏好问题，可以用**一个四问决策树**收敛：

```text
问 1：这份数据是「写后立刻读」还是「读多写少」？
     写后立刻读   -> 直写缓存（write-through），OS page cache 天然胜任
     读多写少     -> 只读缓存，才轮到应用层缓存登场

问 2：自管缓存要不要承担「双写一致性」？
     要 -> 磁盘与缓存两份同步更新，分布式下极难保证
     不 -> 说明这个场景本来就不需要应用层缓存

问 3：运行时有没有「对象开销 + GC」这笔税？
     JVM / Go -> 有：对象头、对齐填充、堆越大 GC 越慢
     C / Rust  -> 少：本条论据大幅减弱

问 4：进程崩了，缓存里的数据怎么办？
     自管 -> 数据随进程消失，还需自建持久化
     交给 OS -> 内核还在，脏页照常回写；掉电才丢
```

**两条缓存范式的本质差别**（这是本题的灵魂）：

```text
只读缓存（read-only cache）
  数据来源唯一：磁盘
  读 miss -> 查盘 -> 填缓存
  写     -> 要同时更新磁盘 + 缓存（双写）
  痛点   -> 一致性 + 置换策略 + 命中率
  典型   -> Redis / Memcached / 本地 Caffeine

直写缓存（write-through / page cache）
  写先落在缓存层，由下层异步回写
  天然覆盖"刚写完就被读"的访问模式
  不需要维护"磁盘 vs 缓存"两份副本的一致性
  典型   -> OS page cache / buffer cache
消息队列的访问模型就是后者：
  生产者刚 append -> 消费者马上拉取 -> 命中刚写进去的页
```

## 方案取舍

```text
方案 A：完全交给 OS（Kafka 的选择）
  + 零自研、零 GC、无对象开销、内存由内核统一调度
  + 崩溃语义好：进程死了内核照样回写
  - 淘汰策略不可控，无法针对业务定制
  - 掉电仍丢未刷盘数据 -> 必须靠副本兜底
  适用：追加写日志、消息队列、顺序扫描型存储

方案 B：应用层自管（Redis / Caffeine / 自研 LRU）
  + 淘汰策略与数据结构完全可控，可做业务定制
  + 可以缓存"计算结果"而不只是"原始页"
  - 双写一致性、对象开销、GC、崩溃恢复全部要自己扛
  适用：读多写少、热点集中、value 是计算结果的场景

方案 C：混合（OS 缓存打底 + 应用层缓存热点）
  + 两层各司其职
  - 内存总量要在两层间划分，容易互相挤压（double buffering）
  适用：既持久化又要极低延迟读的系统
```

**三个"反直觉但重要"的判断**：

```text
1. 内存给 OS 不等于浪费
   空闲内存被拿去做 page cache，应用需要时内核会自动回收，
   自管缓存反而会长期占着不还。

2. Kafka 敢不刷盘，不是因为它不怕丢
   是因为它把可靠性外包给了多副本 —— 单机可靠性让位于集群可靠性。

3. "定制化淘汰策略命中率最高"是有代价的结论
   定制意味着要深入理解访问模式、持续维护，多数团队付不起这笔成本。
```

## 答题技巧

```text
1. 先定性再列理由
   「这不是性能优化题，是职责边界题 —— 缓存管理这件事
     操作系统已经做得足够好，Kafka 没必要重做一遍。」

2. 四条理由按重要性排序，别平铺
   ① 读写特性契合（最根本，决定能不能用）
   ② 避开 JVM 对象开销
   ③ 避开 GC 拖累
   ④ 降低复杂度 + 更好的崩溃语义

3. 一定要点"直写 vs 只读"这个分野（区分度最高）
   「读多写少才需要应用层只读缓存，而它要解决一致性双写；
     Kafka 是写后即读的直写模型，天然没有这个负担。」

4. 主动给边界，不说满话
   「进程崩溃不丢数据，因为内核还在；
     机器掉电或内核崩溃才会丢未刷盘的数据 ——
     所以真正的可靠性靠多副本，不靠刷盘。」

5. 用数字收尾（杀伤力最大）
   「实测 2000 条消息：只写页缓存末尾一次 Sync 是 34ms，
     每条都 Sync 是 41.7 秒 —— 相差 1200 倍。
     这就是为什么 Kafka 拒绝逐条刷盘。」

6. 拔高一句
   「架构里最划算的优化，往往是把活交给已经做好的那一层。」
```

**可能被追问的深水区**：

```text
Q：所有消息中间件都这么干吗？
A：RocketMQ 同样依赖 page cache + 顺序写；关键差别在刷盘策略
   （RocketMQ 提供同步/异步刷盘可配），但默认也都交给 OS。

Q：Go 写的存储组件还需要"避开 GC"这条论据吗？
A：需要但更弱。Go 没有 JVM 那种厚对象头，但大堆仍有 GC 压力，
   所以 Go 项目常见做法是 mmap / 堆外 / 字节切片复用。

Q：什么情况下应用层缓存反而必须存在？
A：当缓存的 value 不是磁盘上的原始内容，而是计算结果
   （聚合值、渲染后的页面、鉴权结果）时，OS 帮不了你。
```
