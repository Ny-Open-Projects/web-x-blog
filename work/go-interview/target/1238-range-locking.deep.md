# 1238 深挖：普通索引范围查询的加锁全景与事故预防

> 分类：数据库 / MySQL 锁 | 难度：L4 | 题型：综合题 | 频率：高 | 关键词：**范围查询、临键锁、幻读、扫描终止、隐式类型转换、全表行锁**

> 原文锚点：第 33~75 段「所有命中的二级索引的列都被加上了临键锁，直到最大的虚拟记录行也被加上了临键锁…如果只加记录锁，记录锁是无法防止插入操作的…会出现幻读…整表的数据全部都被加锁了…它并不是加了表锁，而是加的是临键锁和行锁…查询条件发生了类型的强制转换，所以会走全表扫描」

## 思路与架构

把普通索引的**范围加锁**拆成「扫描 → 加锁 → 防幻读 → 防事故」四步：

1. **扫描：先确定走过的路**。范围查询不是点查，而是沿二级索引扫描，**一直扫到第一条不满足条件的记录才停**；若条件类型正确且区间无数据，扫描会在最近的那条记录处终止。
2. **加锁：扫到什么锁什么**。命中的二级索引记录全部加**临键锁**（左开右闭），扫描终止的那条**同样加临键锁**（含其自身索引值），一直延伸到 **Supremum 伪记录**；命中的主键行加**记录锁**。
3. **防幻读：解释为什么不退化**。非唯一索引不具唯一性，记录锁**只能挡删改、挡不住插入**；若只加记录锁，其他事务可插入同值记录，使本事务前后两次查询结果集不同，即**幻读**。因此必须加临键锁，把记录与其前间隙一并锁死。
4. **防事故：类型写错会锁全表**。索引列是字符串而条件给数字，触发**隐式类型转换** → 索引失效 → 二级索引**全表扫描**（EXPLAIN `type=index`）→ 全表每条记录都被加行锁（**是行锁不是表锁**）→ 整表写入阻塞。修正条件为字符串即可恢复 `type=range`。

## 方案取舍

| 场景 | 锁型 | 锁范围 | 风险 |
|---|---|---|---|
| 范围查询命中 | 临键锁 + 主键记录锁 | 命中项 + 终止项 + Supremum | 区间大时锁面广 |
| 范围查询未命中 | 临键锁 + 主键记录锁 | 仅扫描终止的那一条 | 极小，但确实有锁 |
| 等值查询命中（唯一索引） | 退化为记录锁 | 仅该行 | 最小，可退化 |
| 等值查询命中（非唯一） | 临键锁 + 主键记录锁 | 命中项 + 右邻间隙 | 不可退化 |
| 隐式转换导致全表扫描 | 全表行锁 | 整表所有记录 | **最高，整表写阻塞** |

取舍要点：**锁范围由「扫描范围」决定，而非由「命中行数」决定**。想缩小锁面，唯一有效手段是让扫描范围变小——命中索引、写对类型、缩小查询区间；靠「反正查不到数据」来侥幸是不可靠的，未命中同样会加锁。

## 答题技巧

1. **先说扫描再说锁**：开口讲「沿索引扫描到第一条不满足项」，比直接报锁型更有说服力，也能自然引出「终止项也加锁」。
2. **把「为什么」讲到底**：非唯一 → 记录锁挡不住插入 → 幻读 → 临键锁，这条因果链讲完，临键锁的存在意义就清楚了。
3. **主动区分全表行锁与表锁**：这是高频送分点，说「全表每条记录各加行锁，不是单个表级锁」即可体现深度。
4. **带排查手段**：EXPLAIN 看 `type`（index vs range）、8.0 查 `performance_schema.data_locks`，能报出工具的答案更可信。
5. **止步档位**：能讲清扫描终止与临键锁即达 L4；能再讲防幻读机理、隐式转换锁全表并给出排查手段，即达 L5。

## ⚠️ 原文纠错
1. 事实核校：命中项加临键锁并延伸至 Supremum、终止项同样加临键锁、记录锁无法防插入导致幻读、隐式转换致全表扫描且锁型为行锁而非表锁——均与 InnoDB 行为一致 `[经验]`。
2. 补充：本批结论均基于 **RR 隔离级别的当前读**；RC 下间隙锁与临键锁不存在，普通快照读在 RR 下走 MVCC 不加锁。答题时先声明前提可避免被追问时失分 `[经验]`。
3. 崩坏词归一：源码将临键锁、间隙锁、记录锁、幻读、全表扫描、主键索引等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
