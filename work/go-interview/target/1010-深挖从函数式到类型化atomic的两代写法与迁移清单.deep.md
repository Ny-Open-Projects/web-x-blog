# 1010 深挖：从函数式到类型化——atomic 的两代写法与迁移清单

> 分类：Go/并发 | 难度：L4 | 题型：迁移题 | 频率：中 | 关键词：**Go 1.19**/**类型化原子**/**atomic.Int64**/**atomic.Pointer**/**对齐**/**无锁编程**/**ABA**
> 原文锚点：第 19~35 段「atomic 除了能操作整型，还能操作布尔类型…还提供了一个 Value 类型，可以存放任意值，比如我们可以存放一个结构体…原子操作保护的是某个变量，受保护的范围是变量级」
> [边界] 本文只讲**两代 API 的差别、迁移与底层约束**：五方法签名语义见 1010，使用陷阱见 104，与锁的选型见 105，均不重述。

## 思路与架构

用"**谁来保证不出错**"这条线串起两代 API：

```text
第一代：函数式（atomic.AddInt64(&x, 1)）
  类型安全靠"人肉保证"
    - 你可以对同一个 int32 变量误调 AddInt64      -> 静默未定义行为
    - 可以对非原子变量混用普通读写                 -> 数据竞争
    - 编译器基本帮不上忙
  优点：写法短，老代码遍地都是

第二代：类型化（Go 1.19+，var c atomic.Int64; c.Add(1)）
  类型安全由"编译器保证"
    - 类型本身携带"我是原子的"这一语义
    - 方法集恰好是五个：Add/Load/Store/Swap/CompareAndSwap
    - 无法对它做普通读写，从源头消灭混用
  额外收益：结构体里放 atomic.Int64 天然满足对齐要求
```

**底层三条硬约束**（面试深水区，必须能答）：

```text
1. 对齐（alignment）
   32 位平台上 64 位原子操作要求 8 字节对齐。
   把 int64 放在结构体中间可能被编译器挤到非 8 字节边界，
   在该平台直接 panic 或行为未定义。
   解法：把 64 位原子量放结构体**第一个字段**，或直接用 atomic.Int64。

2. 不可复制（no copy）
   atomic.Int64 内含 noCopy 语义，复制它会把锁/状态一起复制。
   传参必须传指针，或让它一直是结构体字段。

3. 保护范围只有一个变量
   "读-判断-写"这种复合逻辑，原子操作保不住 —— 要 CAS 循环或锁。
```

## 方案取舍

```text
维度              函数式 API                类型化 API（Go 1.19+）
──────────────────────────────────────────────────────────────
写法              atomic.AddInt64(&x, 1)    c.Add(1)
类型安全          靠人                      靠编译器
能否误调错类型    能                        不能
能否混用普通读写  能（埋雷）                不能（字段不可直接访问）
结构体对齐        要自己保证                类型内部已处理
适用              Go < 1.19 或老代码        Go ≥ 1.19 的新代码
──────────────────────────────────────────────────────────────
结论：新代码一律用类型化；老代码按模块逐步迁移，不必一次改完。
```

**atomic.Value vs atomic.Pointer[T] 的取舍**：

```text
atomic.Value
  + 能存任意类型（结构体、切片、map…）
  - 类型约束只在运行时检查 -> 换类型 panic
  - 首次 Store 不能是 nil
  适用：配置热更新这类"整体替换、读取频繁"的场景

atomic.Pointer[T]（Go 1.19+）
  + 编译期就锁定 T，不可能存错类型
  + 语义更清晰：我就是一个原子指针
  - 只能存指针
  适用：新代码里替代 atomic.Value 的首选
```

**无锁编程的三条纪律**：

```text
1. CAS 循环里失败后必须重新 Load，不能拿过期 old 硬试
2. 高竞争场景先怀疑"要不要上锁"
   —— CAS 反复重试的开销可能超过一次加锁
3. 留意 ABA 问题：值从 A 变 B 又变回 A，CAS 会误判"没变过"
   经典解法：加版本号（把 value+version 打包成一个字）
```

## 答题技巧

```text
1. 先给结论再展开
   「五个方法里最容易搞混的是 Add 和 Swap：
     Add 返回**新值**，Swap 返回**旧值**，CAS 返回**成败**。」

2. 主动暴露版本意识（区分度最高）
   「Go 1.19 之后推荐类型化 API，atomic.Int64 / Bool / Pointer[T]，
     类型安全由编译器保证，老式的函数式写法只在老代码里保留。」

3. 被问 atomic.Value 时一定要主动说 panic
   「换具体类型会 panic，文案是
     'sync/atomic: store of inconsistently typed value into Value'——
     这是运行时检查不是编译期，所以要靠约定或改用 Pointer[T]。」

4. 深水区主动抛"对齐"
   「32 位平台上 64 位原子量要 8 字节对齐，
     放结构体第一个字段，或者干脆用 atomic.Int64。」

5. 收尾拔高
   「atomic 快是因为它绕过了锁，代价是只能保护一个变量、
     且复合逻辑保不住。会用是能力，知道什么时候不用是功力。」
```

**面试官可能的追问**：

```text
Q：为什么 atomic.Value 不能在编译期保证类型？
A：它的设计目标是"存任意值"，API 是 Store(x any)，
   类型信息在运行时的 interface 里，只能运行时检查。
   Go 1.19 的 atomic.Pointer[T] 才是编译期方案。

Q：CAS 循环要不要 sleep 或 Gosched？
A：不要。失败说明有竞争者成功，立刻重读再试即可；
   主动让出反而增加延迟。真到竞争激烈时应该换锁。

Q：atomic 比 mutex 快多少？
A：无竞争时 atomic 是几条 CPU 指令，mutex 是 fast path 一次 CAS，
   差距不大；真正的差距在高竞争下——但那时 atomic 的
   重试成本会迅速追上甚至超过锁。
```
