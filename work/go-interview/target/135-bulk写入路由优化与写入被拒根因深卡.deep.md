# 135 bulk 写入路由优化与写入被拒根因（深卡）

> 分类：Elasticsearch · 分布式写入 | 难度：L3 | 题型：调优题 | 频率：中 | 关键词：**bulk 分批**/**routing 打包**/**写入队列打满**/**写入被拒**
> 原文锚点：第 41~48 段「协调节点对 bulk 同分片请求打包；不指定 routing 散列成片数倍写请求；超大规模集群分片多易写入被拒；相同 routing 打包缓解」

## 思路与架构
本卡把"ES 大规模写入"从**请求层**拉到**路由与队列层**看：bulk 不是简单批量 API，而是协调节点先把"同一分片的子请求"打包、再转发到对应分片的机制。写入被拒（~rejected）往往不是单条慢，而是**路由散列 + 节点抖动**放大成队列积压。

- **bulk 内部**：协调节点收到 bulk 后，按目标分片把请求分组，每个分片的子批一次性转发；未指定 routing 时以 `_id` 路由，一次 bulk 会被拆成"分片数"倍写请求。
- **写入被拒链路**：分片数过多 + 部分节点故障 / GC 卡顿 / 网络抖动 → 某些分片写入延迟 → 节点写入队列打满 → `indexing_queue` 满后新写入被 reject。

## 方案取舍
| 策略 | 做法 | 收益 | 代价 |
| --- | --- | --- | --- |
| 相同 routing 打包 | 把同维度文档放同一 bulk、手动指定 routing | 收敛为单分片写，减少跨分片扇出 | 需业务能划分维度（如按 UID） |
| 手动 routing | 写入时显式 `routing`，让每批都路由到固定分片 | 避免"片数倍"散列、降低队列压力 | routing 设计不当会数据倾斜 |
| 自动 ID（日志场景） | 无更新场景让 ES 生成 ID | 省"先查同 ID"的一次磁盘 IO | 无法按业务 ID 更新 |

**取舍结论**：日志 / 度量等"只写不更新"场景，优先自动 ID + 按维度 routing 打包；有更新场景用业务 ID 但同样按维度 routing 收敛扇出 `[经验]`。

## 答题技巧
- 被问"写入慢 / 写入被拒怎么排查"：先说**路由散列扇出**（bulk 不指定 routing → 片数倍请求），再说**节点侧**（GC/网络/故障）与**队列打满**（indexing queue），最后给"routing 打包 + 手动 routing"两招。
- 惊艳点：点出"分片数越多，不指定 routing 的 bulk 放大越严重"——把"分片规划"和"写入性能"连起来（呼应 1316-shard-planning 的分片数权衡）。
- 边界声明：本卡聚焦**路由层与队列层**的写入优化，与 `1314-doc-index-api`（Go 写入 API / refresh 语义）和 `1316-refresh-translog`（refresh/translog 内部机制）互补，不重复其内部细节；`1314-bulk-processor` 讲 Go 侧 bulk 两式（Add/Do），本卡讲集群侧路由放大与拒绝根因。
