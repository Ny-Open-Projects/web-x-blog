# 159 限流的实现方式：四大算法与三种部署形态

> 分类：分布式 / 高可用 | 难度：L2 | 题型：方案题 | 频率：高 | 关键词：**固定窗口**/**滑动窗口**/**令牌桶**/**漏桶**/**延迟队列**/**分布式限流**

> 原文锚点：第 2~13 段「时间窗口两式 → 令牌桶 → 漏桶 → 延迟队列/分布式/客户端」

## 一句话总述
限流是**预防性**措施，控制流入速率防崩溃。算法四件套：**固定窗口**（简单但窗口边界有 2 倍突刺）、**滑动窗口**（子窗口细分更平滑）、**令牌桶**（恒速发牌、允许突发）、**漏桶**（恒速放行、削平突发）；形态三层次：**延迟队列**（排队+满则拒，如 ES 读写线程池）、**分布式限流**（网关集中式 or 节点协同）、**客户端限流**（策略下发到端）。

## 面试官视角
限流题的两级分档：第一级问算法——答得出四个名字只是及格线，**能对比「允许突发与否」「实现复杂度」「突刺问题」**才算懂；第二级问架构——单机算法怎么变分布式（Redis+Lua 原子化）、ES 线程池队列为什么算延迟队列式限流。最加分的一答是**用数字说话**：固定窗口边界突刺能到 2 倍配额——这是拍脑袋背算法和真算过账的区别。

## 主问答
**Q（面试官原话）：** 限流有哪些实现方式？

1. **固定窗口**：时间切成固定窗口，每窗口配额固定，超了就拒。实现最简单；致命伤是**窗口边界的突刺**——[实测] 配额 10/窗口，前一窗口尾 10 个 + 后一窗口头 10 个跨边界连发，**20 个全放行、拒绝 0**——瞬时速率达到配额 2 倍。
2. **滑动窗口**：把大窗切成小子窗统计（或环形数组逐格滑动），消除边界突刺、控速更平滑；代价是**实现复杂度与统计开销**上升。
3. **令牌桶**：恒速往桶里放令牌，请求取到令牌才通过，桶空则拒。**允许突发**——桶内积攒的令牌可支持短时尖峰，同时限制长期平均速率。适合「平时有余量、偶尔要冲量」的调用方。
4. **漏桶**：请求像水滴入桶，**恒速流出**，桶满拒新。**不允许突发**——出口速率恒定，削平一切尖峰。适合保护「只承受得住固定速率」的脆弱下游。
5. **延迟队列式**：请求进**有限长度队列**按固定速率处理，队满则拒——缓解突刺但**增加延迟**。**ES 的读写线程池就是此式**：固定容量线程池，满则拒绝对应读写请求（拒绝即 429/EsRejectedExecutionException）。
6. **部署形态两翼**：**分布式限流**——中心化（API 网关统一控制）或各节点按全局信息协同；**客户端限流**——策略下发给调用方自控，减轻服务端压力但依赖配合。生产常组合：网关粗限 + 服务内细限 + 客户端自觉。

## 关键代码
```go
// 固定窗口: 演示边界突刺 (配额 10/窗, [实测] 跨窗 20 连发全放行)
const limit = 10
count := map[int]int{} // 窗口编号 -> 计数

func allow(t int) bool { // t: 逻辑时间片
	w := t / 10 // 窗口宽度 10
	if count[w] < limit {
		count[w]++
		return true
	}
	return false
}

// 前一窗口尾 10 发 + 后一窗口头 10 发: 20 发全过 -> 瞬时 2 倍配额
```

## ⚠️ 原文纠错
1. 术语核校： [经验] 原文「令拍筒」=令牌桶、「预值」=阈值、「突刺」用词保留（业内亦称尖刺/spike），已归一。
