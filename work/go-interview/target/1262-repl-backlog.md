# 1262 复制积压缓冲区：环形队列与容量估算

> 分类：Redis | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**repl-backlog-size**/**环形缓冲区**/**默认 1MB**/**覆盖退化**/**容量估算**

> 原文锚点：第 55~59 段「缓冲区结构与查看」、第 75~93 段「覆盖后果与大小估算」

## 一句话总述
复制积压缓冲区是**主节点上一段固定长度的环形队列**，默认 1MB，专门用于支持断连后的增量同步：断连期间缺失的数据若仍在缓冲区内就走增量，一旦被新写入覆盖就只能退回全量。容量 ≈**每秒写命令量 × 断连恢复时间**，通常再乘 2。

## 面试官视角
考官爱问「调大有什么用、调多大」。能给出可计算的公式而不是拍脑袋，并且知道调太大的代价（占主节点内存），就是工程级答案。顺带说出它是**环形覆盖**而非阻塞，也很关键。

## 主问答
**Q（面试官原话）：** 复制积压缓冲区是什么？怎么设大小？

1. **位置与形态**：它保存在主节点上，是一个固定长度的先进先出队列，本质是**环形缓冲区**，从节点连接时创建，专门存放主从连接期间主节点产生的写命令。
2. **写入时机**：主节点每执行完一条写命令，都会把命令数据追加进这块缓冲区，同时发给从节点。
3. **默认与查看**：默认大小为 1MB；用 `INFO replication` 可以看到总容量、已写入大小和当前偏移量。
4. **写满即覆盖**：因为环形，写满后主节点继续写入会**覆盖最早的数据**；主库写入远快于从库读取时，缓冲区很快被覆盖。
5. **估算公式**：按「每秒写命令量 × 断连到恢复的平均时间」估算，通常再取两倍应对突发；配置过大会占用更多主节点内存，需结合内存资源评估。

## 关键代码
```go
// Go 侧视角：按"写速率 × 断连时长 × 2"算出建议值，并换算成配置
package main

import "fmt"

func backlogSize(writeMBPerSec float64, downtimeSec float64) string {
	mb := writeMBPerSec * downtimeSec * 2 // 两倍余量应对突发
	return fmt.Sprintf("repl-backlog-size %dmb", int(mb))
}

func main() {
	fmt.Println(backlogSize(10, 10)) // 10MB/s × 10s × 2 = 200mb
}
```

## 总结与追问预判
核心：**环形、会覆盖、决定断连后能否增量；容量 = 写速率 × 断连时长 × 2**。追问常拐向「为什么网络一抖就全量」，备好「缓冲太小被覆盖」这句话。

## ⚠️ 原文纠错
1. 事实核校： [经验] 原文举例「主库每秒 10MB 写、断连 10 秒 → 需要 100MB」计算正确；但紧接着又说「通常设置成预估值的两倍」，则实际应配 **200MB**，原文举例与结论未衔接，本卡明确给出两步算式。
2. 事实核校： [经验] 原文称缓冲区「在从节点连接时被创建」——准确说是**主节点侧**在有从节点连接时创建并维护，**所有从节点共享同一块**缓冲区，并非每个从节点各有一份。
3. 崩坏词归一：源码将 Redis / 复制积压缓冲区 / INFO replication 等音译为多组崩坏词，本卡统一为规范术语。
