# 1832·深 五种 IO 模型一张图讲透：两轴判定与 Go 的落点

> 分类：操作系统 / 网络 | 难度：L4 | 题型：原理题 | 频率：高 | 关键词：**五种IO模型**/**阻塞IO**/**非阻塞IO**/**IO多路复用**/**信号驱动IO**/**异步IO**/**io_uring**/**netpoll**
> 原文锚点：第 14~37 段「常见的 IO 模型有五种…第一个是阻塞 IO…第二种是非阻塞 IO…第三种是 IO 多路复用…第四种是信号驱动 IO…第五个 IO 模型是异步 IO…阻塞 IO 和非阻塞 IO 是两种不同的操作模式」
> [边界] 本文是 `1832-blocking-vs-nonblocking` 的深挖，主卡已讲的"等待+拷贝两阶段"此处不重述；三种多路复用系统调用的实现对比见 1834。

## 思路与架构

把五种模型压成**一张两轴坐标图**，横轴是第一阶段（等数据）谁负责，纵轴是第二阶段（拷贝）谁阻塞：

```text
阶段①  等数据就绪          阶段②  内核→用户拷贝         模型
─────────────────────────────────────────────────────────────
阻塞等待（线程挂起）        阻塞（同步拷贝）              阻塞 IO
立即返回 + 应用轮询         阻塞（同步拷贝）              非阻塞 IO
select/poll/epoll 阻塞等    阻塞（同步拷贝）              IO 多路复用
不等，内核发信号通知         阻塞（同步拷贝）              信号驱动 IO
不等，内核全程包办           不等，内核拷完再通知          异步 IO        ← 唯一的真异步
```

三条推导链：

1. **为什么前四种都叫同步 IO**：同步的定义是"真正的读操作由应用自己发起并等待其完成"。前四种最终都要应用自己调 `recvfrom`/`read` 完成**拷贝**，这一步必然阻塞，所以**全是同步**。
2. **为什么多路复用比非阻塞强**：它把"轮询"这件事从**用户态循环**搬到了**内核里的一次等待**。应用不再空转，一次调用可以同时盯住成百上千个 fd，就绪了才动手。
3. **为什么异步 IO 最难落地**：它要求内核把拷贝也做完再回调。Linux 原生 AIO 长期只对 `O_DIRECT`（绕过页缓存）有效，且不支持 socket；直到 **5.1 引入 `io_uring`** 才有了统一、可用的真异步接口。

## 方案取舍

```text
选型判断树（面试里按这个顺序往下问自己）
────────────────────────────────────
Q1 连接数少（< 几百）且逻辑简单？
    └─ 是 → 阻塞 IO + 每连接一线程/协程。代码最简单，可读性最高。
Q2 连接数多、但每个连接大部分时间在等？
    └─ 是 → 非阻塞 fd + IO 多路复用（Linux: epoll / BSD: kqueue）。
Q3 想彻底消除"拷贝阶段也阻塞"、且跑在 Linux 5.1+？
    └─ 是 → io_uring。但要接受复杂度与内核版本门槛。
Q4 用 Go / Node / Rust tokio 这类运行时？
    └─ 是 → 直接用语言原生抽象，别自己碰系统调用。
```

- **阻塞 IO 的取舍**：换来**代码直白**，付出**线程被占死**。Go 里这个代价被 goroutine 摊销了——goroutine 初始栈极小、阻塞时被 netpoll 摘下不占 OS 线程，所以 Go 代码**看起来是阻塞写法，底层跑的是多路复用**。这是 Go 网络编程最大的"骗术"，也是面试加分点。
- **非阻塞 + 轮询的取舍**：换来**线程不挂起**，付出**CPU 空转**。实测 200ms 空转 413 万次循环、等 100ms 数据要 106876 次 `read`——**单独使用基本没有收益场景**。
- **信号驱动 IO 的取舍**：换来**不用轮询**，付出**信号处理复杂、信号队列可能溢出、在多线程里语义混乱**。工程上**极少使用**，面试知道名字和位置即可。
- **异步 IO 的取舍**：换来**两阶段都不阻塞**，付出**平台不统一**（Windows IOCP 成熟、Linux 靠 io_uring、macOS 无原生）、**心智负担重**。写业务服务通常不值得。

## 答题技巧

- **开口先立两阶段**，再摆两轴，最后点模型。这个顺序能救回 80% 的卡壳——很多人一上来就背五种名字，越背越乱。
- **必背的那句反转**：「**非阻塞 IO 不是异步 IO，它只是第一阶段不等，第二阶段拷贝照样阻塞，所以它仍然属于同步 IO。**」这句话一出口，基本锁定 P7。
- **把 Go 拉进来做收尾**：Go 的 `net` 包在 Linux 用 epoll、macOS/BSD 用 kqueue（源码文件名即证据：`netpoll_epoll.go` 是 `//go:build linux`、`netpoll_kqueue.go` 是 `//go:build darwin || ...`）。所以**你写的同步阻塞代码，运行时底下跑的是多路复用**。
- **主动划清边界**：提到异步 IO 时补一句"Linux 原生 AIO 长期只支持 `O_DIRECT`、不支持 socket，真正可用是 5.1 的 `io_uring`"，能挡掉追问。
- **别踩的坑**：不要说"五种模型是并列的"——它们是**按两轴组合出来的**，多路复用本质仍是同步阻塞在第二阶段。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| POSIX 全平台 | 五种模型定义恒定 | 通用答案 |
| Linux 2.6+ | epoll 可用 | 多路复用默认选 epoll |
| Linux 5.1+ | `io_uring` 引入 | 真异步才有生产级方案 |
| macOS / BSD | 无 epoll、无 io_uring | 对应 kqueue |
| Windows | 模型不同，是 **IOCP**（真异步） | 别与 epoll 直接类比 |
| Go 全版本 | netpoll 按平台选后端 | 业务层写阻塞式代码即可 |

## 细节与核心 API

```go
// 五种模型（以“读取”为例，区别在“等数据就绪”与“拷数据”两个阶段由谁/何时做）
// 1) 阻塞：recv 一直等到数据到并拷完
c, _ := net.Dial("tcp", addr); buf := make([]byte, 1024); c.Read(buf) // 阻塞直至完成
// 2) 非阻塞：反复轮询，立即返回 EWOULDBLOCK
//    f.SetNonblock(true); for { n,err := f.Read(buf); if err==EAGAIN { continue } }
// 3) IO 多路复用：select/poll/epoll 同时盯多个 fd，就绪再读（仍是阻塞在 select）
// 4) 信号驱动：SIGIO 通知就绪，再读
// 5) 异步 IO（AIO / io_uring）：提交后立刻返回，内核拷完发事件，期间线程干别的
// Go 用户写的是“阻塞风格”，runtime 用 netpoller（epoll/kqueue）把每个 conn 的阻塞
// 翻译成 G 挂起、M 不阻塞，从而一个线程撑海量连接（等价模型3但写法如模型1）
// 性能：模型5 拷贝也异步，延迟与吞吐最优；模型1 简单但每连接一线程，C10K 即爆
```
