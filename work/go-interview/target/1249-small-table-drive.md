> 原文锚点：第 1~2 段「那第四点呢就是我们可以用小表来驱动大表…通过合理的设计查询语句…在查询性能上获得一定的提升」（小表放 join 驱动位置/连接子句前置 → 减少大表扫描与过滤）

## 一句话总述
「小表驱动大表」是 join 优化经验：**把结果集更小的表作为驱动表（外层表）放在连接条件的前置位置**，让内层大表被探测/扫描的次数最小化；其本质是「用驱动表的行数 × 内层探测成本」去换「大表全扫次数」。

## 面试官视角
这题考 join 执行模型的直觉，而非死记名词。考点：① 驱动表决定内层被扫描几次；② 为什么小表当驱动表能降本；③ 现代优化器会不会自动选——会不会被追问「那优化器自己选不就好了」。能答出「优化器基于成本通常能选对，但统计信息失真/用了 STRAIGHT_JOIN 时顺序由人定」才算过关。

## 主问答
**Q（面试官原话）：** 什么是小表驱动大表？为什么要把小表放在驱动位置？

**A：**
1. **驱动表决定内层探测次数**：嵌套循环 join（NLJ）中，驱动表（外层）每出一行，就去内层表按连接键探测一次。若驱动表有 100 行、大表 1000 万行，大表最多被「索引探测」100 次（每次走索引，极快）；反过来若大表驱动，则要对 1000 万行各探测小表一次，成本翻万倍。
2. **小表前置 = 减少大表扫描/过滤**：把小表放到 `JOIN ... ON` 的驱动侧，大表只做「被探测」角色，借助其连接键索引完成点查，避免大表被反复全扫或大量回表过滤。
3. **优化器通常会自动选，但人需兜底**：MySQL 优化器基于统计信息估算两表成本，多数情况会自动选小表驱动；但当**统计信息过时**或用 `STRAIGHT_JOIN` 强制顺序时，顺序由 SQL 写法定，此时「小表驱动大表」就是手写经验。
4. **前提**：驱动表要「真小」且连接键有索引；若小表无选择性、大表无连接索引，强制小表驱动反而可能更慢——这是被优化器反超的常见场景。

## 版本与兼容性
- 该经验适用于所有基于 NLJ/Hash Join 的 RDBMS（MySQL/PostgreSQL/Oracle）；MySQL 用 `EXPLAIN` 看 `select_type`/`rows` 确认驱动表，`STRAIGHT_JOIN` 可强制顺序。
- InnoDB 下连接键应有索引，否则退化为「块嵌套循环（BNL）」或直接大表全扫，驱动顺序的意义被稀释。
- 注意与「小表全扫是优化器择优」（见 1221.md`）区分：那是**单表**小表为何全扫，本卡是**两表 join** 的驱动顺序，二者不同维度。

## 关键代码

```sql
-- 小表驱动大表：orders（小，百万级）驱动 user_log（大，亿级）
-- 优化器通常自动选 orders 为驱动表；用 STRAIGHT_JOIN 可强制顺序
EXPLAIN
SELECT /*+ ... */ o.id, u.uid
FROM orders o
STRAIGHT_JOIN user_log u ON u.order_id = o.id   -- o 小表前置，u 走 order_id 索引点查
WHERE o.status = 1 AND o.created_at > '2026-01-01';

-- 对比：若反过来让大表驱动，user_log 每行都去 orders 做探测，成本翻数倍
EXPLAIN
SELECT o.id, u.uid
FROM user_log u
STRAIGHT_JOIN orders o ON o.id = u.order_id;     -- 反模式：大表驱动
```

## 总结与追问预判
收口：**驱动表行数 ≈ 内层探测次数；小表驱动让大表只走索引点查，省掉反复全扫**。预判追问：① 优化器为何有时选错（统计信息，见 `1221`）→ ② 更大规模的降本手段（分库分表，见 1249.md`）；③ 表结构层优化（动静分离，见 1249.md`）。回答时把「NLJ 成本 = 驱动行数 × 内层探测」一句抛出，最显功底。

## ⚠️ 原文纠错
源视频转写将 join / 驱动表 / 小表 / 连接子句 等音译为崩坏词（如「well 子句」指代连接 on 子句、「驱动大表」语义保留但「well」崩坏），本卡已还原为规范术语（连接子句 ON / 驱动表 / 小表驱动大表）。交付卡禁止保留任何原词崩坏写法。

> **[经验]** 「小表驱动大表」在**有索引的 NLJ** 场景下成立；若内层大表连接键无索引，大表每次都被全扫，驱动谁都一样慢——此时正解是补索引而非纠结驱动顺序。面试中主动点出「前提是连接键有索引」，能区分背口诀的人和真懂执行计划的人。
