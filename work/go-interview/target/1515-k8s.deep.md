# 1515 K8s 声明式控制循环本质深挖

## 思路与架构
K8s 解决的本质问题是：**当容器数量从「几个」膨胀到「成千上万」时，人工调度、扩缩、自愈、服务发现都不可持续**——它用一个**声明式控制循环**（调和「期望状态」与「实际状态」）把运维经验固化成系统能力。

```text
为什么需要 K8s（问题域）
  裸容器/脚本部署
    ├─ 调度靠人：扩缩容手敲命令，易错
    ├─ 无自愈：容器挂了没人拉
    ├─ 无服务发现：Pod IP 变，调用方硬编码崩
    └─ 跨机编排难：几千容器怎么分布？
        ↓
  K8s 控制循环：用户写 YAML(期望) → APIServer 入 etcd → Controller 调和 → kubelet 执行
    └─ 期望≠实际时自动纠正（自愈/扩缩/重调度）
```

## 方案取舍
| 方案 | 适用 | 代价 | 何时选 |
| --- | --- | --- | --- |
| 裸容器 / docker run | 单机小应用 | 无调度/自愈/发现 | 学习/原型 |
| Docker Compose | 单机多容器 | 无跨机编排 | 小团队中等规模 |
| K8s | 多机/大规模/需弹性 | 学习+运维成本高 | 生产微服务/弹性/跨云 |
| 其他编排(Swarm/Nomad) | 轻量编排 | 生态弱于 K8s | 简单场景/已有栈 |

**取舍结论**：K8s 是「规模 + 弹性 + 跨云」场景的事实标准，但对小项目是过度工程。核心抽象（Pod/Controller/Service/Namespace）和声明式控制循环是其价值根基。

**分层关系**：微服务（架构风格，`152/154/157/158`）决定「怎么拆」，K8s 决定「怎么跑」——二者不同层、可叠加。K8s 提供基础设施级弹性（副本/自愈/HPA），服务网格（如 Istio）提供应用级治理（熔断/限流），按需叠加。

## 答题技巧
1. **架构→优势→场景→边界** 四段式：先讲 Master/Node/Pod 架构，再讲六大优势机制，再讲场景，最后必带「不适合小项目」边界。
2. **机制优于名词**：高可用→副本+探针自愈；弹性→HPA 追指标；可移植→声明式抽象底层。
3. **数字显专业**：Pod 是最小单位、etcd 是唯一真相源、成熟集群数千节点/数十万容器、HPA 指标驱动。
4. **边界收尾**：明确「K8s 不是银弹」，小项目用 Compose 更划算——这是高阶分水岭。
5. **避坑**：不说「Pod 是最小容器」（应是最小调度单位，含共享网络的一组容器）；不把 RC 当现代用法（已被 RS/Deployment 取代）；不把 Service 当负载均衡器本体（它定义规则，kube-proxy 执行）。

## 细节与核心 API

**核心抽象落地（声明式 YAML）：**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: orders }
spec:
  replicas: 3                       # 副本+探针自愈
  selector: { matchLabels: { app: orders } }
  template:
    metadata: { labels: { app: orders } }
    spec:
      containers:
      - name: app
        image: orders:v1
        resources:
          requests: { cpu: "100m", memory: "128Mi" }
          limits:   { cpu: "500m", memory: "256Mi" }   # limits.cpu=2 → cpu.max "200000 100000"
---
apiVersion: v1
kind: Service
spec:
  selector: { app: orders }
  ports: [{ port: 80, targetPort: 8080 }]   # Service 定义规则，kube-proxy 执行
```

**控制循环（期望状态 vs 实际状态自动调和）：**

```text
kubectl → apiserver(认证/鉴权/准入) → etcd(唯一真相源) → Controller 调和 → kubelet 执行(自愈/扩缩/重调度)
分层：微服务(怎么拆) + K8s(怎么跑) + 服务网格(熔断/限流，应用级治理) 可叠加
```
