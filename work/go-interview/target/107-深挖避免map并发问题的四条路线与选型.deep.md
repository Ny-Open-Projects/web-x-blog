# 107 深挖：避免 map 并发问题的四条路线与选型

> 分类：Go 并发 | 难度：L5 | 题型：综合题 | 频率：高 | 关键词：**整体重新赋值、sync.Map、读写锁、分片 map、channel 串行化、锁粒度、选型**

> 原文锚点：第 1~74 段「map 是非并发安全的，map 的底层实现中会进行强制校验，如果出现并发写操作，就会导致程序崩溃。前面的章节介绍了两种方法，一个是对整个 map 变量进行重新赋值，而不是去操作单个的键值；第二个是使用 Go 标准库 sync 提供的并发安全的 map…选择哪种方法取决于具体的场景和需求。在许多情况下，使用互斥锁和读写锁是足够的…大部分场景下，我们使用 sync 标准库提供的 sync.Map 就可以了」

## 思路与架构

按「**为什么必须处理 → 四条路线 → 怎么选**」三层把握：

1. **为什么必须处理**：**map 是非并发安全的**，**map 的底层实现中会进行强制校验**，**如果出现并发写操作，就会导致程序崩溃**。所以它不像普通数据竞争那样"结果不可预期"，而是**直接崩**——没有侥幸空间。
2. **四条路线（由轻到重）**：
   - **① 整体重新赋值**：**对整个 map 变量进行重新赋值，而不是去操作单个的键值**。思路是"**不改共享的那份，而是整体换一个新的**"，适合**读多、更新频率低、且可以接受整体替换**的场景（如配置热更新）。
   - **② 使用 `sync.Map`**：**Go 标准库 sync 提供的并发安全 map**。**大部分场景下用它就可以了**——它内部用 **read / dirty 双 map 做读写分离**读路径无锁，适用**读多写少**（详见 `922-*` 那批）。
   - **③ 自己用锁封装**：**`sync.RWMutex` + 原生 map**，**get 读锁、set/delete 写锁、range 读锁 + 迭代器回调**。优点是**可控、可配泛型保证类型安全**；缺点是**整个 map 是一把大锁、粒度过于集中**。进一步优化即**分片 map**：**用切片存放 32 个 map、每片一把独立锁**，**分片号 = FNV(key) % 分片数**，**同 key 同片、异 key 打散**；遍历要**两层循环且锁在循环内**，**提前 return 前必须再解锁**。
   - **④ channel 串行化**：**起一个专门的 goroutine 处理全部 map 操作**，**把操作封装成 request（op + key + value + 返回值）投递进 channel**，`run` 循环取出按 op 分派，**get 用 response channel 回传**。安全来自"**只有一个 goroutine 碰 map**"，本质是串行化。
3. **怎么选**：
   - **原文给的判据**：**选择哪种方法取决于具体的场景和需求**；**在许多情况下，使用互斥锁和读写锁是足够的**；**大部分场景下，使用 `sync.Map` 就可以了**。
   - 介绍这些方法的主要目的是**掌握应对并发安全问题的多种手段**，而非鼓励重复造轮子。

## 方案取舍

| 方案 | 并发度 | 类型安全 | 遍历 | 适用 |
|---|---|---|---|---|
| 整体重新赋值 | 读无锁、写整体换 | 可配泛型 | 快照语义 | 配置/字典类，低频全量更新 |
| `sync.Map` | 读无锁、写加锁 | `any`，无编译期检查 | `Range` 快照 | 读多写少、写一次读多次 |
| 读写锁封装 | 读并发、写独占 | 可配泛型 | 持锁遍历会阻塞写 | 通用首选，读多写少 |
| 分片 map | 按 key 打散，高 | 可配泛型 | 两层遍历、弱一致 | 写较密集且 key 分布均匀 |
| channel 串行化 | **恒为 1** | 可配泛型 | 遍历大 map 阻塞全部 | 思路演示、事件总线 |

取舍要点：**四条路线本质上是在"并发度"与"实现复杂度"之间做交换**——整体替换最省心但只适合低频全量更新；`sync.Map` 是官方通用解但丢了类型安全；读写锁是平衡点；分片 map 用更高复杂度换更高写并发；channel 串行化把并发度降到 1，**通常是性能最差、但语义最清晰**的一条。

## 答题技巧

1. **开场必须先说"会崩"**：**map 并发写不是数据错乱，是底层强制校验直接抛异常**——这一定性判断先立住。
2. **四条路线要能一口气列全**：整体重新赋值 / `sync.Map` / 锁（含分片）/ channel 串行化。
3. **讲锁时一定要带上"粒度"这条主线**：**一把大锁 → 分片打散**，这是本节最有价值的技术递进。
4. **分片方案要报出三个细节**：**32 个分片**、**FNV 哈希**、**锁加在循环内且 return 前解锁**——这三个细节是它区别于泛泛而谈的证据。
5. **主动给选型结论**：**大部分场景用 `sync.Map`；许多情况下读写锁就够**；**channel 方案并发度恒为 1，仅作思路演示**。
6. **止步档位**：能写出读写锁封装并说出分片思路即达 L4；能列全四条路线、讲清分片细节与 channel 的串行瓶颈，并给出场景化选型，即达 L5。

## 细节与核心 API

**① 整体重新赋值**（配置/字典类，低频全量更新，读无锁）：

```go
var cfg atomic.Value
func update(m map[string]int) { cfg.Store(m) }                 // 全量换，不改共享那份
func get(k string) (int, bool) { return cfg.Load().(map[string]int)[k] }
```

**② sync.Map**（读多写少、不相交 key 集合；read/dirty 双 map，读路径无锁）：

```go
var m sync.Map
m.Store("k", 1)
v, ok := m.Load("k")
v, loaded := m.LoadOrStore("k", 2)
m.Range(func(k, v any) bool { return true }) // 快照遍历
```

**③ RWMutex + 原生 map**（通用首选，读多写少，可配泛型保证类型安全）：

```go
type SafeMap[K comparable, V any] struct {
    mu sync.RWMutex
    m  map[K]V
}
func (s *SafeMap[K, V]) Get(k K) (V, bool) { s.mu.RLock(); defer s.mu.RUnlock(); return s.m[k] }
func (s *SafeMap[K, V]) Set(k K, v V)      { s.mu.Lock(); defer s.mu.Unlock(); s.m[k] = v }
func (s *SafeMap[K, V]) Range(f func(K, V) bool) {
    s.mu.RLock(); defer s.mu.RUnlock()
    for k, v := range s.m { if !f(k, v) { return } } // 持锁遍历会阻塞写
}
```

**分片 map**（写较密集且 key 分布均匀；32 分片、FNV 哈希、锁在循环内、return 前必须再解锁）：

```go
const shards = 32
type Sharded[K comparable, V any] struct {
    mu [shards]sync.RWMutex
    m  [shards]map[K]V
}
func (s *Sharded[K, V]) idx(k K) uint32 {
    h := fnv.New32a(); h.Write([]byte(fmt.Sprintf("%v", k))); return h.Sum32() % shards
}
func (s *Sharded[K, V]) Get(k K) (V, bool) {
    i := s.idx(k); s.mu[i].RLock(); defer s.mu[i].RUnlock(); return s.m[i][k]
}
```

**④ channel 串行化**（并发度恒为 1，思路演示/事件总线；单 goroutine 碰 map）：

```go
type op int
const getOp, setOp op = 0, 1
type req struct{ op op; key string; val int; resp chan any }
func run(in <-chan req, data map[string]int) {
    for r := range in {
        switch r.op {
        case getOp: r.resp <- data[r.key]
        case setOp: data[r.key] = r.val; r.resp <- nil
        }
    }
}
```

> 边界：map 并发 panic 本质见 914；分片降低锁粒度见 925；race detector 验证见 1018。
