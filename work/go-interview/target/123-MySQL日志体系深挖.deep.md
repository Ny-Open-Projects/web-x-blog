# 123 MySQL 日志体系深挖

> 原文锚点：第 1~113 段「MySQL 日志体系与 binlog 配置」

## 一句话总述
在四类日志骨架之上，深挖通用查询日志的实践细节、配置文件加载顺序的真实语义，并定位 binlog/redo 对比的归属。

## 主问答
**Q（面试官原话）：** 四类日志之外，还有哪些容易踩的细节？
**A：**
1. **通用查询日志（general log）**：`general_log=ON` 开启、`general_log_file` 指定路径；记录所有连接/断开/每条 SQL，**量极大、高并发迅速撑满磁盘、拖累性能**，生产慎开；默认关，若不指定路径落到 `/var/lib/mysql`（常是系统盘）。
2. **配置文件加载顺序**：MySQL 按 `--help` 中 `default-options` 列出的顺序**从左到右**读，`my.cnf` 列表**越靠后优先级越高**（后读覆盖先读），当前目录 `./my.cnf` 与 `~/.my.cnf` 通常在末位、优先级最高。
3. **binlog 与 redo 的边界**：本（一）只铺日志体系与 binlog 配置；**redo log vs binlog 的物理/逻辑、循环/追加、引擎层/server 层差异在 12-4（二）**，勿混。

## 关键代码
```sql
SET GLOBAL general_log = ON;
SET GLOBAL general_log_file = '/data/mysql/general.log';
```

## 思路与架构
- 四类日志是"入口诊断—性能优化—全量审计—复制恢复"的完整链路；通用日志是链路里**最危险**的一环（全量+系统盘风险），故单独深挖。
- 配置文件"后读覆盖先读"是 MySQL 配置生效的**根本规则**，理解它才能解释"为何当前目录 my.cnf 优先级最高"。

## 方案取舍
- 通用日志：排查问题时**临时**开启、`general_log_file` 指向数据盘，用完即关；切忌长期常开。
- binlog 保留时长 `binlog_expire_logs_seconds`：默认 30 天，备库延迟大的场景要调长，避免 binlog 被清理导致备库断裂。

## 答题技巧
1. 面试官问"有哪些日志"后常追"哪个最危险"——直接点通用日志（量+盘风险）。
2. 配置优先级题：先讲加载顺序，再讲"后读覆盖先读"，最后落到当前目录/家目录 my.cnf 最高。
3. 把 binlog/redo 对比**明确指到 12-4**，体现你清楚知识边界，不抢答。

## 总结
通用日志全量审计但有性能/磁盘代价；配置"后读覆盖先读"决定最终生效值；redo/binlog 实质差异归 12-4。
