# 107 用读写锁封装并发安全的 map：迭代器模式与"一把大锁"的瓶颈

> 分类：Go 并发 | 难度：L3 | 题型：实现题 | 频率：高 | 关键词：**RWMutex、读写锁、读锁、写锁、迭代器、匿名函数、锁粒度**

> 原文锚点：第 1~23 段「map 是非并发安全的，map 的底层实现中会进行强制校验，如果出现并发写操作，就会导致程序崩溃…首先我们定义了一个结构体，它有两个字段，第一个字段是一个读写锁，第二个字段是键值为 any 类型的一个 map…get 操作加的是读锁，set 操作加的是写锁，delete 操作也是一个写锁…range 方法的入参是一个匿名函数，这个匿名函数返回了一个布尔类型，这里是读操作所以只需要加一个读锁…读锁的使用在一定程度上提升了 map 的并发性能，但是整个 map 是一把大锁，锁的粒度过于集中，还有优化的空间」

## 一句话总述
用 **`sync.RWMutex` + 原生 map** 封装一个并发安全容器：**结构体只有两个字段**（读写锁 + `map[any]any`），**`get` 加读锁、`set`/`delete` 加写锁**，**`range` 用"匿名函数作入参"实现迭代器**（回调返回 `true` 继续、返回 `false` 终止，遍历属读操作故只加读锁）。读锁提升了并发读性能，但**整个 map 仍是一把大锁，粒度过于集中**。

## 面试官视角
- 考察意图：能否把"加锁"从会调 `Lock()` 升级为**按操作性质选锁 + 封装成可用 API**。
- 分档：P5 知道并发写 map 会崩；P6 能写出 `RWMutex` 封装；P7 能补上**迭代器模式**（回调 bool 控制终止）、**读锁只用于遍历**的理由，以及**"一把大锁"这一瓶颈及其优化方向（分片）**。
- 红旗答案：遍历时也加写锁；或不知道原生 map 并发写会直接崩溃（**底层有强制校验**）。
- 惊艳点：**并发写原生 map 不是"数据错乱"而是程序崩溃**——map 底层实现中**会进行强制校验**，一旦检测到并发写就抛出异常 `[源码]`。

## 主问答
**Q（面试官原话）：** 怎么用锁实现一个并发安全的 map？

1. **结论**：用 **`sync.RWMutex`** 保护一个原生 map 并封装操作方法：**读加读锁、写与删除加写锁、遍历加读锁并用迭代器回调** `[源码]`。
2. **为什么必须做**：**map 是非并发安全的**，**map 的底层实现中会进行强制校验**，**如果出现并发写操作，就会导致程序崩溃** `[源码]`。
3. **结构体**：只有**两个字段**——**第一个是读写锁**，**第二个是键值为 `any` 类型的一个 map** `[源码]`。
4. **get / set / delete 的锁选择**：**`get` 加读锁**，返回传入 key 对应的值；**`set` 加写锁**，把 key 对应的 value 设置进 map；**`delete` 也是写锁**，调用 map 的 `delete` 方法删除 key 对应的值 `[源码]`。
5. **range 与迭代器**：**`range` 方法对 map 进行遍历，入参是一个匿名函数，该函数返回一个布尔类型**；**因为遍历是读操作，所以只需要加读锁，解锁时解除读锁**；**遍历过程中把得到的键值传给传进来的参数 `f`**；**这种"匿名函数作为参数去接收值"的方式，是 Go 语言里很常见的一种迭代器实现** `[源码]`。
6. **终止语义**：**在这个匿名函数里返回 `true`，表示迭代器继续执行；返回 `false`，迭代器就会终止** `[源码]`。
7. **效果与瓶颈**：**对 map 的访问使用读锁、修改和删除使用写锁，读锁在一定程度上提升了 map 的并发性能**；**但整个 map 是一把大锁，锁的粒度过于集中，还有优化空间** `[源码]`。

**加分层：** 这个封装暴露了一个通用判断——**读写锁只在"读远多于写"时才有意义**；若写占比高，读写锁的额外复杂度换不来收益，直接用 `sync.Mutex` 更省心。

## 关键代码
```go
package main

import "sync"

// SafeMap：读写锁 + 原生 map，两个字段即全部状态
type SafeMap struct {
	mu sync.RWMutex
	m  map[any]any
}

func NewSafeMap() *SafeMap { return &SafeMap{m: make(map[any]any)} }

func (s *SafeMap) Get(k any) any { // 读 -> 读锁
	s.mu.RLock()
	defer s.mu.RUnlock()
	return s.m[k]
}

func (s *SafeMap) Set(k, v any) { // 写 -> 写锁
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[k] = v
}

func (s *SafeMap) Delete(k any) { // 删 -> 写锁
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.m, k)
}

// Range：遍历是读操作 -> 只加读锁；匿名函数作迭代器，返回 false 终止
func (s *SafeMap) Range(f func(k, v any) bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	for k, v := range s.m {
		if !f(k, v) {
			return
		}
	}
}

func main() {
	sm := NewSafeMap()
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ { // 并发写：原生 map 会崩，这里安全
		wg.Add(1)
		go func(i int) { defer wg.Done(); sm.Set(i, i) }(i)
	}
	wg.Wait()
	sm.Range(func(k, v any) bool { return true })
}
```

## 总结与追问预判
**必追问的是"这把大锁怎么优化"**——答案是**分片**：**把锁的粒度分散到各个分片而不是整个 map**，见 `107-sharded-map`。追问常接"那还要不要自己写"——**大部分场景直接用标准库的 `sync.Map` 即可**（见 `922-*` 那批），自己写主要用于**需要类型安全（配泛型）或需要自定义遍历/批量语义**的场景。

## ⚠️ 原文纠错
1. 事实核校：原生 map 非并发安全且底层有强制校验、并发写导致程序崩溃、结构体为读写锁加 map 两字段、get 读锁、set/delete 写锁、range 入参为返回 bool 的匿名函数且遍历只加读锁、回调返回 true 继续 false 终止、匿名函数作迭代器是 Go 常见写法、读锁提升并发读但整个 map 仍是一把大锁故粒度过于集中——均与 Go 语义一致 `[经验]`。
2. 补充：**迭代期间持锁会阻塞所有写操作**，若回调里执行耗时逻辑（如网络调用）会严重拖慢写入；生产实现应先持锁拷贝快照、出锁后再遍历回调 `[经验]`。
3. 崩坏词归一：源码将读写锁、键值对、迭代器、匿名函数、goroutine、锁粒度等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
