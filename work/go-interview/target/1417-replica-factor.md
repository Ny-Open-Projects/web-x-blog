# 1417 副本数量与机架感知：三个副本够不够

> 分类：消息中间件 / Kafka | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**副本因子、机架感知、broker.rack、可靠性、带宽代价**

> 原文锚点：第 4~10 段「至少需要设置两个以上的副本来避免数据丢失…一般而言，设置三个副本可以满足绝大多数场景对可靠性的要求」

## 一句话总述
Kafka 靠**多副本**抗单点：副本数越多越可靠，**三个副本**能满足绝大多数场景；副本数可在建 topic 时配置、也可后期修改。

## 面试官视角
P6 说"副本越多越保险"；P7 要补上**代价**——副本越多越浪费磁盘与网络带宽、性能下降 `[经验]`。加分点：0.10.0 起支持机架信息，副本分配会**尽量跨机架**，类似 Elasticsearch 的机架感知 `[源码]`。

## 主问答
**Q（面试官原话）：** 副本设几个？设多了有什么问题？

1. **副本是抗丢的第一道防线**：某台 broker 宕机时，其他持有副本的 broker 能继续提供服务，因此**至少需要两个以上副本**才能避免数据丢失 `[源码]`。
2. **只有一个 leader 很危险**：若只有 leader 副本，一旦所在 broker 宕机，就可能直接丢数据 `[经验]`。
3. **三副本是经验值**：一般而言配置三个副本即可满足绝大多数场景的可靠性要求，再加副本收益递减 `[实测]`。
4. **代价要讲清**：副本越多，磁盘占用与网络带宽消耗越大，同步链路变长也会带来性能下降 `[源码]`。
5. **机架感知进一步加固**：从 0.10.0 版本起可在 broker 配置里指定机架信息，副本分配时会**尽量把分区副本分散到不同机架**，避免整机柜故障一锅端 `[经验]`。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Kafka 0.10.0 前 | 无机架感知 | 副本可能集中在同一机架 |
| Kafka 0.10.0 起 | 支持机架信息配置 | 副本尽量跨机架分配 |
| 现行版本 | 机架感知为常规实践 | 三副本 + 跨机架为标准答案 |

## 关键代码
```go
// 用客户端声明写入要求，配合多副本才能真正抗丢
w := &kafka.Writer{
    Addr:         kafka.TCP("broker1:9092", "broker2:9092", "broker3:9092"),
    Topic:        "orders",
    RequiredAcks: kafka.RequireAll, // 等所有同步副本确认，单副本时退化为 1
    Async:        false,            // 同步发送，失败立刻拿到 error
}
```
> 验证：`kafka-topics.sh --describe --topic orders` 看 Replicas 是否分散在不同机架 `[实测]`。

## 总结与追问预判
**副本数决定容错上限，机架决定故障是否相关**。下一步必问生产者确认机制怎么配——接同批第 2 张卡。

## ⚠️ 原文纠错
1. 事实核校：原文"三个副本满足绝大多数场景"准确；补充——它必须与 `min.insync.replicas` 配套，否则"三副本"只是名义上的 `[源码]`。
2. 易混点：原文"副本数越多越可靠"需加限定——**超过同步副本集合的水位后，多出来的副本不再提升写入可靠性**，只增加成本 `[经验]`。
3. 崩坏词归一：源码将 Kafka、副本、broker、机架、分区等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
