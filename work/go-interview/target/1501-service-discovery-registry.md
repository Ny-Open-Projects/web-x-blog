## 一句话总述
服务注册与发现让微服务**运行时动态寻址、免硬编码 IP**：独立高可用的**注册中心**（etcd/consul/zookeeper）存实例信息；实例启动**注册** name/IP/port 并定期发**心跳**，停发心跳则被标记不可用并摘除；调用方**发现**时查注册中心、按客户端负载均衡（轮询/随机/最少连接）选一个实例。客户端可缓存实例减轻注册中心压力。

## 面试官视角
注册中心是微服务的"电话簿"。面试官想确认你懂"注册-心跳-发现-客户端LB"全链路，以及 etcd/consul/zookeeper 这类组件的定位。

## 主问答
**Q（面试官原话）：** 微服务怎么实现服务发现和注册？

**A：**

1. **注册中心**：一个高可用独立组件（常见 etcd / consul / zookeeper），负责存所有服务实例的元数据（名称、IP、端口、健康状态），并提供查询与订阅。
2. **服务注册 + 心跳**：实例启动时把自己的标识注册进中心；之后**定期发心跳**证明存活；若停止发心跳，中心将其标记为不可用，超时后从列表删除（对应 `157` 治理里的"心跳摘除"）。
3. **服务发现**：调用方需要与某服务通信时，向注册中心查询可用实例；拿到一个或多个地址后，按**客户端负载均衡**策略（轮询/随机/最少连接）选一个通信。
4. **客户端缓存 LB**：客户端可缓存实例列表在本地做负载均衡，减轻注册中心压力、降低每次调用的 lookup 延迟；注册中心变更时通过订阅/通知刷新缓存。

## 追问链（L1~L5）
| 层 | 追问 | 在测什么 | 怎么接 | 答不出停档 |
|----|------|----------|--------|------------|
| L1 | 常见注册中心 | 是否懂组件 | etcd / consul / zookeeper | 答不出停档 |
| L2 | 心跳停了会怎样 | 是否懂摘除 | 标记不可用、超时删除 | 答不出停档 |
| L3 | 客户端 vs 服务端 LB | 是否懂两类 | 客户端缓存本地选、服务端侧代理 | 答不出停档 |
| L4 | 注册中心挂了 | 是否懂容错 | 客户端用缓存续跑、中心需高可用 | 答不出停档 |
| L5 | 一致性要求 | 是否懂 CP/AP | zookeeper/etcd 偏 CP、consul 可配 | 答不出停档 |

## 版本与兼容性
- etcd（Go 实现，k8s 背后底座）、consul、zookeeper 长期作为注册中心；gRPC 生态常用 consul/etcd + resolver 插件。
- 健康检查/心跳间隔、摘除超时各框架可配。

## 关键代码
```go
// Go 用 consul 注册实例（go-micro/consul 客户端示意）
reg := consul.NewRegistry()
// 启动时注册
_ = reg.Register(&registry.Node{Id: "user-1", Address: "10.0.0.1:8001"})
// 定期心跳由 sdk 内部 TTL 续约；停发则 consul 标记 failing 并摘除
// 发现时客户端按本地缓存 LB 选节点
nodes, _ := reg.GetService("user")
_ = nodes
```

## 总结与追问预判
- 口诀：**注册中心存实例 → 注册+心跳保活 → 发现+客户端LB选节点 → 缓存减负**。
- 预判追问："不用注册中心行不行？"答：小集群可硬编码/DNS，但规模上来必须注册发现，否则无法动态扩缩容。
