# 804 编译前端：AST 与类型检查

> 分类：工程化与编译 | 难度：L2 | 题型：原理题 | 频率：中 | 关键词：**AST** / **类型检查** / **types2**
> 原文锚点：第 2~9 段「语法分析构建抽象语法树…类型检查识别节点类型并推断」

## 一句话总述
前端把文本变成带类型的 AST：词法+语法分析产出 AST（只查括号/操作符匹配），类型检查遍历 AST 推断并校验类型，二者都架构无关。

## 面试官视角
- 意图：是否分得清"语法正确"和"类型正确"，知类型推断发生在编译期。
- P5 知前端概念 / P6 说清 AST 与类型检查分工 / P7 知类型信息存于 `types2`、推断在编译期完成。
- 红旗：以为类型错误能在语法分析阶段发现；以为 `x:=1` 运行时才定类型。
- 惊艳点：未声明类型的 `x := 1` 在类型检查阶段由编译器推断为 int，不是运行时 —— 验证 `go/types` 推断逻辑 `[源码]`。

## 主问答
**Q（面试官原话）：** 编译前期都在干什么？语法分析和类型检查是一回事吗？
**A：**
1. **结论**：语法分析只检查"写得合法不合法"（括号/操作符匹配），类型检查才给每个节点判定类型并可推断（如 `x:=1`→int）`[源码]`。
2. **机制**：`syntax` 包解析出 AST 后，`noder` 转成 `ir` 并借 `types2` 遍历节点做类型校验与推断，`x:=1` 这类短变量声明在此定类型 `[源码]`。
3. **边界**：语法分析查不出"把字符串传给 int 参数"这类错，那属于类型检查；类型信息随 AST 保留供后端使用。
**加分层：** 前端产物与 CPU 架构无关，是"一次编写"能被多后端复用的关键。
