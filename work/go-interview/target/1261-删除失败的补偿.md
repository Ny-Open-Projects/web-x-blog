# 1261 删除失败的补偿：重试、MQ 异步、订阅 binlog

> 分类：缓存 / Redis | 难度：L4 | 题型：方案题 | 频率：高 | 关键词：**删除失败、重试、消息队列、binlog、Canal、过期时间兜底**

> 原文锚点：第 68~86 段「一旦缓存删除失败，缓存和数据库的数据还是会发生不一致的问题…数据库一旦更新成功，我们就需要尽可能的确保缓存也删除成功…通常最简单有效的方案就是重试…另一种方案就是将重试的动作与当前处理流程解耦，更新完 DB 之后就删除缓存，如果删除失败就往消息队列里面发送一条消息，然后在消费端进行指定次数的删除重试…还有一种更优雅的做法就是订阅 binlog 进行异步删除…Canal 中间件可以模拟 MySQL 主从复制的交互协议，把自己伪装成一个 MySQL 的从节点，向 MySQL 的主节点发送 dump 请求…给缓存设计一个较短的过期时间」

## 一句话总述
数据库更新成功就必须确保缓存删除成功：可用**同步重试**（简单但耗时）、**MQ 异步重试**（解耦）、或**订阅 binlog 异步删除**（最优雅、耦合最低）；最后用**较短的缓存过期时间**做一致性兜底。

## 面试官视角
P6 会说「失败了重试」；P7 要给出**三级方案与取舍**，并能讲清 Canal 的工作原理——**伪装成从节点、发 dump 请求、接收并解析 binlog**，这是区分是否真用过的关键。

## 主问答
**Q（面试官原话）：** 缓存删失败了怎么办？Canal 是怎么知道的？

1. **失败仍有不一致**：一旦**缓存删除失败**，缓存与数据库仍会不一致 `[源码]`。
2. **原则**：数据库更新失败可以不删缓存；但**数据库一旦更新成功，就需尽可能确保缓存也删除成功** `[源码]`。
3. **方案一 · 同步重试**：发现删除失败后设置一定重试次数进行重试，最简单有效 `[源码]`。
4. **重试的代价**：重试**会占用当前请求的时间** `[源码]`。
5. **方案二 · MQ 异步重试**：把重试与当前处理流程**解耦**——更新完数据库后删除缓存，失败则**往消息队列发送一条消息**，由消费端执行指定次数的删除重试 `[源码]`。
6. **不引入中间件也可行**：也可直接在业务代码中做**一定次数的删除重试** `[源码]`。
7. **方案三 · 订阅 binlog**：更优雅的做法，可**最大程度降低业务耦合度** `[源码]`。
8. **Canal 原理**：Canal 模拟 **MySQL 主从复制的交互协议**，把自己**伪装成从节点**，向主节点发送 **dump 请求**；主节点收到后推送 **binlog**，Canal 解析字节流转成结构化数据，订阅后即可执行删除 `[源码]`。
9. **下游形态**：下游可以是消息队列，也可以是处理删除缓存的业务代码 `[源码]`。
10. **兜底**：给缓存设置**较短的过期时间**，万一不一致，缓存过期后即可恢复正常 `[源码]`。

## 关键代码

// 方案一：同步重试（简单，但占用请求时间）
func delWithRetry(key string, max int) error {
	var err error
	for i := 0; i < max; i++ {
		if err = rdb.Del(ctx, key).Err(); err == nil {
			return nil
		}
		time.Sleep(time.Duration(i+1) * 100 * time.Millisecond)
	}
	return err
}

// 方案二：失败投递 MQ，消费端重试（与主流程解耦）
func updateThenDelWithMQ(id int64, age int) error {
	if err := db.Exec("UPDATE user SET age=? WHERE id=?", age, id).Error; err != nil {
		return err
	}
	if err := rdb.Del(ctx, cacheKey(id)).Err(); err != nil {
		// 删除失败 -> 投递消息，由消费端重试
		return mq.Publish("cache.del", cacheKey(id))
	}
	return nil
}

## 总结与追问预判
**三级方案按耦合度递进：同步重试 → MQ 异步 → binlog 订阅**。答题时务必补上「给缓存设置较短过期时间」这个兜底——它是所有方案失效后的最后一道防线。完整方案选型见同批 1261-cache-consistency.deep。
