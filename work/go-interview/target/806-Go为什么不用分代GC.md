# 806 Go 为什么不用分代 GC

> 分类：Go/运行时 | 难度：L3 | 题型：深度题 | 频率：中 | 关键词：**非分代** / **逃逸分析** / **tcmalloc** / **并发优先** / **分代假设**
> 原文锚点：第 48~67 段「Go 用追踪式变种：无分代+不整理+并发三色标记清除；为何不用分代：①逃逸分析把多数新生对象放栈、分代假设失效 ②tcmalloc 基本无碎片、整理无收益 ③Go 更关注并发执行而非减 STW」

## 一句话总述
Go 的 GC 是**无分代、不整理、并发**的三色标记清除，与 Java 的"分代+并发"不同。Go 不用分代有三个根因：**① 逃逸分析把多数短命对象放栈上**，分代假设（重点回收新生对象）失效；**② tcmalloc 分配器基本无碎片**，分代"整理解决碎片"的优势无收益；**③ Go 团队更关注让 GC 与用户代码并发执行**，而非单纯压低 STW。

## 面试官视角
- 意图：这是 GC 题的**高阶追问**——"既然分代 GC 很成熟（Java 在用），Go 为什么不用？"考察对 Go 设计取舍的理解深度。
- P6 能说出"逃逸分析让新生对象在栈上"这一主因；P7 能完整讲出三个根因并区分"分代假设失效 / 无碎片收益 / 并发优先"。
- 红旗：以为 Go 用分代（Go 长期非分代）；把"不分代"说成缺陷（实际是权衡后的主动选择）。
- 惊艳点：点出"分代假设的核心是回收短命对象，而 Go 的短命对象根本进不了堆（在栈上随函数返回直接回收）"，逻辑闭环。

## 主问答
**Q（面试官原话）：** Java 用分代 GC 很成熟了，Go 为什么不用？
**A：**
1. **结论**：Go 的 GC 是**无分代、非移动（不整理）、并发**的三色标记清除。不用分代是三个根因叠加的主动取舍，不是能力缺失。
2. **根因①：逃逸分析让分代假设失效**。分代 GC 依赖"**分代假设**"——多数新对象存活时间短、应重点回收。但 Go 编译器通过**逃逸分析**把大多数新生对象分配在**栈上**，函数返回时栈随之一并回收，**根本不进堆、无需 GC 参与**。于是分代假设瞄着的"堆里的短命对象"在 Go 里大量不存在，分代优势直接打折。
3. **根因②：tcmalloc 基本无碎片，整理无收益**。分代 GC 的一大卖点是"整理消除碎片、允许顺序分配器"。但 Go 运行时用 **tcmalloc** 风格分配器，**基本不产生内存碎片**，且顺序分配器在多线程下并不适用；对对象做"整理搬移"反而无实质性能提升，还破坏指针稳定性（Go 的并发三色标记依赖指针不变）。
4. **根因③：并发优先于压 STW**。Go 团队的核心目标是**让 GC 与用户代码并发执行**，使 STW 时间与对象数量/大小解耦；分代 GC 在"减少 STW"上的边际收益对 Go 不明显，团队更聚焦"用适当 CPU 并发回收"这一单一目标 `[经验]`。

## 关键代码
```go
// 逃逸分析：多数新生对象留在栈上，函数返回直接回收，根本不进堆
func localSum() int { // 不返回指针 → a,b 留在栈上
    a, b := 1, 2
    return a + b // 函数返回，栈帧回收，无 GC 参与
}
func newPoint() *Point { // 返回指针 → p 逃逸到堆，才需 GC
    p := &Point{x: 1}
    return p
}
// 验证逃逸：go build -gcflags="-m" 可见 "escapes to heap" 提示
// 这正是"分代假设"在 Go 中失效的根：短命对象大多在栈，不进堆
```

## 总结与追问预判
- Go 非分代三因：逃逸分析放栈（分代假设失效）/ tcmalloc 无碎片（整理无益）/ 并发优先（STW 与对象解耦）。
