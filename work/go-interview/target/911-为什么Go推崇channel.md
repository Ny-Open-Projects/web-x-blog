# 911 为什么 Go 推崇 channel：CSP 模型与设计取舍

> 分类：Go 并发 | 难度：L2 | 题型：设计题 | 频率：中 | 关键词：**CSP**/**通信顺序进程**/**不要通过共享内存通信**/**通过通信共享内存**/**适用边界**

> 原文锚点：第 34~35、40 段「CSP 模型 / 通过通信共享内存」

## 一句话总述
Go 的并发哲学来自 **CSP（Communicating Sequential Processes，通信顺序进程）**：**「不要通过共享内存来通信，而要通过通信来共享内存」**——用 channel 在协程间传递数据所有权，而非让多协程抢同一块共享内存。这能把大型高并发程序的并发控制从「锁的泥潭」简化为「数据流向」。

## 面试官视角
这题考设计观，不是背语法。能背出那句 CSP 名言、讲清「channel 传的是所有权而非共享引用」、再落到「何时该用 / 不该用」的取舍，就是合格；只说「channel 安全」不算数。

## 主问答
**Q（面试官原话）：** 为什么 Go 推荐用 channel 做并发？

1. **CSP 名言**：Rob Pike 的「Do not communicate by sharing memory; instead, share memory by communicating」——核心是把「共享内存 + 锁」换成「传递数据 + channel」。
2. **传所有权而非共享**：channel 发送会**复制值**（见 911.md`），接收方拿到独立副本，从根本上规避了多协程同时改同一块内存的数据竞争。
3. **简化大型并发程序**：协程间靠 channel 串联成流水线（扇入/扇出、worker pool），控制流就是数据流，比散落各处的锁更易推理与测试。
4. **性能并非更优**：channel 每次收发都加 hchan.lock + 可能 gopark/goready 调度（见 609.md`），高频计数器 / 标志位 / 状态机用 `atomic` / `sync.Mutex` 更轻——**channel 不是万能锁**。
5. **适用边界**：适合「传递数据所有权、协调生命周期、流水线」；不适合「高频无结构共享状态」——后者用原子/锁更合适，呼应 609 的取舍结论。

## 版本与兼容性
| 维度 | channel | mutex/atomic |
|------|---------|--------------|
| 语义 | 传数据所有权 | 保护共享内存 |
| 适用 | 流水线/生命周期/协调 | 高频计数/状态/标志 |
| 成本 | 加锁+可能调度 | 原子更轻、锁中等 |

## 关键代码
```go
// CSP 风格：用 channel 传递任务所有权，而非共享一个 slice + mutex
jobs := make(chan int, 10)
go func() {
    for i := 0; i < 5; i++ {
        jobs <- i // 传递的是值副本，接收方独占
    }
    close(jobs)
}()
for j := range jobs { // 接收方拿独立副本，无数据竞争
    _ = j
}
```

## 总结与追问预判
核心：**CSP = 通过通信共享内存；channel 传所有权、简化数据流，但非性能最优、不适合高频共享状态**。追问拐向「channel 底层」——备好「hchan 三队列 + 锁」（见 609.md` / `609-channel-concurrency-lock.md`）。
