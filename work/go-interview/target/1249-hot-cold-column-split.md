> 原文锚点：第 15~16 段「那第六个优化点呢，就是表字段的动静分离…某些列的数据更新特别频繁…将这些数据列拆分出来，存储到单独的表当中…导致数据列的缓存失效，从而呢影响页缓存的命中率」（高频更新列垂直拆分，避免原表页缓存命中率下降）

## 一句话总述
「动静分离」是**表结构层**的 SQL 优化：把更新极频繁的「热列」（如 status、计数）从大表中**垂直拆分**到独立表，避免这些列的频繁变更不断使原表数据页失效，拖垮 buffer pool 命中率、连累其他查询回磁盘。

## 面试官视角
这题考「表结构设计」维度的优化意识，属于比「改 SQL / 加索引」更深一层。考点：① 为什么高频更新列会拖慢整张表（buffer pool 页失效）；② 拆分的做法与代价（多一次 join）；③ 与「分库分表」「覆盖索引」的层级关系。能说出「热列更新导致相邻冷列所在的页被反复刷出缓冲池」，是 DBA 向高阶信号。

## 主问答
**Q（面试官原话）：** 什么是表的动静分离？为什么高频更新的列要拆出去？

**A：**
1. **问题根源：热列更新拖垮缓冲池命中率**。InnoDB 以「页」为单位缓存数据（默认 16KB）。若某列频繁 UPDATE，它所在的页会被不断标记为脏、刷出、再读入；而**同页内的其他冷列也被迫跟着失效**——哪怕那些冷列根本没变。结果是 buffer pool 命中率下降，本可内存命中查询被迫回磁盘。
2. **解法：垂直拆分热列到独立表**。把高频更新列（status/计数器/最后活跃时间）拆到一张「热表」，原表只留稳定冷列。热列的更新只影响热表自己的页，原表冷数据页长期稳定驻留 buffer pool，命中率回升。
3. **代价与取舍**：读取时需要 `JOIN` 热表（或冗余到查询缓存），写热列不再惊动冷表。适合「热列更新频率 ≫ 冷列、且冷列被广读」的场景；若热列冷列总一起读，拆分反而增加 join 成本，需权衡。
4. **与覆盖索引互补**：动静分离解决「页缓存失效」，覆盖索引解决「回表 IO」，二者在不同层；高频更新的列本就不该进联合索引（否则每次更新都改索引页，见 1247.md`），拆分后热列独立，索引维护成本也降。

## 版本与兼容性
- 依赖 InnoDB buffer pool 机制（默认 16KB 页、`innodb_buffer_pool_size` 控制），该优化对所有 InnoDB 版本通用。
- 垂直拆分常与**读写分离 / 冷热数据分层存储**（见 199.md`）配合：热表放高性能存储、冷表放大容量存储。
- 注意区分：本卡是「**列**级垂直拆分」；「分库分表」（见 1249.md`）是「**行**级水平拆分」，二者维度不同、可叠加。

## 总结与追问预判
收口：**动静分离 = 热列垂直拆表，切断「热列更新 → 同页冷列缓存失效 → 命中率下降」的连锁**。预判追问：① 更底层的并发限制（SMO/分库分表，`1249-smo-sharding.md`）；② 单 SQL 降本（小表驱动，`1249-small-table-drive.md`）；③ 覆盖索引边界（`1247`/`1239`）。回答时强调「以页为单位的缓冲池失效」这一机制，比说「减少 IO」更精确。

## ⚠️ 原文纠错
源视频转写将缓存失效 / buffer pool / 页缓存 / 垂直拆分 等音译为崩坏词（如「数据列的缓存失效」「页缓存的命中率」表述保留但「频繁变更导致失效」机制被音译模糊），本卡已还原为规范术语（缓冲池 buffer pool 页失效 / 垂直拆分 / 冷热列）。交付卡禁止保留任何原词崩坏写法。

> **[经验]** 动静分离与「覆盖索引」是**两层**优化：前者解决「热列更新把冷列所在缓冲页刷掉」（缓存层），后者解决「查询要回表读聚簇索引」（IO 层）。面试中若被问「高频更新列该不该进联合索引」，标准答是**不该**——否则每次更新都改索引页，动静分离白做。这条常被忽略。

```sql
-- 原表：热列 status 频繁更新，拖累冷列所在的缓冲页
CREATE TABLE task (
  id BIGINT PRIMARY KEY,
  deleted TINYINT,
  status TINYINT,        -- 热列：频繁变更
  txttype TINYINT,
  name VARCHAR(255)      -- 冷列：被广读但很少变
);

-- 动静分离：热列拆到独立热表
CREATE TABLE task_hot (
  id BIGINT PRIMARY KEY,
  status TINYINT,        -- 只热列
  updated_at DATETIME
);
-- 冷表 task 只留冷列；热列更新不再惊动 task 的缓冲页
-- 读取时按需 JOIN（或冗余到缓存）
SELECT t.id, t.name, h.status
FROM task t LEFT JOIN task_hot h ON h.id = t.id WHERE t.deleted = 0;
```
