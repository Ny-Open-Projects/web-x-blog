# 916 无序性的运行时机制与有序替代方案深挖

> 覆盖源 9-16 的机制延伸：range 随机起点在 runtime 里的实现位置、哈希种子防 DoS 的因果链、小 map「碰巧相同」的概率解释、需要确定顺序时的结构选型。主卡已给三层原因，本附录做机制与替代深挖。

## 思路与架构

```text
一次 range 遍历的随机化全链 (runtime/map.go)
├─ range 编译为 mapiterinit
│   ├─ r.h = 遍历的 map
│   ├─ r.startBucket = fastrand() % 桶数  <- 随机起点
│   └─ r.offset = fastrand() & (桶内槽数-1) <- 桶内随机偏移
├─ 遍历顺序: startBucket 起, (i+offset)%8 定桶内首个
│   ├─ 目的1: 防止「碰巧有序」被写成依赖
│   └─ 目的2: 均摊遍历成本 (不总是第一个桶挨罚)
├─ 哈希种子 (1.2+)
│   ├─ 进程级伪随机, 同键跨进程/跨机器落桶不同
│   └─ 防哈希碰撞 DoS (攻击者无法预测分布)
└─ 扩容期: 遍历要同时扫新旧桶, 位置动态迁移
```

## 方案取舍
- **随机化是「对开发者的保护」**：没有遍历随机化时，顺序虽无契约但「实测稳定」，早期没问题、换版本/换数据量后悄然漂移——这类 bug 的排查成本远大于习惯成本。Go 把「不能依赖」升级为「必然不满足」，把问题前移到第一次测试。**在 API 设计里，宁可不满足也不给隐性契约**——这一设计哲学与 map 遍历、goroutine 调度顺序一脉相承 [经验]。
- **小 map「碰巧相同」的概率账**：[实测] 3 键单桶 map，同一进程内三次遍历连续输出相同（如 312,312）——桶内随机偏移只有 8 种取值，3 个元素可现排列有限，连续相同的概率不可忽略。**反过来说明规范为什么强调「不保证顺序」而非「保证无序」**——「每次必不同」其实也是保证不了的，规范只承诺「不保证有序」，一切巧合都不可依赖 [实测]。
- **需要确定顺序时的三个替代**：① **键切片排序**（主卡方案）——通用但 O(n log n)+O(n) 内存；② **顺序敏感场景直接用切片**——搜索结果类数据天然有序列表，map 只做索引（id→item），输出走切片，O(1) 追加；③ **有序 map 需求**——Go 没有内置，可用「map+双向链表」（LRU 结构，见 `711-pool-task-queue.md` 的池化思路）或排序键前缀。**结构选型优于事后排序**——输出顺序是需求时就别把数据纯存 map [经验]。
- **防 DoS 因果链**：哈希种子随机化前，攻击者可离线构造大量碰撞键让 map 退化为链表（CPU 100%）；1.2+ 进程级随机种子使碰撞集无法预构造。这也是标准库**不接受自定义哈希**的原因之一——开放哈希函数等于重开 DoS 大门，要自定义哈希就用自己的 map 封装 [经验]。

## 答题技巧
- 先分两层答：「存放无序（哈希定位）」+「遍历不确定（随机起点，故意的）」——分层本身就是得分点 [经验]。
- 用 [实测] 说话：跨进程 123 vs 312、同进程小概率连排相同——顺手把「规范只说不保证有序」带出来 [实测]。
- 被问「怎么有序」→ 先反问是「输出有序」还是「维护有序」，前者键切片排序、后者换结构——结构选型优于事后排序 [经验]。
- 被问「为什么故意随机」→ 报防脆弱代码 + 均摊遍历 + 防 DoS 三重动机，落到「不给隐性契约」的设计哲学 [经验]。
- 主动边界到 `916-map-key-unordered`（三层原因主线）、`915-map-growth`/`915-map-growth-internals.deep`（渐进迁移全景）、`914-map-hmap-bmap`（桶结构）、`510-comparison-rules.deep`（map 键类型约束），构成「map 底层」专题 [边界]。
