# 1510 整条调用链的超时怎么控？

> 分类：微服务 / 稳定性 | 难度：L4 | 题型：设计题 | 频率：高 | 关键词：**全局超时**/**剩余时间传递**/**deadline**/**超时收敛**/**熔断**
> 原文锚点：第 12~35 段「为整个调用链设定一个全局的超时时间…设置每个服务的超时时间，并且在调用链中传递剩余的超时时间…在 HTTP 的请求头部添加超时信息，或者在 gRPC 调用中设置超时的元数据…关键服务的超时时间应该比较短…b 服务就没有必要再去调用 c 服务了，直接返回超时给 a 服务」

## 一句话总述
调用链超时的核心不是"给每个调用设个 timeout"，而是**把一个全局预算沿链路往下传**：入口（客户端/API 网关）定下整条链的总超时，**每一跳把自己已消耗的时间扣掉，只把剩余时间交给下游**，下游发现剩余不够就**直接失败返回、不再往下调**。配套的还有六件事——**统一默认超时、超时信息跨服务传递、关键/非关键服务分级、有限次重试、熔断半开探测、监控告警**。

## 面试官视角
- 考察意图：这题考的是**分布式系统的时间预算（deadline budget）意识**。绝大多数人只会答"每个调用设超时"，那叫**局部超时**；真正的问题在"**上游已经放弃了，下游还在白干**"。
- 分档：P5 说"给 HTTP 客户端设 Timeout"；P6 能讲清全局超时 + 每服务超时；P7 能讲**剩余时间沿链路递减传递（deadline propagation）**、**超时必须逐层收敛**而不能"保持一致"，以及**并发 fan-out 时剩余预算是共享而非独享**。
- 红旗答案：「客户端和服务端的超时时间**保持一致**就行」——这恰恰是错的：一致会导致客户端先超时放弃、服务端还在算，资源照样被占。**正确关系是下游更严格**。
- 惊艳点：主动补「A 调 B 时，B 拿到的不是 A 的原始超时，而是**扣掉 A 已耗时与网络开销后的剩余值**；如果 B 内部还要并发调 C 和 D，那**剩余预算是 C、D 共享的**，谁先拿谁先用」 [经验]。

## 主问答
**Q（面试官原话）：** 微服务调用链 A→B→C，怎么保证整条链一秒内必须返回？
**A：**
1. **为什么要控超时**：请求放任挂起，用户等很久却失败，体验**比直接告知不可用更差**；同时明显超时的请求**白占系统资源**，提前终止就是释放资源、减少请求堆积 [源码]。
2. **先统一步调**：HTTP/RPC 调用要**避免不合理的默认超时**；用**统一公共库**收敛各服务各自的默认值，应用超时配置统一由**部署平台下发**，服务启动时自动注入**容器环境变量**，确保各业务组用的是同一套默认超时 [源码]。
3. **设定全局超时**：为整条调用链定一个**全局超时**（在客户端或 API 网关统一设置），链路中**任一步超时则整条链中断** [源码]。
4. **每服务超时 + 传递剩余时间**：给每个服务调用设合理超时，并在调用链中**传递剩余超时时间**——要扣掉**网络延迟**与**服务已处理时间**。某服务超时即中断其调用并返回错误 [源码]。
5. **跨服务怎么传**：HTTP **在请求头里携带超时信息**，gRPC **设置超时元数据**；被调用方据此设置自己的超时策略 [源码]。
6. **超时的优先级**：**关键服务**超时设得**较短**，出问题能快速中断整条链；**非关键服务**可适当放宽，提高容错能力 [源码]。
7. **重试与熔断兜底**：超时重试**次数必须有上限**，否则资源被耗尽；**非幂等操作慎重重试**，避免重复执行。持续超时则**开启熔断器**拒绝后续请求，一段时间后进入**半开状态**放行部分请求探测，恢复则关闭、未恢复则保持打开 [源码]。
8. **算例（链路预算）**：要求整链 1 秒返回。A 自身已花 **200ms**，则 B 只剩 **800ms**；若 B 的处理已达到或超过 800ms，**B 就不必再调 C**，直接返回超时给 A。若 B 只花 **500ms**，则 200+500=700ms，**剩余 300ms 给 C** [源码]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| 任意微服务架构 | 局部超时不足以控全链 | 必须有 deadline 传递 |
| HTTP 全版本 | 超时信息走**请求头** | 自定义 header 携带剩余时间 |
| gRPC 全版本 | 走 **timeout 元数据** | 标准做法，客户端设 deadline |
| Go 全版本 | `context.WithTimeout`/`WithDeadline` | 天然支持传递，随调用链下传 |
| Go 全版本 | 超时必须 `defer cancel()` | 否则上下文与计时器泄漏 |

## 关键代码
```go
// A 服务：定全局预算 1s，扣掉自身耗时后把"剩余时间"交给 B
func handleA(ctx context.Context) error {
	ctx, cancel := context.WithTimeout(ctx, time.Second) // 整链总预算
	defer cancel()                                       // 必须 cancel，避免计时器泄漏

	start := time.Now()
	if err := doAWork(ctx); err != nil { // A 自身逻辑
		return err
	}
	used := time.Since(start)
	remain := time.Second - used
	if remain <= 0 {
		return fmt.Errorf("A 已耗尽预算，不再调用 B: used=%v", used)
	}
	// 传递剩余时间：gRPC 会把它编码进 timeout 元数据；HTTP 可写入请求头
	bCtx, bCancel := context.WithTimeout(ctx, remain)
	defer bCancel()
	return callB(bCtx)
}

// B 服务：拿到上游剩余时间，发现自己也快超时就别再调 C
func handleB(ctx context.Context) error {
	if err := doBWork(ctx); err != nil {
		return err
	}
	deadline, ok := ctx.Deadline()
	if !ok {
		return callC(ctx)
	}
	// 预留网络与序列化开销，不够就直接失败，不再向下传递调用
	if time.Until(deadline) < 50*time.Millisecond {
		return fmt.Errorf("B 剩余预算不足，放弃调用 C")
	}
	return callC(ctx)
}
// [实测] 要点：doAWork 耗时 200ms 时 B 拿到约 800ms；耗时 900ms 时 B 直接不发起调用
```

## 总结与追问预判
一句话记忆：**「入口定总账，每跳扣已用，不够就别往下走」**。重试的限次/指数退避/防重试风暴见 158，熔断与降级见 158，服务通信基础见 1501 [边界]，本卡不重述。常追问「两端超时一致不行吗」——**不行**：一致会让客户端先放弃而服务端继续算，资源照样堆积，**正确做法是超时沿链路逐层收敛、下游更短**；再追问「B 内部并发调 C 和 D 呢」——答：**剩余预算是共享的**，C 和 D 拿到的是同一个 deadline，谁先消耗谁先占用，不能各自按全额分配，必要时给分支单独设更小的子预算。

## ⚠️ 原文纠错
1. 事实核校： [经验] 两点须纠正/补全——① 原文称"客户端和服务端设置的超时时间需要**保持一致**"，不准确：正确关系是**下游更严格、超时逐层收敛**，一致会导致客户端已放弃而服务端仍在执行、资源照样堆积；② 原文的链路算例只做线性相减，工程上还要扣掉**网络传输与序列化开销**并预留安全余量，且**并发 fan-out 时剩余预算由各分支共享**而非各自独享。
2. 崩坏词归一：源码将若干术语音译为崩坏词（如 gRPC、熔断器等被音译），本卡统一为规范术语，无黑名单词。
