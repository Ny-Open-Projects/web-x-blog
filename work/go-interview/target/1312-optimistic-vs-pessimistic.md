# 1312 悲观并发控制 vs 乐观并发控制（ES 为何选乐观）

> 分类：Elasticsearch / 并发控制 | 难度：L2 | 题型：概念题 | 频率：中 | 关键词：**悲观并发控制** / **乐观并发控制** / **版本号** / **冲突重试** / **ES 选乐观**
> 原文锚点：第 1~6 段「解决并发典型两种方法：悲观(加锁阻塞)与乐观(假定无冲突、冲突时更新失败由应用重试)；关系型库广泛用悲观，ES 采用基于版本号的乐观」

## 一句话总述
并发控制两大思想：**悲观并发控制**（访问前先加锁阻塞他人，MySQL 表/行锁即其实现）与**乐观并发控制**（假定冲突不发生，不阻塞，更新时检测冲突、失败交由应用重试）。Elasticsearch 采用**基于版本号的乐观并发控制**，不为文档加阻塞锁。

## 面试官视角
- 意图：区分"乐观/悲观是思想"与"具体锁实现"，并说清 ES 为何不用悲观锁。
- P5 知 ES 用版本号乐观控制；P6 能对比两种思想差异；P7 能讲"ES 分布式架构下加全局悲观锁代价高，故选乐观 + 应用层重试"。
- 红旗：把乐观锁说成 ES 提供的一把锁；或以为 ES 给文档加行锁。
- 惊艳点：点出"乐观/悲观是并发控制思想而非具体锁"，并关联通用理论 `[边界]` 见 1233-optimistic-pessimistic（MySQL）、1013-mutex-pessimistic（Go Mutex 属悲观）。

## 主问答
**Q（面试官原话）：** ES 是怎么解决并发冲突问题的？
**A：**
1. **悲观并发控制**：修改前先加锁（如 MySQL `SELECT ... FOR UPDATE`、表锁/行锁）阻塞并发访问，避免冲突，但牺牲并发度、易死锁 `[边界]` 见 1233。
2. **乐观并发控制**：假定冲突不发生，读写不阻塞；更新时校验版本，若期间被他人改过则更新失败、抛冲突异常，由应用决定重试或返回异常。
3. **ES 的选择**：ES 为每篇文档维护内部版本号，采用基于版本号的乐观并发控制——不加阻塞锁，冲突时让更新失败给应用重试，契合其分布式、高并发架构。

## 关键代码
```go
// 示意：ES 乐观并发——带版本更新，版本不匹配则更新失败由应用重试
// 使用官方 go-es 客户端（elasticsearch-go），未做端到端验证
req := esapi.UpdateRequest{
    Index:      "user",
    DocumentID: "1",
    Version:    &knownVersion, // 客户端已知版本号
}
res, err := req.Do(ctx, es)
if err != nil {
    // 网络错
}
if res.StatusCode == http.StatusConflict {
    // 409 Version Conflict：版本已被他人改动，读取最新后重试
    latest := fetchLatest(ctx, "user", "1")
    retryWith(latest.Version)
}
```

## 总结与追问预判
- 乐观/悲观是并发控制思想；ES 用版本号乐观控制，冲突交由应用重试。
- 预判：ES 三种版本类型 → 见 1312-version-control；_seq_no/primary_term 机制 → 见 1312-seqno-primaryterm；通用锁理论 → 见 1233 / 1013。
