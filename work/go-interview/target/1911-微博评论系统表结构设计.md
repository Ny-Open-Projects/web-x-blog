# 1911 微博评论系统表结构设计：把一张表拆成五张的三条硬理由

> 分类：数据库 / 表设计 | 难度：L3 | 题型：设计题 | 频率：高 | 关键词：**垂直拆分**/**评论主表**/**内容表**/**汇总表**/**楼层折叠**/**页缓存命中率**/**数据页密度**
> 原文锚点：第 1~13、22~27 段「首先第一张表是我们这个微博的评论表…我们将微博评论内容的这张表单独拆分出来了…第三张表是我们的一些汇总信息…我们将这些汇总数据和我们这个评论的主表进行了分离…表的数据读取之后会加载到操作系统的页缓存，而表数据的频繁更新会使得页缓存失效的概率变高，从而降低了缓存的命中率…让 MySQL 的一个数据页上可以缓存更多的数据行，而且大字段带来的大 IO 会拖慢评论和回复元数据的获取」
> [边界] 本文只讲**存储层的表结构垂直拆分**：整体架构（BFF 网关 / 削峰填谷 / 分区保序 / 预读异步化 / Cache-Aside）见 1910，计数器的缓存与 DB 方案见 1912，冷热列拆分的通用思路见 1249，均不重述。

## 一句话总述
微博评论系统把一张宽表**垂直拆成五张**——**评论主表 / 评论内容表 / 评论汇总表 / 回复表 / 回复内容表**。驱动拆分的不是"表太大"这种模糊理由，而是**三条可量化的硬理由**：① **查询频率**——评论列表是最高频查询，混表会引入额外过滤条件；② **页缓存命中率**——频繁更新的计数字段留在主表会让缓存页频繁失效；③ **数据页密度**——大字段挤占 16KB 数据页，一个页能装的行变少、单次 IO 变重。再配**楼层默认折叠 + 按 `parent_id` 按需加载**，规避递归查询与深度不可控的慢查。

## 面试官视角
- 考察意图：这是**"你会不会拆表"的试金石**。面试官不想听"分库分表"这种大词，他想听你**说出拆分的具体代价与收益**——尤其是**页缓存命中率**和**数据页密度**这两条，说出来就是分水岭。
- 分档：P5 只能说"一张表太大就拆"；P6 能说"冷热分离、大字段拆出去"；P7 能讲出**三条驱动理由各自对应哪张表**、**楼层折叠的真实动机是避免递归慢查**，以及**拆分带来的二次查询代价**。
- 红旗答案：「评论和回复本质都是评论，应该放一张表」——**这是源码里的原话，但它是被推翻的那个观点**。正确答案恰恰是拆开。
- 惊艳点：主动补「**统计字段不是'可以'拆，而是'必须'拆**——它每来一条回复就更新一次，留在主表会让主表所在的数据页在全集群的页缓存里反复失效，把最高频的评论列表查询一起拖垮」[经验]。

## 主问答
**Q（面试官原话）：** 高并发的微博评论系统，表结构你会怎么设计？为什么要把内容和主表分开？

**A：**
1. **第一张：评论主表（comment）**——存**主键 id、微博 id、发布评论的用户 id、评论状态、置顶状态、创建与更新时间**。因为评论列表是**按微博 id 取的**，所以**对微博 id 建索引** [经验]。
2. **第二张：评论内容表（comment_content）**——存**评论 id + 具体内容 + 创建更新时间**。拆出来的核心理由是**让 MySQL 的一个数据页能缓存更多的数据行**；大字段留在主表会带来**大 IO**，拖慢评论元数据的获取 [经验]。
3. **第三张：评论汇总表（summary / count）**——存**当前评论下第一楼层的回复数量**、**所有楼层的回复总数**这类统计值。拆出来的理由是**表数据会被加载进操作系统页缓存**，而**频繁更新会让页缓存失效概率变高、命中率下降**；把这些高频更新字段挪走，主表的缓存就稳了 [经验]。
4. **第四张：回复表（reply）**——回复之间**有嵌套层级**：用户 A 发评论、B 回复 A、C 又回复 B。虽然"评论的回复"和"评论"本质上都是评论，但业务上**打开评论页先展示的是评论列表**，查询频率最高的就是它；混在一张表里会让查询逻辑变复杂、需要额外过滤条件 [经验]。
5. **第五张：回复内容表（reply_content）**——内容同样**单独一张表**存储，理由与评论内容表一致（数据页密度 + 大 IO）[经验]。
6. **楼层为什么要折叠**：如果一次性加载所有楼层，就需要**递归查询**；**楼层深度不可控会直接导致慢查**。所以**默认折叠、只展示指定数量的楼层**，用户点击才被动加载下一层——这既兼顾体验，又规避了性能问题 [经验]。
7. **读取流程（拆表的代价在这里）**：先按**微博 id + 分页**查出评论的**元数据**；再用这批分页得到的**评论 id 作为 `IN` 条件**去内容表批量取内容；楼层回复则按 **`parent_id` 过滤**出当前楼层的回复列表，内容再去回复内容表取 [经验]。
8. **长远演进**：评论与回复的**内容**其实更适合放 **KV 数据库**——它是纯 KV 形态、没有复杂查询需求、数据量又最大 [经验]。

## 版本与兼容性

## 关键代码
```sql
-- ① 评论主表：只存元数据，按微博 id 建索引支撑最高频的列表查询
CREATE TABLE comment (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  weibo_id    BIGINT UNSIGNED NOT NULL COMMENT '微博 id',
  user_id     BIGINT UNSIGNED NOT NULL COMMENT '发布评论的用户 id',
  status      TINYINT      NOT NULL DEFAULT 0 COMMENT '评论状态',
  top_flag    TINYINT      NOT NULL DEFAULT 0 COMMENT '置顶状态',
  created_at  DATETIME     NOT NULL,
  updated_at  DATETIME     NOT NULL,
  PRIMARY KEY (id),
  KEY idx_weibo (weibo_id)          -- 评论列表按微博 id 获取
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ② 评论内容表：大字段独立，提高主表数据页的行密度
CREATE TABLE comment_content (
  comment_id  BIGINT UNSIGNED NOT NULL,
  content     TEXT NOT NULL,
  created_at  DATETIME NOT NULL,
  updated_at  DATETIME NOT NULL,
  PRIMARY KEY (comment_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ③ 评论汇总表：高频更新的统计值独立，避免拖垮主表页缓存命中率
CREATE TABLE comment_summary (
  comment_id     BIGINT UNSIGNED NOT NULL,
  first_floor_cnt INT NOT NULL DEFAULT 0 COMMENT '第一楼层回复数',
  total_reply_cnt INT NOT NULL DEFAULT 0 COMMENT '所有楼层回复总数',
  PRIMARY KEY (comment_id)
) ENGINE=InnoDB;

-- ④ 回复表：parent_id 表达嵌套层级，折叠时按层加载
CREATE TABLE reply (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  comment_id  BIGINT UNSIGNED NOT NULL,
  parent_id   BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '上一层回复 id，0 表示直接回复评论',
  user_id     BIGINT UNSIGNED NOT NULL,
  created_at  DATETIME NOT NULL,
  PRIMARY KEY (id),
  KEY idx_comment_parent (comment_id, parent_id)  -- 按指定楼层取回复
) ENGINE=InnoDB;

-- ⑤ 读取流程：先分页拿元数据，再用 id 集合回查内容（拆表的二次查询代价）
SELECT id, user_id, top_flag, created_at
FROM comment
WHERE weibo_id = ? AND status = 0
ORDER BY top_flag DESC, id DESC
LIMIT 10;

SELECT comment_id, content FROM comment_content WHERE comment_id IN (?, ?, ...);

SELECT id, user_id FROM reply WHERE comment_id = ? AND parent_id = ? LIMIT 20;
```

> 验证要点（`[经验]` 判据，非运行时输出）：① 主表不含 `TEXT` 字段，单行约几十字节，16KB 数据页可容纳数百行，列表查询的**页缓存效率**显著高于宽表；② 汇总表的 `total_reply_cnt` 每来一条回复就 `+1`，若放在 `comment` 主表，会让主表页持续变脏、缓存失效；③ `idx_comment_parent` 让"展开某一楼层"变成**一次索引范围扫描**，而不是对全表做递归；④ 拆表后取内容必须**二次回查**，这是"提高页密度"换来的代价，需用 `IN` 批量化把多次往返压成一次。

## 总结与追问预判
- 一句话收尾：**"高频的元数据留主表、高频更新的计数拆汇总表、大字段拆内容表、嵌套的回复拆楼层表"**——四句对应四张表，背下来就能画。
- 大概率被追的三问：① 拆这么多张表，一次查询是不是变慢了（是的，多了二次回查，但用 `IN` 批量化和缓存抵消，换来的页缓存收益更大）；② 汇总数据能不能放 Redis（能，但要有 DB 兜底与对账，见 1912）；③ 楼层深度有没有上限（工程上必须**设上限 + 折叠**，否则递归深度不可控就是慢查源头）。
- 反向加分：主动指出**"评论和回复本质都是评论所以可以放一张表"这个直觉是错的**——**业务读取模式**（先看评论列表、按需展开楼层）才是拆表的依据，不是数据形态。

1. 源码先说评论与回复「本质上都属于评论，可以放一张表」又拆开，却**未给拆分判据**——本卡补三条 [经验]。
2. 源码称楼层折叠主要为体验——更关键的是**避免递归查询与深度不可控的慢查** [经验]。
3. 源码未提 **MySQL 数据页为 16KB**，大字段会显著压低单页行密度 [经验]。
4. 源码称统计信息「也可以在业务层合并」——不如拆表，异步合并会带来**短暂不一致** [经验]。
5. 源码未讲**取内容需二次查询**（先分页拿元数据再 `IN` 回查），这是拆表的代价 [经验]。
6. 源码未说明内容**长远应迁 KV 库**的理由：纯 KV 形态、无复杂查询、体量最大 [经验]。
