# 147 深挖：Kafka 写入与消费的完整链路及工程要点

> 分类：消息队列 / Kafka | 难度：L4 | 题型：综合题 | 频率：高 | 关键词：**分区、分区策略、写入链路、ISR、重平衡、位移存储、顺序性**

> 原文锚点：第 1~82 段「如果一个 topic 只对应一个文件，那么这个文件所在的机器 IO 就会成为这个 topic 的性能瓶颈…分区策略其实就是决定了生产者将消息发送到哪个分区的算法…新发送的消息会追加到当前活跃的日志分段…Kafka 使用了 ISR 列表来维护所有与主副本同步的追随者副本，只有已提交的消息才可以被消费者消费…消费者组中的某个 consumer 实例加入或者是退出…都会再次触发消费者的重平衡」

## 思路与架构

把 Kafka 的写入与消费串成**一条对称的链路**：

1. **为什么分区**：单文件会让**所在机器的 IO 成为整个 topic 的瓶颈**。分区使数据打散、读写按分区粒度进行、分区可分布到不同节点，从而提供**负载均衡**与**高伸缩性**；这与其他系统的分片（MongoDB / Elasticsearch）与 region（HBase）是同一思想。
2. **写哪里 —— 分区策略**：轮询最均匀；随机效果通常不如轮询；**哈希策略的价值不在均衡而在保序**——按业务 key 把同 ID 数据固定到同一分区，利用「分区内有序」满足订单等场景的顺序要求。支持自定义，实际轮询与哈希已覆盖绝大多数场景。
3. **怎么落盘 —— 写入链路**：producer 发送 → 按策略选分区 → 追加到该分区**唯一的活跃日志分段**（每段对应一个数据文件 + 一个索引文件）→ **先写操作系统内存缓冲区、再同步磁盘** → 同步副本 → broker 应答。高性能来自**顺序追加 + 页缓存 + 单活跃段**三件套。
4. **何时算成功 —— ISR**：全同步太慢、纯异步会丢数据，Kafka 用 **ISR 列表**折中：消息被 **ISR 内所有副本写入**才算**已提交**，**只有已提交才可被消费**；leader 故障由**控制器**从 ISR 中选新 leader。
5. **怎么消费 —— 消费链路**：订阅 → **重平衡**分配分区（实例进出或分区数变化都会触发）→ **按批次拉取**（先二分索引随机定位，后顺序批读）→ 处理 → **提交位移**并循环。工程上**实例数应等于分区数**，多则空转、少则变慢；位移从 **0.8 前的 ZooKeeper** 演进到 **0.9 起的 `__consumer_offsets` 内部 topic**。

## 方案取舍

| 决策点 | 方案 A | 方案 B | 取舍依据 |
|---|---|---|---|
| 分区策略 | 轮询 | 哈希 | 无顺序要求选轮询；需同 key 保序选哈希 |
| 分区数量 | 少（够用） | 多（高吞吐） | 分区只能增不能减，过多会增加句柄与同步开销 |
| 应答级别 | acks=1 | acks=all | 追求可靠选 all，配合 min.insync.replicas |
| 副本选举 | 仅 ISR 内选 | 允许非 ISR | 一致性优先则关闭 unclean 选举 |
| 消费实例数 | 等于分区数 | 多于/少于 | 多则空转、少则变慢，等于最优 |
| 位移存储 | ZooKeeper | 内部 topic | 0.9 起默认内部 topic，性能与可扩展性更好 |

取舍要点：**写入侧的核心矛盾是吞吐与可靠**（页缓存带来速度，副本 ISR 带来安全）；**消费侧的核心矛盾是并行度与重平衡成本**（分区数决定并行上限，实例变动会触发重平衡暂停消费）。

## 答题技巧

1. **先说「为什么」再说「怎么做」**：先讲单机 IO 瓶颈，自然引出分区，再讲策略与链路，逻辑最顺。
2. **把术语与语义配对**：ISR → 提交判定；控制器 → 选举；重平衡 → 分区分配；页缓存 → 写入性能。配对记忆不易混。
3. **主动点出顺序性边界**：Kafka 只保证**分区内有序**，且哈希保序**仅在分区数不变时成立**——这是区分真懂与背诵的分水岭。
4. **带版本号显功力**：0.8 前位移存 ZooKeeper、**0.9 起存 `__consumer_offsets`**，报得出版本号可信度立刻上升。
5. **止步档位**：能讲清分区目的与写入链路即达 L4；能完整讲出 ISR 提交语义、重平衡触发条件、位移存储演进并给出实例数匹配建议，即达 L5。

## 细节与核心 API

**对称链路关键配置：**

```go
// 写哪里——分区策略：轮询(均衡) / 哈希(保序)
config.Producer.Partitioner = sarama.NewHashPartitioner // 同 key 固定分区，利用分区内有序
// 何时成功——ISR：消息被 ISR 内所有副本写入才算已提交，才可被消费
// 怎么消费——实例数=分区数最优（多则空转、少则变慢）；位移 0.9+ 存 __consumer_offsets
```
```properties
acks=all                         # 追求可靠配合 min.insync.replicas
min.insync.replicas=2
unclean.leader.election.enable=false
```
