# 101 减少上下文切换的四类方法

> 分类：并发基础 | 难度：中 | 题型：方案题 | 频率：高 | 关键词：**减少锁、CAS、减少线程、协程、M:N 模型**

> 原文锚点：第 40~62 段「减少上下文切换的优化方式」

## 一句话总述
降低上下文切换有四类手段：**避免/减少锁**（数据分段）、**CAS 自旋**（免锁阻塞），**减少线程数**（任务粒度重排），**协程**（用户态 M:N 调度，单线程内多任务切换，免内核切换）。一句话背法：**「减切换四法：分段减锁 → CAS 免锁 → 减线程 → 协程用户态切换」**。

## 面试官视角
考官看你能不能从「减少切换」反推并发调优手段，是否覆盖锁/CAS/线程数/协程四个层次。能讲清"协程本质是把调度从内核搬到用户空间，一个线程当多个线程用"，说明有体系；只答「用多线程」——与减少切换背道而驰，是红旗。
- **P5**：知道减锁/减线程。
- **P6**：知道 CAS 自旋免锁阻塞。
- **P7**：知道协程 M:N、用户态切换更轻。

## 主问答
**Q（面试官原话）：** 有哪些方法可以减少上下文切换、提高执行效率？

**先铺垫（由浅入深第 1 层）**：上下文切换贵在"要陷入内核 + 缓存失效"。要减少它，思路就两条——要么少竞争（不让人等）、要么少用内核线程（把调度搬出内核）。四法就是从"规避竞争"到"用户态调度"层层递进。

1. **避免/减少锁（第 2 层）**：多线程竞争锁会触发切换；可用 ID 哈希取模分段（不同线程处理不同数据段）、整体更新 map 避免并发写、借鉴 `sync.Map` 的读写分离分散锁粒度，从源头规避竞争。
2. **CAS 算法（第 3 层）**：Compare-And-Swap 是原子操作，比较内存值与预期值，相等才替换，否则自旋重试；免锁保护共享资源，避免锁开销与线程阻塞。
3. **减少线程数（第 4 层）**：线程切换本身有开销，合理拆分/合并任务粒度，用更少线程完成相同工作，直接降低切换总次数。
4. **使用协程（第 5 层·最轻）**：goroutine 采用 M:N 模型，一个线程可绑多个协程，在用户空间完成上下文切换，避免用户态↔内核态切换；单线程内维持多任务调度，等效「一线程当多线程用」。
5. **误用风险（第 6 层）**：CAS 自旋在超竞争激烈时变"忙等"反而烧 CPU（见 1012 自旋锁），需权衡；分段不当会把数据倾斜到少数段重新引发竞争。

## 关键代码
```go
package main

import (
	"fmt"
	"sync"
)

// 数据分段：每个 worker 独占一段，规避锁竞争（减少切换）
func partitionDemo(ids []int, workers int) {
	chunks := make([][]int, workers)
	for _, id := range ids {
		chunks[id%workers] = append(chunks[id%workers], id) // 哈希取模分段
	}
	var wg sync.WaitGroup
	for w := 0; w < workers; w++ {
		wg.Add(1)
		go func(c []int) {
			defer wg.Done()
			// 每 worker 独占一段，无锁竞争 → 无锁等待切换
			_ = c
		}(chunks[w])
	}
	wg.Wait()
	fmt.Println("分段完成，无跨段锁竞争")
}

func main() {
	ids := make([]int, 1000)
	for i := range ids {
		ids[i] = i
	}
	partitionDemo(ids, 8)
}
```

## 总结与追问预判
**背这三句就够**：① **减锁：数据分段 / sync.Map 读写分离，从源头避竞争**；② **CAS：比较+交换原子操作，免锁阻塞但超竞争会变忙等**；③ **协程 M:N 把切换留在用户态，单线程当多线程用，最轻**。
**预判追问**：
- 「CAS 一直失败怎么办？」→ 自旋重试，但超竞争激烈时烧 CPU（见 1012 自旋锁 / 1014 Mutex）。
- 「sync.Map 怎么分散锁？」→ 读写分离 + 原子指针，读无锁（见 107 读写锁 map / 105 原子）。
- 「协程调度细节？」→ 见 815 GMP、1024 for死循环（用户态切换 vs 内核）。
