# 144 批量发送、数据压缩与横向扩展：Kafka 高吞吐的网络层与架构层

> 分类：消息中间件 / Kafka | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**批量发送、batch、linger.ms、batch.size、数据压缩、横向扩展、并行读写**

> 原文锚点：第 61~73 段「当我们调用 SDK 的 send 方法发送一条消息之后，无论是同步发送还是异步发送，Kafka 的 SDK 都不会立即把这条消息发送出去，而是会先把这条消息存放在内存的 batch 当中缓存起来，然后当这个消息达到我们参数配置的大小之后，或者是达到我们配置的时间之后，它才会把内存 batch 中的所有消息一次性地发给 broker，简单的说也就是攒一波一起发…在 Kafka 服务器上并不会把这一批消息再还原成多条消息一条一条地去处理，而是依然被当做是一批消息处理…把整个 batch 的数据一起压缩能更大幅度地减少数据量…通过增加更多的 Kafka 节点可以提高整个系统的吞吐量」

## 一句话总述
Kafka 高吞吐还有三条：**①批量发送**——`send` 后 SDK **不立即发送**，而是先攒进内存的 **batch**，**到达配置的大小或时间阈值后一次性发给 broker**；且**broker 端不会把批次拆开还原**，**写盘与副本同步的整个流程都以批次为单位处理**。**②数据压缩**——**重复数据越多压缩效果越好**，**整批一起压缩能更大幅度减少数据量**。**③分布式横向扩展**——**topic 分成多个分区、每个分区可独立读写**，有效分摊负载、提高并行度，配合多副本提升容错。

## 面试官视角
- 考察意图：能否讲清"批量"不只是客户端行为，而是**端到端贯穿的一条优化链**（攒批 → 网络 → 落盘 → 复制 → 压缩）。
- 分档：P5 知道有批量发送；P6 能说"攒够大小或时间再发"；P7 能补上 **broker 端不解批**、**批次与压缩的联动**（整批一起压效果更好）、以及**分区提供并行读写能力**。
- 红旗答案：以为 batch 只是客户端的事；或把"攒批"与"压缩"看成两个无关优化。
- 惊艳点：**broker 在整个处理流程中都不会把批次解开**——写入磁盘、复制到其他副本，始终当作**一条批消息**处理，这让批次的收益贯穿整条链路 `[源码]`。

## 主问答
**Q（面试官原话）：** 批量发送怎么提升吞吐？broker 端会拆开处理吗？

1. **结论**：SDK 攒批后一次性发送，**减少网络请求次数**；**broker 端不解批**，批次作为最小单位贯穿写盘与副本复制；同时**整批压缩**进一步减少数据量；再加上**分区独立读写带来的并行度** `[源码]`。
2. **批量 · 发送时机**：**调用 SDK 的 `send` 方法发送一条消息后，无论同步还是异步，SDK 都不会立即把这条消息发送出去**，而是**先把它存放在内存的 batch 当中缓存起来** `[源码]`。
3. **批量 · 触发条件**：**当消息达到参数配置的大小之后，或者达到配置的时间之后**，才会**把内存 batch 中的所有消息一次性发给 broker**——**简单说就是攒一波一起发** `[源码]`。
4. **批量 · 收益**：**通过将多条消息组成一个批次一次性发给 broker，可以减少网络请求的次数，提高网络传输的效率** `[源码]`。
5. **批量 · 端到端不拆包**：**消息批量化发给 Kafka 之后，在 Kafka 服务器上并不会把这一批消息再还原成多条消息一条一条地处理**，而是**依然被当做一批消息处理**；也就是说 **broker 在整个处理流程中，无论是写入磁盘，还是把这些消息复制到其他副本的过程中，批消息都不会被解开**，**始终当作一条批消息来处理** `[源码]`。
6. **压缩 · 为什么配批次**：**数据压缩的基本原理是重复数据越多，压缩效果越好**；因此**将整个 batch 的数据一起压缩，能更大幅度地减少数据量**，**从而更大程度地提高网络的传输效率** `[源码]`。
7. **分布式 · 横向扩展**：**Kafka 是一个分布式系统，可以横向扩展，通过增加更多的 Kafka 节点可以提高整个系统的吞吐量** `[源码]`。
8. **分布式 · 分区并行**：**Kafka 的 topic 可以分成多个分区，每个分区可以独立地进行数据的读写**，**这样可以有效地分摊系统的负载、提高并行处理的能力**；**同时支持多副本机制，可以充分利用分布式系统的容错能力，提高数据的可靠性和可用性** `[源码]`。

**加分层：** 一条完整的优化链——**攒批（省请求数）→ 整批压缩（省字节数）→ broker 不解批（省处理次数）→ 分区并行（省单机的串行瓶颈）**，四环相扣，任何一环掉了收益都会打折。

// Go 侧配置 Kafka 生产者：攒批 + 整批压缩
package main

import (
	"time"

	"github.com/segmentio/kafka-go"
)

func main() {
	w := &kafka.Writer{
		Addr:         kafka.TCP("broker1:9092", "broker2:9092"),
		Topic:        "order-events",
		Balancer:     &kafka.Hash{},       // 按 key 哈希选分区
		BatchSize:    100,                 // 攒够 100 条发一批
		BatchTimeout: 10 * time.Millisecond, // 或攒够 10ms 就发（两者先到先触发）
		Compression:  kafka.Snappy,        // 整批一起压缩，重复数据越多效果越好
		Async:        true,                // 异步发送不阻塞业务线程
		RequiredAcks: kafka.RequireAll,    // 配合多副本保障可靠性
	}
	defer w.Close()

## 总结与追问预判
**最爱追问的是"批次越大越好吗"**——**不是**：`batch.size` 与 `linger.ms` 是一对权衡，**批次越大延迟越高**（消息要在内存里等更久才发出），吞吐与延迟不可兼得；低延迟场景要把 `linger.ms` 调小甚至设为 0。追问常接"压缩选哪种"——**Snappy / LZ4 偏重速度，Gzip / ZSTD 偏重压缩比**；Kafka 默认不压缩，需在 producer 侧显式开启，且**压缩是在整批级别做的**，这也解释了为什么批次太小会把压缩收益吃掉。
