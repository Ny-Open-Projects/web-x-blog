# 1415 异步生产者三管道模型与关闭时序 深挖

> 覆盖源 14-15 全文：三种发送方式的语义与取舍、Go SDK 异步生产者的 `Input`/`Successes`/`Errors` 三管道、退出前必须 `AsyncClose` 的时序要求，以及 `max.in.flight.requests.per.connection`（默认 5）、`acks`、重试次数三个性能旋钮。主卡已给选型结论与可运行示例，本附录做「三管道为什么必须都消费」「AsyncClose 与 Close 的差别」「在途请求数与顺序性的关系」「同步何时反而更合适」四层深挖。

## 思路与架构

```text
AsyncProducer 内部
├─ Input()  chan<- *ProducerMessage   业务投递口(只写)
│     └─ 内部按 topic-partition 分桶攒批 → 后台批量提交
├─ Successes() <-chan *ProducerMessage 成功回执(需 Return.Successes=true)
├─ Errors()    <-chan *ProducerError   失败回执(需 Return.Errors=true)
└─ 关闭时序: AsyncClose() 触发排水 → 两结果管道被关闭 → 业务 Wait 返回
         Close() = AsyncClose() + 阻塞等到排空
```

## 方案取舍
- **为什么必须有结果管道**：异步化的代价是**调用点拿不到返回值**。若不消费 `Successes()`/`Errors()`，成功与失败都沉在管道里——失败消息**完全静默**，连一条日志都没有；管道写满后内部逻辑被堵住，异步退化成卡死。所以「开异步却不管结果管道」是最典型的误用 [经验]。
- **`AsyncClose()` vs `Close()`**：`AsyncClose()` 只**触发**关闭与排水，立即返回，你要自己继续读结果管道直到它们被关闭；`Close()` 等于「AsyncClose + 帮你等到排空」。生产程序想做优雅停机、需要先停流量再收尾的，用 `AsyncClose()` 配合 `WaitGroup`；短生命周期脚本用 `Close()` 更省心。**共同点**：都必须先关闭生产者，否则管道里已投递但未提交的消息会随进程退出而丢失 [经验]。
- **`max.in.flight.requests.per.connection` 的两面性**：它限的是**单条连接上已发出但还没收到响应的请求数**，默认 5。调大 → 链路利用率高、吞吐好；但一旦某个请求失败重发，后发请求可能先成功落盘，**同分区出现乱序**。因此严格保序场景要么把它压到 1（牺牲吞吐），要么开启幂等生产者（Kafka 0.11+），靠序列号在服务端去重重排，**在 5 的在途上限下依然保序** [经验]。
- **同步并不总是更慢**：异步的优势来自**攒批 + 管道并发**。如果业务是「投一条、等一条结果」的写法，异步的攒批窗口根本填不满，收益趋近于零，反而多了一层管道和两条 goroutine。批量导入、日志采集这类**允许攒批、允许微小丢失**的场景才是异步的主场 [经验]。
- **acks 与重试是延迟的另一半**：在途数决定「能同时飞多少」，而 `acks` 决定「每条要等多久才回」、重试次数决定「失败后还要再等多久」。三者共同构成发送延迟模型，只调其中一个很容易调出「吞吐上去了、P99 却炸了」的结果 [经验]。

## 答题技巧
- 被问「Go 里异步怎么写」直接报三管道：`Input()` 投递、`Successes()` 收成功、`Errors()` 收失败，并强调**后两个必须有人读** [经验]。
- 追问「退出时怎么保证不丢」→ 答「先 `AsyncClose()`，再继续排空两个结果管道，等它们关闭后才让进程退出」；只答「defer Close」只算半对 [经验]。
- 追问「在途数调大会怎样」→ 先答吞吐提升，立刻补**乱序风险**，再给「压到 1 或开幂等」两条解法，这是区分 P6 与 P7 的分水岭 [经验]。
- 反问式加分：主动说「如果业务要求强保序且不能容忍重试乱序，我会优先选同步 + 幂等，而不是硬上异步」 [经验]。
- 主动边界到 `1420-kafka-go-sdk`（sarama 与 confluent-kafka-go 选型）、`1420-producer-reconnect`（重连与幂等配置）、`1417-producer-acks`（acks 语义与副本数），构成生产者全链路 [边界]。
