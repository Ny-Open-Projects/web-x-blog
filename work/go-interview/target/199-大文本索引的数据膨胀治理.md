# 199 大文本索引的数据膨胀治理

> 分类：搜索引擎/ES 调优 | 难度：L3 | 题型：场景题 | 频率：中 | 关键词：**_source** / **best_compression** / **索引膨胀** / **僵尸用户淘汰**
> 原文锚点：第 8~24 段「大文本索引后存储膨胀比原文还大；开启 best_compression、关闭大字段 _source、按字数截断、淘汰长期不搜的用户」

## 一句话总述
大文本建索引后体量常比原文更大（term dictionary + doc_values + _source 三重开销），治理靠"压存储 + 限尺寸 + 淘冷数据"三板斧，本质是用确定的体验代价换集群可控。

## 面试官视角
- 意图：考察候选人对 ES 存储模型的真实理解，而非只会建索引。
- P5 知道 _source 可关、压缩可开；P6 能说清膨胀来源与字数截断的取舍；P7 能把"僵尸用户淘汰"抽象成 TTL 冷数据治理。
- 红旗：以为关 _source 只是省点空间；说不清为什么大文本索引膨胀比原文大。
- 惊艳点：指出"PB 级大文本几乎无法 reindex"，所以源头治理比事后抢救重要。

## 主问答
**Q（面试官原话）：** 大文本字段建索引后为什么存储反而比原文大？怎么治理？
**A：**
1. **结论**：索引后膨胀来自倒排索引（term dictionary/posting）、doc_values 正排、以及 _source 原文三部分叠加，大文本尤甚，治理用压缩 + 关 _source + 字数截断 + 淘冷。
2. **机制**：`index.codec: best_compression` 用 DEFLATE 压 posting，比默认 LZ4 更省；大文本字段设 `"_source": {"excludes":["content"]}` 不存原文；ingest 阶段按字数上限截断超大文档。
3. **边界**：以上都牺牲"取原文/高亮"能力，只对"只搜不取原文"的场景成立；长期不搜的用户数据按可配置 TTL（如 100 天）淘汰，再次搜索时重建索引 `[经验]`。

## 关键代码
```go
// 入库前按 rune 截断超大文本，避免单文档拖垮集群
func truncateText(s string, maxRune int) string {
    if utf8.RuneCountInString(s) <= maxRune {
        return s
    }
    rs := []rune(s)
    return string(rs[:maxRune])
}
```

## 总结与追问预判
- 大文本治理=压存储（压缩/_source）+ 限尺寸（截断）+ 淘冷（TTL）三层。
- 预判：高亮慢 → 见 199；写入忙 → 见 199。
