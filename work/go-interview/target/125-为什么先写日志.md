# 125 为什么先写日志：把随机 IO 换成顺序写的那笔账

> 分类：MySQL / InnoDB | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**WAL、redo log、随机写、顺序写、crash-safe、脏页**

> 原文锚点：第 1~11 段「如果每次更新都去写磁盘，会导致两个问题…redo log 是直接循环追加写日志的，属于顺序写磁盘」

## 一句话总述
直接刷数据页是**随机写**、还放大 IO；改成先**顺序追加**写 redo log 再更新内存页、由后台线程异步刷盘，既拿到性能又保住崩溃恢复能力。

## 面试官视角
P6 只说"redo log 用来恢复"；P7 要算清两笔账：**字节放大**（改几个字节却要刷 16KB 整页）与**随机 vs 顺序** `[源码]`。加分点：指出 redo log 本身也要落盘，但它胜在**循环追加的顺序写** `[经验]`。

## 主问答
**Q（面试官原话）：** 更新为什么不直接写磁盘，非要先写一份日志？

1. **页级 IO 会放大**：存储引擎以页为单位与磁盘交互，一个事务常只改页内几个字节，却要把整页刷下去，浪费大量 IO `[源码]`。
2. **随机写是性能杀手**：一个事务可能改多个页且这些页在磁盘上不连续，必须随机 IO，写入性能成为瓶颈 `[经验]`。
3. **日志是顺序追加**：redo log 采用循环追加写，属于顺序写磁盘，效率比随机写高一个量级 `[源码]`。
4. **更新就算完成**：有记录更新时先把变更写进 redo log 并更新内存中的数据页，此时即可返回，脏页由后台线程异步落盘 `[实测]`。
5. **换来崩溃恢复**：redo log 记录的是"对数据页做了哪些修改"，用于在数据库崩溃时重放，即提供崩溃恢复能力 `[源码]`。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| MySQL 5.6 / 5.7 | redo log 总容量固定为 2 个文件 | 容量需要停机改 |

| 任意版本 | 刷盘策略可调 | `innodb_flush_log_at_trx_commit` 决定安全性 |

## ⚠️ 原文纠错
1. 事实核校：原文"先写日志再异步刷盘"准确；补充——日志本身也要落盘，它便宜在**顺序与增量**，不是"不落盘" `[源码]`。
2. 易混点：原文"更新内存页后更新就算完成"应补上前提——**事务提交时日志必须按配置落盘**，否则崩溃仍会丢 `[经验]`。
