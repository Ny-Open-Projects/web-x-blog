# 148 重平衡的 STW 代价、参数治理与分配策略演进 深挖

> 覆盖源 14-8 全文：整组停止工作（STW）的代价量化与根因、Eager 协议的缺陷、心跳三层超时参数的正确设置、静态成员与增量协作重平衡两大治理手段、分配策略三代演进。主卡已给五步流程与角色分工，本附录做代价分析与治理方案四层深挖。

## 思路与架构

```text
重平衡 STW 的时间线 (Eager 协议)
├─ 触发: 成员离组(崩溃/心跳超时) 或入组(扩容/重启)
├─ Coordinator: Revoke -> 全员放弃现有分区 (STW 开始)
├─ 全员重新 JoinGroup (受 session.timeout.ms 约束)
├─ Leader 计算分配方案 (组越大越慢)
├─ SyncGroup 下发
└─ 全员恢复消费 (STW 结束)
治理三板斧
├─ 参数: session.timeout.ms / heartbeat.interval.ms / max.poll.interval.ms
├─ 静态成员: group.instance.id -> 重启不触发
└─ 增量协作: 只迁移受影响分区, 其余照常消费
```

## 方案取舍
- **STW 的根因是 Eager 协议的设计**：经典重平衡要求全员**先放弃所有已分配分区**（Revoke），再集体重新入组、重新分配——哪怕只有一个成员抖动，全组的正常消费也被打断。组规模越大（成员 N 多）、分区越多，方案计算与下发越慢，STW 越长。这是「一致性优先、可用性让路」的协议级取舍 [经验]。
- **三层超时参数是最常考的治理点**：① `session.timeout.ms`——心跳失联多久算死亡（默认 45s，旧版 10s），设太小会把 GC 停顿/网络抖动误判为死亡，频繁触发重平衡；② `heartbeat.interval.ms`——心跳间隔，惯例为 session 的 **1/3**（约 3 次机会）；③ `max.poll.interval.ms`——两次 poll 的最大间隔，处理逻辑太慢超过它会被踢出组。**误判三连**（频繁重平衡）九成出在这三个参数与业务处理耗时的错配上——先把单批处理耗时降下来，再谈调参 [经验]。
- **静态成员（KIP-345）是滚动发布的治本方案**：给消费者配 `group.instance.id`（稳定身份），Coordinator 按 ID 而非 session 识别成员——**应用重启后（Fencing 窗口内）旧 session 未超时则直接复用，不触发重平衡**。代价：同 ID 双活会被隔离（新实例接管时旧的被踢），要保证 ID 唯一（如 Pod 名） [经验]。
- **增量协作重平衡（KIP-429）改变 STW 的边界**：不再全量 Revoke——Coordinator 只回收「必须迁移」的分区，未受影响的分区**继续消费**；多轮增量收敛到稳态。从「整组停」变为「最小受影响面」，是延迟敏感业务升级消费端协议的直接理由。三代分配策略一并对比：**Range**（按 topic 逐个切，易倾斜）→ **RoundRobin**（全局轮转，更均匀但重平衡迁移多）→ **Sticky**（尽量保留原分配，减少分区迁移）——选型的核心指标从「均匀」进化到「迁移最小化」 [经验]。
- **Go SDK 的分区数坑是工程避雷点**：部分 Go 版 SDK 在**分区数动态增加**时不会自动触发重平衡，新分区无人消费——表现为「topic 明明有消息但部分分区 lag 持续增长」。规避：分区数尽量规划到位不动态扩；确需扩容时**滚动重启消费组**确认新分区分配到位（源文明确提醒这一点） [经验]。

## 答题技巧
- 主线答五步流程，随即主动抛 STW 代价：「整个过程中组内所有消费者停止工作」——从背流程跳到讲代价 [源码]。
- 被问「重平衡很慢怎么办」→ 按三板斧顺序：调心跳三层参数 → 静态成员止住重启触发 → 升级增量协作协议，层层递进 [经验]。
- 被问「参数怎么设」→ 报惯例值（heartbeat = session/3）+ 误判三连的场景（GC 停顿、批量处理超 max.poll），体现调过参 [经验]。
- 用「均匀 vs 迁移最小化」概括分配策略三代演进，一句话立住架构视野 [经验]。
- 主动边界到 `147-consumer-rebalance`（消费链路与实例数匹配）、`1417-producer-acks`（生产端可靠性，对应消费端位移动画）、`143-*`（分区内有序与拉取批次），构成 Kafka 全链 [边界]。
