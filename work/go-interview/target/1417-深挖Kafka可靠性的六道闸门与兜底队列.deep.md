# 1417 深挖：Kafka 可靠性的六道闸门与兜底队列

> 分类：消息中间件 / Kafka | 难度：L4 | 题型：架构题 | 频率：极高 | 关键词：**副本、acks、ISR、未同步选主、刷盘、位移提交、死信队列、重试队列**

> 原文锚点：第 1~70 段「哪些因素会影响到 Kafka 消息的可靠性…死信队列、回退队列与重试队列…根据业务需求平衡性能、可用性和持久性」

## 思路与架构

这一节的核心问题只有一句：**Kafka 到底会不会丢数据**。答案是"**在只考虑 Kafka 自身用法的前提下，什么样的配置会把丢失风险压到多低**"——可靠性用几个九衡量，任何系统都不可能绝对可靠：能应付单机故障，也难应付集群或数据中心级故障。

风险分散在**六个环节**，按消息流经顺序串起来就是一张检查清单：

**第一，副本数量。** 副本是抗 broker 宕机的第一道防线，至少需要两个以上副本；只有一个 leader 副本时，节点宕机就可能直接丢数据。一般三个副本即可覆盖绝大多数场景；副本越多越可靠，但磁盘与网络带宽消耗同步上升、性能下降。0.10.0 起支持在 broker 配置中指定机架信息，副本分配会尽量跨机架，避免整机柜故障把多个副本一锅端。

**第二，生产者确认机制。** `acks` 默认 1（leader 写入即返回）；设为 0 不等任何响应，吞吐最大、丢消息也无从感知；设为 -1/all 需等同步副本集合全部写入，可靠性最强。但 all 会**退化**：追随者同步慢被踢出 ISR 后，集合里只剩 leader，all 就等价于 1。兜底参数是 `min.insync.replicas`（默认 1，等于没有约束），典型配法是副本 3、该值配 2——代价是副本不足时拒绝写入，用可用性换可靠性。

**第三，未同步副本能否当 leader。** `unclean.leader.election.enable` 为 true 时允许从非同步副本选主，代价是丢掉未同步的消息；为 false 时该分区可能暂时不可写。它在 0.11.0 把默认值从 true 改成了 false，是少数被官方翻转过的参数，传递的信号很明确：**宁可不可用，也不静默丢数据**。

**第四，刷盘策略。** broker 端的条数与时间两个刷盘参数默认不控制、交给操作系统，依赖页缓存。同步刷盘确实更稳，但对海量数据组件而言性能损耗过大；正确做法是用**多副本**而不是单机刷盘来承担可靠性——刷盘是单机保险，副本是集群保险。

**第五，消费位移提交。** 自动提交默认开启，提交时机与业务处理不同步，既会重复消费也会丢消息；高可靠场景必须关掉改手动，铁律是**业务处理成功才提交**。取舍原则是宁可重复消费也不丢消息，因此消费端幂等是强制配套；解析不了的"毒药消息"要隔离出去，避免卡住整体进度。

**第六，发送方式。** 发后即忘（无回调）性能最高、可靠性最差，遇到不可重试异常就丢；同步发送阻塞等待响应，可靠性最高、性能最差；带回调的异步发送居中，异常由回调处理。

**兜底机制：死信、回退与重试队列。** 写入失败或消费失败的消息不能随意丢弃，应投递到死信队列另作处理——"死信"可以是消费者不能处理、不想处理、或不符合处理要求的消息。回退队列解决的是"不断回滚又回到队头"的死循环；重试队列可视为它的分级版本：按重试等级设置递增的重新投递延时（如一级 5 秒、二级 10 秒），超过上限再进死信队列。

## 方案取舍

| 决策 | 选项 | 取舍 |
|---|---|---|
| 副本数 | 1 / 3 / 更多 | 3 是经验值，再多收益递减、成本线性上升 |
| 生产者确认 | 0 / 1 / all | all 最稳但要配最小同步副本数，否则会退化 |
| 最小同步副本 | 1 / 2 | 配 2 拒绝"伪可靠"写入，代价是副本不足时不可写 |
| 未同步选主 | true / false | false 保数据，代价是极端情况分区不可写 |
| 刷盘 | 强制同步 / 交操作系统 | 同步刷盘性能损耗大，应靠副本而非刷盘 |
| 位移提交 | 自动 / 手动 | 手动可靠，但要求消费端实现幂等 |

取舍要点：

- **别把单个参数当银弹。** acks=all 配 `min.insync.replicas=1` 等于白配；三副本配未同步选主 true 同样白搭。
- **可靠性、可用性、吞吐三者只能取二。** 每一处加固都对应另一处的让步，答题时把代价说全才有说服力。
- **消费端责任不比生产端小。** 位移提交与幂等是"至少一次"语义成立的前提，只聊生产者配置是典型的不完整回答。
- **兜底队列是最后一道网。** 死信队列保证消息不被无声丢弃，重试队列用递增延时避免雪崩式重试 `[经验]`。

## 答题技巧

1. **开场先破题**：可靠性用几个九衡量、不存在绝对可靠，这句话立刻把回答拉到架构层级 `[经验]`。
2. **按消息流经顺序数六道闸门**：副本 → 确认 → 选主 → 刷盘 → 位移 → 发送方式，一条不漏就是完整答案 `[源码]`。
3. **报出关键默认值**：acks 默认 1、最小同步副本默认 1、自动提交默认 true、未同步选主在 0.11.0 起默认 false `[源码]`。
4. **主动点破两个陷阱**：acks=all 会因 ISR 退化而失效；关闭未同步选主影响的是分区可用性而非整个集群 `[源码]`。
5. **给配置必给配套方案**：直接甩"副本 3 + acks=all + min.insync=2 + 手动提交 + 消费幂等"，比逐个参数解释更像做过生产决策 `[经验]`。

## 细节与核心 API

**六道闸门标准配置（可靠性优先，三件套必给）：**

```properties
default.replication.factor=3
min.insync.replicas=2
unclean.leader.election.enable=false
# acks=all 必须配 min.insync.replicas，否则 ISR 退化只剩 leader 时退化为 acks=1（伪可靠）
```

```go
// 生产者：acks=all
config.Producer.RequiredAcks = sarama.WaitForAll // acks=-1/all
config.Producer.Return.Successes = true

// 消费者：关自动提交，业务处理成功才提交（宁可重复不丢，配消费端幂等）
config.Consumer.Offsets.AutoCommit.Enable = false
```

**兜底队列（最后一道网）：**

```text
死信队列(Dead Letter)：消费/解析失败的消息隔离出去，避免毒药消息卡住进度
重试队列：按等级递增延时重投（一级 5s、二级 10s），超上限进死信
回退队列：解决"不断回滚回队头"死循环
```

**刷盘策略：依赖 OS 页缓存，可靠性靠多副本而非单机刷盘；同步刷盘性能损耗过大，海量组件不默认控。**
