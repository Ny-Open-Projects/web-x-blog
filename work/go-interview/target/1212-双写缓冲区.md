# 1212 双写缓冲区：为什么 16KB 的页需要写两遍

> 分类：数据库 / MySQL 存储 | 难度：L4 | 题型：原理题 | 频率：高 | 关键词：**双写缓冲区、doublewrite、部分写失效、页断裂、16KB、4KB、顺序IO、共享表空间**

> 原文锚点：第 1~26 段「InnoDB 在写数据的时候，为了确保落盘数据的原子性，它使用了双写缓冲区来对落盘的数据进行双写…当 InnoDB 正在写入某个页到磁盘的时候，某些特殊情况下这个页写了一部分就发生了宕机，这种情况我们称为部分写失效或者是页断裂…redo log 记录的是对页的物理操作，它并不包含修改后的数据页的完整内容，如果这个页本身已经损坏，那么 redo log 记录的操作是无法修复这个已经损坏的页的…先将数据拷贝到内存中的 doublewrite buffer 当中，接着会从 doublewrite buffer 分两次写入到磁盘的共享表空间当中，这个写入过程是顺序IO，而且每次会写入 1MB 的文件…等到第二步完成之后，再将 doublewrite 中的脏页数据写入到实际的各个表空间文件当中，这个更新表数据的写入操作就属于随机IO」

## 一句话总述
InnoDB 为了保证**落盘数据的原子性**，在脏页刷盘前**先把它顺序写一份到共享表空间的 doublewrite 区**（**2MB 连续空间，每次写 1MB，分两次**），成功后再把脏页**随机写入各自的表空间文件**；一旦发生**部分写失效（页断裂）**，就用这份**页副本**还原损坏页，再应用 redo log 完成恢复。

## 面试官视角
- 考察意图：能否解释"**redo log 已经存在，为什么还需要 doublewrite**"——这是本机制的灵魂问题。
- 分档：P5 知道有双写这个东西；P6 能说"先写一份副本再写数据页"；P7 能讲清**16KB vs 4KB 的页大小不对等**、**顺序 IO 先行 + 随机 IO 后置**的两阶段写入，以及**redo log 修不了损坏页**这一根因。
- 红旗答案：以为 doublewrite 是为了"多存一份数据做备份"；或以为 redo log 能修复损坏的页。
- 惊艳点：**redo log 记录的是"对页做了什么修改"，不是"页改完之后长什么样"**——所以**页本身坏了，重做多少次都还是坏的**，必须有一个**完整页的副本** `[源码]`。

## 主问答
**Q（面试官原话）：** 双写缓冲区是干嘛的？为什么有了 redo log 还要双写？

1. **结论**：InnoDB 写数据时**为确保落盘数据的原子性**，用**双写缓冲区对落盘数据进行双写**——**先把脏页副本顺序写到共享表空间，再把脏页随机写到真实表空间** `[源码]`。
2. **根因 · 部分写失效**：InnoDB 正在把某个页写入磁盘时，**某些特殊情况下这个页写了一部分就发生了宕机**，这种情形称为**部分写失效或页断裂**；**页断裂会导致数据丢失** `[源码]`。
3. **根因 · redo log 修不了坏页**：**redo log 记录的是对页的物理操作，并不包含修改后的数据页的完整内容**；**如果页本身已经损坏，redo log 记录的操作无法修复这个已损坏的页**。因此**在重做之前需要一个页的副本**，发生崩溃时**通过副本还原该页，再进行重做** `[源码]`。
4. **根因 · 页大小不对等**：InnoDB **写入以页为单位**；**数据库的页通常比底层文件系统的页大，且一般是文件系统页大小的整数倍**，所以**数据库的数据块无法保证原子持久化**。实测 **MySQL 数据页为 16KB**，而**底层文件系统页为 4KB**——**数据库把 doublewrite 缓冲区的一个页写到磁盘时，需要底层文件系统把 4 个页全部持久化才算写入成功** `[源码]`。
5. **两阶段写入过程**：
   - **第一步**：一系列机制触发**脏页刷新**时，**并不会直接写入磁盘数据文件**，而是**先将数据拷贝到内存中的 doublewrite buffer** `[源码]`。
   - **第二步**：**从 doublewrite buffer 分两次写入磁盘的共享表空间**；**这个写入过程是顺序 IO，性能很高，而且每次会写入 1MB 的文件** `[源码]`。
   - **第三步**：**等第二步完成后，再将 doublewrite 中的脏页数据写入实际的各个表空间文件**（去磁盘上更新具体的表数据）；**更新表数据的写入操作属于随机 IO** `[源码]`。
   - **收尾**：**当脏页数据持久化到磁盘之后，doublewrite 文件就可以标记为可覆盖** `[源码]`。
6. **崩溃恢复**：**操作系统将页写入磁盘的过程中发生崩溃时，InnoDB 可以从 doublewrite 文件里找到该页的副本，再通过重做日志对数据进行恢复** `[源码]`。
7. **开关**：**doublewrite 机制默认是开启的**，可通过 **`innodb_doublewrite`** 变量查看 `[源码]`。

**加分层：** 一句话记法——**doublewrite 用"一次额外的顺序写"买下了"页的完整性"**，把不可控的随机写风险转移到了可控的顺序写阶段。

## 关键代码
```go
// Go 侧观测 doublewrite 状态与页大小（通过 information_schema / 变量查询）
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/go-sql-driver/mysql"
)

func main() {
	db, _ := sql.Open("mysql", "root:pass@tcp(127.0.0.1:3306)/mysql")
	defer db.Close()

	var name, value string

	// 1) 双写是否开启（默认 ON）
	db.QueryRow("SHOW VARIABLES LIKE 'innodb_doublewrite'").Scan(&name, &value)
	fmt.Println("innodb_doublewrite =", value)

	// 2) InnoDB 数据页大小：默认 16384 = 16KB
	db.QueryRow("SHOW VARIABLES LIKE 'innodb_page_size'").Scan(&name, &value)
	fmt.Println("innodb_page_size =", value, "(16KB，需底层写 4 个 4KB 页)")

	// 3) 双写区落盘量：8.0.20+ 可用 Innodb_dblwr% 系列状态
	rows, _ := db.Query("SHOW GLOBAL STATUS LIKE 'Innodb_dblwr%'")
	for rows.Next() {
		rows.Scan(&name, &value)
		fmt.Printf("%s = %s\n", name, value)
	}
}
```

## 总结与追问预判
**必追问的是"能不能关掉双写"**——可以（设 `innodb_doublewrite=OFF`），但**只在底层设备能保证 16KB 原子写时才安全**；普通 SSD/HDD 关掉等于把页断裂风险暴露出来。追问常接三个思考题——**为什么 redo log 不需要 doublewrite、为什么不能用 redo log 代替、为什么 doublewrite 自己不会写坏**（见 1212）。

## ⚠️ 原文纠错
1. 事实核校：双写用于保证落盘原子性、部分写失效/页断裂定义、redo log 不含完整页内容因而修不了坏页、数据库页大于文件系统页且为其整数倍、MySQL 页 16KB 与文件系统页 4KB、脏页先拷贝进内存 buffer、再分两次顺序写入共享表空间且每次 1MB、随后随机写入各表空间、持久化后可覆盖、崩溃时用副本 + redo log 恢复、默认开启——均与 InnoDB 实现一致 `[经验]`。
2. 补充：**原文"刷一个八 k 的页需写四个磁盘页"与前文"16KB 页写 4 个 4KB 页"不一致，属口误**；正确为 **16KB 数据页对应 4 个 4KB 文件系统页**。另 **8.0.20 起双写区已移出系统表空间，改为独立双写文件** `[经验]`。
3. 崩坏词归一：源码将 doublewrite、页断裂、共享表空间、脏页、重做日志、InnoDB 等术语音译为多组崩坏词，本卡统一为规范术语 `[经验]`。
