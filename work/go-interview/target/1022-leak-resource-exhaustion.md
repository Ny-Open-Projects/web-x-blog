# 1022 协程泄露的资源耗尽维度（端口/内存/长任务）

> 分类：Go 运行时 · 并发缺陷 | 难度：L3 | 题型：事故题 | 频率：中 | 关键词：**端口耗尽**/**内存 OOM**/**长任务堆积**/**下游故障放大**/**资源维度**
> 原文锚点：第 4~6 段、56~63 段「协程占端口/内存；长任务无超时堆积；大文件占内存 OOM」

## 一句话总述
协程泄露不只"内存涨"一种表现，按**耗尽资源**可分三类：**端口/句柄耗尽**（协程发起网络请求占本地端口，堆积到端口用完）、**内存 OOM**（协程读大文件/处理大数据，同时运行太多把内存吃满）、**长任务堆积**（并发大 + 下游慢且无超时，协程数失控）。三者根因都是"无界创建 + 无退出"，解法见 1022-leak-prevention。

## 面试官视角
- 考察意图：能否从"资源视角"理解泄露的破坏面，而非只盯着内存。
- 分档：P5 知泄露涨内存；P6 知端口/内存/长任务三类资源维度；P7 能点出"下游故障 + 无超时 = 雪崩式堆积"的放大效应。
- 红旗：以为泄露只表现为 OOM；或没意识到网络协程会耗尽本地端口。
- 惊艳点：点出"一个无限创建协程去调下游的服务，下游一抖就端口/协程双耗尽"——这是生产最常见、最隐蔽的泄露放大链。

## 主问答
**Q（面试官原话）：** 协程泄露除了 OOM 还会怎样？
**A：**
1. **端口/句柄耗尽**：协程常用来发网络请求，每个占用本地端口/文件句柄；无界创建 → 端口或句柄耗尽，新连接全失败 `[经验]`。
2. **内存 OOM**：协程读大文件/处理海量数据，同时跑太多 → 内存被吃满 → OOM 被 kill。
3. **长任务堆积**：高并发服务访问慢下游，又**没设超时** → 请求协程越积越多，最终服务崩溃（下游故障被无超时放大成雪崩）。
4. **治理指向**：三类都靠"超时 + 协程池/信号量限并发 + 大文件分而治之"化解（详见 1022-leak-prevention）。
