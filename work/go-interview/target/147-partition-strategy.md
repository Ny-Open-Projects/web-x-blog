# 147 Kafka 分区策略：轮询、随机、哈希与自定义

> 分类：消息队列 / Kafka | 难度：L3 | 题型：选型题 | 频率：高 | 关键词：**轮询策略、随机策略、哈希策略、消息键 key、分区有序、自定义分区器**

> 原文锚点：第 11~22 段「分区策略其实就是决定了生产者将消息发送到哪个分区的算法…内置的分区策略有下面几种：第一个是轮询策略，消息被轮流发送到当前 topic 的每个分区，最大优势是可以将消息最大限度的平均分配在所有的分区上…第二个是随机策略，实际效果通常要比轮询策略要差…第三个是哈希策略，可以为每个消息定义一个业务层的消息键 key…哈希策略最大的优势在于可以借助哈希算法将相同业务 ID 的数据发送到同一个分区，而相同分区上的消息具有有序性」

## 一句话总述
Kafka 内置**轮询、随机、哈希**三种分区策略并支持自定义：**轮询**分配最均匀，**随机**效果通常不如轮询，**哈希**则按消息键把同业务 ID 的数据固定到同一分区，从而**保证该键下的顺序性**。

## 面试官视角
P6 知道有这三种；P7 要讲清**各自的适用场景与代价**，尤其**哈希策略的价值不在均衡而在保序**——同 key 进同分区、分区内有序，这是订单等有状态业务的关键；并能说出轮询与随机的优劣对比。

## 主问答
**Q（面试官原话）：** 生产者怎么决定消息写进哪个分区？各策略怎么选？

1. **策略的定义**：分区策略就是**决定生产者将消息发送到哪个分区的算法** `[源码]`。
2. **轮询策略**：消息**轮流发送到当前 topic 的每个分区**；最大优势是**最大限度平均分配**到所有分区 `[源码]`。
3. **随机策略**：消息**随机发送**到各个分区；本质也是尽量均匀分散，但**实际效果通常比轮询策略差** `[源码]`。
4. **哈希策略**：可为每个消息定义**业务层的消息键 key**；key 可以是**有明确业务含义的字符串**（如用户 ID） `[源码]`。
5. **哈希的价值在保序**：借助哈希把**相同业务 ID 的数据发送到同一个分区**，而**相同分区上的消息具有有序性** `[源码]`。
6. **典型场景**：订单处理可用**订单 ID 或用户 ID 作为 key**，把同一订单的变更或同一用户的订单发到同一分区，避免处理不同状态订单产生**乱序问题** `[源码]`。
7. **自定义策略**：Kafka **支持自定义分区策略** `[源码]`。
8. **实践结论**：实际开发中，**轮询策略与哈希策略基本能覆盖绝大部分业务场景** `[源码]`。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Kafka 全版本 | 三种内置策略稳定 | 语义未变 |
| 无 key 时 | 早期随机、后改轮询 | 现代版本默认轮询/粘性 |

## 关键代码
```go
package main

import "github.com/IBM/sarama"

func main() {
	cfg := sarama.NewConfig()

	// 1) 轮询策略：最均匀，适合无顺序要求的吞吐型场景
	cfg.Producer.Partitioner = sarama.NewRoundRobinPartitioner

	// 2) 随机策略：效果通常不如轮询
	// cfg.Producer.Partitioner = sarama.NewRandomPartitioner

	// 3) 哈希策略：按 key 固定分区，保证同 key 有序（订单场景的标配）
	// cfg.Producer.Partitioner = sarama.NewHashPartitioner

	producer, _ := sarama.NewSyncProducer([]string{"127.0.0.1:9092"}, cfg)
	defer producer.Close()

	// 带上业务 key：同一 orderID 的消息恒定落入同一分区
	msg := &sarama.ProducerMessage{
		Topic: "orders",
		Key:   sarama.StringEncoder("order-10086"),
		Value: sarama.StringEncoder("paid"),
	}
	_, _, _ = producer.SendMessage(msg)
}
```

## 总结与追问预判
**哈希策略的题眼是「同 key 同分区 → 分区内有序」**，不是「更均匀」。追问常是「分区数变了会不会破坏顺序」——会：哈希映射随分区数变化，扩容分区会打乱 key 与分区的对应关系，需在业务低峰期规划。分区的目的见同批 147-partition-purpose。

## ⚠️ 原文纠错
1. 事实核校：三种内置策略、轮询最均匀、随机效果通常差于轮询、哈希按 key 路由、同分区有序、订单场景用订单/用户 ID 作 key、支持自定义、轮询与哈希覆盖大部分场景——均与 Kafka 设计一致 `[经验]`。
2. 补充：原文提到哈希策略保证「相同分区上的消息具有有序性」，需补充前提——**该顺序保证仅在分区数不变时成立**；且 Kafka 只保证**分区内有序**，不保证 topic 全局有序 `[经验]`。
