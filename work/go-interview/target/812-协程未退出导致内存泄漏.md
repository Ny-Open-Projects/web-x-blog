# 812 协程未退出导致内存泄漏

> 分类：Go 运行时 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**goroutine 泄漏**/**永不退出**/**NumGoroutine**
> 原文锚点：第 63~88 段「没有让启动的协程及时退出…数量越来越多」

## 一句话总述
Go 虽自带 GC，但**启动后永不退出的 goroutine** 会一直持有其栈与引用的对象，无法被回收；若持续创建而不退出，就会堆积成内存泄漏。

## 面试官视角
- 考察意图：是否理解"GC 只回收无引用对象，管不了卡死/阻塞的 goroutine"。
- 分档：P5 知"goroutine 没退出会泄漏"；P6 能举 for 循环狂开 goroutine 的例子；P7 能讲监控与根因定位。
- 红旗答案：以为"有 GC 就不会泄漏"、把 goroutine 泄漏说成"只是慢一点"。
- 惊艳点：用 `runtime.NumGoroutine()` 或 pprof goroutine profile 直接观测数量只增不减 `[经验]`。

## 主问答
**Q（面试官原话）：** 哪些情况容易造成 Go 内存泄漏？协程这块怎么理解？
**A：**
1. **结论**：最常见泄漏是**协程没退出**——它在 for 循环里被不断启动去处理任务，却因阻塞或死循环永不 return。
2. **机制**：协程一旦阻塞在 channel 收发、死循环、或等待一个永不发生的事件，它的栈和引用的对象就一直可达，GC 不敢回收；新协程还源源不断被创建。
3. **边界**：单个协程栈初始约 2KB 看似很小，但堆积到几十万时内存与调度开销都爆炸，最终 OOM。

**加分层：** 用 `ticker` 每秒打印 `runtime.NumGoroutine()` 可直观看到数量单调递增——这是定位协程泄漏的第一现场。

## 关键代码
```go
func main() {
    // 每 1s 打印当前协程数，观察是否只增不减
    ticker := time.NewTicker(time.Second)
    go func() {
        for range ticker.C {
            fmt.Println("goroutines:", runtime.NumGoroutine())
        }
    }()
    for i := 0; i < 100000; i++ {
        go func() {
            // 没有退出条件 → 协程永远阻塞/空转
            select {} // 模拟永不结束的任务
        }()
    }
    select {} // 防止 main 退出
}
```

## 总结与追问预判
协程泄漏本质是"被创建却永不退出"。监控 `NumGoroutine()` 看趋势，根因多在 channel 阻塞或缺少退出信号。追问接"channel 收发阻塞泄漏"与"pprof 定位"。
