# 1910 高并发评论系统：写削峰与读预读的内存陷阱 深挖

> 覆盖源 19-10 全文：评论系统的产品形态（发布支持楼层与楼中楼、读取按时间与热度双维度排序、删除对用户与作者双向授权、管理支持置顶与后台审核），以及整体架构（负载均衡 → 入口网关 → BFF 业务网关 → 评论服务层 → comment worker 消费消息队列写 MySQL；读走 Cache-Aside + readahead 预读，预读异步化；写队列以微博 ID 作分区 key 保序）。主卡已给架构结论与可运行骨架，本附录做「为什么瓶颈一定在 DB」「预读为什么必须由 worker 做」「保序与倾斜的两面性」「BFF 降级的价值」「产品形态如何反向约束架构」五层深挖。

## 思路与架构

```text
客户端 → LB → 入口网关 → BFF(聚合/定制/降级) → 评论服务层
                              │               ├─ 写: MQ(按微博ID分区) → worker → MySQL
                              │               └─ 读: Cache-Aside → 未命中只查第一页
                              │                        └─ 预读任务 → MQ → worker → 回填缓存
                              └─ 非核心 gRPC: 敏感词检查 / 账号服务 → 可降级
```

## 方案取舍
- **为什么瓶颈一定在 DB**：读可以靠缓存无限横向扩展（缓存是无状态的、可加副本），而**写终究要穿透到 DB**——无论前面加多少层队列、多少台应用，最终落库的那一次事务是串行的、受限于单机写能力。所以系统的极限吞吐由 DB 的写入能力决定，前面所有设计（队列削峰、预读回填）本质都是**保护 DB**。认清这点，才能解释"为什么可以接受评论短暂延迟"——延迟是把瞬时峰值摊平到时间轴上的代价 [经验]。
- **预读为什么必须由 worker 做**：预读的朴素实现是"顺手把后几页也查出来写进缓存"，这在低峰期没问题，但在**高峰期就是自杀**——应用会在极短时间内把大量评论数据读进**堆内存**，一方面直接触发 **OOM**，另一方面这批查询本身又给 DB 造成远超正常读的**突发压力**。把预读改成"投递任务到 MQ、由 worker 消费后回填"，等于把"内存占用"和"DB 压力"两件事都搬到了**可控速率的后台**，请求线程只留一个投递动作 [经验]。
- **保序与倾斜是一对矛盾**：以**微博 ID 作分区 key** 能让同一条微博的评论进入同一分区，从而消费端**顺序消费**、保证楼层语义——这是它必须这样做的理由。但代价是：**热点微博的全部评论压到一个分区**，单分区吞吐有上限，反而可能成为新的瓶颈。工程上的折中是 **`微博ID + 分桶号` 二次哈希**打散（牺牲严格全局顺序换取吞吐），或对头部热点做**独立通道/独立扩容**。面试时把这一对矛盾主动说出来，比只答"用微博 ID 保序"高出一个档 [经验]。
- **BFF 层为什么值得单独加一层**：入口网关管"流量与安全"，BFF 管"业务编排与终端定制"。没有 BFF 时，移动端/Web/小程序各自要并发调 N 个后端接口再自己拼装，既慢又重复；BFF 把它们收敛成一次聚合调用，还能做**合并、过滤、排序**。更重要的是——**降级点要收敛在 BFF**：敏感词检查、账号等级这类非核心依赖一旦抖动，BFF 直接降级返回，绝不让故障沿调用链传导到核心评论服务 [经验]。
- **产品形态反向约束架构**：支持**楼中楼回复**意味着评论是一棵树而非平铺列表，读取要按**时间 + 热度双维度**排序，说明需要两套索引（时间序 + 热度分）；删除要**用户与作者双方**都有权限，说明权限判定要在服务层而非网关层；作者可**置顶**，说明存在需要强一致读取的"尾部小数据"，这类数据通常不走缓存 TTL 而走**主动失效**。这些都说明：**架构不是凭空画的分层，是被产品语义逼出来的** [经验]。

## 答题技巧
- 开口先定瓶颈：**「写终究穿透 DB，DB 是瓶颈，所以整个架构围绕保护 DB 展开」**——这一句立住，后面所有取舍都顺理成章 [经验]。
- 讲到预读时**主动说出 OOM 风险**，再给异步化解法；只答"用预读提升体验"会被判定为没踩过坑 [经验]。
- 被追问「为什么用微博 ID 当 key」→ 先答保序，立刻补**分区倾斜**与二次哈希，展示两面性 [经验]。
- 被追问「BFF 和入口网关区别」→ 答「入口网关管流量与安全，BFF 管业务编排与终端定制，**降级点收敛在 BFF**」 [经验]。
- 主动边界到 `1419-partition-strategy`（分区数与 key 哈希）、`1419-backlog-causes`（积压成因）、`1415-producer-send-modes`（生产者发送方式），构成消息链路全栈 [边界]。

## 细节与核心 API

```go
// 架构：写走 MQ 异步，读走缓存，热点隔离
// 1) 提交评论：先写 Redis 缓冲 + 发 Kafka，异步落 DB（削峰）
comment := accept(r)
rdb.LPush(ctx, "comment:queue:"+postID, marshal(comment))
producer.Publish("comments", postID, marshal(comment))
// 2) 读取列表：优先 Redis 缓存（ZSET 按时间排序），miss 回源 DB 并回填
list, _ := rdb.ZRevRange(ctx, "comment:list:"+postID, 0, 19).Result()
if len(list) == 0 { list = loadFromDB(postID); rdb.ZAdd(/*回填*/, /*TTL*/) }
// 3) 热点防击穿：互斥重建（singleflight）+ 逻辑过期
// 4) 计数：Redis INCR 评论数，异步持久化（见 counter 卡）
// 关键点：写可最终一致；读要快且防缓存击穿/穿透/雪崩；恶意刷评用限流+风控
```
