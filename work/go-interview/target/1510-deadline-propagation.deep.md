# 1510 调用链超时预算制 深挖

> 覆盖源 15-10 全文：为什么需要超时控制（用户体验 + 释放资源 + 减少堆积）、七条落地手段（统一默认超时与部署平台下发、全局超时、每服务超时并传递剩余时间、跨服务传递超时信息、关键/非关键分级、有限次重试与非幂等谨慎、熔断与半开探测、监控告警），以及 A→B→C 的链路算例。主卡已给结论与可运行示例，本附录做「局部超时为什么不够」「为什么答案是递减而不是一致」「扇形调用的预算分配」「七条手段的内在层次」「答题如何分层」五层深挖。

## 思路与架构

```text
入口(客户端/网关): 全局预算 T_total = 1s
├─ A 消耗 200ms → 传递 remaining = 800ms 给 B
│   ├─ B 消耗 500ms → 传递 remaining = 300ms 给 C
│   └─ B 若已用 ≥800ms → 不再调 C, 直接失败返回(这是关键动作)
└─ 每跳都要: 扣已耗时 + 扣网络/序列化开销 + 预留安全余量

并发 fan-out: 同一个 deadline 给多个分支, 预算共享而非独享
```

## 方案取舍
- **局部超时的失效点在于"放弃不同步"**：如果链路上每一跳只知道"我这次调用最多等 800ms"，那么当 A 已经在 400ms 超时放弃时，B 还在按自己的 800ms 慢慢算——**用户已经走了，资源还在烧**。这就是原文提到的"客户端 500ms、服务端 1s 会导致服务端资源堆积"。所以全链路控制要解决的核心不是"给每个调用设上限"，而是「**让上游的放弃立刻传导到下游**」，唯一的办法就是把**同一个 deadline 沿链路往下传** [经验]。
- **为什么答案是"逐层递减"而不是"保持一致"**：这是本题最容易答错的一句。若两端**一致**，由于网络传输与调度存在延迟，客户端的时钟几乎总是**先**到达临界点——于是每次都是客户端先放弃、服务端后知后觉。把下游设得更短（**上游 > 下游**），能确保「**下游先失败并把错误快速回传，上游还有余量做降级或兜底**」，而不是上游先崩、下游成孤儿。一句话：**让最先感知超时的永远是最下游** [经验]。
- **扇形调用的预算是共享的**：上述"线性相减"只在**串行链路**成立。一旦 B 要并发调用 C 与 D，它们拿到的是**同一个 deadline**——这不是 Bug 而是必须：**总数不能超过上游给的总额**。若给每个分支都独立分配全额剩余，B 的实际耗时可能达到 `remaining × 分支数`，链路预算瞬间翻倍失效。工程上通常给每个分支再设**更小的子超时**（按重要性加权切分），并保证 `max(分支耗时) + B 自身开销 ≤ remaining` [经验]。
- **七条手段其实是三个层次**：① **治理层**——统一默认超时（公共库 + 部署平台下发 + 环境变量注入），解决的是"各服务各写一套默认值"的混乱；② **运行时层**——全局超时 + 剩余时间传递 + 跨服务携带 + 关键/非关键分级，这是真正的链路控制；③ **兜底层**——有限重试、非幂等谨慎、熔断半开探测、监控告警。**面试按这三层答，比罗列七条更像有体系** [经验]。
- **为什么关键服务超时反而要更短**：直觉相反但很合理——**关键服务的失败必须早暴露**，因为它的结果决定了整条链是否有意义，拖到最后才失败等于前面所有资源全白烧；**非关键服务**（如推荐位、装饰性数据）放宽超时，即使慢一点也能返回，实在不行还能降级跳过，用时间换成功率 [经验]。

## 答题技巧
- 开口先立核心：**「关键在于把同一个 deadline 沿链路往下传，而不是每跳各自设超时」**——这一句就把 P6 和 P7 分开 [经验]。
- 一定要主动纠正"超时保持一致"的说法：答**逐层递减、下游更短**，并说明"让最下游最先感知超时" [经验]。
- 把七条收敛成**治理 / 运行时 / 兜底三层**再展开，体系感立刻出来 [经验]。
- 讲算例时补一句**「串行是线性相减，并发 fan-out 是预算共享」**，这是区分背过和做过的关键 [经验]。
- 主动边界到 `158-retry-timeout`（重试限次、指数退避、防重试风暴）与 `158-circuit-breaker-degrade`（熔断与降级）、`1501-service-communication`（服务通信基础），本卡只讲**链路上 deadline 的传递与预算** [边界]。
