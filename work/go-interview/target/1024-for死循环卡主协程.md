# 1024 for{} 死循环卡主协程：抢占式调度版本边界修正

> 分类：Go 并发 / 调度 | 难度：L3 | 题型：机制题 | 频率：中 | 关键词：**for 死循环** / **抢占式调度** / **GOMAXPROCS** / **Go 1.14** / **饿死**
> 原文锚点：第 4~13 段「for死循环占CPU；1.4前 GOMAXPROCS=1 时协程可能永不被调度；1.4 加入抢占式调度后让出CPU」

## 一句话总述
用 `for {}` 空转可卡住 main，但会**持续占 CPU**；更关键的是调度版本边界——**源码称 Go 1.4 引入抢占式调度，实际是 Go 1.14 才落地异步抢占**。在 1.14 之前、且 `GOMAXPROCS=1`（单逻辑核）时，一个不含函数调用的 `for {}` 会独占 P，导致其他 goroutine 长期得不到调度（饿死）。

## 面试官视角
- 意图：不止考"怎么卡 main"，更考对抢占式调度演进与单核饿死陷阱的理解。
- P5 知 for{} 空转占 CPU；P6 知 GOMAXPROCS=1 单核下紧循环会饿死其他协程；P7 知异步抢占实为 Go 1.14（非 1.4），以及 `runtime.Gosched`/函数调用可主动让出。
- 红旗：照背"1.4 就解决了"；或以为死循环不影响其他协程。
- 惊艳点：点出"1.4 是协作式（需函数调用让出），1.14 才是异步抢占真正解决紧循环饿死" `[边界]` 见 815、816-gmp-tradeoff（P 与调度）。

## 主问答
**Q（面试官原话）：** for 死循环为什么能让主协程不退出？会不会有问题？
**A：**
1. **空转占 CPU**：`for {}` 不含阻塞/让出，main 永远在跑，既卡住退出又空耗一个核。
2. **单核饿死（1.14 前）**：在 `GOMAXPROCS=1` 时，不含函数调用的紧循环独占 P，其他 goroutine 拿不到调度机会；**异步抢占实为 Go 1.14 引入**，此前只有协作式（需函数调用/chan 操作才让出）。
3. **1.14 后缓解**：异步抢占可强制紧循环让出 CPU，其他协程获得执行机会，但 `for {}` 仍在空转轮转，资源浪费依旧。
4. **主动让出**：循环内插入 `runtime.Gosched()` 或函数调用（产生协作点）可在旧版本下缓解饿死，但治标不治本。

## 关键代码
```go
package main

import "runtime"

func main() {
	// 危险：GOMAXPROCS=1 且 Go<1.14 时，go work() 可能永不被调度
	// go func() { for { work() } }()
	for {
		// 旧版本在循环内插入让出点可缓解饿死（治标）
		runtime.Gosched()
	}
}
```

## 总结与追问预判
- for{} 空转卡 main 但浪费 CPU；单核紧循环饿死是 1.14 前痛点，异步抢占才是真解（非源码所称 1.4）。
- 预判：GMP 调度与 P → 见 815、816-gmp-tradeoff；协程生命周期 → 见 1018。
