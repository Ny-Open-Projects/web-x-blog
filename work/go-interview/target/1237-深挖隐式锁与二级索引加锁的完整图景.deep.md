# 1237 深挖：隐式锁与二级索引加锁的完整图景

> 分类：MySQL / InnoDB | 难度：L4 | 题型：架构题 | 频率：中高 | 关键词：**延迟加锁、锁转换、临键锁、伪记录、排查路径**

> 原文锚点：第 1~92 段「隐式锁机制…二级索引加锁规则…最大虚拟记录行」

## 思路与架构

这一章的两块内容，本质是**同一个问题的两个面**：InnoDB 如何在"不浪费锁内存"和"不破坏隔离性"之间取平衡。

**第一条线：延迟加锁。** 插入一条新记录时，如果立刻为它建显式锁对象，批量导入场景会瞬间产生海量锁结构。于是 InnoDB 选择什么都不建——只加表级意向排他锁，行上的保护由一个已有的东西兼职：记录头里的隐藏事务标识。

保护之所以成立，是因为这个事务标识在 MVCC 里本来就要读：判断一行可见与否，看的就是"最后改动它的事务是否还活跃"。同一份数据复用两次，零额外存储。

当别的事务真来抢这一行时，系统才做**锁转换**：抢锁方先给表加自己的意向锁，再替持有方在这行补一把排他记录锁，把隐式的承诺兑现成显式的锁对象，然后自己排队等待。注意这里有个反直觉的细节——**锁是抢锁方替别人建的**。这条链路在聚簇索引上只需一步；在二级索引上没有隐藏列，于是退化为两级判定：先用页头的最大事务号做快速否决（若小于当前最小活跃事务号，说明本页改动全部已提交），落在灰区才回表到聚簇索引查那份唯一的真相。

**第二条线：加锁范围。** 二级索引等值查询不是点查而是扫描，因为同值可能有多条。规则是可预测的：

- 沿索引向右扫，到第一个不满足条件的记录停止；
- 扫到的二级索引记录加临键锁（左开右闭，左端是同层前一个索引值）；
- 命中的主键记录回表加记录锁；
- 若目标不存在，不满足项上的临键锁退化为纯间隙锁，且主键不加锁。

最后一块拼图是页尾的虚拟最大记录。当等值命中的正好是索引最大值时，向右扫描撞上的是这条伪记录，它也会拿到临键锁，于是锁定区间延伸到 `(最大索引值, +∞)`。这个"最大"是**索引列的值**，绝不能和主键自增位置混为一谈。

## 方案取舍

| 设计选择 | 收益 | 代价 |
|---|---|---|
| 插入不建显式锁 | 批量导入省锁内存与申请开销 | 冲突时要做锁转换，路径变长 |
| 二级索引用页头代理 | 不为每条二级索引记录存系统列 | 灰区要回表，最坏多一次查找 |
| 等值不满足项退化为间隙锁 | 缩小锁范围、提高并发 | 规则复杂，容易记混 |
| 伪记录参与加锁 | 用统一结构覆盖无穷上界 | 区间语义反直觉，易误判 |

取舍的关键提示：

- **隐式锁不是"没锁"。** 它的隔离强度与显式锁等价，区别只在锁对象的创建时机。面试里把"没有锁"说成"没有保护"是硬伤。
- **锁区间永远绑定在具体索引上。** 判断插入是否被阻塞，要问两件事：锁建在哪棵索引树上、插入值按该列的排序规则落在哪个区间。主键大小是干扰项。
- **字符串比较按排序规则，不按数值直觉。** 这是原文那个"id=22 能插、name=9 被阻塞"实验的全部谜底。

## 答题技巧

1. **用"延迟"这个词起手。** 一句话点题"加锁被推迟到冲突发生"，比背流程更能让面试官确认你理解到位。
2. **把两条线画出层次。** 先讲聚簇索引的判定三步，再讲二级索引的页头快筛 + 回表终审，层次感本身就是分。
3. **抢答那个反直觉实验。** 主动抛出"自增 ID 已经到 22 了还能插进去"，再解释索引列与主键的区别，说服力极强。
4. **带上排查工具。** MySQL 8.0 用 `performance_schema.data_locks` 看锁型与锁状态，5.7 用 `information_schema.innodb_trx` 配合 `SHOW ENGINE INNODB STATUS`，报出工具名比空谈理论可信 `[经验]`。
5. **隔离级别一定要声明。** 所有间隙、临键结论都只在 RR 下成立，开口先说"以下按 RR"，这是老手的习惯动作 `[经验]`。
