# 1826 内存页置换算法：六种策略与它们的近似路线

> 分类：操作系统 / 内存管理 | 难度：L2 | 题型：原理题 | 频率：中 | 关键词：**缺页中断**/**OPT**/**FIFO**/**LRU**/**Clock**/**LFU**
> 原文锚点：第 1~34 段「内存页置换算法是操作系统中用于决定内存不足的时候应该替换哪些页面到磁盘的策略…最佳页置换算法使用未来信息…先进先出…最近最久未使用…时钟页置换算法是 LRU 的一种近似实现…最不常用算法…随机置换算法」

## 一句话总述
物理内存不足发生**缺页中断**时，OS 要选一页换出到磁盘——六种算法按「用什么信息预测未来」分三条路线：**向前看**（OPT，不可实现的理论基准）、**向后看**（LRU 用历史时间近似 OPT、LFU 用历史频率、FIFO 只看进入顺序）、**不记录精确信息**（Clock 用硬件使用位近似 LRU、Random 纯随机）；工程上真正落地的是 **Clock 一族**，因为精确 LRU 的软件维护代价太高。

## 面试官视角
- 考察意图：不止背名字，而是看你是否理解「**信息来源决定近似质量**」——OPT 用未来（不可得）、LRU 用过去、Clock 用硬件帮我们留下的一个 bit。
- 分档：P5 报出 OPT/FIFO/LRU/LFU 四个名字；P6 讲清 LRU 为何近似 OPT、Clock 的使用位如何转；P7 能给 FIFO Belady 异常反例、对比 Clock 与 Redis 近似采样两条近似路线。
- 红旗答案：把「缺页」说成「内存不够报错」；认为 LRU 一定比 FIFO 命中率高（Belady 异常恰恰说明不是）。
- 惊艳点：主动指出「**Clock 是 OS 的近似 LRU，Redis 近似 LRU 是随机采样——两条不同的廉价路线，前者靠硬件使用位，后者靠对象内时间戳**」 [经验]。

## 主问答
**Q（面试官原话）：** 内存页置换算法有哪些？各自优缺点是什么？
**A：**
1. **OPT（最佳置换）**：淘汰**未来最长时间不会被访问**的页，缺页率理论最低——但需要预知未来访问序列，**无法实现**，价值是当基准：任何算法的缺页率都以它为下界 [源码]。
2. **FIFO（先进先出）**：维护进入顺序队列，淘汰最早进入的页。实现最简单，但**页面进入时间与使用模式无关**，性能差；还有 **Belady 异常**——分配的物理帧变多、缺页反而变多，实测经典串 `1,2,3,4,1,2,5,1,2,3,4,5`：FIFO 3 帧缺页 **9** 次，4 帧反而 **10** 次 [实测]。
3. **LRU（最近最久未使用）**：淘汰**最久没被访问**的页，用「历史使用」近似 OPT 的「未来使用」，局部性好时表现优秀。但**精确实现太贵**：每次访存都要在链表里找到该页、删除、移到表头——这个维护代价正是 Redis 弃用链表 LRU 的同一组理由（额外空间 + 移动开销），见 `1259-lru-vs-lfu` [边界]。
4. **Clock（时钟置换）**：LRU 的**硬件友好近似**。页组织成环形链表，访问时 MMU 把**使用位置 1**；缺页时指针顺时针扫描：使用位为 0 → 淘汰；为 1 → 清 0 跳过。指针回环模拟时针。**软件不维护访问顺序**，只消费硬件留下的 1 bit [源码]。实测同串 Clock 缺页 9 次，与精确 LRU（10）相当甚至更稳 [实测]。
5. **LFU（最不常用）**：每页维护**访问次数计数器**，淘汰计数最小的页。只看频率不看**时间**——历史上高频、如今已冷的页赖着不走，刚升温的新页反被误伤，这是它的结构性缺陷（Redis LFU 用**时间衰减**修的就是这个，见 `1259-lru-vs-lfu` [边界]） [源码]。
6. **Random（随机）**：随机选一页换出。实现零成本，性能不稳定；在**没有引用位硬件支持**的平台上反而是诚实的选择 [经验]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| 教材六算法 | 与具体 OS 版本无关 | 按「信息来源」三条路线组织回答 |
| Linux 实际实现 | 不是裸 Clock/LRU，是 **active/inactive 双链 LRU 变体** | 被问「Linux 用哪种」时答双链近似 LRU，非精确 LRU |
| 无引用位硬件 | MMU 不置使用位时 Clock 失效 | 退化为 FIFO/Random，这是嵌入式 Random 存在的理由 |
| 应用层缓存 | Redis 弃链表 LRU 改近似采样，LFU 加时间衰减 | 与 OS 层分开答，见 1259 系列 [边界] |

## 关键代码
```go
// Clock 置换算法：使用位 + 指针回环（缺页时扫描，0 淘汰 / 1 清 0 跳过）
func clockFaults(ref []int, frames int) int {
	pages := make([]int, frames)
	use := make([]int, frames)
	for i := range pages {
		pages[i] = -1
	}
	hand, faults := 0, 0
	for _, p := range ref {
		hit := false
		for i := range pages { // 命中：置使用位
			if pages[i] == p {
				use[i] = 1
				hit = true
				break
			}
		}
		if hit {
			continue
		}
		faults++
		for { // 回环扫描
			if use[hand] == 0 {
				pages[hand] = p
				use[hand] = 1
				hand = (hand + 1) % frames
				break
			}
			use[hand] = 0
			hand = (hand + 1) % frames
		}
	}
	return faults
}
// [实测] 经典串 1,2,3,4,1,2,5,1,2,3,4,5：FIFO 3帧缺页=9、4帧缺页=10（Belady 异常）；同串 LRU 3帧=10、Clock 3帧=9
```

## 总结与追问预判
一句话记忆：**「OPT 向前看不可实现；FIFO 只看年龄会 Belady；LRU 看历史但太贵；Clock 用 1 bit 近似；LFU 只看频率会误伤；Random 兜底」**。应用层缓存的同题不同答——Redis 的近似 LRU 采样与带衰减的 LFU 见 `1259-lru-vs-lfu`、InnoDB Buffer Pool 的 young/old 分区 LRU 见 `125-bufferpool-lru-young-old` [边界]。常追问「Linux 到底用哪个」——答 active/inactive 双链近似 LRU；再追问「缺页中断一定很差吗」——答 minor fault（页在内存只是没建映射）代价低，major fault（要读盘）才是性能杀手，排查方向见 `188-load-diagnosis.deep` 的 D 状态归因 [边界]。

## ⚠️ 原文纠错
1. 术语归一：[经验] 源为语音转写，「缺液中断」应为「缺页中断」，「CRLRU」应为「LRU」，其余音译崩坏词统一为规范术语。
2. 量词纠错：「随机选择一个月进行置换」应为「一页」；「护一个队列」应为「维护一个队列」。
3. 补充：源未提 FIFO 的 Belady 异常与 Clock 的硬件使用位来源（MMU 置位），这两点是本算法高频追问点，本卡已补 [实测]。
