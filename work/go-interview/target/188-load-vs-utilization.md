# 188 平均负载高，CPU 使用率就一定高吗？

> 分类：操作系统 / 性能排查 | 难度：L3 | 题型：概念辨析题 | 频率：高 | 关键词：**load average**/**可运行+不可中断**/**指数衰减**/**D 状态**/**IOwait**
> 原文锚点：第 7~39 段「平均负载是指单位时间内系统处于可运行状态和不可中断状态的平均进程数…是不可中断状态是为保证进程数据与写入磁盘数据的一致性…平均负载为三意味着只有三个 CPU 的机器上所有 CPU 都刚好被完全占用…指数衰减平均值…CPU 使用率是单位时间内 CPU 的繁忙情况统计」

## 一句话总述
**平均负载 ≠ CPU 使用率**。平均负载是**单位时间内处于可运行状态（R）与不可中断状态（D）的活跃任务数的指数衰减平均值**——它统计的是「**有多少任务在排队要资源**」；CPU 使用率统计的是「**CPU 忙不忙**」。平均负载高可能来自 CPU 密集计算，也可能来自**等 IO（D 状态）**或**等 CPU 调度**，后两者的 CPU 使用率未必高。

## 面试官视角
- 考察意图：这是一道经典的**概念辨析 + 排障思维**题。面试官要的是「你看到 load 高了，第一步干什么」的完整链路，而不是背定义。
- 分档：P5 认为 load 就是 CPU 使用率（最常见的错误，工作几年的工程师也常这么说）；P6 能说出 load = R + D 的活跃任务数；P7 能讲清**三种 load 高但 CPU 使用率不同的组合**、知道用 load / 核数判断过载，并能指出容器里的坑。
- 红旗答案：「load average 第一个数 0.02 说明 CPU 用了 2%」「load 高就赶紧加 CPU」——前者概念混淆，后者可能误诊（若高在 IO，加 CPU 毫无用处）。
- 惊艳点：补一句「**Linux 的 load 包含 D 状态，BSD/macOS 只算 runnable**，跨平台不可直接对比」，以及「容器里 `/proc/cpuinfo` 看到的是宿主机核数，要按 cgroup CPU quota 判断」 [经验]。

## 主问答
**Q（面试官原话）：** 线上 load 飙到 20 了，是不是 CPU 打满了？你怎么判断？
**A：**
1. **先把概念掰清楚**：`top` 第一行 `load average: x, y, z` 是**过去 1 / 5 / 15 分钟**的平均负载；它表示单位时间内处于**可运行状态（R，正在用或正在等 CPU）** 与 **不可中断状态（D，等硬件 IO 响应且不允许被打断）** 的**平均活跃任务数**，和 CPU 使用率**没有直接关系** [源码]。
2. **它是加权平均不是算术平均**：实际是**指数衰减平均值**——对近期数据赋予更高权重、对历史数据权重按指数规律衰减，所以要多久才能反映当前趋势，看的是衰减常数，而不是简单的滑动窗口 [源码]。
3. **判断过载必须除以核数**：负载值本身没意义，要看 `load / CPU 核数`。例如负载 3：3 核机器上**刚好满载**；6 核机器只用了 **50%**（一半空闲）；1 核机器上则有 **2/3 的任务抢不到 CPU** [源码]。核数用 `grep 'model name' /proc/cpuinfo | wc -l`（或 `nproc`）查 [经验]。
4. **三个值要一起看**：1/5/15 分钟三者接近 → 系统**负载平稳**；1 分钟**远小于** 15 分钟 → 近期负载在**下降**，过去压力大；1 分钟**远大于** 15 分钟 → 近期负载在**上升**，可能是抖动也可能是趋势，需持续观察 [源码]。**一旦 1 分钟平均负载接近或超过 CPU 核数，就是过载信号**，要立即分析优化 [源码]。
5. **load 高不等于 CPU 使用率高——三种组合**：① **CPU 密集型**：大量计算，load 与 CPU 使用率**同时升高**（两者一致）；② **IO 密集型**：大量任务堵在等 IO 上，load 升高但 **CPU 使用率不一定高**；③ **大量进程等待 CPU 调度**：排队等 CPU，load 与 CPU 使用率**都高** [源码]。
6. **D 状态是关键线索**：不可中断状态是为保证**进程数据与写入磁盘数据的一致性**而设的保护机制（最典型是等磁盘 IO 响应，也称 disk sleep）。**D 状态任务多 → 优先怀疑磁盘/存储 IO**，而不是 CPU [经验]。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在该怎么答 |
|---|---|---|
| Linux 全版本 | load 含 R + D 两类任务 | 按「活跃任务数」答，含 IO 等待 |
| BSD / macOS | load **只算 runnable**，不含 D | 跨平台对比要注明口径差异 |
| 内核 < 4.x 容器 | `/proc` 未隔离，看到宿主机视图 | 容器内 top / cpuinfo 不可信 |
| 内核较新 + cgroup v2 | `/proc/loadavg` 仍可能来自宿主机 | 核数取 cgroup CPU quota 换算 |
| 任意版本 | 判断用 `load / 核数` | 别孤立看 load 绝对值 |

## 关键代码
```go
// 一个最小负载巡检：读 /proc/loadavg 与 CPU 核数，输出是否过载并给方向性归因
package main

import (
	"fmt"
	"os"
	"runtime"
	"strconv"
	"strings"
)

func main() {
	b, err := os.ReadFile("/proc/loadavg")
	if err != nil {
		fmt.Println("非 Linux：", err)
		return
	}
	fields := strings.Fields(string(b))
	load1, _ := strconv.ParseFloat(fields[0], 64)
	cores := float64(runtime.NumCPU())
	ratio := load1 / cores
	fmt.Printf("load1=%.2f cores=%.0f ratio=%.2f\n", load1, cores, ratio)
	switch {
	case ratio >= 1.0:
		fmt.Println("结论：过载。再查 CPU 使用率——若 CPU 不高而 load 高，优先看磁盘 IO 与 D 状态任务数")
	case ratio >= 0.7:
		fmt.Println("结论：接近满载，需观察趋势")
	default:
		fmt.Println("结论：资源有余量")
	}
}
// [实测] 输出：load1=0.35 cores=8 ratio=0.04 → 结论：资源有余量
```

## 总结与追问预判
一句话记忆：**「负载看排队人数，使用率看 CPU 忙不忙，两者不必同高」**。进程状态机（R/D/S/Z 与不可中断为何不可被打断）见 `187-process-states` [边界]，本卡不重述；用户态/内核态切换代价见 `1820-user-kernel-space`、调度基础见 `1829-scheduling-overview.deep` [边界]。常追问「load 高第一步查什么」——答：先拿**核数算比值**判断真过载，再同时看 CPU 使用率与 IO 等待：CPU 高且 load 高是算力瓶颈，CPU 低而 load 高要立刻怀疑**磁盘 IO 或锁竞争导致的 D 状态堆积**；再追问「容器里怎么办」——答：容器内读到的可能是**宿主机**核数与负载，应按 **cgroup CPU quota** 折算有效核数。

## ⚠️ 原文纠错
1. 事实核校： [经验] 「load = 单位时间 R 态 + D 态平均活跃任务数」「指数衰减平均」「负载要与核数比较」「负载高不等于 CPU 使用率高」均正确。两点补充——① 严格说 Linux 统计的是**任务（含线程）**而非仅传统意义的进程；② 原文未提**跨平台口径差异**：BSD/macOS 的 load 不含 D 状态，不能与 Linux 直接对比，容器场景下还需按 cgroup quota 而非 `/proc/cpuinfo` 折算核数。
2. 崩坏词归一：源码将若干术语音译为崩坏词（如 disk sleep、top 等被音译），本卡统一为规范术语，无黑名单词。
