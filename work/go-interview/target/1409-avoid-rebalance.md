# 1409 避免重平衡：触发源到对策的映射，完全避免不可能

> 分类：消息队列 / Kafka | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**触发源分类**/**隔离原则**/**recover 防 panic**/**max.poll.interval**/**session.timeout**
> 原文锚点：第 1~25 段「完全避免消费者的重平衡也是不可能的，因为重平衡是 Kafka 为确保消费的负载均衡和容错而设计的内置机制…可以采取策略来降低重平衡的概率和影响…消费者长时间不提交消息会被判定为死亡踢出消费组…确保消费者实例在判定死亡之前能够至少发送三次心跳」

## 一句话总述
重平衡是 Kafka 的**内置容错机制，只能降频不能根除**——按触发源逐个拆解：**重启类**（发版/改配置）用**隔离原则**拆微服务 + **recover 捕获 panic** 防异常退出；**消费慢类**按「业务最长耗时 × 2」设 `max.poll.interval.ms`；**心跳类**按「session.timeout = 3 × heartbeat.interval」配对设置（经验值 heartbeat=2s、session=6s）；**无故频繁触发**则查 GC 日志——每一类都有对应抓手。

## 面试官视角
- 考察意图：这是重平衡的**工程应用题**——考「背触发条件」之上的一层：每个触发源能不能给出**可落地的对策**，以及「配对参数」的量化经验。
- 分档：P5 能说出调心跳参数；P6 能按触发源分类给对策、报出 2s/6s 配对；P7 能讲隔离原则、recover 防线、GC 排查与「完全避免不可能」的定位。
- 红旗答案：「调大 timeout 就行」——session 调太大反而让真死成员迟迟不被剔除，消费长期停滞；「重平衡可以彻底消灭」。
- 惊艳点：「**发布链路才是最大触发源**——把消费代码隔离成独立微服务，让业务发版不再牵连消费者重启；再加 recover 兜住 panic，非计划重启归零」 [经验]。

## 主问答
**Q（面试官原话）：** 怎么避免消费组的重平衡？
**A：**
1. **定位先说准**：重平衡是负载均衡与容错的内置机制，**完全避免不可能**，目标是**降低概率与影响**。方法是「触发源 → 对策」逐一映射 [源码]。
2. **触发源①：消费者被重启**（发版、改配置、改分区数后的必然重启）。对策两条：**隔离原则**——把消费代码拆成独立微服务，非消费代码的变更不再牵连消费者发版；**健壮性**——消费循环内用 `recover` 捕获 panic，避免一次代码异常导致整个应用退出、全组重平衡 [源码]。
3. **触发源②：消费耗时过长**。两次 poll 间隔超过 `max.poll.interval.ms`（默认 300000ms = **5 分钟**），消费者被判死亡踢出组。对策：按**业务最长处理耗时 × 2** 设置——业务最长 10 秒就配 20 秒，留一倍余量但不放任 [源码]。
4. **触发源③：心跳不及时**。两个参数配对：`session.timeout.ms`（判死时限）与 `heartbeat.interval.ms`（心跳间隔），要求**判死前至少发出 3 次心跳**——即 session = 3 × heartbeat。经验配置 **heartbeat=2s、session=6s**（注意配置单位是毫秒）。**不能一味调大**：真死的实例要尽早剔除，否则分区空转、消息堆积 [源码]。
5. **触发源④：无故频繁触发**。参数都对了还频繁重平衡，查 **GC 日志**——应用或 Kafka 服务端的长时间 Full GC 会让消费线程停顿、错过心跳窗口，被误判死亡。改分区数后消费者**一段时间识别不到新分区**也属此类怪象，需手动重启消费确认 [源码]。

## 关键代码
```go
// 消费循环的 panic 防线 + 参数配对 (sarama 形态 [源码])
config := sarama.NewConfig()
config.Consumer.Group.Session.Timeout = 6 * time.Second   // session.timeout.ms=6000
config.Consumer.Group.Heartbeat.Interval = 2 * time.Second // heartbeat=2000 (1/3 关系)
config.Consumer.MaxProcessingTime = 20 * time.Second       // 业务最长 10s -> 配 20s

for {
	msg := <-consume() // 消费循环外层兜 panic: 一次异常不能带崩整个应用
	func() {
		defer func() {
			if r := recover(); r != nil {
				log.Printf("consume panic recovered: %v", r) // 记录+告警, 不退出进程
			}
		}()
		handle(msg)
	}()
}
// [经验] 隔离原则: 消费代码独立微服务 -> 业务发版不再牵连消费者重启
```

## 总结与追问预判
一句话记忆：**「降频不根除：重启靠隔离+recover，消费慢配 max.poll=业务×2，心跳 session=3×heartbeat（2s/6s），无故频繁查 GC」**。重平衡的五步流程与 STW 根因见 `148-rebalance-process`、`148-rebalance-cost.deep`（协议层治理：静态成员/增量协作）[边界]；消费速率与分区数匹配见 `147-consumer-rebalance`。常追问「session 调大有坏处吗」——答真死实例要等满 session 才被剔除，期间分区停摆，需在「误判容忍」与「故障剔除速度」间权衡；再追问「怎么监控重平衡」——答消费组 lag + rebalance 日志/指标告警，频繁触发先看 GC 再看发布记录。
