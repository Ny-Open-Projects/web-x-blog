# 810 哪些情况会触发 GC（四分类触发时机 + 调步算法）

> 分类：Go 运行时 / GC | 难度：L3 | 题型：总结题 | 频率：中 | 关键词：**GC 触发时机** / **堆内存增长** / **定时调度** / **手动触发** / **调步算法**
> 原文锚点：第 1~23 段「触发GC四因素：堆内存增长率/占用率、CPU占用率、定时调度(默认2分钟)、手动触发(runtime.GC/FreeOSMemory)；Go1.5调步算法算下次时机」

## 一句话总述
Go 的 GC 由后台调度按**调步算法（pacer，Go 1.5 起）**动态计算时机，触发条件分四类：① **堆内存增长**——上一周期剩余堆 + 新分配超过触发标记阈值，或分配时无足够空间；② **CPU 占用率**——调度会权衡 GC 的 CPU 消耗，避免拖慢业务；③ **定时调度**——默认约 2 分钟（forcegcperiod）强制一轮；④ **手动触发**——`runtime.GC()` / `debug.FreeOSMemory()`。

## 面试官视角
- 意图：考察对 GC 触发机制的体系化理解，而非只背"内存不够就回收"。
- P5 知四类触发（堆增长/CPU/定时/手动）；P6 知 pacer（Go 1.5）、定时默认约 2 分钟、堆增长基于"上次剩余+新分配"；P7 知自动 GC 异步并发、手动同步串行 STW、forcegcperiod 含义。
- 红旗：以为只有"内存满"才触发；或不知定时强制轮与手动触发的存在。
- 惊艳点：点出"触发由 pacer 按目标堆增长率动态算，而非固定阈值" `[边界]` 见 807/808/809（三色标记与 STW 演进）、811-go-runtime-allocator（分配器）、1006-setmemorylimit（软内存限制与 GOGC）。

## 主问答
**Q（面试官原话）：** 哪些情况会触发 GC？
**A：**
1. **堆内存增长**：上一 GC 周期结束时的存活堆，加上此后新分配的内存，超过 pacer 标注的触发标记大小即触发；分配时若无足够空间或达一定比例也会触发回收。
2. **CPU 占用率**：GC 本身耗 CPU，pacer 会考虑当前系统 CPU 占比，平衡回收频率与业务吞吐，避免 GC 把业务拖慢。
3. **定时调度**：GC 按时间间隔强制回收，默认约 2 分钟一轮（forcegcperiod）；并据触发比例动态调整频率。
4. **手动触发**：代码中调用 `runtime.GC()` 或 `debug.FreeOSMemory()` 可强制触发；自动调度是异步并发，手动则是同步串行（执行期间 STW）。

## 关键代码
```go
package main

import (
	"runtime"
	"runtime/debug"
)

func main() {
	// 手动触发：同步串行、STW（自动调度为异步并发）
	runtime.GC()
	// 手动触发并立即把已回收内存还给 OS（不保证成功）
	debug.FreeOSMemory()
}
```

## 总结与追问预判
- 触发四分类：堆增长（pacer 算）/ CPU 权衡 / 定时约 2 分钟 / 手动；自动异步、手动同步 STW。
- 预判：三色标记与 STW 演进 → 见 807/808/809；分配器 → 见 811-go-runtime-allocator；软内存限制与 GOGC → 见 1006-setmemorylimit、810-reduce-gc-frequency；手动触发差异 → 见 810-manual-gc-freeosmemory。
