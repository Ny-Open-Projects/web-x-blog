# 1258 Redis 持久化与主从复制中的过期键处理

> 分类：Redis / 持久化 | 难度：L2 | 题型：原理题 | 频率：中 | 关键词：**RDB 过期键**/**AOF DEL 追加**/**AOF 重写过滤**/**主从一致性**/**从库不主动删**

> 原文锚点：第 2~14 段「RDB 生成/载入 → AOF 删除追加与重写过滤 → 主从处理差异」

## 一句话总述
过期键在持久化与复制链路中的规则一句话版：**RDB 生成时不写入过期键，载入时主库检查不恢复、从库全量载入（等主库同步纠正）；AOF 因惰性/周期删除而追加 DEL 命令，重写时过滤过期键；主从场景从库从不主动删过期键，等主库发 DEL——一切规则都为「主从一致性」服务**。

## 面试官视角
这是「过期删除」与「持久化/复制」两个专题的**交叉题**，考的是规则矩阵的完整性：RDB 生成/载入×主/从、AOF 写入/重写×主/从，四块规则各有细节，漏一块就露馅。真正的杀招是追问「**从库为什么不主动删过期键**」——答出「保证主从一致、以主库为唯一删除决策点」，才算理解 Redis 主从的设计立场。

## 主问答
**Q（面试官原话）：** Redis 持久化时，对过期键会如何处理？

1. **RDB 生成**：快照保存全量数据，但**已过期的键不写入 RDB 文件**——生成前被惰性/周期删除掉的键自然不在，仍在内存但已过期的键也会被过滤。
2. **RDB 载入分主从**：**主库**载入时对每个键做时间检查，过期键不恢复；**从库**载入时**全部载入、忽略过期检查**——因为随后主从全量同步会用主库 RDB 覆盖从库，从库本地判断毫无意义且可能造成不一致。
3. **AOF 写入**：AOF 记录的是写命令。键被惰性删除（访问时）或周期删除（扫描时）时，Redis **向 AOF 追加一条 DEL 命令**——过期键不会凭空消失于 AOF，而是以 DEL 的形式被记录。
4. **AOF 重写**：重写基于当前数据库状态生成新 AOF，**已过期的键直接过滤**——新文件不含过期数据，这也是重写「压缩体积」的一部分。
5. **主从复制的过期键**：**从库不主动删除**——即使逻辑上已过期：① 读到过期键照常返回（3.2 前；3.2 起从库读也返回 nil，见 1255.md`），但**物理不删**；② 主库删除过期键后**向从库发送 DEL**，从库收到才删。目的：保证主从数据一致性——「过期」的判断权只在主库，避免主从时钟差异导致判断冲突。
6. **一致性总纲**：一个键在主库存在（未删），从库就必存在——即便它已逻辑过期；持久化与复制链路上的所有规则都是这一立场的推论。

## 版本与兼容性
| 主题 | 规则 | 说明 |
|------|------|------|
| RDB 生成 | 过期键不写入 | 全程有效 |
| RDB 载入 | 主库检查不恢复 / 从库全载 | 从库等主从同步纠正 |
| AOF | 删除时追加 DEL | 惰性/周期删除均触发 |
| AOF 重写 | 过期键过滤 | 新文件不含过期数据 |
| 主从 | 从库不主动删, 收主库 DEL 才删 | 一致性优先 |
| 从库读 | 3.2 起过期键返回 nil | 物理仍在, 语义不可见 |

## 关键代码
```go
// 模拟 RDB 载入时对「过期键」的决策矩阵 (规则示意, 与官方语义对齐)
type Role string

const (
	Master Role = "master"
	Slave  Role = "slave"
)

func loadKey(role Role, expired bool, key string) string {
	switch {
	case !expired:
		return key + " 恢复"
	case role == Master:
		return key + " 过期, 不恢复"
	default:
		return key + " 过期但全量载入 (等主库 RDB 同步覆盖)"
	}
}
```

[实测] 输出：master 对过期键「不恢复」；slave「全量载入，等主库 RDB 同步覆盖」——决策矩阵与规则一致。

规则矩阵总表：
```text
过期键处理规则矩阵 (持久化 × 主从)
├─ RDB 生成: 过期键不落盘
├─ RDB 载入: 主库 -> TTL 检查, 过期不恢复
│            从库 -> 全部载入 (等主库 RDB 同步覆盖)
├─ AOF 写入: 惰性/周期删除时追加一条 DEL 命令
├─ AOF 重写: 基于当前状态生成, 过期键直接过滤
└─ 主从复制: 过期判断权只在主库
    ├─ 主库删除 -> 向从库广播 DEL
    └─ 从库从不主动删 (即便逻辑过期)
        -> 目的: 主从时钟差异下的一致性
```

## 总结与追问预判
核心：**RDB「生成不写、载入主查从不查」；AOF「删时追加 DEL、重写过滤」；主从「从库从不主动删、收 DEL 才删」——总纲是主从一致性**。追问常拐回两个母专题：过期删除策略本体（惰性+周期、25% 阈值）见 1255.md`/`1256-periodic-scan-internals.deep.md`，三种持久化机制本体见 1253.md`/`1253-aof.md`/`1253-hybrid.md`/`1253-aof-rewrite.md`。

## ⚠️ 原文纠错
1. 术语核校： [经验] 原文「IOF/LOF/LDF/ROF」均为 **AOF** 的音转；「重复器/重复」=从库（slave/replica）；「数据」多处音转为「质队/键值对」，已归一。
2. 事实核校： [经验] 原文说「从库读过期键时『照常处理这个命令』」并暗示客户端能拿到值——需补版本边界：**3.2 起从库读到逻辑过期的键会返回 nil**（物理不删但语义不可见）；「客户端拿不到值」是 3.2+ 的行为，原文未给版本边界易误导。另原文末段「过期的键值不会被加载到内存」仅对**主库载入 RDB** 成立，从库载入是全量载入，前文规则与末段总结自相矛盾，以规则矩阵为准。
