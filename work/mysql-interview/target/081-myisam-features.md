# 081 MyISAM 的特点与适用场景

> 分类：存储引擎 | 难度：L2 | 题型：八股题 | 频率：中 | 关键词：**堆表** / **表级锁** / **MYD/MYI** / **myisampack**
> 原文锚点：第 60~80 段「MyISAM 存储引擎是一种非事务的存储引擎…数据呢是以堆表的方式来进行存储的…使用的是表级锁」

## 一句话总述
MyISAM = **非事务 + 堆表 + 表级锁**：索引叶子节点直指**物理地址**（少一次回表查找，查询性能好），但**读写互相阻塞**，适合**读远大于写**的场景。

## 面试官视角
- **考察意图**：从"为什么现在不用 MyISAM 了"反推你对锁粒度与一致性的理解。
- **P5** 知道它不支持事务 / **P6** 能说清堆表与表锁的后果 / **P7** 能讲"索引叶子指向物理地址"这个性能点，以及压缩表、REPAIR TABLE 这类运维手段。
- **红旗**：① "MyISAM 查询快所以适合高并发"；② 忘了崩溃后易损坏需修复；③ 不知道 8.0 已无 .frm。
- **惊艳点**：MyISAM 的 COUNT(*) 无 WHERE 时可**直接返回行数** `[经验]`，这是它少数仍被提及的优势。验证：大表上对比 InnoDB 的 COUNT(*)。

## 主问答
**Q（面试官原话）：** MyISAM 和 InnoDB 比，有什么本质区别？

**A：**
1. **先给结论**：三件事——**不支持事务**、**表级锁**、**堆表存储**。
2. **再给机制**：堆表意味着数据**没有特定顺序**、不存在聚簇索引，索引叶子节点直接指向**数据的物理位置**，因此索引查找**不需要二次查找**，单纯查询性能上有优势；但表级锁导致读会阻塞写、写也会阻塞读，并发写混合场景直接崩。
3. **最后给边界**：文件层面数据存 **.MYD**、索引存 **.MYI**（8.0 起 .frm 已并入数据字典）；它支持 **B 树 + 空间索引 + 全文索引**（InnoDB 到 5.6 才有全文、5.7 才有空间索引），还可用 `myisampack` 压缩、用 `CHECK TABLE` / `REPAIR TABLE` 检查修复。

**加分层**：MyISAM 常见故障是**索引文件损坏**，典型处理就是 `REPAIR TABLE`；这也是它缺乏崩溃恢复能力的直接代价。

## 追问链
| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | 支持事务吗 | 概念 | 不支持 | 换题 → 不及格 |
| L2 | 锁粒度 | 机制 | 表级锁 | 判 P5 |
| L3 | 为何查询快 | 原理 | 叶指物理地址无回表 | 判 P6 |
| L4 | 适合什么场景 | 决策 | 读多写少、非事务 | 判 P6+ |
| L5 | 崩了怎么办 | 运维 | REPAIR TABLE | 答上判 P7 |

## 版本与兼容性
| 结论成立版本 | 变化点 | 现在该怎么答 |
|---|---|---|
| ≤ 5.5 | 默认引擎 | 老系统存量表 |
| 5.6 / 5.7 | mysql 系统库仍有 MyISAM 表 | 不新建 |
| 8.0 | .frm 取消，并入数据字典 | 文件结构说明需区分版本 |

## 关键代码
```sql
CREATE TABLE t_myisam (id INT, c1 VARCHAR(20)) ENGINE=MyISAM;
CHECK TABLE t_myisam;                 -- 检查，异常时报错
REPAIR TABLE t_myisam;                -- 修复（索引文件损坏时）
```

```bash
# 压缩表（-b 先备份为 .OLD，-f 强制执行）
myisampack -b -f /data/mysql/stock/t_myisam
```

## ⚠️ 原文纠错
原文称"MyISAM 查询性能一直好于 InnoDB"，这是**单指纯索引查找路径**的情形，且有前提（无并发写争用、不要求事务），卡面已限定为"单纯查询性能上有优势"。原文"数据文件和索引分别存储为 MYD/MYI"正确；未提及 8.0 取消 .frm，卡面已补。核对范围：第 60~100 段。

## 总结与追问预判
- MyISAM：**非事务 + 表锁 + 堆表**，读多写少可用，并发写不行。
- 运维工具：`myisampack` 压缩、`REPAIR TABLE` 修复。
