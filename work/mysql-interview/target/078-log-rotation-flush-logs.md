# 078 FLUSH LOGS 与日志轮转：怎么切、什么时候切

> 分类：日志类 | 难度：L2 | 题型：工程题 | 频率：中 | 关键词：**FLUSH LOGS** / **max_binlog_size** / **轮转** / **慢日志切割**
> 原文锚点：第 415 段「同样我们先来刷新一下我们的日志，然后重新生成一个二进制日志」

## 一句话总述
`FLUSH LOGS` 手动**关闭当前日志并开新文件**（binlog 序号 +1、慢日志/错误日志重新打开）；binlog 还会在达到 `max_binlog_size` 时**自动轮转**。

## 面试官视角
- **考察意图**：日志不是越攒越大越好，看你会不会"切文件"来定位与回收空间。
- **P5** 知道 FLUSH LOGS / **P6** 知道 binlog 自动轮转阈值 / **P7** 能讲清**轮转 ≠ 清理**（切出来的旧文件仍在磁盘上），以及慢日志切割要**先改名再 FLUSH**。
- **红旗**：① 以为 FLUSH LOGS 会删日志；② 切慢日志直接 `rm` 当前文件（句柄还在，空间不释放）；③ 把 max_binlog_size 当成"精确上限"。
- **惊艳点**：事务不会被切到两个文件——**一个大事务会让当前 binlog 超过 max_binlog_size** `[源码]`。验证：跑一个大事务后看文件大小。

## 主问答
**Q（面试官原话）：** 我想把慢查询日志按天切开归档，怎么做？

**A：**
1. **先给结论**：**先给文件改名，再 `FLUSH LOGS`**（或 `FLUSH SLOW LOGS`），让 MySQL 重新打开原路径的新文件。
2. **再给机制**：MySQL 启动时打开日志文件并持有**文件句柄**，直接 `rm` 只是删了目录项、句柄仍在，**磁盘空间不会释放**、日志也继续往已删除的 inode 写；`FLUSH LOGS` 才会关闭并重开句柄。
3. **最后给边界**：binlog 轮转由 `max_binlog_size`（默认 1GB `[经验]`）触发，但**单个事务不会跨文件拆分**，所以文件可能超过阈值；轮转只管"切"，**回收空间要配合 PURGE**（见 077）。

**加分层**：原文演示里每次做对比实验前都先 `FLUSH LOGS`，目的就是**让本次操作落到独立的新文件**里，这是读 binlog 的实用习惯。

## 关键代码
```sql
FLUSH LOGS;                 -- 切 binlog 并重开慢日志/错误日志
FLUSH SLOW LOGS;            -- 只切慢查询日志
SHOW VARIABLES LIKE 'max_binlog_size';
SHOW BINARY LOGS;           -- 确认新文件已生成
```

```bash
# 慢日志按天归档（logrotate 或手工）：先改名，再通知 MySQL 重开
mv /data/mysqllog/slow.log /data/mysqllog/slow.log.$(date +%F)
mysql -uroot -p -e "FLUSH SLOW LOGS;"
```

## ⚠️ 原文纠错
原文只在演示中多次出现"刷新日志重新生成一个二进制日志"，未解释其原理与"轮转≠清理"的区别，卡面补充的 `max_binlog_size` 默认值、句柄与 `rm` 的坑属于通用实践，标注 `[经验]`。机翻「flashlog」还原为 `FLUSH LOGS`。核对范围：第 415 段及前后演示。

## 总结与追问预判
- 切文件的正确顺序：**改名 → FLUSH LOGS**。
- 轮转只切不删，空间回收靠 PURGE。
