# 096 异步复制的事务时序与丢数据风险

> 分类：架构/复制 | 难度：L2 | 题型：事故题 | 频率：高 | 关键词：**异步复制** / **事务丢失** / **从库间不一致**
> 原文锚点：第 71~87 段「MySQL 的主从复制是一种异步复制…不但不能保证主从数据同步，甚至两个从之间数据也不是同步的」

## 一句话总述
异步复制下主库写完 binlog 就返回客户端成功，**不等从库确认**；此时主库宕机，尚未传走的 binlog 事件即永久丢失。

## 面试官视角
- **考察意图**：是否理解「返回成功」与「数据已冗余」不是一回事，这是选型半同步的前提。
- **P5** 知道复制是异步的 / **P6** 画出时序并指出丢失窗口 / **P7** 补上「两个从之间也不一致」与「异步复制不等于高可用」。
- **红旗**：「主从复制就是高可用」；「主库提交成功从库一定已有」；只提延迟不提丢事务。
- **惊艳点**：一主两从下两个从各自独立拉取，**彼此进度也不同**，「切到任一从库都一样」是错误假设 —— 验证：同一时刻在两台从库执行 `SHOW REPLICA STATUS`，对比 `Retrieved_Gtid_Set` 与 `Executed_Gtid_Set`（8.0.36 `[经验]`）。

## 主问答
**Q：主库返回更新成功了，能认为数据已经同步到从库了吗？**
**A：**
1. **先给结论**：**不能**。异步复制下主库把变更写进 binlog 并提交后就返回客户端，从库拉取与回放都在之后发生。
2. **再给机制**：时间线是「主库执行 → 写 binlog → 提交 → 返回客户端」在前，「IO 线程拉走 → 写 relay log → SQL 线程回放」在后，两段无等待关系。
3. **最后给边界**：丢失窗口正是这两段的间隔——主库在此期间宕机且 binlog 未传出，已提交的事务在新主上不存在；且各从库进度不同，切换要挑数据最全的那台。
**加分层**：这正是半同步要关闭的窗口（见 097）。
