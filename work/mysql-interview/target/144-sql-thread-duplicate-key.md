# 144 SQL 线程报错 1062 主键冲突的成因

> 分类：复制/排障 | 难度：L3 | 题型：事故题 | 频率：高 | 关键词：**1062** / **主键冲突** / **从库宕机** / **relay log 位点**
> 原文锚点：第 146~152 段「IO 线程状态是正常的，但 SQL 线程的状态则变为了 No…表中出现了主键冲突」

## 一句话总述
**IO 正常、SQL 线程 No** 说明日志拉到了但回放不了；主键冲突（1062）只有两类成因——**从库被人为写入**，或**从库宕机后重复回放了一段日志**。

## 面试官视角
- **考察意图**：能否从"哪个线程坏了"反推故障域，这是复制排障的基本功。
- **P5** 会看两个线程状态 / **P6** 能区分两类成因 / **P7** 能说出 relay log 位点丢失的机理与预防参数。
- **红旗**：① 不看错误信息直接跳过；② 只想到人为写入，漏掉宕机重复回放；③ 跳过之后不做校验。
- **惊艳点**：从库崩溃时**已回放的位点可能没来得及落盘**，重启后从旧位点重放，就会撞上已存在的行 `[经验]`。

## 主问答
**Q：从库 SQL 线程报主键冲突，可能是什么原因？**
**A：**
1. **先给结论**：两类——从库上被人为写入了同主键数据；或从库曾宕机，重启后**重复回放**了已执行过的日志事件。
2. **再给机制**：复制位点信息默认保存在**文件**中，宕机时可能丢失最新位点；重启后从稍早的位点继续回放，已插入的行再次插入即触发 1062。
3. **最后给边界**：这两类的处置不同——人为写入要清掉多余数据，重复回放要确认重放范围；**不能一律跳过**。
**加分层**：把位点存进事务表并开启崩溃恢复（5.6+ 的 `relay_log_info_repository=TABLE` + `relay_log_recovery=ON`）可从根上避免第二类 `[经验]`。
