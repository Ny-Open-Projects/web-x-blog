# 083 Archive 引擎：只插不改的高压缩归档

> 分类：存储引擎 | 难度：L2 | 题型：八股题 | 频率：低 | 关键词：**Archive** / **zlib 压缩** / **只支持 INSERT/SELECT** / **归档**
> 原文锚点：第 155~180 段「Archive 存储引擎会缓存所有的写操作，并利用 zlib 压缩对插入的行进行压缩…只能进行 insert 和 select 操作」

## 一句话总述
Archive = **只支持 INSERT 与 SELECT**（不支持 UPDATE/DELETE）、用 **zlib 压缩**写入行，比 MyISAM 省约 75% 空间，只能建**一个自增列索引**，专供**日志与历史归档**。

## 面试官视角
- **考察意图**：看你会不会按"写一次、读很少、绝不改"的数据特征选引擎。
- **P5** 知道它只能插查 / **P6** 能说出压缩率与索引限制 / **P7** 会把它和"冷数据归档 / 日志采集"场景对上，并知道删除需要整表处理。
- **红旗**：① 当成可更新的业务表；② 想建第二个索引；③ 以为压缩无代价（写入要缓冲、查询要解压）。
- **惊艳点**：Archive **没有 undo/redo 一类事务开销且行级压缩**，适合"只追加"的审计流水 `[经验]`。验证：同量级数据对比三引擎的 `.ibd`/`.ARZ` 文件体积。

## 主问答
**Q（面试官原话）：** 有几亿行日志只写不查不改，怎么存最省？

**A：**
1. **先给结论**：用 **Archive** 引擎，压缩率高、磁盘省，只允许 INSERT 和 SELECT。
2. **再给机制**：它**缓存所有写操作**再用 zlib 压缩插入的行，同样数据量比 MyISAM 约小 75%、比 InnoDB 约小 23% `[实测口径以原文为准]`；执行 UPDATE/DELETE 会直接报"引擎不支持该操作"。
3. **最后给边界**：索引上**只允许一个**，且必须建在**自增 ID 列**上，再建第二个会报错；所以查询条件基本只能走主键，不适合多维检索。要"删数据"只能整表清理或换引擎重建。

**加分层**：它把"不会再变"的业务前提**固化成引擎约束**——这本身就是一种数据治理手段，避免误更新历史数据。

## 关键代码
```sql
CREATE TABLE my_archive (
  id INT NOT NULL AUTO_INCREMENT,
  c1 VARCHAR(20), c2 VARCHAR(20),
  KEY (id)
) ENGINE=ARCHIVE;                  -- 自增列必须是索引列
INSERT INTO my_archive (c1,c2) VALUES ('a','b');
DELETE FROM my_archive WHERE id=1;  -- 报错：引擎不支持该操作
CREATE INDEX idx_c1 ON my_archive(c1);  -- 报错：最多只能有一个索引
```

## ⚠️ 原文纠错
原文压缩比例（比 MyISAM 小约 75%、比 InnoDB 小约 23%）属课程实测口径，卡面保留并标注来源为原文；不同数据分布下压缩率差异很大，面试答"高压缩"即可，不必背具体百分比。机翻「active」「lab 压缩」还原为 Archive、zlib 压缩。核对范围：第 155~185 段。

## 总结与追问预判
- Archive：**只插查 + 高压缩 + 单自增索引**，用于日志与历史归档。
- 数据一旦写入就不该改——引擎帮你兜底。
