# 050 每线程缓冲区与内存放大

> 分类：服务器配置 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**sort_buffer_size** / **join_buffer_size** / **按连接分配**
> 原文锚点：第 294~313 段「以上这几个参数全是被每个线程来进行分配的，如果我们有一百个连接，可能就会分配一百倍以上的内存」

## 一句话总述
`sort_buffer_size`、`join_buffer_size`、`read_rnd_buffer_size` 等都是**按线程（连接）分配**的，且**按需一次性分配满额**——值设大 + 连接多 = **内存成百倍放大**，是 MySQL OOM 的头号元凶。

## 面试官视角
- **考察意图**：这是本章最有含金量的性能题，看你能不能把"单个参数值"换算成"整机内存占用"。
- **P5** 知道这些是排序/连接缓冲区。
- **P6** 能说出"按每个连接分配"，100 连接 × 100MB = 约 10GB。
- **P7** 能区分**一次性分配满额**（sort/join/read buffer）与**按需分配**（read_rnd_buffer_size、`key_buffer_size` 全局）的差异，并给出内存预算算法。
- **红旗**：① 说"调大 sort_buffer_size 就能让排序更快，越大越好"；② 只算单连接不算并发；③ 把它们当成全局共享缓冲。
- **惊艳点**：`sort_buffer_size=100M` 且 100 个并发同时排序 → 占用约 **10GB** `[经验]` —— 验证：并发压测时观察 `SHOW STATUS LIKE 'Sort_merge_passes'` 与实例 RSS 增长。

## 主问答
**Q（面试官原话）：** 有批大查询排序很慢，把 sort_buffer_size 调到 100M 行不行？

**A：**
1. **结论**：**风险极高**。这类缓冲是**按线程分配**的，且查询需要排序时**立即分配满额**，不管实际用多少。
2. **机制**：100 个连接同时排序，就会占用 `100 × 100M ≈ 10G`；`join_buffer_size` 更狠——**一个查询关联多张表，每个关联都会分配一个**。
3. **边界**：`read_rnd_buffer_size` 同样按查询分配；而 `key_buffer_size` 是**全局共享**的（MyISAM 索引缓冲），不随连接放大。内存预算要按 **全局缓冲 + 每线程缓冲 × 最大连接数** 一起算。

**加分层**：调这些值的前提是**先优化 SQL 与索引**——缓冲区调优只是兜底，放大参数往往会先把实例打挂。

## 追问链
| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |

## 关键代码
```sql
SHOW VARIABLES LIKE 'sort_buffer_size';
SHOW VARIABLES LIKE 'join_buffer_size';
SHOW STATUS LIKE 'Sort_merge_passes';   -- 排序落盘次数，判断缓冲是否偏小
-- 内存粗算：全局缓冲 + (每线程缓冲之和 × max_connections)
```

## ⚠️ 原文纠错
原文"read_rnd_buffer_size 只会在需要时分配"与官方一致；补充原文表述不严谨处：`sort_buffer_size` / `join_buffer_size` 是**需要时一次性分配满额**，不是按实际用量分配，卡面已明确该边界。机翻音译（sortofthesize、joininbackset）已还原为 sort_buffer_size、join_buffer_size。

## 总结与追问预判
- 排序/连接缓冲 = **每线程、按需满额分配**，是最容易 OOM 的一类参数。
- 调优顺序：**先 SQL/索引，再考虑缓冲区**；内存要按并发数做预算。
