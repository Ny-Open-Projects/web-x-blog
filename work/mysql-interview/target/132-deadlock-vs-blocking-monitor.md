# 132 死锁与阻塞的区别，以及慢查询怎么盯

> 分类：管理监控 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**死锁回滚** / **阻塞等待** / **PROCESSLIST** / **慢查询**
> 原文锚点：第 41~50 段「无论两个事务怎样都不可能继续运行下去……MySQL 处理死锁的方式是在产生死锁的事务中选择一个回滚」

## 一句话总述
**阻塞**是一个事务等另一个释放锁（可自愈，但会拖垮性能）；**死锁**是互相持有对方要的锁，只能由 InnoDB **回滚其中一个**才能打破。

## 面试官视角
- **考察意图**：这是被混淆最多的一对概念，顺带考察有没有慢查询的日常治理机制。
- **P5** 能说出「死锁要回滚、阻塞只是等」/ **P6** 能说清 InnoDB 选**回滚代价小**（影响行数少）的事务 / **P7** 会补「死锁对吞吐影响小但要**监控频率**，频繁死锁说明业务访问顺序不一致」。
- **红旗**：「死锁会导致数据库挂掉」；「阻塞久了会自动回滚」；「有死锁就说明索引有问题」。
- **惊艳点**：`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段**只保留最近一次**死锁，历史死锁必须在 `innodb_print_all_deadlocks=ON` 时落错误日志（8.0.36 `[经验]`）。

## 主问答
**Q：死锁和阻塞有什么不一样？慢查询你们怎么监控？**
**A：**
1. **先给结论**：阻塞 = 单向等待，可能自行解除；死锁 = 循环等待，InnoDB 主动**回滚其中一个事务**打破环。
2. **再给机制**：InnoDB 按**回滚代价**（通常是影响行数少者）挑一个受害者回滚并报 1213；应用必须能捕获这个错误并重试，否则就是业务报错。
3. **最后给边界**：死锁本身对性能危害不大（秒级解决），真正要盯的是**死锁频率**；慢查询则靠两条路——定期分析慢日志，或查 `information_schema.PROCESSLIST` 里 `Time` 超过阈值的会话。
**加分层**：`PROCESSLIST` 是**瞬时快照**，慢日志才是完整记录；两者互补，别只留一个。

## 关键代码
```sql
-- 查正在跑且超过 60 秒的会话（8.0 推荐 performance_schema 版本）
SELECT id, user, host, db, command, time, LEFT(info, 80) AS sql_text
FROM performance_schema.processlist
WHERE command <> 'Sleep' AND time > 60 ORDER BY time DESC;
-- 死锁：开启全量落日志，否则只能看到最近一次
SET GLOBAL innodb_print_all_deadlocks = ON;
```

## ⚠️ 原文纠错
原文说「死锁对于数据库性能的危害并没有阻塞那么大」，判断正确，已保留并强化为「要盯频率而非单次」。但原文**未提到死锁历史只保留最近一次**、需开启 `innodb_print_all_deadlocks` 才能留存，已补为惊艳点与版本要点。机翻「chrislist / preciislist / informationschemmer」还原为 **`PROCESSLIST` / `information_schema`**。未发现其他技术错误。
