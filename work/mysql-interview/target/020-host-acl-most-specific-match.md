# 020 host 访问控制列表与最精准匹配

> 分类：用户管理 | 难度：L3 | 题型：排障题 | 频率：中 | 关键词：**最精准匹配** / **网段授权** / **权限不生效**
> 原文锚点：第 38~40 段「MySQL 会使用最精准匹配到的那个账号来进行授权」

## 一句话总述
登录时 MySQL 用**来源 IP 做最精准匹配**选账号：同名多 host 时命中**范围最窄**的那个，所以"给宽范围账号授了权却不生效"多半是被更精准的账号截胡。

## 面试官视角
- **考察意图**：看你是否被"授权不生效"真实折磨过，而不只是背过 GRANT。
- **P5** 知道一个用户名可以配多个 host。
- **P6** 能说清**最精准优先**，并用 `SHOW GRANTS FOR 'u'@'host'` 逐个核对。
- **P7** 能先用 `CURRENT_USER()` 定位生效账号，再决定改哪个账号。
- **红旗**：① 说多个同名账号的权限会合并；② 排障只看权限不看 host。
- **惊艳点**：`CURRENT_USER()` 返回**匹配后生效的账号**，`USER()` 返回客户端登录名，两者不一致就是踩坑现场 `[经验]` —— 验证：两条函数同执行对比结果。

## 主问答
**Q（面试官原话）：** 我给 `app@'%'` 授了全部权限，应用还是报权限不足，可能是什么原因？

**A：**
1. **结论**：极可能同时存在**更精准**的账号（如 `'app'@'10.0.0.1'`），登录命中的是它，你授给 `%` 的权限根本没被用到。
2. **机制**：MySQL 按来源 IP **最精准匹配**（越具体优先级越高），命中后**只用它、不合并**。
3. **边界**：host 由服务端按来源地址自动判定，客户端登录时不能指定；改动必须落在会被命中的那个账号上。

**加分层**：排障第一步永远是 `SELECT CURRENT_USER();`，再 `SHOW GRANTS FOR <该账号>`，而不是凭印象去改 `%`。

## 关键代码
```sql
SELECT USER(), CURRENT_USER();
SHOW GRANTS FOR CURRENT_USER();
SELECT user, host FROM mysql.user WHERE user = 'app' ORDER BY host;
```

## 总结与追问预判
- **最精准优先、权限不叠加**是"授权不生效"的第一嫌疑。
- 排障顺序：`CURRENT_USER()` → `SHOW GRANTS FOR` → 改命中的账号。
