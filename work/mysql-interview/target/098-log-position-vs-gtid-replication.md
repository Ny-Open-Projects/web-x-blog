# 098 基于日志点复制与基于 GTID 复制的选型

> 分类：架构/复制 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**日志点复制** / **GTID 复制** / **故障迁移** / **兼容性**
> 原文锚点：第 261~310 段「我们先要知道什么是基于日志点的复制、什么是基于 GTID 的复制，以及各自有什么特点」

## 一句话总述
**日志点复制**靠「binlog 文件名 + 偏移量」定位，**GTID 复制**靠全局事务 ID 定位；后者让故障迁移不用猜位点，代价是兼容性更窄。

## 面试官视角
- **考察意图**：有没有真的做过主从切换——「换主时位点怎么找」是分水岭问题。
- **P5** 知道有两种复制方式 / **P6** 说出各自定位依据与优劣 / **P7** 结合发行版混部与 MMM/MHA 支持情况给选型结论。
- **红旗**：「GTID 全面取代日志点」；「开了 GTID 就一定能和 MariaDB 互为主从」（见 006）；认为两种方式复制流程不同。
- **惊艳点**：两种方式**复制流程完全一样**，差别只在从库告诉主库「我同步到哪了」的表达方式 —— 验证：`CHANGE MASTER TO` 分别用 `MASTER_LOG_FILE/POS` 与 `MASTER_AUTO_POSITION=1`（8.0.36 `[经验]`）。

## 主问答
**Q：基于日志点的复制和基于 GTID 的复制该怎么选？**
**A：**
1. **先给结论**：**能用 GTID 就用 GTID**；只有跨发行版混部、或依赖 MMM 这类不再支持 GTID 的老架构时才退回日志点。
2. **再给机制**：日志点复制传的是「文件名 + 字节偏移量」，而同一事务在主从上记录的文件名与偏移量**并不相同**，换主时很难在新主上找到正确位点；GTID 复制传的是全局唯一事务 ID，主库一比就知道还差哪些事务，迁移只需挑「已执行 GTID 集最大」的那台当新主。
3. **最后给边界**：兼容性上日志点更宽——官方版、Percona、MariaDB 通用；GTID 只在官方版与 Percona 间互通，MariaDB 的 GTID 实现不同（见 006）。MMM 与 MHA 都支持日志点，MMM 因缺乏维护不支持 GTID `[经验]`。
**加分层**：GTID 还带来 `enforce_gtid_consistency` 约束——`CREATE TABLE ... SELECT` 一类语句会被直接拒绝。

|---|---|---|

## 关键代码
```sql
-- 日志点复制：必须给出文件名与偏移量
CHANGE MASTER TO MASTER_HOST='m1', MASTER_LOG_FILE='binlog.000012',
  MASTER_LOG_POS=154, MASTER_USER='repl', MASTER_PASSWORD='***';
-- GTID 复制：不需要位点，只需打开自动定位
CHANGE MASTER TO MASTER_HOST='m1', MASTER_USER='repl',
  MASTER_PASSWORD='***', MASTER_AUTO_POSITION=1;
```

## ⚠️ 原文纠错
原文称 MMM 不支持 GTID 复制，理由写成「存在的时间比较久」——更准确原因是 **MMM 已缺乏维护**，并非能力上不可能。机翻「热典/季节 d」还原为**日志点 / GTID**。

## 总结与追问预判
- 差别只在定位方式；GTID 赢在故障迁移，输在兼容性。
