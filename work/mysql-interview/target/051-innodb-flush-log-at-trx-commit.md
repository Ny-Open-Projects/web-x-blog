# 051 innodb_flush_log_at_trx_commit 三档

> 分类：服务器配置 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**redo 刷盘** / **0/1/2** / **宕机丢数据**
> 原文锚点：第 318~323 段「它控制了重做日志也就是 redo log 的写盘策略，安全性从 0 到 2 逐档提升」

## 一句话总述
`innodb_flush_log_at_trx_commit` 决定 **redo log 何时刷盘**：**1**（默认，每次提交刷盘，最安全）、**2**（每次提交写 OS 缓存，每秒刷盘）、**0**（每秒写并刷盘，最快最不安全）。

## 面试官视角
- **考察意图**：这是"数据安全 vs 性能"最经典的权衡题，必考。
- **P5** 知道有 0/1/2 三档，1 是默认。
- **P6** 能说清每档的刷盘时机与对应丢失窗口。
- **P7** 能指出 **`2` 只在 MySQL 崩溃时安全、OS 宕机仍会丢 1 秒事务**，并与 `sync_binlog` 搭配讲"双一配置"。
- **红旗**：① 说"设成 2 就完全不丢数据"；② 把 redo 刷盘和 binlog 刷盘混为一谈；③ 为了性能把它设为 0 却不说代价。
- **惊艳点**：真正的"不丢数据"要 **`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`** 双一组合 `[经验]` —— 验证：压测对比二者不同组合的 TPS 差异即可感受代价。

## 主问答
**Q（面试官原话）：** innodb_flush_log_at_trx_commit 设成 0、1、2 有什么区别？

**A：**
1. **结论**：**1** = 每次事务提交都把 redo 刷到磁盘（默认、最安全）；**2** = 每次提交只写入 OS 缓存，每秒刷盘一次；**0** = 每秒写缓存并刷盘一次。
2. **机制**：崩溃时的丢失窗口分别是——**1 基本不丢**；**2** 在 MySQL 宕机不丢、**OS 宕机可能丢约 1 秒事务**；**0** 宕机可能丢约 1 秒事务。
3. **边界**：它是**性能与持久性的取舍**——设为 0/2 能显著提升写吞吐，但必须业务能接受丢失窗口；金融类业务必须 1。

**加分层**：只调这一个参数不够，binlog 侧要配 `sync_binlog=1`，两者都开才是完整的"崩溃不丢"。

## 关键代码
```sql
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'sync_binlog';
-- 双一配置（最安全，写入性能有代价）
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
SET GLOBAL sync_binlog = 1;
```

## ⚠️ 原文纠错
原文"值为 2 时每次事务提交会把日志写入文件系统，MySQL 数据库宕机不会丢失事务，操作系统宕机则可能丢失 1 秒事务"——与官方一致，未发现技术错误。补充原文未展开的：完整不丢需配合 `sync_binlog=1`。机翻音译（SYNCDlog、引 ODB）已还原为 sync_binlog、InnoDB。

## 总结与追问预判
- **1 最安全、2 折中、0 最快**；值 2 在 OS 宕机时仍会丢约 1 秒事务。
- 完整"不丢"要 **redo + binlog 双一**。
