# 090 InnoDB 读不阻塞写

> 分类：存储引擎/事务 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**MVCC** / **非锁定读** / **排他锁** / **快照读**
> 原文锚点：第 406~426 段「InnoDB 的读是否会阻塞写呢…没有阻塞到客户端一对数据进行查询」

## 一句话总述
InnoDB 的**普通读不会被写阻塞**：写事务持有行排他锁时，读事务不申请锁，而是去 undo 日志取它可见的旧版本返回。

## 面试官视角
- **考察意图**：区分「背过 MVCC 四个字母」和「真动手做过实验」。
- **P5** 知道 InnoDB 读写不冲突 / **P6** 能复述两客户端实验并说出去 undo 取旧值 / **P7** 能补上「只有快照读不阻塞，当前读仍会等锁」。
- **红旗**：「InnoDB 读不加锁所以更快」；「MVCC 让所有读都不阻塞」；把 MyISAM 的表锁结论直接套到 InnoDB。
- **惊艳点**：同一行被写事务锁住时，另一会话普通 `SELECT` 立即返回旧值，而 `SELECT ... FOR UPDATE` 会挂起 —— 验证：两个会话各开事务，B 更新不提交，A 分别跑这两条语句（8.0.36 `[经验]`）。

## 主问答
**Q：InnoDB 里一个事务正在改这行，另一个事务查这行会被卡住吗？**
**A：**
1. **先给结论**：**普通 SELECT 不会**。写事务加了行排他锁，读事务照样立刻返回提交前的旧值。
2. **再给机制**：读事务发现该最新版本被别的活跃事务持有，就沿 undo 日志回退到对自己可见的版本再返回，整条路径**不申请任何锁**，因此不存在被阻塞的对象。
3. **最后给边界**：「不阻塞」只对**快照读**成立。`SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`、`UPDATE` 走当前读，必须抢锁，会一直堵到写事务提交或锁等待超时。
**加分层**：代价是长事务钉住旧版本不让回收，undo 表空间持续膨胀（见 091）。

## 关键代码
```sql
-- 会话 B：改，但先不提交
BEGIN;
UPDATE stock.stock SET num = 30 WHERE id = 1;  -- 持有行排他锁，旧值写入 undo

-- 会话 A：下面两条的对比就是本题判据
SELECT num FROM stock.stock WHERE id = 1;              -- 立即返回旧值，不等锁
SELECT num FROM stock.stock WHERE id = 1 FOR UPDATE;   -- 阻塞，直到 B 提交或超时
```
