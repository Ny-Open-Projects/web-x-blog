# 140 为什么改用 ROW 格式能消除主从差异

> 分类：复制/binlog | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**binlog_format** / **statement** / **ROW** / **不确定函数**
> 原文锚点：第 87~89 段「由于 statement 格式是在主从服务器上分别执行 SQL…改为使用 row 格式」

## 一句话总述
statement 记的是**SQL 语句**（两端各自再算一遍），ROW 记的是**行的实际变化**（从库直接应用），所以 ROW 天然不受不确定函数影响。

## 面试官视角
- **考察意图**：是否理解两种格式记录的"对象"不同，而不是只记得"ROW 更安全"。
- **P5** 知道 ROW 更稳 / **P6** 能说清"语句 vs 行变更" / **P7** 能指出 ROW 的代价与选型判断。
- **红旗**：① "ROW 一定更好"；② 举不出真正的不安全函数；③ 不知道 ROW 的日志量代价。
- **惊艳点**：**`NOW()` 在 statement 下其实是安全的**——binlog 会带时间戳；真正不安全的是 `SYSDATE()`、`UUID()` 这类 `[经验]`。

## 主问答
**Q：statement 格式为什么会造成主从数据不一致？改成 ROW 就好了吗？**
**A：**
1. **先给结论**：statement 把 **SQL 原句**记进日志，从库重放时再执行一次；遇到不确定函数就会算出与主库不同的值，改 ROW 可根治。
2. **再给机制**：ROW 格式记录的是主库**每一行的实际修改**，从库直接应用这些行事件，不再重算表达式，因此不存在"两端各算一遍"的偏差。
3. **最后给边界**：ROW 的代价是**日志体积显著变大**（一次 UPDATE 十万行就记十万条行变更），且 binlog 不再可读，排查时要配合 `binlog_row_image` 与解码工具。
**加分层**：如果仍要用 statement，就把不确定函数改成确定性写法（如用 `NOW()` 而非 `SYSDATE()`），这是折中方案。

```sql

SET GLOBAL binlog_format = 'ROW';
SELECT @@binlog_format, @@binlog_row_image;   -- FULL / MINIMAL / NOBLOB
```

## ⚠️ 原文纠错
原文把「取当前系统时间作为默认值的数据列」列为 statement 下的不一致来源，表述不够准确：默认值为 `CURRENT_TIMESTAMP` 的列在 statement 下由 binlog 携带时间戳，**实际是安全的**；真正不安全的是 `SYSDATE()`、`UUID()` 等。机翻中的格式名音译已还原。

## 总结与追问预判
- ROW 记行变更 → 天然等价；代价是日志膨胀。
