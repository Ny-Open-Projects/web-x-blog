# 095 主从复制工作原理与三个线程

> 分类：架构/复制 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**binlog** / **relay log** / **IO 线程** / **SQL 线程**
> 原文锚点：第 56~70 段「复制是由主服务器 master 端来完成的…从服务器读取中继日志中的事件并在从库上重放」

## 一句话总述
主从复制分三步：**主库写 binlog → 从库 IO 线程拉取成 relay log → 从库 SQL 线程回放**，涉及主库 dump 线程与从库 IO、SQL 两个线程。

## 面试官视角
- **考察意图**：能否把复制拆成可定位的阶段——线上排障第一步就是判断卡在哪一段。
- **P5** 说出三个步骤 / **P6** 点名 dump / IO / SQL 三类线程与职责 / **P7** 据此判断延迟卡在拉取还是回放。
- **红旗**：「从库直接读主库 binlog 执行」；把 IO 与 SQL 线程混为一谈；漏了主库必须开 binlog 这一前置条件。
- **惊艳点**：复制卡住看线程状态而非延迟数字——验证：`SHOW REPLICA STATUS` 的 `Replica_IO_Running` / `Replica_SQL_Running` 与 `Last_SQL_Error`（8.0.36 `[经验]`；8.0 起 `SHOW SLAVE STATUS` 更名）。

## 主问答
**Q：说一下 MySQL 主从复制是怎么工作的？**
**A：**
1. **先给结论**：三段流水线 + 三类线程，主库只负责写 binlog，其余都在从库侧完成。
2. **再给机制**：① 主库把变更记入 **binlog**（须提前开启，旧版本默认不开）；② 从库 **IO 线程**与主库建立普通客户端连接，主库起 **dump 线程**推送 binlog，从库写入本地 **relay log**；③ 从库 **SQL 线程**读 relay log 并重放——语句格式重放 SQL，行格式直接应用行变更。
3. **最后给边界**：relay log 与 binlog 格式一致；从库回放后是否再写自己的 binlog，取决于 `log_replica_updates`（见 075）。
**加分层**：这三段就是排障坐标——先判断事件卡在产生、传输还是回放。

## 关键代码
```sql
-- 8.0 用 replica 命名（5.7 为 SHOW SLAVE STATUS）
SHOW REPLICA STATUS\G
-- 关键判据：两个 Running 是否 Yes、SQL 线程 STATE 与 Last_SQL_Error
-- 主库侧确认 binlog 已开
SHOW VARIABLES LIKE 'log_bin';
```

## ⚠️ 原文纠错
原文称「由四个线程所执行的事件」「由 CQ 进程完成」，系 ASR 误识：复制共**三类**线程（主库 dump + 从库 IO、SQL），回放由 **SQL 线程**完成。已按实际架构更正。
