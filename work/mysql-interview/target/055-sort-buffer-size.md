# 055 sort_buffer_size 一次性全量分配

> 分类：服务器配置 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**sort_buffer_size** / **按需但全量** / **内存放大**
> 原文锚点：第 295~299 段「不是在连接初始化的时候就给缓冲区分配内存，而是在有查询需要做排序操作时才分配…一旦查询需要排序，MySQL 会立即分配该参数所指定大小的全部内存」

## 一句话总述
`sort_buffer_size` 是**每线程**的排序缓冲：**触发时才分配，但一分配就是全额**——100 个并发排序 × 100MB 就是 10GB，是 OOM 经典来源。

## 面试官视角
- **考察意图**：考"按需分配"的准确含义，以及你会不会做**并发内存乘法**。
- **P5** 知道是每线程排序缓冲 / **P6** 说清"延迟分配但全额占用" / **P7** 指出正解是加索引并知道 `Sort_merge_passes` 判据。
- **红旗**：① "为了排得快设成 100M"；② 认为不排序就不占内存所以随便设；③ 把排序慢一律归因于缓冲小。
- **惊艳点**：缓冲再大也救不了无索引大排序——超出就走磁盘归并，`Sort_merge_passes` 会涨 `[经验]` —— 验证：`SHOW GLOBAL STATUS LIKE 'Sort%';`

## 主问答
**Q（面试官原话）：** 大查询排序很慢，我把 sort_buffer_size 调到 100M 行不行？

**A：**
1. **先给结论**：不行。它是**每连接**分配，100 个并发排序就吃 10GB。
2. **再给机制**：**需要排序时**才分配（非连接建立时），但一旦需要就**立即全额分配**参数值，不看实际排多少行。
3. **最后给边界**：它只是**排序工作内存**，数据量超出就落盘做多路归并，瓶颈变成磁盘 IO 与扫描行数。有效手段是**用索引消除排序**、`LIMIT`、减少排序列宽。

**加分层**：`Sort_merge_passes / Sort_scan` 走高说明频繁落盘归并，但先看能否加索引，别先加内存。

## 关键代码
```sql
-- 判据：是否需要动这个参数
SHOW GLOBAL STATUS LIKE 'Sort_merge_passes';  -- 归并次数，持续上涨 = 频繁落盘
SHOW GLOBAL STATUS LIKE 'Sort_scan';          -- 由全表扫描触发的排序次数
SHOW GLOBAL STATUS LIKE 'Sort_range';         -- 由范围扫描触发的排序次数
SHOW VARIABLES LIKE 'sort_buffer_size';

-- 正解：让 ORDER BY 走索引，从执行计划确认没有 Using filesort
EXPLAIN SELECT id, name FROM t WHERE status = 1 ORDER BY create_time LIMIT 20;
-- key 命中索引 且 Extra 不含 "Using filesort" 才算消除排序
```

## ⚠️ 原文纠错
原文"一旦查询需要排序，MySQL 就会立即分配该参数所指定大小的全部内存"与官方描述一致，未发现技术错误。需补充原文未提的一点：它是**会话级**变量，单条大查询可以会话内临时调大（`SET SESSION sort_buffer_size`），避免全局放大——这是原文"不能设太大"结论下的实操出口。机翻音译（sortofthesize、p有时候、msql、十个g）已还原为 sort_buffer_size、有时候、MySQL、10GB。

## 总结与追问预判
- **延迟分配、全额占用**；先算 `并发 × 参数值` 再决定。
- 排序慢先查 `Using filesort`，加索引优先于加内存。
