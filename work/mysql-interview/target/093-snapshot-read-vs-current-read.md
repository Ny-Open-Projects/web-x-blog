# 093 快照读与当前读

> 分类：存储引擎/事务 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**快照读** / **当前读** / **FOR UPDATE** / **幻读**
> 原文锚点：第 406~409 段「对于修改操作需要在相关数据上加上排他锁，以保证这些数据在修改没有被提交前不会被其他事务读取」

## 一句话总述
**快照读**走版本链、不加锁、可能读到旧值；**当前读**读最新已提交版本并加锁——`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 都是当前读。

## 面试官视角
- **考察意图**：能否同时说对「MVCC 不阻塞」与「我会丢更新」这两件事。
- **P5** 知道 `FOR UPDATE` 会锁行 / **P6** 能分清两类读并说出各自可见性规则 / **P7** 能用它解释「先查后写」的丢更新与幻读，并给出正确写法。
- **红旗**：「MVCC 下所有读都不加锁」；「先 SELECT 判断再 UPDATE 是安全的」；把 RR 下快照读的无幻读直接套到当前读上。
- **惊艳点**：同一事务里 `SELECT` 与 `UPDATE ... WHERE` 看到的行集可能不同——先快照读判定「不存在」再插入，并发下会撞唯一键 —— 验证：两个会话同时跑「查无则插」，观察 duplicate key 报错（8.0.36 `[经验]`）。

## 主问答
**Q：都说 MVCC 读不加锁，那 `SELECT ... FOR UPDATE` 算什么？**
**A：**
1. **先给结论**：不带后缀的 `SELECT` 是**快照读**，读版本链不加锁；`FOR UPDATE`、`LOCK IN SHARE MODE`、`UPDATE`、`DELETE` 是**当前读**，读最新已提交版本并加锁。
2. **再给机制**：写操作必须先拿到行的最新版本再改，否则等于在别人的旧版本上覆盖写入，所以 DML 内部的读一律走当前读并加排他锁。
3. **最后给边界**：RR 下快照读靠 ReadView 天然看不到新插入的行，但当前读看得到，必须靠**间隙锁**才挡得住幻读——「RR 能防幻读」只对快照读无条件成立（见 094）。
**加分层**：凡是「先判断有没有、再扣减」的业务逻辑都必须用当前读，否则并发超卖。

## 关键代码
```sql
-- ❌ 典型超卖：快照读判定与后续扣减之间没有锁
BEGIN;
SELECT num FROM stock WHERE id = 1;           -- 快照读，看到旧值
UPDATE stock SET num = num - 1 WHERE id = 1;  -- 当前读，此时可能已 <= 0
COMMIT;

-- ✅ 把条件写进 UPDATE，用当前读 + 行锁一次判定
UPDATE stock SET num = num - 1 WHERE id = 1 AND num > 0;  -- 用 affected rows 判成败
```

## ⚠️ 原文纠错
原文只说「修改加排他锁、查询加共享锁」，未区分快照读与当前读，据此容易推出「普通查询也加锁」的错误结论。本卡按 InnoDB 实际行为补全两类读的划分，并标 `[经验]`。

## 总结与追问预判
- 读不加锁 ≠ 写不加锁；要最新值就必须当前读。
