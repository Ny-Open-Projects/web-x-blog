# 054 sync_binlog 与双一配置

> 分类：服务器配置 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**sync_binlog** / **双一** / **binlog 刷盘**
> 原文锚点：第 291~293 段「sync_binlog 设置了每写多少次缓存，就会让磁盘同步一次 binlog 日志…对于 master 服务器来说，最少设置为 1」

## 一句话总述
`sync_binlog = N` 表示**每 N 次 binlog 提交才 fsync 到磁盘**；主库取 `1` 与 `innodb_flush_log_at_trx_commit = 1` 组成「双一」，用一次 fsync 换崩溃不丢事务。

## 面试官视角
- **考察意图**：区分"写缓存"和"落盘"，看你是否懂持久化的真实代价与故障域。
- **P5** 知道主库设 1 / **P6** 说清 N=1 是每事务 fsync 且要配「双一」 / **P7** 能给出代价与从库放宽 + 半同步的取舍。
- **红旗**：① 说"设 1 没代价"；② 把它和 `innodb_flush_log_at_trx_commit` 混为一谈；③ 分不清进程崩溃与操作系统崩溃。
- **惊艳点**：`=1` 保证**进程崩溃不丢**，`=0/N` 时**操作系统崩溃**会丢最多 N 个已提交事务——故障域不同 `[经验]` —— 验证：`sync_binlog=0` 下 `kill -9 mysqld` 与断电对比 binlog 尾部。

## 主问答
**Q（面试官原话）：** 主库 sync_binlog 设成多少？设成 1 会不会很慢？

**A：**
1. **先给结论**：主库**至少 1**，与 `innodb_flush_log_at_trx_commit=1` 组成「双一」，是复制下不丢数据的标配。
2. **再给机制**：binlog 先写 OS 缓存，`sync_binlog=N` 表示每 N 次提交做一次 fsync；`N=0` 交给 OS，OS 崩溃可丢大量已提交事务。
3. **最后给边界**：代价是**每事务一次 fsync**，高并发下 TPS 明显下降；从库常放宽到 0/1000，主库靠半同步补一致性而非放松 fsync。

**加分层**：又快又不丢的正解是**组提交 + 好盘（NVMe）**降低单次 fsync 成本，不是把 N 调大。

## 关键代码
```sql
-- 双一核对（主库必须两个都是 1）
SHOW VARIABLES LIKE 'sync_binlog';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';

-- 在线调整（5.7+ 可动态，但需同时写配置文件防重启回退）
SET GLOBAL sync_binlog = 1;
SET PERSIST sync_binlog = 1;          -- 8.0 推荐

-- 从库放宽（无上游强一致要求时的常见取舍）
SET GLOBAL sync_binlog = 1000;
```

## ⚠️ 原文纠错
原文"binlog 通常都是先写到系统的缓存区，然后再同步到磁盘"正确；但"每写多少次缓存就让磁盘同步一次"表述易误解为**计数刷新**——实际语义是**每 N 次事务提交**触发一次 fsync。另原文说"值为 1 是最安全的"，需补一句：`sync_binlog=1` 单独并不等于不丢，必须与 `innodb_flush_log_at_trx_commit=1` 同时成立（两阶段提交的 redo/binlog 一致性）。机翻音译（SYNCDlog、dlog、master）已还原为 sync_binlog、binlog、主库。

## 总结与追问预判
- 主库**双一**；N>1 是用可靠性换吞吐，故障域是**操作系统崩溃**。
- 优化方向是**降低单次 fsync 成本**，不是放大 N。
