# 102 多线程并行复制的演进与前提

> 分类：架构/复制 | 难度：L3 | 题型：八股题 | 频率：中 | 关键词：**并行复制** / **LOGICAL_CLOCK** / **DATABASE** / **replica_parallel_workers**
> 原文锚点：第 690~695 段「使用多个 SQL 线程来对 relay log 进行恢复…5.6 的多线程复制是针对数据库级的」

## 一句话总述
并行复制就是**多个 worker 线程同时回放 relay log**；5.6 只能按库并行（单库无效），5.7 起按组提交并行才有普适收益。

## 面试官视角
- **考察意图**：会不会盲目开参数——「为什么开了并行复制延迟没降」是典型追问。
- **P5** 知道有并行复制开关 / **P6** 能说出 5.6 按库、5.7 按组的差异 / **P7** 能指出它仍达不到主库并发度，且有大事务串行化上限。
- **红旗**：「并行复制能让从库追平主库性能」；「worker 数设越多越好」；不知道 5.6 单库场景无效。
- **惊艳点**：并行度上限受**组提交**约束——主库并发低时 binlog 里本就没有可并行的组，worker 再多也是空转 —— 验证：调大 `replica_parallel_workers` 后对比 `Seconds_Behind_Master` 是否下降（8.0.36 `[经验]`）。

## 主问答
**Q：从库开了多线程复制，为什么延迟还是降不下来？**
**A：**
1. **先给结论**：多半是**版本与并行粒度不匹配**——5.6 的并行是**按库（DATABASE）**的，写压力集中在单库时等于没开。
2. **再给机制**：5.7 起 `slave_parallel_type=LOGICAL_CLOCK`，把主库**同一组提交**的事务视为可并行的一批，分发给多个 worker 回放，这才与库的数量无关 `[经验]`。
3. **最后给边界**：并行度上限受主库**组提交密度**限制，达不到主库原始并发；单个大事务仍只能由一个 worker 串行回放，所以它不能替代拆大事务（见 101）。
**加分层**：worker 数不是越大越好——线程开销与从库资源有限，一般按 CPU 核数与库表分布取值。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在怎么答 |
|---|---|---|
| 5.6~8.0（验证 8.0.36） | 5.6 引入 `DATABASE` 粒度；5.7 引入 `LOGICAL_CLOCK`；8.0 术语改 replica 前缀 | 按「5.7+ 才有普适收益」答 |

## 关键代码
```sql
-- 5.7/8.0 推荐配置（8.0 用 replica 前缀，5.7 为 slave 前缀）
SET GLOBAL slave_parallel_type = 'LOGICAL_CLOCK';
SET GLOBAL slave_parallel_workers = 4;
-- 保留在主库上的组提交信息，是并行判定的依据
SET GLOBAL binlog_group_commit_sync_delay = 0;   -- 调大可提高并行度，但会增加主库提交延迟
```

## ⚠️ 原文纠错
原文「在 MySQL 5.7 之后对多线程复制进行了优化，所以针对表进行多线程复制」——准确说法是 5.7 引入基于**组提交（LOGICAL_CLOCK）**的并行，可跨表并行，而非单纯的「按表」；已按实际机制更正并标 `[经验]`。

## 总结与追问预判
- 5.6 按库、5.7 按组；先确认版本再谈收益。
