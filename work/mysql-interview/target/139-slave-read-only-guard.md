# 139 从库只读防线：read_only 与 super_read_only

> 分类：复制/权限 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**read_only** / **super_read_only** / **SUPER 权限**
> 原文锚点：第 81~86 段「在 slave 实例中设置 read_only…5.7 之后增加了 super_read_only」

## 一句话总述
`read_only` 只挡**没有 SUPER 权限**的用户，MySQL 5.7 起补上 `super_read_only` 才能连 **SUPER 用户**一起挡住——两者叠加才是完整的从库只读防线。

## 面试官视角
- **考察意图**：知不知道 `read_only` 有个"SUPER 后门"，这是这道八股的分水岭。
- **P5** 知道设 `read_only` / **P6** 知道它挡不住 SUPER / **P7** 能说出开启顺序与复制线程不受影响的原因。
- **红旗**：① "开了 read_only 就没人能写"；② 不知道 `super_read_only` 的版本；③ 担心它会阻断复制。
- **惊艳点**：**复制的 SQL 线程以系统内部权限回放，不受 `read_only` 约束**——所以开只读不会中断复制 `[经验]`。

## 主问答
**Q：怎么防止有人误在从库上写数据？**
**A：**
1. **先给结论**：同时开启 `read_only` 与 `super_read_only`（5.7+），前者挡普通用户，后者补上 SUPER 用户的口子。
2. **再给机制**：`read_only=ON` 后，不具备 SUPER 权限的用户无法提交写命令；`super_read_only=ON` 进一步把具备 SUPER 的用户也禁掉，从库真正变成只读实例。
3. **最后给边界**：这两个开关**不影响复制回放**，SQL 线程照常应用日志；但它挡不住拥有 `SUPER` 且手动关闭开关的人，所以还要配合账号权限收敛。
**加分层**：开启顺序应为先 `read_only` 再 `super_read_only`；直接设后者在部分版本会被前者连带约束，需实测确认 `[存疑]`。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在怎么答 |
|---|---|---|
| 5.6 及更早 | 5.7 才引入 `super_read_only` | 5.6 只能靠 `read_only` + 不给业务账号 SUPER；5.7/8.0 两个都开 |

## 关键代码
```sql
-- 从库上执行：同时开启两道只读防线
SET GLOBAL read_only = ON;
SET GLOBAL super_read_only = ON;   -- 5.7+ 才有
SELECT @@read_only, @@super_read_only;
```
