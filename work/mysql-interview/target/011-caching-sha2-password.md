# 011 caching_sha2_password 与驱动兼容

> 分类：MySQL 8.0 新特性/安全 | 难度：L3 | 题型：事故题 | 频率：高 | 关键词：**caching_sha2_password** / **默认认证插件** / **驱动兼容**
> 原文锚点：第 282~287 段「8.0 默认认证插件改变、同密码密文不同、老客户端登录失败」

## 一句话总述
MySQL 8.0 将默认认证插件改为 **caching_sha2_password**：同密码每次密文不同、登录更快更安全；但**老客户端/驱动不支持会登录失败**——这是 8.0 迁移最高频的坑。

## 面试官视角
- **考察意图**：是否踩过/知道 8.0 认证变更的兼容性雷区。
- **P5** 知道 8.0 默认密码插件变了。
- **P6** 能说清密文不同 + 老驱动失败的现象与解法。
- **P7** 能讲迁移时如何平滑过渡（改回 mysql_native_password 或升驱动）。
- **红旗**：说「8.0 密码更不安全了」。
- **惊艳点**：点出「同密码密文不同」正是防字典破解的关键改进 `[源码]`。

## 主问答
**Q：MySQL 8.0 升级后应用连不上，可能什么原因？**
**A：**
1. **结论**：多半是 **caching_sha2_password** 默认认证插件导致旧驱动不支持；8.0 之前默认是 mysql_native_password。
2. **机制**：新插件同密码生成不同密文（防重复密文被破解），且登录走缓存认证更快；但 5.7 及更早的 JDBC/Connector 未实现该插件会拒绝连接。
3. **边界**：解法有二——升级客户端驱动到支持 8.0 的版本，或在服务端把用户改回 `mysql_native_password`（折中兼容）。
**加分层**：生产迁移应提前统一驱动版本，避免上线后大面积登录失败。
