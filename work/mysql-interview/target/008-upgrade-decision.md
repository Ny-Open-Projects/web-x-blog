# 008 升级决策：是否升级 MySQL

> 分类：运维/版本 | 难度：L3 | 题型：工程题 | 频率：高 | 关键词：**收益分析** / **风险评估** / **不为升级而升级**
> 原文锚点：第 127~156 段「分析升级收益（业务痛点/运维痛点）与风险（驱动/sql_mode/优化器）」

## 一句话总述
决定升级 MySQL 必须先算**收益**（解决业务痛点如主从延迟、或运维痛点如新监控视图）再算**风险**（JDBC 驱动、sql_mode 默认值、查询优化器变化）；**绝不能为升级而升级**。

## 面试官视角
- **考察意图**：是否有严谨的变更决策方法论，而非盲目追新。
- **P5** 能说出升级前要想清楚。
- **P6** 能列出收益与风险两个维度及具体例子。
- **P7** 能讲出真实升级故障案例与回滚预案。
- **红旗**：说「新版本肯定更好，直接升」。
- **惊艳点**：点出「performance_schema 在 5.6 初期开启反而拖慢短查询」这类反直觉风险 `[经验]`。

## 主问答
**Q：如何决定是否升级 MySQL？**
**A：**
1. **结论**：先评估**收益**再评估**风险**，两者都站得住才升；否则不升。
2. **机制（收益）**：解决业务痛点（如 5.6→5.7 多线程复制降主从延迟、8.0 只复制 JSON 修改部分）；或运维痛点（5.7 引入 sys 视图、8.0 增强监控）。
3. **边界（风险）**：JDBC 驱动需匹配、sql_mode 默认值变化致语句报错、查询优化器变化可能让索引失效、开启 performance_schema 在旧版反而损性能。
**加分层**：强调「升级必须解决真实痛点 + 充分测试 + 备回滚」。
