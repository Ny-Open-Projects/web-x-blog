# 097 半同步复制原理与超时降级

> 分类：架构/复制 | 难度：L3 | 题型：八股题 | 频率：高 | 关键词：**半同步** / **rpl_semi_sync** / **超时降级** / **AFTER_SYNC**
> 原文锚点：第 73~102 段「MySQL 5.6 引入了半同步复制的机制…超过等待确认的过期时间后，主从复制会从半同步降低为异步复制」

## 一句话总述
半同步让主库**提交后阻塞等待从库确认收到 relay log**，等不到就按超时降级为异步；它缩小的是丢事务窗口，不是零丢失。

## 面试官视角
- **考察意图**：能不能说清「半」在哪——保证的是**日志已传到从库**，不是**从库已回放**。
- **P5** 知道有半同步插件 / **P6** 说清等待点是收完 relay log 而非回放完成 / **P7** 指出 5.7 起默认 `AFTER_SYNC` 与 5.6 的 `AFTER_COMMIT` 差异。
- **红旗**：「半同步等于零丢失」；「半同步保证从库已应用」；不知道会超时降级。
- **惊艳点**：半同步只保证从库**收到**日志，从库仍可能没回放完，此时读从库照样读到旧值 —— 验证：半同步已生效时立即在从库查询，`Seconds_Behind_Master` 仍可能大于 0（8.0.36 `[经验]`）。

## 主问答
**Q：半同步复制是怎么减少数据丢失的？它和异步复制的差别在哪？**
**A：**
1. **先给结论**：主库在提交阶段**阻塞等待从库确认收到日志**后才返回客户端，把「已提交但 binlog 未传出」的窗口压到最小。
2. **再给机制**：从库 IO 线程把事件写入本地 relay log 后向主库发 ACK，主库收到才继续。5.7 起默认 `AFTER_SYNC`——先等 ACK 再让事务对客户端可见，避免 5.6 的 `AFTER_COMMIT` 下「主库已可见、从库还没有」的丢数据 `[经验]`。
3. **最后给边界**：主库不能无限等：`rpl_semi_sync_master_timeout` 超时后**自动降级为异步**，从库恢复后自动升回；所以它是「大概率不丢」而非「保证不丢」。
**加分层**：超时值要在「主库可用性」与「丢失窗口」之间权衡——设太大会让主库写入被从库拖垮。

## 关键代码
```sql
-- 主库：安装插件并设定超时（单位微秒，此处 500 毫秒）
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';
SET GLOBAL rpl_semi_sync_master_enabled = 1;
SET GLOBAL rpl_semi_sync_master_timeout = 500000;
-- 确认是否真的在半同步运行（clients 数应 > 0）
SHOW STATUS LIKE 'Rpl_semi_sync_master_status';
SHOW STATUS LIKE 'Rpl_semi_sync_master_clients';
```

## ⚠️ 原文纠错
原文只说「主的 commit 操作被堵塞，收到确认后才返回客户端」，未区分 `AFTER_SYNC` / `AFTER_COMMIT`；5.6 默认的 `AFTER_COMMIT` 下事务在主库已可见才等 ACK，存在主库可见而从库无日志的窗口。本卡按 5.7 起的默认行为补充并标 `[经验]`。

## 总结与追问预判
- 半同步 = 等日志落地从库 + 超时降级；保证收到、不保证已回放。
