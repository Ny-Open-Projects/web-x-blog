# 105 读负载与写负载的治理路径

> 分类：架构/扩展性 | 难度：L3 | 题型：设计题 | 频率：高 | 关键词：**读写分离** / **中间件** / **分库分表** / **写扩展**
> 原文锚点：第 919~948 段「如何解决数据库读写负载大的问题…要解决写负载大的唯一方法就是对数据库进行分库分表」

## 一句话总述
**读负载靠加从库 + 读写分离**解决；**写负载加从库无效**——所有写最终都要在各节点重放，唯一出路是**分库分表**。

## 面试官视角
- **考察意图**：能否区分「读扩展」与「写扩展」两条完全不同的路径，这是设计题的分水岭。
- **P5** 知道加从库能扛读 / **P6** 说清读写分离两种实现与取舍 / **P7** 指出复制与 MGR 都不减少写负载，并给出分片落地方式。
- **红旗**：「加从库能解决性能问题」（不分读写）；「用 MGR 集群提升写吞吐」；只谈分片不谈路由与全局 ID。
- **惊艳点**：异步复制与 MGR 都**不降低写负载**——每个写最终都要在所有节点各应用一次，所以它们是高可用方案而非写扩展方案 `[经验]`。

## 主问答
**Q：数据库压力大，你怎么扩展？读和写是一回事吗？**
**A：**
1. **先给结论**：**不是一回事**。读负载加从库 + 读写分离即可；写负载只能靠分库分表。
2. **再给机制**：读扩展——先挂若干从库并做好高可用，再让应用支持读写分离：可改程序直连（损耗最小），也可引入 ProxySQL / MaxScale 一类中间件（对应用透明但有转发开销）。
3. **最后给边界**：写扩展——分库分表后数据按规则散到多个实例，应用或中间层按同一规则路由；代价是跨库 JOIN、分布式事务、全局主键都要自己解决。
**加分层**：先判断瓶颈在读还是在写——写多读少时读写分离毫无意义（见 103）。
