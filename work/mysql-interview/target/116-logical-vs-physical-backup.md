# 116 逻辑备份与物理备份怎么选

> 分类：备份恢复 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**逻辑备份** / **物理备份** / **跨平台** / **恢复效率**
> 原文锚点：第 18~32 段「逻辑备份的结果通常是人工可读的 SQL 文件……物理备份是对数据库数据目录的直接备份」

## 一句话总述
**逻辑备份**导出的是 SQL 语句（可读、可跨平台跨版本、体积小），**物理备份**拷的是数据文件（快、适合大库、但移植性差）——选型就是「可移植性」与「速度/体积」的权衡。

## 面试官视角
- **考察意图**：会不会只说「用 mysqldump」，而说不出为什么大库要换物理备份。
- **P5** 能说出两者区别 / **P6** 能列出各自三个优缺点 / **P7** 会补「逻辑备份**适用所有引擎**（含 Memory 表），物理备份对 Memory **无意义**」。
- **红旗**：「物理备份可以直接跨版本恢复」；「逻辑备份更快」；「Memory 表用物理备份备份」。
- **惊艳点**：原文实测 **338GB 库逻辑备份压缩后仅占物理备份约 1/10 空间**（`[经验]`，课程作者环境）；逻辑恢复要重放 SQL，通常比备份更慢。

## 主问答
**Q：逻辑备份和物理备份有什么区别？你们生产用哪种？**
**A：**
1. **先给结论**：逻辑备份 = 导 SQL 文本（mysqldump / mysqlpump），物理备份 = 拷数据目录（XtraBackup / 企业版 backup）。小库用逻辑，大库用物理，两者常并存。
2. **再给机制**：逻辑备份结果是**可读的建表与插入语句**，所以能跨平台、跨版本、跨存储引擎，还便于压缩和长期留存；物理备份只拷文件，**不解析内容**，所以备份恢复都快，但要求**同版本、同平台、同目录结构**。
3. **最后给边界**：物理备份对 **Memory** 引擎无意义（数据在内存，重启即空）；逻辑恢复慢，还会把冷数据读进缓冲池。
**加分层**：生产常见组合是「物理全备 + 增量 + binlog 保底」，逻辑备份用于小库、单表导出和跨版本迁移。

## 关键代码
```sql
-- 逻辑备份前先确认哪些引擎不是 InnoDB（Memory 表必须走逻辑备份）
SELECT table_schema, table_name, engine FROM information_schema.tables
WHERE engine <> 'InnoDB' AND table_schema NOT IN ('mysql','sys','performance_schema');
```
```bash
# 逻辑备份（压缩后体积远小于物理备份）
mysqldump --single-transaction --master-data=2 -A | gzip > all.sql.gz
```

## ⚠️ 原文纠错
原文说物理备份「不能对 memory 这种存储引擎的表备份」——准确原因是 **Memory 表数据只存于内存，重启即丢**，物理拷文件拿不到数据；已按此重写。原文「逻辑备份集可移植性好、恢复效率低；物理备份移植性差」表述正确，保留。机翻中工具名与引擎名的音译写法已统一还原为标准术语。

## 总结与追问预判
- 逻辑 = 可移植、慢；物理 = 快、受版本平台约束。
