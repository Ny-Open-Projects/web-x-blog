# 092 共享锁与排他锁兼容矩阵

> 分类：存储引擎/锁 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**共享锁** / **排他锁** / **兼容矩阵** / **表锁**
> 原文锚点：第 406~413 段「对于修改操作需要在相关数据上加上排他锁…使用 MyISAM 的时候读操作和写操作会相互阻塞」

## 一句话总述
**排他锁与任何锁都不兼容，共享锁之间兼容**；MyISAM 只有表级锁所以读写互斥，InnoDB 用行级锁加 MVCC 才做到普通读写不互斥。

## 面试官视角
- **考察意图**：锁粒度与兼容性分不分得清，能否解释「同样是读，为什么有的引擎会堵」。
- **P5** 背得出 S 与 X 互斥 / **P6** 能画出兼容矩阵并点出锁粒度差异 / **P7** 能补上「MVCC 让普通读压根不申请锁，所以不在矩阵里」。
- **红旗**：「读锁和写锁可以一起加」；「InnoDB 的读也加共享锁」（那是 `LOCK IN SHARE MODE`）；「行锁一定优于表锁」。
- **惊艳点**：普通 `SELECT` 在 InnoDB 里**一把锁都不加**，所以读写不阻塞并不是兼容矩阵变宽松，而是它根本没进矩阵 —— 验证：`SHOW ENGINE INNODB STATUS` 的 TRANSACTIONS 段看不到纯 SELECT 的锁记录（8.0.36 `[经验]`）。

## 主问答
**Q：共享锁和排他锁的兼容关系是怎样的？为什么 MyISAM 读写会互相堵？**
**A：**
1. **先给结论**：X 与 X、X 与 S 都**互斥**；S 与 S **兼容**。
2. **再给机制**：MyISAM 只有**表级**锁，一次写就把整张表锁住，任何读都得排队，于是读写互相阻塞；InnoDB 是**行级**锁，只锁命中的那几行。
3. **最后给边界**：光有行锁还不够——同一行上的写锁照样会堵住要读它的读，InnoDB 靠 MVCC 让普通读**完全不加锁**才彻底不阻塞（见 090）。
**加分层**：行锁不是白拿的，加锁本身有开销，还会引入死锁与间隙锁；纯读多写少的场景，表锁反而更省。

SELECT * FROM t WHERE id = 1 FOR UPDATE;          -- X 锁

## ⚠️ 原文纠错
原文「排查锁」为 ASR 误识，还原为**排他锁**。另有一处因果错误：原文称「共享锁之间兼容，这就是为什么 MyISAM 读写会相互阻塞」——MyISAM 阻塞的真正原因是**表级锁粒度**，与共享锁兼容性无关，已按正确因果重写。

## 总结与追问预判
- S 与 S 兼容，其余互斥；粒度决定阻塞范围，MVCC 决定要不要加锁。
