# 133 CPU 冲高伴 QPS 下降的判读

> 分类：排障/性能 | 难度：L3 | 题型：事故题 | 频率：高 | 关键词：**CPU 100%** / **QPS 反降** / **曲线背离**
> 原文锚点：第 7~26 段「CPU 的占用率一度达到了百分之百…QPS 的值达到了最低」

## 一句话总述
CPU 冲高而 QPS 反降，说明有线程占着 CPU 却干不出活——**两条曲线背离**就是报警依据，优先往阻塞与慢查询查。

## 面试官视角
- **考察意图**：能否把两条监控曲线放在一起读，而不是单看某一个指标。
- **P5** 知道 CPU 高先查慢查询 / **P6** 能区分阻塞与慢查询的曲线差异 / **P7** 能补上"磁盘 IO 先打满"这条因果链。
- **红旗**：① "CPU 高就扩容"；② 把 QPS 下降归因于业务低峰却不看 CPU；③ 只提慢查询漏掉阻塞。
- **惊艳点**：过业务低峰后 QPS 本就该降，**CPU 却反升**才是真异常 `[经验]`。

## 主问答
**Q：凌晨数据库 CPU 冲到 100%，QPS 反而在掉，你第一反应查什么？**
**A：**
1. **先给结论**：低峰期 CPU 与 QPS 应同向下降，**背离**就意味着线程占着 CPU 不出活，先查阻塞与慢查询。
2. **再给机制**：每条正在执行的查询占一个 CPU 资源，大量阻塞或慢查询会把 CPU 占满而吞吐下降；磁盘非高速存储时 IO 先打满，线程进 IO 等待同样推高 CPU `[经验]`。
3. **最后给边界**：还要排除同机**其他服务**抢 CPU 与硬件故障（内存、磁盘损坏），这两类在 MySQL 内部查不到线索。
**加分层**：先花半分钟用系统命令确认 CPU 是不是 mysqld 吃掉的，再进 MySQL 内部，能省一半排查时间。

## 追问链
| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | CPU 高先看什么 | 概念 | 先确认进程归属 | 换题 |
| L2 | 阻塞与慢查询表现有何不同 | 机制 | 阻塞有锁等待、慢查询无 | 判 P5 |
| L3 | IO 打满为何推高 CPU | 因果链 | 线程进 IO 等待 | 判 P6 |
| L4 | 同机有其他服务怎么排 | 边界 | 按进程看占用 | 判 P6+ |
| L5 | 线上真排过吗 | 实战 | 讲监控曲线与结论 | 答上判 P7 |

## 关键代码
```sql
-- MySQL 侧先确认是否有长事务/阻塞源
SELECT trx_id, trx_started, trx_state, trx_rows_locked, trx_query
FROM information_schema.innodb_trx
WHERE trx_started < NOW() - INTERVAL 10 SECOND;
```

## ⚠️ 原文纠错
原文「每一个正在执行的 CPU 都会占用一个 CPU 资源」为机翻语病，应为「**每一条正在执行的查询**占用一个 CPU 资源」。其余结论与公认事实一致。

## 总结与追问预判
- 曲线背离 → 阻塞 / 慢查询 → 再排除外部服务与硬件。
