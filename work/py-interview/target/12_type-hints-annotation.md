# 12. 类型注解：提示而非检查

> 分类：版本差异/工程 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**type hints** / **__annotations__** / **mypy** / **PEP 484**
> 原文锚点：第 47~56 段「我们可以给变量加一个类型提示…主要起提示作用，并没有实现真正的类型检查」

## 一句话总述
类型注解是**写给工具与人的元数据**：解释器运行期**不做检查**，真正的校验靠 `mypy` 等静态检查器在 CI 里完成。

## 面试官视角
- **考察意图**：知不知道注解只是"半套"方案，以及怎么把它变成真正的防线。
- **P5** 知道能加注解 / **P6** 知道运行期不检查 / **P7** 能说清注解存在哪里、怎么接入 CI。
- **红旗**：① "加了类型注解就不会有类型错误"；② 以为解释器会拒绝错类型；③ 只写注解不跑检查器。
- **惊艳点**：注解会真实写进函数的 `__annotations__`，可运行期读取——它既是提示也是可用的元数据 `[经验]`。

## 主问答
**Q：Python 的类型注解能防止类型错误吗？**
**A：**
1. **先给结论**：**不能靠解释器**——注解只是提示，传入错误类型照样执行，直到某处操作失败才报错。
2. **再给机制**：注解按 PEP 484 引入，值被存进函数对象的 `__annotations__` 字典；真正的检查由 `mypy`、`pyright` 这类静态分析器完成 `[经验]`。
3. **最后给边界**：注解的价值在**IDE 提示 + CI 门禁**；如果只写注解不跑检查器，等于只买了一半的保险。
**加分层**：它最大的收益其实在**大项目可维护性**——正好对冲"动态语言重构难"这笔代价，这也是近年 Python 后端工程的标配。

## 追问链
| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | 注解怎么写 | 语法 | `def f(x: int) -> str` | 换题 |
| L2 | 运行期会检查吗 | 机制 | 不会 | 判 P5 |

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在怎么答 |
|---|---|---|
| 3.5 起（PEP 484） | 3.9 起内置泛型可直接写 `list[int]`；3.10 引入 `X | Y` | 现在按 3.5+ 语法答，新项目用 3.10+ 写法 |

## 关键代码
```python
def greet(name: str) -> str:
    return "hello " + name

print(greet.__annotations__)   # {'name': <class 'str'>, 'return': <class 'str'>}
print(greet(123))              # 运行期照样报错，但不是注解拦的
```
