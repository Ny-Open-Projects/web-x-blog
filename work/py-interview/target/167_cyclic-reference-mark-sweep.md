# 167. 循环引用与标记清除

> 分类：Python/内存 | 难度：L3 | 题型：原理题 | 频率：高 | 关键词：**循环引用** / **标记清除** / **可达性** / **内存泄露**
> 原文锚点：第 100~129 段「引用计数解决不了循环引用→内存泄露；a.append(b);b.append(a) 互引，del 后仍各为1；标记清除从根对象遍历可达图，不可达标灰清除」

## 一句话总述
**循环引用**（如 `a` 引用 `b`、`b` 引用 `a`）让双方的引用计数**永不归零**，引用计数无能为力，造成内存泄露；CPython 用**标记清除**从**根对象**出发遍历引用图，把**不可达**的孤立环标灰并回收。

## 面试官视角
- **考察意图**：是否理解"为什么引用计数有死角"以及标记清除如何补位。
- **P5** 能举例循环引用、说出标记清除"从根找可达" / **P6** 能讲清 del 后计数仍为 1、为何必须靠可达性分析 / **P7** 能说明标记清除只针对**容器对象**（只有容器能成环）、以及它会引入暂停（STW）代价。
- **红旗**：认为 `del a; del b` 一定释放循环引用的两个对象；或认为标记清除每时每刻都在跑。
- **惊艳点**：标记清除**只对容器对象**（list/dict/自定义对象等可能成环的）生效，原子类型（int/str）不会成环，所以不参与——这解释了为何 GC 开销可控 —— 验证：`gc.get_objects()` 返回的都是"可能成环"的容器 `[源码]`。

## 主问答
**Q（面试官原话）：** 引用计数不是能回收吗？为什么还会有内存泄露？怎么解决循环引用？

**A · 标准答案骨架：**
1. **先给结论**：`a→b`、`b→a` 互引时，即使 `del a; del b`，各自引用计数仍 **1→不为 0**，引用计数**无法回收**，形成泄露。
2. **再给机制**：**标记清除**从**根对象**（当前栈、全局变量）出发，沿引用关系遍历得到**可达集**；不在可达集内的孤立环被标为不可达并清除。
3. **最后给边界**：该过程**周期性**触发（非实时），且只对**容器对象**生效；实时释放仍靠引用计数，标记清除只兜底"环"。

**加分层**：引用计数处理"普通生死"，标记清除专门收拾"互相抱着死"的环——二者分工清晰 `[经验]`。

## 关键代码
```python
import gc
class Node:
    pass
a = Node(); b = Node()
a.other = b; b.other = a   # 循环引用
del a, b
print(gc.collect())         # 标记清除回收这对环对象 [实测]
```
