# 229. 系统设计回答框架：三大要素与延伸

> 分类：系统设计 | 难度：L3 | 题型：方法论+实战思路 | 频率：高 | 关键词：**三大要素** / **场景与限制** / **数据存储** / **算法模块** / **QPS 估算** / **扩展** / **容错**
> 原文锚点：第10章 10-1「回答框架三大要素：①场景与限制条件(问清使用场景/用户量/峰值与平均QPS,避免杀鸡用牛刀或需上缓存扛高并发) ②数据存储设计(按需求选型:关系型vs NoSQL,建表字段类型,索引设计,是否需要缓存;mysql+redis常可支撑) ③算法模块设计(接口定义参数与返回,算法/模型选型,时空权衡);延伸考点=扩展(性能QPS扩展/数据规模扩展)+容错(单点失败/多点失败/雪崩)」

## 一句话总述
**答系统设计题围绕"三大要素"展开**：① **场景与限制**（先问清场景、用户量、估算峰值/平均 QPS）；② **数据存储**（按需求做库选型、建表、索引、缓存）；③ **算法模块**（定义接口、选算法、做时空权衡）。延伸再看**扩展**（QPS/数据规模）与**容错**（单点/雪崩）。

## 面试官视角
- **考察意图**：是否在开口写方案前先"厘清需求、量化约束"，再结构化推进，而非凭直觉堆组件。
- **P5** 能说出三大要素名称 / **P6** 能对每个要素展开（QPS 估算方法、关系型 vs NoSQL 取舍、接口契约定义、时空权衡） / **P7** 能主动补"扩展（性能/数据规模）与容错（单点失败/雪崩）"的中高级延伸，并给出具体手段（缓存、分库分表、多副本）。
- **红旗**：跳过场景直接画架构图；不会算 QPS 就决定"上 Redis/分库"；把缓存当万能药不顾一致性。
- **惊艳点**：能强调"先估算再选型、避免杀鸡用牛刀"，并点出"单点失败→多副本/负载均衡、雪崩→降级熔断" `[经验]`。

## 主问答
**Q（面试官原话）：** 拿到一道系统设计题，你一般怎么回答？

**A · 标准答案骨架：**
1. **要素一 · 场景与限制条件**：先**反问面试官**使用场景、用户量、峰值/平均 QPS。QPS=每秒请求量；从 DAU/并发推算后才知道该"杀鸡用牛刀"还是轻量方案——量小则简单 MySQL，量达成千上万则需缓存扛并发 `[经验]`。
2. **要素二 · 数据存储设计**：按需求做**数据库选型**（关系型 vs NoSQL/文档型），再**建表**定字段与类型，并规划**索引**（是否加索引、怎么设计）与是否引入**缓存**。原文强调"现在很多业务 MySQL + Redis 就能支撑"，重点在**优化（索引/缓存）而非盲目换库"**。
3. **要素三 · 算法模块设计**：先定义**接口契约**（入参、出参），再选**算法/模型**，并做**时空权衡**（以时间换空间 or 以空间换时间）。定下存储与算法后即可编码实现。
4. **延伸 · 扩展与容错**（中高级追问）：**扩展**分两类——性能 QPS 扩展（用户多/并发高怎么办）、数据规模扩展（存储不够怎么办，如分库分表）；**容错**——如何处理单点失败、多点失败乃至**雪崩**（降级、熔断、多副本）`[经验]`。

**加分层**：能用一句"系统 = 服务 + 存储，正如程序 = 算法 + 数据结构"收束三大要素；并能把短网址（见后续实战）套进这套框架自洽演示。

## 追问链
| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | 回答框架有几步 | 基本认知 | 场景/存储/算法三要素 | 换题 → 不及格 |
| L2 | 怎么估 QPS | 量化能力 | DAU→峰值QPS，决定选型 | 判 P5 |

| L5 | 扩展与容错 | 高阶 | QPS/数据扩展+雪崩降级 | 答上判 P7 |
