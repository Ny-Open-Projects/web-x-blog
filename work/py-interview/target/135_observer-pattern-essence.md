# 135. 观察者模式与发布订阅：一对多通知，解耦生产者与响应者

> 分类：编程范式/设计模式 | 难度：L2 | 题型：八股题 | 频率：高 | 关键词：**观察者模式** / **发布订阅** / **解耦** / **回调**
> 原文锚点：第 4~5 段「观察者模式：对象改变时观察者执行相应动作；发布订阅是最常用实现」

## 一句话总述
**观察者模式**定义**一对多**依赖：一个**发布者**状态变化，所有**订阅者**自动收到通知并执行各自回调；**发布订阅（Pub/Sub）**是它的常用实现，典型用于**解耦**业务逻辑。

## 面试官视角
- **考察意图**：考你能否分清"观察者（紧耦合，直接持有订阅者列表）"与"发布订阅（经中间 broker，双方互不认识）"——很多人把两者画等号。
- **P5** 能说出"一个变化、多方响应" / **P6** 能区分**观察者**（发布者直接持有订阅者引用）与**发布订阅**（经消息总线/主题，发布订阅双方解耦）/ **P7** 能指出观察者模式的**内存泄漏风险**（订阅后忘了取消导致对象无法回收）与**通知顺序不确定** `[经验]`。
- **红旗**：① 把发布订阅和观察者完全等同（缺了"中间 broker 解耦"这一层）；② 说不出怎么取消订阅；③ 忽略悬挂引用导致的泄漏。
- **惊艳点**：经典观察者里发布者**直接持有**订阅者列表（紧耦合）；Pub/Sub 多了**中间代理**使发布方不认识订阅方。验证：观察者模式 `remove` 后不再收到通知 `[实测]`。

## 主问答
**Q：观察者模式是什么？和发布订阅一样吗？**
**A：**
1. **结论**：观察者 = 一对多通知，发布者状态变，订阅者自动响应；**发布订阅**是它最常见的实现形式。
2. **机制**：发布者维护订阅者列表，事件发生时遍历调用各订阅者的**回调**；发布订阅在此基础上引入**中间 broker**（主题/信道），发布方与订阅方互不直持引用。
3. **边界**：纯观察者**耦合更紧**（发布者直接持有订阅者）；Pub/Sub **更解耦**（经总线），适合跨模块/跨服务。
**加分层**：实际工程里还常用 `weakref` 存订阅者，避免忘记取消订阅造成的内存泄漏。

## 关键代码
```python
class Publisher:
    def __init__(self): self._subs = []
    def subscribe(self, fn):   self._subs.append(fn)     # 注册回调
    def notify(self, data):
        for fn in self._subs: fn(data)                   # 一对多通知
```

## ⚠️ 原文纠错
原文"观察者模式：对象发生改变时观察者执行相应动作；发布订阅是最常用的实现方式"——准确，予以保留。机翻"release"指提供发布订阅能力的**库/机制**（如 Redis 的 pub/sub），"parisiser"=**publisher（发布者）**。原文未区分"观察者（紧耦合）"与"发布订阅（经 broker 解耦）"这层关键差异，已在机制与惊艳点补充 `[经验]`；也未提取消订阅与泄漏风险，已在红旗与 P7 补充。无事实错误，仅术语音译需还原。
