# 52. 什么样的对象才能做字典的 key

> 分类：算法与数据结构/字典结构 | 难度：L2 | 题型：八股题 | 频率：中 | 关键词：**可哈希** / **__hash__** / **__eq__**
> 原文锚点：第 98~101 段「如果想作为字典的 k 的话，必须是可哈希的，但是可变对象它是不可哈希的」

## 一句话总述
能做 dict 键的对象必须**可哈希**：实现 `__hash__` 且生命周期内哈希值不变，并与 `__eq__` 保持一致；**可变容器（list / set / dict）一律不可哈希**。

## 面试官视角
- **考察意图**：是否把"可哈希"这个前置条件讲成机制，而不只是背一句"list 不能当 key"。
- **P5** 知道 list 不能当 key / **P6** 说出 hash+eq 契约 / **P7** 能解释"自定义对象默认可哈希"及其坑。
- **红旗**：① 说"tuple 一定能当 key"（套了 list 就不行）；② 以为改了 `__eq__` 还能保持默认 `__hash__`；③ 不知道哈希值必须稳定。
- **惊艳点**：自定义类一旦定义 `__eq__` 而未定义 `__hash__`，`__hash__` 会被置为 `None`，实例立刻变成**不可哈希**。验证：`A.__hash__` 为 None `[实测]`。

## 主问答
**Q：为什么 list 不能作为字典的 key，tuple 却可以？**
**A：**
1. **先给结论**：dict 基于哈希表，key 必须**可哈希**；可变对象内容随时变、哈希值随之变，所以 list / set / dict 都不可哈希。
2. **再给契约**：可哈希 = 有 `__hash__` 且**哈希值在整个生命周期内不变**，且 `a == b` 必须推出 `hash(a) == hash(b)`。
3. **最后给边界**：tuple 可哈希是**有条件的**——其所有元素也必须可哈希，`([1], 2)` 照样 `TypeError: unhashable type`。
**加分层**：业务里要把一组字段当复合键，就转成 tuple（或 `namedtuple`）；若需要可变，就改用 frozenset 或自行实现不可变记录类。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在怎么答 |
|---|---|---|
| Python 3.x | 定义 `__eq__` 会把 `__hash__` 置 None | 自定义值对象要显式写 `__hash__` |
| Python 3.7+ | dataclass(frozen=True) 自动生成 | 复合键优先用 frozen dataclass（可哈希、可比较） |

## 关键代码
```python
d = {}
try:
    d[[1, 2]] = "v"          # TypeError: unhashable type: 'list'
except TypeError as e:
    print("list 不可:", e)
d[(1, 2)] = "ok"             # tuple 可以
try:
    d[([1], 2)] = "bad"      # 元素含 list，同样报错
except TypeError as e:
    print("含 list 的 tuple 也不可:", e)

class A:
    def __eq__(self, o): return isinstance(o, A)
print(A.__hash__)            # None —— 已不可哈希
```

## ⚠️ 原文纠错
原文表述"可变对象不可哈希，因为它一直在变，哈希值也在变"方向正确但需补正：准确说法是**哈希值必须在对象生命周期内保持稳定**，且可哈希还要求与 `__eq__` 一致。其余未发现技术错误。

## 总结与追问预判
- 可哈希 = 稳定 `__hash__` + 与 `__eq__` 一致；tuple 可哈希有条件。
