# 108. 元类用在哪：ORM 框架是它最常见的主场

> 分类：编程范式/元类 | 难度：L2 | 题型：八股题 | 频率：中 | 关键词：**ORM** / **元类** / **字段映射** / **类创建钩子**
> 原文锚点：第 61~68 段「元类的最常见使用场景是 ORM 框架」

## 一句话总述
元类允许**在类生成时拦截并改写类**，因此适合做"声明式 → 运行时结构"的转换；**ORM** 是最典型场景：用户只声明字段，元类自动收集字段、建立**类与表、属性与列**的映射。

## 面试官视角
- **考察意图**：考"知道边界"——写业务代码几乎用不到元类，但读框架源码必须懂。
- **P5** 知道元类很高级 / **P6** 能说出 ORM、注册表、接口校验三类场景 / **P7** 能对比**元类 vs 装饰器 vs `__init_subclass__`** 给出选型 `[经验]`。
- **红旗**：① 说"业务代码里也应该多用元类"；② 只举得出 ORM 一个例子且说不出机制；③ 不知道 `__init_subclass__`（Python 3.6+）能替代多数简单场景。
- **惊艳点**：优先用更轻的工具——**Python 3.6+ 的 `__init_subclass__` 与类装饰器**能覆盖 90% 需求，**元类只在需要影响"类对象本身的创建过程"时才上**。验证：把一个注册型元类改写成 `__init_subclass__`，行为等价且更易读 `[实测]`。

## 主问答
**Q：元类一般用在什么地方？为什么 ORM 要用它？**
**A：**
1. **价值**：元类**控制类的生成**——可修改属性、注入方法、校验结构、注册类，属于"创建时钩子"。
2. **ORM**：用户写 `class User(Model): name = CharField(...)` 只做**声明**；元类在类创建时把 `Field` 收集成字段表，建立**类名↔表名、属性↔列**的映射，后续才能拼 SQL。
3. **代价**：元类属高级主题，**写业务代码基本碰不到**；它增加理解成本并可能引发元类冲突（多重继承时两个元类不兼容）。
**加分层**：选型顺序——能用**普通继承**就别用钩子；需要"父类感知子类定义"用 `__init_subclass__`；需要改类本身（字段改写、强制接口）才用元类；类装饰器适合"事后包装"。

## 关键代码
```python
class Field:
    def __init__(self, col): self.col = col

class ModelMeta(type):
    def __new__(mcs, name, bases, attrs):
        cols = {k: v.col for k, v in attrs.items() if isinstance(v, Field)}
        attrs['_columns'] = cols                 # 收集字段 → 建映射
        return super().__new__(mcs, name, bases, attrs)

class Model(metaclass=ModelMeta): pass

class User(Model):
    name = Field('name')
    age = Field('age')

print(User._columns)          # {'name': 'name', 'age': 'age'}
```

- 元类 = **类创建钩子**；ORM 靠它把**声明转映射**；业务代码基本不用，优先 `__init_subclass__`。
