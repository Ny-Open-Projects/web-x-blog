# 204. SQL 语句编写重点与连接查询总览

> 分类：数据库 | 难度：L2 | 题型：概念+规范 | 频率：中 | 关键词：**SQL 编写** / **连接查询** / **JOIN** / **阿里规范** / **逻辑下沉**
> 原文锚点：第8章 8-3「SQL 编写重点=连接查询（JOIN）；互联网复杂 SQL 在高并发表现差，倾向把逻辑下沉代码层；阿里 Java 规范禁止超过 3 张表 join」

## 一句话总述
**面试 SQL 编写重点在连接查询（JOIN）**；由于复杂 SQL 在高并发下表现差，业界（阿里 Java 规范）倾向"数据库只做存取、join 不超过 3 张表、复杂逻辑下沉到代码层"。

## 面试官视角
- **考察意图**：是否理解"为什么限制 join"以及 join 的语义，而非只会写 SELECT。
- **P5** 能说出 SQL 编写常考连接查询，且知道内/左/右连接 / **P6** 能解释"为什么复杂 join 在高并发差"——数据库计算成本高、锁持有久、难优化 / **P7** 能说出阿里规范"join 不超过 3 张表"并补充"复杂逻辑下沉代码层"的架构权衡。
- **红旗**：认为"join 越多越省事"，不知大 join 在高并发的代价；把全连接当成 MySQL 原生支持。
- **惊艳点**：能结合分库分表讲"跨分片 join 基本不可行，必须下沉到应用层聚合"，体现生产经验 `[经验]`。

## 主问答
**Q（面试官原话）：** SQL 语句编写有哪些重点？为什么常说要少写复杂 join？

**A · 标准答案骨架：**
1. **重点在连接查询（JOIN）**：互联网业务的 SQL 往往不复杂，常考点就是各种常用连接（内连接、左/右外连接、全连接），掌握这几类基本大同小异。
2. **复杂 SQL 在高并发下表现差**：源文件明确指出"特别复杂的 SQL 在高并发场景表现比较差劲"——大 join 意味着大量数据在数据库内做关联、锁持有时间更长、优化器难选优。
3. **业界实践：逻辑下沉 + 限制 join 张数**：很多公司（参考阿里巴巴 Java 开发手册）**禁止超过 3 张表的 join**；倾向"数据库只做数据存取，复杂逻辑拿到代码层做"。

**加分层**：分库分表后跨分片 join 基本无法在数据库层完成，必须应用层多次查询再聚合——这是"少 join"更深一层的工程动因。

## ⚠️ 原文纠错
- 机翻还原：「circle / circle语句」→ **SQL 语句**；「innerjoy / innership」→ **INNER JOIN / inner join**；「elevejoin」→ **LEFT JOIN**；「nuve」→ **NULL**；「taxt」→ **test（示例库名）**；「教育本章」→ "**禁止超过三张表 join（关联）**"（阿里巴巴规范）。
- 原文"全连接"仅概念提及（"只要某表存在匹配就返回"），但**未演示且 MySQL 不支持 FULL OUTER JOIN**——需用 `LEFT JOIN ... UNION RIGHT JOIN` 模拟（见 206 卡）。
- 原文把复杂 SQL 高并发差归因于"表现差劲"，准确机制是：大 join 带来大量行关联、更长锁持有、优化器选择空间大但易选错。

SQL 编写面试题的核心是**连接查询**，且要懂"为什么要限制 join"。面试官常顺问"INNER/LEFT/RIGHT 的区别"与"全连接怎么写"，可衔接：**内连接（见 205 卡）**、**外连接与全连接模拟（见 206 卡）**。
