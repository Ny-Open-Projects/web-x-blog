# 35. GIL 是怎么被让出来的：切换间隔

> 分类：并发/GIL | 难度：L3 | 题型：八股题 | 频率：中 | 关键词：**switch interval** / **字节码计数** / **setswitchinterval**
> 原文锚点：第 32~35 段「每隔一段 tick，执行多少字节码之后会去检查…尝试释放当前线程的锁，让其他线程获取」

## 一句话总述
持锁线程在**切换间隔到期**或**进入阻塞调用**时放锁，其他线程再竞争获取——CPython 早期按"执行 N 条字节码"让出，**3.2 起改为按时间间隔**（默认 5ms）。

## 面试官视角
- **考察意图**：是只知"会切换"，还是知道切换机制本身随版本变过。
- **P5** 知道会切换 / **P6** 能说出 `sys.setswitchinterval` 与默认值 / **P7** 知道 3.2 从指令计数改为时间片的原因与副作用。
- **红旗**：① 说"线程跑完才换下一个"；② 说默认按字节码条数（那是 3.1 及以前）；③ 以为调小间隔能提升性能。
- **惊艳点**：默认切换间隔是 **5 毫秒**（`sys.getswitchinterval()` 可查），调小只增加**切换开销与尾延迟抖动**，不会让 CPU 密集变快。验证：CPython 直接查询 `[实测]`

## 主问答
**Q：GIL 是什么时候被释放的？能不能控制？**
**A：**
1. **先给结论**：两条路径——**阻塞 IO 时主动释放**，以及**切换间隔到期时让出**；可用 `sys.setswitchinterval()` 调后者。
2. **再给机制**：早期 CPython 按"执行 N 条字节码"计数让出（`sys.setcheckinterval`）；3.2 起改为按**时间间隔**，避免 CPU 快慢导致切换频率在不同机器上差异过大。
3. **最后给边界**：调小间隔**不会**让程序变快，只是让线程切换更频繁，增加上下文切换成本与延迟抖动；它也不改变任何操作的原子性。
**加分层**：这条机制正是"**有了 GIL 仍要加锁**"的直接原因——你写的一条 Python 语句可能被切成多条字节码，中途完全可能换线程。

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在怎么答 |
|---|---|---|
| CPython 3.2+ | 3.2 起 `setcheckinterval` 被 `setswitchinterval` 取代；3.9 起旧接口移除 | 一律答按时间片切换，默认 0.005s |

## 关键代码
```python
import sys
print("默认切换间隔:", sys.getswitchinterval())          # 0.005 秒
sys.setswitchinterval(0.001)                             # 切更频繁，不提速
print("setcheckinterval 还在吗:", hasattr(sys, "setcheckinterval"))  # 3.9+ 为 False
```

## ⚠️ 原文纠错
原文描述为"每隔一段 tick、执行多少字节码之后检查并释放"，这是 **CPython 3.1 及以前**的行为；**3.2 起已改为按时间间隔**（默认 5ms），按指令计数会让快机器与慢机器的切换频率相差过大。此处按现行实现更正。

## 总结与追问预判
- 放锁靠"IO 阻塞 + 时间片到期"；切得再勤也不等于更快、也不等于安全。
