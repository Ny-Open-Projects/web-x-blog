# 192. 乐观锁与悲观锁

> 分类：数据库 | 难度：L2 | 题型：对比题 | 频率：高 | 关键词：**乐观锁** / **悲观锁** / **SELECT FOR UPDATE** / **版本号** / **CAS** / **冲突频率**
> 原文锚点：第 68~83 段「悲观锁：操作前先加锁再改（一锁二查三更新，SELECT FOR UPDATE）；乐观锁：先改，发现版本变了就回滚，靠版本号/时间戳，即 CAS」

## 一句话总述
**悲观锁**假设别人一定会改，操作前**先加锁再读写**（如 MySQL `SELECT ... FOR UPDATE`），冲突少但加锁有开销；**乐观锁**假设别人不会改，先改，**提交时比对版本号/时间戳**，变了就回滚重试，无锁开销但冲突高时要重试——**按冲突频率与重试代价选型**。

## 面试官视角
- **考察意图**：是否理解两者语义差异与选型权衡，能落到具体实现。
- **P5** 能说出"悲观=先加锁、乐观=版本号重试" / **P6** 能讲清悲观锁用 `SELECT FOR UPDATE` 行锁、乐观锁用 `UPDATE ... WHERE version=?` 比对版本 / **P7** 能给出选型判据（冲突低用乐观、冲突高/重试贵用悲观），并指出乐观锁本质是 **Check-And-Set** 而非 CPU 的 Compare-And-Swap。
- **红旗**：把乐观锁说成"不会冲突"（它只是不提前加锁，冲突时靠重试）；或认为悲观锁"一定慢"（只读冲突场景它反而简单可靠）。
- **惊艳点**：乐观锁的"CAS"在数据库语境是 **Check-And-Set（版本号比对）**，不是 CPU 指令级的 Compare-And-Swap；高冲突下乐观锁会**大量回滚重试**，此时反而比悲观锁更糟 `[经验]`。

## 主问答
**Q（面试官原话）：** 乐观锁和悲观锁有什么区别？什么时候用哪个？

**A · 标准答案骨架：**
1. **先给结论**：**悲观锁**操作前先加锁（假设会冲突），**乐观锁**先改后校验版本（假设不冲突）；差异在"何时加锁/校验"。
2. **再给机制**：悲观锁——`SELECT ... FOR UPDATE` 对行加**排他锁**，事务提交前别人改不了（"一锁二查三更新"）；乐观锁——表里加 `version` 列，`UPDATE ... SET val=?, version=version+1 WHERE id=? AND version=?`，**受影响行数为 0 说明版本变了，回滚重试**。
3. **最后给边界**：**冲突频率低、重试代价小** → 乐观锁（省锁开销）；**冲突频繁或重试代价高**（如大事务） → 悲观锁更稳；还要看响应时延要求。

**加分层**：高并发"扣库存"类场景常**先用 Redis 分布式锁或队列串行化写入**，再配合乐观锁兜底，避免数据库锁竞争 `[经验]`。

## 关键代码
```sql
-- 悲观锁：对目标行加排他锁 [实测]
SELECT * FROM account WHERE id=1 FOR UPDATE;   -- 别人此行改不了，直到本事务提交
UPDATE account SET bal=bal-50 WHERE id=1;

-- 乐观锁：版本号比对，受影响行数=0 即冲突回滚重试
UPDATE account SET bal=bal-50, version=version+1
 WHERE id=1 AND version=:old_version;
```
