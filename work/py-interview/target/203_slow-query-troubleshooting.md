# 203. 慢查询排查的三板斧

> 分类：数据库 | 难度：L3 | 题型：实战 | 频率：中 | 关键词：**慢查询** / **慢查询日志** / **EXPLAIN** / **全表扫描** / **分页** / **类型不匹配**
> 原文锚点：第8章 8-2「排查慢查询三手段：① 慢查询日志定位超阈值 SQL ② EXPLAIN 分析索引 ③ 业务代码层修类型匹配与分页；多数根因仍是缺索引或索引不合理」

## 一句话总述
**慢查询排查三板斧：看慢查询日志定位问题 SQL → 用 EXPLAIN 分析索引使用 → 在业务代码层修类型匹配与分页**；多数慢查询根因仍是"缺索引或索引不合理"。

## 面试官视角
- **考察意图**：是否有真实排障经验，而非只会说"加索引"；是否理解"用证据说话"的闭环。
- **P5** 能说出慢查询日志、EXPLAIN、代码层调整三种手段 / **P6** 能具体说 EXPLAIN 看哪些字段（`type`/`key`/`rows`/`Extra`），并知道慢日志由 DBA 配置或平台化 / **P7** 能结合实战讲"Python 参数类型不一致导致隐式转换全表扫描""一次取太多数据要分页"等代码层根因。
- **红旗**：认为慢查询"一定是 SQL 写得差"，忽视业务代码（类型不匹配、一次拉全量）与缺失索引。
- **惊艳点**：提到公司"慢查询日志平台"主动发现 + 用 `pt-query-digest` 聚合 Top SQL 的工程化做法 `[经验]`。

## 主问答
**Q（面试官原话）：** 线上出现慢查询，你怎么排查和解决？

**A · 标准答案骨架：**
1. **① 慢查询日志（slow query log）**：首先观察哪些 SQL 超过 `long_query_time` 阈值。通常由 DBA 配置，或公司有慢查询日志平台可直接检索。
2. **② EXPLAIN 分析**：在 MySQL 里直接对问题 SQL 跑 `EXPLAIN`，看是否走了索引、`type` 是否 `ALL`（全表扫描）、`rows` 估算扫描行数、`Extra` 是否 `Using filesort`/`Using temporary`。
3. **③ 业务代码层修复**：调整索引 + 修正代码里不合理的访问，例如**参数类型不匹配导致的全表扫描**、**一次获取过多数据**（应分页拉取）。
4. **最常见根因**：源文件明确指出——**多数是缺索引或索引不合理**；其次才是业务代码实现问题（类型不匹配、无分页）。代码层两类典型问题：**数据类型不匹配**（触发隐式转换→全表扫描）、**单次拉取数据量过大**（应分批/分页）。

**加分层**：慢查询不是"先改 SQL"而是"先看证据"——日志定位 → EXPLAIN 验证 → 代码/索引修。分页不仅是性能手段，也是防止 OOM 与长事务锁持有的工程实践。

## 追问链
| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | 第一板斧是什么 | 基本认知 | 慢查询日志定位超阈值 SQL | 换题 → 不及格 |
| L2 | EXPLAIN 里 type=ALL 说明什么 | 是否懂工具 | 全表扫描，未用/失效索引 | 判 P5 |
| L3 | 代码层哪些写法拖慢查询 | 真理解根因 | 类型不匹配（隐转）、一次取全量 | 判 P6 |
| L4 | long_query_time 一般设多少 | 工程经验 | 通常 1s/0.5s，按业务容忍度，DBA 配 | 判 P6+ |
| L5 | 如何聚合分析慢日志 | 实战工具 | pt-query-digest 或日志平台按指纹聚合 Top SQL | 答上判 P7 |

## 关键代码
```sql
-- 开启慢查询日志（示例，通常由 DBA 统一配置）[实测, MySQL 8]
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;

-- 用 EXPLAIN 看索引使用情况
EXPLAIN SELECT * FROM orders WHERE user_id = 123;

-- 代码层：分页替代一次拉全量
SELECT * FROM orders WHERE user_id = 123 ORDER BY id LIMIT 100 OFFSET 0;
```

## ⚠️ 原文纠错
- 机翻还原：「全秒扫描」→ **全表扫描**；「英诺DB / inlDB」→ **InnoDB**；「pyon」→ **Python**。
- 原文将慢查询归因于"缺少索引或索引不合理"和"业务代码实现"，分类准确；补充：慢日志需主动开启且阈值要合理，否则"没日志 ≠ 没慢查询"。
- 补充根因闭环：类型不匹配→隐式转换→索引失效（详见 201 卡），这是代码层最常见的"伪全表扫描"。

## 总结与追问预判
慢查询排查的核心方法是**用证据说话**：慢日志找 SQL → EXPLAIN 验索引 → 代码层治本（类型对齐、分页）。面试官常问"你线上怎么发现并解决慢查询的"，可用"慢日志平台发现 Top SQL + EXPLAIN 显示 type=ALL + 发现 Python 参数类型不一致导致隐式转换，对齐类型后恢复索引"作为完整闭环作答。顺势会问：**索引失效（见 201 卡）**、**聚集/非聚集索引与回表（见 202 卡）**。
