# 201. 索引失效三大场景与统一根因

> 分类：数据库 | 难度：L3 | 题型：原理+排错 | 频率：高 | 关键词：**索引失效** / **模糊匹配** / **隐式类型转换** / **最左前缀** / **B+树 key 比较**
> 原文锚点：第8章 8-2「索引失效三口诀：① 模糊匹配以 % 开头 ② 类型隐式转换 ③ 违反最左前缀；统一根因——B+树 key 无法直接比较」

## 一句话总述
**索引失效的三种高频场景——LIKE 以 % 开头、隐式类型转换、违反最左前缀——根因只有一个：B+树的 key 无法被直接比较**，理解这一点就不用死记。

## 面试官视角
- **考察意图**：是否只会背口诀，还是能讲清"为什么失效"；能否把三种场景归一到同一底层逻辑。
- **P5** 能背出三种场景：前导通配符 LIKE、类型隐转、最左前缀不匹配 / **P6** 能解释至少一种场景的底层原因（如最左不匹配导致无法从第一个 key 开始比） / **P7** 能一句话统一三种场景"失效都是因为 B+树 key 不能直接比较"，并举例 `(a,b,c)` 联合索引下 `bc` 无法利用。
- **红旗**：把"隐式转换"说成"参数类型写错没关系，MySQL 会帮忙转"（实际正是它导致失效）；认为 `LIKE '%x'` 和 `LIKE 'x%'` 一样能用索引。
- **惊艳点**：能现场说明联合索引 `(a,b,c)` 的多列 key 拼接，并演示 `WHERE b=1 AND c=2` 为什么无法定位（缺最左基准 a）`[经验]`。

## 主问答
**Q（面试官原话）：** 什么情况下索引会失效？有哪几种经典场景？

**A · 标准答案骨架：**
1. **① 模糊匹配以 % 开头**：`LIKE '%abc'` 或 `LIKE '%abc%'`，B+树 key 前面字符未知，无法从根节点二分定位，只能全表扫描；而 `LIKE 'abc%'`（后缀确定）**可以**用索引。
2. **② 隐式类型转换**：查询参数类型与列类型不一致，MySQL 会对索引列做类型转换（等价于对列套函数），导致 key 无法直接比较。源文件举例 Python 动态语言中传入参数类型与表字段类型不一致，多次踩坑。
3. **③ 违反最左前缀**：联合索引 `(a,b,c)` 必须从左往右匹配；`WHERE b=? AND c=?`（缺 a）无法利用索引。
4. **统一根因**：三种场景本质都是**"B+树 key 无法被直接比较"**。B+树查找从 key 的第一个列/字节开始逐段比较并决定走向；一旦开头不确定（% 开头）、类型不同（无法比）、或最左列缺失（没有比较基准），就无法沿树下降，退化为扫描。类比 Python 元组比较：`(1,2,3)` 与 `(1,2,4)` 先比第 0 位、相同再比第 1 位——联合索引多列 key 也是同样的"从左比较"语义。

**加分层**：最左前缀"失效"≠"完全不用索引"，MySQL 可能做 **index scan（扫整个索引树）** 而非 ref，性能仍差，需以 EXPLAIN 为准；范围查询（如 `a>1`）之后的列也会因"范围截断"而失效。

## 追问链
| 层 | 追问 | 在测什么 | 怎么接 | 答不出停在哪档 |
|---|---|---|---|---|
| L1 | `LIKE 'abc%'` 能用索引吗 | 基本认知 | 能，只有前导 % 才失效 | 换题 → 不及格 |
| L2 | 为什么类型不一致会失效 | 是否理解隐转 | 索引列被函数化，破坏 key 比较 | 判 P5 |
| L3 | `(a,b,c)` 下 `a=1 AND c=2` 能用吗 | 真理解最左 | 只用上 a，c 因缺 b 被截断 | 判 P6 |
| L4 | `a>1 AND b=2` 呢 | 范围截断 | a 是范围，b 在之后失效 | 判 P6+ |
| L5 | 如何验证 SQL 是否用索引 | 实战工具 | EXPLAIN 看 key/type，type=ALL 即全扫 | 答上判 P7 |

## 版本与兼容性
| 结论成立版本 | 翻转点 | 现在怎么答 |
|---|---|---|
| 隐式转换与最左前缀规则在 MySQL 5.6/5.7/8.0 行为一致 | MySQL 8.0 引入不可见索引 `INVISIBLE`、降序索引 | 可用 `EXPLAIN FORMAT=JSON` 看清索引选择；隐藏索引用于"先观察再删"的安全排查 |

## 关键代码
```sql
-- 失效：前导通配符（全表扫描）[实测, MySQL 8]
SELECT * FROM user WHERE name LIKE '%明';

-- 生效：后缀确定（可用 name 索引）
SELECT * FROM user WHERE name LIKE '张%';

-- 失效：phone 是 varchar，传入数字触发隐式转换
SELECT * FROM user WHERE phone = 13800000000;   -- 应写成 '13800000000'

-- 联合索引 (a,b,c)
CREATE INDEX idx_abc ON t(a,b,c);
SELECT * FROM t WHERE b=1 AND c=2;   -- 缺 a，索引失效
```

## ⚠️ 原文纠错
- 原文"类型隐转"即"隐式类型转换"，表述无误，但需强调**失效的是被转换的那一侧索引列**——是索引列被函数化，而非参数本身。
- 机翻还原：「多列索缀」→ 多列索引；「具体索索 / 聚错索引」→ 聚集索引（见 202 卡）。
- 补充：最左前缀"失效"在 EXPLAIN 里可能显示 `type=index`（扫描整棵索引）而非 `ALL`，仍慢，必须以 `key`/`type` 字段为准。

## 总结与追问预判
三句口诀——**模糊别用前导 %、类型要对齐、最左不能缺**——本质全是"B+树 key 不可直接比"。面试官最爱追问"你线上真遇到过索引失效吗"，可答 Python 参数类型不一致导致隐式转换的实战案例，并补一句"用 EXPLAIN 验证"收尾。顺势会问：**联合索引与最左前缀（见 199 卡）**、**慢查询排查（见 203 卡）**。
