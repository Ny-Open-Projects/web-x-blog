# 228. 系统设计概述与难点

> 分类：系统设计 | 难度：L3 | 题型：概述+认知 | 频率：中 | 关键词：**系统设计** / **System Design** / **微服务** / **feed 流** / **短网址** / **DRY 原则**
> 原文锚点：第10章 10-1「系统设计=定义系统架构/模块/接口/数据满足特定需求的过程；难点=经验要求高(需领域/算法经验+架构能力,如 feed 流推拉模型)、需熟悉后端组件(消息队列/缓存/数据库/Web 框架及其场景与底层)、需写文档画流程图架构图并编码；微服务架构下业务按功能拆成独立服务→系统设计题流行；常见考题=短网址/评论服务/feed 流(微博知乎)/抢红包；遵循 DRY 原则(公司级共享服务而非各业务重复造轮子)」

## 一句话总述
**系统设计 = 定义一个能"满足特定需求"的系统架构、模块、接口与数据的过程**。它难在既要求领域/架构经验（如 feed 流推拉模型），又要求熟悉后端组件（MQ/缓存/DB/Web 框架）并能画图编码；微服务拆分让"独立设计与实现一个服务"成为高频面试题。

## 面试官视角
- **考察意图**：看候选人是否有"从需求→拆解→选型→权衡"的全局架构思维，而非只会写 CRUD。
- **P5** 能说出系统设计是什么、举出常见题（短网址/feed 流/抢红包） / **P6** 能讲清三大难点（经验门槛、组件熟悉度、文档+图+编码）并指出微服务背景 / **P7** 能针对某一题（如 feed 流）展开推/拉模型取舍，体现真实架构能力。
- **红旗**：把系统设计当成"写代码题"直接开干；不知道先问清场景与 QPS 就拍脑袋选型。
- **惊艳点**：能点出"DRY 原则——公司级共享服务而非各业务重复造轮子"，以及"先估算再选型、避免杀鸡用牛刀" `[经验]`。

## 主问答
**Q（面试官原话）：** 什么是系统设计？为什么它难、常考什么？

**A · 标准答案骨架：**
1. **定义**：系统设计是把"需求"落成为**系统架构、模块划分、接口契约、数据模型**的过程——要同时满足特定业务需求，而不只是实现某个函数。
2. **为什么流行/难**：① **经验门槛高**——需要相关领域或算法经验与架构能力（例如 feed 流若不懂**推拉模型**基本答不上来）；② **组件熟悉度**——要熟悉消息队列、缓存、数据库、Web 框架的**使用场景甚至底层原理**（何时用 MQ 解耦/削峰、何时用缓存、缓存的一致性问题）；③ **工程闭环**——真实场景还要写设计文档、画流程图/架构图、最终编码实现。
3. **常见考题**：短网址服务（长链→短链）、评论服务、feed 流（微博/知乎）、抢红包系统等。它们近年流行，主因是**微服务架构**下业务按功能拆成独立服务，要求工程师能独立设计实现单个服务。
4. **设计哲学**：遵循 **DRY 原则**——提供"公司级共享服务"（如统一短网址服务），各业务来请求接口，而不是每个业务组重复造一套轮子 `[经验]`。

**加分层**：能补"系统设计题可深可浅、区分度高，常按候选人级别追问扩展与容错"，并顺势引出回答套路（见 229 卡）。

```python
# 用 DAU 粗略估算峰值 QPS（系统设计第一步：量化场景）[实测, python]
DAU = 1_000_000                 # 日活
peak_ratio = 0.1                # 假定 10% 用户在高峰 1 小时内集中访问
req_per_user = 20               # 人均请求数
seconds = 3600
peak_qps = DAU * peak_ratio * req_per_user / seconds
print(round(peak_qps))          # 约 556 QPS，据此决定是否上缓存/分库
```
