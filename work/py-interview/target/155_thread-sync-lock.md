# 155. 线程同步之锁（互斥量）

> 分类：并发 | 难度：L2 | 题型：原理题 | 频率：高 | 关键词：**互斥锁** / **临界区** / **threading.Lock**
> 原文锚点：第 35~40 段「通过锁机制防止多个线程同时访问公共资源；with lock 持有期间他人不能改」

## 一句话总述
**锁（互斥量）**保证同一时刻只有一个线程进入**临界区**；Python 用 `threading.Lock`，`with lock` 持有期间其他线程阻塞，从而把 `i += 1` 这类非原子操作变安全。

## 面试官视角
- **考察意图**：会不会用锁解决竞态，以及是否理解"锁保护的是临界区而非变量"。
- **P5** 会用 `with lock` 包住共享变量修改 / **P6** 能说清锁的获取/释放语义、阻塞等待 / **P7** 知道锁粒度（太粗串行、太细易漏）、死锁风险与规避（按固定顺序加锁）。
- **红旗**：锁加到不共享的局部变量上；或认为加锁后整段代码都快不起来。
- **惊艳点**：`Lock` 不可重入，**同一线程重复 `acquire` 会死锁**；需重入用 `RLock` —— 验证：单线程连调两次 `lock.acquire()` 直接卡死 `[实测]`。

## 主问答
**Q（面试官原话）：** 多线程改同一个全局变量怎么保证安全？你用过什么同步方式？

**A · 标准答案骨架：**
1. **先给结论**：用**锁（互斥量）**把修改共享数据的代码包成**临界区**，同一时刻只允许一个线程进入。
2. **再给机制**：`threading.Lock` 的 `acquire` 抢不到就**阻塞**，`with` 块结束自动 `release`；持锁期间其他线程改同一数据被挡在外面。
3. **最后给边界**：锁只保护**真正共享且会写**的部分；只读或局部变量无需锁；锁范围过大反而丧失并发收益。

**加分层**：用锁后该段变串行，要权衡临界区大小——这是"正确性换并发度"的典型 trade-off `[经验]`。

## 关键代码
```python
import threading
lock = threading.Lock()
counter = 0

def inc():
    global counter
    with lock:          # 临界区：同一时刻仅一个线程进入
        counter += 1     # 非原子操作被锁保护后变安全 [实测]

ts = [threading.Thread(target=inc) for _ in range(10)]
for t in ts: t.start()
for t in ts: t.join()
```
