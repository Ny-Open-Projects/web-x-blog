# 182. 阻塞 IO 与 IO 多路复用

> 分类：网络 | 难度：L2 | 题型：概念题 | 频率：高 | 关键词：**IO多路复用** / **阻塞IO** / **事件循环** / **单线程高并发** / **select**
> 原文锚点：第 1~30 段「什么是 IO 多路复用：操作系统提供一种同时监听多个 socket 的机制，单线程单进程即可处理多个 socket」

## 一句话总述
**IO 多路复用**是操作系统提供的"**一个线程同时监听多个 socket**"的机制；它能用**单进程/单线程**支撑成千上万并发连接，关键在于把"等待多个 fd 就绪"交给内核，**应用只在有 socket 可读/可写时才被唤醒处理**。

## 面试官视角
- **考察意图**：是否理解"为什么多线程/进程模型撑不住 C10K"，以及多路复用到底解决了什么。
- **P5** 能说出"一个线程管多个连接" / **P6** 能讲清阻塞 IO 两段式（等数据 + 拷贝）与多路复用只阻塞在"等就绪"这一步 / **P7** 能对比"每连接一线程"与"事件循环"的资源模型，并说清多路复用绕开了什么瓶颈。
- **红旗**：把多路复用说成"不阻塞"（其实 select 仍阻塞在等待就绪）；或认为多路复用能让单连接变快（它只提升"连接数密度"，不降低单连接延迟）。
- **惊艳点**：select/poll 每次调用都要**把全量 fd 集合从用户态拷到内核态并线性扫描**，这本身就是连接数上去后的新瓶颈——epoll 用内核态红黑树 + 就绪链表规避它 `[经验]`。

## 主问答
**Q（面试官原话）：** 为什么高并发服务器不用"一个连接开一个线程"，而要用 IO 多路复用？它到底解决了什么？

**A · 标准答案骨架：**
1. **先给结论**：线程/进程模型"每连接一线程"在 C10K 面前**资源耗尽**——创建开销大、内存占用高，一台机器开几千上万个线程很快就 OOM / 上下文切换爆炸；IO 多路复用让**一个线程管几万连接**，把这个瓶颈绕开。
2. **再给机制**：阻塞 IO 调 `recvfrom` 要经历"**内核等数据**"+"**数据从内核拷到用户**"两段，两段都完应用才拿到数据，一次只能等一个 socket；多路复用（以 `select` 为例）只阻塞在"**等任一 fd 就绪**"这一步，一旦有 socket 可读就返回，应用再 `recvfrom` 直接拿——**把"等待多个"交给内核一次完成**。
3. **最后给边界**：多路复用**不消除**单连接的阻塞拷贝，只是把"等"的维度从"一个"扩成"一堆"；CPU 密集或连接极少时，它相比多线程**没有优势**，反而增加编码复杂度（回调/状态机）。

**加分层**：典型写法是"**死循环 + select + 遍历就绪事件**"，这就是**事件循环**的雏形——单进程单线程内高效轮转多个客户端 `[经验]`。

## 关键代码
```python
import select, socket
# 事件循环雏形：一个线程监听多个 socket [实测]
socks = [s1, s2, s3]                              # 多个客户端 socket
rlist, _, _ = select.select(socks, [], [], 1.0)    # 阻塞到任一可读（只阻塞在"等就绪"）
for s in rlist:                                   # 只遍历就绪的，不空转
    data = s.recv(4096)                           # 此时 recv 几乎不阻塞（数据已在内核）
```
