### 3) 出现的 PPT / 公式 / 图表 / 代码的关键内容

*   **关键代码：`StockController.java`**
    ```java
    @GetMapping("/stock")
    public String stock() {
        MyLock myLock = new MyLock();
        myLock.setMethodName("stock");

        try {
            myLockMapper.insert(myLock); // 获取锁

            int stock = Integer.parseInt(redisTemplate.opsForValue().get("stock"));
            if(stock > 0) {
                stock--; // 扣减库存
                redisTemplate.opsForValue().set("stock", stock+"");
                System.out.println("库存扣减成功，剩余库存：" + stock);
            } else {
                System.out.println("库存不足！！！");
            }

            // 释放锁
            myLockMapper.deleteByMethodName("stock");
        } catch (Exception ex) {
            System.out.println("没有获得锁，不能执行减库存操作...");
        }

        return "OK";
    }
    ```

### 4) 关键场景与演示描述

*   **场景一：锁的获取与释放**
    *   **描述**：演示者在 `StockController` 中，通过 `myLockMapper.insert(myLock)` 方法尝试获取锁。如果成功，会执行后续的库存扣减逻辑；如果失败，则会进入 `catch` 块，打印“没有获得锁”的日志。在 `finally` 块中，无论是否成功获取锁，都会调用 `myLockMapper.deleteByMethodName("stock")` 方法释放锁，确保锁的最终释放，避免死锁。

*   **场景二：库存扣减逻辑**
    *   **描述**：在成功获取锁后，程序从 Redis 中读取当前库存值。如果库存大于 0，则执行 `stock--` 操作，并将更新后的值写回 Redis。如果库存小于等于 0，则打印“库存不足！！！”提示，不执行扣减操作。

*   **场景三：并发测试与结果验证**
    *   **描述**：通过模拟并发请求，观察控制台日志。演示者展示了在没有分布式锁的情况下，多个请求会同时读取到相同的库存值并进行扣减，导致“超卖”现象。在引入分布式锁后，只有第一个成功获取锁的请求能执行扣减操作，其他请求会因无法获取锁而被阻塞，从而保证了库存数据的准确性。同时，通过 Redis Desktop Manager 工具，可以直观地看到 Redis 中 `stock` 键的值在每次成功扣减后递减，验证了锁机制的有效性。

*   **场景四：异常处理**
    *   **描述**：在 `try` 块中，如果 `myLockMapper.insert(myLock)` 方法抛出异常（例如，Redis 连接失败或锁操作失败），程序会进入 `catch` 块，打印“没有获得锁，不能执行减库存操作...”的日志，确保程序不会因锁操作失败而崩溃，并向用户反馈了失败的原因。
