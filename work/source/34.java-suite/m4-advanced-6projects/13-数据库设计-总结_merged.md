### 3) 出现的 PPT / 公式 / 图表 / 代码的关键内容

*   **核心概念**：
    *   **范式设计**：
        *   **第一范式 (1NF)**：数据库表的每一列都是不可分割的基本数据项。
        *   **第二范式 (2NF)**：所有非主键属性必须完全依赖于主键。
        *   **第三范式 (3NF)**：属性间不存在传递依赖关系（如 A->B, B->C，则 A->C 不符合 3NF）。
    *   **反范式设计**：在范式设计与查询性能之间寻找平衡点，适用于业务场景。
    *   **数据库模型**：
        *   **概念模型**：面向用户，描述业务概念。
        *   **逻辑模型**：面向系统，细化功能和数据结构。
        *   **物理模型**：面向计算机系统，描述具体实现。

*   **设计原则**：
    *   **核心原则**：
        *   不在数据库做运算（CPU 计算务必至业务层）。
        *   控制列数量（建议字段数少于 20）。
        *   平衡范式与冗余（效率优先，牺牲范式）。
        *   拒绝 3B：拒绝大 SQL、大事务、大批量操作。
    *   **字段类型原则**：
        *   用好数值类型。
        *   字符转数字（提高查询性能）。
        *   避免使用 NULL 字段（影响索引和查询）。

*   **命名与表设计规范**：
    *   **命名规范**：
        *   命名有意义。
        *   数据库、表名小写。
        *   数据表形如：`backend_client_device_info`。
        *   命名不超过 25 字符。
        *   不要使用保留字。
        *   同一字段在不同表中类型和长度一致。
        *   备份表加时间标识。
    *   **表设计规范**：
        *   选择 InnoDB 引擎。
        *   每个表有主键（可选自增或整型）。
        *   尽量设置字段为 `NOT NULL`（避免 NULL 值存储开销和优化复杂性）。
        *   使用更短的列（如整型）。
        *   存储精确浮点数必须使用 `DECIMAL`。
        *   建议使用 `unsigned` 存储非负值。
        *   建议使用 `int unsigned` 存储 IPv4。

*   **业务设计三步法**：
    *   **先理解**：明确核心模块和对象。
    *   **画关系**：梳理模块间依赖、包含、聚合、组合关系。
    *   **再细化**：填充对象属性，适当加入反范式设计，斟酌与权衡。
