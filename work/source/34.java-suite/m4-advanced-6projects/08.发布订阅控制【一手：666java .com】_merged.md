### 1) 视频摘要

本视频演示了一个基于 Spring Cloud 的微服务架构中，如何实现一个带有访问控制（ACL）的 MQTT 消息发布服务。核心内容包括：

*   **服务端开发**：在 `ActController.java` 中编写了两个 HTTP 接口，分别用于处理 MQTT 的 `POST /superuser` 和 `POST /pubsub` 请求。
*   **访问控制逻辑**：通过 `clientId`、`access` 和 `topic` 三个参数，对请求进行多层校验。例如，`clientId` 不能为空，`access` 必须为 2 才能发布到 `server` 主题，`access` 为 1 才能发布到 `vm` 主题。
*   **数据持久化**：通过 `LambdaQueryWrapper` 查询数据库中的虚拟机实体 `VendingMachineEntity`，并根据查询结果进行业务逻辑判断。
*   **客户端测试**：使用 `SecureCRT` 终端模拟 MQTT 客户端，构造并发送符合 ACL 规则的请求。
*   **消息接收**：在 `Key Value - Consul` 的 Websocket 界面中，订阅特定主题并接收服务端发布的消息。

整个演示流程清晰，展示了从后端代码开发、数据库交互、到前端客户端测试的完整闭环。

    ```java
    public ResponseEntity<?> superuser(@RequestParam(value = "clientId", defaultValue = "") String clientId,
                                       @RequestParam(value = "username", defaultValue = "") String username){
        if(clientId.startsWith("mqtt")){
            log.info(clientId + "是超级用户");
    ```

    ```java
    @PostMapping("/pubsub")
    public ResponseEntity<?> pubsub(@RequestParam(value = "clientId", defaultValue = "") String clientId,
                                   @RequestParam(value = "access", defaultValue = "") int access,
                                   @RequestParam(value = "topic", defaultValue = "") String topic){
        log.info("ACL 发布订阅控制 clientId:" + clientId + " access:" + access + " topic:" + topic);
        if(Strings.isNullOrEmpty(clientId)){
            return new ResponseEntity<>(headers, null, HttpStatus.BAD_REQUEST);
        }
        // 查询数据库
        var qm = new LambdaQueryWrapper<VendingMachineEntity>();
        qm.eq(VendingMachineEntity::getClientId, clientId);
        var vm = vmservice.getOne(qm);
        if(vm == null){
            return new ResponseEntity<>(headers, null, HttpStatus.BAD_REQUEST);
        }
        // 权限校验
        if(access == 2 && topic.equals("server" + vm.getInnerCode())){
            return new ResponseEntity<>(headers, null, HttpStatus.OK);
        }
        if(access == 1 && topic.equals("vm" + vm.getInnerCode())){
            return new ResponseEntity<>(headers, null, HttpStatus.OK);
        }
        log.info(clientId + "不能发布订阅消息");
        return new ResponseEntity<>(headers, null, HttpStatus.BAD_REQUEST);
    }
    ```

### 4) 关键场景与演示描述

*   **场景一：超级用户认证**
    *   **描述**：在 `ActController.java` 中，通过 `clientId` 的前缀判断用户类型。如果 `clientId` 以 "mqtt" 开头，则认为是超级用户，返回 `200 OK`；如果以 "monitor" 开头，则认为是监控用户，也返回 `200 OK`；否则返回 `400 BAD_REQUEST`。
    *   **演示**：在 `SecureCRT` 中，通过发送带有 `clientId=mqtt` 的请求，成功触发了超级用户认证逻辑。

*   **场景二：普通用户发布消息**
    *   **描述**：在 `ActController.java` 中，`@PostMapping("/pubsub")` 方法接收 `clientId`、`access` 和 `topic` 三个参数。首先校验 `clientId` 是否为空，然后查询数据库获取对应的虚拟机实体 `vm`。最后，根据 `access` 和 `topic` 的值进行权限校验。
    *   **演示**：在 `SecureCRT` 中，发送一条 `access=2`、`topic=server+vm内码` 的请求，成功触发了权限校验逻辑，并在 `Key Value - Consul` 的 Websocket 界面中接收到消息。

*   **场景三：权限校验失败**
    *   **描述**：如果 `access` 不符合要求，或者 `topic` 不匹配，服务端会返回 `400 BAD_REQUEST`。
    *   **演示**：在 `SecureCRT` 中，发送一条 `access=1`、`topic=server+vm内码` 的请求，服务端返回 `400 BAD_REQUEST`，客户端无法接收到消息。

*   **场景四：数据库查询**
