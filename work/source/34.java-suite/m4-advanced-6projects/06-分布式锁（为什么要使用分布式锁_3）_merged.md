        @RestController
        public class StockController {

            @GetMapping("/stock")
            public String stock() {
                synchronized (this) {
                    int stock = Integer.parseInt(redisTemplate.opsForValue().get("stock"));
                    if(stock > 0) {
                        stock--;
                        redisTemplate.opsForValue().set("stock", stock+"");
                        System.out.println("库存扣减成功，剩余库存：" + stock);

### 4) 关键场景与演示描述

*   **场景一：演示无锁并发问题**
    *   **描述**: 视频首先展示了 `StockController.java` 中未加锁的 `stock()` 方法。随后，使用 JMeter 发起 5 个线程、循环 50 次的请求。运行后，控制台输出大量“库存不足！！！”的错误信息，表明在没有锁的情况下，多个线程同时读取和修改 Redis 中的库存值，导致数据不一致，出现了超卖现象。

*   **场景二：演示 `synchronized` 解决单机并发问题**
    *   **描述**: 在 `StockController.java` 中，开发者在 `stock()` 方法上添加了 `synchronized(this)` 关键字。再次运行 JMeter 测试，控制台输出变为“库存扣减成功，剩余库存：X”，并且输出的数字是递减的，表明 `synchronized` 关键字成功地将方法设为同步方法，确保了同一时间只有一个线程能执行该方法，从而解决了单机环境下的并发问题。

*   **场景三：引出分布式锁概念**
    *   **描述**: 视频通过展示一个 Markdown 文档，明确指出“单机锁”无法解决“分布式部署”下的并发问题。文档中提到“下面将程序进行集群部署”，并展示了一个包含 Nginx、两个 Tomcat 和一个 Redis 的架构图，为后续讨论如何在分布式环境中实现锁（如使用 Redisson）做了铺垫。

*   **场景四：高并发测试验证**
    *   **描述**: 在 `synchronized` 有效后，视频将 JMeter 的线程数和循环次数调高至 100，以模拟更激烈的并发压力。测试结果显示，虽然并发请求增多，但库存扣减成功的信息依然出现，说明 `synchronized` 在单机环境下是有效的，但为后续的分布式锁讨论埋下了伏笔。
