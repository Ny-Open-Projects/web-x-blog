# 安全与合规须知

本页是全库博客的统一安全提示，覆盖 blog 目录下十个阶段共 315 篇受影响篇目（弱口令 275 篇、MD5 密码场景 38 篇、JWT 静态密钥 18 篇、云密钥占位 25 篇，篇目间有交叉）。这些篇目的标题下方都有一行「🔒 安全提示」指针指向这里。受影响篇目的示例代码一律保持课程教学原貌、未做任何改动，生产环境的真实要求以本须知为准。

## 适用范围与教学口径

全库示例里的口令、密钥、证书，全部出自课程录制时的教学环境：虚拟机组成的内网、单机 Docker、演示账号与演示数据。教学目标是把机制讲清楚，口令强度、密钥托管、算法选型这些生产话题不在每节课的射程之内，因此示例里留下了 root 配 123456 这类「能跑就行」的简化。

转写成博客时保持了课程忠实度：代码、配置、命令一律不改，只加提示。这样做一是为了可复现，读者按文中的命令能在自己的环境里得到同样的结果；二是为了对得上视频，正文与画面逐处可核对。

所以要先立一条总口径：**全库出现的所有口令与密钥，都是课程教学环境的演示口径，不是最佳实践，更不能带上公网。** 判定方法很简单：任何一段配置要从演示环境搬进真实项目之前，先过一遍本须知下面五节的检查，逐节替换。

指针行的使用方式：受影响篇目只在开头放一行提示，不重复展开细节，所有解释集中在本页。阅读任何一篇时看到指针，就应当意识到该篇的示例存在本页列出的某一类简化，复制示例之前先到这里查对应小节。

## 一、弱口令：root/123456 只是课堂道具

全库最常见的模式是 MySQL 的 `root/123456`，此外还有 Redis 的 `requirepass 123456`、RabbitMQ 与 Gogs 的演示账号、Jenkins 与 Grafana 的初始口令、Eureka 与 Elasticsearch 完全不设认证等。它们出现在 Docker 命令的 `-e` 参数里、`application.yml` 里、Postman 的请求体里。

弱口令的实际风险在于它是自动化攻击的第一批字典：公网上的爆破工具每时每刻都在扫 3306、6379、5601 这些端口，`123456` 永远在字典的第一页。更危险的组合是「管理后台弱口令加内网横向」：一个 Jenkins 或 Grafana 弱口令被拿住，攻击者就获得了执行脚本与刺探内网的落脚点，课程里那套 `172.16.x.x` 内网在演示里安全，放到公网环境就是另一回事。

还要考虑人在多个系统之间复用口令的习惯。员工把工作口令同时用在邮箱、网盘与个人设备上，任何一处泄露都会回流到内网，这叫撞库攻击，防御方式除了独立随机的口令，还包括对登录行为本身做风控：异地登录提示、异常时段告警、同一账号多来源并发访问的自动锁定。

| 课程示例 | 生产建议 |
|---|---|
| `root/123456` 一套走天下 | 每个服务独立账号，口令 16 位以上随机生成，交给密码管理器托管 |
| 口令写死在 `docker -e` 与 `yml` 里 | 改由部署环境注入，或放配置中心并加密（如 Vault、KMS 加密后的配置项） |
| root 直连业务库并绑定 `0.0.0.0` | root 禁止远程登录，业务账号按库表做最小授权 |
| Redis、Elasticsearch 裸奔 | 开认证加 ACL，只绑定内网地址，Redis 另做危险命令改名 |

在此基础上，管理后台全部启用 MFA（多因素认证），登录加失败次数限制与告警，访问与操作留审计日志。口令本身的生命周期也要管：定期轮换、离职即吊销、绝不复用。

## 二、密码存储：MD5 与加盐 MD5 都已过时

万信金融项目用 MD5 加盐存登录密码，Shiro 系列示例里是 `Md5Hash` 与 `SimpleHash` 加随机盐，HRM 项目的用户导入给新账号设默认密码 `123456`。MD5 这类做法在 2010 年代初的教材里常见，现在必须整体替换。

原因要讲透：MD5 的设计目标是快速校验，而「快」在密码存储里恰恰是缺点。一块普通显卡每秒能算百亿级次的 MD5，拖库之后攻击者对每个账号做暴力穷举只是算力问题。加盐解决的是彩虹表（预计算的「哈希到原文」对照表），挡不住穷举本身；如果全库用同一个固定盐，还会让攻击者一次算完所有账号。

现代方案的核心思想是「故意变慢、自带随机盐」：BCrypt 自带盐并可调 cost 因子，Spring Security 的 `BCryptPasswordEncoder` 开箱即用；Argon2id 是密码哈希竞赛的胜者，额外引入内存困难，抗 GPU 与专用芯片，新系统优先考虑；scrypt 同理可用。

| 课程示例 | 生产建议 |
|---|---|
| `md5(password + salt)`，盐自己拼 | `BCryptPasswordEncoder.encode(password)`，盐由算法自动生成并随哈希一起存储 |
| 固定轮数或 cost，多年不调 | cost 调到单次验证约 100 至 300 毫秒，随硬件升级定期上调 |
| 明文存储或可逆加密存储 | 密码只存慢哈希、永不可逆，找回密码改成重置密码 |
| 默认密码 `123456` 批量开户 | 初始化密码走随机生成加首次登录强制修改 |

存量数据怎么迁移：新用户直接用新算法；老用户在下一次登录成功时透明重哈希（校验通过后立刻用 BCrypt 重算并落库，标记位记录算法版本）；长期未登录与高危账号强制重置。这样不需要一次性全量洗数据，风险随时间自然收敛。

算法之外还有两条配套纪律。其一，口令长度下限要提上来，十二位起步，同时禁止把口令限制得过死，比如强制要求特定字符种类反而会诱导规律性拼凑；其二，可以在注册与改密环节对接已知泄露口令库做校验，把「密码本身曾经泄露」这类最差选择直接挡在门外。

## 三、JWT 密钥管理：从静态 HS256 到非对称与轮换

多个项目用 JWT 做登录态与接口鉴权：HRM 的 jwt 系列把 HS256 的签名密钥写成了源码里的固定字符串（`siging-key` 这类拼写是课程原样），探花与万信金融的鉴权也是同一口径。这类写法演示了 token 的结构与签发流程，但密钥管理是空白。

问题分三层。第一，HS256 是对称签名，校验方必须持有签发密钥，任何拿到密钥的服务都能伪造任意用户的 token，信任边界崩塌。第二，密钥写死在源码里，随仓库扩散，仓库一旦泄露或密钥被提交进历史，所有环境一起沦陷，而且短密钥能被离线爆破。第三，token 签出后无法单独吊销，改密钥等于全员掉线。

| 课程示例 | 生产建议 |
|---|---|
| HS256 加源码内固定密钥 | 改 RS256 或 ES256 非对称签名，私钥只留在签发服务，公钥分发给各校验方 |
| 密钥写死在配置文件 | 密钥托管到 KMS 或专用密钥服务，用 `kid` 支持多密钥并存与平滑轮换 |
| token 长期有效 | 短效 access token（分钟级）加 refresh token，refresh 可单独吊销 |
| 只验签名不验其他声明 | 同时校验 `exp`、`iss`、`aud`、`nbf`，并固定算法白名单，防 `alg=none` 与密钥混淆攻击 |

配套动作：敏感操作（改密、提现）在 token 之外做二次认证；登出、封号、权限回收要靠网关侧黑名单或会话校验兜底，不能指望 token 自知；密钥轮换要有记录与演练，轮换当天新旧密钥并行验证。

## 四、云密钥管理：AK/SK 与 KMS

对象存储、短信、人脸识别、支付渠道这些篇目里，云服务的访问密钥以 `example-ak`、`example-secret` 占位，部分课程画面里还出现过真实形态的 AK。先说口径：**课程演示里出现过的任何 AK/SK，无论真假，都应视为已作废**；生产凭据的纪律只有一条，绝不进代码库。

AK/SK 泄露的后果是直接的资产损失：对象存储被刷流量、短信接口被盗刷、支付渠道被盗用，账单以小时计增长。泄露途径排第一的就是代码仓库与配置文件，其次是聊天记录、截图、日志。

| 课程示例 | 生产建议 |
|---|---|
| AK/SK 写进代码或 `yml` | 部署环境注入或 KMS 加密下发，代码仓库保持零凭据 |
| 长期有效的 AK/SK | 最小权限的 RAM 角色加 STS 临时凭证，有效期以小时计，定期轮换 |
| 无泄露检测 | CI 流水线与 git hook 做凭据扫描，命中即阻断合并 |
| 发现泄露再手动换 | 预案化：发现即轮换加调用记录审计，确认影响面 |

原则收拢成一句：密钥的生成、分发、轮换、销毁全部走 KMS，应用侧只持有引用而不持有明文；每个密钥绑定最小权限与审计，能随时单独吊销。

## 五、支付合规：PCI-DSS 要点与 P2P 清退背景

聚合支付项目（闪聚支付）演示了渠道代理、商户进件与通道路由，渠道密钥直接写在配置与界面里；万信金融是 P2P 网贷题材的完整项目。这两个方向的教学价值在流程与架构，但合规边界必须单独说明。

**PCI-DSS 要点**（涉及银行卡数据的系统底线）：一是敏感认证数据零存储，CVV/CVC 任何情况下不得保存；二是主账号 PAN 加密存储、展示脱敏，加密密钥与数据分离管理；三是网络分段、按角色最小授权、全程日志；四是定期漏洞扫描与渗透测试，按交易量对应级别完成合规认证。国内收单侧另有银联与网联的接入规范，思路一致。

**业务资质背景**：P2P 网贷行业自 2020 年起全面清退、备案清零，万信金融这类平台在现实中已无对应业态，课程只作教学题材；真实的资金撮合与借贷业务必须持牌经营。聚合支付需要支付业务许可证，或与持牌机构合作，无资质的二次清算（二清）是监管红线；渠道密钥是商户资金安全的边界，必须 KMS 托管、界面不留明文、操作全留痕。课程里简化的回调验签、金额对账、幂等与防重放，生产环境一个都不能省。

支付与金融场景还叠加个人信息与数据合规的约束：用户手机号、身份证号、银行卡号的收集要有明确目的与最小范围，存储要加密，使用要留痕并取得授权。相关法律对数据出境、委托处理与安全事件报告都有明确要求，系统设计时就要把数据的分类分级画清楚，而不是等功能跑通后再补。

## 六、快速自检清单

把上面五节收拢成一份可执行的清单，任何项目上线前逐项打勾：

- 所有默认口令已更换为随机口令，并由密码管理器托管；
- 数据库、缓存、消息队列均为最小权限专用账号，root 禁止远程；
- 登录密码以 BCrypt 或 Argon2id 存储，无 MD5 与 SHA1 体系残留；
- JWT 使用非对称签名，密钥托管于 KMS 并有轮换记录；
- 代码仓库经过凭据扫描，无 AK/SK、无私钥文件入库；
- 云资源使用临时凭证与最小权限角色；
- 支付相关系统满足对应级别的 PCI-DSS 要求，渠道密钥无明文落盘；
- 关键后台启用 MFA 与操作审计；
- 完成过一次真实的漏洞扫描或渗透测试，高危项已修复。

教学环境里的每个简化都有它的用途：让注意力集中在机制本身。而把这些简化逐条还原成生产配置，正是从看懂到上岗之间的距离。
