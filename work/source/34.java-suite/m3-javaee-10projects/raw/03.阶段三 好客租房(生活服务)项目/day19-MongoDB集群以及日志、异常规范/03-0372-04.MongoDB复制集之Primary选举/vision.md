表格：
- 表头：成员 | 说明
- 行1：Secondary | 正常情况下，复制集的Secondary会参与Primary选举（自身也可能会被选为Primary），并从Primary同步最新写入的数据，以保证与Primary存储数据一致。Secondary可以提供读服务，增加Secondary节点可以提供数据冗余能力，同时提升集群的可用性。另外，MongoDB支持对复制集的Secondary节点进行灵活的配置，以适应多种场景的需求。
- 行2：Arbiter | Arbiter节点不参与投票，不能被选为Primary，并且不从Primary同步数据。比如你部署了一个3节点的复制集，1个Primary，2个Secondary，复制集将不能提供写服务。
