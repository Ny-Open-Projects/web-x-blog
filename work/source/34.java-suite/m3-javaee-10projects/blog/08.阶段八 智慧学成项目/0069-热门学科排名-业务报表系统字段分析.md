# 热门学科排名报表字段分析：七个字段撑起一份学科榜单

需求分析定下了指标与增幅口径，接下来的问题是数据结构：报表页面上到底流转哪些字段、什么类型、请求怎么发。这一步是在给后面所有环节立目标：采集要采出支撑这些字段的原料，统计要算出这些字段的值，同步要把这些值原样搬进业务库。热门学科排名的报表契约不复杂，一次抓包就能看全，但字段背后的三层对应关系值得逐个拆开。

## 先给结论

- 报表接口 `/courseSubject/statistics` 返回七个业务字段：`subjectName` 学科名，`saleNum` 销售量、`salePercent` 销售量增幅，`saleAmount` 销售额、`amountPercent` 销售额增幅，`userNum` 学生人数、`userPercent` 学生人数增幅。
- 类型规律好记：学科名是字符串，三个数值字段是整数，三个增幅字段是小数。
- 请求参数两个：`datePickerSel` 带选中的时间值，`type` 指定周月年；一个接口吃下三个级别，响应结构不变。
- 这七个字段就是后续 APP 层与业务库建表的目标结构，数值与增幅按列落表，学科名来自课程分类维度。
- 名次不入库：排名是前端按指标排序生成的序号，接口契约里另有排序参数支撑这一交互。

## 抓包看契约：页面上流转的 JSON

切到热门学科排名的原型页面，打开浏览器开发者工具的网络面板，榜单数据的来源一目了然：页面对统计接口发起一次 GET 请求，响应是一段 JSON，数组里每个元素对应一个学科的完整数据。按抓包结果与讲义整理，字段与类型如下：

| 字段名 | 字段说明 | 数据格式 | 数据示例 |
|---|---|---|---|
| subjectName | 学科名 | string | 大数据 |
| amountPercent | 销售额增幅 | float | 0.9999 |
| saleAmount | 销售额 | int | 999 |
| saleNum | 销售量 | int | 99 |
| salePercent | 销售量增幅 | float | 0.9999 |
| userNum | 学生人数 | int | 99 |
| userPercent | 学生人数增幅 | float | 0.9999 |

响应样例如下（科目与数值为模拟值，结构与类型以接口契约为准）：

```json
{
  "code": 200,
  "msg": "success",
  "result": [
    {"subjectName": "Java",   "saleNum": 49687, "salePercent": 0.44,
     "saleAmount": 999, "amountPercent": 0.51,
     "userNum": 52198, "userPercent": 0.38},
    {"subjectName": "大数据", "saleNum": 31415, "salePercent": 0.61,
     "saleAmount": 826, "amountPercent": 0.47,
     "userNum": 40872, "userPercent": 0.55}
  ]
}
```

字段按「一列学科名加三对数值增幅」记就行。数值是整数计数，销售量几单、销售额多少、学生人数几人；增幅是小数比率，比如 `0.44` 表示同比上涨四成四，前端再格式化成百分比展示。这份数据的源头是大数据统计分析的结果：清洗统计落进数仓 APP 层，同步进业务库，报表系统从业务库取数组装成这段 JSON，前端拿数值画图、拿增幅标趋势。所以这份字段清单同时约束三层：统计程序的输出结构、业务库的表结构、接口的响应结构。

## 请求分析：一个接口吃下周月年

抓包同时能看到请求参数。周月年三种查询共用同一个接口，变的只有两个参数的取值：`type` 在 week、month、year 之间切换，`datePickerSel` 随之带上第几周、哪个月、哪一年：

```text
周查询  datePickerSel=2019-39&type=week    以周为单位返回当前周学科统计
月查询  datePickerSel=2019-09&type=month   以月为单位返回当月学科统计
年查询  datePickerSel=2019&type=year       以年为单位返回当年学科统计
```

三个级别的响应格式完全一致，差别只在聚合口径：周请求按周聚合、月请求按月聚合、年请求按年聚合。前端组件因此完全复用，切换级别只是换参数重发一次请求，返回的数据结构不换。另外契约里还备有两个可选排序参数：`orderBy` 指定按哪一项排（如 `userNum`），`order` 指定升序降序，榜单上的名次就由排序结果生成。排序发生在展示侧，数仓不存名次，这一点直接决定了后面建表不需要任何排名列。

## 字段落地的目标：APP 层与业务表

七个字段反过来就是数仓与业务库的建图目标。以学生人数周报表为例，章内讲义给出的 APP 层 Hive 表与同步后的 MySQL 业务表结构如下：

```sql
-- Hive APP 层：学科学生人数周报表（真实建表语句，出自章内讲义）
CREATE EXTERNAL TABLE
IF NOT EXISTS data_subject.subject_user_week_biz
(course_category_dim_id String,
 course_category_name String,
 user_num Int,
 user_percent FLOAT)
PARTITIONED BY (years String, week_of_year String)
ROW FORMAT DELIMITED FIELDS TERMINATED BY '\t'
STORED AS PARQUET
location'/user/hive/external/data_subject/subject_user_week_biz';

-- MySQL 业务库：学生人数周报表业务表（真实建表语句，出自章内讲义）
CREATE TABLE `subject_user_week_biz` (
  `course_category_dim_id` varchar(255) NOT NULL,
  `course_category_name` varchar(255) DEFAULT NULL,
  `user_num` int(11) NOT NULL,
  `user_percent` float(11,4) DEFAULT NULL,
  `date_info` varchar(255) DEFAULT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8;
```

对照接口字段，映射关系就清楚了：`subjectName` 对应表里的 `course_category_name`，即课程分类名，学科口径由此而来；`userNum` 对应 `user_num`，`userPercent` 对应 `user_percent`，类型从接口的 int 与 float 一路贯通到表列。落库侧比接口侧多出两样东西：`course_category_dim_id` 是维度主键，统计分析靠它关联课程分类维度拿到学科名；`date_info` 是时间列，由分区列拼接而来。销售量与销售额也各有对应的周月业务表，命名与列结构同理，数值列换成 `sale_num`、`sale_amount` 及各自增幅。整条数据链路画出来是这样的：

```mermaid
flowchart LR
    A["统计分析结果 Hive APP 层"] -->|"NiFi 同步"| B["MySQL 业务库 subject_user_week_biz 等"]
    B --> C["报表接口 组装七个字段"]
    C --> D["前端图表 明细表 排名"]
```

关键路径在业务表到接口的那一跳：表里按维度主键、学科名、数值、增幅、时间列存放，接口把这组数据按 `subjectName` 加三对数值增幅的形状吐给前端。字段分析的意义正在于此，采集与统计阶段照着目标结构倒推，就能保证每一步产出都对得上最终契约。

## 常见误区

- **把增幅当百分数整数存。** 错例：接口里看到 44% 就建 int 列存 44。正解：契约里是 `0.44` 这样的比率小数，建表用 `float(11,4)`，百分比格式化留给前端。
- **把排名当存储字段。** 错例：建表加一列 rank，统计程序按指标排好名次写进去。正解：名次是展示层排序的衍生结果，契约里的 `orderBy` 与 `order` 参数就是干这个的，为每个指标存名次只会让统计与排序逻辑重复。
- **接口字段与表字段照抄互套。** 错例：以为业务表里就有一列叫 `subjectName`。正解：表里是 `course_category_name` 与 `course_category_dim_id`，接口形状是同步组装出来的，两层结构各有职责。
- **数值与增幅类型混用。** 错例：七个字段全建成 varchar。正解：数值 int、增幅 float，类型乱了图表聚合与增幅计算都会失真，清洗统计的输出类型要与表列一一对应。

## 面试可能被问到的问题

1. 面试官追问：「热门学科排名的七个字段分别从哪来？」
   答：学科名来自课程分类维度的分类名；销售量与销售额由课程购买量数据聚合而来，学生人数由用户选课数据统计而来；三个增幅字段分别由各自数值字段的本期聚合值与上一等长周期聚合值计算得到。响应外层的 code、msg、result 是接口通用外壳。
2. 面试官追问：「一个接口怎么同时支持周月年三种查询？」
   答：请求参数只有两个，`type` 指定级别，`datePickerSel` 带具体时间值。三个级别复用同一响应结构，差别只在服务端的聚合口径，前端切级别只是换参数重发请求，展示逻辑零改动。
3. 面试官追问：「榜单的名次为什么不在数仓里排好存起来？」
   答：名次是展示层按用户所选指标排序的衍生结果，用户可以按销售量排、也可以按学生人数排，为每种排序各存一份既浪费又容易和实际排序参数脱节。接口契约用 `orderBy` 与 `order` 表达排序意图，数仓只存聚合值与增幅。
4. 面试官追问：「接口字段和业务表字段为什么不完全一致？」
   答：分层职责不同。业务表面向数仓与同步，存维度主键 `course_category_dim_id`、学科名、数值、增幅与时间列 `date_info`，时间列由分区列拼接而来；接口面向前端，把维度信息收敛成 `subjectName` 加三对数值增幅。同步与接口组装层承担两层形状之间的转换。
5. 面试官追问：「这份字段分析对后续采集与统计开发有什么用？」
   答：它是反向定目标的依据。学生人数字段说明必须采集用户选课数据，学科名字段说明清洗时要关联课程分类维度，增幅字段说明统计要算本期与上一周期两次聚合。采集清单、清洗关联、统计输出、建表结构，全部由这份契约倒推得出，避免做原型用不上的字段。
