# 打包产物进容器：用 WinSCP 加 docker cp 替换 NiFi 里的旧 jar

代码改完、Maven 打包通过，很多人以为联调可以直接开跑，结果调度触发后统计的还是老数字。原因很简单：NiFi 调度脚本里 spark-submit 指向的是容器内 `/opt/run/jars` 目录下的 jar，开发机里那个新打出来的包根本没进容器。这一节要做的就是把三个模块的新包安全地送进 NiFi 容器替换旧包，顺带把测试阶段的调度策略配置讲清楚，让后面逐指标的调度执行有章可循。

## 先给结论

- 上传是一条接力路径：开发机的 target 目录，经 WinSCP 传到宿主机 `/opt/tmp` 中转，再用 `docker cp` 拷进 `xc-online-nifi` 容器的 `/opt/run/jars`。
- 换包前先删旧包：进容器清空 `/opt/run/jars` 里的三个 jar，避免新旧混杂、覆盖不全。
- 需要上传的是离线、搜索（即时查询）、实时三个包；实时分析代码未改，包是顺手重打的，一起传保持同一次构建。
- 测试阶段调度用时间驱动（Timer driven）并配一个超长 Run Schedule，生产环境用 CRON 表达式；配置只动处理器组的第一个处理器。
- 造数流程同样吃这套日期机制：数据目录由时间表达式算成昨天，清洗统计读昨天的目录，链路日期才能对齐。

## 上传路径的接力：两级跳进容器

容器的文件系统与宿主机是隔离的，WinSCP 这类图形化工具连的是宿主机 SSH，看不见容器内部，所以必须有个中转。课程环境的接力路径如下：

```mermaid
flowchart LR
    A["开发机 target 目录"] -->|"WinSCP 上传"| B["宿主机 /opt/tmp"]
    B -->|"docker cp"| C["xc-online-nifi 容器 /opt/run/jars"]
    C --> D["spark-submit 按脚本指向加载"]
```

开发机与宿主机之间用 WinSCP 图形界面拖拽即可，目标目录是 `/opt/tmp`；宿主机与容器之间走 `docker cp` 命令。三个 jar 分别来自 `xc-service-offline`、`xc-service-search`、`xc-service-rt` 模块的 target 目录，文件名以 `jar-with-dependencies` 结尾，一个包就带齐了 Spark、HBase、ES 全部依赖，容器里不需要额外配 classpath。

## 换包三步：删旧、拷新、验证

**第一步，删旧包。** 在宿主机开一个终端，确认 `/opt/tmp` 下三个包都在，然后进入 NiFi 容器把旧包清掉：

```bash
# 宿主机确认中转目录里的三个包
ls -lh /opt/tmp

# 进入 NiFi 容器（终端是 bash）
docker exec -it xc-online-nifi bash
cd /opt/run/jars
# 删除旧的三个 jar，务必确认当前就在 NiFi 容器内
rm -f xc-service-offline-jar-with-dependencies.jar \
      xc-service-rt-jar-with-dependencies.jar \
      xc-service-search-jar-with-dependencies.jar
exit
```

删包这个动作有个隐蔽风险：终端窗口开多了容易分不清自己在宿主机还是容器里，删错位置轻则白删，重则误伤别的文件。执行前用 `hostname` 或提示符确认一下，是个不花成本的习惯。

**第二步，docker cp 逐个拷入。** 回到宿主机终端，把三个包依次拷进容器的 `/opt/run/jars`：

```bash
docker cp /opt/tmp/xc-service-offline-jar-with-dependencies.jar xc-online-nifi:/opt/run/jars/
docker cp /opt/tmp/xc-service-rt-jar-with-dependencies.jar  xc-online-nifi:/opt/run/jars/
docker cp /opt/tmp/xc-service-search-jar-with-dependencies.jar xc-online-nifi:/opt/run/jars/
```

`docker cp` 的方向由源与目标的书写顺序决定，目标写成 `容器名:路径` 就是进容器。三个包对应三个模块，offline 是离线分析，search 是即时查询，rt 是实时分析，与调度脚本里各指标 `--class` 所在的 jar 一一对应。

**第三步，验证。** 再次进入容器 `ls` 一遍 `/opt/run/jars`，确认三个包齐、大小与宿主机 `/opt/tmp` 下的源文件一致。到这一步，容器内的程序世界已经换成新代码，NiFi 界面上处理器组还是原来的样子，不需要任何改动。

## 调度策略：测试用 Timer，生产用 CRON

jar 换完就可以在 NiFi 上调度测试了，动手前把调度策略的两种选择弄明白。NiFi 处理器的 Scheduling Strategy 常用的是时间驱动（Timer driven）与 CRON 驱动两种：

- **Timer driven**：配一个 Run Schedule 间隔，本轮执行结束后等待这么久再触发下一轮。课程环境配的是 9000 秒这样的超长间隔，真实作用不是定时，而是拉开两轮的距离，测试阶段想手动启停处理器组多少次都不会撞上自动触发。
- **CRON 驱动**：填标准 CRON 表达式，比如 `0 0 6 * * ?` 代表每天早上六点整调度一次，配置灵活精确，是生产环境的常规选择。

测试阶段恰恰不能用 CRON：表达式要到点才触发，总不能为了验证一轮流程等到明天早上六点。所以联调期间统一用 Timer driven，把启动与停止都握在自己手里；生产环境再按业务需要配 CRON。这套取舍的原则是：模拟生产环境模拟的是部署形态与执行方式，不是照抄生产的每一项参数。

还有一个配置点要记住：处理器组内以第一个处理器的调度配置为准，第一个处理器配了调度策略与启动行为，组内后续处理器跟着执行，不需要逐个去配。启动与停止永远只操作处理器组这个整体。

## 造数目录的日期也要对齐

数据生产这条支线吃同一套日期机制。往 HDFS 写测试数据的处理器，输出目录里的日期段同样用 NiFi 表达式算成了昨天，也就是 `${now():toNumber():minus(86400000):format('yyyy-MM-dd')}` 拼出来的路径。这样今天点下启动，数据落进昨天的目录，后面的清洗统计程序按昨天读目录，正好能读到。若造数目录用当天日期而清洗读昨天，两边永远错开一天，联调时表现就是清洗任务成功但数据为零。线上真实采集走的是 js 埋点与 binlog，目录日期由采集时刻决定，天然与 T 加 1 的统计口径一致；造数是模拟，就要靠表达式手动对齐这个口径。

## 常见误区

- **以为打包完就万事大吉。** 错例：Maven 出包成功后直接启动调度。正解：NiFi 加载的是容器内 `/opt/run/jars` 的包，没经过 WinSCP 加 docker cp 的替换，跑的永远是旧代码。
- **不删旧包直接覆盖。** 错例：把新包 cp 进去就完事，结果容器里同名包新旧并存或残留旧版本。正解：先清空 `/opt/run/jars` 再拷入，验证时三个包的数量与大小都要核对。
- **把生产环境的 CRON 配置原样搬进测试。** 错例：联调时也配每天六点执行，流程验证被迫隔天进行。正解：测试用 Timer driven 长间隔加手动启停，CRON 留给生产按需配置。
- **对处理器组内每个处理器单独配调度。** 错例：组里有五六个处理器就配五六个调度策略。正解：只配置处理器组的第一个处理器，其余跟随执行，这是处理器组的既定行为。

## 面试可能被问到的问题

1. 面试官追问：「docker cp 和数据卷挂载各适合什么场景？」
   答：docker cp 是一次性手工拷贝，适合部署单个 jar、脚本这类偶发动作，直观且不依赖预先规划；数据卷是把宿主机目录与容器目录做持久映射，适合配置文件、日志、数据这类需要持续同步或跨容器重建后仍在的内容。本课的 jar 替换用 cp 就够，若追求工程化，把 `/opt/run/jars` 挂成卷再配合发布脚本会更顺。
2. 面试官追问：「为什么 jar 要打成带依赖的包？」
   答：集群容器里没有现成的依赖库，Spark 只提供运行时骨架。带依赖的 jar 把 Spark SQL、HBase client、ES 的 Spark 支持等全部打进去，spark-submit 一条命令就能跑，不依赖容器内 classpath 的维护。代价是包体大、传输慢，以及个别依赖会与集群自带版本冲突，需要用 provided 或 relocation 处理。
3. 面试官追问：「Timer driven 与 CRON 驱动在 NiFi 里的本质区别是什么？」
   答：Timer driven 是相对时间，从上一轮执行结束后再等 Run Schedule 指定的间隔，任务慢了会自动顺延，适合自循环、测试类流程；CRON 是绝对时间的日历语义，表达式命中就触发，与上一轮是否跑完无关，适合每天定点、每周定时的生产任务。选型的分界是要不要「挂钟时刻」这个概念。
4. 面试官追问：「换包之后需要重启 NiFi 吗？」
   答：不需要。jar 是由调度脚本每次触发时通过 spark-submit 现场提交给 Spark 集群的，进程级加载，替换文件后下一轮调度自然用新包。需要重启的是长驻类服务，比如改了 NiFi 自身配置或容器内常驻程序；理解这一点的前提是分清哪些代码以进程形态常驻，哪些以任务形态按次运行。
5. 面试官追问：「如何确认容器里跑的确实是新代码？」
   答：三个手段叠加，一是文件层面核对容器内 jar 的大小与修改时间；二是调度执行时到 Spark Master 的 8080 页面看任务描述与运行应用，确认主类与提交时间；三是在结果侧核对行为变化，比如新参数化逻辑生效后按指定日期统计才有数。发布验证永远要有一条业务侧证据，不能只看命令执行成功。
