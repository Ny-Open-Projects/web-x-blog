# Druid 数据怎么删：保留规则、软删与物理清理

在 MySQL 里删错数据，一条 DELETE 或者 DROP 就完事；到了 Druid 里会发现找不到行级 DELETE。导入演练时测试数据混进了正式数据源，或者只想清掉某一天的读数，操作方式与关系库的直觉完全不同。原因在段模型：数据一旦入库就固化成不可变的段，删除只能让段整段退出服务，再由后台把文件清掉。

## 先给结论

- Druid 的删除是段级别的「软删加物理清理」：先把段标记为不再使用，查询立即不可见，磁盘释放交给后台完成。
- 常规两条路：在数据源上配置 Retention 保留规则让过期段自动退场；在 Datasources 页的 Actions 里用 Drop data 手动触发删除。
- Drop data 支持两种粒度：按时间区间删（drop data by interval），或整个数据源直接删（drop data source）。
- 删除请求由 Coordinator 在巡检周期里落实，最终由 kill task 物理清理段文件，物理删除不可逆。
- 删除只作用于已入库数据，不影响 supervisor 继续摄入新消息。

## 为什么删除不能按行走

Druid 的存储单元是 segment，每一段覆盖一个时间区间，写入后不再修改，查询时由 Historical 加载这些段提供数据。行级删除意味着要重写段文件，代价与段模型的设计初衷冲突，所以 Druid 把删除定义成段级别的操作：让整段整段的数据退出服务。

```mermaid
flowchart LR
    A["删除请求"] --> B["段标记为不再使用"]
    B --> C["Historical 卸载 查询立即不可见"]
    C --> D["Coordinator 定时巡检"]
    D --> E["kill task 物理删除段文件"]
    E --> F["磁盘空间释放"]
```

这张图的关键分界在第三格与第五格之间：标记完成后，业务视角的数据已经查不到了；存储视角要等 Coordinator 巡检与 kill task 清理两步，期间段文件还占着磁盘。标记动作只改元数据，秒级生效且可以反悔（把段重新标记为使用中即可恢复）；物理清理不可逆，所以交给后台慢慢做，不阻塞线上查询。

## 保留规则：过期数据自动退场

管理台 Datasources 页点数据源的 Retention 列，打开规则编辑框。默认规则是 loadForever，所有段永久加载。规则的主要形态有三种：

- loadByPeriod(P100)：只加载最近一个周期内的段，更早的自动卸载，但文件保留。
- dropByPeriod(P300)：超过这个周期的段直接删除，课程示例里的 P30D 就是这个思路，超过 30 天的数据清掉。
- dropForever：全部删除，演示里就是把 wikipedia 的 loadForever 改成了 dropForever 再保存。

规则自上而下逐条匹配，命中即执行，所以排列顺序有讲究，越特殊的规则放越前面。保存时 Console 会弹出一个变更说明输入框，问为什么要做这次修改，这是管理台的审计设计，改规则时值得把原因写清楚。保存成功后页面提示 Retention rules submitted successfully。

保留规则解决的是「按时间自然淘汰」：数据源持续摄入，老数据按周期自动退场，不需要人定期去删。

## 手动删：Drop data 与按时间区间

紧急清理走 Datasources 页 Actions 列的 Drop data 按钮。点击后弹确认框，询问是否确定删除数据源的全部数据；确认后顶部提示 Data drop request acknowledged, next time the coordinator runs data will be dropped，请求已受理，等 Coordinator 下一次巡检时落实。粒度分两种：

**drop data by interval，按时间区间删。** 只删指定时间范围内的段，适合误导某天数据、只清理一部分记录的场景。

**drop data source，整个数据源删。** 段全部标记为不再使用，数据源从页面上消失，适合下线演练用的数据源。

脱离 Console 用接口同样能做，Coordinator 提供 REST 入口（不同版本路径与参数略有差异，示例按 Druid Coordinator 接口写法补全）：

```bash
# 整个数据源下线，所有段标记为不再使用
curl -X DELETE "http://druid.example.com:8081/druid/coordinator/v1/datasources/wikipedia"

# 只删一段时间区间内的数据
curl -X DELETE "http://druid.example.com:8081/druid/coordinator/v1/datasources/wikipedia?interval=2015-09-12/2015-09-13"
```

请求提交后查询立刻查不到对应数据；磁盘上的段文件要等 Coordinator 巡检把段置为弃用，再由 kill task 从深存储里物理删除。

## 冷链平台里的删除场景

平台数据源 all_device_message 长期摄入，两类典型动作都围绕上面的机制展开。

**清脏数据。** 设备时钟漂移时，某一天可能写进一批时间戳错乱的读数，统计出来全是噪音。按那一天的时间区间删掉即可，supervisor 不受影响，设备修复后的数据照常进库。

**下线测试数据源。** 演练与压测用的数据源连同数据一起清理，直接 drop data source，段标记弃用后由后台回收空间。

有个现象值得留意：演示里 wikipedia 数据源删除后行数归零，Supervisors 页它的 supervisor 依然在 RUNNING，往队列再投新消息又会攒出新数据。删数据与停摄入是两件事，删数据清的是存量，停摄入要在 Tasks 页对 supervisor 做 suspend 操作，两者分开处理。

## 常见误区

- **以为点了 Drop data 数据立刻从磁盘消失。** 错例：删完马上去深存储目录找段文件准备核对。正解：提示语已写明等 Coordinator 下次巡检才删，标记秒级生效，物理清理是异步的。
- **以为删数据源会连 supervisor 一起停掉。** 正解：删除只作用于已入库段，摄入通道照常工作；要停摄入应 suspend supervisor，删数据与停摄入是两个独立操作。
- **把保留规则当紧急删除手段。** 错例：想立刻清数据却去改 dropByPeriod 再等生效。正解：规则是周期性自动淘汰机制，紧急清理走 Drop data 或 Coordinator 接口，立即触发标记。
- **删除前不留退路。** 正解：段文件物理清理后无法恢复；重要数据源先确认源头可重放（Kafka 消息可回溯、离线文件还在），再执行删除。

## 面试可能被问到的问题

1. 面试官追问：「Druid 为什么不支持行级 DELETE？」
   答：数据按段组织，写入后不可变，查询由 Historical 直接加载段提供，行级删除意味着重写段文件，代价与设计初衷冲突。Druid 把删除定义在段级别，让整段数据退出服务，兼顾性能与实现复杂度。
2. 面试官追问：「软删和物理删分别发生在什么时候？」
   答：删除请求提交时先把段标记为不再使用，Historical 随即卸载，查询立刻不可见，这是软删；Coordinator 巡检确认后由 kill task 从深存储物理删除段文件，磁盘空间这时才释放，两步之间有巡检周期的延迟。
3. 面试官追问：「只想删某一天的数据怎么做？」
   答：用按时间区间的删除方式，Console 里走按 interval 的 drop data，或调 Coordinator 的删除接口带上 interval 参数，只把落在该区间的段标记弃用，其他时段数据不受影响。
4. 面试官追问：「retention 规则有哪些形态，怎么生效？」
   答：常见有 loadByPeriod、dropByPeriod、dropForever，配合默认的 loadForever 使用；规则自上而下逐条匹配，命中即执行。Coordinator 按周期评估每个数据源的规则，把不满足加载条件的段卸载或标记删除。
