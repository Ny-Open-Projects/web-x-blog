# Druid 查询的聚合粒度 granularity：从秒到年的三种写法与选型

同一张数据表，小时曲线和天报表都要出，差别的来源就是查询参数里的 `granularity`：按什么时间单位把数据合并起来。这个词看起来只是一个字段，实际牵出时间窗划分、预聚合上限、时区对齐三件事，配错一个，曲线就画错一格。这一节把粒度的写法与影响讲全。

## 先给结论

- `granularity` 是查询在时间维度上的合并单位，配合 `aggregations` 对指标求和或计数，每个时间窗输出一行。
- 三种写法：字符串写法覆盖 second、minute、hour、day 到 year；duration 写法按毫秒划固定窗口；period 写法按 ISO 8601 周期并支持指定时区。
- 粒度越粗，结果行数越少、数值越大；粒度越细，行数越多、查询开销越高。
- 查询粒度不能细于存储粒度，这条上限由导入期的预聚合决定。
- 按「天」聚合中国业务时默认是 UTC 时区，会整体偏移 8 小时，period 写法配 `timeZone` 解决。

## 粒度加聚合：一个词的两层含义

Druid 存的是事件数据：设备读数、页面点击，每条都带时间戳。查询时的第一步是沿时间轴切窗，第二步是在每个窗内对指标做计算，两步合起来叫聚合粒度。以课程里导入的 wikipedia 数据为例，它记录维基百科各栏目的点击事件，原始数据按天内的秒级时间入库，`count` 指标就是点击量，`granularity` 定成小时，就是「每小时各栏目点击了多少次」。

字符串写法支持的单位正好覆盖常见报表口径：second、minute、fifteen_minute、thirty_minute、hour、day、week、month、quarter、year，另有 `all` 表示整个区间合成一行。要查「过去一年某项指标的总和」，粒度选 month 或 year，聚合方式选 sum，两个词就构成了查询的时间骨架。

## 三种写法

**字符串写法**，一个值搞定，最常用：

```json
"granularity": "hour"
```

**duration 写法**，按毫秒划固定长度的窗口，适合字符串写法表达不了的间隔，比如每两小时一段：

```json
{
  "type": "duration",
  "duration": 7200000,
  "origin": "2015-09-12T00:00:00Z"
}
```

`origin` 指定窗口对齐的起点，省略时从纪元起算。每 90 分钟一个窗口、每 6 小时一个窗口这类非整点需求，只有 duration 写法能表达。

**period 写法**，按 ISO 8601 周期书写，`PT1H` 一小时、`P1D` 一天、`P1M` 一月，最大的价值是能指定时区：

```json
{
  "type": "period",
  "period": "P1D",
  "timeZone": "Asia/Shanghai"
}
```

字符串写法的 month、day 按 UTC 划窗，period 写法加了 `timeZone` 之后，一天的边界就是北京时间零点。做国内业务报表，这一项几乎是必配。以上均为 Druid 0.15 的官方粒度写法。

## 实操：一次 groupBy 看清粒度的作用

用一次按小时聚合的 groupBy 查询验证（查询 JSON 为课程画面所示，地址以 example.com 占位）：

```json
{
  "queryType": "groupBy",
  "dataSource": "wikipedia",
  "granularity": "hour",
  "dimensions": ["language"],
  "aggregations": [{ "type": "count", "name": "count" }],
  "intervals": ["2018-01-01T00:00Z/2020-01-01T00:00Z"]
}
```

四个要素各司其职：`granularity` 定时间窗，`dimensions` 的 language 定普通维度分组，`aggregations` 的 count 定聚合方式，`intervals` 定扫描范围。Postman 构造 POST 请求发给查询端点，Header 的 `Content-Type` 必须是 `application/json`，Body 选 raw 再贴 JSON；用 curl 等价发送：

```bash
curl -X POST -H "Content-Type: application/json" \
  --data @query.json http://druid.example.com:8888/druid/v2
```

端点用 Router 的 8888 或 Broker 的 8082 都可以。返回按小时一行一组的统计：课程演示中跑出的结果里，不同 language 分组的 count 分别是 226 和 1134 这样的数值，每组一行，`timestamp` 是所属小时窗的起点。

把 `granularity` 从 hour 换成 day，结果形态立刻变化，文档里按 day 粒度的示例返回长这样：

```json
{
  "version": "v1",
  "timestamp": "2015-09-12T22:00:00.000Z",
  "event": { "count": 1570, "language": null }
}
```

同样的聚合方式，小时窗合并成了天窗，每组行数骤减，count 数值变大；`language` 为 null 是未分类事件归入的那一组。

```mermaid
flowchart LR
    A[秒级事件行] -->|"granularity hour"| B[每小时一行 count 226 1134]
    A -->|"granularity day"| C[每天一行 count 1570]
    B -->|"向上汇总"| C
```

这张图在讲粒度与结果形态的对应关系：同一批秒级事件，小时窗与天窗只是合并单位的差别，天窗的行总能由小时窗向上汇总得到。图后的关键解读：选粒度本质上是在选报表口径，行数、数值大小、查询开销都随之而变。

## 粒度对结果与性能的影响

**结果形态。** 结果行数约等于时间窗数乘以分组数，小时粒度查一年，光时间窗就有八千多个，再乘维度分组，行数直接放大。曲线图选 hour、日报表选 day，粒度跟着展示口径走。

**查询开销。** 粒度粗意味着合并多、返回行少，扫描与序列化的负担都小；粒度细返回行多，网络传输与前端渲染都受影响。跨度大、粒度细的组合要格外谨慎，必要时拆分查询。

**存储上限。** 查询粒度受导入期预聚合的约束：数据按天聚合存储，就还原不出小时曲线；按分钟存，分钟、小时、天都能查。规划数据流时先想清楚未来报表的最细口径，再定导入策略。

## 常见误区

- **查询粒度细于存储粒度。** 错例：导入时按天 roll-up，查询却写 `granularity: hour`，结果里每个天窗只出一个时间戳。正解：导入前确定最细查询口径，让存储粒度等于或细于它。
- **按天聚合无视时区。** 错例：字符串写法 `"granularity": "day"`，天窗按 UTC 零点切，国内业务的数据被错切进相邻两天。正解：period 写法加 `timeZone: Asia/Shanghai`。
- **把 `granularity` 和 `dimensions` 混为一谈。** 正解：`granularity` 是时间维度上的合并单位，`dimensions` 才是普通维度分组，两者共同决定结果行数，少配一个统计口径就少一半。
- **`intervals` 跨度大而粒度细。** 错例：查两年数据按 second 粒度聚合，行数以千万计。正解：收紧时间范围或放宽粒度，展示层需要细粒度时分段查询。

## 面试可能被问到的问题

1. 面试官追问：「Druid 的 granularity 有哪几种写法？」
   答：三种，字符串写法如 hour、day，覆盖常用时间单位；duration 写法按毫秒定义固定窗口，可配 origin 对齐起点；period 写法按 ISO 8601 周期如 P1D、P1M，支持 timeZone，做本地时区报表时用它。
2. 面试官追问：「查询粒度和存储粒度什么关系？」
   答：查询粒度不能细于存储粒度。导入期的 roll-up 已经按存储粒度合并过数据，细于它的部分信息在导入时就没了；反过来，细粒度存储可以任意向上聚合成小时、天。
3. 面试官追问：「为什么按天聚合的结果时间戳不是北京时间零点？」
   答：Druid 默认按 UTC 划时间窗，UTC 零点对应北京时间早上八点。需要本地历法口径时，把粒度改成 period 写法并指定 timeZone 为 Asia/Shanghai。
4. 面试官追问：「粒度选择对性能有什么影响？」
   答：结果行数约等于时间窗数乘分组数，粒度越细行越多，扫描、序列化与前端渲染开销都上升；粒度粗则合并多、开销小。跨度大的区间配细粒度最容易出问题，应收紧范围或放宽粒度。
5. 面试官追问：「聚合查询里的 timestamp 字段是什么含义？」
   答：它是该行结果所属时间窗的起点，粒度是小时就是整点时刻，粒度是天就是当天窗的起点，配合 event 里的聚合值构成一行统计，前端画图直接用它做横轴。
