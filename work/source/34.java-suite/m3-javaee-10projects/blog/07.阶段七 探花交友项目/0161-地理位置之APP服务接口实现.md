# App 位置上报接口：baidu 路径、dubbo 透传与一次真实抓虫

dubbo 侧的 `updateUserLocation` 已经就绪，地理位置功能还差最后一口气：App 端要一个 HTTP 入口，把定位到的经纬度交上来。App 端定位交给百度地图的定位能力，拿到坐标与地名后调服务端上报接口，接口路径因此挂在了 `baidu` 目录下。mock 契约先行，Controller 与 Service 转手就能写完，真正有营养的是联调环节：接口返回 200，数据却没有全对，一条「地址没更新」的真 bug 在这一课被当场抓出来修掉。

## 先给结论

- 契约是 POST `baidu/location`，请求体 JSON 三个参数：`longitude`、`latitude`、`addrStr`；用户身份由 token 解出，不从请求体传。
- Controller 只做解参与状态码，`BaiduService` 用 `@Reference` 引 `UserLocationApi`，当前用户 id 加三个参数直接透传 dubbo。
- 联调抓到真 bug：更新分支漏更新 `address`，上海上报成功后地址还停在北京；补一行 `.set("address", ...)` 修复，再用广州复测全字段通过。
- 测试 APK 装上后每 5 分钟自动上报一次，位移超 500 米立即上报，`user_location` 从此持续沉淀，搜附近有了数据原料。

## 一、契约先行：三个参数一个身份

接口文档上的 mock 契约给出三件事：路径 `baidu/location`，请求头 `Content-Type: application/json`，请求体三个必填参数，经度 longitude、纬度 latitude、位置描述 addrStr。注意请求体里没有 userId，身份由请求头里的 token 经拦截器解析后放进 `UserThreadLocal`，上报人是谁由服务端说了算，客户端没有指定余地。

Controller 按契约落码：

```java
@RestController
@RequestMapping("baidu")
public class BaiduController {

    @Autowired
    private BaiduService baiduService;

    /**
     * 上报地理位置
     */
    @PostMapping("location")
    public ResponseEntity<Void> updateLocation(@RequestBody Map<String, Object> param) {
        try {
            Double longitude = Double.valueOf(param.get("longitude").toString());
            Double latitude = Double.valueOf(param.get("latitude").toString());
            String address = param.get("addrStr").toString();
            Boolean bool = this.baiduService.updateLocation(longitude, latitude, address);
            if (bool) {
                return ResponseEntity.ok(null);
            }
        } catch (Exception e) {
            e.printStackTrace();
        }
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).build();
    }
}
```

路径里的 `baidu` 指的是数据来源：App 端用百度地图的定位能力拿坐标与地名，服务端只是沿用了这层来源命名。服务端代码不依赖任何地图 SDK，收到的就是三个现成的值，将来客户端换高德或其他定位方案，契约不变，服务端一行不用改。

## 二、Service：薄薄一层也要单独存在

`BaiduService` 薄到只剩透传：

```java
@Service
public class BaiduService {

    @Reference(version = "1.0.0")
    private UserLocationApi userLocationApi;

    public Boolean updateLocation(Double longitude, Double latitude, String address) {
        try {
            User user = UserThreadLocal.get();
            this.userLocationApi.updateUserLocation(user.getId(), longitude, latitude, address);
            return true;
        } catch (Exception e) {
            e.printStackTrace();
            return false;
        }
    }
}
```

`@Reference` 引来的是 dubbo 远端实现，调用即发起一次 RPC。这层薄归薄，职责却分得清：Controller 管 HTTP 语义，解参、状态码、异常兜底；Service 管业务语义，谁在上报、成功失败怎么定义。往后再叠位置合法性校验、上报频控、距离跳跃检测，落点都在 Service，Controller 不用动。

```mermaid
flowchart LR
    A["App 定位：百度地图能力"] -->|"longitude latitude addrStr"| B["BaiduController 解参"]
    B --> C["BaiduService 取 UserThreadLocal 用户"]
    C -->|"dubbo：userId 加三参数"| D["UserLocationApiImpl"]
    D --> E["user_location 有则更新无则新增"]
    E -->|"200 或 500"| A
```

整条链路自上而下只有一次真实的写库：dubbo 实现按 userId 查 `user_location`，查不到新增、查到部分更新，这正是上一课铺好的能力，App 接口是它的第一消费者。

## 三、联调抓虫：200 之后的字段级核对

重启 dubbo 服务与 server，用接口测试工具按契约发第一笔请求，请求体取上海的一组坐标：

```json
{
  "longitude": 121.51677520125,
  "latitude": 31.1219412243813,
  "addrStr": "上海"
}
```

在 Controller 与 Service 各打一个断点，请求进来先落 Controller，三个参数依次解出，往下走 Service 透传，dubbo 更新完成后返回 true，响应 200。看似收官，翻库核对 `user_location` 却发现问题：`location` 已经是 121 与 31 这组上海坐标，`address` 还是上一课写进去的「北京」。

回头读实现就明白了，更新分支的 `Update` 对象只动了 `location`、`updated`、`lastUpdated` 三个字段，`address` 从头到尾没进更新清单。修复只差一行：

```java
Update update = Update.update("location", userLocation.getLocation())
        .set("address", userLocation.getAddress())  //补上地址更新
        .set("updated", System.currentTimeMillis())
        .set("lastUpdated", ul.getLastUpdated());
```

重启后再测一轮，这回换广州，坐标 113 与 23 开头，请求发出，断点放行，回库刷新核对：`created` 纹丝不动，`updated` 刷新成本次时间，`location` 与 `address` 同步变成广州的坐标与地名。四个字段一个变化一个不变，各自符合预期，这次才算真通过。

这条 bug 的教学价值超过接口本身：响应 200 只代表调用成功，不代表所有该写的字段都写进去了。跨层写库时，字段清单要拿数据说话，集成验证的断言对象是库里那行文档，不是接口的状态码。

## 四、定时上报与数据闭环

服务端就绪后，装上课程资料提供的测试 APK，它会每 5 分钟自动上报一次位置；位移超过 500 米立即上报的策略同样由客户端实现，服务端不用感知节奏，来一条存一条。跑起来之后 `user_location` 里每个在线用户都有一行持续刷新的位置文档，2dsphere 索引静静待命。

到这一步，搜附近功能需要的数据原料齐了：谁在哪里、什么时候更新的、地名是什么。按距离筛选附近用户的查询接口，后续课程基于这套数据展开，还会给出 MongoDB 版与 Elasticsearch geo 版两种实现对照，本课的上报接口届时原样复用，一行不改。

## 常见误区

- **把 200 当成写库正确的证明。** 错例：响应 200 就宣布通过，字段级问题全部漏网。正解：核对库里文档的 `created`、`updated`、`location`、`address`，该变的变化、不该变的不变，才算通过。
- **userId 从请求体收。** 错例：契约里顺手加个 userId 参数，客户端想报谁就报谁。正解：身份只从 token 解，请求体只装位置本身，从根上掐掉替别人上报的口子。
- **Content-Type 与接收方式不匹配。** 错例：客户端发 JSON，服务端却按表单收参，参数全为 null 转 Double 时抛异常。正解：契约是 `application/json`，服务端就用 `@RequestBody` 接 Map，两端以 mock 文档为准。
- **更新分支照抄新增分支。** 错例：存在记录时也 `save`，主键与 `created` 被新文档覆盖，位置历史被冲掉。正解：更新走 `updateFirst` 并维护完整字段清单，新增字段时两个分支一起过一遍。

## 面试可能被问到的问题

1. 面试官追问：「上报接口为什么叫 baidu，服务端耦合地图厂商了吗？」
   答：路径沿用的是数据来源命名，App 端用百度地图的定位能力取坐标与地名。服务端只收三个普通参数，不依赖任何地图 SDK，客户端换定位厂商时契约不变、服务端零改动。路径命名反映来源而非实现依赖，这层区分要能讲清。
2. 面试官追问：「上报节奏为什么定在位移 500 米或 5 分钟？」
   答：这是精度与成本折中的经验值。上报太勤浪费电量流量还冲击服务端，太疏位置就失真。500 米对公里级的好友搜索完全够用，5 分钟兜底保证驻留用户的位置也不会长期陈旧。参数放配置里，按业务密度随时调。
3. 面试官追问：「怎么防伪造位置或替别人上报？」
   答：userId 由 token 解出，请求体不收身份，防了替别人上报；位置伪造属于客户端信任问题，服务端可以叠加合理性校验，比如相邻两次上报的位移除以时间差得到速度，超出物理可能就拒绝或标记。课程规模下第一层已实现，第二层在 Service 里留好了扩展点。
4. 面试官追问：「地址字段漏更新的 bug，怎么从流程上避免再犯？」
   答：三点。集成验证以库中数据为准，断言具体字段而非状态码；契约字段与写入字段维护成清单，新增字段时逐项过两分支；测试用例覆盖「新增」与「更新」两条支路，本课的 bug 恰好更新支路没有覆盖到全部字段，第二轮复测换城市重报才暴露。
