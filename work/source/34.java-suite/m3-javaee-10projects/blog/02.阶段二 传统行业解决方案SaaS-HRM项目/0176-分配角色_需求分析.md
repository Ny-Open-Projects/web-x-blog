# 分配角色需求分析：一次勾选如何写穿用户、角色、权限三层

权限 CRUD 收尾之后，系统有了权限资源，也有了角色，但它们和「人」还没有连起来。新员工入职，管理员给他挂上「人事经理」这个角色，人事经理这个角色又绑着一组权限，这个人下次登录就能看到对应的菜单。分配角色与分配权限正是 RBAC 模型里承上启下的两个动作：把用户、角色、权限三层串成一条链。本课先不写代码，把交互流程、数据流向和接口契约分析清楚。

## 先给结论

- 分配角色解决「谁能用什么」的入口问题：用户与角色多对多，角色与权限多对多，两条关系各有一张中间表（`pe_user_role`、`pe_role_permission`）。
- 交互入口在员工列表：每行一个「分配角色」按钮，弹层勾选角色提交；角色管理页的「分配权限」是另一条对称的链路。
- 弹层数据全部现成：分配角色时查当前企业全部角色，分配权限时查企业可见的权限（enVisible 为 1），都是既有列表接口换个调用场景。
- 接口契约极简：`PUT /sys/user/assignRoles`，请求体只有用户 id 和角色 id 数组两个字段，一次提交覆盖该用户的全部角色。
- SaaS 企业管理菜单不出现在分配权限弹层，不是漏查，而是它 enVisible 为 0、平台私有，企业侧分配时天然被过滤。

## 一、RBAC 链路上缺的最后两环

用户、角色、权限三张主体表都已就位，RBAC 模型还差两段关系：用户与角色之间、角色与权限之间。设计阶段的结论是两个多对多，各配一张中间表：

| 关系 | 中间表 | 字段 | 谁维护 |
|---|---|---|---|
| 用户 ↔ 角色 | `pe_user_role` | user_id、role_id | 分配角色功能 |
| 角色 ↔ 权限 | `pe_role_permission` | role_id、permission_id | 分配权限功能 |

为什么必须是多对多？一个用户可以身兼数职，既有员工角色又有考勤专员角色；一个角色也面向全公司的同类岗位，一个「人事经理」可以配给张三也可以配给李四。多对多无法在任意一张主体表里用一列表达，中间表是关系型数据库的标准解法。

分配角色和分配权限这两个功能，本质上就是中间表的写入入口。它们不产生任何新主体，只建立连接：分配角色往 `pe_user_role` 里写几行 user_id 加 role_id；分配权限往 `pe_role_permission` 里写 role_id 加 permission_id。写完之后，权限判断的完整链路就通了：用户登录，先查他有哪些角色，再查这些角色绑了哪些权限，菜单和按钮按权限渲染，接口按权限码拦截。

```mermaid
flowchart LR
    U["用户 bs_user"] ---|"多对多 pe_user_role"| R["角色 pe_role"]
    R ---|"多对多 pe_role_permission"| P["权限 pe_permission 及三张子表"]
    A["员工列表：分配角色"] -.写入.-> U
    B["角色管理：分配权限"] -.写入.-> R
```

图上实线是三层主体与两张中间表的关系，虚线是本课与下一课要写的两个功能，各自只碰一段关系。分工明确之后，每个功能的改动范围都很小。

## 二、两个弹层的交互流程

**分配角色的入口在员工列表。** 每行员工后面有「分配角色」操作，点击弹出对话框，里面是当前企业全部角色的复选框。交互分三步：打开弹层时先查该用户已分配的角色并勾上（回显），再查出企业下所有角色渲染复选框，用户勾选调整后提交。

前端组件真实代码把这三步写得很直白：

```javascript
import {findAll} from "@/api/base/role"
import {assignRoles,detail} from "@/api/base/users"

// 打开弹层：回显已分配角色 + 拉取全部角色
toAssignPrem(id) {
    detail({id:id}).then(res1 => {
        this.checkedRoles = res1.data.data.roleIds;
        findAll().then(res => {
            this.id = id;
            this.roles = res.data.data
            this.roleFormVisible=true
        })
    })
},
// 提交：勾选的角色 id 数组 + 用户 id
createData() {
    assignRoles({id:this.id,roleIds:this.checkedRoles}).then(res => {
        this.roleFormVisible=false
    })
}
```

复选框组绑定的 `checkedRoles` 存的就是角色 id，模板里 `el-checkbox` 的 `label` 直接写 `item.id`，勾选结果天然是 id 数组，提交时不需要任何转换。回显那次 `detail` 请求返回的 `roleIds` 就是该用户当前的角色 id 列表，拿它初始化勾选状态，二次打开弹层不会丢失历史分配。

**分配权限的入口在角色管理页。** 「为某角色分配权限」的弹层里是权限树，可勾选的节点来自权限列表接口，参数组合是 type 0 加 enVisible 1，也就是菜单加按钮、只要企业可见的。这里能直接回答一个容易疑惑的问题：权限设置页里明明还有 SaaS 企业管理这类菜单，分配弹层里为什么看不到？因为那是平台侧的管理菜单，enVisible 为 0，属于平台私有资源，租户企业的角色本来就不该拿到，列表接口按 enVisible 过滤后它自然消失。过滤发生在查询层，而不是分配层，这个设计让「平台资源不可分配」成为默认行为，不依赖每个调用点的自觉。

## 三、接口契约：两个字段决定整个写入

用户 api 文件里，分配角色是一条独立的请求封装：

```javascript
export const assignRoles = data => createAPI(`/sys/user/assignRoles`, 'put', data)
```

对应到接口文档，`PUT /sys/user/assignRoles` 的请求体只有两个字段（字段名以前端真实提交为准）：

```json
{
  "id": "1071634835609235456",
  "roleIds": ["1063590243767500800", "1063594283013713920"]
}
```

`id` 是被分配用户的 id，回答「给谁分配」；`roleIds` 是角色 id 数组，回答「分了哪些」。文档示例里这个数组字段写作 `roleId`，与前端代码提交的 `roleIds` 差了一个字母，属于文档与代码脱节的典型，联调以真实请求为准。用一个数组而不是单个角色，意味着接口的语义是「整体设置」：本次提交的数组就是该用户最终的完整角色集合，多选的追加、少选的移除，都以提交为准。这个语义直接决定了后端的实现策略，先清后写或者整体重建关系，下一段代码实现时再展开。

注意请求是 PUT 而不是 POST。资源本身（用户）已存在，这次操作改变的是用户的关联资源，幂等的整体覆盖语义与 PUT 的含义更贴近。前端 `createData` 不做新增或更新分流，同一个接口同时服务首次分配和调整分配两种场景，契约越简单，误用的空间越小。

整条链路收束成一句话：员工列表点「分配角色」，弹层勾选后一次 PUT 请求，把用户 id 和角色 id 数组交给后端，后端负责把这份选择落成 `pe_user_role` 中间表里的若干行。需求分析到此为止，下一课进入代码实现。

## 常见误区

- **把分配角色理解成新增数据**：它不创建用户也不创建角色，只维护两者的关联。接口语义是整体覆盖：本次提交的角色数组就是用户最终的角色集合，不是在旧集合上追加。
- **分配权限弹层里找不到平台菜单就以为查询有缺陷**：SaaS 企业管理这类菜单 enVisible 为 0，属于平台私有资源，分配查询按 enVisible 1 过滤是正确行为，企业侧永远不该拿到它们。
- **回显和列表用同一个接口**：弹层需要两份数据，一份是候选角色（企业全部角色），一份是已分配角色（该用户的 roleIds），来源不同。只查候选列表无法回显历史勾选。
- **请求体里的数组字段名随手改**：前端提交的是 `roleIds` 数组，后端按这个名字取值；改掉任何一端，另一端取到的就是 null，分配悄悄失败。接口文档示例里的 `roleId` 与代码不一致，以真实联通的字段名为准。

## 面试可能被问到的问题

1. 面试官追问：「RBAC 模型的核心思想是什么？」
   答：把「用户能做什么」拆成「用户有什么角色」加「角色有什么权限」两段关系，权限不直接挂到用户身上。用户与角色多对多、角色与权限多对多，各自用中间表维护。好处是授权粒度清晰：岗位变化只改用户角色关系，职责调整只改角色权限关系，不用逐人重新授权。

2. 面试官追问：「用户和角色为什么用中间表，而不是在用户表加一列？」
   答：多对多关系无法用单列表达，一列存多个角色 id 违反第一范式，查询与维护都要靠字符串解析，也无法建外键约束。中间表每行一个用户角色对，天然支持任意组合，SQL 用 join 就能查「某用户的所有角色」或「某角色的所有用户」。

3. 面试官追问：「分配角色的接口为什么设计成整体覆盖，而不是增量添加？」
   答：弹层的交互形态是复选框全集勾选，用户看到的就是最终结果，提交即覆盖，语义与界面一致，也不需要额外的删除接口来取消某个角色。增量语义适合逐条操作的界面（如单项授权按钮），各有适用场景，关键是接口语义要与交互形态匹配。

4. 面试官追问：「分配权限时如何保证平台私有资源不会被企业拿到？」
   答：过滤发生在查询层而不是分配层。权限列表接口支持 enVisible 条件，企业侧的分配弹层按 enVisible 1 查询，平台私有的管理菜单根本不进入候选集；数据库层面也不依赖前端自觉，后端分配接口同样可以校验提交的权限 id 归属，双重防线。

5. 面试官追问：「这个系统的权限校验链路从登录开始怎么走？」
   答：登录认证通过后，按用户 id 查 `pe_user_role` 得到角色集合，再按角色查 `pe_role_permission` 得到权限集合，权限里包含菜单（决定前端渲染哪些导航）、按钮（决定页面操作显隐）和 API（决定接口访问权）。后续请求携带凭证，网关或拦截器按权限码校验接口访问，完整链路就是这两张中间表把三层串起来的结果。
