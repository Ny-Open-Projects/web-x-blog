# 用户实体类设计：字段分组、多对多关联与序列化死循环的剪断方式

系统微服务的骨架立起来了，写业务代码的第一步是把实体类备齐。用户、角色、权限加上三张子表，六个实体的字段量不小，资料包的工具代码里已经全部备好，拷进公共实体模块就能用。真正值得花时间的不是把字段敲一遍，而是读懂三处设计：User 的字段为什么分这么多组、双向多对多的中间表由谁来维护、JSON 序列化的死循环靠什么剪断。

## 先给结论

- 六个实体同住公共实体模块的 `com.example.domain.system` 包：User、Role、Permission 加 Menu、Point、Api 三张子表实体，六个服务将来谁用到谁扫描。
- User 对 Role 是多对多，User 侧用 `@JoinTable` 声明并维护中间表 `pe_user_role`；Role 侧用 `mappedBy` 声明不维护。
- 双向关联的两侧都要加 `@JsonIgnore`，否则对象转 JSON 时互相引用无限递归，接口直接栈溢出。
- Permission 用 `type` 区分菜单、功能、API 三种粒度，用 `pid` 把菜单、按钮、API 串成父子树。
- 三张子表实体与 Permission 主键同值，一对一，各存本粒度专属字段。

## 一、User：一张表里住着三组字段

对照 `bs_user` 的建表语句读 `User.java`，字段虽多，按用途一刀切成三组就清楚了（包名已改为 `com.example`）：

```java
@Entity
@Table(name = "bs_user")
@Getter
@Setter
public class User implements Serializable {
    private static final long serialVersionUID = 4297464181093070302L;

    @Id
    private String id;                 // 主键，雪花算法生成
    private String mobile;             // 手机号码，登录凭证之一
    private String username;           // 用户名称
    private String password;           // 密码
    private Integer enableState;       // 启用状态 0为禁用 1为启用
    private Date createTime;           // 创建时间

    private String companyId;          // 企业ID
    private String companyName;        // 企业名称（冗余）
    private String departmentId;       // 部门ID
    private String departmentName;     // 部门名称（冗余）

    private Date timeOfEntry;          // 入职时间
    private Integer formOfEmployment;  // 聘用形式
    private String workNumber;         // 工号
    private String formOfManagement;   // 管理形式
    private String workingCity;        // 工作城市
    private Date correctionTime;       // 转正时间
    private Integer inServiceStatus;   // 在职状态 1.在职 2.离职
}
```

**登录组**是 `mobile`、`username`、`password`、`enableState`。手机号在建表语句里挂了唯一索引 `idx_user_phone`，一个人一个号，它就是将来的登录账号；`enableState` 是管理开关，禁用态的用户连登录门都进不来。`password` 当前只是普通字符串列，散列加密在认证章节处理。

**归属组**是 `companyId`、`companyName`、`departmentId`、`departmentName`。前一对把用户钉在某个租户企业里，是 SaaS 数据隔离的锚点；后一对把用户挂到组织架构的某个节点上。名称列与 id 列成对出现，是刻意的冗余设计：列表页几乎每次都要显示部门名，存一份省掉连表，代价是部门改名时要同步更新。

**档案组**是入职时间到在职状态那一串，属于人力资源管理属性，本章节的增删改查暂时不碰它们，员工管理章节再登场。一张用户表同时服务权限、组织、员工档案三个模块，字段分组记在心里，写查询时才知道哪些列是本模块的。

## 二、多对多：User 侧维护中间表，Role 侧只声明

用户与角色的多对多落在 User 侧的 `roles` 字段上：

```java
@ManyToMany
@JsonIgnore
@JoinTable(name = "pe_user_role",
    joinColumns = {@JoinColumn(name = "user_id", referencedColumnName = "id")},
    inverseJoinColumns = {@JoinColumn(name = "role_id", referencedColumnName = "id")})
private Set<Role> roles = new HashSet<Role>();   // 用户与角色 多对多
```

`@JoinTable` 的两段配置就是中间表两列的说明书：`joinColumns` 描述本方（用户）在中间表里的列名 `user_id`，`inverseJoinColumns` 描述对方（角色）的列名 `role_id`。中间表 `pe_user_role` 的主键正是这两列的联合主键，同一对用户角色关系插两次直接撞主键。

Role 侧的对应字段只声明关系、不维护关系：

```java
@Entity
@Table(name = "pe_role")
@Getter
@Setter
public class Role implements Serializable {
    @Id
    private String id;
    private String name;         // 角色名
    private String description;  // 说明
    private String companyId;    // 企业id，角色是租户内部数据

    @JsonIgnore
    @ManyToMany(mappedBy = "roles")
    private Set<User> users = new HashSet<User>(0);   // 角色与用户 多对多

    @JsonIgnore
    @ManyToMany
    @JoinTable(name = "pe_role_permission",
        joinColumns = {@JoinColumn(name = "role_id", referencedColumnName = "id")},
        inverseJoinColumns = {@JoinColumn(name = "permission_id", referencedColumnName = "id")})
    private Set<Permission> permissions = new HashSet<Permission>(0);   // 角色与权限 多对多
}
```

`mappedBy = "roles"` 的意思是：这段关系的维护权交给对方 User 的 `roles` 字段，本侧改 `users` 集合不会碰中间表。维护权只能有一侧持有，两侧都写 `@JoinTable` 会生成两张中间表，数据从哪张读都说不清。Role 对 Permission 的关联则由 Role 侧维护，中间表换成 `pe_role_permission`，这与业务直觉一致：分配角色时动的是用户，配权限时动的是角色。

## 三、@JsonIgnore：给序列化剪断死循环

微服务对外返回的全是 JSON 字符串，Jackson 序列化 User 对象时顺着 `roles` 走到 Role，Role 身上又有 `users` 指回 User，再转 User 的 `roles`，往返没有尽头：

```mermaid
flowchart LR
    A["序列化 User"] --> B["进入 roles 集合"]
    B --> C["序列化 Role"]
    C --> D["进入 users 集合"]
    D --> A
```

图里这条环只要不破，递归就一直转下去，最终以 `StackOverflowError` 收场，接口返回 500。`@JsonIgnore` 就是那把剪刀：序列化到这个字段时直接跳过，环在 User 与 Role 两侧各被剪断一次，无论从哪边开始转都出不了两步。

代价是响应里没有 `roles` 字段，前端拿不到用户的角色列表。这不是缺陷而是分工：列表页本就不该背着一堆角色数据跑，用户与角色的指派是独立接口的职责，需要时单独查询再返回。

## 四、Permission 与三个子表实体：type 分流，pid 串树

Permission 实体的 `type` 与 `pid` 在表设计一篇里已经拆过：`type` 的 1、2、3 决定这条权限去哪张子表补细节，`pid` 把菜单、按钮、API 串成父子树。初始化数据里有现成的例子：员工管理是一条 `type=1` 的菜单权限，「用户删除按钮」`type=2` 且 `pid` 指向该菜单，「删除用户 api」`type=3` 且 `pid` 指向该按钮，三层链条一目了然。

三个子表实体的结构与主表一一呼应，以 API 子表为例：

```java
@Entity
@Table(name = "pe_permission_api")
@Getter
@Setter
public class PermissionApi implements Serializable {
    @Id
    private String id;        // 与权限主表 id 同值
    private String apiUrl;    // 接口地址
    private String apiMethod; // 请求类型
    private String apiLevel;  // 权限等级 1通用接口权限 2需校验接口权限
}
```

菜单子表放图标与排序，按钮子表放权限代码与状态，结构与它同构。三张子表没有各自的关联注解，与主表的一对一靠「主键同值」这个约定维持：主表一条 `type=3` 的权限，id 是多少，API 子表里就有一条相同 id 的记录。JPA 层面它们是三个独立实体，关联逻辑由业务代码按 `type` 手工拼接，这正是「权限表不知道自己代表什么」这条设计原则在实体侧的样子。

## 常见误区

- **双向关联漏加 `@JsonIgnore`**：只在 User 侧加了，Role 侧没加，从角色列表接口一进序列化照样死循环。环的两侧都要剪，检查双向多对多的每一个集合字段。
- **维护权两侧都配 `@JoinTable`**：User 侧配了中间表，Role 侧又配一张同名的，Hibernate 建表时直接冲突或生成重复表。规则记死：一侧 `@JoinTable` 维护，另一侧 `mappedBy` 声明。
- **子表实体另造主键**：给 `PermissionApi` 配了独立生成的 id，再想用外键关联主表，一对一退化成一对多。子表 id 必须与主表 `id` 同值，保存权限时一次生成、两处落库。
- **`roles` 集合不初始化**：字段声明成 `private Set<Role> roles;`，新建的 User 对象一调 `getRoles().add()` 就空指针。声明时 `new HashSet<>()` 是这类关联字段的固定写法。

## 面试可能被问到的问题

1. 面试官追问：「双向 ManyToMany 不加 `@JsonIgnore` 会发生什么？」
   答：Jackson 序列化时沿 User 到 Role 再回到 User 无限递归，最终抛 `StackOverflowError`，接口 500。解决办法是在关联的集合字段上加 `@JsonIgnore` 切断序列化路径，或者用 `@JsonManagedReference` 与 `@JsonBackReference` 控制引用方向。

2. 面试官追问：「`mappedBy` 是什么含义，放在哪一侧？」
   答：它声明本侧不维护关联关系，维护权在被引用的那个字段上。多对多里维护侧负责写中间表，另一侧对集合的修改不会落库到中间表。放置原则是跟业务操作走：分配用户角色走 User 侧维护，配置角色权限走 Role 侧维护。

3. 面试官追问：「实体里为什么同时存 `departmentId` 和 `departmentName`？」
   答：典型的读优化冗余。用户列表页高频展示部门名称，冗余一列省掉与部门表的连接查询；代价是部门改名时必须同步更新所有员工的冗余列。适合读多改少、改名低频的场景，属于用空间和一致性维护成本换查询性能。

4. 面试官追问：「主键为什么用 String 存雪花 id，不用数据库自增？」
   答：应用层生成 id 后，保存前就能拿到主键，便于在服务间传递与组装关联；分库分表时自增 id 会冲突，雪花 id 天然全局唯一且趋势递增，对 B+ 树索引友好。用 String 承载是简化处理，对长度敏感的场景可用 long。

5. 面试官追问：「Permission 的 `type` 与 `pid` 各自解决什么问题？」
   答：`type` 解决分流，1 菜单、2 功能、3 API 决定这条权限去哪张子表补专属字段；`pid` 解决层级，把菜单下的按钮、按钮对应的 API 串成父子树，支撑勾选菜单时带出子权限这类联动授权。一个是横向分类，一个是纵向组织。

6. 面试官追问：「实体类为什么放在公共模块，而不是各微服务内部？」
   答：多个微服务要扫同一批实体，抽到公共模块可以一份维护、多处引用，课程工程因此把 domain 独立成模块。代价是实体成了所有服务的公共契约，改一个字段牵动多服务重新编译，严格的服务化实践中实体应归属各服务内部，公共模块只放真正的共享对象，这是教学工程与服务化理想之间的折中。
