# 搭建交易服务工程：导入工程、发布 Nacos 配置与启动验证

> 🔒 安全提示：文中示例的口令/密钥均为课程教学环境演示口径，生产环境的安全要求见《安全与合规须知》。

支付渠道参数配置的功能开发正式开始，第一步是把新角色交易服务跑起来。这一课的工程不再从零手建：资料包里带着一个完整的交易服务工程，导入、配置、启动、验证，四步走完，Nacos 服务列表里就会出现 `transaction-service`。

## 先给结论

- 交易服务工程由父工程 `pay-transaction` 与两个子工程组成：`pay-transaction-api` 定义接口，`pay-transaction-service` 实现接口，典型的 Dubbo 双工程结构。
- 导入工程的方式与企业开发一致：工程代码随资料提供，复制进代码目录后用 IDEA 的 Import Module 按 Maven 模型导入。
- 工程预置了实体类、Mapper、MapStruct 转换类、MyBatis-Plus 与 Swagger 配置，本课只需补 Nacos 侧配置，后续课程在 service 里写业务即可。
- Nacos 里要发布服务主配置 `transaction-service.yaml`（Group 为 `PAY_GROUP`），覆盖 context-path、数据源与 MyBatis-Plus 三段；`bootstrap.yml` 中的 namespace 要替换成自己的 dev 命名空间 ID。
- 启动成功的判据有两个：控制台无报错，Nacos 服务列表里出现 `transaction-service`。

## 从手动创建到导入：搭建方式的变化

商户平台应用与商户服务两个工程是此前手动创建的，从交易服务开始，工程改为导入。这样安排贴近企业实际：公司里的工程通常早已存在于代码仓库，新成员从 Git 上拉取代码就能开发，很少有人从空目录开始手搭。资料包提供了交易服务工程目录，把 `pay-transaction` 目录复制到聚合支付工程的根目录下，再打开 IDEA，通过 Project Structure 的 Modules 窗口执行 Import Module，选择 Maven 模型导入。

导入的对象是三个 Maven 工程：父工程 `pay-transaction`，子工程 `pay-transaction-api` 与 `pay-transaction-service`。导入时 SDK 选 1.8，依赖以 `.iml` 格式管理，一路确认即可。导入完成后工程结构里多出交易服务的两棵源码树。

## 工程结构：api 与 service 的分工

交易服务对外暴露的是 HTTP 还是 Dubbo？这个问题决定着对工程结构的理解。商户平台应用处在平台的接入层，对接前端，提供的是 HTTP 接口；交易服务处在业务服务层，里面绝大部分是对外暴露的 Dubbo 服务。Dubbo 服务的标准结构正是 api 加 service 两件套：api 工程放接口定义与 DTO，service 工程放实现。后续课程的绑定服务类型、查询渠道列表、保存渠道参数接口，都会按这个结构落位。

api 工程的 DTO 已经备好，`PlatformChannelDTO`、`PayChannelDTO`、`PayChannelParamDTO` 等都在 `com.study.pay.transaction.api.dto` 包下：

```java
@ApiModel(value = "PlatformChannelDTO", description = "平台支付渠道")
@Data
public class PlatformChannelDTO implements Serializable {

    @ApiModelProperty("支付渠道ID")
    private Long id;

    @ApiModelProperty("支付渠道名称")
    private String channelName;

    @ApiModelProperty("支付渠道编码")
    private String channelCode;
}
```

service 工程预置的基础代码分四类。实体类 `PlatformChannel`、`PayChannel`、`AppPlatformChannel`、`PayChannelParam` 等与交易库三张基础表一一对应；`mapper` 包下是继承 `BaseMapper` 的 Mapper 接口与 XML 映射文件；`convert` 包下是 MapStruct 转换器；`config` 包下是 MyBatis-Plus 与 Swagger 两个配置类。MyBatis-Plus 配置类上 `@MapperScan("com.study.pay.**.mapper")` 扫描全部 Mapper，分页与性能分析插件也已注册。启动类本身极简：

```java
@SpringBootApplication
@EnableDiscoveryClient
public class TransactionBootstrap {
    public static void main(String[] args) {
        SpringApplication.run(TransactionBootstrap.class, args);
    }
}
```

`@EnableDiscoveryClient` 把服务注册进 Nacos 服务发现，`SpringApplication.run` 完成启动。service 工程的 pom 已声明 nacos-config、nacos-discovery、dubbo、mybatis-plus、druid、mysql、freemarker、redis 等依赖，后续加缓存能力时不需要再动依赖清单。

## Nacos 配置：发布 transaction-service.yaml

导入了工程不等于万事俱备，配置必须自己接上。`bootstrap.yml` 里 `spring.application.name` 是 `transaction-service`，`file-extension` 是 yaml，两者拼出服务主配置的文件名 `transaction-service.yaml`，Nacos 配置中心里还没有这个文件，需要新建发布。Group 按项目约定选业务组 `PAY_GROUP`，不要留在默认分组。

发布的内容按讲义口径分三段覆盖，通用配置里已有的项，这里按交易服务的需要覆盖：

```yaml
#覆盖 spring-boot-http.yaml 的项目
server:
  servlet:
    context-path: /transaction
#覆盖 spring-boot-starter-druid.yaml 的项目
spring:
  datasource:
    druid:
      url: jdbc:mysql://127.0.0.1:3306/pay_transaction?useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai&useSSL=false
      username: root
      password: 123456
#覆盖 spring-boot-mybatis-plus.yaml 的项目
mybatis-plus:
  typeAliasesPackage: com.study.pay.transaction.entity
  mapper-locations: classpath:com/study/pay/*/mapper/*.xml
```

三段各有指向。context-path 覆盖成 `/transaction`，交易服务若有 HTTP 接口就从这个路径进入；数据源连交易库 `pay_transaction`，库在环境搭建时已建好，账号密码按本机环境填写，课程环境为 root/123456；MyBatis-Plus 两项指明实体别名包与 Mapper XML 的扫描位置，XML 与接口同放在 java 源码目录的 mapper 包下，所以路径写作 classpath 下的包路径。

发布完成后还差一步，让工程找得到这份配置。`bootstrap.yml` 中 discovery 与 config 的 namespace 还是样例值，必须替换成自己 Nacos 里 dev 命名空间的 ID，配置才能挂对地方。工程内的 bootstrap 骨架如下：

```yaml
spring:
  application:
    name: transaction-service
  cloud:
    nacos:
      discovery:
        server-addr: ${nacos.server.addr}
        namespace: ${nacos.namespace}
        cluster-name: DEFAULT
      config:
        server-addr: ${nacos.server.addr}
        file-extension: yaml
        namespace: ${nacos.namespace}
        group: PAY_GROUP
        ext-config:
          - refresh: true
            data-id: spring-boot-http.yaml
            group: COMMON_GROUP
          - refresh: true
            data-id: spring-boot-starter-druid.yaml
            group: COMMON_GROUP
          - refresh: true
            data-id: spring-boot-mybatis-plus.yaml
            group: COMMON_GROUP

dubbo:
  protocol:
    name: dubbo
    port: 20893
  registry:
    address: nacos://127.0.0.1:8848
```

ext-config 挂了三份通用配置，属于通用组 `COMMON_GROUP`；本服务自己的覆盖项走服务主配置，属于业务组 `PAY_GROUP`，两层组各管各的。Dubbo 协议端口 20893，与商户服务的 20890、商户平台应用的 20891 错开，避免本机多服务联调时端口撞车。

## 启动与验证

配置齐了就可以启动。找到 service 工程的启动类 `TransactionBootstrap`，直接运行。工程里业务代码还是空的，但实体、配置、依赖都在，启动没有障碍。判断启动成功看两处：一是控制台，报错会在第一时间滚出来，常见的是数据库连不上与 Nacos 地址不对；二是 Nacos 控制台的服务列表，刷新后看到 `transaction-service` 注册进来，服务发现侧就绪。到这一步交易服务工程的搭建完成，后续课程的接口开发都在这个工程里展开。

## 常见误区

- **导入工程后不配 Nacos 就直接启动。** 错例：服务能跑起来，但配置全是通用配置的默认值，context-path 与数据源都不对。正解：导入后先发布服务主配置 `transaction-service.yaml` 并替换命名空间 ID，再启动。
- **配置发布进了默认分组。** 错例：`transaction-service.yaml` 放在 `DEFAULT_GROUP`，工程按 `PAY_GROUP` 去拉取，配置加载不到。正解：发布侧与引用侧的 Group 必须一致，业务配置归 `PAY_GROUP`。
- **namespace 照抄样例值。** 错例：bootstrap 里的命名空间 ID 是资料里教师环境的，照抄后连到别人的命名空间，配置与服务都找不到。正解：换成自己在 Nacos 创建的 dev 命名空间 ID。
- **把交易服务当成纯 HTTP 服务理解。** 错例：在工程里找 HTTP 接口入口，找不到就认为服务没用。正解：交易服务主要暴露 Dubbo 接口，api 与 service 两个工程对应契约与实现，HTTP 只是辅助。
- **数据源指向商户库。** 错例：url 抄了商户服务的配置，连到 `pay_merchant_service`。正解：交易服务连交易库 `pay_transaction`，微服务一对一建库，不能共用。

## 面试可能被问到的问题

1. 面试官追问：「交易服务的 api 工程和 service 工程为什么要拆开？」
   答：api 工程只放接口定义与 DTO，是 Dubbo 的契约载体，提供方与消费方都依赖它，签名变动在编译期就能暴露；service 工程放实现与内部组件。拆开后契约与实现解耦，消费方不需要引入实现类的任何依赖。
2. 面试官追问：「导入别人的工程时，哪些步骤不能省？」
   答：导入只是把代码放进工作区。Nacos 侧的服务主配置要按本环境重新发布，bootstrap 里的命名空间 ID 要替换成本环境的值，数据库连接要指向本地库并改账号密码。环境相关的配置从来不随代码走，导入后必须逐项核对。
3. 面试官追问：「怎么确认一个微服务启动成功？」
   答：看两处。控制台无报错说明 Spring 容器与各组件装配完成；注册中心的服务列表出现服务名，说明服务发现注册成功。二者缺一不可，只看控制台不报错可能漏掉注册失败的情况。
4. 面试官追问：「服务主配置和通用配置在 Nacos 里怎么划分？」
   答：多个服务共用的配置放通用组，如 spring-boot-http.yaml、spring-boot-starter-druid.yaml、spring-boot-mybatis-plus.yaml，工程通过 ext-config 引入；单个服务自己的覆盖项发布为服务主配置，文件名由服务名加扩展名拼出，放业务组。通用给底，主配置做覆盖。
5. 面试官追问：「@EnableDiscoveryClient 在这里起什么作用？」
   答：开启服务发现能力，配合 classpath 里的 nacos-discovery 依赖，启动时把当前服务以服务名、IP、端口注册到 Nacos，供消费方发现与调用；没有这个开关或依赖，服务只是本地运行，注册中心里不会有它。
