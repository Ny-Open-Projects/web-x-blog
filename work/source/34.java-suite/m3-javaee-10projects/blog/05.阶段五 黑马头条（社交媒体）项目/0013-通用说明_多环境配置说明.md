# 多环境配置：三个 properties、Maven profile 与 -P 打包切换

开发时连本机数据库，测试时连测试库，正式上线后连的是机房里的生产库，账号密码、日志级别、注册中心地址也各不相同。这些值如果写死在代码里，每次换环境都要手改一遍，改完忘一处就是一个线上事故。工程的做法是在每个微服务的工程根目录放三份 properties 文件，分别定义开发、生产、测试环境的参数，构建时按指定的环境把对应那份的值注入配置。每个新微服务创建时把这三份文件连同 Maven 插件配置一起拷过去，重新填写即可，环境切换从此只认参数不认手改。

## 先给结论

- 工程根目录放三份文件：`maven_dev.properties`（开发）、`maven_prod.properties`（生产）、`maven_test.properties`（测试），开发阶段使用测试环境。
- pom.xml 里 maven-resources-plugin 开启 filtering，构建时把 resources 中的占位符替换成当前 profile 对应 properties 里的值。
- profile 通过 `activeByDefault` 指定默认加载 test；打包时用 `mvn package -P test/dev/prod` 显式切换环境。
- 三份文件的键完全一致、值不同，差异集中在数据库连接、日志级别与注册中心地址；生产环境地址换成机房 IP，日志级别不应照抄 DEBUG。

## 同一套键，三份不同的值

先看文件本体。以测试环境为例，文件在工程根目录下，与 pom.xml 平级（数据库按项目改名为 leadnews，驱动类名按 MySQL 8 环境取 cj 包，画面原值为旧类名 `com.mysql.jdbc.Driver`）：

```properties
# log 日志配置
log.level=DEBUG
log.pattern=%d{DEFAULT} [%thread] %-5level %msg%n

# 测试环境数据库连接
mysql.core.jdbc.url=jdbc:mysql://localhost:3306/leadnews?autoReconnect=true&useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
mysql.core.jdbc.username=root
mysql.core.jdbc.password=root
mysql.core.jdbc.driver=com.mysql.cj.jdbc.Driver
mysql.core.root.mapper=mappers
mysql.core.aliases.package=com.study.headline.model.**
mysql.core.tx.scan.package=execution(* com.study.headline.service.**.*(..))

# admin 账户名
admin.username=admin
admin.password=admin

# 注册中心等环境相关地址同样在此维护
```

三份文件的结构完全一样，差异全在值里：开发与测试环境连的是 `localhost` 本地库，生产环境换成机房里数据库服务器的 IP，对应真正的生产实例；日志级别、账号这类条目按环境各自维护。键名统一以后，消费这些值的一方（配置文件、代码、切面）完全感知不到环境差异，它只认 `mysql.core.jdbc.url` 这样的键，值是什么由构建决定。测试环境与生产环境的差异对照如下：

| 键 | 测试环境 | 生产环境 |
|---|---|---|
| 数据库地址 | localhost:3306 | 机房服务器 IP:3306 |
| 日志级别 | DEBUG | 按生产规范收敛 |
| 注册中心地址 | 本机或测试机 | 生产集群地址 |

## Maven profile：把环境钉进构建流程

光有三份文件还不够，得告诉 Maven 构建时用哪一份。pom.xml 里定义了三个 profile，每个 profile 用 `<filters>` 指定自己的参数文件：

```xml
<profiles>
    <profile>
        <id>dev</id>
        <build>
            <filters>
                <filter>maven_dev.properties</filter>
            </filters>
        </build>
    </profile>
    <profile>
        <id>test</id>
        <build>
            <filters>
                <filter>maven_test.properties</filter>
            </filters>
        </build>
    </profile>
    <profile>
        <id>prod</id>
        <build>
            <filters>
                <filter>maven_prod.properties</filter>
            </filters>
        </build>
    </profile>
</profiles>
```

filter 指向根目录下的 properties 文件；如果工程习惯把参数文件收进 config 子目录，这里就写成 `config/maven_dev.properties`，路径与文件实际位置对应即可。profile 生效靠的是 maven-resources-plugin 的过滤开关，构建时它把 resources 目录下文件里的占位符按 filter 文件的键值替换：

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-resources-plugin</artifactId>
    <version>3.2.0</version>
    <configuration>
        <encoding>UTF-8</encoding>
        <useDefaultDelimiters>true</useDefaultDelimiters>
        <resource>
            <directory>src/main/resources</directory>
            <includes>
                <include>**/*</include>
            </includes>
            <filtering>true</filtering>
        </resource>
        <testResource>
            <directory>src/test/resources</directory>
            <filtering>true</filtering>
        </testResource>
    </configuration>
</plugin>
```

默认环境由 profile 的 `activeByDefault` 声明，工程把它指向 test：开发阶段日常构建、日常启动用的都是测试环境参数，与本机联调的习惯一致，不用每次都带参数。占位符的落点在 common 工程的 `mysql-core-jdbc.properties` 这类文件里，形如 `mysql.core.jdbc.url=${mysql.core.jdbc.url}`，等号左边的键是消费方认的键，右边的 `${...}` 会在构建时被 filter 文件里同名键的值替换掉，两条同名键一对照，替换关系就清楚了。

## 打包与启动：-P 一个参数切环境

打包命令直接在 `package` 后跟 `-P` 加 profile id，P 大写：

```bash
# 打生产包：构建时按 maven_prod.properties 过滤占位符
mvn clean package -P prod

# 打测试包（-P test 可省略，test 是 activeByDefault 默认值）
mvn clean package -P test

# 开发包
mvn clean package -P dev
```

不指定 `-P` 时走默认的 test；IDE 里也可以在 Maven 面板勾选 profile 后点打包，效果相同。整条链路如下图：

```mermaid
flowchart LR
    CMD["mvn package -P prod"] --> ACT["激活 prod profile"]
    ACT --> FIL["filter 指向 maven_prod.properties"]
    FIL --> RES["maven-resources-plugin filtering"]
    RES -->|"替换占位符"| JAR["resources 中配置拿到生产参数"]
    JAR --> RUN["应用启动后按生产参数连库与写日志"]
```

关键路径是环境选择发生在构建期而不是运行期：打进 jar 包的配置值在打包那一刻就已确定，产物本身携带了环境属性，运维拿到生产包直接部署即可，不需要在服务器上再改任何文件。

## 与 Spring profile 的关系

Maven 这套机制与 Spring Boot 自带的 `spring.profiles.active` 是两套互补的手段。Maven filter 解决的是「打包进产物的值是什么」，在构建期生效，适合数据库地址、第三方密钥这类随环境变化的参数；Spring 的 profile（`application-dev.yml` 与 `application-prod.yml` 分文件加启动参数指定）解决的是「运行时读哪份配置」，在启动期生效，适合直接以 yml 形式维护的 Spring 参数。两者可以只用其一，也可以配合：构建时用 filter 填一部分占位符，启动时再按 profile 决定读哪份 yml。分清生效时点，就不会出现「改了 yml 却没生效」或「换了 profile 打包值没变」的迷糊。

## 常见误区

- **三份文件只改一份，键名漂移。** 加新键时只写进了 test 文件，prod 文件缺失同名键，构建出的生产包里占位符原样保留，启动即报配置错误；三份文件的键集合必须完全一致，值才轮换。
- **filtering 忘记开启。** 只定义了 profile 与 filter，resources 插件没开 filtering，占位符 `${...}` 会原样打进 jar；判断方法很简单，解包看配置文件里替换了没有。
- **生产环境照抄 DEBUG 日志级别。** DEBUG 全量输出拖慢性能还可能带出敏感数据，生产环境按规范收敛到 INFO 或 WARN， pattern 保持一致便于日志采集。
- **把 Maven profile 与 Spring profile 混为一谈。** 前者是构建期占位符替换，后者是运行期配置文件选择，机制、时点、维护对象都不同；出问题先确认改的是哪一层的配置。

## 面试可能被问到的问题

1. 面试官追问：「Maven 的 profile 多环境切换是怎么工作的？」
   答：pom 里定义多个 profile，每个 profile 用 build 下的 filters 指向一份参数文件，maven-resources-plugin 开启 filtering 后，构建时会把 resources 中文件的占位符替换成当前激活 profile 参数文件里的值。activeByDefault 指定默认环境，打包时用 `package -P` 显式切换，环境选择固化在构建产物里。
2. 面试官追问：「Maven filter 替换和 Spring Boot 的 profile 有什么区别？」
   答：生效时点不同，Maven filter 在构建期把值写进产物，Spring profile 在启动期决定读哪份配置文件。维护对象也不同，filter 管的是 properties 占位符类参数，Spring profile 管的是 yml 配置。两者可独立使用也可组合，构建期定连接串、启动期定行为开关是常见分工。
3. 面试官追问：「activeByDefault 在什么情况下会失效？」
   答：命令行用 `-P` 显式指定了 profile 时，默认声明就不再生效，以显式指定的为准；另外同一 pom 里其他 profile 被激活（比如按 JDK、操作系统自动激活）也可能使它失效。依赖默认行为有风险，生产打包建议始终显式带 `-P prod`，让意图写进命令与流水线。
4. 面试官追问：「为什么生产环境的日志级别要区别于开发环境？」
   答：开发环境 DEBUG 便于跟踪细节；生产环境日志量巨大，DEBUG 级别会产生海量输出，拖慢性能、撑爆磁盘，还容易在日志里带出参数明文等敏感信息。生产按规范收敛到 INFO 或 WARN，配合集中采集，出问题再按需临时调级。
5. 面试官追问：「新加一个微服务，多环境配置怎么迁移最稳妥？」
   答：三份 properties 连同 pom 的 profiles 与 resources 插件配置一起拷贝，逐键核对键集合一致后，只替换数据库、注册中心这类环境值；打包分别用三个 `-P` 各出一次产物验证占位符替换结果，确认无误再接入流水线。
