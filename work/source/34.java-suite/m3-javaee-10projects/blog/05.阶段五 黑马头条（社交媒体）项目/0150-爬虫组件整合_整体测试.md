# 爬虫组件整合整体测试：从入口 URL 到正文字段的全链路验收

day09 的代码到流程管理器为止全部就位，可是一行都没真正跑过。整体测试把 init、help、content 三级解析串成的全链路点起来，用断点看对象状态、用日志看节奏耗时，顺手把现场暴露出来的问题修掉。这一讲也是 day09 的收官：跑通之后，链路从「配置里的一行入口 URL」推进到「文章页的结构化字段」，解析阶段的活全部干完。

## 先给结论

- 测试类 `@SpringBootTest` 注入 `ProcessingFlowManager`，调 `handle()` 点火，主线程 `Thread.sleep(Integer.MAX_VALUE)` 挂住，否则测试方法一返回容器销毁，抓取半路夭折。
- 测试前做三件准备：初始化 URL 收敛到一个分类、分页补抓页数置 0 不翻页、确认无头浏览器驱动路径有效。
- 断点观察清单：`processFlowList` 五个 Bean 及其顺序，原始数据处理环节灌 URL，三个解析器按 100、110、120 接力。
- 目标页解析跑出 8 个字段全部有值，解析链路验收到位。
- 测试现场修复一处配置：表达式按 class 写而元素实为 id，改配置即生效，规则与代码分离的红利当场兑现。
- 本阶段数据停在 `cl_news_url` 台账层，`cl_news` 文章表要等数据保存环节，验收口径是台账状态加日志。

## 测试类与那一个 sleep

```java
@RunWith(SpringRunner.class)
@SpringBootTest
public class ProcessingFlowManagerTest {

    @Autowired
    private ProcessingFlowManager processingFlowManager;

    @Test
    public void test() throws InterruptedException {
        // 正向入口点火
        processingFlowManager.handle();
        // 抓取是长任务，测试方法一返回容器就销毁，主线程必须挂住
        Thread.sleep(Integer.MAX_VALUE);
    }
}
```

测试要启动完整容器，`@RunWith(SpringRunner.class)` 配 `@SpringBootTest` 让 JUnit 跑在 Spring 的环境里，注入 `ProcessingFlowManager` 等于拿到整台引擎的点火钥匙。真正的关键在那一行 sleep：JUnit 以测试方法返回作为用例结束的标志，上下文随用例销毁，Spider 的抓取线程是跟着容器走的，方法一返回抓取就被掐死在半路。`Integer.MAX_VALUE` 毫秒接近 25 天，语义是「主线程别想返回」，实际验证完手动停掉即可。这一行看似凑数，没有它所有日志都停在启动阶段，是初跑整合测试最容易踩的坑。

## 测试前的三件准备

```properties
# 初始化 URL 清单只保留一个分类入口，收敛爬取范围
crawler.init.url.list=https://news.example.com/category/java
# 分页补抓页数置 0：小于 1 不翻页，空间页只抓第一页
crawler.help.nextPagingSize=0
# 无头浏览器驱动路径必须有效，路径错整个兜底通道失效
crawler.selenium.driver.path=D:/tools/chromedriver.exe
```

三处收敛各有一个理由。初始化 URL 全量加进去，一轮跑完时间不可控，调试期要的是可重复的小链路，只留一个分类入口，变量立刻减半；分页补抓页数置 0，小于 1 直接跳过翻页，空间页只抓第一页，链路最短，日志最好读；无头浏览器驱动路径提前核对，HttpClient 被目标站拦住时兜底通道要靠它，路径无效会让排查在两条通道之间来回跳。键名按工程惯例整理，示例形态以本课写法补全。

## 断点观察：五个 Bean 与一条顺序

在 `startTask` 打断点，第一件要看的是清单。`processFlowList` 注入了实现 `ProcessFlow` 接口的全部环节，一共五个：原始数据处理、下载器、三个解析器。用鼠标停在变量上看内容，顺序必须是「初始化 URL、下载、init 解析器、help 解析器、doc 解析器」，这个顺序由启动时的优先级排序压住，错一个环节，后面解析器就会在没有链接可抽时提前空转。

单步往下走，循环里只有原始数据处理环节的 handle 有实质内容：它从配置读出那个唯一的分类入口，组装条目灌进 Spider 队列。其余环节的 handle 都是空实现，等回调驱动。循环结束，`getSpider().start()` 点火，线程起循环，断点的使命完成，后面的验证交给日志与放行。

## 日志观察：三级接力与字段到齐

放行之后，控制台按固定节奏刷三类日志。第一类是初始化环节的灌入日志，唯一的分类入口 URL 出现在台账与队列里；第二类是下载与解析的开始完成配对日志，每一级都有 url、handleType 与耗时；第三类是字段级日志，「添加数据字段到 page 中的 field」逐条刷出字段名与内容。

```mermaid
flowchart LR
    A["配置初始化 URL"] --> B["原始数据处理环节灌队列"]
    B --> C["Spider 启动"]
    C --> D["下载分类入口页"]
    D --> E["init 解析器 100"]
    E --> F["HELP 链接回灌"]
    F --> G["下载个人空间页"]
    G --> H["help 解析器 110"]
    H --> I["PAGE 链接回灌"]
    I --> J["下载文章页"]
    J --> K["doc 解析器 120"]
    K --> L["8 个字段挂进 page 结果集"]
    L --> M["cl_news_url 台账推进<br/>待保存环节接手"]
```

链路上值得盯住的三段：init 解析器抽出个人空间链接后升格 HELP 回灌，Spider 随即去抓空间页；help 解析器接手空间页，抽出文章链接，本例一条空间 20 篇，分页大小为 0 不补抓，升格 PAGE 回灌；doc 解析器逐篇解析文章页，author、releaseDate、转发数等 8 个字段全部有值，「解析目标页数据完成」带耗时收尾。断点看对象状态，日志看节奏与耗时，两把尺子并用，链路的每一跳都能对上账。

## 结果核对：台账状态与文章表的边界

跑完之后核对数据落点。本阶段的数据停在 URL 台账层，用一条聚合 SQL 看推进状态（示例按本课写法补全）：

```sql
-- 台账推进核对：各文档类型的数量与状态分布
SELECT document_type, handle_type, status, COUNT(*) AS cnt
FROM cl_news_url
GROUP BY document_type, handle_type, status;
```

读数的方法：INIT 行对应入口页，HELP 行对应空间页，PAGE 行对应文章页，各行的 status 反映待抓与完成的分布。PAGE 行的文章地址齐了、字段日志有值，解析链路的验收即告完成。`cl_news` 文章表此刻应为空，字段还停在 page 结果集里，组装与落库属于数据保存环节的活，把验收标准定成「文章表有数」会误判自己失败。

## 测试现场抓出的问题

第一轮测试目标页字段大面积为空，排查发现配置表达式按 class 属性写的，页面元素实际挂在 id 上，把表达式里的定位改过来，字段立刻到齐。一处配置改动，代码一行没动，这正是规则集中注册在配置清单里的设计红利：站点结构与预期不符时，修的是清单不是代码。

## 常见报错与处置

- **请求超时。** 多为驱动路径无效或目标站拦截，HttpClient 与无头浏览器两条通道先后失败。处置顺序：核对驱动路径、换代理验证出口、按站点响应速度回调 `Site` 的超时参数。
- **解析结果为空。** 表达式与页面结构不匹配，class 与 id 用错、站点改版都算。处置：拿最新页面源码局部验证表达式，改配置清单，改完重跑小链路确认。
- **流程卡住没有后续日志。** 大概率是测试方法没有 sleep，容器提前销毁。处置：主线程挂住再观察，确认线程还活着再看抓取间隔参数。
- **同一 URL 反复抓取。** 去重环节尚未上场，同一地址会在多轮里重复出现，属已知边界。处置：测试期收敛入口范围控制重复量，去重组件排上日程后自然收口。

## 常见误区

- **sleep 当成可有可无的仪式。** 错例是写完测试直接跑，日志停在启动段就下结论说代码有 bug。正解是长任务测试必须挂住主线程，容器活着抓取才活着。
- **验收标准定成文章表有数据。** 本阶段数据停在台账层，字段在 page 结果集里，落库要等数据保存环节。正解是按台账状态加字段日志验收，与环节职责对齐。
- **断点跟进 Spider 线程逐帧走。** 抓取是多线程异步循环，断点会改变时序，越走越乱。正解是断点只看 startTask 与各解析器入口的静态状态，节奏与耗时交给日志。
- **调试期全量入口直接开跑。** 错例是配置里几十个分类一次全灌，跑一轮半小时，改一个表达式又要半小时。正解是先收敛到单分类、零分页的小链路，稳定后再放开。

## 面试可能被问到的问题

1. 面试官追问：「整合测试为什么要 sleep 一个极大值？」
   答：JUnit 以测试方法返回为用例结束，Spring 上下文随用例销毁，Spider 的抓取线程跟着容器走，方法一返回抓取就中断。主线程挂住才能让异步任务跑完，这是测试长任务的通用手法，实际项目里会换成计数器或超时等待。
2. 面试官追问：「测试期你通过什么手段确认解析链路正常？」
   答：两个手段并用。断点看静态状态：流程清单的五个 Bean 与顺序、条目的类型字段、字段值；日志看动态节奏：每级解析的开始完成配对、字段逐条落日志、耗时统计。再加上台账状态聚合查询，三级接力每一跳都能对上账。
3. 面试官追问：「字段抽出来是空的，你会怎么排查？」
   答：先看字段日志确认是哪几个字段为空，再判断是抽取问题还是页面问题。取最新页面源码局部跑表达式，多半是 class 与 id 用错或站点改版；表达式无误则查规则清单有没有注册、字段名是否与保存侧一致。修复落在配置清单，重跑小链路确认。
4. 面试官追问：「请求超时的可能原因和处置顺序？」
   答：先查无头浏览器驱动路径，路径无效兜底通道必挂；再换代理验证出口是否被目标站拉黑；然后看目标站响应是否本身变慢，按需调大 Site 的超时参数。排查要从本机配置到网络身份再到站点状态，由近及远。
5. 面试官追问：「为什么调试期要把爬取范围收敛到一个分类？」
   答：抓取是长任务，变量越多定位越难。单分类加零分页把链路压到最短，一轮几分钟跑完，表达式与链路问题都能快速验证，稳定后再逐级放开范围，这是调试爬虫的基本功。
