# 目标页解析器：把文章页源码变成结构化字段

> 🔒 安全提示：文中示例的口令/密钥均为课程教学环境演示口径，生产环境的安全要求见《安全与合规须知》。

解析链走完前两级，手里已经攒下一整批 PAGE 类型的文章链接，剩下的活只有一个：把每一篇的文章页源码变成标题、作者、发布时间、正文这样能入库的字段。这一级是解析侧的第三个子类，也是最后一个，目标页解析器。它跑完，三类页面的解析全部到位，页面源码到结构化数据的转换就闭环了。

这一讲先把子类的身份与钩子写完，再看 `handlePage` 里「取规则清单、工具类跑批、字段回填」的三步走，顺带把正文富文本的清洗与解析结果的去向交代清楚。

## 先给结论

- 第三个子类 `CrawlerDocPageProcessor` 只认 FORWARD 方向与 PAGE 文档类型，优先级 120，排在初始化 100、空间页 110 之后，等链接全部摸全才动手。
- 解析规则从 `CrawlerConfigProperty.getTargetParseRuleList()` 取清单，交给 `ParseRuleUtils` 对页面跑批，抽到的内容回填进规则对象。
- 回填结果按「字段名、内容」成对挂进 WebMagic 的 page 结果集，`putField` 一条调用管一个字段，保存环节按字段名对号入座。
- 正文是富文本，表达式圈定容器之后仍会混进 script、style 这类噪音节点，入库前要有一道清洗兜底。
- 起止日志带耗时、字段逐条打日志，目标页的解析过程全程可回放。

## 目标页解析器的身份

三类页面三个解析器，分工在空间页那一讲已经排定：入口页的源码变成 HELP 链接，空间页的源码变成 PAGE 链接，文章页的源码在最后一级变成字段。目标页解析器沿用模板的写法，类声明与身份钩子如下：

```java
@Component
@Log4j2
public class CrawlerDocPageProcessor extends AbstractCrawlerPageProcessor {

    @Autowired
    private CrawlerConfigProperty crawlerConfigProperty;

    @Autowired
    private CrawlerHelper crawlerHelper;

    @Override
    public boolean isNeedHandleType(String handleType) {
        // 只处理正向任务
        return CrawlerEnum.HandleType.FORWARD.name().equals(handleType);
    }

    @Override
    public boolean isNeedDocumentType(String documentType) {
        // 只认 PAGE 类型的页面，也就是文章详情页
        return CrawlerEnum.DocumentType.PAGE.name().equals(documentType);
    }

    @Override
    public int getPriority() {
        // 100 是初始化，110 是空间页，目标页最后动手
        return 120;
    }
}
```

优先级 120 的意义靠排序兑现：排序时数值小的在前，文章页解析的前提是空间页把文章链接摸全，空间页解析的前提是入口页把空间链接摸全，120 排在整条解析链的末尾，动手时输入天然是齐的。两个身份钩子照旧按 `name()` 字符串比对，方向不对、类型不对的数据都自动滑走，不占用这一级的处理时间。

## handlePage 主流程：备参数、取规则、跑批抽取

钩子的主体分三步，先看完整代码再逐段读：

```java
@Override
public void handlePage(Page page) {
    // 记录起始时间，出口算耗时
    long currentTimeMillis = System.currentTimeMillis();
    // 处理方向从请求属性上取，与条目保持一致
    String handleType = crawlerHelper.getHandleType(page.getRequest());
    // 当前文章页地址
    String url = page.getRequest().getUrl();
    log.info("开始解析目标页, url: {}, handleType: {}", url, handleType);
    // 取目标页解析规则清单
    List<ParseRule> targetParseRuleList = crawlerConfigProperty.getTargetParseRuleList();
    // 页面包装对象与清单一起交给工具类跑批，抽取结果回填进规则对象
    targetParseRuleList = ParseRuleUtils.parseRuleList(page.getHtml(), targetParseRuleList);
    if (null != targetParseRuleList && !targetParseRuleList.isEmpty()) {
        for (ParseRule parseRule : targetParseRuleList) {
            log.info("添加数据字段到page中的field,url: {},handleType: {},field: {},content: {}",
                    page.getUrl(), handleType, parseRule.getField(), parseRule.getContent());
            // 字段名与内容成对挂进 page 结果集
            page.putField(parseRule.getField(), parseRule.getContent());
        }
    }
    log.info("解析目标页数据完成, url: {}, handleType: {}, 耗时: {}ms",
            url, handleType, System.currentTimeMillis() - currentTimeMillis);
}
```

**第一，参数备齐三样。** 时间戳、处理方向、页面地址，一件不少。日志一头一尾各打一条，出口做差得耗时，整链路验收时目标页解析花多久、瓶颈在不在这一级，全靠这组数字说话。处理方向照旧从请求属性上取而不是写死，将来反向回抓复用同一套解析器时不用改一行。

**第二，规则清单与跑批。** 清单的注册位置在配置类，前面前置准备那一讲已经立好规矩：目标页要抽的字段全部以 `ParseRule` 对象集中注册，每条带名称、类型与表达式。清单的形态大致如下（表达式按目标站页面结构定制，示例按本课写法补全）：

```java
parseRules.add(new ParseRule("title", CrawlerEnum.ParseRuleType.XPATH,
        "//h1[@class='article-title']"));
parseRules.add(new ParseRule("author", CrawlerEnum.ParseRuleType.XPATH,
        "//a[@class='author-name']"));
parseRules.add(new ParseRule("publishTime", CrawlerEnum.ParseRuleType.XPATH,
        "//span[@class='publish-time']"));
parseRules.add(new ParseRule("content", CrawlerEnum.ParseRuleType.XPATH,
        "//div[@class='article-content']"));
```

跑批交给 `ParseRuleUtils.parseRuleList`，入参两个：`page.getHtml()` 是 WebMagic 的 HTML 包装对象，页面源码字符串进去就具备 XPath 查询能力，底下是 Jsoup 的 DOM 解析与 Xsoup 的选择器引擎在协作；第二个参数就是规则清单。工具类逐条按表达式抽取，抽到的内容回填进规则对象，「要什么」与「抽到了什么」始终在同一个对象里。规则对象上承载结果的两个取值，`getField` 是规则名对应的入库字段名，`getContent` 是本次抽取回填的内容。

**第三，字段回填。** 循环里核心一行是 `page.putField(parseRule.getField(), parseRule.getContent())`。`Page` 自带一个结果集容器，`putField` 按「字段名、内容」成对往里挂。字段名不是随手起的，它是规则名称的镜像，保存环节就靠这个名字从结果集里取值组装数据，改了字段名保存侧就取不到。

## 正文字段的清洗

`content` 抽出来的是整段富文本 HTML，容器圈得再准，里面也常混着统计脚本、内联样式这类对正文毫无意义的节点。表达式负责圈准容器，容器内部的噪音交给清洗，两层分工明确。清洗动作按主流写法补一份示例，安排在保存前作为最后一道工序：

```java
/**
 * 正文清洗：移除 script、style 等噪音节点，压缩多余空白（示例按本课写法补全）
 */
public String cleanContent(String content) {
    if (StringUtils.isBlank(content)) {
        return content;
    }
    Document document = Jsoup.parse(content);
    // 脚本与样式节点对正文没有价值，整节点移除
    document.select("script, style").remove();
    String text = document.body().html().trim();
    // 连续空白压成一个，避免入库后排版稀碎
    return text.replaceAll("\\s{2,}", "\n");
}
```

清洗位置可以商量，但「清洗独立成一步」不能省：写进表达式里硬抠会让规则变得又长又脆，站点一改版全完；独立成方法后，清洗规则可以单独调整与测试，表达式只管定位。

## 解析结果的去向

字段挂进 page 结果集之后，这一级的任务就完成了。结果的下一站在保存侧：组件整合之后，每页解析完成由流程收口把结果集组装成 `CrawlerParseItem` 待保存形态，进文档队列再落库。解析器自己不碰数据库，职责边界与前面两级完全一致。

```mermaid
flowchart LR
    A["PAGE 条目出队"] --> B["WebMagic 下载文章页"]
    B --> C["process 回调进入模板"]
    C --> D["管理器分发命中的目标页解析器"]
    D --> E["ParseRuleUtils 按清单跑批"]
    E --> F["putField 字段对挂进 page 结果集"]
    F --> G["清洗兜底"]
    G --> H["组装 CrawlerParseItem 待保存"]
```

关键路径从左往右读：抽取与保存之间隔着 page 结果集与条目组装两层，解析器只管把源码变成字段，组装与落库由后面的环节收口，两层解耦让解析逻辑可以单独测试。

## 常见误区

- **字段名随手起。** 错例是 `putField` 的键名与规则清单里的名称对不上，保存环节按字段名取值时全部落空，还不报错。正解是字段名严格镜像规则名称，两处一处定义。
- **解析为空继续往下走。** 错例是清单抽完 content 为空时静默跳过，下游拿到空正文照常组装，脏数据进了库才发现。正解是空值打告警日志，必要时跳过该条目的保存。
- **清洗写进表达式硬抠。** 错例是在 XPath 里用 `not(script)` 层层排除，表达式越写越长还盖不住内联样式。正解是表达式只管圈容器，噪音交给独立清洗方法。
- **在目标页解析器里再发请求。** 错例是发现正文分页后又主动翻页下载，解析器一沾请求就绕开了框架的调度与限流。正解是分页链接升格成条目回灌队列，交给下载环节按节奏抓。

## 面试可能被问到的问题

1. 面试官追问：「目标页解析器和前两级解析器的核心差异是什么？」
   答：前两级抽的是链接，产出新任务；目标页抽的是字段，产出最终数据。抽法上三级共用同一套规则跑批与模板骨架，差异只在规则清单与升格类型，前两级出去的是 HELP、PAGE 链接，目标页出去的是 page 结果集里的结构化字段。
2. 面试官追问：「putField 里的字段最后去了哪里？」
   答：字段挂在 WebMagic Page 的结果集容器里，解析完成后由流程收口把结果集组装成待保存的解析条目，再交给文档管理与保存环节落库。解析器不直接写库，这样落库策略调整时解析代码不动。
3. 面试官追问：「解析规则为什么要做成清单配置而不是写在代码里？」
   答：站点改版是常态，改清单里的表达式就行，代码一行不动；规则对象带名称与类型，抽取结果直接对号入座；清单集中注册在配置类里，评审、回滚、复用都落在同一处。
4. 面试官追问：「正文里的 script、style 怎么处理比较稳妥？」
   答：表达式负责圈定正文容器，容器内的噪音交给独立的清洗方法，用 Jsoup 按 `script, style` 选择器整节点移除，再压缩多余空白。清洗独立成步骤，可以单独测试与调整，不把脆弱逻辑塞进表达式。
5. 面试官追问：「优先级 120 为什么不能是 50？」
   答：优先级决定解析器之间的接力顺序，数值小的先跑。文章页解析依赖空间页抽出的链接，空间页又依赖入口页，120 排在 100 与 110 之后，保证目标页动手时输入已经齐了，写成 50 会先于前两级空转。
