# 补上混合架构的最后一角：Docker 部署主从复制集群并开启同步

两套 PXC 分片已经就绪，架构图里还剩一个角落：存放广告等一般数据的主从复制集群。它和 PXC 的部署思路完全不同，PXC 靠参数把节点「织」进一个集群，主从靠 binlog 位点把两台独立的 MySQL「串」成上下级，多一步配置、多一类失败原因。

这一课把 master 与 slave 两个实例用 Docker 部署出来，配好同步账号与位点，开启复制并验证主从生效。做完这一步，整个混合架构的 6 个 MySQL 实例就全部到位，MyCat 的读写分离路由随时可以接入。

## 先给结论

- 节点规划：master 端口 23306，slave 端口 23307，镜像 `percona:5.7.23`，配置与数据用宿主机目录挂载。
- master 必须开启二进制日志 `log-bin=mysql-bin`，`server-id=1`；slave 的 `server-id=2`，全局唯一，绝不能重复。
- master 上要创建专用同步账号并授予 `REPLICATION SLAVE` 权限，不能用业务账号凑合。
- `CHANGE MASTER TO` 的日志文件名与位点必须抄 `SHOW MASTER STATUS` 的当前输出，不能凭感觉填。
- 验收标准是 `SHOW SLAVE STATUS` 里 `Slave_IO_Running` 与 `Slave_SQL_Running` 同时为 Yes，主库建库建表从库立即可见。

## 一、master：开 binlog、定 server-id、授权同步账号

先建目录结构，配置与数据分开挂载，升级镜像或重建容器时数据不丢：

```bash
# 创建 master 的目录结构
mkdir /data/mysql/haoke/master01 -p
cd /data/mysql/haoke/master01
mkdir conf data
chmod 777 * -R
```

配置文件写三件关键事：开二进制日志、定服务 id、统一 sql_mode：

```bash
# /data/mysql/haoke/master01/conf/my.cnf
[mysqld]
log-bin=mysql-bin #开启二进制日志，主从复制的载体
server-id=1 #服务id，不可重复
sql_mode= STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION
```

`log-bin` 是主从复制的载体，主库所有写操作都记进 binlog，从库靠回放它追平数据；`server-id` 是复制拓扑里每个节点的身份证，主从各不相同才能正确寻址。然后创建容器并启动：

```bash
# 创建并启动 master 容器，端口 23306
docker create --name percona.haoke-master01 \
  -v /data/mysql/haoke/master01/data:/var/lib/mysql \
  -v /data/mysql/haoke/master01/conf:/etc/my.cnf.d \
  -p 23306:3306 -e MYSQL_ROOT_PASSWORD=root percona:5.7.23
docker start percona.haoke-master01 && docker logs -f percona.haoke-master01
```

启动完成后做两件事：建同步账号、记录 master 状态：

```sql
-- 创建专用同步账号并授权
CREATE USER 'repl'@'%' IDENTIFIED BY 'repl';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
FLUSH PRIVILEGES;

-- 记录 binlog 文件名与当前位点，从库要用
SHOW MASTER STATUS;
-- 输出示例：mysql-bin.000003 | 758
```

同步账号只授 `REPLICATION SLAVE`，权限最小化；账号密码同步链路上明文传输，绝不该用 root。`SHOW MASTER STATUS` 输出的文件名和 Position 是从库接入的起点，这一步抄错，后面同步要么缺数据要么直接报错。

## 二、slave：同一套模板，改掉 server-id

slave 的目录结构与 master 完全同款：

```bash
# 创建 slave 的目录结构
mkdir /data/mysql/haoke/slave01 -p
cd /data/mysql/haoke/slave01
mkdir conf data
chmod 777 * -R
```

配置文件复制 master 的模板改一处：`server-id` 换成 2。这是整份配置里唯一不能出错的硬要求，id 重复会导致从库无法在拓扑中注册：

```bash
# /data/mysql/haoke/slave01/conf/my.cnf
[mysqld]
log-bin=mysql-bin #从库可不开，做级联复制时才需要
server-id=2 #服务id，不可重复
sql_mode= STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION
```

创建 slave 容器，命令与 master 同款，只换名字、目录与端口：

```bash
# 创建并启动 slave 容器，端口 23307
docker create --name percona.haoke-slave01 \
  -v /data/mysql/haoke/slave01/data:/var/lib/mysql \
  -v /data/mysql/haoke/slave01/conf:/etc/my.cnf.d \
  -p 23307:3306 -e MYSQL_ROOT_PASSWORD=root percona:5.7.23
docker start percona.haoke-slave01 && docker logs -f percona.haoke-slave01
```

## 三、接入主库并开启同步

在 slave 上执行 `CHANGE MASTER TO`，把主库地址、端口、同步账号和上一步抄下的位点一次配齐：

```sql
-- 在 slave（23307）上执行
CHANGE MASTER TO
MASTER_HOST='192.168.1.18',
MASTER_PORT=23306,
MASTER_USER='repl',
MASTER_PASSWORD='repl',
MASTER_LOG_FILE='mysql-bin.000003',
MASTER_LOG_POS=758;

START SLAVE;
```

文件名与位点来自 master 的 `SHOW MASTER STATUS`：从库从 758 这个位置开始往后回放，起点之前的数据属于初始化范畴，不在复制链路里。开启后立刻验证状态：

```sql
SHOW SLAVE STATUS\G
-- 关键两项：
-- Slave_IO_Running: Yes
-- Slave_SQL_Running: Yes
```

两个线程都为 Yes 才算配置成功，这一对状态是主从排障的第一入口：

```mermaid
flowchart LR
    A["master 23306"] --- A2["binlog 事件，log-bin=mysql-bin"]
    A2 -->|"Binlog Dump 线程推送"| B["slave IO 线程"]
    B --> C["relay log 中继日志"]
    C --> D["slave SQL 线程回放"]
    D --> E["slave 23307 数据更新"]
```

图里对应着两个 Yes 的来历：`Slave_IO_Running` 管「从库能不能收到主库的 binlog」，`Slave_SQL_Running` 管「收到的日志能不能落地回放」，任何一个是 No，主从就断了一环。

## 四、验证：主库建库建表，从库立即可见

在 master 上创建业务库与广告表（这张表在混合架构里就落在主从集群，不走 PXC 分片）：

```sql
-- 在 master（23306）上执行
CREATE DATABASE haoke DEFAULT CHARACTER SET utf8;

-- 示例：广告表骨架，按本课写法补全
CREATE TABLE haoke.t_ad (
  id BIGINT PRIMARY KEY,
  type TINYINT COMMENT '广告类型',
  title VARCHAR(100) COMMENT '广告标题',
  url VARCHAR(200) COMMENT '广告链接',
  created DATETIME,
  updated DATETIME
);
```

到 slave（23307）刷新，库和表同时出现；再在 master 插一条数据，从库立刻可查。到这里主从集群部署完成，混合架构 6 个 MySQL 实例全部就位：4 个组成两套 PXC 分片，2 个组成这套主从，MyCat 的 `dataNode` 配置可以把它们统一纳管起来。

## 常见误区

- **主从 `server-id` 配成一样的。** 复制拓扑里 id 是节点身份，重复后从库无法正常注册，`SHOW SLAVE STATUS` 报「The server id is the same as the master server」类错误。配完核对一遍是标配动作。
- **只看到 IO 线程是 Yes 就开始用。** IO 正常只说明 binlog 收到了，SQL 线程没跑通数据照样不落地。两项必须同时为 Yes，再配合主库写入做实际验证。
- **位点凭印象填。** `MASTER_LOG_FILE` 与 `MASTER_LOG_POS` 必须来自主库 `SHOW MASTER STATUS` 的当前输出，随手写一个位点，轻则缺事务、重则 SQL 线程直接报错停止。
- **拿业务账号当同步账号。** 同步链路只需要 `REPLICATION SLAVE` 权限，用 root 或业务账号扩大了泄露面；专用账号权限最小化，泄露了也只影响复制。
- **把主从当强一致集群用。** 异步复制存在延迟窗口，主库写完从库可能还没追上。这条集群就是为广告这类可容忍丢失的数据准备的，核心数据仍应走 PXC 分片。

## 面试可能被问到的问题

1. 面试官追问：「主从复制涉及哪些线程，各自负责什么？」
   答：主库侧一个 Binlog Dump 线程，负责把 binlog 事件推送给从库；从库侧两个线程，IO 线程接收主库推送写入 relay log，SQL 线程读取 relay log 在本地回放。对应 `SHOW SLAVE STATUS` 里的 Slave_IO_Running 与 Slave_SQL_Running 两项状态。

2. 面试官追问：「`CHANGE MASTER TO` 里的日志文件和位点怎么确定？」
   答：在主库执行 `SHOW MASTER STATUS` 拿当前 binlog 文件名和 Position，从库从这个位点开始回放。填错位点会导致事务缺失或回放报错，全量初始化通常配合主库备份加位点的方式完成。

3. 面试官追问：「`server-id` 冲突会发生什么？」
   答：复制拓扑靠 server-id 标识节点，主从 id 相同时从库无法注册到主库，IO 线程报错断开。一个拓扑内每个节点必须有全局唯一的 id。

4. 面试官追问：「从库需要开 `log-bin` 吗？」
   答：单纯做读库不需要，binlog 是主库向下游传播变更的载体，从库不再往外复制就不用开。要把这台从库级联给下一层从库，或者需要它承担备份恢复，才开启 log-bin。

5. 面试官追问：「主从延迟大了怎么排查和处理？」
   答：先看 `SHOW SLAVE STATUS` 里两个线程是否正常、Seconds_Behind_Master 的数值，再查从库回放是否被大事务、锁等待卡住，以及主库写入峰值是否超出从库单线程回放能力。处理手段包括拆分大事务、提升从库配置、开启并行复制，以及把实时性要求高的读强制路由回主库。
