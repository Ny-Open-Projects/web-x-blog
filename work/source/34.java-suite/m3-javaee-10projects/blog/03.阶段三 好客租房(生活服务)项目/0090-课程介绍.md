# 第六天开篇：给房源接口换上 GraphQL，把前台系统搭起来

前几天的 GraphQL 练习一直跑在内存里的假数据上，`User` 和 `Card` 都是 new 出来的，规范和用法都熟了，
却还没碰过真实业务。第六天补上这一环：把房源查询做成真正的 GraphQL 服务；同时另一条线启动，
前端团队写好的前台系统进场，搭起来、跑起来、和后端对接上，首页轮播广告作为第一个前后端联动的功能。

## 先给结论

- 今天两条主线：用 GraphQL 开发房源接口（按 id 查房源、查房源列表两个服务），以及搭建前台系统并实现首页轮播广告。
- 房源接口的层次是 Dubbo 服务承载业务逻辑，GraphQL 套在外面做查询门面，业务实现和之前没有差别。
- 轮播广告的策略是先用 RESTful 把整条链走通，再原地把接口改造成 GraphQL，两种风格有一份可对照的实现。
- 前端侧引入 Apollo Client 发起 GraphQL 请求，这是前端第一次接入 GraphQL 通信。
- 前台系统的库脚本已经放进资料包，`myhome.sql` 里 10 张表齐备，`swipes` 表就是轮播广告的数据源。

## 主线一：房源接口的两个服务

要开发的接口只有两个：根据房源 id 查询房源数据、查询房源列表。实现顺序从最底层开始：
先写「根据 id 查询房源数据的 Dubbo 服务」，定义接口方法、写实现、连上数据库里的房源表；
确认服务本身没问题之后，再在外面套一层 GraphQL。

分层关系是这样：

```mermaid
flowchart LR
    A["客户端查询语句"] --> B["GraphQL 门面层 GraphQLProvider"]
    B --> C["解析查询并定位 DataFetcher"]
    C --> D["调用 Dubbo 服务"]
    D --> E["业务实现与数据访问"]
    E --> F["数据库房源数据"]
```

关键认知在 B：GraphQL 不是替代 Dubbo，而是替代「每个接口写一个 RESTful 方法」的暴露方式。
房源怎么查、缓存怎么做、事务怎么管，全在 Dubbo 服务那一层，和前几天的写法一致；GraphQLProvider
负责解析查询语句、找到对应字段并把调用转发给服务层。列表查询的接口在单条查询跑通之后照葫芦画瓢，
难点只剩分页参数怎么进查询语句。

测试不用等到前端接入：IDE 里装一个 Altair GraphQL Client 插件就能直接对服务发查询、看响应，
开发过程中随时验证 Schema 写得对不对。这一步还会顺手重构一次 GraphQLProvider 的实现逻辑，
把构建 Schema 和绑定取数器的代码整理成可扩展的样子，为后面不断加接口做准备。

## 主线二：前台系统与轮播广告

前台系统是前端团队已经实现好的工程，这一天的任务是搭起来：工程导入、依赖安装、node 服务启动、
页面能访问，然后走读它的功能模块和数据加载流程，搞清页面数据是从哪个接口来的。这是前后端分离的
标准协作方式：界面长什么样、交互怎么组织由前端负责，后端只管把数据接口提供稳。

轮播广告是前后端的第一个会合点，推进节奏刻意放慢成三步：

1. 分析数据结构和表结构，明确广告数据长什么样、存哪张表；
2. 后端实现查询的 Dubbo 服务，暴露成 RESTful 接口，前端完成整合测试，整条链先跑通；
3. 接口原地把通信方式改造成 GraphQL，前端换成 Apollo Client 发请求，对比改造成本。

**先 RESTful 后 GraphQL 的顺序不是绕路。** 全新链路上同时换数据接口和通信协议，出了问题分不清是
数据错了还是协议错了；先用熟悉的方式验证数据和服务都对，再换通信方式，每一变量独立可控。
改造完成后，同样的广告数据在两种接口风格下各有一条完整实现，差异一目了然。

## 轮播广告的数据已经备好

资料包里的前台系统库脚本 `myhome.sql` 建了 10 张表，覆盖房源、用户、聊天、地图等前台功能，
其中 `swipes` 就是轮播广告表：

```sql
CREATE TABLE `swipes` (
  `id` int(11) NOT NULL AUTO_INCREMENT,
  `original_path` varchar(255) COLLATE utf8_bin DEFAULT NULL,
  `thumbnail_path` varchar(255) COLLATE utf8_bin DEFAULT NULL,
  `status` tinyint(2) DEFAULT NULL,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB AUTO_INCREMENT=4 DEFAULT CHARSET=utf8 COLLATE=utf8_bin;

INSERT INTO `swipes` VALUES ('1', 'public/1.png', 'pic-thumb1.png', null);
INSERT INTO `swipes` VALUES ('2', 'public/2.png', 'pic-thumb2.png', null);
INSERT INTO `swipes` VALUES ('3', 'public/3.png', 'pic-thumb3.png', null);
```

结构很直白：原图路径、缩略图路径加一个状态位，预置的三条数据对应首页三张轮播图。
分析表结构时对着它想两件事就够了：查询接口要返回哪些字段，图片路径是相对路径还是完整 URL、
前端怎么拼访问地址。房源相关的数据则继续走后端服务体系，`myhome.sql` 里的 `homes`、`users` 等
表属于前台系统自己的数据域，两边的库不要混。

## 常见误区

- **以为 GraphQL 要取代 Dubbo。** 业务逻辑、事务、缓存仍然住在 Dubbo 服务层，GraphQL 只是换了
  一种更灵活的查询暴露方式，两层职责不同，不存在谁淘汰谁。
- **以为前台系统要从零写页面。** 界面和交互前端团队已经完成，后端要做的只有三件事：
  把工程跑起来、看懂数据加载流程、把接口对接稳。
- **把 `myhome.sql` 当成后端房源库。** 它是前台系统的库，轮播广告查 `swipes` 表；房源接口的
  数据在后端自己的服务体系里，两套数据域要分清。
- **轮播广告一上来就写 GraphQL。** 通信协议和数据链路同时全新，排错成本高；先 RESTful 走通，
  再原地改造，才有对照组。

## 面试可能被问到的问题

1. 面试官追问：「前后端分离项目里，前后端是怎么协作对接的？」
   答：前端独立工程独立部署，负责页面与交互；后端只提供数据接口。双方先约定接口的路径、参数和
   响应结构，再各自开发，联调阶段对接口进行验证。职责边界清晰，任何一侧可以独立迭代和换人。
2. 面试官追问：「GraphQL 服务和 Dubbo 服务是什么关系？」
   答：Dubbo 服务承载业务逻辑和数据访问，是能力层；GraphQL 是查询门面，负责解析客户端查询、
   校验 Schema 并把字段调用转发到服务层。业务能力不变，暴露方式更灵活，客户端按需取数。
3. 面试官追问：「为什么轮播广告要先做 RESTful 再改造成 GraphQL？」
   答：控制变量。先按熟悉的方式把数据、服务、前端整合全链路验证通过，再把通信协议换成 GraphQL，
   出问题能立刻定位是新协议引入的。同时保留两份实现，便于评估 GraphQL 的实际收益。
4. 面试官追问：「Apollo Client 解决什么问题？」
   答：它是前端的 GraphQL 客户端库，封装查询语句构造、请求发送、响应解析和缓存管理。
   开发者声明要什么数据，Apollo 负责把查询发到端点、把结果映射进组件状态，减少手写请求代码。
5. 面试官追问：「把已有 RESTful 接口改造成 GraphQL，后端要动哪些地方？」
   答：增加 GraphQL 门面层，编写 SDL 声明类型与字段，在 RuntimeWiring 里把字段绑定到已有的
   服务调用上；原有 Dubbo 服务和业务实现不动，改动集中在接口暴露层，这正是分层带来的低改造成本。
