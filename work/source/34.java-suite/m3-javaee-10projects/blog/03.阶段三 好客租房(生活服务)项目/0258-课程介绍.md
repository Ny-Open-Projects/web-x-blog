# 单机 MySQL 的天花板到了：day17 用四种集群方案逐个击破

> 🔒 安全提示：文中示例的口令/密钥均为课程教学环境演示口径，生产环境的安全要求见《安全与合规须知》。

好客租房的数据层一直只有一个 MySQL 实例在扛：Tomcat 服务读写、Redis 缓存挡在前头，底下就是这一台数据库。用户量和数据量涨上来之后，它会先于任何代码出问题。day17 一整天都围着数据库层转，路线是先诊断单机的问题，再把四种集群方案逐个学透并动手实现，收尾回到项目里把库表拆开做综合选型。

## 先给结论

- day17 的主线：分析数据层问题 → 学习集群方案 → 逐个实现 → 综合应用到项目。
- 主从复制（读写分离）是地基：主库负责写、从库负责读，靠 binlog 把数据同步过去，复制是异步的。
- MyCat 是数据库中间件：对应用伪装成一个数据库，内部做分库分表与 SQL 路由，读写分离也靠它落地。
- HAProxy 管负载均衡：在 MySQL 或 MyCat 前面做 TCP 层的请求分发与健康检查。
- PXC 提供另一种复制哲学：同步复制强一致，任何节点都可读写，代价是写入要在所有节点确认。
- 学习顺序即依赖顺序：没有主从就没有读写分离，MyCat 建在多个 MySQL 节点之上，HAProxy 给中间件层再加一道入口。

## 一、先诊断：数据层现在长什么样

课件把项目架构里的数据层画了出来：业务模块与微信小程序的请求打到 Web 服务层，服务层下游是 Redis 缓存与 MySQL 数据库。用图说话：

```mermaid
flowchart TD
    A ["业务模块 Business Module"] --> S ["Web 服务层 Tomcat"]
    W ["微信小程序"] --> S
    S --> R ["Redis 缓存"]
    S --> DB ["MySQL 单实例"]
```

看起来清爽，疼点也全在这台单实例上。**第一面墙，读写争抢。** 房源搜索、详情页这类读请求远多于写请求，缓存能挡掉一部分，但缓存未命中、复杂统计照样落到 MySQL，读和写在同一个实例上互相拖累。**第二面墙，容量上限。** 数据量涨上去，单机的磁盘、内存、备份窗口全都吃紧，索引重建一次比一次慢。**第三面墙，单点故障。** 这台实例一挂，写入口直接没了，项目核心功能停摆，没有第二台机器能顶上。

## 二、四条路线，各对一个症状

课件把方案排成一列，其实是按依赖关系排的，每一条都在解决上一条没解决的问题：

| 方案 | 定位 | 解决什么 | 要付的代价 |
|---|---|---|---|
| 主从复制 | 数据冗余与读写分离 | 主库写、从库读，读压力摊开，数据有热备 | 异步复制有延迟，主库宕机可能丢最近事务 |
| MyCat | 数据库中间件 | 分库分表突破单机容量，SQL 路由对应用透明 | 引入新组件，跨库 join 与分布式事务要绕行 |
| HAProxy | 负载均衡 | 请求分发到多个 MySQL 或 MyCat 节点，坏节点自动摘除 | 多一层转发，配置要维护 |
| PXC | 同步复制强一致集群 | 多节点都可读写，数据强一致，没有主从延迟 | 写入要在全节点确认，写性能随节点数下降 |

主从复制靠 binlog：主库把变更写进二进制日志，从库的 IO 线程拉取、SQL 线程重放，数据就同步过去了。MyCat 在它之上做读写分离与分片，应用连的是 MyCat 的逻辑库，数据实际落在哪台机器它说了算。HAProxy 工作在 TCP 层，给这套集群一个统一入口。PXC 则换了一条路，用同步复制把强一致拿到手，适合一致性要求高的核心数据。

```mermaid
flowchart TD
    P ["单机 MySQL 三面墙"] --> M ["主从复制：读写分离与热备"]
    M --> C ["MyCat：分库分表与读写路由"]
    C --> H ["HAProxy：统一入口与负载均衡"]
    P --> X ["PXC：同步复制强一致"]
    M --> F ["综合应用：项目库表拆分与选型"]
    C --> F
    H --> F
    X --> F
```

四条路线不是四选一：典型落法是主从集群或 PXC 做存储层，MyCat 做中间件，HAProxy 做入口，组合起来用。

## 三、学习路线为什么这么排

主从复制放在第一个，因为后面所有方案都以多个 MySQL 节点为前提，先把「一主多从、数据能同步」跑通，读写分离才有对象。MyCat 排第二，它把这些节点统一成一个逻辑库，应用的 SQL 只写一处，落到主库还是从库、分片落在哪个库都由它路由。HAProxy 排第三，给 MyCat 与 MySQL 层做负载均衡与故障摘除。PXC 排第四，作为异步复制之外的另一条一致性路线学对比。收尾的综合应用回到项目：把好客租房的库表做拆分，判断哪张表适合哪种集群。

方案还没展开，先放两条最小预览感受形态（示例按主流写法补全，课程后面会逐项细讲）。主库打开 binlog 并建好复制账号，就迈出了主从复制第一步：

```ini
[mysqld]
server-id=1
log-bin=mysql-bin
binlog-format=ROW
```

```sql
-- 主库创建复制账号
CREATE USER 'repl'@'192.168.1.%' IDENTIFIED BY 'Repl#123456';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'192.168.1.%';

-- 从库指定主库并启动复制
CHANGE MASTER TO
  MASTER_HOST='192.168.1.7',
  MASTER_USER='repl',
  MASTER_PASSWORD='Repl#123456',
  MASTER_LOG_FILE='mysql-bin.000001',
  MASTER_LOG_POS=154;
START SLAVE;
SHOW SLAVE STATUS\G
```

`SHOW SLAVE STATUS` 里 `Slave_IO_Running` 与 `Slave_SQL_Running` 双 Yes，复制链路就算通了。入口层再看一眼 HAProxy 的形态（同样为补全示例），四个 server 行就是四台可被分发的后端：

```conf
listen mysql-cluster
    bind *:3307
    mode tcp
    balance roundrobin
    server mysql1 192.168.1.7:3306 check
    server mysql2 192.168.1.8:3306 check
```

## 常见误区

- **以为做了主从复制就是高可用。** 异步复制有延迟，主库宕机瞬间还没同步的事务会丢；高可用还要靠故障检测与切换，复制只是地基。
- **把 MyCat 当成一种数据库。** 它是代理中间件，自己不存数据，应用连上去像连 MySQL，数据实际都在后面的节点里。
- **把 PXC 和主从复制当成随便二选一。** 两者一致性语义不同：主从异步、可能有延迟，PXC 同步、强一致但写更慢。按业务对一致性的要求选，核心数据与读多写少的数据可以分开对待。
- **以为 HAProxy 只能转发 HTTP。** 它同样支持 TCP 模式，MySQL 这类四层协议的分发与健康检查正是它的常用场景。

## 面试可能被问到的问题

1. 面试官追问：「单机 MySQL 的瓶颈主要体现在哪几个方面？」
   答：读写并发争抢同一实例、数据量增长后的容量与备份压力、单点故障没有兜底。对应的思路分别是读写分离、分库分表、集群冗余，这也是常见集群方案的分类依据。
2. 面试官追问：「主从复制的原理说一下。」
   答：主库把数据变更写入 binlog，从库 IO 线程连接主库拉取日志写入本地 relay log，SQL 线程重放 relay log 里的变更。默认异步复制，主库提交不等从库确认，所以存在主从延迟与宕机丢事务的风险。
3. 面试官追问：「MyCat 分库分表是怎么对应用透明的？」
   答：应用把 MyCat 当 MySQL 连，SQL 发给 MyCat 后由它解析并按分片规则路由到真实库表，结果聚合后返回。应用感知到的是一个逻辑库，数据物理上分散在多个节点，跨库 join 与分布式事务需要架构上规避。
4. 面试官追问：「HAProxy 在 MySQL 架构里解决什么？」
   答：TCP 模式下它作为统一入口把连接分发到多个后端 MySQL 或 MyCat 节点，配合健康检查把故障节点自动摘除。上层应用只认 HAProxy 地址，后端扩容或切换不需要改应用配置。
5. 面试官追问：「PXC 和主从复制最核心的区别是什么？」
   答：复制方式。主从是异步的，主库提交即返回，从库延迟重放；PXC 基于同步复制，写操作要在多数节点确认后才返回，任何时刻节点间数据强一致。代价是写性能，读多写少的场景主从更常见，强一致要求高的数据适合 PXC。
6. 面试官追问：「让你给一个日增百万级数据的项目设计数据库层，怎么选？」
   答：先看读写比例与一致性要求。读多写少优先主从复制加读写分离，配合缓存；单表数据量持续增长再上 MyCat 分库分表；对一致性敏感的核心表考虑 PXC；最后用 HAProxy 收口做负载均衡与故障转移。方案是组合而非单选，按表逐个定策略。
