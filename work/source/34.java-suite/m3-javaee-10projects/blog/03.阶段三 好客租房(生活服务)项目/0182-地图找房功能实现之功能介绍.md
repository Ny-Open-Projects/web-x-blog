# 地图找房：把房源钉在地图上，缩放之间完成聚合

房源列表页再精致，也给不了「这套房子离地铁站多远、在哪个学区内」的空间感受。地图找房补的就是这一块：打开一张城市地图，房源以点的形式钉在对应的地理位置上，滚动滚轮放大地图，视野里的点随范围聚合成一个个标着数字的圆圈，越放大越具体，直到看见小区级的单个房源。这个功能在房源类网站里做得最好的是链家，课程的演示就对着它的地图找房页面过了一遍，要实现的就是同样的效果，也是整个租房项目里最有亮点的一个功能。

## 先给结论

- 地图找房的交互三件套：地图底图、房源覆盖物、随缩放变化的数据聚合；缩放级别决定展示粒度，城市级看区县聚合圈，街道级看小区点位。
- 点位不能逐个硬画：一个城市上万套房源全画上去，点位互相覆盖、拖动卡顿；按视野范围聚合数量、用带数字的圆圈展示，是这类功能的标准解法。
- 覆盖物不必自研：资料包自带的 `textIconOverlay.js` 是百度地图开放平台的官方开源库 `BMapLib.TextIconOverlay`，专门负责「图标加文字」复合覆盖物的绘制，数字与图标样式按规则自动匹配。
- 数据侧的路线已定：房源点带经纬度入库，前端把地图视野交给后端，按范围查询返回点位；课程后面几课先用 GraphQL 服务接数据，再上 MongoDB 的地理位置索引做动态加载。
- 实现节奏是先静态后动态：下一课先写前端代码把效果画出来，随后再把写死的演示数据替换成真实接口。

## 一、功能长什么样：从城市到小区的逐级下钻

对着链家的效果拆解，地图找房的体验是一条清晰的缩放链路。刚进入页面，看到的是城市全域，每个行政区头上顶着一个圆点，圆点里的数字告诉用户这个区有多少套房，有的实现还会顺带标出区域均价，用户对「房源分布在哪里」一眼就有了整体印象。滚轮往下滚，地图放大一档，视图进入某个区内部的商圈与街道，原来的大圈拆成更多更小的点，数字也变得更具体。继续放大到街道级别，聚合圈消失，具体小区的房源直接以小图标钉在地理位置上，红色小图标代表房源，点开就能看到房源详情。演示里从上海全域一路下钻到人民广场、徐家汇、漕溪北路，每一档缩放都对应一种展示形态。

这条链路背后的决策逻辑是一张分流图：

```mermaid
flowchart LR
    U["用户缩放或拖动地图"] --> Z["缩放级别与视野范围变化"]
    Z --> C{"视野内房源点数量"}
    C -->|成百上千| G["聚合成带数字的圆圈"]
    C -->|数量不多| M["逐个绘制房源点图标"]
    G -->|继续放大，范围缩小| C
    M -->|点开图标| D["查看房源详情"]
```

关键分流在「视野内房源点数量」这个判断上：范围越大、点越多，越要聚合；范围越小、点越少，才逐个绘制。同一个功能界面，缩放级别不同，渲染策略随之切换，这就是地图找房区别于普通地图标注的核心。

## 二、为什么必须聚合：点多了，地图就瞎了

把聚合的动机讲透，得先看不聚合会怎样。假设一个城市有上万套在租房源，最直觉的实现是初始化地图后把所有房源循环画上去，一个房源一个 marker。结果可以预见：上万个 DOM 节点同时挂进地图容器，首屏渲染慢、拖动掉帧，缩放时浏览器直接卡住，密的地方几十个点叠成一团，谁也看不见谁。问题不在地图引擎弱，在渲染策略错，屏幕就那么大，一次能呈现的信息是有限的。

聚合的思路是反过来做减法：只渲染当前视野需要的那一层信息。城市视野下用户关心的不是某一套房，而是「哪个区房源多」，所以把视野内相邻的房源合并成一个覆盖物，用文字标出「多少套」，数量越大圆圈越大，颜色也随数量分档；地图放大后视野缩小，圈内的房源被重新拆开，形成更细一级的聚合点；直到视野内的点少到可以直接逐个绘制，才亮出真实的房源图标。信息密度被缩放级别控制在一个恒定的区间内，地图再大也不卡。

这套机制里「文字加图标」的复合覆盖物有个现成的轮子。课程资料包里带的 `textIconOverlay.js` 就是百度地图开放平台的官方开源库文件，类的头注释把职责写得明明白白：

```js
/**
 * 此类表示地图上的一个覆盖物，该覆盖物由文字和图标组成，从 Overlay 继承。
 * 文字通常是数字（0-9）或字母（A-Z），文字与图标之间有一定的映射关系，
 * 根据该文字和一定的映射关系，自动匹配相应颜色和大小的图标。
 */
var BMapLib = window.BMapLib = BMapLib || {};

// 构造：传入经纬度位置、要显示的文字、可选的一组图标风格
BMapLib.TextIconOverlay = function(position, text, options){
    this._position = position;
    this._text = text;
    this._options = options || {};
    this._styles = this._options['styles'] || [];
    (!this._styles.length) && this._setupDefaultStyles();
};

// 继承自百度地图的基础覆盖物 Overlay
T.lang.inherits(TextIconOverlay, BMap.Overlay, "TextIconOverlay");
```

三个入参与聚合场景严丝合缝：`position` 是聚合点的经纬度，`text` 是要显示的数量，`options` 里的 `styles` 是一组按数量分档的图标风格，不传就走默认的五档样式。库内部处理了覆盖物的初始化、随地图拖拽缩放重绘定位、文字变化时自动匹配对应大小的图标这些脏活。它是点聚合组件家族的底层件，上层聚合器负责「算出视野内有多少点、合并成一个覆盖物」，`TextIconOverlay` 负责「把这个覆盖物画得好看」。下一课写前端代码时，它就是画聚合圈的原料。

## 三、数据从哪来：接口形态预告

前端画什么、画在哪，取决于后端返回什么。地图找房的数据接口与普通列表接口的关注点不同：列表接口按页返回全量字段，地图接口要回答的是「某个地理范围内有哪些点、或者哪些聚合后的点」。一条聚合点位数据大致长这样（示例按本课写法补全，字段以后续课程实际实现为准）：

```json
{
  "id": 1001,
  "name": "徐家汇",
  "lng": 121.437325,
  "lat": 31.194661,
  "count": 128,
  "price": 65000
}
```

`lng` 与 `lat` 是这个点的经纬度坐标，聚合层级下是区块中心坐标，点位层级下是具体小区的坐标；`count` 是范围内的房源数量，驱动覆盖物上的数字与图标样式；`price` 这类区域属性按需扩展。前端拿到这批数据，逐条 `new` 出覆盖物挂上地图即可。

课程给这个接口安排了三步走的改造路线。第一步，前端代码先把效果写出来，数据用静态的演示数据，交互链路先跑通。第二步，房源列表、轮播广告都已经用过 GraphQL 的查询服务，地图找房的数据供给沿用同一套模式，用 GraphQL 服务把静态数据替换成后端查询。第三步，房源的经纬度存进 MongoDB 并建地理位置索引，查询条件直接用地图当前视野的矩形范围，地图拖到哪、缩到哪，查询范围就跟着变，真正实现数据随视野动态加载。静态页、接口层、存储层各占一课，层层次递进。

## 常见误区

- **以为要把全部房源点一次性画上地图。** 上万 marker 同时渲染，首屏与拖动都不可用。正确姿势是按视野与缩放级别分层展示，数量大就聚合，数量小才逐点绘制。
- **以为聚合算法要自己从零写。** 数量统计、圈心计算、缩放联动这些逻辑开源库都已封装，`TextIconOverlay` 负责覆盖物绘制，配对的聚合器组件负责点的合并，工程任务是把它们接上自己的数据。
- **忽略坐标系的统一。** GPS 采集的是 WGS84 坐标，百度地图用的是 BD-09，高德用的是 GCJ-02，拿原始坐标直接往地图上画会出现几百米的系统性偏移。接口入什么坐标系要与所用地图引擎对齐，转换一次到位。
- **把地图找房的接口当普通列表接口来设计。** 列表按分页返回全量字段，地图接口要按矩形视野范围过滤、按区域聚合计数，查询形态完全不同，这也是后面要给 MongoDB 建地理位置索引的原因。

## 面试可能被问到的问题

1. 面试官追问：「什么是地图找房，它比列表找房好在哪？」
   答：把房源按地理位置钉在地图上展示，缩放地图时视野内点位聚合成标数量的圆圈，逐级下钻到具体房源。它补上了列表页缺失的空间维度，用户能直观看到房源分布、区位密度与距离关系，选房决策从「看文字描述」变成「看地理位置」。

2. 面试官追问：「点聚合的原理是什么？」
   答：按当前地图视野与缩放级别，把一定地理范围内的相邻点位合并成一个聚合覆盖物，文字显示范围内的房源数量，数量决定图标的大小与样式；地图放大后视野缩小，聚合重新计算，点被逐级拆开。核心是「信息密度恒定」，渲染的元素数量不随数据总量增长。

3. 面试官追问：「地图找房的数据接口要返回什么，怎么设计？」
   答：返回当前视野范围内的点位列表，每条包含经纬度、房源或区块标识、数量与区域属性。查询条件是地图视野的矩形范围加缩放级别，级别决定走聚合查询还是明细查询；聚合层可以预计算区域汇总数据，避免每次都全量扫描。

4. 面试官追问：「为什么选 MongoDB 做地理位置查询？」
   答：MongoDB 原生支持地理空间索引与查询，给包含经纬度的字段建 `2dsphere` 索引后，可以用 `$near` 查附近、用 `$geoWithin` 查矩形或多边形范围，配合范围过滤与计数聚合就能覆盖地图找房的查询形态，而关系型数据库做这类空间计算要么缺索引支持，要么要引入额外扩展。

5. 面试官追问：「房源点在地图上整体偏移了几百米，会是什么原因？」
   答：典型的坐标系不一致。GPS 原始坐标是 WGS84，国内地图服务商用的是加偏后的坐标系，百度是 BD-09，高德与腾讯是 GCJ-02，拿原始坐标画在加偏底图上就会系统性偏移。解决办法是统一坐标系，入库前或渲染前做一次 WGS84 到目标坐标系的转换。
