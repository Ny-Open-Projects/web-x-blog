# ES 环境搭建：Elasticsearch 7.3.1 单机部署与标的索引库准备

标的快速检索的方案定了：查询走 ES 索引库，同步交给 Logstash。动手开发之前，得先把本机的 ES 环境立起来，并把存放标的信息的索引库和映射建好。这一课全是准备工作，但每一件都是后面 Logstash 同步与检索开发的硬前置：索引库没建，同步无处落数据；映射没配，分词与类型就会乱套。

## 先给结论

- 技术组件三件套：Elasticsearch 7.3.1、IK 分词器、head 图形界面插件，安装配置此前课程都学过，本课按既定配置走一遍。
- 教学环境暂用单机，`elasticsearch.yml` 里以 `discovery.type: single-node` 声明；企业实际部署视情况换集群。
- 索引库名按本项目命名口径记作 `finance_project`，3 个分片、0 个副本，用 head 插件创建。
- 映射相当于索引库的表结构，用 Postman 向 `_mapping` 端点发 POST 请求创建；只有标的名称与描述两个字段参与分词（`ik_max_word`），其余字段不分词。
- head 插件本身是一个前端工程，在根目录执行 `npm run start` 启动，占用 9100 端口。

## 版本与组件清单

三个组件各司其职。Elasticsearch 是检索引擎本体，提供 9200（HTTP，REST API 用）与 9300（TCP 传输）两个端口；IK 分词器是中文分词插件，标的名称、描述这类中文文本字段靠它切词建倒排索引；head 插件是跑在 9100 端口的图形界面，建索引、看分片状态、浏览数据都直观。本机暂用单机环境，版本统一为 7.3.1，版本一致性在这里就要立下规矩，后面 Logstash 也必须用同一个版本，混用版本会出问题。

## elasticsearch.yml 逐行过一遍

配置文件在 ES 安装目录的 `config` 文件夹下。以下配置与讲义一致，集群名与节点名按本项目口径改写，`path.data` 与 `path.logs` 必须换成自己的实际安装路径：

```yaml
cluster.name: finance
node.name: finance_node
network.host: 0.0.0.0
http.port: 9200
transport.tcp.port: 9300
discovery.zen.minimum_master_nodes: 1
bootstrap.memory_lock: true
discovery.type: single-node
http.cors.enabled: true
http.cors.allow-origin: "*"
path.data: D:/elasticsearch-7.3.1/data
path.logs: D:/elasticsearch-7.3.1/logs
```

逐段拆解。`cluster.name` 与 `node.name` 是集群与节点的名字，节点名可随意命名；`network.host: 0.0.0.0` 表示监听本机所有网卡。`http.port` 与 `transport.tcp.port` 是前文说的两个端口。`discovery.zen.minimum_master_nodes: 1` 与 `discovery.type: single-node` 都是单机环境的配套：可用主节点最少一个、以单节点模式运行，免掉集群选主的条件。`bootstrap.memory_lock: true` 让 ES 锁定内存，禁止操作系统把进程内存换出到交换分区。中间两行 `http.cors` 解决跨域问题，head 插件是浏览器里的前端页面，要跨域访问 9200 端口，这两行不配，head 连不上 ES。最下面两行是数据与日志目录，照抄别人的路径没有意义，换成自己的安装路径即可。

这张图在讲本机 ES 环境里各组件的角色与端口关系：

```mermaid
flowchart LR
    H["head 插件 前端工程"] -->|"跨域 HTTP 9100 到 9200"| E["Elasticsearch 7.3.1"]
    P["Postman"] -->|"REST API 创建映射"| E
    E -->|"HTTP 9200"| E2["对外 REST 服务"]
    E -->|"TCP 9300"| E3["节点间传输端口"]
```

## 启动 ES 与 head 插件

ES 在 `bin` 目录下双击 `elasticsearch.bat` 启动。启动画面值得盯一会儿：控制台日志按级别输出，出现 `ERROR` 才说明有问题，满屏 `INFO` 都是正常装载。日志里能看到 IK 分词器被加载的记录，看到插件加载条目逐一出现，最后启动完成。ES 7.3.1 对 JDK 的提示是 11，安装包自带了对应 JDK；实测用本机 JDK 8 也能把这一版本跑起来，环境差异导致的报错优先看日志级别再定位。

head 插件是独立的前端工程，启动方式不是双击脚本，而是在它的根目录打开命令行窗口执行：

```bash
npm run start
```

启动很快，随后浏览器访问 `http://localhost:9100`。页面连上后，顶部输入框填的就是本机 ES 的 9200 地址，head 本质是一个客户端，为 9200 端口上的 ES 提供一层可视化操作界面。

## 创建索引库与映射

两步准备工作对应关系型数据库里的两件事：建库与建表。索引库用 head 创建：点「新建索引」，名称与讲义保持一致填 `finance_project`，分片数 3、副本数 0，副本设 0 是因为单机环境没有第二台机器可以放副本。创建完成后，head 的索引列表里出现这条索引，状态绿色（3 of 3 表示 3 个分片全部就位），此时点开映射信息是空的，因为还没建。

映射相当于数据库的表结构：有哪些字段、每个字段什么类型、哪些字段分词哪些不分词。head 的功能太弱建不了映射，改用 Postman 向映射端点发 POST 请求，地址是 `http://localhost:9200/finance_project/_mapping`，`_mapping` 是固定写法，body 选 JSON 格式，把映射描述作为请求体传过去：

```json
{
  "properties": {
    "id":                { "type": "long" },
    "consumerid":        { "type": "long" },
    "userno":            { "type": "keyword" },
    "projectno":         { "type": "keyword" },
    "name":              { "type": "text", "analyzer": "ik_max_word" },
    "description":       { "type": "text", "analyzer": "ik_max_word" },
    "amount":            { "type": "double" },
    "annualrate":        { "type": "double" },
    "borrowerannualrate":{ "type": "double" },
    "commissionannualrate": { "type": "keyword" },
    "period":            { "type": "integer" },
    "repaymentway":      { "type": "keyword" },
    "projectstatus":     { "type": "keyword" },
    "isassignment":      { "type": "keyword" },
    "type":              { "type": "keyword" },
    "status":            { "type": "keyword" },
    "createdate":        { "type": "date" },
    "modifydate":        { "type": "date" }
  }
}
```

这份映射的字段与标的信息表的列一一对应，小写字段名是后面 Logstash 采集进来的文档字段。类型选择的原则一句话说清：需要按值精确匹配、过滤、排序的用 `keyword` 或数值类型；需要按内容模糊搜索的中文文本用 `text` 并指定 `ik_max_word` 分词器。全表只有 `name`（标的名称）与 `description`（标的描述）两个分词字段，其余一概不分词，这直接决定了后面哪些条件能模糊搜、哪些条件只能精确筛。请求发送后返回 `acknowledged: true` 即创建成功，回到 head 里刷新，映射信息不再是空的，逐字段核对一遍即可收工。

## 常见误区

- **`path.data` 与 `path.logs` 照抄别人的路径。** 错例：把示例配置原样粘贴，两个目录指向别人的桌面路径，启动直接失败。正解：这两行必须改成自己的安装路径，其他行可以照抄。
- **单机环境给副本设 1。** 错例：创建索引时随手设 1 个副本，head 里索引状态变黄。正解：单机没有第二个节点承接副本，副本设 0；副本数的作用是多机容灾，集群部署时再按需调整。
- **映射里把所有字段都设成 `text` 分词。** 错例：图省事全部用 `text` 加默认分词。正解：状态、编码、还款方式这类枚举值用 `keyword` 精确匹配；金额、利率、期限用数值类型参与过滤排序；只有名称与描述这类中文语义文本才需要 `ik_max_word` 分词，乱分词会白白膨胀索引并污染检索结果。
- **head 起不来就怀疑 ES。** 错例：head 页面打不开先去重启 ES。正解：head 是独立前端工程，依赖 Node 环境，先确认 `npm run start` 是否报错、9100 端口是否被占用，再检查 ES 侧的跨域配置两行是否生效。

## 面试可能被问到的问题

1. 面试官追问：「Elasticsearch 的 9200 和 9300 端口各是干什么的？」
   答：9200 是 HTTP 端口，对外提供 REST API，客户端调用、Postman、head 插件都走它；9300 是 TCP 传输端口，用于节点之间的内部通信与集群协调。单机部署时 9300 看似闲置，配置里仍要保留，它是集群语义的一部分。
2. 面试官追问：「索引、映射、文档三个概念怎么对应到 MySQL？」
   答：索引对应数据库里的表（本课的 `finance_project` 对应标的信息表），映射对应表结构（字段名、类型、是否分词），文档对应表里的一行数据。Logstash 同步时一条标的信息就是一篇文档，以表主键作为文档 ID 写入。
3. 面试官追问：「`ik_max_word` 和 `ik_smart` 的区别是什么，标的信息检索该用哪个建索引？」
   答：`ik_max_word` 做最细粒度切分，把文本按词组、词语尽量拆全，索引进的词多、召回率高；`ik_smart` 做粗粒度切分，词少、精确度高。索引侧一般用 `ik_max_word` 保证检索覆盖率，查询侧可搭配 `ik_smart`，本课的标的名称与描述建索引时用的是 `ik_max_word`。
4. 面试官追问：「为什么要给 head 插件配 CORS？」
   答：head 是跑在 9100 端口上的浏览器前端页面，页面 JS 向 9200 端口的 ES 发请求属于跨源请求，被浏览器同源策略拦截。`elasticsearch.yml` 里 `http.cors.enabled: true` 与 `http.cors.allow-origin: "*"` 两行放开跨域限制，head 才能正常访问。
5. 面试官追问：「分片数设 3、副本数设 0 的依据是什么？」
   答：分片数决定索引的数据并行度与容量上限，3 个分片供单机演示足够，生产上按数据量与节点数规划且建好后不可修改；副本数是容灾与读并发的保障，单机没有第二个节点可放副本，设 0，集群部署时至少 1。分片不可变而副本可动态调整，这也是创建索引前要想清楚分片数的原因。
