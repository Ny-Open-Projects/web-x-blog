# 用户投标前后端集成测试：一次满标复测揪出边界判断缺陷

接口④⑤全部实现，2.1 到 2.13 的代码链路已经打通，接下来是把前端页面拉进来做一次完整的集成测试。投标是资金类业务，测试前的准备清单、测试数据的关联关系、逐项验证的顺序都比普通功能苛刻，而且这次测试还真测出了一个问题：标的恰好投满的边界场景被误拦，满标永远达不成。跟着这次测试走一遍，既是一次集成测试示范，也是一次「边界值漏测」的现场修复。

## 先给结论

- 集成测试前先拉两张清单：启动清单（前端工程、Apollo、全部微服务、银行存管系统、Redis、ES）与测试清单（前置校验逐项、投标与交易记录落库、状态更新、满标状态、预期收益）。
- 测试数据必须提前造好并保证关联关系对得上：登录用户要已开户、存管侧要人工充值、标的与借贷双方信息要规范，数据问题会伪装成代码问题。
- 逐项验证顺序：小额投标拦最小金额、超额拦余额、正常投标一笔核对落库与同步状态，最后专攻满标场景。
- 满标复测揪出缺陷：投后剩余额度为 0 时也小于最小投标金额，原判断把它当非法投标抛了异常，修复方式是先排除等于 0 的满标场景再比较。
- 修复后全投一笔让标的满标，标的状态变 `FULLY`，投标功能整体收官。

## 测试前先把清单和数据备齐

业务越复杂，测试前欠的账越多。启动清单照依赖顺序过：前端工程要提前登录好，Apollo、全部微服务工程一个不落，银行存管系统必须起（冻结动作发生在它那），Redis 与 ES 也在列。服务全起之后内存压力不小，16G 的机器占用逼近 80%，测试前把无关程序关掉，否则排障时分不清是代码慢还是机器撑不住。

测试清单把要验证的功能列成条目：前置条件判断（最小投标金额、余额、满标等）逐项试，交易中心保存投标记录，存管代理保存交易记录，处理完后同步状态、满标状态与预期收益的更新，一条条对着过。

比清单更要紧的是测试数据。投标链路牵扯登录、标的、余额多个数据源，它们之间靠用户编码、标的 id 关联，造数据时关联关系必须能对上：登录账号要已开户，存管侧余额要用前面说的改库方式人工充值，被投的标的数据要规范，借款人与投资人信息要齐。**数据没造规范，报出来的错看着像代码 bug，实际是数据问题**，这条经验在资金类测试里反复应验。本次测试选定标的是「左丘」的借款记录，借款总额 12000 元，已有三人出借，剩余可投 4000 元，测试账号存管侧余额 9000 元。

## 前端走一遍：从拦截到正常出借

进入标的详情页点授权出借，前端先把能拦的拦掉。投 50 元提交，提示投标金额不能小于最小投标金额；投 10000 元超过账户余额 9000，前端直接提示余额不足；投 5000 元虽然低于余额，但超过了剩余总额 4000，同样被拦。前端确认出借页的判断逻辑在归档源码里能看到：

```javascript
// 确认出借页提交逻辑 节选自前端工程归档
submitHandle() {
    if (this.userInfo.balance < this.amount) {
        uni.showToast({ icon: 'none', title: '余额不足，请充值后再试！' });
        return false;
    }
    this.request({
        url: 'transaction/my/tenders',
        method: 'POST',
        params: { id: this.$route.query.id, amount: this.amount }
    }).then(res => {
        uni.setStorage({ key: 'lendDataInfo', data: res.data.result, success() {
            uni.navigateTo({ url: '/pages/lend/lendSuccess' });
        }});
    }).catch(err => {
        uni.showToast({ icon: 'none', title: err.data.msg });
    });
}
```

前端的余额拦截只是体验层，后端五道校验在 Postman 阶段已经逐条验证过，这里真正要测的是两边都放行之后，整条链路能不能走通。投 3550 元（投后剩 450），同意协议确认出借，页面返回投标成功并展示预期收益。

落库核对在数据库里做：交易库 `tender` 表多出一条 3550 的投标记录，投标人编码、标的编码、状态字段齐全；存管代理库的交易记录表按创建时间找到新纪录，同步状态已置为已同步；前端返回的预期收益与标的利率、期限对应。**三处数据一致，链路才算真通**，只看页面成功提示不算数。

## 满标场景：测出一个边界缺陷

剩余额度 450 元，正好用来测最后两道校验的边界。投 430 元，投后剩 20 元，低于最小投标金额 100，页面提示「此次投标后标的剩余金额不满足最小投标金额」，拦得正确。

按业务规则，把 450 元全投出去应该满标成功。实际点击确认却报错了，控制台没有任何报错，说明是纯逻辑问题。定位到投后额度的判断处打断点复测，断点里两个值说清了真相：

```java
// 修复前 差值为 0 的满标场景被误判为非法投标
BigDecimal subtract = remainingAmount.subtract(amount);
// 450 全投时 subtract = 0.00 0.00 与最小投标金额 100 比较结果是 -1
if (subtract.compareTo(miniAmount) < 0) {
    throw new BusinessException(TransactionErrorCode.E_150111);
}
```

投后剩余 0.00 元，与 100 比较 `compareTo` 返回 -1，走进了「小于最小投标金额」的分支抛异常。可剩余额度恰好为 0 意味着标被投满，是完全合法且应当放行的场景，判断漏掉了这个边界。修复就是在异常分支里先把 0 排除：

```java
// 修复后 剩余额度恰好为 0 是满标 放行
BigDecimal subtract = remainingAmount.subtract(amount);
if (subtract.compareTo(BigDecimal.ZERO) != 0
        && subtract.compareTo(miniAmount) < 0) {
    throw new BusinessException(TransactionErrorCode.E_150111);
}
```

两个条件连起来读：投后剩余既不是 0（不是满标）、又小于最小投标金额，才拒绝。改完重启交易中心再复测，450 元全投成功，页面展示投标金额与预期收益。最后去标的表核对，「左丘」这笔标的状态已经变成 `FULLY`，满标达成。这条边界缺陷从暴露到修复不到半小时，靠的不是运气，是「先测非法、再测恰好合法」的用例顺序。

## 收官复盘：一条链路牵出的整章能力

测试全部通过，用户投标功能收官。回看这一仗的准备与执行，值得沉淀的有三件事。**第一，集成测试的成功标准是三处数据一致**：前端展示、交易库投标记录、存管侧交易记录与冻结结果互相印证，缺一处核对都算测试没做完。**第二，边界值用例必须显式设计**，投后剩余恰好为 0 这种「恰好合法」的值，顺着正常思路想很难想到专门去测，把它列进测试清单才不会漏。**第三，测试数据的关联关系要提前画出来**，用户编码、标的 id、存管侧记录一环对不上，整条链路的报错会把人引向错误的排查方向。

标的满标之后，下一站是平台管理员审核与放款，投标冻结在存管侧的资金终于要流向借款人，那是第四章最后一块拼图。

```mermaid
flowchart LR
    A["准备清单 启动+测试"] --> B["造数据 开户/充值/标的关联"]
    B --> C["前端拦截验证 最小金额/余额/剩余额度"]
    C --> D["正常投标 3550 落库核对三处一致"]
    D --> E["边界场景 430 拦截正确"]
    E --> F["全投 450 暴露满标误拦缺陷"]
    F --> G["修复边界判断 重启复测"]
    G --> H["标的状态 FULLY 收官"]
```

这张图在讲本次集成测试的推进路径，关键分叉在「全投 450」一步：它同时承担了满标验证与缺陷暴露两个角色，边界用例的价值正体现在这里。

## 常见误区

- **只看页面成功提示就算测试通过。** 错例：投标成功页正常展示就翻篇。正解：交易库投标记录、存管代理交易记录的同步状态、标的状态与预期收益都要去库表核对，页面只是链路的最后一层展示。
- **测试数据随用随造、不核对关联。** 错例：登录账号没开户、存管侧没充值就开测，报错后先去查代码。正解：提前造好数据并核对用户编码与标的 id 的关联关系，把数据问题与代码问题分开定位。
- **边界测试只测非法值不测恰好合法值。** 错例：验证了 430 被拦就认为投后额度校验没问题。正解：把「恰好等于 0」的满标场景写进用例，本次缺陷正是 0 被误判为小于最小投标金额。
- **改完代码不重启就复测。** 错例：修复判断逻辑后直接在页面重试，行为没变化。正解：改动在哪个服务就重启哪个服务，本次是交易中心，重启后再执行满标复测。

## 面试可能被问到的问题

1. 面试官追问：「前后端集成测试前要准备什么？和接口级测试的区别在哪？」
   答：要拉启动清单与测试清单，造好带关联关系的测试数据。接口级测试用 Postman 控制参数、配合断点验证分支；集成测试从前端真实操作进入，验证的是网关、鉴权、多个服务与数据库的整条链路，成功标准是前端展示与多处库表数据一致。
2. 面试官追问：「这次测出的满标误拦缺陷，根因是什么？怎么防？」
   答：投后剩余额度恰好为 0 的满标场景没有从「小于最小投标金额」的判断中排除，`compareTo` 对 0 与 100 也返回负数，被误判为非法投标。防法是把边界值显式列入用例，特别是「恰好等于阈值」「恰好为 0」这类恰好合法的值，资金类校验每个比较分支都要有一个为 0 的用例。
3. 面试官追问：「前端已经做了余额与金额校验，后端为什么还要再校验一遍？」
   答：前端校验只服务正常用户的体验，请求可以被绕过前端直接打到接口。资金安全必须以后端校验为准，最小投标金额、余额、满标、剩余额度五道闸都在交易中心侧执行，前端拦截只是第一层筛子。
4. 面试官追问：「集成测试报错时，怎么区分是数据问题还是代码问题？」
   答：先核对报错涉及的数据在库里的真实状态：账号是否开户、余额是否充值、标的编码与用户编码是否关联正确、标的状态是什么。数据符合预期再走断点看代码分支，本次测试准备阶段就把关联关系核对当作硬性步骤，避免误判方向。
5. 面试官追问：「一次投标成功后，你会核对哪些库表数据？」
   答：交易库投标记录的金额、投标人编码、标的编码、业务状态与可用状态；存管代理库交易记录的流水号与同步状态；存管系统侧余额明细的冻结金额变动；满标场景下标的表状态是否变为满标。四处数据对齐，才能确认冻结链路真正闭环。
