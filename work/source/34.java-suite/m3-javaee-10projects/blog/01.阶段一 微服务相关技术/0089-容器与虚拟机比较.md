# 同一台物理机，虚拟机装三个就吃紧，容器能跑几十个

要理解 Docker 为什么轻，最好把它和传统虚拟机摆在同一张图里比。两者底层都一样：最下面是服务器硬件，往上是宿主机操作系统。分叉点在这之后：虚拟机多垫一层 Hypervisor 虚拟出完整 Guest OS，容器则直接在宿主机操作系统上跑一个 Docker 引擎。少掉的那个 Guest OS，就是体积和启动速度差距的根源。

## 先给结论

- 传统虚拟机在宿主机 OS 之上加 Hypervisor，再虚拟出完整的 Guest OS；Docker 在宿主机 OS 之上只跑 Docker 引擎，容器共享宿主机内核。
- 虚拟机里每个应用都背着一套独立操作系统，内存占用大，单机能虚拟的系统数量受内存限制。
- 容器的二进制和库直接跑在 Docker 引擎上，与宿主机 OS 是「共享内核」的隔离关系，占用体积小。
- 启动虚拟机等于启动一套操作系统，启动容器只是调用宿主机内核能力，速度差一到两个数量级。
- 容器环境依赖宿主机 OS 类型（必须同类），虚拟机则可以虚拟出与宿主机不同类型的操作系统。

## 一、两种架构的层次对比

把两者从下到上拆开看，最底下两层完全相同，分叉在第三层。

```mermaid
flowchart TD
    subgraph VM["传统虚拟机"]
        A1["App A / App B"] --> B1["Bin / Libs"]
        B1 --> C1["Guest OS（多份、可异类）"]
        C1 --> D1["Hypervisor（虚拟层）"]
        D1 --> E1["Host OS（宿主机操作系统）"]
        E1 --> F1["Server（硬件）"]
    end
    subgraph DK["Docker 容器"]
        A2["App A / App B"] --> B2["Bin / Libs"]
        B2 --> C2["Docker Engine"]
        C2 --> E2["Host OS（宿主机操作系统）"]
        E2 --> F2["Server（硬件）"]
    end
```

图里最直观的差异：虚拟机栈里每个应用下面都压着一份 Guest OS，再由 Hypervisor 虚拟硬件；Docker 栈里应用下面只有 Bin/Libs 和 Docker 引擎，Guest OS 这层整个被拿掉了。

## 二、为什么虚拟机更重

传统虚拟化（以 VMware 这类软件为例）的层次是：服务器硬件 → 宿主机操作系统 → Hypervisor（管理虚拟机的软件）→ 多个 Guest OS → 应用。Hypervisor 能虚拟出各类硬件，因此 Guest OS 可以和宿主机 OS 不是同一种类型，宿主机是 Windows 也能虚拟出 Linux。

问题在于每个 Guest OS 都是独立运行的操作系统，要吃掉大量内存才能启动。内存有限，单台物理机能虚拟出来的系统个数就被卡住了。启动一个虚拟机，速度和启动一台真实机器差不多，因为它本来就是引导一整套操作系统。

## 三、为什么容器更轻

Docker 的层次是：服务器硬件 → 本机操作系统 → Docker 引擎 → 二进制与库 → 应用。容器内部看似各有一套「操作系统」，但那其实是通过 Docker 引擎调用宿主机 OS 内核能力实现的隔离，并不是真的再装一份 OS。

**第一，内存是共享的。** 各容器与宿主机 OS 之间是共享关系，不像虚拟机那样每个实例独占一份系统内存，所以硬盘和内存占用都更小。

**第二，启动只是调用内核。** 启动容器并不重新构建操作系统，而是复用宿主机内核来实现等价功能，因此速度极快。课程里提到大多数 Docker 容器启动不到 1 秒，而启动虚拟机要等系统引导完成。

**第三，要接受类型约束。** 容器环境依赖宿主机 OS 类型，宿主机是 Linux，容器也得是 Linux 系；虚拟机则没有这个限制。这是轻量换来的代价。

下面用一组对照感受差异（均为示意命令，非课程原始工程）：

```bash
# 虚拟机：启动一台 Guest OS，耗时按「分钟」计，占用数百 MB 到数 GB 内存
vagrant up ubuntu-vm

# 容器：启动一个隔离环境，耗时按「秒」计，额外占用仅几十 MB
docker run -d --name web nginx:latest
```

再看资源占用的量级差异，同样一台 8G 内存的机器：

```bash
# 虚拟机：受 Guest OS 内存下限限制，通常只能跑 2 ~ 3 个
# 容器：共享内核，轻松跑几十个，彼此通过 Docker 引擎隔离
docker ps --format "table {{.Names}}\t{{.Status}}"
```

## 四、怎么选

需要彻底隔离、要跑和宿主机不同类型的内核或操作系统时，虚拟机更合适，比如测试不同 OS 的兼容性。追求高密度部署、快速启停、和微服务打包分发时，容器是更好的选择。实际生产里常见组合是「物理机 / 云主机上先跑虚拟机做硬隔离，虚拟机内部再用容器做密度和弹性」。

## 常见误区

- **容器里真的有一套独立操作系统**：错。容器复用宿主机内核，只是通过 Docker 引擎做隔离，不是再装一份 OS。
- **容器能跑任意类型的系统**：错。容器环境依赖宿主机 OS 类型，必须同类；要跑异类系统得用虚拟机。
- **容器比虚拟机更安全**：不一定。共享内核意味着隔离边界更薄，多租户强隔离场景仍倾向虚拟机。
- **两者只能二选一**：错。常见做法是虚拟机做底层硬隔离，容器在其上做高密度部署，二者互补。

## 面试可能被问到的问题

1. 面试官追问：「Docker 容器和虚拟机最本质的区别是什么？」
   答：虚拟机通过 Hypervisor 虚拟出完整 Guest OS，每个实例独立占用系统资源；容器共享宿主机内核，只通过引擎做环境隔离，不虚拟操作系统，因此更轻量、启动更快。

2. 面试官追问：「为什么容器启动比虚拟机快那么多？」
   答：启动虚拟机等于引导一整套操作系统，要经历内核初始化等完整流程；启动容器只是复用宿主机已运行的内核，创建可写层和命名空间隔离，几乎没有系统引导开销，通常不到 1 秒。

3. 面试官追问：「容器能不能跑和宿主机不同类型的操作系统？」
   答：不能。容器共享宿主机内核，环境依赖宿主机 OS 类型，必须同类；要跑异类系统只能用虚拟机，因为虚拟机自带 Guest OS。

4. 面试官追问：「为什么说容器更省资源？」
   答：每个虚拟机都背着一份独立操作系统，内存和磁盘占用大，单机数量受内存限制；容器与宿主机共享内核和大部分资源，每个实例只增加应用及其依赖的少量开销，单机可运行的数量远超虚拟机。

5. 面试官追问：「容器隔离性弱于虚拟机，生产环境怎么用？」
   答：通常用虚拟机或云主机做底层强隔离，再在其上用容器做高密度部署；对安全多租户要求极高的场景，会选择虚拟机或加强容器的安全配置（如 gVisor、Kata 等轻量虚拟机型运行时）。
