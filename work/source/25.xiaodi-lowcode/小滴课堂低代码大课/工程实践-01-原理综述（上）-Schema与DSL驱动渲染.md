# 低代码平台技术原理综述（上）：Schema / DSL 如何驱动页面渲染

> 视角：低代码平台落地专家。
> 目的：课程 229 篇把"低代码平台"从需求到上线**一行行代码敲了出来**，却很少点破一件事——**为什么在编辑器里拖一下、配几个属性，发布出去就是一个能跑的页面？** 答案就四个字：**Schema 驱动**。本文把课程里"做出来"的部分，升华到"为什么成立"，并全部用课程真实篇目作样本。

## 一、核心命题：低代码 ≠ 少写代码，而是"配置即 UI"

普通 CRUD 系统：每个页面都是手写的 `.tsx` / `.vue`，改一个字段要改代码、改构建、发版本。
低代码平台：页面**不是被写出来的，而是被描述出来的**——用一份"描述页面长什么样、有哪些组件、每个组件什么属性"的数据（Schema），交给一个**通用的渲染器**解释执行。

> 这份"描述数据"就是 Schema；把 Schema 表达成更紧凑、带逻辑语法的形态，就是 DSL（领域特定语言）。

课程的发布页渲染，就是一份教科书级的 Schema 驱动样本。

## 二、活样本：发布页渲染（呼应《低代码项目发布页面—获取页面渲染》20-6）

`20-6` 里，发布页拿到后端返回后，核心逻辑是：

```ts
// 后端返回的数据（这正是 Schema 本体）
// 每个组件含：id、type、props(options)
// 例：{ id, type:'input', props:{ text:'请输入姓名' } }

localData.components.map(item =>
  getComponentByType(item.type)   // type → 组件 的映射
);
// 用扩展运算符把 props 摊开到组件标签上：<Comp {...props} />
// 输入型组件通过 onChange→onUpdate 回写 localData
```

拆解成 Schema 驱动的四个要素：

| 要素 | 课程里的对应 | 说明 |
|------|--------------|------|
| **Schema（数据）** | `{id, type, options}` 组件数组 | 描述"有哪些组件、各自什么属性" |
| **渲染器（Runtime）** | `ComponentRender` + `getComponentByType(type)` | 通用解释器，按 type 选组件、摊开 props |
| **组件注册表** | `share` 公共包里的 `getComponentByType` | type 与组件的映射表，新增组件即登记 |
| **数据回写** | `onChange→onUpdate→useImmer setLocalData` | 视图输入与 Schema 保持同步 |

**一句话**：编辑器里"配出来的页面"，发布后就是这份 Schema；发布页不过是一个**读 Schema、映射组件、摊开属性**的通用渲染器。这就是低代码的本质。

## 三、更深一层：编辑器编辑的其实是"数据"，不是"画面"

看《低代码项目平台编辑模块—页面组件拖拽排序功能开发》（18-4），拖拽排序的本质是：

```ts
// 拖拽 = 数组里两个索引的位置交换
const moveComponent = (oldIndex, newIndex) => {
  runInAction(() => {
    store.components = arrayMove(store.components, oldIndex, newIndex);
  });
};
```

课程自己总结了关键一句：**「所有拖拽动作，最终都被转换成数组里两个索引的位置交换，视图只是这份数组的投影。」**

这正是 Schema 思维的延伸：
- 画布上的组件列表 = Schema 数组的**投影**；
- 拖拽、键盘上下移、删除、复制粘贴 = 对数组做**增删改**；
- 发布 = 把这份数组（Schema）写库；
- 渲染 = 把数组读出来再投影一次。

所以"编辑器"和"发布页"共享同一份数据契约，只是**一个可写、一个只读**——这正是《低代码项目发布页面—后端接口低代码组件获取》（20-2）里"编辑端按 `user` 查、发布页按 `pageId` 查、复用同一服务层"的设计动机。

## 四、升华：Schema 与 DSL 的关系

| 概念 | 形态 | 角色 | 课程对应 |
|------|------|------|----------|
| **Schema** | JSON 数据（结构化描述） | 运行时被渲染器**解释执行** | `{id,type,options}` 组件数组 |
| **DSL** | 专用语言 / 配置语法 | 经**编译/解释**生成 Schema 或代码 | 本课程用 JSON Schema 直驱（未另起 DSL） |

**什么时候需要 DSL？**
当配置维度超出"表单填属性"的承载能力时——例如：
- 组件间的**条件显隐**（A 选"是"才显示 B）；
- **跨页面 / 跨数据源联动**；
- **循环、分支、表达式**。

这时用纯 JSON 表单去配会非常笨重，改用一段 DSL（或可视化逻辑编排）表达更简洁，再编译成 Schema 交给渲染器。本课程把"条件/逻辑"固化进了组件 props（`input`/`radio`/`checkbox` 的 `defaultXxx` 与 `onUpdate` 映射，见 20-6），属于"用 Schema 直接承载简单逻辑"的轻量路线，够用但**扩展性有限**——这正是商用化时需要补 DSL/逻辑编排层的地方。

**业界对照（便于建立坐标系）**：

| 平台 | 驱动方式 |
|------|----------|
| 阿里 LowCodeEngine | 协议式 Schema（assets 协议 + schema 协议） |
| 百度 Amis | JSON Schema 直驱渲染 |
| Retool | 数据绑定 DSL |

## 五、给自研者的落地铁律

1. **必须先固化 Schema 协议**：组件 `type` 枚举、每个 `type` 的 `props` 规范、Schema 版本号。否则组件一多、属性一乱，渲染器无从维护——课程 `getComponentByType` 的**注册表模式**是最小可行起点。
2. **编辑器与渲染器共享契约**：同一份 Schema，编辑端可写、发布端只读。不要为两端各写一套数据结构（课程的"复用同一服务层"已体现该原则）。
3. **把 UI 当作数据的投影**：任何"画布上的操作"（拖拽、排序、删除）都先想清楚"它改的是数组里的哪一段"，再谈视图。
4. **预留 DSL / 逻辑层接口**：哪怕当前只用 JSON 直驱，也要在 Schema 里留出"逻辑表达式"字段，避免将来推倒重来。
