# 工作流模块设计（平台内）· 工程实践-06

> 本文是 `工程实践-05-参考实现蓝图.md` 的**平台内模块增补**。目标：把"ComfyUI 式可视化编排"作为**低代码平台内部的一个模块**落地，主次分明、随平台一体部署，且**全设计以"后期可商业化"为硬约束**。
> 阅读前提：已读 05（主工程蓝图）。本文不重复 05 已定义的 Monorepo、技术栈、PageSchema、部署与压测，只在"平台内模块"视角做增量设计。

---

## 1. 定位与边界（主次分明）

- **主**：低代码平台（主工程 monorepo）。
- **次**：`workflow` 是 `apps/server/src/modules/` 下与其它业务模块（auth/page/component/form/oss/stats/rbac）**平级**的一个模块；其画布是 `apps/studio` 内的一个 Tab，与 page-builder 并列。
- **不是独立系统**：不单建仓库、不单起服务、不单建 DB 实例、不单列 CI。共用主工程的编译、部署、配置、可观测体系。
- **仍保持模块内高内聚**：engine / nodes / entities 自洽，对外只暴露 controller 接口与 canvas 组件。

```
lowcode-platform/
├─ apps/
│  ├─ server/src/modules/
│  │  ├─ auth/ page/ component/ form/ oss/ stats/ rbac/
│  │  └─ workflow/                # 本模块
│  │     ├─ workflow.controller.ts
│  │     ├─ workflow.service.ts   # 图存储（wf_* 表）
│  │     ├─ engine/               # DAG 解析/拓扑/执行/追踪
│  │     ├─ nodes/                # 节点注册表（节点=平台已有能力）
│  │     └─ entities/             # wf_graph / wf_node / wf_run / wf_run_node
│  ├─ studio/src/
│  │  ├─ page-builder/            # 页面搭建
│  │  └─ workflow-canvas/         # 工作流画布（React Flow），并列 Tab
│  ├─ render/  admin/             # 渲染端 / 统计后台（不变）
├─ packages/shared/               # 平台级类型（含 PageSchema、WorkflowContract）
└─ docker-compose.yml             # 整体一键起（wf_* 表在主库内）
```

## 2. 节点词汇表（复用平台已有能力）

工作流节点的本质是**把平台既有 module 的 service 编排起来**，因此节点不"另起炉灶"，而是平台能力的可编排封装。端口带类型，连线即数据/控制流。

| 类别 | 节点 | 底层复用 | 输出端口 |
|---|---|---|---|
| 触发 | `trigger.webhook` / `trigger.schedule` / `trigger.formSubmit` | 平台 webhook/定时任务/form module | `trigger` |
| 数据源 | `source.formSubmission` / `source.mysqlQuery` / `source.apiGet` / `source.ossRead` | form / 主库连接 / http client / oss module | `data` / `record` |
| 变换 | `transform.map` / `transform.filter` / `transform.aggregate` / `transform.script`(JS/Python 片段) | 平台脚本沙箱（见 §7） | `data` |
| 逻辑 | `logic.branch`(if) / `logic.merge` / `logic.loop` / `logic.delay` | — | `trigger` / `condition` |
| **UI 发射** | `ui.emitComponent` / `ui.composePage` | 复用 `PageSchema` 与 component registry | `schema` |
| 动作 | `action.sendSms` / `action.callApi` / `action.writeDb` / `action.webhook` | 短信/HTTP/DB/Webhook module | `trigger` |
| 高级 | `ai.generatePage`（LLM 产出节点或 PageSchema） | LLM 服务（可选接入） | `schema` / `data` |

> 关键：所有节点经 `packages/shared` 的 `NodeContract` 统一声明 `{type, ports:{in,out}, execute}`；前端画布与后端引擎共用同一注册表，避免前后端各写一份。

## 3. Graph DSL（图的 JSON 表示）

与 ComfyUI 的 prompt 同构，作为平台内持久化与传输格式：

```json
{
  "id": "wf_xxx",
  "name": "审批流-请假",
  "version": 1,
  "nodes": [
    { "id":"n1", "type":"trigger.formSubmit", "params":{ "pageId":"p_leave" } },
    { "id":"n2", "type":"transform.map",      "params":{ "expr":"r=>({...r,status:'pending'})" } },
    { "id":"n3", "type":"ui.composePage",     "params":{ "title":"审批页" } },
    { "id":"n4", "type":"action.sendSms",     "params":{ "tpl":"已提交审批" } }
  ],
  "edges": [
    { "id":"e1", "from":"n1","fromPort":"out", "to":"n2","toPort":"in" },
    { "id":"e2", "from":"n2","fromPort":"out", "to":"n3","toPort":"source" },
    { "id":"e3", "from":"n3","fromPort":"page","to":"n4","toPort":"ctx" }
  ]
}
```

- `nodes[].params` 经 schema 校验后入库；`execute` 实现只在后端 nodes 包内，前端拿不到逻辑体。
- 图版本化：`wf_graph.version` 单调递增，已发布图的 `type`/`ports` 改名即破坏兼容性，需走节点版本契约（见 §8）。

## 4. DAG 执行引擎设计（模块内，可单测）

`apps/server/src/modules/workflow/engine/`（纯 TS，不依赖 HTTP 层，便于单测）：

1. **解析**：载入图 → 构建节点表与邻接表。
2. **校验**：端口类型匹配、必填 params 存在、节点 `type` 在注册表内。
3. **拓扑排序**：Kahn 算法检测环；有环则拒绝执行（避免死循环）。
4. **执行**：按拓扑序逐节点 `execute(inputs, ctx)`，将输出按 edges 注入下游 `in` 端口；支持异步节点并发（无依赖的兄弟节点可并行）。
5. **上下文 `ctx`**：携带 `tenantId`、`runId`、`caller`、限流配额、审计句柄。
6. **追踪/重放**：每次执行落 `wf_run` + `wf_run_node`（输入/输出摘要、耗时、状态），支持失败重跑与逐步调试。
7. **错误边界**：单节点失败按图配置决定"整图回滚/跳过/告警"，不拖垮主服务。

> 引擎对主平台零侵入：它只调用各 module 暴露的 service 接口，不直接碰别 module 的表。

## 5. 模块边界与协作接口

- **对外接口（controller）**：
  - `POST /workflow` / `GET /workflow/:id` / `PUT /workflow/:id` / `DELETE /workflow/:id`（图 CRUD）
  - `POST /workflow/:id/run` / `GET /workflow/run/:runId`（执行与查询）
  - `GET /workflow/nodes` （返回节点注册表元信息供画布渲染）
- **与 page/component 协作**：`ui.composePage` 节点产出标准 `PageSchema`，写入主平台 `page` 表（走 page module 的 service，不直写表），随后由 `apps/render` 照常渲染——这就是"连线即生成可运行页面"。
- **与 form/oss/短信协作**：均通过对应 module 的 service，保证能力单一来源、权限统一（RBAC 在 module 层把关）。

## 6. 数据模型（`wf_*` 表，主库内，预留 `tenant_id`）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `wf_graph` | id, name, version, graph_json, status, **tenant_id**(预留), owner_id, created_at | 图定义，version 单调递增 |
| `wf_node_def` | type, category, ports_json, version, deprecated | 节点注册表持久化（与代码注册表镜像，供前端拉取） |
| `wf_run` | id, graph_id, status, trigger, **tenant_id**, caller, started_at, finished_at | 一次执行 |
| `wf_run_node` | run_id, node_id, status, input_md, output_md, duration_ms | 节点级追踪/重放 |

> 商业化预留：`tenant_id` 现已落字段但不强制隔离逻辑；后续做多租户时只需补隔离策略与索引，无需改结构。

## 7. 沙箱方案（高级模式：LLM/脚本节点）

`transform.script` 与 `ai.generatePage` 涉及执行用户/AI 提供的代码，是商业化前必须解决的**安全硬门槛**：

- **默认关闭**，仅授权租户/内部可用。
- **隔离执行**：容器（短生命周期 microVM / Docker）或 WASM 受限运行时执行，禁止访问主库直连、文件系统、内网。
- **资源配额**：CPU/内存/超时/网络白名单，超限即杀。
- **输入白名单**：脚本只能消费上游端口数据，不能引用平台密钥（密钥仅在 module service 内解析，不传入沙箱）。
- **审计**：每次沙箱执行留痕（who/what/when/output 摘要）。

> 轻量版（推荐先上）**不包含**脚本/LLM 节点，只用预置固定节点拼装——天然安全、可立即商用；沙箱作为后续增强。

## 8. 商业化就绪设计（硬约束，贯穿全程）

| 维度 | 设计决策 | 目的 |
|---|---|---|
| **开源协议** | 依赖只用 MIT/Apache-2.0/BSD 等商业友好协议；自研代码默认 MIT，禁止引入 GPL/AGPL 等传染性协议 | 可闭源商用 |
| **多租户预留** | 全表预留 `tenant_id`；能力按 tenant 做配额与计量钩子 | 后续 SaaS 化零结构改动 |
| **合规（PIPL）** | 手机号/短信等个人信息走脱敏存储与最小化采集；审计日志保留 | 国内合规 |
| **密钥安全** | 密钥仅存服务端配置/密钥库，永不进前端、不进图 JSON、不进沙箱 | 防泄露 |
| **可观测** | 执行埋点统一接入平台日志/指标；预留告警钩子 | 运维与 SLA |
| **计量钩子** | 图执行次数、节点调用次数、资源消耗在 `ctx` 打点 | 后续计费基础 |
| **配置外置** | OSS region、短信通道、LLM 接入、限流阈值全走 env/config，无硬编码 | 多环境交付 |
| **契约稳定** | `PageSchema`/`NodeContract`/`WorkflowContract` 版本化，破坏性变更走节点 version | 生态兼容 |
| **品牌去课程化** | 不绑定任何课程品牌/域名水印（沿用 05 治理规范） | 可独立售卖 |
| **扩展性** | 节点 SDK 开放注册，便于后续"节点市场"商业化生态 | 平台增值 |

## 10. 风险与决策点

1. **节点能力依赖平台完成度**：workflow 在 M3 才能端到端打通，需 05 的 page/form/oss/短信模块先就绪。建议先完成 05 P0–P3 再上 M0–M3。
2. **图版本兼容**：节点 `type`/端口改名破坏已发布图，必须靠节点 version 契约 + 迁移脚本。
3. **沙箱是商业化前提**：含脚本/LLM 节点的版本，未做隔离不得对外商用（见 §7）。
4. **避免过度设计**：先把"预置节点拼装"做扎实（高价值、低风险），脚本/AI 生成留作增强而非首版。
