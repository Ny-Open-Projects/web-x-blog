## 1. 总体架构

三层分离，核心是 **Schema 即产物**：

```
创作者/管理员(浏览器) ──▶ React 编辑器(apps/editor) ──HTTP/JSON──▶ NestJS 服务端(apps/server)
                                                                      │
                                                              MySQL / Redis / OSS
                                                                      │
普通用户(浏览器)   ──▶ Next.js 渲染端(apps/render) ◀──读取同一份 Page Schema──┘
                                                                      │
                                                             用户提交表单/问卷
                                                                      ▼
                                                              数据统计后台(apps/admin)
```

- **创作端**只产生/编辑一份 JSON（Page Schema），不发任何 HTML。
- **渲染端**拿到同一份 Schema，按 `type` 映射组件、摊开 `options` 渲染——这正是博客 20-2 / 20-6 描述的机制。
- **服务端**存 Schema、做鉴权、存提交数据、对接 OSS。

## 4. 核心数据模型（Schema 本体）

**Page Schema（前端/后端/渲染端唯一契约）**
```ts
type ComponentNode = {
  id: string;        // 组件实例唯一 id
  type: string;      // 组件类型，如 'input' | 'select' | 'button' | 'form'
  options: Record<string, any>; // 属性：label/placeholder/required/数据源等
};
// 一个页面 = ComponentNode[]，存库即产物，渲染端直接消费
```

**数据库表（TypeORM 实体，MVP 最小集）**
| 表 | 字段要点 | 对应博客 |
|---|---|---|
| `user` | id, phone, password(加密), openid | 注册/登录（11-3/11-6） |
| `role` / `user_role` | RBAC 三端 | 6-2 三端模型 |
| `page` | id, title, status(草稿/已发布), schema_json, owner_id | 14-2/14-3 发布接口 |
| `page_component` | id, page_id, node_id, type, options | 20-2 获取接口返回结构 |
| `form_submission` | id, page_id, data_json, created_at | 20-7 提交问卷 |
| `oss_file` | id, key, url, size, owner_id | 17-1 OSS |

## 6. 关键模块实现要点（映射博客，写代码时的依据）

1. **拖拽排序（18-4）**：页面组件本质是数组，拖拽 = 数组索引交换；视图是数组投影，无需单独存"位置字段"。
2. **Schema 渲染（20-2/20-6）**：渲染端维护 `componentRegistry: Record<type, ReactComponent>`，`getComponentByType(type)` 取到组件后把 `options` 摊开为 props。
3. **OSS 安全（17-1）**：`accessKeySecret` **只在服务端持有**，前端走 STS 临时凭证或直传回调；文档/代码里一律用占位符，绝不出现真实 secret（呼应治理规范 4.3）。
4. **RBAC（6-2）**：创作者/普通用户/管理员三端，接口层用守卫（Guard）按角色放行。
5. **草稿↔发布（14-2/14-3）**：`page.status` 区分草稿与已发布；发布即把编辑器当前 Schema 固化进 `page_component`。

## 7. 部署与压测（DevOps / perf 阶段）

- `docker-compose.yml` 一键拉起 mysql/redis/server/editor/render/admin。
- 每个 app 一个 `Dockerfile`（多阶段构建，nginx 托管前端静态）。
- `deploy/nginx.conf` 做反向代理与静态分流。
- 云效流水线：push → 构建镜像 → 推仓库 → 服务器拉起（博客 DevOps 阶段）。
- JMeter 对"获取页面组件""提交问卷"两个高频接口做聚合报告压测（perf 阶段）。

## 11. 风险与决策点（呼应原理综述下）

- **自研 vs 采购**：若只需"表单/问卷类轻量场景"，采购或开源方案（如 amis、formily）更省；若要做"自有产品中嵌的可视化搭建能力"，自研参考实现是合适地基。蓝图默认走自研地基路线。
- **Schema 锁定**：组件 `type` 一旦对外发布，改名即破坏已发布页面，需版本化注册表。
