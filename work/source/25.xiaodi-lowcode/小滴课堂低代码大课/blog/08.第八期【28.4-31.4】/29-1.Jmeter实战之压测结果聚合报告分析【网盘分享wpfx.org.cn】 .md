# JMeter 实战之压测结果聚合报告分析

> **导语**：脚本会跑了，但"性能好不好"得看数字说话。本文先厘清 TPS / QPS / 响应时间三个核心概念，再逐项拆解聚合报告（Aggregate Report）每一列的含义，并给出"逐步加压、以零异常换最大吞吐"的压测方法论。

## 前置知识

本文建立在《Http取样器复用和Http请求头管理实战》之上，需已会用线程组、取样器、监听器，并能通过调度器做持续压测。

## 正文

### 三个必须先懂的性能指标

- **TPS（Transactions per Second，每秒事务数）**：侧重**增、删、改**类操作。比如一秒内完成多少次"注册用户""删除订单""修改昵称"这种涉及写库的业务流程。一秒能支撑 1000 次写操作，就是 1000 TPS。
- **QPS（Queries per Second，每秒查询数）**：侧重**查询**类操作，统计一台服务器每秒能响应多少次读请求。一秒支撑 2000 次查询，就是 2000 QPS。
- **RT（Response Time，响应时间）**：单个接口请求来回的耗时。业界通常要求核心接口在 **200ms 以内**；打开浏览器控制台 Network 面板，看异步请求的 Time 即可直观感受。

> 关系：纯查询接口，吞吐量既可称 TPS 也可称 QPS，日常口语常混用；只有涉及写库的业务流，严格用 TPS 描述更贴切。

### 聚合报告各列含义

添加**聚合报告**监听器后跑一轮压测（例如 500 线程、调度器开启、循环"永远"、持续 20 秒），会得到如下字段：

| 列 | 含义 |
| --- | --- |
| Label | 取样器名称（即你给接口起的名字） |
| # Samples | 总请求数（样本数） |
| Average | 平均响应时间 RT（毫秒） |
| Median | 中位数，即 50% Line，一半请求快于该值 |
| 90% Line | 90% 的请求响应时间不超过该值（长尾指标） |
| 95% Line / 99% Line | 同理，更严格的尾部延迟分界 |
| Min / Max | 最小 / 最大响应时间 |
| Error% | 异常（失败）请求占比 |
| Throughput | 吞吐量，默认每秒完成的请求数，可类比 QPS/TPS |
| Received KB/sec | 每秒接收数据量 |
| Sent KB/sec | 每秒发送数据量 |

示例一轮结果：20 秒内共发 2174 个请求，平均 RT 约 4 秒，最小 186ms、最大 6.3 秒，吞吐量约 95.1/s，异常 0%。这组数字说明该查询接口在当前机器上**性能偏差**（平均 4 秒远超 200ms 标准），有较大优化空间。

> 注意：压测数值与机器性能强相关。讲师用的是较老旧的电脑，所以绝对数值仅供参考；重点在于**读懂指标、掌握方法**。

### 方法论：逐步加压，用"零异常 + 最大吞吐"定性能水位

不要一上来就拉满线程数。正确做法是：

1. 从一个较低线程数（如 500）开始，开调度器持续压一段时间，记录吞吐量、异常%。
2. 逐步加大线程数（每次 +300、+500……直到数千），每档都跑一轮。
3. 观察：**当异常%（Error%）降为 0，且吞吐量达到最大时**，对应的线程数就是该接口在当前环境下的性能水位，此时的吞吐量即最优 QPS/TPS。

反例：直接上 3000 线程，因本机性能/数据库撑不住，结果大量报错（异常 75%），样本虽多但无效。遇到高并发崩接口属正常，应调小线程数重测，直到异常归零。

## 小结

- TPS 描述增删改事务，QPS 描述查询，RT 是响应时间，核心接口建议 < 200ms。
- 聚合报告关键看：# Samples、Average、Median、90/95/99% Line、Error%、Throughput。
- 90% Line 代表 90% 请求快于该值，是衡量长尾延迟的核心。
- 压测方法：低线程起步逐步加压，以"异常为 0 且吞吐量最大"定位性能水位。
- 绝对数值依赖机器，重点是掌握读数与加压思路。
