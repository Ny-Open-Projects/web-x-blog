# 低代码项目后端接口开发：手机验证码接口

> **导语**：一个"获取短信验证码"按钮，背后牵动第三方短信服务、Redis、DTO、图形验证码与频率限制。本文完整拆解该接口的业务时序与实现分层：RandomTool 随机工具、Controller 参数与 key 设计、Service 中 60 秒限流、图形验证码校验、发送与存储、以及失败回滚。读完你能照着写出一个防刷、可校验、能对账的验证码接口。

建议先读《低代码项目后端接口开发—加密+Redis 模块配置》了解 Redis 模块与 IP/设备加密 key 的由来，再读《低代码项目后端接口开发—图形验证码接口》和《第三方短信验证码发送装饰器封装实战》，本篇会直接复用其中的 CaptchaDto、图形验证码收发逻辑与 sendMsgCode 装饰器。

## 正文

### 先把业务时序理清楚

动手前先梳理整条链路：用户在前端点击"获取验证码" → 客户端请求后端的短信验证码接口 → 后端生成 4 位随机数字，连同手机号调用阿里云第三方短信服务 API → 短信服务把验证码发到用户手机 → 用户填写验证码并点击注册 → 注册逻辑中校验验证码是否正确。

关键在于后端要把这 4 位数字做两件事：一是发给短信运营商，二是存进 Redis。只有存下来，注册接口回来时才有依据比对。整个流程里，验证码既是"发给用户的内容"，也是"服务端留存的凭证"。

### 随机工具类 RandomTool

第一步先准备工具。在 utils 下新建一个 @Injectable() 的 RandomTool 类，把随机能力集中收拢：

```ts
@Injectable()
export class RandomTool {
  // 生成 4 位随机数字验证码
  randomCode(): number {
    return Math.floor(Math.random() * 9000) + 1000;
  }
  randomAvatar() { /* 从 OSS 预置的 20 张头像中随机取一张 */ }
  randomNickname() { return `编程小白${Math.floor(Math.random() * 90000) + 10000}`; }
}
```

randomCode 用 Math.floor + Math.random 生成 1000–9999 的四位数。讲师还顺手把后面项目要用的随机头像、随机昵称一起写好：随机头像基于提前放在阿里云 OSS 上的 20 张图片，用一个接收 number 的 baseImageUrl 函数做边界收敛（取到 0 归 1、大于等于 19 归 19、否则取原值），拼上数字就能得到不同头像；随机昵称则用固定前缀"编程小白"加随机数字后缀，给未设置昵称/头像的用户兜底。

### Controller：参数、DTO 与 Redis key

短信验证码接口接收三个参数：phone（手机号）、captcha（图形验证码）、type（用途类型，登录还是注册）。参照 CaptchaDto 复制出 SendCodeDto 做参数校验，顺带把之前遗留的错误提示字段从 id 改成 type。

```ts
@Post('send-code')
async sendCode(@Body() body: SendCodeDto) {
  const { phone, captcha, type } = body;
  // key 由用户 IP 与设备信息加密生成，用于区分不同用户
  const key = encryptIpAndDevice(/* ... */);
  return this.userService.sendCode(phone, captcha, type, key, this.randomTool.randomCode());
}
```

为什么要额外取用户 IP 与设备？因为 Redis 里的验证码必须可区分：不同用户、不同用途的数据不能互相覆盖。把 IP 与设备加密后作为 key 的一部分，就能保证唯一性。注意 randomCode 是方法，调用时别忘了执行——演示里第一次就因为只写了 this.randomTool.randomCode（传了函数而非值）而报类型错误；同时 RandomTool 必须在模块的 providers 中注册，否则注入会失败。

### Service：六步防线

服务层方法标记为 async，因为涉及 Redis 等异步操作。逻辑按校验顺序层层推进：

1. **60 秒限流**：用模板字符串拼出 key（type、code、phone 以下划线连接），从 Redis 取值后 split('_')[0] 拿到时间戳，转成 number，再用 dayjs 转换；`dayjs().diff(dateRedis, 'second') <= 60` 就抛 BadRequestException（"请勿重复获取验证码，60 秒内"）。dayjs 需安装并在 monorepo 里用 `pnpm --filter server add dayjs` 装到 server 子包，引入方式为 `import * as dayjs from 'dayjs'`。
2. **是否获取过图形验证码**：用 IP+设备加密的 key 调 exists 判断，没有则抛"请先获取图形验证码"。
3. **图形验证码比对**：从 Redis 取出 captcha，与前端传入值都经 toLowerCase() 后再比较，从而忽略大小写（大写 A 与小写 a 都算通过）；不一致抛"图形验证码不正确"。
4. **发送短信**：`await sendMsgCode(phone, randomCode)` 调用前面封装好的第三方短信装饰器，把验证码发到用户手机。
5. **清理与存储**：图形验证码校验通过后即失去价值，用 del 从 Redis 删除以节省空间；再把短信验证码写入 Redis——value 为 `Date.now()` 与验证码的拼接（时间戳在前，方便下次比对发送时间），过期时间设为 60 秒。
6. **结果处理**：发送返回的 code 为 0 表示成功，接口不返回具体数据（统一响应里 data 为空）；失败则删除 Redis 中的图形验证码并抛"发送失败，请重试"，由异常拦截器把错误交给前端。

这套顺序有个明显好处：越靠前的校验成本越低（限流、图形验证码都在本地 Redis 完成），只有全部通过才去调收费的第三方短信接口。

### 联调验证

启动项目后在 Apifox 里按两步走：先请求图形验证码接口（type 为 register），拿到图形验证码；再请求短信验证码接口，填入手机号、图形验证码、register 类型并发送。成功时 data 为空、code 为 0；刷新 Redis 能看到新写入的值形如"时间戳_6294"，与手机上收到的 6294 完全一致，说明发送与留存对得上。

排错时两处最常见：randomCode 忘记执行传成了函数，以及 RandomTool 没在模块里注册导致依赖注入报错。逐个核对即可。

## 小结

- 业务时序：生成 4 位随机码 → 调阿里云短信发给用户 → 同时存 Redis → 注册时比对。
- RandomTool 集中提供 randomCode、randomAvatar、randomNickname；注意 randomCode 要执行、类要在模块 providers 注册。
- Controller 用 SendCodeDto 校验 phone/captcha/type，并用 IP+设备加密结果作为 Redis key 保证唯一性。
- Service 六步：60 秒限流（dayjs diff）→ 图形验证码存在性 → 忽略大小写比对 → 发短信 → 删图形验证码并按"时间戳_验证码"写 60 秒 → 按返回 code 处理结果。
- 低成本校验前置、第三方短信后置，失败要清理 Redis 并抛异常，由统一响应/异常拦截器处理。
