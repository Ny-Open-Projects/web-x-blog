# 后端接口开发—低代码项目编辑模块页面组件获取接口

> **导语**：用户登录进入低代码编辑页时，编辑器要能把「他上次发布过的页面」还原出来——有哪些组件、每个组件的属性配置是什么。这一集开发的正是这个回显接口：带 token 鉴权，按用户 id 查页面记录，再按组件 id 逐个查出组件详情返回给前端。本文把 Controller、Service、依赖注入和联调踩坑完整走一遍。

## 正文

### 这个接口要解决什么

发布过的页面会存进数据库。所以用户一进入编辑页，前端就要请求一个接口，问后端：「当前这个用户之前配置并发布过页面吗？如果有，页面里有哪些组件、各自的属性（options）是什么？」拿到这些数据，前端才能把画布**原样渲染**出来——这就是编辑器的「回显」能力。

它和发布接口是一对反向操作：发布是把组件数据写进去，本接口是把它们读出来。

### Controller：GET + 只认 token

在上一节课的发布控制器基础上复制一份，改成页面组件获取控制器：

- 用 `GET`，**不需要传参**，只要请求头 `authorization` 里带 token；
- 路径用 `release`，组件数据命名为 `withUser`（不同用户有各自的页面）；
- 方法名 `getReleaseData`，仍然要走用户鉴权：校验 token 是否合法、解析出的用户 id 在数据库里是否存在；
- 校验通过后把用户信息附加到 request 上，通过工具取出用户信息传入 Service。

```ts
@Get('release/withUser')
async getReleaseData(@Req() req) {
  return this.releaseService.getReleaseData(req.user);
}
```

（装饰器与路径细节以 `代码（已8期）/14-5/lowcode/packages/server` 下源码为准。）

### Service：先查页面，再逐个查组件

Service 里新建 `getReleaseData(user: TokenUser)`，逻辑分三步：

1. **查页面**：解析 token 拿到用户 id，到页面表里 `findOneBy({ codeId: userId })`，看该用户有没有发布过页面。没有就直接 `return`——没发布过自然无从获取。
2. **取组件 id**：有页面记录时，从记录里拿到 `componentIds`（组件 id 数组）。
3. **逐个查组件**：遍历 id 数组，到组件表里查出每个组件的详情（含 `options`），收集起来返回。

```ts
async getReleaseData(user: TokenUser) {
  const page = await this.pageCodeRepository.findOneBy({
    codeId: user.id,
  });
  if (!page) return;

  const componentIds: string[] = page.componentIds ?? [];
  const components = [];
  for (const componentId of componentIds) {
    const component = await this.componentRepository.findOneBy({
      id: Number(componentId),   // 转 number，避免查出的是字符串
    });
    components.push(component);
  }
  return { components, componentIds };
}
```

两个细节值得留意：

- `Number(componentId)` 是必要的——页面表里存的组件 id 可能是字符串，而组件表的主键是 number，直接查会匹配不上；
- 返回的是 `components`（组件详情）和 `componentIds`（id 数组）两份数据，前者给渲染用，后者给前端维护组件顺序等逻辑用。

### 依赖注入：别漏了装饰器

Service 里要注入 `Page` 与 `Component` 两个 Repository，同时在 Module 里注册对应实体。讲师联调时就踩了一个坑：从别处复制 `@InjectRepository(...)` 时，因为编辑器换行只复制了一半，启动时报「找不到依赖」。把装饰器完整补上后服务才正常。

这类报错的排查方向很固定——**先看装饰器是不是完整、Module 里有没有注册**，而不是怀疑查询逻辑写错。

### Apifox 联调与数据验证

在接口调试工具里发 `GET /release/withUser`，header 里带 `authorization`（注意参数名要写对），复用发布接口拿到的 token。

验证结果分两种：

- 当前 token 对应 `accountId = 8` 的用户，发布时配置的 `components` 为空，组件表里也没有这个用户的数据，因此接口返回的 `components` 为空；
- 手动往页面记录里加一个组件 id（演示里填了 `一二三`）再请求，`componentIds` 就能拿到对应的字符串数组，但 `components` 仍为空——因为组件表里确实没有 id 对应的记录。

这恰好说明接口的行为是对的：**它只做「按 id 查得到什么就返回什么」**，不会凭空造组件。等前端逻辑开发完成，发布时会把组件类型、pageId、accountId 以及内容丰富的 `options`（swiper 每项的图片 URL 与样式、list 的 items 数组里每项的 id/title/description/titleLink 等）一并传过来，届时这两个数组就能完整还原页面。

前端这一侧，编辑模块用到的依赖可对照 `代码（已8期）/14-5/lowcode/packages/client/package.json`：`antd`、`ahooks`、`axios`、`mobx`、`react-router-dom`、`tailwindcss` 等。

## 小结

- 该接口是发布接口的反向操作，负责把用户已发布页面的组件与配置回显给编辑器。
- Controller 用 `GET release/withUser`，不传参，只靠 `authorization` 里的 token 鉴权。
- Service 先按用户 id 查页面记录，没有则直接返回；有则遍历 componentIds 逐个查组件表。
- 组件 id 要 `Number()` 转换；返回 `components` 与 `componentIds` 两份数据。
- `@InjectRepository` 与 Module 注册要完整，缺了会启动报「找不到依赖」。
