# 发布接口《上》：三张表定义与 JWT 权限校验准备

> **导语**：发布接口不是简单点一下按钮就能写出来的，动手写业务之前得先铺好两件事：数据库表怎么设计，以及"谁有资格发布"。本文梳理低代码编辑模块发布接口的前置准备——页面表、组件表、组件数据表三张实体，公共 `share` 包里的类型定义，以及基于 `@nestjs/passport` + `passport-jwt` 的 token 解析策略与用户信息参数装饰器。读完后你能看懂发布接口的权限链路与数据模型。

## 正文

### 先看清发布流程

发布接口的逻辑可以先用流程图定下来。用户在编辑页配好组件、设置属性、预览确认后点击"发布"：

1. 前端点击发布，请求打到 NestJS 后端；
2. 后端按**用户 ID + 页面 ID / 页面名**去页面表里查询该页面是否已存在；
3. 若已存在，执行**更新**页面表与组件表的数据；
4. 若不存在，则**创建**页面与组件数据。

也就是说发布本质是一次"存在则更新、不存在则创建"的 upsert 操作，前提是页面、组件、组件数据三张表先定义好。

### 三张实体表

用 NestCLI 生成 `lowcode` 模块后，在 `entity.ts` 里通过 `@Entity()` 一次性定义三张表（同一个文件里可以定义多个实体）。

**页面表**：记录组件 ID、用户 ID、页面名、页面包含哪些组件（`components` 是一个由组件 ID 组成的数组，用 `simple-array` 类型）、以及 TDK（页面描述）与关键字等 SEO 相关字段。

**组件表**：描述"一个页面里有哪些组件、各自什么配置"。字段包括组件类型（视频、轮播图、图片、文本等，默认值给一个文本标题类型）、所属配置 ID、所属页面 ID、所属用户 ID，以及 `options`——也就是右侧属性面板里用户自定义的那些配置，以对象形式存储，用 `simple-json` 类型。

**组件数据表**：提前建好，用来存发布页面后用户提交的数据。若发布的是问卷类页面，用户填入输入框、选择单选/多选框并提交，这些数据就落到这里。字段关联到哪个页面、哪个组件、哪个用户，以及 `purpose`——一个数组，每项为对象，记录对应组件的 id 与用户填写的 value。

### 公共类型放到 share 包

三张表的属性类型不该散落在各处，统一提到公共子项目 `share` 里，前端和其他地方都能直接引入，避免重复定义。在 `share/src/lowcode.ts` 中定义三个接口：`ILowcode`（页面表）、`IComponent`（组件表）、`IComponentData`（组件数据表）。

其中 `options` 这类"键值对集合"用 TypeScript 内置工具类型描述最合适：

```ts
export interface IComponent {
  id: number;
  type: TComponentTypes;
  pageId: number;
  userId: number;
  options: Record<string, any>;
}
```

`Record<string, any>` 表示键为字符串、值为任意类型的对象集合，正好对应每个组件各不相同的属性配置。

组件类型再单独放到 `share/src/components/type.ts`，定义 `TComponentTypes`，把视频、轮播图、二维码、卡片、列表、图片、文本、分割线、富文本等一一映射成字符串字面量类型。最后在 `share/src/index.ts` 里统一 `export` 出去——注意导出时要用对象/星号导出的形式，否则别处会提示"没有默认导出"。

类型文件改完，还要执行构建才能被其他子项目引用。根工程 `代码（已8期）/代码（已8期）/14-2/lowcode/package.json` 已经备好了脚本：

```json
{
  "scripts": {
    "build:share": "pnpm --filter share run build"
  }
}
```

执行 `pnpm build:share`（或对应脚本）打包后，重新加载编辑器窗口，之前"找不到模块"的警告就会消失。配套资料可参考 `packages/share/tsconfig.json` 与 `pnpm-workspace.yaml`。

### 发布接口需要权限

发布不该是所有人都能点的操作：必须是成功登录、且后端校验 token 正确的用户才能调用。因此需要新增一个**解析 token 的工具**，验证用户是否登录、token 是否有效、以及解密出的用户在数据库里是否真实存在。

### JWT 策略：解析与校验

用 `@nestjs/passport` 与 `passport-jwt` 定义 `JwtStrategy`，继承 `PassportStrategy`。在 `constructor` 里调用 `super` 传入两项关键配置：

- `secretOrKey`：签发 token 时用的那段自定义密文；
- `jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken()`：从请求 header 的 `authorization` 里取出 `Bearer` 拼接的 token 字符串。

核心是 `validate` 方法，按校验顺序处理：

1. 解析后无数据 / token 无效 → 提示"请先登录"；
2. 用解析出的过期时间与当前时间比对，小于零说明已过期 → 提示"登录已过期，请重新登录"；
3. 拿解析出的用户 ID 去用户表查找，查不到 → 提示"出现错误，请重新登录"；
4. 全部通过，则把查到的用户数据（**密码置空**）`return`。

Passport 会把这个返回值自动附加到 `request` 对象上，后续接口就能在请求上下文里直接拿到用户信息。

### 用户信息参数装饰器

配套再定义 `getUserMessage`：用 `createParamDecorator` 创建参数装饰器，内部通过 `ctx.switchToHttp().getRequest().user` 取出上一步附加的用户信息并返回。这样在 controller 的接口参数上写一个装饰器，就能拿到当前登录用户的完整信息，不必每个接口重复解析 token。

`JwtStrategy` 作为 Provider 要在 `app.module.ts` 里全局引入，之后在 `lowcode.controller` 中配合参数装饰器即可使用。以上这些，都是正式开发发布接口之前的准备工作。

## 小结

- 发布流程是"按用户 ID + 页面 ID 查询 → 存在则更新、不存在则创建"的 upsert。
- 三张实体表：页面表、组件表（含 `simple-json` 的 options）、组件数据表（存问卷提交数据）。
- 公共类型集中在 `share` 包，`options` 用 `Record<string, any>`，组件类型用 `TComponentTypes` 字面量映射。
- 改完 `share` 类型要执行 `build:share` 打包，别处才能正常引入。
- 权限用 `JwtStrategy` 继承 `PassportStrategy`，`validate` 依次校验 token 有效性、过期时间、用户是否存在，并把用户数据挂到 request。
- `getUserMessage` 参数装饰器从 `request.user` 取用户信息，供各接口复用。
