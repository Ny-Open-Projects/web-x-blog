# 低代码项目平台编辑模块—页面组件服务端获取开发

> **导语**：编辑页刷新后，最新组件配置到底来自本地草稿还是服务端？本文讲解 `useStoreComponents` 中 `readDataFromServer` 方法的实现：如何从服务端获取页面组件、把后端返回结构转换成前端 store 结构，并修正后端少返回的标题与关键字字段。

## 前置知识

- 已理解发布功能的入参与本地缓存时间，见《低代码项目平台编辑模块—页面头部发布功能开发》。
- 已掌握从 `localStorage` 读取组件（`readDataFromLocal`）的判断逻辑：有本地缓存且缓存时间晚于发布时间时优先用草稿。
- 后端「获取页面组件」接口已开发，路径为 `GET /local/releaseWithUser`。

## 正文

### 为什么需要 readDataFromServer

在 `useStoreComponents` 中，读取组件的逻辑分两条路：

- 有本地缓存，且缓存时间晚于发布时间 → 说明最新配置在草稿里，走 `readDataFromLocal`；
- 本地缓存时间早（已发布过更新版本），或本地缓存为空 → 必须从服务端拉取，走 `readDataFromServer`。

`readDataFromServer` 就是本节课要补充的从服务端获取页面组件的逻辑。

### 调用后端获取页面组件接口

`readDataFromServer` 是一个 `async` 的 action，内部请求后端「获取页面组件」接口：

```ts
// api/local 中定义，GET 请求，无需参数
const res = await getLocalPage(); // GET /local/releaseWithUser
```

该接口路径即服务端控制器中的 `releaseWithUser`，拿到返回数据后，需要把后端结构转成前端 store 的结构。

### 后端结构转前端 store 结构

后端返回的每个组件需要映射到前端储存格式：每个元素是一个对象，包含 `id`、`type` 以及 `options`（该组件的全部属性信息）。转换后写入 store 的两个变量：

- `componentConfigs`：组件 ID 到配置对象的映射；
- `sortableComponentConfig`：所有组件 ID 组成的排序数组。

排序数组的 ID 来源很简单：前面处理好的数据是一个「ID → 组件属性」的键值对，用 `Object.keys(...)` 取出 key 即可作为排序数组。

### 默认选中与页面信息更新

从服务端取回数据后：

- 默认选中第一个组件：取 `sortableComponentConfig[0]` 的 ID 作为当前选中项；
- 调用 `updatePage` 更新页面动态信息（标题、关键字、描述）。`updatePage` 同样是 store 中的 action，通过 MobX 修改 page 模块下这三个属性。

### 修正后端少返回的字段

联调时发现，之前的「获取页面组件」接口只返回了 `components` 与 `componentIds`，漏掉了 `title`、`description`、`tdk` 三个字段。修复方式是在服务端用 `omit` 把 `components` 剔除后，把剩余的页面级属性（`title`、`description`、`tdk`、用户 ID、页面 ID）一并返回给前端，确保前端能正确回填全局属性。

### 行为验证

- 删除组件、重新编辑（图片、文本、列表），点「存草稿」后刷新 → 因草稿时间更晚，提示「已自动从草稿中读取数据」，无接口请求；
- 增加二维码、空组件后点「发布」，再刷新 → 发布时间更晚，提示「已自动从服务器读取数据」，并有接口请求返回最新配置；
- 仅点「存草稿」再刷新 → 不会发起任何服务端请求，直接从缓存取。

## 小结

1. 读取组件分两条路：草稿时间更新则用本地，否则从服务端拉取。
2. `readDataFromServer` 是异步 action，调用 `GET /local/releaseWithUser`。
3. 后端结构需转成 `{ id, type, options }` 并写入 `componentConfigs` 与 `sortableComponentConfig`。
4. 取回后默认选中第一个组件，并通过 `updatePage` 回填标题/关键字/描述。
5. 后端需补齐返回 `title`、`description`、`tdk`，否则全局属性无法回填。
