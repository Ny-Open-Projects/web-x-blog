# 低代码平台项目后端 Nest 项目配置—接口响应+异常拦截器+DTO

> **导语**：裸接口返回格式杂乱、错误无统一结构，前端难以消费。本节在小滴低代码后端的 Nest 项目中一次性配置统一响应拦截器、异常拦截器与请求参数 DTO 校验，让接口输出规范、可控。

## 前置知识
- 已完成 Nest 后端 TypeORM 基础配置：建议先看《低代码平台项目后端 Nest 项目配置—TypeORM》。
- 理解 Nest 的拦截器与装饰器机制：可参考专题《Nest的响应拦截器》《Nest的异常拦截器》。

## 正文
### 统一响应拦截器
在 `packages/server/src/common` 目录下新建响应拦截器文件。它负责把所有成功返回统一包裹成如下结构：

```json
{
  "code": 0,
  "data": { }
}
```

`code` 为 `0` 代表成功，业务数据统一放在 `data` 字段中，前端按固定字段解析即可。

### 统一异常拦截器
同样在 `common` 目录新建异常拦截器 `http-exception.filter.ts`，把运行时报错统一收敛为：

```json
{
  "code": -1,
  "data": "错误提示信息"
}
```

这样无论正常还是异常，接口外层的 `code` 与 `data` 形态都一致，前端不用为每种错误写特殊分支。

### 在全局注册
打开 `src/main.ts`，引入两个处理器后通过全局 API 注册：

```ts
app.useGlobalInterceptors(new ResponseInterceptor());
app.useGlobalFilters(new HttpExceptionFilter());
```

### 用户接口接入 DTO 校验
以查询用户为例，前端通过用户 `id` 查询信息，要求 `id` 必须为 `number` 且不能为空。新建 `find-user.dto.ts`：

```ts
import { IsInt, IsNotEmpty } from 'class-validator';

export class FindUserDto {
  @IsInt()
  @IsNotEmpty()
  id: number;
}
```

在 `main.ts` 中开启全局管道校验：

```ts
app.useGlobalPipes(new ValidationPipe());
```

控制器改为接收 `body` 并校验：

```ts
@Post()
findOne(@Body() dto: FindUserDto) {
  return this.userService.findOne(dto.id);
}
```

`UserService.findOne` 内部用 `userRepository.findOne({ where: { id: dto.id } })` 查询并返回。

### 验证效果
- 请求 `GET /user`：返回带 `data`、且 `code` 为 `0` 的包裹结构。
- 请求不存在的路径：返回 `code` 为 `-1` 及对应错误提示。
- 用 API 工具 `POST` 用户接口，传入 `body` 中 `id` 为 `25`：成功返回数据。
- 把 `id` 改为空或字符串：拦截器提示「id 必须为 number 类型且不能为空」。

## 小结
- 响应拦截器统一成功结构 `{ code: 0, data }`，异常拦截器统一错误结构 `{ code: -1, data }`。
- 两者通过 `useGlobalInterceptors` / `useGlobalFilters` 全局注册。
- DTO 配合 `class-validator` 与全局 `ValidationPipe` 完成参数校验。
- 统一结构后前端联调成本大幅下降。
