# 深度解析 pnpm-workspace 的灵动工作空间管理

> **导语**：本文讲解本项目的工程化基石——pnpm-workspace。我们将说明为何用单一代码库管理多个子项目（client / release / server / share），以及 pnpm-workspace 在依赖提升、版本一致与开发体验上的优势，并预览 `pnpm-workspace.yaml` 的结构。

## 前置知识
阅读本文建议先看完《阿里云 Linux 服务器容器化安装 Redis》，基础设施就绪后进入工程初始化阶段。

## 正文

### 本项目有哪些子项目
低代码平台涉及多个项目，统一放在一个工作区（`lowcode` 根目录）下：

- **client**：基于 React 的后台编辑端与数据统计前端；
- **release**：基于 Next.js 的 H5 发布页（服务端渲染）；
- **server**：基于 Nest 的后端接口服务；
- **share**：提供各子项目公共的组件与类型，提升复用。

低代码组件在 client（React）与 release（Next）中高度相似，因此抽到 `share` 共用。

### 什么是 pnpm-workspace
pnpm 是类似 npm 的包管理工具，workspace 引入「工作区」概念：让一个项目内管理多个子项目及其依赖。VS Code 打开一个文件夹即一个工作区，workspace 使单个工作区可维护多个子项目，并把公共依赖提取到根目录。

### 核心优势
- **单一代码库**：多个子项目共处一个工作区，而非各建独立仓库；
- **统一依赖管理**：React、React DOM 等公共依赖提升到根目录 `node_modules`，子项目无需重复下载，减小体积；
- **版本一致**：一条 `pnpm install` 安装全部子项目依赖，避免版本冲突；
- **安装更快、体验更好**：不必逐个进入子项目安装；
- **结构清晰**：易于导航与多项目协同。

### 工作区结构
在根目录创建 `pnpm-workspace.yaml`，声明子项目所在目录：

```yaml
packages:
  - "packages/*"
```

所有子项目都放在 `packages/` 下，各自拥有自己的 `package.json` 与锁定文件；根目录 `node_modules` 存放公共插件依赖。Dockerfile、Nginx 等部署相关文件后续才会用到。

## 小结
- 本项目用 pnpm-workspace 管理 client / release / server / share 四个子项目；
- workspace = 单一代码库 + 工作区概念，公共依赖提升到根目录；
- 优势：统一依赖、版本一致、安装更快、结构清晰、复用 share；
- 关键配置文件 `pnpm-workspace.yaml` 用 `packages: ["packages/*"]` 声明子项目目录。
