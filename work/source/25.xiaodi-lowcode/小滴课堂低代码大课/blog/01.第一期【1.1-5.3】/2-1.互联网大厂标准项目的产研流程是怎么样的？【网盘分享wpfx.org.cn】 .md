# 互联网大厂标准项目的产研流程是怎么样的？

> **导语**：技术选型是理论性知识，而理论必须落地在真实的研发流程里。本文梳理互联网大厂一个标准项目的「产品—研发—上线—复盘」全流程，帮你在动手写代码前，先建立 Leader / 技术组长应具备的流程意识。

## 前置知识

建议先阅读《低代码平台项目亮点+疑惑》，理解项目分 P3/P2/P1 三档难度。本文偏流程与协作，无需编码基础。

## 正文

### 为什么先讲流程

研发任何项目前，都要先确认技术栈、框架或解决方案。如果开发到一半才发现选型不可行，再去亡羊补牢，会大幅增加人力与时间成本。所以作为 Leader 或技术组长，技术选型与流程把控是必备能力。

### 标准产研流程图解

#### 1. 需求调研（产品/项目经理）

需求来源包括：竞品或自身调研、同事建议、技术迭代需求，以及「老板说要加」——花钱的是老板，需求通常要接。

#### 2. 梳理需求（产品经理）

把调研到的需求整理清楚，准备内部评审。

#### 3. 需求评审（原型图方式）

用**原型图**（黑白、无精美配色、带逻辑的草图）做内部评审，确认：

- 优先级排序；
- 逻辑能否走通、是否详细；
- 上线预估时间；
- 拉技术 Leader 确认大方向技术能否实现；
- 过滤不合理 / 无法实现 / 性价比低的需求；
- 技术 Leader 评估工时，决定需求是否需要裁剪。

不通过则打回产品经理重新梳理。

#### 4. 交付 UI 设计

需求文档通过后，交 UI 设计高保真图。

#### 5. 团队需求会议

产品经理拉前端、后端、测试、UI 全体开评审会，细节不通过同样打回。会议中明确：

- 需求细节是否合理；
- 前端组内按人拆分页面，落实到开发者并确认完成时间（常用**甘特图**排期）；
- 一般后端先开发接口（或前后端同步），先定好接口协议再返回哪些数据，前端可先用模拟数据开发；
- 制定排期计划，定期校对进度、能否准时提测。

#### 6. 研发测试

后端开发接口、前端开发页面、前后端联调，联调完提测。测试发现问题在 **bug 管理平台**提交：归属你的问题会指派给你；若不属于你，沟通后**移交**对应负责人（如后端接口问题移交后端）。

#### 7. 测试用例会议

开发前由测试同学拉 UI、产品、前后端开会，提前对齐后续要测的用例、性能与测试数据。

#### 8. 研发中的协作日常

- **每日晨会**：每个开发者汇报进度与遇到的问题，及时反馈。
- **不可私自接受变更**：已确认的需求，若产品私下再下发需求，应反馈给自己 Leader，从团队需求走流程，避免「锅从天上来」。
- **Code Review**：各端负责人（如组长）对组员合入主分支的代码做复核。
- 需求管理平台示例：阿里内部用 **AOne**。

#### 9. 上线

- 提测完成、产品与测试确认无误后上线，避免无人值班时段（前后端都没人）上线。
- 本次发版相关开发负责人需留人；测试回归完，产品经理线上二次验收，确认后通知全体上线验收。
- 部署平台示例：阿里用**悍马**或**云效**。

#### 10. 复盘

上线后复盘：踩了哪些坑、是否有临时变更、预估工时是否准确（差很多说明排期有遗漏）、如何避免。这是保障后续项目质量的关键环节。

### 一个协作小经验

对接接口时，如果对方迟迟不回，可在有领导的大群里 @ 对方及其领导，通常会秒回——这是推动跨端协作的实用技巧。

## 小结

1. 标准流程：需求调研 → 梳理 → 评审 → UI 设计 → 团队需求会议 → 研发测试 → 测试用例会议 → 日常晨会/Code Review → 上线 → 复盘。
2. 需求评审用原型图，过滤不合理需求并评估工时。
3. 前后端先定接口协议，前端可用模拟数据并行开发。
4. 已确认需求不可私自接受变更，必须走团队流程。
5. 上线避开无人值班时段，需产品二次验收与全体验收。
6. 复盘沉淀经验，优化后续排期与质量。
