# 低代码平台技术原理综述（下）：引擎、权限与边界

> 视角：低代码平台落地专家。
> 承接（上）篇的 Schema 驱动内核，本篇补齐方法论层的另外三块拼图：**表单/流程引擎的职责**、**RBAC 在多端的落地**、以及**低代码 vs 零代码 / 自研 vs 采购的边界决策**。全部以课程真实篇目为锚点。

## 一、表单引擎 / 流程引擎：课程里已经有了雏形

课程没有直接喊"表单引擎""流程引擎"这些词，但它把这两类引擎的**核心机制**都做出来了——只是散落在实现里，需要点破。

### 1.1 表单 / 页面引擎（雏形已在）

课程的"组件拖拽 + 属性配置 + Schema 渲染"链路，本质就是**表单/页面引擎的最小可行实现**：

- **组件注册表**：`share` 公共包 `getComponentByType`（见《低代码项目发布页面—获取页面渲染》20-6）；
- **属性面板 Schema**：每个组件有"展示视图 + 配置属性"成对开发（14-x 系列：视频/图片/轮播/卡片/文本/富文本/二维码/警告/问卷输入等组件，均有「展示视图」与「配置属性」两篇）；
- **数据回写**：`onChange→onUpdate` 把视图输入写回 Schema（20-6）；
- **拖拽编排**：dnd-kit 数组重排（18-4）。

> 这四点合起来，就是一个**无代码表单/页面引擎**：拖组件 → 配属性 → 存 Schema → 渲染。商用化时，只需把"组件列表"抽象成可插拔的**组件市场**、把"属性配置"抽象成**引擎配置协议**即可。

### 1.2 流程引擎（课程未做，需补齐）

流程引擎负责"**业务如何流转**"：审批流、状态机、定时触发等。课程里**只有状态与动作的雏形**，没有真正的流程引擎：

- 发布页有「草稿 / 预览 / 发布」三态（19-2 草稿、19-3 预览、19-4 发布）；
- 问卷有「提交 / 是否提交过」状态（20-3、20-4）。

但"审批流、会签、条件分支流转"并未涉及。**落地建议**：若业务需要审批流，引入 BPMN 或轻量状态机，**与表单引擎解耦**——表单引擎产出数据，流程引擎决定数据怎么流转，二者通过事件/接口协作，不要揉成一团。

## 二、权限模型：RBAC 在多端的落地

课程在《放长线钓大鱼—规划低代码平台的系统架构》（6-2）里明确了平台三端：

| 端 | 角色 | 鉴权要求 |
|----|------|----------|
| 后台编辑端 | 编辑 / 管理员 | **需登录**：token 解析 `user` |
| 发布页 H5 | 访客 | **不鉴权**：凭 `pageId` 取数 |
| 后台数据统计 | 管理员 | 需登录 + 数据权限 |

这套"同一份数据，不同端不同可见性"，正是 **RBAC（角色-权限-资源）** 思想的体现。课程里已埋下关键零件：

- **用户身份提取**：《低代码项目后端接口开发—获取用户信息装饰器配置》（11-1）用装饰器从 token 解析 `user`，全局复用；
- **发布接口鉴权**：《后端接口开发—低代码项目编辑模块发布接口《上》》（14-2）处理"谁能发布"的权限判断；
- **访客免登录**：《低代码项目发布页面—后端接口低代码组件获取》（20-2）发布页接口不鉴权、用 `user?.id` 可选链兜底。

**RBAC 落地建议（商用化）**：

```
角色(管理员 / 编辑 / 访客) × 资源(页面 / 组件 / 问卷数据) × 操作(读 / 写 / 发布)
```

- 用 **NestJS Guard + 装饰器**（呼应 11-1 的用户信息装饰器）做统一鉴权，不要在 Controller 里散写 `if (!user)`；
- 数据权限（谁能看哪些问卷数据）单独一层，不要和菜单权限混用；
- 前端路由级 + 接口级双重拦截，避免"前端藏按钮、接口仍裸奔"。

## 三、低代码 vs 零代码：边界到底在哪

| 维度 | 低代码 | 零代码 |
|------|--------|--------|
| 研发介入 | 必须（写组件/接接口/改渲染器） | 不需要 |
| 灵活度 | 高，可深度定制与系统集成 | 受限，受平台能力边界约束 |
| 适用人群 | 研发 / 全栈工程师 | 业务运营 / 产品 |
| 典型代表 | 本平台、LowCodeEngine、Retool | 简道云、轻流、表单工厂 |
| 何时选 | 业务差异化、需集成、长期演进 | 标准化后台、快速交付 |

**关键判断**：如果"业务方想自己拖一个页面、且永远不需要研发改代码"，那是零代码场景，本资产**不适用**，应另起零代码材料。如果"页面要和公司既有系统深度打通、要有自研组件和接口"，那就是低代码，本平台路线正确。

## 四、自研 vs 采购：决策树（ROI 视角）

```
业务是否高度差异化 / 需深度系统集成 / 要长期自主演进？
├─ 是 → 自研低代码平台（本平台路线）
│       前期成本高，但长期可控、不与供应商锁定
└─ 否 → 采购 / 接入成熟方案
         ├─ 要"JSON 配置出页面" → 阿里 LowCodeEngine / Amis
         ├─ 要"数据后台 + 流程" → 商用 aPaaS（简道云 / 轻流类）
         └─ 标准化管理后台 → 直接上 Admin 框架，别造轮子
```

**ROI 提示**：自研的真正价值不在"省了多少写页面时间"，而在**业务差异化能力被沉淀成可复用资产**。若只是做几个标准化后台，采购远比自研划算。
