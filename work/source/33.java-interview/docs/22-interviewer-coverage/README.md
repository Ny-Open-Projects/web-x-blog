## 22.2 补漏合集（14 缺口 → 可背答案）

### G1. StringBuilder vs StringBuffer？字符串拼接编译器优化？（一面必问）

**【参考回答（可背）】** 三层：① StringBuffer 线程安全（方法 synchronized）、StringBuilder 不安全但快——单线程拼字符串一律 StringBuilder；② 编译器优化：`"a" + b` 常量折叠（编译期常量直接合并）+ 非 aconst 拼接在 javac 层自动改写为 StringBuilder（JDK8 及以前），**JDK 9+ 改为 invokedynamic + StringConcatFactory**（运行时按实际拼接形态选策略，比手写 StringBuilder 更快）；③ 循环内拼字符串即使编译器优化也每轮新建 Builder——循环拼接必须手动提到循环外。
**【追问链】** String.concat / + / StringBuilder 三者字节码差异？→ concat 每次 new；+ 在 JDK9+ 走 StringConcatFactory.makeConcatWithConstants。为什么 JDK9 改？→ 预估长度+按形态 specialize，基准测试比预 StringBuilder 快。
**【P10 加分项】** "我们规范：编译器已优化单行拼接，禁止手写 StringBuilder 反而降低可读性；循环拼接才强制 Builder。规范要跟着 JDK 版本演进，别把 8 年前的老规矩当真理。"

### G2. Java 8 Lambda/Stream 核心机制？（一面高频）

**【参考回答（可背）】** 四点：① Lambda 本质是**函数式接口实例**（单抽象方法），编译为 invokedynamic + LambdaMetafactory 生成实现类（非匿名内部类，延迟到首次调用才生成）；② Stream 三段式：源 → 中间操作（惰性，只记录不执行）→ 终端操作触发；③ 中间操作分无状态（filter/map）与有状态（sorted/distinct），有状态操作会打断"一次遍历"优化；④ **parallelStream 底层就是 commonPool**——IO 任务禁用（呼应第 2 章 2.4a.2 的全局故障域坑），数据量小或操作轻时并行反而慢（拆分/合并开销）。
**【追问链】** Optional 解决什么？→ 显式表达"可能缺失"，消灭 `if (obj != null)` 防御式代码；map/flatMap 链式判空。Stream 关闭吗？→ 文件 IO 的 Stream 要 try-with-resources。
**【P10 加分项】** 团队规范视角："我们规定 Stream 只用于集合内的声明式转换，业务逻辑复杂的用 for——可读性优先；parallelStream 一律需压测证明有收益才允许。"

### G3. JDK 8→21 新特性你用过哪些？（必考开放题）

**【参考回答（可背）】** 按"用过→知道→跟踪"分层背：
- **用过**：8 Lambda/Stream/Optional；9 模块化+Compact Strings；10 var；14 文本块 """；16 record（不可变数据载体，自动 equals/hashCode）；17 sealed + switch 模式匹配（限制继承层级）；21 虚拟线程（生产已上，见第 2 章）。
- **知道**：9 G1 转正；15 偏向锁移除；21 分代 ZGC。
- **跟踪**：Valhalla 值类型、Loom 后续、Amber 持续语法增强。
**【追问链】** record 和 Lombok @Data 区别？→ record 是语言级不可变语义（final 字段、无 setter、可加紧凑构造器校验），Lombok 是编译期代码生成；record 适合 DTO/值对象。sealed 解决什么？→ 把"继承权限"显式化，配合 switch 模式匹配做穷尽检查（exhaustiveness）——权限系统/状态机的建模利器。
**【P10 加分项】** "新特性落地的判断标准：record 我们全面替换了 DTO；sealed 用于权限模型；虚拟线程只在 IO 密集服务——每个特性都先回答'解决了我们什么痛'。"

### G5. 枚举单例为什么防反射/防反序列化？深浅拷贝？（一句话级补齐）

**【参考回答（可背）】** ① 反射防：JVM 规定**枚举类不能被反射创建实例**——Constructor.newInstance 遇到 enum 直接抛 IllegalArgumentException（源码里显式判断）；② 反序列化防：枚举的反序列化走 valueOf 按 name 查找既有实例，**不走 readObject 新建**——序列化前后的实例是同一个；③ 对比：普通单例防反射要私有构造器里加"已存在即抛异常"的判断，防序列化要写 readResolve——枚举天然全免。④ 深浅拷贝一句话：浅拷贝复制引用（clone 默认），深拷贝递归复制或序列化重造；不可变对象天然免拷贝问题。
**【追问链】** 枚举单例的缺点？→ 不能懒加载（类加载即初始化）、不能继承、有状态枚举难测试。

### G6. BlockingQueue 家族怎么选？（并发深挖追问）

**【参考回答（可背）】** 四类一张表（背）：① **ArrayBlockingQueue**：定长数组、单锁、内存预分配——有界要求首选；② **LinkedBlockingQueue**：可选有界（默认 Integer.MAX_VALUE！）、两把锁（读写分离）吞吐更高——Executors 的坑就是它的默认无界；③ **SynchronousQueue**：零容量、直接交接——CachedThreadPool 与高吞吐交换场景；④ **DelayQueue**：到期才能取——本地延迟任务（TTL 缓存/超时关闭）。另加 PriorityBlockingQueue（优先级）与 LinkedTransferQueue（无锁、tryTransfer）。
**【追问链】** put/take/offer/poll 四方法的阻塞语义矩阵？→ put 满阻塞、offer 立即返回/false、offer(timeout) 限时；take 空阻塞、poll 同理。
**【P10 加分项】** "线程池队列选型（第 2 章）的本质就是在这张表里选：有界保命选 Array，吞吐优先选有界 Linked，任务必快选 Synchronous。"

### G8. 数据误删了怎么办？备份恢复体系？（P10 稳定性必问）

**【参考回答（可背）】** 分"防、备、救"三层：
1. **防**：生产库权限分级（业务账号无 drop/truncate 权限）、高危 SQL 平台审批（工单+二次确认）、延迟从库（delayed replica，延迟 1 小时回放——误删的活数据在从库上还在）；
2. **备**：全量（XtraBackup 物理热备，每日）+ 增量（binlog 实时归档到远端对象存储）+ 定期恢复演练（**备份没恢复过等于没有备份**）；
3. **救**（按时间线）：① 立即停写/缩小影响面（FGW 只读、从库断复制防扩散）；② 误删表：从最近全量恢复到临时实例，用 binlog 回放到误删点前一秒，只导回误删数据（按表过滤，不能整库覆盖）；③ 小范围误删行：解析 binlog 反向生成补偿 SQL（或用闪回工具 my2sql），审核后执行；④ 恢复后对账 + 复盘。
**【追问链】** drop table 能闪回吗？→ drop 的恢复靠"全量+binlog 到误删前"重建整表，闪回工具只对 DML 有效，DDL 恢复成本高得多——这就是 DDL 平台化的原因。恢复期间业务怎么办？→ 只读降级 + 关键写走延迟从库临时顶（数据比主库旧一小时，业务确认可接受才切）。
**【P10 加分项】** "误删演练我们做过真实演练：从告警到恢复 40 分钟，其中 35 分钟花在'找最近有效备份'——之后备份元数据（位置/可用性/时间戳）进了监控。恢复速度是设计出来的，不是祈祷出来的。"

### G9. 连接池参数与连接泄漏排查？（高频）

**【参考回答（可背）】** 以 HikariCP 为准：① **maximumPoolSize**：连接数上限——不是越大越好（DB 侧连接数 = 实例数 × 池大小，轻易打爆 max_connections），公式起点 = CPU 核 × 2 + 磁盘数（HikariCP 官方建议，压测校准）；② **connectionTimeout**：获取连接等待超时（默认 30s，生产建议 1~3s 快速失败）；③ **idleTimeout/maxLifetime**：空闲回收与连接最长寿命（maxLifetime 要小于 DB 侧 wait_timeout，防"连到已断连接"）；④ **leakDetectionThreshold**：连接泄漏检测（借出超阈值打栈）——**排查连接泄漏的武器**：泄漏 = 业务拿了连接没还（事务里做 RPC/慢查询忘记关闭）；⑤ 兜底：minimumIdle 保持与 max 相同（连接预热，避免突发扩容抖动）。
**【追问链】** 连接打爆怎么排查？→ DB 侧 show processlist 看来源实例 → 该实例 Arthas/HikariCP 指标（active/idle/waiting）→ waiting 堆栈找"借了不还"的代码；连接池和线程池的联动（第 2 章 2.4.1：下游配额才是真瓶颈）。
**【P10 加分项】** "我们的事故：营销服务事务里调了慢 RPC，连接持有 30s×200 线程 → 打爆 DB。修复两件事：事务瘦身（RPC 移出事务）+ leakDetectionThreshold=30s 上线——把这类问题从'告警后人工翻'变成'日志直接给栈'。"

### G10. Netty：Reactor 模型/粘包拆包/零拷贝？（高并发深挖追问）

**【参考回答（可背）】** 三块：
1. **Reactor 模型演进**：单 Reactor 单线程（Redis 模式）→ 单 Reactor 多工作线程 → **主从 Reactor 多线程**（Netty 默认：boss 接收连接、worker 处理 IO，EventLoop 绑定线程——一个 Channel 生命周期锁定一个 EventLoop，无锁串行处理）；
2. **粘包拆包**：TCP 是字节流无消息边界——Netty 解码器四种解法：定长、分隔符、**长度域解码器 LengthFieldBasedFrameDecoder**（最常用）、自定义；本质都是"在应用层定义消息边界"；
3. **零拷贝**：堆外内存（DirectBuffer 避免堆内→堆外拷贝）+ CompositeByteBuf（逻辑聚合不拷贝）+ FileRegion（sendfile）；呼应第 7 章 Kafka zero-copy。
**【追问链】** Netty 空轮询 bug？→ JDK epoll 空轮询导致 100% CPU，Netty 检测后重建 Selector。为什么业务网关用 WebFlux 而不直接 Netty？→ Netty 是传输层框架，业务网关要的是"协议+路由+过滤器"生态（WebFlux/自研），直接 Netty 的团队要自己补齐整栈——选型讲清层次。
**【P10 加分项】** "我们对自研长连接网关的选型结论：Netty 做接入层、业务逻辑走独立服务（网关只做编解码与路由）——'Netty 只做 IO，业务不进 EventLoop'是长连接网关稳定的第一原则。"

### G11. Redis 延迟队列/pipeline？（追问补齐）

**【参考回答（可背）】** ① **ZSet 延迟队列**：score 存执行时间戳，消费端每秒 ZRANGEBYSCORE key 0 now LIMIT n → 取到即 ZREM（**原子性**：多消费者并发 ZREM 只有成功者执行——Lua 封装"取+删"两步防竞争）；可靠性：ZREM 成功后写"任务表"再执行，崩溃重启扫任务表补偿。② **pipeline**：攒 N 条命令一次发送（省 N-1 次 RTT），但**不保证原子**（与 Lua 的区别）；大批量导入用它，原子需求用 Lua（呼应 6.7.2）。③ 对比：毫秒级精度+轻量用 ZSet；任意精度/海量用 RocketMQ 时间轮（第 7 章）；本地内存级用 Netty 时间轮。
**【追问链】** ZSet 方案的缺点？→ 轮询空转耗 CPU（sleep 控制）、无 Ack 机制（崩溃即丢，需任务表补偿）、堆积无背压——所以"有 MQ 就别用 Redis 做延迟队列"。

### G12. 一致性哈希原理 + 负载均衡算法 + Feign 调优？（三合一补齐）

**【参考回答（可背）】** ① **一致性哈希**：把哈希空间组织成环（0~2^32-1），节点与 key 都映射到环上，key 顺时针找第一个节点——增删节点只影响相邻区段；**虚拟节点**（每物理节点映射几百个虚拟点）解决"节点少时分布倾斜"。场景：缓存分片、多活路由。对比取模（扩容全量迁移）与槽制（Redis Cluster 预分槽，折中方案）。② **负载均衡算法速览**：轮询/加权轮询（机器异构）/最少连接/一致性哈希/最慢优先——LVS 四层、Nginx 七层、网关层再按"机房→单元→实例"三级路由（呼应单元化）。③ **Feign 调优三件套**：超时（connect/read 分设，默认 read 过长会拖死线程池）、重试（默认 GET 才重试；POST 重试必须幂等！）、熔断（配 Sentinel/CircuitBreaker）；**连接池**：Feign 默认每请求新建连接，换 OkHttp/Apache HttpClient 连接池化。
**【追问链】** Feign 原理？→ 接口 + 注解 → 动态代理（JDK Proxy）→ 方法签名翻译为 HTTP 请求 → Ribbon/LoadBalancer 选实例 → 编码发送 → 解码返回。重试引发重复下单的事故怎么防？→ "重试必须配幂等"，呼应第 7 章幂等四法。

### G13. 微调还是 RAG？怎么选？（AI 高频追问）

**【参考回答（可背）】** 决策矩阵（背）：① **知识时效性/频繁更新** → RAG（改文档即生效；微调要重训）；② **行为/风格/格式对齐** → 微调（RAG 只给知识，调不动语气与输出结构）；③ **私有领域术语与推理** → 先 RAG 后微调（RAG 见效快成本低，微调需要高质量标注对）；④ **成本结构**：RAG 每次检索+长上下文 token 费用，微调一次训练费+小模型推理费——高频调用场景微调小模型更省。工程结论：**RAG 是默认起点，微调是效果上限的补刀**；两者可叠加（微调小模型做检索改写/意图分类，RAG 供知识）。
**【追问链】** 微调的数据要求？→ 数千到万级高质量样本，脏数据微调=负优化；怎么评估微调效果？→ 固定评测集回归（呼应 10.7.6）。

### G14. TCP/HTTP 基础（低优先级，给口径）

**【口径（知道即可，不展开）】** 三次握手（确认双向通信能力）/四次挥手（TIME_WAIT 等待 2MSL 防旧包）；TIME_WAIT 过多 = 频繁短连接，开连接复用解决；HTTP/2 多路复用解决队头阻塞（应用层仍有），HTTP/3 QUIC 基于 UDP；HTTPS = TLS 握手换密钥 + 对称加密传输。P10 层的考察点只有一个：**这些决定了你的连接池/超时/keep-alive 参数怎么配**（呼应 G9），纯原理题极少出现。
