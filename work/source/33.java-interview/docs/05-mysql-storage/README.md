## 5.1 零基础起步

### 卡片 1：MySQL 分层架构
连接器（认证/连接池）→ 分析器（词法/语法）→ 优化器（选索引/join 顺序）→ 执行器（调存储引擎接口）→ **InnoDB 存储引擎**。
记忆：Server 层管"语法与计划"，引擎层管"数据怎么存"。

### 卡片 2：为什么用 B+ 树不用 B 树/哈希/红黑树？
- **vs 哈希**：哈希不支持范围查询与排序；
- **vs 红黑树/AVL**：二叉树高，1000 万节点约 23 层 = 23 次磁盘 IO；B+ 树矮胖，3~4 层搞定（每页 16KB 可存大量键，非叶子节点只存键不存数据，扇出极大）；
- **vs B 树**：B+ 树数据全在叶子、叶子双向链表相连 → 范围查询/遍历 O(叶子数)；非叶子节点不存数据 → 扇出更大。
一句话背：**矮胖减少 IO，叶子链表支持范围扫**。

### 卡片 3：聚簇索引与回表
- 主键索引（聚簇索引）：叶子节点存**整行数据**；表本身就是按主键组织的 B+ 树。
- 二级索引（普通索引）：叶子存**索引列 + 主键值**；查其他列要拿主键回聚簇索引再查一次——**回表**。
- **覆盖索引**：查询列全在二级索引里，免回表（explain 出现 Using index）——高频 SQL 优化第一招。

### 卡片 4：ACID 分别靠什么实现
- **原子性**：undo log（回滚）；
- **持久性**：redo log（WAL：先写日志后写页）；
- **隔离性**：锁 + MVCC；
- **一致性**：前三者共同保证的结果（一致性是目的，其他是手段）。

### 卡片 5：一条 SQL 很慢，第一反应看什么？
`EXPLAIN` 关键列必背：
- type：system>const>eq_ref>ref>range>index>ALL（**ALL 全表扫要消灭**）；
- key：实际用的索引；rows：预估扫描行数；
- Extra：Using index（覆盖索引，好）/ Using filesort（排序没走索引）/ Using temporary（临时表，差）。

## 5.2 入门题（P4-P6）

### 题 5.2.1：什么是索引下推？什么是最左前缀？联合索引 (a,b,c) 能支持哪些查询？

**【参考回答（可背）】**
- **最左前缀**：联合索引按 a→b→c 排序，查询条件必须从最左列开始连续命中：`a=1`、`a=1 and b=2`、`a=1 and b=2 and c=3` 可用；`b=2`、`a=1 and c=3`（c 断层，只能用到 a）。范围查询（a>1）后右边的列用不上索引排序，但过滤仍可走（ICP）。
- **索引下推 ICP（5.6+）**：`where a like '张%' and b=10`，没有 ICP 时引擎要回表所有"张"姓行再由 Server 过滤 b；有 ICP 时**在引擎层先用索引里的 b 过滤**，回表次数大幅减少（explain 出现 Using index condition）。
- 排序优化：`order by a, b` 可用索引免排序；`where a=1 order by b` 也可用（a 是常量后 b 有序）。

**【追问链】**
1. 建索引原则？→ 区分度高、查询频繁、联合索引把等值条件放前、区分度放后（视场景）；前缀索引（长字符串取前 N 位，注意失去覆盖能力）；不超过太多列（写放大）。
2. 为什么主键要自增？→ 顺序插入页尾，避免**页分裂**（随机主键如 UUID 导致频繁分裂+碎片+缓存命中率低）。分布式下用雪花 ID 等"趋势递增"。

**【P10 加分项】**
讲"索引是双刃剑"：每个索引都是一棵要维护的 B+ 树，写放大 = 每个索引都要写；change buffer 对二级索引写优化（非唯一索引，页不在内存时先记 buffer，读时合并）。给出团队规范示例：单表索引 ≤5 个（经验值不是教条）、上线前慢 SQL 门禁（explain 成本预估）。

### 题 5.2.2：讲讲 MVCC？ReadView 是怎么生成的？RC 和 RR 的区别在哪？

**【参考回答（可背，高频压轴预备题）】**
1. **隐藏列**：每行有 trx_id（最后修改事务 ID）、roll_pointer（指向 undo log 版本链）。
2. **ReadView**：一致性视图，四要素：m_ids（生成时活跃未提交事务集合）、min_trx_id、max_trx_id、creator_trx_id。
3. **可见性判断**（必背逻辑）：沿 undo 版本链从新到旧找，对每个版本的 trx_id：
   - == creator → 可见（自己改的）；
   - < min_trx_id → 可见（生成视图前已提交）；
   - ≥ max_trx_id → 不可见（视图生成后才开始）；
   - 介于 min/max 之间：在 m_ids 里 → 不可见（未提交）；不在 → 可见（已提交）。不可见就顺着 roll_pointer 找上一版本重复判断。
4. **RC 与 RR 的唯一区别**：RC **每条查询语句**生成新 ReadView（能看到别人最新已提交）；RR **事务第一次查询**生成、整个事务复用（实现可重复读）。

**【追问链】**
1. RR 下能完全避免幻读吗？→ **不能完全避免**。快照读（普通 select）靠 MVCC 防幻读；**当前读**（select ... for update / update / delete）靠**间隙锁（gap lock）+ 行锁合成 Next-Key Lock** 防幻读；但"快照读后紧跟当前读"的混用模式仍会出现幻读（经典例子：先 select 无记录，update 却更新到了别人插入的行）。
2. RR 为什么是默认？→ 历史主因：基于语句复制（statement binlog）在 RC 下会出现主从不一致（RC 没有间隙锁+binlog 顺序问题），RR 才安全；现在 row 格式复制下 RC 其实也安全，互联网公司很多业务切 RC（锁冲突更小、死锁更少）。

**【P10 加分项】**
能画出undo 版本链 + ReadView 判断过程的图，并给出工程结论："我们把交易库从 RR 切到 RC 的收益：间隙锁消失后死锁率下降一个数量级；前提是 binlog 已是 ROW 格式 + 从库 GTID 复制。选隔离级别是工程决策不是教条。"

### 题 5.2.3：redo log、undo log、binlog 各自的作用？两阶段提交是干什么的？

**【参考回答（可背）】**
- **redo log**（InnoDB）：物理日志，"某页做了什么修改"，**循环写**，保证崩溃恢复（持久性）；WAL 思想：顺序写日志代替随机写页，MySQL 高写性能的基石。
- **undo log**：逻辑日志，反向操作（insert 的 undo 是 delete），保证原子性（回滚）+ MVCC 版本链。
- **binlog**（Server 层）：逻辑日志，语句/行/混合三种格式（**生产用 ROW**），追加写，用于**复制与恢复**。
- **两阶段提交（2PC，必背）**：update 语句的提交顺序：
  1. 写 redo log，置 **prepare** 状态；
  2. 写 binlog；
  3. redo log 置 **commit**。
  崩溃恢复规则：redo prepare 但未 commit → 查 binlog：binlog 完整则提交，不完整则回滚。
  **为什么必须两阶段**：保证 redo 与 binlog 的一致性——否则崩溃后"主库有数据从库没有"或反之，存在必然分叉的崩溃窗口（主库有数据从库没有或反之），复制与恢复必错。

**【追问链】**
1. redo 和 binlog 区别一句话？→ 层级（引擎/Server）、物理/逻辑、循环写/追加写、崩溃恢复/复制归档。
2. 组提交是什么？→ 多个事务的 redo/binlog 合并一次 fsync（binlog_group_commit_sync_delay 微调），高并发下把"每事务一刷盘"摊薄成"一批一刷盘"，TPS 显著提升——**高并发写优化的隐藏大招**。
3. innodb_flush_log_at_trx_commit 和 sync_binlog 怎么配？→ 双 1（1,1）：不丢数据但每事务两次 fsync，最安全最慢；金融必双 1，普通业务 (1,2) 或 (2,1) 换吞吐，接受宕机丢 1 秒。

**【P10 加分项】**
指出双 1 的真实代价与折中：组提交 + NVMe 盘 + RAID 卡 BBU 缓存后，双 1 的 TPS 并不灾难；"参数调优前先问业务能接受丢多少"——把存储参数翻译成业务风险语言。

### 题 5.2.4：InnoDB 有哪些锁？死锁怎么办？

**【参考回答（可背）】**
锁分类：
1. 粒度：全局（FTWRL）、表级（表锁、**元数据锁 MDL**、意向锁 IS/IX）、行级；
2. 行锁三种（RR）：**记录锁**、**间隙锁**（锁区间不锁记录，RR 防幻读的关键，RC 无）、**Next-Key**（记录+间隙，左开右闭）；
3. 意图：共享 S / 排他 X（select for update、DML 自动加 X）；
4. 插入意向锁（gap 冲突时的兼容协调）；
5. 其他：自增锁（auto-inc，MySQL 8 改为轻量级互斥量，innodb_autoinc_lock_mode=2 交错模式配合批量插入最佳）、外键锁。

死锁：两个事务互相等待对方持有的锁。排查：`show engine innodb status` 的 LATEST DETECTED DEADLOCK 段（生产建议打开 innodb_print_all_deadlocks 记全量到错误日志）。
预防清单：**多表/多行操作按固定顺序、大事务拆小、RR→RC 消间隙锁、热点行用乐观锁版本号或排队串行化、索引避免锁升级为表扫（无索引 where 会锁全部扫过的行）**。

**【P10 加分项】**
热点行更新（秒杀扣库存）专项：单行锁成为瓶颈时——① 库存分段（拆 N 行轮询）② Redis 预扣 + 异步落库 ③ 排队（串行化消除锁竞争）；并讲 MySQL 8.0 的热点更新优化（innodb 允许 skipping lock wait 的 SKIP LOCKED / NOWAIT）。

## 5.3 进阶题（P7-P8）

### 题 5.3.1：主从复制的原理？主从延迟怎么解决？

**【参考回答（可背）】**
复制三线程：主库 **binlog dump**（推 binlog）→ 从库 **IO 线程**（写 relay log 中继日志）→ 从库 **SQL 线程**（回放）。
并行复制演进：MySQL 5.6 库级并行 → 5.7 **组提交 LOGICAL_CLOCK**（同一组提交的事务并行回放）→ 8.0 **writeset**（按行冲突检测并行，延迟显著改善）。
保证不丢：半同步复制（semi-sync，至少一个从库确认收到 binlog 才返回客户端成功）；更高：MGR（组复制，Paxos 多数派）。
**主从延迟原因**：从库单线程回放慢（大事务、DDL）、机器差、锁冲突。
**延迟方案（分场景背）**：
1. 写后读强一致：**读主库**（写后 N 秒内读主，会话标记法）；
2. GTID/位置等待：确认 binlog 已回放再读；
3. 业务兜底：关键校验（支付结果页）强制读主；
4. 架构级：读写分离路由中间件（ShardingSphere/ProxySQL）内置延迟感知。

**【追问链】**
1. binlog 三种格式的坑？→ statement 有不确定性函数问题（now()/uuid() 主从不一致）；row 量大但安全（默认）；mixed 自动切换但边界难控。
2. 大表 DDL 怎么做？→ Online DDL 有局限（部分操作仍锁表），大表用 gh-ost/pt-osc（影子表+增量同步+原子切换）；8.0 的 INSTANT ADD COLUMN 是例外。

**【P10 加分项】**
高可用架构对比：MHA（外挂切换）/ MGR（Paxos）/ 云厂商 RDS 三节点企业版；讲"RTO/RPO 权衡 + 故障演练"——数据库高可用是要**演练验证**的，不是架构图画出来的。

### 题 5.3.2：什么时候分库分表？怎么选分片键？如何扩容？

**【参考回答（可背，P9 必考）】**
**要不要分（先给决策树，别上来就分）**：
1. 先优化：索引、SQL、冷热分离、读写分离、归档——**能撑到千万级再考虑**；
2. 单表行数经验阈值：B+ 树 3~4 层可承受约 2000 万~5000 万行（取决于行宽），但**真正的瓶颈是"写入吞吐与运维操作（DDL/备份）"而非查询**；
3. 分库（解决连接数与写吞吐）优先于分表（解决单表数据量）。

**分片键选择四原则**：① 最高频查询带分片键；② 分布均匀防热点；③ 业务身份相关（user_id 最常见，订单按 user_id 分片 + 订单号路由表/基因法）；④ 尽量避免跨片查询与跨片事务。
**路由算法**：取模（均匀，扩容难）vs 范围（好扩容，热点）vs 一致性哈希/基因法（订单号携带 user 分片位，双维度查询免二次路由）。
**非分片键查询**：异构索引（ES 宽表）、CQRS（写 MySQL 读 ES）、二次路由表。
**扩容方案**：翻倍扩容（32→64 库，mod 迁移一半数据，双写切换四步：存量迁移 → 增量双写 → 数据校验 → 切读切写）；或提前规划足够分片数（如一开始就 1024 逻辑库，物理上先合并部署）。
**分布式 ID**：雪花（时钟回拨问题：回拨等待/序列扩展/备用位）、号段模式（DB 批量取段）、Leaf/UidGenerator。

**【追问链】**
1. 分库后跨库事务怎么办？→ 见第 8 章：尽量单库事务化（按用户聚合）、最终一致（消息表/SAGA）、强一致场景 TCC；分布式事务是分库的最大代价，**能不分就不分**。
2. 分页怎么翻？→ 分片键内分页正常；全局分页用 ES/宽表，或"禁止跳页改滚动"（游标法）。

**【P10 加分项】**
完整讲一次迁移项目叙事：背景（单表 8 亿行，DDL 6 小时）→ 方案对比（分库分表 vs TiDB/OceanBase vs 归档+读拆）→ 最终选择（历史库归档 + 热数据分 16 库 64 表 + ES 承接复杂查询）→ 双写灰度四步走 → 数据校验工具（对账平台逐行 checksum）→ 效果（写 TPS x3，DDL 分钟级）。**完整决策链 + 被否决的备选方案**是 P10 叙事标志。

### 题 5.3.3：count(*)、count(1)、count(id)、count(字段) 哪个快？为什么 InnoDB 不存总行数？

**【参考回答（可背）】**
- InnoDB 不存总行数因为 **MVCC**：不同事务看到的行数不同（并发未提交/已删除），无法全局缓存一个数。
- 四者效率：count(*) ≈ count(1) ≥ count(id) > count(字段)。count(*)/count(1) 优化器选最小索引树扫；count(id) 要取主键值；count(字段) 要判 NULL 且不能走覆盖就回表。
- 大表计数方案：explain 估算（不精确）、缓存计数（Redis，接受误差）、**计数表**（独立小表 + 事务内增减 + 定期校准）、信息表分区汇总。

**【P10 加分项】**
把 count 问题升华成"分布式计数一致性"：高并发计数（点赞数/库存显示）= 计数与明细的最终一致问题，给出"明细为准 + 异步聚合 + 展示容忍分钟级误差 + 对账兜底"的通用范式。

## 5.4 压轴题（P9-P10）

### 题 5.4.1：设计一个支撑亿级用户的账户余额系统（资金安全 + 高并发扣减）

**【参考回答（框架可背：建模 → 一致性 → 并发 → 对账）】**
1. **建模**：账户表 = 余额 + 版本号 + 流水表分离；余额更新只增不减可通过"记账"实现（每笔交易双向流水），支持审计。
2. **并发扣减三方案**：
   - 乐观锁：`update account set balance=balance-100 where id=? and balance>=100`（条件更新防超扣，一行 SQL 原子，**默认方案**）；
   - 悲观锁 select for update（短事务下可用）；
   - 热点账户：**余额分桶**（拆 100 份轮询）或记账缓冲（先记流水异步合并，T+1 落余额，展示用预估）。
3. **一致性**：扣减 + 流水同库同事务；跨账户转账 = 两笔流水的最终一致（消息表/SAGA + 冲正），避免跨库 2PC。
4. **资金安全三道闸（必背）**：
   - 事前：幂等（请求号唯一索引，防重复扣）、限额风控；
   - 事中：条件更新防负余额、隔离级别 RC 降低锁冲突；
   - 事后：**对账系统**——准实时（流式对账延迟告警）+ T+1 全量对账，差异工单自动冲正。
5. **扩展性**：按 user_id 分库分表；平台大商户热点单独通道；审计流水分库按时间归档。

**【追问链】**
1. 余额要展示精确值，缓冲记账怎么保证？→ 展示层读"已落库余额 + 未合并流水增量"，用户视角强一致，底层异步合并。
2. 为什么不用分布式锁？→ 锁是串行化手段，吞吐低且有锁服务故障风险；数据库行锁 + 条件更新在单行内已是原子，分布式锁只适合跨资源协调。

**【P10 加分项】**
资金系统黑话四件套（能说出即有实战）：**对账（reconciliation）、冲正（reversal）、幂等、日切**；再补一句架构观："资金系统宁可降级不可错账，可用性让步于一致性"——这是和普通业务系统相反的价值观，面试官在听这个。

### 题 5.4.2：MySQL 会不会被 NewSQL（TiDB）替换掉？你怎么做存储选型？

**【参考回答（开放题，考技术判断力）】**
1. **MySQL 的统治力来源**：生态（运维/工具/人才）、稳定 30 年、单机性能足够大多数业务、云厂商 RDS 把运维难度打平。
2. **NewSQL 的甜区**：数据量超大（TB~PB）、写入吞吐单机瓶颈、需要弹性扩缩、强一致多副本（TiDB Raft/PD 调度）；代价：资源占用高、复杂 SQL 优化器不如 MySQL 成熟、运维与人才成本。
3. **中间路线**：PolarDB/Aurora 存算分离（读写分离+共享存储，兼容 MySQL 无需分库分表）、ShardingSphere 分片中间件、归档+冷热分层。
4. **选型决策框架（背这个）**：数据量 <500G 用 MySQL 主从；500G~5T 存算分离云数据库或分库分表；>5T 或写入超单机且需要分布式事务 → NewSQL；分析型 → OLAP（ClickHouse/Doris）；全文检索 → ES。**按"数据量×写入吞吐×一致性要求×团队运维能力"四维打分。**
5. **判断**：MySQL 不会被替换，而是**边界化**——OLTP 热数据仍是它的天下，超大规模与多模场景被 NewSQL/专用引擎分食。技术人的正确姿势是"组合拳"而非"信仰"。

**【P10 加分项】**
给一个真实案例：订单库 3T 后从"分库分表"与"换 TiDB"两条路中选型，最终理由（改造成本 vs 运维成本 vs 团队熟悉度），并量化结论。**选型题的胜负手在"为什么不要另一个选项"。**

## 5.5 本章高频追问链图谱

```
B+ 树 ──→ 扇出/3~4 层 ──→ 自增主键/页分裂 ──→ 雪花 ID
联合索引 ──→ 最左前缀 ──→ ICP ──→ 覆盖索引 ──→ explain 门禁
MVCC ──→ ReadView ──→ RC/RR ──→ 间隙锁 ──→ 幻读边界 ──→ RC 选型
redo/undo/binlog ──→ 两阶段提交 ──→ 组提交 ──→ 双 1 与业务取舍
主从复制 ──→ 半同步/MGR ──→ 延迟方案 ──→ 读写分离路由
单表瓶颈 ──→ 分片键四原则 ──→ 基因法 ──→ 双写扩容四步 ──→ 分布式 ID
```

## 5.6 一页速记卡

1. B+ 树：矮胖省 IO、叶子链表扫范围；主键自增防页分裂。
2. 二级索引存主键，回表是成本；覆盖索引免回表；ICP 引擎层先过滤。
3. MVCC 四要素 ReadView + 版本链；RC 每语句、RR 每事务一次视图。
4. RR 防幻读：快照读靠 MVCC，当前读靠 Next-Key；混用仍有幻读。
5. 两阶段提交：redo prepare → binlog → redo commit；崩溃看 binlog 定夺。
6. 双 1 最安全；组提交提吞吐；参数翻译成业务风险再定。
7. 死锁预防：固定顺序、小事务、热点分段、RC 减间隙锁。
8. 主从延迟：关键读走主库；并行复制 writeset；半同步保不丢。
9. 分库分表：先榨干单库，分片键选 user_id，扩容用双写四步。
10. 资金三道闸：幂等 → 条件更新 → 对账冲正。

## 5.8 增补题（v1.1 深度扩充）

### 题 5.8.1：复制链路断了，从库延迟持续增大，完整排查路径？

**【面试官意图】** 检验"会搭复制"之上——是否会救故障。
**【参考回答（可背）】** 四步定位：① 看 `show slave status\G` 的 Last_IO_Errno/Last_SQL_Errno 区分 IO 线程断还是 SQL 线程停——IO 断多是网络/权限/binlog 位点丢失；SQL 停多是一条 DML/DLL 报错（1062 主键冲突最常见）；② SQL 线程停：读 Relay_Log_Info 定位出错事务，业务判断跳过（`SET GLOBAL sql_slave_skip_counter=1`）还是修复数据；③ 单线程回放瓶颈：看 Seconds_Behind_Master 曲线与并行复制是否开启（writeset）；④ 断点续传依赖：GTID 开启时自动找位点，无 GTID 手动找 master 位点极痛苦——**GTID 是生产必开项**。
**【追问链】** ① 1062 跳过会造成数据不一致吗？（会，跳过=人工判定为幂等或可重做，跳过后必须走对账核平）② 大事务为什么拖垮回放？（SQL 线程按事务粒度回放，一个 2 小时的事务回放也 2 小时——根因治理还是"大事务拆小"，呼应 5.2.4）。
**【P10 加分项】** 给"复制健康度监控清单"：Seconds_Behind_Master、SQL 线程吞吐对比主库写入速率（差值=积压速率）、relay log 磁盘水位——三条都接告警，延迟问题从"用户报障发现"提前到"分钟级发现"。

### 题 5.8.2：新表上线前的索引设计 checklist（P10 会怎么评审建表 SQL）

**【参考回答（可背）】** 十条评审清单（背成模板）：① 主键趋势递增（自增/雪花，禁 UUID）；② 每个高频查询模式都有一条索引覆盖（联合索引列序：等值在前、范围在后、排序列跟后）；③ 区分度低的列（如性别/状态）不单独建索引，只能做联合索引前置等值；④ 长字符串用前缀索引且接受失去覆盖能力，或 hash 列辅助；⑤ 单表索引数 ≤5 且每个索引有明确服务对象（问"这个索引给哪条 SQL 用"答不上就删）；⑥ 外键不用（应用层保证一致性），但**逻辑外键关系要文档化**；⑦ 大字段（TEXT/BLOB）拆溢出表；⑧ 时间列必建（归档/范围查询刚需）；⑨ 每 DDL 走 Online DDL 评审（gh-ost）；⑩ 预估数据量 >千万的表提前规划分片键。
**【追问链】** ① 索引多了写放大怎么权衡？（写 TPS 下降可压测量化：每多一个二级索引，insert 成本 +一次 B+ 树写入，热点表 3 个以上二级索引就要压测）② 统计信息过期导致选错索引怎么办？（analyze table 定期 + 监控 explain 走错案例）。
**【P10 加分项】** "清单进 CI：DDL 上线卡点自动检查（无主键/无时间列/索引超限自动拦截）+ 大表 explain 成本门禁——索引设计从'师傅经验'变成'平台能力'。"

### 题 5.8.3：Buffer Pool 的调优与命中率监控？

**【参考回答（可背）】** 原理一句话：InnoDB 用 Buffer Pool 缓存页（默认 LRU 变种：young/old 子链 5:3，老区停留 1s 才晋升——**防全表扫污染**）。调优：① 大小：专机给物理内存 60%~70%（innodb_buffer_pool_size），容器按 Min(堆外预算, 60%)；② 命中率：`show global status like 'innodb_buffer_pool_read%'`，(1 - read_requests/物理读) 应 >99%，突然下跌=大扫描/冷启动/池太小；③ change buffer：对写多读少的二级索引页有效，随机写场景可观察。预警信号：命中率下降 + 物理读 IOPS 上升 = 内存被"烫穿"，先查新增大扫描 SQL。
**【追问链】** ① 为什么双 LRU 要 1 秒滞留？（一次性全表扫的页只进 old 区不污染 young 热点——预热与防污染的关键设计）② 预读机制怎么配合？（线性读预读连续页进 old 区，随机读预读关闭）。
**【P10 加分项】** 类比升华："Buffer Pool 命中率下降的排查与 Redis 缓存命中率下降同构——都是'回源流量异常'，第一反应应该是'谁新增了全表扫描/谁把热点 key 冲掉了'，而不是先调参。存储层缓存思想是通的。"

### 题 5.8.4：大表 DDL 为什么必须用 gh-ost？它的原理？

**【参考回答（可背）】** 背景：大表 Online DDL（8.0 INSTANT 之外的操作）仍有锁表风险（如改列类型、加索引在低版本仍是 INPLACE+长时间执行），且主从延迟不可控。gh-ost 原理四步：① 创建幽灵表（ghost table，目标结构）；② 拉取 binlog 作为变更流（不依赖触发器——比 pt-osc 更安全的关键差异）；③ 批量拷贝存量行 + 并行应用增量 binlog；④ cut-over：原子 Rename 切换（拿独占锁的瞬时窗口完成换表）。可控点：限速（按主从延迟自适应节流）、暂停、随时回滚。
**【追问链】** ① 8.0 的 INSTANT ADD COLUMN 为什么快？（只改元数据不动数据行，但注意：INSTANT 列只能加在末尾且与行格式有约束）② gh-ost 期间业务能写吗？（能，双写进幽灵表由 binlog 流保证，cut-over 瞬间一致性）。
**【P10 加分项】** "DDL 平台化：所有 DDL 走 gh-ost 管道（限速模板/审核/一键回滚），DBA 只审不操——把'最危险的操作'变成'最安全的流程'，这是 DBA 团队从操作者变平台的关键跃迁。"
