## 25.1 零基础起步（四张概念卡）

### 卡片 1：文档模型
数据单位是**文档**（BSON = 二进制 JSON），类似一条 JSON：字段可为嵌套文档/数组。**单文档上限 16MB**，天然原子（单文档读写在副本集内始终原子）。对应关系模型：集合（collection）≈ 表，文档 ≈ 行，但**无固定 schema、无 JOIN**——关联关系用**嵌入**（1:少量，一起读）或**引用**（1:多，手动两次查询或 $lookup）表达。建模第一问："数据是整体读还是分开读？"——整体读就嵌入，分开更新就引用。

### 卡片 2：ObjectId
文档默认主键 `_id`。现代驱动的 ObjectId = **4 字节秒级时间戳 + 5 字节随机（进程级）+ 3 字节递增计数**——时间戳前缀使其**天然趋势递增**，作为 `_id` 写入分布式友好（类似雪花 ID 的效果）。

### 卡片 3：副本集
一主多从，主可写从可读；复制靠 **oplog**（固定容量的操作日志，从库拉取回放）。主挂了触发选举（类 Raft 多数派协议，**最多 50 成员、7 个可投票**）。写关注（Write Concern）：w:1 主确认即返回、w:"majority" 多数派确认（不丢已确认写）、w:0 不等确认；读关注（Read Concern）：local 读本机最新（可能被回滚）、majority 读已多数派确认、linearizable 线性一致。

### 卡片 4：分片
三层：**mongos**（路由）→ **config 副本集**（元数据）→ **shard**（每个是副本集）。数据按 **shard key** 切分（range 或 hashed）。mongos 对不带分片键的查询广播全分片——**查询必带分片键**是性能第一原则。

## 25.2 入门题（P5-P6）

### 题 25.2.1：什么场景选 MongoDB 而不是 MySQL？

**【参考回答（可背）】** 四类适配：① **schema 多变**：商品不同类目属性不同（图书有作者页数，手机有内存颜色）——MongoDB 无需 NULL 字段与 DDL 变更；② **嵌套整体读**：商品详情/商品评价一起读写——嵌入文档免 JOIN；③ **海量写入水平扩展**：日志、行为埋点、IoT——分片开箱即用；④ **快速迭代**：原型期 schema 未稳。MySQL 仍主导：强事务、多表关联复杂、资金账务。**常见混合架构：核心账务 MySQL + 商品/内容/行为 MongoDB，以 binlog/CDC 同步。**

**【追问链】** MongoDB 完全没有事务吗？→ 错：单文档天然原子；4.0 起副本集多文档事务、4.2 起分片集群事务（走 session，默认 60s 超时）——但**能用单文档原子解决就不开事务**。mongoose/ORM 的坑？→ ODM 层掩盖了文档模型本质，P10 应能脱离 ODM 直谈文档设计。

### 题 25.2.2：MongoDB 有哪些索引类型？

**【参考回答（可背）】** 单字段/复合/多键（数组自动展开）/文本/地理（2dsphere）/通配符（4.2+，schema 多变的字段）；特殊用途：**TTL**（expireAfterSeconds，后台约 60 秒一轮删除过期文档）、**partial**（部分索引只索引满足条件的文档，省空间）、sparse、唯一。底层 B 树；explain 看 COLLSCAN/IXSCAN——与 MySQL 的 explain 思路同构。

**【追问链】** 索引越多越好吗？→ 和 MySQL 一样是双刃剑：每个索引都参与写放大；无索引查询走 COLLSCAN 全集合扫描。

## 25.3 进阶题（P7-P8）

### 题 25.3.1：ESR 原则是什么？举例说明复合索引设计。

**【参考回答（可背）】** MongoDB 官方复合索引设计原则：**E（Equality 等值）→ S（Sort 排序）→ R（Range 范围）**。例：查询 `{userId: "u1", status: {$in: [...]}}` 按 `createdAt` 倒序取 10 条——索引 `{userId: 1, status: 1, createdAt: -1}`（等值列在前，排序列随后，范围列最后）。为什么 E 在 S 前：等值列保证排序连续性。和 MySQL 联合索引原则基本同构，但 MongoDB 明确给了 ESR 口诀。

**【追问链】** $in 算 E 还是 R？→ $in 是多组等值，官方按 E 处理（每组内排序有效）。覆盖索引？→ projection 排除 _id 后全走索引即 covered query。

### 题 25.3.2：副本集选举、oplog 与回滚？

**【参考回答（可背）】** 主挂 → 有投票权成员多数派选新主（类 Raft：term/多数派/日志新度优先，通常数秒完成）。从库异步拉 oplog 回放——**异步复制 → 主挂可能丢"未多数派确认"的写**，这些写在新主上被回滚（写进 rollback 目录，可人工恢复）。工程防御：Write Concern w:"majority" 让写得到多数派确认（代价是延迟）；Read Concern majority 读已确认数据。**"MongoDB 会不会丢数据"的正确回答**：取决于写关注配置——w:1 会丢、majority 不丢（多数派持久），这是性能与持久性的旋钮。

**【追问链】** oplog 满了怎么办？→ capped collection 循环覆盖，从库落后超过 oplog 窗口就得全量重同步——**oplog 窗口监控是运维必配**。仲裁节点（arbiter）的作用与争议？→ 只投票不存数据省资源，但削弱多数派持久性，生产慎用。

### 题 25.3.3：分片键怎么选？选错了怎么办？

**【参考回答（可背）】** 三原则：**高基数**（避免单调递增值全打到最后一个分片——hashed 分片可解）、**查询必带**（不带则全分片广播）、**写分布均匀**。类型：range（范围查询友好）vs hashed（写均匀，范围查询废）。选错代价：分片键**不可随意更改**——4.4 可 refine 追加后缀字段，5.0 有 reshardCollection 在线重分片但代价大。**所以分片键是 MongoDB 里最像"分库分表分片键"的一次性重大决策**（呼应第 5 章 5.3.2 的分片键原则——两个领域同构）。

**【追问链】** chunk 是什么？→ 数据切分单位（默认按范围），balancer 自动在分片间迁移 chunk 均衡负载；4.4+ 平衡策略更细化。jumbo chunk？→ 超过切分阈值不可分割的 chunk（同分片键值海量子文档），需手动拆分或调整。

## 25.4 压轴题（P9-P10）

### 题 25.4.1：设计一个商品详情/内容平台的数据架构（混合存储）

**【参考回答（框架可背）】**
1. **存储分工**：账务/库存 MySQL（强事务）；商品详情 MongoDB（schema 多变：不同类目不同属性结构，嵌入整体读）；搜索 ES；缓存 Redis 多级。
2. **商品建模**：主文档 = 基础字段 + `attributes` 嵌套数组（类目异构属性）+ `skus` 嵌套（SKU 数量有限）；评价/浏览历史引用拆集合（1:多且独立增长，避免 16MB 与无限嵌入）；热点字段**冗余**进主文档（如类目名，免 $lookup）。
3. **一致性**：MySQL 库存扣减（强事务）与 MongoDB 商品状态通过**领域事件/CDC** 同步（最终一致）；对账兜底。
4. **索引**：ESR——`{categoryId: 1, status: 1, updatedAt: -1}`；TTL 索引清理过期秒杀缓存文档；partial 索引只索引"上架"商品。
5. **规模演进**：商品集合按 categoryId 分片（查询必带类目）或 hashed productId（写均匀）；预估迁移路径先于数据量到达。
6. **Java 集成**：Spring Data MongoDB——MongoRepository 简单 CRUD，**复杂聚合用 MongoTemplate**（更显式可控）；连接池（maxConnectionPoolSize 与服务实例数联动）；事务走 @Transactional（副本集即可用）。

**【追问链】** 16MB 文档上限会撞吗？→ 评价/日志独立集合；大字段（图文）拆 GridFS 或对象存储存 URL。聚合管道性能？→ $match 前置走索引、$lookup 是性能黑洞（能冗余就冗余）、$facet 注意内存限制（allowDiskUse）。

**【P10 加分项】** 混合架构的真相："我们最终没有'替换 MySQL'，而是**按数据特征分工**——账务留 MySQL，商品与内容迁 MongoDB，搜索走 ES。中间的同步层（CDC）才是整个架构最脆弱也最值得投入的地方。"——混合架构最难的不是单库选型而是边界与同步。

---

### 题 25.4.2：从 MySQL 迁移商品数据到 MongoDB，怎么迁？

**【参考回答（框架可背）】** 复用第 5 章 5.3.2 的双写四步法（两领域同构）：① 建模转换（表→文档，嵌套化设计先评审）；② 存量迁移（快照导出→转换→导入）；③ 增量双写（CDC 捕获 MySQL 变更→写 MongoDB，对账工具逐文档比对）；④ 切读切写。**MongoDB 特有风险点**：建模错误返工成本极高（文档结构改动=全量重写），所以建模评审在迁移前必须做两次；事务语义差异（MySQL 多表事务 → MongoDB 单文档原子+少量多文档事务）。

**【追问链】** 为什么不直接用 Flink CDC 同步？→ 可以，正是推荐方案；关键是 MongoDB 侧的**幂等写**（upsert by _id）与乱序容忍（按 updated_at 版本号丢弃旧写）。

## 25.6 一页速记卡

1. 建模第一问：整体读还是分开读？嵌入 vs 引用；16MB 上限决定大字段拆集合/GridFS。
2. 单文档天然原子；4.0 副本集多文档事务、4.2 分片事务；能用单文档就不开事务。
3. ObjectId = 4B 时间戳 + 5B 随机 + 3B 计数——趋势递增，写入友好。
4. 索引 ESR：等值→排序→范围；TTL 每 60 秒巡检；partial 省 space；explain 看 COLLSCAN/IXSCAN。
5. 副本集最多 50 成员 7 投票；oplog 是 capped 循环——**oplog 窗口监控必配**。
6. 写关注 w:1 会丢、majority 不丢（多数派持久）——性能与持久性的旋钮；读关注同理。
7. 分片键三原则：高基数、查询必带、写均匀；range vs hashed；选错靠 refine(4.4)/reshard(5.0) 补救。
8. mongos 对不带分片键的查询广播全分片——查询必带分片键。
9. Java：MongoRepository 简单 CRUD、复杂聚合用 MongoTemplate；事务 @Transactional（副本集起）。
10. 混合架构：账务 MySQL + 商品/内容 MongoDB + 搜索 ES；**最脆弱的是 CDC 同步层**。
