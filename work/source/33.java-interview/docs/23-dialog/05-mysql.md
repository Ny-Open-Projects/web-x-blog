# 对话版 · 第 5 章 MySQL 与存储（二面重头戏，约 30 分钟）

**【面试官】** 为什么 MySQL 索引用 B+ 树，不用哈希、红黑树、B 树？

**【面试者】** 对比答：哈希不支持范围与排序；红黑树是二叉的太深（千万行 23 层=23 次磁盘 IO）；B 树数据存在所有节点、扇出小、范围查询要中序回溯。B+ 树两个特点：非叶节点只存键（扇出极大，千万行 3~4 层）+ 叶子双向链表（范围扫顺链走）。矮胖省 IO，链表支持范围——就这么简单。

**【面试官】** 什么是回表？怎么避免？

**【面试者】** 二级索引叶子存"索引列+主键"，查其他列要回聚簇索引再查一次。避免：覆盖索引——查询列全在索引里（explain 出 Using index）。高频 SQL 优化第一招。索引设计还有 ICP（5.6+，引擎层先用索引里的其他列过滤再回表）。

**【面试官】** 联合索引 (a,b,c)，哪些条件能走索引？

**【面试者】** 最左前缀：a=1、a=1 and b=2、a=1 and b=2 and c=3 走；b=2 不走；a=1 and c=3 只用到 a（c 断层）。范围查询后的列用不上索引排序。长字符串用前缀索引（失去覆盖能力）。

**【面试官】** MVCC 怎么实现的？RC 和 RR 的区别到底在哪？

**【面试者】** 三件套：隐藏列（trx_id/roll_pointer）+ undo 版本链 + ReadView（m_ids/min/max/creator）。可见性判断沿版本链从新到旧。**RC 和 RR 的唯一区别：RC 每条语句生成新 ReadView，RR 事务首次查询生成、全程复用。** RR 下快照读靠 MVCC 防幻读、当前读靠 Next-Key Lock（记录+间隙，左开右闭），但"快照读后紧跟当前读"的混用模式仍有幻读。

**【面试官】** 你们生产用什么隔离级别？为什么敢不用默认 RR？

**【面试者】** RC。前提是 binlog 已是 ROW 格式（statement 格式下 RC 会主从不一致）。收益：间隙锁消失，死锁率降一个数量级，锁冲突更小。这是工程决策不是教条——每条都有前提和收益量化。

**【评注】** ⭐ "敢不用默认值+前提+收益量化"是二面亮点。

**【面试官】** redo log、undo log、binlog 各干什么？为什么提交要两阶段？

**【面试者】** redo：物理日志循环写，崩溃恢复（持久性），WAL 是高写性能基石；undo：逻辑反向日志，回滚+MVCC 版本链；binlog：Server 层逻辑日志追加写，复制与恢复。两阶段提交：redo prepare → 写 binlog → redo commit；崩溃恢复时 redo prepare 但 binlog 完整则提交、不完整则回滚——保证 redo 与 binlog 一致，否则主从必错。

**【面试官】** 死锁遇到过吗？怎么排查和预防？

**【面试者】** 排查：show engine innodb status 的 LATEST DETECTED DEADLOCK，生产开 innodb_print_all_deadlocks。预防四条：多表操作按固定顺序、大事务拆小、热点行分段或乐观锁、RR→RC 减间隙锁。热点行更新（秒杀扣库存）专项：库存分段、Redis 预扣+异步落库。

**【面试官】** 主从延迟怎么处理？写操作后马上要读怎么办？

**【面试者】** 治理：并行复制（5.7 LOGICAL_CLOCK、8.0 writeset）、半同步保不丢。读策略：写后读强一致走主库（会话标记法）；监控三级：Seconds_Behind_Master、回放速率对比写入速率、relay log 水位。GTID 必开——断线自动找位点。

**【面试官】** 数据被误删了一行，你怎么恢复？

**【面试者】** 体系是"防、备、救"：防——业务账号无 drop/truncate 权限、高危 SQL 平台审批、延迟从库（延迟 1 小时，误删数据还在上面）；备——每日 XtraBackup 物理热备 + binlog 实时归档远端 + **定期恢复演练（没恢复过的备份等于没有备份）**；救——先停写缩小影响面，从最近全量恢复到临时实例，binlog 回放到误删前一秒，按表导回误删数据（不整库覆盖）；小范围误删行用 binlog 逆向补偿 SQL（my2sql 类工具）审核后执行。最后对账+复盘。

**【评注】** ⭐⭐ G8 补漏题。答出"恢复演练"和"延迟从库"就是有真平台的标志；"没恢复过的备份等于没有备份"是总监级金句。

**【面试官】** 单表多大要分库分表？怎么迁？

**【面试者】** 决策树：先榨干单库（索引/读写分离/归档/冷热分离）；真正的瓶颈是写入吞吐和运维操作（DDL/备份）不是查询。分片键选最高频查询条件（user_id）+ 基因法兜底订单维度查询。迁移四步：存量迁移 → 增量双写 → 对账（分区 checksum）→ 切读切写。分布式 ID 用雪花（防时钟回拨）或号段（双 buffer）。

**【面试官】** count(*) 那么慢，怎么办？为什么 InnoDB 不存总行数？

**【面试者】** 因为 MVCC：不同事务看到的行数不同，没法全局缓存。count(*) ≈ count(1) ≥ count(id)，优化器选最小的索引树扫。大表方案：计数表（事务内增减+定期校准）、Redis 展示层容忍误差、explain 估算。危险动作：缓存计数当资金数字——计数与明细要对账。

**【面试官】** 连接池参数你关注哪些？连接泄漏怎么发现？

**【面试者】** HikariCP 四参数：maximumPoolSize（不是越大越好，DB 侧连接数=实例数×池大小；公式起点 CPU×2+磁盘数，压测校准）、connectionTimeout（建议 1~3s 快速失败）、maxLifetime（小于 DB wait_timeout）、**leakDetectionThreshold（借出超阈值打栈——排查泄漏的武器）**。真实事故：事务里调慢 RPC，连接持有 30 秒 × 200 线程打爆 DB——修复是事务瘦身+泄漏检测上线。

**【评注·终局】** 定级 **P7~P8**。亮点：RC 选型量化、误删恢复体系、连接池事故叙事。MySQL 域过。

## 对话要点速记（本章）

1. 追问顺序：B+ 树 → 回表 → 最左前缀 → MVCC → 锁 → 两阶段 → 主从 → 误删 → 分库分表 → count → 连接池。
2. 三个超预期点：RC 选型前提量化、误删"防备救"三层、连接泄漏"日志直接给栈"。
3. 姿态：所有选型都带"前提+收益"——敢不用默认值且能论证，才是真懂。
