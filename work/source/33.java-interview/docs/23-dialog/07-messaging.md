# 对话版 · 第 7 章 消息队列与异步化（二面，约 25 分钟）

**【面试官】** 为什么用 MQ？代价呢？

**【面试者】** 三作用：异步（下单后 5 个下游 300ms→5ms）、解耦（新增订阅方零改动）、削峰。代价主动说：一致性变弱（最终一致）、链路变长（排障难）、多一个要运维的中间件。选型：交易类 RocketMQ（事务消息/延迟/轨迹全）、大数据日志 Kafka（吞吐+流生态）、小流量灵活 RabbitMQ。

**【面试官】** 消息不丢怎么保证？三端说全。

**【面试者】** 发送端：acks=all + retries + 幂等 producer（PID+序列号防 broker 端重复）+ 带回调失败补偿；Broker 端：replication.factor=3 + min.insync.replicas=2 + 禁 unclean 选举；消费端：**先处理完再手动提交 offset**（先提交后处理=丢），重复交给消费幂等。端到端兜底：对账平台定时核对上游与下游结果——技术不丢≠业务不丢。

**【面试官】** 消费重复怎么处理？

**【面试者】** 重复是常态（至少一次语义+rebalance），幂等四法：唯一键约束（消息 ID 落库 unique index，最硬）、状态机（订单状态单向流转，重复消息无效）、乐观锁版本号、Redis 去重表（弱，需 DB 兜底）。**幂等是消费端义务，不是 MQ 的能力。**

**【面试官】** 事务消息的原理？和本地消息表怎么选？

**【面试者】** 半消息（对消费者不可见）→ 执行本地事务 → commit/rollback → 超时未确认 broker **回查**生产者的本地事务状态。本质是 2PC+回查。选型：有基建选事务消息（代码侵入小），快速落地选本地消息表（一张表+扫表投递，强依赖业务库但简单可控）。边界要主动说：事务消息只保证"本地事务+消息到达"，**不保证消费成功**——下游失败靠重试+死信+人工，整条链路是 SAGA。

**【评注】** ✅ 主动划边界是二面关键动作——候选人不画大饼，面试官信任度上升。

**【面试官】** 顺序消息怎么实现？值得全局顺序吗？

**【面试者】** 同 key（订单号）哈希到同分区 → 分区内天然有序 → 消费端单线程（多线程要按 key 二次哈希到内存队列）。RocketMQ 用 MessageQueueSelector + MessageListenerOrderly（队列级锁）。**默认不追求顺序**：顺序的成本是热分区、消费并行度锁死、失败重试阻塞队列——用幂等+状态机把乱序变成可重放，只在账务等"非它不可"场景局部启用。

**【面试官】** rebalance 频繁怎么办？

**【面试者】** 头号诱因：处理耗时超 max.poll.interval.ms（默认 5 分钟）→ 调小 max.poll.records、异步化耗时逻辑；升级 CooperativeStickyAssignor（增量 rebalance）；消费幂等兜底重复。积压应急 SOP：定性（消费慢还是生产突增）→ 扩容消费者至≤分区数 → 批量+按 key 多线程 → 极端转储后重置 offset，事后补数。

**【面试官】** Kafka 为什么快？分区数怎么定？

**【面试者】** 五因：顺序写（追加日志）、Page Cache（不自己管堆内存）、zero-copy（sendfile）、批量+压缩、分区并行。分区数 = 目标吞吐 ÷ 单分区吞吐（经验 10~50MB/s），预留余量；**只能增不能减**。陷阱知识：分区过多性能反而降（文件句柄+fetcher+页缓存碎片化），KRaft 替代 ZooKeeper 解决元数据瓶颈。

**【面试官】** 消息积压 500 万条，应急？

**【面试者】** 定性：消费慢（栈阻塞/下游故障）还是生产突增；消费慢先修复慢点，再按速率估算消化时间；扩容到分区数上限；批量化+按 key 多线程（不破坏顺序语义）；极端转储到表后重置 offset 补数。**积压告警阈值按"消化完积压的时间"动态算**，不是固定条数。

**【面试官】** 最后：MQ 用法上你踩过什么坑？

**【面试者】** 三条真实反模式：① 同步链路等消费结果（发完立即查下游查不到）——MQ 是最终一致别当同步 RPC；② 消息当数据库用（全量大 JSON 塞消息）——消息只传事件，数据以存储为准；③ Topic 大杂烩——topic 是隔离单位也是运维单位。防复发：MQ 使用规范 + 死信告警 SOP + 全链路 traceId。

**【评注·终局】** 定级 **P7**。亮点：EOS 边界、顺序成本清单、反模式带真实事故语气。MQ 域过。

## 对话要点速记（本章）

1. 追问顺序：三作用→选型→不丢三端→幂等→事务消息→顺序→rebalance→Kafka 性能→积压→反模式。
2. 三个超预期点：事务消息边界主动划、顺序成本清单、积压动态阈值。
3. 关键姿态：承认"至少一次+幂等"的工程本质，不吹 exactly-once。
