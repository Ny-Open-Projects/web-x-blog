# 对话版 · 第 6 章 Redis 与缓存体系（二面/三面，约 25 分钟）

**【面试官】** Redis 为什么快？数据结构说说？

**【面试者】** 四因：内存、IO 多路复用（epoll）、单线程无锁无切换、专用数据结构。五大类型到场景：String 缓存/计数、Hash 对象、List 最新动态、Set 去重/抽奖、ZSet 排行榜（跳表+字典双结构）。扩展：BitMap 签到、HyperLogLog UV（0.81% 误差 12KB）、GEO 附近的人、Stream 消息队列。

**【面试官】** 持久化 RDB 和 AOF 怎么选？

**【面试者】** RDB 快照恢复快、丢两次快照间数据；AOF everysec 最多丢 1 秒；**4.0+ 混合持久化是默认推荐**（重写时基础 RDF + 增量 AOF）。fork 有卡顿风险（内存越大越明显，看 latest_fork_usec），单实例控制在 10G 内。纯缓存可以关持久化，有数据态必须持久化+哨兵。

**【面试官】** 缓存穿透、击穿、雪崩——分别怎么解决？统一视角是什么？

**【面试者】** 穿透（查不存在）挡：布隆过滤器前置+空值短 TTL；击穿（热点过期瞬间打穿）合：单飞互斥重建或逻辑过期；雪崩（大量同时过期/Redis 挂）抖：TTL 加随机+多级缓存+限流降级。统一视角：**三大问题本质都是"回源流量治理"——前置挡、收敛合并、缓冲削峰、兜底降级**。

**【面试官】** 缓存和数据库一致性，你们的方案？

**【面试者】** 标准答案：先更新 DB 再删缓存（Cache Aside），**binlog 异步删兜底**（Canal 订阅，与业务解耦、天然覆盖主从延迟），所有缓存配 TTL 做最终一致的最后防线。走过弯路：延迟双删在延迟队列积压时脏窗口拉长，后来迁到 Canal 方案。前提共识要说出来：双写不可能强一致，方案选型是"按业务容忍度收敛到秒级"。

**【面试官】** 分布式锁怎么实现？RedLock 你怎么看？

**【面试者】** 单实例：SET NX PX + 唯一 value + Lua 原子释放 + 看门狗续期（Redisson）。RedLock 争议要会说：Martin 指出 GC 停顿/时钟跳变下失效、缺 fencing token；antirez 反驳依赖时钟单调。**工程结论：RedLock 复杂且未达真正共识，锁要分级——效率锁（缓存重建）用 Redisson，正确性锁（资金）用 DB 乐观锁兜底**。正确性从来不依赖锁本身。

**【面试官】** 哨兵和 Cluster 怎么选？Cluster 扩容怎么做？

**【面试者】** 数据量 <50G 哨兵+主从足够；要水平扩展上 Cluster（16384 slot）。哨兵四步选从：replica-priority → offset 最大 → runid 最小；脑裂用 min-replicas 防护。Cluster 扩容：cluster meet → 按槽迁移 → MIGRATING/IMPORTING + ASK 重定向——**大 key 是迁移前置工程**（MIGRATE 同步阻塞源节点）。

**【面试官】** 热 key 和大 key 分别怎么治理？

**【面试者】** 热 key（单 key QPS 打爆单分片）：本地缓存兜底 + key 打散加后缀 + 预热，发现靠客户端埋点/--hotkeys；**热 key 是预测出来的，不是故障时发现的**。大 key（string>10KB、集合>5000）：拆分分桶、压缩、UNLINK 异步删、巡检门禁；大 key 还是 Cluster 迁移的雷。

**【面试官】** 没有 MQ 的话，Redis 怎么做延迟队列？

**【面试者】** ZSet 方案：score 存执行时间戳，消费端 ZRANGEBYSCORE 0 now LIMIT n → **ZREM 原子竞争**（Lua 封装"取+删"，多消费者只有一个成功）→ 成功后写任务表再执行，崩溃扫表补偿。缺点主动说：轮询空转、无 Ack（需任务表补偿）、无背压——**有 MQ 就别用 Redis 做延迟队列**。pipeline 补一句：攒批省 RTT 但不保证原子，原子需求用 Lua。

**【评注】** ⭐ G11 补漏题。"有 MQ 就别用 Redis 做延迟队列"这种边界结论比方案本身值钱。

**【面试官】** 内存满了淘汰策略怎么配？碎片呢？

**【面试者】** 淘汰必配 allkeys-lru 或 allkeys-lfu（绝留 noeviction）。碎片看 mem_fragmentation_ratio：>1.5 碎片化开 activedefrag（4.0+ 在线整理）；**<1 更危险——数据被换到 swap 了**。三条曲线分流：碎片→defrag、swap→迁容量、无界增长→大 key 巡检。

**【面试官】** 6.0 的多线程 IO 你了解吗？

**【面试者】** 网络读写多线程化（io-threads），**命令执行仍单线程**——保留免锁模型与延迟确定性；且**默认关闭**（io-threads=1），大吞吐场景显式开启才有收益。7.0 还有 Multi-Part AOF（重写不再双写丢数据）、Function（托管 Lua）、Sharded Pub/Sub（广播收窄到 slot）——版本演进主线是"编码简化→IO 并行化"。

**【评注·终局】** 定级 **P7~P8**。亮点：回源流量治理统一视角、锁分级、ZSet 延迟队列边界结论、版本演进主线。Redis 域过。

## 对话要点速记（本章）

1. 追问顺序：快因 → 持久化 → 三大问题 → 一致性 → 锁与 RedLock → 哨兵/Cluster → 热大 key → 延迟队列 → 淘汰碎片 → 版本演进。
2. 四个超预期点：回源治理统一视角、RedLock 边界结论、"有 MQ 别用 Redis 延迟队列"、演进主线归纳。
3. 所有结论都带"成本/边界"——Redis 题最容易答成名词堆砌，带边界的才是实战派。
