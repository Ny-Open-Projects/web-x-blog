## 7.1 零基础起步

### 卡片 1：MQ 解决什么问题？
三大作用（必背）：
1. **异步**：下单后同步调用 5 个下游 300ms → 发一条消息 5ms，主链路 RT 降一个数量级；
2. **解耦**：生产者不需要知道消费者是谁，新增订阅方零改动（开闭原则在系统间落地）；
3. **削峰**：突发流量先进队列，消费端按自身能力匀速处理（漏斗思想）。
代价（P10 必提）：**一致性变弱（最终一致）、链路变长（排障变难）、多一个要运维的中间件**。

### 卡片 2：三种投递语义
- **At most once**：最多一次，可能丢（先发后处理）；
- **At least once**：至少一次，可能重（先处理后确认，**主流选择**）；
- **Exactly once**：恰好一次，需要端到端幂等或事务支持（Kafka 事务仅限 Kafka 内部流处理）。
记忆口诀：**"至少一次 + 消费幂等" = 工程上的"恰好一次"**。

### 卡片 3：为什么消费要幂等？
网络抖动/重平衡/超时都会导致重复投递，这不是可以消灭的异常，而是常态。幂等四法：
1. **唯一键约束**：消息 ID 落库 unique index（最硬）；
2. **状态机**：订单状态只能单向流转，重复消息更新无效；
3. **版本号/乐观锁**：更新带 version 条件；
4. **Redis setnx 去重表**（弱，Redis 丢失会重，需 DB 兜底）。

### 卡片 4：选型一句话
- **Kafka**：吞吐王者、日志/流处理生态（Kafka Streams/Flink 对接）；弱在延迟消息、事务消息、消息查询。
- **RocketMQ**：业务特性全（事务消息、延迟/定时、消息轨迹、顺序消息），阿里系电商标配。
- **RabbitMQ**：路由灵活、低延迟小流量、管理界面友好；吞吐低于前两者。
- **Pulsar**：存算分离、多租户，新锐但生态弱。
**结论**：电商交易类选 RocketMQ，大数据日志流选 Kafka，没有绝对优劣。

## 7.2 入门题（P4-P6）

### 题 7.2.1：Kafka 的架构与核心概念？为什么快？

**【参考回答（可背）】**
概念：Producer → Topic（逻辑分类）→ Partition（物理分片，顺序追加日志）→ Consumer Group（组内每个分区只被一个消费者消费）→ Offset（消费位移，存内部 topic __consumer_offsets）。
**为什么快（必背 5 条）**：
1. **顺序写**：分区日志追加写磁盘，顺序 IO 接近内存速度；
2. **Page Cache**：读写都走 OS 缓存，不自己管堆内存（避免 JVM GC 抖动）；
3. **Zero-copy**：sendfile 系统调用，数据从页缓存直达网卡，跳过用户态两次拷贝；
4. **批量 + 压缩**：producer 攒批（linger.ms/batch.size）+ snappy/gzip/lz4；
5. **分区并行**：水平扩展的单位。

**【追问链】**
1. 分区数怎么定？→ 目标吞吐 ÷ 单分区吞吐（经验 10MB/s~50MB/s），预留扩容余量；**分区只能增不能减**（减少会破坏 offset 映射）。
2. 消息怎么保证按 key 有序？→ 同 key 哈希到同分区，分区内有序；全局有序 = 单分区（牺牲并行）。

**【P10 加分项】**
解释"为什么 Kafka 分区多了性能反而下降"：每个分区对应文件句柄、rebuild 元数据、fetcher 线程，页缓存碎片化；KIP-500（KRaft 替代 ZooKeeper）消除元数据瓶颈——说明你跟进了版本演进（Kafka 3.x 已生产 KRaft）。

### 题 7.2.2：Kafka 怎么保证消息不丢？（三端保障，必背矩阵）

**【参考回答（可背）】**
1. **生产端**：
   - `acks=all`（leader + 所有 ISR 副本确认）；
   - `retries=Integer.MAX_VALUE` + 幂等 producer（enable.idempotence=true，PID + 序列号防 broker 端重复）；
   - 发送用带回调的异步 API，失败记录补偿（本地消息表）；
   - 不要用 fire-and-forget。
2. **Broker 端**：
   - `replication.factor >= 3`；
   - `min.insync.replicas >= 2`（ISR 不足 2 拒写，牺牲可用性保一致——CAP 取舍）；
   - 禁 unclean.leader.election（不允许落后副本当 leader）。
3. **消费端**：
   - **先处理完再手动提交 offset**（enable.auto.commit=false），重复消费交给幂等；
   - 千万不要"先提交后处理"。
一句话总结：**发送端确认 + 多副本持久化 + 消费后提交 + 全链路幂等。**

**【追问链】**
1. ISR 是什么？→ 与 leader 保持同步的副本集合（replica.lag.time.max.ms 内追上）；ISR 收缩过多时 acks=all 会写入失败——可用性与一致性的旋钮。
2. HW 与 LEO？→ LEO 每副本日志末端；HW = ISR 中最小 LEO，消费者只能读到 HW 之前，防止读到未确认数据。

**【P10 加分项】**
端到端视角：技术不丢 ≠ 业务不丢——消费失败进死信、人工干预流程、**对账平台**（上游订单 vs 下游处理结果定时核对）才是最终兜底。"MQ 的可靠性 SLA 要写进与业务方的契约"。

### 题 7.2.3：RocketMQ 的事务消息原理？

**【参考回答（可背）】**
解决"本地事务与发消息的原子性"：
1. 生产者发**半消息**（half message，对消费者不可见），broker 持久化；
2. 执行本地事务；
3. 根据结果提交/回滚半消息（commit → 消息可见；rollback → 删除）；
4. 若 broker 长时间没收到二次确认 → **回查**：回调生产者的 checkLocalTransaction（查本地事务状态表/流水）决定提交或回滚。
本质：**2PC + 事务状态回查**，把"先发消息还是先落库"的两难用最终一致化解。

**【追问链】**
1. 和本地消息表方案的取舍？→ 本地消息表：业务库一张表 + 定时扫表投递，实现简单、强依赖业务库；事务消息：MQ 侧封装、代码侵入小，但依赖 broker 回查实现质量。团队有基建选事务消息，快速落地选消息表。
2. 消费端失败怎么办？→ 重试队列（16 次梯度退避）→ 死信队列（DLQ）→ 人工/自动处理 + 告警。

**【P10 加分项】**
指出事务消息边界：只保证"本地事务 + 消息到达"原子，**不保证消费成功**——下游失败要靠重试+死信+人工兜底，整条链路是 SAGA 思想。能画出完整时序图（生产者/broker/消费者三泳道）的候选人在此题直接封顶。

---

### 题 7.2.4：消费者怎么避免重复消费？rebalance 是什么？有什么问题？

**【参考回答（可背）】**
重复消费根源：offset 提交时机（处理完未提交就宕机/被踢）+ 至少一次语义 → **幂等是唯一正解**（见卡片 3）。
Rebalance（再均衡）：消费者组内成员变化（上下线、心跳超时、分区数变化）时重新分配分区。
问题（必背）：rebalance 期间 **Stop-The-World**，全组暂停消费 → 长时间空转、重复消费风暴。
治理：
1. 心跳参数调优（session.timeout.ms / max.poll.interval.ms：**处理耗时超 max.poll.interval 是 rebalance 头号诱因**，max.poll.records 调小单次拉取量）；
2. StickyAssignor / CooperativeSticky（增量 rebalance，尽量保留原分配，Kafka 2.4+）；
3. 消费逻辑幂等兜底。

**【P10 加分项】**
讲"消息积压应急 SOP"：定位（是消费慢还是生产突增）→ 扩容（分区数与消费者数匹配，消费者数 ≤ 分区数；无法扩分区就批量+多线程处理单分区内消息）→ 降级（跳过非关键消息先记日志后补偿）→ 复盘（积压告警阈值、容量规划）。

## 7.3 进阶题（P7-P8）

### 题 7.3.1：顺序消息怎么实现？乱序会出什么问题？

**【参考回答（可背）】**
需求场景：同一订单的 创建→支付→发货 必须按序。
Kafka 方案：同 key（订单号）→ 同分区 → 分区内顺序 → **单分区内消费还要单线程**（多线程消费破坏顺序，要按 key 二次哈希到内存队列再串行）。
RocketMQ：MessageQueueSelector 自定义选队列 + 顺序消费模式（MessageListenerOrderly，队列级锁）。
乱序的典型事故：先收到"支付成功"后收到"订单创建"（重试导致），状态机直接拒绝乱序消息 + 告警——**状态机是顺序的最后防线**。

**【追问链】**
1. 顺序与吞吐的矛盾？→ 分区数决定并行度，key 分布倾斜会造成热分区；热点订单拆子序号或接受局部无序+状态机兜底。
2. 全局顺序值得吗？→ 几乎不值得（单分区 = 单点+低吞吐），业务上几乎总能找到 key 维度。

**【P10 加分项】**
"顺序性成本清单"：热分区风险、消费并行度锁死、失败重试会阻塞后续（顺序消费模式下重试是卡队列的）——所以**默认不追求顺序，用幂等+状态机把乱序变成可重放**，这是反直觉但正确的工程判断。

---

### 题 7.3.2：延迟消息/定时消息的实现与场景？

**【参考回答（可背）】**
场景：订单 30 分钟未支付自动取消、定时开售、重试退避。
- **RocketMQ 5.0**：任意精度定时（timer wheel 时间轮，消息先入定时主题，到点转投目标主题）；4.x 只有 18 个固定等级（1s/5s/10s/30s/1m...），业务适配等级。
- **Kafka**：原生不支持；变通：① 应用层延迟队列（时间轮 + DB/Redis 扫描）② 多 topic 分延迟档 + 定时任务转投 ③ 直接用调度系统（xxl-job/SchedulerX）扫表。
- 自研方案（面试常考设计）：**时间轮（HashedWheelTimer）+ 持久化任务表**：任务落库（防丢）+ 时间轮内存调度 + 扫描补偿——Netty 时间轮是理论基础。

**【P10 加分项】**
"扫码关单"的量级问题：亿级订单的延迟取消不能用 DB 扫全表——分片扫描（按订单号分桶）+ 延迟消息精准触发（订单创建时发 30min 延迟消息，取消前二次确认支付状态）。两种方案的成本对比展示方案深度。

## 7.4 压轴题（P9-P10）

### 题 7.4.1：设计大促秒杀的消息链路（与第 9 章联动）

**【参考回答（框架可背）】**
1. **前置过滤**：静态资源 CDN、按钮防重、风控限流（网关层把 100 万 QPS 压到 1 万）；
2. **库存预扣**：Redis lua 原子扣减（防超卖），扣成功才进 MQ——**MQ 不是第一道闸，Redis 才是**；
3. **异步下单**：下单消息进 RocketMQ（削峰），消费端按 DB 能力拉取（消费者限速），DB 行锁扣真实库存 + 创建订单同事务；
4. **失败闭环**：消费失败重试 → 死信 → 自动回补 Redis 库存（**回补幂等：以订单维度记录已回补标记**）；
5. **用户体验**：排队中状态轮询（前端轮询订单状态接口，结果落 Redis）；
6. **兜底**：MQ 积压监控、Redis 预扣与 DB 实扣差异对账、活动结束二次对账。
量化示例：10 万库存、100 万请求 → Redis 扛 100 万 QPS → MQ 消费速率设为 DB 可承受的 5000 TPS → 20 秒内售罄。

**【追问链】**
1. Redis 预扣和 DB 实扣不一致怎么办？→ 以 DB 为准做对账；预扣是"资格闸门"不是账本，差异通过回补与对账收敛。
2. 为什么不用 DB 直接扛？→ 行锁串行化，100 万并发扣同一行 = 连接池爆炸与锁等待雪崩；MQ 把"并发扣减"转成"排队扣减"。

**【P10 加分项】**
"削峰的度"：削峰不是无限延迟——用户等待超过 30s 就流失，所以**限速值 = 业务可接受的最大售罄时间**推导而来。把技术参数翻译成业务指标（售罄时间、转化率），是 P10 的语言。

---

### 题 7.4.2：MQ 用法反模式清单（你们踩过哪些坑？）

**【参考回答（背 6 条 + 各配一个坑故事）】**
1. **同步链路里等消费结果**：发消息后立即查下游数据 → 查不到（还没消费）→ 改同步 RPC 或状态轮询；MQ 是最终一致，别当同步调用用。
2. **消息当数据库用**：把大 JSON 全量塞消息做存储 → 消息积压=数据丢失风险、重放不可控 → 消息只传"发生了什么"（事件），数据以存储为准。
3. **无幂等消费**：重复消费造成重复发货 → 唯一键/状态机，幂等是消费端义务。
4. **广播当集群用（或反之）**：Kafka 组内竞争、RocketMQ 广播模式每实例都收——语义弄反直接事故。
5. **Topic 大杂烩**：一个 topic 承载 N 种业务消息，消费端解析所有 → 拆分 topic 或消息体带类型+过滤；topic 是隔离单位也是运维单位。
6. **无死信处理**：失败消息堆重试队列无人管 → DLQ 必须有告警与处理 SOP，死信不是垃圾桶。
7. （加分）**链路追踪缺失**：消息体带 traceId + 消息轨迹平台，否则跨系统排障是大海捞针。

**【P10 加分项】**
上升为治理：MQ 使用规范（命名、topic 治理、消息体 Schema 演进与兼容性、消费 SLA 分级）+ 平台化（消息轨迹、积压看板、一键限速）。"中间件治理"叙事是 P9→P10 的分水岭。

## 7.5 本章高频追问链图谱

```
三大作用 ──→ 代价（一致性/排障） ──→ 选型矩阵
不丢 ──→ acks=all/ISR ──→ min.insync.replicas ──→ 手动提交 ──→ 幂等 ──→ 对账兜底
不重 ──→ 幂等四法 ──→ 状态机 ──→ 唯一键
rebalance ──→ max.poll.interval ──→ CooperativeSticky ──→ 积压 SOP
事务消息 ──→ 半消息+回查 ──→ 本地消息表对比 ──→ SAGA
顺序 ──→ key→分区 ──→ 状态机兜底 ──→ "默认不追求顺序"
```

## 7.6 一页速记卡

1. MQ 三作用：异步、解耦、削峰；代价：最终一致+排障链长。
2. 语义：至少一次 + 消费幂等 = 工程上的恰好一次。
3. 不丢三端：发送确认（acks=all+幂等 producer）、broker（3 副本+minISR=2）、消费（先处理后手动提交）。
4. Kafka 快五因：顺序写、Page Cache、zero-copy、批量压缩、分区并行。
5. rebalance 头号诱因：处理时间超 max.poll.interval.ms。
6. 事务消息 = 半消息 + 本地事务 + 回查；只保证发送侧原子。
7. 顺序消息：key 同分区 + 状态机兜底；默认不追求全局顺序。
8. 延迟消息：RocketMQ 时间轮；Kafka 需自建；任务表防丢。
9. 幂等四法：唯一键、状态机、版本号、去重表。
10. 死信队列必须有告警与 SOP；消息带 traceId。

## 7.7 增补题（v1.1 深度扩充）

### 题 7.7.1：Kafka 的 HW/LEO 与 min.insync.replicas 的可用性代价？

**【面试官意图】** 检验你对副本一致性机制的量化理解，而不是背 ISR 名词。
**【参考回答（可背）】** LEO 是各副本日志末端位移；HW 是 ISR 中最小 LEO，消费者只能读到 HW 之前——保证读到的都是"已被多数派确认"的。min.insync.replicas=2 与 acks=all 组合意味着 ISR 少于 2 个副本时写入直接失败（NotEnoughReplicasException）：**用可用性换一致性**，这是 CAP 取舍在 Kafka 的具体落点。副本失效判定靠 replica.lag.time.max.ms（默认 10s 追不上即踢出 ISR）。
**【追问链】** ① HW 截断与数据丢失窗口？（leader 崩溃前 follower 已复制但未提交部分会被截断，unclean 选举禁止后此风险收敛到 minISR 内）② 为什么不能无限调大 minISR？（副本抖动时集群大面积写入失败，一般是 2 of 3）。
**【P10 加分项】** 给出容量规划公式：minISR=⌊replicas/2⌋+1，并说明"3 副本 + minISR=2"能容忍 1 副本故障；再讲 KRaft 元数据替代 ZooKeeper 后，元数据一致性由 Raft 保证，分区扩容速度大幅提升——跟版本演进的人在这里明显高一档。

### 题 7.7.2：RocketMQ 顺序消息的锁机制？热点队列怎么办？

**【参考回答（可背）】** RocketMQ 顺序消费 = 队列级锁（Broker 端分布式锁 + 消费端 ProcessQueue 锁）：MessageQueueSelector 按 key（如订单号）选队列，保证同 key 消息同队列；消费端用 MessageListenerOrderly，先拿队列锁再消费，单队列内串行。热点 key（大商户订单全进一个队列）会拖垮并行度。
**【追问链】** ① 顺序消息的失败重试会阻塞后续消息吗？（会，顺序消费模式下重试是原地卡队列的，必须配死信与超时阈值）② 怎么拆热点？（订单拆子序号并行消费 + 状态机兜底乱序；或按时间片换队列）。
**【P10 加分项】** 反直觉结论："默认不追求顺序，用幂等+状态机把乱序变成可重放"，顺序只在'非它不可'时局部启用（如账务流水）——讲顺序的成本清单（并行度锁死、重试阻塞、热分区）。

### 题 7.7.3：消息轨迹与跨系统排障怎么做？

**【参考回答（可背）】** 三层设计：① 消息体携带 traceId/messageId/业务键，生产者生成；② Broker 端开启消息轨迹（RocketMQ trace-topic 或独立轨迹存储），记录"谁发的、到哪了、谁消费的、结果如何"；③ 消费端把 traceId 写入日志与 APM span，让 MQ 跳转在链路图上可视。
**【追问链】** ① 轨迹消息量大怎么办？（采样：错误消息全量、正常消息 1% 采样）② 生产者发失败没有轨迹怎么办？（本地消息表就是最原始的轨迹）。
**【P10 加分项】** 讲"消息契约"治理：消息体 schema 版本化管理、向后兼容（只加不改）、消费端按版本路由；再补一键限速/一键禁投的平台化运维能力。

### 题 7.7.4：几万个 Topic 的集群会有什么问题？怎么治理？

**【参考回答（可背）】** Topic/分区数膨胀带来：① 元数据与 rebalance 压力（Kafka 每个 partition 对应文件句柄与 fetcher，数万分区时 controller 与 GC 明显恶化）；② 页缓存碎片化（顺序性被打散）；③ 运维失控（没人知道哪个 topic 没人用了）。治理三板斧：生命周期管理（建 topic 走审批+默认配置）、僵尸 topic 下线（按流量报表定期回收）、单 topic 分区数上限与规范。
**【追问链】** ① 怎么找到僵尸 topic？（生产速率+消费速率双指标连续 30 天为零）② KRaft 改善了什么？（元数据从 ZK 迁到 Raft 内嵌控制器，controller 扩展性提升）。
**【P10 加分项】** 提"topic 是隔离单位也是成本单位"——跨业务复用 topic 的诱惑与代价（一个慢消费者拖垮整 topic 的保留期），最终给出"按业务域建 topic、按一致性要求定acks"的团队规范。

### 题 7.7.5：消息积压 500 万条，应急 SOP 完整版？

**【参考回答（可背）】** 五步：① 定性：消费慢（栈阻塞/下游故障）还是生产突增（上游 bug/活动）——看消费 RT 曲线与生产曲线；② 若消费慢：先查是否有慢消费者（死循环/外呼超时），修复后按当前速率估算消化时间；③ 扩容：加消费者实例至 ≤ 分区数（分区不够先加分区，注意对 key 顺序的破坏）；④ 改造：单分区内批量拉取+按 key 哈希到内存队列多线程（并行度=CPU 数），不动顺序语义；⑤ 极端情况：跳过策略——非关键消息转储（快照到表）后重置 offset，事后补数。
**【追问链】** ① 重置 offset 怎么保证不丢业务？（先全量转储到宽表再重置，转储即"消息不丢"的补偿语义）② 积压告警阈值怎么定？（按"当前消费速率消化完积压的时间"动态计算，而非固定条数）。
**【P10 加分项】** 把 SOP 沉淀为值班手册：积压平台化看板（按 topic 分级）、一键扩容/限速/重置的审批链路——"应急操作平台化"是 P10 对事故复盘的终态。

### 题 7.7.6：Exactly-Once 端到端的真实边界在哪？

**【参考回答（可背）】** Kafka 事务+幂等 producer 只保证 **Kafka 内部**（读-处理-写回 Kafka）的恰好一次；一旦写入外部系统（DB/ES），事务不覆盖，必须靠**消费幂等**补齐。流处理（Flink）实现端到端 EOS 靠两阶段提交（预提交+checkpoint 后提交+恢复时重放未提交事务），代价是提交间隔与吞吐。
**【追问链】** ① 幂等 producer 的原理？（PID+分区序号去重，仅防 broker 端重复，不防应用重试导致的多条）② 为什么生产上常直接选"至少一次+幂等"？（EOS 的吞吐与复杂度代价大，而幂等消费通常已实现）。
**【P10 加分项】** 一句话哲学："分布式系统的 EOS 是'由哪个组件买单'的问题——Kafka 买单则限制在内部，你的业务买单则用幂等。没有免费恰好一次。"
