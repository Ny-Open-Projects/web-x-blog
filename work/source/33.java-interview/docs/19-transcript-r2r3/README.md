## 上篇：二面实录（项目深挖，压力测试型面试官）

> 二面面试官的风格是"不认可式追问"——每个回答都先质疑再听。这种风格考的不是知识，是**被质疑时的姿态与逻辑稳定性**。

**面试官**：你简历写详情页 P99 从 45ms 降到 8ms。我怎么知道这 8ms 不是你挑了个好时间测的？

**候选人**：三个可信度来源：一是全量监控（Prometheus 按分钟聚合的 P99，不是压测报告），改造前后各 30 天曲线我截过图；二是口径没变——都是网关层计时、同一接口、同一机房；三是可以现场拉给你们看 Grafana。另外说明一下曲线里有两个毛刺：一次是热 key 推送服务重启，一次是 Redis 主从切换，都是已修复的独立事件，不影响趋势结论。

> 【评注】✅✅ 这是"数据可信度"问题的满分答法：来源（全量监控非自证）、口径（防"换测量点"质疑）、可验证（当场拉图）、以及**主动暴露毛刺并归因**——比一张完美曲线可信十倍。面试官"质疑式开场"的真正目的就是看你会不会防御性地否认瑕疵。

**面试官**：binlog 异步删缓存，你说一致性收敛到秒级。我怎么相信是秒级不是十秒？

**候选人**：用日志测的：Canal 消费端打印"收到变更→删缓存完成"的时间戳与 DB 提交时间戳的差值分布，P99 是 800ms、P999 2.3s。但这里有个前提我说清楚：这个秒级是"失效到达"的时间，不是"数据已一致"的时间——本地缓存还有短 TTL 兜底，所以用户视角的脏窗口上限是 TTL（我们设 3 秒）。两个数我都背得出来，因为告警阈值就是按 P999 2.3s 设的。

> 【评注】✅ 妙在两层：① 给的是分布（P99/P999）不是单点数字；② 主动区分"失效到达时间"和"用户可见脏窗口"——两个概念混着答会被立刻抓住。**把告警阈值当作数字的来源**，证明这些数不是背来的。

**面试官**：你说大促时延迟双删的延迟队列积压导致脏窗口拉长。积压了为什么不直接改成强一致读主库？

**候选人**：评估过，两个原因放弃：一是读主库把 QPS 直接怼回 DB，按当时容量 DB 扛不住，等于把一致性问题换成可用性问题；二是脏读的内容是商品标题/图片这类低敏字段，价格和库存走的是独立实时服务不走这条缓存。所以是"损失可容忍字段的一致性，保住不可容忍字段的实时性"——分字段分级而不是一刀切。这个分级决策跟业务方拍过板，有记录。

> 【评注】✅ 面试官抛的是二选一陷阱题（改强一致 or 承认方案差）。候选人用"分字段分级"跳出了二选一，并且第三次主动提"跟业务方拍板有记录"。**三次出现业务共治证据，交叉面评语里"技术方案业务化"的标签就是这么攒出来的。**

**面试官**：你说订单库迁移写了逐行 checksum。5000 万行对一遍要多久？你们多久对一次？停机了吗？

**候选人**：5000 万行按主键分 512 区间并行，每区间 10 万行一次 CRC 聚合，单区间秒级，全量一轮约 40 分钟、压测时跑到 15 分钟。灰度期每天全量一轮 + 准实时增量；切换当夜做最后一次全量（凌晨 2 点业务低峰，40 分钟不影响）。没停机——这正是双写+对账方案对比"停机迁移"的核心优势，当时也是为了不申请停机窗口才选的这条路。

> 【评注】✅ 三个数字（40 分钟/15 分钟/凌晨 2 点）+ 一个架构动机回环（"为什么选这条路"）。所有数字都经得起"怎么算的"追问——**每个数字背后有一个计算公式**，这是对"数字真实性"质疑的终极防御。

**面试官**：OK，项目我认可了。最后一个硬题：如果让你重做这个迁移，你会改哪一步？

**候选人**：会改对账工具的自愈能力。当时发现差异要人工判"是双写 bug 还是补偿队列丢的"，一次差异人工排查半天；重做的话会把对账结果接"自动归因"——按差异类型路由到补偿重放（queue 丢失类自动重发）或告警人工（规则 bug 类），预期能把人工介入从每周几小时压到近零。另外会提前做"迁移演练"——当时只在预发跑过双写，真实流量下的补偿队列行为是生产上第一次见，应该在大促后的流量镜像里先演练一次。

> 【评注】✅ "重做会改什么"是二面终局题，考反思深度。两个答案都属于"机制升级"而非"具体 bug 修补"，并且第二个（演练缺失）是**自我批评**——敢说自己方案的预发验证不充分，这是总监面最爱看的特质。二面结束，评语预写"P9，真实性高"。

## 下篇：三面实录（架构白板，40 分钟）

> 三面只考一道大题加一次中途"变局"——面试官会在你画到一半时追加约束，看你推倒重来的能力。

**面试官**：白板设计：一个面向第三方开发者的开放平台 API 网关。先问我三个澄清问题再动手。

**候选人**：三个问题：① 规模：日调用多少、峰值 QPS、开发者数量级？② 核心诉求排序：限流/鉴权/计量的优先级，以及 SLA 承诺（网关自己挂了第三方全挂，可用性要求是不是最高）？③ 现状：是全新平台还是从网关 + 各业务自建鉴权迁移过来？

**面试官**：日 10 亿调用、峰值 20 万 QPS、开发者 5 万。可用性第一、计量计费第二、限流第三。已有自研网关，这次是把散落的鉴权和计量收进来。

> 【评注】✅ 澄清环节先拿"可用性第一"这个关键约束——后面所有设计都会围绕它，这是三面白板与二面问答最大的差异：**约束先行，方案跟着约束走**。

**候选人**（边画边讲）：整体四层：
1. **接入层**：LVS/SLB + 多机房接入，网关本身无状态水平扩；
2. **网关核心**：过滤器链——鉴权（AppKey/签名校验）→ 风控 → 路由 → 限流 → 转发。异步化架构（WebFlux 或虚拟线程），单实例压测目标 2 万 QPS，20 万 QPS ≈ 100 实例 + 冗余到 150；
3. **控制面**：AppKey/配额/路由规则存 DB，经配置中心推送到网关内存（网关运行时不查 DB——**数据面零 DB 依赖**是可用性第一的直接推论）；
4. **计量链路**：调用日志异步批量落 Kafka → Flink 聚合计费，网关侧只写内存计数器+异步 flush，**计量故障不影响转发**。

**面试官**：（打断）加一个约束：计量计费是收费依据，一分钱都不能差。你这个"异步可能丢"的计量怎么办？

**候选人**：（停顿，改设计）好，这个约束改变了计量架构。拆成两路：**计费路径**用"准实时对账兜底"——网关本地计数器 + 每 5 秒原子快照 flush 到 Kafka，消息带序列号；下游按序列号检测空洞，空洞触发"按天全量重算"（对账任务从网关落盘的原始访问日志二次汇总）。也就是说：**接受计费分钟级误差，用 T+1 精确对账收敛到分毫不差**——实时层求快，对账层求准，两层各司其职。如果连分钟级误差都不接受，那就得在转发路径同步写计量库，20 万 QPS 下这是个 DB 灾难，我会把这个代价明确抛回来请业务决策。

> 【评注】✅✅ 这是三面的决胜题。被追加约束后的处理是满分模板：① 停顿承认约束改变设计；② 给出"实时层+对账层"双层方案并明确各自职责边界；③ **把"同步写计量库"的代价作为选项摆出来请决策**——不擅自把性能灾难吞进设计里。三面评委找的就是这种"把不确定性显式化"的能力。

**面试官**：鉴权签名被重放攻击怎么办？

**候选人**：四要素防重放：时间戳（±5 分钟窗口）+ 随机 nonce + 签名覆盖全部关键参数 + 服务端 nonce 去重（Redis setnx，TTL 5 分钟窗口，window 外靠时间戳直接拒）。补充：HTTPS 是前提但不够——中间人拿到完整请求仍可原样重放，所以 nonce 是必须的而不是可选的。

**面试官**：限流你们按什么维度？第三方 AppKey 恶意刷呢？

**候选人**：三级漏斗：按 AppKey 配额（ contractual 限额，超了按合同降级返回 429）→ 按 IP+AppKey 组合风控（识别一个 AppKey 多 IP 刷量）→ 全局兜底保护网关自身。限流实现用 Redis+Lua 集群配额（每 AppKey 独立 key，无热点），降级到本地配额预估（配额同步容忍分钟级误差）——呼应"可用性第一"：限流组件挂了宁可放过不可全拒。

**面试官**：最后 5 分钟，讲讲这个系统怎么灰度上线。

**候选人**：按"先内部后外部、先只读后收费"三阶段：① 内部业务先接入（背锅的是自己人，问题收敛快）；② 开放只读接口给种子开发者（10 家），计量双轨（新旧计量并行对账）；③ 计量对平后切计费、全量开放。每阶段有回滚开关——网关过滤器链按开关装配，鉴权/计量都可以独立关闭回退到旧链路。上线节奏里最危险的其实是"计量切换"，所以对账双轨期要比正常灰度长一倍。

> 【评注】✅ 灰度收尾再次命中"识别最危险步骤"的 P10 模式。40 分钟里候选人完成了：约束澄清 → 分层设计 → 中途变局重构 → 安全细节 → 灰度收尾，每一步都有可追溯的决策理由。三面评语："具备 P10 白板推演能力，建议通过。"

## 三条实录通读后的自检清单

1. 我的每个数字有没有"计算公式或数据来源"能扛住两层追问？
2. 我有没有至少 3 处"跟业务方拍板/共治"的证据？
3. 被追加约束时，我能否像三面那样"停顿→重构→抛代价请决策"？
4. 我敢不敢在任何一轮里说出"这个我没有一手经验，只能给到机制层"？
5. 收尾灰度方案里，我能不能主动指出"最危险的一步"？

## 速记卡

1. 数据可信度三件套：来源（全量监控）、口径（未变）、可验证（当场拉图）；毛刺主动交代。
2. 数字背后必须有计算公式或告警阈值——分布（P99/P999）优于单点。
3. 二选一陷阱跳出来答：分字段分级、分场景策略。
4. 中途追加约束 = 三面决胜点：停顿 → 重构 → 把代价作为选项抛回请决策。
5. 防重放四要素：时间戳窗口 + nonce 去重 + 全参数签名 + HTTPS（不充分）。
6. 限流降级方向：宁可放过不可全拒（可用性第一的推论）。
7. 灰度收尾必答"最危险的一步"并对它加倍谨慎。
8. "重做会改什么"答机制升级 + 一处自我批评。
