## 6.1 零基础起步

### 卡片 1：Redis 是什么，为什么快？
单线程内存 KV 数据库（6.0 起网络 IO 多线程，**命令执行仍单线程**）。快的原因四条：
1. 纯内存操作；
2. **IO 多路复用**（epoll，单线程处理万级连接）；
3. 单线程无锁竞争、无上下文切换；
4. 高效数据结构（SDS、跳表、压缩列表等专用优化）。

### 卡片 2：五大类型 + 典型场景（必背）
| 类型 | 场景 | 底层编码（简） |
|------|------|----------------|
| String | 缓存、计数器、分布式锁 | SDS（简单动态字符串：O(1) 取长度、二进制安全、预分配） |
| Hash | 对象缓存、购物车 | listpack（小）/ hashtable |
| List | 消息列表、最新动态 | quicklist（双向链表+listpack 节点） |
| Set | 去重、抽奖、共同好友 | intset（全整数小集合）/ hashtable |
| ZSet | 排行榜、延迟队列 | listpack（小）/ **跳表+字典**（一个结构两种索引） |

扩展类型：BitMap（签到）、HyperLogLog（UV 估算，0.81% 误差 12KB）、GEO（附近的人）、Stream（消息队列，消费者组）。

### 卡片 3：跳表为什么替换了 ziplist/平衡树？
- vs 平衡树：实现简单，范围查询同样高效，且按概率分层无需旋转；
- vs B+ 树：内存型，无需页对齐，层数期望 O(log n)；
- 关键点：ZSet 用**跳表（排序范围查询）+ 字典（O(1) 按 member 查 score）**双结构，空间换时间。

### 卡片 4：过期删除与内存淘汰（必背）
- 过期策略：**惰性删除**（访问时检查）+ **定期删除**（周期抽样清理），不用定时器（CPU 太贵）。
- 内存满时 **8 种淘汰策略**：noeviction（默认，写报错）、allkeys-lru / volatile-lru、allkeys-lfu / volatile-lfu（4.0+，适合有冷热分层）、allkeys-random / volatile-random、volatile-ttl。
- **生产必配**：allkeys-lru 或 lfu；绝不留 noeviction。

## 6.2 入门题（P4-P6）

### 题 6.2.1：缓存穿透、击穿、雪崩分别是什么？怎么解决？

**【参考回答（可背，出现率 Top3）】**
1. **穿透**：查**不存在**的数据，缓存和 DB 都没有，每次都打到 DB（可能是恶意攻击）。
   解决：① 缓存空值（短 TTL，如 60s）；② **布隆过滤器**前置（不存在直接拒绝，注意误判率与不可删除，可用 Counting BF/布谷鸟过滤器）；③ 参数校验与风控限流。
2. **击穿**：某个**热点 key 过期瞬间**，大量并发同时打到 DB。
   解决：① **互斥重建**（单飞：分布式锁/本地锁，一个线程查库回填，其他等待）；② 逻辑过期（不设物理 TTL，值里带过期时间，发现过期异步重建，读到旧值但不穿透）；③ 热点 key 永不过期 + 消息刷新。
3. **雪崩**：**大量 key 同时过期**或 Redis 整体不可用，流量全砸 DB。
   解决：① TTL 加随机抖动（错峰）；② 多级缓存（本地 Caffeine 兜底）；③ 限流降级（Sentinel 对 DB 保护）；④ Redis 高可用（哨兵/Cluster）；⑤ 大促前预热。

**【追问链】**
1. 布隆过滤器原理？→ bit 数组 + k 个哈希，插入置位、查询查位；**有误判（说存在可能不存在）但无漏判（说不存在必不存在）**，误判率与位数组大小/哈希数相关，不支持删除（删除用计数布隆）。
2. 逻辑过期的缺点？→ 短暂返回旧数据（业务要容忍）；重建线程管理复杂。

**【P10 加分项】**
指出三大问题的统一视角："**缓存与 DB 之间的'回源流量'治理**"——本质是保护回源路径：前置挡（布隆/空值）、收敛（单飞合并）、缓冲（队列削峰）、兜底（本地缓存+降级开关）。能把三个名词归纳成一个模型，是架构思维的信号。

### 题 6.2.2：缓存与数据库一致性怎么保证？先删缓存还是先更新库？

**【参考回答（可背，本晶标准答案矩阵）】**
前提共识：**缓存与 DB 双写不可能强一致**（无分布式事务），方案矩阵按一致性强度排列：
1. **Cache Aside（旁路缓存，默认推荐）**：读 → 先缓存后 DB 并回填；写 → **先更新 DB，再删缓存**（不是更新缓存）。
   - 为什么删而不是更新缓存？→ 并发写会乱序覆盖、懒加载避免冷数据写放大；
   - 为什么先库后删？→ 先删后写：写库期间读请求把旧值回填，脏数据长期留存；先写后删的脏窗窗口极短（删除失败才留脏）。
2. **延迟双删**：写库后删一次，延迟几百 ms 再删一次（覆盖"删后读旧值回填"的窗口）；延迟时间 = 主从同步耗时 + 一次读耗时，工程上靠压测定。
3. **订阅 binlog 异步删除（推荐进阶）**：Canal/Flink CDC 订阅 binlog → 删除/更新缓存；解耦业务代码，天然覆盖主从延迟（消费从库 binlog 完成后再删）。
4. **强一致需求**：加分布式锁串行化读写（性能大跌），或干脆**不用缓存直读 DB**——承认缓存不适合。
兜底：**所有方案都配 TTL**（最终一致的最后防线）+ 对比校验任务。

**【追问链】**
1. 删除失败怎么办？→ 重试队列（MQ 异步重试）+ binlog 方案天然重投。
2. 为什么不用"更新缓存"？→ ① 并发写覆盖（A 后写先到）；② 计算型缓存每次写都算浪费；③ 写多读少时缓存被反复写却没人读。
3. Read-Through/Write-Through/Write-Behind？→ 读穿透（缓存层自己回源，业务无感）、写穿透（同步双写）、Write-Behind（异步批量落库，快但可能丢——适合计数类）。

**【P10 加分项】**
真实复盘："我们商品详情最初用延迟双删，大促时延迟队列积压导致脏数据窗口拉长到分钟级；后迁移到 Canal 订阅 binlog 删除方案 + 本地 Caffeine 二级缓存，一致性收敛到秒级且与业务代码解耦。"——方案演进叙事是最高级回答。

### 题 6.2.3：Redis 持久化 RDB 和 AOF 怎么选？

**【参考回答（可背）】**
- **RDB**：定时快照（save/bgsave），**fork 子进程**写临时文件后原子替换。优点：文件小恢复快；缺点：两次快照间的数据会丢，fork 瞬间可能卡顿（内存越大越明显，COW 写时复制）。
- **AOF**：追加写命令日志。三种刷盘：always（每命令 fsync，最安全最慢）、**everysec（默认，最多丢 1 秒）**、no（交给 OS）。重写（bgrewriteaof）压缩体积（合并为最终数据集的写命令）。
- **4.0+ 混合持久化（推荐）**：重写时基础部分 RDF 格式 + 增量 AOF，恢复快且丢得少。
- 选型：纯缓存可以关持久化；有数据态（如分布式锁、计数）必须持久化 + 哨兵/Cluster 故障转移。

**【追问链】**
1. fork 卡顿怎么办？→ 大实例（10G+）监控 latest_fork_usec；控制单实例内存（建议 <10G）；物理机开大页禁用（THP off，反而 Redis 要禁 THP 否则 COW 放大内存）。
2. AOF 重写期间新命令怎么办？→ 重写缓冲区追加，写完后追加重写文件。

**【P10 加分项】**
容量与实例治理：单实例内存上限的工程共识（10~20G 内便于恢复/迁移/fork）、热 key 与大 key 排查（--bigkeys、rdb 分析工具 redis-rdb-cli）、大 key 治理（拆分、压缩、异步删除 unlink/ lazy free）。

### 题 6.2.4：Redis 分布式锁怎么实现？RedLock 有争议？

**【参考回答（可背）】**
**单实例正确姿势（必背）**：
```
SET lock_key unique_value NX PX 30000
```
- NX 互斥、PX 过期防死锁、**value 存唯一值（UUID+线程 ID）**用于安全释放；
- 释放用 **Lua 脚本**原子校验 value 再删（防删别人的锁）；
- 业务超时风险：锁过期但业务没执行完 → **看门狗**（Redisson watchdog：持锁线程定期续期，默认锁 30s 每 10s 续）。
- Redisson 实现：Lua + hash 结构（记录持有者与重入次数，支持可重入）+ Pub/Sub 唤醒等待者。

**RedLock 争议（P10 必聊）**：向 N 个独立主节点依次加锁，多数派成功才算获取。Martin Kleppmann 批评：GC 停顿/时钟跳变下锁语义失效，且没解决 fencing token（令牌递增校验）；antirez 反驳依赖时钟单调与正确实现。**工程结论：RedLock 复杂且未达真正共识，要么接受单实例+看门狗的"效率锁"语义，要么用支持 fencing 的方案（ZK 顺序节点/etcd lease + 版本校验）。关键资源（资金）不依赖"效率锁"，用 DB 乐观锁兜底。**

**【追问链】**
1. 锁与 DB 的关系？→ 分布式锁是**效率优化**（防重复计算）不是**正确性保证**（fencing 缺失）；正确性始终应当由存储层的原子条件更新兜底。
2. 主从切换锁丢失？→ 主节点加锁未同步到从就宕机，新主没有锁 → 双持有。这是 RedLock 试图解决又没彻底解决的问题。

**【P10 加分项】**
给出锁选型矩阵：效率锁（缓存重建）用 Redisson；正确性锁（扣库存）用 DB 乐观锁/原子操作；协调锁（选主）用 ZK/etcd。**"锁的正确性分级"是面试官想听的架构判断。**

## 6.3 进阶题（P7-P8）

### 题 6.3.1：Redis 主从复制原理？哨兵怎么选主？

**【参考回答（可背）】**
复制：
1. **全量**：从库发 psync → 主库 bgsave RDB 传输 → 期间新写命令进 **replication buffer** → RDB 加载完补发 buffer；
2. **增量**：repl_backlog（环形缓冲区）+ offset，断线重连 offset 还在 backlog 内则部分重同步（psync 增量），否则退全量——**backlog 大小影响闪断恢复成本**（默认 1M，生产按"写入速率×容忍断线时长"调）；
3. 主从复制是**异步**的 → 存在丢失窗口（min-replicas-to-write 可缓解：至少 N 个从延迟 <M 秒才接受写）。

哨兵（Sentinel）：
- 三个定时任务：每 1s ping、每 2s 交换信息（__sentinel__:hello）、每 10s/1s（故障时）获取拓扑；
- 主观下线（单个 sentinel 认为）→ **客观下线**（quorum 个同意）→ 选举 leader sentinel（Raft 思想）→ 执行故障转移；
- **从库选主四步**：优先级 replica-priority → 复制 offset 最大（数据最全）→ runid 最小。

**【追问链】**
1. 哨兵数量？→ 至少 3 个奇数（防脑裂的多数派）；部署在与 Redis 不同故障域。
2. 脑裂（split brain）？→ 网络分区时旧主仍在接受写，恢复后这些写丢失；缓解 min-replicas-to-write=1。

**【P10 加分项】**
Cluster 与哨兵的选型：哨兵+主从适合"数据量小、扩展靠客户端分片"场景；Cluster（16384 slot、CRC16(key) mod、MOVED/ASK 重定向、gossip 协议）适合水平扩展与自动化——但**多 key 操作受限（hash tag）、运维复杂**。给出"何时不上 Cluster"的判断（数据量 <50G 哨兵足够）是加分信号。

### 题 6.3.2：热 key 与大 key 问题怎么治理？

**【参考回答（可背）】**
**热 key**（单 key QPS 极高打爆单分片）：
- 发现：客户端埋点统计、redis-cli --hotkeys（需 LFU）、监控 proxy 维度；
- 治理：① **本地缓存兜底**（热 key 推送到各应用本地 Caffeine）；② key 打散（加随机后缀分片成 N 个，读随机取一，写双写/广播）；③ 读写分离读扩展（接受秒级延迟）；④ 集群热分片问题：slot 迁移或专用副本组。
**大 key**（value 过大：string >10KB、集合元素 >5000 经验阈值）：
- 危害：慢查询阻塞单线程（删除 100 万元素的 set 阻塞秒级）、网络带宽打满、迁移卡顿、内存倾斜；
- 治理：拆分（hash 分桶：field 取模）、压缩（value gzip/snappy）、**异步删除 UNLINK**（后台线程释放，4.0+ lazy-free）、过期用 SCAN 分批删而不是 KEYS。
- 防复发：写入前代码层检查（尺寸门禁）、定期 --bigkeys/rdb 分析巡检。

**【P10 加分项】**
大促热 key 预案完整叙事：压测发现 top10 hot key → 推送本地缓存 + 接口限流 + 集群分片手工均衡 → 大促值班实时看板。**"热 key 是预测出来的，不是故障时发现的"**——预案文化是 P10 信号。

## 6.4 压轴题（P9-P10）

### 题 6.4.1：设计一个支撑百万 QPS 的商品详情页缓存架构

**【参考回答（分层可背）】**
1. **流量特征**：读多写少、热点集中（top 1% 商品占 50% 流量）、允许秒级不一致。
2. **多级缓存漏斗（必背顺序）**：
   - **L1 本地缓存**（Caffeine，进程内，纳秒级）：top 热点商品 + 静态化数据；TTL 1~5s 短窗口兜一致性；命中率 60%+；
   - **L2 Redis 集群**（毫秒级）：全量商品数据，分片；命中率 35%+；
   - **L3 DB**：仅 5% 未命中，限流保护。
3. **数据拆分**：主数据（标题价格库存状态）与扩展数据（详情图文）分 key，避免大 key；价格库存走独立实时服务（不强缓存）。
4. **一致性**：binlog（Canal）→ MQ → 广播失效 L2 + 各节点 L1（Pub/Sub 或 MQ 广播）；本地缓存短 TTL 兜底最终一致。
5. **热点治理**：实时热 key 探测（滑动窗口统计）→ 自动推送本地缓存；缓存预热（大促前按预测 top 列表提前加载）；**防击穿**：热点重建单飞。
6. **防雪崩**：TTL 抖动、DB 限流熔断（Sentinel）、降级开关（极端时返回静态兜底页/降级文案）。
7. **可观测**：各级命中率、回源 QPS、热 key 榜、大 key 榜——命中率突降告警。

**【追问链】**
1. 本地缓存内存多大？→ 有界（Caffeine maximumSize/权重），按"top N 商品 × 单条大小"预算，绝不能无界。
2. 多机房怎么做？→ 单元化部署（按用户分片各机房自闭环）或跨机房只读副本 + 本机房缓存。

**【P10 加分项】**
量化叙事："详情页 P99 从 45ms 降到 8ms，DB QPS 从 12 万降到 6000，成本是双倍内存与秒级一致性——这笔账跟业务方确认后落地。"**用成本与业务妥协讲清方案，而不是堆技术名词。**

### 题 6.4.2：如果让你重新设计 Redis，你会改进什么？（开放架构题）

**【参考回答（框架：肯定 → 短板 → 改进 → 现实约束）】**
1. 肯定：单线程模型的价值（简单、可预测延迟）、丰富数据结构的 API 设计、社区生态。
2. 短板与改进方向：
   - **单线程命令执行**在慢命令（大 key、KEYS、复杂 Lua）下全实例阻塞 → 强制配额（执行时间上限、扫描类命令限流）、细粒度慢日志自动熔断；
   - **主从异步复制**的丢失窗口 → 分层一致性选项（类似 min-replicas 但做成 per-key 语义）；
   - **内存碎片与 COW** → 更细粒度内存管理（Redis 7 listpack 化已在改善）；
   - **多 key 事务/ Lua 的原子性范围**仅限单实例 → Cluster 下 cross-slot 原子操作原生支持；
   - **集群脑裂保护**参数粒度粗 → 引入类 Raft 自动选主（KeyDB/Dragonfly 已在尝试多线程架构，说明单线程不是不可动摇）。
3. 现实约束收尾：兼容性是最大约束——Redis 生态价值在协议兼容，重设计必须兼容 RESP 协议与数据格式，否则生态归零。**架构创新要还"兼容性债"。**

**【P10 加分项】**
提到替代品动态（Dragonfly 多线程共享内存架构、KeyDB、以及云厂商代理层方案），并给出判断："性能瓶颈从 CPU 转向网络与内存时，多线程 Redis 才有收益；对我们业务，Redis 的真正瓶颈是**一致性语义与运维成本**，不是吞吐。"——展示技术雷达 + 业务落点。

## 6.5 本章高频追问链图谱

```
五大类型 ──→ 底层编码 ──→ 跳表 ──→ 双结构 ZSet ──→ 内存量化
穿透 ──→ 布隆过滤器 ──→ 击穿 ──→ 单飞/逻辑过期 ──→ 雪崩 ──→ TTL 抖动+多级缓存
一致性 ──→ 先库后删 ──→ 延迟双删 ──→ Canal binlog ──→ TTL 兜底
分布式锁 ──→ NX PX + Lua ──→ 看门狗 ──→ RedLock 争议 ──→ fencing token ──→ 锁分级
主从 ──→ repl_backlog ──→ 哨兵选主四步 ──→ 脑裂 ──→ Cluster 16384 slot
热 key ──→ 本地缓存+打散 ──→ 大 key ──→ UNLINK/分桶 ──→ 巡检门禁
```

## 6.6 一页速记卡

1. Redis 快四因：内存、epoll、单线程无锁、专用数据结构。
2. ZSet = 跳表 + 字典双结构；List 是 quicklist；小对象 listpack 压缩。
3. 过期 = 惰性 + 定期抽样；淘汰必配 allkeys-lru/lfu。
4. 穿透挡（布隆/空值）、击穿合（单飞/逻辑过期）、雪崩抖（TTL 随机+多级）。
5. 一致性标准答案：先更新 DB 再删缓存 + binlog 异步删 + TTL 兜底。
6. 锁：SET NX PX + 唯一 value + Lua 删 + 看门狗；正确性靠 DB 兜底。
7. RDB 快恢复丢数据，AOF everysec 丢 1 秒，4.0 混合是推荐默认；fork 卡顿看 latest_fork_usec。
8. 哨兵：主观→客观→Raft 选 leader→四步选从；奇数 ≥3 防脑裂。
9. 热 key：本地缓存+打散；大 key：UNLINK+分桶+巡检。
10. 单实例内存 <10G；KEYS 禁用；Redis 7 listpack 全面化。

## 6.7 增补题（v1.1 深度扩充）

### 题 6.7.1：Redis Cluster 扩容怎么迁移 slot？业务无感知靠什么？

**【面试官意图】** Cluster 运维深度——多数人只会说 16384 槽，不会迁移。
**【参考回答（可背）】** 流程：① 新节点加入（cluster meet）→ ② 规划槽位分配（从重负载节点各匀一些）→ ③ 按槽迁移：源节点 MIGRATING、目标节点 IMPORTING、逐 key `CLUSTER GETKEYSINSLOT` + MIGRATE 原子搬迁（MOVE 选项，ttl 保留）→ ④ 更新槽归属广播。**业务无感知的关键**：迁移中对该槽的请求，源节点返回 **ASK 重定向**（带临时跳转语义），客户端（Smart Client）缓存槽位映射并处理 MOVED/ASK——客户端"无感"其实依赖客户端实现的正确性。
**【追问链】** ① MOVED 与 ASK 区别？（MOVED=槽已永久归属他节点，客户端应更新映射缓存；ASK=槽在迁移中，本次临时跳、不更新缓存）② 迁移期间多 key 命令会怎样？（跨槽多 key 操作报 CROSSSLOT 错——hash tag {user123} 强制同槽是解法，但会制造新热点）。
**【P10 加分项】** "扩容预案里最值钱的是'限速迁移'：MIGRATE 是同步阻塞的，大 key 迁移会卡源节点——所以大 key 治理（6.3.2）是 Cluster 扩容的前置工程，两件事必须串起来讲。"

### 题 6.7.2：Lua 脚本的使用边界？写多了会怎样？

**【参考回答（可背）】** 价值：多命令**原子性**（无中途插队）+ 减少网络往返。边界三铁律：① Lua 执行期间**单线程被独占**——脚本里禁用 O(N) 大命令（KEYS/SMEMBERS 大集合），必须用 SCAN 分片思维；② 脚本只操作 KEYS 参数里声明的 key（Cluster 下跨槽直接报错，且可被集群正确路由）；③ 脚本要有幂等性与超时意识（script kill 只能杀"没写过数据"的脚本——写了数据的只能等执行完或 reset 硬杀）。替代：复杂原子逻辑上移到应用+分布式锁，或下移到 Redis 7 的 Function（可管理、可重载）。
**【追问链】** ① 为什么说"Lua 里调 KEYS 是生产事故高发点"？（keys 全库扫描阻塞主线程数秒，且藏在脚本里慢日志都抓不到全过程）② Lua 与 WATCH/MULTI 取舍？（事务乐观锁轻量无原子计算；Lua 能"读后写"决策——按值条件操作只能 Lua）。
**【P10 加分项】** "我们给 Lua 定了'10 行以内、单 key 组、O(1) 命令'三红线并纳入 code review 清单——脚本复杂度失控等于把业务逻辑写进了单线程瓶颈里。"

### 题 6.7.3：Redis 的内存碎片怎么来的？怎么治理？

**【参考回答（可背）】** 来源：jemalloc 按尺寸类分配，大量"写后删+写"的负载（特别是频繁 set 不同长度的大 value、ziplist/listpack 频繁扩缩容）产生类间空隙。观察：`INFO memory` 的 mem_fragmentation_ratio（>1.5 且 RSS 远大于 used_memory 即碎片严重；<1 反而说明发生了 swap，更危险）。治理：① 4.0+ 的 **activedefrag**（active-defrag-enabled，利用 jemalloc 空闲页实时整理，在线不阻塞）；② 极端情况重启（受控 failover 逐节点）；③ 源头治理：value 长度稳定化、避免频繁大对象写删。
**【追问链】** ① mem_fragmentation_ratio 正常区间？（1.0~1.4；容器环境要算上预留页，读 RSS 才准确）② 为什么 <1 比 >1.5 更紧急？（used_memory 比 RSS 大=数据被换到 swap，性能塌方）。
**【P10 加分项】** "内存三大症候的分流诊断：碎片（ratio>1.5）→ activedefrag；swap（ratio<1）→ 限内存+迁移；增长无上限 → 大 key/集合无界巡检。三条曲线看懂 Redis 内存体检单。"

### 题 6.7.4：Redis 版本演进你关注哪些点？（6/7 的关键变化与升级收益）

**【参考回答（可背）】** 背这个演进清单：6.0——**多线程 IO**（网络读写并行化，命令执行仍单线程，大吞吐收益 2x+）、ACL 权限；6.2——可用性命令增强；7.0——**Multi-Part AOF**（基线+增量流，重写不再双写缓冲）、**Function**（服务端函数替代散装 Lua）、listpack 全面替代 ziplist（内存与实现简化）、Sharded Pub/Sub（Cluster 下订阅按 slot 分片，避免广播风暴）。升级判断：6→7 对"大 value+高吞吐+重 Lua"场景收益明确；跨大版本升级走"主从滚动+哨兵切换"灰度。
**【追问链】** ① 多线程 IO 为什么命令执行保持单线程？（保留免锁模型与延迟确定性，网络才是瓶颈）② Sharded Pub/Sub 解决什么？（Cluster 全量广播的 fanout 风暴，订阅收窄到 slot 所属分片）。
**【P10 加分项】** "看 Redis 演进的主线其实是'**内存编码持续简化 + 网络与持久化的并行化**'——数据结构红利（ziplist→listpack）吃尽后，瓶颈转向 IO，6/7 的所有大特性都在这条线上。能用主线归纳版本特性的，说明真跟进了演进。"
