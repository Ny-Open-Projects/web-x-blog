## 8.1 零基础起步

### 卡片 1：CAP 与 BASE
- **CAP**：网络分区（P）发生时，一致性与可用性**二选一**。P 是必选项（分布式系统生命周期内网络故障迟早发生），所以真实选择是 CP（ZK/etcd：分区时拒绝服务保一致）vs AP（Eureka/Nacos AP 模式：返回旧数据保可用）。
- **BASE**：基本可用（Basically Available）、软状态（Soft state）、最终一致（Eventually consistent）——AP 的工程化表达。
- 常见误区：CAP 不是"三选二"，无分区时 C 和 A 可以兼得；分区只是概率事件。

### 卡片 2：微服务拆分的基本动作
单体 → 按业务域拆（DDD 限界上下文）→ 每服务独立数据库 → 服务间 RPC/消息通信。
**先有共识**：微服务的成本 = 分布式事务、链路排障、运维复杂度×N。**不是拆得越细越好**——"拆分的粒度 = 团队规模与业务变更频率"（康威定律）。

### 卡片 3：分布式事务问题从哪来？
一个业务动作跨多个库/服务，本地事务管不住。例：下单 = 订单库 + 库存库 + 账户库。任何"跨库写"都需要协议来对齐。

### 卡片 4：限流熔断降级三兄弟
- **限流**：控制进入的流量（阀门）；
- **熔断**：下游坏了就别再调（断路器，防止雪崩传染）；
- **降级**：系统过载时砍掉非核心功能（保命的优先级取舍）。

## 8.2 入门题（P4-P6）

### 题 8.2.1：Raft 协议的流程？和 Paxos、ZAB 什么关系？

**【参考回答（可背）】**
Raft 三角色：Leader / Follower / Candidate。三个子问题：
1. **选主**：心跳超时的 Follower 变 Candidate，term+1 拉票；多数派投票（每 term 一票，先到先得）成为 Leader；日志不全的候选人拿不到票（投票条件：候选日志不旧于自己）。
2. **日志复制**：客户端请求 → Leader 追加日志 → 并行发给 Follower → **多数派确认后提交** → 应用状态机 → 响应；Follower 事后异步 apply。
3. **安全性**：Leader 崩溃后新 Leader 必须包含所有已提交日志（选举限制保证）；term 小的日志被覆盖丢弃。
**Paxos**：正确但难懂难实现（Multi-Paxos 无标准实现）；**Raft 的贡献是可理解性**——把问题分解成选主/复制/安全三块，成了工业界事实标准（etcd、TiKV、Nacos CP 模式）。
**ZAB**：ZooKeeper 的协议，与 Raft 同族（Fast Leader Election + 崩溃恢复 + 消息广播），epoch 对应 term。

**【追问链】**
1. 为什么日志型系统都要"多数派"？→ 2N+1 容忍 N 故障；少数派数据可能过期，多数派一定包含最新已提交数据（法定人数 Quorum：W+R>N）。
2. 脑裂怎么防？→ 任一时刻只有一个多数派能选出 Leader，旧 Leader 的写无法凑齐多数派确认。

**【P10 加分项】**
指出"工程上的 Raft"还要处理：成员变更（joint consensus/单步变更）、日志压缩快照、读线性化（ReadIndex/Lease Read，etcd 的实现）——读过 etcd/raft 源码或实现过状态机复制的候选人极少，这是硬通货。

### 题 8.2.2：分布式事务方案全景对比？

**【参考回答（必背对比矩阵）】**
| 方案 | 一致性 | 性能 | 侵入性 | 适用 |
|------|--------|------|--------|------|
| 2PC/XA | 强 | 低（同步阻塞、协调者单点） | 低（JTA） | 传统数据库间短事务，互联网少用 |
| TCC | 强（业务级） | 中（资源预留） | **高**（Try/Confirm/Cancel 三接口） | 资金类核心链路 |
| SAGA | 最终 | 高 | 中（每步要补偿） | 长流程、跨多服务（下单→扣库存→物流） |
| 本地消息表 | 最终 | 高 | 中（一张表+扫描） | 快速落地、依赖本地事务 |
| 事务消息 | 最终 | 高 | 中 | RocketMQ 生态 |
| 最大努力通知 | 弱 | 高 | 低 | 通知类（支付结果通知外部商户） |

**选型心法（背）**：
1. **能不用就不用**：拆服务时按"事务边界"聚合（能一个库解决不拆）；
2. 资金强一致 → TCC（Try 预留资源，Confirm/Cancel 补偿，要处理空回滚/悬挂/幂等三大坑）；
3. 一般业务 → SAGA/消息最终一致；
4. 2PC 在互联网规模基本不用（阻塞+协调者故障放大）。

**【追问链】**
1. TCC 三大坑怎么防？→ **空回滚**（Try 没到 Cancel 先到：Cancel 检查有无 Try 记录，无则记空回滚标记）；**悬挂**（Cancel 后 Try 才到：Try 检查回滚标记直接拒绝）；**幂等**（Confirm/Cancel 可能重试多次，以事务 ID 去重）。
2. SAGA 补偿失败怎么办？→ 补偿也要重试+人工兜底；设计时让每步补偿"可成功"（预留/标记代替真扣）。

**【P10 加分项】**
"不引入分布式事务"的架构手段清单：业务聚合（订单+流水同库）、状态机 + 异步补偿、对账兜底、用户补偿交互（可撤销的体验设计）。**最好的分布式事务是设计掉它**——这句话必须有案例支撑（举一个自己拆事务的真实设计）。

### 题 8.2.3：Nacos/Eureka/ZooKeeper 作为注册中心的区别？服务发现选什么？

**【参考回答（可背）】**
- **ZooKeeper**：CP。选主/分区时不可用——服务发现场景反而致命（宁可给旧列表也别没列表）；会话依赖心跳，网络抖动误摘除。
- **Eureka**：AP。自我保护机制（心跳丢失比例高时暂停摘除），返回可能过期的列表；已进维护模式。
- **Nacos**：AP/CP 双模——临时实例（默认，Distro 协议，AP，心跳续约）与持久实例（Raft，CP）；配置中心一体，国内主流。
- 工程结论：**服务发现选 AP**（可用性 > 短暂不一致，客户端可做失败转移兜底）；**选主/元数据协调选 CP**（ZK/etcd）。一个系统两个都要：服务发现 Nacos AP + 分布式锁 etcd。

**【追问链】**
1. 客户端怎么做故障容错？→ 本地缓存服务列表（注册中心挂了也能跑）、负载均衡重试、熔断。**"客户端韧性"是服务发现真相：注册中心挂掉不该立刻影响线上流量。**
2. 推 vs 拉发现？→ 拉（轮询，简单有延迟）vs 推（长连接推送，实时）vs Nacos 混合（UDP 推 + 定时拉兜底）。

**【P10 加分项】**
服务网格视角：Istio 把服务发现/流量治理下沉 Sidecar，Java SDK 退化为纯业务——成本是 Sidecar 资源与运维复杂度；判断："规模不大时 Spring Cloud + Nacos 性价比更高，Mesh 适合多语言异构团队与规模化平台团队。"

## 8.3 进阶题（P7-P8）

### 题 8.3.1：限流算法全家与 Sentinel 实战？

**【参考回答（可背）】**
1. **计数器（固定窗口）**：最简单，临界突刺问题（窗口边界双倍流量）。
2. **滑动窗口**：细分格子滚动统计，解决突刺（Sentinel 底层 LeapArray 滑动窗口）。
3. **漏桶**：恒定速率流出，削平突发（保护脆弱下游）。
4. **令牌桶**：恒定速率放令牌，桶容量允许突发（Guava RateLimiter，允许一定 burst 更贴近真实流量）。
5. 分布式限流：Redis + Lua（原子取令牌）或中间件（Sentinel 集群流控 token server）。
**Sentinel 实战要点**：流控规则（QPS/并发线程数）、熔断策略（慢调用比例/异常比例/异常数，半开恢复）、热点参数限流（对商品 ID 单独限）、系统自适应保护（Load/CPU 水位兜底）、规则动态推送（Nacos 数据源）。

**【追问链】**
1. 单机限流 vs 集群限流？→ 集群限流精确但依赖 token server（本身要高可用）；常用折中：网关层粗限 + 单机均分配额（配额同步容忍误差）。
2. 限流后被拒的请求怎么办？→ 快速失败给友好提示 / 排队等待（稀疏请求）/ 降级数据。**拒绝也是一种服务能力，要有专门响应。**

**【P10 加分项】**
"限流值怎么定"方法论：压测得出单实例安全水位 → 容量 × 冗余系数（1.5~2）→ 大促专项压测验证 → 运行时根据 P99 RT 自适应调整（不是拍脑袋 1000）。把限流放进**容量管理**体系讲。

### 题 8.3.2：可观测性三大支柱？怎么做全链路追踪？

**【参考回答（可背）】**
1. **Metrics**（指标）：时序数值（QPS/RT/错误率/资源水位），Prometheus + Grafana，告警的主数据源。
2. **Tracing**（追踪）：请求跨服务链路 —— traceId 全局唯一、spanId 父子关系；OpenTracing/OpenTelemetry 标准化，Jaeger/SkyWalking 存储；SkyWalking 字节码无侵入是国内主流。
3. **Logging**（日志）：结构化（JSON）+ traceId 注入 → ELK/Loki 聚合检索。
三者关联：**告警（Metrics）→ 定位服务（Tracing）→ 看日志（Logging）→ 定位代码**，一条链打通才有价值。
工程要点：traceId 必须跨异步边界传递（MQ 消息体携带、线程池 TTL 传递——连接第 2 章）、采样率权衡（全量太贵，错误请求强制保留）、Span 深度控制（性能开销）。

**【追问链】**
1. 告警怎么避免风暴？→ 分级（P0 电话/P1 短信/P2 群）、收敛（同因合并）、基于 SLO 的错误预算告警而非阈值裸告警。
2. 一个线上问题你的定位路径？→ 背模板：告警面板（哪个服务哪些指标坏）→ trace 拉出慢/错 span（定位到下游接口）→ 该接口日志与最近变更（上线 diff）→ 代码。**"最近改了什么"是 80% 线上问题的第一问。**

**【P10 加分项】**
SLO 体系：定义用户视角的可靠性目标（如 99.95% 可用、P99 <200ms）→ 错误预算（一个月允许 21 分钟故障）→ 预算耗尽冻结发布优先修复——把稳定性从"救火文化"变成"预算管理"。这是 Google SRE 的核心思想，P10 级团队必备。

## 8.4 压轴题（P9-P10）

### 题 8.4.1：单体到微服务怎么拆？什么时候该合并回来？

**【参考回答（方法论可背）】**
1. **何时拆**：单体部署发布互相阻塞（一个模块出 bug 全体回滚）、团队 >2 个披萨（康威定律）、模块伸缩需求差异大（营销模块要独立扩容）。
2. **怎么拆（DDD 方法）**：
   - 事件风暴梳理领域事件 → 识别限界上下文（订单/商品/库存/支付/营销）；
   - **上下文映射**定集成方式（防腐层隔离外部模型）；
   - 按上下文先"逻辑分层"（模块化单体）再物理拆分——**渐进式，不一步到位**；
   - 数据库跟随服务走（每个服务私有库，跨库只走 API——**禁止共享库**）。
3. **拆分红线**：先稳定再拆（业务快速试错期不拆）、拆之前先做单元化（按领域建 Maven 模块）、拆完有监控与回归手段。
4. **何时合并（P10 加分，敢说合并的人少）**：拆过细的信号——一次需求跨 5 个服务改、分布式事务泛滥、调用链成环；合并手段：同上下文服务合并、逻辑回单体（模块化单体 Modular Monolith 回潮是有道理的）。
5. **演进结论**：微服务是手段不是信仰，粒度跟着"变更频率 × 团队边界"走。

**【追问链】**
1. 服务间怎么通信？→ 同步 RPC（内网强依赖、契约演进难）vs 异步事件（解耦但调试难）；原则：核心链路同步直连，旁路全异步事件。
2. 接口契约怎么演进？→ 向后兼容原则（只加字段不删不改语义）、契约测试（Pact）、版本共存（/v2 双跑切换）。

**【P10 加分项】**
讲组织视角："拆服务本质是拆组织沟通成本，先问这个服务给哪个团队负责、oncall 是谁，回答不了就不该拆。"——康威定律的正反两面都用上，P10 信号极强。

### 题 8.4.2：怎么保证系统"高可用"？给出你的稳定性工程体系（不是背关键词）

**【参考回答（体系可背：预防 → 感知 → 止血 → 复盘）】**
1. **预防（架构期）**：
   - 冗余：无单点（多机房/多可用区部署、数据库多副本）；
   - 隔离：业务隔离（核心链路独立集群）、线程池/连接池舱壁；
   - 弹性：限流熔断降级三板斧预置 + 预案平台（一键开关）；
   - 容量：全链路压测（影子流量/影子库压真实链路，大促前发现瓶颈）。
2. **感知（监控期）**：Metrics/Tracing/Logging 三支柱 + 黄金指标（延迟/流量/错误/饱和度）+ SLO 错误预算告警分级。
3. **止血（应急期）**：
   - 演练过的预案才有用：故障演练（ChaosBlade 注入超时/网络断、机器杀进程）常态化；
   - 止血四板斧：回滚（通常最快最安全——发布必须支持一键回滚）、扩容、降级/限流、切流（流量迁移到健康单元）；
   - 值班体系：oncall 分级、MTTR 目标、事故指挥官（IC）机制。
4. **复盘（改进期）**：无责复盘文化（对事不对人）、时间线还原、action item 落地跟踪、同类隐患横向排查。
5. **量化**：可用性 4 个 9 = 年 52 分钟；用 MTBF（无故障时长）与 MTTR（恢复时长）表达——**高可用 = 降低故障概率 × 缩短恢复时间**。

**【追问链】**
1. 全链路压测怎么实现？→ 流量标记透传（压测标 header）→ 数据隔离（影子表/影子 Redis 前缀）→ 中间件全链路识别压测标 → 逐步加压找瓶颈点 → 瓶颈治理清单。
2. 灰度发布方式？→ 金丝雀（小流量验证）→ 蓝绿（双环境切流）→ 单元化按用户灰度；配套：发布可观测看板 + 自动回滚触发（错误率阈值）。

**【P10 加分项】**
一句话升华："稳定性的上限不是技术，是组织——无责复盘、预案演练、变更管理三板斧都是管理动作。P10 交付的不是代码，是**可预期的可靠性**。"

## 8.5 本章高频追问链图谱

```
CAP ──→ CP/AP 实例（ZK/Nacos） ──→ Quorum ──→ Raft 三子问题 ──→ 工程化（etcd/ReadIndex）
分布式事务 ──→ 2PC 阻塞 ──→ TCC 三坑 ──→ SAGA 补偿 ──→ 消息最终一致 ──→ 对账兜底 ──→ "设计掉"
注册中心 ──→ AP/CP 选择 ──→ 客户端韧性 ──→ Mesh 取舍

可观测 ──→ 三支柱 ──→ traceId 跨异步 ──→ SLO/错误预算 ──→ 故障演练
拆分 ──→ DDD 限界上下文 ──→ 康威定律 ──→ 模块化单体回潮
```

## 8.6 一页速记卡

1. CAP：分区时 C/A 二选一；注册中心选 AP，协调选 CP。
2. Raft：选主（term+多数派）→ 复制（多数派提交）→ 安全（选举限制）。
3. TCC 三坑：空回滚、悬挂、幂等——都以事务记录表解决。
4. 最好的分布式事务是设计掉它：聚合库、状态机、对账。
5. 限流四算法：计数器（突刺）→ 滑动窗口 → 漏桶（恒速）→ 令牌桶（允许突发）。
6. Sentinel 熔断三策略：慢调用比例/异常比例/异常数，半开试探恢复。
7. 可观测三支柱一条链：Metrics 告警 → Tracing 定位 → Logging 取证。
8. traceId 必须跨 MQ/线程池传递；错误请求强制采样。
9. 稳定性四段：预防（冗余隔离）、感知（SLO）、止血（回滚优先）、复盘（无责）。
10. 拆分跟随团队边界；拆细了要敢合并；禁止共享库。

## 8.7 增补题（v1.1 深度扩充）

### 题 8.7.1：Raft 的成员变更怎么做？为什么不能直接改配置？

**【面试官意图】** 检验是否真读过 Raft 论文第 6 节，而非只会背三个子问题。
**【参考回答（可背）】** 直接改成员配置会出现两个多数派（新旧配置分别凑齐多数派）→ 同一 term 产生两个 Leader → 脑裂。两种方案：① **联合共识**（joint consensus）：过渡阶段同时需要新旧两个多数派批准，安全但实现复杂；② **单成员变更**（Single-Server Membership Change，etcd/多数实现采用）：每次只增删一个成员，因为任意新旧配置的多数派必然有交集，天然安全——但存在"3→4 变更中间宕机导致可用性降级"的边界，靠新一轮变更修复。
**【追问链】** ① 为什么 3→4 中间态可用性变差？（4 的多数派是 3，容错能力反而从 1 降到 0，所以要一次变更内尽快恢复奇数）② 日志压缩快照什么时候做？（状态机 apply 后定期快照 + 截断已应用日志）。
**【P10 加分项】** 提工程细节：etcd 的 raft 库把成员变更当一条特殊日志处理（ConfChange entry）；变更失败的可观测指标（conf change failed 计数）。能聊到"成员变更日志也要参与选举限制"属顶级。

### 题 8.7.2：分布式 ID 方案对比？雪花算法时钟回拨怎么处理？

**【参考回答（可背）】** 三方案矩阵：① 雪花（64 位：时间戳+机器位+序列）：本地生成无网络开销，但依赖时钟与机器位分配；② 号段模式（DB 批量取号段）：简单可控，DB 是瓶颈点，双 buffer 预取优化；③ Redis 自增：性能好但持久化丢号风险。雪花时钟回拨对策（背四条）：回拨小（<5ms）等待；回拨大报警拒绝服务；机器位用持久化配置防重复分配；或改用"逻辑时钟"（时间戳用上次最大值取 max）。
**【追问链】** ① 雪花 ID 为什么趋势递增但不严格递增？（同毫秒内序列递增，跨节点无法保证全局顺序）② 号段+雪花混合怎么做？（Leaf-segment 与 Leaf-snowflake 并存，按场景选）。
**【P10 加分项】** 讲"ID 即索引"的隐藏代价：分库分表后 ID 作为主键要兼顾路由（基因法把 user 分片位嵌入 ID）——把 ID 设计与第 5 章分库分表串起来，属于架构级答案。

### 题 8.7.3：全链路压测的影子库与流量染色怎么实现？

**【参考回答（可背）】** 三个环节：① **染色**：网关给压测流量打标（header/http 参数，如 X-Load-Test: 1），标记全链路透传（RPC/MQ/线程池都要透传——MQ 靠消息属性，线程池靠 TTL）；② **隔离**：数据层按标记路由到影子表（同库影子表或独立影子库），Redis 用前缀 key，缓存/ES 同理；③ **改造点清单**：定时任务、消息消费者、第三方回调等"非入口流量"要加染色识别，漏一处就是生产数据被压测污染。
**【追问链】** ① 影子表数据怎么清理？（压测前建表压测后 truncate，或用独立账号+权限隔离防误写主表）② 压测基准怎么算？（目标峰值×1.5 稳态 + 突发脉冲场景，分层加压定位瓶颈拐点）。
**【P10 加分项】** 讲大促演练的完整指标：压测通过标准 = 目标 QPS 下 P99 达标 + 无错误率爬升 + 中间件资源水位 <70%；瓶颈治理清单按"DB→缓存→下游→JVM→网关"顺序收敛，呼应第 9 章 RT 三角。

### 题 8.7.4：服务网格 Istio 的数据面原理与落地成本？

**【参考回答（可背）】** 架构：控制面 istiod 维护服务发现与策略，数据面每个 Pod 侧挂 Envoy Sidecar；配置下发走 **xDS 协议**（LDS 监听器、RDS 路由、CDS 集群、EDS 端点），Envoy 按 L4/L7 过滤器链转发，实现流量治理（金丝雀/熔断/重试/遥测）下沉到平台层，应用代码零 SDK。成本：① 每个 Pod 额外 CPU/内存（Proxy 开销随流量增长）；② 注入失败/Sidecar 版本升级的运维复杂度；③ 多一跳网络（latency +1~3ms）；④ Java 应用与 Mesh 功能重叠（SDK 已有熔断限流时收益打折）。
**【追问链】** ① 什么时候值得上 Mesh？（多语言异构团队规模大、平台团队成熟、SDK 治理难以统一时）② Sidecarless 方向？（Cilium eBPF 把 L4 下沉内核，L7 仍留 proxy——趋势判断加分）。
**【P10 加分项】** 给决策框架："Mesh 的本质是把治理从'代码能力'变成'平台能力'，买它等于买'治理一致性'；规模不到，一致性痛点没出现，就别付这份税。"

### 题 8.7.5：单元化（LDC）部署怎么做？和普通灰度发布什么区别？

**【参考回答（可背）】** 普通灰度是"同一份服务按流量比例分版本"；单元化是把**用户按 ID 分片映射到物理机房（单元）**，每个单元自闭环（应用+数据都在本单元），写流量只落归属单元，跨单元调用通过路由层（网关按用户 ID 解析单元路由）转发。收益：① 容量弹性按单元复制；② 故障爆炸半径=单单元，可切流；③ 数据同城/异地容灾按单元粒度做主备。
**【追问链】** ① 数据怎么保证单元内闭环？（路由键一致性：DB 分片键=单元分片键，都是 user_id 取模/哈希）② 某单元故障切流，数据怎么办？（主备单元间准实时同步，切流时停写-追平-切写，RPO 秒级）。
**【P10 加分项】** 引阿里 LDC 实践：单元化是"容量、容灾、灰度三合一"的终极方案，但改造代价大（所有链路必须带路由键），适合头部业务；中小业务"同城双活+应用层灰度"性价比更高——给出分阶段演进路径（双活→同城单元化→异地多活）。

### 题 8.7.6：分布式系统的时钟问题怎么解？讲讲 Spanner 的 TrueTime 思想

**【参考回答（可背）】** 问题：多机时钟不同步导致事件排序歧义（NTP 毫秒级误差）。三种路线：① **逻辑时钟**：Lamport 时间戳/HLC（混合逻辑时钟）保证因果序，无全局物理时序；② **共识序**：用 Raft/Paxos 的日志顺序作为全序（etcd watch revision 就是这个思想）；③ **物理时钟+不确定性区间**：Google Spanner TrueTime 用原子钟+GPS 把误差收敛到 ±ms 内，写时等待"最大不确定区间结束"（commit wait）实现外部一致性（事务时间序与真实时间一致）。
**【追问链】** ① 为什么要外部一致性？（用户视角"先转出后到账"的顺序必须成立）② 我们系统常用哪种？（HLC/TiDB TSO——中心授时节点，简单但有单点，靠 PD 高可用）。
**【P10 加分项】** 落到工程："分布式事务里的时间戳分配方式决定了产品的延迟与扩展性——TiKV 用中心 TSO 换单点授时（RT 稳定），CockroachDB 用 HLC 换无中心（RT 受时钟误差影响）。选型即权衡。"能把时钟问题讲到 TSO/HLC 分岔的，基本没有第二个候选人。
