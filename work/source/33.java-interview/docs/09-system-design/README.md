# 第 9 章 亿级高并发系统设计与真实场景题 —— 方法论与五大经典设计

> 场景设计题是 P10 面试的**压轴主菜**（30~45 分钟）。考察的不是"背方案"，而是：
> ① 澄清需求（先问清规模再动手）② 估算（流量/存储）③ 分层方案（先通再优）
> ④ 权衡表达（每个选择说代价）⑤ 演进（10 倍量怎么办）。
> 本章先给**万能答题框架**，再拆 5 道经典题的完整答案。

---

## 9.0 答题框架（P10 场景题五步法，必背）

1. **澄清需求**：业务目标？QPS/数据量/增长？一致性要求？延迟要求？读写比例？
   （开口先问，直接画图反被扣分——" clarify before design"）
2. **估算**：QPS 峰值 = 日请求 × 峰谷比（2:8 法则下峰值≈日均×20÷(4×3600)量级）；
   存储 = 单条大小 × 日增 × 保留期；带宽 = QPS × 响应大小。
   例：日活 1 亿 App，每人日 50 请求 → 日 50 亿请求，峰值 QPS ≈ 50亿×20%/(4h) ≈ 7 万/s。
3. **主干设计**：入口（网关）→ 服务层 → 缓存 → 存储；先画能跑通的 happy path。
4. **难点攻坚**：找 2~3 个瓶颈（热点、一致性、扩展性）逐个给方案，**每个方案说代价**。
5. **演进与兜底**：数据量 10 倍怎么办？机房挂了怎么办？监控与预案是什么？

## 9.1 题一：设计一个短链接系统（如 t.cn）

**【需求澄清】** 长链转短链 + 301/302 跳转；读多写少（读写比 100:1）；不可预测性：短码不能被穷举。

**【估算示例】** 日增 1 亿短链，保留 5 年 → 约 1800 亿条。每条 60B → 10TB 级 → 需分库分表。跳转 QPS 峰值假设 10 万/s → 读靠缓存扛，写 1 千/s 轻松。

**【核心设计：短码生成】**
- 方案 A：自增 ID + Base62（0-9a-zA-Z）：62^6 ≈ 568 亿，6 位足够。**问题**：可预测（竞品爬你全量链接），需加混淆（不可逆置换/异或扰动）或随机。
- 方案 B：哈希（MurmurHash）+ 冲突解决：冲突时重哈希或加长；查重成本高。
- **推荐**：发号器（号段模式，类似 Leaf）+ Base62 + 扰动；发号器天然分片可水平扩展。
- **62 进制换算要会现场演算**。

**【跳转设计】**
- 302（临时重定向，可统计点击）vs 301（永久，浏览器缓存省服务但失去统计）——业务要统计选 302；
- 链路：CDN/边缘节点（Top 热链）→ 网关 → 多级缓存（本地+Redis）→ DB 兜底；
- 缓存 key：短码，value：长链；穿透防护：不存在短码缓存空值 + 布隆过滤器。

**【存储】** 短码分库分表（短码哈希分片）；归档：过期短链冷存。

**【难点与代价】** 发号器单点风险（号段预取+多实例）；短码冲突率 0（发号器保证唯一）；恶意刷短链（风控+限额）。

## 9.2 题二：设计一个秒杀系统（必考）

**【需求澄清】** 10 万商品库存，瞬时 100 万 QPS；不允许超卖；允许排队 10 秒内；防黄牛。

**【分层削峰漏斗（核心答案，必背）】**
1. **前端/CDN**：静态页 CDN 化、按钮置灰防重复点击、答题验证码削峰 + 防机器人；
2. **网关层**：限流（令牌桶按库存量配额）、风控（IP/设备指纹黑名单）、只有"有资格"的请求才往后走；
3. **Redis 预扣库存（第一道正确性闸门）**：Lua 脚本原子判断+扣减，`DECR` 后 <0 则拒绝并回补；单 Redis 分片扛 10 万 QPS，热 key 分片（库存拆 100 份逻辑桶）；
4. **MQ 异步下单**：预扣成功发消息，消费端按 DB 能力限速消费，真正落订单+DB 库存扣减（同本地事务）；
5. **DB**：`update stock set n=n-1 where id=? and n>0` 条件更新防超卖；热点行用库存分段。
**一致性闭环**：Redis 预扣 ≠ 最终库存，**对账任务**核对 Redis 桶与 DB，差异回补；用户支付超时回滚库存（延迟消息触发 + 幂等回补）。

**【防超卖三道锁】** Redis 原子扣（挡并发）→ MQ 串行化 → DB 条件更新（最后防线）。

**【用户体验】** 排队页面轮询结果（结果缓存于 Redis）；售罄即时返回（本地标记）。

**【量化叙事】** 100 万请求 → 网关限流后 20 万 → Redis 挡下 10 万成功预扣 → MQ 5000 TPS 消费 → 20 秒内全部下单完成，DB 峰值 CPU <60%。

## 9.3 题三：设计 Feed 流（微博/朋友圈信息流）

**【需求澄清】** 关注关系 + 推/拉模式选择；Feed 数量；时间序 vs 排序。

**【核心设计：推模式 vs 拉模式】**
- **推（写扩散）**：发布时写入所有粉丝的收件箱（Redis ZSet，score=时间戳）。读 O(1) 快；**大 V 问题**：亿级粉丝写扩散爆炸。
- **拉（读扩散）**：读时聚合关注人的发件箱。写 O(1)；读慢（聚合 N 个关注者），缓存命中差。
- **混合推拉（工业标准）**：普通用户推（粉丝 <10 万），大 V 拉（读时聚合）；粉丝极多的场景大 V 内容单独缓存（内容不易变，重排序轻）。
- **存储**：收件箱 Redis ZSet（截断保留最近 3000 条，翻页走归档存储 Timeline 服务）；发件箱（个人主页）全量存 DB+缓存。
- **一致性**：推拉混合的去重（发布 ID 唯一）+ 已读游标。

**【难点】** 缓存淘汰策略（收件箱 LRU + 写扩散预算）；热点事件（某明星发布 → 拉流量爆炸）→ 大 V 发件箱预热缓存；翻页深度限制（社交产品仅允许浅翻页，工程上是合理的业务约束）。

## 9.4 题四：设计一个抢红包系统（微信红包）

**【需求澄清】** 100 元拆 10 份、1 万人抢；不能超发；抢到即到账或可领取；高并发窗口秒级。

**【核心设计】**
1. **拆分时机**：发红包时**预拆分**（二倍均值法：每次抽剩余均值×2，最后一份拿剩全部——现场要会推公式）生成 N 个子红包记录，**发红包时一次性落库**（金额预冻结）；
2. **抢红包**：Redis Lua 原子"检查+扣子红包池"（SET 存剩余子红包 ID，SPOP 弹出）；成功者记录"已获得待领取"；
3. **领取**：抢到的人异步领取入账（MQ），同账户体系事务；24h 过期退回（延迟消息 + 幂等退回）；
4. **正确性**：预拆分使"抢"变成从池子里取唯一元素，天然不超发；DB 层金额冻结+流水对账（资金三道闸，见第 5 章）；
5. **性能**：单红包抢并发被 Redis 分片 + 预拆池子摊薄；群红包热点天然分散（每群一个池）。

**【难点】** 金额精度（分单位整型计算，绝不用浮点）；抢与领分离（抢轻量高并发、领重但稀疏）；微信实际方案的公开资料（预分配 + 一拆二随机算法演进）可作谈资。

## 9.5 题五：设计一个支持亿级用户的排行榜（如游戏积分榜）

**【需求澄清】** 全服榜/分区榜、实时性要求、Top N 展示 vs 个人排名查询。

**【核心设计】**
- **Top N（亿级用户取前 100）**：Redis ZSet 只放**候选池**（分数可能进 Top 的活跃用户，配合"分数门槛"，普通用户分数低于门槛不入池）；ZSet 命令 ZINCRBY/ZREVRANGE O(logN)；
- **个人排名**：ZREVRANK 对池内用户 O(logN)；**海量普通用户排名不能全放 ZSet**（内存爆炸）——近似排名：按分数分桶统计（每个桶内人数）+ 前缀和 → O(1) 算出"你打败了 98.7% 的玩家"；
- **精确排名需求**：分片 ZSet + 两级（全球榜按大区分片）或上 OLAP 引擎（ClickHouse 预聚合）；
- **更新吞吐**：积分写入先进 MQ/批量管道，聚合后更新 ZSet（写合并，ZSet 单 key 更新 10 万/s 上限，热榜分桶：按分数段/时间段分 key 滚动）；
- **归档与重置**：日榜/周榜滚动 key（rank:20261111），过期归档。

**【难点】** ZSet 单 key 热点（更新与读取都集中）→ 分桶滚动榜；并列名次处理（score 拼时间戳次级排序）；作弊分数（风控侧清洗后才入榜）。

## 9.6 高并发三板斧与性能方法论（背诵模块）

### 性能优化通用武器库（先讲思路再讲技术）
1. **缓存**：多级缓存、热点预热（带宽最大的优化，命中一次省一次 DB）；
2. **异步**：MQ 削峰、CompletableFuture 并行调用（RT = max(下游) 而非 sum）；
3. **池化**：连接池/线程池/对象池（复用昂贵资源）；
4. **批量**：批量读写合并网络往返（N 次 RPC → 1 次）；
5. **并行/分片**：数据分片水平扩展、计算分片（热点桶）；
6. **压缩与裁剪**：响应裁剪（只返回需要的字段）、gzip/protobuf；
7. **预计算**：写时算好（排行桶、宽表、物化视图），读时零计算。

### RT/QPS/线程数的三角关系（背公式）
- QPS = 线程数 / 平均 RT（同步阻塞模型）；
- 线程数 = QPS × RT；QPS 固定 RT 上升 → 线程数需求上升 → 线程切换开销上升 → RT 更高（死亡螺旋，故障的经典机理）；
- 排查口诀：**RT 涨了先看下游与 GC，别急着加机器**。

### 高并发系统设计十大军规（速记）
1. 读写分离，读走缓存；2. 无状态水平扩展；3. 削峰填谷宁等勿崩；
4. 热点必须打散或下沉本地；5. 一切写操作幂等；
6. 降级开关常备且演练过；7. 容量按峰值 2 倍规划；
8. 大对象（大 key/大事务/大查询）是万恶之源；
9. 监控先行，无观测不优化；10. 10 倍冗余思考，2 倍容量落地。

## 9.7 压轴开放题：你们系统的性能是怎么一步步做上去的？（复盘叙事）

**【参考叙事模板（STAR 变体，背结构）】**
1. **背景**：业务量级（日活/QPS/数据量）+ 性能目标（P99 RT、可用性）；
2. **基线**：改造前指标（P99 800ms，DB CPU 85%，大促前 3 周压力）；
3. **排查**：APM trace 定位 top3 慢点（串行 RPC ×3、无缓存的全量查询、GC 停顿）；
4. **动作**（对应三板斧）：并行化改造（RT 800→350ms）→ 引入多级缓存（DB QPS -70%）→ JVM 参数与代码修复（GC 停顿 -60%）→ 网关限流预案；
5. **验证**：全链路压测通过 3 倍峰值；P99 从 800ms 到 120ms；
6. **沉淀**：性能门禁接入 CI（接口 RT 基线）、缓存使用规范、容量评审流程。
**关键**：每一步都有"为什么是这个方案、放弃了什么"，而不是技术罗列。

## 9.9 一页速记卡

1. 场景题五步：澄清→估算→主干→难点→演进；先问规模再画图。
2. 秒杀漏斗：CDN/风控 → 网关限流 → Redis 预扣 → MQ 削峰 → DB 条件更新 → 对账。
3. 防超卖：Redis 原子 + DB `n>0` 条件更新 + 幂等回补。
4. Feed 混合推拉：小 V 推、大 V 拉、收件箱 ZSet 截 3000 条。
5. 红包：发时预拆（二倍均值）、抢时取池、领时异步、过期退回；金额用分。
6. 排行榜：Top N 用 ZSet 候选池，全民排名用分桶前缀和。
7. QPS = 线程数/RT；RT 涨→线程涨→切换涨→RT 更涨（死亡螺旋）。
8. 优化优先级：缓存 > 异步并行 > 批量 > 分片 > 换语言。
9. 一切写幂等；降级开关要演练过才算数。
10. 大对象三宗罪：大 key、大事务、大查询。

## 9.5a 增补场景题（v1.1 扩充）

### 题 9.5a.1：设计一个分布式任务调度平台（xxl-job 类）

**【需求澄清】** 十万级任务数、秒级到天级周期、分片并行任务（如按城市跑批）、不重复执行、失败重试与告警。

**【核心设计】**
1. **调度中心与执行器分离**：中心管"什么时候调、调谁"，执行器只管"怎么跑"——中心无状态可水平扩，任务元数据存 DB+缓存；
2. **防重复调度的核心**：分片锁——每个任务按分片算法（hash(任务ID+分片序号)）只归属一个调度节点，节点宕机靠 DB 行锁/Redis 抢占+心跳重新分配（"抢占式选举"）；
3. **执行模型三层**：单机任务（任意选一台）→ 广播任务（每台都跑，各自处理本地分片）→ 分片任务（中心按分片参数下发，执行器自取分片并行）；
4. **可靠性闭环**：失败重试（指数退避）→ 死信告警 → 手工重跑入口；任务超时熔断；执行器上报心跳防"僵尸任务"；
5. **大任务量优化**：调度触发器分桶扫描（DB 分页+延迟削峰，避免整点雪崩）、任务编排 DAG（依赖上游成功）。

**【难点追问】**
- 中心单点怎么办？→ 中心集群+分布式锁抢分片，DB 为最终裁决源；
- 任务跑一半执行器宕机？→ 执行器幂等（任务 ID+分片序号做唯一键）+ 中心超时重派；
- 万级任务同秒触发？→ 触发时间打散（随机秒偏移）+ 调度节点按分片认领。

**【P10 加分项】** 上升到"任务调度是平台的成本中心"：按优先级分池调度、大促期间业务任务让路给核心任务、全平台任务执行时长报表——调度平台的价值不是"能跑"而是"可控可治理"。

### 题 9.5a.2：设计电商优惠券/营销系统（发放 + 核销 + 防刷）

**【需求澄清】** 万人同时抢限量券、券规则复杂（满减/折扣/叠加互斥）、核销与退款联动、防黄牛套现。

**【核心设计】**
1. **发放漏斗**（复用秒杀骨架）：风控前置（设备指纹/频次限制/黑名单）→ Redis 原子扣减券池（Lua 判库存+扣减+写"待发放"标记）→ MQ 异步落库（券码生成+用户券记录，同事务）→ 用户中心页轮询结果；
2. **券模型**：券模板（规则：门槛/适用商品/互斥组/有效期）+ 用户券实例（状态机：未用→已用/已过期/已锁定——**锁定状态**给"下单占券未支付"用，超时回滚）；
3. **核销一致性**：下单锁定券（状态机 CAS）→ 支付成功核销 → 支付失败/退款解锁或返还；券核销与订单状态用**本地消息表/SAGA** 最终一致（呼应第 7/8 章）；
4. **防刷三道闸**：领券侧（实名/频次/设备聚合风控）、使用侧（订单金额与券规则二次校验——**不能信任下单时校验**，支付前再校验一次规则）、审计侧（券流水全量可追溯 + 异常核销率告警，同一设备/收款账户聚合度检测）；
5. **资金侧兜底**：营销费用预算表（券成本入预算账）+ T+1 对账（发券量/核销量/费用对平），差异冲正。

**【难点追问】**
- 叠加互斥怎么算？（互斥组模型：券之间声明 group，同 group 互斥；计算顺序固定：先单品后订单，固定算法版本防"算价漂移"）
- 券池和库存系统什么关系？（券是"有限资格"不是商品库存——用资格池模型，超卖后果是资金风险而非履约风险，所以对账比秒杀更严）
- 大促预热？→ 规则与券池提前加载 + 压测（回放真实核销流量）+ 降级预案（高并发时段改"报名抽签发放"削峰）。

**【P10 加分项】** 营销系统是"资金敏感度被低估的系统"：一句话点题——"秒杀超卖损失的是履约，券超发损失的是真金白银，所以营销系统要按资金系统标准建（幂等/对账/审计三件套，见第 5 章 5.4.1）。能把这两类系统的风险等级区分开，是业务判断力的体现。"
