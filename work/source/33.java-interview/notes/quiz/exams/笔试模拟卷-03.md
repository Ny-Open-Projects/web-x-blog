# 参考答案与解析（自测后再看）

**1.1**（来源 spring）
**答案：B**
**解析：** @Autowired 按 byType 注入多个候选时需 @Primary 或 @Qualifier 消歧。原因：按类型找到多个候选先看 @Primary 再按字段名匹配，都不确定抛 NoUniqueBeanDefinitionException。

**1.2**（来源 mysql）
**答案：A**
**解析：** innodb_io_capacity 告诉 InnoDB 磁盘能力（SSD 建议 2000+）。原因：刷脏速率匹配磁盘吞吐，设置过低脏页堆积触发"连击"刷脏引发性能抖动（ wal 快满时激进刷盘）。

**1.3**（来源 redis）
**答案：A**
**解析：** ZSet 延迟队列：score 存执行时间戳，轮询 zrangebyscore 取到期任务。原因：本项目实现并实测的方案，优点：有序+分数范围查询天然适配，缺点：轮询间隔与并发取任务竞争（Lua/分布式锁保证）。

**1.4**（来源 mongodb）
**答案：D**
**解析：** 聚合 $sort/$group 超内存默认报错需 allowDiskUse=true 落盘。原因：100MB 限制防止拖垮节点，落盘性能下降明显，优先优化管道（前置 match/拆分阶段）。

**1.5**（来源 mq）
**答案：B**
**解析：** RocketMQ 消费失败重试 16 次（间隔递增）后进死信队列。原因：重试队列 %RETRY% 主题，间隔按延迟级别递增（10s~2h 总约 2 小时），本项目核对的次数（16 次），之后 DLQ 人工/补偿处理。

**1.6**（来源 distributed）
**答案：A**
**解析：** 服务间通信：同步（RPC，强实时）vs 异步（事件/MQ，解耦削峰），主链路同步旁路异步。原因：异步化降低耦合与 RT（上游不等下游），但引入最终一致与排查复杂度，P10 决策：强一致需求同步、可逆旁路异步、读写分离（CQRS）。

**1.7**（来源 ai）
**答案：B**
**解析：** 企业级 RAG 必须引用溯源：生成答案标注来源（文档+段落），评估与信任的基础。原因：防幻觉的用户感知手段（可点击验证），评估时对照来源判定忠实度（faithfulness），无溯源的 RAG 在企业场景不可上线。

**1.8**（来源 algorithm）
**答案：B**
**解析：** 海量判重：bitmap（int 位图 40 亿整数 512MB）、布隆过滤器（允许误判更省）。原因：1 个 int 1 bit（32 倍压缩），布隆误判率可控（位数组+多哈希），Redis bitmap/RD-009 联动，与缓存穿透方案联动。

**1.9**（来源 java-ai）
**答案：B**
**解析：** 框架选型的年度再评估：能力矩阵（JA-391 对比表）年度刷新+社区健康度（发版/issue 响应），防锁定。原因：选型不是终身（JA-039 动态化），框架演进方向变化（如合并/停滞）触发再评估，与供应商治理联动。

**1.10**（来源 agent-dev）
**答案：B**
**解析：** 消息四角色：system（宪法）/user（用户与任务）/assistant（模型输出含工具调用）/tool（工具结果），角色是协议结构。原因：角色让模型理解对话结构（谁说的/工具结果），角色混用是解析错误根源，与消息抽象（JA-076/088）对等。

**1.11**（来源 java-basics）
**答案：A**
**解析：** 对值为 null 的包装类做自动拆箱会抛 NullPointerException。。原因：拆箱编译为 xxxValue() 调用，null 调用即 NPE；三目运算符两侧类型不一致时也会触发隐式拆箱。。

**1.12**（来源 concurrency）
**答案：D**
**解析：** Executors.newCachedThreadPool 最大线程数是 Integer.MAX_VALUE 可无限创建线程。原因：SynchronousQueue 无容量不排队，来一个任务必建一个新线程，高并发瞬间创建数万线程耗尽内存与线程句柄。

**1.13**（来源 jvm）
**答案：B**
**解析：** C1 编译的代码带性能探针，采集分支/类型分布指导 C2 深度优化。原因：C1 快速出产物并收集 profile（虚方法实际实现/分支频率），C2 基于真实分布做激进优化（单态内联/分支消除），这是分层编译收益的机制来源。

**1.14**（来源 spring）
**答案：A**
**解析：** Spring 事件机制：ApplicationEventPublisher 发布、@EventListener 监听默认同步执行。原因：监听器在发布线程内执行（同调用方法一样），异常会传播回发布者，解耦发布方与消费方。

**1.15**（来源 mysql）
**答案：C**
**解析：** 冷热分离：热数据（近 N 月）在线库，冷数据归档库（压缩表/对象存储），查询路由按时间。原因：在线库保持小容量（索引高效），归档按 partition drop 秒级清理，归档库查询走专门服务。

**2.1**（来源 redis）
**答案：B**
**解析：** 正确表述应为——Redis 事务 MULTI/EXEC 队列化执行不支持回滚。原因：命令入队时语法错误整个事务不执行，运行时错误（如对 string 执行 LPUSH）不回滚继续执行后续命令，官方认为回滚无必要（编程错误场景）。

**2.2**（来源 mongodb）
**答案：A**
**解析：** 正确表述应为——分片三层架构：mongos（路由）→config 副本集（元数据）→shard（每个是副本集）。原因：mongos 无状态可扩容，config 存 chunk 分布元数据，shard 是普通副本集参与分片，各层独立伸缩。

**2.3**（来源 mq）
**答案：A**
**解析：** 正确表述应为——消息体设计：最小化（ID+事件类型+时间戳+必要上下文）、可追溯（traceId/消息 ID）、可扩展（版本字段）。原因：消息体塞全量业务数据（大且耦合 schema），消费方需要就回查源库（事件通知模式），版本字段兼容消费方升级。
