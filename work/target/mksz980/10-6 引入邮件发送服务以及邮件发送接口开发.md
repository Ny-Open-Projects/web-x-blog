# 10-6 引入邮件发送服务以及邮件发送接口开发

## 【学习目标】

学完本节，应当能够：

- 把上一节点生成的 Excel `File` 以 `excelFile` key 回流状态机，并为其配置替换（Replace）策略；
- 新建 `SendEmailNode`，用 `state.value("excelFile")` 的 `Optional` 重载做「有附件 / 无附件」分支；
- 引入 `spring-boot-starter-mail` 并完成邮件发送配置；
- 把邮件发送拆成 `EmailService` 接口，理解「节点管编排、service 管执行」的分层理由。

## 【正文】

第二个节点生成的 Excel 文件并没有放进状态机，下一个节点拿不到它。所以这一节先开发第三个节点，发送邮件，把 Excel 发给提问人，同时把文件回流到状态机。

### 一、把 Excel 文件存回状态机

在第二个节点里定义一个 key `excelFile`，它的 value 不再是 `String` 或 `int`，而是一个 `File` 对象，直接把生成的 Excel 文件放进状态机。相应地，也要回到图（Graph）定义里为该 key 配置 value 策略，这里继续用「替换策略」。

状态机的 value 策略决定了「同名 key 被多个节点写入时会发生什么」：替换策略（`ReplaceStrategy`）下后写覆盖先写，累加策略下则保留全部历史。`excelFile` 用替换策略是自然的选择，一次请求只应有一份最新报表，历史文件留着只会干扰下游判断。

这里还有一个常被问到的设计点：**为什么不把 Excel 重新生成一遍，非要放状态机？** 因为生成动作有成本（查库 + POI 构建 + 写盘），更因为「生成结果」本身就是前一个节点的确定产出。节点之间通过状态机传对象，是工作流引擎的基本协作方式，每个节点只取自己关心的 key，只写自己负责的 key，彼此不需要知道对方的内部逻辑。放到 Web 开发的语境里，状态机相当于请求上下文（Request Context），`excelFile` 就是上下文中传递的业务产物。

由于第二个节点生成 Excel 不太好单独测试，我们干脆先把第三个节点（发送邮件）写完，再做全链路测试。

### 二、创建邮件发送节点

在 `nodes` 包里新建 `SendEmailNode`，实现 `NodeAction` 并重写 `apply` 方法。业务逻辑很清晰：

1. 拿到上一个节点生成的 Excel 文件；
2. 通过邮件发送器把邮件发出去。

#### 业务逻辑梳理

**1. 获取 Excel 文件**：前面取值都是 `state.value(key, defaultValue)`，这里换用另一个重载，只传 key `excelFile`。拿到的是 `Optional<Object>` 包裹的对象，正好可以用它来判空。

两个重载的分工很清晰：`value(key, defaultValue)` 适合「上游一定写入了该 key，缺了就是异常」的场景，给个默认值让链路不炸；`value(key)` 返回 `Optional`，适合「该 key 可能本来就不存在」的场景，查询结果为空时，`ExecSQLAndCreateExcelNode` 直接抛异常，`excelFile` 压根不会进状态机。用 `Optional` 而不是判 `null`，是把「可能缺失」编码进了类型里，编译器会提醒你必须处理空分支。

**2. 判空分支**：如果 Excel 文件为空，就只发纯文本邮件（不带附件）；如果有 Excel 文件，则发带附件的邮件。

为什么要做该分支？因为查询结果为空时（用户问的内容在数据库里确实没有对应数据），我们也应该通知用户「当前没有查到数据」，而不能什么都不返回，否则用户会以为系统出故障了，一直拿不到结果。

```java
package com.carl.ai.helper.nodes;

import com.alibaba.cloud.ai.graph.OverAllState;
import com.alibaba.cloud.ai.graph.action.NodeAction;

import java.util.Map;

/**
 * @description: 发送邮件节点
 * @author: carl
 * @createDate: 2025-12-04 21:00
 * @since: 1.0
 */
public class SendEmailNode implements NodeAction {
    @Override
    public Map<String, Object> apply(OverAllState state) throws Exception {
        Optional<Object> excelFile = state.value(key: "excelFile");
        if (excelFile.isEmpty()) {
            return Map.of();
        } else {
            // excel文件则发送邮件的操作
            return Map.of();
        }
    }
}
```

```mermaid
flowchart TD
    A[SendEmailNode.apply] --> B["state.value(excelFile)<br/>返回 Optional&lt;Object&gt;"]
    B --> C{Optional 为空?}
    C --|是: 查询无结果| D["sendEmail(to, 查询数据不存在)<br/>纯文本通知"]
    C --|否: 报表已生成| E["强转为 File"]
    E --> F["sendEmailWithAttachment(to, file)<br/>带附件邮件"]
    D --> G[return Map.of 链路到 END]
    F --> G
```

该分支在产品层面很重要：Agent 系统的「静默失败」是最伤用户体验的模式。用户问了一个查无数据的问题，如果系统什么都不返回，用户无法区分「没查到」和「系统挂了」，只会反复重试。发一封「查询数据不存在」的纯文本邮件，把系统的确定状态明确告知用户，哪怕结果是负向的。Agent 设计里有个朴素原则：**任何终态都要给用户一个可感知的交代**。

### 三、引入邮件依赖与配置

当前 `pom.xml` 没有邮件相关依赖，添加 `spring-boot-starter-mail` 并刷新，没有报错。然后到配置文件里补上邮件发送配置：直接把之前「智能库存调拨优化系统」里配好的邮件配置复制过来，放在数据库配置下面即可（邮件服务的具体配置方式在此前的 Agent 里已讲过）。

```yaml
spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:mysql://localhost:3306/bi-helper?useUnicode=true&characterEncoding=utf-8&useSSL=false&serverTimezone=Asia/Shanghai
    username: root
    password: 123456
mail:
  host: smtp.qq.com
  port: 587
  username: 152761478@qq.com
  password: efwwvmpklycjg
  properties:
    mail:
      smtp: true
      starttls: enable: true
      required: true
server:
  port: 8877
logging:
  level:
    com.carl.ai: debug
```

`spring-boot-starter-mail` 的自动装配会创建一个 `JavaMailSender` bean，这是下一节 `EmailServiceImpl` 直接注入的对象。配置项里两个要点：`port: 587` 配合 `starttls` 是 SMTP 提交邮件的标准组合（先明文建连再升级 TLS）；`username`/`password` 位对 QQ 邮箱而言填的是「授权码」而非登录密码，需在邮箱设置中开启 SMTP 服务后获取。另外注意上面这段是抽取出的片段，`starttls: enable: true` 的嵌套写法有噪音，正确层级是 `spring.mail.properties.mail.smtp.starttls.enable: true`，实际配置时以 Spring 官方属性结构为准。

### 四、拆分出邮件服务

邮件发送涉及不少代码，不要全堆在节点里，而是抽到一个 `service` 中，节点只负责引入并调用。新建 `EmailService` 接口，再写实现类 `EmailServiceImpl` 并加 `@Service` 注解；节点里定义 `EmailService` 属性并通过构造方法注入。

接口里定义两个方法：

1. `sendEmail(String to, String content)`：发送纯文本内容邮件；
2. `sendEmailWithAttachment(String to, File file)`：发送带附件的邮件。

定义好接口后，下一节在实现类里把这两个方法落地。

```java
package com.carl.ai.helper.service;

/**
 * @description:
 * @author: carl
 * @createDate: 2025-12-04 21:06
 * @since: 1.0
 */
public interface EmailService {
    // 发送文本内容的邮件
    void sendEmail(String to, String content);
}
```

分层的收益在测试时兑现：`SendEmailNode` 的编排逻辑（判空、分流）可以用一个 mock 的 `EmailService` 单测，完全不碰 SMTP；而 `EmailServiceImpl` 的发送细节（MimeMessage 组装、附件、异常处理）也可以独立验证。如果把两摊代码揉在节点里，任何一次测试都要背上真实的邮件服务器。接口先行（这里只定义了一个方法，另一个在下一节补齐）也是惯例：先把调用方的契约定下来，实现类照着契约长。

## 【易错点 / 面试题】

1. **面试官问：「File 对象放状态机，和放成员变量/静态缓存有什么区别？」**
   答：状态机是本此请求（conversation/execution）的上下文，随执行流自然流转、随执行结束销毁，不存在跨请求串数据的问题；成员变量在单例节点里会被并发请求互相覆盖，静态缓存则有生命周期与清理难题。工作流产物走状态机，是确定性和并发安全兼得的做法。

2. **易错点：忘记给新 key 配置 value 策略。** `excelFile` 不在 `KeyStrategyFactory` 里注册，节点写入时可能直接报错或行为不可预期。新增状态 key 时，「写代码」和「注册策略」必须同步完成，这也是 10-8 编排工作流时要补的一环。

3. **面试官问：「邮件发送失败（SMTP 超时/拒收），链路怎么处理？」**
   答：至少三层：节点内 try-catch 记日志并明确抛错（本节实现的做法）；对 `EmailService` 加重试与熔断（生产上可引入 resilience4j 这类库，本课程工程 `980-demo` 对 LLM 调用正是这么封装的，见 `980-demo/src/main/java/com/carl/ai/transfer/extract/TransferOrderExtractor.java` 上的 `@CircuitBreaker`）；对通知类诉求进一步改异步，避免外部 SMTP 拖垮主链路。

## 【小结】

本节完成了第三个节点的骨架与外部依赖：`excelFile` 以 `File` 形态回流状态机并配置替换策略，`SendEmailNode` 用 `Optional` 重载做出「无数据发文本、有数据发附件」的分支，`spring-boot-starter-mail` 提供 `JavaMailSender` 自动装配，邮件发送逻辑被拆到 `EmailService` 接口之后。判空分支的设计体现了 Agent 的终态原则：**任何结果都要给用户一个明确交代，包括「查无数据」这种负向结果**。下一节在 `EmailServiceImpl` 里落地两个发送方法，把 MimeMessage、附件、异常处理写完整。

对照本课程第 5 章工程 `980-demo/` 的同层设计：`980-demo/src/main/java/com/carl/ai/transfer/controller/TransferController.java` 与 BI 系统的 `GenSQLController` 同为「HTTP 入口接收自然语言、触发一次 Agent 执行」的形态；`980-demo/src/main/java/com/carl/ai/transfer/service/TransferOrderServiceImpl.java` 与本节的 `EmailService` 同为「节点只管编排、确定性执行下沉 service」的分层范本，区别只在于 BI 把执行结果发去邮箱，调拨系统把执行结果写进 H2（`repository/BbTransferOrderRepository.java`）。
