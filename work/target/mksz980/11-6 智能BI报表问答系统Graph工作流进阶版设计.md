# 11-6 智能BI报表问答系统Graph工作流进阶版设计

## 【学习目标】

学完本节，应当能够：

- 说清初级版评估节点「判死不闭环」的局限，以及进阶版要补的三样能力：条件边、回环边、循环上限；
- 画出进阶版工作流全图，并解释三个出口（回退重生成、放行执行、超限终止）各自的触发条件；
- 向面试官讲清「为什么必须限制循环次数」，以及上限值该放在代码里还是配置里；
- 把「数据驱动控制流」的设计思想迁移到其他 Agent 链路。

## 【正文】

初级版本的评估节点已经开发完成，也验证过效果：生成的 SQL 评估通过会返回 `pass`，不通过则返回 `fail`。但初级版本有一个绕不开的能力缺口，当 SQL 被评估为 `fail` 时，它只能「判死」，并不能让流程真正闭环。本节先把进阶版的「执行图纸」画出来，把「评估不通过就重生成」这件事设计到位，后续章节再落到代码。

### 一、初级版的局限：fail 之后流程断在哪里

初级版的节点链路是单向的：

`START → 生成SQL → 评估 → 执行SQL → 发送邮件 → END`

评估节点只负责打分。评出 `fail` 之后，流程就断在这里，没有任何一条边把流程带回到生成节点，模型没有第二次机会。翻译成生产语境：一次评估失败等于一次任务失败，用户拿到的是失败，而不是一次重试后的成功。

这里要先建立一个认知：**大模型生成 SQL 本质是一个有噪声的采样过程**。Temperature 大于 0 时，同一套表结构、同一个问题，模型这次漏掉 JOIN 条件，下次漏掉 GROUP BY，都很正常（11-8 节会专门讲 Temperature）。评估结论 `fail` 只说明「这一次采样不合格」，并不说明「该任务不可完成」。正确的姿势是重新采样，而不是直接判死。高级能力要回答的问题不是「怎么判得更准」，而是「判不准的时候怎么办」：

> 如果大模型生成的 SQL 被评估节点判为 `fail`（没通过），就应该**回退到生成 SQL 的节点**，让大模型重新生成一条 SQL，再重新进入评估节点；评估通过后才进入下一个节点（执行 SQL、生成报表、发邮件）。

从用户视角看，差别更直接：初级版遇到一次失败的采样就交白卷，用户重试一次又要完整等一轮链路；进阶版把重试消化在链路内部，用户侧只感知到「得到回答」的时长略长。Agent 的体验优化，很多时候就来自这类「把不确定性关在链路里」的设计。

两个版本的能力差异可以归纳成一张对照表：

| 维度 | 初级版 | 进阶版 |
|---|---|---|
| 评估失败后的走向 | 断链，无出路 | 回退到生成 SQL 节点重生成 |
| 重试次数控制 | 无 | 有上限，超限直接终止 |
| 控制流驱动方 | 静态边，编译期写死 | 状态机数据（`evaluateResult` / `loop`） |
| 链路形态 | 开环管道 | 条件闭环 |

这不是一套新发明的机制。**智能库存调拨优化系统**里就出现过条件边，人类审核节点那里，审核结论同样是在运行期决定流程往哪走。本次进阶版相当于把同一模式从「人工决策」扩展到「机器自检」：审核的是 SQL 质量，执行回退的是同一张图。设计上可复用的先例，工程上要补齐的只有循环上限这一块刹车。

### 二、进阶版工作流：评估 + 条件边 + 循环

进阶版比初级版只多两样东西：一个「SQL 评估节点」和一条**条件边**。但正是这条条件边，把链路从「管道」变成了「环」。整体链路如下：

1. `开始` → **RAG 检索生成 SQL**（即大模型生成 SQL 节点）；
2. 生成 SQL → **SQL 评估节点**；
3. 评估节点通过条件边判断结果：
   - 如果是 `fail`，沿回环边（标注 `GenSQL`）回到「RAG 检索生成 SQL」节点，重新生成 SQL，再次进入评估；
   - 如果是 `pass`，沿 `execSqlAndCreateExcelNode` 边走到「执行 SQL」，接着「发送邮件」 → `结束`。
4. 另外从评估节点还有一条标注 `END` 的线，用于在需要终止时直接结束流程。

把这张「执行图纸」用 mermaid 画出来：

```mermaid
flowchart TD
    S([START]) --> G["RAG 检索生成 SQL<br/>GenSQLNode"]
    G --> E{"SQL 评估节点<br/>EvaluateNode"}
    E -- "pass" --> X["执行 SQL 并生成 Excel<br/>ExecSQLAndCreateExcelNode"]
    E -- "fail 且未超限" -->|回环边 GenSQL| G
    E -- "loop 达到上限" --> Z([END])
    X --> M["发送邮件<br/>SendEmailNode"] --> Z
```

三个出口的语义值得逐一盯住：

- **pass → 执行**：唯一「往前走」的分支，评估结论成为放行依据，控制流第一次由数据说话；
- **fail → 回退**：把控制权交还给生成节点，形成「生成 → 评估 → 再生成」的循环体；
- **超限 → END**：循环的刹车，见下一节。

换言之，第一次评估 `fail` 就退回重生成、再评估；第二次如果 `pass`，就往后走执行 SQL、发邮件、结束。同一个评估节点，依据状态机里的数据走出三条完全不同的路，这就是「数据驱动控制流」：编译期不再决定「下一步去哪」，运行期由状态说话。

### 三、必须加循环次数限制

有一个绕不开的问题：如果 SQL 一直评估不通过，流程就会通过条件边无限回退到生成节点，形成**死循环**。死循环危害很大：

- 非常消耗资源，大模型会一直被这条链路占着，影响它处理其他任务；
- 任务一直挂在这里，其他业务代码执行也会受影响。

往深处拆一层：每一次「生成 → 评估」循环都是一次真实的 LLM 调用，花钱、花时间、占连接。没有刹车的循环等于把模型当成免费资源，它不仅烧钱，还会把连接、线程、邮件发送配额全部拖死，最终波及同一实例上的其他业务。这和一个失控的重试策略没有区别：HTTP 客户端无限重试会把下游打挂，消息无限重投会把队列堵死，Agent 循环无限回退会把模型连接耗尽。

所以一定要在评估节点里加「循环次数限制」：每次进入评估节点时，先判断这条 SQL 已经被评估了多少次；如果达到了设定的循环上限，就**直接结束流程**，不再往后走、也不再回退循环，把资源释放掉。

该设计有一个更通用的名字，**重试预算**。重试预算的思想在分布式系统里随处可见：客户端的最大重试次数、消息队列的最大重投次数、熔断器的探测窗口，内核思想一致，允许系统「再试一次」，但绝不允许「无限试下去」。上限该设多大？11-9 节给出的经验区间是 3 到 5 次，没有固定规范，需要结合实际测试微调；课程同时留了作业：把循环次数放到 **Nacos** 配置里支持动态更新。理由很直接，一开始你未必知道循环几次合适，太大浪费性能，太小又可能生成不出准确的 SQL，配置化才能按业务持续调。

三个设计决策点归纳如下：

| 决策点 | 可选方案 | 本节选择 | 理由 |
|---|---|---|---|
| 回退目标 | 生成节点 / 执行节点 | 生成节点 | 只有重新生成才可能改变评估结论，回到执行节点毫无意义 |
| 终止判断位置 | 评估节点内 / 条件边内 | 两处协同 | 评估节点负责累加 `loop`，条件边负责按次数路由，读写分离 |
| 上限配置 | 写死常量 / 配置中心 | 先常量跑通，再下沉 Nacos | 与「预值放配置」的既有做法一致，支持不重启调整 |

## 【易错点 / 面试题】

1. **面试官问：「评估失败为什么要回退到生成节点，而不是直接把失败返回给用户，让用户重试？」**
   答：用户重试的成本远高于系统重试。系统回退是确定性的、可观测的、有预算的（循环上限兜底），用户侧无感知；把失败抛给用户，等于把重试责任和重试策略都推给使用方，体验和成本都更差。Agent 的价值就在于把「一次采样失败」消化在链路内部，对外仍然呈现为一次完整任务。

2. **面试官问：「循环上限设 5 和设 50 有什么区别？怎么定？」**
   答：上限决定「成本天花板」与「任务成功率」的交换。设 5，最多 6 次 LLM 调用，成本和时间可控，但可能错杀本可成功的难题；设 50，理论成功率更高，但单任务成本和时间都可能失控，还会长期占用模型连接影响其他任务。课程给的经验区间是 3 到 5 次，且应放到配置中心（Nacos）按业务微调，而不是写死在代码里。

3. **易错点：只加回环，不加终止出口。** 回环边与终止边必须成对出现。只有「fail → 生成节点」的回环、没有「超限 → END」的出口，条件边便永远等不到返回 `StateGraph.END` 的分支，死循环必然发生。设计条件边时先问自己：每条路径的尽头是什么？

4. **易错点：把循环上限的判断放在评估业务之后。** 次数检查必须发生在「这次评估要不要做」之前，进了评估节点第一件事就是看 `loop` 是否已超限。顺序反了，超限的那一次仍然会实打实调用一次模型，预算就漏了一个口子。

## 【小结】

本节给出了进阶版的执行图纸：RAG 生成 SQL → 评估节点（带条件边与循环上限）→ 通过则执行并发送报表、不通过则回退重生成、超限则终止。核心变化是控制流从「编译期写死的静态边」升级为「运行期由 `evaluateResult` 与 `loop` 驱动的条件闭环」。下一节基于这张图纸改造评估节点，把条件边和循环限制落到代码。同款「有刹机的闭环」思想在配套工程 `980-demo` 中也有对应：`980-demo/src/main/java/com/carl/ai/transfer/extract/TransferOrderExtractor.java` 用 resilience4j 的 `@CircuitBreaker` 给 LLM 抽取调用加熔断降级（`extractFallback` 返回空 param，由上层决定是否抛业务异常），`980-demo/src/main/java/com/carl/ai/transfer/agent/TransferAgent.java` 在抽取结果为空时返回明确的失败文案而不是继续往下走，评估节点用循环上限防「无限重试」，工程用熔断与判空防「无限失败」，守的都是同一条资源防线。
