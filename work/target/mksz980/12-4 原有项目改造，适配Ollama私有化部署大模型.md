# 12-4 原有项目改造，适配Ollama私有化部署大模型

## 【学习目标】

- 独立完成「Ollama 拉模型 → 项目依赖切换 → base-url 改远程 → 全链路调用验证」的完整闭环。
- 说清 OpenAI 兼容协议在私有化部署中的作用：为什么换模型供应商只改配置不改代码。
- 掌握从报错信息反查节点的调试方法，理解 Ollama 方案的成本优势与并发短板及适用边界。

## 【正文】

上一节已经在 AutoDL 服务器上把 Ollama 安装并启动成功。这一课回到代码，把智能库存调拨优化系统接到服务器上的 Ollama 私有化大模型：先在 Ollama 官网下载 Qwen3 8B 模型，再改造项目配置，最后完整跑一遍链路做验证。

## 一、下载并启动 Qwen3 8B 模型

来到 Ollama 官网的 models 页面。课程统一使用 Qwen3（千问三）系列大模型，这里选 5.2G 的 Qwen3 8B，直接复制它给出的命令，回到服务器终端里粘贴执行：

`ollama run qwen3:8b`

下载需要一些时间，稍作等待。等它下载完毕，模型会自动启动，终端会提示输入 message。输入「你好」试一下，它能正常回复，说明模型已经可以用了。

`ollama run` 是个二合一命令：本地没有该模型时先拉取，拉取完成后直接进入交互式对话。这也是它被称作「傻瓜式部署」的原因，拉模型和起服务是一条命令。5.2G 的体积对 4090 这类 24G 显存的卡来说非常轻松，后续还会看到，模型体积直接决定了下载成本和机器门槛，这是 12-5 选型时的重要变量。

## 二、改造项目配置：从 OpenAI 切回 Ollama

模型就绪，接下来要解决的是：如何在本地调用这台 AutoDL 服务器上部署的 Ollama。

回到智能库存调拨优化系统。之前引入过 Ollama 的依赖并测试过，后来把它注释掉、改用 OpenAI 的对话模型。现在要验证 Ollama，就把顺序倒过来：先把 OpenAI 的依赖注释掉，再把 Ollama 的依赖打开，最后刷新 Maven 让依赖生效。

配置文件同理：之前用 Ollama 的地方都注释掉了，实际跑起来的是 OpenAI，现在把 OpenAI 注掉、把 Ollama 打开。

关键改动是 base-url：之前指向本地，现在要指向远程的 AutoDL 服务器。上一节把 Ollama 的监听端口改成了 6006，而 AutoDL 控制台的「自定义服务」里正好展示着 6006 端口映射到公网的地址，复制该地址，粘贴到 base-url 里即可。

最后把模型名改成与服务器上实际部署的模型保持一致。配置改完大致如下：

```yaml
spring:
  cloud:
    ai:
      ollama:
        base-url: https://u819324-a1bb-01491aa3.westc.gpwhub.com:8443
        chat:
          options:
            model: qwen:3b
```

如实说明：原稿正文选用的是 Qwen3 8B，配置示例中的模型名却是 `qwen:3b`，两者不一致，属于讲稿笔误。配置时的原则是模型名与服务器上 `ollama list` 的实际输出严格一致，本例应为 `qwen3:8b`。另外，公网映射地址与端口因机器与租用时段而异，每次租用都要去控制台重新复制，不要照抄示例地址。

这里有一个值得展开的架构知识点：Ollama 对外提供的是 OpenAI 兼容接口，所以项目里切换模型供应商时，代码一行不用动，只改 base-url 和 model 两个配置项。Spring AI 的 OpenAI starter 连的是 OpenAI 协议的端点，Ollama 与 vLLM 都实现了该协议，于是「换模型」退化成「换配置」。这也是私有化部署章节的核心思路：用协议兼容把供应商锁定风险降到最低。

依赖切换还有两个容易漏的动作：其一，注释与打开的依赖必须成对做，只开不关会同时引入两套 ChatModel 自动配置，启动时报 bean 冲突；其二，改完 pom 必须刷新 Maven，让新依赖真正进入 classpath，否则代码用的是旧 starter，配置项根本不生效。

## 三、启动依赖与项目

智能库存调拨优化系统依赖 Redis、Nacos 和 Kafka，先在 Docker 里把这三个服务启动，再启动项目本身。项目启动时要加载的东西比较多，会稍微慢一些，启动成功后就可以发起调用了。

中间件先行是 Spring 项目的常规顺序：Nacos 承担注册配置中心，Redis 做缓存，Kafka 做异步消息。用 Docker 统一拉起的好处是环境干净、可重复销毁重建。项目启动慢通常与 Nacos 配置拉取、Kafka 消费者注册有关，属于正常现象，不要误判为卡死。

## 四、全链路调用验证

还是以调拨场景为例：E 商品、E 仓库、数量 5、日期选今天，发起一次执行，重点观察整条链路的调用过程。

链路走得很清楚：先执行商品、库存这两个查询节点，接着进入预测节点；预测完成后进入提取 JSON 的节点，最后到发送邮件。用 Spring AI Alibaba Graph 的视角看，这是「查询 → 预测 → 提取 → 执行」的线性状态机流转，每个节点是一个 `NodeAction`，状态在 `OverallState` 中逐节点传递。

```mermaid
flowchart LR
    A[商品查询节点] --> B[库存查询节点]
    B --> C[预测节点]
    C --> D[提取 JSON 节点]
    D --> E[发送邮件节点]
```

中间控制台报了一个 consumer 错误。把报错信息复制到项目里搜索，可以定位到是 agent consumer 消费时打印的日志，它拿到的是空值。但此时整个节点已经成功执行，预测和提取都已经完成，问题出在后续创建对应实体类的环节。在对应节点上打个断点重新执行，就能看到明细。

这段排障过程本身就是方法论：从报错文本反查代码位置（全文搜索报错关键字），再结合「节点已成功执行」的现象缩小范围，最后用断点确认。消费端拿到空值多半是上游消息体与反序列化目标不匹配，日志能定位到具体消费点，就已经解决了一半问题。

照此思路跟一遍：预测节点走完，提取 JSON 节点也走完，流程直接走到了发送邮件。再在发送邮件节点里打个断点，重新发起一次调拨（这次只卖 1 个），清掉之前的查询日志，等 Ollama 完成推理。用 Ollama 作为对话模型，响应会比在线 API 稍慢一些，本地单卡推理没有云端集群的并发与调度优化，属于预期内的差距。等它执行完，可以看到预测节点、执行节点依次完成，最后走到发送邮件节点，邮件成功发出。

发送邮件节点的核心逻辑，就是从状态里取出模型返回的 JSON，解析出 comment 字段作为邮件正文发出去：

```java
public class SendEmailAction implements NodeAction {
    @Override
    public String execute(OverallState state) throws Exception {
        String inventoryTransferJsonStr = state.value("inventoryTransferJson");
        JSONObject json = JSONUtil.parseObj(inventoryTransferJsonStr);
        String comment = json.getStr("comment");
        String threadId = state.value("threadId", defaultValue);
        emailService.sendTemplateEmail(to, subject, comment, threadId);
        return "success";
    }
}
```

如实说明：该代码块为原稿节选，`defaultValue`、`to`、`subject`、`emailService` 等标识符在片段中未给出声明，应理解为类成员或上下文中的既有定义。三个关键动作值得记住：从 `OverallState` 取上游节点写入的 JSON 串；用 hutool 的 `JSONUtil.parseObj` 解析；取 `comment` 字段作为模板邮件正文。

打开邮箱，智能库存调拨生成的内容已经发过来了：一封包含调拨单的邮件，模型分析出来的内容已经填了进去。这次模型返回的结构化内容大致如下：

```json
{
  "调拨方向": "华东仓向华南仓调拨",
  "调拨理由": "根据历史销售数据，华东仓在第四季度需求较高（2025年Q4销售413），而华南仓当前库存（227）相对充足，结合历史数据（2025年Q1向华东仓调拨29），需平衡区域库存以应对季节性波动。",
  "风险提示": "需监控2026年Q1华东仓是否存在满足需求，若预测增长提前补充。"
}
```

注意这份 JSON 的字段是中文键，且值是带数字引用的自然语言。它出自 5-16 调拨单提示词的输出约定，「提取 JSON 节点」存在的意义就是把模型自由文本转成这种可解析结构。在 Spring AI 2.0.1 中，同类诉求有更工程化的写法：`chatClient.prompt().user(...).call().entity(XxxParam.class)`，底层由 `BeanOutputConverter` 完成绑定，无需手写 `JSONUtil.parseObj` 和逐个取字段。两种方式的取舍在 5-16 与配套工程中都有体现：讲稿为了展示「大模型生成 JSON 再提取」的完整过程保留了手动解析；生产代码建议直接用结构化输出，减少字符串到 POJO 之间的人工环节。

最后回到数据库，打开库存调拨的记录，最新一条是 15；执行一次「采纳」操作，记录就变成了 16，相关数据也都更新到了最新。到这儿，就通过 Ollama 完成了私有化部署，让自己项目直接连上了自己服务器上的大模型。

## 五、Ollama 的好处与短板

可能有同学会问：实际公司业务里，真的会有公司用 Ollama 吗？它看起来这么「轻」。

先说观点：一项技术没有绝对的好与坏，关键要看公司的业务规模和自身条件。就像老技术的存在不该被全盘否定，新技术也是从旧技术的土壤里长出来的，没有原来的积累哪来的新东西。看待新技术、老技术，都要有辩证的思维，不要一棍子打死。Ollama 虽然有它一定的弊端，但好处也很实在。

好处主要有三点：

1. **成本低**。这里说的成本既包括价格成本，也包括时间成本。如果公司 AI 业务量很小，对大模型能力要求也不高，又不想花太多钱买算力服务器、买 GPU，完全可以买一台稍好一点的轻量级无 GPU 服务器，用 CPU 来跑 Ollama，Ollama 本身支持直接用 CPU 跑，甚至可以直接部署到公司原有的服务器上。
2. **部署快**。亲眼看到的结果是：花了不到 20 分钟，就把 Ollama 在服务器上部署完毕，项目也连上了远程服务器上的私有化大模型。
3. **改动简单**。不管是对运维还是对开发，这种改造都非常简单，时间花费很短。项目想快速上线，这会是一个比较好的方案。最核心的一点：如果公司没钱买 GPU，这套方案是非常好的选择。

短板同样明显：

1. **模型多为量化版本**。Ollama 上的这些大模型个头都不大，说得通俗一点，都是「阉割版本」，没有满血版本的大模型聪明，很多东西被裁掉了；但也正因为小，部署起来才非常快。
2. **并发支持有限**，这是它最大的问题。如果公司业务量比较大、并发也比较大，Ollama 的并发支持就不太够用了。这类「不缺钱」、业务量和并发性都比较强的公司，建议优先选择后面要讲的 vLLM 部署方案。

所以结论也很清晰：小公司，或者业务量非常小的场景，推荐 Ollama；业务量和并发上来了，再考虑 vLLM。任何技术都不是银弹，没有什么对与错，最终还是要回到公司实际业务和实力去权衡。

| 维度 | Ollama | vLLM |
|---|---|---|
| 部署门槛 | 低，一条命令装模型起服务 | 需要 Python 环境与虚拟环境 |
| 模型形态 | 以量化版为主，体积小 | 可选满血版，体积大 |
| 并发能力 | 有限，小业务量适用 | 强，为高并发推理设计 |
| 适用场景 | 小公司、快速验证、无 GPU | 业务量与并发上来的生产场景 |

对 Java 工程师还有一层现实意义：Ollama 的「改动简单」体现在改配置不改代码，这意味着可以在不动核心业务代码的前提下做技术验证，验证通过再评估是否迁移到 vLLM。把「先跑通、再跑快」作为私有化落地的节奏，比一上来就搭 vLLM 更符合大多数公司的实际节奏。

这一课完整走了一遍 Ollama 私有化部署的落地：下载模型、改造配置、全链路验证，也聊了该方案的适用边界。接下来，换一种玩法，用 vLLM 来部署大模型。

## 【易错点 / 面试题】

1. **面试题：项目要从 OpenAI 切到私有化模型，要改哪些东西？** 答：只改两处配置，base-url 指向私有化端点，model 改成服务器上实际部署的模型名；代码不动，因为 Ollama 与 vLLM 都提供 OpenAI 兼容接口。若原来同时引了两套 starter，还要处理依赖互斥与自动配置冲突。
2. **易错点：模型名与服务器不一致。** 配置里写 `qwen:3b` 而服务器上跑的是 `qwen3:8b`，调用直接报模型不存在。原则是配置值与 `ollama list` 输出严格一致。
3. **易错点：忽略 Ollama 的响应延迟。** 私有化单卡推理比在线 API 慢是正常现象，联调时要放宽超时；若超时报错，优先排查是否模型没加载到 GPU（`nvidia-smi` 看显存占用）。

## 【小结】

本节完成了第一个私有化部署闭环：Ollama 拉模型、项目换 base-url、全链路（查询 → 预测 → 提取 → 邮件）跑通、数据库落库。Ollama 的价值不在性能而在门槛，无 GPU、20 分钟、改动简单；边界在并发与量化模型能力，业务量上来后再迁移 vLLM。

配套工程 `980-demo` 把这条链路做成了离线可跑的生产级实现：`980-demo/src/main/java/com/carl/ai/transfer/config/ChatModelConfig.java` 用 `transfer.llm.base-url` 指向远程 Ollama 或 vLLM 端点，`transfer.offline` 开关在真实模型与 `OfflineChatModel`（固定 JSON）之间切换；`980-demo/src/main/java/com/carl/ai/transfer/extract/TransferOrderExtractor.java` 用 `ChatClient` 的 `call().entity(TransferOrderParam.class)` 复刻「提取 JSON 节点」；`980-demo/src/main/java/com/carl/ai/transfer/convert/TransferOrderConvert.java`（MapStruct）与 `BbTransferOrderRepository` 对应「转换入库」环节。读博客时对照这四个模块，「配置切换 → 结构化抽取 → 转换 → 落库」的每一环都能找到可运行的代码。
