# 8-7-根据测试实现上传文件列表功能

上节课写完了测试，这节课根据测试采用 TDD 的方式完成代码。先把第一个测试打开，其他的用 only 关闭。

## UploadFile 数据结构

要展示一个文件列表并且可以动态增减，自然想到响应式数组，数组里的内容会根据上传过程实时变化，也就是一个 ref 数组包裹着一系列 reactive 对象。

先描述对象的结构。创建 `export interface UploadFile`：uid 是独一无二的标识符；size 是文件大小，number 类型；name 是 string；status 很重要，表示当前状态，直接使用已定义好的 UploadStatus 类型；最后是 raw，存放上传的原始文件类型 File。

接着在 setup 最开始创建对应的数组：`const uploadedFiles = ref<UploadFile[]>([])`，初始值为空数组。数组的每一项在 handleChange 时创建：创建一个响应式对象 fileObj，用 reactive 并以 UploadFile 作泛型支持。其中的内容：ID 使用我们熟悉的 uuid v4；size 用 file 对象上的 uploadedFile.size；name 同理用 uploadedFile.name；初始 status 是 loading；raw 就是 uploadedFile。对象创建完毕后，用 `uploadedFiles.value.push(fileObj)` 添加进数组。

然后在不同时机修改状态：成功回调里把 fileObj.status 设为 success，失败时设为 error。至此不再需要单独的 fileStatus 变量来指示状态，把它删掉。

## isUploading 与按钮状态

现在需要一个变量指示 button 是否处于上传中。规则是 uploadedFiles 里只要有一项是 loading，整个按钮就是 loading 状态，自然想到 computed。添加 isUploading：`computed(() => uploadedFiles.value.some(item => item.status === 'loading'))`，并 return 出去。

有了它就可以做替换：模板不再需要之前的四段判断，v-if 判断 isUploading 显示"正在上传"，v-else 显示"点击上传"（现在每次上传完毕文字都会恢复原状）。同时 uploading 时要把按钮设置为 disabled：`:disabled="isUploading"`。

接着用 v-for 把列表展示出来（我已写好，直接拷贝过来），并把 uploadedFiles return 出去。

## 修正 disabled 断言

跑一下测试看看进展。发现 button 的 disabled 属性断言出错了。把实际值 console.log 出来：`wrapper.get('button').attributes()`。可以看到 disabled 的时候，属性值并不等于 true，而是只要存在这个 key 即可；没有 disabled 时这个 key 不存在。所以把断言换成判断是否有这个 key：`toHaveProperty('disabled')`。运行测试，通过。

## 动态 class 的小重构

下一步是根据不同状态添加 class，加在 li 上。Vue 有动态 class，但要分别判断三个值会很啰嗦：比如状态是 uploading 就要加 upload-loading 等等。其实我们已经有了 item.status，而它本身就是完美的 class 名称字符串，直接把它改成模板字符串 `` `upload-${file.status}` `` 即可，不用再写判断。

注意测试里的类名要相应修改：这里叫 upload-loading（类名是自己指定的，选择实现最简便的方法即可）。运行测试，第一个测试通过。这个动态 class 就体现了测试帮助我们重构代码：实现时可以选择最简单的方案。

## 完成第二个测试

继续第二个测试。它有两处没通过：一是上传失败后文字应恢复成"点击上传"，改一下即可；二是 delete-icon 点击时要删除对应条目，这个功能还没实现。实现很简单：创建 removeFile 函数，内部用 filter 按 uid 过滤，return 出去；在 delete-icon 的 click 上调用 `removeFile(file.uid)`。补上 delete-icon 的 class，测试全部通过。

## 页面验证与一个隐藏 bug

在实际页面做个小测试：添加最简单的 style 区分状态，三种状态对应 yellow、green、red 三种颜色。选择第一张图：一开始是黄色，上传成功后变绿；再上传一张 editor-one.png 也成功；点击 delete 删除也没问题。

但再上传一次 editor-one 时发现：连续上传相同的图片没有反应。回顾代码，实际上传是在 onChange 时触发的，而 change 触发的条件是 input 值发生改变；选择同一张图片时 input 里的值相同，所以没有触发。解决方案很简单：上传完毕后把值清空，在 finally 里判断（DOM 节点可能为 null），如果存在就 `input.value = ''`。再试一次，连续上传同一张图也没问题了。

那为什么单元测试没有捕捉到这个 bug？因为测试里是直接 trigger 的 change 事件，和界面操作的方式还是有区别的。所以单元测试和实际功能之间有时存在一些 gap，大家需要注意。
