# 15-2-6-方法二：完成裁剪后重新上传图片

这节课来完成第二种裁剪图片的方式：拿到裁剪后的数据，重新上传生成一张新的图片。上节课已经提到，先用 `getCroppedCanvas` 拿到 canvas element，再调用 HTML canvas element 上的 `toBlob` 方法，就能拿到对应的 blob 对象。blob 对象是 file 对象的基础，拿到它之后就可以上传了。

由于我本人不会采用这种处理方式，这里只写一个大体的过程。如果你想选用这种方式，可以在内部加上一些 UI 优化，比如 loading 状态、上传成功后的提示等效果，这里就不添加了。

## 在 handleOk 中重新上传

处理逻辑应该放在 `handleOk` 里执行，也就是重新上传这一步。首先还是在 Cropper 实例上做文章：调用学过的 `getCroppedCanvas`，它返回之前说过的 HTML canvas element，接着调用上面的 `toBlob` 方法。

注意 `toBlob` 接受的是一个回调，它不是直接返回 blob 值。回调的第一个参数是 blob 对象，类型是 blob 或者 null，所以要先判断它存在，再进行后续处理。

## 构造 FormData 并上传

到这里就重新回到了上传文件的逻辑，很简单：先新建一个 `FormData`，然后通过 `append` 把数据添加进去。`append` 有三个参数：

- 第一个是 name，这里随便起一个，叫 `croppedImage`；
- 第二个是 value，文档提示得很清楚，类型是 string 或者 blob。我们之前传 file 类型也没问题，因为 file 继承自 blob，完全适配。这里直接把 blob 添加进去；
- 第三个参数要特别注意，它叫 filename。

为什么第三个参数如此重要？文档中 `append` 方法的说明写了：当 blob 或 file 作为第二个参数时，blob 对象的默认文件名就是 "blob" 这四个字符，file 对象的默认文件名才是该文件的名称。而我们的后端有文件名判断，默认文件名会直接导致上传失败，所以必须显式传入一个合法的文件名。如果想每次都不一样，可以引入 uuid，这里就直接用 `test.png`。

数据准备好之后就可以用 axios 发送请求了。如果你打算采用这种方式，建议把 Uploader 中发送请求的逻辑（也就是 axios post 那一块）抽取出来，做成一个单独的上传函数，两边共享。我为了简便起见直接平铺直叙地写，不做抽象。参数和之前一模一样：第一个是 URL 地址（这里用本地地址，大家可以用我提供的测试地址）；第二个是数据，也就是 FormData；第三个是一系列配置参数，其中不要忘记 `headers`，要把 `Content-Type` 设置成之前讲过的 `multipart/form-data`。

设置完毕之后调用 `then`：图片重新上传完成后拿到 response，response 里有新的 URL，这时调用 `context.emit`，把这个新获得的 URL 以 change 事件发送出去。取值路径是 `response.data` 里还有一层 `data`，里面的 `url` 就是最终结果。发送出去以后，别忘了把原来在外面发送的代码注释掉，不再在外面发了；同时把 `showModal.value` 的关闭也放在这里，这时候才把弹窗关掉。这些位置我都先简单注释一下。

当然这里面还有很多可以优化的地方，大家可以自己去完善，我只负责把主逻辑写出来。

## 验证效果

现在来验证最终成果。点击裁剪图片，往下选一点，把头像裁剪一块，然后点击确认，它会重新发送一次请求。可以看到 Network 里 upload 已经成功，并返回了新的图片地址。当 `context.emit('change')` 发出去之后，编辑器的值被更新，新图片就显示出来了。可以看到它是一个单独的 URL，也就是我们新上传的图片。

这个过程就完成了。这种方式意味着可以在上面多次完成裁剪任务，因为现在是一张单独的图片，而不是在后面追加 URL。

通过这两种裁剪图片的方式，相信大家心中已经有了一个比较，最后选用哪种方案，就看你的取向了。这节课就到这里。
