# 14-41-总结

本周的学习完成了。这一周循序渐进地学习了应用的部署过程：从最开始刀耕火种的原始方式（直接把代码 clone 到服务器上完成部署），到最终用 GitHub Actions 结合 Docker 完成自动部署。最后一课简单回顾一下学到的知识点。

## 环境与 Cluster

第一部分学了 egg 应用的生产环境和本地环境的异同：本地环境用 egg-bin 启动，它有针对本地开发的一系列优化；生产环境用 egg-script，其内部是 egg-cluster。借着 cluster 的东风，简介了 Node.js cluster 的几个概念：基本介绍、针对普通模式的优势、worker 之间的通讯。最后介绍了 egg 启动进程的种类：master、worker、agent，它们的区别请大家自己再复习。

## 云服务器与传统部署

有了基础知识做铺垫，来到云服务器。部署需要一台云服务器：先调研了几大服务商的对比；购买之后做了 Linux 初次使用的安全设置，我认为这很重要，有服务器的都建议做：创建子账户并给子账户 root 权限，禁用 root 用户登录，再到使用 SSH key 免登录。

接着是传统部署的刀耕火种过程：登录服务器，安装必备软件（数据库、Redis），clone 代码，运行启动脚本。如果你是 egg 应用（像我们一样），自然用 egg-script（内部是 egg-cluster）；如果是其他 Node.js 应用，建议使用 PM2，它内部也是用 cluster 做进程管理。

## Docker

Docker 是之后自动部署的关键。讲了安装、images 镜像操作、container 容器的基本概念和进阶操作（比如数据持久化）；然后学了 Dockerfile 这个特殊文件：语法，以及用它构建自定义镜像；最后学了 Docker 启动多个容器以及它们之间的互相通讯。

发现多容器通讯比较繁琐，需要一种简洁的方式来启动容器并完成通讯，于是有了 Docker Compose 这样的 YAML 文件，学习了它的基本使用。因为要把多个服务一起用，就遇到了权限问题：

- MongoDB 设置访问权限。两层：第一层设置最大权限的 root 用户；再用 root 给对应的数据库设置不同的操作员权限。代码中使用的是操作员权限登录。
- Redis 设置了密码访问。

针对敏感信息，用 .env 文件保存，构建时把 .env 传进去。

之后讲了优化 Docker 构建速度和大小的方式：优化大小用 Alpine 镜像；提高速度讲了 layer 的概念并缓存特殊步骤，比如 node_modules 没变就不重新安装。

学完这些后在服务器上部署 Docker 镜像。对比手动最基础的部署：只需登录服务器，到对应代码目录下执行 `docker compose up -d` 就能运作。这种方式看起来比第一种简单，但还是达不到最终要求：除了初次启动，还需要更新，而更新仍是比较繁琐的流程。

## GitHub Actions

于是引出 GitHub Actions：学了基本概念和一些进阶内容，学了自定义 action 的使用，最后学了用 GitHub Secrets 保存敏感信息。

## 集大成：Actions 结合 Docker 的部署流程

最后来到集大成的流程。这里再总结一遍优化后的线上部署流程，因为过程比较繁琐：

1. 用 tag push 触发对应的 Actions。
2. 第一步创建 .env 文件，里面包含 GitHub Secrets 中的一系列敏感信息。
3. 在 GitHub Runner 上用 push 的 tag build 对应的镜像。
4. 镜像持久化：push 到阿里云 ACR 容器服务。
5. 版本替换：在 docker-compose-online 文件中查找占位符，替换成刚 push 成功的镜像 tag 版本。
6. 用 scp 把文件拷到服务器：docker-compose-online.yaml、.env 文件、mongo-entrypoint（初始化 Mongo 的文件夹）。
7. SSH 到服务器，停止之前的服务，启动新的应用版本。

这种方式可以完全和源代码库脱离开来，用几个简单的文件就能完成一次新的部署。最后用 release-it 工具优化了整个发布流程。到这里，自动化部署就比较完备了。

## 两点建议

第一是多实践。CI/CD 工具和 Docker 这些内容，不能光看我写，必须亲自写代码、真正去跑对应的流程。使用 GitHub Actions 时，GitHub 时断时续可能带来困扰，请有耐心，多试几次，只要配置成功就能触发。

第二是学习部署的具体流程。要了解整体过程，不局限在某个特定的 CI/CD 工具上：我这里用 GitHub Actions，假如你用 Jenkins 或 Travis，完全可以使用相同的流程完成部署，把这套流程发扬光大。

这就是本周的所有内容。希望大家对 Node.js 类型应用部署的理解，能上升到一个新的台阶。
