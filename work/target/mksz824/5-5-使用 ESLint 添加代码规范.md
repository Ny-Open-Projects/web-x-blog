# 5-5-使用 ESLint 添加代码规范

上节课简介了 Vite 和 Vue CLI 的区别，这一章先做一些准备工作，谈谈代码规范的问题。一个人做项目时，什么问题都不是问题，只要自己看得懂就行。但现代项目讲究团队合作，从头到尾只有一个人完成的情况非常少，所以代码规范很重要。很多人刚入职新公司要做的几件事之一，就是熟悉公司的代码格式，规范的代码格式可以在一定程度上把整个工作的效率提到最高。

说说没有规范可能出现的问题。第一个是代码难以读懂。假如每个人都有自己的一套风格，修改别人的代码时势必遇到自己不熟悉的格式，难以理解的同时，还可能顺手把代码改成自己熟悉的格式。这样一来，整个代码库就充斥着各种风格的代码，像不一样的面条搅在一起。第二个问题是提交噪音。每次提交里可能混入大量纯粹格式上的修改，不是逻辑变更。比如你喜欢用两个空格，李四喜欢用 Tab，他改逻辑的时候顺便帮你调整了格式，自认为帮了大忙，提了 PR；而你作为 reviewer 看到自己的代码被改得面目全非，愤怒地点了 decline，接着可能就是无休止的争吵，造成不必要的时间消耗。

这个故事告诉我们：要解决问题，先把规矩列出来写在文件里。代码规范有点像项目中的法律条款，不管什么原因都必须遵守。于是大名鼎鼎的 ESLint 出现了。ESLint 是一个开源的 lint 工具，使用 Espree 把 JavaScript 代码解析成抽象语法树 AST，然后通过 AST 分析代码、发现错误。同时它也是一个命令行工具。项目初始化的时候已经添加了 ESLint，可以在项目根目录下运行 `npm eslint --version`，能看到版本号是 6.8.0。

也可以手动通过命令校验代码：`npx eslint --ext .ts,.vue src/**`，其中 ext 参数指定要校验的后缀名，这里是 ts 和 vue；后面的 `src/**` 是 glob 格式，代表 src 下面的所有文件。回车执行，就输出了之前故意写的错误代码。

把项目运行起来（npm run serve），它做的事情和手动执行一样，只不过是自动运行这个命令，每次代码修改时就跑一遍，于是可以实时看到错误。想深入了解命令行用法，可以到官网 User Guide 下的 Command Line Interface 一节，所有参数都有详细说明。

除了在命令行显示错误，还需要在编辑器里以最快速度展示，比在终端里直观得多，所以要安装插件。用 VS Code 的话，建议所有人安装 ESLint 插件，安装之后在任何编辑器里写代码，错误都会实时以红线形式显示出来，非常方便调错。

不过默认配置有一点问题：在 App.vue 里的错误能显示出来，但 main.ts 里的错误没有显示，命令行里却能看到它。这肯定是 ESLint 插件的配置问题。打开插件的 Extension Settings，再点 Add in settings.json，在配置文件里加一项 `eslint.validate`，指定要校验哪些文件。它默认只包含 javascript 和 javascriptreact，没有 TypeScript，需要手动添加 typescript 和 vue。保存后回去看，main.ts 的错误就出现了，说明设置生效了。

除了 ESLint 插件，还强烈推荐 Vetur，这是 VS Code 官方推荐的 Vue 开发插件，属于必装。它特性非常多，而且会自动关联 Vue 文件，最基础的是给 template、script 等不同区域添加高亮；刚才 ESLint 能直接支持 vue 格式的文件，可能也有它在里面起作用。这两个插件建议大家必装。

现在有了这两个插件，ESLint 规则在命令行和编辑器中都能良好运作，第一个任务完成了。下节课稍微深入一下 ESLint 的配置文件，看看里面的规则怎样自定义和修改。到这里，谢谢大家。
