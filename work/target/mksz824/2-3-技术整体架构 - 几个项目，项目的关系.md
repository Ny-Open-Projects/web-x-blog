# 2-3-技术整体架构 - 几个项目，项目的关系

上节课分析了需求并做了归类，现在完成架构师的第一个任务：技术架构。这是项目的整体技术设计，要秉持的原则是看整体，从上帝视角出发，不要陷入技术细节。后端要做哪些接口、数据库怎么选型、用户鉴权怎么实现、前端编辑器的拖拽移动怎么完成，这些具体内容留到前端开发和后端开发阶段，针对特定难点再做设计的细化。整体设计阶段的第一个任务，是从宏观角度为前后端开发指明方向。

所以第一步要研究：我们需要几个项目。

## 项目一：前端 OpsFlow

从需求来看，这个应用非常典型，属于前后端分离的项目。前端尤其是编辑器，有大量和数据交互的操作；后端是典型的 RESTful API，以接口的形式提供给前端。既然是前后端分离，自然要有一个前端项目，它是一个 SPA 项目，可以使用 Vue 或 React，我们称之为 OpsFlow。

这里希望大家多加一点思考。编辑器页面拥有大量的交互和数据操作，是整个应用里最复杂的；其他页面基本都是数据列表的展示或单体展示，复杂度和编辑器不在一个数量级。那能不能把前端分成两个项目，放在两个 repository 里？一个是很复杂的编辑器，叫 OpsFlow editor；其他页面叫 OpsFlow pages。两者甚至可以用不同的技术栈，OpsFlow pages 主要做条目展示，可以用 Nuxt 或 Next.js 这种 SSR 框架完成。

这是一个很好的思考方向，但本项目暂时不这么做。分成两个项目会让维护和复杂度上升，而 B 端天然耦合在一起，所以我们不拆。当然，如果你愿意，完全可以拆成两个 repo，这里面蕴含了现在非常流行的概念：微前端。

## 项目二：后端

后端可以称为 OpsFlow 后端，主要任务是为前端提供 RESTful API。但如果还记得需求分析，里面有一块非常另类的内容：H5 页面，也就是那个 URL 打开的展示页。它的任务是把编辑器创建完成的页面原封不动地展示出来，看起来像是属于前端项目，加一个路由展示页就行。但我们的前端是 SPA，页面内容由 JS 渲染完成，而这里明显要展示的是一个简单的静态页面，不希望有 JS 的开销。所以可以想到用 SSR（Server Side Rendering）：在后端用 SSR 的方式，把前端保存到数据库的页面渲染成静态页面再展示，让整个页面的渲染速度更快。

## 项目三：公共组件库

有了 SSR 需求，就会发现需要一个桥梁，来对接编辑器中的组件元素。海报由一个背景和一系列元素组成，元素中有最常见的文本，也有图片。我们需要把这些内容抽象成一个组件库，提供给前端和后端两个项目共同使用。

所以还需要一个项目：公共组件库，OpsFlow 组件库。这也是中大型公司前端架构的常见做法，把和公司业务相关的通用页面元素封装成组件库，供多个项目使用。

课程里还有与业务无关的研发支撑系统（脚手架、组件平台、监控平台），这里只讲业务项目，支撑系统由课程讲师在之后介绍。

## 项目之间的关系

明确了"做几个项目"，第二个问题是这些项目之间的关系。用图的方式描绘更直观清楚。

- **OpsFlow（紫色，前端 SPA）**：内部分成两部分。编辑器太特殊，有非常复杂的交互和行为，单拿出来；剩下的是 B 端其他页面。
- **OpsFlow 后端（绿色）**：也分两块。最主要的是服务器端 RESTful API，为 B 端其他页面和编辑器分别提供接口；另一块是服务器端 H5 渲染页面，它和编辑器产生联系，编辑器点击发布后会创建一个对应的 H5 海报。
- **OpsFlow Components（黄色，组件库）**：作为前端和后端的桥梁。它可以供编辑器做 JS 方式的渲染，渲染出对应的画布区域；也可以用 SSR 渲染的方式为 H5 页面渲染，让这两部分形成同构关系。

## 小结

这节课确定了 OpsFlow 的整体技术架构，解答了两个重要问题：要做几个项目；这些项目之间有哪些关系。以后做技术架构设计时，都要先从这两个问题出发，先搞清楚整体轮廓。
