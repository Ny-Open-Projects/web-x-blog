# 3-5-组件库难点解决方案

上节课的难点分析产出了一系列难点，按分类可以归为两类：一类是业务组件库的问题，一类是编辑器的问题。这节课先解决业务组件库的问题，共三个：两个项目（H5 端和 B 端编辑器）怎样重用组件？组件的属性应该怎样设计？组件的扩展性怎样保持？

## 问题一：两个项目怎样重用组件

在不同项目中重用组件，自然而然的想法是抽取成单独的代码库。我们新建一个代码库 OpsFlow Components，这样就降低了和任何一个项目的耦合度，让业务组件拥有独立、标准的开发流程。

这个开发流程包括：编码；组件特别适合单元测试，所以有测试环节；编码和测试通过后打包，生成一系列 JS 模块，可以是 ES modules、CommonJS 或 AMD 等；打包后发布到 npm，两个项目就可以通过 npm install 安装使用；最后再加一步 CI/CD 自动发布，给 OpsFlow 组件库打一个 tag，push 之后自动检测并运行测试，测试通过就自动发布到 npm，完成整个流程。

于是编辑器可以用 npm install 安装 OpsFlow 组件库，H5 端渲染时同样用 npm install 安装这系列组件。第一个问题解决，把思路记录到技术方案里。

这个思考过程中还衍生出一些通用总则。业务组件库大多数是展示型组件：把对应的 template 加上属性展示出来，属性大部分是 CSS，只有少量行为（如点击跳转）。而且这些组件会在多个不同端展示，所以业务组件库要从简，必须避免和编辑器的编辑流程耦合，一定要把编辑器抛开。

组件命名规则：使用字母 L 代表 OpsFlow，加组件名称命名，比如 LText（两个单词大写），或 l-text（小写中间用杠连接）。

## 问题二：组件的属性怎样设计

看业务组件需求，每个基础组件由通用属性和特有属性组成，加起来和组件的属性一一对应。对每个组件，可以把需求中的属性分成两大类：一类是样式属性，就是 CSS，控制它长成什么样；另一类是其他属性。以文本组件 l-text 为例，长度对应 height、宽度对应 width 等，都是 CSS；唯一不一样的是文字内容，以及事件功能（点击后跳转到哪个链接），这两者不属于 CSS 范畴。

怎么实现？写伪代码，有两个方案。

**方案一：CSS 作为统一对象传入。**

```html
<l-text :css="{ color: '#fff', ... }" text="你好" />
```

组件内部实现很简单，要生成一个 p 标签的话，style 直接用接收到的 props.css 即可。

**方案二：所有属性平铺，没有两层结构。**

```html
<l-text text="你好" color="#fff" />
```

这种方案内部实现稍微复杂一点，要先选出哪些是 style，需要一个类似 stylePick 的函数，从 props 中把 styles 拿出来再赋上去。

对比一下哪个更好。方案一内部实现简单，但保存的时候要多保存一层结构：编辑器的整体状态里要多一层 CSS，后端可能也要多一层；更新数据时，表单中的值回灌到属性里，还要甄别这个值是样式还是其他属性，是样式就要深入到 CSS 这一层。方案二内部实现复杂一些，但保存非常简单，直接平铺保存所有属性；更新数据时也不需要甄别，因为都在第一层，直接塞进去就行。

我认为方案二明显更好。当然你也可能总结出其他更好的方案，就看怎样分析这个问题了。

## 公共属性与代码重用

从另一个维度看，组件需求里有一组所有组件都有的通用属性。一听到"公共"，就要特别注意代码重用性的问题。比如 l-text 和 l-image 都有页面跳转功能，它属于公共属性中的行为，自然要抽象出通用的函数，在组件中完成通用功能。比如可以抽象出一个 useClick 函数，在 l-text 和 l-image 中直接调用，把 props 传进去，就完成了点击跳转。这里只分析可能遇到的问题，不写具体代码，都以伪代码代替。

经过这样的分析，我们就解决了组件属性的设计问题，把成果一一写进实现方案文档。这样第二个问题也完成了。

## 问题三：扩展性怎样保持

我觉得扩展性在业务组件库本身不存在什么问题，因为每个组件都是独立的个体，实现方案相对独立。这里的扩展性其实是跟编辑器相关的：编辑器是否能对组件进行适配，包括展示，尤其是点击后能否在右侧表单中对这些属性进行编辑的适配。所以这个问题可以合并到之后的编辑器实现方案中讨论。

## 小结

经过分析，我们解决了业务组件库的一系列问题，同时完成了组件库实现的技术方案。以后进一步实现时，就可以用这个文档作为指导思想进行编码开发。

这节课展示了一个完整的过程：需求分析，寻找技术难点，攻克技术难点，并且以这些难点为脉络撰写技术文档。
