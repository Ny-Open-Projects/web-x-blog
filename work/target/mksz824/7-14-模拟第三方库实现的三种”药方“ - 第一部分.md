# 7-14-模拟第三方库实现的三种”药方“ - 第一部分

上节课我们完成了界面测试，使用 mount 的 global.components 字段给全局组件添加了假的实现，让它按我们想要的界面进行展示。现在来测行为。行为本身很简单：登录和非登录两种状态下点击按钮，各自触发不同的方法。

难点在于，这几行代码里只有七八行，却都要调用第三方库的一系列方法，而且各有特点：store.commit、message.success、router.push。先看 message.success，它是两层嵌套，从 main.ts 导出，导出一个 message 对象，对象上有一个 success 方法，调用后出现最终结果。剩下两个也是两层嵌套，但要注意中间的过渡不是一个对象，而是一个函数：调用这个函数后返回另一个对象，那个对象上才有 push 和 commit 方法。这个区别要先牢记。

login 要触发的方法有两个：store.commit 和 message.success。测试宗旨就是验证这两个行为是否被触发。

先从 message.success 测起。之前 mock axios 时是要改它的实现，这次只需要测它是否被调用，所以可以用 jest.mock 的第二个参数。第二个参数是一个 function，直接返回模块的实现。这里返回一个 object，第一层是 message，第二层是 success，值为一个 jest.fn()，这样就能监控它是否被触发。整个模块就这样被一个简单实现代替了，和替换全局组件有异曲同工之妙。

接着触发点击：给函数加上 async，`await wrapper.get('div').trigger('click')`。然后把 message 从模块中导出来，因为要测它是否被触发：`import { message } from './main'`。特别注意，在测试文件中导入第三方模块时，jest.mock 会在最顶部运行，所以此时拿到的 message 早已是假的模块，也就是我们定义的 jest.fn，而不是真正的实现。

于是可以放心断言：`expect(message.success).toHaveBeenCalled()`。同时要把 store.commit 那部分先注释掉，因为还没实现它，留着会报错。跑一下，测试通过，message.success 的判断就完成了。

第二个要模拟的是 store，它通过 useStore 函数获得。可以用第一种方式模拟，但总用同一种实现未免乏味，所以换第二种药方：不用假模块，对 store 来真的。组件里之所以能用 useStore 拿到全局的 store，是因为组件实例 use 了 store 插件，也就是 main.ts 里 `app.use(store)` 之后，全局就能通过 useStore 获得实例。那如果测试的 wrapper 也提供一种机制，把这个 store 挂载到实例上，不就达成一样的效果了吗？

mount 有没有这种能力呢？答案是肯定的，不过很难找。官方文档里我没有找到具体说明，而是在 Vue Test Utils 的 GitHub Issue 中，由框架作者回答其他人的问题时提到的。这个 issue 问的就是：组件在 setup 中调用了 router 或 store，测试时怎么办。作者除了提供 mock 方案外，还给出了另一个方案：使用 global 中的 provide 把 store 挂载进去。因为 useStore 底层正是用 provide 和 inject 来完成任务的。

这也是我平时解决问题的习惯：Google 查不到就去 GitHub Issues 里找，常常有意外收获。文档里没有的知识弥足珍贵，要花时间和精力去寻找，请大家记住这个思路。

现在把真实的 store 放进去：在测试用例里 `import { store } from './store'` 拿到 store 实例，挂载时第二个参数传 `global: { provide: { store } }`，store 就挂载进去了。既然有了真的 store，就不用 mock 了，把原来的 mock 删掉，把 store.commit 的注释去掉，测一个真实场景：点击之后不再判断函数是否被调用，而是断言 store 里的状态是否改变，`expect(store.state.user.username).toBe('Viking')`。状态改变了，就说明 commit 被成功调用，state 中已有新值。

跑一下，测试通过。这节课完成了前两个任务，总结出对付第三方模块的两种方法：第一种是用 jest.mock，前面写模块名，后面传一个 function 给出整体实现；第二种是另辟蹊径，给测试的 wrapper 注入真实的 store，通过状态变化判断逻辑是否正确。下节课再来第三种新思路。通过组件测试这一个切面，我们不断扩充测试的知识面，希望这个系列学完之后，任何疑难杂症式的组件测试问题我们都能应付。到这里，谢谢大家，再见。
