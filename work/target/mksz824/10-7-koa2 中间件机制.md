# 10-7-koa2 中间件机制

这节课来看 Koa 2 的中间件机制，并和 Express 做个对比。

之前说过，Express 的中间件是线性模式，一个接一个运行，每个中间件通过调用 next 进入下一个。因为 Express 基于回调，它的中间件也是基于回调函数的：从 request 到 response，每个中间件是嵌套关系，第一个的 next 包裹着第二个函数体，第二个的 next 又包裹第三个，以此类推，像俄罗斯套娃一样组织起来。用假代码模拟的话，第一个中间件 f1 在调用 next 时其实是调用了第二个中间件，第二个调用 next 时进入第三个，最终输出 hello world。

这种方式对错误捕获不太友好。每个回调都拥有一个新的调用栈（context），你没法对单个 callback 做整体的 try catch，只能在每个 callback 里各自捕获错误，再一层层向外传递。

Koa 2 对此做了大刀阔斧的改革。上节课提到它基于 Promise，所以 Koa 2 使用的是洋葱模型，特点是级联：通过 await next 调用下游中间件。最外层中间件调用 await next 时进入第二个，再进入第三个，直到下游没有中间件、堆栈执行完毕，然后按反向顺序流回：middleware3、middleware2、middleware1，最后发起响应。因为整个运行时由 Promise 链构成，捕获错误容易得多，只要在单独的 Promise 上做 try catch。另外，之前用 Express 需要两个中间件完成的任务（比如记录请求响应耗时），现在写在一个中间件里就行：进来时记开始时间，流回时记结束时间，相减就是耗时。

光看图可能还不直观，用代码验证一下。复制三个中间件 f1、f2、f3，它们都有两个参数：ctx（就是上面的 context 对象）和 next（调用下一个中间件）。特别注意中间件必须是 async function，因为调用下一个中间件要用 await next。注册顺序是 app.use(f1)、app.use(f2)、app.use(f3)。f1 里打印 f1 start，f2 里打印 f2 start，f3 里打印 f3 service。

按洋葱模型，预期输出是 f1 start、f2 start、f3 service，堆栈执行完毕后向上返回 f2 end、f1 end。刷新 test 路由验证，实际输出 F1 start、F2 start、F3 service、F2 end、F1 end，和预想完全一致。

有了这个基础，改造上节课用 Express 记录请求时间的例子就很容易了。在 f1 里创建 const requestTime = Date.now()，然后在函数后半段处理：duration 等于当前时间减去 requestTime，得到时间差。接着设置 response header，用 ctx 上的 response 对象的 set 方法，设置 X-Response-Time 为 duration。顺带一提，把函数单独拿出来后它就没有任何类型了，后面项目用 TS 时你会发现 TypeScript 真的好用。来到 Network 面板刷新，Test 路由的 Response Header 里出现 X-Response-Time，值为 4，改造成功。

从这个例子还能感受到响应机制的区别。Express 中，任何中间件一旦调用了 res.send，响应立马返回，后面的逻辑完全不会执行。Koa 2 不同：在最后的中间件（router）里设置了 ctx.body，响应并没有立即返回，后面的逻辑照常执行。所有中间件都可以对 ctx.body 进行设置、增减它的值。好处是响应发出前还留有操作空间，而 Express 想在上层中间件再做事就难了。当所有中间件运行完毕，Koa 才把你设置的值一股脑返回出去，所以设置 ctx.body 只是设置值，不是直接完成返回。

至此我们调研完 Koa 的中间件机制。对比 Express，基于 Promise 的洋葱模型中间件更有吸引力，Koa 2 是更好的选择。但它有个问题：太轻量级。除了核心什么都没提供，代码规范、目录结构、逻辑分层这些都要靠第三方中间件，自己研究最佳实践。这就引出了下一节的 egg.js。
