# 5-9-了解 Git Flow 标准

前面几堂课我们在做编码前的准备工作：讨论了代码规范、项目文件结构和文件命名规范。现在来到最后一步，源码多人协作的规范。之前说过，所有这些规范都是针对多人设定的，意在让多人协作的过程更顺畅、更简单，减少不必要的冲突和时间浪费。一个人编码的话，想怎么玩就怎么玩，没这么多规矩。

源代码的多人协作是很容易出现冲突的流程，自然需要一套特定的规则。现在源码管理工具都用 Git，所以这套流程称为 Git Flow。Flow 指的是工作流程，这里要确定的是本次编码采用的 Git Flow 规范。课程讲师之前已经大体讲过大厂使用的 Git Flow，这里我会再举两个典型的例子，并选用我认为适合本次开发的流程。

第一个称为原汁原味的 Git Flow，它是诞生最早、跟随 Git 工具一起出现的流程。它预设两个长期分支，这称为它的分支模式。第一个是 master，只能用来包含产品代码，不能直接在 master 上工作，而是在其他指定的独立特征分支中工作。不直接提交到 master，是很多工作流程共同的规则。第二个预设是 develop，它是进行任何新开发的基础分支：开始一个新的功能分支时以它为基础，它也汇集所有已完成的功能，等待整合到 master 分支中。

这两个分支称为长期分支，会存活在项目的整个生命周期中；其他分支（比如针对功能的、针对发行的）只是临时存在，根据需求创建，完成自己的任务之后会被删除。接下来说这些临时分支。第一个当然是功能开发：要开发一个新功能，就创建一个前缀为 feature 的分支，加上斜线后面是功能名称，比如 feature/xxx。经过一系列编码做完后，把工作整合到 develop 中，在那里等待：一是在更广泛的背景下做全面测试，二是稍后和积攒在 develop 中的其他功能一起发布。

第二个重要的流程是 release，这是版本控制处理中我认为非常重要的话题。什么时候该发布一个 release？当我们认为 develop 分支的代码已经很成熟的时候：一是所有功能已经添加完、必要的 bug 已经修复；二是它已经被测试过。满足这两个条件就可以发一个新的 release。release 分支用版本号命名。看看 Vue3 的 release，其实就是在特定提交上打 tag，把截止到这次提交的内容称为一次发布。release 有大有小：大型的可能是里程碑式的发布，小型的可能只是一系列 bug 修复。

说完 feature 和 release，来谈谈 bug。很多时候悲剧难免发生：虽然对 release 版本做了全面测试，可能还是会出现小错误。这时会创建一个前缀为 hotfix 的分支，后面是要修复的 bug 的简称。因为这是对产品代码进行修复，所以 hotfix 基于 master，我们希望这个 bug 赶紧修掉。这也是和 release 分支最明显的区别：release 分支都是基于 develop 的，因为不应该在一个还不稳定的开发分支上修复产品代码。bug 修复完毕后，把 hotfix 分支上的代码合并到 master 和 develop 中，创建一个新的 release 部署代码，这个周期就算完毕了。

我原来的公司就采用这种 Git Flow。它的优点是清晰可控、流程成熟；缺点是相对复杂，要同时维护两个长期分支。大多数工具把 master 作为默认分支，可开发却在 develop 上进行，导致经常要切换分支，非常烦人。而且它不太适合持续部署的概念，现在很多公司一次提交就立刻触发一次部署，没必要搞那么多分支。这时 GitHub Flow 出现了，它是 Git Flow 的简化版，专门配合持续发布，也是 GitHub.com 使用的工作流程。

看它的官方文档，非常形象地描述了整个流程。它只有一个长期分支 master。第一步根据需求从 master 拉出分支，不管是 feature 还是 bug fix 都一样简单。然后进入激烈的开发阶段，各种开发、提交 commit。功能开发完毕后，发起 pull request。Pull request 其实是一个通知，让别人接收到你的请求，也是一种对话机制：大家一起评审和讨论你的代码，这就是下一步 discuss and review your code。对话过程中你还可以不断提交代码。我认为这个过程非常重要，我在这个过程中学到很多，这是你和工程师（包括各种大牛）交流的最佳机会，所以要珍惜那些给你提意见的人，他们是在利用自己的时间帮你提高。PR 通过以后，就可以部署到测试环境测试（deploy），测试完毕都没问题，就可以把代码 merge 到 master，整个流程结束。

GitHub Flow 最大的优点是简单，对持续发布的产品来说是最合适的流程，我认为也非常适合本项目，所以我选择采用这样的流程。当然，在这个流程之外有两点我自己确定的规定，要非常注意。

第一，我混合了两个 flow 的特点，那就是 branch 名称的命名，这是强制性的：延续 feature 开头的约定，开一个 feature 开头的分支表示进行功能开发；hotfix 开头表示在修复一个 bug。就这么一个简单的规矩。

第二是 commit 信息。太多人每次提交的信息都是 update 或者 fix bug，等于没写，一串废话，对后来 revisit、回看自己的修改非常不友好。如果有人要改你的代码，他只能看 commit 信息，看到这种描述毫无帮助。所以我建议每次提交必须言之有物：不要求长篇大论，但至少要言简意赅地把每次 commit 完成的任务说清楚。

现在看项目的实际做法。我已经创建了 main branch 作为主要分支，看一下提交：commit 信息是 create initial setup for OpsFlow project。中文英文都可以，关键是言简意赅地描述这次任务。接着要开发一个新功能：为项目添加 Prettier 支持。创建分支 feature/prettier，注意命名。切到这个分支提交，信息是 add prettier support for the whole project，也是比较明晰的提交。

开发完毕后，下一步就是创建 pull request，也就是 PR。创建后会出现一个界面，就可以添加别人进行 review 了：大家提问题，你去修复，再添加一些 commit。没问题的时候就可以 merge，点击 merge pull request，代码就会 merge 到 main 中。我这里只是演示，不会真正 merge，因为我本人不太喜欢这个分支，就不会再添加了。

到这里整个 Git Flow 都演示完了，我以后还会产出一个对应的规范文档。
