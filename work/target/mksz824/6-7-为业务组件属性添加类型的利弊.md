# 6-7-为业务组件属性添加类型的利弊

上节课我们使用图的方式描述了整个添加组件到中间编辑器的过程，流程图能更直观地体现数据流动。同时上节课留下一个问题：是否要使用特定的 interface 描述业务组件的一系列属性？因为现在代码中有太多 any 出现，这是我不愿意看到的场景。但业务组件的属性会比较多，这样做是否值得？是不是一个双刃剑？这是值得讨论的问题。

这节课我在本地已经完成了修改，就不和大家一行行写代码了，只分析这么做是否值得。首先我添加了一个 CommonComponentProps 的 interface，对应通用的一系列组件属性；还添加了 TextComponentProps，它是 LText 特有的一系列属性，继承于通用属性，多出这些特有的字段。可以看到这两个类型文件确实比较长，我将它们添加到了 defaultProps 中。

有的同学也许觉得麻烦，这些类型真的值得添加吗？看看它给应用带来了什么改变。有了这两个类型，整个应用中目前添加的所有变量和数据流转，都能获得更精确的类型，而不是原来模棱两可的 indexable type 或者最不好用的 any。看代码。第一处是 editor 中的替换：可以告别 props 是 any 的类型，改用 Partial<TextComponentProps>，因为传入的是 props 的一部分。当然在 addItem 这个方法中还无法完全体现优势，代码没有特别大的改观，但 props 上面的属性已经可以非常方便地联想出来，包括属性名和对应的类型。未来需要某个属性时，大大减少了代码书写量。

再看另一处。来到 useComponentCommon，这时 props 也定义成了对应的 TextComponentProps。注意它是 Partial，因为可能只传几个而不是全部；同时还是 Readonly，因为传入的是 Vue3 组件里面的 props，是只读的，这样才能做到类型兼容。有了这个类型，写 props.actionType 时能获得对应的补全和类型，url 也是同样，判断就更简单了。

而且，假如把赋值这一行直接放到外面、不判断就处理，是会报错的：因为 href 需要一个 string 类型，而 props.url 是 undefined 或 string。把它包在 if 中正好消除这个错误，这就是 type guard 的作用：只有它存在的时候才能赋值。TS 就这样帮我们减少了一个错误，体现了 TS 的两大特点：自动补全和类型检查，在这个小函数中体现得淋漓尽致。

还有一个点。来到 defaultProps 中的 transformToComponentProps 方法，原来我们使用泛型在调用时传入类型。而现在可以很笃定地确认 props 就是 TextComponentProps 类型，所以放弃了泛型写法，直接给 props 附上对应的类型。这样返回值也能直接返回对应的类型，更好理解，也不需要泛型这种难以理解的做法，整个应用看起来更好理解。

所以我认为，给业务组件属性添加对应的 interface 是利大于弊的做法。使用 TS，我首先建议不要怕定义类型的麻烦：有时定义类型只多花五分钟，多写一些类型文件，但在未来可能给你节省五个小时，帮你减少各种 bug 的出现。第二个中心思想是争取让所有变量都获得类型，争取消灭 any。我反正看到 any 就很头疼，也许是我使用 TS 的一种代码洁癖。这就是我使用 TS 的宗旨，希望大家可以慢慢把它灌输到使用 TS 项目的核心思想当中去。

这节课我们给业务组件的属性添加了对应的类型，最后留一个课后小作业：现在已经有了点击左侧添加到中间的逻辑，希望大家添加一个删除组件的逻辑，在中间编辑器的右侧添加一个小按钮，点击按钮就可以删除对应的元素。作为课后作业大家去完成即可。这节课就讲到这里，谢谢大家。
