# 13-16-限制上传图片大小以及格式

完成上传多文件的任务之后，还需要做一些扫尾工作。第一个是对文件格式和大小的校验：不可能让用户上传任意类型的文件，上传的是图片就应该限制为最常见的图片格式；也不希望用户上传无限大小的文件。这两个条件都要限制。egg-multipart 插件里有对应的配置，来看看有什么玄机。

## 白名单限定文件格式

egg-multipart 有一个默认的 WhiteList（白名单），只能上传这些类型的文件，之外的类型会返回 400 Bad Request。我们希望只能上传图片，所以要自定义。自定义方式参考 custom config 一节：如果想添加用 fileExtensions，我们不希望添加而是重写，所以用 override，直接设定 whiteList 参数即可。

打开 config.default.ts，找到 multipart 的配置，whiteList 是一个数组，只保留几种图片格式，其他都不允许。保存后测试：把上传文件换成一张 SVG 图片（不在白名单里），点击 Send，确实返回了 400 Bad Request 和一系列错误信息。

## 自定义错误格式

我们不希望直接抛出这个错误，希望错误都符合一定的格式。之前已经有一个在做这件事的中间件 customError，所以逻辑应该添加到它里面。错误信息已经提前添加好了两条：一个是"不能上传这种文件格式"，一个是"上传文件超过最大限制"。

customError 里已有 `if (error.status === 401)` 处理 JWT 的错误，这里用 else if 多添加一个条件。最好先判断它的 path，也就是确认是在上传路由下触发的再处理，因为 400 错误在很多情况下都可能被触发，需要甄别：`ctx.path` 等于上传路由的路径时，再做进一步处理。条件用 `error.status === 400`，命中就 return，和上面一样：`ctx.helper.error(ctx, 'uploadFormatError', error)`。error 信息取自 error 对象上的 message 属性。

再试一下：点击 Send，出现了自定义的错误 103002，message 正常弹出，详细信息里写着 invalid filename，cannot SVG，说明不能上传 SVG 格式。第一个任务完成。

## fileSize 限制的坑

接下来是文件大小。配置里有一个 fileSize 属性，可以用人类可读的形式设置，比如 '10mb' 或多少 KB 等单位。看起来很简单，但真的这样就能完成任务吗？测试一下。

为了测试给它设一个较小的值 100KB，然后选一张 500 多 KB 的图片，点击 Send。按理应该弹出超过限制的错误，结果并没有，两张图片都上传成功了。刷新控制台，刚上传的两张图片也都出现了。这不是我们想要的结果。为什么限制没生效？

看源码就查到玄机了。回到 context.js 的源码：我们用的 ctx.multipart 直接返回 co-busboy 的 parse 方法，这里面没有任何限制，直接 parse 处理。而假如用插件写好的方法，比如上节课分析的 saveRequestFiles（保存文件的形式），里面会做对应的处理：可以看到 `if (part.truncated)` 时抛出 requestFileSizeLimit 错误。那 fileSize 限制传到哪里了？在 multipart 初始化时的参数里，它的 multipart options 就是我们传递的配置。所以它是经过参数传递并做了错误处理的，而我们的代码根本没有这部分内容，因此出现了这个问题。同理 getFileStream 也经过参数传递，有这个限制，监听 limit、stream 出现 truncated 属性时弹出 limit 错误。

## 照猫画虎修改代码

按照它的逻辑修改我们的代码。第一步，在 ctx.multipart 调用时把参数加上。参数来自 Busboy 的 constructor，里面有 limits 配置，其中有 fileSize 的设置。先把参数拿出来：`app.config.multipart.fileSize`。打印这个参数会发现，它会自动把人类可读的设置（100KB 或多少兆）转换成字节的 number 类型，可以自己实验验证。所以这里不是字符串类型了。

把参数传递进去：`ctx.multipart({ limits: { fileSize } })`。这里有一点小问题：limits.fileSize 期望是 number，而 config 里的值类型可能是 string，但我们清楚它返回的是 number，所以做一个简单的类型断言（fileSize as number）即可。

有了参数的加持，接下来像源码一样判断 part.truncated 属性。这个属性从哪里来？Busboy 文档写得很清楚：假如配置中的 limit reached（达到配置上限），stream 会带上一个 boolean 属性 truncated。出现这个 boolean 属性就说明达到上限了，直接判断即可，和源码中的实现完全一样。放到代码里：`if (part.truncated)`，类型补全都有。命中后 `return ctx.helper.error(ctx, 'uploadSizeError', ...)`，error 里写上"已经达到了最大值上限"，告诉用户已达上限。

点击 Send，错误提示如我们所愿弹出了，并且完全正确。但还有一个问题：刷新控制台可以看到，虽然错误弹出了，但一个文件已经上传了，正好是限制的 100KB 大小，下载下来根本没法渲染，因为只上传了一部分。所以还需要清理工作，把这个文件清掉。

看源码，它也有对应的清理工作：truncated 时调用 cleanUpRequestFiles，把本地上传的文件清除。我们也做清除，清的是上传的云文件：调用 ctx.oss 上的 delete 方法，传入对应的文件路径 savedOssPath。

再试一次：点击 Send，错误弹出没问题；刷新 OSS 控制台，没有新的文件被上传上去，说明清理生效了。最后验证正常情况：都是小于 100KB 的图片，点击上传，两张图片都能上传成功，刷新后多了两张图片，整个流程完整了。

通过这个过程完成了文件大小和格式的限制，还借助源码的灵感完成了对应的错误处理。这就是看源码的好处：如果没有搞清楚源代码以及它的实现方式，遇到这个需求其实不知道该如何下手。
