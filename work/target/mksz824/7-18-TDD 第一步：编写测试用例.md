# 7-18-TDD 第一步：编写测试用例

上节课介绍了 TDD 的开发方式以及 ColorPicker 组件的需求。如果用 TDD 进行开发，第一步就是把这些需求转换成 Test Case。这节课就来写这些测试用例，做法很简单：根据需求分析写出一系列测试。

测试的大体结构已经写好，一共分三个 case。wrapper 创建时要传入一个 props，其中有一个属性叫 value，这是之前分析过的：表单组件都必须有一个 value 属性和一个 change 事件。

ColorPicker 组件现在还是一个空的结构，什么都没有。第一个 case 判断是否渲染出正确的界面结构（should render the correct interface）。先预想一下结构：根据原型图，它是左右两栏。左边是一个 input，type 为 color；右边是一个 ul，class 随便起一个，叫 picked-color-list，里面应该有一系列 li，class 从 0 编到最后。注意最后一个 li 是特殊的：它是透明的，点击后要发送特殊的事件。

来看具体的测试。首先测左侧是否为 input：`expect(wrapper.find('input').exists()).toBe(true)`，存在即为 true。

接着判断类型和值是否正确。要拿到 input 真实的 DOM 节点，用 `wrapper.get('input').element`。然后 `expect(input.type).toBe('color')`，color 是特殊的 input 类型，点击后可以渲染出颜色选择器。value 应该和我们传入的值一样：`expect(input.value).toBe('ffffff')`，传入的是六个 f。

第二个 case 是检测右侧是否有颜色列表。我传入了 defaultColors，它就是默认渲染的颜色列表，所以 li 的长度应该和它相同。注意列表最后一项特意是空的，也就是点击它之后会把颜色属性清除。写法很简单：`expect(wrapper.findAll('.picked-color-list li').length).toBe(defaultColors.length)`。

接下来检查第一个元素的 CSS background 属性是否和对应的颜色相同。新建一个变量 firstItem：`wrapper.get('li:first-child')`。注意 li 下面还包裹着一个 div 结构，真正渲染色块的是这个 div，所以再取它的子元素：`const element = firstItem.find('div')`，并给它做类型断言，断言成 HTMLElement。然后 `expect(element.style.backgroundColor).toBe(defaultColors[0])`。

再测最后一项是否有一个特殊的类名。最后一项和前面都不一样：点击后要发送一个空值，渲染上也有特殊处理，需要用一个特殊的类名渲染出透明的界面。新建 lastItem，用 `li:last-child` 选择器，然后判断 class：`expect(lastItem.classes()).toContain('transparent-background')`，classList 上的 classes 方法返回所有 class，toContain 判断是否包含 transparent-background。这样界面部分的用例就写完了，每条上面都有注释，很清楚。

第二个方面测行为。第一个：修改 input 之后是否发送对应的事件和对应的值。先创建一个要修改成的值，叫 blackHex，是一个十六进制颜色。拿到左侧唯一的 input，用 setValue 变更它的值：`await wrapper.get('input').setValue(blackHex)`。值传进去以后会触发 change 事件，事件应该已经发送，于是 `expect(wrapper.emitted()).toHaveProperty('change')`。

再判断发送出来的事件携带什么值。用 `const events = wrapper.emitted('change')` 拿到事件数组，`expect(events[0]).toEqual([blackHex])`。

第二个行为：点击右侧颜色列表之后，是否发送对应的值。拿第一个元素，这里不需要 element，直接对 firstItem trigger 一个 click。注意前面已经发送过一个 change 事件了，所以现在的事件应该是第二个：`expect(events[1]).toEqual([defaultColors[0]])`。

到这里整个测试用例就写完了。保存之后，现在肯定是一系列失败。但从另一个角度看，我们已经通过测试用例把代码的需求和实现梳理了一遍。如我们所愿，所有测试都 fail 了。下节课就从这些测试用例出发，一个个实现组件的功能，看看这样的开发方式到底怎么样。这节课到这里，谢谢大家，再见。
