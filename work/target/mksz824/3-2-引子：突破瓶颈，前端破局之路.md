# 3-2-引子：突破瓶颈，前端破局之路

上节课抛出的两个问题，是工作两到三年的同学非常常见的困惑，总结起来就是：现在的工作没法和个人提升的意愿相匹配，需要一个更复杂、更高级的项目来提升自己。这种积极上进的态度很好，说明大家有自我提升的驱动力。

"复杂""高级"这类词非常抽象。我个人认为，什么是复杂项目？有同学维护好几万行的老代码，面条一样的逻辑全搅在一起，每天改 bug 苦不堪言；有同学做后台管理系统，每个页面都是差不多的 CRUD 操作，表格控件复制了一遍又一遍。这些项目体量巨大，但它们算复杂项目吗？对自我提升有多大价值？我认为微乎其微。当今的前端开发早已不是刀耕火种的切图时代了。

我定义的复杂项目，可以从两个维度来看。

## 维度一：业务的复杂度

**交互的复杂性。** 前端工程师最早、最大的职能就是处理交互，从下拉菜单的显示隐藏、对话框的显隐，到稍复杂的拖动排序。交互是用户和你写的应用最直观的接触，完成复杂交互是一个难点。以 OpsFlow 为例，画布上的元素可以拖动边框改变大小，按住元素拖动可以改变位置，还有大量属性，改变属性值就会改变元素在画布上的样子。再比如绘制流程图的工具，功能类似：拖动、改变大小、快速编辑文本属性，编辑完立刻反映到界面上。

**数据结构和状态的复杂性。** SPA 应用让前端脱离了"后端渲染页面输出到前端"的简单逻辑，前端会储存非常复杂的全局状态。这些数据怎样设计、管理和高效储存，都是一门学问。OpsFlow 的编辑器界面就有非常多的状态：画布上每个元素的各种属性、模板元素、用户状态、图层设置、页面设置，甚至整个作品的设置，比如预览、保存等等，这些都是全局状态。

**多项目互相依赖的复杂性。** 一个公司一般有好几个项目。这些项目之间往往有很多共性，能否从中抽象出通用的功能？比如界面元素一样：button 长得一样、表单长得一样，就有了组件库；一些数据和状态也可以共享，比如多个项目都要用用户登录、用户信息；还可能有第三方库可以共享，比如自研的弹幕库，两个项目都有视频播放，就可以共用。这就是多项目互相依赖的复杂性。

**针对不同项目进行打包。** 抽象出不同的模块后，要在不同地方使用，就需要打包，输出在不同项目中适配的通用格式，可能是 ES modules，可能是 CommonJS，也可能是比较古老的 AMD。

**性能优化。** 打包过程中可以想到一个点就是性能优化，它是大型项目的要点，省下的流量就是公司的真金白银。我们公司曾有一个组专门搞性能优化，当时用亚马逊的一系列云服务，优化后给公司省了几百万美元，自然也受到老板嘉奖。

**第三方库的使用、调研与二次开发。** Web 世界非常繁杂，不可能所有模块都自研。使用优质的第三方模块可以省时省力，对不完全满足的需求还可以在它上面做二次开发。这也是项目中很容易遇到的基本难点。

## 维度二：流程的复杂度

另一个维度是流程的复杂度，它有一个标准流程化的问题。很多同学从中小公司出来，一个人负责一大块独立业务，戏称自己是"全干工程师"，每次上线只能祈祷不要出问题。而大厂一个日进斗金的项目，开发中要尽量减少甚至消灭缺陷，流程必不可少。开发软件和生产汽车一样，流水线的每个步骤都有具体的流程和生产内容。符合大厂流程的开发实践，是脱离软件小作坊式开发的必经之路。

1. **Git Flow**：大公司如何规范使用 Git 管理项目，开发一个功能时要采用怎样的标准 Git 流程。
2. **标准 Lint 工具**：先制定代码规范，再用 lint 规则统一不同程序员的代码风格，减少差异化，便于管理。
3. **单元测试**：小公司特别容易忽略的东西，没人愿意写，觉得没用。但在组件化的 Web 世界里，组件对单元测试非常友好，通过测试可以让代码更健壮。课程中会一点一滴地灌输测试的知识和流程。
4. **标准 commit 信息**：代码经常要修改或重构，能追溯的除了代码修改本身，还有用人类能读懂的语言描述这次修改到底解决了什么问题。很多人修完问题写的 commit 信息就是"修复 bug""fix issue""update"，后来要改你代码的人肯定要骂娘。标准 commit 信息不仅帮助自己，也帮助别人。大厂对此有特别要求，有些甚至要求前面写 Jira 号，后面写描述。
5. **PR review**：把自己的代码发 pull request 让别的工程师审核，既是防止 bug，也是互相学习的重要步骤。我在公司时从 PR 过程中学到很多有用的知识，而且他们给我提的意见越多我越开心，说明大家都认真看了我的 PR，毫无保留地帮我提高。
6. **CI/CD**：非常重要的一环，是大厂和小作坊拉开差距的重要过程。它让项目迭代更容易，让开发和运维解耦，上线做到版本化，回滚变得非常容易。从此再也不用上线前双手合十祈祷了。

## 授课风格

最后讲讲这门课的授课风格，它和实战课有所不同。实战课我一般从零到一手把手带大家写代码，但到了体系课这个高度，我们不会事无巨细地一对一写代码讲细节，而是培养大家达到前端架构师这个头衔所要求的分析问题、解决问题的能力。

其实在实战课中我也经常说"授之以渔"：我带领大家搭一个架子。拿盖大楼举例，我们教你怎样画蓝图、打地基、建造大楼的基本结构，至于内部风格、选用什么色彩、更多功能，可以根据你的想象力和具体需求自行完成，起到抛砖引玉的效果。

听完这些讲解，对于"什么是复杂项目"这个问题，大家心中是不是也有了一个类似的答案？
