# 8-5-上传基本流程的测试编写

这节课给现有的基本流程添加测试，保证基本功能的通过。上节课演示了三个 case，对应三个功能：初始界面的渲染、上传成功并显示对应界面、上传失败并显示对应界面。从这三个方面保证代码质量即可。

## Case 1：初始渲染

基础框架已经搭好，wrapper 创建之后就可以直接做断言：上传 button 出现在 DOM 中并且有对应的文字，file input 是隐藏的。

第一个断言 `expect(wrapper.find(...).exists())` 强化记忆。第二个断言文字：`wrapper.get('button span')` 的 text 应该是"点击上传"。最后判断隐藏：`wrapper.get('input').isVisible()` 返回 false，用 `toBeFalsy` 断言。

运行测试，第一个测试通过。

## Case 2：上传成功

第二个测试是正常上传流程。真实流程是在界面上点击后手动选择文件触发 input 的 change，但单元测试没法模拟手动点击选择的过程。其实这个过程的目的是触发 change 事件，所以可以直接用 trigger 方法触发 input 的 change。可见单元测试和真实的端到端（e2e）用户操作是有区别的，它不是真正模拟用户全手动的过程。

这里有两个没接触过的难点：一是触发 change 需要特定的事件对象，即 `e.target.files`，怎么给它设置值？二是怎样创建一个文件。

创建文件不需要真的有一个文件，用 `new File` 构造函数即可，它有三个参数：第一个是 bits（内容，一个数组）；第二个是文件名称；第三个是其他属性，比如 `type` 文件类型。据此创建测试文件，内含测试内容、名称 test file、类型 image/png。

关于给 target 赋值，可以求助 vue-test-utils 官方文档的 trigger 一节，其中 "setting the event target" 详细描述了做法：trigger 创建一个 event 对象并 dispatch 在 wrapper element（外面包围的 DOM 元素）上，所以要发送的 target 值没法直接编辑，但可以直接在 DOM 节点上赋值，文档的例子就是拿到 input element 这个 DOM 节点，给它的 value 赋值，然后再 trigger。

照此实现：拿到 DOM 节点 `const fileInput = wrapper.get('input').element`，断言它是 HTMLInputElement，然后 `fileInput.files = testFile`。这时出现了错误：files 对应的是 FileList 对象，而我们给了它一个 File 数组，类型不匹配。FileList 有没有构造函数？经过一小时资料查询，答案是 FileList 没有构造函数，所以只能做类型断言，把最不愿意用的 any 拿过来做一个 hack：`fileInput.files = testFile as any`。TS 通过了，但最终逃不过浏览器的解析错误：浏览器提示 HTMLInputElement 的 file 属性值不是 FileList 类型。

怎么办？经过一段时间搜索，我想到在根源上做一个 hack：使用 Object.defineProperty，它可以直接在一个对象上定义新属性或修改现有属性并返回该对象。于是用它修改 files 属性，value 设为 files，writable 设为 false。删掉之前的赋值方式，测试总算通过了。请大家好好看看这两段代码，这是整个测试的难点，为写这两行我查了半个多小时。解决之后，后面的内容就容易了。

接下来触发 change 之前先模拟 axios：给 mockedAxios.post 设置 mockResolvedValue，并用 once 只模拟一次（之后还有失败的测试），返回值随意写一个 success 状态。然后 `await wrapper.get('input').trigger('change')`（记得加 async）。触发之后，断言 mockedAxios.post 被调用了一次（toHaveBeenCalledTimes(1)），并且界面文字变为"正在上传"。再用 flushPromises 把 promise 推到最终状态，断言文字变成"上传成功"。运行测试，通过。

## Case 3：上传失败

上传失败的测试很简单。这里我重新创建一个 wrapper，让成功和失败两个流程互不影响（也可以继续用之前的 wrapper，看大家习惯），我这里直接继续写下去了。

重新 mock 一次：`mockedAxios.post.mockRejectedValueOnce('error')`。再触发一次 change。由于多次调用之间没有 reset，post 的调用次数应该是两次。中间的"正在上传"判断也照抄。最后断言文字是"上传失败"。运行测试，全部通过。

至此上传基本流程的测试用例书写完成，以后开发新功能时就不必担心影响之前的功能了。在开发进度表的第一个功能前打一个勾，并把经验（尤其是 trigger input 的各种 hack）记录在下面，值得记下来。这节课就到这里，谢谢大家。
