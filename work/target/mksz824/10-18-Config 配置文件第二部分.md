# 10-18-Config 配置文件第二部分

上节课我们解释了配置文件中的可配置项，以及在不同环境下采用不同的配置文件。这里还有一个希望：能让配置文件发挥 TS 的威力。因为我们发现，写的一些业务逻辑，也就是 baseConfig 里面的类型，在不同的文件中没法做到自动联想，这就是个问题，因为这些属性同学们经常写错。我们希望它有 TS 提供的类型。

最终的愿望是在多处都要有类型支持。第一处，是在 controller 和 service 当中能够获取正确的类型，能够支持多级提示并且自动关联。第二处，是在其他配置文件中能够获得我们 default 中的一个正确的类型，比如在 config.production 和 config.local 当中，我们也希望有这一系列的提示。最后是在中间件中，因为中间件也可以获得它同名的相应配置，它也希望能获得正确的类型。

其实 Egg.js 生成的 config.default.ts 模板文件已经非常接近这个目标了，它的目的是把 baseConfig 这个类型合并到 PowerPartial<EggAppConfig> 类型当中去。

先解释一下模板文件中几个特殊的写法。第一个写法是添加了一个特殊的类型断言：`as PowerPartial<EggAppConfig>`。大家都记得 Partial 这个内置类型，它可以将一个对象上的所有属性都变成可选。而 PowerPartial 是 Egg.js 特别推出的、在 Partial 之上的特别类型。看名称就可以知道，它做的也是 Partial，只不过更进一步：可以在多个对象嵌套的情况下，将内嵌对象也变成可选。把鼠标放上去可以看到解释，里面有个例子：有一个对象是 view.defaultEngine，它是嵌套的，然后这两层都可以变成可选。我们也能感受到，在 config.security 上面我们也可以支持一系列嵌套的输入，比如 xframe.enable，都是可以的，这就是 PowerPartial 的威力。

解释完这个，第二步说说为什么模板代码并没有生效。其实是它的代码出现了一点问题：文档中修复了这个问题，文档里的代码是没有问题的，但模板代码并没有修复。先明确 Egg 是怎样把这个类型（我们最终想扩充的类型，EggAppConfig）进行扩充的。如果大家去研究自动生成的类型，比如打开 typings 文件夹，会发现里面的一系列内容跟你的文件结构是对应的。看 config 下面的 index.d.ts，会发现有这么一系列代码。注释特别写到：这个文件是自动生成的，不要随便修改。给大家解释一下这段代码是怎样运作的：它首先拿到了 egg 当中的 EggAppConfig，这是原始的类型；然后特别注意它把我们的 config.default 文件 import 进来了，因为我们导出的是一个函数，所以用 typeof 操作符先拿到这个函数的类型；拿到函数的类型以后，再用 ReturnType（TS 提供的内置类型，可以拿到一个函数类型的返回类型）拿到返回的类型；拿到返回类型后起了个别名，然后进行扩充，这样完成了 EggAppConfig 的类型扩充。

但现在的问题是它没有扩充成功。原因在哪？config.default 直接的返回类型是 any，所以最终 EggConfig 就是直接 extends 了一个 any，等于没有添加任何类型。直接去看 default 文件，把鼠标放上去就可以看到它返回的是 any 类型。问题就出在这里：我们希望它返回的是 baseConfig 上的类型，但在 baseConfig 和 config 进行合并组合的过程中，由于 config 的不确定，把它变成了 any 类型。

文档中教了我们很讨巧的一招：现在我们的关注点就是 baseConfig 这个类型，希望把这个类型扩展到最终的 appConfig 类型上去，所以直接添加一个类型断言，把它断言成一个空对象 `{}`，不让 config 去产生任何影响。现在观察修改以后的类型：config.default 返回的就是 baseConfig 上面的一系列类型；再看 index.d.ts，config.default 变成了这个类型，然后进行扩充，把业务逻辑的一系列配置的类型扩充到上面，就完成了整个过程。这样我们就修复了这个文件中的一个小的类型问题。有兴趣的同学可以去 Egg 官方提一个 pull request，帮他修复。

现在尝试一下效果。首先在其他的配置文件中要有联想，所以来到 config.production，写 config.myLogger，这时候已经能联想出来了；myLogger 当中的值 allowedMethod 也能联想出来，没问题。

除了配置文件，刚才说了还要在 controller 里做一个对应的测试。在 controller 当中，可以在 ctx.app.config 上面拿到整个的类型，点一下 myLogger，这时候也出现了，allowedMethod 也能自动联想出来，说明在 controller 中也没问题。

最后在中间件中进行处理。直接到 myLogger 当中，这里的 options 还是 any。现在希望让它获取对应的类型，就是跟它同名的一个类型。把 AppConfig 拿出来，这是经过组合以后的新类型，直接能拿到 myLogger。拿到以后它里面所有的属性都可以出现，我们就不用再手打了。做个测试：`options.allowedMethod` 出现了，并且它是个数组，可以调用数组的一系列方法，比如 includes。这样就避免同学们打错这些比较复杂的子字符串。

任务完成了。通过这节课我们成功修复了 config 当中的一个类型问题，让不同的文件都能享受 TS 的红利，让一些自定义的配置也可以轻松地完成多层级的自动联想，很完美。
