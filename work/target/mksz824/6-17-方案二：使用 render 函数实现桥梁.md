# 6-17-方案二：使用 render 函数实现桥梁

这节课讨论第二种实现方案，也就是不使用 JSX 的方案：怎样在 Vue template 中渲染一个 VNode？在之前的演示中大家看到，使用 template 最终的结果也是转换成 createVNode 一系列创建虚拟 DOM 节点的过程。转换过程中编译器会处理 template 上面的一系列指令，然后根据这些指令生成 createVNode 的逻辑。但这个过程中对于一些对象（比如一个 VNode），它会被直接转换成 string 进行输出。所以我们想给中间加一层转换：新建一个使用 render 函数或者 Function Component 的组件，在里面使用 JSX 或者 createVNode 完成这个功能。

到这里，Vue 写组件的三种方式我们也算接触到了。第一种很熟悉，就是一直使用的单文件形式 SFC：混合了三种标签，使用 .vue 作为后缀名，它返回一个 Vue template 特殊写法。第二种是 Function Component：直接用一个函数描述整个组件，返回内容可以写成 JSX（一种语法糖），也可以直接写 h 函数。第三种称之为 Render Function：它是一个对象，对象上有 render 方法进行返回，同样使用 JSX 或者 h 函数书写。像这样，定义一个对象，使用 render 方法，里面写对应的 JSX。

除了这些，还有一种特殊的方法我们也预见了：在 setup 中直接返回一个 function，里面同样使用 JSX 书写。

现在创建一个组件，使用 render function 进行转换。当 template 编译到这个组件的时候，会执行组件内部的逻辑，从而把里面的内容转换出来。所以这个组件就像一个桥梁一样。看看怎样做，很简单：这里我创建了一个 RenderVnode.ts 组件，defineComponent 已经写好。首先确定 props：一个叫 vnode，type 是两种：一种是 VNode，写成 object；另外一种是 string。它是必选项，required 为 true。

写完 props 写 render，return 什么呢？其实直接返回 vnode 就可以，不管它是对象还是字符串，直接返回就能渲染了。这个函数就这么简单，作为一个中间的桥梁。

现在把这个组件引入到 PropsTable 当中：import RenderVnode from './RenderVnode'，添加到 components 属性上。然后在模板中使用它做替换：写 render-vnode，它有一个属性叫 vnode，应该等于 option.text。把原来直接渲染的删掉。到界面上看看是否好用：点击一下选择，可以看到字体被渲染成功了，说明组件成功起了作用。

我们使用一个非常简单的带有 render 函数的组件就完成了这个任务。当然写成 Function Component 也是一样的，这里这样写是为了让大家了解组件的多种写法。

最后我们发现，这么多种组件的写法，最后返回其实就两大类：一类是单文件组件上面使用 template 的返回，另一类是我们使用 JSX 或者 h 函数的返回。来看一下这两种各有什么优劣。

先说 template 的语法。优点有三个。第一，它内置了非常多的指令，可以快速完成一系列任务。第二，它基于 DOM 结构，很容易看清代码要表达的意图，而且 DOM 对很多程序员来说很亲切。第三，Vue3 基于 template 分析做了很多优化，并且对使用者是透明的，编译器默默完成了所有的优化操作。缺点当然是不够灵活：对某些特定场景它比较难以胜任，刚才这个场景就是一个例子。

再说 JSX 的优点：灵活，可以使用 JavaScript 表达各种逻辑。缺点有两个。第一是可读性差，这其实也是过于灵活带来的后遗症：因为它太灵活，大家怎么写的都有，很容易出现比较糟糕的代码，而且难以理解。第二是刚才说的编译优化：template 会有默认的优化分析，假如使用 JSX，则需要手动进行一些优化操作，比如提取静态的 JSX 片段到 render 函数外部等等。

对比两者的优劣，说一些结论。我的结论是优先选择 template；当 template 写起来比较费劲或者完成不了的时候，可以选择 JSX。其实官方也是这么说的：Vue 推荐在绝大部分情况下使用模板（template）来创建你的 HTML，而在某些特定的场景中，你真的需要 JavaScript 的完全编程能力，那么就可以使用 JSX。

第一个特性的完善就讲完了。通过这个小需求的完成，我想给大家灌输的是多种写 Vue 组件的方法，以及它们之间的关系和优劣，不知道大家掌握得怎么样。这节课就到这里，谢谢大家。
