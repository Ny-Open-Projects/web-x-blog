# 17-6-2-编辑器获取作品 第二部分 - 根据数据渲染至画布

上节完成了 actionWrapper 的改造，编辑器页面已经能成功发请求拿到数据。这节在 fetchWork 对应的 mutation 中处理数据，把作品渲染到编辑器里。

## 编辑器需要什么数据

编辑器要正确显示，需要哪些数据？看一直在用的 EditorProps：可能来自后端的有两部分。第一部分是 components，中间编辑渲染的数组，最重要；另一部分是 pageData，它有两层，第一层是页面基本信息（id、title、description、coverImage 等），第二层是 props 这个对象，里面保存页面的一系列属性。

再看后端返回。请求 `api/works/71` 的返回简化后是这样的：id、title、description 第一层平铺在 data 里，对应编辑器的 page 一层；但注意，pageProps 不是平铺的，它在另一个 content 下面的 props 里；components 同样在 content 当中，是一个数组。所以前后端结构之间要做一次简单的转换。

## 定义 WorkData 类型

先把 pageData 稍作修改，补充了几个保存作品时要用的属性，它其实有很多属性，用到时再陆续添加，暂且加这么多。

然后到专门界定后端返回类型的 responseTypes 里新建类型。作品信息和编辑器结构一一对应，只是 props 的位置不同，所以可以直接复用 pageData：从 editor 导入 PageData 和 PageProps，用 TypeScript 内置的 Omit 工具类型做继承，第一个泛型传 PageData，第二个传要省略的属性名 props（后端结构里 props 在 content 下面，第一层没有）：

```ts
interface WorkData extends Omit<PageData, 'props'> {
  components: ComponentData[]
  props?: PageProps
}

export type ResponseWorkData = ResponseData<WorkData>
```

components 的类型是 ComponentData 数组；props 是可选的，后端新创建的作品没有 props，但 components 一定在，即使没添加任何元素也是空数组，所以加问号。最后导出 ResponseWorkData，即最基本的 ResponseData 传入 WorkData。

## mutation 中的转换

有了类型，到 store 里处理。新添加 fetchWork mutation，第一个参数 state，第二个参数 data（ResponseWorkData 类型）。

要做的是把后端结构转成编辑器结构。先取除 content 以外的所有属性，用三个点的 rest 语法：从 data 中把 content 单独解构出来，剩下的自动组成一个 object，id、title、description、coverImage 就都在里面了。

赋给 state.page 时不要直接等于 rest，因为创建作品时 page 有一系列默认属性，用展开写法把 rest 覆盖上去即可完成属性复制。剩下两项就简单了：先判断 content 存在（可能没有），然后 `state.page.props = content.props`、`state.components = content.components`。类型全部正确匹配。

## 验证效果

展示界面，还是选作品 71，它的数据比较丰富。页面加载后编辑器完整还原了之前存储的内容：两个文字元素和背景图片都在。点击页面设置，高度、背景图都存在；点击文字元素，字体、加粗、尺寸等属性也都正常。

至此成功从后端读取数据并渲染到编辑器上。两节课下来，数据展示的任务完成了。
