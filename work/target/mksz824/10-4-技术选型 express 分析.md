# 10-4-技术选型 express 分析

课程开始之前我们说过，会使用 Node.js 和 TypeScript 进行应用的开发。在最终选择之前，需要调查一下目前最流行的几个 Node.js Web 应用框架。由于最终不会选用这几个框架，所以不会深入它们的代码，只谈谈它们的优势和劣势，以及为什么我们不选它们。

第一个当然是 Express，它应该是使用人数最多的 Node.js 后端框架。看它的 GitHub，star 数达到了惊人的 54.7k。它最大的特点，到首页就能看到这么几个词。第一个叫高度包容，翻译成英文是 unoptionated，意思是没有任何规则：项目中的文件结构、代码组织方式、书写方式，都没有明确规定应该怎么写，可以说是没有任何限制。之后的特点还有快速而极简，这从它的名字就能看出。

快速极简和高度包容在一定程度上是双刃剑。没有规则会让上手非常迅速，用简单的代码就能运行程序，对一个人搭建快速应用来说非常合适，比如要做一个 to do list。但对多人协作的项目来说，如果代码没有合理的分层和标准约束，很容易出现一个回调函数中一大坨代码的情况，也就是意大利面条式的代码。所以现在很多流行的框架会在 Express 的标准上进行二次开发，二次造轮子，打造一些具有强约束的框架。其中有个叫 NestJS 的，也基于 Express，是现在非常火的 Node.js 框架。

回到 Express。相信很多人已经用过，所以我计划只花五分钟简单了解一下它的语法，重点是后面手写它的中间件。因为它的中间件和我们之后要调研的 Koa2、以及要使用的 Egg.js（Egg 基于 Koa2）的中间件，有本质上的区别。

我已经新建了一个项目，非常简单。npm 安装 express 之后就可以使用。如果想看复杂的例子，文档入门部分有一个 Express 生成器，用 `npx express-generator` 加目录名称，就可以生成一个复杂的例子，里面会包括一个完整的 Web 应用，还预装了模板引擎和中间件等常用内容，可以自己试试。

我认为一个 Web 应用，即使是最复杂的应用，核心内容其实就是和 HTTP 相关的几部分：第一是路由，在什么样的 URL 上触发什么样的内容；第二是请求，也就是 request；最后是 HTTP 响应，也就是 response。学习任何新的 Node.js 后端框架，先把这几个问题搞清楚，就可以快速上手了。

现在看 Express 解决这三个问题的方法。我已经创建了入口文件，添加了一个简单的程序，在 package.json 里用 npm start 就能运行。我添加了 nodemon 作为 dev dependency，它的作用是当 app.js 有修改时就重新执行应用，方便快速看到修改后的结果。Express 的代码都是非常直接的，即使没用过它，也能很快弄懂。

核心三要素。第一个是路由，是在 app 上面定义的一系列方法：app.get、post、patch 和 delete，URL 是它的第一个参数。假如对根目录请求就输出对应的代码；拷贝一份写到 /test 路由上输出 hello test，访问 /test 就能看到 hello test。

第二个要素是请求。请求来源于 router 的回调函数，也就是第二个参数回调函数中的第一个参数，我们用 req（request）命名。在上面能拿到一系列和请求相关的属性，比如 query：请求时带上 `hello=a`，输出 req.query 就能拿到对应的 query；还有 headers，输出 req.headers，headers 信息也就都来了。所以关于请求的内容，其实都是 req 上面的一系列属性。

第三个要素是响应，来自第二个参数 response。response 上面有一系列方法用来返回不同的 HTTP 内容：send 直接返回一个普通的字符串；想返回 JSON 可以直接调用 json 方法，虽然内容格式一样，但它返回时会添加 content-type 为 application/json，说明返回的是 JSON 类型；还有一个 download，可以生成一个可下载的响应。我们添加一个指向 jpg 文件的 download，刷新页面就能看到它帮你下载一个文件。

五分钟就解释了 Express 的三大要素，其他的无非是深入文档，查一下 request 和 response 还有哪些具体属性，会了解得非常快。

Express 就是快速的意思，这也是它的一大优点：快速、简单、易上手。初学者花五分钟也能运行起来一系列可用的代码。但对大型项目，我认为问题有这么几个。第一，路由响应中很可能有从外部请求服务的逻辑，比如从数据库请求特殊的数据、从第三方 API 请求对应的数据；还有验证路由请求参数的逻辑，要验证是否传递了某个参数；以及返回特定的 JSON 格式。假如把这些逻辑不分青红皂白地全部写在一起，就很容易产生非常冗长且难以维护的代码，这是它的一大缺点。另外还有一些大型应用必备的步骤和模块：第三方服务需要初始化，比如数据库需要一开始建立连接，这些代码写在哪里？HTTP 的安全，比如防钓鱼攻击、防 XSS；日志应该怎样储存和切分？这些模块都没有明确的标准，需要你自己去实现或制定，带来非常多的额外工作。

这就验证了开头说的：快是 Express 的双刃剑。应用选择框架时要按照具体需求做定制化的选择。结论就是 Express 不太适合我们的应用，我们不选它。不过下节课还要了解一下它的中间件，我会写一个简单的中间件，让大家明白它的工作原理，这是它最重要的内容。
