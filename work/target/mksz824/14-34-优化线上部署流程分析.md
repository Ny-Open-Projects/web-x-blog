# 14-34-优化线上部署流程分析

通过几节课学习了 GitHub Actions 的简单用法，加上上节课学的 SSH action，其实已经能完成更新线上应用的任务了。流程很简单：每次代码更新后，登录到对应的服务器（使用 SSH action），然后：

1. 关闭服务：`docker compose down`；
2. 更新代码：`git pull`。如果 .env 有更新（可能添加了新服务、新的敏感信息），需要重新设置 .env，往原始文件里添加新内容（这步不一定有）；
3. 重新 build 应用镜像：代码已更新，`docker compose build opsflow-backend` 生成新的本地镜像；
4. 重启服务：`docker compose up -d`，完成整个线上更新流程。

大家可以自己试一下，但我不会采用这种方案，因为它不能完全满足需求，应用场景很有限：要让它跑起来，必须有一步预先操作。初次上线和更新其实是两件事，初次上线需要特别的操作，就是之前手动部署的过程：clone 代码、设置环境变量，最后 docker compose up -d。两步完全分离。

我追求的效果是：每次提交可以自动一次性部署到任何服务器，实现初次启动或更新。我认为这才是真正完美的 DevOps 流程。这是个宏大的目标，实现它对前端来说也会有巨大的喜悦感。

## 审视 docker-compose 文件

实现目标前，第一个任务是审视目前的 Docker Compose 文件。这是我简化后的文件，认真观察会发现里面有一个镜像可谓异类：我们自己的应用 opsflow-backend。为什么？因为它是一个本地镜像，每次需要手动 build，里面有特殊的 build 字段：context 是本地文件夹，dockerfile 是我们的 Dockerfile，这个镜像只存在于本地。而另外两个依赖的服务 opsflow-redis 和 opsflow-mongo，镜像都是从 Docker Hub 直接拉取的。

于是有一个思考：如果 opsflow-backend 的镜像也能存在远端仓库上，每次发布有对应的版本，那么运行整个应用就不需要代码库中的任何文件了。比如镜像在仓库中的版本是 1.0.1，每次直接拉取这个版本就好；我们只需要一个 docker-compose YAML 文件，运行 docker compose up，应用就可以轻松地在任何服务器直接运行。非常方便。

所以现在第一个任务是：有一个服务可以把我们 build 好的镜像直接 push 上去。之前用的镜像来自 Docker Hub，但去看它的定价页面会发现：免费的话对私人镜像是有限制的，所以需要一个国内服务来完成这个任务。我推荐阿里云的容器镜像服务（ACR），地址在文档里。它的个人版完全免费，完全能胜任现在的任务。

注册后点击管理控制台，会有智能助手帮你一步一步完成。选择个人版后有一个新手指引（我已完成，就不演示了），大概几步：先设置访问凭证（一个密码），然后创建命名空间，命名空间其实类似于 GitHub 的用户名；然后可以建一系列镜像仓库，镜像仓库属于你的命名空间，里面保存对应的镜像。地址结构是：命名空间在前、镜像仓库在后，再带镜像版本号，这就是一个保存镜像的路径。

留给大家的任务：注册 ACR，创建自己的命名空间和镜像仓库。这节课针对部署流程提出了优化方案，需要私有镜像存储服务，引出了阿里云 ACR。下节课看构建好的镜像怎样推送到对应的存储空间。
