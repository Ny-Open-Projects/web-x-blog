# 21-12-使用 jwt 实现用户验证 后端编码

上节课完成了前端登录注册的基本流程，后端在数据库里查到了具体用户（findOne）并进行了 compare。现在进入下一步：用户认证。认证采用 JWT 形式，关于 JWT 的详细情况请参考之前的后端课程《用户系统设计与实现》第五章"使用 JWT 完成用户验证"，里面有 JWT 方方面面的知识。这种无状态的认证方式也是现在最流行的，细节不再展开，直接编码。

今天的任务有两部分：一是把 login 接口继续写下去，用 JWT 加密登录后的信息；二是设置规则保护对应的 API，也就是一些路由需要有登录状态才能访问。

## 安装与配置

请自行安装 `jsonwebtoken`：`npm install jsonwebtoken --save`。特别注意它的类型定义文件要单独安装：`@types/jsonwebtoken`，两个依赖都要装。

然后配置 JWT 选项。JWT 加解密需要一个 secret，写到配置文件里。在 runtime config 后面加一项 `jwt`，第一个字段是 secret。secret 是非常敏感的信息，要放到 env 里。env 里的命名规则再强调一次：想覆盖配置，环境变量要以 Nuxt 开头，然后是 JWT、SECRET，和配置路径保持一致。我这里直接设成了 XYZ，大家可以按自己的喜好设置。除了 secret，还要配置过期时间 `expiresIn`，以秒计数，我们希望一小时，即 60 乘 60。

## 签发 token

来到 `login.post.ts`，把逻辑继续写下去。要把哪些信息加密到 token 里？不需要把整个 user 加密进去，里面字段太多，只加密它独特的属性：`_id`（最关键的 ID）和 username，这两项是最能代表唯一性的两个条目。

```ts
const config = useRuntimeConfig()
const userData = {
  username: user.username,
  userId: user._id
}
const token = jwt.sign(userData, config.jwt.secret, {
  expiresIn: config.jwt.expiresIn
})
```

把 jsonwebtoken 拿过来，用它的 `sign` 方法。第一个参数是要加密的数据 userData；第二个是 secret，来自 config（注意这里 config 还没拿，先 `useRuntimeConfig()`）；再加一个特别属性 expiresIn，即多久过期，直接用配置里的值。

## 用 cookie 保存 token

token 生成后保存到哪里？我们用 cookie 保存。cookie 设置完毕后，只要在相同域名下，每次请求浏览器都会自动带上并发送。cookie 的具体知识很多，可以参考《用户系统设计与实现》第四章"使用 session 实现用户验证"第一节"cookie 的基础知识回顾及加深"，这里不赘述。

Nitro 提供了非常好用的全局函数 `setCookie` 来完成设置。它接收四个参数：event 事件对象；cookie 的 key，设为 token；对应的值，即这个 token；还有配置选项。cookie 也希望有过期时间，和 JWT 保持一致，两者同时过期，是比较完美的方案。配置选项叫 maxAge，单位也是秒，含义是过多少秒过期，把 expiresIn 直接传过来就行，两者单位和意义完全一样。最后把 user 数据返回出去，整个 login 过程就完美了。

这里 user 有个问题：它含有 password 等敏感信息。记得我们在 user models 里设置过 `toJSON`，用它可以删掉这些字段。返回时也希望删掉，所以要把 `.lean()` 换成 `.exec()`：lean 已经转换成了简单 JSON，不能再调用 toJSON，exec 返回的是完整的 document 类型，可以调用 `user.toJSON()` 后返回。

## 测试

编码完成后先测 API 是否返回 cookie 和用户信息，用 Postman 更简单。请求 login 接口并写入 email 和 password，点击发送：成功返回了用户信息，cookies 里也返回了 token，value 就是加密后的值。之后用户信息就要用这个 token 解密取得 ID 和 username。

## 中间件保护路由

第二部分任务是保护一系列 API，有的必须登录后才能访问。想到的最佳位置就是 middleware。之前在 server 下已经创建了 `auth.ts`，里面的旧内容没用了，直接删掉。

middleware 会在所有路由上运行，所以先要判断哪个 API 不需要登录、哪个需要。目前的需求是 login 和 signup 不需要登录就能访问，其他 API 都需要登录才能访问。用正则来匹配是最优方案：API/users 下的路由只有 login 和 signup 不需要验证，其他都需要，这个正则完美实现了需求。未来有更多规则可以一一添加。

接下来进行 test：

```ts
if (!regex.test(event.path)) {
  return
}
```

匹配到 login 和 signup 就直接 return，不需要验证；其他在 api/users 下的路由才需要验证。

验证需要 JWT 上的其他方法。先拿 config（`useRuntimeConfig()`），再用 `getCookie(event, 'token')` 拿刚才保存的 token，和 setCookie 完全相对：第一个参数是 event，第二个是 key。然后判断：如果根本没有 token，直接抛错：

```ts
if (!token) {
  throw createError({
    statusCode: 400,
    statusMessage: 'unauthorized'
  })
}
```

测试这个分支：Postman 里 api/users 已在中间件的作用下。先把 cookie 完全删掉（如果已设置，请求会自动带着，点开 cookies 能看到 token 已存在），删除后发送请求，弹出 unauthorized，说明分支在运作。

## 解密与上下文存储

继续往下写。这里有解密过程，完全可以写一个 try catch。加密用了 sign，解密对应的是 `jwt.verify`：传入 token 和 config 上的 jwt secret。

验证以后要把数据保存在一个地方，供中间件之后的路由逻辑使用，因为后面需要拿到 ID 或 username。可以用缓存如 Redis，或者某个变量。这里有一个特别适合的位置：event 上有个属性叫 context，就是让大家保存在事件对象上共享的上下文信息。把解密出的 userData 保存在这里：`event.context.user = userData`，整个流程就完成了。

还要处理错误。catch 里要做几步：说明 token 是假的或已失效，先把 token 删除，和 get/set 相对还有一个 `deleteCookie`，把 event 和 token 的 key 传进去完成删除；最终再抛错，告诉用户 token 已过期。

## 全流程测试

保存后试一下整套流程。首先登录：之前 cookie 删掉了，重新点击 login 的 send，cookie 成功种上。同一个 URL 下 cookies 会被自动带着，再点 send，验证通过，数据返回了。看 headers，cookie 被自动带着：token 等于多少多少，就是刚才加密的值，说明 verify 成功，也拿到了之前存进去的值。

再做个反向测试：把 cookie 的 token 改成错误的值，删掉前三个字符，保存后再次发送请求，就会显示 token 已过期。
