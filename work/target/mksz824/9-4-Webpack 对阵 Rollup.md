# 9-4-Webpack 对阵 Rollup

上节课我们介绍了打包工具的最大用途，也提出了目前市面上最出名的两大打包工具 Webpack 和 Rollup，并用命令行跑出了打包后的代码。和很多工具、框架一样，这里先做一个简单的对比，说说两者各自的特点。两者在不同领域各有优势，掌握不同的打包工具，在我看来是架构师挺重要的一项技能。

所以本次课程里，Webpack 和 Rollup 都会涉猎，而且会用在两个完全不同的场景中，目的就是扩展大家的知识广度。

先说 Webpack。对前端工程师来说，这个名字应该如雷贯耳，就算没直接用过，也多半听过它的大名。它是打包界的老大哥和前辈，诞生于 2012 年，目的就是上节课说的那件事。这张图说得很清楚：把各种各样互相依赖的文件，包括 JS、Image、CSS file、模板文件等，统称为一系列的 assets，也就是 modules with dependencies；再通过特殊的配置和插件，用 Webpack 生成一系列可供用户使用的静态文件，也就是 static assets。所以 Webpack 的最大定位，就是致力于大型 SPA 项目的模块化构建，也就是我们常说的 Web 应用。

它的特点有这几个。用过 Webpack 的同学都知道，它有非常丰富的 loader，用来处理各种不同类型的静态资源；还可以通过各种插件 plugins 对整体文件做统一维度的处理；它提供 code splitting，可以把公共模块提取出来。开发相关的能力也很全：提供 webpack server 支持本地开发，而且 server 支持 HMR 热替换，模块热替换非常方便，修改一个模块时浏览器不用刷新就直接替换。你会发现它的逻辑思想都围绕一件事：Web 应用的开发和打包一条龙服务。所以对脚手架工具来说它毫无疑问是首选，Vue CLI、Create React App 底层都选了 Webpack 做本地开发和打包。记住，它是一个适用范围很广的工具。

接下来说 Rollup。先讲一个新闻：2017 年 Facebook 把 React 的构建工具换成了 Rollup。不止 React，Vue 和 D3 等众多知名项目也都用 Rollup 做构建打包。它们为什么没选 Webpack？

原因是 Rollup 设计之初就面向 ES Modules，目标是构建出结构扁平、性能出众的类库，特别注意"类库"这两个字。ES Module 和 CommonJS 的最大区别在于：CommonJS 是动态的模块系统，在任何地方都可以调用 require，运行时才知道需要什么模块和方法；ES Modules 则相反，它走静态化路线，编译时就能确定模块的依赖关系，以及输入和输出的变量。为了让模块静态化，ES Modules 定了一系列规则：第一，import 只能作为模块顶层的语句，不能出现在 function 里面，也不能出现在 if else 里面；第二，import 的模块名只能是字符串常量；第三，不管 import 语句写在哪里，模块初始化时所有 import 都必须已经导入完成。看起来这些规则让灵活性不如 CommonJS，但换来的是 ES Modules 可以被静态分析。

那什么叫静态分析？就是工具在运行之前就能告诉你哪些模块被引入、哪些模块被导出。从图上可以看到，最上面两个 import，一个 `import myComponent from "myComponent"`，一个 `import add from "mathUtilities"`，经过工具分析都可以变成 AST，也就是抽象语法树。有了语法树，打包工具做优化就有了可能，于是就有了 Rollup 最早独特发明的特性：Tree Shaking。很多人应该听说过，翻译过来就是摇树，摇一棵大树让死叶子掉下来。Tree Shaking 支持 ES6 Modules，因为 ES Modules 可以细粒度地引用模块中导出的内容，模块里没有被使用过的引用代码就不会被打包。

上节课的例子正好体现了这一点。hello 模块有两个 function 用 export 导出，而 main 当中只使用了其中一个 hello，另一个并没有用到，我们只调用了 hello。看一下最终打包出来的代码：只剩下了 hello，另一个导出因为没被使用，自动被 Tree Shaking 摇掉、直接丢弃了。这就是 Tree Shaking 的特性，帮我们去掉根本没用到的代码片段。当然现在 Tree Shaking 也不是 Rollup 的专属了，虽然它是发明者，Webpack 2 其实也已经支持这个机制。

Rollup 的第二个特点是哲学思想很简单，只有一条：把 ES Modules 打包生成一种特定类型的 JS 模块文件，并且最大程度减小它的体积。它做的事情很专注，就是打包脚本并让它变小，跟 Webpack 那套 App 开发服务一条龙都没什么关系。

对比完特点，结论就出来了：构建 App 应用的时候，Webpack 明显更合适；但如果是纯 JS 的类库项目，Rollup 明显更合适。Webpack 的优势在于强大的生态系统（各种插件和 loader），面向开发的各种特性（HMR、按需加载、公共模块提取），以及面向 Web 开发的简化能力（比如图片自动转 Base64、资源缓存等）。Rollup 的优势：第一，它专注做一件事，构建高性能的模块文件，这正是做类库所需要的；第二，上节课也看到了，编译出来的代码可读性很好、体积更小、执行效率更高，而 Webpack 构建出来的是一大堆混淆在一起、不易读的代码；第三，它的配置相对 Webpack 简单很多。Webpack 初期的配置相当复杂，甚至有个笑话，说有个专门的职业叫 Webpack 配置工程师，大家对它的配置都颇有微词。

通过分析再次得出结论：组件库是一个纯 JS 模块，所以我们自然选择 Rollup。
