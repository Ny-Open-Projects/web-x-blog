# 7-2-为什么要有测试

上一周我们完成了 LText 业务组件的样式和编码部分的工作，以及连接器的一部分功能，整个编辑器已经大体开始工作了。那么这一周是不是要赶快继续写完其他没有完成的组件呢？答案是否定的，因为这时候我们已经发现了开发过程中的一些痛点。

要测试一个组件好不好用，唯一的方法就是手动创建一大堆不同类型的组件，给它们冠以不同的属性，然后用肉眼观测页面上的组件是否符合预期。这是一种非常低效的做法：工作时间长、眼花了，可能把错的看成对的，人终究会犯错误。还有更麻烦的情况：更新代码、给原来的组件添加新功能时，需要把每一种类型属性的组件重新创建一遍，再观测一遍，看看新代码对原来的功能有没有影响。这样的效率实在太低了，光听这么一说脑袋都大了，更别说去做了。

所以这周来讲这套课程中比较重要的一部分：测试。我希望通过这周的学习，让每个开发者真正体会到测试的好处，并且爱上给自己的代码写测试。

先聊聊测试在国内的现状。我觉得它是一个被严重忽视的话题。第一，很多公司把它看作无足轻重的内容，在项目进度和压力之下，很少有人能在完成功能的同时为代码提供测试。第二，需求一直在修改，测试的 case 经常需要更新和维护，这让许多工程师想写都觉得绝望。第三，很多工程师并不知道测试应该怎么写：从何开始、应该设计哪些 case。于是开发完功能后就是自己在界面上点来点去，觉得没问题就上线，上线后只能闭着眼睛祈求没有重大 bug 出现。

上面这几点概括了国内互联网公司测试的现状。人类面对重复、复杂的流程时很容易犯错，但计算机非常喜欢处理重复性的复杂流程：不会疲倦、不会累、不会像人一样犯错。所以聪明的程序员可以写一些任务，让计算机完成类似的自动化流程，让每次提交代码后都把相应的流程跑上一遍又一遍，不需要自己在界面上点来点去。

测试的第一个优点：保证你的代码可以运行并且没有 bug，从而产生高质量的代码。第二：更早地发现 bug，很实际的一个目的就是为公司节省成本。想象一下，bug 上线后才暴露，对产品冲击有多大，公司可能损失很多钱。第三：测试可以让重构和升级更加容易、可靠。当你升级重大功能或者重构大部分代码时，测试可以保证升级后的版本没有问题；要为应用添加新 feature 时，往往需要修改旧的代码和设计，如果原来就有单元测试，就可以用敏捷的方式开发新功能，而没有后顾之忧。

接下来介绍一个概念：测试金字塔。它是 Martin Fowler 在 2012 年提出的，现在已经是很多大公司设计自动化测试和持续集成的最佳实践。金字塔从下到上：底座是 unit test，单元测试，把代码分成很多互相独立、没有相互依赖的部分，测试每一个部分都能良好工作，可以联想 Vue 或 React 的每一个组件；中间是 service test，把几部分单元测试组合起来，验证它们还能良好工作；最上面是 UI test，也称为 e2e test，模拟真实的用户场景对整个应用进行测试，可以模拟点击、填写表单等一系列操作。

从金字塔上应该发现，单元测试占比是最多的，因为它们容易编写、改动小、容易维护，而且跑起来时间短。越往上的测试恰恰相反：每次改动大、难以维护，尤其 e2e 要真实模拟环境，跑一次可能用很长时间。所以理想状态是有很多很多 unit test、一些 service test 和比较少的 e2e 或 UI test。但很多公司的实际做法是这样的，这张图被称作冰激凌图：最上面是 manual test，手动测试，主要靠开发和 QA 手动点点点；下面是 QA 写的一大堆基于界面的 UI 测试，由于开发没有介入，这些 UI 测试经常出错、需要修改；service 和 unit test 少之又少，因为这部分本该由开发来写，而开发根本没时间。这就是互联网公司的反例。我们在这套课程中要极力避免这种情况：给组件和逻辑写单元测试，写得最多的就是 unit test，另外两种测试暂不涉猎。

最后聊聊组件化框架为什么非常适合写单元测试。第一，组件化意味着一个个独立的单元，互不影响。第二，组件是属性和界面的映射，有固定的输入和固定的输出，很适合写单元测试。第三，单向数据流让组件不会随便修改外部传入的数据，只需要测试是否触发相应的回调、是否发送对应的事件即可。

另外是状态管理工具，它脱离整个组件或界面而存在，包含整个应用的数据结构和变化逻辑，数据的复杂变化可能都在 store 里。这时候可以给 store 单独写测试，脱离界面验证数据的逻辑，分开来非常方便好用。

这节课讲了测试的优点、测试的分类和测试金字塔的概念。下节课开始正式为组件添加测试，让我们一起写出越来越完美的组件。到这里，谢谢大家，再见。
