# 5-4-小花絮：Vue CLI 对战 Vite

上节课我们用 OpsFlow CLI 创建了项目，并简单介绍了各文件的作用。这节课来一点小花絮，说说另外两个脚手架工具。随着 Vue3 的诞生，Vue 生态里出现了一个新的构建工具 Vite，这个词在法语里就是"快"的意思，据称它的开发服务器比 Vue CLI 快十到一百倍，这就成功引起了我的好奇心。

学前端开发，兴趣非常重要。大家都说前端发展太快跟不上，但快是好事，说明生态繁荣。对新东西要有一种玩的心态，不一定非要精通。它既然说快十到一百倍，那就装上和已有的工具对比一下：感觉不错就深入研究，觉得没什么意思就放下。好奇心是最好的老师，请大家努力培养。

回到正题。Vue CLI 大家已经很熟悉了，主要功能是工程脚手架，还有开发服务器、一系列插件系统和 UI 界面，是一个非常成熟的脚手架工具。要注意的是，Vue CLI 构建在 Webpack 之上，它的开发服务器和构建功能、性能都属于 Webpack，所以速度瓶颈主要在 Webpack 的性能上。

Vite 与 Vue CLI 类似，也提供基本的项目脚手架和开发服务器，但它不基于 Webpack，有自己的开发服务器。它利用浏览器原生的 ES Modules 架构，使开发服务器比 Webpack 的快了几个数量级；构建则采用 Rollup，速度也比 Webpack 更快。不过 Vite 当时还处于测试阶段，它不像 Vue CLI 那样是一体化的工具，而是专注于提供快速的开发服务器和一个基本的构建工具。

接下来是激动人心的对比时刻。先在 Vue CLI 项目里执行 npm run serve，最简单的项目，最终显示启动耗时 1780 毫秒。再跑 Vite 项目执行 npm run dev，几乎是秒开。修改内容试试：在 Vite 打开的页面里加一个 test 保存，瞬间就更新完了，快到几乎看不清过程。

它是怎么做到这么快的？用图来说明。先看 Vue CLI：底层由 Webpack 完成。源代码是 ES Modules、TypeScript、Single File Component 等一系列格式，并不是所有浏览器都支持，所以 Webpack 通过解析代码中的每一个 import 或 require，把整个应用构建成一个基于 JavaScript 的捆绑包，并在运行时转换这些文件。转换完成后，目标代码就是兼容所有浏览器的 JS 代码，可能是一个或几个巨大的文件。打开 network 看，js 就是几个比较大的文件，源代码被打包成了 Webpack 模式。这个转换过程非常耗时，也就决定了 Vue CLI 的速度。

再看 Vite 的思路，正好相反。不是所有浏览器都支持 ES Modules，但有一部分支持。那不妨换个思维：只支持这些浏览器，就完全不用做耗时的浏览器兼容性转换，只做很小程度的转换就能直接运行。还是原来那一大堆源代码，用 Rollup 做简单转换，输出和源代码一一对应的 ES Modules，并利用浏览器高效的默认模块处理，所以明显更快。打开 network 看，文件和源代码一一对应。这个架构避免了服务端对整个应用的 bundle，因此 Vite 最大的特点就是开发服务器快得离谱。

不过 Vite 确实有一些缺点。第一，当时还在测试阶段，可能有 bug、不够稳定。第二是浏览器支持性问题，只支持支持 ES Modules 的新版浏览器。第三，第三方库也需要支持 ES Modules 才能良好运作。第四，它可以把 CommonJS 转换为 ES Modules，但在一些边缘情况下可能做不到，也就是对 CommonJS 支持有限。最后一条我认为比较严重：它的开发和构建是两套系统，开发走 ES Modules，构建则像 Webpack 一样打成支持所有浏览器的大文件。开发环境和生产环境用的代码完全不一样，可能导致生产和开发行为不一致。

最后补充一个小知识：Vite 并不是唯一一个利用浏览器 JavaScript 模块的开发服务器项目，它的前辈是更早推出的 Snowpack。Vite 的文档里也写到它是受了 Snowpack 1.0 的启发，感兴趣的可以看看 Snowpack 的文档。

这节课比较了 Vue CLI 和 Vite 的各种特点。Vite 还是测试版本，如果要在正式项目中使用，建议三思而后行；但如果是自己做 Demo、探索特性，可以毫不犹豫地用起来，速度提升非常大，效率会很高。这节课就到这里，谢谢大家。
