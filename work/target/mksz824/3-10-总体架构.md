# 3-10-总体架构

前面经过需求分析、抽象难点、技术解决方案的撰写到技术选型，我们完成了复杂项目的第一步，也是非常重要的一步。现在把这些整合起来，看项目的整体架构。

## 项目一：OpsFlow Components 业务组件库

我们确定了要做两个项目。第一个是业务组件库，称为 OpsFlow Components。在我们的设计思路下，业务组件库主要完成展示功能，不会有特别复杂的交互逻辑。目前有几个基本组件：l-text 文本、l-image 图片、l-shape 形状。当然它具有可扩展性，为未来做更多组件打下基础。

具体分析可以回顾之前写的业务组件库技术解决方案，看看我们是怎样分析难点和解决难点的。

给它选择技术栈，从上到下：最上层是自研的命令行工具 imooc-cli；之后是 TypeScript；框架用 Vue 3；测试工具选择官方的 Vue Test Utils，业务组件库的组件完全分割开来、是解耦的，非常适合测试。特别注意它产出的内容并不是 Web 应用，而是一系列的 JS 模块，并且要上传到 npm，所以打包工具特意选择了 Rollup，实现时会调研 Rollup 和 Webpack 的异同。持续集成方面选择了 Travis，以拓宽知识面。此外还有一些提交前检查等工作，比如提交前检查代码格式是否正确、测试有没有通过，这些工具之后再说。

## 项目二：B 端主站

第二个项目是 B 端，也就是主站 OpsFlow 网站。从页面维度分，它有编辑器、首页、登录页、详情页、我的作品列表页等。不难看出编辑器是其中的重点，所以特意标出。我们分析了其中的难点，完成了技术方案和典型场景的设计，可以回顾那些非常丰富的流程图，以及写得很长的 B 端编辑器技术实现方案。

在这个技术实现方案中，有一个方案把表单和数据的对应关系做了高层次的抽象。写过后台系统的同学会有很多表单，针对这种情况，其实有公司已经做了现成的解决方案。阿里就有一个库叫 FormRender，专门解决这个问题，常用于自定义搭建配置界面生成。它的规范和内容更多，但思路和我们是一样的：用 object 来描述一系列的表单，里面有各种各样的属性。不知不觉中我们和大型项目不谋而合，可谓英雄所见略同。大家课下可以分析一下它的例子和思路。

B 端的技术栈和组件库项目类似，但因为产出的是一个 Web 界面，所以有一些增强的内容。最上面同样是 imooc-cli、TypeScript、Vue，不再多说。因为是 SPA 项目，自然有状态管理 Vuex、路由 Vue Router，UI 组件库选择 Ant Design Vue。测试一样用 Vue Test Utils。打包采用 Webpack。由于生成的是页面应用，性能优化非常重要，课程会详细讲性能优化怎么做。最后的 CI/CD 持续发布，使用 imooc-cli 内置的发布工具。

## 头脑风暴：还能怎么拆

回顾整体架构会发现，编辑器这么独特、复杂、重要，看起来和其他页面有点格格不入，是否可以单独把它拿出来做一个项目？这样就多做出一个项目。再进一步思考，编辑器和其他页面其实有一些共同的东西，比如通用状态：用户信息、登录、登出等操作。那是否可以抽象出一个单独的数据模型项目，叫 imooc-data-service？这个数据模型可以供多个项目使用：主站可以使用它，编辑器也可以使用它，完成代码的跨项目使用。如果能思考到这里，说明你真的认真动脑子了。

但对于项目目前的复杂度，用奥卡姆剃刀原理来说：如无必要，勿增实体。这样做会增加好几个新项目，还要处理一系列由此引发的问题，比如项目依赖增加、路由展示怎么处理等等。这个问题没有正确答案，两者有利有弊，看自己的选择和个人爱好。

在这个头脑风暴的过程中，我们还不知不觉接触了一个前沿概念：微前端。它听起来高大上，其实就是把一个整体项目划分成更小的组合，比如把一个大项目划分成三个项目的组合，让更精益的团队按不同功能模块完成功能，然后通过特定的手段把这些模块整合成一个应用。当然它会带来新的挑战，比如刚才说的那几个问题。之后我们会深入介绍微前端这个概念。
