# 9-2-Javascript 模块化历史

在开始业务组件库的打包之前，先聊一段小历史：JavaScript modules，也就是模块发展的历史。这段历史很有意思，它是前端开发发展的一个缩影。首先搞清楚什么是模块。相信大家都有自己的答案：模块是语言层面的。如果你熟悉其他编程语言，模块是一个非常常见的概念，都有这么一个模块系统。

比如 Python，可以使用 `from package import function` 的方式引入一个单独的功能。Go 语言也一样，用 package import 引入模块。模块最简单来说，就是一组可重用的代码，被提取到不同的文件中。这样做有什么好处呢？第一是可维护性：根据定义，每个模块都是独立的，良好设计的模块会尽量与外部代码撇清关系，以便独立地改进和维护，维护一个独立的模块要比一团意大利面一样的代码轻松得多。第二是可复用性：现实工作中，我们经常把之前写好的代码复制到新项目里，复制粘贴大法虽然快，但如果有一个可以重复利用的模块，那就开心多了。

在前端领域，我们说的 module 一般就是 JavaScript modules，它往往表现为一个单独的 JS 文件，对外暴露一些属性或者方法。然而这么一个简单的需求，是经过了很长时间的奋斗才达到的。

ES6 之前是一个没有模块的年代，JavaScript 并没有原生的模块。看一下当年使用 Backbone 框架的例子：它的依赖以 script 标签引入的方式手动排列顺序来管理，需要 jQuery、underscore，然后是 backbone 和它的插件 backbone.localStorage，最后是代码实现 todos.js。依赖处理没有任何办法，看起来非常繁琐。五六年前很多工程师还是这么写代码的，现在有些项目仍然使用这种方式进行本地开发。

为了解决这个问题，JavaScript 开发者通过各种约定或妥协实现了模块的特征，大致经历过三个阶段。第一个阶段称之为全局变量加命名空间（namespace），非常原始：整个项目使用同一个全局变量，各模块按照各自的命名空间进行挂载，典型例子就是 jQuery 以及很多较早的项目。全局变量上有一系列角色，比如 private members、public method、private method，最后有一个产出，return 一个 object，把 key value 的产出挂载到这个对象上。注意它使用了一个 IIFE，自执行函数进行包裹，可以创建封闭的作用域，然后赋值给全局变量。使用的时候通过全局变量加方法名调用对应的方法或属性。

这种做法比较原始，有很多弊端：第一，依赖全局变量，污染全局作用域的同时也不太安全；第二，依赖约定的命名空间来避免冲突，可靠性不高，很容易发生冲突；第三，需要手动管理依赖并控制执行顺序，非常容易出错；最后，上线前需要合并所有用到的模块，有可能还是手动过程，很不方便。

接下来是 CommonJS。2009 年 Node.js 推出的时候，给前端开发带来了翻天覆地的变化，它想把 JavaScript 开发延伸到服务器端，自然开发出了自己的模块系统，这个标准就称为 CommonJS。语法很简单：使用 require 进行导入，使用 module.exports 进行导出。这东西虽然好，但它是为服务器端设计的，不符合浏览器的标准，浏览器中同步加载文件是阻塞的，会浪费大量时间，所以在浏览器中没法直接使用。

但我们还想用这种标准，前端工程师们绞尽脑汁，发明了一种类似 CommonJS 的格式，称之为 AMD。这 AMD 可不是显卡，而是 Asynchronous Module Definition 的缩写。近几年才开始学前端的，可能对这个格式非常陌生。它把革命性的模块化开发加速带到了前端：有一个全局暴露的函数 define，在 define 中有一个 function，通过 require 相对路径获取模块依赖，模块产出可以直接 return，想产出什么就产出什么。

这种做法有很多好处：只需要在全局定义 require 和 define，不需要其他全局变量；通过文件路径或者模块自己声明的模块名进行定位，并且提供了打包工具自动分析依赖、进行合并。注意它使用时需要配合特定的 AMD 加载器，当年非常火的 RequireJS 是它的标配。那个年代还诞生了很多类似的模块标准，比如阿里发明的 CMD，加载器叫 sea.js，当时和 AMD 是竞争关系，很多阿里系的产品都使用了 CMD 格式，这是一段非常有意思的历史。

在各路工程师自己发明了很多年以后，JavaScript 委员会终于制定了模块的标准，也就是我们现在前端开发世界都在使用的大一统解决方案：ES6 Modules，也就是 ES2015。它为 JavaScript 世界带来了规范的模块化方案，相比 AMD 和 CommonJS 更为强大，引用和暴露的方法更加多样，并且支持较为复杂的静态分析，构建工具可以细粒度地移除模块实现中的无用代码。规范就是大家熟悉的 import 和 export，我们一直在使用，就不多说了。其实大家觉得现在自然而然的东西，是经过长期发展才最终确定的。

那么这个格式可以被浏览器良好使用吗？答案是否定的：只有几个最新版浏览器支持 import export 语法，而且支持的场景比较有限。之前在 Vue CLI 和 Yarn 部分也讲过，Yarn 之所以快，是因为浏览器原生支持 ES modules，不用再做一大堆转换。但对主流的大部分浏览器来说，很难满足支持 ES modules 这个条件。然而我们在开发过程中都无缝使用了这种格式，运行良好。这些问题是怎样解决的呢？这节课先到这里，下节课我们再来一起探讨研究。到这里，谢谢大家，再见。
