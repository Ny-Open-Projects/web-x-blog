# 16-5-4-撤销重做编码第三部分：根据当前情况添加测试

上节课完成了撤销重做的第一部分需求，这节课来测试这段比较复杂的逻辑。store 是独立的数据结构，mutation 只修改里面的数据，没有界面和交互的干扰，非常适合做单元测试。策略是分两步走：先给撤销重做写单元测试，再拿到界面上测，看看最终效果。

editor 的测试内容越来越多、case 也越来越多，我把它挪到了一个单独的文件中，新建测试用例并用 `only` 修饰只跑它。

## 准备工作：resetEditor

前面的测试会污染 editor 的状态，第一步先把它复原到什么数据都没有的最初状态。给 store 添加一个 `resetEditor` mutation，这在真实项目里也有用武之地，比如以后进入路由时需要先把 editor 整个状态 reset 到最初：

```ts
resetEditor(state) {
  state.currentElement = ''
  state.historyIndex = -1
  state.histories = []
}
```

就是把各项值赋回初始状态：取消选中、历史指针归位、历史数组清空。测试开头先 `store.commit('resetEditor')`。

## 预先添加三个操作

接下来模拟一系列操作：添加两个图层、删除一个图层、再修改剩下图层的属性。

添加图层用之前写过的 `addComponent`，直接复制代码（想把这些常用操作封装成函数也完全可以）。第二个图层的 payload 改一下：id 用 `2345`，text 改成 `text2`。第三步删除第二个图层，commit `deleteComponent`，id 传 `2345`。第四步 update，key 用 `text`、value 改成 `updated`、id 是剩下的 `1234`。

然后用 `setActive` 选中剩下的 `1234` 图层，再通过 getter 拿到当前元素（指定为 `ComponentData` 类型）。undo 之前先验证它确实被更新过：

```ts
expect(currentElement.props.text).toBe('updated')
```

准备工作到此完成。

## 三步 undo

**第一步 undo step one**：commit `undo`，text 应该从 `updated` 回滚到最初的 `text1`：

```ts
expect(currentElement.props.text).toBe('text1')
```

跑一下，通过，说明 modify 类型的历史记录是成功的。

**第二步 undo step two**：这次遇到的是 delete 记录，回滚后应该有两个元素，而且被删的元素要回到正确的位置。先 commit `undo`，然后断言：

- components.length 应该变回 2；
- 被删除的元素在最后一位：取 `components` 的 `lastItem`，它的 id 应该是之前删除的 `2345`。

都通过，说明删除的元素能成功回到原位。

**第三步**：第三条记录是添加元素，undo 它就意味着把那个元素删掉，剩下最后一个。再 commit `undo`，断言 length 变为 1，并且 `lastItem2` 的 id 是 `1234`，`2345` 已经被删掉了。通过。

最后还有一步大家可以自己补：第四个操作是 add，再 commit 一次 `undo`，components.length 应该等于 0，所有东西回到最初，说明状态可以清除干净。

到这里 undo 的测试用例就写完了。redo 的测试大家可以顺着这个逻辑继续写，正好把相反的逻辑过一遍。
