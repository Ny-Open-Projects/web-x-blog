# 20-23-配置文件以及环境变量

接着上面的内容，看看目前的问题：配置文件中有一系列敏感信息被直接写成了明文，比如 password、host 等。要去除这个隐患。在之前的后端内容中我们大量使用了环境变量，而 Nuxt 3 提供了一个特殊选项来完成这个任务，叫 runtimeConfig。看名字就知道，这个配置是在运行时才被赋值的，适合那些私密的、不愿暴露在代码中的信息，比之前直接使用 process.env 更强大。

在 defineNuxtConfig 下新添加一个字段 runtimeConfig（可以自动联想出来，代表这系列配置在运行时才被感知）。先放一个测试值 apiKey，随便赋值为 1234。然后在两个地方获取它，看结果有什么不同。

首先在后端，test.ts 中通过一个组合式函数获取：useRuntimeConfig。它能自动联想出 apiKey，打印出来，访问 /api/test，终端打印出 apiKey 是 1234，说明后端可以拿到。

然后在前端试一下，把取值的代码放到首页。console 里显示 apiKey 是 undefined。所以 runtimeConfig 只在后端能被读取到，前端拿不到。

当然，有些信息是想让前端也感知到的，比如不私密的信息：URL 地址、语言选项等等。这时可以在 runtimeConfig 下用一个新的值 public，public 里面的值前端和后端都能拿到。比如创建一个 apiBase，是一个之后要在应用中使用的 URL。保存后，代码中取值时注意：public 是保留字，不能直接解构，要先赋值给 config，再取 `config.public.apiBase`。验证后，public 里的值前端能拿到，但不在 public 里的值（比如 apiKey）前端依然拿不到。这样就保证了最终生成的前端代码中不会泄露秘密。

不过我们还没和环境变量结合起来。Nuxt 在这方面有特殊设计，可以通过特殊的命名完成自动覆盖。创建大家都很熟悉的 `.env` 文件，把 apiKey 的值写到环境变量中。要覆盖 runtimeConfig 的环境变量，命名有讲究：要有 NUXT 前缀，加下划线，后面的部分根据大写字母分割、下划线相连。apiKey 对应的就是 NUXT_API_KEY（环境变量中全部大写，A 和 P 之间要分割，K 前面也要分割）。给它设置成 3456，甚至可以先把原值清空。设置完毕后，后端 API 返回的 apiKey 就变成了 3456，自动覆盖成功。

除了 runtimeConfig，还有一部分信息是整个应用应有的普通信息，比如应用的主题、标题或其他不敏感的内容。它们不需要运行时才决定，编译之前就可以确定。这类配置放在一个新的配置文件 app.config.ts 中：

```ts
export default defineAppConfig({
  theme: {
    primaryColor: 'blue',
  },
})
```

想在前端获取这个值，有一个和 useRuntimeConfig 非常相似的组合式函数 useAppConfig，同样有完整的 TS 支持，能拿到刚才定义的值。比如把颜色展示出来。注意：第一次新建这个文件时会报错，需要重启一下应用；之后就没有问题了。重启完成后，就能拿到配置文件中的值 blue。

最后总结两者的适用场景。runtimeConfig 支持环境变量（值写在 .env 里），appConfig 不支持。所以 runtimeConfig 更适合运行时才能提供的敏感、隐私数据；appConfig 更适合应用的整体配置里不敏感的数据，并且 appConfig 支持 HMR，修改任何值在开发环境不用刷新就能直接生效。

现在介绍了这两个概念，但还没解决本节课开头提出的问题：我们希望在 nuxt.config 的配置里也能使用 runtimeConfig 的方式，但在配置文件中没法使用 useRuntimeConfig 这样的组合式函数。下节课再研究有没有新的方式解决这个问题，并引出一个新概念。
