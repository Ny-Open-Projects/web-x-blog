# 5-8-项目结构规范

之前的课程里我们完成了代码规范的配置，讲了 ESLint 的玩法、一些知名的规范合集，以及另辟蹊径帮你格式化代码的 Prettier。至于选择怎样的规范，由你们自己确定。每个人对代码规范都有自己的答案，一千个人心中有一千个哈姆雷特。如果你在架构师或 Team Leader 的位置上，可以和工程师讨论，得出大家都满意心仪的规范，然后像我之前做的那样创建一个编码规范文档，让每个人都可以追溯、查找和修改。

代码规范确定以后，接下来是项目结构规范。代码格式针对的是每个文件的书写格式，而项目结构针对的是文件应该以怎样的标准存放和管理，对大中型项目来说同样是必须有的规范。我以前的工作中特别喜欢研究所谓的文件结构标准。有一个帖子描述了很多工程师醉心于用超级复杂的结构构建项目：嵌套了非常多层文件夹，导入某个模块的时候会让人感到绝望。这种做法其实不可取，我的观点后来发生了改变。

我特意去翻看 Vue 的官方文档，想找项目结构的指导思想，发现没有；而 React 官方文档里有几个简单的指导思想，可以拿来做基本标准。文档标题问的是"有没有推荐的项目结构标准"，回答很直接：没有任何推荐或强制的标准，一般有两种主流做法。第一种是按功能或路由组织（Grouping by Features or Routes），比如 common 放大家通用的东西，Feed、Profile 等按功能划分。第二种是按文件类型组织（Grouping by File Type），比如所有组件都放在 components 里，API 类的文件放到 api 文件夹下。我个人更倾向于第二种方案，稍后展示我的成果。

除了这两种标准，文档特意提醒了两点。第一是避免多层嵌套。我以前的项目就是这样，功能本来不复杂，却人为增加了复杂度，看起来繁琐，引入也麻烦。第二是不要过度思考（Don't overthink it）。之前的经验里，我们有时会进入一种误区，觉得项目一开始必须有一个非常完美的结构：层次很深的嵌套、规矩很多、井井有条。现在认为这不正确：开始一个项目时，不要在选择文件结构上花超过五分钟，选一种很自然的方式开始写代码。等你写了真正的代码以后，可能会重新考虑它，用另外一种方式组织。

所以这个项目在开始阶段，我也只花了不到五分钟确定结构：在原有结构上做一个简单的扩展。逐个看一遍。第一个是 assets，放一些静态文件，不多说了。第二个是 components 文件夹，放置所有组件。这里说一下命名规范：两个单词都首字母大写的，称为帕斯卡命名法，组件会采用这种命名方式，这是确定的必要规范。

之后是 views 文件夹。因为我们做的是 SPA 项目，自然会有很多路由，这里放置不同的路由页面，比如首页 home.vue，编辑页面 editor.vue。编辑页面里可能还有一些独立模块，也可以放到 views 中，所以它指的是一些独立的、可以被访问的模块。再往下是 router，放路由相关的文件。然后是 store，即全局状态，它可以分成多个文件：index 存放整体结构，editor 是整个编辑器的状态结构，user 是用户的数据状态结构等等。

然后是 hooks，这是之前说过的一些通用逻辑的放置处，是 Vue3 推出的新功能。命名上有讲究：前面是一个 use，后面采用帕斯卡命名，比如 useLoader（我这里就应该写成大写的 L），改完之后就是这样。接下来是 plugins，放一些插件化的内容。编辑器页面上可能有很多插件，比如快捷键、右键菜单等等，可以用插件化的形式放在这里，与整个编辑器的结构和逻辑形成解耦。最后是 test，单元测试文件，命名要做到和组件完全一致，只是加一个 spec 后缀，代表它是组件对应的测试。最外层还有 App.vue 和 main.ts，大家应该很清楚，不再赘述。

这就是产出的文件结构。由于现在还没开始写代码，大家可能还无法抽象出 hooks、plugins 这些概念，所以项目刚开始可以尽量简单。随着规模扩大，实践中通常会混搭之前说的各种方式，你还可能修改规则，因此一开始就选出"正确"的方式并不是很重要，一定不要教条主义，选择适合自己项目的方法。同样，大家在完成自己的项目结构后，请在语雀中创建一个文档，供其他成员 review。

这节课简单介绍了项目的代码文件结构和命名，并要产出对应的文档。注意这个文档很重要，供其他工程师参考和修改。到这里，谢谢大家。
