# 12-17-总结 egg-session 的优缺点

通过前面用 Session 会话方式实现用户认证的学习，可以发现 egg-session 提供了两种方法来完成这个功能。这节课对两种方法的利弊做个总结，这也是面试中经常问到的知识点，准备面试的同学不妨记一下笔记。

## 方式一：默认实现（cookie session）

**优点有两个。** 第一，通过研读源码可以知道，它巧妙地把信息加密后存进 Cookie，再次访问时解密拿到用户信息，服务器上不保存任何状态。这刷新了我们对 Session 常规实现的认识，思路其实非常类似之后要讲的 token-based 认证方式（比如最终要采用的 JWT，即 JSON Web Token），只是加密方式不太一样。第二，它非常适合小型应用，可以以极低的成本解决持久化和横向扩展的问题。

**缺点也有两个。** 第一，信息都存在 Cookie 里，也就是 JSON encode 后的数据，数据可能比较大。比如把所有用户信息都 JSON encode 进去，但浏览器对 Cookie 有大小限制，上限是 4093 字节。当设置的 Cookie value 超过这个值时，框架会打印一条警告日志。对大数据来说，根本没法存进 Cookie。

第二，HTTP 的特性是同源请求会自动携带 Cookie（DevTools 里会标注 "This header was automatically added"）。这意味着请求任何资源都会带上 Cookie，当 Cookie 很大时，势必拖慢 HTTP 的传输速度。

### 扩展：从 Cookie 角度理解 CDN

顺着这一点扩展一个面试常见问题：静态资源为什么要采用 CDN？一般的回答是 CDN（Content Delivery Network，内容分发网络）通过多服务器就近请求的原则大幅提升响应速度。但如果你能从 Cookie 的角度再补充一层，面试官会刮目相看。

以知乎为例：访问 zhihu.com 时，document 请求的 Request Cookies 非常多。如果静态资源也放在这个主域名下，每请求一张图片或一个 CSS/JS 文件都会附带这么一大串 Cookie，而图片、CSS、JS 其实根本不需要这些 Cookie，纯粹是资源浪费。知乎的解决方式是把静态资源放到另一个域名（pic*.zhimg.com）下，这样请求静态资源时 Cookie 极少，Request Header 里甚至没有 Cookie，传输速度大幅提高。下次面试可以把这个角度展示出来。

## 方式二：外部存储（经典模型）

第二种是 Session 的经典实现方式：egg-session 使用外部存储，可以放内存，可以放缓存（Memcached、Redis），也可以持久化到数据库。

**优点：** 一是原理简单易懂、实现方便，对照经典模型图很快就能理解具体做法；二是可以对已登录用户做快速操作，比如封禁、踢出登录等，做法就是删掉数据库里那一条记录，用户随即被踢出登录态。

**缺点有三个。** 第一，硬件成本：无论内存还是软件方案，都要占用服务器资源。第二，强依赖：Session 功能依赖第三方服务，服务挂了 Session 就完全不可用，网站的一大块功能直接 down 掉。第三，多进程或多服务器时的同步问题：应用部署成集群、多个节点时，用户 A 在节点一登录（记录存在节点一），用户 B 在节点二登录；之后用户 A 被分配到节点二再登录，就会发现节点二没有这条数据，登录必然失败。所以需要一个数据同步过程，把两个节点的数据用某种算法 merge 到一起，这会让系统更复杂。另一种方案是引入第三方统一服务：Session 和用户验证统一存在一个服务里（比如 Redis），任何节点做鉴权都调用它。这样数据源唯一、不需要同步，但 Redis 需要额外采购部署，成本随之上升。

## 小结

这节课分析了 Session 会话方式做用户认证的优势和劣势。经过源码分析和代码实现，你对这种形式应该有了比较深刻的认识。下节课继续介绍我们要采用的 token-based 验证模式，其中的代表就是 JWT（JSON Web Token），看看它的原理以及如何实现用户认证。
