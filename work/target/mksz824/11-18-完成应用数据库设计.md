# 11-18-完成应用数据库设计

上节课分析了内嵌和引用两种数据关系的优劣，现在根据具体情况决定怎么选。我们的应用数据关系是典型的一对多，需要按不同情况讨论：一对多里的"多"到底有多少？根据 schema design best practices 这篇设计文档，一对多可以分成几种。

第一种叫 one to few，"几个"的意思，最多十几个。比如每个作品中要存储的 channel（渠道）信息，渠道应该肉眼可见地只有最多十几个数据，这就是 one to few。其实还有一个隐藏的对应关系也是 one to few：构成作品画面的元素信息。一个作品包含一些元素但不会特别多，不可能有几百个元素。对这种关系，在没有特殊因素的情况下推荐使用内嵌，直接保存类似的文档。结构应该是：一个 work，channels 像数组一样放置在内部，带一系列属性。我用 MongoDB 建模软件建立了对应的 collection：work 集合上有一系列字段，这里不深说，之后会有设计文档提供给大家。特别想说 channels 以数组形式直接存在于 work collection 中，比如有 channelName 和 workId 属性；里面有一个 object 叫 content，包含所有页面相关信息：页面属性保存在 props 中，多个元素保存在 components 中。id、name、isHidden、isLocked、layerName、props 这些就是每个元素的一系列属性。这就是一对 few 的做法。

第二种叫 one to many，many 是几十到上百甚至几百的数据量。这种量级就不能奢求在一个文档里拿到所有数据了，需要新建对应的集合。我们应用里的 user 和 work 明显就是这种关系：一个用户可能创建很多作品，所以按规则把用户和作品分成两个不同的 collection，用之前学过的保存对方 ID 的形式描述一对多。完成方式有两种。我们把一对多的"多"一方叫子集，少的叫父集。第一种：在子集合中用一个字段保存父集合的 ID，显然就是在 work 中加一个字段（比如叫 user）保存对应用户的 ID 信息，work1 和 work2 都保存同一个 user 的 ID。第二种：在父集合中使用数组保存所有子集合的 ID，比如 user 中新建一个叫 works 的数组，里面是一系列 work 的 ObjectID。特别注意：既然用了这种方式，work 里就不需要再存 userId 了，再加就是画蛇添足。针对第二种方式，假如子集数据中有基于数组顺序的一系列操作，比如 works 可能有排序等功能，建议用第二种；我们的应用没有这种需求，两种都可以。我们用了第一种：在 work 中添加特殊字段 user 保存 userId，完成 user 到 work 的一对多关系。建模软件上也能清晰看到：user 是单独的 collection，work 里添加了对应的 ID 字段，user 保存对应的 userId，两者建立一对多关系，软件里 ID 连线到最下面的 user，分叉开，清楚地标明一对多。

最后一种叫 one to squillions，squillions 表示非常大量的数据，比如几百万。现实中存在这样的数据：一台服务器的 log 就是一对 squillions 的关系，完全可能达到几百万级别。这时如果用数组存 ID，ID 会疯涨，数组里可能有几百万个 ID。特别注意不能让数组里的个数完全不受控，很容易达到之前说的单文档 16 兆限制。所以这种海量一对多关系只能选第一种方式（子文档引用父文档 ID），不能用第二种数组方式。

总结一下关于数组的规则，宗旨是数组的大小不应该毫无顾忌地扩张。一对多数组只有几项到几十项（few）时推荐内嵌；几十到几百（many）时两种都可以：引用方式，或父集合用数组保存子集合 ID；到亿万级数据（squillions）时只能用引用方式，不能再用数组保存 ID。

最后的关系是 many to many 多对多，非常常见，我们的应用目前没有这种结构，简单了解一下。举一个任务分配系统的例子：一个用户有多个任务，一个任务也可以对应多个用户，典型的多对多。做法是两边都添加数组保存对方的 ID 完成引用：User 的 document 里创建 tasks 数组保存一系列 task 的 ID；task 那边一样，有一个 owners 属性，数组里保存多个 userId。这样多对多关系就完成了。

最佳实践里的几种关系介绍完了。这节课学了那篇文章的几个精华点，并根据实践完成了自己的数据库集合设计。设计文档我会上传到语雀，字段含义大家可以自行了解。最后留个作业，考验大家对这节课的理解，这些特性都可以扩展到现有应用里：第一，给作品添加分类，每个作品对应一个分类，一个分类可以包含多个作品，分类可以是假期、科技、商业、招聘等；第二，给作品添加 tag 系统，每个作品可以添加多个用户自定义的 tag，比如国庆节、红色、双十一、亲子等。大家可以把它加到现有数据系统里，看看会做怎样的设计。

这些只是一般情况下的基本规则。MongoDB 的条件是 no rules，没有定死的规则，灵活多变也是我们选它的一大理由。最重要的还是针对自己应用的特点，设计出符合应用的数据库结构。
