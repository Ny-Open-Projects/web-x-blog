# 后端校招面试直通车: 设计模式七大原则

## 纲要

- 开闭原则：对扩展开放、对修改关闭，尽量写新代码而不是改老代码
- 里氏替换原则：子类可扩展父类功能，但不改变父类原有功能
- 依赖倒置原则：面向接口编程，高层与低层都依赖抽象
- 单一职责原则：一个类（一个函数）只有一个引起它变化的原因
- 接口隔离原则：客户端不应被迫依赖它不使用的方法
- 迪米特法则：没有必要就不要让两个类直接联系
- 合成复用原则：优先考虑组合而非继承来完成复用
- 收尾：规则是死的，因地制宜，适合的才是最好的

## 为什么要先学原则

设计模式的经典分类里有 23 种模式，但在实际工作与面试中，真正被反复考察的只有单例、建造者、适配器、装饰器、代理等少数几种。比背模式更重要的，是理解这些模式背后的**设计原则**——模式是原则在具体场景下的落地形态，原则才是可以迁移的部分。

## 开闭原则

定义：当应用的需求发生变化时，尽可能在不修改原有软件实体源代码（或二进制代码）的情况下，通过扩展模块功能来满足新需求。

为什么强调"不改老代码"？因为改老代码的成本远高于写新代码：

- 必须先回到原有的实现体系里，理解当初为什么这么写
- 很多历史实现并不完全契合当下场景，改动很容易引入新错误

对软件测试的影响尤其大：如果代码迭代时不改原有代码，测试只需要覆盖新增的逻辑，原有逻辑做回归即可，既省成本又能更好地保证质量。同时，可复用性与可维护性也随之提高。

当然，这一切的前提是**第一次设计时就把类设计好**，让它具备足够的扩展点，后续才能尽量少改动。

## 里氏替换原则

通俗表述：子类可以扩展父类的功能，但**不能改变父类原有的功能**。继承时要特别留意几点：

- 子类可以实现父类的抽象方法，但不要覆盖父类的非抽象方法
- 子类可以增加自己特有的方法，即扩展功能
- 重载（overload）时，子类方法的**输入要比父类方法更宽松**
- 实现（override）父类虚函数时，子类方法的**输出要比父类方法更严格**

原因很直观：继承的目的是扩展父类能力，所以入参要更宽松才符合"扩展"语义；而覆写的目的是把抽象的虚函数具象化，因此返回值必须更具体、更严格，否则实现就没有意义。

## 依赖倒置原则

定义较长，核心一句话：**面向接口编程，而不是面向实现（具体类）编程**。

展开来说：

- 高层模块不应该依赖低层模块，两者都应该依赖其抽象
- 抽象不依赖细节，细节依赖抽象

带来的收益：

| 收益 | 说明 |
| --- | --- |
| 降低耦合度 | 依赖方只依赖接口，实现被替换不影响调用方 |
| 提高系统稳定性 | 别人修改实现，不影响依赖接口的其他类 |
| 减少并行开发风险 | 接口定义得好，多个实现可以并行开发而互不影响 |
| 提高可读性 | 阅读代码时只需看接口定义，不必下沉到具体实现 |
| 提高可维护性 | 修改实现的影响面被接口隔离，改动更安全 |

## 单一职责原则

定义：设计一个类时，应该让它的功能尽可能单一，即**有且仅有一个可以引起它变化的原因**。否则这个类就是复杂的，应当拆分。

这条原则不只对类成立，对函数同样成立：一个函数里不要塞进过多功能。

收益：降低类与函数的复杂度，提高可读性、可维护性，同时降低变更引起的风险——功能单一时，依赖关系更少，改起来更简单。

## 接口隔离原则

定义：客户端不应该被迫依赖于它不使用的方法。编码时要遵循**最少依赖原则**：没有必要引入的依赖一定不要引入，让接口保持最小、让实现的依赖也保持最小。

除了提高灵活性与可维护性，最实际的一条收益是**减少工程代码冗余**：

- 代码量精简，依赖复杂度下降
- 静态检查工具会提示未被使用的依赖，及时清理
- 依赖变少后，工程的构建速度更快，对编辑器分析与 CI/CD 流水线都更友好

## 迪米特法则

定义：两个（或多个）类之间，如果没有必要，就不要直接联系。目的是降低类之间的耦合度、提高模块的相对独立性。

平时使用消息队列、代理层，本身就是符合迪米特法则的做法：双方不直接耦合，而是通过中间层通信。装饰器模式、代理模式也都可以看作它的具体体现。

代价同样明显：会产生大量中介类，系统复杂性上升，模块之间的通信效率下降。

实践建议：两个实体类之间的关系越简单越好——要么直接相互调用，要么通过代理/消息队列建立联系，要么根本没有关系。不要出现"你包含我、我包含你、你隐式调用我、我显式调用你"这类纠缠不清的关系。

## 合成复用原则

定义：做功能复用时，除了继承之外，还可以优先考虑**组合（合成）与聚合**的方式。

为什么要慎用过继承：

- 继承复用会破坏类的封装性，父类与子类耦合度过高
- 组合方式维护了类的封装性，新类与既有类之间的耦合度更低
- 组合的灵活性更高，可以针对不同功能自由组合

装饰器模式就是合成复用原则的典型体现：不用继承也能扩展功能。

## 七大原则速记

| 原则 | 一句话 | 关键词 |
| --- | --- | --- |
| 开闭原则 | 扩展开放、修改关闭 | 写新代码 |
| 里氏替换原则 | 子类只扩展、不改变父类行为 | 继承约束 |
| 依赖倒置原则 | 面向接口编程 | 依赖抽象 |
| 单一职责原则 | 一个类一个变化原因 | 职责单一 |
| 接口隔离原则 | 不依赖用不到的方法 | 最小依赖 |
| 迪米特法则 | 无必要不直接联系 | 降低耦合 |
| 合成复用原则 | 优先组合而非继承 | 组合复用 |

## Demo 示例

> 以下代码根据讲稿逻辑用 Go 语言补充，用一个订单通知的例子同时体现开闭原则、依赖倒置、接口隔离与合成复用，单文件可直接运行。

### 运行说明

```bash
mkdir principle-demo && cd principle-demo
go mod init principle-demo
# 将下方代码保存为 main.go
go run main.go
```

```go
package main

import "fmt"

// Notifier 通知抽象：只声明一个方法，符合接口隔离原则
type Notifier interface {
	Send(to string, msg string) error
}

// EmailNotifier 邮件通知实现
type EmailNotifier struct{}

func (EmailNotifier) Send(to string, msg string) error {
	fmt.Printf("[email] to=%s msg=%s\n", to, msg)
	return nil
}

// SMSNotifier 短信通知实现
type SMSNotifier struct{}

func (SMSNotifier) Send(to string, msg string) error {
	fmt.Printf("[sms] to=%s msg=%s\n", to, msg)
	return nil
}

// PushNotifier 新增实现：不修改 OrderService 一行代码，符合开闭原则
type PushNotifier struct{}

func (PushNotifier) Send(to string, msg string) error {
	fmt.Printf("[push] to=%s msg=%s\n", to, msg)
	return nil
}

// OrderService 高层模块：依赖 Notifier 抽象而非具体实现（依赖倒置）
// 通过组合注入通知能力，而不是继承某个通知基类（合成复用）
type OrderService struct {
	notifier Notifier
}

// NewOrderService 构造时注入依赖
func NewOrderService(n Notifier) *OrderService {
	return &OrderService{notifier: n}
}

// Create 创建订单并发送通知，职责单一
func (s *OrderService) Create(orderID string, user string) error {
	fmt.Println("order created:", orderID)
	return s.notifier.Send(user, "your order "+orderID+" is created")
}

func main() {
	// 换一种通知方式，只需替换注入的实现
	NewOrderService(EmailNotifier{}).Create("1001", "alice")
	NewOrderService(SMSNotifier{}).Create("1002", "bob")
	NewOrderService(PushNotifier{}).Create("1003", "carol")
}
```

预期输出：

```text
order created: 1001
[email] to=alice msg=your order 1001 is created
order created: 1002
[sms] to=bob msg=your order 1002 is created
order created: 1003
[push] to=carol msg=your order 1003 is created
```

### 代码说明

- `OrderService` 只依赖 `Notifier` 接口，不依赖任何具体实现类，这就是**依赖倒置**；新增 `PushNotifier` 时 `OrderService` 完全不用改，体现了**开闭原则**
- 通知能力通过字段组合注入，而不是继承某个通知基类，体现了**合成复用**；将来要换成"短信 + 推送"双通道，只需再写一个组合实现，无需改动既有类
- `Notifier` 只有一个方法，调用方不会被迫实现用不到的方法，符合**接口隔离**
- `Create` 只负责下单与通知两个连贯动作，职责清晰；`OrderService` 变化的原因只有"订单流程变化"一个，符合**单一职责**

### 技术点总结

- 七大原则是设计模式的底层共识，比记模式本身更有迁移价值
- 依赖倒置 + 开闭通常一起生效：面向接口编程，新需求靠新增实现满足
- 组合优于继承，装饰器与代理都是组合复用的产物
- 原则之间会有张力（如迪米特法则会引入中介类），需要按真实场景权衡
