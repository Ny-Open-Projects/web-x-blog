## FRP-302：框架运行时剖析：一次更新的成本归因方法

**答**：
- 归因维度四段：触发（哪个状态/事件）、调度（何时渲染/同步异步）、执行（render/diff/patch 各段耗时）、提交（DOM 写了多少）——按段量化才能定位
- 各框架的观测点：React Profiler（actualDuration/beginWork）、Vue DevTools（组件渲染时间轴）、Solid 的 effect 调用计数——框架内置工具 vs 浏览器 trace
- 成本大头规律：大列表 diff（key 不稳）、props 引用不稳（子树重跑）、computed 重算链——「状态设计」比框架选择更决定性能
- DOM 写入成本：patch 的实际 DOM 操作数（追加/移动/属性）——Performance 面板 Layout/Paint 联动看「框架写 DOM 引发的重排」
- 度量口径统一化：跨框架项目用「自定义探针」（mark/measure 包住关键组件）而不是框架各自工具——对比才公平

```text
成本归因模板:
  触发源: store X 变更 → N 个组件订阅
  调度: 同帧 M 次渲染 (批合并失效?)
  执行: render 8ms / diff 12ms / patch 5ms
  提交: DOM 写 45 次 → 3 次强制 layout
定位: 最大段 → 对应优化策略
```
