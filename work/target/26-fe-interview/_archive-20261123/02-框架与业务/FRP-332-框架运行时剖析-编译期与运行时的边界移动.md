## FRP-332：框架运行时剖析：编译期与运行时的边界移动

**答**：
- 边界移动的驱动力：运行时开销（diff/依赖收集）向编译期转移（React Compiler/Vapor/Svelte）——「编译器能证明的优化」进编译期，「证明不了的」留运行时
- 编译期能力的边界：静态可分析（组件内数据流）可编译优化；动态（运行时字符串模板/第三方突变）必须保留运行时兜底
- React Compiler 的折中：运行时仍是 vdom（不换模型），编译器只加缓存——保守路线；Vapor/Solid 换模型——激进路线
- 调试与心智的代价：编译器优化让「代码 ≠ 行为」（渲染次数不可见）——React Compiler 提供「可缓存性 lint」缓解
- 团队影响：编译器质量成为框架竞争力（Solid 编译器 bug 的历史教训）——选型要评估编译器成熟度

```text
边界移动光谱:
  React Compiler:  保留 vdom, 编译加缓存 (保守)
  Vue Vapor:       去掉 vdom, 编译生成细粒度更新 (激进)
  Svelte:          全编译, 运行时最小
  代价: 编译器复杂度 + 「代码≠行为」的可观测性下降
```
