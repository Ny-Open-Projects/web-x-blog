## R19-415：并发渲染的产品侧权衡：三个真实场景的取舍

**答**：
- 场景一（电商搜索）：输入 + 大列表过滤——deferredValue + 虚拟列表；「旧结果显示 + 角标提示更新中」的产品设计（stale 可见性）；收益：输入 P95 从 300ms → 60ms
- 场景二（IM 会话切换）：transition 切换会话 + Activity 预渲染相邻会话——旧会话保持直到新会话就绪；取舍：双缓冲内存 vs 切换流畅
- 场景三（仪表盘刷新）：30s 轮询数据刷新——不用 transition（后台刷新不抢输入优先级），直接低频 setState + 图表实例 setData；教训：并发特性不是处处适用
- 共同方法论：先量化（INP/渲染耗时）→ 语义判断（可丢弃性）→ 特性选择 → 指标验收 → 可回滚
- 反面案例：把所有 setState 包 transition 的「一刀切」——输入延迟 + 双渲染开销，全量劣化；并发特性是工具箱不是默认值

```text
方法论:
  量化现状 → 语义判断(可丢弃?) → 特性选择 → 指标验收 → 可回滚
  电商搜索: deferredValue ✓ (输入优先)
  IM 切换: transition + Activity ✓ (切换流畅)
  仪表盘: 同步 setState ✓ (后台刷新无需打断能力)
```
