## V3-478：运行时性能剖析：组件更新成本归因方法

**答**：
- 归因三步：谁触发的更新（component update 的 stack）、更新了什么（patch 哪些 vnode/props）、为什么这么贵（子树规模/重计算 props）
- 工具链：Vue DevTools Performance 面板（按组件树时间轴）、Chrome Performance 里搜 `patch` / `componentUpdate` 自定义 mark、vite-plugin-vue-devtools 的组件 inspector
- 常见成本源：computed 过度重算（依赖链长）、watch deep 大对象（每次全量遍历）、大列表无虚拟化、子组件 props 引用不稳定（每次新对象）
- 量化口径：单次更新耗时（P95）、更新频率（每秒 update 次数）、重渲染组件数——「贵而少」的更新可接受，「碎而多」的要治理
- 与原生指标关联：组件更新必须落在 INP 之外（INP 只算交互延迟）——「更新慢但交互不卡」是可接受，「更新堵在输入处理里」必须切走

```javascript
// 自定义 mark 定位组件更新
import { onRenderTriggered } from 'vue';
onRenderTriggered((e) => {
  performance.mark(`update:${__filename}:${e.key}`);
  // DevTools Performance 中可见触发源
});
```
