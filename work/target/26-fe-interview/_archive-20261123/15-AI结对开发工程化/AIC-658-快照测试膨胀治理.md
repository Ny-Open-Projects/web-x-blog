## AIC-658：AI 爱写大快照测试，膨胀后没人敢看，怎么治理？

**答**：
- 结论先行：**快照测试（snapshot）的问题是「易生成、难审查」——AI 一写一个几千行快照，review 时全点「更新」成了习惯，快照就失去意义**。治理核心是「限制快照大小 + 关键行为用显式断言」。
- 为什么会膨胀：AI 为了让测试「覆盖全」，把整个组件渲染结果存成快照；每次 UI 微调都要更新，更新时没人逐行看——快照变成「橡皮图章」（AIC-237 快照治理）。
- 治理手段：1) **大小阈值**：单个快照超过 N 行（如 50）就 CI 告警/拒绝——强制 AI 缩小快照范围；2) **局部快照**：只快照关键子树，而非整页；3) **显式断言替代**：对「价格显示」「库存状态」等关键行为，用 `expect(getByText('¥99')).toBeInTheDocument()` 明确断言，比快照更可读、更抗变更；4) **更新审查**：快照更新必须 review diff，禁止无脑 `-u`。
- 让 AI 做对：在 rules 里写「禁止对整个页面做快照，只快照单个纯展示子组件，且不超过 50 行」；生成后扫快照大小。
- 追问钩子：为什么「显式断言」比「快照」更适合 AI 生成的代码？——因为快照断言的是「当前输出长这样」（包括所有偶然细节），一点无关变更就失败；显式断言的是「关键行为符合预期」，稳定且可读——AI 代码变更频繁，显式断言维护成本远低于快照。

```typescript
function checkSnapshotSize(snapshots: { name: string; lines: number }[], maxLines = 50) {
  const oversized = snapshots.filter(s => s.lines > maxLines);
  return {
    oversized: oversized.map(s => `${s.name}: ${s.lines}行`),
    passed: oversized.length === 0,
    suggestion: oversized.length ? '拆分为局部快照或改用显式断言' : undefined,
  };
}

const r = checkSnapshotSize([
  { name: 'ProductPage', lines: 800 },   // 超标
  { name: 'PriceTag', lines: 12 },        // OK
], 50);
console.log(r.passed === false && r.oversized.length === 1);
console.log(checkSnapshotSize([{ name: 'Tag', lines: 10 }]).passed === true);
```
