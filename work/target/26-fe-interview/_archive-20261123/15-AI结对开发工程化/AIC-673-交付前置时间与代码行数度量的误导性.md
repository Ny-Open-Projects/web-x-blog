## AIC-673：用「代码行数」或「前置时间」度量 AI 产出为什么误导？

**答**：
- 结论先行：**代码行数衡量「投入不衡量产出」（AI 爱写冗长代码），前置时间衡量「流程速度不衡量价值交付」**——两者都不是好指标，要用「有效交付 + 质量护栏」。
- 代码行数的陷阱：1) AI 倾向写「防御性冗长代码」（层层校验、重复逻辑），行数增加但价值没增；2) 好的重构是「减少代码」，行数指标会把它算成负产出；3) 一行核心算法可能胜过 500 行样板——行数与价值弱相关。
- 前置时间的陷阱：1) 只压缩了「编码」段，但评审/测试段拥堵——总前置时间没变；2) 可以靠「拆小 PR」刷低前置时间（每个 PR 都小都快，但总交付没变）；3) 快交付但上线回滚 = 负价值，前置时间不会体现。
- 更好的指标：1) **有效交付吞吐量**（通过评审 + 7 天存活的功能点，AIC-663）；2) **价值流效率**（增值时间/总时间，识别等待浪费）；3) **质量护栏**（逃逸率、回滚率）一起看——速度与质量必须成对出现。
- 追问钩子：为什么「拆小 PR」能让前置时间数据变好看却不代表真提效？——因为前置时间是按 PR 平均的，把大 PR 拆成 5 个小 PR，平均前置时间自然下降，但用户等待的完整功能交付时间没变；这是「指标优化」而非「效率优化」——古德哈特定律的典型案例。

```typescript
type Metrics = { linesAdded: number; prCount: number; avgLeadTimeH: number; deliveredPoints: number; survived: boolean };

function evaluate(m: Metrics): { good: boolean; issues: string[] } {
  const issues = [];
  if (m.linesAdded > 2000 && m.deliveredPoints < 10) issues.push('行数高但交付少：可能灌水');
  if (m.prCount > 20 && m.deliveredPoints < 20) issues.push('PR多但交付少：可能拆PR刷数据');
  if (m.avgLeadTimeH < 4 && !m.survived) issues.push('快但没存活：交付无效');
  return { good: issues.length === 0, issues };
}

console.log(evaluate({ linesAdded: 3000, prCount: 25, avgLeadTimeH: 2, deliveredPoints: 8, survived: false }).issues.length); // 3
console.log(evaluate({ linesAdded: 300, prCount: 3, avgLeadTimeH: 10, deliveredPoints: 15, survived: true }).good); // true
```
