## AIC-627：两个模型给出冲突方案，怎么裁决而不是拍脑袋？

**答**：
- 结论先行：**裁决靠「测量优先」——把方案之争转成可验证的指标之争**（AIC-452 双模型仲裁器）。谁的理论再漂亮，跑不过测试就是错的。
- 裁决四步：1) **转成可执行**：让两个方案各自生成最小可运行 demo 或测试用例；2) **定义度量**：性能（耗时/包体积）、正确性（边界测试通过率）、可维护性（圈复杂度）、成本，按场景加权；3) **实测**：在相同输入下跑，拿数据说话；4) **人类拍板**：数据接近时，由人按业务上下文（团队熟悉度、交付时间）决定。
- 避免两种坑：1) **「让第三个模型投票」**——三个模型可能同质化地错（AIC-638 投票多样性），投票不等于正确；2) **「选更详细的那个」**——详细度与正确性无关，LLM 擅长把错方案写得很详尽。
- 保留分歧记录：把「为什么选 A 不选 B」写进 ADR（架构决策记录），供后人理解，也供将来复盘（AIC-224 ADR 评审）。
- 追问钩子：为什么「测量优先」能破解「模型都很自信」的僵局？——因为 LLM 的自信度与实际正确率相关性很弱（校准差），但测试结果是客观的；把主观自信之争转成客观数据之争，僵局自然消解。

```typescript
type Plan = { name: string; metrics: { perf: number; correct: number; complexity: number } };

function arbitrate(plans: Plan[], weights = { perf: 0.3, correct: 0.5, complexity: 0.2 }): Plan {
  const scored = plans.map(p => ({
    plan: p,
    score: p.metrics.perf * weights.perf
      + p.metrics.correct * weights.correct
      + p.metrics.complexity * weights.complexity,
  }));
  scored.sort((a, b) => b.score - a.score);
  return scored[0].plan; // 数据优先，接近时再由人按业务上下文定
}

const a: Plan = { name: '方案A-虚拟滚动', metrics: { perf: 9, correct: 7, complexity: 5 } };
const b: Plan = { name: '方案B-分页', metrics: { perf: 6, correct: 9, complexity: 8 } };
console.log(arbitrate([a, b]).name); // 按权重算：B 略高，数据说话
```
