## AIC-137：用 AI 做 API 设计评审的 prompt 怎么写？「红队视角」评审法是什么？
**答**：
- 常规评审 prompt：给接口契约（OpenAPI/类型定义）+ 业务场景，从一致性（命名/分页/错误码规范）、演进性（版本化、兼容性）、易用性（调用方视角）三个维度评审。
- 红队视角评审法：让 AI 扮演「想搞坏这个 API 的调用方」——找出会被误用的参数（可空但没默认？布尔陷阱？）、缺失的限流与幂等设计、并发调用的破坏面。红队产出的问题往往比正面评审尖锐。
- prompt 要点：给「错误码字典」让它检查语义分配；给「现有 API 三例」让它对齐风格；要求输出「最容易被前端踩的 3 个坑」——前端视角的 API 评审最实用。
- 流程：设计稿阶段就跑 AI 评审（改契约成本低），定稿前人裁决——API 是最难改的资产，评审前置价值最高。
- 追问钩子：红队 prompt 也要防「表演性挑刺」——要求每个问题给出具体触发场景，不能泛泛说「可能有风险」。

```javascript
// API 红队评审 prompt
const redTeamPrompt = `
你是想搞坏这个 API 的恶意调用方/粗心调用方。找出：
1. 容易误用的参数设计（可空无默认、布尔陷阱、单位不明）
2. 并发/重复调用的破坏面（缺幂等键？）
3. 前端最可能踩的 3 个坑（含具体触发场景）
<contract>${openapiYaml}</contract>
现有风格参考：${examples}`;
```
