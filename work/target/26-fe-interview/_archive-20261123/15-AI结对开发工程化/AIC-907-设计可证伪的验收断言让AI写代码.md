## AIC-907：让 AI 写代码前，如何设计「可证伪」的验收断言，避免它产出「看起来对、其实没法验证」的代码？
**答**：
- 可证伪 = 断言必须能被运行结果判定真假；「性能要好」「代码要优雅」不可证伪，要转成「P95 < 200ms」「圈复杂度 < 10」这类可测指标。
- 先写断言（测试先行）再让 AI 写实现：断言就是验收契约，AI 有明确目标，人也只需核对断言是否覆盖了真实需求。
- 断言要包含「反例」——不仅验证正确输入产出正确，也验证错误输入被拒绝（如非法优惠码不能打折），否则 AI 可能写出只过 happy path 的代码。
- 追问钩子：能说出「如果一条验收标准你无法写出它的失败条件，它就还不该交给 AI」的候选人，掌握了可验证性的核心。

```typescript
// 可证伪断言：每条都能被运行判定真假
const acceptance = [
  { name:'正确计价', run:(f)=> f(100,2) === 200 },
  { name:'负数量拒绝', run:(f)=> f(100,-1) === 0 || f(100,-1) === null },
  { name:'超大数量封顶', run:(f)=> f(100, 1e9) <= Number.MAX_SAFE_INTEGER },
];
function accept(f) {
  return acceptance.map(a => ({ name:a.name, pass:a.run(f) }));
}
// 交给 AI 前先把断言固定；断言含反例，AI 无法只写 happy path 蒙混
console.log(accept((p,q) => q>0 ? p*q : 0));
```
