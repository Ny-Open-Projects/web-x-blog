## TST-816：面对多业务线，如何平衡「统一测试基建」与「业务线灵活性」？
**答**：
- 结论：基建统一「机制」、业务保留「策略」——平台提供标准执行引擎与门禁能力，业务线在自己的边界内定制用例与阈值。
- 统一层：runner、CI 模板、报告格式、flaky 治理、数据工厂——这些是规模效应最强的公共能力。
- 灵活层：业务线自定义用例集、风险阈值、门禁松紧（在平台护栏内），允许「有理有据」的例外。
- 治理机制：通过「基类 + 继承 + override」而非 fork，例外需登记并定期复审，防止演变成各自为政。
- 追问钩子：某业务线坚持不用统一基建，你如何判断它是「合理的特殊性」还是「逃避治理」？

```javascript
// 统一基类 + 业务线 override：机制统一，策略灵活
class TestBaseline {
  gate() { return { coverage: 0.7, flaky: 0.01 }; }
  runner() { return 'vitest'; }
}
class PaymentLine extends TestBaseline {
  gate() { return { ...super.gate(), coverage: 0.85 }; } // 支付线更严
  // runner 沿用统一基建
}
const line = new PaymentLine();
console.log(line.runner(), line.gate()); // vitest { coverage:0.85, flaky:0.01 }
```
