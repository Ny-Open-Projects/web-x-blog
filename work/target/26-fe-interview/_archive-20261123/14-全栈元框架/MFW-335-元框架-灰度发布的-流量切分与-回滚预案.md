## MFW-335：元框架应用的灰度发布如何做流量切分与回滚预案？

**答**：
- 按请求特征切流：UID 尾号 / Cookie 标记 / Header，比按比例随机更可回访（同一用户稳定命中同一版本），这是 SSR 应用首选。
- 中间件（`middleware.ts`）是最自然的切流点：命中实验组改写目标到新版本部署，注意改写不要破坏静态资源前缀。
- 新旧版本必须共享同一套静态资源哈希空间，避免「旧 HTML 引到新 chunk」：要么版本目录隔离，要么旧版本产物保留一个回滚窗口期。
- 回滚预案要演练：回滚 = 把中间件切流规则归零 + 路由指回旧版本目录，秒级生效，而不是重新走构建。
- 追问钩子：灰度期间 Server Action / API contract 不兼容怎么办？——双版本共存期接口做向后兼容，禁止灰度期改协议。

```ts
// middleware.ts：Cookie + 尾号双条件灰度
export function middleware(req: NextRequest) {
  const bucket = req.cookies.get('beta')?.value
    ?? (Number(req.headers.get('x-uid') || 0) % 100 < 10 ? 'on' : 'off');
  if (bucket === 'on' && req.nextUrl.pathname.startsWith('/p/')) {
    const url = req.nextUrl.clone();
    url.pathname = `/beta${req.nextUrl.pathname}`; // 转发到新版本路由
    return NextResponse.rewrite(url);
  }
  return NextResponse.next();
}
// 回滚：把 beta Cookie 下发开关关掉 + 尾号阈值调 0，旧版本即时恢复
```
