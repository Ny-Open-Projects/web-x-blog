## WCN-866：编译平台的「缓存失效」策略如何设计？

**答**：
- 结论先行：缓存失效的目标是「该失效的绝不留住，能复用的绝不重算」——靠「精确的依赖追踪 + 多维度的 key 校验」实现，宁可保守失效，不可返回陈旧产物。
- 缓存层次：解析缓存（源码→AST）、转换缓存（AST→IR）、产物缓存（IR→code）、构建缓存（整包产物）——粒度越细复用率越高，但管理越复杂。
- 失效触发：源码内容变化（内容哈希）、依赖变化（传递失效）、配置变化（config hash）、编译器/插件版本变化、环境变量变化——任一变化即让相关缓存失效。
- 依赖追踪：构建时记录「谁依赖谁」的精确图（含动态依赖、样式/token 等隐式依赖），变更时只失效反向依赖链；用 hash 比对避免无谓失效（内容没真变就不失效）。
- 持久化与校验：磁盘缓存跨进程复用，加载时校验 key 与完整性（hash/checksum），损坏则重算；设容量上限与 LRU 淘汰。
- 追问钩子：面试官会问「增量编译偶尔产出旧代码怎么排查」——答：多半是失效条件漏了——如隐式依赖没记录、config hash 没纳入、mtime 误判；用「干净构建 vs 增量构建产物对比」定位，补齐失效维度。

```javascript
// 多维度缓存 key：任一维度变化即失效
function cacheKey(file, sources, deps, ctx) {
  const hash = (s) => [...s].reduce((h, c) => (h * 31 + c.charCodeAt(0)) | 0, 0);
  const sourceHash = hash(sources[file]);
  const depHash = (deps[file] || []).map(d => hash(sources[d] || '')).join('-');
  return [
    file, sourceHash, depHash,
    ctx.compilerVersion, ctx.configHash, ctx.pluginVersions.join(','),
  ].join('|');
}
function getOrCompute(key, cache, compute) {
  if (cache.has(key)) return cache.get(key);       // 命中
  const value = compute(); cache.set(key, value); return value;
}
```
