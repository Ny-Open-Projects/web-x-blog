## WCN-884：设计系统的「设计债务」如何识别与管理？

**答**：
- 结论先行：设计债务是「设计层的不一致与粗糙」——如 token 裸值、组件视觉不统一、交互模式矛盾、过时样式——它像技术债一样会累积利息（用户困惑、开发返工、品牌受损），需要显式管理。
- 识别来源：设计走查（design review）发现的偏差、视觉回归差异、token 裸值扫描、用户反馈（「这个按钮怎么跟那个不一样」）、设计师的「设计债 backlog」。
- 量化：给每笔设计债标「影响面」（多少页面/组件受影响）与「利息」（导致的返工工时、体验投诉），按影响×利息排序；与技术债一起纳入统一看板。
- 管理：固定比例人力偿还、大改版（设计系统 2.0）时集中清偿、新组件严格遵循规范避免制造新债；用「设计 lint」（自动检测裸值/不一致）持续拦截。
- 与技术债协同：很多设计债的偿还伴随代码改动（换 token、调布局）——设计债与技术债应统一排期，别分成两套互不相干的清单。
- 追问钩子：面试官会问「设计师和工程师对什么是债看法不同怎么办」——答：用「用户影响 + 维护成本」作为共同语言量化，而非「好不好看」的主观争论；让数据驱动优先级。

```javascript
// 设计债看板：影响面 × 利息 排序
const designDebts = [
  { id: 'bare-color', impact: 40, interest: 8, type: 'token' },
  { id: 'two-button-styles', impact: 15, interest: 12, type: 'component' },
  { id: 'outdated-shadow', impact: 60, interest: 3, type: 'style' },
];
function prioritizeDebts(list) {
  return list.map(d => ({ ...d, score: d.impact * d.interest }))
             .sort((a, b) => b.score - a.score);
}
console.log(prioritizeDebts(designDebts).map(d => `${d.id}: ${d.score}`));
```
