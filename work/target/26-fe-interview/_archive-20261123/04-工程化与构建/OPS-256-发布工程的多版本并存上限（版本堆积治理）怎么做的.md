## OPS-256：版本堆积怎么治理？
**答**：
- 版本来源：灰度并存/长尾用户残留/App 各版本在线——线上真实版本分布比「当前版本」复杂得多。
- 治理指标：活跃版本数（7 日内有流量的版本）、各版本流量占比——版本数 > 5 时复杂度告警（兼容矩阵/排障成本指数上升）。
- 治理手段：强制升级（App）/刷新引导（Web）/N-2 资源清理（SCN-OPS-218 保留窗口）/灰度时限（SCN-OPS-213）。
- 兼容矩阵随版本数膨胀：每个在线版本 × 服务端 API 的兼容测试——版本堆积直接放大测试成本。
- 追问钩子：为什么版本数 > 5 要告警——每个在线版本都是一个「必须兼容的现存事实」：排障时要考虑 5 种版本行为、兼容矩阵 5×N、修复要验证多版本——版本复杂度的成本是超线性的；堆积治理（强制升级/清理）是把复杂度压回可控区间的手段。

```javascript
function versionSprawl(activeVersions, { cap = 5 } = {}) {
  const withTraffic = activeVersions.filter(v => v.traffic7d > 0);
  return {
    count: withTraffic.length,
    distribution: withTraffic.map(v => ({ v: v.id, pct: v.trafficPct })),
    alert: withTraffic.length > cap
      ? { action: '强制升级/清理 N-2/灰度收口', note: '兼容矩阵成本超线性增长' } : null,
  };
}
```
