## OPS-244：跨版本会话怎么处理？
**答**：
- 横跳场景：灰度调整（放量/回滚）后同一用户可能在两次请求间跨越版本边界——会话稳定性优先：会话内 sticky（首次分配的版本保持到会话结束），新会话才重新分流。
- sticky 实现：会话级版本戳（cookie/session 存储），网关优先按会话戳分流——防止用户一半请求新版本一半旧版本（购物车/表单状态混乱）。
- sticky 的副作用：放量后新用户分配快、老用户滞后——放量进度看板区分「新会话渗透率」与「全量渗透率」。
- sticky 生命周期：会话结束（或 24h 过期）重新分流；紧急回滚时 sticky 可被覆盖（回滚优先于 sticky）。
- 追问钩子：为什么跨版本横跳必须用「会话 sticky」而不是允许混跑——用户一半请求 v1 一半 v2 时，前端状态（购物车 schema/表单草稿）在两版本间不一致，可能出现「提交的是 v1 数据 v2 解析」的复合错误；sticky 用会话级版本戳把混跑变成「版本内一致」，这是数据一致性的底线设计。

```javascript
function resolveVersion(user, session) {
  if (session.versionStamp && !emergencyRollback)
    return session.versionStamp;                       // sticky：会话内稳定
  const v = gatewaySplit(user);
  session.versionStamp = v;                            // 首次分配固化
  return v;
}
// 回滚覆盖 sticky：emergencyRollback 强制全量回旧版
```
