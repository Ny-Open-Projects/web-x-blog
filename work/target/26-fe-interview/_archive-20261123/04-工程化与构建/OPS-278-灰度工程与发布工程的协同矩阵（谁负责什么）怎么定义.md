## OPS-278：责任矩阵怎么定义？
**答**：
- RACI 落到发布环节：构建（开发）→ 审批（owner/平台）→ 灰度决策（发布人 + 业务方）→ 哨兵处置（值班）→ 回滚决策（发布人 + 值班经理）→ 善后（发布人）——每个环节唯一负责（Accountable），避免「都管都不管」。
- 灰糊地带显式化：灰度指标的业务解读（技术看得懂错误率看不懂转化波动）——显式分配给业务方，技术方提供数据。
- 矩阵随风险级别变化：L0 发布可自动化（无人工环节），L3 每个环节都有人工角色——责任矩阵是风险分级的配套。
- 矩阵的入口展示：发布计划生成时展示「本发布各环节的负责人」——责任前置可见而不是事后追责。
- 追问钩子：为什么责任矩阵要「随风险级别变化」——L0 小变更全流程人工审批是浪费（ automation 覆盖），L3 大变更无人工环节是冒险；矩阵与风险分级的联动让「流程重量匹配风险重量」——这是分级治理在责任维度的落点。

```javascript
const raci = {
  L0: { build: 'auto', approve: 'auto', gray: 'auto', sentinel: 'auto', rollback: 'auto' },
  L3: { build: 'dev', approve: ['owner', 'platform', 'oncall-mgr'],
        gray: ['release-owner', 'biz-owner'], sentinel: 'oncall',
        rollback: ['release-owner', 'oncall-mgr'], aftermath: 'release-owner' },
  show: (plan) => plan.raci,                           // 责任前置可见
};
```
