## ENG-255：回滚策略怎么设计？
**答**：
- 回滚分类：产物回滚（切回旧入口，秒级，SCN-ENG-251）vs 数据回滚（新版本写入了新 schema 数据，回滚产物也不兼容）——发布前必须识别「数据写入型变更」。
- 前向修复优先：能 hotfix（旧版本兼容新数据：读旧写旧 + 读新降级）就不回滚数据——数据回滚是最后手段（有损）。
- 回滚演练：回滚流程与发布流程同级演练（每季度真实回滚一次生产预发），未演练的回滚是纸面能力。
- 回滚半径：回滚操作记录影响面（哪些用户会看到版本回退/哪些本地状态失效），提前公告。
- 追问钩子：为什么「前向修复」优于「回滚数据」——数据回滚意味着用户刚产生的数据（订单/草稿）可能丢失或需要迁移回旧格式；让旧版本「容忍」新数据（向后兼容读取）成本更低且无数据损失风险。

```yaml
# 发布风险标记
changes:
  - type: data-write        # 新 schema 写入 → 回滚需兼容读取
    forwardFix: 'v1 读新字段降级为默认值'
  - type: pure-ui           # 纯 UI → 产物回滚即可
rollback:
  entrySwitch: '< 1min'
  drill: quarterly
```
