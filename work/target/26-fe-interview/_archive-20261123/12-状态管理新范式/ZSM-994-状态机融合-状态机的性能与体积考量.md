## 994：状态机的运行时开销与体积考量

**答**：
- 体积：XState 核心 ~8kb（gz）+ 可视化工具不进生产——体积成本可控；运行时开销：每次 send 的状态查找 O(状态数)（小机器可忽略）、subscription 通知（与 zustand 同级）。
- 性能热点：高频事件（鼠标移动逐事件 send）——高频输入不该进机器（节流在入口层，机器收低频语义事件「dragging moved」而非每像素）；大 context 的 assign 拷贝（context 大对象 assign 全量拷贝——context 保持小而结构化，大数据放外部 store）。
- 实例管理：机器实例的创建销毁成本（每流程一台——流程结束 stop 机器防泄漏）；常驻机器（全局会话机）单例常驻无成本。
- 追问钩子：为什么「大数据放外部 store」？——机器 context 的每次 assign 都产生新对象（不可变语义）——把 10MB 列表放 context，每次迁移全量拷贝；context 只存「流程必需的最小状态」，数据引用外部。

```ts
// 反模式：大数据进 context（每次 assign 全量拷贝）
// 正解：context 存引用 + 数据在外部 store
context: { listRef: null as ListStore | null }   // 引用而非数据本体
// 高频事件：入口节流后发语义事件
onMouseMove = throttle(e => actor.send({ type: 'MOVED', x: e.x }), 100);
```
