## ZSM-723：状态侧的错误边界与恢复：store 异常时 UI 怎么不白屏

**答**：
- 状态层抛错的三类：1) **selector 抛错**（数据结构不符）——渲染期异常，React ErrorBoundary 可接；2) **action 抛错**（提交失败）——事件回调异常，boundary 接不住（不在渲染期），要 action 层自己 catch 并写入错误状态；3) **订阅回调抛错**——会炸掉通知循环，让其他订阅者收不到更新（状态库内部要 try/catch 隔离每个 listener）。
- 恢复策略分级：selector 错 → 降级渲染（fallback 值 + 错误标记）；action 错 → 错误状态机（可重试）；持久层错 → 丢弃缓存回默认值（ZSM-502 的容错）。原则：**store 永远是「可渲染的合法形状」**——任何路径都要保证 state 不是 undefined/null 树。
- 防御性 selector：读取可能缺失的结构用安全路径（`data?.user?.name ?? '—'`），或 select 里 try/catch 返回降级值；但大量 try/catch 是「数据形状失控」的信号，应修数据层而不是到处兜。
- 状态库内部的错误隔离：notify 循环里每个 listener 单独 try/catch（TanStack/Zustand 都这么做），一个坏订阅不影响其他；日志必须记录被吞的错误（静默吞错是排查地狱）。
- 追问钩子：ErrorBoundary 的 reset 与状态对齐——boundary 重置 UI 时要同步重置 store（`queryClient.resetQueries()` 或 store 回初始值），否则「UI 重置了状态还是错的」。

```javascript
// 订阅通知的错误隔离（状态库内部）
function notifySubscribers(subs, state) {
  for (const fn of subs) {
    try {
      fn(state)
    } catch (e) {
      // 单个坏订阅不炸通知循环
      console.error('[store] subscriber error', e)   // 必须记录，不静默
      // 可选：自动退订坏订阅（反复抛错的）
    }
  }
}

// action 层错误状态机
const useUpload = create((set, get) => ({
  phase: 'idle',
  error: null,
  async submit() {
    if (get().phase === 'submitting') return            // 重入防护
    set({ phase: 'submitting', error: null })
    try {
      await api.submit()
      set({ phase: 'done' })
    } catch (e) {
      // 错误进状态：UI 渲染错误 + 可重试，不抛给 boundary
      set({ phase: 'error', error: { code: e.code, retryable: e.code !== 'FORBIDDEN' } })
    }
  },
}))

// selector 防御
const useUserName = () => useStore((s) => s.data?.user?.name ?? '—')

// boundary reset 与状态对齐
function ErrorFallback({ resetErrorBoundary }) {
  return <button onClick={() => {
    queryClient.resetQueries()                 // 状态同步重置
    resetErrorBoundary()
  }}>重试</button>
}
```
