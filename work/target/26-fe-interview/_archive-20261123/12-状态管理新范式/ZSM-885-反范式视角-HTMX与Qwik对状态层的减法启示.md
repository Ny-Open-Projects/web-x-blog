## ZSM-885：反范式视角：HTMX/Qwik 对状态层的「减法」启示

**答**：
- 反范式（去框架化）思潮对状态层的启示不是「抛弃状态库」而是「识别哪些状态根本不需要存在」：
- **HTMX 的启示**：服务端返回 HTML 片段替换 DOM——「大部分『状态』其实是『服务端数据的临时镜像』，请求-响应直接替换就不需要镜像」。应用到 React：列表筛选如果每次都是完整请求-替换（无局部交互），URL + 服务端渲染即可，零客户端状态（ZSM-795 RSC 直读的极端版）。
- **Qwik 的启示**：组件级代码懒加载（可恢复性 resumability）——「状态序列化到 HTML，恢复时无需重放」。启示：状态的水合成本可以被消除——「能序列化就别重算」——对我们 persist/初始注入（751/830）的启发是「快照优于重放」在特定场景成立。
- **减法清单**（状态层的「不需要状态」检查表）：1) 纯服务端展示数据 → RSC 直读；2) 纯展示联动 → CSS :has；3) 一次性请求 → use(promise)；4) 导航态 → Navigation API；5) 可由派生得出的 → 派生不存储。五项检查后再决定「这个状态要不要建」。
- 减法的边界：交互密集区（编辑器/协同/动画）的复杂状态不可减——反范式适合「内容展示型」应用，不适合「工具型」应用——判断维度是「交互密度」。
- 追问钩子：面试中引用反范式的正确姿势——「我研究过 HTMX/Qwik 的思路，它们提醒我们把『不需要状态的地方』识别出来——我的实践是在形状评审（618）里加了『不需要状态检查表』五项」——展示视野而非站队。
