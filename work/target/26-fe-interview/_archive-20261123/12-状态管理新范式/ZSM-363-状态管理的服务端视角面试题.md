## ZSM-363：服务端同学常问：前端为什么缓存而不是每次都拉接口

**答**:
- 三理由：体验（缓存命中零延迟渲染，等待即流失）、成本（重复请求打后端，QPS 与带宽翻倍）、一致性工程（缓存 + 失效协议让「读扩散」可控）
- 前端的承诺：失效协议保证最终一致（操作后失效 + 推送 + 校准），「缓存」不等于「陈旧展示」——staleTime 是业务允许的陈旧窗口，服务端可以参与定义（Cache-Control/ETag）
- 配合点：服务端给版本号/ETag/推送能力，前端按「新鲜度分级」缓存；强一致域（资金）服务端声明 no-cache，前端照办
- 反向提问法：面试中把「你们接口能提供失效通知吗」抛回去，展示缓存体系的协商意识

```javascript
// 服务端可控的新鲜度
useQuery({ queryKey, queryFn, staleTime: 30_000 })   // 前端声明窗口
// 协商：服务端 ETag → 前端条件请求 304 免重传
const res = await fetch(url, { headers: { 'If-None-Match': etag } })   // 304 → 缓存仍新鲜
```
