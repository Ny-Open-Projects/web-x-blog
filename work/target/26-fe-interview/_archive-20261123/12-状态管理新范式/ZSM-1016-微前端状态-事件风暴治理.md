## 1016：微前端总线的「事件风暴」（事件泛滥）治理

**答**：
- 事件风暴的形态：事件数量失控（几百个事件——契约评审形同虚设）、同义事件（order.updated/order.changed/order.modified——语义重叠）、粒度混乱（有的事件带全量数据有的带 id——消费方处理不一致）。
- 治理三招：命名审计（同域事件集中评审——合并同义事件，破坏性变更走版本化过渡）、粒度标准（事件只带「标识+变更类型」——数据由消费方按需取（缓存/API），全量 payload 是带宽与耦合的放大器）、数量红线（每应用 provides 上限——超限触发架构评审「是不是拆错了」）。
- 度量：事件流量看板（每事件的发布/订阅数——零订阅事件是死事件该删；高扇出事件是耦合热点）。
- 追问钩子：为什么「事件只带 id 不带全量数据」更好？——全量 payload 让发布方「猜」消费方需要什么（字段永远不够用→越加越多→契约膨胀）；id+类型让消费方自己取数（各自缓存/API）——契约瘦身且数据主权归消费方。

```txt
事件风暴治理：
1. 命名审计：合并同义事件（版本化过渡）
2. 粒度标准：事件 = 标识 + 变更类型（不带全量数据）
3. 数量红线：provides 上限触发架构评审
度量：零订阅事件 / 高扇出事件看板
```
