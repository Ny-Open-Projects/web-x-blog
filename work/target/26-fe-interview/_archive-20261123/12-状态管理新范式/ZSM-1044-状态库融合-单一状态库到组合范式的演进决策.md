## 1044：从单一状态库到「组合范式」的演进决策

**答**：
- 演进的触发信号：单一库的局限暴露（服务端缓存语义缺——引入 Query；复杂流程 if/else 地狱——引入状态机；跨应用冲突——引入微前端治理）——范式组合是「痛点驱动」的演进不是「技术时髦」的追逐。
- 组合的终态架构：Query（服务端状态）+ Zustand（客户端共享数据）+ XState（复杂流程）+ 组件局部 state（瞬时 UI）——四层各司其职，边界清晰（每层数据有且仅有一个家）。
- 演进的管理：每引入一个范式记录「为什么」（ADR）+「边界规则」（什么数据进哪层）——范式组合的复杂度靠「边界纪律」控制，无纪律的组合是复杂度爆炸。
- 追问钩子：为什么「一个库打天下」会先于「范式组合」失败？——单一库的甜蜜区是中小应用；大型应用里服务端缓存/流程建模/共享数据的语义差异太大——一个库必然用错语义（Query 当请求库/状态机当垃圾桶）。

```md
## 状态范式组合（终态架构）
| 层 | 范式 | 职责 |
| 服务端 | TanStack Query | 数据缓存与失效 |
| 共享数据 | Zustand | 客户端共享/偏好 |
| 流程 | XState | 复杂流程建模 |
| 瞬时 | useState | 组件局部 UI |
纪律：每份数据有且仅有一个家（ADR 记录）
```
