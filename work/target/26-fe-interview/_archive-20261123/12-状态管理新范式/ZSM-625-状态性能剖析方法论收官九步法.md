## ZSM-625：状态性能剖析方法论收官：九步法把一次优化做完整

**答**：
- 完整方法论的九步：1) **现象采集**——用户反馈/INP 数据/长任务定位到具体交互；2) **复现脚本化**——Playwright 固定轨迹，可重复测量；3) **基线测量**——渲染次数、提交耗时、阻塞时长、INP（ZSM-601）；4) **分层归因**——状态层 vs 渲染层（ZSM-606/607），找到主导分段；5) **根因定位**——三类重渲根因（ZSM-602）+ selector 热路径量化（ZSM-603）+ 序列化/内存排查（ZSM-605/609）；6) **修复方案决策**——按修复决策树（ZSM-614）+ 渐进式档位（ZSM-621）选定最低风险方案；7) **效果验证**——基准复测（ZSM-619）+ 统计显著性（ZSM-622），不显著不算成功；8) **防回退门禁**——性能预算进 CI（ZSM-616）+ review checklist；9) **生产验证**——INP 前后对比（ZSM-617），用户侧指标改善才算闭环。
- 方法论的本质：把「感觉卡」翻译成「可测量的分解问题」，每步都有产物（脚本/数据/报告/门禁），跨团队可交接。
- 面试应用：按九步法讲一个完整案例（现象 → 数据 → 归因 → 修复 → 数字对比），每步有具体数字，远胜于罗列「我知道 useShallow」。
- 缺步警示：跳过第 4 步分层归因直接 memo 组件是常见的「修错层」；跳过第 7 步显著性验证常导致「优化了个寂寞」。

```javascript
// 九步法产物清单（执行可校验）
const methodology = {
  1_现象采集: { artifact: '问题单 + INP p75 数据', tool: 'RUM/Sentry' },
  2_复现脚本: { artifact: 'playwright 轨迹脚本', tool: 'Playwright' },
  3_基线: { artifact: '基线表（renders/commit/blocking/INP）', tool: 'Profiler API + RUM' },
  4_分层归因: { artifact: '主导分段结论（状态层 or 渲染层）', tool: 'LayerProfiler' },
  5_根因: { artifact: 'Top selector 榜 + 泄漏清单 + stringify 耗时', tool: 'SelectorProfiler/Memory' },
  6_修复决策: { artifact: '决策树输出 + 选定档位', tool: 'suggestFixes' },
  7_效果验证: { artifact: '基准对比 + p 值', tool: 'Bench + ABValidator' },
  8_门禁: { artifact: '预算表进 CI', tool: 'BudgetGate' },
  9_生产验证: { artifact: 'INP p75 前后对比报告', tool: 'INP 归因探针' },
}
console.log(methodology)
```
