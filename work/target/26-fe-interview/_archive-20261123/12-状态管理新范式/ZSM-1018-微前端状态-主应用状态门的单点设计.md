## 1018：主应用作为「状态门」的单点设计与可用性

**答**：
- 状态门模式：主应用作为「共享状态的唯一入口」（认证/权限/字典——子应用一律通过状态门 API 获取）——单点带来可控性（变更可审计/缓存统一）也带来单点风险（主应用挂了全挂）。
- 可用性设计：状态门的降级快照（主应用异常时子应用用最后已知快照运行——只读降级）、关键数据的本地冗余（子应用缓存最近一次状态门响应——主应用重启期间可继续工作）。
- 状态门的接口稳定性：API 版本化（门是最高频的契约——变更影响所有子应用）+ 向后兼容承诺（增字段不删字段）。
- 追问钩子：为什么状态门「值得」承担单点风险？——共享状态分散（各应用各取各的）的一致性事故成本 > 单点可用性成本——且单点的可用性可以工程化（快照降级/冗余缓存），分散的一致性无法工程化（永远在补救）。

```ts
// 状态门：带降级快照
const stateGate = {
  get: k => authStore.getState()[k] ?? snapshot.get(k),  // 实时 -> 降级快照
  subscribe: authStore.subscribe,
};
// 子应用本地冗余
gate.subscribe(s => localCache.set('last_known', s));    // 降级时用
```
