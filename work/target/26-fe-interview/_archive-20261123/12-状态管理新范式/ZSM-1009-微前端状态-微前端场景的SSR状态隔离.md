## 1009：微前端 + SSR 的状态隔离（水合冲突）

**答**：
- 冲突场景：主子应用各自 SSR 水合（各自的全局状态序列化注入 window——key 冲突/双份水合顺序问题）；子应用的水合数据与主应用的全局状态不一致（主应用更新的用户态 vs 子应用 SSR 时的旧态）。
- 治理：水合数据命名空间化（window.__MF_STATE__[appName]——各应用独立桶）、水合顺序（主应用先水合（提供权威全局态），子应用后水合并校验全局态版本——版本不匹配放弃水合改客户端渲染）。
- 降级策略：子应用水合校验失败（全局态版本冲突）——降级为客户端渲染（白屏一瞬间换正确性）——SSR 的收益不值得用正确性换。
- 追问钩子：为什么子应用要「校验全局态版本」再水合？——子应用 SSR 时的快照基于「当时的全局态」，客户端水合时全局态可能已更新（另一请求/另一应用）——基于旧全局态的水合会渲染出与当前态矛盾的内容。

```ts
// 子应用水合前的版本校验
const ssrSnapshot = window.__MF_STATE__['order-app'];
if (ssrSnapshot.globalVer === globalState.version) {
  hydrate(qc, ssrSnapshot.queryState);          // 版本一致才水合
} else {
  renderClientOnly();                            // 冲突降级客户端渲染
}
```
