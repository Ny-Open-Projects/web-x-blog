## ZSM-132：什么情况下服务端状态不得不「复制」进客户端状态？怎么把复制风险降到最低？
**答**：
- 合法场景：需要本地编辑的草稿（表格行内编辑的副本）、离线可用数据、要参与纯本地计算的高频数据（拖拽坐标）、以及服务端不存在的派生结构（树展开态）。
- 降险三板斧：1) 复制时机集中（useQuery onSuccess/_effect 里一次性拷贝，禁止散落多处）；2) 标记版本/时间戳，重取后做 merge 策略（本地未 dirty 的字段跟服务端走）；3) 写回后立刻失效服务端缓存，回到单一真源。
- 反模式识别：把整页接口响应 setState 进 store「方便后面用」——90% 的字段从没被读过，纯负担；只拷实际用的子集。
- 面试要点：承认复制有时是必要的工程妥协，重点展示「你怎么管理复制的一致性」而不是背「不要复制」口号。

```javascript
// 行内编辑：受控副本 + dirty 跟踪 + 保存后失效
function useRowDraft(goods) {
  const [draft, setDraft] = useState(null)          // null = 非编辑态
  useEffect(() => {                                 // 服务端数据到达才拷贝
    if (goods && !draft?.dirty) setDraft({ ...goods, dirty: false })
  }, [goods])

  const edit = (patch) => setDraft(d => ({ ...d, ...patch, dirty: true }))

  const save = async () => {
    const saved = await api.updateGoods(draft.id, pick(draft, EDITABLE))
    await queryClient.invalidateQueries({ queryKey: ['goods', draft.id] })
    setDraft(null)                                  // 回归单一真源（缓存）
    return saved
  }
  return { draft, edit, save }
}
```
