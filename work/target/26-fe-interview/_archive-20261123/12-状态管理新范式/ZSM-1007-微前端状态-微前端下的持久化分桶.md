## 1007：微前端场景的持久化分桶与冲突

**答**：
- 分桶策略：持久化 storage key 带应用前缀（mf:order:list vs mf:user:list）——同 storage 各应用独立空间不互踩；共享数据（主题偏好）用约定的共享 key（单一写入者=主应用）。
- 版本与清库：子应用升级（数据结构变化）用 buster 清自己桶——子应用无权清其他应用的桶（各自治理）；主应用统一清理入口（用户登出时通知各应用清各自的敏感桶——事件驱动）。
- 冲突场景：同 key 双写（两个应用写同一 key——last-write-win 静默丢数据）——分桶杜绝；共享 key 的写权限单点化（只有主应用写，子应用通过 API 请求写入）。
- 追问钩子：为什么共享 key 要「单一写入者」？——多写入者的并发写（两应用同时写主题设置）谁后谁赢且无感知；单一写入者（主应用）让共享数据的变更可控可审计——写入权=数据主权。

```ts
// 分桶 key 规范
const storageKey = (app: string, k: string) => `mf:${app}:${k}`;
// 共享 key：主应用单写
bus.subscribe('theme.change', e => {   // 主应用监听子应用请求
  localStorage.setItem('mf:shared:theme', JSON.stringify(e));  // 只有主应用写
});
```
