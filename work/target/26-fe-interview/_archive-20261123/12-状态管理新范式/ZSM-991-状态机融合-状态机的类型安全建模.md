## 991：状态机的 TypeScript 类型安全（有限状态类型化）

**答**：
- 类型收益：事件类型与状态类型收窄（send 的事件名拼错编译报错、getState 的 value 是字面量联合——state.matches('editing') 的拼写检查）——状态机的「非法状态不可表示」在类型层再上一道锁。
- 建模纪律：状态名/事件名用 as const 或枚举（不散落字符串字面量）、context 类型显式声明（assign 的部分更新类型推导）、机器产出类型从 def 推导（XState 的 typeof machine 推导）。
- 常见类型坑：context 的 partial 更新（assign 返回部分字段——类型上要求完整 context，用 assign 的函数式部分更新）、事件的 payload 类型（每个事件独立 payload 类型标注）。
- 追问钩子：为什么「state.matches」比「state.value === 」好？——matches 支持嵌套路径（'editing.form'）且类型收窄（在 matches 分支内 context 类型自动收窄到该状态的专属字段——类型守卫语义）。

```ts
type CheckoutEvent =
  | { type: 'EDIT'; value: string }
  | { type: 'SUBMIT' }
  | { type: 'PAID' };
const machine = createMachine({
  context: { email: '' } as { email: string },       // 显式 context 类型
  states: { editing: { on: {
    EDIT: { actions: assign(({ context, event }) =>
      ({ email: event.value })) },                    // event 类型收窄
  } } },
});
type State = typeof machine;   // 状态/事件/Context 全类型化
```
