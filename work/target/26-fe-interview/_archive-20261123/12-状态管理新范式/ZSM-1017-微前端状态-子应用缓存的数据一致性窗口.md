## 1017：微前端下同实体数据的跨应用一致性窗口

**答**：
- 一致性窗口：A 应用改了订单 -> 事件传播 -> B 应用失效缓存 -> B 重取——窗口期内 B 展示旧数据（几百 ms 到数秒）——窗口期是微前端的固有属性（事件解耦的代价）。
- 窗口的业务容忍度分级：强一致数据（余额/库存）不走事件（直接查询权威源或主应用单点提供）、准一致数据（列表/详情——窗口可接受）、展示数据（统计/图表——窗口无感）。
- 窗口期的 UI 策略：收到失效事件到数据到达之间「标记数据可能过期」（stale 标识——比展示旧数据诚实）；关键操作（基于该数据的提交）前置校验（提交时服务端最终校验——窗口期的兜底）。
- 追问钩子：为什么「提交时服务端校验」是窗口期的最后防线？——前端一致性窗口不可消除（事件传播有延迟），但「提交时刻」服务端校验把窗口期风险拦在数据变更之前——最终一致性靠服务端兜底是分布式的通用结论。

```ts
// 窗口期策略：stale 标记 + 提交前校验
bus.subscribe('order.updated', e => {
  qc.invalidateQueries({ queryKey: ['order', 'detail', e.id] });
  markStale(e.id);                                // UI 标注「数据更新中」
});
async function submitAgainst(orderId) {
  await serverValidate(orderId);                  // 提交前服务端校验（防窗口期旧数据）
  return submit(orderId);
}
```
