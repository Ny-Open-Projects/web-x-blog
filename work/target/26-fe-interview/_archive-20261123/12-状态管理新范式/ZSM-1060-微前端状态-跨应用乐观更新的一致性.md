## 1060：跨应用乐观更新（A 乐观改的数据 B 正在展示）

**答**：
- 场景：A 应用乐观修改订单状态（立即更新自己的缓存），B 应用正展示同一订单的列表（B 的缓存还是旧值——A 乐观成功前 B 看到的是过期数据，乐观失败 A 回滚 B 无感知）。
- 治理：A 的乐观更新分两阶段广播——「optimistic.applied」（通知 B：数据可能已变——B 标记 stale）与「confirmed/rolledback」（终态通知——B 失效或按新值更新）；B 的列表展示 stale 标识（诚实）。
- 简化权衡：若 B 展示的容忍度高（列表最终一致即可）——只在「终态」广播（confirmed/rolledback），B 失效即可，不做 stale 中间态——按业务容忍度选复杂度。
- 追问钩子：为什么跨应用乐观更新的复杂度比单应用高一个量级？——单应用乐观更新的快照/回滚在同一缓存内闭环；跨应用后「乐观值」要传播给无法回滚的第三方（B 无法回滚 A 的乐观值）——所以跨应用只在「确认后」传播（乐观态不出应用边界）。

```ts
// A：乐观更新两阶段广播
onMutate: () => { /* 本地乐观 */ bus.publish('order.optimistic', { id }); },
onSuccess: d => bus.publish('order.confirmed', { id, data: d }),
onError: () => { rollback(); bus.publish('order.rolledback', { id }); },
// B：只订阅终态（stale 中间态按容忍度可选）
bus.subscribe('order.confirmed', e => qc.invalidateQueries(...));
```
