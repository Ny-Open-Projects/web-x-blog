## ZSM-692：富文本编辑器的状态架构：内容模型、选区、历史三层分离

**答**：
- 编辑器状态三层的铁律：**内容模型**（文档树/JSON，数据的权威）、**选区**（anchor/focus 位置，交互态，不进内容模型）、**历史栈**（undo/redo，内容模型的差量序列）。混层的后果：把选区塞进内容状态——undo 恢复了选区却没恢复内容（或反之），产生「光标乱跳」类 bug。
- 内容模型的更新纪律：所有变更经 **transaction**（一次输入 = 一个事务 = 内容 diff + 历史入栈 + 一次重渲）。打字高频——事务合并策略（同段落连续字符合并为一个 undo 单元，停顿 500ms 断开）与 ZSM-531 的命令栈合并一致。
- 选区的三态处理：受控选区（React 状态驱动 DOM selection，会破坏 IME 输入）vs 非受控（DOM 自己管理，store 只在需要时读取）——**中文 IME 输入期间绝不碰 DOM selection**，这是中文编辑器 headless 库（Slate/ProseMirror）处理组合事件的核心纪律。
- 外部变更（协同）与本地编辑的融合：远端 op 应用时本地未提交事务先行 flush，选区按「插入点补偿」平移（远端在光标前插入 N 字符，选区 offset += N）。
- 追问钩子：为什么编辑器状态不适合直接放 Zustand/Jotai——选区与 IME 的时序敏感、事务合并、DOM 双向绑定都是特化需求，编辑器库内部自成状态系统，外部 store 只镜像「需要跨组件展示的投影」（如字数、协作光标列表）。

```javascript
// 三层分离的架构骨架
class EditorState {
  #content = []        // 内容模型：[{ type: 'p', text }]
  #history = []        // 历史栈：事务序列
  #redoStack = []
  #mergeWindow = 500
  #lastTxAt = 0

  // 事务：内容变更唯一入口
  apply(tx, { mergeable = false } = {}) {
    const prev = structuredClone(this.#content)
    const next = tx(this.#content)
    const now = Date.now()
    // 合并策略：同段连续输入合并为一条历史
    const mergeWith = mergeable && now - this.#lastTxAt < this.#mergeWindow
    if (mergeWith && this.#history.length) {
      this.#history.at(-1).redo = next          // 替换最后事务的终点
    } else {
      this.#history.push({ redo: next, undo: prev })
    }
    this.#lastTxAt = now
    this.#redoStack = []                        // 新事务清空 redo
    this.#content = next
    this.notify()
  }

  undo() {
    const tx = this.#history.pop()
    if (!tx) return
    this.#redoStack.push({ redo: this.#content, undo: tx.undo })
    this.#content = tx.undo
    this.notify()
  }

  // 投影：跨组件消费（字数等）
  get wordCount() { return this.#content.reduce((a, b) => a + b.text.length, 0) }

  // 选区独立管理（不进内容模型）
  selection = { anchor: 0, focus: 0 }           // 编辑器内部维护，外部只读投影
}
```
