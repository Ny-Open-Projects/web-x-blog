## ZSM-125：缓存失效策略怎么设计？失效（invalidate）和直接写缓存（setQueryData/setCache）怎么选？
**答**：
- 原则：写操作后，能精确算出结果就写缓存（省一次请求），算不精确就失效（让缓存自己重取）——失效是安全默认，写缓存是性能优化。
- 失效粒度三级：精确 key（`invalidateQueries({ queryKey: ['goods', id] })`）、前缀批量（`['goods']` 失效整个商品域）、全库 `queryClient.invalidateQueries()`（退出登录/切换租户时用）。
- 写缓存的前提：mutation 响应携带完整实体且与列表项结构一致；部分字段响应（如只返回 status）必须失效，否则新旧字段混合出脏数据。
- 策略要成文：团队约定「 mutation 响应约定 + 失效清单」，失效清单跟 key 工厂放一起，改 key 时一并检查。

```javascript
const qc = useQueryClient()

// 场景 1：mutation 返回完整实体 → 精确写缓存 + 不重取
const { mutate: updateGoods } = useMutation({
  mutationFn: api.updateGoods,
  onSuccess: (updated) => {
    qc.setQueryData(['goods', updated.id], updated)
  },
})

// 场景 2：mutation 只改了统计口径 → 前缀批量失效
const { mutate: reviewGoods } = useMutation({
  mutationFn: api.reviewGoods,
  onSuccess: (_, goodsId) => {
    qc.invalidateQueries({ queryKey: ['goods', goodsId] })  // 详情
    qc.invalidateQueries({ queryKey: ['goods-list'] })      // 列表统计
  },
})

// 场景 3：身份切换 → 全库失效 + 清理
export function onSwitchTenant() {
  qc.clear()                                   // 直接清空最干净
}
```
