## SCN-270：地图与 LBS 场景的前端工程怎么总收束？

**答**:
- 全景五域：性能（261 首屏/262 海量点/269 自定义图层——canvas/WebGL 替代 DOM marker 是核心分水岭）、定位（263 围栏/265 漂移——采集质量分级+去抖确认）、交互（266 列表联动/267 路线导航/268 唤起 App）、数据（坐标系统一/空间索引/二进制传输）。
- 核心分水岭：DOM marker（交互性好，上限 ~500）vs Canvas/WebGL（性能好，万级以上）——按 marker 数量与交互需求分层使用，交互 marker 少量 DOM、展示 marker 海量 canvas。
- 定位工程哲学：GPS 数据天生不可信（漂移/精度/频率限制），前端的职责是"采集质量分级+滤波平滑+节流去抖"，业务裁决交服务端多源融合——前端不做业务级位置判断的最终裁决。
- 收束心法：地图场景的性能本质是"投影计算与绘制的批量化"——把 DOM 操作换成 canvas 批绘、把实时计算换成预聚合、把全量换成视口裁剪；坐标系统一是所有功能的隐形地基（GCJ-02/WGS-84 混用是最高频事故）。

```text
LBS 全景：
性能：首屏预取 SDK / 海量点 canvas+聚合 /
  自定义图层 WebGL / 视口裁剪
定位：围栏去抖确认 / 漂移滤波分级 /
  业务裁决在服务端
交互：列表双向联动防循环 / 导航跟随 /
  Scheme 唤起+web 兜底
数据：坐标系统一转换层 / 空间索引 /
  二进制扁平传输。
分水岭：>500 marker → canvas 批绘。
```
