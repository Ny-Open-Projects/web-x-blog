## RBL-920：综合深水：长列表数据管道——游标编码与增量加载

**答**:
- 长列表（万级商品/消息）的增量加载协议：1) **游标设计**（cursor = 最后一条的排序键 + id——不是页码：插入/删除时页码错位；cursor 编码要防篡改（HMAC 或不可猜测）与防越权（遍历导出数据——cursor 含范围上限））；2) 增量协议（`:after` 游标取增量 + 客户端合并去重）；3) 客户端缓冲策略（可视区 ±N 页缓存 + 顶部新数据插入时的锚点保持 RBL-976 WCN 衔接）。
- 构建器的配合：1) 列表虚拟化库的 chunk 归属（长列表页专用 RBL-597）；2) 「数据管道 mock 的分页一致性」（RBL-874 哲学：mock 必须实现真实游标语义——游标逻辑 bug 在 mock 下测不出 = 联调假象）；3) 协议 schema 的类型共享（游标结构 client/server 单源 RBL-741）。
- 游标的边界语义：首屏（无游标）/ 到尾（hasMore=false + endCursor=null）/ 中间插入的新数据（新增项的 cursor 在旧游标之前——增量协议要处理「回头补」）。
- 防遍历导出：游标加密签名 + 请求频率限制——「cursor 可枚举」是数据爬取的入口（页码 API 的 page=N 是公开邀请）。
- 追问钩子：为什么「游标比页码」在数据变更场景是必要的？——页码锚定「位置」（第 3 页），数据增删后位置漂移（看到重复/跳过）；游标锚定「实体」（这条之后）——增量语义稳定；代价是无法跳页（交互上需要跳页的场景用页码 + 快照区间：分页快照一致性）——「锚定实体 vs 锚定位置」是数据一致性优先场景的选择依据。

```javascript
// 游标编码（签名 + 防篡改）
import { createHmac } from 'crypto';
function encodeCursor(item, { secret }) {
  const payload = Buffer.from(JSON.stringify({ id: item.id, sort: item.sortKey })).toString('base64url');
  const sig = createHmac('sha256', secret).update(payload).digest('base64url').slice(0, 16);
  return `${payload}.${sig}`;
}
function decodeCursor(cursor, { secret }) {
  const [payload, sig] = cursor.split('.');
  if (createHmac('sha256', secret).update(payload).digest('base64url').slice(0, 16) !== sig)
    throw new Error('cursor 签名无效——防篡改');         // 伪造/遍历防护
  return JSON.parse(Buffer.from(payload, 'base64url').toString());
}
// 查询：WHERE (sort, id) > (cursor.sort, cursor.id) ORDER BY sort, id LIMIT n
```
