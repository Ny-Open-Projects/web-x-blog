## RBL-743：样式方案的构建期处理：CSS Modules / vanilla-extract / Tailwind 的管线差异

**答**:
- 三类方案的构建形态：1) **CSS Modules**（构建期改写类名 + 生成映射，运行时零成本——纯构建期方案）；2) **vanilla-extract/linaria**（「CSS-in-TS 编译期提取」：TS 文件编译成 CSS 文件 + 类名导出，构建管线要处理双产物与类型导出）；3) **Tailwind/UnoCSS**（扫描提取原子类，RBL-630）。差异本质是「类名的产生时机」：静态字符串 / 编译期表达式 / 扫描推断。
- 构建器的集成点差异：CSS Modules 需要「类名映射导出」（`styles.foo` 访问 → 映射后的 scoped 名）；vanilla-extract 需要「双 pass」（先跑 TS 编译提取 CSS，再注入产物）；Tailwind 需要「内容收集与失效」（类名集合变化触发 CSS 重生成）。
- sourcemap 与类名映射：scoped 类名（`_foo_1a2b3`）的调试体验靠 sourcemap（映射回源类名）+ 映射表导出（e2e/测试用 data-testid 替代类名选择器——类名不稳定是测试反模式）。
- 顺序敏感问题（RBL-628）：三方案都受 CSS 顺序影响，但 CSS Modules 的模块顺序由 import 顺序决定——构建器保证「import 图序 = CSS 注入序」；混合使用三方案时的顺序冲突（Tailwind preflight 与组件样式）需要显式 layer 声明（@layer）。
- 追问钩子：为什么 vanilla-extract 式方案的构建成本高？——它把 CSS 写进 TS，需要「真实类型检查/编译才能提取」，构建管线多一整轮 TS 编译（每主题/每文件）；换来的是「类型安全主题 + 死代码自动剔除（未引用的样式不产出）」——成本收益都是编译期的。

```javascript
// CSS Modules 的构建处理
function transformCssModule(code, id) {
  const classes = extractSelectors(code);                // .foo -> foo
  const mapping = Object.fromEntries(classes.map(c => [c, scopedName(c, id)]));
  const scoped = rewriteSelectors(code, mapping);        // .foo -> ._foo_1a2b3
  return {
    css: scoped,
    js: `export default ${JSON.stringify(mapping)};`,    // styles.foo 访问映射
    map: generateMap(code, scoped),
  };
}
// vanilla-extract 的双 pass 集成（构建器侧）
// pass1: compile .css.ts -> css + exports（构建器 transform 钩子先跑）
// pass2: CSS 进常规样式管线（RBL-628 顺序控制），JS 导出类名映射
```
