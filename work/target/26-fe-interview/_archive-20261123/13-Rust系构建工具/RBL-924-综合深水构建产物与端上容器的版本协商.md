## RBL-924：综合深水：端容器版本协商——WebView 基线的兼容层

**答**:
- 产物跑在「不可控的端容器」里（用户 App 版本参差）：1) **容器能力协商**（容器注入 bridgeInfo：版本/支持的 JSBridge 方法集/内核版本——产物按能力矩阵启用特性 RBL-884）；2) 兼容层策略（新特性 = 能力检测 + 降级路径——降级链按「容器版本 × 浏览器能力」二维判定）；3) 容器版本的灰度现实（用户 6 个月才完成升级——产物要同时支持 N 个容器版本 6 个月）。
- 构建器的配合：1) 能力矩阵作为构建输入（声明「目标容器版本集合」→ 影响语法 target/polyfill/bundle 拆分——RBL-745 平台矩阵的容器版）；2) 容器专项测试矩阵（CI 跑 min/max 支持版本的 WebView——中间版本抽样）；3) 能力检测的构建期生成（RBL-751 能力清单的容器扩展：bridge 方法级检测）。
- 版本协商的协议：产物声明「要求的最小容器能力」→ 容器声明「提供的」→ 协商结果决定渲染模式（如新渲染管线 vs 降级）；协商失败的最小可用路径（核心功能不依赖协商成功）。
- 长尾成本的治理：容器版本长尾让「降级路径」代码常驻——预算化（降级层体积预算）+ 退役节奏（容器版本覆盖率 > 99% 后移除支持——版本退役声明与 RBL-768 退役清单同构）。
- 追问钩子：为什么「容器版本长尾」决定了产物的架构风格？——Web 的 evergreen 浏览器假设在容器场景失效（App 壳的 WebView 内核跟随用户升级节奏，慢 6-12 个月）；产物必须「能力检测 + 降级」而不是「假设最新」——这影响从语法 target 到状态管理的所有选型（不用最新 API 的豪华特性/降级层常驻）；「运行环境的可控性」是前端架构选型的第一变量，比框架流行度重要。

```javascript
// 容器能力协商
const REQUIRED_CAPS = { 'app.pay': '8.0', 'app.share': '7.2', newRenderer: '9.0' };
function negotiate(containerInfo = {}) {
  const caps = containerInfo.bridgeMethods ?? [];
  const appVer = containerInfo.appVersion ?? '0.0.0';
  const missing = Object.entries(REQUIRED_CAPS)
    .filter(([m, v]) => !caps.includes(m) || ltVer(appVer, v));
  return {
    mode: missing.some(([m]) => m === 'newRenderer') ? 'legacy' : 'modern',
    degraded: missing.map(([m]) => m),                 // 降级方法清单
    minimalPath: true,                                 // 核心功能不依赖协商成功
  };
}
const ltVer = (a, b) => { const pa = a.split('.'), pb = b.split('.');
  return pa.some((x, i) => +x < +(pb[i] ?? 0)); };
// 容器版本退役
function retireContainerVersion(version, coverage) {
  if (coverage > 0.99) return { action: 'retire', note: '降级层移除（RBL-768 退役清单）' };
  return { action: 'keep', coverage };
}
```
