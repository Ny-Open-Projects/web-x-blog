## RBL-773：产物证据链：构建到部署的可追溯（attestation 与供应链合规）

**答**:
- 供应链合规（SLSA 框架）的核心诉求：「这个产物是谁、在哪、用什么代码构建的」全程可验证——证据链（attestation）：每次构建生成签名声明（构建者：CI 系统；源：commit SHA；输入：lockfile hash；输出：产物 hash 列表；审计：安全扫描结果），部署层验签后才接受。
- 工程价值：1) 事故溯源（线上 bug → 产物 hash → 构建记录 → commit + 构建环境，分钟级定位）；2) 信任降级防护（产物被篡改/非 CI 构建的产物无法发布）；3) 审计合规（金融类需求：证明发布内容 = 评审内容）。
- 构建器的角色：生成 attestation 的输入（完整 manifest + 构建环境快照——工具版本/OS/依赖闭包 hash）；「可复现构建」（RBL-543 确定性）让证据链可独立验证（重构建 hash 一致 = 证据可信）。
- 证据链的存储：与产物同发布（`.attestation.json` 签名文件）+ 独立归档（构建数据库——产物可删，证据保留合规期）。
- 追问钩子：为什么「可复现构建」是证据链的前提？——attestation 声称「用 commit X 构建」，验证者重构建一遍 hash 一致才证明声明为真；不可复现的构建（时间戳/路径混入产物）让证据链只能「信任声明」而不能「验证声明」——信任与验证的差距就是供应链攻击面。

```javascript
// 构建证据生成
async function emitAttestation({ manifest, ctx }) {
  const att = {
    buildType: 'https://slsa.dev/attestation/v1',
    builder: { id: `ci://${process.env.CI_RUNNER}` },
    invocation: { commit: ctx.commit, workflow: ctx.workflow,
      inputs: { lockHash: ctx.lockHash, configHash: ctx.configHash } },
    materials: [{ uri: 'git+ssh://repo', digest: { sha1: ctx.commit } }],
    output: { files: manifest.files.map(f => ({ name: f.name, hash: f.hash })) },
    audit: { criticalVulns: 0, auditedAt: ctx.auditAt },
    signed: await sign(canonicalJSON(att)),
  };
  fs.writeFileSync('.attestation.json', JSON.stringify(att));
}
// 部署层验证
function verifyAttestation(att, { verifySig, expectedCommit }) {
  if (!verifySig(att.signed, strip(att))) throw new Error('签名无效——拒绝发布');
  if (att.invocation.commit !== expectedCommit) throw new Error('commit 不匹配');
  return true;
}
```
