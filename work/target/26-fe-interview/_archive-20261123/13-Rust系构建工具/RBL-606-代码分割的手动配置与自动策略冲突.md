## RBL-606：手动 chunk 配置与自动分割的冲突治理：manualChunks 的边界条件

**答**：
- manualChunks（rollup/vite）允许按模块 id 把模块强制归组，但与自动分割共存时产生四类经典冲突：1) **动态 import 指向被手动合并的模块** → 该动态 import 失去懒加载价值（模块已在首屏 chunk）；2) 手动 chunk 包含 entry 模块 → 与 entry chunk 冲突；3) 循环依赖组被拆散 → 违反 SCC 不可分割（RBL-592）；4) 手动组引用自动 chunk 的模块 → 边界模糊。
- 治理策略：1) **构建期静态校验**——manualChunks 结果跑冲突检测（是否含 entry、是否拆散 SCC、是否吞掉动态边界），冲突给 warning + 修正建议；2) **优先级明确**——手动配置 > 动态边界 > 共享启发式，但 SCC 不可分割是硬约束（手动也不能违反），违反时合并处理并告警；3) 函数式 manualChunks 提供 `getModuleInfo`（引用计数/是否动态入口）让配置可感知上下文。
- 商业场景校准（延续 RBL-596）：「工具函数 + UI 库」手动组的风险是 UI 库改动频繁导致大 chunk 失效——手动组的成员要按「变更频率相近」原则分组（设计系统稳定、业务组件高频），这是把「缓存粒度」作为手动分组的第一性原则。
- Vite 的实践约束：manualChunks 里如果判断依据用了循环依赖中的模块，可能触发「Cannot access 'xxx' before initialization」——因为 chunk 初始化顺序被打乱；治理是禁止手动组跨越初始化顺序敏感边。
- 追问钩子：为什么大厂最终常常「手动配置只留 vendor 粗分组 + 信任自动分割」？——手动配置的维护成本随业务增长线性上升，且每次依赖升级都可能需要重新校准；自动策略 + 监控回归（产物体积 CI）比精细手动更可持续。

```javascript
// manualChunks 冲突静态校验
function validateManual(manualResult, graph) {
  const warnings = [];
  for (const [chunkName, mods] of manualResult) {
    if (mods.some(m => graph.entries.has(m)))
      warnings.push({ chunk: chunkName, issue: 'contains-entry', fix: `entry ${mods.filter(m => graph.entries.has(m))} 应留在 entry chunk` });
    const scc = graph.sccOf(mods);                     // 模块所在 SCC
    const broken = scc.filter(c => c.length > 1 &&
      !c.every(m => mods.includes(m)) && c.some(m => mods.includes(m)));
    if (broken.length) warnings.push({ chunk: chunkName, issue: 'splits-scc', fix: '循环依赖组须整体同 chunk' });
    for (const m of mods)
      if (graph.dynamicEntries.has(m))
        warnings.push({ chunk: chunkName, issue: 'eats-dynamic-boundary', fix: `${m} 是动态入口，合并进 ${chunkName} 会失去懒加载` });
  }
  return warnings;
}
```
