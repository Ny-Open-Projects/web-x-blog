## RBL-616：依赖预构建的触发与失效判定：为什么 node_modules 要单独走 ESM 化

**答**：
- dev server 按需编译（unbundle 模式）对源码友好，但对 node_modules 是灾难：1) 依赖是 CJS 或多格式混合，浏览器无法直接 import；2) 一个依赖可能内部几百个小文件（lodash-es 数千模块），按需逐个请求会打爆网络瀑布；3) 解析开销每次请求都重付。所以 vite 类工具对裸导入做**预构建**（esbuild/rolldown 一次性 bundle 成单 ESM 文件缓存）。
- 触发时机：1) 首次发现新裸导入（dev server 运行中扫描 import）；2) 启动时按缓存目录存在性跳过。失效判定四要素：**lockfile hash**（依赖版本变化）、**配置 hash**（resolve alias/polyfill/define 变化）、构建器版本、显式 force 标志——lockfile hash 是主键，配置 hash 是次键（配置变了旧产物语义不成立）。
- 运行中发现新依赖的处理：dev server 响应里注入「re-optimize 通知」→ 页面 full-reload（vite 的 new dependencies optimized, reloading）；体验优化是**启动扫描**（静态分析入口的 import 闭包预判裸导入集合，把「运行中发现」变成「启动时已知」——扫描不到的动态 import 才会触发中途 reload）。
- 缓存目录的完整性校验：预构建产物目录里有 `_metadata.json`（hash + 依赖清单）——校验失败/缺失即重跑；多 dev server 并发（两个终端同时起）会产生写竞争——文件锁或原子目录 rename。
- 追问钩子：为什么预构建产物不参与主构建的增量缓存体系？——键域不同（裸导入集合 vs 模块图失效），且预构建是「输入=lockfile+配置」的独立任务；混合会让失效传播复杂化。隔离的代价是「源码 import 依赖的桥接层」（optimizeDeps 的入口 shim）。

```javascript
// 预构建失效判定
async function needsPrebuild(cacheDir, ctx) {
  const metaPath = `${cacheDir}/_metadata.json`;
  if (!fs.existsSync(metaPath)) return true;                       // 无缓存
  const meta = JSON.parse(fs.readFileSync(metaPath));
  const currentHash = await hashInputs(ctx);                       // lockfile+config+tool version
  return meta.hash !== currentHash;                                // 键不匹配 -> 重跑
}
async function hashInputs({ lockfile, config, toolVersion }) {
  return sha256(JSON.stringify({
    lock: hashFile(lockfile), cfg: stableStringify(config), tool: toolVersion }));
}

// 启动扫描：预判裸导入集合（把运行中发现变启动时已知）
function scanBareImports(entries) {
  const found = new Set();
  walk(entries, (mod) => {
    for (const imp of mod.imports) {
      if (!imp.source.startsWith('.') && !imp.source.startsWith('/')) {
        found.add(topLevelOf(imp.source));                         // 'react/jsx-runtime' -> 'react'
      }
    }
  });
  return found;                                                    // -> esbuild bundle 列表
}
```
