## RBL-956：综合深水：静默错误清单——18 种「不报错但错」的模式

**答**:
- 静默错误（构建全绿但线上错）的模式清单：1) 缓存污染（RBL-637）；2) 漏失效（RBL-636）；3) 摇树误删副作用（594）；4) 循环依赖顺序错（592）；5) chunk 双版本混用（888）；6) 半成品产物（583）；7) sourcemap 错配（795）；8) 幽灵依赖发布后崩（832）；9) mock 残留进生产（834）；10) env 整对象泄漏密钥（660）；11) 虚拟模块静默失效（612）；12) SSR 数据内联越权（804）；13) 迁移语义漂移未声明（649）；14) manualChunks 吞懒加载（606）；15) TLA 传染错序（747）；16) AI 幻觉依赖（942）；17) 灰度撕裂（916）；18) 离线闭包缺口（897）。
- 清单的使用：1) **review 时对照**（PR 触及的模式 → 检查对应防线是否开启）；2) 事故复盘归类（新事故 → 匹配已有模式 → 补防线；新模式 → 清单生长 RBL-899）；3) 面试的「失败模式轰炸」：面试官问「这个方案什么时候会静默错」——清单是你的弹药库。
- 静默错误的共同预防原则：**每个静默模式都有一个「把它变响」的手段**（断言/审计/校验/演练）——防线的价值函数就是「静默 → 显性」的转化率（RBL-899 哲学）。
- 清单的优先级：按「发生频率 × 修复成本」排序——缓存污染/漏失效/双版本混用是 Top3（高频且难定位）。
- 追问钩子：为什么「构建全绿」不是质量的证据而是「静默错误的风险面」？——构建器只能验证「它知道的契约」（语法/引用闭合），大量语义契约（副作用/顺序/版本配对）不在构建器视野；「全绿」给的安全感恰恰让团队跳过语义验证——所以成熟团队的 CI 里「构建通过」只是入口，语义审计才是主体（RBL-661 审计清单的存在理由）。

```javascript
// 静默错误注册表
const SILENT_MODES = [
  { id: 'cache-poison', rbl: 637, detect: '签名校验+抽样复算', freq: 'high' },
  { id: 'missed-invalidation', rbl: 636, detect: '产物源码 hash 对账', freq: 'high' },
  { id: 'dual-version', rbl: 888, detect: 'entry 闭包双版本审计', freq: 'high' },
  { id: 'side-effect-shake', rbl: 594, detect: '双模式语义 diff', freq: 'medium' },
  // ... 18 项
];
function reviewGuard(pr, enabledDefenses) {
  const risks = SILENT_MODES.filter(m => pr.touches(m) && !enabledDefenses.has(m.detect));
  return risks.map(r => `PR 触及 ${r.id} 但防线 ${r.detect} 未开启——静默风险`);
}
```
