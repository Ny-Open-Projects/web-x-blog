## RBL-785：构建报告的机器可读出口：stats.json 的 schema 演进与消费方治理

**答**:
- 构建报告（stats.json 类）是工具链的「总线」：体积分析工具/CI 门禁/监控平台/AI 助手都消费它——schema 设计责任重大：1) **版本化**（schemaVersion 字段 + 变更日志；消费方按版本适配）；2) 稳定字段 vs 实验字段分离（experimental. 前缀，不承诺兼容）；3) 冗余与完整性的平衡（产物清单是核心，构建计时/内存画像可开关——体积敏感的 CI 报告）。
- schema 的演进纪律：新增字段是 minor（消费方忽略未知字段——宽容读取原则：消费者不得因新字段崩溃）；语义变更走 major（字段改名/单位变化）；「单位显式化」（bytes vs KB 混用是 stats.json 生态的历史混乱源头）。
- 消费方治理：内部消费方注册表（谁在读 stats.json 的哪个字段）——字段废弃前的「消费方通知期」（deprecated 字段保留两个 minor + 构建时警告使用方）；这与插件生态治理（RBL-651）同构。
- 生成成本：全量 stats 的序列化在大项目 10MB+——分级输出（summary：字段白名单小报告；full：完整）+ 流式写盘。
- 追问钩子：为什么「宽容读取 + 严格生成」是 stats.json 生态的黄金法则？——报告生成方是少数（构建器团队控制），消费方是多数（各工具/脚本）；严格生成保证数据可信，宽容读取保证演进不破坏下游——Postel 法则在工具链数据契约的应用。

```javascript
// stats.json 生成器（版本化 + 分级）
function emitStats(manifest, profile, { level = 'summary' } = {}) {
  const base = {
    schemaVersion: '2.1',
    generatedAt: new Date().toISOString(),
    outputs: manifest.files.map(f => ({
      name: f.name, role: f.role,
      bytes: f.size,                                    // 单位显式：bytes
      hash: f.hash,
    })),
  };
  if (level === 'full') {
    base.experimental = {
      phaseTimings: profile.phases,                     // 实验字段：不承诺兼容
      memory: profile.memoryCurve?.slice(-20),
    };
  }
  return JSON.stringify(base);
}
// 字段废弃流程
const DEPRECATED = { 'chunks[].size': { since: '2.0', removal: '3.0', use: 'outputs[].bytes' } };
function lintStatsConsumers(consumerCode) {
  for (const [field, meta] of Object.entries(DEPRECATED))
    if (consumerCode.includes(field))
      warn(`消费方使用已废弃字段 ${field}（${meta.since} 弃用，${meta.removal} 移除）——改用 ${meta.use}`);
}
```
