## RBL-783：内部构建器团队与开源上游的协作：fork 策略与 upstream-first

**答**:
- 用开源构建器（rolldown/rspack）的内部团队迟早遇到「需要上游没有的能力」——策略光谱：**插件解决**（90% 的需求，不碰上游代码）→ 配置/PR 上游（upstream-first：需求通用就提 PR，等合并）→ fork 维护（最后手段）。fork 的真实成本：每 upstream 版本 rebase 冲突 + 「fork 里的修复不在社区版本」的双头维护——大多数 fork 死于半年后无人敢动。
- upstream-first 的工程化：需求提案带「通用性论证」（不是我们特有的 hack）+ 内部等待窗口（PR 合并通常 2-8 周）；等待期用插件 shim 过渡（内部 fork 临时补丁 ≤100 行，上游合并后删除）——shim 的大小是「纪律指标」。
- fork 的生存规则（必须 fork 时）：fork 命名清晰（@internal/rolldown）、与 upstream 的 diff 每个版本重新评估（哪些补丁可以提上游）、退出策略（upstream 实现后回归社区版的迁移计划）——fork 是负债要定期「还债」。
- 上游跟踪机制：upstream release 的 watch + 兼容性自动测试（内部插件矩阵 × upstream canary）——提前发现 upstream breaking（比 stable 发布早几周知道）。
- 追问钩子：为什么「插件优先」不只是技术判断还是组织判断？——插件代码在仓库内（团队完全可控、review 正常进行）；fork 的补丁在外部代码库里（只少数人懂、知识孤岛化）；同样的功能，维护位置决定组织成本——内部工具团队的健康度可以用「fork 行数」粗略度量。

```javascript
// 上游兼容性自动跟踪
async function trackUpstream(repo, ourMatrix) {
  const releases = await gh.listReleases(repo, { per_page: 5 });
  for (const rel of releases.filter(r => r.prerelease)) {    // canary/beta 先测
    const results = await Promise.all(ourMatrix.map(p =>
      smokeTestWithCore(p, rel.tag)));
    const broken = results.filter(r => !r.ok);
    if (broken.length)
      notify(`上游 ${rel.tag} 破坏插件: ${broken.map(b => b.plugin)}——提前评估迁移`);
  }
}
// fork 负债度量
function forkDebt(fork) {
  return {
    patchCount: fork.diffFiles.length,
    loc: fork.diffLines,
    upstreamable: fork.diffFiles.filter(f => isGenericPatch(f)).length,  // 可提上游的比例
    ageVersions: fork.behindUpstreamVersions,
  };   // 上游可提比例低 + 落后版本多 = 高负债告警
}
```
