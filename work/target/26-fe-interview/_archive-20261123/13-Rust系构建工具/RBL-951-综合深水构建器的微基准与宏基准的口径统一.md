## RBL-951：综合深水：微基准与宏基准的口径统一——micro-benchmark 说谎的原因

**答**:
- 微基准（单函数计时）的说谎机制：1) **JIT 暖机**（V8 优化编译——第一次慢后续快，测的是哪个？）；2) **死代码消除**（微基准的循环结果没被消费——引擎把整个循环优化掉，测了个寂寞）；3) **内联与去优化**（微基准里被内联的函数在真实调用链不内联）；4) **GC 时机**（分配密集的微基准把 GC 成本摊到平均——真实场景 GC 集中爆发）。宏基准（真实构建任务）慢但真实——「口径统一」：微基准只用于「定位热点」，决策依据必须是宏基准（RBL-587 基准套件）。
- 工程上的正确用法：微基准 = 显微镜（函数级对比：`text.replace` vs 手写循环），宏基准 = 体检（构建总时长）——「显微镜找到的优化必须在体检上复验」——两基准脱节时（微基准快 30% 但宏基准没变化）说明优化无关紧要。
- 统计纪律（RBL-588 扩展）：宏基准的方差大（IO/GC），样本量要求更高；微基准的方差小但偏差大（系统性失真）——「方差小 ≠ 准确」是微基准最大的误导。
- 工具的诚实度：benchmark 库（benchmark.js/mitata）的自动暖机与统计——但「测什么」仍由人决定（测错对象统计再好也错）。
- 追问钩子：为什么「微基准快 30% 但宏基准没变化」的优化应该回滚？——宏基准不变 = 该函数不是真实负载的热点（占比 <1%）；合并的维护成本与行为风险（优化常引入微妙 bug）为纯负收益——「优化决策的依据是占比 × 收益」而占比只能从宏基准 profile 得出（RBL-587 火焰图）；微基准只能回答「这个函数能不能更快」，不能回答「值不值得」。

```javascript
// 微基准的正确姿势（mitata 风格）
const { bench, run } = mitata;
bench('replace', () => str.replace(/-/g, '_'))
  .bench('manual', () => { let s = ''; for (const c of str) s += c === '-' ? '_' : c; return s; });
await run();                                             // 微基准：仅定位
// 决策流程
async function optimizationGate(microDelta, macroProfile) {
  const share = macroProfile.functionShare(fnName);      // 函数在真实负载的占比
  const expectedGain = microDelta * share;               // 期望宏收益
  if (expectedGain < 0.02) return { verdict: 'reject', reason: `占比 ${share} 过低，宏收益 <2%` };
  return { verdict: 'macro-verify', note: '微基准通过——必须在宏基准复验后合并' };
}
```
