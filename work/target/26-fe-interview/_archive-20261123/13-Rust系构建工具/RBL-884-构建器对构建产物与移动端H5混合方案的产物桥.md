## RBL-884：场景题：移动端 H5 混合方案——JSBridge 协议的构建期契约

**答**:
- H5 页面嵌 App WebView 的 JSBridge：桥协议（方法名/参数 schema/回调格式）需要「构建期契约」：1) **协议声明文件**（bridge.d.ts 或 schema：方法集/参数类型/返回类型）——前端调用与 App 实现（双端）从同一声明生成；2) 能力检测（bridge 可用性随 App 版本变化——调用前检测方法存在，缺失降级到 H5 实现）；3) 版本协商（协议版本随 App 大版本演进——旧 H5 跑在新 App/新 H5 跑在旧 App 的兼容矩阵）。
- 构建器的配合：1) bridge 调用的静态校验（调用了未声明的方法 → 构建失败——协议是类型化契约不是字符串约定）；2) 桥层 chunk 隔离（bridge 封装独立模块，mock 桥（dev 浏览器运行）与真桥按环境切换 RBL-834）；3) App 版本能力的「能力清单」注入（App WebView 注入的 bridgeInfo 常量 → 前端运行时判定）。
- 调试契约：dev 环境的桥 mock（浏览器无 App——mock 实现 schema 全部方法返回 fixture）；「mock 与真桥的协议同构」（RBL-834 mock 哲学）。
- 追问钩子：为什么 JSBridge 要「类型化契约」而不是字符串约定？——桥调用跨进程（JS→Native），字符串写错 = 运行时静默失败（Native 收不到不报错或报错难追）；类型化让「App 改了方法名」在前端构建期即红——跨端契约的类型化与 GraphQL codegen（RBL-741）同构：契约单源、双端生成、漂移即构建失败。

```javascript
// 桥协议 schema（单源）
const BRIDGE_SCHEMA = {
  version: 3,
  methods: {
    'app.pay': { params: { orderId: 'string', amount: 'number' }, returns: 'PayResult', since: '8.0' },
    'app.share': { params: { title: 'string', url: 'string' }, returns: 'void', since: '7.2' },
  },
};
// 生成的前端调用（带能力检测）
function createBridge(injected, appVersion) {
  return new Proxy({}, {
    get(_, method) {
      const spec = BRIDGE_SCHEMA.methods[method];
      if (!spec) throw new Error(`未声明桥方法: ${method}`);       // 构建期可静态校验
      return async (params) => {
        if (versionLt(appVersion, spec.since))
          return h5Fallback(method, params);           // 能力缺失降级
        return injected.call(method, params);          // 真桥
      };
    },
  });
}
// 构建期校验：扫描 bridge.xxx() 调用 ⊆ schema.methods
```
