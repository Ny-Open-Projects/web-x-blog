## RBL-866：终局判断：构建器的可替换性设计——「下一个 rolldown」的迁移成本

**答**:
- 构建工具三年一换（gulp→webpack→vite→rolldown→?）——组织的设计目标是「换工具的成本可控」：1) **接口层隔离**（业务代码不直接依赖构建器 API：插件用抽象层/配置用语义层 RBL-848 preset）；2) manifest 统一 schema（RBL-826 总线）；3) 语义等价测试基建（迁移验证的最贵资产，跨工具复用 RBL-655）；4) 构建器专有能力的「替代清单」（每个 tool-specific 配置标注「换工具时怎么办」）。
- 可替换性的度量：「换工具的预估成本」= 配置翻译（preset 已收敛则小）+ 插件迁移（抽象层的等价物）+ 验证成本（测试基建现成）——度量随架构演进更新；「可替换性」不是为换而换，是「不被单一工具绑架」的谈判筹码（上游 fork 决策 RBL-783 的底气）。
- 反模式：业务代码 import 构建器运行时（import.meta.glob 是可接受的边界——有 Vite 外的标准语义；webpack require.context 是深度耦合）——「耦合面清单」是迁移成本的主要构成。
- 与 schema/preset 的协同：语义配置层让「翻译」变「映射」（RBL-666 翻译器的输入域收敛）；迁移平台（RBL-789）把一次性迁移经验沉淀——下一个工具出现时成本减半。
- 追问钩子：为什么「语义等价测试基建」是可替换性的最大资产？——换工具最大的风险是「行为变了但不知道」（静默错 RBL-583）；有跨工具的语义验证（行为测试集/语义 diff 工具），换工具从「赌博」变「验证流程」——工具可替换，验证基建长存，这正是 RBL-850「不变量投资」的实践形态。

```javascript
// 可替换性度量
function replaceabilityScore(repo) {
  return {
    configCoupling: repo.presetCoverage,               // preset 覆盖率（1 - 独立配置比例）
    pluginAbstraction: repo.plugins.filter(p => p.viaAbstraction).length / repo.plugins.length,
    deepCoupling: repo.codeRefsToToolRuntime.length,   // import 构建器运行时的业务代码数
    testInfra: repo.semanticTestCount,                 // 跨工具行为测试数
    score: 0,                                          // 综合分：抽象率高 + 深耦合低 + 测试多 = 高
  };
}
// 换工具成本预估
const estimateMigrationCost = (score) => ({
  configHours: (1 - score.configCoupling) * 8,
  pluginHours: (1 - score.pluginAbstraction) * repo.plugins.length * 2,
  verifyHours: score.testInfra > 50 ? 4 : 20,          // 测试基建现成则验证便宜
  total: '配置 + 插件 + 验证',
});
```
