## RBL-641：插件钩子的时序契约：resolveId/load/transform 的调用保证与幂等要求

**答**:
- rollup 式三钩子的时序契约是插件生态的宪法：**resolveId**（id 规范化，可多次调用、必须幂等）→ **load**（同 id 只调用一次直到成功，缓存后不再调用）→ **transform**（每模块一次，顺序按插件注册序）。契约的隐含要求：resolveId 与 load 必须纯（同输入同输出），transform 可以有状态但要声明（否则增量缓存失效）。
- 有状态 transform 与增量缓存的冲突：插件内部计数器/全局缓存会让「同输入不同输出」——构建器无法安全缓存其产物；契约要求 transform 的输出只依赖（id, code, options），有外部依赖的插件要显式声明 `cacheable: false`（退出缓存体系，接受性能代价）。
- 钩子返回值的协议丰富度：resolveId 返回 null（继续下一个插件）/ string（命中）/ `{ id, external }`；load/transform 返回 null（放行）/ code / `{ code, map }`——map 缺失时的语义是「继承上一个 map」（sourcemap 链不断裂的契约，见 RBL-526）。
- this 上下文：插件内 `this.warn/error/emitFile/addWatchFile`——emitFile 的产物要参与 hash 级联（RBL-598），addWatchFile 让虚拟逻辑感知文件系统变化——上下文 API 的完备度决定插件能力上限。
- 追问钩子：为什么 resolveId「可能被多次调用」？——构建器会以不同条件（相对/绝对/裸导入、不同 importer）试探解析；插件必须对重复调用幂等（无副作用累积），缓存失败结果的插件要按 (id, importer) 键缓存。

```javascript
// 钩子契约的调度器实现（简化）
async function runResolveHook(plugins, id, importer) {
  for (const p of plugins) {
    if (!p.resolveId) continue;
    const r = await p.resolveId.call(ctx(p), id, importer);
    if (r == null) continue;                             // null/undefined：下一个
    const resolved = typeof r === 'string' ? { id: r } : r;
    return resolved;                                     // { id, external? }
  }
  return null;                                           // 全部放行 -> 内置解析
}

async function runTransform(plugins, mod) {
  let code = mod.code, map = mod.map;
  for (const p of plugins) {
    if (!p.transform) continue;
    const r = await p.transform.call(ctx(p), code, mod.id);
    if (r == null) continue;
    const t = typeof r === 'string' ? { code: r } : r;
    code = t.code;
    map = t.map ?? map;                                  // 契约：缺 map 继承
  }
  return { code, map };
}
// 缓存协议：cacheable: false 的插件不进增量缓存键
```
