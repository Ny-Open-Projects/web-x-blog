## RBL-887：场景题：构建工具链的故障演练——三类基础设施故障的预案

**答**:
- 构建依赖的基础设施故障预案：1) **远程缓存宕机**（命中率归零——构建变慢但不失败：fail-open 设计 RBL-679；演练验证「无远程缓存时 CI 时长是否可接受」——依赖缓存活命的长任务要标 red）；2) **缓存污染**（错误产物扩散——预案：签名校验 RBL-638 + 按时间窗失效 + 逃生开关一键禁用缓存）；3) **registry 故障**（依赖安装失败——预案：镜像降级/离线缓存 pnpm store）；4) 工具链发布事故（RBL-722 回滚）。
- 演练的方法：定期「拆掉一根柱子」（关闭远程缓存/污染一条缓存/断网）看系统行为——预案写没写、fail-open 有没有生效、逃生开关好不好按——纸面预案与真实行为的差距只有在演练中暴露。
- 故障演练的度量：MTTR（演练中的恢复时间）——目标不是「不故障」而是「快速恢复」；演练报告的改进项进平台 backlog。
- 「优雅降级」的层级：远程缓存失效 → 本地缓存 → 全量构建（性能降级）；远程缓存污染 → 禁用缓存（正确性优先）；registry 故障 → 镜像/离线包——每层降级都有「明确的功能损失声明」而不是静默错误。
- 追问钩子：为什么「缓存污染」比「缓存宕机」危险一个量级？——宕机是 fail-open（慢但正确），污染是 fail-wrong（快但错误产物上线）——静默错误的代价（线上事故）远大于性能损失；所以污染的防线（签名/校验/失效）投入必须高于可用性防线——安全性与可用性的不对称优先级在 RBL-637 已论证。

```javascript
// 故障演练场景定义
const DRILLS = [
  { name: 'remote-cache-down', setup: () => disableRemoteCache(),
    assert: (r) => r.buildOk && r.durationMs < SLOW_BUDGET,
    note: 'fail-open：慢但必须成功' },
  { name: 'cache-poison', setup: () => injectPoisonedArtifact(),
    assert: (r) => r.detected && r.rejected,                // 签名校验必须拦住
    note: 'fail-wrong 不可接受' },
  { name: 'registry-down', setup: () => blockRegistry(),
    assert: (r) => r.installedFromMirror || r.offline },
];
async function runDrill(drill) {
  const undo = await drill.setup();
  const result = await timedBuild();
  const pass = drill.assert(result);
  report({ drill: drill.name, pass, mttr: result.durationMs });
  await undo();
}
```
