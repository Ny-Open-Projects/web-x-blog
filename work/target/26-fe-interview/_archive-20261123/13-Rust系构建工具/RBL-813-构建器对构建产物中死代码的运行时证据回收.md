## RBL-813：场景题：用运行时证据驱动 tree-shaking 精化——RUM 使用面反哺构建配置

**答**:
- Tree shaking 静态分析的局限：保守假设保留了很多「疑似副作用」模块——运行时证据（RUM：哪些模块/导出真的被执行过）可以反哺构建：生成「使用面白名单」，下一轮构建对「长期未执行」的模块做激进 shake（flag 控制 + 行为验证）。
- 数据链路：1) 产物注入「模块执行探针」（每个模块首次执行时上报 module id——成本极低一次性上报）；2) RUM 聚合使用面（模块级覆盖率：执行的模块 / 打包的模块）；3) 覆盖率报告 → 构建器诊断「疑似死代码」（未执行且静态分析无法判死的）；4) 激进 shake flag 试点（RBL-589 feature flag 流程：双模式对比 + 语义验证）。
- 判定的谨慎边界：「未执行」≠「死代码」——低频路径（错误处理/特定入口）在采样期没被触发是正常的；判定阈值（90 天 0 执行）+ 白名单（错误处理/动态入口闭包强制保留）——运行时证据是「证据链的一环」不是自动结论。
- 与产物归因（RBL-739）的联合：体积报告标注「运行时未执行」的模块——「可以省的体积」与「实际省的体积」两层报告，让优化决策有据。
- 追问钩子：为什么运行时证据不能直接当 shake 依据而要「双模式验证」？——RUM 采样有偏差（老版本产物/特定用户群/采样的时间窗），误判 = 线上功能缺失（静默错）；所以流程必须是「证据提出假设 → 双模式语义 diff → 灰度放量」——数据驱动但要经过验证管线，这与 A/B 的纪律同构。

```javascript
// 模块执行探针（产物注入）
const probe = `if(!window.__modExec){window.__modExec=new Set();
addEventListener('pagehide',()=>{navigator.sendBeacon('/rum/mods',[...window.__modExec].join(','))});}
window.__modExec.add('${moduleId}');`;

// 使用面报告 -> 激进 shake 候选
function deadCandidates(rum, manifest, { days = 90 } = {}) {
  const executed = new Set(rum.executedModules(days));
  return manifest.modules
    .filter(m => !executed.has(m.id))
    .filter(m => !m.isErrorPath && !m.inDynamicClosure)    // 白名单
    .map(m => ({ id: m.id, sizeKB: m.sizeKB, lastSeen: rum.lastSeen(m.id) }));
}
// 双模式验证（RBL-589）
const cmp = await compareModes({ experimental: { rumDrivenShake: true } });
if (cmp.semanticDiff.length) fail('激进 shake 语义差异——候选名单有误判');
```
