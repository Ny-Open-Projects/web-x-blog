## RBL-811：迁移复盘：构建时间数据的采集口径——为什么两份报告说构建「快了 8 倍」与「快了 2 倍」

**答**:
- 「快了 8 倍 vs 2 倍」的口径差异来源：1) **测什么**（冷构建 vs 热构建 vs dev 启动 vs HMR——各自差异量级完全不同：冷构建可能 8 倍、增量可能 2 倍）；2) 测的输入（基准仓库 vs 真实仓库——真实仓库常被缓存加成）；3) 计时边界（进程启动到产物落盘？含类型检查吗？含 npm install 吗？）；4) 统计量（单次最好 vs P50——最好成绩是幸存者偏差）。
- 口径规范化的要素：**定义一次测量协议**（计时起止点/输入集固定/预热次数/统计量/硬件环境）写入迁移报告模板；所有对外数字标注协议（「rolldown vs webpack，3 仓库基准套件，冷构建 P50，同机」）。
- 迁移汇报的诚实结构：收益分层呈现——确定性收益（冷构建加速，基准可复现）、概率收益（增量/HMR，与开发者行为相关）、间接收益（CI 并行度提升）——混成一个「快了 N 倍」的数字是营销不是工程。
- 采集自动化：CI 在构建任务中埋点（开始/结束时间戳 + 输入 hash + 缓存命中状态），数据进时序库——「口径一致」靠自动化采集而非人工掐表；本地开发时长则靠 opt-in 遥测（RBL-679）。
- 追问钩子：为什么「含类型检查与否」会让数字差出一倍？——类型检查是全局闭包任务（不受构建器并行化影响），webpack 项目常把 tsc 并入 build 而 rolldown 项目独立跑——把 tsc 从一侧剔除会让对比失真；口径协议必须显式声明各子任务归属，否则每个团队都能「合法」地算出对自己有利的数字。

```javascript
// 测量协议（显式定义）
const MEASURE_PROTOCOL = {
  scope: 'build only',                                   // 不含 install/typecheck
  timing: { start: 'config loaded', end: 'all outputs flushed' },
  warmup: 1, runs: 7, stat: 'p50',
  cache: 'cold',                                         // 冷构建口径
  hardware: 'ci-runner-m5.2xlarge',
};
function reportSpeedup(oldMs, newMs, protocol = MEASURE_PROTOCOL) {
  return {
    speedup: +(oldMs / newMs).toFixed(1),
    protocol: `${protocol.scope}/${protocol.cache}/${protocol.stat}/${protocol.hardware}`,
    note: '口径必须随数字一起出现——无口径的加速比是营销',
  };
}
```
