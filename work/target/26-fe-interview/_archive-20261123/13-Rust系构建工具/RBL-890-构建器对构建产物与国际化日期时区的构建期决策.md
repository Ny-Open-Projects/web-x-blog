## RBL-890：场景题：国际化日期时区的构建期决策——Intl vs 库

**答**:
- 日期时区方案的构建期决策：1) **Intl API 优先**（Intl.DateTimeFormat/Intl.RelativeTimeFormat 原生零体积——覆盖 80% 格式化需求；polyfill 只补老 Safari 的差异）；2) 库兜底（时区转换 Intl 的 TimeZone 数据不全/复杂日历——dayjs+plugin ~7KB 或 luxon 25KB，moment 全 locale 已淘汰 RBL-739）；3) 服务端/客户端时区一致性（UTC 存储 + 显式时区渲染——「服务器时区默认值」是国际化经典 bug）。
- 构建器的配合：1) date-fns/moment 的 locale 按需打包（RBL-739 归因驱动的按需改造）；2) Intl polyfill 的特性检测注入（RBL-703 usage 模式——目标矩阵缺什么补什么）；3) 「时间常量的构建期固化」（有效期判断的基准时间不能构建期固化——new Date() 在运行时；「构建时间戳注入」用于版本展示而非业务逻辑）。
- 时区的测试义务：跨时区测试矩阵（UTC+8 开发者在 UTC-5 用户的边界日问题——日期归属日界）——「本地时区开发看不见的 bug」需要 TZ 环境变量矩阵测试。
- 相对时间的语义：「3 分钟前」的服务端 vs 客户端计算（时钟漂移）——相对时间由客户端计算（Intl.RelativeTimeFormat）+ 服务端下发绝对时间戳。
- 追问钩子：为什么「构建时间戳注入业务逻辑」是反模式？——构建期固化的时间是「产物诞生时间」，不是「运行时间」；有效期判断（token 过期/活动截止）用构建时间 = 用户端逻辑全部错（产物部署晚一周全过期）；构建期常量只允许用于「版本标识」——「构建期 vs 运行时」的分界（RBL-760）在时间语义上的具体化。

```javascript
// 日期方案分层
function formatTime(date, locale, { tz } = {}) {
  return new Intl.DateTimeFormat(locale, { timeZone: tz, dateStyle: 'medium', timeStyle: 'short' })
    .format(date);                                       // Intl 优先零体积
}
// 库兜底：跨时区转换（Intl 无法直接转非本机时区的日历计算）
import { tz } from 'dayjs/plugin/timezone';
// 相对时间客户端计算
function relative(ts, locale) {
  const diff = Date.now() - ts;                          // 运行时 now（绝不构建期固化）
  const rtf = new Intl.RelativeTimeFormat(locale);
  const mins = Math.round(diff / 60000);
  return rtf.format(-mins, 'minute');
}
// TZ 矩阵测试（CI）
const TZ_MATRIX = ['UTC', 'America/New_York', 'Asia/Tokyo'];

```
