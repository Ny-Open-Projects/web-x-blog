## RBL-541：构建产物体积分析与瓶颈归因：从 bundle 报告到行动项

**答**：
- 体积分析的产出不是「图表」而是「行动项」——分析管线四步：
- 1) **组成拆解**：每 chunk 的模块构成（哪些库占多少 gzip KB）——source map 反解到模块（模块级体积归因）。
- 2) **重复检测**：多版本依赖共存（lodash@3 + lodash@4）、多 chunk 重复模块（chunk 分配不当）——重复是体积的第一杀手。
- 3) **可达性分析**：入口不可达模块为什么进来了（被引用但未使用 / 副作用强制保留 / 动态 import 预加载过度）——「为什么在产物里」比「有多大」更重要。
- 4) **行动项生成**：按「节省 KB/修复难度」排序——动态 import 拆分（大依赖）、重复去重（版本收敛）、tree-shaking 修复（副作用误标）。
- 体积的「预期 vs 实际」基线：体积预算（RBL-541 与 ZSM-616 同构）——超预算阻断 CI——「体积分析要制度化才有用」。
- 追问钩子：gzip 后体积 vs 原始体积的误导——分析报告必须双口径（raw/gzip），且 gzip 口径用实际压缩（不同内容压缩比差异大：JSON 高、已压缩 JS 低）。

```javascript
// 体积分析管线四步
const SIZE_ANALYSIS = {
  组成拆解: 'source map 反解到模块——模块级体积归因（gzip KB）',
  重复检测: ['多版本依赖共存（lodash@3+@4）', '多 chunk 重复模块（chunk 分配不当）——重复是第一杀手'],
  可达性: '入口不可达模块为什么进来（引用未用/副作用保留/动态预加载过度）——「为什么在」比「多大」重要',
  行动项: '按 节省KB/修复难度 排序：动态 import 拆分 > 版本收敛 > tree-shaking 修复',
  制度化: '体积预算进 CI（ZSM-616 同构）——超预算阻断',
  双口径: 'raw + gzip（实际压缩）——单口径误导',
}
```
