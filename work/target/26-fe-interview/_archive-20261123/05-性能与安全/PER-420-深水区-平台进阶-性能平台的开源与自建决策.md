## PER-420：性能平台自建 vs 开源的决策框架？

**答**:
- 分层决策：指标采集 SDK——**用开源**（web-vitals 官方实现，口径权威，PER-255 自己写只为学习/定制）；数据管道与存储——**用现成**（消息队列 + OLAP 是通用基建，不要自己造分位数引擎）；看板——**用现成**（Grafana 类）+ 薄自定义层；**平台特有逻辑自建**——指标注册中心（口径即代码）、告警路由到业务组织结构、诊断包生成、预算卡口与 CI 集成——这些与团队流程强耦合，开源没有现成答案。
- 决策三问：这层是"通用技术"还是"业务逻辑"？通用 → 买/用开源；维护成本我们能承受吗（开源的升级/定制负担）？数据主权与合规要求自建吗（PII 出境/私有化部署）？
- 混合架构（常见落点）：开源底座（SDK/管道/看板）+ 自建中台层（指标注册/告警路由/诊断/预算）+ 自研薄 SDK 层（封装 web-vitals 与自定义指标原语）。
- 评估误区：把"能自己写"当成"该自己写"——分位数引擎/存储这类通用件自建的维护成本远超预期；反之把"业务流程耦合层"寄希望于开源配置，会被迫削足适履。

```text
自建 vs 开源分层决策：
采集 SDK      → 用开源 web-vitals（口径权威），自研薄封装层
管道与存储    → 用现成（Kafka + ClickHouse），不造分位数引擎
看板          → Grafana 类 + 薄自定义
自建中台层    → 指标注册中心 / 告警路由 / 诊断包 / 预算卡口（业务流程耦合）
决策三问：通用技术还是业务逻辑？维护成本可承受？合规要求数据主权？
误区："能写"≠"该写"；通用件自建维护成本远超预期
```
