## PER-433：微前端下的 CSP 协调：主子应用 CSP 头如何共存？

**答**:
- 冲突机理：CSP 响应头只认**文档的 HTTP 头**（子应用 JS 注入的 meta CSP 会被忽略或叠加混乱）；iframe 方式子应用有独立文档可带自己的头；非 iframe（qiankun 类运行时加载）的子应用脚本跑在主文档里——必须全部满足主文档 CSP，子应用的白名单需求要合并进主策略。
- 协调方案：① 策略合并器——构建期收集所有子应用的资源清单（脚本域/nonce 需求），生成合并后的主策略（白名单并集，nonce 由主应用统一签发，子应用脚本注入时使用主应用的 nonce——加载器统一改写）；② iframe 模式则各文档独立 CSP，主子通过 postMessage 白名单通信（PER-358）；③ 子应用新增资源需求走申请流程（进合并器配置），CI 校验子应用构建产物与白名单一致（新域未申请即拦截）。
- 风险点：合并白名单 = 攻击面并集（最宽松的子应用决定整体强度）——所以申请流程与子应用审计（PER-316）必须严格；strict-dynamic 在合并策略中依然有效（主应用信任链覆盖子应用动态加载）。

```text
微前端 CSP 协调（运行时加载模式）：
主文档 CSP = 所有子应用需求合并（构建期策略合并器）
  nonce：主应用统一签发，子应用脚本注入时由加载器改写注入
  白名单：子应用资源域并集 —— 攻击面并集，靠申请流程与 CI 校验收敛
  strict-dynamic：主应用信任链覆盖子应用动态加载
iframe 模式：各文档独立 CSP + postMessage 白名单（PER-358）
CI 防线：子应用构建产物扫描，新域未申请 → 拦截发布
```
