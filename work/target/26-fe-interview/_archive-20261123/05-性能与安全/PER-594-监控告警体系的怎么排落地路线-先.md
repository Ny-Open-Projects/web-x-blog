## PER-594：监控告警体系的怎么排落地路线？先做什么后做什么才能最快产生价值？

**答**：
- 价值优先排序（不是大而全）：第一步 **错误采集 + 告警**（JS 错误/接口失败，这最能救命）；第二步 **核心性能指标 + 分位数看板**（Web Vitals + 接口耗时）；第三步 **trace 串联与慢样本下钻**；第四步 **告警治理**（聚合/抑制/值班 Runbook）；第五步 **平台化自助**（指标注册、自定义看板）。
- 反模式警告：一上来先做炫酷大屏和自研存储"——没有采集与告警的看板是装饰；自研存储除非有明确规模压力，否则先用现成（ClickHouse/ES）。
- 每一步的验收标准要量化：错误上线两周内抓到至少 1 个真 bug、告警误报率 < 30%、排障 MTTD 从小时降到分钟。
- 落地资源估算：前两步 1~2 人月（用开源 SDK 二次开发），后三步持续投入；靠先用开源攒信任，再逐步自研推进。

```javascript

const roadmap = {
  phase1: { do: '错误+失败采集、page 告警、值班群', accept: '两周内抓到 >=1 个真 bug', cost: '0.5 人月' },
  phase2: { do: 'Web Vitals + 接口分位数看板（开源 SDK）', accept: '误报率 < 30%', cost: '1 人月' },
  phase3: { do: 'traceparent 串联前后端 APM', accept: '慢样本可一键跳后端 trace', cost: '1 人月' },
  phase4: { do: '聚合/抑制/Runbook/演练', accept: 'MTTD < 5min，page/周 < 10', cost: '持续' },
  phase5: { do: '指标注册 + 自助看板 + 平台化', accept: '业务方可自助排障', cost: '长期' },
  antiPattern: '先做大屏与自研存储 —— 没有告警的看板是装饰',
};
console.log(roadmap.antiPattern);
```
