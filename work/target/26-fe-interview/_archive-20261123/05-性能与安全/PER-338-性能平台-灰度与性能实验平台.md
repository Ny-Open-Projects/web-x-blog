## PER-338：性能实验平台怎么设计？性能优化的 A/B 验证与灰度发布如何联动？

**答**：
- 为什么性能优化也要 A/B："优化后快了"必须验证对业务指标的正向作用（PER-249 的显著性问题）。性能实验的标准设计：实验组（优化版）/对照组（现状），同口径切片对比 p75 LCP/INP + 业务指标（转化/留存），双显著才算成功。
- 平台三能力：① 分流——SDK 端按实验配置分桶（会话级一致），上报带实验分组；② 指标对比——内置 bootstrap 显著性 + 长尾指标专项（p98 别被均值骗）；③ 灰度联动——实验成功后按流量比例逐步放量（5%→25%→100%），每档跑性能回归，异常自动回退。
- 性能实验特有坑：实验分组本身不能影响性能（分流 SDK 要轻）；样本量——性能指标方差大，需要的样本比业务实验多（提前算 MDE）；观察期——28 天滚动窗口口径下，结论至少跨 2 周。
- 组织机制：性能优化实验优先级排期、实验结论沉淀成"性能优化案例库"（哪个手段在哪个场景有效多少收益），避免每次重新发明。

```text
性能实验流程：
假设（虚拟列表让列表页 INP -30%）→ 实验设计（分流 5%/5%，样本量按 MDE=10% 计算）
  → SDK 分流（会话一致）→ 观察 14 天
  → 判定：INP p75 显著改善 AND 转化率不回退 → 放量 25% → 性能回归 → 100%
  → 沉淀案例库（手段/场景/收益数字）
反例（常见失败）：上线即全量，说"感觉快了"——无对照组无显著性，无法说服任何人
```
