## PER-588：接口成功率监控的口径怎么定？前端看到的失败和后端看到的失败为什么对不上？

**答**：
- 口径差异四来源：**前端视角包含网络层失败**（超时/断网/DNS 失败，请求根本没到后端）、**取消的请求**（用户切页 abort，后端可能已执行但前端算取消）、**重试放大**（前端重试使后端看到的请求量翻倍）、**时间窗口差**（前端按发起时间，后端按完成时间）。
- 健康口径：前端按业务结果分类——成功、可重试失败（超时/5xx）、不可重试失败（4xx 业务错）、取消（不计失败）；后端对齐时把前端超时但后端成功单独归为慢成功，它不是失败但是体验问题。
- 统计维度：按接口 + 设备档 + 网络分层，因为弱网下超时率天然高；聚合口成功率用加权，别把低 QPS 接口和高 QPS 接口直接平均。
- 对账机制：每周前端/后端成功率 diff 超过 0.5% 触发口径核对，防止两边各自漂移。

```javascript

const apiStatusSchema = {
  classify(res, err) {
    if (err?.name === 'AbortError') return 'cancelled';     // 不计失败
    if (err) return /timeout|network/i.test(err.name) ? 'retryable-net' : 'client-error';
    if (res.ok) return 'success';
    return res.status >= 500 ? 'retryable-5xx' : 'biz-error-4xx';
  },
  align: {
    slowSuccess: '前端超时但后端 200 -> 归慢成功，单独看不是失败',
    retryFactor: '前端重试倍数需上报，后端侧按请求量换算',
    reconcile: '周对账：前后端成功率 diff > 0.5% 触发口径核对',
  },
};
console.log(apiStatusSchema.align.slowSuccess);
```
