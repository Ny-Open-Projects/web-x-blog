## PER-623：第三方脚本对页面拥有什么能力？如何评估一个第三方 SDK 的安全风险？

**答**：
- 引入第三方 `<script src>` 等于交出全权：能读写 DOM（偷表单/篡改页面）、读 cookie（非 HttpOnly 部分）、发起同源请求带凭据、记录键盘事件——第三方被黑即等于本站被黑（典型事件：供应商被注入挖矿/窃卡脚本）。
- 评估清单：**来源可信度**（官方域名/CDN、有无 SRI 发布惯例）、**权限需求**（是否真的需要读全 DOM？还是只需自己的容器）、**更新机制**（锁定版本+ SRI 还是跟随 latest——跟随 latest 则 SRI 不可用，风险敞口不同）、**数据出境**（收集什么数据、传到哪、是否合规）、**供应商安全**（有无 SOC2/漏洞响应记录）。
- 收敛手段（从强到弱）：不引入 -> facade 懒加载（用户交互后才拉起）-> iframe 沙箱容器（第三方只在自己 origin 的 iframe 里跑，postMessage 桥接）-> CSP 限制其外联域名 -> SRI 锁版本。
- 决策依据："能塞进 iframe 的绝不放主文档"——地图/客服/广告/统计各有不同的可行收敛级别。

```javascript

const thirdPartyEval = {
  levels: [   // 从强到弱的收敛阶梯
    { l0: '不引入：功能自研或砍掉' },
    { l1: 'facade：占位图 + 用户点击后才加载真实 SDK' },
    { l2: 'iframe 沙箱：第三方跑在自家 origin 的 iframe，postMessage 桥接' },
    { l3: 'CSP 收敛：script-src 限定其域名，connect-src 限定上报域' },
    { l4: 'SRI 锁版本：integrity hash + 固定版本号' },
  ],
  checklist: ['来源域名是否官方', '是否需要主文档 DOM 权限', 'latest vs 锁版本',
    '收集数据与出境合规', '供应商漏洞响应记录'],
  rule: '能塞进 iframe 的绝不放主文档；必须主文档的用 CSP+SRI 双约束',
};
console.log(thirdPartyEval.rule);
```
