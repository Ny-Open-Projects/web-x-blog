## PER-430：像后端慢查询日志一样运营前端慢样本清单（Slow Log）？

**答**:
- 概念迁移：后端 DBA 靠慢查询日志治理，前端同样可以运营"慢日志"——自动汇聚的慢样本清单（慢交互/慢资源/慢会话），每周自动聚类、指派、跟踪修复，让性能治理有"清单驱动"的执行形态。
- 慢日志条目设计：{类型: 慢交互/慢资源/慢接口/慢会话, 场景指纹: 页面+元素+归因Top, 量级: 频次×影响用户数, 首次出现/持续时长, 关联版本, 状态: 新增/修复中/已修复/已忽略}。指纹聚类让"同一问题"聚合为一个条目而不是一千个样本。
- 运营节奏：周报自动生成（新增条目/修复关闭/超期条目）；条目生命周期管理——超 30 天未处理的自动升级到 owner lead；"已忽略"要写理由（防反复出现在清单里）。
- 与工单系统打通：慢日志条目一键转工单（带全部归因上下文 PER-390），修复 PR 关联条目，修复后自动验证关闭（指标回落确认）。

```text
前端 Slow Log（慢日志）运营模型：
条目 = 场景指纹聚类 { 慢交互/慢资源/慢接口/慢会话 }
字段：指纹（页面+元素+归因Top）/ 频次×影响用户 / 首次出现+持续 / 关联版本 / 状态
周报：新增 N 条、关闭 M 条、超期 K 条（>30 天升级 owner lead）
闭环：条目一键转工单（带诊断包）→ 修复 PR 关联 → 指标回落自动验证关闭
反模式：慢日志只有清单没有生命周期（变成积压坟场）；"已忽略"必须写理由
```
