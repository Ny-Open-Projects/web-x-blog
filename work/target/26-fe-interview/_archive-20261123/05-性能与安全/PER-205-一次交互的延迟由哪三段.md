## PER-205：一次交互的延迟由哪三段组成？各段怎么归因？

**答**：
- input delay：事件被浏览器接收后，因主线程被其他任务占用而排队等待的时间。归因方法看 Performance 面板时间轴上事件之前的" blocking task"，常见元凶是长任务、轮询上报、三方脚本。
- processing：事件 handler 及其同步调用链的执行时间。用 Chrome DevTools 的 Event Log / Performance 面板的 Event track 定位到具体 handler；新版可用 Long Animation Frames API 的 `scripts` 字段直接拿到慢脚本与函数归属。
- presentation delay：handler 结束后浏览器计算样式、布局、绘制到下一帧的时间。归因看 Rendering 面板的 Layout Shift / Paint Flashing，重点排查强制同步布局（读写交错触发 reflow）、大面积样式失效与复杂合成层。
- 优化顺序建议：先消 input delay 的长任务（收益最大、风险最小），再瘦身 processing（逻辑切片），最后压 presentation（渲染成本）。三段要分开归因，笼统说"慢"无法落地。

```javascript
// 用 LoAF（Long Animation Frames API）把"慢帧"直接归因到脚本，覆盖 presentation 段
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration < 50) continue;
    console.log(`慢帧 ${entry.duration}ms，阻塞总时长 ${entry.blockingDuration}ms`);
    for (const s of entry.scripts) {   // 归因到具体脚本与函数
      console.log(`  ${s.invoker}(${s.invokerType}) ${s.sourceURL}:${s.sourceLineNumber} 耗时 ${s.duration}ms`);
    }
  }
}).observe({ type: 'long-animation-frame', buffered: true });
// input delay 段看 event.startTime 与 handler 实际开始的差值；
// processing 段看 event.target 的 handler 执行（Event timing API 的 processingStart/End）。
```
