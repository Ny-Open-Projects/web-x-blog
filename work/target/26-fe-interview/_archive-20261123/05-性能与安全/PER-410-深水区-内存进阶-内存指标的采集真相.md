## PER-410：内存指标的采集真相：performance.memory 的量化误差与盲区？

**答**：
- performance.memory 的三个真相：① 量化误差——默认粒度约 1MB 桶（粗量化），小幅变化不可见，只能看趋势；② 不含 GPU 内存——Canvas/WebGL 位图、合成层内存不在 jsHeapSize 里（Chrome 任务管理器才有 GPU 列），Canvas 应用只看 jsHeap 会严重低估；③ Chrome-only——Safari/Firefox 无此 API，RUM 内存监控天然偏科。
- 更完整的口径组合：jsHeap（JS 对象）+ 手工记账（Canvas 位图 尺寸×4、缓存已知大小）+ estimate()（磁盘配额，非内存）+ 实验室任务管理器（Memory + GPU Memory 两列）——四源拼出接近真相的画像。
- RUM 落地的诚实姿态：内存指标标注"Chrome-only、趋势用途"，Safari 用户进"不可测"桶而不是假设正常；版本对比（同浏览器口径）仍有效。
- 误用警示：拿 jsHeapSize 绝对值当 SLO（不同页面业务不同无意义）、拿单次采样当状态（GC 抖动）——必须最小值近似 GC 后水位（PER-278）。

```text
内存口径组合（接近真相的四源）：
1. performance.memory.usedJSHeapSize  —— JS 堆，Chrome-only，1MB 量化，趋势用
2. 手工记账 —— Canvas/WebGL 位图（w×h×4）、已知缓存大小，跨浏览器可算
3. navigator.storage.estimate —— 磁盘配额（不是内存，别混）
4. 实验室 Chrome 任务管理器 —— Memory + GPU Memory 两列（GPU 盲区的补充）
RUM 诚实标注："内存 = Chrome-only 趋势指标"；Safari 用户标 unmeasured 不进对比
绝对值不做 SLO；GC 后最小值采样（PER-278）才能判定泄漏
```
