## PER-459：性能 bug 修完如何保证不再复发？

**答**:
- 三重锁：① 基准测试锁——把修复场景固化为可重复基准（固定交互脚本 + 固定环境），指标写进 budgets.json 卡口（PER-339/381 组件基准模式），回归即拦；② 单测锁——行为级防护（如"防抖必须能取消"的断言、切片函数的单片耗时上限断言、缓存必须有容量上限的类型约束），用单测把"正确用法"固化；③ 结构锁——lint 规则禁掉反模式（PER-432），API 设计上让错误用法写不出来（强制封装的虚拟列表/图片组件）。
- 锁的粒度选择：基准锁最准但最贵（CI 时间），单测锁最便宜；组合策略——高频复发场景上基准锁，其余单测/lint 锁。
- 闭环度量："复发率"指标——同类性能 bug 在同页面 30 天内再出现的比例；每复发一次 = 该场景的锁不够强，升级锁级别。
- 与案例库联动：修复 PR 模板强制勾选"已加何种锁"——修复不带锁不允许合入。

```text
性能修复三重锁：
① 基准锁：修复场景固化为基准 + budgets.json 卡口（贵而准，高频复发场景用）
② 单测锁：行为断言（防抖可取消/切片耗时上限/缓存容量约束）（便宜，普遍用）
③ 结构锁：lint 禁反模式 + API 封装让错误用法写不出来（PER-432/341）
度量：复发率（同类 bug 30 天再现）—— 每次复发升级锁级别
纪律：修复 PR 强制勾选"已加何种锁"，不带锁不合入
```
