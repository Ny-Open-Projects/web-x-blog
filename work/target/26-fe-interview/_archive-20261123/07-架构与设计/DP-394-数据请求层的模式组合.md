## DP-394：请求层模式组合

**答**：
- 请求层的模式全景：外观（统一入口 request()）、责任链（中间件管道）、策略（重试/缓存策略）、代理（in-flight 合并）、观察者（请求事件订阅）、备忘录（请求去重的缓存）
- 一个 request() 的分层：管道（auth→throttle→cache→retry→log）→ 策略注入（每接口配置）→ 代理合并 → 观察者上报
- 组合的正确顺序：缓存应在重试之前（重试不绕缓存——缓存命中不重试）、鉴权在最前（无 token 不发请求）、日志最后（记录最终结果）
- 配置的层级：全局默认（超时/重试）→ 接口覆盖（某接口特殊重试策略）→ 调用覆盖（单次特殊）
- 深水点：请求层的「可测试性」——管道各环节独立可测（中间件单测）+ 组合后集成测（管道顺序断言——auth 在 cache 前）

```javascript
const request = compose([
  withAuth(tokenStore),                              // 1. 鉴权
  withConcurrencyLimit(6),                           // 2. 并发池
  withCache(cacheStore),                             // 3. 缓存 (命中短路)
  withRetry({ attempts: 2 }),                        // 4. 重试
  withLog(metrics),                                  // 5. 埋点
])(fetchAdapter);
// 每个中间件独立单测; 管道顺序有集成断言
```
