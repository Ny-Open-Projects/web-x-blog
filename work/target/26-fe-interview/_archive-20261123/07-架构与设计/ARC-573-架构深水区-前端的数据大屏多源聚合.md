## ARC-573：数据大屏多源聚合
**答**:
- 场景：大屏指标来自多系统（订单库/支付平台/风控/物流）——前端聚合多源必然慢且口径难对齐。架构原则：聚合下沉（数据平台宽表/指标服务统一出数，前端只对接一个指标 API，ARC-381 指标字典的落地形态）。
- 指标服务设计：指标注册（名称/口径/来源/更新频率——口径单源防"两个屏数字不一样"事故）、查询 API（统一维度/时间粒度协议）、缓存与预计算（常用指标预聚合，分钟级刷新——实时性预期管理：标注"数据延迟 ≤ 5min"）。
- 前端聚合兜底：指标服务未覆盖的长尾需求临时前端聚合（多源并发 + 客户端合并）——标记为"临时口径"进治理清单（长期必须指标服务化）。
- 一致性对账：指标服务与源系统的定期对账（口径漂移告警——源表结构变更没同步是经典事故）。
- 展示层：同源同口径（大屏/工作台/报表同一指标 API——ARC-381/538 一致性原则）。
```javascript
// 指标服务统一查询
const metrics = await metricApi.query({
  names: ['gmv', 'order_count', 'pay_rate'],
  dims: { region: 'all' }, granularity: '5m',
  range: { last: '24h' }
});
// 口径单源：metricApi 内部查注册表（gmv = sum(pay_flow.amount, status=paid)）——大屏/报表同源
```
