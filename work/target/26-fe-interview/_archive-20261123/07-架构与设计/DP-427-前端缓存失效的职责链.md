## DP-427：缓存失效的职责链

**答**：
- 缓存失效的模式组合：观察者（失效事件广播——写操作通知所有缓存层）、责任链（多级缓存逐级失效：内存→SW→IDB→CDN）、策略（失效策略：全清/按 key 前缀/TTL 自然过期）
- 失效传播的完整性：写操作后的失效必须「穿透所有层」——只清内存层，持久层的旧数据会在下次读取时复活（最常见的缓存 bug）
- 失效的依赖关系：失效「订单列表」应同时失效「购物车数量」（派生数据——失效图）——失效的传递闭包
- 实战结构：CacheInvalidator（失效链：内存→SW→CDN 逐级调用 invalidate）+ invalidation graph（key → 派生 keys 映射）
- 深水点：失效的「竞态」——失效与在途写操作的竞态（写请求在途时失效 → 写完成后旧数据写入缓存）——失效版本号（写入时带版本，旧版本写入被拒）

```javascript
class CacheInvalidator {
  #layers = [];        // 责任链: [memCache, swCache, idbCache]
  #graph = new Map();  // key -> [派生keys]
  use(layer) { this.#layers.push(layer); return this; }
  invalidate(key, seen = new Set()) {                 // 失效传递闭包
    if (seen.has(key)) return;
    seen.add(key);
    for (const layer of this.#layers) layer.delete?.(key);
    for (const derived of this.#graph.get(key) ?? [])
      this.invalidate(derived, seen);                  // 递归失效派生数据
  }
  onWrite(key, version) {                              // 写版本仲裁
    this.#versions.set(key, version);
    this.invalidate(key);
  }
}
// 竞态防护: 写完成后缓存写入携带版本号, 旧版本写入丢弃
```

**答**（要点）：失效传播的完整性（穿透所有层）；失效图（派生数据递归失效）；失效与写操作的竞态（版本号仲裁）。
