## 1114：一次完整的注入事故复盘会长出哪些改进

**答**：
- 复盘产出按层分布：检测层（为什么没检出——补检测规则/变体）、架构层（为什么注入能造成危害——权限与内容信任联动缺口）、运营层（为什么响应慢——告警路由缺口）。三层都有改进才叫复盘完成，只补检测规则是常见不完整复盘。
- 时间线还原靠审计：事故复盘必须能精确到「哪条内容、在哪一跳进入上下文、触发了哪个工具」——审计能力不足的团队复盘只能靠猜。
- 改进项「可验证」：每条改进挂验收标准（回归用例/演练场景），下次演练验证；不挂验收的改进项三个月就烂尾。
- 追问钩子：怎么区分「根因」和「现象」？——连问五个为什么：检出失败是现象，根因常是「防线假设外部内容可信」这类架构决策；改现象（加规则）不改假设，事故会换姿势复发。

```md
## 事故复盘 INC-2026-041
时间线：外部工单(14:02) -> 检索入上下文 -> 触发 mail.send(14:07) -> 用户举报(15:30)
根因（5why）：工具未限制外发 <- 无信任联动 <- 假设「检索内容可信」
改进：[检测] 工单类内容强制消毒；[架构] external 上下文禁用外发工具；
     [运营] 外发类动作 P0 告警
验收：红队用例 rt-88/89 回归通过 + 混沌演练（注入工单）拦截
```
