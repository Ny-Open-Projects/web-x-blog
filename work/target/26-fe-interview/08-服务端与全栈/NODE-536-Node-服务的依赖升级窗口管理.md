## NODE-536：依赖升级窗口管理
**答**:
- 问题：大版本升级（框架/Node/DB 驱动）散落各团队自发进行——版本碎片 + 重复踩坑。窗口化管理：升级季（每半年一个窗口：统一版本目标 + 集中升级 + 统一验证——ARC-364/420 的组织化）。
- 升级季流程：窗口前调研（目标版本收益/风险/依赖兼容矩阵——平台团队预研）、分批升级（按服务重要性分批：工具服务先行→核心服务殿后——每批验证再下一批）、共享库先行（公共包先升级适配——下游服务跟随成本降低 NODE-514）、窗口收尾（未完成的债务登记——下一窗口处理，防无限拖）。
- 升级工具化：升级 PR 批量生成（Renovate 分组 NODE-409）、兼容性扫描（废弃 API 使用扫描——升级前清单）、统一回归（升级季的专项回归套件——升级验证标准化）。
- 风险控制：升级冻结交叉（升级季避开大促冻结——窗口规划）、单服务升级灰度（NODE-469 流程）、回滚预案（NODE-477 演练覆盖升级回滚）。
- 度量：版本一致率（季末统一版本覆盖率）、升级事故数、升级人力消耗（趋势优化——工具化收益）。
```yaml
# 升级季计划
upgrade-season: 2026-H2
target: { node: 22, framework: koa3 }
phases:
  - { batch: 'shared-libs + tools', when: 'W1-W2' }
  - { batch: 'edge services', when: 'W3-W4' }
  - { batch: 'core services', when: 'W5-W6' }
carryOver: '未完成登记为债务，H1 窗口处理'
```
