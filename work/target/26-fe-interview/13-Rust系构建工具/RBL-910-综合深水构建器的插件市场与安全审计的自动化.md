## RBL-910：综合深水：插件市场与供应链审计自动化——全程防线

**答**:
- 插件（及依赖）供应链的审计链：1) **准入**（静态扫描：恶意模式 eval/网络外传/混淆代码 + 许可证 + 维护者信誉——RBL-653 注册表）；2) **锁定**（lockfile + 完整性 hash + 范围限制：插件只能访问声明的钩子上下文）；3) **运行时**（超时/内存预算 RBL-557 + 行为审计：插件访问了声明外的 API → 诊断）；4) **持续**（月度重扫 + CVE 订阅——准入不是一次性）。
- 自动化的关键是「审计规则的数据化」：规则即代码（regex/AST 模式 + 严重度）——审计器输出结构化报告（命中规则/证据位置/处置建议）进 CI 门禁（RBL-656 三级分级模式）。
- 权限模型的现实妥协：JS 插件无法真正沙箱（同进程）——「权限模型」实际是「契约 + 审计」：声明能做什么 + 运行时验证声明（越界诊断）——与 App 权限模型的『声明式』哲学相同。
- 供应链攻击的典型向量与对策：typosquatting（名字相似包——内部 registry 白名单）；install 脚本攻击（postinstall——pnpm 默认禁脚本 + 白名单）；版本劫持（registry 缓存投毒——签名 RBL-717）。
- 追问钩子：为什么「postinstall 脚本」是供应链攻击的第一向量？——install 脚本在 npm install 时以用户权限执行任意代码（构建机器的 CI token/ssh key 全部暴露），且发生在「代码 review 之外」（没人 review node_modules）；pnpm 的 onlyBuiltDependencies 白名单把「任意执行」变成「声明+审批」——供应链防御的核心都是「把隐式信任变成显式声明」。

```javascript
// 插件审计规则（数据化）
const AUDIT_RULES = [
  { id: 'net-exfil', pattern: /fetch\s*\(\s*['"]https?:\/\//, severity: 'high',
    note: '插件内网络请求——检查是否外传数据' },
  { id: 'eval', pattern: /\beval\(|new Function\(/, severity: 'high' },
  { id: 'obfuscation', pattern: /_0x[a-f0-9]+/, severity: 'medium',
    note: '疑似混淆代码' },
  { id: 'fs-write', pattern: /fs\.writeFile|writeFileSync/, severity: 'medium',
    note: '声明外文件写入' },
];
async function auditPlugin(code, { allowNet = false } = {}) {
  const findings = [];
  for (const r of AUDIT_RULES) {
    if (r.id === 'net-exfil' && allowNet) continue;
    for (const m of code.matchAll(new RegExp(r.pattern.source, 'g')))
      findings.push({ rule: r.id, severity: r.severity, at: m.index, note: r.note });
  }
  const high = findings.filter(f => f.severity === 'high').length;
  return { findings, verdict: high ? 'reject' : findings.length ? 'review' : 'pass' };
}
```
