## RBL-940：综合深水：构建产物的最终交付物清单——一次发布的完整物料

**答**:
- 「构建完成」的完整物料清单（远不止 dist）：1) **产物**：代码 chunk + 静态资产 + html；2) **元数据**：manifest（产物清单+hash+角色 RBL-618）+ buildId + attestation（RBL-773）；3) **调试**：sourcemap（上传绑定 RBL-795）+ 转换快照（可选 RBL-645）；4) **部署配置**：缓存头策略（618）+ CSP hash 清单（894）+ import map（750）+ CDN 预推清单（693）；5) **合规**：SBOM（659）+ THIRD-PARTY-NOTICES（807）+ 审计报告（661）；6) **观测**：能力清单（751）+ 预算报告（739）+ trace profile（728）。
- 物料的「消费方矩阵」：每个物料谁消费（网关/监控/合规/运维）——物料的价值由消费方定义；「没有消费方的物料」要么砍掉（构建提速）要么补消费方（否则白生成）。
- 物料的版本绑定：全部物料共享 buildId（一次构建的物料集合原子关联 RBL-825 聚合视图）——「混版本的物料」（新产物配旧 sourcemap）是最常见的发布事故。
- 交付的完整性校验：物料清单的闭包断言（声明交付的物料都存在 + hash 一致——RBL-656 闭合校验的物料版）。
- 追问钩子：为什么「产物 = dist」的心智是危险的？——dist 只是六类物料之一；「部署成功但监控没反解/合规没留痕/预算没记录」 = 交付不完整（排查/合规/优化的能力全部丢失）——「构建的输出是一个系统而不是一个目录」，这也是平台化（RBL-893）与单仓脚本的本质差异。

```javascript
// 交付物料清单与完整性校验
const DELIVERABLES = {
  artifacts: { files: (m) => m.files, consumer: 'CDN/网关' },
  manifest: { file: 'manifest.json', consumer: '部署编排' },
  attestation: { file: '.attestation.json', consumer: '合规审计' },
  sourcemaps: { files: (m) => m.maps, consumer: '错误监控' },
  cspList: { file: 'csp.json', consumer: '网关' },
  sbom: { file: 'sbom.json', consumer: '安全扫描' },
  budgets: { file: 'budget-report.json', consumer: '性能治理' },
};
async function verifyDelivery(dir) {
  const problems = [];
  for (const [name, spec] of Object.entries(DELIVERABLES)) {
    const exists = spec.file ? await fsExists(`${dir}/${spec.file}`)
      : (await fsGlob(dir, spec.files)).length > 0;
    if (!exists) problems.push({ material: name, consumer: spec.consumer,
      detail: '交付物料缺失' });
  }
  return { problems, complete: problems.length === 0 };
}
```
