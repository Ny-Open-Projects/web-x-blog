## RBL-799：构建缓存的分层存储：内存/磁盘/远程的层级访问与淘汰策略

**答**:
- 构建缓存三层：内存（本次会话最快）、磁盘（跨会话，RBL-633）、远程（跨机器，RBL-637）——访问顺序 L1→L2→L3，命中即止；写入策略「write-through 到内存 + 异步刷盘 + 按需上传远程」——同步写全层会让热路径变慢。
- 每层的淘汰策略不同：内存 LRU（容量 = 单构建需要的峰值）；磁盘 LRU + 总量上限（如 2GB，防止缓存吃满开发者磁盘——DiskFull 的降级：禁用缓存继续构建）；远程按访问热度 + TTL（团队共享冷数据清理）。
- 层间一致性：磁盘条目的 version 戳（RBL-634）与远程共享——「远程返回的条目版本旧于磁盘」时以磁盘为准（本地更可信：本地有 watch 上下文）；版本冲突的仲裁规则要显式。
- 缓存键的层级差异：L1/L2 键含「会话上下文」（内存中未持久化的插件状态版本）；L3 键是纯内容指纹（跨机器可复现）——键的规范化（RBL-582）在 L3 更严格。
- 追问钩子：为什么「异步刷盘」而不是写穿磁盘？——transform 的产物在构建结束前还可能被后续 pass 修改（中间态）；写穿会造成无效 IO 与中间态污染；构建结束/模块最终化时统一刷盘（批次写）——「缓存写入的时机跟随产物稳定性」。

```javascript
class TieredCache {
  #l1 = new Map(); #l2; #l3;
  async get(key, validate) {
    if (this.#l1.has(key)) return this.#l1.get(key);
    const disk = await this.#l2.get(key);
    if (disk && validate?.(disk)) { this.#l1.set(key, disk.value); return disk.value; }
    const remote = await this.#l3?.get(key);
    if (remote) {
      // 仲裁：远程版本旧于磁盘则以磁盘为准
      if (!disk || remote.version >= disk.version) {
        this.#l1.set(key, remote.value);
        await this.#l2.set(key, remote);
        return remote.value;
      }
    }
    return null;
  }
  async put(key, value, version) {
    this.#l1.set(key, value);                              // 写穿内存
    this.#pending.add({ key, value, version });            // 异步刷盘
  }
  async flush() {                                          // 构建结束统一刷盘
    for (const e of this.#pending) await this.#l2.set(e.key, e);
    this.#pending.clear();
  }
}
```
