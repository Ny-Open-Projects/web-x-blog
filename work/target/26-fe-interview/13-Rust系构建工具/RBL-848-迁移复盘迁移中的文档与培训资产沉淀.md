## RBL-848：迁移复盘：培训资产沉淀——迁移知识的三层文档结构

**答**:
- 迁移知识的受众分层决定文档形态：1) **操作层**（仓库 owner 视角：怎么迁我的仓库——步骤化 checklist + 常见错 FAQ，10 分钟能上手）；2) **原理层**（构建团队视角：为什么这样设计——规则库的理由/工具的边界/架构决策 ADR）；3) **演进层**（接手者视角：工具怎么改——迁移平台的代码结构/测试策略/发布流程）。三层混写是文档没人读的主因（操作的人被原理淹没，维护的人找不到演进信息）。
- FAQ 的来源自动化：迁移支持群的问答 → 归类去重 → 自动沉淀 FAQ 候选（RBL-781 的已知问题库同构）——FAQ 是活文档，每次答疑都要有归档路径。
- checklist 的可校验化：操作文档的每一步尽量是「可执行校验」（命令 + 预期输出），而不是描述性文字——「跑 `pnpm build` 应产出 dist/manifest.json」比「构建成功后」可靠——文档步骤的可验证性决定新手成功率。
- 文档的时效治理：与代码同步门禁（RBL-590 文档即测试）——迁移文档里的命令要在 CI 中定期执行验证（文档腐化的机械防线）。
- 追问钩子：为什么「FAQ 自动沉淀」比「鼓励大家写文档」有效？——写文档的成本在「回忆与组织」，答疑已经在回答（信息已产生），沉淀只是「换个地方保存」——降低增量成本是文档体系可持续的关键；同理 checklist 可校验化是把「读文档验证」变成「跑命令验证」，执行成本更低。

```javascript
// 三层文档结构（目录约定）
const DOC_LAYOUT = {
  'playbook/': '操作层：per-repo checklist + FAQ（owner 读）',
  'adr/': '原理层：规则库理由 + 工具边界（构建团队读）',
  'platform/': '演进层：迁移平台代码结构 + 测试 + 发布（接手者读）',
};
// FAQ 沉淀流水线
function sedimentFAQ(supportThreads) {
  const candidates = supportThreads
    .filter(t => t.reactions > 2 || t.repeated >= 3)     // 高价值问题
    .map(t => ({ q: t.question, a: bestAnswer(t), tags: classify(t) }));
  dedupeBySimilarity(candidates);                        // 相似归并
  return candidates.map(c => `FAQ: ${c.q}\nA: ${c.a}`);  // 自动入 playbook/faq.md
}
// checklist 可校验化
const CHECKLIST = [
  { step: 'pnpm i', expect: 'exit 0' },
  { step: 'pnpm build', expect: 'dist/manifest.json 存在' },
  { step: 'node scripts/verify.mjs', expect: 'semantic-diff 为空' },
];
```
