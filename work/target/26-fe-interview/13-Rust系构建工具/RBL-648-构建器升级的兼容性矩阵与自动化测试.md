## RBL-648：构建器升级的兼容性矩阵：版本升级的回归测试自动化

**答**:
- 业务仓库升级构建器（webpack→rspack、rspack 小版本升级）的风险不是 API 变化而是**产物语义漂移**（chunk 划分变了/模块顺序变了/ polyfill 差异）——回归测试要对「语义级产物」断言而非文本 diff。
- 兼容性矩阵的三个维度：1) 配置兼容（旧配置在新版本的行为，未知字段是否告警）；2) 插件兼容（生态插件版本约束表，peerDependencies 边界）；3) 产物兼容（语义 diff：导出集合/依赖闭包/资源清单）——升级前跑「双版本对比」（旧版构建 vs 新版构建，RBL-585 的语义比较器）。
- 自动化升级验证流水线：1) 固定测试项目集（团队核心项目快照）；2) 双版本并行构建；3) 语义 diff 报告（哪些 chunk 划分变化、哪些模块移动）；4) 行为测试（产物在 puppeteer 里跑关键页面断言）；5) 体积/性能回归报告。全绿才允许合并升级 PR。
- 版本策略工程：构建器版本锁定在 lockfile（minor 也不自动升——构建器 minor 也可能改变产物），升级走「受控升级流程」（升级 PR + 语义 diff 评审 + 灰度仓库名单）；团队级「构建器版本看板」暴露版本碎片（十几个仓库十几个版本）——统一是维护性红利。
- 追问钩子：为什么「升级后产物完全一致」有时反而不对？——新版修复了旧版错误（如循环依赖顺序 bug），diff 是预期的行为修复；所以语义 diff 报告要区分「预期变化」（升级说明里声明）与「意外变化」——评审人对照 changelog 判定。

```javascript
// 双版本对比流水线
async function upgradeCheck({ project, oldVersion, newVersion }) {
  const oldOut = await build(project, { rolldown: oldVersion });
  const newOut = await build(project, { rolldown: newVersion });

  const report = {
    semanticDiff: diffSemantics(oldOut, newOut),         // 导出集合/chunk 划分/资源清单
    sizeDelta: newOut.totalSize - oldOut.totalSize,
    behavior: await smokeTest(newOut),                   // puppeteer 关键页面
    declared: parseChangelog(newVersion).declaredChanges, // changelog 声明的变化
  };
  const unexpected = report.semanticDiff.filter(d =>
    !report.declared.some(c => matches(c, d)));
  if (unexpected.length) fail(`升级引入未声明变化: ${unexpected.map(u => u.kind)}`);
  return report;
}
// 版本碎片看板（团队级）
const versionMap = await scanRepos('org/*', 'rolldown');
console.table(groupBy(versionMap, 'version'));           // 版本碎片可视化
```
