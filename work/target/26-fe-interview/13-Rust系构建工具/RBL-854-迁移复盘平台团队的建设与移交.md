## RBL-854：迁移复盘：平台团队的可持续性——单点风险识别与知识移交

**答**:
- 迁移后的最大组织风险：知识集中在 1-2 个「迁移专家」身上（专家离开 = 平台变成无人敢动的黑盒）——单点风险的度量：每个核心组件的「可维护者数 ≥ 2」与「文档覆盖度」；识别用「巴士因子」检查（≥2 人离岗系统是否停摆）。
- 移交的结构化：不是「拉个会讲讲」——1) 运维手册（值班 runbook：常见故障处置 RBL-831 预案卡）；2) 演进文档（RBL-848 三层文档的 platform 层）；3) 结对维护（新人至少共同处理 3 个工单才能独立值班）。
- 单点的工程解法：降低系统的「理解门槛」——迁移平台的模块边界清晰（每个检查器独立可测）、关键路径有注释与测试；「复杂度是知识单点的根源」——把精巧的 hack 换成平淡的实现（可维护性 > 聪明度）。
- 专家的退出节奏：渐进退出（主导 → 评审 → 顾问）而非立即抽身——每次值班轮换验证文档与团队的实际支撑力。
- 追问钩子：为什么「复杂度」与「知识单点」是因果关系？——精巧 hack（绕过限制的 200 行 patch）只有作者能改；平淡实现（显式配置/标准模式）任何人能改——知识单点不是「人不肯分享」造成的，是「代码不可分享」造成的；降低系统复杂度是知识转移的前置条件，文档只是必要不充分。

```javascript
// 巴士因子检查
function busFactor(components, maintainers) {
  const risks = [];
  for (const c of components) {
    const who = maintainers.filter(m => m.canMaintain(c));
    const doced = c.hasRunbook && c.tests > 0;
    if (who.length < 2 || !doced)
      risks.push({ component: c.name, busFactor: who.length, documented: doced,
        action: who.length < 2 ? '结对移交' : '补 runbook' });
  }
  return { risks, ok: risks.length === 0 };
}
```
