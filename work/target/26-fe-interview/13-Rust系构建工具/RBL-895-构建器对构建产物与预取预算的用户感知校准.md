## RBL-895：场景题：预取预算的用户感知校准——RUM 反推预取参数

**答**:
- 预取策略参数（RBL-769 的 budgetKB/hover 阈值）的校准不能拍脑袋：1) **hover 意图命中率**（hover 触发的预取中有多少变成真实导航——命中率高说明 hover 窗口合适；低说明阈值太灵敏浪费流量）；2) 空闲预取的浪费率（预取了但从未导航的占比——浪费率 > 50% 时收紧预算或去掉低频路由）；3) 带宽竞争观测（预取期间的交互请求延迟 vs 无预取基线——预取是否挤占了交互）。
- RUM 数据的采集点：预取开始/完成/是否用于导航（chunk 请求被 navigation 复用 = 命中）——「预取命中率」是核心指标（命中 = 省的导航等待，浪费 = 白付的字节）。
- 参数的自适应校准：浪费率高的路由降低预取优先级（移出空闲清单）；命中率高的路由提升（hover→立即）；网络状况分级（RBL-769 conn 判断的细化——4g 全量、3g 只 hover、2g 全关）。
- 校准的周期：参数不是常量——月度回顾（路由流行度变化/内容大小变化）调整；校准报告与 RBL-851 收益看板并列。
- 追问钩子：为什么「预取命中率」比「预取覆盖率」更适合做北极星？——覆盖率（多少路由被预取）鼓励多预取（覆盖 100% 但浪费 90%）；命中率衡量「预取的性价比」（每字节预取换来的导航加速概率）——指标定义决定优化方向，覆盖率会把系统推向「浪费最大化」；指标选择的反身性（RBL-881 劣化检测同样面临：选错桶会把治理引向歧途）。

```javascript
// 预取命中率统计与参数校准
function prefetchAnalytics(events, { wasteThreshold = 0.5 } = {}) {
  // events: { url, ts, type: 'prefetch'|'navigate', reused?: boolean }
  const prefetches = events.filter(e => e.type === 'prefetch');
  const navigations = new Set(events.filter(e => e.type === 'navigate').map(e => e.url));
  const hits = prefetches.filter(e => e.reused || navigations.has(e.url));
  const byRoute = groupBy(prefetches, e => routeOf(e.url));
  const report = {
    hitRate: +(hits.length / prefetches.length * 100).toFixed(1),
    wasteByRoute: Object.fromEntries(Object.entries(byRoute).map(([r, es]) =>
      [r, +((es.filter(e => !navigations.has(e.url)).length / es.length)).toFixed(2)])),
  };
  report.adjustments = Object.entries(report.wasteByRoute)
    .filter(([, w]) => w > wasteThreshold)
    .map(([r]) => ({ route: r, action: '移出空闲预取清单（浪费过高）' }));
  return report;
}
```
