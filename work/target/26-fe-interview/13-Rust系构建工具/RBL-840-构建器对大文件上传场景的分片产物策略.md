## RBL-840：场景题：大文件上传场景的产物策略——分片上传 SDK 的构建与体积预算

**答**:
- 上传场景（视频/大附件）的产物要点：1) **hash 计算的 Worker 化**（大文件秒级 hash——MD5/SHA 全量计算冻结主线程；worker chunk RBL-709 + 流式增量 hash）；2) 分片调度器（并发切片上传 + 失败重传 + 断点续传的 manifest）；3) 上传 SDK 的体积预算（常驻成本——上传是低频功能，SDK 懒加载，core 只留触发器）。
- 构建配合：hash worker 与上传调度是独立 chunk（按需动态 import）；polyfill 边界（File.slice/FileReader 在目标环境全覆盖——browserslist 校验）。
- 断点续传的产物层：上传 manifest（已传分片列表）存服务端 + localStorage 双份——构建器不管运行时逻辑，但要保证「多入口共享同一上传 SDK 单例」（chunk 去重 RBL-597——两个页面各自打包上传库 = 双份常驻）。
- 体积归因（RBL-739）驱动：上传 SDK 内常见「全量引入（axios+xlsx+md5 全家桶）」——归因报告揭示「上传功能 300KB 但只有 40KB 被 execute」——按需改造的依据。
- 追问钩子：为什么大文件 hash 必须「流式增量」而不是「读全量再算」？——2GB 文件读入内存 = 移动端直接 OOM；流式（slice 循环 + crypto.subtle.digest 分段拼接或 spark-md5 增量）内存恒定 O(chunk)；这也决定 hash 必须在 worker（主线程被分片读取循环卡死）——「流式 + worker」是大文件场景的固定组合。

```javascript
// 分片上传调度（Worker + 断点续传）
class Uploader {
  async upload(file, { chunkMB = 5, concurrency = 3 }) {
    const fileId = await hashWorker.md5(file);           // Worker 流式 hash（秒级）
    const done = await server.resume(fileId);            // 断点查询
    const chunks = sliceFile(file, chunkMB);
    const queue = chunks.filter((_, i) => !done.has(i));
    const pool = createScheduler({ concurrency });       // RBL-565
    for (const c of queue)
      pool.schedule(() => server.putChunk(fileId, c.i, c.blob), 5);
    await pool.run();
    return server.complete(fileId);                      // 合并触发
  }
}
// 构建配置：上传 SDK 懒加载 + 单例共享
const uploaderPlugin = {
  manualChunks: { uploader: ['src/lib/uploader/**'] },   // 独立 chunk（多入口共享）
};
// 产物审计：上传 SDK 不进首屏闭包
auditLayers({ core: { modules: entryClosure }, enhanced: { modules: ['uploader'] } },
  imports, { core: 200 });                               // RBL-725 预算门禁
```
