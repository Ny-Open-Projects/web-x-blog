## RBL-851：迁移复盘：迁移收益的长期追踪——一次性报告 vs 持续指标看板

**答**:
- 迁移报告的时效性问题：「迁移后构建快 3 倍」在半年后无人验证——收益是否守住（依赖膨胀会吃掉提速）需要持续指标：构建时长趋势/缓存命中率/产物体积趋势——看板化（按周聚合）让「收益流失」可见。
- 收益流失的典型模式：新依赖引入（体积涨）、构建配置腐化（特殊 alias 堆积）、缓存键变宽（命中率降）——每一个都有对应的看板指标与阈值告警（RBL-705 指标体系的延续）。
- 指标的「行动绑定」：看板数字必须绑定行动（超阈值 → 自动 issue 指派给最近触发的 PR 作者）——无行动绑定的看板是装饰；「指标 → 责任 → 动作」的闭环。
- 复盘的最后一块：迁移成本的 amortization（迁移工时 ÷ 每日节省 = 回本天数）——回本周期是向管理层证明平台投资的语言。
- 追问钩子：为什么「一次性报告」会主动误导组织？——它给决策者「完成」的错觉，而构建性能是漏水的桶（每次依赖升级/配置变更都在漏水）；持续看板把「保持性能」变成日常运营——平台的 ROI 叙事必须包含「守成成本」，否则下一次迁移的预算申请会失败。

```javascript
// 收益追踪看板
const WATCH_METRICS = {
  buildP50: { threshold: '+10%', action: 'issue-to-blame' },
  cacheHitRate: { threshold: '-5%', action: 'issue-to-tooling' },
  entrySizeKB: { threshold: '+8%', action: 'issue-to-pr-author' },
};
async function weeklyWatch(history, baselines) {
  const findings = [];
  for (const [k, cfg] of Object.entries(WATCH_METRICS)) {
    const cur = weeklyP(history, k), base = baselines[k];
    const drift = (cur - base) / base;
    if (Math.abs(drift) > parsePct(cfg.threshold)) {
      const issue = await createIssue({
        title: `${k} 漂移 ${(drift * 100).toFixed(1)}%`,
        assignee: cfg.action === 'issue-to-blame' ? blameOf(history, k) : 'platform-team',
      });
      findings.push({ metric: k, drift, issue });
    }
  }
  return findings;                                       // 指标 -> 责任 -> 动作闭环
}
// 回本计算
const roi = (migrationHours, dailySavingMin) =>
  `${(migrationHours * 60 / dailySavingMin).toFixed(0)} 天回本`;
```
