## RBL-768：迁移复盘：旧构建器退役清单——切换后还有哪些事必须做完

**答**:
- 「切换成功」≠「迁移完成」——退役清单：1) **依赖清理**（旧工具的 devDependencies/插件/loader 全删——残留会被安全扫描盯上且误导新人）；2) **文档替换**（README/内部 wiki 的构建章节、CI 脚本注释）；3) **脚本清理**（package.json scripts 里 build:legacy 类双轨命令删除）；4) 缓存目录清理（旧缓存目录不再使用，CI 缓存 key 更换避免死缓存占空间）；5) 团队公告 + 新人培训材料更新。
- 观察期：切换后 2 周的「异常监测窗」——构建失败率/产物体积/HMR 延迟的看板对比基线（RBL-705 指标体系），窗口期保留「一键回滚」能力（旧配置文件保留但标记 deprecated，观察期后删除）。
- 经验沉淀的载体：迁移复盘文档（预估 vs 实际成本/踩坑清单/规则库）+ 迁移工具（codemod/检查器）入内部仓库——下个仓库迁移的启动成本从「从零探索」降到「跑工具 + 复查」。
- 退役的「反清单」（不要做的）：不要立即删除旧配置文件的历史（git 历史永远在，但迁移期的 diff 对照有价值）；不要跳过观察期直接删回滚能力——「切换成功」的证据是指标，不是主观感觉。
- 追问钩子：为什么退役清理常被拖延数月？——没有明确的「完成定义」；解法是把退役清单做成 CI 可校验项（旧依赖存在即 fail 的检查任务），让「迁移完成」变成可验证状态而非口头宣布。

```javascript
// 退役清单校验（CI 任务）
const RETIREMENT_CHECKS = [
  { id: 'no-legacy-deps', run: (pkg) =>
      !Object.keys({ ...pkg.dependencies, ...pkg.devDependencies }).some(d =>
        /webpack|gulp|grunt/.test(d)) },
  { id: 'no-legacy-scripts', run: (pkg) =>
      !Object.keys(pkg.scripts || {}).some(s => /legacy|webpack/.test(s)) },
  { id: 'cache-key-rotated', run: (ci) => !ci.cacheKey.includes('webpack') },
  { id: 'docs-updated', run: () => !grep('docs/', 'webpack.config') },
];
function retire() {
  const failures = RETIREMENT_CHECKS.filter(c => !c.run(currentState()));
  if (failures.length) fail(`退役未完成: ${failures.map(f => f.id).join(', ')}`);
  // 观察期后：删除 deprecated 旧配置 + 回滚能力
}
```
