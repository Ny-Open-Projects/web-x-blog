## RBL-686：场景题：大促前的构建体系容量预案——从「能构建」到「能抗流量」

**答**:
- 大促场景的构建压力模型：发布频率 ×2（热修频繁）、构建并发 ×3（多需求并行发布）、紧急回滚要求（分钟级重发旧版本）——容量预案要覆盖「并发构建池扩容 + 缓存预热 + 回滚快车道」三件事。
- 回滚快车道是生命线：产物是内容寻址的（RBL-598）——「回滚到上周版本」= 把上次 release 的 manifest 与产物重新置顶（不动 CDN 历史文件），零构建完成；预案要求「发布记录保留 N 周 + 产物物理不删除」。
- 缓存预热：新版本发布前，把高频 chunk 预热到 CDN（回源流量被打挂是真实事故）；预热清单来自 RUM 数据（上次版本的高频资源），构建器输出「资源重要性分级」。
- 并发池预案：构建服务限流（租户级并发上限）+ 弹性扩容阈值（队列积压 > N 触发 worker 扩容）；紧急插队机制（热修 P0 任务可抢占，RBL-564 优先级）。
- 追问钩子：为什么大促前要做「构建体系压测」而不仅是前端页面压测？——构建是发布链路的单点：发布高峰时构建慢 = 无法热修；压测模拟「峰值发布并发」验证池容量与队列行为，这才是容量预案的验证手段。

```javascript
// 容量预案检查表
const CAPACITY_PLAN = {
  buildPool: {
    baseline: 8, peakTarget: 24,                         // 弹性扩容
    scaleTrigger: { queueDepth: 10, waitP95Ms: 30000 },
  },
  cache: {
    warmup: { strategy: 'rum-top', threshold: 'P95 usage', beforeRelease: true },
  },
  rollback: {
    channel: 'manifest-switch',                          // 零构建回滚
    retentionWeeks: 8,                                   // 产物保留窗口
    drillFrequency: 'per-sprint',                        // 回滚演练
  },
  rateLimit: { perTenant: 4, queueTimeoutMs: 120000 },
};

// 回滚执行（零构建）
async function rollbackTo(releaseId) {
  const record = releases.get(releaseId);
  if (!record) throw new Error(`发布记录过期（保留 ${CAPACITY_PLAN.rollback.retentionWeeks} 周）`);
  await cdn.switchManifest(record.manifest);             // 产物文件仍在 CDN
  return { rolledBackTo: releaseId, buildTimeMs: 0 };    // 零构建秒级回滚
}
```
