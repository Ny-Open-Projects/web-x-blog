## RBL-598：产物文件名哈希策略：内容寻址的层级与失效传播范围

**答**:
- hash 文件名的本质是内容寻址 + 永久缓存：`main.abc123.js` 的 hash 决定「哪些请求能继续命中 CDN」。策略关键是**hash 的输入范围**——范围过宽（整次构建一个 hash）导致任何模块改动使全部产物失效；范围过窄（仅文件自身内容）导致引用断裂。
- 正确层级是**自底向上传播**：叶子模块改动 → 其所在 chunk 内容变 → chunk hash 变 → **引用该 chunk 的入口/runtime 也要更新引用名** → 入口 hash 变。即 hash 是依赖图上的函数，不是文件局部函数。构建器要先算无引用者的 hash，再拓扑序向上传播（这就是「级联 hash」）。
- 失效传播范围控制：chunk 分割的缓存粒度价值就在这里——模块改动的失效范围 = 其所在 chunk 的引用闭包；如果业务代码与 vendor 混在一个 chunk，改一行业务代码连 vendor 一起失效（这就是「合理分割是缓存粒度设计」的原因）。
- runtime/manifest 的地位：跨 chunk 引用靠 runtime 里的映射表（chunkId → hash 文件名），runtime 本身 hash 变化最频繁——所以「内容无变化的 chunk hash 不变」要排除 runtime 注入的影响（如把动态 import 路径从 chunk 内容里抽象出来）。
- 追问钩子：`[contenthash]` vs `[chunkhash]` vs `[hash]`——[hash] 整构建一级（最粗），[chunkhash] chunk 内容级，[contenthash] 文件内容级（css 提取后不变）；现代工具基本统一为 contenthash + 级联，旧概念只是兼容历史。

```javascript
// 级联 hash 计算（拓扑序自底向上）
function computeHashes(chunks, graph) {
  const hashes = new Map();
  // 先算不引用其他 chunk 的（叶子 chunk）
  const order = topoSortByChunkRefs(chunks);           // 被引用者先算
  for (const c of order) {
    const refs = chunksOf(c).map(r => hashes.get(r)).join(',');
    const input = chunkContent(c) + '|' + refs;         // 内容 + 引用链共同决定 hash
    hashes.set(c, sha256(input).slice(0, 8));
  }
  // 产物名与引用改写
  const nameOf = (c) => `${c.name}.${hashes.get(c)}.js`;
  for (const c of order) {
    c.code = rewriteChunkRefs(c.code, r => nameOf(r));  // import 路径替换成带 hash 名
  }
  return new Map([...hashes].map(([c, h]) => [c, nameOf(c)]));
}

// 验证失效传播：只改 chunk X 内容
// -> X 的 hash 变 -> 引用 X 的 runtime/entry hash 变 -> 无关 chunk hash 不变（缓存保留）
```
