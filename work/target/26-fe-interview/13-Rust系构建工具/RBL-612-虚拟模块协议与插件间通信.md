## RBL-612：虚拟模块协议：\0 前缀、约定与插件间数据传递的标准模式

**答**：
- 虚拟模块 = 不存在于磁盘、由插件动态生成的模块（CSS 注入、宏展开、manifest 注入）。协议核心：**id 空间隔离**——Vite/rollup 用 `\0` 前缀标记虚拟 id，保证不与真实路径冲突、不被其他 resolve 逻辑捕获；协议还包括「resolve 虚拟 id 必须稳定」（同参数同 id）与「id 需可序列化进 sourcemap（sources 显示成虚拟路径）」。
- 数据传递标准模式：插件 A 生成虚拟模块内容（如扫描 src/routes 产出路由表），插件 B（或用户代码）import 它——两种实现：1) `resolveId + load`：A 拦截虚拟 id 的 resolve 与 load，运行时再生成（惰性、最新鲜）；2) emitFile：构建早期把内容物化成产物。选择标准：内容是否依赖其他模块的处理结果（依赖 → load 时机惰性）。
- 命名约定：虚拟 id 要携带参数（`\0/routes.json` vs `\0/i18n:zh-CN`），参数变化 = 不同模块；同时要防「参数注入路径分隔」（对参数做编码）。虚拟模块的 watch/失效：内容生成依据变化时要主动 invalidate 虚拟模块（Vite 插件里发 server.moduleGraph invalidate）。
- 与 external 的区分：虚拟模块是**构建期可解析的合成代码**，external 是运行时代理解析；两者的优先级顺序（resolve 插件里谁先命中）要明确——虚拟 id 因为 \0 前缀天然先于包解析。
- 追问钩子：HMR 下虚拟模块的完整性——虚拟内容生成依据（如 routes 目录）变化 → 虚拟模块失效传播到所有 import 它的模块；如果插件忘记 invalidate，页面表现为「路由表是旧的但不报错」——静默失效是虚拟模块最典型的线上 bug。

```javascript
// Vite 式虚拟模块插件
function virtualRoutes() {
  const VIRTUAL = '\0/routes.json';                      // \0 前缀协议
  return {
    name: 'virtual-routes',
    resolveId(id) {
      if (id === 'virtual:routes') return VIRTUAL;       // 用户 import 'virtual:routes'
    },
    load(id) {
      if (id !== VIRTUAL) return;
      const routes = scanRoutes('./src/pages');          // 构建期扫描
      return {
        code: `export default ${JSON.stringify(routes)};`,
        map: { sources: ['virtual:routes'], names: [], mappings: '' },  // sourcemap 兜底
      };
    },
    // 失效：路由目录变化时（watchPlugin 配合）
    handleHotUpdate(ctx) {
      if (ctx.file.startsWith('src/pages/')) ctx.server.moduleGraph.invalidateModule(
        ctx.server.moduleGraph.getModuleById(VIRTUAL));
    },
  };
}
// 用户侧：import routes from 'virtual:routes'
```
