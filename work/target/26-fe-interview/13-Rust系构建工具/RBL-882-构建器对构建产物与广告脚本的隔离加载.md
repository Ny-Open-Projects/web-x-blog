## RBL-882：场景题：广告/第三方脚本的隔离加载——性能税与沙箱

**答**:
- 第三方脚本（广告/统计/客服）的性能税治理：1) **加载时机**（idle 后加载——不与首屏抢带宽，RBL-769 空闲调度的三方版）；2) 隔离执行（iframe sandbox/Worker——第三方脚本的长任务不阻塞主线程；Partytown 模式：main-thread 转发到 worker）；3) 失败隔离（第三方挂了不影响主站——超时/错误边界）；4) consent 门控（RBL-827 联动——追踪类同意后才加载）。
- 构建器的配合：1) 第三方脚本清单化（manifest 三方资产区——审计与预算的对象）；2) loader 注入（统一的第三方加载器：优先级/超时/失败重试/consent 检查——业务代码不直接写 script 标签）；3) 性能预算的隔离（三方脚本预算独立——「第三方不能挤占业务预算」是谈判依据）。
- 沙箱的取舍：iframe 沙箱（强隔离但通信成本/DOM 访问受限）vs Worker 转发（DOM API 需代理，覆盖面有限）vs 直接加载（无隔离——只给必需品）；按「第三方的 DOM 需求」选型。
- 长任务的观测：三方脚本的 long task 归因（PerformanceObserver 的 attribution）——「第三方占主线程 X ms」的数据是砍脚本/沙箱化的依据。
- 追问钩子：为什么「第三方脚本独立预算」是治理的杠杆？——混合预算下，业务膨胀会挤掉三方预算（业务优先），三方膨胀也会挤掉业务（加载器先到先得）；独立预算让「三方税」显性化（广告脚本 200KB 是产品决策不是默认接受）——预算的隔离本质是「责任主体分离」，与微前端的资源隔离同构。

```javascript
// 第三方加载器（统一入口）
const THIRD_PARTY = [
  { id: 'analytics', src: '/tp/analytics.js', consent: 'analytics', idle: true, timeout: 5000 },
  { id: 'ads', src: '/tp/ads.js', consent: 'ads', idle: true, sandbox: 'iframe' },
];
async function loadThirdParty(id) {
  const t = THIRD_PARTY.find(x => x.id === id);
  if (t.consent && !(await consentGranted(t.consent))) return null;   // RBL-827
  const run = () => new Promise((res, rej) => {
    const s = document.createElement('script');
    s.src = t.src; s.async = true;
    const timer = setTimeout(() => rej(new Error('third-party timeout')), t.timeout);
    s.onload = () => { clearTimeout(timer); res(); };
    s.onerror = () => { clearTimeout(timer); rej(new Error('load fail')); };  // 失败隔离：不重试不冒泡
    document.head.appendChild(s);
  });
  if (t.sandbox === 'iframe') return loadInSandbox(t);
  return run();
}
requestIdleCallback(() => loadThirdParty('analytics'));   // idle 后加载
```
