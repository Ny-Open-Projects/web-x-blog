## RBL-715：构建器产物协议验证：导出面、全局污染与模块格式的契约测试

**答**:
- 产物是「对下游的契约」：库产物（SDK/组件库）发布后，消费方按 package.json 的 exports/main/types 解析——契约测试验证「产物结构与声明一致」：1) exports 字段列出的每个入口文件真实存在；2) 导出面（运行时 export 名集合）与 d.ts 声明一致；3) UMD 全局变量挂载正确（window.ReactSDK 存在）；4) 无意外全局污染（产物执行后 window 上新增的键 = 声明的 globals）。
- 协议漂移的典型事故：重构后入口改名（index.js → main.js）但 exports 未同步 → npm 包安装即报错（Cannot find module）；导出面收缩（删了某导出）→ 下游运行时 undefined——发布前契约测试是最后防线（RBL-649 语义 diff 的发布态版本）。
- 模块格式契约：ESM 产物不得含 CJS 残留（require/module.exports 混入会让「纯 ESM」声明失效）；CJS 产物验证 default 导出互操作（esModule 标记）。构建器输出格式自检 + 契约测试兜底。
- 全局污染检测的实现：产物在受控沙箱执行后对比 sandbox 全局快照——新增键超出声明即诊断；这类「意外全局」常来自插件注入或全局 polyfill，是库类产物的真实事故源。
- 追问钩子：为什么「导出面与 d.ts 一致」重要？——TS 用户按类型补全开发，运行时缺导出是「类型说有、运行时没有」的静默错（TS 编译过了但 runtime undefined）；契约测试在发布前把两类产物（代码与声明）绑定验证。

```javascript
// 产物契约测试
async function verifyContract(pkg) {
  const problems = [];
  // 1) exports 声明与文件存在性
  for (const [sub, target] of Object.entries(pkg.exports)) {
    const file = resolveExport(pkg, sub, target);
    if (!fs.existsSync(file)) problems.push(`exports '${sub}' 指向不存在的 ${file}`);
  }
  // 2) 导出面 vs d.ts
  const runtime = await import(pathToFileURL(pkg.main));
  const declared = parseDtsExports(pkg.types);
  const rtSet = new Set(Object.keys(runtime).concat(runtime.default ? ['default'] : []));
  for (const name of declared)
    if (!rtSet.has(name)) problems.push(`d.ts 声明导出 '${name}' 但运行时缺失`);
  // 3) 全局污染（UMD）
  if (pkg.format === 'umd') {
    const sandbox = runInSandbox(pkg.file);
    const polluted = Object.keys(sandbox.globals).filter(k => !pkg.allowedGlobals.includes(k));
    if (polluted.length) problems.push(`意外全局污染: ${polluted.join(', ')}`);
  }
  return problems;                                       // 空 = 契约通过
}
```
