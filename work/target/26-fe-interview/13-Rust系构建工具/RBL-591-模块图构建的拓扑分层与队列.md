## RBL-591：模块图构建算法：分层 BFS 与优先队列在依赖展开中的取舍

**答**：
- 模块图构建 = 从 entry 出发的「解析即发现」过程：transform 一个模块 → 提取 import 语句 → resolve 出新模块 → 入队。图构建顺序影响两个工程指标：首 chunk 可用时间（BFS 层序天然贴近请求顺序）与并行度（队列宽度决定线程喂饱程度）。
- 纯 BFS 的优点：依赖层次展开，浅层模块（页面直接 import）最先完成，dev 模式首屏链路短；缺点：单层内无优先级，热门大模块与冷门小模块同级排队。
- 优先队列方案（RBL-564 的通用化）：按「依赖深度 + 请求热度 + 预估成本」打分排序——构建器可先用浅层信息调度，随 parse 结果动态修正分数；代价是堆操作开销与饥饿管理（低分模块长期搁置，需要 aging 机制）。
- 循环依赖在图构建期的处理：不是错误而是「待定边」——A import B 且 B import A 时，先把 A 标记为「部分解析」，B 的解析继续，等闭包收敛后再补边；编译期只记录环供后续产物排序决策（RBL-595）。
- 实现细节：去重入口——同一模块被 10 个模块 import 只 transform 一次（引用计数或 in-flight 表 + 等待合并）；「合并并发相同请求」是打包器最基础的去重原语。
- 追问钩子：为什么构建器不用拓扑排序作为主驱动？——图在构建过程中是**不完整的**（解析才知道边），拓扑排序需要完整 DAG；实际做法是「边发现边调度」，拓扑约束留到产物生成阶段（chunk 内容排序）才生效。

```javascript
// 图构建主循环（概念实现）
async function buildGraph(entries) {
  const graph = new Map(); const inflight = new Map();
  const queue = [...entries];                        // BFS 队列起步

  async function loadModule(id) {
    if (graph.has(id)) return graph.get(id);         // 已完成
    if (inflight.has(id)) return inflight.get(id);   // 并发合并：等同一个 promise
    const p = (async () => {
      const mod = await transform(id);               // CPU 密集 -> 内部走 rayon
      graph.set(id, mod);
      // 发现依赖：resolve 后继续入队（BFS 层序）
      const deps = await Promise.all(mod.imports.map(i => resolveId(i.source, id)));
      mod.edges = deps.map(d => d.id);
      queue.push(...mod.edges.filter(e => !graph.has(e)));
      return mod;
    })();
    inflight.set(id, p);
    const m = await p; inflight.delete(id);
    return m;
  }

  while (queue.length) {
    const batch = queue.splice(0, queue.length);     // 分层批量出队 -> 并行
    await Promise.all(batch.map(loadModule));
  }
  return graph;
}
// 循环依赖自然收敛：A 部分解析时 B 入队，B 引用 A 走 graph/inflight 命中，无死循环
```
