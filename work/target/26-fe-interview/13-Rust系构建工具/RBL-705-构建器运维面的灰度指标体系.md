## RBL-705：构建器运维面的灰度指标体系：升级后如何确认「没问题」

**答**:
- 构建器升级后的「没问题」不是看「构建成功」，而是看四层指标：1) 成功率（构建失败率对比基线，异常升高立即预警）；2) 产物质量（体积分布、语法兼容性告警数、chunk 数量分布——结构性变化）；3) 性能（构建时长 P50/P95、内存峰值——回归检测）；4) 端到端（HMR 触发到生效延迟、dev server 启动时间——开发者体验指标）。
- 指标采集的载体：CI 汇总（构建时长/失败率天然有）、本地遥测（opt-in）、产物审计（体积/兼容性）；分维度看板（按仓库/团队/分支）——混合均值掩盖局部回归（RBL-637 同理）。
- 灰度判定的量化标准：新版本成功率 ≥ 基线 −0.3% 且 P95 时长 ≤ 基线 +10% 持续 3 天才放全量；任何一项破线回退 flag（RBL-589 的逃生门在指标层的联动）。
- 预警的去噪：正常波动（业务大改导致体积上涨）vs 工具回归（同样代码体积上涨）——用「固定基准仓库」（不受业务变更干扰的哨兵项目）分离两类信号；哨兵仓库是构建器运维的关键资产。
- 追问钩子：为什么「dev 体验指标」要单列？——构建成功且产物 OK 但 dev server 启动从 2s 变 8s，用户的体感是「工具变差了」；CI 指标捕捉不到 dev 场景，必须从本地遥测/哨兵开发流程采集——开发者工具的北极星是「编辑-反馈循环时长」。

```javascript
// 灰度看板指标定义
const METRICS = {
  successRate: { source: 'ci', baseline: 0.995, guard: (v, b) => v >= b - 0.003 },
  buildP95: { source: 'ci', guard: (v, b) => v <= b * 1.1 },
  peakMem: { source: 'telemetry', guard: (v, b) => v <= b * 1.15 },
  hmrLatency: { source: 'local', guard: (v, b) => v <= b * 1.2 },   // dev 体验
  sizeDistribution: { source: 'audit', kind: 'distribution', guard: compareDistributions },
};

async function gate(promotion) {                         // 灰度放量判定
  const results = await collectMetrics(promotion.version, { days: 3, repo: 'sentinel-*' });
  const broken = Object.entries(METRICS).filter(([k, m]) => {
    const base = baseline(k); const cur = results[k];
    return !m.guard(cur, base);
  });
  if (broken.length) return { promote: false, broken: broken.map(([k]) => k) };
  return { promote: true };
}
```
