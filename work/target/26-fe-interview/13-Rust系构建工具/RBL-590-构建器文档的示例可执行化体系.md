## RBL-590：构建器文档的示例可执行化：文档代码即测试的工程化

**答**：
- 构建器文档的核心痛点是**示例腐化**：API 改版后文档里的配置悄悄失效，用户照抄报错——解法是把文档示例当一等公民纳入测试：「文档代码即测试」（doctest 模式）。
- 三级可执行化：1) **语法级**：文档中的代码块全部抽取并 parse 校验（最低成本，防语法腐化）；2) **执行级**：标注 `<!-- verify -->` 的示例进 fixture 体系真实构建，断言产物特征（如「该配置下 codeSplitting 生效：产物含 2 个 chunk」）；3) **结果级**：示例旁内嵌「预期输出」块（三反引号 output 块），CI 构建后 diff——输出变了要么改文档要么确认是预期行为变更。
- 工程化要点：示例与文档版本绑定（每个发布版本的 docs 从源码 tag 构建，站上是快照不是 HEAD）；示例的依赖版本锁定（package.json 放进 fixture）；错误示例（「不要这样写」）也要可验证——断言其产生特定诊断码。
- 组织收益：API 设计评审时直接审「示例能不能表达意图」——写不出简洁示例的 API 大概率设计有问题（esbuild 的 API 一直以示例极简为设计目标）。
- 追问钩子：与 changelog 自动化的联动——breaking change 的 PR 模板强制要求「更新示例 + 提供迁移片段」，CI 校验受影响文档示例全绿后才可合并；这把「文档腐化」从道德问题变成门禁问题。

```javascript
// 文档示例抽取与验证
const md = fs.readFileSync('docs/config.md', 'utf8');

function extractSnippets(md) {
  const FENCE = '`'.repeat(3);
  const re = new RegExp(FENCE + '(js|output)(?:\\s+verify)?\\n([\\s\\S]*?)' + FENCE, 'g');
  const blocks = []; let m;
  while ((m = re.exec(md))) blocks.push({ lang: m[1], code: m[2], verify: new RegExp(FENCE + 'js verify').test(m[0]) });
  return blocks;
}
const blocks = extractSnippets(md);

// 1) 语法级：全部 parse
blocks.filter(b => b.lang === 'js').forEach(b => parse(b.code));

// 2) 执行级 + 结果级：verify 块配对 output 块
for (const b of blocks.filter(b => b.verify)) {
  const expected = nextOutputBlock(b);              // 紧随其后的 output 代码块
  const actual = await runSnippet(b.code);          // 真实构建
  expect(actual.summary).toEqual(expected.text);    // 输出即断言
}

// 3) 错误示例验证：断言诊断码
const bad = blocks.find(b => b.lang === 'js' && b.neg);
expect(await runSnippet(bad.code)).toMatchDiagnostic('RBL1001');
```
