## RBL-737：Resolve 缓存的并行化：目录枚举与包解析的两级并行策略

**答**:
- resolve 是构建的隐形大头（RBL-602）：每个 import 可能触发十几次 stat——并行策略两级：1) **目录枚举并行**（多个 importer 同时解析时，node_modules 上溯的目录列表缓存共享，枚举只做一次）；2) **包解析并行**（不同包的 exports/package.json 解析 rayon 并行）。共享缓存（DashMap）+ 负结果缓存（解析失败的也要缓存——防止重复 stat 不存在路径，这是 resolve 慢的最大来源之一）。
- 负缓存的安全语义：文件「不存在」的结论也会失效（新建文件）——负缓存的 TTL/watch 联动：watch 模式下目录变更事件清空对应负缓存；一次性构建中负缓存可信（构建期间文件系统基本不变）。
- 并行正确性：resolve 是纯函数（id, importer, conditions）→ 结果可缓存可并行；唯一竞争是「缓存写入」——并发解析同一 id 时用「单飞」（single-flight：第一个算，其他等结果）避免重复工作。
- 缓存键设计：`{ id, importerDir, conditions, tsconfigScope }`——importerDir 而非完整 importer（同目录 importer 解析结果一致，命中率大幅提升）。
- 追问钩子：为什么 resolve 优化常排在 transform 前面？——profile 显示大仓库 resolve 占 30-50%（transform 有并行红利、resolve 是串行热路径的隐性串行点）；且 resolve 优化是纯缓存工程（无语义风险），收益确定性高——「先摘低垂果实」的排序依据。

```javascript
// 两级并行 resolve
class ParallelResolver {
  #dirCache = new Map();     // 目录 -> { entries, mtime }
  #negCache = new Map();     // '不存在'结论缓存
  #singleFlight = new Map();

  async resolve(id, importerDir, conditions) {
    const key = `${id}|${importerDir}|${conditions.join(',')}`;
    if (this.#singleFlight.has(key)) return this.#singleFlight.get(key);   // 单飞
    const p = this.#doResolve(id, importerDir, conditions);
    this.#singleFlight.set(key, p);
    p.finally(() => this.#singleFlight.delete(key));
    return p;
  }
  async #doResolve(id, dir, conditions) {
    // 上溯 node_modules：目录枚举缓存共享
    for (const nm of this.upwalk(dir)) {
      const pkgDir = `${nm}/${scopeOf(id)}`;
      if (this.#negCache.has(pkgDir)) continue;           // 负缓存跳过
      try { return await this.parsePackage(pkgDir, conditions); }
      catch { this.#negCache.set(pkgDir, Date.now()); }   // 失败也缓存
    }
    throw new Error(`Cannot resolve ${id}`);
  }
  invalidateDir(dir) {                                    // watch 联动
    for (const k of [...this.#negCache.keys()])
      if (k.startsWith(dir)) this.#negCache.delete(k);
  }
}
```
