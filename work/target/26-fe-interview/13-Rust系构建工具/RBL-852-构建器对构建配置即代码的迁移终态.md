## RBL-852：迁移复盘：配置即代码的终态——schema 化与评审的边界

**答**:
- 迁移终态的配置形态：1) **schema 化**（配置文件带类型定义/校验——非法值构建期即诊断 RBL-575）；2) **差异化收敛**（共享 preset + 白名单覆盖 RBL-677）；3) 变更走 PR 评审（配置即代码——但「评审什么」要有边界：语义变更（新 alias/新 loader）需要评审，格式化变更不应占用 review 注意力）。
- schema 化的深度分层：类型层（字段类型/枚举约束）→ 语义层（依赖约束：format=iife 不得 codeSplit）→ 意图层（alias 命名规范）——「越往上越靠约定」，schema 管得住前两层。
- 配置评审的自动化前置：PR 上跑「配置 lint」（schema 校验 + 语义约束 + 与 preset 的 diff 报告）——评审人只看「语义 diff」而不是全文；配置变更的「影响面预估」（改 alias 影响 N 个文件的解析）。
- 终态的判定标准：新仓库接入成本 < 10 分钟（preset 引入 + 两个字段）、配置漂移可检测（RBL-765 覆盖审计）、构建团队不需要逐仓救火——「自服务」是配置终态的北极星。
- 追问钩子：为什么「配置评审」容易流于形式？——配置 diff 的可读性差（嵌套对象的变化难以人眼评估）且评审人不了解影响面；解法是把评审对象从「配置文本」换成「语义影响报告」（工具生成：这次变更改了什么解析行为/影响哪些模块）——评审的输入决定评审的质量。

```javascript
// 配置 PR 的语义影响报告
async function configImpactReport(prDiff, baseConfig) {
  const newConfig = merge(baseConfig, prDiff.config);
  const semanticChanges = [];
  if (diffKeys(baseConfig.resolve?.alias, newConfig.resolve?.alias))
    semanticChanges.push({ type: 'alias-change', detail: diffKeys(...),
      impact: `影响 ${countAliasUsage(diff)} 个文件的解析` });
  if (newConfig.output?.sourcemap !== baseConfig.output?.sourcemap)
    semanticChanges.push({ type: 'sourcemap-toggle', impact: '产物体积与调试体验' });
  return {
    semanticChanges,
    schemaValid: validateSchema(newConfig),             // RBL-576 校验
    presetDrift: overridesOf(newConfig),                // RBL-678 覆盖审计
  };
}
// 评审人视角：只看 semanticChanges 列表 + 影响数字
```
