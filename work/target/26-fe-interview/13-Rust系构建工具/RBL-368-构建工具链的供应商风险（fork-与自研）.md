## RBL-368：构建工具链的供应商风险

**答**:
- 风险识别：关键工具单点依赖（上游停维护/方向改变/许可变更）——评估维度：维护活跃度、商业化风险（license 变更先例）、社区可替代性
- 应对策略谱系：锁版本观望 → fork 自维（补丁级）→ 抽象层（自建适配隔离供应商 API）→ 自研（最后手段，构建工具自研 ROI 通常极低）
- 抽象层实践：preset 层隔离工具 API（换引擎只改 preset 内部）——供应商解耦的最佳投资点
- 上游协作：发现上游 bug 贡献修复（比 fork 维护成本低）+ 参与上游 RFC（影响方向）——「参与」是比「fork」更高级的风险管理

```text
策略谱：锁版本 → fork 补丁 → 抽象层解耦 → 自研（慎）
最佳实践：preset 抽象层 + 上游贡献参与
```
