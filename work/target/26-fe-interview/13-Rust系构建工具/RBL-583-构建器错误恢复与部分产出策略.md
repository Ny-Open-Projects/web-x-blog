## RBL-583：构建失败时的部分产出策略：fail-fast、best-effort 与产物一致性

**答**：
- 构建中途失败，输出目录处于什么状态？三种策略：1) **fail-fast + 不落盘**：所有产物先写临时目录，全量成功后原子 rename/替换（最安全，dev server 场景浪费）；2) **best-effort 部分产出**：能出多少出多少（错误模块标红），利于 dev 下边报错边看页面；3) **stale 标记**：失败时保留上次成功产物但打 manifest 标记（CI 与部署层可识别「产物是旧版」）。
- 一致性核心：**产物目录的原子切换**——写 `.output.tmp` → 校验完整（manifest 全）→ rename 到 `.output`。防半成品：部署流水线直接拿走写到一半的目录是真实事故（CDN 同步了 50% 的文件）。
- dev 场景的 best-effort 细节：失败模块产出「错误占位模块」（运行时抛出带诊断的 Error），页面其余部分照常工作——HMR 错误覆盖层的本质就是把失败模块替换为错误模块，等修复后原位替换回来。
- prod 场景必须 fail-fast 且不污染旧产物：CI 失败后 dist 应该保持上次成功状态或干脆清空（由部署流程决定），绝不允许「新版混旧版」——sourcemap 与 JS 的版本错配会让错误定位全错。
- 追问钩子：多 chunk 产物间的版本一致性（chunk A 引用 chunk B 的 hash 文件名）——任何 best-effort 都必须保证「引用闭包内完整」：要么这批 chunk 全出，要么全不出（分组原子性），单个 chunk 独立落盘是错的。

```javascript
// 原子产物目录切换
async function writeOutput(artifacts) {
  const tmp = '.output.tmp';
  await fs.rm(tmp, { force: true });
  for (const a of artifacts) await fs.writeFile(path.join(tmp, a.name), a.content);
  await writeManifest(tmp, artifacts);            // manifest 最后写，完整性标志
  await fs.rename(tmp, '.output');                // 原子切换（同分区 rename 原子）
}

// dev 错误占位模块
function errorModule(id, diag) {

}
```
