## RBL-675：构建器维护者的运营面：issue 分诊、复现请求与贡献者路径

**答**:
- 构建器 issue 的分诊困境：报障量大且多数缺复现（用户的仓库是私有巨仓库）——「最小复现请求」模板（issue 模板强制：构建配置 + 最小文件集 + 预期/实际）+ 缺失复现的机器人提示（无复现 14 天自动关闭策略）——没有复现的 issue 无法修复，快速关闭是生态健康。
- 分诊自动化：按错误码/堆栈特征自动打标签（crash/perf/regression）、按内容匹配历史 issue（重复检测）；「回归」标签最高优先（新版本引入的问题，影响升级信心）。
- 贡献者路径设计：good-first-issue 精心维护（文档/小 bug，让新人能落地）、CONTRIBUTING 里写清「跑通本地测试集」的最短路径（构建器开发环境复杂——cargo + node binding 双侧）、PR 模板强制「测试与 fixture」（修复必须带回归用例，RBL-585）。
- 维护者可持续性：issue 积压是维护者倦怠的根源——定期「issue 清扫日」（关闭过时/无法复现）比「永远开着」健康；响应时限分级（crash 24h / 其他 1 周）公开承诺比默默拖延好。
- 追问钩子：为什么「复现模板 + 自动关闭」不是对用户不友好？——无复现 issue 挂着会消耗维护者时间，最终拖慢所有人的修复；闭环是「关闭时给复现指引」——用户补齐复现可重开，而不是简单拒绝。

```javascript
// issue 分诊机器人规则
const TRIAGE_RULES = [
  { when: (i) => /panic|segfault|crash/i.test(i.body), label: 'crash', priority: 'P0' },
  { when: (i) => /slow|slower|regression/i.test(i.body), label: 'regression', priority: 'P1' },
  { when: (i) => !i.hasRepro && ageDays(i) > 14, action: 'close',
    comment: '缺少最小复现（配置 + 文件集 + 预期/实际）。补充后可重开：docs/repro-guide' },
  { when: (i) => similarTo(i, closedIssues) > 0.8, label: 'duplicate',
    comment: `疑似重复 #${similarTo(i, closedIssues).id}` },
];

// 修复 PR 门禁：必须带回归 fixture
function checkFixPR(pr) {
  const hasFixture = pr.files.some(f => f.startsWith('tests/fixture/'));
  const hasTest = pr.files.some(f => /\.test\.(rs|ts|js)$/.test(f));
  if (!hasFixture && !hasTest)
    fail('修复 PR 必须包含最小复现 fixture 或测试（RBL-585 回归集只增不减）');
}
```
