## RBL-569：构建器的内存画像：峰值剖析与 OOM 治理

**答**：
- 大仓库构建 OOM（CI 4GB 限制）是 Rust 构建器的常见线上问题——内存画像三阶段：峰值时点（哪一阶段最贵：模块图驻存 / transform 并发峰值 / chunk 生成 / sourcemap 内存）、单模块成本（AST + 转换产物 + 元数据）、驻存策略（哪些对象活到构建结束）。
- 峰值来源排序：1) **全量模块图驻存**（resolve 后的完整图 + 每模块元数据，O(n) 驻存）；2) **并行 transform 的瞬时峰值**（concurrency × 单模块峰值，10 并发 × 50MB 模块 = 500MB 瞬时）；3) **sourcemap**（VLQ map 可达源码 3~5 倍体积，全量驻存最贵）；4) 重复字符串（模块路径/包名，可用 Atom/StringCache 去重 intern）。
- 治理手段：transform 完成即 drop 源码与 AST（只留产物 + span）；sourcemap 按需生成（dev 全量、prod 只留必要）或流式写盘不驻存；并发限流按内存预算而非纯核数（峰值感知调度）；字符串 intern（同包名 1 万次引用只存一份）。
- 度量：CI 里加内存采样线程（每 200ms 记 RSS），产出「阶段-内存」曲线；OOM 前的死亡报告（allocation profile）比事后猜有用得多。
- 追问钩子：JS 工具（webpack）的 OOM 与 Rust 工具的 OOM 根因不同——webpack 是 GC 压力 + 无法释放的闭包引用，Rust 是无 GC 但驻存策略错误（该 drop 不 drop），排查工具链完全不同（heap snapshot vs valgrind/自建采样）。

```javascript
// CI 内存画像采样（构建器内嵌概念）
async function withMemoryProfile(build, { sampleMs = 200 }) {
  const curve = []; let stop = false;
  (function sample() {
    if (stop) return;
    curve.push({ t: Date.now(), rss: process.memoryUsage.rss(), phase: build.currentPhase() });
    setTimeout(sample, sampleMs);
  })();
  try { return await build.run(); }
  finally {
    stop = true;
    const peak = curve.reduce((a, b) => (b.rss > a.rss ? b : a));
    console.log(`peak RSS=${fmt(peak.rss)} @phase=${peak.phase}`); // 峰值定位到阶段
    writeReport('memory-profile.json', curve);                     // 曲线供复盘
  }
}

// 治理配置示例
const builder = rolldown({
  parallel: { byMemory: true, maxConcurrent: 16 },  // 峰值感知并发
  sourcemap: { retention: 'necessary' },            // 按需保留
  stringInterning: true,                            // 路径/包名去重
});
```
