## RBL-954：综合深水：可调试性作为一等特性——产物调试体验设计

**答**:
- 可调试性的产物设计清单：1) **sourcemap 完整性**（names 段保留——压缩后变量可反解 RBL-608；sourcesContent 的取舍）；2) **x_google_ignoreList**（RBL-620——依赖代码出断点栈）；3) **错误消息的可搜索性**（诊断码 RBL-673 + 错误消息不含动态噪声（路径随机后缀——报错可复制搜索））；4) **调试构建模式**（debug build：不压缩/保留语义变量名/断言开启——「调试包」是产品功能不是 hack）；5) 运行时错误的上下文携带（chunk 加载失败的 URL/期望 hash RBL-623）。
- 可调试性与性能的张力：debug 包大 5-10 倍——「分层调试产物」（CI 全量 debug 包存档 + 线上 prod 包——事故时用 debug 包本地复现，不污染线上）。
- 团队的「可调试性 review」：每个新特性 PR 问「出了错怎么排查」——日志点/诊断码/trace 覆盖（RBL-728）与功能同 review——可调试性作为验收标准而不是事后补。
- 可调试性的度量：「平均排查时长」（从错误报告到根因定位）——SLO 化（RBL-904 的平台 SLI 扩展）；排查时长的构成分析（信息不足 vs 工具缺失 vs 代码复杂）。
- 追问钩子：为什么「可调试性」是构建器被采纳的隐性决策因素？——工具选型时性能对比最显眼，但日常成本在「出问题时的排查体验」——报错可读/map 完整/诊断码可搜的工具让团队每小时省几分钟 × 全员 = 性能差距持平后的决胜项；「隐性决策因素」需要被显性化评估（选型矩阵加调试体验维度 RBL-650）。

```javascript
// 调试包构建配置
const debugBuild = {
  minify: false,                                         // 保留语义变量名
  sourcemap: { names: true, sourcesContent: true },      // 全量反解能力
  assertions: true,                                      // 运行时断言开启
  diagnostics: { codes: true, hints: true },
  // 产物存档：CI 产物库（不部署，事故复现用）
  archive: 'debug-builds/',
};
// 可调试性 review 清单
const DEBUG_REVIEW = [
  '新增错误都有诊断码？（RBL-673）',
  '异步链路有 trace span？（RBL-728）',
  'chunk 加载失败携带版本信息？（RBL-623）',
  'sourcemap names 段保留？（RBL-608）',
];
function debugReview(pr) {
  const missing = DEBUG_REVIEW.filter(q => !pr.checklist?.includes(q));
  return { missing, ok: missing.length === 0 };
}
```
