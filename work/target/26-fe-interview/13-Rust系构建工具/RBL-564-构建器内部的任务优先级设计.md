## RBL-564：构建器内部的任务优先级：为什么 dev server 要把「首屏模块」提前

**答**：
- 全量构建是批处理语义（所有模块平等），dev server 是交互语义：用户等的是**首屏模块链**（entry → 按需 import 的第一层）——turbopack/rolldown dev 都引入任务优先级，把首屏依赖链排到队列头部，深依赖懒加载。
- 优先级来源：1) 请求驱动（浏览器 GET /index.js 到达时提升该 chunk 链）；2) 入口静态分析（parse 后把 entry 的 import 闭包标记高优先级）；3) 历史 profile（上次构建耗时长的模块提前）。
- 实现：任务队列不是 FIFO 而是优先级堆/多级队列；抢占边界是「模块 transform」粒度（Rust 侧 transform 任务小，天然可抢占——大任务要切片）。
- HMR 与冷启动的优先级冲突：编辑触发模块的失效传播应插队到最高级（用户正在等），冷启动的后台预热（如预构建 node_modules）降到 idle 级——vite 的 optimizeDeps 后台化就是同类思路。
- 追问钩子：如何验证优先级有效？——指标是 TTFB of first module 与「首屏链完成时间」，而非总构建时间；压测方法：记录每个模块从入队到产出时间，对比 FIFO 基线。

```javascript
// 优先级调度示意（伪代码）
enum Prio { Critical, High, Normal, Idle }

class TaskQueue {
  #heaps = new Map([[Prio.Critical, []], [Prio.High, []], [Prio.Normal, []], [Prio.Idle, []]]);
  push(task, prio = Prio.Normal) { this.#heaps.get(prio).push(task); }
  pop() { // 高优先级先出，同级 FIFO
    for (const prio of [Prio.Critical, Prio.High, Prio.Normal, Prio.Idle]) {
      const h = this.#heaps.get(prio);
      if (h.length) return h.shift();
    }
  }
}

// 请求驱动提升：dev server 收到 chunk 请求 -> 该依赖闭包插队
server.onRequest('/main.js', () => {
  graph.depsClosure('main.js').forEach(id => queue.push(tasks.get(id), Prio.Critical));
});

// HMR 插队 + 后台预热降级
graph.onInvalidate(id => queue.push(rebuild(id), Prio.Critical));
idle(() => nodeModules().forEach(id => queue.push(build(id), Prio.Idle)));
```
