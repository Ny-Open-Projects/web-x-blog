## RBL-775：场景题：国际化电商的多区域构建——多区域产物矩阵与差异治理

**答**:
- 多区域（US/EU/JP/CN）构建矩阵的维度叠加：region × locale × currency × 合规特性（EU cookie banner/JP 地址表单/CN 备案文案）——矩阵爆炸的治理：**基础产物一份 + 区域差异层**（差异以运行时注入/动态 import 而非独立构建——除非差异是代码级）。
- 构建器需要支持的区域机制：1) region 条件解析（`./shipping.us.ts` vs `./shipping.jp.ts`——RBL-746 平台解析的 region 版本）；2) region 特性 flag（define 注入 REGION 常量做编译期裁剪——合法合规逻辑编译进去，文案走 i18n 层 RBL-695）；3) 合规产物的区域绑定审计（EU 产物必须含 cookie consent 代码——缺失即门禁失败）。
- 矩阵规模控制：区域数 × 构建次数的 CI 成本——分层（公共层构建一次 + 区域层增量）、按发布节奏裁剪（区域独立发布节奏——EU 改动不触发 JP 构建）。
- 区域差异的失效传播：共享代码变更 → 全区域失效（真全量）；区域文件变更 → 只该区域——affected 计算加 region 维度（RBL-726）。
- 追问钩子：为什么「合规逻辑」要编译期裁剪而「文案」走运行时？——合规是法律边界（EU 产物不含 GDPR 逻辑 = 不可接受的实现遗漏风险，编译期保证存在性）；文案是数据（运行时灵活、多语言共享产物）——「存在性保证 vs 数据灵活性」决定编译期/运行时分界。

```javascript
// 多区域构建配置
const REGIONS = ['us', 'eu', 'jp', 'cn'];
const REGION_REQUIREMENTS = {
  eu: ['cookie-consent', 'dsar-entry'],                  // 合规特性必须存在
  cn: ['beacon-备案'],
};
async function buildRegions(src) {
  const outs = {};
  for (const region of REGIONS) {
    outs[region] = await build({
      input: src,
      extensions: [`.${region}.ts`, ...defaultExts],     // region 条件解析
      define: { __REGION__: JSON.stringify(region) },    // 编译期裁剪
      alias: { '#region': `./src/regions/${region}` },
    });
    // 合规审计
    for (const req of REGION_REQUIREMENTS[region] ?? [])
      if (!outs[region].includesFeature(req))
        fail(`${region} 产物缺失合规特性: ${req}`);
  }
  return outs;
}
```
