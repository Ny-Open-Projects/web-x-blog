## RBL-614：多入口产物的公共依赖下沉：从重复打包到共享 chunk 的收益模型

**答**：
- 多入口（多页面/微前端多子应用）最朴素的问题是公共代码重复：10 个入口都 import lodash 就复制 10 份。「下沉」= 把公共依赖抽成共享 chunk，入口只保留引用。收益模型不是简单「体积下降」：抽出后总字节减少但请求数增加，**首次访问多一个 RTT**——收益成立条件是「复用次数 × 缓存命中收益 > 额外请求成本」。
- 收益判定的输入：模块被多少入口共享（引用计数）、模块大小、入口并发加载概率（同一用户会连续访问几个入口？后台管理高、营销页低）——「被 10 个入口引用的 100KB 模块」几乎必然下沉，「被 2 个冷门入口共享的 5KB 模块」内联复制可能更优（RBL-596 的复制取舍）。
- 下沉的层次：1) 入口闭包交集（最保守）；2) 按「引用集合签名」分组——引用该模块的入口集合完全相同的模块归为一组（保证一个 shared chunk 服务固定入口群，缓存友好）；3) 图划分算法（理论最优但难解释）。
- 与 CDN 缓存的配合：shared chunk 的 URL 稳定性（级联 hash，RBL-598）决定复用价值；入口改动不影响 shared chunk 的 hash 才有「跨版本复用」——所以下沉分组要把「变更频率」也作为分组依据（vendor 类长缓存）。
- 追问钩子：为什么下沉不能只看「总字节减少」？——传输层因素：HTTP/2 多路复用下请求数成本下降但仍非零（连接建立/流控）；预加载提示（modulepreload）可以抹平 RTT 成本——所以现代答案常是「下沉 + 预加载关键 shared chunk」组合。

```javascript
// 引用集合签名的下沉分组
function extractShared(entries, modules, opts) {
  const refs = new Map();                                // module -> Set(entryId)
  for (const e of entries) for (const m of e.closure)
    refs.get(m) || refs.set(m, new Set()).get(m).add(e.id);

  // 按引用集合签名分组：同签名的模块进同一 shared chunk
  const groups = new Map();                              // signature -> modules[]
  for (const [m, set] of refs) {
    if (set.size < opts.minShared) continue;
    const size = modules.get(m)?.size ?? 0;
    if (size < opts.minSize) continue;                   // 太小内联
    const sig = [...set].sort().join('+');
    (groups.get(sig) || groups.set(sig, []).get(sig)).push(m);
  }
  // 收益过滤：预估「减少字节」必须 > 组内平均 chunk 开销（估算常数）
  const out = [];
  for (const [sig, ms] of groups) {
    const dupBytes = ms.reduce((s, m) => s + modules.get(m).size * (refs.get(m).size - 1), 0);
    if (dupBytes > opts.overheadKB * 1024) out.push({ sig, modules: ms, savedKB: dupBytes / 1024 });
    else ms.forEach(m => inlineCopy(m));                 // 收益不足：复制
  }
  return out;
}
```
