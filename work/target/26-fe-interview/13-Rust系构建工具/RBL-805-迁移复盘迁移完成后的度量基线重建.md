## RBL-805：迁移复盘：度量基线重建——迁移后的性能数据如何重新建立可信基线

**答**:
- 迁移后旧基线失效：构建时长/内存/产物体积的分布都变了（这是迁移的目的）——旧门禁阈值（RBL-662 的 relativePct 基线）会立刻误报或失效；基线重建是迁移收尾的必要步骤。
- 重建流程：1) 冷却期（迁移后的前 N 次构建数据丢弃——缓存冷/首次全量等一次性因素）；2) 新基线采集（稳定期连续 M 次构建的 P50/P90 记录为基线）；3) 门禁阈值重算（相对基线 + 绝对预算双轨重设）；4) 基线版本化（基线变更记录原因——迁移/业务扩容/工具升级）。
- 「数据可比性」的诚实处理：迁移前后对比报告要用「同任务同输入」的对照（RBL-587 基准套件），业务真实构建的绝对值对比会混入业务变化——「迁移收益」的数字只能来自基准仓库。
- 基线漂移的持续防护：基线本身要定期复核（每季度/每次大版本）；「基线自动刷新」的风险是漂移钝化（每次微涨都刷新基线 = 温水煮青蛙）——刷新需要人工确认或涨速门禁。
- 追问钩子：为什么「冷却期」必要？——迁移后第一次构建常是全量冷缓存（RBL-581），第二次有增量缓存加速——前几次数据不是稳态；用非稳态数据建基线 = 基线失真（偏慢的基线让后续优化虚高，偏快则门禁误报）——基线的价值取决于采集时点的稳态性。

```javascript
// 基线重建流程
async function rebaseline({ history, cooldownBuilds = 3, sampleSize = 10 }) {
  const usable = history.slice(cooldownBuilds);          // 冷却期丢弃
  const sample = usable.slice(-sampleSize);
  if (sample.length < sampleSize)
    return { ready: false, need: sampleSize - sample.length };   // 数据不足
  const p50 = median(sample.map(h => h.buildMs));
  const p95 = percentile(sample.map(h => h.buildMs), 0.95);
  const baseline = { p50, p95, setAt: new Date(), reason: 'post-migration' };
  await saveBaseline(baseline);
  return { ready: true, baseline };
}
// 防钝化：基线刷新需确认
function proposeBaselineUpdate(newP50, oldP50, driftLimit = 0.03) {
  const drift = newP50 / oldP50 - 1;
  if (Math.abs(drift) < driftLimit) return 'no-change-needed';
  return `基线漂移 ${(drift * 100).toFixed(1)}% 需人工确认（原因分类：业务扩容/工具变更/性能回归）`;
}
```
