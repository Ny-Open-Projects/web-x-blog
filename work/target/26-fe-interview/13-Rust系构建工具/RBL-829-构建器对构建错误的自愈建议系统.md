## RBL-829：场景题：构建错误自愈建议系统——从诊断到可执行修复脚本

**答**:
- 「自愈」的正确形态不是自动修（改代码有风险）而是**可执行的修复建议**：诊断码 → 修复模板（codemod 级别：安装缺失依赖/改配置字段/加 polyfill）——用户确认后一键执行；全自动只对「零风险类」开放（安装缺失 peer 依赖、清缓存重试）。
- 修复模板的结构：`{ code, match(diag), plan(diag) -> steps[], risk: 'zero'|'low'|'review' }`——zero（清缓存/重装依赖）可全自动；low（npm install 缺包）一键确认；review（配置重构）只给步骤清单。
- 修复的验证闭环：修复执行后自动重跑构建——失败则回滚修复动作（修复步骤要有 undo——npm install 的 undo 是卸载）+ 报告；成功则记录「诊断 → 修复」映射数据（修复命中率是模板库的迭代指标）。
- 模板库的维护：与错误码注册表（RBL-674）联动——每个诊断码可以声明修复模板；社区/内部共享（同一错误码的修复经验沉淀）。
- 追问钩子：为什么「自动改代码」必须排除在自愈之外？——构建错误的根因常在业务语义（alias 指向哪里是对的？），工具无从判断；自动化改代码的错误会被「自愈」的名义掩盖（用户不再 review）；零风险类的边界（不改文件内容的动作）是安全自动化的定义——自愈的价值在「把确认成本降到一键」而不是「消除确认」。

```javascript
// 修复模板库
const FIXES = [
  {
    code: 'RBL1001',                                     // Cannot resolve
    risk: 'low',
    match: (d) => /Cannot resolve/.test(d.message),
    plan: (d) => {
      const pkg = d.labels[0].text.match(/'([^']+)'/)[1];
      return [{ cmd: `npm i ${pkg}`, undo: `npm rm ${pkg}` }];
    },
  },
  {
    code: 'RBL-CACHE', risk: 'zero',
    match: (d) => /cache corruption/i.test(d.message),
    plan: () => [{ cmd: 'rm -rf .rolldown-cache && rebuild', undo: null }],
  },
];
async function selfHeal(diag, { exec, confirm, autoZero = true }) {
  const fix = FIXES.find(f => f.match(diag));
  if (!fix) return { healed: false, hint: diag.hints };
  if (fix.risk !== 'zero' && !(await confirm(fix.plan(diag))))
    return { healed: false, hint: fix.plan(diag) };
  for (const step of fix.plan(diag)) {
    try { await exec(step.cmd); }
    catch (e) {
      if (step.undo) await exec(step.undo);              // 失败回滚
      return { healed: false, error: e.message };
    }
  }
  const ok = await rebuild();
  return { healed: ok, note: ok ? null : '修复执行但构建仍失败——进入人工排查' };
}
```
