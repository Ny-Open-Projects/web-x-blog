## RBL-880：场景题：性能预算的实时闭环——CI 门禁到 RUM 回流

**答**:
- 性能预算的完整闭环：1) **CI 门禁**（构建期体积预算 RBL-662——产物层）；2) **RUM 回流**（真实用户指标 LCP/TTI——体验层）；3) **回归判定**（RUM 劣化 → 归因到产物变化——哪个 release/哪个 chunk）；4) **策略调整**（预算阈值从 RUM 分布校准——P75 用户设备能承受的预算）。三层构成「预算的实证闭环」：CI 保证不引入劣化，RUM 验证预算是否合理。
- RUM 与产物的关联键：RUM 上报携带 buildId（RBL-795 release 绑定）——「每个 release 的 LCP 分布」可与产物体积 diff 交叉（体积 +5% 的 release，LCP 分布右移——因果假设供归因）。
- 归因的方法论：RUM 劣化 → 按路由/设备分桶 → 与该 release 的产物 diff（新增/膨胀的 chunk）→ 候选归因清单——自动化归因有限（相关性），人工确认因果；「归因报告附产物 diff」让排查有的放矢。
- 预算校准的实证方法：预算不该拍脑袋——RUM 分布（P75 设备的网络/算力）反推「JS 预算 = TTI 目标 − 不可控时间（网络/渲染）」；阈值随设备分布演化调整（一年一次校准）。
- 追问钩子：为什么只有 CI 门禁没有 RUM 回流的预算体系是「半闭环」？——CI 管的是「产物层代理指标」（KB 数），体验的真实约束在用户设备（同 300KB 在旗舰机与低端机的 TTI 差 3 倍）；没有 RUM 就不知道「预算设对了没」——预算可能是过松（体验差没发现）或过严（白白限制业务）；两层闭环让预算从「约定」变成「实证校准的约定」。

```javascript
// 预算闭环
async function budgetLoop({ release, rum, baseline }) {
  // 1) RUM 劣化检测（分桶）
  const buckets = groupBy(rum.forRelease(release), b => `${b.route}|${b.deviceTier}`);
  const degraded = Object.entries(buckets).filter(([k, samples]) => {
    const p75 = percentile(samples.map(s => s.lcp), 0.75);
    const base = baseline[k];
    return base && p75 > base * 1.15;
  });
  // 2) 归因：与产物 diff 交叉
  for (const [key] of degraded) {
    const route = key.split('|')[0];
    const sizeDiff = await manifestDiff(release, baseline.release, route);
    report({ route, degradation: key, suspectChunks: sizeDiff.top });
  }
  // 3) 预算校准建议（年度）
  // JS 预算 = TTI 目标(3s) - 网络(RUM 网络分布 P75) - 渲染(设备分布)
}
```
