## RBL-668：迁移期的配置漂移守卫：双构建器并行时的单一来源策略

**答**:
- 双构建器并行的头号风险：团队在旧配置上修 bug（比如加个 alias），新配置没同步——切换日才发现新构建缺配置，累积漂移一次性爆发。守卫思路是「单一来源」：要么旧配置是源（每次变更触发翻译器重跑 + diff 检查），要么直接迁移到「构建器无关配置层」。
- 方案 A（翻译器联动）：旧配置 hash 变化 → CI 拒绝合并并提示重跑 codemod——简单但多一步人工；方案 B（共享配置层）：把两构建器共同语义的配置抽出（entry/alias/define/rules 的语义层），各自 adapter 渲染成原生配置——改一处两边同步，漂移被结构性消灭。
- 漂移检测的另一层：产物级每日对比（影子构建的 semantic diff 趋势），配置层守卫漏掉的（如插件行为差异）在产物层暴露——双层防线。
- 共享配置层的边界：不是所有配置都能共享（loader 语法差异大）——共享「语义意图」（如 aliases: {}、envDefines: {}、targets: []），构建器特定项留在各自文件；抽象泄漏时明确标注「此项不可共享」。
- 追问钩子：为什么「漂移」比「一次性不兼容」更危险？——一次性问题在切换时集中暴露可修复；漂移是「隐性正确性破坏」（新构建缺 alias 仍能构建成功，只是解析到错误位置），上线才炸。守卫的本质是把隐性差异显性化。

```javascript
// 共享语义层 + 双 adapter
// config/base.js —— 语义意图层
export const BASE = {
  entries: { main: 'src/main.ts', admin: 'src/admin.ts' },
  aliases: { '@': 'src', '@shared': 'packages/shared/src' },
  defines: { __APP_VERSION__: pkg.version },
  targets: { modern: 'es2019' },
  devProxy: { '/api': 'http://localhost:8080' },
};

// rspack.adapter.js
export const toRspack = (b) => ({
  entry: b.entries,
  resolve: { alias: b.aliases },
  plugins: [new rspack.DefinePlugin(b.defines)],
  builtins: { presetEnv: { targets: b.targets.modern } },
});

// webpack.adapter.js
export const toWebpack = (b) => ({
  entry: b.entries,
  resolve: { alias: b.aliases },
  plugins: [new webpack.DefinePlugin(b.defines)],
});
// 别名/定义改动只改 base.js —— 双构建器同步，结构性消灭漂移

// 双层守卫（CI）
const cfgDrift = hashFile('config/webpack.js') === readCache('rspack.sourceHash');
const prodDrift = semanticDiff(dist, distRspack).length === 0;
if (!cfgDrift || !prodDrift) fail('迁移并行期漂移检测未通过');
```
