## RBL-855：场景题：构建系统的成本核算——CI 分钟数与开发时长的量化模型

**答**:
- 构建优化的成本核算模型：1) **CI 成本**（构建分钟数 × 单价——机器规格差异大，统一折算成「等效分钟」）；2) **开发者等待成本**（本地构建时长 × 触发次数 × 人力单价——被低估的大头：每次等 30s × 每天 40 次 × 100 人 = 每天 33 人时）；3) 排队成本（CI 队列等待 = 团队上下文切换成本）。模型让优化投资有 ROI 语言（RBL-851 回本天数）。
- 开发等待成本的计算口径：不是「等的时间」而是「被打断的专注」（等待 > 10s 就切换上下文——重返回成本 2-5 分钟）——「等待成本 = 次数 × 上下文重置成本」比纯等待时间大一个量级，这是构建提速真正的商业价值。
- 核算的反直觉结论：CI 分钟数便宜（自动化小时 $0.05-0.2），人贵（$50-100/h）——「优化 CI 时长但不优化本地体验」是投资错向；本地 dev 的「编辑→反馈循环」时长是最贵的单一指标（RBL-705 的 hmrLatency）。
- 度量的落地：CI 分钟从 CI 平台 API 直接拉（按 job 聚合）；本地等待从遥测（RBL-679 opt-in）——数据的分桶（团队/仓库/任务类型）让投资决策可定位（优化哪个仓库 ROI 最高）。
- 追问钩子：为什么「CI 分钟」是糟糕的优化北极星？——它可以被作弊（减少检查任务/关闭测试 = 分钟数降但风险升）；它与「人等待」脱钩（CI 快 10 分钟对 PR 作者的价值远小于本地快 5 秒）——北极星必须绑定「人的时间」，CI 分钟只是成本项不是价值项；优化目标的错位会引导团队做「数字好看但没人受益」的优化。

```javascript
// 成本核算模型
function buildCostModel({ ciMinutes, ciPricePerMin, devs, localBuildSec, triggersPerDay, contextSwitchMin = 3 }) {
  const ciCost = ciMinutes * ciPricePerMin;              // CI 侧
  const waiting = devs * triggersPerDay *                // 开发等待（上下文重置口径）
    (localBuildSec > 10 ? contextSwitchMin : localBuildSec / 60) / 60;  // 人时/天
  return {
    ciCostPerMonth: ciCost * 22,
    developerHoursPerDay: +waiting.toFixed(1),
    developerCostPerMonth: waiting * 22 * 100,           // $100/h 人力
    insight: waiting * 22 * 100 > ciCost * 22
      ? '人等待成本 >> CI 成本：优先优化本地 dev 循环'
      : 'CI 成本占优：优化 runner 效率与缓存',
  };
}
console.log(buildCostModel({ ciMinutes: 20000, ciPricePerMin: 0.1,
  devs: 100, localBuildSec: 30, triggersPerDay: 40 }));
// developerHoursPerDay = 100*40*3/60 ≈ 200 人时/天 —— 本地体验是最大成本项
```
