## RBL-200：笔试：给一个真实仓库设计端到端 CI 提速方案（架构设计题）

**题目**：场景：电商 monorepo，12 个前端应用 + 30 个包，pnpm workspace + webpack，CI 单 job 串行：install 8min → build 15min → test 25min → deploy 4min，共 52min，全量跑所有包。要求：1) 给出三阶段优化路线（每阶段列改动点、预期收益、风险）；2) 画出优化后的 job 拓扑（文字图）；3) 关键缓存 key 设计列出；4) 写出"回归防护"：优化不能改变产物行为，用什么校验；5) 给出度量指标与终态目标值。

```text
【阶段一：零风险速赢（1 周，预期 52→28min）】
- job 拆分：install 缓存（lockfile key）+ build/lint/test 三 job 并行（needs 编排）
- test 分 4 片（LPT 加权，RBL-179）
- deploy 与 test 并行（部署不依赖测试结果时）或仅依赖 build
- 风险：缓存污染 → key 加版本段，出事 bump

【阶段二：内核升级（1 周，预期 28→12min）】
- webpack→Rspack（影子构建+产物 hash 对比灰度，RBL-145）build 15→3min
- babel-loader 相关全部下线；minify 走 SWC
- tsc --build 增量化 + tsbuildinfo 缓存
- 风险：转换语义差异 → 回归用例集 + sourcemap 抽查

【阶段三：任务级缓存（1 周，预期 12→4min）】
- 引入 turbo 远程缓存（自托管，RBL-157）+ affected 构建（RBL-158/175）
- PR 只构建受影响子图；main 定时预热（RBL-193）
- job 拓扑：
    install ──┬─ lint(2min, 缓存)
              ├─ build(3min, Rspack+任务缓存)
              ├─ typecheck(2min, tsbuildinfo)
              └─ test×4 shards(5min)
    deploy ← build（artifact 传递，不重构建）

【缓存 key 清单】
- deps:  {os}-{pnpm-lock-hash}-v1
- build: {rspack 版本}-{包源码 hash}-{lockfile hash}-v1（含环境变量白名单）
- test:  {源码 hash}-{shard}-{框架版本}-v1
- 全局版本段 vN 支持一键失效

【回归防护】
- 产物级：manifest + gzip 体积 diff 门禁（RBL-182/186），±5% 警告
- 行为级：e2e 冒烟集跑优化前后同一 commit，结果一致才全量切换
- 性能级：耗时回归门禁（RBL-198）防优化退化

【度量与终态】
- PR P50：52min → ≤5min；缓存命中率 ≥80%；产物 gzip 差异 ≤1%
- 可观测：阶段耗时 + 命中率时序（RBL-168/190），连续回归告警
```
**评分点**：
- 分阶段且每阶段有改动/收益/风险三要素（不是一锅端）。
- 优化顺序符合投入产出比（缓存并行 → 内核 → 任务缓存）。
- 缓存 key 分层明确且含全局失效手段。
- 有回归防护意识（产物 diff + 行为校验 + 性能门禁）。
- 给出可量化终态指标；能说出"先度量后优化"原则。
