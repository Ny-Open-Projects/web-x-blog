## RBL-862：场景题：发布流水线的检查点设计——每阶段的通过条件与回滚点

**答**:
- 发布流水线（build → verify → stage → canary → prod）的检查点设计原则：每个阶段有「明确的通过条件 + 独立的回滚点」——检查点不是仪式而是「阶段间的合同」：1) build 后：产物审计（体积/闭合/许可 RBL-661/807）；2) verify 后：行为测试 + 语义 diff 基线；3) canary：真实流量指标（错误率/延迟 P95 对比基线 RBL-705）；4) prod 前最后人工确认（canary 指标 review）。
- 回滚点的独立性：每阶段回滚的成本不同（build 后回滚 = 免费；canary 后回滚 = 流量切回；prod 后回滚 = manifest switch RBL-686）——回滚预案与检查点一一绑定，出问题时「在哪一步回滚」不需要现场决策。
- 检查点的自动化与人工的分工：可量化条件自动化（指标门禁），主观判断人工（canary 指标的业务解读）——但人工检查点必须有「数据包」（canary 报告自动生成），不让人从零分析。
- 流水线的可观测：每个检查点的耗时/通过率统计——频繁卡住 human-gate 说明自动化覆盖不足（下一步补自动化）。
- 追问钩子：为什么 canary 阶段的指标要「对比基线」而不是「绝对阈值」？——绝对阈值（错误率 < 1%）在业务高峰期会误报（流量大基数大）或漏报（低流量期样本不足）；对比基线（canary 与 stable 同期 diff）消除了流量/时间因素——「控制变量」是 canary 统计学的核心，也是 A/B 实验与灰度发布的共同基础。

```javascript
// 发布检查点定义
const GATES = [
  { stage: 'post-build', auto: (m) => auditArtifacts(m, budgets).length === 0, rollback: 'free' },
  { stage: 'post-verify', auto: (r) => r.behavior === 'green' && r.semanticDiff.length === 0, rollback: 'free' },
  { stage: 'canary', auto: (metrics, baseline) =>
      metrics.errorRate <= baseline.errorRate * 1.2 &&     // 相对基线（控制变量）
      metrics.p95 <= baseline.p95 * 1.1,
    manual: true, rollback: 'traffic-switch' },
  { stage: 'prod', manual: true, rollback: 'manifest-switch' },
];
async function runPipeline(release) {
  for (const gate of GATES) {
    const pass = await gate.auto?.(release[gate.stage], release.baseline) ?? true;
    if (!pass) return { failed: gate.stage, rollback: gate.rollback };   // 回滚点预定义
    if (gate.manual && !(await humanApprove(gate.stage, report(release))))
      return { failed: `${gate.stage}:manual` };
  }
  return { released: true };
}
```
