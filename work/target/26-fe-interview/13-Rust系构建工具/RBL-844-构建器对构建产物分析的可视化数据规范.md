## RBL-844：场景题：产物分析可视化——treemap 数据结构与交互钻取的规范

**答**:
- 体积分析的 treemap（bundle-analyzer 式）数据规范：1) **层级树**（bundle → chunk → 模块 → 包路径），每节点 `{ id, name, size, children? }`——叶子节点的 size 之和 = 父节点（聚合一致性，不能有「丢失的字节」）；2) gzip 双度量（原始/gzip 切换）；3) 虚拟根（多 entry 产物挂同一个 root）。
- 交互钻取的数据支持：点击节点下钻 = children 展开（数据已含全树，交互只做视图变换）；「搜索定位」需要节点路径索引（path → node 引用 O(1)）；「对比模式」（两次构建的 treemap diff——节点增删/大小变化的着色）需要稳定节点 id（模块 id 跨构建稳定——RBL-571 intern 的 id 在跨构建时不可用，要用内容地址）。
- 大数据的渲染约束：万节点 treemap 全量渲染卡死——**渲染裁剪**（可视区叶子合并：小于阈值像素的节点聚合为「+N more」）；数据与渲染分离（数据全量、渲染分层懒展开）。
- 数据的正确性审计：treemap 数据的「守恒断言」（叶子 size 和 = bundle size，RBL-656 闭合校验的数据版）——聚合不一致的可视化会误导优化决策（数字对不上没人信工具）。
- 追问钩子：为什么「叶子之和必须等于父节点」是可视化工具的生命线？——分析工具的价值在于「找到该优化的字节」，聚合不一致 = 某些字节在树里丢失（ sourcemap 缺失模块/动态代码），用户看到 90% 的体积有归属、10% 凭空消失——「丢失的 10%」恰恰是最该被发现的（往往是 polyfill/运行时代码）；守恒断言逼着工具把每个字节归因。

```javascript
// treemap 数据构建（守恒断言）
function buildTreemap(manifest) {
  const root = { id: 'root', name: 'bundles', size: 0, children: [] };
  for (const f of manifest.files.filter(f => f.type === 'js')) {
    const chunkNode = { id: f.name, name: f.name, size: f.size, children: [] };
    for (const m of manifest.modulesOf(f)) {
      chunkNode.children.push({ id: m.id, name: m.id, size: m.size });
      chunkNode.size += 0;                               // size 由叶子累加
    }
    chunkNode.size = chunkNode.children.reduce((s, c) => s + c.size, 0);
    if (Math.abs(chunkNode.size - f.size) > f.size * 0.02)
      warn(`${f.name} 叶子聚合偏差 ${(chunkNode.size - f.size)}B——存在未归因字节`);
    chunkNode.size = f.size;                             // 以产物为准，偏差标注
    root.children.push(chunkNode);
    root.size += f.size;
  }
  return root;
}
// 渲染裁剪
function cull(node, minPx, depth = 0) {
  if (!node.children || node.size < minPx * (depth + 1)) return { ...node, more: node.children?.length };
  return { ...node, children: node.children.map(c => cull(c, minPx, depth + 1)) };
}
```
