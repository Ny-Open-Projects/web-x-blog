## RBL-673：错误码百科工程化：诊断文档的自动生成与搜索体验

**答**:
- 错误码是用户与工具的「搜索接口」：`RBL1001` 出现在报错里，用户第一动作是搜索——错误码文档必须可直达（错误码 permalink）、内容含「原因/典型场景/修复/相关码」。手工维护文档必腐化，工程化方案是**从诊断定义自动生成**：诊断在源码里单一定义点（code + message 模板 + hint + docs 链接），文档站构建时抽取生成。
- 单一定义点的结构：诊断构造器要求 code 必填且在注册表校验（未注册的 code 构建时报「内部错误」——错误码也是被治理的资产）；文档与代码的同步由 CI 保证（文档站构建依赖核心源码 tag）。
- 搜索体验：错误码精确匹配（RBL1001）之外，还要支持「症状搜索」（用户记不住码，搜「循环依赖警告」）——文档的全文索引 + 诊断 message/hint 的关键词；中文社区还要考虑翻译同步（翻译腐化比英文更常见——用英文源 + 机翻辅助 + 校对标记）。
- 错误码的语义分层设计：前缀段表类别（RBL4xxx=类型相关、RBL2xxx=tree-shaking、RBL3xxx=性能建议），数字段表具体诊断——「段位规划」让错误码可读（看到 4xxx 就知道是 TS/类型问题）。
- 追问钩子：为什么 hint 要「可操作」而非「描述性」？——「 Cannot resolve x」是描述，「npm i x 或检查 alias 配置」是动作；诊断文档的质量指标可以是「用户从报错到解决的平均时长」（telemetry opt-in），驱动 hint 迭代。

```javascript
// 诊断单一定义点 + 文档生成
const DIAGNOSTICS = {
  RBL1001: {
    message: (id) => `Cannot resolve '${id}'`,
    hint: (id) => [`npm i ${id}`, `检查 resolve.alias 与 tsconfig paths`],
    docs: '/diagnostics/RBL1001',
  },
  RBL2001: {
    message: (mod) => `模块 ${mod} 可能包含副作用，未被 tree-shaking`,
    hint: () => [`在 package.json sideEffects 中声明`, `或添加 /*@__PURE__*/`],
    docs: '/diagnostics/RBL2001',
  },
};

function generateDocs() {
  return Object.entries(DIAGNOSTICS).map(([code, d]) => ({
    code,
    section: code.slice(3, 4),                           // 段位分类
    title: d.message(''),                                // 参数示例化
    hints: d.hint(''),
    url: d.docs,
  }));
}
// CI 校验：诊断定义必须在注册表 && 文档站存在对应页面
for (const d of generateDocs())
  if (!docsSiteHas(d.url)) fail(`错误码 ${d.code} 缺文档页`);
```
