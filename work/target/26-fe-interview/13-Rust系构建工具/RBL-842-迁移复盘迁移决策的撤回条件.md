## RBL-842：迁移复盘：迁移决策的撤回条件——什么样的信号应该放弃迁移

**答**:
- 迁移的沉没成本陷阱：投入 3 周后发现不对劲，撤回显得「浪费」——决策要预设「撤回条件」（kill criteria），触达即停：1) **语义不可达**（关键行为差异无法收敛——语义 diff 修复率 < 90% 且剩余项无解）；2) 生态断崖（核心插件无等价物且自研成本 > 收益）；3) 收益证伪（基准测试显示提速 < 2 倍且团队时间成本高——前提失效）；4) 团队风险（关键人离开且知识未沉淀）。
- 撤回的工程动作：不是删除一切——「冻结 + 归档」：迁移分支保留、复盘文档记录「撤回原因 + 已学到的可复用资产」（检查器/测试基建仍是资产）；撤回不等于清零。
- 撤回时机的前置设计：迁移评估阶段（RBL-664）就写 kill criteria 并让决策者签字——事后补的撤回条件是拖延借口；「阶梯检查点」（每阶段门禁 RBL-801 自带撤回评估）。
- 与「坚持」的区分：阻力 ≠ 撤回信号——迁移必然有阻力，撤回条件是「目标不可达」的客观证据（语义不可收敛/收益证伪），不是「进度慢」；区分需要基线数据而非情绪。
- 追问钩子：为什么「收益证伪」要在试点期就验证而不是全量后？——试点期的基准数据是最便宜的证伪点（3 个仓库的成本）；全量后证伪 = 200 仓库成本——kill criteria 的检查点越早越便宜，这与「左移」的测试哲学同构：错误发现得越晚修复越贵。

```javascript
// kill criteria 检查器
const KILL_CRITERIA = [
  { id: 'semantic-reachability', check: (m) =>
      m.semanticDiffFixedRate >= 0.9, signal: '语义差异修复率 < 90% 且剩余无解' },
  { id: 'ecosystem', check: (m) =>
      m.blockingPlugins.every(p => p.alternative || p.customCost < m.benefit), signal: '核心插件无解' },
  { id: 'benefit-proof', check: (m) =>
      m.baseline.speedup >= 2, signal: '基准提速 < 2 倍——前提失效' },
  { id: 'team-risk', check: (m) =>
      m.knowledgeDocumented, signal: '关键知识未沉淀且人员风险' },
];
function killCheck(migration) {
  const failed = KILL_CRITERIA.filter(c => !c.check(migration));
  if (failed.length)
    return { action: 'freeze', reasons: failed.map(f => f.signal),
      salvage: ['检查器/测试基建保留', '复盘文档记录撤回原因'] };
  return { action: 'continue' };
}
```
