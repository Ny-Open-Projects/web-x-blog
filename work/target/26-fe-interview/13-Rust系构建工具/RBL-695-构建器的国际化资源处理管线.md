## RBL-695：构建器的 i18n 资源管线：命名空间切分、按需加载与缺 key 诊断

**答**:
- i18n 资源管线四步：1) **编译期提取**（扫描 t('key') 调用收集使用 key 集合）；2) **按需切分**（命名空间/路由维度把翻译 JSON 拆成懒加载 chunk，只打包使用到的 key——未使用的 key 剔除是体积优化的主力）；3) **校验诊断**（代码用了但翻译缺失的 key = 缺失诊断；翻译有但代码未用 = 冗余诊断，跨语言一致性比对）；4) **产物生成**（每语言 chunk + manifest 映射语言 → URL）。
- 缺 key 的处理策略分层：构建期硬错误（正式语言缺失阻断发布——面向用户的文案不能展示 key）、警告（低优先级语言）、运行时兜底（fallback 语言链 zh→en→key 本身）——策略在构建配置声明（per-language severity）。
- 翻译文件的失效粒度：语言 chunk 独立 hash（RBL-598 级联），改一个翻译只失效对应语言 chunk——把翻译从业务 chunk 中剥离（独立 chunk）是缓存友好的关键；i18n 提取插件的产物是虚拟模块（RBL-612）。
- 动态 key 的边界：`t(dynamicVar)` 无法静态提取——诊断告警（列出位置），要求改用显式映射或维护动态 key 白名单；完全不管会静默丢失文案。
- 追问钩子：为什么「剔除未使用 key」要谨慎？——动态拼接 key（t('status.' + type)）与后端下发文案场景下，静态扫描会误删；工程答案是「显式声明保留集」（reserveKeys）+ 扫描器对动态模式默认保守。

```javascript
// i18n 提取与切分
function extractKeys(code) {
  const keys = new Set(); const dynamic = [];
  const re = /\bt\(\s*(['"])((?:\1)|[^']+?)\1/g;
  let m;
  while ((m = re.exec(code))) {
    const key = m[2];
    if (!key) dynamic.push(m.index);                     // 模板变量 -> 动态告警
    else keys.add(key);
  }
  return { keys: [...keys], dynamic };
}

function buildLocaleChunks(locales, translations, usedKeys, reserve) {
  return Object.fromEntries(locales.map(lang => {
    const all = translations[lang];
    const kept = usedKeys.size
      ? Object.fromEntries(Object.entries(all).filter(([k]) => usedKeys.has(k) || reserve.includes(k)))
      : all;
    const missing = [...usedKeys].filter(k => !(k in all));
    return [lang, { code: JSON.stringify(kept), missing }];
  }));
}
// 诊断：missing 按语言 severity 分级（zh 硬错误 / xx 低优先级警告）
```
