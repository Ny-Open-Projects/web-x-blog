## RBL-717：构建器与安全扫描的集成：依赖审计窗口与产物签名

**答**:
- 构建期安全扫描的定位：不是替代独立安全工具（Snyk/审计数据库），而是在构建热路径上做「低成本高杠杆」检查：1) **已知漏洞依赖**（audit 数据库查询结果缓存，构建时比对 lockfile——查询走缓存不阻塞构建）；2) 产物 SBOM 生成（RBL-659）；3) 产物完整性签名（manifest 带 Ed25519 签名，部署层验签——防产物被篡改后发布）。
- 漏洞依赖的处置分级：critical（阻断构建——已知可利用漏洞不得上线）、high（警告 + 豁免机制带过期）、其他（信息记录）——与体积预算门禁（RBL-662）同构：双轨 + 豁免 + 记录。
- 签名链路：构建器在 CI 内签名（私钥在 CI secret）→ manifest 携带签名 → 部署/CDN 边缘验签 → 不验签拒绝发布——签名解决「产物在构建到部署之间的完整性」。
- 审计窗口（audit window）：漏洞数据库是滚动的，「构建时刻的审计结果」要记录在 manifest（auditAt + 无 critical 声明），部署层可以拒绝「审计过期」的产物（超过 N 天未审计）——把安全合规做成产物元数据。
- 追问钩子：为什么安全检查要在构建期做而不是发布时？——发布时发现 critical 漏洞已经来不及（产物已生成/流程已走完）；构建期阻断让修复发生在 PR（依赖升级 PR 可当轮完成），且构建器有完整依赖图上下文（比发布工具的 lockfile 解析更准）。

```javascript
// 构建期安全门禁
async function securityGate({ lockfile, auditCache, exemptions }) {
  const deps = parseLockfile(lockfile);
  const audit = await auditCache.get(deps, { ttl: 3600 });   // 审计结果缓存（不阻塞热路径）
  const problems = audit.vulnerabilities.filter(v =>
    !exemptions.some(e => e.pkg === v.name && !isExpired(e)));
  const critical = problems.filter(v => v.severity === 'critical');
  if (critical.length)
    throw new Error(`构建阻断（critical 漏洞）: ${critical.map(v => v.name).join(', ')}`);
  return { warnings: problems.filter(v => v.severity === 'high'),
           auditedAt: new Date().toISOString() };
}

// 产物签名
async function signManifest(manifest, { sign }) {
  const body = JSON.stringify(stableStringify(manifest.files));
  manifest.signature = await sign(body);                  // Ed25519（CI secret 私钥）
  manifest.auditAt = audit.auditedAt;
  manifest.noCritical = true;
  return manifest;
}
// 部署层验签：verify(signature, body) 失败 / auditAt 超 7 天 -> 拒绝发布
```
