## RBL-899：终局判断：构建产物一致性守护清单——26 道防线总览

**答**:
- 产物一致性（用户看到的 = 开发者写的）的防线总览，按构建→部署→运行三层组织：
  - 构建层：1) 语义等价测试（RBL-546/655）；2) 确定性构建（543）；3) 最小失效集（635）；4) 导出面契约（715）；5) isolatedModules 诊断（647）；6) 路径安全（659）。
  - 产物层：7) 引用闭合（656）；8) 级联 hash（598）；9) 体积预算（662）；10) 安全模式审计（762）；11) 许可审计（807）；12) SBOM（659）；13) 双产物对齐（700/779）。
  - 部署层：14) 原子产出（583/584）；15) 缓存策略生成（618）；16) CDN 预推顺序（693/694）；17) 灰度锚定（888）；18) attestation（773）；19) sourcemap 绑定（795）。
  - 运行层：20) chunk 守卫（622/623）；21) 能力清单降级（751/724）；22) HMR 失效传播（600）；23) SW 版本协同（707）；24) 离线闭包（897）；25) trace 归因（728）；26) 审计可见化（645）。
- 清单的使用方式：不是「全都要」而是「按风险分级」——金融/支付类全开；内容站保 1/8/14/20；「防线的选择 = 业务的风险画像」——这也是答题时展示判断力的维度（RBL-886 答题框架的 step4）。
- 防线的共同哲学：**每条防线都是「把隐性问题显性化」**——静默错误（半成品产物/缓存污染/泄漏）是事故主因，防线的作用是把它们变成构建红/告警/演练发现。
- 追问钩子：为什么「防线数量」不是目标而是「防线的覆盖率」？——26 道防线覆盖的是「已知的错误模式」；真正的工程能力是「发现新错误模式并把它变成防线」（复盘 RBL-831 的模式化沉淀）——清单是起点不是终点，防线库随组织经验生长。

```javascript
// 防线分级选择
const DEFENSE_TIERS = {
  financial: Object.keys(ALL_DEFENSES),                  // 全开
  content: ['semantic-test', 'cascading-hash', 'atomic-output', 'chunk-guard'],
  internal: ['semantic-test', 'atomic-output', 'accessibility-audit'],
};
function defenseProfile(biz) {
  const tier = DEFENSE_TIERS[biz.riskTier] ?? DEFENSE_TIERS.content;
  const missing = tier.filter(d => !biz.enabled(d));
  return { required: tier, missing, gap: missing.map(d => `${d}: ${ALL_DEFENSES[d].rbl}`) };
}
// 防线注册表（随经验生长）
const ALL_DEFENSES = {
  'semantic-test': { rbl: 'RBL-546', layer: 'build' },
  'cascading-hash': { rbl: 'RBL-598', layer: 'build' },
  'atomic-output': { rbl: 'RBL-583', layer: 'deploy' },
  'chunk-guard': { rbl: 'RBL-622', layer: 'runtime' },
  // ... 26 项
};
```
