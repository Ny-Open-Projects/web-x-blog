## RBL-953：综合深水：构建器的默认值设计——零配置可用与可深调的分层

**答**:
- 默认值设计的分层：1) **零层**（零配置：new 项目 5 分钟跑起来——默认值覆盖 P80 场景：esm 输出/浏览器目标/基础分包）；2) **一层**（声明式意图：`targets: 'modern'`、`mode: 'ssr'`——用户表达意图工具展开细节）；3) **二层**（专家调优：并发/缓存策略/插件时序——默认值最优但可覆盖）。分层的判据是「用户的决策成本」：零层零决策、一层一个意图、二层需要领域知识。
- 好默认值的来源：默认值不是「随便选的合理值」而是「基准测试驱动的最优值」（RBL-650 的一致性）——「默认值更新日志」（升级时默认值变了什么、影响什么）是升级文档的核心段落。
- 默认值的兼容纪律：默认值变更 = 行为变更（semver major 或 flag 双轨 RBL-589）——「默认值漂移」是用户信任的头号杀手（升级后行为悄悄变了）。
- 错误配置的体验：分层设计让「错误配置」也能分层诊断（零层错误给修复命令/二层错误给权衡解释 RBL-829）。
- 追问钩子：为什么「零配置」不是「没有配置」而是「替用户做对了决策」？——零配置的产品价值在于「默认路径的最优性」：用户不配置时的行为 = 我们基准测试过的最优行为（不是「能跑就行」）；esbuild/vite 的零配置口碑来自「默认值就是经过决策的最优解」——默认值是产品承诺而非实现细节，这与 RBL-589 默认值翻转的谨慎一脉相承。

```javascript
// 分层配置 API 设计
export default defineConfig({
  // 零层：什么都不写 → 全部默认
  // 一层：意图声明
  mode: 'ssr',
  targets: 'modern',
  // 二层：专家调优（默认已最优）
  advanced: {
    parallel: { byMemory: true },
    cache: { transformShare: 'global' },
  },
});
// 默认值变更声明（升级文档核心段）
const DEFAULT_CHANGES = {
  '2.0': [
    { key: 'output.sourcemap', from: 'inline', to: 'external',
      impact: '产物不再内联 map——CI 上传 map 的流水线需适配',
      flag: 'sourcemap=inline 可回退一个 minor' },
  ],
};
function defaultChangeDiff(fromVer, toVer) {
  return DEFAULT_CHANGES[toVer]?.filter(c => semverGte(toVer, fromVer)) ?? [];
}
```
