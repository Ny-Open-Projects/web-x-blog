## RBL-618：构建器与浏览器缓存的协商：产物层缓存头的设计责任

**答**:
- 缓存头决策通常在 CDN/网关层，但**只有构建器知道产物的变更语义**——所以现代构建器把「缓存策略元数据」写进产物 manifest（每个文件标注 cacheable: immutable / mutable），部署层照此下发 Cache-Control。hash 文件名 → `max-age=31536000, immutable`；index.html / manifest → `no-cache`（每次回源校验）。
- immutable 的严谨性：文件名带内容 hash 时才敢 immutable——任何「同名覆盖」发布模式（无 hash）都不能下发 immutable，否则用户永远拿旧版；这是「构建器产物形态决定缓存上限」的直接例证。
- 不可 hash 化文件的缓存策略：index.html 用 no-cache（ETag 协商）而非 no-store（利用 304）；service worker 文件必须 no-cache（SW 更新检查语义要求最新）；API 响应与静态产物策略完全不同。构建器能提供的是「文件角色分类」（entry/html/sw/asset/chunk），部署层按角色套模板。
- 304 与「滚动发布」的互动：no-cache + ETag（内容 hash 当 ETag）能优雅处理发布窗口期——旧 ETag 的请求返回 304，新版本用户拿到新 html 引用新 hash 资源；混部期间「新 html 引旧资源」的 404 风险靠「旧版本资源保留 N 个版本」（构建器输出版本保留策略）解决。
- 追问钩子：为什么构建器还要输出 `_headers` / `vercel.json` 类配置？——把缓存策略随产物一起交付（IaC 化），避免「部署平台默认值」与构建器意图不一致；这是 manifest 元数据的消费端。

```javascript
// 产物角色分类与缓存头模板
function emitCacheHeaders(manifest) {
  const POLICY = {
    immutable: 'public, max-age=31536000, immutable',   // hash 文件
    negotiated: 'public, max-age=0, must-revalidate',   // html/sw：ETag 协商
    api: 'no-store',                                    // 动态响应
  };
  return manifest.files.map(f => ({
    path: f.name,
    'Cache-Control':
      f.role === 'entry-html' ? POLICY.negotiated :
      f.role === 'service-worker' ? 'no-cache' :
      f.hash ? POLICY.immutable : POLICY.negotiated,     // 无 hash 文件不敢 immutable
    ETag: `"${f.hash ?? sha(f.content)}"`,               // 内容 hash 即 ETag
  }));
}

// 版本保留策略（滚动发布防 404）
// manifest.versions = { keep: 3 }  // dist 保留最近 3 个版本的旧 hash 文件
// 部署时：新版本文件全量上传 + 旧版本按 keep 清理（过期异步清理，留缓冲窗口）
```
