## RBL-938：综合深水：错误监控闭环——上报到构建修复

**答**:
- 错误监控的六段闭环：1) **采集**（window.onerror/unhandledrejection/资源错误——采样率控制：错误全采 + 噪声丢弃）；2) **反解**（sourcemap 反解 RBL-621——版本绑定）；3) **聚合**（错误指纹：堆栈归一化（去变量名/行号模糊化）→ 分组——「同一 bug 一条 issue」而不是十万条事件）；4) **归因**（buildId/commit/release 关联 RBL-795 + 用户影响面估算）；5) **分发**（新错误 → issue 指派 + 严重度分级——影响面 × 新旧）；6) **修复验证**（修复 release 后错误率曲线下降确认——闭环的最后一环）。
- 指纹归一化的工程细节：堆栈的「噪声源」——行号随构建变化（同源码不同产物）、异步堆栈断裂、浏览器差异——归一化策略：函数名序列 + 源文件（反解后）+ 错误类型，忽略行列；「聚合质量」指标（重复 issue 率）。
- 采样的反直觉：错误不采样（全采）但「日志上下文」采样（全量错误的面包屑太贵）——「错误全采 + 上下文按需补采」的两段式。
- 修复验证的自动闭环：release N+1 部署后监控该指纹的错误率——持续下降 → 自动关闭 issue；不降 → 修复无效重开——「issue 生命周期由数据驱动」。
- 追问钩子：为什么「错误聚合」比「错误上报」更决定监控系统的价值？——上报只是搬运（Sentry 都会）；聚合质量决定「工程师看到的是 3 个真 bug 还是 10 万条噪声」——噪声淹没下的监控系统等于没有；指纹归一化的算法质量（去噪/跨版本稳定性）是监控平台的核心竞争力，与告警降噪（RBL-836）同源。

```javascript
// 错误指纹归一化
function errorFingerprint(err, { sourceMapResolve }) {
  const frames = (err.stack ?? '')
    .split('\n').slice(1, 6)                             // 顶部 5 帧
    .map((l) => {
      const m = /at\s+(\S+)\s+\(?([^):]+):(\d+):(\d+)\)?/.exec(l);
      if (!m) return null;
      const src = sourceMapResolve?.(+m[3], +m[4], m[2]);  // 反解到源码
      return src ? `${src.file}` : stripHash(m[2]);      // 函数名噪声大，文件为主
    })
    .filter(Boolean);
  return hash([err.name, ...frames].join('|'));          // 类型 + 文件链
}
// 修复验证闭环
async function verifyFix(fingerprint, newRelease, monitor) {
  const rate = await monitor.errorRate(fingerprint, { release: newRelease, windowH: 48 });
  const prev = await monitor.errorRate(fingerprint, { release: 'previous', windowH: 48 });
  if (rate < prev * 0.1) await closeIssue(fingerprint, '修复已验证（错误率降 90%+）');
  else if (rate >= prev) await reopenIssue(fingerprint, '修复无效——错误率未降');
}
```
