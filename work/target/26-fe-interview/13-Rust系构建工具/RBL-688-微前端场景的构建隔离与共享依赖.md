## RBL-688：场景题：微前端的构建协同——多团队独立构建下的共享依赖治理

**答**:
- 微前端的构建核心矛盾：各团队独立构建（独立仓库/CI/发布节奏）但共享 react/vue 等基础依赖——共享失败是多实例（内存翻倍+context 断裂），强制统一又锁死发布节奏。治理方案：**版本协商协议**——子应用声明依赖需求（semver 区间），宿主运行时按已加载版本匹配（module federation 的 shared 语义），不匹配才加载子应用自带副本。
- 构建配置的分工：宿主提供「共享注册表」（哪些包可共享 + 版本）；子应用 external 化共享包但声明「fallback 副本」（构建产物内嵌兜底版本，宿主没有时加载）——构建器要支持「双产物」（external 主产物 + 内联 fallback）。
- 样式与全局状态的构建隔离：CSS 转换加 scope 前缀（构建期 postcss 处理，防跨应用污染）；全局变量挂载走沙箱命名空间（构建器注入，如 window.__mf_childA__）。
- 契约测试：宿主与子应用的「接口契约」（挂载函数签名/共享版本区间/事件协议）单独测试（RBL-656 的动态环检查在微前端 chunk 组织下是高频 bug）。
- 追问钩子：为什么微前端里「共享一个 react」需要运行时协商而不是构建期假设？——独立发布意味着「构建时的宿主版本」与「运行时实际版本」必然漂移；协商把漂移变成显式分支（匹配复用/不匹配 fallback），失败模式从崩溃降级为多实例。

```javascript
// module federation 式共享配置
// 宿主（构建器配置）
const hostConfig = {
  exposes: { './layout': './src/Layout.tsx' },
  shared: {
    react: { singleton: true, requiredVersion: '^18.0.0' },
    'react-dom': { singleton: true, requiredVersion: '^18.0.0' },
  },
};
// 子应用：external + fallback 副本
const childConfig = {
  remotes: { host: 'host@/mf-manifest.json' },
  shared: {
    react: { singleton: true, requiredVersion: '^18.0.0',
             fallback: true },                     // 构建产物内嵌兜底副本
  },
};

// 运行时协商（简化）
async function loadShared(name, requiredVersion, loaded) {
  const current = loaded.get(name);
  if (current && semverSatisfies(current.version, requiredVersion))
    return current.module;                           // 版本匹配：复用宿主实例
  return import(`${name}/fallback`);                 // 不匹配：子应用自带副本
}
// 构建期生成 fallback：产物含共享包副本 + 注册元数据（version/requiredVersion）
```
