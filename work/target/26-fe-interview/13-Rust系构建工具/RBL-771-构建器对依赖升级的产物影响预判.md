## RBL-771：依赖升级的产物影响预判：升级 PR 里的「体积与兼容性预检」

**答**:
- 依赖升级（dependabot/renovate PR）的风险预判要在 PR 阶段完成：1) **体积预检**（新版本构建 vs 旧版本——体积 diff 直接挂在 PR comment；依赖体积涨 30% 自动标记 review 必看）；2) 兼容性预检（新版本的 exports 条件变化——原用 `module` 字段改 `exports` 后子路径封装，升级即断）；3) 副作用声明变化（新增 sideEffects: false 但实际有副作用 → tree shaking 误删——语义 diff 捕捉）。
- 预判的数据来源：升级 PR 的 CI 跑「双版本构建对比」（RBL-649 语义 diff + 体积 diff + chunk 移动报告）；lockfile diff 解析（哪些传递依赖被动升级——直接依赖没变但闭包变了的隐性风险）。
- 分级响应：patch 升级（只跑体积 diff + 冒烟）；minor（+ 语义 diff）；major（+ 全量行为测试 + 兼容性矩阵）——CI 成本与风险对齐。
- 批量升级的编排：renovate 的分组策略（devDependencies 批量、生产依赖逐个）——「生产依赖一次升多个」时语义 diff 无法归因（哪个包引入的变化），逐个升级是可归因性的代价。
- 追问钩子：为什么「传递依赖被动升级」是升级风险的暗礁？——直接依赖的 semver 区间允许新版本拉入新传递依赖（间接 breaking）；预检要 diff lockfile 的全量闭包（不只是直接依赖版本），并对比传递依赖的 changelog 风险关键词（「breaking removed deprecated」）。

```javascript
// 升级预检流水线
async function upgradeCheck({ lockBefore, lockAfter }) {
  const changed = lockDiff(lockBefore, lockAfter);       // 直接 + 传递闭包 diff
  const risk = changed.filter(d => d.depth > 1).length;  // 传递依赖被动升级数
  const out = await dualBuild();
  return {
    sizeDelta: out.new.totalKB - out.old.totalKB,
    semantic: classifyDiff(out.old, out.new, []),
    transitiveUpgraded: risk,
    gate: out.new.totalKB - out.old.totalKB > 50 ? 'review-required' : 'auto-merge-ok',
  };
}
// PR comment 模板
// 📦 lodash 4.17.20 -> 4.17.21（patch）
// 体积: +0.3KB；语义 diff: 无；传递依赖: 0
// ✅ 可自动合并
```
