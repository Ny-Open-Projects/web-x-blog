## RBL-789：迁移复盘：迁移工具的复用资产化——从一次性脚本到内部迁移平台

**答**:
- 多仓库迁移的组织级模式：第一个仓库的迁移脚本（配置翻译/检查器/diff 工具）通常是一次性的——第二个仓库开始出现重复劳动，第五个仓库时「迁移平台」的投入产出才为正——资产化的触发时机是「第三次重复」（Rule of three）。
- 迁移平台的组成：1) **检查器库**（兼容扫描/配置翻译/语义 diff——RBL-664/666/649 的通用化）；2) 状态跟踪（每个仓库的迁移进度看板：阶段/负责人/阻塞项）；3) 报告生成（统一格式的迁移 PR 描述模板）。
- 资产化的工程纪律：迁移脚本从仓库内的 scripts/ 提升到内部 npm 包（版本化）；脚本里的「仓库特定逻辑」参数化（配置文件路径/入口名——迁移配置而非硬编码）；测试随脚本走（迁移工具有自己的单测——它自己也要可靠）。
- 平台的边界：不追求「全自动迁移」（语义判断总需人工），目标是「人工只做决策，机械部分全部工具化」——迁移平台度量自己的价值：每仓库人工工时的下降曲线。
- 追问钩子：为什么迁移工具自身需要测试与版本化？——迁移工具的错误是「静默错」高发区（翻译器漏转换不报错，RBL-666 的哲学）；它被多仓库信任复用，一次工具 bug = N 个仓库错误；工具的可靠性标准应该与构建器自身一致（fixture + 回归）。

```javascript
// 内部迁移平台 CLI
// @internal/migrate
export async function migrate(repo, { from, to, dryRun = true }) {
  const plan = await assess(repo, { from, to });          // 评估（RBL-664）
  const report = { plan, steps: [] };
  for (const step of plan.steps) {
    const result = await step.run({ dryRun });             // 翻译/替换（RBL-666）
    report.steps.push({ id: step.id, ...result });
  }
  report.diff = await semanticDiff(repo, { from, to });    // 验证（RBL-649）
  writeReport(`migrate-report-${repo}.json`, report);
  return dryRun ? report : applyAndCommit(report);
}
// 看板数据源：各仓库 report 汇总
const board = repos.map(r => ({ repo: r.name, stage: r.report.plan.stage, blocked: r.report.plan.blocked }));
console.table(board);
```
