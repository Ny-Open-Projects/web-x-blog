## RBL-659：构建器的安全边界：路径穿越、虚拟模块注入与供应链防线

**答**:
- 构建器的攻击面常被低估：1) **路径穿越**——alias/glob/exports 通配符解析出 `../` 逃出项目根，读到 CI 里的密钥文件并打进产物（`.env` 被意外打包是真实事故类别）；防线：resolve 结果做「根内校验」（canonicalize 后前缀检查），glob 目录参数锁定。
- 虚拟模块注入：插件返回的代码是「完全信任的代码」——恶意插件（或被劫持的插件）可注入任意运行时代码；防线是插件审计（RBL-653）+ 产物 diff 审查（未知模块出现在产物中要告警）。
- env 泄漏：`process.env` 被 define 全量注入（webpack 的 DefinePlugin `process.env` 整对象替换）→ 密钥进产物；防线：构建器默认拒绝 `define: { 'process.env': ... }` 整对象（只允许白名单前缀），诊断码明确提示。
- 供应链纵深：依赖解析（node_modules 内包名劫持/typosquatting）在构建期执行任意代码（postinstall）——构建器的贡献是「锁文件严格化 + 完整性校验」与「产物依赖清单」（sbom 输出：哪些包进了产物，供安全扫描）。
- 追问钩子：为什么「构建产物的 SBOM」重要？——产物直接面向用户，其依赖组合与 package.json 不一致（tree shaking 后只剩部分包）；安全事件（某包 CVE）发生时，SBOM 才能回答「我们的产物里有没有它」——这是构建器独有的可观测性贡献。

```javascript
// 路径穿越校验
function assertInsideRoot(resolved, root) {
  const rel = path.relative(root, resolved);
  if (rel.startsWith('..') || path.isAbsolute(rel))
    throw new Error(`路径越界: ${resolved} 超出项目根 ${root}`);
  return resolved;
}
// alias 解析后校验：
// resolveAlias('@shared/util') -> '/src/../secrets'  ✗ 抛错

// define 白名单防线
function validateDefine(define) {
  for (const key of Object.keys(define)) {
    if (key === 'process.env')
      throw new Error('禁止整对象注入 process.env——请逐个声明所需变量，防止密钥进产物');
    if (/^process\.env\.\w+$/.test(key)) continue;      // 单变量白名单
  }
}

// SBOM 输出
function emitSBOM(graph) {
  const pkgs = new Map();
  for (const mod of graph.modules())
    if (mod.inNodeModules) {
      const pkg = pkgOf(mod.id);
      pkgs.set(pkg.name + '@' + pkg.version,
        [...(pkgs.get(...) || []), mod.id]);
    }
  fs.writeFileSync('dist/sbom.json', JSON.stringify({
    format: 'cyclonedx-lite',
    components: [...pkgs.keys()],
  }));
}
```
