## RBL-587：构建器的性能回归防线：基准套件、噪声控制与归因流程

**答**:
- 构建器迭代频繁，性能回归必须像功能回归一样有 CI 防线：**基准套件**（固定输入集：小/中/大仓库 + 特征化场景：海量小模块/深层循环依赖/巨型单文件）× 每次 PR 跑构建，超阈值（如 +5%）即阻塞合并。
- 噪声控制是基准可信的前提：1) 固定机器规格与隔离（CI 专用 runner，禁共享）；2) 多次运行取中位数（≥5 次），报 p50/p90 而非单次；3) 预热（首轮 page cache 冷；分 cold/warm 两组报告）；4) 关闭无关干扰（并行任务的 CPU 抢占）；5) 用 CPU 时间 + wall time 双指标（虚机 wall time 噪声大）。
- 归因流程：回归确认 → 二分定位提交（bisect 自动化）→ 火焰图/profile 对比回归前后 → 输出归因报告（哪个阶段哪个函数）；没有归因的「性能修复」往往是瞎猜。
- 指标选择：总构建时间之外，要盯「阶段分解」（resolve/transform/chunk/codegen 各占多少）与内存峰值（RBL-569）——总时间掩盖结构性劣化（resolve 翻倍但并行 transform 提速抵消）。
- 追问钩子：与用户侧性能基准的关系——构建器自己的 benchmark 是开发者体验指标；业务侧的「接入前 vs 接入后」对比（真实项目迁移）才是用户价值证明，两者都要做但数据不可混用。

```javascript
// 基准运行器（PR CI 概念）
const SUITES = [
  { name: 'small-app', input: 'bench/small', runs: 7 },
  { name: '10k-modules', input: 'bench/large', runs: 7 },
  { name: 'deep-cycle', input: 'bench/cycle', runs: 7 },
];

async function benchOne(suite) {
  await build(suite.input);                        // 预热（warm 组）
  const times = [];
  for (let i = 0; i < suite.runs; i++) {
    dropOsCache();                                  // cold 组由 runner 单独测
    const t0 = process.hrtime.bigint();
    await build(suite.input);
    times.push(Number(process.hrtime.bigint() - t0) / 1e6);
  }
  times.sort((a, b) => a - b);
  return { p50: times[Math.floor(times.length / 2)], p90: times[Math.floor(times.length * 0.9)] };
}

// 回归判定与基线对比
const result = await runAll(SUITES);
const baseline = loadBaseline('main');              // 主干基线（每日定时刷新，防基线本身回归）
for (const s of SUITES) {
  const delta = result[s.name].p50 / baseline[s.name].p50 - 1;
  if (delta > 0.05) fail(`性能回归 ${s.name}: +${(delta * 100).toFixed(1)}%`);
}
```
