## RBL-836：场景题：构建告警体系——CI 构建失败的通知分级与降噪

**答**:
- 构建失败的通知分级：1) **主干失败**（P0：全员即时通知——阻塞所有人的合入）；2) **PR 失败**（P2：只通知 author——PR 失败是正常流程不是事故）；3) **定时任务失败**（夜间构建/基线任务：P1 通知值班——不及时处理会污染基线）；4) flaky 失败（重试后通过：聚合报告不即时通知——flaky 通知是告警疲劳的头号来源）。
- 降噪三原则：1) **同因合并**（同一错误码短窗口内的多次失败合并成一条通知 + 计数）；2) 责任路由（失败归因到最近合入者——blame 信息进通知，而不是全员广播）；3) 恢复通知（失败后恢复也要通知——「还在挂吗」的心理负担消除）。
- 告警疲劳的度量：通知的「行动率」（收到通知后是否处理）——低行动率的通知类别自动降级（从即时改为日报）；告警体系自身要有指标（RBL-705 的元指标）。
- 失败归因的技术：错误指纹（错误码 + 关键 token 哈希）→ 与「该 PR 合入前后的失败」关联（合入前绿合入后红 = 高置信归因）——归因到 PR 而非「最新失败者」的公平性。
- 追问钩子：为什么 flaky 不即时通知？——flaky 的行动是「进 flaky 库批量治理」（RBL-，测试系列的根因库）而非即时修复；即时通知让它混入 P0 流，团队对构建通知的敏感度被稀释——告警系统的最大敌人是「狼来了」，分级与降噪是保护 P0 信号的信噪比工程。

```javascript
// 告警分级路由
const ROUTES = [
  { when: (e) => e.branch === 'main', level: 'P0', channel: 'im-immediate',
    notify: (e) => `@channel 主干构建失败 ${e.fingerprint} 归因: @${e.blame}` },
  { when: (e) => e.flaky, level: 'flaky', channel: 'batch-report',
    notify: (e) => `[flaky] ${e.test} 第 ${e.occurrences} 次——入根因库` },
  { when: (e) => e.scheduled, level: 'P1', channel: 'oncall' },
  { when: () => true, level: 'P2', channel: 'author-only',
    notify: (e) => `@${e.author} 你的 PR 构建失败: ${e.firstError}` },
];
function routeAlert(e, routes = ROUTES) {
  const r = routes.find(r => r.when(e));
  const merged = alertWindow.merge(r.level, e.fingerprint);    // 同因合并
  if (merged.suppressed) return null;                    // 短窗口去重
  return { level: r.level, channel: r.channel, message: r.notify(e), count: merged.count };
}
```
