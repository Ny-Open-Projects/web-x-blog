## RBL-739：产物体积归因报告：从「总量超标」到「哪个依赖贡献了多少字节」

**答**:
- 体积归因的层次：bundle 总量 → chunk 分布 → 模块贡献（每个模块产出的压缩/未压缩字节）→ 依赖包聚合（lodash 各模块归到 lodash）→ 来源分类（业务/vendor/复制代码）。构建器输出的是「可下钻的树」，analyze 工具（source-map-explorer 类）只是消费端。
- 归因的技术基础：1) 模块 → 产物字节映射（codegen 时记录每模块的输出 span——不做 sourcemap 也能算）；2) 压缩前后双报告（gzip 报告才是网络视角，未压缩报告定位重复代码）；3) 复制代码的标注（多 chunk 内联复制 RBL-597 的模块要在报告里标 duplicated）。
- 报告的可执行性：归因的终点是「行动建议」——`lodash: 70KB（用了 12/600 个函数，全量打包）→ 建议按需导入或换 lodash-es`；`moment: 90KB（locale 全量）→ 建议忽略 locale`——把「体积异常」翻译成「具体优化动作」。
- 报告的时间维度：单次报告之外，趋势对比（与上次 release 的 diff——哪个依赖涨了）才能驱动持续治理；与 CI 门禁联动（RBL-662 预算超标时附归因报告，评审有的放矢）。
- 追问钩子：为什么「压缩后体积」归因更难也更真实？——压缩/摇树后的产物才是传输现实，但模块边界在压缩后消失（变量名混淆）；解法是 codegen 阶段记录映射（或 sourcemap 反推 RBL-608）——体积工具链的精度差异常源于此。

```javascript
// 归因报告生成
function sizeReport(chunks, modules, { gzip = true } = {}) {
  const byModule = new Map(), byPkg = new Map();
  for (const chunk of chunks)
    for (const m of chunk.modules) {
      const bytes = chunk.spanOf(m)?.length ?? sizeOf(modules[m].code);
      byModule.set(m, (byModule.get(m) || 0) + bytes);   // 复制模块会累加（含 duplicated 标注）
      const pkg = pkgOf(m);
      byPkg.set(pkg, (byPkg.get(pkg) || 0) + bytes);
    }
  const rows = [...byPkg.entries()]
    .map(([pkg, bytes]) => ({ pkg, rawKB: kb(bytes), gzipKB: kb(gzipSize(byPkgCode(pkg))) }))
    .sort((a, b) => b.gzipKB - a.gzipKB);
  return { rows, advice: rows.slice(0, 5).map(adviceFor) };
}
const adviceFor = (row) =>
  /moment/.test(row.pkg) ? 'moment locale 全量——建议 ignore locale 或换 dayjs'
  : /lodash(?!-es)/.test(row.pkg) ? 'lodash 全量——建议 lodash-es 按需'
  : row.rawKB > 200 ? `${row.pkg} 体积过大——检查是否误打包动态依赖`
  : null;
```
