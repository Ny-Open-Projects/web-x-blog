## RBL-635：增量编译的失效算法：从单文件变更到依赖闭包的最小失效集

**答**:
- 文件变更后的最小失效集计算：变更文件 F → 重新 transform F → 若 F 的**导出面与依赖列表不变**，失效范围仅 F 自身；若导出签名变化（删了导出/改了导出名），所有 import 该导出的模块都要失效——「失效传播 = 语义变化量」，而不是「改了就全量失效」。
- 三级失效粒度：1) 内容变但语义不变（注释/空白）→ 仅重写产物内容（甚至可跳过）；2) 模块内部变化、接口不变 → 该模块 + 该模块所在 chunk 重生成；3) 接口变化 → 反向引用传播（importers 闭包）+ chunk 级联。构建器需要「模块接口指纹」（导出名集合 + 类型信息）参与失效判定。
- 依赖闭包的动态性陷阱：新增 import（F 引用了新模块 G）→ 不只是 F 失效，chunk 分割结果可能变化（G 的加入改变引用计数）→ 保守起见 chunk 层重算，但模块级缓存（G 的 transform）仍可复用。
- 环上的失效：循环依赖里 A 改导出、B 依赖 A——B 失效后又引 A，传播要在 SCC 内收敛（访问集合去重），不能无限传播（RBL-601 的 HMR 传播同构，这里管增量重编译）。
- 追问钩子：为什么「失效最小化」要和「正确性保守化」平衡？——漏失效是静默错误（用户看到旧代码），过失效只是性能损失；所以**接口级判定存疑时向保守降级**（接口指纹不完整就按内容变化处理），并把「缓存命中率」做成可观测指标（漏失效可通过产物 diff 测试捕获，见 RBL-546）。

```javascript
// 最小失效集计算
function computeInvalidation(changedFile, graph, prevMeta) {
  const stale = new Set([changedFile]);
  const newMeta = analyze(changedFile);                  // { exports, imports }
  const oldMeta = prevMeta.get(changedFile) ?? { exports: [], imports: [] };

  const exportsChanged = diffSet(oldMeta.exports, newMeta.exports);
  const importsChanged = diffSet(oldMeta.imports, newMeta.imports);

  if (exportsChanged.size === 0 && importsChanged.size === 0)
    return { retransform: [changedFile], rechunck: false };   // 接口不变：最小失效

  if (importsChanged.size) {
    // 新依赖 -> chunk 结构可能变
    return { retransform: stale, rechunck: true };
  }
  // 导出变化 -> 反向传播
  const propagate = (id, seen) => {
    for (const imp of graph.importersOf(id)) {
      if (seen.has(imp)) continue;                       // 环收敛
      seen.add(imp); stale.add(imp);
      propagate(imp, seen);
    }
  };
  propagate(changedFile, new Set([changedFile]));
  return { retransform: [...stale], rechunck: true };
}
// diffSet 返回变化的成员（新增+删除），用于区分「语义变」与「内容变」
```
