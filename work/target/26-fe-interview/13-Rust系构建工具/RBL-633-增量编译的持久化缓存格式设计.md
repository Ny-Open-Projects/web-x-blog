## RBL-633：增量编译的持久化缓存格式设计：条目结构、版本戳与懒校验

**答**:
- 持久化缓存（.rspack-cache / .vite-optimize）的条目结构：`{ key, value, deps: 指纹列表, meta: { tool version, profile } }`——key 是输入指纹（源码 hash + 配置片段 + 插件版本），value 是产物（transform 后代码/AST 序列化），deps 是「该条目依赖的其他文件指纹」（缓存失效是闭包判定不是单点判定）。
- 版本戳（tool version + 格式 version）必须参与 key：工具升级后旧缓存格式可能语义漂移（转换规则变了）——不兼容即整体作废（简单可靠），细粒度版本兼容收益低风险高。
- 懒校验（lazy validation）是性能核心：重启时**不校验全部缓存**（O(模块数) 的 IO），只校验「本次构建要用的条目」——第一次命中才查指纹；配合 mtime 快路径（mtime+size 未变直接信任，避免逐文件 hash）——mtime 不可靠的场景（git 操作会动 mtime）才回退内容 hash。
- 一致性风险与对策：1) 部分写入（进程崩溃）→ 单条目原子写（tmp+rename）+ 目录级 manifest；2) 并发写（两个构建进程）→ 文件锁或按 key 分片写无竞争；3) 缓存膨胀 → LRU 清理（按 lastAccess）+ 总量上限。
- 追问钩子：为什么「缓存了 AST」的收益常常不如预期？——AST 序列化/反序列化成本接近重新 parse（bumpalo arena 的 AST 无法直接 memcpy）；更有效的是缓存「transform 产物字符串 + sourcemap」（跳过的是转换计算而非 parse）。

```javascript
// 缓存条目读写（单条目原子性）
class PersistentCache {
  #dir; #version;
  async get(key, validateDeps) {
    const file = `${this.#dir}/${sha(key)}.json`;
    if (!fs.existsSync(file)) return null;
    const entry = JSON.parse(fs.readFileSync(file));
    if (entry.version !== this.#version) return null;          // 版本不兼容即弃
    if (!entry.deps.every(d => fingerprintMatch(d))) return null;  // 闭包指纹校验
    return entry.value;
  }
  async set(key, value, deps) {
    const file = `${this.#dir}/${sha(key)}.json`;
    const tmp = file + '.tmp';
    fs.writeFileSync(tmp, JSON.stringify({
      key, value,
      deps: deps.map(d => ({ path: d, hash: quickHash(d) })),   // mtime+size 快指纹
      version: this.#version, at: Date.now(),
    }));
    fs.renameSync(tmp, file);                                   // 单条目原子替换
  }
}
// 快指纹：
function quickHash(p) { const st = fs.statSync(p); return `${st.mtimeMs}:${st.size}`; }
// 校验时 mtime+size 一致即信任；不一致才读内容 hash（懒校验的慢路径）
```
