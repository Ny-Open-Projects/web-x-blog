## RBL-760：环境变量注入的分层设计：构建期/运行时/边缘的变量边界与类型安全

**答**:
- 环境变量的三层边界：1) **构建期内联**（PUBLIC_* 前缀，define 替换——变更需重新构建）；2) **运行时读取**（window.__ENV 注入或 config endpoint 拉取——同产物多环境部署）；3) **边缘/服务端**（process.env 只在 SSR/edge 代码合法，混入 client 代码 = 泄漏 + 报错）。构建器的职责是「边界校验」：client 产物引用 process.env.PRIVATE_* 直接诊断错误。
- 类型安全：环境变量声明文件（env.d.ts 或 schema）→ 构建器校验「代码引用的变量都在声明里」（拼错变量名是静默 undefined——TS 只对 import.meta.env 有类型，裸 process.env 无）——声明驱动的诊断 + 生成类型。
- 注入的确定性：构建期注入值参与产物内容（hash 联动）——「同代码不同环境值」会产生不同产物 hash（缓存失效）；多环境部署场景应把环境值移到运行时层（产物一份、环境多份）——这是「构建期 vs 运行时」的分界判据：值随环境变的 → 运行时。
- 脱敏防线：整对象注入拒绝（RBL-660）+ 前缀白名单 + 「构建日志不打印变量值」——日志泄漏密钥是 CI 事故源。
- 追问钩子：为什么「随环境变的值」不该构建期内联？——内联把环境维度编译进产物：5 个环境 = 5 次构建 = 5 份缓存；运行时注入（config endpoint 或 window.__ENV）让「一次构建多环境部署」成立——部署效率与缓存效率都赢，代价是首屏多一个 config 请求（可内联进 HTML）。

```javascript
// 环境变量边界校验
function validateEnvUsage(code, { declared, layer }) {
  const problems = [];
  for (const m of code.matchAll(/process\.env\.(\w+)/g)) {
    const name = m[1];
    if (layer === 'client')
      problems.push(`client 代码引用 process.env.${name}——改用 import.meta.env 或运行时注入`);
    if (name.startsWith('PRIVATE_') && layer !== 'server')
      problems.push(`PRIVATE_ 变量 ${name} 泄漏到 ${layer} 层`);
    if (!declared.includes(name))
      problems.push(`未声明变量 ${name}——请在 env.d.ts 声明（防拼错静默 undefined）`);
  }
  return problems;
}
// 类型生成
function generateEnvTypes(declared) {
  return `interface Env { ${declared.map(v => `${v}: string`).join('; ')} }
declare const __ENV: Partial<Env>;
export const env: Env = new Proxy({} as Env, { get: (_, k) => { 
  if (!(k in __ENV)) throw new Error(\`env.\${String(k)} 未注入\`);
  return __ENV[k]; } });`;   // 运行时缺变量显式报错（而非 undefined 传播）
}
```
