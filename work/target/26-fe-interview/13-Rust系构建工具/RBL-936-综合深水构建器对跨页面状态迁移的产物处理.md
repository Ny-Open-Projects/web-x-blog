## RBL-936：综合深水：跨页面状态迁移——列表锚点与表单草稿恢复协议

**答**:
- SPA 跨页状态恢复的三类场景：1) **列表锚点**（列表页 → 详情 → 返回：滚动位置 + 筛选条件 + 已加载数据恢复——「快照协议」：列表状态序列化进 history.state 或 store 快照栈）；2) **表单草稿**（意外离开的草稿保留——debounce 持久化 + 恢复提示）；3) **跨标签同步**（storage 事件广播）。构建器的角色较薄（协议是运行时），但产物层的「状态序列化安全」是构建相关：history.state 的体积限制（浏览器 ~640KB）、敏感数据不入 state（token 进 state = 历史记录泄漏）。
- 快照协议的设计：快照键（路由 + 查询参数的 hash）、快照生命周期（push 时入栈/pop 时取用——返回导航才恢复，前进新导航丢弃）；「快照过期」（数据时效：30 分钟前的列表快照要重新拉数据还是直接用——按业务）。
- 恢复的数据一致性：快照数据 vs 服务端现状（商品下架了）——恢复策略分级（缓存数据先渲染 + 后台刷新 + diff 更新——乐观恢复）；「快照版本标记」（数据拉取时间戳）。
- 构建期审计：state 序列化的体积（大列表全量入 history.state 会爆——只存游标 + 已加载数据存 store）；敏感字段扫描（token/userId 进 state 的诊断——RBL-760 泄漏检测的 state 版）。
- 追问钩子：为什么「敏感数据不入 history.state」？——history.state 会进浏览器历史（用户共享电脑/同步浏览器 = 数据跨设备泄漏）；且 history.state 可被扩展程序读取；「状态序列化的安全面」与 localStorage 同级——快照协议要有「字段白名单」（可序列化的业务数据）而非「全量序列化」——序列化边界的安全审计（RBL-659 哲学）。

```javascript
// 列表快照协议
class ListSnapshot {
  static save(routeKey, { scrollY, filters, items, cursor, ts }) {
    const safe = { scrollY, filters, cursor, ts,
      itemIds: items.map(i => i.id),                  // 不存全量数据（体积与安全）
      items: sanitize(items),                          // 字段白名单
    };
    history.replaceState({ listSnapshot: safe }, '');
    store.set(routeKey, safe);                         // 大数据进 store，state 只存游标
  }
  static restore(routeKey, { maxAgeMs = 30 * 60000 } = {}) {
    const snap = history.state?.listSnapshot ?? store.get(routeKey);
    if (!snap || Date.now() - snap.ts > maxAgeMs) return null;   // 过期不恢复
    return snap;
  }
}
// 构建期审计：state 敏感字段
function auditStateFields(code) {
  const SENSITIVE = /token|secret|password|credit/i;
  return [...code.matchAll(/history\.(?:replace|push)State\(\s*\{([^}]*)/g)]
    .flatMap(m => [...m[1].matchAll(/(\w+)\s*:/g)].map(k => k[1]))
    .filter(k => SENSITIVE.test(k))
    .map(k => `敏感字段 ${k} 不得入 history.state（历史记录泄漏）`);
}
```
