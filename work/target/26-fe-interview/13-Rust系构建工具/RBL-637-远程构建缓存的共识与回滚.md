## RBL-637：远程构建缓存的工程化：上传竞争、签名校验与灰度回滚

**答**:
- 远程缓存（turbo remote cache/s3）的核心风险不是「缓存丢失」而是「缓存污染」：错误的产物被缓存后，会随命中扩散到整个团队/所有 CI——所以远程缓存的安全设计优先于性能设计。
- 防污染三件套：1) **键完整性**（RBL-582 的多源指纹——env 白名单遗漏是污染主因）；2) **上传签名与校验**（产物打包带 hash 清单，下载后逐文件校验——防传输损坏与恶意替换）；3) **写入权限分级**（主分支 CI 可写、开发者本地只读或受限写——防止本地脏环境污染共享缓存；turbo 的 signed artifacts 模式）。
- 上传竞争：同键并发上传（两个 PR 改同一文件）——解法是「内容寻址幂等上传」（同 hash 覆盖无害）+ 上传去重（服务端 304/ETag 判定）；下载与上传解耦，命中判定靠键不靠新鲜度。
- 灰度与回滚：缓存是「数据」，可以像代码一样回滚——维护「缓存发布日志」（键→产物版本），出现污染事故时按时间窗失效（invalidate before T）；团队级「逃生开关」（禁用远程缓存 env 一键回退本地构建）是运维底线。
- 追问钩子：为什么远程缓存的命中率监控要按「团队/分支/任务类型」分桶？——混合均值掩盖问题（monorepo 主仓 95% 命中率下藏着某子任务 0% 命中的 bug）；分桶后才能定位「键计算错误」vs「真实无复用」。
- 安全细节：缓存产物是**可执行代码**——从缓存恢复产物目录相当于「运行第三方构建结果」，所以签名校验不是可选项；这也是 GitHub Actions 缓存投毒（cache poisoning）攻击的防线。

```javascript
// 远程缓存客户端（签名校验 + 幂等上传）
class RemoteCache {
  async fetch(key) {
    const res = await this.get(`/artifacts/${key}`);
    if (!res) return null;
    const bundle = await unzip(res.body);
    const manifest = JSON.parse(bundle.get('manifest.json'));
    for (const [f, h] of manifest.hashes)               // 逐文件校验
      if (sha256(bundle.get(f)) !== h) throw new Error(`产物校验失败: ${f}（可能被篡改或损坏）`);
    return bundle;
  }
  async put(key, files) {
    const manifest = { hashes: Object.fromEntries(files.map(f => [f.name, sha256(f.content)])) };
    const body = zip([...files, { name: 'manifest.json', content: JSON.stringify(manifest) }]);
    const res = await this.request(`/artifacts/${key}`, { method: 'PUT', body });
    if (res.status === 304) return 'dedup';             // 服务端已存在（幂等）
    return 'stored';
  }
}
// 权限模型（CI 侧）
// env TURBO_REMOTE_CACHE_SIGNATURE=true + 只读 token（开发者本地）
// 主分支 runner 持写 token + PR runner 只读（防 PR 投毒）
```
