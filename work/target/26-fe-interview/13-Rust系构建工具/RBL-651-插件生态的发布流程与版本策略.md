## RBL-651：插件的发布流程工程：版本策略、peer 约束与废弃管理

**答**:
- 构建器插件的版本耦合比普通 npm 包更强：插件依赖核心的**钩子 API 语义**，核心 minor 升级可能改变钩子行为（新字段/新返回值协议）——插件正确声明 peerDependencies（"rolldown": ">=1.0 <2"）且 CI 里跑「核心版本矩阵测试」（当前 major 各 minor 各跑一遍插件测试集）。
- 废弃管理：插件作者停止维护是常态——生态级解法：1) deprecated 标记（npm deprecate + README 置顶）；2) 核心内置「废弃插件诊断」（构建时检测已废弃插件并建议替代）；3) 组织内「插件注册表」（内部源维护已审计插件清单与替代关系）——企业场景比公共生态更可控。
- 发布流水线：插件要有「兼容性 changelog」（钩子行为变化标 breaking）；semver 严格性比普通包高（因为被 CI 依赖链放大）；发布前置检查（对最新核心版本跑测试 + 对最低声明版本跑测试——两端验证）。
- 内部插件的分发：企业内不用 npm 公网——私有 registry（verdaccio/artifactory）+ scope 命名规范；「插件市场」的元数据（用途/维护者/质量分）降低选型成本。
- 追问钩子：为什么插件测试要跑「核心版本矩阵」而普通库不用？——普通库依赖稳定 API，插件依赖的是「正在快速演进的平台」，平台每次升级都是兼容性测试日；矩阵测试把「生态兼容问题」在插件侧提前暴露，而不是等用户升级核心后炸。

```javascript
// 插件 CI 的核心版本矩阵
const CORE_VERSIONS = ['1.0.0', '1.1.0', '1.2.0'];       // peer 声明范围内
for (const v of CORE_VERSIONS) {
  await exec(`pnpm add -D rolldown@${v}`);
  const ok = await runTests('./tests');                  // 插件自己的测试集
  if (!ok) fail(`rolldown@${v} 下插件测试失败 —— peer 范围需收紧或修复`);
}
// 发布前置检查
// 1) npm view rolldown version -> 最新版冒烟
// 2) peer 声明的最低版本冒烟
// 3) changelog 中 breaking 检查（commit-lint 强制 BREAKING CHANGE 标注）

// 废弃诊断（核心内置）
function checkDeprecatedPlugins(plugins) {
  for (const p of plugins) {
    const meta = registry.get(p.name);                   // 内部注册表
    if (meta?.deprecated)
      warn(`插件 ${p.name} 已废弃，替代方案：${meta.replacedBy}（移除原因：${meta.reason}）`);
  }
}
```
