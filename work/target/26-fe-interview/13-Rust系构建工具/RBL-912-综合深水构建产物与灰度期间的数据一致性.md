## RBL-912：综合深水：灰度期间的数据一致性——新旧版本并存

**答**:
- 灰度期间（新旧产物并存，RBL-888）的数据面问题：1) **埋点统计**（新旧版本的事件 schema 不同——统计口径分裂：埋点事件带 version 字段，分析侧按版本分桶；「旧版本事件在灰度结束后仍流入」的长尾处理）；2) **本地存储 schema**（localStorage/IndexedDB 的结构 v1→v2：迁移函数 + 向后兼容读——「版本标记 + 迁移链」）；3) **API 契约**（新旧前端对同一后端——后端字段变更必须兼容两个版本窗口期）。
- 存储迁移的构建配合：schema 版本声明进产物常量；迁移函数链（v1→v2→v3 逐级）在启动时执行——「迁移失败不丢数据」（迁移前快照 + 失败回退旧 schema 读）。
- 埋点长尾：灰度结束 ≠ 旧版本消失（用户不刷新页面）——旧版本事件可能流入数天：统计口径的分桶必须按 buildId（RBL-795 release 绑定）而不是「当前版本」——「数据的时间维度」是灰度统计的常见盲区。
- 灰度决策的数据可信性：新旧版本的转化率对比要「同质样本」（分桶 RBL-881）——设备/地域/流量渠道混杂会得出错误结论。
- 追问钩子：为什么「埋点按当前版本分桶」是灰度统计的经典错误？——「当前版本」在灰度期间是个混合态（70% 旧 + 30% 新），按当前版本分桶 = 新旧数据混在一起；正确键是「产生事件的产物版本」（buildId 随事件上报）——数据的时间与版本维度错配会让 A/B 结论完全失真；这与 RBL-795 的 release 绑定一脉相承。

```javascript
// 存储迁移链
const MIGRATIONS = {
  1: (v1) => ({ ...v1, v: 2, cartItems: v1.cart ?? [] }),       // v1->v2
  2: (v2) => ({ ...v2, v: 3, currency: 'CNY' }),                // v2->v3
};
function migrateStorage(raw, { snapshot = true } = {}) {
  let data = raw;
  const from = data?.v ?? 1;
  if (snapshot) saveSnapshot(raw);                       // 迁移前快照
  for (let v = from; v < CURRENT; v++) {
    try { data = MIGRATIONS[v](data); }
    catch (e) {
      restoreSnapshot();                                 // 失败回退：按旧 schema 读
      return { data: raw, migrated: false, from };
    }
  }
  return { data, migrated: true };
}
// 埋点带版本
track('purchase', { amount, __build: window.__BUILD_ID });   // 版本分桶键
```
