## RBL-683：场景题：低代码平台的动态打包服务——多租户实时构建架构

**答**:
- 场景：低代码平台用户每次「发布」都触发构建（schema → bundle），数千租户并发——架构核心：1) **构建即服务**（构建器常驻进程池/独立容器，任务队列按租户隔离）；2) **schema 指纹缓存**（schema 未变直接返回上次产物，低代码场景改动小、命中率极高）；3) 冷热分离（首次构建走常驻 worker，重构建走弹性池）。
- 构建器形态选择：常驻 Rust 构建器进程（比冷启动 NAPI 快一个量级）+ 任务级隔离（每任务独立 arena/虚拟 FS）；泄漏防线（RBL-561 arena 生命周期绑定任务）——长驻进程最大的坑是「内存随任务数增长」。
- 多租户的配置隔离：租户配置（主题 token/自定义组件）注入为虚拟模块（RBL-612），配置变更即虚拟模块失效——每个租户是一份独立「配置快照」，不能共享可变状态。
- SLA 设计：发布请求分级（预览构建 P2：秒级可接受；正式发布 P0：限时完成）——队列优先级调度（RBL-565）；构建超时的降级（上次产物 + 「构建中」标记）。
- 追问钩子：为什么低代码场景「缓存命中率」比通用构建高一个量级？——schema 改动通常是局部（改一个组件属性），依赖闭包失效极小（RBL-635 最小失效集）；把「schema diff → 增量构建」做深是这类平台的性能护城河。

```javascript
// 构建服务队列（多租户隔离）
class BuildService {
  #queue = createScheduler({ concurrency: 8 });
  async publish({ tenantId, schemaHash, schema, lastArtifact }) {
    if (lastArtifact?.schemaHash === schemaHash)
      return lastArtifact;                               // 指纹命中：直接复用
    const task = buildTenantBundle;                      // 常驻 worker 函数
    return this.#queue.schedule(
      () => task({ tenantId, schema, signal: timeoutSignal(30_000) }),
      tenantTier(tenantId) === 'p0' ? 1 : 5,             // 发布 P0 / 预览 P2
    );
  }
}

// 常驻构建器的任务隔离
async function buildTenantBundle({ tenantId, schema, signal }) {
  const arena = createArena();                           // 任务级 arena：退出即回收
  try {
    const vfs = new MemFs({                              // 租户虚拟 FS
      '/schema/components.js': schemaToCode(schema),
      '/theme/tokens.css': tenantTokens(tenantId),       // 虚拟模块：配置注入
    });
    return await builder.build({ fs: vfs, signal, arena });
  } finally {
    arena.drop();                                        // 防长驻进程内存增长
  }
}
```
