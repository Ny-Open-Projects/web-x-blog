## RBL-914：综合深水：水合不一致根因矩阵——SSR/CSR 差异的系统化排查

**答**:
- 水合 mismatch 的根因矩阵（本目录知识 + 14 目录衔接）：1) **时间类**（Date.now()/随机数——服务端渲染时的时间 ≠ 客户端水合时；对策：时间戳由 server 下发 props/渲染后补丁）；2) **环境类**（window/document/localStorage——RBL-779 边界审计；媒体查询 useEffect 后判定）；3) **数据类**（server 与 client 各自 fetch 结果不同——数据必须单源：server 传 props，client 复用）；4) **格式类**（Intl/数字/日期格式化依赖 locale 环境——locale 显式传入而非读 navigator）；5) **结构类**（条件渲染依赖运行时状态——isMobile 首屏判定）。每类给出「构建期能预防的」与「只能运行时约定」的标注。
- 构建期的防线：环境类用边界审计（RBL-779 server bundle 扫 window 引用）；格式类的 lint（Date 格式化未传 locale）；数据类的架构约束（数据获取必须 loader 化——框架保证）。
- 排查的工程化：水合 diff 的自动定位（React 的 hydration error 带 DOM 对比——生产环境关闭水合 diff 的体积代价，dev 全开；错误上报带 diff 指纹聚合根因分布 RBL-881）。
- 与 RSC 的差异：RSC 场景（RBL-779）没有传统水合（Flight payload 序列化）——mismatch 形态变为「可序列化违规」；根因矩阵要按渲染架构分版。
- 追问钩子：为什么「时间类 mismatch」的对策是「server 下发时间」而不是「suppressHydrationWarning」？——suppress 只是压掉警告（UI 仍是错的——用户看到的时间戳冻结在渲染时）；下发时间让两端同源（真实正确）；「压警告 vs 修数据源」的选择是所有 mismatch 处理的分水岭——warning 是症状不是病，mismatch 的修复必须回到数据单源原则。

```javascript
// mismatch 根因矩阵与防线标注
const MISMATCH_MATRIX = {
  time: { example: 'Date.now()/随机数', buildPreventable: false,
    fix: 'server 下发时间戳 props；客户端相对计算' },
  env: { example: 'window/localStorage 直接引用', buildPreventable: true,
    fix: 'RBL-779 边界审计 + typeof 守卫/useEffect 延后' },
  data: { example: '双端各自 fetch 结果不同', buildPreventable: true,
    fix: 'loader 单源：server fetch -> props 传递' },
  format: { example: 'Intl/locale 隐式依赖', buildPreventable: true,
    fix: 'locale 显式化（lint 检测未传 locale 的格式化调用）' },
  structure: { example: 'isMobile 首屏分支', buildPreventable: false,
    fix: 'CSS 响应式优先；必要分支用 useEffect 后切换' },
};
function classifyMismatch(diff) {
  return Object.entries(MISMATCH_MATRIX)
    .find(([, m]) => m.example && diff.includes(m.example.split('/')[0]))?.[0] ?? 'unknown';
}
```
