## RBL-888：场景题：产物灰度的百分比调度——一致性 hash 分流与版本亲和

**答**:
- 产物灰度（新旧版本混跑）的分流要求：1) **会话亲和**（同一用户/设备在整个会话拿到同一版本——中途换版本 = 状态错乱：chunk 版本混用）；2) 百分比精确（10% 灰度就是 10%——hash 分桶的均匀性）；3) 可逆（一键回滚 RBL-686 manifest switch）；4) 分流依据稳定（用户 id hash 而非随机——每次刷新换版本会让缓存统计失真）。
- 实现：**一致性 hash 分桶**（hash(userId) % 100 < grayPercent → 新版）——网关/CDN edge 计算（html 注入版本标记）或运行时 SDK 判定；「会话内锚定」（判定结果存 sessionStorage——刷新不变）。
- 版本混用的防线：灰度用户的 html 引用新 manifest——「同会话版本锁定」防止「旧 html + 新 chunk」的错配（RBL-694 顺序契约的用户侧）；跨版本状态（storage schema 变化）的兼容层。
- 灰度的可观测：分桶比例监控（实际灰度占比 vs 配置——CDN 边缘 hash 分布不均的校正）；灰度期错误率对比（RBL-863 canary 逻辑延长版）。
- 追问钩子：为什么「随机分流」不能用于产物灰度？——随机 = 每次请求可能不同版本 → 同一用户会话中 html 与 chunk 版本错配（旧 runtime 引新 hash chunk = ChunkLoadError 风暴）；产物灰度的分流键必须是「稳定的用户属性 + 会话锚定」——与 A/B 实验的分流本质相同，产物灰度多了「版本物理文件」的约束。

```javascript
// 一致性 hash 分桶 + 会话锚定
function pickVersion(userId, { grayPercent, newManifest, oldManifest }) {
  // 会话锚定优先
  const cached = sessionStorage.getItem('__build_ver');
  if (cached) return cached === 'new' ? newManifest : oldManifest;
  const bucket = hash(userId) % 100;
  const ver = bucket < grayPercent ? 'new' : 'old';
  sessionStorage.setItem('__build_ver', ver);
  return ver === 'new' ? newManifest : oldManifest;
}
// hash 分桶均匀性监控
function auditBucketBalance(assignments) {               // assignments: { userId, bucket }
  const counts = new Array(100).fill(0);
  assignments.forEach(a => counts[a.bucket]++);
  const expected = assignments.length / 100;
  const skewed = counts.filter(c => Math.abs(c - expected) > expected * 0.3).length;
  if (skewed > 10) warn(`分桶不均（${skewed}/100 桶偏差 >30%）——hash 分布校正`);
}
```
