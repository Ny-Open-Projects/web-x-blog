## RBL-669：构建性能优化的反模式清单：那些「看起来是优化」的坑

**答**:
- 反模式 1「过度 chunk 拆分」：把每个 npm 包拆成独立 chunk（maxAsyncRequests 手工调大）——HTTP 请求爆炸 + waterfall 依赖；正确思路是「按变更频率与使用路径分组」而不是「越细越好」。
- 反模式 2「缓存键过宽」：把整个 package.json 内容塞进每个模块的缓存键——依赖描述变化（无关 devDependencies）导致全量失效；键应最小完备（只含影响产物的字段）。
- 反模式 3「并行度拉满」：并发数 = CPU 核数看似合理，实际 transform 混合 IO 时上下文切换 + 内存峰值（RBL-569）反而变慢；并发要按负载特征调优并测量。
- 反模式 4「微优化插件」：花一周优化「某个 loader 快 50ms」，而 resolve 慢路径占 30s——优化要按 profile 排序（火焰图先行），不能按「感觉的痛点」。
- 反模式 5「dev 配置污染 prod」：为 dev 提速关闭的检查（如 sourcemap、TS 转换严格性）静默影响 prod 配置共享层——dev/prod 配置要显式分层，共享项审计。
- 反模式 6「预构建一切」：把业务代码也预构建（想加速冷启动）——预构建产物失效频繁，得不偿失；预构建只适合「稳定依赖」。
- 追问钩子：这些反模式的共同根因是什么？——「优化的度量缺位」：没有 profile/基准就直接动手；每一项的正确做法都从「测量 → 归因 → 定向优化 → 复测」开始（RBL-587 基准体系）。

```javascript
// 反模式自检清单（构建性能 review 用）
const ANTIPATTERNS = [
  {
    name: 'over-split-chunks',
    detect: (config, stats) => stats.chunkCount > 100,
    fix: '按变更频率/使用路径分组（RBL-596），合并 <20KB chunk',
  },
  {
    name: 'over-broad-cache-key',
    detect: (config) => JSON.stringify(config.cacheKey?.includes?.('package.json')),
    fix: '缓存键最小完备：只含影响产物的字段（RBL-582）',
  },
  {
    name: 'max-parallel-blindly',
    detect: (config) => config.parallel === 'max' || config.parallel === os.cpus().length,
    fix: '按内存预算感知并发（RBL-569），基准复测',
  },
  {
    name: 'micro-opt-without-profile',
    detect: (pr) => pr.touches === 'loader' && !pr.hasProfile,
    fix: '火焰图先行（RBL-587），按占比排序优化对象',
  },
];
```
