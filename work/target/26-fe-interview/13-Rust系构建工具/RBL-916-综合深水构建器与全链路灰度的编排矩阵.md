## RBL-916：综合深水：全链路灰度编排——前端/网关/后端三层协同

**答**:
- 全链路灰度（不只前端产物）的三层编排：1) **前端层**（产物灰度 RBL-888：一致性 hash 分桶）；2) **网关层**（路由规则：灰度流量的 header/cookie 透传——`x-gray-tag: exp-123`）；3) **后端层**（服务实例的灰度染色——同 tag 请求路由到灰度实例）。协同的关键是「分流键的全程一致」：前端按 userId 分桶 → 请求带 tag → 网关按 tag 路由 → 后端按 tag 染色——「一个键贯穿三层」，任何一层用了不同键 = 灰度撕裂（前端新版调旧 API）。
- 撕裂的具体形态与防线：前端新版本调用旧后端接口（后端没灰度）——接口契约兼容（新前端兼容旧 API：版本协商头/能力协商）；「灰度矩阵声明」（每层就绪状态：前端 ready/网关 ready/后端 ready——全 ready 才放量，RBL-862 检查点的三层版）。
- 回滚的联动：一键回滚要「三层同时回」（前端 manifest switch + 网关规则关闭 + 后端流量切回）——单层回滚 = 撕裂；回滚编排是原子操作（RBL-694 的三层扩展）。
- 灰度标识的透传链路：入口（CDN/网关）生成 → 前端 html 注入 → 后续 API 请求 header 携带 → 后端日志染色——「标识透传」的每跳都要显式处理（丢失一跳 = 后端统计口径分裂）。
- 追问钩子：为什么「分流键一致」是全链路灰度的第一原则？——三层各用各的键（前端 userId、网关 IP、后端随机）会导致「同一个用户的前端是新版、后端是旧版」——行为组合爆炸（2^3 种状态）且不可复现排查；单键贯穿让「灰度状态」成为用户维度的一维属性——状态空间从 8 维坍缩到 2 维，可观测与可回滚性都依赖这个坍缩。

```javascript
// 三层灰度编排
const GRAY_MATRIX = {
  frontend: { ready: true, strategy: 'userId-hash' },
  gateway: { ready: true, strategy: 'header-tag', key: 'x-gray-tag' },
  backend: { ready: false, strategy: 'instance-dye' },   // 后端未就绪！
};
function canProceed(matrix) {
  const notReady = Object.entries(matrix).filter(([, l]) => !l.ready).map(([k]) => k);
  if (notReady.length) fail(`灰度撕裂风险: ${notReady} 未就绪——前端新版将调用旧后端`);
  return notReady.length === 0;
}
// 标识透传链
const passthrough = (req) => ({
  tag: req.headers['x-gray-tag'] ?? req.cookies.gray ?? deriveFromUser(req.userId),
  // 每跳显式透传：网关 -> 前端 html（meta 注入）-> 前端 API 调用（header）-> 后端日志
});
// 原子回滚（三层）
async function rollbackAll(tag) {
  await Promise.all([
    manifestSwitch('old'),                               // 前端 RBL-686
    gateway.disableRule(tag),                            // 网关
    backend.undye(tag),                                  // 后端
  ]);                                                    // 三层同时回——单层回滚 = 撕裂
}
```
