## AV-303：音视频平台专项：SDK 版本兼容与 breaking change 管理

**答**：
- 题目：SDK 版本兼容——老版本客户端连新服务端（协议协商）、API 废弃流程（deprecate→remove 两阶段）、类型定义同步。
- 思路：能力协商（offer 中带 SDK 版本/capabilities → 服务端按版本适配响应）；API 废弃：v2.0 标记 deprecated + v3.0 移除；TS 类型随 SDK 发布。
- 评分点：协商机制；废弃两阶段；类型同步。

```javascript
class SDKCompat {
  negotiate() {                                              // 能力协商
    const capabilities = {
      sdkVersion: '2.3.0',
      features: ['simulcast', 'e2ee', 'datachannel-binary'],
    };
    this.ws.send(JSON.stringify({ type: 'hello', ...capabilities }));
    // 服务端按 capabilities 降级响应（不支持 e2ee → 关闭该功能并通知）
  }
}
// API 废弃流程：
// v2.0: @deprecated 标记 + console.warn + 迁移指南链接
// v2.x: 继续工作（warn）
// v3.0: 移除（breaking change 通知提前一个大版本）
// 类型同步：SDK npm 包带 .d.ts——TS 用户编译期就能发现 API 变化
```

## 追问（补充）

**追问**：

1. 能力协商为什么必须放在握手第一步？ → SDK 的可用功能决定后续信令格式；晚一步协商，服务端已经按默认能力下发过媒体参数，只能重协商，用户会看到一次黑屏重连。
2. 废弃 API 为什么要留「一个大版本」？ → 移动端与 Electron 客户端的升级周期不可控，SDK 直接被老版本调用；提前一个大版本通知 + 运行时 warn + 迁移文档，是让存量集成方能排期的最低成本做法。
3. 类型真能防住 breaking change 吗？ → 只能防住 TS 用户在编译期发现签名变化；运行时行为变化（同一签名语义不同）必须靠 CHANGELOG 与灰度放量发现，别把 `.d.ts` 当保险。
4. 降级策略怎么验证？ → 在测试环境强制伪造 `hello` 的 capabilities（去掉 e2ee/simulcast）跑一遍主流程，确认关闭功能后 UI 与信令都不报错；只测正常路径等于没测降级。
