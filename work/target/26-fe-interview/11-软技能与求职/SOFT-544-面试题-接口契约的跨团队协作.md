## SOFT-544：前后端/跨系统接口契约的协作机制（谁定/怎么改/怎么防漂移）

**答**：
- 契约机制三支柱：单一事实源（OpenAPI/协议文档进 git，MR 式变更——改契约走评审）、变更流程（破坏性变更=新版本+过渡期，双版本并行期双方各自迁移）、自动化校验（CI 契约测试：provider 验证+consumer 驱动——前端 mock 从 schema 生成，后端实现过 schema 验证）。
- 防漂移的关键是「不让手写绕过」：前端类型从 schema 生成（手写类型是漂移之源）、后端实现与 schema 的一致性测试进 CI。
- 争议解决：字段语义歧义（"金额含不含优惠券"）在契约文档写例子而非抽象描述——一个具体 example 胜过十行定义。

**可复用模板**（契约协作规则）：

```text
事实源：api/contracts/*.yaml（git管理，MR评审）
变更：破坏性=v2路径+旧版保6个月；字段语义必须带example
自动化：①前端类型自动生成 ②后端CI跑schema验证
       ③前端MSW mock从schema生成
漂移：CI抓到不一致→阻断合并→契约MR修复
```

**反例**：接口靠聊天记录与口头约定，后端改字段前端编译才发现——每次联调都是考古现场。
