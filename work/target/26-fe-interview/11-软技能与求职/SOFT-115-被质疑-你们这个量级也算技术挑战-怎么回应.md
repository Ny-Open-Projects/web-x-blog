## SOFT-115：被质疑"你们这个量级也算技术挑战？"——小流量项目怎么讲出含金量？

**答**：
- 不跟面试官争量级，直接换维度：复杂度不止并发——业务复杂度（状态多、联动多）、约束复杂度（老浏览器、内网、合规）、交付复杂度（从 0 到 1 无基建可用）都是合法的技术挑战。
- 用"约束下的解法"重新定位难点："并发不高，但我们连 websocket 兼容到 IE11，方案空间小很多"——难题的本质是约束而不是规模。
- 顺带展示对规模的认知不缺席：说明"如果流量涨到 X，方案要怎么演进"，证明不是没想过，只是场景不需要。
- 最忌讳的反应是慌乱拔高数字，被追问一句就崩；坦然承认量级 + 讲清约束，反而显成熟。

```text
量级质疑应答模板：
承认："确实不是高并发场景，日活 {X}。"
换维："这个项目真正的挑战在 {业务/约束/交付} 维度：
      比如 {具体约束}，把常规方案都堵死了，最后用的
      {方案} 是自己权衡出来的。"
补认知："如果量级到 {Y}，我会把 {A} 换成 {B}，
      这块我们做过压测预案。"

可选维度清单：状态复杂度 / 兼容性约束 / 安全合规 /
从 0 到 1 基建缺失 / 跨团队协议设计 / 长期维护成本。
```
