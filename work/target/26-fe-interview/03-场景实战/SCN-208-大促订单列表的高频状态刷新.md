## SCN-208：大促订单状态频繁变化（待付款→已付款→发货），列表页刷新怎么设计？

**答**:
- 状态源收敛：订单状态三来源（列表接口/详情接口/推送消息）统一进状态中心（单一事实源），列表渲染只读状态中心——多源写入按时间戳与状态机序合并（已发货不能被旧状态覆盖）。
- 增量更新：推送只带 orderId+新状态，列表按 orderId 局部更新（不整页刷新）；状态机校验非法迁移（SCN-471 状态机思想：pending→paid→shipped 合法序，乱序推送丢弃+触发一次全量校正）。
- 刷新策略：页面可见时轻量轮询（可见才轮询，不可见暂停）、关键操作后主动刷新（支付返回→立即刷新该单）、下拉刷新全量校正——三种刷新互补。
- 大列表性能：状态徽标局部更新（只更新变化行的 DOM，虚拟列表行缓存），状态变更动效克制（大促流量下动画降级）。

```javascript
const orderState = createStore();
const FLOW = ['created','paid','shipped','delivered','done'];
function applyUpdate(orderId, status, ts) {
  const cur = orderState.get(orderId);
  if (cur && FLOW.indexOf(status) <= FLOW.indexOf(cur.status)
      && cur.ts >= ts)
    return scheduleResync(orderId);          // 乱序推送→触发校正
  orderState.set(orderId, { status, ts });   // 单行局部更新
}
// 页面可见时轮询：visibilitychange 控制；
// 支付回跳：refreshOne(orderId) 单单刷新。
// 推送：ws.on('order', m => applyUpdate(m.id, m.status, m.ts))。
```

**追问**：

1. 乱序推送触发 `scheduleResync`，高频时会不会把接口打爆？ → 校正要合并去重并限流，同一订单 N 秒内只校正一次，否则洪峰下自伤。
2. 状态序比较用 `FLOW.indexOf`，遇到「已取消」这种不在主链上的态怎么办？ → 取消与关闭是旁支终态，要单独判定并优先于线性比较，否则会被判成乱序。
3. 页面不可见时暂停轮询，回来后怎么补齐中间漏掉的状态？ → 重新可见时先做一次全量校正再恢复轮询，不能只等下一次增量。
