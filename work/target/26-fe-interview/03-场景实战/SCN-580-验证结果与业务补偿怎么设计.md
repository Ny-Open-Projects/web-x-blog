## SCN-580：验证结果与业务补偿怎么设计？
**答**：
- 结果语义分层：验证通过 ≠ 业务成功——验证 token 证明「是本人」，业务失败（库存没了/限额）另走业务提示；文案必须区分「验证未通过」与「操作失败」。
- 补偿路径：业务失败且 token 未消费 → token 仍有效期内重试业务；已消费 → 重新验证但保留业务上下文（表单不重填）。
- 异步补偿：降级放行（SCN-558）的操作进补验队列，服务恢复后批量复核，复核不通过再追责冻结。
- 闭环度量：统计「验证通过但业务失败」占比，识别体验断点（如验证太晚导致库存被抢完，考虑验证前置）。
- 追问钩子：验证前置会误伤多少正常用户——用漏斗数据说话，把验证挪到「加入购物车」还是「支付」是产品决策，前端提供数据支撑。

```javascript
async function payWithGuardedRetry(order) {
  const v = await riskGuard('pay');
  for (let i = 0; i < 2; i++) {
    const res = await api.post('/pay', { orderId: order.id, riskToken: v.token });
    if (res.ok) return res;
    if (res.code === 'TOKEN_CONSUMED') {           // token 已消费：重验但保上下文
      const v2 = await riskGuard('pay');
      v.token = v2.token;
      continue;                                    // 表单状态保留
    }
    if (res.code === 'TOKEN_USED') continue;
    return showBizError(res);                      // 业务失败：与验证无关
  }
}
```
