| 文件 | 原文片段（≤30字，要能 grep 到） | 问题 | 精确改法 |

| NODE-736-笔试题-实现MQ消费者完整框架.md | `redis.set(\`mq:${message.id}\`, 1, 'PX', 86400_000, 'NX')` | 幂等键在**消费前**写入且失败路径不删除：handler 抛错后走 `delayedQueue.schedule` 重投，重投消息 id 不变，SETNX 返回 null 直接 `return`，于是「退避重试」「3 次后进 DLQ」两条链路**永不生效**，毒消息被静默丢弃。 | 改为「成功后标记」：`const ok = await redis.set(key,1,'PX',...,'NX'); if(!ok) return; try{ await handler } catch(e){ await redis.del(key); ...重投/DLQ }`。 |
| NODE-488-Node-服务的幂等消费实现矩阵.md | `if (t.rowCount === 0) return ackDuplicate(msg);` | `t` 是事务句柄，`t.rowCount` 恒为 `undefined`；`undefined === 0` 为 false，唯一索引兜底分支永远不进，重复消息会继续执行 `doBusiness`，严格兜底等于没有。 | `const r = await t.query(...); if (r.rowCount === 0) return ackDuplicate(msg);`（pg 取 `result.rowCount`，mysql2 取 `affectedRows`）。 |
| NODE-132-接口限流四种算法的完整实现对比-计数器-滑动窗口.md | `// ARGV：当前毫秒、每秒补币速率、桶容量` | 时间戳用毫秒（`Date.now()`），补币/漏水却按「每秒」速率直接与毫秒差相乘：`tokens + (ts - (d[2] or ts)) * tonumber(ARGV[2])`，乘了 1000 倍，桶永远瞬间满（漏桶则永远瞬间空），令牌桶/漏桶限流彻底失效。 | 分母补 `/1000`：`tokens + (ts - last) * rate / 1000`（漏桶 `leaked` 同理），与 NODE-641 的写法保持一致。 |
| NODE-800-笔试题-实现Node服务三级收束与自检清单.md | `const ok = await c.run().catch(() => false);` | 所有检查项的 `run` 都是同步返回 boolean（如 `run: () => eldP99() < 100`），boolean 上没有 `.catch`，`selfCheck()` 第一项就抛 `TypeError: c.run(...).catch is not a function`，整个自检跑不起来。 | `const ok = await Promise.resolve(c.run()).catch(() => false);` 或 `let ok; try { ok = await c.run(); } catch { ok = false; }`。 |

## 存疑

| 文件 | 原文片段 | 疑点 |
|---|---|---|
| NODE-074-设计一个定时任务系统 | `schedulerQueue.upsertJobRepeatable(name, { pattern: cron, tz: 'Asia/Shanghai' });` | BullMQ 无 `upsertJobRepeatable` 这个 API（v5 的等价物是 `Queue.upsertJobScheduler(schedulerId, repeatOpts, jobTemplate)`；v4 及之前是 `add(name, data, { repeat: { pattern } })`），照抄会 `TypeError`。同段 `await schedulerQueue.add(name, payload, { repeat, jobId: name })` 的固定 `jobId` 还会让首轮之后的迭代被去重掉。 |
| NODE-074-设计一个定时任务系统 | `// BullMQ 保证同一 repeatable job 同一时刻只有一个 worker 在跑` | 该断言不成立：repeatable job 每到一个触发点都会**新生成一个 job**（jobId 含时间戳），上一轮仍在 active 时新一轮照样入队并被执行（`concurrency: 5`），BullMQ 不做跨迭代互斥。防重仍需业务唯一键或分布式锁。 |
| NODE-146-幂等与事务消息如何用本地消息表实现 | `'SELECT * FROM outbox WHERE status = 0 AND next_retry_at <= NOW() LIMIT 100'` | 上文 INSERT 只写 `(biz_id, payload, status)`，未写 `next_retry_at`；若该列无 `DEFAULT CURRENT_TIMESTAMP`，`NULL <= NOW()` 恒为 NULL（非真），**首次投递永远扫不到新行**。需确认 DDL 是否给了默认值，或把条件改成 `(next_retry_at IS NULL OR next_retry_at <= NOW())`。 |
| NODE-684-Node服务的积分营销账户系统 | `await tx.insert('point_ledger', { batchId: b.id, delta: -use, idemKey });` | FEFO 循环里每个批次插一行流水，却共用同一个 `idemKey`；若 `idem_key` 上是唯一索引（幂等键的常规做法），第二个批次就唯一冲突回滚，一笔跨批次扣减必然失败。需确认是复合唯一键 `(idem_key, batch_id)` 还是幂等键只落在首个批次。 |
| NODE-760-笔试题-实现AI网关流式透传与计量 | `cache.set(cacheKey, sseSnapshot);` | `sseSnapshot` 在全段从未定义，运行到此处即 `ReferenceError`；同时计量（`metering.charge`）出现在 `pipeline` 之后，若客户端中途断开 pipeline reject，本次已产出 token 不会入账，与追问 1「按已产出 token 入账」自相矛盾。 |
