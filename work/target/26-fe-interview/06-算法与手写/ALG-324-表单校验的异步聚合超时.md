**场景**：邮箱唯一性校验服务 3s 未响应——阻塞提交（用户卡死）vs 超时降级（视为通过 + 提交后服务端复查，不一致回滚提示）。降级决策按"校验的业务强制性"分级。

**思路**：Promise.race 超时 → 降级决策表（强校验阻塞重试一次后拒绝 / 弱校验超时放行+标记）。

```javascript
async function validateWithTimeout(rule, value, { timeout = 3000, policy = 'soft' } = {}) {
  const result = await Promise.race([
    rule(value),
    new Promise((_, rej) => setTimeout(() => rej(new Error('validation-timeout')), timeout)),
  ]).catch((e) => (e.message === 'validation-timeout' ? 'timeout' : Promise.reject(e)));
  if (result !== 'timeout') return result;                // 正常返回
  // 超时降级：按策略分级
  if (policy === 'hard') {                                // 强校验（如支付风控）：重试一次仍超时 → 拒绝提交
    const retry = await Promise.race([rule(value), new Promise((r) => setTimeout(() => r('timeout'), timeout))]);
    return retry === 'timeout' ? { block: true, reason: '校验服务不可用，请稍后重试' } : retry;
  }
  return { pass: true, flagged: true };                   // 弱校验（唯一性检查）：放行 + 标记
}
// 提交流：flagged 的字段提交后服务端复查 → 不一致回滚提示（"该邮箱刚被注册，请修改"）
// 决策表语义：
// soft（唯一性/黑名单）：误放行成本 = 服务端兜底拒绝 → 放行+标记
// hard（风控/实名）：误放行成本 = 资损 → 阻塞（宁可卡用户不可放过）
// 分级依据 = 误放行的业务成本，不是技术便利
```

**评分点**：
- Promise.race 超时 + 按业务强制性分级降级（soft 放行标记/hard 阻塞）——本题核心。
- hard 的重试一次再拒绝（网络抖动容错）。
- flagged 提交后服务端复查回滚的闭环。
- 分级依据 = 误放行成本（业务决策不是技术决策）。
