## ALG-345：前端多租户数据分片：IDB 按 tenant 分库（隔离/配额/清理的租户粒度）？
**答**：多租户前端应用（客服切换客户）——本地缓存按租户分库（`tenant-{id}` 前缀）——切换租户时：旧租户数据不跨租户可见（隔离）、可整体清库（清理粒度）、配额按租户记账（PER-318 用量归因）。

**思路**：DB 名带租户前缀 → Store 层透传 → 切换租户 = 打开对应库 → 退出租户 deleteDatabase（数据不残留）。

```javascript
class TenantDB {
  #current = null;
  async switch(tenantId) {
    this.#current = tenantId;
    return this.#open(`tenant-${tenantId}`);               // 分库：隔离天然成立
  }
  async #open(name) { /* HW-107 IDB 封装，库名带租户前缀 */ }
  async exitAndWipe() {                                    // 退出租户：整库删除（不残留）
    if (this.#current) {
      indexedDB.deleteDatabase(`tenant-${this.#current}`);
      localStorage.removeItem(`tenant-${this.#current}:*`);   // 同前缀的 localStorage 也清
      this.#current = null;
    }
  }
}
// 分库 vs 分键空间（u:123: 前缀，PER-360）：
// 分库：隔离/清理/配额都是"库"粒度（IDB deleteDatabase 原子清库）—— 租户切换频繁/数据大的场景
// 分键空间：同库内前缀（省库数）—— 租户少数据小的场景
// 跨租户访问防御：Store 层强制注入 tenantId（查询自动带租户条件——应用代码无法绕过）
// 泄漏防线：切换租户后旧库连接关闭（IDB 连接泄漏 = 内存泄漏，PER-263 清单）
```

**评分点**：
- 分库 vs 分键空间的取舍（租户粒度操作需求）——本题核心。
- exitAndWipe 整库原子清理。
- Store 层强制租户注入（应用代码不可绕过的隔离）。
- 旧库连接关闭（泄漏防线）。
