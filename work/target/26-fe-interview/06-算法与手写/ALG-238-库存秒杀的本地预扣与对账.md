**场景**：秒杀：服务端推送可售数（如 100），用户点击抢购——本地立即减 1（按钮即时反馈），抢购请求异步发出；失败（售罄/超时）本地回滚 +1；定期与服务端推送对账（本地虚扣/漏扣修正）。

**思路**：本地计数器 + 在途请求计数（in-flight 扣减未确认不算已失败）；对账以服务端推送为准强制覆盖；按钮 disabled 条件 = local ≤ inFlight（全部在途，不能再点）。

```javascript
class SeckillCounter {
  constructor(initial) { this.local = initial; this.inFlight = 0; }
  tryGrab() {
    if (this.local <= this.inFlight) return { ok: false, reason: 'sold-out' };  // 可售（含在途）不够
    this.local--; this.inFlight++;                       // 乐观预扣
    return { ok: true,
      confirm: async (result) => {                       // 服务端确认/失败
        this.inFlight--;
        if (!result.ok) this.local++;                    // 失败回滚
        return result;
      } };
  }
  sync(serverCount) {                                    // 服务端推送对账：强制覆盖
    this.local = serverCount; this.inFlight = 0;         // 在途请求的结果以服务端最终推送为准
  }
  get canBuy() { return this.local > this.inFlight; }
}
// 一致性语义：local 包含 inFlight（乐观未确认的可售）—— 按钮禁用条件 local <= inFlight
// 对账兜底：本地漂移（丢消息/重复回滚）由服务端周期推送修正 —— 最终一致
// UX：失败回滚 +1 后按钮重新可用；成功后进入订单流程
```

**评分点**：
- 乐观预扣 + 在途计数的模型（local 包含 inFlight，禁用条件正确）——本题核心。
- 失败回滚 +1；对账强制覆盖（服务端为准）的最终一致设计。
- 按钮可点性判定与本地/服务端漂移的兜底说明。
- 能说出"本地预扣只为响应速度，库存真相在服务端"。
