**场景**：向导流程有分支（步骤 3 选择"企业"走 3a，"个人"走 3b）——从 3b 回退到步骤 2 改选择为"企业"后：3b 数据清除（分支变了）、共享步骤数据保留——分支感知回退。

**思路**：步骤依赖图（每步声明 deps）→ 回退到步 N 时：依赖链上被分支改变的步骤清数据，独立步骤保留——判定 = "该步数据是否依赖被改的分支决策"。

```javascript
function branchAwareBack(steps, currentIdx, targetIdx, changedDecision) {
  // steps: [{ id, deps: [stepId] }]；changedDecision: 被修改的分支决策步 id
  const affected = new Set([changedDecision]);
  let grew = true;
  while (grew) {                                          // 影响集闭包：依赖被改决策的所有下游步
    grew = false;
    for (const s of steps) {
      if (s.deps?.some((d) => affected.has(d)) && !affected.has(s.id)) {
        affected.add(s.id); grew = true;                  // 传递闭包
      }
    }
  }
  return steps.slice(targetIdx).map((s) => ({
    id: s.id,
    keep: !affected.has(s.id),                            // 在影响集内：清数据；否则保留
  }));
}
// 例：steps = info→type→corpForm(deps:type)→contact→confirm
// 从 confirm 回退到 type 且改了 type → affected = {type, corpForm} → corpForm 清、contact 保留
// 语义：
// 分支依赖闭包判定"哪些步的答案因决策改变而失效" —— 比"回退全清"（丢用户输入）与"全保留"（分支错配数据）都精准
// 全清的反例：联系方式/备注与分支无关，全清 = 用户重复填写（流失点）
// 全保留的反例：企业表单数据残留在个人流程（错配数据提交 = 事故）
```

**评分点**：
- 分支依赖闭包判定（影响集传递）——本题核心。
- 三种策略对照（全清丢输入/全留错配/闭包精准）。
- 数据保留或清除的决策输出（keep 字段驱动）。
- 依赖声明（deps）的可维护性。
