# 07 请求调度与限流

> 这块是从「会写函数」到「能设计基础设施」的分界。**能力分层**：L1 能写对 → L2 能写全边界 → L3 能讲清取舍。

请求调度类题目有个共同陷阱：**代码写出来都很短，但面试官问的从来不是代码本身**。p-limit 二十行谁都能背，真正分档的是「为什么锁要在 finally 里放」「令牌桶为什么不用 setInterval」「抢占式取消会不会把已发出的写请求 abort 掉」。所以本专题每道精讲都按「实现 → 必须覆盖的边界 → 追问链」三层给，答追问时优先讲因果，不要背结论。

一个自查标准：写完 p-limit 后，你能不能立刻说出「如果第 4 个任务同步抛错、第 5 个任务还在队列里，会发生什么」。能答上来，说明你真的拥有这把刀，而不是背下了刀的图片。

## 精讲（6 题）

### 精讲 1 · [HW-007] 手写 p-limit 并发控制

**为什么考这个**：这是所有调度题的地基。面试官让你写它，看的不是代码，而是你有没有把「并发上限」当成一个**状态机**来思考——active、queue、release 三者之间的关系错一处，就会出现并发超标或任务饿死。

**标准实现**：
```javascript
// p-limit 的极简可信版本：active 计数 + 启动器队列
function pLimit(concurrency) {
  if (!Number.isInteger(concurrency) || concurrency < 1) {
    throw new TypeError('concurrency 必须是正整数');
  }
  let active = 0;            // 正在执行的任务数
  const queue = [];          // 排队的是「启动器」，不是任务本身（延迟调用才有意义）

  const release = () => {
    active--;                            // 先释放槽位
    if (queue.length) queue.shift()();   // 再拉起一个（一次只补一个，上限才不会被冲破）
  };

  return (fn) => new Promise((resolve, reject) => {
    const start = () => {
      active++;
      // fn 可能同步抛错：包一层 then，保证 release 一定执行
      Promise.resolve().then(fn).then(resolve, reject).finally(release);
    };
    if (active < concurrency) start();
    else queue.push(start);              // 满员排队，等 release 唤醒
  });
}

// ===== 可运行验证：100 个任务、并发 5，统计峰值 =====
(async () => {
  const limit = pLimit(5);
  let running = 0, peak = 0;
  const jobs = Array.from({ length: 100 }, (_, i) => limit(async () => {
    running++; peak = Math.max(peak, running);
    await new Promise((r) => setTimeout(r, 5));   // 模拟 IO 等待
    running--;
    return i;
  }));
  const results = await Promise.all(jobs);
  console.log('完成', results.length, '峰值并发', peak);   // 完成 100 峰值并发 5
})();
```

**必须覆盖的边界**：

- **release 必须在 finally**：任务 reject 时若不释放槽位，队列会永久卡死——这是这道题最高频的死法。
- **队列里存启动器而非 Promise**：存 `fn()` 的结果等于立刻发起了请求，限流形同虚设。
- **同步抛错**：`fn` 直接 throw 时，`active--` 不能丢；用 `Promise.resolve().then(fn)` 兜住。
- **一次释放只补一个**：若写成 while 循环补位，会在某些重入场景下瞬间超出上限。
- **并发数校验**：0、负数、小数都应抛 TypeError，否则 `active < 0` 永远成立，队列永不排。

**追问链**：

1. **为什么不能直接用 Promise.all 分批（chunk）？** → 分批是「批内全等」，最慢的任务会拖住整批，吞吐只有最短板的水平；p-limit 是「流水线」，任一完成立刻补位，整体耗时接近 `总耗时 / 并发数`。
2. **任务本身返回非 Promise 会怎样？** → `Promise.resolve().then(fn)` 已经统一包装，同步返回值会走 resolve，不需要额外分支。
3. **怎么拿到每个任务的结果数组？** → 外层 `Promise.all` 收集返回的 Promise 即可，顺序与提交顺序一致（因为每个 Promise 独立 resolve），不因完成顺序错乱。
4. **如果要在运行时调整并发数呢？** → 把 `concurrency` 换成 getter 或 `setLimit(n)`，`setLimit` 上调后立即调用一次 `release()` 风格的补位循环；下调只影响后续释放，不杀在途任务。

### 精讲 2 · [HW-063] 指数退避重试（含抖动与条件重试）

**为什么考这个**：`retry(fn, 3)` 是应届生答案，`retry(fn, { factor, jitter, shouldRetry })` 才是工程答案。面试官问「为什么要加抖动」时，答「防惊群」还不够，要能说出「1000 个客户端同时失败、同时 500ms 后重试，会把刚恢复的服务再打挂」。

**标准实现**：
```javascript
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

function retry(task, {
  retries = 3,            // 额外重试次数，总尝试 = retries + 1
  delay = 300,            // 首次退避基数（ms）
  factor = 2,             // 退避系数：delay * factor^i
  maxDelay = 8000,        // 单次退避上限，防止指数爆炸
  jitter = true,          // 抖动：打散重试时刻
  shouldRetry = () => true,
  signal,
  onRetry,
} = {}) {
  return (async () => {
    for (let i = 0; ; i++) {
      if (signal?.aborted) throw new DOMException('已取消', 'AbortError');
      try {
        return await task(i);                    // 每次重新调用，绝不复用已 reject 的 Promise
      } catch (err) {
        if (i >= retries || !shouldRetry(err)) throw err;   // 抛最后一次真实错误
        const base = Math.min(delay * factor ** i, maxDelay);
        // 全抖动：[0.5, 1] 区间，既保留指数增长趋势，又打散峰值
        const wait = jitter ? Math.round(base * (0.5 + Math.random() * 0.5)) : base;
        onRetry?.(err, i + 1, wait);
        await sleep(wait);
      }
    }
  })();
}

// ===== 可运行验证 =====
(async () => {
  let calls = 0;
  const ok = await retry(async () => {
    if (++calls < 3) throw Object.assign(new Error('503'), { status: 503 });
    return 'ok';
  }, { retries: 4, delay: 10, jitter: false });
  console.log(ok, '尝试次数', calls);         // ok 尝试次数 3

  let n = 0;
  await retry(async () => {
    n++;
    throw Object.assign(new Error('400'), { status: 400 });
  }, { retries: 5, delay: 1, shouldRetry: (e) => e.status >= 500 })
    .catch((e) => console.log('不重试', e.message, '尝试次数', n));   // 不重试 400 尝试次数 1
})();
```

**必须覆盖的边界**：

- **抛最后一次错误**：循环里若忘了 `throw err`，最终 reject 的是 undefined，调用方拿到「空错误」，排查时抓瞎。
- **每次重新调用 task**：缓存第一次的 Promise 再 await，等于永远拿到同一个失败结果。
- **条件重试**：4xx（除 429）重试无意义，还会放大日志噪音；只有 408/429/5xx 和网络错误值得重试。
- **maxDelay 截断**：`factor=2, retries=10` 时第 10 次是 300×512 秒，必须封顶。
- **abort 感知**：用户取消后不应继续 sleep 等下一次尝试，循环开头检查 `signal.aborted`。
- **幂等性**：非幂等写请求（下单、支付）不能盲目重试，见精讲外的 HW-132。

**追问链**：

1. **指数退避 vs 固定间隔 vs 线性？** → 固定间隔在服务端过载时会持续施压；指数退避让压力随时间指数衰减，给下游恢复窗口；线性是折中但恢复慢。
2. **抖动有哪几种？** → full jitter（`random(0, base)`）、equal jitter（`base/2 + random(0, base/2)`）、decorrelated jitter（以上次间隔为基准随机）。我用的 `0.5~1.0` 属于 equal jitter 变体，兼顾下限与打散。
3. **重试要不要放在网关层做？** → 前端重试只处理「用户可感知的瞬时抖动」；跨机房、限流类重试应在网关/服务网格做，否则重试风暴会乘性放大。
4. **怎么避免重试把 UI 卡住？** → 重试期间保持 loading 并可取消；给整体加 totalTimeout，超过就放弃并提示「网络不稳定」。

### 精讲 3 · [HW-064] 手写令牌桶限流器

**为什么考这个**：四种限流（固定窗口、滑动窗口、令牌桶、漏桶）里，令牌桶是唯一同时满足「允许突发」和「长期匀速」的。面试官追问「为什么不用 setInterval 补桶」，就是筛掉只会背实现的人。

**标准实现**：
```javascript
class TokenBucket {
  constructor({ rate, capacity = rate, now = () => Date.now() }) {
    if (!(rate > 0) || !(capacity > 0)) throw new TypeError('rate/capacity 必须为正数');
    this.rate = rate;             // 每秒补多少令牌（匀速）
    this.capacity = capacity;     // 桶容量 = 允许的最大突发量
    this.tokens = capacity;       // 初始满桶：冷启动即可突发
    this.last = now();
    this.now = now;
    this.timer = null;
    this.queue = [];              // 等待者 resolve 队列（FIFO）
  }

  #refill() {                                  // 惰性补桶：只在读写时按时间差补
    const t = this.now();
    const delta = Math.max(0, (t - this.last) / 1000);
    this.tokens = Math.min(this.capacity, this.tokens + delta * this.rate);
    this.last = t;
  }

  tryAcquire(n = 1) {                          // 非阻塞：拿不到立刻拒绝
    this.#refill();
    if (this.tokens < n) return false;
    this.tokens -= n;
    return true;
  }

  acquire(n = 1) {                             // 阻塞：排队等够令牌
    return new Promise((resolve) => {
      this.queue.push(resolve);
      this.#drain();
    });
  }

  #drain() {
    while (this.queue.length) {
      this.#refill();
      if (this.tokens < 1) return this.#schedule();   // 不够就等下一个令牌时刻
      this.tokens -= 1;
      this.queue.shift()();                           // 按到达顺序放行
    }
  }

  #schedule() {
    if (this.timer || !this.queue.length) return;
    const wait = Math.max(0, ((1 - this.tokens) / this.rate) * 1000);
    this.timer = setTimeout(() => { this.timer = null; this.#drain(); }, wait);
  }
}

// ===== 可运行验证：rate=5/s, capacity=5，一次打 8 个请求 =====
(async () => {
  const bucket = new TokenBucket({ rate: 5, capacity: 5 });
  const t0 = Date.now();
  const stamps = [];
  await Promise.all(Array.from({ length: 8 }, () =>
    bucket.acquire().then(() => stamps.push(Date.now() - t0))));
  console.log('通过时刻(ms)', stamps.join(','));
  // 前 5 个 ~0ms（突发），第 6/7/8 个约 200/400/600ms（匀速补桶）
})();
```

**必须覆盖的边界**：

- **惰性补桶**：用 `setInterval` 每 100ms 加 0.5 个令牌，精度受定时器精度与后台节流影响，还会在页面隐藏时堆积回调；惰性补桶是 O(1) 纯计算，零定时器开销。
- **`tokens` 封顶 capacity**：不封顶的话，空闲 1 小时会攒出 3600 个令牌，一次放 3600 个请求，等于没限流。
- **首次 `last` 初始化**：设为构造时刻即可；若设为 0，第一次调用会算出巨大 elapsed 直接满桶（结果无害但语义错）。
- **补桶与放行的顺序**：必须先 refill 再判 tokens，否则刚到的令牌要等下一轮才生效，吞吐偏低。
- **定时器合并**：`#schedule` 里加 `this.timer` 判空，否则每次 acquire 失败都排一个 timer，队列越长回调越多。
- **多令牌请求**：`acquire(5)`（如批量接口按条数计费）需要单独的等待阈值，不能只判 `>= 1`。

**追问链**：

1. **令牌桶 vs 漏桶的本质差别？** → 令牌桶以「桶里有多少令牌」决定放行，桶可攒，所以允许突发；漏桶以「水位是否溢出」决定拒绝，输出恒定，是纯整形器。前者保护自己（抗突发），后者保护下游（削峰）。
2. **固定窗口的边界突刺怎么产生？** → 1 秒 100 次的窗口，在第 0.99 秒打 100 次、第 1.01 秒再打 100 次，跨窗口的 200ms 内实际过了 200 次。
3. **分布式场景怎么限流？** → 单机内存只能限单实例，多实例要 Redis + Lua 脚本原子执行「读 tokens、算 delta、扣减、回写」，或直接用网关层的集群限流。
4. **前端真的需要限流吗？** → 需要：搜索联想、滚动加载、埋点上报都是高频入口，前端限流能省掉大量注定被 429 的请求。

### 精讲 4 · [HW-079] 请求去重合并器

**为什么考这个**：列表页里 20 个商品卡片同时请求详情，浏览器并发就 6 个，剩下 14 个排队——用户看到的是「卡片一个个慢慢亮」。合并器把 20 次请求压成 1 次批量接口，这是「性能优化」从配置层面下沉到架构层面的典型题。

**标准实现**：
```javascript
class RequestMerger {
  constructor(batchFn, { window = 'microtask' } = {}) {
    this.batchFn = batchFn;
    this.inflight = new Map();   // key -> Promise（同 key 共享同一个 Promise）
    this.pending = new Map();    // key -> { resolve, reject }（当前批次）
    this.scheduled = false;
    this.window = window;
  }

  get(key) {
    if (this.inflight.has(key)) return this.inflight.get(key);      // ① 并发去重

    const p = new Promise((resolve, reject) => {
      this.pending.set(key, { resolve, reject });
    });
    this.inflight.set(key, p);

    if (!this.scheduled) {                    // ② 合批：同一轮同步代码只发一次
      this.scheduled = true;
      queueMicrotask(() => this.#flush());
    }
    return p;
  }

  async #flush() {
    this.scheduled = false;
    const batch = this.pending;               // 取走并重置，后续新请求进入下一批
    this.pending = new Map();
    const keys = [...batch.keys()];

    const settle = (fn) => {
      for (const k of keys) {
        this.inflight.delete(k);              // 先清在途：失败后允许重试
        fn(batch.get(k), k);
      }
    };

    try {
      const results = await this.batchFn(keys);       // 一次批量请求
      settle(({ resolve, reject }, k) =>
        results.has(k) ? resolve(results.get(k)) : reject(new Error(`缺少结果 ${k}`)));
    } catch (err) {
      settle(({ reject }) => reject(err));            // 失败分发：所有等待者一起 reject
    }
  }
}

// ===== 可运行验证：5 次调用（a/b 各重复一次）应合并成 1 次批量请求 =====
(async () => {
  const calls = [];
  const merger = new RequestMerger(async (keys) => {
    calls.push([...keys]);
    await new Promise((r) => setTimeout(r, 5));
    return new Map(keys.map((k) => [k, `item:${k}`]));
  });
  const out = await Promise.all(['a', 'b', 'a', 'c', 'b'].map((k) => merger.get(k)));
  console.log(out.join('|'));                       // item:a|item:b|item:a|item:c|item:b
  console.log('批量次数', calls.length, '批次key', calls[0].join(','));   // 1 a,b,c
})();
```

**必须覆盖的边界**：

- **两层次要分开**：同 key 去重（共享 Promise）解决「重复请求」，合批（微任务窗口）解决「小请求碎片化」，前者是 Map 查在途，后者是攒批发送。
- **失败必须分发**：批量接口整体 500 时，所有等待者都要 reject，否则调用方的 loading 永不结束，界面卡死。
- **失败要清 inflight**：不清的话这个 key 永久返回那个已 reject 的 Promise，用户点重试也没用。
- **单 key 缺结果**：批量接口可能部分成功，缺的那个要单独 reject，不能静默 resolve(undefined)。
- **窗口不能太长**：微任务窗口是「同一轮同步代码」；用 `setTimeout(0)` 会把首屏关键的单个请求硬拖一帧。
- **缓存不是去重**：去重只共享「在途」，请求结束后必须能再次发起（数据会变）。

**追问链**：

1. **为什么用 microtask 而不是 setTimeout？** → 同一轮渲染/事件处理里发起的请求天然属于同一批，微任务在当前宏任务结束时立刻执行，延迟最小；setTimeout 至少多等一个任务队列轮次。
2. **`Promise.all` 里同一个 Promise 出现两次会怎样？** → 不会重复执行，两次 await 拿到同一个结果——这正是去重的基础。
3. **怎么扩展成「带缓存」的版本？** → inflight 之外再加一层 TTL Map（HW-078），命中未过期缓存直接返回；注意缓存 key 要含参数指纹。
4. **批量接口本身有上限（如一次 50 个 id）怎么办？** → flush 时按 chunk 切分（HW-053），多批并发发送，结果合并后统一分发。

### 精讲 5 · [HW-066] 优先级任务队列（并发上限 + 抢占 + 去重）

**为什么考这个**：p-limit 不分轻重，用户点击和后台预取在一个队列里排队，点击会被预取堵住 300ms。优先级队列考的正是「你能不能识别出流量有等级」——这是做基础设施与写业务代码的分水岭。

**标准实现**：
```javascript
class PriorityQueue {
  constructor(concurrency = 4) {
    if (!Number.isInteger(concurrency) || concurrency < 1) throw new TypeError('并发数必须为正整数');
    this.limit = concurrency;
    this.active = 0;
    this.buckets = new Map();     // priority -> job[]（同优先级 FIFO，靠数组顺序保序）
    this.levels = [];             // 已排序的优先级（降序），避免每次取任务都 sort
    this.dedupe = new Map();      // dedupeKey -> Promise
  }

  push(task, { priority = 0, dedupeKey } = {}) {
    if (dedupeKey && this.dedupe.has(dedupeKey)) return this.dedupe.get(dedupeKey);

    const p = new Promise((resolve, reject) => {
      if (!this.buckets.has(priority)) {
        this.buckets.set(priority, []);
        this.levels.push(priority);
        this.levels.sort((a, b) => b - a);      // 只在新增层级时排序，O(k log k)
      }
      this.buckets.get(priority).push({ task, resolve, reject });
    });

    if (dedupeKey) {
      this.dedupe.set(dedupeKey, p);
      const clean = () => this.dedupe.delete(dedupeKey);
      p.then(clean, clean);                     // 成败都清，避免缓存已失效的结果
    }
    this.#drain();
    return p;
  }

  #take() {                                     // 取最高优先级桶的队头
    for (const lv of this.levels) {
      const arr = this.buckets.get(lv);
      if (arr.length) return arr.shift();
    }
    return null;
  }

  #drain() {
    while (this.active < this.limit) {
      const job = this.#take();
      if (!job) return;
      this.active++;
      Promise.resolve().then(job.task)
        .then(job.resolve, job.reject)
        .finally(() => { this.active--; this.#drain(); });   // 释放后重新按优先级取
    }
  }
}

// ===== 可运行验证：并发 1，观察插队顺序 =====
(async () => {
  const q = new PriorityQueue(1);
  const order = [];
  const job = (name, priority) => q.push(async () => {
    await new Promise((r) => setTimeout(r, 1));
    order.push(name);
    return name;
  }, { priority });

  await Promise.all([
    job('prefetch-1', 0),   // 先到，立刻占住唯一槽位
    job('prefetch-2', 0),
    job('click', 10),       // 排队中，但优先级最高
    job('idle-1', -1),
    job('hover', 5),
  ]);
  console.log(order.join(' > '));   // prefetch-1 > click > hover > prefetch-2 > idle-1
})();
```

**必须覆盖的边界**：

- **同优先级 FIFO**：用 Map 分桶 + 数组 push/shift 天然保序；若把全部任务放一个数组每次 sort，同优先级顺序会因排序不稳定而抖动。
- **不在途抢占，只排队插队**：一旦 `active` 满了，新来的高优任务只能等槽位释放；真要抢占得 abort 低优在途请求，那是 HW-082 的活，不要混在这一题里。
- **去重必须按 key 共享 Promise**，且任务结束后清 key，否则「同样的请求第二次发出」会被错误地复用第一次的结果。
- **优先级排序成本**：`levels` 缓存排序结果，避免每次取任务 `sort` 一次队列（O(n log n) 放在热路径上会被压测打出来）。
- **饥饿**：持续有高优任务涌入时低优任务永远排不到；真实系统要加老化（等待超过 N ms 提升优先级）。
- **异常任务**：`task` reject 必须继续 drain，否则一个失败任务让整个队列停摆。

**追问链**：

1. **优先级队列用堆还是分桶？** → 优先级是离散小集合（如 -1/0/5/10）时分桶 O(1) 更划算；优先级连续或范围极广时用二叉堆。前端场景几乎没有连续优先级，分桶更实用。
2. **「抢占」到底要不要做？** → 只对可丢弃的请求做（预取、埋点、图片），对写请求抢占会造成数据不一致；生产上用 AbortController 取消最低优在途。
3. **去重和合并的区别？** → 去重是同 key 共享一个结果；合并是不同 key 打成一个批量接口（HW-079），二者可叠加：先合批，再对整批做去重。
4. **队列要不要持久化？** → 页面级队列不持久化；离线场景（HW-108）要落 IndexedDB，恢复时按原优先级重排。

### 精讲 6 · [HW-109] 请求取消管理器（AbortController 编排）

**为什么考这个**：输入框每敲一个字符发一次搜索，不取消就会有一堆请求在飞，回来的顺序还不保证——这是真实项目里最常见的线上 bug。能把手写「取消管理器」写利落，说明你理解 AbortSignal 的生命周期，而不是只会 `ctrl.abort()`。

**标准实现**：
```javascript
class AbortManager {
  constructor() {
    this.map = new Map();                       // key -> AbortController
    if (typeof addEventListener === 'function') {
      // 页面卸载/进后台时全量取消，避免僵尸请求回填已销毁的组件
      addEventListener('pagehide', () => this.abortAll());
    }
  }

  run(key, task, { signal: outer } = {}) {
    this.abort(key);                            // 同 key 新请求 → 取消旧请求（竞态治理）
    const ctrl = new AbortController();
    const signal = outer ? AbortSignal.any([ctrl.signal, outer]) : ctrl.signal;
    this.map.set(key, ctrl);

    return Promise.resolve()
      .then(() => {
        // 取消可能发生在任务启动前的微任务窗口：信号已 abort 就不能再跑
        if (signal.aborted) throw signal.reason ?? new DOMException('aborted', 'AbortError');
        return task(signal);
      })
      .finally(() => {
        if (this.map.get(key) === ctrl) this.map.delete(key);   // 只清自己，别清掉后任
      });
  }

  abort(key, reason = 'superseded') {
    const ctrl = this.map.get(key);
    if (!ctrl) return false;
    this.map.delete(key);
    ctrl.abort(new DOMException(reason, 'AbortError'));   // 带上 reason 便于区分取消来源
    return true;
  }

  abortAll() {
    for (const ctrl of this.map.values()) ctrl.abort(new DOMException('unmount', 'AbortError'));
    this.map.clear();
  }

  get size() { return this.map.size; }
}

// ===== 可运行验证：模拟可取消的请求 =====
const fakeRequest = (url, signal, ms) => new Promise((resolve, reject) => {
  const timer = setTimeout(() => resolve(`data:${url}`), ms);
  signal.addEventListener('abort', () => {
    clearTimeout(timer);
    reject(signal.reason ?? new DOMException('aborted', 'AbortError'));
  }, { once: true });
});

(async () => {
  const mgr = new AbortManager();
  const p1 = mgr.run('search', (s) => fakeRequest('q=a', s, 50))
    .catch((e) => `cancelled:${e.name}`);
  const p2 = mgr.run('search', (s) => fakeRequest('q=ab', s, 10));
  console.log(await p1, await p2);            // cancelled:AbortError data:q=ab

  const p3 = mgr.run('detail', (s) => fakeRequest('d/1', s, 100))
    .catch((e) => `cancelled:${e.name}`);
  mgr.abortAll();
  console.log(await p3, '剩余在途', mgr.size);  // cancelled:AbortError 剩余在途 0
})();
```

**必须覆盖的边界**：

- **同 key 自动取消**：这是 90% 的使用场景（搜索、tab 切换、详情页切商品），把「取消旧请求」内建到 run 里，业务代码就永远不会忘。
- **finally 里的身份校验**：`this.map.get(key) === ctrl` 必须比对，否则后发请求完成后会把新请求的 controller 删掉，新请求就再也取消不了。
- **abort 之后 fetch 的 reject 是 AbortError**：调用方要单独识别并静默，不能当作错误弹 toast。
- **`AbortSignal.any` 合并**：业务取消 + 组件卸载/超时两个来源都要能中断；Node 18 以下需 polyfill 或手工 addEventListener 转发。
- **abort 与启动的微任务窗口**：`run` 里用 `Promise.resolve().then` 延后执行任务，若两次 `run` 在同一轮同步代码里发生，第二个的 `abort` 会先于第一个任务启动；不查 `signal.aborted` 就会「取消了却照跑」。
- **不要在 abort 后删 controller 还留着 signal**：signal 一旦 abort 就永久 aborted，复用会导致所有新请求立刻失败——每次 run 必须新建 controller。
- **取消 ≠ 服务端没执行**：abort 只关闭连接，服务端可能已经处理完，写请求不能依赖取消做补偿。

**追问链**：

1. **abort 之后还能拿到响应吗？** → 不能，fetch 会以 AbortError reject，response body 也读不了；务必在业务层判 `e.name === 'AbortError'`。
2. **AbortController 和防抖的关系？** → 防抖减少请求数量，取消处理「已经发出的多余请求」，两者互补；只防抖不取消，慢网络下仍会有过期响应覆盖新结果。
3. **怎么给请求加超时？** → `AbortSignal.timeout(5000)` 与业务 signal 用 `AbortSignal.any` 合并；超时和取消的区分靠 `reason.name`（TimeoutError / AbortError）。
4. **卸载后 setState 警告怎么根治？** → 取消只是省流量，真正的根治是序号/mounted 标志双保险（HW-117），因为 abort 有竞态窗口：响应已到、setState 未执行时卸载仍会写入。

### 四种限流器的选择依据

| 算法 | 允许突发 | 输出速率 | 内存 | 适用场景 |
|---|---|---|---|---|
| 固定窗口 | 交界处 2 倍 | 不平滑 | O(1) | 粗粒度配额（每日调用数） |
| 滑动窗口（队列） | 不允许超限 | 平滑 | O(limit) | 精确 QPS 限制，量不大 |
| 滑动窗口（分桶） | 近似 | 近似平滑 | O(buckets) | 高 QPS 近似限流 |
| 令牌桶 | 允许（容量内） | 长期匀速 | O(1) | 允许 Burst 的 API 网关 |
| 漏桶 | 不允许 | 恒定 | O(1) | 保护脆弱下游、第三方 API |

## 常见扣分点

| 扣分点 | 后果 | 正确做法 |
|---|---|---|
| 释放槽位写在 then 里而不是 finally | 任务失败后并发数永久 -1，队列卡死 | `finally(() => release())` |
| 队列里直接存 `fn()` 的执行结果 | 请求立刻发出，限流完全失效 | 队列存启动器，出队时才调用 |
| retry 缓存第一次的 Promise | 重试永远拿到同一个失败 | 每次 `attempt` 重新调用 `fn()` |
| retry 最终 `reject(undefined)` | 调用方拿不到真实错误 | `throw lastErr` |
| 令牌桶用 `setInterval` 补桶 | 定时器泄漏、后台节流后精度崩 | 惰性补桶（时间差计算） |
| 令牌数不封顶 capacity | 空闲后一次放出全部积压 | `Math.min(capacity, ...)` |
| abort 后复用同一个 controller | 新请求立刻 AbortError | 每次请求新建 controller |
| 只做 Abort 不做序号校验 | 响应已到、卸载瞬间仍写入 | 序号 + Abort 双保险 |
| 优先级队列每次取任务都 sort | 热路径 O(n log n)，压测掉帧 | 分桶 + 缓存 levels |
| 乐观更新回滚直接恢复快照 | 冲掉其它已成功的操作 | 回滚后按序重放后续成功操作 |
