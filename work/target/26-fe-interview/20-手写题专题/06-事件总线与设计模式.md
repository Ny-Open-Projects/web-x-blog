# 06 事件总线与设计模式

> 这块考的是「同一套骨架，能不能按场景改出不同的约束」。**能力分层**：L1 写得出 API → L2 想得到注销与异常 → L3 说得清边界与取舍。

这一组题的共同点：结构都很小（一个 Map、一个数组、一张表），难点全在**约束**上。EventEmitter 考的是「订阅者集合在遍历中被修改怎么办」；FSM 考的是「非法输入怎么办」；命令栈考的是「什么该合并、什么必须分开」。同一个"数组 + 循环"，加上不同的约束就成了四种模式。写的时候把约束写在注释里，比堆代码更能说明你懂。

### 精讲 1 · [HW-020] 手写 EventEmitter

**为什么考这个**：这是所有「解耦」设计的原子操作，也是考察基本功最快的一题。面试官通常只盯两个细节：`once` 的退订怎么和原函数对上，`emit` 遍历时有人在回调里 `off` 会不会漏触发。

**标准实现**：

```javascript
class EventEmitter {
  constructor() { this.events = new Map(); }   // 事件名 -> Set<handler>

  on(type, fn) {
    if (typeof fn !== 'function') throw new TypeError('listener must be a function');
    if (!this.events.has(type)) this.events.set(type, new Set());
    this.events.get(type).add(fn);             // Set 天然去重：同一 fn 只存一次
    return this;                               // 链式调用（Node 风格）
  }

  once(type, fn) {
    const wrap = (...args) => {
      this.off(type, wrap);                    // 先退订再执行：抛错也不会重复触发
      fn(...args);
    };
    wrap.origin = fn;                          // 记住原函数，off(fn) 也能摘掉
    return this.on(type, wrap);
  }

  off(type, fn) {
    const set = this.events.get(type);
    if (!set) return this;
    if (!fn) { this.events.delete(type); return this; }   // 不传 fn：清空整个事件
    [...set].forEach((h) => {                  // 拷贝：回调内可能继续 off
      if (h === fn || h.origin === fn) set.delete(h);
    });
    if (!set.size) this.events.delete(type);
    return this;
  }

  emit(type, ...args) {
    const set = this.events.get(type);
    if (!set) return false;
    [...set].forEach((fn) => fn(...args));     // 拷贝后遍历：回调里 on/off 不影响本轮
    return true;
  }
}

// ================= 验证 =================
const bus = new EventEmitter();
const log = [];
const onLogin = (user) => log.push('login:' + user);
bus.on('login', onLogin).on('login', onLogin);          // 重复注册被 Set 去重
bus.once('login', (user) => log.push('once:' + user));
bus.emit('login', 'tom');
bus.emit('login', 'tom');                                // once 不再触发
bus.off('login', onLogin);                               // 用原函数摘掉
bus.emit('login', 'jerry');
// once 的 off(fn) 反查验证
const handler = () => log.push('should-not-run');
bus.once('pay', handler);
bus.off('pay', handler);
bus.emit('pay');
console.log(log);
```

四个方法的分工：`on` 存、`once` 包一层、`off` 摘、`emit` 遍历。示例里同一函数注册两次只触发一次（Set 去重），`once` 第二次 `emit` 不再响应，`off(fn)` 能摘掉 `once` 包装过的函数——这三个现象就是三个考点。

**必须覆盖的边界**：
- **遍历前拷贝**：`[...set].forEach`。回调里 `off` 自己或别人时，直接遍历 Set 会跳过元素（删除会影响迭代器），这是最经典的漏触发 bug。
- **once 与原函数的对应**：包装函数要在 `off` 时能被原函数反查，所以挂 `wrap.origin = fn`；否则用户 `off(type, fn)` 摘不掉，泄漏到天荒地老。
- **先退订再执行**：`once` 里先 `off` 再 `fn()`，这样回调抛错也不会被重复触发。
- **空集合清理**：事件全部退订后删掉 Map 的 key，否则长生命周期总线会积累一堆空 Set。
- **类型校验**：`on` 时校验 fn 是函数，早失败好过 emit 时才 `TypeError`。
- **链式调用**：`return this`，Node 风格，也让 `bus.on().on()` 可读。

**追问链**：
1. **emit 时新增的监听会不会在本轮触发？** → 不会，因为遍历的是拷贝。这是刻意的语义：本轮事件的订阅者集合在派发开始时就确定了。
2. **on 里做去重合理吗？** → 分场景。浏览器 `addEventListener` 会自动去重，Node 的 EventEmitter 允许重复（同一函数可注册多次）；示例选了去重，回答时要说明这是产品决策而不是唯一解。
3. **内存泄漏怎么排查？** → 组件卸载没 `off` 是首因；调试时打印 `events` 的 key 与 size，或给 on 加调用栈记录（开发环境）。
4. **和 DOM 事件的区别？** → DOM 事件有捕获/冒泡、`stopPropagation`、`preventDefault`；总线是平铺的，需要命名空间和优先级就得上 HW-315 的增强版。

### 精讲 2 · [HW-028] 手写任务队列（串行执行）

**为什么考这个**：串行队列是「把不稳定的一堆操作排成一条线」的基本功，上传、埋点、离线操作重放都靠它。核心就一句：**用 Promise 接力，而不是循环 await**。前者能在运行时持续加任务，后者只能处理固定数组。

**标准实现**：

```javascript
class SerialQueue {
  constructor() {
    this.tail = Promise.resolve();   // 队尾指针：永远指向「最后一个任务结束」
    this.size = 0;
  }

  add(task) {
    this.size += 1;
    // 接力：新任务挂在上一个任务的 then 后面 → 天然串行，且支持运行时动态加任务
    const result = this.tail.then(() => task());
    // 队尾必须吞掉错误，否则一次失败会让后面所有任务都落进 rejected 链
    this.tail = result.then(
      () => { this.size -= 1; },
      () => { this.size -= 1; },
    );
    return result;                   // 对外仍返回真实结果（可能 reject）
  }

  addAll(tasks) {
    return Promise.allSettled(tasks.map((t) => this.add(t)));
  }

  idle() { return this.tail; }        // 等队列排空
}

// ================= 验证 =================
const q = new SerialQueue();
const log = [];
const task = (name, ms, fail = false) => () =>
  new Promise((resolve, reject) => {
    log.push('start:' + name);
    setTimeout(() => {
      if (fail) { log.push('fail:' + name); reject(new Error(name)); }
      else { log.push('end:' + name); resolve(name); }
    }, ms);
  });

const t1 = q.add(task('A', 30));
const t2 = q.add(task('B', 5, true));      // 中间一个失败
const t3 = q.add(task('C', 5));            // 后续任务照常执行

Promise.allSettled([t1, t2, t3]).then((results) => {
  console.log('执行顺序:', log.join(' -> '));
  console.log('各自结果:', results.map((r) => r.status));
  console.log('队列剩余:', q.size);
});
```

示例里 A 慢、B 失败、C 快，执行顺序严格是 `A 结束 → B 开始 → B 失败 → C 开始`。注意 `Promise.allSettled` 拿到的三个结果分别是 fulfilled / rejected / fulfilled，说明「一个失败不阻塞后续」和「每个任务的结果对调用方可见」同时成立。

**必须覆盖的边界**：
- **队尾要吞错误**：`this.tail = result.catch(() => {})`。不吞的话，一旦某个任务 reject，后面所有任务都是「在 rejected 链上 then」，整条队列报废。
- **对外保留真实结果**：吞错误只影响队尾指针，`add` 返回值必须是原始 promise，调用方才能 `await` 到自己的异常。
- **动态追加**：`add` 可以在任意时刻调用，新任务自然接在队尾；这是链式优于 `for...of await` 的地方。
- **size 的增减**：成功和失败两条路径都要减，否则监控面板上队列永远「没排空」。
- **一次只跑一个**：真正的串行是 `tail.then(task)`，不要写成 `Promise.all` 或提前 `task()`（提前调用就已经并发了）。
- **可等待排空**：暴露 `idle()`，便于测试和「关闭前确保写入完成」。

**追问链**：
1. **暂停/恢复怎么做？** → 不直接暂停 promise 链，而是引入一个「闸门」promise：`await gate`，`pause()` 时把 gate 换成 pending，`resume()` 时 resolve 旧 gate。不要在任务内部 sleep 轮询。
2. **和并发控制（plimit）什么关系？** → 串行是并发上限为 1 的特例；plimit 用「正在跑的数量 + 等待队列」调度，队列用 shift/push 即可。
3. **优先级怎么加？** → 从 FIFO 队列换成小顶堆或按 priority 分桶，取任务时先取高优桶；注意高优任务连续插入会饿死低优任务，需要老化（aging）。
4. **失败要重试怎么办？** → 在任务外包一层 retry（指数退避），重试仍失败再抛给调用方；不要重试整个队列。

### 精讲 3 · [HW-074] 手写有限状态机（FSM）

**为什么考这个**：一切「多步流程 + 状态」的 UI 都能被 FSM 收拾干净。硬编码 `if (status === 'x')` 的代码，两三步之后必然出现「不可能的中间态」。FSM 把状态转移变成**数据**，非法路径在运行时就被拦住。

**标准实现**：

```javascript
class FSM {
  constructor({ initial, states = {}, transitions, strict = true }) {
    this.state = initial;
    this.states = states;              // { idle: { entry, exit } }
    this.transitions = transitions;    // { idle: { START: 'running' | { to, guard } } }
    this.strict = strict;              // 非法事件：true 抛错，false 忽略
  }

  can(event) {
    return Boolean(this.transitions[this.state]?.[event]);
  }

  async dispatch(event, payload) {
    const t = this.transitions[this.state]?.[event];
    if (!t) {
      if (!this.strict) return false;
      throw new Error(`非法转移：${this.state} --${event}--> ?`);
    }
    const to = typeof t === 'string' ? t : t.to;
    const guard = typeof t === 'object' ? t.guard : undefined;
    if (guard && !(await guard(payload, this.state))) return false;   // 条件不满足：状态不变

    const from = this.state;
    await this.states[from]?.exit?.(payload, to);   // 1. 离开旧状态
    this.state = to;                                 // 2. 执行转移
    await this.states[to]?.entry?.(payload, from);   // 3. 进入新状态
    return true;
  }
}

// ================= 验证 =================
const log = [];
const machine = new FSM({
  initial: 'idle',
  states: {
    idle: { exit: () => log.push('exit:idle') },
    running: { entry: () => log.push('entry:running'), exit: () => log.push('exit:running') },
    done: { entry: () => log.push('entry:done') },
  },
  transitions: {
    idle: { START: 'running' },
    running: { FINISH: { to: 'done', guard: (p) => p.ok === true } },   // 带守卫
  },
});

(async () => {
  console.log('can START:', machine.can('START'), '| can FINISH:', machine.can('FINISH'));
  await machine.dispatch('START');
  console.log('状态:', machine.state, '| 钩子:', log.join(' > '));

  const blocked = await machine.dispatch('FINISH', { ok: false });   // 守卫拦截
  console.log('守卫拦截:', blocked, '状态仍为:', machine.state);

  await machine.dispatch('FINISH', { ok: true });
  console.log('最终状态:', machine.state);

  try { await machine.dispatch('START'); }                            // 非法转移
  catch (e) { console.log('捕获:', e.message); }
})();
```

输出的三行就是三个考点：`can` 是「事前询问」，避免按钮可点却报错；守卫返回 false 时状态**保持不变**（既不改状态也不触发钩子）；非法事件抛出的错误里带上了 `from --event-->` 上下文，方便定位。

**必须覆盖的边界**：
- **转移表而不是 if 链**：`transitions[from][event] = to | { to, guard }`，新增状态只改数据，不改逻辑。
- **非法转移的策略可配置**：`strict: true` 抛错（开发环境），`false` 返回 false（生产环境容错），默认值要想清楚。
- **钩子顺序**：`exit(from)` → 改状态 → `entry(to)`。顺序错了会出现「entry 时读到的还是旧状态」。
- **钩子可以是异步的**：`await` 保证 entry 里的请求/动画完成后再算转移结束，否则外部拿到的是中间态。
- **守卫先行**：guard 不通过时不能触发任何钩子，否则会出现「exit 跑了但没进新状态」的脏局面。
- **guard 里不要改状态**：守卫只做判断，副作用放 entry/exit。

**追问链**：
1. **FSM 和状态模式（GoF）的区别？** → 状态模式把每个状态的行为封装成对象/类，靠多态分派；FSM 把转移关系抽成表，靠数据驱动。前者适合状态行为差异大，后者适合状态多、转移规则复杂。
2. **状态爆炸怎么办？** → 分层状态机（HLSM，子状态继承父状态的转移）或状态图（statechart）+ 正交区域；再复杂就上 XState。
3. **guard 里要发请求可以吗？** → 不建议，guard 应是纯判断；需要异步校验就先 `await check()` 再把结果作为 payload 传入 dispatch。
4. **前端哪里真的用得到？** → 播放器（idle/buffering/playing/paused）、上传（pending/uploading/success/failed）、订单状态、多步表单；配合 XState 还能可视化。

### 精讲 4 · [HW-100] 手写 undo/redo 命令栈

**为什么考这个**：编辑器、画板、表单草稿都绕不开撤销。面试官要看的是三件事：命令对象的接口是不是**可泛化**、连续操作为什么要合并、redo 分支什么时候清空。

**标准实现**：

```javascript
class CommandStack {
  constructor({ limit = 100, coalesceMs = 500 } = {}) {
    this.limit = limit;
    this.coalesceMs = coalesceMs;
    this.done = [];
    this.undone = [];
  }

  execute(cmd) {
    cmd.execute();
    cmd.time = Date.now();
    const last = this.done[this.done.length - 1];
    // 合并：连续同类型操作（连续打字）合成一条，undo 一次退掉一整段
    if (last && last.mergeWith?.(cmd, this.coalesceMs)) {
      cmd.merged = true;                     // 新命令已被吸收，不入栈
    } else {
      this.done.push(cmd);
      if (this.done.length > this.limit) this.done.shift();   // 容量上限：丢最旧
    }
    this.undone.length = 0;                  // 新操作清空 redo 分支
    return this;
  }

  undo() {
    const cmd = this.done.pop();
    if (!cmd) return false;
    cmd.undo();
    this.undone.push(cmd);                   // 移到 redo 栈
    return true;
  }

  redo() {
    const cmd = this.undone.pop();
    if (!cmd) return false;
    cmd.execute();
    this.done.push(cmd);
    return true;
  }
}

// 命令对象：只要求 execute / undo，可选 mergeWith（返回 true 表示已合并）
class TypingCommand {
  constructor(doc, char, at) {
    this.doc = doc; this.text = char; this.at = at; this.time = 0;
  }
  execute() {
    this.doc.value = this.doc.value.slice(0, this.at) + this.text + this.doc.value.slice(this.at);
  }
  undo() {
    this.doc.value = this.doc.value.slice(0, this.at) + this.doc.value.slice(this.at + this.text.length);
  }
  mergeWith(next, windowMs) {
    const adjacent = next.at === this.at + this.text.length;     // 紧挨着往后打
    if (!adjacent || next.time - this.time > windowMs) return false;
    this.text += next.text;                                      // 吸收新字符
    this.time = next.time;
    return true;
  }
}

// ================= 验证 =================
const doc = { value: '' };
const stack = new CommandStack({ limit: 3, coalesceMs: 500 });
const type = (text, at) => stack.execute(new TypingCommand(doc, text, at));

type('h', 0);
type('i', 1);
type('!', 2);                       // 三次连续输入 → 合并成 1 条命令
console.log('内容:', doc.value, '| 栈深:', stack.done.length);
stack.undo();
console.log('undo 一次后:', JSON.stringify(doc.value), '| 栈深:', stack.done.length);
stack.redo();
console.log('redo 后:', doc.value);

type('X', 0);                       // 新操作清空 redo
console.log('redo 可用:', stack.redo(), '| 内容:', doc.value);
for (let i = 0; i < 5; i += 1) type(String(i), 0);   // 超出 limit=3
console.log('容量上限后栈深:', stack.done.length, '| 内容:', doc.value.slice(0, 3));
```

跑出来的关键三行：连打三个字符后 **栈深仍然是 1**（合并生效），undo 一次把 `hi!` 整段退掉，redo 又整段回来；新操作之后 redo 返回 false（分支被清空）；limit=3 时连续 5 次操作只留最后 3 条。

**必须覆盖的边界**：
- **命令接口最小化**：只要 `execute()` / `undo()`，其余（合并、时间戳、分组 id）都是可选能力；接口越小越容易泛化到画板、表格、表单。
- **合并窗口**：同类型 + 位置相邻 + 时间间隔小于 `coalesceMs` 才合并。三个条件缺一个都会把「用户以为的两步」合成一步。
- **合并后的 undo 语义**：合并命令的 `undo` 必须一次退掉整段（示例里 `text` 累加，undo 按整段长度删除）。
- **redo 清空**：新操作入栈时 `undone.length = 0`，这是标准的线性历史模型；要保留分支就得画 DAG，但用户无法理解。
- **容量上限**：`shift()` 丢最旧。注意丢的应该是最旧而不是最新，且被丢的命令不能再被 undo。
- **undo 里不要再 execute**：`undo()` 是逆操作，不是「重放旧命令」；命令必须自己保存逆操作所需的数据（示例里靠 `at` + `text.length`）。

**追问链**：
1. **怎么保证 undo/redo 幂等？** → 命令执行前后状态必须可推导：`execute` 记录 before/after 快照，`undo` 恢复 before。最稳的做法是命令里存「逆操作参数」，而不是重算。
2. **连续操作合并的边界在哪？** → 光标移动、失焦、切换字段、超过时间窗都应强制断组（`breakGroup()`）；否则用户 undo 一次会退掉一大段，体验极差。
3. **撤销栈要不要持久化？** → 编辑器通常只在内存里存，草稿持久化存「当前文档」而不是历史；要跨刷新撤销就得把命令序列化，成本和风险都高。
4. **和不可变数据（immutable）怎么配合？** → 直接存整棵快照最省心，代价是内存；可以只存结构共享后的根引用（immer 的 patches 就是天然的 undo/redo 记录）。

### 精讲 5 · [HW-315] 手写增强事件总线（命名空间 / 通配 / 异步）

**为什么考这个**：普通 EventEmitter 只能撑一个小模块，中大型应用的事件名会迅速长成 `user:login:success` 这种字符串拼接。命名空间解决「按模块批量卸载」，通配解决「不想枚举所有事件」，异步聚合解决「一个监听报错拖垮全场」。

**标准实现**：

```javascript
class EnhancedEmitter {
  constructor() { this.handlers = new Map(); }   // event|pattern -> Set<{ fn, ns }>

  on(event, fn, { ns = '' } = {}) {
    let set = this.handlers.get(event);
    if (!set) this.handlers.set(event, (set = new Set()));
    for (const h of set) if (h.fn === fn) return () => {};   // 同 fn 去重，返回空取消函数
    const record = { fn, ns };
    set.add(record);
    return () => {                                            // 返回取消订阅函数
      set.delete(record);
      if (!set.size) this.handlers.delete(event);
    };
  }

  offNs(ns) {                                   // 按命名空间批量移除（跨事件）
    for (const [event, set] of this.handlers) {
      [...set].forEach((h) => { if (h.ns === ns) set.delete(h); });
      if (!set.size) this.handlers.delete(event);
    }
    return this;
  }

  _match(event) {
    const hit = [];
    for (const [pattern, set] of this.handlers) {
      if (pattern === event) { hit.push(...set); continue; }
      if (!pattern.endsWith('.*')) continue;
      const prefix = pattern.slice(0, -1);                    // 'user.*' -> 'user.'
      if (event.startsWith(prefix) && !event.slice(prefix.length).includes('.')) {
        hit.push(...set);                                     // 通配只吃末段：不匹配 user.a.b
      }
    }
    return hit;
  }

  async emit(event, payload) {
    const handlers = this._match(event);
    // 异步监听：allSettled 聚合，单个失败不影响其余监听者，也不会 unhandledRejection
    const results = await Promise.allSettled(handlers.map((h) => h.fn(payload, event)));
    const failed = results.filter((r) => r.status === 'rejected');
    return { count: handlers.length, failed: failed.length, results };
  }
}

// ================= 验证 =================
const bus = new EnhancedEmitter();
const log = [];
bus.on('user.login', (p) => { log.push('exact:' + p.name); });
bus.on('user.*', (p, evt) => { log.push(`wild:${evt}:${p.name}`); }, { ns: 'analytics' });
bus.on('user.*', async () => { throw new Error('埋点失败'); }, { ns: 'analytics' });   // 故意抛错
bus.on('user.*', (p) => log.push('also:' + p.name));

(async () => {
  const r1 = await bus.emit('user.login', { name: 'tom' });
  console.log('命中:', r1.count, '失败:', r1.failed);
  console.log('日志:', log.join(' | '));

  const r2 = await bus.emit('user.login.deep', { name: 'tom' });   // 末段通配不匹配多级
  console.log('多级事件命中:', r2.count);

  bus.offNs('analytics');                                           // 批量移除命名空间
  const r3 = await bus.emit('user.login', { name: 'jerry' });
  console.log('移除后命中:', r3.count, '失败:', r3.failed);
})();
```

验证输出体现了四个设计：`user.login` 同时命中精确订阅与 `user.*` 通配（4 个监听）；其中一个监听故意抛错，`allSettled` 把它记成 failed 但其余照常执行；`user.login.deep` 不被 `user.*` 匹配（通配只吃末段）；`offNs('analytics')` 一次摘掉两个带命名空间的监听。

**必须覆盖的边界**：
- **同一个 fn 去重**：Set 存 `{ fn, ns }` 记录对象而不是裸函数，否则同名不同命名空间的注册会被误删。
- **返回取消函数**：`on` 返回 `() => set.delete(record)`，组件卸载时不用记事件名；这是与 React effect 最契合的形态。
- **通配只匹配末段**：`user.*` 匹配 `user.login` 但不匹配 `user.login.deep`。要支持多级通配就得递归拆分（成本高，收益低）。
- **异步不阻断**：`Promise.allSettled` 一定不会 reject，也避免了「忘了 catch 导致 unhandledRejection」。
- **失败要可见**：返回 `{ count, failed, results }`，让调用方能上报，而不是静默吞掉。
- **遍历拷贝**：`_match` 返回的是快照数组，回调里注册/注销不影响本轮。

**追问链**：
1. **为什么不用正则匹配通配？** → 事件名高频触发，正则编译 + 回溯成本高；`startsWith` + 一次 `includes('.')` 足够，且行为可预测。
2. **命名空间和事件名的分隔符怎么选？** → 常用 `:` 分层（`user:login`）+ `#` 标命名空间（`#analytics`），避免与业务里的点号冲突（`user.login` 本身可能就是事件名）。
3. **异步监听会不会打乱顺序？** → 会。`allSettled` 只保证「都结束」，不保证执行顺序；需要顺序就串行 `for...await`，但会拖慢派发。
4. **怎么防内存泄漏？** → 返回的取消函数必须在 `useEffect` 的 cleanup 里调用；再加一个 `offAll()` 用于路由切换时兜底。

### 精讲 6 · [HW-340] 手写插件系统（生命周期 / 隔离 / 依赖）

**为什么考这个**：插件系统是「架构题伪装成手写题」。要同时答出拓扑排序保证加载顺序、异常隔离保证宿主不崩、逆序销毁保证资源释放——这三点分别对应构建、运行时、清理三个阶段。

**标准实现**：

```javascript
class PluginSystem {
  constructor(api = {}, { onError = (e, name, hook) => console.warn('[plugin]', name, hook, e.message) } = {}) {
    this.api = Object.freeze({ ...api });   // 沙箱：插件只能拿到宿主显式暴露的能力
    this.plugins = new Map();
    this.order = [];
    this.onError = onError;
  }

  register(plugin) {
    if (!plugin?.name) throw new Error('plugin.name 必填');
    if (this.plugins.has(plugin.name)) return this;   // 幂等：重复注册直接忽略
    this.plugins.set(plugin.name, plugin);
    return this;
  }

  _resolve() {                              // 拓扑排序：依赖先于使用者
    const order = [];
    const state = new Map();                // 1 = 访问中（用于环检测），2 = 已完成
    const visit = (name) => {
      const s = state.get(name);
      if (s === 2) return;
      if (s === 1) throw new Error(`循环依赖：${name}`);
      const p = this.plugins.get(name);
      if (!p) throw new Error(`缺少依赖：${name}`);
      state.set(name, 1);
      (p.depends || []).forEach(visit);
      state.set(name, 2);
      order.push(name);
    };
    [...this.plugins.keys()].forEach(visit);
    return order;
  }

  async _call(hook, name) {
    const p = this.plugins.get(name);
    const fn = p?.hooks?.[hook];
    if (!fn) return;
    try {
      await fn(this.api, { name, version: p.version });   // 只传受控 API + 元信息
    } catch (e) {
      this.onError(e, name, hook);          // 异常隔离：单插件报错不拖垮宿主与其它插件
    }
  }

  async start() {
    this.order = this._resolve();            // 先做全量校验，失败则不启动任何插件
    for (const name of this.order) await this._call('init', name);
    for (const name of this.order) await this._call('ready', name);
    return this;
  }

  async destroy() {
    for (const name of [...this.order].reverse()) await this._call('destroy', name);  // 逆序释放
    this.order = [];
  }
}

// ================= 验证 =================
const log = [];
const system = new PluginSystem(
  { track: (msg) => log.push('api:' + msg) },
  { onError: (e, name, hook) => log.push(`error:${name}:${hook}`) },
);

system
  .register({
    name: 'i18n', version: '1.0.0',
    hooks: { init: (api) => api.track('i18n init'), ready: () => log.push('i18n ready') },
  })
  .register({
    name: 'chart', version: '1.0.0', depends: ['i18n'],
    hooks: {
      init: () => { throw new Error('依赖没装'); },          // init 抛错也不影响别人
      destroy: () => log.push('chart destroy'),
    },
  })
  .register({
    name: 'theme', version: '1.0.0', depends: ['chart'],
    hooks: { init: () => log.push('theme init'), destroy: () => log.push('theme destroy') },
  });

(async () => {
  await system.start();
  console.log('加载顺序:', system.order.join(' -> '));
  console.log('日志:', log.join(' | '));
  await system.destroy();
  console.log('销毁顺序:', log.slice(-2).join(' | '));

  try { await system.register({ name: 'x', depends: ['nope'] }).start(); }
  catch (e) { console.log('缺失依赖:', e.message); }
})();
```

输出里最值得讲的是这两行：`加载顺序: i18n -> chart -> theme`，虽然注册顺序是 i18n、chart、theme，但依赖声明决定了一切；`日志: api:i18n init | error:chart:init | theme init | i18n ready`，chart 的 init 抛错被隔离成一条 error 记录，theme 照常初始化，宿主完全没感知。销毁时是 `theme -> chart`，严格逆序。

**必须覆盖的边界**：
- **先全量校验再启动**：`_resolve` 一次性检查缺依赖与循环依赖，任何一处不合法就整体失败，避免「启了一半」的脏状态。
- **拓扑排序用三色标记**：未访问 / 访问中 / 已完成。访问中再次遇到就是环，直接报错；只靠递归容易栈溢出且发现不了环。
- **钩子异常隔离**：每个钩子 `try/catch` 并回调 `onError`，绝不让单个插件阻断启动；同时要上报，否则问题永远发现不了。
- **销毁逆序**：后初始化的插件可能依赖先初始化的资源，释放必须反过来；`destroy` 里还要逐个隔离异常，避免第一个报错导致后面全不释放。
- **沙箱只给白名单 API**：`Object.freeze({ ...api })` 防插件改写宿主接口；真正的隔离（iframe/Worker）成本太高，前端插件一般靠约定 + 冻结。
- **注册幂等**：同名插件重复注册直接忽略，避免 HMR 下重复 init。

**追问链**：
1. **循环依赖为什么必须报错而不是警告？** → 环意味着「A 的初始化需要 B 已初始化，B 又需要 A」，任何加载顺序都无法满足；继续执行只会得到半初始化对象和随机 bug。
2. **版本兼容怎么做？** → semver 区间校验：`depends: [{ name: 'i18n', range: '^1.2.0' }]`，用 `semver.satisfies` 判断；不满足就按缺依赖处理。
3. **插件通信怎么设计？** → 只允许通过 host 提供的服务（`api.eventBus`、`api.store`），禁止插件之间直接 import；否则依赖图会退化成网状，卸载变得不可能。
4. **和前端微内核（如 VS Code、Babel）的关系？** → 同一套骨架：内核只定义生命周期与扩展点，能力全在插件里；差别在 Babel 是编译期 visitor 钩子，VS Code 是运行时 activate/deactivate。

## 速览（2 题）

### HW-027 发布订阅

**评分点**：与 EventEmitter 同源，但范式不同——`subscribe` 返回**取消订阅函数**，`publish` 返回命中数量，`once` 用闭包自退订。要和观察者模式区分：发布订阅中间有事件中心，发布者不认识订阅者。

```javascript
function createPubSub() {
  const subs = new Map();
  const off = (type, fn) => {
    const set = subs.get(type);
    if (!set) return;
    set.delete(fn);
    if (!set.size) subs.delete(type);
  };
  return {
    subscribe(type, fn) {
      if (!subs.has(type)) subs.set(type, new Set());
      subs.get(type).add(fn);
      return () => off(type, fn);          // 与 useEffect cleanup 同款范式
    },
    once(type, fn) {
      const un = this.subscribe(type, (...args) => { un(); fn(...args); });
      return un;
    },
    publish(type, ...args) {
      const set = subs.get(type);
      if (!set) return 0;
      [...set].forEach((fn) => fn(...args));   // 拷贝：回调里退订不打乱遍历
      return set.size;
    },
  };
}
```

**追问**：`once` 里为什么先 `un()` 再 `fn()`？→ 语义上「只消费一次」，先退订可以保证回调内部再 `publish` 同一事件时不会重入；同时也避免回调抛错后订阅残留。

### HW-075 状态机驱动的多步表单向导

**评分点**：每一步是一个 state，`next` 的 guard 就是「当前步校验通过」；`back` 保留已填数据；每次前进持久化草稿。校验、流转、持久化三件事分开，不要让按钮的 onClick 里塞满 if。

```javascript
function createWizard({ steps, validate, storage = new Map(), draftKey = 'wizard' }) {
  let index = 0;
  let data = JSON.parse(storage.get?.(draftKey) || '{}');   // 草稿恢复
  const save = () => storage.set?.(draftKey, JSON.stringify(data));
  return {
    get step() { return steps[index]; },
    get data() { return { ...data }; },
    set(field, value) { data[field] = value; save(); return this; },
    next() {
      const msg = validate[steps[index]]?.(data);   // guard：校验不过不许走
      if (msg) return { ok: false, error: msg };
      if (index === steps.length - 1) return { ok: true, done: true, data: { ...data } };
      index += 1; save();
      return { ok: true, step: steps[index] };
    },
    back() { if (index > 0) index -= 1; return { ok: true, step: steps[index] }; },
  };
}
```

**追问**：为什么回退不重新校验？→ 回退是「查看/修改已填内容」，重新校验会拦住用户回到前面修正错误；校验只发生在**前进**与**提交**两个方向。跳步（点步骤条）也必须走 `next` 的 guard 链，逐级判断。

## 设计模式对照

| 模式 | 数据结构 | 解决什么 | 对应题目 |
|---|---|---|---|
| 观察者 | 目标持有观察者数组 | 一对多通知 | EventEmitter |
| 发布订阅 | 事件中心 `Map<type, Set>` | 彻底解耦发布者与订阅者 | HW-020 / HW-027 / HW-315 |
| 状态机 | 转移表 + 当前态 | 约束非法流转 | HW-074 / HW-075 |
| 命令 | `{ execute, undo }` 数组 + 指针 | 可撤销、可回放 | HW-100 |
| 模板方法 / 微内核 | 生命周期钩子数组 | 稳定内核 + 可变扩展 | HW-340 |

## 常见扣分点

| 扣分点 | 后果 | 正确做法 |
|---|---|---|
| emit 直接遍历原 Set | 回调里 off 导致漏触发 | `[...set]` 拷贝后遍历 |
| once 不挂 origin | `off(fn)` 摘不掉，泄漏 | `wrap.origin = fn` 并反查 |
| 队列不吞错误 | 一个失败后续全不跑 | 队尾 `catch(() => {})` |
| FSM 先改状态再校验 | 守卫失败留下脏状态 | 先 guard，再 exit → 改 → entry |
| 合并窗口无时间/位置限制 | 一次 undo 退掉一大段 | 类型 + 相邻 + 时间三重条件 |
| redo 不清空 | 出现分叉历史，用户困惑 | 新命令入栈即清空 undone |
| 通配用正则 | 高频事件上开销大 | 前缀匹配 + 末段判断 |
| 插件顺序按注册序 | 依赖未初始化就使用 | 拓扑排序 + 环检测 |
| 插件销毁正序 | 依赖方先死，释放报错 | 逆序 destroy |

## 现场写题的 5 分钟节奏

1. **先说骨架**：一个 Map 还是两个栈？先讲结构，再写代码，面试官会跟着你的结构走。
2. **把"约束"单独列出来**：注销、异常、顺序、上限——这四类约束是设计模式题的全部难点。
3. **写一个能打印的验证**：触发次数、执行顺序、栈深，三个数字足以证明正确。
4. **主动交代取舍**：为什么通配只支持末段、为什么合并要限时、为什么销毁要逆序。
5. **给一个真实场景**：编辑器撤销、播放器状态、微前端插件，比纯玩具实现可信得多。

## 一句话总结

这八道题共用一副骨架：**注册 → 触发 → 注销**，或者**入栈 → 执行 → 回滚**。骨架只有十行，剩下三十行全在回答「异常、顺序、上限」怎么办——把这三个词写进注释，就是设计模式题的满分答案。
