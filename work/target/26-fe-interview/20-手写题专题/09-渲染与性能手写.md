# 09 渲染与性能手写

> 这块考的是「你做过大列表/大画布没有」。**能力分层**：L1 能写对 → L2 能写全边界 → L3 能讲清指标与取舍。

渲染性能题和白板算法题最大的区别：**代码只是入场券，指标才是答案**。同一个虚拟列表，有人写 20 行能跑，有人说得出「为什么 transform 不重排、Long Task 卡在哪一帧、掉帧率怎么量」，面试评级差两级。所以本专题每道题都按「实现 → 边界 → 追问」三层给，答追问时优先报数字和因果链，不要堆形容词。

## 能力分层

| 层级 | 题目 | 面试要求 |
|---|---|---|
| L1 必会 | 定高虚拟列表 / 基础表格渲染 | 15 分钟内写对，能说清 padding 占位 |

| L3 深水 | 通用虚拟列表引擎 / 视口剔除与 LOD | 能讲清复杂度、降级链与性能指标 |

## 精讲（6 题）

### 精讲 1 · [HW-067] 虚拟列表快速滚动白屏修复

**为什么考这个**：定高虚拟列表谁都会写，但「快速滚动白屏」是真实项目才会遇到的坑——滚动条一甩到底，中间区域闪白半秒。能讲清这一点的候选人很少，因为它要求你理解「滚动位置是连续的，渲染是离散的」这对矛盾。

**标准实现**：
```javascript
// 需浏览器环境（DOM + rAF），node --check 仅能验语法
function createVirtualList(scroller, { itemHeight: H, total, overscan = 8, renderItem }) {
  const spacer = scroller.querySelector('[data-spacer]'); // 撑开滚动条高度
  const layer = scroller.querySelector('[data-layer]');   // 承载绝对定位行
  let range = { start: 0, end: 0 };
  let ticking = false;

  spacer.style.height = `${total * H}px`;

  // 滚动位置 -> 渲染区间：上下各留 overscan 行，抵消一帧内的滚动位移
  const rangeAt = (top) => {
    const first = Math.floor(top / H);
    const count = Math.ceil(scroller.clientHeight / H) + 1;
    return {
      start: Math.max(0, first - overscan),
      end: Math.min(total, first + count + overscan),
    };
  };

  function paint(next) {
    const frag = document.createDocumentFragment();
    for (let i = next.start; i < next.end; i++) {
      const el = renderItem(i);
      el.dataset.index = String(i);
      // 用 transform 定位：走合成层，不触发布局；top 会引发重排
      el.style.transform = `translateY(${i * H}px)`;
      frag.appendChild(el);
    }
    layer.replaceChildren(frag); // 一次替换，只产生一次布局
    range = next;
  }

  function onScroll() {
    if (ticking) return;             // rAF 合帧：一帧最多算一次
    ticking = true;
    requestAnimationFrame(() => {
      ticking = false;
      const next = rangeAt(scroller.scrollTop);
      // 跳变超过两倍缓冲区，说明是「甩动式快速滚动」：
      // 直接以目标区间为锚点整块替换，绝不逐帧补中间状态
      const jumped = Math.abs(next.start - range.start) > overscan * 2;
      if (jumped || next.start !== range.start || next.end !== range.end) paint(next);
    });
  }

  scroller.addEventListener('scroll', onScroll, { passive: true });
  paint(rangeAt(0));
  return { refresh: () => paint(rangeAt(scroller.scrollTop)) };
}
```

**必须覆盖的边界**：
- 滚动事件高频触发 → rAF 合帧，一帧只算一次，`ticking` 防重入。
- 滚动过快跳过中间区 → 锚点定位 + 双向缓冲，绝不渲染空区间。
- 容器高度与总高度不一致 → spacer 撑开 `total * H`，行用绝对定位浮在上面。
- 行节点回收 → 生产版要复用池（Map<index, node>），避免 `replaceChildren` 的 GC 抖动。

**追问链**：
1. 为什么用 transform 而不是 top？→ transform 只触发合成，不参与布局计算；改 top 每帧都会重排整层。
2. 不定高怎么办？→ 预估 + 实测修正 + 缓存，前缀和二分定位，见精讲 2。
3. 怎么验证真的不卡？→ Performance 面板看 Long Task 与掉帧，`PerformanceObserver` 采 longtask，滚动时 FPS 应稳定 55+。
4. overscan 取多大？→ 按「一帧最大滚动距离」反推：快速甩动可达 2000px/帧，8~10 行是折中；太大反而增加 DOM 数量。
5. 为什么不用 IntersectionObserver 做？→ 它能省监听但无法解决「区间跳变」，虚拟列表的核心是算区间而不是感知可见。

### 精讲 2 · [HW-068] 动态高度虚拟列表

**为什么考这个**：真实业务里行高几乎都不固定（评论、商品卡、折叠面板）。这题区分「背过八股」和「真做过」：只会定高公式的人，一遇到实测回写就露馅。

**标准实现**：
```javascript
class DynamicVirtualList {
  constructor({ count, estimate = 60, overscan = 4, viewportHeight }) {
    this.count = count;
    this.estimate = estimate;                 // 未测行的预估值
    this.overscan = overscan;
    this.viewportHeight = viewportHeight;
    this.heights = new Float64Array(count).fill(estimate);
    this.measured = new Uint8Array(count);    // 0 未测 / 1 已测
    this.prefix = this.#buildPrefix();        // prefix[i] = 前 i 行总高
  }

  #buildPrefix() {
    const p = new Float64Array(this.count + 1);
    for (let i = 0; i < this.count; i++) p[i + 1] = p[i] + this.heights[i];
    return p;
  }

  // 二分定位：prefix[i] <= offset < prefix[i+1]，O(logN)
  indexAt(offset) {
    let lo = 0;
    let hi = this.count - 1;
    while (lo < hi) {
      const mid = (lo + hi + 1) >> 1;
      if (this.prefix[mid] <= offset) lo = mid;
      else hi = mid - 1;
    }
    return lo;
  }

  window(scrollTop) {
    const first = this.indexAt(scrollTop);
    const start = Math.max(0, first - this.overscan);
    let end = first;
    let acc = 0;
    while (end < this.count && acc < this.viewportHeight) acc += this.heights[end++];
    end = Math.min(this.count, end + this.overscan);
    return { start, end, padTop: this.prefix[start] };
  }

  // 实测回写：返回高度差，调用方据此补偿 scrollTop，保持视觉不跳
  measure(index, height) {
    if (this.measured[index]) return 0;
    this.measured[index] = 1;
    const delta = height - this.heights[index];
    if (delta === 0) return 0;
    this.heights[index] = height;
    this.prefix = this.#buildPrefix();       // 生产用 Fenwick 树做 O(logN) 增量
    return delta;
  }
}
```

**必须覆盖的边界**：
- 未测行用预估，实测后**只修正一次**（`measured` 位图），防止抖动循环。
- 修正发生在视口上方时，`scrollTop += delta` 做滚动补偿，否则内容会「往上跳」。
- 总高度随实测变化 → 滚动条长度会微调，用阈值（如累计偏差 > 2px）才提交，避免抖。
- 快速滚动到未测区域 → 先按预估渲染，RO 回填后再静默修正，不能让用户看到空白。

**追问链**：
1. 为什么用前缀和 + 二分而不是线性累加？→ 10 万行线性扫描每帧 10 万次，二分 17 次，量级差 4 个数量级。
2. ResizeObserver 会不会打爆主线程？→ 只观察已挂载的 20~30 个节点，回调批量触发；避免在回调里同步改布局。
3. 实测修正导致滚动跳动怎么办？→ 修正点在视口上方时补偿 scrollTop，在下方时不动；锚定首个可见行做 offset 保持。
4. 前缀和每次全量重建 O(N) 能接受吗？→ 1 万行可以，10 万行换 Fenwick 树或分块（block）数组。
5. 能否不做测量？→ 可以，用 CSS `contain-intrinsic-size` 给占位估计值，靠浏览器原生跳过屏外布局，但精度不如实测。

### 精讲 3 · [HW-080] 时间切片调度器

**为什么考这个**：它是 React Fiber 的民间版，考的是「你对主线程是被谁占住的理解」。答得好的人，能顺手解释掉帧、INP 劣化和批量渲染的取舍。

**标准实现**：
```javascript
class TimeSlicer {
  constructor(budget = 5) {
    this.budget = budget;      // 5ms 是常见值：留出样式/布局/合成与输入响应
    this.urgent = [];
    this.normal = [];
    this.running = false;
    this.epoch = 0;            // 紧急任务计数器，用于打断当前切片
  }

  push(task, urgent = false) {
    (urgent ? this.urgent : this.normal).push(task);
    if (urgent) this.epoch++;
    if (!this.running) {
      this.running = true;
      void this.#loop();
    }
    return this;
  }

  async #loop() {
    while (this.urgent.length || this.normal.length) {
      const queue = this.urgent.length ? this.urgent : this.normal;
      const deadline = performance.now() + this.budget;
      const seen = this.epoch;
      while (queue.length && performance.now() < deadline) {
        const task = queue.shift();
        task();
        // 普通队列执行中来了紧急任务：立刻让位，下一轮优先跑 urgent
        if (queue === this.normal && this.epoch !== seen) break;
      }
      if (this.urgent.length || this.normal.length) await this.#yield();
    }
    this.running = false;
  }

  #yield() {
    // 原生让出优先：scheduler.yield 会保留优先级继承，比 setTimeout 更早恢复
    if (typeof scheduler !== 'undefined' && typeof scheduler.yield === 'function') {
      return scheduler.yield();
    }
    return new Promise((resolve) => setTimeout(resolve, 0));
  }
}

// 用法：1 万行分片挂载；用户点击时插队
const slicer = new TimeSlicer(5);
for (const row of rows) slicer.push(() => mountRow(row));
slicer.push(() => applyFilter(keyword), true); // 紧急任务
```

**必须覆盖的边界**：
- 预算按**时间**而不是条数：单条任务可能耗时 3ms，固定条数会超帧。
- 单个任务本身超预算 → 无法抢占（JS 无中断），只能靠任务内再切片或下沉 Worker。
- 让出降级链：`scheduler.yield` → `MessageChannel` → `setTimeout(0)`。
- 重入与空转：`running` 标记保证单循环；队列空必须退出，否则永久微任务循环。

**追问链**：
1. 30ms 还是 5ms？→ 30ms 适合纯计算批处理，但会吃掉 2 帧；与 UI 并存的渲染任务建议 5ms。
2. 为什么不用 `requestIdleCallback`？→ 空闲回调触发时机不可控（可能几百 ms 后），首屏渲染等不起。
3. 紧急任务怎么定义？→ 用户输入（点击、键入）产生的状态更新；用事件优先级映射到 urgent 队列。
4. 怎么证明切片有效？→ 对比 Long Task 数量：切片前单帧 80ms，切片后每帧 < 16ms 且无 > 50ms 任务。
5. 和 Web Worker 怎么选？→ 切片解决「必须操作 DOM」的任务；纯计算且数据可序列化，Worker 更彻底。

### 精讲 4 · [HW-327] 通用虚拟列表引擎

**为什么考这个**：前两题是「一个列表」，这题是「一套列表」——要求你把 fixed / dynamic / horizontal 三种场景抽象成同一组接口。这是 L3 的分水岭：能不能在 40 行内同时支持三种模式，且不写三个 if 分支堆在一起。

**标准实现**：
```javascript
class VirtualEngine {
  constructor({ count, estimate = 40, overscan = 6, axis = 'y' }) {
    this.count = count;
    this.estimate = estimate;     // 唯一的高度/宽度来源：未测即预估
    this.overscan = overscan;
    this.axis = axis;             // 'y' | 'x'：只影响调用方读哪个滚动量
    this.sizes = new Map();       // index -> 实测尺寸（卸载后保留，重进不跳）
    this.dirty = true;
    this.prefix = [0];
  }

  size(i) {
    return this.sizes.get(i) ?? this.estimate;
  }

  #ensure() {
    if (!this.dirty) return;
    const p = new Array(this.count + 1);
    p[0] = 0;
    for (let i = 0; i < this.count; i++) p[i + 1] = p[i] + this.size(i);
    this.prefix = p;
    this.dirty = false;
  }

  indexAt(offset) {
    this.#ensure();
    let lo = 0;
    let hi = this.count - 1;
    while (lo < hi) {
      const mid = (lo + hi + 1) >> 1;
      if (this.prefix[mid] <= offset) lo = mid;
      else hi = mid - 1;
    }
    return lo;
  }

  // 返回渲染窗口 + 定位偏移，调用方据此设置 padding 或 transform
  window(offset, viewportSize) {
    const first = this.indexAt(offset);
    const start = Math.max(0, first - this.overscan);
    let end = first;
    let acc = 0;
    while (end < this.count && acc < viewportSize) acc += this.size(end++);
    end = Math.min(this.count, end + this.overscan);
    return { start, end, offset: this.prefix[start], total: this.prefix[this.count] };
  }

  setSize(index, size) {
    if (this.size(index) === size) return null;
    this.sizes.set(index, size);
    this.dirty = true;
    this.#ensure();
    return { total: this.prefix[this.count] };
  }
}
```

**必须覆盖的边界**：
- 定高场景不特殊分支：构造函数里预填 `sizes` 即可退化成 O(1) 定位，代码只有一条路径。
- 横向只是 `axis` 不同：区间算法完全复用，只换读 `scrollLeft` 还是 `scrollTop`。
- 测量缓存永不删除：卸载后保留，重进时高度已知，不产生二次跳动。
- 总尺寸变化要通知容器：返回 `total`，调用方更新 spacer 高度或宽度。

**追问链**：
1. 为什么把 estimated 和 measured 合并成一个 `sizes` Map？→ 少一层判断，`size(i)` 一个函数就是全部高度语义，插桩和调试都简单。
2. 缓存无限增长会内存泄漏吗？→ 索引是整数且上限等于行数，Map 规模受 count 约束；真正的风险是 count 动态增长，需要按数据版本重建。
3. 为什么不在引擎里操作 DOM？→ 引擎只做「区间计算」，渲染交给适配层（React/Vue/原生），这样同一套逻辑能跑三端，也方便单测。
4. 二分查找的边界怎么写不容易错？→ 统一用「找最后一个 `prefix[mid] <= offset`」，`lo = mid` 而非 `mid+1`，避免死循环。
5. 10 万行以上的前缀和怎么办？→ 分块前缀和（每 1024 行一个块和）+ 块内扫描，更新 O(1)、查询 O(块内)。

### 精讲 5 · [HW-341] Canvas 渲染循环：脏区域与局部重绘

**为什么考这个**：Canvas 没有 DOM 的差异更新，全量重绘在 5000 图元时必卡。脏区检测是把「重绘成本」从「图元总数」降到「变化区域」，这是图形编辑器的核心优化。

**标准实现**：
```javascript
class CanvasRenderer {
  constructor(canvas, nodes = []) {
    this.canvas = canvas;
    this.ctx = canvas.getContext('2d');
    this.nodes = nodes;
    this.dirty = [];        // 待重绘包围盒
    this.frame = 0;         // rAF 句柄，兼作「本帧已排队」标记
  }

  markDirty(node, pad = 8) {
    const b = node.bounds();
    // 扩盒：阴影/描边/抗锯齿会溢出几何边界，不扩会留下残影
    this.dirty.push({ x: b.x - pad, y: b.y - pad, w: b.w + pad * 2, h: b.h + pad * 2 });
    if (!this.frame) this.frame = requestAnimationFrame(() => this.flush());
  }

  flush() {
    this.frame = 0;
    const boxes = CanvasRenderer.merge(this.dirty);
    this.dirty.length = 0;
    for (const box of boxes) {
      this.ctx.save();
      this.ctx.beginPath();
      this.ctx.rect(box.x, box.y, box.w, box.h);
      this.ctx.clip();                                  // 裁剪：防止重绘溢出脏区
      this.ctx.clearRect(box.x, box.y, box.w, box.h);
      for (const n of this.nodes) {
        if (CanvasRenderer.hit(n.bounds(), box)) n.draw(this.ctx);
      }
      this.ctx.restore();
    }
  }

  drawAll() {
    const { width, height } = this.canvas;
    this.ctx.clearRect(0, 0, width, height);
    for (const n of this.nodes) n.draw(this.ctx);
  }

  static hit(a, b) {
    return a.x < b.x + b.w && b.x < a.x + a.w && a.y < b.y + b.h && b.y < a.y + a.h;
  }

  // 相交即合并：把 N 个碎盒收敛成少数大盒，减少 clip/clear 次数
  static merge(boxes) {
    const out = [];
    for (const raw of boxes) {
      let box = { ...raw };
      for (let i = 0; i < out.length; ) {
        if (CanvasRenderer.hit(out[i], box)) {
          const a = out.splice(i, 1)[0];
          const x = Math.min(a.x, box.x);
          const y = Math.min(a.y, box.y);
          box = {
            x, y,
            w: Math.max(a.x + a.w, box.x + box.w) - x,
            h: Math.max(a.y + a.h, box.y + box.h) - y,
          };
        } else i++;
      }
      out.push(box);
    }
    return out;
  }
}
```

**必须覆盖的边界**：
- 脏盒合并要做「迭代合并」：合并后的大盒可能又和别的盒相交，一轮不够。
- 透明/模糊/阴影必须扩盒，否则边缘残影——这是真实 bug 的高发点。
- `clearRect` 只清脏区，不能整屏 clear，否则优化白做。
- 背景非纯色时，清完要重绘背景层，不能只画图元。

**追问链**：
1. 为什么脏区要合并？→ 每次 clip+clear 都有固定开销，10 个小盒合并成 1 个，draw call 降一个量级。
2. 重绘时为什么还要遍历全部节点做相交判断？→ 可以用空间索引替代，见 HW-358；节点少时线性遍历更快（缓存友好）。
3. 脏区法和图层法怎么选？→ 图元少、改动局部用脏区；图元多、有静态背景用离屏图层（静态层缓存成 bitmap，只重绘动态层）。
4. 怎么避免一帧内多次重绘？→ rAF 合帧 + `frame` 句柄去重，多次 `markDirty` 只排一次 flush。
5. 怎么证明优化有效？→ 打点统计 `dirtyBoxes` 数量与 `draw` 调用次数，优化前后对比；再用 Performance 看 paint 时间。

### 精讲 6 · [HW-358] 大画布性能优化：视口剔除与细节分级

**为什么考这个**：1 万图元的白板，滚动时全量遍历 + 全量绘制必卡。视口剔除是「不画看不见的」，LOD 是「看不清的别细画」，两者叠加才能把 60fps 守住。

**标准实现**：
```javascript
class SpatialGrid {
  constructor(cell = 256) {
    this.cell = cell;
    this.buckets = new Map();   // "cx,cy" -> Set<id>
    this.owner = new Map();     // id -> 占用的桶 key 列表
  }

  key(cx, cy) {
    return `${cx},${cy}`;
  }

  insert(node) {
    const b = node.bounds();
    const keys = [];
    // 跨桶登记：一个节点覆盖几个桶就进几个桶，查询才不会漏
    for (let cx = Math.floor(b.x / this.cell); cx <= Math.floor((b.x + b.w) / this.cell); cx++) {
      for (let cy = Math.floor(b.y / this.cell); cy <= Math.floor((b.y + b.h) / this.cell); cy++) {
        const k = this.key(cx, cy);
        if (!this.buckets.has(k)) this.buckets.set(k, new Set());
        this.buckets.get(k).add(node.id);
        keys.push(k);
      }
    }
    this.owner.set(node.id, keys);
  }

  remove(id) {
    for (const k of this.owner.get(id) ?? []) this.buckets.get(k)?.delete(id);
    this.owner.delete(id);
  }

  move(node) {
    this.remove(node.id);
    this.insert(node);
  }

  query(rect) {
    const out = new Set();
    for (let cx = Math.floor(rect.x / this.cell); cx <= Math.floor((rect.x + rect.w) / this.cell); cx++) {
      for (let cy = Math.floor(rect.y / this.cell); cy <= Math.floor((rect.y + rect.h) / this.cell); cy++) {
        const bucket = this.buckets.get(this.key(cx, cy));
        if (bucket) for (const id of bucket) out.add(id);
      }
    }
    return out;                          // 粗筛结果，调用方再做精确相交
  }
}

function renderFrame(ctx, grid, nodes, viewport, scale) {
  const byId = new Map(nodes.map((n) => [n.id, n]));
  const candidates = grid.query(viewport);
  let drawn = 0;
  for (const id of candidates) {
    const node = byId.get(id);
    if (!node) continue;
    const b = node.bounds();
    if (!intersects(b, viewport)) continue;              // 网格是粗筛，这里精筛
    const lod = scale < 0.15 ? 0 : scale < 0.35 ? 1 : 2; // 细节分级
    node.draw(ctx, { lod, showText: lod > 0, showStroke: lod > 1 });
    drawn++;
  }
  return { total: nodes.length, drawn, culled: nodes.length - drawn };
}

function intersects(a, b) {
  return a.x < b.x + b.w && b.x < a.x + a.w && a.y < b.y + b.h && b.y < a.y + a.h;
}
```

**必须覆盖的边界**：
- 节点跨桶：登记到所有覆盖桶，否则大节点在边界处会闪。
- 节点移动：`remove` 旧桶 + `insert` 新桶，不能只更新坐标。
- LOD 阈值要按 zoom 的连续区间分级，且阈值附近要留滞回（hysteresis），否则缩放时会反复切档闪烁。
- 视口本身要外扩一圈（预渲染区），否则快速拖拽时边缘空一帧。

**追问链**：
1. 空间网格 vs 四叉树怎么选？→ 图元尺寸接近用网格（O(1) 插入）；尺寸差异极大用四叉树/松散网格。
2. 剔除率怎么量？→ `culled / total`，白板场景缩放到 20% 时剔除率应在 90% 以上。
3. LOD 会不会看起来糊？→ 缩放到 15% 时单个图元不足 2px，本来就看不清；关键是缩放停下后能立即恢复细节。
4. 为什么不用 Canvas 自带的视口裁剪？→ 它只省绘制像素，不省 CPU 的遍历与状态切换；JS 侧剔除省的是循环本身。
5. 什么情况下应该上 WebGL？→ 图元 > 2 万且每帧都变化；或需要大量纹理/滤镜。低于这个量级 2D 往往更快。

## 速览（2 题）

### [HW-102] 水平虚拟滚动

横向是纵向的镜像：把 `scrollTop` 换成 `scrollLeft`，把 padding 占位换成 `left` 绝对定位。真正的差异在**列宽不均**（甘特图里节假日 48px、工作日 96px），所以必须前缀和 + 二分，不能用 `index * width`。

```javascript
function visibleColumns(widths, scrollLeft, clientWidth, buffer = 3) {
  const prefix = [0];
  for (let i = 0; i < widths.length; i++) prefix[i + 1] = prefix[i] + widths[i];
  // 找最后一个 prefix[i] <= scrollLeft
  let lo = 0;
  let hi = widths.length - 1;
  while (lo < hi) {
    const mid = (lo + hi + 1) >> 1;
    if (prefix[mid] <= scrollLeft) lo = mid;
    else hi = mid - 1;
  }
  let end = lo;
  let acc = prefix[lo];
  while (end < widths.length && acc < scrollLeft + clientWidth) acc += widths[end++];
  return { start: Math.max(0, lo - buffer), end: Math.min(widths.length, end + buffer) };
}
```

追问重点：为什么横向用 `left` 而不是 `padding-left`（padding 会挤压内容宽度，left 不参与流式布局）；列宽数组变化后必须重建前缀和；1 万天的时间轴定位是 O(logN)，与总列数无关。

### [HW-147] 大表格渲染优化

1000 行表格卡的根因是「每行都参与布局和样式计算」。三层解法：`table-layout: fixed` 让列宽不依赖内容；`contain: content` 把单元格的布局/样式影响锁在子树内；`content-visibility: auto` 让屏外行直接跳过渲染。再加分块挂载控制单帧成本。

```javascript
function mountInChunks(tbody, rows, { budget = 8 } = {}) {
  let i = 0;
  function step() {
    const start = performance.now();
    const frag = document.createDocumentFragment();
    while (i < rows.length && performance.now() - start < budget) {
      frag.appendChild(buildRow(rows[i++])); // 片段内构建，零次中间 reflow
    }
    tbody.appendChild(frag);
    if (i < rows.length) requestAnimationFrame(step);
  }
  requestAnimationFrame(step);
}
```

配套 CSS 才是重点：`td { height: 40px; overflow: hidden; text-overflow: ellipsis; white-space: nowrap; contain: content; }`——固定行高是「行高契约」，内容溢出截断，杜绝内容撑高引发的整表重排。追问常问「contain 和 content-visibility 区别」：前者限制影响范围，后者直接跳过屏外渲染，后者省得更多但需要 `contain-intrinsic-size` 提供占位尺寸。

## 反直觉：什么时候不该上虚拟列表

面试加分项不是「什么都会用虚拟列表」，而是知道它的代价。第一，虚拟列表会破坏浏览器的原生能力：Ctrl+F 找不到未渲染的内容、打印缺页、无障碍树不完整、锚点跳转失效。内容型页面（文章、帮助中心）应该用 `content-visibility` 而不是虚拟列表。第二，行内有大量交互状态（展开、编辑、拖拽）时，节点回收会导致状态丢失，需要把状态外置到数据层，改造成本常常高于收益。第三，只有当 DOM 节点数超过约 1000 且滚动是主要交互时才值得上；几百行的表格用分块挂载加 `contain` 就够了。判断顺序应该是：先减少节点（分页/折叠）→ 再让浏览器跳过（content-visibility）→ 最后才是 JS 虚拟列表。能把这条降级链讲清楚，比多写 20 行代码更能证明你做过真实项目。

## 性能指标与验收口径

| 指标 | 采集方式 | 合格线 | 说明 |
|---|---|---|---|
| 滚动 FPS | Performance 面板 / rAF 计数 | ≥ 55 | 连续掉到 30 说明每帧超 33ms |
| Long Task | `PerformanceObserver({ entryTypes: ['longtask'] })` | 无 > 50ms | 一个 Long Task 就是一次可感知卡顿 |
| 单帧渲染耗时 | `performance.mark` 包住 paint | < 8ms | 留一半给样式/布局/合成 |
| 掉帧率 | 掉帧数 / 总帧数 | < 5% | 快速滚动 3 秒采样 |
| 节点数 | `layer.childElementCount` | 视口行数 × 3 以内 | 超了说明缓冲或回收有问题 |
| 内存 | Performance monitor / heap snapshot | 滚动 1 分钟不增长 | 节点泄漏的典型表现 |

## 常见扣分点

| 扣分点 | 后果 | 正确做法 |
|---|---|---|
| scroll 里直接 setState / 改 DOM | 一帧多次渲染，必然掉帧 | rAF 合帧 + 脏值比较 |
| 用 top 定位行 | 每帧重排整层 | transform: translateY |
| 不定高却按定高算 | 滚动条长度错、位置漂移 | 预估 + 实测 + 前缀和 |
| 实测回写不补偿 scrollTop | 内容上下跳 | 修正视口上方元素时补偿偏移 |
| 脏区不扩盒 | 阴影/描边残影 | 按效果外扩 8~16px |
| 剔除只做一次 | 图元移动后消失或残留 | 移动时更新空间索引 |
| 只讲「用了虚拟列表」 | 无法证明有效 | 报 FPS、Long Task、节点数、剔除率 |
| 忽略 passive 监听 | 滚动被同步监听阻塞 | `{ passive: true }` |

## 一句话总结

渲染性能手写的评分顺序是：**先证明区间算对了（不白屏、不跳），再证明边界想到了（快滚、不定高、残影），最后用指标证明真的快了**。三者缺一，都只能算「写出来了」，不算「做过了」。
