# 10 引擎化设计题

> 40 道「手写一个 X 引擎」看起来是 40 个轮子，其实只有一套骨架。**能力分层**：L1 能写出主流程 → L2 能留出扩展点 → L3 能讲清抽象边界与失败语义。

面试官出这类题，不是要你把模板引擎写到能上生产，而是看你**有没有「把变化点收敛成配置、把稳定点固化成流程」的意识**。所以答题时先给骨架（五部件），再填当前题的特有逻辑，最后补失败路径。只会写 happy path 的人，代码再长也是 L1。

## 能力分层

| 层级 | 题目 | 面试要求 |
|---|---|---|
| L1 必会 | 表单校验 / 重试 / 限流 / 事件总线 | 20 分钟写完主流程，能跑通 |
| L2 进阶 | 模板 / 规则 / DI / DAG / 埋点 / 灰度 | 有配置层、扩展点、错误处理 |
| L3 深水 | DSL / 正则 / 序列化 / 插件系统 | 能说清编译与执行分离、隔离与降级 |

判断自己是否真的会：随便挑一个引擎，能否在 30 秒内说出它的「配置长什么样、编译成什么、执行时谁调谁、扩展点在哪、失败怎么办」。

## 引擎设计的五个通用部件

这是本专题最重要的一节。所有「X 引擎」都可以拆成同一组部件，**答题时按这五步讲，比直接贴代码高一个层级**。

| 部件 | 要解决的问题 | 典型产物 | 答不出来的后果 |
|---|---|---|---|
| ① 配置声明 | 变化点是什么？谁来决定行为？ | schema / JSON / DSL 文本 | 逻辑硬编码，加需求就改核心 |
| ② 解析 / 编译 | 如何把声明变成可执行结构？ | AST / 闭包函数 / 执行计划 | 每次执行都重新解析，性能塌方 |
| ③ 执行 | 谁在什么上下文里跑？ | 解释器 / 调度器 / 渲染器 | 状态散落，无法测试与回放 |
| ④ 扩展点 | 别人怎么介入而不改核心？ | 注册表 / 钩子 / 中间件 | 每加功能就 if-else 堆分支 |
| ⑤ 错误与降级 | 坏了怎么办？ | 错误码 / 重试 / 兜底 / 隔离 | 一处失败拖垮整条链路 |

**最小引擎骨架**（这段代码可以套到本专题任何一题上）：
```javascript
class EngineError extends Error {
  constructor(code, detail = {}) {
    super(code);
    this.name = 'EngineError';
    this.code = code;      // 错误码可被上层识别并决定降级
    this.detail = detail;
  }
}

function createEngine({ schema, compile, handlers = {}, plugins = [] }) {
  const registry = new Map(Object.entries(handlers));

  return function setup(config) {
    // ① 配置声明：启动期校验，坏配置绝不带进运行期
    for (const [key, rule] of Object.entries(schema)) {
      if (rule.required && config[key] === undefined) {
        throw new EngineError('INVALID_CONFIG', { key });
      }
    }
    // ② 解析 / 编译：声明 -> 可执行计划，只做一次并被复用
    const plan = compile(config);

    return {
      // ③ 执行：上下文统一收口，处理器从注册表按名取，便于替换与单测
      async run(input, outer = {}) {
        const context = { input, config, outer, state: {}, log: [] };
        // ④ 扩展点：插件只挂钩子，不碰核心流程
        for (const p of plugins) await p.beforeRun?.(context);
        try {
          const output = await plan(context, registry);
          for (const p of plugins) await p.afterRun?.(context, output);
          return output;
        } catch (error) {
          // ⑤ 错误与降级：统一出口，重试/兜底/上报都在这里决策
          for (const p of plugins) await p.onError?.(context, error);
          throw error instanceof EngineError
            ? error
            : new EngineError('EXEC_FAILED', { cause: String(error) });
        }
      },
      use(name, fn) {
        registry.set(name, fn);
        return this;
      },
    };
  };
}
```

配套用法示例（规则引擎）：
```javascript
const setupRules = createEngine({
  schema: { rules: { required: true } },
  compile: (config) => (context) => config.rules.filter((r) => r.test(context.input)),
  handlers: { log: (ctx, msg) => ctx.log.push(msg) },
});
const engine = setupRules({ rules: [{ name: 'adult', test: (u) => u.age >= 18 }] });
engine.run({ age: 20 }).then((hits) => hits.map((r) => r.name)); // ['adult']
```

## 精讲（6 题）

### 精讲 1 · [HW-301] 模板引擎

**为什么考这个**：它是最典型的「编译 vs 解释」题。用字符串 `replace` 每帧拼一次，和编译成函数缓存复用，性能差一个数量级；而用 `eval` 求值又引入注入漏洞。能不能同时讲清这两点，直接决定评级。

**标准实现**：
```javascript
const escapeHTML = (v) =>
  String(v ?? '').replace(/[&<>"']/g, (c) =>
    ({ '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' }[c]));

// 只解析路径（a.b[0].c），绝不执行任意 JS：模板注入的根因是「把用户输入当代码跑」
function readPath(scope, path) {
  const keys = path.replace(/\[(\d+)\]/g, '.$1').split('.').filter(Boolean);
  return keys.reduce((cur, k) => (cur == null ? undefined : cur[k]), scope);
}

function compile(template) {
  const parts = template.split(/(\{\{\{?[\s\S]*?\}?\}\})/g).filter(Boolean);
  const body = [];
  const stack = [];
  let depth = 0;

  for (const part of parts) {
    if (!part.startsWith('{{')) {                       // 纯文本：直接进输出
      body.push(`out.push(${JSON.stringify(part)});`);
      continue;
    }
    const raw = part.startsWith('{{{');                 // 三括号不转义
    const expr = (raw ? part.slice(3, -3) : part.slice(2, -2)).trim();

    if (expr.startsWith('#if ')) {
      body.push(`if (__get(scope, ${JSON.stringify(expr.slice(4))})) {`);
      stack.push('if');
    } else if (expr === '/if') {
      stack.pop();
      body.push('}');
    } else if (expr.startsWith('#each ')) {
      const [path, alias = 'item'] = expr.slice(6).split(/\s+as\s+/);
      depth += 1;
      body.push(`{ const __prev${depth} = scope;`);
      body.push(`for (const [__i, ${alias}] of (__get(scope, ${JSON.stringify(path)}) || []).entries()) {`);
      body.push(`scope = Object.assign(Object.create(__prev${depth}), { ${alias}, $index: __i });`);
      stack.push({ each: true, depth });
    } else if (expr === '/each') {
      const top = stack.pop();
      body.push(`scope = __prev${top.depth}; }`);       // 关 for
      body.push('}');                                   // 关块作用域
      depth -= 1;
    } else {
      body.push(raw
        ? `out.push(String(__get(scope, ${JSON.stringify(expr)}) ?? ""));`
        : `out.push(__esc(__get(scope, ${JSON.stringify(expr)})));`);
    }
  }

  // 编译一次生成函数，之后渲染 N 次都不再解析模板
  const render = new Function('data', '__get', '__esc', `
    let scope = data;
    const out = [];
    ${body.join('\n')}
    return out.join('');
  `);
  return (data) => render(data, readPath, escapeHTML);
}
```

**必须覆盖的边界**：
- 未定义变量输出空串而不是 `undefined`，避免页面出现 "undefined"。
- 默认转义 HTML，只有三括号才直出——XSS 的第一道闸。
- 未闭合的 `#if`/`#each` 要在编译期报错，不能生成语法错误的函数。
- 编译结果必须缓存：`compile` 只调一次，模板相同直接复用 render。

**追问链**：
1. 为什么不用正则一路 replace？→ 每条规则都要扫全文，10 条规则就是 10 遍；一次分词 + 一次编译只扫一遍。
2. `new Function` 安全吗？→ 模板本身来自开发者（可信），数据来自用户（不可信）。只要不把数据拼进代码字符串、只用路径取值，就是安全的。
3. 为什么用 `Object.create(__prev)` 做作用域链？→ 嵌套 each 需要向上查找外层变量，原型链天然实现词法作用域，且退出时只需恢复指针。
4. 和虚拟 DOM 的区别？→ 模板引擎输出字符串，适合 SSR/邮件/低交互页面；虚拟 DOM 输出描述树，适合高频更新。
5. 怎么支持自定义指令？→ 在 `expr` 分支前加指令注册表，命中就调用 `directive(node, scope, out)`，这就是扩展点。

### 精讲 2 · [HW-303] 规则引擎

**为什么考这个**：它考「数据结构 + 递归 + 失败语义」。业务里的券门槛、风控、灰度条件，本质都是这棵树。答得好的人会主动说「缺字段算命中还是不算」，这就是产品思维。

**标准实现**：
```javascript
const OPS = {
  eq: (a, b) => a === b,
  neq: (a, b) => a !== b,
  gt: (a, b) => a > b,
  gte: (a, b) => a >= b,
  lt: (a, b) => a < b,
  in: (a, b) => Array.isArray(b) && b.includes(a),
  contains: (a, b) => String(a ?? '').includes(String(b)),
  regex: (a, b) => new RegExp(b).test(String(a ?? '')),
};

function evaluate(cond, fact, depth = 0) {
  if (depth > 20) throw new Error('rule-too-deep');       // 防递归炸弹
  if (cond.all) return cond.all.every((c) => evaluate(c, fact, depth + 1)); // 短路
  if (cond.any) return cond.any.some((c) => evaluate(c, fact, depth + 1));
  if (cond.not) return !evaluate(cond.not, fact, depth + 1);
  if (!cond.field || !OPS[cond.op]) throw new Error(`bad-rule:${cond.op}`);

  const value = cond.field
    .split('.')
    .reduce((obj, key) => (obj == null ? undefined : obj[key]), fact);
  if (value === undefined) return false;                  // fail-closed：缺字段不命中
  return OPS[cond.op](value, cond.value);
}

class RuleEngine {
  constructor(rules) {
    this.rules = rules;
  }
  run(fact) {
    return this.rules
      .filter((rule) => evaluate(rule.when, fact))
      .map((rule) => rule.name);
  }
}

// 用法：成年且非 VIP 发新客券
new RuleEngine([{
  name: 'new-user-coupon',
  when: {
    all: [
      { field: 'age', op: 'gte', value: 18 },
      { not: { field: 'vip', op: 'eq', value: true } },
    ],
  },
}]).run({ age: 20 }); // ['new-user-coupon']
```

**必须覆盖的边界**：
- 短路求值：`every` 遇 false 即停、`some` 遇 true 即停，避免无谓的正则计算。
- 未知 `op` 在编译期或首次求值时报错，不能静默返回 false。
- 字段缺失 fail-closed：风控场景宁可漏发券，也不能错发。
- 深度上限防构造恶意嵌套导致的栈溢出。

**追问链**：
1. 为什么用 `{all/any/not}` 而不是字符串表达式？→ JSON 可序列化、可存库、可由运营后台可视化编辑，且天然不存在注入。
2. 规则多了怎么优化？→ 先按「必过条件」建索引（如按城市分桶），再做树评估；高频规则可编译成位运算。
3. 怎么解释「为什么命中/没命中」？→ 求值返回 trace 数组，记录每个叶子节点的结果，前端做决策链路展示。
4. 规则热更新怎么做？→ 规则集带版本号，求值前比对版本，新版本编译成功后原子替换。
5. 和策略模式的区别？→ 策略模式是代码级分支，规则引擎把分支外化成数据，运营可改而不发版。

### 精讲 3 · [HW-308] DSL 解析器

**为什么考这个**：这是「编译器前端」的最小完整版：词法 → 语法 → AST → 执行。能写出来说明你理解分层；写不出来通常是把「解析」和「执行」搅在一起，边扫字符串边干活。

**标准实现**：
```javascript
function lex(src) {
  const tokens = [];
  let i = 0;
  while (i < src.length) {
    const ch = src[i];
    if (/\s/.test(ch)) { i++; continue; }
    if (ch === '"' || ch === "'") {                         // 字符串：允许内含逗号
      let j = i + 1;
      let value = '';
      while (j < src.length && src[j] !== ch) value += src[j++];
      if (src[j] !== ch) throw new Error(`unterminated-string@${i}`);
      tokens.push({ type: 'string', value, pos: i });
      i = j + 1;
      continue;
    }
    if (/[\w.$-]/.test(ch)) {                               // 标识符 / 数字 / 路径
      let j = i;
      let value = '';
      while (j < src.length && /[\w.$-]/.test(src[j])) value += src[j++];
      tokens.push({ type: 'word', value, pos: i });
      i = j;
      continue;
    }
    if (',{}'.includes(ch)) { tokens.push({ type: ch, pos: i }); i++; continue; }
    throw new Error(`unexpected-char:${ch}@${i}`);          // 错误必须带位置
  }
  return tokens;
}

function parse(src) {
  const tokens = lex(src);
  let p = 0;
  const peek = () => tokens[p];

  function command() {
    const head = tokens[p++];
    if (!head || head.type !== 'word') {
      throw new Error(`expect-command@${head?.pos ?? src.length}`);
    }
    const args = [];
    while (peek() && (peek().type === 'word' || peek().type === 'string')) {
      args.push(tokens[p++].value);
    }
    if (peek()?.type === ',') p++;                          // 容忍分隔逗号
    const children = [];
    if (peek()?.type === '{') {                             // 嵌套块
      p++;
      while (peek() && peek().type !== '}') children.push(command());
      if (peek()?.type !== '}') throw new Error('unclosed-block');
      p++;
    }
    return { name: head.value, args, children };
  }

  const ast = [];
  while (p < tokens.length) ast.push(command());
  return ast;
}

// 语义校验放在执行期：解析器不认识业务命令，只保证语法正确
function run(ast, handlers, ctx = {}) {
  return ast.map((node) => {
    const handler = handlers[node.name];
    if (!handler) throw new Error(`unknown-command:${node.name}`);
    const children = node.children.map((child) => run([child], handlers, ctx)[0]);
    return handler({ args: node.args, children, ctx });
  });
}
```

**必须覆盖的边界**：
- 字符串内的逗号/大括号不能当分隔符，否则参数被切断。
- 括号不配对要报位置，不能抛一个无信息的 undefined 错误。
- 语法正确 ≠ 语义正确：未知命令在执行期报，解析器不耦合业务。
- 深度嵌套要限制层数，防止栈溢出。

**追问链**：
1. 为什么要两阶段而不是边解析边执行？→ 分层可复用：同一份 AST 可以执行、可以静态分析、可以格式化成不同目标代码。
2. 递归下降的局限？→ 左递归会死循环，需要改写文法；运算符优先级要手写层级或用优先级爬升。
3. 错误恢复怎么做？→ 记录出错 token 位置，跳到下一个同步点（`,{}`）继续解析，一次报多个错。
4. 怎么支持变量和表达式？→ 在执行期引入 scope，`word` 若命中 scope 则取值，否则当字面量。
5. 和 JSON 配置的区别？→ DSL 有嵌套块和顺序语义，表达力更强；但解析成本更高，能用 JSON 就别造 DSL。

### 精讲 4 · [HW-314] 依赖注入容器

**为什么考这个**：它考「对象生命周期」的理解——单例、瞬态、父子容器、循环依赖。答得好的人能把 Angular/NestJS 的 DI 讲透；答不好的人会写出「resolve 时无限递归爆栈」。

**标准实现**：
```javascript
class DIContainer {
  constructor(parent = null) {
    this.registry = new Map();     // name -> { factory, scope, deps }
    this.singletons = new Map();   // 只存 singleton 实例
    this.parent = parent;
  }

  register(name, factory, { scope = 'transient', deps = [] } = {}) {
    this.registry.set(name, { factory, scope, deps });
    return this;
  }

  #find(name) {
    return this.registry.get(name) ?? this.parent?.#find(name);
  }

  resolve(name, stack = new Set()) {
    if (stack.has(name)) {                                  // 循环依赖：实例化前就发现
      throw new Error(`circular-dep:${[...stack, name].join('->')}`);
    }
    const def = this.#find(name);
    if (!def) throw new Error(`not-registered:${name}`);

    if (def.scope === 'singleton' && this.singletons.has(name)) {
      return this.singletons.get(name);                     // 单例：懒创建 + 缓存
    }

    stack.add(name);
    const instance = def.factory(...def.deps.map((dep) => this.resolve(dep, stack)));
    stack.delete(name);

    if (def.scope === 'singleton') this.singletons.set(name, instance);
    return instance;                                        // transient：每次新实例
  }

  createChild() {
    return new DIContainer(this);                           // 子容器找不到时向上查
  }
}

// 用法
const root = new DIContainer();
root.register('db', () => ({ query: () => [] }), { scope: 'singleton' });
root.register('userService', (db) => ({ list: () => db.query() }), { deps: ['db'] });
root.resolve('userService').list();
```

**必须覆盖的边界**：
- 循环检测必须在**实例化之前**，用解析栈而不是事后检查，否则已经爆栈。
- 单例缓存放当前容器而不是父容器，保证子容器各自独立。
- 父容器查找只读，子容器注册同名服务应覆盖父级（就近原则）。
- factory 抛错时要从栈里清理，否则后续解析被误判为循环。

**追问链**：
1. 为什么用 `deps` 显式声明而不是解析函数参数名？→ 压缩后参数名会变；显式声明更稳，也便于静态分析依赖图。
2. 单例什么时候销毁？→ 容器级生命周期，通常挂在应用卸载时统一 dispose；需要 `dispose` 钩子。
3. 循环依赖能不能用懒加载解？→ 可以，注入 `() => resolve(name)` 延迟到首次使用，但会让依赖关系变成隐式。
4. 和模块系统的区别？→ ES Module 是静态图 + 编译期绑定；DI 容器是运行时图，可按环境替换实现（测试 mock）。
5. 怎么做测试替换？→ `register` 同名覆盖，或在子容器里注册 mock，天然隔离。

### 精讲 5 · [HW-316] 任务编排引擎（DAG）

**为什么考这个**：前端也有编排：构建流水线、页面初始化、埋点上报链。核心是「拓扑序 + 并行 + 失败传播」。能说清「失败为什么只影响下游」的人，说明真的调度过任务。

**标准实现**：
```javascript
async function runDAG(tasks, { retries = 0 } = {}) {
  const byId = new Map(tasks.map((t) => [t.id, t]));
  const indegree = new Map(tasks.map((t) => [t.id, (t.deps || []).length]));
  const dependents = new Map(tasks.map((t) => [t.id, []]));
  for (const task of tasks) {
    for (const dep of task.deps || []) dependents.get(dep)?.push(task.id);
  }

  const result = new Map();                       // id -> { status, ms, value?, error? }
  let ready = tasks.filter((t) => indegree.get(t.id) === 0).map((t) => t.id);

  while (ready.length) {
    const wave = ready;                           // 同层入度为 0：天然可并行
    ready = [];
    await Promise.all(wave.map(async (id) => {
      if (result.has(id)) return;                 // 已被上游失败标记 skipped
      const task = byId.get(id);
      const started = performance.now();
      try {
        const value = await attempt(task.run, retries);
        result.set(id, { status: 'done', ms: performance.now() - started, value });
        for (const next of dependents.get(id)) {
          indegree.set(next, indegree.get(next) - 1);
          if (indegree.get(next) === 0) ready.push(next);
        }
      } catch (error) {
        result.set(id, { status: 'failed', ms: performance.now() - started, error: String(error) });
        skipDownstream(id);                       // 只跳过依赖链，旁支继续跑
      }
    }));
  }

  function skipDownstream(id) {
    for (const next of dependents.get(id)) {
      if (result.has(next)) continue;
      result.set(next, { status: 'skipped' });
      skipDownstream(next);
    }
  }

  if (result.size !== tasks.length) throw new Error('dag-cycle'); // 有环则跑不完
  return result;
}

async function attempt(fn, retries) {
  let lastError;
  for (let i = 0; i <= retries; i++) {
    try { return await fn(); } catch (error) { lastError = error; }
  }
  throw lastError;
}
```

**必须覆盖的边界**：
- 环检测：拓扑跑完后仍有节点未出结果，说明有环，必须显式报错。
- 失败传播只沿 `dependents` 递归，不能影响无依赖关系的旁支。
- 依赖 id 不存在：`dependents.get(dep)` 为 undefined，要显式校验，否则任务永远不 ready。
- 重试要只对可重试错误生效，业务错误（参数错）重试是浪费。

**追问链**：
1. 为什么按层跑而不是一次性全跑？→ 层内并行、层间串行的语义最直观，也天然满足依赖；代价是长尾任务会拖慢整层。
2. 想要「依赖完成即触发」怎么办？→ 改成事件驱动：每个任务完成递减入度，入度归零立即入队，配合并发池。
3. 失败后能不能继续跑下游？→ 要看语义：数据流水线必须跳过（脏数据不能流下去），清理任务则应继续。
4. 怎么展示进度？→ 每个任务状态机 pending/running/done/failed/skipped，聚合出百分比与关键路径。
5. 和 Promise.all 的区别？→ all 是全有或全无、无依赖概念；DAG 表达偏序，允许部分失败。

### 精讲 6 · [HW-340] 插件系统

**为什么考这个**：这是「架构题」而不是算法题。核心是三个词：**加载顺序、失败隔离、逆序销毁**。能主动提到「插件不能直接拿到 host 内部对象」的人，说明做过真正的扩展体系。

**标准实现**：
```javascript
class PluginSystem {
  constructor(host) {
    this.host = host;              // 受控 API：插件只能看到这一层
    this.plugins = new Map();
    this.active = [];
  }

  register(plugin) {
    if (!plugin.name) throw new Error('plugin-name-required');
    if (this.plugins.has(plugin.name)) throw new Error(`duplicate:${plugin.name}`);
    this.plugins.set(plugin.name, { ...plugin, depends: plugin.depends || [] });
    return this;
  }

  #order() {
    const output = [];
    const done = new Set();
    const visiting = new Set();

    const visit = (name) => {
      if (done.has(name)) return;
      if (visiting.has(name)) throw new Error(`circular-plugin:${name}`);
      const plugin = this.plugins.get(name);
      if (!plugin) throw new Error(`missing-dep:${name}`);   // 依赖缺失：启动期就炸

      visiting.add(name);
      for (const dep of plugin.depends) visit(dep);          // 先装依赖
      visiting.delete(name);
      done.add(name);
      output.push(plugin);                                   // 后装自己 = 拓扑序
    };

    for (const name of this.plugins.keys()) visit(name);
    return output;
  }

  async boot() {
    for (const plugin of this.#order()) {
      try {
        await plugin.hooks?.init?.(this.host);
        await plugin.hooks?.ready?.(this.host);
        this.active.push(plugin);
      } catch (error) {
        // 单插件失败不阻断宿主：隔离 + 上报 + 继续
        this.host.report?.('plugin-error', { name: plugin.name, error: String(error) });
      }
    }
    return this;
  }

  async shutdown() {
    for (const plugin of this.active.reverse()) {            // 逆序释放
      try { await plugin.hooks?.destroy?.(this.host); } catch { /* 隔离 */ }
    }
    this.active = [];
  }
}
```

**必须覆盖的边界**：
- 依赖缺失/重复注册/循环依赖都在 `boot` 前抛出，不能装到一半才失败。
- 钩子异常必须 try/catch 隔离，一个插件崩不能带走宿主。
- `destroy` 逆序：后初始化的可能依赖先初始化的资源。
- 版本兼容：`depends` 可带 semver 区间，避免 API 不匹配。

**追问链**：
1. 为什么用 DFS 拓扑而不是排序？→ DFS 天然给出「依赖在前」的顺序，且能顺带检测环，O(V+E)。
2. 插件间怎么通信？→ 走 host 提供的事件总线，禁止直接互相 import，避免形成隐式耦合。
3. 怎么保证插件不污染全局？→ 只传受控 API，不给 `window`；必要时用 Proxy 拦截写操作。
4. 热插拔怎么做？→ 记录插件的副作用（注册的指令/路由/监听），destroy 时按记录反向清理。
5. 和微前端的区别？→ 插件系统共享同一运行时与状态；微前端是应用级隔离，代价更高。

## 横向对比：六个引擎的「五部件」映射

| 引擎 | ① 配置 | ② 编译 | ③ 执行 | ④ 扩展点 | ⑤ 失败处理 |
|---|---|---|---|---|---|
| 模板 HW-301 | 模板字符串 | 编译成 render 函数 | 传 data 求值 | 自定义指令 | 未闭合报错、转义兜底 |
| 规则 HW-303 | JSON 条件树 | 校验 op/结构 | 递归求值 + 短路 | OPS 注册表 | 缺字段 fail-closed |
| DSL HW-308 | DSL 文本 | 词法 + 递归下降 → AST | 遍历 AST 调 handler | handlers 注册表 | 带位置语法错误 |
| DI HW-314 | register 声明 | 依赖图解析 | 递归构造实例 | 父子容器覆盖 | 循环检测、未注册报错 |
| DAG HW-316 | 任务 + deps | 拓扑排序 | 分层并行调度 | 每任务重试/钩子 | 失败传播 skipped |
| 插件 HW-340 | plugin 声明 | 依赖拓扑排序 | 生命周期钩子 | hooks + host API | 单插件隔离、逆序销毁 |

这张表就是本专题的「万能答题卡」：面试时先报这五列，再展开当前题，结构分先拿满。

## 常见扣分点

| 扣分点 | 后果 | 正确做法 |
|---|---|---|
| 配置和执行混在一起 | 加需求必改核心，无法复用 | 先声明、再编译、后执行 |
| 每次执行都重新解析 | 模板/规则量大时直接卡死 | 编译结果缓存 |
| 没有错误码，只 throw 字符串 | 上层无法分类降级 | `EngineError(code, detail)` |
| 扩展点靠 if-else | 分支爆炸、无法插拔 | 注册表 / 钩子 / 中间件 |
| 一个插件异常拖垮全部 | 宿主白屏 | try/catch 隔离 + 上报 |
| 循环依赖不做检测 | 栈溢出，错误信息无用 | 解析栈 / visiting 集合 |
| 只讲 happy path | 评为 L1 | 主动补失败语义与降级 |
| 忽略复杂度说明 | 显得没工程判断 | 报 O(V+E)、O(logN) 等 |

## 一句话总结

引擎题的答案永远是同一个结构：**把变化点抽成配置，把配置编译成计划，把计划放进带上下文的执行器，在前后留钩子，在出口统一处理失败**。记住这句话，40 道题只是换了个名词。
