## ARC-201：模块联邦 2.0 解决了 1.0 的哪些核心痛点？
**答**：
- 1.0 痛点一：强绑定构建器——只支持 Webpack，Rspack/Vite 生态各自造轮子。2.0 把运行时抽成独立的 @module-federation/enhanced 运行时，与构建器解耦，Webpack/Rspack/Vite 可互联。
- 1.0 痛点二：版本冲突静默失败——共享依赖谁先加载用谁的。2.0 引入共享依赖版本协商与 semantic 匹配，运行时可按 semver 选择最优实例，冲突可观测。
- 1.0 痛点三：manifest 缺失——无法做部署期编排。2.0 生成 manifest/snapshot（含 expose 清单、依赖图、hash），平台可在发布时做依赖编排、预加载与回滚。
- 1.0 痛点四：SSR 支持残缺。2.0 提供标准化的 node 运行时与 chrome（ MF runtime chrome），SSR/边缘环境一等公民。
- 追问钩子：版本协商失败时的兜底策略（fallback 到独立构建）如何设计？

```javascript
// 2.0 运行时：manifest 驱动的加载与版本协商
import { init, loadRemote } from '@module-federation/enhanced/runtime';

await init({ name: 'host', remotes: {
  shop: { entry: 'https://cdn.example.com/shop/mf-manifest.json' }, // 2.0 用 manifest 而非裸 entry
}});

// loadRemote 按 manifest 的 exposes + 依赖图加载，共享依赖先做 semver 协商
const Button = await loadRemote('shop/Button');
// manifest snapshot 示例（构建产物）：
// { id: "shop@1.4.2", buildVersion: "1.4.2", remotes: [...], exposes: [{ id: "./Button", assets: [...] }], shared: [{ usedIn: [...], sharedName: "react", version: "18.2.0" }] }
// 平台侧可依据 snapshot 做"谁依赖我"的反查与影响面评估——1.0 做不到
```
