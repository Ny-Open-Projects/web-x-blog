## ARC-203：联邦共享依赖的版本协商机制是怎么工作的？
**答**：
- 每个模块把 shared 依赖声明为 `share: { react: { singleton, requiredVersion } }`，运行时加载前先在全局注册表（作用域）里登记自己提供的版本。
- 协商规则：请求方声明 requiredVersion（semver 范围），运行时在已加载/待加载的提供方里选满足范围的最高版本；singleton 为 true 时全页面只允许一个实例，版本不满足则告警并复用已有实例（而不是双实例）。
- singleton 下的版本冲突是常态风险：主应用 React 17、子应用要 18 时，2.0 的策略是"先到先得 + 冲突上报"，因此要求 CI 里做 requiredVersion 兼容性检查，把冲突从运行时前移到发布时。
- 兜底：设置 fallback 版本与 strictVersion，冲突时可降级为子应用独立打包版本（牺牲体积保可用）。

```javascript
// 运行时协商伪代码（简化版 share-scope）
const scope = { react: [{ version: '18.2.0', from: 'host', get: () => import('react') }] };

function negotiate(name, requiredVersion, { singleton }) {
  const candidates = scope[name];
  if (!candidates?.length) return null;                       // 无人提供 → 用自己的异步包
  const best = candidates
    .filter(c => satisfies(c.version, requiredVersion))
    .sort(bySemverDesc)[0] ?? candidates[0];                  // 满足范围取最高，否则取首个并告警
  if (singleton) {
    if (!satisfies(best.version, requiredVersion)) reportConflict(name, best.version, requiredVersion);
    return best;                                              // 单例强制复用，不产生第二实例
  }
  return best;
}
// 实践：CI 阶段用 manifest 的 shared 段做主子应用 requiredVersion 交叉校验，发布前拦截冲突
```
