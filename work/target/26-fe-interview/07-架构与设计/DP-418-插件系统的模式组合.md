## DP-418：插件系统组合

**答**：
- 插件系统的模式全景：观察者（插件挂接宿主事件——hook 点）、策略（插件替换宿主行为——可插拔实现）、组合（插件管道——按序处理）、外观（宿主暴露给插件的 API 门面——能力受控）
- Hook 点设计：宿主的「扩展点清单」（生命周期/渲染前/渲染后/命令注册）——扩展点是插件系统的 API 契约
- 插件的隔离：插件异常不崩宿主（错误隔离——try/catch 边界）、插件能力白名单（不能访问内部状态——门面限权）
- 加载与依赖：插件间依赖声明（插件 A 依赖插件 B——拓扑排序加载）
- 深水点：插件 API 的「版本化」——宿主升级后插件兼容（semver + 弃用警告）——插件生态的治理核心

```javascript
class PluginHost {
  #plugins = []; #hooks = new Map();
  use(plugin) {
    plugin.setup(this.#facade());                    // 门面: 受控 API
    this.#plugins.push(plugin);
  }
  #facade() { return { on: (n, f) => this.on(n, f), trigger: (h, c) => this.trigger(h, c) }; }  // 只暴露受控 API，不漏内部状态
  on(hookName, fn) { if (!this.#hooks.has(hookName)) this.#hooks.set(hookName, []); this.#hooks.get(hookName).push(fn) } // set 返回的是 Map 本身，不能链 .push
  async trigger(hook, ctx) {
    for (const fn of this.#hooks.get(hook) ?? []) {
      try { ctx = await fn(ctx) ?? ctx; }            // 管道: ctx 逐插件传递
      catch (e) { console.error(`plugin error in ${hook}`, e); }   // 隔离
    }
    return ctx;
  }
}
```

**边界与易错**：

- 钩子语义必须统一：哪些钩子可改写上下文、哪些只作通知，混用会让插件作者误以为能改，隐性依赖就藏进了执行顺序里。
- 拓扑排序只管显式声明的依赖，插件通过副作用（改全局、改同一 DOM）形成的隐式依赖排不出来，只能靠文档约定与评审兜底。
- 卸载时若不按注册的逆序 destroy，插件注册的监听、定时器会残留，热更新几次就泄漏一批。

**追问**：

1. 插件 API 版本化具体怎么做，才不会升一次大版本生态全崩？ → 门面层保留旧方法做适配转发、加运行时弃用警告、至少留一个大版本的缓冲期，破坏性变更只在主版本发生。
2. 两个插件都要接管同一个钩子且互斥，宿主怎么裁决？ → 显式声明优先级字段，注册时做冲突检测直接报错，不能靠注册先后顺序决定谁生效。
3. 生产环境插件报错被隔离吞掉，线上怎么排查？ → 隔离 catch 里带上插件名与钩子名打点到监控，dev 环境直接抛出，并统计各插件的错误率作为禁用依据。
