## ARC-384：企业级表单引擎的数据校验架构如何设计？
**答**：
- 校验三层：字段级（类型/格式/范围，schema 驱动）、跨字段（联动约束：结束>开始、互斥选项，规则引擎）、异步级（唯一性校验/风控，防抖 + 取消）。
- 架构核心：校验与 UI 解耦——校验器输入 formState 输出 errors 集合；UI 只订阅 errors 渲染。这样同一套校验可在提交前/提交时/服务端复用。
- schema 协议：字段描述（type/validators/dependsOn）+ 校验规则声明（JSON），与后端校验 schema 同源（一份契约两端用），前端做即时提示，后端做最终裁决（前端校验只是体验优化不是安全边界）。
- 异步校验治理：防抖 + 竞态取消 + 缓存（同值不重查）；提交前统一跑全量校验，异步未完成的字段阻塞提交。
- 错误呈现策略：失焦校验单字段、提交时全量、错误定位滚动到首个错误；错误文案字典化。
```javascript
function createValidator(schema) {
  return async (state) => {
    const errors = {};
    for (const f of Object.keys(schema)) {
      for (const rule of schema[f].validators) {
        const r = await rule(state[f], state);            // 支持异步规则
        if (r !== true) { errors[f] = r; break; }
      }
    }
    for (const rule of schema.__cross__ ?? [])            // 跨字段规则
      if (rule.check(state) === false) errors[rule.at] ??= rule.msg;
    return errors;
  };
}
```

**追问**：

1. 异步唯一性校验：用户改名后又改回原值，缓存会返回旧错误，怎么处理？ → 缓存 key 要含字段值与规则版本，请求带取消令牌，只认最后一次响应（按序号比对），过期响应直接丢弃。
2. 前端 schema 与后端同源，但后端有更严的业务规则，提示对不上怎么兜？ → 后端错误按字段路径合并进同一个 errors 集合（errors[].field 映射），前端只负责定位与呈现，语义说明统一走错误码字典。
3. 大表单提交时全量校验卡顿，怎么优化？ → 规则分同步与异步两批，同步规则一次遍历先出结果，异步并发限流且只校验脏字段，未完成的字段阻塞提交并给出明确等待态。
