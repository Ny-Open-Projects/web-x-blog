## ARC-433：设计系统的运营与衰减防治
**答**:
- 衰减形态：组件覆盖不了新需求 → 业务绕过组件库手写 → 两套 UI 并存 → 设计系统失去权威性。根因是"供应"跟不上"需求"且缺少升级通道。
- 防治机制：需求漏斗（业务组件诉求 → 评估抽象级别 → 进组件库/进业务扩展层/拒绝并说明）、版本节奏（月度 minor + 破坏性变更走 RFC）、迁移自动化（codemod 降升级阻力）。
- 权威性维护：lint 检测"手写了组件库已有能力"（用 DOM 结构/类名特征启发式检测）；设计侧 token 贯通（Figma 与代码同源，ARC-163）。
- 双层供应：核心组件（高质量通用）+ 模式库（页面级组合范式，半成品允许业务定制）——覆盖长尾需求而不是硬造万能组件。
- 运营指标：覆盖率（页面使用组件库比例）、组件健康度（使用量/issue 响应时长）、逃生舱使用率（逃生舱高频 = 供应缺口信号）。
```javascript
// 设计系统健康看板
const dsHealth = {
  coverage: 0.87,                        // 业务页面覆盖率
  adoptionTrend: +0.04,                  // 季度趋势
  topRequests: ['日期区间快捷选项', '表格行展开编辑'],       // 需求漏斗入口
  escapeUsage: { 'custom-button': 23 },  // 逃生舱高频使用 → 组件缺口信号
  rfcQueue: 2, codemodCoverage: 0.9
};
```
