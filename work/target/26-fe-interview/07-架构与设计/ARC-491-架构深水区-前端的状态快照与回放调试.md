## ARC-491：状态快照与回放调试架构
**答**:
- 调试痛点：bug 依赖用户操作序列，本地难复现。回放调试 = 操作序列 + 状态快照可持久化，拿到现场即可复现。
- 架构：操作日志层（所有 dispatch/命令带时间戳入环形缓冲）+ 快照层（关键节点全量快照或 Immer patch 序列）+ 回放器（按序重放命令，支持暂停/跳步/单步）。
- 轻量实现： Redux/Vuex 的 devtools 本质就是 action log + state diff；生产环境可把 patch 序列（比全量快照小）随诊断包导出（ARC-465）。
- 分寸控制：回放调试有性能与隐私成本——默认只在 dev/test 开启，生产只记 patch 且脱敏（字段白名单）；录制开启有显式开关。
- 与协同/服务端数据的边界：纯前端状态可回放，涉及服务端时序的要配合 trace（ARC-357）联查——回放工具解决前端态，服务端靠链路。
```javascript
// patch 录制（Immer）
const patches = [];
const store = create(prod => (state, action) => {
  produce(state, draft => prod(draft, action), (p) => patches.push({ t: Date.now(), p, action: action.type }));
});
function replay(log) {
  let s = log[0].snapshot;
  for (const { p } of log) s = applyPatches(s, p);            // 逐步重放
  return s;
}
// 导出诊断：patches 环形缓冲（500 条）+ 白名单脱敏
```

**边界与易错**：

- 只录操作不够：接口返回、时间、随机数、设备差异都会让回放结果和用户看到的不是一回事，响应要一并录进日志或打桩。
- patch 依赖初始快照，快照脱敏过度或缺 schema 版本，回放时 applyPatches 会直接报结构错误。
- 环形缓冲会丢头部，回放必须从最近一个完整快照开始，不能在截断的 patch 序列上硬重放。

**追问**：

1. 生产环境录制会不会拖慢主线程、占满内存？ → 只存 patch 与轻量 diff，序列化成异步批量（空闲回调里做），缓冲定长并设体积上限，超限丢最旧的一段。
2. 回放时遇到定时器、请求这类异步副作用，顺序怎么保证？ → 副作用统一走可注入的 effect 层，录制时记下触发与完成时序，回放用虚拟时钟按记录顺序驱动。
3. 脱敏之后还能复现 bug 吗，字段被替换会不会改了逻辑？ → 脱敏用同类型占位值而不是删字段，保证结构与分支判断不变；长度、枚举这类会参与逻辑的字段单独定规则。
