## ARC-557：接口变更兼容演练
**答**:
- 场景：服务端发布把老客户端炸了（字段删除/枚举新增未兜底/时间格式变化）——上线后用户投诉才发现。演练目标：发布前证明"最低支持版本的客户端在真实链路可用"。
- 兼容回归自动化：多版本客户端套件（最低支持版本 + 上上版本 + 最新版）× 核心链路 E2E，服务端每次发布前跑（NODE-464 E2E 矩阵扩展）；契约断言按客户端版本选择器（同断言对不同版本期望不同 ARC-449 数据兼容）。
- 兼容性 lint（服务端）：接口响应 schema 与"历史版本契约"比对（diff 出不兼容变更阻断发布——NODE-447 契约通知的强执行版）。
- 真机/真客户端验证：模拟请求（构造老版本 UA/能力头）打预发——覆盖"老客户端特有的请求路径"（老版本可能走不同接口组合）。
- 流程嵌入：服务端发布单强制附"兼容性验证通过"证据（多版本 E2E 绿灯）——漏跑的门禁等价于没有。
```javascript
// 多版本兼容回归
const versions = ['1.2.0', '2.0.0', '3.1.0'];                    // 最低+主流+最新
for (const v of versions) {
  test(`核心链路 @ client ${v}`, async ({ request }) => {
    const r = await request.get('/api/order/1', { headers: { 'x-client-ver': v } });
    expect(r.status()).toBe(200);
    const body = await r.json();
    expect(body.items).toBeDefined();                            // 各版本均有的契约点
    if (semver.lt(v, '2.0.0')) expect(body.newField).toBeUndefined(); // 版本差异断言
  });
}
```
