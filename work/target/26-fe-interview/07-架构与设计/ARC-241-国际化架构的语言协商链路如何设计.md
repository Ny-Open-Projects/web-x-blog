## ARC-241：国际化架构的语言协商链路如何设计？
**答**：
- 协商优先级（高→低）：URL 路径/参数（/?lang=ja，SEO 与分享确定性）→ 用户账户设置 → Cookie/localStorage 记忆 → Accept-Language → 默认语言。每层都可覆盖下一层，用户显式选择永远最优先。
- 服务端协商（关键）：为了 SSR/CDN 首屏正确，语言必须在**服务端**定下来——SSR 读 URL+Cookie 定语言，渲染对应语言 HTML，并把决定（Set-Cookie/内联变量）传给客户端，客户端不再二次协商（防闪变）。
- 语言标签规范化：BCP 47（zh-CN/zh-TW/pt-BR），匹配用最佳匹配算法而不是字符串相等；支持 fallback 链 zh-CN → zh → en（ARC-085 基础上的全局统一）。
- 架构落点：协商逻辑做成独立模块（同构），服务端与客户端共用一套实现，测试表驱动覆盖。

```typescript
// 同构语言协商模块
export function negotiate(req: { url: string; cookies: Record<string,string>; headers: Record<string,string> }): string {
  const urlLang = new URL(req.url, 'http://x').searchParams.get('lang');
  if (isValid(urlLang)) return urlLang;                       // 1. URL 显式指定
  if (isValid(req.cookies.lang)) return req.cookies.lang;     // 2. 用户记忆
  const al = req.headers['accept-language'];                  // 3. 浏览器偏好：q 值加权
  const best = parseAcceptLanguage(al)
    .flatMap(tag => matchChain(tag))                          // ja-JP → [ja-JP, ja, en]
    .find(t => supported.includes(t));
  return best ?? DEFAULT_LANG;
}
// SSR：const lang = negotiate(req); res.setHeader('Set-Cookie', `lang=${lang}`); render(lang)
```
