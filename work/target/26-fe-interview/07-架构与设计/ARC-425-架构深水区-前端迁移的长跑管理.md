## ARC-425：前端长周期迁移如何管理与防烂尾？
**答**:
- 烂尾根因：没有明确终点、新旧共存成本无人承担、业务排期永远优先。管理上先立"终局"：目标态清晰（迁移完成的定义）、预算封顶、双轨期最长时限。
- 拆分原则：迁移切片按"可独立交付 + 可独立验证"（一个模块/一个路由），每片有回滚方案；进度看"剩余存量占比"曲线而非做了多少。
- 防倒灌：新代码默认新体系（模板/脚手架已切换），存量修复任务"顺手迁移"计入工时；禁止在新模块里引用旧体系（适应度函数卡住）。
- 冻结机制：双轨期截止日写入团队 OKR，到期未完成的存量降级维护模式（只修不扩）并公示。
- 沉淀：迁移完成后的 codemod/工具归档为能力，下次迁移复用（webpack→Vite 经验迁移到下个项目）。
```javascript
// 迁移进度看板数据模型
const migration = {
  target: '全部路由使用 Vue3 + 新请求层',
  slices: [{ name: 'module-a', done: true }, { name: 'module-b', done: false, blocker: null }],
  metrics: { legacyRatio: 0.42, weeklyDelta: -0.03 },          // 剩余占比与周降幅
  deadline: '2026-Q2 末', freezePlan: '到期未完成模块进入只修不扩'
};
```
