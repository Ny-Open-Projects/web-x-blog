## OPS-282：灰度机制健康度怎么评估？
**答**：
- 度量对象是「灰度机制本身」而非某次灰度：分流正确性（SRM 发生率）、哨兵质量（误报率/漏报率）、放量节奏遵守率（灰度时限遵守）、回滚时效（各阶段 SLO 达标率）、灰度覆盖（发布走灰度的比例——绕过灰度的直发是制度漏洞）。
- 漏报比误报更致命：哨兵漏报意味着带病全量——漏报率单独统计（事故后回溯「哨兵当时有没有信号」）。
- 机制改进闭环：度量发现的短板（如 SRM 频发）进灰度机制迭代——度量自身有价值必须有闭环。
- 健康分看板：机制健康分趋势 + 短板归因——灰度体系的「体检报告」。
- 追问钩子：为什么哨兵「漏报率」比「误报率」更值得单独追踪——误报的代价是熔断疲劳（可治理）；漏报意味着哨兵在线但没发现真实问题，等于灰度的安全网有洞——漏报只能靠「事故后回溯哨兵当时的数据信号」才能统计，需要专门的回溯机制。

```javascript
function grayMechanismHealth() {
  return {
    split: { srmRate: srmIncidents / totalGrays },
    sentinel: { fpRate, missRate: incidentsWhereSentinelHadSignal / incidents },   // 漏报：事故回溯
    discipline: { rampSloOk: onTimeAdvances / advances, bypassRate: directPublishes / publishes },
    rollback: { sloMet: rollbackWithinSlo / rollbacks },
    loop: '短板 → 机制迭代 → 复测',
  };
}
// 漏报回溯：事故后检查哨兵当时数据
postIncident(incident => sentinelHadSignal(incident.window));
```
