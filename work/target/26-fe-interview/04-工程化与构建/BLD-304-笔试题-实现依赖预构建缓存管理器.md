## BLD-304：手写预构建缓存

**需求与边界**：
- 需求：依赖预构建（SCN-BLD-210）的缓存管理——① 缓存键（lockfile hash + optimizeDeps 配置 + 工具版本）；② 缓存失效判定与重跑；③ 依赖发现补偿（运行时发现新依赖 → 中断重预构建——vite 的 missing dep 机制）；④ 缓存体积治理（旧版本清理）。
- 边界：① 键完整（exclude/include 变化也要失效）；② 补偿发现的依赖写入 include（下次不再中断）；③ 并发预构建防重复（同键单飞）。

**答**：
```javascript
async function optimizeDeps(config, lockfile, { cacheDir = 'node_modules/.vite' } = {}) {
  const key = sha256(JSON.stringify({
    lock: sha256(lockfile),                            // lockfile 变更 → 失效
    cfg: config.optimizeDeps,                          // include/exclude 变更 → 失效
    ver: ESBUILD_VERSION,                              // 工具版本
  }));
  const cachePath = path.join(cacheDir, key);
  if (fs.existsSync(cachePath)) return { hit: true, deps: cachePath };   // 命中
  return withSingleFlight(key, async () => {           // 并发单飞（SCN-ENG-276）
    const discovered = await esbuildPrebundle(config.optimizeDeps.include);
    const missing = await runtimeDiscoverMissing();    // 运行时新依赖补偿
    if (missing.length) {                              // 新依赖：写入 include 重跑
      config.optimizeDeps.include.push(...missing);
      persistInclude(config);                          // 下次命中（补偿发现）
      return optimizeDeps(config, lockfile);           // 重跑
    }
    cleanupOldCaches(cacheDir, { keep: 3 });           // 旧缓存清理（体积治理）
    return { hit: false, deps: cachePath, discovered: discovered.length };
  });
}
```

**评分点**:
- 缓存键三要素（lockfile/配置/工具版本——SCN-BLD-210 失效条件）。
- 补偿发现循环（运行时新依赖 → 写 include → 重跑——不再中断）。
- 单飞防并发预构建。
- 旧缓存清理（体积治理）。

## 变体与延伸（补充）

**变体与延伸**：

1. 多进程同时构建怎么保证只预构建一次？ → 缓存目录上加文件锁，进程内用单飞合并并发请求，产物先写临时目录再原子 rename，避免读到半成品。
2. 缓存目录膨胀怎么治理？ → 按 key 保留最近 N 份并做 LRU 清理，总体积超阈值时优先删最久未命中的，同时打印回收量便于观察。
3. 怎么验证缓存键的完整性？ → 分别改 lockfile、include 配置、esbuild 版本，三次断言 key 都发生变化；再补一次无改动断言 key 保持不变。
