## OPS-283：发布决策支持怎么设计？
**答**：
- 决策支持器：发布申请时聚合「风险因素」（变更大小/触及路径/当前系统健康度/业务日历/历史相似发布的成功率）输出建议（建议发布/建议延迟/建议缩小范围）——决策仍是人的，建议是量化依据。
- 系统健康度输入：当前线上错误率/性能基线是否正常（带病发布放大风险）——「系统不健康时推迟发布」是隐含规则但常被忽略。
- 相似发布画像：同类型变更（触及相关模块/同规模）的历史成功率与问题——历史是最好的预测器。
- 建议的可解释性：每个建议列出依据因素（建议延迟因为：系统错误率 2× 基线 + 触及支付链路）——黑盒建议不会被采纳。
- 追问钩子：为什么「系统当前健康度」要进发布决策——带病发布（系统已有异常）会让新版本的异常与既有异常混杂，归因灾难且爆炸半径叠加；决策支持器把「等系统恢复再发」变成显式建议，对抗「排期压力下的带病发布」——这是决策支持最有价值的拦截。

```javascript
function publishAdvice(plan) {
  const factors = {
    risk: riskLevel(plan),                             // OPS-202
    systemHealth: currentHealth(),                     // 带病发布检查
    similarHistory: searchSimilar(plan).successRate,   // 历史画像
    calendar: businessCalendar.conflicts(plan.window),
  };
  if (factors.systemHealth.degraded)
    return { advice: 'DELAY', reasons: ['系统错误率 2× 基线', '触及支付链路'] };
  return { advice: factors.similarHistory > 0.9 ? 'PROCEED' : 'NARROW-SCOPE',
           reasons: explain(factors) };                // 可解释
}
```
