## ENG-311：手写缓存命中率审计

**需求与边界**：
- 需求：按任务类型统计缓存命中率；定位低命中任务——① 归因分析：命中失败的键输入中「哪个输入段最常变化」（源文件/env/依赖）；② 输出优化建议（env 声明过多/源码大 monorepo 全量 hash）。
- 边界：① 命中率分母包含「应命中」（键相同但缓存缺失也算 miss——缓存被清理）；② 变化归因需要记录每次的键输入分段 hash（键 = f(sourceHash, envHash, depHash, taskdefHash)）；③ 样本量小的任务不做归因。

**答**：
```javascript
function cacheAudit(records, { minSamples = 20 } = {}) {
  const byTask = groupBy(records, 'task');
  return Object.entries(byTask).map(([task, list]) => {
    const hit = list.filter(r => r.hit).length;
    const miss = list.filter(r => !r.hit);
    const rate = hit / list.length;
    // 归因：miss 样本中哪个输入段与上次不同
    const segments = { source: 0, env: 0, deps: 0, taskdef: 0, absent: 0 };
    for (const r of miss) {
      if (!r.prevKeys) { segments.absent++; continue; }    // 键相同缓存缺失
      for (const seg of ['source', 'env', 'deps', 'taskdef'])
        if (r.keys[seg] !== r.prevKeys[seg]) segments[seg]++;
    }
    const dominant = list.length >= minSamples
      ? Object.entries(segments).sort((a, b) => b[1] - a[1])[0] : null;
    return {
      task, hitRate: rate,
      suggestion: dominant?.[0] === 'env' ? 'env 声明过多，裁剪非必要变量'
        : dominant?.[0] === 'source' ? '源码输入过宽，收窄 include'
        : dominant?.[0] === 'absent' ? '缓存被清理，检查保留策略' : null,
    };
  }).sort((a, b) => a.hitRate - b.hitRate);              // 低命中置顶
}
```

**评分点**:
- 应命中区分（键同缓存缺失 vs 键真的变了——归因的前提）。
- 分段归因（哪个输入段最常变——ENG-205 治理落点）。
- 分段归因建议映射（env/source/absent → 对应优化动作）。
- 样本量下限（小样本不归因防误导）。

## 变体与延伸（补充）

**变体与延伸**：

1. 命中率低但构建仍快说明什么？ → 缓存没覆盖真正的热点任务，优化对象应是耗时分布，而不是命中率这个数字本身。
2. 怎么把未命中归因到具体任务？ → 按任务类型分组，再把 key 变化原因分成源码、依赖、配置、环境四类，逐类统计占比。
3. 修复后怎么验证？ → 同 commit 前后各跑一次对比命中率与总耗时，并固定机器规格排除环境差异。
