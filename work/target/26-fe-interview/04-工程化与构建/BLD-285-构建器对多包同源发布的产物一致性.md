## BLD-285：多包一致性怎么保证？
**答**：
- 一致性目标：固定版本组（SCN-ENG-204）的多包产物「语义对齐」——tokens 改了颜色，ui 组件构建必须用新 tokens（不是旧缓存）。
- 保证机制：同一次构建触发（turbo 依赖图：ui 依赖 tokens 的 build——自动先建 tokens）+ 缓存键传递（tokens 的内容 hash 进 ui 的构建键——上游变更传递失效）。
- 发布编排：多包同发（changesets fixed 组）+ 发布后冒烟（组内包组合验证——SCN-ENG-233 接线验证）。
- 一致性破坏场景：手动只发 ui 不发 tokens（版本错位）——CI 校验组内版本一致（SCN-ENG-308 bump 推断联动）。
- 追问钩子：为什么「tokens 的内容 hash 进 ui 的构建键」是一致性的技术核心——构建缓存按键命中：ui 的缓存键若不含 tokens hash，tokens 改色后 ui 命中旧缓存（旧色打包进产物）——「上游内容作为下游键的一部分」让依赖变更自动传播失效，这是缓存正确性在多包场景的必然要求。

```javascript
// 缓存键传递
// ui 的构建键 = ui源码hash + tokens产物hash（上游）
turbo.build.inputs = ['src/**', '../tokens/dist/**'];
// 组内版本一致校验
fixedGroup.forEach(p => assert(p.version === groupVersion));   // 错位即失败
```
