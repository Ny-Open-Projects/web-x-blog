## BLD-282：压缩器选择怎么做？
**答**：
- 压缩器矩阵：terser（体积最优、慢、JS 生态成熟）、esbuild minify（快 10~50×、体积差 1~3%）、swc minify（快、体积接近 terser）、Google Closure（体积极致、生态窄）。
- 选择决策：构建时长敏感（大仓频繁构建）→ esbuild/swc；体积敏感（移动端弱网）→ terser/Closure；混合——dev/esbuild + prod/terser。
- 压缩比对比的实验方法：同一真实项目跑各压缩器 → gzip 前后体积 + 耗时矩阵——用真实产物（不同压缩器对「重复模式多」的代码表现差异大）。
- 兼容性回归：换压缩器必须跑产物行为回归（压缩器 bug 边界不同——SCN-BLD-252 golden 回归）。
- 追问钩子：为什么「同一项目实测」比「看 benchmark 数据」重要——压缩比高度依赖代码特征（框架产物的高度重复模式 vs 手写工具函数的紧凑逻辑），不同压缩器的优化侧重不同——官方 benchmark 的项目特征与你不同；实测一次（体积+耗时矩阵）的成本远低于选错的长期代价。

```javascript
// 实测矩阵
for (const m of ['terser', 'esbuild', 'swc']) {
  const r = await build({ minifier: m });
  table.push({ minifier: m, raw: r.size, gzip: r.gzipSize, ms: r.duration });
}
// 混合策略
dev: esbuild minify (快) / prod: terser (体积最优)
```
