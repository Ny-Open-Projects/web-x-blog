# 08 性能与大数据量（ALG-149~152 / 169 / 189 / 224 / 285 / 332）

大数据量题在前端面试里几乎只有四种解法，而且优先级是固定的：**能不做的就不做（降采样 / 虚拟化）→ 能搬走的就搬走（Worker）→ 搬不走的就切碎（时间片）→ 切不碎的才谈流式（不攒全量）**。面试官问"10 万条数据怎么渲染"，真正想听的不是某个 API，而是你会不会先算预算：一帧 16.7ms、长任务阈值 50ms、主线程留给渲染和输入的时间到底还剩多少。

> **识别特征**：题干出现「10 万条 / 百万行 / 上万个定时器 / 80MB / 5000 万 / 卡死十几秒 / 页面无响应」，第一反应是问自己三个问题：这批数据**真的要全量处理吗**（能否降采样 / 分页 / 虚拟化）？这活**必须主线程干吗**（能否 Worker）？必须主线程干的话，**一段最多能干多久**（8ms 预算，然后让出）？

## 场景范式（四条主线）

**范式一：先削减规模，再谈优化。**
1 万个点画在 800px 的画布上，每像素有 12.5 个点，多出来的点不但看不见，还会因为抗锯齿叠加让线条变粗、颜色失真。所以第一刀永远是降采样（ALG-285）：按像素宽度分桶，每桶只保留 min 和 max 两个点，输出 2×width 个点，视觉上峰值一个不丢。同理，10 万条日志不该一次性塞进 DOM，虚拟列表只渲染视口内那几十行；100 万行导出也不该在前端"全部转成字符串"，而是分批转、边转边攒。**优化第一步不是写更快的循环，而是让循环的次数变少。** 这条在面试里最容易被忽略——很多人上来就 Worker，却没发现请求本身只要 800 个点。

**范式二：把计算搬离主线程，注意搬运成本。**
Worker 的价值是把"计算"从渲染线程剥离，但 `postMessage` 默认是结构化克隆，1 亿个 float64 复制一次就是 800MB 的搬运，比计算本身还贵。所以要么用 Transferable（`postMessage(buf, [buf])` 把 ArrayBuffer 所有权转移，零拷贝但原线程失去访问权），要么用 SharedArrayBuffer（多线程共享同一块内存，需要 COOP/COEP 响应头，且有 Atomics 同步成本），要么像 ALG-224 那样把大数组切片，只把"本块"转移给对应 Worker。判据：**数据量 × 拷贝次数 > 计算量时，转移才有意义**；小数据（几万条）用 Worker 反而更慢，因为启动 Worker 本身就要几毫秒。

**范式三：时间片——用"预算"而不是"条数"丈量让出时机。**
固定 batch 大小（每 1000 条让出一次）在数据项耗时波动时会翻车：某批里恰好有几条超慢的记录，这一批就跑成了 200ms 的长任务。正确做法是每处理一条就看一次 `performance.now()`，累计超过 8ms 就 `await` 一个宏任务让出——8ms 是给渲染和输入留出的余量，保证每帧总占用不逼近 16.7ms，也不会触发 50ms 长任务告警。让出手段有三档：`setTimeout(0)`（最通用，但被嵌套层级限流到 4ms 起）、`requestAnimationFrame`（对齐渲染帧，适合动画相关）、`requestIdleCallback`（只在空闲时跑，适合非紧急渲染，但可能被无限推迟，必须配 timeout 兜底）。

**范式四：流式——峰值内存恒定，而不是总量变小。**
80MB 的 NDJSON 用 `JSON.parse` 整体解析，会同时持有原始字符串、解析中间态和最终对象树，峰值可能是文件大小的 3~5 倍。流式的关键不是"分块读"，而是**缓冲区只保留不完整的残余片段**：每读到一块，用 `TextDecoder({ stream: true })` 解码（处理 UTF-8 多字节字符被切断的情况），按换行切出完整行立即 parse 并交给消费者，剩下的半行留在 buffer。这样无论文件多大，内存都是 O(一行 + 一个 chunk)。同理，CSV 导出用 `Blob(parts)` 累积 encode 后的 Uint8Array 片段，而不是反复 `str +=`（字符串不可变，反复拼接是 O(n²) 的拷贝）。

## 答题前先算三笔账

面试里报数字比背 API 更能体现工程感，这三组数字建议直接记住：

**时间账**：60fps 对应每帧 16.7ms，其中浏览器自身的样式计算、布局、绘制要吃掉一半左右，真正留给 JS 的只有 8ms 上下；超过 50ms 的任务会被 Performance 面板标红，也就是 INP 开始劣化的起点；用户可感知的"卡"大约从 100ms 起，超过 1s 就会觉得"点了没反应"。所以时间片的预算取 8ms 不是拍脑袋，而是"每帧给 JS 的余量"。

**内存账**：一个 JS 数字占 8 字节（SMI 除外），1000 万个 float64 就是 80MB，1 亿个是 800MB——这已经逼近移动端单标签页的实际可用上限（桌面 Chrome 约 4GB，iOS Safari 更紧）。所以"1 亿条求和"的第一句回答必须是"数据不该以对象数组的形式待在前端"，第二句才是 Worker 并行。

**搬运账**：结构化克隆的成本约等于"序列化 + 反序列化 + 分配新内存"，几十 MB 起步就明显可见；Transferable 是 O(1) 的所有权转移，但转移后原线程失去数据；SharedArrayBuffer 才是真正的零拷贝共享，代价是需要 COOP/COEP 响应头与 Atomics 同步。答题时说清这三者的取舍，比写十个 `new Worker` 都有用。

## 精讲（6 题）

### 精讲 1 · [ALG-149] 10 万条日志的时间分片渲染

**场景**：运营后台要展示一次批量操作的 10 万条日志。直接 `for` 循环 `appendChild`，主线程被占十几秒，页面白屏、按钮点不动、用户以为卡死。

**问法**："怎么让这 10 万条渲染完，同时页面全程可交互？为什么不能一次性 append？"

**思路**：两个问题要分开治。**重排**问题用 `DocumentFragment`：先把节点挂在离线容器里，最后一次性挂到 DOM，整个过程只触发一次布局；如果直接往真实 DOM 上 append，每次插入都可能触发样式计算与重排（虽然浏览器会合并，但节点数上万时依然昂贵）。**长任务**问题用空闲时间分片：`requestIdleCallback` 给出的 `timeRemaining()` 表示"这一帧还剩多少毫秒可以挥霍"，只要大于 1ms 就继续塞节点，塞到不够就排队下一个空闲片，把控制权还给浏览器。注意必须在 `timeRemaining()` 里留余量（不要塞到 0），否则会挤占渲染。

```javascript
function renderInChunks(items, renderRow, mount, onDone) {
  const frag = document.createDocumentFragment();        // 离线容器：避免中间态重排
  let i = 0;
  const ric = window.requestIdleCallback ||
    (cb => setTimeout(() => cb({ timeRemaining: () => 8 }), 16));  // 兜底一帧
  function work(deadline) {
    // 只要还有空闲预算就继续塞，留 1ms 余量给渲染
    while (i < items.length && deadline.timeRemaining() > 1) {
      frag.appendChild(renderRow(items[i++]));
    }
    if (i < items.length) {
      ric(work, { timeout: 200 });                       // 未完：排队下一个空闲片
    } else {
      mount(frag);                                       // 完成：一次挂载，一次布局
      onDone && onDone(items.length);
    }
  }
  ric(work, { timeout: 200 });
}

// 演示（浏览器）：10 万行表格体
// renderInChunks(logs, log => Object.assign(document.createElement('tr'), { textContent: log.msg }),
//   frag => tbody.appendChild(frag), n => console.log('done', n));
```

**边界与追问**：① `requestIdleCallback` 在 Safari 长期缺失，必须写兜底；② 空闲回调**可能一直不触发**（页面持续有动画），所以 `timeout` 兜底是必需的，超时后浏览器会强制以低优先级调用；③ 10 万行 DOM 即使分片渲染，最终内存也扛不住，正确终点是虚拟列表（只渲染视口），分片只是"必须全量渲染"时的止血方案；④ 追问"为什么不 `innerHTML +=`"——每次都重新解析整段 HTML，O(n²)，且会摧毁已有节点的事件与焦点。

### 精讲 2 · [ALG-150] Web Worker 分治统计 5000 万条记录

**场景**：埋点明细页要展示 5000 万条记录的求和与均值，主线程一次循环要好几秒，页面直接假死。

**问法**："Worker 怎么拿数据？为什么不直接 `postMessage(大数组)`？分治在这里解决了什么？"

**思路**：三层要点。**搬运**：绝不能把整份数据深拷贝给 Worker（5000 万个数字的结构化克隆本身就要几百毫秒 + 双倍内存），要么用 Transferable 转移所有权，要么切片后只转移本片。**分治**：递归二分到 100 万条以下就直接累加——不是为了算法复杂度（都是 O(n)），而是让单次循环短、缓存友好，并且天然可扩展成"多 Worker 各算一段再合并"的 map-reduce。**回传**：Worker 只回传聚合结果（两个数字），不回传中间数组，主线程全程 O(1)。如果数据是 1 亿条，则升级到 ALG-224 的 Worker 池 + 分块并行。

```javascript
// sum-worker.js 的内容（真实项目放独立文件，或用 Blob URL 内联）
const workerSrc = `
self.onmessage = ({ data }) => {
  const arr = new Float64Array(data.buf);          // 本片数据（已 transfer 过来）
  let sum = 0, max = -Infinity;
  for (let i = 0; i < arr.length; i++) {
    sum += arr[i];
    if (arr[i] > max) max = arr[i];
  }
  self.postMessage({ sum, max, count: arr.length }); // 只回聚合值
};`;

function aggregateInWorker(f64, parts = 4) {
  const url = URL.createObjectURL(new Blob([workerSrc], { type: 'text/javascript' }));
  const chunk = Math.ceil(f64.length / parts), jobs = [];
  for (let p = 0; p < parts; p++) {
    const start = p * chunk, end = Math.min(f64.length, start + chunk);
    if (start >= end) break;
    const part = f64.slice(start, end);            // 只拷贝本片，避免整份克隆
    const w = new Worker(url);
    jobs.push(new Promise(resolve => {
      w.onmessage = e => { resolve(e.data); w.terminate(); };
      w.postMessage({ buf: part.buffer }, [part.buffer]);  // Transferable 零拷贝
    }));
  }
  return Promise.all(jobs).then(rs => ({
    sum: rs.reduce((a, r) => a + r.sum, 0),
    max: Math.max(...rs.map(r => r.max)),
    count: rs.reduce((a, r) => a + r.count, 0),
  }));
}

const data = Float64Array.from({ length: 1e6 }, (_, i) => i % 100);
aggregateInWorker(data, 4).then(r => console.log(r.count, r.max));  // 1000000 99
```

**边界与追问**：① 转移后主线程的 `part.buffer` 变成 detached，长度归零，别再访问；② 多个 Worker 同时持有同一个 ArrayBuffer 只有在 SharedArrayBuffer 下才可能，普通 buffer 转移给一个 worker 后其他 worker 就拿不到了；③ Worker 里不能访问 DOM，且 `new Worker` 的脚本必须同源（Blob URL 例外）；④ 追问"5000 万条数据从哪来"——真实场景应该由服务端聚合，前端只负责展示，Worker 是"数据已经在前端"时的补救。

### 精讲 3 · [ALG-151] NDJSON 的流式解析

**场景**：接口按 NDJSON（每行一个 JSON）下发 80MB 数据，`await res.json()` 或 `JSON.parse(await res.text())` 直接把标签页打爆。

**问法**："为什么要用 `TextDecoder` 的 `stream: true`？缓冲区怎么控制大小？最后没有换行的那一行怎么办？"

**思路**：`response.body` 是 `ReadableStream`，一次给你一个 Uint8Array 块，块边界**与字符边界、行边界都无关**——一个中文字符可能被切成两半，一行 JSON 也可能横跨三块。所以：① 解码必须用 `TextDecoder({ stream: true })`，它会把不完整的多字节序列留在内部，等下一块拼上；② 用字符串缓冲区拼接，每凑够一个 `\n` 就切出一行立即 `JSON.parse` 消费，缓冲区只剩残余；③ 流结束后必须 `decoder.decode()` 再 flush 一次，并处理最后一行没有换行符的尾行。整个过程内存是 O(单行 + 单块)，与文件总大小无关。

```javascript
async function parseNDJSONStream(response, onRecord) {
  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buf = '', count = 0;
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    // stream: true 让不完整的多字节字符留在 decoder 内部，等下一块
    buf += decoder.decode(value, { stream: true });
    let idx;
    while ((idx = buf.indexOf('\n')) >= 0) {
      const line = buf.slice(0, idx).trim();
      buf = buf.slice(idx + 1);           // 缓冲区只保留残余，不攒全量
      if (line) { onRecord(JSON.parse(line)); count++; }
    }
  }
  buf += decoder.decode();                // flush 残留的半个字符
  if (buf.trim()) { onRecord(JSON.parse(buf.trim())); count++; }  // 尾行可能没有换行
  return count;
}

// 演示（浏览器 / Node 18+）：Response 可直接用字符串构造
const text = '{"id":1,"uv":10}\n{"id":2,"uv":20}\n{"id":3,"uv":30}';
parseNDJSONStream(new Response(text), r => console.log('record', r.id, r.uv))
  .then(n => console.log('共', n, '条'));   // 逐条输出 1/2/3，共 3 条
```

**边界与追问**：① 不要用 `split('\n')` 处理整个 buffer，那会一次性分配全量数组，等于放弃流式；② 每行 `JSON.parse` 要 try/catch，脏行不能中断整个流；③ 若服务端下发的是标准 JSON 数组（不是 NDJSON），就得用增量 JSON 解析器（如 streaming-json），面试可以点一句"NDJSON 是为流式而生的格式"；④ 追问"背压"——`reader.read()` 本身就是拉模式，消费慢时流会自动减速，不需要额外实现。

### 精讲 4 · [ALG-152] 上万个定时器：时间轮

**场景**：在线房间里每个道具/Buff 都有自己的到期时间，上万个 Buff 就是上万个 `setTimeout`。浏览器定时器数量一多，注册/清理开销和内存都失控，页面开始掉帧。

**问法**："为什么上万个 setTimeout 不行？时间轮怎么用 O(1) 的添加代价管理它们？超过一圈的任务怎么办？"

**思路**：每个 `setTimeout` 都是一次宿主环境登记 + 一个闭包 + 一个定时器对象，上万个会让定时器线程和内存都吃不消；而且到期时间分散，无法批量处理。时间轮把时间切成固定大小的槽（如 60 个 1s 槽），整个系统**只开一个** `setInterval` 每秒 tick 一次，tick 时把当前槽里的任务全部取出执行。任务按 `ceil(delay / tickMs)` 算出"还有几格"，取模定位槽位；如果延迟超过一圈，就用 `round` 记录"要转几圈"，每经过一次该槽就 `round--`，减到 0 才真正执行——这就是分层时间轮的单层简化版。添加 O(1)，tick 均摊只处理到期的槽。

```javascript
class TimingWheel {
  constructor(slots = 60, tickMs = 1000) {
    this.slots = Array.from({ length: slots }, () => []);  // 环形槽
    this.tickMs = tickMs;
    this.current = 0;
    this.timer = null;
  }
  add(delayMs, fn) {
    const ticks = Math.max(1, Math.ceil(delayMs / this.tickMs));  // 至少下一格
    const slot = (this.current + ticks) % this.slots.length;
    // 超出一圈的部分折算成 round，每转一圈减一；ticks 正好等于一圈时 round 为 0
    this.slots[slot].push({ fn, round: Math.floor((ticks - 1) / this.slots.length) });
  }
  tick() {                                                 // 由唯一的系统定时器驱动
    this.current = (this.current + 1) % this.slots.length;
    const bucket = this.slots[this.current];
    const keep = [];
    for (const task of bucket) {
      if (task.round > 0) { task.round--; keep.push(task); }  // 还没到，留到下一圈
      else task.fn();                                          // 到期，执行
    }
    this.slots[this.current] = keep;
  }
  start() { if (!this.timer) this.timer = setInterval(() => this.tick(), this.tickMs); }
  stop() { clearInterval(this.timer); this.timer = null; }
}

const wheel = new TimingWheel(60, 1000);
const fired = [];
wheel.add(1500, () => fired.push('buff-A'));   // 1.5s 后
wheel.add(2500, () => fired.push('buff-B'));   // 2.5s 后
wheel.tick(); wheel.tick();                    // 手动推进 2 秒（演示用）
console.log(fired);                            // ['buff-A']
```

**边界与追问**：① 单层时间轮的精度是 tickMs，要更高精度就加分层（时/分/秒三层）或减小 tick；② `setInterval` 在后台标签页会被节流到 1s 甚至更久，所以时间轮 tick 时应按"实际经过的时间"补跑，而不是假设每次都准时；③ 任务取消需要返回句柄（在 task 上标记 `cancelled = true`，tick 时跳过）；④ 追问"和优先队列（最小堆）比"——堆的添加 O(log n)、取最近到期 O(1)，适合到期时间高度分散；时间轮适合"大量任务、时间范围集中"的场景，Redis 的定时任务就用了时间轮。

### 精讲 5 · [ALG-189] 百万行 CSV 的分批导出

**场景**：运营报表要导出 100 万行、20 列的表格。`rows.map(...).join('\n')` 一次性生成几百 MB 字符串，主线程卡死并且很容易触发内存上限。

**问法**："为什么不能先拼成一个大字符串？分批之后为什么还要用 Blob parts？CSV 的转义规则是什么？"

**思路**：字符串在 JS 里不可变，`s += chunk` 每次都要分配新字符串并拷贝旧内容，100 万行拼下来是 O(n²) 的拷贝量，而且峰值同时存在"旧串 + 新串"。正确做法是**按批转换**：每 5000 行转成一段字符串，`TextEncoder` 编码成 Uint8Array 收进数组（二进制片段不会再被拼接拷贝），最后 `new Blob(parts)` 把片段列表交给浏览器拼接。每批之间 `await` 一个宏任务让出，保证进度条能刷新、取消按钮能点。转义是另一条必答项：字段内出现双引号要翻倍，字段整体用双引号包裹，否则值里的逗号会把列冲散。

```javascript
const sleep = () => new Promise(r => setTimeout(r, 0));

async function exportCSV(rows, columns, filename, { batch = 5000 } = {}) {
  const encoder = new TextEncoder();
  const esc = v => `"${String(v ?? '').replace(/"/g, '""')}"`;   // 引号翻倍 + 整体包裹
  const parts = [encoder.encode(columns.map(c => esc(c.title)).join(',') + '\n')];
  for (let i = 0; i < rows.length; i += batch) {
    const lines = rows.slice(i, i + batch).map(row =>
      columns.map(c => esc(row[c.key])).join(',')
    );
    parts.push(encoder.encode(lines.join('\n') + '\n'));  // 二进制片段，避免字符串拼接
    await sleep();                                        // 每批让出，页面保持可响应
  }
  const blob = new Blob(parts, { type: 'text/csv;charset=utf-8' });
  const url = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url; a.download = filename; a.click();
  setTimeout(() => URL.revokeObjectURL(url), 1000);       // 及时释放 Blob
  return blob.size;
}

// 演示：3 行数据，含逗号与引号
const cols = [{ key: 'name', title: '名称' }, { key: 'note', title: '备注' }];
const rows = [{ name: 'A', note: 'a,b' }, { name: 'B', note: 'say "hi"' }];
exportCSV(rows, cols, 'demo.csv').then(size => console.log('bytes =', size));
```

**边界与追问**：① 加 BOM（`\uFEFF`）可以让 Excel 正确识别 UTF-8，但会影响程序读取，按需加；② 百万行 Blob 仍会在内存里驻留一份，超过 2GB 必须改用 File System Access API 的 `createWritable()` 真流式写入；③ `URL.revokeObjectURL` 要延后调用，立刻 revoke 会让下载中断；④ 追问"为什么不用 CSV 库"——库通常也是字符串拼接，大数据量下要确认它是否支持流式输出。

### 精讲 6 · [ALG-285] 万点折线的 min/max 分桶降采样

**场景**：监控大盘要画 1 万个点的曲线，画布只有 800px 宽。全量绘制既慢又丑——多个点挤在同一像素列里，抗锯齿叠加让线变粗、峰值被抹平。

**问法**："1 万个点画在 800px 上有什么问题？为什么保留 min/max 而不是取平均？"

**思路**：800px 意味着每列只能表达一个纵向区间，塞进去 12 个点纯属浪费。分桶降采样把数据按"每像素一桶"切开，每桶保留**最小值与最大值**两个点（按原始时间顺序输出），输出规模固定为 2×width。为什么不是平均值：平均值会把尖峰削平——一个瞬时 100% 的 CPU 尖刺，和 11 个 10% 的点取平均后变成 17%，告警就看不出来了；min/max 保留了桶内的极值，所以"峰值一个不丢"，这在监控场景是硬需求。LTTB（最大三角形三桶）能用更少的点保持更好的视觉形状，但实现复杂，min/max 是性价比最高的答案。

```javascript
function minMaxDownsample(data, width = 800) {
  if (data.length <= width * 2) return data;             // 点不够多，不降采样
  const bucketSize = data.length / width;
  const out = [];
  for (let b = 0; b < width; b++) {
    const start = Math.floor(b * bucketSize);
    const end = Math.min(data.length, Math.floor((b + 1) * bucketSize));
    if (start >= end) continue;
    let minI = start, maxI = start;
    for (let i = start + 1; i < end; i++) {
      if (data[i].y < data[minI].y) minI = i;            // 记录本桶最小值下标
      if (data[i].y > data[maxI].y) maxI = i;            // 记录本桶最大值下标
    }
    // 按原始时间顺序输出，避免折线回折
    if (minI < maxI) out.push(data[minI], data[maxI]);
    else out.push(data[maxI], data[minI]);
  }
  return out;
}

// 演示：1 万个点压到 400 桶
const raw = Array.from({ length: 10000 }, (_, i) => ({ x: i, y: Math.sin(i / 50) * 100 }));
raw[5000].y = 999;                                       // 人为埋一个尖峰
const thin = minMaxDownsample(raw, 400);
console.log('原点数', raw.length, '降采样后', thin.length);
console.log('尖峰是否保留', thin.some(p => p.y === 999));  // true
```

**边界与追问**：① 桶数应取 `canvas CSS 宽度 × devicePixelRatio`，否则 Retina 屏会丢细节；② 如果数据是流式追加的（实时曲线），不要每次重算全量，维护"当前桶"的 min/max，桶满再推入结果；③ 追问"缩放后怎么办"——放大到局部时应回到原始数据重新分桶，而不是对已降采样的点再降采样（误差会累积）；④ 与 ALG-332 的关系：降采样减少的是"绘制量"，原地过滤减少的是"内存分配"，两者常一起用。
