# 04 排序、查找与二分（ALG-066~073 / 153 / 235 / 302）

前端真正会用到排序和查找的地方，几乎都不是"给一个数组排个序"这么直白：虚拟列表要在每帧里从 `scrollTop` 反推出"第一屏是第几项"，表格要求同价的行保持原渲染顺序，商品页要在 10 万条里拿前 10 名，搜索框要在 5 万个热词里挑出 3 个最像的。这些需求的共同前提是**数据有序**或**可以低成本变有序**，而所有"高频、每帧、每次输入都调用"的定位，都必须把 O(n) 压成 O(log n) 甚至 O(1)。所以这一章的考点不是背排序模板，而是三件事：能不能识别"这里的有序性从哪来"、能不能说清稳定性的业务后果、能不能在"排序 / 堆 / 二分 / 计数"之间按数据特征选型。

**识别特征**：看到「滚动/拖拽/输入时高频求位置」先想二分；看到「只取前 K 个」先想堆而不是全排；看到「值域很小（评分 1~5、状态码、年龄）」先想计数/桶排序；看到「相同的要保持原顺序」先问是不是稳定排序；看到「数据基本有序，只有少量乱序」先想插入排序或 TimSort 的自然 run。

## 场景范式

**范式一：二分的前提是"单调"，而单调往往是算出来的。** 数组本身常常无序——虚拟列表的 `heights` 是一堆杂乱像素值，但它的**前缀和** `offsets` 一定单调递增（高度非负），于是"scrollTop 落在第几项"就从"遍历累加"变成了"在前缀和里找第一个大于它的位置"（[ALG-066](../06-算法与手写/ALG-066-虚拟列表各项高度不定-已预计算每项的累计高度前缀.md)）。同一招在拖拽定位（[ALG-235](../06-算法与手写/ALG-235-拖拽排序的-THRESHOLD-与降级.md)）、时间轴刻度、分页累计条数上反复出现。答题时先明确指出"我对谁二分、它为什么单调"，比直接写 `while (lo < hi)` 有说服力得多。

**范式二：比较排序有 O(n log n) 下界，但那只约束"只靠比较"的算法。** 评分只有 1~5 时，计数排序开 5 个桶扫两遍就完事，O(n + k) 直接击穿下界（[ALG-072](../06-算法与手写/ALG-072-评价系统要按评分-整数-15-对几万条评价排序展.md)）——因为它根本没有做比较，只是在"计数 + 按值域顺序展开"。判断能不能用计数排序的两个条件：**值域小且是整数**、**不要求按对象的其他字段做次级排序**（否则要在桶内保序）。值域大就用桶排序，值是字符串就老老实实比较排序。

**范式三：稳定性是业务需求，不是学术细节。** "价格相同的行保持原有渲染顺序"这句话就是稳定排序的定义（[ALG-069](../06-算法与手写/ALG-069-表格对-10-万行数据排序-要求价格相同的行保持.md)）。归并稳定是因为合并时相等取左（`<=`），快排不稳定是因为分区交换会跨越相等元素（[ALG-070](../06-算法与手写/ALG-070-面试常要求手写快排-并说清它为什么不稳定-前端什.md)）。ES2019 起规范要求 `Array.prototype.sort` 稳定，V8 实际用 TimSort（归并 + 插入的混合），所以日常业务直接 `sort` 就够；但要能在面试里说清"如果我手写快排，就得额外带上原下标做兜底比较"，这就是 DSU（装饰-排序-去装饰）的意义（[ALG-073](../06-算法与手写/ALG-073-面试官问表格多列排序-评论排序-大列表排序-你在.md)）。

**范式四：要"前 K 个"就别全排。** 全量排序 O(n log n) 会把 10 万条全部排好，而你只需要前 10 个。小顶堆把复杂度降到 O(n log k)：堆里永远只留当前最大的 K 个，新元素只跟堆顶（K 个里最弱的）比一次，赢了才替换（[ALG-153](../06-算法与手写/ALG-153-10-万个商品要取销量前-10-名展示-全量排序.md)）。如果 K 接近 n，堆反而不如直接排序；如果数据是流式的、无法回看，堆是唯一选择。另一个路线是快速选择（quickselect），平均 O(n) 但会打乱数组且最坏 O(n²)，工程上要的是"稳定可预期的 n log k"，所以堆更常见。

**范式五：二分的正确性靠"区间定义 + 不变量"，不靠记忆。** 写之前先声明区间是左闭右开 `[lo, hi)` 还是闭区间 `[lo, hi]`，再声明循环不变量（"答案一定在区间内"），最后确定 `mid` 归哪边。`hi = mid` 表示 mid 仍可能是答案，`lo = mid + 1` 表示 mid 已被排除——把这两句想清楚，`while (lo < hi)` 还是 `while (lo <= hi)`、返回 `lo` 还是 `lo - 1` 就不会再靠猜。旋转数组那题还多一层：**必须和右端点比**而不是左端点，否则"整体有序"和"断点在左"两种情况无法区分（[ALG-068](../06-算法与手写/ALG-068-CDN-节点按轮换制调度-日志里节点-id-数组.md)）。


## 精讲（6 题）

### 精讲 1 · [ALG-066] 前缀和 + 二分：虚拟列表的每帧定位

**场景**：消息列表 5 万条、每条高度由内容决定（40~200px 不等），滚动时只渲染可视区附近的 20 条。每次 `scroll` 都要回答一个问题：`scrollTop = 12873` 时，屏幕最上面那条是第几项？如果用 `findIndex` 累加高度，最坏 5 万次加法，而滚动一秒触发几十次，主线程直接卡死。

**问法**："已经给你每条的高度，怎么 O(log n) 定位视口起点？为什么可以对它二分？"

**思路**：单个 `heights` 数组是无序的，没法二分；但**累计高度** `offsets[i] = 前 i 项之和` 一定是单调递增的（高度非负），这就把"找第几项"变成了"在有序数组里找第一个大于 scrollTop 的位置"。注意这里的判定要用 `offsets[mid + 1] <= scrollTop`（第 mid 项的**底部**还在视口上方，说明整项都被滚过去了），而不是 `offsets[mid] <= scrollTop`——后者会把"刚好贴着视口顶部"的项错误地排除掉。可视区底部同理再二分一次，两次 O(log n) 就拿到 `[start, end)`，5 万条也只需约 16 次比较。这道题的真正考点是**结构化预处理**：花 O(n) 建一次前缀和，换此后每帧 O(log n)，与"每次滚动都 O(n)"差一个数量级。

**代码**：

```javascript
// offsets[i] = 前 i 项高度之和，offsets[0] = 0，长度 = 项数 + 1
function buildOffsets(heights) {
  const offsets = new Array(heights.length + 1);
  offsets[0] = 0;
  for (let i = 0; i < heights.length; i++) offsets[i + 1] = offsets[i] + heights[i];
  return offsets;
}
// 找"底部越过 scrollTop 的第一项"：即 offsets[idx + 1] > scrollTop 的最小 idx
function findStart(offsets, scrollTop) {
  let lo = 0, hi = offsets.length - 1; // 项下标区间 [0, 项数)
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (offsets[mid + 1] <= scrollTop) lo = mid + 1; // 第 mid 项整个在视口上方
    else hi = mid;                                    // mid 可能是答案，保留
  }
  return lo;
}
// 一次滚动只做两次二分，拿到需要渲染的 [start, end)
function visibleRange(offsets, scrollTop, viewportH) {
  const start = findStart(offsets, scrollTop);
  const lastVisible = findStart(offsets, scrollTop + viewportH);
  return [start, Math.min(lastVisible + 1, offsets.length - 1)];
}
const offsets = buildOffsets([40, 60, 30, 50]); // [0, 40, 100, 130, 180]
console.log(offsets, findStart(offsets, 0), findStart(offsets, 45), visibleRange(offsets, 0, 100));
// [0,40,100,130,180]  0  1  [0,3]
```

**边界与追问**：`offsets` 长度是 `n + 1`，`offsets[0] = 0` 让"第一项从 0 开始"这个边界不需要特判；`scrollTop` 超过总高度时要 clamp，否则会得到 `n`（越界）。最高频的追问是"高度会变怎么办"——某项展开/收起导致高度变化时，不能每次重建整个前缀和（那又退回 O(n)），工程上用树状数组/线段树支持 `O(log n)` 的单点更新 + 前缀查询，或者用"分块 + 块内偏移"的近似结构；如果只是图片加载后高度小幅抖动，可以用 `ResizeObserver` 收集变更、在下一帧批量重建。再追"为什么不做缓存上次位置"，答"可以，但用户拖动滚动条跳跃时缓存失效，二分才是保底"。

### 精讲 2 · [ALG-068] 旋转数组二分：和谁比决定了正确性

**场景**：CDN 节点按"轮换制"调度，节点 id 数组是 `[3, 4, 5, 1, 2]` 这种"升序数组在某点被切断再拼回去"的形态。调度器要 O(log n) 找到轮换起点（也就是最小值），因为每次请求都要算一次，O(n) 扫不行。

**问法**："旋转数组找最小值，为什么必须和右端点比较？和左端点比会怎样？"

**思路**：二分的关键是"每次比较都必须能排除一半区间"。旋转后数组被断点分成两段，每段内部升序。取 `mid` 后看 `nums[mid]` 和 `nums[hi]`：如果 `nums[mid] > nums[hi]`，说明 `mid` 在左段、断点在它右边（否则右半段应该整体更大），于是 `lo = mid + 1`；如果 `nums[mid] < nums[hi]`，说明从 `mid` 到 `hi` 是有序的，断点在 `mid` 左边**且 mid 自己可能就是最小值**，所以是 `hi = mid`（不是 `mid - 1`）。如果和左端点比，遇到"数组根本没旋转"时 `nums[mid] > nums[lo]` 恒成立，你无法区分"断点在右"和"整体有序"，逻辑立刻分叉。相等时（有重复元素）无法判断，只能 `hi--` 缩小一格，这也是重复元素版本最坏退化到 O(n) 的原因。

**代码**：

```javascript
function findMin(nums) {
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (nums[mid] > nums[hi]) lo = mid + 1;  // 右端比中点小 → 断点在右半，最小值在 mid 右侧
    else if (nums[mid] < nums[hi]) hi = mid; // 右半段本身有序 → 断点在左（mid 可能就是起点）
    else hi--;                               // 首尾相等（重复值），安全收缩一格
  }
  return nums[lo]; // 收敛到轮换起点，也是最小值
}
console.log(findMin([4, 5, 6, 7, 0, 1, 2])); // 0
console.log(findMin([3, 4, 5, 1, 2]));       // 1
console.log(findMin([2, 2, 2, 0, 2]));       // 0
console.log(findMin([1, 3, 5]));             // 1（未旋转）
```

**边界与追问**：未旋转的 `[1,3,5]` 也要能返回 1（此时 `nums[mid] < nums[hi]` 一路把 `hi` 拉回 0）；单元素直接返回它自己；全相同 `[2,2,2,2]` 靠 `hi--` 退化成线性但结果正确。追问"如果要在旋转数组里搜 target 呢"——先二分找断点，再判断 target 落在哪一段，然后在段内做普通二分，总共还是 O(log n)；追问"为什么不用 `nums[lo]` 做参照然后记录 min"——那只能处理无重复且要额外处理整体有序分支，边界多、易错，右端点参照是最少特判的写法。

### 精讲 3 · [ALG-069] 归并排序：稳定性藏在 `<=` 里

**场景**：10 万行的订单表格，用户点"按价格排序"，运营要求"价格一样的行，保持接口返回时的顺序"。如果排序不稳定，同样价格的订单每次点击后顺序都不一样，用户会觉得"表格在乱跳"，截图对账时也对不上。

**问法**："手写一个稳定排序，并指出稳定性的那行代码在哪。"

**思路**：归并排序的稳定性只取决于合并时的一个符号。合并两个已排好的半区时，若 `left[i]` 与 `right[j]` 相等，取左边那个——因为左半区的元素在原数组中本来就更靠前（递归是按下标切分的），先放它就能保住原始相对顺序。写成 `cmp(left[i], right[j]) <= 0` 就是稳定，写成 `<` 就变成不稳定（相等时会让右边的先出）。这个"符号即语义"的细节是面试官最爱追问的点。另外要能解释为什么快排做不到：快排的分区是**长距离交换**，可能把两个相等元素跨越整个数组换位，谁先谁后完全由 pivot 位置决定，无法用局部规则保证。

**代码**：

```javascript
function mergeSort(arr, cmp) {
  if (arr.length <= 1) return arr;
  const mid = arr.length >> 1;
  const left = mergeSort(arr.slice(0, mid), cmp);
  const right = mergeSort(arr.slice(mid), cmp);
  const out = [];
  let i = 0, j = 0;
  while (i < left.length && j < right.length) {
    // <= 是稳定性的全部秘密：相等时先取左半（原数组里更靠前的那个）
    if (cmp(left[i], right[j]) <= 0) out.push(left[i++]);
    else out.push(right[j++]);
  }
  while (i < left.length) out.push(left[i++]);
  while (j < right.length) out.push(right[j++]);
  return out;
}
const rows = [
  { id: 'a', price: 10 }, { id: 'b', price: 5 },
  { id: 'c', price: 10 }, { id: 'd', price: 5 },
];
console.log(mergeSort(rows, (x, y) => x.price - y.price).map((r) => r.id)); // [ 'b', 'd', 'a', 'c' ]
```

**边界与追问**：复杂度是稳定的 O(n log n)（不像快排会退化到 O(n²)），代价是 O(n) 额外空间；递归深度是 log n，10 万条也只有 17 层，不会爆栈。比较函数必须满足"自反、传递"，返回 `NaN`（比如字段缺失导致 `undefined - undefined`）会让归并结果错乱，工程上要在 comparator 里兜底 `Number(x) || 0`。追问"为什么 V8 用 TimSort 而不是纯归并"——因为真实数据常有大量已有序片段（run），TimSort 先识别 run 再对短 run 用插入排序，近乎有序时能接近 O(n)，而纯归并无论如何都要 n log n；追问"原地归并存在吗"——存在但常数极大、只在内存受限时用，前端不必。

### 精讲 4 · [ALG-070] 三路快排：为什么它能扛住大量重复值

**场景**：评论列表按点赞数排序，几万条评论里大量点赞数是 0 或个位数——重复值极多。用两路快排（分成"小于 pivot"和"大于等于 pivot"），一旦 pivot 等于这个高频值，每次分区只削掉一个元素，直接退化到 O(n²)。

**问法**："手写快排，说明为什么不稳定，以及三路分区比两路好在哪。"

**思路**：三路分区把数组切成 `< pivot`、`== pivot`、`> pivot` 三段，维护 `lt`（小于区的右边界）、`i`（当前扫描位）、`gt`（大于区的左边界）。遇到小于 pivot 就和 `lt` 交换、两者同时右移；遇到大于就和 `gt` 交换、**`gt` 左移但 `i` 不动**（因为从尾部换过来的元素还没被检查过，这是最容易写错的一行）；遇到等于就 `i++`，把它留在中段。递归只处理左右两段，等于 pivot 的一整批一次性排好——重复值越多，这题越快。随机 pivot 是为了避开"已排序数组 + 固定取首元素"导致的 O(n²)。不稳定的根源就在这些交换：`[3a, 3b]` 里 3b 可能被换到 3a 前面，相等元素的相对顺序被打破。

**代码**：

```javascript
// 三路分区：切成 < pivot | == pivot | > pivot 三段，等于 pivot 的一批不再参与递归
function quickSort(arr, lo = 0, hi = arr.length - 1) {
  if (lo >= hi) return arr;
  const pivot = arr[lo + ((Math.random() * (hi - lo + 1)) | 0)]; // 随机 pivot，避开有序退化
  let lt = lo, i = lo, gt = hi;
  while (i <= gt) {
    if (arr[i] < pivot) {
      [arr[lt], arr[i]] = [arr[i], arr[lt]]; // 换到左段
      lt++; i++;
    } else if (arr[i] > pivot) {
      [arr[i], arr[gt]] = [arr[gt], arr[i]]; // 换到右段
      gt--;                                   // 换过来的值还没看过，i 不动
    } else {
      i++;                                    // 等于 pivot：留在中段
    }
  }
  quickSort(arr, lo, lt - 1);
  quickSort(arr, gt + 1, hi);
  return arr;
}
console.log(quickSort([3, 1, 4, 1, 5, 9, 2, 6, 5])); // [1,1,2,3,4,5,5,6,9]
console.log(quickSort([]), quickSort([2, 2, 2]));    // [] [2,2,2]
```

**边界与追问**：空数组和单元素靠 `lo >= hi` 直接返回；全相等数组在第一层分区就把 `lt..gt` 撑满整个区间，递归立即结束，这正是三路分区的高光时刻。追问"稳定性怎么补"——排序前给每个元素附上原下标，比较时相等则比下标（DSU，见 [ALG-073](../06-算法与手写/ALG-073-面试官问表格多列排序-评论排序-大列表排序-你在.md)），代价是 O(n) 额外空间；追问"最坏 O(n²) 怎么彻底避免"——随机 pivot 只是概率保证，要确定性上界得用"中位数的中位数"选 pivot，工程上不值得；追问"前端还用快排吗"——业务排序交给 `sort`（TimSort），但需要自己实现"部分排序 / 第 K 大"时，快排的分区思想（quickselect）仍然有用。

### 精讲 5 · [ALG-153] TopK：为什么是小顶堆而不是大顶堆

**场景**：商品排行榜要从 10 万个商品里取销量前 10 名。全量 `sort` 是 O(n log n) 且要排完 10 万个，实际只需要 10 个。

**问法**："10 万取前 10，时间复杂度多少？为什么用最小堆？"

**思路**：这里的直觉反了——求**最大**的 K 个，用的却是**小顶堆**。原因是堆顶要承担"守门员"的角色：堆里存的是当前最强的 K 个，堆顶必须是这 K 个里**最弱**的那个，这样新元素只需和堆顶比一次就能 O(1) 判断"够不够格进榜"。如果用大顶堆，堆顶是最强的，你没法用一次比较淘汰弱者，就得把整个堆翻一遍。流程是：前 K 个直接建堆，之后每个元素与堆顶比较，更大就 `pop` 掉堆顶再 `push` 自己（O(log k)），否则跳过（O(1)）。总复杂度 O(n log k)，K=10 时 log k ≈ 3.3，几乎等于线性扫描一遍。最后堆里剩的就是 TopK，如果展示要按序，再对 K 个元素排一次（O(k log k)），不影响总复杂度。

**代码**：

```javascript
class MinHeap {
  constructor(cmp) { this.a = []; this.cmp = cmp; }
  get size() { return this.a.length; }
  get top() { return this.a[0]; }
  push(v) {
    this.a.push(v);
    let i = this.a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.cmp(this.a[p], this.a[i]) <= 0) break; // 父节点已更小，堆序成立
      [this.a[p], this.a[i]] = [this.a[i], this.a[p]];
      i = p;
    }
  }
  pop() {
    const top = this.a[0], last = this.a.pop();
    if (this.a.length) {
      this.a[0] = last;
      let i = 0;
      for (;;) {
        const l = i * 2 + 1, r = l + 1;
        let m = i;
        if (l < this.a.length && this.cmp(this.a[l], this.a[m]) < 0) m = l;
        if (r < this.a.length && this.cmp(this.a[r], this.a[m]) < 0) m = r;
        if (m === i) break;
        [this.a[m], this.a[i]] = [this.a[i], this.a[m]];
        i = m;
      }
    }
    return top;
  }
}
function topK(products, k) {
  const heap = new MinHeap((x, y) => x.sales - y.sales); // 小顶堆，堆顶是当前 TopK 里最弱的
  for (const p of products) {
    if (heap.size < k) heap.push(p);
    else if (p.sales > heap.top.sales) { heap.pop(); heap.push(p); } // 比最弱的强才换人
  }
  return heap.a.slice().sort((x, y) => y.sales - x.sales).map((x) => x.id);
}
const list = [72, 11, 99, 45, 3, 68, 90, 120, 7, 55].map((s, i) => ({ id: 'p' + i, sales: s }));
console.log(topK(list, 3)); // [ 'p7', 'p2', 'p6' ]
```

**边界与追问**：`k >= n` 时直接全排更简单（堆反而多做无用功）；`k = 0` 要提前返回空数组，否则 `heap.top` 是 `undefined` 会在比较时抛错。销量并列时"取谁"是业务问题：要么规定"并列都展示"（返回可能超过 K 个），要么按 id 兜底保证结果稳定。追问"数据是流式的、总量未知怎么办"——堆天然适合流式，内存只有 O(k)，这正是它比"先收集再排序"强的地方；追问"quickselect 不是平均 O(n) 更快吗"——是，但它会破坏原数组、最坏 O(n²)，而且只能拿到"第 K 大"还要再划分一次才能拿前 K 个，工程上堆的可预期性更值钱。

### 精讲 6 · [ALG-302] 编辑距离 Top3：把 DP 剪到能上生产

**场景**：搜索框输入 `iphon`，要推荐 3 个最可能的词。热词表 5 万个，每个词平均 8 个字符。对每个词都算完整编辑距离是 5 万 × 8 × 8 ≈ 320 万次单元格计算，每次输入跑一遍，输入法级别的卡顿。

**问法**："编辑距离怎么算？5 万个词怎么剪枝？"

**思路**：编辑距离的 DP 定义是 `dp[i][j]` = `a` 前 i 个字符变成 `b` 前 j 个字符的最少操作数，转移取三种操作的最小值：删（`dp[i-1][j] + 1`）、增（`dp[i][j-1] + 1`）、改（`dp[i-1][j-1] + cost`）。每行只依赖上一行，空间可压到 O(n)。真正让它能上生产的是**三层剪枝**：①长度差超过阈值直接跳过（编辑距离不可能小于长度差）；②长度窗口粗筛，只跟长度在 `[len-2, len+2]` 的词比；③**行最小值剪枝**——如果某一行的最小值已经超过阈值 `k`，由于后续行只会更大（每格都从上面/左边 +1 递增），可以立刻放弃这个词。剪枝后绝大多数候选在第 2~3 行就被淘汰，只剩几百个词跑完整 DP。排序按"距离升序、同距离按词频降序"——距离一样近时用户更可能想找热词。

**代码**：

```javascript
// 带阈值的编辑距离：超过 limit 立即剪枝，避免全表 O(n·L²) 的白算
function boundedEditDistance(a, b, limit) {
  if (Math.abs(a.length - b.length) > limit) return limit + 1; // 长度差已超阈值
  const n = b.length;
  let prev = Array.from({ length: n + 1 }, (_, j) => j); // 空串 a 变 b 的前 j 个字符
  for (let i = 1; i <= a.length; i++) {
    const cur = new Array(n + 1);
    cur[0] = i;
    let rowMin = cur[0];
    for (let j = 1; j <= n; j++) {
      const cost = a[i - 1] === b[j - 1] ? 0 : 1;
      cur[j] = Math.min(prev[j] + 1, cur[j - 1] + 1, prev[j - 1] + cost); // 删/增/改
      if (cur[j] < rowMin) rowMin = cur[j];
    }
    if (rowMin > limit) return limit + 1; // 整行都超阈值，后面只会更大
    prev = cur;
  }
  return prev[n];
}
function suggest(query, dict, { maxDist = 2, topK = 3 } = {}) {
  const scored = [];
  for (const item of dict) {
    if (Math.abs(item.word.length - query.length) > maxDist) continue; // 长度窗口粗筛
    const d = boundedEditDistance(query, item.word, maxDist);
    if (d <= maxDist) scored.push({ word: item.word, d, freq: item.freq });
  }
  scored.sort((x, y) => x.d - y.d || y.freq - x.freq); // 距离优先，同距离热词优先
  return scored.slice(0, topK);
}
const dict = [
  { word: 'iphone', freq: 900 }, { word: 'ipad', freq: 700 },
  { word: 'ipod', freq: 300 }, { word: 'siphon', freq: 50 },
  { word: 'phone', freq: 800 },
];
console.log(suggest('iphon', dict)); // iphone(1) / siphon(1) / phone(2)，ipod 同为 2 但词频低被挤掉
```

**边界与追问**：空串的编辑距离就是另一个串的长度（`prev` 的初始化已经覆盖）；`maxDist = 2` 是召回率与性能的折中，超过 2 的纠错结果用户基本不敢信。中文要按字符（`[...str]`）而不是 `length` 切，否则代理对会被拆开；大小写、全半角、前后空格要先归一化，否则"IPhone "和"iphone"距离是 3。追问"BK 树是什么"——按编辑距离构造的度量树，查询时用三角不等式 `|d(a,b) - d(b,c)| <= d(a,c)` 剪掉整棵子树，复杂度接近 O(候选)，但插入/删除要维护树结构，词表频繁更新时不划算；追问"为什么不只按首字母索引"——用户首字母打错（`siphon` / `iphon`）就直接漏召回，长度窗口比首字母更安全。
