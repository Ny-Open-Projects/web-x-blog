# 03 链表、栈队列与哈希（ALG-035~053 / 060~062 / 208 / 299）

这类题的共同点是：业务需求听起来是"界面问题"（弹幕池、浏览器历史、Keep-Alive 缓存、凑单提示），落到实现上却全是在问"你的容器支持哪几种 O(1) 操作"。链表、栈、队列、哈希表这四个结构本身都极简，真正考的是**组合**——两个栈拼出队列、双向链表配哈希拼出 LRU、单调栈把 O(n²) 的"往后找第一个更小"压成 O(n)。面试官要听的不是你背过模板，而是你能不能说出"为什么必须是这个结构，换个结构会在哪一步退化"。

**识别特征**：看到「先进先出但只有后进先出」「任意时刻 O(1) 取最值」「命中后要把这一项挪到最新」「要删的节点只拿到了它自己」「数据是流式到达、只关心最近 N 条」，先别写代码，先在纸上列出"需要哪几个操作、每个操作被调用多少次"，再倒推结构。凡是"删除/移动任意节点"出现的场景，基本就锁定了双向链表；凡是"每个元素只需进出一次"的场景，基本就是单调栈/单调队列。

## 场景范式

**范式一：先数操作次数，再选结构。** 面试里最容易被追问倒的一步是"你为什么用链表不用数组"。正确回答永远不是"链表插入快"，而是报出操作配比：LRU 的 `get` 是每帧几十次、淘汰是每几百次一次，而"把命中节点挪到头部"需要 O(1) 删除任意节点——只有双向链表能做到，数组要搬移、单链表拿不到前驱。反过来，如果需求是"按下标随机读取 + 尾部追加"（比如虚拟列表的数据窗口），数组的 O(1) 下标访问直接把链表打成筛子。**结构没有优劣，只有操作配比。**

**范式二：哨兵结点消灭边界分支。** 删除倒数第 N 个（[ALG-044](../06-算法与手写/ALG-044-日志链表太长要做裁剪删除倒数第-N-条日志如何一.md)）、删除含某域名的历史项（[ALG-208](../06-算法与手写/ALG-208-导航历史截断-链表删除节点.md)）、合并两个有序链表（[ALG-042](../06-算法与手写/ALG-042-两个埋点-SDK-各自按时间升序产出日志链表-要.md)）、LRU 的头尾操作（[ALG-047](../06-算法与手写/ALG-047-手写-LRU-时为什么必须用双向链表而不是单链表.md)），全都靠一个 dummy 结点把"删的是头结点""链表为空""插到空链"这三类特判统一掉。写链表题时先加哨兵，代码量通常能少三分之一，而且不会在 `head` 上写出 `if (!head) return` 的漏判。

**范式三：空间换时间有两种换法——加辅助结构，或者加指针。** 最小栈（[ALG-037](../06-算法与手写/ALG-037-浏览器历史记录很长-产品要求任意时刻-O-1.md)）和多一个 `min` 变量的区别在于：变量在 `pop` 掉最小值后无法回退，所以要么同步压一个"历史最小值栈"，要么在每个结点里存"以我为栈顶时的最小值"（链表版）。LRU 则是给每个结点加 `prev` 指针换 O(1) 删除。这两种换法都要在答案里明确说出"额外空间的量级"，因为面试官经常追问"能不能 O(1) 空间"——那就只能上快慢指针（[ALG-043](../06-算法与手写/ALG-043-模块依赖管理器用链表串起模块加载链-怀疑某次改动.md)、[ALG-045](../06-算法与手写/ALG-045-请求去重器发现某个请求链成环导致重复请求死循环.md)）。

**范式四：均摊分析要说清"每个元素一生的总账"。** 双栈队列（[ALG-036](../06-算法与手写/ALG-036-消息推送要求先进先出-但底层只有两个后进先出的栈.md)）单次 `pop` 可能搬 n 个元素，看着像 O(n)，但每个元素一生只被搬一次，所以 m 次操作总共 O(m)。同类还有动态数组扩容、单调栈（每个下标入栈出栈各一次）、环形缓冲的覆盖写。面试里说"均摊 O(1)"必须紧跟一句"每个元素最多进出各一次"，否则就只是背了个词。

**范式五：单调结构 = 主动淘汰"不可能成为答案"的候选。** 单调栈/单调队列的核心不是"维护有序"，而是**当新元素进来时，某些旧元素永远不可能再被选中，可以就地丢弃**。求下一个更低价时，比当前价高的历史价格再也不可能是"第一个更低价"（[ALG-038](../06-算法与手写/ALG-038-商品详情页要展示再等几天会降到更低价-每日温度的.md)）；滑动窗口最大值里，比新值小的旧值在窗口内永远压不过新值（[ALG-060](../06-算法与手写/ALG-060-监控大盘的折线图要求每秒展示过去-60-秒内的最.md)）。想清楚这句"为什么可以丢"，复杂度自然就是 O(n)。

## 精讲（6 题）

### 精讲 1 · [ALG-047] LRU 为什么必须用双向链表

**场景**：`<KeepAlive max="10">` 缓存了 12 个页面组件实例，切回某个页面时如果实例已被销毁，滚动位置和表单草稿全丢。要求"命中就算用过，容量满淘汰最久没用的那个"，`get` / `put` 都必须 O(1)。

**问法**："手写一个 LRU，说说为什么节点要用双向链表，单链表行不行？"

**思路**：先把 LRU 需要的能力拆成三件事——按 key 定位（哈希表）、把任意节点从链上摘下来（需要**前驱**）、把节点插到头部。第二件事就是单链表做不到的地方：`get` 命中后我们手里只有这个节点本身，单链表要改它的前驱的 `next`，可是往前找不到人，只能从头再扫一遍，O(1) 立刻破功。双向链表每个节点自带 `prev`，摘除是两行赋值。第三件事是"节点必须同时存 key"——很多人只存 value，淘汰尾结点时手里只有节点对象，Map 里的 key 还指望着它，只能遍历整个 Map 反查，于是又退化成 O(n)。哨兵头尾则是把"链表为空""插到第一个""删最后一个"三类边界统一掉，`head.next` / `tail.prev` 永远合法。

**代码**：

```javascript
class Node {
  constructor(key, val) { this.key = key; this.val = val; this.prev = null; this.next = null; }
}
class LRUCache {
  constructor(cap) {
    this.cap = cap; this.map = new Map();
    // 哨兵头尾：head 侧是"最新"，tail 侧是"最旧"，省掉所有 null 判断
    this.head = new Node(0, 0); this.tail = new Node(0, 0);
    this.head.next = this.tail; this.tail.prev = this.head;
  }
  #remove(node) { node.prev.next = node.next; node.next.prev = node.prev; }
  #addFirst(node) {
    node.next = this.head.next; node.prev = this.head;
    this.head.next.prev = node; this.head.next = node;
  }
  get(key) {
    const node = this.map.get(key);
    if (!node) return -1;
    this.#remove(node); this.#addFirst(node); // 命中即刷新热度
    return node.val;
  }
  put(key, val) {
    const old = this.map.get(key);
    if (old) { old.val = val; this.#remove(old); this.#addFirst(old); return; }
    const node = new Node(key, val);
    this.map.set(key, node); this.#addFirst(node);
    if (this.map.size > this.cap) {
      const lru = this.tail.prev;                  // 尾部前一个 = 最久未使用
      this.#remove(lru); this.map.delete(lru.key); // 必须靠 node.key 反查
    }
  }
}
const c = new LRUCache(2);
c.put(1, 'a'); c.put(2, 'b'); c.get(1); c.put(3, 'c');
console.log(c.get(2), c.get(1), c.get(3)); // -1 a c
```

**边界与追问**：`capacity = 0` 时任何 `put` 都应立即丢弃（`map.size > 0` 成立，走一遍淘汰逻辑也能自洽）；`put` 一个已存在的 key 必须**更新值并刷新热度**，只刷新不更新是常见 bug。面试官常追问："JS 的 Map 本身有序，是不是一行都不用写链表？"——能，见 [ALG-048](../06-算法与手写/ALG-048-KeepAlive-组件缓存在内存中的实例数有上.md)，但你要主动说明这依赖 Map 迭代序 = 插入序的语言规范，而手写双向链表才是通用答案；再追问"多线程/多实例下 LRU 会怎样"，答"读写不是原子的，命中刷新和淘汰之间可能被并发修改，需要加锁或换成分段 LRU"。

### 精讲 2 · [ALG-036] 两个栈倒灌出队列

**场景**：消息推送 SDK 底层只暴露了 `push` / `pop` 两个 LIFO 接口（比如某个宿主环境的原生能力），但业务侧的消费顺序必须是先进先出，否则同一会话的消息会乱序。

**问法**："用两个栈实现队列，并证明你的 `pop` 是均摊 O(1)。"

**思路**：关键在于"倒两次等于不反"。`inbox` 负责收，元素按到达顺序压进去；要出队时把 `inbox` 整体 `pop` 到 `outbox`，顺序被反转一次，此时 `outbox` 的栈顶恰好是最早进来的那个，再 `pop` 就是队头。**最容易写错的地方是倒灌时机**：必须"`outbox` 为空时才搬"，如果每次 `pop` 都搬，遇到"进一个出一个"的交替访问就会每次搬 n 个，退化成 O(n)。均摊证明只需一句话：每个元素一生最多被搬进 `outbox` 一次、被弹出一次，m 次操作总代价 O(m)，摊到每次就是 O(1)。另外 `peek` 不能先 `pop` 再压回去，那样会打乱 `outbox` 的顺序，应该直接看 `outbox` 的栈顶。

**代码**：

```javascript
class StackQueue {
  constructor() { this.inbox = []; this.outbox = []; }
  // 入队：只管往 inbox 压，O(1)
  push(x) { this.inbox.push(x); }
  // 出队前准备：outbox 空了才把 inbox 整体倒过来（顺序恰好反转）
  #shift() {
    if (this.outbox.length === 0) {
      while (this.inbox.length) this.outbox.push(this.inbox.pop());
    }
  }
  pop() {
    this.#shift();
    return this.outbox.length ? this.outbox.pop() : undefined;
  }
  peek() {
    this.#shift();
    return this.outbox[this.outbox.length - 1];
  }
  get size() { return this.inbox.length + this.outbox.length; }
}
const q = new StackQueue();
[1, 2, 3].forEach((v) => q.push(v));
console.log(q.pop(), q.peek(), q.size); // 1 2 2
```

**边界与追问**：空队列 `pop` 返回 `undefined` 而不是抛错，业务侧才能安全地"没有消息就跳过"；`size` 必须是两个栈长度之和，只算一个是最常见的自测失败点。追问"两个栈不够，要求 O(1) 最坏而不是均摊怎么办"——那就得上循环数组或链表，栈这个前提本身限制了最坏情况；追问"为什么不用一个栈加递归"，递归深度就是元素个数，栈溢出风险，而且本质还是借了调用栈这个"第二个栈"。

### 精讲 3 · [ALG-038] 单调栈求"下一个更低价"

**场景**：商品详情页要展示"再等 3 天，预计降到 ¥199"，数据源是每天的最低价快照。需要对每一天算出"之后第一个比它低的价格出现在几天后"。

**问法**："暴力是 O(n²)，怎么做到 O(n)？为什么可以边扫边丢数据？"

**思路**：暴力解对每个 i 往后找，重复比较了大量已经确定不会更低的历史价格。单调栈的核心洞察是：**当新价格 p 进来时，栈里所有比 p 高的历史价格，它们的"第一个更低价"就是今天**——它们一直在等，等到的第一个更低值必然就是当前这个。所以栈里始终维护一段"价格单调递增、且都还没等到答案"的下标序列，只需与栈顶比，比栈顶低就弹栈结算，直到栈空或栈顶更便宜，再压自己进去。每个下标进出栈各一次，共 2n 次操作。这里必须**存下标而不是存价格**，因为答案要的是"几天后"（`i - j`），存值就算不出距离。

**代码**：

```javascript
// 返回每个位置"再等几天降价"，0 表示之后不会再降
function nextLowerDistance(prices) {
  const res = new Array(prices.length).fill(0);
  const stack = []; // 存下标，对应价格单调递增
  for (let i = 0; i < prices.length; i++) {
    while (stack.length && prices[i] < prices[stack[stack.length - 1]]) {
      const j = stack.pop(); // i 就是 j 之后第一个更低的那天
      res[j] = i - j;
    }
    stack.push(i); // 暂时等不到的更贵价格继续留在栈里
  }
  return res;
}
console.log(nextLowerDistance([100, 90, 95, 80])); // [1, 2, 1, 0]

// 变体：求"下一个更大元素的值"，比较符反过来、从右往左扫即可
function nextGreater(nums) {
  const res = new Array(nums.length).fill(-1), stack = [];
  for (let i = nums.length - 1; i >= 0; i--) {
    while (stack.length && stack[stack.length - 1] <= nums[i]) stack.pop();
    if (stack.length) res[i] = stack[stack.length - 1];
    stack.push(nums[i]);
  }
  return res;
}
console.log(nextGreater([2, 1, 5, 3, 6])); // [5, 5, 6, 6, -1]
```

**边界与追问**：判等要用严格小于 `<` 还是小于等于 `<=` 取决于业务口径——"降到更低"用 `<`，"降到不高于"用 `<=`，一字之差会让平价位的结果完全不同，面试时主动指出这点很加分。扫描结束后栈里剩下的下标就是"之后不会再降"的，填 0 即可，前端可以隐藏该提示。常见变体是接雨水（[ALG-064](../06-算法与手写/ALG-064-图表库里有个柱状图蓄水体积的可视化插件-要计算一.md)）和柱状图最大矩形：都是"用单调栈找左右第一个更小/更大的边界"，把这题的骨架记住，变体只是把"结算时算什么"换掉。

### 精讲 4 · [ALG-045] 环入口定位：从"有没有环"到"环在哪"

**场景**：请求去重器按"请求 A 触发了请求 B"的关系串成一条链，线上出现某个页面无限发请求。只知道有环没用，运维要的是**环是从哪个请求开始重复的**，才能定位到出问题的调用点。

**问法**："O(1) 空间判断链表有环，并返回入环的第一个节点。"

**思路**：第一阶段 Floyd 判圈：慢指针 1 步、快指针 2 步，若有环，两者在环内的相对速度是 1，快指针必然在某一圈追上慢指针（不可能"跳过"）。第二阶段是纯数学：设头到入口距离 a，入口到相遇点距离 b，环长 c。相遇时慢指针走了 `a + b`，快指针走了 `a + b + kc`，由 `2(a+b) = a+b+kc` 得 `a = kc - b`。这个式子的含义是：**从相遇点继续走 a 步（绕完剩下的环再走 a），和从头结点走 a 步，会同时落在入口**。所以把一个指针拨回头部、两者同速前进，再次相遇处就是入口。为什么不用哈希表记访问过的节点？能过，但 O(n) 空间，而快慢指针是 O(1)；代价是常数更大、缓存不友好，工程上节点数不大时哈希表反而更直观。

**代码**：

```javascript
function detectCycleEntry(head) {
  let slow = head, fast = head;
  // 阶段一：判圈，快指针每次 2 步，套圈后必与慢指针相遇
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) break;
  }
  if (!fast || !fast.next) return null; // 快指针到达链尾，无环
  // 阶段二：一个指针回起点，两指针同速走，相遇处即环入口
  let p = head;
  while (p !== slow) { p = p.next; slow = slow.next; }
  return p;
}
const a = { v: 1, next: null }, b = { v: 2, next: null };
const c = { v: 3, next: null }, d = { v: 4, next: null };
a.next = b; b.next = c; c.next = d; d.next = b; // 环从 b 开始
console.log(detectCycleEntry(a).v, detectCycleEntry({ v: 9, next: null })); // 2 null
```

**边界与追问**：循环条件必须是 `fast && fast.next`，只判 `fast` 会在偶数长度链表上对 `null.next` 取值；无环时第二阶段前要先 return null，否则 `p` 会一路走到 null 后死循环。高频追问三个：①环长——相遇后让一个指针绕一圈数步数；②为什么慢指针进环后一定没走满一圈就被追上——因为快指针相对速度 1，慢指针走不到 c 步快指针就已经追上；③自环（`node.next = node`）能否处理——能，`slow === fast` 第一次就比较成功，第二阶段 `p` 立刻等于 slow。

### 精讲 5 · [ALG-050] 两数之和：凑单提示的哈希反查

**场景**：购物车差 12 元到满 199 减 30，页面要提示"再加一件 ¥12 的商品即可享受满减"。价格数组是当前可推荐的候选池，要找出所有"两件之和恰好等于目标差额"的组合并高亮。

**问法**："不用双重循环，O(n) 找出来；如果价格有重复怎么办？"

**思路**：双重循环的问题不是慢在常数，而是每个元素都被拿去和"之前所有元素"配一遍，做了大量重复的加法。哈希做法的视角转换是：遍历到当前商品时，**我不再问"你能和谁配"，而是问"能让总和成立的那个搭档价格，我之前见过吗"**——`need = target - price`，一次 `Map.get` 就够。这就是"用空间换掉内层循环"的套路，O(n²) → O(n)。两个细节决定这题能不能过：第一，**必须先查后存**，如果先把当前价格存进 Map 再查，价格为 `target/2` 的商品会和自己配对，返回一件商品出现两次的荒唐结果；第二，价格可能重复（两件 ¥50 凑 100），所以 Map 的 value 不能是单个商品而应是**候选桶**，配对成功就把桶里的一个消费掉（`pop`），这样同一件商品不会被两个组合同时占用。

**代码**：

```javascript
// 返回所有"两件商品价格之和恰好为 target"的组合，同一件商品不能重复用
function findCombos(items, target) {
  const seen = new Map(); // price -> 还没被配对掉的同名商品列表
  const res = [];
  for (const item of items) {
    const need = target - item.price;
    const bucket = seen.get(need);
    if (bucket && bucket.length) {
      res.push([bucket.pop(), item]); // 配对成功，消费掉一个候选
    } else {
      if (!seen.has(item.price)) seen.set(item.price, []);
      seen.get(item.price).push(item); // 先查后存，避免自己配自己
    }
  }
  return res;
}
const items = [
  { id: 'A', price: 30 }, { id: 'B', price: 70 },
  { id: 'C', price: 30 }, { id: 'D', price: 70 },
];
console.log(findCombos(items, 100).map((p) => p.map((x) => x.id))); // [['A','B'],['C','D']]
```

**边界与追问**：价格为 0 时"自己配自己"的检查更微妙（`need = target` 可能匹配到自己），先查后存依然安全；`target <= 0` 直接返回空。如果业务要的是"最接近但不超过"（更贴近真实凑单），哈希就不适用了，因为哈希只能判等不能判序，得改用排序 + 双指针；如果允许三件组合，就退化成三数之和（[ALG-063](../06-算法与手写/ALG-063-凑单升级版从商品价格中找三件组合恰好等于满减金额.md)），复杂度上到 O(n²)，这也是面试官从这题往下挖的常见路径。

### 精讲 6 · [ALG-052] 不用 Map，手写一个拉链法 HashMap

**场景**：面试官想确认你理解 `Map` 的内部结构，也可能是在一个受限宿主环境里（如某些沙箱/小程序旧基础库）不能用 Map，需要自己实现一个轻量字典。

**问法**："实现 set/get/delete，说说冲突怎么处理，为什么桶数取质数。"

**思路**：哈希表 = 桶数组 + 哈希函数 + 冲突策略。哈希函数用 31 进制滚动哈希：`h = h * 31 + charCode`，选 31 是因为它是奇质数、分布均匀，且 `h * 31` 可被编译器优化成 `(h << 5) - h`（Java 的 String.hashCode 同款）。算出哈希后对桶数取模定位桶。冲突用**拉链法**：同桶的键值对挂在一条数组链上，查找时先比哈希落桶、再在链上线性比对原始 key——注意**必须比较原始 key 而不是哈希值**，哈希相等只是必要条件。为什么不选开放寻址（冲突了就往后找空位）？因为删除会留下"墓碑"，不处理会让后续探测链断掉，而前端缓存场景删除很频繁，拉链法删除更干脆。桶数取质数是为了让取模结果对不均匀的哈希更分散，减少聚集。

**代码**：

```javascript
class SimpleHashMap {
  constructor(cap = 97) { // 桶数取质数，减少哈希聚集
    this.cap = cap;
    this.buckets = Array.from({ length: cap }, () => []);
    this.count = 0;
  }
  #hash(key) {
    const s = String(key);
    let h = 0;
    for (let i = 0; i < s.length; i++) h = (h * 31 + s.charCodeAt(i)) >>> 0;
    return h % this.cap;
  }
  set(key, val) {
    const bucket = this.buckets[this.#hash(key)];
    const hit = bucket.find((p) => p[0] === key);
    if (hit) hit[1] = val;                          // 覆盖
    else { bucket.push([key, val]); this.count++; } // 拉链：冲突挂在同一条链上
  }
  get(key, def = undefined) {
    const hit = this.buckets[this.#hash(key)].find((p) => p[0] === key);
    return hit ? hit[1] : def;
  }
  delete(key) {
    const bucket = this.buckets[this.#hash(key)];
    const i = bucket.findIndex((p) => p[0] === key);
    if (i === -1) return false;
    bucket.splice(i, 1); this.count--; return true;
  }
  get size() { return this.count; }
}
const m = new SimpleHashMap(8);
m.set('view', 10); m.set('click', 20); m.set('view', 11);
console.log(m.get('view'), m.get('miss', 0), m.size, m.delete('click'), m.size); // 11 0 2 true 1
```

**边界与追问**：工程版还差三件事，面试时主动说出来就是加分项——①**负载因子与扩容**：`count / cap > 0.75` 时桶数翻倍并 rehash，注意逐个迁移而不是整体重建；②**桶内过长退化**：Java 8 在链长超过 8 时转红黑树，把最坏 O(n) 压到 O(log n)；③**key 类型**：这里用 `String(key)` 只用于算哈希，比较仍用原值，所以 `1` 和 `'1'` 是两个不同的 key（与 Map 语义一致，但与普通对象不同）。追问"哈希被恶意构造怎么办"——答"限制 key 长度 + 桶内转树 + 加随机盐"。
