# 01 列表、表格与文本处理（ALG-001~020 / 121~128 / 541~543）

后台系统里 80% 的"算法题"其实是列表清洗与文本格式化：接口给的是脏数据，UI 要的是分好组、排好序、带千分位、能点开明细的结果。这类需求的共同点是**输入规模不可控、边界比主逻辑多**，所以面试官真正在看的不是你会不会用 `Map`，而是你能不能在动手前把"键是什么、相等怎么定义、空值放哪"这三件事问清楚。**识别特征**：需求里出现「去重 / 分组 / 排序 / 格式化 / 拍平 / 对比」时，先把数据结构想清楚，再选手法；能一趟遍历解决的，不要拆成链式三段。

## 场景范式

**1. 先定唯一的"键"，再谈去重与分组。** 业务说的"重复"几乎从来不是引用相等：同一商品是 id 相等，同一订单是「用户 + 商品 + 批次」相等。键选错，后面所有聚合、对比、排序都会跟着错，而且错得很安静——页面不报错，只是数字不对。所以开口第一句应该是「按什么判重」，而不是「用 Map 还是 Set」。

**2. 一趟遍历能做完的事，不要拆成两趟。** 分组、求和、计数、Top-K 的共同结构是「边扫描边往桶里放」，`reduce` / `Map` 只是这个结构的语法糖。先 `groupBy` 再遍历求和，在 1 万条时是常数差异，在百万条、每秒刷新的报表里就是能不能用的差别；更别说中间数组会把内存峰值抬高一个量级。

**3. 排序的稳定性是需求，不是实现细节。** 表格里价格相同的两行，用户会记得谁在上面；虚拟列表里同权重的项来回跳动，会被当成 bug 提。ES2019 之后 `sort` 规范上稳定，但你自己手写的快排、以及某些老引擎都不保证，所以要么依赖规范并写进注释，要么显式记录原始下标做最后一级比较。

**4. 文本处理的难点在边界，不在主逻辑。** 千分位要问负数和小数位；模板插值要问 `null` / `undefined` / `0` 分别显示什么；字符串压缩要问「压完更长怎么办」；URL 解析要问 `+` 是空格还是加号、重复 key 取首个还是数组。先写一张边界表再写正则，返工率会低一个数量级。

**5. 别把 O(n²) 藏在链式调用里。** `list.filter(x => ids.includes(x.id))`、`list.map(x => all.find(...))` 是最常见的隐形平方：代码读起来很函数式，数据一过万就卡。看到「在另一个集合里找」就要条件反射换成 `Set` / `Map`，把查找降到 O(1)，这是性价比最高的一次优化。

## 精讲（6 题）

### 精讲 1 · [ALG-003] 订单按城市分组并求和

**场景**：报表页拿到 `[{ city, amount }]`，要按城市分组展示每组的订单数和总额，点开还能看明细。

**问法**：数据换成 100 万条，你这个实现还成立吗？如果分组键不是字符串而是对象呢？

**思路**：分组的本质是"用一个键把元素归到同一个桶"，所以键的选择比容器更重要。新手常写 `groupBy` 得到 `{city: [...]}` 再遍历求和，两趟扫描、两次分配数组；其实一趟就能同时维护 `items` 和 `total`。容器优先用 `Map`：普通对象在键叫 `__proto__`、`constructor` 时会污染原型或直接取到函数，而 `Map` 保留插入顺序、支持任意类型键，还不会把数字 `1` 和字符串 `'1'` 混为一谈。什么时候不成立：需要按"城市 × 品类"交叉出报表时，单层 Map 不够，要嵌套分组或先拼复合键；数据超过内存时要改成流式聚合，或者干脆交给服务端，前端只做展示。

**代码**：

```javascript
// 一次遍历同时完成分组与求和：避免"先 groupBy 再 reduce"的两趟开销
function groupAndSum(list, keyFn, valFn) {
  const buckets = new Map(); // Map 而非对象：键可以是对象/数字，且不受原型污染
  for (const item of list) {
    const key = keyFn(item);          // 键由业务决定，这里用 city
    const value = Number(valFn(item)) || 0; // 归一化：字符串金额、null 都要能算
    const bucket = buckets.get(key);
    if (bucket) {
      bucket.items.push(item);
      bucket.total += value;          // 边扫边聚合，不额外存中间数组
    } else {
      buckets.set(key, { items: [item], total: value });
    }
  }
  return buckets;
}

const orders = [
  { city: '北京', amount: 100 },
  { city: '上海', amount: '80' },
  { city: '北京', amount: 200 },
];
for (const [city, { total, items }] of groupAndSum(orders, o => o.city, o => o.amount)) {
  console.log(city, total, items.length); // 北京 300 2 / 上海 80 1
}
```

**边界与追问**：
- `amount` 是 `null`、`undefined`、"1,200" 这类脏数据时，先归一化再聚合，否则 `NaN` 会悄悄污染整组总额。
- 分组结果的顺序是"首次出现顺序"，不等于业务顺序，展示前要按总额或城市名再排一次。
- 追问"如何按每个城市取金额 Top3"：分组后对桶内做局部排序或小顶堆，整体仍接近 O(n)。

### 精讲 2 · [ALG-004] 表格点表头做多列排序

**场景**：商品表格点表头：先按分类升序，分类相同按价格降序，再相同则保持接口返回的原始顺序。

**问法**：为什么不能连着调用两次 `sort`？`undefined` 的价格排在哪？中文分类名怎么排才符合预期？

**思路**：多字段排序就是字典序比较——前一个字段相等才看下一个，所以必须写进**一个**比较器。`sort(byCategory).sort(byPrice)` 是错的：后一次排序会重新排列所有元素，只有当排序稳定且你把次要字段放在前面时才"碰巧"对，这种碰巧不该进生产代码。稳定性上规范已经保证，但显式记录原始下标作为最后一级比较，既兼容老引擎，也兼容以后有人把 `sort` 换成手写快排。空值必须显式处理：`undefined > 5` 和 `undefined < 5` 都是 `false`，比较器会给出前后矛盾的结果，V8 遇到不一致比较器的排序结果是不确定的。

**代码**：

```javascript
// 多字段排序：规则按优先级依次比较，全相等时用原始下标兜底保证稳定
function multiSort(list, rules) {
  return list
    .map((item, index) => ({ item, index })) // 记住原始位置，sort 不稳定时也有序
    .sort((a, b) => {
      for (const { field, order = 1, collator } of rules) {
        const va = a.item[field];
        const vb = b.item[field];
        if (va === vb) continue;   // 当前字段相等，交给下一个字段
        if (va == null) return 1;  // 空值统一沉底，避免 undefined 参与比较
        if (vb == null) return -1;
        const cmp = collator ? collator.compare(va, vb) : (va > vb ? 1 : -1);
        if (cmp !== 0) return cmp * order; // order：1 升序，-1 降序
      }
      return a.index - b.index;   // 所有字段都相等，还原原始顺序（稳定）
    })
    .map(x => x.item);
}

const goods = [
  { category: '图书', price: 30 },
  { category: '数码', price: 90 },
  { category: '图书', price: 50 },
];
console.log(multiSort(goods, [{ field: 'category' }, { field: 'price', order: -1 }]));
```

**边界与追问**：
- 中文/中英混排要用 `Intl.Collator` 实例化一次复用，`localeCompare` 每次调用内部建实例，几万行会明显变慢。
- 追问"10 万行排序会不会卡主线程"：会，量级到十万级应放到 Worker 或让后端排序，前端只做局部重排。
- 追问"排序字段是嵌套路径 `sku.price`"：比较前先取值（可缓存成扁平元组），避免比较器里反复走路径。

### 精讲 3 · [ALG-011] 金额千分位格式化

**场景**：订单金额 `-1234567.8` 要显示成 `-1,234,567.80`，正负号、小数补齐、超大金额都要覆盖。

**问法**：正则一行能不能搞定？`toLocaleString` 有什么坑？金额到底该用 number 还是字符串？

**思路**：千分位拆成三件事：符号、整数位每三位插逗号、小数位按币种补齐。正则 `/\B(?=(\d{3})+(?!\d))/g` 很简洁，但它作用在整个字符串上时会把小数部分也算进去，所以要么先按小数点切开、只对整数段替换，要么干脆逆序扫描——从右往左数，每三位插一个分隔符，逻辑短且一眼能验。真正的坑在数值本身：金额超过 `2^53` 会丢精度，1.005 这类值在二进制浮点下乘 100 会变成 100.49999，四舍五入直接错一分。所以财务场景应当从接口拿字符串、用字符串或 `BigInt` 做运算，格式化函数只负责"排版"，不负责"求值"。另一个高频错误是先 `Math.round(num * 100) / 100` 再格式化，`1.005 * 100` 在二进制里是 100.49999，四舍五入后直接少一分，单笔看不出来，日终对账时就是一笔差异。

**代码**：

```javascript
// 千分位：分离符号 / 整数 / 小数，再对整数部分从右往左每三位插逗号
function formatThousands(input, digits = 2) {
  const num = Number(input);
  if (!Number.isFinite(num)) return String(input ?? ''); // NaN / Infinity 原样返回，别显示 NaN
  const sign = num < 0 ? '-' : '';
  const [intPart, decPart] = Math.abs(num).toFixed(digits).split('.');
  let out = '';
  for (let i = 0; i < intPart.length; i++) {
    // 从右数剩余位数是 3 的倍数，且不是第一位时插分隔符
    if (i > 0 && (intPart.length - i) % 3 === 0) out += ',';
    out += intPart[i];
  }
  const tail = digits > 0 ? '.' + decPart : '';
  return sign + out + tail;
}

console.log(formatThousands(-1234567.8));   // -1,234,567.80
console.log(formatThousands('1234567.891')); // 1,234,567.89
console.log(formatThousands('abc', 0));     // abc
// 生产环境优先：new Intl.NumberFormat('zh-CN', { minimumFractionDigits: 2 }).format(n)
```

**边界与追问**：
- 负零、`NaN`、超长数字字符串都要有明确出口；`toFixed` 对 1.005 这类值会给出 1.00，需要按"分"整数运算。
- 不同币种小数位不同（日元 0 位、人民币 2 位），`digits` 要按币种传，不要写死 2。
- 追问"为什么不用 `toLocaleString`"：它依赖运行环境 ICU 数据，部分老浏览器和小程序环境输出不一致，且不能自定义分隔符。

### 精讲 4 · [ALG-001] 混装列表去重（原始值 + 对象 + NaN）

**场景**：接口返回 `[1, '1', 1, NaN, NaN, { id: 1 }, { id: 1 }]`，要求一次去重，对象按业务 id 判重。

**问法**：为什么 `indexOf` 去不掉重复的 `NaN`？不传 key 时对象按什么判重？

**思路**：判重的前提是"相等"的定义。原始值用 SameValueZero（`Set` 的语义），它能把 `NaN` 当作同一个值——这正是 `indexOf` / `includes` 的分水岭：`indexOf` 用严格相等，永远找不到 `NaN`。对象没有天然相等，只有两种选择：按引用（不传 keyFn）或按业务键签名。按引用只能去掉"同一个对象被 push 两次"，接口重新序列化后内容相同但引用不同的对象去不掉，这是线上最常见的"去重没生效"。把原始值和对象放进两个命名空间，可以避免 `1` 和 `{id: 1}` 互相误杀。什么时候不成立：需要"深度相等"去重时，签名要换成稳定序列化（键排序后的 JSON），单次判断从 O(1) 变成 O(对象大小)，超大数据要先算哈希再比较。

**代码**：

```javascript
// 统一去重：原始值用 SameValueZero（Set 语义），对象按 keyFn 生成的签名
function uniqueBy(list, keyFn) {
  const primitiveSeen = new Set(); // NaN 在 Set 里视为同一个值，天然去重
  const objectSeen = new Set();    // 存业务签名或对象引用
  const result = [];
  for (const item of list) {
    const isObject = item !== null && typeof item === 'object';
    if (!isObject) {
      if (primitiveSeen.has(item)) continue;
      primitiveSeen.add(item);
      result.push(item);
      continue;
    }
    // 不传 keyFn 时退化为按引用去重；传了就按业务键
    const key = keyFn ? keyFn(item) : item;
    if (objectSeen.has(key)) continue;
    objectSeen.add(key);
    result.push(item);
  }
  return result;
}

const raw = [1, '1', 1, NaN, NaN, { id: 1 }, { id: 1 }, { id: 2 }];
console.log(uniqueBy(raw, o => o.id)); // [1, '1', NaN, {id:1}, {id:2}]
```

**边界与追问**：
- keyFn 返回 `undefined` 会让所有对象塌成一条，务必在 keyFn 里做兜底或抛错。
- 去重结果要保证"首次出现"的顺序：`Set` 天然保持插入顺序，若换成普通对象再 `Object.keys`，数字型键会被引擎重排成升序。
- 保留"第一条"还是"最后一条"是业务语义：想保留最新值就倒序遍历或先建 Map 再覆盖。
- 追问"百万条如何更快"：单趟 + Set 已经是 O(n)；若需跨请求去重，可上布隆过滤器做前置判断。

### 精讲 5 · [ALG-015] 上传前检测循环引用

**场景**：把表单数据和关联对象序列化上传，`JSON.stringify` 抛 `Converting circular structure to JSON`，需要提前判定并给出友好提示。

**问法**：用全局 `visited` 集合为什么是错的？`{a: shared, b: shared}` 这种菱形结构算环吗？

**思路**：环的定义是"沿着引用能走回自己的祖先"，所以依据必须是**当前递归栈上的节点**，而不是"见过的所有节点"。用全局 visited 会把菱形结构（同一对象被两个字段引用）误判成环，而它其实是合法且常见的——比如两个订单都引用同一个地址对象。正确做法是维护 `inStack`：进入节点时加入、离开时删除，撞上 `inStack` 才是真环。再加一个 `WeakSet` 记录"已确认无环"的子树，可以把共享子树的重复遍历从指数级压回线性；用 `WeakSet` 而不是 `Set`，是因为它不阻止垃圾回收。只遍历 `Object.keys` 是对齐 `JSON.stringify` 的行为（它忽略 symbol 和非枚举属性），如果业务里 Map/Set/Date 也要参与序列化，就得自己扩展这些分支。

**代码**：

```javascript
// 检测循环引用：用"当前递归栈"上的节点集合，而不是全局 visited
function hasCircular(obj) {
  const inStack = new Set();   // 只装祖先链上的节点，出栈即删
  const safe = new WeakSet();  // 已确认无环的子树，避免重复计算
  const walk = (node) => {
    if (node === null || typeof node !== 'object') return false;
    if (inStack.has(node)) return true;  // 撞到自己的祖先 = 真环
    if (safe.has(node)) return false;    // 之前验过，直接复用结论
    inStack.add(node);
    for (const key of Object.keys(node)) { // 与 JSON.stringify 的可见性对齐
      if (walk(node[key])) return true;
    }
    inStack.delete(node); // 回溯：离开这棵子树
    safe.add(node);
    return false;
  };
  return walk(obj);
}

const a = { name: 'a' };
a.self = a;
console.log(hasCircular(a));                // true
const shared = { city: '北京' };
console.log(hasCircular({ from: shared, to: shared })); // false，菱形不是环
```

**边界与追问**：
- 层级过深（上万层）递归会爆栈，生产实现要换成显式栈 + 手动维护进出标记。
- 检测通过到真正 `stringify` 之间对象可能被改，需要序列化前快照，或直接在一次遍历里完成"检测 + 复制"。
- 追问"如何序列化带环对象"：用 `WeakMap` 给对象编号，环处写 `{"$ref": n}`，反序列化时按编号回填。

### 精讲 6 · [ALG-541] 双指针原地去重

**场景**：虚拟列表的索引数组是有序的百万级 id，内存吃紧，要求原地去重，不额外开数组。

**问法**：为什么不用 `[...new Set(arr)]`？`splice` 版本差在哪？返回值为什么要给新长度？

**思路**：原地去重的骨架是快慢指针：慢指针维护"结果区末尾"，快指针负责扫描。因为数组有序，重复值一定相邻，所以只要 `nums[fast] !== nums[slow]`，就把 fast 的值写到 `slow + 1`，写入次数等于唯一值个数。`splice` 版本是 O(n²)：每删一个元素，后面所有元素都要前移，10 万条就会肉眼可见地卡。返回新长度而不是直接改 `length`，是因为调用方可能还持有这块缓冲区、或者后面还有逻辑要读原始数据；真需要截断时再显式 `arr.length = len`。什么时候不成立：数组无序时"相邻比较"失效，要么先排序（O(n log n)），要么用 Set 记录（O(n) 空间换时间）——这时候就不该硬套双指针。

**代码**：

```javascript
// 有序数组原地去重：slow 指向"已确认结果"的最后一个位置
function removeDuplicates(nums) {
  if (nums.length === 0) return 0;
  let slow = 0;
  for (let fast = 1; fast < nums.length; fast++) {
    if (nums[fast] !== nums[slow]) { // 有序 => 只和新值比较即可
      slow++;
      nums[slow] = nums[fast];       // 写入次数 = 唯一值个数，不搬动整段
    }
  }
  return slow + 1; // 调用方只读前 slow+1 项
}

// 变体：每个值最多保留 k 次（埋点合并连续重复）
function removeDuplicatesK(nums, k) {
  let slow = 0;
  for (const n of nums) {
    // 结果区里倒数第 k 个还是同一个值，说明已经保留够了
    if (slow < k || nums[slow - k] !== n) nums[slow++] = n;
  }
  return slow;
}

const arr = [0, 0, 1, 1, 1, 2, 2, 3];
const len = removeDuplicates(arr);
console.log(len, arr.slice(0, len));            // 4 [0, 1, 2, 3]
console.log(removeDuplicatesK([1, 1, 1, 2, 2, 3], 2)); // 5
```

**边界与追问**：
- 空数组返回 0；调用方忘记按新长度截断，尾部会残留脏数据，接口里要写清楚契约。
- 元素是 `NaN` 时 `!==` 永远为真，有序数组里 NaN 的位置本身也不可靠，需要先用 `Object.is` 语义单独处理。
- 追问"对象数组按 id 去重"：把比较换成 `nums[slow].id !== nums[fast].id`，前提同样是先按 id 排序。
- 若业务要求"保留最后一个"而不是第一个，把快慢指针改成从右往左扫，写法完全对称。
