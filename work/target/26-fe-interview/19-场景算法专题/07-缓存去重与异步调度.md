# 07 缓存、去重与异步调度（ALG-154~170 / 190~196 / 282 / 544~549）

这一组题是业务代码里"最容易写出事故"的地方：一个首页十个组件各拉一次用户信息、发版后用户浏览器里还躺着半年前的表结构、弱网下用户点了三次提交生成三笔订单。它们看起来是十个不同的需求，本质上却只问三件事——**能不能合并（合并同 key 的并发）、能不能丢弃（负缓存、限流、过期数据）、要不要排队（互斥、重试退避、时间片）**。

> **识别特征**：题干里出现「并发 / 重复 / 同时 / 击穿 / 突刺 / 风暴 / 覆盖 / 竞态 / 后台仍在跑」，先别写代码，先判断这是 **合并** 还是 **丢弃** 还是 **排队**。答错方向，代码写得再漂亮也是 0 分：该合并的你做了限流，用户会看到随机失败；该丢弃的你做了合并，会把脏数据缓存一小时。

## 场景范式（五条，背下来就能开口）

**范式一：合并 —— 同 key 的并发只留一个在途请求。**
singleflight 的全部价值在于"把 N 次网络 IO 塌缩成 1 次"，代价是所有调用方共享同一个失败。所以它只适合**幂等读**；如果是写请求（创建订单），必须换成幂等键（ALG-163），因为合并写请求会让"用户点了两下"变成"只创建一单"，看似更好但会掩盖参数不同的两次真实提交。判据：同 key 且 fetcher 无副作用 → 合并；有副作用 → 幂等键。

**范式二：丢弃 —— 明确"这个数据不值得请求"。**
三层缓存穿透防护是这一范式的标准答案：布隆过滤器用 O(k) 的时间把"一定不存在"挡在最前面（无假阴性，只有假阳性）；负缓存把"查过了、没有"这个结论也缓存 60s，让重复的坏 id 在 TTL 内不再回源；单飞把同一瞬间的 N 个 miss 合成一次回源。三层缺一不可——只有布隆会漏掉假阳性，只有负缓存会被海量不同 id 冲爆内存，只有单飞挡不住持续的单发请求。

**范式三：限速 —— 先分清"防突刺"还是"控均值"。**
固定窗口（ALG-194）只记"窗口起点 + 计数"，O(1) 最省，但两个窗口交界能放过 2 倍流量；滑动窗口（ALG-195）记时间戳队列，精确但内存随 QPS 增长；令牌桶（ALG-196）用"余额"代替"计数"，容量决定突发上限、补充速率决定长期均值，天然适配"允许用户连点 10 次但不能一直点"。选型口诀：**只要均值 → 固定窗口；不许突刺 → 滑动窗口；既要突发又要均值 → 令牌桶**。多维度（用户 + 接口 + 全局）就在令牌桶外面套一层"逐层 acquire、失败回滚"（ALG-548）。

**范式四：排队 —— 用 Promise 链代替锁，用退避代替立刻重试。**
浏览器没有真正的锁，但 `chain = chain.then(fn).catch(() => {})` 就能得到一条串行队列（ALG-170），临界区里的"读 → 改 → 写"变成原子段。重试同理：立刻重试等于把故障放大 N 倍，正确做法是 `min(cap, base × 2^i)` 做上界、`Math.random() × 上界` 做 full jitter 打散，并且只对 429/5xx 重试。抖动不是锦上添花——没有抖动，所有客户端会在同一毫秒醒来，制造第二个风暴。

**范式五：让出 —— 事件循环是唯一能"暂停 JS"的机制。**
微任务在当前宏任务结束后、渲染前被清空，所以 `await Promise.resolve()` 之间的两次 DOM 修改只会渲染一次；要让用户看见中间态，必须让出到宏任务（`setTimeout`/`rAF`/`rIC`）。同理，3 秒的循环必须每 8ms 检查一次 `performance.now()` 并主动让出，否则超过 50ms 就是长任务，INP 直接劣化。这也是"竞态"的根源：请求返回顺序不等于发起顺序，必须用 seq 或 abort 建立"谁是最新"的唯一权威。

## 精讲（6 题）

### 精讲 1 · [ALG-158] 并发请求同一接口的去重合并

**场景**：首页由十个独立组件拼成，用户信息、配置、购物车角标各自由组件自己拉。首屏一挂载，`/api/user/info` 在同一帧内被打了 10 次，QPS 随组件数线性膨胀。

**问法**："十个组件同时请求同一个接口，怎么保证只发一次？如果请求失败了，这十个组件该怎么办？"

**思路**：核心数据结构是 `Map<key, Promise>`。第一个调用者创建 Promise 并存入 Map，后续同 key 的调用者直接拿到这个 Promise —— 它们 await 的是同一个网络请求，因此天然共享结果、也天然共享异常。关键在 `finally` 里删除：不删，这个 key 就永远返回旧结果，缓存永远不会更新；只在成功时删，失败一次就会让该 key 永久卡在 rejected 状态。用 `Promise.resolve().then(fetcher)` 而不是直接 `fetcher()`，是为了把同步抛出的异常也转成 rejection，避免 Map 里留下一个"已同步炸掉但没被删"的僵尸条目。

```javascript
// 并发同 key 只发一次真实请求，其余复用同一个 Promise
function createSingleflight() {
  const inflight = new Map();                          // key -> 进行中的 Promise
  return function load(key, fetcher) {
    if (inflight.has(key)) return inflight.get(key);   // ① 命中在途请求，直接复用
    const p = Promise.resolve()
      .then(fetcher)                                   // ② 包一层：同步异常也变 rejection
      .finally(() => inflight.delete(key));            // ③ 成功/失败都摘除，放行下次
    inflight.set(key, p);
    return p;
  };
}

// 演示：10 个组件并发请求 /api/user/info
let realCalls = 0;                                     // 统计真实网络请求次数
const fetchUser = () => new Promise(resolve => {
  realCalls++;
  setTimeout(() => resolve({ id: 1, name: 'ada' }), 50);
});
const load = createSingleflight();
Promise.all(Array.from({ length: 10 }, () => load('/api/user/info', fetchUser)))
  .then(list => console.log('真实请求次数 =', realCalls, '结果条数 =', list.length));
// 输出：真实请求次数 = 1 结果条数 = 10
```

**边界与追问**：① key 必须包含全部影响结果的参数（`/api/list?page=1&size=20` 而不是 `/api/list`），否则不同参数会被错误合并；② 失败共享——若业务希望失败后各组件独立重试，需要在 catch 里转成各自的重试策略，或者只合并"成功"路径；③ 它只合并"同一时刻"，请求完成后立刻摘除，所以它**不是缓存**，要缓存请叠加 SWR（ALG-159）；④ 写完再问一句"如果 fetcher 是 POST 呢"——这就是 ALG-163 幂等键的入口。

### 精讲 2 · [ALG-157] 重试风暴：指数退避 + 抖动

**场景**：大促触发限流，前端 SDK 收到一堆 429 后立刻重试，恢复瞬间几十万客户端同时打回来，服务再次被打挂，形成"雪崩—重试—再雪崩"。

**问法**："重试为什么反而把服务打挂了？指数退避里的抖动解决的是什么问题？"

**思路**：立刻重试等于把一次失败放大成 N 次并发，且所有客户端的重试时间点高度相关（都在收到 429 后的同一毫秒），这叫惊群。指数退避把第 i 次重试推到 `base × 2^i` 之后，让压力随重试轮次指数衰减；但如果所有客户端都用同一个公式，它们仍然会**同时**醒来，所以必须加 jitter：full jitter 取 `random(0, exp)`，把唤醒时间摊平到整个区间，任意小时间窗内的到达量都被抹平。另外两条纪律：只重试可恢复错误（429/502/503/504），4xx 参数错误重试一万次也不会成功；重试必须配次数上限和总时长上限，否则弱网下会无限挂着。

```javascript
const sleep = ms => new Promise(r => setTimeout(r, ms));
const isRetryable = e => e && (e.status === 429 || (e.status >= 500 && e.status < 600));

async function retryWithBackoff(fn, { retries = 4, base = 200, cap = 5000 } = {}) {
  let lastErr;
  for (let i = 0; i <= retries; i++) {
    try {
      return await fn(i);                      // 把尝试次数传给 fn，便于打点
    } catch (e) {
      lastErr = e;
      if (i === retries || !isRetryable(e)) break;   // 不可重试/次数用尽：直接抛
      const exp = Math.min(cap, base * 2 ** i);      // 指数上界 + 封顶
      await sleep(Math.random() * exp);              // full jitter：打散唤醒时刻
    }
  }
  throw lastErr;
}

// 演示：前两次 503，第三次成功
let attempt = 0;
retryWithBackoff(async () => {
  attempt++;
  if (attempt < 3) { const e = new Error('503'); e.status = 503; throw e; }
  return `第 ${attempt} 次成功`;
}).then(v => console.log(v));                       // 第 3 次成功
```

**边界与追问**：① 抖动有三种变体——full（`random(0, exp)`）、equal（`exp/2 + random(0, exp/2)`）、decorrelated（基于上次延迟），面试答 full 即可，但要知道它会让平均等待变短；② 重试必须与幂等键绑定，否则超时重试会创建两笔订单（ALG-163）；③ 浏览器对同一域名的并发连接有限（HTTP/1.1 约 6 个），重试队列应当自己控并发，别指望网络层；④ 追问"指数退避会不会让用户等太久"——医疗/支付场景应改为快速失败 + 用户手动重试，而不是默默等 30 秒。

### 精讲 3 · [ALG-195] 固定窗口的边界突刺与滑动窗口

**场景**：埋点 SDK 限制"每秒最多 10 条"。上线后发现两个窗口交界处会瞬间放出 20 条，服务端按 10/s 做的保护被绕过。

**问法**："固定窗口限流有什么缺陷？滑动窗口怎么消除它？代价是什么？"

**思路**：固定窗口只维护 `windowStart + count`，判断"是否跨窗口"就重置。问题在于窗口是**人为切分**的，它不关心"最近 1 秒"，只关心"本窗口内"。于是在 990ms 打满 10 条、1010ms 又打满 10 条，最近 1 秒内实际通过了 20 条 —— 突刺上限是阈值的 2 倍。滑动窗口改成记录每次放行的时间戳：每次请求先把 `<= now - windowMs` 的记录移出队首（因为时间戳天然有序，用 `shift` 即可），再看队列长度是否到上限。它衡量的是真正的"最近 1 秒"，所以不存在突刺。代价是每个被放行的请求都留一条记录，内存与判定成本都是 O(窗口内请求数)；高 QPS 场景用分桶近似（把 1 秒切成 10 个 100ms 的格子只存计数）来换内存。

```javascript
function fixedWindow(max, windowMs) {
  let start = 0, count = 0;
  return (now) => {
    if (now - start >= windowMs) { start = now; count = 0; }   // 跨窗口整体重置
    if (count >= max) return false;
    count++;
    return true;
  };
}

function slidingWindow(max, windowMs) {
  const hits = [];                                   // 窗口内每次放行的时间戳
  return (now) => {
    while (hits.length && hits[0] <= now - windowMs) hits.shift();  // 移出过期记录
    if (hits.length >= max) return false;
    hits.push(now);
    return true;
  };
}

// 边界突刺：上限 5/秒，在 990ms 打满，1010ms 再打满（同一"真实秒"内）
const burst = [990, 991, 992, 993, 994, 1010, 1011, 1012, 1013, 1014];
const fw = fixedWindow(5, 1000), sw = slidingWindow(5, 1000);
console.log('fixed 放行', burst.filter(t => fw(t)).length);      // 10 → 两倍突刺
console.log('sliding 放行', burst.filter(t => sw(t)).length);    // 5  → 正确
```

**边界与追问**：① 用 `shift()` 是 O(n) 出队，量大时改用数组 + 头指针（或环形缓冲），避免每帧搬移；② 分布式场景下时间戳队列无法共享，服务端要用 Redis ZSET 或分桶计数；③ 询问"滑动窗口就一定好吗"——它对内存不友好且无法表达"允许突发"，需要突发能力时选令牌桶（ALG-196）；④ 前端限流天生可被绕过（刷新页面即重置），它只是"保护自己别把后端打挂"的礼貌，不是安全边界。

### 精讲 4 · [ALG-164] 事件循环：微任务、宏任务与渲染顺序

**场景**：一面必考题。代码里同步日志、`setTimeout`、`Promise.then`、`queueMicrotask`、`async/await` 交错，要求写出输出顺序。

**问法**："说出输出顺序，并解释为什么 `await` 之后的代码排在 `queueMicrotask` 后面。"

**思路**：三条规则就够：① 同步代码先跑完（async 函数在第一个 await 之前也是同步执行的）；② 当前宏任务结束后，**清空整个微任务队列**（FIFO），期间新产生的微任务追加到队尾、同一轮继续清空；③ 微任务清空后才渲染，然后取下一个宏任务。`await x` 等价于 `Promise.resolve(x).then(后续)`，所以 await 之后的代码是一个微任务，它排在当前已入队的微任务之后。本题还有一个陷阱：`then` 链的第二个 then 属于"下一个微任务"，因为第一个 then 的返回值要等它执行时才产生，所以它会排到本轮微任务队列的末尾。

```javascript
console.log('1');                                    // 同步
setTimeout(() => console.log('2'));                  // 宏任务，最后
Promise.resolve()
  .then(() => console.log('3'))                      // 微任务 A
  .then(() => console.log('8'));                     // 微任务 A'（A 完成后才入队，排到队尾）
queueMicrotask(() => console.log('4'));              // 微任务 B
(async () => {
  console.log('5');                                  // await 之前：同步执行
  await null;                                        // 后续代码进微任务队列
  console.log('6');                                  // 微任务 C
})();
console.log('7');                                    // 同步
// 输出：1 5 7 3 4 6 8 2
// 同步(1,5,7) → 微任务(3,4,6) → then 链第二个(8) → 宏任务(2)
```

**边界与追问**：① `await null` 与 `await Promise.resolve()` 都是"让出一个微任务"，但 `await` 一个已 resolve 的 thenable 可能多一层 tick，面试常在这里埋坑；② 微任务里再产生微任务会**延长当前轮**，极端情况（无限 `Promise.resolve().then`）会饿死渲染，页面直接卡死；③ 追问"用户什么时候能看到 DOM 改动"——同一轮微任务里的多次修改只会渲染一次，要有中间态必须让出到宏任务（ALG-168）；④ Node 与浏览器的差异：Node 有 `process.nextTick`（优先级高于 Promise）和 `setImmediate`，浏览器没有。

### 精讲 5 · [ALG-166] 竞态：AbortController 与版本号

**场景**：搜索联想输入 "a" 发出请求 A（慢，800ms），继续输入 "ab" 发出请求 B（快，100ms）。B 先返回渲染了正确结果，A 后返回把列表覆盖成 "a" 的旧结果。

**问法**："为什么会覆盖？AbortController 和版本号分别解决什么问题，能只用一个吗？"

**思路**：根因是"响应到达顺序 ≠ 请求发起顺序"，而代码默认"谁最后回来谁是最新"。两种守卫：**AbortController** 是物理取消——发新请求前 `abort()` 旧的，fetch 以 `AbortError` reject，省掉带宽与服务端压力；**版本号**是逻辑丢弃——每次请求自增 seq，回来时比对 `mySeq !== currentSeq` 就丢弃。前者依赖底层支持取消（fetch/XHR 可以，某些 JSONP、第三方 SDK 不行），后者与传输无关但旧请求仍然占着连接。生产上两者叠加：先 abort 省资源，再用 seq 兜住"abort 与 resolve 竞态"的极小窗口。

```javascript
function createSearch(fetcher) {
  let controller = null;
  let seq = 0;                                        // 当前最新请求的版本号
  return async function search(keyword) {
    controller?.abort();                              // ① 物理取消上一个请求
    controller = new AbortController();
    const mySeq = ++seq;                              // ② 逻辑版本：本次是第几发
    try {
      const data = await fetcher(keyword, controller.signal);
      return mySeq === seq ? data : null;             // ③ 已被更新请求取代：丢弃结果
    } catch (e) {
      if (e.name === 'AbortError') return null;        // 主动取消是预期行为
      throw e;
    }
  };
}

// 演示：先发慢请求 a，再发快请求 ab
const fakeFetch = (kw, signal) => new Promise((resolve, reject) => {
  const timer = setTimeout(() => resolve(kw), kw === 'a' ? 60 : 10);
  signal.addEventListener('abort', () => {
    clearTimeout(timer);
    const e = new Error('aborted'); e.name = 'AbortError'; reject(e);
  });
});
const search = createSearch(fakeFetch);
search('a').then(v => console.log('a 的结果', v));      // null（已被取消）
setTimeout(() => search('ab').then(v => console.log('ab 的结果', v)), 5); // "ab"
```

**边界与追问**：① 不要用 `finally` 里的 return 做丢弃——它会吞掉正常返回值，语义上是反模式，判断要写在 try 的分支里；② abort 后必须 catch `AbortError`，否则控制台一片红；③ 同一个 controller 不能复用给多个请求，每次都要 new；④ 追问"防抖能不能解决"——防抖只减少请求数，用户停止输入后仍可能有两次在途请求，竞态守卫仍然必要。

### 精讲 6 · [ALG-282] 缓存穿透的三层防护

**场景**：商品详情页的 id 来自 URL，爬虫或恶意脚本用随机 id 疯狂请求，缓存永远不命中，每个请求都打到数据库。

**问法**："什么是缓存穿透？负缓存、布隆过滤器、单飞各自解决哪一段？为什么三层都要？"

**思路**：穿透的本质是"查询的 key 在数据源里根本不存在，所以永远无法被缓存"。负缓存解决"同一个坏 key 重复打"——把 `null` 也写进缓存，TTL 短（60s），防止脏数据长期占位；布隆过滤器解决"大量不同的坏 key"——O(k) 判断"一定不存在"直接返回，代价是有假阳性（可能把存在的 key 判成存在，但绝不会把存在判成不存在），假阳性只会让请求落到下一层，不会丢数据；单飞解决"同一瞬间的 N 个 miss"——把并发回源合并成一次。三层是正交的：布隆挡海量随机 key，负缓存挡重复 key，单飞挡并发尖峰。

```javascript
function createGuardedCache(loader, { ttl = 5000, negativeTtl = 60000, bloom = null } = {}) {
  const l1 = new Map();                              // key -> { value, at, ttl }
  const inflight = new Map();                        // key -> 进行中的 Promise
  return async function get(key) {
    if (bloom && !bloom.has(key)) return null;       // ① 布隆：确定不存在，直接返回
    const hit = l1.get(key);
    if (hit && Date.now() - hit.at < hit.ttl) return hit.value;   // ② 命中（含负缓存）
    if (inflight.has(key)) return inflight.get(key);             // ③ 单飞：合并回源
    const p = loader(key)
      .then(v => {
        const miss = v === null || v === undefined;
        // 负缓存：查过了确实没有，也记一笔，TTL 更短
        l1.set(key, { value: miss ? null : v, at: Date.now(), ttl: miss ? negativeTtl : ttl });
        return miss ? null : v;
      })
      .finally(() => inflight.delete(key));
    inflight.set(key, p);
    return p;
  };
}

let dbCalls = 0;
const bloom = { has: k => k !== 'ghost' };           // 演示用：ghost 一定不存在
const getProduct = createGuardedCache(
  async id => { dbCalls++; return id === '404' ? null : { id }; },
  { bloom }
);
(async () => {
  await Promise.all([getProduct('404'), getProduct('404'), getProduct('ghost')]);
  await getProduct('404');                           // 负缓存命中，不再回源
  console.log('回源次数 =', dbCalls);                 // 1（三个 404 合并 + ghost 被布隆挡）
})();
```

**边界与追问**：① 负缓存 TTL 不能太长，否则"刚创建的数据"会被判为不存在，通常 30~60s；② 布隆不支持删除，数据删除后位数组仍有 1，只能靠 TTL 重建或改用计数布隆（ALG-549）；③ 布隆的假阳性率由 `m/n` 与 k 决定，`m = -n·ln p /(ln2)²`，面试可以现场算；④ 追问"本地缓存要不要做 LRU"——要，否则负缓存本身会变成内存泄漏（ALG-544）。
