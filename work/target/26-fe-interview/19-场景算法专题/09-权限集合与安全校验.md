# 09 权限、集合与安全校验（ALG-007 / 104 / 142 / 171~176 / 197 / 209 / 227 / 236）

> 权限与安全是前端面试里"看起来不难、答起来全是坑"的一类题：需求方说"判断一下有没有权限""做个水印防删""接口别被刷"，你要在十分钟里同时交代清楚**数据结构、边界、以及这套方案到底防得住谁**。这类题的分水岭不在代码长度，而在你有没有先问一句：**攻击者能做什么？** 是普通用户手滑，是会开 DevTools 的前端，还是能跑脚本、能改请求、能掐着毫秒计时的黑产？威胁模型不同，方案完全不同——防手滑用 CSS，防改包用签名，防时序爆破必须常数时间比较，而"前端加密"从来只是提高成本，不是安全边界。

## 一、场景 → 算法 映射

| 你会听到的需求 | 背后的算法 | 复杂度 | 原卡 |
|---|---|---|---|
| "改版了，对比新旧权限集合，输出新增/回收/保留" | Set 构建 + 单次遍历求交并差 | O(n+m) | ALG-007 / ALG-209 |
| "用户有没有这个权限点"（权限点 ≤ 31 个） | 整数位掩码 + 按位与 | O(1) | ALG-104 |
| "统计用户有几项权限 / 判断某权限码是不是 2 的幂" | Brian Kernighan 消最低位 1 | O(k)，k 为 1 的个数 | ALG-104 |
| "128 个权限点要塞进 JWT，还要能快速判交并" | 位图 BitSet（16 字节 / base64） | O(1) 判断，O(n/8) 集合运算 | ALG-236 |
| "勾选父部门自动勾选所有子部门，子部门勾一半父级显示半选" | 树上双向传播 + 三态派生 | O(n) | ALG-197 |
| "用户输入 `<b>`、`<a>` 要能渲染，但不能被注入脚本" | 白名单 DOM 遍历（简化 DOMPurify） | O(节点数) | ALG-171 |
| "页面水印被删 DOM / 调透明度" | MutationObserver 监听 + 重建 + 上报 | O(变更数) | ALG-172 |
| "抽奖接口被脚本高频调用薅羊毛" | HMAC 签名 + 时间窗 + nonce | O(1) / 请求 | ALG-173 |
| "本地 mock 数据、调试标记不想被一眼看懂" | Base64 + 循环 XOR 混淆 | O(n) | ALG-174 |
| "生成强随机密码，不能用 Math.random" | CSPRNG + 拒绝采样消除模偏差 | O(n) | ALG-175 |
| "签名比对用了 `===`，审计说有时序攻击面" | 常数时间比较（XOR 累积） | O(n)，与内容无关 | ALG-176 |
| "商品标签要过滤 2 万敏感词，还要限制字符集" | Trie/AC 扫描 + 正则字符集白名单 | O(文本长) | ALG-227 |
| "`api/*/read` 匹配单段，`api/**` 匹配任意层" | 按 `/` 拆段 + 递归 + memo | O(段数²) | ALG-142 |

这张表要能反向使用：面试官说"我们有 128 个权限点，前端每次渲染菜单都要判几百次"，你脑子里第一反应应该是 ALG-236 的位图，而不是 `Set.has`——不是因为 Set 慢，而是因为**这份权限要跟着请求走**，序列化体积才是真瓶颈。

## 二、场景范式（这类题的通用套路）

**范式 1：先定威胁模型，再选技术。** "水印防删"里，删 DOM 的人一定是能开控制台的内部员工，MutationObserver 只能提高门槛；"接口防刷"里，攻击者能完整复刻你的前端逻辑，所以签名密钥必然泄露，真正的频控必须在服务端。答题时主动说出"这套方案防的是 X，防不住 Y"，比多写 20 行代码更能拿分。

**范式 2：白名单永远优于黑名单。** XSS 过滤、标签字符集、href 协议、路径权限，全部用"允许什么"而不是"禁止什么"。黑名单的失败模式是**漏一个就全线失守**（`<svg onload>`、`onerror` 大小写、HTML 实体编码、mXSS 重解析），白名单的失败模式只是"少支持一个标签"，用户能忍，安全不能赌。

**范式 3：唯一数据源 + 派生 UI 态。** 权限树的 checked / indeterminate、水印的可见性、位图的权限集合，都应该只有一份真值，其余全部由它派生。ALG-197 里把半选态存进节点，就必然出现"父节点说全选、子节点其实没选"的脏数据；正确的做法是选中集合是唯一真值，`indeterminate` 每次渲染算出来。

**范式 4：复杂度要从"操作次数"反推。** 集合运算 20 万次 × O(n·m) 会卡死页面，O(n+m) 不会；权限判断每次渲染几百次，必须是 O(1) 而不是"遍历数组找一下"。面试里能主动报出"这个方案单次 O(log n)、总量 O(q log n)"，说明你真的想过数据规模，而不是背了个模板。

**范式 5：安全代码要"可审计"。** 三个细节最能体现工程素养：密钥/签名比较走常数时间、`target="_blank"` 必须补 `rel="noopener noreferrer"`、随机数必须来自 `crypto` 而不是 `Math.random`。这三条几乎是安全岗面试的固定考点，写业务代码时顺手加上，面试时就能当例子讲。

## 三、精讲（6 题）

### 精讲 1 · [ALG-104] 位运算表达权限位

**场景**：SaaS 后台有十几个权限点（读、写、删、导出、审批……），用户态是一个整数，跟着登录态存进 localStorage 或 JWT。路由守卫、按钮显隐、接口入参全都要判权限，一次页面渲染可能判上百次。

**问法**：如何判断"有没有某权限"？如何授权、回收、取反？如何统计用户拥有几项权限？如何判断某个权限码本身是不是单一权限（2 的幂）？

**思路**：为什么用整数而不是对象/数组？三个原因。一是**体积**：`{read:true, write:false, ...}` 序列化后几百字节，一个整数 8 字节；二是**比较成本**：判权限是一次按位与，没有哈希、没有字符串比较、没有内存跳转，CPU 一条指令；三是**组合表达**：`READ|WRITE` 天然表示"至少拥有其中之一或全部"，传参时不用数组。判断必须写 `(perm & mask) === mask` 而不是 `!== 0`——后者在组合掩码下会把"只有 READ"的用户误判成"拥有 READ+WRITE"，这是最常见的 bug。统计 1 的个数用 Brian Kernighan：`n &= n - 1` 每次消掉最低位的 1，循环次数等于 1 的个数，而"逐位右移"固定要跑 32 次。

**代码**：

```javascript
const PERM = { READ: 1 << 0, WRITE: 1 << 1, DELETE: 1 << 2, ADMIN: 1 << 3 };

// 判权限：必须用 === mask，否则组合掩码会误判
const has = (perm, mask) => (perm & mask) === mask;
// 判"拥有其中任意一个"
const hasAny = (perm, mask) => (perm & mask) !== 0;

const grant = (perm, mask) => perm | mask;        // 授权
const revoke = (perm, mask) => perm & ~mask;      // 回收
const toggle = (perm, mask) => perm ^ mask;       // 切换

// Brian Kernighan：只循环 1 的个数次
function countBits(n) {
  let count = 0;
  while (n) { n &= n - 1; count++; }
  return count;
}

// 单一权限（2 的幂）判定：n & (n-1) 必须为 0，且 n > 0
const isSinglePerm = n => n > 0 && (n & (n - 1)) === 0;

// 反解成权限名列表，便于渲染
const toList = perm => Object.keys(PERM).filter(k => has(perm, PERM[k]));

const user = grant(grant(0, PERM.READ), PERM.WRITE);   // 0b011
console.log(has(user, PERM.READ | PERM.WRITE));        // true
console.log(has(user, PERM.READ | PERM.ADMIN));        // false（缺 ADMIN）
console.log(countBits(user), isSinglePerm(PERM.ADMIN)); // 2 true
```

**边界与追问**：① JS 位运算会截断到 32 位有符号整数，**超过 31 个权限点必须换 BitSet 或 BigInt**，`1 << 31` 是负数；② `perm & ~mask` 结果可能是负数，但位模式仍然正确，判空用 `=== 0` 而不是 `< 0`；③ 持久化时用 `perm >>> 0` 转无符号，否则后端读到 `-2147483648` 会以为你传了个脏数据；④ 追问"权限点会超过 31 个怎么办"——正好接 ALG-236 的位图；⑤ 追问"权限能不能继承"——继承是树的问题，见 ALG-197。

### 精讲 2 · [ALG-236] 权限点的位图存储与快速判断

**场景**：中台有 128 个细粒度权限点，用户登录后权限要随每个请求带上（放在 JWT 或自定义 Header 里），服务端和前端都要能判"有没有某点"，还要能算"两个角色的权限交集"。

**问法**：128 个布尔值怎么存最省？判断单点、求交集/并集、统计数量、序列化传输分别怎么做？

**思路**：直接存数组要 128 个元素、JSON 约 1~3KB，塞进 JWT Header 会超限；存 Set 更糟，序列化是字符串数组。位图把 128 位压成 **16 字节**，base64 后 24 个字符，且集合运算就是按字节的 AND/OR，16 次循环搞定。为什么按字节而不是按 32 位整数做？因为 JS 位运算只有 32 位，128 位需要 4 个 32 位段，而 `Uint8Array` 更省内存、序列化更直接（`Buffer`/`btoa` 都按字节走）。位下标换算：`bytes[bit >> 3] & (1 << (bit & 7))`，`>> 3` 等价除以 8，`& 7` 等价取模 8。

**代码**：

```javascript
class PermBitmap {
  constructor(bits = 128, bytes = null) {
    this.size = bits;
    this.bytes = bytes ? Uint8Array.from(bytes) : new Uint8Array(bits >> 3); // 128 位 = 16 字节
  }
  has(bit) { return (this.bytes[bit >> 3] & (1 << (bit & 7))) !== 0; }
  add(bit) { this.bytes[bit >> 3] |= 1 << (bit & 7); return this; }
  remove(bit) { this.bytes[bit >> 3] &= ~(1 << (bit & 7)); return this; }

  and(other) {                       // 交集：两个角色的公共权限
    const out = new PermBitmap(this.size);
    for (let i = 0; i < this.bytes.length; i++) out.bytes[i] = this.bytes[i] & other.bytes[i];
    return out;
  }
  or(other) {                        // 并集：角色叠加
    const out = new PermBitmap(this.size);
    for (let i = 0; i < this.bytes.length; i++) out.bytes[i] = this.bytes[i] | other.bytes[i];
    return out;
  }
  count() {                          // 统计拥有的权限点数量
    let n = 0;
    for (const b of this.bytes) { let x = b; while (x) { x &= x - 1; n++; } }
    return n;
  }
  toString() { return Buffer.from(this.bytes).toString('base64'); }
  static fromString(s, bits = 128) { return new PermBitmap(bits, Buffer.from(s, 'base64')); }
}

const admin = new PermBitmap().add(0).add(1).add(7);
const guest = new PermBitmap().add(0);
console.log(admin.has(7), guest.and(admin).count(), admin.or(guest).toString());
```

**边界与追问**：① **位序必须和后端写进契约**（bit 0 是最低位还是最高位、跨字节怎么排），否则前后端各算各的，权限全错且难查；② `Uint8Array.from(bytes)` 是拷贝，不要直接复用外部数组，否则集合运算会污染原对象；③ base64 编码要分块（`String.fromCharCode.apply` 一次性传 16 字节没问题，但上千字节会爆栈）；④ 追问"128 位不够用呢"——扩到 256 位只是多 16 字节，或改用 BigInt（但 BigInt 不能直接位运算混合 Number）；⑤ 追问"怎么在 SQL 里查"——`WHERE (perm & 8) = 8`，位图在存储层同样成立，这是它比字符串数组强的地方。

### 精讲 3 · [ALG-142] 通配符路径权限匹配

**场景**：网关/前端路由的权限配置写成 `api/*/read`、`api/**`、`admin/user/*`，`*` 只匹配一段，`**` 匹配任意多层（含 0 层）。用户请求进来要判"这条路径是否被授权"。

**问法**：如何实现 `*` 与 `**` 的匹配？为什么不能直接用正则？复杂度多少？

**思路**：按 `/` 拆成段数组后，问题退化成"两个序列的匹配"，递归定义很干净：`*` 只能吃一段且必须还有段，`**` 可以吃 0 到剩余全部段。**必须加记忆化**——连续两个 `**` 时分支会指数膨胀（`**/**/**/...`），`memo[(i,j)]` 把状态压到 O(n·m)。为什么不用正则？语义不一样：正则 `.*` 会跨 `/`，得手写 `[^/]+` 和 `(?:[^/]+/)*`，动态拼接还要转义用户输入的 `.` `+` `(`；更关键的是递归版能顺手返回"匹配到了哪些段"，便于做参数提取和审计日志。也可以编译成正则**缓存**复用（每个 pattern 只编译一次），这是生产里更常见的做法，但面试要先讲清分段递归的原理。

**代码**：

```javascript
function pathMatch(pattern, path) {
  const ps = pattern.split('/').filter(Boolean);
  const xs = path.split('/').filter(Boolean);
  const memo = new Map();

  function match(i, j) {
    if (i === ps.length) return j === xs.length;        // 模式用完，路径也必须用完
    const key = i * (xs.length + 1) + j;
    if (memo.has(key)) return memo.get(key);

    let ok;
    if (ps[i] === '**') {
      ok = false;
      for (let k = j; k <= xs.length; k++) {            // ** 吞 0 段到全部剩余段
        if (match(i + 1, k)) { ok = true; break; }
      }
    } else if (j === xs.length) {
      ok = false;                                       // 模式还有段但路径没了
    } else if (ps[i] === '*' || ps[i] === xs[j]) {
      ok = match(i + 1, j + 1);                         // * 只吃一段
    } else {
      ok = false;
    }
    memo.set(key, ok);
    return ok;
  }
  return match(0, 0);
}

console.log(pathMatch('api/*/read', 'api/user/read'));      // true
console.log(pathMatch('api/*/read', 'api/a/b/read'));       // false（* 不跨段）
console.log(pathMatch('api/**', 'api/a/b/c'));              // true
console.log(pathMatch('**/read', 'read'));                  // true（** 可吞 0 段）
```

**边界与追问**：① 空段处理——`/api//read` 要不要合并连续斜杠，取决于网关规范，必须显式约定；② 大小写与前缀匹配：REST 路径通常大小写敏感，但静态资源可能不敏感，别默认 `toLowerCase()`；③ 安全默认值：`**` 放行等于全开，配置校验时要禁止"只有 `**`"的规则；④ 追问"段内通配 `read*` 怎么办"——段级再做一次 glob（`*` 在段内表示任意字符），此时才该上正则；⑤ 追问复杂度——状态 O(n·m)，每个 `**` 状态枚举 O(m)，最坏 O(n·m²)，实际路径段数 < 10，可忽略；要严格 O(n+m) 可用双指针回溯（Wildcard Matching 的经典写法）。

### 精讲 4 · [ALG-171] 富文本 XSS 白名单净化

**场景**：评论区允许用户发少量富文本（加粗、链接、列表），提交后直接 `innerHTML` 渲染。产品要"好看"，安全要"别被注入"，于是需要一份简化版 DOMPurify。

**问法**：白名单过滤怎么写？为什么不能用黑名单/正则替换 `<script>`？`href` 要怎么额外处理？

**思路**：核心是**用浏览器的解析器解析，而不是用字符串规则去猜**。HTML 不是正则语言：属性引号可省、标签可自闭合、实体可编码、浏览器还会做容错重解析（mXSS 就是利用"净化后再次解析结构变了"）。所以先用 `DOMParser` 得到一棵真实的 DOM 树，再自顶向下遍历：标签不在白名单就整棵移除，属性不在白名单就删掉，`href` 额外做**协议白名单**（只允许 `http/https/mailto/相对路径/#`），因为 `javascript:alert(1)`、`java\nscript:`、`&#106;avascript:` 都能绕过朴素的字符串判断。黑名单必然漏：`<svg onload>`、`<img src=x onerror>`、大小写 `OnError`、`<iframe srcdoc>`——每漏一个就是一次线上事故。

**代码**：

```javascript
// 浏览器环境执行；Node 下用 jsdom 提供 DOMParser（本段 node --check 通过，运行时需 DOM）
const ALLOWED_TAGS = new Set(['p', 'b', 'i', 'u', 'a', 'ul', 'ol', 'li', 'br', 'span', 'code', 'pre']);
const ALLOWED_ATTR = { a: new Set(['href', 'title']), span: new Set(['class']), p: new Set(['class']) };
const SAFE_URL = /^(https?:|mailto:|\/(?!\/)|#)/i;   // 只允许这几种协议/相对路径

function sanitize(html) {
  const doc = new DOMParser().parseFromString('<div id="root"></div>', 'text/html');
  const root = doc.getElementById('root');
  root.innerHTML = html;                             // 交给浏览器解析，拿到真实树

  const walk = node => {
    for (const el of [...node.children]) {           // 快照遍历，边删边遍历会漏节点
      const tag = el.tagName.toLowerCase();
      if (!ALLOWED_TAGS.has(tag)) { el.remove(); continue; }

      const allow = ALLOWED_ATTR[tag] || new Set();
      for (const attr of [...el.attributes]) {
        const name = attr.name.toLowerCase();
        if (!allow.has(name)) { el.removeAttribute(attr.name); continue; }
        if (name === 'href' && !SAFE_URL.test(attr.value.trim())) el.removeAttribute('href');
      }

      if (tag === 'a') {                             // 外链必须切断 opener 引用
        el.setAttribute('rel', 'noopener noreferrer nofollow');
        el.setAttribute('target', '_blank');
      }
      walk(el);                                      // 递归子树
    }
  };

  walk(root);
  return root.innerHTML;
}

const dirty = '<p onclick="steal()">hi <b>there</b><img src=x onerror=alert(1)>' +
              '<a href="javascript:alert(1)">x</a><a href="https://a.com">ok</a></p>';
console.log(sanitize(dirty));
```

**边界与追问**：① 只处理 HTML 命名空间，`<svg>`/`<math>` 内的 `xlink:href` 是另一套规则，最稳的是**直接把 svg/math 从白名单拿掉**；② 样式类属性同样有风险（`style="background:url(javascript:...)"` 在现代浏览器已拦，但别赌），所以 `style` 一律不进白名单；③ 注释节点、`<template>` 内容不会被 `children` 遍历到，需要额外清理或直接删；④ 生产不要自己写，用 DOMPurify + CSP（`script-src 'self'`）双保险，本段是原理演示；⑤ 追问"后端要不要再过滤一遍"——必须，前端净化只保护当前渲染，接口被直接调用时前端完全不在链路上。

### 精讲 5 · [ALG-176] 签名校验的时序攻击与常数时间比较

**场景**：前端 SDK 收到服务端回调（或校验 webhook 签名），代码里写了 `if (sign === expected)`。安全审计打回：这里存在时序攻击面（timing attack）。

**问法**：`===` 为什么危险？时序攻击怎么利用？如何写常数时间比较？前端做这个有意义吗？

**思路**：字符串比较是**逐字节、遇错即停**的：第 1 个字节就不同，函数立刻返回 false；前 10 个字节相同，就要多跑 10 次比较。攻击者不需要知道签名，只需要**测量响应时间**：在本地反复请求十万次取中位数，能把纳秒级差异从噪声里拉出来，于是可以逐位试出正确前缀（每一位平均试 62 次即可定位），最终完整伪造签名——这叫"逐位爆破"。常数时间比较的做法是**让所有字节都参与运算**：用 `diff |= a[i] ^ b[i]` 累积差异，循环次数只与长度有关，与"对了多少位"无关，最后统一判 `diff === 0`。注意 JS 里很难做到**真正**恒定时间（JIT 优化、GC、CPU 分支预测都会引入抖动），所以关键校验必须在服务端做；前端这一层是为了不给攻击者一个明显的旁路入口。

**代码**：

```javascript
// 危险写法：短路比较，耗时与"公共前缀长度"正相关
const naiveEqual = (a, b) => a === b;

function timingSafeEqual(a, b) {
  const ba = new TextEncoder().encode(String(a));   // 按字节比，不按 UTF-16 码元
  const bb = new TextEncoder().encode(String(b));
  const len = Math.max(ba.length, bb.length);
  let diff = ba.length ^ bb.length;                 // 长度差异也并入，不提前返回
  for (let i = 0; i < len; i++) {
    diff |= (ba[i] ?? 0) ^ (bb[i] ?? 0);            // 越界补 0，保证循环次数固定
  }
  return diff === 0;
}

const expected = 'a3f5c9e1b7d2';
console.log(timingSafeEqual('a3f5c9e1b7d2', expected)); // true
console.log(timingSafeEqual('a3f5c9e1b7d3', expected)); // false，但耗时与上例相同
```

**边界与追问**：① 长度不同时直接 `return false` 也可以（长度不是秘密），但统一并入 `diff` 代码更简单、也不会因为"长度提前返回"泄漏长度信息；② 必须比**字节**而不是字符，中文/emoji 的代理对会让 `charCodeAt` 的长度语义出错；③ Node 侧直接用 `crypto.timingSafeEqual`（要求两个 Buffer 等长，先判长度）；④ 追问"前端做常数时间比较有用吗"——有，但定位是"不给旁路"，真正的密钥校验与频控在服务端；⑤ 追问"时间窗 + nonce 和这个什么关系"——那是防重放（ALG-173），时序攻击防的是**猜签名**，两者解决不同问题，答的时候别混。

### 精讲 6 · [ALG-197] 权限树的级联勾选与半选态

**场景**：权限管理页是一棵部门/菜单树。勾选父节点要自动选中所有子孙；勾掉某个子节点，祖先要变成"半选"（`indeterminate`）；提交时只提交叶子权限点。

**问法**：三态怎么传播？为什么半选不能存进数据？懒加载节点怎么处理？复杂度多少？

**思路**：两个方向、一份真值。**向下**：勾/取消时 DFS 整棵子树同步（父选则子全选，父取消则子全取消）。**向上**：从被操作节点的父节点开始沿祖先链聚合——所有孩子都选中则父选中，否则父取消，**"部分选中"不落数据，只作为派生 UI 态**。为什么半选不能存？因为它是"子节点状态的函数"，一旦存下来就多了第二个真值来源，任何一次异步更新（懒加载补齐、后端回填、并发勾选）都会让它和真实状态不一致，出现"父节点半选、子节点全选"的鬼数据。把 `checked/indeterminate` 都从 `Set` 派生，就永远不会自相矛盾。复杂度：向下 O(子树大小)，向上 O(深度 × 分支数)，整体 O(n)。

**代码**：

```javascript
function applyTreeState(tree, selected, id, value) {
  const nodes = new Map(), parentOf = new Map();
  (function build(list, parent) {
    for (const n of list) { nodes.set(n.id, n); parentOf.set(n.id, parent); build(n.children ?? [], n.id); }
  })(tree, null);

  (function down(n, v) {                       // ① 自顶向下：整棵子树同步
    v ? selected.add(n.id) : selected.delete(n.id);
    for (const c of n.children ?? []) down(c, v);
  })(nodes.get(id), value);

  for (let p = parentOf.get(id); p != null; p = parentOf.get(p)) {
    const kids = nodes.get(p).children ?? [];   // ② 自底向上：全选则选，否则不选
    kids.every(k => selected.has(k.id)) ? selected.add(p) : selected.delete(p);
  }

  function state(n) {                           // ③ 三态是派生量，不写回数据
    const kids = n.children ?? [];
    if (!kids.length) return { checked: selected.has(n.id), indeterminate: false };
    const states = kids.map(state);
    const checked = states.every(s => s.checked);
    const some = states.some(s => s.checked || s.indeterminate);
    return { checked, indeterminate: !checked && some };
  }

  const view = new Map();                      // 递归收集全树的三态，不能只 map 顶层
  (function collect(list) {
    for (const n of list) { view.set(n.id, state(n)); collect(n.children ?? []); }
  })(tree);
  return { view, selected };
}

const tree = [{ id: 'root', children: [
  { id: 'a', children: [{ id: 'a1' }, { id: 'a2' }] },
  { id: 'b', children: [{ id: 'b1' }] },
]}];
const selected = new Set();
applyTreeState(tree, selected, 'a', true);            // a、a1、a2 全选
const { view } = applyTreeState(tree, selected, 'a2', false);
console.log(view.get('a'));    // { checked: false, indeterminate: true }
console.log(view.get('root')); // { checked: false, indeterminate: true }
```

**边界与追问**：① 懒加载节点"未加载"和"未选中"是两回事，父节点聚合时只能看**已加载**孩子，否则会把"没拉过"当成"全不选"；② 禁用节点（`disabled`）不参与父级勾选传播，需要单独维护"可选子集"；③ 顺序必须是先向下、再向上，反了会用到旧状态；④ 追问"选中集合要不要包含父节点 id"——只提交叶子最干净，父节点状态由后端按需推导；⑤ 追问"上万节点卡不卡"——向下传播只走子树、向上只走祖先链，是 O(子树 + 深度)，不是 O(n)；真正贵的是每次全量 `state()` 重算，实际项目里应改成"只重算受影响的祖先链"。

## 五、自测三问（能用一句话答上来才算过）

1. 为什么判权限必须写 `(perm & mask) === mask`，而集合包含却可以直接比 size？——前者防「组合掩码误判」，后者是因为集合去重后基数可以代表包含关系。
