## AIC-028：代码任务上下文超长时，裁剪策略有哪些？「按依赖闭包裁剪」是什么思路？
**答**：
- 裁剪优先级：目标文件全文 > 直接依赖（import 的模块）的**签名层**（函数名/参数/返回类型，去掉函数体）> 类型定义 > 相关测试 > 其余统统不要。
- 依赖闭包裁剪：从改动文件出发沿 import 图收集依赖，对叶子依赖只保留类型与导出签名，核心依赖才给实现——保证模型「够用且不多」。
- 通用手法：丢长注释/空行、大文件取窗口（改动点前后 N 行）、列表截断加「共 X 条」、历史对话压缩成摘要。
- 判断裁剪是否过度的信号：模型开始「编造」没给出的 API、或问你已贴过的内容——说明裁过头了，回补关键上下文。
- 追问钩子：可以写脚本自动做裁剪（详见笔试题 AIC-148 上下文预算分配器），把「贴多少」变成工程问题而非手感问题。

```javascript
// 按依赖闭包裁剪：核心给全文，叶子只给签名
function buildContext(targetCode, imports, readFile) {
  const parts = [`// 目标文件\n${targetCode}`];
  for (const dep of imports) {
    const code = readFile(dep);
    if (dep.includes('/core/')) parts.push(`// 依赖(全文)：${dep}\n${code}`);
    else parts.push(`// 依赖(签名)：${dep}\n${extractSignatures(code)}`);
  }
  return parts.join('\n\n');
}
function extractSignatures(code) {
  // 粗略抽取 export 声明作为签名层
  return code.split('\n')
    .filter(l => /^(export\s+(async\s+)?(function|const|class|interface|type)|\s*(public|private)\s)/.test(l))
    .join('\n');
}
```
