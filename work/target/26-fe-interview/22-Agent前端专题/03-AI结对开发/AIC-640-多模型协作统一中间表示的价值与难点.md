## AIC-640：多模型协作要「统一中间表示」（IR），价值和难点在哪？

**答**：
- 结论先行：**中间表示（IR）把「模型间传递」从自然语言转述升级为结构化契约**，是多模型协作从「口头接力」走向「工程流水线」的关键——就像编译器用 IR 解耦前端后端。
- 价值：1) **无损传递**：自然语言转述会丢细节和引入歧义，IR（任务卡 JSON/设计文档 schema/diff 摘要结构）保留精确语义；2) **解耦**：规划模型只管产出符合 IR schema 的计划，编码模型只管消费 IR，两者可独立替换（AIC-290 降低锁定）；3) **可验证**：IR 可被 schema 校验，不合格在传递前就拦截，而非等到下游出错。
- 难点：1) **IR 设计难**：太简单表达力不够（装不下设计意图），太复杂模型生成不出来；2) **信息压缩损失**：把丰富上下文压成结构化 IR 必然丢信息，要设计「可附原文引用」的机制；3) **模型遵循度**：模型可能不按 schema 输出，需要 AIC-027 结构化输出约束 + 校验重试。
- 实践：不必追求「通用 IR」——针对具体场景定义轻量 schema（如「重构任务 IR」= {目标文件, 约束, 验收用例, 弃用方案[]}），够用即可。
- 追问钩子：为什么「轻量场景 IR」比「通用 IR」更现实？——因为通用 IR 要覆盖所有任务类型，复杂度爆炸且模型难以遵循；场景 IR 只服务一类任务，schema 小、约束明确、模型生成稳定——工程上「够用且可靠」胜过「完备但脆弱」。

```typescript
// 轻量场景 IR：重构任务的中间表示
interface RefactorIR {
  goal: string;
  targets: string[];
  constraints: string[];
  acceptance: { test: string; expect: string }[];
  abandoned: { approach: string; why: string }[]; // 弃用方案，防下游重踩
}

function validateIR(ir: any): ir is RefactorIR {
  return !!ir && typeof ir.goal === 'string' && ir.goal.length > 0
    && Array.isArray(ir.targets) && ir.targets.length > 0
    && Array.isArray(ir.acceptance) && ir.acceptance.every((a: any) => a.test && a.expect);
}

// 规划模型产出 → 校验 → 编码模型消费
const ir = {
  goal: '商品列表改虚拟滚动', targets: ['list.tsx'],
  constraints: ['不改API'], acceptance: [{ test: '1万条首屏', expect: '<1s' }],
  abandoned: [{ approach: 'key重挂载', why: '图片重复加载' }],
};
console.log(validateIR(ir)); // true —— 合格的 IR 才往下传
console.log(validateIR({ goal: '' })); // false
```
