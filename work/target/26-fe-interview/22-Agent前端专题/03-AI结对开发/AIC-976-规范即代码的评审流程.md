## AIC-976：团队推行「规范即代码」（rules 像代码一样版本化），这类规范的变更应该怎么评审？
**答**：
- 规范即代码意味着规范也要走完整 PR 流程：提 PR、写清变更动机与影响范围、CI 校验规范本身的语法与冲突、相关 owner 评审——结论：规范不是文档，是需要被同等对待的代码资产。
- 评审重点不同于业务代码：要看「这条规范会不会误伤合法场景」「与现有规范是否冲突」「是否有对应工具支撑落地」，纯文字好看但无法执行的规范应被打回。
- 要有「灰度与回滚」：规范变更先在小范围试运行（观察误报/绕过数据），确认无误再全量；出问题能快速回滚到旧版本。
- 追问钩子：能提出「规范变更要像代码一样有测试——用一组『应该被拦/应该放行』的样例验证新规范效果」的候选人，把规范的验证也工程化了。

```typescript
// 规范变更评审：语法/冲突/样例三重校验
function reviewRuleChange(newRule, existing, samples) {
  const issues = [];
  if (!newRule.id || !newRule.check) issues.push('语法不完整');
  if (existing.some(r=>r.id===newRule.id)) issues.push('规则ID冲突');
  const falsePositives = samples.filter(s=>s.shouldPass && !newRule.check(s.code));
  const falseNegatives = samples.filter(s=>!s.shouldPass && newRule.check(s.code));
  if (falsePositives.length) issues.push('误伤合法场景x'+falsePositives.length);
  if (falseNegatives.length) issues.push('漏放违规场景x'+falseNegatives.length);
  return { approved: issues.length===0, issues };
}
console.log(reviewRuleChange(
  {id:'R2',check:src=>!src.includes('eval(')},
  [{id:'R1'}],
  [{code:'const x=1',shouldPass:true},{code:'eval("x")',shouldPass:false}]));
```
