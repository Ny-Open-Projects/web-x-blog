## AIC-867：工具链升级时，破坏性变更怎么治理才不让全团队一起返工？
**答**：
- 先把「破坏性」显性化：用**语义化版本（SemVer）**——major 才允许破坏性变更（AIC-868），并在变更日志里明确列出 breaking changes 与迁移路径。含糊的「优化」最容易坑人。
- 流程上：**弃用期（deprecation）**先行——旧 API 标记 deprecated 但继续可用 1~2 个版本，同时提供新 API 和自动迁移工具（codemod），给消费方充裕时间；通过运行日志/call-site 扫描统计还有谁在用旧 API，定向通知而非广而告之。
- 提供**兼容层 / 适配器**：在 major 版本间保留一个 shim 把旧调用转发到新实现，让业务分批迁移；但兼容层要有明确删除时间表，不能永久背着。
- 配套保障：CI 中的「契约测试」提前发现不兼容；灰度发布工具链新版本，先让志愿者团队试用；回滚方案要现成。
- 追问钩子：能说出「破坏性变更必须有 deprecation 周期 + 自动迁移工具 + 使用方清单」，而非直接发新版强推的候选人，理解平台化的社会责任。

```typescript
// 用调用点扫描统计旧 API 的使用方，实现定向通知
type CallSite = { repo: string; api: string; file: string };

function deprecationPlan(calls: CallSite[], oldApi: string, newApi: string) {
  const affected = calls.filter(c => c.api === oldApi);
  const repos = [...new Set(affected.map(c => c.repo))];
  return {
    affectedRepos: repos,
    notice: `以下仓库仍在使用 ${oldApi}，请在 v3 前迁移至 ${newApi}: ${repos.join(', ')}`,
    // 配合 codemod 自动迁移 + 兼容层 shim + 到期删除
    canBreak: repos.length === 0, // 无人使用才可在 major 版本删除
  };
}
console.log(deprecationPlan([
  { repo:'web-app', api:'sdk.chatV1', file:'src/a.ts' },
  { repo:'admin', api:'sdk.chatV1', file:'src/b.ts' },
], 'sdk.chatV1', 'sdk.chat')); // canBreak:false，需先迁移
```
