## AIC-625：多模型「接力编码」流水线什么时候值得用？

**答**：
- 结论先行：**接力（规划模型→编码模型→审查模型）的价值在于「能力互补」，只有当任务各阶段的最优模型确实不同时才值得**；否则就是花三倍成本做一件事。
- 适合接力的场景：1) **阶段能力差异大**：规划需要强推理模型（架构决策），编码需要快模型（大量样板代码），审查需要「挑刺型」模型——三者各有所长；2) **高风险变更**：支付/权限模块，值得用审查模型做第二道防线；3) **长任务**：规划模型分解任务（AIC-311），编码模型批量执行，避免单一模型上下文耗尽。
- 不适合的场景：1) 简单 CRUD——单模型足够，接力纯属过度设计（AIC-084）；2) 需要深度上下文连贯的任务——模型间传递信息会丢失细节；3) 成本敏感且质量已达标。
- 接力的工程关键：**阶段间用结构化中间产物传递**（任务卡/设计文档/diff 摘要），而非自然语言转述；每个阶段有明确验收标准，不合格就打回而非硬往下传（AIC-248 统一验收）。
- 追问钩子：为什么「接力」比「多个模型同时做同一件事再投票」更适合编码？——因为编码是「流水线」而非「并行投票」：规划、实现、审查有天然先后顺序，后一步依赖前一步产出；接力尊重这个依赖，且每步可用最合适的模型，比「三个模型都做完整实现再选一个」省得多。

```typescript
type Stage = { name: string; model: string; validate: (out: any) => boolean };

function runRelay(task: string, stages: Stage[]): { output: any; trace: string[] } {
  let output: any = task;
  const trace: string[] = [];
  for (const stage of stages) {
    // 实际这里调用对应模型的 API，用伪函数示意
    output = `${output} -> [${stage.model}] ${stage.name}`;
    trace.push(stage.name);
    if (!stage.validate(output)) {
      throw new Error(`${stage.name} 阶段验收失败，打回`);
    }
  }
  return { output, trace };
}

const r = runRelay('实现商品列表', [
  { name: '规划', model: 'reasoning-strong', validate: o => o.includes('规划') },
  { name: '编码', model: 'code-fast', validate: o => o.includes('编码') },
  { name: '审查', model: 'review-strict', validate: o => o.includes('审查') },
]);
console.log(r.trace.join('→')); // 规划→编码→审查
```
