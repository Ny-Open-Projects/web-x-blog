## AIC-817：自研模型和第三方模型如何统一纳管，避免两套体系？
**答**：
- 统一的前提是**统一抽象**：无论自研还是第三方，都通过同一套 `ProviderAdapter`（AIC-808）接入，对外暴露统一的请求/响应、usage、错误语义。业务层不应该知道模型来自哪里。
- 生命周期统一建模：`candidate → beta → stable → deprecated → retired`，每个阶段有明确的准入门槛（评测通过率、SLO、安全审查）。自研模型不能因为「是自己人」跳过门禁。
- 能力声明统一：自研模型也要注册到能力注册表（AIC-801），声明它擅长什么、不擅长什么，由协商器公平参与竞争——避免「内部保护主义」导致劣质自研模型强行上线。
- 成本口径统一：自研模型也要算「成本」（GPU 折旧 + 推理开销），用同一套成本模型（AIC-812）核算，否则无法公平比较「自研 vs 采购」的真实收益。
- 追问钩子：能说出「自研模型必须和第三方走同一套评测与门禁，成本也要计入 GPU 摊销」的候选人，既有平台思维又有商业理性。

```typescript
type Lifecycle = 'candidate' | 'beta' | 'stable' | 'deprecated' | 'retired';
type Model = {
  id: string; source: 'internal' | 'vendor';
  lifecycle: Lifecycle; evalScore: number;
  costPer1k: number; // 自研 = GPU 摊销 + 电费，第三方 = 采购价
};

// 准入：统一门禁，不因来源区别对待
function canPromote(m: Model): { ok: boolean; reason: string } {
  if (m.evalScore < 0.8) return { ok: false, reason: 'eval score below 0.8' };
  if (m.costPer1k <= 0) return { ok: false, reason: 'cost not accounted' };
  const order: Lifecycle[] = ['candidate', 'beta', 'stable', 'deprecated', 'retired'];
  // 只能逐级晋升，不能从 candidate 直接到 stable
  return { ok: true, reason: 'pass — enter next stage' };
}

const internal: Model = { id: 'our-code-7b', source: 'internal', lifecycle: 'candidate',
  evalScore: 0.83, costPer1k: 0.0008 };
const vendor: Model = { id: 'vendor-x', source: 'vendor', lifecycle: 'stable',
  evalScore: 0.91, costPer1k: 0.003 };
console.log(canPromote(internal)); // 同样要过 eval 和成本门槛
```
