## AIC-613：大促前紧急修 bug，怎么平衡「快」和「验证充分」？

**答**：
- 结论先行：**紧急不等于跳过验证，而是「把验证收窄到最小必要集」**。AI 能在分钟级生成修复，但验证不足上线引发二次事故的成本远高于慢几分钟——所以要「精准验证」而非「全面验证」或「不验证」。
- 分层验证策略：1) **必做**：针对该 bug 的回归用例（AI 顺手补，AIC-065）、类型检查、相关单测；2) **可做**：局部 E2E、灰度开关（AIC-370 feature flag）先放 5% 流量；3) **缓做**：全量回归、深度性能——大促后补。
- AI 的正确用法：让 AI 做「诊断加速」（定位根因、生成候选修复、补全回归用例），但**修复方案的最终决策和上线审批必须人来**（AIC-088 人类审批点）。紧急场景下 AI 幻觉的风险被放大，因为没人有空仔细审查。
- 护栏不降级：即使是 hotfix，安全扫描、敏感数据检查（AIC-596）这类「一次疏忽就出大事」的检查不能省；可以省的是「锦上添花」的风格类检查。
- 追问钩子：为什么说「越紧急越不能全信 AI」？——因为紧急场景下人的审查注意力最低，而 AI 出错概率不变，两者叠加使「未被发现的 AI 错误」概率最高；所以紧急时反而要提高对 AI 产出的验证强度，而不是降低。

```typescript
type Check = { id: string; tier: 'must'|'should'|'defer'; AIRelevant: boolean };

function buildHotfixPipeline(checks: Check[], emergency: boolean): string[] {
  // 紧急时：必做 + AI相关的应做项，砍掉缓做项
  const selected = checks.filter(c => {
    if (c.tier === 'must') return true;
    if (emergency) return c.tier === 'should' && c.AIRelevant;
    return c.tier !== 'defer';
  });
  return selected.map(c => c.id);
}

const checks: Check[] = [
  { id: 'regression-test', tier: 'must', AIRelevant: true },
  { id: 'type-check', tier: 'must', AIRelevant: false },
  { id: 'security-scan', tier: 'must', AIRelevant: true },
  { id: 'local-e2e', tier: 'should', AIRelevant: true },
  { id: 'full-regression', tier: 'defer', AIRelevant: false },
];
console.log(buildHotfixPipeline(checks, true));
// [regression-test, type-check, security-scan, local-e2e]
```
