## AIC-830：AI 修好的旧 bug 又被改回来了，「回归守卫」怎么设计？
**答**：
- 根因：AI 不知道历史上为什么这么写（那段奇怪的判空是为了兼容某个 IE 版本/某个接口返回 null），它看到「不优雅」就顺手重构掉了。知识只存在于 commit message 或某人的记忆里，没有变成可执行约束。
- 回归守卫三要素：① ** bug → 测试用例**，每个修复必须沉淀一条能复现该 bug 的测试；② **测试 → 注释锚点**，在代码旁用注释写明「不能改成 X，因为 bug#123」，AI 读上下文时能看到；③ **CI 强制运行**，这些测试进阻断级门禁（AIC-828）。
- 更进一步：把「禁区」写进 AI 的规则文件（如「payment 目录禁止改金额计算逻辑，除非同时改测试」），让 AI 在生成阶段就避开，而不是事后 review 发现。
- 守卫本身要治理：测试会随重构失效（误报），要有 owner 定期复核；一个 bug 反复复现 3 次说明守卫不够强，要升级为静态检查规则而非仅靠测试。
- 追问钩子：能说出「把历史 bug 变成规则文件里的约束 + 可执行测试双保险」的候选人，完成了从「修 bug」到「沉淀组织记忆」的跃迁。

```typescript
// 回归守卫：bug 修复 → 可执行测试 + 代码旁锚点注释
// 锚点示例（写在源码旁，AI 读上下文可见）：
// REGRESSION-GUARD[BUG-123]: 此处必须判空，旧版接口会返回 null，勿"优化"掉

type RegressionCase = {
  bugId: string; description: string;
  reproduce: (input: any) => boolean; // 返回 true 表示 bug 未复现（守卫通过）
  owner: string; createdAt: number;
};

const guards: RegressionCase[] = [{
  bugId: 'BUG-123',
  description: '旧版支付接口返回 null 时不得崩溃',
  reproduce: (res) => safeParseTotal(res) === 0, // null 时应安全返回 0
  owner: 'zhangsan',
  createdAt: Date.now(),
}];

function runGuards(cases: RegressionCase[]) {
  const failed = cases.filter(g => !g.reproduce(null)); // 注入历史触发条件
  return {
    pass: failed.length === 0,
    failed: failed.map(g => `${g.bugId}: ${g.description}`),
  };
}
console.log(runGuards(guards)); // 若有人删了判空，这里会 fail → CI 阻断
function safeParseTotal(res: any) { return res?.total ?? 0; }
```
