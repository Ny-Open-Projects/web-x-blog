## AIC-848：一旦拿采纳率考核，大家就开始疯狂点「接受」，怎么防？
**答**：
- 这是古德哈特定律的直接体现：**指标一旦成为目标就不再是好指标**。防御第一原则是「**任何单一指标都不用于个人绩效考核**」——考核驱动必然刷。
- 技术层面用**组合指标互相制衡**：采纳率必须和「存活率」「回滚率」「返工率」一起看——点了接受但随后删掉/改掉，采纳率虚高但存活率会露馅。刷一个指标会拉低另一个。
- 引入**质量护栏一票否决**：逃逸缺陷、生产事故不因其他指标好看而被抵消；指标体系中必须有「不能刷的硬约束」。
- 数据层面做**异常检测**：某人采纳率 99%、平均 review 时长 0 秒、代码存活率 10%，这种分布异常要标记复核（AIC-849）；同时保留原始事件流供审计。
- 组织层面：把效能数据用于**团队复盘和改进**，不用于排名和奖金；透明公开指标的计算口径，让被考核者能验证。
- 追问钩子：能说出「最有效的反作弊是不把指标和个人考核挂钩」的候选人，理解问题是制度设计而非算法检测。

```typescript
type DevStats = { adoption: number; survival: number; revertRate: number; bugs: number; reviewSec: number };

function antiGaming(s: DevStats) {
  const flags: string[] = [];
  if (s.adoption > 0.95 && s.survival < 0.4) flags.push('采纳高但存活低：疑似无脑接受');
  if (s.reviewSec < 3 && s.adoption > 0.8) flags.push('review 时长异常短：疑似走过场');
  if (s.bugs > 5 && s.adoption > 0.8) flags.push('高采纳高缺陷：质量护栏触发');
  return {
    suspicious: flags.length > 0,
    flags,
    // 组合分：采纳必须乘以存活，刷采纳但代码不留分不高
    adjustedScore: +(s.adoption * s.survival * (1 - s.revertRate)).toFixed(3),
  };
}
console.log(antiGaming({ adoption:0.99, survival:0.15, revertRate:0.6, bugs:6, reviewSec:1 }));
// suspicious:true, adjustedScore 极低 —— 刷采纳率被组合指标揭穿
```
