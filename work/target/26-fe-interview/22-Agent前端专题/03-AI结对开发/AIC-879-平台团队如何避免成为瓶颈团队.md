## AIC-879：平台团队做大了反而成了「瓶颈团队」，怎么破？
**答**：
- 瓶颈的根因是**所有需求都要平台团队排期**：业务想改个 prompt 模板也要提需求给平台——平台从「赋能者」变成「收费站」。
- 破局靠**自助化 + 分层**：把高频低风险的能力（改 prompt、看自己团队的看板、接标准 SDK）完全自助化，平台只管「影响半径大」的底座（模型准入、安全、计费）；平台团队从做需求转为做工具与护栏。
- **内部开源**思路：平台代码对内开源，鼓励业务团队贡献适配器/工具（他们最懂自己的场景），平台做 code owner 审核而非亲力亲为——把「1 个平台团队」变成「N 个贡献者 + 1 个守门人」。
- 度量平台是否健康：**自助率**（多少接入没经过平台人工）、**需求等待时间**、**业务团队贡献占比**。自助率低、等待时间长就是瓶颈信号。
- 追问钩子：能说出「平台 KPI 应该是让业务不找平台也能成事（自助率），而不是平台自己交付了多少功能」的候选人，把握了平台团队的正确定位。

```typescript
type Request = { type: string; selfServiceable: boolean; risk: 'low'|'high' };

function routeRequest(r: Request, maturity: number) {
  if (r.selfServiceable && (r.risk === 'low' || maturity >= 4)) {
    return { path:'self-service', note:'自助门户完成，平台零介入' };
  }
  return { path:'platform-team', note:'平台排期（应逐步自助化以降低此项）' };
}
function platformHealth(requests: Request[], manualCount: number) {
  const selfServiceable = requests.filter(r => r.selfServiceable).length;
  return {
    selfServiceRate: +(1 - manualCount / requests.length).toFixed(2),
    avoidableManual: requests.filter(r => r.selfServiceable && r.risk==='low').length,
    verdict: manualCount / requests.length > 0.3 ? '瓶颈预警：过多人工介入' : '健康',
  };
}
console.log(platformHealth([
  { type:'改 prompt', selfServiceable:true, risk:'low' },
  { type:'新增供应商', selfServiceable:false, risk:'high' },
], 1)); // selfServiceRate 0.5 → 瓶颈预警
```
