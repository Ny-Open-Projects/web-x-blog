## AIC-635：模型混用让代码风格割裂，怎么量化检测和统一？

**答**：
- 结论先行：**风格割裂可以量化——把「风格」拆成可测的维度（命名、引号、回调风格、错误处理模式），逐维打分离散度**；离散度高就是割裂，需要统一。
- 量化维度：1) **命名风格**：camelCase / snake_case 比例；2) **语法风格**：单/双引号、分号有无、箭头函数 vs function；3) **模式风格**：错误用 try-catch vs `.catch()`、状态用 useState vs useReducer；4) **抽象风格**：内联逻辑 vs 抽 hook。统计各文件在这些维度的分布，计算熵或方差——混用越乱，离散度越高。
- 统一手段：1) **Formatter 兜底**：Prettier/ESLint 统一语法层（引号/分号），这是最容易的；2) **Rules 约束模式层**：在 rules 里写死「状态管理统一用 useState + custom hook」「异步统一 async/await」；3) **Refactor Agent**：让一个模型按团队风格重写「离群」文件，即 AIC-591 多次生成分歧检测的反用——这里要收敛而非保留分歧。
- 边界：不要追求「100% 一致」——过度统一会扼杀合理差异（如测试代码与生产代码风格本就不同）；关注「同一模块内」的一致性即可。
- 追问钩子：为什么 Formatter 能解决语法层割裂却解决不了模式层割裂？——因为语法是确定的（Prettier 有唯一正确格式），而模式是设计的（用 useReducer 还是 useState 各有道理，无法用规则机械判定）；模式层只能靠 rules 软约束 + review 把守。

```typescript
type FileStyle = { quotes: 'single'|'double'; semi: boolean; asyncStyle: 'await'|'promise' };

function styleEntropy(styles: FileStyle[]): number {
  const freq = (key: keyof FileStyle) => {
    const m = new Map<string, number>();
    for (const s of styles) {
      const v = String(s[key]);
      m.set(v, (m.get(v) || 0) + 1);
    }
    return [...m.values()].map(c => c / styles.length);
  };
  // 对每个维度算熵 -Σ p·log2(p)，取最大（最割裂的维度）
  const entropies = (['quotes', 'semi', 'asyncStyle'] as const).map(k => {
    const ps = freq(k);
    return -ps.reduce((s, p) => s + p * Math.log2(p), 0);
  });
  return Math.max(...entropies);
}

const styles: FileStyle[] = [
  { quotes: 'single', semi: true, asyncStyle: 'await' },
  { quotes: 'double', semi: false, asyncStyle: 'promise' },
  { quotes: 'single', semi: true, asyncStyle: 'await' },
];
console.log(styleEntropy(styles) > 0.5); // true —— 存在割裂
console.log(styleEntropy([styles[0], styles[0]]) === 0); // 完全一致
```
