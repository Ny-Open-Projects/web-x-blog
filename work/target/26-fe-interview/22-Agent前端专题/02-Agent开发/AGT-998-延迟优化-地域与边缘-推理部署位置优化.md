## 998：用户全球分布时，推理请求的部署位置怎么优化

**答**：
- 延迟构成拆解：用户到接入点（网络 RTT）+ 接入点到模型（跨区 RTT）+ 推理本身；模型 API 通常固定区域，跨区调用是大头——接入点尽量靠近模型区域，而不是靠近用户。
- 优化策略：推理网关部署在模型同区域（省跨区 RTT）、静态资源与 SSE 推送用边缘节点靠近用户、检索索引按用户区域多副本（检索在边缘、推理在中心）。
- 一致性代价：多区域索引副本有同步延迟，容忍分钟级差异的业务才做多副本；强一致场景回落中心区。
- 追问钩子：为什么不让推理也上边缘？——边缘算力跑不动大模型且成本高，当前合理分工是「边缘做 I/O 密集（缓存/检索/流转发），中心做计算密集（推理）」。

```ts
// 分工：边缘处理 I/O，中心跑推理
export default {
  async fetch(req, env) {
    const { user } = await auth(req);
    const hits = await env.SEARCH_REGION(bind(user.region))   // 检索走边缘就近副本
      .search(q);
    return fetch(env.INFERENCE_URL, {                          // 推理固定在模型同区域
      method: 'POST', body: buildPrompt(hits, q),
    }); // 推理网关与模型同区域部署，省跨区 RTT
  },
};
```
