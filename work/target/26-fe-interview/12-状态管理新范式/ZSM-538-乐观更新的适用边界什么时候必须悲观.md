## ZSM-538：乐观更新的适用边界：什么操作绝对不能乐观

**答**：
- 可乐观的三特征：**幂等/可逆、服务端几乎必成功、用户预期即时反馈**——点赞、收藏、改备注、本地排序。回滚成本低（UI 抖一下即可接受）。
- 绝对悲观的四类：1) **有资损的交易**（支付、扣库存）——服务端可能拒绝（风控/余额），本地先扣会让用户误以为成功；2) **不可逆操作**（删除、退款提交）——删除乐观成功后用户刷新看到数据还在，信任崩塌；3) **服务端会做再加工的**（风控过滤评论、审核）——本地乐观展示的内容可能根本不会出现；4) **会产生副作用链的**（下单触发通知/优惠券核销）。
- 灰色地带的处理：评论提交可以「乐观展示为 pending 态」（半透明+转圈），成功转正、失败上浮重试——比纯乐观（直接显示为正常评论）或纯悲观（按钮 loading）体验都好。
- 工程上的一致标准：**乐观更新的失败补救必须用户可见**（toast + 状态回滚 + 可重试），静默回滚等于骗用户点过一次。
- 追问钩子：TanStack Query 的 `onMutate` 快照 + `onError` 回滚就是这一标准的封装。

```javascript
// TanStack Query 乐观更新标准骨架
useMutation({
  mutationFn: (newTodo) => api.createTodo(newTodo),
  onMutate: async (newTodo) => {
    await queryClient.cancelQueries({ queryKey: ['todos'] })  // 停掉在途 refetch 防覆盖
    const prev = queryClient.getQueryData(['todos'])          // 快照
    queryClient.setQueryData(['todos'], (old) => [...old, { ...newTodo, _optimistic: true }])
    return { prev }                                            // 传给 onError/onSettled
  },
  onError: (_err, _vars, ctx) => {
    queryClient.setQueryData(['todos'], ctx.prev)             // 回滚
    toast.error('发布失败，请重试')                             // 必须可见
  },
  onSuccess: (saved) => {
    queryClient.setQueryData(['todos'], (old) =>
      old.map((t) => (t._optimistic ? { ...saved } : t)))     // 转正：以服务端 id 为准
  },
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['todos'] }), // 终局对账
})
```
