## ZSM-612：派生数据的计算位置决策链：selector、store、服务端还是构建期

**答**：
- 派生值放哪计算，决策链按「变更频率 vs 读取频率」四个位置：
- 1) **selector（读时算）**：读取频率低、输入小（列表 < 100 条）——成本可忽略，保持代码简单。默认选项。
- 2) **写时算（存进 store）**：读多写少且计算贵（聚合统计、嵌套 join）——写入时算一次存结果字段，读取 O(1)。代价：每次写多算一步，且有「派生字段一致性」维护责任。
- 3) **服务端/worker 算**：数据量大（万级以上）或计算特别重——服务器聚合接口，或 worker 计算（ZSM-580）。主线程 selector 只做轻映射。
- 4) **构建期算**：完全静态的派生（路由表、枚举映射、静态权限矩阵）——打包时生成常量，运行时零成本。
- 判断公式：`单次计算成本 × 读取频率`（读侧成本）对比 `单次计算成本 × 写入频率`（写侧成本）+ 通信/序列化成本，取小者；再叠加「复杂度与一致性风险」做最终裁决。
- 追问钩子：写时算的派生字段是「反范式」——必须保证「唯一写路径」（所有 set 都经过 action），否则出现脏派生；这也是 RTK selector 记忆化流派反对写时算的原因之一。

```javascript
// 决策链示例：订单统计派生
// 场景：5000 订单，聚合报表页面每 30s 刷新，中间频繁读

// 位置4：构建期（静态映射）
export const STATUS_ORDER = buildTimeConstant   // 打包时生成

// 位置2：写时算（读多写少且贵）
const useOrderStore = create((set) => ({
  orders: [],
  // 写入时同步更新聚合（聚合贵：O(n) 但读频率极高）
  addOrder(order) {
    set((s) => {
      const orders = [...s.orders, order]
      return { orders, stats: computeStats(orders) }   // 派生随写更新
    })
  },
}))
const total = useOrderStore((s) => s.stats.total)   // 读 O(1)

// 位置3：worker/服务端（量大或计算重）
const bigStats = useQuery({ queryKey: ['stats'], queryFn: api.getAggregatedStats })  // 服务端算

// 位置1：selector 默认（小数据直算）
const activeCount = useOrderStore((s) => s.orders.filter((o) => o.active).length)
```
