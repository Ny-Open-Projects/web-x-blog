## 999：支付流程的状态机全建模案例

**答**：
- 完整建模：idle -> selecting（选支付方式，parallel 子状态：方式+优惠）-> paying（invoke 支付 API + after 30s 超时）-> confirming（支付结果确认中——后端轮询对齐）-> done/failed/cancelled 终态；错误路径：重试 guard 3 次 -> 降级（换支付渠道）-> 放弃。
- 关键设计点：支付结果以「后端推送」为最终真相（confirming 状态等推送，PAID 事件才进 done——前端乐观的 paying->done 必须经后端确认）、金额等敏感数据不进持久化 context。
- 协作产物：状态图评审（产品确认支付路径/QA 穷举测试矩阵——状态×事件）——支付是零容错流程，图的评审价值最高。
- 追问钩子：为什么支付流程「confirming」状态不可或缺？——支付 API 返回成功 ≠ 支付成功（回调可能失败/延迟）——终态必须由后端推送确认，confirming 是「前端乐观与后端真相」之间的缓冲态（缺它就是超卖事故的来源）。

```ts
const payment = createMachine({
  initial: 'idle',
  states: {
    idle: { on: { START: 'selecting' } },
    selecting: { type: 'parallel', states: { method: {}, coupon: {} },
      on: { CONFIRM: 'paying' } },
    paying: { invoke: { src: payApi,
      onDone: 'confirming', onError: { target: 'retrying', guard: c => c.tries < 3 } },
      after: { 30000: 'confirming' } },
    confirming: { on: { PAID: 'done', FAILED: 'failed' },
      after: { 60000: 'failed' } },
    retrying: { entry: assign(c => ({ tries: c.tries + 1 })),
      on: { RETRY: 'selecting', GIVE_UP: 'failed' } },
    done: { type: 'final' }, failed: {}, cancelled: {},
  },
});
```
