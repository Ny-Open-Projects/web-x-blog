## ZSM-605：大状态树的序列化开销：什么时候 stringify 会成为瓶颈

**答**：
- 量化基准：JSON.stringify 大约 100MB/s~500MB/s 量级（V8 快路径），10MB 状态树序列化一次 20~100ms——**一次交互触发两次 stringify（persist 写入 + devtools 推送）就是 200ms 阻塞**，这就是「打开 devtools 变卡」的常见原因。
- 典型瓶颈点：1) persist 中间件每次 set 全量序列化写 localStorage；2) devtools 中间件每次 set send 全量 JSON；3) 快照导出/调试日志全量 stringify；4) storage 事件跨 tab 同步大状态。
- 修法优先级：1) **partialize**——持久化/调试只序列化必要切片（交易态十几个字段 vs 全树几 MB）；2) **节流**——persist 写盘 debounce 1s，devtools 推送节流；3) **异步序列化**—— stringify 放 requestIdleCallback 或 worker；4) 增量——只序列化变更切片（按 store 分片存储）。
- 判断有没有瓶颈：Performance 面板火焰图找 `JSON.stringify` / `writeString` 长条；或探针计时 persist 的 setState。
- 追问钩子：structuredClone 比 stringify 快且保留类型（Map/Date），但产物不能进 storage 通道——「内存快照用 clone、通道传输用 JSON」分工。

```javascript
// 优化前后对比：persist 的序列化策略
// 优化前：全量每次 set
const bad = create(persist((set) => ({ big: [...100万条], cart: [] }), { name: 'app' }))
// 每次 set → stringify 10MB → localStorage.setItem → 卡

// 优化后：partialize + debounce
const good = create(persist(
  (set) => ({ big: [], cart: [] }),
  {
    name: 'app',
    partialize: (s) => ({ cart: s.cart }),      // 只持久化交易切片
    storage: createJSONStorage(() => debouncedStorage(localStorage, 1000)),
  }
))

function debouncedStorage(base, delay) {
  let timer = null
  return {
    getItem: base.getItem.bind(base),
    setItem: (k, v) => {
      clearTimeout(timer)                        // 1s 内多次写合并
      timer = setTimeout(() => base.setItem(k, v), delay)
    },
    removeItem: base.removeItem.bind(base),
  }
}

// 异步序列化（空闲时写）
function idleStringify(obj) {
  return new Promise((resolve) => {
    requestIdleCallback(() => resolve(JSON.stringify(obj)))
  })
}
```
