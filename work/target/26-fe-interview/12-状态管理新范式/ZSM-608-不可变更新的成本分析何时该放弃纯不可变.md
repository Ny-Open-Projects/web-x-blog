## ZSM-608：不可变更新的成本分析：什么时候该放弃纯不可变写法

**答**：
- 不可变更新的隐藏成本：`{ ...state, items: [...state.items, x] }` 每次复制数组 O(n)。万级数组高频追加（日志流、消息流）每秒几十次 = 每秒百万级元素复制——CPU 全花在复制上。对象浅拷贝同理但通常浅层便宜。
- 成本判断三问：1) 数组多大（>1000 元素警惕）；2) 更新频率多高（每帧/每秒几十次警惕）；3) 更新发生在头部还是尾部（尾部 push 其实 V8 引擎可变长数组扩展较快，但 [...spread] 仍全量复制）。
- 替代方案谱系：1) **分片**——大数组拆成页/chunk，只复制变更页；2) **Mutate + 版本号**——状态可变，顶层带 version 计数，订阅按版本比对（放弃引用比较，换 O(1) 写入；适合 canvas/图表数据）；3) **transient updates**——高频数据根本不进 React 状态（ZSM-518）；4) immer 的结构共享只省「读侧引用稳定」，写侧 draft 仍有 Proxy 开销，高频场景不占优。
- 何时坚持纯不可变：普通业务 CRUD（数组几百条、事件驱动更新）——引用稳定带来的 memo/缓存收益远大于复制成本。
- 追问钩子：权衡的度量方式是「单次变更总耗时」，两种写法在真实数据上跑基准再定，不靠信仰。

```javascript
// 基准：1 万条数组尾部追加 × 60 次
function benchImmutable() {
  const items = new Array(10000).fill(0)
  const t0 = performance.now()
  let state = { items }
  for (let i = 0; i < 60; i++) state = { items: [...state.items, i] }   // 全量复制
  return performance.now() - t0
}

function benchMutate() {
  const items = new Array(10000).fill(0)
  let version = 0
  const t0 = performance.now()
  for (let i = 0; i < 60; i++) { items.push(i); version++ }   // O(1) 追加 + 版本号
  return performance.now() - t0
}
console.log('immutable:', benchImmutable().toFixed(1), 'ms')   // 通常 5~20ms
console.log('mutate+ver:', benchMutate().toFixed(2), 'ms')     // <0.1ms

// Mutate + 版本号 的订阅模型
class VersionedStore {
  constructor() { this.data = []; this.version = 0 }
  append(x) { this.data.push(x); this.version++ }              // 写 O(1)
  subscribe(fn, lastV = -1) {
    if (this.version !== lastV) fn(this.data)
  }
  // 渲染侧：版本没变不重渲；变了全量重画（canvas 场景整幅重绘成本低）
}
```
