## ZSM-790：状态治理的角色分工：谁管架构、谁管门禁、谁管告警

**答**：
- 状态治理的三个角色与 RACI：1) **架构 Owner**（架构组）——ADR 评审、分层规范、选型决策、健康分巡检（ZSM-784）；2) **门禁 Keeper**（平台组）——lint 规则维护、CI BudgetGate、告警阈值调优、工具链研发（探针/巡检器）；3) **业务 Owner**（各业务组）——本域 store 的日常演进、竞态测试补齐、runbook 编写、债务申报。
- 协作流程四条：1) **新 store 流程**——业务 Owner 提案（六问表）→ 架构 Owner 评审 ADR → 合入 registry → lint 门禁自动生效；2) **告警响应流程**——告警触发 → 业务 Owner 按本域 runbook 处置 → 复盘回写审计清单 → 平台 Owner 调阈值；3) **债务流程**——业务申报/巡检发现 → 架构定策略（立即/计划/不还）→ 排期 → 偿还销账；4) **季度巡检**——平台出数据 → 架构出评分 → 业务出整改承诺。
- 分工的关键设计：**告警的处置权在业务 Owner**（最懂本域状态），**阈值与工具在平台**（横向一致性）——避免「告警没人认领」的常见治理失灵。
- 治理会议的最低配置：周度 15 分钟状态站会（告警与债务速览）+ 季度巡检会（健康分 + 整改承诺）——治理不能靠自觉，要靠会议节拍。
- 追问钩子：角色缺失的后果推演——没有架构 Owner：选型碎片化（每页一个状态库）；没有平台 Keeper：门禁形同虚设（规则过期无人维护）；没有业务 Owner：告警无人认领（P0 也无人响应）。

// 治理 RACI 矩阵

    '门禁Keeper(平台组)': ['lint 维护', 'CI BudgetGate', '告警阈值', '工具链(探针/巡检器)'],
    '业务Owner(业务组)': ['本域store演进', '竞态测试补齐', 'runbook 编写', '债务申报'],
  },
  流程: {
    新store: '业务提案(六问) → 架构评 ADR → registry 合入 → lint 生效',
    告警响应: '触发 → 业务按 runbook 处置 → 复盘回写审计 → 平台调阈值',
    债务: '申报/发现 → 架构定策略(立即/计划/不还) → 排期 → 销账',
    季度巡检: '平台出数据 → 架构出评分 → 业务出整改承诺',
  },
  会议节拍: { 周度: '15min 状态站会(告警+债务速览)', 季度: '巡检会(健康分+整改承诺)' },
  缺失后果: {
    无架构Owner: '选型碎片化（每页一个状态库）',
    无门禁Keeper: '门禁形同虚设（规则过期）',
    无业务Owner: '告警无人认领（P0 无响应）',
  },
}
// 关键设计：处置权在业务、一致性在平台 —— 防告警无人认领
