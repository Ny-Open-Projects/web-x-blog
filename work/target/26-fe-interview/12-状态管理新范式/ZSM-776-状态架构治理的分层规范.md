## ZSM-776：状态架构治理：目录分层规范与 store 注册清单

**答**：
- 治理的第一步是「状态有户口」：目录分层规范——`stores/core/`（全局单例：auth/user/config，受控创建）、`stores/domain/`（业务域：cart/order，按域文件）、`stores/feature/`（页面级/功能级：可随 chunk 懒加载）、`stores/ui/`（纯 UI 态：弹窗栈/主题）。层级决定生命周期与共享半径（ZSM-550 的共享半径问题落到目录结构）。
- store 注册清单（registry）：所有 store 在 registry 登记 `{ name, layer, persist, consumers, adr }`——lint 规则检查「引用了未注册的 store」「feature 层 import core 层（允许）反向（禁止）」。清单是依赖图可视化（ZSM-557/716）的数据源。
- 依赖方向规则：`ui → feature → domain → core` 单向；跨层通信走显式协议（action/invalidate），禁止反向 import 与隐式订阅。违反方向的依赖是「状态架构腐化」的第一信号。
- 命名规范：`useXxxStore`（hook）、`xxxStoreApi`（非 React 访问）、`xxxAtom`（Jotai）——命名里隐含层级与用法，grep 友好。
- 治理的度量：registry 的「层数分布」（core ≤ 10 个、feature 数量随业务增长）与「跨层违规数」（目标 0）进架构周报。
- 追问钩子：分层不是教条——「这个状态放哪」用 ZSM-550 六问（事实源/共享半径/更新形态/一致性/生命周期/可观测）判定，目录是结论不是原因。

```javascript
// store 注册清单
// stores/registry.ts
export const STORE_REGISTRY = [
  { name: 'authStore',    layer: 'core',    persist: true,  consumers: ['全局'], adr: 'ADR-0001' },
  { name: 'userStore',    layer: 'core',    persist: false, consumers: ['全局'], adr: 'ADR-0002' },
  { name: 'cartStore',    layer: 'domain',  persist: true,  consumers: ['cart', 'checkout'], adr: 'ADR-0007' },
  { name: 'checkoutStore',layer: 'domain',  persist: false, consumers: ['checkout'], adr: 'ADR-0007' },
  { name: 'wizardStore',  layer: 'feature', persist: false, consumers: ['order-wizard'], adr: 'ADR-0012' },
  { name: 'dialogStore',  layer: 'ui',      persist: false, consumers: ['全局'], adr: 'ADR-0009' },
] as const

// 依赖方向 lint（简化规则示意）
// stores/core/*     只能被 import，不 import 其他层 ✓
// stores/domain/*   可 import core，不可 import feature/ui
// stores/feature/*  可 import domain + core，不可 import ui 层之外页面
// stores/ui/*       不可 import domain/feature（UI 态独立）
// eslint-plugin-boundaries 配置即可实现

// 命名规范
// useCartStore      ← hook（React 消费）
// cartStoreApi      ← 命令式访问（组件外/测试）
// cartCountAtom     ← Jotai atom
```
