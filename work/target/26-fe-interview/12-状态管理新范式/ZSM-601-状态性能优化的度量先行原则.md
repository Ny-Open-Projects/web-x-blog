## ZSM-601：状态性能优化的「度量先行」：改之前先立基线

**答**：
- 状态性能优化的第一原则是**先测量后修改**：没有基线的优化是玄学——改完说「感觉快了」在面试里是减分项。基线三件套：交互延迟（点击到 paint 的 ms）、单次提交重渲组件数、长任务数量与总阻塞时长（TBT）。
- 标准测量姿势：React Profiler API 录制固定脚本（Playwright 驱动相同交互），输出 `renderCount/commitDuration` 数值存档；每次优化前后跑同一脚本对比。人工 DevTools 录制只做探索，不做结论。
- 指标选择：开发环境用「重渲次数 + commit 耗时」（灵敏、可归因）；生产环境用 INP/长任务（真实但不精确）。两边口径要记录在案，避免「开发优化了但用户没感知」。
- 反直觉提醒：**重渲次数下降不等于总耗时下降**——把 10 次 2ms 的重渲合并成 1 次 25ms 的重渲可能更糟。度量要看「总阻塞时长」而非单一计数。
- 追问钩子：建立「性能预算」制度——状态变更提交超过 16ms/重渲超 N 个组件在 CI 报警（ZSM-563 的门禁），防止劣化悄悄累积。

```javascript
// 基线测量脚本（Playwright + Profiler API 注入）
// 前提：应用渲染包在 <Profiler id="PerfTest" onRender={collect}>
async function measureBaseline(page, scenario) {
  await page.goto('/app')
  await page.evaluate(() => { window.__perfLog = [] })
  const t0 = Date.now()
  for (const step of scenario) {
    await page.click(step.selector)
    await page.waitForSelector(step.expect)
  }
  const wall = Date.now() - t0
  const { renders, worstCommit, blockingMs } = await page.evaluate(() => {
    const log = window.__perfLog
    return {
      renders: log.length,
      worstCommit: Math.max(...log.map((e) => e.duration)),
      blockingMs: log.reduce((a, e) => a + Math.max(0, e.duration - 16), 0),  // 超 16ms 部分
    }
  })
  return { scenario: scenario.name, wall, renders, worstCommit, blockingMs }
}

// 基线存档：优化前后对比表
// | 指标          | 优化前 | 优化后 | 变化 |
// | renders       | 87     | 23     | -74% |
// | worstCommit   | 42ms   | 11ms   | -74% |
// | blockingMs    | 310    | 46     | -85% |
// | INP(p75生产)  | 280ms  | ——     | 待验证 |
```
