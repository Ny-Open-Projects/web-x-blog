## ZSM-683：权限矩阵与功能开关的组合状态：两层门禁怎么不冲突

**答**：
- 权限（RBAC，ZSM-532）回答「**这个用户**能不能用 X」，功能开关（feature flag，ZSM-548）回答「**这个环境/灰度桶**里 X 是否存在」——两层正交：flag 关 = 功能不存在（入口整体隐藏），flag 开 + 无权限 = 功能存在但不可用（按钮灰显 + 提示申请）。
- 组合判定函数：`available(action) = flagOn(action) && can(action)`。语义层级：`flag off → 'absent'`（渲染 null）；`flag on + can → 'enabled'`；`flag on + !can → 'locked'`（灰显 + 「需要权限」提示）。UI 组件按三态渲染，逻辑只有一处。
- 数据源分离：flag 来自配置中心（运行时可变，随灰度变更），权限来自会话/服务端（登录期基本稳定）——两层各自订阅各自的 store，组合值用派生（不缓存组合结果，避免两层更新不同步的脏数据）。
- 陷阱：1) **flag 切换的布局跳变**——灰度开功能时按钮突然出现，用 CSS 占位/骨架平滑；2) 组合缓存脏数据——`useMemo([flag, perm])` 忘了依赖会读到旧组合；3) 服务端也要用同一组合逻辑（前端隐藏 ≠ 服务端放行，flag+权限必须服务端二次校验）。
- 追问钩子：「flag off」与「无权限」的埋点差异——功能渗透率（flag 命中后使用率）与权限申请转化是两个指标，混在一起就失去分析价值。

```javascript
// 两层门禁的统一派生
const useFeatureFlags = create(() => ({ newInvoice: false, betaExport: false }))
const useAuthPerms = create(() => ({ perms: new Set(['invoice:view']) }))

function useActionState(action) {
  const flag = useFeatureFlags((s) => s[action])            // 环境层
  const perm = useAuthPerms((s) => s.perms.has(action))     // 用户层
  // 派生组合（不缓存，两层各自订阅）
  return flag ? (perm ? 'enabled' : 'locked') : 'absent'
}

// UI 三态渲染
function InvoiceButton() {
  const state = useActionState('newInvoice')
  if (state === 'absent') return null                       // flag 关：不存在
  if (state === 'locked') return <Tooltip title="需要发票权限"><button disabled>开票</button></Tooltip>
  return <button onClick={create}>开票</button>
}

// 服务端二次校验（同一组合逻辑）
function assertAction(user, action, flags) {
  if (!flags[action]) throw new Error('FEATURE_NOT_AVAILABLE')    // flag 层
  if (!user.perms.includes(action)) throw new Error('FORBIDDEN')  // 权限层
}
```
