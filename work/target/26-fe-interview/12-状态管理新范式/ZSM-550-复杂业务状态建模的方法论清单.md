## ZSM-550：复杂业务状态建模的方法论清单：拿到需求先问哪六个问题

**答**：
- 一问**事实源**：这个状态的权威在服务端还是本地？（交易金额/权限=服务端；草稿/视图偏好=本地）——决定要不要快照、能不能乐观。
- 二问**共享半径**：谁消费？单组件用 useState，跨路由用 store，跨页面恢复用 URL/持久化。共享半径决定存储层级，别一上来就全局 store。
- 三问**更新形态**：低频事件（提交/切换）→ 状态机建模；高频连续（拖拽/输入）→ transient/事件驱动，绕过渲染。
- 四问**一致性要求**：能容忍短暂不一致（乐观+对账）还是要强一致（悲观+等待）？乐观更新的适用边界要先于实现讨论。
- 五问**生命周期**：何时创建、何时销毁？会话态（弹窗栈） vs 持久态（草稿） vs 请求态（缓存）分开建模，生命周期混在一起是内存泄漏的根源。
- 六问**可观测性**：出错时能不能回放？关键业务状态要有变更日志（谁、何时、从什么改成什么）——线上排查全靠它。

```javascript
// 方法论的落地骨架：一个「状态清单表」模板
// | 状态         | 事实源 | 共享半径 | 更新形态 | 一致性 | 生命周期 | 可观测 |
// |--------------|--------|----------|----------|--------|----------|--------|
// | 购物车 items | 服务端 | 全局     | 事件     | 强一致 | 会话+持久 | 变更日志 |
// | 拖拽坐标     | 本地   | 单组件   | 高频     | 无要求 | 会话     | 无需 |
// | 草稿 content | 本地   | 编辑器树 | 高频+低频 | 最终一致 | 持久     | 版本链 |
// | 权限 can(x)  | 服务端 | 全局     | 事件     | 强一致 | 登录期   | 审计日志 |

// 示例：按清单落一个草稿状态
const draftState = {
  factSource: 'local',            // 本地事实 → 不做乐观对账
  scope: 'editor + provider',
  update: { input: 'high-freq', save: 'event' },
  consistency: 'eventual',        // 自动保存最终一致
  lifecycle: 'persist (IndexedDB) + expire 30d',
  observability: 'version chain (undo log)',
}
```
