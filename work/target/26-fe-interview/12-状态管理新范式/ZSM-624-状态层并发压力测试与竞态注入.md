## ZSM-624：状态层的并发压力测试：竞态注入怎么暴露隐藏 bug

**答**：
- 状态层 bug 的大头不是性能而是竞态：乐观更新与真实响应交错、多源写入（WS + 用户操作）、批处理期间的乱序。单元测试按「正常顺序」跑很难命中，需要**竞态注入**——刻意打乱时序让 bug 现形。
- 注入手段：1) **mock 计时器打乱**——vitest 的 fake timers 把 debounce/timeout/延迟响应按随机顺序 flush；2) **响应乱序**——mock fetch 返回 Promise 按随机延迟 resolve（反转请求顺序）；3) **交错事件**——模拟「WS 消息 × 用户点击」在微任务/宏任务交错到达；4) **重复投递**——同一事件发两次，验证幂等。
- 压测维度：高频 set（每毫秒一次 × 10 秒）跑完断言「最终状态 = 预期收敛值」——专测批处理/合并逻辑的正确性；配合内存断言（订阅数回归基线）。
- 断言设计：竞态测试的断言重点是「不变量」而非具体值——如「balance 永不为负」「队列最终清空」「UI 状态机不在非法组合」（rendering+error 同时）。
- 追问钩子：竞态测试是概率性的——靠随机种子控制可复现（seed 打印进失败信息），CI 里固定跑 N 个种子。

```javascript
// 竞态注入测试示例（vitest）
test('乐观更新 + 乱序响应不丢变更', async () => {
  vi.useFakeTimers()
  const responses = new Map()
  // mock：响应按乱序 resolve
  fetch.mockImplementation((url, init) => {
    const body = JSON.parse(init.body)
    const p = new Promise((resolve) => {
      const delay = 100 - body.seq   // seq 大的先回 → 乱序
      setTimeout(() => resolve({ ok: true, json: async () => ({ ok: true }) }), delay)
    })
    return p
  })

  const rc = createReconciler(...)
  rc.applyOptimistic('op1', 'likes', (s) => { s.likes++ })
  rc.applyOptimistic('op2', 'views', (s) => { s.views++ })
  rc.confirm('op2', { likes: 1, views: 2 })   // op2 先确认
  await vi.runAllTimers()
  rc.confirm('op1', { likes: 3, views: 2 })   // op1 后确认
  expect(rc.getState().likes).toBe(3)          // 不变量：确认结果为准
  expect(rc.pending()).toHaveLength(0)         // 不变量：队列清空
})

test('重复投递幂等', () => {
  const t = createUnreadTracker()
  t.addMessage(1); t.addMessage(1)             // 同一消息两次
  expect(t.unread()).toBe(1)
})

// 压力收敛测试
test('高频 set 10 秒最终收敛', async () => {
  const start = Date.now()
  while (Date.now() - start < 10000) {
    store.setState((s) => ({ n: s.n + 1 }))
    await new Promise((r) => setTimeout(r, 1))
  }
  expect(store.getState().n).toBeGreaterThan(9000)   // 收敛断言
})
```
