## ZSM-606：性能视角下的分层：状态层慢还是渲染层慢怎么判别

**答**:
- 一次状态变更的总耗时 = **状态层**（setState 回调执行 + selector 重算 + listener 通知）+ **渲染层**（React reconcile + commit + effect）。判别方法：在探针里分段计时——setState 入口到通知结束记为状态层耗时，配合 React Profiler 的 commitDuration 记渲染层。两段各自和 16ms 帧预算比较。
- 状态层慢的典型：O(n) selector 重算（万级数组过滤）、不可变更新深拷贝大对象、通知风暴（listener 数量 × 通知成本）、序列化（persist/devtools）。
- 渲染层慢的典型：订阅该状态的大子树 diff（成百组件重渲）、昂贵的组件 render（大列表无虚拟化）、effect 级联。
- 判别口径下的修复分工：状态层慢 → 优化 selector/更新结构/批处理；渲染层慢 → memo/useShallow/拆订阅/虚拟化。**先判层再动手**，避免在渲染层拼命 memo 而根因是 selector O(n²)。
- 追问钩子：两层的优化会互相影响——selector 拆细减少重渲（渲染层受益），但过度拆分增加 selector 调用次数（状态层成本上升）；总账要按「单次变更总耗时」衡量。

```javascript
// 分段计时探针
function instrumentStore(api) {
  const origSet = api.setState
  api.setState = (updater, replace, name) => {
    const t0 = performance.now()
    let notifyMs = 0
    const origSub = api.subscribe
    // 通知段计时（简化：包 subscribe）
    origSet(updater, replace, name)
    const stateMs = performance.now() - t0
    const commitMs = window.__lastCommitDuration ?? 0   // Profiler onRender 写入
    if (stateMs + commitMs > 16) {
      console.warn(`[分层] ${name}: 状态层 ${stateMs.toFixed(1)}ms + 渲染层 ${commitMs.toFixed(1)}ms`)
    }
    return { stateMs, commitMs }
  }
}

// React Profiler 侧记录 commitDuration
let lastCommit = 0
window.__lastCommitDuration = 0
function onRender(id, phase, actualDuration) {
  window.__lastCommitDuration = actualDuration
  lastCommit = actualDuration
}

// 判别输出示例
// [分层] cart/addItem: 状态层 38ms + 渲染层 6ms → 根因在 selector（O(n) 过滤）
// [分层] list/refresh: 状态层 2ms + 渲染层 55ms → 根因在大子树 diff（虚拟化/拆订阅）
```
