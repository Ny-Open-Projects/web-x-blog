## ZSM-602：状态重渲的三类根因：订阅过宽、引用不稳定、通知风暴

**答**：
- **订阅过宽**：selector 返回大对象/整棵状态子树，无关字段变更也触发。诊断：render reason 显示「store 值变化」但组件只用其中一个字段。修法：selector 拆标量（性能最优解）或 useShallow。
- **引用不稳定**：selector 每次返回新数组/对象（filter/map 派生），store 任何变更都产出新引用。诊断：组件依赖的底层字段没变却重渲。修法：useMemo 派生（输入引用稳定时缓存生效）、selector 内记忆化、useShallow 浅比较。
- **通知风暴**：一次交互连环 set 多个 store/多次 set 同一 store（逐次通知），或订阅回调里又触发 set（级联放大）。诊断：tracer 日志显示一次点击产生 N 条变更记录。修法：合并为单次 set、批量事务（ZSM-523/524）、把级联逻辑改为派生而非订阅回调写状态。
- 排查顺序有讲究：先用 tracer 定位「变更源」（一次交互多少次 set）——通知风暴优先修（一次顶十次）；再查引用不稳定（memo 失效）；最后拆订阅粒度（收益最线性但改动最多）。
- 追问钩子：三类根因对应三种度量——变更次数、无效重渲次数、单次提交组件数，分别立指标。

```javascript
// 三类根因的对照示例
// 根因1：订阅过宽
const s = useStore((st) => st)          // BAD：整树订阅
const name = useStore((st) => st.name)  // GOOD：标量

// 根因2：引用不稳定
const done = useStore((st) => st.todos.filter((t) => t.done))       // BAD：每次新数组
const done = useStore(useShallow((st) => st.todos.filter((t) => t.done)))  // 浅比较
const done = useStore((st) => useMemo(() => st.todos.filter((t) => t.done), [st.todos])) // memo 化

// 根因3：通知风暴（级联订阅写状态）
// BAD：订阅回调里再 setState
storeA.subscribe(() => storeB.setState({ ts: Date.now() }))   // A 每次变更都触发 B
// GOOD：级联改为派生
const combined = useStore((st) => ({ a: storeA.getState().x, b: storeB.getState().y }))

// 诊断工具：一次交互的变更/重渲计数
let interactions = 0
window.addEventListener('click', () => { interactions = 0 }, { capture: true })
storeApi.subscribe(() => { interactions++; if (interactions > 5) console.warn('通知风暴', interactions) })
```
