## ZSM-751：首屏状态的关键路径：初始 store 注入的时机与体积控制

**答**：
- 首屏状态链路：HTML（含初始状态注入）→ JS 解析 → store 创建 → hydrate → 首帧渲染。每个环节的体积/时机决策影响 FCP/TTI：初始状态要「最小必要」（首屏组件订阅的字段），非首屏状态懒加载。
- 注入方式对比：1) **内联 script**（`window.__INITIAL_STATE__`）——同步可用、阻塞解析（放 body 尾）；2) **RSC props / dehydrated**（框架级）——流式注入、按段水合；3) **独立请求**——不阻塞 HTML 但多一次 RTT。选型：SSR 场景 1/2，CSR 首屏关键数据 2，次要数据 3。
- 体积红线：初始状态 > 100KB 就要审查——反模式「把整个用户配置/菜单树塞进去」；修法：partialize 首屏字段、树形菜单只注入展开路径、列表只注入第一页。
- 序列化安全（回顾 ZSM-561）：`</script>` 注入逃逸（`JSON.stringify` 后替换 `<` 为 `\u003c`）——XSS 经典洞，面试常考。
- 追问钩子：首屏状态与代码分割的协同——「组件懒加载 + 其状态懒创建」（ZSM-611），首屏 bundle 只含首屏 store；测量方式是 Performance 面板的「脚本执行段」按模块归因。

```javascript
// 服务端注入（防 XSS 转义 + 最小化）
function serializeInitialState(state) {
  return JSON.stringify(state)
    .replace(/</g, '\\u003c')            // </script> 逃逸
    .replace(/>/g, '\\u003e')
    .replace(/&/g, '\\u0026')
    .replace(/\u2028/g, '\\u2028')       // 行分隔符
    .replace(/\u2029/g, '\\u2029')
}

// SSR 模板
const html = `
<body>
  <div id="root">${ssrHtml}</div>
  <script>window.__INITIAL_STATE__ = ${serializeInitialState(minimalState)}</script>
  <script type="module" src="/app.js"></script>
</body>`

// 客户端注入 + 懒状态
function hydrateStore(store, injected) {
  if (!injected) return
  store.setState(injected, true)         // replace：初始值整体写入
}

// 懒创建（非首屏 store 不在首包）
// dashboard.ts（异步 chunk）
let _dashboardStore = null
export function getDashboardStore() {
  return (_dashboardStore ??= createStore(defaults))
}

// 体积预算：首屏状态只含首屏字段
const minimalState = {
  user: { id, name, avatar },            // 首屏 header 需要
  feed: { firstPage: items.slice(0, 10) },   // 只注入第一页
  // menus/settings 刻意不注入：懒加载
}
```
