## ZSM-500：状态层收官整合方案
**需求**：把 201~499 的机制整合成一个「状态层运行时」蓝图：给出模块划分、依赖方向与验收清单（一道架构设计题的标准答案结构）。

```javascript
// 状态层运行时蓝图（模块 + 依赖方向）
const runtime = {
  // L0 核心（零依赖）
  core: ['store(vanilla)', 'keyFactory', 'versioning', 'abortScope'],
  // L1 数据（依赖 L0）
  data: ['queryCache(invalidate映射)', 'mutation(幂等opId)', 'projection(乐观三态)'],
  // L2 协同（依赖 L0-L1）
  collab: ['crossTab(version仲裁)', 'wsProjector(seq补拉)', 'offlineQueue(重放)'],
  // L3 治理（依赖全部，只观测不阻塞）
  governance: ['metrics(p95/命中率)', 'alerts(forMs规则)', 'patrol(巡检机器人)', 'advisor(修复建议)'],
  // 依赖红线：L3 不得写业务状态；L1-L2 不得反向依赖 L0 之外的层
  rules: {
    dependencyDirection: 'L0←L1←L2←L3（单向）',
    governanceWrites: '禁止',
    failureIsolation: 'governance 崩溃不影响业务路径',
  },
  // 验收清单（架构题收尾）
  acceptance: [
    '写路径幂等（重复事件/重放安全）',
    '失效映射登记齐全（改哪失效哪）',
    '错误分级传播（致命才炸边界）',
    '降级链存在（每个外部依赖有 fallback）',
    '可观测四件套（指标/告警/巡检/报告）',
    '回滚能力（迁移回滚点/flag 关停）',
  ],
}
```
**评分点**：
- 分层清晰且依赖单向（治理层只读观测——架构题最常见的失分点是治理层反向写业务）
- 每层职责一句话可解释（考官追问任何模块都能回答「它解决什么问题」）
- 验收清单可执行（不是空话，每条对应前面具体笔试题的实现）
- 诚实标注权衡（治理与性能、一致性与可用性的取舍）——架构题的成熟度信号
