## ZSM-803：源码级面试题的三层追问应对：从 API 到实现到边界

**答**：
- 源码题（「Zustand 的 selector 为什么不会全量重渲」）的追问通常三层递进，每层有标准应对：
- **L1 API 层**：直接答机制——「selector + Object.is 比较，订阅粒度在 hook 层」。错误答法：背「Zustand 很轻量」这类营销话术。
- **L2 实现层**（追问「内部怎么做到的」）：useSyncExternalStoreWithSelector 的双缓存（输入 state 引用级 + 输出浅相等级），commit 后防撕裂校验。答法带上「我读过这部分源码」的证据——具体到函数/变量名（inst.hasValue）。
- **L3 边界层**（追问「什么场景会失效」）：并发渲染的 tearing、selector 返回新引用的抖动、getServerSnapshot 不稳定的 SSR throw——边界案例是区分「背过」与「理解」的分水岭。
- 通用策略：每层答案的长度递减（L1 一句话、L2 三句话、L3 举反例）——浅层讲结论、深层讲证据、边界讲反例，节奏感比信息量重要。
- 反向利用：主动抛「这里有个坑我踩过」的具体案例（比如 immer draft 里 async 报错）——真实踩坑经历是最强的源码理解证明。
- 追问钩子：三层答完后面试官再深挖——「源码我读到 useSyncExternalStoreWithSelector 的 inst 缓存，再往下是 React 内部的 useSyncExternalStore 实现，我没继续追，如果你感兴趣我们可以看它的订阅时机」——诚实划界比硬编好。

```javascript
// 源码题三层应对模板（以 Zustand selector 为例）
const THREE_LAYER = {
  L1_API: {
    q: 'selector 为什么不会全量重渲？',
    a: '一句话：selector 粒度订阅 + Object.is 结果比较，相等不触发渲染',
    length: '1 句话',
    trap: '不要背营销话术（轻量/简单）',
  },
  L2_实现: {
    q: '内部怎么实现的？',
    a: 'useSyncExternalStoreWithSelector 双缓存：inst.hasValue 缓存上次输出，输入 state 引用没变直通；变了重算后与旧输出比对（可配 shallow），浅相等返回旧引用',
    evidence: '具体到 inst.hasValue/inst.value 变量名 = 读过源码的证据',
    length: '3 句话',
  },
  L3_边界: {
    q: '什么场景会失效？',
    a: '三个反例：① selector 返回新对象字面量 → 每次重渲（解法 useShallow）；② 并发渲染 tearing → commit 后校验强制重渲兜底；③ getServerSnapshot 返回不稳定引用 → SSR 注水直接 throw',
    length: '举反例 = 理解 > 背诵的分水岭',
  },
  主动案例: '踩坑证明：immer draft 里 await 直接 throw（同步约束）——真实经历最强',
  划界: '诚实划界（「再往下是 React 内部实现，没继续追」）> 硬编',
}
```
