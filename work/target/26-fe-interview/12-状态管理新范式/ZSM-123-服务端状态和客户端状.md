## ZSM-123：服务端状态和客户端状态的本质区别是什么？为什么「服务端数据」不该当普通 state 管？
**答**：
- 服务端状态的本质是「远端数据的本地缓存副本」：唯一真源在服务端、随时可能被别人改、需要失效/重取/去重/竞态处理；客户端状态真源就在前端（UI 偏好、表单、选中项），没有同步问题。
- 把接口数据塞进 Redux/Zustand 手动管理，等于把缓存层当数据层用：要自己实现 loading/error/去重/失效/重取/分页缓存，全是重复造轮子且容易漏（竞态和失效是重灾区）。
- 「状态管理新范式」的核心主张：按所有权分层——服务端状态交给 TanStack Query/SWR/Apollo 这类缓存库，客户端状态交给 Zustand/Jotai，URL 状态交给路由，组件私有状态用 useState，各层用对的工具。
- 面试金句：「Redux 管状态，Query 管缓存；缓存是状态的超集问题，但不是所有状态都需要缓存」。

```javascript
// 反模式：接口数据放 Zustand，手动维护五个平行标记
const useBadStore = create((set) => ({
  list: [], loading: false, error: null, page: 1, dirty: true, // 状态爆炸
  fetch: async () => { /* 去重？竞态？失效？全要手写 */ },
}))

// 正解：分层——服务端数据走 Query，客户端条件走 Zustand
const useFilterStore = create((set) => ({ kw: '', setKw: (kw) => set({ kw }) }))

function GoodsList() {
  const kw = useFilterStore(s => s.kw)                       // 客户端状态
  const { data, isLoading } = useQuery({                     // 服务端状态
    queryKey: ['goods', kw],
    queryFn: () => api.goods(kw),
  })
  return <List items={data ?? []} loading={isLoading}/>
}
```
