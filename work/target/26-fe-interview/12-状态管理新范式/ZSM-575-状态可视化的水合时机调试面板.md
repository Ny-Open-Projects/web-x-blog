## ZSM-575：SSR 场景的状态调试：注水前后状态对不上怎么查

**答**：
- 典型症状：服务端渲染出 A 状态的 HTML，客户端注水瞬间跳成 B 状态——报 hydration mismatch 或视觉闪变。根因三类：1) 双方初始状态不同（服务端每请求 store 注入的数据没被客户端读对）；2) 客户端在注水前就跑了改状态的代码（module 顶层 setState、第三方脚本）；3) 依赖「客户端才有」的输入（Date.now/localStorage/随机数）参与了渲染。
- 调试手段：1) 序列化诊断——在服务端渲染结束时把 store 快照写进 HTML（`<script>__HYDRATE_STATE__</script>`），客户端注水前对比初始 store 与注入值，diff 打印（该诊断代码只在 dev 跑）；2) 标记法——给关键节点加 `suppressHydrationWarning` 前先确认差异字段；3) 时间轴——`performance.mark('hydrate-start')` 到首次 store set，检查是否有注水窗口期的变更。
- 注水窗口纪律：所有「客户端需要立即改状态」的逻辑放到 useEffect（注水完成后），绝不放 module 顶层或渲染期间；读写 localStorage/日期的组件标记 client-only。
- React 19 的改进：注水 mismatch 从整树丢弃变为局部重渲染，但诊断路径不变。
- 追问钩子：状态库的 getServerSnapshot/getInitialState 双快照设计（ZSM-513）就是从机制上预防这类问题的。

```javascript
// 服务端：注入快照
export function render(req) {
  const store = createCounterStore()          // 每请求实例
  store.setState({ initialData: loadData(req) })
  const html = renderToString(<StoreProvider store={store}><App /></StoreProvider>)
  return html + `<script>window.__HYDRATE_STATE__=${JSON.stringify(store.getState())}</script>`
}

// 客户端（dev only）：注水前诊断
if (import.meta.env.DEV) {
  const injected = window.__HYDRATE_STATE__
  const clientInitial = store.getState()
  const diffs = Object.keys(injected ?? {}).filter((k) => !Object.is(injected[k], clientInitial[k]))
  if (diffs.length) {
    console.warn('[hydration] 注水前后状态不一致的字段:', diffs,
      { server: injected, client: clientInitial })   // 精确定位漂移字段
  }
}

// 纪律示例：错 vs 对
// 错：module 顶层读取客户端数据并改状态
// store.setState({ theme: localStorage.getItem('theme') })   // 注水前变更 → mismatch

// 对：注水完成后再应用
useEffect(() => {
  const theme = localStorage.getItem('theme')
  if (theme) store.setState({ theme })   // 注水后，safe
}, [])
```
