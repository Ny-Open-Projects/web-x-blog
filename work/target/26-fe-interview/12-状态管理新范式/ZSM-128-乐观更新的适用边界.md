## ZSM-128：乐观更新的适用边界在哪？哪些操作坚决不能用乐观更新？
**答**：
- 适用：高频、低风险、幂等或用户自己能撤销的操作——点赞、已读标记、列表排序、加入草稿；判据是「失败可回滚且回滚用户无感」。
- 不适用：产生外部副作用的操作——支付下单、发送消息/邮件、审批流、库存扣减；失败后「回滚 UI」回滚不了已发出的邮件，且用户基于假成功做出后续决策损失放大。
- 灰色地带要配「乐观 + 确认」：消息发送可乐观展示 pending 态，服务端 ack 才转正常，超时转失败重试，这是 IM 的标准做法。
- 面试答题模板：先说判据（可逆性/幂等性/副作用可见性），再给一个自己踩过的坑（如乐观下单导致重复支付）。

```javascript
// 消息发送：乐观 pending → ack 确认 / 失败重试（灰色地带标准解）
function useSendMessage(roomId) {
  const qc = useQueryClient()
  return useMutation({
    mutationFn: api.sendMessage,
    onMutate: async (draft) => {
      const tmp = { id: draft.clientId, text: draft.text, status: 'pending' }
      await qc.cancelQueries({ queryKey: ['messages', roomId] })
      qc.setQueryData(['messages', roomId], (old = []) => [...old, tmp])
      return { prev: qc.getQueryData(['messages', roomId]) }
    },
    onSuccess: (msg) => qc.setQueryData(['messages', roomId], (old = []) =>
      old.map(m => m.id === msg.clientId ? { ...msg, status: 'sent' } : m)),
    onError: (_, draft, ctx) => qc.setQueryData(['messages', roomId], (old = []) =>
      old.map(m => m.id === draft.clientId ? { ...m, status: 'failed' } : m) // 不删，可重试
        ?? ctx.prev),
  })
}
// 对比：支付按钮只能 pending 态 + 服务端结果驱动，不做乐观
```
