## ZSM-545：全局弹窗编排（嵌套确认、互斥）怎么用状态机建模

**答**：
- 反模式：每个弹窗一个 `useState<boolean>`，全局十几个布尔互相打架——「确认删除」弹到一半关了「编辑」弹窗、遮罩层级错乱、Esc 关错层。
- 正确建模：弹窗栈（stack）+ 每层描述 `{ id, kind, payload, resolve }`。栈顶才是可交互层，关闭永远 pop 栈顶；栈结构天然解决互斥（一次只有栈顶激活）和嵌套确认（删除确认盖在编辑弹窗上）。
- Promise 化 API：`confirm({ kind: 'delete', payload })` 返回 Promise，resolve 在用户点击时调用——调用侧 `if (await confirm(...)) doDelete()`，把「弹窗交互」写成同步逻辑，消灭回调地狱。
- 与状态机结合：弹窗流本身有状态（编辑中→删除确认→关闭），用 XState 建模成 `editing.on.CONFIRM_DELETE = 'confirming'`，弹窗栈由状态驱动的 UI 渲染——复杂多步弹窗（向导式）用状态机，简单确认用 Promise 栈。
- 追问钩子：Esc/遮罩点击 pop 栈顶时要触发该层的 `resolve(false)`（取消语义），Promise 泄漏是弹窗系统最常见的 bug。

```javascript
const useDialogs = create((set, get) => ({
  stack: [],   // { id, kind, payload, resolve }

  open({ kind, payload }) {
    return new Promise((resolve) => {
      set((s) => ({ stack: [...s.stack, { id: crypto.randomUUID(), kind, payload, resolve }] }))
    })
  },

  close(result) {
    const { stack } = get()
    const top = stack.at(-1)
    if (!top) return
    top.resolve(result)                        // 必须兑现 Promise：取消也是 false
    set({ stack: stack.slice(0, -1) })         // 只关栈顶
  },
}))

// 业务侧：Promise 化编排
async function onDeleteDraft(draft) {
  if (!await useDialogs.getState().open({ kind: 'confirm', payload: { text: '删除后不可恢复' } })) return
  try {
    await api.delete(draft.id)
    toast.success('已删除')
  } catch {
    await useDialogs.getState().open({ kind: 'alert', payload: { text: '删除失败' } })  // 失败也是一次弹窗编排
  }
}

// 渲染层：栈顶可交互，其余禁用
{stack.map((d, i) => (
  <Dialog key={d.id} interactive={i === stack.length - 1} kind={d.kind} payload={d.payload} />
))}
```
