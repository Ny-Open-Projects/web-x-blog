## ZSM-535：服务端数据归一化建模（按 id 扁平化）比嵌套对象好在哪

**答**：
- 嵌套问题：接口返回 `{ order: { items: [{ goods: {...} }] } }` 这类深嵌套，同一 goods 在多个 order 里重复出现；改「某商品标题」要遍历所有引用处，漏改即不一致，且 immer 更新深路径成本高。
- 归一化建模：`entities: { goods: Map<id, Goods>, orders: Map<id, Order> }`，关联用 id：`order.itemIds`。更新实体一次写入，所有引用处自动「最新」——引用靠派生 join。
- 派生 join：selector 里 `order.itemIds.map(id => goodsById[id])`。缺点是返回新数组，需 useShallow/记忆化；优点是数据永远一致。
- 增删改的 O(1)：删除商品从 Map delete 一项 + 把所在 order 的 itemIds 过滤，无深拷贝；嵌套模型则要 clone 整棵树。
- 追问钩子：normalize 代价是写「schema 拆包」逻辑（Redux Toolkit 的 createEntityAdapter / normalizr 是现成方案），数据量小（<100 条且不互相引用）时嵌套直存更简单——归一化是为「同实体多处引用 + 独立更新」的规模问题服务的。

```javascript
// 接口原始数据 → 归一化
function normalize(orders) {
  const goods = new Map(), ordersMap = new Map()
  for (const o of orders) {
    ordersMap.set(o.id, { ...o, items: undefined, itemIds: o.items.map((i) => i.goodsId), itemQty: Object.fromEntries(o.items.map((i) => [i.goodsId, i.qty])) })
    for (const it of o.items) goods.set(it.goods.id, it.goods)  // 同一 goods 只存一份
  }
  return { goods, orders: ordersMap }
}

const useShop = create(() => normalize(await fetchOrders()))

// 派生 join：订单详情视图
const useOrderDetail = (orderId) => useShop(useShallow((s) => {
  const order = s.orders.get(orderId)
  if (!order) return null
  return order.itemIds.map((id) => ({
    goods: s.goods.get(id),
    qty: order.itemQty[id],
  }))
}))

// 更新商品标题：一次写入，全部订单视图同步
useShop.setState((s) => {
  const goods = new Map(s.goods)
  goods.set(id, { ...goods.get(id), title: '新标题' })
  return { goods }
})
```
