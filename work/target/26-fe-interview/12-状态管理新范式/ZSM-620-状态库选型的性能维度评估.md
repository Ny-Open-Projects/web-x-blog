## ZSM-620：状态库选型的性能维度评估：同一需求四种库的压测对比

**答**：
- 选型性能评估的标准维度：1) **通知粒度**——单字段更新触发多少组件（Zustand selector 粒度最细；Context 类最粗）；2) **写入成本**——不可变复制 vs proxy 拦截 vs 版本号（万级数据追加场景差异 90 倍，见 ZSM-619）；3) **派生成本**——依赖图重算策略（Jotai 动态图 vs 手写 selector memo）；4) **序列化成本**——persist/devtools 的字符串化压力。
- 同需求压测设计：固定「万条列表 + 高频更新 + 派生统计」场景，四种方案（Context+useReducer / Zustand / Jotai / Valtio）跑同一基准，对比四维数据。结论示例：高频大数组追加 mutate 场景 Valtio 的 proxy 有额外拦截开销但避免复制，Zustand 纯不可变复制成本最高但通知最省。
- 评估之外的权衡：性能差异通常在「正常业务量级」下不可感知（几百条、事件驱动）——选型的默认权重应是生态/TS 体验/团队熟悉度，性能权重只在确有热路径需求时上调。**先用基准证明瓶颈在状态库，再为性能换库**。
- 迁移成本评估：压测结论要叠加迁移工作量（API 差异、订阅点重写、测试重录），收益/成本比决定是否值得动。
- 追问钩子：压测要在「目标设备档次」跑（低端安卓手机 4x CPU 差异巨大），开发机数据不代表性。

```javascript
// 四库统一基准骨架
const scenarios = {
  // 场景1：万条数组高频追加（写入成本维度）
  appendHeavy: (ctx) => { for (let i = 0; i < 1000; i++) ctx.append(i) },
  // 场景2：单字段更新触发组件数（通知粒度维度）
  singleFieldUpdate: (ctx) => ctx.updateField('flag', true),
  // 场景3：派生聚合重算（派生成本维度）
  derivedStats: (ctx) => ctx.readStats(),
}

// 库适配器接口（每种库实现同一接口才能公平对比）
// { append, updateField, readStats, subscriberCount }

// 结论记录表
// | 维度          | Context | Zustand | Jotai  | Valtio |
// |--------------|---------|---------|--------|--------|
// | 追加万条(ms)  | 18      | 22      | 15     | 9      |
// | 单字段触发组件 | 42(全)  | 3       | 1      | 3      |
// | 派生统计(ms)  | 8       | 6       | 4      | 7      |
// | persist 开销  | 高      | 中      | 中     | 中     |
// 结论：热路径为「高频大数组」→ Valtio/版本号方案；一般业务 → Zustand 默认
```
