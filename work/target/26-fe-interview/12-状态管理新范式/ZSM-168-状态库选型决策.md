## ZSM-168：给新项目做状态库选型，决策树长什么样？请给出完整推导而不是背结论。
**答**：
- 第一问「数据从哪来」：服务端为主 → TanStack Query（复杂交互/中后台）或 SWR（轻量/内容站），客户端状态几乎只需要少量 store；重离线/协同 → yjs + 缓存库。
- 第二问「客户端状态的形状」：少而大的领域对象、要组件外读写 → Zustand；多而小的原子 + 复杂派生 → Jotai；命令式高频交互 → Valtio；已有 Redux 资产且团队熟 → RTK（+RTK Query）。
- 第三问「约束」：SSR 诉求 → 都支持但优先 Query+Zustand（SSR 资料全）；包体积敏感 → Zustand 最小；团队规模大要强约束 → RTK 的模板反而是优点。
- 输出形态：一张决策树 + ADR 记录（背景/选项/结论/边界），并约定「引入第三套状态库需要 ADR」的治理条款。

```javascript
// 伪决策树（面试白板版）
// 数据来源？
// ├─ 服务端为主
// │   ├─ 交互重（乐观更新/失效复杂）→ TanStack Query + Zustand(薄)
// │   └─ 展示为主 → SWR / RSC 直出
// ├─ 客户端为主
// │   ├─ 领域对象少而大 → Zustand
// │   ├─ 原子多、派生复杂 → Jotai
// │   ├─ 命令式高频（画布/表单草稿）→ Valtio / ref
// │   └─ 已有 Redux 资产 → RTK
// └─ 协同/离线 → yjs + UndoManager
//
// 治理条款：新库引入需 ADR；状态库 ≤2 个；服务端数据禁止进客户端 store
```

**边界与易错**：

- 把服务端数据也算进状态库选型：第一问应是「这份数据归谁所有」，答错就会拿 Zustand 重造一遍缓存层。
- 只按包体积选：Zustand 最小但缺约束与规范，大团队半年后又分裂出第二套。
- 决策树不给退出条件：技术选型要写清什么信号下重新评估，否则一套库用五年没人敢换。

**追问**：

1. 已经有两套状态库了怎么收敛？→ 先冻结新增，按数据所有权把服务端数据迁到 Query，剩下的一类一类合并，不要一次性重写。
2. 团队有人坚持 Redux 怎么用数据说服？→ 拿真实页面的样板代码行数、新人上手时间、改动扩散面做对比，而不是讲理念。
3. SSR 下 Zustand 有什么坑？→ 服务端单例 store 会跨请求共享用户数据，必须每请求新建 store 并通过 provider 注入。
