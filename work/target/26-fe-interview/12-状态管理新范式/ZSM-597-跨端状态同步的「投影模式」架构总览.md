## ZSM-597：跨端状态同步的「投影模式」架构：每个端持有全量还是投影

**答**：
- 全量镜像模式：每个端（tab/设备/窗口）持有完整状态副本，通过同步协议保持一致（ZSM-578）。优点：每端离线可用、响应快；缺点：同步协议复杂、冲突面大、内存翻倍。
- 投影模式：**权威状态在一个端（leader/主进程/服务端）**，其他端只订阅「自己需要的切片」+ 发送意图（intent）。每端的 store 是权威状态的投影（projection），不持有数据主权。优点：冲突几乎消失（写路径单一）、流量按需；缺点：权威端挂了要故障转移、离线能力弱。
- 选型矩阵：文档协同（全量+CRDT，需要离线并发编辑）、IM（投影为主，服务端权威 + 本地缓存）、仪表盘多窗口（投影，Electron 主进程权威）、配置中心（投影，服务端权威）。
- 混合架构是常态：**事实数据投影 + 交互态全量**——全局购物车走服务端投影（交易态强一致），本地 UI 态（弹窗/选中）每端独立全量持有，两层用「意图」协议连接。
- 追问钩子：投影模式下「写延迟」的体验处理——意图发出后立即本地乐观投影更新，等权威确认后对账（和 ZSM-528 对账器同一套思路）。

```javascript
// 投影模式骨架：客户端投影 + 服务端权威
class ProjectionStore {
  constructor(slice) {
    this.slice = slice              // 订阅切片：['cart', 'session']
    this.projection = {}            // 权威状态的本地投影
    this.subs = new Set()
  }

  // 服务端推送（权威变更）
  onServerPatch(patch) {
    for (const key of this.slice) {
      if (patch[key] !== undefined) this.projection[key] = patch[key]
    }
    this.subs.forEach((fn) => fn(this.projection))
  }

  // 本地意图：乐观更新投影 → 发给权威端 → 确认后对账
  async dispatch(intent) {
    applyOptimistic(this.projection, intent)      // 乐观投影
    this.subs.forEach((fn) => fn(this.projection))
    try {
      const confirmed = await authority.execute(intent)   // 权威端（服务端/leader/主进程）
      this.projection = confirmed                 // 确认值覆盖（服务端可能合并了他人变更）
    } catch (e) {
      this.projection = await authority.refetch(this.slice) // 失败重拉投影
    }
    this.subs.forEach((fn) => fn(this.projection))
  }
}

// 混合分层示例
// projection: { cart, session }   ← 服务端权威，投影订阅
// local:      { dialogs, selection, dragPos }  ← 端内独立全量
// intent:     'cart/addItem' → authority.execute → 对账
```
