## ZSM-278：支付流程（下单/轮询/回调）为什么适合状态机管理

**答**:
- 支付是典型长事务：状态多（待支付/支付中/成功/失败/超时/退款）、事件源多（用户操作/轮询结果/服务端回调），布尔标志组合会爆炸（isPaying && !isTimeout...），状态机让非法转移不可表达
- XState/Zedux 或自写 FSM：定义 states + transitions，轮询结果/回调作为事件驱动转移；进入终态才解锁 UI
- 关键设计：轮询幂等查单（GET 状态）作为恢复手段——页面刷新后从服务端拉当前状态重建 FSM，不依赖前端内存
- 竞态：支付成功回调与轮询同时到达，FSM 的事件去重（终态后忽略后续事件）天然解决

```javascript
const payMachine = createMachine({
  id: 'pay', initial: 'idle',
  states: { idle: { on: { SUBMIT: 'paying' } },
    paying: { on: { POLL_SUCCESS: 'success', POLL_FAIL: 'failed', TIMEOUT: 'timeout' } },
    success: { type: 'final' }, failed: {}, timeout: { on: { RETRY: 'paying' } } },
})
// 终态后收到的重复事件被忽略 → 回调与轮询竞态安全
```
