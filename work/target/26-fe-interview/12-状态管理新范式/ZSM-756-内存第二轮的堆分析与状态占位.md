## ZSM-756：内存分析第二轮：heap snapshot 里定位状态占用的操作路径

**答**：
- 定位「哪个 store 吃了内存」的操作路径（Chrome DevTools Memory 面板）：1) 采集堆快照（操作前后各一次）；2) Summary 视图按 constructor 过滤——`Map/Set/Array/Object` 的 Retained Size 排序，大对象就是嫌疑；3) 点开对象看 Retainers 链——顺着引用链找「谁拽着它」（通常是 store 闭包 → entries → data）；4) Comparison 视图（两次快照 diff）看 `#Delta` 增长的对象类型——增长即泄漏（ZSM-609 五泄漏面的实证）。
- 快照命名约定：`before-scroll-1000` / `after-scroll-1000`——同脚本两快照，diff 才有意义；Heap allocation profiling（时间线式）适合抓「分配热点」（高频 new 的函数）。
- 状态层的常见大对象：未虚拟化的全量列表缓存（10 万行 × 每行 1KB = 100MB）、时间旅行快照、undo 历史、atomFamily 无淘汰、图片 Blob 引用未 revoke。
- 修法验证闭环：修完重跑同脚本对比 Retained Size 曲线——「锯齿回落」才算修复；长期驻留的大对象要有明确解释（为什么必须驻留）。
- 追问钩子：生产环境的内存监控没有 heap snapshot——用 `performance.memory`（Chrome）的趋势监控 + 自报的 store 统计（`rows.size`、`history.length`），趋势异常触发「带 store 统计的错误上报」。

```javascript
// DevTools Memory 操作路径（对照步骤）
// 1) 录制：Heap snapshot A → 执行脚本（滚动加载 1000 行）→ Heap snapshot B
// 2) Comparison 视图选 B vs A → 按 Retained Size 降序
// 3) 找到增长对象：Map → (store rows) → Retainers 链
//    rows Map ← useTable store ← module closure ← window.__stores
// 4) 确认泄漏：#Delta 持续增长且 GC 后不回落 = 泄漏

// 生产侧替代：store 统计自报
function collectStoreStats() {
  return {
    rows: useTable.getState().rows.size,
    historyLen: historyStack.length,
    atomFamilySize: itemFamily.size?.() ?? 'n/a',
    heapMB: performance.memory ? performance.memory.usedJSHeapSize / 1048576 : null,
  }
}

// 趋势监控：内存增长 + store 统计联合上报
setInterval(() => {
  const stats = collectStoreStats()
  if (stats.heapMB > 500 || stats.rows > 200000) {
    report({ type: 'memory-trend', stats, sessionId: SESSION_ID })   // 带统计的错误上报
  }
}, 60000)

// Blob 引用泄漏（图片预览常见）
function showPreview(file) {
  const url = URL.createObjectURL(file)
  img.src = url
  return () => URL.revokeObjectURL(url)    // 必须 revoke，否则 Blob 常驻堆
}
```
