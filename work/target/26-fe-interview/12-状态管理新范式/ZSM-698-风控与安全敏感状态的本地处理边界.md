## ZSM-698：安全敏感状态的前端处理边界：验证码、风控弹窗与防刷

**答**：
- 原则一句话：**安全状态的判定永远在服务端，前端只做「体验层」**。验证码状态机（未获取→已发送倒计时→可重发）、风控挑战（滑块/短信二次验证）在前端只是「服务端指令的投影」——服务端返回 `need_captcha` / `need_sms_verify`，前端渲染对应流程，不自判「用户可疑」。
- 倒计时的防刷边界：重发验证码的 60s 倒计时必须服务端裁决（前端倒计时可以被刷新绕过），前端倒计时只是 UI 提示；**提交时带 attempt token**（获取验证码时下发的一次性 token），服务端校验 attempt 有效性与频次。
- 风控弹窗的状态机：`normal → challenged(挑战中) → verified/pass → normal`，挑战失败有限次（3 次）后进入锁定（服务端下发 lockUntil）；本地状态机不决定锁定，只忠实渲染服务端指令——否则前端逻辑被逆向后成为绕过工具。
- 前端防刷的正确姿势：不造轮子做反爬（无意义），只做「抬高成本」的措施——行为埋点（点击轨迹/停留时长随请求上报，供服务端风控模型）、请求签名（前端 SDK 算签名，算法可逆向但抬高门槛）、防自动化检测（环境指纹）。
- 追问钩子：面试标准答案的收尾——「前端所有安全措施都是延迟攻击者几分钟，真正的防线是服务端限流+风控+审计」，展示对边界的清醒认知。

```javascript
// 验证码状态机（服务端指令投影）
const captchaMachine = setup({}).createMachine({
  context: ({ input }) => ({ countdown: 0, attempts: input.attempts ?? 0, token: null }),
  initial: 'idle',
  states: {
    idle: {
      on: {
        REQUEST: { target: 'sending' },
      },
    },
    sending: {
      invoke: {
        src: 'sendCaptcha',
        onDone: { target: 'counting', actions: assign({ countdown: ({ event }) => event.output.cooldown, token: ({ event }) => event.output.token }) },
        onError: [
          { guard: ({ event }) => event.error.code === 'RATE_LIMITED', target: 'locked',
            actions: assign({ lockUntil: ({ event }) => event.error.lockUntil }) },
          { target: 'idle' },
        ],
      },
    },
    counting: {
      on: { TICK: { actions: ({ context }) => ({ context: { countdown: context.countdown - 1 } }) } },
      always: [{ guard: ({ context }) => context.countdown <= 0, target: 'idle' }],
    },
    locked: { type: 'final' },        // 服务端下发的锁定期
  },
})

// 提交带 attempt token：服务端校验一次性
async function submitWithCaptcha(phone, code, token) {
  const res = await api.verify({ phone, code, attemptToken: token })   // token 用后即焚
  return res
}
```
