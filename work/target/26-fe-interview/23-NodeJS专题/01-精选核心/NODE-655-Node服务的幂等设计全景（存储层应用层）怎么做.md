## NODE-655：幂等设计全景怎么做？
**答**：
- 存储层幂等：唯一约束（最可靠——重复插入直接冲突报错，应用层捕获转幂等响应）；乐观锁（version 条件更新——只生效一次）；条件写（INSERT ... ON CONFLICT DO NOTHING）。
- 应用层幂等：幂等键表（key → 结果缓存——重放返回原结果而非重执行）；状态机约束（只在合法状态迁移——重复请求命中已终态直接返回）。
- 幂等键生命周期：客户端生成（UUID 随请求）→ 服务端存储（结果 + TTL）→ 重放返回存储结果——TTL 内的重试/重放零副作用（SCN-FIN-541 同源）。
- 幂等的边界：查询天然幂等；非幂等操作（扣款）必须键控；批量操作按子项幂等。
- 追问钩子：为什么「唯一约束」优于「先查后插」的幂等检查——先查后插在并发下有竞态（两个请求同时查都「不存在」然后都插入）；唯一约束是存储层的原子判定（并发插入只有一个成功）——把幂等下沉到存储层，并发正确性由数据库保证而非应用逻辑。

```javascript
// 唯一约束幂等（并发安全）
try {
  await db.insert('payments', { idemKey, ...payload });   // 唯一索引 idem_key
  return { status: 'CREATED' };
} catch (e) {
  if (e.code === '23505') {                               // 重复：返回原结果
    const prior = await db.query('SELECT * FROM payments WHERE idem_key=$1', [idemKey]);
    return { status: 'DUPLICATE', result: prior };
  }
  throw e;
}
```

## 边界与易错（补充）

**边界与易错**：

- 幂等键要在进入业务逻辑之前先落库占位（状态 PROCESSING）。只做「先查后插」，两个并发请求会同时查到「不存在」，然后都往下走。
- 唯一冲突后的回查要在能读己之写的会话里。主从延迟下查不到刚插入的那行，会被当成失败并触发客户端重试，等于幂等失效。
- 幂等键 TTL 必须长于客户端最大重试窗口。过期后同一个 key 重放会真的执行第二次，扣款这类操作要把 TTL 设到覆盖人工补单周期。
