## TST-053：测试金字塔是什么？前端场景下怎么落地？
**答**：
- 经典模型：底层大量单测（快、稳、便宜）→ 中层集成/接口测试 → 顶层少量 E2E（慢、脆、贵），越往上数量越少、维护成本越高。
- 前端适配（「奖杯」模型）：UI 逻辑大多在组件层，Testing Library 组件测试承担大头（挂载真实渲染、mock 外部依赖）；纯逻辑（utils/store/hook）走纯单测；少量 E2E 走关键路径。
- 反面是「沙漏/冰淇淋」：几乎全靠 E2E 兜底——跑得慢、flaky 高、反馈在 CI 尾部，定位要人肉排查。
- 落地比例参考：单测/组件测试 70%+、集成与 MSW 接口测试 20%、E2E <10% 且只覆盖核心转化路径（登录、下单、支付）。
- 追问钩子：比例不是硬指标，约束的是「问题在哪一层暴露」——能在单测暴露的逻辑不要漏到 E2E 才发现。

```javascript
// 分层示例：同一个「下单」能力的三层测试
// ① 单测：金额计算纯函数
expect(calcTotal([{ price: 100, qty: 2 }], 0.9)).toBe(180);
// ② 组件测试（奖杯中层）：OrderButton 渲染与点击行为
render(<OrderButton disabled={stock === 0} onBuy={spy} />);
await user.click(screen.getByRole('button'));
expect(spy).toHaveBeenCalled();
// ③ E2E：完整下单转化路径（少量）
await page.goto('/product/1');
await page.getByRole('button', { name: '立即购买' }).click();
await expect(page).toHaveURL(/\/pay\/\d+/);
```
