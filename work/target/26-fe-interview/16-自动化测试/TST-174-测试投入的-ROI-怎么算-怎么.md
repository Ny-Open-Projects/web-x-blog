## TST-174：测试的 ROI 怎么算？怎么向团队/老板证明投入值得？
**答**：
- 成本侧（可量化）：编写工时（用例数 × 单条成本）、维护工时（每次改版需更新的用例数）、CI 资源与时长、flaky 处理时间。收益侧：拦截的缺陷数（按线上事故成本折算）、回归人肉测试时间节省、发版提速（自动化代替两天回归）、可重构性带来的迭代速度。
- 说人话的三个指标：① 拦截率——测试抓住的 bug 数/总 bug 数（缺陷用例闭环统计）；② 回归成本对比——上线前人工回归从 2 人天降到 0.5 人天；③ 事故成本避免——按「线上 P1 事故 = X 工时 + 商业损失」折算被拦截的 N 个缺陷。
- 投入策略：不追求全覆盖，按风险排序投入——最近出过事故的链路、核心交易链路、高频改动模块先补；低风险静态页面用视觉回归/不做。这是「用 ROI 指挥测试投入」的正确姿势。
- 反面论证也要会说：过度测试的成本（维护拖慢迭代）、假测试的机会成本（写了一堆没抓住 bug 的）、覆盖率 vanity metric 的陷阱。
- 追问钩子：怎么持续证明？——季度复盘：本季测试拦截图、flaky/维护工时、投入产出比曲线，让数据进入团队 OKR。

```javascript
// ROI 简易模型（汇报用）
const roi = {
  cost: {
    writing: '120 条 × 0.5 人天 = 60 人天',
    maintain: '每季 10 人天',
    ci: '机器 2k/月',
  },
  benefit: {
    intercepted: '季度拦截 8 个 P1/P2，折算 32 人天 + 事故损失',
    regressionSaved: '上线回归 2 人天 → 0.2 人天，季度省 15 人天',
    refactorSpeed: '大重构 3 次零回归，节省返工 20 人天',
  },
  conclusion: '季度投入 ~75 人天，收益 ~67 人天 + 事故风险折价，年化 ROI > 2x',
};
```
