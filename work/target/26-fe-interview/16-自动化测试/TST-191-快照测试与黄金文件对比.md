## TST-191：快照测试的正确打开方式？黄金文件、内联快照与序列化定制
**答**：
- 快照的本质：把输出序列化成文本存盘（黄金文件），下次运行 diff——它是「特征测试」工具，验证「输出没变」，不验证「输出正确」。第一次生成时无人审查 = 把 bug 钉进基线。
- 适用的三个场景：错误信息格式（文案回归）、序列化结果（复杂对象结构）、大体积渲染产物（生成的配置/schema）。不适用的：高频改版的 UI 组件（天天 -u）、包含动态字段（时间戳/随机 id——必须先序列化清洗）。
- 内联快照（`toMatchInlineSnapshot`）：期望值写进测试代码里，review 一眼可见，适合小输出；外部文件快照适合大输出。团队规范：能用内联就用内联。
- 序列化定制（关键技巧）：`expect.addSnapshotSerializer` 把动态字段归一化——时间戳→`<TIMESTAMP>`、随机 id→`<ID>`，快照才稳定；React 组件用 `render` 的 HTML 输出时先清洗 class（CSS Modules hash）。
- 更新纪律：`-u` 更新快照必须出现在 PR diff 里被 review；CI 禁止自动更新；快照 diff 在 review 里要看内容而不是「无脑 approve」。
- 追问钩子：快照 vs 显式断言怎么配比？——关键行为显式断言为主，快照只做兜底防止「意外的额外变化」。

```javascript
// 序列化定制：清洗动态字段
expect.addSnapshotSerializer({
  test: (val) => typeof val === 'string' && /^\d{4}-\d{2}-\d{2}T/.test(val),
  print: () => '<TIMESTAMP>',
});

test('导出结构稳定', () => {
  const result = exportReport({ items: [...], generatedAt: new Date() });
  expect(result).toMatchInlineSnapshot(`
    {
      "items": [...],
      "generatedAt": "<TIMESTAMP>",   // 动态字段已归一化
    }
  `);
});

// React 组件快照：先清洗再存
test('卡片渲染', () => {
  const { container } = render(<GoodsCard name="x" />);
  expect(clearCssHash(container.innerHTML)).toMatchSnapshot();
});
```
