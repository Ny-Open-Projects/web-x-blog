## TST-170：发布门禁（质量卡点）怎么设计？哪些必须卡、哪些弹性放行？
**答**：
- 必须卡（硬门禁）：单测全绿 + 类型检查、增量覆盖率达标、E2E 冒烟全绿、无 `.only`/skip 未授权、构建产物大小预算不超。理由：快、稳、可解释，误杀率低。
- 弹性卡（软门禁/告警）：视觉回归 diff（允许 review 后放行）、a11y moderate 级、性能分数波动 10% 内、代码重复率。这类指标噪声大，一刀切会逼团队造假。
- 门禁分层到发布节奏：feature 合并 → PR 硬门禁；提测 → 硬门禁 + 每夜全集近 3 天趋势；上线 → 冒烟 + 灰度 RUM 观察窗口（错误率回滚阈值）；热修复 → 精简门禁（冒烟 + 相关域用例）但人工 sign-off。
- 卡点逃逸治理：门禁失败不能靠「跳过按钮」文化救——绕过必须走审批（记录 bypass 日志 + 事后补门禁证明），绕过率本身是监控指标。
- 追问钩子：门禁太多导致发版慢怎么办？——用并行化（门禁 job 并发跑）、受影响用例选择器、把慢而稳的门禁移到合并后而不是上线前。

```javascript
// 发布门禁聚合脚本（release-gate.mjs）
const checks = await Promise.all([
  run('npm run test:unit'),            // 硬
  run('node scripts/diff-coverage.mjs'), // 硬
  run('npx playwright test --grep @smoke'), // 硬
  run('node scripts/visual-check.mjs'),   // 软：失败可评审放行
  run('node scripts/budget-check.mjs'),   // 硬
]);
const hard = checks.filter((c) => c.hard && !c.ok);
const soft = checks.filter((c) => !c.hard && !c.ok);
console.log('HARD FAIL:', hard.map((c) => c.name));
console.log('SOFT (review needed):', soft.map((c) => c.name));
process.exit(hard.length ? 1 : 0);   // 软失败可带 --waive=jira-1234 放行
```
