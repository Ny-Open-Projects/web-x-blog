## TST-056：什么是脆弱测试？怎么提升测试的可维护性？
**答**：
- 脆弱测试定义：被测行为没变、只是实现细节变了（类名、DOM 结构、内部调用顺序），测试就红了。特征是「每次重构都要顺手改一堆测试」。
- 三大来源：① 断言实现细节（查询 className/组件树结构、spy 内部方法）；② 共享夹具被一个用例改坏传染全组；③ 环境噪音（时间、异步时序、随机数据）。
- 治理手段：优先可访问性查询（role/label 而非 class）；断言「用户可观察的结果」而不是内部状态；夹具工厂每用例独立；显式等待杜绝 sleep。
- 成本指标：一次业务改动（行为不变）导致的测试修改数量——理想接近 0，数量大说明测试绑死了实现。
- 追问钩子：可维护性比覆盖率更值钱——脆弱测试会训练团队「无脑 -u/无脑重试」，最终测试体系失信被废弃。

```javascript
// ❌ 脆弱写法：绑定实现细节
// expect(container.querySelector('.buy-btn--disabled')).toBeTruthy();
// expect(spyOn(orderModule, 'calcTotal')).toHaveBeenCalled();

// ✅ 稳定写法：绑定用户可观察行为
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('库存为 0 时购买按钮不可用', async () => {
  render(<ProductPage stock={0} />);
  const btn = screen.getByRole('button', { name: /立即购买/i });
  expect(btn).toBeDisabled();                      // 用户视角：点不了
  await userEvent.click(btn);                      // userEvent 会校验可交互性
  expect(screen.queryByText('订单已提交')).not.toBeInTheDocument();
});
// 重构 DOM 结构/class 命名时，这两条断言一行都不用改。
```
