## TST-168：前端稳定性体系里，自动化测试和线上监控怎么配合？
**答**：
- 分工：测试管「发布前的已知问题拦截」，监控管「发布后的未知问题发现」。测试挡不住的是：真实用户环境（机型/网络/灰度）、后端契约变更、数据边界——这些靠监控兜底。
- 闭环链路（这是面试的高分答案）：线上告警 → 归因定位 → **补一条回归用例**（缺陷→用例闭环）→ 下次同类问题被测试拦截。没有补用例的修复 = 修复不完整，纳入 PR 模板强制项。
- 监控侧输入反哺测试：错误上报的 Top 问题聚类 → 高频错误的场景进入用例库；性能 RUM 数据 → 调整性能预算基线；用户行为日志（rrweb 回放）→ 补充 E2E 场景。
- 发布节奏配合：测试通过 → 灰度 1% → RUM 指标对比基线（错误率/INP）→ 全量；灰度期间自动回滚阈值（JS 错误率 > 0.5%）+ 发布门禁联动。
- 追问钩子：监控误报多怎么办？——按版本/灰度维度聚合降噪、指纹去重、关键页面白名单，告警治理和 flaky 治理同构。

```javascript
// 闭环示例：线上错误 → 用例（PR 模板强制项）
/**
 * Bugfix: JIRA-1234 线上白屏（goods/1 页 item Optional chaining 缺失）
 * 根因: 接口 list 元素可能为 null，前端直接访问 item.name
 * 回归用例: TST-135 关联 — goods.spec.ts::空元素不崩溃并渲染兜底
 * 监控关联: 报警指纹 f=TypeError#goods
 */
test('接口返回 null 元素不崩溃', async () => {
  server.use(http.get('/api/goods', () =>
    HttpResponse.json({ list: [null, { id: 2, name: 'ok' }] })));
  render(<GoodsList />);
  await screen.findByText('ok');                    // 渲染有效项
  expect(screen.queryByText('undefined')).toBeNull();
});
```
