## TST-814：如何建立「测试设计评审」机制，让用例质量前移到写之前？
**答**：
- 结论：评审对象不是「代码」而是「测试设计」——在写用例前先评审场景覆盖、边界与断言策略，从源头避免无效用例。
- 评审清单：是否覆盖正常/异常/边界三类场景、断言是否验证行为而非实现、是否过度 mock、是否可被并行执行。
- 形式：高风险需求强制评审，低风险用模板自检；评审结论沉淀为「用例模式库」供复用。
- 度量：评审拦截率（评审阶段发现的设计缺陷 / 上线后发现的缺陷），用来证明评审的价值并持续优化。
- 追问钩子：评审增加了流程成本，团队抱怨「太慢」，你如何用数据证明它其实在提速？

```javascript
// 测试设计评审检查表驱动的自检器
const checklist = {
  hasHappyPath: '覆盖正常流程',
  hasEdgeCases: '覆盖边界值',
  hasErrorPath: '覆盖异常分支',
  assertsBehavior: '断言行为而非实现',
  minimalMock: '不过度 mock',
  parallelSafe: '可安全并行',
};
function reviewDesign(design) {
  return Object.entries(checklist)
    .filter(([k]) => !design[k])
    .map(([, desc]) => `缺失：${desc}`);
}
console.log(reviewDesign({ hasHappyPath: true, assertsBehavior: true,
  hasEdgeCases: true })); // ['缺失：覆盖异常分支', ...]
```

## 追问（补充）

**边界与易错**：

- `reviewDesign` 只查「有没有」不查「够不够」，`hasEdgeCases: true` 不代表真列了空值、0、负数、超长，评审必须要求附具体用例清单。
- `assertsBehavior` 是自评字段，评审要直接看断言代码，出现 `toHaveBeenCalledWith` 这类实现细节断言就应打回。
- `parallelSafe` 必须在评审阶段判定：依赖共享账号或共享 DB 记录的用例，事后改并行成本极高。

**追问**：

1. 评审增加了前置成本，怎么用数据证明它在提速 → 度量评审拦截率（评审期发现的设计缺陷 ÷ 上线后缺陷）与用例返工工时，对比评审前后的返工率与 flaky 率。
2. 高风险强制评审，「高风险」谁定标准 → 按变更影响面定：涉及资损、权限、核心链路、跨服务契约的自动进强制评审，其余走模板自检。
3. 评审流于形式、大家只点通过怎么办 → 评审产出必须落成可执行物（场景清单加断言清单），并抽检通过评审的用例上线后缺陷率，反馈到评审人。
