## TST-115：覆盖率门禁怎么定阈值？怎么避免「为覆盖率而测试」？
**答**：
- 阈值策略：不搞一刀切。分层定——纯逻辑模块（utils/hooks/store）80~90%、业务组件 60~70%、页面/样板代码不设或排除；用 vitest `coverage.thresholds` 的 glob 覆写按目录差异化。上线节奏：先设当前值 -5% 防倒退（ratchet 棘轮），逐步收紧到目标。
- 防刷分设计：① 看 diff coverage（只卡新增代码），不逼人补历史债；② thresholds 开 `perFile`，防止一个大文件高分拉平烂文件；③ 排除名单要评审（`coverage.exclude` 里塞太多 = 门禁形同虚设）；④ 配合变异测试抽查（见 TST-140），断言为空的测试骗不过 mutation score。
- 典型刷分行为与识别：只调不 assert 的 smoke test、`expect(true).toBe(true)`、为了覆盖把私有函数 export、把分支改成不可达。Review 时盯「测试是否真的在验证行为」。
- 工程化：门禁脚本输出增量覆盖率到 PR 评论，低于阈值 fail CI 并 @ 作者；历史豁免进 `.coveragerc` 式清单并标注到期时间。
- 追问钩子：leader 要求 100% 怎么办？——给出成本论证：从 80 到 100 的投入曲线陡增，最后 10% 多是 UI 样板与不可观测 glue code，性价比最低，用变异分数和缺陷率说话。

```javascript
// vitest.config.ts —— 分层阈值
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      include: ['src/**'],
      exclude: ['src/**/*.d.ts', 'src/main.tsx', 'src/types/**'],
      thresholds: {
        branches: 70, functions: 70, lines: 75, statements: 75,
        perFile: true,                                  // 不许互相拉平
        'src/utils/**': { branches: 85, lines: 90 },    // 逻辑层更严
        'src/pages/**': { branches: 0, lines: 0 },      // 样板层豁免
      },
    },
  },
});
```
