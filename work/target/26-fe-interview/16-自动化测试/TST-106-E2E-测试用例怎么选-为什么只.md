## TST-106：E2E 用例怎么选？为什么不能把单测场景全搬到 E2E？
**答**：
- 选例标准三条：① 用户核心链路（注册→登录→下单→支付）；② 跨页面/跨服务才能验证的集成点（token 传递、跳转、回单）；③ 回归成本高的关键功能（checkout、发布流程）。选的是「这条链断了业务就受伤」的路径。
- 为什么不全搬：E2E 单条成本 = 编写慢（10~20 倍于单测）+ 运行慢（分钟级）+ 维护贵（UI 一动就断）+ 定位难（失败原因可能是前后端任一层）。金字塔模型下 E2E 该是「薄而关键的一层」，数量上通常几十条封顶一个业务域。
- 边界划分：表单校验细节、状态机分支、纯函数逻辑 → 单测管；页面交互与渲染 → 组件测试管；E2E 只断言链路「走得通 + 关键节点正确」，不断言中间过程细节。
- 反模式：「E2E 全覆盖」论——追求行覆盖率的 E2E 会把团队拖死；「E2E 只冒烟」论——只测登录就漏掉了下单链路的集成回归。
- 追问钩子：怎么向 leader 论证 E2E 投入？——按「线上事故 × 链路关键度」排优先级，先补最近出过事故的链路。

```javascript
// 用例分级清单（白板可写）
const e2eSuite = {
  smoke: [ // 每次部署必跑，5 分钟内
    '首页可打开且商品接口 200',
    '登录 → 商品列表 → 加购 → 下单成功',
  ],
  critical: [ // 每日定时跑
    '支付回调后订单状态流转',
    '退款申请 → 审核 → 到账',
    '优惠券叠加计算（跨服务集成）',
  ],
  notE2E: [ // 交给单测/组件测试，不要写在这里
    '优惠券金额计算的 32 种组合', // → 单测参数化
    '表单每个字段的校验提示',      // → 组件测试
    '按钮 hover 样式',             // → 视觉回归/不测
  ],
};
```
