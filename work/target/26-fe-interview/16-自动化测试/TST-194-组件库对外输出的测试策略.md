## TST-194：组件库（对外输出）的测试策略和业务代码有什么不同？
**答**：
- 本质差异：业务组件面向「一个场景」，断言可以绑定业务语义；组件库面向「未知的使用者」，必须测试**公共 API 契约**——props 每个组合、受控/非受控双模式、事件回调参数、a11y 语义、SSR 兼容、可组合性（children/portal/ref 转发）。
- 必测清单（组件库特有）：① 受控与非受控两套（value + onChange / defaultValue）都要测；② 受控值变更被拒绝时 UI 回弹（controlled fallback）；③ ref 转发（forwardRef 拿到真实 DOM）；④ 事件参数完整性（event + data）；⑤ 键盘交互全集（见 TST-138）；⑥ theme/CSS 变量定制生效；⑦ SSR 渲染不出错（无 window 访问）；⑧ tree-shaking 副作用（import 不崩）。
- 兼容性测试：semver 语义——minor 版本发布跑「下游示例项目」集成测试（demo app 装 alpha 版跑 E2E）；破坏性 API 变更走 deprecation 预警（runtime warning + changelog）再在下个大版本移除。
- 文档即测试：每个 props 的每个值都有 story（TST-193）+ 至少一条断言；类型层面用 `expectTypeOf` 锁 API 形状（TST-024），类型破坏在编译期就拦住。
- 追问钩子：组件库测试的最大成本在哪？——组合爆炸（props 组合），解法是优先测交互协议而非穷举组合 + 属性测试生成参数组合（TST-190）。

```typescript
// 受控/非受控双模式契约测试
import { renderHook } from '@testing-library/react';
import { expectTypeOf } from 'vitest';
import { useCombobox } from './useCombobox';

test.each([
  ['uncontrolled', { defaultValue: 'a' }],
  ['controlled', { value: 'a', onChange: () => {} }],
] as const)('%s 模式：输入更新行为正确', async ([, props]) => {
  const { result } = renderHook(() => useCombobox(props));
  // 两种模式对外行为一致：输入更新后 open 且过滤
});

test('类型契约锁定', () => {
  expectTypeOf(useCombobox).parameter(0).toMatchTypeOf<{
    value?: string; defaultValue?: string; onChange?: (v: string) => void;
  }>();
});

// 事件参数完整性
test('onChange 携带 (value, event, meta)', () => {
  const onChange = vi.fn();
  // ... 触发选择
  expect(onChange).toHaveBeenCalledWith('a', expect.anything(),
    expect.objectContaining({ action: 'select' }));   // 组件库必须文档化 meta
});
```
