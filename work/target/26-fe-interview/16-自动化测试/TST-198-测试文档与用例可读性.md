## TST-198：测试文档和用例可读性怎么管理？半年后还能看懂的测试长什么样？
**答**：
- 核心理念：好测试自己就是文档——命名即文档（describe 业务域/it 行为描述「当 X 时应该 Y」），结构即文档（AAA 分段/ Given-When-Then 语义），失败信息即文档（断言消息带上下文）。文档孤岛（独立 wiki 里的测试说明）注定过期，可执行的测试不会。
- 可读性清单：① 用例名说业务不说技术（`提交超限时按钮禁用并提示` 而非 `test6`）；② 一个用例一条路径无分支；③ 魔法值有名字（`const OVER_LIMIT_COUNT = 100`）；④ helper 命名语义化（`givenLoggedInUser()`）；⑤ 断言失败可自解释（toBeVisible 的元素用 role+name 定位，报错自带语义）。
- 团队文档维护三件套：测试 README（怎么跑、目录约定、test-utils 用法）、门禁与豁免清单（哪些目录为什么豁免）、决策记录（ADR：为什么选 Playwright/为什么覆盖率 80%）——这些写进仓库随代码 review 更新，不放外网 wiki。
- 用例过载的信号与治理：测试文件超过 500 行 → 按子域拆 describe；重复 setup 三次以上 → 抽 helper；命名开始编号化 → 重写命名。
- 追问钩子：怎么让人愿意读测试？——review 时把测试当一等公民讲（PR 描述里写「本 PR 新增了哪些行为锁定」），测试在团队叙事里是资产不是负担。

```javascript
// 可读性对比
// ❌ 半年后看不懂
test('test_003', () => {
  const d = getData(2);
  expect(d).toBe(4);
});

// ✅ 自文档化
describe('优惠券叠加规则', () => {
  const MAX_STACK = 2;                       // 最多可叠加 2 张券

  it('叠加超过上限时只生效前 2 张并提示', () => {
    const cart = givenCartWithItems({ price: 300 });
    const result = applyCoupons(cart, [coupon20, coupon10, coupon5]); // 3 张
    expect(result.discount).toBe(30);        // 20 + 10，第 3 张不生效
    expect(result.warnings).toContain('最多叠加 2 张优惠券');
  });
});
```
