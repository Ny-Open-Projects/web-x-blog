## TST-196：多浏览器与设备矩阵怎么取舍？Chrome-only 团队要不要测 Safari？
**答**：
- 数据先行：取用户量分布（埋点 UA 统计）——Safari iOS 占比 > 15% 就必须覆盖，< 2% 可降级为人工抽测。矩阵宽度 = 流量价值 × 兼容风险，不是「能测多少测多少」。
- 分级策略：Tier 1（全量 E2E）——桌面 Chrome/Edge + iOS Safari（iPhone 主流机型）+ Android Chrome；Tier 2（冒烟 + 视觉抽样）——Firefox、macOS Safari、低端 Android；Tier 3（人工/不测）——IE（若仍要求，走降级兼容方案而非测试覆盖）。
- 引擎思维省成本：Chromium 系（Chrome/Edge）测一个引擎级等价，Playwright 里 Edge 复用 chromium 测试；WebKit（Safari）必须真测——Safari 的已知坑多（date 解析、flex gap 旧版、100vh、::-webkit 前缀）。
- 设备矩阵按「分辨率 × 触摸能力 × 性能」抽代表：iPhone 小屏（SE）、iPhone 大屏、iPad、主流 Android（Pixel）、低端 Android（2GB 内存）——用 Playwright devices 描述文件组合，性能分级加 CPU throttle。
- 发布节奏区分：PR 只跑 Tier 1 单引擎（chromium 快）；每夜跑 Tier 1 全部；发布候选跑 Tier 2；Tier 3 季度抽测。矩阵成本和发布风险对齐。
- 追问钩子：Safari-only 的 bug 怎么进流程？——WebKit 引擎跑失败用例复现 + 特征快照，修复后把该场景固化为 WebKit 专属回归用例。

```javascript
// playwright.config.ts 分级矩阵
export default defineConfig({
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },      // PR
    { name: 'ios-safari', use: { ...devices['iPhone 14'] } },         // nightly
    { name: 'firefox', testMatch: /smoke/, use: { ...devices['Desktop Firefox'] } }, // smoke only
    { name: 'low-end-android', testMatch: /smoke/,
      use: { ...devices['Pixel 5'], cpuThrottle: 4 } },               // 低端机模拟
  ],
});
```
