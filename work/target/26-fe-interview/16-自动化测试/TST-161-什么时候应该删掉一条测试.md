## TST-161：什么时候应该删掉一条测试？测试的退役标准是什么？
**答**：
- 该删的四类：① 验证的需求已下线（功能不存在了，测试只是维护负担）；② 重复覆盖（同一行为已有更快更稳的用例，这条是历史叠加产物）；③ 假测试（永真断言、只测三方库、mock 了被测逻辑本身——它们通过率 100% 但保护力为 0）；④ 维护成本远超保护价值（每改版必改的 UI 细节快照）。
- 判断框架：问三个问题——这条测试过去一年抓住了 bug 吗？它挂的时候是真的坏了还是环境/时序抖动？删掉后 PR 里再出对应回归谁兜底？前两个答案为否、第三个有人接住，就可以删。
- 为什么「删」难：团队心理账户认为测试越多越好、删测试像是在偷工减料。对策是把「测试资产盘点」常态化——每季度评审 skip 清单、最慢 Top10、flaky Top10，三张榜单就是退役候选名单。
- 替代优于删除：有些测试不该删但该降级——全集移到每夜、E2E 改单测、快照改关键断言、重量级改成契约断言。
- 追问钩子：删测试要不要 review？——要，而且和写测试同级别对待，PR 里单独说明删除理由，形成「测试变更可见」的文化。

```javascript
// 测试退役评估表（季度盘点用）
const retireCheck = [
  { q: '对应功能/需求是否已下线', yes: '删' },
  { q: '行为是否已被更快的用例覆盖', yes: '删（保留更优的那条）' },
  { q: '是否为假测试（永真/mock 被测逻辑）', yes: '删或重写' },
  { q: '过去 12 个月是否抓到过 bug', no: '进入退役候选' },
  { q: '是否频繁因环境/时序误报', yes: '降级：移出 PR 门禁进每夜' },
  { q: '维护成本（改版必改）是否超过保护价值', yes: '降级或重写' },
];
```
