## TST-999：门禁放行了却出事，怎么建立「事后验证」闭环来修正门禁而不是事后甩锅？
**答**：
- 结论：每次发布后回填「实际质量结果」——线上缺陷、回滚、SLO 异常，与当时的门禁判定对照；漏放的案例进入「门禁误判库」驱动阈值与信号调整。
- 做法：计算门禁的「漏放率」与「误拦率」作为门禁自身的质量指标；定期复盘误判样本。
- 价值：让门禁自己也在持续测试与进化，而不是一成不变的教条。
- 追问钩子：门禁连续 3 次拦住了其实安全的发布，研发开始绕流程，你怎么用数据修复门禁信誉？

```javascript
function postReleaseReview({ decisions, outcomes }) {
  let missed = 0, falseAlarm = 0, correct = 0;
  for (const d of decisions) {
    const bad = outcomes[d.releaseId]?.defect || outcomes[d.releaseId]?.rollback;
    if (d.passed && bad) missed++;          // 漏放
    else if (!d.passed && !bad) falseAlarm++; // 误拦
    else correct++;
  }
  const total = decisions.length || 1;
  return {
    missRate: +(missed / total).toFixed(2),
    falseAlarmRate: +(falseAlarm / total).toFixed(2),
    advice: falseAlarm / total > 0.2
      ? '误拦过高：放宽阈值或降权相关信号，修复门禁信誉'
      : missed / total > 0.05 ? '漏放过高：收紧关键信号' : '门禁健康',
  };
}
console.log(postReleaseReview({
  decisions: [{ releaseId: 'r1', passed: true }, { releaseId: 'r2', passed: false }],
  outcomes: { r1: { defect: true }, r2: { defect: false } },
}).advice); // '误拦过高：放宽阈值或降权相关信号，修复门禁信誉'
```
