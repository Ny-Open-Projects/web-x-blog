## TST-171：「缺陷 → 用例」闭环怎么做？为什么 bugfix 必须带回归用例？
**答**：
- 闭环流程：线上缺陷 → 复现并写成失败的测试（先红）→ 修复代码（变绿）→ 用例与修复同一 PR 合入 → 用例元数据记录缺陷单号。先写测试的价值：证明 bug 真实存在、证明修复有效、防止将来回归（这是自动化测试存在的根本理由）。
- 强制机制：PR 模板里 bugfix 类型必须填「回归用例路径」字段，review 第一项检查；漏填的 PR 不予合并。例外走审批（无法自动化的 UI 视觉问题，补视觉回归基线或人工测试记录）。
- 用例元数据：`test('JIRA-1234: ...')` 命名带上缺陷单号，或 Playwright annotations（`test.info().annotations.push({ type: 'issue', description: 'JIRA-1234' })`），后续看板能统计「每条用例抓住过几次回归」——这是评估测试价值的硬指标。
- 数据反馈：缺陷用例覆盖率高 = 用例库质量高；某模块线上 bug 多而用例少 = 补测优先级最高。把「线上事故分布 × 用例密度」做成热力图指导测试投入。
- 追问钩子：时间不够时 bugfix 不补测试怎么办？——宁可不修也不裸修，裸修等于把同一个 bug 留给了未来的自己。

```javascript
// Playwright：缺陷关联 annotation
import { test, expect } from '@playwright/test';

test('列表页空元素不崩溃（JIRA-1234）', async ({ page }) => {
  test.info().annotations.push({
    type: 'issue', description: 'https://jira.example.com/browse/JIRA-1234',
  });
  // 先红后绿的复现步骤：接口返回 list 里混入 null
  await page.route('**/api/goods', (route) => route.fulfill({
    json: { list: [null, { id: 2, name: 'ok' }] },
  }));
  await page.goto('/goods');
  await expect(page.getByText('ok')).toBeVisible();      // 有效项正常渲染
  await expect(page.getByText('undefined')).toHaveCount(0); // 不渲染脏数据
});
```
