## TST-188：TDD 在前端可行吗？哪些场景适合、哪些不适合？
**答**：
- 结论：逻辑层非常适合（红→绿→重构循环天然成立），UI 视觉层不适合（视觉是「看到才知道对不对」的探索过程），交互流程半适合（行为明确时先写用例是优势）。
- 适合的场景：纯函数（格式化/校验/计算——需求即输入输出规格，先写测试就是先明确规格）；hooks 状态机（useCart 的增删逻辑）；表单校验规则；工具库/API client（输入输出契约清晰）。TDD 的真实收益不是「测试覆盖率」而是**逼你先想清楚接口设计**。
- 不适合的场景：像素级 UI 调整（样式先写了测试也是猜）、探索型需求（产品自己也说不清要什么，先写测试锁死想象）、一次性脚本。折中方案：UI 探索完后再补测试（测试后置但不缺位）。
- 前端 TDD 的实践变体：① ATDD——从验收标准出发写用例骨架；② 半步 TDD——先写测试签名（it 描述）不写断言体，作为任务清单；③ 循环里用 watch 模式（vitest watch）保持秒级反馈，反馈慢是 TDD 失败的第一原因。
- 追问钩子：怎么向团队推 TDD？——不推「主义」，推「先写 it 描述」这个最小习惯，成本低收益立现，团队尝到甜头自然深化。

```javascript
// TDD 循环示例：优惠券计算
// RED：先写失败的测试（此时函数不存在）
test('满 100 减 20，叠加 VIP 9 折', () => {
  expect(coupon({ price: 150, vip: true, rule: 'full100cut20' })).toBe(117);
  expect(coupon({ price: 99,  vip: true, rule: 'full100cut20' })).toBe(89.1); // 未满门槛不叠加
});
// GREEN：最小实现
// REFACTOR：提取 isEligible / applyVip 纯函数，测试保持绿

// 半步 TDD：任务清单即测试签名
describe('购物车 checkout', () => {
  it('空购物车禁止结算');        // 先只写描述，实现时补断言
  it('库存不足的 SKU 提示并排除');
  it('地址未选择时阻止跳转');
});
```
