## TST-060：单测设计方法论总结：面试官问「你怎么设计测试」怎么答？
**答**：
- 第一层（分层定位）：先问自己这个逻辑值得哪层测试——纯逻辑单测、组件行为测试（RTL）、还是关键路径 E2E；默认金字塔比例，逻辑能单测就不上 E2E。
- 第二层（用例设计）：等价类 + 边界值列输入域（正常/空/0/负/极大/非法/并发重复），错误分支与状态机转移逐条覆盖；用 it.each 表驱动落地。
- 第三层（解耦设计）：纯函数优先、依赖注入、mock 只打进程外边界；测行为不测实现，用「重写实现测试是否仍绿」自检。
- 第四层（工程化）：夹具工厂统一造数据、AAA 结构与命名规范、覆盖率变更门禁、flaky 记录与治理闭环。
- 收尾话术：补一个真实案例（如金额计算边界浮点坑、重构时测试网拦住回归），证明方法论来自实战而非背书。

```javascript
// 「设计测试」的现场白板框架（可以直接讲）
function designTest(feature) {
  return {
    layer: pickLayer(feature),            // 单测/组件/E2E
    cases: equivalenceClasses(feature)    // 正常/边界/非法/并发
      .concat(errorBranches(feature)),    // 失败分支与状态转移
    isolation: pureFirst(feature),        // 依赖注入 + mock 外部边界
    shape: 'AAA + 行为级断言 + 表驱动',
    guard: ['变更覆盖率门禁', 'flaky 清单', 'only 禁止'],
  };
}
// 答题顺序：分层 → 用例域 → 解耦 → 规范 → 案例。
```

**边界与易错**：

- 只写正常路径加一个异常：漏掉空数组、0、负数、极大值、并发重复提交，而这些正是线上事故来源。
- 断言写在实现细节上（内部方法调用几次）：一重构就红，测试变成改代码的阻力，应断言输出与可观察副作用。
- 用 `it.only` 或没固定时间和随机：本地绿、CI 红，或者整片用例被静默跳过没人发现。

**追问**：

1. 覆盖率 80% 就算测好了吗？→ 覆盖率只证明「跑过」，要看变更覆盖率与分支覆盖，关键是断言是否有效。
2. mock 用太多说明什么？→ 说明模块耦合重、边界不清；mock 只该出现在进程外依赖，内部模块靠依赖注入替掉。
3. flaky 用例怎么处理？→ 先隔离进清单不阻断主干，定位是时序、共享状态还是网络，修复或删除，禁止用 retry 长期掩盖。
