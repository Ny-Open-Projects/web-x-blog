## TST-195：测试执行的资源成本怎么优化？并发、缓存与云设备的取舍
**答**：
- 成本构成：CI 机器时长（E2E 大头——浏览器实例 + 真实环境）、E2E 机器规格（内存 4G+/并发 worker）、云真机/云浏览器按分钟计费、视觉回归的存储（基线图）与计算（像素 diff）。
- 优化顺序（先免后省）：① 不跑不必要的测试——受影响用例选择器、PR 只冒烟、结果缓存（turbo 按 hash 缓存单测：源码没变不重跑）；② 并发提密度——同机器多 worker、sharding 按机器数；③ 复用基建——BrowserContext 复用、storageState 免登录、Docker 层缓存浏览器二进制；④ 降级资源——本地开发用 chromium 单引擎，CI 全矩阵只留给发布前检查。
- 云设备策略：模拟器（Playwright devices）覆盖 90% 兼容性测试，云真机只留给「模拟器测不了的」（性能、摄像头、真实 WebView）核心链路——真机按分钟计费，用例必须精挑。
- 度量闭环：CI 时长趋势监控（单次 PR 测试时长、每夜总时长）、单位用例平均耗时、机器利用率——测试成本也当产品指标管。
- 追问钩子：并行度拉高反而变慢（资源争抢）怎么办？——找到机器规格的甜点位（worker 数 ≈ CPU 核数），E2E 浏览器内存是瓶颈时按内存配 worker。

```javascript
// 成本优化清单（可执行）
const costOps = {
  avoid: [
    'turbo run test --filter=...[origin/main]   // 只跑受影响包',
    'vitest 缓存 + playwright shard 按需',
    'PR 只跑 @smoke，全集每夜',
  ],
  reuse: [
    'storageState 登录态复用（省每条用例 5~10s）',
    'Docker 缓存 playwright 浏览器镜像',
    'route.abort() 拦截埋点/字体/广告',
  ],
  downgrade: [
    '本地单引擎 chromium；CI 三引擎留给 nightly',
    '云真机只跑核心链路 10 条',
  ],
};
```
