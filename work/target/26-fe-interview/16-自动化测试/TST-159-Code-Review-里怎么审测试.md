## TST-159：Code Review 里怎么审测试代码？一份可执行的 checklist
**答**：
- 先看「有没有」：新功能/新分支（if-else 新路径、新交互）是否都有对应用例；bugfix 是否附带复现该 bug 的回归用例（缺陷→用例闭环）。
- 再看「对不对」：断言的是行为还是实现（断言用户可见结果优先）；mock 是否只收敛在网络/时间/随机；选择器是否 role/testid 而非 CSS class；有无 sleep、有无可控时序（fake timers/条件等待）。
- 再看「稳不稳」：数据是否自造自清（唯一前缀、teardown）；是否依赖执行顺序/共享可变状态；随机与时间是否可控；失败信息能否独立定位（断言消息带上下文）。
- 最后看「值不值」：测试长度与被测代码比例是否失衡（测试比实现长 3 倍 = 信号）；是否在测三方库；快照是否新增且无人看。
- 反提问技巧：review 时常问三个问题——「这条测试挂了说明什么坏了？」「这条测试过了能保证什么？」「删掉实现里这行，这条会挂吗？」（会挂 = 测到位，不会挂 = 假测试）。

```javascript
// Review checklist（可贴进 PR 模板）
const reviewChecklist = [
  '新逻辑每个分支都有用例？bugfix 带回归用例？',
  '断言用户可见行为，而非内部实现/渲染次数？',
  'mock 只在网络/时间/随机/三方边界？没有 mock 被测逻辑？',
  '无 sleep，异步用条件等待/fake timers？',
  '数据自造自清，无顺序依赖？随机/时间可控？',
  '测试失败信息可独立定位？',
  '没有为了覆盖率写的空断言用例？',
];
```
