## TST-114：覆盖率的行/分支/函数/语句指标分别说明什么？哪个最有价值？
**答**：
- 行/语句覆盖：每行代码是否执行过。最常用也最容易刷——一个 if 分支只测 true 时，行覆盖可能已很高，但另一半逻辑根本没验证。
- 分支覆盖：每个判断的 true/false 都走到。最能暴露「漏测的 else」，是四类里信息量最高的；`v8 provider` 需开 `all: true` 才统计未加载文件的分支。
- 函数覆盖：每个函数是否被调用过。对前端意义主要是揪出「导出了但没人测的工具函数」。
- 组合解读技巧：行覆盖 90% 但分支覆盖 60% → 说明测试只走了 happy path，边界和异常全是盲区；行覆盖低但都是 UI 样板代码 → 说明该测的逻辑没抽出来。
- 最有价值的是**增量分支覆盖**（diff coverage）：新代码必须测，存量代码逐步治理——全员 100% 不现实，增量门禁可行。
- 追问钩子：覆盖率报告里 `1x, 0x, 2x` 前缀是什么？——Istanbul 的命中次数；`!` 是没走完的分支、`E` 是 else path。会读报告比会刷数字重要。

```javascript
// 覆盖率盲区示例：行覆盖 100%？分支覆盖 50%
function getLevel(score) {
  if (score >= 90) return 'A';      // 测了
  if (score >= 60) return 'B';      // 测了
  if (score > 0) return 'C';        // 测了
  return 'D';                       // 没测：score<=0 → 行覆盖仍 100%（return 行算覆盖）？
}
// 不对：最后一行没执行，行覆盖 75%。但换成：
const fmt = (n) => (n >= 0 ? `+${n}` : `${n}`); // 一行三元
// 只测 n>=0 时：行覆盖 100%，分支覆盖 50%，负数路径是盲区
// 结论：门禁必须同时看 branches，单独 lines 会被三元/短路骗过
```
