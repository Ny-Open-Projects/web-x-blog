## PER-904：如何设计一个前端性能平台？整体架构分层是怎样的

**答**：
- 采集层：SDK 埋点（web-vitals + 自定义指标）→ 上报网关（批量/压缩/重试）。
- 计算层：Flink/ClickHouse 做聚合，按 页面/版本/机型/地域/运营商 多维下钻，产出 P75/P90 分位。
- 应用层：看板、告警（burn-rate）、劣化归因（对比发版前基线）、实验分析。
- 治理层：性能预算登记、CI 门禁、豁免审批、专项任务流转，形成闭环。
- 追问点：为什么看 P75 而非均值（尾部用户体验代表真实满意度，Chrome 官方口径也是 P75）。

```javascript
// 平台核心数据模型：性能记录
interface PerfRecord {
  page: string;          // 页面标识
  buildId: string;       // 发版版本，用于新旧基线对比
  lcp: number; cls: number; inp: number; ttfb: number;
  deviceTier: 'low' | 'mid' | 'high';
  region: string; ts: number;
}
// 计算层按 (page, buildId, deviceTier) 分桶取 P75
// 平台侧 SQL（ClickHouse）示意：
// SELECT quantile(0.75)(lcp) FROM perf
//   WHERE page = ? AND buildId = ? GROUP BY deviceTier
```

**边界与易错**：

- 采集端要区分首屏、路由切换、交互三类场景，混在一起算 P75 会失真。
- 数据链路必须采样加聚合下推，原始明细全量入库的成本不可控。
- 要能区分指标劣化与样本结构漂移，机型或地域占比变化会伪造出劣化信号。

## 追问（补充）

**追问**：

1. 分层怎么划？ → 采集层、传输层、存储计算层、应用层，边界按变更频率切，避免一层改全域动。
2. 采集层要解决什么？ → 指标标准化、采样、离线补报与版本兼容，避免上游随意改口径。
3. 怎么支撑归因？ → 预留 trace 与资源瀑布的关联字段，否则只能看到数字看不到原因。
