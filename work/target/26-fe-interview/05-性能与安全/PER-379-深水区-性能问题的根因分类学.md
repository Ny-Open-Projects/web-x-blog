## PER-379：性能问题的根因分类学：把历史工单归类后能发现什么规律？

**答**：
- 为什么要分类学：治理到中期后，新工单的形态开始重复——把 200 个历史工单按根因归类，会发现 80% 的工单集中在 6~8 类根因上。按类投入（改基建/改规范）比逐个修的杠杆大得多。
- 典型分类（按频次降序的经验分布）：① 数据链路类（接口串行/大 payload/无缓存）≈ 28%；② 资源类（图片未优化/字体阻塞/render-blocking）≈ 22%；③ 主线程类（长任务/强制同步布局/大计算在主线程）≈ 18%；④ 三方脚本类 ≈ 12%；⑤ 配置类（CDN/缓存头/HTTP2 配置错误）≈ 10%；⑥ 框架反模式（不当 memo/无限渲染/泄漏）≈ 7%；⑦ 其他 ≈ 3%。
- 分类后的治理动作：①②类 → 基建化（BFF 聚合器、图片组件默认优化、统一字体方案）；③类 → 规范 + 工具（切片 util、lint 检测强制同步布局模式）；④类 → 网关与白名单；⑤类 → 巡检自动化；⑥类 → lint 规则与组件库约束。
- 复利效应：每类根因基建化后，同类新工单数量断崖下降——工单分布本身就是治理效果的度量（"老问题不再来"）。

```text
根因分类与治理杠杆（示例分布，按自家工单实际归类）：
数据链路 28% → BFF 聚合器 + 接口预算卡口       （基建后同类工单 -85%）
资源     22% → <Img> 组件 + 字体方案 + 关键CSS  （-90%）
主线程   18% → yieldToMain util + lint 检测     （-70%）
三方     12% → 网关白名单 + facade 模板          （-80%）
配置     10% → 自动巡检（PER-364/238 合并）      （-95%，纯机器活）
框架     7%  → lint 规则 + 组件库约束            （-60%）
度量方式：季度工单根因分布对比 —— "老问题不再来"是治理成色的直接证据
```
