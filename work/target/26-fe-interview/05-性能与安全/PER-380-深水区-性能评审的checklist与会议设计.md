## PER-380：新项目/新功能的性能评审怎么做？评审清单与会议设计？

**答**：
- 评审时机与分层：小改动（PR 级）走 CI 卡口自动评审；中型功能（新页面/新模块）走异步 checklist 评审（owner 填表，平台组抽查）；大型项目（新业务线/架构级）才开正式会议——大多数问题不该开会。
- 大型评审 40 分钟议程：10min 方案介绍（架构图 + 预期流量/数据量）→ 15min 按清单逐项过（见下）→ 10min 挑战与风险（最坏情况推演：大流量/大列表/弱网/低端机）→ 5min 结论（通过/带条件通过/驳回 + 行动项）。
- 评审清单核心项：首屏预算方案、数据链路（接口数/串并行/缓存）、渲染方案（列表量级与虚拟化）、三方脚本清单、监控与 SLO 承诺、降级预案。
- 会议纪律：结论必须有行动项（谁/什么/何时）；性能评审不替代技术评审（重叠部分合并）；评审记录进案例库（好方案沉淀为模板，下次免评审）。

```text
性能评审 checklist（大型项目 40min 会议用）：
[ ] 首屏预算：预算表（体积/请求数/时间）已填写且 < 页面分层 SLO
[ ] 数据链路：接口清单、依赖图（无 >2 跳串行）、缓存策略
[ ] 渲染：列表数据量级预估、虚拟化方案、动画走合成器路径
[ ] 三方：脚本清单（域/体积/加载方式），全部走统一加载器
[ ] 监控：RUM 接入、SLO 承诺、告警 owner
[ ] 降级：弱网/低端机/配额满的降级路径
[ ] 边界：最坏情况推演（10 倍数据量/弱网 3G/低端安卓）
结论模板：通过 / 带条件通过（条件 + deadline）/ 驳回（理由 + 改法）
```
