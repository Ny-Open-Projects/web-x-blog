## PER-384：前端重试/离线重放机制背后的接口幂等设计：Idempotency-Key 的完整协议？

**答**：
- 为什么需要：前端重试（HW-063）与离线重放（PER-330）都会造成"同一操作发多次"——支付/下单/点赞没有幂等就是资损。幂等由服务端保证，前端负责正确传递键。
- 协议四要素：① 键生成——客户端 UUID，**同一次用户操作的重试与重放共享同一键**（入队时就生成并持久化，不是每次发送重新生成）；② 传递——请求头 `Idempotency-Key`；③ 服务端行为——首次执行并记录 键→结果；重放命中返回首次结果（200 + 原响应体，不是新执行）；进行中返回 409/425；④ 键生命周期——TTL（如 48h）后清理，超期同键视为新请求。
- 前端配套：入队时把键写进持久化队列（断电不丢）；冲突响应（409）按"已成功"处理（PER-330 的重放逻辑）；键与业务实体绑定（订单草稿 id）避免无谓随机。
- 测试：重放测试——同键发两次，断言响应一致且副作用只发生一次；并发同键（两个请求同时到）断言只有一个执行。

```javascript
// 前端：一次操作一个键，重试与重放共享
async function submitOrderWithRetry(draft) {
  const key = draft.idempotencyKey ?? crypto.randomUUID();     // 首次生成，持久化到草稿
  draft.idempotencyKey = key; saveDraft(draft);                 // 断电也不丢
  try {
    return await fetch('/api/order', { method: 'POST',
      headers: { 'Idempotency-Key': key, 'Content-Type': 'application/json' },
      body: JSON.stringify(draft) }).then((r) => r.json());
  } catch (e) {
    await offlineQueue.push({ url: '/api/order', body: draft, key });   // 重放复用同键
    throw e;
  }
}
// 服务端语义：首次 201；重放命中 200 + 首次响应体；并发同键 409（前端按成功处理）
// 测试：同键 ×2 断言副作用一次；并发同键断言单执行；48h 后同键 = 新请求
```
