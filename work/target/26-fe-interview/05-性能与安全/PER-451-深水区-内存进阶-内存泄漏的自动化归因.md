## PER-451：从"内存涨了"到"谁引用着它"的自动化 Retainer 分析？

**答**:
- 人工三快照（PER-264）的瓶颈：Retainer 链要人肉读。自动化思路：CI 中用固定泄漏场景脚本 + CDP（Chrome DevTools Protocol）的 HeapProfiler 拍快照，程序化解析 Retainer 链，输出"泄漏对象 → 引用链 → 归属模块"的结构化报告。
- 实现路径：CDP HeapProfiler.takeHeapSnapshot → 快照 JSON（节点+边）→ 图遍历：从增长对象出发反向找 GC 根路径 → 路径上标记模块归属（按 script URL 映射）→ 报告 Top 引用链与涉及模块排行。
- 判读规则自动化：Detached DOM + listener closure → "监听器未解绑"结论模板；Map 持有 + 模块级变量 → "全局缓存无上限"结论模板——把高频泄漏模式的判读规则固化，报告直接给修复建议。
- 与人工的关系：自动化覆盖常见模式（70%），复杂链（WeakRef 环/iframe 隔离）仍人工——自动化把"泄漏分析"从专家技能降为普通技能。

```text
自动化 Retainer 分析（CI 泄漏冒烟）：
场景脚本（打开/关闭弹窗 ×5）→ CDP HeapProfiler 快照 → Comparison（程序化 diff）
→ 对增长对象反向遍历引用链至 GC 根 → 按 script URL 标注归属模块
→ 结论模板匹配：
  Detached DOM + listener closure → "监听器未解绑"（给出组件名）
  Map + 模块级变量 → "全局缓存无上限"（给出缓存键）
输出：Top 引用链 + 模块排行 + 修复建议 —— PR 中直接可见
覆盖度：常见模式 ~70% 自动归因，复杂链人工兜底
```
