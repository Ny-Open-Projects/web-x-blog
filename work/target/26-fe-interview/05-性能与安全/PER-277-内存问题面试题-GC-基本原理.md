## PER-277：V8 的 GC（分代、增量标记）基本原理是什么？对前端优化有什么实际指导？

**答**：
- 分代假设：大多数对象朝生夕死。新生代（Scavenge 算法，半空间复制，快、频繁）、老生代（Mark-Compact 标记清除/整理，慢、偶发）。长命对象从新生代晋升到老生代。
- 停顿控制：老生代用**增量标记**（标记与 JS 交替执行）+ 并发标记（标记在后台线程）+ 三色标记法（白灰黑，灰色屏障处理并发期间的引用变更）；写屏障保证增量正确性。
- 对前端的实际指导：① 分配压力控制（少创建大临时对象，减少 Scavenge 频率）；② 长命对象尽早"定型"（避免反复在新生代/老生代间拷贝——其实晋升单向，重点是别让大对象进老生代后又马上死）；③ 大数组用 typed array（非指针密集，标记成本低且可 transfer）；④ GC 造成的偶发 longtask 是正常的，别把它误归因为业务代码慢（看 Performance 面板的 GC 标记）。
- 面试表达：能画"新生代/老生代 + 三色标记 + 写屏障"的图，并落到"为什么少分配 = 少 GC = INP 更稳"。

```text
V8 GC 心智模型：
new obj → 新生代（Semi-space）→ 存活 2 次 Scavenge → 晋升老生代
Minor GC（Scavenge）：复制存活对象，几 ms，频繁 —— 分配猛就频繁
Major GC（Mark-Sweep/Compact）：三色标记 + 写屏障 + 增量/并发，几十 ms —— 泄漏/大堆就慢
前端启示：
  1. 事件路径上别 JSON.parse(JSON.stringify(big)) —— 每次分配几十 MB = Minor GC 风暴
  2. 常驻大缓存进老生代后别反复重建 —— 稳定引用
  3. Performance 面板带 GC 标记的帧不算业务代码慢
```
