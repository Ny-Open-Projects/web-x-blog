## PER-313：引入一个新的 npm 依赖前，安全评审清单应该包含哪些项？

**答**：
- 身份与活跃度：包名精确核对（typosquatting 近似名攻击，如 `crossenv` 冒充 `cross-env`）；发布者与仓库归属、最近发布时间与下载量、维护者数量（单人包风险高）。
- 投毒信号：install 脚本（package.json 的 preinstall/postinstall 是否必要，尽量选无 install 脚本的包）；发布时间与版本节奏（一次性大量版本、深夜发布可疑）；CHANGELOG 与代码是否对应。
- 传递依赖体积：`npm view <pkg> dependencies` 看依赖树深度；`npm ls <pkg>` 模拟安装看总共引入多少包——前端要的是"零依赖"或浅依赖的包。
- 漏洞与许可：`npm audit`/OSV 查已知 CVE；license 兼容（GPL 传染性对商业代码）；`package-lock.json` 锁定 + 镜像源校验。
- 后续监控：依赖告警（Dependabot/Renovate + lockfile 审计进 CI）；新增依赖进 SBOM 清单（软件物料清单），漏洞通告时能反查"我们哪些项目用了它"。

```text
依赖引入评审清单（逐项）：
[ ] 包名逐字符核对（防 typosquatting），来源仓库与 npm 注册信息一致
[ ] 无 preinstall/postinstall 脚本（或有合理解释）
[ ] 维护活跃（<6 个月有更新）+ 多维护者 + 下载量正常
[ ] 依赖树浅（npm ls 模拟 < 10 个传递包）
[ ] npm audit / OSV 无高危；license 与公司合规兼容
[ ] lockfile 提交、CI 审计卡口开启、进 SBOM 清单
[ ] 版本固定（~ 而非 ^ 对安全敏感包），升级走评审
```
