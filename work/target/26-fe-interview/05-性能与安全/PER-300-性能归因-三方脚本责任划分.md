## PER-300：性能归因到三方脚本后，如何与三方团队/供应商扯清楚责任并推动修复？

**答**：
- 证据链三件套：LoAF invoker 归因（脚本 URL + 函数名 + 阻塞时长）、加载瀑布（该脚本发现延迟/下载时长/是否阻塞渲染）、体积与请求清单。把"你的脚本让我的 INP 从 180ms 变 420ms"量化成数据，而不是"感觉很卡"。
- 责任划分框架：加载责任（脚本自身体积/是否同步加载）与运行时责任（是否全局监听事件、是否同步计算）分开；再分"我们能改的"（加载方式：defer/idle/facade/worker 化，我方主导）与"对方必须改的"（SDK 内部实现，如高频事件监听、同步 localStorage 读写）。
- 推动手段：接入合同里写性能条款（SDK gzip ≤ X KB、主线程阻塞 ≤ X ms/页面）；季度性能评审给供应商排名；内部一方"三方"（公司内其他团队）用同样的工具链出具报告，权威性靠统一口径。
- 无法推动时的自保：wrapper 隔离——对三方 SDK 做超时熔断、失败降级（不阻塞业务）、事件监听器节流包装（拦截其 addEventListener 调用做 passive+throttle）。

```javascript
// Wrapper 隔离示例：拦截三方 SDK 的全局监听，强制 passive + 节流
const origAdd = EventTarget.prototype.addEventListener;
EventTarget.prototype.addEventListener = function (type, fn, opts) {
  const highFreq = ['scroll', 'touchmove', 'pointermove', 'wheel'].includes(type);
  if (highFreq && this === window) {                 // 三方高频监听 → 节流包装
    let last = 0;
    return origAdd.call(this, type, (e) => {
      const now = performance.now();
      if (now - last < 100) return;
      last = now; fn(e);
    }, { ...(typeof opts === 'object' ? opts : {}), passive: true });
  }
  return origAdd.call(this, type, fn, opts);
};
loadScript({ src: 'https://third.example/sdk.js', trigger: 'idle' });
// 配套：LoAF 报告持续归因，若包装后仍 >50ms 阻塞，出报告找供应商
```
