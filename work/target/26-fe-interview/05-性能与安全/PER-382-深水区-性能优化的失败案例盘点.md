## PER-382：性能优化的失败案例盘点：哪些"优化"反而让性能更差或引发事故？

**答**：
- 案例一：滥用 memo/useMemo——所有组件都包 memo，比较成本超过重渲染成本，且 props 每次新对象引用让 memo 全部失效（白包）。教训：memo 只加在"确认重渲染昂贵且 props 稳定"的地方，用 profile 验证收益。
- 案例二：过碎的切片——把 30ms 的任务切成 60 个 0.5ms 片，yield 调度成本让总耗时翻 3 倍。教训：切片预算 20~50ms（PER-283）。
- 案例三：无限 will-change——给整页元素加 will-change 提升层，合成层爆炸（内存 +400%、滚动掉帧）。教训：will-change 只给动画进行中的元素，结束移除。
- 案例四：SRI 上线未对齐发布时序——先传资源后切 HTML 的窗口期全站脚本校验失败（PER-309）。教训：内容 hash 文件名 + CDN 探活后才切 HTML。
- 案例五：预取风暴——路由切换时预取全部可能页面的数据，弱网用户带宽被预取挤占，当前页反而更慢。教训：预取限流 + 命中率监控 + saveData 尊重。
- 共性教训：所有优化必须 before/after 同口径度量 + 灰度验证；"听起来对"不是证据。失败案例进案例库（与成功案例同等价值——反面模式让新人少踩坑）。

```text
失败案例清单（反面模式 → 正确做法）：
全员 memo          → profile 定位昂贵渲染再 memo（验证 props 引用稳定性）
切片过碎(<5ms)     → 单片预算 20~50ms（PER-283）
无限 will-change   → 动画进行时才提升，结束移除
SRI 时序错配       → 内容 hash 文件名 + CDN 探活后切 HTML（PER-309）
预取风暴           → 限流 + 命中率监控 + saveData 尊重（PER-326）
共性纪律：before/after 同口径 + 灰度验证 —— "听起来对"不是证据
```
