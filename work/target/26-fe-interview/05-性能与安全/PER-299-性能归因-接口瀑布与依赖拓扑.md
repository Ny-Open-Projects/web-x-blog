## PER-299：页面有十几个接口，如何归因"接口瀑布"（串行依赖）并优化？

**答**：
- 还原拓扑：Network 面板按 Waterfall 看 start time——接口 B 的发起时间 > 接口 A 的完成时间且 B 的参数来自 A，即串行依赖。代码层更快：搜调用点，"then 里发下一个请求"或"await 链"就是依赖边。
- 量化瀑布代价：总时长 = 关键路径上接口耗时之和（不是所有接口之和）。把依赖图画出来，找出关键路径（最长链），关键路径上的串行跳数就是要优化的对象。
- 优化手段：① 无依赖的接口并行化（Promise.all / BFF 聚合，见 OPT-020）；② 伪依赖拆解——B 只用 A 的部分字段时，让 A 一次返回两个接口需要的字段或提前下发公共字段；③ 预取——用户进入上一页时预取下一页首屏接口；④ 流式——首个接口返回后先渲染骨架对应区块，后续接口完成增量渲染（不等待全部）。
- 前端职责边界：能改 BFF 的改 BFF（服务端并行，省一次 RTT 与浏览器调度），改不了的前端并行化 + 预取；关键路径每砍一跳约省一个 RTT + 接口耗时。

```javascript
// 伪依赖拆解示例：详情页只要 goods.sellerId，却等整个 /api/goods
// 反例（瀑布）：
const goods = await fetch('/api/goods/1').then(r => r.json());      // 300ms
const seller = await fetch(`/api/seller/${goods.sellerId}`);        // 200ms —— 串行
// 优化一：字段提前（BFF 在 goods 响应头/首字段返回 sellerId）
// 优化二：服务端聚合：/api/composite?goods=1 一次返回 goods+seller（BFF 并行调两个下游）
// 优化三：前端并行+容错（sellerId 可从路由参数兜底）：
const goodsP = fetch('/api/goods/1');
const sellerP = fetch(`/api/seller/${routeSellerId}`).catch(() => null);   // 不等 goods
const [goods, seller] = await Promise.all([goodsP, sellerP]);             // 300ms 内完成
// 渲染不等待：goods 到了先渲染，seller 到了增量填充
```
