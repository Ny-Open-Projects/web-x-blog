## PER-499：平台 API 的向后兼容演进？

**答**:
- 演进纪律：① 版本化（/v1 冻结——只修 bug 不改语义；新能力 /v2）——消费方按自己节奏迁移；② 字段只增不删（删除字段必须先标 deprecated 一个版本周期 + 使用方普查）；③ 语义变更走新端点（verdict 的含义变化不能原地改——发布系统的自动化契约会瞬间失义 PER-422）；④ 兼容层——旧字段映射到新模型（服务端适配而不是要求所有消费方同步改）。
- 消费方管理：API 使用方登记（PER-474 能力目录）——字段删除前的使用方普查有数据依据；废弃公告（时间表 + 迁移指南 + 双跑期）。
- 内部 API 的特殊性：内部平台 API 容易"反正都是自己人直接改"——历史教训是改一次破坏一次发布流水线；纪律与对外 API 同标准（内部消费方更多且更脆弱——发布流水线坏了影响所有人）。

```text
平台 API 演进纪律：
/v1 冻结只修 bug；新能力 /v2
字段只增不删；删除先 deprecated + 使用方普查（PER-474 登记）
语义变更走新端点（verdict 含义变化 = 发布契约失义 PER-422）
兼容层：服务端适配旧字段，消费方异步迁移
内部 API 同对外标准 —— 内部消费方（发布流水线）更多更脆弱
```
