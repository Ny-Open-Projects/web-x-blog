## PER-388：灰度发布下的缓存一致性：新旧版本共存时如何避免混版渲染？

**答**：
- 混版形态：灰度期间用户可能拿到"新 HTML + 旧 chunk"或"旧 HTML + 新接口响应"——组件结构与新数据 schema 不匹配导致渲染崩溃或样式错乱。混版是灰度发布的最大稳定性风险。
- 三层对齐机制：① HTML 与静态资源——内容 hash 文件名让每个版本的资源独立存在，HTML 引用永远自洽（新旧 HTML 各自指向自己的资源集，不存在共享冲突）；② HTML 与接口——接口 schema 变更必须向后兼容（新增字段不删字段；字段语义变更开新端点），或接口带版本头（X-Api-Version）按 HTML 版本路由；③ 本地缓存——SW 缓存按版本命名空间（cache-v25/），activate 时清旧版本（PER-329），禁止跨版本读缓存。
- 灰度用户一致性：灰度按用户/会话分桶（不是按请求随机），保证同一会话内版本稳定（PER-338 会话级一致）；灰度期间旧版本接口至少保留一个下线周期。
- 验证手段：混版监控——错误上报带版本号，出现"版本 A 的 JS 报版本 B 的错误"即混版实锤；灰度期错误率分版本看板。

```text
混版防线三层：
1. 静态资源：内容 hash 文件名 → 各版本资源集独立，HTML 自洽引用
2. 接口契约：向后兼容（只增不删）/ 版本头路由（X-Api-Version 按 HTML 版本）
3. 本地缓存：SW cache 按版本命名空间，activate 清旧版，禁止跨版本读
灰度分桶：按会话一致（非请求随机）；旧接口保留下线周期
监控：错误上报带版本号，版本错配错误 = 混版实锤 → 自动暂停放量
```
