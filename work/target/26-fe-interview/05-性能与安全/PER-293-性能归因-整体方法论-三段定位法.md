## PER-293：性能归因的整体方法论是什么？拿到"页面慢"如何系统化定位而不是瞎猜？

**答**：
- 第一步定"谁说慢"：RUM 分位数先看 p75/p98 与样本分布——是全量慢（系统性问题）还是长尾慢（特定设备/地域/版本），方向完全不同。全量慢查架构，长尾慢查兼容与弱网。
- 第二步定"哪个指标慢"：CWV 四指标 + 自定义业务指标逐个对照 SLO。LCP 慢查加载链路、INP 慢查主线程与渲染、CLS 慢查布局、TTFB 慢查网络与服务端。指标不同，工具链完全不同。
- 第三步定"哪一段慢"：把指标拆段——LCP 拆 TTFB/资源发现/加载/渲染四段；INP 拆 input delay/processing/presentation 三段。段拆解能直接指向修复手段，避免"整体优化"式盲改。
- 第四步定"谁背锅"：段内归因到资源（Resource Timing）、脚本（LoAF invoker）、接口（Server-Timing）、三方（按 URL 分组）。归因要落到"可指派的责任人"。
- 闭环：修复后同口径复测（实验室回归 + RUM 观察 7 天），确认指标回落才关闭。全程用数据说话，每一步结论都有证据字段支撑。

```text
归因决策树（示例：p75 LCP = 4.2s 超标）：
全量 or 长尾？ → 全量
拆段：TTFB 1.8s（大头）→ 资源发现 0.3s → 加载 1.2s → 渲染 0.9s
TTFB 1.8s → CDN 命中率 60% + 接口串行 → SSR 流式 + HTML 边缘缓存 + BFF 并行聚合
加载 1.2s → LCP 图 800KB PNG → AVIF + fetchpriority=high + 预载
渲染 0.9s → render-blocking CSS 120KB → 关键 CSS 内联
预期收益：1.8→0.4 + 1.2→0.3 + 0.9→0.2 ≈ LCP 2.5s 达标 —— 每项都有对应段与证据
```
