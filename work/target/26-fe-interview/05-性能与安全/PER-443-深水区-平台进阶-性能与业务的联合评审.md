## PER-443：需求评审阶段如何提前发现"性能不可行"的需求？

**答**:
- 为什么需求阶段介入：代码写完才发现"需求本身不可行"（数据量/交互密度超出预算）返工成本最高。联合评审让性能视角进入需求定义。
- 评审要点清单：① 数据量级——列表展示多少条（> 500 必须虚拟化方案、> 1 万必须分页/搜索化）；② 交互密度——多少个实时联动（联动图深度 > 3 层要拆）；③ 视觉方案——每屏多少动画元素（合成器路径可承载量）、每屏图片量；④ 三方依赖——新三方脚本数量与用途（能用自研轻量版吗）；⑤ 实时性——推送频率与 UI 更新耦合度。
- 结论输出：可行（预算内）/ 有条件可行（明确约束：如"列表 ≤ 200 条或上虚拟列表"）/ 不可行（需求降级方案：分页/搜索/按需加载）。约束写进 PRD——性能约束是需求的一部分不是技术附加。
- 案例：需求要"一页展示 5000 条库存明细" → 有条件可行：虚拟列表 + 服务端聚合预计算；"每行 5 个动画徽标" → 不可行全量动画：徽标动画只在视口内开启。

```text
需求联合评审清单（性能视角）：
数据量级：展示条数 → >500 必须虚拟化方案写进 PRD
交互密度：实时联动层数 → >3 层拆分或批处理
视觉方案：动画元素数 → 合成器路径承载评估
三方依赖：新增三方清单 → 自研替代评估
实时性：推送频率 × UI 更新耦合 → 批处理方案
结论：可行 / 有条件可行（约束写进 PRD）/ 不可行（需求降级方案）
案例：5000 条明细 → 虚拟列表+服务端聚合（约束进 PRD）—— 事后补救变事前设计
```
