## PER-273：频繁 GC（内存分配压力）如何拖慢交互？为什么说内存问题和 INP 相互放大？

**答**：
- GC 是主线程任务：Minor GC 频繁时每次几 ms 抢占主线程，Major GC（老生代标记）可达几十 ms——直接变成 longtask，吃掉 INP 的 input delay 预算。
- 分配压力的来源：高频 handler 里创建大临时对象（点击时 new 大数组、clone 深层结构）、频繁字符串拼接、每次渲染新建闭包/对象字面量。分配越猛，GC 越频繁。
- 相互放大的循环：内存泄漏 → 堆越大 → Major GC 标记越慢 → 交互延迟越差 → 用户多点几次 → 分配更多。所以内存治理同时就是 INP 治理。
- 优化手段：① handler 里复用对象/数组（池化），避免在事件路径上分配；② 大计算挪 Worker（GC 也隔离了）；③ 避免深拷贝（传引用/结构共享）；④ DevTools Memory 面板的 Allocation timeline 找分配热点（蓝色柱密 = 分配猛）。

```javascript
// 分配热点反例与优化对照
listEl.addEventListener('click', (e) => {
  const snapshot = JSON.parse(JSON.stringify(bigList));   // 每次点击深拷贝 10MB => GC 风暴
  render(snapshot.filter(x => x.active));                  // 又 filter 新数组
});
// 优化：不在事件路径上做大分配
const reusable = new Float64Array(cap);                      // 复用缓冲
listEl.addEventListener('click', (e) => {
  const id = e.target.dataset.id;
  // 直接引用 + 视图过滤，不复制数据
  renderView(bigList, id, reusable);
});
// 验证：Memory 面板 Allocation timeline，交互前后蓝色柱密度显著下降
```
