## MFW-684：generateStaticParams 的增量扩展

**答**:
- generateStaticParams 的增量扩展：1) **构建期清单**（RBL-535 diff：上次构建清单 + 本次新增——只渲染新增）；2) Next 的 generateStaticParams 是「每次全量」（构建时全渲染——增量清单无法直接接入）；3) 增量的正确姿势：generateStaticParams 只返回「核心集」（Top N——构建期预渲染）+ 其余 on-demand ISR（fallback: blocking——首访问渲染 RBL-509）；「全量 vs 核心+按需」的容量权衡。
- fallback 的语义：`fallback: 'blocking'`（首访问 SSR 渲染 + 缓存——后续命中缓存）；`fallback: false`（未预渲染 = 404）；`fallback: true`（首访问静态壳 + 流式数据）；blocking 的体验（首访问慢但完整——SEO 友好）。
- 增量清单的接入：generateStaticParams 内 diff（上次 manifest 的缓存读取——构建缓存 RBL-633 的预渲染维度）。
- 追问钩子：为什么「generateStaticParams 全量」在百万 SKU 场景不可行而「核心 + on-demand」可行？——全量 = 构建时长线性（100 万 × 200ms = 55 小时——CI 超时）；核心 + 按需 = 构建期 Top 1%（1000 页 × 200ms = 3 分钟）+ 长尾首访问渲染（用户访问才付成本）；「构建成本 vs 首访问成本」的分配：热点页预渲染（命中率高的预渲染）、长尾按需（访问率低的懒渲染）——与 CDN 缓存的流行度加权（RBL-599）同构。

```typescript
// 核心 + on-demand 的混合
export async function generateStaticParams() {
  // 只渲染 Top N（构建增量：diff 上次清单——新增 SKU 才渲染）
  const cached = await readBuildCache('prerendered.json');   // RBL-633
  const hotSkus = await db.products.hot(1000);
  const previous = new Set(cached?.rendered ?? []);
  return hotSkus
    .filter(s => !previous.has(s.id))                      // 增量：只渲染新增
    .map(s => ({ sku: s.id }));
}
export const dynamicParams = true;                         // 非预渲染的按需 ISR
// 长尾 SKU：首访问 blocking 渲染 + 缓存
// 请求 /p/999999 → SSR 渲染 → Full Route Cache → 后续命中
// 构建缓存（增量清单）
// .next/prerendered.json: { rendered: ['sku-1', 'sku-2', ...], hash: 'xxx' }
```
