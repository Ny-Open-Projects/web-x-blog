## MFW-701：大促首页动态洞粒度

**答**:
- 大促首页的渲染模式选择（RBL-620 决策树的应用）：1) 页面 95% 静态（活动海报/楼层结构/商品卡片——构建期预渲染）+ 5% 动态（个人优惠券/实时库存/倒计时——动态洞）；2) **PPR 的应用**：静态壳 CDN 缓存 + 动态洞流式——首屏 TTFB = 静态（CDN 命中即发）+ 洞流式；3) 动态洞的粒度（每洞一个独立数据源——优惠券 fetch/库存 fetch——洞粒度 = 数据粒度 RBL-655）。
- 洞粒度的优化：1) **洞合并**（多个小洞 → 一个边界（一次 fetch 一批数据——减少流式 patch 数 RBL-520）；2) 洞拆分（大洞拆小（长查询拆两个并行——先完成的先渲染 RBL-655）；3) 洞的优先级（LCP 洞浅层 RBL-520、非关键深层）。
- 大促的缓存策略：静态壳 immutable（大促页面结构稳定）；动态洞的 TTL（库存 5s/优惠券 0（每用户）/倒计时 client 计算——洞级缓存策略 RBL-526）。
- 追问钩子：为什么「动态洞合并」在大促场景是双刃剑？——合并 = 一次 fetch 一批（网络效率↑、patch 数↓）；但合并洞的粒度变粗（一个洞慢 = 整批延迟——最慢查询决定整批显示 RBL-585 瀑布的洞级版）；拆分 = 独立流式（快的先显示）但 patch 多（网络开销）；「合并 vs 拆分」的决策：数据源相同（同 DB 同查询）→ 合并（一次查询高效）；数据源不同（库存/优惠券/推荐）→ 拆分（独立流式互不阻塞）。

```tsx
// 大促首页的 PPR 结构
export const experimental_ppr = true;
export default function CampaignPage() {
  return (
    <>
      <Hero />                                            {/* 静态：构建期 */}
      <Suspense fallback={<CouponSkeleton />}>
        <UserCoupons />                                   {/* 动态洞：每用户 */}
      </Suspense>
      <Suspense fallback={<StockSkeleton />}>
        <RealtimeStock />                                 {/* 动态洞：实时库存 */}
      </Suspense>
      <Suspense fallback={null}>
        <Countdown endTime={CAMPAIGN_END} />              {/* client 计算：无 server */}
      </Suspense>
      <StaticFloors />                                    {/* 静态：商品卡片楼层 */}
    </>
  );
}
// 洞的缓存策略（RBL-526）
async function RealtimeStock() {
  const stock = await fetch('/api/stock', { next: { revalidate: 5 } });   // 5s
  return <StockBar items={stock} />;
}
// 洞合并 vs 拆分：数据源不同 → 拆分（独立流式）
```
