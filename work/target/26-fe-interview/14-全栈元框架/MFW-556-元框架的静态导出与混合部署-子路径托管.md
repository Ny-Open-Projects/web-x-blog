## MFW-556：静态导出与混合部署：basePath 产物改写

**答**:
- 静态导出部署到「现有服务的子路径」（example.com/app/——不是独立域）：basePath 配置 → 产物全量改写（内部 Link 自动加前缀/静态资源 URL 前缀/next/image 路径—— basePath 进入 RSC payload 与 manifest 全链路）。
- 混合部署的反向：SSR App 托管在子路径（网关 rewrite 转发 + basePath）——header 转发的陷阱（X-Forwarded-* 链——重定向/绝对 URL 需信任 forwarded 头；多层网关的 forwarded 链路污染）。
- basePath 与缓存键：路径含 basePath —— CDN 缓存键以完整 URL（含前缀）——同 App 不同 basePath 部署 = 独立缓存（各自失效）；跨 basePath 共享 chunk（不同 App 的相同 chunk URL 不同前缀 = 缓存不共享——CDN 缓存按完整 URL：跨 App 共享失效）。
- 追问钩子：为什么 basePath 的「全链路改写」容易漏（JSX 里的硬编码 URL/OG 图绝对 URL/sitemap）？——basePath 改写只覆盖「框架感知的 API」（Link/Image/router）；「框架不感知的 URL」（手写 <img src="/x.png">、OG metadata 绝对地址、第三方回调 URL）需手动——「框架边界外的逃逸面」是 basePath 事故的主因：审计方式 = 产物 grep 绝对路径（RBL-661 产物审计的具体项）。

```javascript
// basePath 配置
// next.config: { basePath: '/app' }
<Link href="/products">                                  // 自动 → /app/products
// 逃逸面审计（构建后产物扫描）
function auditBasePathEscape(dist, basePath) {
  const leaks = [];
  for (const f of dist.js) {
    for (const m of f.code.matchAll(/["'](\/(?!\/)[^"']*\.(?:png|jpg|js|css))["']/g)) {
      if (!m[1].startsWith(basePath) && !m[1].startsWith('/_next'))
        leaks.push({ file: f.name, url: m[1], detail: '硬编码路径缺 basePath 前缀' });
    }
  }
  return leaks;                                          // 非 _next 的绝对路径 = 逃逸嫌疑
}
// 反向：网关转发与 forwarded 链
export async function generateMetadata() {
  const proto = headers().get('x-forwarded-proto') ?? 'https';
  const host = headers().get('x-forwarded-host') ?? headers().get('host');
  return { metadataBase: new URL(`${proto}://${host}`) };   // OG 绝对 URL 的基准
}
```
