## MFW-632：多区域部署的路由与数据

**答**:
- 多区域路由的形态：1) **域分区**（us.app.com / eu.app.com——用户就近 DNS 解析；区域感知数据）；2) **路径分区**（/eu/**——单域路径分流）；3) **CDN 自动路由**（edge 函数全球——数据区按 req.cf.region）。区域路由 = 「用户与数据的地理匹配」。
- 数据分区的一致性难题：用户从 us 迁移到 eu（旅行）——他的数据在 us 区（主库）——「数据跟随 vs 数据固定」：固定主区（写回 us——跨区写延迟）vs 跟随迁移（数据迁移——一致性窗口）；「用户的主区」是账户属性（注册区）——读写路由：读可就近（副本）、写回主区（RBL-575 CQRS）。
- 跨区域复制的延迟容忍：读副本 lag（主从延迟秒级——刚写的数据副本没有——「写后读」的一致性：写后立即读走主区（sticky session——写后的 N 秒内路由主区））。
- 追问钩子：为什么「写后读一致性」是多区域架构的隐形杀手？——写回主区（us）→ 读走副本（eu 延迟 2s）→ 用户刚提交的订单不在列表（「我买了怎么没有」客诉）；解法：写后 cookie 标记（主区路由窗口——N 秒内所有读写走主区）；「一致性的时间窗口」与「路由策略」的联动：sticky 路由的成本（跨区 RTT）换一致性——写后读的一致性窗口是「用户可感知的一致性」的最低保证。

```typescript
// 区域路由 + 写后读 sticky
export async function middleware(req) {
  const userRegion = req.cf?.country ?? 'us';
  const region = REGIONS.includes(userRegion) ? userRegion : 'us';
  // 写后 sticky：最近写过 → 路由主区
  const sticky = req.cookies.get('recent-write');
  const target = sticky ? PRIMARY_REGION : region;
  const res = NextResponse.rewrite(new URL(req.nextUrl.pathname, req.url),
    { headers: { 'x-region': target } });
  return res;
}
// action 写后设置 sticky cookie
'use server';
export async function placeOrder(data) {
  await primaryDb.order.create(data);
  (await cookies()).set('recent-write', '1', { maxAge: 10 });   // 10s sticky
}
// 读路由：action 后 N 秒走主区（写后读一致）
export async function GET(req: Request) {
  const sticky = req.headers.get('cookie')?.includes('recent-write');
  const db = sticky ? primaryDb : replicaDb(getRegion(req));
  return NextResponse.json(await db.order.list());
}
```
