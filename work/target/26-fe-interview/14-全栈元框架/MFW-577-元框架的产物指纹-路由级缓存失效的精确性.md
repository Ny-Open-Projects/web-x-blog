## MFW-577：tag 设计与失效范围控制

**答**:
- tag 的设计粒度：1) **实体级**（product:123——单实体变更精确失效）；2) **集合级**（products——列表页失效）；3) **层级失效**（revalidateTag('product:123') 应同时失效列表（实体变了列表也旧）——tag 依赖图（tag → 父 tag）：失效传播 RBL-635 的缓存版）；4) tag 命名规范（`${entity}:${id}` / `${entity}:list`——规范让失效可推理）。
- 失效范围的错误设计：tag 过粗（'all'——任何变更全站失效：缓存全灭）；tag 过细（每个查询一个 tag——管理爆炸）；「tag 的粒度 = 失效范围 = 缓存收益的倒数」——粒度设计是缓存架构的核心决策。
- 失效的触发源映射：CMS webhook → revalidateTag('products')；用户下单 → revalidateTag('cart:'+userId)（个人化缓存）；「变更源 → tag」的映射表（失效的完备性：漏了触发源 = 静默旧数据 RBL-956）。
- 追问钩子：为什么「实体变更要同时失效实体 tag 和列表 tag」？——列表缓存里嵌入了实体的快照（列表页显示 product:123 的旧价格）；只失效实体 tag → 详情页新价格、列表页旧价格（不一致——用户困惑与客诉）；「缓存的一致性域」：实体与包含它的聚合要同失效（依赖闭包失效 RBL-635 的缓存语义）；层级 tag（父子关系）让失效传播可声明而非手工枚举。

```typescript
// tag 层级与失效传播
const TAG_HIERARCHY = {
  products: ['product:*'],                               // 集合 tag 失效 → 所有实体 tag 也失效
  'product:*': [],                                       // 实体 tag 无子级
  cart: ['cart:*'],
};
function revalidateWithHierarchy(tag) {
  const affected = [tag, ...childrenOf(tag)];            // 自身 + 依赖闭包
  affected.forEach(t => revalidateTag(t));
}
// revalidateTag('products') → products + 所有 product:* 失效
// 触发源映射表（失效完备性）
const TRIGGER_MAP = {
  'cms.product.updated': (p) => revalidateWithHierarchy('products'),
  'order.created': (userId) => revalidateTag(`cart:${userId}`),
  'inventory.changed': (sku) => revalidateWithHierarchy('products'),
};
// 反模式：tag 过粗
// revalidateTag('all')  —— 任何变更全站缓存全灭
```
