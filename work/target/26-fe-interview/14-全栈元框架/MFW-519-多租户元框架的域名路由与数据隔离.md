## MFW-519：多租户元框架：域名路由与数据隔离

**答**:
- 多租户的域名路由：1) 子域（tenant.app.com）→ middleware 解析 host 提取租户 → rewrite 到租户数据（缓存键含租户——Full Route Cache 的租户维度 RBL-508）；2) 自定义域（tenant.com → CNAME）→ middleware/host header 映射表（KV 查询租户）。
- 数据隔离三层：1) **请求上下文**（AsyncLocalStorage 携带 tenantId——全链路隐式传参，DB 查询自动加 where tenant_id（行级隔离））；2) 缓存隔离（Data Cache 键含租户：`fetch(url, { next: { tags: [`${tenant}:products`] } }`——跨租户缓存污染是安全事件不是性能问题）；3) schema 隔离（DB per tenant——重隔离场景）。
- Full Route Cache 的租户陷阱：静态路由 × N 租户 = 缓存键爆炸（域名进入缓存键）——Next 的做法：域名为缓存键一部分（同路由不同域不同缓存条目）——「租户数 × 页面数」的缓存规模要预算（KV/Redis 承载）。
- 追问钩子：为什么「缓存键含租户」是安全问题而不是优化问题？——漏租户键 = A 租户请求命中 B 租户缓存 = 数据越权（静默、无报错、审计极难发现）；隔离边界的检查（RBL-659 路径越界同构）必须在缓存读写两侧——多租户缓存的正确性 = 键完整性，性能只是副产品。

```javascript
// middleware：租户提取与路由
export function middleware(req) {
  const host = req.headers.get('host');
  const tenant = host.endsWith('.app.com')
    ? host.split('.')[0]                                 // 子域
    : await KV.get(`domain:${host}`);                    // 自定义域映射
  if (!tenant) return new Response('Unknown tenant', { status: 404 });
  const res = NextResponse.rewrite(new URL(req.nextUrl.pathname, req.url));
  res.headers.set('x-tenant', tenant);                   // 传给渲染层
  return res;
}
// AsyncLocalStorage 上下文
export const tenantContext = new AsyncLocalStorage();
export async function getTenant() {
  const ctx = tenantContext.getStore();
  if (!ctx) throw new Error('tenant 上下文缺失');
  return ctx.tenant;
}
// DB 层自动隔离
function scopedQuery(sql) {
  return db.query(sql, { tenant: getTenant() });         // driver 注入 where tenant_id
}
// 缓存键含租户
fetch(url, { next: { tags: [`${tenant}:products`] } });  // revalidateTag(`${t}:products`) 精确失效
```
