## MFW-506：客户端组件引用的模块加载：chunk 预取与按需时序

**答**:
- Flight payload 的 `I["chunk-id"]` 引用 → 客户端 resolve = 动态 import chunk——加载时序三层：1) **SSR 同步注入**（首屏 HTML 里 `<script src>` 直接带 client 组件 chunk——水合不等待）；2) **Flight 预取**（payload 的 I 引用被解析器收集 → 批量 prefetch——Suspense 内组件在显示前加载）；3) **按需**（懒边界展开时才 import——RBL-596 的 RSC 版）。
- chunk 引用与 manifest：构建器输出「模块 id → chunk url」映射（RBL-598 hash 文件名）——Flight 里只带模块 id，客户端查 manifest 定位 URL——「协议里不写 URL」让 chunk 文件名策略自由（hash 变更不影响 payload 语义）。
- 加载失败的体验：chunk 404（旧 payload + 新产物 RBL-622 场景）→ Suspense 边界内 error boundary 捕获 + 重载引导。
- 追问钩子：为什么 Flight 引用「模块 id」而不是「chunk URL」？——URL 是部署细节（hash/CDN 域名/版本目录），id 是语义；引用 URL 会让 payload 与产物文件名强耦合（每次发布 payload 语义变 → 缓存全失效）；「协议与部署解耦」是分层设计的通用原则——payload 的缓存有效性不依赖产物命名策略。

```javascript
// 客户端模块引用 resolve（框架内部简化）
const manifest = window.__CHUNK_MANIFEST__;              // 构建器注入：id -> url
function resolveClientRef(chunkId, exportName) {
  return import(manifest[chunkId]).then(mod => {
    const comp = mod[exportName];
    if (!comp) throw new Error(`chunk ${chunkId} 缺导出 ${exportName}——版本错配`);
    return comp;                                         // RBL-622 守卫语义
  });
}
// 预取收集：解析器遇到 I 行即收集 chunk
const prefetchSet = new Set();
function onModuleRef(chunkId) {
  if (!prefetchSet.has(chunkId)) {
    prefetchSet.add(chunkId);
    const link = document.createElement('link');
    link.rel = 'modulepreload'; link.href = manifest[chunkId];
    document.head.appendChild(link);                     // 预取不阻塞水合
  }
}
```
