## MFW-576：缓存语义版本化：升级时的缓存迁移

**答**:
- 元框架升级（13→14/14→15）的缓存语义翻转：Next 13 fetch 默认缓存 → 14/15 默认不缓存——升级后「存量 fetch 行为翻转」：页面从静态变动态（每请求渲染——成本爆炸）或反之——「缓存语义的版本迁移」是元框架升级的最大风险面。
- 迁移策略：1) **codemod 显式化**（升级工具把「依赖默认值」的 fetch 改写为显式声明——RBL-941 幂等 codemod；语义标注：原 13 默认缓存 → 显式 next: { revalidate: false }（保持原行为））；2) **行为 diff 验证**（升级前后双渲染对比 RBL-540——静态/动态标记 diff：路由级画像 RBL-561 的升级前后对比）；3) **渐进路由迁移**（共存期 RBL-541）。
- 缓存键的版本隔离：升级后缓存条目格式变化（payload 格式 v2）——旧缓存条目不兼容新读取——「缓存命名空间按框架版本隔离」（.next/cache 按 major 分目录或键含版本前缀）。
- 追问钩子：为什么「默认值翻转」比「API 废弃」更危险？——API 废弃 = 编译报错（显性）；默认值翻转 = 行为静默变化（编译通过行为变——成本/性能/正确性全可变）；「静默行为变化」的防御 = 显式化（依赖默认值的代码是风险——显式声明让升级变成纯版本号变化）——这与 RBL-953 默认值纪律、RBL-966「宁可少转换」的哲学一致：升级安全的核心是「行为显式化」。

```javascript
// 升级 codemod：fetch 默认值显式化（幂等）
// Next 13 → 15：默认缓存 → 默认不缓存
// 迁移前：fetch(url)          // 13 语义：缓存
// 迁移后：fetch(url, { next: { revalidate: false } })  // 显式保持缓存
// 或：   fetch(url, { cache: 'no-store' })            // 接受新语义（人工决策）
const codemod = (code) => code.replace(
  /fetch\(([^,)]+)\)(?!\s*,\s*\{)/g,
  "fetch($1, { next: { revalidate: false } }) /* TODO: 13 默认缓存，确认语义 */");
// 升级前后路由画像 diff（RBL-561）
function upgradeDiff(before, after) {
  return before.map((r, i) => ({
    route: r.route,
    typeChanged: r.type !== after[i].type,               // static→dynamic = 成本爆炸
    sizeDelta: +(after[i].firstLoadKB - r.firstLoadKB).toFixed(1),
  })).filter(x => x.typeChanged || Math.abs(x.sizeDelta) > 5);
}
// 缓存命名空间版本隔离
const cacheDir = `.next/cache/v${NEXT_MAJOR}/`;          // major 分目录：旧缓存不污染
```
