## MFW-535：构建期路由清单：预渲染 URL 枚举策略

**答**:
- 动态路由的预渲染需要「URL 清单」：generateStaticParams（Next）/prerender（Astro）/SvelteKit prerender 探测——枚举策略四种：1) 构建期 API 拉取（全部商品 id——构建时长随数据量增长）；2) 采样预渲染（Top N + 其余 on-demand ISR）；3) sitemap 驱动（已有 sitemap 作为清单源）；4) 运行时按需（访问时生成——ISR fallback blocking）。
- 大数据量的构建时长问题：百万 URL 全量预渲染 = 构建数小时——「采样 + on-demand」是标配（RBL-509）；构建期清单的缓存（商品 id 列表缓存——构建增量：只预渲染上次构建后变化的 URL——增量预渲染）。
- 清单的发布契约：sitemap 与实际可渲染 URL 的一致性（RBL-839 死链检测的站点版）——清单源（CMS）与渲染能力对账。
- 追问钩子：为什么「增量预渲染」需要构建器知道「上次构建的清单」？——增量 = diff（本次清单 − 上次清单 = 新增 URL 才渲染）；需要持久化上次清单（构建产物元数据 RBL-633 缓存条目）+ 清单的稳定序列化（排序后 hash 比对）；这是「构建过程的缓存键」从代码级扩展到「数据级」——CMS 数据成为构建输入的一部分（构建缓存键必须含数据指纹 RBL-582 的数据维度）。

```javascript
// 增量预渲染（清单 diff）
async function incrementalPrerender({ current, previous, render }) {
  const prevSet = new Map(previous);                     // url -> contentHash
  const changed = current.filter(u => {
    const prev = prevSet.get(u.url);
    return !prev || prev !== u.dataHash;                 // 新增或数据变更
  });
  const removed = [...prevSet.keys()].filter(u => !current.find(c => c.url === u));
  for (const { url } of changed) await render(url);      // 只渲染变化
  // 保存本次清单供下次 diff
  await saveManifest(current);
  return { rendered: changed.length, removed, skipped: current.length - changed.length };
}
// 清单源与渲染对账（sitemap 一致性）
function reconcile(sitemap, prerenderable) {
  const can = new Set(prerenderable);
  return sitemap.filter(u => !can.has(u));               // sitemap 声明但不可渲染 —— 死链风险
}
```
