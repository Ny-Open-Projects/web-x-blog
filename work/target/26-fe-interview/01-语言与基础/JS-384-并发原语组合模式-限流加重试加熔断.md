## JS-384：并发原语组合模式：限流 × 重试 × 熔断的管道

**答**：
- 管道思维：请求出站前经过「缓存检查 → 熔断判定 → 限流排队 → 重试包裹 → 超时」各层装饰器——每层单一职责、可组合可测试，比一个上帝函数好维护
- 熔断器状态机：closed（正常）→ 连续失败 ≥5 开路 open（直接快速失败 30s）→ half-open（放一个探测请求）→ 成功回 closed / 失败回 open——前端防「依赖服务挂了还疯狂重试拖垮页面」
- 限流与熔断的位置：限流在「出站保护自己」（并发上限），熔断在「入站反馈」（服务健康感知）——两者互补不可替代
- 组合实现纪律：每层独立可测（单测覆盖单层）、层间传递上下文（retry 知道 circuit 状态）、观测埋点在每层出口（哪层拒绝可归因）
- 现成方案认知：TanStack Query 的 retry + 网络模式、axios 拦截器链、ky 的 hooks——理解原语后看懂这些库的分层

```javascript
function withCircuit(fn, { threshold = 5, cooldown = 30_000 } = {}) {
  let fails = 0, openedAt = 0;
  return async (...args) => {
    if (fails >= threshold && Date.now() - openedAt < cooldown)
      throw new CircuitOpenError();
    try {
      const r = await fn(...args);
      fails = 0;                                   // 成功重置
      return r;
    } catch (e) {
      if (++fails >= threshold) openedAt = Date.now(); // >= 而非 ===：冷却后再失败也要续期，否则熔断永不重开
      throw e;
    }
  };
}
// 管道组合
const call = withTimeout(withRetry(withCircuit(withLimit(apiCall, 4))), 5000);
```

**追问**：

1. 熔断器的失败计数该按什么维度存？ → 必须按目标/key（`Map<key, state>`）；全局共用一个计数器，会导致一个接口挂掉就把所有接口一起熔断。
2. half-open 时同时涌入 100 个请求怎么办？ → 只放行一个探测请求，其余继续快速失败；状态机要加 `probing` 标志，探测结束前拒绝新请求。
3. `withRetry` 应该包在熔断外面还是里面？ → 放外层：每次真实失败都计入熔断，达到阈值立刻停止；放里层会放大失败次数，让熔断提前误开。
