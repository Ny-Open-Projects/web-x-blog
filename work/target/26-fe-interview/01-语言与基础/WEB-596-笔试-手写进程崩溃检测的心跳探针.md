## WEB-596：笔试：手写进程崩溃检测心跳探针

**答**：实现 `CrashProbe`：① 每 5s 写一条 IndexedDB 心跳 `{ ts, url, seq }`；② pagehide 时写 `clean-exit` 标记；③ 下次启动读取心跳与标记：无 clean-exit 且心跳间隔 > 30s 判定 `suspect-crash`，上报断层时长与 URL；④ 崩溃上报只保留最近 10 条防止无限膨胀；⑤ 所有 IDB 操作失败降级 localStorage。写出核心实现。

```javascript
class CrashProbe {
  constructor(store) { this.store = store; this.seq = 0; }
  async start() {
    await this._checkCrash();                       // 先读上次会话残留的心跳，再写新的
    this.timer = setInterval(() => this._beat(), 5000);
    await this._beat();
  }
  async _beat() {
    try {
      await this.store.put('hb', { ts: Date.now(), url: location.href, seq: ++this.seq });
      const all = (await this.store.all('hb')) || [];
      for (const old of all.slice(0, -10)) await this.store.del('hb', old.seq); // 保留10条
    } catch {
      try { localStorage.setItem('hb', JSON.stringify({ ts: Date.now(), url: location.href })); } catch {}
    }
  }
  async _checkCrash() {
    let last = null;
    try { last = await this.store.last('hb'); } catch {}
    if (!last) return;
    const clean = sessionStorage.getItem('clean-exit') === '1';
    const gap = Date.now() - last.ts;
    if (!clean && gap > 30_000) {
      navigator.sendBeacon('/api/mon/crash', JSON.stringify({
        type: 'suspect-crash', gap, url: last.url, now: location.href,
      }));
    }
    sessionStorage.removeItem('clean-exit');
  }
  stop() {
    clearInterval(this.timer);
    sessionStorage.setItem('clean-exit', '1'); // 在 pagehide 调用
  }
}
```

**评分点**：
- 判定逻辑三要素：无 clean-exit 标记 + 心跳断层超阈值
- 心跳保留上限防存储膨胀；IDB 失败降级 localStorage
- clean-exit 用 sessionStorage（随会话消失）而非 localStorage 的理由能说清
- 启动即检查并上报断层，闭环到监控

## 变体与延伸（补充）

**变体与延伸**：

1. clean-exit 为什么存 sessionStorage 而不是 localStorage？ → 会话级标记随标签页关闭自动清除；用 localStorage 会把上次会话的标记带到下次启动，导致崩溃被误判为正常退出。
2. 心跳 5s、判定 30s 的阈值如何取舍？ → 间隔越小写入越频繁、IDB 压力越大，30s 阈值给后台节流与短暂卡顿留余量，避免把页面切后台误报成崩溃。
3. 这个探针检测不到什么？ → 只能发现进程被杀与 OOM 崩溃；主线程死循环卡死仍会继续写心跳，需配合主线程 watchdog 或用 Worker 写心跳才能覆盖。
