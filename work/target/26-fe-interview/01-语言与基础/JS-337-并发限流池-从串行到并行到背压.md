## JS-337：并发限流池：从串行到并行到背压

**答**：
- 三级模型：串行（for await）→ 无界并行（Promise.all，任务多时打爆网络/内存）→ 有界并行（池：N 个槽位 + 等待队列）——工程默认是有界并行
- 背压语义：上游生产快于下游消费时的处理——池满时「挂起生产者」（返回 promise）而不是「丢弃任务」，配合暂停迭代实现拉模式
- 实现要点：空闲槽位通知（微任务级唤醒）、任务取消传播（AbortSignal 进池）、错误隔离（单任务失败不炸整池）、统计暴露（active/pending/done）
- 与 p-limit 类库的差异认知：p-limit 只管并发数；完整池还要管「取消、超时、重试、背压」——面试手写要体现分层
- 验证方式：压测上游 1000 任务 × 下游 4 槽，观察峰值内存与总耗时曲线，对比无界 all 的差异

```javascript
function createPool(limit) {
  const queues = [];
  let active = 0;
  const next = () => {
    if (active >= limit || !queues.length) return;
    active++;
    const { fn, resolve, reject } = queues.shift();
    fn().then(resolve, reject).finally(() => { active--; next(); });
  };
  return (fn) => new Promise((resolve, reject) => { queues.push({ fn, resolve, reject }); next(); });
}
// 用法: pLimit 语义 + 背压(上游被 await 挂住)
const limit = createPool(4);
for await (const task of tasks) {
  await limit(() => task.run());   // 池满时这里挂起 → 天然背压
}
```

**追问**：

1. `createPool(0)` 会发生什么？ → `next()` 里 `active >= limit` 恒成立，任务永远不启动，所有 Promise 悬挂；必须校验 `limit >= 1`，否则退化成串行。
2. 为什么 `await limit(...)` 就构成背压？ → 池满时该调用返回的 Promise 不 resolve，上游 for-await 循环被挂住不再生产新任务；前提是上游是 async iterable，同步数组塞进去仍会先全部入队。
3. `finally` 里调用 `next()`，如果下一个 `fn()` 同步抛错会怎样？ → 异常会从 finally 里冒出来，覆盖掉原本的任务结果；`next` 内要用 try/catch 包住 `fn()`，或约定 fn 必须返回 Promise。
