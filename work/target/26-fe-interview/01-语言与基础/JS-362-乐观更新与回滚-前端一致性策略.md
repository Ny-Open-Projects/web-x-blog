## JS-362：乐观更新与回滚：前端一致性策略

**答**：
- 乐观更新模型：先改本地状态立即渲染 → 发请求 → 成功确认 / 失败回滚到快照——「快照 + 恢复」是实现核心，状态库无关（redux undo/React Query optimistic 皆同构）
- 快照粒度：只快照受影响的实体（列表项/计数器）而不是整棵树——回滚按实体 patch 反向应用
- 并发乐观更新冲突：两个乐观操作在途时先后失败——操作队列化（每个乐观操作带序号，回滚只回滚自己的变更，后续操作重放）
- 服务器返回值校正：服务端可能返回与乐观值不同的数据（真实库存/审核状态）——以服务端为准覆盖（reconcile），不要信任本地乐观值
- 场景边界：点赞/收藏类高频低风险适合乐观；支付/库存扣减类强一致场景不用乐观（或乐观展示但明确「处理中」态）

```javascript
async function optimisticLike(id) {
  const snapshot = store.getItem(id);          // 快照
  store.patch(id, { liked: true, count: snapshot.count + 1 });  // 乐观
  try {
    const real = await api.post(`/like/${id}`); // 服务端为准
    store.patch(id, { liked: true, count: real.count });  // reconcile
  } catch (e) {
    store.patch(id, snapshot);                  // 回滚
    toast('点赞失败, 已恢复');
  }
}
// 并发保护: 操作带序号, 失败回滚后重放其后操作
```
