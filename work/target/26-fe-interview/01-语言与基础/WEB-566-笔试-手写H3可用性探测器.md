## WEB-566：笔试：手写 HTTP/3 可用性探测器

**答**：实现 `probeH3(url)`：探测当前环境下 h3 是否可用。要求：① 用 `fetch` 带 AbortController 限时 2s 发起一个 HEAD 探测请求；② 读取 Response 或 PerformanceEntry 中的 `nextHopProtocol` 判断实际协议；③ 区分三种结果：`h3-ok` / `fallback`（请求成功但协议是 h2/h1）/ `blocked`（超时或失败，疑似 UDP 被拦）；④ 同一 url 探测结果缓存 5 分钟避免重复探测。

```javascript
const cache = new Map(); // url -> { result, ts }
const TTL = 5 * 60 * 1000;

async function probeH3(url) {
  const hit = cache.get(url);
  if (hit && Date.now() - hit.ts < TTL) return hit.result;

  const result = await new Promise((resolve) => {
    const ctrl = new AbortController();
    const timer = setTimeout(() => { ctrl.abort(); resolve('blocked'); }, 2000);
    fetch(url, { method: 'HEAD', cache: 'no-store', signal: ctrl.signal })
      .then((res) => {
        clearTimeout(timer);
        // 发起一次 resource timing 读取真实协议（响应头不直接暴露协议）
        const [entry] = performance.getEntriesByName(res.url);
        const proto = entry?.nextHopProtocol || res.headers.get('x-proto') || '';
        resolve(proto.startsWith('h3') ? 'h3-ok' : 'fallback');
      })
      .catch(() => { clearTimeout(timer); resolve('blocked'); });
  });

  cache.set(url, { result, ts: Date.now() });
  return result;
}
```

**评分点**：
- 用 AbortController 实现硬超时，超时归类为 blocked 而不是让 Promise 悬挂
- 判断协议用 `nextHopProtocol`（resource timing），知道响应头拿不到协议这一事实
- 结果三分类且缓存结果与 TTL，避免探测风暴
- 注意探测请求本身要走 no-store，避免命中缓存的 h2 资源导致误判

## 变体与延伸（补充）

**变体与延伸**：

1. 为什么协议只能从 nextHopProtocol 拿，响应头里没有？ → 协议协商发生在传输层连接建立时，属于连接属性而非 HTTP 语义，只有 Resource Timing 的 PerformanceEntry 暴露。
2. 这套探测逻辑在 Node 环境下还成立吗？ → 不成立，Node 没有 Resource Timing 与浏览器 UDP 策略，需从 undici 的连接信息或 socket 的 ALPN 协议判断。
3. 5 分钟 TTL 期间协议可能变化吗？ → 会，Alt-Svc 生效、换网或代理切换都会改变实际协议，所以缓存键应绑 host 而非完整 url，并允许关键请求强制重探。
