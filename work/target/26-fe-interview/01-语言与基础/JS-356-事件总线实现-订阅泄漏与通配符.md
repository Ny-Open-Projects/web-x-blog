## JS-356：事件总线实现：订阅泄漏与通配符设计

**答**：
- 核心结构：Map<event, Set<handler>>——Set 保证同 handler 不重复注册、删除 O(1)；once 用包装函数 + 自动解除
- 订阅泄漏是事件总线头号问题：组件卸载忘 off → 闭包持有组件引用 → 泄漏；防御设计：命名空间订阅（`on('user:change', fn, 'comp-A')` + `offNamespace('comp-A')` 批量解除）、实例化总线（每组件域一个，随组件销毁）
- 通配符与命名空间：`user.*` 模式匹配用前缀树或正则过滤——事件量大时通配符遍历成本要评估；派发时快照订阅列表（遍历中新增/删除的防御）
- 错误隔离：单 handler 抛错不应中断其他 handler——try/catch 包裹 + 上报，这是总线健壮性的关键
- 与原生 EventTarget 的取舍：现代项目优先用 EventTarget（原生、类型化 CustomEvent），自研总线只在需要通配符/异步派发/命名空间时才有必要

```javascript
class EventBus {
  #map = new Map();
  on(ev, fn, ns) {
    const set = this.#map.get(ev) || this.#map.set(ev, new Set()).get(ev);
    set.add({ fn, ns });
    return () => this.off(ev, fn);
  }
  once(ev, fn, ns) {
    const off = this.on(ev, (...a) => { off(); fn(...a); }, ns);
    return off;
  }
  off(ev, fn) { this.#map.get(ev)?.forEach(h => { if (h.fn === fn) this.#map.get(ev).delete(h); }); }
  offNs(ns) { for (const set of this.#map.values()) for (const h of [...set]) if (h.ns === ns) set.delete(h); }
  emit(ev, ...args) {
    for (const h of [...this.#map.get(ev) ?? []]) {   // 快照防遍历中修改
      try { h.fn(...args); }
      catch (e) { reportError(e); }                    // 错误隔离
    }
  }
}
// 组件卸载统一清理
useEffect(() => { bus.on('user', handler, 'comp-A'); return () => bus.offNs('comp-A'); }, []);
```

## 追问（补充）

**追问**：

1. emit 时为什么先快照订阅列表？ → 遍历中 handler 增删会改变 Set 迭代结果，可能漏发或死循环，浅拷贝成数组再遍历保证本次派发稳定。
2. once 用包装函数实现有什么隐藏陷阱？ → 外部 `off(ev, 原fn)` 找不到包装体，必须维护原函数到包装函数的映射，否则 once 监听无法手动取消。
3. 相比原生 EventTarget，自研总线的额外成本是什么？ → 错误隔离、通配符匹配、命名空间回收、异步派发全要自己实现并保证不泄漏，能用 EventTarget 就不自研。
