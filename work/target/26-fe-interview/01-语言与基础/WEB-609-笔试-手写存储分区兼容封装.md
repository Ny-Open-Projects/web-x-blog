## WEB-609：笔试：手写第三方存储分区兼容封装

**答**：实现 `PartitionedStore`（用于第三方 iframe 内）：① 读写 localStorage 时自动给 key 加分区前缀：`partitionKey = 顶层站点(从 window.name 或约定 postMessage 获取) + 当前 origin`，避免不同宿主站数据串；② 提供 `get/set/remove`；③ 顶层站点不可直接读时（跨域），通过约定的 postMessage 握手从宿主获取 host 标识；④ 超时 1s 未握手成功降级用 origin-only 前缀。写出核心实现。

```javascript
class PartitionedStore {
  constructor() { this.prefix = null; this._ready = null; }
  async init() {
    if (this._ready) return this._ready;
    this._ready = new Promise((resolve) => {
      // 向宿主请求分区标识
      const timer = setTimeout(() => resolve(this._fallback()), 1000);
      addEventListener('message', function h(e) {
        if (e.data?.__host) {
          clearTimeout(timer); removeEventListener('message', h);
          resolve(`${e.data.__host}|${location.origin}`);
        }
      });
      parent.postMessage({ __wantHost: true }, '*'); // 宿主校验来源后回 __host
    });
    return this._ready;
  }
  _fallback() { return location.origin; } // 握手失败: 仅按自身 origin 分区
  async set(k, v) { localStorage.setItem(`${await this.init()}::${k}`, JSON.stringify(v)); }
  async get(k) {
    const raw = localStorage.getItem(`${await this.init()}::${k}`);
    return raw ? JSON.parse(raw) : null;
  }
  async remove(k) { localStorage.removeItem(`${await this.init()}::${k}`); }
}
// 宿主页面侧:
addEventListener('message', (e) => {
  if (e.data?.__wantHost && trustedOrigins.has(e.origin)) {
    e.source.postMessage({ __host: location.hostname }, '*');
  }
});
```

**评分点**：
- 分区 key = 宿主站点 + iframe origin，理解存储分区动机
- 握手超时降级 + 宿主侧校验来源 iframe
- API 全异步化（init 是 Promise），避免未握手就写脏数据
- 能说明原生 Storage Partitioning 已按 top-site 自动分区，此封装是兼容/语义层兜底

## 变体与延伸（补充）

**变体与延伸**：

1. 浏览器已原生实现 Storage Partitioning，这层封装还有必要吗？ → 老版本未分区，且被封装的 SDK 可能被嵌入任意宿主站，语义层统一前缀能保证跨宿主数据不串并兜底不支持的浏览器。
2. postMessage 里 host 侧直接 `'*'` 回发有什么风险？ → 任意源都能收到，会泄露宿主标识；必须校验 `e.origin` 白名单后向精确 origin 回发。
3. 为什么这里选 localStorage 而不用 IndexedDB？ → 数据量小、同步读简单；但分区语义与介质无关，大数据仍应走 IDB，用 top-site 拼库名实现同等隔离。
