## JS-398：笔试：手写请求去重拦截器

**答**：实现 `dedupeFetch(input, init)`：① 同 method+url+body 的并发请求合并为一次真实请求，所有调用方共享同一结果；② 只合并幂等方法（GET/HEAD），写请求不去重；③ 响应是 Response 对象（body 只能读一次）——需克隆或直接回传 JSON 解析结果，设计接口 `dedupeJson()` 返回解析后的数据避免 body 冲突；④ 请求失败所有调用方一起失败且缓存清理（可重试）；⑤ TTL 内结果复用（可选）。写出实现。

```javascript
const inflight = new Map();

async function dedupeJson(input, init = {}, { ttl = 0 } = {}) {
  const method = (init.method || 'GET').toUpperCase();
  if (!['GET', 'HEAD'].includes(method)) return rawJson(input, init);  // 写请求不合并
  const key = `${method} ${input} ${init.body ?? ''}`;
  const cached = ttlCache.get(key);
  if (cached && Date.now() - cached.t < ttl) return cached.v;
  if (inflight.has(key)) return inflight.get(key);          // 合并并发
  const p = rawJson(input, init)
    .then(v => { if (ttl) ttlCache.set(key, { v, t: Date.now() }); return v; })
    .finally(() => inflight.delete(key));                   // 失败也清理(可重试)
  inflight.set(key, p);
  return p;
}
const ttlCache = new Map();

async function rawJson(input, init) {
  const res = await fetch(input, init);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}
// 效果: 列表渲染 20 个卡片并发请求 /api/detail?id=1 → 实际 1 个请求
```

**评分点**：
- 只合并幂等方法（写请求合并会丢操作语义）
- key 构造含 method+url+body，防不同参数误合并
- 返回解析后 JSON 而非 Response（body 一次性消费的冲突规避）
- 失败清理 inflight（可重试）+ 可选 TTL 复用

## 变体与延伸（补充）

**变体与延伸**：

1. 为什么不能把同一个 Response 直接返回给多个调用方？ → body 是只读一次流的 ReadableStream，第二个调用方调 json() 会抛 body already used，必须 clone 或统一先解析。
2. key 里拼 init.body 会踩什么坑？ → FormData、Blob、普通对象直接字符串化都会变成 "[object Object]"，需稳定序列化，大 body 时可只按 method+url 合并。
3. 失败时为什么一定要 finally 清理 inflight？ → 否则后续同 key 请求永远拿到已 rejected 的 promise，等于对该接口永久熔断，必须清理才能重试。
