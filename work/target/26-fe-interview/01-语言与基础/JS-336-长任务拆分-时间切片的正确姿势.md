## JS-336：长任务拆分：时间切片的正确姿势

**答**：
- 拆分目标：单个任务 <50ms（长任务红线），交互场景 <16ms；切片粒度按预算动态调整而不是固定行数
- 让出主线程的三种方式：`await scheduler.yield()`（新 API，保持任务优先级）、MessageChannel postMessage（最快宏任务，不被 setTimeout 最低 4ms 限制）、setTimeout(0)（有 4ms 聚合与嵌套节流问题）
- isInputPending：切片循环里检测是否有待处理输入，有则优先让路给输入事件——调度器实现的关键 API
- 优先级设计：高优先级切片继续用微任务/直接执行，低优先级用 idle；React 的并发调度本质就是这个模型（过期时间 + 小顶堆）
- 验证：Performance 面板 long task 消失、INP 改善；错误恢复（切片中抛错）要决定「继续/中止」语义

```javascript
async function processWithBudget(items, deadline = 8) {
  for (const item of items) {
    handle(item);
    if (navigator.scheduling?.isInputPending?.()) await yieldNow(); // 输入优先
    else if (performance.now() % 1000 >= deadline) await yieldNow(); // 预算耗尽
  }
}
function yieldNow() {
  return scheduler?.yield?.() ??
    new Promise(r => { const c = new MessageChannel(); c.port1.onmessage = () => r(); c.port2.postMessage(0); });
}
```

**追问**：

1. 示例里 `performance.now() % 1000 >= deadline` 这个预算判断对吗？ → 不对，取模得到的是毫秒数的低位，与本次切片何时开始无关；应记录 `sliceStart = performance.now()`，再判断 `now - sliceStart >= deadline`。
2. 直接写 `scheduler?.yield()` 有什么风险？ → `scheduler` 未声明时可选链救不了，会抛 ReferenceError；要用 `globalThis.scheduler?.yield?.()` 包一层再回落。
3. 每次 yield 都 new 一个 MessageChannel，会有什么问题？ → 端口与回调不复用会持续泄漏，高频切片下内存上涨、GC 抖动；应复用单例 channel 或用完 `close()`。
