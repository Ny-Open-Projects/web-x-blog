## WCN-886：设计系统平台的「权限模型」：谁能发布、审核、弃用组件？

**答**：
- 结论先行：权限模型要「和治理流程对齐」——用 RBAC（基于角色的访问控制）把「提交、审核、发布、弃用」分权，确保任何破坏性操作都有第二人把关，且责任可追溯。
- 角色划分：贡献者（Contributor，可提交组件 PR）、审核者（Reviewer，a11y/API 专家，可批准但不可直接发布）、发布者（Maintainer，可合并发布、管版本）、管理员（Admin，管权限与平台配置）；业务方通常是纯消费者。
- 关键分权：提交者不能自己审核自己的破坏性变更（四眼原则）；弃用/删除公共组件需委员会 + 管理员双签；发布需通过所有自动化门禁（CI 通过）才允许。
- 实现：RBAC 表（角色→权限）+ 资源级权限（某个组件的 owner 对其有特殊权限）；所有操作记审计日志（谁/何时/做了什么）；临时权限有有效期。
- 与 WCN 结合：组件发布到 registry 需要发布者凭证，CI 中用最小权限的服务账号；防止单个开发者绕过流程直接发布污染生产。
- 追问钩子：面试官会问「紧急修复没时间走完整流程怎么办」——答：设「紧急通道」——允许跳过部分人工审核，但必须事后补审 + 自动通知 + 完整审计日志，且紧急发布同样要过自动化门禁（不能跳过机器检查）。

```javascript
// RBAC 权限校验：角色 → 允许的操作
const PERMISSIONS = {
  contributor: ['submit', 'comment'],
  reviewer:    ['submit', 'comment', 'review'],
  maintainer:  ['submit', 'comment', 'review', 'publish', 'deprecate'],
  admin:       ['*'],
};
function can(role, action) {
  const perms = PERMISSIONS[role] || [];
  return perms.includes('*') || perms.includes(action);
}
// 四眼原则：提交者不能审核自己的变更
function canReview(role, author, reviewer) {
  return can(role, 'review') && author !== reviewer;
}
console.log(can('reviewer', 'publish'));            // false
console.log(canReview('maintainer', 'alice', 'alice')); // false
console.log(canReview('maintainer', 'alice', 'bob'));   // true
```
