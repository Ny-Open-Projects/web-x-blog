## WCN-687：设计系统发版后如何让业务方平滑升级？变更沟通机制如何设计？

**答**：
- 结论：用「语义化版本 + 变更日志 + 迁移指南 + 弃用周期」四件套；破坏性变更走 major + codemod + 至少一个版本的弃用警告。
- 做法：发布 PR 自动生成 changelog；文档站标注 breaking changes；提供升级 diff 示例与 codemod；提前在社区渠道预告。
- 追问钩子：如何衡量升级推广效果？用「各版本采用率看板」——考察对「发布不是终点、推广才是」的理解。

```javascript
const RELEASE = {
  version: '3.2.0',
  changes: [
    { type: 'feat', desc: 'Button 新增 loading 态' },
    { type: 'breaking', desc: 'type 属性改名为 variant', codemod: 'type-to-variant' },
  ],
  deprecation: { old: 'type', removeIn: '4.0.0' },
};
function genChangelog(release) {
  const breaking = release.changes.filter(c => c.type === 'breaking');
  return breaking.length
    ? `⚠️ ${release.version} 含 ${breaking.length} 项破坏性变更，请阅读迁移指南`
    : `✅ ${release.version} 无破坏性变更`;
}
console.log(genChangelog(RELEASE));
```
