## WCN-861：编译平台的「编译耗时剖析」与优化方法有哪些？

**答**：
- 结论先行：优化编译速度的第一步是「测量」——用分阶段计时找出瓶颈（解析？类型检查？变换？代码生成？），再针对性优化，而不是盲目上缓存。
- 剖析手段：在各阶段埋点计时生成 flamegraph/时间线；记录每文件、每 Pass 的耗时分布；区分冷构建与热构建、全量与增量；用 `why-did-you-compile` 类工具找重复工作。
- 常见瓶颈与对策：① 重复解析——缓存 AST/IR；② 全量扫描——增量编译只处理变更；③ 低效遍历——一次遍历做多个 Pass（pass fusion）；④ 类型检查重——用 transpile-only 跳过类型、类型检查单独并行；⑤ 字符串拼接——用 SourceMap 友好的高效构造器。
- 架构级优化：并行编译（Worker 池）、持久化缓存跨进程复用、按需编译（只编译入口依赖图）、跳过无关文件（include/exclude 精确）。
- 权衡：速度 vs 产物质量 vs 调试体验——不能为了快牺牲 SourceMap 准确性或优化效果；给用户「开发态快编译、生产态全优化」两档。
- 追问钩子：面试官会问「热更新为什么还是慢」——答：HMR 慢常因失效范围过大（一个改动让整棵依赖链重编）或运行时重建成本高，要收窄失效边界 + 缓存模块图 + 减少重复初始化。

```javascript
// 编译分阶段计时剖析
function profiledCompile(source, stages) {
  const timings = {};
  let data = source;
  for (const [name, fn] of Object.entries(stages)) {
    const t0 = performance.now();
    data = fn(data);
    timings[name] = +(performance.now() - t0).toFixed(2);
  }
  const slowest = Object.entries(timings).sort((a, b) => b[1] - a[1])[0];
  return { data, timings, bottleneck: slowest?.[0] };
}
const r = profiledCompile('const a = 1', {
  parse: s => ({ ast: s }),
  lower: x => ({ ir: x.ast }),
  optimize: x => x,
  emit: x => 'code',
});
console.log(r.timings, '瓶颈:', r.bottleneck);
```
