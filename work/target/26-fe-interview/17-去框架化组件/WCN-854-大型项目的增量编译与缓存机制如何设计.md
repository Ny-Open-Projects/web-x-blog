## WCN-854：大型项目的「增量编译」与缓存机制如何设计？

**答**：
- 结论先行：增量编译的核心是「依赖图 + 内容哈希」——只重新编译「变更文件及其受影响的依赖链」，其余复用缓存，把 O(N) 的编译降到 O(变更规模)。
- 依赖图：构建时记录模块间的 import 依赖与「编译产物依赖」（A 的样式/token 变了影响哪些组件）；文件变更时能沿反向依赖找到需重编的最小集合。
- 内容哈希缓存：以源码内容（而非 mtime，避免时间戳误判）计算哈希作缓存 key；缓存产物（AST、IR、生成代码）到磁盘/内存，命中则直接复用。
- 失效策略：依赖变更时做「传递失效」——上游变了下游缓存作废；用版本号/哈希比对避免无效重编；持久化缓存（跨进程复用）进一步加速 CI。
- 边界：全局性变更（如 token 主题、全局类型）会影响大量模块，需要特殊处理；并行编译时注意缓存读写竞争；缓存正确性优先于命中率——宁可多编也不能用陈旧产物。
- 追问钩子：面试官会问「怎么保证缓存不被污染」——答：缓存 key 包含源码哈希 + 编译器版本 + 配置哈希 + 依赖哈希，任一变化即失效；并定期清理 + 校验产物完整性。

```javascript
// 增量编译核心：内容哈希 + 反向依赖图 + 传递失效
const cache = new Map();           // filePath -> { hash, result }
const revDeps = new Map();         // filePath -> Set<依赖它的文件>
function hash(s) { let h = 0; for (const c of s) h = (h * 31 + c.charCodeAt(0)) | 0; return h; }
function compileFile(path, sources) {
  const h = hash(sources[path]);
  const hit = cache.get(path);
  if (hit && hit.hash === h) return hit.result;       // 命中复用
  const result = `/* compiled ${path} */` + sources[path]; // 真实这里是 transform
  cache.set(path, { hash: h, result });
  return result;
}
function rebuild(changed, sources) {
  const dirty = new Set([changed]);
  // 传递失效：变更文件的反向依赖全部标脏
  const queue = [changed];
  while (queue.length) {
    const f = queue.pop();
    for (const dependent of (revDeps.get(f) || [])) if (!dirty.has(dependent)) { dirty.add(dependent); queue.push(dependent); }
  }
  for (const f of dirty) compileFile(f, sources);
  return [...dirty];
}
```
