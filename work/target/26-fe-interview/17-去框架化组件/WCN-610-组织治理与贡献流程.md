## WCN-610：元素库要从「一个团队维护」走向「多团队共建」，治理模型如何设计？

**答**：
- 结论：治理 = 分层所有权（CORE 团队守底座 / 业务团队贡献业务组件）+ 准入 Checklist + 评审与发布流程。
- 机制：设 RFC 流程（重大 API 变更先提案）、CODEOWNERS 分区、贡献者需通过契约测试与 A11Y 基线才能合并。
- 追问钩子：如何避免贡献质量参差？用「门禁自动化」——CI 跑契约/视觉/体积/安全扫描，人只评审设计合理性，把机器能判的交给机器。

```javascript
// CODEOWNERS + CI 门禁配置示意
const GOVERNANCE = {
  core: ['token', 'button', 'input', 'modal'],
  contributionFlow: [
    'RFC 提案（涉及新 API）',
    '实现 + 契约测试 + 视觉快照',
    'CI: lint / a11y / bundle / security',
    'CODEOWNERS 评审合并',
    '灰度发布 → 全量',
  ],
  gates: ['contractTest', 'a11yBaseline', 'sizeBudget', 'securityScan'],
};
function canMerge(pr) {
  return GOVERNANCE.gates.every(g => pr.checks[g] === 'pass');
}
console.log(canMerge({ checks: { contractTest: 'pass' } })); // false
```

## 追问（补充）

**边界与易错**：

- `canMerge` 里 `pr.checks[g] === 'pass'` 对未上报的 check 返回 false，这是对的（缺门禁即拒绝），但必须保证 CI 里对应 job 一定上报，否则永远合不进去。
- 灰度不能只按用户百分比，要按 token 版本双跑比对，否则新旧样式混用会被当成线上 bug 提单。
- `core` 边界要落进 CODEOWNERS 路径而不是 `GOVERNANCE.core` 数组，数组不参与真实评审，等于没有约束。

**追问**：

1. 多团队共建后 API 风格发散怎么办 → 底座团队守 API 契约（命名、事件、props 语义）并提供 lint 规则，新组件必须过契约测试才能入库。
2. 业务团队贡献的组件没人用了怎么下线 → 埋点统计引用数与版本分布，标 deprecated 给迁移期，超期先在 CI 报警告再升级为 error。
3. 主版本破坏性变更怎么推 → 走 RFC 加 codemod 自动迁移脚本，新旧 API 共存一个 minor 周期，禁止直接删。
