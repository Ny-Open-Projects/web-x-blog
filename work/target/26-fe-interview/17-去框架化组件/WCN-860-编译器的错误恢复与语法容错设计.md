## WCN-860：编译器的「错误恢复」与语法容错设计怎么做？

**答**：
- 结论先行：好的编译器「报一个错不够，还要继续解析以报出多个错」——错误恢复让解析器遇到语法错误后能重同步继续，一次编译暴露尽可能多的问题，提升开发体验（尤其在 IDE 实时编译场景）。
- 恢复策略：① 删除法——跳过当前 token 尝试继续；② 插入法——假设缺失了某个 token（如漏分号）继续；③ 恐慌模式（panic mode）——遇到错误后丢弃 token 直到同步点（分号、右括号、语句起始关键字），再从同步点恢复。
- 错误节点：解析失败时在 AST 里放 `ErrorNode`/`MissingNode` 占位，让后续阶段能继续处理（跳过或降级），而不是让整个编译崩溃。
- 错误质量：给出精确位置（行列）、期望 vs 实际 token、修复建议；错误消息要人类可读，而非「unexpected token」。
- IDE 场景：容错还要支持「代码写到一半」的不完整输入（如刚敲了 `<div` 还没闭合），解析器要能产出「部分 AST」供补全与高亮。
- 追问钩子：面试官会问「恢复过度会不会产生连锁误报」——答：会用「错误抑制窗口」——相邻错误太近时只报第一个，避免一次语法错误引发一串无意义的连锁报错。

```javascript
// 恐慌模式错误恢复：遇错跳到同步点继续解析
const SYNC = new Set([';', '}', 'let', 'const', 'return']);
function parseStatements(tokens) {
  const stmts = [], errors = [];
  let i = 0;
  while (i < tokens.length) {
    try {
      const stmt = parseOne(tokens, i);   // 解析单条语句
      stmts.push(stmt.node); i = stmt.next;
    } catch (e) {
      errors.push({ at: i, message: e.message });
      // 重同步：跳到下一个同步点
      while (i < tokens.length && !SYNC.has(tokens[i])) i++;
      if (tokens[i] === ';') i++;         // 消费同步点
    }
  }
  return { stmts, errors };               // 即使有错也返回已解析部分
}
function parseOne(tokens, i) {
  if (tokens[i] !== 'let') throw new Error(`期望 let，实际 ${tokens[i]}`);
  return { node: { type: 'Decl', name: tokens[i + 1] }, next: i + 3 };
}
console.log(parseStatements(['let','a','=','1',';','const','b',';','let','c',';']));
```
