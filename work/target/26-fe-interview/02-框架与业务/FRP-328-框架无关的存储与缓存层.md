## FRP-328：框架无关的存储与缓存层

**答**：
- 三层存储内核：内存缓存（LRU Map）、持久缓存（IndexedDB 封装）、HTTP 缓存协作（ETag/If-None-Match）——框架层只消费接口
- IDB 封装的关键协议：promise 化 + 版本迁移 + 事务粒度收敛——框架无关后可 100% 单测（fake-indexeddb）
- 缓存失效策略统一：TTL + 显式失效（revalidate 语义）——各框架数据层（Query/自定义）调用同一失效入口
- 跨 tab 一致性：BroadcastChannel 通知 + storage 事件兜底——内核层实现（框架层零感知）
- 与 SSR 的边界：持久缓存在客户端独有——SSR 数据直注（不走缓存层）vs 客户端水合后缓存——「两条数据路径」的合并点

```javascript
// 内核: 分层缓存
export function createCache({ idb, ttl = 5 * 60_000 } = {}) {
  const mem = new Map();
  return {
    async get(key) {
      if (mem.has(key)) return mem.get(key).v;
      const v = idb ? await idbGet(idb, key) : null;
      if (v) mem.set(key, { v, at: Date.now() });
      return v;
    },
    async set(key, value) {
      mem.set(key, { v: value, at: Date.now() });
      if (idb) await idbSet(idb, key, value);
      bc.postMessage({ type: 'cache:set', key });     // 跨 tab 通知
    },
    invalidate(key) { mem.delete(key); idb && idbDel(idb, key); bc.postMessage({ type: 'cache:del', key }); },
  };
}
```

**追问**：

1. 内存层和 IndexedDB 双写不一致怎么兜？→ 先写内存让它立刻生效，IDB 写失败时把内存回滚或标脏；读路径固定"内存热层 → IDB 冷层"，不允许只写一半就当成功。
2. BroadcastChannel 消息丢了会怎样，怎么补？→ 它无投递保证，新开的 tab 也收不到历史消息；必须用 storage 事件兜底，并在启动时比对版本号做一次全量校验。
3. 用户切换账号后缓存怎么隔离？→ key 里带 tenant/userId 前缀，登出时按前缀批量失效，否则新账号会读到上一个账号的列表数据，属于越权级 bug。
