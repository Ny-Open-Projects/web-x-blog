## V3-252：SSR 下响应式系统为什么不建立依赖订阅？数据更新靠什么完成？
**答**：
- 原因：服务端一次请求渲染一次，渲染完实例即销毁，不存在"后续变化要触发更新"的生命周期，订阅没有意义且白白耗内存。
- 实现：SSR 渲染时 effect 求值走 `pauseTracking` 关闭 track，computed/refs 行为退化为"可读的可变值"。
- 数据更新模型：服务端"数据 → 渲染"是请求驱动；客户端 hydration 后接管响应式，之后的更新由客户端交互驱动。
- 边界：服务端渲染期间修改 ref 不触发任何重渲——若模板依赖在 setup 后被异步改写，输出可能不一致，async setup 必须 await 完成再返回。
- 面试钩子：解释为什么 SSR 页面"每次交互必须回到客户端才生效"——服务端无事件系统也无订阅。

```javascript
// 服务端：数据先取好，一次渲染
export default defineComponent({
  async setup() {
    const list = ref(await api.fetchList()); // 渲染前 await，之后的修改无意义
    // list.value = 'new'   // ❌ 不会触发重渲染，SSR 无订阅
    return () => h('ul', list.value.map((i) => h('li', i.name)));
  },
});
// 客户端水合后：同一组件的 setup 重新执行（或复用 payload），从此交互走响应式
```
