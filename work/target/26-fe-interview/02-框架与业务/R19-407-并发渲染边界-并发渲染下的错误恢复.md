## R19-407：并发渲染边界：并发渲染下的错误恢复流程

**答**：
- 恢复粒度决策：组件级（局部重试）、边界级（重挂子树）、根级（整页 reload）——成本递增；优先局部
- React 19 的 use 指令错误：promise reject → 边界捕获 → 「重试 = 重新调用数据函数」——配合缓存失效（新 promise）才有意义；缓存不失效的重试读到旧 rejection
- 无边界恢复（React 19 experimental）：`onUncaughtError` root 选项——未捕获错误的全局策略（上报 + 可选恢复）
- 恢复后的状态一致性：重挂子树丢局部状态——关键状态提升到边界外（URL/store）才能跨恢复存活
- 恢复 UX 设计：重试按钮带 loading（transition 包裹）、连续失败改「联系支持」态、自动重试限 3 次带退避

```jsx
function DataBoundary({ fetcher, children }) {
  const [error, setError] = useState(null);
  const [key, setKey] = useState(0);
  const retry = () => {
    queryClient.invalidateQueries({ queryKey: ['data'] });  // 缓存失效
    setError(null);
    setKey(k => k + 1);                                     // 强制重建
  };
  if (error) return <ErrorUI onRetry={retry} error={error} />;
  return <ErrorBoundary fallbackRender={({ error }) => { setError(error); return null; }} key={key}>{children}</ErrorBoundary>;
}
```

**追问**：

1. 重试为什么用 key 变化而不是直接清 error？→ `setState({error:null})` 只是让同一棵子树重新 render，已经坏掉的局部状态仍被复用；key 变化强制卸载重挂，拿到的是干净实例。
2. 重挂之后滚动位置和未提交的表单输入丢了怎么处理？→ 恢复粒度越粗丢得越多，把滚动位置、草稿提升到 URL、sessionStorage 或边界外的 store，重挂后回填；或者改用局部错误提示，不整块重挂。
3. 自动重试为什么要退避并设上限？→ 服务端故障时立即重试会放大流量形成重试风暴；指数退避加抖动、上限 3 次，并且要区分 4xx（不重试）与 5xx/网络错误。
