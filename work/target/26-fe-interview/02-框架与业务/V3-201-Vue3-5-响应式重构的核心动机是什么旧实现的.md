## V3-201：Vue 3.5 响应式重构的核心动机是什么？旧实现有哪些痛点？
**答**：
- 旧实现痛点：依赖用 `Set<Effect>` 存储，每次 trigger 后 cleanup 需要把整个 dep 清空再全量重新收集，大数组/高频更新下开销巨大。
- 内存开销：每个 Effect 携带 deps 数组 + Set 双向引用，结构冗余；3.5 前内部字段多、GC 压力大。
- 性能数据：官方基准显示 3.5 内存占用减少约 56%，大列表更新提速明显。
- 重构核心：依赖改为**双向链表**存储 + **版本计数（version counting）**判定脏状态，避免全量 cleanup。
- 兼容性：对外 API（reactive/ref/computed/watch）完全不变，属纯内部重构，这正是"重构"而非"重写"的示范。

```javascript
// 旧实现：trigger 后需要全量清空依赖再重新收集
function trigger(target, key) {
  const deps = targetMap.get(target).get(key);
  // 旧逻辑：复制一份避免遍历时 cleanup 修改集合
  const effectsToRun = new Set(deps);
  effectsToRun.forEach((effect) => {
    // cleanup：从所有关联 dep 中删除自己，重新执行时再全量收集
    effect.cleanup?.();
    effect.run();
  });
}
// 3.5 后：双向链表 + 版本号，只需从链表摘除失效节点，不用清空重建
```
