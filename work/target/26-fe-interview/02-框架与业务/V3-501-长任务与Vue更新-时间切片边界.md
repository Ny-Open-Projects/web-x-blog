## V3-501：长任务与 Vue 更新：同步渲染的时间切片边界

**答**：
- Vue3 更新是同步的：nextTick 批合并后，一次 patch 在单个微任务内完成（flushJobs 由 `Promise.then` 派发）——没有 React 的并发切片；一次更新触碰数千组件 = 一次长任务
- 应对策略一（减少单次更新规模）：列表虚拟化、按区域拆组件、v-memo——「把大更新切成小更新」是唯一正路
- 应对策略二（错峰）：非关键更新 defer 到 idle（数据进队列，rAF 分批 ref.set）——手动时间切片，牺牲实时性换流畅
- 应对策略三（Worker 预处理）：数据转换/过滤在 Worker 完成，主线程只接收最终状态——更新规模小但状态突变大，配合骨架过渡
- 与 INP 的关系：交互 handler 内触发的 Vue 更新直接计入 INP——高频状态（拖拽/输入）的绑定更新必须「降频到 rAF 级」

```javascript
// 拖拽场景: 状态降频
const pos = ref({ x: 0, y: 0 });
const display = ref(pos.value);
let raf = 0;
onDrag((x, y) => {
  pos.value = { x, y };                      // 高频原始值
  if (!raf) raf = requestAnimationFrame(() => {
    display.value = pos.value;               // 每帧一次驱动渲染
    raf = 0;
  });
});
```

**边界与易错**：

1. 把 `nextTick` 当异步渲染：它只等本轮 flush 结束，patch 仍在同一个微任务里同步跑完，几千个组件照样阻塞主线程。
2. `v-memo` 依赖漏写：漏项会让该块永不更新，多写等于没优化；套在频繁变化的节点上是负收益。

**追问**：

1. Vue 为什么不做时间切片？→ 切片需要可中断的 fiber 与双缓冲提交，Vue 的 patch 是递归同步的，改造等于重写渲染器。
2. 线上长任务怎么定位？→ Performance 面板找超过 50ms 的任务，再用 `performance.mark` 包住更新，区分耗时在 patch 还是业务计算。
3. defer 到 idle 会不会丢状态？→ `requestIdleCallback` 繁忙时可能长时间不触发，要设 timeout 兜底并保证最后一次状态落地。
