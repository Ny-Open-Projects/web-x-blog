## AGT-218：RAG 和微调分别解决什么问题——决策框架是什么？

**答**:
- 本质分工：RAG 解决"知识"问题（模型不知道的事实，可随时更新、可溯源）；微调解决"行为"问题（输出格式/语气/领域任务模式，如特定 JSON schema 稳定输出、客服话术风格）——知识常变用 RAG，行为固定才微调。
- 典型误用：用微调灌知识（成本高、更新难、易过拟合且不可溯源）——"知识进 RAG，风格进微调"是默认原则；微调记忆知识还会放大幻觉（模型自信地背错）。
- 组合策略：成熟企业两者结合——微调底座（任务模式+格式纪律）+ RAG 供知识（实时/可溯源/可审计），再加评测闭环持续调两边。
- 决策清单：知识更新频率高/需要引用溯源/多租户隔离 → RAG；输出格式不稳/领域风格差异大/小模型蒸馏 → 微调；都要 → 组合并明确边界。

```text
RAG vs 微调决策表：
知识频繁更新？     → RAG（微调更新=重训）
需要引用溯源？     → RAG（微调无法溯源）
多租户知识隔离？   → RAG（元数据过滤）
输出格式不稳定？   → 微调（SFT 格式纪律）
领域风格/术语？    → 微调 + 词表注入
端侧/低成本小模型？→ 微调蒸馏
默认：知识进 RAG，行为进微调，
  两者可组合，边界要写进架构文档。
```
