## 本章回顾

本章围绕「云应用市场」展开，目标是把零散的云原生能力（Pod、中间件、存储、镜像等）以「应用」的形式包装起来，让使用者像在手机应用商店安装 App 一样一键安装一套完整的云上方案。

从工程视角看，本章完成的工作可以归纳为三条主线：

### 服务端开发

我们基于 go-micro 构建了 `appStore` 微服务，自下而上分为四层：

- **Model 层**：定义了 `AppStore` 主表以及 `AppImage`、`AppPod`、`AppMiddle`、`AppVolume`、`AppComment`、`AppCategory`、`AppIsv` 等辅助信息表，主表通过 GORM 的 `ForeignKey:AppID` 与子表建立一对多关联。
- **Repository 层**：以接口 `IAppStoreRepository` 对外提供 `InitTable`、`CreateAppStore`、`FindAppStoreByID`、`DeleteAppStoreByID`、`UpdateAppStore`、`FindAll`，以及安装数、浏览数的统计方法；删除操作通过事务级联清理所有关联子表。
- **Service 层**：以接口 `IAppStoreDataService` 封装业务逻辑，向外暴露 CRUD 与四个统计方法（安装数增/查、浏览数增/查）。
- **Handler 层**：实现 Proto 中声明的所有 RPC，把请求 Proto 通过 `common.SwapTo` 转换为领域模型，再委托给 Service。

### 市场 API 开发

在 Proto 中声明了 9 个 RPC：添加、删除、更新、按 ID 查询、查询全部，以及安装数、浏览数的增/查。Handler 与 Service、Repository 逐层对接，形成完整闭环。由于关联数据较多（图片、Pod、中间件、存储、评论），添加应用（AddAppStore）的表单处理相对特殊：关联资源均以「模板 ID」的形式记录，而非在应用市场内重新创建。

### 前端联调

本章仅把两个主要页面（应用列表、应用详情）展现出来，用于说明交互形态：应用以平铺方式展示，可通过分类筛选；详情页聚合图片、模板组合与评论。前端表单的字段名（如 `inputname`）已与服务端约定好，可直接对接。

## 两个思考题

### 云应用市场能满足哪些应用场景

课程里强调，云应用市场本质上是把「一组可运行的云资源」打包成「一个应用」对外分发。除了最直观的「应用打包上架」之外，它还能支撑以下场景：

- **标准化交付**：把经过安全扫描、官方审核的 Middleware（MySQL、Redis 等）和存储模板沉淀为可复用资产，避免每个团队重复搭建。
- **组合编排**：多个基础组件（Pod 模板 + 中间件 + 存储）组合成一个业务应用，使用者无需关心底层依赖。
- **版本与权限治理**：对应用、服务商（ISV）、数据进行统一的权限与生命周期管理。
- **自助式开通**：使用者在前端选择应用即可一键安装，免去手动配置资源规格。

### 云市场对私有化有哪些帮助

公有云场景下，应用直接发布到公网即可；但在企业内网，尤其是中大型企业对数据安全要求极高，往往要求所有服务器部署在自有机房，形成「私有云」。此时云应用市场的价值尤为突出：

- 在私有云内部署应用市场后，企业可以把经过内部审核的组件、业务系统以「应用」形式在内部快速分发与复装。
- 统一的模板与分类让私有环境下的资源交付标准化，降低运维与合规风险。
- 服务商（ISV）体系可以在私有云中映射为企业内部的供应商/团队，实现内部结算与权限隔离。
