# Go PaaS 平台开发: 路由前端管理页面与效果演示

## 纲要

- 前端页面如何衔接后端 `routeApi` 完成「添加 / 删除路由」
- 添加路由的四要素：名称、域名、路径、后端 Service 名
- 演示效果：Ingress 中两个域名绑定到不同 Service
- 通过 host 绑定或 DNS 解析验证外网可达
- 端口对应注意事项（Service 端口 vs Pod 端口）

本节完成路由功能的「前端闭环」：通过页面调用后端 API，把一条路由真正建到 Kubernetes 里，并验证外网可以访问。前端页面不是课程重点，讲师提供的是效果演示页，可自行用熟悉的框架重构。

## 添加路由的前置条件

添加路由前，后端 Pod 与 Service 要就位：

- 创建应用时（例如一个 Nginx）已经拉起对应的 Pod；
- 创建 Service 时，把该应用的服务名称记录下来——添加路由时「后端 Service 名」必须填这个名称，否则会出错。

## 添加路由：四个字段

在前端「路由设置」页添加路由，需要填写：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| 名称 | 路由自定义名称 | `nginx2` |
| 域名 | 对外绑定的域名 | `nginx2.example.com` |
| 路径 | 绑定到服务的 URI | `/` |
| 后端 Service 名 | 前面创建 Service 时的名称 | `nginx2` |

提交后，页面会多出一条记录。演示中已存在一条 `nginx`、一条刚创建的 `nginx2`，即两个域名分别绑定到两个不同 Service。

## 验证外网可达

在服务器上查看 Ingress，可以看到两个域名 + 路由已绑定到对应 Service，端口为 80：

```bash
kubectl get ingress
# 或直接看简写
kubectl get ing
```

要验证从浏览器访问，有两种方式：

- **host 绑定**（本地调试）：把 `nginx2.example.com` 指向服务器节点的公网 IP，浏览器直接访问即可。
- **DNS 解析**：正式环境把域名解析到该 IP。

访问成功即说明：应用程序通过路由把外网地址映射到了后端 Service，且后端 Service 的端口（演示为 80）已正确打通。

## 端口对应注意事项（重点）

创建应用和路由时，端口极易配错，务必注意：

- 暴露端口与 Pod 端口要对应。例如 Nginx 官方默认 80，若写成其他端口可能映射不出去。
- 添加 Service 时注意后端 Pod 端口；`RouteBackendServicePort` 填的是 **Service 暴露数据的端口**。
- Nginx Service 的 `port`（对外）与 `targetPort`（到 Pod）可以不一致，但绑路由时填的是 Service 的 `port`，和 Pod 内部端口不是一回事——填错会导致路由不通。

## 删除路由

删除同样在前端操作：点删除后，调用 `routeApi` 的 `DeleteRouteById`，后端先删 Kubernetes 里的 Ingress，再删数据库记录；页面刷新后路由列表即消失。

> 前端页面里的 API 地址要改成你实际部署的网关地址；联调时 `routeApi` 网关服务必须启动，否则通过 IP 访问接口会不通。

## 技术点总结

- 前端只是「调用 `routeApi`」的壳，核心仍是后端的添加/删除逻辑。
- 添加路由四要素：名称、域名、路径、后端 Service 名，其中 Service 名必须已在集群中存在。
- 验证靠 host 绑定或 DNS 解析；端口对应（Service port ↔ Pod port）是最高频的坑。
- 删除走「先 K8s 后 DB」的事务顺序，页面与集群状态保持一致。
