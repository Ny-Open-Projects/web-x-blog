# Go PaaS 平台开发: 服务端工程目录结构与分层说明

## 纲要

- 工程采用 DDD 式分层：domain（model / repository / service）、handler、plugin、proto
- 入口与交付物：main.go、Dockerfile、Makefile
- 分层带来的价值：需求迭代时各层独立演进、互不污染
- 课程提供自动化工具生成基础代码，再在其上扩展业务逻辑

## 为什么要定义工程目录

本章是首次正式开发代码，先把工程目录结构讲清楚。本 PaaS 平台的服务端（以 Pod 服务为例）采用清晰的分层结构，目的是让后续需求迭代时**改业务只动 service、改表只动 repository、改模型只动 model**，避免把所有逻辑堆在 handler 或 controller 中导致强耦合、难拆分。

课程约定使用 Go 1.16，创建工程时目录结构需与生成工具产出的目录保持一致，便于工具自动生成代码并落到同一目录树。

## 目录结构

```dir
pod/                        # 某个微服务，如 pod / svc / volume / route
├── domain/                 # 领域层
│   ├── model/              # 数据库模型映射（GORM 结构体）
│   ├── repository/         # 与数据库交互的数据访问层
│   └── service/            # 业务逻辑层（核心）
├── handler/                # 对外暴露的 gRPC/API 实现
├── plugin/                 # 公共插件（熔断器、中间件等）
├── proto/                  # proto 原始定义与生成代码
│   └── pod/
│       ├── pod.proto
│       ├── pod.pb.go        # protoc 生成
│       └── pod.micro.go     # go-micro 生成
├── main.go                 # 程序入口（主函数）
├── Dockerfile              # 将二进制打成镜像
└── Makefile                # 打包、生成代码等常用命令
```

## 各层职责

- **domain/model**：存放与数据库表对应的结构体（GORM tag），以及 `json` tag 用于序列化转换。
- **domain/repository**：所有与数据库交互的代码，封装增删改查与事务。
- **domain/service**：业务逻辑核心层。本层既操作数据表，又操作 K8s（TYS）等资源，是需求变更最频繁、最需要被保护的一层。
- **handler**：实现 proto 中定义的方法，并通过 gRPC 对外暴露，供 API 层或其他服务调用。
- **plugin**：常用插件统一放置，如熔断器，也可放置自定义插件。
- **proto**：存放服务的 `.proto` 原始文件，以及 protoc 生成的 `*.pb.go`、`*.micro.go` 依赖代码。

## 入口与交付

- **main.go**：程序入口，负责初始化数据库、注册中心、配置中心、K8s client，并启动服务。
- **Dockerfile**：将 `go build` 产出的二进制打包成镜像，是容器化部署的标配。
- **Makefile**：把 `go build`、生成 proto 代码等常用操作封装为命令，简化日常开发。
