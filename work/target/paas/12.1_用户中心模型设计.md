# Go PaaS 平台开发: 用户中心模型设计与多对多关联

## 纲要

- 用户中心是 Go PaaS 平台的最后一章，目标是把「用户—角色—权限」的鉴权闭环补齐。
- 基于 RBAC（Role-Based Access Control，基于角色的访问控制）建模，这是系统中最常见的权限管理方案。
- 本章服务端开发三层：model（模型） → repository（数据层） → handler（接口层），并编写多个 proto 文件。
- 三个核心模型：User（用户）、Role（角色）、Permission（权限），彼此通过多对多关系关联。
- 多对多关联使用 XORM 的 `manytomany` 标签，框架会自动创建中间关联表（如 `user_role`、`role_permission`）。
- Permission 的 `Action` 字段承载被保护资源，最常用做法是直接存放路由 / API 的访问路径，鉴权时比对「用户 ID + API 路径」是否在可控范围内。

## 用户中心的整体定位

用户中心是 Go PaaS 平台收尾的一章，把平台里「谁（User）能做什么（Permission）」这件事彻底闭环。业界最成熟的落地方式是 RBAC：给用户分配角色，给角色挂载权限，最终通过「用户 → 角色 → 权限」的链路做访问控制。

本章服务端以 `user` 服务为主体向外扩展，依次实现 `role`（角色）与 `permission`（权限）两个子域。整体分层与前面章节保持一致：

- model：定义数据结构与表关联。
- repository：封装数据库读写（基于 XORM，模板生成基础 CRUD 后按需补充接口）。
- handler / proto：对外暴露 gRPC 接口，再与前端页面联调。

## 用户模型 User

用户模型关注账号本身与状态，关键字段如下：

- `Username`：用户名，必须唯一且不能为空。
- `Email`：登录账号对应的邮箱，同样不能为空。
- `IsAdmin`：是否为管理员。
- `Password`：密码，入库前必须加密（例如使用 SHA-256），对外序列化时隐藏。
- `Status`：账号状态，通常用整型（如 0 表示正常）。
- `Roles`：与角色的多对多关联。

```go
package model

// User 平台用户
type User struct {
	ID       int64   `xorm:"pk autoincr" json:"id"`
	Username string  `xorm:"unique not null" json:"username"`
	Email    string  `xorm:"not null" json:"email"`
	IsAdmin  bool    `xorm:"default 0" json:"is_admin"`
	Password string  `xorm:"not null" json:"-"` // 入库前加密，序列化时不外泄
	Status   int     `xorm:"default 0" json:"status"`
	Roles    []*Role `xorm:"manytomany(user_role)" json:"roles"`
}
```

`xorm:"manytomany(user_role)"` 表示 User 与 Role 是多对多关系。XORM 在首次同步表结构（`Sync2`）时会自动创建名为 `user_role` 的中间表，表中保存 `user_id` 与 `role_id`，从而把「一个用户拥有多个角色、一个角色属于多个用户」这种多对多联系映射成数据。

## 角色模型 Role

角色模型相对简单：一个主键、角色名、状态，以及与权限的多对多关联。

```go
package model

// Role 角色
type Role struct {
	ID          int64        `xorm:"pk autoincr" json:"id"`
	RoleName    string       `xorm:"not null" json:"role_name"`
	Status      int          `xorm:"default 0" json:"status"`
	Permissions []*Permission `xorm:"manytomany(role_permission)" json:"permissions"`
}
```

角色名可按业务自由命名，例如总监、组长、CTO、运维岗、测试岗等。状态 `Status` 用于标识角色是否挂起或处于其他特殊类别，例如是否需要额外审批。

注意 `manytomany(role_permission)`：角色与权限同样是多对多，XORM 会自动建出 `role_permission` 中间表。这里标签名里的下划线连接词会被框架识别为关联表名，需要在代码与初始化参数上保持一致。

## 权限模型 Permission

权限模型描述「能操作什么」：

- `Name`：权限名称。
- `Description`：权限的详细描述。
- `Action`：权限对应的动作，最常用的写法是直接存放路由 / API 的访问路径（如 `/api/v1/pods`）。
- `Status`：权限状态。

```go
package model

// Permission 权限
type Permission struct {
	ID          int64  `xorm:"pk autoincr" json:"id"`
	Name        string `xorm:"not null" json:"name"`
	Description string `xorm:"varchar(255)" json:"description"`
	Action      string `xorm:"not null" json:"action"` // 路由 / API 访问路径
	Status      int    `xorm:"default 0" json:"status"`
}
```

`Action` 的理解是权限系统的核心。最粗粒度的方式就是把 API 的访问路径直接作为动作：收到请求后，用「用户 ID + 当前 API 路径」去权限集合里匹配，命中即放行，否则拒绝。当然 `Action` 也可以承载路径之外的特殊匹配字符，满足更细的匹配需求。

## 三层关联关系一览

用户、角色、权限形成一条清晰的链：

```mermaid
graph LR
    U[User 用户] -- user_role --> R[Role 角色]
    R -- role_permission --> P[Permission 权限]
    P -- Action 路由/API --> A[受保护资源]
```

- 一个用户可拥有多个角色，一个角色也可被多个用户拥有（User ⇄ Role 多对多）。
- 一个角色可挂载多个权限，一个权限也可被多个角色共享（Role ⇄ Permission 多对多）。
- 最终落到 Permission 的 `Action` 字段，即真正受控的路由或 API。

表结构由 XORM 在初始化时自动创建，关键是在 `Sync2` 或 `Sync` 调用时把这三个模型都传入，并确认框架的「自动建表」参数已开启：

```go
// 初始化时同步表结构（示例）
if err := engine.Sync2(new(User), new(Role), new(Permission)); err != nil {
	log.Fatalf("sync model failed: %v", err)
}
```

## 小结

用户中心的建模以 RBAC 为骨架，三个模型通过 XORM 的 `manytomany` 标签完成多对多映射，无需手工维护关联表。下一节将基于 User 与 Role 的多对多关系，落地 `repository` 数据层，先从角色的数据访问开始。
