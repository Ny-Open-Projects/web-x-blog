## 本章内容回顾

1. **Ingress 与 Ingress Controller 的作用**：Service 的 ClusterIP 只能在集群内部访问，NodePort / LoadBalancer 虽能公网访问但管理麻烦、受云厂商约束。于是在 Service 之上引入 Ingress，再由 Ingress Controller 通过 Nginx 反向代理到 Service。
2. **运作原理**：Ingress Controller 监听 Kubernetes API Server，通过队列定时拉取路由变更并实时更新，保证路由配置始终有效。这块原理对理解 PaaS 网络至关重要，建议结合前面的原理章节再回顾。
3. **代码实战**：与以往一样，讲师带大家开发了 Ingress Controller 的接入、用代码创建 Ingress、把路由绑定到 Service，并结合前端页面演示了效果，后台数据库操作也一并演示。

## 部署与使用经验

### DaemonSet 模式更省心

官方建议用 Deployment + LoadBalancer，但那要依赖云平台的额外 IP。课程采用 **DaemonSet** 模式，不需要云厂商 IP，高并发场景下也更适合。该模式下 Controller 直接使用主机的 80 和 443 端口对外服务，部署清单里讲师对相关字段做了注释调整，建议对照官方模板查看差异。

### 路由必须加审核与定期审查

如果长期只用一份 YAML 文件把所有路由一次性部署到集群，当路由数量超过上千甚至五千条时会极其难管理：你不知道某条路由是否还在用、是谁创建的、什么时间创建的。

因此在 PaaS 平台上，路由申请一定要加**审核机制**：

- 记录路由是谁在用、使用的时间段；
- 不定期**审查**路由背后的 Service 是否已被删除；
- 清理「僵尸路由」（后端 Service 已不存在却仍保留的路由），否则没有删除机制会越积越乱。

## 技术点总结

- 路由功能的本质是：Ingress（规则）+ Ingress Controller（执行）+ Nginx（反向代理）。
- 生产化关键不在「能创建」，而在「可治理」：审核 + 定期审查僵尸路由。
- DaemonSet + hostNetwork 是去云厂商依赖、简化部署的务实选择。
- 网络配置理解透彻，是做好 PaaS 平台的基础。
