# 11-12-本章总结

本节针对本章做一个总结。本章主要讲的是三个重点话题：熔断、限流、降级。这三个话题属于微服务生态中的一套机制，主要都是用来去保护程序，给用户更好的体验。

对于熔断，它主要的应用是针对于在客户端请求服务的时候，服务因为一些特殊的情况导致了异常，无法被请求或者请求失败，而这些请求失败的因素是非正常的错误，比如严重的超时问题。当遇到这样的情况的时候，意味着服务端可能比较繁忙，没法进行访问或者服务端有内部的故障。因此在客户端来说，如果所有的请求每一次都去请求服务端，都要去涉及到超时，并且性能并不一定很好，也会造成没必要的资源的消耗。所以程序上对于在请求服务端的时候，这种存在故障的情况，就会去设置熔断，根据请求在请求过程中它的失败和请求的情况，做一个计算，计算它是否达到了一个阈值。如果达到一个阈值，那么此时之后的请求有一段时间将不再去请求服务端，而是直接给它返回出错误的信息，熔断了与服务端的访问，直接返回出结果。

在 go-zero 中，对于熔断，它的设置是有两个地方的，分别是在客户端和服务端，它们的拦截器中都有应用熔断。因为对于熔断来说，无论在服务端层面还是在客户端层面都是有必要的。在客户端设置熔断是因为服务端可能会存在故障的因素导致宕机，访问不到，所以此时用熔断是有必要的。而在服务端使用熔断是因为服务端内部的程序在执行的过程中也可能会产生不定的因素，导致服务端内部业务的执行会有较长的延迟问题，因此内部它自己也是直接性的熔断了。所以这里在客户端和服务端均有设置熔断机制。

而在熔断的时候，实际上来说，它主要的核心是基于这个自适应的熔断算法来实现的。在算法中，它根据一定时间的请求数及请求成功数这两者来计算结果，而以 k 作为一个固定的阈值，可以说作为一个权衡值。在过程中，正常而言，请求成功数等于请求总数，这是正常情况，那么以公式的结果来计算，它一定是小于零的。但在不正常的情况下面，请求总数远远大于了成功数，此时通过公式的运算，发现结果大于零，那么此时就会开启熔断。这就是这个自适应的公式，也是整个自适应熔断核心的算法。

而在熔断中，针对业界来说，它往往会设置三个状态：开启、关闭、半开放，这是在常规熔断器中的实现。业界中大部分的熔断机制都会有这么三个状态，可以了解一下。关闭是属于初始状态；开启是已经达到阈值了，那么就开启；半开放状态的特点是会放一个请求往后执行，如果成功就恢复，失败就继续开启，它主要起到一个恢复的作用。这是在业界中大部分熔断机制的实现。当然在 go-zero 的熔断中，它主要是基于自适应算法，在这个自适应算法中就已经自动地去进行了这三个开关的处理，不需要再额外去做一些处理。

接下来看限流。限流在 go-zero 中的实现，主要有三个方面：第一是基于 channel，第二是基于令牌桶，第三是基于滑动窗口计数，这三种方式的实现。

其中基于 channel，这个是很容易理解的，channel 本身是一个有缓冲的通道，从它的源码来看，在这个有缓冲的通道中，向它里面写数据的时候，如果说是满的情况，会阻塞；如果说是还有空间，那是能够写进去的。所以它这里定义了两个方法，一个是向它写数据，第二个是向它读数据。向它写数据是验证是否进行限流了，而向它读数据是用于释放这一个信号量。所以在使用这一个机制的时候，这两个方法一定要都存在，如果说缺失一个，会导致程序阻塞，可能会引发死锁问题。所以在使用这两个方法时候，要注意。

基于令牌桶的实现，可以看这个流程图。在图中，程序中一般都会有一个定时器，用于去恒定去生成 Token，同时也会定义一个桶，它能存放到 Token，生成的 Token 都会使用到这个桶里面。如果说这个桶是满的，那么生成的 Token 都会被丢弃。当请求进来之后，是从桶中去获取 Token，请求的时候，如果能够得到，那么就正常处理，如果不能得到，那就失败。而 go-zero 中对它的设计，主要是基于 Redis 来实现的。在上面这一份脚本，是去获取令牌的，然后再依据后续的流程，再去进行相应的处理。在流程中，它针对 Redis 也可能会存在一些异常的情况，因此它还提供了自己内部实现的机制来进行兜底，以免 Redis 出现了异常，然后导致这一个机制出现了故障，所以它也提供了自己默认的方式来进行兜底。

再来看滑动限流。滑动限流和 Token 具有相似性，它是以恒定的速率来进行滑动。然后在滑动过程中，它会为自己的这个计算的公式的范围，定义对应的窗口。它的滑动速率，一般是根据这个窗口的数量及滑动的时间来进行计算，计算出它的滑动速率，然后再依据滑动速率来进行移动。在这个过程中，会有请求进来，请求进来的时候都会填写在最前面的这个窗口里面，那么会存放着所有这个请求。然后会定义一个阈值，这个阈值定义好之后，每一次请求的时候都会去计算，在这个窗口里面，它所有的请求数是否达到了这个阈值。如果没有达到，那么可以继续的写数据，如果达到了，那么就会拒绝。而在过程中，如果说它滑动过去了，那么之前在这个窗口内的数据，就不会作为计算的条件了。所以这个过程，它是不断地去变化的。而这个滑动限流的方式，实际上在 go-zero 中也主要是基于 Redis。在这里这一份脚本，在过程中它基于 TTL 定义了一个过期的 key，它会通过这个命令去统计，在这个时间范围内所接收的请求数量，再以此来判断它是否超过了最大的值，并返回出相应的结果，依次来实现限流。

再来看降级。对于降级，在 go-zero 中的应用主要可以分为两种，就是它自己内部实现的 API 的中间件，及 RPC 的拦截器，但它们主要应用在服务端。而结合熔断器实现的，主要是面向于 RPC 客户端的。再来看看，在服务端中，中间件与拦截器它们的应用，是利用了 go-zero 的自动降级，自动降级主要是依据滑动平均算法来实现。在这个算法中，核心点就是依据在上一个时间点所计算的平均值，以及当前这一个点所计算的平均值，再围绕这个权重值得到的值，再与最大的负载值进行计算，判断是否进行降级。而这一个算法，在应用中，它主要应用在服务端，因为它除了根据当前请求所能承受的速率以外，它基于 CPU 的这些情况，来进行限流，在这里就实现了。所以在 go-zero 中，主要就为 API 和 RPC 服务这两者去使用自动降级。

在客户端中，想要去对某个 RPC 的请求情况去应用降级，那么可以结合熔断器，熔断器也为它提供了相应的方法，可以供我们去进行使用，这两个都是可以去应用到的，在失败的时候去进行执行。当然这一种方式，就意味着会导致代码的侵入了。

整体来说，这是本节课的重点内容：熔断、限流、降级。本节课就总结到这里。
