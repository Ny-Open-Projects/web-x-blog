# 12-6-ELK日志收集三件套架构分析

前面已经理解了 go-zero 中的链路跟踪。接下来讨论微服务系统中的日志收集三件套 ELK。

本节先了解 ELK 是做什么的、能解决什么样的问题，再了解 ELK 的工作模式和工作过程。

## ELK 解决什么问题

理解 ELK，可以先从一个问题谈起：目前的服务系统下部署的服务比较多，像用户服务、订单服务，除了微服务以外，还有 MySQL、Redis 这些服务。每个服务在运行过程中都会产生相应的日志文件。这些日志文件产生之后，在系统运行或程序性能分析中，我们会尝试收集这些日志再进行分析，通过日志排查系统是否存在问题，或者系统中是否有更好的优化空间。

所以项目中日志的收集和分析必不可少。但目前的问题是，日志分散在多个服务，不同服务之间又相互关联，此时日志如何收集就成了一个新的问题，而且是一个比较大的挑战。

为此业界提出了 ELK 架构来解决。它可以帮助开发人员收集日志并将日志汇总，转化成可视化的仪表盘，通过仪表盘分析项目的执行情况和日志的数据情况。

## ELK 的工作过程

ELK 是三个软件的结合：E 是 Elasticsearch，L 是 Logstash，K 是 Kibana，即这三个程序的合称。

首先，在各个运行的程序中都会有一份脚本，这个脚本（即 Beats 系列的程序）帮助 Logstash 收集各个服务自己的日志文件信息。Logstash 会将收集的日志推送给 Elasticsearch。Elasticsearch 专注于搜索引擎，再结合 Kibana 做数据的可视化，根据日志展示出各个仪表盘。开发人员可以通过 Kibana 配置相应的仪表盘，很快分析出项目的实际情况、日志的数据情况。

ELK 三件套的工作过程如下：

```mermaid
flowchart LR
    A[「各服务产生的日志文件」] --> B[「Filebeat：Beats 系列采集脚本」]
    B --> C[「Logstash：收集日志并推送」]
    C --> D[「Elasticsearch：专注于搜索引擎」]
    D --> E[「Kibana：数据可视化仪表盘」]
```

这就是整个 ELK 的工作过程。

另外有一点注意：关于 ELK 的信息搜集，这里的脚本叫 Filebeat，属于 Beat 系列。除了日志以外，它还可以搜集项目运行过程中的系统情况，比如 CPU 的执行情况、内存情况等，都会搜集起来。所以它能搜集的信息其实非常多。目前业界中也经常通过这套方案来解决系统日志信息的搜集。

以上就是 ELK 这套架构的整体工作情况。
