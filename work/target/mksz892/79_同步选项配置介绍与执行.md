# 79. Argo CD 同步选项：忽略差异、同步策略、重试与状态机全解

## 纲要

- **同步选项是 Argo CD 的「自动驾驶规则」**：忽略差异（什么不管）+ 同步策略（何时自动推）+ 同步选项（怎么推）+ 重试（失败怎么办）四层配置
- **忽略差异的头号场景是 HPA**：YAML 声明 1 副本、集群 HPA 扩到 3——不忽略 `/spec/replicas`，同步会把 3 个 Pod 砍成 1，HPA 反复横跳
- **selfHeal 是双刃剑**：开它=集群永远对齐 git（配置漂移的克星）；但**回滚必先关它**——否则刚回滚的版本被自动「修复」回 git 里的版本
- **六项 syncOptions 各有分工**：Validate 验证格式、CreateNamespace 自动建 ns、PruneLast 删除排最后、ApplyOutOfSyncOnly 只同步变动、ServerSideApply 服务端合并、RespectIgnoreDifferences 联动忽略配置
- **重试策略指数退避**：limit 5 次、初始 5 秒、因子 2 倍增、上限 3 分钟——5s→10s→20s→40s…封顶 3m
- **状态机两维**：同步状态（Synced/OutOfSync/Unknown/Error）× 健康状态（Healthy/Degraded/Progressing/Paused/Missing）——排查先定位是哪一维出问题

## 一、场景引入：自动同步不是「开了就完事」

#77 讲过：Argo CD 默认只检测 diff、不自动同步。开自动同步只要一个开关，但**开完之后会发生什么、什么该忽略、失败了怎么办**，全靠同步选项这层配置。课程用一整节讲它，因为这里是 Argo CD 生产落地的「规则密集区」——配错了的典型症状：

- HPA 扩好的 Pod 被同步砍掉，监控疯狂报警；
- 想回滚到旧版本，回滚完秒变回新版（selfHeal 在暗中「修复」）；
- 改了个镜像 tag，整个应用所有资源重新 apply 一遍，API Server 压力山大；
- 同步偶发失败一次，应用就卡在 OutOfSync 没人管。

本节把四层规则（忽略差异 / 同步策略 / 同步选项 / 重试）+ 两维状态机一次讲透。

## 二、忽略差异：什么不用管

### 2.1 概念与头号场景

「忽略差异」定义**同步期间要忽略的某个资源的差异配置**。课程的头号场景是 HPA：

> 「我们要忽略的这个配置是我们的一个副本配置的一个副本。YAML 配置了一个副本，但是集群当中已经启动了自动伸缩功能，这个时候集群当中存在三个副本……当我们的资源清单同步到集群当中的时候，它就会把三个 Pod 变成一个。同步之后，这两个 Pod 就不存在了。所以我们的自动伸缩就会受到影响。」

即：**声明值（1）与运行时值（3）的合法分歧**——HPA 按负载扩容是运行时决策，git 声明不该覆盖它。配置：

```yaml
ignoreDifferences:
- group: "apps"
  kind: "Deployment"
  jsonPointers:
  - /spec/replicas        # 副本数永不同步
```

`jsonPointers` 是 JSON Pointer 语法——精确到字段级忽略（`/spec/replicas`），不是忽略整个资源。分析模板篇（#85）还会遇到第二个忽略场景：**Service 的 `rollouts-pod-template-hash` 选择器**（Argo Rollout 动态改写，不同步会打架）。

## 三、同步策略：何时自动推

```yaml
syncPolicy:
  automated:
    prune: true        # 自动清理 git 中已删除的资源
    selfHeal: false    # 自愈：集群被改歪自动拉回 git 状态
    allowEmpty: false  # 不允许同步空的资源定义
```

三个开关逐个看：

| 开关 | 作用 | 课程讲解 |
| --- | --- | --- |
| **prune** | git 里删了某资源 → 同步时自动清集群的对应资源 | 「在 git 这边删除了，那 Argo CD 读到这个仓库有发生变化之后，就会自动清除这个集群当中的 SVC」 |
| **selfHeal** | 集群现状与 git 不一致 → 自动修复 | 「保证我们集群当中的 YAML 跟我们 git 仓库当中的 YAML 一模一样」 |
| **allowEmpty** | 允许同步为空的资源定义 | false——空清单肯定不允许 |

**页面开启路径**（课程实拍）：进入应用 → 点**细节** → 同步策略 → 手动开启 → 勾选「自动同步」「自动修剪」→ 点 ok。三个开关在页面上是两个勾选框（自动同步 + 自动修剪）加一个恒不勾的自动修复——**页面能开，但 syncOptions 六项与 retry 页面没有对应控件**，课程因此转向「终端 apply 一份配好的 YAML」：「这些都需要我们每一次都去勾上，才会选中这些选项，所以我们需要在终端上进行配置。后面我们再手动点，也不需要再每次都来这里勾了。」这就是 #79 标题里「配置介绍」与「执行」两节的由来：策略开关页面点，其余规则 YAML 写。

**selfHeal 与回滚的冲突是本节最重要的生产知识点**。课程的推演：

> 「比如说我们当前的集群是第二个版本 b2……我们现在要通过 Argo CD 把我们的版本回滚到 b1。这个时候集群的 image 是 b1，跟仓库当中的 b2 不匹配。当我们开启了自动修复之后，我们回滚到 b1，它就会又自动帮我们修复成 b2 的版本……所以这个自愈的功能，我们不可以开启。」

即：**回滚的本质是让集群暂时偏离 git**（git 还写着旧 tag），selfHeal 的存在会让回滚秒失效。生产纪律：**回滚前关 selfHeal，回滚完成、git 也更新后再开回来**。这也是课程配置里 selfHeal 恒为 false 的原因。

## 四、同步选项：怎么推

六项 syncOptions，课程逐个解释了含义（课件样例全量启用）：

| 选项 | 作用 | 课程讲解 |
| --- | --- | --- |
| `Validate=true` | 同步前验证 YAML | 「对我们的 YAML 文件进行验证……字段配错了或者格式没有对齐就会报错」——改格式重新提交 |
| `CreateNamespace=true` | 命名空间不存在则自动创建 | 「需不需要自动创建」 |
| `PrunePropagationPolicy=foreground` | 前台模式执行（清理过程可见） | 「想要在前台当中显示正在部署清理什么的」 |
| `PruneLast=true` | 删除操作排最后 | 「优先先同步 Deployment 这个资源，然后再把我们的 SVC 进行删除」——先建后删，避免服务真空 |
| `ApplyOutOfSyncOnly=true` | 只同步变动过的资源/字段 | 「只修改了 image 字段，那我就只同步这个字段的内容，不会把整个 YAML 都再重新执行一遍」 |
| `ServerSideApply=true` | 用服务端 apply | 「相当于我们在服务器上执行 kubectl apply」 |
| `RespectIgnoreDifferences=true` | 让忽略差异配置生效 | 「我们要不要开启忽略差异……开启了之后，我们就可以执行我们前面讲的忽略差异的一个配置」 |

课程实战的两个关键验证：

1. **`ApplyOutOfSyncOnly` + 忽略差异的配合**：配了 `/spec/replicas` 忽略后，把副本从 2 改 1——「可以看到没有变化，那就证明这个配置已经成功了，这边不管怎么修改，这边都不会进行同步」；
2. **YAML 配了即生效**：即使 UI 复选框没勾，YAML 里写了的 syncOptions 照样生效——「尽管那个同步的复选框我们没有给它加上来，也没有问题了」。

### 4.1 忽略差异的字段细节

课程实拍补了两个官网不会细说的点：

- **group 填 API 组不填版本**：Deployment 的 apiVersion 是 `apps/v1`，`group` 只填 `apps`——版本段不进 group；
- **不需要同步的字段可注释**：jsonPointers 列表项可以注释掉临时恢复同步，改完再放开——调试忽略配置时不用整段删。

### 4.2 从「配了」到「生效」的完整动线

课程的执行顺序值得照抄：**先准备一份含全部规则的 YAML（同步策略 + syncOptions + retry + revisionHistoryLimit 6 + 忽略差异）→ `kubectl apply` → 回页面点 sync 确认选项已勾上 → 改副本数 2→1 验证忽略生效**。「apply 完就看效果、效果不对再核页面」——YAML 是唯一事实源，页面只是它的投影。

## 五、重试策略与历史版本

```yaml
retry:
  limit: 5                    # 最多重试 5 次
  backoff:
    duration: 5s              # 首次重试等 5 秒
    factor: 2                 # 每次延迟 ×2
    maxDuration: 3m           # 延迟上限 3 分钟
revisionHistoryLimit: 6       # 保留 6 个历史版本
```

指数退避的节奏：**5s → 10s → 20s → 40s → …（封顶 3 分钟）**——课程原话：「第一次会等五秒，第二次就五乘二十秒，第三次五乘以二再乘以二……最大不会超过三分钟。」`revisionHistoryLimit` 控制页面「历史版本与回滚」里保留几条记录。

## 六、状态机：同步状态 × 健康状态

Argo CD 应用的展示是两维状态，排查先定位维度：

### 6.1 同步状态（Sync Status）

| 状态 | 含义 | 处置 |
| --- | --- | --- |
| **Synced** | 集群与 git 一致 | — |
| **OutOfSync** | 检测到不一致 | 点 sync，或开自动同步 |
| **Unknown** | 同步期间出错，状态未定 | 查同步日志 |
| **Error** | 同步失败 | 查 YAML 配置/资源问题 |

### 6.2 健康状态（Health Status）

| 状态 | 含义 | 课程讲解 |
| --- | --- | --- |
| **Healthy** | 正常 | — |
| **Degraded** | 部署失败 | 「检查是镜像有问题还是哪里有问题」 |
| **Progressing** | 部署中 | — |
| **Paused** | 暂停 | 灰度发布专用——「先部署两个 Pod，后面的暂时不部署，验证通过再继续」 |
| **Missing** | 资源缺失 | 「某些资源在应用程序中缺失」——如 Service 被删 |

### 6.3 两种「不同步」的方向差异（课程实战核心）

课程实拍了一个极易混淆的点，专门澄清：

- **git → 集群方向**：仓库变了显示 OutOfSync/diff，靠**同步策略（automated）**自动同步；
- **集群 → git 方向**：集群里的 YAML 被手工改了/资源被删了，显示 OutOfSync 或 Missing，靠 **selfHeal** 自动修复——不开 selfHeal 就水远差着。

「比如我这边先删除一下 Service……它就会显示缺失状态，因为它不会帮我们做同步嘛，我们没有开启自动同步。」——页面删集群资源制造 Missing，再 sync 拉回，课程用这个动作演示了状态转换的完整闭环。

### 6.4 两种粒度的 sync：全局与单资源

课程实拍区分了两个入口：

- **全局同步**：页面顶部 sync——「全局同步所有的有变化的清单文件」，多应用有变化时一把推；
- **单资源同步**：进应用内对某个资源（如 Service）点 sync——「只会同步这个 service 变化的一个清单文件」，精准修复单个资源。

配套的观察技巧：首页可按状态筛选——课程删了 Service 后「选中缺失就可以看到我们有两个应用是显示缺失的状态」，批量巡检缺失/不同步应用时比逐个翻快得多。sync 完成后状态回到 Healthy，再 sync 一次让全部保持一致。

## 七、生产实践要点

1. **忽略差异先配 HPA 场景**：任何用 HPA 的 Deployment，`/spec/replicas` 必须进 ignoreDifferences——这是 Argo CD + HPA 共存的铁律；
2. **selfHeal 按需分级**：测试环境可开（漂移即修复），生产环境权衡——要「 Git 纯净」就开，要「应急手工改集群」就关；**回滚前必关**；
3. **prune 开启前审 git**：prune 会自动删集群资源——git 里误删一份 YAML，集群服务跟着消失。重要仓库开分支保护 + PR review 再开 prune；
4. **syncOptions 全量启用是稳妥默认**：Validate/CreateNamespace/PruneLast/ApplyOutOfSyncOnly/ServerSideApply 五项生产建议全开；RespectIgnoreDifferences 与忽略配置联动开；
5. **retry 防抖动**：指数退避 limit 5 + maxDuration 3m 是官方推荐值——同步偶失败（如 API Server 限流）自动重试，不用人盯；
6. **状态机两维定位法**：先看同步状态（git 到集群的通路问题）还是健康状态（ Pod 自身问题）——Degraded 查镜像/探针，OutOfSync 查同步策略，Missing 查 prune 或误删；
7. **历史版本 6 条够用**：revisionHistoryLimit 6 平衡追溯与存储；回滚认 commit message（#80）。
8. **3 分钟轮询是保底不是主力**：Argo CD 默认每 3 分钟读一次仓库——紧急变更别干等，手动点 sync 或配 webhook（#80）立刻触发。
9. **忽略配置跟着策略走**：忽略差异只有在 `RespectIgnoreDifferences=true`（或同步选项勾了忽略差异）时才生效——只配 ignoreDifferences 不开联动开关，等于没配。
10. **页面勾选与 YAML 双轨归一**：调试期可在页面勾选项快速试效果，定型后必须落 YAML——页面勾选不随集群迁移重建，YAML 才是团队共享的真相。

## 八、报错排查表

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| HPA 扩的 Pod 被同步砍掉 | 没配 `/spec/replicas` 忽略 | ignoreDifferences 加 jsonPointers |
| 回滚后秒变回新版 | selfHeal 开着，「修复」了回滚 | 回滚前关 selfHeal |
| git 删了 YAML 集群资源还在 | prune 没开 | syncPolicy.automated.prune: true |
| 改一个字段全量 apply | ApplyOutOfSyncOnly 没开 | syncOptions 加 `ApplyOutOfSyncOnly=true` |
| 集群手工改的配置被冲掉 | selfHeal 自动修复 | 需要的临时改动走 git；或评估关 selfHeal |
| 应用显示 Missing | 集群资源被删 | 点 sync 拉回；查谁删的 |
| 应用 Degraded | Pod 起不来（镜像/探针/资源） | 进应用看 Pod 事件与日志 |
| 同步偶发失败后卡住 | 没配 retry | 加 retry backoff 指数退避 |
| 忽略配了但不生效 | `RespectIgnoreDifferences` 没开 / group 填错 | 开联动开关；group 填 `apps` 不填 `apps/v1` |
| 页面勾了选项 YAML 却没有 | 只点了页面没落 YAML | 配好的 YAML 重新 apply，页面与 YAML 双轨归一 |
| 批量应用缺失难定位 | 逐个翻应用 | 首页按「缺失」筛选，批量定位后逐个 sync |

## 九、面试考点与追问

**Q1：忽略差异是干什么的？典型场景？**
定义同步期间要忽略的资源字段差异。典型场景：HPA——YAML 声明 1 副本、HPA 按负载扩到 3，不同步 `/spec/replicas` 避免把扩容结果砍回去。

**Q2：selfHeal 的作用？为什么回滚前要关掉？**
selfHeal 让集群持续对齐 git（配置漂移的克星）。回滚是让集群**暂时偏离** git（git 还写着旧 tag），selfHeal 会把回滚结果「修复」回 git 版本——所以回滚前必关，回滚完 git 更新后再开。

**Q3：prune 与 allowEmpty 的区别？**
prune：自动清理 git 中已删除的资源（集群跟着删）；allowEmpty：是否允许同步空的资源定义（恒 false）。一个管「删干净」，一个管「防空同步」。

**Q4：syncOptions 六项各是什么？**
Validate（同步前验证 YAML）、CreateNamespace（命名空间不存在自动建）、PrunePropagationPolicy=foreground（前台执行）、PruneLast（删除排最后，先建后删）、ApplyOutOfSyncOnly（只同步变动字段）、ServerSideApply（服务端 apply）。RespectIgnoreDifferences 让忽略配置生效。

**Q5：重试策略的参数与退避节奏？**
`retry.limit: 5`、`backoff.duration: 5s`、`factor: 2`、`maxDuration: 3m`——节奏 5s→10s→20s→40s…封顶 3 分钟，防同步抖动卡死。

**Q6：同步状态与健康状态分别有哪些？怎么定位问题？**
同步状态：Synced/OutOfSync/Unknown/Error（git 到集群通路）；健康状态：Healthy/Degraded/Progressing/Paused/Missing（Pod 自身）。先定位维度：Degraded 查镜像探针、OutOfSync 查同步策略、Missing 查 prune/误删。

**Q7：「git 变了不同步」和「集群变了不同步」是一回事吗？**
不是。git 变 → 靠 automated 同步策略自动推；集群被手工改/删 → 靠 selfHeal 自动修复，不开就永远差着。两个方向两套机制。

**Q8：全局 sync 与单资源 sync 怎么选？**
全局 sync 推所有有变化的清单（多应用批量变更时高效）；单资源 sync 只推该资源变化的字段（精准修复、减少无关 apply 抖动）。日常小改走单资源，版本发布走全局。

**Q9：ignoreDifferences 的 group 字段怎么写？**
填 API 组不填版本——Deployment 的 `apps/v1` 只写 `apps`；Service 这类核心组写空字符串 `""`。写错的表现是「配了忽略却不生效」。

**Q10：为什么说页面勾选只是权宜？**
页面勾选存在 Argo CD 的应用状态里，不随 YAML 迁移、不便评审、重建环境即丢。团队协作与 IaC 都要求规则落 YAML——页面是调试台，YAML 是事实源。

**技术点总结**：Argo CD 同步选项 = 四层规则叠加：**忽略差异**定边界（HPA 的 `/spec/replicas` 是头号必配）、**同步策略**定时机（automated + prune + selfHeal，其中 selfHeal 与回滚互斥——回滚前必关）、**syncOptions** 定手法（Validate/CreateNamespace/PruneLast/ApplyOutOfSyncOnly/ServerSideApply 六项，YAML 写了即生效）、**retry** 定容错（5s×2 指数退避封顶 3m）。配完后靠**两维状态机**运维：同步状态（Synced/OutOfSync/Unknown/Error）看 git 到集群的通路，健康状态（Healthy/Degraded/Progressing/Paused/Missing）看 Pod 自身。两条生产铁律收口：**HPA 场景忽略副本、回滚前后管理 selfHeal**——自动同步不是开了就完事，规则配对才是自动驾驶。
