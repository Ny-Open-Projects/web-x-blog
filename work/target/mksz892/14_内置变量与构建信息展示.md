# Jenkins 内置变量与构建信息展示：让报警说人话

## 纲要

- **内置变量是报警信息的原料**：不引用变量，报警只能说"构建失败了"；引用后能说"test 项目第 63 次构建的 clone 阶段失败了"
- **四个最常用变量**：`JOB_NAME`（项目名）、`BUILD_NUMBER`（第几次构建）、`STAGE_NAME`（当前阶段）、`BUILD_URL`（构建链接）
- **查看全部变量的官方入口**：`流水线语法 → 全局变量`，不用猜也不用背
- **`currentBuild.description` 与 `displayName`**：把镜像版本、commit id、提交消息写到构建页面上，一眼定位这次构建发布的是什么
- **Build User 插件补齐"谁触发的"**：提供 `BUILD_USER_ID` / `FIRST_NAME` / `LAST_NAME` / `EMAIL` 系列变量，用 `wrap` 方法启用
- **最佳位置是 `post` 而非 `steps`**：成功时显示"部署成功 + 镜像名"，失败时显示"部署失败"，信息随构建结果动态变化
- **自由式项目做同样的事很别扭**：要在不同配置页东翻西找，流水线一处搞定——又一次印证 Pipeline 的优势

## 一、内置变量：报警信息的原料

### 1.1 为什么必须用内置变量

先看一个反面案例。很多新手写的报警长这样：

```groovy
post {
    failure {
        sh 'curl ... -d "构建失败了"'
    }
}
```

收到这条报警的人第一反应是：**哪个项目？第几次？哪一步？链接在哪？** ——然后他要自己去 Jenkins 翻，翻的过程就是时间浪费。

**用了内置变量之后**，同一条报警可以变成：

```text
❌ 构建失败
项目：test
构建号：#63
阶段：clone
链接：http://jenkins.example.com/job/test/63/
```

信息完整，收到就能点链接进去看。**这就是内置变量的价值——它让报警说人话。**

### 1.2 四个最常用变量

| 变量 | 含义 | 报警里的用途 |
|---|---|---|
| `JOB_NAME` | 当前部署的**项目名字** | 指明是哪个项目出问题 |
| `BUILD_NUMBER` | 你是第几个构建 | 唯一标识本次构建 |
| `STAGE_NAME` | 当前是哪一个阶段 | 定位失败在哪个环节 |
| `BUILD_URL` | 本次构建的链接 | 一键跳转看日志 |

还有一批常用的：

| 变量 | 含义 |
|---|---|
| `BUILD_ID` | 构建 ID（历史上与 BUILD_NUMBER 相同） |
| `BUILD_TAG` | `jenkins-${JOB_NAME}-${BUILD_NUMBER}` 拼接串 |
| `JENKINS_URL` | Jenkins 地址 |
| `WORKSPACE` | 当前工作空间路径 |
| `GIT_COMMIT` | 当前提交的 commit hash |
| `GIT_BRANCH` | 当前分支 |

### 1.3 去哪里查全部变量

**不用背。** Jenkins 提供官方入口：访问 **`流水线语法（Pipeline Syntax）→ 全局变量（Global Variables）`** 页面，里面列出了所有内置变量（`BUILD_ID`、`JOB_NAME`、`BUILD_TIME` 等）。

> 课件原话：**如果我们需要哪一个变量，我们可以把这个变量拷过来，直接输出就可以。**

### 1.4 实战：拼一条完整的报警信息

```groovy
stage('Clone') {
    steps {
        echo '''
            部署项目：${JOB_NAME}
            构建编号：#${BUILD_NUMBER}
            部署阶段：${STAGE_NAME}
            构建链接：${BUILD_URL}
        '''
    }
}
```

课件实测输出：

```text
部署项目：test
构建编号：#63
部署阶段：clone
```

对应关系：

- `JOB_NAME` = `test`（流水线名称）
- `BUILD_NUMBER` = `63`（第 63 次构建）
- `STAGE_NAME` = `clone`（当前 stage 名）

> **注意 `STAGE_NAME` 的语义**：它是**当前所在 stage 的名字**。在 `clone` stage 里 echo，输出的就是 `clone`。放在 `post` 里用时要注意——`post` 在 stage 外执行时 `STAGE_NAME` 可能取不到值，需要单独处理。

### 1.5 变量的典型用法

课件点明了核心场景：

> 这个变量一般是用在我们构建完成之后，**调用这个变量来进行报警**。那我们可以知道构建项目是哪一个、构建仓库是哪一个、build id 是哪一个。

即：**`post` + 内置变量 = 完整可定位的报警**。

## 二、构建页面信息展示：把关键信息写到构建上

光有报警还不够。**构建列表页**上默认只显示 `#63` 这样的数字，时间一长根本分不清哪个构建对应哪个版本。

Jenkins 允许你**自定义构建的描述信息和显示名称**。

### 2.1 两个关键属性

| 属性 | 作用 | 适合放什么 |
|---|---|---|
| `currentBuild.description` | **构建描述信息**，显示在构建页面 | 镜像版本号、commit id、提交消息 |
| `currentBuild.displayName` | **构建的显示名称**，替换默认的 `#数字` | `部署成功-v1.2.3-#63` |

### 2.2 实操写法

```groovy
stage('Info') {
    steps {
        script {
            currentBuild.description = "镜像: app:${BUILD_TAG}<br>Commit: ${GIT_COMMIT}"
            currentBuild.displayName = "v1.2.3-#${BUILD_NUMBER}"
        }
    }
}
```

**课件里强调 description 可以填写的内容**：

- **构建的镜像版本号**
- **构建的 commit id**
- **构建的提交消息**

配完之后，**在构建地址的构建页面上就可以查看到这个构建信息**。

### 2.3 放在 post 里更合适

课件明确说：这个配置放在 `steps` 里**并不是最适合的位置**，**我们可以把它放到 `post` 里面**。

```groovy
post {
    success {
        script {
            currentBuild.displayName = "部署成功-v1.2.3-#${BUILD_NUMBER}"
        }
    }
    failure {
        script {
            currentBuild.displayName = "部署失败-#${BUILD_NUMBER}"
        }
    }
}
```

课件实测效果：

- 构建成功 → 构建列表显示 **"部署成功-v1.2.3-#63"**；
- 把流水线改成失败 → 显示 **"部署失败-#64"**。

**这样扫一眼构建列表，就知道每次构建的结果和版本**，不用逐个点进去。

### 2.4 Build User 插件：补上"谁触发的"

前面的信息解决了"哪个项目、哪个版本、成功没有"，但还有一个维度：**这次构建是谁触发的？**

手动点的能看"构建用户"，但 **webhook 自动触发时显示的是"自动触发"**，看不出是谁提交的代码。

装 **Build User 插件**可以补齐。装完后提供这些变量：

| 变量 | 含义 |
|---|---|
| `BUILD_USER_ID` | 用户 ID |
| `BUILD_USER_FIRST_NAME` | 名字 |
| `BUILD_USER_LAST_NAME` | 姓 |
| `BUILD_USER_EMAIL` | 邮箱 |

**启用方式**（不是直接可用，要用 `wrap` 包起来）：

```groovy
stage('Build User') {
    steps {
        wrap([$class: 'BuildUser']) {
            echo "构建用户: ${BUILD_USER_ID}"
            echo "姓名: ${BUILD_USER_FIRST_NAME} ${BUILD_USER_LAST_NAME}"
            echo "邮箱: ${BUILD_USER_EMAIL}"
        }
    }
}
```

课件实测：用 `wrap` 包裹后能正确输出构建用户 `test`。

**如果不知道插件怎么用**：插件管理 → 已安装 → 搜索该插件 → 点进去有**插件帮助页面**，列出所有变量与用法。这是查插件用法的标准路径。

> **补充说明**：`script` 块可以执行流水线内置方法、Groovy 脚本，也可以执行 `sh` 命令——所以 `currentBuild` 与 `wrap` 这类调用都放在 `script` 里。

## 三、为什么这些一定要用流水线做

课件做了自由式项目的对比，结论明确：

> 我们使用流水线的话，配置这些是非常方便的。但是如果你用自由式的项目的话，那使用起来配置起来就比较麻烦一点。

具体差在哪：

- **设置构建用户**：自由式项目要装插件后去特定配置页勾选，且**没装插件时那个配置项根本不存在**（课件说"以前我部署的时候，它这个是要你输入一个变量名，现在这边已经没有输入框了"——版本差异导致配置位置不稳定）；
- **描述信息 / 显示名称**：自由式项目要么装插件要么写后处理步骤，散落多处；
- **流水线**：全部在 `post` + `script` 里统一完成，可读、可版本化。

## 四、常见报错与排查

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| `${JOB_NAME}` 输出空 | 用了单引号，或不在 pipeline 上下文 | 用双引号 / 三引号 |
| `STAGE_NAME` 取不到值 | 在 `post` 里执行，已脱离 stage 上下文 | 在 stage 内先用局部变量存起来 |
| `BUILD_USER_ID` 为空 | 没用 `wrap([$class: 'BuildUser'])` 包裹 | 用 wrap 启用 |
| `currentBuild.displayName` 不生效 | 没放 `script` 块 | 包在 `script { }` 内 |
| 构建列表名称没变 | 配在 `steps` 里但构建后又跑了别的 | 移到 `post` 的 success/failure |
| 装完插件没这些变量 | 没重启 | `/restart` |

## 五、面试考点与追问

**Q1：常用的 Jenkins 内置变量有哪些？分别用途？**
`JOB_NAME`（项目名）、`BUILD_NUMBER`（构建序号）、`BUILD_URL`（构建链接）、`STAGE_NAME`（当前阶段名）、`GIT_COMMIT`/`GIT_BRANCH`（Git 信息）、`WORKSPACE`（工作空间）。核心用途是拼装报警信息，让报警可定位。

**Q2：`currentBuild.description` 和 `currentBuild.displayName` 的区别？**
`description` 是构建的**描述信息**，显示在构建详情页，适合放镜像版本、commit id、提交消息；`displayName` 是**显示名称**，替换构建列表里默认的 `#数字`，适合放"部署成功-v1.2.3-#63"这类结论性信息。

**Q3：为什么这两类信息更适合放 `post` 里？**
因为 `post` 能按构建结果分支处理——成功时显示"部署成功 + 版本"，失败时显示"部署失败"。放在 `steps` 里则无法根据结果动态调整，且可能在构建失败前来不及执行。

**Q4：Build User 插件的变量能直接用吗？**
不能。必须用 `wrap([$class: 'BuildUser']) { }` 包裹才能生效。这是插件的特殊机制——它需要包一层构建上下文才能注入变量。

**Q5：webhook 自动触发时怎么知道是谁的代码？**
`BUILD_USER` 系列在自动触发时反映的是触发源。要精确到"哪次 commit 是谁提交的"，应结合 `GIT_COMMIT` 去 Git 平台查提交记录，或让报警内容带上 commit 信息与提交消息（通过 `currentBuild.description` 写入）。

**Q6：不知道某个插件提供哪些变量，怎么查？**
插件管理 → 已安装 → 搜索该插件 → 点进插件详情页，官方帮助页面会列出所有变量与用法。这是标准查询路径，比到处搜博客可靠。
