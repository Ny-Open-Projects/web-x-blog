# 30. agenticRAG 实战：基于 ReAct 的多文档 RAG Router

## 纲要

- **问题背景**：RAG 知识库可能涉及多类独立知识（如前述制度问答 RAG、前述金融智库 Graph RAG）。若对每个问题在所有库全量检索：① 增加召回不相关信息风险；② 许多检索本没必要（金融问题不必查制度库）。
- **Router 路由思路**：分析问题属性，把问题分流到对应知识库——制度的查制度库、金融的查金融库，检索更有针对性、效率更高。
- **实现方式**：用 ReAct，把两个 RAG pipeline 各封装成一个**工具**（制度问答 RAG、金融智库 Graph RAG），加一个兜底「其他问题」工具（返回「不能回答」）。提示词让模型对问题分类后调对应工具。
- **实战 Agent 结构**：
 - **工具类**：三个方法 = 制度问答 RAG pipeline / 金融智库 Graph RAG pipeline / 其他问题（返回不能回答）；每个工具附**功能 + 详细描述**（决定模型选对）。
 - **ReAct 提示词模板**：工具描述（名称/作用/参数）+ 任务（把问题分为「公司规章制度 / 企业金融商业 / 其他」三类）+ 经典 Thought/Action/Action Input/Observation 模式。
 - **Agent 类**：初始化（工具+LLM+系统提示词）；每轮迭代输出解析（正则提取 Action 工具名/参数/Observation）；据解析调真实工具生成新 Observation；拼接回提示词进入下一轮（设 2 轮迭代）。
- **实测效果**：问「请假如何请」→ 命中制度工具→调制度 RAG 答；问「哪些公司企业转型」→ 命中金融智库工具→调 Graph RAG 答；问「感冒如何治疗」→ 识别为其他类→返回「不能回答」。
- 本章按课程口径重构；代码为知识重构（外部代码卷未挂载），演示基于 ReAct + 两个既有 RAG pipeline；产品名已规范（ReAct / Graph RAG）。

## 一、为何要 RAG Router

当系统接了多个独立 RAG 知识库（本例：制度问答 RAG、金融智库 Graph RAG），全量检索有两个坑：
1. **噪声风险**：在无关库里召回不相关信息，污染上下文；
2. **无效检索**：金融问题去查制度库纯属浪费。

Router 在检索前先分析问题类别，只路由到对应库——**检索更准、效率更高**。

## 二、路由的设计：把 RAG 当工具

用 ReAct 思路实现路由，本质是把两个 RAG pipeline 各封装成一个可调用工具：

| 工具 | 作用 | 说明要点 |
| --- | --- | --- |
| 制度问答 RAG | 查询公司规章制度 | 描述含「规章/制度文档」细节 |
| 金融智库 Graph RAG | 查询企业金融/商业 | 描述含「企业金融商业」细节 |
| 其他问题 | 返回「不能回答」 | 兜底，避免乱答 |

提示词任务：把输入问题分为「公司规章制度 / 企业金融商业 / 其他」三类之一，再据分类调对应工具。工具描述（功能+细节）越准，模型分类越对——需实测不同写法调优。

## 三、实战 Agent 拆解

### 1. 工具类定义
三个方法对应三类工具，每个附**功能说明 + 详细描述**（这是 ReAct 中 Action 选工具的关键信息）。例：制度问答=查询公司规章制度工具；金融智库=查询企业金融商业工具；其他=返回不能回答。

### 2. ReAct 提示词模板
两部分拼装：
- **工具描述模板**：工具名 + 作用 + 详细说明 + 参数说明；
- **ReAct 模板**：任务（分类三类）+ Thought/Action/Action Input/Observation 经典模式，可多轮迭代，Final Answer 终止。

### 3. Agent 类与迭代解析
- 初始化：`工具列表（描述+实体）` + `LLM` + `系统提示词`（函数把工具描述填进模板生成）。
- 每轮解析：模型输出含 Thought/Action/Action Input/Observation，**正则**定位各段起始，提取「要调的工具名 + 参数 + 本轮 Observation」。
- 调真实工具：解析出工具名 → 调对应 RAG pipeline → 结果作新 Observation。
- 串联流程：query 加标签填入提示词 → LLM 首轮迭代 → 解析出 Action → 执行工具得真 Observation → 拼回提示词 → 第二轮迭代（设计 2 轮）→ 完成路由。

## 四、实测验证

| 输入问题 | 识别类别 | 调用工具 | 结果 |
| --- | --- | --- | --- |
| 请假如何请 | 规章制度 | 制度问答 RAG | 依两篇公司规章文档作答，符合内容 |
| 哪些公司企业转型 | 企业金融商业 | 金融智库 Graph RAG | 图谱查转型上下文，列出公司+时间 |
| 感冒如何治疗 | 其他 | 兜底工具 | 返回「对不起，不能回答」并解释 |

三类均按预期路由，证明 ReAct Agent 能自动切换不同信息源。

## 五、FAQ

**Q1：Router 为什么不用分类模型而用 LLM+ReAct？**
ReAct 借 LLM 语义理解做零样本分类，且能结合工具描述推理；无需标注训练，改工具只需改描述。

**Q2：工具描述写不好会怎样？**
模型会选错 RAG 工具（如金融问题误调制度库），路由失效——描述需实测调优。

**Q3：为什么设 2 轮迭代上限？**
防 Thought/Action 死循环烧 token；多数分类一轮即定，两轮足够兜底。

**Q4：解析模型输出为什么用正则？**
ReAct 输出按固定段（Thought/Action/Action Input/Observation）组织，正则提取工具名与参数，但需对格式漂移做兜底。

## 六、面试高频问答

**1. agenticRAG 的 Router 解决什么？**
多 RAG 库全量检索的噪声与无效检索；按问题类别路由到对应库。

**2. Router 怎么用 ReAct 实现？**
把各 RAG pipeline 封装成工具，ReAct 提示词让模型分类后调对应工具（含兜底）。

**3. Agent 类核心步骤？**
初始化工具+LLM+提示词 → 每轮正则解析 Action → 调真实工具得 Observation → 拼回迭代（设上限）。

**4. 实测三类问题如何路由？**
制度问题→制度 RAG；金融问题→Graph RAG；其他→兜底返回不能回答。

## 七、ops 提示（增效）

> **路由是「多知识库 RAG」的必选项**：库一多，全量检索必崩；先路由再检索，准度与成本双赢。
>
> **工具描述要实测调优**：Router 准确率几乎完全取决于工具功能/参数描述，上线前用小样本集回归测试。
>
> **兜底工具防幻觉**：永远保留「其他/不能回答」分支，避免模型硬答超出知识域的问题。
