# 19. 查询增强五种方法：Query2doc / HyDE / 子问题 / 改写 / Step Back

## 纲要

- **查询增强的定位**：属于**检索前增强**，发生在检索模块之前。目的是对用户问题做重写、改造、扩充，使其更清晰具体，从而提升检索准确性——本质是让「查询」与「文档」在语义上更一致。
- **为什么要查询增强**：用户问题常有四类缺陷——表达不清/语义模糊、过于简短缺上下文、有歧义、含过多子问题或细节。拿这些问题直接检索，语义匹配度低、召回精度差。
- **五种方法**：
 1. **Query2doc**：让 LLM 直接回答原问题生成「伪文档」，把伪文档+原问题拼成新查询去检索（文本拼接，可配 BM25）。
 2. **HyDE**（假设文档向量）：LLM 生成假设性文档 → 向量化 → 与原问题向量取均值 → 用平均向量做稠密检索。
 3. **子问题查询**：复杂问题拆成多个子问题，各自检索+各自回答，再综合成最终答案。
 4. **查询改写**：利用 LLM 从多角度重写问题，复原用户真实意图，多版本问题分别检索后汇总。
 5. **Task Step Back**：把过细的问题**抽象化/通用化**，去掉无关细节，从更高层视角检索。
- **共同目标**：为问题「增加额外信息、丰富语义」，提高与知识库文档的匹配概率，从而提高召回率。
- 本章按课程口径重构；产品/框架名已规范化（LangChain / LlamaIndex / HyDE / BM25）；剥离营销与课程群引流。

## 一、为什么需要查询增强（用户问题的四类缺陷）

在 RAG 流程里，我们会拿用户问题去知识库检索。但用户行为不可控，提问常存在缺陷：

1. **表达不清 / 语义模糊 / 缺关键信息**：模型不知道到底问什么。
2. **过于简短 / 缺上下文**：信息量太小，语义匹配信号弱。
3. **有歧义**：容易误解用户意图。
4. **含过多子问题 / 细节太多**：单次向量化检索可能丢失部分语义。

拿这些问题去检索，语义匹配度低 → 召回的上下文精度差。查询增强就是针对这些缺陷，在检索前把问题「变好」。

## 二、方法一：Query2doc（伪文档拼接）

- **思路**：给定问题 → 让 LLM 直接写一段话回答它，生成「伪文档」→ 把**伪文档 + 原问题**拼成新查询去知识库检索。
- **伪文档的价值**：因为是为回答该问题而生成的，里面一定包含回答所需的有价值信息，等于为原问题补充了额外语义细节。
- **额外好处**：伪文档是文本，拼接后增加了关键词，因此**能配合稀疏检索（如 BM25）**提高精度。
- **实现关键**：提示词极简——「写一段话来回答这个给定问题」即可。伪文档答案未必准确，但扩展了细节，提高匹配可能性。

## 三、方法二：HyDE（假设文档向量）

- **思路与 Query2doc 一致**，不同点在最后一步：
 - Query2doc 把伪文档**当文本**直接拼接检索；
 - HyDE 把伪文档**向量化后再检索**。
- **流程**：LLM 生成一段（或多段、多视角）假设性文档 → 每段经 embedding 模型向量化 → 与原问题向量一起**取均值** → 用平均向量做知识库相似度检索。
- **向量空间视角**：原问题与真实文档在向量空间里可能相距很远；通过生成假设文档补充信息，让最终查询向量尽可能贴近真实文档向量，从而提高召回率。平均后的向量同时包含「用户查询」与「所需答案」的相关信息，更适合**稠密检索**。
- **两种框架实现**：
 - **LangChain**：把 HyDE 当成一个 embedding 模型封装，设计生成假设文档的 prompt → 生成并向量化 → 检索。
 - **LlamaIndex**：用对应类完成计算，参数 `include_original` 控制「是否把原问题也纳入向量平均」。

## 四、方法三：子问题查询（复杂问题拆解）

- **针对场景**：问题太复杂，内含多个语义子问题。直接用复杂问题向量化检索，可能丢失部分语义。
- **思路**：用 LLM 把大问题拆成多个子问题 → 每个子问题分别做向量化检索得上下文 → 每个上下文+子问题送 LLM 生成各自答案 → 把全部答案综合成原始复杂问题的最终答案。
- **重点**：如何拆解。提示词给明确指令——「生成一系列小问题帮助回答用户的复杂问题」，并附指导原则（子问题须相关、尽可能明确等），可按任务调整。
- **类比**：类似 RAG 评估里把「生成答案/标准答案」拆成陈述句的做法，核心是保持原始问题语义完整。

## 五、方法四：查询改写（多角度重写）

- **针对场景**：问题表意不清、措辞差、缺关键信息。
- **思路**：用 LLM 根据原问题从多角度重写 N 个新版本问题 → 每个新问题进行检索得上下文 → 汇总上下文送 LLM 回答原问题。
- **实现关键**：提示词「根据原问题生成五种不同版本的问题，帮助更好地检索信息」。多视角重写能复原用户提问初衷、间接捕捉意图，补充额外信息。

## 六、方法五：Task Step Back（退后一步 / 抽象化）

- **针对场景**：问题问得太细、含大量细节，反而掩盖了真正要问的更宽泛问题，导致检索时忽略关键信息。
- **思路**：把具体细节问题**抽象化 / 通用化**，转成一个更高层、更普遍的问题，关注高级概念或更宽泛原则，从而更有效检索。
- **实现关键**：提示词「你是世界知识专家，用 step-back 方式把用户问题转述为更普遍通用、更易回答的问题」。例：原问题「某人在 2007–2008 效力于哪队」→ step-back「该人职业生涯共效力过多少队」。去掉时间细节后，从更高层视角检索，提升相关性。

## 七、FAQ

**Q1：Query2doc 和 HyDE 到底差在哪？**
思路完全一致（都生成假设性文档补充信息），区别仅在末步：Query2doc 拿文本拼检索（利于稀疏/BM25），HyDE 拿向量平均后检索（利于稠密）。

**Q2：五种方法该用哪个？**
问题简短/缺上下文 → Query2doc 或改写；问题太细 → Step Back；问题复杂含多子问题 → 子问题拆解；要提升稠密召回 → HyDE。

**Q3：查询增强会不会引入错误答案？**
伪文档/假设文档答案未必准确，但其价值在「补充语义细节、提高匹配概率」，而非提供事实。最终仍以知识库检索到的真实文档为准。

**Q4：子问题查询和直接检索比，优势？**
避免复杂问题单次检索的语义丢失，各子问题分别召回，上下文更完整全面。

## 八、面试高频问答

**1. 查询增强属于哪类增强？目的是什么？**
检索前增强；对用户问题重写/扩充，使查询与文档语义一致，提升检索准确性。

**2. 五种查询增强方法？**
Query2doc、HyDE、子问题查询、查询改写、Task Step Back。

**3. HyDE 和 Query2doc 的核心区别？**
末步：Query2doc 文本拼接检索（配 BM25），HyDE 向量平均后稠密检索。

**4. Task Step Back 解决什么问题？**
问题过细、细节掩盖真意图；通过抽象化转成更普遍问题，提升检索相关性。

## 九、ops 提示（增效）

> **先诊断问题类型再选型**：不要盲目套方法。缺信息用 Query2doc/改写，太细用 Step Back，太复杂用子问题。
>
> **HyDE 记得取均值 + 可含原问题**：多段假设文档向量与原问题向量平均，参数 `include_original` 按需开启，否则召回会偏。
>
> **查询增强是「低成本的检索前补丁」**：不改知识库、不动向量库，只动输入，先试它往往比直接上重排更划算。
