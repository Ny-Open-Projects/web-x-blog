# 22. Self-RAG 自我评估增强与 LangGraph 工作流实战

## 纲要

- **Self-RAG 的核心思想**：在 RAG 流程中**自动加入判别步骤**，根据每步结果好坏**动态选择策略**，从而生成更好答案。本质是把「评估」从「生成之后」前移到「流程之中」。
- **三个判别器（都用 LLM + 提示词实现）**：
 1. **上下文相关性**：检索到的文档与问题是否相关（yes/no）→ 只留相关文档，不相关则触发查询增强（如 Query2doc / 改写）再检索。
 2. **答案支持度**：生成答案能否从上下文找到事实依据（防胡编）→ 不支持则丢弃/多次尝试生成。
 3. **答案有用性**：生成答案能否回答原问题 → 无用则触发查询重写再检索，或直接结束。
- **与 Ragas 的关联**：三个判别的思路与 Ragas 评估指标同源（都是让 LLM 做相关性判别），但 Self-RAG 把判别**嵌入推理流程**实时决策。
- **LangGraph 实现**：把流程建成**状态图（StateGraph）**——节点（检索/查询增强/生成/判别）+ 边（含条件边 `add_conditional_edges`）。节点三要素：输入、具体任务、输出；输出又是对下面点的输入，节点间靠共享状态传递。
- **防死循环**：对 Query2doc / 查询重写执行次数计数，超过阈值（如各限 1 次）强制不再增强，直接进入下面点或结束。
- 本章按课程口径重构；代码为知识重构（外部代码卷未挂载），演示基于 LangChain + LangGraph；产品名已规范（LangChain / LangGraph / Self-RAG / Ragas）。

## 一、Self-RAG：把判别嵌入流程

回顾普通 RAG：检索 → 生成 →（事后）评估 → 据结果迭代优化。评估在生成**之后**，流程中并未参与决策。Self-RAG 要回答的问题是：**能否把评估嵌进生成之前的每一步？**

做法：在流程中插入判别模块，依据判别结果动态选择策略。可插入的判别点：

- **检索后**：判断检索文档与问题是否相关。相关→进生成；不相关→丢弃或触发查询增强（改写 / 生成假设文档）再检索（可多次迭代判别）。
- **生成后**：① 判断答案是否**有上下文依据**（支持度）；② 判断答案是否**能回答问题**（有用性）。不支持→丢弃/多次尝试；无用→查询重写再检索或结束。

有了判别标准，每步好坏可知，好的进下一轮、不好的换策略重试，整体精度随之提升。

## 二、三个判别器的提示词设计

三个判别都靠 LLM 能力，关键是写好提示词（明确角色 + 领域描述 + 输出要求）：

1. **上下文相关性判别**：角色=评分员；定义「文档含与问题相关的关键词或语义信息即相关」；输出**二元分类 yes/no**。
2. **答案支持度判别**：评估答案是否基于/由上下文事实支持；输出 yes（支持）/no（不支持）。
3. **答案有用性判别**：评估答案是否可解决所提问题；输出 yes（有用）/no（没用）。

> 提示词是引导 LLM 生成/判别的最核心手段，跨领域复用时要针对任务调整提示词。

## 三、LangGraph 节点与边（状态图）

LangGraph 可视为 LangChain 的工作流封装：用**节点（node）**执行任务、**边（edge）**定义数据流动。整体建成有向图，据节点结果决定后续走哪个节点。

**节点三要素**：
- **输入**：通常是列表，承载节点间/全流程共享数据（如问题、快速 DOC 次数、查询重写次数）。
- **具体任务**：如检索节点调用抽离出的检索方法（输入问题→向量库检索→返回文档+上下文）。
- **输出**：列表封装，把本步结果及需透传的中间状态传给下面点。

**关键节点**：
- 检索节点：context_query 不为空时用它检索（兼容假设文档/重写问题作为输入）。
- 查询增强节点：Query2doc（生成假设文档作新 context_query，计数+1）、QueryRewrite（改写问题作新 context_query，计数+1）。
- 生成节点：用原 RAG prompt 模板，拼接上下文，经 LLM + output_parser 得答案。
- 判别节点：文档相关性判别、答案相关性判别（含支持度 + 有用性两步）。

**边与条件分支**：
- 普通边：`add_edge` 串联（如检索→文档判别）。
- 条件边：`add_conditional_edges`，据节点输出结果选路径。例：文档判别输出「需增强/不需增强」→ 需增强且未超次数则走 Query2doc，否则走生成；答案判别输出 `useful / nouseful / nosupport / end` 四结果分别指向对应下面点（nosupport 与 end 直接结束，nouseful 走查询重写）。

## 四、实战：节点设计与防死循环

- **检索节点抽离**：把 baseline RAG pipeline 里的检索模块单独成函数（输入问题→向量库检索→返回文档+上下文），供图内复用。
- **透传计数**：Query2doc、QueryRewrite 节点每次执行都把对应计数器 +1，并随状态透传，用于条件判断。
- **防死循环逻辑**：文档相关性判别若不相关→触发 Query2doc；但 Query2doc 又会回到检索→再判别，形成「不相关→增强→还不相关→再增强」的死循环。对策：对执行次数设阈值（实战设为只允许 1 次 Query2doc），超阈值即使仍需增强也强制进入下面点。
- **答案判别同理**：nouseful 会触发查询重写，对重写次数也限 1 次，超次直接结束，避免无限循环。

## 五、实战：运行与验证

- **输入封装**：把问题按检索节点要求的字典格式（含 key 与状态信息）传入，用 `invoke` 启动整个图。
- **过程可观测**：可打印每步输出观察节点执行情况。实测流程：检索→文档判别（2 不相关 1 相关）→ 触发 Query2doc 生成假设文档 → 再检索→再判别（已超次数、2 相关）→ 进生成 → 答案判别（有用）→ 结束。
- **另一实测**：三次检索均不相关且已达次数上限 → 强制生成 → 答案判别仍判有用，输出了有价值信息。

> 应用到其他领域时，三个判别器的提示词需重新尝试调整以获得更好结果。

## 六、FAQ

**Q1：Self-RAG 和 Ragas 什么关系？**
判别思路同源（都让 LLM 做相关性判断），但 Ragas 是**事后离线评估**，Self-RAG 是**实时嵌入流程做决策**。

**Q2：为什么三个判别都用 LLM？**
相关/支持/有用判断都需语义理解，LLM 强于语义且可规模化，比规则或人工更适配。

**Q3：LangGraph 节点为什么要透传计数？**
为条件分支服务——靠计数判断是否超过增强次数阈值，从而打破「不相关→增强→再不相关」死循环。

**Q4：条件边和普通边的区别？**
普通边固定指向下面点；条件边（add_conditional_edges）根据节点输出结果动态选路径，是 Self-RAG 实现「动态策略」的关键。

## 七、面试高频问答

**1. Self-RAG 的核心思想？**
在 RAG 流程中嵌入判别步骤，据每步结果动态选策略，把评估从生成后前移到流程中。

**2. Self-RAG 三个判别器？**
上下文相关性、答案支持度、答案有用性（均 yes/no 二元）。

**3. 用 LangGraph 怎么实现 Self-RAG？**
建状态图：检索/查询增强/生成/判别为节点，普通边+条件边串联，据判别结果走不同分支。

**4. 如何避免 Self-RAG 死循环？**
对 Query2doc / 查询重写等增强节点设执行次数阈值，超阈值强制不再增强。

## 八、ops 提示（增效）

> **Self-RAG 适合「质量优先、可接受延迟」场景**：每步多一次 LLM 判别，成本与延迟上升，但答案可靠性显著增强，客服/合规类业务值得上。
>
> **计数阈值是生命线**：不设计次数上限，不相关分支会无限循环烧 token；Query2doc、QueryRewrite 各限 1 次是稳妥起点。
>
> **提示词要调**：三个判别器的 prompt 直接决定判别准度，换领域务必重新调参验证，别直接搬。
