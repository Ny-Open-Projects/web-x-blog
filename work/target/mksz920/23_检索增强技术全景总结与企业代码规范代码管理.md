# 23. 检索增强技术全景总结与企业代码规范 / 代码管理

## 纲要

- **14 种检索增强技能全景收口**：本章从「检索前 / 检索后 / 系统性」三维度系统讲解了提升 RAG 检索性能的方法，全部落地于制度问答 baseline。
- **查询增强（检索前·改问题）**：Query2doc、HyDE、子问题查询、查询改写、Task Step Back——从问题出发扩充/改写，使查询与文档语义一致。
- **多索引增强（检索前·改索引）**：父文档（大小文档）、总结索引、假设问题索引——同一文档建不同维度 embedding，检索用小索引、返回对应大块。
- **检索后增强**：融合检索（BM25+embedding 用 RRF 融合）、重排序 Re-rank（Cross-Encoder 精排，BGE reranker 本地）。
- **系统性增强**：迭代检索增强生成（多次迭代拼答案再检索）、Self-RAG（流程嵌判别，动态选策略）。
- **企业工程素养（AI 应用开发必备）**：① 代码规范（命名/格式/注释/结构/错误处理/SOLID 设计原则）；② 代码管理（git 分支策略 master/develop/feature/hotfix，用 git 记录 AI 调参试错）。
- 本章按课程口径重构；产品/框架名已规范化（LangChain / LangGraph / BGE / BM25 / SOLID / git）；剥离营销与课程群引流。

## 二、实战统一做法

所有增强都基于前述制度问答 baseline 的 RAG pipeline（Chroma 向量库 + BGE-M3 embedding + Qwen 类 LLM + LangChain），做法是把 baseline 的检索/生成模块抽离复用，再叠加各增强逻辑：

- **查询增强 / 多索引**：在检索前改造输入或知识库索引；
- **融合 / Re-rank**：在检索后叠加 RRF 或 Cross-Encoder 精排；
- **迭代 / Self-RAG**：把 RAG 当模块多次编排，Self-RAG 进一步用 LangGraph 状态图实现条件分支。

## 三、企业代码规范

项目成立之初就要约定代码规范，原因：① 多角色协作保持一致风格、提效；② 利于代码维护；③ 提升个人专业形象。

主要约定维度：
- **命名**：驼峰式或下划线式；好命名「简洁且知名知义」。
- **格式**：缩进（空格/制表符）、每行最大长度、空行用法；常用语言工具强制提醒（超长告警）。
- **注释**：解释复杂逻辑/算法，简洁扼要，也为日后自己回看留线索。
- **代码结构**：目录组织、模块化设计、类与函数设计规范。
- **错误处理**：规定异常捕捉，提升稳健性，防止单点故障拖垮整体。
- **设计原则（SOLID 六原则）**：单一职责、开闭（开放扩展、封闭修改）、接口隔离、迪米特法则、里氏替换、依赖倒置。

> 可参考 Google 的 Python / C++ 开发规范文档，结合项目实际制定。每个公司、每种语言的规范不同。

## 四、代码管理（git）

代码管理保存每次变化（commit），便于跟踪里程碑、多人协同。最常用的是 **git**（分布式版本控制，Linux 底层即用 git 管理）。

**典型分支策略**：
- `master`：生产分支；
- `develop`：开发分支；
- `feature`：特性分支（新功能）；
- `hotfix`：修复分支（线上问题）。

**开发到发布流程**：从 master 拉 develop → develop 上开发 v1.0 → 准备上线时拉 release/tag 分支部署 → 发布后合并回 master 保持主干一致；线上出问题打 hotfix 分支修复，再合并回 master 与 develop。

## 五、AI 应用开发特别提示：用 git 管理试错

AI 应用开发与传统软件开发最大区别是**充满不确定性**。应对方式：先建 baseline，再在 baseline 上不断试优化。这个过程要**记录不同方案（参数、提示词）**以便回溯——哪些有用、哪些没用。

建议：把每次操作作为一个小版本，在 git 本地仓库管理；用**分支名区分不同方案**。用 git 管理 AI 开发全流程，比口头/文档记录更可靠、可比对。

## 六、FAQ

**Q1：14 种技能怎么记？**
按三维记：检索前（改问题 5 种 + 改索引 3 种）、检索后（融合 + Re-rank）、系统性（迭代 + Self-RAG）。

**Q2：AI 应用开发为什么特别需要 git？**
方案多、参数/提示词多变、需反复试错回溯；git 分支记录不同方案，比文档更可靠。

**Q3：代码规范对 AI 项目也重要吗？**
更重要——AI 代码常含复杂 prompt 与 pipeline，规范命名/注释/错误处理能大幅降低协作与维护成本。

**Q4：SOLID 里最常被忽视的是哪个？**
单一职责（一个函数只做一件事）与开闭原则（扩展开放、修改封闭），在 pipeline 模块化设计里尤其关键。

## 七、面试高频问答

**1. 检索增强分哪几类？各举两例。**
检索前（Query2doc/HyDE/多索引）、检索后（融合/RRF、Re-rank）、系统性（迭代检索增强、Self-RAG）。

**2. 融合检索用什么算法融合？**
RRF 加权倒数排名 `1/(k+rank)`，k 经验取 60，跨方法加权求和。

**3. 企业代码管理典型分支策略？**
master(生产)/develop(开发)/feature(特性)/hotfix(修复)。

**4. 为什么 AI 应用开发要用 git 管试错？**
不确定性高、需记录多方案参数与 prompt 以便回溯比对，分支区分方案最可靠。

## 八、ops 提示（增效）

> **增强选型先分维**：问题差→检索前改问题；索引单一→多索引；召回杂→检索后融合/Re-rank；要自动决策→Self-RAG。别堆砌。
>
> **AI 项目从 day1 用 git**：每个提示词/参数方案一个分支，回溯成本趋近于零，是 AI 工程化的底线习惯。
>
> **规范先于规模**：团队一上来就定命名/注释/错误处理/SOLID，比事后重构省力一个数量级。
