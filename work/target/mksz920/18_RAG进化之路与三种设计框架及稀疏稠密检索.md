# 18. RAG 进化之路、三种设计框架与稀疏/稠密检索

## 纲要

- **RAG 的瓶颈在检索**：RAG 成功的关键，是能检索到与问题高度相关的上下文。如何增强检索性能，是开发 RAG 应用的核心命题。
- **RAG 进化之路（三类增强）**：以「检索模块」为界，可分为 **检索前增强**（从问题出发，改写/扩充查询）、**检索后增强**（对检索到的上下文做处理，如融合、重排）、以及 **系统性 / 模块化增强**（从整体流程角度优化，如加入判别模块的 Self-RAG、多次迭代）。
- **三种 RAG 设计框架**：① 普通 RAG（检索→生成）；② Advance RAG（在普通 RAG 上叠加检索前/检索后增强）；③ 模块化 / 系统 RAG（把流程拆成可编排的模块，如 Self-RAG、迭代检索增强生成）。
- **检索两大形态**：① **稀疏检索**（关键词匹配的统计扩展，典型 TF-IDF、BM25，只看词频、不看词序与上下文）；② **稠密检索**（基于 embedding 向量的语义检索，典型 BGE、GTE，压缩语义、含词序与上下文）。二者各有短板，故常融合。
- **用户问题的多样性是根因**：表达不清、过于简短、有歧义、含过多子问题或细节——正是这些缺陷催生了五花八门的检索增强技术。

## 一、RAG 进化之路：从普通 RAG 到三类增强

普通 RAG 流程非常直白：拿用户问题去知识库检索 → 得到上下文 → 连同问题一起送进大模型生成答案。但**用户的问题不可控**（写法、描述千差万别），相似度匹配拿到的上下文不一定高质量，噪声上下文会直接拉低答案质量。

人们在普通 RAG 基础上增加额外操作来提升检索性能，总体可归为三类：

- **检索前增强**：从问题角度出发，对问题做改写、扩充，补充额外信息，提高与知识库文档的语义匹配度（如 Query2doc、HyDE、子问题拆解、查询改写、Step Back）。
- **检索后增强**：对检索后的上下文做处理。最常见的是**融合多种检索策略**（稀疏+稠密），以及对上下文做**相关性重排（Re-rank）**，只挑最相关的送进大模型。
- **系统性 / 模块化增强**：从整体流程角度优化。例如在流程中加入**验证 / 判别模块**（Self-RAG），或通过**多次迭代**做检索增强（迭代检索增强生成）。

> 一句话记忆：前两类是「单步增强」，第三类是「把 RAG 当模块反复编排」。

## 二、三种 RAG 设计框架

| 框架 | 核心做法 | 典型代表 |
| --- | --- | --- |
| **普通 RAG** | 检索 → 生成，流程最短 | 前述制度问答 baseline |
| **Advance RAG** | 普通 RAG + 检索前/检索后增强 | 查询增强、融合检索、Re-rank |
| **模块化 / 系统 RAG** | 把流程拆成可编排节点，加入判别或迭代 | Self-RAG、迭代检索增强生成 |

- **普通 RAG**：最直接，适合快速验证可行性，但面对复杂问题精度有限。
- **Advance RAG**：在普通 RAG 基础上「打补丁」，针对检索前、检索后分别优化，实战中最常用。
- **模块化 RAG**：把「检索 / 生成 / 判别」抽象成节点，用图（如 LangGraph 的状态图）串起来，根据每步结果动态选策略。Self-RAG 是典型——它在流程中嵌入判别，能自动决定「要不要增强、要不要重写」。

## 三、检索两大形态：稀疏 vs 稠密

### 稀疏检索（关键词匹配的统计扩展）

- **思想**：通过统计「问题中每个关键词在文档里出现的次数（词频）」来评估相关性并排序。
- **两大算法**：
 - **TF-IDF**：`TF`（词在文档中出现次数占比，度量词对本文档的重要性，需先去除语气词/连接词等停用词）× `IDF`（逆文档频率 = log(语料总文档数 / 含该词的文档数)，越稀缺的词权重越高）。
 - **BM25**（Best Matching 25）：TF-IDF 的变种，TF、IDF 计算更复杂、带经验参数，效果更稳，是融合检索里稀疏侧的首选。
- **致命短板**：只看词频，**不关注词序与上下文语义**。例：「男朋友送的礼物」vs「送男朋友的礼物」关键词完全相同但语义相反；「白衬衫灰裤子」vs「灰衬衫白裤子」同理——关键词匹配会全命中，却语义错乱。

### 稠密检索（基于 embedding 的语义检索）

- **思想**：用 embedding 模型（典型 BGE、GTE，均为 BERT 架构）把文本转成固定长度向量，向量里压缩了语义（含词序与上下文）。两向量做相似度即匹配度。
- **本质**：文本本身很稀疏（一字一字），embedding 是把稀疏文本压缩进稠密数值数组——**有信息丢失风险**，但语义理解远强于关键词。
- **与稀疏的关系**：二者各有所长，因此实战常把「关键词的精准」与「语义的泛化」融合。

## 四、FAQ

**Q1：为什么 RAG 要分检索前 / 检索后增强？**
因为问题（输入）和上下文（输出）两边都可能出问题：问题写得差 → 检索前改问题；检索回一堆但良莠不齐 → 检索后融合/重排。

**Q2：稀疏检索和稠密检索能二选一吗？**
可以单独用，但各有短板。稀疏对精确关键词友好、对语义错乱无感；稠密懂语义、但可能把「相似但不相关」的文档排前面。融合二者最稳。

**Q3：模块化 RAG 比 Advance RAG 强在哪？**
Advance RAG 是「在固定流程上打补丁」；模块化 RAG 把步骤拆成节点可动态编排，能根据每步结果走不同分支（如 Self-RAG 自动决定是否重写），适应性更强。

**Q4：BM25 和 TF-IDF 怎么选？**
两者思路一致，BM25 是 TF-IDF 的改进版，统计方式更精细、带调参，实战直接用 BM25 即可，无需自己实现。

## 五、面试高频问答

**1. RAG 三类增强是什么？**
检索前增强（改查询）、检索后增强（融合/重排）、系统性/模块化增强（判别/迭代）。

**2. 三种 RAG 设计框架？**
普通 RAG、Advance RAG、模块化/系统 RAG。

**3. 稀疏检索 vs 稠密检索的核心区别？**
稀疏（TF-IDF/BM25）基于关键词词频统计，不看词序与上下文；稠密基于 embedding 向量语义匹配，含词序与上下文但可能信息丢失。

**4. 稀疏检索的短板举例？**
「男朋友送的礼物」与「送男朋友的礼物」关键词一致却语义相反，关键词匹配会误命中。

## 六、ops 提示（增效）

> **先定位瓶颈再选增强**：问题差 → 检索前增强；召回杂 → 检索后增强；要自动决策 → 模块化。别一上来就堆技术。
>
> **稀疏 + 稠密融合是性价比之王**：多数企业场景直接上 BM25 + embedding 融合（RRF），比单用 embedding 鲁棒得多。
>
> **embedding 不是万能**：稠密检索存在「相似但不相关」的假阳性，必须配 Re-rank 兜底。
