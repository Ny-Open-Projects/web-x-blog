### Q7572 · 多轮会话上下文串号事故复盘

难度：P6 ｜ 标签：Agent / 会话隔离 / 并发 / 事故复盘 / 安全

**问**：多轮对话服务上线后，偶发用户 A 在对话里看到用户 B 的上下文（订单号、姓名）。事故怎么发生？怎么从会话管理架构上根除这类串号？

**答**：

**结论**：串号的经典成因是把会话状态存在"进程级单例/全局变量"里而不是按会话 ID 隔离：异步并发下（asyncio 单线程并发或线程池），请求 A 写入全局 conversation 列表，请求 B 的处理流程读到了它。更隐蔽的变体：连接池里复用的对象带残留状态、缓存键缺会话维度、日志 trace 串上下文（contextvars 没设对）。这类事故不只是 bug，是数据安全事故（用户间信息泄露），修复优先级最高。架构解：会话状态外置存储（DB/Redis，键含 session_id），请求处理链路无任何进程级可变单例；上下文传递用 contextvars（asyncio 安全）而非模块级变量。

**取舍**：状态放内存（按 session_id 的 dict）vs 外置存储：内存方案快但要处理多实例路由（同一会话必须粘到同一实例，粘性路由又引入负载不均与发布漂移）；外置存储（Redis + TTL）天然多实例安全，每轮多 1-2ms 读取成本。生产选外置 + 内存只做只读缓存。另一个决策：串号检测要不要做主动对账？——高价值场景加"上下文归属校验"（每次取会话历史断言 user_id 匹配，不匹配报错并告警），成本一行代码，能拦截绝大多数串号恶化。

**实战**：事故复盘时用 trace 定位：找到串号请求对，对比两者的 session_id、处理时间线与共享的可变状态；排查清单按出现频率：全局单例 > 缓存键缺维度 > contextvars 误用（在线程池里没 copy）> ORM 会话复用。Python 侧给 async handler 写"无共享可变状态"的 lint 规则与测试（并发压测断言各会话历史独立）。

```python
# 会话隔离对照：全局单例（bug 版） vs 外置存储 + contextvars（修复版）
# 仅标准库，Python 3.9+
from __future__ import annotations

import asyncio

GLOBAL_HIST: dict = {}  # 进程级单例：无会话维度 → 串号源


async def handle_buggy(session: str, user: str, msg: str) -> list:
    hist = GLOBAL_HIST.setdefault("all", [])  # 所有会话共享一个列表
    hist.append(f"{user}:{msg}")
    await asyncio.sleep(0.001)                # 并发交错点：另一个会话也写入了
    return list(hist)


class SessionStore:
    """外置存储（模拟 Redis，键含 session_id）+ 归属校验。"""

    def __init__(self) -> None:
        self._data: dict[str, dict] = {}

    def append(self, session: str, user: str, msg: str) -> None:
        rec = self._data.setdefault(session, {"owner": user, "hist": []})
        if rec["owner"] != user:
            raise PermissionError(f"串号防护: session {session} 属于 {rec['owner']}")
        rec["hist"].append(f"{user}:{msg}")

    def history(self, session: str, user: str) -> list:
        rec = self._data[session]
        if rec["owner"] != user:
            raise PermissionError("串号防护")
        return rec["hist"]


async def main() -> None:
    # bug 版：两个并发会话互相污染
    r = await asyncio.gather(
        handle_buggy("sA", "alice", "hi"),
        handle_buggy("sB", "bob", "hello"),
    )
    assert len(r[0]) == 2 and len(r[1]) == 2  # 互相看到了对方
    print("bug 版：两个会话历史均为", r[0], "→ 串号")

    # 修复版：按 session 隔离 + 归属校验
    store = SessionStore()
    await asyncio.gather(
        asyncio.to_thread(store.append, "s1", "alice", "hi"),
        asyncio.to_thread(store.append, "s2", "bob", "hello"),
    )
    assert store.history("s1", "alice") == ["alice:hi"]
    try:
        store.history("s1", "bob")  # B 偷看 A 会话 → 拦截
        raise SystemExit("不应到达")
    except PermissionError:
        print("修复版：会话隔离 + 归属校验，串号被结构性拦截")


if __name__ == "__main__":
    asyncio.run(main())
```

**追问链**：

- 追问 1：为什么 contextvars 能在 asyncio 下安全传递请求上下文，而 threading.local 不行？——asyncio 每个任务有独立的 context（Task 创建时复制 contextvars），任务间互不串；threading.local 以线程为单位，单线程跑多协程时所有协程共享同一个 local 值——恰是串号源。线程池里要用 `contextvars.copy_context().run`。
- 追问 1.1：粘性路由方案的发布期隐患？——滚动发布时新旧实例并存，粘到旧实例的会话在实例下线后被强制迁移，迁移瞬间状态（若只存内存）丢失；所以即使做粘性路由，状态也要外置，粘性只作为缓存优化而非正确性依赖。
- 追问 2：归属校验（owner 断言）会不会误伤合法场景（管理员查看用户会话）？——校验逻辑分"同用户访问"（强校验）与"授权角色访问"（走审计授权通道并记 access log）；误伤源于把两类访问混在一个入口。设计上 owner 校验放数据层，授权访问放管理面单独链路。

**背诵要点**：

1. 串号根因排行：进程级可变单例 > 缓存键缺会话维度 > contextvars/threading.local 误用 > ORM 会话复用；本质是用户间信息泄露的安全事故。
2. 修复结构：状态外置（Redis+TTL，键含 session_id）、请求链路无全局可变状态、asyncio 用 contextvars 传上下文。
3. 归属校验一行代码拦截恶化：每次读会话断言 owner；粘性路由只能做缓存优化，不能当正确性依赖。
