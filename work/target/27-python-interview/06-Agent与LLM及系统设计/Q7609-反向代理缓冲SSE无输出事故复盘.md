### Q7609 · 反向代理缓冲导致 SSE 流式"无输出"事故复盘

难度：P6 ｜ 标签：事故复盘 / SSE / 流式

**问**：LLM 应用迁移到新接入层后，用户反馈"点发送后页面转圈 30 秒，然后答案一次性全部出现"。直连后端测试一切正常（TTFT ~1s）。接入层动了什么？SSE 链路上还有哪些"缓冲陷阱"？

**答**：
- **结论**：SSE 是单向 `text/event-stream` 长连接，逐块下发；正常时 TTFT≈模型首 token 时间。故障链：新接入层在 Nginx/网关上开了默认响应缓冲（`proxy_buffering on`）或启用了 gzip/压缩、请求体/响应体聚合中间件——代理把上游的分块攒到缓冲区满或响应结束才发给客户端，流式退化为"等 30 秒一次性到"。**后端完全无辜**，故障只存在于代理层配置。同类陷阱：响应头带了 `Content-Length`（SSE 必须无长度/chunked）、中间有聚合日志组件同步读全量、客户端 SDK 自带 read 缓冲没按行 flush、HTTP/2 的流量窗口过小。
- **取舍**：配置与设计要点：① 代理层对 SSE 路由显式关缓冲：Nginx `proxy_buffering off; proxy_cache off;` + `X-Accel-Buffering: no` 响应头兜底（应用可对个别路由自证）；② 关 gzip（`gzip off` 对 event-stream），压缩需要攒满块才能压缩；③ 心跳注释帧（`: ping\n\n`，见 Q2323）保证中间设备不因空闲掐连接，也让用户端首字节提前到达；④ 客户端按事件边界（`\n\n`）解析而不是按字节；⑤ 监控把"网络首字节时间"与"模型 TTFT"分开打点——两者差值就是代理层缓冲的量化证据。
- **实战**：事故剧本：① 用 curl `curl -N` 直连后端确认逐块到达，再过代理确认一次性到达，定位在代理层；② 检查代理配置找到 `proxy_buffering`/压缩项，SSE location 单独关；③ 加 `X-Accel-Buffering: no` 让应用层自保护；④ 打通端到端首字节监控（gateway 与浏览器 Performance API 对拍）；⑤ 复盘项：接入层变更 checklist 增加"流式路由专项验证"（脚本化：curl -N 间隔 <1s 判 PASS）。

```python
# SSE 缓冲陷阱自检 + 代理配置判定（标准库模拟）
# 基线：Python 3.9+；真实链路 curl -N + Nginx/网关配置

from dataclasses import dataclass


@dataclass
class ProxyRoute:
    name: str
    proxy_buffering: bool
    gzip_enabled: bool
    has_content_length: bool
    x_accel_buffering: str = ""


def sse_ok(route: ProxyRoute) -> tuple[bool, list[str]]:
    issues = []
    if route.proxy_buffering:
        issues.append("proxy_buffering on：分块被攒到结束才下发")
    if route.gzip_enabled:
        issues.append("gzip 对 event-stream 生效：压缩要攒块")
    if route.has_content_length:
        issues.append("带 Content-Length：SSE 必须 chunked/无长度")
    if route.x_accel_buffering.lower() == "no":
        return not issues, issues + ["X-Accel-Buffering:no 应用层已自保护（仍建议代理侧显式关闭）"]
    return len(issues) == 0, issues


def main() -> None:
    bad = ProxyRoute("gateway-sse", proxy_buffering=True, gzip_enabled=False,
                     has_content_length=False)
    ok, issues = sse_ok(bad)
    assert not ok
    for i in issues:
        print("缓冲陷阱:", i)

    fixed = ProxyRoute("gateway-sse", proxy_buffering=False, gzip_enabled=False,
                       has_content_length=False, x_accel_buffering="no")
    ok, issues = sse_ok(fixed)
    assert ok
    print("OK: SSE 路由三查——缓冲/压缩/Content-Length，应用层 X-Accel-Buffering 兜底")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么心跳注释帧能部分缓解"缓冲"类问题？
→ 一句话提示：注释帧让链路上始终有字节流动，空闲超时/中间设备不会掐连接、部分代理按"有数据就 flush"转发；但若代理是硬缓冲（攒满才发），心跳也会被攒住——心跳治空闲超时，缓冲必须靠配置关。

**追问 2**：客户端侧怎么区分"模型慢"和"链路缓冲"？
→ 一句话提示：看首字节时间（TTFB）与模型侧 TTFT 日志的差值：差值大 = 链路缓冲/排队；若首字节快但块间间隔巨大也是缓冲特征；两端打点对拍是最直接的证据链。

## 背诵要点
- 流式退化三查：代理 `proxy_buffering`、gzip 对 event-stream、Content-Length 头；后端无辜，故障在中间层配置。
- 应用层自保护：响应头 `X-Accel-Buffering: no` + 心跳注释帧；端到端监控把网络 TTFB 与模型 TTFT 分开打点。
- 验收脚本化：curl -N 断言块间隔 <1s，接入层变更 checklist 固化流式专项。

## 复盘追问
- 为什么这个事故往往在"接入层迁移"后爆发？提示：新网关默认配置（缓冲/压缩/WAF 深度检测）与旧环境不同，直连测试永远过不了这条路径——验收必须覆盖完整生产链路。
- WAF/安全设备对流式的额外影响？提示：深度包检测可能整段重组后才放行，等效缓冲；要么对 SSE 路由降级检测策略，要么把安全校验移到请求侧（鉴权/输入过滤）而非响应侧。
