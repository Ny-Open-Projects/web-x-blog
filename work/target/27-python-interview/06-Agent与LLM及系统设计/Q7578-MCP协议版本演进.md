### Q7578 · MCP 协议版本演进与工具层适配

难度：P6 ｜ 标签：版本演进 / MCP / 工具协议 / Agent

**问**：MCP 从早期 stdio 传输演进到 Streamable HTTP（带 auth、会话恢复、无状态模式），工具生态版本混杂。怎么让 Agent 应用层不被 MCP 协议版本变迁反复打断？

**答**：

**结论**：MCP 的演进主线是"本地进程协议 → 远程服务协议"：stdio 传输（本地子进程、无认证）适合桌面场景；HTTP+SSE→Streamable HTTP 支持远程 server、OAuth 授权、会话恢复（session id）、无状态模式。版本混杂是现实：同一个 Agent 可能同时接 stdio 老工具与 Streamable HTTP 新工具。应用层防御是协议抽象：工具调用统一到内部接口（list_tools / call_tool / 能力协商三件事），传输与版本细节由 client SDK 层吸收；版本协商（initialize 握手里的 protocolVersion）显式处理——不支持回退到最低公共版本并记录告警，而不是假设两端永远同版。会话恢复语义是迁移最大的坑：老 server 崩了就重连重初始化，新 server 有 session id 可续，Agent 的重连逻辑要按能力分支。

**取舍**：直接用官方 SDK vs 自己抽象：SDK 升级跟得快但 API 随协议演进频繁 breaking；内部抽象层成本是写一次 + 跟版本维护，收益是应用代码稳定。团队规模大、工具多的选抽象层；小团队直接 SDK + pin 版本更快。另一个取舍：server 侧要支持无状态模式（每请求自带上下文）才能上 K8s 水平扩展——有状态会话模式（session id 粘实例）扩容与滚动发布都麻烦，生产 server 默认无状态 + 外部存储。

**实战**：适配要点清单：① initialize 握手记录双方版本，不匹配时按官方兼容矩阵回退；② 工具 schema 缓存失效（server 重连后 tools/list 重新拉取，禁止进程内永久缓存）；③ 错误归一（stdio 的 JSON-RPC error vs HTTP 的状态码 → 统一错误分类）；④ 安全面：远程 MCP server 的工具描述与返回内容当作不可信输入（prompt 注入面，与 Q7525 呼应），stdio 本地工具校验可执行文件来源。

```python
# MCP 客户端适配骨架：版本协商 + 传输归一 + 会话恢复分支（仅标准库）
# 仅标准库，Python 3.9+；生产用 mcp SDK（python-sdk，2024-2025 活跃演进）
from __future__ import annotations


class McpClient:
    SUPPORTED = ("2025-06-18", "2025-03-26", "2024-11-05")  # 已知协议版本

    def __init__(self, transport: str) -> None:
        assert transport in ("stdio", "streamable-http")
        self.transport = transport
        self.protocol: str | None = None
        self.session_id: str | None = None
        self.tools: list[str] | None = None  # None 表示未拉取

    def initialize(self, server_version: str) -> None:
        """版本协商：回退到双方共同支持的最高版本。"""
        common = [v for v in self.SUPPORTED if v == server_version]
        self.protocol = common[0] if common else self.SUPPORTED[-1]
        self.tools = None  # 重连后 schema 必须重新拉取
        if self.transport == "streamable-http":
            self.session_id = f"sess-{self.protocol}"  # 服务端下发
        print(f"协商完成: server={server_version} → using {self.protocol} "
              f"(transport={self.transport}, session={self.session_id})")

    def list_tools(self) -> list[str]:
        assert self.tools is None or True
        self.tools = [f"{self.transport}:{t}" for t in ("search", "write_file")]
        return self.tools

    def reconnect_resume(self, was_crashed: bool) -> str:
        """会话恢复按能力分支：有 session id 可续，否则重新初始化。"""
        if was_crashed and self.session_id:
            return "resume-with-session"
        return "reinitialize"


def main() -> None:
    c1 = McpClient("stdio")
    c1.initialize("2024-11-05")  # 老版本工具
    c2 = McpClient("streamable-http")
    c2.initialize("2025-06-18")  # 新版本
    assert c1.protocol == "2024-11-05" and c2.protocol == "2025-06-18"

    # 未知未来版本 → 回退最低公共版并告警
    c3 = McpClient("streamable-http")
    c3.initialize("2099-01-01")
    assert c3.protocol == "2024-11-05", "未知版本回退到最老已知版"

    assert c2.reconnect_resume(True) == "resume-with-session"
    assert c1.reconnect_resume(True) == "reinitialize"
    print("结论：版本协商回退 + 传输归一 + 恢复分支，应用层不感知协议变迁")


if __name__ == "__main__":
    main()
```

**追问链**：

- 追问 1：为什么 stdio 模式不能简单换成 Streamable HTTP 就上生产？——stdio 是本地信任边界内的子进程（无认证、同用户权限）；换成远程 HTTP 后认证（OAuth token 生命周期）、传输安全（TLS）、多租户隔离、DoS 防护全是新命题。迁移是安全模型升级，不只是传输切换。
- 追问 1.1：会话恢复（session id）与水平扩展的矛盾怎么解？——session 粘实例则滚动发布/扩缩容断会话；解法是 server 无状态模式 + 会话状态外置（Redis），session id 只是逻辑键。代价是每请求多一次状态读取，与 Q7571 的检查点外置同一思路。
- 追问 2：工具 schema 缓存为什么必须随重连失效？——server 可能在运行期更新工具实现或参数（甚至恶意篡改描述注入提示）；永久缓存会让 Agent 按旧 schema 调用新实现，参数错配或安全绕过。schema 拉取结果是安全审计对象，不是静态配置。

**背诵要点**：

1. MCP 演进主线 stdio（本地信任、无认证）→ Streamable HTTP（OAuth、session、无状态模式）；应用层只依赖内部抽象（list/call/协商）。
2. 版本协商显式化：initialize 握手，未知版本回退最低公共版并告警；工具 schema 随重连失效，禁止永久缓存。
3. 生产 server 默认无状态 + 会话状态外置才能水平扩展；远程 server 的工具内容按不可信输入对待（注入面）。
