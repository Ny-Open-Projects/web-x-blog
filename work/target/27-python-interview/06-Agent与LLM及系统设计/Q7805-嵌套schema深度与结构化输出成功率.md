### Q7805 · 嵌套 schema 的深度账：结构化输出为什么在第三层开始崩

难度：P7 ｜ 标签：结构化输出、JSON Schema、嵌套深度、失败率、扁平化

基线：库知识库外知识卡，用"每层字段成功率随深度衰减"的模型模拟嵌套 schema 的整体生成成功率，对比扁平化与分次调用。

**问**：合同抽取接口的 schema 有 4 层：`contract.parties[].contacts[].addresses[]`，每个对象还有 3~5 个必填字段。上线后整体校验失败率 43%，badcase 里大量"第三层的 `city` 丢了""`addresses` 被写成对象而不是数组"。把 schema 拍平成 `party_name, contact_name, city, street` 四列后失败率降到 9%，但业务侧要自己重组。嵌套到底难在哪？为什么不是"模型不够强"？有没有既保留结构又稳定的做法？

**答**：

- **结论**：结构化输出是**逐 token 自回归**生成的：每多一层嵌套，模型要同时维护"当前在哪个对象、哪个数组、下一个必填字段是什么、括号/逗号是否闭合"的状态。深度增加带来三个放大：① **状态长度**变长，注意力被稀释，深层字段更容易漏；② **错误恢复**变难，少一个 `}` 后面全错，而扁平结构一处错只影响一行；③ **数组/对象歧义**，模型在"空数组"与"缺字段"、"对象"与"数组"之间摇摆。失败率不是线性增加，而是**每层相乘**：单字段 97% 正确，12 个字段串起来就只剩约 60%。
- **取舍**：① 扁平化 + 应用层组装：最稳，字段级校验/重试容易，代价是冗余与重组代码；② 分次调用（先抽主体，再按主体抽联系人，再抽地址）：每次深度 ≤2，成功率乘积可控，代价是调用次数与上下文传递；③ 保留嵌套但减少必填/层数：schema 设计约束（≤2 层、数组元素扁平、可空字段显式 nullable），成本最低；④ 约束解码：保证括号/类型合法，但保证不了"深层字段不漏"，仍需业务校验。
- **实战**：① schema 设计规则：嵌套 ≤2 层、数组元素用扁平对象、必填字段 ≤6 个、用 `oneOf + discriminator` 代替模糊联合；② 每个节点单独校验，失败只重试该子树，不要整份重生成；③ 评测按"深度/字段数"分层，别只看整体成功率；④ 对深层数组，先让模型输出"实体列表"，再逐实体补齐详情，避免一次生成整棵树。

下面用"每层字段成功率随深度衰减"的模型，量化嵌套、扁平、分次调用的整体成功率。

```python
# 嵌套 schema 的成功率: 每层字段相乘, 深度越深整体越低
import random


def field_p(depth):
    # 浅层 99.5%, 每深一层掉 2 个点
    return 0.995 - 0.020 * (depth - 1)


def success_rate(depths, trials=4000, seed=0):
    rng = random.Random(seed)
    ok = 0
    for _ in range(trials):
        if all(rng.random() < field_p(d) for d in depths):
            ok += 1
    return ok / trials


flat = [1] * 12
nested = [1] + [2] * 3 + [3] * 4 + [4] * 4
r_flat = success_rate(flat)
r_nested = success_rate(nested)
print(f"[1] 扁平 12 字段(深度1): 成功率={r_flat:.0%}")
print(f"[2] 4 层嵌套 12 字段: 成功率={r_nested:.0%}")
assert r_flat > 0.9
assert r_nested < r_flat - 0.15
print("    → 实测 同样的字段数, 嵌套把成功率从 0.94 拉到 0.59")

# 深度递增的边际: 第 3->4 层是断崖
for depth in (1, 2, 3, 4):
    p = success_rate([depth] * 6)
    print(f"[3] 6 个字段全在深度 {depth}: 成功率={p:.0%}")

# 分次调用: 每次深度 <=2, 成功率相乘
step1 = success_rate([1] * 4 + [2] * 2)
step2 = success_rate([1] * 4 + [2] * 2)
combined = step1 * step2
print(f"[4] 分两次调用(每次深度<=2): 单次={step1:.0%}, 合计={combined:.0%}")
assert combined > r_nested
print("    → 实测 分次调用把'一棵深树'拆成'两棵浅树', 成功率高于一次生成")

# 扁平化的代价: 行数膨胀, 需要应用层重组
rows_per_contract = 12
print(f"[5] 扁平化后每份合同 {rows_per_contract} 行, 需按 contract_id 重组")
assert rows_per_contract == 12
print("    → 实测 结构稳定性与重组成本是一对账; 深层数组优先'先列实体再补详情'")
```

**追问一**：约束解码不能保证深层字段不丢吗？—— 约束解码保证的是**语法合法**（括号、类型、枚举），不保证**语义完整**：模型可以在合法 JSON 里少写一个可选字段，或者把 `addresses` 输出成空数组。必填字段可以在文法层强制，但"该有 3 个联系人却只给了 1 个"是内容问题，只能靠业务校验/二次抽取。

**追问二**：为什么扁平化后还要按 `contract_id` 重组？不能直接给业务用吗？—— 扁平表适合存储/校验/重试，但业务对象是树。重组逻辑要显式：按 `contract_id` 分组、按 `party_index/contact_index` 排序、空值补默认。重组代码是确定性的，可以单测；让模型直接生成树则是概率性的，难测。把不确定性收敛到"字段抽取"，把确定性留给"组装"。

## 背诵要点

- 结构化输出逐 token 生成，嵌套越深状态越长、错误恢复越难、数组/对象歧义越多；成功率按字段相乘，不是线性下降。
- 设计规则：嵌套 ≤2 层、数组元素扁平、必填 ≤6、`oneOf + discriminator`；深层数组"先列实体再补详情"。
- 扁平化 + 应用层重组最稳；分次调用让每次深度 ≤2；约束解码保语法，不保内容完整。
