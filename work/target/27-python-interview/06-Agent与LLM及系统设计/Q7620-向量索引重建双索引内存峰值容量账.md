### Q7620 · 向量索引重建期间的双索引内存峰值容量账

难度：P6 ｜ 标签：容量规划 / HNSW 重建 / 向量库

**问**：1 亿条 768 维向量（fp32）建在 HNSW 上，需要换参数重建（M/ef_construction 调整）。重建期间新旧索引并存，内存怎么算？重建时长与在线服务怎么共存？"灰度切流"的容量检查点是什么？

**答**：
- **结论**：内存账三层：① **原始向量层**——1 亿 × 768 维 × 4B ≈ 288GB（fp32）；halfvec/fp16 可减半（Q7616 已谈压缩路线），量化（PQ）可再压 10~30x 但召回有损；② **图结构层**——HNSW 的邻居列表：每节点 M 个邻居（两层结构平均按 M*2 记），每条边 4B ID + 建图期临时开销，M=32 时约 1 亿 × 64 边 × 4B ≈ 25GB，加上层级结构与链表开销按 1.5x 计 ≈ 40GB；③ **重建峰值** = 旧索引常驻（328GB）+ 新索引构建中（328GB × 增长曲线）+ 构建临时缓冲（候选集/visited 位图）——峰值接近 2 倍常驻，再加 20% 余量。所以"重建机器"要么是独立实例（构建完再换），要么原集群要预留 >2 倍内存——后者常不可能，答案通常是**独立构建集群**。时长账：HNSW 构建吞吐约 1~5k 向量/s/节点（视参数与机器），1 亿条 / 3k/s ≈ 9 小时/节点，横向扩 N 节点分片并行可到 1~2 小时级（但分片间是独立的图，查询要扇出）。共存策略：重建期间旧索引继续服务；新索引就绪后做**召回率与延迟对拍**（同一查询集 diff），达标后按查询比例灰度切流，旧索引保留回滚窗口（内存因此要容得下"切流期双索引"）。
- **取舍**：原地重建 vs 双索引 vs 独立集群：原地（删旧建新）零双倍内存但服务中断数小时，通常不可接受；双索引内存最贵、切换最平滑；独立集群构建折中——构建期不占服务内存，但需要一次全量数据传输与最终切换。切流检查点：召回@10 与旧索引差 <1%（查询集抽样）、P99 延迟不升、内存水位 <80%、增量写入双写一致（重建窗口内的新增数据必须补进新索引——快照 + binlog/队列回放，否则切流丢数据）。
- **实战**：落地：① 重建前用 10 万条子集实测目标参数的召回/延迟/构建吞吐，外推全量时长与内存；② 构建集群规格按"2 × 常驻 + 20% 缓冲"申请，构建完降配释放；③ 快照点 + 增量回放保证"构建期间写入不丢"；④ 切流按 5%→25%→100% 观察，回滚开关保留 72 小时；⑤ 重建窗口避开大促与索引升级叠加。

```python
# HNSW 重建容量账：向量层 + 图层 + 重建峰值 + 切流共存
# 基线：Python 3.9+ 标准库；参数以子集实测外推
from dataclasses import dataclass


@dataclass
class IndexSpec:
    n_vectors: int
    dim: int
    bytes_per_el: float = 4.0     # fp32
    m: int = 32                   # HNSW 邻居数


def base_memory_gb(s: IndexSpec) -> float:
    vec = s.n_vectors * s.dim * s.bytes_per_el
    edges = s.n_vectors * s.m * 2 * 4 * 1.5   # 双向边 + 结构开销
    return (vec + edges) / 1024**3


def rebuild_peak_gb(s: IndexSpec, buffer_factor: float = 1.2) -> float:
    return 2 * base_memory_gb(s) * buffer_factor


def build_hours(s: IndexSpec, throughput_per_node: float, nodes: int) -> float:
    return s.n_vectors / (throughput_per_node * nodes) / 3600


def main() -> None:
    s = IndexSpec(n_vectors=100_000_000, dim=768)
    base = base_memory_gb(s)
    vec = 1e8 * 768 * 4 / 1024**3
    assert abs(vec - 286) < 2                    # 向量层 ~286GB
    assert 300 < base < 380, base                # 全索引 ~330GB
    peak = rebuild_peak_gb(s)
    assert peak > 2 * 300                        # 峰值 > 600GB -> 单机不可行
    print(f"常驻 {base:.0f}GB；原地重建峰值 {peak:.0f}GB -> 需独立构建集群")

    h = build_hours(s, throughput_per_node=3000, nodes=1)
    assert 8 < h < 10                            # 单节点 ~9.3h
    assert build_hours(s, 3000, 8) < 1.5         # 8 节点分片 ~1.2h
    print(f"单节点构建 {h:.1f}h；8 节点分片 {build_hours(s,3000,8):.1f}h（查询需扇出）")

    # 切流检查点：召回 diff<1%、水位<80%、增量回放一致
    print("OK: 峰值=2x常驻x1.2; 快照+增量回放保证重建窗口写入不丢")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"快照 + 增量回放"是重建窗口的标配？
→ 一句话提示：重建数小时，期间新写入只进旧索引；切换时若不把窗口内增量补进新索引，召回质量出现静默缺口——快照定起点、队列/binlog 回放补增量，对拍确认无缺口后才切流。

**追问 2**：分片并行构建为什么会让查询变复杂？
→ 一句话提示：每个分片是独立 HNSW 图，跨分片没有邻居关系，查询要扇出到所有分片再归并 top-k——扇出放大延迟与 QPS 压力，分片数要在构建时长与查询扇出之间权衡。

## 背诵要点
- 内存账：向量层 = n×dim×4B（1 亿×768 fp32 ≈ 288GB），图层 ≈ n×M×2×4×1.5（M=32 约 40GB）；重建峰值 = 2×常驻×1.2，单机不可行 → 独立构建集群。
- 构建吞吐 1~5k 向量/s/节点外推时长；分片并行把 9h 压到 1h 级，代价是查询扇出归并。
- 切流检查点：召回@10 diff<1%、P99 不升、内存 <80%、增量回放一致；回滚开关保留 72 小时。

## 复盘追问
- 为什么参数调优的重建要"子集实测外推"而不是拍参数直接全量？提示：M/ef_construction 对召回与构建吞吐的影响非线性且依赖数据分布，子集实测同时拿到质量与时长两个外推基线，避免全量跑完才发现召回不达标。
- 重建窗口里"删向量"怎么处理？提示：HNSW 删除通常是标记而非真删，重建是把死向量清掉的机会——重建前要统计死向量占比，占比高时重建收益翻倍（内存与召回都改善），这也是重建排期的依据之一。
