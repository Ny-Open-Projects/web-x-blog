### Q7598 · Agent 工具调用超时未取消导致重复执行事故复盘

难度：P7 ｜ 标签：Agent / 工具调用 / 超时 / 事故复盘

**问**：Agent 调用一个"创建工单"工具，下游服务超时 30 秒返回 Timeout，Agent 框架自动重试，结果下游实际创建了两张工单；反例是另一次超时后框架放弃，但下游 20 秒后其实执行成功，状态永远对不上。超时后的"未知态"为什么是工具设计的头号难题？

**答**：
- **结论**：超时不等于失败——客户端放弃时服务端可能仍在执行（"客户端超时/服务端成功"是分布式系统经典歧义）。工具调用因此有四种结局：成功、明确失败、超时（未知态）、部分执行。事故机理：把超时当失败重试 = 重复执行副作用；把超时当失败放弃 = 状态悬空。正确设计是把"超时"与"失败"分开建模：① 工具必须是幂等的——调用方携带唯一 `request_id`（幂等键），下游用幂等表去重，重试安全；② 超时后先查询再重试——用 `request_id` 查下游状态（或本地记录"待确认"状态），确认失败才重试；③ 无法提供查询接口的工具必须声明为"非幂等高危"，框架对它禁用自动重试并把超时事件升级人工。
- **取舍**：幂等键方案 vs 对账方案：幂等键在写入前挡重复（强一致，要求下游配合改造）；对账方案事后比对（弱一致，适合不可改造的第三方）；两者常并用——先幂等、兜底对账。另一层取舍在超时预算：工具超时设太短会制造大量未知态（重试风暴），太长会拖死 Agent 主循环（每步的 step 预算被单工具吃掉）；工具超时应 ≤ 步骤预算的 1/3，且长任务工具应改成异步任务模式（提交返回 task_id + 轮询）。
- **实战**：事故剧本：① 复盘重复工单：下游幂等表 + 框架全链路透传 request_id；② 工具分类分级：只读/幂等/非幂等三档，非幂等档禁自动重试并要求人工确认流程；③ 悬空态检测：本地"待确认"队列定期对账未闭合的调用；④ 复盘项：监控"超时后重试导致的重复执行率"作为工具健康指标。

```python
# 工具调用幂等与未知态处理框架（纯标准库）
# 基线：Python 3.9+

import enum
import uuid


class Outcome(enum.Enum):
    OK = "ok"
    FAILED = "failed"
    TIMEOUT_UNKNOWN = "timeout_unknown"


class IdempotentDownstream:
    """带幂等表与查询接口的下游（可改造型）"""

    def __init__(self, fail_first: bool = True) -> None:
        self.requests: dict[str, str] = {}
        self.fail_first = fail_first

    def query(self, request_id: str) -> str | None:
        return self.requests.get(request_id)

    def execute(self, request_id: str, payload: str) -> str:
        if request_id in self.requests:
            return self.requests[request_id]  # 幂等命中
        if self.fail_first:
            self.fail_first = False
            raise TimeoutError("simulated timeout after side effect")
        self.requests[request_id] = f"ticket({payload})"
        return self.requests[request_id]


def call_tool(ds: IdempotentDownstream, payload: str,
              max_retries: int = 3) -> Outcome:
    """超时 -> 先查询 -> 确认未执行才重试"""
    rid = str(uuid.uuid5(uuid.NAMESPACE_URL, payload))  # 确定性幂等键
    for _ in range(max_retries):
        try:
            ds.execute(rid, payload)
            return Outcome.OK
        except TimeoutError:
            if ds.query(rid) is not None:
                return Outcome.OK        # 未知态闭合：其实已成功
            # 未执行 → 安全重试
    return Outcome.TIMEOUT_UNKNOWN


def main() -> None:
    ds = IdempotentDownstream(fail_first=True)  # 第一次超时但实际已写?这里模拟未写
    r = call_tool(ds, "refund-42")
    assert r == Outcome.OK
    assert len(ds.requests) == 1, "重试不应造成重复执行"
    # 模拟"超时但服务端已成功"：query 闭合，不重试
    ds2 = IdempotentDownstream(fail_first=False)
    rid = str(uuid.uuid5(uuid.NAMESPACE_URL, "refund-42"))
    ds2.requests[rid] = "ticket(refund-42)"   # 服务端其实成功了
    class Timeouter:
        def execute(self, *_): raise TimeoutError
        def query(self, rid_): return ds2.query(rid_)
    r2 = call_tool(Timeouter(), "refund-42")
    assert r2 == Outcome.OK
    print("OK: 幂等键 + 查询闭合，重试不产生重复副作用")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么长任务工具应该改成"提交 + 轮询"异步模式？
→ 一句话提示：同步等待把超时歧义扩大（等得越久未知态越多）；提交返回 task_id 后，客户端状态机变成"提交→查询→终态"，超时只影响查询本身，可无限次安全重查。

**追问 2**：对账方案（事后比对）怎么避免"把合法新请求当重复"误杀？
→ 一句话提示：对账必须用与执行相同的幂等键关联，且比对窗口要覆盖下游最大处理延迟；窗口外的键视为已闭合，只处理窗口内"待确认"未闭合的悬空态。

## 背诵要点
- 超时 = 未知态 ≠ 失败：当失败重试会重复执行副作用，当失败放弃会状态悬空。
- 解法分层：幂等键透传（request_id 全链路）→ 超时先查询再重试 → 不可改造的第三方用对账兜底；非幂等工具禁自动重试。
- 工具超时 ≤ 步骤预算 1/3；长任务工具改"提交 + task_id 轮询"消灭未知态。

## 复盘追问
- 为什么幂等键要由调用方（Agent 框架）生成而不是下游？提示：下游生成的"重复检测"无从判断两次请求是否同一意图；调用方持有重试上下文，确定性生成（如 uuid5(payload)）保证重试复用同一键。
- Agent 主循环里的步骤预算怎么和工具超时联动？提示：单工具超时吃掉全部预算会导致循环里后续工具全部饿死；预算分配应按工具分级（只读短、写入长），并在接近预算时降级为"返回部分结果 + 终止"。
