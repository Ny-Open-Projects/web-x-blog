### Q7671 · LLM 网关到上游的连接池容量账

难度：P6/P7 ｜ 标签：容量规划、LLM 网关、连接池
基线：httpx 0.27+（`Limits(max_connections, max_keepalive_connections)` 语义稳定）。

**问**：LLM 网关用 httpx 异步转发到模型供应商，并发 200 时 P99 延迟陡增、偶发连接超时。网关到上游的连接池容量怎么算？池参数、超时与限流如何联动？

**答**：**结论**：LLM 转发的连接特征与普通 API 网关不同：**单请求占用连接的时间极长**（流式响应几十秒到几分钟），连接池容量 ≈ 并发在途请求数，而不是"QPS × 平均短耗时"。容量账核心公式：`池大小 ≥ 并发上限 × (1 + 冗余)`；池小于并发数时，请求排队等连接，排队时间叠加在 LLM 首字延迟上，表现为 P99 陡增但平均正常——这正是事故形态。

**取舍**：三个参数的联动：① `max_connections` 决定并发天花板，应等于"供应商侧并发配额"（TPM/RPM 之外还有并发连接限制），超出即 429；② 排队不是坏事——显式排队（信号量/队列 + 队列超时）比隐式连接池等待可观测、可公平调度，所以生产上推荐"信号量限并发 + 池略大于信号量"；③ keepalive 复用对 LLM 场景收益有限（响应时间长、复用率低），`max_keepalive_connections` 不必设大。

**实战**：监控四件套：在途请求数、池在用/空闲、等连接排队长度、等连接耗时（单独计时，和上游延迟分开）——P99 陡增时先看排队耗时是不是主因；信号量上限与供应商并发配额联动更新（Q7582 的配额账）。

```python
# 连接池容量账：排队模型 + 参数联动（纯模拟，可运行）
import time
import math
from collections import deque

def pool_latency_model(
    concurrency: int,        # 业务并发在途
    pool_size: int,          # max_connections
    upstream_seconds: float, # 单请求上游耗时（流式取总时长）
) -> dict:
    """M/M/c 近似排队：池不够时请求先排队等连接。"""
    wait_q = deque(range(max(0, concurrency - pool_size)))
    # 每个排队者按"前面人占用时长/池大小"近似估等待
    est_wait = len(wait_q) * upstream_seconds / pool_size
    return {
        "queued": len(wait_q),
        "queue_wait_s": round(est_wait, 1),
        "total_p99_s": round(upstream_seconds + est_wait, 1),
        "verdict": ("池吃紧：调大 max_connections 或限并发"
                    if est_wait > upstream_seconds * 0.3 else "正常"),
    }

# 流式响应平均 45s，并发 200，池 64 —— 经典事故参数
print(pool_latency_model(200, 64, 45))
# queued=136, 等待 ~95s > 上游 45s：P99 由排队主导

# 参数联动设计：信号量 = 供应商并发配额，池 = 信号量 + 10% 冗余
def sizing(vendor_concurrency: int, safety: float = 1.1) -> dict:
    return {"semaphore": vendor_concurrency,
            "max_connections": math.ceil(vendor_concurrency * safety),
            "keepalive": min(32, vendor_concurrency // 4)}
print(sizing(120))

# httpx 生产写法（缺库时降级为上面的模型计算）
try:
    import httpx
    limits = httpx.Limits(max_connections=132, max_keepalive_connections=32)
    timeout = httpx.Timeout(connect=5.0, read=600.0, write=30.0,
                            pool=10.0)   # pool 超时是排队上限
    print("httpx 可用：Limits+Timeout 已构造",
          limits.max_connections, timeout.pool)
except ImportError:
    print("httpx 未安装：以上模型结果即为容量基线")
```

**追问 1**：为什么流式场景 keepalive 复用收益低？
提示：连接在响应期间持续占用，请求结束即归还；下次请求多半是"数秒后另起的连接"，复用窗口对不上——keepalive 主要省的是 TLS 握手，对 45s 的请求，握手占比可忽略。

**追问 2**：`pool` 超时该设多少？设太大会怎样？
提示：它限制"等连接"时长，应略小于上游请求总超时的预期排队份额；设太大时故障表现为请求悬死几分钟后集中超时（重试风暴），设太小则正常排队被误杀——按排队模型 P99 × 1.5 定。

**追问 3**：为什么排队要显式化（信号量）而不是依赖池的隐式等待？
提示：显式队列可观测（长度、等待分布）、可公平（按租户/优先级出队）、可在入队前拒绝（过载保护）；池隐式等待只有 `pool timeout` 一个信号，无法区分"谁在等、等了多久"。

## 背诵要点
1. LLM 网关连接特征：单连接占用 = 流式总时长（数十秒），池大小 ≈ 并发在途数，不是 QPS 公式。
2. 排队显式化：信号量 = 供应商并发配额，池 = 信号量 × 1.1；queue_wait > 30% 上游耗时即告警。
3. keepalive 收益低（长响应复用不上），pool 超时按排队 P99 × 1.5 定，防悬死与重试风暴。
