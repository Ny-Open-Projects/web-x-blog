### Q7590 · 向量检索查询侧 QPS 容量账与副本扩容触发器

难度：P6/P7 ｜ 标签：容量规划 / 向量检索 / RAG

**问**：RAG 服务的向量检索（HNSW 索引，常驻内存）在晚高峰 P99 从 15ms 涨到 120ms，检索排队拖垮整条链路。查询侧的 QPS 容量怎么算？副本该按什么触发器扩、扩多少？为什么"加机器后延迟反而没降"？

**答**：
- **结论**：查询侧容量账三步走：① 先测**单副本稳态 QPS**——单条查询耗时 ≈ `ef_search × 每跳距离计算成本`，单副本吞吐 ≈ `1 / P50查询耗时 × 并发度`（受 CPU 核数限制，内存型索引是 CPU-bound 不是 IO-bound）；② 算**副本需求**：`副本数 = ceil(峰值QPS × 安全系数 / 单副本QPS) × (1 + 故障冗余)`，安全系数取 1.3-1.5（晚高峰 + 重试放大），冗余至少 +1（一台挂掉剩余副本要接得住全量）；③ 定**扩容触发器**：不要等 P99 爆才扩——用"单副本 QPS 水位"（当前 QPS / 单副本容量）做先行指标，水位 >0.6 预扩、>0.8 紧急扩，因为 HNSW 查询延迟在高并发下是**非线性恶化**（CPU 争抢 + 缓存失效，QPS 逼近容量时 P99 阶梯式跳升）。
- **取舍**："加机器延迟没降"的三种常见根因：① **ef_search / top_k 随流量被动调大**（上游为了压召回率加了 k，单查询成本涨了，容量账基础变了）；② **热向量集超出 CPU 缓存**——单副本 QPS 是低负载下测的，高峰期图遍历的随机内存访问 cache miss 率上升，实际单副本容量比压测值低 30-50%；③ **瓶颈根本不在检索层**——embedding 调用或元数据过滤（后过滤）才是大头，加向量副本无效。所以扩容前必须先做延迟分段记账（query/embed/rerank/post-filter 各段占比），确认检索段占比 >50% 再扩副本。
- **实战**：落地：① 基准值不是常数——每次改索引参数（M、ef_construction、ef_search）或换维度后重测单副本 QPS，容量账版本化管理；② 副本扩展是"无状态横向扩"（向量只读，加副本加路由权重即可），比分片便宜优先用；分片会改变召回结果（每片只搜局部），除非单机内存装不下否则不切；③ 触发器联动预案：水位超阈值先降 ef_search 降级（损失一点召回）再扩容，扩容生效（加载索引 1-5 分钟）期间的空窗靠 ef_search 降档扛住；④ 监控四件套：单副本 QPS 水位、P99 分段延迟、ef_search 降档触发次数、副本加载完成度。

```python
# 向量检索查询侧容量账与扩容触发器（纯标准库）
# 基线：Python 3.9+

import math


def single_replica_qps(p50_ms: float, cores: int, contention: float = 0.75) -> float:
    """单副本稳态 QPS。contention = 高峰期实际有效并发系数（cache miss/CPU 争抢折损）。"""
    per_query_s = p50_ms / 1000.0
    return cores * contention / per_query_s


def replica_needed(peak_qps: float, single_qps: float,
                   safety: float = 1.4, fault_redundancy: int = 1) -> int:
    """副本数 = ceil(峰值*安全系数/单副本) + 故障冗余；冗余台也必须接得住全量。"""
    base = math.ceil(peak_qps * safety / single_qps)
    return base + fault_redundancy


def scale_trigger(current_qps: float, single_qps: float) -> str:
    """水位 = 当前QPS/单副本容量。0.6 预扩，0.8 紧急扩。"""
    w = current_qps / single_qps
    if w > 0.8:
        return f"水位={w:.0%} 紧急扩容 + ef_search 降档"
    if w > 0.6:
        return f"水位={w:.0%} 预扩容（副本加载 1-5min 空窗）"
    return f"水位={w:.0%} 正常"


def main() -> None:
    # 单副本：P50=15ms，8 核，高峰折损 0.75
    sq = single_replica_qps(15.0, cores=8)
    assert 350 < sq < 450, sq  # 8*0.75/0.015 = 400

    # 峰值 1200 QPS：1.4 安全系数 -> ceil(1200*1.4/400)=5，加 1 台故障冗余
    n = replica_needed(1200, sq)
    assert n == 6, n
    # 故障演练：挂 1 台后剩余 5 台仍 > 峰值*安全系数
    assert (n - 1) * sq > 1200 * 1.4

    assert "紧急" in scale_trigger(400, sq)      # 400/400 = 100%
    assert "预扩" in scale_trigger(260, sq)      # 65%
    assert "正常" in scale_trigger(200, sq)

    print(f"单副本QPS={sq:.0f} 峰值1200需副本={n}台（含1台冗余）")
    print("降档预案：ef_search 60->40 召回约 -2pp，换扩容空窗不排队")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么向量检索扩副本优先于切分片？
→ 一句话提示：副本是只读无状态扩展、召回结果与单机完全一致；分片后每查询只搜局部子集，召回率下降需要提高 ef_search 或扇出聚合补偿，成本与正确性都要重新算账。

**追问 2**：ef_search 降档降级和扩容怎么配合才不抖动？
→ 一句话提示：降档是秒级生效的"临时桥"，扩容是分钟级的"根治"，降档触发时同步启动扩容、副本就绪后恢复 ef_search，且水位判定加滞回（升 0.8 降 0.7）防止反复进出。

**背诵要点**：
1. 容量账三步：测单副本稳态 QPS → 副本数 = ceil(峰值×1.4/单副本) + 1 台故障冗余 → 水位 0.6 预扩 / 0.8 紧急扩。
2. "加机器不降延迟"三根因：ef_search/top_k 被调大、高峰 cache miss 使单副本实际容量低 30-50%、瓶颈在 embed/后过滤段——先分段记账确认检索段 >50%。
3. 副本扩优先于分片：副本保召回一致性；分片改变召回结果，只在内存装不下时启用。

**复盘追问**：
1. 单副本 QPS 基准为什么会在高峰期失真？——提示：低负载压测的 cache 命中率与高峰不同，容量基准要按高峰折损系数（如 0.75）打靶，不能拿裸压测值排班。
2. 晚高峰 P99 从 15ms 到 120ms 的跳变形态说明什么？——提示：非线性恶化（逼近容量后排队 + CPU 争抢），是"过容量"信号而非"变慢"，看水位而不是只看绝对延迟。
