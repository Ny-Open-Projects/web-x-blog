### Q7531 · LLM 网关容量规划：单实例到底能挂多少个流式会话？

> 难度:★★★★ | 标签:容量规划, LLM 网关, 流式

**问**：LLM 网关的容量规划和普通 API 服务不一样：每个流式会话要长时间占用一个并发槽，token 吞吐是瓶颈。单实例能挂多少个同时生成的会话怎么算？实例数怎么推？扩容触发器（水位 vs 延迟）怎么设？

**答**：结论：单实例可挂会话 = **并发槽约束与吞吐约束取小**再打利用率折扣——并发槽（内存/连接/事件循环）是硬上限，吞吐约束 = 网关总 token 预算 ÷ 单会话流式速率；稳态并发会话数 = 到达率 × 会话时长（Little 定律），实例数 = 峰值并发 ÷ 单实例可挂。扩容触发器用**双门限**：容量水位 70% 或排队 P99 超预算，任一命中即扩。

机理与实战：
- **为什么流式服务容量算不平**：普通 API 请求毫秒级返回、连接即用即还；流式会话占槽几十秒——容量从"QPS"变成"同时在线会话数"，任何按 QPS 做的容量估算都会错一个量级。
- **吞吐约束常被忽略**：200 个并发槽 ≠ 200 个会话——单会话流式 25 token/s 时，3500 token/s 的出口预算只够 140 个会话；利用率折扣（70%）留给头部波动与重试。
- **排队恶化是非线性的**：负载超 100% 后等待时间按 (负载-1) 快速恶化，P99 比 TPS 先崩——所以触发器必须带延迟门限，只看水位会在 95% 水位时安然自得然后突然雪崩。
- **两个容易漏的账**：① 重试与多轮对话会放大到达率（用户重发、Agent 重试），容量账要乘放大系数；② TTFT 是体验核心，排队 1 秒的 TTFT 恶化比吞吐下降更容易被用户感知——P99 门限应锚定 TTFT 预算。

```python
# 基线:Python 3.10+;纯标准库模拟 LLM 网关容量账(TTFT/吞吐/并发 -> 实例数与扩容触发器)
# 真实场景:流式会话占并发槽;并发数 = 到达率 x 会话时长;容量双约束取小
from __future__ import annotations


def sessions_per_instance(max_conc: int, stream_tok_per_s: float,
                          gateway_tok_per_s: int, utilization: float = 0.7) -> float:
    """单实例可挂会话:并发槽约束 vs 吞吐折算,取小再打利用率折扣。"""
    by_conc = max_conc
    # 每会话占用的网关吞吐 = 单会话流式速率;吞吐折算会话数 = 总吞吐 / 单会话速率
    by_throughput = gateway_tok_per_s / stream_tok_per_s
    return min(by_conc, by_throughput) * utilization


def concurrent_sessions(arrival_per_s: float, duration_s: float) -> float:
    """稳态下的同时在生成会话数(Little 定律)。"""
    return arrival_per_s * duration_s


def wait_p99_s(concurrent: float, capacity: float, ttft_s: float) -> float:
    """粗略排队:P99 等待随 (负载-1) 恶化;未饱和时只有抖动项。"""
    load = concurrent / capacity
    if load <= 1:
        return ttft_s * 0.2
    return ttft_s * (load - 1) * 8


def demo() -> None:
    # 参数:单实例并发槽 200、单会话流式速率 25 tok/s、实例吞吐预算 3500 tok/s、TTFT 0.8s
    per_inst = sessions_per_instance(200, stream_tok_per_s=25.0,
                                     gateway_tok_per_s=3500)
    print(f"单实例可挂会话 ≈ {per_inst:.0f}(并发槽 200 vs 吞吐折算 "
          f"{3500 / 25:.0f},取小 x70%) ✅")

    duration = 800 / 25                                  # 800 token 会话流式 32s
    peak_conc = concurrent_sessions(arrival_per_s=4, duration_s=duration)
    inst = -(-int(peak_conc) // int(per_inst))
    print(f"到达 4 会话/s x {duration:.0f}s = 并发 {peak_conc:.0f} -> 实例 {inst} ✅")

    print("扩容触发器扫描(容量 = 实例 x 单实例可挂):")
    for rate in (2, 3.5, 4.5, 7.5):
        conc = concurrent_sessions(rate, duration)
        cap = inst * per_inst
        p99 = wait_p99_s(conc, cap, ttft_s=0.8)
        load = conc / cap
        trigger = "扩容!" if load > 0.7 or p99 > 1.0 else "正常"
        print(f"  {rate}/s: 并发 {conc:.0f}/容量 {cap:.0f} = {load:.0%},"
              f"P99 等待 {p99:.2f}s -> {trigger}")
    assert wait_p99_s(concurrent_sessions(7.5, duration), inst * per_inst, 0.8) > 1.0
    print("双门限:水位 70% 或 P99 > 1s 任一命中即扩容 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：为什么"按 QPS 做的压测报告"对流式网关几乎没有参考价值？
答：QPS 压测的请求生命周期毫秒级，测的是连接建立与短计算；流式网关的瓶颈是"槽位驻留时长 × 吞吐"——同样 100 QPS，回答 100 token 和回答 2000 token 的容量差 20 倍。压测必须按"会话到达率 × 会话时长分布"建模，并模拟真实 token 长度分布（长尾回答决定 P99 槽占用）。

**追问二**：单实例并发槽受什么限制？多路复用（同一连接并发多个流）能提升容量吗？
答：槽 = 事件循环连接数 × 内存（每会话缓冲）× 下游连接池；多路复用把"连接数"上限拉开后，瓶颈转移到吞吐与内存——模型变了但账没变：还是并发槽与吞吐取小。另外下游供应商侧也有并发会话配额，网关扩容前要先确认供应商配额不是真正的天花板。

## 背诵要点
- 单实例可挂会话 = min(并发槽, 总吞吐/单会话流式速率) × 利用率(0.7)；流式会话驻留几十秒，容量单位是"并发会话"不是 QPS。
- 稳态并发 = 到达率 × 会话时长（Little 定律）；重试/多轮放大到达率要乘系数。
- 扩容双门限：水位 70% 或排队 P99 超 TTFT 预算——负载过 100% 后 P99 非线性恶化，只看水位会雪崩。

## 复盘追问
- 峰值时段 TTFT 从 0.8s 恶化到 5s 但吞吐看起来正常，最可能的原因？（提示：并发会话逼近容量、排队发生在"拿槽"阶段——看排队长度与水位，而非 token 吞吐）
- 如何把"多轮对话"的容量放大系数估出来？（提示：按会话轮次分布 × 每轮 token 分布建模，用真实流量回放校准，系数通常 1.5-3 倍）
