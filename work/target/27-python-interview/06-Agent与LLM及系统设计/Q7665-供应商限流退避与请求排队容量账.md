### Q7665 · 供应商限流退避与请求排队容量账：429 风暴怎么算

难度：P6-P7 | 标签：容量规划、限流、LLM 供应商

**问**：业务高峰时 LLM 供应商返回 429（RPM/TPM 超限），客户端指数退避重试后 429 反而更密——重试风暴。退避参数怎么设计？发送前的"本地配额账"怎么算才能少撞限？多模型/多供应商时配额账怎么合并？

**答**：结论：429 风暴是**重试流量叠加新流量**的排队论问题：撞限后 N 个客户端同时指数退避，退避到期又同时涌入（thundering herd），本地无预算控制时重试流量放大打满配额。修复三层：① 客户端退避带抖动（jitter）避免同步；② **发送前本地预算账**——按已知 RPM/TPM 在客户端维护令牌桶，超预算的请求排队而不是撞上 429 再退（Q7582 租户分配是服务端视角，本卡是客户端视角）；③ 429 响应里的 `Retry-After` 必须遵守并计入本地预算重置。

取舍与实战：
1. 退避参数：初始 0.5-1s、倍率 2、上限 30s、full jitter（随机区间 [0, min(cap, base*2^n)]）——AWS 指数退避论文结论 full jitter 优于 equal/partial jitter；重试次数 4-5 次后进入降级（切模型/排队/失败，Q7646 切换预案）。
2. 本地预算账的输入：供应商配额是**实例级**（API key 维度）的 RPM+TPM 双桶；多实例部署要配额分片（每实例固定份额 + 动态借用），否则实例间互相踩。TPM 比 RPM 更紧（长上下文单请求几千 token），预算按 TPM 为主 RPM 为辅。
3. 排队账：本地队列长度 = 可容忍延迟 / 平均处理时长；排队优于重试的点在于"已知要等，不如有序等"——429 后重试本质是把排队外包给供应商的随机丢弃。
4. 多供应商合并：预算账抽象成 ProviderQuota 接口，主供撞限自动切备供（备供配额单独记账）；切流本身要限速防止把备供也打爆。

```python
"""客户端 TPM 令牌桶 + 带抖动退避决策（标准库，可运行）"""
import random, time

class TokenBucket:
    def __init__(self, rate_per_min: int):    # TPM/RPM
        self.capacity = rate_per_min
        self.tokens = float(rate_per_min)
        self.ts = time.monotonic()

    def take(self, n: int) -> float | None:
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.ts) / 60 * self.capacity)
        self.ts = now
        if self.tokens >= n:
            self.tokens -= n
            return None                        # 可立即发送
        wait = (n - self.tokens) / self.capacity * 60
        return wait                            # 建议等待秒数

def backoff(attempt: int, base=1.0, cap=30.0) -> float:
    return random.uniform(0, min(cap, base * 2 ** attempt))   # full jitter

bucket = TokenBucket(rate_per_min=90_000)      # TPM 预算
wait = bucket.take(5_000)                       # 一个 5k token 的请求
print("本地预算等待:", f"{wait:.1f}s" if wait else "立即发送")
print("429 后第 3 次退避:", round(backoff(3), 2), "s (full jitter)")
assert wait is None or wait > 0
```

**追问 1**：为什么 full jitter 优于 equal jitter（固定部分+随机部分）？
**提示**：equal jitter 的固定底让所有客户端退避后仍在相近时刻到达（同步成分保留）；full jitter 完全打散到达时刻，实证吞吐恢复最快（AWS Architecture Blog 对比结论）。

**追问 2**：`Retry-After` 与本地令牌桶怎么协同不冲突？
**提示**：429 的 Retry-After 是服务端权威信号，收到后应把本地桶的可用时间推到该时刻（而不是继续按本地速率放行）；同时把这次超限量记账，修正本地预算与真实配额的偏差。

## 背诵要点
- 429 风暴 = 重试同步叠加新流量；解法三层：full jitter 退避、发送前 TPM/RPM 令牌桶、遵守 Retry-After。
- TPM 比 RPM 紧（长上下文单请求数千 token）；多实例部署配额要分片防互踩。
- 本地排队优于撞限重试：已知等待时长比随机丢弃有序；重试 4-5 次后切模型/供应商降级。
