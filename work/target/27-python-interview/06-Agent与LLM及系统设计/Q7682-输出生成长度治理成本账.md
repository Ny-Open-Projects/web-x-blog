### Q7682 · 输出侧的成本工程：生成长度治理与 max_tokens 的账

难度：P6 ｜ 标签：成本工程、输出 token、生成长度
基线：LLM 计费通用规则（输出 token 单价通常为输入的 3-4 倍）；openai 1.x / anthropic 0.3x。

**问**：团队都在优化"prompt 瘦身"，但账单大头其实是输出——输出 token 单价是输入的 4 倍，而平均输出 1800 token 远超业务需要。输出侧的成本工程有哪些手段？"少给 max_tokens"是省钱还是埋雷？

**答**：**结论**：输出成本 = 单价高（3-4 倍）× 数量失控（模型倾向写多）。四段治理：① **长度预算显式化**——按用例类型设 max_output_tokens（分类/抽取 200、摘要 600、代码生成 2000），而不是全链路一个默认值；② **指令级约束**——prompt 明确"不超过 N 字/条目化输出"，实测可降 20-40%，但要配合长度监控防漂移；③ **停止条件**——stop 序列、结构化输出（JSON schema 天然限定输出形状）、多轮工具调用中只回传摘要；④ **推理模型的隐藏账**——o 系列/思考型模型的"推理 token"计入输出，复杂度低的任务换标准模型省 10 倍。max_tokens 设小不是省钱是埋雷：**截断是双输**——内容残缺导致下游解析失败，用户重试反而双倍计费；正确做法是"预算给足 + 指令压短 + 监控截断率"。

**取舍**：指令压短的收益与质量风险并存：摘要任务压 30% 通常无损，创意/代码任务过度压缩直接降质——按用例分级做 A/B，把"长度-质量"曲线画出来再定阈值。结构化输出的取舍是灵活性：schema 限形省钱但表达受限，长流程任务的中间推理仍需自由文本。推理模型的取舍是延迟与质量：混用路由（简单任务走标准模型）的判定本身要有置信度兜底，误路由的返工成本要计入账。

**实战**：输出预算账与截断率监控（标准库）：

```python
# 输出 token 成本账：分用例预算 + 截断监控
PRICE_IN, PRICE_OUT = 2.5 / 1e6, 10 / 1e6   # 输出单价是输入的 4 倍

BUDGETS = {   # 用例 -> (max_output, 目标平均输出)
    "分类/抽取": (300, 120),
    "客服摘要":  (800, 450),
    "代码生成":  (2500, 1400),
}
in_tok = 1200   # 输入侧已优化稳定

total = 0
for name, (mx, target) in BUDGETS.items():
    out = target
    cost = (in_tok * PRICE_IN + out * PRICE_OUT)
    total += cost
    print(f"{name}: 输入 {in_tok} + 输出 {out}/{mx} -> {cost*1000:.2f} 厘/次")
print(f"未治理（统一 2000 输出）: {(in_tok*PRICE_IN + 2000*PRICE_OUT)*1000:.2f} 厘/次\n")

# 截断率监控：max_tokens 设小的雷
class TruncationMonitor:
    def __init__(self, budget: int):
        self.budget = budget
        self.hits = 0
        self.n = 0

    def observe(self, out_len: int, finish_reason: str):
        self.n += 1
        if finish_reason == "length":   # 因 max_tokens 截断
            self.hits += 1
            return "ALERT: 截断 -> 下游解析失败率上升，重试双倍计费"
        return None

m = TruncationMonitor(300)
m.observe(280, "stop")
print(m.observe(300, "length") or "ok")
print(f"截断率 {m.hits/m.n*100:.0f}% —— 预算设置的原则是截断率 <1%")

# 推理模型隐藏账：reasoning token 计入输出
reasoning_tok, visible_tok = 4000, 300
eff_out = reasoning_tok + visible_tok
print(f"\n推理模型单次有效输出 {eff_out} tok = "
      f"{eff_out*PRICE_OUT*1000:.0f} 厘 —— 是标准模型可见输出的 {eff_out/300:.0f} 倍")
```

**追问 1**：为什么输出截断的实际代价比表面更大？
提示：截断的 JSON/半截代码触发下游重试与降级链路，重试是全额重新计费（输入+输出），一次截断重试的成本约等于 2.5 次正常请求，还叠加用户等待。

**追问 2**：怎么把"指令压短"的效果做成可监控的闭环？
提示：输出长度 P50/P95 按用例打点，指令调整后对比分布；设定目标 P95 预算与告警，prompt 版本变更时长度分布作为回归指标之一。

**追问 3**：推理模型（o 系列）什么时候值得用？
提示：决策标准是"正确率提升幅度 × 业务价值 > 推理 token 溢价"；仅在高难推理/数学/复杂规划上用，且给它的输出预算要含 reasoning——预算忘了算会成倍的账。

## 背诵要点
1. 输出单价是输入的 3-4 倍，账单大头常在输出：按用例设 max_output 预算（抽取 200/摘要 600/代码 2000）而非全局默认。
2. 截断是双输：残缺触发重试（≈2.5 倍成本）+ 解析失败；预算原则"截断率 <1%"，压长度靠指令与结构化输出而非压 max_tokens。
3. 推理模型的 reasoning token 计入输出：低复杂度任务误用推理模型成本放大 10 倍，路由判定要有置信度兜底。
