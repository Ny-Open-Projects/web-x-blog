### Q7797 · 流式响应重试的幂等：半截输出已经推给用户之后怎么收场

难度：P7 ｜ 标签：Agent、流式输出、SSE、重试、幂等、message_id、断点续传

基线：库知识库外知识卡，代码用标准库模拟——用 message_id + seq 的客户端缓冲复现重复前缀与替换语义，不调用外部 API。

**问**：LLM 流式接口在网关层配了"超时自动重试"，某次上游卡顿触发重试，用户看到回复开头重复了两遍："您好您好，关于这个问题……"。更糟的是有的客户端把两段拼在一起，语义直接错乱。流式响应已经推了一半，重试到底该怎么设计？同一个 `message_id` 重发会怎样？换新 id 用户会不会觉得"重新开始"？已经产生的 token 计费能退吗？

**答**：

- **结论**：流式输出是**单向、不可撤回**的：一旦 chunk 推给客户端，服务端就无法"收回"。所以重试的幂等性必须由**协议层**保证，而不是靠"再发一次"。三种收场方式：① **同 `message_id` 从头发**（最常见的事故源）：客户端按到达顺序 append，于是前半段重复，文本变成"您好您好……"；② **新 `message_id` + 显式 abort**：先发一个 `abort` 事件说明"上一条中断"，再用新 id 重新生成，客户端**替换**而不是追加——语义清晰，代价是用户看到内容"重来"；③ **断点续传**：客户端带 `last_seq`/`Last-Event-ID`，服务端从断点继续发，客户端按 `seq` 去重。③体验最好，但要求服务端保留生成状态（多数 LLM API 不提供真正的续传，只能重新生成）。
- **取舍**：同 id 重发实现最简单，但**必须**让客户端能去重（按 `seq` 覆盖写而不是 append），否则一定重复；新 id 最稳，但要有"替换"语义的协议约定（客户端收到新 id 时清空当前消息），且要处理"用户已经读了一半"的体验。断点续传最难：要存 KV/已生成 token、要处理"续传时模型状态已丢"的降级（退化成重新生成），还要防"客户端伪造 last_seq"导致跳过内容。工程上多数团队选②，把③留给自建推理服务。
- **实战**：一次网关 504 重试，用户看到"您好您好，关于退款……"，客服系统把重复文本当成两次意图，触发了两个工单。修复三层：① 网关对"已经开始流式响应"的请求**不再自动重试**（只能重试尚未写出第一个字节的请求）；② 服务端每条流带 `message_id`，重试生成新 id 并先发 `abort` 事件；③ 客户端按 id 做"替换/追加"判定，同 id 的重复 `seq` 直接丢弃。计费侧无法退回已生成的 token——重试就是双份成本，所以网关的重试预算要单独记账。

下面用 message_id + seq 模拟三种收场，观察客户端最终文本。

```python
# 流式重试: 同 id 追加 / 新 id 替换 / 断点续传
class Client:
    def __init__(self, dedup=True):
        self.mid = None
        self.parts = []        # [(seq, text)]
        self.dedup = dedup
        self.aborted = []

    def recv(self, mid, seq, text):
        if self.mid is None:
            self.mid = mid
        elif mid != self.mid:
            self.mid = mid
            self.parts = []    # 新消息: 丢弃旧半截(替换语义)
        self.parts.append((seq, text))

    def abort(self, mid):
        self.aborted.append(mid)

    def text(self):
        if not self.dedup:
            return "".join(t for _, t in self.parts)      # 盲追加
        latest = {s: t for s, t in self.parts}            # 同 seq 覆盖
        return "".join(latest[k] for k in sorted(latest))


FIRST = [(1, "你"), (2, "好"), (3, "，"), (4, "世")]     # 推到 seq=4 后断流
RETRY = [(1, "你"), (2, "好"), (3, "，"), (4, "世"), (5, "界")]

naive = Client(dedup=False)
for s, t in FIRST:
    naive.recv("m1", s, t)
for s, t in RETRY:                    # 同 id 从头发
    naive.recv("m1", s, t)
print(f"[1] 同 id 重发: {naive.text()!r}, '你好'出现 {naive.text().count('你好')} 次")
assert naive.text().count("你好") == 2 and naive.text() == "你好，世你好，世界"

clean = Client()
for s, t in FIRST:
    clean.recv("m1", s, t)
clean.abort("m1")
for s, t in RETRY:                    # 新 id: 替换
    clean.recv("m2", s, t)
print(f"[2] 新 id 替换: {clean.text()!r}, abort 记录 {clean.aborted}")
assert clean.text() == "你好，世界" and clean.text().count("你好") == 1

resume = Client()
for s, t in FIRST:
    resume.recv("m1", s, t)
resume.recv("m1", 5, "界")            # 断点续传: 只发缺失 seq
print(f"[3] 断点续传: {resume.text()!r} (只补 seq=5, 无重复)")
assert resume.text() == "你好，世界" and len(resume.parts) == 5

# 计费账: 两次生成都要计费, 重试成本 = 已产出 + 重生成
first_tokens, retry_tokens = 4, 5
print(f"[4] 计费: 首次 {first_tokens} + 重试 {retry_tokens} = "
      f"{first_tokens + retry_tokens} tokens, 是单次成功的 "
      f"{(first_tokens + retry_tokens) / retry_tokens:.2f}x")
assert first_tokens + retry_tokens > retry_tokens
print("    → 实测 体验可以替换, 成本不能撤销; 重试预算必须单独记账")
```

**追问一**：客户端按 `seq` 去重就能解决同 id 重发吗？—— 只能解决"重复内容"，解决不了"内容不一致"：同 id 重试时模型重新生成，seq=5 之后的文本可能与第一次不同，客户端按 seq 覆盖会得到"前 4 个 chunk 来自第一次、后面来自第二次"的拼接，语义可能断裂（比如前半句说"是"，后半句说"不是"）。所以**同 id 只应允许"原样重放"**（服务端缓存已发 chunk），一旦要重新生成就必须换 id。协议上要区分 `replay`（同 id、同内容、幂等）与 `regenerate`（新 id、新内容），不能混用。

**追问二**：网关为什么不能无条件重试流式请求？—— 因为"请求是否已经开始写出响应"决定了重试是否可见：如果第一个字节还没发给客户端，重试是透明的（客户端无感）；一旦写出一部分，重试就会造成重复或拼接。网关要维护"已提交（committed）"标记——写出 header/首字节后不可重试，只能把错误作为流内事件传给客户端，由客户端决定"重试/重新生成"。这也是 HTTP 语义里"幂等方法"的延伸：GET 可以重试，已经开始返回 body 的流式 POST 不能当作幂等。

## 背诵要点

- 流式输出不可撤回；同 id 重发会让客户端 append 出重复前缀，必须靠 `seq` 去重或直接禁止。
- 三种收场：同 id 原样重放（replay，内容必须一致）、新 id + abort（regenerate，客户端替换）、断点续传（按 last_seq 补发，需服务端保留状态）。
- 网关只可重试"尚未写出首字节"的请求；已提交的流只能发错误事件；重试的 token 双份计费，需单独预算。

## 复盘追问

- 用户看到"您好您好"，你怎么判断是网关重试还是客户端 append 逻辑错？（看两条流的 message_id 是否相同、seq 是否重复；同 id 重复 seq 即协议层缺去重）
- 断点续传为什么经常会退化成"重新生成"？（LLM 无状态，服务端没保留 KV/已生成 token；多数 API 不支持真续传，只能换 id 重来）
