### Q7605 · MCP 协议版本演进与能力协商迁移

难度：P6 ｜ 标签：MCP / 协议演进 / 版本演进

**问**：平台上接了二十多个 MCP server（自家 + 第三方），MCP 协议从 2024-11 版演进到 2025-06 版（新增 elicitation、resource indicator、OAuth 资源服务器语义、结构化工具输出等），升级期间怎么保证新旧 server/client 混用不炸？能力协商机制怎么用？

**答**：
- **结论**：MCP 的版本协商机制：initialize 握手时双方各自声明 `protocolVersion`，按"服务器版本优先"回退到双方都支持的最近版本——这意味着客户端必须实现多版本兼容层，而不是只支持最新版。升级破坏点集中在：① 传输层——STDIO 到 Streamable HTTP 的迁移（2025-03 起弃用 HTTP+SSE 双端点），远程 server 全部要换传输实现，老客户端只讲 SSE 会连不上；② 能力声明——elicitation（server 向用户请求补充输入）等新能力客户端不支持时要正确降级（返回 method not found 而不是崩溃）；③ 工具输出——结构化 outputSchema 出现后，依赖纯文本解析的旧客户端拿到结构化内容块要能忽略不认识的块；④ 鉴权——OAuth 资源服务器语义引入后，token audience 校验变严，旧 token 在新 server 上可能直接 401。
- **取舍**：兼容策略两极：客户端做多版本协商（工程量大、通用性强）vs 平台统一 pin 协议版本（简单、吃不到新能力）。自建平台建议：server 侧跟随最新（官方 SDK 同步升级便宜），客户端实现"协商 + 能力探测 + 降级"三层，把"不认识的能力"当默认降级而不是报错——协议演进的本质是"新能力可选、旧能力不破"。
- **实战**：步骤：① 盘点全部 server 的协议版本与传输方式，建兼容矩阵；② 客户端 initialize 协商结果落日志（版本分布是升级进度仪表盘）；③ 对不支持的新能力做显式降级测试（elicitation 不支持时工具应返回可读错误而非挂起）；④ 复盘项：第三方 server 升级走灰度接入池，新版本 server 先进影子池跑一周再进正式池。

```python
# MCP 版本协商与能力降级模拟（纯标准库）
# 基线：Python 3.9+

SUPPORTED_VERSIONS = ["2025-06-18", "2025-03-26", "2024-11-05"]


def negotiate(server_version: str, client_versions: list[str]) -> str | None:
    """MCP 语义：服务器版本优先，回退到双方都支持的最近版本"""
    common = [v for v in client_versions if v == server_version]
    if common:
        return server_version
    # 双方支持集的交集，取 server 支持序列中最新的
    return None if server_version not in SUPPORTED_VERSIONS else (
        next((v for v in SUPPORTED_VERSIONS
              if v == server_version and v in client_versions), None))


def handle_capability(client_caps: dict, server_wants: str) -> str:
    """客户端不支持的新能力 -> 显式降级而非崩溃"""
    if client_caps.get(server_wants) is True:
        return "OK"
    return f"DEGRADE: 客户端不支持 {server_wants}，返回 method-not-found 语义"


def main() -> None:
    # 老客户端只讲 2024-11，server 是 2025-06：协商失败 -> 拒绝连接并提示
    r = negotiate("2025-06-18", ["2024-11-05"])
    assert r is None
    print("协商失败 -> 拒绝连接（需升级客户端或 server 降级发布）")
    # 客户端支持多版本：命中 server 版本
    assert negotiate("2025-06-18", SUPPORTED_VERSIONS) == "2025-06-18"
    # elicitation 降级
    assert handle_capability({"elicitation": False}, "elicitation").startswith("DEGRADE")
    assert handle_capability({"elicitation": True}, "elicitation") == "OK"
    print("OK")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么能力协商要"客户端显式降级"而不是"server 探测后不用新能力"？
→ 一句话提示：server 无法预知所有客户端形态，把选择权交给客户端（initialize 时声明能力集）才能让新旧客户端同一 server 共存；server 端探测会造成隐式行为差异，排障困难。

**追问 2**：STDIO 本地 server 和远程 Streamable HTTP server 的运维差异是什么？
→ 一句话提示：STDIO 进程生命周期绑定客户端（简单、无鉴权、不可共享），远程 server 需要鉴权（OAuth 资源服务器语义）、水平扩展与速率限制；平台化部署基本收敛到远程 HTTP + 本地敏感数据 server 走 STDIO 的混合形态。

## 背诵要点
- 版本协商：initialize 双方声明 protocolVersion，服务器版本优先、回退取交集；客户端须实现多版本兼容。
- 新能力（elicitation/结构化输出/OAuth 资源服务器）客户端不支持时显式降级（method-not-found 语义），不崩溃。
- 传输层迁移：HTTP+SSE 双端点 → Streamable HTTP；兼容矩阵 + 协商版本日志 + 影子池灰度是升级三件套。

## 复盘追问
- 为什么第三方 MCP server 要进影子池而不是直接升级？提示：第三方行为不可控（工具语义变化、输出格式漂移），影子池用真实流量对比新旧输出差异，一周无异常再切，爆炸半径被隔离。
- 工具输出结构化（outputSchema）对旧客户端意味着什么？提示：内容块类型扩展了（structured content + JSON），旧客户端按"忽略不认识的块"处理不会崩，但可能拿不到结构化数据退化为纯文本——客户端要显式声明支持集避免这种静默降级。
