### Q7793 · 中文查询搜不到英文语料：跨语言检索的召回断层与翻译扩展

难度：P6 ｜ 标签：跨语言检索、多语言嵌入、查询翻译、术语词典、召回断层、语料语言分布

基线：Python 3.12；用词集重叠模拟向量相似度，复现"中文 query 召回为零"的跨语断层，实现查询翻译扩展与术语词典增强，全标准库实跑。

**问**：知识库一半是英文文档（API 手册、上游依赖文档），用户全是中文提问。线上"未命中率"明显偏高：用户问"怎么配置重试"，对应英文文档《Retry Configuration Guide》就在库里却召回不出来。跨语言检索的断层出在哪几层？查询翻译扩展（把中文 query 译成英文再搜）的收益与噪声怎么权衡？要不要为了跨语把整库换多语言嵌入模型？

**答**：

- **结论**：断层有三层：① **嵌入空间断层**——单语嵌入模型（中文BERT系/英文BERT系）把中英文映射到几乎不相交的语义空间，中文 query 的向量与英文文档的向量余弦相似度天然低，不管文档多相关都排在后面，这是最底层的断层；② **词汇断层**——即便嵌入模型有部分跨语能力，领域术语（中文业务名 ↔ 英文配置项）没有对齐："重试"对 "retry/backoff" 的映射是术语级的，通用嵌入对齐不了专有名词，召回的是"泛相关"而非"术语命中"；③ **分词与形态断层**——英文的词形变化（retries/retried）与中文无空格分词，在 BM25 类词法检索里直接漏配。解法按成本递增：**查询翻译扩展**（query 离线/实时译成多语言变体，每个变体独立检索后合并，成本是 N 倍检索但不动库）、**术语词典增强**（业务词典把"重试"映射到 retry/backoff，拼进 query 变体，成本最低、对领域断层最有效）、**换多语言嵌入模型**（multilingual 系模型一个空间对齐多语，一劳永逸但代价是全库重嵌入 Q2303 + 单语精度可能回退）。
- **取舍**：翻译扩展的噪声账：译文质量决定扩展质量——翻译错的 query 会召回不相关文档，**合并策略必须是"原查询优先 + 扩展变体降权"**（RRF 融合里原查询的排名权重高），并且扩展变体的 top-k 取小一些（扩 2 个变体、各取前 10），别让噪声变体的大池子淹没原查询；词典增强几乎零成本但对覆盖敏感——词典没收录的术语依然断层，需要从"未命中 query 聚类"里滚动补词（Q2580 query 日志聚类的副产品）；换多语言嵌入的决策不是"跨语性能"单指标：单语召回精度回退 1~2 个点是常见代价，若线上 90% 流量是单语，为 10% 的跨语流量做全库重嵌入不划算——**先用翻译扩展+词典把跨语断层补到可接受，跨语流量占比持续上升（或翻译延迟不可接受）再换模型**。还有一个常被忽略的点：语料侧也可以做文章——重要英文文档补中文摘要/双语标题，入库时打语言标签（语言标注的过滤检索 Q1209），让"用户语言优先 + 跨语兜底"成为检索策略而不是全靠模型对齐。
- **实战**：① 诊断先行：把未命中 query 抽样人工分类——"库里其实有（跨语断层）"还是"库里真没有（覆盖缺口）"，前者才值得做跨语优化，别把覆盖缺口当跨语问题修；② 翻译扩展的延迟预算：实时翻译一次 100~300ms，加进检索链路前先测 P99；预算紧的用词典增强起步（纯查表零延迟）；③ 融合参数显式化：原查询权重、变体数量、变体 top-k 都做成配置并做回归集（Q1212 golden-set）验证，防止调参不可复现；④ 监控按语言分桶：检索未命中率按 query 语言分别统计——跨语断层被修好后"中文 query 未命中率"曲线应显著下降，这条曲线就是跨语优化的验收指标。

```python
"""Q7793 跨语言检索断层: 词集重叠模拟相似度 + 翻译扩展与词典增强。"""

DOCS = {
    "d1": "Retry Configuration Guide: set max_retries, backoff and timeout",
    "d2": "Logging Best Practices: structured logs and levels",
    "d3": "重试机制配置说明：最大重试次数、退避策略与超时",
    "d4": "数据导入导出流程与常见问题",
}
QUERY_ZH = "怎么配置重试次数和退避"

TERM_DICT = {"重试": "retry retries", "退避": "backoff", "配置": "configuration config"}
TRANSLATE = {"怎么配置重试次数和退避": "how to configure retry count and backoff"}


def tokens(text: str) -> set[str]:
    """极简分词: 英文按空格小写, 中文按字(模拟无词法检索的断层)."""
    out: set[str] = set()
    for w in text.split():
        if w.isascii():
            out.add(w.lower().strip(",.:"))
        else:
            out.update(w)
    return out


def sim(a: set[str], b: set[str]) -> float:
    """词集重叠相似度(模拟嵌入对齐能力: 中文字符与英文词几乎不相交)."""
    if not a or not b:
        return 0.0
    return len(a & b) / len(a | b)


def search(query: str, k: int = 2) -> list[tuple[str, float]]:
    scored = sorted(((d, sim(tokens(query), tokens(t))) for d, t in DOCS.items()),
                    key=lambda x: -x[1])
    return scored[:k]


def expand(query: str) -> list[str]:
    """查询翻译扩展 + 术语词典增强, 原查询排首位."""
    en = TRANSLATE.get(query)
    dict_enh = " ".join(TERM_DICT.get(w, "") for w in query if w in TERM_DICT)
    return [query] + [v for v in (en, dict_enh) if v]


def fused_search(query: str, k: int = 2, variant_k: int = 3) -> list[str]:
    """原查询优先 + 变体独立检索合并(简化 RRF: 分数加权)."""
    merged: dict[str, float] = {}
    for i, q in enumerate(expand(query)):
        w = 1.0 if i == 0 else 0.6          # 原查询优先, 变体降权
        for d, s in search(q, k=variant_k):
            merged[d] = merged.get(d, 0.0) + w * s
    return [d for d, _ in sorted(merged.items(), key=lambda x: -x[1])[:k]]


if __name__ == "__main__":
    base = search(QUERY_ZH)
    print(f"原中文查询直接检索: {base}  <- 英文文档 d1 榜上无名(断层复现)")
    print(f"扩展变体: {expand(QUERY_ZH)}")
    fused = fused_search(QUERY_ZH)
    print(f"翻译扩展+词典融合后: {fused}  <- d1 进入前列")
    top_score = sim(tokens(QUERY_ZH), tokens(DOCS[fused[0]])) if fused else 0.0
    hit = "d1" in fused and fused[0] in ("d1", "d3")
    print(f"校验: 无扩展断层复现 + 扩展后跨语文档命中 -> {'通过' if hit else '异常'}")
    print("结论：断层三层=嵌入空间/术语词汇/分词形态; 先翻译扩展+词典低成本低风险,")
    print("      原查询优先变体降权防噪声, 跨语流量占比升了再考虑换多语言嵌入")
```

**追问一**：翻译扩展引入的噪声怎么度量与控制？译错的 query 召回了不相关文档，怎么在融合层把它压下去？

→ 解析：噪声度量与控制分三步：① **离线度量**：用 golden-set 量化"扩展 vs 不扩展"的双向账——跨语命中提升多少（收益），单语场景的 top-k 精度下降多少（噪声代价），两个数都摆出来才决定扩展开关与权重；噪声的来源要拆开看：译文语义错（"退避"译成 "avoidance"）召回漂移文档、译文多义（"重试"可译 retry/re-attempt）召回多条分支——语义错靠提升翻译质量或词典锁死（领域术语不走通用翻译），多义靠多变体各自检索后 RRF 合并（多义不合并成一个错误变体，而是变成多个弱变体，相关性排序自然分流）；② **融合层压制**：扩展变体降权只是第一步，更强的手段是**命中后验证**——跨语变体召回的文档，用词典/术语表检查"文档是否真的包含 query 的核心术语"，不含的降级到候选尾部（术语级验证比向量相似度更硬），以及 top-k 收紧（变体只取前 3~5，不让噪声池撑大候选窗，Q7791 rerank 候选窗的同族账）；③ **运行时监控**：分语言统计"由扩展变体贡献的最终命中占比"与"扩展命中后的用户点击/采纳率"——若扩展命中的采纳率显著低于原查询命中，说明扩展在送噪声，权重该降。总原则：**翻译扩展是把"检索问题"换成"翻译质量 + 融合治理"问题，收益是可量化提升的跨语召回，代价是必须建立的噪声护栏——只看收益不看噪声的扩展，会在单语主流量上悄悄变差。**

**追问二**：团队决定换多语言嵌入模型做一劳永逸的对齐，这个决策的完整成本清单是什么？怎么验证新模型没把单语召回做坏？

→ 解析：换嵌入模型的真实成本远超"重嵌入一次"：① **直接成本**：全库重嵌入的算力与时间（Q2303 重嵌入队列与灰度切换的账）、双库并行期的存储双倍、嵌入调用单价变化；② **隐性成本**：阈值重标定——新旧模型的相似度分布完全不同，语义边界阈值（Q2579 扫参选 F1）必须全量重扫，直接复用旧阈值会出现"全部高分"或"全部低分"；rerank/下游依赖相似度绝对值的逻辑全部重标；评测基线作废重跑；③ **回归验证**：单语精度守护是关键验收——用"单语 golden-set（原查询 → 期望文档）+ 跨语 golden-set"双集对比新旧模型，单语 top-k 精度回退超过容忍线（如 1 个点）就要评估损失 vs 跨语收益，而不是只看"跨语能搜到了"的演示效果；④ **灰度策略**：双库并行（旧模型库 + 新模型库同查双写）按流量灰度切读，检索质量指标（命中率/采纳率）分语言分桶对比，异常即回切——灰度期是发现"特定类别文档在新模型下召回塌陷"的唯一窗口；⑤ **运维约束**：嵌入维度变化影响向量库索引（换模型常换维度），分片与内存账（Q7545）重算。决策建议：**换模型是"检索基建重做"级别的工程，先跑完单语回归验证（最容易翻车的点）再做投入决策；翻译扩展+词典是可灰度可回滚的渐进路线，两者不互斥——先渐进路线止血，跨语流量与维护成本证明换模型的必要性后再立项。**

## 背诵要点
- 跨语断层三层：嵌入空间断层（单语模型空间近乎不相交）→ 术语词汇断层（业务词 ↔ 英文配置项无对齐）→ 分词形态断层（retries/retried、中文无空格）；诊断先分清"库里有但召回不到"与"库里真没有"。
- 低成本路线：术语词典增强（纯查表零延迟）+ 查询翻译扩展（N 倍检索），融合必须"原查询优先 + 变体降权 + 变体 top-k 收小（3~5）"，否则译文噪声淹没原查询。
- 换多语言嵌入属于"检索基建重做"：全库重嵌入 + 阈值全量重标 + 单语/跨语双 golden-set 回归（单语回退容忍约 1 个点）+ 双库并行灰度切读，先跑单语回归再立项。

## 复盘追问
- 动手做跨语优化之前必须先做哪个判断？（抽样未命中的 query 分两类："库里有但召回不到"才是跨语断层，"库里真没有"是覆盖缺口——把覆盖缺口当跨语问题修，白做一轮还有副作用）
- 翻译扩展上线后盯哪两件事防止"单语流量悄悄变差"？（变体降权 + 变体 top-k 收小；按语言分桶看未命中率与"扩展贡献命中的采纳率"，采纳率显著低于原查询命中就说明在送噪声）
