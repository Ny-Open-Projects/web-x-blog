### Q7612 · 大上下文请求体与代理/网关 body 上限的容量账

难度：P6 ｜ 标签：容量规划 / 网关 / 上下文

**问**：Agent 支持上传文档做 RAG 后，部分用户把长会话 + 全文粘贴进来，请求体到了 8-20MB。部分用户收到 413 Request Entity Too Large，另一些用户请求"莫名 502"。上下文预算（token）明明没超，为什么 HTTP 层先炸了？body 上限的容量账怎么建？

**答**：
- **结论**：token 窗口和 HTTP body 是**两个独立预算**：模型侧按 token 计费/校验，链路侧每个节点有自己的 body 上限与超时——Nginx `client_max_body_size` 默认 1MB、云 LB 8-32MB 不等、某些 API 网关默认 4-10MB、上游模型 API 自身也有请求体限制。故障形态：超过某层上限 → 413（这层明确拒绝）；更隐蔽的是"接近上限 + 大 body 慢传输"触发代理的 `client_body_timeout`/上游 `proxy_read_timeout` → 502/504；以及大 body 反复重试时网关缓冲全量请求（内存放大 = body × 并发）。20MB 会话上下文的链路账要逐节点核对，任何一层都是静默炸弹。
- **取舍**：设计选项：① **客户端瘦身**：大文档不进消息体——走文件上传 + 附件引用（对象存储 + RAG 检索），消息体只带引用与少量引用片段，这把 body 从 20MB 压到 KB 级，是根治；② 链路对齐：确需大 body 的路径，逐层显式调高上限（client_max_body_size / LB 配置 / 网关配额）并对齐超时（`body_timeout ≥ 传输时间 P99`）；③ 分片传输：超长上下文走多次请求累积（会话状态服务端化），单请求控制在 MB 级；④ 监控：body 大小分布 + 413/超时计数按路由分桶，P99 body 接近任一层上限即告警。预算公式：`单请求 body 预算 = min(各层上限) × 0.8`，留水位给 base64 膨胀（图片/文件 base64 后体积 ×1.33）与 JSON 转义膨胀。
- **实战**：容量账步骤：① 盘点链路节点及各自 body 上限/超时（LB→网关→应用→上游模型 API）；② 采样真实 body 大小分布，找 > 预算的请求特征（粘贴全文/多图 base64）；③ 大 body 改附件引用架构；④ 压测各层 413/超时边界，写成配置基线进 IaC；⑤ 复盘项：网关错误码看板按 413/499/502 分桶，body P99 水位线告警。

```python
# 链路 body 上限盘点与单请求预算（标准库模拟）
# 基线：Python 3.9+；真实配置来自 Nginx/云 LB/网关清单

from dataclasses import dataclass


@dataclass
class LinkNode:
    name: str
    body_limit_mb: float
    body_timeout_s: float


def body_budget(nodes: list[LinkNode], transfer_p99_s: float) -> tuple[float, list[str]]:
    """预算 = min(各层上限) × 0.8；同时校验每层超时 >= 传输 P99"""
    limit = min(n.body_limit_mb for n in nodes)
    issues = [f"{n.name}: body_timeout {n.body_timeout_s}s < 传输 P99 {transfer_p99_s}s"
              for n in nodes if n.body_timeout_s < transfer_p99_s]
    return limit * 0.8, issues


def payload_size_mb(text_chars: int, images_b64: int = 0) -> float:
    """JSON 转义膨胀 ~1.1×；base64 图片每张按 2MB 原图 ×1.33"""
    json_bytes = text_chars * 3 * 1.1        # 中文 UTF-8 3 字节
    img_bytes = images_b64 * 2 * 1024**2 * 4 / 3
    return (json_bytes + img_bytes) / 1024**2


def main() -> None:
    chain = [
        LinkNode("cloud-lb", body_limit_mb=32, body_timeout_s=60),
        LinkNode("api-gateway", body_limit_mb=8, body_timeout_s=30),
        LinkNode("nginx-ingress", body_limit_mb=1, body_timeout_s=10),   # 事故层：默认 1MB
        LinkNode("model-api", body_limit_mb=64, body_timeout_s=600),
    ]
    # 场景：长会话 + 3 张 base64 图 ≈ 9MB
    size = payload_size_mb(text_chars=200_000, images_b64=3)
    assert 8 < size < 12
    print(f"请求体 {size:.1f}MB → nginx 1MB 上限直接 413，gateway 8MB 也超")

    budget, issues = body_budget(chain, transfer_p99_s=25)
    assert budget == 0.8 and issues, "瓶颈层是 nginx(1MB) 且超时不足"
    for i in issues:
        print("链路隐患:", i)

    # 根治：附件引用后 body 回到 KB 级
    slim = payload_size_mb(text_chars=2_000, images_b64=0)
    assert slim < 0.1
    print(f"附件引用改造后 {slim*1024:.0f}KB，预算内")
    print("OK: body 预算 = min(各层上限)×0.8，超时逐层对齐；大文档走引用不走消息体")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"502 莫名出现"往往比 413 更难查？
→ 一句话提示：413 是明确拒绝（错误码直指 body），502/504 是代理与上游间的超时/连接问题（body 传输慢、上游提前断、缓冲满）——成因多样且日志分散在各层，需要端到端 trace 才能归因。

**追问 2**：base64 内嵌图片为什么是 body 账的重灾区？
→ 一句话提示：base64 是 4/3 膨胀 + JSON 转义再放大，一张 2MB 图变 2.7MB 文本；多模态输入的正确姿势是文件引用（URL/上传 ID），模型侧按需拉取，消息体保持轻量（呼应 Q7596 多模态预处理）。

## 背诵要点
- token 窗口与 HTTP body 是两个独立预算：链路每层（LB/网关/ingress/上游 API）都有上限与超时，单请求预算 = min(各层上限) × 0.8。
- 413 = 上限超；502/504 = body 慢传输触发超时——大 body 问题的根治是附件引用（对象存储 + RAG），消息体 KB 级。
- base64 内嵌是重灾区（×1.33 再 ×1.1 转义），多模态走文件引用；body P99 水位与 413/超时计数按路由分桶监控。

## 复盘追问
- 怎么把"链路 body 上限"变成版本化资产？提示：各层配置进 IaC 并由脚本定期核对实际生效值（配置漂移检测），链路清单作为架构文档的一部分随部署变更同步更新。
- 会话状态服务端化（分片累积上下文）引入什么新问题？提示：服务端会话存储的一致性与 TTL 管理、并发修改冲突（呼应 Q7552）、以及断点续传语义；换来的是单请求 body 可控与重试成本低。
