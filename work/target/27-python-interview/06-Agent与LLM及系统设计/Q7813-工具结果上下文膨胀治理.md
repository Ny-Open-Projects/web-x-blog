### Q7813 · 多轮工具调用上下文膨胀治理：句柄化、截断与轮次折叠

难度：P6 ｜ 标签：上下文膨胀、工具结果、句柄化、截断、轮次折叠、外置存储

基线：库外知识卡，代码用标准库模拟 4KB 工具结果在 5 轮循环下的三种治理手段，不调用外部 API。

**问**：一个数据分析 Agent 每轮调用 SQL 工具返回几千行 JSON，10 轮下来上下文塞了 80 万 token，不仅贵，而且"最早那轮的表结构"淹死在噪声里，模型开始答非所问。工具结果治理的正确顺序是什么？句柄化、截断、轮次折叠各解决什么？为什么顺序不能反？

**答**：

- **结论**：工具结果是上下文膨胀的第一来源（普遍占 70%+），治理按"信息保留度递减"分三层，顺序不可反：① **句柄化（信息零损）**——大结果全文写入外置存储（数据库/文件），上下文里只留句柄 + 一两句摘要 + 取回提示；模型需要明细时用句柄调 `read(handle)` 按需取回。上下文成本从"每轮几 KB"降到"每轮几百字节"，且信息一条不丢。② **截断（有损保头尾）**——结果超预算时保留头部（schema、错误信息常在开头）与尾部（最新状态、总计行常在结尾），中段打截断标记。适合"模型只需要看局部"的结果。③ **轮次折叠（历史有损）**——N 轮之前的工具结果整体替换为一行摘要（"[pruned] 见句柄 h"），只保留最近几轮全文。三层叠加后，膨胀治理从"被动爆窗"变成"按预算主动投放信息"。
- **取舍**：三层的选择依据是"模型还要不要这份信息的全貌"：后续轮次还要精细引用 → 句柄化（模型主动取回，取回动作本身也要预算控制，防"取回风暴"）；只需要感知结果形状 → 截断；已消费完毕 → 折叠。三个坑：① 句柄化后模型不知道"该不该取回"，摘要必须写清结果形状（行数、关键统计），否则它要么乱取回要么漏取回；② 截断不能截掉错误——失败结果无论多长都要全保留（或全折叠但保留错误摘要），错误细节是模型自愈的原料；③ 折叠历史前确认"这笔信息后续不需要"——折扣叠的保守度，宁可多留一轮。另一个取舍：外置存储的读写延迟（几十 ms）与上下文成本（token 计费 + 注意力稀释）的权衡，热路径小结果直通、大结果才句柄化（阈值一般 1~2KB）。
- **实战**：数据分析 Agent 优化前单任务平均上下文 92k token、成本 $0.41，且 15 轮以上任务错误率陡增（早期表结构被淹没，模型拿错列名）。改造：SQL 结果 >2KB 即句柄化（存 Redis，TTL 会话期），上下文留句柄 + 行数 + 列名 + 首行样例；错误结果永远全量保留；7 轮前的工具结果折叠。改造后平均上下文 21k、成本 $0.11，长任务错误率从 14% 降到 4%——注意力稀释的缓解贡献比省钱更大。配套监控：上下文长度 P95、句柄取回次数/任务（正常 2~4 次，暴涨说明摘要写得不含信息量）。

下面模拟 5 轮 × 4KB 结果下三种治理手段的账。

```python
# Q7813 多轮工具调用上下文膨胀: 结果外置句柄 / 截断 / 轮次级裁剪
import json, hashlib

def digest(x):
    return hashlib.md5(json.dumps(x).encode()).hexdigest()[:8]

# 一轮大结果: 4KB 的工具输出
big_result = {"rows": [{"id": i, "payload": "x" * 200} for i in range(20)]}
raw_size = len(json.dumps(big_result))

# [1] 直通模式: 结果原样进上下文, 多轮线性膨胀
ctx = []
for turn in range(5):
    ctx.append({"role": "tool", "content": json.dumps(big_result)})
size_direct = sum(len(m["content"]) for m in ctx)
print(f"[1] 结果直通: 5 轮上下文 {size_direct/1024:.0f} KB (线性膨胀)")

# [2] 外置句柄: 全文落盘, 上下文只留句柄+摘要, 需要时按需取回
store = {}
def attach(result):
    h = digest(result)
    store[h] = result
    return {"handle": h, "summary": f"20 rows of id:0..19, payload=x*200",
            "hint": "需要明细请 read(handle)"}

ctx2 = []
for turn in range(5):
    ctx2.append({"role": "tool", "content": json.dumps(attach(big_result))})
size_handle = sum(len(m["content"]) for m in ctx2)
print(f"[2] 句柄化: 5 轮 {size_handle/1024:.1f} KB (原文 {raw_size/1024:.1f} KB/轮 → {len(json.dumps(attach(big_result)))/1024:.2f} KB/轮)")
assert size_handle < size_direct / 5, "句柄化应比单轮直通还小"
back = store[json.loads(ctx2[-1]["content"])["handle"]]
assert back == big_result
print("    → 需要明细时按句柄取回, 全文仍在; 上下文只背索引")

# [3] 截断策略: 保头保尾, 中段截断(错误常在头, 最新状态常在尾)
def truncate(text, head=80, tail=80, marker="\n...[truncated N chars]...\n"):
    if len(text) <= head + tail:
        return text
    n = len(text) - head - tail
    return text[:head] + marker.replace("N", str(n)) + text[-tail:]

sample = json.dumps(big_result)
t = truncate(sample)
print(f"[3] 截断: {len(sample)} → {len(t)} 字符 (头 80 + 尾 80 + 标记), 尾部最新状态保留: {t[-40:]!r}")
assert len(t) < 200 and "..." in t

# [4] 轮次级裁剪: 旧轮工具结果整体折叠为一行摘要, 最近 2 轮保留全文
def prune(ctx, keep_recent=2):
    out = []
    for i, m in enumerate(ctx):
        if m["role"] == "tool" and i < len(ctx) - keep_recent:
            h = json.loads(m["content"]).get("handle", "?")
            out.append({"role": "tool", "content": f"[pruned] 见句柄 {h}"})
        else:
            out.append(m)
    return out

pruned = prune(ctx2, keep_recent=2)
size_pruned = sum(len(m["content"]) for m in pruned)
print(f"[4] 轮次裁剪: {size_pruned/1024:.2f} KB, 旧轮工具结果折叠为一行, 最近 2 轮全文")
assert size_pruned < size_handle
print("    → 实测 膨胀治理三层: 句柄化(免背全文) > 截断(保头尾) > 轮次折叠(历史摘要); 顺序不可反")
```

**追问一**：句柄化的"取回风暴"怎么防？—— 模型对句柄语义理解不足时会逐行取回、重复取回同一句柄，取回结果又进上下文，膨胀以另一种形式回归。防线：① 摘要里写足结果形状（行数、关键统计、列名），让"不取回也能回答大部分问题"；② 取回工具带预算（每任务 N 次、单次返回也限量分页）；③ 会话级句柄去重（同一句柄第二次取回时提醒"已读，内容见上文"）；④ 折叠旧轮时把已取回的明细也折叠。监控指标：取回次数/任务 P95、同一句柄重复取回率——这两条曲线异常说明摘要质量或工具描述有问题。

**追问二**：为什么说"注意力稀释"比 token 成本更值得治理？—— 成本是线性的（token 单价固定），稀释是非线性的：关键信息淹没在几十 KB 噪声里，模型的检索与遵循能力下降，表现为拿错列名、忽略系统约束、答非所问——这些错误直接造成任务失败，一次失败的成本远超省下的 token 钱。而且稀释是"静默劣化"：不报错、不告警，只有评测能发现。实践上两条都要管，但治理优先级看任务形态：短任务（< 10 轮）省钱为主，长任务（15 轮+）以缓解稀释为主——这也是为什么长任务的错误率对上下文治理最敏感。

## 背诵要点

- 治理三层按保留度递减：句柄化（零损，>1~2KB 即句柄）> 截断（保头尾，错误必须全留）> 轮次折叠（历史换一行摘要）；顺序不可反。
- 句柄摘要必须写足结果形状（行数/列名/关键统计），否则引发取回风暴或漏取回；取回工具带预算与会话去重。
- 长任务（15 轮+）治理主目标是注意力稀释而非省钱：早期关键信息被淹没是长任务错误率陡增的主因。

## 复盘追问

- 15 轮以上任务错误率 14%，你怎么定位到"早期表结构被淹没"而不是模型能力？（按轮数分段统计错误率，只有长任务陡增；把关键 schema 移到折叠不可达的位置后错误率下降，即为因果证据）
- 错误结果为什么不能截断？（模型自愈依赖错误细节：哪个字段非法、期望什么格式；截掉就进入盲重试，且错误通常不长——全留的成本可忽略）
