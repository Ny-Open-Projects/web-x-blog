### Q7545 · 容量规划：5000 万条 1536 维向量要多少内存？分几片？

> 难度:★★★★ | 标签:容量规划, 向量检索, HNSW

**问**：RAG 语料库预计 5000 万条、1536 维向量，选型时怎么算内存账？为什么原始向量 (5000 万×1536×4B≈300GB) 与实际内存占用差好几倍？HNSW 索引的内存放大怎么估？量化压缩与分片数怎么在容量账里权衡？

**答**：结论：内存账 = **原始向量 + 索引结构（HNSW 邻接表）+ 元数据 + 运行时余量**，HNSW 的 M×2×8B/节点邻接表在高维场景让总占用达到原始向量的 1.5-2 倍；5000 万条 FP32 全量内存方案要 500GB+，通常不可行，工程答案三选一：**标量量化（int8 省 4 倍）、索引外置/磁盘型（内存留索引、向量走 mmap/磁盘）、按租户/时间分片分库**。分片数按单分片内存上限（QPS 与内存双约束）推算，与 Redis 分片规划同构。

机理与实战：
- **账目拆解**（每节点）：向量本体 N×dim×bytes；HNSW 邻接表 ≈ N×(M×2)×4B（层级偏移另计，M=16 时约 128B/节点）；ID 与元数据映射（几百 B/条）；查询时的图遍历缓存。5000 万×1536 维：FP32 本体 300GB、int8 量化 75GB、邻接表约 8-12GB、元数据视 schema 10-50GB。
- **量化取舍**：int8/PQ 量化省内存但召回率下降（int8 通常掉 1-3%，PQ 视参数 5-15%）——必须用自家评测集测召回，不能信厂商宣传；混合方案"量化候选 + FP32 精排 top-K"用少量内存换回精度，是成本/精度曲线的甜点。
- **分片规划**：单分片内存上限（如 32GB，含索引与查询余量）→ int8 方案 5000 万条需 2-3 片；但 QPS 约束可能要求更多分片（单分片检索 CPU 上限）。分片按哈希分片（均匀）还是按租户路由（隔离+成本分账）要在容量阶段定，后期改分片键成本极高。
- **增长预留**：语料年增长（如 50%/年）× 增量索引的临时内存（构建 HNSW 时的 buffer 可到单分片 30%）→ 容量按 2 年视角采购，避免一年后 reshard。

```python
# 基线:Python 3.10+;纯标准库,向量库内存账估算与分片数推算
from __future__ import annotations
from dataclasses import dataclass
import math


@dataclass
class VectorWorkload:
    rows: int
    dim: int
    bytes_per_component: float = 4.0   # FP32;int8=1.0
    hnsw_m: int = 16                   # 每节点邻接数
    meta_bytes_per_row: int = 300      # 元数据/ID 映射
    growth_years: float = 2.0
    annual_growth: float = 0.5         # 年增长 50%


def memory_gb(w: VectorWorkload, replicas: int = 1) -> dict:
    raw = w.rows * w.dim * w.bytes_per_component / 2**30
    adjacency = w.rows * w.hnsw_m * 2 * 4 / 2**30       # M*2 邻接 × 4B 偏移
    meta = w.rows * w.meta_bytes_per_row / 2**30
    growth = (1 + w.annual_growth) ** w.growth_years
    total = (raw + adjacency + meta) * growth * replicas
    return {"向量本体GB": round(raw, 1), "HNSW邻接GB": round(adjacency, 1),
            "元数据GB": round(meta, 1), "增长系数": growth,
            "总内存GB": round(total, 1)}


def shard_plan(total_gb: float, shard_cap_gb: float = 32,
               qps_shards_needed: int = 1) -> dict:
    by_mem = math.ceil(total_gb / shard_cap_gb)
    shards = max(by_mem, qps_shards_needed)
    return {"按内存": by_mem, "建议分片": shards,
            "含副本实例": shards * 2}


def demo() -> None:
    w32 = VectorWorkload(rows=50_000_000, dim=1536)
    m32 = memory_gb(w32)
    w8 = VectorWorkload(rows=50_000_000, dim=1536, bytes_per_component=1.0)
    m8 = memory_gb(w8)
    print(f"FP32 方案: {m32}")
    print(f"int8 量化: {m8} (省 {1 - m8['总内存GB'] / m32['总内存GB']:.0%})")
    assert m8["总内存GB"] < m32["总内存GB"] * 0.3   # 本体省 4 倍
    assert m8["总内存GB"] > 100                      # 仍需百 GB 级:不是"很小"
    plan = shard_plan(m8["总内存GB"], shard_cap_gb=48)
    print(f"分片规划: {plan}")
    assert plan["按内存"] == math.ceil(m8["总内存GB"] / 48)
    # 增长敏感:不预留 2 年增长会一年内 reshard
    w8_no_growth = VectorWorkload(rows=50_000_000, dim=1536,
                                  bytes_per_component=1.0, growth_years=0, annual_growth=0)
    assert memory_gb(w8_no_growth)["总内存GB"] < m8["总内存GB"]
    print("内存账=本体+邻接表+元数据+增长;量化需用自家评测集验证召回 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：HNSW 的 M 参数怎么影响内存与召回的权衡？
答：M 是每个节点的邻接数，M↑ 召回率↑ 但邻接表内存线性↑（M=16→32 翻倍）、构建时间↑、查询遍历可能略快。工程默认 M=16-32；内存紧张时先降 M 再考虑量化之外的方案，因为 M 降档的召回损失通常比 int8 量化小——但同样要评测集说话，两个旋钮（M、量化）要联合调参。

**追问二**：为什么"磁盘向量索引"（mmap/DiskANN 类）是中等规模的最优解？
答：5000 万条以内、QPS 要求不高（<500）的场景，全内存的成本曲线陡（百 GB 内存节点很贵），而 mmap/DiskANN 把向量本体放磁盘、内存只留邻接表与热页缓存，内存需求降一个数量级，用 SSD 随机读延迟（百微秒级）换内存费（省 60-80%）；代价是 P99 延迟抖动与需要更大的 page cache 调优。规模再往上（亿级）就要 IVF-PQ 类极致压缩或真正的分布式引擎——容量账决定选型边界。

## 背诵要点
- 向量内存账 = 本体（N×dim×bytes）+ HNSW 邻接表（≈N×M×2×4B）+ 元数据 + 2 年增长系数；全量是原始向量的 1.5-2 倍。
- 量化省内存必有召回代价（int8 掉 1-3%、PQ 5-15%），用自家评测集验证；甜点方案 = 量化候选 + FP32 精排 top-K。
- 分片 = max(内存约束, QPS 约束)，分片键（哈希 vs 租户路由）在容量阶段定死；中等规模优选 mmap/DiskANN 磁盘索引换内存费。

## 复盘追问
- 上线三个月内存打满 OOM，但语料只增长 10%，泄漏还是估算错？（提示：增量索引构建 buffer（可达单分片 30%）、删除导致的图碎片不回收、page cache 被算进进程 RSS 都会让实际占用超过稳态估算；OOM 复盘要区分"账错"与"运行时膨胀"，容量账要含构建期峰值）
- 为什么按租户路由的分片在"大租户"出现后会失衡，怎么补？（提示：哈希分片假设均匀，租户路由假设租户规模相近；大租户要二次拆分（租户内哈希）或给大租户独立分片组——分片策略设计期就要问"最大的 1% 租户占多少数据"）
