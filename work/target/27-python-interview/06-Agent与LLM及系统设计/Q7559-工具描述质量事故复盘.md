### Q7559 · 工具描述质量的事故复盘与描述契约化

难度：P6 | 标签：工具设计、选型准确率、描述契约、回归评测

**问**：用户问"报销流程是什么"，Agent 却去搜了互联网，把博客文章当制度回答。两个搜索工具的描述都写着"搜索信息"——为什么工具描述的措辞质量能决定 Agent 的对错？描述怎么"契约化"并进回归？

**答**：
- **结论**：模型选工具的唯一依据是工具名 + 描述（以及少量历史调用），描述含糊等于让模型在两个一样的东西里猜——本例修复前选型准确率 0.50，内部制度问题被送去互联网搜索。修复靠描述契约四要素：功能定义（做什么）、适用边界（什么问题找我）、明确的不适用场景（什么问题别找我、该用谁）、参数说明。修复后准确率 1.00。关键动作是把"描述"当成代码一样发布：发布前跑"问题→期望工具"固定集回归，工具改名视为破坏性变更——描述的 diff 没过回归不许上线。
- **取舍**：描述里写"不适用场景 + 替代工具"是最有效的一句——负向约束比正向罗列更能拉开工具间的边界；但描述也不能写成说明书（token 成本与模型注意力有限），经验是 2-3 句话覆盖四要素。工具家族命名要有taxonomy（search_web/search_docs 而不是 search/search_v2），名字本身是模型看到的第一个信号。
- **实战**：落地清单：① 工具注册表新增"描述契约"字段与 owner；② 黄金集：每工具 ≥10 条"该用/不该用"问题，发布必跑；③ 上线后收集"选错工具"的用户负反馈，回填黄金集——描述的回归集跟事故一起生长。

```python
"""工具描述质量事故：模糊描述误导模型选错工具与描述契约化。"""

TOOLS = {
    # 事故前的描述：两把锤子长得一样，模型只能靠名字猜
    "search_web":  {"desc": "搜索信息"},
    "search_docs": {"desc": "搜索信息"},
}
TOOLS_AFTER = {
    "search_web":  {"desc": "搜索互联网公开信息。适用：外部资讯、新闻、通用知识。"
                            "不适用：公司内部制度/文档（用 search_docs）"},
    "search_docs": {"desc": "检索公司内部知识库与制度文档。适用：内部政策、产品手册、"
                            "流程规范。不适用：互联网公开信息（用 search_web）"},
}

def bigrams(s: str) -> set[str]:
    return {s[i:i + 2] for i in range(len(s) - 1)}

def model_picks_tool(question: str, registry: dict) -> str:
    """极简选型模拟：按问题与描述的字符二元组重合度打分（真实场景由模型完成）。"""
    q = bigrams(question)
    best, best_score = None, -1.0
    for name, t in registry.items():
        score = len(q & bigrams(t["desc"])) / max(len(q), 1)
        if score > best_score:
            best, best_score = name, score
    return best

GOLDEN = [
    ("报销流程是什么？", "search_docs"),      # 内部制度
    ("最近 AI 行业有什么新闻？", "search_web"),  # 互联网资讯
]

def eval_selection(registry: dict) -> float:
    hits = sum(model_picks_tool(q, registry) == exp for q, exp in GOLDEN)
    return hits / len(GOLDEN)

print(f"模糊描述的选型准确率 = {eval_selection(TOOLS):.2f}"
      f"（内部制度问题被搜到互联网上，答案张冠李戴）")
print(f"描述契约化后准确率   = {eval_selection(TOOLS_AFTER):.2f}")
print("描述契约四要素：功能定义 / 适用边界 / 明确的不适用场景（含替代工具）/ 参数说明；"
      "发布前跑'问题->期望工具'固定集回归，工具改名=破坏性变更")
```

**追问链**：
1. 追问一层：为什么"不适用场景 + 替代工具"比"功能罗列"更有效？——选型本质是排除法：模型在候选里比相对适配度，"不适用"直接划掉了竞品的主场；只写功能的两个工具在模型的嵌入空间里高度相似，等于没有区分信号。负向约束让边界显式化，这是工具家族设计的通用规律。
2. 追问二层：描述改了之后"固定集回归过了"但线上还是选错，差在哪？——固定集覆盖不了真实问题的分布（用户问法千奇百怪）；补两件事：线上负反馈回流（选错的 case 进黄金集）与描述的 embedding 相似度检查（工具描述之间余弦过高 = 区分度不足，提示改写）。

**背诵要点**：
1. 模型选工具只看名字与描述：描述含糊 = 让模型猜，选型准确率掉一半。
2. 描述契约四要素：功能定义 / 适用边界 / 不适用场景（含替代工具）/ 参数说明。
3. 描述当代码发布：黄金集"问题→期望工具"回归必跑，改名是破坏性变更。

**复盘追问**：
1. 为什么这类事故在"工具一多"之后集中爆发？（两三个工具时模型靠参数差异也能蒙对；工具超过 5 个、功能相近的家族出现后，描述边界成为唯一区分信号——描述债是随工具数量指数恶化的）
2. 复盘时怎么区分"描述问题"和"模型能力问题"？（把选型做成离线可复现：同一批问题、同一注册表、只换描述或只换模型——描述换了分数变化则描述债，模型换了才变化则能力问题）
