### Q7816 · 会话摘要与原文对齐：轮次锚点、实体对账与失真检测

难度：P6 ｜ 标签：会话摘要、上下文压缩、轮次锚点、实体对账、失真检测、溯源

基线：库外知识卡，代码用标准库模拟带锚点摘要与实体对账，不调用外部 API。

**问**：长对话塞不下，把前 10 轮摘要成 3 句话继续聊。之后用户问"刚改的那个订单是哪单？"——摘要里根本没有订单号，模型只好瞎答。会话摘要怎么设计才能既压缩又可溯源？摘要与原文的"对账"怎么做？摘要幻觉（把 1001 写成 2001）怎么被发现？

**答**：

- **结论**：朴素摘要的两大缺陷是**无锚点**与**无校验**。修法：① **带轮次锚点的摘要**——每条摘要绑定它覆盖的轮次区间 `(span: (1,2), text: "...")`，用户追问"刚改的订单"时按锚点回查原文（原文不丢，只是移出上下文，句柄/索引仍在）；摘要文本里尽量保留关键实体（订单号、人名、日期），实体就是天然的追问钩子。② **实体对账**——摘要声称的每个实体（数字、专名）必须能在对应原文里找到，找不到即标记失真；这是检测摘要幻觉的廉价确定性手段（正则提取数字 + 实体白名单比对，实测能抓住"1001→2001"这类致命错误）。③ **摘要后的一致性动作**——摘要替换原文后，先跑一遍对账再放行；失真条目回退为"保留原文"或要求重新摘要。三条合起来：摘要不是有损压缩的终点，而是"压缩 + 索引 + 校验"三件套。
- **取舍**：摘要的激进程度按追问概率定：业务对话（订单、工单）追问实体细节的概率极高，摘要必须保留关键实体且锚点完备；闲聊开场白可以激进压缩甚至丢弃。谁来做摘要也有取舍：LLM 摘要流畅但会幻觉（必须配对账），规则摘要（抽取关键句）零幻觉但生硬——生产常用 LLM 摘要 + 规则对账的混合。另一个关键取舍：**摘要进上下文后原文还在不在**——原文全丢则追问细节必答错；正确姿势是原文进外置存储（如 Q7813 的句柄），摘要里带锚点句柄，追问时取回对应轮次。成本上摘要本身一次 LLM 调用（200~500 token 输出），换来后续每轮省几千 token，长会话净赚；短会话（<10 轮）不值得摘要。
- **实战**：客服会话摘要上线两周后出现一类事故：用户说"刚才改的仓是哪个订单来着"，模型回答了错误订单号——溯源发现摘要把订单 1001 写成了 2001（幻觉），且原文已从上下文丢弃，模型无从对证。修复三件：摘要条目全部带轮次锚点 + 关键实体强制保留（订单号/金额/日期不许省略）；每次摘要跑实体对账，失真即重摘要或回退保留原文；原文按轮次存档，摘要挂句柄，追问实体细节时按锚点取回原文段落回答。上线后此类事故归零，摘要导致的追问失败率从 9% 降到 1.2%。规范沉淀：**摘要里的任何数字与专名都必须可回溯到原文，这是不可协商的对账纪律**。

下面模拟带锚点摘要、溯源与实体对账的完整链路。

```python
# Q7816 会话摘要与原文对齐: 摘要溯源 / 对账校验 / 失真检测
import json, re, hashlib

TURNS = [
    {"t": 1, "role": "user", "text": "我要把订单 1001 从北京仓改发上海仓"},
    {"t": 2, "role": "assistant", "text": "已提交改仓请求, 预计 2 小时生效"},
    {"t": 3, "role": "user", "text": "另外把发票抬头改成 XX 科技"},
    {"t": 4, "role": "assistant", "text": "发票抬头已更新为 XX 科技"},
    {"t": 5, "role": "user", "text": "算了, 发票保持原样"},
    {"t": 6, "role": "assistant", "text": "已取消发票修改, 保留原抬头"},
]

# [1] 朴素摘要: 每 2 轮压成一句, 摘要本身不含轮次定位
def naive_summary(turns):
    out = []
    for i in range(0, len(turns), 2):
        chunk = turns[i:i + 2]
        text = "; ".join(t["text"][:12] for t in chunk)
        out.append(text)
    return out

naive = naive_summary(TURNS)
print(f"[1] 朴素摘要: {naive}")
print("    → 没有轮次锚点: 用户问『刚改的仓是哪单?』时摘要里无法溯源")

# [2] 带锚点摘要: 每条摘要绑定轮次区间 + 关键实体, 可回查原文
def anchored_summary(turns):
    out = []
    for i in range(0, len(turns), 2):
        chunk = turns[i:i + 2]
        text = "; ".join(t["text"][:12] for t in chunk)
        out.append({"span": (chunk[0]["t"], chunk[-1]["t"]), "text": text})
    return out

anchored = anchored_summary(TURNS)
for a in anchored:
    print(f"[2] 轮次 {a['span']}: {a['text']}")
assert anchored[0]["span"] == (1, 2)

def lookup(anchored, turns, turn_no):
    for a in anchored:
        if a["span"][0] <= turn_no <= a["span"][1]:
            origin = [t for t in turns if a["span"][0] <= t["t"] <= a["span"][1]]
            return a["text"], [o["text"] for o in origin]
    return None, None

txt, origin = lookup(anchored, TURNS, 1)
print(f"[2b] 溯源轮次 1 → 摘要 {txt!r} ← 原文 {origin}")
assert origin == [TURNS[0]["text"], TURNS[1]["text"]]

# [3] 对账校验: 摘要声称的事实必须在原文出现, 否则标 [失真] (数字与实体都要查)
ENTITIES = {"1001": "订单号", "上海仓": "改仓目标", "XX 科技": "发票抬头"}
def audit(summary_items, turns):
    full = " ".join(t["text"] for t in turns)
    issues = []
    for a in summary_items:
        for tok in re.findall(r"\d+", a["text"]):        # 摘要里的数字必须存在于原文
            if tok not in full:
                issues.append((a["span"], tok))
        for ent in ENTITIES:
            if ent in a["text"] and ent not in full:
                issues.append((a["span"], ent))
    return issues

assert audit(anchored, TURNS) == []
print("[3] 对账: 摘要中的实体全部能在对应原文找到 → 无失真")

# [4] 失真实例: 摘要生成时把 1001 写成 2001 (幻觉), 对账立即抓出
bad = [{"span": (1, 2), "text": "把订单 2001 改发上海仓"}]
issues = audit(bad, TURNS)
print(f"[4] 失真检测: 幻觉实体 2001 → {issues}")
assert issues == [((1, 2), "2001")]
print("    → 实测 摘要必须带轮次锚点+实体对账; 没有对账的摘要是不可信输入, 幻觉会随会话滚动放大")
```

**追问一**：摘要与 Q1137 那种"摘要轮转窗口"的关系是什么？两者怎么配合？—— 摘要轮转是**触发机制**（到阈值就压缩最旧轮次），带锚点摘要 + 对账是**压缩的质量机制**（压出来的东西可信可溯源）。两者不冲突：轮转窗口负责"何时压、压多少"，锚点+对账负责"压得对不对"。工程上一个常见漏配是：轮转触发了，但压出来的摘要没跑对账就顶进上下文——幻觉摘要进入后续所有轮次，污染随会话滚动放大。所以轮转的执行链必须是"摘要生成 → 对账 → 失真处理（重摘/回退）→ 才允许替换原文"，校验不通过不许上桌。

**追问二**：对账能抓哪些幻觉、抓不住哪些？—— 能抓的：**实体级幻觉**——数字（订单号/金额/日期）、专名（人名/产品名）在摘要与原文间不一致，这是正则+白名单就能确定性检测的，也是危害最大的类别（错单号=业务事故）。抓不住的：**语义级失真**——"用户同意了方案 A"原文其实是"用户说再考虑一下"（倾向被夸大）、因果倒装、态度反转。这类要靠 LLM 复核（用另一模型对照原文检查摘要忠实度，NLI 方向）或人工抽查。所以对账是"便宜确定性 + 高价值实体"的第一道，LLM 忠实度校验是"贵但语义级"的第二道，关键场景两道都要；非关键场景第一道 + 抽样第二道。

## 背诵要点

- 摘要三件套：轮次锚点（span 可回查）+ 关键实体强制保留（订单号/金额/日期）+ 实体对账（数字与专名必须在原文可查）。
- 对账抓实体级幻觉（确定性、正则即可），语义级失真（倾向夸大/因果倒装）要 LLM 忠实度复核或人工抽查。
- 摘要替换原文前必须过对账；原文进外置存储挂句柄，追问细节时按锚点取回——摘要不是压缩终点，是"压缩+索引+校验"。

## 复盘追问

- "刚改的仓是哪单"答错订单号，事故链上哪一环是根因？（摘要幻觉 1001→2001 且原文已丢——两层叠加；只修摘要不回原文，追问细节仍会失败，所以锚点+句柄取回是根治）
- 为什么摘要里的实体"不许省略"而其他内容可压？（实体是后续追问的钩子与业务对账的锚，丢实体 = 丢可回答性；形容词、过程描述才是可压缩部分）
