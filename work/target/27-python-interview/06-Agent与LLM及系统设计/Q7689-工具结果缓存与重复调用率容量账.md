### Q7689 · Agent 一晚上把同一个接口打了 8 万次：工具结果缓存的账

难度：P6 ｜ 标签：容量规划、工具缓存、去重
基线：Agent 工具执行层（function calling 循环）；本地 TTL 缓存（cachetools 或自建）。

**问**：上线"批量客户查询"Agent 后，下游订单接口夜间被打 8 万次，其中 92% 是重复参数的重复查询——Agent 在多轮推理里反复调同一工具。重复调用从哪来？工具结果缓存的容量账（TTL、命中率、失效）怎么算？

**答**：**结论**：重复调用三个来源：① **推理循环特性**——模型对同一事实反复取证（尤其上下文被压缩后"忘了"之前查过）；② **并行分支重复**——多个子任务独立查同一客户；③ **重试放大**——上层重试把整轮工具序列重放。缓存账四项：**键设计**（工具名+规范化参数的哈希，参数要排序/钳制后归一化）、**TTL**（按数据新鲜度分级：客户资料 1h、库存 30s、汇率 5min）、**命中率预算**（重复率 92% 时命中率理论上限就是 92%，缓存把它变成 1 次真实调用）、**失效语义**（写路径要主动失效：Agent 更新订单后必须 evict，否则下一轮读到旧数据自我污染）。额外收益：缓存命中的工具结果**不消耗供应商 token**（直接回填结果），8 万次 × 每次 2k token 的调用上下文是隐形成本的大头。

**取舍**：缓存的代价是**一致性风险**：Agent 决策建立在可能过期的数据上，且用户无感知——分级 TTL 必须"按数据的新鲜度容忍度"定，宁可命中率低也不能让资金/库存类数据过期。多实例部署时本地缓存各自为政，命中率打折且失效不同步——共享缓存（Redis）代价是网络往返与另一个组件，工具结果是纯读小对象，通常值得共享。另一个取舍：缓存查询结果 vs 缓存"工具调用的 LLM 请求指纹"——后者连模型调用都省，但键要含完整消息上下文，命中窗口窄。

**实战**：重复率与缓存收益账（标准库）：

```python
# 工具结果缓存账：重复率 -> 命中率 -> 降载与 token 节省
import hashlib, json, time
from collections import Counter

calls = [("get_customer", {"id": i % 400}) for i in range(80_000)]  # 夜间调用
freq = Counter((name, tuple(sorted(p.items()))) for name, p in calls)
unique = len(freq)
repeat_rate = 1 - unique / len(calls)
print(f"夜间 {len(calls):,} 次调用，唯一参数 {unique} -> 重复率 {repeat_rate*100:.0f}%")

TTL_BY_FRESHNESS = {"get_customer": 3600, "get_stock": 30}

def cache_key(tool: str, params: dict) -> str:
    norm = json.dumps({"t": tool, "p": params}, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(norm.encode()).hexdigest()[:16]

class ToolCache:
    def __init__(self):
        self._store: dict[str, tuple[float, str]] = {}

    def get(self, tool, params):
        k = cache_key(tool, params)
        hit = self._store.get(k)
        if hit and time.monotonic() - hit[0] < TTL_BY_FRESHNESS.get(tool, 60):
            return hit[1]
        return None

    def put(self, tool, params, value):
        self._store[cache_key(tool, params)] = (time.monotonic(), value)

    def evict(self, tool, params):        # 写路径主动失效
        self._store.pop(cache_key(tool, params), None)

cache = ToolCache()
real_calls, token_saved = 0, 0
for name, params in calls:
    v = cache.get(name, params)
    if v is None:
        real_calls += 1
        cache.put(name, params, f"result:{params['id']}")
    else:
        token_saved += 2000               # 命中省掉一次完整调用上下文
print(f"缓存后真实调用 {real_calls:,} 次（降载 {(1-real_calls/len(calls))*100:.0f}%）")
print(f"节省供应商 token 约 {token_saved:,} -> 折 {(token_saved*2.5/1e6)*30:.0f} 元/月输入费")

# 写路径失效演示
cache.evict("get_customer", {"id": 7})
print("订单更新后 evict(id=7) -> 下一轮推理强制读到新数据")
```

**追问 1**：为什么"上层重试重放工具序列"也该被缓存吸收？什么情况不该？
提示：重试时参数与结果大概率仍有效（幂等读），缓存直接回填省整轮重放；但非幂等写工具（下单/扣款）绝不能靠缓存吸收重试——要幂等键而不是缓存。

**追问 2**：TTL 按新鲜度分级怎么和数据 Owner 对齐？
提示：从数据源的更新频率与业务容忍度推导（资料类小时级、交易类秒级），写进工具注册表的元数据；没有 Owner 认可的 TTL 值默认取保守小值。

**追问 3**：共享缓存（Redis）与本地缓存怎么选？
提示：工具结果小、读多写少、多实例部署 → 共享缓存命中率高且失效同步；单实例或超高频调用（网络往返占比高）→ 本地 + 短 TTL。失效广播成本要计入。

## 背诵要点
1. 重复调用三来源：推理循环反复取证、并行分支重复查询、重试重放；重复率即命中率理论上限。
2. 缓存账四项：参数归一化键（排序+钳制）、TTL 按新鲜度分级（资料 1h/库存 30s）、写路径主动 evict 防自我污染、命中省供应商 token 是隐形成本大头。
3. 非幂等写工具禁用缓存吸收重试（用幂等键）；多实例部署默认共享缓存（Redis），失效同步是选型第一权重。
