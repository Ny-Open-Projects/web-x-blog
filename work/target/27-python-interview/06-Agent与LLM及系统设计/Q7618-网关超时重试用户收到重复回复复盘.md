### Q7618 · 网关超时重试导致用户收到重复回复事故复盘

难度：P6 ｜ 标签：事故复盘 / 幂等 / LLM 网关

**问**：LLM 网关对上游超时做了自动重试，某天用户投诉"同一条回复收到两遍"：一次是慢到的原始响应、一次是重试的新响应。超时后的"取消"为什么救不了？流式与非流式场景下重复的形态有什么不同？修复的层次怎么排？

**答**：
- **结论**：机理：网关设置 60s 超时，上游模型推理 70s 后正常完成——网关侧已判超时并重试发起第二次请求；第一次请求的推理没有真正取消（超时 ≠ 取消，Q7598 同源：取消要显式传播到上游），两个请求都走完计费并各自把回复写进会话存储 → 用户看到两条。流式场景更隐蔽：第一次连接在 SSE 上吐了一半被网关掐断，客户端已渲染部分内容；重试的完整回复又进来，UI 出现"半截 + 重复全文"。三层根因：① 重试语义错——对**非幂等且不可取消**的长推理请求盲目自动重试；② 取消缺失——超时后没有向上游发取消（断连/Abort），上游继续算、继续计费、继续写存储；③ 入库无幂等——会话存储按"响应到达"追加写入，没有"一个请求最多落一条"的约束。修复层次：① 立即——网关对该类请求关闭自动重试（或只对"明确未发出"的失败重试：连接拒绝/429，不对超时重试）；② 应用侧——每个推理请求带唯一 request_id，会话入库按 request_id 幂等（唯一键），重复到达丢弃；③ 链路侧——超时即向上游传播取消（HTTP: 断开连接/AbortController 语义；SDK: 显式 cancel），并做"取消确认"（上游 acknowledge 后才允许重试）；④ 对账——按 request_id 对账网关计费与会话存储条数，重复写入是常态监控项。
- **取舍**：重试策略矩阵：连接失败/429 → 可自动重试（请求未消耗推理）；5xx 且未开始流式 → 可重试一次（幂等键保护下）；**超时/部分流式已出 → 不可自动重试**，要么等要么让用户显式重发。流式场景的折中：网关对流的"首字节超时"（TTFT）可以重试——此时多半还没开始推理；对"流中途卡死"的重试要带幂等键且先取消旧流。代价权衡：取消传播依赖上游支持（有的推理服务不认断连即取消），拿不到保证时只能靠入库幂等兜底——**幂等键是底线，取消是优化**。
- **实战**：落地：① 网关重试策略按错误类别白名单化（connect/429/5xx-before-first-byte），超时类默认不重试；② SDK 层给每个请求自动注入 request_id 并透传到入库路径；③ 会话存储 unique(request_id) + 写入冲突时 diff 内容（重复且内容不同 = 异常告警）；④ 计费对账 job 每小时跑：同一 request_id 多次计费即告警；⑤ 复盘指标：重复回复率、取消成功率、孤儿计费请求数。

```python
# 网关重试与取消语义模拟：幂等键兜底重复回复
# 基线：Python 3.9+ 标准库；真实场景网关(SDK) + 会话存储唯一键
from dataclasses import dataclass, field


@dataclass
class Inference:
    """上游推理：慢完成且不感知网关超时（除非显式取消）。"""
    latency_s: float
    cancelled: bool = False

    def cancel(self) -> bool:
        self.cancelled = True
        return True  # 假设上游支持断连取消


@dataclass
class SessionStore:
    """会话存储：按 request_id 幂等。"""
    rows: dict[str, str] = field(default_factory=dict)
    dropped: int = 0

    def append(self, request_id: str, content: str) -> bool:
        if request_id in self.rows:
            self.dropped += 1
            return False
        self.rows[request_id] = content
        return True


def gateway_call(inference: Inference, store: SessionStore, rid: str,
                 timeout_s: float, retry_on_timeout: bool) -> list[str]:
    """返回实际入库的响应路径数。"""
    paths: list[str] = []
    timed_out = inference.latency_s > timeout_s
    # 超时且取消成功 -> 上游不再产生响应；否则上游稍后仍完成并入库
    if not (timed_out and inference.cancelled):
        if store.append(rid, "answer"):
            paths.append("original")
    if timed_out and retry_on_timeout and not inference.cancelled:
        if store.append(rid + ":r2", "answer"):
            paths.append("retry")
    return paths


def main() -> None:
    # 事故形态：70s 推理、60s 超时、自动重试 -> 原始(迟到)+重试 都入库
    store = SessionStore()
    out = gateway_call(Inference(70), store, "req-1", 60, retry_on_timeout=True)
    assert len(store.rows) == 2, store.rows
    assert out == ["original", "retry"]
    print(f"事故: 超时自动重试 -> 存储 {len(store.rows)} 条回复（重复）")

    # 修复1: 超时不自动重试 -> 只有一条（迟到但唯一）
    store2 = SessionStore()
    gateway_call(Inference(70), store2, "req-2", 60, retry_on_timeout=False)
    assert len(store2.rows) == 1

    # 修复1b: 超时+取消传播 -> 上游不产生响应，零入库
    store2b = SessionStore()
    inf_c = Inference(70)
    inf_c.cancel()
    assert gateway_call(inf_c, store2b, "req-2b", 60, retry_on_timeout=True) == []
    assert len(store2b.rows) == 0

    # 修复2: 即使重试，入库按 request_id 幂等 -> 重复到达被丢弃
    store3 = SessionStore()
    assert store3.append("req-3", "answer")
    assert not store3.append("req-3", "answer") and store3.dropped == 1
    print("修复: 超时不重试/取消传播 + request_id 唯一键幂等是底线")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"超时后断开连接"不一定能停止上游推理？
→ 一句话提示：取消依赖上游把"客户端断连"翻译成任务取消——多数推理框架能感知断连，但排队中的请求、批处理合并的请求可能继续算完并计费；对账要按 request_id 查"取消确认"而不是假设断连即停。

**追问 2**：流式场景"半截回复"要不要落库？
→ 一句话提示：不落——半截内容既不可续传（模型状态已丢）又会污染会话上下文；正确做法是整条响应原子入库（完成才写），前端渲染未完成的流但不进历史，重试后以新 request_id 的完整回复为准。

## 背诵要点
- 超时 ≠ 取消：网关超时后上游继续推理、继续计费、继续入库；自动重试叠加未取消的旧请求 = 用户收到重复回复。
- 重试白名单：连接失败/429/首字节前 5xx 可自动重试；超时与流中卡死不可自动重试——幂等键是底线，取消传播是优化。
- 会话入库按 request_id 唯一键幂等 + 计费对账（同 id 多次计费告警）；流式半截回复不落库，整条原子写入。

## 复盘追问
- 为什么这个事故在"上游变慢的那天"才爆发？提示：平时推理 < 超时阈值，重试路径从不触发；上游 P99 漂移过阈值后，重试+不取消的组合被成规模激活——阈值型配置是静默耦合。
- 网关重试与 SDK 重试同时存在时会怎样？提示：两层自动重试相乘（网关 2 次 × SDK 3 次 = 最多 6 个请求），且外层对内层重试不可见——重试策略必须收敛到一层，另一层显式关闭。
