### Q7674 · 异步工具回调丢失导致 Agent 挂起：复盘

难度：P6/P7 ｜ 标签：事故复盘、异步、Agent
基线：asyncio 3.9+；回调型工具指"提交任务拿 task_id，结果走 webhook/轮询"的外部系统。

**问**：Agent 调用的某个工具是异步的（提交后等回调），回调丢了之后 Agent 会话永久挂起，用户侧一直转圈。事故链条与修复方案是什么？

**答**：**结论**：挂起的根因是**"等待回调"没有超时与对账**——会话状态停在 WAITING_TOOL，回调丢失（网关丢包、下游任务失败未发回调、消息去重误杀）后无人负责唤醒。事故链条：工具提交成功 → 下游任务失败/回调路由失败 → Agent 状态机无超时 → 会话永久挂起 → 用户重试造成重复任务 → 配额与成本放大。

**取舍**：三种修复的层级：① 每个挂起点加超时（asyncio.wait_for / 状态机 deadline）——必做，但超时后的语义要定义（失败重试？告知用户？）；② **对账扫描（reaper）**——后台任务周期扫描超时的 WAITING 状态，主动向下游查证任务真实状态（回调丢失 ≠ 任务失败，可能是回调丢了任务成了），按查证结果推进状态机；③ 回调改"轮询 + 回调"双通道——回调是优化，轮询是保底。只做 ① 会把"回调丢了但任务成功"误判为失败，造成重复执行副作用（Q7542/Q7598 同源）。

**实战**：状态机设计三要素：每个非终态必须有 deadline 字段；超时处理 = 先查证再定论（查证调用也要超时，查证失败才判失败）；会话挂起率（WAITING 超时数/总会话）作为核心监控。

```python
# 回调型工具的状态机：deadline + 查证后再定论（asyncio 标准库）
import asyncio
import time
from dataclasses import dataclass, field

@dataclass
class PendingTool:
    task_id: str
    deadline: float                    # 绝对时间戳
    state: str = "WAITING"             # WAITING / DONE / FAILED
    result: str | None = None

class ToolReaper:
    """超时扫描：先向下游查证任务真实状态，再决定终态。"""
    def __init__(self, verify):
        self.pending: dict[str, PendingTool] = {}
        self.verify = verify            # async def verify(task_id) -> str|None

    def submit(self, task_id: str, timeout: float = 30):
        self.pending[task_id] = PendingTool(
            task_id=task_id, deadline=time.time() + timeout)

    def on_callback(self, task_id: str, result: str):
        t = self.pending.get(task_id)
        if t:
            t.state, t.result = "DONE", result

    async def sweep(self) -> list[str]:
        now = time.time()
        actions = []
        for tid, t in list(self.pending.items()):
            if t.state != "WAITING":
                continue
            if now < t.deadline:
                continue
            real = await self.verify(tid)          # 查证：回调丢≠任务失败
            if real is not None:
                t.state, t.result = "DONE", real
                actions.append(f"{tid}: 回调丢失但任务成功，查证补单")
            else:
                t.state, t.result = "FAILED", None
                actions.append(f"{tid}: 查证失败 -> FAILED（超时）")
        return actions

# 演示：两个任务，回调都丢了；下游真实状态一个成功一个没跑
fake_downstream = {"t-ok": "job finished", "t-bad": None}

async def verify(task_id: str) -> str | None:
    await asyncio.sleep(0.01)
    return fake_downstream.get(task_id)

async def main():
    reaper = ToolReaper(verify)
    reaper.submit("t-ok", timeout=0.05)
    reaper.submit("t-bad", timeout=0.05)
    await asyncio.sleep(0.1)          # 回调丢失窗口
    for line in await reaper.sweep():
        print(line)
    print("终态:", {k: v.state for k, v in reaper.pending.items()})

asyncio.run(main())
# -> t-ok 被查证补单（避免重复执行副作用），t-bad 判 FAILED

# 会话挂起率监控指标
def hang_rate(waiting: int, total: int) -> float:
    return waiting / total if total else 0.0
print(f"挂起率阈值告警: {hang_rate(3, 100):.1%} -> {'OK' if hang_rate(3,100)<0.02 else '告警'}")
```

**追问 1**：为什么超时后必须先查证再判失败？
提示：回调丢失与任务失败是两个独立事件；直接判失败会触发重试，重复执行已成功的副作用（下单、写库），事故从"挂起"升级成"重复执行"。

**追问 2**：查证调用本身也失败/超时怎么办？
提示：查证失败不能无限重试——设查证重试上限与降级策略（判 FAILED 但留人工复核队列），并把"查证不可用"当作下游系统健康度指标。

**追问 3**：webhook 回调链路如何降低丢回调概率？
提示：回调签名 + 幂等键（下游可安全重发）、回调网关重试队列、以及"回调只是加速器，轮询/查证才是真相源"的架构定位。

## 背诵要点
1. 回调型工具必须配 deadline + 对账扫描（reaper）；挂起根因是"等待无超时、超时无查证"。
2. 超时后先查证下游真实状态再定论——直接判失败会把"回调丢了但成功"变成重复执行副作用。
3. 架构定位：回调是加速器，轮询/查证是真相源；挂起率（超时 WAITING/总会话）是核心监控。
