### Q7679 · 沙箱并发配额与 CPU/内存容量账

难度：P6/P7 ｜ 标签：容量规划、沙箱、Agent
基线：容器化沙箱（cgroup 限额）；与 Q7587（沙箱冷启动成本）、Q7662（常驻与按起分界）互补——本卡算**并发承载**的账。

**问**：Agent 的代码执行沙箱跑在容器里（每个任务一个沙箱），高峰 500 并发任务时宿主机 OOM。沙箱的并发配额怎么算？CPU/内存限额怎么配才不互相拖垮？

**答**：**结论**：沙箱并发账的核心公式：`可承载并发 = min(宿主内存 / 单沙箱内存预算, 宿主 vCPU / 单沙箱 CPU 需求 × 超卖系数)`。内存是硬上限（OOM 即杀进程，无弹性），CPU 是软上限（cgroup 限流只变慢不崩溃），所以**内存按足额预算、CPU 允许适度超卖**（典型 2-3 倍，因为代码执行任务多为间歇性 CPU，且 IO 等待期间不占 CPU）。事故常见根因是只按 CPU 规划并发、内存按平均值算——Python 沙箱的单任务峰值内存（numpy 导入即 ~100MB，pandas 300MB+）是平均值的数倍。

**取舍**：限额的三个参数：`memory limit`（硬顶，按任务类型的 P99 峰值 × 1.3）、`cpu quota`（按均值或 P50，允许排队）、`pids limit`（防 fork 炸弹，常被忽略）。配额模式二选一：**均质配额**（所有沙箱同规格，好算好排）vs **任务分级**（轻任务小沙箱、重任务大沙箱，需要任务分类器）。500 并发重任务场景必须分级，否则为 P99 任务给所有沙箱配大内存，成本翻数倍。

**实战**：容量账用实测分布：对任务类型采样 P50/P95/P99 内存峰值（cgroup memory.peak 或进程 RSS），按类型配额；准入控制 = 内存预算硬闸（可用内存 < 单沙箱预算时排队而不是放行），并监控"排队深度 vs OOM 次数"找平衡点。

```python
# 沙箱并发容量账：内存硬上限 + CPU 超卖（标准库可运行）
from dataclasses import dataclass

@dataclass
class HostCap:
    mem_gb: float
    vcpu: float
    reserved_gb: float = 2.0      # 系统与网关预留

    def usable_mem_gb(self) -> float:
        return self.mem_gb - self.reserved_gb

def sandbox_capacity(
    host: HostCap,
    task_profiles: dict[str, dict],   # {类型: {p99_mem_mb, p50_cpu}}
    mix: dict[str, float],            # 任务类型占比
    cpu_oversell: float = 2.5,
) -> dict:
    # 混合负载的单"标准沙箱"平均内存预算 = Σ(占比 × P99内存) × 1.3 安全系数
    avg_mem_mb = sum(task_profiles[t]["p99_mem_mb"] * mix[t]
                     for t in task_profiles) * 1.3
    mem_cap = int(host.usable_mem_gb() * 1024 / avg_mem_mb)
    avg_cpu = sum(task_profiles[t]["p50_cpu"] * mix[t] for t in task_profiles)
    cpu_cap = int(host.vcpu * cpu_oversell / avg_cpu)
    return {"avg_mem_mb_per_task": round(avg_mem_mb),
            "memory_bound": mem_cap,
            "cpu_bound": cpu_cap,
            "max_concurrency": min(mem_cap, cpu_cap),
            "binding": "内存" if mem_cap <= cpu_cap else "CPU",
            "note": "内存是硬上限（OOM），CPU 超卖只变慢不崩"}

host = HostCap(mem_gb=64, vcpu=32)
profiles = {
    "light":  {"p99_mem_mb": 150, "p50_cpu": 0.2},   # 纯 Python 脚本
    "medium": {"p99_mem_mb": 600, "p50_cpu": 0.8},   # pandas 处理
    "heavy":  {"p99_mem_mb": 2500, "p50_cpu": 2.0},  # numpy 大数组
}
mix = {"light": 0.6, "medium": 0.3, "heavy": 0.1}
cap = sandbox_capacity(host, profiles, mix)
print(cap)
# 内存约束 ~90 并发 < CPU 约束 ~160：内存是瓶颈，按内存准入

# 分级配额对照：heavy 任务单独大沙箱，不打满所有沙箱的预算
def tiered_capacity(host: HostCap, profiles: dict, mix: dict) -> dict:
    out = {}
    for t, p in profiles.items():
        mem = p["p99_mem_mb"] * 1.3
        out[t] = int(host.usable_mem_gb() * 1024 / mem * mix[t])
    return {"分级各类型并发": out,
            "总计": sum(out.values()),
            "对比均质": cap["max_concurrency"]}
print(tiered_capacity(host, profiles, mix))
# 分级后总并发高于均质：重任务不再绑架全量内存预算

# 准入控制：内存预算硬闸，排队优于 OOM
def admit(running_mem_mb: float, incoming_mb: float, host: HostCap) -> bool:
    return running_mem_mb + incoming_mb <= host.usable_mem_gb() * 1024
print("放行 600MB:", admit(58_000, 600, host), "| 排队 instead of OOM:", admit(61_000, 600, host))
```

**追问 1**：为什么 CPU 允许超卖而内存不行？
提示：CPU 超额由 cgroup CFS 限流，任务变慢但不失败（SLA 表现为延迟上升）；内存超额直接 OOM kill，任务是失败不是变慢——所以内存按 P99 × 安全系数足额，CPU 按 P50 超卖。

**追问 2**：`pids limit` 为什么必须设？
提示：沙箱执行的是不可信代码，无 pids 限制时一个 `fork` 循环就能耗尽宿主进程表（影响宿主上所有容器）；连同文件句柄、输出体积配额一起构成沙箱的资源闭环（Q2997 输出配额同源）。

**追问 3**：任务分级需要"任务分类器"，分类错误（重任务被分进轻沙箱）怎么办？
提示：分类错配的表现是 OOM 而不是报错，难以归因；对策是轻沙箱也设 OOM 监控与自动升级重试（失败任务按更大规格重跑一次），并把分类准确率纳入监控——这是分级方案的隐性运维成本。

## 背诵要点
1. 并发公式：min(内存硬上限, vCPU × 超卖系数 / 单任务 CPU)；内存按 P99 峰值 × 1.3 足额，CPU 按 P50 超卖 2-3 倍。
2. Python 沙箱峰值内存远超均值（numpy ~100MB、pandas 300MB+），按平均值配额必 OOM。
3. 重任务占比高时用分级配额（轻/重分规格），配 pids limit 防 fork 炸弹；排队优于 OOM。
