### Q7541 · 事故复盘：供应商一返回 429，所有客户端同时重试把自己锁死

> 难度:★★★★ | 标签:事故复盘, 限流, 重试风暴

**问**：LLM 供应商达到配额返回 429 后，业务系统上百个请求各自按固定 1 秒间隔重试，结果 429 持续不恢复，配额恢复瞬间又被同步洪峰打满。为什么单请求的"正确重试策略"在全局是错的？重试要怎么协调？429 响应里的 Retry-After 与供应商配额维度怎么用？

**答**：结论：单请求视角的"指数退避"在全局视角会退化成**同步重试锁死**——所有请求在同样的错误触发点用同样的退避序列，重试节拍完全同步，形成脉冲式洪峰，永远踩不满配额恢复窗口的正确时机。解法是把重试从"每请求各自为战"升级为**全局协调**：进程内共享的重试预算与全局退避（一个断路器管所有对同一供应商的请求）、抖动打散节拍、尊重 Retry-After 并把它全局化（取响应里的建议时间做全队列统一暂停）。

机理与实战：
- **同步化机制**：429 洪峰是"批量请求同时被拒"造成的，各自退避 1s/2s/4s 后又同时重试——退避没有 jitter 时节拍完全相关。修复第一层是 full jitter（随机 0-退避上限）；第二层是全局配额协调：从 429 响应头读 `x-ratelimit-remaining-*`，在进程内维护令牌桶，请求发出前先看桶，429 时把整个桶的补充速率调低，而不是让每个请求自己碰运气。
- **配额维度**：供应商限流是分维度的（RPM 请求每分钟、TPM token 每分钟、并发数），429 可能是任一维度触发——重试策略必须读取响应体/头里"哪个维度超了"：RPM 超就节流发请求，TPM 超要**裁剪上下文**（重试同样的长 prompt 永远过不去）。
- **风暴防御链**：① 请求级：jitter 退避 + 最多 3 次；② 全局级：共享断路器（429 率超阈值时全队列暂停 Retry-After 时长）；③ 架构级：多供应商路由，429 时切到备用供应商（Q7516 成本路由的降级分支）。
- **复盘要点**：事故里"重试日志淹没监控"是典型次生灾害——重试计数要单独上报并与首试区分，否则错误率指标全是重试噪声。

```python
# 基线:Python 3.10+;纯标准库,全局协调的 429 重试:令牌桶+full jitter+Retry-After 全局暂停
from __future__ import annotations
import random
import time
from collections import deque


class GlobalRetryCoordinator:
    """对同一供应商的所有请求共享的限流协调器。"""

    def __init__(self, rpm_budget: int = 60) -> None:
        self.window: deque[float] = deque()   # 最近请求时刻
        self.rpm_budget = rpm_budget
        self.paused_until = 0.0

    def allow(self, now: float) -> bool:
        if now < self.paused_until:
            return False                       # 全局暂停(Retry-After)
        while self.window and self.window[0] < now - 60:
            self.window.popleft()
        return len(self.window) < self.rpm_budget

    def record_sent(self, now: float) -> None:
        self.window.append(now)

    def on_429(self, now: float, retry_after: float, jitter_frac: float = 0.2) -> float:
        """429 全局化:暂停时长 = Retry-After + 抖动,作用于整个队列。"""
        pause = retry_after * (1 + random.uniform(-jitter_frac, jitter_frac))
        self.paused_until = max(self.paused_until, now + pause)
        return pause


def call_with_retry(prompt_tokens: int, tpm_left: int, coord: GlobalRetryCoordinator,
                    clock: list[float], max_retry: int = 3) -> str:
    if tpm_left < prompt_tokens:
        # TPM 维度超限:重试原样请求永远失败,必须裁剪上下文
        return "trim-context-and-retry"
    for attempt in range(max_retry + 1):
        now = clock[0]
        if not coord.allow(now):
            clock[0] += 0.5
            continue
        coord.record_sent(now)
        return "ok"
    return "gave-up"


def demo() -> None:
    random.seed(11)
    coord = GlobalRetryCoordinator(rpm_budget=5)
    t = [100.0]
    # 第一波 5 个请求打满预算
    for _ in range(5):
        assert call_with_retry(500, 100_000, coord, t) == "ok"
    # 第 6 个触发 429,全局暂停 10s±20%
    pause = coord.on_429(t[0], retry_after=10.0)
    assert 8.0 <= pause <= 12.0
    # 暂停期内所有请求被协调器统一挡住(而不是各自重试)
    sent = sum(coord.allow(tt) for tt in [t[0] + 1, t[0] + 5, t[0] + 9])
    assert sent == 0
    # 暂停结束且滑出 60s 窗口后恢复放行
    assert coord.allow(t[0] + 65)
    # TPM 维度:配额不足时走裁剪路径而非重试
    r = call_with_retry(prompt_tokens=8000, tpm_left=1000, coord=coord, clock=t)
    assert r == "trim-context-and-retry"
    print("429 防御链:请求级 jitter + 全局协调器 + Retry-After 全局化 + TPM 裁剪 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：为什么 TPM 超限时的重试和 RPM 超限时的重试是两种完全不同的动作？
答：RPM 超限是"等一等就能过"，重试有意义；TPM 超限是"这个请求本身太大"，原样重试每次都命中同一上限，是确定性失败——正确动作是裁剪上下文/压缩历史后重试，或直接失败返回给上层降级。重试逻辑必须读 429 的维度信息分类处置，盲目重试会把"不该重试的错误"重试成双倍延迟与双倍账单。

**追问二**：多供应商路由下，429 切换备供应商有什么坑？
答：① 备供应商的上下文格式/工具协议可能不同，切换要过协议适配层，失败率会瞬间升高；② 切换瞬间的在途请求要么放弃要么重放，重放要带幂等键防双计费；③ 备供应商也可能被同一场流量洪峰打爆（如果共享同一个上游），所以降级矩阵要按"供应商独立性"设计，而不是简单的主备。

## 背诵要点
- 429 风暴本质：批量请求同步退避 → 节拍相关 → 脉冲洪峰；修复两层：full jitter 打散 + 全局协调器（共享令牌桶 + Retry-After 全局暂停）。
- 429 分维度处置：RPM 超=等待重试；TPM 超=裁剪上下文（原样重试是确定性失败）；并发超=降低全局并发。
- 重试计数单独上报区分首试，防监控噪声；架构兜底是多供应商路由，切换需协议适配层+幂等键防双计费。

## 复盘追问
- 为什么事故期间"错误率告警"比平时更晚触发？（提示：大量请求处于退避等待中，"在途未失败"不计入错误率，监控看到的是延迟攀升而非错误攀升；重试系统的告警要基于 p99 时延与重试率，而非最终失败率）
- 全局协调器的"全局"边界是什么？跨实例怎么协调？（提示：单实例内存状态只协调自己，50 个实例=50 个独立洪峰源；跨实例协调用 Redis 共享令牌桶或网关统一收口——这就是 LLM 网关存在的核心理由之一）
