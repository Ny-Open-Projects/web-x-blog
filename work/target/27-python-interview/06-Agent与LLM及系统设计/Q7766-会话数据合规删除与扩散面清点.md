### Q7766 · 用户要求删掉所有对话记录：会话数据的合规删除与扩散面清点

难度：P6 ｜ 标签：合规删除、数据保留、GDPR、扩散面、删除证明

基线：Python 3.12；实现删除请求处理器（资产清单驱动）+ 删除执行与证明生成，演示"备份里的删除"靠 TTL 与密钥销毁，全标准库实跑。

**问**：用户（或合规团队）发来请求：删除该用户全部会话数据，并要求**删除证明**。你以为 UPDATE 一张表就完事了——实际上会话数据的副本散落在：主存储、只读副本、向量索引（做过 embedding 的记忆）、缓存、日志、trace、备份、下游数仓。每一处的删除语义都不一样：有的能立刻删，有的只能靠过期，备份根本不该重写。合规删除的工程结构是什么？删除证明怎么出？

**答**：
- **结论**：合规删除是**资产清单驱动的扩散面清点**，不是一条 DELETE。工程结构四步：① **资产清单**：登记该用户数据所在的每一类存储及其删除语义——主库（可即时删）、副本（跟随主库）、向量索引（按用户 id 过滤删除，embedding 密文场景配合密钥销毁，Q7762）、缓存（TTL 短，等过期或主动清）、日志/trace（按保留期自然过期，或重写代价太高只能声明"到期清除"）、备份（**不重写**，靠备份保留期滚动过期 + 加密密钥销毁让历史备份密文永久不可读，Q6763）；② **执行编排**：按清单逐项执行并记录每项的状态（完成/按期清除/密钥销毁）；③ **删除证明**：一份机器可验证的报告——列出资产、动作、时间戳、残余风险声明（备份内的副本将于 X 日随保留期清除，密钥已销毁故不可读）；④ **复核与异议期**：删除后抽样验证（该用户 id 在各存储已不可检索），保留期内的异议窗口允许恢复（误删保护）。原则一句话：**能删的删，删不动的声明清除期限并切断可读性**。
- **取舍**：① 重写备份 vs 密钥销毁：重写 30 天滚动窗口内所有备份的成本与出错率极高，密钥销毁（按用户派生的内容密钥，Q7762）是密码学层面的等效删除——前提是备份真的加密了，明文备份只能靠保留期；② 向量索引的删除滞后：embedding 通常异步生成，删除请求到达时可能有"在途 embedding 任务"还没写入——删除编排要含"取消在途任务 + 清理任务队列"；③ 日志里的删除滞后：结构化日志按保留期（如 30 天）过期是可接受的合规姿态，前提是保留期写进隐私政策并向用户披露；④ 保留义务与删除权的冲突：法定留存（财务、审计）的数据不删，在证明里单独声明法律依据。
- **实战**：① 资产清单代码化（每类存储一个 handler），新存储类型上线时清单评审是门禁——"这个新库能按用户删吗"进设计评审模板；② 删除请求带幂等键，重复提交不重复执行；③ 删除编排的可观测：每项资产的删除耗时与失败率进 SLO，删除卡壳是合规风险；④ 定期演练：每季度抽一个测试账号走全流程删除+证明，验证清单没有漏（与备份恢复演练同级的重要度）。

```python
"""合规删除编排: 资产清单驱动 + 逐项执行 + 删除证明。"""
import datetime as dt
import json


# 资产清单: 存储类型 -> (删除方式, 是否即时, 保留期天)
ASSETS = {
    "primary_db":    ("按用户 id 行删除", True, 0),
    "replica":       ("跟随主库复制", True, 0),
    "vector_index":  ("按 metadata.user_id 过滤删除", True, 0),
    "cache":         ("TTL 自然过期(最长1小时)", False, 0),
    "logs":          ("按保留期自然过期", False, 30),
    "traces":        ("按保留期自然过期", False, 14),
    "backups":       ("不重写: 保留期滚动过期 + 按用户派生密钥销毁", False, 30),
}


def process_deletion(user_id: str, rows_affected: dict[str, int]) -> dict:
    """删除编排: 逐资产执行, 输出证明。返回可 JSON 化的删除证明。"""
    actions, pendings = [], []
    for asset, (method, immediate, retain_days) in ASSETS.items():
        n = rows_affected.get(asset, 0)
        if immediate:
            actions.append({"asset": asset, "action": f"{method} (已删除 {n} 条)",
                            "status": "done", "at": _now().isoformat()})
        else:
            deadline = (_now() + dt.timedelta(days=retain_days)).date().isoformat()
            actions.append({"asset": asset,
                            "action": f"{method} -> 不晚于 {deadline} 清除",
                            "status": "scheduled", "at": _now().isoformat()})
            pendings.append(asset)
    cert = {
        "user_id_hash": __import__("hashlib").sha256(
            user_id.encode()).hexdigest()[:12],
        "executed_at": _now().isoformat(),
        "actions": actions,
        "residual_disclosure": (
            f"备份与日志中的副本将在保留期内清除; "
            f"备份密文因按用户派生密钥已销毁而永久不可读; "
            f"法定留存数据不受本删除影响" if pendings else "全量即时清除"),
    }
    return cert


def _now() -> dt.datetime:
    return dt.datetime(2026, 11, 24, 15, 0)


def verify_deleted(user_id: str, store: dict) -> bool:
    """复核: 各存储按用户检索应为空。"""
    return all(user_id not in v for v in store.values())


if __name__ == "__main__":
    rows = {"primary_db": 312, "replica": 312, "vector_index": 58,
            "cache": 9, "logs": 1200, "traces": 800, "backups": 312}
    cert = process_deletion("user_42", rows)
    print("删除证明:")
    for a in cert["actions"]:
        print(f"  [{a['status']:>9}] {a['asset']}: {a['action']}")
    print(f"\n残余披露: {cert['residual_disclosure']}")

    # 复核: 主存储与向量索引应已不可检索
    stores = {"primary_db": [], "vector_index": [],
              "cache": ["user_42 会话缓存(TTL 中)"]}
    print(f"复核(主库/向量已清, 缓存待过期): "
          f"主库无残留={verify_deleted('user_42', {'primary_db': stores['primary_db']})}, "
          f"缓存暂有={not verify_deleted('user_42', {'cache': stores['cache']})}")

    # 幂等: 重复请求不重复执行
    cert2 = process_deletion("user_42", rows)
    print(f"重复请求: 证明内容一致={json.dumps(cert, sort_keys=True) == json.dumps(cert2, sort_keys=True)}")
    ok = all(a["status"] in ("done", "scheduled") for a in cert["actions"])
    print(f"校验: 每项资产有明确动作与状态 -> {'通过' if ok else '异常'}")
    print("\n结论：合规删除=资产清单驱动+逐项执行+删除证明;")
    print("      备份不重写: 保留期滚动 + 密钥销毁实现密码学等效删除")
```

**追问一**：备份里的数据到底怎么"删"才合规？

→ 解析：业界标准答案分三档。第一档：**可重写备份**（对象存储上的逻辑备份），删除窗口内重新导出并过滤该用户数据——成本高、出错率高（重导出引入新不一致），只在备份频率低、数据量小时用。第二档（主流）：**保留期滚动过期**——备份只保留 30 天，用户数据最迟在 30 天后随备份轮换消失，把这个期限写进隐私政策即是合规的"声明式删除"。第三档（最强）：**密钥销毁**——备份是加密的且密钥按用户派生，销毁该用户的派生密钥后，任何备份里的该用户密文**永久不可读**，等效于删除且立即生效（Q6763 的派生密钥结构在这里变现）。合规审查里最常被挑战的是第二档的"30 天内仍存在"，用第三档 + 第一档的组合回应：窗口期内不可读（密钥没了）、窗口期满物理消失（滚动过期）。前提纪律：备份必须加密——明文备份的删除只有第一档一条路。

**追问二**：删除权与"AI 记忆"的冲突怎么处理？

→ 解析：Agent 的记忆层（用户偏好、历史结论）是最容易漏的扩散面，而且它**不只是存储问题**——记忆影响未来行为。三点处理：① 记忆库纳入资产清单：向量化的记忆条目按用户删除（Q251/Q2292 的记忆分层各层都要清），包括"记忆提取任务"的在途队列（还没写入的也要取消）；② **派生影响**：其他用户的数据里可能引用了该用户的贡献（多人协作场景的共享记忆），删除策略要区分"直接引用"（删）与"统计性影响"（模型的聚合特征里间接存在，声明为不可定点清除，类似统计去标识化的处理）；③ 恢复冲突：Agent 记忆常被缓存到端侧/本地，服务端删除后端侧副本靠下次同步覆盖——删除证明里要声明端侧副本的收敛机制。审查口诀：删除请求的边界不是"会话表"，是"这个用户的行为在系统里留下的一切可关联痕迹"。
