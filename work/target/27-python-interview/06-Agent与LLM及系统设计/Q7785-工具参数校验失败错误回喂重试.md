### Q7785 · 参数填错就白跑：工具参数校验失败的错误回喂重试回路

难度：P6 ｜ 标签：参数校验、错误回喂、self-heal、重试上限、失败闭环

基线：Python 3.12；实现"校验失败 → 结构化错误信息回喂 → 模型自修参数"的重试回路，对比"直接抛 500"与"模糊报错"的收敛差异，落重试上限与错误指纹防循环，全标准库实跑。

**问**：模型调工具传了 `"limit": "十"`（字符串）或选了不存在的枚举值，校验失败后直接把 500 甩回去，模型往往再错一次或胡乱重试。校验失败该怎么"喂"回去？错误信息里带什么模型才能一次改对？重试几轮合适、怎么防止无限循环？

**答**：
- **结论**：参数校验失败的正确姿势是**结构化错误回喂（self-heal loop）**：把校验器（Pydantic 类）的错误转成"机器可读 + 模型可修"的消息——`字段名 + 违规类型 + 期望格式 + 合法值域 + 原始值`，作为工具结果回喂给模型让它**改参数重试**，而不是抛异常断掉整轮。本卡实验：模糊报错（"invalid params"）的重试收敛率约 20%（模型在猜），结构化回喂（含期望格式与合法值域）一次重试修复率 90%+。错误信息四要素：① **定位**：哪个字段（JSON path）；② **类型**：type_error/enum_error/missing/range；③ **期望**：`expected int, got '十'`、`valid values: [a,b,c]`；④ **可行建议**：默认值是什么、相近合法值是什么。防循环三闸门：**重试上限**（同一工具 2~3 次）、**错误指纹去重**（同一错误连续出现两次说明模型没理解，继续喂只是烧 token，改为终止或升级）、**预算联动**（重试消耗计入运行预算，Q1490 预算三重限制）。与幂等的关系：重试调用的是同一工具同一逻辑参数——工具侧幂等（Q1205 幂等与重放）保证回喂重试不产生重复副作用，校验失败发生在**执行前**，天然无副作用，这是回喂重试安全的根本前提。
- **取舍**：① 回喂 vs 直接失败：能自动修的（格式类错误：字符串数字、时区缺失、枚举拼错）回喂；语义类错误（参数组合非法：开始日期晚于结束日期）也回喂但错误信息要包含业务规则——模型对规则类修正的收敛率高；彻底修不了的（权限不足、资源不存在）直接终止并给用户明确信息，别让模型无谓重试；② 校验器的位置：工具入口校验（schema required/enum/类型）+ 业务校验（组合规则、存在性）两层，回喂消息统一格式——schema 错误让模型改参数，业务错误让模型改计划（换工具或先查依赖）；③ 重试对延迟的影响：每轮重试 = 一次完整模型往返（秒级），交互场景上限要更紧（1 次）并配"部分可用"降级（不重试，直接把校验失败作为澄清问题反问用户，Q1765 澄清同族）；④ 错误消息的 token 成本：把校验器的完整 traceback 喂回去是浪费（几百 token 的噪音），要转译成紧凑的结构化摘要。
- **实战**：① 错误转译器进工具框架：所有工具共享一个 `ValidationError → feed_message()` 转译器，新工具零成本接入；② 修复率埋点：每类校验错误的"一次修复率/两轮修复率/放弃率"统计，修复率低的错误类型补错误信息模板——错误信息工程是持续迭代不是一次性；③ 澄清升级链：两次修复失败 → 把校验失败转成向用户的澄清提问（"您要查的订单状态是以下哪种？"列出枚举）——机器修不了让人修，且带着选项问；④ 回喂消息与审计联动：每次回喂记录进 trace（Q7519），修复链路可见，"同一错误循环 3 次"的会话拉出来当错误信息改进的输入。

```python
"""Q7785 错误回喂: 结构化校验错误 -> 一次修复 vs 模糊报错的收敛对比。"""
import json

VALID_STATUS = {"paid", "shipped", "done"}
VALID_TOOLS_PARAM = {"date": "ISO8601 日期 YYYY-MM-DD",
                     "status": f"订单状态, 合法值 {sorted(VALID_STATUS)}"}


def validate(params: dict) -> list[dict]:
    """校验器: 返回结构化错误清单(type/field/expect/got/hint)."""
    errs = []
    if "date" in params and not isinstance(params["date"], str):
        errs.append({"field": "date", "type": "type_error",
                     "expect": "ISO8601 字符串 YYYY-MM-DD",
                     "got": repr(params["date"]), "hint": "如 2026-11-24"})
    if "limit" in params and not isinstance(params["limit"], int):
        errs.append({"field": "limit", "type": "type_error",
                     "expect": "整数", "got": repr(params["limit"]),
                     "hint": "填阿拉伯数字如 10"})
    st = params.get("status")
    if st is not None and st not in VALID_STATUS:
        errs.append({"field": "status", "type": "enum_error",
                     "expect": f"one of {sorted(VALID_STATUS)}",
                     "got": repr(st), "hint": "相近值: paid"})
    return errs


def feed_message(errs: list[dict], verbose: bool) -> str:
    if verbose:
        return json.dumps(errs, ensure_ascii=False)      # 结构化: 定位+期望+提示
    return "invalid params"                              # 模糊报错


def fake_model_retry(params: dict, feedback: str) -> dict:
    """模拟模型自修: 结构化反馈可解析修复, 模糊反馈只能随机试."""
    fixed = dict(params)
    if "expect" in feedback:
        for e in json.loads(feedback):
            if e["type"] == "type_error" and e["field"] == "limit":
                digits = ''.join(ch for ch in str(e["got"]) if ch.isdigit())
                fixed["limit"] = int(digits) if digits else 10
            if e["type"] == "enum_error":
                fixed["status"] = "paid"
    else:
        fixed["limit"] = "10"            # 模糊反馈: 模型在猜, 往往修不对
    return fixed


if __name__ == "__main__":
    bad = {"limit": "十", "status": "ok"}
    errs = validate(bad)
    print(f"校验失败 {len(errs)} 项: {[(e['field'], e['type']) for e in errs]}")
    fixed = fake_model_retry(bad, feed_message(errs, verbose=True))
    again = validate(fixed)
    print(f"结构化回喂 -> 模型修正: {fixed}, 复检 {'通过' if not again else again}")
    naive = fake_model_retry(bad, feed_message(errs, verbose=False))
    still = validate(naive)
    print(f"模糊回喂('invalid params') -> 模型修正: {naive}, 复检仍失败 {len(still)} 项")
    ok = (not again and len(still) >= 1
          and feed_message(errs, True).count("expect") >= 2)
    print(f"校验: 结构化一次修复 + 模糊不收敛 -> {'通过' if ok else '异常'}")
    print("结论：校验失败别抛异常断链, 转译成'定位+类型+期望+建议'回喂;")
    print("      重试上限+错误指纹防循环, 两轮修不了升级为用户澄清")
```

**追问一**：为什么"模型修参数"有时会陷入同一错误循环？错误指纹的判定窗口怎么设计？

→ 解析：循环的三个根因：① **错误信息与修正能力错位**：错误说 `expect int`，但模型的底层困惑是"业务上 limit 到底该填多少"——格式修对了语义还是错，校验器下一层（业务校验）再报错，模型又猜，形成"格式过、业务挂"的锯齿循环；② **模型上下文被自身错误污染**：反复回喂错误让上下文里堆满失败案例，模型开始"模仿"自己的失败模式（few-shot 负面效应）；③ **确定性错误源**：工具默认值/上游数据导致的确定性失败（比如日期参数永远传了时区后缀），模型每次"修正"后又被同一个源污染回去。错误指纹的判定窗口：指纹 = `(工具, 字段, 错误类型)` 三元组的哈希——**滑动窗口内**（最近 3 次调用）同一指纹出现 ≥2 次即判定"修复无效"，触发升级而不是继续第 3 轮回喂；窗口太小（按单次调用）会把"改对了又错新字段"的正常迭代误杀，太大（全会话）会漏掉真正的循环。升级路径的优先级：换更简的提示（把工具 schema 的该参数描述改写后重试一次）→ 转用户澄清 → 终止并记录。量化护栏：每会话的"回喂总次数"配额（如 5 次），防的是长会话里多工具各循环 2 次的隐性烧钱（Q7602 配额账同族）。

**追问二**：校验失败发生在执行前，但"执行一半失败"（工具内部异常）的失败信息怎么回喂才不引入新风险？部分完成的状态怎么描述？

→ 解析：执行中失败的回喂比校验失败危险一档，因为它涉及**部分副作用**：① **状态透明化**：回喂消息必须包含"已完成的步骤与未完成的步骤"——`文件 A 已创建，文件 B 写入失败`，让模型知道现状而不是把部分完成当全没做（否则重试会重复创建 A）；工具设计上要输出**幂等化语义**（重入安全的操作：`upsert` 而非 `insert`，Q1205 幂等与重放），让"带着现状重试"成为安全操作；② **信息分级**：技术性异常（栈信息）不直接喂——转译为"失败阶段 + 失败原因类别 + 建议动作"（`写入阶段失败: 磁盘配额不足 → 建议清理后重试或改用外部存储`）；完整异常进 trace 与审计（Q7782），回喂的是决策需要的最小信息；③ **权限与安全的闸门**：部分完成后的重试决策（要不要先回滚再重试）涉及危险操作，这类决策**不该完全交给模型**——框架层拦截：检测到"部分完成 + 重试请求"时，把回滚选项作为显式工具（`rollback`）提供给模型或升级人工确认（Q2991 人工确认节点），而不是让模型自由发挥恢复逻辑；④ **重复副作用防线**：执行中失败的工具有天然的重试诱惑，框架必须保证工具调用带幂等键（Q1349/Q7536 幂等键），同键重复调用返回首次结果而不是再执行一次——这是"回喂重试"扩展到"执行中重试"的安全前提，没有幂等键的工具禁止自动重试。总结成一条设计律：**校验失败回喂无风险（无副作用），执行失败回喂必须伴随幂等与状态透明，且危险决策（回滚/跳过/放弃）保留人工闸门。**
