### Q7692 · 并发会话串话与状态污染事故复盘

难度：P7 ｜ 标签：事故复盘、会话隔离、并发、状态管理

基线：Python 3.9+；asyncio 会话服务 / FastAPI；多租户 agent 网关。

**问**：用户 A 的对话里突然冒出了用户 B 刚上传的文档内容，另一个用户看到了别人的查询结果。复盘发现是 agent 服务的"会话状态"在并发下串了。什么样的代码写法会导致串话？为什么测试环境测不出来？

**答**：
- **结论**：串话的本质是**共享可变状态跨越了会话边界**，高频写法四种：(1) 模块级 dict/单例缓存会话上下文，key 用了用户 ID 但写入路径漏了 key（先 get 后 set 的竞态）；(2) `contextvars` 用错——在线程池/TaskGroup 里没有正确传播，读到别的任务的值；(3) 全局"当前会话"变量（`global current_session`），asyncio 单线程里两个协程交错执行导致互相覆盖；(4) 对象池/连接池里的对象带着上一个会话的状态没清。测试环境单用户串行执行，永远触发不了竞态，所以测不出来——**并发测试（多会话压测 + 断言隔离性）必须进 CI**。
- **取舍**：会话状态的正确归属是"请求作用域"——用 contextvars（asyncio 友好）或显式传参会话对象，禁止模块级可变单例；跨请求记忆（用户偏好）走显式存储（DB/Redis，key 带租户），与"会话内上下文"分开管理。取舍点是显式传参啰嗦 vs 全局变量隐式出事，agent 编排框架里尤其要选"状态显式"的那类。
- **实战**：复盘整改——(1) 审计所有模块级可变全局，消灭"当前 X"模式；(2) contextvars 写清楚：`ContextVar.set()` 的作用域与任务传播；(3) 加"串话金丝雀"：压测里两个会话注入不同标记串，断言输出不含对方标记；(4) 日志带 session_id 全链路，串话可追溯。

```python
# 演示串话 vs 隔离：全局变量方案 vs contextvars 方案（标准库可运行）。
import asyncio
from contextvars import ContextVar

_session_bad: dict = {}          # 错误示范：全局"当前会话"
_session_good: ContextVar[str] = ContextVar("session", default="-")

async def handle_bad(sid: str, n: int):
    _session_bad["cur"] = sid     # 协程交错：写入后被另一个协程覆盖
    await asyncio.sleep(0.01 * n)
    return _session_bad["cur"]    # 读到的可能不是自己的 sid

async def handle_good(sid: str, n: int):
    _session_good.set(sid)        # contextvars 按任务隔离
    await asyncio.sleep(0.01 * n)
    return _session_good.get()

async def main():
    bad = await asyncio.gather(handle_bad("A", 1), handle_bad("B", 2))
    good = await asyncio.gather(handle_good("A", 1), handle_good("B", 2))
    print("全局变量方案:", bad, "->", "串话!" if bad[0] != "A" else "正常")
    print("contextvars 方案:", good, "->", "隔离OK" if good == ["A", "B"] else "串话!")

if __name__ == "__main__":
    asyncio.run(main())
    # 全局变量方案: ['B', 'B'] -> 串话!（协程交错覆盖）
    # contextvars 方案: ['A', 'B'] -> 隔离OK
```

**追问**：
- 一层：为什么 contextvars 在 asyncio 下能隔离，在线程池里要注意什么？→ 提示：每个 Task 拷贝 context；`run_in_executor` 的线程默认不带 context，要 `ctx.run()` 或用 `asyncio.to_thread`（3.9+ 会传播）。
- 二层：会话内状态很大（长文档）时怎么兼顾隔离与内存？→ 提示：状态外置存储 + context 只放句柄/引用；进程重启可恢复；配合 TTL 清理防泄漏。

**背诵要点**：
1. 串话根因四类：模块级 dict 竞态、contextvars 传播断裂、全局"当前会话"被协程交错覆盖、池化对象残留状态。
2. 正解：会话状态走请求作用域（contextvars/显式传参），跨请求记忆走带租户 key 的存储，两者分开。
3. 单用户测试永远测不出竞态：CI 加多会话压测 + 金丝雀串话断言。

**复盘追问**：
1. 为什么事故用户是"偶发个别人"？提示：竞态依赖交错时序，负载高峰才触发；复盘要能从日志 session_id 还原交错链。
2. 第三方 agent 框架内部有全局状态怎么查？提示：审计依赖源码的全局/单例用法，压测金丝雀兜底，必要时 fork 修复。
