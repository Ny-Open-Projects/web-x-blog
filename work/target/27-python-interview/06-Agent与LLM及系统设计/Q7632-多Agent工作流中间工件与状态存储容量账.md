### Q7632 · 多 Agent 工作流的中间工件（消息/文件/检查点）与状态存储容量账

难度：P6 ｜ 标签：容量规划 / 多 Agent / 状态存储

**问**：一个多 Agent 流水线（规划 → 检索 → 撰写 → 审阅），每步产出的中间结果都落库（消息、检索文档、草稿版本、检查点）。上线两个月，状态库涨到几百 GB，查询变慢，恢复一个旧会话要分钟级。中间工件到底该存什么、存多久？容量账怎么算？

**答**：
- **结论**：先分类。中间工件四类，留存策略完全不同：① **状态检查点**（可恢复性需要）——最新 + 前一版足够，旧检查点只留哈希链引用（Q2021 增量存储同源），体积大头；② **消息与工具调用记录**（审计/回放需要）——全量但转冷，文本 KB 级 × 会话数可控，工具返回的大 payload（网页抓取/文件内容）要截断或存指针；③ **派生工件**（草稿/检索文档块）——可重建的最适合过期删除，保留"重建配方"（参数+输入指针）代替本体；④ **最终产物**——长存。容量账公式：`增速 = 会话数/天 × 每会话(检查点 × 版本数 × 快照体积 + 工具 payload × 条数)`，其中快照体积（整个消息树序列化）常是凶手——每步全量快照让一个 20 步会话膨胀到几十 MB。治理三板斧：快照改增量（只存 diff）、大 payload 出库入对象存储存指针、派生件 TTL（7-30 天）。恢复变慢的根因也是存储结构问题：按会话聚簇（索引按 session_id）+ 冷热分层（30 天内热、之外归档），否则回放要扫全表。
- **取舍**：中间结果"可重建"还是"可回放"？可重建（存配方）省存储但依赖上游存活且耗时；可回放（存本体）恢复秒级但存储线性涨。决策变量是"恢复场景的时效与上游稳定性"：在线会话恢复要秒级（存本体，只留近两版），事故取证/审计可接受小时级（存配方+冷归档）。另一个取舍：审计合规要求可能强制全量留存，此时唯一的账是"分层与压缩"而不是"能不能删"。
- **实战**：① 快照落库前算账：单会话快照体积 > 阈值（如 5MB）自动转增量模式；② 工具 payload > 64KB 截断 + 对象存储指针，指针带过期时间；③ 恢复演练：随机抽 30 天前会话回放，测恢复耗时与完整性（哈希链校验）；④ 存储增速按四类工件分桶监控，哪类暴涨清哪类。

```python
# 四类工件容量账: 快照增量化/payload出库/派生TTL; 增速按类分桶
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class WorkflowStorage:
    sessions_per_day: int
    steps: int
    snapshot_mb: float          # 全量快照单份
    tool_payload_kb: float      # 单条工具返回
    tool_calls: int

    def growth_gb_day_naive(self) -> float:
        snap = self.steps * self.snapshot_mb            # 每步全量快照
        tools = self.tool_calls * self.tool_payload_kb / 1024
        return self.sessions_per_day * (snap + tools) / 1024

    def growth_gb_day_tuned(self) -> float:
        snap = 2 * self.snapshot_mb * 0.15              # 增量: 2 全 + 步级 diff 15%
        tools = self.tool_calls * 0.064                 # >64KB 截断出库
        return self.sessions_per_day * (snap + tools) / 1024


def main() -> None:
    w = WorkflowStorage(sessions_per_day=2000, steps=20,
                        snapshot_mb=1.5, tool_payload_kb=200, tool_calls=8)
    naive = w.growth_gb_day_naive()
    tuned = w.growth_gb_day_tuned()
    assert naive > 58                     # ~60GB/天, 两个月 3.6TB
    assert tuned < 2.0                    # ~1.9GB/天
    assert tuned / naive < 0.05
    print(f"全量快照: {naive:.0f}GB/天 (两个月≈{naive*60:.0f}GB+)")
    print(f"治理后: {tuned:.2f}GB/天 (增量快照+payload出库+派生TTL)")
    print("OK: 快照体积是凶手; 恢复秒级靠按会话聚簇+冷热分层, 不靠全存")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"每步全量快照"的存储成本随步数是平方级而不是线性级？
→ 一句话提示：第 n 步快照包含前 n 步全部消息，Σ(1..n) 的消息体累计 = O(n²) 体积；增量快照只存第 n 步 diff，总量回到 O(n)——步数越深的会话，全量快照模式越不可持续。

**追问 2**：工具返回的大 payload"截断+指针"后，回放时指针失效（对象被生命周期清理）怎么办？
→ 一句话提示：指针记录对象存储版本与哈希，回放校验哈希失败时降级为"载荷缺失占位"并标记该段不可完整回放——回放完整性与存储成本是光谱两端，占位标记让边界诚实可见。

## 背诵要点
- 工件四分法：检查点（最新+前一版）、消息审计（全量转冷）、派生件（TTL/存配方）、最终产物（长存）；容量增速按类分桶监控。
- 全量快照 O(n²) 是存储凶手，增量化回 O(n)；payload >64KB 截断出对象存储存指针。
- 恢复秒级靠结构（按 session 聚簇 + 冷热分层）不靠全存；定期恢复演练（30 天前会话回放 + 哈希链校验）验证承诺。

## 复盘追问
- 为什么"状态库变慢"往往先于"存储报警"出现？提示：体积涨的同时索引/查询计划劣化（扫描行数涨），IO 成本先撞墙——容量账要包含查询路径复杂度，不只是磁盘余量。
- 审计合规强制全量留存时，还能优化什么？提示：只剩分层与编码手段——冷层压缩、去重（相同 payload 哈希）、以及把"查询模式"迁到冷层专用索引；删是没得删了，账在单价与检索性上。
