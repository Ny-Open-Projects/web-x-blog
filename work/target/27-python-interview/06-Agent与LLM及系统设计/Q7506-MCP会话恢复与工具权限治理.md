### Q7506 · MCP Streamable HTTP 的会话恢复与工具权限治理

> 难度:★★★ | 标签:MCP, 协议, 安全

**问**：我们从 stdio 迁到 Streamable HTTP 接 MCP 服务，遇到断线重连后会话丢失、工具权限全开的问题。MCP 的会话（session）机制怎么工作？工具权限治理在生产上该怎么落地？

**答**：结论：Streamable HTTP（MCP 2025-03-26 规范起）用 `Mcp-Session-Id` 响应头标识会话——initialize 时服务端下发，后续请求携带；会话状态（协商的能力、订阅的 SSE 流、分页游标）由服务端持有，客户端重连时**携带原 session id 请求恢复；服务端失效（重启/过期）则返回 404，客户端必须重新 initialize**——"重连即续用"是伪命题，要有重协商兜底。权限治理的核心是**三层收口：服务端白名单（tool 级 allowlist）、参数级约束（JSON Schema + 业务校验）、运行时审计（每次 call 记录 tool+参数指纹+调用方）**，客户端声明的"我需要什么权限"永远不可信。

机制与实战：
- 会话生命周期：session id 随服务端进程生死（内存态），网关负载均衡必须会话粘性（同 session 路由到同实例），否则 SSE 流与状态散落两台机器；滚动发布时靠"旧实例排空 + 客户端 404 重协商"完成迁移。
- 权限治理分层实战：mcp server 侧按 API key 映射 tool 白名单（只暴露该租户可用的 tool）；危险工具（写操作、出网调用）要求二次确认参数（confirm token）+ 速率限制；审计层落库 tool 调用轨迹，敏感参数（如 SQL、文件路径）留指纹不留明文。
- 事故复盘：某内部 Agent 网关把所有 MCP server 的 tools/list 全量暴露给前端，测试环境的 drop-table 工具被误调。修复：网关层按"环境 × 租户"双维白名单 + 危险工具调用强制 confirm token + 审计告警（未在白名单的调用即拦截并告警）。

```python
# 基线:Python 3.9+ 标准库;session 恢复语义 + 工具白名单网关(可运行)
import uuid

class McpServer:
    def __init__(self) -> None:
        self.sessions: dict[str, dict] = {}
    def initialize(self) -> str:
        sid = uuid.uuid4().hex
        self.sessions[sid] = {"negotiated": True}
        return sid
    def call(self, sid: str, tool: str) -> str:
        if sid not in self.sessions:
            raise LookupError("404: session 失效,客户端须重新 initialize")
        return f"ok:{tool}"

def gateway_call(server: McpServer, sid: str, tool: str,
                 allowlist: set[str]) -> tuple[bool, str]:
    """网关三层收口:白名单 → 会话 → 审计。"""
    if tool not in allowlist:
        return False, "blocked: not in allowlist"      # 第一层:权限
    try:
        r = server.call(sid, tool)
    except LookupError:
        return False, "renegotiate"                    # 第二层:会话恢复语义
    return True, r                                     # 第三层:审计落库(略)

if __name__ == "__main__":
    s = McpServer()
    sid = s.initialize()
    print(gateway_call(s, sid, "search", {"search", "read_file"}))
    print(gateway_call(s, sid, "drop_table", {"search", "read_file"}))
    print(gateway_call(s, "expired", "search", {"search"}))   # 触发重协商
```

**追问**：
- 一层追问：会话粘性和负载均衡冲突怎么办？——Session id 做一致性哈希路由（网关粘性）；实例重启导致的 404 是预期路径，客户端重 initialize 成本只是一次握手，不要为了"绝对续用"把 session 状态外置到 Redis（状态外置引入一致性新问题，MCP 规范也不要求）。
- 二层追问：MCP 工具的 JSON Schema 校验放在哪一层？——两层都要：server 侧校验（防注入与越权参数），网关侧复检（防 server 自身被绕过，尤其第三方 MCP server）；网关层校验失败的调用直接拒绝并计入该租户风险分。
- 三层追问：怎么防止"白名单里的工具组合出危险行为"？——工具级白名单不够，要做"调用链治理"：同一会话内（read → write → exec）序列模式识别，命中危险序列（如先读凭证再出网）即熔断；这是从"单点权限"升级到"行为权限"的思路。
