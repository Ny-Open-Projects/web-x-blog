### Q7565 · 离线批量推理的窗口与折扣成本账

难度：P6 | 标签：成本工程、批量 API、容量规划、离线推理

**问**：2 亿输出 token 的离线任务（每日摘要生成），直接走实时 API 一天 4800 元。批量通道（batch API，5 折）能省一半，但要 8 小时内跑完，并发怎么算？哪些任务适合迁批量通道？

**答**：
- **结论**：三笔账：① 单价账——批量/离线通道通常 5 折（供应商用闲置算力换延迟容忍），2 亿 token 省 2400 元/天；② 窗口账——耗时 = token 总量 / (单并发吞吐 × 并发数)，2 亿 token、40 token/s、8 小时窗口需要约 175 并发；并发先算够再谈折扣；③ 失败账——批量任务部分失败率高于实时，要有重试与对账（按输入 ID 对账产出，缺口补跑）。适合迁批量的判据：延迟容忍（小时级）+ 幂等可重跑 + 非交互；实时通道留给交互与时效敏感任务。
- **取舍**：批量通道把"算力峰值"变成"算力填充"：供应商给折扣买你的延迟容忍，平台侧的收益是成本曲线平滑。但批量任务挤占夜间窗口与实时任务抢配额的冲突要预设：批量可中断、可降并发，实时优先级永远更高。
- **实战**：落地：任务改造三件事：输入按 ID 幂等化（重跑不重复计费）、输出与输入 ID 对账（缺口补跑）、并发自适应（窗口剩余时间反推所需并发）。成本看板把"可迁批量但仍在实时通道跑的量"标出来——那是纯粹的浪费清单。

```python
"""离线批量推理的成本账：夜间窗口 + 批量折扣 vs 实时 API。"""
PRICE_REALTIME = 24.0     # 元/百万输出 token
PRICE_BATCH = 12.0        # 批量/离线通道通常 5 折
THROUGHPUT = 40           # token/s 单并发

def cost(tokens, price):
    return tokens / 1e6 * price

def hours_needed(tokens, concurrency):
    return tokens / THROUGHPUT / concurrency / 3600

tokens = 200_000_000            # 2 亿输出 token 的离线任务
print(f"实时通道成本 {cost(tokens, PRICE_REALTIME):.0f} 元")
print(f"批量通道成本 {cost(tokens, PRICE_BATCH):.0f} 元（省 {cost(tokens, PRICE_REALTIME)-cost(tokens, PRICE_BATCH):.0f} 元）")
for conc in (100, 300):
    need = hours_needed(tokens, conc)
    ok = need <= 8              # 夜间窗口 8 小时
    print(f"并发 {conc}: 需 {need:.1f} 小时 {'可完成' if ok else '超窗口'}")
print("要点：能接受小时级延迟的任务全部迁批量通道；窗口账=吞吐×并发，先把并发算够再谈折扣")
```

**追问链**：
1. 追问一层：批量任务的"部分失败"为什么比实时更常见？（批量通道执行时间长，中途配额波动/上游限流概率累积；所以对账+补跑是批量任务的标配而非可选项）
2. 追问二层：夜间窗口的并发从哪来？（共享实时配额的闲时容量，或独立预留；两种来源的成本不同——闲时便宜但不可承诺，要留实时通道兜底）

**背诵要点**：
1. 三笔账：单价折扣、窗口并发（token/吞吐/并发/3600）、部分失败对账。
2. 迁批量判据：延迟容忍 + 幂等可重跑 + 非交互。
3. 批量可中断可降并发，实时优先级永远更高；"可迁未迁"就是浪费清单。

**复盘追问**：
1. 批量任务跑到 90% 时配额被实时流量挤占，窗口超了，怎么止损？（先出已完成部分 + 剩余缺口转实时小批量补齐，按 ID 对账）
2. 为什么"并发先算够再谈折扣"？（折扣是单价优惠，窗口是容量约束；并发不够折扣也救不了 SLA）
