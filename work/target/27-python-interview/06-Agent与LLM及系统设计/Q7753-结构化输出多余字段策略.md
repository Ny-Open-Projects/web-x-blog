### Q7753 · 多出来的 note 字段去了哪：结构化输出的多余字段策略

难度：P6 ｜ 标签：LLM、结构化输出、additionalProperties、字段策略、数据泄漏

基线：Python 3.12；演示多余字段的三种策略（拒绝/剥离/透传）在正常路径与泄漏路径上的差异。

**问**：工单抽取要求输出 `{"category","priority"}` 两个字段，模型时不时多给一个 `"note"` 或 `"confidence"`。早期代码用 `dict(**obj)` 透传给下游 ORM，一直没事；直到某天模型多输出了一个 `"owner_id"` 字段（从上文里抄来的内部 ID），被 ORM 当成可写属性写进了数据库，触发了一次越权写入。多余字段到底该拒绝、剥离还是透传？

**答**：
- **结论**：多余字段是**未声明的自由度**，三种策略对应三种风险：① **透传**——多余字段原样进入下游，等价于"模型可以动态扩 schema"，轻则报错，重则把不该写的字段写进存储（这次事故就是透传 + ORM 的宽松构造器共同造成）；② **静默剥离**——代码能跑，但模型的输出偏好被掩盖，剥离率高说明 schema 描述与模型行为有偏差，你永远看不到；③ **显式拒绝（strict）**——Pydantic 默认忽略额外字段，配 `model_config = ConfigDict(extra="forbid")` 后多余字段直接校验失败，配合一次修复重试把 schema 拉回来。生产推荐：**对外交付路径 forbid + 统计剥离率，内部中间路径允许 ignore 但要计量**。
- **取舍**：① strict 会让解析失败率上升，必须配修复重试（把 JSON Schema 回灌让模型修一次，Q2666/Q7517 思路）与降级链（Q2031），否则可用性受损；② 有的字段"多余"其实是**版本滞后**——模型升级或提示词改动后多出的稳定字段，说明 schema 该扩了，走 schema 版本演进（Q7606）而不是一直剥离；③ `additionalProperties: false` 在 API 侧（如 OpenAI strict 模式，Q7707）是硬保证，客户端校验只是第二道防线，两道都要上。
- **实战**：① 输出管线里"多余字段计数"做成指标，按字段名分组——稳定出现的字段进 schema 评审，偶发字段看是否注入内容泄漏；② forbid 的报错信息要带多余字段名，喂回模型时明确"移除未声明字段"；③ ORM/存储层加第三道防线：白名单字段构造（`Model(**allowed_keys)`），纵深防御不指望单点。

```python
"""多余字段三策略：透传(事故源)/剥离(不可见)/forbid(显式拒绝+修复重试)。"""


class Ticket:
    allowed = {"category", "priority"}

    def __init__(self, **kw):
        # 模拟 ORM 的宽松构造器：任何 kwargs 都进 __dict__
        self.__dict__.update(kw)

    @classmethod
    def strict_create(cls, **kw):
        extra = set(kw) - cls.allowed
        if extra:
            raise ValueError(f"未声明字段: {sorted(extra)}; 允许={sorted(cls.allowed)}")
        return cls(**kw)


def pass_through(obj: dict) -> Ticket:
    return Ticket(**obj)                       # 透传：事故路径


def strip_silent(obj: dict) -> dict:
    return {k: obj[k] for k in ("category", "priority") if k in obj}


def forbid(obj: dict) -> tuple[bool, str]:
    allowed = {"category", "priority"}
    extra = set(obj) - allowed
    if extra:
        return False, f"移除未声明字段 {sorted(extra)}，只输出 {sorted(allowed)}"
    return True, ""


def repair_with_schema(malformed: dict) -> dict:
    """修复重试：把禁用字段的错误信息回灌（此处模拟模型修复结果）。"""
    ok, feedback = forbid(malformed)
    if ok:
        return malformed
    return {k: v for k, v in malformed.items() if k in {"category", "priority"}}


if __name__ == "__main__":
    good = {"category": "billing", "priority": "high"}

    leak = {"category": "billing", "priority": "high",
            "owner_id": 42, "note": "客户态度不好"}      # 模型从上下文抄来的字段
    t = pass_through(leak)
    print("透传:", t.__dict__, "-> owner_id 进入 ORM, 存在越权写入面")

    print("静默剥离:", strip_silent(leak), "-> 能跑, 但剥离行为不可见")

    ok, fb = forbid(leak)
    print("forbid:", ok, "|", fb)
    fixed = repair_with_schema(leak)
    print("修复重试后:", fixed, "-> Ticket.strict_create 成功:",
          Ticket.strict_create(**fixed).__dict__)

    print("\n正常路径不受伤: forbid(good) =", forbid(good)[0])
    print("结论：交付路径 extra=forbid + 修复重试；中间路径可剥离但必须计量剥离率")
    print("      稳定多出的字段是 schema 演进信号, 不是噪音")
```

**追问一**：`extra="forbid"` 会不会让解析失败率大涨，得不偿失？

→ 解析：短期会，长期不会。涨上来的失败率里，一部分是模型偶发多嘴（修复重试一轮解决），另一部分是**本来就该暴露的问题**：schema 描述含糊、few-shot 样例带了多余字段、提示词里残留旧版字段说明。透传模式下这些问题都被静默吞掉，表面平稳；forbid 把它们变成可统计的信号。工程上关键是配齐三件套：修复重试、降级链、多余字段计量——禁用本身不产生价值，禁用产生的信号与修复路径才产生价值。

**追问二**：模型多出的字段内容可能来自哪？为什么说这是泄漏面？

→ 解析：模型上下文里有系统提示词、会话历史、工具结果、RAG 文档——它"顺手"输出的字段值可能来自任何一层：把内部账号 ID（owner_id）、未脱敏的手机号、甚至系统提示词里的规则文本（Q2577 的 prompt 隔离问题）封装成字段输出。一旦透传进存储或 API 响应，就完成了"内部数据 → 对外可见"的泄漏。这也是为什么多余字段策略不只是 schema 卫生问题，而是**数据边界问题**：forbid 等于声明"模型无权扩 schema"，把自由度收回平台手里。
