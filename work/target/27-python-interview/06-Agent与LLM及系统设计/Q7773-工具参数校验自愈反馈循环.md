### Q7773 · 校验失败就放弃太浪费：工具参数的自愈反馈循环与修复预算

难度：P6 ｜ 标签：工具调用、参数校验、错误反馈、自愈循环、修复预算

基线：Python 3.12；实现"校验失败 → 结构化错误回传 → 模型修正 → 重试"的最小自愈循环（含修复轮数预算与超限转人工），全标准库实跑。

**问**：模型调工具时参数写错（订单号漏了前缀、状态枚举是脏值），第一版实现直接报错返回、整个任务失败——但错误信息明明足够模型自己修。校验失败后怎么把错误"喂回去"让模型自愈？错误信息该怎么设计？修复循环怎么防止变成死循环？

**答**：
- **结论**：参数校验失败不是终点，是**反馈的起点**。自愈循环三要素：① **结构化错误回传**：错误按 `field + reason + expected` 三段式返回（"status: 'SHIPPED!!' 不是合法状态，expected: [pending, shipped, done]"）——模型读这种信息一次就能修对；模糊的 "Invalid argument" 只能靠瞎猜，重试三次都撞墙；② **循环挂进 Agent 主循环**：工具层校验失败 → 错误作为 tool 结果回传 → 模型产出修正后的调用 → 重试，**复用** Agent 现有的"工具结果 → 下一轮推理"机制，不需要新框架（Q7741 成对裁剪的语义在这里同样适用：错误回传也是工具结果，也必须与调用对）；③ **修复预算**：同一工具调用最多自愈 2 轮，超限终止任务并转人工——**没有预算的自愈循环就是死循环温床**（模型可能永远修不对，每次都烧 token）。本卡演示两轮修复：订单号补前缀、脏枚举映射到合法值，第三轮成功。
- **取舍**：① 修复轮数的预算值：1 轮太紧（格式类错误常要两跳：先补前缀再清脏值），3 轮烧钱且超过它通常是"模型根本不理解任务"——2 轮是甜点；② 哪些错误值得自愈：**可定位可修正**的（格式、枚举、缺字段）自愈；**语义性错误**（金额超权限、订单不存在）不进自愈循环——修对了也不能执行，直接走业务错误路径；③ 错误回传的 token 成本：结构化错误几百 token，比"任务失败人工介入"的人力成本便宜两个量级，但要有预算封顶；④ 预判式防御优先：工具描述里写清格式与示例（Q7746 示例值的坑也要防）、Pydantic 校验 + 友好 error dict，把需要自愈的频率压到个位数百分比。
- **实战**：① 错误消息模板化：所有工具的校验错误统一 `{field, reason, expected}` 结构，模型侧的修复成功率才可统计；② 监控自愈健康度：修复成功率（修复后成功/触发修复次数）、平均修复轮数、超预算率——修复成功率骤降是提示/模型回归的信号；③ 修复轨迹进审计日志：模型"从什么修到什么"是 prompt 改进的一手语料；④ 幂等保护：修复重试意味着同一工具可能被调多次，写类工具必须有 step-id 幂等（Q1481），否则自愈循环叠加重试就是重复扣款。

```python
"""Q7773 工具参数校验失败的自愈反馈: 结构化错误回传给模型重试, 修复轮数有预算。"""
import json

VALID_STATUS = {"pending", "shipped", "done"}


def tool_update_order(order_id: str, status: str) -> dict:
    """业务工具: 严格校验参数."""
    if not order_id.startswith("O"):
        return {"ok": False, "error": "invalid_param",
                "field": "order_id",
                "reason": "必须以 O 开头的订单号",
                "expected": "O + 数字"}
    if status not in VALID_STATUS:
        return {"ok": False, "error": "invalid_param",
                "field": "status",
                "reason": f"{status!r} 不是合法状态",
                "expected": sorted(VALID_STATUS)}
    return {"ok": True, "order_id": order_id, "status": status}


def agent_loop(raw_calls: list[dict], *, max_repairs: int = 2) -> dict:
    """模型侧循环: 校验失败 -> 错误回传 -> 模型按 expected 修正 -> 重试."""
    repairs = 0
    trace = []
    for call in raw_calls:
        attempt = call
        while True:
            result = tool_update_order(**attempt)
            trace.append({"call": attempt, "result_ok": result["ok"]})
            if result["ok"]:
                break
            repairs += 1
            if repairs > max_repairs:
                return {"aborted": True, "trace": trace,
                        "reason": f"修复轮数超预算({max_repairs}), 转人工"}
            # 模拟模型读错误信息自我修正: 按 expected 提示修正参数
            fixed = dict(attempt)
            f = result["field"]
            if f == "order_id":
                fixed[f] = "O" + "".join(c for c in attempt[f] if c.isdigit()) or "O1"
            elif f == "status":
                fixed[f] = next((s for s in VALID_STATUS
                                 if attempt[f].lower() in s or s in attempt[f].lower()),
                                "pending")
            attempt = fixed
    return {"aborted": False, "trace": trace, "repairs": repairs}


if __name__ == "__main__":
    # 模型第一次给的参数: 订单号缺 O, 状态是脏值 "SHIPPED!!"
    r = agent_loop([{"order_id": "8821", "status": "SHIPPED!!"}])
    print(f"修复轮数: {r['repairs']}, aborted: {r['aborted']}")
    for t in r["trace"]:
        print(f"  call={t['call']} -> ok={t['result_ok']}")
    final = r["trace"][-1]["call"]
    ok = (not r["aborted"] and r["repairs"] == 2
          and final["order_id"] == "O8821" and final["status"] == "shipped")
    print(f"校验: 两次自愈修复 + 修复预算兜底 -> {'通过' if ok else '异常'}")
    print("结论：校验失败的错误信息要按'字段+原因+expected'结构化回传, 模型才能精准修;")
    print("      修复轮数必须有预算, 超预算转人工——自愈循环不加闸门就是死循环温床")
```

**追问一**：什么样的错误信息能让模型一次修对？"reason + expected"之外还缺什么？

→ 解析：模型修参数的过程是"读错误 → 定位字段 → 猜修正方向"，错误信息要服务这条链：① **field 精确到嵌套路径**：`items[2].sku` 而不是笼统 `items`——嵌套结构的定位失败是修复轮数暴涨的主因；② **expected 给正例不给描述**：`expected: ["pending","shipped","done"]` 直接可抄，`expected: 合法的订单状态字符串` 还要模型再猜一次；③ **原值回显**：`got: 'SHIPPED!!'`——模型上下文里参数还在，但显式回显消除歧义（多轮后上下文被裁剪时回显是唯一依据，Q7741 裁剪账）；④ **同类错误的批量报告**：一次校验把所有字段错误都返回（而不是修一个错一个），把 3 轮修复压成 1 轮——这是修复成本最大的优化；⑤ 反例标注：`'SHIPPED!!' 的多余字符 '!!' 需要去掉` 类的 reason 直接说差异，比复述规则省模型一轮推理。衡量标准：修复成功率（一次修复即过的比例），错误消息格式改版前后 A/B 一把就知道哪条最值钱。

**追问二**：自愈循环和"验证器给模型的反馈"有什么本质区别？什么任务不该做自愈？

→ 解析：自愈循环修的是**参数的形**（格式、枚举、类型——有唯一正解的机械问题），反馈闭环短、成功率高、风险低；"验证器反馈"（如代码任务跑单测后把失败贴回去）修的是**语义的对**——解空间开放、修复轮数不可预估、每一轮都可能是"模型在测试上过拟合"（改测试结果而非修代码）。所以自愈适合挂在工具层（确定性校验，字段级定位），验证器反馈适合挂在任务层（带轮数预算与轨迹审查）。不该做自愈的任务：① **不可重入的副作用工具**：转账、退款、发消息——第一次调用失败在"执行后校验"阶段时，重试可能双发（幂等表能救部分，但语义性失败不该重试）；② **失败原因在用户侧**：缺权限、订单被锁定——修复轮数烧完结果还是"不能做"，应该直接把业务原因透传给用户；③ **失败率高到失控**：修复成功率 <50% 时自愈是成本黑洞，先修提示与工具描述（Q7746/Q7748），把源头失败率压下来再谈自愈。预算、幂等、语义分层，三者齐了自愈循环才是资产，缺任何一个是负债。
