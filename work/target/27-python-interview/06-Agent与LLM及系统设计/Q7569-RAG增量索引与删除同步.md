### Q7569 · RAG 增量索引与删除同步

难度：P6 | 标签：RAG、索引同步、事故复盘

**问**：知识库每天改几百篇文档，全量重建 embedding 太贵。增量索引怎么做？"删除"为什么是 RAG 一致性最容易翻车的环节？

**答**：
- **结论**：增量索引 = 内容指纹 diff + 三类变更计划：指纹变了 → 重建该文档全部切片；文档没了 → 删除向量与切片元数据；新增 → 切片入库。全量重建只在 embedding 模型升级或分块策略变更时做。删除是翻车高发区：向量库删了但缓存没清、切片表删了但向量残留（HNSW 标记删除）、权限变了但向量元数据没更新——都会导致"检索到已删/越权内容"，直接变成幻觉引用。
- **取舍**：同步触发（写路径里删向量，强一致但写放大、失败会阻塞业务写）vs 异步对账（事件驱动 + 定时对账兜底，最终一致）。生产选异步：业务写 → 发事件 → 索引 worker 消费；对账任务每天按指纹全量 diff 一次兜底漏删。指纹要覆盖"影响检索的全部因素"：正文、权限、租户，任一变更都要重建。
- **实战**：事故复盘：用户搜到了离职员工才能看的文档——根因是权限变更没触发向量元数据更新。防线：把权限列放进向量库的 payload 并参与过滤；权限变更走同一指纹 diff 流程；检索层加"引用回查"——引用的 doc_id 先到主库校验可见性再输出，作为最后一道闸。

```python
"""RAG 增量索引同步：按内容指纹 diff 出 add/update/delete 计划。"""
import hashlib

def fp(text):
    return hashlib.sha1(text.encode()).hexdigest()[:12]

current = {  # 索引里已有的：doc_id -> 指纹
    "d1": fp("部署手册 v1"), "d2": fp("发布流程"), "d3": fp("旧版制度"),
}
source = {   # 文档库现状
    "d1": fp("部署手册 v2"),   # 内容变更 -> 重建
    "d2": fp("发布流程"),      # 未变 -> 跳过
                                # d3 被删 -> 删除向量
    "d4": fp("新员工指南"),    # 新增 -> 入库
}

def sync_plan(index, source):
    plan = []
    for did, f in index.items():
        if did not in source:
            plan.append(("delete", did))
        elif source[did] != f:
            plan.append(("update", did))
    for did in source:
        if did not in index:
            plan.append(("add", did))
    return plan

print(sync_plan(current, source))
print("要点：指纹 diff 是增量的前提；删除要同步清向量与元数据，否则 RAG 引用已删/越权内容")
```

**追问链**：
1. 追问一层：为什么"只对变更文档重建切片"还不够？（分块策略变化会改变切片边界，旧索引里的切片和新策略不一致；策略变更必须全量重建并开新索引灰度切换）
2. 追问二层：HNSW 索引的删除是物理的还是逻辑的？（多数实现是标记删除，段合并时才物理回收；大量删除后要触发 compaction，否则索引膨胀且被删向量可能仍在候选集中）

**背诵要点**：
1. 增量 = 指纹 diff 出 add/update/delete，指纹覆盖正文+权限+租户。
2. 删除是 RAG 一致性最高危环节：向量、切片、缓存、权限四处同步。
3. 异步事件 + 每日对账兜底；引用输出前回查主库可见性。

**复盘追问**：
1. 已下线产品文档仍被检索引用，对账流水线为什么没抓住？（对账只比正文指纹没比状态位）
2. embedding 模型升级时如何做到"索引服务不中断"？（双索引并存、回填追平、灰度切换、旧索引延迟删除）
