### Q7627 · SSE 长连接的句柄与并发容量账

难度：P6 ｜ 标签：容量规划 / SSE / 长连接

**问**：Agent 产品全量走 SSE 流式输出，峰值 5000 并发会话。网关/应用服务器的句柄与内存账怎么算？长连接架构与短连接的容量模型差在哪？5000 并发下"每会话一个进程"为什么必死，正确的并发形态是什么？

**答**：
- **结论**：账的三层：① **句柄账**——每条 SSE 连接占：一个 TCP socket（fd）、HTTP/1.1 下一个 worker 连接槽、上游到 LLM 供应商的一条并发流；fd 上限（ulimit -n，容器默认常是 1024）与反向代理（nginx 默认 worker_connections 1024~4096）是第一道墙——5000 并发需要显式调高 fd 与代理连接数配额，且代理要**关缓冲**（Q7609 已谈缓冲吞 SSE）；② **内存账**——每连接的状态：流缓冲（几 KB~几十 KB）、会话上下文引用、asyncio 任务栈；每连接 50~200KB 量级，5000 连接 ≈ 0.25~1GB，可控；真正危险的是"每会话一个线程/进程"形态——5000 线程 × 8MB 栈 = 40GB，进程更甚，必死；③ **上游配额账**——5000 并发流 × 每流输出速率，供应商 TPM/RPM 配额与并发流上限（Q7582/Q7586 同源）才是硬天花板，网关要做准入排队而不是让 5000 条全打上去。容量模型差异：短连接的容量单位是 **QPS**（吞吐模型，worker 复用）；长连接是**并发连接数**（驻留模型，每连接占住一份资源直到会话结束）——压测口径、告警指标（连接数而不是 RPS）、扩容触发器全部要换。正确并发形态：**单进程 asyncio 事件循环 + async 流转发**（每连接一个 coroutine，成本 KB 级），多实例水平扩展，网关侧 max_connections 显式配置 + 准入限流。
- **取舍**：技术选型：uvicorn/FastAPI 的 async SSE（StreamingResponse）天然适配；同步框架（Flask+gunicorn sync worker）每连接占一个 worker，5000 并发要 5000 worker——直接排除或用 gevent/gthread 补偿但心智负担大。断连治理：客户端断开要传播取消到上游（Q7598/Q7618 同源：取消省上游算力），心跳注释行（`: ping`）保中间设备不掐空闲连接。扩容触发器按"活跃连接数"与"上游并发流余量"双指标，而不是 CPU——长连接下 CPU 常很闲（等流）但容量已满。
- **实战**：落地：① 容器与代理层显式配置：`ulimit -n 65535`、nginx `worker_connections`/`proxy_buffering off`/`proxy_read_timeout`（>最长流时长）、LB 空闲超时对齐；② 压测用长连接专用场景（保持 N 并发流 M 分钟）而非 wrk 短连接 QPS；③ 监控三指标：活跃连接数、上游并发流数、每连接内存分布（防泄漏，Q218 进程泄漏同源）；④ 准入排队：超过上游流上限时排队/降级为非流式，而不是让连接全量建立后上游 429。

```python
# SSE 长连接容量账: 句柄/内存/上游配额三层, 并发形态选型
# 基线: Python 3.9+ 标准库; 真实场景 uvicorn + 反代配置门禁
from dataclasses import dataclass


@dataclass
class ConnBudget:
    per_conn_kb: float          # 流缓冲+任务栈+上下文引用
    proc_per_conn_mb: float     # 每线程/进程形态的单位占用


def memory_gb_asyncio(n: int, kb: float) -> float:
    return n * kb / 1024 / 1024


def memory_gb_thread_per_conn(n: int, mb: float, stack_mb: float = 8.0) -> float:
    return n * (mb + stack_mb) / 1024


def fd_gate(n: int, ulimit: int, proxy_conns: int) -> list[str]:
    issues = []
    if n * 2 > ulimit:            # 应用侧: 每连接 client+upstream 两个 fd
        issues.append(f"ulimit {ulimit} 不足以支撑 {n}x2 fd")
    if n * 2 > proxy_conns:
        issues.append(f"反代 worker_connections {proxy_conns} 需调高")
    return issues


def main() -> None:
    n = 5000
    mem_async = memory_gb_asyncio(n, 120)
    assert 0.5 < mem_async < 1.0, mem_async          # ~0.57GB, 可控
    mem_thread = memory_gb_thread_per_conn(n, 10)
    assert mem_thread > 80                            # 5000x18MB ≈ 88GB, 必死
    print(f"asyncio 形态 {mem_async:.2f}GB vs 每连接一线程 {mem_thread:.0f}GB -> 形态即生死")

    issues = fd_gate(n, ulimit=4096, proxy_conns=4096)
    assert len(issues) == 2                           # 双双不足
    assert fd_gate(n, 65535, 16384) == []
    print("句柄门禁:", issues, "-> 显式调 ulimit 与 worker_connections")

    # 上游配额是硬天花板: 准入排队而非全量打入
    upstream_streams, demand = 3000, 5000
    assert demand > upstream_streams
    print(f"上游流上限 {upstream_streams} < 需求 {demand}: 网关准入排队/降级非流式")
    print("OK: 长连接容量单位=并发连接数(驻留模型); 扩容看连接数不看CPU")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么长连接场景的扩容触发器不能只看 CPU？
→ 一句话提示：流转发大部分时间在等上游数据，CPU 很闲但 fd/内存/上游流配额已近上限——按 CPU 扩容会漏掉真正的墙；触发器要用活跃连接数与上游并发流余量。

**追问 2**：SSE 心跳（注释行）解决什么问题、间隔怎么定？
→ 一句话提示：防中间设备（LB/代理/NAT）按空闲超时掐断静默连接；间隔要小于链路上最激进的空闲超时（常见 30~60s，取 15~20s 安全），且心跳本身不计入模型 token。

## 背诵要点
- 长连接容量单位是并发连接数（驻留模型）而非 QPS；三层账 = fd（每连接 client+upstream 两个，ulimit/代理 connections 显式调高）+ 每连接内存（KB 级 asyncio vs 线程形态 8MB 栈 ×N 必死）+ 上游并发流配额。
- 并发形态即生死：单进程 asyncio 事件循环 + async 流转发（5000 连接 ≈ 0.5GB），同步 worker-per-connection 形态直接排除；网关对上游配额做准入排队。
- 配置门禁：`ulimit -n`、nginx worker_connections / proxy_buffering off / read_timeout>最长流时长；压测用"N 并发流保持 M 分钟"专用场景；扩容触发器看连接数与上游余量。

## 复盘追问
- 为什么"每会话一个线程"在压测 50 并发时看起来没问题？提示：50×8MB=400MB 可控，容量问题按平方外推在低并发下不可见——5000 并发才爆；容量评审必须按目标峰值算账而不是按当前流量。
- 断连取消传播在长连接架构里为什么同时是成本问题？提示：用户关页后连接断了但上游推理继续（计费继续、并发流配额被占），取消传播直接回收上游算力——SSE 架构里断连处理是容量账的一部分，不只是体验问题。
