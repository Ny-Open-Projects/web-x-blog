### Q7769 · 中文 Emoji 解出半个字符：流式响应的 UTF-8 多字节边界与增量解码

难度：P6 ｜ 标签：UTF-8、流式解码、SSE、增量解码器、编码边界

基线：Python 3.12；实测多字节字符被 chunk 从中间切开时 naive decode 报错/乱码，与 codecs 增量解码器的正确行为，全标准库实跑。

**问**：SSE 流式输出对接前端，日志里偶发 `UnicodeDecodeError: invalid continuation byte` 或者数据库里落了"ä¸­æ–‡"这样的乱码——中文和 emoji 被网络分块从字节中间切开了。为什么按 chunk 收流再 decode 会撞上多字节边界？正确的解码姿势是什么？SSE 的帧边界、UTF-8 字节边界、JSON 边界三层怎么各管各的？

**答**：
- **结论**：UTF-8 里中文 3 字节、多数 emoji 4 字节，TCP 分块只看字节数不看语义——chunk 边界随时落在多字节字符中间。**对每个 chunk 独立 `bytes.decode()` 必然撞墙**：半个字符的字节序列不是合法 UTF-8，严格模式抛 UnicodeDecodeError；用 `errors="replace"`/`"ignore"` 则每个跨界字符永久变乱码（数据库里的 mojibake 就是这么来的）。正确姿势是**增量解码器**（`codecs.getincrementaldecoder("utf-8")()`）：它维护"待续字节"状态，chunk 到了先喂给 decoder，不完整的尾字节暂存，等下一个 chunk 拼上再出字符——跨 chunk 字符在拼接完成后完整出现，零报错零乱码。三层边界各管各的：**字节层**（增量解码出完整文本）、**帧层**（SSE 按 `\n\n` 分事件，Q2316 断线续传）、**语义层**（事件里的 JSON 增量解析或完整后再 parse，Q1134 流式工具调用）。乱码事故的根因几乎都是把三层挤在一起处理。
- **取舍**：① `errors="replace"` 的诱惑：它让程序不崩，但把"字节流处理错误"掩盖成"数据质量问题"（脏数据入库、前端乱码），生产流式路径禁用宽松错误策略——崩掉修代码，好过乱码入库洗不掉；② 增量解码的状态管理：decoder 实例要与流的生命周期绑定（每条连接一个），跨连接复用会把 A 连接的半个字符吐进 B 连接——连接断开时 decoder 里的残余字节按中断处理（Q7508 取消时已消耗内容的语义）；③ 二进制与文本的分层：读流阶段用 bytes、解码在固定一层做，混层处理（有人 decode 有人不 decode）是 mojibake 温床（Q5155 bytes 与 str 比较恒假的同族）；④ 性能账：增量解码器每 chunk 一次调用，开销可忽略，别为了省一次调用整包 decode。
- **实战**：① 流式网关统一用增量解码器收 SSE（一处实现，所有下游受益）；② 数据库写入前断言字符串不含 U+FFFD 替换符（乱码入库的最后闸门）；③ 压测样本覆盖边界：中文/emoji/组合字符（é 的分解形式）按 1 字节步长切流的用例（Q2686 帧级排障的十六进制 dump 定位）；④ 跨语言管线（Python 收流→Node 处理→存储）统一 UTF-8 声明，禁 latin-1 中转。

```python
"""流式 UTF-8 多字节边界: naive decode 报错/乱码 vs 增量解码器正确拼接。"""
import codecs


def naive_decode_stream(chunks: list[bytes], errors: str = "strict") -> str:
    """反例: 每个 chunk 独立 decode (chunk 边界撞上多字节字符)。"""
    parts = []
    for c in chunks:
        try:
            parts.append(c.decode("utf-8", errors=errors))
        except UnicodeDecodeError as e:
            parts.append(f"<DECODE_ERROR@{len(parts)}>")
            _ = e
    return "".join(parts)


def incremental_decode_stream(chunks: list[bytes]) -> str:
    """正解: 增量解码器, 尾部不完整字节暂存到下一个 chunk。"""
    dec = codecs.getincrementaldecoder("utf-8")()
    parts = []
    for c in chunks:
        parts.append(dec.decode(c))          # 不完整尾字节内部暂存
    parts.append(dec.decode(b"", final=True))
    return "".join(parts)


def split_bytes(data: bytes, step: int) -> list[bytes]:
    """按固定步长切流, step=1 时每个多字节字符必被切开。"""
    return [data[i:i + step] for i in range(0, len(data), step)]


if __name__ == "__main__":
    text = "订单已创建✅ 请查收📦 后续跟进中"        # 混合 1/3/4 字节字符
    raw = text.encode("utf-8")

    # 1 字节切流: 最恶劣边界
    chunks1 = split_bytes(raw, 1)
    bad = naive_decode_stream(chunks1)
    good = incremental_decode_stream(chunks1)
    print(f"原文: {text}")
    print(f"\n1 字节切流, 逐 chunk 独立 decode (strict):")
    print(f"  结果: {bad[:40]}...")
    print(f"  报错占位符 {bad.count('<DECODE_ERROR')} 处 -> 每个多字节字符撞墙一次")
    print(f"1 字节切流, 增量解码器:")
    print(f"  结果: {good}")
    print(f"  与原文一致? {good == text}")

    # 2 字节切流 + replace 宽松模式: 不崩但永久乱码 (mojibake 入库)
    chunks2 = split_bytes(raw, 2)
    loose = naive_decode_stream(chunks2, errors="replace")
    print(f"\n2 字节切流 + errors='replace': {loose[:30]}...")
    print(f"  含替换符 U+FFFD? {'\\ufffd' in loose} -> 乱码静默入库, 事后洗不掉")

    # 混合切流 (随机 1~5 字节) 的正确性
    rng_steps = [1, 5, 2, 3, 1, 4, 2]
    pos, mixed = 0, []
    while pos < len(raw):
        step = rng_steps[pos % len(rng_steps)]
        mixed.append(raw[pos:pos + step])
        pos += step
    print(f"\n混合切流: 增量解码一致? {incremental_decode_stream(mixed) == text}")

    ok = good == text and "\\ufffd" in loose and incremental_decode_stream(mixed) == text
    print(f"校验: 增量解码零乱码 + replace 乱码复现 -> {'通过' if ok else '异常'}")
    print("\n结论：多字节边界是流式第一层坑; 增量解码器暂存尾字节;")
    print("      字节层(解码)->帧层(SSE 事件)->语义层(JSON) 三层各管各的")
```

**追问一**：SSE 场景里，字节边界与事件边界为什么要分层处理？合并处理会发生什么？

→ 解析：SSE 的协议层按 `\n\n` 切事件、事件内 `data:` 行承载载荷；UTF-8 的字节边界在任意位置。合并处理的典型错误是"在字节流上直接找 `\n\n` 再 decode"：分隔符本身是 ASCII 单字节不会撕裂，看似能工作——但当 data 行里含多字节字符且 chunk 切在其中间时，从字节层捞出的"完整事件"尾部是半个字符，decode 报错或乱码。分层后各司其职：字节层用增量解码器把字节流转成完整字符流（尾字节暂存），帧层在**字符流**上按 `\n\n` 找事件边界（此时分隔符与载荷都是完整的 str），语义层对事件载荷做 JSON 解析。三层各自的恢复语义也清晰：字节层残余字节=连接异常、帧层半事件=断线续传（Q2316 用 Last-Event-ID 重放）、语义层 JSON 不完整=分片协议（Q1134 增量拼接）。合在一起写的代码，出问题时三层症状混在一个堆栈里，排障成本翻几倍。

**追问二**：连接中断时，增量解码器里残留的半字符算什么？直接丢掉对吗？

→ 解析：不算丢数据——半字符**本来就不是字符**，UTF-8 里它是"未完成的编码序列"，语义上等于"传输被截断的字符"。正确处理：① decoder 的 `decode(b"", final=True)` 会把残余不完整字节按错误处理（strict 模式抛错或按策略替换），这是显式的"流被截断"信号，应该触发该连接的收尾逻辑（标记输出不完整、计费按已产出内容算，Q7508 流式取消与计费一致性）；② 残余绝不能"等下一条连接接着用"——decoder 状态与连接绑定，跨连接复用会把 A 的半个字拼进 B 的开头，产出谁都不认识的字符；③ 写入侧的闸门：如果截断发生在写库前，落库内容要么带"不完整"标记（前端显示"…"），要么不入库等重试——把"半个字符"当正常文本入库是最恶劣的脏数据，事后清洗要对全表扫 U+FFFD 和非法序列。工程上把这归类为"流式输出的中断语义"：中断输出 ≤ 完整输出 < 无输出（对事务性任务），分层协议让每一层都能显式表达自己在哪一档。
