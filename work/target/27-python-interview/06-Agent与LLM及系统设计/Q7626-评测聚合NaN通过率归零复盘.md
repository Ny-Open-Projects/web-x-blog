### Q7626 · 评测聚合 NaN 导致通过率归零的事故复盘

难度：P6 ｜ 标签：事故复盘 / 评测工程 / pandas

**问**：某天评测平台报告核心 Agent 的通过率从 92% 骤降到 0%，告警拉响。排查发现评测结果表里混入了几条 judge 输出解析失败的 NaN 行，聚合脚本 `df.mean()` 整列变 NaN，通过率算成 0。为什么一行 NaN 能污染整列聚合？这类"评测管道的元故障"怎么防？

**答**：
- **结论**：机理：① pandas 的 `mean()`/`sum()` 等默认 `skipna=True`，但**整列全 NaN 或 object dtype 列里 NaN 与字符串混存**时行为翻转——judge 输出解析失败写入 `None`，列被 pandas 推断成 object，`mean()` 直接报错或产 NaN；另一常见形态是 `df[df.score > 0.8].shape[0] / df.shape[0]` 中布尔过滤被 NaN 比较（`NaN > 0.8` = False）悄悄吞掉样本——通过率分母不变分子变小；② 本事故的具体链路：judge 模型一次输出格式漂移（多了个前缀）→ 解析函数没做防御返回 None → 几行 NaN 混入 → 聚合口径没区分"解析失败"与"评测失败" → 0% 通过率假象。深层教训：**评测管道是数据管道**（Q7033 dtype 漂移同源），judge 输出是外部数据（不可信，Q7525 同源思想），必须走"解析失败显式标记 + 口径区分"而不是静默混入。通过率 0% 与 92% 之间的巨变本身也该触发"先怀疑测量再怀疑系统"的反射——测量系统故障的先验概率常高于业务瞬间全崩。
- **取舍**：防御层次：① 解析层——judge 输出解析失败返回显式状态（`status="parse_error"`），score 列保持数值 dtype，失败行不参与分母也不被静默丢弃；② 聚合层——用 `pivot` 前先 `df.dtypes` 断言 + 通过率计算显式写 `valid = df[df.status=="ok"]`，分母分子都从 valid 出；③ 告警层——"通过率环比跌幅 >30% 且 valid 样本数下降"判为测量故障（先查解析），"valid 数稳定但通过率跌"才是业务退化；④ 复算层——原始 judge 原始输出落库（不可再生），解析器可重放修复历史，事故后回填当天数据消除统计空洞。
- **实战**：落地：① 评测 schema 门禁：score 列 dtype、status 枚举、null 比例上限三道检查（Q7036 事件 schema 契约同源）；② 聚合函数收敛为平台统一实现，禁止各评测脚本自带 `mean()`；③ 解析器带版本号，原始输出 + 解析器版本一起存——可重放可追溯；④ 告警规则区分"样本量变化"与"指标变化"两个信号；⑤ 事后补一条 CI：用含 NaN/坏格式的 fixture 跑聚合，断言口径正确。

```python
# NaN 污染聚合的机理与防线: 显式 status 口径 + dtype 门禁
# 基线: Python 3.9+ 标准库模拟; 真实管道用 pandas 复现(skipna 语义)
from dataclasses import dataclass


@dataclass
class EvalRow:
    case_id: str
    status: str        # ok | parse_error | judge_fail
    score: float | None


def parse_judge_output(raw: str) -> EvalRow:
    """防御性解析: 失败显式标记, 不返回裸 None 混入数值列。"""
    try:
        s = float(raw.strip().strip(chr(96)*0).removeprefix("score:").strip())
        if not 0.0 <= s <= 1.0:
            return EvalRow("?", "judge_fail", None)
        return EvalRow("?", "ok", s)
    except (ValueError, AttributeError):
        return EvalRow("?", "parse_error", None)


def pass_rate(rows: list[EvalRow]) -> tuple[float, int, int]:
    """通过率只从 status==ok 的样本出; 返回 (rate, valid, parse_errors)。"""
    valid = [r.score for r in rows if r.status == "ok"]
    errs = sum(1 for r in rows if r.status == "parse_error")
    if not valid:
        return 0.0, 0, errs
    return sum(1 for s in valid if s >= 0.8) / len(valid), len(valid), errs


def dtype_gate(rows: list[EvalRow]) -> bool:
    """门禁: score 列只允许数值或 None 且 None 仅出现在非 ok 行。"""
    return all(r.score is None or isinstance(r.score, float) for r in rows) and \
           all(r.score is not None or r.status != "ok" for r in rows)


def main() -> None:
    rows = [EvalRow(f"c{i}", "ok", 0.9) for i in range(9)] + \
           [EvalRow("cx", "ok", 0.7)]
    assert abs(pass_rate(rows)[0] - 0.9) < 1e-9

    # 事故注入: judge 输出格式漂移 -> parse_error 显式标记(而非裸 None)
    bad = parse_judge_output("score: 0.95 -> (the answer is correct)")
    assert bad.status == "parse_error" and bad.score is None
    polluted = rows + [bad]
    rate, valid, errs = pass_rate(polluted)
    assert errs == 1 and valid == 10        # 分母只含 valid, 不被 NaN 吞
    assert abs(rate - 0.9) < 1e-9
    print("防线: parse_error 显式入列, 通过率分母口径稳定, 告警可区分测量故障")

    assert dtype_gate(rows) and dtype_gate(polluted)
    # 反例: 裸 None 混进 ok 行 -> 门禁拦截
    assert not dtype_gate(rows + [EvalRow("cy", "ok", None)])
    print("OK: 评测管道=数据管道; 跌幅>30%且valid数下降 -> 先怀疑测量")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"通过率瞬间 92%→0%"应该先怀疑测量系统？
→ 一句话提示：业务退化的形态通常是渐进或局部（按任务类型/租户分布），瞬间归零且无对应变更更符合测量故障（解析漂移、聚合口径变化、上游数据缺失）——先验证测量再排查业务是成本最低的排障序。

**追问 2**：原始 judge 输出落库为什么必须做？
→ 一句话提示：解析器可升级重放，聚合口径可以修复历史（否则事故当天的统计永久空洞）；这也是评测可审计的基础——复算任何人都能对上数。

## 背诵要点
- NaN 污染机理：object 列混入 None 使聚合翻车、`NaN > 0.8` = False 让布尔过滤静默吞样本；judge 输出是外部数据，解析失败必须显式 status 标记而非裸 None。
- 口径纪律：通过率分母分子都从 `status=="ok"` 出；告警双信号——valid 数下降+指标跳水 = 测量故障先查，valid 稳定+指标跌 = 业务退化。
- 设防三层：schema 门禁（dtype/枚举/null 比例）、统一聚合实现（禁各脚本自带 mean）、原始输出+解析器版本落库可重放回填。

## 复盘追问
- 为什么评测脚本各自实现聚合是隐患？提示：口径漂移（分母含不含 parse_error、阈值 0.8 还是 0.75）在不同脚本间不可比，历史趋势被悄悄改写；统一聚合 + 版本化口径是可比性的前提。
- 解析失败的行"不参与分母"会不会掩盖质量退化？提示：会——如果 parse_error 本身是模型退化（输出格式漂移也是模型行为），把 parse_error 率单列指标监控，与通过率并列；parse_error 率上升本身就是告警。
