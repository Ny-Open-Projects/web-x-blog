### Q7754 · 发票合计 12345.67 认成 12345.57：OCR 数字错位对下游的破坏与校验防线

难度：P6 ｜ 标签：多模态、OCR、数字校验、结构一致性、 fail-closed

基线：Python 3.12；模拟 OCR 的常见混淆（l/1、O/0、小数点漂移）与"合计 = 明细之和"的结构校验防线。

**问**：发票/账单类文档走"视觉模型 + OCR"入账，数字识别错误率单独看只有 0.5%，但落到报销系统就变成了持续的账务差异工单——单字符错位（12345.67 → 12345.57）、l 认成 1、O 认成 0、小数点漂移，每一个都足以让金额错一位。单字段准确率明明不差，为什么账就是不平？数字类 OCR 该配什么防线？

**答**：
- **结论**：数字错的破坏力来自**结构联动**：一张发票上"合计 = 各明细之和（含税变换）"是一个可计算的**结构约束**，OCR 逐字识别时没有任何模型"知道"这个约束，0.5% 的单字错误落进合计列，账就不平。防线设计因此不靠提高识别准确率，而靠**结构校验 + fail-closed**：① 抽取后立刻跑结构断言（明细之和 = 合计、税额 = 金额 × 税率、大小写金额一致），任何一条不满足就整张打回人工，绝不带病入账；② 置信度门限——OCR/视觉模型对数字区域通常给 per-token 置信度（logprobs 思路，Q7702），低于阈值的数字字段直接标记"待人工"而不是猜；③ 金额与"大写金额"列做交叉验证，是免费的冗余校验源。
- **取舍**：① 全字段人工复核成本不可接受，只把"结构校验失败的文档"路由给人工，占比通常 <3%；② 自动"猜"（把 1.5 修成 15 之类）在账务场景禁止——宁可人工，不可篡改；③ 对同一文档做**双通道识别**（OCR 引擎 + 视觉模型各跑一次）并对数字逐位比对，不一致即打回，用双倍算力换错误率数量级下降；④ 校验失败率本身要监控：暴涨说明新版版式/扫描质量变化，上游先处理。
- **实战**：① 数字字段与文本字段分开处理：数字列用字符白名单解码（只允许 0-9.），杜绝 l/O 混淆；② 结构断言库和业务一起维护，每类单据一组断言；③ 校验失败的样本自动回流成评测集（Q1783 坏例回流），驱动识别端迭代；④ 金额字段在系统内全程用最小单位整数（Q2474），OCR 输出转分，避免二次浮点误差叠加。

```python
"""OCR 数字防线：字符白名单解码 + 结构断言 + fail-closed。"""
import re

OCR_CONFUSION = {"l": "1", "O": "0", "o": "0", "I": "1", "，": ".", "。": "."}


def ocr_number(raw: str) -> tuple[str | None, list[str]]:
    """数字字段专用解码：字符白名单 + 混淆归一。返回 (值, 修正记录)。"""
    fixes = []
    out = []
    for ch in raw.strip():
        if ch in OCR_CONFUSION:
            fixes.append(f"{ch}->{OCR_CONFUSION[ch]}")
            out.append(OCR_CONFUSION[ch])
        elif ch.isdigit() or ch in ".,":
            out.append(ch)
        else:
            return None, [f"非法字符 {ch!r}"]
    return "".join(out).replace(",", ""), fixes


def assert_structure(items: list[dict], total: float, tax_rate: float = 0.0
                     ) -> list[str]:
    """结构断言：明细之和 = 合计；可选税额约束。"""
    problems = []
    detail_sum = round(sum(i["amount"] for i in items), 2)
    if abs(detail_sum - total) > 0.01:
        problems.append(f"明细之和 {detail_sum} != 合计 {total}")
    if tax_rate:
        expect_tax = round(total * tax_rate, 2)
        if abs(sum(i.get("tax", 0) for i in items) - expect_tax) > 0.01:
            problems.append(f"税额与 {tax_rate:.0%} 税率不符")
    return problems


def ingest(items_raw: list[dict], total_raw: str) -> str:
    total, fixes = ocr_number(total_raw)
    if total is None:
        return "打回人工: 合计字段解码失败"
    items = []
    for it in items_raw:
        v, _ = ocr_number(it["amount_raw"])
        if v is None:
            return "打回人工: 明细数字解码失败"
        items.append({"name": it["name"], "amount": float(v)})
    problems = assert_structure(items, float(total), tax_rate=0.06)
    if problems:
        return f"打回人工(fail-closed): {'; '.join(problems)}"
    return f"入账成功: 合计 {total} 与明细一致{' (' + '; '.join(fixes) + ')' if fixes else ''}"


if __name__ == "__main__":
    invoice = {"items": [{"name": "咨询费", "amount_raw": "5O00.00"},
                         {"name": "差旅费", "amount_raw": "7345.67"}],
               "total_raw": "12345.57"}            # 0.5% 错误: 67 被认成 57
    print("OCR 原始:", invoice["items"], invoice["total_raw"])
    print("处理结果:", ingest(invoice["items"], invoice["total_raw"]))

    good = {"items": [{"name": "咨询费", "amount_raw": "5000.00"},
                      {"name": "差旅费", "amount_raw": "7345.67"}],
            "total_raw": "12345.67"}
    print("正确识别:", ingest(good["items"], good["total_raw"]))

    print("\n结论：单字 0.5% 错误靠结构断言拦截入账; 数字列白名单解码消灭 l/O 混淆")
    print("      账务场景宁可打回人工, 禁止自动猜数; 失败样本回流评测集")
```

**追问一**：为什么"提高识别模型准确率"不是这个场景的首选解？

→ 解析：准确率从 99.5% 提到 99.9% 要付出模型升级/算力成本，且永远到不了 100%——而账务系统的要求是"错的绝对不能入账"，这是一个**拦截问题**不是**识别问题**。结构断言把"单字段 99.9% 正确"放大成"整张账单结构自洽才放行"，一张 10 行明细的发票 10 个数字全对的概率即便只有 95%，断言也能保证错账进不了系统（进人工队列）。两者是互补的：识别端降低人工量，校验端守住正确性底线，顺序不能颠倒。

**追问二**：双通道识别比对具体怎么做才不会误伤？

→ 解析：两个通道只在**数字字段**上逐位比对（文本字段模糊匹配即可），不一致的位标红而不是整张打回——一个金额里 8 位数字错 1 位，两通道不一致的那 1 位就是嫌疑位。误伤主要来自格式歧义（千分位逗号、全角数字），所以比对前先做归一化（去分隔符、全角转半角、单位统一）。真正的模糊地带是手写体与低质量扫描，双通道经常都不确定——这类直接按置信度门限进人工，不要用"两通道一致"当免死金牌，两个模型可能错得一样（同源偏差）。
