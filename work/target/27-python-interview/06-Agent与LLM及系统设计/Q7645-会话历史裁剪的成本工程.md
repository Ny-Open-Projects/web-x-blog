### Q7645 · 多轮会话历史裁剪的成本工程

难度：P6 ｜ 标签：成本工程 / 上下文管理 / 会话

**问**：一个多轮 Agent 平均会话 25 轮，到后期每轮请求都带着全部历史，token 成本随轮次超线性增长，长会话毛利为负。历史裁剪（截断/摘要/结构化保留）的策略怎么设计才能既控成本又不伤任务质量？裁剪策略本身怎么做成可配置的成本工程？

**答**：
- **结论**：先看清成本结构：无裁剪时第 n 轮的输入 token ≈ 历史累计 + 前缀，**整个会话的总输入 token 是 O(n²)**——25 轮会话的输入总量约等于"平均历史长度 × 轮数"，这正是 Q7614 多轮重复计费的会话级版本。裁剪策略按"信息寿命"分层：① **永不裁剪层**：system prompt、任务目标、关键约束（用户明确说过的规则）——裁掉这层的代价是行为漂移（Q7630 的约束丢失类事故）；② **摘要层**：中段历史用小模型压缩成要点（一次性成本，此后每轮携带固定大小），摘要本身有丢失风险，要保留"可指回原文"的引用（轮次编号）；③ **滚动窗口层**：最近 K 轮原文保留（工具调用的参数与结果细节只在这层有完整形态）；④ **工具结果瘦身**：历史里的工具输出往往占 60%+ 的 token（Q7575 的单次压缩延伸到会话层——多轮重复携带同一大结果是最贵的浪费），旧轮次工具结果替换成"结果摘要 + 检索指针"。成本工程化：裁剪策略做成配置（各层 token 上限 + 触发阈值），与计费联动——每轮请求记录"输入 token 构成"（system/摘要/窗口/工具结果），超预算会话触发策略升级，A/B 验证"裁剪强度 vs 任务成功率"的曲线找成本质量拐点。
- **取舍**：裁剪强度加大省 token 但伤质量（丢上下文答错），且质量损失是**非线性的**——关键约束被裁掉的那一轮会灾难性失败，平均成功率掩盖了长尾。摘要用小模型（便宜）vs 大模型（保真）：摘要质量差会导致下游用错误的记忆回答，账上"省的 token"被"增加的错误"吃回（Q7640 返工账联动）。激进方案（每轮裁）vs 触发式（超阈值才裁）：触发式避免小会话的额外开销。
- **实战**：① 输入 token 构成打点（四层各占多少），是策略调优的数据基础；② 摘要生成放在轮间异步做（不占用户延迟），摘要失败降级为"保留原文窗口"；③ 关键约束提取显式化：会话开始时把"用户规则"抽成结构化字段单独保存，比指望摘要模型记住可靠。

```python
# 会话历史分层裁剪: 固定层 + 摘要层 + 滚动窗口 + 工具结果瘦身
# 基线: Python 3.9+ 标准库 (token 数用近似估算)
from dataclasses import dataclass, field


def approx_tokens(text: str) -> int:
    return max(1, len(text) // 3)          # 中文近似: 3 字符/token


@dataclass
class HistoryPolicy:
    fixed_budget: int = 300                # system+约束 永不裁
    summary_budget: int = 400              # 摘要层上限
    window_rounds: int = 5                 # 最近 K 轮原文
    tool_result_budget: int = 150          # 旧轮工具结果瘦身上限

    def build_context(self, rounds: list[dict]) -> tuple[int, list[str]]:
        parts: list[str] = ["[system+约束]"]
        used = self.fixed_budget
        # 摘要层: 旧轮次(窗口外)压成要点
        old = rounds[:-self.window_rounds]
        if old:
            summary = "要点:" + ";".join(r["gist"] for r in old)
            used += min(approx_tokens(summary), self.summary_budget)
            parts.append("[摘要]")
        # 窗口层: 最近 K 轮原文, 旧轮工具结果瘦身
        for r in rounds[-self.window_rounds:]:
            used += approx_tokens(r["text"])
            if approx_tokens(r.get("tool_out", "")) > self.tool_result_budget:
                used += self.tool_result_budget   # 瘦身为摘要+指针
            else:
                used += approx_tokens(r.get("tool_out", ""))
            parts.append("[窗口]")
        return used, parts


def main() -> None:
    # 无裁剪: 25 轮会话, 每轮增量 200 token, 累计历史 O(n^2)
    total_naive = sum(200 * i for i in range(1, 26))     # 65000
    assert total_naive == 65_000
    # 裁剪后: 每轮输入约 固定300+摘要400+窗口5轮x200 ≈ 1700 封顶
    policy = HistoryPolicy()
    rounds = [{"gist": f"轮{i}要点", "text": "x" * 600,
               "tool_out": "y" * 900} for i in range(25)]
    used, parts = policy.build_context(rounds)
    assert used < 2500, used                       # O(n) 封顶
    assert len(parts) >= 6                         # system+摘要+5窗口
    savings = 1 - used / total_naive
    assert savings > 0.9
    print(f"无裁剪总计 {total_naive} tok(O(n^2)) vs 裁剪每轮约 {used} tok(O(n))")
    print(f"层构成: {parts[:3]}...; 省约 {savings:.0%}")
    print("OK: 四层裁剪(固定/摘要/窗口/工具瘦身) + 超阈值升级策略")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么工具结果是裁剪的第一优先级而不是旧轮对话文本？
→ 一句话提示：历史里工具结果（JSON/长文档）体积占比最大（常 60%+）且信息寿命最短（结果已被吸收进回答），摘要化收益最高；对话文本信息密度高、误裁直接伤质量。

**追问 2**：摘要失败或摘要质量差怎么兜底？
→ 一句话提示：降级为"保留更多原文窗口"（成本上升但质量不崩）+ 摘要质量抽检（对照原文问答一致性）；关键约束不依赖摘要——开始时抽成结构化字段单独携带。

## 背诵要点
- 无裁剪的会话输入是 O(n²)，分层裁剪后 O(n)：固定层（system/约束不裁）+ 摘要层（旧轮压缩）+ 滚动窗口（最近 K 轮原文）+ 工具结果瘦身（第一优先级）。
- 裁剪强度与任务成功率是曲线关系，平均成功率掩盖长尾灾难（关键约束被裁）；关键约束显式抽取为结构化字段。
- 工程化：输入 token 构成打点（四层占比）、策略配置化与阈值触发、摘要异步生成 + 失败降级保原文。

## 复盘追问
- 如何 A/B 验证"裁剪强度 vs 任务质量"的拐点？提示：按裁剪档位分流真实流量，对比任务成功率/追问率/人工接管率，找质量开始下滑的档位前留两档安全边际。
- 摘要引用"轮次编号"有什么用？提示：下游回答可以指回来源（引用溯源 Q7523 的会话内版本），需要细节时按编号重新取原文（工具/存储），形成"摘要为索引、原文为事实源"的结构。
