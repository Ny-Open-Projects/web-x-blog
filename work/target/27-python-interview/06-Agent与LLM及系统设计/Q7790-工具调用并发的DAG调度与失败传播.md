### Q7790 · 工具调用并发的失败传播：DAG 并行度、三态合并与部分成功

难度：P7 ｜ 标签：Agent、工具调用、DAG、并发、失败传播、部分成功、取消

基线：库知识库外知识卡，代码用标准库模拟——手工实现依赖 DAG 的波次调度与 fail-fast/fail-soft 两种失败策略，不调用外部 API。

**问**：Agent 规划出 6 个工具调用，依赖关系是 A→B→C、A→D→E、C+E→F。并行执行时 B 失败了：C 该不该跑？F 还能不能出结果？已经在飞的 D、E 要不要取消？如果这是"查资料"这种可降级任务，和"下单"这种不可降级任务，失败传播策略应该一样吗？

**答**：

- **结论**：DAG 执行要先定义**失败语义**，再谈并发。节点状态不是二态而是三态以上：`ok` / `failed` / `skipped`（依赖失败，未执行）/ `cancelled`（外部取消，已排队或运行中）。三种策略：① **fail-fast**：任一节点失败，立即取消所有未完成节点（包括无关分支），整体失败——适合事务性/不可降级链路；② **fail-soft**：只把失败节点的**下游**标记 `skipped`，无关分支继续跑，最后合并部分成功——适合检索、摘要、多源查询；③ **降级（fallback）**：失败节点用备用工具/缓存值替代，图上相当于换一条边。并行度由 DAG 的**层宽**决定（同一波次可并发的节点数），不是由线程池大小决定；线程池只设上限，真正的并发上限是"当前就绪且互不依赖的节点数"。
- **取舍**：fail-fast 语义清晰、资源回收快，但会浪费无关分支已经付出的 token/调用成本；fail-soft 利用率高，但**部分成功的合并很危险**——下游如果默认"所有字段都有值"，缺失字段会变成幻觉或静默 0。正确做法是让合并结果携带**每个字段的来源与状态**（`{field: (value, status)}`），下游必须显式处理 `skipped`，不能 `dict.get(k, default)` 一把梭。另外，"取消"在工具调用里不等于"停止计费"：HTTP 请求可能已经到了服务端，取消只是本地不再等待，必须用幂等键防重复副作用（Q7598 的重复执行事故）。
- **实战**：一个"竞品分析"Agent 并发调用搜索、财报、新闻三个工具，再汇总。某次搜索超时，代码用了 fail-fast，把已经成功的财报和新闻也丢了，用户看到"分析失败"；改成 fail-soft 后，汇总 prompt 里明确写"搜索数据缺失，仅基于财报与新闻"，并在输出里标注来源缺口。另一条"下单"链路保持 fail-fast，因为库存扣减失败后继续支付会造成资损。两条链路共用同一个调度器，但**失败策略是每个 DAG 的元数据**，不是全局配置。

下面用波次调度模拟同一张 DAG 在两种策略下的节点状态与并行度。

```python
# 工具 DAG: 波次并行 + fail-fast / fail-soft 的失败传播
from collections import defaultdict

TASKS = {
    "A": [],
    "B": ["A"],
    "C": ["B"],
    "D": ["A"],
    "E": ["D"],
    "F": ["C", "E"],
    "G": [],                 # 与 B 分支无关的独立任务
}
FAIL = {"B"}                 # B 失败


def run(policy):
    status = {}
    remaining = dict(TASKS)
    waves = []
    while remaining:
        ready = [t for t, deps in remaining.items()
                 if all(d in status for d in deps)]
        if not ready:
            break
        waves.append(sorted(ready))
        for t in ready:
            deps = TASKS[t]
            if any(status[d] != "ok" for d in deps):
                status[t] = "skipped"
            elif t in FAIL:
                status[t] = "failed"
            else:
                status[t] = "ok"
            remaining.pop(t)
        if policy == "fail_fast" and "failed" in status.values():
            for t in list(remaining):
                status[t] = "cancelled"
            remaining.clear()
    return status, waves


soft, waves_s = run("fail_soft")
fast, waves_f = run("fail_fast")
print(f"[1] 波次(层宽): {waves_s}, 最大并行度 {max(len(w) for w in waves_s)}")
print(f"[2] fail-soft: {soft}")
print(f"[3] fail-fast: {fast}")
assert max(len(w) for w in waves_s) == 2
assert soft["B"] == "failed" and soft["C"] == "skipped" and soft["F"] == "skipped"
assert soft["D"] == "ok" and soft["E"] == "ok" and soft["G"] == "ok"
assert fast["D"] == "ok" and fast["G"] == "ok"       # 同波次在飞的来不及取消
assert fast["C"] == "cancelled" and fast["E"] == "cancelled" and fast["F"] == "cancelled"
print("    → 实测 soft 保住无关分支; fast 只能取消'还没开始'的节点, 同波次在飞的照常完成")

# 部分成功合并: 每个字段带状态, 下游不能默认有值
results = {"search": ("", "skipped"), "finance": ("营收+18%", "ok"),
           "news": ("发布新品", "ok")}
usable = {k: v for k, (v, s) in results.items() if s == "ok"}
missing = [k for k, (_, s) in results.items() if s != "ok"]
print(f"[4] 合并: 可用 {list(usable)}, 缺失 {missing}")
assert "search" in missing and len(usable) == 2
print("    → 实测 合并结果必须携带状态; dict.get(k, '') 会把'没查到'伪装成'查到空'")

# 取消的代价: 已发出的调用仍可能产生副作用, 需要幂等键
inflight = ["D", "E"]
side_effects = {t: f"effect:{t}" for t in inflight}
retried = {t: f"effect:{t}" for t in inflight}      # 重试同键
assert side_effects == retried
print("[5] 取消后重试: 幂等键相同 -> 副作用不重复, 但计费可能发生两次")
print("    → 实测 并发上限由层宽决定, 失败语义由 DAG 元数据决定, 二者不能混为一谈")
```

**追问一**：已经在飞的节点，fail-fast 真的能"取消"吗？—— 多数执行器只能做到"不再等待 + 标记 cancelled"，底层 HTTP/gRPC 请求未必能中断；即使连接断了，服务端可能已经执行。所以取消的语义是**本地放弃**，不是**远端回滚**。对写操作必须靠幂等键（step_id + 业务键）保证重试不重复；对读操作取消是安全的，最多浪费一次调用。设计 DAG 时要把节点标成 `read_only` / `write`，写节点不参与"可随意取消"的并发编排。

**追问二**：并行度是不是越高越好？—— 不是。并行度受三个约束：① **层宽**（DAG 结构决定的理论上限）；② **下游限流**（外部 API 的 QPS/并发配额，超了会 429，反而更慢）；③ **上下文预算**（并发结果都要塞进 prompt，N 个长结果会撑爆窗口）。工程做法是给每个工具配"并发信号量 + 超时 + 结果截断"，调度器按 `min(层宽, 工具配额, 预算允许)` 决定实际并发。盲目开大线程池只会把限流错误放大成重试风暴。

## 背诵要点

- 节点四态：ok/failed/skipped/cancelled；fail-fast 取消全部未完成，fail-soft 只 skip 下游、保留无关分支。
- 并行上限 = min(DAG 层宽, 工具并发配额, 上下文预算)；线程池大小只是上限，不是并行度。
- 部分成功合并必须带字段级状态；取消不等于远端回滚，写操作要靠幂等键防重复副作用。

## 复盘追问

- B 失败后 C 和 G 的命运为什么不同？（C 依赖 B → skipped；G 无依赖 → fail-soft 下继续 ok，fail-fast 下被 cancelled）
- 为什么不能用一个全局开关决定 fail-fast 还是 fail-soft？（同一 Agent 里查询类可降级、下单类不可降级；策略应挂在 DAG/任务元数据上）
