### Q7542 · 事故复盘：工具超时后 Agent 重试，客户被退款了两次

> 难度:★★★★ | 标签:事故复盘, 幂等, Agent 工具

**问**：Agent 调用"退款"工具，下游支付服务响应慢，客户端 10 秒超时后 Agent 判定失败并重试，结果客户被退了两次款。超时 ≠ 失败的原因是什么？Agent 侧工具调用的幂等设计怎么落地？"查询-确认-重试"的恢复协议怎么写？

**答**：结论：超时只是"调用方放弃等待"，**服务端可能仍在执行且终将成功**——对有副作用的工具（退款、下单、发消息），超时后重试就是把一次成功执行变成两次。防线三层：**工具调用带幂等键**（服务端按键去重）、**超时后先查询后重试**（用幂等键查结果而不是盲发）、**副作用工具与只读工具分类治理**（只读可随便重试，副作用必须走幂等协议）。

机理与实战：
- **超时误判的语义**：timeout 是客户端视角的三态之外的第四态——成功/失败/未知。Agent 框架里如果超时被简单映射为"工具失败"，LLM 会基于错误事实推理（"退款失败，我再试一次"），错误事实 → 错误决策 → 副作用重复，这是 Agent 系统独有的事故形态。
- **幂等键协议**：每次工具调用生成 `idempotency_key = agent_run_id + step_index + tool_name + 参数哈希`，放进请求头；服务端把 key 与结果一起持久化，同 key 重复请求直接返回首次结果（支付/退款类 API 的标准做法）。注意 key 必须跨重试稳定——放在"逻辑步骤"级别而不是"HTTP 请求"级别。
- **恢复协议**：超时 → 状态置 unknown → 用幂等键调用"查询工具"（只读）→ 查到成功/失败按事实继续推理，查不到且超龄则人工介入。恢复协议要写进 Agent 的工具结果语义里（unknown ≠ failure），否则 LLM 依然会按失败处理。
- **工具分类治理**：只读（查询/检索）可重试；副作用（写库/付款/发消息）必须幂等键+查询恢复；长任务（训练/导出）改异步作业模型（提交任务 ID → 轮询状态），彻底绕开超时三态问题。

```python
# 基线:Python 3.10+;纯标准库,幂等键工具调用与"查询-确认-重试"恢复协议
from __future__ import annotations
import hashlib
import json
from dataclasses import dataclass, field


@dataclass
class ToolServer:
    """模拟带幂等去重的服务端。"""
    executed: dict[str, str] = field(default_factory=dict)

    def execute(self, idem_key: str, payload: dict) -> tuple[str, dict]:
        """返回 (status, result);同 key 直接回放首次结果。"""
        if idem_key in self.executed:
            return "replayed", {"amount": self.executed[idem_key]}
        # 真实执行(带副作用)
        self.executed[idem_key] = payload["amount"]
        return "executed", {"amount": payload["amount"]}

    def query(self, idem_key: str) -> str | None:
        """恢复协议用:只读查询幂等键对应的执行结果。"""
        return self.executed.get(idem_key)


def idem_key(run_id: str, step: int, tool: str, args: dict) -> str:
    """幂等键绑定逻辑步骤而非 HTTP 请求。"""
    blob = json.dumps({"r": run_id, "s": step, "t": tool, "a": args},
                      sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(blob.encode()).hexdigest()[:16]


@dataclass
class Outcome:
    status: str   # ok / failed / unknown
    detail: str = ""


def call_tool(server: ToolServer, key: str, args: dict,
              timeout_s: float = 0.05) -> Outcome:
    """模拟一次可能超时的调用;超时返回 unknown 而非 failed。"""
    # 模拟:首次调用慢于超时,服务端最终成功
    import time
    start = time.time()
    status, result = server.execute(key, args)
    if time.time() - start > timeout_s:  # 演示中恒 False,真实场景由 HTTP 超时触发
        return Outcome("unknown")
    return Outcome("ok", json.dumps(result, ensure_ascii=False))


def recover(server: ToolServer, key: str, args: dict, tries: int = 3) -> Outcome:
    """查询-确认-重试协议:先查后重试,绝不盲发。"""
    for _ in range(tries):
        found = server.query(key)
        if found is not None:
            return Outcome("ok", f"查询确认已执行:{found}")
    # 查无结果且确认未执行 -> 才允许带同一幂等键重发
    status, result = server.execute(key, args)
    return Outcome("ok" if status in ("executed", "replayed") else "failed",
                   f"{status}:{result}")


def demo() -> None:
    server = ToolServer()
    key = idem_key("run-1", 3, "refund", {"order": "A1", "amount": "99"})
    # 事故对照:误把超时当失败,用新 key 重发 -> 两次执行
    k2 = idem_key("run-1", 3, "refund", {"order": "A1", "amount": "99"})  # 同步骤应同 key
    o1 = call_tool(server, key, {"order": "A1", "amount": "99"})
    o2 = call_tool(server, k2, {"order": "A1", "amount": "99"})
    assert o1.status == "ok" and o2.status == "ok"
    # 服务端同 key 去重:replayed,只退一次
    r = server.query(key)
    assert r == "99"
    assert len(server.executed) == 1
    # 恢复协议:结果丢失后按 key 查询确认,不盲发
    server2 = ToolServer()
    k3 = idem_key("run-2", 1, "refund", {"order": "B2", "amount": "50"})
    server2.execute(k3, {"order": "B2", "amount": "50"})
    rec = recover(server2, k3, {"order": "B2", "amount": "50"})
    assert "查询确认" in rec.detail and len(server2.executed) == 1
    print("工具三态:超时=unknown≠failed;幂等键去重 + 查询确认恢复 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：LLM 本身不管理幂等键，框架层怎么保证"重试用同一个 key"？
答：幂等键由框架在"逻辑步骤"层生成并缓存：Agent 循环里每次决定重试时查缓存复用，只有进入新步骤（新的 tool call 决策）才生成新 key。同时把 key 写进工具调用日志，trace 里可见——这样重放/补偿也有据可查。若让 LLM 自由发挥（自己生成参数），参数漂移会导致 key 变化去重失效，所以框架要对"重试路径"锁定参数。

**追问二**：为什么长任务要改成异步作业模型而不是加长超时？
答：加长超时只是把 unknown 窗口拉大，且占用连接资源；作业模型把"执行"变成"提交+轮询"：提交立即返回 job_id（幂等键天然就是 job_id），Agent 在后续步数预算内轮询状态，超时只影响轮询不影响任务本身。这个模型把超时从"结果未知"降级为"状态未就绪"，语义干净，是所有 >30s 工具的推荐形态。

## 背诵要点
- 超时是第四态 unknown，不是 failed：副作用工具超时后盲重试 = 副作用重复执行；Agent 框架必须把 unknown 语义传给 LLM。
- 幂等键绑定逻辑步骤（run_id+step+tool+参数哈希），服务端按 key 去重回放；重试路径由框架锁定参数，防 LLM 参数漂移导致去重失效。
- 恢复协议：超时 → 只读查询幂等键 → 确认未执行才同 key 重发；>30s 工具一律改异步作业模型（提交 job_id + 轮询）。

## 复盘追问
- 为什么那次事故的"退款两次"直到对账才发现？（提示：工具层日志记了两次"成功"（一次真实一次重放被当作新成功），而幂等回放与真实执行在日志上无区分；服务端必须区分 executed/replayed 状态并单独上报，对账也要按幂等键聚合）
- 只读工具真的可以随便重试吗？（提示：只读但非幂等语义的例外——如"获取下一个待办"（队列消费）本质是副作用；工具分类要按"是否有可观测状态变化"而非表面读法，分类错误会造成任务双取）
