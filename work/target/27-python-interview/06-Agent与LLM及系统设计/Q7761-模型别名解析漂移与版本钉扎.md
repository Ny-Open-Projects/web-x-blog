### Q7761 · 配置里的 gpt-4 突然变聪明了：模型别名解析漂移与版本钉扎

难度：P6 ｜ 标签：模型别名、版本钉扎、评测基线、配置治理、供应商演进

基线：Python 3.12；实现别名注册表与解析快照，演示别名漂移导致评测基线实际换了模型，全标准库实跑。

**问**：评测基线是三个月前用配置里的 `model=gpt-4` 跑的，今天重跑同样的评测集与参数，分数整体漂了 4 个点——提示词没改、temperature 没变。查了半天发现供应商把 `gpt-4` 这个别名**静默指向了新快照版本**。别名（alias）与快照版本（snapshot）的关系该怎么管理？评测与生产分别该用哪个？

**答**：
- **结论**：模型 API 的 model 参数分两层：**别名**（`gpt-4`、`claude-sonnet-4`）是供应商维护的"始终指向最新稳定版"的可变指针；**快照版本**（`gpt-4-0613`）是不可变的具体版本。别名漂移是评测口径的隐形杀手：基线用别名跑、复测还用别名跑，中间供应商更新指向，等于**A/B 测了两个模型却以为在测同一模型**（Q7759 的方差治理管不了这种"模型本身换了"的系统性漂移）。管理规则三条：① **评测与基线一律钉快照版本**，别名只在"永远要最新"的探针评测里用；② **别名解析落日志**：每次调用记录"请求别名 → 响应头/文档里的实际版本"，漂移可检测（很多供应商在响应头带 `x-*-*version` 或 usage 里的版本字段）；③ **生产可以用别名**（跟随供应商迭代是价值），但生产与评测的模型选择必须显式分离配置，禁止共用同一份 model 字段（Q7680 默认参数漂移的姊妹问题）。
- **取舍**：① 钉快照的代价：旧快照会被供应商弃用（deprecation 有 clock，Q7687 迁移窗口），钉住意味着要主动管理升级——用"别名探针评测"定期探测新快照，确认无回归后人工切；② 漂移检测的盲区：并非所有供应商都暴露响应版本，检测不到时的兜底是**金丝雀评测集**（固定小样本+固定期望，分数突变即告警）；③ 自建网关可以做"别名到快照"的内部解析层：配置统一写别名，网关按策略解析成快照并记录——把漂移点收拢到一处；④ 评测报告必须带模型版本字段，缺版本的结果不可比。
- **实战**：① 配置分层：`model_alias`（生产用）与 `model_snapshot`（评测用）两个键，禁止混用；② 每次评测输出头部打印模型快照，报告模板带版本列；③ 快照弃用通知（供应商邮件/changelog）进值班日历，提前 30 天发起基线重测；④ 双跑对拍（Q7548）的模型版本钉扎检查前置——两边版本不同的对拍没有意义。

```python
"""模型别名解析漂移: 别名指针 -> 快照版本, 评测基线的系统性漂移。"""
from dataclasses import dataclass, field


@dataclass
class AliasRegistry:
    """供应商侧: 别名 -> 快照的指向 (会随时间被更新)。"""
    mapping: dict[str, str] = field(default_factory=dict)

    def resolve(self, alias: str) -> str:
        return self.mapping[alias]

    def retarget(self, alias: str, new_snapshot: str) -> str:
        old = self.mapping.get(alias)
        self.mapping[alias] = new_snapshot
        return f"别名 {alias}: {old} -> {new_snapshot} (静默漂移)"


@dataclass
class EvalRunner:
    """评测器: 记录每次评测实际解析到的版本。"""
    runs: list = field(default_factory=list)

    def run(self, name: str, model_param: str, registry: AliasRegistry,
            pin_snapshot: bool, score: float) -> None:
        actual = (model_param if pin_snapshot else registry.resolve(model_param))
        self.runs.append({"name": name, "param": model_param,
                          "actual": actual, "score": score})

    def compare(self, base: str, new: str) -> str:
        b = next(r for r in self.runs if r["name"] == base)
        n = next(r for r in self.runs if r["name"] == new)
        drift = (b["actual"] != n["actual"])
        delta = n["score"] - b["score"]
        if drift:
            return (f"{b['actual']} vs {n['actual']} -> 模型漂移! 分数差 "
                    f"{delta:+.1f}pp 是版本差异而非提示词效果, 结论无效")
        return f"同快照 {b['actual']}, 分数差 {delta:+.1f}pp -> 可归因"


if __name__ == "__main__":
    reg = AliasRegistry({"gpt-4": "gpt-4-0613"})

    runner = EvalRunner()
    # 三个月前: 基线评测, 配置写别名 (未钉快照)
    runner.run("baseline", "gpt-4", reg, pin_snapshot=False, score=82.0)
    # 供应商静默更新别名指向
    print(reg.retarget("gpt-4", "gpt-4-1125"))
    # 今天: 复测同提示词同参数
    runner.run("rerun", "gpt-4", reg, pin_snapshot=False, score=78.0)
    print(f"未钉快照对比: {runner.compare('baseline', 'rerun')}\n")

    # 正确姿势: 评测钉快照版本
    runner2 = EvalRunner()
    runner2.run("baseline", "gpt-4-0613", reg, pin_snapshot=True, score=82.0)
    runner2.run("rerun", "gpt-4-0613", reg, pin_snapshot=True, score=81.6)
    print(f"钉快照对比:   {runner2.compare('baseline', 'rerun')}")

    # 探针评测: 用别名感知供应商更新 (合法用法)
    probe_version = reg.resolve("gpt-4")
    changed = probe_version != "gpt-4-0613"
    print(f"\n别名探针: 当前指向 {probe_version} -> "
          f"{'发现新快照, 发起对拍评审后再切换基线' if changed else '无更新'}")
    ok = runner.runs[0]["actual"] != runner.runs[1]["actual"]
    print(f"校验: 别名漂移被解析记录捕获 -> {'通过' if ok else '异常'}")
    print("\n结论：评测钉快照、生产用别名、两者配置显式分离;")
    print("      每次调用记录'别名->实际版本', 漂移可检测才可归因")
```

**追问一**：供应商不提供响应版本字段时，怎么检测别名漂移？

→ 解析：三层兜底。① **金丝雀评测**：固定 30~50 条样本 + 固定输出期望（截断到前 N token 的哈希或语义指纹），每天跑一次；分数/指纹突变先于用户反馈发现漂移——注意与 Q7759 的方差治理结合：金丝雀跑 3 次取区间，避免把采样噪声当漂移。② **行为指纹**：对固定输入记录结构特征（输出长度分布、JSON 键集合、拒答率），漂移常表现为这些分布的整体平移。③ **外部信号**：供应商 changelog/状态页的订阅进值班信息流，用户报告"回答风格变了"的工单按时间聚类——聚类时间点与金丝雀突变点重合即可确认。三层都命不中的漂移确实存在（供应商内部微调不公告），这就是为什么重大基线对拍（Q7548）必须在同一天双跑，时间窗拉近能消掉大部分隐性漂移。

**追问二**：生产用别名跟进新版本，怎么避免"新版本质量回退直接伤生产"？

→ 解析：别名跟进要配**回退保险**：① 网关解析层支持即时切换——生产配置写别名，但网关保留"别名→上一个已知良好快照"的映射，出事一条配置回退（降级链 Q1172 的模型维度应用）；② 新快照上线先用灰度流量验证：网关把 5% 流量发新快照、95% 留旧快照，对比质量指标（拒答率、用户点踩率、人工抽检）再全量（Q1781 灰度思路的模型版本应用）；③ 每次供应商公告的版本更新走轻量评审：金丝雀评测 + 抽 20 条真实流量人工对拍，成本半小时，换来的是不至于某天用户集体发现"AI 变笨了"而运维一脸茫然。别名是便利，便利的代价是主动治理——不治理的别名等于把生产质量交给供应商的发布节奏。
