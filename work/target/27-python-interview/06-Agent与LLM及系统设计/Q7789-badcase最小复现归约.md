### Q7789 · badcase 二十轮对话没法归因：最小复现归约与 prompt 反例缩小

难度：P7 ｜ 标签：最小复现、反例缩小、badcase归因、变异不变性、评测集治理

基线：Python 3.12；实现"badcase 缩小器"（delta-debugging 思想）：对长对话/长 prompt 的上下文做删除变异，保留失败不变的最小子集，与"整例重跑归因"的成本对比，全标准库实跑。

**问**：一个 20 轮对话的 badcase，上下文 3 万 token，工程师拿到手只能"看着猜"——是哪条历史消息、哪段检索内容、哪条系统规则触发的？delta-debugging 式的最小复现归约怎么用在 prompt 上？归约过程中失败判定"不变"怎么保证（模型输出的随机性怎么办）？缩小后的反例怎么进入评测集治理？

**答**：
- **结论**：最小复现归约把"3 万 token 的失败现场"压缩到"几百 token 的最小触发集"——归因成本从读长对话降到读一小段，而且最小反例往往直接暴露病因（缩到只剩"系统规则某一条 + 一条检索片段"时，病灶一目了然：是规则冲突还是检索污染）。算法骨架（delta debugging 的 ddmin 思想）：① 把上下文拆成可删除单元（每轮消息、每条检索片段、每条规则——粒度是归约的关键，太粗缩不动太细轮次爆炸）；② 迭代变异：把单元集切成 2 的 n 次幂子块，逐块删除，每次删除后重跑失败判定——失败保持则保留删除（上下文更小），失败消失则回滚；③ 直到无法再删（最小反例）。失败判定的稳定性是第一坑：模型输出有随机性（temperature>0），"失败不变"必须以**行为断言**（错误类别一致：都触发了同样的违规/同样的错误工具）而不是**文本全等**判定，且关键判定用多次采样多数投票（n=3~5）压随机性。成本账：ddmin 轮次 O(k·log k)（k=单元数），每轮一次判定调用——20 轮对话 40 个单元约 40~80 次判定调用，比"工程师读 3 万 token + 反复试"的隐性成本便宜且可自动化；对线上推理有配额压力时用确定性回放（temperature=0 专用复现实例）优先。
- **取舍**：① 单元粒度的选择：消息级是默认；怀疑检索片段时切片段级；怀疑规则时切规则子句级——按归因假设选粒度，一版归约出方向后再细粒度二轮归约；② 归约的语义保持：删除上下文单元可能改变任务定义（删掉用户的任务描述，什么都会"失败"或"成功"，归约结果失去意义）——**不可删单元**要标记（当前用户消息、系统规则骨架），变异只作用于"可删白名单"；③ 失败判定器即归因假设：判定器写什么，归约就找什么——判定器太宽（任何 bad 行为都算）找到的是"任意触发集"，太窄（精确到错误文本）在随机性下不收敛；正确姿势是先用分类器化的宽判定（错误类别）缩，再人工确认；④ 缩小反例的泛化风险：最小反例是"最脆弱的触发组合"，直接进评测集可能过拟合（修好这一例不代表修好同类）——反例进集前要做**同类泛化检查**（同病灶的其他样本也失败吗），并标注病灶类别（Q1783 坏例回流的分类维度）。
- **实战**：① 归约流水线自动化：badcase 入库（Q7537 快照）→ 自动归约任务 → 最小反例 + 归因假设报告，工程师接手时看到的是"3 个单元的最小反例"而不是 20 轮对话；② 归约结果与仓库联动：最小反例直接转成评测用例（prompt + 期望断言），修复 PR 必须带"反例转绿"证据；③ 缩小过程的副产品：每次"删除后失败消失"的单元就是**病因候选**，多个 badcase 的病因候选聚类（按片段指纹）能发现系统性问题（某类检索内容是惯犯 Q1506 归类同族）；④ 随机性的工程兜底：归约环境固定 temperature=0 + 固定 seed（模型支持时）+ 复现实例独立部署（不与线上抢配额，Q7631 评测跑批错峰同族）。

```python
"""Q7789 badcase 最小复现归约: delta-debugging 删除变异 + 行为断言判定。"""


def trigger_risky(unit_ids: set[str]) -> bool:
    """模拟模型行为: 只有特定组合(规则r2 + 片段d3)才触发错误."""
    return "r2" in unit_ids and "d3" in unit_ids


UNITS = ["r1", "r2", "m1", "m2", "m3", "d1", "d2", "d3", "d4"]   # 规则/消息/片段
KEEP = {"m3"}        # 不可删单元(当前用户消息)


def ddmin(units: list[str], failing, keep: set[str]) -> set[str]:
    """ddmin: 逐块尝试删除(白名单单元不可删), 失败保持则保留删除."""
    cur = set(units)
    n = 2
    while n <= len(cur - keep):
        chunks = _split(sorted(cur - keep), n)
        removed = False
        for chunk in chunks:
            trial = cur - set(chunk)
            if trial and failing(trial):
                cur = trial
                removed = True
                n = 2                       # 集合变了, 回到粗粒度重切
                break
        if not removed:
            n *= 2
    return cur | keep


def _split(items: list[str], n: int) -> list[list[str]]:
    k = max(1, len(items) // n)
    return [items[i:i + k] for i in range(0, len(items), k)] or [[]]


if __name__ == "__main__":
    full = set(UNITS)
    assert trigger_risky(full), "原始现场应复现失败"
    mini = ddmin(UNITS, trigger_risky, KEEP)
    print(f"原始上下文: {len(UNITS)} 个单元 {sorted(UNITS)}")
    print(f"最小触发集: {len(mini)} 个单元 {sorted(mini)} (含不可删 {sorted(KEEP)})")
    print(f"归约率: {1 - len(mini) / len(UNITS):.0%}  <- 归因只需看 {sorted(mini)}")
    # 验证: 可删单元再删任意一个即不再触发(真正最小)
    truly_minimal = all(not trigger_risky(mini - {u}) for u in mini - KEEP)
    keep_ok = KEEP <= mini
    print(f"最小性: 可删单元删任一即不触发={truly_minimal}, 白名单保全={keep_ok}")
    ok = (mini == {"r2", "d3", "m3"} and truly_minimal and keep_ok)
    print(f"校验: 归约到病灶组合 + 最小性 + 白名单保全 -> {'通过' if ok else '异常'}")
    print("结论：badcase 归因先归约再归因: ddmin 删除变异, 行为断言抗随机;")
    print("      最小反例暴露病灶组合, 进评测集前做同类泛化检查防过拟合")
```

**追问一**：模型输出有随机性，归约的失败判定怎么设计才能既稳定又不把"随机犯错"误判为"触发失败"？判定器分层怎么落？

→ 解析：判定设计的核心是把"失败"从**文本事件**提升为**行为断言**：① **判定分层**——L1 结构断言（输出是否 JSON 合法/是否调了禁用工具/是否包含 PII，确定性高）；L2 类别断言（错误类别一致：都是"编造了不存在的产品名"——用分类器/规则归类而非文本全等）；L3 语义断言（答案与金标偏离程度，需要人工或 judge）——归约用 L1/L2，L3 留给最终确认；② **采样稳定化**：temperature=0 优先（多数模型 0 温度仍非完全确定但方差大幅缩小），判定用 n 次采样多数投票（n=3，同类 ≥2 算失败），单次判定成本 ×3 换判定稳定性；③ **随机犯错的边界**：模型在无关上下文下也可能随机触发同类错误——归约判定的含义要明确为"删除后触发率显著下降"而不是"删除后为零"，严格版用触发率比较（删除前后各采 5 次，触发率下降即保留删除），宽松版多数投票即可；成本敏感时宽松版起步，归约出候选后再严格复核；④ **判定器漂移**：判定器是规则/分类器，本身有版本——归约结果要记录判定器版本（golden 同源纪律 Q7277），判定器升级后关键反例要复归约。本质认知：**归约的可靠性上限 = 失败判定的可靠性，随机生成场景下任何"不变性"都是统计意义的不变——工程上要做的是让判定便宜、可重复、可复验，而不是追求绝对确定。**

**追问二**：最小反例直接进评测集有什么过拟合风险？"修复通过"的证据怎么才算充分？

→ 解析：三层风险与对应的证据标准：① **脆弱触发风险**：最小反例是"恰好触发的最小组合"，修复策略若只针对这个组合（加一条规则禁掉这句话），同病灶换个说法立刻复发——证据要求**病灶级验证**：修复 PR 除了反例转绿，还要跑"同类扩展集"（同病灶的其他 5~10 个自然变体，可由反例人工/模型扩写），全部转绿才算修复；② **回归面风险**：修复动作（改规则/改检索过滤）可能把原来正确的 case 弄坏——证据要带**回归集全跑**（评测集全量 + 分数不降），坏例修复掩盖全盘劣化是最常见的假修复（Q7607 评测集治理的同族纪律）；③ **评测集污染风险**：反例带着"病灶指纹"进了评测集，后续模型迭代可能**背会**这些特定样本（评测分数涨、真实能力不变，Q7607 评测泄漏）——缓解三招：反例进"保留集"（不进日常回归，季度性抽查）、同病灶变体轮换、评测集定期从线上流量滚动补充（Q2988 滚动更新）。归因闭环的组织流程：badcase → 自动归约（最小反例+病因候选）→ 人工确认病灶类别 → 修复 PR（反例转绿 + 扩展集转绿 + 回归集不降）→ 反例归档进保留集——四步每步都有机器可验证的证据，"看起来修好了"不能作为收工标准。总原则：**最小反例是归因工具不是修复终点，它的价值是让修复动作有靶子、让验证证据有基线——过拟合的防线不在反例本身，在验证的广度。**
