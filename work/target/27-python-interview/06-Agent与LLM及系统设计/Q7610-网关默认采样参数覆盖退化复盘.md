### Q7610 · 网关默认采样参数静默覆盖导致输出退化事故复盘

难度：P6 ｜ 标签：事故复盘 / LLM 网关 / 参数治理

**问**：接入统一 LLM 网关后，某分类任务的准确率从 96% 掉到 88%，prompt 没改、模型没换。排查发现网关会为"未显式设置的参数"填默认值（temperature=0.7、top_p=0.9）。一层"贴心"的默认值为什么能造成事故？请求参数应该怎么治理？

**答**：
- **结论**：确定类任务（分类、抽取、评测 judge）依赖低温度采样，温度是**准确率的直接变量**而不是"可调偏好"。事故链：应用层 SDK 只传了 prompt，未传 temperature——网关的"参数补全"填了 0.7；语义缓存/请求指纹（Q2867）也因此把这类请求当作新参数集；更隐蔽的是不同供应商默认值不同（OpenAI 1.0、Anthropic 1.0、部分兼容层 0.7），多路由场景下同一个逻辑请求在不同时刻落在不同参数集上，输出分布漂移，离线评测（低温跑的）与线上（网关默认高温跑的）出现系统性差异。**根因是"参数的默认归属不清晰"**：应用以为没传就用供应商默认，网关以为没传就替你补全。
- **取舍**：参数治理三原则：① **显式即合同**：网关只转发，不补全——未传参数一律透传缺省（让供应商默认生效），或在路由配置里显式声明补全策略并审计；② **按任务模板锁定参数集**：prompt 模板与采样参数打包成一个版本化"配置对象"（见 Q7507 Prompt 版本管理），评测与线上引用同一版本，禁止散落传参；③ **对拍监控**：网关记录每次请求的完整参数指纹，离线评测集抽样重放对拍（Q7583 影子流量），参数漂移即告警。温度对确定性任务的影响还要配合 seed/fixed sampling（部分供应商支持）与自一致性策略权衡：要绝对稳定就 temperature=0 + 幂等缓存，要多样性再开温度。
- **实战**：事故剧本：① 从网关日志 diff 出"参数集变化"时间点与准确率下滑时间对齐；② 应用层所有调用显式传 temperature/top_p（模板层统一）；③ 网关关闭静默补全或把补全策略写进路由配置并版本化；④ 加参数指纹监控：按 (模板版本, 参数集) 分桶看准确率，分桶间 diff 超阈值告警；⑤ 复盘项：供应商迁移/网关升级的 checklist 加入"参数透传一致性验证"（同请求对拍新旧链路输出分布）。

```python
# 请求参数指纹与覆盖检测（标准库模拟网关参数治理）
# 基线：Python 3.9+；真实实现 LLM 网关（LiteLLM/自研）+ 模板配置中心

from dataclasses import dataclass, field

GATEWAY_DEFAULTS = {"temperature": 0.7, "top_p": 0.9}   # 事故源：静默补全
VENDOR_DEFAULTS = {"temperature": 1.0, "top_p": 1.0}


@dataclass
class RouteConfig:
    name: str
    fill_defaults: dict = field(default_factory=dict)   # 空 dict = 纯透传


@dataclass
class Template:
    name: str
    version: str
    params: dict    # 模板层锁定的参数集（合同）


def effective_params(t: Template, route: RouteConfig) -> dict:
    """真实生效参数 = 模板显式参数 ∪ 网关补全（只补模板未设的）"""
    eff = dict(route.fill_defaults)
    eff.update(t.params)     # 模板显式优先
    return eff


def fingerprint(eff: dict) -> str:
    return ",".join(f"{k}={eff[k]}" for k in sorted(eff))


def audit(t: Template, route: RouteConfig, expected_fp: str) -> list[str]:
    eff = effective_params(t, route)
    fp = fingerprint(eff)
    problems = []
    if fp != expected_fp:
        problems.append(f"参数漂移: 实际 {fp} != 期望 {expected_fp}")
    return problems


def main() -> None:
    tmpl = Template("intent-classify", "v3", {"temperature": 0.0, "top_p": 1.0})
    expected = fingerprint({"temperature": 0.0, "top_p": 1.0})

    # 事故路由：网关对未传参数补 0.7/0.9（模板未显式传时生效）
    bad_route = RouteConfig("old-gateway", fill_defaults=dict(GATEWAY_DEFAULTS))
    tmpl_old = Template("intent-classify", "v2", {})   # 旧模板没锁参数 → 被补全
    problems = audit(tmpl_old, bad_route, expected)
    assert problems and "参数漂移" in problems[0]
    print("事故复现:", problems[0])

    # 治理后：模板显式锁定 + 新网关纯透传
    good_route = RouteConfig("new-gateway", fill_defaults={})
    assert audit(tmpl, good_route, expected) == []
    print(f"治理后生效参数: {fingerprint(effective_params(tmpl, good_route))}")

    # 多供应商默认值差异提示：透传时各 vendor 默认不同，模板锁定是唯一解
    for v, d in (("openai", VENDOR_DEFAULTS), ("compat-layer", GATEWAY_DEFAULTS)):
        print(f"  {v} 默认 {d} —— 未锁定参数时输出分布随路由漂移")
    print("OK: 参数治理三原则——显式即合同/模板锁定/指纹对拍")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"temperature=0 就完全确定"这个说法也不严谨？
→ 一句话提示：温度 0 是贪心解码（每步取最大 logit），但 MoE 路由、浮点非结合性、批处理位置、供应商侧负载均衡的数值差异都会造成输出抖动；绝对确定要靠缓存/幂等设计而不是采样参数。

**追问 2**：参数指纹监控里怎么处理"供应商新参数"？
→ 一句话提示：指纹按白名单参数集计算，出现白名单外的键即告警（可能是供应商加参或 SDK 变化）——把"参数面变化"当作和模型版本变更同级的事件对待（呼应 Q7548 双跑对拍）。

## 背诵要点
- 采样参数是准确率的直接变量：确定类任务必须显式锁 temperature/top_p；网关静默补全 + 多供应商默认值不同 = 输出分布漂移。
- 治理三原则：显式即合同（网关纯透传）、prompt 模板与参数打包版本化、参数指纹按桶对拍监控。
- temperature=0 也非绝对确定，绝对稳定靠缓存/幂等；参数面变化与模型版本变化同级对待。

## 复盘追问
- 离线评测为什么没拦住这次退化？提示：评测环境直连供应商（低温度生效）而线上走网关（被补全）——评测与生产的链路参数不一致；评测必须复用与生产完全相同的调用封装与路由配置。
- 网关"补全默认值"的合理场景是什么？提示：全局兜底（超时/重试上限）、公司级安全策略（如强制脱敏）；但采样语义类参数必须白名单化并审计，补全范围越窄越好。
