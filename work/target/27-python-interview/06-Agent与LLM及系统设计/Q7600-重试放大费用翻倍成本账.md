### Q7600 · 重试放大：网关重试叠加客户端重试的费用翻倍成本账

难度：P7 ｜ 标签：LLM 网关 / 重试 / 成本工程

**问**：某晚上游模型 API 5xx 率升高，总调用量（计费请求数）反而涨到平时 3 倍，费用翻倍——用户请求量并没有变化。重试是怎么把故障放大的？重试策略怎么设计才不会互相叠加？

**答**：
- **结论**：重试放大 = 各层重试次数的乘积：客户端 SDK 重试 3 次 × Agent 框架重试 2 次 × 网关对上游重试 2 次 = 一次用户请求最多打 12 发，且 5xx 升高时每一发的失败率都更高，重试消耗与故障强度成正比放大——故障越重，费用越高，还把本已过载的上游打死（重试风暴的正反馈）。叠加的根源是"每层都不知道别的层在重试"：SDK 默认重试、tenacity 装饰器、网关 failover、上层 Job 级重试各管各的。设计原则：**全链路只允许一个重试点**（通常在网关层统一做），客户端禁用 SDK 内置重试（`max_retries=0`）改由网关响应决定；重试必须区分"可重试错误"（429/5xx 按退避）与"不可重试"（400 参数错误、401），且上游过载（429/529）时重试预算要收缩而不是扩张（熔断联动）。
- **取舍**：重试 vs 降级的切换点：重试是"同一模型再试"，降级是"换模型/换供应商"，5xx 持续超过阈值（如 30 秒）就该从重试切降级——重试解决瞬时抖动，解决不了容量故障。预算维度：每个请求要有"总尝试数上限 + 总 token 花费上限"，网关按请求粒度记账，超限即返回降级响应而不是继续烧。
- **实战**：事故剧本：① 全链路盘点重试点（SDK/tenacity/网关/Job 层），收敛为网关单点；② 网关按"错误类别 × 指数退避 + 抖动"实现统一重试，429 读 Retry-After；③ 加请求级花费上限与全局重试比例熔断（重试请求占比 > 50% 触发降级）；④ 复盘项：监控"计费请求数 / 用户请求数"的放大系数，1.2 是警戒线——它是重试健康度的直接指标。

```python
# 重试放大系数计算与统一重试决策器（纯标准库）
# 基线：Python 3.9+

def amplification(layers: list[int], base_error_rate: float) -> float:
    """放大系数 = Π(每层最大尝试数)，故障下每层独立重试"""
    total = 1.0
    for tries in layers:
        total *= tries
    return total


def effective_cost(layer_tries: list[int], error_rate: float,
                   price_per_call: float) -> dict:
    """期望调用次数：每层独立重试，失败才进下一发（乘性放大）"""
    import math
    k = math.prod(layer_tries)
    # 期望次数 = Σ_{i=0}^{k-1} p^i = (1-p^k)/(1-p)
    p = error_rate
    expected = (1 - p ** k) / (1 - p) if p < 1 else k
    return {"max_calls": k, "expected_calls": round(expected, 2),
            "cost_x": round(expected / 1, 2),
            "billed_usd_per_user_req": round(expected * price_per_call, 4)}


def retry_decision(status: int, retried: int, max_retries: int = 3,
                   gateway_only: bool = True) -> str:
    """网关单点重试决策；客户端收到的是最终裁决"""
    if not gateway_only:
        return "FORBID: 客户端不允许自行重试，统一交网关"
    if retried >= max_retries:
        return "FALLBACK: 超预算，走降级"
    if status in (429, 529, 500, 502, 503, 504):
        return f"RETRY#{retried + 1}: 指数退避+抖动"
    return "FAIL: 4xx 参数/鉴权类错误不重试"


def main() -> None:
    # 三层各自重试 3/2/2 次 → 最多 12 发
    amp = amplification([3, 2, 2], 0.5)
    print("放大上限:", amp)
    assert amp == 12
    c = effective_cost([3, 2, 2], error_rate=0.5, price_per_call=0.02)
    print(c)
    assert c["max_calls"] == 12 and c["expected_calls"] > 1.9
    # 收敛为网关单点 3 次
    c2 = effective_cost([4], error_rate=0.5, price_per_call=0.02)
    assert c2["max_calls"] == 4 and c2["expected_calls"] < c["expected_calls"]
    assert "RETRY#1" in retry_decision(429, 0)
    assert "FALLBACK" in retry_decision(500, 3)
    assert "FAIL" in retry_decision(400, 0)
    assert "FORBID" in retry_decision(429, 0, gateway_only=False)
    print("OK")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 429 的重试要尊重 Retry-After 而不是用本地退避？
→ 一句话提示：Retry-After 是服务端根据自身容量给出的恢复时间估计，本地指数退避可能比它激进（继续撞墙）也可能保守（浪费时间）；但也要设本地最大等待上限防止被恶意拉长。

**追问 2**：重试比例熔断（retry ratio breaker）和普通错误率熔断有什么区别？
→ 一句话提示：错误率熔断看失败率，但在"上游慢但能成功"的场景不触发；重试占比反映的是"系统靠重试在续命"的真实压力，占比飙升说明重试预算即将失控，要提前降级——它是更早的预警信号。

## 背诵要点
- 放大系数 = Π 各层重试次数；3×2×2=12 发/请求，故障时费用与失败率同向放大成正反馈。
- 全链路单重试点原则：客户端 max_retries=0、网关统一"错误分类 × 指数退避 + 抖动 + Retry-After 尊重 + 花费上限"。
- 监控放大系数（计费请求数/用户请求数）警戒线 ~1.2；5xx 持续 >30s 从重试切降级。

## 复盘追问
- 为什么"指数退避 + 抖动"里的抖动（jitter）不可省略？提示：无抖动时所有客户端在相同时间点齐发重试（thundering herd），把恢复中的上游再次打挂；full jitter（随机 0~上限）是最抗同步化的选择。
- 请求级"总 token 花费上限"怎么实现才准确？提示：流式响应中途失败已消耗的 input token 无法退还，网关要按"已计费部分累计"记账，重试前先估算最大可能花费（max_tokens + 前缀），超预算直接降级。
