### Q7760 · 月度可用性 99.5% 谁说了算：SLA 分母口径与错误分类

难度：P6 ｜ 标签：SLA、可用性、错误分类、分母口径、外部依赖

基线：Python 3.12；实现请求日志的错误分类器与双分母口径的可用性计算，演示一次故障在两种口径下的结论差异。

**问**：LLM 应用给客户承诺月度可用性 99.5%，月底一算：99.8% 达标；客户算出来 98.9% 违约。两边都"没造假"——分母和分子口径不同。哪些请求该进分母？供应商（模型 API）故障算谁的？客户端取消和超时怎么分类？一份可对账的 SLA 口径应该怎么写？

**答**：
- **结论**：可用性 = 成功数 / 分母，**口径之争全在分母**。分类器把请求分六桶：① 服务端错误（5xx、网关异常）——我方责任，进分母算失败；② **供应商错误（模型 API 429/5xx/超时）**——商务上可约定为"不可抗力"剔除或按加权计入，但必须白纸黑字写进 SLA 条款，默认应计入（客户不关心你的供应商）；③ 客户端错误（4xx、非法参数）——剔除分母（不是服务问题），但激增要单独告警（可能是接口兼容性问题在制造 4xx，Q7691）；④ 客户端取消（用户关页面）——剔除，流式场景要区分"真取消"与"服务端卡死后客户端超时重试"（后者其实是服务问题）；⑤ 成功——进分母算成功；⑥ 部分成功（流式中断但已输出大部分）——按约定比例或直接算失败。可对账的口径 = **分类规则表 + 每桶的进退分母规则 + 演练复算流程**：客户拿原始请求日志能按规则表独立复算出同一个数，才叫可对账。
- **取舍**：① 剔除供应商错误让数字好看，但把风险转移给自己——供应商故障是 LLM 应用最大故障源（Q7646），SLA 里剔除等于自我豁免最常发生的事故，客户侧不接受；② 取消的分类最模糊：流式断线归因难（Q2316 断线续传、Q7508 取消计费），保守做法是"取消且已产生输出"算成功（用户拿到了价值）、"取消且零输出"按服务端超时嫌疑排查；③ 分桶监控与 SLA 计算用同一份分类代码——两套实现必然漂移；④ 时间粒度：按请求算 vs 按分钟算（分钟级可用性 = 该分钟成功率>阈值），分钟级更能反映"持续故障"，按请求算会被大流量时段稀释。
- **实战**：① SLA 条款附录给分类规则表，每桶一句话定义 + 判定字段；② 月度 SLA 报告附六桶计数与剔除明细，客户可复算；③ 分类器单测覆盖边界（取消带部分输出、供应商重试后成功）；④ 内部同时监控"含供应商错误的可用性"与"剔除后可用性"双指标——前者驱动供应商治理，后者面向客户承诺。

```python
"""SLA 分母口径: 错误六桶分类 + 双口径可用性计算。"""
from collections import Counter
from dataclasses import dataclass


@dataclass
class RequestLog:
    req_id: str
    status: str          # ok / server_err / vendor_err / client_err / cancel / partial
    output_tokens: int = 0


# 分桶规则表: 桶 -> (是否进分母, 是否算失败)
BUCKET_RULES = {
    "ok":         (True,  False),   # 成功: 进分母, 不算失败
    "server_err": (True,  True),    # 我方错误: 进分母, 算失败
    "vendor_err": (True,  True),    # 供应商错误: 默认计入 (条款可另约定)
    "client_err": (False, False),   # 客户端错误: 剔除分母
    "cancel":     ("conditional", False),  # 取消: 有输出算成功进分母, 零输出剔除
    "partial":    (True,  True),    # 部分成功: 按约定算失败
}


def classify_and_measure(logs: list[RequestLog], exclude_vendor: bool = False) -> dict:
    """按分桶规则算可用性, 支持两种口径对比。"""
    buckets = Counter(l.status for l in logs)
    denom = fails = 0
    for l in logs:
        rule = BUCKET_RULES[l.status]
        if l.status == "cancel":
            in_denom, is_fail = (l.output_tokens > 0, False)   # 有输出=拿到价值
        else:
            in_denom, is_fail = rule
        if l.status == "vendor_err" and exclude_vendor:
            in_denom = False                                   # 商务条款剔除
        if in_denom:
            denom += 1
            if is_fail:
                fails += 1
    avail = (denom - fails) / denom if denom else 1.0
    return {"buckets": dict(buckets), "denominator": denom,
            "failures": fails, "availability": avail}


if __name__ == "__main__":
    # 一次故障日的请求日志: 供应商大面积 429/超时 + 少量自身错误
    logs = ([RequestLog(f"r{i}", "ok", 300) for i in range(980)] +
            [RequestLog(f"v{i}", "vendor_err") for i in range(30)] +
            [RequestLog(f"s{i}", "server_err") for i in range(5)] +
            [RequestLog(f"c{i}", "client_err") for i in range(10)] +
            [RequestLog(f"x{i}", "cancel", 250) for i in range(8)] +
            [RequestLog(f"p{i}", "partial", 120) for i in range(4)])

    m_strict = classify_and_measure(logs, exclude_vendor=False)
    m_lenient = classify_and_measure(logs, exclude_vendor=True)
    print(f"分桶: {m_strict['buckets']}")
    print(f"\n口径A (供应商错误计入, 面向客户): 分母 {m_strict['denominator']}, "
          f"失败 {m_strict['failures']}, 可用性 {m_strict['availability']:.2%}")
    print(f"口径B (剔除供应商错误, 内部视角):   分母 {m_lenient['denominator']}, "
          f"失败 {m_lenient['failures']}, 可用性 {m_lenient['availability']:.2%}")

    sla = 0.995
    print(f"\nSLA 承诺 {sla:.1%}: 口径A {'达标' if m_strict['availability'] >= sla else '违约'}, "
          f"口径B {'达标' if m_lenient['availability'] >= sla else '违约'}")
    ok = m_strict["availability"] < m_lenient["availability"]
    print(f"校验: 剔除供应商错误抬高可用性 -> {'通过 (口径差异可对账: 规则表公开)' if ok else '异常'}")
    print("\n结论：SLA 之争=分母之争; 分类规则表+剔除明细让双方可独立复算;")
    print("      内部双指标并行: 含供应商的驱动治理, 剔除后的面向承诺")
```

**追问一**：客户端取消为什么是最难分类的桶？

→ 解析：因为"取消"的归因要看时序细节：用户主动关页面（真取消，剔除）与服务端卡死 30 秒后客户端超时放弃（假取消，实为我方故障）在日志里都是 client_close。判别信号：① 取消时刻与预期生成时长的关系——正常流式输出时用户等得下去，"1 秒就断"更像是服务端迟迟没吐首 token（Q2050 TTFT）；② 取消前是否已收到有效输出；③ 同一用户随后是否立即重试且成功（重试成功说明刚才确实是服务端问题）。工程上给取消记录打两个标签（取消时已收输出字节数、取消距请求发起的时长），分类规则基于标签而非裸的"cancel"状态。规则演进要留痕：分类规则表是 SLA 契约的一部分，变更走评审与客户通知，不能服务端悄悄改。

**追问二**：分钟级可用性和请求级可用性什么时候会给出相反结论？

→ 解析：两个场景。① **短时全量故障 + 高流量**：1 分钟内 100% 失败（1200 个请求全挂），其余 1439 分钟全成功——请求级可用性 = 1 - 1200/432000 ≈ 99.7% 达标；分钟级 = 1439/1440 ≈ 99.9%？不对——分钟级若要求"成功率高 于阈值"，那故障分钟是 1 个坏分钟，99.93% 也达标；但当 SLA 定义为"持续故障不超过 N 分钟"时，客户感知的是"我那 1 分钟里所有请求都失败了"，请求级稀释了体验。② **长尾散点失败**：全天 0.4% 的请求随机失败（没有任何一个连续坏分钟）——分钟级 100% 达标，但请求级 99.6% 未达标，客户每天都有失败请求。结论：分钟级防"短时全瘫"，请求级防"长尾散点"，SLA 里两个都算、取较差者，内部告警也按双维度设阈值。
