### Q7563 · 工具调用结果缓存与幂等

难度：P6 | 标签：工具调用、缓存、幂等、成本工程

**问**：Agent 一次任务里反复调用同一个搜索接口、重试时重复下单。工具层怎么做结果缓存？"只读工具缓存"和"写工具幂等"为什么是两套机制？

**答**：
- **结论**：两套机制对应两类风险。只读工具（搜索、查询、读取）：缓存键 = 工具名 + 参数规范化哈希（sort_keys、去空白），带 TTL——重复调用直接命中缓存，省的是钱和延迟；风险是数据新鲜度，TTL 按"该工具数据的合理陈旧窗口"定。写工具（下单、发工单、发邮件）：不能缓存（第二次调用返回缓存等于骗过 Agent），必须幂等键——以"工具名+业务参数哈希"为键记账，重试时识别已执行直接返回首结果，否则 Agent 的重试天性会重复产生副作用。
- **取舍**：缓存放工具层（对 Agent 透明）vs 放 Agent 循环层（可结合任务上下文判断"这次真需要新数据"）。工具层更稳；Agent 层能表达"我明知道刚刚查过，请强制刷新"的语义。参数规范化是正确性关键：{"q":"py 3.12"} 和 {"q":"py3.12"} 要不要算同一次调用，要按工具语义定白名单规则。
- **实战**：成本账：一次 Agent 任务平均 15-30 次工具调用，其中 30%+ 是语义重复调用（重试、多分支同查）——缓存把任务成本降 20-30%。写幂等的落地与业务幂等一致：唯一键进 DB 唯一约束，或前置 Redis SETNX；工具返回里带上"首次执行 ID"，让 Agent 能区分"新结果"和"幂等命中"。

```python
"""工具调用结果缓存与副作用幂等：只读工具缓存，写工具靠幂等键。"""
import hashlib, json, time

def call_key(tool, args):
    return hashlib.sha1(f"{tool}:{json.dumps(args, sort_keys=True)}".encode()).hexdigest()[:12]

class ToolBox:
    def __init__(self, ttl=300):
        self.cache = {}                      # key -> (ts, result)
        self.ttl = ttl
        self.executed = set()                # 写操作幂等账本
        self.calls = 0

    def run(self, tool, args, side_effect=False):
        k = call_key(tool, args)
        if not side_effect:                  # 只读：TTL 缓存
            hit = self.cache.get(k)
            if hit and time.monotonic() - hit[0] < self.ttl:
                return f"cached:{hit[1]}"
        else:                                # 写操作：幂等键，重复调用直接返回首结果
            if k in self.executed:
                return "idempotent-skip"
            self.executed.add(k)
        self.calls += 1
        result = f"result-of({tool})"
        if not side_effect:
            self.cache[k] = (time.monotonic(), result)
        return result

box = ToolBox()
print(box.run("search_web", {"q": "py3.12"}))
print(box.run("search_web", {"q": "py3.12"}))                 # 缓存命中
print(box.run("create_ticket", {"t": "a"}, side_effect=True))
print(box.run("create_ticket", {"t": "a"}, side_effect=True)) # 幂等跳过
print("真实调用次数:", box.calls)
print("要点：只读工具参数哈希+TTL 省成本；写工具必须幂等键，Agent 重试才安全")
```

**追问链**：
1. 追问一层：为什么写工具不能"缓存结果"来伪装幂等？——缓存返回会让 Agent 以为副作用发生在"现在"，时间敏感的副作用（下单时间、通知发送）会错乱；幂等是"识别重复请求返回真实结果"，不是"伪造结果"。
2. 追问二层：多实例部署下幂等账本放哪？——进程内 set 失效，必须外置（Redis SETNX+TTL 或 DB 唯一约束）；TTL 要覆盖最大重试窗口，否则跨窗口重试仍会重复执行。

**背诵要点**：
1. 只读工具：参数规范化哈希 + TTL 缓存，省 20-30% 任务成本。
2. 写工具：幂等键 + 唯一约束，返回"幂等命中"标识而非缓存伪造。
3. 幂等账本必须外置且 TTL 覆盖最大重试窗口。

**复盘追问**：
1. Agent 重试导致发了两封相同的客户邮件，幂等键为什么没拦住？（键含了时间戳/随机参数，规范化失败）
2. 缓存 TTL 定 5 分钟后出现"搜索结果过期"投诉，怎么权衡？（按工具数据更新频率分级 TTL + 关键工具免缓存）
