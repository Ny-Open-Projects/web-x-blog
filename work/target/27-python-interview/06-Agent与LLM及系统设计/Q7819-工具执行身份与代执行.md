### Q7819 · 工具执行身份：服务身份、用户代执行与审计三元组

难度：P6 ｜ 标签：工具执行身份、on-behalf-of、权限收窄、最小权限、审计、越权

基线：库外知识卡，代码用标准库模拟服务身份/用户代执行的权限判定与审计链，不调用外部 API。

**问**：Agent 用一个服务账号调用企业日历 API，某用户让 Agent"帮我删掉下周全部会议"，Agent 轻松做到了——包括别的同事的会议。因为服务账号是管理员权限。工具应该以谁的身份执行？服务身份和用户代执行（on-behalf-of）怎么选？审计要记哪些字段才能事后追责？

**答**：

- **结论**：工具执行身份有两类，权限语义完全不同。① **服务身份（service identity）**：Agent 以自己的账号执行，权限是"公共池"级别的最小集（如只读公共日历）——适合无需区分用户的操作（搜索公开文档、查询通用配置）。② **用户代执行（on-behalf-of）**：以发起请求的用户的身份执行，**真实权限主体是该用户**——用户能让 Agent 做的事 = 用户本人能做的事（代执行是权限的搬运不是放大），用户没权限删同事的会议，Agent 代执行同样被拒。事故的根源是"服务账号给了管理员权限"：Agent 变成所有用户的公共提权通道。第三条是**审计三元组**：每次工具执行记录 actor（哪个 Agent/服务）、on_behalf（代谁执行）、principal（真实权限主体），加上工具名、参数、结果，缺一不可——只有 actor 时无法回答"是谁删的会议"。
- **取舍**：代执行的实现成本在于授权链：OAuth token 交换（用户授权 Agent 访问其资源，scope 收窄到工具所需）比静态服务账号复杂得多，且 token 过期、刷新、失效都要处理——所以很多团队偷懒全走服务账号，这是权限事故的温床。折衷路线：**读多写少**场景服务身份只读公共池、写操作一律强制代执行；无法代执行的场景（系统级任务如定时提醒）用独立的任务身份，权限白名单到具体动作。另一个取舍是权限收窄的方向性：代执行只能**收窄**不能放大——用户授权 Agent 的 scope 应该是"用户权限 ∩ 工具所需"，即使用户本人是管理员，Agent 的 scope 也按工具最小集走（管理员用户的 Agent 也不该有全量删库权）。审计的留存期与不可篡改性（追加写/WORM 存储）按合规要求定，至少要覆盖"能回答半年前谁删了什么"。
- **实战**：一次越权事故复盘：用户让日程 Agent"清理下周日历"，Agent 用管理员服务账号删掉了全团队的 37 条日程（包括 boss 的）。整改三件：写类工具（create/delete/update）全部改 on-behalf-of，OAuth scope 按工具最小集签发（删除工具只给 `calendar.events.delete` 且带 owner 校验，只能删本人创建的）；服务账号权限降为只读公共池；审计记录 actor/on_behalf/principal/工具/参数/结果三元组+，接入 SIEM，删操作实时告警。整改后同类请求只能删到用户自己的日程（本人权限内）。教训：**工具身份的设计顺序是先定"谁受益谁授权"，再定账号形态；反过来（先建账号再想权限）必然走向管理员账号一把梭**。

下面模拟服务身份/用户代执行的权限判定与审计链。

```python
# Q7819 工具执行身份: 服务身份 vs 用户代执行 / 权限边界 / 审计
PERMISSIONS = {
    "svc-agent":     {"read:calendar", "read:mail"},                    # 服务身份: 只读公共池
    "user:bob":      {"read:calendar", "write:calendar", "read:mail"},  # bob 本人权限
    "user:eve":      {"read:calendar"},                                 # eve 权限更小
}

AUDIT = []

def execute_tool(actor, tool, args, on_behalf=None):
    """on_behalf: 用户代执行时, 真实权限主体是该用户, 不是服务身份"""
    principal = on_behalf if on_behalf else actor
    need = {"read_events": "read:calendar", "create_event": "write:calendar",
            "delete_event": "write:calendar"}[tool]
    allowed = need in PERMISSIONS.get(principal, set())
    AUDIT.append({"actor": actor, "on_behalf": on_behalf, "principal": principal,
                  "tool": tool, "ok": allowed})
    return allowed

# [1] 服务身份读日历: OK
assert execute_tool("svc-agent", "read_events", {})
print("[1] 服务身份 svc-agent read_events: OK (公共池只读)")

# [2] 服务身份试图写日历: 拒 — 写操作必须以用户身份代执行
ok = execute_tool("svc-agent", "create_event", {})
print(f"[2] 服务身份 create_event: {'OK' if ok else '拒绝'} (服务身份无写权限)")
assert not ok

# [3] 用户代执行: bob 让 Agent 建日程, 主体是 bob, 用 bob 的权限
ok = execute_tool("svc-agent", "create_event", {}, on_behalf="user:bob")
print(f"[3] 代执行(bob): {'OK' if ok else '拒绝'} (真实主体 bob, 权限随 bob)")
assert ok

# [4] 越权防线: eve 让 Agent 删事件, eve 本人也无权限 → 拒, 不能因『Agent 有服务身份』放行
ok = execute_tool("svc-agent", "delete_event", {}, on_behalf="user:eve")
print(f"[4] 代执行(eve) delete: {'OK' if ok else '拒绝'} (代执行是权限收窄不是提权)")
assert not ok

# [5] 审计链: 每次执行记录 actor/on_behalf/principal, 三元组缺一不可查
for a in AUDIT:
    print(f"[5] audit: actor={a['actor']}, on_behalf={a['on_behalf'] or '-'}, "
          f"principal={a['principal']}, tool={a['tool']}, ok={a['ok']}")
assert all(("principal" in a and "on_behalf" in a) for a in AUDIT)
assert sum(1 for a in AUDIT if a["tool"] == "create_event" and a["ok"]) == 1
print("    → 实测 工具身份三件: 服务身份最小权限 / 用户代执行随用户权限(只可收窄) / actor+on_behalf+principal 全量审计")
```

**追问一**：OAuth scope 怎么做到"代执行只能收窄不能放大"？—— scope 签发时做交集：`effective_scope = user_permission ∩ tool_required`。实现上用户授权时只签发工具所需的细粒度 scope（如 `calendar.events.delete`），而不签发用户的全量权限；工具执行时除 scope 外还要做**资源属主校验**（删除目标事件的 owner == on_behalf 用户），防止"有删除 scope 的用户删别人的事件"。放大漏洞的典型形态：Agent 的后端持有用户授权后的 refresh token，却用同一 token 为其他用户服务——token 必须绑定会话主体，跨主体使用要失效。这三层（scope 交集、属主校验、token 绑定）合起来才是"收窄"的完整语义。

**追问二**：系统级任务（定时提醒、批量导入）没有发起用户，身份怎么设计？—— 用**任务身份**（task identity）：每个自动化任务一个独立最小权限账号，白名单到具体动作（定时提醒只有 `calendar.create`，且创建的资源带系统标记便于追溯），不与服务身份/用户身份混用。审计三元组照记：actor=任务名、on_behalf=None、principal=任务账号——之所以独立账号而不是共用服务账号，是为了权限爆炸半径隔离与审计可归因（一个任务账号被滥用时能精确停用它而不影响其他链路）。触发链也要留痕：定时任务由调度器触发，审计里带 trigger 字段（cron/webhook/人工），否则"为什么这个任务跑了"无从回答。

## 背诵要点

- 服务身份=公共池最小权限（只读为主）；写操作一律用户代执行：真实主体是用户，用户能做的 Agent 才能做——代执行是搬运不是放大。
- scope 签发做交集（user ∩ tool）+ 资源属主校验 + token 绑定会话主体，三层合起来才是"收窄"；系统级任务用独立任务身份。
- 审计三元组 actor/on_behalf/principal 缺一不可，带工具、参数、结果与 trigger；删除类操作实时告警。

## 复盘追问

- Agent 删掉了全团队 37 条日程，除了降服务账号权限还要补什么才不会复发？（写类工具强制 on-behalf-of + OAuth 细粒度 scope + 属主校验；审计接入 SIEM 实时告警——权限模型、执行身份、审计三层一起改）
- 为什么"代执行是权限的搬运"这句话在架构上如此重要？（它把 Agent 的权限问题化归为已解决的 IAM 问题：用户权限模型已经过审计与治理，Agent 复用它即可；另造一套"Agent 权限"等于新建一个不受治理的平行权限体系）
