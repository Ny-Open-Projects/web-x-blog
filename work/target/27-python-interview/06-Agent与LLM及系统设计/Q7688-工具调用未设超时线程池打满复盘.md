### Q7688 · Agent 卡在工具调用上：未设超时与线程池打满事故复盘

难度：P6 ｜ 标签：事故复盘、工具调用、超时治理
基线：OpenAI function calling；concurrent.futures.ThreadPoolExecutor；httpx 超时分设。

**问**：Agent 服务的一个"查询库存"工具依赖的下游 RPC 偶发挂死（无响应也不断连），10 分钟后整个 Agent 服务假死——所有会话都停在"正在调用工具"。事故链是什么？为什么说"工具没设超时"是 Agent 的默认地雷？

**答**：**结论**：事故链：工具函数裸调 `requests.post(...)` 不传 timeout（requests 的默认是**无限等待**）→ 下游 RPC 挂死时线程永久阻塞 → Agent 主循环是同步工具执行（线程池并发处理多会话），阻塞线程不释放 → 线程池容量耗尽，新会话排队 → 表现为服务假死而非报错（最难排查的一类）。三层修复：① **协议层**——所有工具的 HTTP/RPC 调用必须显式 timeout（httpx 分连接/读/写超时），这是红线，用 lint/评审门禁兜住；② **执行层**——工具执行包超时壳（线程池场景用 `future.result(timeout=...)` + 隔离池，注意超时后原线程仍在跑要换进程池或可取消的异步实现）；③ **会话层**——单会话工具调用总时长预算（如 60s），超限终止会话并返回降级回复，防"每个工具都慢一点"的累积挂起。

**取舍**：async 与线程的超时语义差异：asyncio 的 `asyncio.wait_for` 能真正取消任务（ cooperative 取消），线程无法杀死——`future.result(timeout)` 超时后阻塞线程还占着资源，只是调用方不再等。所以工具层长期方向是 **async 化工具 + wait_for**，线程池方案只做过渡。另一个取舍：超时值的分级——快工具（DB 查询 2s）、慢工具（文件解析 30s）不能一刀切，超时配置要跟工具注册表走，而不是全局一个值。

**实战**：工具执行的超时壳与预算治理（标准库）：

```python
# 工具调用的超时壳：会话预算 + 分级超时
import time, threading
from concurrent.futures import ThreadPoolExecutor, TimeoutError as FTimeout

TOOL_TIMEOUTS = {"query_stock": 2.0, "parse_file": 30.0}   # 按工具分级
SESSION_BUDGET_S = 60                                       # 单会话总预算

class ToolRunner:
    def __init__(self, pool: ThreadPoolExecutor):
        self._pool = pool
        self._spent = 0.0                                   # 会话已耗时间

    def run(self, tool: str, fn, *args) -> str:
        timeout = TOOL_TIMEOUTS.get(tool, 5.0)
        if self._spent + timeout > SESSION_BUDGET_S:
            return "[降级] 会话工具预算耗尽，终止调用链"
        fut = self._pool.submit(fn, *args)
        t0 = time.monotonic()
        try:
            result = fut.result(timeout=timeout)
        except FTimeout:
            # 注意：线程无法被杀死，阻塞的线程仍占用池位 —— 过渡期方案
            return f"[超时] {tool} {timeout}s 未返回，调用方已脱身"
        self._spent += time.monotonic() - t0
        return result

def bad_tool(url: str) -> str:
    """事故里的写法：requests.get(url) 无 timeout —— 默认无限等待。"""
    raise RuntimeError("演示：裸调用无超时，下游挂死即线程永久阻塞")

def ok_tool(x: int) -> str:
    time.sleep(0.2)
    return f"库存 {x}"

def hang() -> str:
    time.sleep(5)              # 模拟挂死工具（演示缩短）
    return "late"

if __name__ == "__main__":
    pool = ThreadPoolExecutor(max_workers=4)
    runner = ToolRunner(pool)
    print(runner.run("query_stock", ok_tool, 42))
    TOOL_TIMEOUTS["query_stock"] = 0.1     # 演示：把超时压到 0.1s
    print(runner.run("query_stock", hang))  # 调用方 0.1s 脱身（线程仍占池位）
    print(f"会话已耗 {runner._spent:.2f}s / 预算 {SESSION_BUDGET_S}s")
```

**追问 1**：为什么 `future.result(timeout)` 后服务还是可能被拖死？
提示：Python 线程不可强杀，超时只是调用方放弃等待，阻塞线程继续占池位——挂死工具反复触发会把池排干；根治是 async wait_for（可取消）或进程池隔离。

**追问 2**：async 版工具的正确超时写法是什么？
提示：`async with asyncio.timeout(...)`（3.11+）或 `asyncio.wait_for(coro, timeout)`，取消传播到 httpx 的连接层真正断开；注意 C 扩展内不响应取消的点（CPU 长计算）仍需进程隔离。

**追问 3**：工具超时与会话预算的监控信号有哪些？
提示：按工具打点超时率与 P99 耗时、会话预算耗尽率；预算耗尽集中出现说明上游工具普遍变慢（容量/依赖问题），要接告警而不是只让单个会话降级。

## 背诵要点
1. requests/httpx 默认不设超时即无限等待——工具调用必须显式 timeout（分连接/读/写），这是 Agent 服务的默认地雷。
2. 线程超时壳的局限：`future.result(timeout)` 只让调用方脱身，阻塞线程仍占池位直至池排干；根治是 async wait_for（可取消）或进程隔离。
3. 双层预算：按工具注册表分级的超时（2s/30s）+ 单会话工具总时长预算（60s），防慢工具累积挂起；预算耗尽率要接告警。
