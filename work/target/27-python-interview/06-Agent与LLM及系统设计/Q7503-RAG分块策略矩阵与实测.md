### Q7503 · RAG 分块策略矩阵:语义分块 vs 递归 vs 版式感知

> 难度:★★★ | 标签:RAG, 分块, 检索

**问**：知识库有 PDF 手册、Markdown 文档、代码仓库三类语料，现在统一用固定 512 token 切块，检索效果一般。三种分块策略的适用矩阵是什么？"更好"怎么实测而不是感觉？

**答**：结论：分块的三个自由度——块大小、切分依据、元信息保留——没有全局最优，只有"语料类型 × 查询模式"的局部最优。**递归分块**（按段落→句子递归降级）是通用基线，成本低；**语义分块**（按 embedding 相邻句相似度断点）对叙事性长文提升明显，但一次 embedding 全量、成本高且对结构化语料无益；**版式感知**（按标题层级/表格/代码块保持完整性）对手册与代码是刚需——把表格切开等于毁掉它。实测方法：固定评测集（问题→标准出处块），对每个策略跑检索召回@k + 端到端答案正确率，做成本-效果曲线，而不是看几个 demo 问题。

矩阵与实战：
- 语料 × 策略：手册 PDF → 版式感知（标题路径进元数据，表格整块保留 + 摘要块）；对话/论坛 → 递归 + 问答对拼接；代码 → 按函数/类边界（AST 切分）+ 文件路径元数据；纯叙事长文 → 语义分块，块 200~400 token，重叠 10~15%。
- 块大小的隐性约束：太小检索准但答案缺上下文（需要 parent-child 检索：小块检索、父块喂模型）；太大召回下降且噪声多。工程上常用"检索用小块、生成用父块"的双粒度结构，效果普遍优于单一粒度。
- 事故复盘：合同问答把条款表格按 512 token 拦腰切断，"违约金比例"永远查不到。修复：版式感知切分 + 表格前导摘要（"表 7-2 违约金标准"入块头），检索命中率从 61% 到 92%。教训：分块 bug 表现为"模型答错"，先查检索层再怪模型。

```python
# 基线:Python 3.9+ 标准库;递归分块 + 简单召回评测骨架(可运行)
def recursive_split(text: str, max_len: int, seps: list[str] = None) -> list[str]:
    """按分隔符优先级递归降级切块;块超长则继续下级切分。"""
    seps = seps or ["\n\n", "\n", "。", " "]
    chunks: list[str] = []
    def rec(seg: str, depth: int) -> None:
        if len(seg) <= max_len or depth >= len(seps):
            chunks.append(seg.strip())
            return
        parts = seg.split(seps[depth])
        buf = ""
        for p in parts:
            if len(buf) + len(p) > max_len and buf:
                rec(buf, depth + 1)          # 降级:用更细分隔符再切
                buf = p
            else:
                buf = (buf + seps[depth] + p) if buf else p
        if buf:
            rec(buf, depth + 1)
    rec(text, 0)
    return [c for c in chunks if c]

def recall_at_k(gold: set[str], hits: list[str], k: int = 3) -> float:
    """评测:标准出处是否出现在 top-k。"""
    return len(gold & set(hits[:k])) / len(gold)

if __name__ == "__main__":
    doc = "第一章 总则。\n\n" + "条款正文。" * 30
    for size in (64, 256):
        cs = recursive_split(doc, size)
        print(f"max_len={size}: {len(cs)} 块, 平均 {sum(map(len, cs))/len(cs):.0f} 字")
```

**追问**：
- 一层追问：语义分块的"断点"怎么判定？——滑动窗口算相邻句 embedding 余弦相似度，相似度骤降（比局部均值低 δ）处切断；代价是全量 embedding 预计算 + 对短句密集语料（如 FAQ）反而退化，所以要 A/B 实测。
- 二层追问：元数据该往块里放什么？——标题路径（`产品手册 > 第三章 > 7.2 违约`）、文档版本、时间戳；这三样分别服务"过滤召回""生效性判定""新旧冲突仲裁"。检索后过滤（先按版本/时间裁剪再排序）比纯向量相似度更可控。
- 三层追问：评测集从哪来、多大才够？——从真实查询日志抽 top 频次问题 + 人工补边界问题，200~500 条起步，关键不是量大而是覆盖查询意图分布；用 SRM 思路校验评测集意图分布与线上一致，否则结论是自嗨。
