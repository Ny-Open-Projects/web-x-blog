### Q7536 · 事故复盘：超时重试让供应商同一句话计费两次

> 难度:★★★★ | 标签:事故复盘, 幂等键, 计费一致性

**问**：月账单对账发现同一请求被计费两次。网关超时重试导致的计费不一致是怎么发生的？幂等键怎么设计（网关生成还是客户端传递、TTL、供应商不支持怎么办）？流式请求的幂等有什么特殊问题？对账怎么兜底？

**答**：结论：双计费链路 = 客户端超时 → 网关重试 → 供应商侧**两次真实执行**（第一次往往已成功、只是响应慢）→ 两笔账单。防线三层：① **幂等键贯穿**——网关为每个语义请求生成指纹键，重试复用同一键，网关侧在途锁 + 结果缓存把重试合并为单次执行；② **超时与重试预算对齐**——客户端超时 < 供应商 P99 时重试必然放大双计费，重试预算要按供应商延迟分布重算；③ **计费对账兜底**——本地计量账与供应商账单定期 diff，异常双扣进冲正流程。

机理与实战：
- **幂等键的所有权**：网关生成（对客户端透明、防客户端乱传）优于客户端传递；键 = 请求指纹（模型+system+消息归一化）而非随机 UUID——同语义重试才命中同一键（Q2867 指纹归一化）；键带 TTL 与会话边界。
- **供应商侧不支持幂等时**：网关本地兜底——在途集合做 singleflight 合并并发重试，完成缓存让后续重试直接返回首次结果；代价是网关故障恢复后缓存丢失可能漏拦（对账兜底）。
- **流式的特殊性**：流式没有"响应已收"的干净边界——断连/取消后重试会造成部分生成重复计费；流式幂等要用会话内 step-id + 生成指纹（Q1481），并把"已计费 token 数"记账到 step 粒度。
- **对账工程**：供应商不返回 request id 时，按时间窗 + token 量级做模糊匹配，超阈值差异人工冲正；长期解是推动供应商接入幂等协议或列入供应商评估项。

```python
# 基线:Python 3.10+;纯标准库模拟网关重试与计费幂等(指纹+在途去重+对账冲正)
# 真实场景:超时重试 -> 供应商两次执行两笔账单;幂等键贯穿/本地在途锁兜底
from __future__ import annotations
import hashlib


def fingerprint(system: str, user_msg: str, model: str) -> str:
    """请求指纹:同语义请求同指纹(重试复用)。"""
    return hashlib.sha256(f"{model}|{system}|{user_msg}".encode()).hexdigest()[:16]


class Provider:
    """供应商侧:不支持幂等键时的'裸'行为(每次调用都真实执行+计费)。"""

    def __init__(self) -> None:
        self.calls = 0
        self.billed = 0

    def generate(self, fp: str) -> str:
        self.calls += 1
        self.billed += 1                                 # 每次真实执行都计费
        return f"answer-for-{fp[:8]}#{self.calls}"


class Gateway:
    """网关:幂等键贯穿 + 在途锁 + 结果缓存(供应商不支持幂等时的本地兜底)。"""

    def __init__(self, provider: Provider) -> None:
        self.provider = provider
        self.inflight: set[str] = set()
        self.done: dict[str, str] = {}
        self.billed_events: list[str] = []

    def handle(self, fp: str, attempt: int = 1) -> str:
        if fp in self.done:                              # 重试命中已完成结果:不再计费
            self.billed_events.append(f"attempt{attempt}:dedup-hit")
            return self.done[fp]
        if fp in self.inflight:                          # 并发重试:在途合并(单飞)
            self.billed_events.append(f"attempt{attempt}:inflight-merged")
            return "merged-inflight"
        self.inflight.add(fp)
        try:
            ans = self.provider.generate(fp)             # 只此一处真实执行
        finally:
            self.inflight.discard(fp)
        self.done[fp] = ans
        self.billed_events.append(f"attempt{attempt}:executed")
        return ans


def demo() -> None:
    fp = fingerprint("sys", "总结这份合同", "gpt-x")
    p = Provider()
    gw = Gateway(p)

    # 事故链:客户端超时重试,无幂等 -> 供应商执行两次,两笔账单
    p2 = Provider()
    p2.generate(fp); p2.generate(fp)
    assert p2.calls == 2 and p2.billed == 2
    print(f"无幂等:重试导致供应商执行 {p2.calls} 次、计费 {p2.billed} 笔 ✅ 双计费")

    # 修复:网关幂等键贯穿(重试同指纹) -> 只执行一次只计费一次
    r1 = gw.handle(fp, attempt=1)
    r2 = gw.handle(fp, attempt=2)                        # 客户端超时后的重试
    r3 = gw.handle(fp, attempt=3)                        # 网络抖动再试
    assert r1 == r2 == r3 and p.calls == 1 and p.billed == 1
    print(f"网关幂等:3 次请求 1 次执行 1 笔计费 ✅ 计费事件:{gw.billed_events}")

    # 并发双击:新请求仍在途时第二个并发调用合并,不产生第二笔
    fp2 = fingerprint("sys", "总结这份合同 v2", "gpt-x")
    gw.inflight.add(fp2)
    merged = gw.handle(fp2, attempt=4)
    assert merged == "merged-inflight"
    print("并发重试在途合并 ✅(singleflight 语义,不放大计费)")


if __name__ == "__main__":
    demo()
```

**追问一**：为什么"客户端超时 < 供应商 P99"是双计费的放大器？
答：客户端等不到响应就重试，而供应商侧慢请求最终都完成了——超时越短，"已成功但客户端放弃"的比例越高，重试放大系数越大。重试预算的正确算法：客户端超时 ≥ 供应商 P99 + 网关开销，或对重试标记"可放弃"并接受失败率，而不是无脑三次重试。

**追问二**：冲正流程怎么设计才不变成"每次人工查账"？
答：对账分层——量级对账（本地估算 vs 账单总量，偏差 >2% 告警）、请求级对账（指纹+时间窗模糊匹配，配不上的进差异池）、冲正自动化（双扣且指纹相同 + 时间窗内 = 自动发起 credit 申请），人工只处理配不上的长尾；月度复盘把高频差异模式推动到协议层修复。

## 背诵要点
- 双计费链路：客户端超时 → 网关重试 → 供应商重复执行；防线 = 幂等键贯穿（指纹键+在途 singleflight+结果缓存）+ 超时对齐 P99 + 对账冲正。
- 幂等键用"请求指纹"而非随机 UUID，同语义重试才命中；流式用会话 step-id 记账到 token 粒度。
- 对账分层：量级偏差告警 → 请求级模糊匹配 → 自动冲正；供应商幂等协议支持是采购评估项。

## 复盘追问
- 月账单比本地计量高 5%，排查顺序？（提示：先分层对账定位是重试放大还是计价口径差异（缓存价/档位），再看客户端超时配置与重试系数，最后查供应商侧重复执行证据）
- 幂等键的 TTL 定多长、过期后重试怎么办？（提示：TTL ≥ 重试窗口 + 结果缓存生命周期；过期重试等价于新请求会重新计费——键里带时间窗分区，超窗重试要显式确认）
