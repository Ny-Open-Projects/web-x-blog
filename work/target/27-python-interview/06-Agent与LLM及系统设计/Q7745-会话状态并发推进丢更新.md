### Q7745 · 两个请求同时推进会话状态机：后写的把先写的槽位覆盖了

难度：P7 ｜ 标签：Agent、多轮会话、状态机、乐观锁、丢失更新

基线：Python 3.12；用"加载—修改—保存"窗口 + 版本号 CAS 模拟会话状态的并发写。

**问**：多轮下单助手把槽位（商品、数量、地址、时间）存在 Redis/DB 的会话状态里，每轮"读出整个 state → 修改 → 写回"。用户手快，前端并发发了两个请求（一个补地址、一个改数量），偶尔出现"地址填了但又变回空"，日志里两条请求都成功。单用户串行操作时从没出现过。为什么？

**答**：
- **结论**：读—改—写不是原子操作，两个请求各自读到**同一版本**的 state（比如都读到 `{city: null, qty: 1, v: 3}`），一个写入 `city=上海`，另一个用自己的副本覆盖，写回 `{city: null, qty: 2}`——地址槽位被"回滚"了。数据库不会报错，因为两次都是合法写入；这就是经典的**丢失更新**。LLM 的多轮对话尤其容易触发：一次生成要几秒，窗口被拉得很长。
- **取舍**：三条路：① **乐观锁（CAS）**：state 带 `version`，写回时 `UPDATE ... WHERE version = :expected`，影响行数 0 就说明被别人改过，重新加载再合并重试；② **字段级更新**：不要整块覆盖，只 `HSET session city 上海` / `UPDATE ... SET city = ?`，不同槽位互不影响（但同一槽位并发仍需 CAS）；③ **串行化**：按 session_id 加锁（Redis 分布式锁或单分区串行队列），代价是并发度下降、锁要处理超时。
- **实战**：① 重试必须**重新加载 + 合并**，不能拿旧副本再写一次；重试次数设上限（比如 3 次）并打点；② 槽位合并策略要显式：新值覆盖旧值，还是"用户最新说的优先"（带时间戳/轮次号）；③ 状态里存"最后修改的 turn_id"，冲突时能判断谁更新；④ 前端也要去抖/串行化同一会话的请求，减少并发概率——但正确性不能依赖前端。

```python
"""整块覆盖导致槽位丢失；版本号 CAS + 重新加载合并才正确。"""
import copy


class Conflict(Exception):
    pass


class SessionStore:
    def __init__(self) -> None:
        self.state = {"version": 1, "slots": {"city": None, "qty": 1}}

    def load(self) -> dict:
        return copy.deepcopy(self.state)

    def blind_save(self, state: dict) -> None:
        """无版本检查：后写覆盖先写。"""
        state["version"] = self.state["version"] + 1
        self.state = state

    def save(self, state: dict, expected_version: int) -> None:
        if self.state["version"] != expected_version:
            raise Conflict(f"expected v{expected_version}, actual v{self.state['version']}")
        state["version"] = expected_version + 1
        self.state = state

    def patch(self, **slots) -> None:
        """字段级更新：只改指定槽位，外加版本自增。"""
        self.state["slots"].update(slots)
        self.state["version"] += 1


if __name__ == "__main__":
    # 1) 整块覆盖：地址被回滚
    s = SessionStore()
    turn_a = s.load()
    turn_b = s.load()
    turn_a["slots"]["city"] = "上海"
    s.blind_save(turn_a)
    turn_b["slots"]["qty"] = 2
    s.blind_save(turn_b)
    print("整块覆盖后:", s.state["slots"], "-> city 被回滚成 None")

    # 2) CAS：冲突后重新加载并合并
    s2 = SessionStore()
    a = s2.load()
    b = s2.load()
    a["slots"]["city"] = "上海"
    s2.save(a, expected_version=1)
    b["slots"]["qty"] = 2
    try:
        s2.save(b, expected_version=1)
    except Conflict as e:
        print("\nCAS 冲突:", e)
        latest = s2.load()                     # 重新加载，不能拿旧副本硬写
        latest["slots"]["qty"] = 2
        s2.save(latest, expected_version=latest["version"])
    print("CAS 合并后:", s2.state["slots"], "version =", s2.state["version"])

    # 3) 字段级更新：不同槽位天然不冲突
    s3 = SessionStore()
    s3.patch(city="上海")
    s3.patch(qty=2)
    print("\n字段级更新:", s3.state["slots"])

    print("\n结论：整块读改写必须带版本号；能按槽位更新就不要整块覆盖")
```

**追问一**：CAS 重试会不会变成活锁？怎么设上限？

→ 解析：同一 session 的高频写入（用户连点、多个子 Agent 同时更新）会让 CAS 反复失败。上限一般 3 次，超过就返回"状态冲突，请重试"或降级为字段级更新。重试要加**随机抖动退避**，避免两个请求同步重试再撞一次。更根本的是减少写冲突面：把"一个大会话状态"拆成多个独立槽位记录（地址、商品各一条），冲突概率从 O(并发) 降到几乎为 0。

**追问二**：把整段对话历史也塞进 state 一起 CAS，会有什么问题？

→ 解析：历史是**追加型**数据，两个请求并发追加时 CAS 必然冲突，而且重试要重新拼整段历史、成本高。正确做法是分离：对话历史用 append-only 的消息表（按 `seq` 自增或 `created_at + id` 排序，写入不需要 CAS），状态槽位用版本化记录（需要 CAS）。两者通过 turn_id 关联。这样"追加"和"修改"各自用合适的并发控制，而不是让一个 version 管所有东西。
