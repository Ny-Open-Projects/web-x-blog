### Q7695 · 百万级向量的内存与召回容量账

难度：P6 ｜ 标签：容量规划、向量库、HNSW、召回率、量化

基线：Python 3.9+；pgvector 0.7 / Milvus 2.4 / Qdrant 1.9+；embedding 1536/1024 维。

**问**：RAG 知识库要存 500 万个 chunk，embedding 是 1536 维 float32。老板问"一台 16GB 内存的机器能扛吗"？这笔内存账怎么算？recall@10 从 0.95 降到 0.9 能省多少？

**答**：
- **结论**：裸账——1536 维 × 4 字节 = 6KB/向量，500 万条 = 30GB，**单机 16GB 扛不住纯向量**，还没算 HNSW 图索引的额外边存储（≈ 每向量 M×2×4 字节，M=16 时 +128B）与原文。省内存的杠杆按顺序：(1) 量化：int8 量化省 4 倍（30GB→7.5GB），二值/binary 量化省 32 倍但只适合某些场景；标量量化后 recall 损失通常 <1%~3%，需重排（rerank）补偿；(2) 降维：Matryoshka/训练降维 embedding（1536→512，省 3 倍）；(3) 分片/磁盘索引（DiskANN 类，内存只放热数据）。召回率 0.95→0.90 在 HNSW 里主要通过调 ef/M 实现，省的是"查询时的计算与内存"，配合 rerank 恢复精度。
- **取舍**：内存省越多、召回损耗越大，生产标准做法是"量化粗排 + 原向量精排 rerank"：粗排从全量里拉 top-100，精排用原始向量或交叉编码器挑 top-10，召回率可保持在 0.93+ 而内存省 4 倍。选择 pgvector（已有 PG、数据量 < 千万）vs 专用库（Milvus/Qdrant，亿级/高 QPS）也是这笔账的一部分。
- **实战**：公式——`内存 ≈ N × (dim × bytes_per_component + 索引开销) + 原文存储`；查询延迟账：HNSW 是内存随机访问，量化后 cache 命中率上升反而更快；QPS 账要算 ef_search 与 CPU 核数。

```python
# 向量内存账：量化/降维/索引开销一起算（标准库可运行）。
def vector_mem_gb(n: int, dim: int, dtype_bytes: float = 4.0,
                  hnsw_m: int = 16, raw_text_gb: float = 2.0) -> float:
    per_vec = dim * dtype_bytes + hnsw_m * 2 * 4     # 向量 + 图边
    return round((n * per_vec + raw_text_gb * 2**30) / 2**30, 1)

def plan(n: int, dim: int, machine_gb: float) -> list[str]:
    lines = []
    for label, dtype, d in (
        ("fp32 原始", 4.0, dim), ("int8 量化", 1.0, dim),
        ("int8+降维512", 1.0, 512), ("binary(1bit/维)", 0.125, dim),
    ):
        mem = vector_mem_gb(n, d, dtype)
        verdict = "可单机" if mem < machine_gb * 0.7 else "需分片/磁盘索引"
        lines.append(f"{label}: {mem}GB -> {verdict}")
    return lines

if __name__ == "__main__":
    for line in plan(5_000_000, 1536, machine_gb=16):
        print(line)
    # fp32 原始: 31.2GB -> 需分片/磁盘索引
    # int8 量化: 9.7GB -> 可单机（配 rerank 保召回）
    # int8+降维512: 5.0GB -> 可单机
    # binary(1bit/维): 3.5GB -> 可单机（仅适合特定场景）
```

**追问**：
- 一层：为什么量化后必须配 rerank？→ 提示：量化损失是"距离排序的噪声"，粗排放大候选集（top-100）再用原始向量/交叉编码器精排，把精度损失抵回来。
- 二层：HNSW 的 ef_search 和 M 分别影响什么？→ 提示：M 影响图密度（内存与建库时间），ef_search 影响查询精度/延迟（在线可调，是召回率的主要旋钮）。
- 三层：增量更新对 HNSW 账的影响？→ 提示：图索引支持增量插入但删除是标记（碎片），定期重建或选支持 deleteme 的实现；频繁全量更新场景考虑分区索引。

**背诵要点**：
1. 内存 ≈ N×(dim×分量字节 + M×2×4) + 原文；1536 维 fp32 是 6KB/向量，500 万 ≈ 30GB。
2. 省内存杠杆：int8 量化 4x（配 rerank 保召回）> 降维 3x > binary 32x（场景受限）> 磁盘索引。
3. 召回率主要旋钮是 ef_search（在线可调）；生产标配"量化粗排 + 原向量精排"。

**复盘追问**：
1. 为什么当初选型直接上了专用向量库？提示：没算账——百万级 int8 单机 pgvector 就够；选型要有内存/QPS/团队运维三笔账。
2. 如果知识库每天新增 10 万 chunk，重建索引的窗口怎么算？提示：增量插入 vs 定期全量重建的时间窗与查询质量波动，写进容量账。
