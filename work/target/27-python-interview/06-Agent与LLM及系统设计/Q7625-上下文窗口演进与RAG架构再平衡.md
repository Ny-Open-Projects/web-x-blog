### Q7625 · 上下文窗口演进（32k→1M+）对 RAG 架构的再平衡

难度：P6 ｜ 标签：版本演进 / RAG / 长上下文

**问**：模型上下文窗口从 32k 涨到 128k、200k、乃至 1M+。是不是 RAG 检索层就可以砍掉、把整库塞进上下文？窗口扩大的真实收益、代价与"RAG 过时论"怎么评估？架构再平衡的决策框架是什么？

**答**：
- **结论**：窗口扩大的真实收益：① 少量中等文档可以"整文入上下文"，消灭检索漏召回（检索不到=必然答错，整文入=上限抬高）；② 多文档交叉推理（对比、汇总）质量优于"检索片段拼接"；③ 减少检索层维护（索引、切分、嵌入模型升级链）。代价：① **注意力稀释/lost in the middle**——超长上下文中部信息利用率下降，"能塞下"不等于"都能用上"，长文档任务的准确率随长度衰减；② **成本与延迟**——按 token 计费下整库入上下文的成本远高于检索后的精准注入（Q7528 已谈决策），且 prefill 时间随长度线性增长，TTFT 恶化；③ **缓存失效**——每次查询上下文都不同，前缀缓存命中率低（Q7580 同源）；④ **数据治理**——把全库塞上下文意味着权限过滤在推理侧做（泄露面更大），且原始文档质量参差直接进模型。所以"RAG 过时论"不成立：变化的是**分工**——检索层从"负责找到答案片段"演变为"负责圈定范围 + 权限过滤 + 控成本"，窗口负责"圈定范围内的完整推理"。决策框架：文档集小（<窗口的 20%）且交叉推理多 → 整文入；集大或权限敏感 → 检索 + 大窗口（检索 top-k 可以放宽到 50k token 注入）；混合 → 分级（热文档整文、长尾检索）。
- **取舍**：评估方法：用业务问答集跑三种架构（纯长上下文整文 / 传统 RAG 小片段 / 检索+大窗口宽松注入），对比准确率、单位查询成本、TTFT 三个维度——常见结果是"检索+大窗口"在质量与成本上双优；纯长上下文只在"范围明确的小集合"胜出。还有一个被低估的点：**检索层还承担权限与时效**——文档删除/更新后整文入上下文的缓存与快照一致性问题比索引更新更麻烦。
- **实战**：落地：① 架构决策写 ADR，附三架构实测数据，不跟风；② 宽松注入检索：top-k 从"挤进 8k"放宽到"注入 50k~100k"，召回率显著提升且成本可控；③ 分级：文档集按访问频率与更新频率分"整文通道 / 检索通道"；④ 长上下文质量监控：答案位置偏差（中部信息丢失）作为专项指标抽检；⑤ 权限过滤永远在检索层做，不交给推理侧。

```python
# 三架构再平衡账: 质量/成本/延迟三维对比
# 基线: Python 3.9+ 标准库; 数值为量级演示, 决策以业务问答集实测为准
from dataclasses import dataclass


@dataclass
class Arch:
    name: str
    accuracy: float
    tokens_per_query: int      # 注入上下文 token
    ttft_s: float              # prefill 主导
    output_price_per_mtok: float = 15.0
    input_price_per_mtok: float = 2.5


def cost_per_query(a: Arch) -> float:
    return a.tokens_per_query * a.input_price_per_mtok / 1e6


def verdict(cands: list[Arch], corpus_tokens: int, window: int) -> str:
    """决策框架: 小集合+交叉推理->整文; 大集合->检索+宽松注入。"""
    if corpus_tokens < window * 0.2:
        return "整文入上下文(消灭漏召回)"
    best = max(cands, key=lambda a: a.accuracy - cost_per_query(a))
    return f"{best.name}(质量-成本联合最优)"


def main() -> None:
    # 大语料 (2亿 token) 三架构实测样例
    pure = Arch("纯长上下文", 0.71, 400_000, ttft_s=45.0)
    rag_small = Arch("传统RAG小片段", 0.74, 6_000, ttft_s=2.5)
    rag_wide = Arch("检索+宽松注入", 0.82, 30_000, ttft_s=6.0)
    cands = [pure, rag_small, rag_wide]

    for a in cands:
        assert a.accuracy > 0
    assert cost_per_query(pure) > cost_per_query(rag_wide) * 5    # 整库入成本爆炸(约13倍)
    assert rag_wide.accuracy > rag_small.accuracy                 # 宽松注入召回升
    print("大语料: 宽松注入(30k) 质量-成本联合最优; 整库入 TTFT 45s 不可用")

    # 小集合: 窗口的20%以内 -> 整文通道
    assert verdict(cands, corpus_tokens=20_000, window=200_000).startswith("整文")
    assert verdict(cands, corpus_tokens=200_000_000, window=200_000) == "检索+宽松注入(质量-成本联合最优)"
    print("OK: RAG未过时-分工变了: 检索层管范围/权限/成本, 窗口管圈内推理")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么权限过滤不能随"整文入上下文"一起交给推理侧？
→ 一句话提示：推理侧过滤意味着无权数据已经进入模型上下文——泄露面不可控（可能被诱导复述、进日志与缓存）；权限必须在前置的检索/圈定层物理生效，这是架构红线不是优化项。

**追问 2**：lost in the middle 怎么量化并纳入监控？
→ 一句话提示：构造"答案位于上下文不同位置"的探针集（开头/中部/结尾各一组），测各位置准确率曲线；生产上抽检答案与引用位置的相关性，中部衰减加剧即触发注入顺序调整（关键内容前置/后置）。

## 背诵要点
- 窗口扩大改变的是分工：检索层从"找片段"变为"圈范围 + 权限过滤 + 控成本"；"整库塞上下文"败在注意力稀释、成本（整库 token 计费）、TTFT 线性增长、前缀缓存失效。
- 决策框架：语料 < 窗口 20% 且交叉推理多 → 整文通道；大语料 → 检索 + 宽松注入（top-k 放宽到 50k~100k，质量/成本双优，示例账中整库入成本约为宽松注入的 6.7 倍且 TTFT 45s 不可用）。
- 红线：权限过滤永远在检索层；长上下文质量用位置探针集监控（lost in the middle），关键内容前置/后置注入。

## 复盘追问
- 为什么说"检索漏召回"和"注意力稀释"是两种不同性质的失败？提示：漏召回是确定性丢失（没进上下文必错），稀释是概率性退化（进了但没用上）——前者靠放宽注入修复，后者靠注入位置与结构修复，监控指标也要分开设计。
- 模型窗口升级到 1M 后，原有的"分块大小/检索 top-k"超参数要不要全部重调？提示：要——它们是在旧窗口约束下调优的；窗口变大后最优解通常是"块更大、k 更少、注入更多"，沿用旧参数等于把旧架构的保守性带进新窗口。
