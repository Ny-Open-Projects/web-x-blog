### Q7798 · 用户一句“对了帮我查下天气”：会话内任务切换的检测与上下文软重置

难度：P6 ｜ 标签：多任务会话、话题切换检测、软重置、槽位污染、意图漂移、相似度骤降

基线：Python 3.12；模拟话题相似度序列与切换检测（阈值触发 + 滞回双确认），对比"不重置 vs 软重置"的槽位污染干扰率，全标准库实跑。

**问**：用户前 10 轮在订机票（填了出发地、日期、舱位槽位），第 11 轮突然说"对了，顺便帮我查下明天的天气"——之后 Agent 开始把"明天"当出发日期、把目的地城市的天气查成了机票改签。会话内任务切换为什么要专门检测？软重置和硬重置（清空一切）的边界在哪？误判切换（其实是关联子话题）怎么防？

**答**：

- **结论**：切换不检测的代价是**任务态污染**：会话的槽位（出发地/日期/舱位）、激活的工具集（航班搜索）、任务目标（"完成订票"）都是上一任务的运行时状态，新话题的请求会被旧状态静默劫持——"明天"填进日期槽位是最典型的污染（槽位填充模型只看局部语义，不知道任务换了）。切换检测的信号按可靠度排：① **槽位冲突**——新请求要填的槽位与已填值语义冲突（日期槽已填出发日期，新请求的"明天"语义上是查询日期），冲突即强信号；② **相似度骤降**——新消息与"会话主题向量"（滚动平均的近 N 轮向量）的相似度显著低于会话内均值，是通用信号但会误伤关联子话题（"改签要收手续费吗"与订票主题相似度也低）；③ **显式标记词**（"对了""另外""切换一下""重新开个话题"）——可靠但覆盖不全。**软重置 vs 硬重置的边界**：任务态（槽位、激活工具、任务目标、进行中的多轮流程）全清——它们属于旧任务；用户事实层（称呼、偏好、已确认的常量如"用户在杭州"）保留——它们跨任务复用；历史对话原文不动——只是不再作为当前任务的指令来源。软重置 = 清任务态、留事实层、历史降级为背景。
- **取舍**：① **误判的代价不对称**：该切没切（污染旧状态，答非所问）与不该切切了（丢掉有用上下文，用户要重说一遍）——两者都伤体验，但污染往往产生"自信的错误答案"（把天气查成改签，用户还以为对了），比"遗忘"更隐蔽；因此检测策略偏敏感，用**滞回双确认**防误伤：单轮信号只降权旧任务态（槽位标记 pending），连续两轮新话题信号才触发真重置——第一轮是"疑似"，第二轮确认，单轮内的关联子话题（下一轮回到原话题）自动解除 pending；② **检测器成本**：相似度检测需要向量计算（本地 embedding 可接受，不能为检测再调一次 LLM——路由器同理，Q7795 的零调用原则）；标记词是纯正则零成本，先跑标记词再跑相似度，短路省算力；③ **重置的用户告知**：软重置后 Agent 的行为变化（"已忘记之前的航班要求"）要向用户可见——静默重置会让用户误以为上下文还在，连续答错；告知话术进系统提示的固定行为规范；④ **多任务并行请求**（"同时帮我订票和查天气"）不是切换而是拆分——检测器要区分"替换旧任务"与"追加新任务"，追加走子任务隔离（Q1487 并发隔离子会话），别把追加误判成切换。
- **实战**：① 槽位 schema 带任务归属：每个槽位登记所属任务类型，跨任务请求命中他人槽位时强制走"槽位冲突评审"分支（清空/新建/拒答），这是比相似度更结构化的切换判定；② 检测信号打点：每轮记录"是否触发 pending/重置/误判回滚"，误判回滚率（重置后下一轮用户说"不是，我是说…"）是检测器调参的直接反馈；③ 会话主题向量用滚动窗口更新（近 N 轮 EMA），避免单轮长文把主题拽偏；④ 软重置的实现要点：重置的是"运行时任务态容器"（槽位表/工具注册/流程状态机），历史消息列表与用户画像存储不动——架构上任务态与事实层必须分容器存放，混存则软重置无从谈起。

```python
"""Q7798 任务切换检测: 信号分级 + 滞回双确认 + 软重置分层。"""
import statistics

SWITCH_MARKERS = ("对了", "另外", "顺便", "重新开", "换个话题")


def topic_sim(new: str, theme: list[str]) -> float:
    """字集重叠模拟相似度: 新消息与主题(近几轮聚合)的字符集重叠率."""
    theme_chars = set(c for t in theme for c in t if c.strip())
    new_chars = set(c for c in new if c.strip())
    if not theme_chars or not new_chars:
        return 0.0
    return len(theme_chars & new_chars) / len(new_chars)


class SwitchDetector:
    """滞回双确认: 单轮信号 -> pending(旧任务态降权); 连续两轮 -> 软重置."""

    def __init__(self, drop: float = 0.18):
        self.drop = drop
        self.pending = False

    def feed(self, msg: str, theme: list[str]) -> str:
        marked = any(m in msg for m in SWITCH_MARKERS)
        sim = topic_sim(msg, theme)
        low = sim < self.drop
        signal = marked or low
        if signal:
            if self.pending:                 # 第二轮连续信号 -> 确认切换
                self.pending = False
                return "reset"
            self.pending = True              # 第一轮 -> 疑似, 槽位降权
            return "pending"
        self.pending = False                 # 回到原话题 -> 自动解除
        return "same"


def soft_reset(state: dict) -> dict:
    """软重置: 清任务态容器, 保留事实层与历史(分容器是前提)."""
    return {
        "slots": {},                 # 任务态: 清
        "tools": [],                 # 任务态: 清
        "goal": None,                # 任务态: 清
        "facts": state["facts"],     # 事实层: 保留(称呼/偏好/常量)
        "history": state["history"], # 历史原文: 不动, 降级为背景
    }


if __name__ == "__main__":
    theme = ["订机票 出发地 上海 日期 舱位", "航班 时间 价格", "改签 手续费"]
    state = {"slots": {"depart": "上海", "date": "明天", "cabin": "经济舱"},
             "tools": ["flight_search"], "goal": "订机票",
             "facts": {"user_city": "杭州", "call": "王先生"},
             "history": ["...前10轮对话..."]}

    det = SwitchDetector()
    seq = ["帮我看看明天的天气", "再看看后天要不要带伞"]     # 连续两轮新话题
    acts = [det.feed(m, theme) for m in seq]
    print(f"信号序列: {list(zip(seq, acts))}")
    final_state = soft_reset(state) if acts[-1] == "reset" else state
    print(f"重置后: slots={final_state['slots']} tools={final_state['tools']} "
          f"facts={final_state['facts']} 历史保留={len(final_state['history']) > 0}")
    # 误伤演练: 高相关追问 -> 低相似旁支(pending) -> 回到原话题(自动解除)
    det2 = SwitchDetector()
    r = [det2.feed("出发地改成杭州行吗", theme),
         det2.feed("顺便看看目的地的酒店", theme),
         det2.feed("回到航班, 那航班几点起飞", theme)]
    print(f"误伤演练: {r}  <- 旁支仅pending不重置, 回原话题自动解除")
    ok = (acts == ["pending", "reset"] and final_state["slots"] == {}
          and final_state["facts"]["user_city"] == "杭州" and r == ["same", "pending", "same"])
    print(f"校验: 双确认触发 + 事实层保留 + 关联子话题不误伤 -> {'通过' if ok else '异常'}")
    print("结论：任务态(槽位/工具/目标)污染新话题是静默错误; 软重置=清任务态留事实层;")
    print("      滞回双确认防误伤: 单轮pending, 连续两轮reset, 回原话题自动解除")
```

**追问一**：相似度骤降会误伤关联子话题，滞回双确认会不会让真正的切换慢一拍？信号融合的权重怎么定？

→ 解析：滞回的代价与信号融合的设计：① **慢一拍的真实成本**——双确认下，切换的第一轮处于 pending（旧槽位降权但不新建），若这一轮用户的问题是完整自包含的（"帮我查明天天气"），pending 状态足够正确响应（旧槽位降权后不会被误填，新请求按新意图处理）——pending 不是"忽略"，是"降权观察"，所以双确认的真实代价主要落在"第一轮就依赖新任务态"的场景（罕见）；真正要防的是把 pending 做成了"照旧用旧槽位"，那才是慢一拍的事故；② **信号融合**——三类信号不同质：显式标记词是强信号（用户亲口说的），可单信号触发（不需要第二确认，用户说"换个话题"就是切换）；槽位冲突是结构性强信号（同样可单触发，但"冲突"的判定本身要谨慎——语义冲突 vs 正常追问要区分）；相似度骤降是弱信号（统计性），必须走双确认。融合规则按信号等级组合：强信号单触发、弱信号双确认、强+弱立即触发——写成显式规则表而不是加权打分（打分模型的阈值永远说不清，规则表可审计可调）；③ **主题向量的鲁棒性**——会话主题被单轮长消息拽偏是误报来源之一：主题向量用 EMA 平滑（近 N 轮滚动），长消息只贡献有限权重；④ **回归调参**——误判回滚率（用户说"不是，我是说…"）与漏切率（badcase 里发现污染）两个指标对拉，滞回阈值与信号等级的调整要有这两条曲线的证据，别拍脑袋。总原则：**信号分级 + 规则表融合优于统一打分：强弱信号的处理路径不同（单触发 vs 双确认），混在一个加权公式里会让每个信号的语义都失真。**

**追问二**：软重置的"事实层"边界怎么划？哪些东西看似任务态实则该保留（或反之）？多任务追加（用户同时要两件事）怎么与切换区分？

→ 解析：① **分层判据**——保留与否的判据是"是否依附于特定任务"：依附任务的是任务态（日期槽位、舱位选择、进行中的确认流程、激活的工具集），跨任务成立的是事实层（用户称呼、所在地、语言偏好、已声明的约束如"不要发短信"）；模糊地带用"反问测试"：删掉它，下一个新任务还需要它吗？需要→事实层；不需要→任务态。常见误分类：已确认的常量（"就订经济舱，永远不坐红眼"——看似订票任务态，实为长期偏好，留事实层）； conversational 状态（"刚才说到哪了"的流程指针——纯任务态，清）；② **反向的坑**——任务态里也有该部分保留的：切换前**已完成并确认的产出**（已生成的订单号、已确认的方案摘要）是成果不是状态，清了用户会炸——软重置后这类成果要归档为事实层的"会话成果清单"；③ **追加与切换的区分**——判据是"旧任务是否被抛弃"：新请求与旧任务可共存（订票 + 查天气并行）→追加，走子任务隔离（每个子任务独立槽位容器与工具注册，互不可见彼此的任务态，结果分别交付）；新请求显式替代（"算了不订了，帮我查天气"）→切换（软重置）+旧任务的取消语义（未完成动作要终止，Q1759 取消传播）；判别的实现：槽位冲突检测里"新请求是否引用旧任务实体"（引用"那张机票"=关联，完全不提=候选切换/追加），加上显式替代词（"算了""不订了"）检测；④ **并发追加的工程底座**——子任务隔离要求会话状态机支持多活跃任务（单任务指针的架构撑不住追加场景，要么改多任务容器要么在检测到追加时明确告知"请分开问"，产品上做减法也是取舍）。总原则：**软重置的正确性取决于分层容器的架构前提——任务态与事实层物理分离不是优化项，是这个功能的地基；混存的会话状态做不了软重置，只能做昂贵的硬重置。**

## 背诵要点
- 不检测切换的代价是**任务态污染**：槽位表、激活工具集、任务目标都是上一任务的运行时状态，新请求被静默劫持（"明天"填进出发日期）；污染产出的是"自信的错误答案"，比遗忘更隐蔽。
- 信号按可靠度排：槽位冲突（强，结构化）> 主题相似度骤降（通用但误伤关联子话题）> 显式标记词（可靠但覆盖不全）；策略偏敏感 + 滞回双确认（单轮只把旧任务态降权为 pending，连续两轮才真重置）。
- 软重置边界：清任务态、留事实层（称呼/偏好/长期约束）、历史原文降级为背景；架构上任务态必须与事实层、历史分容器存放，否则无从软重置；"追加新任务"走子会话隔离，不是切换。

## 复盘追问
- 为什么"该切没切"比"不该切却切了"更危险？（前者污染旧状态还给出自信的错误答案，用户难以察觉；所以检测偏敏感，用 pending 降权 + 双确认把误伤挡在"只降权不重置"这一层）
- 软重置对架构提了什么前置要求？（任务态容器（槽位表/工具注册/流程状态机）与用户事实层、历史消息分开存放——混存只能硬重置，等于丢掉全部上下文）
