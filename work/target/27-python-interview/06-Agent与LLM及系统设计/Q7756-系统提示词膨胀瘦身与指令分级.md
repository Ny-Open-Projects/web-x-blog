### Q7756 · 系统提示词长到 8000 token：指令分级与瘦身实验

难度：P6 ｜ 标签：提示词工程、指令分级、token 预算、瘦身实验、回归验证

基线：Python 3.12；用规则命中统计模拟"哪些指令从未被用到"，计算瘦身收益并做回归闸门。

**问**：客服 Agent 的系统提示词经过两年迭代膨胀到 8000 token：二十几条"注意不要""必须先""如果遇到"，还嵌着一整段产品说明。团队不敢删——怕删了哪条行为就退化。提示词膨胀的代价是什么？怎么在不改坏行为的前提下科学地瘦身？

**答**：
- **结论**：膨胀的代价不只是钱：① **指令稀释**——关键约束（如"不得承诺赔付"）淹没在长文里，遵守率下降（Q7660 的挤占效应在系统提示词内部同样存在）；② **维护失控**——新旧条款互相矛盾（"总是先道歉"vs"不要过度道歉"），模型自行仲裁，行为漂移；③ **预算挤压**——8000 token 系统词 + 历史消息很快顶到窗口，历史被更早裁剪（Q7645）。瘦身方法论是**证据驱动的指令分级**：用生产 trace 统计每条指令的"可观察命中"（它约束的行为在会话里是否出现过），从未命中的指令分组处置——删除、合并、或降级为按需注入（工具调用时才拼进上下文）。
- **取舍**：① 删除类指令有风险上限，必须配**回归评测集**（覆盖每条指令的目标行为）做瘦身实验：一次只删一组，回归不过即恢复，小步快跑；② "防御性指令"（安全红线）不适用命中统计——没触发是好事，这类归安全层永不瘦身，且要定期用对抗样本验证有效（Q2318）；③ 按需注入（动态提示词）省 token 但增加工程复杂度与首 token 延迟，核心常驻指令保持静态。
- **实战**：① 提示词入库走版本管理（Q1140），每条规则带 ID，trace 里的命中统计按 ID 归因；② 瘦身实验记录：删除哪几条、回归集各场景分数变化、决策（删/留/合并），像代码 PR 一样留档；③ 把"系统提示词 token 数"做成监控指标，超过预算水位（如 4000）即触发瘦身评审，从源头防膨胀。

```python
"""提示词瘦身：指令命中统计 -> 分级处置 -> 回归闸门。"""
RULES = {
    "R01": {"text": "禁止承诺赔付", "class": "safety", "hits": 0},
    "R02": {"text": "先核对订单号再查询", "class": "behavior", "hits": 4120},
    "R03": {"text": "退货政策详细说明(嵌800字)", "class": "knowledge", "hits": 380},
    "R04": {"text": "не使用内部术语(俄语残留)", "class": "legacy", "hits": 0},
    "R05": {"text": "遇到投诉转人工", "class": "behavior", "hits": 96},
    "R06": {"text": "重复解释SLA条款(与R03重叠)", "class": "legacy", "hits": 60},
    "R07": {"text": "API限流说明(仅工具调用时相关)", "class": "on-demand", "hits": 0},
}
TOKENS = {"R01": 40, "R02": 30, "R03": 820, "R04": 60, "R05": 25,
          "R06": 310, "R07": 210}


def classify(r) -> str:
    if r["class"] == "safety":
        return "保留(安全层永不瘦身, 定期对抗验证)"
    if r["class"] == "legacy":
        return "删除(过期/矛盾)"
    if r["class"] == "on-demand":
        return "按需注入(工具调用时才拼入)"
    if r["hits"] < 100 and r["class"] == "knowledge":
        return "合并/压缩(低频长文)"
    return "保留"


def slim(plan: dict[str, str]) -> dict:
    removed = {k for k, a in plan.items() if a.startswith("删除")}
    ondemand = {k for k, a in plan.items() if a.startswith("按需")}
    merged = {k for k, a in plan.items() if a.startswith("合并")}
    base = sum(v for k, v in TOKENS.items() if k not in removed | ondemand | merged)
    keep_part = {k: TOKENS[k] for k in merged}
    return {"常驻": base, "合并后": sum(keep_part.values()) // 2,
            "按需(不占常驻)": sum(TOKENS[k] for k in ondemand)}


if __name__ == "__main__":
    plan = {k: classify(v) for k, v in RULES.items()}
    print(f"{'规则':<5}{'类':<10}{'命中':>6}{'token':>6}  处置")
    for k, r in RULES.items():
        print(f"{k:<5}{r['class']:<10}{r['hits']:>6}{TOKENS[k]:>6}  {plan[k]}")

    before = sum(TOKENS.values())
    after = slim(plan)
    resident = after["常驻"] + after["合并后"]
    print(f"\n系统提示词: {before} token -> 常驻 {resident} token "
          f"(省 {1 - resident / before:.0%}), 另有 {after['按需(不占常驻)']} token 按需拼入")
    print("回归闸门: 一次只删一组 -> 跑回归集 -> 行为退化即恢复, 小步快跑")
    print("结论：瘦身靠证据(命中统计)而非直觉; 安全指令永不瘦身; 预算水位防再膨胀")
```

**追问一**：命中统计为 0 的防御性指令为什么不能删？

→ 解析：因为"没有命中"有两种含义完全相反的解读：对功能性指令（如"先核对订单号"），零命中说明场景没出现或指令冗余；对防御性指令（"禁止承诺赔付""不输出内部信息"），零命中恰恰说明它在阻止行为——删掉后这些行为会**回来**，且通常以事故的形式被发现。防御层指令的验证方式是主动对抗：定期用诱导性输入测它是否仍然有效（红队测试），而不是等生产 trace 说话。指令分级的第一刀就是"安全/非安全"，统计方法只适用于后者。

**追问二**：按需注入指令会不会因为"不在场"而被模型忽略？

→ 解析：会。按需注入的指令在上下文里的位置靠后、权重感知低于系统提示词，遵守率通常略降，尤其是"工具使用规范"这类在多步任务中被后续内容稀释的指令。缓解手段：① 注入点贴近使用时机——在决定调用工具的那一轮才注入，而不是会话开头；② 注入内容压缩成 3-5 行要点式，别把整段文档塞回去；③ 关键约束（如"调用退款工具前必须人工确认"）不入"按需池"，宁可常驻。按需化的边界就是：**省 token 不能省在影响正确性的指令上**，收益和风险都要按条评估，不是一刀切。
