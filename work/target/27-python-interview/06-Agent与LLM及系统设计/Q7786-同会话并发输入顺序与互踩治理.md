### Q7786 · 用户双开两个窗口：同会话并发输入的消息顺序与互踩治理

难度：P6 ｜ 标签：会话并发、消息顺序、客户端时钟、双开互踩、串行化

基线：Python 3.12；模拟同会话双客户端并发发消息的乱序/互踩场景，实现"会话级排队 + 客户端序号裁决 + 生成锁"的治理模型与多设备状态同步，全标准库（threading）实跑。

**问**：用户手机和电脑同时开着同一个对话，两边各发一条消息，Agent 可能拿着乱序的两条消息生成回答，或者电脑的旧回复覆盖了手机的新对话。并发输入的正确模型是什么？消息顺序以服务端到达序还是客户端序为准？正在生成时来了新消息怎么办（打断/排队/合并）？

**答**：
- **结论**：同会话并发输入要治理三层：① **顺序裁决**：客户端时钟不可信（手机与电脑时钟差、网络延迟让"后发先至"），唯一稳定序是**服务端接收序**；但纯到达序可能与用户意图错位（电脑慢网的用户后按发送先到达），工程折衷是**客户端单调序号 + 服务端到达序兜底**——同客户端的序号定相对序（客户端内乱序重排，按序号），跨客户端用到达序（用户双开的两个窗口语义上就是"两个人"在说，到达序合理）。② **生成互斥**：Agent 正在流式生成时来了新消息，三种策略——**打断**（取消当前生成，新消息并入上下文重新生成，交互体验最好、token 浪费 Q7508 计费一致性要处理）、**排队**（当前生成完再处理，消息积压时要合并）、**合并**（生成窗口内到达的多条消息打包成一条上下文输入，节省往返）。默认策略按场景：聊天助手打断+合并，任务型 Agent 排队（打断代价高）。③ **状态同步**：双端的会话视图要收敛到同一服务端状态（消息列表 + 生成状态），客户端只做展示不做本地权威——两端口径不一致的根源就是本地乐观更新没有对齐服务端版本号。
- **取舍**：① 生成锁的粒度：会话级互斥（本卡）vs 消息级流水（每条消息独立生成独立回答，像群聊）——交互对话默认会话级（回答引用完整上下文），协作场景（多人同会话）消息级更自然但上下文一致性难；② 打断的实现成本：流式中断 + 已生成 token 的处理（丢弃/保留作部分答案，Q7727 截断语义）+ 计费对账，比排队复杂一档；③ 乐观 UI 与权威序：客户端本地先显示"已发送"（乐观），服务端确认后按**服务端序号**重排——顺序跳动是可接受的代价，乱序才是不可接受；④ 跨设备通知：设备 A 打断重生成时，设备 B 要实时感知（SSE/长连接推送生成状态，Q1175 流式协议），否则 B 看到旧回答继续对话，语义脱节。
- **实战**：① 消息信封标准化：`{client_id, client_seq, sent_at, content}` 三元组进每个消息，服务端分配 `server_seq`——排序逻辑全部基于 server_seq + client_seq 二级键，别用时间戳；② 会话入口排队器：每会话一个 FIFO 队列 + 一个生成锁，消息入队、锁空闲时出队处理——实现简单且天然防互踩；③ 观测指标：打断率、排队深度、双开并发率——打断率高说明生成太慢或 UI 没提示"正在生成"，排队深说明用户被静默积压；④ 演练：双设备并发脚本（两客户端同时发 5 条）作为回归用例，断言"服务端最终序与展示序一致、无消息丢失"。

```python
"""Q7786 同会话并发输入: 排队+序号裁决+生成锁(threading 实跑)。"""
import threading
import time
from collections import deque


class Session:
    def __init__(self):
        self.queue: deque = deque()
        self.lock = threading.Lock()
        self.gen_lock = threading.Lock()      # 会话级生成互斥
        self.server_seq = 0
        self.history: list[str] = []
        self.interrupted = 0

    def send(self, client_id: str, content: str, gen_ms: int = 30) -> dict:
        with self.lock:
            self.server_seq += 1
            seq = self.server_seq
            self.queue.append({"seq": seq, "client": client_id, "msg": content})
        self._process(gen_ms)
        return {"seq": seq}

    def _process(self, gen_ms: int):
        """取出队列消息: 有生成在跑则打断(合并新消息重答)."""
        while True:
            with self.lock:
                if not self.queue:
                    return
                batch = [self.queue.popleft()]
                while self.queue:             # 生成窗口内到达的消息合并
                    batch.append(self.queue.popleft())
            if self.gen_lock.locked():        # 生成中 -> 打断重生成
                self.interrupted += 1
            with self.gen_lock:
                time.sleep(gen_ms / 1000)     # 模拟流式生成
                self.history.extend(
                    [f"[{b['client']}] {b['msg']}(@{b['seq']})" for b in batch])
                return                        # 本批合并为一个回答


if __name__ == "__main__":
    sess = Session()
    # 双设备并发: 手机/电脑各发 2 条(线程同时 send)
    results: list[str] = []
    t1 = threading.Thread(target=lambda: results.append(str(
        sess.send("phone", "帮我看订单")["seq"])))
    t2 = threading.Thread(target=lambda: results.append(str(
        sess.send("pc", "等下,用退款那个功能")["seq"])))
    t3 = threading.Thread(target=lambda: results.append(str(
        sess.send("phone", "顺便查物流")["seq"])))
    for t in (t1, t2, t3):
        t.start()
    for t in (t1, t2, t3):
        t.join()
    print(f"最终会话历史(服务端序): {sess.history}")
    print(f"打断/合并次数: {sess.interrupted}, 无消息丢失: "
          f"{len(sess.history) == 3}")
    seqs = [int(h.split('@')[1].rstrip(')')) for h in sess.history]
    ok = (seqs == sorted(seqs) and len(sess.history) == 3
          and all(len(x) == 1 for x in results))
    print(f"校验: 服务端序单调 + 零丢失 + 请求序号回执 -> {'通过' if ok else '异常'}")
    print("结论：顺序以服务端序为准(客户端序号定相对序); 生成中到达的消息")
    print("      打断合并重答; 会话级生成锁防互踩, 本地乐观UI必须对齐服务端版本")
```

**追问一**：为什么"客户端时间戳排序"必错？client_seq 只解决"同一客户端内"的序，跨客户端乱序有什么真实的业务影响？

→ 解析：客户端时间戳排序的失效链：设备时钟偏差（手机 ±几秒很常见）、发送时刻与到达时刻的网络延迟差（WiFi 切 4G 的几秒漂移）、客户端时钟回拨（NTP 校准）——用户"后发先至"后，按时间戳排的消息序与用户感知的对话序相反，Agent 的回答基于错序上下文，轻则答非所问（"等下，用退款功能"排在"帮我看订单"之后才合理，乱了顺序回答就接错），重则状态机错乱（用户在 A 设备确认、B 设备又收到"待确认"的追问）。跨客户端到达序的业务影响：双开语义上近似"两个提问的人"，到达序虽然可能与"输入先后"不同，但每条消息都完整可见、上下文自洽，Agent 按到达序回答不会语义断裂；风险点是**用户在两个窗口交替推进同一任务**（A 窗口改了参数、B 窗口还按旧参数问）——这不是排序能解决的，是会话状态的同步问题，靠服务端权威状态 + 各设备实时推送（本卡第 ③ 层）治理。工程结论：**排序键必须单调且服务端权威；跨设备的"意图序"永远不可靠，治理对象是状态一致性而不是排序精度。**

**追问二**：打断正在生成的流式回答，已生成 token 与计费怎么处理？打断策略的误触发怎么防？

→ 解析：打断的三笔账：① **计费账**：已生成的 token 已经消耗（模型按生成计费），打断不退款——打断重生成意味着双倍消耗，高频打断的成本要有监控（打断率 × 平均已生成 token），Q7508 流式计费一致性的专项；② **体验账**：已流式展示的部分内容怎么办——完全消失（突兀）还是保留展示但标记"已更新"？主流做法是保留旧内容直到新内容首 token 到达（无空窗切换），旧内容折叠；③ **技术账**：取消流式连接（SSE 断开/取消信号）、上下文里已生成内容的处理（丢弃干净 vs 保留作"草稿"影响下一轮——丢弃干净，避免模型看到自己的半成品）。误触发防护：打断的触发条件不能是"收到新消息就打断"——**打字中**（用户还在输入，输入框有内容）的新消息事件不能打断（前端节流：输入停止 2 秒才真正提交）；**批量粘贴**（一次进 10 条）应该合并成一条而不是打断 10 次；打断了但新消息与生成内容无关（用户只是在另一个话题闲聊）——打断判据要结合语义相关性（轻量分类）或至少给"不打断继续完成"的选项（排队 + 完成后展示）。策略矩阵落地：默认"输入完成 + 语义相关 + 生成超过 2 秒"才打断，其余排队合并。一句话：**打断是体验优先的高价操作，触发条件要像熔断器一样有门槛、有统计、可回退。**
