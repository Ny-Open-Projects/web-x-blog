### Q7528 · 长上下文模型的取舍：语料都能塞进 128K，RAG 还有必要吗？

> 难度:★★★★ | 标签:RAG, 长上下文, 成本

**问**：模型窗口到了 128K-1M token，团队有人主张"全部语料直接塞上下文，砍掉检索系统"。什么时候这个判断是对的？什么时候是灾难？

**答**：结论：能塞不等于该塞。决策矩阵看四个量：**语料是否稳定可控**（单任务相关文档 <50K token 且随任务变化小）、**成本曲线**（每次请求都为全部语料付费 vs 检索只为相关块付费——1M token 上下文单价通常是 8K 的数倍，高频调用下成本差 10-100 倍）、**质量特征**（长窗口的"lost in the middle"：中部信息召回率显著低于首尾；RAG 把相关块放进近端反而更稳）、**延迟**（预填充与上下文长度近线性，128K 输入的首 token 延迟秒级到十秒级，RAG 检索 + 数 K 上下文是百毫秒级）。判断"对"的场景：一次性深读单文档（合同审阅）、小语料高频追问（prompt cache 友好）；"灾难"场景：语料持续增长的全库问答、多租户隔离要求、成本敏感的高频入口。

机理与实战：
- 成本账要算"边际"：长上下文 + KV cache 复用下，同一大前缀重复提问的边际成本会降一个量级——这是"小语料 + prompt cache"路线真正可行的原因；但语料一变（哪怕一个文档更新）缓存全失效，回退到全价预填充。检索路线的成本是稳定的：每次只增量付费。
- 质量账：长窗口塞满不代表模型"读完"了。中段信息利用率低是可复现现象，关键事实埋在中部的任务（"第 40 页的违约条款"）长上下文直塞的召回明显差；RAG 的隐性优势是**证据可溯源**（引用块 id），长上下文直塞的答案溯源要靠模型自律。
- 混合形态是主流终态：粗检索裁剪候选（top-k 块 + 层级摘要）→ 窗口内组装（预算分配器）→ 长窗口兜底（候选全塞）。窗口长度是"预算富余度"参数而不是架构选择——先按成本与延迟预算定窗口用量，再决定塞多少检索结果。

```python
# 基线:Python 3.9+ 纯标准库 ;成本-延迟决策模型
from dataclasses import dataclass


@dataclass
class RouteProfile:
    name: str
    input_tokens: int          # 每次请求输入量
    price_per_mtok: float      # 每百万 token 输入价
    prefill_ms_per_ktok: float # 预填充延迟系数 ms/千token
    cache_discount: float = 0.1


def cost_per_call(p: RouteProfile, qps_per_day: int,
                  cache_hit_rate: float = 0.0) -> float:
    billed = p.input_tokens * (1 - cache_hit_rate * (1 - p.cache_discount))
    return billed / 1_000_000 * p.price_per_mtok * qps_per_day


def first_token_latency_ms(p: RouteProfile) -> float:
    return p.input_tokens / 1000 * p.prefill_ms_per_ktok


def decide(corpus_tokens: int, calls_per_day: int, cacheable: bool) -> str:
    rag = RouteProfile("rag", input_tokens=4000, price_per_mtok=4.0,
                       prefill_ms_per_ktok=8)
    long = RouteProfile("long_ctx", input_tokens=corpus_tokens,
                        price_per_mtok=8.0, prefill_ms_per_ktok=15)
    cache = 0.6 if cacheable else 0.0
    c_rag = cost_per_call(rag, calls_per_day)
    c_long = cost_per_call(long, calls_per_day, cache)
    verdict = []
    verdict.append(f"RAG 日成本 ${c_rag:.1f} / 首token {first_token_latency_ms(rag):.0f}ms")
    verdict.append(f"长上下文 日成本 ${c_long:.1f}(缓存率{cache:.0%}) / "
                   f"首token {first_token_latency_ms(long):.0f}ms")
    verdict.append("决策: " + ("塞窗口可行" if c_long <= c_rag * 1.5
                              and first_token_latency_ms(long) < 2000
                              else "走检索路线"))
    return "\n".join(verdict)


def main() -> None:
    # 小语料高频追问 + 缓存友好 -> 直塞窗口可行
    print("场景A 小语料(30K)高频:\n", decide(30_000, 500, cacheable=True))
    # 大语料高频入口 -> 检索
    print("\n场景B 全库问答(900K)高频:\n", decide(900_000, 20_000, cacheable=False))


if __name__ == "__main__":
    main()
```

**追问一**：lost in the middle 的工程缓解手段？
答：位置编排——把最相关的块放上下文首尾（首条 system 后与最后一条用户消息前），中段放次相关；或层级摘要（长文档先摘要再按需展开）。可以用"针在稻草堆"探针集实测各位置的召回率，把自己的模型/供应商版本真实摸底，而不是引用论文结论。

**追问二**：多租户场景为什么几乎必须 RAG？
答：直塞窗口意味着"每次请求把全租户语料喂给模型"，成本爆炸且租户隔离靠 prompt 自律（可被注入突破）；RAG 检索层天然按租户过滤（元数据前置），上下文只进本租户内容，隔离是结构性的而不是纪律性的。

**背诵要点**：
- 决策四量：语料稳定性、边际成本（cache 复用 vs 检索增量付费）、lost in middle、首 token 延迟。
- 小语料 + 高频 + 缓存友好 = 直塞可行；全库问答/多租户/高频入口 = 必须检索。
- 终态是混合：粗检索裁剪 → 预算内组装 → 长窗口兜底。

**复盘追问**：
- 如何用针探针集量化自家模型各位置的信息利用率？
- 语料更新导致 prompt cache 全失效的成本尖峰如何预测与平滑？

## 背诵要点
- 窗口长度是预算参数：先定成本/延迟预算，再定塞多少。
- 多租户隔离靠检索层结构性过滤，不靠 prompt 纪律。
- 缓存复用是直塞路线的生死线，语料一动全失效。
