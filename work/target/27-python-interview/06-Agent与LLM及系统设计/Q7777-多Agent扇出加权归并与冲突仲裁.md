### Q7777 · 三个 Agent 吵起来了：多 Agent 扇出的加权归并与冲突仲裁

难度：P7 ｜ 标签：多 Agent、结果归并、冲突仲裁、加权投票、扇出架构

基线：Python 3.12；实现多 Agent 扇出的归并协议（(答案，置信度，权重) 三元组）与仲裁规则（加权共识 / 分歧升级），全标准库实跑。

**问**：营销 Agent、风控 Agent、合规 Agent 对"要不要发这张优惠券"给出三个不同结论——多 Agent 并行的意义在多样性，但归并时冲突怎么办？"取多数"什么时候是错的？归并协议的输入契约该怎么设计？仲裁不了的怎么办？

**答**：
- **结论**：归并协议的设计核心是**输入契约**：每个 Agent 回传的不只是结论，而是 `(答案, 置信度, 权重)` 三元组——置信度是 Agent 对自己结论的确信度，权重是该 Agent 在此问题域的权威度（合规对"能不能发"的话语权高于营销）。归并规则分两档：① **加权共识**：`得分 = 置信度 × 权重` 求和，最高者得票占比 ≥ 60%（共识阈值）时直接采纳；② **冲突升级**：得分分布过散（最高占比 < 60% 或存在实质性对立）时**不裁决，升级人工**——本卡演示：approve 1.38 vs reject 1.20，最高占比 53%，进仲裁失败分支。**"取多数"什么时候是错的**：当少数方是**高权威域**时——合规说不能发，营销和风控说能发，2:1 的多数恰恰是事故（合规否决不是意见是红线）。所以权重不是装饰：高风险域的 Agent 权重配一票否决位，普通域才用加权多数。
- **取舍**：① 冲突是 feature 不是 bug：三个 Agent 一致通过不等于结论正确（可能共享同一个错误前提——同源偏差），冲突率异常低也要警惕；② 置信度本身要校准：各 Agent 的"0.9"语义不同（有的模型自信有的保守），归并前按各自历史正确率做分位数归一，否则权重被置信度的量纲污染（Q7776 校准的跨 Agent 版）；③ 扇出的成本结构：N 个 Agent = N 倍 token，只在高错误成本决策上扇出（发券、放款、公开内容），日常任务单 Agent + 校验器足够；④ 升级不是失败是协议：升级率监控 + 升级案例回流评测集，人工裁决的历史数据反过来校准各 Agent 权重——仲裁系统是活的。
- **实战**：① 归并器独立成组件：输入三元组流、输出决策 + 依据（谁投了什么、得分几何），审计可回放——决策必须有"为什么"（Q7523 引用溯源的决策版）；② 冲突类型的语义分类：值冲突（发不发）、事实冲突（库存 100 还是 50——后者该对账数据而不是投票）、标准冲突（用什么口径算 ROI）——只有值冲突适合仲裁，事实冲突去查数据，标准冲突升级定口径；③ Agent 的角色卡里写明"本 Agent 的一票否决域"与"建议域"，归并器按卡执行；④ 灰度：新 Agent 接入归并时先影子模式（只记录不投票），人工对比其结论与最终决策，校准后再给权重。

```python
"""Q7777 多 Agent 扇出结果归并: 加权投票 + 冲突检测 + 无法仲裁时升级。"""
# 三个专家 Agent 对"该不该发这个优惠券"给出判断 (答案, 置信度, 专长权重)
AGENTS = [
    ("approve", 0.9, 1.0),    # 营销 Agent: 高置信
    ("approve", 0.6, 0.8),    # 风控 Agent: 中置信
    ("reject", 0.8, 1.5),     # 合规 Agent: 高置信 + 高权重(一票意义大)
]


def weighted_vote(votes: list[tuple[str, float, float]]) -> dict:
    tally: dict[str, float] = {}
    for ans, conf, weight in votes:
        tally[ans] = tally.get(ans, 0.0) + conf * weight
    total = sum(tally.values())
    best = max(tally, key=tally.get)
    share = tally[best] / total
    split = len(tally) > 1 and max(tally.values()) / total < 0.6
    return {"tally": tally, "best": best, "share": round(share, 2),
            "conflict": split}


def decide(votes: list[tuple[str, float, float]]) -> tuple[str, str]:
    r = weighted_vote(votes)
    if not r["conflict"]:
        return r["best"], f"共识: {r['best']} (得票 {r['share']:.0%})"
    # 冲突: 少数高权威方的反对不允许被多数淹没 -> 升级人工
    return "escalate", (f"仲裁失败: {r['tally']} 分布过散(最高 {r['share']:.0%}), "
                        f"升级人工复核")


if __name__ == "__main__":
    r1 = decide([("approve", 0.9, 1.0), ("approve", 0.8, 1.0), ("approve", 0.7, 1.0)])
    r2 = decide(AGENTS)
    print(f"全票场景: {r1}")
    print(f"分歧场景: {r2}")
    v = weighted_vote(AGENTS)
    print(f"分歧票型: {v['tally']} -> 最高 {v['share']:.0%}, conflict={v['conflict']}")
    ok = r1[0] == "approve" and r2[0] == "escalate" and v["conflict"] is True
    print(f"校验: 共识直行 + 分歧升级 -> {'通过' if ok else '异常'}")
    print("结论：多 Agent 归并的输入契约是(答案,置信度,权重)三元组;")
    print("      仲裁靠权重与阈值, 仲裁不了的必须升级人工——静默取多数是最大的坑")
```

**追问一**：为什么"事实冲突"不能进投票？举一个投票把错数据合法化的例子。

→ 解析：投票的前提是分歧来自**价值判断**（同一事实、不同立场），而事实冲突的分歧来自**数据源不同**——这时正确答案是客观存在的，投票只是在给错误数据加权。典型事故：库存 Agent 读的是 5 分钟前的缓存（100 件），实时 Agent 读的是 DB（已售罄），分析 Agent 用昨天的快照算出"销量趋势良好"——三个 Agent 对"能不能接这单"投票 2:1 放行，超卖就是结果。正确处理：**事实冲突走对账不走向投票**——归并器识别出"两个结论基于不同时间戳/不同数据源"时，先触发数据仲裁（取最新权威源、或标记数据不可用直接拒绝），Agent 的意见只在数据一致后才进入价值投票。实现上要求三元组里再加**依据字段**（引用的数据源与时间戳，Q7523 溯源）：归并器先做依据一致性检查，依据冲突即短路进对账流程。判据一句话：**能查证的不投票，查不了的不静默**——投票是给查不了的价值判断用的最后手段。

**追问二**：多个 Agent"全体一致"就安全吗？同源偏差（shared bias）怎么检测？

→ 解析：不安全，一致性可能是**共享偏差的伪装**：所有 Agent 读同一份有误的上下文、用同一底座模型（错误假设共享）、或提示里嵌了同一个错误前提——三个 Agent 高度一致地给出同一个错误答案，比 2:1 分歧更危险，因为它伪装成"共识=正确"。检测手段：① **输入消融**：对关键前提做扰动重跑（把"库存充足"换成"库存紧张"再扇出一次），结论随扰动翻转说明 Agent 们在独立推理，纹丝不动说明在复读共同前提；② **底座异构**：不同 Agent 用不同厂商/不同代际的模型——同源偏差的概率随异构性指数下降，成本换多样性（Q7771 self-consistency 的跨模型版）；③ **一致性率监控**：历史数据里某类决策的"全票率"异常高于基线（比如从 60% 涨到 95%），往往意味着某个共享输入退化成唯一信号源（其他输入失效了）；④ 交叉验证样本：定期构造"已知标准答案"的决策样本进扇出，量三 Agent 与标准答案的距离。多 Agent 架构的价值公式：**多样性收益 = Agent 间独立性 × 各自准确率**——独立性归零时，N 个 Agent 等于 1 个 Agent 花 N 倍钱。
