### Q7714 · 超时重试的尾延迟放大：p99 被重试预算拖垮

难度：P7 ｜ 标签：尾延迟、重试预算、超时、hedged request

基线：Python 3.12；纯 Python 模拟重试对 p99/p999 的放大。

**问**：LLM 调用设了 2 秒超时、失败重试 2 次。单次调用的 p99 是 1.8 秒，按说最多 6 秒。但线上监控的 p99 从 2 秒涨到 3 秒、p999 到了 4 秒，极端请求接近 6 秒，用户侧超时率反而上升。重试不是提高成功率吗，为什么把尾延迟推得更高？

**答**：
- **结论**：重试把"单次尾延迟"变成"多次尾延迟的**最大值**"。设单次超时 T、重试 n 次，最坏耗时是 (n+1)×T，p99 大概率为 (n+1) 个样本中至少一个落入尾部的分位——重试次数越多，**至少一次慢**的概率越高，尾延迟被系统性放大。更糟的是重试会**增加上游负载**：上游变慢 → 超时 → 重试 → 负载更高，形成正反馈，尾延迟进一步恶化。
- **取舍**：重试适合"瞬时错误"（连接重置、429、明确未执行的 5xx），不适合"上游过载导致的慢"。治理手段：**重试预算**（按成功率/错误率动态限制重试比例，如 Google SRE 的 retry budget）、**只对幂等且未执行的请求重试**、**hedged request**（并行发一份，取先返回的，代价是双倍成本）、**超时分层**（总预算固定，重试从剩余预算里扣，而不是每次重新计时）。
- **实战**：① 总超时预算 = 用户可接受等待，重试不能突破总预算；② 记录每次请求的 attempt 数与总耗时，区分"首次成功"与"重试成功"的 p99；③ 对 429/5xx 用指数退避 + 抖动，别立即重试；④ 监控重试率与上游负载的相关性，重试率升高时优先降载而不是加机器。

```python
import random


def simulate(attempts: int, timeout_s: float, n: int = 200_000) -> dict[str, float]:
    rng = random.Random(11)
    totals = []
    for _ in range(n):
        elapsed, ok = 0.0, False
        for _ in range(attempts):
            latency = min(rng.lognormvariate(-0.3, 0.55), timeout_s)
            elapsed += latency
            if latency < timeout_s:
                ok = True
                break
        totals.append(elapsed)
    totals.sort()
    pick = lambda q: totals[int(q * (len(totals) - 1))]
    return {"p50": pick(0.50), "p99": pick(0.99), "p999": pick(0.999)}


if __name__ == "__main__":
    for attempts in (1, 2, 3):
        print(f"最多 {attempts} 次:", {k: round(v, 2) for k, v in simulate(attempts, 2.0).items()})
    print("结论：重试次数增加会把尾延迟推向 (n+1)×timeout，需用总预算约束")
```

**追问一**：为什么"每次重试重新计时"会让总延迟失控？
→ 解析：每次 attempt 都拿完整的 2 秒预算，最坏总耗时就是次数 × 2 秒，而用户只愿意等 3 秒。正确做法是**deadline 传播**：请求带一个绝对截止时间，每次重试只能用剩余预算，剩余不足就直接失败，避免把用户拖到超时之后。

**追问二**：hedged request 为什么能降尾延迟，代价是什么？
→ 解析：在 p95 延迟时点再发一份相同请求，两份取先返回的，能把"偶发慢"从尾延迟里削掉；代价是额外请求与成本（通常增加 5%-10% 流量），且要求请求幂等或只读，否则会重复产生副作用。
