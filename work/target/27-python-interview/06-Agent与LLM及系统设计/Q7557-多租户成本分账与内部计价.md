### Q7557 · 多租户成本分账与内部计价（showback）

难度：P6 | 标签：成本工程、多租户、showback、成本归因

**问**：LLM 平台月账单 750 美元，三个业务线都说"不是我花的"。没有分账的平台会发生什么？请求级打标、聚合账单与公共成本分摊怎么做？showback 和 chargeback 的顺序为什么不能反？

**答**：
- **结论**：没有分账的平台必然走向"公地悲剧"：没人有动力选小模型、开缓存、砍冗余调用，成本随用量线性失控。分账三件套：① 请求级打标：网关在入口注入租户/模型/任务模板标签，缺标签的请求进"未归因"桶并告警（未归因率是分账质量的硬指标）；② 聚合账单：token 计价（输入/输出/缓存三价分离，缓存命中的输入按折扣价），按租户月度聚合；③ 公共成本分摊：网关、评测、监控这类公共开销按各租户直接费用占比分摊，避免"平台费没人认"。本例 growth 承担 68% 的费用，异常归因先看"模型选择与缓存命中率"再看量增长。
- **取舍**：showback（只看账不扣钱）与 chargeback（真扣预算）的顺序不能反：先 showback 让团队习惯"成本有主"，暴露出大量"大模型干小模型的活"的低 hanging fruit；等成本行为被治理、口径被认可后再上 chargeback，否则第一天就会引发"标签打得对不对"的口水仗而不是降本行动。
- **实战**：落地清单：① 网关强制打标（缺标签请求拒绝或归入告警桶）；② 月度账单自动发送 owner，附环比与 Top 任务模板；③ 缓存命中单独计价列——让"接缓存的团队账单变薄"的激励可见。

```python
"""多租户成本分账（showback）：请求级打标、聚合账单与分摊策略。"""
from collections import defaultdict
from dataclasses import dataclass

PRICE = {"gpt-main": (3.0, 15.0), "gpt-mini": (0.3, 1.2)}   # $/1M：输入, 输出

@dataclass
class Usage:
    tenant: str
    model: str
    in_tok: int
    out_tok: int
    cached_tok: int = 0        # 缓存命中的输入 token（供应商按折扣计费）

def cost_of(u: Usage) -> float:
    pin, pout = PRICE[u.model]
    billable_in = max(u.in_tok - u.cached_tok, 0)
    cached_rate = pin * 0.5                       # 缓存折扣价简化
    return (billable_in * pin + u.cached_tok * cached_rate) / 1e6 + u.out_tok / 1e6 * pout

# 一个月的用量样例（三个租户）
ledger = [
    Usage("growth", "gpt-main", 90_000_000, 12_000_000),
    Usage("support", "gpt-mini", 300_000_000, 40_000_000, cached_tok=120_000_000),
    Usage("growth", "gpt-mini", 80_000_000, 10_000_000),
    Usage("data", "gpt-main", 30_000_000, 2_000_000),
]
bills = defaultdict(float)
for u in ledger:
    bills[u.tenant] += cost_of(u)

GATEWAY_OVERHEAD = 40.0     # 网关/评测等公共成本，按租户费用占比分摊
total_direct = sum(bills.values())
for tenant, fee in bills.items():
    shared = GATEWAY_OVERHEAD * fee / total_direct
    print(f"{tenant:<8} 直接成本 ${fee:8.2f} + 分摊 ${shared:5.2f} = ${fee + shared:8.2f}")

spike = max(bills, key=bills.get)
print(f"异常归因：最大头是 {spike}，"
      f"先查'模型选择（大模型干小模型的活）'与'缓存命中率'，再看量增长")
print("纪律：请求级打标（租户/模型/任务模板）在网关完成；"
      "showback 先行（只看账不扣钱），成本有主后再谈 chargeback")
```

**追问链**：
1. 追问一层：为什么缓存命中要单独计价列？——缓存是唯一"用得越多花越少"的杠杆，混在总价里它的激励就不可见；单列后"support 缓存命中 40%、账单比上月薄"成为可复制的榜样，分账的真正目的是塑造行为而不只是记账。
2. 追问二层：分摊公共成本为什么按"费用占比"而不是"请求数占比"？——公共成本（网关、评测、监控）大致随费用规模走（贵模型调用占用更多网关算力与评测预算）；按请求数分摊会让"用 mini 模型的高频租户"补贴"用大模型的低频租户"，扭曲激励。分摊规则要写进文档并保持年度稳定。

**背诵要点**：
1. 无分账 = 公地悲剧；分账三件套：网关强制打标、三价分离聚合、公共成本按费用占比分摊。
2. 未归因率是分账质量硬指标，缺标签请求进告警桶。
3. showback 先行、chargeback 后置：先塑造行为再谈扣款，顺序反了只剩口水仗。

**复盘追问**：
1. 月底发现 8% 的用量没有租户标签，怎么处理？（当月进"未归因"桶显性展示 + 网关补齐打标校验；追查来源通常是内部脚本绕过网关直连——这正是分账要抓的漏点）
2. 为什么"某租户成本突增"的第一嫌疑是模型选择而不是用量增长？（用量增长有业务信号可对照；大模型干小模型的活、缓存失效这类"单价漂移"没有业务解释且往往一夜发生——先查单价构成再查量）
