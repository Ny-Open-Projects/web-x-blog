### Q7631 · 回归评测跑批与线上流量共享模型配额的错峰容量账

难度：P6 ｜ 标签：容量规划 / 评测 / 配额

**问**：模型端点限流 2000 TPM 级别的并发预算是全租户共享的。线上高峰把配额吃掉大半后，每次 PR 触发的回归评测（几百个用例并发）就撞限流，评测跑 40 分钟、结果还因 429 重试失真。评测流量和线上流量怎么分预算？"错峰跑"和"拆配额"怎么选？

**答**：
- **结论**：先算账。评测负载 = 用例数 × 每用例请求数（多轮/重试）× token 密度；线上峰值预留 = P99 峰值 × 安全系数。两种分法：**拆配额**——评测用独立 API key/项目，配额硬隔离，互不挤压但配额申请和成本分开算；**错峰**——评测绑定低峰窗口（线上 P99 谷值时段），共享配额但争抢为零，代价是反馈延迟（提交后要等窗口）。判定标准：回归评测的**时效要求**——PR 门禁需要 10 分钟内反馈就必须拆配额（错峰满足不了），日级全量回归可以错峰。评测失真问题独立于配额：429 重试会拉长个别用例时延，而很多评测指标（响应时延分位、流式 TTFT）对时延敏感，被限流污染的评测结果不能当回归基线——所以"评测流量必须限速稳定"本身是指标效度要求，不只是礼貌问题。并发上限推导：评测并发 = min(分配配额 / 单用例速率, 用例并发上限)，并用令牌桶全局限速（Q7122 同源：全局限流器，worker 只是消费者）。
- **取舍**：评测用便宜模型还是与线上一致模型？回归门禁的意义是"行为与线上一致"，用便宜模型回归对不齐；折中：PR 门禁跑分层抽样的小集（Q7555）用一致模型，日级全量错峰跑大集——预算一致性与覆盖度的平衡。另一个变量：评测失败后是否自动重跑？撞限流的 run 要标记 invalidated 重跑，而不是把 429 污染的结果写进趋势线。
- **实战**：① 评测 runner 全局令牌桶 + 并发上限，速率 = 分配配额 × 0.8；② 评测窗口监控：429 率 >1% 的 run 标记 invalid 不进基线；③ 拆配额时评测项目独立计费（Q7557 成本分账），防止评测暴涨挤占生产预算却看不见；④ 全量回归错峰跑并记录实际耗时与配额占用，作为扩配额申请的证据。

```python
# 评测配额账: 并发 = min(分配配额x0.8/单用例速率, 用例上限); 429>1% 判 invalid
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class EvalBudget:
    quota_rpm: float               # 本评测流分配到的配额(请求数/分)
    case_latency_s: float          # 单次请求平均时长
    cases: int
    reqs_per_case: int = 10        # 多轮/多请求用例
    max_concurrency: int = 64

    def concurrency(self, safety: float = 0.8) -> int:
        """并发 = 配额rps x safety x 单请求时长(在途请求数), 封顶并发上限。"""
        by_quota = self.quota_rpm / 60 * safety * self.case_latency_s
        return int(min(by_quota, self.max_concurrency))

    def run_minutes(self, safety: float = 0.8) -> float:
        c = self.concurrency(safety)
        return self.cases * self.reqs_per_case * self.case_latency_s / c / 60


def valid(run_429_rate: float, threshold: float = 0.01) -> bool:
    return run_429_rate <= threshold


def main() -> None:
    # 线上抢走配额: 评测只剩 300 rpm, 并发被压到 24
    starved = EvalBudget(quota_rpm=300, case_latency_s=6.0, cases=400)
    assert starved.concurrency() == 24            # 300/60*0.8*6
    assert 15 < starved.run_minutes() < 20        # ~16.7min, 反馈太慢
    # 拆配额: 评测专属 60k rpm -> 并发封顶 64, 分钟级反馈
    isolated = EvalBudget(quota_rpm=60_000, case_latency_s=6.0, cases=400)
    assert isolated.concurrency() == 64
    assert isolated.run_minutes() < 10
    assert not valid(0.05) and valid(0.003)
    print(f"抢配额: c={starved.concurrency()} {starved.run_minutes():.0f}min; "
          f"拆配额: c={isolated.concurrency()} {isolated.run_minutes():.1f}min")
    print("OK: PR 门禁要拆配额, 日级全量可错峰; 429>1% 的 run 不进基线")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"被限流污染的评测结果不能进基线"，即使通过率看起来正常？
→ 一句话提示：时延类指标（TTFT/总时延分位）被 429 退避系统性抬高，重试还可能改变多轮路径走向——污染的 run 与健康 run 不可比，进基线等于把噪声固化成对照物，之后的回归误报全是它引起的。

**追问 2**：错峰窗口里评测和线上仍偶发撞车，怎么兜底？
→ 一句话提示：评测侧令牌桶对 429 做 AIMD 反馈降速（Q7122 同源），线上优先级永远高于评测（评测可中断可重跑）；窗口选择依据线上 24h 流量曲线的谷值而非"凌晨"拍脑袋。

## 背诵要点
- 分配公式：评测并发 = min(分配配额×0.8/单用例速率, 并发上限)；拆配额 vs 错峰的判定标准 = 评测反馈时效要求（PR 门禁必须拆配额）。
- 评测限速是指标效度要求：429 率 >1% 的 run 标记 invalid 不进基线，时延类指标被退避污染不可比。
- 全局令牌桶限速 + AIMD 反馈 + 评测项目独立计费分账（Q7557），线上流量优先级恒高于评测。

## 复盘追问
- 为什么"评测撞限流跑 40 分钟"不只是慢，还会让结果失真？提示：不同用例在窗口内遭遇的限流程度不同，时延分布被非均匀污染，分位数失去统计意义；配额账和指标效度要一起算。
- 评测配额应该怎么"按证据申请扩容"？提示：记录错峰窗口的实际占用曲线与 invalid 率，用"配额不足 → 结果失效 → 门禁延迟"的业务代价链向平台方申请，而不是直接要数字。
