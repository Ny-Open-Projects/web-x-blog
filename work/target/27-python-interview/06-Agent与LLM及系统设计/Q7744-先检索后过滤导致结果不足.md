### Q7744 · 先向量检索再按租户过滤：top_k 里只剩 2 条，正确答案早在第 15 名

难度：P7 ｜ 标签：RAG、元数据过滤、pre-filter、post-filter、召回

基线：Python 3.12；用余弦相似度 + 线性扫描模拟向量检索，对比"后过滤"与"预过滤"。

**问**：多租户知识库，向量检索统一 `top_k=10`，取回后再在应用层按 `tenant_id` 过滤。上线后小租户的问答质量极差，日志显示检索回来的 10 条里有 8 条是别的租户的，过滤后只剩 2 条，有时 0 条。更奇怪的是，用小租户自己的问题去搜，明明有一条高度相关，却总是不出现。为什么？

**答**：
- **结论**：这是典型的 **post-filter（先检索后过滤）** 问题。向量索引对"所有租户的数据"一起建，`top_k=10` 是在**全局**取前 10；大租户数据多，占满了名额，小租户能挤进前 10 的只有零星几条，正确答案可能排在第 15、第 50，根本没被取回——过滤只能删，不能补。**过滤发生在截断之后，召回上限已经被烧掉了**。
- **取舍**：三种做法：① **pre-filter**：把租户条件下推到检索（pgvector 的 `WHERE tenant_id = $1` 会和向量排序一起在索引扫描中过滤；Qdrant/Milvus 的 `filter` 参数同理），保证 `top_k` 是"过滤后的 10 条"；② **分区/多租户隔离索引**：每租户一个 collection/partition，检索天然只在本租户内，代价是索引数量与运维复杂度（小租户可以合并到共享分区，但要保证过滤下推）；③ **扩大候选再过滤**：`top_k * 10` 再过滤，简单但只是缓解——租户差距越大越无效，而且成本翻十倍。
- **实战**：① 只要检索结果需要按任何维度过滤，就必须确认该维度**支持过滤下推**（看执行计划/`EXPLAIN`，别信文档）；② 监控"过滤后剩余条数"的分布，`< top_k` 的比例高就是信号；③ 评测集按租户分层，别用一个大租户的语料评估全站；④ 向量库的 HNSW 在过滤很严时可能退化为暴力扫描，要设置"过滤后候选比例"阈值，必要时切 IVFFlat 或分区。

```python
"""post-filter 把 top_k 烧在别的租户上；pre-filter 才是过滤后的 top_k。"""
import math

DOCS = []
for i in range(60):
    tenant = "A" if i % 6 == 0 else "B"        # 小租户 A：10 条；大租户 B：50 条
    DOCS.append({
        "id": f"doc-{i:02d}",
        "tenant": tenant,
        "vec": (1.0, i / 60),                  # 与查询的相似度随手构造
        "text": f"{tenant} 租户的政策文档 {i}",
    })
QUERY = (1.0, 0.0)
GOLD = "doc-12"                                # A 租户的正确答案


def cosine(a: tuple[float, ...], b: tuple[float, ...]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    return dot / (na * nb)


def search(tenant: str | None, top_k: int) -> list[dict]:
    """tenant=None 表示不过滤（全局检索）；否则为 pre-filter。"""
    candidates = [d for d in DOCS if tenant is None or d["tenant"] == tenant]
    ranked = sorted(candidates, key=lambda d: -cosine(QUERY, d["vec"]))
    return ranked[:top_k]


if __name__ == "__main__":
    top_k = 10

    post = [d for d in search(None, top_k) if d["tenant"] == "A"]
    pre = search("A", top_k)

    print("post-filter: 全局 top10 里 A 租户的:", [d["id"] for d in post])
    print("  A 租户最终拿到:", len(post), "条")
    print("pre-filter : A 租户 top10:", [d["id"] for d in pre][:5], "...")
    print("  A 租户最终拿到:", len(pre), "条")

    global_rank = [d["id"] for d in search(None, len(DOCS))].index(GOLD) + 1
    print(f"\n正确答案 {GOLD} 的全局排名: {global_rank}（top_k={top_k} 取不到）")
    print("  出现在 post-filter 结果里:", GOLD in [d["id"] for d in post])
    print("  出现在 pre-filter 结果里 :", GOLD in [d["id"] for d in pre])

    # 扩大候选只能缓解：租户差距越大越无效
    for factor in (1, 3, 10, 30):
        got = [d for d in search(None, top_k * factor) if d["tenant"] == "A"]
        print(f"  候选 top_k×{factor:<2} -> A 租户 {len(got):>2} 条, 命中金标: {GOLD in [d['id'] for d in got]}")
    print("\n结论：过滤必须下推到检索；post-filter 的召回上限由全局竞争决定")
```

**追问一**：过滤下推之后，为什么检索反而可能变慢？

→ 解析：HNSW 是"沿图贪心走"，过滤条件会剪掉大量邻居，导致可达节点变少、候选不足，引擎只能扩大 `ef_search` 甚至退化为**暴力扫描**来凑够 `top_k`。选择性越低（比如租户只占全库 0.1%），退化越明显。所以"下推"解决的是召回正确性，延迟要靠别的手段补：按租户分区（每区独立图）、把过滤维度做进索引的 payload 并限制候选比例、或对小租户直接走精确检索（数据量小，暴力扫也快）。

**追问二**：租户隔离只靠 `tenant_id` 过滤够吗？

→ 解析：不够。`tenant_id` 是应用层传进来的参数，一旦被注入/写错（比如从请求体取而不是从鉴权上下文取），就会跨租户泄露。正确做法是**双保险**：① 检索层用行级安全（PG 的 RLS、向量库的 payload 强制过滤）绑定鉴权上下文，应用代码无法绕过；② 评测与巡检里加"跨租户召回"的负向用例（用 A 的查询检索 B 的语料，必须 0 命中）。另外 embedding 缓存、重排缓存、日志里的 chunk 也要带租户维度，泄露常发生在这些旁路。
