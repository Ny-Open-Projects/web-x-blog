### Q7633 · HITL 审批等待期的资源占用成本账：暂停会话占用什么、等多久、花多少

难度：P6 ｜ 标签：成本工程 / HITL / 会话生命周期

**问**：Agent 关键操作走人工审批（HITL）。上线后发现"等待审批中的会话"越积越多——审批人半天不看，会话把内存里的上下文、数据库连接、幂等预留都占着，超时默认策略又不敢乱设。等待期的会话到底占用哪些资源？怎么设计暂停态让"等三天"和"等三秒"成本一样？

**答**：
- **结论**：等待期的成本在**资源持有而非计算**：① 内存——上下文消息树常驻进程（几 MB/会话，数千个等待会话就是 GB 级）；② 连接——DB/Redis 连接被会话占着（Q6603 同源：池被慢外呼占满的模式换了个马甲）；③ 预留副作用——预扣的幂等 token、预占的库存/配额，长期等待要么占用别人额度要么到了自动释放期；④ 恢复窗口——审批到达时若实例重启过，内存态会话根本恢复不了。正确设计是**暂停态显式化**：审批点即持久化检查点（消息树+待执行动作快照），进程内会话立刻释放（内存/连接全还），审批完成时从存储恢复继续——让等待成本降到"一行状态记录"。超时策略分层：审批超时（如 24h）→ 默认动作按操作风险分级（低危自动拒绝并通知，高危升级人工），默认动作必须可审计（Q1149/Q1150 基础上往前一步）。成本账：`等待成本 = 会话数 × 平均等待时长 × 每会话持有成本`，持久化方案把持有成本降三个数量级。
- **取舍**：暂停态存多少？全量快照（可恢复性最强，体积大）还是存"待执行动作+输入指针"（紧凑，恢复时重建上下文）？审批只是放行/拒绝一个**已确定的动作**，不需要完整上下文在场——审批队列只需动作描述+参数+风险级；只有"审批后要继续对话"才需要检查点。所以两段式：审批队列存动作（轻），对话恢复存检查点（按需）。另一个取舍：审批超时前提醒（如 20h 时推送催办）比超时自动动作更省钱，但打扰审批人——按操作风险配提醒策略。
- **实战**：① `pause_for_approval()` 强制：写检查点 → 释放连接 → 会话状态置 paused；② 审批队列独立存储，含动作 schema、参数、风险级、超时时间与默认动作；③ 恢复走统一回放路径（与崩溃恢复共用，Q1147/Q1148），不写第二条恢复逻辑；④ 监控 paused 会话年龄分布，长尾（>24h）告警并按策略清退；⑤ 幂等预留 TTL 与审批超时对齐，避免"审批通过但预留已过期"。

```python
# HITL 成本账: 暂停态持久化把持有成本从 常驻资源 降到 一行状态记录
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class SessionHold:
    waiting_sessions: int
    context_mb: float           # 常驻上下文
    connections: int            # 占用的池连接
    hold_hours: float


def in_memory_cost(s: SessionHold) -> float:
    """进程内等待: 内存GB + 连接占用。"""
    mem_gb = s.waiting_sessions * s.context_mb / 1024
    return mem_gb


def persisted_cost(s: SessionHold) -> float:
    """检查点方案: 只存一行状态记录, ~2KB/会话。"""
    return s.waiting_sessions * 2 / 1024 / 1024   # GB


def approve(session: dict) -> dict:
    """恢复: 与崩溃恢复共用回放路径。"""
    assert session["state"] == "paused"
    return {**session, "state": "running"}


def main() -> None:
    s = SessionHold(waiting_sessions=3000, context_mb=2.0,
                    connections=1, hold_hours=24)
    assert in_memory_cost(s) > 5.8            # ~5.9GB 常驻内存
    assert persisted_cost(s) < 0.006          # ~6MB 状态记录
    assert in_memory_cost(s) / persisted_cost(s) > 900
    paused = {"state": "paused", "action": "refund_500",
              "risk": "high", "deadline_h": 24}
    resumed = approve(paused)
    assert resumed["state"] == "running"
    print(f"进程内等待 {in_memory_cost(s):.1f}GB vs 检查点 "
          f"{persisted_cost(s)*1024:.0f}MB -> 差三个数量级")
    print("OK: 审批队列存动作(轻), 对话恢复存检查点(按需); 幂等TTL对齐审批超时")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"审批队列只存动作、不存上下文"是两段式的关键？
→ 一句话提示：审批的决策输入是动作描述与参数（风险级/影响面），不需要几十 KB 的对话历史在场；把审批与对话恢复解耦后，审批队列轻到可以全量常驻内存，而昂贵的检查点只在真正要继续对话时才恢复。

**追问 2**：幂等预留 TTL 与审批超时不对齐会发生什么？
→ 一句话提示：预留先过期 → 审批通过时动作重复执行或额度已被释放给别人；预留后过期 → 拒绝的会话白占额度到 TTL 结束——对齐规则是 TTL ≥ 审批超时 + 执行时长余量，且到期未批的预留随默认动作一起释放。

## 背诵要点
- 等待成本在资源持有：内存（上下文常驻）+ 池连接 + 幂等预留 + 恢复窗口；暂停态持久化把数千会话从 GB 级降到 MB 级（差三个数量级）。
- 两段式：审批队列只存动作（描述/参数/风险级/超时/默认动作），对话恢复走检查点与崩溃恢复共用同一回放路径。
- 默认动作按风险分级且可审计；幂等预留 TTL ≥ 审批超时 + 执行余量；paused 会话年龄分布长尾告警。

## 复盘追问
- 为什么"等三秒和等三天成本一样"是判断暂停态设计是否正确的标准？提示：持有型等待的成本与时长线性相关（内存/连接/额度都是按持有时间累积），持久化等待成本与时长无关——成本曲线形状直接暴露设计缺陷。
- 实例重启后审批到达，最差会发生什么？提示：内存态会话丢失，审批结果无处落地（动作丢或重复）——这就是"审批点必须已持久化"的刚性理由，恢复逻辑与崩溃恢复共用也是为了这个一致性。
