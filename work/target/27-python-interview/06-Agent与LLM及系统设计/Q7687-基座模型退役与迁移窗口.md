### Q7687 · 供应商宣布退役你的模型：迁移窗口与版本演进剧本

难度：P6 ｜ 标签：版本演进、模型退役、迁移规划
基线：OpenAI 模型退役流程（deprecation 公告 → 关停日期，通常给 3-6 个月）；anthropic 同类。

**问**：供应商公告"model-x-2024-08 六个月后停服"，你们的三大场景（客服、文档解析、内部分析）都 pin 在这个版本上。退役迁移的剧本怎么排？窗口期的容量与风险账怎么算？

**答**：**结论**：迁移剧本四阶段：① **盘点周**——按"模型版本字符串"盘点全部引用（代码、配置、prompt 注册表、批处理任务），每个场景标注流量占比与"可替换性风险"；② **候选评测周**——选 2-3 个候选模型在评测集上跑回归（正确率/长度/格式/延迟四卡点），产出替换矩阵（场景 × 候选 × 分数），不同场景可以选不同目标——不是全量升到同一个新版本；③ **灰度月**——按流量 5%→25%→50%→100% 切换，每个场景独立开关与回滚；④ **关停前缓冲**——留 2-4 周全量跑新模型后，把旧版本引用归档（保留请求样本用于事后归因）。窗口风险账：退役日后的不可用风险是刚性的（到期即 410 错误全量失败），所以**日历倒排**——评测与灰度的最坏路径时长必须 < 窗口的 70%，剩下 30% 是缓冲。

**取舍**：一步到位（全场景换最新旗舰）与分场景替换的取舍：一步到位迁移成本低（一套评测、一次灰度）但成本账可能恶化（旗舰贵）；分场景替换能精确优化每场景的"质量-成本"点，但要维护多模型调用矩阵——网关层多模型路由本来就是标配，倾向分场景。另一关键取舍：**要不要趁机换供应商**？窗口期同时换供应商 = 两个大变更叠加，事故概率倍增，原则是"一次迁移只改一个变量"，换供应商另开窗口。

**实战**：迁移倒排日历与替换矩阵（标准库）：

```python
# 模型退役迁移：倒排日历 + 场景替换矩阵
from datetime import date, timedelta

retire = date(2027, 3, 1)                 # 供应商关停日
today = date(2026, 11, 21)
window_days = (retire - today).days

PHASES = [                                # (阶段, 占窗口%, 最坏时长天)
    ("盘点+引用清单", 10, 5),
    ("候选评测(2-3模型x3场景)", 30, 25),
    ("灰度切换 5->100%", 30, 30),
    ("全量观察缓冲", 30, 20),
]
used = sum(d for _, _, d in PHASES)
print(f"窗口 {window_days} 天，最坏路径 {used} 天 -> "
      f"{'OK，缓冲 ' + str(window_days-used) + ' 天' if used < window_days*0.7 else '窗口不足，先申请延期或裁场景'}")
cursor = today
for name, pct, days in PHASES:
    end = cursor + timedelta(days=days)
    print(f"  {name}: {cursor} -> {end}")
    cursor = end
print(f"  硬死线: {retire} (410 全量失败)\n")

# 场景替换矩阵：不同场景可选不同目标
MATRIX = {
    "客服对话":   {"候选": ["model-n", "model-f"], "卡点": "质量>=0.90, 输出P95<1.2k tok"},
    "文档解析":   {"候选": ["model-f"],            "卡点": "格式解析成功率>=99%"},
    "内部分析":   {"候选": ["model-mini"],         "卡点": "成本<=原 60%, 质量>=0.85"},
}
for scene, m in MATRIX.items():
    print(f"  {scene}: 候选 {m['候选']} | 卡点 {m['卡点']}")

# 引用盘点：版本字符串散落点
REF_PATTERNS = ["settings/model.py", "prompt_registry.yaml",
                "batch_jobs/*.json", "notebooks/**"]
print(f"\n盘点模式: {REF_PATTERNS}（漏掉 notebook 与批处理配置是经典翻车点）")
```

**追问 1**：为什么"一次迁移只改一个变量"在这里特别重要？
提示：换模型 + 换供应商同时做时，质量回退无法归因（模型差异 vs 接口差异 vs 计费差异）；出事故时的回滚路径也相互纠缠，必须拆成两个窗口。

**追问 2**：退役前的用量衰减曲线怎么用来控制灰度节奏？
提示：监控旧模型日调用量从 100% 降到 0 的斜率，卡在 >5% 不动说明有长尾调用点没迁移（定时任务/脚本/notebook）——按调用来源标签追到具体系统。

**追问 3**：迁移完成后旧版本的请求样本要保留吗？
提示：保留一段时间（90 天）的请求/响应对，用于"新模型上线后疑似质量回退"的事后归因与评测集扩充；保留方案要过隐私合规（脱敏）。

## 背诵要点
1. 倒排日历铁律：最坏路径时长 < 窗口 70%，评测+灰度是关键路径；退役日是刚性 410 死线，日历驱动不是里程碑驱动。
2. 分场景替换矩阵：各场景独立选候选与卡点（质量/格式/成本），灰度按场景独立开关回滚——不全量升到同一个模型。
3. 一次迁移只改一个变量：换模型与换供应商禁止同窗口叠加；旧版本引用盘点必须覆盖 prompt 注册表、批处理配置与 notebook。
