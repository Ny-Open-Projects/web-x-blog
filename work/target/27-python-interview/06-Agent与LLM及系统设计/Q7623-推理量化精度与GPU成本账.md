### Q7623 · 推理量化（FP8/INT8/INT4）与 GPU 成本的取舍账

难度：P6 ｜ 标签：成本工程 / 量化 / 自托管推理

**问**：自托管 32B 开源模型（fp16 需 2×A100-80G），团队想量化到 FP8/INT4 省 GPU。量化的账怎么算？质量损失怎么验收？"省一半显存"到"省一半成本"之间隔着什么？

**答**：
- **结论**：显存账：权重显存 ≈ 参数量 × 每参数字节数：fp16 32B ≈ 64GB，FP8 ≈ 32GB，INT4 ≈ 16-18GB（含分组 scale 元数据）——加上 KV cache 与激活，fp16 双卡可变单卡（FP8）甚至单卡还有富余（INT4）。吞吐账：FP8 在支持张量核心的卡上（H 系列/新 A 系列 via transformer engine）算力翻倍区，吞吐提升 1.5~2x；INT4 权重省的是显存与带宽（访存瓶颈场景吞吐近翻倍），但 compute 路径收益小于 FP8。**"省一半显存"≠"省一半成本"的三个间隔**：① 质量验收成本——量化后必须跑评测集（任务指标、长上下文、代码/数学子项），FP8 通常近无损、INT8 接近无损、INT4 视模型与任务可能掉 2~5 个点，掉点超阈值就要回退或换更高精度；② 改造与运维成本——量化工具链（GPTQ/AWQ/FP8 后训练量化）、kernel 支持矩阵（旧卡不支持 FP8）、推理框架版本升级；③ 缓存与上下文成本——KV cache 精度（fp16 vs fp8 cache）独立于权重精度，长上下文场景 cache 量化收益可能比权重更大，但精度风险也集中在长文本上。成本结论：FP8 是"当前性价比拐点"（近无损 + 显存/吞吐双收益）；INT4 用于显存受限或吞吐优先的场景，必须带质量验收；"降本"要按 **单位请求成本 = (卡时 × 卡价)/吞吐** 重算，而不是按显存直觉。
- **取舍**：量化时机：优先用官方/社区已验证的量化版本（社区 AWQ/GPTQ 权重），自量化只在"没有现成版本 + 评测基础设施齐全"时做；多租户混部场景，把"fp16 高保真通道 + FP8 经济通道"做成路由矩阵（Q7516 降级矩阵同源），质量敏感请求走高保真。验收集构成：通用能力集 + 业务核心任务集 + 长上下文集 + 已知 badcase 回归集，掉点阈值按任务定（RAG 检索增强类对量化通常更鲁棒，纯生成/数学更敏感）。
- **实战**：落地：① 先 FP8 后考虑更低精度，每档量化独立评测报告归档；② 生产灰度：5% 流量对拍（量化 vs fp16 同请求双跑 diff，Q7548 双跑对拍同源），人工抽检差异样本；③ 监控单位请求成本与质量指标联动，任何一侧恶化触发复评；④ 显存释放的收益落袋：同卡并行更多实例/更大 batch，而不是闲置。

```python
# 量化成本账: 显存/吞吐 -> 单位请求成本, 质量验收门槛
# 基线: Python 3.9+ 标准库; 数值为量级演示, 落地以实测为准
from dataclasses import dataclass


@dataclass
class QuantProfile:
    name: str
    bytes_per_param: float
    quality_score: float      # 评测集得分(0-100)
    tokens_per_s: float       # 单卡吞吐
    gpu_hourly: float


def weight_gb(params_b: float, p: QuantProfile) -> float:
    return params_b * p.bytes_per_param


def cost_per_mtok(p: QuantProfile) -> float:
    return p.gpu_hourly / (p.tokens_per_s * 3600) * 1e6


def accept(p: QuantProfile, baseline: float, threshold: float) -> bool:
    return baseline - p.quality_score <= threshold


def main() -> None:
    fp16 = QuantProfile("fp16", 2.0, 82.0, 1200, 25.0)
    fp8 = QuantProfile("fp8", 1.0, 81.6, 2100, 25.0)
    int4 = QuantProfile("int4", 0.55, 79.0, 1900, 25.0)

    assert abs(weight_gb(32, fp16) - 64) < 1e-6
    assert abs(weight_gb(32, fp8) - 32) < 1e-6     # 单卡可行
    c16, c8 = cost_per_mtok(fp16), cost_per_mtok(fp8)
    assert c8 < c16 * 0.7                          # 吞吐收益 -> 单位成本降
    print(f"fp16 {c16:.2f} -> fp8 {c8:.2f} 元/Mtok；INT4 显存 {weight_gb(32,int4):.0f}GB")

    # 质量验收: fp8 近无损放行; int4 掉 3 分超 RAG 阈值2 -> 拒绝或限场景
    assert accept(fp8, fp16.quality_score, 0.5)
    assert not accept(int4, fp16.quality_score, 2.0)
    assert accept(int4, fp16.quality_score, 3.5)   # 吞吐优先场景可放宽
    print("OK: 降本=单位请求成本重算; 每档量化带验收阈值, 掉点超限回退或限路由")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么长上下文场景 KV cache 量化的收益可能比权重量化更大？
→ 一句话提示：权重显存固定，KV cache 随上下文线性增长（长上下文下占大头）；fp8 cache 直接把这部分减半并提升并发容量——但它也是精度风险集中的地方，长文本质量验收独立做。

**追问 2**：多租户场景"高保真通道 + 经济通道"怎么路由？
→ 一句话提示：按请求的质量敏感度标签（业务线/任务类型）路由，质量敏感走 fp16、批量任务走 FP8；路由规则进网关，两条通道的同请求对拍 diff 作为常态化质量监控。

## 背诵要点
- 显存账：权重 ≈ 参数量×字节数，32B 模型 fp16 64GB / FP8 32GB / INT4 ~18GB；FP8 兼得显存与吞吐（1.5~2x），是性价比拐点。
- "省一半显存≠省一半成本"：隔着质量验收（掉点阈值按任务定）、工具链/内核改造、KV cache 独立变量三件事；降本按 单位请求成本 = 卡时×卡价/吞吐 重算。
- 灰度验收：5% 流量 fp16/FP8 双跑对拍 + badcase 回归集；INT4 掉点超限则限路由到吞吐优先场景，不全局铺开。

## 复盘追问
- 为什么优先用社区已验证量化版本而不是自己量化？提示：社区版本经过大规模用户实测（已知坑已踩），自量化的隐性成本在评测基础设施与工具链调试——除非有现成评测集且无现成版本，否则重复造轮子。
- 量化后"单位请求成本降了但用户投诉变多"怎么归因？提示：质量掉点分布在长尾任务上，评测集可能没覆盖；用双跑 diff 日志定位差异集中的任务类型，把该类型路由回高保真通道——量化事故的典型形态是长尾退化而非整体崩。
