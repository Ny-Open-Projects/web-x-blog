### Q7794 · 系统提示长成了 if-else 森林：模板条件分支的组合爆炸与治理

难度：P6 ｜ 标签：提示工程、模板治理、条件分支、组合爆炸、测试矩阵、版本管理

基线：Python 3.12；模拟嵌套 if-else 模板渲染与"分支外提"重构，量化条件组合的测试矩阵爆炸与外提后的裁剪收益，全标准库实跑。

**问**：一个客服 Agent 的系统提示模板，最初只有 300 行。半年下来加了：VIP 用户特殊话术、灰度开关话术、渠道差异化（App/小程序/网页）、季节性活动说明、A/B 实验变体——模板里挤满了 Jinja 风格的 `{% if %}`，渲染产物最长冲到 6000 token，而且没人说得清"到底有多少种渲染组合"。模板条件分支为什么会失控？怎么治理？测试矩阵怎么建？

**答**：

- **结论**：失控的机理是**条件的笛卡尔积 + 单模板的引力**：k 个独立开关就是 2^k 种渲染产物，5 个开关 32 种、8 个开关 256 种——每种都是线上真实存在的提示，却没有任何人见过全部；同时"加个条件"的成本看起来永远比"拆模板"低，所有需求都往同一个模板里塞，模板从配置退化成代码（而且是无类型、无测试、不可静态分析的代码），长模板还附带 token 成本与指令稀释（Q7756 系统提示膨胀的同族病）。治理的抓手是**分支外提**：把"可选话术块"从模板体内移到模板体外——每个条件块变成独立片段文件（片段 = 带元数据的纯文本），渲染层变成"基座模板 + 按 context 选择片段拼接"，模板里不再有 if；条件逻辑回到代码层，可单测、可 lint、可统计。收益三重：① 组合数显式化（哪些片段互斥、哪些可叠加在代码里声明）；② 渲染产物可控（没用到的片段永不进上下文，token 与指令密度同时改善）；③ 测试矩阵可裁剪（从全组合 2^k 降到"基座 + 每片段单测 + 声明过的互斥组合抽测"）。
- **取舍**：分支外提不是免费午餐：① **片段衔接的连贯性**——独立片段拼出来的提示可能有语气断裂、重复、冲突（两个片段都写"语气要亲切"），治理靠片段元数据（前置声明/语气标签）+ 拼接顺序约定 + 组合冒烟集（高频组合人工过一遍），不可能全自动；② **外提粒度**：太细（每句话一个片段）拼装逻辑复杂度反噬，太粗（只拆季节活动这种大块）治标不治本——经验粒度是"一个完整的功能话术块（3~10 句）"为一段；③ **单模板的残余价值**：强关联的条件（VIP 与渠道的组合话术强耦合）拆开反而丢上下文，允许保留少量"必须共现"的条件在同一片段内——外提是治理原则不是教条；④ **成本对比**：不外提的隐性成本（测试盲区、token 浪费、指令稀释导致遵从度下降）平时不可见，出事时（某组合下模型行为诡异）排查极慢——外提的本质是把隐性成本换成显性工程成本，对高频迭代的 Agent 几乎总是划算。
- **实战**：① 模板登记表：每个片段登记元数据（触发条件、互斥组、语气标签、owner、最后验证日期），没有登记的片段不许上线；② 渲染产物快照：高频组合（覆盖 80% 流量的十几种）做渲染快照进回归集（Q7277 golden 纪律），模板或片段变更必须过快照对比；③ 组合审计脚本：定期跑"实际流量命中了哪些组合 vs 登记了哪些组合"，发现未登记组合（模板 if 残留）或死片段（登记了但零流量）即清理项；④ 上下线纪律：新增条件先问"能不能做成独立片段+显式声明"，模板体内禁止新增 if——冻结存量、管制增量，避免边治理边膨胀。

```python
"""Q7794 模板条件分支治理: 组合爆炸量化 + 分支外提裁剪收益。"""
from itertools import product

# 旧写法: 一个模板里 6 个独立 if 开关
SWITCHES = ["vip", "gray", "channel_app", "season", "ab_test", " pii_strict"]


def render_monolith(ctx: dict, base_tokens: int = 1200, block_tokens: int = 260) -> int:
    """嵌套 if 模板: 命中的分支都留在模板体里 -> 渲染产物 token 数."""
    on = sum(1 for k in SWITCHES if ctx.get(k.strip()))
    return base_tokens + on * block_tokens


def render_composed(ctx: dict, base_tokens: int = 1200, block_tokens: int = 260) -> int:
    """分支外提: 基座模板 + 按 ctx 选择片段, 未选中片段零成本."""
    return base_tokens + sum(1 for k in SWITCHES if ctx.get(k.strip())) * block_tokens


def combos(n_switches: int) -> int:
    return 2 ** n_switches


def prune_matrix(n_switches: int, pairwise: int = 6) -> int:
    """外提后的测试矩阵: 基座 + 每片段单测 + 高风险互斥组合抽测."""
    return 1 + n_switches + pairwise


if __name__ == "__main__":
    k = len(SWITCHES)
    ctx_a = {"vip": True, "channel_app": True, "season": True}
    ctx_b = {"gray": True, "ab_test": True}
    print(f"开关数 {k} -> 全组合 {combos(k)} 种渲染产物, 无人见全")
    print(f"组合A(3开) 旧渲染 {render_monolith(ctx_a)} tok / 外提 {render_composed(ctx_a)} tok")
    print(f"组合B(2开) 旧渲染 {render_monolith(ctx_b)} tok / 外提 {render_composed(ctx_b)} tok")
    empty = {s.strip(): False for s in SWITCHES}
    print(f"全关流量  旧渲染 {render_monolith(empty)} tok / 外提 {render_composed(empty)} tok")
    full = {s.strip(): True for s in SWITCHES}
    print(f"全开极端  旧渲染 {render_monolith(full)} tok / 外提 {render_composed(full)} tok")
    t_full, t_pruned = combos(k), prune_matrix(k)
    print(f"测试矩阵: 全组合 {t_full} -> 外提裁剪后 {t_pruned} "
          f"(压缩 {1 - t_pruned / t_full:.0%})")
    ok = combos(k) == 64 and t_pruned == 13 and render_composed(ctx_a) == render_monolith(ctx_a)
    print(f"校验: 组合数 2^6=64 显式化 + 外提不改变命中产物 -> {'通过' if ok else '异常'}")
    print("结论：k 个开关=2^k 种真实存在的提示; 分支外提到片段+代码层选择,")
    print("      组合显式化/未选片段零 token/测试矩阵从全组合裁到基座+单测+抽测")
```

**追问一**：片段外提后，多个片段拼接的"连贯性"问题（语气断裂、规则重复、相互冲突）怎么治理？

→ 解析：连贯性是外提的核心残余风险，治理分三层：① **声明层**——片段元数据带语气标签与前置条件，拼接器按声明排序（全局规则在前、场景话术在后），互斥组声明让冲突片段在结构上不可能共存（vip 话术与 gray 话术若语义冲突，登记互斥后拼接器直接拒绝渲染该组合，冲突从"线上才发现"提前到"渲染时抛错"）；② **验证层**——高频组合冒烟集人工过（拼接产物的语气/重复/冲突只有人能可靠判断，自动检测只能做启发式：两个片段都含"语气亲切"类短语的重复度报警），加上 LLM 审片段冲突的辅助线（把组合产物喂给强模型问"这些规则有没有相互矛盾"，Q7779 judge 的用法，只做辅助不做门禁）；③ **运行层**——遵从度监控按组合分桶（Q7788 上下文结构化分段与遵从度同族）：某组合的指令遵从度异常低，优先怀疑拼接产物的连贯性问题而非模型能力。还有一个实用纪律：**片段写作规范**——每个片段自带完整上下文（不依赖"承上文"的指代）、单一职责（一个片段只讲一件事）、规则不跨片段重复（全局规则进基座，片段只讲增量）——写作规范是成本最低的连贯性防线，比事后检测便宜得多。总原则：**外提把"一个长模板"换成"一个拼接系统"，连贯性问题从模板内部转移到拼接器与片段规范，治理重心相应从"读模板"变成"管声明与验证组合"。**

**追问二**：模板/片段变更的回归测试，最小集合怎么设计？全量回归太贵、单片段单测漏组合问题，怎么平衡？

→ 解析：分层回归的设计依据是**变更的影响半径**：① **基座模板变更**（影响所有产物）：全量高频组合快照回归——基座是最大公因子，改动传导到每一条渲染产物，这里不能省；② **单片段变更**（影响面 = 含该片段的组合）：该片段单测 + 涉及它的互斥/叠加组合抽测（登记表能直接算出受影响组合清单，按流量加权抽前 N 个）——影响半径可计算是外提相对单模板的最大测试红利（单模板改动影响面永远是全部 2^k，算不出"哪些受影响"）；③ **拼接器/选择逻辑变更**（影响面 = 组合选择正确性）：用"组合选择断言"测试——给定 ctx，断言选中的片段集合与登记表期望一致（纯逻辑测试，零 LLM 调用，可以全量跑）；④ **成本分配的经验比例**：LLM 调用的回归只花在 ①②（产物级验证），③④ 用纯逻辑断言覆盖——大多数回归需求其实落在逻辑层，LLM 回归集可以控制在几十个高频组合，跑批成本可控（Q7631 评测错峰同族）。再加一条工程闸门：**变更必须声明影响类型**（基座/片段/拼接器），CI 按声明选择回归层级——未声明或声明与实际 diff 不符的变更拒收，防止"顺手改了基座却只跑了片段单测"的漏测。总原则：**回归成本的可控性来自影响半径的可计算性，而这正是分支外提买来的结构性质——单模板时代这个问题无解，只能靠全量昂贵回归。**

## 背诵要点
- 失控机理：k 个独立开关 = 2^k 种真实线上提示（6 开关 64 种、8 开关 256 种），组合数无人见全；"加个条件"永远比"拆模板"便宜 → 模板退化成无类型、无测试、不可静态分析的代码，附带 token 膨胀与指令稀释。
- 治理抓手是分支外提：一个片段 = 3~10 句的完整功能话术块，带元数据（触发条件/互斥组/语气标签/owner/验证日期），拼接器按声明选择；模板体内冻结存量、禁止新增 if。
- 测试矩阵从全组合裁到"基座 + 每片段单测 + 声明过的互斥组合抽测"（6 开关 64 → 13）；回归按影响半径分层，变更先声明类型（基座/片段/拼接器）再决定回归层级。

## 复盘追问
- 怎么量化"模板已经失控"而不是凭感觉？（k 个独立开关 = 2^k 种真实线上提示、无人见过全部；渲染产物 token 上限被反复击穿；新增条件绕过了登记表——三条任一成立即失控）
- 分支外提后测试矩阵凭什么能从 2^k 降到线性？（影响半径可计算：基座变更影响全部、单片段变更只影响含它的组合、拼接器变更用纯逻辑断言——单模板时代这个信息根本不存在）
