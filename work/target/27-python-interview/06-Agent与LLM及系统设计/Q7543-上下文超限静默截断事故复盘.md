### Q7543 · 事故复盘：长会话用户突然全被拒答，根因是上下文静默截断

> 长会话场景下 400 错误消失但回答质量崩塌，截断发生在哪里？

> 难度:★★★★ | 标签:事故复盘, 上下文管理, Token 预算

**问**：某天起长会话用户的回答质量断崖下降，但没有报错——排查发现中间件为绕开"context length exceeded"的 400 错误，加了"超限自动截断历史"的逻辑，结果截掉的是 system prompt 尾部与最近几轮对话。静默截断为什么是反模式？正确的上下文预算管理怎么做？

**答**：结论：截断事故的本质是**用"把错误藏起来"替代"把预算管起来"**——400 超限应该触发的是显式的上下文预算策略（有优先级的裁剪顺序），而"自动截断"裁掉了无优先级的任意部分：system prompt 尾部（角色约束丢失）、工具 schema（工具调用全废）、最近对话（任务状态丢失），且全程无日志无告警。正确姿势：**显式 token 预算表（分段配额）+ 有序裁剪（先旧轮次摘要化，永不裁 system/工具 schema）+ 截断必留痕**。

机理与实战：
- **静默截断为什么最危险**：它不报错、有回答、质量下降是统计性的（部分用户部分场景），监控的"成功率"完全正常；等 badcase 从客服渠道反馈回来已过去几天。凡"错误被吞掉换成降级行为"的路径都必须留痕：截断发生时打 metric（截断次数、裁掉了哪段、裁了多少 token）并抽样告警。
- **预算表设计**：总窗口 W 分配：system+工具 schema 20-25%（永不裁）、检索材料 40%（按相关性裁）、对话历史 25%（滚动摘要）、输出预留 10-15%（max_tokens 硬预留）。每段独立计量，超限先裁优先级最低段，裁剪顺序写死在代码里而不是让中间件自由发挥。
- **400 的正确处置**：收到 context length exceeded 时按预算表重裁再试一次是合理自愈，但必须：① 保留原始请求指纹与重裁日志；② 重试次数封顶 1 次（反复裁剪说明预算设计失效）；③ 把"超限频率"作为容量指标监控——超限率上升说明该会话类型需要更大的窗口或更激进的摘要策略。
- **治理闭环**：截断事件进 badcase 采样池，人工标注"截断是否影响答案"，回填裁剪优先级——预算表是数据驱动的演进对象，不是一次性设计。

```python
# 基线:Python 3.10+;纯标准库,上下文分段预算与有序裁剪(截断必留痕)
from __future__ import annotations
from dataclasses import dataclass, field
from collections import deque


@dataclass
class Segment:
    name: str
    priority: int        # 越小越不可裁
    tokens: int


@dataclass
class ContextBudget:
    window: int = 8000
    max_output: int = 1000
    segments: list[Segment] = field(default_factory=list)
    history: deque[str] = field(default_factory=deque)
    trim_events: list[str] = field(default_factory=list)  # 留痕

    def used(self) -> int:
        return sum(s.tokens for s in self.segments) + \
            len(self.history) * 200   # 每轮对话估 200 token

    def total_used(self) -> int:
        return self.used() + self.max_output


def fit(ctx: ContextBudget) -> tuple[bool, list[str]]:
    """有序裁剪:按 priority 从高到低裁,system(1)/schema(2) 永不裁。"""
    actions: list[str] = []
    while ctx.total_used() > ctx.window:
        candidates = sorted((s for s in ctx.segments if s.priority > 2),
                            key=lambda s: -s.priority)
        history_tokens = len(ctx.history) * 200
        # 历史也是可裁资源:优先摘要化旧轮
        if history_tokens and (not candidates or history_tokens * 2 <= candidates[0].tokens):
            dropped = ctx.history.popleft()
            ctx.segments.append(Segment("history-summary", priority=5, tokens=100))
            actions.append(f"摘要化旧轮: {dropped[:12]}...")
            continue
        if not candidates:
            ctx.trim_events.append("预算失效:无可裁资源仍超限")
            return False, actions
        victim = candidates[0]
        cut = min(victim.tokens, ctx.total_used() - ctx.window)
        victim.tokens -= cut
        actions.append(f"裁剪 {victim.name} {cut} tok")
        if victim.tokens <= 0:
            ctx.segments.remove(victim)
    return True, actions


def demo() -> None:
    ctx = ContextBudget(window=4000, max_output=500)
    ctx.segments = [
        Segment("system-prompt", priority=1, tokens=600),   # 永不裁
        Segment("tool-schema", priority=2, tokens=800),     # 永不裁
        Segment("retrieval", priority=3, tokens=2000),
    ]
    ctx.history.extend([f"turn-{i}" for i in range(12)])     # 12 轮 x200 = 2400 tok
    print(f"初始占用: {ctx.total_used()} / 4000")
    ok, actions = fit(ctx)
    print("裁剪动作:", actions)
    assert ok
    assert ctx.total_used() <= 4000
    # system/schema 未被裁
    names = {s.name for s in ctx.segments}
    assert "system-prompt" in names and "tool-schema" in names
    assert ctx.segments[0].tokens == 600
    # 静默截断的反例:直接砍头部历史与 system 尾部(事故现场)
    assert len(ctx.trim_events) == 0
    print(f"留痕检查: {ctx.trim_events} (预算失效才会标记)")
    print("上下文预算:分段配额+有序裁剪+永不裁 system/schema+全程留痕 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：滚动摘要和历史截断的取舍怎么定？
答：截断（丢）省 token 但丢任务状态，摘要（压）保信息但花额外调用与延迟。经验分界：最近 2-3 轮原文保留（任务状态活跃区）、更早轮次摘要化；摘要触发要有频率上限（每 N 轮一次），并验证摘要不丢关键约束（编号/金额/期限）。若摘要质量不可控，宁可保留更多原文轮次——错误摘要比长上下文更伤。

**追问二**：为什么"超限率"要当容量指标监控而不是只在出错时看日志？
答：超限率上升是"用户会话变长/检索材料变大/窗口不够"的先行指标，等错误出现再处理已经伤及用户体验；且截断自愈掩盖了错误，超限率是唯一能暴露预算设计恶化的信号。按会话类型（有无检索、有无长文档）分维度看超限率，才能定位是哪类场景需要调整预算表。

## 背诵要点
- 静默截断 = 用藏错误替代管预算：裁掉 system 尾部/工具 schema/最近轮次导致质量统计性下降且无告警；降级行为必须留痕（截断 metric+抽样告警）。
- 预算表分段配额：system+schema 20-25% 永不裁、检索 40%、历史 25%（最近 2-3 轮原文+旧轮摘要化）、输出 10-15% 硬预留；裁剪顺序代码化。
- 400 超限自愈限 1 次重裁重试；超限率按会话类型监控是预算设计恶化的先行指标。

## 复盘追问
- 为什么中间件作者认为"自动截断"是合理方案？怎么在评审阶段拦住它？（提示：它能让 400 消失、测试全绿——"消除报错"与"消除问题"的混淆；评审要问"降级路径的留痕与告警在哪"，无答案即打回）
- 截断事故后要求"所有截断都告警"，为什么告警量又成了新问题？（提示：截断是常态行为（高频低害），全量告警会淹没值班；分级——预算失效（不可裁仍超限）高危告警，system 被裁高危，普通历史摘要只记 metric+按比例抽样人工复核）
