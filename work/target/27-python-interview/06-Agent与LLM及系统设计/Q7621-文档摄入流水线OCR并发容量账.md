### Q7621 · 文档摄入流水线的 OCR 并发容量账

难度：P6 ｜ 标签：容量规划 / RAG 摄入 / OCR

**问**：RAG 知识库要消化历史档案：50 万页扫描件，OCR 单页 GPU 推理 1.2s（含前后处理 CPU 0.8s），要求 3 天内全部入库。GPU 卡数、CPU worker 数、队列与限流怎么配？摄入完成后这些资源怎么处置？

**答**：
- **结论**：主瓶颈账：GPU 吞吐 = 卡数 / 1.2s；3 天 = 259200s，需要吞吐 = 500000/259200 ≈ 1.93 页/s → 至少 ceil(1.93×1.2)=3 张卡，按利用率 0.8 与余量配 **4~5 张**。但流水线是链式的：OCR(GPU) → 版式解析/清洗(CPU) → 分块/Embedding(GPU 或 API) → 入库，**整线吞吐 = 最慢一段**。CPU 段账：每页 CPU 0.8s，1.93 页/s 需要 1.55 个核 → 配 4 核（余量）；Embedding 段若走 API 按 TPM 配额倒算并发（Q7582 同源），若自建 GPU 与 OCR 共享——共享时两段互相挤压，通常分开卡或分时。队列与限流：OCR 队列深度按"积压页数/吞吐"控制告警水位；上游对象存储拉取限流（带宽）；入库端数据库写入吞吐别成为暗瓶颈（Q6519 批量写）。资源处置：摄入是**一次性峰值负载**——按量/Spot GPU 用完即释（Q7098 抢占式实例同源：OCR 可断点续跑，Spot 中断代价低，是典型 Spot 场景），比包月省 60~80%；常驻留 1 张卡做增量摄入即可。
- **取舍**：自建 GPU vs OCR API：50 万页 × API 单价（约 0.01~0.03 元/页）= 0.5~1.5 万元，一次性；自建 4 卡 × 3 天按量 ≈ 数千元但加工程复杂度。小规模（<10 万页）API 总成本常更低且免运维；大规模或敏感数据（不出域）自建。质量取舍：扫描件质量差的部分 OCR 置信度低，走"低置信度人工复核"通道而不是重试 GPU（重试不改善质量）——复核队列预算单列。
- **实战**：落地：① 先跑 1000 页样本实测吞吐链（各段耗时分布），找出真实最慢段再定卡数——纸面账常常低估 CPU 段（PDF 解析比 OCR 还慢是常见反转）；② 断点续跑：页级幂等（已完成页跳过），Spot 中断无代价；③ 监控按段打点（队列深度、各段 P95、GPU 利用率），瓶颈迁移可见；④ 摄入完成后 GPU 按量实例释放、Spot 池销毁，留增量通道常驻；⑤ 人工复核抽样率按质量目标定（如置信度 <0.9 复核，抽检整体准确率）。

```python
# 摄入流水线容量账：链式吞吐 = min(各段)，GPU 卡数与资源处置
# 基线：Python 3.9+ 标准库；真实耗时用 1000 页样本实测校准
from dataclasses import dataclass


@dataclass
class Pipeline:
    pages: int
    deadline_s: float
    gpu_page_s: float          # OCR 单页 GPU 秒
    cpu_page_s: float          # 前后处理单页 CPU 秒
    gpu_util: float = 0.8      # 调度利用率


def required_gpu(p: Pipeline) -> int:
    rps = p.pages / p.deadline_s
    return int(-(-(rps * p.gpu_page_s / p.gpu_util) // 1))  # ceil


def required_cpu_cores(p: Pipeline) -> int:
    return int(-(-p.pages / p.deadline_s * p.cpu_page_s // 1))


def line_throughput(p: Pipeline, gpus: int, cores: int) -> float:
    return min(gpus * p.gpu_util / p.gpu_page_s, cores / p.cpu_page_s)


def finish_days(p: Pipeline, gpus: int, cores: int) -> float:
    return p.pages / line_throughput(p, gpus, cores) / 86400


def main() -> None:
    p = Pipeline(pages=500_000, deadline_s=3 * 86400,
                 gpu_page_s=1.2, cpu_page_s=0.8)
    need = required_gpu(p)
    assert need in (3, 4)                      # 1.93rps*1.2/0.8 ≈ 2.9 -> 3
    cores = required_cpu_cores(p)
    assert cores == 2 or cores == 3            # 1.55 -> 2
    g, c = max(need, 4), max(cores, 4)         # 余量配置
    assert finish_days(p, g, c) < 3
    print(f"配置 {g} 卡 + {c} 核，预计 {finish_days(p, g, c):.1f} 天完成（整线=min(各段)）")

    # 常见反转：PDF 解析比 OCR 慢 -> CPU 段成瓶颈，加卡无效
    p2 = Pipeline(pages=p.pages, deadline_s=p.deadline_s,
                  gpu_page_s=1.2, cpu_page_s=3.0)
    assert line_throughput(p2, 8, 4) == 4 / 3.0   # 加到 8 卡也不提速
    print("反转检测: cpu_page_s=3 时 8 卡吞吐仍被 4 核钉死 -> 先实测再加卡")

    # 一次性峰值负载: Spot + 页级幂等 -> 用完即释
    print("OK: Spot GPU 按量用完即释(页级幂等断点续跑); 低置信度走人工复核而非重试")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"纸面账定卡数"经常失败？
→ 一句话提示：纸面账只算 GPU 段，真实流水线的最慢段常在解析/清洗/网络拉取；必须用 1000 页样本实测各段耗时分布，按"整线 = 最慢段"配置，否则加卡无效。

**追问 2**：为什么 OCR 低置信度页走人工复核而不是 GPU 重试？
→ 一句话提示：置信度低源于扫描质量而非推理波动，重试同样的输入只会得到同样差的结果；复核是质量杠杆，重试是浪费——重试只该给"基础设施失败"。

## 背诵要点
- 链式吞吐 = min(GPU 段, CPU 段, Embedding 段, 入库段)；GPU 卡数 = 需求 rps × 单页秒 / 利用率(0.8)，示例 50 万页 3 天约 4~5 卡，CPU 段按 0.8s/页另算。
- 一次性峰值负载用 Spot/按量 GPU + 页级幂等断点续跑，用完即释省 60~80%；留 1 张卡做增量常驻。
- 先 1000 页样本实测再定配置（解析常比 OCR 还慢的反转）；低置信度走人工复核通道，重试不改善质量。

## 复盘追问
- 摄入完成后资源处置不当会留下什么浪费？提示：包月 GPU 空转是最常见尾款——摄入类负载必须在立项时就写"用后即释"预案，监控 GPU 利用率掉到个位数即触发降配/释放评审。
- 50 万页里"低置信度比例"本身是个容量变量怎么处理？提示：样本实测时统计置信度分布，复核比例高时人工通道成为新瓶颈——要么提高图像预处理质量（去斜/二值化）要么接受质量分级的入库策略。
