### Q7546 · 成本工程：同一模型的 API 价格差 2-5 倍，分级路由怎么省一半账单？

> 难度:★★★ | 标签:成本工程, 分级服务, 路由策略

**问**：主流供应商对同一模型提供多档服务（如 standard/优先级、flex/低优先、batch/离线批量），价差 50%-90%。哪些流量能降档？降档的隐性代价是什么？分级路由的决策逻辑和兜底设计怎么做？

**答**：结论：降档的本质是**用延迟与可中断性换折扣**——能容忍分钟级延迟的流量（离线报告、批量标注、非实时摘要）走 batch（5 折）；可中断的交互辅助流（后台增强、推荐）走 flex；实时对话与计费关键路径保持 standard。省一半账单的关键不是"尽量降档"，而是**流量画像准确**：给每个业务场景标注"延迟 SLA + 可否重试/中断 + 业务价值"三属性，路由按属性匹配档位，并把降档后的质量回归纳入监控。

机理与实战：
- **档位画像**：batch（50% 折扣、24h 内返回、适合离线流水线）；flex（约 50% 折扣、高峰可排队/中断、适合非关键交互增强）；standard（全价、即时、SLA 稳定）。隐性代价：batch 有 24h 时效与输入限制、flex 高峰期延迟不可控且可能排队失败、两者失败重试的语义与 standard 不同（batch 任务失败要查任务状态而不是同步重试）。
- **路由决策器**：三属性打分——延迟敏感（用户在线等待？）、可中断（失败不伤业务？）、时效窗口（结果 24h 内还有价值？）。"离线且不急"→batch；"在线但非关键"→flex+超时回落 standard；"关键交互"→standard。回落路径必须存在：flex 排队超时自动升档 standard，宁可多花钱不丢 SLA。
- **成本验证闭环**：按场景打账单标签（每请求带 scenario tag），月度看"各档位占比 vs 画像预期"；发现 standard 占比超预期（比如某"离线报告"其实走的 standard）就是路由 bug 或画像过期。降档质量回归：batch 结果与 standard 对拍抽样（不同档位可能同模型不同算力池，输出分布有微小差异）。
- **折扣的脆弱性**：batch/flex 的折扣与限制随供应商版本调整，路由层要把档位参数化（配置中心），不要硬编码价格假设——折扣口径变了账单模型要能跟着改。

```python
# 基线:Python 3.10+;纯标准库,三档推理服务分级路由决策器与月账单对比
from __future__ import annotations
from dataclasses import dataclass
from enum import Enum


class Tier(Enum):
    BATCH = ("batch", 0.5, "24h 内返回")     # (档位, 价格系数, 承诺)
    FLEX = ("flex", 0.5, "高峰可排队/中断")
    STANDARD = ("standard", 1.0, "即时稳定")


@dataclass
class Workload:
    name: str
    online_wait: bool     # 用户在线等待?
    business_critical: bool  # 失败伤业务?
    results_have_deadline: bool  # 24h 内仍有时效?
    monthly_tokens: int


def route(w: Workload) -> tuple[Tier, str]:
    """三属性决策:关键交互 standard;在线非关键 flex;离线批量 batch。"""
    if w.online_wait and w.business_critical:
        return Tier.STANDARD, "用户在线等待且业务关键"
    if w.online_wait and not w.business_critical:
        return Tier.FLEX, "在线但可中断:flex,超时回落 standard"
    if not w.online_wait and w.results_have_deadline:
        return Tier.BATCH, "离线且有时效窗口"
    return Tier.BATCH, "纯离线"


def monthly_bill(w: Workload, price_per_mtok: float) -> float:
    tier, _ = route(w)
    return w.monthly_tokens / 1e6 * price_per_mtok * tier.value[1]


def demo() -> None:
    cases = [
        Workload("客服对话", True, True, False, 50_000_000),
        Workload("文档摘要(后台增强)", True, False, False, 120_000_000),
        Workload("日报生成", False, False, True, 200_000_000),
        Workload("批量数据标注", False, False, False, 300_000_000),
    ]
    total_std = total_routed = 0.0
    for w in cases:
        tier, why = route(w)
        b_routed = monthly_bill(w, 10.0)
        b_std = w.monthly_tokens / 1e6 * 10.0
        total_std += b_std
        total_routed += b_routed
        print(f"  {w.name}: {tier.value[0]} ({b_routed:,.0f} vs 标准 {b_std:,.0f} 元) — {why}")
    print(f"月账单: 路由后 {total_routed:,.0f} vs 全标准 {total_std:,.0f},省 {(1 - total_routed / total_std):.0%}")
    assert route(cases[0])[0] == Tier.STANDARD
    assert route(cases[1])[0] == Tier.FLEX
    assert route(cases[3])[0] == Tier.BATCH
    assert total_routed < total_std * 0.75
    print("分级路由:三属性画像匹配档位,关键路径保持 standard,折扣参数化 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：flex 高峰期排队失败时，"升档回落"怎么实现才不产生双计费？
答：回落 = 放弃 flex 请求（若已发出则带相同幂等键取消/确认未执行）→ 以 standard 重新提交；关键是状态机原子性：flex 状态与 standard 状态互斥，回落时 flex 必须先终态化。与 Q7536 的重试双计费同源——任何跨档位切换都是一次"重试"，幂等键与状态机是同一个问题的不同切片。

**追问二**：batch 的 24h 时效怎么防止"结果过期后才被使用"？
答：把时效变成数据契约：batch 任务提交时记录 deadline，结果消费侧校验 `now < deadline` 才使用，过期结果丢弃并降级为 standard 重算或跳过。事故场景通常是"日报生成依赖的 batch 结果次日才回来，没人发现日报用了过期数据"——所以时效校验要在消费点强制执行，且过期率要进 SLA 指标（过期率高说明提交时间规划错了）。

## 背诵要点
- 分级路由 = 流量画像（在线等待/业务关键/时效窗口三属性）匹配档位：关键交互 standard、在线非关键 flex、离线批量 batch（约 5 折）。
- 降档隐性代价：flex 高峰排队中断、batch 24h 时效与任务态失败语义、跨档位回落是"重试"需幂等键防双计费；回落路径必须存在。
- 成本闭环：每请求带 scenario tag 归因账单，standard 占比超预期=路由 bug；batch 结果消费点强制校验 deadline，过期率进 SLA。

## 复盘追问
- 月度账单里"批量标注"全走的 standard，复盘路由层哪里坏了？（提示：画像属性可能标错了（results_have_deadline 漏标）或路由规则更新后旧场景未回归；画像表要有 owner 与季度校准，scenario tag 的覆盖率也要监控——没打 tag 的请求路由决策不可审计）
- 供应商调整了 batch 限制（输入上限缩小一半），系统怎么第一时间感知？（提示：batch 任务提交失败率突增是信号；路由层的档位参数要配置化+契约测试（每周用小样本跑各档位探活），把供应商契约变更从"账单异常"提前到"探活告警"）
