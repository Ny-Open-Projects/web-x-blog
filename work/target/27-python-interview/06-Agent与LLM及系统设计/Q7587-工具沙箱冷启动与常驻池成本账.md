### Q7587 · 工具沙箱冷启动与常驻池的成本账

难度：P6/P7 ｜ 标签：沙箱 / 成本工程 / 容器

**问**：代码解释器类 Agent 每次执行都起一个隔离容器（基线 Python 3.12+，容器隔离），P95 执行延迟里 3 秒是冷启动，容器月费用也失控。冷启动与常驻池的成本账怎么算？架构怎么选？

**答**：
- **结论**：成本模型两条曲线：**冷启动模式**成本 = 执行次数 × 容器生命周期（启动 2-4s + 执行 + 销毁），延迟差但"用完即走"无闲置浪费；**常驻池模式**成本 = 池大小 × 单价 × 时长（含闲置），延迟好但利用率决定经济性——`池利用率 = 峰值并发 ÷ 池大小`，利用率 <30% 时常驻池的钱大半在养闲置。临界点：`执行频率 × 平均占用时长` 高（高 QPS 场景）选常驻池，低频长尾选按需冷启动或混级（池 + 溢出冷启动）。
- **取舍**：三种实现的取舍：① Docker 容器（启动秒级、隔离中等、生态熟）；② Firecracker/gVisor 微 VM（启动 ~125ms 级、隔离强、运维门槛高）；③ 进程内隔离（Windows Job Object/Pyodide/WASM，启动毫秒但隔离最弱）。冷启动优化优先级：镜像瘦身与预热（Python 环境预装、模型/库预下载）> 快照恢复（CRIU/微 VM snapshot 把启动压到百毫秒）> 池化。
- **实战**：落地：① 池大小按"峰值并发 × P95 占用时长"定，而不是均值——`池大小 = ceil(并发 × 时长/窗口) × 1.2`；② 池内会话亲和：Agent 多步执行复用同一沙箱（省重复启动），步间超时归还池；③ 按租户/工具分级：热租户独占池、长尾共享池；④ 观测三项：启动耗时分布、池利用率、执行排队深度，利用率连续低于 30% 缩池，排队深度高扩池。

```python
# 冷启动 vs 常驻池的成本与延迟对比（纯标准库）
# 基线：Python 3.9+


def cold_start_month_cost(execs: int, lifetime_s: float, price_per_s: float = 1e-5,
                          startup_s: float = 3.0) -> float:
    return execs * (lifetime_s + startup_s) * price_per_s


def pool_month_cost(pool_size: int, seconds: int = 30 * 86400,
                    price_per_s: float = 1e-5) -> float:
    return pool_size * seconds * price_per_s


def pool_size(peak_concurrency: int, p95_exec_s: float, window_s: int = 60,
              headroom: float = 1.2) -> int:
    return max(1, -(-int(peak_concurrency * p95_exec_s * headroom) // window_s))


def main() -> None:
    execs, life = 100_000, 2.0
    cold = cold_start_month_cost(execs, life)
    ps = pool_size(peak_concurrency=50, p95_exec_s=2.0)
    pool = pool_month_cost(ps)
    util = 50 * 2.0 / ps / 60
    print(f"池大小={ps} 月成本 冷启动=${cold:,.0f} vs 池=${pool:,.0f} 利用率={util:.0%}")
    # 低频场景冷启动更省
    assert cold_start_month_cost(2_000, life) < pool_month_cost(pool_size(5, 2.0))
    # 高频场景池更省（启动时间被摊掉且池利用率高）
    assert pool_month_cost(pool_size(500, 2.0)) < cold_start_month_cost(2_000_000, life)


if __name__ == "__main__":
    main()
```

**追问 1**：为什么池利用率低时"常驻池"是负资产？
→ 一句话提示：常驻按时间计费，闲置时段全额付费；利用率 <30% 时同等延迟用"冷启动+镜像预热/快照"通常更省，要定期用数据复核选型。

**追问 2**：快照恢复（microVM snapshot）省了什么、漏了什么？
→ 一句话提示：省掉内核引导与 Python 解释器/依赖初始化（恢复内存页到毫秒级），漏掉的是网络连接、缓存文件句柄等外部状态，恢复后要重建；且快照镜像要与宿主内核版本匹配。

## 背诵要点
- 选型判据：执行频率 × 占用时长——低频用冷启动（+镜像预热/快照），高频用常驻池（利用率 >50% 才划算）。
- 池大小 = 峰值并发 × P95 时长 × 1.2 按窗口折算；Agent 多步复用同一沙箱（会话亲和）。
- 冷启动优化优先级：镜像预热 > 微 VM 快照（~125ms）> 池化；进程内隔离最快但隔离最弱。

## 复盘追问
- 为什么成本失控常出现在"每租户独立池"的方案？提示：租户数 × 池大小线性叠加，长尾租户利用率极低，要改为共享池 + 租户配额。
- 如何区分"启动慢"与"执行慢"的责任边界？提示：延迟分布里把启动段与执行段分段计时打点，P95 分解后才不至于盲目扩池。
