### Q7596 · 多模态输入的预处理与成本

> 难度:★★☆ | 标签:多模态, 视觉, 成本

**问**：用户传 20MB 的截图让模型分析——为什么「原图直接塞给 API」又贵又可能失败？图片 token 是怎么算的（分辨率决定），预处理流水线（压缩/裁剪/降采样）该在哪做，多图/视频帧的成本爆炸怎么控，「OCR 先行」和「直接视觉理解」怎么选？

**答**：① 成本机制：视觉模型按**图片分辨率换算 token**（长边超限被拒或自动缩放，tile 计价——高分辨率图是文本的 100-1000 倍成本），20MB 原图（手机 4000×3000）塞进去一次几毛到几块钱。② 预处理流水线：**压缩到任务够用的分辨率**（读文字 1500px 长边够、认场景 768px 够）→ 格式统一（JPEG/WebP 质量 80）→ 裁剪无关区域（UI 截图去掉浏览器 chrome）→ 超限拒绝/降采样。原则：**任务的「最小可读分辨率」而不是「用户上传分辨率」**。③ 多图控制：N 张图的成本线性叠加——页面对比类任务（多图必须同看）没法省，序列类任务（文档逐页）改分批 + 每批摘要传递（map-reduce 模式）控窗口。④ OCR vs 视觉：纯文字提取（合同/发票）OCR（快、便宜、文本可控）+ 文本进 LLM；版面理解（图表关系/截图布局/手写）必须视觉模型——混合策略：先廉价 OCR 抽文本，视觉只处理 OCR 搞不定的部分。

```python
# 全部标准库；demo 实现「分辨率预算计算器 + 多图分批策略 + OCR/视觉分流」
import math, re

def image_tokens(w: int, h: int, tile: int = 512, tokens_per_tile: int = 170) -> int:
    """tile 计价模型（OpenAI 风格简化口径）：分辨率 → token。"""
    tiles = math.ceil(w / tile) * math.ceil(h / tile)
    return tiles * tokens_per_tile

def preprocess_plan(w: int, h: int, task: str, max_tokens_per_img: int = 1600) -> dict:
    """按任务给最小可读分辨率，超预算降采样。"""
    min_side = {"scene": 768, "text": 1500, "chart": 1200}[task]
    scale = min(min_side / min(w, h), (max_tokens_per_img / image_tokens(w, h)) ** 0.5, 1.0)
    nw, nh = int(w * scale), int(h * scale)
    return {"resize": (nw, nh), "tokens": image_tokens(nw, nh),
            "saved_pct": 1 - image_tokens(nw, nh) / image_tokens(w, h)}

def batch_pages(pages: list[int], window_tokens: int = 30000, per_page: int = 1600) -> list[list[int]]:
    """多图分批：窗口内塞满，批间用摘要传递（map-reduce）。"""
    per_batch = window_tokens // per_page
    return [pages[i:i+per_batch] for i in range(0, len(pages), per_batch)]

def route_ocr_vs_vision(task: str, has_chart: bool, is_handwriting: bool) -> str:
    """分流：纯文字 OCR 便宜 10×；版面/图表/手写走视觉。"""
    if task == "extract_text" and not has_chart and not is_handwriting:
        return "ocr + text-llm（成本 1/10）"
    return "vision-model"

if __name__ == "__main__":
    plan = preprocess_plan(4000, 3000, "text")
    print(f"手机原图(4000×3000) 原始 {image_tokens(4000,3000)} tok → "
          f"预处理 {plan['resize']} = {plan['tokens']} tok（省 {plan['saved_pct']:.0%}）")
    assert plan["saved_pct"] > 0.5
    batches = batch_pages(list(range(60)))
    print(f"60 页文档 → {len(batches)} 批 × {len(batches[0])} 页（窗口预算内，批间摘要传递）")
    assert all(len(b) <= 18 for b in batches)
    print("分流:", route_ocr_vs_vision("extract_text", False, False), "/",
          route_ocr_vs_vision("analyze", True, False))
    # 口径：预处理省的是数量级的钱；OCR 先行 + 视觉兜底是成本最优默认架构。
```

**追问**：1) 为什么「文字读取」需要更高分辨率而「场景识别」不用？——文字的最小可读尺寸是像素级的（笔画宽度 ~2px），场景语义在低分辨率下保留（轮廓/颜色布局）；按任务定分辨率就是按信息密度定预算。2) tile 计价和「按面积线性」有什么工程差异？——tile 是阶梯式（超过半 tile 算整 tile），缩小尺寸的收益是阶梯跳跃的——降到 tile 边界下方才能真省，连续微调无效；预算计算器要按 tile 粒度取整。3) 视频帧怎么控？——关键帧抽取（场景切换检测）替代均匀采样（均匀采 90% 是重复信息）+ 事件类任务抽帧密度按内容动态调；帧数 × 每帧 token 一样爆炸，关键帧是数量级杠杆。

## 背诵要点
1. 图片成本 = 分辨率换算 token（tile 计价），预处理按「任务最小可读分辨率」，收益是数量级。
2. 多图分批 map-reduce（批间摘要传递）；tile 阶梯计价要按边界取整才能真省。
3. OCR 先行 + 视觉兜底：纯文字提取便宜 10×，版面/图表/手写才用视觉模型。

## 复盘追问
1. 用户抱怨「上传的清晰图被识别错文字」，预处理降采样过头了怎么平衡？（提示：按任务置信度反馈自适应（识别置信低→提高分辨率重试一次），或文字任务保底 1500px 硬下限）
2. 多模态 RAG 里图片怎么建索引？（提示：图片描述（caption 由视觉模型生成）进文本索引 + 原图按引用关联——检索走文本、回答时才载图，避免全库图片 embedding 成本）
