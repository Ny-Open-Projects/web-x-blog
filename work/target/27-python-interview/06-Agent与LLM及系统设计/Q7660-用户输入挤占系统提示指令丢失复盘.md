### Q7660 · 用户输入挤占系统提示的指令丢失复盘

难度：P6-P7 | 标签：Agent、上下文管理、事故复盘

**问**：长会话 Agent 运行 40 轮后开始"忘记"工具调用规范、输出格式漂移，甚至把系统提示里的安全指令忽略。排查发现是历史裁剪策略"保末尾 N token"把系统提示与早期关键约定挤出了窗口。复盘：为什么会挤占？裁剪策略应该怎么设计才不会丢指令？

**答**：结论：事故结构是"**平铺上下文 + 尾部裁剪**"——系统提示、关键约定与对话历史混在同一线性序列里，按 token 预算从尾部保留时，头部（系统提示与前 N 轮建立的行为约定）最先被挤掉；模型对"窗口外不存在的内容"天然无记忆，于是规范逐轮漂移。修复原则是**分层驻留**：系统提示与关键约定是常驻层（永不裁剪），历史是可裁层（裁剪触发摘要压缩），工具定义按需装载（Q7654）。

取舍与实战：
1. 裁剪预算分账：上下文 = 常驻层（系统提示 + 安全指令 + 输出 schema，占 15-25%）+ 摘要层（被裁历史的滚动摘要，占 10-20%）+ 工作层（最近 K 轮原文，占 40-60%）+ 输出预留。裁剪只动工作层，且触发阈值在 80% 水位（Q2033 用量仪表）提前压缩，而不是撞墙才裁。
2. "关键约定上浮"：会话前几轮用户/系统确立的约定（"以后都用 JSON 输出""不要调这个工具"）要结构化提取进常驻层——纯靠原文保留会随裁剪消失，Q1756 滚动摘要需要带"指令保护区"。
3. 验证手段：指令遗忘回归集——一组跨越多轮的"约束型测试"（第 3 轮设约束，第 30 轮检查遵守），每次改裁剪策略必跑；事故就是没跑这个集。
4. 模型差异：部分模型对首尾内容（primacy/recency 偏置）注意力强、中部弱，关键指令放系统提示（首位）比塞在对话中段可靠。

```python
"""分层上下文预算：常驻/摘要/工作层裁剪守卫（标准库，可运行）"""
from dataclasses import dataclass, field


@dataclass
class ContextBudget:
    total_tokens: int = 128_000
    reserve_out: int = 4_000                  # 输出预留
    system_tokens: int = 6_000                # 常驻层（永不裁剪）
    summary_tokens: int = 8_000               # 滚动摘要层
    work_tokens: int = 0                      # 工作层当前占用
    trigger_pct: float = 0.8                  # 裁剪触发水位

    def work_cap(self) -> int:
        return (self.total_tokens - self.reserve_out
                - self.system_tokens - self.summary_tokens)

    def needs_compaction(self) -> bool:
        return self.work_tokens >= self.work_cap() * self.trigger_pct

    def compaction(self, tokens_to_keep: int) -> dict:
        """裁剪工作层尾部之外内容 → 压入摘要层；返回账目"""
        if not self.needs_compaction():
            return {"action": "none"}
        keep = min(tokens_to_keep, self.work_tokens)
        self.work_tokens = keep
        return {"action": "compact", "kept": keep,
                "常驻层未动": self.system_tokens,
                "工作层水位": f"{keep}/{self.work_cap()}"}

b = ContextBudget(work_tokens=95_000)
print(b.compaction(tokens_to_keep=50_000))
assert b.work_tokens == 50_000 and b.system_tokens == 6_000  # 常驻层没被挤占
```

**追问 1**：为什么"撞墙才裁"比"80% 水位预裁"更容易引发事故？
**提示**：撞墙裁剪发生在请求即将超限的时刻，压缩动作（LLM 生成摘要）本身要耗时耗 token，容易连锁超限失败；且撞墙时来不及做"关键约定上浮"，只能粗暴截断。

**追问 2**：把系统提示放窗口开头就一定安全吗？还有什么会破坏它？
**提示**：注入攻击（Q7652）可以诱导模型"重写/忽略"系统提示；某些供应商在长上下文下对 system 的注意力衰减；防御是安全指令重复驻留（系统提示 + 关键节点重申）+ 输出校验兜底。

## 背诵要点
- 事故根因：平铺上下文 + 尾部裁剪把头部系统提示挤出窗口；修复靠分层驻留（常驻/摘要/工作层）。
- 预算账：常驻 15-25% + 摘要 10-20% + 工作 40-60% + 输出预留；80% 水位预裁不撞墙。
- "指令遗忘回归集"是裁剪策略的必跑测试：跨多轮约束型用例。

## 复盘追问

- 若裁剪策略从"保尾部"改为"重要性打分保留"，回归集要加哪些新用例？
