### Q7748 · 模型输出 userName，schema 要 user_name：必填字段「缺失」，落库全是 None

难度：P6 ｜ 标签：LLM、结构化输出、字段命名、键归一化

基线：Python 3.12；`re` 手写 camelCase→snake_case，含碰撞检测与 fail-closed 策略。

**问**：抽取接口的 JSON Schema 用 snake_case（`user_name`、`order_id`）。加了 few-shot 之后，模型开始输出 `userName`、`orderId`，校验报 `user_name is required`，重试几次仍然如此；后来把校验放宽成"键名包含即可"，又有单据的用户名写成了空。日志里模型输出看着是对的。字段名风格为什么能把整条链路搞挂？

**答**：
- **结论**：模型对**命名风格**没有"契约感"，它会跟随 few-shot 示例、上游代码风格、甚至训练数据里的主流写法。Schema 里 `required` 是精确匹配，`userName != user_name`，所以校验失败；而放宽成模糊匹配（忽略大小写/下划线）后，又可能出现**两个键映射到同一个字段**（`userName` 与 `user_name` 同时出现且值不同），此时随便取一个就是静默错数据。
- **取舍**：① **规范化 + 碰撞检测 + fail-closed**：归一化只做"无损等价"映射（camelCase→snake_case、大小写统一），一旦两个原始键映射到同一目标键就拒绝，让模型重试；② 更稳的是**别名表驱动**：先按 schema 声明的字段生成允许别名（`user_name` ← `userName`/`UserName`），只映射表内的键，未知键保留原样并告警；③ 从源头减少漂移：few-shot 里的示例严格用 schema 的写法，schema 的 `description` 里写明"键名必须是 snake_case"；④ 下游取字段用 `data["user_name"]`（KeyError 早失败），不要 `data.get(...)` 后写 NULL。
- **实战**：① 校验分两层：结构（键集合/类型）与语义（值域/非空），结构失败直接重试，语义失败转人工；② 记录"原始键 → 归一化键"的映射日志，漂移率是 prompt/schema 质量的指标；③ 单测覆盖 camelCase、PascalCase、带数字（`orderId2`）、全大写缩略词（`userID`）；④ 别在归一化里做"拼写纠错"（`usr_name` → `user_name`），那是猜测，不是等价变换。

```python
"""键名漂移：规范化能救格式，救不了碰撞；碰撞必须 fail-closed。"""
import re

SCHEMA_FIELDS = {"user_name", "order_id", "amount"}


def camel_to_snake(key: str) -> str:
    step1 = re.sub(r"(.)([A-Z][a-z]+)", r"\1_\2", key)
    return re.sub(r"([a-z0-9])([A-Z])", r"\1_\2", step1).lower()


def normalize(obj: dict) -> tuple[dict, list[str]]:
    out: dict = {}
    errors: list[str] = []
    for key, value in obj.items():
        target = camel_to_snake(key)
        if target in out and out[target] != value:
            errors.append(
                f"键碰撞: {key!r} 与已有字段都映射到 {target!r}"
                f"（{out[target]!r} vs {value!r}）")
            continue
        out[target] = value
    return out, errors


def validate(data: dict) -> list[str]:
    return [f"missing required: {f}" for f in sorted(SCHEMA_FIELDS)
            if f not in data or data[f] in (None, "")]


def accept(raw: dict) -> tuple[bool, list[str]]:
    norm, collisions = normalize(raw)
    problems = collisions + validate(norm)
    return (not problems), problems


SAMPLES = [
    {"userName": "ann", "orderId": 7, "amount": 100},
    {"user_name": "bob", "order_id": 8, "amount": 50},
    {"userName": "ann", "user_name": "bob", "orderId": 9, "amount": 10},
    {"userID": "u-1", "orderId": 10, "amount": 20},
]

if __name__ == "__main__":
    for raw in SAMPLES:
        norm, collisions = normalize(raw)
        print("原始:", raw)
        print("  归一化:", norm)
        ok, problems = accept(raw)
        print("  碰撞:", collisions or "无")
        print("  最终:", "接受" if ok else f"拒绝 -> {problems}")
        print("  严格校验（不归一化）:", validate(raw) or "通过")
        print()

    # 下游用 .get 会静默写 NULL
    bad = {"userName": "ann", "orderId": 7, "amount": 100}
    print("下游 data.get('user_name') ->", bad.get("user_name"),
          "-> 落库为 NULL，不报错")
    print("结论：先归一化再校验；碰撞即拒绝；下游用 [] 取值让缺失早失败")
```

**追问一**：为什么碰撞不能"按某个优先级取一个"？

→ 解析：两个键同时出现且值不同，说明模型对同一个字段给出了**两个互相矛盾的答案**（类似重复键）。取 camelCase 还是 snake_case、取先出现还是后出现，都是任意规则，且无法从数据本身判断哪个对。正确做法是当作校验失败：把两个键都回灌给模型，让它只输出一个；如果两次仍冲突，转人工。静默取一个的代价是"错数据看起来像对的"，比失败难发现得多。

**追问二**：在 schema 层能不能直接禁止这种漂移？

→ 解析：JSON Schema 的 `additionalProperties: false` 只能拒绝**多余字段**，不能阻止你把 `userName` 当成必填 `user_name` 的替代——它只会让校验失败，模型仍可能继续产生 camelCase。真正减少漂移的是三件事：`enum`/字段名在 description 里显式写死、few-shot 示例严格用 snake_case、以及**输出后做一次规范化再校验**（把失败率降到接近零）。对必须零容忍的场景，用供应商的 strict 模式（约束解码），让模型只能产出 schema 允许的键名。
