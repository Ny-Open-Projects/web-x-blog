### Q7508 · 流式输出的背压与取消:SSE 中断的计费一致性

> 难度:★★★ | 标签:LLM, 流式, 计费

**问**：SSE 流式输出时用户中途关页面，服务端该取消上游 LLM 调用吗？取消后 token 怎么计费才不多算也不少算？实测中还出现过"用户断了但上游还在烧钱"——这条链路怎么设计？

**答**：结论：用户断开必须**尽快取消上游调用**（省真金白银），取消语义要用"尽力终止 + 服务端权威计量"而不是"客户端统计"。计费一致性的正确做法是：**以服务端收到的最终 usage（或流末帧）为准落账，客户端断开造成的部分输出按服务端实际消费的 token 计费**；中间帧只是 UX，不能作为计费依据。核心难点在于三段链路的取消传播：客户端→网关→供应商，任何一段断了都要有"对账"兜底。

机理与实战：
- 取消传播：ASGI/SSE 场景下客户端断开会触发 `request` 取消，要在 finally/取消路径里对上游调用做显式取消（aiohttp/httpx 的 `task.cancel()` + 关闭连接），并把"取消是否成功送达供应商"区分开——供应商侧取消（部分 API 支持 abort）与仅本地断开（供应商继续生成并全额计费）是两种成本结局，监控要分开计数。
- 计费对账：流式响应的 usage 可能在最后一块（stream_options include_usage）或根本不下发（部分供应商），此时用服务端 tokenizer 估算落账，T+1 与供应商账单对账修正。账务上"估算+对账"是唯一可审计的姿势，直接信客户端上报必被刷。
- 事故复盘：用户断开后 P99 成本上涨，排查发现网关用同步客户端读上游（断开不传播），供应商继续生成 2KB 长答案。修复：网关改异步 + 断开即 `cancel` + 供应商支持 abort 的路由优先；取消成功率从 0% 到 92%，月成本降 18%。

```python
# 基线:Python 3.9+ 标准库;取消传播 + 服务端权威计量的骨架(可运行)
import asyncio

async def upstream_stream():
    """模拟供应商流:20 个 chunk,每个 1 token;被取消即停止生成(可 abort 的供应商)。"""
    for i in range(20):
        await asyncio.sleep(0.01)
        yield {"delta": f"w{i}", "tokens": 1}
    yield {"usage": {"total_tokens": 20}}         # 流末权威 usage

async def serve(client_alive_after: int) -> dict:
    """消费流:消费 N 块后模拟客户端断开 -> 取消上游 -> 按服务端实收计费。"""
    billed = 0
    agen = upstream_stream()
    try:
        async for chunk in agen:
            if chunk.get("usage"):                # 权威 usage 优先于逐块累加
                billed = chunk["usage"]["total_tokens"]
                break
            billed += chunk["tokens"]
            client_alive_after -= 1
            if client_alive_after <= 0:           # 用户关页面:传播取消
                await agen.aclose()               # 触发 GeneratorExit -> 上游停止
                break
    except asyncio.CancelledError:
        raise
    return {"billed_tokens": billed}              # 估算值,T+1 与账单对账修正

async def main() -> None:
    print(serve(client_alive_after=20))           # 完整消费 -> 20 token
    print(serve(client_alive_after=3))            # 3 块后断开 -> 仅 3 token

if __name__ == "__main__":
    asyncio.run(main())
```

**追问**：
- 一层追问：取消后已生成的前半段要不要返回给客户端（重连续传）？——产品决策：续传要求服务端缓存半截响应并带幂等键（session+seq），实现复杂且半截词有语义风险；多数产品选择"丢弃+重新生成"，但计费仍按已消耗 token，这就是"花了钱没交付"的真实成本，要进成本模型。
- 二层追问：怎么发现"断开未取消"这类泄漏？——指标三件套：取消请求成功率、上游生成时长 vs 客户端存活时长的差值分布、供应商账单 token 与服务端统计 token 的偏差率；差值持续 > 5% 即有泄漏或计量 bug。
- 三层追问：背压在 LLM 流式链路里体现在哪？——客户端消费慢（不读 SSE）→ TCP 缓冲满 → 网关 write 阻塞 → 应主动断开（省上游），而不是无限缓冲；网关要设输出缓冲上限与"读超时"，这是防止慢客户端拖垮成本的关键。
