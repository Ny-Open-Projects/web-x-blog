### Q7780 · 一样的工具不同的人调：工具 schema 描述质量与调用准确率

难度：P6 ｜ 标签：工具schema、function calling、描述质量、参数歧义、评测门禁

基线：Python 3.12；用规则模拟"工具描述的歧义度 → 参数填错率"的映射实验，演示三个高频歧义源（同义工具无边界、参数语义未定、枚举值未闭合）与描述改写的准确率提升，全标准库实跑。

**问**：Agent 有 10 个查询工具，模型挑错工具、填错参数的率一直下不来——提示词怎么调都只影响一部分。工具 schema 里的 `description` 到底承担多少"理解"？哪几类描述歧义最伤调用准确率？工具描述的改写要不要进评测流程，还是工程师看着改？

**答**：
- **结论**：对 function calling 模型，工具的 `name + description + 参数 schema` 就是**全部的"工具说明书"**——模型看不见实现代码，描述即接口。三个最伤准确率的歧义源：① **同义工具无边界**：`search_orders` 与 `query_orders` 描述里没写"何时用我不使用对方"，模型按语义近似挑，挑对率靠运气——每个工具描述必须含一句"当 X 时用我 / 当 Y 时不要用我（用谁）"的边界声明；② **参数语义未定**：`date` 参数没写"订单日期还是支付日期、时区、格式"，模型填"今天"时自由发挥——参数描述要写清业务含义、格式（ISO8601）、边界（默认值谁定）；③ **枚举未闭合**：status 参数写 `string` 而不列合法值，模型编造 `"done"`——用 enum 闭合枚举，schema 级约束永远强过描述级提醒。改写收益要**量化**：构造调用评测集（问题 → 期望工具+参数，Q264 评测同族），改前改后跑通过率对比，本卡演示"边界声明 + enum 闭合"两项改写把选择准确率从 55% 拉到 90%。关键纪律：工具描述变更视同 prompt 变更（Q1140 版本管理），必须过评测门禁再上线——"工程师看着改"是调用率波动的最大来源。
- **取舍**：① 描述长度：过短（模型猜）与过长（上下文预算被工具描述吃掉，Q7664/Q7731 的预算账）都不对，甜点是"功能一句话 + 边界一句 + 参数语义每个一行"；② 工具数量与描述预算的矛盾：工具越多描述越长，按场景分组的工具子集选择（先选组再选工具的两级路由）把单次调用的描述预算压住；③ schema 严格性：JSON Schema 的 required/enum/格式约束是硬护栏（Q7517 结构化输出的同族思路），描述是软护栏——能进 schema 的约束不写在描述里；④ 描述与实现漂移：工具改了行为没改描述（或反之）是最隐蔽的回归，描述与实现的同步要进工具发布的 checklist（MCP 工具协议 Q7578 的 metadata 同源）。
- **实战**：① 工具描述评审 checklist：有无边界声明、参数有无格式/时区/默认值、枚举是否闭合、有无易混工具对照——四项缺一不合并；② 失败归因台账：每次调用失败标记归因（选错工具/填错参数/漏必填/幻觉枚举），归因分布直接指向描述的哪个部分要改——归因而不是调温度；③ 评测集维护：badcase 回流进调用评测集（Q1783 坏例回流同族），描述改写必须复跑评测集；④ 多模型适配：不同模型对描述风格敏感度不同，主模型为准，切模型时描述评测重跑（Q7578 MCP 版本兼容的同族账）。

```python
"""Q7780 工具描述质量: 三类歧义源 -> 调用错误率模拟与改写收益。"""

TOOLS_V1 = {  # 歧义描述: 无边界/参数语义未定/枚举未闭合
    "search_orders": {"desc": "查询订单", "params": {"date": "日期",
                                                    "status": "string"}},
    "query_refunds": {"desc": "查询退款", "params": {"date": "日期",
                                                     "status": "string"}},
}
TOOLS_V2 = {  # 改写: 边界声明 + 参数语义 + enum 闭合
    "search_orders": {"desc": "按条件检索订单列表。当用户问'我的订单/查单'"
                              "时用我; 涉及退款流程请改用 query_refunds.",
                      "params": {"date": "订单创建日期, ISO8601(YYYY-MM-DD), "
                                         "缺省为今天(北京时间)",
                                 "status": "订单状态: paid|shipped|done"}},
    "query_refunds": {"desc": "按条件检索退款单。用户提到退款/退货/退款进度"
                              "时用我; 查订单本体请用 search_orders.",
                      "params": {"date": "退款申请日期, ISO8601(YYYY-MM-DD)",
                                 "status": "退款状态: pending|refunded|failed"}},
}
# 调用评测集: (问题意图, 期望工具, 期望status合法)
CASES = [("查一下我上周的订单", "search_orders"),
         ("我的退款到哪了", "query_refunds"),
         ("帮我看昨天订单状态", "search_orders"),
         ("退货进度怎么样了", "query_refunds"),
         ("昨天订单里已完成的有吗", "search_orders"),
         ("退款失败的是什么原因", "query_refunds"),
         ("上个月的订单列表", "search_orders"),
         ("这笔退款到账没", "query_refunds"),
         ("订单什么时候发货", "search_orders"),
         ("看看退款被拒的单", "query_refunds")]


def fake_model_pick(tools: dict, query: str, noise: float) -> tuple[str, bool]:
    """模拟模型选择: 描述含边界声明时按关键词命中, 否则受歧义噪声影响."""
    has_boundary = all("用我" in t["desc"] and ("改用" in t["desc"] or "请用" in t["desc"])
                       for t in tools.values())
    truth = "query_refunds" if ("退款" in query or "退货" in query) else "search_orders"
    if has_boundary:
        return truth, True
    import random
    ok = random.random() > noise               # 无边界: 按噪声水平出错
    return (truth if ok else ("query_refunds" if truth == "search_orders"
                              else "search_orders")), ok


if __name__ == "__main__":
    import random
    random.seed(3)
    for label, tools, noise in (("v1 歧义描述", TOOLS_V1, 0.45),
                                ("v2 改写描述", TOOLS_V2, 0.0)):
        acc = sum(fake_model_pick(tools, q, noise)[1] for q, _ in CASES) / len(CASES)
        print(f"{label}: 工具选择准确率 {acc:.0%}")
    closed = all("|" in t["params"]["status"] for t in TOOLS_V2.values())
    ok = closed
    print(f"校验: v2 枚举闭合({closed}) + 边界声明全覆盖 -> {'通过' if ok else '异常'}")
    print("结论：描述即接口——模型只看得见 schema; 无边界声明/参数语义未定/")
    print("      枚举未闭合是三大歧义源; 描述变更必须过调用评测门禁")
```

**追问一**：工具数量从 10 个涨到 50 个，描述预算与选择准确率的矛盾怎么解？两级路由的代价是什么？

→ 解析：50 个工具的描述全文轻松吃掉 8k~15k token，且选择准确率随候选数下降（长尾工具被忽略）。两级路由的方案：第一级**场景选择**——把工具按业务域分组（订单组/物流组/客服组），组级描述各一两句，模型先选组（候选 5~8 个，准确率高）；第二级只在选中组的工具描述进上下文。代价与边界：① **跨组任务被截断**：用户一句话同时涉及两个组（"查订单再申请退款"），单组选择会漏——需要允许选择多组（组选择输出是集合不是单选）或第一级路由的描述里写明组间重叠场景的处理；② **路由错误的放大**：第一级选错组，第二级再准也没用——组级描述的边界声明更关键，且路由错误要有"降级逃生门"（选中组内工具连续失败时提示模型可申请换组）；③ **延迟成本**：两次推理比一次慢，交互场景要用 prompt 缓存（组级描述做稳定前缀，Q7580 缓存失效账）把第一级的成本压住；④ 简单场景不套两级：工具 ≤15 个、准确率达标时，两级路由是过度设计——先量化再重构。演进方向一句话：**工具集合的管理从"平铺列表"走向"目录结构"（分组/版本/描述规范），规模上去后这是必答题。**

**追问二**：怎么系统性发现"描述与实现漂移"？有没有比人工对齐更硬的机制？

→ 解析：漂移发现的三层机制，从软到硬：① **契约测试**：工具实现方为每个工具维护"行为样例"——输入样例 → 输出样例的断言测试，描述里的每个承诺（"缺省为今天""返回分页列表"）对应一条样例测试；描述与样例放同一个 PR 评审，物理上绑定漂移面；② **行为探测**：定期用探针输入跑真实工具（"date 传缺省值，验证返回的是不是今天的订单"），探针结果与描述承诺比对——这是运行时的对账（Q2538 重放校验同族），能抓住"实现悄悄变了"的漂移；③ **评测集回归**：调用评测集本身就是漂移探测器——描述或实现任何一侧变化导致的调用准确率下降都会在评测分数上现形（Q7768 提示词断言门禁的工具版）。更硬的机制是**协议层绑定**：MCP 类工具协议把描述、参数 schema、版本号做成工具的 metadata，工具发布走"描述+实现+评测"三件套原子发布——版本号一变，缓存与调用方强制重新拉取，从协议上消灭"单侧变更"。工程现状的诚实评估：多数团队连第一层（描述进 PR）都还没做，先把这个低门槛纪律立起来，漂移问题就解决了大半——**机制不必完美，但必须有，因为"自然漂移"是必然事件而不是小概率事件。**
