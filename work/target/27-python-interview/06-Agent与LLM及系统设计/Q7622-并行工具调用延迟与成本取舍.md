### Q7622 · Agent 并行工具调用的延迟与成本取舍账

难度：P6 ｜ 标签：成本工程 / 并行编排 / Agent 延迟

**问**：一个 Agent 每轮要调 3~5 个工具（查库、查外部 API、读文档），目前串行执行，单轮 4s。并行化能把延迟压下来，但并行调用会放大什么成本与风险？哪些工具能并行、哪些必须串行？取舍框架是什么？

**答**：
- **结论**：延迟账：串行总时长 = Σ 各工具时延；并行（无依赖时）= max(时延) + 编排开销——3 个 1.2s 工具从 3.6s 压到约 1.3s。成本与风险的三类放大：① **输入 token 放大**——并行结果全部塞回下一轮上下文，若结果是长文本，总上下文 token 可能比串行"边用边裁"更高（串行可以读完 A 再决定要不要拉 B）；② **浪费放大**——并行执行了"串行时会被短路"的调用：串行里 B 依赖 A 的结果（A 失败就不调 B），并行下 A 失败但 B 已发出，调用量与外部 API 费用按扇出倍数放大（Q7600 重试放大同源）；③ **限流与下游压力**——N 路并发打向同一外部 API，429/超时概率上升，重试进一步放大（Q7622 与 Q7564 扇出背压同源）。可并行判定：**数据依赖**（B 需要结果 A）必须串行；**控制依赖**（A 失败则 B 无意义）建议串行或带"取消联动"的并行；两者皆无 → 并行 + 失败隔离（部分失败不阻塞整轮，Q1152 同源）。取舍框架：并行度 = min(无依赖工具数, 下游限流余量, token 预算)；高成本外部调用（付费 API）倾向串行或延迟并行（先并行便宜探查、按需补昂贵调用）。
- **取舍**：实现层面：`asyncio.gather` + 每路独立超时与异常捕获；共享限流器按下游配额（Q7622 与 ETL 全局限流同源）；上下文管理——并行结果按需注入（工具结果超过阈值给摘要而非全文，Q7575 同源）。模型侧注意：让模型**显式声明并行意图**（一轮发多个工具调用）比框架层猜测依赖更可靠，但 prompt 要教会它"有依赖就等"；框架层的自动依赖分析（读工具描述参数来源）只能做保守提示。
- **实战**：落地：① 工具清单标注三色：可并行（无依赖）/ 受控并行（取消联动）/ 必须串行；② 每轮编排记录"并行决策与结果大小"，复盘 token 账与调用量账；③ 下游配额按并行度重新核算（原来按串行 QPS 申请的配额会被并行打爆）；④ 观测：并行轮次 vs 串行轮次的延迟、token、外部调用费用三维对比，防止"省了延迟贵了 token"的假优化。

```python
# 并行工具调用账: 延迟 = max(并行支路), 但 token/浪费/限流三重放大
# 基线: Python 3.9+ 标准库; 真实场景 asyncio.gather + 全局限流器
import asyncio
from dataclasses import dataclass, field


@dataclass
class Tool:
    name: str
    latency_s: float
    result_tokens: int
    cost: float            # 单次调用费用(外部API)
    depends_on: str | None = None


def serial_round(tools: list[Tool]) -> tuple[float, int, float]:
    lat = sum(t.latency_s for t in tools)
    tok = sum(t.result_tokens for t in tools)
    cost = sum(t.cost for t in tools)
    return lat, tok, cost


async def parallel_round(tools: list[Tool]) -> tuple[float, int, float]:
    """无依赖工具并行；有依赖者被短路跳过(A 失败则 B 不执行)。"""
    ok: set[str] = set()
    lat = tok = cost = 0.0
    pending = list(tools)
    while pending:
        runnable = [t for t in pending if t.depends_on is None or t.depends_on in ok]
        results = await asyncio.gather(*[asyncio.sleep(t.latency_s) for t in runnable],
                                       return_exceptions=True)
        nxt = []
        for t, r in zip(runnable, results):
            lat = max(lat, t.latency_s)
            if isinstance(r, Exception) or (t.name == "a" and False):
                continue
            ok.add(t.name)
            tok += t.result_tokens
            cost += t.cost
        nxt = [t for t in pending if t not in runnable]
        if not runnable and nxt:      # 依赖永不满足 -> 短路
            nxt = [t for t in nxt if t.depends_on not in ok]
            pending = nxt if nxt != pending else []
        else:
            pending = nxt
    return lat, tok, cost


def main() -> None:
    tools = [Tool("db", 1.2, 800, 0.0), Tool("ext", 1.0, 2000, 0.02),
             Tool("doc", 1.3, 1500, 0.0)]
    lat_s, tok_s, cost_s = serial_round(tools)
    lat_p, tok_p, cost_p = asyncio.run(parallel_round(tools))
    assert abs(lat_s - 3.5) < 1e-9 and abs(lat_p - 1.3) < 1e-9
    assert tok_p == tok_s and abs(cost_p - cost_s) < 1e-9
    print(f"延迟 {lat_s:.1f}s -> {lat_p:.1f}s; token/费用同量(无浪费因全成功)")

    # 浪费放大: A 失败时串行短路 B, 并行下 B 已发出(白花 0.02)
    async def fail_a():
        await asyncio.sleep(1.0)
        raise RuntimeError("a failed")
    tools2 = [Tool("db", 1.2, 800, 0.0), Tool("ext", 1.0, 2000, 0.02, depends_on="db")]
    print(f"依赖短路: 串行 {serial_round(tools2)[2]:.2f} vs 并行可能白花 B 的费用")
    print("OK: 并行度 = min(无依赖数, 下游限流, token预算); 假优化要三账对拍")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么并行结果"全部塞回上下文"可能比串行更贵？
→ 一句话提示：串行可以在读完 A 后决定"不调 B"或"B 只要摘要"，天然省 token；并行把所有支路结果一次性拉回，配合模型下一轮全量上下文计费（Q7614 同源），省下的秒数可能被 token 账反杀——所以并行要配"结果注入策略"。

**追问 2**：下游限流按串行申请的配额，并行化后要重新核算什么？
→ 一句话提示：并行度 N 意味着瞬时 QPS 放大 N 倍，429 概率陡升且重试进一步放大；要么全局限流器把并行压在配额内（延迟收益打折），要么重新申请配额——不能默认下游扛得住。

## 背诵要点
- 延迟账：串行 Σ时延 → 并行 max 时延 + 编排开销；3 个 1.2s 工具 3.6s→1.3s，但 token/浪费/限流三重放大可能反杀。
- 并行判定：数据依赖必须串行、控制依赖取消联动、双无依赖才真并行；并行度 = min(无依赖数, 下游限流余量, token 预算)。
- 优化有效性要三账对拍（延迟/token/外部费用）；并行结果按需注入（超阈值给摘要），高成本外部调用倾向串行或延迟并行。

## 复盘追问
- 为什么"模型显式声明并行意图"优于框架自动依赖分析？提示：依赖信息在模型对任务的规划里（它知道 A 的结果是不是 B 的输入），框架只能从工具签名保守猜测——猜错就是浪费调用或错误短路；框架层做的是限流与失败隔离，不是依赖决策。
- 假优化（延迟降了、总成本涨了）在监控上怎么第一时间识别？提示：按轮次聚合三维指标（延迟、token、外部调用费用）并算"单位任务总成本"，任一维度改善但总成本上升即告警——单维度看板会掩盖交叉效应。
