### Q7602 · Agent 并发会话数与下游工具 API 配额容量账

难度：P7 ｜ 标签：Agent / 容量规划 / 配额

**问**：Agent 平台支持 500 并发会话，每个会话平均一步调 2 个工具，某工具下游是内部订单系统（QPS 上限 200）。上线后 Agent 会话大量卡顿，订单系统也在告警。会话数到工具 API 的容量换算怎么算？"每会话 × 每步"的乘法账里最容易漏什么？

**答**：
- **结论**：容量链换算：`下游工具 QPS = 并发会话数 × 每步工具调用数 × 工具命中率 / 平均调用时长`——注意并发会话数是"同时在思考/执行的全周期并发"，某时刻真实的工具瞬时并发是 `会话数 × 单会话同时打开的工具调用数`，而不是会话数本身。最容易漏的三项：① **重试系数**——下游偶发 5xx 时各客户端重试，账面 100 QPS 实际 130；② **扇出**——并行工具调用（一次 step 并发调 3 个工具）把瞬时并发乘 3；③ **长尾占用**——P99 慢调用占住连接/槽位，让有效并发低于账面。订单系统 200 QPS 上限对 500 会话 × 命中率 0.3 × 2 工具 = 300 QPS 需求，本身就是超载设计，任何抖动都会雪崩。
- **取舍**：解法按侵入度排序：① 入口限流（会话创建按下游配额反推上限，如 500 × 0.4 = 200 会话）——简单但浪费 Agent 容量；② 按工具分级配额——高危工具（写下游）加令牌桶，低危不限——精细但要改框架；③ 结果缓存与合并——只读工具加短 TTL 缓存，相同参数请求合并（singleflight）。超配额时的行为设计：排队（保序但延迟升）vs 快速失败转降级回复（"系统繁忙，稍后再试"）vs 降级到只读路径——对交互式 Agent，明确告知比静默排队体验好。
- **实战**：步骤：① 给每个工具标注下游容量（QPS/超时/幂等性），形成工具容量表；② 上线前做"会话数 × 压测脚本"推演下游 QPS；③ 框架层实现工具级令牌桶 + 排队深度上限；④ 复盘项：监控"工具级等待时长分布"，排队 P99 > 超时预算的 50% 就要扩下游或限流。

```python
# Agent 会话到下游工具的容量换算器（纯标准库）
# 基线：Python 3.9+

def downstream_qps(
    sessions: int,
    tool_calls_per_step: float,
    hit_rate: float,
    retry_factor: float = 1.3,
    fanout: float = 1.0,
) -> float:
    """瞬时下游 QPS 需求（含重试与并行扇出）"""
    return sessions * tool_calls_per_step * hit_rate * retry_factor * fanout


def safe_sessions(downstream_limit_qps: float, tool_calls_per_step: float,
                  hit_rate: float, retry_factor: float = 1.3,
                  utilization_cap: float = 0.8) -> int:
    """按下游配额反推最大并发会话数"""
    raw = downstream_limit_qps * utilization_cap / (
        tool_calls_per_step * hit_rate * retry_factor)
    return int(raw)


def main() -> None:
    need = downstream_qps(sessions=500, tool_calls_per_step=2,
                          hit_rate=0.3)
    print(f"500 会话需要下游 ≈ {need:.0f} QPS")
    assert abs(need - 390) < 0.1  # 500*2*0.3*1.3
    # 下游只有 200 QPS：反推安全会话数
    s = safe_sessions(200, 2, 0.3)
    print(f"安全会话数 ≈ {s}")
    assert s == 205  # 200*0.8/(2*0.3*1.3)
    # 并行工具调用扇出 3：瞬时并发再乘 3
    assert downstream_qps(100, 1, 1.0, fanout=3) == 390
    print("OK: 会话数须按下游配额反推，不能拍脑袋给 500")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"平均调用时长"不直接出现在 QPS 换算里？
→ 一句话提示：QPS 是到达速率与时长无关，时长决定的是"同时在途的调用数"（Little's Law: 并发 = QPS × 时长）——下游容量按 QPS 定时，要另算下游自己的并发/连接池；两个账都要算，漏一个都会打挂。

**追问 2**：工具级令牌桶的令牌数随下游扩容怎么动态调整？
→ 一句话提示：令牌速率不能硬编码，要从配置中心读下游容量声明并周期性同步，缩容时限速要滞后下调（防抖动）、扩容可立即上调——照抄副本路由的滞回策略。

## 背诵要点
- 下游 QPS = 会话数 × 每步调用数 × 命中率 × 重试系数 × 扇出；漏乘重试与扇出是最常见的超载设计。
- 会话数上限按下游配额反推（配额 × 0.8 / 单会话需求），不给"拍脑袋的 500"。
- 超配额行为三选：排队 / 快速失败明示 / 降级只读路径；交互式 Agent 优先明确告知。

## 复盘追问
- 为什么 Agent 的流量画像和普通 Web 服务不同？提示：Agent 每会话产生突发成串的调用（一步多工具、并行扇出），瞬时尖刺远高于均摊 QPS；容量按均值算必然低估峰值，要按步内最大并发设计。
- 只读工具的缓存 TTL 怎么定才不会喂给 Agent 过期数据？提示：按数据变更频率分级（配置类分钟级、状态类秒级或禁缓存），缓存键必须含全部影响结果的参数，Agent 决策依赖的数据宁缺勿旧。
