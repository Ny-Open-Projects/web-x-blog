### Q7554 · 外部工具 API 的配额与成本账

难度：P6 | 标签：成本工程、配额治理、令牌桶、降级

**问**：Agent 平台接了搜索/地图/汇率等 6 个付费工具，月底账单是预算的 3 倍。外部工具的配额为什么要"应用侧自己管"？预算账本与降级阶梯怎么设计？

**答**：
- **结论**：供应商的限流（rate limit）保护的是供应商自己，不是你的账单——Agent 的扇出模式（一个任务调 3-5 次工具、失败重试、多租户并发）会安静地把调用放大数倍。应用侧要建两本账：① 配额账：令牌桶按供应商配额限速，超出的请求排队而不是硬撞 429（429 触发的重试风暴是成本爆炸主因）；② 预算账：每次调用计价入账（工具×租户打标），月度预算 80% 告警、100% 熔断进入降级路径。降级阶梯从便宜到贵：缓存命中 → 廉价供应商 → 减少工具扇出（砍非必要工具）→ 人工兜底。
- **取舍**：排队 vs 直接失败：排队保住任务成功率但拉长延迟（延迟敏感的交互任务要跳过队列走缓存）；熔断阈值定太高等于没有预算（永远 80% 才想起降级），定太低会频繁打断正常任务——80% 告警 + 100% 熔断 + 熔断期白名单（人工任务豁免）是可操作的组合。
- **实战**：落地清单：① 每个工具注册单价与配额（供应商控制台数据同步进账本）；② 调用带租户标签，月末 showback 到业务线，让成本有主；③ 重试必须过同一个令牌桶（重试也是钱，且重试最容易撞 429）；④ 大盘看"每任务工具成本"分布，找出成本异常的任务模板。

```python
"""外部工具 API 的配额与成本账：令牌桶限速、预算账本与降级路径。"""
import time
from dataclasses import dataclass

@dataclass
class BudgetLedger:
    monthly_cap: float = 50.0        # 美元
    spent: float = 0.0
    alerted_80: bool = False

    def charge(self, calls: int, unit: float = 0.005) -> str:
        self.spent += calls * unit
        if not self.alerted_80 and self.spent >= self.monthly_cap * 0.8:
            self.alerted_80 = True
            return "预算告警：已消耗 80%，触发降级预案"
        if self.spent >= self.monthly_cap:
            return "预算熔断：外部工具只走缓存/免费路径"
        return f"正常记账：本月已用 ${self.spent:.2f} / ${self.monthly_cap:.0f}"

@dataclass
class TokenBucket:
    rate_per_sec: float = 5.0        # 供应商配额：5 QPS
    capacity: float = 10.0
    tokens: float = 10.0
    t: float = 0.0

    def acquire(self, n_calls: int, now: float | None = None) -> int:
        now = time.time() if now is None else now
        self.tokens = min(self.capacity, self.tokens + (now - self.t) * self.rate_per_sec)
        self.t = now
        granted = min(int(self.tokens), n_calls)
        self.tokens -= granted
        return granted

ledger = BudgetLedger()
bucket = TokenBucket()

# 一批 agent 任务并发扇出：每任务 3 次搜索
demand = 30
granted = bucket.acquire(demand)
deferred = demand - granted
ledger.charge(granted)
print(f"请求 {demand} 次搜索：配额放行 {granted} 次，延迟排队 {deferred} 次"
      f"（超出 5 QPS 的部分进队列而不是硬撞供应商限流）")

for calls in (2000, 6000, 2000):     # 每月搜索调用量逐月上涨
    status = ledger.charge(calls)
    print(f"月调用 {calls} 次 -> {status}")
print("降级阶梯：缓存命中 -> 廉价供应商 -> 减少工具扇出 -> 人工兜底；"
      "账本按'工具×租户'打标，成本归因到具体业务线")
```

**追问链**：
1. 追问一层：为什么"重试也过令牌桶"是成本治理的关键细节？——重试是最容易被忽略的调用来源：一次 429 触发的重试风暴能把 QPS 翻倍再翻倍（重试→再限流→再重试），账单和延迟双爆。重试进桶意味着重试也要排队，用延迟换稳定，避免正反馈放大。
2. 追问二层：怎么定位"哪个任务模板在烧钱"？——账本按工具×租户×任务模板三维打标，聚合出"每任务模板平均工具成本"；异常模板通常是：无缓存的重复查询、扇出无上限、失败重试无退避。治理顺序先模板后配额——配额是刹车，模板治理才是省油。

**背诵要点**：
1. 供应商限流保护供应商，账单要自己管：令牌桶排队替代硬撞 429。
2. 预算账按工具×租户打标，80% 告警 / 100% 熔断 / 白名单豁免。
3. 降级阶梯：缓存 → 廉价供应商 → 减扇出 → 人工；重试必须同桶记账。

**复盘追问**：
1. 账单 3 倍超预算，第一步查什么？（按任务模板聚合的调用数分布——通常是某个模板的扇出×重试放大，而不是供应商涨价）
2. 为什么熔断还要留"人工任务白名单"？（熔断是保护预算不是惩罚业务：人工触发的关键任务走豁免通道并单独记账，保证熔断期间核心业务可用、成本可见）
