### Q7573 · 向量索引构建吞吐与增量更新窗口容量账

难度：P6 ｜ 标签：容量规划 / 向量索引 / Embedding / HNSW

**问**：RAG 知识库日增 5 万篇文档，索引构建（embed + 入库）每天要 3 小时，且高峰期构建把向量库打挂导致检索超时。怎么算构建吞吐容量账，安排增量更新窗口？

**答**：

**结论**：容量账三段：① Embedding 吞吐 = API 并发 × 单次延迟（或 GPU 本地推理吞吐 tokens/s），5 万篇 × 平均 2k tokens = 1 亿 tokens/天，API 批量 5000 tokens/请求、10 并发、300ms/请求 → 1.7 亿 tokens/小时，单链路够；瓶颈常不在 embed 而在 ② HNSW 建图：插入是 O(logN) 每条但并发插入会争抢图锁，大批量 insert 打满 CPU 与内存带宽，与在线检索抢资源——这就是"构建打挂检索"的根因。③ 索引膨胀与合并：频繁增量插入导致分段碎片（FAISS 类 segment 合并、PG HNSW 死元组），要预留定期重建窗口。解法：构建流量与检索隔离（独立构建实例/副本，构建完原子切换），增量窗口放低峰，限速（每秒插入条数上限）。

**取舍**：实时插入 vs 批量窗口：实时插入让新文档分钟级可检索（业务有时硬需求），代价是资源争抢与碎片；批量窗口（每小时/每日）吞吐高、资源平稳，但数据新鲜度差。中间态：小的实时通道（热点文档走实时，限速 100 条/秒）+ 大批量窗口兜底，两通道最后由合并任务统一。删除同步是隐藏坑：源文档删除后向量残留会召回过期内容，账里要有 tombstone 与重建频率。

**实战**：账做成表：日增 tokens、embed 吞吐实测（注意限流 429 重试吃掉 20-30% 有效吞吐）、插入限速值、索引大小增长（内存账）、重建周期。Python 侧模拟"构建限速 vs 检索 P99"的资源关系，找出限速阈值。

```python
# 向量索引构建容量账：embed 吞吐 + 限速插入与检索影响模拟
# 仅标准库，Python 3.9+
from __future__ import annotations


def embed_throughput(concurrency: int, latency_s: float,
                     tokens_per_req: int, throttle_factor: float = 0.75) -> float:
    """返回 tokens/小时；throttle_factor 折算 429 重试损耗。"""
    req_per_h = concurrency / latency_s * 3600 * throttle_factor
    return req_per_h * tokens_per_req


def build_window_hours(daily_docs: int, tokens_per_doc: int,
                       throughput_tph: float) -> float:
    return daily_docs * tokens_per_doc / throughput_tph


def search_p99_with_build(base_p99_ms: float, insert_rate: int,
                          interference: float = 0.004) -> float:
    """插入限速对检索 P99 的干扰模型（每条插入的 CPU 争抢近似线性）。"""
    return base_p99_ms * (1 + interference * insert_rate)


def main() -> None:
    tph = embed_throughput(concurrency=10, latency_s=0.3,
                           tokens_per_req=5000)
    print(f"embed 吞吐: {tph/1e6:.1f}M tokens/h")
    h = build_window_hours(50_000, 2_000, tph)
    print(f"日增 5 万篇构建窗口: {h:.1f} h")
    assert h < 2, "构建窗口应在 2h 内"

    # 检索影响：不限速 2000 条/s 时 P99 恶化 9 倍
    p99_free = search_p99_with_build(30, 0)
    p99_bad = search_p99_with_build(30, 2000)
    p99_ok = search_p99_with_build(30, 100)
    print(f"P99: 无构建 {p99_free:.0f}ms / 2000条s {p99_bad:.0f}ms / 限速100条s {p99_ok:.0f}ms")
    assert p99_bad > 200 and p99_ok < 45
    print("结论：低峰窗口 + 插入限速 100 条/s + 构建实例隔离")


if __name__ == "__main__":
    main()
```

**追问链**：

- 追问 1：为什么 HNSW 的增量插入比 ANN 检索更伤资源？——插入要探索图找到邻居并建边，写路径与检索路径同样走贪心搜索，且要加锁更新邻居的出边表；高并发插入时锁竞争 + 内存带宽占满，检索延迟被直接拖累——这是"共享实例构建"必挂的机理。
- 追问 1.1：构建完"原子切换"在 PG/FAISS 两种实现里分别怎么做？——FAISS：构建新 segment/index 后替换指针（或双 index 别名切换）；PG：新表（REINDEX CONCURRENTLY 或新建 HNSW 索引 CONCURRENTLY 建好后 drop 旧的），切换瞬间完成且不锁检索。
- 追问 2：429 重试吃掉 20-30% 有效吞吐，怎么把账算准？——有效吞吐 = 标称吞吐 × 成功率，还要计入退避等待的时长（指数退避下并发空转）；用实测的"每千文档墙钟时间"做账基线，而不是 API 文档的标称 QPS。

**背诵要点**：

1. 构建账三段：embed 吞吐（标称 × 成功率折损 20-30%）+ HNSW 建图资源（与检索同路径抢锁）+ 索引膨胀重建窗口。
2. 构建打挂检索的根因是共享实例资源争抢：独立构建实例 + 原子切换（REINDEX CONCURRENTLY / segment 指针替换）。
3. 插入限速（如 100 条/s）保检索 P99；实时通道限速 + 批量窗口兜底双通道；删除必须有 tombstone 同步。
