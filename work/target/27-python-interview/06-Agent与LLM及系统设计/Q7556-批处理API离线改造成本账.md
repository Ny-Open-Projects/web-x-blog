### Q7556 · 批处理 API 离线任务改造的成本账

难度：P6 | 标签：成本工程、批处理 API、幂等、离线任务

**问**：每月 500M token 的离线文档摘要任务全走在线端点，月账单 3000 美元。供应商的批处理端点（Batch API）便宜一半、SLA 24 小时——哪些任务能搬过去？搬过去之后要补哪些工程件，才不会"省了钱、坏了账"？

**答**：
- **结论**：判定标准只有一条：任务能接受 24 小时内的结果返回就能进批处理，交互路径（用户在等）留在在线端点。搬移后要补三个工程件：① 幂等提交：`custom_id` 用业务主键，重复提交同 id 被去重——批处理的重提交和部分失败重跑极常见，没有幂等键就会双算双写；② 状态机驱动：submitted → in_progress → completed/failed 的轮询推进，failed 带原 custom_id 重提交，形成"提交-轮询-重处理-对账"闭环；③ 对账：产出账本 = 提交数 - 重处理中，每日核对，防"以为成功实际丢了 2%"。本例月成本 3000 → 1500 美元，省 50%。
- **取舍**：批处理的隐性成本是时效耦合：下游依赖摘要结果的流程被拉到 T+1，调度链要重排；失败的等待窗口（轮询 24h 才知道挂了）要求重处理有自动兜底，不能靠人盯。另一个坑是"为了凑折扣把交互任务也塞进批处理"——用户等待 24h 的体验事故比省的钱贵。
- **实战**：落地清单：① 按 SLA 把任务分桶（实时/小时级/天级），只有天级进批处理；② 提交器与轮询器分离，轮询器带断点续查（服务重启不丢作业）；③ 成本账本按"在线/批处理"分列，月度对比节省额与重处理成本（重跑也是钱）。

```python
"""批处理 API 离线任务改造的成本账：半价、SLA 与失败重处理。"""
from dataclasses import dataclass
from enum import Enum

PRICE_ONLINE = 6.0     # $/1M tokens（在线端点）
PRICE_BATCH = 3.0      # 批处理端点通常约半价
MONTHLY_TOKENS = 500   # 500M tokens/月的离线摘要任务

online_cost = MONTHLY_TOKENS * PRICE_ONLINE
batch_cost = MONTHLY_TOKENS * PRICE_BATCH
print(f"在线端点月成本 ${online_cost:,.0f} -> 批处理端点 ${batch_cost:,.0f}"
      f"（省 {(1 - batch_cost / online_cost):.0%}）")

class JobState(Enum):
    SUBMITTED = "submitted"
    IN_PROGRESS = "in_progress"
    COMPLETED = "completed"
    FAILED = "failed"

@dataclass
class BatchJob:
    custom_id: str          # 幂等键：业务主键，重复提交同 id 会被去重
    state: JobState = JobState.SUBMITTED

# 模拟一轮批处理：提交 10 个作业，轮询回 8 完成 2 失败
jobs = [BatchJob(f"doc-{i}") for i in range(10)]
results = [JobState.COMPLETED] * 8 + [JobState.FAILED] * 2
for j, r in zip(jobs, results):
    j.state = r
done = [j for j in jobs if j.state is JobState.COMPLETED]
redo = [j for j in jobs if j.state is JobState.FAILED]
print(f"首轮：完成 {len(done)}，失败 {len(redo)} -> 失败作业带原 custom_id 重提交（幂等，不会双算）")
print(f"完成率核对：产出账本 {len(done)} 条 == 提交 {len(jobs)} - 待重处理 {len(redo)}")
print("改造要点：按时效分级上批处理（24h SLA 可接受的才进）；"
      "custom_id 幂等防重复计费；失败重处理与对账闭环；交互路径仍走在线端点")
```

**追问链**：
1. 追问一层：为什么"custom_id 幂等"在批处理里比在线调用更重要？——在线调用一次一个结果，双发肉眼可见；批处理是异步批量，部分失败重跑时"哪些已经成功"很容易算错，重提交会把已成功的作业再算一遍钱和写一遍库。幂等键让重处理无论触发多少次，效果都只发生一次。
2. 追问二层：怎么决定"哪些任务值得承受 24h SLA"？——看下游消费节奏：摘要喂给周报/知识库索引的是天级消费，白搬；喂给用户"生成中"状态的是实时消费，不搬。判定仪式是画任务依赖图，把"结果新鲜度要求"标在每条边上，天级以上的边才允许进批处理。

**背诵要点**：
1. 批处理判定 = 结果新鲜度要求 > 24h；交互路径永远留在线端点。
2. 三个工程件：custom_id 幂等提交、状态机轮询推进、失败重处理 + 每日对账。
3. 重跑也是钱：成本账按在线/批处理分列，节省额要扣掉重处理成本再看。

**复盘追问**：
1. 批处理上线一个月，财务说只省了 30% 而不是 50%，差在哪？（失败重处理的双算没有幂等键拦截、对账缺失导致重复提交——省下的钱被重跑吃掉，幂等与对账是折扣兑现的前提）
2. 为什么轮询器要和提交器分离？（轮询是长周期、可断点续查的独立进程；耦合在一起时服务重启会丢作业状态，出现"提交了但没人管"的孤儿作业）
