### Q7639 · 推理 GPU 实例扩缩容与预热窗口的容量账

难度：P7 ｜ 标签：容量规划 / 推理服务 / 自动伸缩

**问**：LLM 推理服务用 GPU 实例池 + 自动扩缩容，流量突增时缩容容易扩容难：新实例从拉起到能服务要几分钟（模型加载 + 权重预取 + 预热请求），期间请求全部排队。扩缩容的容量账怎么算：触发器用什么指标、预热窗口怎么补、缩容怎么避免抖动？

**答**：
- **结论**：GPU 推理扩容的致命参数是**就绪延迟**（分钟级，远超无状态服务的秒级），容量账核心公式：`扩容期间积压 = 新增QPS × 就绪延迟`，现有实例必须能吃下这部分积压（通过排队或临时降级），否则触发雪崩。三个设计要点：① **触发器用领先指标**：不用 CPU/GPU 利用率（滞后，GPU 打满时再扩已经晚了），用"排队深度 + P95 TTFT 预算消耗"——队列长度超过 `就绪延迟内可消化量` 就提前扩；② **预热窗口补偿**：按时段预测提前扩容（早高峰前 15 分钟拉实例、加载模型就绪待命），冷启动实例与在线实例用最小副本数兜底；③ **缩容防抖**：缩容阈值要低配滞后（如利用率连续 15 分钟低于 30% 才缩），且每次只缩一个实例、优先缩刚扩的——扩缩抖动的代价（反复冷启动 × GPU 小时费）远高于多留几台的成本。特别地：LLM 推理实例的"容量"不是实例数线性叠加（batching 使单实例吞吐随并发变化），扩容决策应基于实测吞吐曲线（Q7586/Q7613），不是核数线性外推。
- **取舍**：最小副本常驻（保底容量，付 GPU 小时费）vs 纯弹性（省钱但突增必跪）——LLM 推理就绪延迟分钟级，纯弹性基本不可行，最小副本覆盖基线流量是底线；预测式扩容（按历史曲线提前拉）与反应式（队列触发）要组合：预测管"可预期的峰"，反应式管"意外流量"。
- **实战**：① 就绪延迟要演练实测：拉起到第一个成功请求的时间分解（调度/镜像拉取/权重加载/预热），逐段优化（权重用本地 NVMe 或提前预取）；② 健康检查区分"进程活着"与"模型就绪"（Q1111），避免流量打到还在加载权重的实例；③ 缩容前排水：让被缩实例停止接新请求、跑完 in-flight，再释放。

```python
# GPU 推理扩容账: 就绪延迟积压 + 领先指标触发 + 防抖缩容
# 基线: Python 3.9+ 标准库 (数值为演示口径)
from dataclasses import dataclass


@dataclass
class ScaleAccount:
    instances: int
    qps_per_instance: float        # 实测吞吐 (含 batching), 非线性外推
    ready_minutes: float           # 就绪延迟 (拉起到可服务)
    queue_depth: int               # 当前排队请求数
    p95_ttft_ms: float
    ttft_budget_ms: float = 2000

    def backlog_during_scaleup(self, extra_qps: float) -> int:
        """扩容期间新增流量 x 就绪延迟 = 必须由存量实例吃下的积压。"""
        return int(extra_qps * self.ready_minutes * 60)

    def scale_trigger(self) -> str:
        if self.p95_ttft_ms > self.ttft_budget_ms * 0.8 \
                or self.queue_depth > self.instances * 10:
            return "SCALE-OUT: 领先指标(TTFT预算/队列深度)越限"
        return "hold"


def main() -> None:
    acct = ScaleAccount(instances=4, qps_per_instance=10, ready_minutes=4,
                        queue_depth=80, p95_ttft_ms=1800)
    assert acct.scale_trigger().startswith("SCALE-OUT")   # TTFT 1800 > 80% 预算
    backlog = acct.backlog_during_scaleup(extra_qps=5)
    assert backlog == 5 * 4 * 60                    # 1200 请求积压
    # 存量 4 实例容量 40 < 需求 45: 扩容前必须限流/降级兜住积压
    assert 4 * 10 < 45
    assert backlog <= 1200
    # 防抖缩容: 利用率 <30% 连续 15 分钟才缩, 且一次一台
    low_util_minutes = 14
    assert low_util_minutes < 15                    # 尚不满足 -> hold
    print(f"扩容期间积压 {backlog} 请求, 就绪延迟 {acct.ready_minutes} 分钟")
    print("OK: 触发用 TTFT/队列领先指标; 最小副本兜基线; 缩容 15min+单台排水")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 GPU 利用率不适合做扩容触发器？
→ 一句话提示：利用率是滞后指标——GPU 打满时新流量已经在排队，而扩容就绪要几分钟，等实例到位队列已积压成灾；要扩在"TTFT 预算消耗/队列深度"这些领先指标上。

**追问 2**：就绪延迟的几分钟里哪些环节可优化？
→ 一句话提示：镜像拉取（预拉/小镜像）、权重加载（本地 NVMe/预取/共享内存）、预热请求（就绪探针里做）、调度排队（keep-warm 常驻）；加载权重通常是最大头，vLLM 等引擎的启动优化和模型分层加载都能砍。

## 背诵要点
- 核心公式：扩容期间积压 = 新增QPS × 就绪延迟（分钟级），存量实例必须兜住，兜不住就先限流/降级。
- 触发器用领先指标（P95 TTFT 预算消耗 80% / 队列深度），不用滞后的 GPU 利用率；最小副本常驻兜基线 + 预测式提前扩容。
- 缩容防抖：利用率 <30% 连续 15 分钟才缩、一次一台、排水后再释放；实例吞吐按实测曲线（batching）不是线性外推。

## 复盘追问
- 为什么"最小副本"对 LLM 推理比普通 Web 服务更刚性？提示：就绪延迟分钟级 vs 秒级，纯弹性的爬坡期积压不可承受；最小副本成本 = 基线流量的 GPU 时费，是买"可服务性"的钱。
- 扩容后如何确认新实例真的接得住流量？提示：就绪探针含预热请求 + 灰度放量（先切小比例流量观测 TTFT），避免一次性把队列倒给未热身实例。
