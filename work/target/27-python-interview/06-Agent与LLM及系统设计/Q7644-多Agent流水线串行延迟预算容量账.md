### Q7644 · 多 Agent 流水线串行延迟的预算容量账

难度：P6 ｜ 标签：容量规划 / 多 Agent / 延迟

**问**：一条"规划 → 检索 → 生成 → 校验"的四段 Agent 流水线，每段都是一次 LLM 调用，端到端 P95 冲到 30 秒，用户流失。串行流水线的延迟账怎么算：预算怎么分配到各段、哪些段能并行/合并、重试和降级怎么不把 P95 推爆？

**答**：
- **结论**：串行流水线延迟 = **各段延迟之和**，且 P95 不是各段 P95 相加那么简单——正确口径是各段 P95 相加（保守上界，因为段间失败相关性低时实际略低，但按相加做预算是安全实践）。延迟账三步：① **总预算倒推**：产品给定端到端 P95 ≤ 8 秒，倒推每段预算（如 2/1/3/1.5 秒 + 重试余量），预算写进各段的超时配置——没有分段预算的流水线，单段抖动就吃光全局；② **结构优化优先于参数优化**：能并行的段并行（检索的多路召回 Q7564）、能合并的段合并（校验并进生成的结构化输出约束 Q7517，省一次完整调用）、能砍的段砍掉（规划在简单请求上用规则替代）；③ **重试/降级的延迟税**：每段重试 = 段延迟 × (1 + 重试率 × 重试倍数)，P95 预算必须预留重试空间，否则"99% 成功率的段落"在 P95 维度因为尾部重试直接超预算——低延迟段（校验）重试用小模型/缓存，高延迟段（生成）失败直接降级不重试。与容量联动：吞吐 = 并发数 / 端到端延迟，延迟翻倍意味着同样并发下吞吐减半——延迟预算同时是容量预算（Q7544 的并发账在这里接上）。
- **取舍**：串行改并行的代价是**上下文依赖**：后段需要前段结果时无法并行，只能做"推测执行"（speculative：并行跑可能分支、取回后再选）——省延迟但浪费 token（成本账 Q7576 要并）。合并段省一次调用的往返与重复前缀（prompt 缓存友好），代价是单提示词变复杂、可控性下降。
- **实战**：① 每段埋 trace（span 起止），延迟账从真实 trace 聚合而非压测估计；② 分段超时用"预算倒推"配置，段超时触发降级而不是无限等；③ 把"各段延迟占比"做成周报，占比漂移（某段悄悄变慢）比绝对值更早暴露回归。

```python
# 多段流水线延迟预算: P95 相加口径 + 预算倒推 + 重试延迟税
# 基线: Python 3.9+ 标准库 (数值为演示口径)
from dataclasses import dataclass


@dataclass
class Stage:
    name: str
    p95_ms: float
    retry_rate: float = 0.0
    retry_cost_ratio: float = 1.0    # 重试一次的成本倍数(同模型=1, 小模型=0.2)

    def effective_p95(self) -> float:
        """重试延迟税: p95 x (1 + retry_rate x retry_cost_ratio)。"""
        return self.p95_ms * (1 + self.retry_rate * self.retry_cost_ratio)


def budget_check(stages: list[Stage], total_budget_ms: float) -> tuple[bool, dict]:
    e2e = sum(s.effective_p95() for s in stages)
    detail = {s.name: s.effective_p95() for s in stages}
    return e2e <= total_budget_ms, detail


def main() -> None:
    stages = [
        Stage("plan", 1500),
        Stage("retrieve", 800, retry_rate=0.10, retry_cost_ratio=0.2),  # 降级重试
        Stage("generate", 3800, retry_rate=0.05, retry_cost_ratio=1.0),
        Stage("verify", 600, retry_rate=0.15, retry_cost_ratio=0.2),
    ]
    ok, detail = budget_check(stages, total_budget_ms=8000)
    # plan1500 + retrieve816 + gen3990 + verify618 = 6924 <= 8000
    assert ok, detail
    e2e = sum(detail.values())
    assert 6900 < e2e < 6950, e2e
    # 若生成段用同模型重试 40%: gen p95 = 3800*1.4 = 5320, 总账超 8000
    heavy = [Stage("plan", 1500), Stage("retrieve", 800, 0.1, 0.2),
             Stage("generate", 3800, 0.40, 1.0), Stage("verify", 600, 0.15, 0.2)]
    ok2, _ = budget_check(heavy, 8000)
    assert not ok2                       # 高成本重试推爆 P95
    print(f"预算内 e2e={e2e:.0f}ms; 生成段重试20%时超预算 -> 生成段降级不重试")
    print("OK: P95 按段相加 + 重试延迟税进账; 预算倒推到分段超时配置")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么端到端 P95 按各段 P95 相加是保守但安全的口径？
→ 一句话提示：真实 P95 略低于和（各段尾部不总同时发生），但流水线各段有因果顺序、尾部还可能级联（前段慢导致后段超时重试），按相加做预算不会系统性低估；省下来的余量当安全垫。

**追问 2**：推测执行（并行跑分支再选）什么时候值得？
→ 一句话提示：分支选择结果延后才揭晓且各分支成功率高时值得（省等待）；token 成本翻倍，只有当"延迟价值 > token 成本"（如实时对话）才用，批处理任务永远串行省钱。

## 背诵要点
- 串行流水线 P95 = 各段 P95 之和（保守安全口径）；预算从产品总预算倒推到分段超时配置，无分段预算 = 单段抖动吃光全局。
- 重试延迟税 = p95 × (1 + 重试率 × 成本倍数)：低延迟段降级重试（小模型/缓存），高延迟段（生成）直接降级不重试。
- 延迟预算即容量预算（吞吐 = 并发/延迟）；结构优化（并行/合并/砍段）优先于参数调优。

## 复盘追问
- "各段延迟占比周报"如何发现回归？提示：占比相对基线漂移 > 10% 告警——绝对值受流量影响大，占比直接暴露"哪一段悄悄变慢"（如上游检索库索引劣化）。
- 校验段合并进生成（结构化输出约束）省一次调用，什么情况下不能合并？提示：校验逻辑本身需要独立上下文/外部工具（如查事实库）或需要独立供应商（防止生成与校验同源共谋错误）时必须分离。
