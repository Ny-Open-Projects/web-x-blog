### Q7720 · 向量库软删除：删了 40%，为什么只召回 6 条

难度：P7 ｜ 标签：向量库、软删除、tombstone、HNSW

基线：Python 3.12；pgvector / Milvus / Qdrant 的 delete 语义；纯 Python 模拟墓碑过滤。

**问**：知识库每天增量更新，旧文档会被删除再插入新版本。运营发现同样 `top_k=10` 的查询，最近经常只返回 6-7 条，且偶尔召回已删除的旧内容。监控显示向量总数没降，`count` 还是删之前的量。删除到底删了什么？为什么 top_k 会不足？

**答**：
- **结论**：主流向量索引（HNSW/IVF）为了性能，`delete` 通常是**标记删除（tombstone）**：把 id 记入删除位图，图结构不立即断开，物理空间也不回收。查询时 ANN 先在**包含墓碑的全量候选**里取 top_k，再按位图过滤，于是有效结果 = top_k − 命中墓碑数，删得越多、缺口越大；如果过滤放在 ANN 之前反而会破坏图的连通性，所以多数实现选择"先召回后过滤"。
- **取舍**：软删除让写入/删除都快，但带来三个账：① **召回缺口**（top_k 不足）；② **空间不回收**（磁盘/内存按历史量增长）；③ **召回质量下降**（墓碑占据候选位，图邻居被无效点占据）。硬删除/重建能彻底回收，但要全量重扫、构建索引，期间查询性能与一致性都受影响。折中是后台 compaction + over-fetch。
- **实战**：① 查询侧按删除比例放大 `top_k`（如 `k / (1 - delete_ratio)`）再截断；② 监控墓碑比例，超过阈值（如 20-30%）触发 compaction/重建；③ 删除后若要"立即不可见"，在应用层加一层 id 白名单/版本过滤，别只依赖索引；④ 用 `count` 校验数据量时要区分"物理条数"与"有效条数"。

```python
"""模拟墓碑删除：ANN 先取 top_k，再过滤已删除，导致召回缺口。"""
from dataclasses import dataclass


@dataclass
class Node:
    doc_id: str
    vector: float          # 一维示意：越接近 query 越相似
    deleted: bool = False


class TombstoneIndex:
    def __init__(self, nodes: list[Node]) -> None:
        self.nodes = nodes

    def search(self, query: float, k: int, over_fetch: float = 1.0) -> list[str]:
        # 1) ANN 在全量（含墓碑）里取候选
        candidates = sorted(self.nodes, key=lambda n: abs(n.vector - query))
        candidates = candidates[:max(k, int(k * over_fetch))]
        # 2) 过滤墓碑
        return [n.doc_id for n in candidates if not n.deleted][:k]

    @property
    def physical(self) -> int:
        return len(self.nodes)

    @property
    def alive(self) -> int:
        return sum(1 for n in self.nodes if not n.deleted)

    @property
    def tombstone_ratio(self) -> float:
        return 1 - self.alive / self.physical


if __name__ == "__main__":
    nodes = [Node(f"doc{i}", float(i)) for i in range(100)]
    for i in range(0, 100, 2):          # 删掉一半
        nodes[i].deleted = True
    idx = TombstoneIndex(nodes)
    print(f"物理={idx.physical} 有效={idx.alive} 墓碑比例={idx.tombstone_ratio:.0%}")

    plain = idx.search(query=50.0, k=10)
    print("直接 top10:", len(plain), plain)
    print("count 查询:", idx.physical, "-> 和有效数不一致")

    fixed = idx.search(query=50.0, k=10, over_fetch=1 / (1 - idx.tombstone_ratio))
    print("按比例放大候选:", len(fixed), fixed)
    print("结论：软删除导致召回缺口；over-fetch 只能缓解，回收要靠 compaction")
```

**追问一**：为什么向量库不采用"删除时立即从 HNSW 图里摘点"？
→ 解析：HNSW 的邻居关系是双向的，摘掉一个点要修复它所有邻居的边、可能破坏连通性，还要处理并发查询看到的图版本；成本远高于标记。批量删除更会引发大量图重连，导致写放大与查询抖动。所以工程上选择"删除快、查询时过滤、后台重建"。

**追问二**：墓碑比例高时，除了召回缺口还有什么隐患？
→ 解析：① 无效点占据图的邻居槽位，有效点的可达性变差，召回率下降；② 内存/磁盘按物理量计费，成本虚高；③ 过滤后重排可能让"次优但有效"的点挤掉真正相近的点；④ 删除位图本身也占内存。要在比例阈值触发 compaction，并监控"召回条数分布"而不只是平均延迟。
