### Q7742 · 并行工具调用里混了写操作：两次「查库存再扣减」同时读到 10

难度：P7 ｜ 标签：Agent、并行工具调用、副作用、丢失更新

基线：Python 3.12；用"读—改—写"窗口模拟并行 tool_calls 的交错执行。

**问**：Agent 支持并行工具调用（`parallel_tool_calls=true`），模型一次返回两个 `reserve_stock(sku, 1)`，代码用 `asyncio.gather` 并发执行。压测时库存 10，两个并发扣减后变成 **9** 而不是 8；更奇怪的是有时变成 -1。单个工具内部是"先 `SELECT` 再 `UPDATE`"。问题出在工具实现还是并行调度？

**答**：
- **结论**：两者都有，但**根因是把有副作用的工具并行化**。工具内部是典型的"读—改—写"（读 10 → 减 1 → 写 9），两个调用并发时都读到 10，都写 9，其中一次扣减被覆盖（丢失更新）；如果中间还夹着别的请求把库存扣到 0，就会写出 -1。并行调用本身没问题——问题在于"模型可以自由决定并行什么"，而调度层没有按**副作用**做隔离。
- **取舍**：三种策略：① **按工具分类**：标了 `read_only` 的并行，标了 `side_effect`/`write` 的串行（或按资源键串行，同一 `sku` 排队）；② 在工具内部做原子扣减（`UPDATE ... SET stock = stock - 1 WHERE stock >= 1`，靠数据库行锁/条件更新），让"并行"也安全——这是治本，但要求每个写工具都幂等且原子；③ 给写操作加幂等键（`tool_call_id` 作为去重键），并行重复执行也只生效一次。
- **实战**：① 工具注册表里显式声明 `read_only` / `idempotent` / `resource_key`，调度器据此分组：同 `resource_key` 串行、不同资源并行；② 提示词里也说明"写操作不要并行"，但这只是软约束，不能作为正确性保证；③ 压测必须覆盖"模型返回多个写调用"的场景，单调用测试永远发现不了；④ 监控"库存为负/重复扣减"业务指标，比看 QPS 更早暴露。

```python
"""并行扣减的丢失更新：两个 reserve 都基于同一份读到 10 的库存。"""
from dataclasses import dataclass, field


@dataclass
class Stock:
    value: int
    log: list[str] = field(default_factory=list)

    def read(self) -> int:
        self.log.append(f"read -> {self.value}")
        return self.value

    def commit(self, new_value: int) -> None:
        self.value = new_value
        self.log.append(f"write -> {self.value}")


def reserve_parallel(stock: Stock, times: int = 2) -> int:
    """两个调用并发：先都读，再都写（典型的丢失更新）。"""
    seen = [stock.read() for _ in range(times)]     # 阶段一：并发读
    for v in seen:                                  # 阶段二：各自写回
        stock.commit(v - 1)
    return stock.value


def reserve_sequential(stock: Stock, times: int = 2) -> int:
    for _ in range(times):
        v = stock.read()
        stock.commit(v - 1)
    return stock.value


def reserve_atomic(stock: Stock, times: int = 2) -> int:
    """条件更新：DB 侧 `WHERE stock >= 1` 的原子扣减，并行也安全。"""
    for _ in range(times):
        if stock.value >= 1:
            stock.commit(stock.value - 1)
    return stock.value


if __name__ == "__main__":
    s1 = Stock(10)
    print("并行两次 reserve ->", reserve_parallel(s1))
    print("  轨迹:", s1.log)

    s2 = Stock(10)
    print("\n串行两次 reserve ->", reserve_sequential(s2))
    print("  轨迹:", s2.log)

    s3 = Stock(10)
    print("\n原子条件更新 ->", reserve_atomic(s3))

    # 工具注册表：调度器据此决定并行/串行
    TOOLS = {
        "get_order": {"read_only": True, "resource_key": None},
        "reserve_stock": {"read_only": False, "idempotent": True, "resource_key": "sku"},
        "send_sms": {"read_only": False, "idempotent": False, "resource_key": "phone"},
    }
    def plan(calls: list[str]) -> list[list[str]]:
        parallel = [c for c in calls if TOOLS[c]["read_only"]]
        serial = [c for c in calls if not TOOLS[c]["read_only"]]
        return [parallel] + [[c] for c in serial]

    print("\n调度计划（只读并行、写串行）:", plan(["get_order", "reserve_stock", "send_sms"]))
    print("结论：并行的是「读」，不是「调用」；写操作要么串行，要么原子+幂等")
```

**追问一**：工具内部写成 `UPDATE stock SET n = n - 1 WHERE sku = ? AND n >= 1` 就够了吗？

→ 解析：这条语句解决了"丢失更新"（数据库行锁保证串行化），但没解决"**重复执行**"：并行/重试可能让同一个 `tool_call_id` 被执行两次，库存扣两次。所以还需要幂等：把 `tool_call_id` 或业务幂等键写进一张去重表，或让扣减带业务单号唯一约束（`INSERT INTO stock_log(order_id, sku) ...` 冲突即视为已扣）。原子性 + 幂等性是两个正交的问题，缺一个都会在重试/并行下出错。

**追问二**：为什么提示词里写"写操作请串行调用"不能作为解决方案？

→ 解析：模型是概率系统，指令遵循不是契约；温度、上下文长度、供应商版本都会影响它是否遵守。把正确性建立在"模型会听话"上，等于把资金/库存的一致性交给采样。提示词只能用于**降低成本**（减少并行写调用），真正的边界必须在调度层（按 `read_only`/`resource_key` 分组）与存储层（原子 + 幂等）实现。面试里这点要主动说清：软约束与硬约束的分工。
