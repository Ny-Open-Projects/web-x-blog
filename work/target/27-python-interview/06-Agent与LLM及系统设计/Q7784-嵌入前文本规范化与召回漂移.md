### Q7784 · 全半角都能搜到才有鬼：嵌入前的文本规范化与召回漂移

难度：P6 ｜ 标签：文本规范化、全半角、繁简、Unicode NFKC、召回一致性

基线：Python 3.12；用字符相似度模拟嵌入的"表面形式敏感"，复现全半角/繁简/空白不一致导致的召回漂移与索引-查询规范化不对称事故，实现规范化管线与双向一致性断言，全标准库实跑。

**问**：用户搜"ＩＤ证"搜不到含"ID证"的文档——全角字母让向量变了。嵌入前的文本规范化该做哪些（NFKC、繁简、空白、大小写）？为什么"索引时规范化了、查询时没规范化"是致命的不对称？规范化会不会伤语义（比如把有意义的差异抹掉）？

**答**：
- **结论**：嵌入模型对表面形式敏感度不一，但工程上不能赌模型："全角ID/半角ＩＤ""简体认证/繁体認證""多空格/单空格"这些**人类视为等价**的变体，嵌入向量可能差出有效召回距离。规范化的最小管线：① **Unicode NFKC**（兼容分解）：全角字母/数字 → 半角、全角标点归一、连字符号统一——这是覆盖面最大的一刀，`unicodedata.normalize("NFKC", s)`；② **繁简归一**：用映射表或 opencc 类工具统一到简体（面向中文库），繁简同义词的向量差异在中英混排文档上显著；③ **空白归一**：连续空白合并、行尾清零（Q491 Unicode 规范化的同族纪律）；④ **大小写**：英文全小写（品牌名/代码标识符场景要豁免白名单）。**致命的不对称**：索引侧与查询侧的规范化必须是同一函数同一版本——索引时做了 NFKC 查询时没做（或反过来），向量空间直接错位，表现为"明明有这文档就是搜不到"且无报错。规范化的语义风险确实存在：NFKC 会把 `Ⅰ`（罗马数字）折成 `I`、把全角空格折成半角——法条编号、代码片段、密码学文本这些"形式即语义"的内容要走**豁免通道**（按字段配置跳过规范化），规范化策略是字段级配置而不是全局开关。
- **取舍**：① 规范化的位置：入库前规范化（存储层存规范形）vs 检索时双向规范化（原文存储、索引与查询各自归一后嵌入）——前者省一层但丢失原文展示形态（引用回原文需要原文，Q2036 引用定位同族），后者双份维护；主流是**原文存储 + 索引侧归一嵌入 + 查询侧同函数归一**；② 重建成本：规范化策略变更 = 全库重嵌入（Q7684 迁移账的轻量版），策略变更要像 schema 变更一样评审——上线前跑"规范化前后召回对比集"确认收益为正；③ 过度规范化的反噬：全部小写会让 "Apple公司" 与 "apple 水果" 更相似（歧义放大），NER 密集场景大小写是信号，豁免或降级处理；④ 规范化管线的可观测性：每个变更步骤（NFKC/繁简/空白）命中率的统计进埋点——命中率突变说明流量形态变了（新市场、新输入法），是规范化规则要更新的信号。
- **实战**：① 双向一致性断言进 CI：`normalize(index_text) == normalize(query_text)` 的黄金对（全角/繁简/多空格三组变体对）做单测，规范化函数改动必须全绿；② 评测集带变体对：检索评测集里显式加"同义变体对"（全角查询 vs 半角文档），规范化缺失的回归直接在评测分数上现形（Q1199 命中率评估的变体维度）；③ 修复存量索引：规范化升级后旧索引是"未规范化的嵌入"，与新查询向量错位——必须全量重嵌入，灰度用双索引对比（Q7620 双索引重建账）；④ 输入侧兜底：用户输入的不可见字符（零宽字符、BOM）在规范化管线里显式剥离（Q492 BOM 同族），避免攻击性的"隐形字符污染检索"。

```python
"""Q7784 嵌入前规范化: NFKC/繁简/空白 + 索引-查询不对称事故复现。"""
import unicodedata

S2T_MAP = {"证": "證", "认": "認", "单": "單", "银": "銀", "账": "賬"}


def normalize_v1(s: str) -> str:
    """规范化 v1: 仅空白归一(没做 NFKC/繁简) -> 变体漂移."""
    return " ".join(s.split())


def normalize_v2(s: str) -> str:
    """规范化 v2: NFKC + 繁简映射 + 空白归一."""
    s = unicodedata.normalize("NFKC", s)       # 全角->半角等兼容分解
    s = "".join(S2T_MAP.get(ch, ch) for ch in s)  # 简体库场景统一到简体
    return " ".join(s.split())


def fake_embed(s: str) -> tuple:
    """模拟嵌入对表面形式敏感: 字符集合即向量(演示用)."""
    return tuple(sorted(set(s)))


def recall(index_doc: str, query: str, norm) -> bool:
    return fake_embed(norm(index_doc)) == fake_embed(norm(query))


if __name__ == "__main__":
    doc = "ID认证"          # 索引侧文档(半角/简体)
    q_full = "ＩＤ認證"      # 查询: 全角+繁体变体
    print(f"v1(只归空白): 查询 {q_full!r} -> 命中 {recall(doc, q_full, normalize_v1)}"
          f"   <- 全角+繁体让向量错位, 召回失败")
    print(f"v2(NFKC+繁简): 查询 {q_full!r} -> 命中 {recall(doc, q_full, normalize_v2)}")
    # 不对称事故: 索引用了 v2, 查询用了 v1
    asym = fake_embed(normalize_v2(doc)) == fake_embed(normalize_v1(q_full))
    print(f"不对称(索引v2/查询v1): {asym}  <- 规范化版本不一致同样错位")
    # 语义豁免: 罗马数字不该被 NFKC 折叠
    roman = unicodedata.normalize("NFKC", "第Ⅰ章")
    print(f"语义风险: NFKC 把 第Ⅰ章 -> {roman!r} (形式即语义场景需豁免)")
    ok = (not recall(doc, q_full, normalize_v1)
          and recall(doc, q_full, normalize_v2)
          and not asym and roman == "第I章")
    print(f"校验: 变体漂移复现 + 规范化修复 + 不对称实锤 + 豁免认知 -> {'通过' if ok else '异常'}")
    print("结论：嵌入不保证等价变体等向量; 规范化四件套 NFKC/繁简/空白/大小写;")
    print("      索引与查询必须同一函数同一版本, 形式即语义的字段走豁免")
```

**追问一**：规范化策略上线后发现"某些查询的召回反而变差了"，怎么归因？规范化与嵌入模型各自承担什么？

→ 解析：归因三步：① **定位变差的方向**——规范化改的是"变体合并"（把不同表面形式拉到同一向量），它同时合并了"真等价变体"（收益）与"伪等价差异"（损失：`Ⅰ章` vs `I章`、`Apple` vs `apple` 的语义距离被抹掉）；把变差 case 分拣成两类：该命中的没命中（规范化把查询与文档拉远了，罕见但存在——大小写敏感场景）与不该命中的命中了（伪等价合并，污染 top-k 挤掉真答案）。② **分清职责边界**：嵌入模型本该学到的语义等价（繁简、同义词）不该由规范化承担——规范化只负责"确定性的字符变换"（NFKC 类机械映射）；语义级等价靠模型或同义词扩展（Q2039 同义词对拍），规范化兜语义是越俎代庖且伤精度。③ **字段级修正**：把变差 case 对应的字段（如法条编号、产品型号）加进豁免白名单，重新评估——规范化策略最终形态是"全局管线 + 字段豁免表 + 变体评测集守护"的三件套，评测集里同时有"必须命中"与"必须不命中"的对照组，策略任何变更双向跑。底层认知：**规范化是信息有损变换，每一刀都要问"这个差异对检索是噪音还是信号"——噪音砍掉，信号保留，答案永远在评测集里不在直觉里。**

**追问二**：多语言语料库（中英日混排）的规范化策略有什么额外冲突？语言检测在管线里怎么用？

→ 解析：多语场景的冲突点：① **大小写策略分语言**：英文小写化收益大，德语名词大写有意义、日语无大小写——全局 lowercase 会伤德语；策略要按语言分支。② **NFKC 的日文陷阱**：NFKC 会把日文的一些"全角片假名/半角片假名"合并——半角片假名在日文语境是特定历史用法（旧系统、银行账单），机械折叠可能丢失检索信号，日文字段常配置跳过或自定义映射。③ **繁简映射的方向冲突**：简→繁与繁→简不是双射（一简对多繁：'发'→'發/髮'），面向哪个市场定向映射，跨市场检索需要双索引或双向映射表——映射表本身的维护是成本。④ **语言检测的位置**：在规范化管线的入口检测语言（按字符集启发式或 fasttext 类分类器），路由到语言专属分支（不同的大小写/繁简/分词策略，Q7739 分词同族）；检测错误的代价是"用错分支"——中英混排句子的语言检测粒度要降到**片段级**（按 Unicode 块切分连续同语言片段分别归一），整句单标签在混排场景必错。⑤ **评测集分语言加权**：多语评测集按语种分层采样（Q7779 分层采样思想），规范化策略变更的影响按语种分别报告——整体指标掩盖单语退化。多语规范化的总原则：**不存在全局统一策略，只有"语言路由 + 每语言策略表 + 分语种评测"的组合；混排文本一律片段级处理。**
