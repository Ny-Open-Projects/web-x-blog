### Q7614 · 多轮工具调用（Agent 循环）的上下文重复计费成本账

难度：P6 ｜ 标签：成本工程 / Agent / token 计费

**问**：一个 ReAct 风格 Agent 平均一次任务要调 6 轮工具。财务月账单显示该 Agent 的 token 费用是"单轮成本 × 6"的 3 倍。多轮调用的钱到底怎么膨胀的？成本模型怎么建、怎么压？

**答**：
- **结论**：膨胀机制是**每轮都重发全量上下文**：第 k 轮的消息 = 系统提示 + 任务描述 + 前 k-1 轮全部工具结果 + 增量。若系统提示 2k token、工具结果平均 1.5k token，第 6 轮输入 ≈ 2k + 5×1.5k ≈ 9.5k，总输入 = Σk = 2k×6 + 1.5k×(1+2+…+5) ≈ 12k + 22.5k ≈ 35k token——是"单轮 3.5k × 6 = 21k"直觉的近 2 倍，**随轮数平方增长**（输出则线性）。再叠加：工具结果不裁剪（HTML/日志全量进上下文）、prompt 缓存未命中（系统提示每轮全额计费）、以及失败重试也重发全量。成本模型必须按"轮数分布 × 每轮上下文构成"算，而不是按调用次数。
- **取舍**：压缩手段按 ROI 排序：① **裁剪工具结果**：只把工具输出的关键结构（JSON 字段/前 N 行 + 摘要）回填上下文，原文落日志（见 Q7575，通常是最大单项，省 50%+）；② **利用 prompt 缓存**：把稳定前缀（系统提示 + 工具 schema）固定在最前，缓存命中后按 1/10 价格计费（Q7574），多轮场景命中率天然高，省钱且降延迟；③ **减轮数**：并行工具调用一次取多个结果、把多步规则合并进 schema 约束的输出，轮数从 6 → 3 直接砍平方项；④ **上下文窗口管理**：超长历史用滚动摘要（Q7514），近 N 轮全量、远期摘要；⑤ 分层模型：中间轮次用 mini 模型做工具参数规划，最终答案轮用大模型（Q7546 分级差价）。
- **实战**：建模步骤：① 从 trace 抽样统计轮数分布（P50/P95）与每轮输入 token 构成（系统提示/工具结果/历史）；② 算真实成本公式：`Σ_k [base_prompt + Σ_i tool_result_i] × 价格`，与账单对齐；③ 按上述 ROI 清单逐项改造并对拍输出质量（省 token 不能降任务成功率，要跑回归评测）；④ 建立单位经济账：每次任务成本、每成功任务成本（含失败重试），设毛利护栏（Q7547）；⑤ 复盘项：轮数 P95 与 token/任务作为成本 SLA 指标进看板，轮数异常上涨往往是工具失败的先行信号。

```python
# 多轮 Agent 成本模型与压缩收益测算（标准库模拟）
# 基线：Python 3.9+；真实数据来自 Agent trace

from dataclasses import dataclass


PRICE_IN_PER_1K = 0.003      # ¥/1k input tokens（示例口径）
PRICE_OUT_PER_1K = 0.012
CACHE_HIT_RATIO = 0.10       # 缓存命中部分按 1/10 计价


@dataclass
class AgentRun:
    base_prompt_tokens: int          # 系统提示+任务+工具 schema（稳定前缀）
    tool_result_tokens: int          # 单次工具结果
    avg_turns: int
    output_tokens_per_turn: int = 120


def naive_cost(r: AgentRun) -> float:
    """直觉口径：单轮成本 × 轮数（错误）"""
    single_in = r.base_prompt_tokens + r.tool_result_tokens
    single = single_in / 1000 * PRICE_IN_PER_1K + r.output_tokens_per_turn / 1000 * PRICE_OUT_PER_1K
    return single * r.avg_turns


def real_cost(r: AgentRun, *, cache: bool = False, trim: float = 0.0) -> float:
    """真实口径：第 k 轮输入 = base + (k-1)×工具结果，平方增长"""
    total_in = 0
    total_cache = 0
    for k in range(1, r.avg_turns + 1):
        ctx = r.base_prompt_tokens + (k - 1) * r.tool_result_tokens * (1 - trim)
        total_in += ctx
        if cache:
            total_cache += min(r.base_prompt_tokens, ctx)   # 稳定前缀可命中缓存
    out = r.avg_turns * r.output_tokens_per_turn
    billable_in = total_in - total_cache + total_cache * CACHE_HIT_RATIO
    return billable_in / 1000 * PRICE_IN_PER_1K + out / 1000 * PRICE_OUT_PER_1K


def main() -> None:
    run = AgentRun(base_prompt_tokens=2000, tool_result_tokens=1500, avg_turns=6)
    naive, real = naive_cost(run), real_cost(run)
    print(f"直觉成本 ¥{naive:.4f} vs 真实 ¥{real:.4f}（平方膨胀 {real / naive:.1f}×）")
    assert real > naive * 1.5, "多轮重发全量上下文必然平方膨胀"

    c1 = real_cost(run, trim=0.7)
    c2 = real_cost(run, trim=0.7, cache=True)
    print(f"裁剪工具结果 70%: ¥{c1:.4f}（省 {(1 - c1 / real) * 100:.0f}%）")
    print(f"+ prompt 缓存:     ¥{c2:.4f}（累计省 {(1 - c2 / real) * 100:.0f}%）")
    assert c1 < real * 0.6 and c2 < real * 0.45
    # 减轮数：6→3 的平方项收益
    half = real_cost(AgentRun(2000, 1500, 3), trim=0.7, cache=True)
    print(f"轮数 6→3:          ¥{half:.4f}（累计省 {(1 - half / real) * 100:.0f}%）")
    print("OK: 成本按轮数分布×上下文构成建模；裁剪→缓存→减轮数三连降")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"裁剪工具结果"要先设计结构化返回而不是事后截断？
→ 一句话提示：事后截断（前 N 字符）会把 JSON 截成非法态、丢关键字段；结构化返回让工具层自己声明"回填上下文的视图 + 完整落盘的原文"，Agent 需要细节时用 ID 再取——这是信息分层而不是简单裁剪。

**追问 2**：prompt 缓存的命中条件与失效陷阱？
→ 一句话提示：前缀逐字节一致才命中（时间戳/随机 ID/动态计数混进前缀即全灭，见 Q7580）；缓存按前缀分块计价，稳定性 > 长度；工具 schema 列表也要保持顺序稳定。

## 背诵要点
- 多轮成本随轮数平方增长：第 k 轮输入 = 稳定前缀 + (k-1)×工具结果；按"轮数分布 × 构成"建模，调用次数口径严重低估。
- 降本三连按 ROI：裁剪工具结果（结构化视图，省 50%+）→ prompt 缓存（稳定前缀，1/10 计价）→ 减轮数（并行调用/合并规则，砍平方项）。
- 成本 SLA 指标：token/任务、轮数 P95、每成功任务成本；轮数异常上涨是工具失败的先行信号。

## 复盘追问
- 怎么验证"省 token"没有伤任务成功率？提示：改造前后跑同一回归评测集（含难度分桶），成本降 40% 但成功率掉 2% 以内才可通过；困难样本单独看，摘要/裁剪对它们的影响最敏感。
- 失败重试对成本模型的额外影响怎么计入？提示：按重试率加权——有效成本 = 任务成本 × (1 + 重试率 × 重复轮数)，重试还重发全量上下文，所以失败率高的 Agent 成本是非线性恶化的，要先治失败再谈优化。
