### Q7795 · 约束解码的失败面：截断、类型、枚举越界与修复回路

难度：P7 ｜ 标签：Agent、结构化输出、JSON schema、约束解码、失败分类、修复重试

基线：库知识库外知识卡，代码用标准库模拟——手写 schema 校验器 + 语法层修复，`json` 的 `object_pairs_hook` 检测重复键，不调用外部 API。

**问**：工具调用要求输出 `{"action": "buy|sell|hold", "qty": int}`，开了 JSON schema 约束解码后仍有 3% 的调用失败：有的是输出被 max_tokens 截断，有的是 `qty` 给了字符串，有的是 `action` 给了 `"purchase"`，还有的多带了一个 `note` 字段。约束解码不是保证合法吗，为什么还会失败？这些失败面该怎么分类、哪些能自动修、修复回路什么时候该放弃？

**答**：

- **结论**：约束解码（grammar/JSON schema 约束）保证的是**采样过程符合语法**，不等于**语义符合 schema**，也不保证**生成能结束**。失败面至少五类：① **截断**——撞到 `max_tokens` 或 stop 序列，JSON 语法不完整（`{"qty":` 结尾）；② **类型错误**——语法合法但 `"qty": "ten"`，约束只约束 token 的语法形态，未必约束值的类型；③ **枚举越界**——`"action": "purchase"`，模型输出了 schema 之外的字符串，宽松约束会放行；④ **多余字段**——`additionalProperties` 没开或模型忽略，多出 `note`；⑤ **重复键**——`{"action":"buy","action":"sell"}`，`json.loads` 默认 **last-wins**，静默丢掉第一个，最危险。修复回路的原则是：**只做语法层修复（补括号/去尾逗号/丢多余字段），不做语义猜测（类型强转、枚举映射）**，语义层失败一律带错误信息重试。
- **取舍**：修复越激进，越容易把错误"修"成看似合法的错误答案。把 `"purchase"` 映射成 `"buy"` 看似聪明，但如果模型想表达的是"卖出"或"申购"，映射就固化了错误；把 `"ten"` 强转成 10 也一样。可自动修的白名单：截断补全（且补全后必须重新校验）、多余字段按 schema 丢弃（如果业务允许）、尾逗号/单引号等语法噪音。必须重试的：类型不符、枚举越界、必填缺失、重复键（必须报错而不是 last-wins）。重试要有上限（通常 2 次）与降级路径（模板填空/人工/返回结构化错误），否则会陷入"越修越错"的循环。
- **实战**：一次交易助手的 `action` 出现 `"purchase"`，代码里有一段"模糊匹配到最近的枚举值"的逻辑，把它映射成了 `buy`；但用户原意是"申购理财"，被当成买入股票，产生了错误订单。复盘删掉了模糊映射，改成"枚举不匹配 → 带可选值列表重试"，两次失败后转人工确认。另一处是 `max_tokens` 太小导致 JSON 截断，修复器补了 `}` 就放行，结果 `qty` 变成默认 0——修复后必须**重新跑完整校验**，不能只补语法就信。

下面把五类失败逐一构造，跑校验与修复回路，看哪些能修、哪些必须重试。

```python
# 结构化输出失败面: 校验 + 语法层修复 + 重复键检测
import json

ALLOWED, REQUIRED = {"buy", "sell", "hold"}, {"action", "qty"}


def validate(obj):
    if not isinstance(obj, dict):
        return ["not_object"]
    errs = [f"missing:{k}" for k in REQUIRED if k not in obj]
    if "action" in obj and obj["action"] not in ALLOWED:
        errs.append(f"enum:action={obj['action']}")
    if "qty" in obj and (isinstance(obj["qty"], bool) or not isinstance(obj["qty"], int)):
        errs.append("type:qty")
    if set(obj) - REQUIRED:
        errs.append("extra:" + ",".join(sorted(set(obj) - REQUIRED)))
    return errs


def repair(text):
    """只做语法层修复: 补截断的值与未闭合的括号。"""
    t = text.rstrip()
    if t.endswith(":"):
        t += "0"                        # 截断在值上, 补占位值后必须重新校验
    return t + "}" * max(0, t.count("{") - t.count("}"))


def attempt(text, drop_extra=False):
    try:
        obj = json.loads(text)
    except json.JSONDecodeError as e:
        return [f"parse:{e.msg}"]
    if drop_extra and any(e.startswith("extra:") for e in validate(obj)):
        obj = {k: v for k, v in obj.items() if k in REQUIRED}
    return validate(obj)


CASES = {
    "截断": ('{"action":"buy","qty":', None),
    "类型错": ('{"action":"buy","qty":"ten"}', "type:qty"),
    "枚举越界": ('{"action":"purchase","qty":1}', "enum:action=purchase"),
    "多余字段": ('{"action":"buy","qty":1,"note":"x"}', None),
}
for name, (raw, expect) in CASES.items():
    errs = attempt(raw)
    fixed = repair(raw) if errs and errs[0].startswith("parse:") else raw
    errs2 = attempt(fixed, drop_extra=True)
    print(f"[1] {name:>5}: 原始 {errs} -> 修复 {errs2}")
    assert (expect is None and not errs2) or (expect and any(expect in e for e in errs2))


# 重复键: json 默认 last-wins, 必须用 hook 显式拒绝
def dup_hook(pairs):
    keys = [k for k, _ in pairs]
    bad = {k for k in keys if keys.count(k) > 1}
    if bad:
        raise ValueError("duplicate_key:" + ",".join(sorted(bad)))
    return dict(pairs)


try:
    json.loads('{"action":"buy","action":"sell","qty":1}', object_pairs_hook=dup_hook)
    dup = None
except ValueError as e:
    dup = str(e)
print(f"[2] 重复键: {dup}")
assert dup and "duplicate_key:action" in dup

# 修复回路: 语义错误只重试不"修", 2 次后降级
def loop(raw, tries=2):
    for i in range(tries):
        if not attempt(raw):
            return "ok", i + 1
    return "give_up", tries
status, n = loop('{"action":"purchase","qty":1}')
print(f"[3] 枚举越界重试 {n} 次: {status}")
assert status == "give_up"
print("    → 实测 语法可修(补括号/丢多余字段), 语义不可猜(类型/枚举)只能重试后降级")
```

**追问一**：约束解码为什么还会产生"类型错误"？—— 取决于约束的粒度。语法级约束（GBNF/JSON grammar）只保证"token 序列能构成合法 JSON"，`"qty": "ten"` 是完全合法的 JSON，语法约束没有理由拦它；要拦类型，需要**schema 感知的解码器**（在生成 `qty` 的值时只允许数字 token），这类支持在模型/推理框架之间差异很大。即使有 schema 约束，模型也可能用 `"qty": 1.0`（JSON number，schema 要 integer）或 `true`（Python 里 `bool` 是 `int` 子类）绕过。所以**生成端约束 + 服务端校验**必须双保险，不能只信解码器。

**追问二**：为什么"重复键"比"类型错误"更危险？—— 类型错误会被校验器抓住；重复键在 `json.loads` 里默认**静默取最后一个**，校验器看到的是一个合法对象，前面那个值彻底消失。如果模型先输出正确的 `"action":"buy"`、又补了一个 `"action":"sell"`，服务端会按 `sell` 执行，且日志里看不到第一个值。防御方式是解析时用 `object_pairs_hook` 检测重复并拒绝，或直接用支持"重复键报错"的解析器；这在金融/交易类 schema 里是硬要求。

## 背诵要点

- 五类失败面：截断、类型错、枚举越界、多余字段、重复键；约束解码只保证语法，不保证类型/枚举/结束。
- 修复只做语法层（补括号、去尾逗号、按 schema 丢多余字段）且必须重新校验；类型/枚举/重复键一律带错误重试，不做语义猜测。
- 重试上限 2 次 + 降级路径；重复键必须用 `object_pairs_hook` 显式拒绝，默认 last-wins 会静默改写语义。

## 复盘追问

- 约束解码开了还有 3% 失败，怎么分类定位？（按 parse/type/enum/extra/duplicate 打点；parse 多为截断，type/enum 是约束粒度不够）
- 为什么不能把 `"purchase"` 自动映射成 `"buy"`？（语义可能完全不同，映射会固化错误；应带枚举列表重试或转人工）
