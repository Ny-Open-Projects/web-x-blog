### Q7646 · 模型供应商区域故障的切换演练与事故复盘

难度：P6 ｜ 标签：事故复盘 / 高可用 / 供应商治理

**问**：某模型供应商某区域故障 40 分钟，团队"理论上有"多供应商降级方案，实际切换却花了 25 分钟才恢复部分服务，且切过去的备供应商立刻撞配额上限、输出格式不一致引发下游解析失败。多供应商容灾到底要在事前准备什么，演练怎么做才算数？

**答**：
- **结论**：切换慢与切换后连环故障暴露的是"**降级方案只存在于架构图里，不存在于代码与数据里**"。真正的事前准备清单：① **双供应商接续层**（Q7516/Q7577）：请求/响应统一抽象，主备供应商的参数映射、schema 兼容、finish_reason 语义对齐——输出格式不一致是切换后第一大二次故障源，必须在适配层消化而不是让下游兜；② **配额预热**：备供应商的 RPM/TPM 配额（Q7582）要在**平时就以低比例影子流量持续消耗**，既保配额不被云厂商回收（长期 0 流量的配额随时可能缩减），又验证真实链路；③ **切换开关预演**：故障切换做成已验证的配置变更（路由权重 + 缓存策略），不是现场写代码——25 分钟切换时间的主体是"人工决策 + 现场调试"，开关化后目标是 1 分钟；④ **故障语义对账**：主备的错误码/限流头/重试语义不同，切换后客户端重试行为要按备方语义重算。演练标准：不做"读 runbook 的桌面推演"，做**真实流量比例切换**（影子 5% → 灰度 → 全量）并断言指标（错误率、延迟、解析失败率），演练发现的问题回填清单——演练的目标是发现"方案在图上、坑在代码里"的每一处。
- **取舍**：主备双活（影子流量常驻，成本 5-10%）vs 冷备（省成本但切换慢、配额可能失效）：对 LLM 应用，"备方从未真实跑过"几乎等于没有备方——冷备的成本省的是小钱，赌的是大事故。降级目标也要分层：切备供应商（同能力）→ 降级到小模型（能力降）→ 优雅拒绝（排队/稍后重试），不是只有"切供应商"一个选项。
- **实战**：① 适配层对两家供应商跑同一评测集，diff 输出 schema 与行为差异，差异清单进 CI 回归；② 配额对账常态化：备方影子流量的配额用量与账单（Q7604）月度核对；③ 事后复盘三问：切换决策链路用了几分钟（MTTD vs MTTR 分开算）、切换后二次故障清单、哪些准备项缺失。

```python
# 多供应商容灾: 适配层对齐 + 影子流量保配额 + 开关化切换
# 基线: Python 3.9+ 标准库 (语义模型)
from dataclasses import dataclass, field


@dataclass
class Provider:
    name: str
    rpm_quota: int
    used_rpm: int = 0
    schema_version: str = "v1"
    healthy: bool = True


@dataclass
class FailoverRouter:
    primary: Provider
    backup: Provider
    switch: bool = False              # 切换开关(配置化, 非现场写代码)
    shadow_ratio: float = 0.05        # 平时影子流量比例
    events: list[str] = field(default_factory=list)

    def shadow(self, requests: int) -> None:
        """平时影子流量: 保配额 + 验证链路。"""
        self.backup.used_rpm += int(requests * self.shadow_ratio)

    def route(self, n: int) -> str:
        target = self.backup if (self.switch or not self.primary.healthy) \
            else self.primary
        # 切换后二次故障检查: 配额 + schema 兼容
        if target.used_rpm + n > target.rpm_quota:
            self.events.append(f"{target.name}: 配额超限")
            return "DEGRADE: 排队/小模型兜底"
        if target is self.backup \
                and target.schema_version != self.primary.schema_version:
            self.events.append(f"{target.name}: schema 不一致")
            return "FAIL: 适配层未消化 -> 不可全量切换"
        target.used_rpm += n
        return f"OK: routed to {target.name}"


def main() -> None:
    p = Provider("primary-a", 10_000)
    b = Provider("backup-b", 1_000, schema_version="v2")   # 备方 schema 未对齐
    r = FailoverRouter(p, b)
    r.shadow(1000)
    assert r.backup.used_rpm == 50                  # 影子保配额
    assert r.route(100) == "OK: routed to primary-a"
    p.healthy = False                               # 区域故障
    res = r.route(100)
    assert res.startswith("FAIL")                   # schema 未对齐被演练拦住
    assert any("schema" in e for e in r.events)
    b.schema_version = "v1"                         # 适配层对齐后
    b.rpm_quota = 20_000                            # 配额扩容(平时谈好)
    assert r.route(100) == "OK: routed to backup-b"
    print("OK: 影子流量保配额 + 开关化切换 + 适配层消化 schema 差异")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么备供应商"长期零流量"比"没有备供应商"更危险？
→ 一句话提示：零流量意味着配额可能被缩减、适配层从未真实验证、凭证与计费链路未走通——切换时每个假设都在赌；5% 影子流量的成本是给"可用性保险"交保费。

**追问 2**：MTTD 与 MTTR 在这次事故里怎么拆？
→ 一句话提示：MTTD（发现故障）靠监控告警（供应商错误率/延迟异动）；MTTR 25 分钟主体是决策与现场调试——开关化 + 预授权切换把 MTTR 压到分钟级，两者治理手段完全不同，复盘要分开算。

## 背诵要点
- 事前四件套：适配层消化 schema/语义差异、备方影子流量保配额（5% 常驻）、切换开关化预授权、错误/限流语义按备方重算。
- 演练标准 = 真实流量比例切换 + 指标断言（错误率/解析失败率/延迟），桌面推演不算演练；发现的差距回填清单。
- 降级分层：切备供应商 → 小模型 → 优雅拒绝；冷备省小钱赌大事故，"备方从未真实跑过 ≈ 没有备方"。

## 复盘追问
- 切换后"输出格式不一致引发下游解析失败"，为什么要在适配层而不是让下游兼容？提示：下游兼容 = 每个下游都写供应商分支，改动面指数扩大；适配层单点消化是唯一可测试、可回归的位置（Q7577 双轨适配的延伸）。
- 影子流量的比例怎么定？提示：配额保活要求的最小真实用量（供应商政策）+ 评测回归需求，典型 1-10%；太高烧钱，太低失去验证意义，且影子流量必须能升级为真实接管。
