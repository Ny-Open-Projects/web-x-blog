### Q7752 · 评测全绿却在生产翻车：结构化输出的三层漏斗指标

难度：P6 ｜ 标签：LLM 评测、结构化输出、漏斗指标、分层归因

基线：Python 3.12；模拟两组提示词版本的评测样本，输出 解析率→字段准确率→语义合格率 三层漏斗并对比。

**问**：结构化抽取的评测只有一个总分"通过率 82%"，升级提示词后总分涨到 85%，上线后客服投诉反而变多。把评测样本拉出来逐条看：原来新版本让 JSON 更容易解析（解析成功率大涨），但字段填错率也涨了，语义错误被解析改善掩盖。单一总分为什么不够？分层漏斗该怎么设计？

**答**：
- **结论**：结构化输出的质量链条是三级漏斗：① **解析率**——输出能被 json.loads/校验器接受的比例；② **字段准确率**——解析成功的样本里，关键字段与标注一致的比例；③ **语义合格率**——字段对了但整体语义（摘要贴合、口径正确、无幻觉）合格的比例。总分把三级压成一个数，**层间此消彼长完全不可见**：提示词 A 擅长格式、B 擅长语义，总分一样但生产表现完全不同——A 的失败表现为"程序报错"（可重试），B 的失败表现为"静默错数据"（不可重试），后者严重得多。分层指标让每次迭代知道"这一层动了多少"。
- **取舍**：① 漏斗分层的粒度按业务风险定：有下游动作的系统（工单、支付）字段层必须细到关键字段级；② 每层指标要配"失败样本自动落盘"，回归时只重跑失败层；③ 层间样本要**固定同一评测集**，跨版本对比才有意义（Q1507 评估集版本化的前提）；④ 语义层主观性强，用 LLM-as-judge 时要带校准（Q7501），且 judge 的偏差独立报告，不与事实层混算。
- **实战**：① 评测报告固定输出四行：总量、解析率、字段准确率、语义合格率 + 与上版的分层 diff；② 上线门禁改为分层阈值：解析率不得回退、字段准确率不得回退、总分只做参考；③ 生产监控同构：线上解析失败率、字段校验失败率、人工纠正率与评测漏斗对齐（Q7533 离线在线一致性），三层哪层在生产恶化一目了然。

```python
"""结构化输出三层漏斗：解析率 -> 字段准确率 -> 语义合格率，分层 diff 对比。"""
import json

FENCE = chr(96) * 3

SAMPLES = [
    # (raw_output, expected_fields, semantic_ok)
    ('{"order_id": "A1", "amount": 99}', {"order_id": "A1", "amount": 99}, True),
    ('{"order_id": "A2", "amount": 100}', {"order_id": "A2", "amount": 99}, True),
    (FENCE + 'json\n{"order_id": "A3", "amount": 99}\n' + FENCE,
     {"order_id": "A3", "amount": 99}, True),
    ('{"order_id": "A4", "amount": "99元"}', {"order_id": "A4", "amount": 99}, True),
    ('{"order_id": "A5", "amount": 99, "note": "已包含运费(实际不含)"}',
     {"order_id": "A5", "amount": 99}, False),
    ('不是JSON: 订单A6金额99元', {"order_id": "A6", "amount": 99}, True),
]


def strip_fence(raw: str) -> str:
    fence = chr(96) * 3
    if raw.startswith(fence):
        raw = raw.split("\n", 1)[1]
    if raw.endswith(fence):
        raw = raw.rsplit("\n", 1)[0]
    return raw


def funnel(samples: list, extract: callable) -> dict:
    n = len(samples)
    parsed, field_ok, sem_ok = [], [], []
    for raw, expect, sem in samples:
        obj = extract(raw)
        if obj is None:
            continue
        parsed.append((obj, expect, sem))
    for obj, expect, sem in parsed:
        if {k: obj.get(k) for k in expect} == expect:
            field_ok.append((obj, expect, sem))
    sem_ok = [(o, e, s) for o, e, s in field_ok if s]
    return {"总量": n,
            "解析率": len(parsed) / n,
            "字段准确率": (len(field_ok) / len(parsed)) if parsed else 0,
            "语义合格率": (len(sem_ok) / len(field_ok)) if field_ok else 0}


def extract_strict(raw: str) -> dict | None:
    try:
        return json.loads(strip_fence(raw))
    except Exception:
        return None


def extract_lenient(raw: str) -> dict | None:
    """宽松版：从文本里抠出花括号段（修复链的降级策略）。"""
    try:
        return extract_strict(raw)
    except Exception:
        pass
    start = raw.find("{")
    end = raw.rfind("}")
    if start >= 0 and end > start:
        try:
            return json.loads(raw[start:end + 1])
        except Exception:
            return None
    return None


if __name__ == "__main__":
    f_strict = funnel(SAMPLES, extract_strict)
    f_lenient = funnel(SAMPLES, extract_lenient)
    print(f"{'层':<8}{'严格解析':>10}{'宽松修复':>10}")
    for k in ("解析率", "字段准确率", "语义合格率"):
        print(f"{k:<8}{f_strict[k]:>9.0%}{f_lenient[k]:>9.0%}")
    print(f"\n总分对比: 严格 {f_strict['字段准确率'] * f_strict['解析率']:.0%} -> "
          f"宽松 {f_lenient['字段准确率'] * f_lenient['解析率']:.0%}")
    print("解读: 宽松修复只提升解析层; 字段层(99元 vs 99)与语义层(虚假note)不会自愈")
    print("结论：三层漏斗分开看; 上线门禁按层设阈值, 总分掩盖层间此消彼长")
```

**追问一**：字段准确率应该按"整条全对"还是"逐字段"统计？

→ 解析：两者都要，但门禁用"关键字段全对率"（一条样本只要 order_id 或 amount 错就算字段层失败），生产监控用"逐字段错误率"。原因：关键字段是下游动作的触发器，任何一处错都可能引发错误动作，"整条全对率"才反映单次调用的风险；而逐字段错误率用于归因——哪个字段错得多，提示词/schema 的哪个描述要改。只看逐字段会低估风险（每个字段 95% 看着都不错，合起来整条正确率可能只有 80%），只看整条又无法归因。

**追问二**：解析层用宽松修复（抠花括号）提高解析率，会不会反噬字段层？

→ 解析：会，而且这是层间耦合的典型案例。宽松修复把"半截 JSON""JSON 里混着注释"这类样本救回来，但救回的方式可能引入新的字段错误：截断的数值、丢失的必填字段、重复键（Q7740）。所以修复策略必须和字段层校验联动——修复后的对象仍要过 schema 校验与字段比对，"修复成功"只计入解析层指标，字段层该错还是错。更稳的姿势是把修复链（Q7713）的每一步降级动作单独计量，明确知道"这 3% 的解析率提升里，有多少是安全修复、多少是带风险的抢救"。
