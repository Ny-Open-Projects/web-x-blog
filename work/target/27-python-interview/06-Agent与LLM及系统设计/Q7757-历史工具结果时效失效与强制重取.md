### Q7757 · 昨天的库存 30 件只剩 3 件：历史工具结果的时效失效与强制重取

难度：P6 ｜ 标签：Agent、工具结果、时效性、TTL、上下文失效、重取策略

基线：Python 3.12；模拟带时间戳的工具结果进入长会话后，模型基于过期数据作答的场景与"过期标记 + 强制重取"拦截。

**问**：用户昨天问过库存，工具结果"库存 30 件"留在会话历史里；今天用户回来接着问"现在还有货吗"，模型直接引用昨天的 30 件回答，实际只剩 3 件，引发履约事故。历史里的工具结果为什么会变成"毒数据"？怎么让会话内的时间敏感数据自动失效？

**答**：
- **结论**：工具结果进入上下文后就变成了**无时间感知的静态文本**：模型看到"库存 30"这个事实陈述，没有机制判断它是在 30 秒前还是 30 小时前产生的——上下文里只有文本，没有"此刻"的锚。而工具型数据（库存、价格、排队状态、余额）的真实性是**随时间衰减**的。解法是给工具结果加**失效元数据**：写入历史时附带 (产生时间, 数据 TTL/易变级别)，读取会话组装上下文时按"当前时间 - 产生时间 > TTL"打上 `[已过期: 请重新调用工具]` 标记或直接替换占位；对高易变数据（库存/价格/实时状态）无论新旧都**禁止直接引用**，回答前必须重取。
- **取舍**：① 全部工具结果都强制重取会翻倍调用成本，按"易变级别"分级：实时类（库存/价格）强制重取，日类（订单历史/物流单号）按 TTL；② 打标优于删除：删除历史会让会话不连贯，模型看到"[已过期]"标记会主动重取，也保留审计线索；③ TTL 由工具声明（每个工具定义 `data_volatility: realtime/daily/static`），不靠提示词约定——约定会被模型遗忘，元数据由代码强制执行；④ 用户显式说"刚才查的"时，短 TTL（分钟级）内可以复用，避免无意义重调。
- **实战**：① 会话存储里工具消息带元数据字段（时间戳、volatility），组装上下文时统一做时效过滤；② 强制重取的规则放进系统提示词并与代码拦截双保险：代码在易变工具结果上插入过期标记，提示词说明"遇到过期标记必须重新调用"；③ 监控"基于过期数据作答被拦截"的次数，暴涨说明用户会话时长变长或工具易变级别标注错位。

```python
"""历史工具结果时效失效：元数据标记 + 按易变级别强制重取。"""
import datetime as dt

VOLATILITY_TTL = {"realtime": dt.timedelta(minutes=5),
                  "daily": dt.timedelta(days=1),
                  "static": dt.timedelta(days=365)}


def tool_message(tool: str, data: str, volatility: str,
                 produced: dt.datetime) -> dict:
    return {"tool": tool, "data": data, "volatility": volatility,
            "produced": produced}


def assemble_context(messages: list[dict], now: dt.datetime) -> list[dict]:
    """组装上下文: 超过 TTL 的标记过期; realtime 无论多久都标'须重取'。"""
    out = []
    for m in messages:
        age = now - m["produced"]
        ttl = VOLATILITY_TTL[m["volatility"]]
        if m["volatility"] == "realtime" or age > ttl:
            tag = "[已过期|须重新调用工具]" if m["volatility"] == "realtime" \
                else f"[已过期 {age}]"
            out.append({**m, "data": f"{m['data']} {tag}"})
        else:
            out.append(m)
    return out


def decide_reply(ctx: list[dict], asks_realtime: bool) -> str:
    stale = any("须重新调用工具" in m["data"] for m in ctx)
    if asks_realtime and stale:
        return "拦截: 检测到实时类数据过期 -> 先调工具重取, 再回答"
    if asks_realtime:
        return "直接回答(数据在 TTL 内)"
    return "回答(非实时问题, 历史数据可用)"


if __name__ == "__main__":
    now = dt.datetime(2026, 11, 24, 15, 0)
    hist = [
        tool_message("query_stock", "库存 30 件", "realtime",
                     now - dt.timedelta(hours=22)),          # 昨天的查询
        tool_message("get_order", "订单 A100 已发货", "static",
                     now - dt.timedelta(hours=22)),
    ]
    ctx = assemble_context(hist, now)
    for m in ctx:
        print(f"{m['tool']:<12} {m['data']}")
    print("\n用户: 现在还有货吗 ->", decide_reply(ctx, asks_realtime=True))
    print("用户: 我的订单发货了吗 ->", decide_reply(ctx, asks_realtime=False))

    fresh = assemble_context(
        [tool_message("query_stock", "库存 3 件", "realtime", now)], now)
    print("\n重取后:", fresh[0]["data"], "->",
          decide_reply(fresh, asks_realtime=True))
    print("结论：工具结果进历史就失去时间感知; TTL 元数据+过期标记让'毒数据'可见")
    print("      realtime 级数据无论新旧, 回答前必须重取; 打标优于删除, 保留审计线")
```

**追问一**：为什么"在提示词里写'引用数据前检查时间'"不够用？

→ 解析：模型对相对时间的推理并不可靠：历史消息往往**不带时间戳文本**（工具结果的原始输出就一行"库存 30 件"），模型连"这是什么时候产生的"都无从推断；即使带了时间戳，多步推理（现在几点、相差多久、该工具数据多久失效）在长上下文里遵循率有限。代码层拦截是确定性的：组装上下文时标记必然被插入，不依赖模型自觉。提示词的角色是让模型理解标记并采取正确动作（重取），而不是让它自己完成时效判断——分工是"代码判时效，模型做决策"。

**追问二**：用户说"刚才查的还准吗"，怎么在重取成本和体验之间平衡？

→ 解析：引入"软复用窗口"：realtime 数据在 1~5 分钟内允许复用，但回答要带时间标注（"约 2 分钟前查询，库存 3 件"），让用户对时效有感知；超过软窗口则静默重取。判断依据不是用户的措辞，而是数据的易变级别与业务容忍度——价格类数据即使 1 分钟也该重取（成交价敏感），库存类 5 分钟内可容忍。这套窗口参数要做成工具级配置随工具定义走，并监控"软复用率"：复用率过高说明 TTL 配得太松，实际就是在放大过期风险。
