### Q7791 · rerank 的候选窗大小：边际收益曲线与什么时候不值得加

难度：P7 ｜ 标签：Agent、RAG、rerank、候选窗、成本收益、边际收益、break-even

基线：库知识库外知识卡，代码用标准库模拟——用饱和收益曲线 + 线性成本做 break-even 计算，不调用外部 API。

**问**：检索链路是"向量召回 top-100 → rerank → 取 top-5 给模型"，有人提议把候选窗从 100 提到 300，说"多给 rerank 一点候选总没坏处"。这个说法对吗？候选窗该按什么定？如果第一阶段的召回质量已经很高（top-20 就覆盖了 95% 的相关文档），rerank 还值得加吗？怎么用一组离线实验算出"加了不亏"的窗口？

**答**：

- **结论**：rerank 的收益是**饱和曲线**，成本是**近似线性**（每个候选一次 cross-encoder 前向，或至少一次打分），所以"窗口越大越好"只在曲线还没饱和时成立。收益的边际递减来自两个上限：① **召回上限**——rerank 只能在**已召回的候选**里重排，第一阶段没召回的相关文档，窗口再大也变不出来；② **消费上限**——生成端只读 top-k（通常 3～10），rerank 把第 200 名从"不相关"改成"次相关"对最终答案没有影响。所以最优窗口由 **边际质量增益 = 边际成本** 决定，而不是拍一个 100/300。判断"不值得加"的三个信号：第一阶段 recall@k 已接近天花板、生成端 k 很小、候选里长尾质量方差很小（重排排不出差异）。
- **取舍**：窗口大 + 小 k 的组合通常是浪费；窗口小 + 大 k 会让生成端上下文变脏。正确的调参顺序是：先测**第一阶段 recall@N**（N 从 20 到 500），看曲线在哪饱和；再测**rerank 后 nDCG@k** 随窗口的变化；最后把"每提升 1 个点质量值多少钱"与"每多 1 个候选多少毫秒/多少 GPU 成本"对齐，算净收益。rerank 的成本不只是钱：它增加**尾延迟**（一次要等所有候选打分完），对首 token 时延敏感的场景，窗口翻倍可能直接违反 SLO，这时应该用"分批 rerank + 先返回 top-5 的近似结果"而不是硬扩窗。
- **实战**：一个客服 RAG 把窗口从 50 提到 200，离线 nDCG@5 从 0.71 提到 0.73（+2 点），但 P99 从 180ms 涨到 520ms，首 token 超时率从 0.4% 涨到 2.1%。算账：2 个点的质量提升对应的业务收益约等于 0.3% 的解决率，而超时导致的转人工成本更高——结论是**不提窗口**，改为"窗口 50 + 对 top-10 做二次精排"。另一条离线评测链路（不要求实时）则保留了 200 的窗口，因为它没有延迟约束。同一个模型，两种窗口，取决于 SLO。

下面用饱和收益 + 线性成本算最优窗口，并对比"第一阶段已经很强"时的结论。

```python
# rerank 窗口: 饱和收益 vs 线性成本, 求净收益最优与 break-even
import math

V = 100.0          # 1.0 质量分对应的业务价值
C_MS = 0.02        # 1ms 延迟折算的价值损失
BASE_MS = 5.0      # 固定开销
PER_DOC_MS = 0.8   # 每个候选的 rerank 成本


def quality_weak(n):
    """第一阶段较弱: 窗口从 0 到 100 收益明显。"""
    return 0.60 + 0.35 * (1 - math.exp(-n / 25))


def quality_strong(n):
    """第一阶段已很强: top-20 就接近天花板。"""
    return 0.95 + 0.001 * (1 - math.exp(-n / 10))


def net(n, qf):
    return qf(n) * V - (BASE_MS + PER_DOC_MS * n) * C_MS


for name, qf in (("weak", quality_weak), ("strong", quality_strong)):
    rows = [(n, qf(n), net(n, qf)) for n in (0, 10, 20, 50, 100, 150, 200)]
    print(f"[1] {name}: " + ", ".join(f"n={n}:q={q:.3f}:net={v:.2f}" for n, q, v in rows))
    best = max((n for n in range(0, 301, 5)), key=lambda n: net(n, qf))
    print(f"    最优窗口 n={best}, 净收益 {net(best, qf):.2f}")
    if name == "weak":
        best_weak = best
    else:
        best_strong = best
assert 60 <= best_weak <= 160, "弱第一阶段: 窗口有真实最优区间"
assert best_strong == 0, "第一阶段已饱和时, rerank 净收益为负, 应跳过"
print("    → 实测 '窗口越大越好'不成立: 强召回下加窗口只增加成本")

# break-even: 每多一个候选的边际质量收益 = 边际成本
def marginal_q(n, qf):
    return (qf(n + 1) - qf(n)) * V


print(f"[2] 边际成本/候选 = {PER_DOC_MS * C_MS:.4f}")
for n in (20, 50, 100, 150, 200):
    mq = marginal_q(n, quality_weak)
    print(f"    n={n:>3}: 边际收益 {mq:.4f}, 值得加? {mq > PER_DOC_MS * C_MS}")
assert marginal_q(20, quality_weak) > PER_DOC_MS * C_MS
assert marginal_q(200, quality_weak) < PER_DOC_MS * C_MS
print("    → 实测 break-even 之后每加一个候选都是净亏; 窗口应停在边际收益归零点附近")

# 消费上限: 生成端只读 top-5, 窗口超过 5/命中率 后收益封顶
K = 5
HIT = 0.2                     # 每 5 个候选期望覆盖 1 个 top-5 位置
cap = int(K / HIT)
print(f"[3] 生成端只读 top-{K}: 窗口超过 {cap} 后, 多召回的位置没有消费者")
assert cap == 25
print("    → 实测 窗口上限还要被 k 约束; 先确认生成端真的会用第 26 名")
```

**追问一**：rerank 的候选窗和"召回 top-N"是同一个 N 吗？—— 不一定。常见链路是"向量召回 N1 → 粗排/截断到 N2 → rerank N2 → 取 top-k"，N1 可以很大（几百到几千，成本低），N2 才是 rerank 窗口（成本高）。把两者混为一谈会导致"为了 rerank 多召回"或"为了召回扩 rerank"，方向都不对。优化顺序是先把 N1 的 recall@N2 做到饱和（换 embedding、加混合检索、调 ef），再决定 N2 的大小；N2 的收益上限由 N1 的召回率决定，不是由 rerank 模型的能力决定。

**追问二**：为什么 rerank 带来的 nDCG 提升，落到最终答案上经常"看不见"？—— 因为生成端对上下文的利用是**非线性的**：top-1 和 top-3 的差异对答案影响大，top-8 和 top-12 的差异经常被模型忽略（尤其是答案所需信息已经在前面时）。另外 nDCG 是排序指标，答案质量是"关键事实是否在上下文里"的布尔/覆盖率指标，两者不同构。评估时要同时看**排序指标**和**端到端答案指标**（命中率、 faithfulness、人工评分），否则会为"指标好看"付出延迟成本，而用户无感。

## 背诵要点

- rerank 收益饱和（受召回上限与生成端 k 约束）、成本近似线性；最优窗口在"边际质量增益 = 每候选成本"处，不是越大越好。
- 先测第一阶段 recall@N 的饱和点，再定 N2；N2 的收益上限由 N1 的召回率决定，rerank 模型再强也变不出没召回的内容。
- 第一阶段已饱和 / 生成端只读 top-k / 长尾质量方差小 → 不值得加；延迟 SLO 敏感时扩窗往往净亏。

## 复盘追问

- 窗口 50→200 离线 +2 点但线上无感，你怎么判断该不该保留？（看端到端答案指标与 P99/超时率；若质量提升落在生成端不消费的区间，就是白付延迟）
- rerank 成本怎么摊到每个候选上？（固定开销 + 每候选前向耗时；批量能降单位成本但增尾延迟，按 SLO 取平衡）
