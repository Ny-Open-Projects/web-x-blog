### Q7739 · 中文检索按空格切词：整句变成一个 token，关键词召回为 0

难度：P6 ｜ 标签：RAG、中文分词、n-gram、BM25 召回

基线：Python 3.12；`str.split()` 与字符 bigram；倒排索引与 IDF 加权。

**问**：关键词召回那一路上线时用 `text.lower().split()` 切词，英文效果不错。中文商品标题全部变成一个"词"，查询 `"退款"` 与文档 `"退款政策说明"` 的 token 完全不重合，关键词通道召回 0，全靠向量通道兜底。中文该怎么切？

**答**：
- **结论**：中文没有空格分词，`split()` 把整句当成一个 token，倒排索引里每个文档只有一个 key，任何**子串**查询都匹配不上（除非整句完全相等）。三条路：① 专业分词（jieba/pkuseg），精度高但要词典与领域适配；② **字符 n-gram**（bigram：`退款政策` → `退款`/`款政`/`政策`），零依赖、对未登录词友好，代价是倒排膨胀 2~3 倍；③ 混合：n-gram 保召回 + 分词保精度。
- **取舍**：分词精度高但依赖词典，对新词、品牌名、错别字弱，多进程加载词典还占内存；n-gram 零依赖、OOV 友好，但倒排项数暴涨、打分会被高频 bigram 稀释，需要 IDF 压制和高频 bigram 过滤。工程上常见"n-gram 兜底 + 向量主召回"。
- **实战**：① 中文统一走 bigram（或 unigram + bigram 组合）建倒排；② 用 IDF 压低"的/是/了"这类高频字；③ 查询侧用**同样**的切分，保证对称；④ 评测集覆盖专有名词、错别字、中英混排；⑤ 与向量通道用 RRF 融合，而不是把两路分数直接相加。

```python
"""空白切词 vs 字符 bigram：中文关键词召回的天壤之别。"""
import math
import re

CORPUS = {
    "d1": "退款政策说明 签收后 7 天内可申请",
    "d2": "配送时效说明 一线城市次日达",
    "d3": "发票开具流程 支持电子发票",
    "d4": "退款到账时间 原路退回 3 个工作日",
    "d5": "会员权益介绍 积分兑换与折扣",
}
QUERIES = ["退款政策", "发票", "配送时效"]


def split_ws(text: str) -> list[str]:
    return text.lower().split()


def bigrams(text: str) -> list[str]:
    """去掉空白与标点后取相邻两字。"""
    clean = re.sub(r"[\s，。：、,.:]", "", text.lower())
    if len(clean) < 2:
        return [clean] if clean else []
    return [clean[i:i + 2] for i in range(len(clean) - 1)]


def build_index(tokenizer) -> dict[str, set[str]]:
    idx: dict[str, set[str]] = {}
    for doc_id, text in CORPUS.items():
        for tok in set(tokenizer(text)):
            idx.setdefault(tok, set()).add(doc_id)
    return idx


def search(query: str, index: dict[str, set[str]], tokenizer) -> list[tuple[str, float]]:
    q_tokens = set(tokenizer(query))
    n_docs = len(CORPUS)
    scores: dict[str, float] = {}
    for tok in q_tokens:
        docs = index.get(tok, set())
        if not docs:
            continue
        idf = math.log(1 + n_docs / len(docs))      # 高频词权重低
        for d in docs:
            scores[d] = scores.get(d, 0.0) + idf
    return sorted(scores.items(), key=lambda kv: -kv[1])


def recall_at_1(queries, index, tokenizer, expected) -> float:
    hit = 0
    for q in queries:
        res = search(q, index, tokenizer)
        top = res[0][0] if res else None
        hit += int(top == expected[q])
    return hit / len(queries)


if __name__ == "__main__":
    expected = {"退款政策": "d1", "发票": "d3", "配送时效": "d2"}

    ws_index = build_index(split_ws)
    bi_index = build_index(bigrams)

    print("空白切词索引大小:", len(ws_index), "个 token")
    print("bigram 索引大小:", len(bi_index), "个 token -> 膨胀",
          f"{len(bi_index) / len(ws_index):.1f}x")
    print("d1 的空白 token:", split_ws(CORPUS["d1"]))
    print("d1 的 bigram 前 6 个:", bigrams(CORPUS["d1"])[:6])

    print("空白切词 recall@1:", recall_at_1(QUERIES, ws_index, split_ws, expected))
    print("bigram   recall@1:", recall_at_1(QUERIES, bi_index, bigrams, expected))

    for q in QUERIES:
        print(f"  {q!r} ->", search(q, bi_index, bigrams)[:2])

    # 查询侧切分必须对称
    print("查询 '退款' 用空白切:", split_ws("退款"), "-> 索引里不存在该 key")
    print("结论：中文关键词召回必须用 n-gram 或分词；查询与索引的切分必须一致")
```

**追问一**：为什么单用 unigram 效果不好？
→ 解析：单字召回极高但区分度低（"的"几乎出现在所有文档），BM25 的排序会被高频字主导。unigram + bigram 组合（类似 Lucene 的 CJK analyzer）在召回与精度之间更平衡：bigram 提供短语精度，unigram 兜住单字查询。

**追问二**：n-gram 的索引膨胀怎么控？
→ 解析：只对标题/短文本做 bigram，正文用分词；或对 bigram 做哈希压缩、限制每文档 token 数；也可以用引擎内置 tokenizer（SQLite FTS5 的 `trigram`），但 trigram 对 2 字查询支持差，要按查询长度分布选。膨胀的代价主要在存储与写入带宽，查询延迟影响相对小。
