### Q7700 · 推测解码的接受率与延迟账

难度：P7 ｜ 标签：容量成本账、推理优化、speculative decoding、延迟

基线：Python 3.12；纯 Python 模拟草稿-验证两阶段与加速比。

**问**：为了降首 token 后的生成延迟，团队上了 speculative decoding（推测解码/草稿模型），但实测有时快、有时反而更慢。什么决定了它到底加不加速？怎么算这笔延迟账？

**答**：
- **结论**：推测解码用一个小/快模型一次猜出 k 个 token，再用大模型**一次前向并行验证**这些 token，接受则直接采纳、拒绝则从第一个错处重新采样。加速来自"把大模型多次串行的单 token 前向，合并成少量并行前向"。是否加速取决于**接受率 α** 和草稿成本 c：期望加速比近似 `(1-α^(k+1))/((1-α)(1+c·k))` 的倒数关系——草稿太慢（c 大）或接受率低（α 小，草稿模型与大模型分布不匹配）都会使收益为负。
- **取舍**：草稿模型越小越快但接受率越低，越大越准但草稿成本越高，存在最优点；k（每轮猜几个）也不是越大越好，越大被拒浪费越多。它不降低首 token 延迟（TTFT），只优化后续 token 间延迟（TPOT），对短输出几乎无收益。
- **实战**：上线前用真实流量测 α 与 c，别只看 benchmark；对输出短、草稿不匹配的场景直接关掉；监控接受率 drift（模型更新后草稿失效）、每请求被拒重算次数；与量化/KV cache 等优化叠加时要重新测账。

```python
def expected_speedup(alpha: float, k: int, c: float) -> float:
    """近似加速比：alpha=接受率，k=每轮草稿长度，c=草稿单步/大模型单步成本。"""
    if abs(1.0 - alpha) < 1e-9:
        accepted = k + 1
    else:
        accepted = (1.0 - alpha ** (k + 1)) / (1.0 - alpha)
    cost = 1.0 + c * k  # 大模型 1 次验证 + k 次草稿
    return accepted / cost


if __name__ == "__main__":
    for alpha, k, c in ((0.8, 4, 0.1), (0.3, 4, 0.5), (0.9, 6, 0.05)):
        s = expected_speedup(alpha, k, c)
        print(f"alpha={alpha} k={k} c={c}: speedup≈{s:.2f}x "
              f"({'加速' if s > 1 else '反而更慢'})")
    # 接受率高、草稿便宜才加速；草稿贵或接受率低会变慢。
```

**追问一**：为什么推测解码不改善首 token 延迟（TTFT）？
→ 解析：TTFT 由第一个 token 的大模型前向决定，推测解码要先跑草稿再验证，第一步反而多了一次草稿开销；它的收益体现在后续 token 的并行验证上，优化的是 TPOT。

**追问二**：模型升级后接受率下降会怎样？
→ 解析：草稿模型是基于旧模型的分布近似，基座模型升级后分布变化，草稿被拒率上升，加速收益缩水甚至变负。所以要监控接受率漂移，模型升级时同步重训/重选草稿模型。
