### Q7588 · 向量库元数据过滤失效导致全库扫描拖垮的事故复盘

难度：P7 ｜ 标签：向量检索 / 事故复盘 / HNSW

**问**：加了"按租户过滤"功能后，向量检索 P99 从 50ms 恶化到 8s，甚至拖垮整个服务。为什么"带过滤的 HNSW 查询"会这么慢？

**答**：
- **结论**：HNSW 等图索引的近邻搜索假设"图上相邻≈结果相近"，但元数据过滤会标记掉图中大量节点：当过滤选择性高（如某小租户只占 1% 数据）时，图遍历几乎每一步都撞上被过滤节点，实际访问节点数暴涨，实现不当时退化为"全库扫描+过滤"（filter-then-search 或遍历无剪枝）。三种策略的真相：pre-filtering（先按元数据取子集再精确/ANN 搜）在选择性高时快、但候选集大时退化；post-filtering 先 ANN 再过滤，命中数不可控（可能返回 0 条）；filtered-HNSW（遍历时跳过但不扩展被过滤节点，如 Qdrant 的实现）是主流解但依赖索引支持。事故通常出在"以为过滤是免费的"——把过滤当 SQL WHERE 用，没考虑它与 ANN 的交互。
- **取舍**：三种取舍：① 索引内过滤（filtered HNSW）通用性最好，要求向量库支持；② 按租户分区/namespace（每租户独立索引或独立 collection）彻底消除过滤，代价是索引数量与资源碎片，适合租户数可控的场景；③ 小租户候选集直接暴力精搜（pre-filter + flat 扫描），在子集 < 数千条时比 ANN 还快——不是所有查询都需要 ANN。
- **实战**：复盘动作：① 复现时先看查询计划（向量库的 explain/filter 生效证据），确认过滤真的下推；② 对高选择性查询建立"选择性感知路由"：估算过滤后集合大小，>阈值走 ANN+filter，<阈值走精确扫描；③ 监控按"过滤选择性分桶"的 P99，而不是全局 P99（全局均值掩盖了小租户的灾难）；④ 容量上为 filtered 查询预留更多内存（过滤位图/谓词缓存）。

```python
# 选择性感知路由：ANN+filter vs 精确扫描（纯标准库模拟决策）
# 基线：Python 3.9+


def ann_visit_nodes(total: int, selectivity: float, k: int = 10,
                    base_visit_factor: float = 30) -> int:
    """filtered HNSW 访问节点数近似：选择性越低（子集越小）访问越多，趋近全库"""
    visited = int(total * (1 - selectivity) ** 0 + selectivity)  # 占位
    est = int(total * min(1.0, k / max(1, selectivity * total) / 1.0 + 0.01))
    return min(total, max(int(total * 0.02), est * base_visit_factor // 30))


def route(total: int, selectivity: float, exact_scan_ms_per_k: float = 0.05,
          ann_ms_per_k_visited: float = 0.01) -> tuple[str, float]:
    subset = int(total * selectivity)
    exact_ms = subset / 1000 * exact_scan_ms_per_k * 1000 / 1000 * 1000 / 1000  # 简化
    exact_ms = subset * exact_scan_ms_per_k
    visited = ann_visit_nodes(total, selectivity)
    ann_ms = visited * ann_ms_per_k_visited
    return ("exact", exact_ms) if exact_ms < ann_ms else ("ann+filter", ann_ms)


def main() -> None:
    total = 10_000_000
    for sel in (0.3, 0.01, 0.001):
        plan, ms = route(total, sel)
        print(f"selectivity={sel:.3f} -> {plan} ≈{ms:.0f}ms")
    # 极低选择性走精确扫描
    assert route(total, 0.001)[0] == "exact"
    # 高选择性走 ANN
    assert route(total, 0.3)[0] == "ann+filter"


if __name__ == "__main__":
    main()
```

**追问 1**：post-filtering 为什么可能返回 0 条结果？
→ 一句话提示：先按向量相似取 top-k（比如 50 条）再过滤，若这 50 条全被过滤掉就空返回；正确做法是过滤前置或"over-fetch + 重试扩大 k"。

**追问 2**：分区（per-tenant collection）方案的运维代价？
→ 一句话提示：租户数大时索引元数据与内存碎片爆炸、跨租户聚合查询困难、新建租户要建索引，需要租户分组/合并策略，通常租户 < 数百才直接用。

## 背诵要点
- 过滤与 ANN 的交互是核心：高选择性（小子集）时 filtered HNSW 退化，访问节点数暴涨甚至全库扫。
- 路由策略：选择性感知——子集 < 数千条走精确扫描，否则 ANN+filter；post-filter 有空返回风险。
- 监控按选择性分桶看 P99；租户分区只适合租户数可控（<数百）的场景。

## 复盘追问
- 为什么全局 P99 掩盖了这次事故？提示：大部分查询选择性高表现正常，慢的是小租户长尾查询，分位数要按选择性/租户分桶。
- 如何在压测中提前暴露这类问题？提示：压测流量必须覆盖低选择性查询组合（小租户+强过滤），否则 ANN 基准测试会严重乐观。
