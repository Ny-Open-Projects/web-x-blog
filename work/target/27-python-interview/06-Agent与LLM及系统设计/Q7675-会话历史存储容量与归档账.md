### Q7675 · 会话历史的存储容量账与归档设计

难度：P6 ｜ 标签：容量规划、存储、Agent
基线：与 Q7645（会话裁剪的 token 成本）互补——本卡算的是**存储侧**的账。

**问**：Agent 产品上线一年，会话历史表 40 亿行、2TB，主库被拖到慢查询频发。会话历史的存储容量怎么算？热/温/冷分层与归档怎么设计？

**答**：**结论**：会话历史的容量账 = 会话数 × 平均轮次 × 每轮字节（消息 + 元数据 + 工具调用记录），其中**工具调用与 trace 记录通常占 70% 以上**体积——消息本身很小，工具的输入输出 JSON 才是大头。存储分层按访问概率设计：热层（7-30 天，主库/SSD，支撑"继续上次对话"）、温层（30-180 天，对象存储 Parquet，支撑审计与回放）、冷层（180 天+，压缩归档，只留合规需要的最小字段）。归档的硬约束是**可重建性**：只要 trace 血缘完整，冷层可以只存摘要 + 指针。

**取舍**：归档粒度的取舍：按会话整体归档（实现简单，热会话不能部分恢复）vs 按轮次归档（最近 N 轮留主库，其余下沉——查询体验最好但行级搬移成本高）。多数产品选会话粒度 + 主库保留"会话元数据行"（ID、摘要、时间），正文下沉——列表页查元数据永远快。

**实战**：容量预估用真实分布而不是平均：P95 会话轮次远高于均值（长会话吃掉大半存储），按 P95 × 折算预留；归档任务本身要限速（写放大影响主库）、断点续跑、归档后校验（行数 + checksum，Q1409 同源方法）。

```python
# 会话历史容量账与分层归档规划（标准库可运行）
from dataclasses import dataclass

@dataclass
class SessionProfile:
    sessions: int
    avg_turns: float
    p95_turns: float
    msg_bytes: int          # 每轮纯消息字节
    tool_bytes: int         # 每轮工具 IO + trace 字节
    days_hot: int = 30

def storage_forecast(p: SessionProfile) -> dict:
    per_turn = p.msg_bytes + p.tool_bytes
    avg_total = p.sessions * p.avg_turns * per_turn
    p95_total = p.sessions * p.p95_turns * per_turn
    # 分层：热层按近 30 天会话比例估算（设 5% 会话仍活跃）
    hot_ratio = min(1.0, p.days_hot / 365)
    hot = avg_total * hot_ratio
    return {
        "avg_total_tb": round(avg_total / 1024**4, 2),
        "p95_total_tb": round(p95_total / 1024**4, 2),
        "hot_tb": round(hot / 1024**4, 3),
        "tool_share": f"{p.tool_bytes / per_turn:.0%}",
        "note": "工具 IO 占大头，归档时优先压缩/摘要工具记录",
    }

p = SessionProfile(sessions=10_000_000, avg_turns=12, p95_turns=80,
                   msg_bytes=2_000, tool_bytes=12_000)
print(storage_forecast(p))

# 归档策略：会话粒度下沉，主库留元数据
def archive_plan(total_sessions: int, keep_hot_days: int,
                 sessions_per_day: int) -> dict:
    hot_rows = sessions_per_day * keep_hot_days
    archive_rows = total_sessions - hot_rows
    cold_bytes = archive_rows * 14_000 * 0.35     # 归档压缩比 ~65%
    return {"主库保留行数": hot_rows,
            "下沉行数": archive_rows,
            "冷层体积TB": round(cold_bytes / 1024**4, 2),
            "主库瘦身后慢查询": "列表页只查元数据行，恢复全文走对象存储"}

print(archive_plan(400_000_000, 30, 100_000))

# 归档校验：行数 + checksum 分块（迁移校验同源方法）
import hashlib, json
def chunk_checksum(rows: list[dict]) -> list[str]:
    out = []
    for i in range(0, len(rows), 1000):
        chunk = rows[i:i + 1000]
        out.append(hashlib.sha1(
            json.dumps(chunk, sort_keys=True).encode()).hexdigest()[:8])
    return out
sample = [{"sid": s, "turns": s % 20} for s in range(2500)]
print("分块 checksum 数:", len(chunk_checksum(sample)))
```

**追问 1**：为什么说"工具调用记录占 70% 体积"？这个比例如何验证？
提示：消息是几百字节文本，工具 IO 含完整请求/响应 JSON、trace span、重试记录，单次可达几十 KB；验证方法是按表/字段做体积 TOP 统计（pg_relation_size 按表 + 采样行宽），别凭感觉。

**追问 2**：归档后"恢复一次三个月前的会话"的体验怎么保证？
提示：主库留会话元数据行（ID/摘要/时间），恢复走对象存储按会话 key 整取（Parquet 列裁剪）+ 按需反序列化；体验预算是秒级——所以冷层按会话组织而不是按天大文件，避免恢复一个会话扫一天的数据。

**追问 3**：合规要求"删除用户数据"时，归档层怎么响应？
提示：对象存储上按用户前缀组织 + 删除清单任务（软删→物理删两级），并留删除审计；这是归档设计一开始就要定的，事后改造的成本是重写全部冷层 key 结构。

## 背诵要点
1. 容量账 = 会话数 × 轮次 × 每轮字节；工具 IO/trace 占 70%+ 体积，归档优先压它。
2. 分层：热（主库 7-30 天）/温（Parquet 对象存储）/冷（压缩最小字段），按会话粒度下沉、主库留元数据行。
3. 按真实分布（P95 轮次）预留而非均值；归档要限速、断点续跑、行数+checksum 校验。
