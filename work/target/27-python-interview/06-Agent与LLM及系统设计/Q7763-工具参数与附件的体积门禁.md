### Q7763 · Agent 让模型传 100MB CSV 直接 OOM：工具参数与附件的体积门禁

难度：P6 ｜ 标签：工具参数校验、体积门禁、附件处理、OOM、schema 约束

基线：Python 3.12；实现带体积上限声明的工具注册表与执行前置校验器，演示超限拦截与分块替代路径，全标准库实跑。

**问**：分析类 Agent 的"读数据文件"工具，模型（或用户）塞了一个 100MB 的 CSV 进参数，工具实现直接把整个文件读进内存解析——进程 OOM，整条 Agent 会话挂掉。工具的参数体积上限应该在几层设防？schema 里的 max 声明管得住吗？超大输入的正确路径是什么？

**答**：
- **结论**：体积门禁要**三层设防**，每层兜住上一层漏掉的：① **schema 声明层**：工具注册时声明每个参数的上限（字节数/行数/数组长度/字符串长度），模型调用时供应商侧的 strict 校验可拦一部分——但 schema 的 max 语义各家支持不一，不能只靠它（Q7707 schema 子集限制）；② **执行前置层**：工具执行器在调用实现函数**之前**统一检查：参数序列化后的字节数、字符串长度、附件句柄指向的实际大小（附件在对象存储，查 manifest 就知道体积，不用下载）——这一层是门禁的真正执行点，超限返回结构化错误（带"超了什么、建议怎么做"），让模型能自我修正（Q7524 校验自愈循环）；③ **实现防御层**：工具函数内部流式处理（逐行读、分块解析），不给"整读"留任何路径——门禁是闸，流式是坝，只有闸没有坝总有一天漏。超大输入的正解不是"想办法传进来"，是**换路径**：附件走对象存储 + 返回句柄（Q1752 大结果外置的镜像问题）、处理走分块/流式、结果走摘要回传。
- **取舍**：① 上限值怎么定：按工具实测峰值内存 × 安全系数反推（Q7138 RSS 账），宁可偏小再调大——OOM 事故的成本远大于"再传一次"的摩擦；② 附件 base64 塞参数是大忌：体积膨胀 33% 且全部占上下文与请求体（Q7612 请求体上限），一律外置存储+句柄；③ 门禁的错误信息是给模型看的：要可行动（"文件 100MB 超过 10MB 上限，请使用 analyze_summary 工具或先按行分块"），返回原始异常只会让模型瞎猜；④ 会话级累计校验：单工具 10MB 没事，一次会话 50 次调用累计 500MB 也要有会话配额（Q2029 资源配额的体积维度）。
- **实战**：① 工具注册表把 max 声明做成必填字段（没有上限的工具不允许注册）；② 门禁校验在执行器统一实现，工具作者只写业务；③ OOM 事后归因脚本：按工具统计参数体积 P99，超限调用是上限调优的输入；④ 大文件场景的评测样本：评测集加"模型试图传 100MB"的 case，验证门禁与模型自愈路径（Q7768 提示词单测衔接）。

```python
"""工具参数体积门禁: 注册表声明上限 + 执行前置校验 + 流式替代路径。"""
import json


TOOLS = {
    # 每个工具注册时必填参数上限 (字节), 没有上限不允许注册
    "read_csv": {
        "limits": {"csv_data": 10 * 1024 * 1024},   # 10MB
        "hint": "超过上限请改用 analyze_summary 或按行分块多次调用",
    },
    "search_docs": {
        "limits": {"query": 2_000},
        "hint": "查询串过长请拆分关键词",
    },
}


def guard(tool: str, args: dict) -> tuple[bool, str]:
    """执行前置校验: 在工具实现被调用之前统一检查体积。"""
    spec = TOOLS[tool]
    for param, limit in spec["limits"].items():
        if param not in args:
            continue
        size = len(args[param].encode())            # 字节级检查
        if size > limit:
            return False, (f"参数 {param} 体积 {size / 1e6:.1f}MB "
                           f"超过上限 {limit / 1e6:.1f}MB。建议: {spec['hint']}")
    return True, "通过"


def read_csv_all(csv_data: str) -> dict:
    """反例实现: 整读整解析 (门禁被绕过时直接 OOM 的路径)。"""
    rows = csv_data.splitlines()
    return {"rows": len(rows), "preview": rows[:3]}


def read_csv_streamed(csv_data: str, chunk_lines: int = 1000) -> dict:
    """正解实现: 流式分块, 内存恒定 (工具内部是坝)。"""
    total, preview = 0, []
    buf = []
    for line in csv_data.splitlines():
        buf.append(line)
        if len(buf) >= chunk_lines:
            total += len(buf)
            preview = preview or buf[:3]
            buf.clear()
    total += len(buf)
    return {"rows": total, "preview": preview[:3], "mode": "streamed"}


if __name__ == "__main__":
    normal = "id,amount\n" + "\n".join(f"{i},{i * 2}" for i in range(1000))
    huge = "id,amount\n" + "\n".join(f"{i},{i * 2}" for i in range(600_000))  # ~10MB

    print(f"常规调用 (约 {len(normal.encode()) / 1e3:.0f}KB):")
    ok, msg = guard("read_csv", {"csv_data": normal})
    print(f"  门禁: {ok} -> {msg}")
    print(f"  执行: {read_csv_all(normal)}")

    print(f"\n超大调用 (约 {len(huge.encode()) / 1e6:.1f}MB):")
    ok2, msg2 = guard("read_csv", {"csv_data": huge})
    print(f"  门禁: {ok2} -> {msg2}")
    if not ok2:
        # 门禁拦截 -> 引导换路径: 分块流式处理
        lines = huge.splitlines()
        n_chunks = (len(lines) + 999) // 1000
        print(f"  模型自愈: 改走流式路径, {len(lines)} 行分 {n_chunks} 块处理")
        print(f"  流式执行: {read_csv_streamed(huge)}")

    # 无上限工具的注册拒绝
    try:
        _ = TOOLS["no_limit"]                  # noqa
    except KeyError:
        print("\n注册检查: 未声明上限的工具 'no_limit' 不允许注册 (KeyError)")
    ok = not ok2 and len(huge.encode()) > 10 * 1024 * 1024
    print(f"校验: 超限被拦截 + 流式路径可用 -> {'通过' if ok else '异常'}")
    print("\n结论：体积门禁三层设防: schema 声明 -> 执行前置拦截 -> 内部流式;")
    print("      超限错误要可行动, 引导模型换路径而不是让它瞎重试")
```

**追问一**：附件为什么必须走对象存储加句柄，而不是 base64 塞参数？

→ 解析：三笔账都算不过来。① **体积账**：base64 膨胀 33%，100MB 附件变 133MB 字符串，请求体直接撞供应商网关上限（Q7612），就算塞进去也占掉大半上下文预算（Q7764 的预算被一个附件吃光）；② **计量账**：附件作为输入 token 计费（Q7681 多模态计价），100MB 文本按 token 算是天价，而对象存储加句柄只付几十字节的引用；③ **安全账**：附件内容绕过了门禁与扫描层（Q7767 MIME 校验在参数通道上根本摸不到文件），外置存储让上传走独立的扫描与白名单流程。句柄模式还自带审计与生命周期：附件有独立 TTL、权限与删除路径。一句话：**大对象永远走引用，不走值传递**——这与 Q1752 工具结果外置是同一原则的两端（输入端与输出端）。

**追问二**：上限设多少合适，怎么从"拍脑袋"变成"有依据"？

→ 解析：上限是容量模型的输出，不是直觉。推导链：① 测量工具实现的峰值内存曲线（不同输入体积下的 RSS，Q7138 的量测方法），找出"内存峰值 = f(输入体积)"的斜率；② 按容器内存 limit 减去其他占用（基础堆、并发请求余量）得单次调用的内存预算（Q6042 OOMKilled 账）；③ 预算 ÷ 斜率 = 上限，再打 0.7 安全系数防并发叠加（多个请求同时传大参数）；④ 上限随实现优化动态调整——流式改造后同样的预算能撑更大输入，上限可以放宽。运维层面把"参数体积分布"做成按工具的常规指标：P99 逼近上限说明真实需求在顶天花板，要么优化实现要么升配，而不是让业务硬扛摩擦。门禁参数进配置中心随发布调整，别硬编码在工具里。
