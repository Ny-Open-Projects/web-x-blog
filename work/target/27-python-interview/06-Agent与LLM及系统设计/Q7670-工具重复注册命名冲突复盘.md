### Q7670 · 工具重复注册与命名冲突：Agent 拿错工具的复盘

难度：P6/P7 ｜ 标签：事故复盘、工具注册、Agent
基线：OpenAI/Anthropic function calling（本代码为标准库模拟注册表，可运行）。

**问**：Agent 上线新工具后，模型频繁调用错误的旧版工具。排查发现两个模块各自向注册表注册了同名工具。重复注册的破坏机制是什么？注册表层如何防住这类冲突？

**答**：**结论**：破坏机制取决于注册表对重复名的处理——**"后写覆盖"（dict 默认行为）静默替换定义**，模型看到的 schema 是最后注册者的，但调用方可能还按旧实现分发，形成"schema 与实现错配"；若注册表改成"先写保留"则相反。两种都是静默错误：模型行为漂移、无报错。这类事故的可怕之处是**与加载顺序耦合**：单测里导入顺序 A→B 正常，生产进程 B→A 就翻车。

**取舍**：三种注册表策略：① 重复注册直接抛错（fail-fast）——开发期最有效，但会让"有意覆盖"（同一工具的测试桩）变难，需要显式 `override=True`；② 命名空间隔离（`module.tool_name`）——把冲突从机制上消灭，代价是工具名变长、模型选择时描述要写清归属；③ 注册即校验（schema 冲突检测 + 冲突时记录 warning 并进启动失败清单）。推荐 ①+②：开发环境抛错、命名空间兜底。

**实战**：注册表加三条防线：注册时查重抛错、启动时输出"工具清单指纹"（名字+版本+schema 哈希）写日志供 diff、`list_tools()` 只暴露去重后的清单。工具描述里写明模块归属，降低模型选错概率。

```python
class ToolRegistry:
    def __init__(self, strict: bool = True):
        self._tools: dict[str, dict] = {}
        self._owner: dict[str, str] = {}
        self.strict = strict

    def register(self, name: str, schema: dict, owner: str,
                 override: bool = False):
        if name in self._tools and not override:
            if self.strict:
                raise ValueError(
                    f"工具重名: {name} 已被 {self._owner[name]} 注册, "
                    f"新注册方 {owner} —— 改名或加命名空间前缀")
        self._tools[name] = schema
        self._owner[name] = owner

    def fingerprint(self) -> dict:
        """启动时打印：名字 + schema 哈希，供发布 diff 与排障。"""
        import hashlib, json
        return {n: hashlib.sha1(
                    json.dumps(s, sort_keys=True).encode()).hexdigest()[:8]
                for n, s in self._tools.items()}

reg = ToolRegistry(strict=True)
reg.register("search_docs", {"type": "object"}, owner="rag_module")
try:
    reg.register("search_docs", {"type": "object"}, owner="crm_module")
except ValueError as e:
    print("拦截:", e)

# 命名空间兜底：同一能力两个模块并存也不冲突
reg.register("rag.search_docs", {"type": "object"}, owner="rag_module")
reg.register("crm.search_docs", {"type": "object"}, owner="crm_module")
print("注册表:", list(reg._tools))
print("指纹:", reg.fingerprint())

# 复盘要点：错配更隐蔽的形态——schema 与实现分属两个模块
# （schema 覆盖了但实现没覆盖），所以 owner 与实现绑定必须一起登记
assert reg._owner["rag.search_docs"] == "rag_module"
```

**追问 1**：为什么"schema 覆盖了但实现没覆盖"比"整体覆盖"更难排查？
提示：模型按新 schema 发参数，实现按旧签名解析——调用可能因参数缺失报错，也可能静默用默认值执行错逻辑；表象（报错）与根因（注册冲突）相距甚远，通常要靠指纹 diff 才能定位。

**追问 2**：MCP 场景下多个 server 提供同名工具怎么办？
提示：客户端聚合时必须做 namespacing（server 名作前缀）或启动时校验冲突列表；这是 MCP 网关的职责之一，裸聚合必然踩 Q7638/Q7578 同源问题。

**追问 3**：测试桩（测试环境覆盖真实工具）和事故的重复注册，边界怎么定？
提示：用显式 `override=True` + 测试框架 fixture 声明覆盖意图，代码评审可见；静默覆盖永远不允许——机制上区分"声明式覆盖"与"意外碰撞"。

## 背诵要点
1. 重复注册的核心风险是静默：后写覆盖 dict 语义 + 导入顺序耦合，生产单测行为不一致。
2. 防线：注册查重抛错（override 需显式声明）+ 命名空间前缀 + 启动指纹 diff。
3. 最隐蔽形态是"schema 与实现错配"，owner 与实现必须随 schema 一起登记。
