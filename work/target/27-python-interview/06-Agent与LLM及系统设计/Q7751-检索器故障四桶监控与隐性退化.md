### Q7751 · 检索器悄悄变差：空结果/超时/降级的分桶统计与告警分界

难度：P6 ｜ 标签：RAG、检索器监控、故障分类、降级路径、分桶统计

基线：Python 3.12；包装检索调用，按失败形态分桶计数，演示"整体成功率正常但空结果率暴涨"的隐性退化检测。

**问**：RAG 服务上线三个月，检索模块的可用性监控一直是绿的（没有超时、没有 5xx），但用户投诉"答非所问"越来越多。查日志才发现：向量库因为某次数据迁移，大量查询开始返回**空结果或弱相关结果**，请求都"成功"了，监控却看不见。检索器的故障该怎么分类监控？"返回空"到底算成功还是失败？

**答**：
- **结论**：检索器的失败形态至少分四桶：① **异常**——超时/连接失败，传统可用性监控能看见；② **空结果**——请求成功但 0 命中，通常是索引损坏、过滤条件过严、embedding 维度不匹配（Q7684）；③ **弱结果**——有返回但相似度都低于阈值（Q7527 的阈值标定），意味着索引内容陈旧或查询漂移；④ **降级命中**——走了兜底路径（关键词检索/缓存）而非主检索器。②③④ 都披着"成功"的外衣，必须按桶分别计数、分别设阈值：空结果率 >2% 告警（索引故障），降级率 >10% 告警（主链路故障），弱结果率缓慢上涨是数据质量问题。
- **取舍**：① 全量打分贵（每条结果都算相似度），可对空结果全量记录、弱结果按比例抽样打分；② 告警分界要按桶设——把四桶混成一个"成功率"，任何一桶劣化都会被另外三桶稀释；③ 降级路径要显式计量而非静默兜底，否则主检索器挂了业务还"看着正常"；④ 空结果还有业务正常来源（用户乱搜），告警阈值按"同型查询簇的空结果率"（Q2580 频次聚类）算更准。
- **实战**：① 检索包装层统一埋点，四桶计数进指标系统，与 QPS 同权重；② 每日输出"检索健康报告"：四桶占比 + top 空结果 query 列表（回捞用）；③ 空结果样本自动留痕（查询文本、过滤条件、索引版本），故障时第一现场就在手边；④ 上线/迁移后跑检索回归集（Q2044 抽检），在监控告警之前主动暴露。

```python
"""检索器四桶监控：异常/空结果/弱结果/降级，分桶阈值演示隐性退化。"""
import random

THRESH = {"异常率": 0.01, "空结果率": 0.02, "弱结果率": 0.15, "降级率": 0.10}


def call_retriever(query: str, mode: str) -> dict:
    """mode: healthy | index_broken | primary_down"""
    if mode == "index_broken":
        if random.random() < 0.5:
            return {"status": "ok", "hits": [], "score_max": None}
        return {"status": "ok", "hits": ["x"], "score_max": 0.35}
    if mode == "primary_down":
        return {"status": "degraded", "hits": ["kw"], "score_max": 0.8}
    return {"status": "ok", "hits": ["doc"], "score_max": 0.85}


def bucketize(calls: list[dict]) -> dict[str, float]:
    n = len(calls)
    return {
        "异常率": sum(1 for c in calls if c["status"] == "error") / n,
        "空结果率": sum(1 for c in calls if c["status"] == "ok" and not c["hits"]) / n,
        "弱结果率": sum(1 for c in calls
                    if c["status"] == "ok" and c["hits"] and c["score_max"] < 0.5) / n,
        "降级率": sum(1 for c in calls if c["status"] == "degraded") / n,
    }


def alert(buckets: dict[str, float]) -> list[str]:
    out = []
    for k, v in buckets.items():
        if v > THRESH[k]:
            out.append(f"{k}={v:.1%} 超阈值 {THRESH[k]:.0%}")
    return out or ["全部在阈值内"]


if __name__ == "__main__":
    random.seed(3)
    qs = [f"q{i}" for i in range(500)]
    for mode, label in (("healthy", "健康期"), ("index_broken", "索引悄悄坏了"),
                        ("primary_down", "主检索器宕机")):
        calls = [call_retriever(q, mode) for q in qs]
        b = bucketize(calls)
        naive_ok = 1 - b["异常率"]                  # 传统监控只看异常
        print(f"[{label}] 传统成功率={naive_ok:.0%}")
        for k, v in b.items():
            flag = " <-- 超" if v > THRESH[k] else ""
            print(f"    {k}: {v:.1%}{flag}")
        print("    告警:", "; ".join(alert(b)), "\n")
    print("结论：四桶分开计数才看得见'成功但变差'；降级路径要显式计量不许静默")
```

**追问一**：为什么"空结果"不该笼统算失败？业务正常也产生空结果。

→ 解析：用户搜索一个库里确实没有的词，空结果是正确行为；索引坏了导致的全量空结果是故障。区分靠**同型查询簇的空结果率**：把查询归一化聚类（Q2580），某个"历史上总有结果"的簇突然全空，就是索引侧故障的强信号；而"从没有结果"的新簇是业务现象。监控指标也应分两层——整体空结果率看趋势（缓涨=数据陈旧），簇级空结果率突变看故障（跳变=索引事故）。混在一起看，要么告警全是误报、要么真故障被噪声淹没。

**追问二**：降级路径（关键词兜底）兜住了服务，那主检索器挂掉为什么还要紧？

→ 解析：兜底路径的检索质量通常显著低于主路径（无语义匹配、召回窄），降级率持续 >10% 意味着十分之一的用户拿到的是"能用但差"的答案——业务指标（追问率、无答案率）会悄悄恶化，而可用性指标全绿。这就是"静默降级"的陷阱：兜底成功让故障不可见。所以降级必须显式计量并告警，且降级响应里打标（返回给前端"该答案基于简化检索"），让故障在用户体验层面也可追溯。兜底是可用性手段，不是免检金牌。
