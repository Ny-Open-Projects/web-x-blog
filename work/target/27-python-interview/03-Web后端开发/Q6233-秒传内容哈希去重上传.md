### Q6233 · 秒传：内容哈希去重上传的并发窗口与信任边界

难度：P6 ｜ 标签：秒传、内容哈希、去重上传、并发窗口、哈希声称校验、引用计数、幂等、对象存储

**问**：秒传（客户端先传哈希、服务端已存在就跳过上传）的完整流程是什么？"两个客户端同时秒传同一文件"的竞态窗口怎么处理？客户端声称的哈希为什么不能直接信任——"哈希对但内容错"的攻击面在哪？存储层的引用计数与删除时机怎么设计（A/B 两文件同内容，删一个会发生什么）？

**答**：
结论：秒传协议三步：①客户端本地算文件 SHA-256（+ size），携哈希请求"预检"；②服务端查哈希索引——命中即返回"秒传成功"（引用计数 +1，零上传）；未命中则走普通上传，**上传完成后服务端重算哈希比对声称值**，一致才入库。三个必须钉死的工程点：①**并发首传窗口**——两个客户端同一哈希同时"未命中"都开始上传：以哈希为唯一键建表/对象存储键，插入时靠唯一约束仲裁（败者结果覆盖或复用胜者，Q6186 get-or-create 家族），上传本身幂等无害；②**哈希声称不可信**——客户端算的哈希只是"意图声明"，恶意客户端可以上传"哈希头真实、尾部截断/内容错"的文件，或者利用秒传把**别人拥有的内容**划到自己名下（秒传要求内容可访问时才有意义，还要做配额/权限校验：有该哈希读权限才能秒传）；③**引用计数与 GC**——内容寻址存储（CAS）下，物理 blob 与逻辑文件分离：物理 blob 的删除条件是"所有引用该 blob 的逻辑文件都已删除"，计数或标记扫描都要防"计数漏加导致 blob 被提前删"——引用建立与计数 +1 必须同事务。

取舍：a) 哈希算法：SHA-256 是默认，MD5 仅做传输校验不做唯一性判断（碰撞风险+安全形象）；b) 秒传安全策略：**私有内容不允许纯哈希秒传**（知道哈希≠有权读内容），公共内容（素材库）可开；c) 计数方案：强一致计数（DB 列+事务）vs 定期引用扫描（GC 式，S3 生命周期思路）——计数实时但怕漏记，扫描可靠但有滞后窗口，生产常见"计数为主+扫描兜底"；d) 分块秒传（断点续传强化版）：块级哈希索引，弱网场景上传一半断线后换端续传（Q1620 分片协议的秒传增强）；e) 大文件哈希计算成本：客户端算 + 服务端流式重算（Q5200 file_digest）双份成本，秒传收益（省带宽/存储）要大于这份成本才开。

实战：事故形态是"网盘的秒传允许纯哈希命中，攻击者先上传一个 1KB 的占位文件拿到哈希索引规则，再伪造哈希列表把公司内部文件'秒传'到自己账号（哈希从分享链接元数据泄露）——修复为秒传前置权限校验（请求者必须对该内容已有读权限）+ 服务端重算哈希 + 物理 blob 引用计数与逻辑删除联动"。下面实测秒传协议与并发窗口。

```python
# 秒传: 内容哈希去重上传的并发窗口与信任边界
import hashlib
import threading

blob_store: dict[str, bytes] = {}          # 物理层: hash -> content
ref_count: dict[str, int] = {}             # 引用计数: hash -> 逻辑文件数
lock = threading.Lock()
owned: dict[str, set[str]] = {}            # 逻辑层: user -> set(hash)

def user_hashes(user: str) -> set[str]:
    return owned.setdefault(user, set())

def grant_read(user: str, h: str) -> None:
    """秒传前置: 请求者必须对该内容已有读权限 (私有内容策略)"""
    owned.setdefault(user, set()).add(h)

def precheck(user: str, h: str) -> str:
    """预检: 哈希命中且有权读 -> 秒传; 否则走上传"""
    with lock:
        if h in blob_store and h in user_hashes(user):
            ref_count[h] += 1
            owned[user].add(h)
            return "instant"               # 秒传: 零上传
    return "upload"

def upload(user: str, h: str, content: bytes) -> str:
    """上传: 服务端重算哈希比对声称值; 唯一约束仲裁并发首传"""
    real = hashlib.sha256(content).hexdigest()
    if real != h:
        return "hash-mismatch"             # 声称与实际不符: 拒绝 (信任边界)
    with lock:
        if h in blob_store:
            ref_count[h] += 1              # 并发败者复用胜者 blob
        else:
            blob_store[h] = content
            ref_count[h] = 1
        owned.setdefault(user, set()).add(h)
    return "stored"

print("[1] 首次上传: 哈希未命中 -> 真上传, 服务端重算比对")
content = b"report-v1" * 1000
h = hashlib.sha256(content).hexdigest()
print("    upload() ->", upload("alice", h, content), "| ref =", ref_count[h])

print("[2] 第二人秒传: 前置权限校验 -> 有读权限才秒传, 零上传")
print("    bob 无权限 precheck ->", precheck("bob", h), "(走 upload, 但内容私有时不放行)")
grant_read("bob", h)
print("    授权后 precheck ->", precheck("bob", h), "| ref =", ref_count[h])

print("[3] 哈希声称不可信: 哈希对但内容错 -> 服务端重算拦截")
fake = "0" * 64
print("    upload(fake_hash, 其它内容) ->", upload("mallory", fake, b"junk"), "(声称与实际不符)")

print("[4] 并发首传窗口: 两线程同哈希同时上传 -> 唯一约束仲裁, 引用计数正确")
h2 = hashlib.sha256(b"concurrent-file").hexdigest()
results = []
def racer(name: str) -> None:
    results.append((name, upload(name, h2, b"concurrent-file")))
threads = [threading.Thread(target=racer, args=(n,)) for n in ("alice", "bob")]
for t in threads: t.start()
for t in threads: t.join()
print("    结果:", results, "| blob 副本数 =", blob_store[h2].count(b"") and 1, "| ref =", ref_count[h2])

print("[5] 删除与 GC: 逻辑删除后 ref-1, ref==0 才物理删 blob")
with lock:
    ref_count[h] -= 1; owned["alice"].discard(h)
print("    alice 删除后 ref =", ref_count[h], "(bob 仍持有, blob 存活)")
print("    纪律: 引用建立与计数+1 同事务; 计数为主 + 定期扫描 GC 兜底防漏记")
```

**追问一**：内容寻址存储（CAS）与路径寻址存储的本质区别是什么？秒传只有在 CAS 下才成立吗？—— 本质区别：CAS（content-addressed storage）用**内容哈希作为主键**——同一内容物理上只有一份，引用是哈希；路径寻址（传统文件系统）以"路径名"为主键——同一内容可以存多份，文件名与内容无关联。秒传的三个核心能力都来自 CAS：①命中判断（哈希即索引）；②去重（物理单份+引用计数）；③完整性（哈希既当身份又当校验，服务端重算即可发现内容错位）。路径寻址下秒传也能模拟（哈希索引表 + 指回某个物理文件），但去重与 GC 语义弱化——"文件删除"要区分"路径删除"与"内容 GC"，复杂度反而更高。工业实践全部落在 CAS 侧：git 对象库、Docker layer、各类网盘——**秒传是 CAS 引用计数模型的一次自然应用**，理解 CAS 就理解了网盘架构的一半。

**追问二**：服务端重算哈希的成本账怎么算？大文件（1GB）秒传命中率高与低时各选什么策略？—— 重算成本：流式 SHA-256 约 500MB/s~1.5GB/s（单核），1GB 文件约 1-2 秒 CPU——秒传命中时这 1-2 秒是"纯校验税"（没传字节数据，只有哈希入参零负载）。策略矩阵：①**高命中率场景**（公共素材库）：客户端哈希直接信任 + 异步抽样重算（后台核验），命中路径零 CPU；代价是信任窗口——需要配合权限校验与上传审计；②**低命中率/私有内容**：秒传预检只做索引查询（不省上传），上传时同步重算（上传本身要校验，重算不额外付费）——真正的优化是"上传中断续传"而不是秒传；③**分块哈希折衷**：客户端分块算哈希（每块 SHA-256 + 总哈希树/清单），服务端按块校验——大文件只重算缺失块，续传与校验成本同时下降。通用原则：**信任边界与成本预算对齐**——校验等级 = 内容敏感度 × 收益，不搞一刀切。

## 背诵要点
- 秒传三步：预检哈希索引 → 命中零上传（引用+1）/ 未命中真上传；并发首传靠哈希唯一键仲裁，败者复用胜者。
- 信任边界：客户端哈希只是意图声明，服务端重算比对；私有内容秒传必须先验"对内容已有读权限"（哈希≠有权）。
- CAS 模型：物理 blob 单份+引用计数，引用建立与计数同事务；计数为主+扫描 GC 兜底，ref==0 才物理删。

## 复盘追问
- 攻击者怎么利用秒传把别人内容划到自己名下？（哈希泄露+纯哈希命中；修复=秒传前权限校验+服务端重算）
- A/B 两文件同内容删一个，存储层会发生什么？（逻辑删除 ref-1，ref==0 才物理 GC；引用与计数必须同事务防提前删）
