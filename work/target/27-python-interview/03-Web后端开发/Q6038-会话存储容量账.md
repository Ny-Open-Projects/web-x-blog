### Q6038 · 会话存储的容量账：Redis session 内存与过期策略

> 难度:★★★★ | 标签:容量规划, 会话, Redis, TTL

**问**："1000 万注册用户、日活 50 万"的会话存储要多少内存？session 条目的真实字节构成怎么估？TTL 怎么设才不把内存账做爆？会话续期（sliding expiration）的代价是什么？

**答**：容量账从条目构成算起：一条 session = **key（session id，~50B 含 Redis overhead）+ value（序列化后的用户态数据，典型 200B-2KB）+ Redis 数据结构开销（dict entry/skiplist，~100B）+ TTL 记录**，合并约 0.5-3KB/条。峰值条目数 = **活跃会话数**（不是注册数）= 日活 × (1 + 并发设备数) × 会话时长放大系数——日活 50 万 × 会话 7 天滚动 ≈ 稳态 300-500 万条 × 1KB ≈ **3-5GB**，加 50% 余量配 8GB 的 Redis 分片即可；这就是"注册 1000 万不可怕、活跃会话数才决定容量"的要点。TTL 策略：1) **固定 TTL**（7 天）：实现最简单，活跃用户也要重登；2) **滑动续期**（每次访问重置 TTL）：体验好但有成本——a) 每请求一次 EXPIRE 写放大（Redis 写命令翻倍），b) 重大量回写时 AOF/RDB 体积膨胀，c) 续期逻辑要防"未登录流量也续期"；折中是**阈值续期**——剩余 TTL < 50% 才续（Q6009 的 token 轮换同思想）；3) 会话数据瘦身：session 里只放 id+权限版本，用户画像按需查（每条从 2KB 压到 300B 就是 6 倍容量）。监控先行：`used_memory`、keyspace 过期淘汰速率、TTL 分布直方图。

```python
# file: code/03_Web后端开发/q6038_session_capacity.py
"""会话容量账模型 + 阈值续期器. Redis 未安装时降级为内存版演示."""
import json
import time

# --- 1) 条目字节账 ---
def entry_bytes(value_json: str) -> int:
    key_overhead = 60          # session_id key + Redis dict entry
    value = len(value_json.encode())
    struct_overhead = 100      # value 对象头/rob/dict entry
    return key_overhead + value + struct_overhead

thin = json.dumps({"uid": 123456, "pv": 3})                       # 瘦身版
fat = json.dumps({"uid": 123456, "pv": 3, "profile": {"name": "用户" * 10,
                  "avatar": "https://cdn.example.com/a.png", "prefs": list(range(20))}})
print(f"瘦身条目 ≈ {entry_bytes(thin)}B | 全量条目 ≈ {entry_bytes(fat)}B")

# --- 2) 容量推演 ---
DAU, DEVICES, WINDOW_DAYS = 500_000, 1.3, 7
steady = int(DAU * DEVICES * WINDOW_DAYS)          # 稳态活跃会话数(滚动)
for label, per in (("瘦身", entry_bytes(thin)), ("全量", entry_bytes(fat))):
    gb = steady * per / 1024**3
    print(f"{label}: 稳态 {steady:,} 条 × {per}B ≈ {gb:.1f}GB (Redis 配置需 ×1.5 余量)")

# --- 3) 阈值续期器: 剩余 TTL < 50% 才续, 抑制写放大 ---
class SlidingSession:
    TTL = 7 * 86400

    def __init__(self) -> None:
        self.store: dict[str, tuple[dict, float]] = {}   # sid -> (data, expire_at)
        self.renews = 0
        self.expiry_writes = 0

    def touch(self, sid: str, data: dict) -> None:
        now = time.monotonic()
        _, exp = self.store.get(sid, ({}, 0))
        remaining = exp - now
        if sid in self.store and remaining > self.TTL / 2:
            return                                  # 剩余过半: 不续(省一次写)
        self.store[sid] = (data, now + self.TTL)
        self.expiry_writes += 1
        self.renews += 1 if sid in self.store else 0

    def alive(self, sid: str) -> bool:
        item = self.store.get(sid)
        return item is not None and item[1] > time.monotonic()

if __name__ == "__main__":
    sess = SlidingSession()
    sess.touch("s1", {"uid": 1})
    for _ in range(10):                             # 10 次访问只有 1 次续期
        sess.touch("s1", {"uid": 1})
        time.sleep(0.001)
    print(f"阈值续期: 11 次访问, TTL 写次数={sess.expiry_writes} ( naive=11 )")
    print("监控位: used_memory / 过期淘汰速率 / TTL 分布直方图")
```

**追问**：1) 为什么按"活跃会话数"而不是注册数算容量？——注册但未登录的会话根本不在存储里（或只是极小的记住我 token），决定内存的是并发在途的会话条目；按注册数算容量是 20 倍级别的错账。2) Redis 主动过期与内存淘汰的交互？——过期 key 是惰性删除+定期抽样，TTL 分布集中时（如整点批量写入）会有删除尖峰；`maxmemory-policy` 用 volatile-ttl/LRU 时要防"会话被误淘汰"，会话 key 应配独立 DB/实例与 noeviction。3) 多设备场景的会话账怎么变？——条目数 ×设备数、单设备登出要精确失效（会话列表索引，Q2452），索引结构本身也有容量成本。

## 背诵要点
- 容量账：稳态条目 = 日活 × 设备数 × 会话窗口滚动；按活跃会话数算，不按注册数。
- 条目 0.5-3KB：key 开销 + value + Redis 结构开销；session 瘦身（只放 id+权限版本）是最大杠杆。
- 滑动续期写放大翻倍 → 阈值续期（剩余 <50% 才续）；会话 key 独立实例防误淘汰。
