### Q6247 · XSS 防线的上下文输出编码：HTML/属性/JS/URL 四语境

难度：P6 ｜ 标签：XSS、上下文输出编码、html.escape、JSON 嵌入、URL 编码、CSP 协同、转义误区、富文本白名单

**问**：为什么"统一 html.escape 一遍"防不住全部 XSS——HTML 正文、属性、JS 上下文、URL 上下文各自的危险字符与转义方式差在哪？把用户数据嵌入 `<script>` 标签里的 JSON 时要额外防什么（</script> 逃逸、U+2028）？模板引擎的 autoescape 边界（mark_safe/|safe 的豁免口子）怎么管？CSP 与输出编码是什么分工？

**答**：
结论：XSS 的本质是**数据越过语境边界被当作代码执行**——同一个字符串在四个语境里的"危险字符集"完全不同，所以**没有万能转义，只有"按语境选编码器"**：①**HTML 正文**（`<div>{x}</div>`）——转义 `< > & "`（`html.escape(x)`），防标签注入；②**HTML 属性**（`<img alt="{x}">`）——必须**引号包裹 + 转义引号**（`html.escape(x, quote=True)`），因为无引号属性里空格也越界；还要防 `javascript:` 这类**属性值语义注入**（href/src 属性的白名单协议校验，转义防不了 URL 语义攻击）；③**JS 上下文**（`<script>var x = {json}</script>`）——JSON.stringify/json.dumps 只保证 JS 字面量合法，**防不了 HTML 解析层的逃逸**：payload 里含 `</script>` 会提前终结标签（JSON 本身合法但 HTML 解析器看到 `</script>` 就切回 HTML 上下文，后面的内容被当 HTML），标准修法是把 `<` 转成 `\u003c` 或把 `</` 替换为 `<\/`；再加 U+2028/U+2029（JS 合法 JSON 但在老 JS 语法里是行终止符，Q6228 的逃逸细节）；④**URL 上下文**（`href="/search?q={x}"`）——参数值用 `urllib.parse.quote(x, safe="")` 百分号编码，**整个 href 的协议**用白名单（http/https/相对路径），堵 `javascript:alert(1)`。模板层防线：Jinja2/Django 的 **autoescape 默认开启**是底线，但 `|safe`/`mark_safe`/`Markup` 是显式豁免口子——**豁免即承诺"这段 HTML 是可信产物"**，管理纪律是豁免点集中审计（富文本清洗器输出、i18n 模板）+ 对"含用户数据的 safe"零容忍。CSP 分工：输出编码是"第一道主动防线"（阻止注入），CSP（nonce/严格模式，Q6157/Q6224）是"纵深防御"（就算注入成功，内联脚本也不执行）——**编码防注入、CSP 降伤害**，两者不可互替。

取舍：a) 富文本场景（用户要发带格式的内容）：不能用"转义"（会破坏合法格式）——用**白名单清洗器**（bleach 类：标签/属性/协议三层白名单，事件属性 on* 全剥离），清洗器输出才允许 mark_safe；清洗器的解析用 HTML 解析器而非正则（正则防不住嵌套与畸形标签）；b) JSON 嵌入的标准姿势：后端 `json.dumps` + `<`→`\u003c` 替换输出到 `<script>`，或者改用 `data-*` 属性 + JS 读取（属性语境转义）——避免手写"JSON 字符串直接塞 script"；c) 客户端拼接的责任边界：服务端编码了不代表安全——前端 `innerHTML = user_data` 是二次注入点，契约是"API 返回数据，前端按语境编码后插入"（textContent vs innerHTML 的纪律）；d) 转义的位置原则：**在输出点转义，不在入库时转义**——入库时转义会导致二次转义污染（搜索、导出、其他语境复用全是错的）；e) 测试形态：每种语境一条 XSS 样本用例（`<img onerror>`、`javascript:`、`</script><script>`、U+2028）进 CI 快照，模板改动跑回归。

实战：事故形态是"个人主页自定义签名功能：后端统一 html.escape 后返回，前端把签名拼进 `<script>const bio = {json}</script>` 用于埋点——攻击者签名里带 `</script><script>...`，JSON 合法但提前闭合了 script 标签，全站用户侧脚本注入。修复为：JSON 输出统一 `<`→`\u003c` 编码函数 + CSP nonce 全站收紧 + 富文本字段走 bleach 白名单清洗（不再 escape 后 safe）+ CI 增加四语境 XSS 样本回归"。下面实测四语境编码与 JSON 逃逸。

```python
# XSS 上下文输出编码: HTML / 属性 / JS / URL 四语境
import html
import json
from urllib.parse import quote

payload = '<img src=x onerror="alert(1)">'

print("[1] HTML 正文语境: html.escape 转义 < > & 引号")
print("    原文   :", payload)
print("    转义后 :", html.escape(payload))

print("[2] 属性语境: 引号包裹 + quote=True; 协议要白名单而非转义")
attr_safe = html.escape(payload, quote=True)
print("    属性值 :", f'<img alt="{attr_safe}">')
url_attacks = ["javascript:alert(1)", "JaVaScRiPt:alert(1)", " javascript:alert(1)", "/ok-path"]
for u in url_attacks:
    parsed = u.strip().lower()
    verdict = "允许" if parsed.startswith(("http://", "https://", "/")) else "拒绝 (协议白名单)"
    print(f"    href={u!r:<28} -> {verdict}")

print("[3] JS 语境: json.dumps 合法但防不住 HTML 解析器, 必须 < -> \\u003c")
evil_bio = '</script><script>alert("pwned")</script>'
naive = json.dumps({"bio": evil_bio})                       # JSON 层合法
print("    naive JSON :", naive)
print("    HTML 解析器视角: 看到 </script> 即提前闭合 -> 后面被当 HTML 执行!")
def js_safe_json(obj) -> str:
    return json.dumps(obj).replace("<", "\\u003c").replace(">", "\\u003e")\
                          .replace("&", "\\u0026").replace("　", "\\u3000")
safe = js_safe_json({"bio": evil_bio})
print("    安全 JSON  :", safe, "(< 已变 \\u003c, 不再终结 script 标签)")

print("[4] URL 语境: 参数值 percent-encode, safe='' 连 / 都编码")
q = '"><script>alert(1)</script>'
print("    q 编码后  :", quote(q, safe=""))
print("    完整链接  : /search?q=" + quote(q, safe=""))

print("[5] 模板豁免口子: autoescape 默认开, |safe/mark_safe 是显式承诺")
print("    Jinja2: Markup(text) / |safe  -> 豁免点必须集中审计, 含用户数据的 safe 零容忍")
print("[rule ] 四语境四种编码器; JSON 嵌 script 必须 < -> \\u003c; 编码防注入 + CSP 降伤害不可互替")
```

**追问一**：`javascript:` 协议注入为什么"转义"防不了？"URL 上下文的白名单"应该校验哪几层？—— `javascript:alert(1)` 里没有任何"必须转义的危险字符"——它是**合法 URL、合法属性值**，危险在**协议语义**（浏览器对 href 执行 JS 协议）——转义器（字符级）与协议校验（语义级）是两个层面，字符转义不改变 `javascript:` 的语义，甚至大小写混写（`JaVaScRiPt:`）、前导空白（` javascript:`）、控制字符（`java\tscript:`）都是"逃过 naive 前缀匹配"的变体——所以 URL 语境的校验必须是**解析后再判**：用 `urlparse` 拿 scheme（浏览器对 scheme 的解析容忍空白/大小写，应用侧要用宽容解析对齐行为再白名单）、scheme ∈ {http, https} 或无 scheme 的相对路径才放行；相对路径还要防 `//evil.com`（协议相对地址跳外域，开放重定向 Q1650 同族）；data: 协议（可嵌 HTML/SVG 脚本）默认拒绝。三层校验清单：①scheme 白名单（解析后判，不字符串前缀匹配）；②host 校验（防协议相对跳外域）；③参数值 percent-encode（query 部分不破坏 URL 结构）。推论：**"能不能转义"取决于语境的危险来自字符还是来自语义**——HTML/JS 语境危险来自字符（转义有效），URL 语境两者皆有（转义+语义白名单双管）。

**追问二**：富文本白名单清洗器（bleach 类）的实现要点是什么？"清洗后再转义"与"转义后再清洗"为什么都是错的？CSP nonce 与清洗器的防线分工？—— 清洗器要点：①**解析级处理**——用 HTML 解析器（html.parser/bleach 基于 html5lib）重建 DOM，正则清洗防不住畸形标签（`<scr<script>ipt>` 拆词重组、未闭合标签携带属性）；②**三层白名单**——标签白名单（p/b/i/a/img...）、属性白名单（a[href,title]、img[src,alt]）、协议白名单（href/src 只许 http/https/相对）；事件属性（on*）、style 属性（CSS 注入面）、iframe/object 默认全剥离；③**输出再编码**——清洗后的安全 HTML 输出时仍要保证属性值引号转义。顺序错误的两种形态："清洗后再转义"把合法的 `<p>` 转成 `&lt;p&gt;`——富文本变纯文本（功能损毁）；"转义后再清洗"清洗器解析的是**已转义的实体**——攻击者构造 `&lt;script&gt;` 被解码回 `<script>` 后若再输出未编码即注入（或清洗器误把实体当文本放过）——两个顺序都同时破坏功能与安全，唯一正确顺序是**原始输入 → 解析 → 白名单过滤 → 输出安全 HTML（不再全局转义）**。CSP 分工：清洗器是"输入侧主动消毒"（决定什么 HTML 可以存在），CSP nonce/严格模式是"执行侧兜底"（就算清洗有漏网，无 nonce 的内联脚本不执行、外域脚本不加载）——清洗器的漏网率永远非零（解析器差异、新浏览器特性），CSP 是把"漏网"从"事故"降级为"未遂"的那道闸，两者都要上。

## 背诵要点
- 四语境四种编码器：HTML 正文 escape(< > &)、属性引号包裹+quote=True、JS 语境 JSON 后 <→\u003c（防 </script> 提前闭合与 U+2028）、URL 参数 quote(safe="") + scheme 解析后白名单。
- javascript: 注入是语义攻击字符转义无效——URL 语境校验=宽容解析 scheme 白名单+host 校验防 //evil.com；autoescape 默认开、|safe/mark_safe 是豁免承诺须集中审计。
- 富文本唯一正确链：解析→三层白名单（标签/属性/协议）→输出安全 HTML；转义与清洗顺序互斥皆错；编码防注入+CSP 降伤害，不可互替。

## 复盘追问
- 签名嵌 <script> 里的 JSON 为什么会被逃逸？（JSON 合法但 HTML 解析器看到 </script> 提前闭合标签；标准修法是输出前 < 转成 \u003c，配合 CSP nonce 兜底）
- 富文本为什么不能"清洗后再转义"？（转义毁掉合法格式；正确链=解析→标签/属性/协议三层白名单→输出安全 HTML；CSP 是清洗漏网时的执行侧兜底）
