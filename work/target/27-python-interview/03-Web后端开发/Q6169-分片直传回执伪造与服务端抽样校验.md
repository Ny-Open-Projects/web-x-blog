### Q6169 · 分片直传回执伪造与服务端抽样校验

难度：P7 ｜ 标签：分片上传、直传、校验回执、不可信输入、HMAC

**问**：大文件"客户端直传对象存储、应用服务器只收校验回执"时，为什么不能相信客户端上报的 MD5？服务端在合并阶段如何验证分片完整性——全量重算、抽样校验、还是给回执签名？三种策略的成本与安全性怎么权衡？为什么"回执签名"不能替代"内容校验"？本题与 Q1621/Q2448（分片合并与完整性校验）的边界在哪？

**答**：
结论：直传模式下应用服务器**从不接触分片字节**，只拿到"第 N 片上传成功、MD5=xxx"的回执；若把这个回执当真，攻击者可以伪造 MD5 让损坏/篡改的分片通过合并——因为 MD5 是客户端自己算的，**自证不等于他证**。三种防线：① **全量服务端校验**——合并时从对象存储读回所有分片重算 hash，最安全但等于把直传省下的带宽又读了一遍（成本翻倍），大文件场景不可接受；② **抽样校验**——对部分分片（如按 hash 概率或固定比例）读回重算，成本低但只能"概率发现"，适合非高价值内容；③ **回执签名**——让对象存储的回调（callback）带服务端密钥签发的 HMAC，证明"回执确实来自存储服务而非客户端伪造"——但它证明的是**回执来源可信**，不证明**内容未被篡改**（上传时字节已坏，存储照签不误），所以签名与内容校验是两道不同的防线，不能互相替代。Q1621/Q2448 讲的是"如何正确合并与校验以保证正确性"（无对手模型），本题讲的是"回执来自不可信客户端时的信任边界"（有对手模型）——前者是工程正确性，后者是安全。

取舍：高价值文件（合同、镜像）用"回执签名 + 全量或高比例抽样 + 合并后整体 hash 对账"；普通 UGC 用"回执签名 + 低比例抽样"，把成本压在可接受范围。关键是把"对象存储的上传回调"配置为**只信任来自存储服务 IP/签名的通知**，不接受客户端转发的回执——否则签名也形同虚设。抽样要有随机性与可审计记录，固定抽第 1 片会被攻击者针对性绕过。

实战：事故形态是"用户上传的文件偶尔损坏，日志显示所有分片 MD5 校验通过"——根因是服务端信任了客户端上报的 MD5。下面模拟：伪造回执在"信任客户端"路径下通过、在"服务端重算"路径下被抓，以及 HMAC 回执签名如何证明来源。

```python
import hashlib, hmac

SECRET = b"server-only-secret"
chunk = b"real-piece-bytes"

def md5(data):
    return hashlib.md5(data).hexdigest()

def client_report(data, piece_id, forge=False):
    digest = md5(data)
    return {"piece": piece_id, "md5": "0" * 32 if forge else digest}

def merge(chunk_bytes, report, trust_client=False):
    if trust_client:
        return f"merged (trusted client md5={report['md5']})"   # 伪造通过
    actual = md5(chunk_bytes)
    if not hmac.compare_digest(actual, report["md5"]):
        raise ValueError(f"checksum mismatch: reported={report['md5']} actual={actual}")
    return "merged after server recompute"

forged = client_report(chunk, 1, forge=True)
print("trust client :", merge(chunk, forged, trust_client=True))
try:
    merge(chunk, forged)
except ValueError as e:
    print("verify       :", e)

# 回执签名：证明回执来自存储服务，而非客户端伪造
def sign_receipt(piece_id, digest):
    mac = hmac.new(SECRET, f"{piece_id}:{digest}".encode(), hashlib.sha256).hexdigest()
    return {"piece": piece_id, "md5": digest, "sig": mac}

def valid_signature(receipt):
    expected = sign_receipt(receipt["piece"], receipt["md5"])["sig"]
    return hmac.compare_digest(expected, receipt["sig"])

good = sign_receipt(1, md5(chunk))
tampered = dict(good, md5="0" * 32)         # 客户端篡改回执内容但保留旧签名
print("sig good     :", valid_signature(good))
print("sig tampered :", valid_signature(tampered), " <- 篡改被签名捕获")
```

**追问一**：HMAC 签名回执为什么不能替代内容校验？——签名只证明"这条回执是持有密钥的存储服务发出的"，但存储服务收到什么字节就签什么字节：如果上传链路本身损坏或攻击者在上传时替换了内容（而存储照常回调签名），签名依然有效却对应坏数据。要证明"内容正确"，必须有独立的、基于内容本身的计算（重算 hash 并与可信源对比）——签名管**来源真实性**，hash 管**内容完整性**，两个维度。

**追问二**：抽样校验为什么必须随机且不可预测？——若固定"只验第 1 片"或"只验偶数片"，攻击者知道规则后只需保证被抽中的分片正确、其余任意篡改，抽样率再高也失效。正确做法是用服务端密钥 + 分片 ID 计算伪随机选择（如 `hmac(secret, piece_id) % 100 < rate`），让攻击者无法预知哪些片会被验；同时把抽样决策与结果记入审计日志，事后可追责。代价是"发现概率"而非"保证"——所以高价值内容要提高比例或全量。

## 背诵要点
- 直传回执的 MD5 是客户端自证，不可信；信任它会导致损坏/篡改分片被合并。
- 三防线：全量重算（最安全最贵）/ 抽样校验（概率发现、随机不可预测）/ HMAC 回执签名（证明来源，不证明内容）。
- 签名≠内容校验；与 Q1621/Q2448 的"正确性校验"区别在"有对手模型"的信任边界。

## 复盘追问
- 用户上传文件偶尔损坏但日志显示所有分片校验通过，如何用"客户端自证 MD5"解释并设计三防线？（信任边界、全量/抽样/签名取舍、随机抽样与审计）
- 为什么"回执有 HMAC 签名"仍可能对损坏内容通过？（签名管来源真实性不管内容完整性，讨论独立 hash 校验的必要性）
