### Q6049 · 缓存与数据库双写不一致的事故复盘

> 难度:★★★★ | 标签:缓存一致性, 双写, 事故复盘, cache-aside

**问**：事故：价格改了，部分用户看到旧价格持续 2 小时。"先更新 DB 再删缓存"（cache-aside）为什么会不一致？哪些时序能产生脏数据？TTL、延迟双删、binlog 订阅失效各自解决到什么程度？怎么给出可落地的组合方案？

**答**：cache-aside（读：miss 则查 DB 回填；写：更新 DB 后删缓存）的不一致窗口来自**并发读写的交错**：写者 A 更新 DB → 删缓存之前，读者 B miss 缓存、查到**旧 DB 值**（A 的事务还没提交或读到快照）→ B 把旧值回填缓存 → A 删缓存发生在回填之前 → 旧值留存到 TTL。第二个来源：删缓存失败（网络抖动）无重试。治理手段的覆盖矩阵：1) **TTL**：兜底一切未知时序，"不一致最多活 TTL 时长"——所以 TTL 不是性能参数是**一致性参数**，价格类要短（秒-分钟级）；2) **延迟双删**：写后延迟数百 ms 再删一次，覆盖"读旧回填"窗口——实现简单但延迟时长靠猜，高并发下仍有漏网；3) **binlog 订阅失效（CDC）**：以 DB 变更为唯一事实源异步删缓存，解决"删失败"（可重试、有序），但仍是**最终一致**且有订阅延迟；4) **强一致需求**：该路径不该走缓存（直接读 DB 或加分布式锁/版本号 CAS，版本不匹配回源）。落地组合：普通数据 cache-aside + TTL 分钟级；价格/库存这类关键数据"短 TTL + CDC 删缓存兜底 + 读侧容忍窗口"；变更接口响应里带版本号让前端可校验。复盘观测：缓存与 DB 的抽样比对任务（定时 diff 抽样 N 条）作为不一致率的持续度量，而不是等客诉。

```python
# file: code/03-Web后端开发/q6049_cache_db_inconsistency.py
import threading
import time

db = {"price": 100}
cache = {}
cache_lock = threading.Lock()
CONSISTENCY_LOG = []

def read_user_style(delay_before_fill=0.0):
    """读者: miss -> 查 DB -> 回填 (事故里的交错点)"""
    with cache_lock:
        if "price" in cache:
            return cache["price"], "hit"
    time.sleep(delay_before_fill)               # 事务/慢查询窗口
    value = db["price"]                          # 可能读到旧值(A 未提交/快照)
    time.sleep(delay_before_fill)
    with cache_lock:
        cache["price"] = value                   # 旧值回填 = 脏数据来源
    return value, "refill"

def writer_bad(new_price):
    """事故写法: 更新 DB 后直接删缓存, 与读者交错产生脏数据"""
    time.sleep(0.01)
    db["price"] = new_price
    with cache_lock:
        cache.pop("price", None)                 # 删在回填之前 -> 删了个寂寞
    return "deleted"

# 复现交错: 写者在读者"查 DB 后、回填前"删缓存
cache.clear()
reader_result = {}
t = threading.Thread(target=lambda: reader_result.update(
    zip(("val", "how"), read_user_style(delay_before_fill=0.03))))
t.start()
time.sleep(0.02)                                 # 保证读者先进入窗口
writer_bad(200)
t.join()
print(f"DB=200, 读者回填值={reader_result['val']} -> 缓存脏到 TTL ({reader_result['how']})")

# 修复: 写后延迟双删(演示) + TTL 兜底
def writer_delayed_double_delete(new_price, delay=0.05):
    db["price"] = new_price
    with cache_lock:
        cache.pop("price", None)
    time.sleep(delay)                            # 覆盖读旧回填窗口
    with cache_lock:
        cache.pop("price", None)                 # 第二删清掉窗口期回填的旧值

cache.clear()
t = threading.Thread(target=lambda: reader_result.update(
    zip(("val", "how"), read_user_style(delay_before_fill=0.03))))
t.start()
time.sleep(0.02)
writer_delayed_double_delete(300)
t.join()
val, how = read_user_style()
print(f"双删后读: {val} ({how}) -> 窗口期旧值被第二删清除")
print("组合方案: 短 TTL(一致性参数) + 延迟双删 + CDC binlog 订阅兜底; 强一致路径不走缓存")
```

**追问**：1) 为什么是"删缓存"而不是"更新缓存"？——更新缓存在并发写下会写入过期值（两个写者交错），且缓存值常是查询结果的加工态（多表 join），写侧算不出；删除让下次读回源，语义简单正确。2) CDC 删缓存能保证顺序吗？——按表主键分区消费可保单行有序；跨行/跨表依赖（先删 A 后删 B）要用同一分区键；乱序删除会造成旧值覆盖新值的"回填逆序"事故。3) 分布式锁保强一致的代价是什么？——写路径串行化 + 锁服务可用性成为依赖，吞吐与可用性双付；多数业务用"短 TTL + 对账"够用，强一致留给 DB 直读。

## 背诵要点
- 不一致窗口 = 读者"查 DB 旧值后、回填前"被写者删除的交错；删失败是第二来源。
- TTL 是一致性参数不是性能参数；关键数据秒-分钟级短 TTL。
- 组合方案：cache-aside 删不更新 + 延迟双删 + CDC 兜底；强一致路径不走缓存；用抽样 diff 持续度量不一致率。

## 复盘追问
- "部分用户旧价格 2 小时"如何定位是哪种时序？（提示：核对 TTL 与 2 小时的关系、缓存删除日志与 binlog 时间差、读者回填日志）
- 给"价格"这类数据设计一致性 SLA 时，你会承诺什么口径？（提示：承诺"不一致窗口 ≤ TTL/2 + CDC 延迟 P99"并配抽样对账告警，而不是承诺强一致）
