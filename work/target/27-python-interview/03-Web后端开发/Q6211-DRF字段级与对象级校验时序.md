### Q6211 · DRF 校验的执行时序：字段级 validate_<field> 与对象级 validate 的分层

难度：P6 ｜ 标签：DRF、validate_<field>、validate()、to_internal_value、序列化器时序、跨字段校验

**问**：DRF serializer 的 `validate_title`、`validate()`、字段声明的 `validators=[]` 三者按什么顺序执行？为什么对象级校验拿到的 `attrs` 是"字段级校验都通过之后"的数据？字段级校验抛出的异常和 `validate()` 抛出的异常在响应结构上有什么差别？部分更新（PATCH）时 `validate_<field>` 拿不到字段怎么办？

**答**：
结论：DRF 的反序列化链固定为：`to_internal_value()` 逐字段跑（每字段先执行声明式 `validators` → 再执行 `validate_<field>` 方法）→ 全部字段通过后，把清洗后的 `attrs` 整体交给对象级 `validate(attrs)` → 最后才进 `create()/update()`。分层含义：字段级校验只看**单字段值**（格式、范围、枚举），对象级校验拿**清洗后的组合状态**做跨字段约束（开始时间 < 结束时间、权限与角色组合合法性）——`validate()` 拿到的一定是"每个字段都已自洽"的数据，这让对象级规则不必重复字段级检查。异常结构差异：字段级错误聚成 `{field: [msg]}` 字典（ErrorDetail 列表），`validate()` 抛 `ValidationError` 默认归入 `non_field_errors`（可配置 `NON_FIELD_ERRORS_KEY`），响应形态从"哪字段错"退化为"整体错"——所以前端友好的跨字段错误要手动指定字段名：`raise serializers.ValidationError({"end_time": "..."})`。PATCH 场景：`validate_<field>` 只对**本次提交的字段**执行，缺失字段拿不到——需要旧值参与校验时要在 `validate()` 里结合 `self.instance` 的现有值。

取舍：a) 校验逻辑放哪层的判据：只依赖单字段值 → 字段级；需要两个字段以上或数据库状态 → 对象级；需要外部服务唯一性检查 → 唯一 `validators`（框架自带并发语义更准）或对象级；b) `validate()` 不要重复字段级校验——重复=两处维护、错误信息不一致；c) 对象级错误尽量映射回具体字段（返回 dict），全局兜底才用 non_field；d) PATCH 的"缺失字段"陷阱：`attrs.get("end_time", getattr(self.instance, "end_time", None))` 组合新旧值后再做跨字段判断；e) 别在 validate 里做写副作用（写库、发事件）——校验层必须可重入（唯一性校验并发窗口见 Q6186）。

实战：事故形态是"活动报名接口把'名额是否已满'写在 validate_title 里（字段级），PATCH 只改 title 的请求也会触发查库计数，高峰把名额表打挂；重构为：字段级只查格式，容量检查移到 validate() 且只在 attrs 涉及报名字段时执行，并加请求级缓存"。下面模拟执行时序。

```python
FIELDS = ["title", "start", "end"]


class FakeSerializer:
    validators_log = []

    def to_internal_value(self, data):
        attrs = {}
        self.validators_log.clear()
        for name in FIELDS:
            if name not in data:
                continue                                   # PATCH: 缺失字段跳过
            self.validators_log.append(f"declared:{name}")  # 声明式 validators 先跑
            getattr(self, f"validate_{name}", lambda v: v)(data[name])
            attrs[name] = data[name]
        return attrs

    def validate_title(self, value):
        self.validators_log.append("validate_title")
        if len(value) < 2:
            raise ValueError("title 太短")
        return value

    def validate(self, attrs):
        self.validators_log.append("object-validate")
        start, end = attrs.get("start", getattr(self, "inst_start", None)), attrs.get("end", getattr(self, "inst_end", None))
        if start and end and start >= end:
            raise ValueError({"end": "结束时间必须晚于开始时间"})   # 映射回具体字段
        return attrs


s = FakeSerializer()
s.validators_log.clear()
attrs = s.to_internal_value({"title": "活动A", "start": 1, "end": 2})
print("[1] 字段级时序:", s.validators_log)
try:
    s.validate(attrs)
except ValueError as e:
    print("[2] 对象级错误映射回字段:", e)

s2 = FakeSerializer()
s2.validators_log.clear()
try:
    s2.to_internal_value({"title": "x"})
except ValueError as e:
    print("[3] 字段级错误:", e, "| 已跑:", s2.validators_log, "——对象级未执行")
```

**追问一**：为什么 `validate()` 拿到的 attrs 一定是"字段级已通过"的？这个设计有什么代价？—— `to_internal_value` 的实现是逐字段 `field.run_validation()`，任何字段抛 `ValidationError` 都会立即终止并收集，根本到不了 `validate()`。收益是分层清晰、职责不重叠；代价是**信息更少**：对象级校验只拿到清洗后的值，看不到原始输入（如"哪个字段是用户显式提交的"）——PATCH 语义需要这个信息时要自己维护（对比 `self.initial_data` 的键）。另一个代价是错误结构不一致：字段级错误天然带字段名，对象级默认聚合为 non_field_errors，前端要写两套渲染逻辑。

**追问二**：声明式 `validators=[UniqueValidator, RegexValidator]` 与 `validate_<field>` 方法的分工边界？—— 声明式 validators 是**可复用组件**（带构造参数、可跨 serializer 共享、生成标准 OpenAPI 约束文档），方法式是**本 serializer 专属逻辑**（可访问 self 上下文）。选型原则：能参数化的规则（唯一性、正则、范围）用 validators；需要 self.instance/self.context 的规则用方法。危险组合是两处都写同一规则——修改时漏一处就是线上不一致；review 的固定检查项是"validate_<field> 里是否重复了 validators 已声明的能力"。

## 背诵要点
- 反序列化时序：to_internal_value 逐字段（validators → validate_<field>）→ 对象级 validate(attrs) → create/update。
- validate() 拿到的是字段级全通过后的组合数据；错误默认进 non_field_errors，友好做法是 raise ValidationError({字段: 消息})。
- PATCH 缺失字段不触发 validate_<field>，跨字段校验用 attrs.get + self.instance 组合新旧值。
