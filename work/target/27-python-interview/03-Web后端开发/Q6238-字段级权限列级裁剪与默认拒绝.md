### Q6238 · 字段级权限：列级裁剪、角色 ACL 与默认拒绝

难度：P6 ｜ 标签：字段级权限、列级裁剪、ACL、默认拒绝、序列化裁剪、数据最小化、BFF、脱敏

**问**：接口权限做到"行级"（Q790/Q6155）之后，为什么还需要"列级"——同一行数据，客服/运营/财务该看到的字段为何不同？字段 ACL 怎么设计——白名单按角色声明、默认拒绝语义、序列化层裁剪的实现位置？掩码（手机号 138****8000）与完全裁剪的语义差别？与 BFF 视图裁剪（Q1628）、日志脱敏（Q831）是什么分工关系？

**答**：
结论：行级权限回答"**这行数据你能看吗**"，列级权限回答"**这行里的哪些字段你能看**"——同一订单，客服看联系方式不能看佣金、财务看佣金不能看备注原文、运营看统计不能看任何个人身份字段（PII）。列级 ACL 的设计三原则：①**白名单 + 默认拒绝**——按角色显式声明可读字段集，未声明一律不给；反模式是黑名单（"敏感字段列表"永远列不全，新加字段默认泄露）；②**裁剪点在序列化层**——模型→响应的唯一出口处按 ACL 过滤，禁止"业务代码里各处手工 del"（散落裁剪必漏）；底层（DB/ORM）返回全量、出口统一裁，配合"敏感字段注册表"集中声明；③**掩码是降级展示不是裁剪**——手机号 138****8000 让业务可用性保留（客服能核对尾号），掩码规则与字段绑定（哪类字段怎么掩）也要进注册表；两者语义不同：裁剪=字段不存在（响应里没有），掩码=字段存在但降值，前端与下游依赖方要按两种语义分别处理。安全边界：列级 ACL 防"越权读字段"，但**查询单凭 ACL 不够**——聚合查询（sum/count）能绕过行级裁剪推断敏感值（差分攻击面），统计接口要独立的聚合权限。

取舍：a) ACL 的粒度与维护成本：角色×资源×字段三维矩阵爆炸——按"字段标签"（PII/财务/内部）分组授权而不是逐字段，声明量降一个量级；b) 性能：序列化层过滤是 O(字段数) 字典操作，可忽略；代价在"按 ACL 决定是否查询"的场景（无权限的敏感字段连 DB 都不该取——批量接口的列裁剪要下推到 SELECT 列表，Q6199 prefetch 家族）；c) 默认拒绝的配套：新角色上线默认无字段权限（显式授予），比"继承全部再收"安全；d) 与 BFF 分工：BFF 是**按端裁剪**（移动端少字段省流量，产品决策），ACL 是**按角色裁剪**（权限决策，安全决策）——两者可叠加但必须分层实现，把安全语义藏在 BFF 产品逻辑里是漏洞温床；e) 审计：敏感字段的实际读取（谁在什么时候读了佣金）要有读取审计，特别是掩码被"申请临时明文"的通道。

实战：事故形态是"订单详情接口为客服系统加了个 `detail=full` 参数返回全字段，上线后运营同学也用了这个参数看佣金——根因是字段裁剪散落在各视图函数，新入口忘记套 ACL；修复为序列化器统一按角色 ACL 裁剪（白名单+字段标签分组）+ 敏感字段注册表 + 聚合接口独立权限，'detail=full' 之类后门参数全量下线"。下面实测列级 ACL 裁剪器。

```python
# 字段级权限: 角色 ACL + 默认拒绝 + 序列化层裁剪
from dataclasses import dataclass, asdict

@dataclass
class Order:
    id: int
    customer_phone: str
    amount: float
    commission: float
    internal_note: str
    created_at: str

# 字段注册表: 字段 -> 敏感标签 (集中声明, 新字段必须登记)
FIELD_TAGS = {
    "id": "public", "created_at": "public",
    "customer_phone": "pii", "amount": "finance", "commission": "finance",
    "internal_note": "internal",
}
# 字段标签掩码规则 (掩码=降值展示, 区别于裁剪=字段不存在)
MASK_RULES = {"pii": lambda v: v[:3] + "****" + v[-4:] if len(v) > 7 else "****"}

# 角色 ACL: 允许的字段标签白名单 (未声明默认拒绝; 新角色零权限起步)
ROLE_ACL = {
    "support": {"public", "pii"},              # 客服: 联系方式可读, 不看佣金/内部备注
    "finance": {"public", "finance"},
    "ops": {"public"},                          # 运营: 统计字段, 无 PII 无财务
}

def serialize_for(order: Order, role: str, mask: bool = True) -> dict:
    """唯一出口: 按 ACL 白名单裁剪; 允许的敏感标签按需掩码"""
    allowed_tags = ROLE_ACL.get(role)
    if allowed_tags is None:                    # 未知角色: 默认拒绝, 一个字段都不给
        return {}
    out = {}
    for k, v in asdict(order).items():
        tag = FIELD_TAGS[k]
        if tag not in allowed_tags:
            continue                            # 裁剪: 响应中字段不存在
        if mask and tag in MASK_RULES:
            v = MASK_RULES[tag](v)              # 掩码: 字段存在但降值
        out[k] = v
    return out

order = Order(1001, "13812348000", 299.0, 45.0, "客户投诉物流慢", "2026-11-24T10:00:00Z")

print("[1] 三角色同一条订单, 字段集完全不同 (白名单+默认拒绝)")
for role in ("support", "finance", "ops", "unknown_role"):
    print(f"    {role:12} -> {serialize_for(order, role)}")

print("[2] 掩码 vs 裁剪: 掩码保留可用性 (尾号核对), 裁剪字段直接不存在")
full_support = serialize_for(order, "support")
print("    support 看到的手机号:", full_support["customer_phone"], "(掩码降值)")
print("    support 响应里没有 commission:", "commission" not in full_support, "(裁剪)")
print("    finance 不做掩码:", serialize_for(order, "finance", mask=False)["amount"], "(财务需要原值)")

print("[3] 反模式对照: 黑名单永远列不全, 新字段默认泄露")
def serialize_blacklist(order: Order, forbidden: set[str]) -> dict:
    return {k: v for k, v in asdict(order).items() if k not in forbidden}
new_leak = Order(1002, "13999990000", 1.0, 0.99, "note", "2026-11-24")
print("    黑名单漏了新字段 commission -> 泄露:", serialize_blacklist(new_leak, {"internal_note"}))

print("[4] 聚合绕过: 行级裁剪挡不住 sum/count 差分推断, 统计接口要独立聚合权限")
def aggregate(orders: list[Order], field: str, role: str) -> float | None:
    if role == "ops" and field == "commission":     # 无聚合权限: 拒绝而非返回 0
        return None
    return sum(getattr(o, field) for o in orders)
print("    ops 请求 sum(commission) ->", aggregate([order], "commission", "ops"), "(None=拒绝, 防差分推断)")

print("[5] 分工: BFF 按端裁剪(产品) / ACL 按角色裁剪(安全) / 日志脱敏(Q831)防出口泄漏 -- 分层叠加")
print("[6] 下推优化: 批量接口的列裁剪下推到 SELECT 列表, 无权限字段连 DB 都不取")
```

**追问一**："默认拒绝"在字段级权限里的落地难点是什么？新字段上线时怎么保证不漏配？—— 难点在**字段注册的生命周期管理**：①新增字段的流程强制卡点——ORM 模型字段必须先登记 FIELD_TAGS 才能进序列化器，未登记字段在 ACL 模式下"默认拒绝"天然不泄露（这正是白名单的好处：漏登记的结果是"不显示"而不是"泄露"——失败的默认方向是安全的）；②**测试兜底**——序列化器的单测断言"每字段在每角色下的期望可见性"，新增字段没更新 ACL 时测试红；③存量代码迁移期：全量断言日志（记录"被默认拒绝的字段访问"）跑一周，确认没有业务隐式依赖再收紧；④配置漂移防护——ROLE_ACL 进代码评审 + 变更审计，与"detail=full 后门参数"这类旁路做全局扫描清零。核心心智：默认拒绝把"安全默认"与"显式授权"分离，漏配的成本从"泄露事故"降为"功能缺失"，这是结构性优于黑名单的原因。

**追问二**：字段掩码的"反推"攻击面（部分掩码泄露哪些信息）与临时明文通道怎么治理？—— 掩码本身有信息泄露面：①**尾号+前缀**能被字典缩小（知道运营商号段规律，11 位手机号掩 4 位剩约 10^4 空间，配合外部数据可反推）；②**格式泄露**——掩码保住了长度与格式，攻击者可判断"这是手机号还是座机"；③**多源拼合**——同一用户在多个接口的掩码字段拼起来可能还原完整值（A 接口掩中 4 位、B 接口掩前 3 位，拼合得全号）——**跨接口掩码策略必须一致或更保守**（各源都掩到最少可辨识）。临时明文通道（客服"申请查看完整手机号"）的治理：申请走审批留痕（谁、何时、哪个客户、为什么）、明文展示有时效（会话级失效）、读取审计与异常检测（单人批量申请即告警）、掩码在前明文在后（默认掩码，明文是显式特权）。这类设计把"便利性与合规"的矛盾转化为"显式申请+审计闭环"的流程问题——与数据最小化原则（Q831 日志脱敏、Q1628 BFF 裁剪）同属一套治理框架。

## 背诵要点
- 行级管"这行能不能看"，列级管"哪些字段"；ACL 三原则：白名单+默认拒绝 / 序列化层唯一出口裁剪 / 掩码≠裁剪（降值 vs 不存在）。
- 字段注册表 + 标签分组授权（PII/finance/internal）降低矩阵爆炸；新字段漏登记的方向是"不显示"（白名单结构性安全）。
- 聚合查询能差分推断绕过行裁剪，统计接口要独立聚合权限；跨接口掩码策略一致防拼合反推；临时明文走审批留痕+时效。
