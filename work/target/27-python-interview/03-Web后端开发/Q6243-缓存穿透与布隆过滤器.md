### Q6243 · 缓存穿透与布隆过滤器：负缓存、位图预算与误判率账

难度：P6 ｜ 标签：缓存穿透、布隆过滤器、负缓存、误判率、Kirsch-Mitzenmacher、双哈希、bitmap、击穿对比、缓存三件套

**问**：缓存穿透与击穿（Q6066）、雪崩（Q6246）的区分边界是什么——"查不存在的 key"为什么会打穿到存储？布隆过滤器的工作原理与误判率公式、位数组与哈希函数数怎么算预算？"过滤器说存在但缓存/DB 都没有"的假阳性怎么处理？与负缓存（空值缓存）的选型对比？

**答**：
结论：缓存三件套的分野：**击穿**=热 key 过期瞬间并发回源（单飞合并治，Q6066）；**雪崩**=大批 key 同时失效/缓存层整体不可用（抖动 TTL+多级兜底治，Q6246）；**穿透**=**查的数据在存储里根本不存在**（恶意 ID 扫描、过期数据、伪造参数）——每次都"缓存 miss → DB miss"，缓存层形同虚设，DB 被"无效查询"打满。穿透的根因是"**不存在**这个事实本身不可缓存"——传统缓存只存"存在的数据"，防线是让"不存在"也变得可判定、可缓存：①**负缓存**——DB miss 后往缓存写"空值标记"（短 TTL，如 60s），下次同 key 直接命中空标记返回 404——实现最简单，但对**海量随机 key 的攻击**（每次 key 都不同）无效：负缓存被垃圾 key 塞满、命中率接近 0；②**布隆过滤器**——把"合法 key 集合"压进一个位数组：插入时用 k 个哈希函数把 key 映射到 k 个位并置 1；查询时 k 个位全为 1 才"可能存在"，**任一位为 0 则"一定不存在"**（位数组只增不改删）。把它放在缓存查询之前：过滤器说"不存在"直接拒绝（微秒级、不碰缓存不碰 DB）——**这是穿透防御的核心闸门**；假阳性率公式 `p ≈ (1 - e^(-kn/m))^k`（n=元素数、m=位数组大小），给定目标 p 与预期 n 可反解最优 k 与 m。误判的后果是"假阳性 key 走正常查询路径"——**只是浪费一次查询，不会返回错数据**（DB miss 后补写负缓存），这是布隆"宁可放过不可冤枉"的单向安全。

取舍：a) 预算账：n=1 亿用户、目标 p=1% → k≈7、m≈9.6bit/元素 ≈ 114MB 位数组——单机内存可承载，Redis bitmap 分片也行；p 要按业务容忍度定（1% 假阳性 = 1% 的穿透流量漏过闸门，配合负缓存兜住）；b) 删除问题：布隆不支持删除（置 0 会误伤共享位）——需要删除语义用**计数布隆/Cuckoo 过滤器**，或定期全量重建（数据集稳定的场景重建成本可控）；c) 数据一致性：新注册用户要**同步**加入过滤器（DB 写入与过滤器更新的事务边界——过滤器超前无害[假阳性]、滞后有害[新用户被误判不存在]），滞后窗口用"过滤器 miss 但 DB 命中 → 自动回补过滤器"修复；d) 与负缓存组合的标准链路：布隆闸门（不存在→直接拒）→ 缓存（命中返回）→ 负缓存（空标记短 TTL）→ DB（命中后回填缓存+过滤器）——四层各司其职；e) 布隆的适用前提：**key 集合可枚举且过滤方向固定**（"存在性"判定），海量动态 key 的公开 API 更适合负缓存+限流（Q139），别为了炫技上布隆。

实战：事故形态是"秒杀接口被脚本用随机 `goods_id` 扫描，缓存命中率 0%，DB 每秒 4 万次无效主键查询；先上负缓存——攻击 key 每次都变，负缓存命中率 0.3% 无效。终态：商品 id 布隆过滤器（300 万 SKU、p=0.5%、约 2.6MB 位数组常驻进程内）+ 命中假阳性回补负缓存 + 攻击 IP 限流，DB 无效查询归零。另一个坑：新建商品忘了加过滤器，上线 10 分钟内新商品被拒——补'过滤器 miss 但 DB 命中自动回补'的修复路径"。下面实现布隆过滤器并实测误判率与穿透防御链路。

```python
# 缓存穿透: 布隆过滤器 + 负缓存的防御链路
import hashlib

class Bloom:
    """教学版布隆: 位数组 + Kirsch-Mitzenmacher 双哈希派生 k 个位置"""

    def __init__(self, m_bits: int, k: int) -> None:
        self.m = m_bits
        self.k = k
        self.bits = bytearray((m_bits + 7) // 8)
        self.n = 0

    def _positions(self, item: str):
        h1 = int(hashlib.md5(item.encode()).hexdigest(), 16)
        h2 = int(hashlib.sha1(item.encode()).hexdigest(), 16)
        for i in range(self.k):
            yield (h1 + i * h2 + i * i) % self.m        # 双哈希派生, 省一次哈希成本

    def add(self, item: str) -> None:
        self.n += 1
        for pos in self._positions(item):
            self.bits[pos // 8] |= 1 << (pos % 8)

    def __contains__(self, item: str) -> bool:
        return all(self.bits[pos // 8] >> (pos % 8) & 1 for pos in self._positions(item))

print("[1] 布隆语义: 说'不存在'则一定不存在; 说'存在'可能是假阳性")
bloom = Bloom(m_bits=32768, k=3)      # m/n = 16.4 bit/元素
skus = [f"sku-{i}" for i in range(2000)]
for s in skus:
    bloom.add(s)
print("    已录入 2000 个 SKU; 已知 SKU 全部判定存在:", all(s in bloom for s in skus[:500]))

print("[2] 误判率实测: 探测 5000 个不存在 key")
false_pos = sum(1 for i in range(5000) if f"sku-{10000 + i}" in bloom)
print(f"    假阳性 {false_pos}/5000 = {false_pos / 50:.2f}% (理论 (1-e^(-kn/m))^k ≈ 0.5%)")

print("[3] 防御链路: 布隆闸门 -> 缓存 -> 负缓存 -> DB")
class Cache:
    def __init__(self) -> None:
        self.kv: dict = {}
        self.neg: set = set()

    def get(self, key):
        if key in self.neg:
            return "NEGATIVE"                          # 负缓存命中: 不碰 DB
        return self.kv.get(key)

    def put_negative(self, key):
        self.neg.add(key)

db_hits = 0

def get_goods(gid: str):
    global db_hits
    if gid not in bloom:                               # 第一层: 布隆说不存在 -> 一定不存在
        return 404, "布隆闸门直接拒绝 (0 缓存 0 DB)"
    val = cache.get(gid)                               # 第二层: 缓存/负缓存
    if val == "NEGATIVE":
        return 404, "负缓存命中 (假阳性漏网, 不再打 DB)"
    if val is None:
        db_hits += 1
        db_val = db.get(gid)                           # 第三层: DB (教学替身)
        if db_val is None:
            cache.put_negative(gid)                    # DB miss -> 补负缓存 (假阳性止损)
            bloom.add(gid)                             # 回补过滤器 (数据一致性)
            return 404, "DB miss -> 写负缓存 + 回补布隆"
        cache.kv[gid] = db_val
        return 200, db_val
    return 200, val

cache = Cache()
db = {f"sku-{i}": f"goods-{i}" for i in range(2000)}

for probe in ("sku-5", "sku-99999999", "sku-88888888", "sku-5"):
    code, why = get_goods(probe)
    print(f"    GET {probe:<14} -> {code}  {why}")
print(f"    无效请求的 DB 触达次数: {db_hits} (没有布隆时每次都是一次 DB 查询)")

print("[4] 预算公式: p=1% 时 m ≈ 9.6 bit/元素, k ≈ 7")
print("[rule ] 布隆管'集合存在性'且不可删; 新数据同步入滤镜+miss 回补; 与负缓存/单飞组成穿透防线")
```

**追问一**：布隆的 k 个哈希为什么用"双哈希派生"（h1 + i·h2）而不是真的算 k 次？位数组取模的位运算细节展开讲讲？—— 真算 k 个独立哈希的成本是 k 次 hashlib 调用（每次都是 full hash pass）；Kirsch-Mitzenmacher（2006）证明用两个哈希线性组合 `g_i(x) = h1(x) + i·h2(x) + i²` 生成的 k 个位置在误判率上与独立哈希几乎无差——**一次 MD5 + 一次 SHA1 换 k 个位置**，布隆的 CPU 成本从 O(k) 哈希降到 O(2)。位数组操作：`pos // 8` 定位字节、`pos % 8` 定位位、`bits[byte] |= 1 << (bit)` 置位（set）、`bits[byte] >> bit & 1` 读位（test）——Python bytearray 上这些是 O(1) 整数操作，但**位级操作在纯 Python 里比 C 扩展慢百倍**，生产用 Redis `SETBIT/GETBIT`（服务端 C 实现）或 pybloom/bloom-filter2 库（C 加速）。哈希选择注意：hashlib 的 md5/sha1 速度足够且分布均匀；**禁用内建 hash()**——PYTHONHASHSEED 随机化让跨进程/跨重启的位数组不一致（Q5065/Q535 的坑），布隆的哈希必须是确定性的。

**追问二**："过滤器更新与 DB 写入的一致性"有哪些工程形态？"定期重建"的窗口期内服务怎么办？—— 一致性形态：①**双写同步**——DB 事务提交后同步加滤镜（简单，但滤镜故障会拖 DB 写入链路——滤镜侧只做内存置位，故障面极小）；②**事务后异步**——binlog/CDC 订阅驱动滤镜更新（与缓存失效同一管道，Q6049 双写一致性的滤镜版），有毫秒级滞后窗口；③**miss 回补兜底**——查询路径上"布隆说不存在但 DB 查到了"（说明滤镜滞后）→ 立即回补滤镜 + 告警计数（回补频次是滤镜健康度指标）。滞后窗口的语义安全性：滤镜滞后 = 新数据被误判不存在 = **新用户/新商品暂时 404**——业务上通常可容忍秒级（配合客户端重试），比"滤镜超前"（假阳性，只是一次 DB 查询）危害大，所以**更新方向宁多勿漏**。重建形态：滤镜只支持"加"，撤销数据（下架 SKU 删除）会残留假阳性位——定期全量重建（离线扫全表重建新位数组 → 原子切换引用，Q1603 的原子替换同思路）；切换窗口用双滤镜并存：查询先查新滤镜，miss 再查旧滤镜（旧滤镜的假阳性照常走 DB 路径）——重建期间不产生"误判不存在"。

## 背诵要点
- 穿透=查不存在的 key 打穿缓存层；防线链路：布隆闸门（说不存在则一定不存在）→ 缓存 → 负缓存（空标记短 TTL）→ DB（miss 后补负缓存+回补滤镜）。
- 布隆预算：误判率 p≈(1-e^(-kn/m))^k，p=1% 时 m≈9.6bit/元素、k≈7；双哈希派生（h1+i·h2+i²）省 k 次哈希；哈希必须确定性（禁内建 hash()，PYTHONHASHSEED 随机化坑）。
- 一致性方向：滤镜滞后=新数据误判 404（危害大），超前=假阳性多一次 DB 查询（无害）——更新宁多勿漏 + miss 回补 + 定期全量重建原子切换。

## 复盘追问
- 布隆说存在但缓存与 DB 都没有怎么办？（假阳性：走正常查询路径，DB miss 后补负缓存止损——布隆单向安全，不会返回错数据）
- 负缓存为什么挡不住大规模随机 key 攻击、布隆为什么行？（负缓存被海量不同 key 塞满命中率趋零；布隆把"不存在"判定压进固定大小位数组，与 key 数量无关的微秒级拒绝）
