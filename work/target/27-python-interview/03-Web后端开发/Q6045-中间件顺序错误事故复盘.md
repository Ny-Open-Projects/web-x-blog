### Q6045 · 中间件顺序错误的事故复盘

> 难度:★★★☆ | 标签:中间件, 事故复盘, ASGI, 异常处理

**问**：一次事故：接入统一异常处理中间件后，CORS 响应头在 500 错误时消失，前端把所有服务端错误当网络故障重试，引发重试风暴。中间件注册顺序与"洋葱模型"的执行语义到底是什么？哪些顺序约束是硬性的？如何系统性 review 中间件栈？

**答**：ASGI/Starlette 中间件是洋葱模型：**后注册的包在外层**（`add_middleware` 每次把现有 app 包一层，最后加的最先处理请求、最后处理响应）。事故机制：异常处理中间件如果加在 CORS 外层（后注册），它捕获内层异常后自己生成 500 响应返回，这条响应**不会再经过内层的 CORS 中间件**——CORS 头只在"正常路径"存在，错误路径裸奔，浏览器按同源策略拦截响应体，前端只见"网络错误"→ 重试 → 风暴。硬性顺序约束清单：1) **CORS 必须在最内层附近**（最先注册），让包括错误在内的所有响应都带头；2) **异常处理在最外层**，兜住一切中间件的异常；3) **认证在请求体解析/业务中间件之前**（避免 401 还在解析 body，Q731 的读体问题反向踩坑）；4) **trace/request-id 中间件尽量靠外**，保证错误响应也带 trace 头；5) gzip/限流等与顺序相关的语义（先限流后压缩 vs 先压缩后限流的成本差异，Q6011/Q2437）。Review 方法：把中间件栈画成洋葱图核对"每个中间件的响应路径是否被内层短路"；单测必须覆盖**错误路径的响应头断言**（不只测 200）；变更中间件顺序要像改 DB schema 一样走评审。

```python
# file: code/03-Web后端开发/q6045_middleware_order.py
"""标准库模拟 ASGI 洋葱模型, 复现 CORS 头在错误路径消失的事故"""

def cors_middleware(app):
    async def handler(scope, receive, send):
        await app(scope, receive, send)
        # 响应头注入发生在调用 app 之后 -> 内层异常被外层兜住时不会经过这里
        print("  [cors] 注入 Access-Control-Allow-Origin")
    return handler

def error_middleware(app):
    async def handler(scope, receive, send):
        try:
            await app(scope, receive, send)
        except RuntimeError as e:
            print(f"  [error] 兜住异常生成 500 响应: {e}")
            # 注意: 这条 500 不再经过内层 cors 的"响应后注入"
    return handler

def biz_app(scope, receive, send):
    async def call():
        print("  [biz] 抛出异常!")
        raise RuntimeError("db down")
    return call()

# 事故栈: error 后注册 -> 在外层, cors 在内层
inner_stack = cors_middleware(biz_app)
bad_stack = error_middleware(inner_stack)
print("事故顺序: 外层 error -> 内层 cors")
import asyncio
asyncio.run(bad_stack({}, None, None))
print("  -> 500 响应没有 CORS 头, 前端按网络故障重试")

# 修复栈: cors 后注册 -> 在外层, 所有响应(含 500)都带头
fixed_stack = cors_middleware(error_middleware(biz_app))
print("修复顺序: 外层 cors -> 内层 error")
asyncio.run(fixed_stack({}, None, None))
print("  -> 500 响应也带 CORS 头")

# 硬性约束核对表
RULES = [
    "cors: 最先注册(内层), 覆盖错误路径",
    "error: 最后注册(外层), 兜住一切",
    "auth: 在 body 解析之前, 401 不读体",
    "trace/request-id: 尽量靠外, 错误响应也带 trace",
]
for r in RULES:
    print("规则:", r)
```

**追问**：1) 为什么异常处理中间件"生成响应"而不是"让内层响应继续"？——ASGI 里 send 消息序列只能走一次，异常已经中断了内层的响应流程，外层只能自己发完整响应；因此外层兜底者必须**自己负责补齐跨切面响应头**（或把 CORS 做成"响应起始消息改写"式外层）。2) BaseHTTPMiddleware 与纯 ASGI 中间件的顺序语义有差异吗？——BaseHTTPMiddleware 内部再用一层 app 包装，异常传播路径多一层（且历史版本有吞异常/背景任务问题），纯 ASGI 中间件语义可预测，复杂切面建议纯 ASGI。3) 如何在 CI 里锁住中间件顺序？——启动时断言中间件栈的注册顺序（对 app 包装层数与类型断言），并加"错误路径响应头"契约测试。

## 背诵要点
- ASGI 洋葱：后注册在外层，先处理请求、最后处理响应；外层异常兜底的 500 不经过内层响应注入。
- 硬顺序：CORS 最内层、异常最外层、auth 先于 body 解析、trace 尽量靠外。
- Review 用洋葱图核对"响应路径短路"；CI 断言注册顺序 + 错误路径响应头契约测试。

## 复盘追问
- 排查"CORS 头时有时无"这类间歇性问题，你的第一步是什么？（提示：先区分状态码——200 有头、500 无头即是顺序问题；用 curl 直打错误路径验证）
- 新增一个"统一错误页"中间件时，你如何评估它对现有栈每个中间件的影响？（提示：对洋葱图逐层问"它的响应注入是否会被我短路"，必要时把头注入上移到外层）
