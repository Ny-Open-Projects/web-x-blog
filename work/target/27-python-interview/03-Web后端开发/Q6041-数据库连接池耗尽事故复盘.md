### Q6041 · Web 服务数据库连接池耗尽的事故复盘

> 难度:★★★★ | 标签:连接池, 事故复盘, 慢查询, 超时

**问**：一次事故：一个慢查询把 P99 从 200ms 拖到 5s，随后全站 500，报错全是 "connection pool exhausted"。连接池耗尽的完整事故链是什么？为什么"加池子"是错误的第一个动作？正确的分层修复是什么？

**答**：事故链四步：1) 某查询变慢（索引失效/锁等待）→ 每请求持有连接时长 ×20；2) 并发请求按到达速率继续取连接，池被占满；3) 后续请求进入"等连接"队列，等池超时抛 PoolTimeout（或无限等待直接挂住 worker）；4) worker 全部卡在等连接 → 线程/协程耗尽 → 健康检查也 500，故障从"一个慢查询"放大成"全站不可用"。为什么不能先加池子：池大小只是**缓冲**，慢查询不变时耗尽只是推迟，且把连接压力转嫁给 DB（`max_connections` 打满 → 数据库自身雪崩），故障面反而更大。分层修复按优先级：1) **语句级超时**：`statement_timeout`/`SET LOCAL` 级别限定慢查询，让"慢"快速失败而不是无限持锁；2) **池等待超时**：`pool_timeout`（如 5s）必须存在并小于上游请求超时，失败快速返回 503；3) **慢查询治理**：pg_stat_statements/慢日志定位 + 索引修复（Q838）；4) **容量配比**：池大小 = worker 数 × 每 worker 并发，总和 < DB max_connections 的安全份额（Q6046 展开）；5) 熔断/舱壁：慢依赖隔离到独立池（Q1876）。复盘关键观测：请求 P99 与连接持有时长曲线对齐、PoolTimeout 计数、DB active connections。

```python
# file: code/03-Web后端开发/q6041_pool_exhaustion.py
import queue
import threading
import time

class FakePool:
    """模拟连接池: size=5, 等待超时 0.2s"""
    def __init__(self, size=5, timeout=0.2):
        self.free = queue.Queue(maxsize=size)
        for _ in range(size):
            self.free.put(f"conn-{_}")
        self.timeout = timeout
        self.timeouts = 0
        self.lock = threading.Lock()

    def execute(self, latency):
        try:
            conn = self.free.get(timeout=self.timeout)   # 池等待超时
        except queue.Empty:
            with self.lock:
                self.timeouts += 1
            return "503 PoolTimeout"                     # 快速失败
        time.sleep(latency)                              # 查询执行
        self.free.put(conn)
        return "200"

def load_test(pool, n_req, latency, label):
    res = {"200": 0, "503 PoolTimeout": 0}
    def call():
        r = pool.execute(latency)
        res[r] += 1
    ts = [threading.Thread(target=call) for _ in range(n_req)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    print(f"{label}: 池超时 {res['503 PoolTimeout']}/{n_req} "
          f"| 成功 {res['200']} | 耗时 {(time.perf_counter()-t0)*1000:.0f} ms")

if __name__ == "__main__":
    load_test(FakePool(size=5, timeout=0.2), 20, 0.02, "正常(20ms 查询)")   # 池够用
    load_test(FakePool(size=5, timeout=0.2), 20, 0.5, "慢查询(500ms)")      # 耗尽: 大量 503
    # 修复演示: 语句超时(50ms 上限)让慢查询快速失败, 池周转恢复
    load_test(FakePool(size=5, timeout=0.2), 20, 0.05, "语句超时 50ms 修复")
    print("错误动作: 先把池从 5 加到 50 -> 只推迟耗尽并把压力转嫁给 DB max_connections")
```

**追问**：1) 为什么 pool_timeout 必须小于上游（网关/前端）超时？——若等池 30s 而网关 10s 就放弃，等池的请求注定白等：白白占用 worker 与连接预算，还把超时压力逐层上传；预算逐层递减（Q6019）。2) SQLAlchemy 里 `pool_pre_ping` 与耗尽事故有什么关系？——它解决的是"连接已被 DB 侧杀掉"（wait_timeout/网络抖动）的另一种池错误，与耗尽是两类问题；耗尽看 wait/overflow 指标，失效看 pre_ping 触发率。3) 慢查询限流（对特定 SQL 模式限并发）怎么做才不误伤？——按查询指纹聚合计数、设并发上限与排队超时，白名单核心查询；要配灰度观测。

## 背诵要点
- 耗尽事故链：慢查询 → 连接持有变长 → 池满 → 等池队列堵死 worker → 全站 500。
- 加池只是缓冲且转嫁 DB 压力；先上语句超时 + pool_timeout（小于上游超时）快速失败。
- 观测：连接持有 P99、PoolTimeout 计数、DB active connections 三曲线对齐即定位。

## 复盘追问
