### Q6154 · 请求头膨胀与 431 的容量账

难度：P6 ｜ 标签：HTTP 头、431、large_client_header_buffers、容量规划

**问**：请求头有没有大小上限？一次"个别用户 431 Request Header Fields Too Large"的事故里，头膨胀的常见来源（巨型 Cookie、长 JWT、营销埋点参数）如何定位？nginx 的 `large_client_header_buffers`、HTTP/2 的 SETTINGS_MAX_HEADER_LIST_SIZE、Python 侧（http.client/h11）各自的限制与容量账怎么算？

**答**：
结论：头大小上限**没有协议全局默认**，是各实现自设：nginx 默认单 buffer 8KB（`large_client_header_buffers 4 8k`，一行超限或总超限即 431）；HTTP/2 用 SETTINGS 帧协商 `SETTINGS_MAX_HEADER_LIST_SIZE`（默认无强制，实现常取 16KB–64KB）；Python `http.client` 限响应头行数（100 行）与单行 64KB；h11/uvicorn 类似。膨胀来源按频率：① **Cookie 累积**（每个子系统塞一个 cookie，多年累积几 KB 到几十 KB，最容易爆）；② JWT 长令牌（嵌套角色/权限塞进 claims，几十 KB）；③ 营销追踪参数经跳转复制进 cookie。事故复盘法：抓 431 的请求样本看头分布（通常一个 cookie 值 > 4KB），定位写入方；短期清洗（服务端 Set-Cookie 过期旧项）+ 长期把大状态从 Cookie 挪到服务端会话/专用头。

取舍：容量账三层——传输（每请求多传 KB × QPS = 带宽成本，头不做压缩时 HTTP/1.1 裸传）、内存（每连接解析缓冲按最大头预留，万级连接 × 32KB = 数百 MB，这就是连接数容量账的一部分）、失败率（超限 431 直接丢失用户）。治理优先级：先减量（Cookie 白名单化、JWT 瘦身到引用型 opaque token），再调大缓冲（治标，把内存账放大到所有连接）。

实战：观测指标：P99 请求头字节数、按 header 名的字节分布（可从反代日志采样）、431 率；变更门禁要求"新增 cookie/头 > 1KB 必须评审"。HPACK 头压缩只在 HTTP/2 连接内有效且依赖前后文，跨请求重复头（cookie）省传输但首请求仍全量。

```python
import http.client, threading
from http.server import BaseHTTPRequestHandler, HTTPServer

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        total = sum(len(k) + len(v) for k, v in self.headers.items())
        body = f"headers={len(self.headers.items())} total={total}B".encode()
        self.send_response(200)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
    def log_message(self, *a): pass

srv = HTTPServer(("127.0.0.1", 0), Handler)
port = srv.server_address[1]
threading.Thread(target=srv.serve_forever, daemon=True).start()

# 1) 头膨胀画像：模拟多年累积的 Cookie
cookies = "; ".join(f"tracker{i}={'v' * 120}" for i in range(40))   # ~5KB Cookie
conn = http.client.HTTPConnection("127.0.0.1", port, timeout=3)
conn.request("GET", "/", headers={"Cookie": cookies, "X-Metrics": "y" * 9000})
r = conn.getresponse()
print("server saw:", r.read().decode())
conn.close()

# 2) http.client 侧的限制：响应头行数上限（_MAXHEADERS=100）
print("http.client _MAXHEADERS:", http.client._MAXHEADERS,
      " _MAXLINE:", http.client._MAXLINE, "B/行")

# 3) 头容量账：带宽与连接内存
qps = 5_000
cookie_kb = len(cookies) / 1024
print(f"bandwidth cost: {cookie_kb:.1f}KB x {qps}qps = {cookie_kb * qps / 1024:.1f}MB/s 仅 Cookie")
conns, buf_per_conn = 10_000, 16 * 1024
print(f"header buffer memory: {conns} conn x {buf_per_conn//1024}KB = {conns * buf_per_conn // 1024 // 1024}MB")
srv.shutdown()
```

**追问一**：为什么 nginx 要把"单行超限"和"总超限"都查（而不是只查总大小）？——单行超限通常是畸形请求或恶意构造（长 URI、长头注入攻击面），语义与"合法但膨胀"不同；区分两者便于把 414（URI Too Long）与 431 分开归因，也便于对不同来源设置不同白名单。

**追问二**：HTTP/2 的 HPACK 让重复头"传输变便宜"了，服务器内存账反而怎么变化？——HPACK 需要连接级解码表（动态表），每连接常驻状态增加；头越大/越多样，动态表占用与解码 CPU 越高，且 SETTINGS_MAX_HEADER_LIST_SIZE 只是保护服务器不被无限头打爆——传输省了，**每连接内存上界没有降**，高并发连接数容量规划仍按最大头预留。

## 背诵要点
- 头上限是实现自设：nginx 单 buffer 默认 8KB（超限 431）、HTTP/2 SETTINGS 协商、http.client 100 行/64KB 每行。
- 膨胀三源：Cookie 累积、巨型 JWT、营销参数；定位靠头字节分布采样，治理先减量（Cookie 白名单/JWT 瘦身）再调缓冲。
- 容量账：带宽（头字节 × QPS）+ 连接内存（解析缓冲 × 连接数）+ 431 失败率，三者都要进指标。
