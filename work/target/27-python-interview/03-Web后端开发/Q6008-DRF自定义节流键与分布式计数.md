### Q6008 · DRF 自定义节流键与分布式计数

> 难度:★★★ | 标签:DRF 3.14+, 限流, Redis 6-7

**问**：DRF 自定义节流维度怎么写？`SimpleRateThrottle` 默认计数在多 worker/多实例下为什么不可信？正确的分布式计数怎么做？

**答**：自定义节流两步：继承 `SimpleRateThrottle`，设 `scope` 并重写 `get_cache_key` 把维度拼进键（如 `tenant:{id}:user:{id}:ip:{ip}`）；键来源要用**已认证身份优先、伪造头不可信**——从 `request.headers["X-Forwarded-For"]` 取 IP 必须经过信任代理链裁剪，否则攻击者换一个伪造头就绕过限流。多 worker 失效的原因：`SimpleRateThrottle` 的历史窗口用 `cache.get/put` 实现，是**非原子的读-改-写**——两个请求同时读到计数 9，都判定放行，实际并发超限；locmem 缓存还按进程各存一份，4 个 worker 等于限流阈值 ×4。正确姿势：Redis 原子 `INCR` + 首次 `EXPIRE`（incr 后返回值 ==1 时才设 TTL，否则每次请求都续期、窗口永远清不了零）；要求更平滑则用 Redis+Lua 实现滑动窗口或令牌桶（一次脚本调用内完成读写，天然原子）。大租户热点可用分桶：`key#{0..N}` 随机写、读取求和，牺牲一点精度换热点分散。

```python
# 基线:Django 4.2+/DRF 3.14+/Redis 6-7。缺库降级:标准库模拟 INCR+EXPIRE,并演示非原子计数的竞态。
import threading, time

# --- 降级/原理演示:非原子 check-then-act 的竞态 ---
counter, hits, lock_none = {}, {"allowed": 0}, threading.Lock()
def bad_allow(key, limit):
    """读-判断-写,非原子:并发下超放(读后留出切换窗口,模拟真实并发交错)"""
    val = counter.get(key, 0)
    time.sleep(0.001)          # 读-写之间的空窗:另一个线程同时读到同一计数值
    ok = val < limit
    counter[key] = val + 1
    return ok

def race(n, limit=5):
    counter.clear(); results = []
    def req():
        if bad_allow("k", limit): results.append(1)
    ts = [threading.Thread(target=req) for _ in range(n)]
    [t.start() for t in ts]; [t.join() for t in ts]
    print(f"非原子计数:{n} 并发 / 限 {limit} → 实际放行 {len(results)}(超放 {len(results)-limit})")

race(50)

# --- 正确姿势:原子 INCR + 首次 EXPIRE(Redis 伪码,标准库字典模拟原子段) ---
atomic_counter, ttl_flag = {}, {}
atomic = threading.Lock()
def incr_with_ttl(key, window_s):
    with atomic:                       # Redis: pipeline(INCR, 若==1 则 EXPIRE)
        v = atomic_counter.get(key, 0) + 1
        atomic_counter[key] = v
        if v == 1: ttl_flag[key] = window_s   # 只有首个请求设 TTL,防止窗口被无限续期
    return v

print(f"原子 INCR 演示: 3 次调用 → {[incr_with_ttl('k', 60) for _ in range(3)]},TTL 只在第一次设置")

# --- 真实 DRF 写法(需 django+djangorestframework+redis) ---
DRF_SNIPPET = """
class TenantThrottle(SimpleRateThrottle):
    scope = "tenant"
    rate = "100/min"
    def get_cache_key(self, request, view):
        ident = getattr(request.user, "pk", None) or self.get_ident(request)  # 认证身份优先
        return f"throttle:tenant:{request.headers.get('X-Tenant', 'default')}:{ident}"
# allow_request 内部用 cache.get/put —— 非原子;替换为:
# def allow_request(self, request, view):
#     key = self.get_cache_key(request, view)
#     n = redis.incr(key)                # 原子自增
#     if n == 1: redis.expire(key, 60)   # 首次才设 TTL
#     return n <= 100
"""
print("DRF 参考(需 pip install django djangorestframework redis):")
print(DRF_SNIPPET)
```

**追问**：
1) INCR+EXPIRE 为什么「incr 后 ==1 才设 TTL」？——若每次都 EXPIRE，只要有持续请求键就永不过期，固定窗口退化成「永不重置的累计计数」；同时两步非原子可能产生无 TTL 键（INCR 后进程崩在 EXPIRE 前），生产用 Lua/`SET NX EX` 变体把两步做成一次原子调用。
2) 固定窗口 vs 滑动窗口在分布式下的实现差异？——固定窗口就是 INCR+TTL，成本低但窗口边界可突发 2 倍（前窗尾+后窗头）；滑动窗口要 `ZSET` 按时间戳记成员、ZREMRANGEBYSCORE 清窗、ZCARD 计数，成本高但平滑。网关级限流常取折中：固定窗口 + 令牌桶平滑。
3) get_cache_key 返回 None 会怎样？——DRF 跳过该请求的节流（视为不限流对象），所以「未登录/无法识别」路径要么显式给匿名键（IP），要么明确豁免并写进设计文档，返回 None 绝不能是无意的兜底。
