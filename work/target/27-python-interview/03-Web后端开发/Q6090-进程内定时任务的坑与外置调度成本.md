### Q6090 · 进程内定时任务的坑与外置调度的成本账

难度：★★★★☆ ｜ 标签：成本工程 / 定时任务 / APScheduler / 多副本

**问**：把"每小时结算"的 cron 挪进 Web 进程（APScheduler）后，K8s 扩到 4 副本，结算被跑了 4 遍。进程内定时任务到底有哪些坑？"外置调度"的架构成本怎么算？

**答**：
- **结论**：进程内定时（APScheduler/threading.Timer/asyncio 的 call_later）的三个结构问题：① **多副本重复执行**——每个进程都有自己的调度器，没有全局锁就是 N 副本 N 遍；② **生命周期耦合**——worker 重启/滚动发布时任务丢或中断（优雅停机不等待定时任务，Q6074），内存态队列无持久化；③ **资源耦合**——定时任务与请求流量抢同一 worker 的 CPU/线程池，慢任务拖垮在线请求。正解方向：**执行与触发分离**——触发由单点（K8s CronJob / 数据库行锁 / Redis 分布式锁 / 外部调度器）决定，执行可以是幂等 worker。临时救急方案是分布式锁（SET NX + TTL + fence token），但要接受"锁过期双跑"的残余风险，幂等才是根治。
- **取舍**：成本对比：进程内调度 = 0 部署成本 + 上述三坑；K8s CronJob = 单点天然正确 + 只能分钟级粒度 + 每次起 pod 的冷启动（Python 依赖镜像冷启动 10s+）；常驻外置调度器（自研/APScheduler 单实例 Deployment）= 灵活 + 要自己解决它的单点与可观测。选型口诀：**分钟以上粒度、强可靠 → K8s CronJob；秒级/动态任务 → 常驻调度器 + 持久化任务表；与请求同生命周期的小任务（如缓存刷新）才允许进程内，且必须幂等 + 锁兜底**。
- **实战**：复盘清单：1）结算接口加幂等键（周期 + 业务周期号），重复调用返回同结果；2）分布式锁的 TTL 必须 > 任务 P99 时长 + 续期能力（否则长任务中途锁过期被第二个实例抢走）；3）定时任务可观测：每任务一条执行记录表（开始/结束/结果/耗时），重复执行在表上直接可见。

```python
"""多副本重复执行的复现与分布式锁兜底（标准库 threading.Timer 演示）"""
import threading, time, random

# 1) 事故复现：4 个"副本"（进程内调度器）各自触发同一任务
run_log = []
def settle():
    run_log.append(f"run@{threading.get_ident()}")

def in_process_scheduler(periodic_fn):
    """每个 Web 进程都有这么一个调度器 → N 副本跑 N 遍"""
    t = threading.Timer(0.05, periodic_fn)
    t.start()
    return t

threads = [in_process_scheduler(settle) for _ in range(4)]   # 模拟 4 副本
for t in threads: t.join()
print(f"无协调时执行次数: {len(run_log)}（期望 1，实际 = 副本数）")

# 2) 分布式锁兜底（Redis SET NX 的纯 Python 模拟）
class FakeRedis:
    def __init__(self): self.store = {}
    def set(self, key, val, nx=False, ex=None):
        if nx and key in self.store:
            return False
        self.store[key] = val
        return True
    def delete(self, key): self.store.pop(key, None)

rds = FakeRedis()
LOCK, TOKEN = "lock:settle", "token-abc"

def acquire_lock():
    return rds.set(LOCK, TOKEN, nx=True)          # SET NX：单点触发

def settle_with_lock():
    if not acquire_lock():
        return "skipped（其他副本已触发）"
    try:
        time.sleep(0.05)                           # 模拟任务
        return "done"
    finally:
        rds.delete(LOCK)                           # 生产要 Lua 校验 token 再删（防删别人的锁）

results = [settle_with_lock() for _ in range(4)]
print("带锁结果:", results, "| 实际执行:", results.count("done"))

# 3) 正解：幂等键 —— 任务表按业务周期唯一约束（示意）
class SettleTable(set):
    def insert(self, period):                       # period=业务周期号，唯一约束
        if period in self:
            return f"duplicate({period})"
        self.add(period)
        return "executed"

table = SettleTable()
print("幂等表:", [table.insert("2026-11") for _ in range(3)])
print("选型：分钟级强可靠 → K8s CronJob；秒级/动态 → 常驻调度器+任务表；进程内仅限幂等小任务+锁兜底")
```

**追问链**
1. 分布式锁的 TTL 怎么定？任务超过 TTL 会发生什么？续期怎么实现？
   1. TTL ≥ 任务 P99 时长 × 安全系数（如 2 倍），且带看门狗续期（任务运行中周期性 EXTEND）；无续期时长任务中途锁过期 → 第二实例拿到锁并发执行，且原实例结束时还会"删掉别人的锁"——删除必须 Lua 校验 token，或直接用 fence token（单调递增号）拒绝旧持有者写入。
   2. 追问：Redis 主从切换时锁会失效吗？——会：主写锁未同步到从即切换，新主上锁不存在，双执行窗口；强一致场景用 Redlock 争议仍大，结论是"锁是减损，幂等是根治"。
2. K8s CronJob 的冷启动对 Python 服务意味着什么？
   1. 每次执行起一个 pod：拉镜像/初始化解释器/加载依赖 10-30s，分钟级任务可接受、秒级任务完全不适合；且 `concurrencyPolicy`（Allow/Forbid/Replace）决定上一次没跑完时新触发的行为——Forbid 防重叠但要配 activeDeadlineSeconds 防永久卡死。
   2. 追问：任务表（执行记录）为什么是排障神器？——每次执行一行（周期号/实例/起止/结果/耗时），重复执行、漏执行、长尾一目了然；配合告警"到期未出现记录行"比监控进程存活更贴近业务承诺。

## 背诵要点
- 进程内定时三坑：多副本 N 遍执行、生命周期耦合（重启丢任务）、资源耦合（抢在线 worker）；N 副本 = N 个调度器。
- 正解 = 触发与执行分离：K8s CronJob（分钟级/强可靠）或常驻调度器+任务表（秒级/动态）；进程内仅限幂等小任务。
- 分布式锁是减损：TTL ≥ P99×2 + 看门狗续期 + Lua 校验 token 删锁；Redis 主从切换有双执行窗口，幂等键才是根治。
