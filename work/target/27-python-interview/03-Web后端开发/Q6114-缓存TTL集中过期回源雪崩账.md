### Q6114 · 缓存 TTL 集中过期的回源雪崩账

> 难度:★★★★☆ | 标签:容量规划, 缓存, TTL 抖动

**问**:凌晨批量刷新了 50 万条缓存，TTL 统一 6 小时，6 小时后 DB 秒级 QPS 从 500 冲到 8000 后熔断。击穿是单 key（Q6066 已讲），这次的"雪崩"差在哪？TTL 该怎么设、过期时间怎么抖、回源又该怎么限流？

**答**:结论：**击穿**是热点单 key 失效后并发回源打崩；**雪崩**是**大量 key 在同一时刻集体失效**，回源速率 = 失效速率 × 每 key 回源成本，瞬时超过 DB 与应用两层容量。账目推导：50 万条同刻过期，哪怕 10% 命中率冲击也是 5 万次/秒级回源；而 DB 稳态容量 500 QPS，缺口 10 倍以上。三层防线：a) **TTL 抖动**：`ttl = base + random.uniform(0, jitter)`（jitter 取 base 的 10-20%），把集中失效摊成均匀漏斗，回源速率从"脉冲"变"均值"，这是最便宜最有效的一层；b) **批量刷新时禁止同刻写**：预加载任务本身要限速+错峰（定时任务分散到分钟级），否则"集中写"天然制造"集中过期"；c) **回源侧限流 + 旧值兜底**：miss 时不放全量回源，用信号量限制并发回源数，拿不到时**返回旧值（逻辑过期）或降级默认值**——把"必须回源"改成"可以晚点回源"。另外把过期评估做对：TTL 应按"key 的重要度分级"差异化（核心配置长 TTL + 主动更新，长尾数据短 TTL），雪崩的本质是**用统一 TTL 管理了不同生命周期的数据**。

```python
import random, statistics

# 1) 事故账：统一 TTL 的失效脉冲
n_keys = 500_000
same_ttl_fail_per_sec = n_keys / 60          # 假设 1 分钟内全部过期
db_capacity = 500                            # DB 稳态 QPS
print(f"统一 TTL: 峰值回源 {same_ttl_fail_per_sec:,.0f}/s vs DB 容量 {db_capacity}/s "
      f"缺口 {same_ttl_fail_per_sec/db_capacity:.0f}x")

# 2) 修复一：TTL 抖动把脉冲摊平（jitter=20%）
base, jitter = 6 * 3600, 0.2
def jittered_ttl():
    return base * random.uniform(1 - jitter, 1 + jitter)
# 摊平后的瞬时失效 ≈ n / (平均TTL窗口)，但分布均匀，无脉冲
print(f"抖动 TTL: 失效均匀分布，瞬时回源 ≈ n/(平均TTL) 量级，无集中脉冲")

# 3) 修复二：回源信号量 + 旧值兜底（逻辑过期思想）
class BoundedRefill:
    def __init__(self, max_concurrent, fallback):
        self.sem_value = max_concurrent      # 手写信号量语义（演示用，标准库 threading.Semaphore）
        self.fallback = fallback

    def on_miss(self, key, old_value, db_call):
        if self.sem_value <= 0:
            # 回源额度耗尽：返回旧值或降级值，稍后异步重试
            return old_value if old_value is not None else self.fallback(key)
        self.sem_value -= 1
        try:
            return db_call(key)
        finally:
            self.sem_value += 1

def fake_db(key):
    return {"id": key, "data": "fresh"}      # 模拟慢 DB 调用

refill = BoundedRefill(max_concurrent=50, fallback=lambda k: {"id": k, "data": "degraded"})
print("miss 回源(有额度):", refill.on_miss("k1", None, fake_db))
refill.sem_value = 0                                     # 模拟回源额度耗尽（雪崩时刻）
print("miss 回源(无额度):", refill.on_miss("k2", {"id": "k2", "data": "stale-ok"}, fake_db))
refill.sem_value = 50

# 4) 验证抖动的分布效果
samples = [jittered_ttl() / 3600 for _ in range(10_000)]
print(f"10 万条抖动 TTL: 均值 {statistics.mean(samples):.2f}h 标准差 {statistics.stdev(samples):.2f}h （摊成漏斗）")
```

**追问一层**:TTL 抖动为什么用"百分比抖动"而不是"固定秒数"？大量 key 相同 base 时，固定 jitter 会不会自己制造新的峰值（生日碰撞）？
**追二层**:逻辑过期（value 里带过期时间、miss 返回旧值 + 异步刷新）与物理 TTL 的失败矩阵差在哪（对照 Q6032 缓存序列化升级的兼容问题）？双删/binlog 订阅方案（04 类）解决的是一致性，为什么救不了这次的容量问题？

**背诵要点**
- 击穿=单热点 key，雪崩=大量 key 同刻失效；回源速率 = 失效速率 × 每 key 成本。
- 第一防线是 TTL 抖动（base ±10-20% 百分比抖动），第二是批量刷新限速错峰，第三是回源信号量 + 旧值/降级兜底。
- 统一 TTL 管理不同生命周期数据是雪崩根因，重要度分级差异化 TTL 才是终态。

**复盘追问**
- 雪崩后想"立刻全量预热"救场，为什么反而二次打崩？提示：预热本身是回源风暴，必须限速+按热度优先级分批（引 Q6020）。
- 监控上怎么提前两周发现"6 小时后会有雪崩"？提示：按 TTL 分布直方图统计未来各时刻的失效量，加"未来失效速率"指标。
