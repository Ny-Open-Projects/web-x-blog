### Q6067 · 读写分离与副本延迟的容量一致性账

> 难度:★★★★ | 标签:容量规划, 读写分离, 主从延迟, 一致性

**问**：订单列表读接口切到只读副本后，用户刚下单就查不到自己的订单（副本延迟 800ms）。读写分离的容量收益怎么算？哪些读流量不能下放副本？"读己之写"怎么实现？副本数、延迟水位、路由层怎么配？

**答**：容量账：一般 Web 服务读：写 ≈ 10:1~100:1，读流量占 90%+；副本容量 = 每副本 QPS 上限 × 副本数，主库只需扛写+必须一致的读——**容量收益的实质是"把 90% 的读从主库撤走"**，但可下放的读必须满足两条：a) **能容忍副本延迟窗口**（典型 100ms-1s）；b) **不是"读己之写"**（用户写完立刻读自己的数据）。不能下放的清单：下单后跳转订单详情页、支付结果页、"我的"列表首屏、写后紧跟的校验逻辑——这些走主库或走下面的一致性机制。"读己之写"三实现：a) **写后短窗口走主**：session 存 last_write_ts，路由层判定 `now - last_write_ts < replication_lag_estimate` 则走主（简单有效，窗口略保守）；b) **时间戳/token 版本**：写返回 LSN/GTID，读请求带上 token，副本未追上该位点就等或转主（精确但侵入协议，PSQL 的 LSN/MySQL GTID 可做）；c) **关键读走主+其余副本**（粗粒度，按接口白名单）。容量配置账：副本延迟水位告警（>1s 说明主库写压力大或副本在追赶，容量评估作废）；副本数按"副本读 QPS 总量/单副本上限 + 1 冷备"定，注意**副本数越多主库同步开销越大**（binlog 复制是主库的写放大）；路由层做健康摘除——副本延迟超阈值自动摘除流量，宁可主库多扛不可读旧数据。Python 侧落点：SQLAlchemy 2.0 的 `session.bind` 切换 / Django 的 database router（`def db_for_read` 按接口标记路由），白名单在路由层实现，别散在业务代码里。

```python
# file: code/03_Web后端开发/q6067_read_split.py
import time

class Router:
    """最小读写路由: 写后窗口 + 接口白名单 + 延迟摘除"""
    def __init__(self, lag_estimate=0.8):
        self.lag = lag_estimate
        self.sessions = {}          # session_id -> last_write_ts
        self.replica_healthy = True # 延迟水位摘除

    def record_write(self, session_id):
        self.sessions[session_id] = time.monotonic()

    def pick(self, session_id, endpoint, cache_stamp=False):
        # 1) 延迟摘除: 副本不健康全走主
        if not self.replica_healthy:
            return "primary", "副本延迟超标摘除"
        # 2) 接口白名单: 读己之写接口强制主库
        if endpoint in ("order_detail", "pay_result", "my_list"):
            return "primary", "白名单(读己之写)"
        # 3) 写后窗口: 刚写过走主
        last = self.sessions.get(session_id)
        if last and time.monotonic() - last < self.lag:
            return "primary", f"写后窗口<{self.lag}s"
        return "replica", "常规读"

rt = Router(lag_estimate=0.8)
rt.record_write("u42")
print(rt.pick("u42", "order_detail"))    # 白名单 -> primary
print(rt.pick("u42", "feed"))            # 刚写过 -> primary
time.sleep(0.85)
print(rt.pick("u42", "feed"))            # 窗口过后 -> replica

rt.replica_healthy = False               # 副本延迟超标
print(rt.pick("u42", "feed"))            # 摘除 -> primary

# 2) 容量账
read_qps, rw_ratio, per_replica = 45_000, 10, 6_000
write_qps = read_qps / rw_ratio
offload = read_qps - write_qps - 5_000       # 白名单+窗口内的读留主: 演示 5000
replicas = -(-offload // per_replica)        # ceil
print(f"读 {read_qps} 写 {write_qps:.0f}: 可下放 ~{offload} QPS -> 副本数 {int(replicas)} (+1 冷备)")

# 3) 延迟水位: 容量评估的前提
lag_p99 = 0.8
print(f"副本 lag P99={lag_p99}s -> {'容量有效' if lag_p99 <= 1 else '摘除, 容量评估作废'}")
print("账: 容量收益=读流量下放比例; 前提=延迟水位健康; 白名单+写后窗口保一致性")
```

**追问**：1) "写后窗口走主"的窗口取多大？——副本 lag 的 P99（动态取监控值比静态 1s 好）+ 余量；窗口太短仍会读到旧（副本 lag 抖动超估计），太长主库压力大；配合前端"提交后 loading→主动刷新"给窗口留余地。2) 副本延迟怎么监控与摘除？——MySQL `SHOW REPLICA STATUS` 的 Seconds_Behind / PG `pg_stat_replication` 的 lag 字节，>阈值（1s）摘除并告警；摘除要带熔断恢复（慢恢复防抖动）；注意"主库写突增 → 复制堆积 → 全量读回主 → 主库过载"的连锁，主库限流要联动。3) SQLAlchemy/Django 的路由怎么组织？——统一 Router 层（中间件/ORM 路由器）持有白名单与 session 时间戳，业务代码只传 endpoint 标记；禁止业务代码手写 `.bind(primary)` 散落各处——路由决策集中一处才能审计和演练（kill 副本演练一致性路径）。

## 背诵要点
- 容量收益=把 90% 读从主库撤走；可下放条件=容忍延迟窗口且非"读己之写"；订单详情/支付结果/首屏白名单走主。
- 读己之写三实现：写后短窗口走主（lag P99+余量）、写返回位点 token 副本追赶校验、接口白名单粗粒度。
- 副本 lag P99>1s 摘除+告警（容量评估作废）；副本数=可下放 QPS/单副本上限+1 冷备；路由决策集中在 Router 层统一审计。
