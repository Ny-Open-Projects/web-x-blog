### Q6232 · 多文件 zip 流式打包下载：内存峰值与 CRC 校验链

难度：P6 ｜ 标签：zipfile、流式打包、恒定内存、StreamingResponse、CRC-32、非 seekable、zip64、下载中心

**问**：把 100 个文件（每个几百 MB）打包成 zip 给用户下载，为什么"先打包成临时文件再响应"在生产里是错误方案？`zipfile` 的流式写入怎么做——非 seekable 流上写 zip 有什么约束？`zf.open(zinfo, "w")` 与 `writestr` 的内存差在哪？CRC-32 校验在哪一环、客户端下载中断后怎么续传打包结果？

**答**：
结论：打包下载的正确形态是**边压缩边推流**：`ZipFile` 写入一个不落盘的流式 sink，HTTP 层以 chunked 响应把字节直接推给客户端——内存恒定（只有当前压缩块的缓冲），磁盘零临时文件，首字节延迟低（用户立刻开始下载而不是等打包完成）。实现要点：①**writestr vs open(w)**：`writestr(name, data)` 需要整个文件内容在内存里（几百 MB 的文件直接 OOM 面）；`zf.open(ZipInfo(name, date), "w")` 返回写入句柄，业务侧分块 `write(chunk)`——内存只有块缓冲；②**非 seekable 流的约束**：ZipFile 写到无 seek 能力的 sink（如 StreamingResponse 的管道）时，central directory 仍能写（Python 的 zipfile 支持非 seekable 输出），但**必须用 ZipInfo 显式声明 file_size 或用 force_zip64**——否则 header 里 size 字段占位失败；数据描述符（data descriptor, bit 3）模式自动启用，CRC 写在数据之后；③**CRC-32** 由 zipfile 自动计算并写入条目——它是完整性自检（解压器会验），但不是安全校验（CRC 可碰撞，防篡改要外层签名）；④**中断续传**：打包结果本身不可续（zip 是整体结构），工程做法是把"打包任务"异步化——生成 zip 落对象存储，客户端对最终产物用 Range 续传（Q758/Q6109 家族），打包过程失败可重试任务而不是续传流。

取舍：a) 文件小（总包 < 50MB）：内存直接 writestr 也行，别过度工程；b) 文件大/数量多：open(w) 分块 + 流式响应是唯一正解，同时设 zip64（>4GB 单文件或 >65535 条目必须）；c) 压缩级别权衡：业务文件（已压缩的 jpg/mp4）用 ZIP_STORED 零压缩——CPU 省、速度快、体积几乎不变，这是下载中心的常见优化；d) 断点续传语义分两层：**下载侧**对最终产物 Range 续传，**打包侧**异步任务 + 幂等重建，两层协议分开设计；e) 安全：打包内容来自多用户上传时，zip 炸弹（Q6226 同族思路）与路径逃逸（ZipInfo 的 name 带 ../）要在打包侧过滤，解压侧同理。

实战：事故形态是"导出中心把 zip 打包到 /tmp 再发响应：打包 40 分钟，用户等首字节 40 分钟；并发几个大导出就把磁盘写满——修复为 StreamingResponse + zipfile 流式（ZIP_STORED + 分块 open(w)），首字节秒级，磁盘零占用；超大导出再升级异步产物 + Range 续传"。下面实测恒定内存的流式打包链路。

```python
# zip 流式打包: 分块写入 + CRC 校验 + 恒定内存
import io
import time
import zipfile

CHUNK = 1 << 16                                   # 64KB 块缓冲

def make_zip_stream(sink, entries: dict[str, callable], compress=zipfile.ZIP_STORED):
    """把 entries (name -> 生成器函数) 流式打包进 sink; open(w) 分块写, 内存恒定"""
    with zipfile.ZipFile(sink, "w", compress) as zf:
        for name, gen in entries.items():
            info = zipfile.ZipInfo(name, date_time=(2026, 11, 24, 0, 0, 0))
            info.compress_type = compress
            with zf.open(info, "w", force_zip64=True) as handle:   # 显式声明 zip64, 非 seekable 安全
                for chunk in gen():                         # 业务侧分块产出, 不整读内存
                    handle.write(chunk)

def gen_file(size_bytes: int):
    """模拟大文件: 分块生成, 绝不整体物化"""
    produced = 0
    block = b"A" * CHUNK
    while produced < size_bytes:
        take = min(CHUNK, size_bytes - produced)
        yield block[:take]
        produced += take

print("[1] 流式打包: 10 个 5MB 文件 -> zip, 写入内存流仅为验证 (生产 sink 是响应流)")
peak_holder = io.BytesIO()
t0 = time.perf_counter()
entries = {f"report_{i}.csv": (lambda i=i: gen_file(5 * 1024 * 1024)) for i in range(10)}
make_zip_stream(peak_holder, entries)
elapsed = time.perf_counter() - t0
print(f"    打包 50MB 内容, 耗时 {elapsed:.3f}s (ZIP_STORED 零压缩)")

print("[2] CRC-32: zipfile 写条目时自动计算, 解压端自动校验")
peak_holder.seek(0)
with zipfile.ZipFile(peak_holder) as zf:
    infos = zf.infolist()
    crcs = [i.CRC for i in infos]
    print(f"    条目数 {len(infos)}, 每条目 CRC 已写入: {crcs[:3]} ...")
    ok = all(zf.read(name) is not None for name in zf.namelist())
    print("    解包校验通过:", ok, "(zipfile.read 会做 CRC 校验)")

print("[3] 内存账: writestr vs open(w)")
print("    writestr: 整文件进内存 (50MB 全量); open(w): 仅 64KB 块缓冲 -> 恒定内存")
print("    非 seekable sink: ZipInfo 显式声明 + force_zip64, data descriptor 位自动启用")

print("[4] CRC 不是安全校验: CRC-32 可碰撞, 防篡改要外层签名/摘要")
import zlib
print("    zlib.crc32(b'payload') =", zlib.crc32(b"payload"), "(完整性自检, 非防篡改)")
print("[5] 续传分两层: 下载侧对最终产物 Range 续传; 打包侧异步任务+幂等重建 (zip 本体不可续)")
print("[6] 打包侧过滤 ZipInfo name 的 ../ 逃逸与 zip 炸弹 (膨胀率上限)")
```

**追问一**：zip 的 central directory 与 data descriptor 是怎么让"非 seekable 流式写"成为可能的？写普通 seekable 文件时 zipfile 有什么不同？—— zip 格式的布局是 [局部文件头+数据]×N + central directory（尾部目录），**目录在数据之后**——这天然适配流式：写数据时不需要预知总大小。局部文件头里 size/CRC 字段本应"写前已知"（非流式场景），流式场景 zipfile 打开**通用位标志 bit 3（data descriptor）**：头部这些字段填 0，实际 CRC/size 写在数据块之后的 12 字节 descriptor 里——读端看到 bit 3 就知道去数据后取真值。zip64 扩展（4GB+）再叠加一条 ZIP64 扩展字段记录 8 字节 size。而写 seekable 文件时 zipfile 可以**回填**：写完数据后 seek 回头部补真实 CRC/size，descriptor 可不用——两种模式下同一 API 的底层路径不同，这也是"打包到内存/磁盘"与"打包到网络流"行为细节差异的根源（如某些老解压器对 bit 3 支持差，兼容性测试要覆盖）。

**追问二**：下载中心要支持"打包中途断网，用户重试不从头打"，架构怎么设计？与"异步产物"模式的分界线是什么？—— 打包流式响应的天然弱点是**不可续**：zip 是有尾目录的整体结构，中途断流就只能重打。分界线判断：①**小包（分钟内可完成、体积 < 1GB）**：流式直推，断流重试成本可接受，简单可靠优先；②**大包/耗时打包**：切"异步产物"模式——打包任务落队列（幂等：同请求参数产出同一产物名），产物写对象存储，用户拿任务 ID 轮询，完成后对**最终产物**走 Range 断点续传下载（Q758/Q6109 的下载侧协议在此复用）；产物本身带内容哈希与签名（预签名 URL，Q6064），完整性防篡改齐备。中间态还有一条**缓存产物**路线：相同打包参数的请求复用已生成的产物（key = 参数指纹），把"重复打包"消掉——下载中心的核心洞察是**打包结果可缓存可复用，实时流式只是最简单的那一档**。选型按"体积 × 耗时 × 重试频率"三维度切档，别用一种模式硬扛全部场景。

## 背诵要点
- 大包下载 = 流式打包：zf.open(ZipInfo, "w", force_zip64) 分块 write，writestr 整文件进内存是 OOM 面；ZIP_STORED 省零压缩 CPU。
- 非 seekable sink 靠 data descriptor（bit 3）+ central directory 后置实现；CRC-32 自动写入是完整性自检，防篡改要外层签名。
- 续传分两层：下载侧对最终产物 Range 续传、打包侧异步任务幂等重建；打包结果可按参数指纹缓存复用。
