### Q6159 · 查询串解析原理与库差异

难度：P6 ｜ 标签：parse_qs、urlencode、查询串、解析差异、原理深挖

**问**：`a=1&a=2`、`a`（无 =）、`a+1` 与 `a%201`、分号分隔符在各解析器里分别变成什么？为什么 RFC 3986/RFC 1866 对查询串语法定义含糊、导致 Python/浏览器/nginx/JS 各自不同？`parse_qs` 的 `keep_blank_values`/`strict_parsing` 与 `parse_qsl` 的语义差异是什么，防参数注入（参数污染 HPP）该在哪层收口？

**答**：
结论：查询串语法其实没有统一 RFC——RFC 3986 只定义 URI 的通用语法（`?` 后是 query，允许哪些字符），**`k=v&` 的编码细节来自实践**（HTML 规范 form urlencoding）。差异点：① 分隔符：历史上 W3C 建议 `;` 与 `&` 都可用，Python 的 `parse_qs` 曾支持 `;`，3.10 起**仅 `&`**（安全修复：`;` 常出现在 URL path 里被误当分隔符）；② 空格编码：`+` 与 `%20` 解析时**都变成空格**（`urlencode` 编码用 `+`），所以 `a+1` 解出 `a 1`，要与字面 `+` 交互必须编码成 `%2B`；③ 无值 key：`parse_qs("a")` 默认丢弃（`keep_blank_values=False`），`parse_qsl` 返回 `("a", "")`；④ 重复 key：`parse_qs` 聚合成 list（顺序保留），`parse_qsl` 保留对序——取第一个还是最后一个决定**参数污染（HPP）**结果：`?amount=1&amount=100` 过 WAF 时算 1、到应用变 100 的分歧就是经典漏洞。

取舍：收口原则——**解析一次、只在一层**：反代/网关与应用必须用同一种解析语义，应用内统一走框架的 query 对象（Starlette/Django 的 `QueryDict` 已固定"最后值优先/多值列表"语义），禁止业务代码自己再 split("&")。防御 HPP 的实务：入参白名单化 + 关键参数（金额/跳转/权限 ID）在网关层规范化（重复 key 直接 400），而非试图在应用里"猜哪个才是真的"。

实战：排查"同一个 URL 两个服务看到不同参数"时，用本文的四个差异点做决策树（分号？`+`？无值 key？重复 key？）；`urlencode` 与 `quote` 的区别（form 编码 vs RFC 3986 编码，空格 `+` vs `%20`）在拼接第三方 API URL 时是高频坑。

```python
from urllib.parse import parse_qs, parse_qsl, urlencode, quote

q = "a=1&a=2&a"                     # 重复 key + 无值 key

# 1) parse_qs vs parse_qsl
print("parse_qs default :", parse_qs(q))                 # 丢掉无值 key，聚合 list
print("parse_qs keep    :", parse_qs(q, keep_blank_values=True))
print("parse_qsl        :", parse_qsl(q, keep_blank_values=True))

# 2) 分号：3.10+ 只认 &（安全修复）
print("semicolon (3.10+):", parse_qs("x=1;y=2"))        # {'x': ['1;y=2']}

# 3) + 与 %20 都解析为空格，字面 + 必须编码为 %2B
print("plus decode      :", parse_qs("t=a+1&q=a%201&p=a%2B1"))
print("urlencode        :", urlencode({"t": "a 1", "p": "a+1"}))
print("quote (RFC3986)  :", quote("a 1"), "(空格=%20，form 编码才是 +)")

# 4) 参数污染：取首 vs 取尾的分歧
q2 = "amount=1&amount=100"
pairs = parse_qsl(q2)
first, last = pairs[0][1], pairs[-1][1]
print("HPP divergence   : first=%s last=%s -> 网关必须规范化" % (first, last))

# 5) strict_parsing：防呆开关
try:
    parse_qs("a=1&&b=2", strict_parsing=True)
except ValueError as e:
    print("strict_parsing   :", e)

# 6) Starlette/Django 语义对照（多值 QueryDict：getlist 保留全部）
class MiniQueryDict(dict):                  # 模拟 Django QueryDict.getlist 语义
    def getlist(self, key):
        return parse_qs(self["raw"], keep_blank_values=True).get(key, [])
d = MiniQueryDict(raw=q2)
print("QueryDict.getlist:", d.getlist("amount"))
```

**追问一**：为什么 Python 3.10 移除分号支持是安全修复而非功能倒退？——`;` 在 URL path/cookie 里是合法保留字符（如 Java 会话 id `;jsessionid=`），把它当参数分隔符会让"路径里的分号片段"被误解析成参数，造成 WAF 与应用对同一 URL 的语义分歧，正是 HPP 攻击载体；统一为仅 `&` 消除歧义。

**追问二**：`urlencode` 用 `+` 表示空格而 RFC 3986 要求 `%20`，谁对？——都对，属于两个方言：form 编码（application/x-www-form-urlencoded，HTML 表单传统）与 RFC 3986 分量编码；对接 REST/OAuth 等规范 API 必须用 `quote(..., safe='')` 产出的 RFC 方言（OAuth 2.0 明确要求 `%20`），混用会让签名校验失败。

## 背诵要点
- 查询串无统一 RFC：`k=v&` 是 form 实践；3.10 起 parse_qs 仅认 `&`，空格 `+`/`%20` 都解码为空格，字面 `+` 要 `%2B`。
- parse_qs 聚合 list 且默认丢无值 key（keep_blank_values/strict_parsing 两个开关），parse_qsl 保对序。
- HPP 防御在"解析一次、只在一层"：网关对关键参数重复 key 直接 400，应用禁止自行 split。

## 复盘追问
- 一个 URL 在 WAF 与应用里解出不同金额导致越权下单，如何复盘并给出三层收口方案？（分号/重复 key 差异还原、网关规范化、参数白名单，讨论测试用例固化）
- 为什么对接 OAuth API 时签名总失败？从两种空格编码方言切入。（urlencode 的 + 与 quote 的 %20，讨论编码方言与签名一致性）
