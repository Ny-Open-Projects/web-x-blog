### Q6151 · 301 永久重定向缓存不可回滚事故复盘

难度：P6 ｜ 标签：301、307、重定向、HTTP 缓存、事故复盘

**问**：为什么一次配错的 301 能"回滚失败"——CDN/浏览器把旧响应缓存后，服务端改回去为什么无效？301/302/307/308 在"方法保持"与"缓存语义"上的矩阵是什么？迁移域名/改路由时的安全发布流程怎么设计？

**答**：
结论：301 是**永久重定向且默认可缓存**（无显式 Cache-Control 时浏览器按启发式缓存，CDN 常见缓存数天到数月），客户端会**跳过源站**直接执行缓存的跳转——所以服务端改回 200/改目标都没用，要等缓存过期或用户清缓存。事故模型：路由调整时用 301 把 `/a` 指到 `/b`，两周后回滚路由，结果大量用户仍在 `/b`（浏览器与共享 CDN 双层缓存），登录态/CSRF 域都可能错位。方法语义矩阵：301/302 历史上浏览器把 POST 改写成 GET（规范与实现脱节，RFC 9110 承认现状）；307/308 **强制保持方法与 body**——POST 跳转必须用 307/308，否则表单提交静默变 GET。可缓存性：301/308 可缓存，302/307 默认不缓存（但可被 Cache-Control 显式缓存）。

取舍：迁移期永远**不要首发 301**——先 302/307 观察期（可随时回滚）→ 指标确认（流量分布、错误率、搜索收录）→ 再切 301 并带 `Cache-Control: max-age` 显式值（不要裸 301 让启发式接管）。已经撒出去的错误 301 的止血手段：同 URL 再发一个**带不同缓存键的响应**做不到（键就是 URL），只能靠"受影响客户端主动失效"（CDN purge + 引导用户清缓存/短 TTL 覆盖不了已缓存实例）。

实战：发布 checklist 加一条"永久跳转必须显式 Cache-Control 且走灰度"；CDN 层把 301 的 TTL 与 purge 接口纳入变更流程；监控上以"重定向响应占比"与"旧路径命中数"为回滚信号。

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import threading, urllib.request

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/legacy":
            # 观察期：302 可回滚；若是 301 则客户端/CDN 会缓存且不可回滚
            self.send_response(302)
            self.send_header("Location", "/new")
            self.send_header("Cache-Control", "no-store")   # 观察期禁缓存
            self.end_headers()
        elif self.path == "/new":
            body = b"OK new route"
            self.send_response(200)
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
        else:
            self.send_error(404)
    def log_message(self, *a): pass

srv = HTTPServer(("127.0.0.1", 0), Handler)
port = srv.server_address[1]
threading.Thread(target=srv.serve_forever, daemon=True).start()

opener = urllib.request.build_opener(urllib.request.HTTPRedirectHandler)
resp = opener.open(f"http://127.0.0.1:{port}/legacy")
print("followed to:", resp.geturl(), "status:", resp.status)   # 302 自动跟随

# 方法语义：POST + 302（浏览器实现会把 POST 降级为 GET）
import http.client
conn = http.client.HTTPConnection("127.0.0.1", port)
conn.request("POST", "/legacy", body=b"data")
r = conn.getresponse()
print("POST ->", r.status, r.getheader("Location"))
conn.close()
srv.shutdown()

# 矩阵速查（面试背诵用）
matrix = {
    "301": "永久, 可缓存, 方法常被降级为 GET",
    "302": "临时, 默认不缓存, 方法常被降级为 GET",
    "307": "临时, 不缓存, 严格保持方法与 body",
    "308": "永久, 可缓存, 严格保持方法与 body",
}
for k, v in matrix.items():
    print(k, "->", v)
```

**追问一**：为什么 RFC 9110 要"承认"301/302 的 POST→GET 降级而非纠正？——互联网上早已存在依赖该行为的实现（大量旧客户端按 301=重写方法处理），规范改语义会破坏兼容；RFC 9110 用 307/308 补充了"严格保持"选项，把选择权交给服务端。这是"规范追认现实"的经典案例。

**追问二**：CDN 对 301 的缓存键除了 URL 还有什么维度、purge 精度如何？——通常 URL + Host，部分厂商含 Header/Vary 维度；purge 可以按 URL 前缀/标签批量失效，但**浏览器的私有缓存无法远程清除**，所以错误 301 的影响面永远残留一批用户——这决定了"先 302 后 301"是不可省的流程而非过度谨慎。

## 背诵要点
- 301 可缓存且跳过源站，服务端回滚无效；止血只能 CDN purge，浏览器缓存清不掉——迁移必须先 302/307 观察期。
- 方法矩阵：301/302 实现 POST→GET 降级；307/308 严格保持方法与 body；301/308 可缓存、302/307 默认不缓存。
- 裸 301 无 Cache-Control 会落入启发式缓存；发布 checklist 要求永久跳转显式 TTL + 灰度。
