### Q6239 · 加密字段的模糊检索：盲索引、HMAC 归一化与 pepper 管理

难度：P7 ｜ 标签：盲索引、HMAC、确定性加密、模糊检索、pepper、KMS、归一化、范围查询、密钥管理

**问**：手机号/身份证在库里是密文，"按手机号查询用户"怎么实现——LIKE 通配能用吗？盲索引（HMAC(归一化值) 做索引列）的原理与攻击面是什么？为什么要归一化（+86、空格、大小写）再 HMAC——"输错格式查不到"的事故形态是什么？pepper 与 KMS 的管理边界、确定性加密的泄露面（频率分析）怎么权衡？范围查询（按号码段检索）为什么是这类方案的硬伤？

**答**：
结论：密文字段的等值检索靠**盲索引（blind index）**：入库时对明文做**归一化 → HMAC-SHA256(key, normalized) → 索引列**，密文列存加密值，查询时对查询词做同样的 HMAC 后等值查索引列——数据库里没有任何明文，等值检索照样命中。四条铁律：①**归一化在 HMAC 之前**——`+8613812348000`、`138-1234-8000`、`１３８…`（全角）必须归一到同一规范形，否则"同一个人输两种格式查不到自己"（事故形态：客服按用户报的手机号查不到，因为用户带空格输入）；②**HMAC 不是加密是伪随机函数**——同值恒同 HMAC（确定性，可索引），但不可逆，碰撞空间 2^256 可忽略；③**pepper（全局密钥）不入库**——存 KMS/环境配置（Q1829 家族的密钥治理），库里被拖走也推不回明文；④**泄露面**：确定性让攻击者可做**频率分析**（已知小范围候选值时可逐一 HMAC 比对——手机号只有 10^11 空间，离线字典攻击可行），所以盲索引保护的是"库泄露+无候选"场景，**不是免死金牌**；范围查询（LIKE '%138%'、按号段统计）天然不支持——HMAC 打散了有序性，需要前缀桶/范围分桶的扩展设计且泄露面陡增。

取舍：a) 算法选择：盲索引 HMAC-SHA256 是默认；**确定性加密（AES-SIV/FF1 格式保留加密）**能让密文列本身可等值查询（少一列索引），但泄露面同源且实现复杂——除非强约束（列数/存储），默认盲索引；b) 归一化策略要"业务审慎"：归一太激进（去尾 4 位匹配）会制造碰撞放大泄露，太保守（不做归一）用户体验差——归一规则与业务匹配语义对齐并文档化；c) pepper 轮换：HMAC 索引随 pepper 变化，全量重刷索引列的迁移成本要预算——pepper 生命周期规划在先，别事后补；d) 范围检索需求真实存在时：明文映射表（独立库+强权限）或搜索引擎专用管道（ES 的分词+脱敏）——把"可检索"与"加密存储"解耦在两个信任域；e) 与应用层加密（Q1911 哈希参数升级家族）联动：加密字段变更（换算法/换 key）时盲索引列同步重刷，两列一致性要有事务保障。

实战：事故形态是"加密手机号上线后客服查询命中率骤降：用户输入带空格/+86 前缀，归一化层漏了这两类形态，盲索引查不中，客服绕道后台直接看明文（权限旁路）——修复为归一化规则表（去空格/横线/统一国码/全角转半角）+ 未命中时提示'格式不匹配'而非放行明文 + 归一化单测覆盖全格式矩阵"。下面实测盲索引构建与检索。

```python
# 盲索引: HMAC(归一化明文) 作为密文字段的等值检索索引
import hashlib
import hmac
import unicodedata

PEPPER = b"from-kms-not-in-db"                     # 实际从 KMS/环境配置加载, 绝不入库

def normalize_phone(raw: str) -> str:
    """归一化到规范形: 全角转半角 -> 去分隔符 -> 统一国码"""
    s = unicodedata.normalize("NFKC", raw).strip()          # 全角数字 -> 半角
    s = s.replace(" ", "").replace("-", "").replace("+", "")
    if s.startswith("86") and len(s) == 13:                 # 统一去掉国码前缀
        s = s[2:]
    return s

def blind_index(normalized: str) -> str:
    """HMAC-SHA256(pepper, 规范形) -> 索引值 (确定性, 可等值查询, 不可逆)"""
    return hmac.new(PEPPER, normalized.encode(), hashlib.sha256).hexdigest()[:32]

def encrypt_value(raw: str) -> str:
    """示意: 存储列是加密值 (此处以摘要替代, 强调'库里无明文')"""
    return hashlib.sha256(("aes-key" + raw).encode()).hexdigest()[:32]

# 构建索引: 表 -> [(blind_idx, enc_value, user_id)]
table = []
for uid, raw in [(1, "13812348000"), (2, "+8613987654321"), (3, "138 0000 1111")]:
    norm = normalize_phone(raw)
    table.append((blind_index(norm), encrypt_value(raw), uid))

print("[1] 归一化矩阵: 同一手机号的不同输入形态收敛到同一规范形")
for raw in ("13812348000", "+86 138-1234-8000", "１３８１２３４８０００", "13812348000 "):
    print(f"    {raw!r:24} -> normalize = {normalize_phone(raw)!r}")

print("[2] 等值检索: 查询词走同样的归一化+HMAC, 等值命中索引列")
def search(raw_query: str) -> int | None:
    idx = blind_index(normalize_phone(raw_query))
    for bidx, _, uid in table:
        if bidx == idx:                                  # 常数时间比较见 Q6227 同族
            return uid
    return None
print("    查 '+86 138-1234-8000' -> user", search("+86 138-1234-8000"), "(归一化后命中)")
print("    查 '13800112233' -> user", search("13800112233"), "(不存在)")

print("[3] 事故形态: 归一化漏一类形态 -> 查不中 -> 客服绕道看明文 (权限旁路)")
print("    修复: 归一化规则表+格式矩阵单测; 未命中提示'格式不匹配', 不开明文后门")

print("[4] 泄露面权衡: 确定性 => 频率分析/字典攻击 (手机号空间 ~10^11, 可离线枚举比对)")
def offline_dict_attack(candidates: list[str], target_idx: str) -> str | None:
    for cand in candidates:
        if blind_index(normalize_phone(cand)) == target_idx:
            return cand
    return None
print("    已知候选集时盲索引可被逐一比对 (对'库泄露+无候选'场景才有效)")
print("    缓解: pepper 强保密(KMS)+高熵; 小空间字段加用户级盐的权衡(破坏全局检索)")

print("[5] 范围查询是硬伤: HMAC 打散有序性, LIKE '%138%' 无法下推")
print("    真需求: 明文映射表(独立信任域) / 前缀分桶扩展(泄露面陡增) / 搜索引擎脱敏管道")
print("[6] 纪律: 归一化在 HMAC 前; pepper 不入库(KMS); 索引列与密文列同事务维护; 算法变更同步重刷")
```

**追问一**：盲索引的 pepper 泄露后防线还剩多少？"分用户加盐的盲索引"为什么与全局检索矛盾？—— pepper 泄露（配置泄漏/日志打印/代码仓库）后：盲索引退化为"无密钥的哈希"——攻击者拿到库+pepper 即可离线字典攻击（手机号这类小空间字段直接枚举）。防线剩余：①**加密列本身仍是密文**（加密 key 与 pepper 分离，且盲索引只泄露"等值关系"不泄露明文）；②**访问控制与审计仍在**（谁能查谁被查有记录）；③**及时轮换**：pepper 泄露触发索引列全量重刷（这要求 pepper 轮换预案提前设计，与 Q1911 密码哈希参数升级同思路）。分用户加盐：HMAC(user_key, value) 让每个用户的索引密钥不同——字典攻击必须逐用户，泄露面骤减；但代价是**跨用户检索不可能**（"用手机号找到用户"这种全局查询失效，要先定位用户再算其盐）——适合"只能查自己的数据"的场景（用户自助查订单），不适合客服全局检索。矛盾本质：**盐的隔离性与索引的可检索性互斥**，按"谁有权跨用户查"这个业务事实选边。

**追问二**：范围/模糊检索（号段统计、LIKE 前缀）有哪些工程出路？各自的泄露面怎么评估？—— 出路矩阵：①**前缀分桶盲索引**：对号码前 N 位（如前 5 位）额外建 HMAC 桶列——支持"前缀等值"检索，但泄露面陡增：攻击者可按桶统计分布（某前缀桶内密文条数=号段用户数分布），N 越小桶越粗泄露越少但检索越弱——**桶宽是泄露面调节阀**，要按业务真需求定；②**独立明文映射域**：明文手机号只进专用检索库（物理隔离+强访问控制+审计+短留存），加密主库不承担检索——"可检索"与"加密存储"解耦，代价是多一套基础设施与同步链路；③**脱敏搜索管道**：要模糊搜索的字段进 ES 时做形化处理（保留格式打乱数字的 tokenization），支持 LIKE 式体验但搜索结果要二次确认原库；④**业务改造**：很多"模糊检索"是伪需求（客服场景 90% 是"精确手机号+模糊姓名"），姓名可存明文可检索（低敏字段）+手机号盲索引——先拆需求再上技术，别为伪需求付泄露面。评估口径统一为：**泄露面 = f(确定性强度, 候选空间, 桶粒度, 信任域数量)**，每个方案都要过一遍这个函数。

## 背诵要点
- 盲索引 = 归一化 → HMAC-SHA256(pepper, 规范形) → 索引列，等值检索成立、库内无明文；归一化在 HMAC 之前（+86/空格/全角）。
- pepper 不入库走 KMS；泄露后索引退化可离线字典攻击（手机号空间 10^11），轮换预案前置；分用户加盐与全局检索互斥。
- 确定性=频率分析泄露面；范围/LIKE 是硬伤，出路：前缀分桶（桶宽=泄露面调节阀）/独立明文域/脱敏管道/先拆伪需求。
