### Q6213 · Django 管理命令的生命周期：prepare、并发互斥与幂等重启

难度：P6 ｜ 标签：management command、BaseCommand、add_arguments、并发互斥、幂等、crontab

**问**：写一个 Django 管理命令，`handle` 之外还有哪些可覆写的生命周期钩子？crontab 每分钟拉起一次重任务命令，上一轮没跑完又被拉起会发生什么？怎么给管理命令做并发互斥与超时自杀？为什么说管理命令是"绕过所有中间件的全权限代码路径"——这在设计上意味着什么？

**答**：
结论：BaseCommand 的生命周期钩子（按执行序）：`add_arguments(parser)`（启动前注册 CLI 参数）→ `execute()` 内部：数据库连接准备 → `handle()`（核心逻辑）→ `__init__` 阶段还有 `SystemCheckRegistry` 的 check 跑一遍。关键点：管理命令**不经过任何 HTTP 中间件、无 request 对象、无租户上下文**，拿的是 settings 里全部权限的直连路径——跨库操作、外部调用、大事务全都裸奔。crontab 重叠拉起（上一轮 3 分钟没跑完，下一分钟又起）会造成：数据库双写竞态、外部 API 双倍调用、行锁等待雪崩。互斥标准方案是**文件锁（flock，Q381/Q1612）**：启动时对固定锁文件 `LOCK_EX|LOCK_NB`，拿不到即退出退出码 1，锁释放交给内核（进程死亡自动解锁，无陈旧锁问题）。超时自杀用信号守卫（Q5714 的 SIGALRM）或外部 timeout 包装：`timeout 300 python manage.py reindex`。幂等设计：命令必须假设"随时会被中断且会再次执行"，每一步要么天然幂等（set 语义、upsert），要么带断点游标（记录已处理到哪，重启续跑）。

取舍：a) 互斥层级：单机 crontab 用 flock 足够；多机部署的共享任务要分布式锁（DB/Redis）或单机派发（celery beat 单点调度，Q793 一族）；b) 超时由谁管：进程内 SIGALRM 精确但限主线程，外部 `timeout` 命令最简单可靠——生产推荐外部超时 + 进程内进度日志双保险；c) 日志必须落文件而非 print（cron 的 stdout 常被丢弃或进邮件），结构化 + 带轮转；d) 长事务拆段：一个 handle 里跑 40 分钟的 migration 型任务要按批次提交（保存点/分段，Q2497），否则中途被 timeout 杀掉连回滚都困难；e) Django 4.1+ 的 `requires_migrations_checks`/`requires_system_checks` 部署门禁（Q6202）对命令同样生效——迁移不一致时命令拒绝执行，这是好事，别关。

实战：事故形态是"全量重建索引命令跑了 45 分钟，crontab 每 30 分钟一次，三个实例同时跑，ES 写爆且主键冲突；修复：flock 互斥 + 外部 timeout 600 + 批次断点（每 1000 条记录 checkpoint，重启续跑）+ 完成后写运行审计行"。下面实现带互斥与断点的命令骨架。

```python
import fcntl
import os
import tempfile
import threading
import time

LOCK_PATH = None


def run_command(worker, checkpoint=None):
    """管理命令骨架: flock 互斥 + 断点续跑 + 审计"""
    fd = os.open(LOCK_PATH, os.O_CREAT | os.O_RDWR)
    try:
        fcntl.flock(fd, fcntl.LOCK_EX | fcntl.LOCK_NB)
    except BlockingIOError:
        os.close(fd)
        return f"[{worker}] 上一实例仍在运行, 退出(码 1)"
    try:
        start = (checkpoint or 0)
        os.write(fd, f"running:{worker}:{os.getpid()}".encode())   # 写运行态
        time.sleep(0.15)                                            # 模拟任务
        return f"[{worker}] 从断点 {start} 续跑, 处理 1000 条, 完成, 写审计行"
    finally:
        fcntl.flock(fd, fcntl.LOCK_UN)
        os.close(fd)


tmp = tempfile.mkdtemp()
LOCK_PATH = os.path.join(tmp, "reindex.lock")
results = []


def worker_thread(name):
    results.append(run_command(name, checkpoint=5000))


# 模拟 crontab 重叠拉起: 两个实例同时启动
t1 = threading.Thread(target=worker_thread, args=("cron-01",))
t2 = threading.Thread(target=worker_thread, args=("cron-02",))
t1.start(); t2.start(); t1.join(); t2.join()
for r in results:
    print("[1]", r)
print("[2] flock 由内核托管: 进程死亡自动解锁, 无陈旧锁残留")
```

**追问一**：为什么 flock 比自写"锁文件 + pid 检查"更可靠？—— pid 文件方案有三个失效模式：①检查与创建之间 TOCTOU（Q5712）；②持有者崩溃留下陈旧锁，清理逻辑要处理"pid 不存在则接管"，接管窗口内又可能撞上"pid 复用"（新进程恰好同号）；③NFS 上 pid 检查语义更弱。flock 把互斥交还内核：加锁是原子系统调用、解锁自动发生在进程死亡时、陈旧锁概念不存在。它只管"互斥"，不管"谁在持有"——需要可观测的运行态就在锁文件里写内容（本卡示例），但互斥判断永远读锁不读内容。

**追问二**：管理命令要做"租户隔离"时怎么办？—— 没有 request 就没有租户上下文，选项：①参数显式传 tenant（`--tenant=acme`），命令内部切换 schema/连接（配合 Django 的多库路由 Q810）；②循环所有租户逐个处理，但要控制单租户失败不影响整体（错误聚合 + 续跑）；③把逻辑收敛到 service 层（与 Web 共享），命令只是"无上下文的驱动器"——租户上下文在 service 内部显式构造。反模式是在命令里 import 中间件里的全局租户变量：它是 None 或污染值，静默做出错。核心纪律：管理命令与 Web 共享业务层但**绝不共享请求上下文**。

## 背诵要点
- 生命周期：add_arguments → system checks → handle；命令无中间件/租户上下文，是全权限裸路径。
- crontab 重叠：flock(LOCK_EX|LOCK_NB) 内核级互斥 + 外部 timeout 超时；锁随进程死亡自动释放。
- 命令必须幂等可续跑：批次提交 + checkpoint；日志落文件；多机任务上分布式锁或单点调度。
