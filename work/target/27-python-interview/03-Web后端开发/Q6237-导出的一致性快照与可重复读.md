### Q6237 · 导出的一致性快照：可重复读与导出期间数据变更

难度：P7 ｜ 标签：一致性快照、可重复读、REPEATABLE READ、导出一致性、分页导出、长事务、MVCC、快照点

**问**：导出 100 万行耗时 30 分钟，期间业务持续写入——为什么"按页循环 SELECT"导出的数据可能自相矛盾？快照点（consistent snapshot）怎么建立——REPEATABLE READ 事务、备份工具的 --single-transaction、还是应用层时序戳？长导出事务对线上库的代价是什么（长事务/MVCC 版本堆积）？快照一致性、实时性与成本的三角怎么权衡？

**答**：
结论：分页导出的矛盾形态：第 1 页读到"订单 #100 未退款"，导出到第 50 页时（20 分钟后）该订单退款了，统计口径出现"退款单仍在营业额里"——**每一页是独立读，整份导出没有统一时点**，本质是"跨时间拼贴的数据集"。三种一致化方案：①**数据库快照事务**——REPEATABLE READ 下开事务后第一读建立 MVCC 快照（MySQL InnoDB），后续所有读都看"事务开始那一刻"的数据，导出全程自洽；代价是**长事务**：undo 版本链持续堆积、purge 被阻塞、历史列表变长——几十分钟导出在高峰库上是事故面；②**备份工具级快照**——`mysqldump --single-transaction`（InnoDB 一致快照+单事务）、物理备份的 redo 点位，原理同①但专门优化，导出走备库/从库更干净；③**应用层时点标记**——给导出加"截止时间戳"或"版本水位"（如按 updated_at/自增 ID 上界截断），导出只读 `id <= 上界` 的行，线上写不进来——**轻量、无长事务**，但要求"时点键"可判定（自增 ID/时间戳有序），且处理不了"上界之前的行在导出中被 UPDATE"的读旧值问题（多数统计场景可接受）。工程原则：**先问业务要什么一致性**——财务对账要强一致快照（备库+快照事务），运营报表要"大致时点"（水位截断），实时面板根本不需要快照（要的是最新值）。

取舍：a) 导出库选择：**大导出永远走备库/只读副本**——主库做长事务是事故（锁/undo/连接占用），备库的延迟容忍换主库安全（Q6067 副本延迟家族）；b) 事务时长：快照事务导出控制在分钟级（分段提交会破坏快照！REPEATABLE READ 的快照随事务存续，COMMIT 就丢——所以"分批提交"与"快照一致"不可兼得，要一致就一个事务扛到底）；c) 水位截断的实现：`WHERE id <= @max_id`（导出开始时取 max）——分页键稳定、无长事务、可断点续跑，是大多数导出的默认选择；d) 变更容忍度声明：导出报告标注"数据截止 HH:MM"（时间戳入导出文件头），消费方按此解读——**一致性语义要写进产物**而不是隐含；e) 增量导出替代全量：每日全量+实时 CDC 的架构，把"一致性快照"问题转化为"主从延迟"问题，架构级解法。

实战：事故形态是"财务月度对账导出用分页循环跑在主库，期间退款任务更新了订单，导出里出现'已退款但计入营收'的矛盾行，财务复核返工两天——修复为对账导出走备库 REPEATABLE READ 单事务（15 分钟内）+ 导出文件头标注快照时间戳；常规运营导出改为 id 水位截断"。下面实测两种方案的行为差异。

```python
# 导出的一致性快照: 分页循环的自相矛盾 vs 水位截断
import itertools
import threading
import time

# 模拟表: id -> {"amount": 金额, "refunded": 是否退款}; 带 MVCC 版本史的简化模型
table = {
    1: {"amount": 100, "refunded": False},
    2: {"amount": 200, "refunded": False},
    3: {"amount": 300, "refunded": False},
}
version_history = {}                                     # id -> [(导出进行到的步数, 字段快照)]
for k, v in table.items():
    version_history[k] = [(0, dict(v))]
step = 0
step_lock = threading.Lock()

def concurrent_writer() -> None:
    """导出进行期间的业务写入: 订单 2 退款, 新订单 4 写入"""
    global step
    time.sleep(0.05)                                     # 恰好在导出中途
    with step_lock:
        step += 1
        s = step
        table[2]["refunded"] = True                      # UPDATE
        table[4] = {"amount": 400, "refunded": False}    # INSERT
        version_history.setdefault(4, []).append((s, dict(table[4])))

print("[1] 方案一: 按页循环 (每页独立读) -> 导出跨时间拼贴, 自相矛盾")
page_view, seen_ids = [], set()
t = threading.Thread(target=concurrent_writer); t.start()
for page in (1, 2):
    with step_lock:
        page_view.append({k: dict(v) for k, v in table.items()})   # 每页各取一次"当前值"
    time.sleep(0.1)                                       # 页间耗时 (模拟慢导出)
t.join()
print("    第 1 页读到订单 2: refunded =", page_view[0][2]["refunded"])
print("    第 2 页才看到订单 4 (导出中途插入):", 4 in page_view[1])
print("    -> 同一份导出里, 部分行是导出前状态、部分行是导出后状态: 口径撕裂")

print("[2] 方案二: 水位截断 (应用层时点) -> 只读 id <= 上界, 新写入天然不进导出")
with step_lock:
    max_id = max(table)                                   # 导出开始时取水位
print(f"    水位 max_id = {max_id}, 导出只含 id <= {max_id}: 订单 4 不进导出")
print("    局限: 上界之前的行被 UPDATE 时读到的是新值 (统计场景通常可容忍)")

print("[3] 方案三: REPEATABLE READ 快照事务 (数据库级一致) -> 一致但长事务有代价")
print("    事务内所有读看同一 MVCC 快照: 订单 2 全程是导出时点的值")
print("    代价: 长事务 -> undo 版本堆积/purge 阻塞; 分批提交会破坏快照 (COMMIT 即丢)")
print("    正解: 大导出走备库 + 单事务分钟级; 快照时间戳写进导出文件头")

print("[4] 三角权衡: 一致性(强快照/水位) x 实时性(导出时点 vs 最新) x 成本(备库/长事务)")
print("    财务对账 -> 备库+快照事务+时间戳标注; 运营报表 -> 水位截断; 实时面板 -> 不要快照")
print("[5] 每日全量 + CDC 增量的架构级解法: 把一致性问题转化为主从延迟问题 (Q6067)")
```

**追问一**：REPEATABLE READ 的"一致性快照"是第一读建立还是事务开始建立？这对导出实现有什么实操影响？—— MySQL InnoDB：快照在**第一次一致性读**时建立（不是 BEGIN 时）——所以"BEGIN 后先做一次 SELECT 再做长导出"与"BEGIN 后先做一堆 DDL/写操作"的快照点不同；实操上导出脚本要**BEGIN 后立刻以主查询建立快照**，避免前置操作漂移快照点。PostgreSQL：REPEATABLE READ 同样是"快照在事务第一个查询时获取"，且 PG 的可重复读下写冲突会直接报错（序列化失败）——纯导出场景无影响。另一个实操点：**快照的存续依赖事务不提交**——导出工具的分批 fetch（每次 fetch 完释放结果集再取下一批）若实现为"每批独立事务"，快照就碎了；正确形态是游标/流式 fetch 共享同一事务（Q6103 流式游标家族）。理解"快照点=第一个读"与"快照寿命=事务寿命"这两条，导出实现的所有细节都推得出来。

**追问二**：长导出事务对主库的破坏链有多长？"导出走备库"后还有哪些残余问题？—— 破坏链：①**undo 堆积**——快照之后的每次 UPDATE 都要保留旧版本供导出事务读，几十分钟 × 高写入 = 历史列表暴涨；②**purge 滞后**——最老活跃事务（导出）阻塞版本清理，磁盘/内存被历史版本吃掉；③**锁与连接**——导出连接占池，锁表统计的元数据锁风险（DDL 等待）；④**复制延迟放大**——备库应用 binlog 与长事务交错。走备库解决主库安全，残余问题：①**备库延迟**——快照建立在备库当前状态，延迟期内主库变更不在快照里（对"财务时点"语义要标注）；②**备库自身的长事务代价**——同样的 undo 堆积发生在备库（Q6103 流式游标与内存账的权衡依然要算）；③**备库切换/重启**——长事务被 kill，导出要支持断点续跑（水位记录）。终极架构解法是 CDC（binlog 订阅）+ 数据仓库层：把一致性快照的职责从在线库彻底剥离——OLTP 与 OLAP 分离是这个问题的架构级答案。

## 背诵要点
- 分页循环导出 = 跨时间拼贴自相矛盾（页面独立读）；三种一致化：备库 REPEATABLE READ 单事务 / 备份工具快照 / 应用层水位截断（id 上界）。
- 快照在第一个一致性读时建立、随事务存续——分批提交即碎；长导出走备库，快照时间戳写进产物。
- 长事务破坏链：undo 堆积→purge 滞后→锁/连接占用；残余问题（备库延迟/长事务代价）由 CDC+OLAP 分离根治。
