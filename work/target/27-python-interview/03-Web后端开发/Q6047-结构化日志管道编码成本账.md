### Q6047 · 结构化日志管道的编码成本账

> 难度:★★★☆ | 标签:logging, json, 成本工程, 可观测性

**问**：服务接入结构化日志（每请求一条 JSON）后 CPU 涨了 15%。结构化日志的成本构成是什么？哪些字段是"贵但没用"的？如何在"可查询性"与"编码成本"之间取舍，冷却路径（采样/降档）怎么设计而不丢关键日志？

**答**：成本构成四笔：1) **序列化**：`json.dumps` 每条几十微秒（字段多、嵌套深时上百），是最大头；2) **字符串构建**：f-string 拼字段、str(datetime) 等在写日志前已经发生（哪怕被采样丢弃）；3) **IO**：同步写 stdout/文件在请求线程里做（阻塞 worker），高 QPS 下成为串行点；4) **下游**：采集 agent 解析、传输与存储按条计费——**日志成本不止是 CPU，是全链路账单**。贵但没用的字段典型：每条都重复的高基数低价值字段（完整 UA、全量 headers）、深层嵌套对象、debug 字段忘删。取舍原则：**按日志用途分层**——审计/告警路径（必须全量、字段精、序列化用最快路径）；请求分析路径（采样 + 固定字段集，用 `sample_rate` 控制）；debug 路径（级别开关 + 惰性格式化 Q5047）。降档设计：正常时按 X% 采样但**错误与慢请求 100% 保留**（决策条件在序列化**之前**判断，省下丢弃日志的全部成本）；字段瘦身用"编码白名单"；高性能场景把 json.dumps 换 msgspec/orjson（第三方，基线 0.19/3.9，缺库降级标准库）可快 3-8 倍。IO 分离：日志写内存 Queue 由独立线程/进程 flush（注意退出排空，Q5545 的教训）。

```python
# file: code/03-Web后端开发/q6047_log_cost.py
import json
import logging
import random
import sys
import time

random.seed(1)
print("python:", sys.version_info[:3])

# 1) 编码成本基线: 字段数对 json.dumps 的影响
slim = {"ts": "2026-11-20T00:00:00Z", "lvl": "INFO", "route": "/api/x", "status": 200, "dur_ms": 12.3}
fat = {**slim, "headers": {"ua": "Mozilla/5.0 (Macintosh) Chrome/120", "x-forwarded": "1.2.3.4, 10.0.0.1"},
       "trace": {"span": "abc" * 8, "parent": "def" * 8}, "body": {"items": list(range(50))}}

def bench(obj, n=20_000):
    t0 = time.perf_counter()
    for _ in range(n):
        json.dumps(obj)
    return (time.perf_counter() - t0) / n * 1e6

print(f"瘦身条目编码: {bench(slim):.1f} us/条 | 大而全条目: {bench(fat):.1f} us/条 "
      f"({bench(fat)/bench(slim):.0f}x)")

# 2) 降档关键: 决策在序列化之前, 丢弃日志零成本
class SamplingLogger:
    def __init__(self, sample=0.2):
        self.sample = sample
    def should_emit(self, level, dur_ms):
        if level >= logging.WARNING: return True        # 错误全量
        if dur_ms > 500: return True                    # 慢请求全量
        return random.random() < self.sample            # 正常采样

def make_record(with_body=True):
    rec = dict(fat) if with_body else dict(slim)
    rec["dur_ms"] = 12.3
    return rec

sl = SamplingLogger(sample=0.2)
emitted = cost = 0
t0 = time.perf_counter()
for _ in range(10_000):
    rec = make_record(with_body=False)                  # 只构建白名单字段
    if sl.should_emit(logging.INFO, rec["dur_ms"]):
        json.dumps(rec); emitted += 1
print(f"1 万请求: 发出 {emitted} 条, 日志 CPU {(time.perf_counter()-t0)*1000:.0f} ms (丢弃的零编码成本)")

# 3) 对照: 全量大条目(事故写法)
t0 = time.perf_counter()
for _ in range(10_000):
    json.dumps(make_record(with_body=True))
print(f"全量大条目: {(time.perf_counter()-t0)*1000:.0f} ms (差出 {(time.perf_counter()-t0)*1000:.0f} ms 纯浪费)")
```

**追问**：1) 为什么"先序列化再决定是否发送"是常见反模式？——大多数实现把 record 构建绑定在 logger 调用里，采样发生在 handler 层；修复要上移到调用点决策（条件构造）或用惰性 record 对象让 handler 层短路。2) 同步日志 IO 如何确认它是延迟元凶？——py-spy 看 worker 栈是否大量落在 write/flush（Q6010 的定位路径）；火焰图上 logging 栈占比 >5% 就值得异步化。3) 异步日志的丢失窗口怎么定？——内存队列容量 × 条目大小即最大丢失量，进程崩溃时丢失；关键审计日志必须同步写（或双通道），普通访问日志可接受丢失换吞吐。

## 背诵要点
- 结构化日志成本四笔：json 序列化（大头）、字符串构建、同步 IO 阻塞、下游按条计费。
- 降档三原则：错误/慢请求 100%，正常采样，且决策在序列化之前（丢弃零成本）。
- 字段白名单瘦身（去掉 headers/body/深嵌套）+ msgspec/orjson 提速 3-8 倍（缺库降级标准库）。

## 复盘追问
- 日志 CPU 涨 15% 的服务，你按什么顺序拆这四笔成本？（提示：火焰图分序列化/构建/IO，再算条数 × 单价，最后对照下游采集账单）
- 审计合规要求"登录事件 100% 保留"，采样体系里如何给它开独立通道？（提示：双 logger：审计同步+全量+精简字段，访问日志采样异步，避免互相拖累）
