### Q6219 · HTTP 响应头的编码边界：latin-1 限定、UnicodeEncodeError 与文件名转义

难度：P6 ｜ 标签：HTTP 头编码、latin-1、RFC 9110、Content-Disposition、RFC 8187、UnicodeEncodeError

**问**：为什么 HTTP 头的值不能直接放中文——协议的编码限定是什么？WSGI/ASGI 层收到非 latin-1 的头值会发生什么（抛错还是静默 mojibake）？`Content-Disposition: filename="中文.pdf"` 的正确写法是什么？`filename*=UTF-8''...` 的语法为什么长这样？

**答**：
结论：RFC 9110 规定 HTTP 头的字段名与字段值限定在 **octet 且通常仅 latin-1（ISO-8859-1）可表示**的字符集——HTTP/1.x 的线上格式是字节协议，头没有统一的 UTF-8 编码声明，直接放中文就是"把 UTF-8 字节塞进没有编码协商的位置"：①WSGI 层（Django/Flask 传统路径）会直接抛 UnicodeEncodeError（WSGI 规范要求头是 latin-1 str，编码失败即 500）；②ASGI 层（str 透传给服务器）在服务器编码字节时同样失败或产生 mojibake。文件名的规范解法是 **RFC 6266/RFC 8187 组合**：兼容行 `filename="ascii-fallback.pdf"` + 扩展行 `filename*=UTF-8''%E6%96%87%E4%BB%B6.pdf`（百分号编码 + 声明字符集）——现代浏览器取 `filename*`，老客户端取 ASCII 回退。`UTF-8''` 的双引号是 RFC 8187 的语法：charset + 语言标签（可空）+ 两个单引号 + 编码值。

取舍：a) 头值只允许 ASCII/latin-1 是铁律：动态值（用户输入进文件名、header 注入）先白名单过滤 + 编码转义，CRLF 注入（Q1610）是另一个必须同时防的面；b) 文件名策略：ASCII 回退行必填（有些代理/老浏览器忽略 `filename*`），UTF-8 扩展行用百分号编码；c) 想绕过协议限制把任意 Unicode 放头里：只可以走"编码后的值"（base64/percent-encode）并让客户端按约定解码——不要试图"让 HTTP 支持 UTF-8 头"；d) 日志与监控里的头同样按 latin-1 安全处理，中文直接进头字段名的请求大概率是攻击探测（头名合法性校验前置）；e) HTTP/2 的头是 HPACK 压缩的字节串，但语义上仍是 latin-1 字符集约束——协议升级不改变字符集规则。

实战：事故形态是"下载接口把用户上传的原始文件名直接放进 Content-Disposition，中文名在 Flask/WSGI 下 500（UnicodeEncodeError），在另一条 ASGI 路径下变成乱码文件；修复统一为 RFC 8187 双行写法 + 文件名白名单清洗（控制字符/引号剔除）"。下面演示失败与正确姿势。

```python
import urllib.parse


def content_disposition(filename: str) -> str:
    """RFC 6266/8187: ASCII 回退行 + UTF-8 扩展行"""
    ascii_fallback = filename.encode("ascii", "ignore").decode() or "download"
    ascii_fallback = ascii_fallback.replace('"', "")     # 引号剔除
    utf8_encoded = urllib.parse.quote(filename.encode("utf-8"))
    return f"attachment; filename=\"{ascii_fallback}\"; filename*=UTF-8''{utf8_encoded}"


name = "季度报表-2026.pdf"
try:
    name.encode("latin-1")
except UnicodeEncodeError as e:
    print("[1] latin-1 直编失败:", e.reason, "-> 头里不能直接放中文")

print("[2] 正确双行写法:", content_disposition(name))

moji = name.encode("utf-8").decode("latin-1")
print("[3] 静默 mojibake 的样子:", moji, "——ASGI 层不抛错时就是这种垃圾进客户端")

print("[4] ASCII 文件名走回退行:", content_disposition("report.pdf"))
print("[5] 铁律: 头值 latin-1 限定; 动态值先清洗再编码; CRLF 注入另设防线")
```

**追问一**：为什么 WSGI 强制 latin-1 而 ASGI 用原生 str？两者的失败模式有何不同？—— WSGI（PEP 3333）的生态约定：头必须是 latin-1 可编码的 str（因为 WSGI 服务器要按 HTTP 字节协议直接写出），非法值在框架编码层抛 UnicodeEncodeError → 500，**失败快而明显**。ASGI 的 message 里头是 str，服务器在写出时编码，不同实现策略不同（有的替换字符、有的报错）——**失败可能延迟且形态不定**（mojibake 直接到达客户端）。这个差异让"在 WSGI 时代学到的头编码教训"迁移到 ASGI 时更隐蔽：同样的坏数据，一边 500 一边乱码。统一解法不依赖层：出口统一封装一个 header 构建器，所有动态头值先过清洗与编码。

**追问二**：`filename*=UTF-8''...` 里的两个单引号是干什么的？为什么不能省？—— RFC 8187 的 ext-value 语法是 `charset'language'value`：charset 声明百分号编码的字符集，language 是 RFC 5646 语言标签（多数场景填空即 `''`），value 是 percent-encoded 字节。两个单引号是**固定分隔符**，省掉后浏览器无法切分 charset 与 value，整个参数退化成非法值被忽略——表现为"中文文件名变成回退名或乱码"。工程上直接用成熟库生成（werkzeug/Django 的实现都内置），自研要写测试锁住"中文/空格/引号/超长"四个边界——文件名注入（引号截断、控制字符）与头注入是同一族问题。

## 背诵要点
- HTTP 头值限定 latin-1（RFC 9110），没有编码协商：中文直放 = WSGI 抛 UnicodeEncodeError(500) 或 ASGI 静默 mojibake。
- 文件名规范：RFC 6266 + 8187 双行——filename="ascii 回退" + filename*=UTF-8''percent-encoded；单引号是 charset'language' 固定分隔符不可省。
- 动态头值统一走清洗 + 编码封装；CRLF 注入（Q1610）与文件名引号截断同族，一并设防。

## 复盘追问
- 中文文件名下载在两条路径上分别 500 与乱码，怎么统一修复？（latin-1 限定；出口 header 构建器 + RFC 8187 双行写法）
- filename*=UTF-8'' 语法为什么必须带两个单引号？（charset'language'value 分隔符；缺失即非法被浏览器忽略）
