### Q6111 · 时区混用订单时间偏移事故

> 难度:★★★★☆ | 标签:事故复盘, 时区, datetime

**问**:跨日时差排查：用户投诉"昨晚 23:30 下的订单显示成次日凌晨"，而 DB 里存的字面时间确实变了。订单系统 `datetime.now()`、`utcnow()`、数据库 `TIMESTAMP`（无时区）混着用，这笔时间账该怎么对齐？Django `USE_TZ` 与 FastAPI/SQLAlchemy 各自的正确姿势是什么？

**答**:结论：事故根因是**三类时间源混用**：a) `datetime.now()` 取的是**服务器本地时区**（容器里常是 UTC，宿主机是 CST，两者不一致）；b) `datetime.utcnow()` 返回**无时区标记的 UTC 值**（naive），序列化后字段面值与真实时刻差 8 小时（3.12 起 `utcnow` 已弃用，改用 `now(timezone.utc)`，引 Q5044）；c) DB 的 `TIMESTAMP WITHOUT TIME ZONE` 存的是"字面值"，写入库时用的基准与读出时的解释基准不同就漂移。对齐原则只有一条：**存储与传输一律 UTC-aware，展示层最后转用户时区**。落地：Django 开 `USE_TZ=True`（ORM 全部转 UTC 落库，读出为 aware datetime）；SQLAlchemy 用 `DateTime(timezone=True)` + `timestamptz`；API 层响应统一 ISO 8601 带偏移（`+00:00`），前端用用户时区渲染。取舍：`TIMESTAMP WITH TIME ZONE`（PG）内部仍存 UTC 但按会话时区显示，跨时区聚合（"昨天"的账单）必须显式 `AT TIME ZONE`，否则 SUM 的窗口随 DB 时区漂移。DST 复盘另见 Q5049（fold 陷阱）：本质是同一类问题——naive 时刻缺上下文。

```python
from datetime import datetime, timezone, timedelta
import zoneinfo, sys

# 1) 三类时间源的面值差异（同一真实时刻）
now_real = datetime.now(timezone.utc)
print("UTC-aware :", now_real.isoformat())                     # 带 +00:00，唯一事实
print("本地 aware :", now_real.astimezone().isoformat())        # 转本地展示
print("utcnow 语义（3.12- 弃用）: naive 的 UTC 面值", now_real.replace(tzinfo=None).isoformat(), "Z")

# 2) naive 面值在不同时区被解释成不同真实时刻 —— 偏移 8 小时
naive = datetime(2026, 11, 21, 23, 30)
sh = zoneinfo.ZoneInfo("Asia/Shanghai")
as_shanghai = naive.replace(tzinfo=sh)
as_utc = naive.replace(tzinfo=timezone.utc)
print("23:30 按上海解释:", as_shanghai.astimezone(timezone.utc).isoformat())
print("23:30 按UTC解释  :", as_utc.isoformat())
print("两者差:", (as_utc - as_shanghai) + timedelta(0), timedelta(hours=8))

# 3) aware 比较与算术自动归一：跨时区订单排序不再漂移
order_a = datetime(2026, 11, 21, 23, 30, tzinfo=sh)             # 上海 23:30
order_b = datetime(2026, 11, 21, 16, 0, tzinfo=timezone.utc)    # UTC 16:00
print("排序( aware 自动归一 UTC ): ", [o.isoformat()[:19] for o in sorted([order_a, order_b], key=lambda x: x)])

# 4) "昨天"的业务聚合窗口：必须锚定业务时区
biz_tz = zoneinfo.ZoneInfo("Asia/Shanghai")
day_start = datetime(2026, 11, 21, 0, 0, tzinfo=biz_tz).astimezone(timezone.utc)
print("上海 '今天 0 点' 的 UTC 时刻:", day_start.isoformat())   # 前一天 16:00Z
print("Python 版本:", sys.version.split()[0], "（3.12+ 推荐 ZoneInfo，3.9+ 已内置）")
```

**追问一层**:`USE_TZ=False` 的存量 Django 项目改 `True` 会发生什么？为什么迁移必须走"先加 offset-aware 字段读侧兼容，再回填"而不是直接切（对照 Q6035 多 worker 迁移）？
**追二层**:PG 的 `timestamptz` 在 `SET TimeZone` 后 psql 看到的字面值不同——备份恢复、报表 SQL、ORM 迁移各自踩什么坑？`fold` 参数（Q5049）在这个体系里的位置是什么？

**背诵要点**
- 存储/传输一律 UTC-aware（ISO8601 带偏移），展示层才转用户时区；`utcnow()` 已弃用改 `now(timezone.utc)`。
- naive 时刻缺上下文是偏移事故总根源；Django `USE_TZ=True`、SQLAlchemy `DateTime(timezone=True)`+`timestamptz`。
- "昨天/今天"类聚合窗口必须锚定业务时区换算成 UTC 边界。

**复盘追问**
- 事故已发生，DB 里有几百万条 naive 历史数据，怎么确定当时的服务器时区来修复？提示：结合部署记录与 created_at 基准（本地 vs 容器 UTC），构造转换 SQL 灰度回填。
- 为什么"本地开发好的时区逻辑"上生产就错？提示：容器默认 UTC、宿主机 CST、用户时区三层叠加，测试要注入时区环境变量。
