### Q6136 · 缩略图生成的 CPU 成本账与预生成/懒生成策略

难度：P6 | 标签：Pillow、图像处理、异步任务、成本工程

**问**：图片上传后同步生成 5 个尺寸缩略图，高峰期上传接口 P99 从 300ms 涨到 8s，worker 被图像解码吃满。请拆解缩略图的 CPU 成本构成（解码/重采样/编码各占多少），并对比同步、懒生成（首次访问生成）、异步队列、边缘/客户端生成四种策略的成本与风险。

**答**：

**结论**：成本构成：解码（JPEG/PNG→像素）约 30-40%、重采样（LANCZOS 高质量卷积）约 40-50%、编码约 15-20%；4000×3000 原图生成 5 尺寸总耗时 1-3s、核时成本远超接口其他逻辑——同步生成把上传接口的延迟与 worker 容量绑死在图像上。策略对比：(1) 同步：一致性强、延迟差，容量按峰值图像量规划；(2) 懒生成（首次 GET 时生成+写回）：上传快，但首个读者承担延迟、并发首访需要单飞（否则同图重复生成 N 次）、恶意请求可用冷门尺寸打 CPU；(3) 异步队列（推荐）：上传后入队，CDN 上传原图，队列按 worker 数消化，积压水位监控；(4) 客户端/边缘生成：Canvas/边缘函数出缩略图，省服务端 CPU 但失去服务端标准化（尺寸、EXIF 清理、水印）控制权。安全项常被忽略：EXIF 剥离（隐私）、解码炸弹（百兆 PNG 声称 4GB 像素，先验像素上限）。

**取舍**：尺寸裁剪是最大杠杆：5 个尺寸改为按页面实际需要的 2-3 个，成本近半；JPEG quality 从 90 降到 80 视觉无感、编码时间约省 30%。重采样 FILTER 选型：THUMBNAIL/预览用 BILINEAR 足够，只有等比精缩用 LANCZOS。

**实战**：懒生成的单飞实现要点：以 (原图 hash, 尺寸) 为锁键，未命中者等待已完成者的结果而非各自生成；示例基于 Pillow（基线 Pillow>=10，缺库降级为跳过演示）。

```python
# 依赖基线：Pillow>=10；缺失时降级为仅测量尺寸（跳过像素处理）
try:
    from PIL import Image
    HAS_PIL = True
except ImportError:
    HAS_PIL = False
    print("Pillow 未安装，降级演示成本模型")

import io, time

SIZES = [(320, 320), (640, 640)]          # 从 5 尺寸裁剪到 2 尺寸

def gen_thumbs(data: bytes):
    img = Image.open(io.BytesIO(data))
    img.load()                             # 解码（真实成本大头之一）
    out = []
    for w, h in SIZES:
        t = img.copy()
        t.thumbnail((w, h), Image.BILINEAR)  # 预览级用 BILINEAR，不是 LANCZOS
        buf = io.BytesIO()
        t.save(buf, "JPEG", quality=80)
        out.append(buf.getbuffer().nbytes)
    return out

def cost_model():
    """像素账：解码炸弹防御必须先于任何解码。"""
    MAX_PIXELS = 30_000_000                # 3000 万像素上限
    fake_w, fake_h = 4000, 3000
    if fake_w * fake_h > MAX_PIXELS:
        raise ValueError("image too large")
    est_ms = fake_w * fake_h * len(SIZES) / 12_000_000   # 经验系数
    print(f"{fake_w}x{fake_h} x {len(SIZES)} 尺寸 预估 {est_ms:.0f} ms CPU")

if __name__ == "__main__":
    cost_model()
    if HAS_PIL:
        # 造一张真实小图验证流水线可运行
        img = Image.new("RGB", (800, 600), (120, 160, 200))
        buf = io.BytesIO(); img.save(buf, "JPEG")
        sizes = gen_thumbs(buf.getvalue())
        print("缩略图输出字节 ->", sizes)
```

**追问 1**：懒生成场景如何防"冷门尺寸 CPU 打击"？
答：尺寸白名单（只允许预定义枚举）+ 单飞锁 + 每秒生成配额；超出白名单直接 400，不进入生成路径。

**追问 2**：为什么 thumbnail 比 resize 便宜？
答：thumbnail 内部先按比例做 draft 模式（JPEG 解码时降采样，DCT 域缩小 1/2/4/8），解码像素量成倍减少；resize 是全尺寸解码后再卷积。

**追问 3**：异步生成失败（个别图损坏）如何不阻塞队列？
答：单图任务超时 + 失败计数，连续失败进死信队列并打标原图"无缩略图"，页面回退原图；毒丸图（解码 OOM）用子进程隔离防止拖垮 worker。

## 背诵要点

- 成本大头是解码+重采样（各 ~40%），尺寸数与像素量线性放大；同步生成绑死上传接口延迟。
- 策略：异步队列为主，懒生成必须单飞+尺寸白名单，客户端生成失去标准化控制权。
- 安全三件套：先验像素上限防解码炸弹、thumbnail 的 draft 降采样省钱、EXIF 剥离保隐私。
