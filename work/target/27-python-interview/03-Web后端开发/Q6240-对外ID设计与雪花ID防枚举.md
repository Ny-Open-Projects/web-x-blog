### Q6240 · 对外 ID 设计：可枚举风险、雪花 ID 与前缀化不透明 ID

难度：P6 ｜ 标签：ID 设计、雪花算法、可枚举、前缀 ID、不透明 ID、UUID、JS 安全整数、信息泄露、分库分表

**问**：自增主键直接对外暴露有什么风险——枚举爬取、规模泄露、业务量推断的链路是什么？雪花 ID（时间戳+机器位+序列位）怎么生成、时钟回拨怎么处理？"usr_xxx"式前缀不透明 ID（Stripe 风格）解决什么、与 UUID v4/雪花的选择矩阵？ID 方案与分库分表路由、JS Number 精度（Q2734）、排序语义的联动约束有哪些？

**答**：
结论：对外 ID 的设计目标是"**唯一、有序可选、不可推断、可路由**"，自增 ID 三项全输：①**可枚举**——`/orders/10001` 到 `/orders/10002` 无授权边界时遍历爬取（水平越权检测 Q1364 的常客），IDOR 攻击的放大器；②**规模泄露**——ID 增长速率=业务速率，竞对看你的最大订单号就能推日单量；③**语义耦合**——ID 直接暴露分库分表路由规律与迁移历史。三条主流路线：①**雪花 ID**（64 位：时间戳 ms<<22 | 机器 ID<<12 | 序列 12 位）——趋势有序（利于 B+ 树插入）、分布式去中心生成、可路由（机器位可编码分片信息）；坑：**时钟回拨**（NTP 校准让时间倒退→ID 重复风险，处理：回拨小于阈值就等待/借用序列位、大于阈值就报错拒绝服务）、机器 ID 分配（进程重启要复用或新分配，注册中心/配置分发）、worker 位不够时的容量上限（每 ms 4096 个）；②**UUID v4**——完全无序无语义，防推断最强，代价：索引写放大（B+ 树随机插入页分裂）、无序性破坏分页排序语义；③**前缀化不透明 ID**（Stripe 风格 `usr_1AbC…`）——前缀自述类型（usr/order/invoice，调试友好、日志可读）+ 随机体防枚举，本质是"对外 API 层的映射 ID"，内部主键可以仍是自增/雪花，**对外通过映射层翻译**——业务量的推断被随机体挡住。选型矩阵按"是否需要全局有序/是否对外暴露/是否分库分表"三问定路线。

取舍：a) 对外暴露原则：**内外分层**——内部用自增/雪花（有序、紧凑），对外 API 用不透明 ID 或雪花，绝不直接吐自增；b) 排序语义：需要"按创建时间排序/游标分页"的 ID（雪花）能兼任排序键（Q6185 tiebreaker 仍要补），UUID v4 必须另配 created_at 排序列——选 ID 时想清楚它是不是排序键；c) JS 精度：雪花 64 位整数超过 2^53（Q2734），JSON 序列化必须**字符串化**（前端拿到 string），这是雪花落地的强制约定；d) 分库分表联动：雪花机器位可编码"机房/分片"信息，路由查询免去广播；不透明 ID 方案下分片键与对外 ID 解耦，路由靠内部主键——两套 ID 的映射表成本要算；e) 安全兜底：无论哪种 ID，**授权检查都不该依赖"ID 不可猜"**——ID 是便利性防线不是安全边界（Q1364 越权矩阵），不可猜只是纵深一格。

实战：事故形态是"竞对通过订单号连续性测算出平台日订单量并公开发布，同时爬虫靠自增 ID 无授权遍历了 3 万笔订单详情（越权校验漏了 30% 的边角接口）——整改为对外雪花 ID+字符串序列化+全接口越权用例矩阵回归，内部主键保留自增，映射在序列化层完成"。下面实测雪花 ID 生成与可枚举对照。

```python
# 对外 ID 设计: 雪花 ID、可枚举风险与前缀化不透明 ID
import json
import secrets
import threading
import time

class Snowflake:
    """雪花 ID: 64 位 = 时间戳 ms(41) | 机器(10) | 序列(12); 时钟回拨防御内置"""
    def __init__(self, machine_id: int) -> None:
        self.machine = machine_id & 0x3FF                 # 10 位机器 ID
        self.seq = 0
        self.last_ts = -1
        self.lock = threading.Lock()

    def _now(self) -> int:
        return int(time.time() * 1000) - 1700000000000    # 自定义纪元

    def next_id(self) -> int:
        with self.lock:
            ts = self._now()
            if ts < self.last_ts:                         # 时钟回拨
                drift = self.last_ts - ts
                if drift <= 5:                            # 小回拨: 等待追平 (NTP 微调常见)
                    while self._now() < self.last_ts:
                        pass
                    ts = self._now()
                else:
                    raise RuntimeError(f"clock moved back {drift}ms, refuse to serve")
            if ts == self.last_ts:
                self.seq = (self.seq + 1) & 0xFFF         # 同毫秒内序列推进, 12 位上限 4096/ms
                if self.seq == 0:                         # 序列耗尽: 等下一毫秒
                    while self._now() <= self.last_ts:
                        pass
                    ts = self._now()
            else:
                self.seq = 0
            self.last_ts = ts
            return (ts << 22) | (self.machine << 12) | self.seq

print("[1] 自增 ID 的可枚举风险: ID 差值=业务量, 遍历无成本")
ids = [10001, 10002, 10003]
print("    相邻 ID 差:", ids[1] - ids[0], "-> 单量可被竞对推算; /orders/10001 遍历到 99999 无授权代价")

print("[2] 雪花 ID: 趋势有序 + 机器位 + 每毫秒 4096 上限")
sf = Snowflake(machine_id=7)
generated = [sf.next_id() for _ in range(5)]
print("    连续 5 个:", generated)
print("    单调递增:", generated == sorted(generated), "(趋势有序, 兼任分页排序键)")
print("    解码: 机器位 =", (generated[0] >> 12) & 0x3FF, "| 序列位 =", generated[0] & 0xFFF)

print("[3] 并发生成: 单毫秒 4096 上限与序列耗尽等待")
results, lock = [], threading.Lock()
def producer() -> None:
    for _ in range(500):
        with lock:
            results.append(sf.next_id())
threads = [threading.Thread(target=producer) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print("    4 线程 2000 个, 唯一性:", len(set(results)) == len(results))

print("[4] JS 精度: 雪花 64 位超 2**53, JSON 必须字符串化 (Q2734)")
sid = sf.next_id()
print("    JSON 数字:", json.dumps({"id": sid}), "-> 前端精度丢失风险")
print("    JSON 字符串:", json.dumps({"id": str(sid)}), "(强制约定)")

print("[5] 前缀化不透明 ID (Stripe 风格): 类型自述 + 随机体防枚举")
def opaque_id(kind: str) -> str:
    return f"{kind}_{secrets.token_urlsafe(12)}"
print("    订单:", opaque_id("order"), "| 用户:", opaque_id("usr"), "(内部主键仍是自增/雪花, 映射在序列化层)")

print("[6] 选择矩阵: 需全局有序->雪花; 纯防推断->UUID v4(索引写放大); 对外 API->前缀不透明 ID")
print("[7] 兜底: ID 不可猜只是纵深一格, 授权检查永远独立于 ID 可预测性 (Q1364)")
```

**追问一**：雪花 ID 的时钟回拨防御里，"小回拨等待、大回拨拒绝"的阈值怎么定？有没有更工程化的替代？—— 阈值逻辑：NTP 的正常校准（几十 ms 内）会带来小回拨——等待追平的代价是毫秒级停顿（生成延迟），可接受；大回拨（秒级以上，VM 迁移/NTP 跳变/手动改时）意味着"上次已发的 ID 对应的时间在未来"——继续生成必然重复，必须拒绝并告警人工介入，**宁可拒绝服务不可生成重复 ID**（幂等键冲突的代价大于短暂不可用）。工程化替代：①**逻辑时钟**——不依赖 wall clock，检测到回拨就"时间冻结在 last_ts 上继续烧序列位"（1s 回拨 = 烧 4M 序列，跨多 ms 借用），配合告警；②**序列位扩容**——时钟回拨空间换序列空间（Twitter 经典方案变体）；③**中央发号器**（Leaf/号段模式）——放弃去中心化，ID 由少数节点保证单调，回拨问题在服务端统一处理，代价是可用性依赖发号器（双活兜底）。选型口径：小规模自维护雪花+防御足够；大规模/多语言生态用成熟发号器组件，别重造。

**追问二**：不透明 ID 的映射层带来哪些工程成本？"对外 ID 与内部主键解耦"后，日志排障、数据修复怎么关联？—— 成本面：①**映射维护**——序列化层/DAO 层的翻译函数必须全链路一致（任何一处直接吐内部 ID 就是泄漏），靠"统一序列化器+出口断言"（未翻译 ID 在 code review 与测试里拦截）；②**可读性下降**——日志里 `order_9fAb...` 无法直接定位 DB 行，排障要查映射；缓解：内部日志双写（内部 ID+对外 ID 并列），对外 ID 全局唯一让"对外 ID→内部行"查询是 O(1) 索引；③**幂等键与回调耦合**——外部系统的回调携带对外 ID，回调处理要先翻译回内部主键（Q2730 回调确认家族），翻译失败（ID 被撤销）要有明确错误路径；④**存储索引**——对外 ID 需要唯一索引列（查询入口），空间与写放大有限但存在。收益对价评估：随机体防枚举/防推断 + 类型自述（日志一眼看出实体类型） + 内部主键重构自由（换分片/迁移不波及外部）——对外 API 数量大的平台，这套成本值得付；内部工具类服务可以省略映射层直接用雪花。原则：**映射层是"内外契约"的一部分，一旦对外发布就不可回收**——上线前想清楚，上线后当契约守护。

## 背诵要点
- 自增 ID 三宗罪：可枚举爬取（IDOR 放大器）、规模泄露（ID 增速=业务量）、语义耦合；对外绝不直接吐自增。
- 雪花 = 时间戳<<22|机器<<12|序列 12 位：趋势有序兼排序键、4096/ms 上限；时钟回拨小则等大则拒，替代是逻辑时钟/中央发号器；JSON 必须字符串化（超 2^53）。
- 前缀不透明 ID（usr_xxx）= 类型自述+随机体防枚举，映射层是内外契约不可回收；ID 不可猜只是纵深一格，授权永远独立校验。
