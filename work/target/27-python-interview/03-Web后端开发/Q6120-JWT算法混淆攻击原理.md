### Q6120 · JWT 算法混淆（alg confusion）与 none 攻击原理

> 难度:★★★★★ | 标签:原理深挖, JWT, 安全

**问**:为什么"alg 头写在 token 里"本身就是设计缺陷？`alg:none` 攻击、RS256→HS256 算法混淆攻击分别怎么构造？库层面（PyJWT）的默认防线与代码层必须加的防线各是什么（验签成本见 Q6040/Q6097，token 形态演进见 Q6107）？

**答**:结论：JWT 的 `header.alg` 是**攻击者可控的输入**——验签方"读 token 自己声明用什么算法"再据此验证，等于让签名者解释自己的签名。两类经典攻击：a) **none 攻击**：把 alg 置为 `none`、删掉签名段，某些实现（尤其早期库）"无算法=跳过验签"直接放行；b) **RS256→HS256 混淆**：服务端用 RS256（非对称：私钥签、公钥验）时，攻击者把 alg 改成 HS256，**用泄露的公钥当 HMAC 密钥**签 token——验签方按 HS256 拿公钥做对称校验，恰好通过（公钥是公开的！）。两条代码层铁律：a) **验签时白名单锁定算法**：`jwt.decode(token, key, algorithms=["RS256"])`——PyJWT 自 2.0 起强制要求显式 `algorithms` 参数且默认拒绝 none，这是库层默认防线；b) **密钥分离**：公钥只用于验签上下文，绝不能同时出现在"可拿来做 HMAC key"的路径。进阶防线：kid 注入（header.kid 指向攻击者可控的密钥路径/SQLi）要用"kid 白名单/固定映射"而非拼路径；`jku`/`jwk` header 传入自签 JWK 的场景一律忽略 header、只信服务端配置的密钥。原理层总结：**信任边界必须由验签方锚定**——算法、密钥都来自服务端配置，token 里只携带"数据"，不携带"验证方式"。

```python
# 基线: PyJWT>=2.8（库层默认防线）+ cryptography；缺库走降级说明
import base64, json, hashlib, hmac

def b64url(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def b64url_dec(s: str) -> bytes:
    return base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))

# 纯标准库构造/验证器，展示攻击原理（生产一律用 PyJWT）
def make_jwt(header, payload, signer):
    h = b64url(json.dumps(header, separators=(",", ":")).encode())
    p = b64url(json.dumps(payload, separators=(",", ":")).encode())
    signing_input = f"{h}.{p}".encode()
    return f"{h}.{p}.{b64url(signer(signing_input))}"

def verify_hs(token, key):
    h, p, s = token.split(".")
    expect = hmac.new(key, f"{h}.{p}".encode(), hashlib.sha256).digest()
    return hmac.compare_digest(b64url_dec(s), expect)

# ---- 攻击一：alg:none ----
none_token = f"{b64url(json.dumps({'alg':'none','typ':'JWT'}).encode())}." \
             f"{b64url(json.dumps({'sub':'admin'}).encode())}."
print("none token（无签名段）:", none_token[:60], "...")

def verify_strict(token, allowed_algs=("HS256",)):
    header = json.loads(b64url_dec(token.split(".")[0]))
    if header.get("alg") not in allowed_algs:      # 铁律 1：算法白名单
        raise ValueError(f"拒绝算法: {header.get('alg')}")
    if header.get("alg") == "HS256":
        if not verify_hs(token, b"secret-key"):    # 验签失败必须显式拒绝
            raise ValueError("签名校验失败")
        return True
    raise ValueError("不支持的算法")

try:
    verify_strict(none_token)
except ValueError as e:
    print("none 攻击被白名单拦截:", e)

# ---- 攻击二：RS256 公钥当 HMAC 密钥 ----
public_key_bytes = ("-----BEGIN PUBLIC KEY-----\n(MITM taken public key)\n-----END PUBLIC KEY-----").encode()
forged = make_jwt({"alg": "HS256", "typ": "JWT"}, {"sub": "admin"},
                  lambda m: hmac.new(public_key_bytes, m, hashlib.sha256).digest())
print("伪造 alg=HS256 token 已构造（密钥=公钥）:", forged[:40], "...")
# 验签方若"按 token 自声明选算法并用密钥环取 key"，公钥恰好匹配 HS256 -> 攻击成立
# 防线：decode 时 algorithms=["RS256"] 锁死 + 密钥分离（公钥永不进 HMAC 上下文）
try:
    verify_strict(forged)          # 白名单只允许 HS256 且密钥是服务端 secret，非公钥
    print("!! 攻击若成立说明防线缺失")
except Exception:
    print("混淆攻击被拦（算法白名单 + 服务端密钥与公钥分离）")

# ---- 库层默认防线验证（PyJWT） ----
try:
    import jwt as pyjwt
    good = pyjwt.encode({"sub": "u1"}, "secret-key", algorithm="HS256")
    try:
        pyjwt.decode(good, "secret-key")               # 不传 algorithms
    except Exception as e:                             # 库层抛 DecodeError 强制白名单
        print("PyJWT>=2 默认强制 algorithms 参数:", type(e).__name__, "-", e)
    print("PyJWT 正常验签:", pyjwt.decode(good, "secret-key", algorithms=["HS256"])["sub"])
except ImportError:
    print("缺 PyJWT>=2.8 — pip install pyjwt（库层强制 algorithms 白名单）")
```

**追问一层**:`kid` header 注入（路径穿越/SQLi 取密钥）与 `jku`/`jwk` 自带公钥攻击的构造方式是什么？为什么 kid 必须映射成服务端固定表？
**追二层**:RS256→HS256 混淆在"密钥环按 alg 索引"的实现里为什么成立？JWKS 轮换（按 kid 取公钥）怎么同时防混淆与支持轮换（对照 Q6040 公钥缓存）？

**背诵要点**
- header.alg 是攻击者可控输入；none 攻击=删签名，RS256→HS256 混淆=公钥当 HMAC 密钥。
- 两条铁律：decode 显式 `algorithms` 白名单（PyJWT≥2 默认强制），公钥与 HMAC 密钥路径完全分离。
- kid/jku/jwk 一律不信：kid 走服务端固定映射，公钥只来自服务端配置的 JWKS。

**复盘追问**
- 线上已有服务"验证函数接受 alg 参数"，安全审计要求整改，迁移怎么做才不破坏存量 token？提示：按当前签发 alg 收窄白名单灰度发布，双 alg 过渡期后删旧算法。
- 为什么"none 攻击"在很多自研实现里能过？提示：把"无签名"当"无校验需求"实现；签名段存在性与算法白名单要同时校验。
