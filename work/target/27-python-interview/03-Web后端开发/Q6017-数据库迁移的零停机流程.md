### Q6017 · 零停机数据库变更

> 难度:★★★ | 标签:数据库迁移, 零停机, DDL

**问**：线上给千万行表加非空列/改列类型/改索引，为什么「一条 ALTER 跑过去」不可接受——锁表原理是什么？expand-contract 三段迁移怎么走，旧代码兼容期怎么管？

**答**：锁原理：`ALTER TABLE ADD COLUMN NOT NULL DEFAULT x` 在旧版 MySQL 会**重写全表**（拷表 + 元数据锁 MDL），期间所有读写排队——千万行表锁几十分钟是事故；PG 对多数 DDL 快（元数据操作）但 `NOT NULL` 全表扫描验证、改类型必重写。**expand-contract 三段式**：① **Expand**（加法，可在线）：加新列（可空/带默认）、新表、新索引（`CREATE INDEX CONCURRENTLY` 不锁写）；② **双写与回填**：应用同时写新旧两处，存量数据**分批回填**（batch UPDATE，每批几千行 + sleep，别一口气锁全表）；③ **Switch**：读切到新列（应用层开关）；④ **Contract**（减法，确认无流量后才删旧列——**删列是不可逆的**，先删代码引用再删列）。旧代码兼容：双写期间回滚 = 关新列开关（旧代码只写旧列）；deploy 顺序必须「先上兼容代码、后跑 DDL」——DDL 跑在新代码之前会让旧代码读不到新列约束而崩。

```python
# demo 用 SQLAlchemy 2.0 演示 expand-contract 的应用侧配合（回填分批 + 双写开关）
# 缺库降级：无 sqlalchemy 时重点掌握流程与 SQL 口径（CONCURRENTLY/分批 UPDATE）
import sqlalchemy as sa
import time

meta = sa.MetaData()
users = sa.Table(
    "users", meta,
    sa.Column("id", sa.Integer, primary_key=True),
    sa.Column("email", sa.String(255)),
    sa.Column("email_new", sa.String(255), nullable=True),   # Expand：可空新列
)
eng = sa.create_engine("sqlite://")
meta.create_all(eng)
with eng.begin() as c:
    c.execute(users.insert(), [ {"id": i, "email": f"u{i}@x.com"} for i in range(1, 11) ])

WRITE_NEW = {"on": True}                     # 双写开关：回滚 = 关掉它

def backfill(batch=3, pause=0.01):
    """存量回填：分批 UPDATE + sleep，避免长事务/大锁。"""
    with eng.begin() as c:
        n = c.execute(sa.text("SELECT COUNT(*) FROM users WHERE email_new IS NULL")).scalar()
    while n:
        with eng.begin() as c:
            c.execute(sa.text(
                "UPDATE users SET email_new = email "
                "WHERE id IN (SELECT id FROM users WHERE email_new IS NULL LIMIT :b)"),
                {"b": batch})
        time.sleep(pause)                    # 让出主从/锁压力
        with eng.begin() as c:
            n = c.execute(sa.text("SELECT COUNT(*) FROM users WHERE email_new IS NULL")).scalar()
    print("回填完成")

def dual_write(email: str) -> int:
    with eng.begin() as c:
        r = c.execute(users.insert().values(email=email,
             email_new=email if WRITE_NEW["on"] else None))
    return r.inserted_primary_key[0]

if __name__ == "__main__":
    backfill()
    new_id = dual_write("new-user@x.com")
    with eng.begin() as c:
        row = c.execute(sa.text("SELECT email, email_new FROM users WHERE id=:i"), {"i": new_id}).one()
    assert row.email == row.email_new == "new-user@x.com"    # 双写一致
    print("双写 + 分批回填 OK；Switch 后 Contract 删旧列（先删代码引用再删列）")
    # 口径速记：PG 加索引 CONCURRENTLY（不锁写）；NOT NULL 分两步（先加可空+回填，再 ADD CONSTRAINT）；
    # MySQL 8.0 INSTANT ADD COLUMN 快，但带 DEFAULT+NOT NULL 的旧版行为要查版本矩阵。
```

**追问**：1) 为什么「先加 NOT NULL DEFAULT」在 PG 也可能慢？——PG 11 前必全表重写；PG 11+ 对常量默认值是元数据级快路径，但 `DEFAULT volatile()` 或 NOT NULL 校验仍可能扫表——版本矩阵要查。2) expand 阶段锁风险怎么控？——任何 DDL 前先查长事务（`pg_stat_activity` 长事务会卡住 DDL 的 MDL 排队，连带阻塞后面所有查询，锁队列雪崩）；`lock_timeout` 短超时 + 失败重试。3) 回填批大小怎么定？——单批耗时 < 副本延迟预算（如 1s），从 1k 行起步二分调，监控主从延迟与锁等待。

## 背诵要点
1. expand-contract 四步：Expand（加法+CONCURRENTLY）→ 双写+分批回填 → Switch（读切开关）→ Contract（先删代码引用再删列）。
2. 部署顺序铁律：先上兼容代码、后跑 DDL；回滚 = 关双写开关。
3. DDL 前必查长事务（MDL 排队雪崩）；回填批大小 = 副本延迟预算内二分。
