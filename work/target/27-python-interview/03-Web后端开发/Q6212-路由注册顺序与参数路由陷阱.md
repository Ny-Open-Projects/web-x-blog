### Q6212 · 路由注册顺序陷阱：/users/me 为什么被 /users/{id} 吃掉

难度：P6 ｜ 标签：路由匹配、注册顺序、路径参数、FastAPI、Starlette、优先级

**问**：注册了 `/users/me` 和 `/users/{id}` 两条路由，为什么请求 `/users/me` 落到了 `user_detail` 里，参数还变成了字符串 "me"？路由匹配是按"注册顺序"还是"最具体优先"？把固定路由放后面再 fix 有什么隐患？404 之外，路径参数把 "me" 当 int 解析会返回什么状态码？

**答**：
结论：主流框架（Starlette/FastAPI/DRF Router）的路由匹配是**按注册顺序线性扫描、首个命中即返回**——没有"最长/最具体优先"的隐式规则。`/users/{id}` 注册在前时，`me` 会被 `{id}` 捕获（它只匹配"一个段"，但段内内容不限），`user_detail` 收到 id="me"；若 `{id}` 声明了类型转换器（FastAPI 的 `int` 路径参数），"me" 解析失败返回 **422**（校验错误）而不是 404——这也是线上"明明写了 /users/me 却报 422"的来源。正确姿势是**固定路由先注册、参数路由后注册**，或用转换器收紧参数（`/users/{user_id:int}`，Starlette 原生转换器会让 "me" 不再命中该路由而落到下一候选）。隐患面：路由表随业务膨胀，"顺序敏感"的约定靠 code review 维持不可持续——路由漂移（有人把新路由插错位置）是此类事故的常见根因，需要测试锁定关键路径的匹配结果。

取舍：a) 固定段路由（me/admin/health）永远排在同前缀参数路由之前——写成规范或用代码检查；b) 转换器收紧：`{id:int}`、`{slug:str}` 让参数路由"更具体"，即使顺序错也能兜住（Starlette 转换器不匹配会继续尝试下一条）；c) 测试保障：对每个"固定 vs 参数"对写双断言（me → me_handler，/users/123 → detail），放进路由快照测试；d) DRF Router 自动生成的 URL 模式注意动态注册顺序，自定义 detail_route 与固定 view 的混排要显式验证；e) 版本前缀（/v1、/v2）与中间件路由无关，别在中间件里做路径改写来"救"路由顺序——改写会让 OpenAPI 文档与实际行为脱节。

实战：事故形态是"新增 /users/me/permissions 时插到了 /users/{id}/permissions 之后，'me' 被 int 转换器拒绝返回 422，客户端拿 422 当参数错误重试，把错误放大成告警；修复为固定路由统一前插 + 转换器收紧 + 路由匹配快照测试"。下面实现顺序敏感的匹配器。

```python
ROUTES = [
    ("GET", "/users/me", "me_handler"),
    ("GET", "/users/{id:int}", "user_detail"),
    ("GET", "/users/{id}/posts", "user_posts"),
]

CONVERTERS = {"int": str.isdigit}


def match(method, path, table):
    for m, pattern, handler in table:
        if m != method:
            continue
        segs, parts = pattern.strip("/").split("/"), path.strip("/").split("/")
        if len(segs) != len(parts):
            continue
        ok = True
        for s, p in zip(segs, parts):
            if s.startswith("{") and s.endswith("}"):
                token = s[1:-1]
                name, _, conv = token.partition(":")
                if conv and not CONVERTERS[conv](p):   # 转换器不匹配 -> 继续下一条路由
                    ok = False
                    break
            elif s != p:
                ok = False
                break
        if ok:
            return handler, {s[1:-1].split(":")[0]: p for s, p in zip(segs, parts) if s.startswith("{")}
    return None, None


print("[1] /users/me ->", match("GET", "/users/me", ROUTES), "——固定路由在前, 正确命中")
print("[2] /users/123 ->", match("GET", "/users/123", ROUTES))

BAD = [ROUTES[1], ROUTES[0], ROUTES[2]]
print("[3] 顺序颠倒后 /users/me ->", match("GET", "/users/me", BAD), "——int 转换器拒绝 me, 兜底到下一条")
print("[4] 无转换器时颠倒 = 'me' 被 {id} 吃掉, handler 收到字符串 'me'（422 的源头）")
```

**追问一**：为什么 404 和 422 的区分在这里很重要？—— 语义完全不同：404 = "这条 URL 不存在"（客户端应修正请求或放弃），422 = "URL 对但参数非法"（客户端可重试修正参数）。`/users/me` 落进 `{id:int}` 时，"路由匹配失败"被报成"参数校验失败"，监控里 422 率升高会被误判为客户端 bug 潮，排障方向带偏。反过来，显式的转换器设计让"me"不匹配 int 路由继续走注册表，最终要么命中 me 路由、要么诚实地 404——把匹配失败和校验失败分开，是路由设计的可观测性底线。

**追问二**：路由数量增长到几百条后，线性扫描的性能问题怎么解？—— Starlette 的匹配就是逐条尝试（每条还要做正则），几百条路由 × 每请求一次 = 每次 HTTP 请求几十次正则尝试，P99 里路由匹配能占到几百微秒到毫秒级。优化路径：①合并前缀构建基数树/前缀分片（一些框架与自研网关的做法）；②高频路径白名单直达（精确 dict 命中参数路由的正则结果缓存）；③统计每条路由的匹配成本与流量占比，冷路由下沉。但收益要先测：相对上游网络与业务逻辑，路由匹配往往不是瓶颈——优化前用 profile 说话（与 Q6035 一族的成本账思路一致）。

## 背诵要点
- 路由按注册顺序首中即停，无"最具体优先"；固定段路由必须排在同前缀参数路由之前。
- `{id:int}` 等转换器让参数路由拒绝不匹配的段并继续尝试下一条——顺序错误的兜底防线。
- "me" 落进 int 参数返回 422（校验失败）而非 404（路由不存在），监控语义完全不同；关键路径用匹配快照测试锁定。

## 复盘追问
- /users/me 报 422 的完整链路？（参数路由在前 + int 转换器拒绝 me → 报成校验错误；固定路由前插修复）
- 路由表几百条后匹配成本怎么治理？（线性正则扫描的成本账；前缀分片/精确缓存，先 profile 再优化）
