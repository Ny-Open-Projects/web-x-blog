### Q6050 · 多租户限流的内存成本账（键基数爆炸与降档）

> 难度:★★★★ | 标签:限流, 成本工程, 容量规划, 多租户

**问**：按"租户 + IP + 接口"三维限流后，网关内存一周涨了 3GB 且不回落。限流数据结构的内存账怎么算？滑动窗口/令牌桶/漏桶各自的状态成本是多少？键基数爆炸（恶意伪造 IP、超长 tail 租户）如何防御与降档？

**答**：内存账先算结构：滑动窗口每键存一个时间戳列表（每请求一条），成本 = 键数 × 窗口内请求数 × ~8 字节 + 容器开销，每键轻松几 KB；令牌桶每键只需 (tokens, last_ts) 两个数，~百字节级；漏桶介于两者。**键基数才是真正的变量**：租户 1 万 × IP 上万 × 接口 500 = 理论 5 亿键，即使每键 100 字节也是 50GB——三维笛卡尔积是设计错误，攻击者伪造百万随机 IP 能直接把限流器撑到 OOM（限流器自己被打死）。且 dict 只涨不缩（Q5042），流量回落后内存不回落，"一周涨 3GB"就是过期键没清理或基数失控。防御四层：1) **降维**：限流键按场景选维度（防刷用 IP + 接口、计费用租户），不做全维组合；2) **键空间上限**：单维度键数硬上限（如 IP 维度 10 万键），超限即"攻击模式"——切到全局兜底阈值并告警，而不是继续分配；3) **过期清理**：定期扫（惰性过期 + 周期清扫）或用 LRU（lru_cache/Q2632 的无界教训）限制总键数；4) **存储外置**：键数大时放 Redis（EXPIRE 自动过期 + 集群容量），网关只留本地小 LRU 做热点。状态选型结论：多租户默认**令牌桶**（O(1) 状态、支持突发语义清晰），滑动窗口只在需要精确窗口语义时用且必须配键上限。

```python
# file: code/03-Web后端开发/q6050_rate_limit_memory.py
import time
import tracemalloc

class TokenBucket:
    """O(1) 状态: 每键 (tokens, last_ts), 容量账 ~100B/键"""
    __slots__ = ("tokens", "last", "rate", "capacity")

    def __init__(self, rate, capacity):
        self.rate, self.capacity = rate, capacity
        self.tokens = float(capacity)
        self.last = time.monotonic()

    def allow(self):
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

class SlidingWindow:
    """时间戳列表: 每键成本 = 窗口内请求数 × 8B, 突发下膨胀"""
    def __init__(self, window, limit):
        self.window, self.limit = window, limit
        self.hits = []

    def allow(self):
        now = time.monotonic()
        self.hits = [t for t in self.hits if now - t < self.window]
        if len(self.hits) < self.limit:
            self.hits.append(now)
            return True
        return False

class GuardedLimiter:
    """键基数防御: 单维度键上限 + 超限切全局兜底"""
    MAX_KEYS = 50_000

    def __init__(self, rate=10, capacity=20):
        self.buckets = {}
        self.global_bucket = TokenBucket(rate * 1000, capacity * 1000)
        self.attack_mode = False

    def allow(self, key):
        if len(self.buckets) >= self.MAX_KEYS and key not in self.buckets:
            self.attack_mode = True                  # 键空间爆 -> 全局兜底 + 告警
            return self.global_bucket.allow()
        b = self.buckets.get(key)
        if b is None:
            b = self.buckets[key] = TokenBucket(10, 20)
        return b.allow()

if __name__ == "__main__":
    tracemalloc.start()
    lim = GuardedLimiter()
    for i in range(30_000):
        lim.allow(f"ip-{i}")
    for i in range(25_000):                          # 超过 MAX_KEYS -> 攻击模式
        lim.allow(f"evil-{i}")
    cur, peak = tracemalloc.get_traced_memory()
    print(f"5.5 万个随机 IP: 内存 {cur/1e6:.1f} MB, 每 TokenBucket ≈ {cur/len(lim.buckets):.0f} B")
    print("攻击模式:", lim.attack_mode, "-> 键上限触发全局兜底, 限流器不被打死")

    # 结构对比账: 滑动窗口在突发下每键成本
    tracemalloc.reset_peak()
    sw = {f"t{i}": SlidingWindow(60, 1000) for i in range(10_000)}
    for b in sw.values():
        for _ in range(200):                         # 模拟突发: 每键 200 条时间戳
            b.allow()
    cur2, _ = tracemalloc.get_traced_memory()
    print(f"滑动窗口 1 万键 × 200 突发: {cur2/1e6:.1f} MB "
          f"(TokenBucket 每键仅 ~{cur/len(lim.buckets):.0f} B -> 差距即状态成本)")
    print("结论: 多租户默认令牌桶 O(1) 状态; 滑动窗口必须配键上限与过期清理")
```

**追问**：1) 为什么攻击者伪造 IP 能绕过"按 IP 限流"而打不穿"按租户令牌桶"？——伪造 IP 每个都是新键（计费维度在租户侧则伪造无收益）；所以防刷维度选"攻击者难以为发电价的身份"（租户/API key），IP 维度只做辅助。2) Redis 集群上做限流，本地 LRU 与 Redis 的一致性怎么处理？——本地桶做"粗粒度预过滤"（允许略宽），Redis 做"精确配额"，两层阈值比例（如本地=配额/节点数 × 1.1）容忍短时超发，避免每请求一次网络往返。3) 过期键清理在纯内存实现里怎么做到 O(1) 均摊？——惰性过期（访问时判断）+ 概率清扫（每 N 次访问随机抽查一批过期键），Redis 的做法；纯定时扫描在键基数大时本身就是 CPU 事故。

## 背诵要点
- 限流内存账 = 键基数 × 每键状态；令牌桶 O(1) ~百字节，滑动窗口随请求数线性膨胀。
- 三维全组合是设计错误：按场景降维选键，单维度键数设硬上限，超限切全局兜底 + 告警。
- dict 只涨不缩：过期清理（惰性 + 概率清扫）或 Redis EXPIRE 外置，防"流量回落内存不落"。

## 复盘追问
- 网关内存周涨 3GB 不回落，如何证明是限流键基数而非业务泄漏？（提示：对键空间抽样统计基数分布与 TTL 存在性，对照攻击流量日志）
- 设计防御时"键上限"触发后的全局兜底阈值怎么定才不误伤正常租户？（提示：兜底阈值 = 正常峰值聚合 × 安全系数，切换期间按租户白名单保核心，事后回放统计误伤率）
