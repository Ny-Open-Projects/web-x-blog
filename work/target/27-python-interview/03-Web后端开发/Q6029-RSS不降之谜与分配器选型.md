### Q6029 · RSS 不降之谜：glibc arena 与 jemalloc 的取舍

> 难度:★★★★☆ | 标签:glibc, jemalloc, 内存

**问**：对象全释放了、tracemalloc 归零，为什么 RSS 还是降不下来？glibc malloc 的 arena 机制怎么放大这个问题，`MALLOC_ARENA_MAX` 调成多少合适？换 jemalloc 的收益与代价是什么？怎么和真泄漏（Q839）做最终切割？

**答**：两层驻留叠加：1) **pymalloc 层**——小对象池的 arena（256KB）只要还有一个活 block 就整块不还 OS（Q5030），对象散落在大量 arena 里时 RSS 虚高；2) **glibc 层**——pymalloc 的大对象与 C 扩展直接走 glibc malloc，glibc 为减少锁竞争按"每核 8 个"建 arena（默认 8×CPU），每个 arena 维护自己的空闲链表（bin）：释放的内存挂在 bin 里**不归还内核**（除非顶部连续块可 trim），多线程下各线程绑定不同 arena，"你释放的块进你的 bin，别人分配不进来"，碎片率随线程数上升。`MALLOC_ARENA_MAX=2`（或 1）把 arena 数砍下来，多线程服务的 RSS 常降 20-40%，代价是 arena 锁竞争略增。**jemalloc/tcmalloc**（LD_PRELOAD 换分配器）：更激进的归却策略（size class 分箱、定期 purge），对"潮汐式分配"的 Python 服务普遍能降 RSS 与尾延迟；代价：行为差异要回归（个别 C 扩展对分配器有隐含假设）、部署面多一个 LD_PRELOAD 配置。**切割诊断**：tracemalloc 对象账本（Python 层活对象）低 + RSS 高 → 分配器/碎片驻留，不是泄漏；再配 `/proc/PID/smaps` 看匿名页分布与 `malloc_trim(0)` 试探（能 trim 掉的说明只是没还）——malloc_trim 后 RSS 骤降是"驻留非泄漏"的最快证明。

```python
# file: code/03_Web后端开发/q6029_rss_allocator.py
import ctypes, resource, sys

ARENA, BLOCK = 256 * 1024, 512            # pymalloc 分层
blocks_per_arena = ARENA // BLOCK          # 512 块/arena

def resident_model(survivors: int, scatter: int):
    """碎片驻留模型: survivors 个活块散落在 scatter 倍于理想值的 arena 里"""
    ideal_arenas = -(-survivors // blocks_per_arena)      # 理想: 紧凑排布
    real_arenas = ideal_arenas * scatter                  # 现实: 活块分散
    return ideal_arenas * ARENA, real_arenas * ARENA

ideal, real = resident_model(5000, scatter=20)
print(f"5000 个 512B 活块: 理想驻留 {ideal/1e6:.1f}MB,分散后驻留 {real/1e6:.1f}MB")
print("=> tracemalloc(对象账本)只看到 ~2.5MB,RSS 却背了几十 MB 的 arena")

# malloc_trim 试探(仅 Linux): 能被还回去的内存 = "驻留但非泄漏"的最快证明
if sys.platform.startswith("linux"):
    libc = ctypes.CDLL("libc.so.6", use_errno=True)
    freed = libc.malloc_trim(0)
    print("malloc_trim 执行:", bool(freed), "(返回非 0 表示有页被归还)")
else:
    print("malloc_trim: 仅 Linux 可试(macOS 跳过)")

raw = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss   # Linux:KB, macOS:bytes
mb = raw / 1024 if sys.platform.startswith("linux") else raw / (1024 * 1024)
print(f"ru_maxrss ≈ {mb:.0f} MB")
print()
print("处置序: MALLOC_ARENA_MAX=2 -> LD_PRELOAD=jemalloc -> max-requests 周期重生兜底")
print("切割: tracemalloc 低 + RSS 高 = 驻留;tracemalloc 与 RSS 同涨 = 真泄漏(Q839)")
```

**追问**：1) 为什么 glibc 默认敢开 8×核数个 arena？——多线程高并发下单 arena 的锁是吞吐瓶颈，空间换时间；内存充裕的服务无所谓，常驻 Python 服务（几十线程）就吃亏。2) `malloc_trim(0)` 能当常规手段吗？——只能归还顶部连续空闲段，对散落碎片效果有限，且调用本身有成本；用于诊断定性，不用于常态治理。3) jemalloc 的 purge 会不会拖慢分配？——purgatory 机制用后台清理摊薄成本，多数服务 p99 反而改善（避免页错误尖峰）；要 A/B 实测而非默认切换（Q1376 口径）。

## 背诵要点
1. RSS 高 ≠ 泄漏：pymalloc arena 有活块不还 + glibc bin 不归内核，都是"驻留"。
2. glibc arena 默认 8×核数，多线程碎片放大；MALLOC_ARENA_MAX=2 常降 20-40% RSS。
3. 切割证据链：tracemalloc 低+RSS 高=驻留；malloc_trim 骤降=非泄漏；同涨=真泄漏。
