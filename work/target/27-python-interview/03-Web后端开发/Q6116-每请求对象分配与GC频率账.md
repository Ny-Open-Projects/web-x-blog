### Q6116 · 每请求对象分配与 GC 频率账

> 难度:★★★★★ | 标签:成本工程, gc, Web 服务

**问**:压测时发现 P99 有周期性毛刺，间隔与请求量相关；`gc` 模块统计显示 gen0 回收每秒上百次。单个请求会分配多少对象、gen0 阈值 700 意味着什么？Web worker 里 `gc.freeze()`、调阈值、关 GC 的取舍是什么（GC 参数基础见 Q402/Q414）？

**答**:结论：账目推导：gen0 阈值默认 700（净增"容器对象"计数），**单请求如果净增 ~2000 个容器对象（dict/list/中间对象），约每 0.3-0.5 请求触发一次 gen0 回收**——QPS 500 时 gen0 每秒上百次完全正常；gen0 回收本身暂停微秒级，但**触发 gen2（全量）回收时要遍历全部容器对象**，百万级对象时暂停几十毫秒，这就是周期性 P99 毛刺的来源。三段治理：a) **gc.freeze()**：启动期（import 完成、预热后）把常驻对象标记冻结——冻结对象不参与 gen0/gen1 扫描，只剩请求期临时对象在年轻代滚动，全量回收的遍历基数大幅缩水（pre-fork 场景还有共享页收益，引 Q5614）；b) **调阈值**：`gc.set_threshold(2000, 25, 50)` 放宽 gen0 减少频率、调低 gen1/gen2 倍率推迟全量——治标，垃圾滞留更久，RSS 略升；c) **关 GC（`gc.disable()`）**：只对"无环创建"的短生命周期请求可行（纯 Pydantic v2 核心路径可能成环，慎关），关了 GC 后循环引用靠引用计数永远清不掉，长期 RSS 缓涨——Web 服务**不建议裸关**，freeze+调阈值是稳妥组合。观测动作：`gc.set_debug(gc.DEBUG_STATS)`（3.13+ 有 stats）、`gc.get_stats()` 看各代回收次数分布，把"每秒 gen0 次数"与"gen2 距上次全量的秒数"做成指标。

```python
import gc, time, statistics

# 1) 观测基线：当前阈值与各代计数
print("阈值 (gen0, gen1, gen2):", gc.get_threshold())
print("各代对象计数:", gc.get_count())

# 2) 单请求分配画像：一个典型请求的容器对象净增
def handle_request():
    """模拟一个请求：构造校验模型、查询结果包装、响应对象"""
    request_ctx = {"user": "u1", "trace_id": "abc", "headers": {f"h{i}": "v" for i in range(12)}}
    rows = [{"id": i, "name": f"n{i}", "tags": ["a", "b"], "meta": {"k": "v"}} for i in range(50)]
    response = {"code": 0, "data": rows, "ctx": request_ctx}
    return len(response["data"])

before = gc.get_stats()[0]["collections"]      # gen0 已触发次数
gc.collect()                                    # 先清场
base = gc.get_stats()[0]["collections"]
for _ in range(100):                            # 跑 100 个"请求"
    handle_request()
after = gc.get_stats()[0]["collections"]
per_gen0 = max(after - base, 1)
print(f"100 请求触发 gen0 {per_gen0} 次 ≈ 每 {100/per_gen0:.1f} 请求一次回收")

# 3) freeze 收益：冻结常驻对象后 gen2 遍历基数下降
resident = [{"cache": i, "data": [0] * 100} for i in range(200_000)]   # 模拟常驻缓存
gc.collect()
if hasattr(gc, "freeze"):
    gc.freeze()
    print("freeze 后未追踪常驻对象:", gc.get_count(), "（常驻对象退出追踪集）")

# 4) 调阈值对照：gen0 频率的变化
gc.set_threshold(2000, 25, 50)                 # 放宽 gen0
base = gc.get_stats()[0]["collections"]
for _ in range(100):
    handle_request()
print("阈值放宽后 100 请求 gen0 次数:", gc.get_stats()[0]["collections"] - base)

# 5) 全量回收的暂停成本实测（毛刺来源）
big = [[j for j in range(50)] for _ in range(200_000)]   # 百万级容器
t0 = time.perf_counter(); gc.collect(2); t1 = time.perf_counter()
print(f"gen2 全量回收耗时: {(t1-t0)*1000:.1f}ms（这就是 P99 毛刺）")
del big
```

**追问一层**:为什么 Pydantic v2 校验/序列化这类"对象净增大户"对 gen0 压力最大？`__slots__`/不可变对象（tuple/str）为什么几乎不进追踪集（引 Q1273/Q423）？
**追二层**:free-threading（PEP 703）下 GC 改成保守式分代+暂停后的 Web 服务行为变化是什么？为什么 freeze 在 ft 构建下的语义要重新评估（对照 Q5577/Q411）？

**背诵要点**
- gen0 阈值 700 是"净增容器对象数"；单请求净增 ~2000 → 约每 0.3-0.5 请求一次 gen0；毛刺来自 gen2 全量的遍历暂停。
- 治理组合拳：预热后 `gc.freeze()`（缩 gen2 基数）+ 放宽阈值；裸 `gc.disable()` 会因循环引用 RSS 缓涨，Web 服务不建议。
- 指标化：gen0 次/秒、距上次 gen2 的秒数，与 P99 毛刺时刻对齐定位。

**复盘追问**
- freeze 后毛刺仍在，怎么证明 gen2 的遍历基数还是太大？提示：gc.get_objects() 抽样统计追踪对象总量，找"请求路径误入追踪集的常驻结构"。
- 有人提议在 worker 里 `gc.disable()` + 定时 `gc.collect(2)`，这个方案的失败模式是什么？提示：collect 时刻与流量无关，恰好撞高峰就是全量毛刺；改成低峰期触发或增量化。
