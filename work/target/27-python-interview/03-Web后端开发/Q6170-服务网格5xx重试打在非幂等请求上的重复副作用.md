### Q6170 · 服务网格 5xx 重试打在非幂等请求上的重复副作用

难度：P7 ｜ 标签：服务网格、重试、幂等性、Envoy、重复副作用

**问**：Istio/Envoy 默认常配 `retry_on: 5xx, connect-failure`，为什么这对 `POST /pay` 是灾难——上游其实"已经扣款成功但回 500"（如超时后写入才落库），网格重试一次就重复扣款？为什么"5xx 重试"只看状态码看不出"副作用是否已发生"？幂等方法白名单与 `Idempotency-Key` 各自在什么层面挡住重复？本题与 Q6019（超时预算分配）、Q1144/Q2864（重试预算/退避）的边界在哪？

**答**：
结论：5xx 只表达"响应状态"，不表达"请求处理到哪一步"——上游可能在写库成功后才超时/抛 500（响应丢失），此时客户端看到 500，网格按 `retry_on: 5xx` 重发，**同一笔业务执行两次**。GET/PUT/DELETE 从 HTTP 语义上是幂等的（多次执行效果等同一次，Q6160 的矩阵），重试相对安全；POST 非幂等，默认重试等于"随机重复副作用"。两道防线：① **网格层按方法白名单**——只重试 GET/HEAD/OPTIONS/PUT/DELETE，对 POST/PATCH 不自动重试（Envoy 可配 `retry_on` 配合 `x-envoy-retry-on`，但方法判定最好在路由层显式区分）；② **应用层幂等键**——客户端生成 `Idempotency-Key`，服务端按 key 记录首次结果，重放直接返回缓存响应（Q6160 的协议基础）——这是"即使网格重试了也不重复执行"的终极防线，因为它在业务语义层而非传输层。Q6019 管"超时预算怎么自上而下分配、避免重试放大拖长用户等待"，Q1144/Q2864 管"重试次数/退避/失败率闸门"，本题专攻"**重试对象的幂等性判定**"——一个管时间预算、一个管次数策略、一个管"能不能重试"的语义前提。

取舍：网格重试要同时满足三个条件才安全——**幂等方法 + 有限次数 + 总预算受控**（与上游 timeout 协同），缺一不可；对非幂等请求，宁可让客户端收到 500 自己决策（通常查单确认），也不要网格盲目重试。幂等键方案要处理 key 的生成（客户端 UUID）、存储（TTL 覆盖重试窗口）、并发去重（同一 key 并发到达时只执行一次）——成本高于"关掉 POST 重试"，但对支付/下单这类高价值操作是必须的。

实战：事故形态是"用户一次支付收到两笔扣款，网格日志显示两次 500→重试→200"——根因是 POST 走了 5xx 重试且无幂等键。下面模拟一条调用链：GET 安全重试、POST 无键触发重复执行、POST 带键在服务端去重，并展示"方法白名单 + 幂等键"双层防线。

```python
IDEMPOTENT = {"GET", "HEAD", "OPTIONS", "PUT", "DELETE"}

def upstream_chain(method, has_key, statuses, max_retries=2):
    """返回 (实际到达上游的次数, 真正的副作用次数)。"""
    arrivals = 0
    executed = 0
    seen = set()                        # 服务端幂等键去重（示意）
    for status in statuses:
        arrivals += 1
        if has_key and "k" in seen:
            pass                        # 重放：不重复执行，返回首次结果
        else:
            executed += 1               # 真正执行一次业务
            if has_key:
                seen.add("k")
        if status < 500:                # 成功，停止重试
            break
        if method not in IDEMPOTENT and not has_key:
            break                       # 安全防线：非幂等且无键 -> 不重试
        if arrivals - 1 >= max_retries:
            break
    return arrivals, executed

for method, key, statuses in [
    ("GET",  False, [500, 500, 200]),
    ("POST", False, [500, 500, 200]),
    ("POST", True,  [500, 500, 200]),
]:
    arrivals, executed = upstream_chain(method, key, statuses)
    print(f"{method:4} key={key!s:5}: 上游收到 {arrivals} 次, 真正执行 {executed} 次")
```

**追问一**：为什么 PUT/DELETE 幂等但仍建议谨慎开网格重试？——HTTP 语义的幂等是"效果等同一次"，但工程上 DELETE 重复执行可能返回 404（第二次报错）、PUT 带时间戳字段可能生成不同版本；更重要的是"幂等"不保证"无副作用"——PUT 触发的事件通知、DELETE 触发的审计日志可能重复。所以白名单只是"降低风险"，不是"绝对安全"，高价值写操作仍应叠加幂等键或业务级去重。

**追问二**：幂等键与网格重试怎么协同才不会"重试窗口"与"key 的 TTL"错配？——幂等键的 TTL 必须**覆盖整个重试窗口**（网格重试次数 × 单次超时 + 客户端重试），否则 key 过期后重试到达就变成"新请求"、重复执行。实务上把 TTL 设为"最大重试窗口的 2~3 倍"，并在返回 200 后仍保留一段时间以防迟到重试；同时网格重试的 `attempt` 次数与超时预算要在配置里与设计文档对齐，避免"改了重试次数没改 TTL"的隐性错配——这与 Q6019 的超时预算协同是同一条纪律。

## 背诵要点
- 5xx 只表示响应状态，不表示副作用未发生；POST 走 5xx 重试会重复执行。
- 两道防线：网格按幂等方法白名单重试（GET/PUT/DELETE）；应用层 Idempotency-Key 在业务层去重（终极防线）。
- 与 Q6019（时间预算）/Q1144（次数退避）分工：本题管"能不能重试"的幂等前提；key TTL 要覆盖整个重试窗口。
