### Q6142 · URL 双重解码与路径穿越事故

难度：P6 ｜ 标签：urllib.parse、percent-encoding、路径穿越、安全

**问**：文件下载接口用 `unquote(path)` 后拼接磁盘路径，WAF 拦了 `../` 却还是被 `%252e%252e%252f` 穿越。为什么二次解码会绕过校验？percent-encoding 的"解码在哪一层发生"如何决定安全边界？正确的校验姿势是什么？

**答**：
结论：`%252e` 是"被编码的 `%2e`"——第一层 `unquote` 得到 `%2e%2e%2f`，字符串上看不出 `..`，任何基于明文黑名单的校验都会放行；框架/中间件再做一次解码（或代码里手滑 unquote 两次），就还原成 `../` 完成穿越。根因是**解码发生在多个层**（WAF、框架路由、应用代码），而校验只在其中一层做了明文检查。原则：**解码一次、归一化一次、校验一次，且都在同一层**——进入业务代码后绝不再 unquote，也不把"已解码路径"再交给会解码的组件。

取舍：白名单/前缀校验（realpath 后必须落在基目录内）比黑名单可靠；`os.path.realpath` 消解 `..` 与符号链接后做前缀比对（注意 symlink 本身可能指向外面，用 `realpath` 后再 `commonpath` 判断）。拒绝后返回 400 而不是 404，避免给扫描器枚举信息。

实战：修复清单——① 应用层只 unquote 一次并立即校验；② 校验用 realpath + `Path.is_relative_to`（3.9+）；③ WAF 规则补充对 `%25`（双重编码特征）的告警；④ 测试用例固化攻击样本集（%2e、%252e、UTF-8 过长编码 %c0%ae 等）。

```python
import urllib.parse
import os
from pathlib import Path

attack = "%252e%252e%252f%252e%252e%252fetc%252fpasswd"

once = urllib.parse.unquote(attack)
print("decode once :", once)            # ../..//../etc/passwd 形态之一
print("looks evil? :", ".." in once)    # 第二次解码前明文校验被骗过

twice = urllib.parse.unquote(once)
print("decode twice:", twice)           # 穿越链完整显形

# 正确姿势：解码一次 -> realpath 归一 -> 基目录包含校验
BASE = Path("/srv/downloads").resolve()

def safe_join(user_path: str) -> Path:
    decoded = urllib.parse.unquote(user_path)      # 只解一次
    if "%25" in decoded or "%2e" in decoded.lower():
        raise ValueError("suspicious double-encoding")
    candidate = (BASE / decoded).resolve()          # 消解 .. 与符号链接
    if not candidate.is_relative_to(BASE):          # 3.9+；穿越即拒绝
        raise ValueError("path escapes base dir")
    return candidate

for probe in ["report.pdf", "../secret", attack, "a/../../b"]:
    try:
        print(probe, "->", safe_join(probe))
    except ValueError as e:
        print(probe, "-> REJECTED:", e)

# open 前最后一道防线：文件描述符层面用 dir_fd 防符号链接竞态（TOCTOU）
import tempfile, shutil
d = tempfile.mkdtemp()
p = os.path.join(d, "ok.txt")
open(p, "w").write("hi")
dfd = os.open(d, os.O_RDONLY)                        # 以目录 fd 打开，穿越被内核拒绝
try:
    fd = os.open("../etc/passwd", os.O_RDONLY | os.O_NOFOLLOW, dir_fd=dfd)
    os.close(fd)
    print("dir_fd open unexpectedly ok")
except OSError as e:
    print("dir_fd blocks traversal:", e.errno)
os.close(dfd)
shutil.rmtree(d)
```

**追问一**：为什么"解码两次"会真实发生而不只是代码手误？——常见链路：上游代理已解一次、框架路由再解一次（Starlette/Flask 默认解 path 参数）、应用又 unquote；每层都"以为自己是第一层"，所以规范必须规定"解码层唯一"。

**追问二**：`is_relative_to` 与 `realpath` 后字符串前缀比较的差异？——字符串 startswith 可被 `/srv/downloads-evil` 前缀欺骗；`is_relative_to` 基于路径结构比较；resolve 已处理 symlink，但仍要注意 resolve 时 symlink 目标被移走的 TOCTOU，高敏场景用 `dir_fd`/`O_NOFOLLOW`。

**追问三**：UTF-8 过长编码（%c0%ae = 超长 '.')在现代栈还可行吗？——严格 UTF-8 解码器会拒绝超长序列（Python 3 直接报错），但某些后端组件（老版 IIS/自定义解码器）仍接受；防御上按"禁止非规范 UTF-8"统一处理，样本进测试集。

## 背诵要点
- `%252e` 是双重编码：明文校验看不出来，多层各自解码即穿越；解码必须只发生在唯一一层。
- 校验三步：unquote 一次 → `resolve()` 归一 → `is_relative_to(BASE)` 拒绝；补充 `%25/%2e` 特征检测。
- TOCTOU 用 `dir_fd` + `O_NOFOLLOW` 在内核层兜底；拒绝返回 400，不给枚举信息。
