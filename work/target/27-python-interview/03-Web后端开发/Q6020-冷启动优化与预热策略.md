### Q6020 · 服务冷启动与预热

> 难度:★★☆ | 标签:冷启动, 预热, 弹性伸缩

**问**：流量洪峰触发 HPA 扩容，新 Pod 起来后为什么前 30 秒请求延迟翻 10 倍——冷启动的开销清单有哪些（JIT 无关，Python 是什么在慢）？预热怎么做（连接/缓存/JIT 式热点路径），readiness 怎么配才不把冷 Pod 暴露给流量？

**答**：Python 服务冷启动开销清单：① **解释器启动 + import 全量依赖**（FastAPI+Pydantic v2 冷 import 可 2-5s）；② **连接池逐个建连**（DB/Redis 各 5-20 连接，串行建 = 秒级）；③ **运行时热点未热**：字节码特化（3.11+ adaptive interpreter）、dict 键哈希缓存、ORM 反射、正则编译首次触发；④ **进程内缓存全空**（本地 LRU 全 miss，全量回源下游——**冷 Pod 的回源风暴**反过来冲击下游，是扩容毛刺的主因）。预热方案：lifespan 阶段做四件事——并行建连池、主动调用 TopN 热点路径（自探测流量）、加载本地缓存快照（从 Redis 导）、正则/ORM 显式编译。readiness 配置：readiness 探针**必须等预热完成**（应用内部预热标志位），否则冷 Pod 接流即毛刺；HPA 阈值要留预热时长余量，防止「扩容→毛刺→误判需要再扩→过扩」的振荡。

```python
# 全部标准库；demo 演示冷/热路径差异与 lifespan 预热骨架
import time, functools, asyncio

def cold_cost():
    """开销②③：import 与首次调用成本实测。"""
    t0 = time.perf_counter()
    import json, re, email.utils          # 模拟依赖 import
    import_cost = time.perf_counter() - t0
    t1 = time.perf_counter()
    re.compile(r"^\w+@[a-z]+\.[a-z]{2,}$").match("a@b.co")   # 首次编译
    first_call = time.perf_counter() - t1
    return import_cost, first_call

@functools.lru_cache(maxsize=None)
def hot_path(x: int) -> int:
    time.sleep(0.05)                      # 模拟昂贵计算
    return x * x

class WarmupGate:
    """readiness 预热闸门：预热完成才接流。"""
    def __init__(self):
        self.ready = False
        self.warm_cache: dict[int, int] = {}
    async def warmup(self):
        # ① 并行建连（模拟）
        conns = await asyncio.gather(*[asyncio.sleep(0.02) for _ in range(5)])
        # ② 预热 TopN 热点路径（自探测）
        for i in range(20):
            self.warm_cache[i] = hot_path(i)
        self.ready = True                 # ③ 探针据此返回 200
        return len(conns)

async def app_handler(x: int, gate: WarmupGate) -> int:
    if not gate.ready:
        raise RuntimeError("503: not ready（readiness 未就绪时流量本不该进来）")
    return gate.warm_cache.get(x) or hot_path(x)

if __name__ == "__main__":
    ic, fc = cold_cost()
    print(f"import 开销 {ic*1000:.1f}ms；首次调用 {fc*1000:.1f}ms（冷）")
    t0 = time.perf_counter(); hot_path(99); cold_ms = (time.perf_counter()-t0)*1000
    t1 = time.perf_counter(); hot_path(99); hot_ms = (time.perf_counter()-t1)*1000
    print(f"同参首次 {cold_ms:.0f}ms vs 命中缓存 {hot_ms:.3f}ms —— 差距即冷启动毛刺来源")
    gate = WarmupGate()
    assert not gate.ready
    n = asyncio.run(gate.warmup())
    assert gate.ready
    print(f"预热完成（{n} 连接 + 20 热点路径），readiness 放行")
    # 部署口径：readiness 探针打应用内部 /readyz（查 gate.ready），
    # 预热耗时计入 HPA 反应预算；冷 Pod 回源风暴靠「预热拉缓存快照」抑制。
```

**追问**：1) 为什么说「冷 Pod 回源风暴」比自身慢更危险？——扩容本意是分流，冷 Pod 缓存全 miss 反而放大下游 QPS（命中率跌 → 回源翻倍），下游被打挂后整个服务雪崩——预热缓存快照是防这个的。2) Python 3.11+ adaptive interpreter 的「热身」怎么观测？——`-X importtime` 看 import 成本；特化（PEP 659）无直接 API，微基准跑万次前后对比；生产口径看扩容后 5 分钟内 P99 恢复斜率。3) Serverless 场景的冷启动怎么办？——快照恢复（snapshot/Firecracker 类）、常驻最小实例（保底并发）、依赖瘦身（import 树裁剪），Python 侧还有 `PYTHONDONTWRITEBYTECODE` 关闭后的 pyc 预热反向优化。

## 背诵要点
1. 冷启动四开销：import 树、建连串行、热点未特化、进程内缓存全空——最后者会引发回源风暴打挂下游。
2. 预热四件套（lifespan 内）：并行建连、自探测热点路径、缓存快照导入、显式编译。
3. readiness 必须等预热标志位；HPA 阈值留预热时长余量防振荡。
