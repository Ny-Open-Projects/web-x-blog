### Q6068 · 数据归档冷热分层的成本账

> 难度:★★★☆ | 标签:成本工程, 归档, 冷热分层, 容量治理

**问**：订单表三年涨到 8 亿行，OLTP 查询越来越慢、备份窗口超时。冷热分层怎么分界？归档的四条实现路径（分区表/独立归档表/对象存储/宽时序库）成本差异是什么？归档迁移怎么做到业务无感？查询冷数据的路径怎么设计？

**答**：成本账：数据按访问频率分层——热（<90 天，高频 OLTP 查询，SSD 主库）、温（90 天-2 年，偶发查询，便宜的列存/压缩表）、冷（>2 年，审计/合规要求，对象存储 gzip+Parquet 或归档库）。**主库行数本身就是成本**：索引 B+ 树深度、备份窗口、VACUUM/vacuum 成本、复制带宽都随行数走——8 亿行砍到 6 千万，主库内存/IO 需求常降一个数量级，这是"归档不是省钱是保命"的论据。四条路径对比：a) **分区表（PG declarative partition / MySQL 分区）**：按时间 RANGE 分区，归档=detach 分区（秒级 O(1)），查询带时间条件自动分区裁剪——首选，前提是查询模式带时间；b) **独立归档表/库**：job 批量 INSERT SELECT + DELETE（要分批防大事务，锁与复制延迟代价），灵活但双写期一致性要小心；c) **对象存储（Parquet+gzip）**：成本最低（S3 归档层 $/TB/月 是主库 SSD 的几十分之一），查询走 Athena/外部表——适合纯审计；d) **列存/时序库**（ClickHouse/时序化）：温层分析查询。迁移无感三步：①双写期（新数据照旧、归档 job 开始搬历史）；②路由期（DAO 层按时间路由：近查主库、远查归档，业务无感）；③清理期（主库批量删+分区 detach，夜间窗口限速防复制堆积）。查询路径：统一查询入口按时间分派（分页深翻跨层要合并结果，cursor 按 created_at 排序天然分层友好，见 Q6053），冷查询要"慢查询通道"标记（异步化/超时更宽），防止大范围冷查询打到主库。

```python
# file: code/03_Web后端开发/q6068_archive_tiering.py
import sqlite3, gzip, json, time

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE orders(ts REAL, id TEXT, amount REAL);
CREATE TABLE orders_archive(ts REAL, id TEXT, amount REAL);
CREATE INDEX idx_orders_ts ON orders(ts);
""")

# 造 3 年数据: 热近 90 天 1 万行, 历史 3 万行
now = time.time()
rows = [(now - 86400 * 1095 * (i / 40000), f"o{i}", 100.0) for i in range(40_000)]
db.executemany("INSERT INTO orders VALUES(?,?,?)", rows)

# 1) 归档 job: 分批搬运历史 (batch 防大事务/复制堆积)
def archive_job(cutoff_days=90, batch=5000):
    cutoff = now - 86400 * cutoff_days
    moved = 0
    while True:
        cur = db.execute(
            "SELECT rowid FROM orders WHERE ts < ? LIMIT ?", (cutoff, batch))
        ids = [r[0] for r in cur.fetchall()]
        if not ids: break
        db.execute(f"INSERT INTO orders_archive SELECT * FROM orders WHERE rowid IN "
                   f"({','.join('?'*len(ids))})", ids)
        db.execute(f"DELETE FROM orders WHERE rowid IN ({','.join('?'*len(ids))})", ids)
        db.commit()
        moved += len(ids)
        time.sleep(0.001)                 # 限速, 防复制延迟堆积
    return moved

t0 = time.perf_counter()
n = archive_job()
print(f"归档 {n} 行耗时 {time.perf_counter()-t0:.2f}s, 主库剩 {db.execute('SELECT count(*) FROM orders').fetchone()[0]} 行")

# 2) 分层查询路由: 按时间条件分派
def query_orders(ts_from, ts_to):
    cutoff = now - 86400 * 90
    results = []
    if ts_to >= cutoff:                   # 热层: 主库带分区裁剪语义
        results += db.execute("SELECT id FROM orders WHERE ts BETWEEN ? AND ?",
                              (max(ts_from, cutoff), ts_to)).fetchall()
    if ts_from < cutoff:                  # 冷层: 归档表 (生产: Parquet+外部表)
        results += db.execute("SELECT id FROM orders_archive WHERE ts BETWEEN ? AND ?",
                              (ts_from, min(ts_to, cutoff))).fetchall()
    return [r[0] for r in results]

res = query_orders(now - 86400 * 120, now)
print("跨层查询合并:", len(res), "行 (cursor 按 ts 排序天然跨层友好)")

# 3) 冷层压缩成本: 对象存储 Parquet 演示为 gzip JSON
blob = gzip.compress(json.dumps(
    [db.execute("SELECT * FROM orders_archive LIMIT 100").fetchall()]).encode())
print(f"冷层压缩演示: gzip {len(blob)/1024:.0f}KB (生产: Parquet+对象存储归档层, 成本主库的1/30)")

# 4) 慢查询通道: 冷查询异步化
print("路由规则: 近90天主库(分区裁剪) / 历史归档通道(异步+宽超时) / 深翻页用 cursor")
```

**追问**：1) 分区表与归档表怎么选？——查询模式带时间+主库支持好就分区表（detach 是 O(1) 且查询自动裁剪）；归档到独立库/对象存储才是"搬出主库"，分区只是"主库内隔离"，两者常组合：分区表热温层 + detach 后导 Parquet 冷层。2) 归档 job 的限速参数怎么定？——以复制延迟和主库 IO 水位为准（batch 行数×批间隔要使 lag<1s，对照 Q6067 的摘除水位）；夜间窗口+主备切换错峰；大批量 DELETE 分批并留意锁范围（按主键/rowid 批删）。3) 合规要求"7 年可查"和"业务查询 90 天"怎么共存？——把"可查"降级为"可恢复"：冷层 Parquet 归档可还原成查询库（按需起外部表/临时实例），业务查询走 90 天热层；审计场景用 Athena 类引擎按需查，别为合规维护常驻热库——这是分层的核心成本逻辑。

## 背诵要点
- 主库行数本身就是成本：索引深度/备份窗口/vacuum/复制带宽随行数走；分层=热(<90天主库)/温(列存)/冷(对象存储 Parquet)。
- 四路径：分区表 detach（O(1) 首选）、归档表分批搬运（限速防复制堆积）、对象存储 Parquet（成本 1/30）、列存库（温层分析）。
- 无感迁移三步：双写→DAO 按时间路由→清理；冷查询走异步慢通道，cursor 按时间排序跨层友好。

## 复盘追问
- 你们最大的表多少行？查询是否都带时间条件（分区裁剪的前提）？（提示：对照本卡账算归档收益；检查查询模式是否适合分区）
- 归档 job 有没有限速与复制延迟联动？冷查询会不会意外打到主库？（提示：路由层白名单+异步通道；演练一次全量归档的 lag 水位）
