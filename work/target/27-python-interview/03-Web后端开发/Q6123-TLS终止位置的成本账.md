### Q6123 · TLS 终止位置的成本账：LB 终止 vs 应用终止

> 难度:★★★★☆ | 标签:成本工程, TLS, 架构

**问**:TLS 在 LB 上终止还是每台应用机自己终止？握手 CPU、会话复用、内网明文三笔账怎么算？为什么"应用终止"在 Python 服务里通常单核 QPS 掉一半以上？Passthrough/mTLS 场景怎么选？

**答**:结论：三笔账决定位置。a) **握手 CPU**：TLS 1.2 RSA 握手约 1-3ms CPU（ECDHE 更重），TLS 1.3 一次往返但 ECDHE 计算不变；若应用终止且每请求新建连接，Python 单核每秒几百次握手就把 CPU 吃满——LB 终止则用专用硬件/Go 协程消化，且**会话复用**（session ticket/resumption，TLS 1.3 PSK 0-RTT 见 Q5511）能把二次握手降到近乎免费。b) **连接复用率**：终止在 LB 后，LB→app 是内网明文长连接（HTTP keep-alive），app 只付"明文解析"成本；应用终止则每条客户端连接都带 TLS 状态机内存（每连接 30-80KB），长连接万级时内存账也不小。c) **合规/信任**：内网明文是"终止在 LB"的代价——零信任/金融场景要求端到端加密，就得 passthrough 或 mTLS（服务间认证见 Q6021），此时 app 必须付握手账，缓解手段：连接复用（upstream keep-alive）+ 会话票据 + 把握手限流放在内核层。取舍总结：公网入口 → LB 终止；内部强信任需求 → passthrough/mTLS；"应用终止 + 短连接"是最差组合。

```python
import ssl, socket, time, hashlib

# ---- 1) 密码学操作成本下界（决定握手 CPU 账） ----
t0 = time.perf_counter()
for _ in range(200):
    hashlib.pbkdf2_hmac("sha256", b"k", b"s", 1000)     # 模拟一次重计算
t1 = time.perf_counter()
print(f"参考点: 一次'重'密码学计算 ~{(t1-t0)/200*1000:.2f}ms —— TLS 握手的 ECDHE/RSA 同量级")

# ---- 2) 每连接 TLS 状态内存（应用终止的内存账） ----
ctx = ssl.create_default_context()
print(f"SSLContext 单例可复用；每连接 SSL 对象 + 读写缓冲约 30-80KB")
print(f"万级长连接应用终止: 约 {10000*0.06:.1f} GB 量级状态内存（LB 终止时该账归零）")

# ---- 3) 账本模型：两种终止位置的每请求成本 ----
def cost_model(qps, mode):
    """粗账模型: 返回每请求摊到的 CPU 毫秒。"""
    if mode == "lb":            # LB 终止: app 只付明文解析
        return 0.8              # ms/req(应用侧), 握手成本在 LB 且被会话复用摊薄
    if mode == "app-ka":        # app 终止 + 客户端长连接复用
        return 0.8 + 0.05       # TLS 记录层加解密 ~5%
    return 0.8 + 1.5            # app 终止 + 短连接: 每请求一次握手

for mode in ("lb", "app-ka", "app-short"):
    c = cost_model(1000, mode)
    print(f"{mode:10s}: {c:.2f} ms CPU/请求 -> 单核 QPS 上限 ≈ {1000/c:.0f}")

# ---- 4) ssl 模块侧证据: 会话复用开关 ----
ctx2 = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
print("session ticket 支持:", hasattr(ctx2, "num_tickets"), "(TLS1.3 PSK/会话复用由 LB 层开启)")
```

**追问一层**:为什么 TLS 1.3 的 0-RTT 不能随便开？（重放风险：0-RTT 数据无防重放保证，幂等以外的请求会被重放——网关层要按路径白名单启用，呼应 Q5511）。
**追问二层**:LB 终止后如何不丢客户端证书/来源信息？（PROXY protocol v2 / Forwarded 头传递源 IP；mTLS 客户端证书指纹经头透传并由应用校验签名，防止伪造，呼应 Q6121）。
**追问三层**:Python 应用必须端到端加密时的优化顺序？（1. upstream 长连接池复用 TLS 会话；2. 会话票据缓存共享；3. 重握手限频；4. 把大流量路径切到 passthrough 的专用网关）。

## 背诵要点
- 三笔账：握手 CPU（1-3ms/次）、会话复用（二次握手近免费）、每连接 TLS 状态内存 30-80KB。
- 最差组合是"应用终止 + 短连接"：单核 QPS 可掉一半以上；LB 终止 + upstream 长连接是默认解。
- 零信任/合规用 passthrough/mTLS，代价由会话复用与长连接池摊薄；0-RTT 有重放风险按路径白名单。
