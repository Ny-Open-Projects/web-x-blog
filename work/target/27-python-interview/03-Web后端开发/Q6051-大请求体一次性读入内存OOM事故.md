### Q6051 · 大请求体一次性读入内存 OOM 事故复盘

> 难度:★★★ | 标签:multipart, UploadFile, SpooledTemporaryFile, 流式, 事故复盘

**问**：开放文件上传 API 后，几个 500MB 的并发上传直接把 2GB 的容器打爆（OOMKilled）。`await request.body()` 和 UploadFile 的内存模型差在哪？SpooledTemporaryFile 的阈值机制是什么？除了流式还要配哪几道防线？

**答**：根因是**全量物化**：`request.body()`/`json()` 会把整个请求体读进 bytes（再加解析副本，JSON 场景峰值 2-3 倍），N 个并发大上传 = N × 体积 × 倍数，2GB 容器几个并发就死。Starlette 的正确姿势是 `UploadFile`：底层是 `SpooledTemporaryFile`——**小文件留在内存，超过 max_size 阈值自动滚动落盘**，配合框架的分块读取（form parser 按 chunk 搬运），内存占用恒定为 chunk+阈值而不是文件大小。防线再加三道：a) **入口限流**：`Content-Length` 预检（Nginx `client_max_body_size` + 应用层拒绝），不要等读完才报 413；b) **限速/排队**：上传类接口单独的并发信号量，避免大文件挤占工作线程；c) **校验后落盘**：扩展名/MIME/魔数校验 + 存储路径用户输入不可控（防穿越），响应前不信任文件名。认知点：SpooledTemporaryFile 的 `_rolled` 可观测、`max_size` 是字节阈值；落盘位置是系统临时目录，磁盘容量与清理策略（临时区容量账，见 Q6054 的姊妹题）也要进容量表。

```python
# file: code/03_Web后端开发/q6051_upload_oom.py
import io
from tempfile import SpooledTemporaryFile

# 1) 事故复现模型: 一次性读入(框架层面)
body = io.BytesIO(b"x" * (8 * 1024 * 1024))     # 模拟 8MB 请求体
naive = body.read()                              # 反例: 全量物化, 峰值=文件大小
print("一次性读入占用:", len(naive) / 1024 / 1024, "MB × 并发数")

# 2) 正解: SpooledTemporaryFile 分块搬运, 超阈值自动落盘
max_mem = 512 * 1024
body.seek(0)
with SpooledTemporaryFile(max_size=max_mem, mode="w+b") as spool:
    total = 0
    while True:
        chunk = body.read(64 * 1024)
        if not chunk:
            break
        spool.write(chunk)
        total += len(chunk)
    print(f"共接收 {total/1024/1024:.1f}MB, 阈值 {max_mem//1024}KB, 已滚动落盘: {spool._rolled}")
    spool.seek(0)
    print("处理后回读头部:", spool.read(8))

# 3) 防线清单
print("防线: Content-Length 预检(413) -> 上传并发信号量 -> 校验(魔数/扩展名) -> 流式写存储")
# FastAPI 用法: async def upload(file: UploadFile):
#   async for chunk in file:  /  await file.read(chunk_size)  -- 框架已走 SpooledTemporaryFile
```

**追问**：1) `UploadFile.read()` 是 async 的，它背后真的不阻塞吗？——Starlette 的 UploadFile.run_in_threadpool 把同步 SpooledTemporaryFile 读写丢线程池，大文件的磁盘 IO 不会阻塞事件循环；但线程池大小是隐式共享资源，大上传并发高会挤占它（呼应 Q5506 的池饱和）。2) 为什么不建议在 handler 里 `file.read()` 一次读完再处理？——等价于把落盘文件又全量物化回内存，防线白建；必须按 chunk 循环。3) 多文件表单上传的内存形态？——form parser 逐字段流式解析，每个 UploadFile 各自 spool；同时上传 K 个大文件 = K 个落盘文件 + K 个阈值内内存缓冲，并发上限要按这个乘积算。

## 背诵要点
- `request.body()` 全量物化 ×(1-3 倍解析副本)；UploadFile=SpooledTemporaryFile 分块搬运，内存恒定 chunk+阈值。
- SpooledTemporaryFile：`max_size` 字节阈值，超过自动滚落系统临时目录（`_rolled` 可观测），磁盘容量也要进容量账。
- 防线四件套：Content-Length 预检 413 → 上传并发信号量 → 魔数/扩展名校验 → 流式直写存储。

## 复盘追问
