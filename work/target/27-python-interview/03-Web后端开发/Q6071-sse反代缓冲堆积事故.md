### Q6071 · SSE 被反向代理缓冲堆积的事故复盘

> 难度:★★★☆ | 标签:事故复盘, SSE, 反向代理, nginx

**问**：SSE 接口本地直连 uvicorn 秒推，过了 nginx 之后消息"攒够一批才到"，客户端看到 10-60 秒延迟。反向代理为什么缓冲 SSE？X-Accel-Buffering、gzip 对 SSE 的影响、Content-Type 与分段响应头各自的正确设置是什么？K8s ingress/APISIX/Cloudflare 这类层还有哪些各自的坑？

**答**：结论：nginx 反代默认开启 `proxy_buffering on`，上游响应**先进 nginx 缓冲区**、凑满或响应结束才发下游——流式接口被它改造成"批处理"，这是 SSE 延迟事故的头号根因。完整配置清单（服务端主动声明，避免依赖网关侧配置漂移）：a) `X-Accel-Buffering: no` 响应头——nginx 看到它按请求级关闭缓冲，这是唯一能让应用层自带开关的方式；b) `Content-Type: text/event-stream` + `Cache-Control: no-cache` + `Connection: keep-alive`，部分中间件（某些 WAF/SDK）会按 Content-Type 误判做聚合；c) **关闭 gzip**：SSE 响应被压缩后会缓冲整个压缩块，且事件边界被打散，`gzip off`（或对该 location 不压缩）；d) 首字节即发：SSE 协议要求连接建立后立刻发一个心跳/注释行（`: ping\n\n`），让 nginx/客户端确认流已开始，很多"全延迟"其实是首事件前的缓冲。分层坑：K8s ingress-nginx 默认同样 proxy_buffering（配置同上）；APISIX/Lua 层有独立 body filter 缓冲；Cloudflare 免费版对流式响应有 100s 无数据断连，心跳间隔必须小于它；服务端自己的 StreamingResponse 若用了会聚合的中间件（如响应压缩中间件）同样复现。实战：SSE 链路上做"逐跳延迟观测"——服务端打点 send 时间、客户端打点 receive 时间，差值按跳归因，别靠猜。

```python
# file: code/03-Web后端开发/q6071_sse_buffering.py
import asyncio, time, sys

# SSE 正确响应头与心跳(标准库 ASGI 形态, 无需框架也能说明语义)
SSE_HEADERS = [
    (b"content-type", b"text/event-stream"),
    (b"cache-control", b"no-cache"),
    (b"x-accel-buffering", b"no"),          # 让 nginx 按请求关缓冲(事故一的解药)
    (b"connection", b"keep-alive"),
]

async def sse_app(scope, receive, send):     # 极简 ASGI app
    await send({"type": "http.response.start", "status": 200, "headers": SSE_HEADERS})
    # 关键: 连接建立先发注释心跳, 首字节立即可达
    await send({"type": "http.response.body", "body": b": ping\n\n", "more_body": True})
    for i in range(3):
        await asyncio.sleep(0.05)
        body = f"event: t\ndata: msg-{i}\n\n".encode()
        await send({"type": "http.response.body", "body": body, "more_body": True})
        print(f"send t={time.perf_counter():.3f} msg-{i} (服务端打点)")
    await send({"type": "http.response.body", "body": b"", "more_body": False})

# 模拟"nginx 缓冲层" vs "透传层": 对比客户端 receive 时序
async def fake_proxy(buffering: bool):
    sent = []                                  # (send时刻, 数据)
    async def app_send(msg):
        if msg["type"] == "http.response.body" and msg.get("body"):
            sent.append((time.perf_counter(), msg["body"]))
    await sse_app(None, None, app_send)
    # 反代转发时机: buffering=on 时凑满(演示: 最后统一 flush)
    flushed = []
    if buffering:
        payload = b"".join(b for _, b in sent)
        flushed = [(time.perf_counter(), payload)]
    else:
        flushed = sent
    print(f"proxy_buffering={buffering}: 客户端收到 {len(flushed)} 次 flush, "
          f"末次距首条 send {(flushed[-1][0]-sent[0][0])*1000:.0f}ms")

async def main():
    await fake_proxy(True)                     # 事故形态: 攒批, 客户端一次性收到
    await fake_proxy(False)                    # 正确形态: 逐条可达

asyncio.run(main())
print("SSE 检查单: X-Accel-Buffering:no / text-event-stream / gzip off / 首包心跳 / 逐跳打点")
print("python:", sys.version.split()[0])
```

**追问**：1) `X-Accel-Buffering` 为什么比改 nginx 配置好？——它把开关放在应用响应头里，跟随代码走、逐接口生效，不依赖网关配置版本；但只对 nginx 系有效（ingress-nginx 支持，Envoy/APISIX 要各自的流式配置），所以**逐跳都要核**，响应头只是第一跳的解药。2) SSE 和 WebSocket 在这类代理问题上的差异？——SSE 是 HTTP 响应流，全靠响应头的逐跳声明，任何中间层都可能缓冲；WebSocket 走 Upgrade 成隧道后中间层不再解析 body，缓冲问题少但粘性/超时问题多（Q6005）；长连接健康度上 SSE 更容易被 HTTP 层观测（有状态码、有响应头）。3) 事件里加 `id:` 字段和重连协议（Last-Event-ID）跟缓冲问题有关系吗？——间接相关：代理缓冲导致的"批量到达"会让客户端 last-id 跳跃，重连补发逻辑必须按 id 去重补齐，而不是假设"逐条有序到达"。

## 背诵要点
- SSE 延迟事故头号根因是反代 proxy_buffering 攒批；应用层解药是 `X-Accel-Buffering: no` + text/event-stream + no-cache + keep-alive。
- gzip 会缓冲并打散事件边界，SSE 链路必须关压缩；连接建立先发 `: ping` 注释心跳让首字节立即可达。
- 逐跳都要核（ingress/APISIX/CDN 各有缓冲与空闲超时，Cloudflare 100s 断连），观测靠服务端 send 与客户端 receive 双打点。

## 复盘追问
- 你们 SSE 上线时有没有做过"逐跳延迟归因"？如果客户端反馈 30 秒延迟，你的排查顺序是什么？（提示：curl -N 直连 vs 过网关对比，抓 nginx access log 的 $request_time 与 $upstream_response_time 差值）
- 事件堆积在代理缓冲区时服务端以为已送达，这个"假成功"对业务重试逻辑意味着什么？（提示：SSE 送达语义本就是尽力而为，关键业务要 Last-Event-ID 补发 + 业务侧 ACK，不要把 SSE 当可靠投递，见 Q6013 Webhook 可靠投递对照）
