### Q6246 · 缓存雪崩：TTL 抖动、多级兜底与批量失效的容量账

难度：P6 ｜ 标签：缓存雪崩、TTL 抖动、批量失效、缓存预热、多级缓存、熔断降级、Redis 故障、回源风暴

**问**：缓存雪崩与击穿（Q6066）、穿透（Q6243）的边界是什么——"大批 key 同时失效"与"Redis 整体不可用"两条路径的连锁反应链是什么？TTL 加随机抖动的正确做法与常见错误（抖动范围过小/过大）是什么？预热、多级缓存、熔断降级在雪崩防御里的分层职责？

**答**：
结论：雪崩的两种触发形态与同一条连锁链：①**批量过期**——大批 key 用同一 TTL（如批量预热、定点任务写入），到期瞬间集中回源，DB 瞬时 QPS = 集中失效量 ÷ 回源耗时，打满连接池（Q6046）后排队雪崩；②**缓存层不可用**——Redis 宕机/网络抖动，全部流量直达 DB，DB 扛不住连锁扩大的超时与重试（重试放大），上层线程池耗尽，**服务整体不可用**——比"慢"更糟的是重试风暴把故障传播给上游（Q5603 重连风暴同构）。防御按"失效形态"分层：①**TTL 抖动**治批量过期——`ttl = base + random.uniform(0, spread)`，spread 取 base 的 10%-20%（如 base 3600s、抖 300s）：分散失效峰值又不显著降低缓存效率；**常见错误**：spread 过小（±5s）在批量写入场景等于没抖（峰值仍集中）、抖动用固定 hash 而非随机（同批 key 抖出同值）、以及**定时任务刷新缓存用同一时刻**（预热本身就是批量失效源——预热时也要抖动）；②**多级缓存**治"总量"——本地进程缓存（短 TTL 5-30s）+ Redis（长 TTL）双层，Redis 抖动时本地层兜住部分流量，回源风暴的"波及系数"从 1.0 降到本地命中率；③**熔断/限流兜底**治"最坏情况"——回源路径上限流（DB 每秒最多 N 次回源，其余快速失败/降级默认值，Q1334/Q1337），Redis 客户端熔断（连续超时短路 Redis 直走降级，避免在死 Redis 上排队），DB 连接池水位告警（Q6046）；④**预热**治冷启动——发布后先灌缓存再放量（Q1920 预热期判据），预热批量写入必须带抖动。

取舍：a) 抖动范围与业务形态：定时刷新型任务（整点榜单）用"固定基点+抖动"，用户行为型（会话、订单详情）抖动范围可更宽；热点 key 不适用大抖动（抖走热 key 等于主动击穿，热点走单飞+逻辑过期，Q6066）；b) 逻辑过期方案：物理 key 永不过期、值里带逻辑过期时间，过期后异步重建返回旧值——彻底消灭"过期瞬间回源"，代价是短暂数据陈旧与全量 key 常驻内存——**热点字典类**数据适用，长尾数据内存成本不可接受；c) Redis 故障演练：雪崩预案要真演练（kill Redis 看降级路径是否生效、DB 是否被回源打满、熔断是否按预期开启），没演练过的熔断阈值大概率失真；d) 容量账：雪崩的最坏回源 QPS = 缓存命中率的补数 × 峰值 QPS——DB 侧"兜得住的最大回源量"反推 TTL/预热/分层的配置，这是雪崩防御的定量基础（Q2200 容量推导方法）；e) 客户端重试纪律：缓存层故障时的上层重试必须带退避+抖动（Q2901），固定间隔重试是雪崩放大器。

实战：事故形态是"整点跑批刷新 40 万个商品缓存，全部 3600s 固定 TTL——一小时后整点回源风暴，DB QPS 从 3k 冲到 42k，连接池排队雪崩 11 分钟。修复：跑批写入改'base 3600 + uniform(0, 600)' 抖动 + 跑批本身分片错峰（40 万 key 分 20 分钟灌入）+ 回源限流闸（DB 回源上限 8k/s，超出返回降级默认值）+ Redis 客户端熔断，演练验证：手动 kill Redis，P99 稳定在 1.8s（降级态）而非无限排队"。下面实测 TTL 抖动的失效分布与回源风暴对比。

```python
# 缓存雪崩: TTL 抖动的失效分布与回源风暴对比
import random
import statistics

print("[1] 固定 TTL vs 抖动 TTL 的失效时刻分布")
N = 40000
BASE, SPREAD = 3600, 600

fixed_expiries = [BASE] * N                              # 固定 TTL: 同一时刻全部到期
jittered_expiries = [BASE + random.uniform(0, SPREAD) for _ in range(N)]  # 抖动: 均匀散开

def peak_in_minute(expiries) -> int:
    """最大单秒失效数 (跑批完成时刻 + TTL 处的回源峰值)"""
    buckets: dict = {}
    for e in expiries:
        buckets[int(e)] = buckets.get(int(e), 0) + 1     # 简化: 按到期秒聚合
    return max(buckets.values())

print(f"    固定 TTL: 3600s 整点一次性失效 {peak_in_minute(fixed_expiries):>6} 个 key")
print(f"    抖动 TTL: 600s 窗口内峰值单秒 {peak_in_minute(jittered_expiries):>6} 个 key",
      f"(标准差 {statistics.pstdev(jittered_expiries):.0f}s)")
print("    回源风暴差: 峰值差 ~2 个数量级, DB 连接池不再被瞬时打满")

print("[2] 常见错误: 抖动范围过小 = 等于没抖")
small = [BASE + random.uniform(0, 5) for _ in range(N)]
print(f"    spread=5s 时峰值单秒: {peak_in_minute(small):>6} (仍集中在 ~{BASE} 处)")

print("[3] 多级缓存: Redis 抖动时本地层兜住部分流量")
class TwoLevel:
    """L1 进程内(短 TTL, 教学用 set 模拟存活) + L2 Redis 替身"""

    def __init__(self) -> None:
        self.l1: dict = {}
        self.l2: dict = {}
        self.db_hits = 0

    def get(self, key, redis_alive: bool = True):
        if key in self.l1:
            return self.l1[key], "L1"
        if redis_alive and key in self.l2:
            v = self.l2[key]
            self.l1[key] = v
            return v, "L2->回填L1"
        self.db_hits += 1
        v = f"db-{key}"
        if redis_alive:
            self.l2[key] = v
        self.l1[key] = v
        return v, "DB(回源)"

t2 = TwoLevel()
for k in ("a", "b", "c"):
    t2.get(k)                       # 预热 L2
for k in ("a", "b", "c"):
    t2.l2.clear()                   # 模拟 Redis 不可用
print("    Redis 挂掉时的回源: L1 命中部分兜底")
t2.l1.clear()
_, path = t2.get("a", redis_alive=False)
print(f"    L1 也 miss 时: {path} (多级缓存把'波及系数'降到本地命中率的补数)")

print("[4] 熔断兜底: 回源限流闸 (超出返回降级默认值) + Redis 客户端熔断")
print("[rule ] spread=base 的 10%-20%; 预热/跑批也要抖动+错峰; 雪崩预案必须 kill Redis 演练过")
```

**追问一**：逻辑过期（物理 key 永不过期 + 值内逻辑过期时间）与 TTL 抖动的适用边界怎么划？逻辑过期的"异步重建"竞态怎么处理？—— 适用边界：**TTL 抖动**是"低成本默认"——改动一行、无内存代价，适合大多数"允许短暂 miss + 回源"的数据；**逻辑过期**是"热点 key 专用"——消灭回源瞬间的语义（永远有旧值可返回），代价是①key 常驻内存（TTL 不再清理，需要显式淘汰策略）、②短暂陈旧（重建完成前返回旧值）、③重建任务管理。热点判据：单 key QPS 高到"一次回源都嫌贵"（回源 200ms × 5k QPS = 1000 并发回源）——这种 key 用逻辑过期+单飞（Q6066）双保险。异步重建竞态的处理：过期检测触发时**只有一个线程抢到重建权**（Redis SETNX 重建锁 / 进程内 singleflight，Q1854 单飞），其余线程继续返回旧值；重建锁要带 TTL 防持有者崩溃死锁，重建失败要有重试退避——语义是"宁可短暂旧值，绝不并发回源"。两者可组合：长尾数据 TTL 抖动、热点数据逻辑过期——按 key 的访问分布分层配置，而不是一刀切。

**追问二**："DB 兜得住的最大回源量"怎么定量反推？雪崩容量账的完整计算链是什么？—— 反推链：①**DB 承载上限**——回源查询是主键/索引点查，单实例的稳态 QPS 上限可压测得出（如 8k/s，考虑连接池 Q6046 的 worker:pool 配比）；②**回源系数**——缓存 miss 率 m 与单次回源成本 c：风暴峰值 QPS ≈ 峰值请求 QPS × m ÷（1 + 并发合并系数）——单飞/合并能把"同 key 并发回源"合并，合并系数高的系统风暴峰值更低；③**多级缓存的波及折减**——L1 命中率 l1 使真正打到 L2/DB 的比例 = (1-l1)，Redis 挂掉时的最坏回源 = 峰值 QPS × (1-l1) × (1-合并系数)；④**反推配置**——让"最坏回源 ≤ DB 上限 × 0.7（留余量）"，得出 L1 所需最低命中率与预热覆盖范围；若 L1 兜不住（长尾数据 L1 命中天然低），就必须限流闸 + 降级默认值兜底——**降级值的业务可用性**（返回"默认榜单"比返回 500 好）要在产品层预先约定。整个容量账的数据来源：缓存命中率/回源耗时/合并系数都要有监控打点（Q2934 分位数采样），没有打点的容量账全是拍脑袋。演练校准：kill Redis 演练实测回源峰值 vs 理论账，偏差大就修模型——容量账是活的。

## 背诵要点
- 雪崩两条触发路径（批量过期 / Redis 不可用）同一条连锁：回源风暴→连接池耗尽→重试放大→服务整体不可用；与击穿（单热 key）、穿透（不存在 key）分而治之。
- TTL 抖动 spread=base 的 10%-20% 随机 uniform；错误形态：spread 过小、固定 hash 抖动、跑批/预热本身批量写入——预热也要抖动+错峰；热点 key 用逻辑过期+单飞消灭回源瞬间。
- 防御分层：多级缓存降波及系数、回源限流闸+降级默认值兜最坏、Redis 客户端熔断、kill Redis 演练校准；容量账反推配置 = DB 上限 × 0.7 ≥ 最坏回源量。
