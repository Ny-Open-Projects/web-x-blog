### Q6036 · DRF 序列化器的每请求成本与优化路径

> 难度:★★★★ | 标签:成本工程, DRF, 序列化, N+1

**问**：DRF 列表接口慢在"序列化"还是"查询"？Serializer 的每实例成本构成是什么？哪些优化路径收益最大、哪些是伪优化？

**答**：先分离两个瓶颈：**查询侧**（N+1——serializer 每访问一次外键就触发一条 SQL，Q6022 思路在 DRF 场景的对应物）与**序列化侧**（每行构造 Serializer 实例 + 逐字段绑定 + Renderer）。序列化侧成本构成：`Serializer(instance)` 初始化会为**每行**建实例并绑定 fields（反射重）；`many=True` 内部走 ListSerializer 循环；字段数 × 行数的常数成本巨大——100 行 × 20 字段的接口，序列化常占响应时间 40-70%。优化路径按收益排序：1) **裁剪字段**——`fields` 白名单最小化、列表页与详情页拆 Serializer（字段数减半≈成本减半）；2) **消灭 N+1**——`select_related`/`prefetch_related` 与 queryset 注入（serializer 的 `context['view'].get_queryset()` 侧治理，DRF 的 `Prefetch` + `to_representation` 惰性化）；3) **`many_init` 之外的手工路径**——大列表（万级导出）跳过 DRF，直接 `QuerySet.values()`/iterator + orjson 流式输出（Q2924 CSV 思路、Q751 orjson）；4) **真伪辨析**——`serializer.data` 只调用一次、避免在循环里重复 `.data` 是真优化；"换SerializerMicro调优"是无收益伪优化。校准手段：Django Debug Toolbar/sqltrace 数查询条数 + py-spy 确认序列化占比。取舍：DRF 的价值在契约与权限，**大负载路径绕开它是工程正确而非背叛**。

```python
# file: code/03_Web后端开发/q6036_drf_serializer_cost.py
"""DRF 未安装时降级: 用纯 Python 模拟每实例成本, 已装则实测."""
import json
import time

def bench(fn, reps: int = 3) -> float:
    best = float("inf")
    for _ in range(reps):
        t0 = time.perf_counter()
        fn()
        best = min(best, time.perf_counter() - t0)
    return best * 1000

ROWS = [{"id": i, "name": f"user-{i}", "email": f"u{i}@x.com", "bio": "x" * 50,
         "score": i * 1.5, "tags": ["a", "b"]} for i in range(100)]

try:
    from rest_framework import serializers
    HAS_DRF = True

    class UserSlim(serializers.Serializer):          # 裁剪字段: 3 个
        class Meta:
            pass
        id = serializers.IntegerField()
        name = serializers.CharField()
        score = serializers.FloatField()

    class UserFat(serializers.Serializer):           # 全字段: 6 个
        id = serializers.IntegerField()
        name = serializers.CharField()
        email = serializers.CharField()
        bio = serializers.CharField()
        score = serializers.FloatField()
        tags = serializers.ListField(child=serializers.CharField())

    def run(scls):
        return scls(ROWS, many=True).data

    t_slim = bench(lambda: run(UserSlim))
    t_fat = bench(lambda: run(UserFat))
    print(f"DRF 实测: slim(3字段)={t_slim:.1f}ms fat(6字段)={t_fat:.1f}ms")
except ImportError:
    HAS_DRF = False
    # 降级模拟: 每行每字段的绑定成本近似
    def simulate(fields: int) -> float:
        return bench(lambda: [
            {k: row[k] for k in list(row)[:fields]} for row in ROWS])
    t_slim, t_fat = simulate(3), simulate(6)
    print(f"降级模拟(无 DRF): slim≈{t_slim:.1f}ms fat≈{t_fat:.1f}ms (字段数≈线性)")

# 绕过路径: values + orjson/json 流式 (大列表导出)
def bypass(rows) -> str:
    keys = ("id", "name", "score")
    return json.dumps([{k: r[k] for k in keys} for r in rows])

t_bypass = bench(lambda: bypass(ROWS))
print(f"绕过路径(values+json): {t_bypass:.1f}ms  <- 万级导出走这条, DRF 留给契约")
print("优化顺序: 字段裁剪 > 消 N+1(select/prefetch) > 大负载绕行 > 微调伪优化")
```

**追问**：1) N+1 在 DRF 里怎么定位？——Debug Toolbar/sqlite 计数看每请求 SQL 条数；serializer 访问外键关系（`obj.author.name`）在 ListSerializer 循环里每行一条 SQL；治理在 queryset 层 `select_related`(FK)/`prefetch_related`(M2M) 而不是在 serializer 里缓存（缓存跨行不可靠）。2) 为什么"万级导出"不该走 DRF？——ListSerializer 逐行构造的成本 ×10000 直接超预算，且导出场景契约固定、无需权限字段级控制；`iterator()`+流式 chunk 响应（Q2924）才是形态匹配。3) SerializerMethodField 为什么贵？——每字段一次方法调用 + 上下文绑定，反射成本高于声明式字段；热列表页里它是最先该内联成 to_representation 的字段。

## 背诵要点
- 先分瓶颈：查询侧 N+1（select_related/prefetch 治理）vs 序列化侧（字段数×行数的实例成本）。
- 收益排序：字段裁剪 > 消 N+1 > 大负载绕行（values+orjson 流式）> 微调伪优化。
- 万级导出不走 DRF：iterator + 流式 chunk + 轻量序列化；DRF 留给契约/权限场景。
