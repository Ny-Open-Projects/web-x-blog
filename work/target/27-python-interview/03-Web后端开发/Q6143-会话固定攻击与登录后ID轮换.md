### Q6143 · 会话固定攻击与登录后 ID 轮换

难度：P6 ｜ 标签：会话安全、session fixation、事故复盘

**问**：用户反馈"登录后账号在别处被操作"。排查发现攻击者提前拿到一个合法 session id 引诱受害者用它登录。会话固定（session fixation）的攻击链是什么？为什么"登录成功后必须轮换 session id"？Python 侧如何实现轮换与防固定的完整清单？

**答**：
结论：固定攻击三步——① 攻击者从服务取得一个未认证的 session id（或自造 id 若服务接受）；② 通过链接/邮件/子域 Cookie 注入让**受害者浏览器带着这个 id 访问登录页**；③ 受害者登录成功后服务直接沿用该 id 存认证态——攻击者拿同一个 id 即以受害者身份访问。根因：**认证态绑定在攻击者已知的标识上且未轮换**。修复铁律：登录成功瞬间 `session id` 必须换新（旧 id 作废、认证态迁移到新 id），Django 是 `login()` 内自动 cycle，Flask 需重建 session，自研框架最易漏。

取舍：轮换会丢旧 session 的临时数据，实现时把需要保留的白名单字段显式迁移；另一侧的 SameSite=Strict/Lax（Q6058）挡"跨站注入 Cookie"路径，两者互补——SameSite 防"受害者带攻击者 id"，轮换防"攻击者已知 id"，单独任何一个都不完整。

实战：自查清单——① 登录/提权/改密码三个时点都轮换 id；② id 熵 ≥128 位（`secrets.token_urlsafe(32)`），禁止自造 id；③ 旧 id 立即失效（服务端删除，不是只改 Cookie）；④ 记录"同 id 换绑用户"的告警指标（固定攻击特征）。

```python
import secrets
import time

class SessionStore:
    def __init__(self):
        self.sessions: dict[str, dict] = {}          # sid -> {user, created}

    def create_anonymous(self) -> str:
        sid = secrets.token_urlsafe(32)              # 192-bit 熵
        self.sessions[sid] = {"user": None, "created": time.time()}
        return sid

    def login_broken(self, sid: str, user: str):
        """反例：沿用攻击者已知的 sid，直接写认证态 -> 会话固定"""
        self.sessions[sid]["user"] = user            # 不轮换！

    def login_fixed(self, sid: str, user: str) -> str:
        """正解：轮换 id + 迁移白名单字段 + 旧 id 立即作废"""
        old = self.sessions.pop(sid)                 # 旧 id 作废（服务端删除）
        keep = {k: old[k] for k in ("created",) if k in old}
        new_sid = secrets.token_urlsafe(32)
        self.sessions[new_sid] = {"user": user, **keep}
        return new_sid

store = SessionStore()

# 攻击链复现：攻击者取得 id -> 诱导受害者携带 -> 受害者登录
victim_known_to_attacker = store.create_anonymous()
print("attacker holds sid:", victim_known_to_attacker[:12], "...")

store.login_broken(victim_known_to_attacker, "victim")
print("broken login: attacker can reuse the same sid as victim:",
      store.sessions[victim_known_to_attacker]["user"])

# 修复后：登录返回全新 id，旧 id 不存在
store2 = SessionStore()
sid = store2.create_anonymous()
new_sid = store2.login_fixed(sid, "victim")
print("sid rotated:", sid != new_sid, "| old sid alive:", sid in store2.sessions)
assert sid != new_sid and sid not in store2.sessions
```

**追问一**：为什么"改密码/提权"也要轮换 id？——这三点都是"会话信任等级跃迁"；不轮换则攻击者可能通过 CSRF/XSS 拿到的低权 id 继续享有新权限；Django 的 `login()`/`update_session_auth_hash()` 分别覆盖登录与改密两个时点。

**追问二**：无状态 JWT 场景如何对应这个问题？——JWT 的 "jti"/auth_time claim + 短 access 生命周期近似轮换；但 JWT 不可服务端作废，需要 revoke 清单（黑名单/版本号 claim）；对比两者在"强制下线"能力上的差异（这正是 Q6009 撤销矩阵的延伸）。

**追问三**：如何检测线上是否发生过固定攻击？——监控"同一 sid 在短时间内绑定不同 user"与"登录前 sid 与登录后 sid 来自同一 UA/IP 跳跃"的异常模式；会话审计表保留 sid 换绑历史。

## 背诵要点
- 固定攻击 = 认证态写在攻击者已知的 sid 上；登录/提权/改密三时点必须轮换 id 且旧 id 服务端作废。
- sid 用 `secrets.token_urlsafe(32)`（≥128 位熵），禁止接受客户端自造 id。
- 防御是组合拳：id 轮换（防已知 id）+ SameSite（防注入）+ 服务端撤销（防重放）。

## 复盘追问
- 轮换时哪些字段该迁移、哪些该丢弃？（白名单显式迁移 CSRF token 是否重生成、购物车等业务态，讨论"丢弃即安全"的取舍）
- 若历史系统用了可预测 id（时间戳 MD5），如何不踢掉全部在线用户地平滑轮换？（登录即换新 + 旧 id TTL 收紧到小时级 + 强制改密活动，讨论灰度与用户感知）
