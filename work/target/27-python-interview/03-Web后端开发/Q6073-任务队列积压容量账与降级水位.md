### Q6073 · 异步任务队列积压的容量账与降级水位

> 难度:★★★★ | 标签:容量规划, 任务队列, Little's Law, 降级

**问**："接口先把重活丢进队列再返回"把 P99 压下去了，但大促当天队列积压 50 万条、延迟 2 小时，用户反馈"订单状态一直不动"。队列积压的容量账怎么算（Little's Law 入队）？积压告警该看哪个指标而不是队列长度？降级水位线怎么设——哪些任务该被暂停、哪些必须保住？

**答**：结论：队列是"**延迟换吞吐**"的债务工具，容量账用 Little's Law：`L = λ × W`（稳态下队列长度 = 到达率 × 任务在队时间）。推导链：任务处理速率 μ = worker 数 × 单任务速率（含 DB/下游瓶颈，必须压测出真实 μ）；稳态吞吐上限就是 μ，**λ > μ 时积压线性增长**，增速 = λ - μ 条/秒；积压 L 条时的额外延迟 = L/μ（50 万条 ÷ 70 条/秒 ≈ 2 小时，正好对上事故）。关键结论：**队列长度本身不是告警主指标**——大促前预灌数据也会让队列变长；主指标是两个导数：a) **积压增速**（λ-μ，>0 持续即容量缺口）；b) **最老任务年龄**（oldest age，直接等于"最差用户体验的等待时间"，是 SLO 的直接映射）。降级水位线设计（按任务分三档）：P0（支付回调、状态机推进）永不降级，用独立队列+独立 worker 隔离；P1（通知、索引更新）在高水位时改"合并降级"——把 N 条通知合并成 1 条摘要；P2（报表、统计预热）设水位线直接丢弃/跳过本轮，宁可过期结果也不要雪崩。反压回 API 层：队列高水位时接口要么同步降级（返回"已受理、结果稍后"并给查询句柄），要么直接限流（Q6018 的响应头协作），**不能让入队无界**——broker 无界队列 = 把 OOM 从进程内挪到 Redis/磁盘而已。

```python
# file: code/03-Web后端开发/q6073_backlog_capacity.py
import time, sys
from collections import deque

# 1) 容量账: Little's Law 推导(参数可换成压测实测值)
lambda_arrive = 100          # 到达率 条/秒 (大促峰值)
mu_per_worker = 20           # 单 worker 处理速率 条/秒 (压测实测, 含下游瓶颈)
workers = 3                  # worker 数
mu = mu_per_worker * workers # 系统吞吐上限 条/秒
print(f"λ={lambda_arrive}/s, μ={mu}/s -> 缺口 {lambda_arrive-mu} 条/s, 积压线性增长")

backlog = lambda_arrive * 60 * 60            # 一小时后的积压(不再吸收时)
print(f"1 小时积压 ≈ {backlog} 条, 最差等待 = 积压/μ ≈ {backlog/mu/3600:.2f} 小时")
print("Little's Law: L=λ×W 稳态才成立, λ>μ 时队列是积累不是稳态")

# 2) 三档降级水位线: P0 隔离 / P1 合并 / P2 丢弃
queues = {"p0": deque(), "p1": deque(), "p2": deque()}
WATERMARK = 50_000                            # 高水位(条)

def enqueue(level, task):
    q = queues[level]
    if level == "p2" and len(q) > WATERMARK // 10:
        return "dropped(P2 高水位直接丢)"
    if level == "p1" and len(q) > WATERMARK:
        # 合并降级: 同 key 任务攒批, 这里演示按 10 条合并
        if len(q) % 10 == 0:
            q.append(("merged-batch", task))
            return "merged"
        return "coalesced(并入既有批次)"
    q.append(task); return "queued"

for i in range(5):
    print(f"P2 task{i} ->", enqueue("p2", f"report-{i}"))
print(f"P1 task -> {enqueue('p1', 'notify-x')}", f"| P0 task -> {enqueue('p0', 'pay-callback')}")
print("P0 永不降级: 独立队列+独立 worker, 削峰靠扩容不靠丢")

# 3) 告警指标: 不是队列长度, 是增速与最老任务年龄
def oldest_age(q, now, in_ts_field=1):
    if not q: return 0
    return now - q[0][1]

now = time.time()
queues["p0"].append(("job", now - 120))
print(f"最老任务年龄 = {oldest_age(queues['p0'], now):.0f}s (SLO 直接映射, 主告警)")
print("积压增速 = λ-μ > 0 持续 5min -> 容量缺口告警(扩容/降级触发)")

# 4) 反压回 API 层: 高水位时接口返回受理+查询句柄
print("高水位入队策略: 同步降级(受理+查询句柄) 或 限流(429+Retry-After), 禁止无界入队")
print("python:", sys.version.split()[0])
```

**追问**：1) 为什么单任务速率 μ 要"含下游瓶颈"压测而不能用平均耗时算？——平均耗时掩盖长尾与并发争用：任务在 worker 并发下共享 DB 连接池（Q6046 配比）、下游限流，实际 μ 是并发下的系统吞吐，通常比"1/平均耗时×并发"低 20-50%；压测必须带着下游依赖真实形态跑。2) 积压能不能靠"临时扩 worker"消掉？——能但要看瓶颈在哪：瓶颈在 worker CPU/IO → 扩 worker 线性有效；瓶颈在 DB/下游 → 扩 worker 反而拖垮下游（连接池爆、限流触发），正确动作是先定位瓶颈层再扩容，配合 μ 的实时估算（处理速率打点）验证扩容是否有效。3) P2 丢弃怎么对上游交代？——丢弃要有事件记录（丢弃计数+样本）与"可补偿"设计：报表类任务本质幂等可重跑，丢弃后由下个周期自然补齐；不可重跑的任务不能归入 P2。

## 背诵要点
- Little's Law `L=λ×W` 只在稳态成立，λ>μ 时积压线性增长、最差等待=积压/μ；μ 必须带下游瓶颈压测得出。
- 告警主指标是积压增速（λ-μ）与最老任务年龄，不是队列长度；长度只做辅助水位。
- 降级三档：P0 独立隔离永不丢、P1 合并/摘要降级、P2 高水位丢弃（须可重跑）；API 层反压用"受理+查询句柄"或 429，禁止无界入队。
