### Q6115 · 响应瘦身（字段裁剪）的带宽与序列化成本账

> 难度:★★★★☆ | 标签:成本工程, 序列化, 接口设计

**问**:列表接口返回完整 ORM 对象序列化（40 个字段、单条 4KB），移动端每页 50 条就是 200KB；除了"加个分页"，字段裁剪能省多少、省在哪几层（序列化 CPU、gzip、带宽、客户端解析）？`fields` 参数、DTO、GraphQL 三种方案怎么选？

**答**:结论：瘦身的成本账要按四层拆：a) **序列化 CPU**：Pydantic/DRF 的序列化时间近似随字段数线性，40→12 字段大约省 60-70% 序列化耗时（引 Q6036 每请求序列化成本）；b) **压缩**：gzip 对 JSON 的压缩比与字段重复度相关，裁剪掉重复长字段后**压缩后体积下降比原文本更陡**（重复模式减少反而可能让压缩比略降，但绝对字节必然下降）；c) **带宽/流量费**：响应字节直连 CDN/网关出口成本，大列表接口（10 万 QPS × 200KB）是流量账的绝对大头；d) **客户端解析**：移动端 JSON parse 是 CPU 密集，200KB→60KB 带来可感知的冷启动收益。三种方案取舍：**fields/DTO 显式裁剪**成本最低（一层视图代码），但要为每个接口维护字段清单、容易漏敏感字段（引 Q6081 校验错误泄露）；**Pydantic response_model + exclude/exclude_none** 半自动，过度使用 `exclude` 链会拖慢校验；**GraphQL** 让客户端按需取字段，服务端要付解析器与 N+1 防护成本（引 Q6022）。工程实践：列表接口强制"列表 DTO"（只含列表必需字段），详情接口才给全量——这是收益最大、维护最小的一刀。

```python
import json, timeit, gzip

# 模拟：全量 vs 裁剪 DTO 的四层成本对照
full_item = {
    "id": 10086, "title": "商品标题" * 5, "desc": "长描述" * 100,
    "tags": ["a", "b", "c"], "attrs": {f"k{i}": f"v{i}" * 10 for i in range(20)},
    "price": 9900, "stock": 34, "seller": {"name": "店铺" * 10, "star": 4.9},
}
list_dto = {k: full_item[k] for k in ("id", "title", "price", "stock")}  # 列表页只留 4 字段

def page(obj, n=50):
    return json.dumps([obj] * n, ensure_ascii=False)

full_json, dto_json = page(full_item), page(list_dto)
print(f"全量 50 条: {len(full_json)/1024:.0f}KB | 裁剪 50 条: {len(dto_json)/1024:.0f}KB "
      f"({len(dto_json)/len(full_json):.0%})")

# gzip 层：绝对字节下降，压缩比可能变化
gz_full = len(gzip.compress(full_json.encode()))
gz_dto = len(gzip.compress(dto_json.encode()))
print(f"gzip 后: 全量 {gz_full/1024:.0f}KB({gz_full/len(full_json.encode()):.0%}) "
      f"裁剪 {gz_dto/1024:.0f}KB({gz_dto/len(dto_json.encode()):.0%})")
print(f"流量账: 10 万 QPS × 差值 {((len(full_json.encode())-gz_full)-(len(dto_json.encode())-gz_dto))/1024/1024:.0f}MB/s")

# 序列化 CPU 层
t_full = timeit.timeit(lambda: json.dumps([full_item] * 10, ensure_ascii=False), number=200)
t_dto = timeit.timeit(lambda: json.dumps([list_dto] * 10, ensure_ascii=False), number=200)
print(f"序列化: 全量 {t_full:.3f}s vs 裁剪 {t_dto:.3f}s（{t_dto/t_full:.0%}）")

# Pydantic 层演示（基线: pydantic>=2.5；缺库降级说明）
try:
    from pydantic import BaseModel, ConfigDict
    class Item(BaseModel):
        model_config = ConfigDict(from_attributes=True)
        id: int; title: str; price: int; stock: int
    print("DTO 校验开销固定，字段越少校验越快（Q6075 按需校验）:", Item(**list_dto).id)
except ImportError:
    print("缺 pydantic>=2.5，CPU 对照以 json.dumps 为准")
```

**追问一层**:为什么"裁剪重复长字段"可能让 gzip 压缩比变差但总流量仍大降？HTTP/2 的 HPACK 只压 header，body 压缩策略怎么和裁剪配合（引 Q5508）？
**追二层**:字段白名单怎么防"漏敏感字段"（余额、手机号）与"DTO 膨胀回全量"的腐化？schema 测试（契约测试）怎么把"列表接口必须用 ListDTO"固化成 CI 门禁？

**背诵要点**
- 瘦身收益拆四层：序列化 CPU 近似线性省、gzip 后绝对字节必然降、带宽是流量费大头、客户端解析提速。
- 列表接口用裁剪 DTO、详情接口全量，是收益/维护比最高的一刀；exclude 链与白名单各防不同的腐化。
- 压缩比可能因重复度下降而变差，但绝对字节与成本仍下降——看绝对值不看比率。

**复盘追问**
- 客户端强烈要求"列表加一个字段"，DTO 被逐渐加回 30 个字段，治理机制是什么？提示：字段变更走契约 diff 门禁（引 Q6048/Q1627），列表 DTO 长度上限告警。
- 裁剪后某些客户端字段缺失报错，兼容层怎么做？提示：响应带 schema 版本或默认值序列化（exclude_none + 客户端容错），灰度观察。
