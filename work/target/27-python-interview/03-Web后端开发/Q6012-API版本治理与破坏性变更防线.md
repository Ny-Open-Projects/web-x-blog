### Q6012 · API 版本治理

> 难度:★★☆ | 标签:API 设计, 版本管理, 兼容性

**问**：公开 API 迭代时，什么变更算「破坏性」——加字段安全吗、加必填参数呢、改错误码语义呢？版本策略（URL//Header/租户灰度）怎么选，旧版本退役的标准流程是什么？

**答**：破坏性变更判定表：**安全**（非破坏）：响应加新字段、请求加带默认值的可选参数、错误码集合扩容（前提：客户端按「未知错误兜底」写）；**破坏**：删除/重命名字段、字段类型改变（int→string）、可选变必填、语义收紧（`status: "ok"` 开始含 `"degraded"`）、枚举新增值若客户端穷举处理则炸。版本策略：URL 路径（`/v2/`，路由清晰、缓存友好、最主流）> Header（`Accept-version`，URL 干净但调试难、CDN 需配 Vary）> 时间戳（SaaS 惯例）。退役流程五步：① 标记 deprecated（响应头 `Deprecation: true` + `Sunset` 日期）；② 监控旧版本调用量与调用方清单；③ 点对点通知 Top 调用方迁移；④ 流量 < 阈值后只读期（返回旧数据但不再维护）；⑤ 按调用方逐个切断，而不是一刀切下线。

```python
# 全部标准库；demo 实现「兼容性检查器 + 版本路由 + Sunset 流量观测」骨架
from dataclasses import dataclass, field

@dataclass
class FieldSpec:
    name: str
    type_: type
    required: bool = False

def check_breaking(old: list[FieldSpec], new: list[FieldSpec]) -> list[str]:
    """破坏性变更检查器：schema diff 的最小可用版。"""
    old_map = {f.name: f for f in old}
    new_map = {f.name: f for f in new}
    issues = []
    for name in old_map:
        if name not in new_map:
            issues.append(f"BREAKING: 字段删除 {name}")
        elif new_map[name].type_ is not old_map[name].type_:
            issues.append(f"BREAKING: {name} 类型 {old_map[name].type_}→{new_map[name].type_}")
        elif old_map[name].required and not new_map[name].required:
            pass                                            # 必填→可选是安全的放宽
    for name in new_map:
        if name not in old_map and new_map[name].required:
            issues.append(f"BREAKING: 新增必填 {name}")     # 老客户端不发它必然失败
    return issues

v1 = [FieldSpec("id", int, True), FieldSpec("name", str), FieldSpec("tag", str)]
v2 = [FieldSpec("id", int, True), FieldSpec("name", str),
      FieldSpec("tag", str, False), FieldSpec("score", float)]     # 加可选字段
print("v1→v2:", check_breaking(v1, v2) or "安全 ✅")
v3 = [FieldSpec("id", int, True), FieldSpec("username", str)]      # 改名
print("v1→v3:", check_breaking(v1, v3))

# 版本路由 + deprecated 观测（模拟）
VERSIONS = {"v1": {"sunset": "2026-12-31", "callers": {"mobile-app": 8000, "partner-x": 200}},
            "v2": {"sunset": None, "callers": {"web": 50000}}}
def route(version: str) -> dict:
    meta = VERSIONS[version]
    headers = {}
    if meta["sunset"]:
        headers["Deprecation"] = "true"
        headers["Sunset"] = meta["sunset"]            # RFC 8594：退役日期让调用方自扫
    return {"headers": headers, "total_qps": sum(meta["callers"].values())}

for v in ("v1", "v2"):
    print(v, route(v))
# 退役顺序：监控 callers → Top 调用方迁移 → mobile-app 切断 → partner-x 切断 → 删 v1
```

**追问**：1) 为什么「响应加字段」也可能炸？——严格 schema 校验的客户端（如某些 Java 反序列化器/自研 strict parser）遇到未知字段直接抛错；所以加字段前查调用方契约测试覆盖，或开『新字段先在 beta 头下返回』灰度。2) 版本共存期代码怎么组织？——同一 handler 适配多版本（响应 shaper 按版本裁剪字段）优于复制整棵路由树；复制树的漂移是维护灾难。3) `Sunset` 头标准是什么？——RFC 8594，客户端/网关可以自动采集并告警；比自家 `X-Deprecated` 更可复用。

## 背诵要点
1. 破坏性判定：删/改名、类型变更、可选变必填、语义收紧=破坏；加字段/加默认可选参=安全（前提客户端宽松解析）。
2. 版本策略主流是 URL 路径；共存期用响应 shaper 适配，不复制路由树。
3. 退役五步：Deprecation+Sunset 头 → 调用方清单监控 → 点对点迁移 → 只读期 → 按调用方逐个切断。

## 复盘追问
1. 内部服务间 API 要不要版本化？（提示：轻量化——契约测试（schemathesis 类）代替 URL 版本，版本化成本留给外部 API）
2. 客户端怎么写才不会被「加字段」炸？（提示：宽松接收（未知字段忽略）+ 未知错误码兜底分支——契约的精神在客户端防御性）
