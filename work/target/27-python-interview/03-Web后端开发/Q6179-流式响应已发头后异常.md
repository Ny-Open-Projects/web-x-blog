### Q6179 · 流式响应已发 200 头后异常只能截断

难度：P7 ｜ 标签：流式响应、ASGI、Content-Length、截断、错误处理

**问**：一个 CSV 导出接口用 `StreamingResponse` 边查边写，某次下游游标在 60% 处报错，用户下载到的是一个"HTTP 200、但只有 60% 行数"的文件，前端还提示成功。为什么不能改成 500？`http.response.start` 之后协议还允许改状态码吗？如果一开始声明了 `Content-Length: 100`，截断和 chunked 截断对客户端有什么不同？工程上怎么让"流式中途失败"可发现、可恢复？

**答**：
结论：ASGI 的响应是"先 `http.response.start`（状态码 + 头），再若干 `http.response.body`"；`start` 一旦发出，状态码和头就**已经提交给客户端**，之后不能再发第二个 `start`（会报 `Unexpected message 'http.response.start'`），也不能把 200 改成 500。生成器在中途抛异常时，服务器只能中止连接：如果声明了 `Content-Length`，客户端会因"收到字节数少于声明"而报 `IncompleteRead`/连接错误；如果是 chunked 且没有正确的结束块，客户端可能把"连接关闭"当成正常结束，得到一个静默截断的 200。错误处理必须在 `start` 之前完成，或者把错误编码进流内（错误帧/尾行/摘要）。

取舍：流式的收益是内存恒定、首字节快；代价是"响应一旦开始就失去 HTTP 状态码这个错误通道"。对策有三类：a) **前置校验**：在 `start` 前完成鉴权、参数校验、能快速失败的下游探测；b) **不用 Content-Length**，用 chunked/SSE，并在流末尾发一个明确的结束标记/摘要（如 CSV 最后一行 `#END sha256=...`），客户端校验；c) 对"不能半途失败"的导出，先落临时文件/对象存储，完整生成后再返回 URL，用 303 让客户端去下载——牺牲首字节，换原子性。

实战：事故形态是"财务导出少了 40% 行，用户以为数据就这样；对账时才发现"。下面用状态机模拟 ASGI 消息序列：`start` 带 `Content-Length: 100`，发了两块 30 字节后生成器抛错；尝试补发 500 被服务器拒绝；客户端只收到 60/100 字节，属于可检测的截断。若改成 chunked，则要应用层结束标记才能发现。

```python
class ASGIServer:
    def __init__(self):
        self.started = False
        self.bytes_sent = 0
        self.declared = None

    def send(self, message):
        kind = message["type"]
        if kind == "http.response.start":
            if self.started:
                raise RuntimeError("Unexpected message 'http.response.start'")
            self.started = True
            self.declared = dict(message.get("headers", [])).get(b"content-length")
            print("  已发送响应头，状态", message["status"], " Content-Length:", self.declared)
        elif kind == "http.response.body":
            if not self.started:
                raise RuntimeError("response.body before response.start")
            body = message.get("body", b"")
            self.bytes_sent += len(body)
            print("  发送 body 块:", len(body), " 累计:", self.bytes_sent)


server = ASGIServer()
try:
    server.send({"type": "http.response.start", "status": 200,
                 "headers": [(b"content-length", b"100")]})
    for chunk in (b"x" * 30, b"y" * 30):
        server.send({"type": "http.response.body", "body": chunk})
    raise RuntimeError("查询下游时连接被重置")
except RuntimeError as e:
    print("生成器异常:", e)
    print("客户端已收到 200 + 60/100 字节，无法再改成 500")

try:
    server.send({"type": "http.response.start", "status": 500, "headers": []})
except RuntimeError as e:
    print("尝试补发 500 ->", e)
```

**追问一**：为什么 chunked 截断更隐蔽？——chunked 的结束由"0 长度块 + 空行"标记；如果服务器在异常时直接关闭连接，没有发结束块，严格的客户端应报"提前 EOF"，但很多客户端/浏览器会把"连接关闭"当成流结束，交给业务层一个不完整但"成功"的响应。声明 `Content-Length` 反而给了客户端一个可校验的契约：字节数不够就是错误。所以"要不要 Content-Length"是"可检测性 vs 流式灵活性"的取舍。

**追问二**：ASGI 里 `http.disconnect` 和生成器异常是什么关系？——`http.disconnect` 表示客户端已断开，服务器通常会取消/停止发送；生成器异常是服务端自己的错误。两者都可能让流提前结束，但前者不应尝试写错误响应（对端已经走了），后者在 `start` 前还能返回 500、在 `start` 后只能中止。框架/服务器对"生成器异常后是否发送 trailer/错误块"支持不一，不能依赖；要在应用层设计结束标记和监控。

## 背诵要点
- ASGI `http.response.start` 提交状态码/头后不可再改；生成器中途异常只能中止，客户端看到截断的 200。
- 声明 `Content-Length` 让截断可检测；chunked 无结束块可能被当成正常结束，需应用层结束标记/摘要。
- 错误处理前置（start 前校验），或落盘后返回 URL；流式要配套结束标记、校验和、监控。
