### Q6165 · SSE 会话粘性幻觉与全局事件游标

难度：P7 ｜ 标签：SSE、会话粘性、Last-Event-ID、多 worker、事件游标

**问**：SSE 断线重连靠 `Last-Event-ID` 续传，多 worker 部署时给客户端配 sticky session（cookie/IP 哈希）就能保证不漏事件吗？worker 重启、Pod 漂移、扩容后连接落到另一个 worker，本地事件日志的序号空间不一致会发生什么？为什么"会话粘性"对 SSE 是一种幻觉、正确方案是"全局事件日志 + 全局游标"？本题与 Q2316（`Last-Event-ID` 重放机制）、Q6071（反代缓冲）的边界在哪？

**答**：
结论：sticky session 只能"尽量"把同一客户端钉在同一 worker，但**无法保证**——worker 重启/发布、Pod 被驱逐、LB 连接池重建、健康检查摘除都会让重连落到另一个 worker；而每个 worker 若各自维护本地事件日志与自增序号，`Last-Event-ID: 5` 在 A worker 是"第 5 条"，到 B worker 可能对应完全不同的事件甚至还不存在——**序号空间不同**，重放要么漏事件、要么重复、要么从 0 开始把旧事件重发一遍。这就是"会话粘性幻觉"：把"连接粘性"误当成"状态粘性"。正确方案是把**事件源做成共享的、全局有序的**（Redis Stream / DB 表 / Kafka），`id` 用全局单调递增序号，重连时按全局游标 `WHERE seq > last_id` 续传——与落在哪个 worker 无关，worker 变成无状态转发者。Q2316 讲的是 `Last-Event-ID` 的重放机制本身（怎么发、怎么续），本题讲的是**多 worker 下状态分片导致粘性失效**；Q6071 讲的是代理缓冲让 SSE 攒批——三者是"协议 / 状态 / 传输"三个不同层次。

取舍：全局事件日志的代价是引入共享存储与顺序保证——Redis Stream 用 `XRANGE key (last_id +` 天然支持，DB 表要 `(seq)` 索引 + 分片键设计；全局序号要避免热点（单 Stream 顺序写），高吞吐场景按租户/频道分 Stream，游标带上 Stream 标识。若业务能接受"重连后全量刷新状态"（如股价推送），可以不做事件回放、直接让客户端重连后重新拉全量快照——这是用"状态幂等"换掉"事件有序"的更简方案。

实战：事故形态是"发布后用户反馈 SSE 推送断档/重复"，根因正是 worker 漂移后本地序号错位。下面模拟：两个 worker 各有本地序号，客户端从 w1 读到 id=1 后 w1 重启、重连到 w2，本地序号空间不兼容导致漏；再演示全局事件总线 + 全局游标如何与 worker 无关地正确续传。

```python
class Worker:
    def __init__(self, name):
        self.name = name
        self.events = []
    def emit(self, data):
        self.events.append((len(self.events) + 1, data))   # 本地序号空间

class EventBus:
    """共享、全局有序的事件日志（示意；生产用 Redis Stream/DB）。"""
    def __init__(self):
        self.log = []
    def emit(self, data):
        self.seq = len(self.log) + 1
        self.log.append((self.seq, data))
        return self.seq
    def replay_after(self, last_id):
        return [(seq, d) for seq, d in self.log if seq > last_id]

# 1) sticky 幻觉：w1 事件序号与 w2 不在同一空间
w1, w2 = Worker("w1"), Worker("w2")
for i in range(3):
    w1.emit(f"w1-event-{i}")
print("w1 local log:", w1.events)
client = {"worker": "w1", "last_id": 1}          # 已从 w1 读到 id=1

client["worker"] = "w2"                          # w1 重启 -> 重连落到 w2
w2.emit("w2-event-0")
replay = [(seq, d) for seq, d in w2.events if seq > client["last_id"]]
print("w2 local log:", w2.events)
print("replay on w2:", replay, " <- 漏掉 w1 的 event-1/event-2")

# 2) 正解：全局事件总线，重连与落在哪个 worker 无关
bus = EventBus()
for i in range(5):
    bus.emit(f"global-{i}")
print("global replay after last_id=2:", bus.replay_after(2))
```

**追问一**：为什么"会话粘性"连"连接粘性"都保证不了——LB 的 cookie/IP 哈希不是稳定的吗？——因为粘性的键会变：Pod 重启后 IP 变了（IP 哈希失效）、发布后 worker 集合变化（一致性哈希环重分布）、LB 自身重启丢 cookie、长连接空闲超时被摘除后重连。即便键稳定，"同一个连接"也不等于"同一个 SSE 会话实例"——中间任何一层重建都让请求落到别处。所以粘性是"best effort"，不能承载状态正确性。

**追问二**：全局事件日志的"全局有序"在多租户下怎么扩展？——不可能所有频道共享一个全局序号（单点热点），正确做法是按**分区键**（tenant_id / channel_id）分 Stream，每个分区内有序，游标携带 `(stream_key, seq)` 二元组；客户端重连时带分区标识，服务端从对应 Stream 的 seq 之后续传。这样既保持"同一会话内的事件有序可续传"，又避免单一全局序号成为写热点——取舍是跨分区的全局时序不再保证，但 SSE 通常只关心单会话内的顺序。

## 背诵要点
- sticky session 是 best effort：重启/漂移/扩容/摘除都会让 SSE 重连落到别的 worker。
- 各 worker 本地序号空间不同 → `Last-Event-ID` 错位漏/重事件；正解是共享全局有序事件日志 + 全局游标（Redis Stream/DB）。
- 多租户按分区键分 Stream，游标带 `(stream, seq)`；与 Q2316（重放机制）、Q6071（缓冲）是协议/状态/传输三层次。
