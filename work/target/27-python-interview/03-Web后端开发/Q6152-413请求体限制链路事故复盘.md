### Q6152 · 413 请求体限制链路事故复盘

难度：P6 ｜ 标签：413、请求体限制、nginx、Content-Length、事故复盘

**问**：一个上传接口平时正常、大文件偶发 413 或"连接被重置"，请求体大小限制在反代、ASGI 服务器、应用框架三层各自怎么配？为什么限制值不一致时会出现"客户端已发完数据才被拒"的半开连接浪费？500MB 上传的分层限制应该怎么定？

**答**：
结论：请求体限制有三层各自独立的阀门：① 反代（nginx `client_max_body_size`，默认 1MB，超限 413 并立即断开）；② ASGI/HTTP 服务器（uvicorn `--limit-max-request-size` 类参数或 h11 层 Content-Length 校验，默认常不限制或按实现）；③ 应用层（框架/业务校验 Content-Length 或流式计数）。事故的两个典型形态：A) **中间层先拒**：nginx 1MB 上限把 10MB 请求拒掉，客户端收到 413，但应用日志一片空白（请求没到应用）——排障方向被误导；B) **应用层才拒**：限制只在应用读 body 时发现，此时反代已经把数百 MB 转发进来，浪费带宽与 worker 时间，还会触发反代的 upstream 超时（504）而非干净的 413。半开浪费：客户端不读响应体/不处理 413 时，断开可能变成 RST，客户端重试风暴。

取舍：限制要**在最外层就拒绝且逐层一致**：反代设硬上限（业务最大 + 余量），应用层设软校验并返回规范错误体（RFC 9457 风格 + Retry-After 无关字段说明），层间差异写进部署清单。对真正大文件走**另一条通道**——预签名 URL 直传对象存储（应用不经手字节），而不是把反代限制调大迁就业务：反代限制调大会同步放大慢速攻击（slowloris/大 body 占连接）风险面。

实战：分层配置基线：nginx `client_max_body_size 100m; client_body_timeout 60s;` + uvicorn/框架一致 + 业务按 Content-Length 预检（读 body 前就拒绝，省传输）；监控把 413 按层归因（413 出现在 access log 的哪一段）并区分"业务超限"与"限制错配"两类告警阈值。

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import http.client, threading

MAX_BODY = 1024  # 应用层软限制（字节），模拟反代之外的第三层

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        # 预检：先看 Content-Length 再读 body —— 省 500MB 传输的正确姿势
        length = int(self.headers.get("Content-Length", 0))
        if length > MAX_BODY:
            body = b'{"type":"about:blank","title":"Payload Too Large"}'
            self.send_response(413)
            self.send_header("Content-Type", "application/problem+json")
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
            return
        data = self.rfile.read(length)
        self.send_response(200); self.send_header("Content-Length", "2"); self.end_headers()
        self.wfile.write(b"ok")
    def log_message(self, *a): pass

srv = HTTPServer(("127.0.0.1", 0), Handler)
port = srv.server_address[1]
threading.Thread(target=srv.serve_forever, daemon=True).start()

def post(size):
    conn = http.client.HTTPConnection("127.0.0.1", port, timeout=3)
    conn.request("POST", "/upload", body=b"x" * size)
    r = conn.getresponse()
    print(f"body={size:>6}B -> {r.status} {r.getheader('Content-Type')} {r.read()[:60]}")
    conn.close()

post(512)      # 通过
post(4096)     # 预检 413，未读 body

# 事故对照：无预检时先读 body 才拒 —— 传输成本已经付掉
class BadHandler(Handler):
    def do_POST(self):
        data = self.rfile.read(int(self.headers.get("Content-Length", 0)))  # 先全读
        if len(data) > MAX_BODY:
            self.send_response(413); self.send_header("Content-Length", "0"); self.end_headers()
        else:
            self.send_response(200); self.send_header("Content-Length", "2"); self.end_headers()
            self.wfile.write(b"ok")

bad = HTTPServer(("127.0.0.1", 0), BadHandler)
port2 = bad.server_address[1]
threading.Thread(target=bad.serve_forever, daemon=True).start()
conn = http.client.HTTPConnection("127.0.0.1", port2, timeout=3)
conn.request("POST", "/upload", body=b"x" * 4096)
r = conn.getresponse()
print("no precheck -> 413 after full read:", r.status)
conn.close()
srv.shutdown(); bad.shutdown()
```

**追问一**：nginx 收到超过 `client_max_body_size` 的请求，默认行为对客户端表现是什么？——返回 413 并**立即关闭连接**；如果客户端正在分块上传（chunked）或 TCP 缓冲里还有数据，关闭可能表现为 RST 而非干净响应，部分客户端只看到"connection reset"——这就是"偶发 reset 而非 413"事故的成因，需要在 nginx 侧保留 access log 的 413 记录并与客户端重试策略对齐（413 不应重试）。

**追问二**：chunked（无 Content-Length）请求怎么限制大小？——没有预检依据，只能**流式计数**：读满限制立即断/413，反代与服务器都要支持；这也是"预签名直传 + 网关按 byte-range 校验"更优的原因——把大流量从应用链路剥离后，限制只保护应用自身的中小请求。

## 背诵要点
- 限制三层独立：反代（nginx 默认 1MB）、HTTP 服务器、应用；不一致导致"413 日志空白"或"先转发后拒绝"两类事故。
- 应用层必须 Content-Length 预检先拒（省传输），chunked 用流式计数；真正大文件走预签名直传而非调大限制。
- 413 伴随 RST 的成因是反代立即断连 + 客户端重试风暴；413 属不可重试错误。
