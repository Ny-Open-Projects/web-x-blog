### Q6105 · 分布式追踪采样成本账（头部 vs 尾部采样）

> 难度:★★★★☆ | 标签:成本工程, tracing, 采样

**问**:全量 tracing 一天几百 GB，采样丢了慢请求，怎么平衡？

**答**:结论：追踪的成本在两侧——采集侧（应用 CPU：span 序列化+导出，典型占请求耗时 1~5%，Q2999 的最小实现也要付这笔）与存储侧（span 量 × 每条几百字节 × 保留天数）。采样是唯一把两段同时压下来的杠杆，但策略决定价值：**头部采样**（入口处按 rate 决定整条 trace 去留）成本确定、实现最简（`traceparent` 带 sampling flag 全链路传递），但会均匀丢弃"恰好变慢的请求"——恰恰是你要排障的目标；**尾部采样**（collector 收完整条 trace 再按特征留：慢、错误、特殊路由）保留价值样本，代价是 collector 要缓冲整条 trace（内存/延迟）且吞吐有限。工程折中：头部低基线（如 1%）+ 特征升级（错误/慢请求强制保留的规则在尾部补）+ 按服务差异化比例。账的锚点：采样率 × span/trace × 保留天数 = 存储 GB，直接可算可预算。

```python
# 两侧成本的算账模型
def storage_gb(requests_day, spans_per_trace=20, bytes_per_span=500, keep_days=7, sample=0.01):
    return requests_day * sample * spans_per_trace * bytes_per_span * keep_days / 2**30

print(f"1%/天 1 亿次请求 × 20 span: ≈ {storage_gb(1e8):.1f}GB")
print(f"全量同口径:              ≈ {storage_gb(1e8, sample=1.0):.0f}GB")

# 头部采样：入口一次决策，旗标全链路传播
import random

def head_sample(prob=0.01):
    return random.random() < prob

def propagate(sampled: bool) -> str:
    tid = ("traceid" * 4)[:32]
    sid = ("spanid" * 2)[:16]
    return f"00-{tid}-{sid}-{'01' if sampled else '00'}"

print("头部采样旗标:", propagate(head_sample()))

# 尾部采样规则引擎：收完整条后按特征裁决
def tail_rule(trace, slow_ms=500, baseline=0.01):
    if trace["error"] or trace["p99_ms"] > slow_ms:
        return "keep"
    if trace["route"] in {"/pay", "/checkout"}:
        return "keep"                      # 关键路由加倍保护
    return "keep" if random.random() < baseline else "drop"

print("尾部裁决:", tail_rule({"error": True, "p99_ms": 10, "route": "/x"}))
```

**追问一层**:头部采样的旗标如何在 HTTP/RPC/消息队列三类边界上无损传递？丢了会怎样？
**追二层**:尾部采样的 collector 缓冲成本怎么算？trace 时长上限如何影响内存水位？

**背诵要点**
- 追踪成本=采集 CPU（1~5%）+存储（span×字节×保留），采样同时压两侧。
- 头部采样便宜但随机丢慢请求；尾部保价值样本但要缓冲整条 trace。
- 折中方案：低基线头部 + 错误/慢/关键路由的尾部升级规则。

**复盘追问**
- 排障时"想要的 trace 恰好被采掉了"怎么救？提示：基于错误/慢特征的动态采样 + 延迟直方图兜底。
- 多服务间采样决策不一致（各采各的）会造成什么？提示：断链 trace，决策权必须收在入口。
