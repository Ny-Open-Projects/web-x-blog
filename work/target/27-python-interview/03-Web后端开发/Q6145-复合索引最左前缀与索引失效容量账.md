### Q6145 · 复合索引最左前缀与索引失效容量账

难度：P6 ｜ 标签：索引、B+ 树、EXPLAIN、容量规划

**问**：订单表查询 `WHERE user_id=? AND status=? ORDER BY created_at DESC LIMIT 20` 在百万行后变慢，DBA 说索引建了但没用上。B+ 树的最左前缀原则是什么？哪些 Python 代码写法会让索引悄悄失效？联合索引的列序怎么定？

**答**：
结论：B+ 树按 `(user_id, status, created_at)` 字典序组织，查询必须**从最左列开始连续匹配**才能走索引：`WHERE user_id=? AND status=?` 走到第三列做排序也高效；但 `WHERE status=?`（跳过首列）、`WHERE user_id=? ORDER BY created_at`（第二列断裂使排序无法用索引序，需 filesort）、范围列之后的列失效（`user_id>? AND status=?` 中 status 用不上索引精确匹配）都退化。Python 侧三个静默失效写法：① ORM 里对列包函数（`func.upper(name)`、`CAST`）导致表达式无法用普通索引；② 类型不匹配——Python 传 str 给 int 列（`WHERE id='123'`），隐式转换后索引失效；③ 动态拼接把 OR 两个分支条件列不在同一索引上，优化器选全扫。

取舍：列序口诀——**等值列在前（选择性高的优先）、范围/排序列在最后**；覆盖索引（INCLUDE/额外冗余列）可免回表，代价是写放大；索引不是越多越好，每个索引都是写路径的成本。

实战：容量账——失效索引在 500 万行表一次查询读全表（约数 GB IO + 数秒 CPU），走索引则只读命中页（几十 KB）；上线前用 `EXPLAIN QUERY PLAN`（SQLite）/`EXPLAIN ANALYZE`（PG）锁进测试基线，ORM 查询一律打印 plan 审计。

```python
import sqlite3

conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.execute("CREATE TABLE orders (id INTEGER PRIMARY KEY, user_id INT, status TEXT, amount REAL, created_at TEXT)")
cur.executemany("INSERT INTO orders (user_id, status, amount, created_at) VALUES (?,?,?,?)",
                [(i % 500, ["paid", "refund", "pending"][i % 3], i * 1.1,
                  f"2026-01-{(i % 28) + 1:02d}") for i in range(200_000)])
cur.execute("CREATE INDEX idx_user_status_created ON orders (user_id, status, created_at)")
conn.commit()

def plan(sql, params=()):
    row = cur.execute("EXPLAIN QUERY PLAN " + sql, params).fetchall()
    return " ".join(r[3] for r in row)

# 1) 最左前缀成立：user_id + status 等值，created_at 排序沿用索引序
sql1 = "SELECT * FROM orders WHERE user_id=? AND status=? ORDER BY created_at DESC LIMIT 20"
print("case1:", plan(sql1, (7, "paid")))            # SEARCH ... USING INDEX，无排序步骤

# 2) 跳过首列：status 单独查 -> 全表 SCAN
sql2 = "SELECT * FROM orders WHERE status='paid'"
print("case2:", plan(sql2))                          # SCAN TABLE orders

# 3) 首列范围使后续列失效：user_id>x AND status=y 只能用 user_id 部分
sql3 = "SELECT * FROM orders WHERE user_id>? AND status=?"
print("case3:", plan(sql3, (100, "paid")))           # 只 SEARCH 于 user_id

# 4) Python 侧失效写法：表达式包裹（模拟 func.upper）-> 表达式索引缺失
print("case4:", plan("SELECT * FROM orders WHERE upper(status)=?", ("PAID",)))

# 5) 覆盖索引验证：只取索引列，免回表
cur.execute("CREATE INDEX idx_cover ON orders (user_id, status, amount)")
sql5 = "SELECT amount FROM orders WHERE user_id=? AND status=?"
print("case5:", plan(sql5, (7, "paid")))             # USING COVERING INDEX

import time
t0 = time.perf_counter()
n = cur.execute("SELECT count(*) FROM orders WHERE user_id=? AND status=?", (7, "paid")).fetchone()[0]
print(f"indexed query: {(time.perf_counter()-t0)*1000:.2f}ms rows={n}")
```

**追问一**：为什么"等值列选择性高的在前"而不是业务习惯顺序？——等值列都能精确下推时顺序只影响前缀复用度：`(a,b)` 索引可服务 a、ab 两种查询，把"更常单独出现"的列放前面能让一个索引覆盖更多查询，减少索引数量。

**追问二**：隐式类型转换在 SQLite 与 MySQL 行为差异？——SQLite 按亲和性仍可能用索引（TEXT→INT 转换后比较），MySQL 对字符串列传数字会让索引失效（每行转换）；跨库迁移时这批写法要重新审计，测试用真实类型绑定参数（ORM 的 `TypeDecorator`）。

**追问三**：如何监控线上索引失效回潮？——慢查询日志 topN 的 plan 抽样对比基线 + `pg_stat_user_indexes` 的 idx_scan 计数突降告警；发布评审把新 SQL 的 EXPLAIN 输出贴进 PR 模板。

## 背诵要点
- 最左前缀：连续等值可下推，跳首列/范围后列失效；排序列依赖索引序，断裂即 filesort。
- Python 侧三大失效：表达式包列、类型不匹配传参、OR 跨索引；上线前 EXPLAIN 进 PR 基线。
- 列序口诀：等值在前（高频单独出现者优先）、范围排序列最后；覆盖索引免回表但写放大。
