### Q6027 · 进程内定时任务的可靠性参数：misfire、coalesce 与 max_instances

> 难度:★★★☆ | 标签:APScheduler, 定时任务, 可靠性

**问**：进程内调度器（APScheduler 思路，基线 3.10）的三个可靠性参数——`misfire_grace_time`、`coalesce`、`max_instances`——各自管什么？"调度器重启丢任务"、"多实例重复触发"这两个经典坑怎么破？与 Celery beat 的分布式锁方案（Q797）怎么分工？

**答**：三个参数的语义：1) **misfire_grace_time**：触发点错过（进程忙/重启/事件循环卡）后，允许"迟到多久仍执行"的窗口（秒）；超窗即 **misfire**——本次放弃，下轮按周期重算（不是补跑 N 次）。设太短：偶发繁忙就丢任务；设 None（无限容忍）：任务堆积成雪崩，恢复后连环补打。2) **coalesce**：错过的多次触发合并成一次执行（默认开）——重启错过 3 个周期只跑 1 次，配合 grace 使用；关掉它会逐个补跑，仅用于"每次触发都必须执行"的记账类任务。3) **max_instances**：同一任务允许同时运行的最大实例数（默认 1）：上一份没跑完又到新触发点时，放弃本次并告警——防"慢任务叠加、资源滚雪球"，比 grace 更早的一道闸。两个坑：**重启丢任务**——进程内调度器的 trigger 存内存，重启即丢未来计划，用 JobStore 持久化（SQLAlchemy/Redis）或干脆把"调度"上移到 Celery beat/外部 cron（触发即投递任务消息）；**多实例重复触发**——APScheduler 不是分布式锁，两个 Pod 各自调度同一任务就双跑，解法：只在一个实例上跑调度器（选主）或任务本身幂等+分布式锁（Q797），APScheduler 4.x 的事件总线路线仍不解决选主。

```python
# file: code/03_Web后端开发/q6027_inproc_scheduler.py
from dataclasses import dataclass

@dataclass
class Job:
    interval: int          # 周期(秒)
    last_fire: int         # 上次实际执行时刻

def decide(job: Job, now: int, grace: int, coalesce: bool,
           max_instances: int, running: int):
    """调度器对一次触发点的裁决逻辑(语义示意,对齐 APScheduler 3.x)"""
    if running >= max_instances:
        return "skip", f"已有 {running} 个实例在跑(>= max_instances={max_instances}),放弃本次并告警"
    due = job.last_fire + job.interval
    if now < due:
        return "wait", "未到触发点"
    late = now - due
    missed = late // job.interval + 1      # 错过的触发次数
    if late > grace:
        return "misfire", f"迟到 {late}s 超出 grace={grace}s: 放弃,下轮按周期重算"
    if missed > 1:
        if coalesce:
            return "run", f"错过 {missed} 次触发,合并为 1 次执行(coalesce)"
        return "run", f"不合并: grace 内逐个补跑 {missed} 次"
    return "run", f"迟到 {late}s,在 grace={grace}s 内正常执行"

print(decide(Job(60, 0), 65,  30,  True,  1, 0))   # 迟到 5s: 正常跑
print(decide(Job(60, 0), 220, 200, True,  1, 0))   # 错过 3 次但都在窗内: 合并 1 次
print(decide(Job(60, 0), 220, 200, False, 1, 0))   # 不合并: grace 内逐个补跑
print(decide(Job(60, 0), 220, 30,  True,  1, 0))   # 超窗: misfire 放弃
print(decide(Job(60, 0), 65,  30,  True,  1, 1))   # 上一份还在跑: skip
print()
print("两坑: 重启丢任务 -> JobStore 持久化或调度上移 beat;多实例双跑 -> 选主/分布式锁/任务幂等")
```

**追问**：1) grace 与 max_instances 谁先起作用？——max_instances 先：上一份还在跑时新触发直接 skip（不进迟到判定），它防的是"并发叠加"，grace 防的是"迟到补跑"，两者组合覆盖"慢任务"与"进程繁忙"两类异常。2) grace=None（无限容忍）的适用场景？——只给"错过即事故"的关键任务（日终对账），且要配监控防堆积；常规任务给有限 grace（如周期的一半）。3) 为什么推荐"触发与执行分离"？——调度器只负责准时投递（发消息/入队），执行交给 worker 池：调度器故障不影响在跑任务，执行慢也不拖垮调度线程，天然解决 max_instances 之外的资源竞争。

## 背诵要点
1. misfire_grace_time = 迟到容忍窗，超窗放弃并按周期重算；None = 无限容忍，防堆积需配监控。
2. coalesce 合并错过的多次触发为一次；max_instances 限并发实例，先于 grace 生效。
3. 进程内调度器两坑：重启丢内存任务（JobStore/上移 beat）、多实例双跑（选主/锁/幂等）。

## 复盘追问
1. 任务执行时间接近周期本身（60s 任务跑 58s），参数怎么调才不进"永远 skip"？（提示：先治任务（拆批/异步化）再调 max_instances>1 或拉长周期；skip 告警要有，说明任务跟不上节奏）
2. 调度器所在 Pod 被抢占后，正在执行的内存态任务怎么办？（提示：任务要幂等（Q795）+ 状态可续（心跳租约 A104），调度侧 JobStore 恢复计划，执行侧靠队列重投）
