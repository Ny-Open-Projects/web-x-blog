### Q6011 · 响应压缩的取舍与实现

> 难度:★★☆ | 标签:性能, HTTP, 压缩

**问**：API 响应要不要压缩——谁来压（应用层 gzip 中间件 vs CDN/网关）、压什么（哪些 Content-Type 该压、哪些绝对不能压）、压到什么级别（level 选择与 CPU 预算）、动态压缩与预压缩（brotli 静态资源）怎么选？

**答**：① 谁压：**出口处压一次**——前置 CDN/网关（Nginx `gzip`/`brotli`）优于应用中间件（zlib 占应用 CPU，且应用压了网关可能再压一次双倍浪费）；应用压只适合无网关的小服务。② 压什么：文本类（json/html/css/js/svg）压，收益 5-10×；**绝不压已加密内容（TLS+压缩=CRIME/BREACH 攻击面）**、二进制已压缩格式（图片/视频/zip，白耗 CPU）、<1KB 小响应（头开销+字典未热）。③ 压到什么级：gzip level 1 vs 9 体积差约 30% 但 CPU 差 10×；动态 API 用 4-6；静态资源走**预压缩**——构建时生成 .gz/.br，网关直接发，brotli 11 级只配静态。④ 现代口径：静态 brotli（体积比 gzip 小 15-20%），动态 gzip 4-6 级；压缩必须配 `Vary: Accept-Encoding`，否则代理缓存会把 gzip 版本发给不支持的客户端。

```python
# 全部标准库；demo 实测 gzip 级别的体积/CPU 曲线与不可压内容判定
import gzip, json, time, os

payload = json.dumps({"items": [{"id": i, "name": f"产品{i}", "desc": "描述" * 20}
                                for i in range(500)]}).encode()

def bench(level):
    t0 = time.perf_counter()
    gz = gzip.compress(payload, compresslevel=level)
    dt = time.perf_counter() - t0
    return len(gz), dt

print(f"原始: {len(payload)/1024:.0f}KB")
for lv in (1, 4, 6, 9):
    size, dt = bench(lv)
    print(f"gzip-{lv}: {size/1024:.0f}KB ({size*100//len(payload)}%) {dt*1000:.0f}ms")

def compressible(ctype: str, body: bytes, min_size=1024) -> bool:
    """压缩白名单判定：文本类 + 足够大 + 非已压缩格式。"""
    text_types = ("json", "html", "css", "javascript", "svg", "xml", "text")
    already = ("image/", "video/", "audio/", "zip", "br", "gzip")
    if ctype.startswith("image/") or any(k in ctype for k in already):
        return False                          # 已压缩内容再压白耗 CPU
    if any(k in ctype for k in text_types) and len(body) >= min_size:
        return True
    return False

assert compressible("application/json", payload)
assert not compressible("image/webp", b"\x00" * 4096)
assert not compressible("application/json", b"{}")   # <1KB 不压
print("压缩白名单判定 OK")
# 要点清单：Vary: Accept-Encoding 必配；TLS 上压缩注意 BREACH（含机密的响应关压缩）；
# CPU 预算：动态压缩是 CPU 换带宽，CPU 瓶颈型服务宁可裸传。
```

**追问**：1) CRIME/BREACH 攻击的原理？——压缩让「密文长度泄漏明文信息」：攻击者注入猜测内容，对比响应长度差逐字节推断机密（token/cookie）；防御：含敏感头的响应不压缩。2) brotli 为什么静态强动态弱？——brotli 高级别慢（不适合请求时实时压），但压缩率高于 gzip；静态预压一次随便压 11 级。3) 流式响应（SSE/大 JSON）怎么压？——gzip 分块流式压可行但要控制 flush 时机（过密=压缩率差，过疏=客户端等待）；SSE 常「不压」因为事件粒度小、缓冲破坏实时性。

## 背诵要点
1. 出口压一次：网关/CDN 优先，应用中间件是下位替代；Vary: Accept-Encoding 必配。
2. 白名单：文本类+≥1KB 压；图片/视频/zip 不压；TLS 含机密响应不压（BREACH）。
3. 动态 gzip 4-6 级、静态 brotli 预压缩 11 级——压缩是 CPU 换带宽，CPU 瓶颈型服务慎用。

## 复盘追问
1. 你的 API P99 在开启压缩后变差了，怎么排查？（提示：压测分离序列化/压缩/网络段，看是否 CPU 打满；或降级别/白名单收窄）
2. 客户端禁用 Accept-Encoding 时网关行为？（提示：回未压缩版本，缓存键按 Vary 分叉——缓存命中率会掉，监控 Vary 维度命中率）
