### Q6141 · 库存超卖并发事故与锁策略选型

难度：P7 ｜ 标签：并发、数据库锁、乐观锁、事故复盘

**问**：大促期间库存 100 卖出 107 件。代码是先 `SELECT stock` 判断 >0 再 `UPDATE stock = stock - 1`，为什么并发下会超卖？给出悲观锁、乐观锁、原子 UPDATE 三种解法及各自的适用条件与代价。

**答**：
结论：读与写之间不是原子操作——两个事务都读到 stock=1，都判定可卖，各自减一，出现负库存。默认隔离级别（MySQL RR / PG RC）都不阻止这个模式，因为这是"先读后写"的业务竞态，不是脏读。三种解法：① **原子 UPDATE**（`UPDATE ... SET stock=stock-1 WHERE id=? AND stock>0`，检查 rowcount）——最简单，行锁自动串行化，代价是热点行锁排队，QPS 受限于单行更新；② **乐观锁**（版本号 `WHERE version=?`，失败重试）——读多写少/冲突率低时吞吐最好，高冲突时重试风暴反伤；③ **悲观锁**（`SELECT ... FOR UPDATE`）——事务内多次读写的复杂扣减（库存+优惠券+积分跨行）语义最直观，代价是锁持有时间=事务时长，长事务死锁风险。

取舍：单行简单扣减用原子 UPDATE + rowcount 检查即可，别上乐观锁徒增复杂度；跨行一致才需要 FOR UPDATE 或版本号。热点秒杀（万级 QPS 单 SKU）DB 锁都不够，要前置 Redis/内存扣减 + 异步落库（对账兜底）。

实战：事故修复优先原子 UPDATE（一行代码止血）；验证手段——并发压测脚本 + `SELECT ... FOR UPDATE NOWAIT` 观察锁等待；配套：库存禁止负数约束（CHECK stock>=0）作为最后防线。

```python
import sqlite3
import tempfile
import threading
import time
import os

db_path = os.path.join(tempfile.mkdtemp(), "shop.db")

def fresh_db(check: bool):
    if os.path.exists(db_path):
        os.unlink(db_path)
    c = sqlite3.connect(db_path)
    if check:
        c.execute("CREATE TABLE stock (id INTEGER PRIMARY KEY, n INT)")
    else:
        c.execute("CREATE TABLE stock (id INTEGER PRIMARY KEY, n INT CHECK (n>=0))")
    c.execute("INSERT INTO stock VALUES (1, 20)")
    c.commit()
    c.close()

def oversell_demo():
    """反例：先读后写（各自连接），并发下丢失更新 -> 超卖"""
    def buy():
        c = sqlite3.connect(db_path)
        n = c.execute("SELECT n FROM stock WHERE id=1").fetchone()[0]
        if n > 0:                                   # 读到旧值
            time.sleep(0.01)                        # 模拟事务间隙
            c.execute("UPDATE stock SET n=n-1 WHERE id=1")
            c.commit()
        c.close()
    ts = [threading.Thread(target=buy) for _ in range(20)]
    for t in ts: t.start()
    for t in ts: t.join()

fresh_db(check=False)
oversell_demo()
c0 = sqlite3.connect(db_path)
n1 = c0.execute("SELECT n FROM stock WHERE id=1").fetchone()[0]
sold = 20 - n1
print(f"racy: 20 buys attempted, stock left {n1} -> {sold} actually deducted (lost updates)")
c0.close()

# 修法：原子 UPDATE + rowcount 检查 + CHECK 约束兜底
fresh_db(check=True)

results: list[bool] = []
lock = threading.Lock()
def buy_atomic():
    c = sqlite3.connect(db_path)
    cur = c.execute("UPDATE stock SET n=n-1 WHERE id=1 AND n>0")
    c.commit()
    ok = cur.rowcount == 1                          # rowcount=0 即抢空
    c.close()
    with lock: results.append(ok)

ts = [threading.Thread(target=buy_atomic) for _ in range(30)]
for t in ts: t.start()
for t in ts: t.join()
c1 = sqlite3.connect(db_path)
n2 = c1.execute("SELECT n FROM stock WHERE id=1").fetchone()[0]
c1.close()
print(f"atomic buys: {sum(results)} ok / 30 attempts, stock left {n2}")
assert sum(results) == 20 and n2 == 0               # 精确卖完，无超卖
```

**追问一**：默认隔离级别为什么挡不住超卖？——RR/RC 保证读到一致快照，但"读-判断-写"的 gap 没有锁覆盖；PG 的 `SELECT FOR UPDATE` 才加行锁；MySQL 也可以用 `UPDATE` 本身的行锁（原子 UPDATE 等价于隐式加锁后写）。

**追问二**：乐观锁重试风暴怎么量化与设限？——失败率 p 下重试次数期望 ≈ 1/(1-p)，p=80% 时平均 5 次写放大 5 倍；设最大重试 3 次 + 失败走人工/降级，监控重试率超 10% 即改悲观或原子方案。

**追问三**：Redis 预扣与 DB 最终一致的对账怎么设计？——Redis `DECR`/Lua 原子预扣挡流量，异步队列落 DB，对账 job 定时比 Redis 剩余 vs DB 剩余；讨论超时回滚（未支付释放预扣）与幂等键防重复扣。

## 背诵要点
- 超卖根源是"读-判断-写"非原子，快照隔离不覆盖业务竞态；止血用 `UPDATE ... WHERE n>0` + rowcount。
- 选型：单行扣减原子 UPDATE；冲突率低的复杂场景乐观锁（限重试）；多行事务 FOR UPDATE（防长事务死锁）。
- 兜底三件套：CHECK 约束、对账 job、热点 SKU 前置 Redis 原子预扣。

## 复盘追问
- 如果扣减涉及"冻结库存"状态机（下单冻结、支付扣减、超时释放），锁策略如何改？（状态流转表 + 行锁 + TTL 补偿任务，讨论幂等与对账）
- 用 SQLite 演示的方案迁到 MySQL 主从复制下有什么新坑？（主库 OK 但读从库延迟导致判断失真，讨论读写分离下的一致性读点）
