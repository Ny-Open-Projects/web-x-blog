### Q6018 · API 限流的响应头协议

> 难度:★★☆ | 标签:限流, HTTP, IETF

**问**：限流响应该带哪些头——IETF 的 `RateLimit-*` 草案与惯用的 `X-RateLimit-*` 有什么字段语义差异？`429` 和 `503` 各自表达什么，客户端 SDK 拿到这些头该怎么自动调速？

**答**：字段语义（IETF draft-ietf-httpapi-ratelimit-headers vs 惯例）：① **配额窗口**：`RateLimit-Limit/X-RateLimit-Limit`（窗口内总额）、`RateLimit-Remaining/X-RateLimit-Remaining`（剩余量）、`RateLimit-Reset`（**秒数**，语义是「窗口重置还剩几秒」）；② 老的 `X-RateLimit-Reset` 常被实现成**时间戳**（GitHub 风格 epoch 秒）——两种语义混用是客户端调速 bug 的高发点，自建 API 要在文档里写死口径；③ **429 Too Many Requests** = 配额超限（客户端调速能解决）+ `Retry-After`（建议等待秒数）；**503** = 服务过载（不是你的配额问题，主动退避）——把 503 当 429 硬重试会放大故障。客户端自动调速：读 `Remaining`，低于窗口总量 20% 时主动降速（令牌桶 rate × 0.5），0 时等 `Reset`/`Retry-After`——**自适应调速比撞墙重试优雅得多**。

```python
# 全部标准库；demo 实现限流响应头构造 + 客户端自适应调速器
import time

def rate_limit_headers(limit: int, remaining: int, window_sec: int,
                       style: str = "ietf") -> dict:
    if style == "ietf":
        h = {"RateLimit-Limit": str(limit),
             "RateLimit-Remaining": str(remaining),
             "RateLimit-Reset": str(window_sec)}          # 秒数口径
    else:                                                  # GitHub 风格
        h = {"X-RateLimit-Limit": str(limit),
             "X-RateLimit-Remaining": str(remaining),
             "X-RateLimit-Reset": str(int(time.time()) + window_sec)}  # 时间戳口径！
    return h

def too_many_requests(limit, remaining, retry_after) -> tuple[int, dict]:
    return 429, {**rate_limit_headers(limit, remaining, retry_after),
                 "Retry-After": str(retry_after)}          # 429 配额问题 + Retry-After

class AdaptiveClient:
    """读响应头自动调速：Remaining<20% 降速，429 等 Retry-After。"""
    def __init__(self, rate: float):
        self.rate = rate                                    # 当前速率（QPS）
        self.base_rate = rate
    def on_response(self, status: int, headers: dict):
        if status == 429:
            wait = float(headers.get("Retry-After", 1))
            self.rate = max(0.2 * self.base_rate, self.rate * 0.5)
            return f"backoff {wait}s, rate→{self.rate}"
        rem = int(headers.get("RateLimit-Remaining",
                              headers.get("X-RateLimit-Remaining", 99)))
        limit = int(headers.get("RateLimit-Limit",
                                headers.get("X-RateLimit-Limit", 100)))
        if rem < limit * 0.2:
            self.rate = self.base_rate * 0.5                # 低于 20% 主动降速
        else:
            self.rate = min(self.base_rate, self.rate * 1.1)  # 缓慢恢复
        return f"rate={self.rate:.1f} (remaining {rem}/{limit})"

if __name__ == "__main__":
    print("ietf:", rate_limit_headers(100, 5, 30))
    print("github:", rate_limit_headers(100, 5, 30, "github"))
    print("429:", too_many_requests(100, 0, 15))
    c = AdaptiveClient(rate=10)
    print(c.on_response(200, rate_limit_headers(100, 3, 30)))    # <20% 降速
    print(c.on_response(429, too_many_requests(100, 0, 15)[1]))  # 429 退避
    print(c.on_response(200, rate_limit_headers(100, 90, 30)))   # 恢复
    # 口径速记：429=你的配额问题（调速可解）；503=服务过载（退避，别当配额撞）
    # X-RateLimit-Reset 的两种实现（秒数 vs 时间戳）必须在文档写死。
```

**追问**：1) 为什么 `RateLimit-Reset` 定义成秒数？——时间戳口径对多窗口/分片配额（如滑动窗口）无法表达「下一个可用时刻」，秒数相对量更通用；但 GitHub 等生态已用时间戳，兼容不可免。2) 分布式下 Remaining 怎么算准？——Redis 集中计数（原子脚本，A101）后回填响应头；多实例各自计数会导致头不准（「限流头漂移」），要么接受近似要么集中化。3) 慢客户端问题（slowloris）与限流什么关系？——限流管 QPS，慢攻击管连接占用，是两层不同防线（连接超时/读超时 vs 配额）。

## 背诵要点
1. 三字段：Limit（窗口总额）/ Remaining（剩余）/ Reset（IETF 秒数 vs GitHub 时间戳，口径必须写死）。
2. 429=配额超限（配 Retry-After，调速可解）；503=服务过载（退避别撞）。
3. 自适应调速：Remaining<20% 主动半速，429 读 Retry-After，恢复缓慢 ×1.1。

## 复盘追问
1. 你的限流中间件把 Reset 写错口径，客户端会怎么坏？（提示：拿秒数当时间戳 → 等到 1970 年附近直接疯狂重试；契约测试该抓这类）
2. 为什么恢复要 ×1.1 缓慢而不是直接回满速？（提示：下游刚缓过来，满速回冲会二次压垮——AIMD 思想）
