### Q6129 · 批量接口的扇出容量账：N 项请求的并发放大与超时预算

> 难度:★★★★☆ | 标签:容量规划, 扇出, asyncio

**问**:客户端一次提交 500 个 item 的批量接口，服务端对每个 item 查下游 50ms——总耗时该按什么公式估？"无脑 gather"会发生什么？并发上限、超时预算、部分失败语义三者怎么设计？

**答**:结论：批量接口的账是**扇出账**。耗时公式：`总耗时 ≈ ceil(N / 并发上限) × 单项延迟`：N=500、串行 50ms 就是 25s（必超时）；全量 gather（并发=500）理论 50ms 完成，但把"1 个客户端请求"放大成"500 个并发下游调用"——瞬时 RPS 放大 500 倍，下游被打爆的概率极高，且你的超时预算要按最慢者兜底。设计三要素：a) **并发上限**：per-request 的 Semaphore（如 20），总耗时 = ceil(500/20)×50ms ≈ 1.25s，下游压力可控；b) **超时预算**：全局预算（如 3s）> 上限×单项 P99（20×80ms=1.6s），并留重试余量；单项超时不拖全局——用 `asyncio.timeout` 包每个任务而非全局一刀切；c) **部分失败语义**：`gather(return_exceptions=True)` 或 TaskGroup 收集 per-item 结果，返回 207 风格的 `{results:[...], failures:[{index, code}]}`，让客户端决定重试哪些——绝不做"全失败即全失败"的伪原子（除非有事务保证）。容量评审还要问：批量上限 N、并发上限与**全局**下游配额的关系（100 个用户同时批量 = 100×并发上限，需要实例级总闸）。

```python
import asyncio, math, time

async def fetch(item: int, latency: float) -> str:
    await asyncio.sleep(latency)                 # 模拟下游 50ms
    return f"ok-{item}"

async def batch(items: list[int], sem_size: int, item_timeout: float):
    sem = asyncio.Semaphore(sem_size)            # per-request 并发上限
    async def one(i: int):
        async with sem:
            try:
                async with asyncio.timeout(item_timeout):
                    return {"index": i, "result": await fetch(i, 0.05)}
            except TimeoutError:
                return {"index": i, "error": "item-timeout"}

    t0 = time.perf_counter()
    results = await asyncio.gather(*[one(i) for i in items])   # gather 收集, 并发被 sem 压住
    cost = time.perf_counter() - t0
    ok = [r for r in results if "result" in r]
    bad = [r for r in results if "error" in r]
    return cost, ok, bad

async def main():
    items = list(range(50))
    # 1) 串行账
    t0 = time.perf_counter()
    for i in items:
        await fetch(i, 0.002)
    print(f"串行 50 项: {time.perf_counter()-t0:.2f}s（客户端必超时的写法）")

    # 2) 无上限 gather: 下游瞬时 RPS = 50 倍放大（此处用小延迟演示）
    t0 = time.perf_counter()
    await asyncio.gather(*[fetch(i, 0.002) for i in items])
    print(f"全量 gather: {time.perf_counter()-t0:.2f}s —— 但下游瞬时收到 50 并发")

    # 3) 有上限 + 单项超时 + 部分失败
    cost, ok, bad = await batch(items, sem_size=10, item_timeout=0.5)
    expect = math.ceil(50 / 10) * 0.05
    print(f"上限 10: {cost:.2f}s（理论 {expect:.2f}s）, 成功 {len(ok)}, 失败 {len(bad)}")
    print("响应: 207 风格 results+failures, 客户端只重试 failures")

asyncio.run(main())
```

**追问一层**：为什么全局超时不能只设一层？（单项超时防"最慢者拖全局"，全局预算防"单项都慢但都在预算内"的累计超支；两层预算相乘才是客户端体验，呼应 Q6019 超时预算分配）。
**追问二层**：批量接口的幂等怎么做？（Idempotency-Key + item 指纹：重试只重发 failures，成功的项用指纹去重，防止部分重试造成重复副作用，呼应 Q6060）。
**追问三层**：实例级总闸怎么实现？（全局 Semaphore 挂在 app.state，值=下游配额/实例权重；或直接依赖客户端并发配额——两种都要监控下游 P99 作为反馈）。

## 背诵要点
- 扇出账：总耗时 ≈ ceil(N/并发上限)×单项延迟；无脑 gather = 瞬时 RPS 放大 N 倍打爆下游。
- 三要素：per-request Semaphore、双层超时（单项 timeout + 全局预算留余量）、207 风格部分失败语义。
- 全局视角：并发用户数 × per-request 上限要过实例级总闸，否则批量接口是隐性 DDoS。
