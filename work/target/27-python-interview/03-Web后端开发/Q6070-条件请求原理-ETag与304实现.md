### Q6070 · HTTP 条件请求原理：ETag 与 304 的服务端实现

> 难度:★★★★ | 标签:原理深挖, ETag, 条件请求, 缓存语义

**问**：列表页每次都返回 2MB 全量 JSON，客户端其实资源没变。If-None-Match/If-Modified-Since 的协议语义是什么？强/弱 ETag 怎么选？Python 后端怎么实现"读前算 ETag 免序列化"与"写冲突检测（If-Match 乐观锁）"？304 的带宽账怎么算？

**答**：协议语义（RFC 9110）：a) **If-None-Match: "<etag>"**（GET）：客户端缓存命中校验——ETag 相等服务端回 **304 Not Modified**（无 body），客户端用本地副本；b) **If-Modified-Since**：时间粒度的旧机制（秒级精度，多实例时钟漂移会误判，优先 ETag）；c) **If-Match: "<etag>"**（写请求）：资源当前 ETag 与客户端持有的一致才执行写——**乐观锁**，并发编辑冲突时回 412 Precondition Failed；d) ETag 两种：强（字节级一致，`"abc123"`）用于冲突检测/断点续传，弱（`W/"abc123"`，语义等价即可）用于缓存校验。Python 后端实现要点：a) **读路径**：先取资源版本号（更新时间+版本列/内容 hash），与请求头比对——匹配直接 304，**省掉序列化与 body 传输**（账：2MB 响应 × 高频轮询 → 304 只有几百字节 header，出口带宽降 95%+，客户端解析 CPU 也没了）；b) 版本来源选型：`updated_at` 便宜但秒级精度同秒内两次改会漏（强 ETag 用 版本列或 `hash(内容)`）；hash 全量内容则每次要读全量——热点资源的版本号列是正解；c) **写路径 If-Match**：UPDATE ... WHERE id=? AND version=? 原子实现乐观锁，0 行受影响→412；d) Vary 头：响应因 Accept-Encoding 等变化时必须带 Vary，否则代理缓存错乱（与 Q6011 压缩联动）；e) 框架支持：FastAPI/Starlette 手工对比，Django 的 `condition` 装饰器内置 ETag/Last-Modified 处理。轮询类接口（长轮询/webhook 状态）是 304 收益最大的场景。

```python
# file: code/03_Web后端开发/q6070_etag_conditional.py
import hashlib, json

DB = {"id": {"body": {"title": "v1", "items": [1] * 500},
             "version": 7, "updated_at": 1700000000}}
FULL_BODY = json.dumps(DB["id"]["body"]).encode()
print("全量响应大小:", len(FULL_BODY), "bytes")

def etag_of(rec):
    # 版本列便宜且精确; 内容 hash 每次要读全量(热资源不划算)
    return f'"{rec["version"]}"'

def get_resource(res_id, if_none_match=None):
    rec = DB[res_id]
    etag = etag_of(rec)
    if if_none_match:
        client = {t.strip() for t in if_none_match.split(",")}
        if etag in client or "*" in client:
            return 304, {"ETag": etag}, b""          # 304: 无 body, 省序列化+带宽
    return 200, {"ETag": etag, "Cache-Control": "no-cache"}, FULL_BODY

# 1) 首次请求: 200 + ETag
st, hdrs, body = get_resource("id")
print("首次:", st, "ETag", hdrs["ETag"], f"body={len(body)}B")

# 2) 缓存命中: 304, 带宽账
st, hdrs, body = get_resource("id", if_none_match=hdrs["ETag"])
print("命中:", st, f"body={len(body)}B -> 轮询场景带宽省 {100-len(body)/len(FULL_BODY)*100:.0f}%")

# 3) 弱校验: 语义等价可接受时 W/"..." (演示格式)
print("弱 ETag 形式: W/\"" + etag_of(DB["id"]).strip('"') + "\" (资源语义等价即可)")

# 4) 写冲突检测: If-Match 乐观锁 (UPDATE ... WHERE version=? 原子语义)
def put_resource(res_id, new_body, if_match):
    rec = DB[res_id]
    if etag_of(rec) != if_match:
        return 412, "Precondition Failed: 资源已被他人修改"
    rec["body"] = new_body
    rec["version"] += 1                            # 原子递增: 0行受影响=>412
    return 200, {"ETag": etag_of(rec)}

client_etag = '"7"'
st, msg = put_resource("id", {"title": "v2"}, client_etag)   # 持旧版本写入成功
print("写1:", st, msg)
st, msg = put_resource("id", {"title": "v3"}, client_etag)   # 还拿旧 ETag -> 冲突
print("写2(过期ETag):", st, msg)

# 5) If-Modified-Since 的精度坑: 同秒两次改漏判 -> 优先 ETag
print("If-Modified-Since: 秒级+时钟漂移误判, 仅兼容旧客户端时保留")
print("协议链: ETag+Cache-Control+Vary 三件套; 轮询/webhook 状态接口收益最大")
```

**追问**：1) 304 判定要在"读库之前"还是之后？——先查版本再决定是否读全量/序列化：版本可以来自 Redis 元数据/内存索引（热点资源版本热缓存），304 路径只付一次元数据查询，这是"读前算 ETag"的本质；但注意版本缓存与写路径的一致性（写后失效版本缓存，与 Q6049 双写语义联动）。2) ETag 和 Cache-Control 怎么分工？——Cache-Control 决定"客户端/代理要不要重新问"（max-age 内根本不发请求），ETag 决定"问了能不能便宜地得到否定答案"（304）；纯静态内容 max-age 长些配合内容 hash 的 ETag/URL 版本化，动态接口 no-cache+ETag（每次问但常 304）。3) 多实例下 ETag 一致性怎么保证？——ETag 必须跨实例稳定（同资源同 ETag）：用业务版本列/内容 hash 而非"实例本地状态"；P 大坑是把进程启动随机盐（如 PYTHONHASHSEED 影响 hash()，见 Q5065）算进 ETag——不同实例 ETag 不同，304 全失效还互相打架。

## 背诵要点
- If-None-Match→304（无 body，省序列化+带宽，轮询场景带宽省 95%+）；If-Match→写乐观锁（UPDATE WHERE version，冲突 412）。
- ETag 来源选业务版本列（便宜精确）优于内容 hash（每次读全量）与 updated_at（秒级同秒漏判）；If-Modified-Since 仅旧客户端兼容。
- 协议链：ETag（问了能省）+Cache-Control（不问）+Vary（代理缓存维度）；ETag 必须跨实例稳定，严禁混入进程随机状态。
