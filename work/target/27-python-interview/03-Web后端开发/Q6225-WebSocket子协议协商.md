### Q6225 · WebSocket 子协议协商：Sec-WebSocket-Protocol 的服务端裁决

难度：P6 ｜ 标签：WebSocket、Sec-WebSocket-Protocol、子协议协商、版本协商、RFC 6455、协议演进

**问**：WebSocket 握手里的 Sec-WebSocket-Protocol 头是干什么的？服务端能不能回一个客户端没提供的子协议？客户端提供了列表但服务端一个都不支持时，正确的应答是什么——能不能"默认回第一个"？子协议在多版本共存与灰度演进里怎么用？

**答**：
结论：子协议协商是 WebSocket 在**帧格式之上的一层应用语义契约**：RFC 6455 只规定了帧结构（文本/二进制、分片、关闭帧），消息里装的是什么编码、什么消息模型（JSON 还是 protobuf、事件命名、心跳格式）由子协议名声明。协商规则严格：①客户端在升级请求里带 `Sec-WebSocket-Protocol: chat.v2.protobuf, chat.v1.json`（**有序列表**，前面的优先级高）；②服务端只能**从客户端提供的列表里挑一个**回在 `Sec-WebSocket-Protocol` 应答头里——返回列表之外的值属于协议违规，浏览器会**直接断开**连接（fail the WebSocket connection）；③客户端没提供子协议头时，服务端**不能回这个头**（回一个空值或任意值都违规），视为普通升级；④列表里没有服务端支持的项时，正确做法是**拒绝升级**（返回 4xx）或按 HTTP 语义回 406，绝不能"随便回一个自己想用的"——客户端会按它声明的编解码发消息，服务端按另一个格式解析，错配在**首帧即崩**，且这种崩表现为诡异的数据解析错误而不是清晰的握手失败。

取舍：a) 服务端实现要点：从 offer 列表按**客户端给的顺序**取第一个双方都支持的（客户端优先级优先，不是服务端挑自己最喜欢的）；b) 子协议名即版本号：`chat.v1.json` / `chat.v2.protobuf` 的命名让版本成为协商能力而非部署配置——新客户端把 v2 放 offer 首位，服务端支持就自动升级，不支持自然落回 v1，灰度在协议层自动完成；c) 服务端淘汰旧版本：从 supported 集合里移除 v1 之前，先监控 offer 列表里"只提供 v1 的客户端占比"，归零再移除；d) 不要用子协议承载鉴权：token 走查询参数或首帧消息，子协议头是明文握手的一部分且代理可能改写；e) 长连接场景注意：升级成功后子协议就固定了，版本切换必须重连——客户端要实现"收到 4xx/不认识版本时降级重试"的逻辑。

实战：事故形态是"IM 服务端升级支持新消息格式，有人图省事在握手处理里写死 `Sec-WebSocket-Protocol: chat.v2.protobuf` 应答所有客户端——老客户端（只会 JSON 编解码）握手成功后按 v2 被记录，首条消息服务端按 protobuf 解析 JSON 字节流，全场解析错误且没有任何告警指向握手层；修复：严格从 offer 交集挑选、交集为空拒绝升级并打版本监控"。下面演示协商裁决器。

```python
# WebSocket 子协议协商: Sec-WebSocket-Protocol 的服务端裁决
SUPPORTED = {"chat.v1.json", "chat.v2.protobuf"}


def negotiate(offered: list, supported: set) -> tuple:
    """返回 (是否接受, 选中的子协议, 说明); 规则按 RFC 6455: 服务端从客户端列表中挑一个"""
    if not offered:
        return False, None, "客户端未提供子协议 -> 不带 Sec-WebSocket-Protocol 应答(视为普通升级)"
    for proto in offered:                    # 按客户端声明的优先序取第一个双方都支持的
        if proto in supported:
            return True, proto, f"应答 Sec-WebSocket-Protocol: {proto}"
    return False, None, "全部不支持 -> 返回 4xx/直接拒绝升级, 不能随便挑一个回"


cases = [
    (["chat.v2.protobuf", "chat.v1.json"], "新客户端"),
    (["chat.v1.json"], "老客户端"),
    (["chat.v9.xml"], "未知版本"),
    ([], "不带子协议"),
]
for offered, label in cases:
    ok, proto, msg = negotiate(offered, SUPPORTED)
    print(f"    [{label}] offer={offered} -> {'接受' if ok else '拒绝'}: {msg}")

print("[1] 服务端只能从客户端提供的列表里挑, 返回列表外的值属于违规, 浏览器会断开")
print("[2] 没谈拢就拒绝升级, 千万不要'默认回第一个': 客户端按自己的编解码走, 协议错配在首帧即崩")
print("[3] 子协议即版本契约: 客户端按优先级列出可用的, 服务端取交集后回一个 -- 类似 HTTP 内容协商")
print("[4] 演进策略: 新协议排在 offer 首位, 服务端支持即自动升级, 逐步淘汰旧版本后从 supported 里移除")
```

**追问一**：子协议协商与 HTTP 的内容协商（Accept 头）机制上有什么异同？为什么 WebSocket 不复用 Accept 机制？—— 相同点：都是客户端声明可接受集合 + 服务端从中选择，"选择权在服务端、偏好权在客户端"。差异有三：①**时机**：Accept 在普通请求/响应里每请求可变，子协议在升级握手里一次性敲定且**绑定整个连接生命周期**——长连接里不能中途换，这是流式会话与请求响应的根本差异；②**应答形式**：HTTP 协商失败可回 406 并带可用项让客户端重试，WebSocket 拒绝升级后客户端要自己实现降级重试逻辑；③**校验严格性**：Accept 回不匹配的内容只是体验问题（客户端可能解析失败），子协议应答列表外的值是**协议违规**，浏览器直接断连——RFC 6455 把这个头设计成强校验，因为错配的代价是整个消息层语义崩坏。不复用 Accept 的原因：升级握手本身就是 HTTP 的一次特殊使用，用独立头保持升级层与内容层的正交，避免同一个请求里两层协商互相干扰。

**追问二**：服务端怎么做子协议的版本监控与淘汰？协议错配（服务端回了正确协议但帧内格式不对）靠什么发现？—— 淘汰三步：①握手处埋点记录 offer 列表分布（`collections.Counter` 聚合上报），按天看"仅支持旧版本"的客户端占比曲线；②占比归零后先在服务端对旧版本**只读告警**（收到 v1 连接就打日志）一个发布周期，确认没有隐藏流量（企业内网老版本、缓存中的旧前端 bundle）；③从 supported 移除并拒绝升级，同时给老客户端一个明确的拒绝码/文案让它触发降级或强制刷新。协议错配的发现：子协议头对了但**帧内格式**不对（客户端实现 bug、中间代理剥头重写）靠消息层自描述性兜底——每条消息带版本字段/魔术数字，解析失败即上报结构化错误帧并断连，让问题在首帧暴露而不是积累成静默数据损坏；这和"信封地址对了内容写错语言"一个道理，握手层与消息层各要一道校验。

## 背诵要点
- 子协议 = 帧格式之上的消息语义契约；服务端只能从客户端 offer 有序列表挑一个，回列表外的值浏览器直接断连。
- 无 offer 不回该头；交集为空拒绝升级（4xx），绝不"默认回第一个"——错配首帧即崩且难排查。
- 子协议名即版本：新版本放 offer 首位自动灰度升级；淘汰先监控 offer 分布，归零后再移除 supported。

## 复盘追问
- 服务端握手时回自己想用的协议名会怎样？（列表外值=协议违规浏览器断连；列表内错选=首帧解析崩，监控要在握手层埋版本分布）
- 长连接里版本怎么切换？（协商一次性绑定连接生命周期，切换必须重连；客户端要有降级重试逻辑）
