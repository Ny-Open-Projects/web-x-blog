### Q6229 · 图形验证码：会话绑定、一次性消费与防重放

难度：P6 ｜ 标签：验证码、captcha、一次性消费、防重放、限流、恒定时间比对、Redis TTL

**问**：图形验证码的服务端设计要点有哪些——答案存哪、怎么校验？"先 pop 后验"的一次性消费为什么是关键设计？验证码 ID 与答案的绑定关系怎么防"张三的验证码李四用"？验证码为什么必须加 TTL 与签发限流？答案存储用明文还是哈希？

**答**：
结论：验证码的本质是**区分人机的短时效一次性凭证**，设计要点五条：①**ID 与答案解耦存储**：`captcha_id`（随机 token，`secrets.token_urlsafe` 生成不可预测）发给客户端，答案哈希留服务端（Redis + TTL），客户端提交的是 `captcha_id + user_answer` 对——服务端绝不把答案（哪怕哈希）发出去；②**一次性消费 = 先 pop 后验**：校验前先 `STORE.pop(cid)` 把凭证从存储里**弹掉**，无论答案对错、无论后续逻辑——凭证已不存在，重放同一个 id 天然被拒（脚本抓包后反复提交同一验证码撞库的路径直接堵死）；答案错误同样销毁——不让坏答案留在缓存里给攻击者继续试；③**会话绑定**：签发时把 `captcha_id` 与会话/用户标识绑定，校验时核对来源——防"A 的浏览器拿到验证码、交给脚本在 B 的会话里提交"（分布式协作刷接口）；④**TTL 短时效**：180 秒量级——验证码的生命周期就该是"展示到提交"这几分钟，过期作废由 Redis TTL 自动清理，不靠应用定时任务；⑤**签发限流**：验证码图片接口本身要限流（按 IP/会话），否则攻击者可以无限拉图离线 OCR——签发端限流与校验端失败锁定要联动。答案比对用 `hmac.compare_digest` + 大小写/空白归一化。

取舍：a) 存储：Redis TTL 是标配（天然过期、多实例共享）；不用 Cookie 存答案哈希——客户端可控的存储没有可信度；b) 答案哈希（HMAC）vs 明文：服务端内存/Redis 被读时（日志泄漏、SSRF 到 metadata）哈希让答案不直接泄漏，成本是每次校验一次哈希——HMAC 带固定密钥还能防"攻击者自造哈希"，标准做法；c) 图形验证码的**可用性平衡**：扭曲过度真人认不出、过轻被 OCR 秒破——现代实践是"简单图形 + 行为风控"（失败次数、频率、设备指纹），验证码只做第一道闸，深度防护靠风控而非把图形做变态；d) 无状态替代（签名式验证码：答案哈希+过期时间直接签名发给客户端）：省 Redis 但密钥泄漏即全线失守，且无法做服务端签发限流统计——规模小可用，规模大走有状态；e) 已有短信/邮箱验证码的场景，图形验证码通常放在**发短信之前**——防短信轰炸（威胁模型不同：图形码防机器刷短信，短信码防身份冒用）。

实战：事故形态是"登录接口被脚本撞库：分析日志发现攻击者用同一个 captcha_id 在 10 分钟内提交了 4000 次（早期实现只'校验不销毁'，答案对的能反复用、错的也留在缓存里重试），且验证码图片接口无限流被 OCR 离线批量破解；修复：先 pop 后验一次性消费 + 答案错误即销毁 + 签发接口按 IP 10 次/分钟限流 + 失败 5 次锁账号 15 分钟"。下面演示一次性消费的完整语义。

```python
# 图形验证码: 生成、会话绑定与一次性消费
import hashlib
import hmac
import secrets
import time

STORE: dict = {}          # captcha_id -> (answer_hash, expires_at); 生产用 Redis + TTL


def issue(answer: str, ttl: float = 180.0) -> str:
    cid = secrets.token_urlsafe(16)                       # 随机 ID, 不可预测
    digest = hmac.new(b"captcha-secret", answer.strip().lower().encode(), hashlib.sha256).hexdigest()
    STORE[cid] = (digest, time.time() + ttl)
    return cid


def verify(cid: str, answer: str) -> tuple:
    item = STORE.pop(cid, None)                           # 先弹后验: 天然一次性消费
    if item is None:
        return False, "captcha_id 不存在或已消费"
    digest, expires_at = item
    if time.time() > expires_at:
        return False, "验证码已过期"
    user_digest = hmac.new(b"captcha-secret", answer.strip().lower().encode(), hashlib.sha256).hexdigest()
    if not hmac.compare_digest(digest, user_digest):
        return False, "答案不符"
    return True, "通过"


print("[1] 发放: captcha_id(随机) + 答案哈希存储 + TTL 180s")
cid = issue("a7x9")
print("    captcha_id =", cid[:12], "... (图上画 a7x9)")

print("[2] 首次校验: 通过即销毁")
print("   ", verify(cid, "a7x9"))

print("[3] 重放同一 id: 已不存在 -> 拒绝 (防撞库脚本一次抓包反复试)")
print("   ", verify(cid, "a7x9"))

print("[4] 答案不符同样销毁: 不能让坏答案留在缓存里继续试")
cid2 = issue("b2k4")
print("   ", verify(cid2, "0000"))
print("   ", verify(cid2, "b2k4"))

print("[5] 关键设计点: 与会话绑定校验来源(防 A 的验证码给 B 用) + 全局签发限流 + 失败次数联动锁定")
print("[6] 恒定时间比对 + 大小写归一 + 先 pop 后验, 三个细节缺一不可")
```

**追问一**：为什么答案错误也要销毁凭证？"错误 5 次才作废"不是更人性化吗？—— 因为错误次数是攻击者的**信息通道**：验证码答案空间通常只有几千到几万组合（4 位字母数字），"同一凭证试 N 次"等于把在线穷举的入口打开——OCR 半猜出一个候选集后可以逐个试，每次错误都免费获得"这个答案不对"的确认信号。销毁凭证后每次尝试都要**重新拉一张图**（过签发限流 + 重新 OCR），攻击成本从"零成本试错"变为"每猜一次付一次拉图+识别成本"，被限流进一步放大。人性化的正确替代：**签发限流放宽一点**（拉图便宜一点）而不是**校验宽容一点**（同一凭证多试几次）——多试几次是指数级降低攻击成本，多拉几张图只是线性增加正常用户摩擦。

**追问二**：验证码这套设计里，哪些环节最常出"并发竞态"问题？分布式部署时 pop 的原子性怎么保证？—— 三个竞态点：①**并发校验同一 cid**：应用层的"查存在→校验→删除"三步在两个请求同时进入时都可能通过查存在（TOCTOU），同一凭证被消费两次——单进程用锁可解，分布式必须用**原子操作**：Redis 的 `GETDEL`（6.2+）或 Lua 脚本把"取值+删除"做成原语，天然一次性；②**签发与校验跨实例**：实例 A 签发、请求落到实例 B 校验——本地字典方案直接失效，共享存储（Redis）是分布式部署的硬前提，这也是"演示代码用 dict、生产必须 Redis"的真正原因（不只是过期清理）；③**TTL 与业务时长错位**：签发 180s 但用户在提交页停留超时，校验失败——这是体验问题不是安全问题，正确做法是前端在 TTL 内提示刷新，而不是放宽 TTL。`pop` 先于验答的次序在分布式下同样成立：`GETDEL` 返回值之后再做哈希比对，即使比对耗时期间来了并发请求，凭证已被原子弹掉。

## 背诵要点
- 五要点：随机 captcha_id + 服务端存答案 HMAC、先 pop 后验一次性消费、会话绑定防跨用户、TTL 180s、签发限流。
- 答案错误同样销毁：错误次数是穷举信息通道；人性化靠放宽拉图限流，不靠同一凭证多试。
- 分布式必须 Redis + 原子 GETDEL/Lua（并发校验 TOCTOU）；验证码放发短信前防短信轰炸。

## 复盘追问
- 同一 captcha_id 被并发提交两次怎么防？（Redis GETDEL/Lua 原子取删；应用层查删分离存在 TOCTOU）
- 为什么错误答案不能留在缓存里重试？（答案空间小，错误次数=穷举反馈；销毁后每次试错都要重新过拉图限流）
