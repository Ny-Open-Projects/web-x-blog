### Q6104 · 高基数指标标签的爆炸容量账

> 难度:★★★★☆ | 标签:容量规划, 可观测, 指标

**问**:接入 Prometheus 后内存一周涨了一倍，`http_request_duration_seconds` 时间线从 2000 涨到 50 万，发生了什么？

**答**:结论：这是标签基数（cardinality）爆炸——每新增一个 label 取值组合就新建一条时间序列，把 `user_id`/`request_id`/未归一的 `path` 放进 label，序列数 = 各 label 基数的笛卡尔积，几十万×N 的组合直接把内存（每序列几百字节到 1KB+）、存储与查询拖垮。容量账公式：序列数 = Σ 每个 metric 的 label 组合数，内存 ≈ 序列数 × 每序列开销 × 保留时间系数。治理四招：① 把无界值（用户 ID、trace ID）从 label 摘出来走日志/trace（Q6015 分层）；② 路径归一化（`/users/{id}` 而不是原始 path）；③ 限白名单维度，新增 label 走评审；④ 运行期兜底——对每个 metric 设序列上限，超限打告警并丢样本。取舍：低基数 label（method/status）信息价值高可保留；"能查得到"和"查得起"之间永远选后者。

```python
# 基数爆炸的账：label 组合 = 笛卡尔积
def series_count(labels: dict[str, int]) -> int:
    r = 1
    for v in labels.values():
        r *= v
    return r

good = series_count({"method": 5, "status_class": 3, "path_tpl": 40})
bad = series_count({"method": 5, "status": 60, "path_raw": 50_000, "user_id": 10_000})
print(f"治理前序列数 {bad:,} → 治理后 {good:,}（{bad/good:,.0f}x）")
print(f"内存账(每序列 0.5KB)：{bad * 512 / 2**30:.1f}GB vs {good * 512 / 2**20:.0f}MB")

# 运行期兜底：单 metric 序列上限（自实现的门卫）
class CardinalityGuard:
    def __init__(self, cap: int):
        self.cap, self.seen = cap, set()
    def allow(self, key: tuple) -> bool:
        if key in self.seen or len(self.seen) < self.cap:
            self.seen.add(key)
            return True
        return False            # 超限：丢弃 + 告警，保护宿主进程

g = CardinalityGuard(cap=1000)
hits = sum(g.allow(("u", i)) for i in range(1200))
print(f"1200 个取值只放行 {hits}（cap=1000），溢出需告警")
```

**背诵要点**
- 序列数=label 基数笛卡尔积；无界值（ID/原始 path）禁止入 label。
- 内存≈序列数×每序列开销，治理靠归一化+白名单+序列上限。
- 高价值维度走日志/trace，指标只留可聚合维度。
