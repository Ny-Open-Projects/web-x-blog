### Q6264 · Accept 的 q 值与通配符：内容协商何时该回 406

难度：P6 ｜ 标签：HTTP、Accept、内容协商、406、q 值、Vary

基线：CPython 3.12.2，纯标准库；实现一个最小的 Accept 解析与匹配器，覆盖 q 值、`type/*`、`*/*`、q=0 与无匹配。

**问**：同一个 `/export` 接口，浏览器请求返回 HTML，SDK 请求返回 JSON，本来靠 `Accept` 协商。某天 SDK 升级后把请求头写成 `Accept: application/json;q=0.9, text/html;q=0.8`，服务端却返回了 406；另一个客户端发 `Accept: */*` 一直正常，改成 `Accept: application/xml` 后拿到 406 却没人知道为什么。更奇怪的是，有客户端发 `Accept: application/json;q=0` 表示"我就是不要 JSON"，服务端仍然返回 JSON。q 值到底怎么排序？`*/*` 和 `type/*` 的优先级怎么算？什么时候该回 406？

**答**：

- **结论**：`Accept` 是"媒体范围 + 可选 q 值"的列表：`type/subtype`、`type/*`、`*/*`，`q` 取 0～1，默认 1；**q=0 表示明确不接受**，不是"最低优先级"。服务端对每个可提供的类型，先找**最具体**的匹配范围：精确范围覆盖 `type/*`，`type/*` 覆盖 `*/*`，该范围的 q 就是这个类型的 q；如果最具体范围的 q=0，这个类型直接排除，**不能**回退到更宽的通配符去拿一个更大的 q。得到每个候选的 q 后，再按 q 高 → 特异性高 → 服务端偏好排序。所有候选都被排除或没有匹配时，才返回 406。没有 `Accept` 头视为 `*/*`，接受任何类型。匹配时媒体类型参数（如 `application/json; charset=utf-8`）通常不参与范围匹配，除非范围里显式带了参数。
- **取舍**：API 服务常见的做法是"忽略 Accept，永远 JSON"，简单但不符合 HTTP 语义，客户端明确写 `q=0` 时无法拒绝；严格协商更正确，但要处理通配符、q=0、参数、大小写、非法 q、空列表等边角，且要在响应里加 `Vary: Accept`，否则 CDN/代理会把 HTML 缓存给要 JSON 的客户端。另一个取舍是 406 的可用性：直接 406 会让客户端拿到空 body，最好带一个说明支持类型的 JSON/文本 body，并记录 `not_acceptable` 指标，方便排查"为什么突然 406"。
- **实战**：事故的 SDK 把 `Accept` 写成 `application/json;q=0.9, text/html;q=0.8`，服务端只提供 `text/html` 和 `application/xml`（JSON 端点还没上线），HTML 本应以 q=0.8 胜出，但代码把 q 当整数解析（`int("0.9")`、`int("0.8")` 都抛异常，两段范围都被丢弃），只剩 XML 不匹配 → 406。修复：① 用 `float` 解析 q 并按 `[0,1]` 截断，非法 q 视为 0 并记录；② 匹配分数用 `(q, specificity, -server_order)` 排序；③ q=0 的范围直接排除；④ 406 响应带 `Accept` 支持列表，并加 `Vary: Accept`。上线后 406 从每天 1.2 万降到 30，且都能定位到具体客户端。

下面实现解析与匹配，验证 q 排序、通配符特异性、q=0 排除、缺省头与 406。

```python
# Accept 内容协商: q 值 > 特异性 > 服务端偏好; q=0 表示不接受
def parse_accept(header):
    ranges = []
    for order, item in enumerate(header.split(",")):
        item = item.strip()
        if not item:
            continue
        parts = [p.strip() for p in item.split(";")]
        media = parts[0].lower()
        q = 1.0
        for param in parts[1:]:
            key, _, value = param.partition("=")
            if key.strip().lower() == "q":
                try:
                    q = float(value)
                except ValueError:
                    q = 0.0
                q = max(0.0, min(1.0, q))
        if "/" not in media:
            continue
        major, minor = media.split("/", 1)
        if major == "*" and minor != "*":
            continue
        ranges.append((major, minor, q, order))
    return ranges


def specificity(offer, media_range):
    major, minor = offer
    r_major, r_minor, _, _ = media_range
    if r_major == "*" and r_minor == "*":
        return 0
    if r_major == major and r_minor == "*":
        return 1
    if r_major == major and r_minor == minor:
        return 2
    return -1


def quality_for(offer, ranges):
    """返回 (最具体匹配的 q, 该特异性); 无匹配返回 (None, -1)."""
    best_spec = -1
    best_q = None
    for media_range in ranges:
        spec = specificity(offer, media_range)
        if spec < 0:
            continue
        if spec > best_spec:
            best_spec, best_q = spec, media_range[2]
        elif spec == best_spec and media_range[2] > best_q:
            best_q = media_range[2]
    return best_q, best_spec


def negotiate(header, offers):
    """offers: [(type, subtype), ...], 按服务端偏好排序; 返回下标或 None."""
    ranges = parse_accept(header) if header else [("*", "*", 1.0, 0)]
    best = None
    for index, offer in enumerate(offers):
        q, spec = quality_for(offer, ranges)
        if q is None or q == 0:          # q=0: 最具体范围明确拒绝, 不回退
            continue
        score = (q, spec, -index)
        if best is None or score > best[0]:
            best = (score, index)
    return None if best is None else best[1]


offers = [("application", "json"), ("text", "html"), ("application", "xml")]

cases = [
    ("application/json;q=0.9, text/html;q=0.8", 0),
    ("text/*;q=0.5, application/json;q=0.5", 0),      # 同 q, 精确 > 通配
    ("*/*;q=0.1", 0),                                  # 全部匹配, 服务端偏好
    ("application/xml", 2),
    ("application/json;q=0, */*;q=0.5", 1),            # JSON 被 q=0 排除, 选 HTML
    ("application/json;q=0", None),                    # 只排除 JSON, 其他也不匹配
]

for header, expected in cases:
    got = negotiate(header, offers)
    print(f"[1] {header!r} -> {got}")
    assert got == expected, (header, got, expected)

# 缺省 Accept 视为 */*
assert negotiate("", offers) == 0
assert negotiate(None, offers) == 0
print("[2] 缺省 Accept 选择服务端首选")

# 非法 q 视为 0, 不参与
assert negotiate("text/html;q=abc, application/json;q=0.1", offers) == 0
print("[3] 非法 q 被当作 0, JSON 仍胜出")

# 不支持的媒体类型 -> 406
assert negotiate("image/png", offers) is None
print("[4] 无匹配 -> 406")

# 匹配时忽略 offer 的参数, 只看 type/subtype
assert negotiate("application/json", [("application", "json")]) == 0
print("[5] 结论: q 排序 -> 特异性 -> 服务端偏好; 全不匹配才 406")
```

**追问一**：`Accept: */*;q=0` 是什么意思？—— 所有媒体类型都不接受，等价于"别给我任何东西"，服务端应回 406。很多实现会把 `*/*` 当成"接受一切"而忽略 q，这是错的；q=0 必须排除。反过来，`Accept: application/json;q=0, */*` 表示"除了 JSON 都可以"，匹配时 JSON 被排除，其他类型走 `*/*` 的 q=1。

**追问二**：为什么响应要加 `Vary: Accept`？—— 同一个 URL 可能因 `Accept` 返回不同表示；如果共享缓存只按 URL 做键，会把 HTML 响应缓存下来返回给要 JSON 的客户端。`Vary: Accept` 告诉缓存"这个响应的变体维度包括 Accept"，缓存键要带上该请求头。同理，`Accept-Encoding`、`Accept-Language`、`Origin` 等协商维度也要进 `Vary`；漏了就是缓存串味，不是内容协商本身的错。

## 背诵要点

- `Accept` 是媒体范围 + q（0～1，默认 1）；q=0 是明确拒绝，不是最低优先级。
- 选择顺序：q 最高 → 特异性（精确 > `type/*` > `*/*`）→ 服务端偏好；全部 q=0/无匹配才 406。
- 缺省头视为 `*/*`；响应加 `Vary: Accept`，否则共享缓存会串味。

## 复盘追问

- `Accept: text/*;q=0.9, text/html;q=0.1` 请求 `text/html` 时选哪个 q？（更具体的 `text/html;q=0.1` 覆盖 `text/*;q=0.9`，q=0.1；特异性优先于通配）
- 为什么不能只用 `header.split(",")[0]` 做协商？（客户端顺序不代表优先级，q 值才是；第一项可能是 q=0）
