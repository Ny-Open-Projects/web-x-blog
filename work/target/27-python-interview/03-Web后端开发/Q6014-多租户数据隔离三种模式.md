### Q6014 · 多租户数据隔离三种模式

> 难度:★★★ | 标签:多租户, 架构, 隔离

**问**：SaaS 多租户隔离三模式——共享表加 tenant_id、独立 schema、独立数据库——各自的隔离强度/成本/运维复杂度怎么排？行级隔离怎么防「漏租户过滤」这种致命 bug（一个忘写 WHERE 就裸奔），混合模式怎么演进？

**答**：三模式排序：① **共享表 + tenant_id**：成本最低（一套表）、密度最高，隔离强度靠**查询纪律**——每个查询必须带租户条件，致命风险是漏 WHERE（跨租户数据泄漏事故的头号来源）；② **独立 schema**（Postgres schema-per-tenant）：中等隔离、备份/恢复可按租户粒度，但 schema 数量爆炸（万级租户时 catalog 膨胀、连接池按 schema 分键困难）；③ **独立数据库**：隔离最强、单租户故障与慢查询互不影响，成本最高（连接数爆炸、迁移要跑 N 遍），适合大客户/合规要求。防漏过滤的工程手段：**ORM 层强制**——SQLAlchemy with_loader_criteria 全局注入 tenant_id 条件、Django 自定义 manager 默认过滤；**连接层**再兜底（Postgres RLS 行级安全策略，DB 强制即使应用漏了也查不到）；会话级租户上下文（AsyncContextVar）传递，绝不从请求参数拼。演进路径：起步共享表 → 大客户迁独立库 → 混合路由（租户→数据源注册表）。

```python
# 全部标准库 + sqlalchemy（标注基线 SQLAlchemy 2.0；缺库降级看思路注释）
try:
    import sqlalchemy as sa
    from sqlalchemy import event
except ImportError:
    raise SystemExit("缺 sqlalchemy：pip install 'sqlalchemy>=2.0'；降级重点：RLS + ContextVar 思路")

import contextvars
tenant_var = contextvars.ContextVar("tenant", default=None)   # 租户上下文贯穿请求

meta = sa.MetaData()
orders = sa.Table(
    "orders", meta,
    sa.Column("id", sa.BigInteger, primary_key=True),
    sa.Column("tenant_id", sa.String(32), nullable=False),
    sa.Column("amount", sa.Numeric(10, 2)),
)

eng = sa.create_engine("sqlite://")
meta.create_all(eng)

# 防漏过滤第一层：ORM 全局注入 tenant_id（with_loader_criteria）
@event.listens_for(sa.Session, "do_orm_execute")
def _add_tenant_filter(execute_state):
    tenant = tenant_var.get()
    if tenant and not execute_state.is_column_load and not execute_state.is_relationship_load:
        execute_state.statement = execute_state.statement.where(
            orders.c.tenant_id == tenant)          # 所有 ORM 查询自动带上租户条件

# 防漏过滤第二层（Postgres RLS，SQLite 无此功能，此处给伪 SQL 展示思路）：
# CREATE POLICY tenant_isolation ON orders
#   USING (tenant_id = current_setting('app.tenant'));
# ALTER TABLE orders ENABLE ROW LEVEL SECURITY;   → DB 层强制，应用漏写也查不到别的租户

def demo():
    with sa.Session(eng) as s:
        tenant_var.set("t-a")                     # 请求开始时绑定租户（中间件层）
        s.add(orders(id=1, tenant_id="t-a", amount=10))
        s.add(orders(id=2, tenant_id="t-b", amount=20))
        s.commit()
        rows = s.execute(sa.select(orders)).scalars().all()   # 明明没写 WHERE tenant_id
        assert [r.tenant_id for r in rows] == ["t-a"], "全局过滤器自动生效"
        print("漏写 WHERE 仍只见本租户:", [(r.id, r.tenant_id) for r in rows])

demo()
```

**追问**：1) 为什么不推荐「应用层记得写 WHERE」？——人在压力下必漏：新查询、原生 SQL、后台脚本、调试 console 都是漏点；纪律必须固化为机制（ORM 事件/RLS），不能靠 review。2) RLS 的代价？——每查询多一过滤层（优化器可部分消除）、`SET app.tenant` 要随连接池借还管理（连接池 reset 钩子），漏 set 会全表可见或全表不可见。3) 独立库模式的连接池爆炸怎么解？——pgbouncer 事务池 + 租户路由中间层（活跃租户集合远小于总租户数，按需建连），或大客户专用实例+其余共享的混合。

## 背诵要点
1. 三模式：共享表（密度高/漏 WHERE 风险）、schema（备份粒度好/catalog 膨胀）、独立库（隔离强/连接爆炸）。
2. 漏过滤防线三层：ORM 全局注入（with_loader_criteria/自定义 manager）→ Postgres RLS DB 强制 → ContextVar 会话上下文。
3. 演进：共享表起步 → 大客户独立库 → 混合路由；纪律必须固化成机制，不靠 review。
