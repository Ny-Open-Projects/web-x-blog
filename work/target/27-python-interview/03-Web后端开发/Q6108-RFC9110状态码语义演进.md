### Q6108 · RFC 2616 到 RFC 9110 的状态码语义演进

> 难度:★★★★☆ | 标签:版本演进, HTTP, 状态码

**问**:HTTP 语义文档从 RFC 2616 重构为 9110/9112，状态码层面有哪些实质变化？工程上要跟进什么？

**答**:结论：2014 年起 2616 拆解为 RFC 723x，2022 年再演进为 **RFC 9110（语义）+ 9112（HTTP/1.1 报文）**。状态码的实质变化点：① `308 Permanent Redirect`（RFC 7238/7538 转正）补齐永久重定向"保留方法/体"的语义（307 的永久版，Q1900 尾斜杠规范化就在用）；② `418 I'm a teapot` 被正式收编为保留状态码（April Fools → 合法注册）；③ 明确 `201/204` 与 Content-Length 的约束、`451`（法律原因，RFC 7725）等新增；④ 语义收紧：409/410/428（Precondition Required，RFC 6585）等条件请求家族更成体系；⑤ `101` 等仅在 HTTP/1.1 有意义。工程跟进点：错误响应契约按新 RFC 措辞（409 冲突 vs 422 校验失败 vs 428 缺前置条件）、重定向选 307/308 保留方法、API 文档把状态码矩阵挂到 RFC 9110 条目。基础三件套（Q090）之外，资深要能讲"为什么用 428 而不是 412"这类精细语义。

```python
from http import HTTPStatus

# 标准库内建了状态码与 reason 的映射（随版本演进同步）
print(HTTPStatus(308), "|", HTTPStatus(418).phrase, "|", HTTPStatus(451).phrase)

# 语义矩阵：常用但常被误用的边界
matrix = {
    409: "资源状态冲突（如并发写同版本）",
    412: "If-Match 前置条件失败（客户端带了条件）",
    428: "客户端根本没带前置条件，服务端要求必须带",
    422: "语法对但语义校验失败",
    308: "永久重定向且保留方法与请求体",
}
for code, why in matrix.items():
    print(code, HTTPStatus(code).phrase, "->", why)

# 选码流程：条件写接口的完整判定
def choose_status(has_version, if_match_ok, conflicts):
    if conflicts: return 409
    if not has_version: return 428          # 强制乐观并发
    if not if_match_ok: return 412
    return HTTPStatus.NO_CONTENT.value
print("条件写示例:", choose_status(True, False, False), choose_status(False, True, False))
```

**追问一层**:301 与 308 在"POST 改写"场景的行为差异？浏览器与爬虫如何对待？
**追二维**:409/412/428 在乐观并发控制（If-Match ETag）里各自承担什么角色？组合顺序是什么？

**背诵要点**
- 语义演进主线：2616 → 723x → 9110/9112；308/418/451 是可见变化。
- 条件请求三兄弟：412（条件失败）、428（缺条件）、409（状态冲突）。
- 重定向保留方法用 307/308；API 文档状态码矩阵挂 RFC 9110。

**复盘追问**
- 网关/SDK 只认 2xx/4xx/5xx 粗分类时，精细状态码的收益如何落地？提示：错误码契约 + 客户端可编程重试策略。
- 429 与 Retry-After、RateLimit 头（Q6018）在 9110 体系外如何协同？提示：RFC 9336 扩展。
