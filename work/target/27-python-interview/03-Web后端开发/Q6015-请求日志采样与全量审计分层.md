### Q6015 · 请求日志分层

> 难度:★★☆ | 标签:可观测性, 日志, 采样

**问**：万 QPS 服务每天请求日志几百 GB——「全量记」和「采样记」怎么分层？哪些请求必须全量（审计线）、哪些可以采样（观测线）、错误日志怎么保采样不丢关键个案？日志脱敏在分层里放哪一步？

**答**：双线分层：① **审计线（全量、不可采样）**：写操作、鉴权事件、资金/权限变更、合规要求的访问记录——属性是「法律与事故追责需要」，丢失不可接受，只做脱敏不做抽样；② **观测线（采样）**：成功 GET、健康检查、静态资源——属性是「统计分布有意义」，1%-10% 采样足够看延迟分布与流量形状。**错误日志的特殊规则**：错误天然「个案有价值」，按比例采会丢个案——正确姿势是「尾部触发采样」（tail-based sampling）：全请求经过 trace，**只有出现错误的 trace 全量保留**，成功的按比例采——这需要 trace 先落缓冲再决定（ Jaeger/Tempo 的 tail sampling 模式），纯日志做不到就要「错误请求的 trace_id 反查」方案。脱敏在**写入前**一步完成（中间件层统一做，禁止各 handler 自行打日志）：身份证/手机号掩码、token 整体替换，因为日志一落地就进分析管道与第三方备份，落地后再脱敏等于没脱。

```python
# 全部标准库；demo 实现「分层日志路由 + 尾部触发采样 + 脱敏管道」
import json, random, re, time, logging
from collections import deque

class TraceBuffer:
    """尾部触发采样：请求结束后按结局决定全留或按比例采。"""
    def __init__(self, sample_rate: float = 0.1, keep_sec: float = 30):
        self.rate, self.buf = sample_rate, deque(maxlen=50000)
    def record(self, trace: dict):
        keep = (trace["status"] >= 500) or (trace["status"] == 429) \
               or random.random() < self.rate     # 错误/限流全留，成功按比例
        if keep:
            self.buf.append(trace)

MASKS = [
    (re.compile(r"(\d{3})\d{4}(\d{4})"), r"\1****\2"),        # 手机号
    (re.compile(r"(Bearer\s+)\S+"), r"\1***"),                 # token
    (re.compile(r"(\d{6})\d{8}(\d{4})"), r"\1********\2"),     # 身份证
]
def scrub(text: str) -> str:
    for pat, rep in MASKS:
        text = pat.sub(rep, text)
    return text

def classify(method: str, path: str, status: int) -> str:
    if method in ("POST", "PUT", "DELETE") or "/auth" in path or "/pay" in path:
        return "audit"                    # 审计线：全量
    if status >= 400:
        return "error"                    # 错误线：全留个案
    return "sample"                       # 观测线：采样

def log_request(trace: dict, buf: TraceBuffer) -> str:
    line = scrub(json.dumps(trace, ensure_ascii=False))   # 脱敏在写入前最后一步
    bucket = classify(trace["method"], trace["path"], trace["status"])
    if bucket in ("audit", "error"):
        logging.getLogger("audit").info(line)
        return bucket
    buf.record(trace)
    return bucket

if __name__ == "__main__":
    random.seed(1)
    buf = TraceBuffer(sample_rate=0.1)
    tags = {"audit": 0, "error": 0, "sample": 0}
    for i in range(2000):
        tr = {"method": ["GET", "POST"][i % 2], "path": "/api/x" if i % 3 else "/pay",
              "status": 500 if i == 7 else 200, "phone": "13812345678",
              "auth": f"Bearer tok{i}"}
        tags[log_request(tr, buf)] += 1
    print("分层结果:", tags, "| 采样缓冲:", len(buf.buf))
    sample = json.loads(scrub(json.dumps(buf.buf[0])))
    assert sample["phone"] == "138****5678" and sample["auth"].endswith("***")
    print("脱敏落地前生效 ✅")
    assert tags["audit"] > 0 and tags["error"] == 1
```

**追问**：1) 为什么脱敏要在中间件统一做？——分散在各 handler 里必然有遗漏（新增接口忘调），且正则规则要集中维护与审计；统一管道还能对规则本身加测试。2) tail sampling 的成本？——缓冲区内存与延迟（trace 完整后才能判定），高流量下 buffer 溢出策略要先保错误；这是用内存换「错误个案不丢」。3) 审计线日志怎么防篡改？——只追加存储 + 哈希链锚点（每条含前一条哈希），删改即断链（审计轨迹不可篡改的经典做法）。

## 背诵要点
1. 双线分层：审计线（写/鉴权/资金）全量不可采，观测线（成功 GET）1-10% 采样。
2. 错误日志按比例采必丢个案：tail-based sampling（trace 缓冲后按结局判定）是正解。
3. 脱敏在写入前中间件统一做——落地后进管道/备份就晚了。

## 复盘追问
1. 采样后延迟分布还准吗？（提示：低比例采样下分位数置信区间变宽，P99 估计要靠 metric 直方图而非日志采样）
2. 合规审计要求「保留 180 天且不可改」，存储怎么选？（提示：对象存储 WORM + 哈希链 + 冷热分层成本）
