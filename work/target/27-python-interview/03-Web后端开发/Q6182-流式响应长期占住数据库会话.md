### Q6182 · 流式响应长期占住数据库会话：连接池被导出接口吃干

难度：P7 ｜ 标签：FastAPI、StreamingResponse、yield 依赖、连接池、teardown 时机

**问**：CSV 导出改成 `StreamingResponse` 之后，导出本身没报错，但高峰期**所有接口**开始 504、日志里满是 "connection pool timeout"。导出接口明明是慢在"慢慢吐数据"，为什么会让无关接口拿不到连接？依赖里的 `yield` 会话是什么时候归还的？

**答**：
结论：FastAPI 的 `yield` 依赖由 `AsyncExitStack` 管理，而 exit stack 的退出发生在**响应完全发送之后**。也就是说，一个流 60 秒，注入的 DB session/连接就跟着占 60 秒。池大小 3、9 个并发导出 → 其余请求全部排队等连接（实测等待 216 次、总耗时 803ms；改成"取完就还"后 0 次等待、257ms）。慢的不是 SQL，是"持有连接的时间"。

取舍：三条路。a) 导出接口不把会话放进跨整个流的依赖里：分页取数、每页一个短会话（`async with` 包住一次查询）；b) 导出改成异步任务：写对象存储，前端轮询/下载，接口只负责提交；c) 加大池——把问题推给数据库（连接数上限、内存、vacuum），并发再涨还是等。推荐 a 起步、量大了走 b。

实战：事故形态是"导出功能上线一周没事，月底报表高峰全站 504，重启恢复；DB 侧看连接数打满但没有慢查询"。判断信号：DB 连接数等于池上限、`pg_stat_activity` 里有一批 `idle in transaction`、应用侧 pool timeout 而不是 query timeout。下面用信号量模拟池，对比"流期间持有"与"取完即还"两种写法的等待次数与总耗时。

```python
import asyncio
import contextlib

POOL_SIZE = 3
in_use = 0
peak = 0
waiting = 0


@contextlib.asynccontextmanager
async def acquire_session():
    global in_use, peak, waiting
    while in_use >= POOL_SIZE:
        waiting += 1
        await asyncio.sleep(0.01)     # 简化：轮询等连接
    in_use += 1
    peak = max(peak, in_use)
    try:
        yield "session"
    finally:
        in_use -= 1


async def stream_handler(i):
    # 依赖（yield）的清理发生在响应流结束之后 -> 整个流期间都占着连接
    async with acquire_session():
        for _ in range(5):
            await asyncio.sleep(0.05)
        return f"stream-{i} done"


async def early_release_handler(i):
    # 先取完数据、立刻归还连接，再慢慢吐 body
    async with acquire_session():
        rows = list(range(5))
    for _ in rows:
        await asyncio.sleep(0.05)
    return f"export-{i} done"


async def run(handler, label):
    global in_use, peak, waiting
    in_use = peak = waiting = 0
    t0 = asyncio.get_running_loop().time()
    await asyncio.gather(*(handler(i) for i in range(9)))
    cost = asyncio.get_running_loop().time() - t0
    print(f"[{label}] 9 个并发流、池大小 {POOL_SIZE}: 峰值占用 {peak}, 等待次数 {waiting}, 总耗时 {cost*1000:.0f}ms")


async def main():
    await run(stream_handler, "流式响应持有会话")
    await run(early_release_handler, "取完就归还")


asyncio.run(main())
```

**追问一**：为什么"加大 pool_size"通常不是解法？—— 连接是数据库侧稀缺资源：PG 每个连接一个进程（内存、上下文切换），MySQL 有 max_connections 硬上限。池调大只是把排队从应用挪到数据库，同时放大"长事务"的危害（blocking vacuum、锁等待、复制延迟）。真正的指标是"连接持有时间"，不是"连接数"。

**追问二**：客户端中途断开，会话会提前归还吗？—— 会提前，但依赖"取消能传进去"：流被取消时响应协程退出、exit stack 关闭，`async with` 的 finally 执行。前提是流生成器正确响应 `CancelledError`、且没有把工作丢给自建的后台 task（那些不会被自动取消，连接可能继续被用）。所以导出这类长流要显式处理断开（周期检查 `request.is_disconnected()`）。

## 背诵要点
- `yield` 依赖的 teardown 在响应**完全发送后**执行：流式响应期间会话/连接一直被占（实测 9 并发、池 3 → 216 次等待）。
- 正解：分页取数、每页一个短会话；量大改异步任务 + 对象存储。加大池只是把压力推给 DB。
- 判断信号：pool timeout、`idle in transaction`、无慢查询但连接打满。

## 复盘追问
- 导出接口拖垮全站 504，如何用 teardown 时机解释并重构？（exit stack 在响应后、短会话分页）
- 客户端断开后连接何时释放？自建后台任务为什么危险？（取消传播、显式断连检查）
