### Q6245 · 动态 SQL 的拼接边界：白名单标识符与参数化值的分工

难度：P6 ｜ 标签：SQL 注入、参数化查询、白名单标识符、占位符、动态排序、动态列、driver 参数化边界、转义误区

**问**：为什么"参数化查询能防注入"是**部分正确**的说法——占位符不能出现在哪些位置（表名/列名/ORDER BY）？动态排序、动态列、动态 IN 列表三类场景的安全实现分别是什么？"自己转义再拼接"为什么是负优化？ORM 的 raw SQL 通道怎么守住同样边界？

**答**：
结论：SQL 注入的根因是**数据被解释为代码**——把用户输入与 SQL 文本拼接，输入里的引号/注释符改变语句结构。参数化（占位符 `?`/`%s`）防注入的机制是**值与结构分离**：驱动把参数作为纯数据传给 DB（服务端预编译/转义），参数永不进入语句结构解析。但占位符**只能出现在"值"的位置**——表名、列名、ORDER BY 方向、关键字（ASC/DESC）、子句结构（LIMIT 数字在部分驱动可参数化，部分不行）都不能用占位符，因为这些位置驱动只做文本替换不做值转义（`ORDER BY ?` 会变成按常量字符串排序，语义就错了）。这些位置的安全实现是**白名单标识符**：①**动态列/排序字段**——用户给的列名必须命中代码内维护的白名单集合（`{"created_at", "price"}`），方向必须 ∈ {ASC, DESC}——命中才做 f-string 拼接，未命中直接 4xx（Q2165 的排序白名单是本考点的一个角落，这里是完整机制）；②**动态 IN 列表**——占位符数量动态生成（`"?, " * n` 拼占位符本身，值仍走参数），**绝不拼值**；③**动态表名**（分表路由）——表名来自路由函数的输出而非用户输入，且用正则/白名单双重校验。**手工转义是负优化**：`value.replace("'", "''")` 这类自我转义要跟上各驱动的引号语义（反斜杠转义、编码注入如 GBK 宽字节），任何一条遗漏即绕过——**转义是驱动与 DB 的工作，应用层只做白名单与参数化**。ORM 通道：Django `extra()/raw()`、SQLAlchemy `text()` 同样要守边界——`text("... ORDER BY " + col)` 在 ORM 里照样注入，ORM 只是让拼接更隐蔽。

取舍：a) 白名单维护成本：列名白名单要随 schema 演进同步（新列没加白名单 = 功能不可用），治理形态是把白名单做成"按资源类型注册的映射"（registry 模式，启动期从 schema 校验白名单合法性——白名单里的列必须真实存在，防拼写错误与过期白名单）；b) 排序需求升级：多级排序/复杂表达式（`NULLS LAST`、函数排序）时白名单粒度从"列名"升到"排序子句模板"（预定义合法模板 + 参数化值）——粒度越细白名单越难维护，模板化是平衡点；c) LIMIT/OFFSET：强制 int() 转换比白名单更直接（数字只有唯一解释），负数/超大值靠业务校验（Q1353）；d) 动态表名（分表）：白名单 = 分片路由函数的输出域 + `^[a-z0-9_]+$` 双重校验，路由函数本身不接受用户原始输入；e) 报错面：白名单拒绝时统一 400 并记录（未命中样本是攻击探测信号，进风控计数），**绝不把"不合法列名"回显给用户**（信息泄露）。

实战：事故形态是"报表模块为了灵活排序，`ORDER BY {sort}` 直接 f-string 拼接用户参数——安全审计用 `?sort=id;DROP TABLE report;--` 的渗透测试直接命中（DB 账号有多语句权限）。修复：排序/列名白名单 + 方向枚举 + LIMIT 强转 int + DB 账号最小权限（业务账号收回 DDL/多语句），CI 加'用户输入出现在 SQL 字符串字面量中'的静态扫描"。下面用 sqlite3 实测三类动态场景的安全实现与注入尝试的拦截。

```python
# 动态 SQL 的安全边界: 白名单标识符 + 参数化值
import re
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE t_order (id INTEGER PRIMARY KEY, amount REAL, status TEXT, created_at TEXT)")
conn.executemany("INSERT INTO t_order VALUES (?,?,?,?)",
                 [(1, 99.0, "paid", "2026-01-01"), (2, 45.5, "refunded", "2026-01-02"),
                  (3, 120.0, "paid", "2026-01-03")])

print("[1] 占位符的边界: 值可以参数化, 标识符/方向不可以")
# 排序方向: 白名单枚举; 列名: 白名单集合; 值: 占位符
ALLOWED_COLS = {"amount", "created_at", "id"}          # 列名白名单 (registry 维护)
ALLOWED_DIR = {"ASC", "DESC"}                          # 方向枚举

def list_orders(sort_col: str, sort_dir: str, min_amount: float):
    if sort_col not in ALLOWED_COLS:
        raise ValueError(f"illegal sort column: {sort_col!r}")
    if sort_dir not in ALLOWED_DIR:
        raise ValueError(f"illegal direction: {sort_dir!r}")
    sql = (f"SELECT id, {sort_col} FROM t_order "       # 白名单命中才进 f-string
           "WHERE amount >= ? "                          # 值永远走占位符
           f"ORDER BY {sort_col} {sort_dir}, id ASC")    # 固定二级排序防分页不稳 (Q6185)
    return conn.execute(sql, (min_amount,)).fetchall()  # 参数值与结构分离

print("    合法排序:", list_orders("amount", "DESC", 0))
try:
    list_orders("amount; DROP TABLE t_order;--", "ASC", 0)
except ValueError as e:
    print("    注入尝试被白名单拦截:", e)
try:
    list_orders("(SELECT 1)", "ASC", 0)
except ValueError as e:
    print("    子查询注入拦截:", e)

print("[2] 动态 IN 列表: 占位符数量动态生成, 值仍走参数")
ids = [1, 3]
marks = ", ".join("?" * len(ids))                        # 只拼 '?', 不拼值
rows = conn.execute(f"SELECT id, amount FROM t_order WHERE id IN ({marks})", ids).fetchall()
print("    IN ({}) 参数化查询:".format(marks), rows)

print("[3] 动态表名 (分片路由): 白名单 = 路由函数输出域 + 严格正则")
TABLE_RE = re.compile(r"^t_order_[0-9]{2}$")             # 分表名形如 t_order_00..t_order_63
conn.execute("CREATE TABLE t_order_07 AS SELECT * FROM t_order")

def query_shard(shard: str):
    if not TABLE_RE.match(shard):                        # 双重校验: 格式 + 路由域
        raise ValueError("illegal shard table name")
    return conn.execute(f"SELECT count(*) FROM {shard}").fetchone()[0]

print("    分表 t_order_07 行数:", query_shard("t_order_07"))
try:
    query_shard("t_order; DROP TABLE t_order;--")
except ValueError as e:
    print("    分表名注入拦截:", e)

print("[4] 负优化对照: 手工转义再拼接的失效形态")
user_input = "paid' OR '1'='1"
escaped = user_input.replace("'", "''")                  # naive 转义
bad_sql = f"SELECT * FROM t_order WHERE status = '{escaped}'"
print("    naive 转义拼出的 SQL:", bad_sql, "-> 行数:", conn.execute(bad_sql).fetchall().__len__(),
      "(碰巧防住简单场景, 但 GBK 宽字节/反斜杠转义等变体必绕)")
print("[rule ] 值=占位符; 标识符=白名单; 表名=路由域+正则; 转义交给驱动, 应用层只做白名单与参数化")
```

**追问一**：GBK 宽字节注入是怎么绕过"转义后拼接"的？为什么参数化天然免疫这类编码级绕过？—— 机制：应用层把输入的 `0xbf27`（GBK 下是一个合法双字节字符的截断形态）按字节转义 `'`（0x27）成 `\'`（0x5c 0x27），**如果驱动/连接层用 GBK 编码发往 MySQL**，`0xbf 0x5c` 在 GBK 里被重新解释为一个合法的宽字节汉字——**反斜杠被"吃进"宽字节里**，后半的 0x27 就成了裸引号，注入复活。这类绕过的本质：转义发生在**字节流**上，而"引号边界"的解释发生在**解码后的字符流**上，两次解释的编码不一致就产生缝隙。参数化免疫的原理：占位符协议里参数作为**独立的数据包**传输（binary protocol / separate bind variables），值根本不进入语句文本——不存在"转义拼接"这个环节，编码缝隙无从产生。工程纪律的升级版：①参数化是唯一防线（转义拼接禁入业务代码）；②连接编码显式统一（UTF-8MB4 全链路，Q6249 的字符集治理）；③DB 账号最小权限（注入成功的伤害上限）+ 禁多语句执行——三层把"万一注入"的爆炸半径压到最小。

**追问二**：ORM 的 raw SQL 通道（Django raw/extra、SQLAlchemy text()）怎么守住同等边界？为什么说 ORM 让注入"更隐蔽"？—— 隐蔽性机制：ORM 的查询构造器（filter/order_by）内部做了参数化与白名单，团队形成"ORM=安全"的肌肉记忆后，raw 通道的字符串拼接**没有任何提示地**混进业务代码——code review 里一段 `text("... WHERE status = '" + s + "'")` 比 PHP 时代的裸拼接更难被肉眼捕获（它嵌在 ORM 的调用链里，看起来"还是 ORM"）。守边界的工程化：①**模板校验**——SQLAlchemy 的 `text()` 支持命名绑定参数（`:status`），团队 lint 规则禁止 text() 里出现字符串拼接（AST 扫描 f-string/%/+ 进 text 参数即 CI 失败）；②**排序/列名白名单下沉到 ORM 层**——Django 的 `order_by` 只接受模型字段名（引擎层白名单），raw 查询里的动态部分复用同一份白名单 registry；③**审计用例**——CI 里放"注入样本集"（引号/注释/子查询/宽字节字节串）跑过所有 raw 通道断言全拒；④**最小权限账户**——ORM 连接账号与运维账号分离，raw 通道的事故半径由账号权限封顶。原则：ORM 提供的是"默认安全"，raw 通道是"回到裸奔"——进入 raw 通道的那一刻，本卡的完整边界纪律（白名单+参数化+校验）必须重新生效。

## 背诵要点
- 参数化防注入的机制=值与结构分离（占位符只出现在"值"位置）；表名/列名/ORDER BY 方向等标识符位置不能参数化——安全实现是白名单命中才拼接。
- 三类动态场景：动态列/排序=白名单集合+方向枚举、动态 IN=占位符数量生成（`"?"*n`）值走参数、动态表名=路由域+正则双校验；手工转义是负优化（GBK 宽字节等编码绕过必中）。
- ORM raw 通道（raw/extra/text()）同样要守边界：AST lint 禁拼接、白名单 registry 下沉、注入样本 CI、最小权限账号封顶爆炸半径。

## 复盘追问
- 为什么 ORDER BY ? 不能防注入、白名单怎么实现？（占位符只做值绑定不进结构解析，ORDER BY ? 变成常量排序；列名命中白名单集合、方向枚举后拼接，值仍走占位符）
- 手工转义拼接为什么必被绕过？（转义在字节流、引号边界在解码后字符流，编码不一致产生缝隙如 GBK 宽字节吃反斜杠；参数化无拼接环节故天然免疫）
