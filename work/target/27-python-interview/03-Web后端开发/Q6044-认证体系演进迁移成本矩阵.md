### Q6044 · 认证体系演进：session → JWT → OIDC → Passkey 的迁移成本矩阵

> 难度:★★★★ | 标签:认证, 版本演进, JWT, session, Passkey

**问**：一个十年老系统要评估认证体系从"自管 session + cookie"演进到"OIDC 对接 IdP + Passkey 支持"，演进各阶段的真实成本（服务端、客户端、运维、安全面）分别是什么？为什么"全站换 JWT"经常是错误决策？混合并存期怎么设计？

**答**：各阶段成本矩阵（结论先行：**没有一步到位，只有分阶段增量**）：1) **自管 session**：服务端成本 = 存储与会话查询（Q6038 的容量账），优点是可即时吊销；成本大头是跨服务共享会话（sticky/共享存储）。2) **JWT**：把会话状态推出服务端——省了存储与查询，换来**吊销难题**（token 有效期内无法撤销，只能短 TTL + refresh 轮换，Q6009 的双 token 矩阵）与验签 CPU 成本（Q6040，必须缓存公钥）。3) **OIDC/IdP**：把用户生命周期外包，服务端只剩 code 换 token 与 JWKS 验签；成本是运维 IdP 信任（密钥轮换、回调安全）与所有下游改造。4) **Passkey（WebAuthn）**：去掉密码与钓鱼面，服务端加 challenge/attestation 流程（Q6030），成本在**恢复路径**（设备丢失的降级通道）与老客户端兼容。"全站换 JWT"的典型错误：把"需要即时踢人下线"的会话也换成无状态 JWT，吊销只能靠黑名单——等于用 JWT 重建了 session 存储，两头成本都付。并存期设计：**网关统一验签/会话层**，旧 session 与新 token 在网关归一成内部身份；按流量分批迁移（先 API 后 Web、先新端后老端），旧通道保留读兼容与明确的下线时间表；每阶段定义回滚开关。

```python
# file: code/03-Web后端开发/q6044_auth_evolution.py
import hashlib
import hmac
import json
import secrets
import time
import base64
import sys

print("python:", sys.version_info[:3])

SECRET = secrets.token_bytes(32)

# 1) JWT 形态的成本核心: HMAC 验签(演示, 生产用 RS256+公钥缓存)
def b64u(b): return base64.urlsafe_b64encode(b).rstrip(b"=")
def sign_token(payload, ttl=300):
    header = {"alg": "HS256", "typ": "JWT"}
    body = {**payload, "exp": int(time.time()) + ttl}
    h, p = b64u(json.dumps(header).encode()), b64u(json.dumps(body).encode())
    sig = hmac.new(SECRET, h + b"." + p, hashlib.sha256).digest()
    return (h + b"." + p + b"." + b64u(sig)).decode()

def verify_token(token):
    h, p, s = token.split(".")
    expect = hmac.new(SECRET, (h + "." + p).encode(), hashlib.sha256).digest()
    if not hmac.compare_digest(base64.urlsafe_b64decode(s + "=" * (-len(s) % 4)), expect):
        raise ValueError("签名不符")
    body = json.loads(base64.urlsafe_b64decode(p + "=" * (-len(p) % 4)))
    if body["exp"] < time.time():
        raise ValueError("已过期(吊销难题: 只能等 TTL)")
    return body

tok = sign_token({"sub": "u1"})
t0 = time.perf_counter()
for _ in range(10_000):
    verify_token(tok)
print(f"HMAC 验签 1 万次: {(time.perf_counter()-t0)*1000:.0f} ms (每请求成本基线)")

# 2) 混合并存: 网关层把两种凭证归一成内部身份
SESSIONS = {"sess-abc": {"sub": "u1", "via": "session"}}      # 旧通道: 服务端可吊销
def resolve(credential):
    if credential.startswith("sess-"):
        return SESSIONS.get(credential)                        # O(1) 且可即时踢人
    if credential.count(".") == 2:
        return {**verify_token(credential), "via": "jwt"}      # 无状态
    return None

print("session 归一:", resolve("sess-abc"))
print("jwt 归一:", {k: resolve(tok)[k] for k in ("sub", "via")})

# 3) 吊销语义对照: session 即时, jwt 只能短 TTL + 轮换
SESSIONS.pop("sess-abc")                                        # 立即生效
print("session 吊销后:", resolve("sess-abc"))
print("jwt 吊销只能靠短 TTL(如 5min) + refresh 轮换, 黑名单=重建 session 存储")
```

**追问**：1) 为什么 OIDC 迁移后"会话"并没有消失而是换了层？——IdP 侧仍有会话与 SSO 状态，你的服务换成 token 验证；理解这点才能设计"IdP 登出 ≠ 本地会话登出"的前端登出同步。2) Passkey 迁移最大的组织成本是什么？——不是技术（challenge/attestation 有成熟库）而是**恢复流程**与客服体系（设备丢失不能靠密码兜底），必须在切换前定义降级通道的信任级别。3) 迁移期"双读"如何防降权攻击？——两种凭证的授权判定统一走同一套权限模型（scope/角色归一），禁止旧通道走更宽的默认权限。

## 背诵要点
- 演进阶梯 session→JWT→OIDC→Passkey：每步是存储/吊销/运维成本的转移，不是消除。
- 需要"即时踢人"就保留服务端会话；JWT 吊销=短 TTL+refresh 轮换，黑名单等于重建 session。
- 并存期：网关归一内部身份 + 分批迁移 + 每阶段回滚开关；两种凭证共用同一权限模型。
