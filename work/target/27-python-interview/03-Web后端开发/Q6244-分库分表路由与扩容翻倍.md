### Q6244 · 分库分表路由策略：分片键选型、扩容翻倍与双写下线

难度：P6 ｜ 标签：分库分表、分片键、哈希取模、范围分片、扩容迁移、双写切换、路由表、基因法、数据倾斜

**问**：什么时候才真的需要分库分表——单表多大才算"必须拆"？分片键怎么选（哈希取模/范围/查找表/基因法）各自的倾斜与跨片查询代价？"哈希取模扩容要迁移一半数据"的账怎么算，扩容翻倍的迁移与双写下线流程是什么？查询不带分片键时的广播代价怎么治理？

**答**：
结论：分库分表是**最后手段**（索引优化 → 读写分离 Q6067 → 归档冷热 Q6068 → 缓存 → 分片），触发线通常是"单表 2000 万行级 + B+ 树层高增长 + 单机容量/写入瓶颈叠加"，且一旦分片**回不去了**。分片键选型四路：①**哈希取模**（`hash(uid) % N`）——分布最均匀、实现最简单；代价：**扩容必须迁移**（N→N+1 时约 N/(N+1) 的数据要动，翻倍是 50%）、取模簇在模数不均匀时倾斜；②**范围分片**（按时间/id 区间）——扩容加新区间零迁移、范围查询友好；代价：**热点倾斜**（新数据全写最新分片，写集中）；③**查找表/基因法**——路由表显式映射（可自由迁移、扩容只改表）或"分片基因嵌入 ID"（Q6240 的雪花机器位即基因法的特例：uid 的 hash 片段编码进订单 ID，任意关联记录天然带路由信息，免二次路由查询）；④**一致性哈希**（Q1341）——扩容只迁 1/N，但实现复杂、范围查询差，DB 分片少用（缓存分片常用）。**扩容翻倍流程**（N→2N 的标准作业）：`双写阶段（新旧分片同时写，以旧为准）→ 历史数据迁移（后台按 hash 重分布，校验行数/checksum）→ 灰度读切换（按用户比例走新分片，读失败回退旧分片）→ 全量切读 → 停旧写下线`——每一步可回滚，全程旧分片保底；迁移期间的路由规则"**新数据看新表，旧数据双查兜底**"（写已双写、读旧表 miss 再查新表）。

取舍：a) 分片键业务耦合是最大代价：**所有查询必须带分片键**——运营后台"按手机号查订单"这类不带 uid 的查询要么广播全部分片（N 次查询合并，延迟=最慢分片），要么冗余索引（手机号→uid 的全局映射表）——分片键决策先审计 TOP 查询模式再定；b) 分片数预留：一次到位选"当前 10 倍容量"的分片数（如现在 2 分片撑得住但建 16 个逻辑片映射到 2 个物理库）——**逻辑分片与物理库分离**（路由表管映射），扩容只是把逻辑片搬家，应用层路由规则不变，这是"免翻倍迁移"的主流解（Vitess/TiDB 的机制内核）；c) 事务边界：分片后跨片事务没了本地 ACID——同 uid 的数据尽量落同片（基因法），跨片业务用最终一致（Q5503 部分失败补偿）；d) 自增主键：分片后全局唯一靠雪花（Q6240），各片独立自增会撞号；e) 广播查询治理：BI/运营类低频查询允许广播（读副本），C 端热路径严禁广播——审计清单里给每个查询标"带/不带分片键"。

实战：事故形态是"订单表 8000 万行，按 `uid % 8` 分 8 片后运营报表查询（不带 uid）把 8 片全广播，高峰 DB CPU 95%；同时扩容时直接改取模数上线——一半订单'消失'（路由到了还没迁移数据的分片）。修复：扩容按四阶段双写流程重做（校验 checksum 后才切读）；报表查询迁到读副本的聚合层；热门'手机号查订单'加全局映射表；路由规则做成配置中心下发的版本化映射（逻辑分片→物理库），扩容=搬家不再改应用代码"。下面实测取模翻倍的迁移率账与双写切换的路由兜底。

```python
# 分库分表: 取模路由、扩容翻倍迁移率与双写切换兜底
import hashlib

def route(key: str, n: int) -> int:
    """哈希取模路由 (教学: md5 避免内建 hash 的 PYTHONHASHSEED 随机化)"""
    return int(hashlib.md5(key.encode()).hexdigest(), 16) % n

print("[1] 取模分片: 分布均匀性实测")
N = 8
keys = [f"user-{i}" for i in range(80000)]
dist = [0] * N
for k in keys:
    dist[route(k, N)] += 1
print("    8 分片分布:", dist, "(max/min =", max(dist) / min(dist), "-> 哈希分片天然均匀)")

print("[2] 扩容翻倍的迁移率: 8 -> 16, 只有半数数据要搬家")
moved = sum(1 for k in keys if route(k, 16) != route(k, 8))
# 新分片 h%16 落在新半区 (8..15) 的 key 必须物理搬家; 落在旧半区的 key 才算原地保留
print(f"    8->16 迁移率: {moved / len(keys):.0%} (取模扩容的固有代价; 逻辑分片映射可免)")

print("[3] 双写切换期路由: 旧表为准 + 新表兜底, 切读后回退安全")
class Router:
    """迁移窗口期路由: 写双写, 读旧表 miss 再查新表 ( checksum 通过前旧表保底)"""

    def __init__(self, old_n: int, new_n: int, migrated: set) -> None:
        self.old_n, self.new_n = old_n, new_n
        self.old_data: dict = {}
        self.new_data: dict = {}
        self.migrated = migrated             # 已完成历史迁移的 key 集合 (教学替身)

    def write(self, key: str, value: str) -> None:
        self.old_data[key] = value           # 阶段一: 双写, 以旧为准
        self.new_data[key] = value

    def read(self, key: str) -> str:
        if key in self.old_data:             # 读旧表 (迁移期旧数据最全)
            return self.old_data[key]
        if key in self.new_data:             # 旧表 miss -> 新表兜底 (防漏迁)
            return self.new_data[key]
        return "NOT_FOUND"

    def migrate(self, key: str) -> None:     # 后台迁移作业: 校验后标记
        if key in self.old_data:
            self.migrated.add(key)

r = Router(2, 4, set())
for i in range(6):
    r.write(f"order-{i}", f"v{i}")
r.old_data.pop("order-3")                    # 模拟: order-3 只在新表 (漏迁/双写窗口边界)
r.migrate("order-0")
print("    读旧表命中:", r.read("order-0"), "| 旧 miss 新兜底:", r.read("order-3"),
      "| 旧 miss 新也 miss:", r.read("order-99"))

print("[4] 跨片广播的代价: 不带分片键 = N 次查询合并, 延迟=最慢分片")
print("    治理: 全局映射表(手机号->uid) / 基因法(id 内嵌分片键) / 报表走读副本聚合")
print("[rule ] 分片是回不去的最后手段; 逻辑分片+路由表让扩容变搬家; 切换四阶段每步可回滚")
```

**追问一**："逻辑分片 + 路由表"为什么能免掉翻倍迁移？它的运维成本与失效场景是什么？—— 机制：应用层路由规则是"**逻辑片 → 物理库**"的映射表（如 1024 个逻辑片映射到当前 2 个库：各 512 片），扩容只是把一部分逻辑片"搬家"到新库——路由表更新后新查询直达，**历史数据的物理搬迁**仍在（数据在新库要能查到），但可以**按逻辑片粒度后台慢慢迁**（每个逻辑片独立搬、独立校验、独立切流量），不再有"全量翻倍窗口期"；而且分片数永不改变（1024 逻辑片不变），应用代码与取模规则**永远不用改**——这就是 Vitess/sharding-proxy 类中间件的标准形态。运维成本：①路由表成为关键配置（配置中心下发、版本化、灰度生效——Q1381 的双写切换开关同构）；②数据搬迁作业（每个逻辑片：停写该片→拷贝→校验→切路由→恢复写，或用双写+切读的两阶段）；③映射倾斜监控（某逻辑片数据量异常增长）。失效场景：路由表丢失/回滚错误 = 查询打到错误库（读到空/错数据）——**路由表的变更必须与数据搬迁的完成状态强绑定**（搬迁未完成的片不许切路由），校验手段是行数+checksum 双闸。

**追问二**：基因法（把分片键的 hash 片段编码进实体 ID）具体怎么操作？它解决了什么、又引入了什么新约束？—— 操作：生成订单 ID 时取 `uid_hash 的低 N 位`作为"基因"嵌入 ID 的保留位段（如 64 位雪花里划出 6 位基因位：基因 64 取值 → 对应 64 个逻辑片的映射关系），之后**任何携带订单 ID 的查询都能直接解出该订单所在分片**——客服后台"按订单号查"、退款流水"按 ID 关联"都不需要先查 uid 再路由。解决的三件事：①关联查询免二次路由（订单→订单详情/物流，ID 自带路由）；②运营单键查询免广播（订单号直查）；③历史归档迁移时数据自描述。新约束：①**ID 格式被分片架构锁死**——ID 一旦包含基因位，分片方案的"逻辑片总数"就与 ID 位宽绑定（64 片上限），未来扩容超上限要换 ID 格式（对外契约，Q6240 的不可回收原则）；②**uid 与订单的分片映射必须恒定**——基因取自 uid hash，若 uid 的路由策略变了，旧基因与新路由不一致（新老数据异构，查询要按"ID 版本"分支）；③**ID 结构公开即暴露路由**——分析 ID 可推断分片拓扑（对外不透明性下降，加密/混淆基因位是缓解）。适用判据：强关联的"主实体-从实体"族（订单族、消息族）收益最大；弱关联/自由查询多的业务慎用——基因省的是路由查询，换来的是 schema 演进自由度。

## 背诵要点
- 分片是回不去的最后手段（优化链：索引→读写分离→冷热归档→缓存→分片）；分片键四路：哈希取模（均匀但扩容迁移 50%）、范围（免迁移但热点）、查找表/基因法（映射解耦）、一致性哈希（1/N 迁移）。
- 扩容标准作业：双写（旧为准）→ 历史迁移（checksum 校验）→ 灰度切读（失败回退）→ 停旧写下线；主流免迁移解 = 逻辑分片+路由表（1024 逻辑片映射物理库，扩容=搬家）。
- 分片键决策先审计 TOP 查询：不带键查询的治理 = 全局映射表/基因法/读副本聚合；跨片事务无 ACID，同 uid 数据同片（基因）+ 最终一致补偿。

## 复盘追问
- 扩容直接改取模数上线为什么会让"一半订单消失"？（路由先变数据未迁：新模数把旧 key 路由到未迁移分片；必须双写四阶段+checksum 后切读）
- 逻辑分片+路由表怎么把扩容变成搬家？（1024 逻辑片→物理库映射，分片数永不改；搬片粒度独立迁移校验切流；路由表与搬迁状态强绑定防打到错库）
