### Q6066 · 缓存击穿与单飞请求合并

> 难度:★★★★ | 标签:事故复盘, 缓存击穿, singleflight, 进程内合并

**问**：热点商品缓存过期的一瞬间，数据库 QPS 从 200 跳到 3 万被打挂（缓存击穿）。为什么"查 miss 就回源"在热点上会放大几百倍？进程内 singleflight 合并怎么做？分布式锁、逻辑过期、永不过期+异步刷新三条路怎么选？

**答**：击穿机理：单 key 过期瞬间，N 个并发请求同时 miss、同时回源——**放大系数=并发在途数**（Q6063 的 L），热点页 L=1500 时 DB 瞬收 1500 个相同查询；雪崩是"全量 key 同时过期"（放大×key 数）。对比穿透（查不存在的数据绕过缓存，用布隆过滤器/空值缓存）与雪崩（TTL 加随机抖动，见 Q6049 双写卡的语境），击穿专治"单热点 key"。四条解法按部署形态选：a) **进程内 singleflight**：同进程内同 key 的并发请求合并为一次回源（asyncio Future/锁 + inflight dict），零额外依赖、消灭本实例重复，N 个实例仍各回源 1 次（DB 压力=实例数，通常可接受）；b) **分布式锁回源**：Redis SETNX 抢锁，抢到的回源写缓存，未抢到的短暂自旋/返回旧值——DB 压力降到 1，代价是锁服务依赖与失败路径复杂（持锁者崩了要 TTL 释放，Q6060 的 inflight 超时同构）；c) **逻辑过期**：value 里存 expires_at 但物理不过期，读到"逻辑过期"的请求先返回旧值、异步触发刷新——**零阻塞零击穿**，代价是短暂旧数据（价格类场景要先评估容忍度）；d) **后台定时刷新**：热点 key 白名单+定时任务续命，适合可枚举的 Top-N。实现要点：inflight 的清理要在 finally（异常时不能残留，否则后续请求永远等到死 Future）；singleflight 返回的 result 要共享对象或拷贝语义明确（调用方改 dict 污染所有等待者——又是可变共享坑）。

```python
# file: code/03_Web后端开发/q6066_singleflight.py
import asyncio, time, random

cache = {}
db_hits = {"n": 0}

async def db_query(key):
    db_hits["n"] += 1
    await asyncio.sleep(0.05)      # DB 查询 50ms
    return {"price": 199, "key": key}

# 1) 无保护: 并发全 miss -> DB 被并发数放大
async def unprotected(key):
    if key not in cache:
        cache[key] = await db_query(key)
    return cache[key]

# 2) 进程内 singleflight: inflight dict + Future 合并
inflight: dict[str, asyncio.Future] = {}
sf_lock = asyncio.Lock()

async def singleflight(key):
    async with sf_lock:
        if key in cache:
            return cache[key]
        if key in inflight:                       # 已有回源在飞: 挂到同一 Future
            fut = inflight[key]
        else:
            fut = asyncio.ensure_future(db_query(key))
            inflight[key] = fut
    try:
        val = await fut
    except Exception:
        if key in inflight and inflight[key] is fut:
            inflight.pop(key, None)               # 失败清理, 不残留死 Future
        raise
    async with sf_lock:
        cache[key] = val
        inflight.pop(key, None)
    return val

async def burst(handler, key="hot-sku", n=500):
    return await asyncio.gather(*[handler(key) for _ in range(n)])

async def main():
    await burst(unprotected)
    print("无保护: 500 并发 miss -> DB 查询", db_hits["n"], "次 (放大=并发在途)")

    db_hits["n"] = 0; cache.clear()
    vals = await burst(singleflight)
    print("singleflight: DB 查询", db_hits["n"], "次 (合并为 1)")

    # 3) 逻辑过期: 物理不过期, 读到逻辑过期返回旧值并异步刷新 (零阻塞)
    async def logical_expire(key):
        entry = cache.get(key)
        if entry is None:                          # 首次: 真回源 (可再配 singleflight)
            v = await db_query(key)
            cache[key] = {"v": v, "exp": time.monotonic() + 10}
            return v
        if time.monotonic() > entry["exp"]:        # 逻辑过期: 立即返回旧值
            asyncio.create_task(refresh(key))      # 异步刷新, 不等待
        return entry["v"]

    async def refresh(key):
        v = await db_query(key)
        cache[key] = {"v": v, "exp": time.monotonic() + 10}

    db_hits["n"] = 0; cache.clear()
    vals = await burst(logical_expire)
    print("逻辑过期: 首请求真回源", db_hits["n"], "次, 其余读旧值零击穿")
    print("注意: 并发下首窗口会多次回源, 生产将逻辑过期与 singleflight 叠加使用")

asyncio.run(main())
print("选型: 进程内 singleflight(默认) / 分布式锁(DB=1,复杂) / 逻辑过期(容忍旧值) / Top-N 定时续命")
print("搭配: TTL 加随机抖动防雪崩 + 空值缓存/布隆防穿透, 三问题各配各药")
```

**追问**：1) singleflight 的共享 result 有什么坑？——所有等待者拿到同一个对象引用，任何调用方原地修改（`val["price"]=0`）污染所有等待者与缓存；要么缓存前深拷贝、要么返回不可变对象（frozen dataclass，见 Q5070）、要么文档明确"只读"；这与 Q5061 迭代变异、Q5561 ContextVar 存可变对象同属"共享可变状态"家族。2) 分布式锁方案的"锁 TTL 与回源时长"怎么配？——锁 TTL 要 > 回源 P99×2（慢查询被锁窗口放大时别人不能抢），持锁者用看门狗续期（Redisson 思路）或锁内分片推进；回源失败必须释放锁否则 key 击穿变成 key 永久锁死——失败路径测试是这方案的验收重点。3) 怎么提前发现"将击穿"的热 key？——缓存访问日志聚合 Top-N（按 miss+回源次数），接入自动续命；热点探测（客户端计数上报 Redis，抖音式方案）用在超大规模；至少要给 DB 侧"单 SQL QPS 突增"告警——击穿在 DB 视角是"同一 SQL 瞬时并发"。

## 背诵要点
- 击穿=单热点 key 过期瞬间放大系数=并发在途数 L；穿透=查不存在（布隆/空值缓存）；雪崩=同时过期（TTL 抖动），三问题各配各药。
- singleflight：inflight dict+Future 合并同实例并发，失败路径 finally 清理防死 Future；共享 result 是同一引用，须不可变或拷贝。
- 逻辑过期零阻塞但容忍旧值；分布式锁 DB=1 但失败路径复杂（TTL>回源 P99×2）；热点 Top-N 定时续命。
