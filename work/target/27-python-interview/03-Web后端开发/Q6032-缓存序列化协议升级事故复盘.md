### Q6032 · 缓存序列化协议升级：旧缓存反序列化崩溃事故复盘

> 难度:★★★★ | 标签:事故复盘, 缓存, 序列化兼容, 版本演进

**问**：把缓存值从 pickle 换成 JSON（或加 schema 字段）发布后，一批请求 500 了——为什么缓存是"最容易被忽略兼容性的存储"？灰度期间的混合缓存怎么处理？安全的协议升级协议怎么设计？

**答**：事故链：缓存是**唯一不随代码一起发布的存储**——DB 有迁移工具、消息有 schema registry，缓存却散落在各 Redis key 里、TTL 数小时到数天，新代码读到旧格式（或旧代码读到新格式）立刻崩。三类典型爆点：1) pickle→JSON 切换：旧值 bytes 直接 `json.loads` 抛错，或旧代码 `pickle.loads` 解到 JSON 文本抛 ValueError；2) 结构演化：字段增删/嵌套结构变化，新代码 `d["new_key"]` KeyError；3) 类型漂移：int/float、list/tuple 差异在严格校验层（Pydantic strict）炸出。升级协议设计：**信封模式（envelope）**——缓存值永远是 `{"v": 协议版本, "t": 类型, "d": 数据}`，读路径按 v 分派解析器，未知版本走"剔除+回源"降级而非报错；写路径只写最新版本。灰度期混合处理三规则：a) **读旧写新**——解析器带旧版本兼容层，写全用新协议，让 TTL 自然滚掉旧值；b) **无法兼容的破坏性变更换 key 前缀**（`v1:` → `v2:`），旧缓存等 TTL 过期或主动 flush 前缀，绝不允许同一 key 双格式；c) **回源熔断**——解析失败率超阈值时旁路缓存直接回源 DB，防崩溃扩散。缓存键本身也要进版本策略：结构变了但语义没变→同 key；语义变了→key 必须带版本（Q5037 的持久化契约同源思想）。

```python
# file: code/03_Web后端开发/q6032_cache_envelope.py
"""缓存信封协议: 版本分派解析 + 旧值兼容 + 崩溃熔断."""
import json
import pickle

class CacheEnvelope:
    def __init__(self, fallback_parse_fail_rate_threshold: float = 0.5):
        self.parse_failures = 0
        self.reads = 0
        self.threshold = fallback_parse_fail_rate_threshold

    # --- 写: 永远最新版本 ---
    @staticmethod
    def dump(payload: dict) -> str:
        return json.dumps({"v": 2, "t": "json", "d": payload})

    # --- 读: 按 v 分派, 未知/损坏 -> 回源信号(None) ---
    def load(self, raw) -> dict | None:
        self.reads += 1
        try:
            if isinstance(raw, (bytes, bytearray)) and raw.startswith(b"\x80"):
                # 旧 pickle 时代遗留: 兼容层解析(v1)
                data = pickle.loads(raw)          # 仅内部缓存可用, 信任域
                self._validate(data)
                return data
            doc = json.loads(raw)
            version = doc.get("v")
            if version == 2:
                self._validate(doc["d"])
                return doc["d"]
            if version == 1:
                return self._migrate_v1(doc["d"])  # 旧结构迁移
            raise ValueError(f"unknown cache version {version!r}")
        except Exception as e:                     # 任何解析失败: 降级回源, 不 500
            self.parse_failures += 1
            print(f"cache parse fail ({type(e).__name__}), -> 回源 DB")
            return None

    def _validate(self, data: dict) -> None:
        if not isinstance(data, dict):
            raise ValueError("payload not dict")

    @staticmethod
    def _migrate_v1(d: dict) -> dict:
        return {"id": d.get("id"), "amount": d.get("price", 0)}  # 旧字段名迁移

    def should_trip(self) -> bool:
        return self.reads > 100 and self.parse_failures / self.reads > self.threshold

# --- 演示: 新代码读三种来源 ---
cache = CacheEnvelope()
print("v2 正常读:", cache.load(cache.dump({"id": "A", "amount": 9})))
legacy_v1 = json.dumps({"v": 1, "t": "json", "d": {"id": "B", "price": 5}})
print("v1 迁移读:", cache.load(legacy_v1))
print("垃圾数据读:", cache.load(b"\x00garbage"), "| 回源兜底生效")
print("熔断器:", cache.should_trip(), f"(失败率 {cache.parse_failures}/{cache.reads})")
```

**追问**：1) 为什么不用"try 解析 JSON 失败再试 pickle"？——双猜测解析掩盖协议边界、性能翻倍且 pickle 对不可信来源有安全面（Q5009/Q5037）；信封的显式版本字段把猜测变成查表。2) 灰度期"新 worker 写 v2、旧 worker 写 v1"并存会怎样？——同 key 双格式，读方必须同时兼容两版（本卡的 v1/v2 分派），这是读旧写新策略的强制要求；v1 兼容层存活期=TTL 上限+灰度时长。3) 换 key 前缀方案的容量账？——切换瞬间缓存命中率归零、DB 回源翻倍，要配预热（Q2191/Q6020）与回源限流（Q6018），否则协议升级演变成 DB 事故。

## 背诵要点
- 缓存是唯一不随代码发布的存储，兼容策略必须独立设计；同 key 双格式是事故之源。
- 信封协议：值= {v,t,d}，读按 v 分派、未知版本降级回源；写永远最新版。
- 破坏性变更换 key 前缀 + TTL 自然滚掉旧值；解析失败率熔断旁路缓存防崩溃扩散。
