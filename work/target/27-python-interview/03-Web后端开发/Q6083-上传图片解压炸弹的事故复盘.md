### Q6083 · 上传图片解压炸弹撑爆 worker 的事故复盘

难度：★★★★☆ ｜ 标签：事故复盘 / 解压炸弹 / 上传安全 / 容量

**问**：一张 3MB 的"图片"让 8 个 worker 全部 OOM。解压炸弹的原理是什么？图片、压缩包、XML 三类炸弹各自怎么防？校验放在哪一步才真正有效？

**答**：
- **结论**：解压炸弹 = 高压缩比数据（重复字节、嵌套压缩），3MB 输入可解出数十 GB 输出。事故链：上传体积限制（3MB）只约束**压缩态**，解压发生在 worker 内存里——PIL 打开 PNG（声明 40000×40000 RGBA ≈ 6.4GB 位图）、zlib 爆解、XML billion laughs（实体展开指数级）三兄弟。防御核心是**在解压前知道解压后的大小**：1）图片：Pillow 设 `Image.MAX_IMAGE_PIXELS`（默认约 1.78 亿像素会抛 DecompressionBombError，但要显式校验头部宽高而非依赖它——默认值太高且可被绕过的格式众多）；2）zlib：用 `decompressobj` 流式解压并**限制输出字节**，超限即停；3）XML：禁用外部实体（`xml.etree` 默认禁，`xml.sax` 要显式关 DTD）。
- **取舍**：校验层次：传输层（大小限制，拦压缩态）→ 头部层（读宽高/声明的解压尺寸，拦声明值）→ 流式层（解压过程限额，拦"头部撒谎"）→ 隔离层（独立转换 worker/沙箱，限制内存 cgroup，兜底）。只用一层都会漏：头部可伪造、流式限额依赖实现、沙箱只是减损。内容类型校验用**魔数**而非 `Content-Type` 头（客户端可随便填）。
- **实战**：复盘要点：1）OOM 后第一件事是看 worker RSS 时间线与当时的上传日志（体积正常但处理时长异常）；2）把解压操作挪到独立进程/容器（配合 Q6087 的 worker 拓扑），主网关永不触碰原始文件解码；3）配额：单用户上传频率 + 全局解压并发上限（信号量）防止并发炸弹叠加。

```python
"""解压炸弹的限额解压与头部校验（标准库 zlib + Pillow 基线 10.x）"""
import zlib, io, sys, struct

# 1) zlib 炸弹：1MB 压缩 → 巨量展开。安全解法：decompressobj 流式限额
bomb = zlib.compress(b"\x00" * 200_000_000, 9)   # 200MB 的零 → 约 200KB
print(f"压缩态大小: {len(bomb)/1024:.0f} KB，解压态 200MB —— 体积限制拦不住")

MAX_OUT = 32 * 1024 * 1024                        # 输出上限 32MB
def safe_inflate(data: bytes, max_out: int) -> bytes:
    d = zlib.decompressobj()
    out = bytearray()
    for chunk in (data[i:i+65536] for i in range(0, len(data), 65536)):
        piece = d.decompress(chunk, max_out - len(out) + 1)   # 单次解压也限额
        out += piece
        if len(out) > max_out:
            raise ValueError(f"解压输出超限 {len(out)} > {max_out}：拦截")
        if d.eof:
            break
    if not d.eof:
        raise ValueError("输入不完整")
    return bytes(out)

try:
    out = safe_inflate(bomb, MAX_OUT)
    print(f"200MB 内 < {MAX_OUT//1e6}MB 限额时才允许解出（本例被拦截预期不同）")
except ValueError as e:
    print("限额拦截:", e)

# 反面：d.decompress 一次性解压才会爆 —— 演示在 32MB 限额下直接读完（数据只有 200MB，可控）
print("对照：直接 zlib.decompress(bomb) 会无上限展开（危险，勿在生产使用）")

# 2) 图片炸弹：头部宽高校验先于解码
def image_head_check(data: bytes, max_pixels=25_000_000):
    """PNG 头解析（标准库，不依赖 Pillow）：IHDR 里读宽高"""
    if data[:8] != b"\x89PNG\r\n\x1a\n":
        raise ValueError("非 PNG（魔数校验，别信 Content-Type）")
    import struct
    w, h = struct.unpack(">II", data[16:24])       # IHDR: 宽高各 4 字节大端
    if w * h > max_pixels:
        raise ValueError(f"声明尺寸 {w}x{h}={w*h} 超限（解码前拦截）")
    return w, h

tiny_png = (b"\x89PNG\r\n\x1a\n" + b"\x00\x00\x00\rIHDR"
            + struct.pack(">II", 1, 1)
            + b"\x08\x02\x00\x00\x00")
print("合法小图头部:", image_head_check(tiny_png))
evil_png = (b"\x89PNG\r\n\x1a\n" + b"\x00\x00\x00\rIHDR"
            + __import__("struct").pack(">II", 40000, 40000) + b"\x08\x02\x00\x00\x00")
try:
    image_head_check(evil_png)                     # 16 亿像素声明，未解码即拦
except ValueError as e:
    print("图片炸弹拦截:", e)

# 3) XML 炸弹：etree 默认禁外部实体，sax 要显式关
import xml.etree.ElementTree as ET
print("etree 默认禁 DTD 实体展开（billion laughs 安全）；xml.sax 需显式 feature_external_ges=False")
print("分层结论：体积限(压缩态) → 头部限(声明值) → 流式限(实际输出) → 隔离(cgroup 减损)")
```

**追问链**
1. Pillow 的 DecompressionBombError 默认阈值是多少？为什么不能只靠它？
   1. 默认 `MAX_IMAGE_PIXELS` ≈ 1.789 亿像素（约 0.25GB RGBA），超过抛异常、超过 2 倍给 warning——但阈值是"够一张大图"的量级，配合多张并发即可打爆；且它只看声明像素，EXIF/mosaic 类混淆格式与第三方解码器不在保护内。
   2. 追问：为什么 WebP/GIF 这类动图更危险？——逐帧解码，总像素 = 帧数 × 尺寸，头部校验单帧尺寸拦不住帧数放大，必须流式按帧计数限额。
2. "解压挪到独立 worker"的架构怎么落地？
   1. 主服务收到上传后只做魔数/大小/头部三层校验，入队后由解压专用 worker（cgroup 内存 limit、低并发度）消费；队列里放对象存储引用而非字节流。价值：OOM 只炸转换实例、可独立扩缩容与限流，主网关 SLA 与解压风险解耦。
   2. 追问：同步接口需要"秒出缩略图"怎么办？——同步路径只做头部级快速校验 + 低限额流式解压（如 ≤4MB 输出），超大图明确走异步 + 轮询/回调，把"快"与"安全"分成两条协议承诺。

## 背诵要点
- 解压炸弹：体积限制只约束压缩态，解压发生在 worker 内存；PNG 声明 40000² ≈ 6.4GB 位图即事故。
- 四层防御：魔数+体积（压缩态）→ 头部宽高（声明值）→ decompressobj 流式输出限额（实际值）→ 独立 worker + cgroup 减损。
- zlib 用 decompressobj 限额；etree 默认禁实体，sax 要显式关；Pillow 默认 1.789 亿像素阈值只是兜底不是防线。
