### Q6074 · 优雅停机的排空窗口与 preStop 宽限期容量推导

> 难度:★★★★ | 标签:容量规划, 优雅停机, K8s, preStop

**问**：滚动发布时总有 0.5% 请求 502/超时，根因常是"pod 被杀时连接没排空"。从 SIGTERM 到进程退出，一个 uvicorn 实例的排空要经过哪几步？`terminationGracePeriodSeconds`、`preStop sleep`、就绪探针摘除时序三者的时间账怎么算？长连接（WebSocket/SSE）与后台任务的排空窗口为什么不同？

**答**：结论：排空窗口 = **摘流量时间 + 在途请求处理时间**，K8s 的时间账必须显式算：pod 收到 SIGTERM 后，**端点摘除（EndpointSlice 更新 + kube-proxy 规则下发）与 SIGTERM 是并发的**，LB/iptables 可能还有几秒把新请求打进正在关闭的 pod——这就是 `preStop: sleep 2-5s` 存在的原因（先等摘除生效再开始自己的关闭逻辑）。完整时序：1) SIGTERM 发出；2) preStop hook 执行（如 sleep 3s + curl 摘健康检查端点）；3) 应用收到 SIGTERM 后：停止 accept（listener 关闭）、**摘就绪探针返回失败**（让 Service 尽快摘端点）、停止后台生产者（定时器/消费者）；4) 等在途请求完成（uvicorn 默认等待现有连接，`--timeout-graceful-shutdown` 控制上限）；5) 宽限期到点 SIGKILL 强杀。容量推导：`排空时间 ≈ 摘除生效延迟(2-5s) + max(在途请求 P99.9, 长连接最大寿命策略) + 后台任务检查点间隔`；`terminationGracePeriodSeconds` 必须 ≥ 排空时间 × 1.5，uvicorn 的 `--timeout-graceful-shutdown` 要小于它 2-3 秒留缓冲。长连接特殊性：WS/SSE（Q6005/Q6054）不能等它自然结束，策略是"停止接收新连接 + 广播 goaway + 客户端带退避重连到其他实例"，窗口按客户端重连风暴上限算（万级客户端 × 退避 1s）；后台任务（Q6027）要可恢复：SIGTERM 时做检查点存盘，重启后从断点续，而不是硬等完成。实战清单：SIGTERM 处理必须幂等可重入（可能收到多次）；应用要能在 500ms 内完成"停止 accept+摘就绪"这一步，超过说明初始化了不可逆资源。

```python
# file: code/03-Web后端开发/q6074_graceful_shutdown.py
import os, signal, time, threading, sys, subprocess
from concurrent.futures import ThreadPoolExecutor

# 1) 时间账模型(可调参数=你们的真实观测值)
T_ENDPOINT_REMOVAL = 3.0      # 端点摘除生效(含 kube-proxy/LB 传播) s
P999_INFLIGHT      = 4.0      # 在途请求 P99.9 s (压测/监控实测)
T_CHECKPOINT       = 1.0      # 后台任务检查点间隔 s
drain = T_ENDPOINT_REMOVAL + P999_INFLIGHT + T_CHECKPOINT
grace = drain * 1.5
print(f"排空时间 ≈ {drain:.1f}s -> terminationGracePeriodSeconds ≈ {grace:.0f}s")
print("uvicorn --timeout-graceful-shutdown 应 ≈ grace - 3s (给 K8s SIGKILL 留缓冲)")

# 2) 真实 SIGTERM 驱动的排空状态机(幂等可重入)
class Server:
    def __init__(self):
        self.accepting = True
        self.ready = True
        self.inflight = 0
        self.stopped = threading.Event()
        self._sig_seen = 0

    def handle_sigterm(self, *_):
        self._sig_seen += 1
        if self._sig_seen > 1:
            print("SIGTERM 重复收到 -> 幂等: 状态机已在排空, 直接返回")
            return
        print("step1: 停止 accept + 就绪探针置 false(摘端点加速)")
        self.accepting = False; self.ready = False
        print("step2: 等待在途请求排空 (模拟 P99.9=4s 压缩为 1s 演示)")
        deadline = time.time() + P999_INFLIGHT
        while self.inflight > 0 and time.time() < deadline:
            time.sleep(0.05)
        print(f"step3: 在途清零(残留 inflight={self.inflight}), 停后台生产者+检查点")
        self.stopped.set()

srv = Server()
pool = ThreadPoolExecutor(max_workers=1)
pool.submit(lambda: (setattr(srv, "inflight", 1), time.sleep(1.0),
                     setattr(srv, "inflight", 0)))

signal.signal(signal.SIGTERM, srv.handle_sigterm)   # 仅主线程可注册
subprocess_run = os.kill(os.getpid(), signal.SIGTERM)
t0 = time.perf_counter()
while not srv.stopped.is_set() and time.perf_counter() - t0 < 5:
    time.sleep(0.05)
print(f"排空完成耗时(演示压缩): {time.perf_counter()-t0:.2f}s")
pool.shutdown(wait=False)

# 3) 长连接策略: 停新连 + goaway 广播 + 客户端退避重连
print("长连接: abort 新连接 -> 广播 goaway -> 客户端退避重连其他实例 (窗口按重连风暴上限算)")
print("后台任务: SIGTERM 做检查点存盘, 重启续跑, 不硬等完成")
print("python:", sys.version.split()[0])
```

**追问**：1) 为什么 preStop 里 sleep 比依赖"摘端点快"可靠？——摘除链路（EndpointSlice→API server→kube-proxy/ingress controller→数据面规则）各环节异步，端到端延迟不可承诺；sleep 是把"摘除传播时间"显式化成常量，配合就绪探针摘除双保险；代价是每次发布多等几秒，用 PDB（PodDisruptionBudget）控制并发驱逐数。2) uvicorn 的 `--timeout-graceful-shutdown` 与应用内排空什么关系？——它是 uvicorn 在 SIGTERM 后**等待连接关闭的总上限**，到点强制断；应用必须在这个窗口内自己完成"拒新+清旧"，所以应用内部要有独立的排空 deadline（略小于该值），两者不匹配的典型事故是"uvicorn 先强杀、应用清理逻辑没跑完"。3) SIGKILL 前如果还有任务没排完怎么办？——设计上就该接受"强杀窗口"存在：一切在 SIGTERM 后要完成的动作必须有持久化检查点（outbox、任务状态表、分片游标），把"未完成"变成"可恢复"而不是"必完成"——排空的工程本质是收敛中断面，不是消灭中断。

## 背诵要点
- 排空时间 ≈ 端点摘除传播(2-5s) + 在途 P99.9 + 检查点间隔；gracePeriod ≥ 排空×1.5，uvicorn graceful-shutdown 比它小 2-3s。
- preStop sleep 2-5s 是把不可承诺的"摘除传播时间"显式化，与就绪探针摘除双保险；SIGTERM 处理必须幂等可重入。
- 长连接走"拒新+goaway+客户端退避重连"，后台任务走检查点续跑；排空的工程本质是收敛中断面（一切未完成可恢复），不是消灭中断。
