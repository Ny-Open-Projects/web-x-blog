### Q6061 · 事务内调下游 RPC 的事故复盘与拆解

> 难度:★★★★ | 标签:事故复盘, 事务边界, 分布式, 一致性

**问**：下单接口把"扣库存 RPC 调用"包进了数据库事务：`with session.begin(): ...; requests.post(coupon_service)`。下游抖动时连接池被长事务占满（见既有 Q6041），且下游成功了本地事务却回滚，优惠券被核销但订单没建。这个反模式的三个代价是什么？正确的事务边界怎么划？

**答**：三个代价：a) **连接占用放大**：事务期间连接被独占，RPC P99 500ms 就意味着每请求持锁持连接 500ms+，几十并发就榨干连接池，故障从"下游抖"放大成"本服务也瘫"（故障传播）；b) **一致性地狱**：下游是外部系统**不受本地事务管辖**——本地回滚了下游照样生效，产生"下游已执行、本地未提交"的脏状态，反向（本地提交下游失败）又需要补偿；c) **锁表时长放大**：行锁/间隙锁跨网络 RTT 持有，阻塞其他事务，死锁概率与锁等待雪崩式上升。正确边界：**事务只包数据库操作，最小化**；跨系统一致性用"本地消息表/Outbox"模式——本地事务里写业务表+outbox 表（原子），提交后由投递器异步调下游并按 outbox 状态重试（至少一次），下游用幂等键去重；已发生的脏数据走**对账任务**（定时比对两侧状态，补偿/冲正）。拆解迁移路径：①RPC 挪出事务，先改"下游调用失败即整单失败"为"订单落库状态机 PENDING → 异步核销"；②补 outbox 表与投递 worker；③历史脏数据跑对账脚本修复。验证手段：压测对照事务内外 P99 与连接池占用曲线，演练下游 503 时订单创建成功率。

```python
# file: code/03_Web后端开发/q6061_txn_boundary.py
import sqlite3, threading, time, queue

db = sqlite3.connect(":memory:", check_same_thread=False)
db.executescript("""
CREATE TABLE orders(id INTEGER PRIMARY KEY, status TEXT, user_id INT);
CREATE TABLE outbox(id INTEGER PRIMARY KEY, order_id INT, event TEXT,
                    sent INT DEFAULT 0, payload TEXT);
""")

conn_lock = threading.Lock()      # 单连接演示: 模拟连接池独占

def create_order_bad(user_id):
    """反模式: 事务内调下游 (演示: sleep 代替 RPC, 锁占用 300ms+)"""
    t0 = time.perf_counter()
    with conn_lock:               # 等价于连接被事务独占
        db.execute("BEGIN")
        cur = db.execute("INSERT INTO orders(status,user_id) VALUES('PENDING',?)", (user_id,))
        time.sleep(0.3)           # <-- RPC 在事务内: 下游 P99=300ms, 连接全被占
        db.execute("COMMIT")
    return time.perf_counter() - t0

def create_order_good(user_id):
    """正确: 事务只包 DB 双写(订单+outbox), RPC 异步走投递器"""
    t0 = time.perf_counter()
    with conn_lock:
        db.execute("BEGIN")
        cur = db.execute("INSERT INTO orders(status,user_id) VALUES('PENDING',?)", (user_id,))
        db.execute("INSERT INTO outbox(order_id,event,payload) VALUES(?,?,?)",
                   (cur.lastrowid, "coupon.use", f"order:{cur.lastrowid}"))
        db.execute("COMMIT")      # 原子提交, RPC 不在事务内
    return time.perf_counter() - t0

# 1) 连接占用对比: 3 并发下事务内 RPC 让吞吐塌掉
ts0 = [threading.Thread(target=lambda: create_order_bad(1)) for _ in range(3)]
t0 = time.perf_counter()
for t in ts0: t.start()
for t in ts0: t.join()
print(f"反模式 3 并发串行总耗时: {time.perf_counter()-t0:.2f}s (300ms RPC x 3 = 连接占用放大)")

t0 = time.perf_counter()
ts1 = [threading.Thread(target=lambda: create_order_good(1)) for _ in range(3)]
for t in ts1: t.start()
for t in ts1: t.join()
print(f"正确边界 3 并发总耗时: {time.perf_counter()-t0:.2f}s")

# 2) Outbox 投递器: 异步调下游 + 至少一次 + 幂等键
deliveries = []
def deliverer():
    while True:
        row = db.execute(
            "SELECT id, order_id, payload FROM outbox WHERE sent=0 LIMIT 1").fetchone()
        if not row: break
        oid, order_id, payload = row
        # RPC: 下游按 payload 里的幂等键(order_id)去重, 失败下轮重试
        deliveries.append((payload, "ok"))
        db.execute("UPDATE outbox SET sent=1 WHERE id=?", (oid,))
        db.execute("UPDATE orders SET status='PAID' WHERE id=?", (order_id,))

deliverer()
print("投递器:", deliveries, "| 订单状态:",
      db.execute("SELECT status FROM orders").fetchall())

# 3) 对账: 两侧状态不一致的兜底 (演示简单比对)
dirty = db.execute(
    "SELECT count(*) FROM orders o JOIN outbox b ON o.id=b.order_id "
    "WHERE b.sent=1 AND o.status!='PAID'").fetchone()[0]
print("对账脏数据:", dirty, "(生产: 定时任务比对本地与下游, 补偿/冲正)")
print("铁律: 事务只包 DB; 跨系统一致=Outbox+幂等投递+对账兜底")
```

**追问**：1) Outbox 怎么保证"至少一次"又不重复调用？——投递器按 outbox 行状态推进（发送成功才置 sent=1），崩溃在中间就重发，所以必须**至少一次 + 下游幂等键**（order_id 作 dedup key），两者缺一不可；投递器多实例部署要 SELECT FOR UPDATE SKIP LOCKED（见既有 Q6007）分片。2) "本地提交了但进程崩在 outbox 投递前"怎么办？——outbox 行还在，投递器扫表兜底，延迟=扫描周期（秒级），这是该模式的本质收益：把"跨系统原子性"降级为"本地原子 + 异步最终一致"；对实时性敏感的读可以"读本地状态优先，下游结果异步回写"。3) 为什么不用 TCC/SAGA 直接上？——TCC 要下游实现 Try/Confirm/Cancel 三接口改造重；SAGA 补偿链长、中间态暴露（见 06 类既有卡）；订单+优惠券这类场景 Outbox+幂等+对账三件套复杂度最低，优先级应是 Outbox → 对账 → 重型 saga。

## 背诵要点
- 事务内调 RPC 三代价：连接占用放大（故障传播）、下游不受事务管辖产生脏状态、锁表时长跨 RTT 放大死锁概率。
- 正确边界：事务只包 DB，本地原子写业务表+outbox，投递器异步至少一次投递 + 下游幂等键去重 + 定时对账兜底。
- 优先级：Outbox+幂等 > 对账任务 > TCC/SAGA；迁移先挪 RPC 出事务再补 outbox 与对账。
