### Q6063 · 压测定容：单实例 QPS 上限与水位推导

> 难度:★★★★ | 标签:容量规划, 压测, Little's Law, 水位线

**问**：运营问"一台 4C8G 实例到底能扛多少 QPS"，拍脑袋 1000 行不行？压测到 800 QPS 后 P99 从 50ms 跳到 2s，是压垮了还是配置错了？怎么用 Little's Law、拐点法、水位线把容量算成可复核的数？

**答**：框架化四步：a) **理论账**：Little's Law `L = λ × W`（并发数 = QPS × 平均耗时）——800 QPS × 50ms = 40 并发在途，uvicorn worker 的并发上限（线程池+连接池总容量）若只有 50，再往上排队即延迟跳变；b) **拐点压测**：QPS 从低到高阶梯加压，记录每档 P50/P99/错误率/CPU——容量=吞吐量曲线的拐点（P99 开始非线性上升处），800 QPS 的 2s 跳变大概率是**连接池/线程池排队**（并发超限）或 CPU 打满（每请求 CPU×QPS>核预算），两个原因的判据：CPU 未满时延迟跳变 → 排队问题；CPU 满 → 计算瓶颈（对照 Q6034 每请求 CPU 画像）；c) **水位线**：生产容量 = 拐点 × 安全系数 0.7（留给 GC、流量毛刺、依赖抖动），告警阈值设拐点的 60%；d) **依赖修正**：压测打的通常是"理想依赖"，真实下游 P99 加进来要重算 W——用分层账：本服务 CPU 时间 + 下游耗时 P99 决定 W 与容量，下游抖动时容量自动缩水，这就是"限流阈值要动态"的原因。工程规范：压测报告必须含——环境规格（worker 数/连接池/依赖 mock 与否）、阶梯表、拐点证据、水位线结论；容量数字绑定版本（优化后重测），写进部署文档。常见错账：压测客户端本身成了瓶颈（连接数不足/不并行，看到的是客户端吞吐）、压"读接口"外推"写接口"、忽视角落（启动冷缓存/定时任务抢占）。

```python
# file: code/03_Web后端开发/q6063_loadtest_capacity.py
import time, statistics, threading, queue

# ---- 模拟被测服务: 每请求 CPU 2ms + 依赖 IO 30ms ----
CPU_MS, IO_MS = 2, 30
MAX_CONCURRENCY = 40          # worker 并发上限(线程池+连接池)

results = []
sema = threading.BoundedSemaphore(MAX_CONCURRENCY)
lock = threading.Lock()

def handle():
    with sema:                                 # 并发超限就在这里排队
        t0 = time.perf_counter()
        _ = sum(i * i for i in range(700))     # ~2ms CPU
        time.sleep(IO_MS / 1000)               # 下游依赖 IO
        with lock: results.append((time.perf_counter() - t0) * 1000)

def step(qps, duration=1.0):
    interval = 1 / qps
    results.clear()
    n = int(qps * duration)
    threads = []
    t0 = time.perf_counter()
    for i in range(n):
        th = threading.Thread(target=handle)
        threads.append(th)
        th.start()
        time.sleep(interval)
    for th in threads: th.join(timeout=30)
    lat = sorted(results)
    if not lat: return qps, 0, 0
    p99 = lat[int(len(lat) * 0.99) - 1]
    in_flight = qps * statistics.median(lat) / 1000   # Little's Law
    return qps, p99, in_flight

print(f"{'QPS':>6} {'P99(ms)':>9} {'Little并发':>10}  判读")
for qps in (200, 400, 800, 1200):
    q, p99, conc = step(qps)
    verdict = "拐点!" if p99 > 500 else "线性区"
    print(f"{q:>6} {p99:>9.0f} {conc:>10.1f}  {verdict}")

# 1) 拐点理论核对: 并发上限 40, W=32ms -> 拐点 ~1250 QPS
knee = MAX_CONCURRENCY / ((CPU_MS + IO_MS) / 1000)
print(f"理论拐点 = 并发上限/W = {MAX_CONCURRENCY}/{CPU_MS+IO_MS}ms = {knee:.0f} QPS")

# 2) 水位线结论
safety = 0.7
print(f"生产容量 = 拐点 x {safety} = {knee*safety:.0f} QPS; 告警阈值 = 拐点x0.6 = {knee*0.6:.0f} QPS")

# 3) 客户端瓶颈自检: 压测并发低于拐点时看到的吞吐是客户端的
print("自检: 压测端并发 >= 服务端拐点/2 才可信; 否则量的是客户端吞吐")
print("报告四件套: 环境规格 / 阶梯表 / 拐点证据 / 水位线结论")
```

**追问**：1) P99 跳变而 CPU 才 40%，最先查什么？——排队点：worker 并发上限（uvicorn 默认线程池 40）、DB 连接池 size、下游 client 连接池、sema/队列配置；判据是"并发在途数 vs 各池上限"，Linux 上 `ss -s` 与应用内池指标（活跃/等待）直接定位，扩池后容量立刻恢复线性。2) Little's Law 在什么情况下失真？——闭系统压测（固定并发数打，而非开放速率）时 L 是自变量不是 λ×W，拐点会失真——开放模型压测（wrk/vegeta/locust 的固定速率模式）才符合线上随机到达；这也是"locust 默认并发模式测出来的容量偏乐观"的原因。3) 水位线 0.7 怎么定？——按流量形态：毛刺大（秒杀/推送）用 0.5，平稳流量 0.7-0.8；再留"依赖降级"预案——下游抖动 W 变大时容量缩水，限流要能动态下调，静态 0.7 只防自身问题不防依赖问题。

## 背诵要点
- Little's Law：L=λ×W；容量=并发上限/单请求耗时（本服务 CPU+下游 P99）；P99 跳变先查排队池（worker/连接池）再查 CPU。
- 压测用开放模型固定速率阶梯加压找拐点；闭系统压测（固定并发）容量失真；客户端并发不足时量到的是客户端。
- 生产容量=拐点×0.7（毛刺大用 0.5），告警=拐点×0.6；容量数字绑定版本重测，报告含四件套。
