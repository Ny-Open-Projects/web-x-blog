### Q6113 · 发布滚动窗口的容量损耗账

> 难度:★★★★☆ | 标签:容量规划, 滚动发布, K8s

**问**:10 个副本滚动发布，单实例冷启动 45s（含应用初始化 + readiness 通过），K8s 默认 maxUnavailable=25%/maxSurge=25%，发布期间真实服务容量降到多少？P99 在发布窗口抖到 SLO 之外，这笔损耗账怎么推导、怎么补？

**答**:结论：滚动发布的瞬时容量 = **可用副本数 × 单副本吞吐**，可用副本在每个滚动批次里经历"旧终止 → 新启动 → readiness 通过"的空窗。推导（10 副本、maxUnavailable=25%、maxSurge=25%、冷启动 45s）：25% 向下取整为每批更新 2 个副本，旧副本被杀是即时的，而新副本要 45s 才计入可用——最坏瞬时可用 8 个（2 个旧终止 + 2 个新未就绪）；若滚动总时长 5 分钟，平均可用副本 ≈ 10 - 2×(45s/300s×批次数) ≈ 9.4。maxSurge=25% 补的是"新 pod 提前排"的资源额度，使更新期间总量短暂到 12，对"旧副本终止后的空窗"不直接补容量。真正的容量杀手是三件事叠加：a) **readiness 太松**（探针通过但连接池没热）；b) **连接排空不优雅**（旧 pod 直接断流，在途请求 502，引 Q6074 优雅停机排空）；c) **每新副本冷启动都对下游做一次性冲击**（缓存空、连接池新建，引 Q6020 冷启动预热）。补容量手段：maxSurge 提到 50%（用额外资源换无损发布）、preStop sleep 让 LB 摘流后再杀进程、readiness 包含"缓存预热完成"信号；Python 侧把冷启动从 45s 压到 15s（延迟 import、预编译 pyc、模型懒加载）比调参数收益大。

```python
# 纯标准库：滚动发布容量损耗的模拟推导
import itertools

def rolling_capacity(n, max_unavail_pct, cold_s):
    """逐批模拟滚动发布：每批杀 min(max_unavail, 剩余) 个旧副本，等冷启动后进下一批"""
    max_unavail = max(1, int(n * max_unavail_pct))   # 终止侧额度（向下取整，至少 1）
    remaining, ready, starting = n, n, 0
    cap_log, clock = [], 0
    while remaining > 0:
        kill = min(max_unavail, remaining)
        ready -= kill
        starting += kill
        remaining -= kill
        # 等本批新副本就绪（冷启动）后才继续下一批：逐 tick 记录可用数
        for _ in range(cold_s):
            clock += 1
            cap_log.append(ready)
        ready += starting
        starting = 0
    return cap_log

cap = rolling_capacity(n=10, max_unavail_pct=0.25, cold_s=45)
print(f"滚动完成 tick 数: {len(cap)}")
print(f"可用副本最坏: {min(cap)}  平均: {sum(cap)/len(cap):.2f}  容量损耗峰值: {(10-min(cap))/10*100:.0f}%")

# 参数对照：冷启动缩短的收益（maxSurge 是资源层手段，这里对照冷启动维度）
for cold in (45, 30, 15):
    c = rolling_capacity(10, 0.25, cold)
    print(f"冷启动={cold}s: 最坏可用 {min(c)} 副本, 平均 {sum(c)/len(c):.2f}")

# 结论辅助：最坏可用副本数决定需要预补的静态余量
worst = min(cap)
print(f"\n建议: 保留副本数 = ceil(10/{worst}×10) 中取整 —— 至少按 {worst}/10 比例放大 maxSurge 或常态多部署 {10-worst} 个副本")
```

**追问一层**:为什么 maxUnavailable 保证的是"终止侧下限"、maxSurge 保证的是"新增侧上限"，两者共同决定的"最坏可用副本"公式是什么？
**追二层**:readiness 探针通过但服务还没热（连接池空、JIT 未热）时，探针怎么设计才能反映真实吞吐（对照 Q6055 健康检查成本、Q6020 预热）？

**背诵要点**
- 瞬时容量 = 可用副本 × 单副本吞吐；滚动空窗 = 旧副本即时终止 + 新副本等冷启动。
- 提 maxSurge（用资源换无损）、压冷启动（延迟 import/pyc 预热）、preStop 摘流三者一起做。
- 最坏可用副本可逐 tick 推导；发布期 P99 抖动优先修排空与预热，其次才是副本数。

**复盘追问**
- 发布窗口错误率尖峰集中在"新 pod 接流后的前 30s"，除了预热还查什么？提示：新 pod 的下游连接冷建立、本地缓存空导致的慢查询放大（引 Q6067）。
- 为什么把"进程池批量 spawn"（Q5613）和这次的"Pod 滚动"算同一类账？提示：都是"批量资源创建 + 预热串行化"的峰值叠加。
