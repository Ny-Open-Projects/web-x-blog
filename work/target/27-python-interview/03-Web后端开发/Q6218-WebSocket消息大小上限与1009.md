### Q6218 · WebSocket 消息大小上限：ws_max_size、1009 关闭与内存尖峰账

难度：P6 ｜ 标签：WebSocket、消息大小限制、uvicorn ws_max_size、1009、分帧、内存尖峰

**问**：WebSocket 一条消息多大算"太大"？uvicorn 的 `ws_max_size`（默认 16MB）在什么位置生效——超限后连接怎么处理，为什么是 1009 而不是 413？客户端故意发"声明 16MB 但慢速发送"的分帧会怎样拖垮服务端？合理的消息上限应该按什么定？

**答**：
结论：WebSocket 帧头自带**长度字段**（7 位扩展至 64 位，理论单帧可达 EB 级），"多大算太大"是应用契约不是协议约束。uvicorn 的 `--ws-max-size`（默认 16MB）在**读取层**生效：收到的消息累计长度超过上限即终止连接——WebSocket 的资源模型是"一条连接一个生命周期"，拒绝服务的方式就是关闭连接，所以用 close code **1009 Message Too Big**（服务端主动发 close 帧再断），HTTP 时代的 413 在这里没有对应物（连接级语义替代请求级语义）。慢速分帧攻击面：攻击者声明大消息但按极小分帧慢发，每帧都合法、总长超限才触发——在触发前，服务端已经为这条连接**持续占用接收缓冲与组装内存**，海量此类连接 = 内存耗尽；防御靠连接级资源配额（每连接缓冲上限 + 空闲超时），不只是单消息上限。合理上限的定法：按**业务最大合法消息 × 安全系数**（如配置同步消息最大 2MB，上限设 8MB），16MB 的默认值对绝大多数业务是过宽的——过宽的上限等于把内存尖峰预算白白让给异常流量。

取舍：a) 大数据传输不走大消息：分片成多条消息（带分片协议）或走 HTTP 直传/对象存储（消息里放引用，Q6064），WS 通道只传控制信令——上限可以压到 KB 级；b) 上限分层：传输层 ws_max_size（连接级兜底）+ 应用层 schema 校验（消息类型各自的上限）——两层缺一不可；c) 接收缓冲账：每连接组装缓冲 = 在途消息大小，并发连接数 × 上限就是内存尖峰的理论值，容量账（Q5574 的每连接缓冲推导）要按这个公式卡预算；d) 关闭时机：超限立即发 1009 close，**不再消费**该连接后续帧（Q5719 的关闭纪律），防止攻击者继续灌；e) 监控：消息大小分布（P99）、超限关闭数——超限率上升说明客户端版本在发畸形大消息，是契约破坏的前兆信号。

实战：事故形态是"客户端某版本在断网重连后把本地 50MB 队列一次性回放，服务端 ws_max_size 默认 16MB 挡住了，但 2000 个重连客户端同时各发 16MB，组装缓冲把 worker 内存顶爆；修复：上限降为 4MB、客户端分片回放（每片 100KB + 服务端 ack）、重连风暴限速（Q5603）、每连接接收配额监控"。下面实现大小限制与分帧账。

```python
MAX_MESSAGE = 4 * 1024 * 1024  # 4MB 传输层上限


def incoming_message(total_len: int, chunks: int, chunk_interval_ms: int, conn_count: int):
    peak_mem = conn_count * min(total_len, MAX_MESSAGE)
    verdict = {
        "action": "deliver",
        "close_code": None,
        "peak_mem_mb": peak_mem / 1048576,
    }
    if total_len > MAX_MESSAGE:
        verdict["action"] = "close"
        verdict["close_code"] = 1009          # Message Too Big: 立即断, 不再消费
    elif chunks * chunk_interval_ms > 30_000:  # 慢速分帧: 30 秒还没发完
        verdict["action"] = "idle-timeout"
    return verdict


print("[1] 正常消息:", incoming_message(100 * 1024, 1, 10, 1000))
print("[2] 超限消息:", incoming_message(5 * 1048576, 1, 10, 1000), "-> 1009 关闭")
print("[3] 2000 连接各 4MB 在途 -> 尖峰:", incoming_message(4 * 1048576, 1, 10, 2000)["peak_mem_mb"], "MB —— 上限即内存预算")
print("[4] 慢速分帧(合法帧, 慢速灌):", incoming_message(3 * 1048576, 100, 500, 1), "-> 需要空闲超时兜底")
print("[5] 设计准则: 上限 = 业务最大合法消息 x 安全系数; 大数据走分片+ack 或直传引用")
```

**追问一**：为什么超限用 1009 关连接而不是"拒收这条消息继续连接"？—— WebSocket 是**有序字节流上的消息封装**，服务端读到超限点时已经在组装缓冲里持有部分数据，协议层没有"丢弃当前消息、重置流"的机制（不像 HTTP 可以等下一个请求边界）——继续维持连接意味着要为"已经没用的部分消息"继续维护状态与缓冲。所以标准行为就是关闭：1009 让客户端明确知道"消息太大被拒"，可以分片或改道。副作用是连接状态丢失，这正好倒逼客户端做大消息的分片设计（带 ack 的小分片），协议层面是自洽的。

**追问二**：`ws_max_size` 与应用层 schema 校验的分工怎么定？—— 传输层上限的职责是**资源保护**（内存尖峰卡预算），值 = 各类合法消息的最大值 × 安全系数，按类型差异化做不到（uvicorn 是连接级全局值），所以它注定"偏宽"；应用层职责是**契约校验**：按消息 type 定各自上限（心跳 ≤1KB、配置同步 ≤2MB、批量导入 ≤8MB），超限走应用级错误响应（连接不断）。两层关系：传输层挡"连接级灾难"，应用层给"业务级反馈"。只配传输层，客户端收到的是冷冰冰的断连（难排障）；只配应用层，资源保护缺位。生产配置要两层都有，且把"超限关闭数"与"应用层超大消息错误数"分开监控。

## 背诵要点
- WS 帧头长度可达 EB 级，上限是应用契约：uvicorn ws_max_size 默认 16MB 在读取层生效，超限发 1009 关连接（连接级语义替代 413）。
- 慢速分帧攻击：每帧合法、组装缓冲长期占用——需连接级配额 + 空闲超时兜底，不只是消息上限。
- 上限 = 业务最大合法消息 × 安全系数；大消息走分片+ack 或对象存储引用；内存尖峰 = 并发连接 × 上限。

## 复盘追问
- 2000 个重连客户端各发 16MB 为什么拖垮 worker？（组装缓冲 = 连接数 × 消息上限；降上限 + 分片回放 + 风暴限速）
- 1009 关连接与 HTTP 413 的语义差别？（WS 无消息级拒绝机制，资源模型是连接生命周期；应用层再给业务反馈）
