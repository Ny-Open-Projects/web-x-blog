### Q6034 · 每请求成本画像：端到端 CPU 预算拆解

> 难度:★★★★ | 标签:成本工程, 性能画像, 容量规划

**问**："这个接口单核能扛多少 QPS"怎么回答？一个请求的 CPU 都花在哪几层？画像方法和"快慢优化"怎么落到预算表？

**答**：先立公式：**单核 QPS = 1000ms ÷ 请求 CPU 成本(ms)**（CPU 密集视角；IO 等待不占核但要计线程/协程）。每请求成本画像按层拆：1) **框架层**——路由/中间件/依赖注入（FastAPI 依赖链每次 resolve、Starlette 中间件洋葱 Q107），典型 0.5-2ms；2) **校验/序列化层**——Pydantic 校验 + JSON 编解码，与负载大小线性（Q6003/Q6004/Q5034），大响应体上常占 30-60%；3) **业务层**——纯 Python 计算；4) **基础设施税**——日志序列化、metrics 打点、trace span 创建（Q6015/Q1385），单请求几十条日志时可达 1-5ms；5) **IO 等待**（不占 CPU，但决定并发结构选择）。画像方法：本地 pprof/pyinstrument（采样不重排）拆分层占比 → 生产 py-spy 抽样验证（Q6010）→ 把占比写进"预算表"随 PR 维护。决策规则：优化只动占比 >15% 的层；框架层微优化（换 uvloop）通常 <10% 收益，**响应体瘦身与日志降噪才是大头**。取舍：画像本身有成本（生产常驻 py-spy 有开销），基线画像 + 故障时抓取的节奏即可。

```python
# file: code/03_Web后端开发/q6034_per_request_cpu.py
"""分层 CPU 画像: 模拟请求的各层成本, 输出预算表."""
import json
import time

def stage(fn, times: int = 1) -> float:
    t0 = time.perf_counter()
    for _ in range(times):
        fn()
    return (time.perf_counter() - t0) * 1000

# --- 模拟各层 ---
def framework_layer() -> None:                       # 中间件+依赖解析
    total = 0
    for i in range(50):
        total += i

def validation_layer(payload: dict) -> dict:         # 校验+模型构建(模拟 Pydantic)
    return {k: v for k, v in payload.items() if k != "_meta"}

def serialization_layer(data: dict) -> str:          # JSON 编码
    return json.dumps(data, separators=(",", ":"))

def logging_tax(payload: dict) -> int:               # 日志序列化税
    return len(json.dumps({"req": payload, "ts": time.time()}))

payload = {"rows": [{"id": i, "name": f"u{i}", "score": i * 1.5} for i in range(200)],
           "_meta": {"trace": "abc"}}

def one_request() -> dict:
    m1 = stage(framework_layer)
    data = validation_layer(payload)
    m2 = stage(lambda: validation_layer(payload))
    m3 = stage(lambda: serialization_layer(data))
    m4 = stage(lambda: logging_tax(payload))
    return {"framework_ms": round(m1, 3), "validation_ms": round(m2, 3),
            "serialization_ms": round(m3, 3), "logging_ms": round(m4, 3)}

BUDGET = one_request()
total_ms = sum(BUDGET.values())
BUDGET["total_cpu_ms"] = round(total_ms, 3)
BUDGET["单核QPS上限"] = int(1000 / total_ms)
for k, v in BUDGET.items():
    print(f"{k:18s} {v}")

print("决策规则: 只优化占比>15%的层; 本例序列化+日志常是头部")
print("生产验证: py-spy 采样对齐分层(本地画像只定结构, 不定数值)")
```

**追问**：1) 为什么"单核 QPS"不能直接乘核数？——多 worker 后共享面（GIL 单进程内的争用、DB 连接池、下游配额）先到上限；横向扩展的账是 `min(CPU 账, 连接池账, 下游配额账)`（Q1343/Q1377）。2) 日志税怎么降？——级别分层 + 采样（Q6015）、结构化日志延后序列化（记录 lazy 字段）、大字段只留哈希/截断；把"每请求日志字节预算"纳入成本画像。3) 画像显示框架层占 40% 正常吗？——小接口正常（固定成本占比高），此时优化方向是合并中间件、缓存依赖解析结果，而不是盲目换框架；占比要结合绝对值看。

## 背诵要点
- 单核 QPS = 1000 ÷ 请求 CPU ms；画像五层：框架/校验序列化/业务/日志税/IO 等待。
- 只优化占比 >15% 的层；响应体瘦身与日志降噪收益通常大于框架微优化。
- 本地画像定结构、py-spy 生产抽样定数值；预算表随 PR 维护防漂移。
