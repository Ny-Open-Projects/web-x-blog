### Q6236 · 维护窗口与只读模式：写请求的优雅拒绝与状态标记

难度：P6 ｜ 标签：维护窗口、只读模式、503、Retry-After、迁移模式、优雅拒绝、状态标记、数据迁移

**问**：数据迁移/DDL/切换存储时，"停机维护"与"只读模式"怎么选？只读模式的判定逻辑放哪一层、状态存哪（内存开关/DB 标记/配置中心）？写请求怎么拒绝才优雅——503+Retry-After 还是 409？管理员与内部探活要不要豁免？只读窗口里"读请求打到新库、写请求被拒"的切换序列怎么编排？

**答**：
结论：只读模式是迁移窗口的**优雅降级**：停机（503 全拒）损失可用性，只读（读放行、写拒绝）把损失压缩到写请求——大多数读多写少的业务，用户几乎无感。设计四要素：①**判定点在最外层中间件**——所有写方法（POST/PUT/PATCH/DELETE）进业务逻辑前先拦，避免写一半再失败（事务回滚是兜底不是设计）；②**状态源分层**——内存开关（单实例快但集群不一致）、配置中心推送（集群一致、秒级生效）、DB 标记（自身就是迁移对象时不可用！迁移期间 DB 是最不可靠的状态源）——生产默认配置中心，迁移开始前推送只读标志；③**响应契约**——写请求返回 **503 Service Unavailable + Retry-After**（Q6018 家族）让客户端按退避重试，辅以业务错误码（如 `MAINTENANCE_READONLY`）让前端显示维护中；**不用 409**（那是资源状态冲突的语义，Q2156）；④**豁免面**——健康检查（liveness 仍 200，readiness 可标记 not ready 让 LB 摘流）、管理员只读操作、幂等的探测请求豁免；**写类管理操作不豁免**（迁移窗口连管理员写都该走特殊通道）。切换编排的完整序列：预迁移检查 → 推送只读 → 排空在途写 → 停后台写任务（cron/队列消费者暂停）→ 迁移 → 校验 → 恢复写——**排空与后台任务暂停**是最常被漏的两步。

取舍：a) 只读 vs 限写：粒度可以是"全只读"或"按表/按接口只读"（迁移 user 表只拒 user 相关写）——细粒度表达力强但判定逻辑复杂，首选全局只读+显式豁免清单；b) 只读的实现深度：**真只读**（DB 用户权限降级为只读账号）与**应用层拦截**双管齐下——应用拦截防"逻辑漏网"，DB 权限是最后防线（防应用 bug 破坏数据）；c) 客户端感知：Retry-After 给自动重试客户端，API 文档与状态页给人工用户——两层通知；d) 只读期间的写请求日志：全量记录被拒的写（用于事后补偿/回放），有业务价值的走队列暂存（队列消费者也停的话就不存，权衡一致性）；e) 时长与预告：窗口超过 30 分钟应有状态页与用户通知，只读是"分钟级窗口"的技术，小时级窗口要重新评估迁移方案。

实战：事故形态是"大表迁移只停了应用写入口，cron 定时任务与消息队列消费者仍在写旧库，迁移期间新旧库数据分叉，切换后丢 2 小时订单——修复为统一的只读开关（配置中心推送）+ 中间件拦截写请求 + 迁移编排里显式暂停 cron/消费者 + 排空在途写（检查活跃连接与事务列表）"。下面实测只读中间件与切换编排。

```python
# 维护窗口与只读模式
import time

class ReadOnlyGate:
    """只读门: 中间件层判定, 状态源为配置中心推送的标志"""

    def __init__(self) -> None:
        self.read_only = False
        self.reason = ""

    def handle_request(self, method: str, path: str, is_admin: bool = False) -> tuple[int, dict]:
        # 豁免面: 健康探活与管理员读
        if path in ("/healthz", "/readyz"):
            return 200, {"status": "ok" if not self.read_only else "read-only"}
        if method in ("GET", "HEAD", "OPTIONS"):
            return 200, {"data": "ok"}
        if is_admin and path.startswith("/admin/view"):
            return 200, {"data": "admin view"}
        if self.read_only:                                # 写请求全部拦截
            return 503, {"error": "MAINTENANCE_READONLY",
                         "message": self.reason or "service under maintenance",
                         "retry_after": 60}
        return 200, {"written": True}

gate = ReadOnlyGate()

print("[1] 正常态: 写请求放行")
print("   ", gate.handle_request("POST", "/orders"))

print("[2] 只读窗口: 配置中心推送后, 写请求 503+Retry-After, 读不受影响")
gate.read_only = True
gate.reason = "database migration 02:00-02:20 UTC"
print("    GET  /orders  ->", gate.handle_request("GET", "/orders")[0], "(读放行)")
code, body = gate.handle_request("POST", "/orders")
print(f"    POST /orders  -> {code} {body}")
print("    /healthz      ->", gate.handle_request("GET", "/healthz"), "(探活豁免, LB 不摘实例)")
print("    503+Retry-After 让客户端退避重试; 不用 409 (那是资源状态冲突语义)")

print("[3] 迁移切换编排: 只读只是其中一环")
steps = [
    "1. 预迁移检查 (数据一致性/容量/回滚预案)",
    "2. 配置中心推送只读标志 -> 所有实例秒级生效",
    "3. 排空在途写: 等待活跃事务结束/连接池排空",
    "4. 暂停后台写: cron 任务/消息队列消费者/异步任务 (最常被漏!)",
    "5. 执行迁移 (双写校验/数据同步)",
    "6. 校验通过 -> 关闭只读 -> 恢复后台任务 -> 客户端退避重试自动恢复",
]
for s in steps:
    print("   ", s)

print("[4] 双防线: 应用层拦截防逻辑漏网 + DB 账号权限降级为只读 (最后防线)")
print("    迁移期间 DB 是最不可靠的状态源 -- 只读标志放配置中心, 不放 DB")
gate.read_only = False
print("[5] 恢复: 关闭只读后, 客户端按 Retry-After 退避自动重试, 写流量回补")
print("[6] 窗口纪律: 分钟级窗口用只读; 小时级要有状态页与用户通知; 被拒写全量记录供事后补偿")
```

**追问一**：为什么"暂停后台写任务"是最常被漏的一步？哪些后台写容易漏？—— 因为迁移清单通常只围绕"在线请求路径"，而**写路径有四条**：在线 API 只是其一，其余三条全部在后台：①**定时任务**（cron/celery beat 的对账、统计、清理）——按计划触发，迁移窗口恰逢其时就在写；②**消息队列消费者**——积压消息在窗口内被消费产生写；③**异步任务/重试队列**——用户请求触发的延后写（迁移前 5 秒提交的导出任务、重试中的失败写）；④**第三方回调**——支付回调、webhook 投递（Q6013）带着写语义进来。漏掉任一条，迁移期间数据分叉（旧库还在长）。根治是**写路径全景清单**：把所有写入口（API/任务/消费者/回调）登记在案，只读开关推送给每一类执行体（不只是 Web 层）——编排脚本里"暂停写"是一组动作不是一行配置。验证手段：迁移窗口内对旧库开 binlog/审计观察"零写入"再动手，用事实而不是清单自信。

**追问二**：只读模式下被拒的写请求怎么办——丢弃、暂存还是回放？"补偿"的设计边界在哪？—— 三档按业务语义选：①**丢弃 + 503 让客户端重试**：默认姿势——写请求的发起方（用户/上游服务）具备重试能力，Retry-After 给出恢复时间，幂等键（Q141）保证重试安全——这是把状态机留在客户端的最简方案；②**暂存队列**：写请求反序列化后进暂存队列，恢复后回放——看似贴心但有暗坑：**请求的时效性语义丢失**（下单回放后库存/价格已变）、顺序性破坏、队列本身成为新的一致性风险点，只适合"纯创建型、无上下文依赖"的写（如表单提交）；③**回放审计**：被拒写全量落日志（方法/路径/幂等键/时间），恢复后按业务需要**人工触发**补偿回放——风控/交易类业务的标准姿势，回放是显式决策不是自动行为。设计边界一句话：**只读模式提供"优雅拒绝"，不承诺"代为执行"**——把恢复责任还给有重试能力的调用方，平台只保证"拒绝得清楚、记录得完整"，越界的代执行会引入比停机更麻烦的一致性问题。

## 背诵要点
- 只读模式 = 迁移窗口优雅降级：中间件拦截写（503+Retry-After+业务码），读放行；不用 409（资源冲突语义）。
- 状态源放配置中心（DB 自身是迁移对象时最不可靠）；双防线 = 应用拦截 + DB 账号降级只读。
- 编排五步中最常漏"排空在途写 + 暂停后台写（cron/消费者/回调）"；写路径全景清单 + binlog 零写入验证。

## 复盘追问
- 迁移后丢 2 小时订单的根因？（后台写路径未暂停导致新旧库分叉；写入口全景清单+只读开关推送所有执行体）
- 被拒的写请求要不要暂存回放？（默认 503+Retry-After 交客户端重试；暂存丢时效语义，回放应是人工显式决策）
