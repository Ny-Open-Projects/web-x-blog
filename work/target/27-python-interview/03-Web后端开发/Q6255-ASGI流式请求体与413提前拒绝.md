### Q6255 · ASGI 流式读请求体：Content-Length 不可信、边读边判上限与 early reject

难度：P7 ｜ 标签：ASGI、请求体、Content-Length、chunked、413、early reject、连接复用、流式读取

基线：库知识卡，代码用标准库模拟 ASGI `receive` 的 chunk 流与 413 提前拒绝。

**问**：一个上传接口按 `Content-Length` 预分配 `bytearray` 再 `await request.body()`，被一条声明 `Content-Length: 10` 实际发送 2GB 的请求打爆内存；另一个接口在超限后直接返回 413，但同一个 keep-alive 连接上的下一个请求全部错位。ASGI 里请求体应该怎么读？`Content-Length` 能信到什么程度？为什么"提前返回 413"必须配合关闭连接？

**答**：

- **结论**：ASGI 的请求体是**消息流**：`receive()` 反复返回 `{"type": "http.request", "body": b"...", "more_body": bool}`，直到 `more_body=False`；也可能返回 `{"type": "http.disconnect"}`。`Content-Length` 只是客户端声明，**可以缺失（chunked）、可以撒谎、可以与实际不符**，服务端不能按它预分配，也不能在没读满时假设"没有更多数据"。正确做法是：①维护**累计字节数**，每收到一个 chunk 就加，超过业务上限立即停止读取并返回 413；②有 `Content-Length` 且明显超限时可以先做"early reject"（不读 body 直接 413），但仍要按"可能撒谎"处理——不能因为声明很小就放心读；③提前返回 413 时，请求体还没读完，HTTP/1.1 的 keep-alive 连接上残留字节会被当成下一个请求的起始行，造成请求走私/错位，所以响应必须带 `Connection: close`（或由服务器在未读完 body 时主动关闭连接）；④chunked 传输没有 Content-Length，只能边读边判。

- **取舍**：a) 流式读取：内存 O(chunk)，可以边读边校验/落盘/转发，适合大文件；代价是业务代码要自己管理状态机与上限；b) 一次性 `await request.body()`：简单，但会把整个 body 读进内存，框架通常有 `max_body_size` 之类的保护，别自己绕过；c) early reject：省带宽、省内存，但只能基于"声明的长度"做第一道闸，不能替代流式累计校验；d) 413 之后是否 drain 剩余 body：drain 可以保持连接复用，但攻击者可以借此让你读 2GB；更安全的是直接关闭连接（`Connection: close`），让客户端重连。

- **实战**：事故形态是"上传接口 OOM"——代码 `size = int(headers["content-length"]); buf = bytearray(size)`，攻击者声明 10 字节却持续发送；另一个事故是"413 之后下一个请求 400"——服务端返回 413 但没读完 body，keep-alive 复用连接，剩余字节被解析成下一个请求的方法名。修复：①删除按 Content-Length 预分配，改为固定大小 chunk 累加 + 上限；②超限立即 `Connection: close` 并停止读取；③网关层（nginx/ingress）也配 `client_max_body_size`，形成两道防线；④对 chunked 请求单独测试（无 Content-Length）。

```python
# ASGI 请求体: Content-Length 不可信, 累计上限, early reject 与连接关闭
class PayloadTooLarge(Exception):
    pass
async def read_body(receive, limit):
    total = 0
    chunks = []
    while True:
        msg = await receive()
        if msg["type"] == "http.disconnect":
            break
        chunk = msg.get("body", b"")
        total += len(chunk)
        if total > limit:
            raise PayloadTooLarge(total)
        chunks.append(chunk)
        if not msg.get("more_body", False):
            break
    return b"".join(chunks)
def make_receive(parts):
    # parts: [(bytes, more_body), ...]
    it = iter(parts)
    consumed = []
    async def receive():
        try:
            body, more = next(it)
        except StopIteration:
            return {"type": "http.disconnect"}
        consumed.append(len(body))
        return {"type": "http.request", "body": body, "more_body": more}
    return receive, consumed
async def app(scope, receive, send, limit=8):
    declared = scope.get("content_length")
    sent = []
    async def _send(msg):
        sent.append(msg)
    # 第一道闸: 声明值明显超限, 不读 body 直接拒绝
    if declared is not None and declared > limit:
        await _send({"status": 413, "headers": [("connection", "close")], "phase": "early"})
        return sent, 0
    try:
        body = await read_body(receive, limit)
    except PayloadTooLarge:
        # 第二道闸: 实际字节超限, 停止读取并关闭连接
        await _send({"status": 413, "headers": [("connection", "close")], "phase": "stream"})
        return sent, None
    await _send({"status": 200, "bytes": len(body)})
    return sent, len(body)
async def main():
    # 1) 声明 100 > limit 8: early reject, 一个字节都不读
    receive, consumed = make_receive([(b"x" * 10, True)] * 3)
    sent, _ = await app({"content_length": 100}, receive, None)
    print("→ early reject:", sent[0]["phase"], "| 已读 chunk:", consumed)
    assert sent[0]["status"] == 413 and sent[0]["phase"] == "early"
    assert consumed == []                      # 没有消费 body
    # 2) 撒谎: 声明 5, 实际 30, 流式累计在第一个 chunk 后超限
    receive, consumed = make_receive([(b"x" * 10, True)] * 3)
    sent, _ = await app({"content_length": 5}, receive, None)
    print("→ 声明撒谎时:", sent[0]["phase"], "| 已读 chunk:", consumed)
    assert sent[0]["status"] == 413 and sent[0]["phase"] == "stream"
    assert consumed == [10]                    # 只读了第一个, 后面的没读
    assert ("connection", "close") in sent[0]["headers"]
    # 3) 没有 Content-Length(chunked): 只能边读边判
    receive, consumed = make_receive([(b"abc", True), (b"def", False)])
    sent, n = await app({}, receive, None)
    print("→ chunked 正常:", sent[0], "| 总字节:", n)
    assert sent[0]["status"] == 200 and n == 6

    # 4) 恰好等于上限: 允许
    receive, _ = make_receive([(b"12345678", False)])
    sent, n = await app({"content_length": 8}, receive, None)
    assert sent[0]["status"] == 200 and n == 8

    # 5) 超过一个字节: 拒绝
    receive, _ = make_receive([(b"123456789", False)])
    sent, _ = await app({"content_length": 9}, receive, None)
    assert sent[0]["status"] == 413

import asyncio
asyncio.run(main())
```

**追问一**：为什么"按 Content-Length 预分配"是经典漏洞？框架的 `max_body_size` 能兜住吗？—— 预分配把"客户端声明的数字"直接变成服务端的内存申请，攻击者用 `Content-Length: 10000000000` 就能在不发送任何 body 的情况下让进程 OOM（或触发 MemoryError 拖垮 worker）；即使框架有 `max_body_size`，如果它在读取前只检查声明值、而读取时又按声明值 `read(n)`，仍可能被"声明大、实发小"或"声明小、实发大"的组合绕过。正确姿势是"固定 chunk 读 + 累计计数"，永远不按声明值一次性分配；框架的 `max_body_size` 是第一道闸，业务自己的流式上限是第二道。

**追问二**：提前返回 413 不读完 body，为什么必须关闭连接？有没有"既复用连接又不读 2GB"的办法？—— HTTP/1.1 是字节流，服务器和客户端靠"消息边界"（Content-Length/chunked 终止）来区分请求；如果服务器在 body 未读完时就发响应，客户端可能继续发送剩余 body，这些字节会留在连接里，被服务器当成下一个请求的起始行（请求走私/错位的根源）。所以规范做法是发 413 后关闭连接（`Connection: close` 或直接 `transport.close()`）。"既复用又不读"理论上可以 drain 剩余 body，但 drain 本身就是读 2GB，攻击者正好利用；折中是"最多 drain N KB，超过就关连接"。HTTP/2 的多路复用没有这个问题（每个 stream 独立 RST_STREAM），但 HTTP/1.1 必须按连接边界处理。

## 背诵要点

- ASGI body 是 chunk 流（`more_body`），Content-Length 可缺失/可撒谎；只能按累计字节数判上限，不能按其预分配。
- 两道闸：声明值超限 early reject（不读 body）；实际字节超限立即停止读取并 413。
- 未读完 body 就响应必须 `Connection: close`，否则残留字节会让 keep-alive 上的下一个请求错位/走私。

## 复盘追问

- 声明 10 字节实际发 2GB，为什么会 OOM？（按 Content-Length 预分配/一次性 read；应按 chunk 累计并设上限）
- 413 之后下一个请求 400，根因是什么？（body 未读完、连接被复用，剩余字节被解析成新请求；响应要 close 连接）
