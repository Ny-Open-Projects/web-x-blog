### Q6153 · 账户锁定防刷与锁定放大攻击的容量账

难度：P6 ｜ 标签：登录防刷、账户锁定、限流、容量规划、暴力破解

**问**：连续失败 N 次锁账户 M 分钟的防刷策略，为什么会被攻击者反向利用成"锁定放大"（批量锁死正常用户）？失败计数按"账户"还是按"IP/指纹"维度存，内存与 Redis 的容量账怎么算？渐进式延迟 + 设备指纹 + CAPTCHA 的组合怎么配比？

**答**：
结论：纯账户维度锁定的代价公式：攻击者用**用户名清单**（泄露库）每个账号发 N 次错密码就能锁死全量用户——`锁定成本 = 用户数 × N 次请求`，极便宜；这是可用性 vs 安全的经典冲突。正确的分维组合：① **账户维度**只做"渐进延迟"（第 k 次失败延迟 k²/指数级，不硬锁）或锁后改用第二因子解锁，而非直接拒绝；② **IP/指纹维度**做硬限流（黑名单 + 短 TTL），攻击者换 IP 成本高；③ **全局维度**兜底总量阈值触发 CAPTCHA。容量账：按账户维存 `user → (fail_count, lock_until)`，TTL 取锁定时长，内存 ≈ 日活用户 × ~100B（两个整数 + 时间戳）；按 IP 维存 `ip → window counts`，量级 = 攻击源 IP 数（可突发百万级），必须上 Redis + 淘汰策略而非进程内 dict——Q6050 已讲多租户限流内存，这里强调"维度选择决定存储形状"。

取舍：锁定时长是双刃剑——长锁定保护密码但放大 DoS；行业标准走向"软锁定"：锁定后允许**仅凭第二因子**登录（短信/Passkey），攻击者仍破不了密码，正常用户不被完全拒之门外。CAPTCHA 触发条件要挂在"风险分数"（失败率 + IP 信誉 + 指纹熵）而非固定失败次数，避免攻击者用低价流量把全站推进 CAPTCHA。

实战：监控三指标——失败尝试总量、锁定中账户数、CAPTCHA 触发率；任一指标突增即为攻击信号。密码喷洒（password spraying，一个密码对大量账户各试 1-2 次）恰好绕过单账户阈值，必须靠**全局维度**（同密码失败率/同 IP 跨账户尝试数）检测。

```python
import time, hashlib

class LoginGuard:
    """三维组合：账户渐进延迟 + IP 硬限流 + 全局 CAPTCHA 触发"""
    def __init__(self, ip_limit=10, ip_window=300, captcha_threshold=50):
        self.user_fails = {}      # user -> (count, last_ts)   渐进延迟
        self.ip_hits = {}         # ip -> (count, window_start)
        self.ip_limit, self.ip_window = ip_limit, ip_window
        self.captcha_threshold = captcha_threshold
        self.total_fails = 0

    def check(self, user: str, ip: str) -> dict:
        now = time.monotonic()
        # IP 维：滑动窗口硬限流
        cnt, wstart = self.ip_hits.get(ip, (0, now))
        if now - wstart > self.ip_window:
            cnt, wstart = 0, now
        self.ip_hits[ip] = (cnt, wstart)
        if cnt >= self.ip_limit:
            return {"allow": False, "reason": "ip-rate-limited"}
        self.ip_hits[ip] = (cnt + 1, wstart)

        # 账户维：渐进延迟（不硬锁，杜绝锁定放大）
        fails, _ = self.user_fails.get(user, (0, now))
        delay = min(fails ** 2 * 0.1, 10.0)       # k^2 * 100ms，封顶 10s
        risk = {"allow": True, "delay_s": delay,
                "captcha": self.total_fails > self.captcha_threshold}
        return risk

    def record_fail(self, user):
        fails, last = self.user_fails.get(user, (0, 0.0))
        self.user_fails[user] = (fails + 1, time.monotonic())
        self.total_fails += 1

    def record_ok(self, user):
        self.user_fails.pop(user, None)

guard = LoginGuard(ip_limit=5)
# 正常用户：失败几次只变慢，不被锁死
for _ in range(3):
    guard.check("alice", "1.2.3.4"); guard.record_fail("alice")
print("alice after 3 fails:", guard.check("alice", "1.2.3.4"))

# 攻击者：单 IP 打 6 次即被 IP 维拦截（账户不受永久锁定）
last = None
for _ in range(6):
    last = guard.check("victim", "9.9.9.9"); guard.record_fail("victim")
print("attacker 6th:", last)

# 全局阈值触发 CAPTCHA（password spraying 检测靠全局维度）
for idx, u in enumerate((f"user{n}" for n in range(50))):
    guard.check(u, f"10.0.0.{idx % 5}"); guard.record_fail(u)
print("captcha triggered:", guard.check("newbie", "7.7.7.7")["captcha"])

# 容量账：账户维内存估算
daily_users, bytes_per_entry = 1_000_000, 120
print("user-dim RAM ~", daily_users * bytes_per_entry // 1024 // 1024, "MB（进程内可行需 Redis 视规模）")
```

**追问一**：为什么渐进延迟不能无限加大？——延迟占用的是**登录 worker/连接**（或 Redis 忙等），攻击者拖高全局延迟等于资源放大攻击；封顶（如 10s）+ 延迟在"响应侧"实现（返回后客户端等待）而非服务端 sleep，才不占服务资源。

**追问二**：锁定状态存 Redis 的 key 设计与淘汰策略？——`lock:{user}` 与 `rl:{ip}:{window_bucket}` 都带 TTL（TTL 即锁定时长/窗口），不手动清理；IP 维防攻击要考虑 key 数量爆炸（百万伪造 IP），用"近 N 窗口计数 + 大 key 上限 + 全局溢出即升级 CAPTCHA"三级降级，避免 Redis 本身被打爆。

## 背诵要点
- 纯账户硬锁会被反向利用：锁定成本 = 用户数 × N，防刷变 DoS；账户维只做渐进延迟（封顶），硬限流放 IP 维。
- password spraying 绕过单账户阈值，必须全局维度检测（失败总量 → CAPTCHA 风险分）。
- 存储：user 维 ~100B/日活可进程内，ip 维可能百万 key 必须带 TTL 的 Redis + 三级降级。
