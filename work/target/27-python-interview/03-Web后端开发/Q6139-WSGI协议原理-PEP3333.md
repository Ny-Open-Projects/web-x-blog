### Q6139 · WSGI 协议原理：PEP 3333 的 environ 与 start_response

难度：P6-P7 | 标签：WSGI、PEP 3333、原理深挖、中间件

**问**：PEP 3333 定义的 WSGI 可调用对象契约具体是什么？`start_response` 为什么设计成回调而不是返回值？响应体为什么要求返回可迭代对象？`close()` 与生成器的关系是什么？这套设计如何支撑中间件洋葱模型？

**答**：

**结论**：WSGI 应用是一个可调用对象 `application(environ, start_response)`：`environ` 是 CGI 风格的字典（请求元数据：REQUEST_METHOD、PATH_INFO、wsgi.input 文件对象等，键全部大写 str），`start_response(status, response_headers, exc_info=None)` 是服务端注入的回调，应用必须在返回可迭代响应体**之前**调用它声明状态与头。三个设计决策都有原因：(1) start_response 用回调而非返回值，是为了支持"应用开始产出响应体后才确定状态/头"的流式场景与 exc_info 错误改写（调用两次 start_response 替换头）；(2) 响应体必须是可迭代对象而非 bytes——服务端按块传输（chunked/写 socket），生成器可边产边发降低内存；(3) 若响应体是带 `close()` 的迭代器（生成器），服务端完成发送后必须调用 `close()`，释放生成器资源——忘记实现 close 是 WSGI 中间件持有资源的经典 bug。中间件模型：中间件是"包了一层的应用"，入参同名调用内层，可以改写 environ、拦截 start_response、包装响应体迭代器，天然洋葱结构。

**取舍**：WSGI 的同步本质（每个请求占一个线程）决定了它与 WebSocket/长连接不兼容——这是 ASGI 出现的原因；但 WSGI 的简单契约让它 20 年不衰：gunicorn/uwsgi 与 Flask/Django 2.x 的同步视图都活在这套协议上。

**实战**：手写一个最小 WSGI 应用 + 记录耗时中间件 + 用 wsgiref 跑起来，能看清协议全貌；排查生产问题时理解 `wsgi.input`（已读 body 流）与中间件包装顺序（最外层最先看到请求）是基本功。

```python
import time
from wsgiref.simple_server import make_server, WSGIRequestHandler

def timing_middleware(app):
    def middleware(environ, start_response):
        t0 = time.perf_counter()
        def custom_start_response(status, headers, exc_info=None):
            elapsed = (time.perf_counter() - t0) * 1000
            headers = list(headers) + [
                (f"X-Process-{'Ms'}", f"{elapsed:.2f}")]   # 注入响应头
            return start_response(status, headers, exc_info)
        body_iter = app(environ, custom_start_response)
        try:
            yield from body_iter          # 包装响应体：逐块转发
        finally:
            close = getattr(body_iter, "close", None)
            if close:
                close()                   # PEP 3333：必须传播 close
    return middleware

def app(environ, start_response):
    body = b"hello wsgi"
    start_response("200 OK", [
        ("Content-Type", "text/plain"),
        ("Content-Length", str(len(body))),
    ])
    # 返回生成器：演示"可迭代响应体 + close 语义"
    yield body

class QuietHandler(WSGIRequestHandler):
    def log_message(self, *a): pass

if __name__ == "__main__":
    srv = make_server("127.0.0.1", 0, timing_middleware(app),
                      handler_class=QuietHandler)
    port = srv.server_address[1]
    threading_runner = __import__("threading")
    t = threading_runner.Thread(target=srv.serve_forever, daemon=True)
    t.start()

    import urllib.request
    with urllib.request.urlopen(f"http://127.0.0.1:{port}/x") as r:
        print("status ->", r.status)
        print("timing header ->", r.headers.get("X-Process-Ms"))
        print("body ->", r.read())
    srv.shutdown()
```

**追问 1**：`start_response` 的返回值是什么？为什么中间件要接住它？
答：返回一个 `write(data)` 可调用，用于绕过迭代器"直接推块"的老式路径（如文件直传）；中间件拦截 start_response 时必须原样返回 write，否则破坏协议。

**追问 2**：environ 里 `wsgi.input` 读 body 有什么坑？
答：按 Content-Length 读还是读到 EOF 依赖服务器实现，某些服务器（如 gunicorn 的特定 worker）在 keep-alive 下未读尽 body 会破坏下一个请求解析——中间件读 body 后必须精确消费 Content-Length 字节。

**追问 3**：WSGI 应用如何做流式响应（大文件下载）？
答：返回文件包装的迭代器（块大小 64KB），配合 `os.sendfile` 或让服务器走 X-Accel/X-Sendfile 卸载给网关——应用层只给路径，避免应用进程内存与带宽被占满。

## 背诵要点

- 契约：application(environ, start_response)，先调回调声明状态头，再返回可迭代响应体，服务端负责 close()。
- 设计原因：回调支持流式/改写头（exc_info 二次调用）；可迭代体支持边产边发；close 传播防资源泄漏。
- 中间件 = 包装应用的可调用（改 environ/包 start_response/包迭代器）；WSGI 同步模型催生 ASGI。
