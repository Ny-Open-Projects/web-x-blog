### Q5585 · 协程与线程切换的成本账：实测方法论

难度：★★★★☆ ｜ 标签：上下文切换 / 成本工程 / asyncio / 基准方法

**问**："协程切换比线程快一个数量级"这句话怎么实测证明？ping-pong 基准里协程切换和线程切换各自的真实成本构成是什么？哪些因素会让这个数量级结论失真？

**答**：
- **结论**：成本构成不同——**线程切换** = 内核态调度（syscall + 调度器决策 + 缓存/TLB 影响）+ GIL 释放/获释的同步开销，Python 线程 ping-pong 一次往返通常在 10-50µs 量级；**协程切换** = 纯用户态的 Task/生成器 yield（保存恢复帧指针、切换就绪队列），一次 await 往返约 0.1-1µs（uvicorn/uvloop 下更低）。实测标准做法是**双向 ping-pong N 轮**：两方交替 `event.wait/set`（线程）或 `asyncio.Event`（协程），总时间 ÷ (2N) 得单次切换成本。失真因素：① 3.12+ 协程有 eager start（Q5502），首启不产生切换，基准要排除；② 线程数超过核数后 OS 抢占混入，量的是调度不是切换；③ GIL 的 `setswitchinterval` 会改变线程让出节奏，基准结论随之漂移。
- **取舍**：切换成本只是选型的一维：协程的优势在**每连接内存**（KB 级 vs 线程 MB 级）与调度无锁；线程的优势在阻塞库兼容与真并行（配合释放 GIL 的 C 代码）。架构决策常被"切换 10 倍差"带偏——真正决定吞吐的是 IO 等待占比与每连接内存，切换成本只在每秒百万级切换时才成为主项。
- **实战**：基准纪律：固定 CPU 亲和性（macOS 上至少记录负载）、预热、多次取中位数、`time.perf_counter` 计时、报告机器与 Python 版本；线程基准还要在 `sys.setswitchinterval` 多档位下跑，验证结论稳健性。

```python
"""线程 vs 协程 ping-pong 切换成本实测（macOS，Python 3.12，标准库）"""
import threading, asyncio, time, sys

ROUNDS = 20_000

def thread_pingpong(rounds):
    """两个线程经 Event 交替，量一次切换"""
    ta, tb = threading.Event(), threading.Event()
    done = threading.Event()
    def player(wait_ev, set_ev):
        for _ in range(rounds):
            wait_ev.wait()
            wait_ev.clear()
            set_ev.set()
        done.set()
    p1 = threading.Thread(target=player, args=(ta, tb), daemon=True)
    p2 = threading.Thread(target=player, args=(tb, ta), daemon=True)
    p1.start(); p2.start()
    t0 = time.perf_counter()
    ta.set()
    done.wait(timeout=30)
    dt = time.perf_counter() - t0
    return dt / (2 * rounds) * 1e6      # µs / 单次切换

def coroutine_pingpong(rounds):
    async def main():
        ev_a, ev_b = asyncio.Event(), asyncio.Event()
        async def player(wait_ev, set_ev):
            for _ in range(rounds):
                await wait_ev.wait()
                wait_ev.clear()
                set_ev.set()
        t1 = asyncio.create_task(player(ev_a, ev_b))
        t2 = asyncio.create_task(player(ev_b, ev_a))
        t0 = time.perf_counter()
        ev_a.set()
        await asyncio.gather(t1, t2)
        dt = time.perf_counter() - t0
        return dt / (2 * rounds) * 1e6
    return asyncio.run(main())

for si in ("default", "0.0005", "0.02"):
    if si != "default":
        sys.setswitchinterval(float(si))
    t = min(thread_pingpong(ROUNDS) for _ in range(3))
    c = min(coroutine_pingpong(ROUNDS) for _ in range(3))
    print(f"switchinterval={si:<7} 线程单次切换 ≈ {t:8.2f} µs | 协程 ≈ {c:6.2f} µs | 比值 ≈ {t/c:.0f}×")
    if si != "default":
        sys.setswitchinterval(0.005)    # 复位默认

print("结论骨架：协程切换为用户态 0.1-1µs 量级，线程为内核态数十 µs 量级（具体数字以本机为准）")
```

**追问链**
1. 为什么线程 ping-pong 的时间大头其实是 GIL 而不是内核调度？
   1. 每次 Event 往返要经历"释放 GIL → 对方 acquire GIL"两次解释器级同步，加上内核 futex 唤醒；把 `setswitchinterval` 调大可减少 GIL 抢占噪声，数值会明显下降——说明结论对解释器参数敏感，基准要扫参。
   2. 追问：free-threading（3.13+）构建下这个基准会怎样？——GIL 消失后线程切换回归纯内核成本，但对象级同步（mprotect/原子操作）进入成本项，比值结构改变，旧结论必须重测。
2. eager task factory 为什么会污染协程切换基准？怎么排除？
   1. `asyncio.eager_task_factory`（3.12+）让 `create_task` 在当前调用栈内直接跑到第一个挂起点，省掉"入队再调度"一次往返；基准里首启段没有切换却计入了时间。排除法：预跑若干轮进入稳态，或显式换回默认 factory 后计时。
   2. 追问：生产上如何观测真实切换频率？——`-X dev` 下跟踪 `await` 延迟、或 py-spy 看 task 队列深度；每秒切换数 = 挂起/恢复事件速率，可用自定义 Task 工厂计数。

## 背诵要点
- 线程切换 = 内核调度 + GIL 同步，数十 µs 量级；协程切换 = 用户态帧切换，0.1-1µs 量级；ping-pong ÷ 2N 是标准测法。
- 结论对 setswitchinterval、eager_task_factory、线程数/核数比敏感，基准必须扫参并报环境。
- 选型主看 IO 等待占比与每连接内存，切换成本只在每秒百万级切换时成为主项。
