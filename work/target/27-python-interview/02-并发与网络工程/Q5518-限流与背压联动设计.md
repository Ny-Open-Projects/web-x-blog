### Q5518 · 客户端限流与服务端背压联动

> 难度:★★★ | 标签:限流, 背压, QoS

**问**：客户端 SDK 要调用一个限流 100 QPS 的下游：客户端令牌桶限流 + 并发上限 + 队列三者怎么配？服务端返回 429/Retry-After 时客户端怎么反应才是「好的公民」？为什么「只重试 3 次」的固定策略在大流量下会形成重试风暴？

**答**：客户端三闸门：① **速率闸**（令牌桶，目标速率 × 0.9 留余量）；② **并发闸**（同时 in-flight 请求上限——速率高但下游慢时，无并发闸会把连接池/内存撑爆）；③ **队列闸**（等待中的请求有界 + 排队超时，超过即快速失败）。429 反应协议：读到 `Retry-After` 就**服从**（哪怕自己令牌桶还没到点），并且**全局共享**重试预算——所有线程共享一个预算池，防止「每个线程都重试 3 次 = N×3 倍流量」。重试风暴的成因：下游 50% 请求失败 → 全部客户端立即重试 → 流量瞬时 ×2~3 → 下游更糟 → 更多失败 → 指数放大。正确做法：指数退避 + 抖动 + **重试预算熔断**（预算耗尽直接失败不重试，等下游恢复）。

```python
# 全部标准库；demo 演示三闸门 + 重试预算联动
import threading, time, random

class RateLimiter:
    """令牌桶 + 全局重试预算（客户端好公民协议）。"""
    def __init__(self, rate: float, retry_budget_ratio: float = 0.2):
        self.rate, self.tokens, self.last = rate, rate, time.monotonic()
        self.lock = threading.Lock()
        self.recent_total = 10
        self.recent_retries = 0
        self.budget_ratio = retry_budget_ratio

    def acquire(self, cost: float = 1.0) -> bool:
        with self.lock:
            now = time.monotonic()
            self.tokens = min(self.rate, self.tokens + (now - self.last) * self.rate)
            self.last = now
            if self.tokens >= cost:
                self.tokens -= cost
                return True
            return False

    def can_retry(self) -> bool:
        """重试预算：重试数不超过近期总请求的 20%——下游劣化时自动停止重试。"""
        with self.lock:
            return self.recent_retries <= self.recent_total * self.budget_ratio

    def record(self, retried: bool):
        with self.lock:
            self.recent_total += 1
            if retried:
                self.recent_retries += 1
            # 简化衰减：总量每 1000 重置（真实实现用滑动窗口）
            if self.recent_total > 1000:
                self.recent_total, self.recent_retries = 10, 0

def call_with_gates(limiter: RateLimiter, inflight_sem: threading.Semaphore,
                    url: str, max_queue_wait: float = 2.0) -> str:
    deadline = time.monotonic() + max_queue_wait
    if not inflight_sem.acquire(timeout=max_queue_wait):    # 闸门②③：并发+排队超时
        raise TimeoutError("排队超时，快速失败")
    try:
        for attempt in range(3):
            while not limiter.acquire():                     # 闸门①：速率
                if time.monotonic() > deadline:
                    raise TimeoutError("总预算耗尽")
                time.sleep(0.01)
            ok = attempt == 0 and random.random() > 0.5 or random.random() > 0.3
            limiter.record(retried=attempt > 0)
            if ok:
                return "200"
            if attempt < 2 and limiter.can_retry():          # 预算允许才重试
                time.sleep(min(0.05 * 2 ** attempt + random.random() * 0.01, 1))
                continue
            return "503-fast-fail"                           # 预算耗尽：不重试直接失败
        return "503"
    finally:
        inflight_sem.release()

if __name__ == "__main__":
    random.seed(7)
    lim = RateLimiter(rate=50)
    sem = threading.Semaphore(10)                            # 并发闸：in-flight ≤ 10
    results = {}
    ts = []
    def run():
        try:
            r = call_with_gates(lim, sem, "http://downstream")
        except TimeoutError as e:
            r = str(e)
        results[r] = results.get(r, 0) + 1
    for _ in range(200):
        th = threading.Thread(target=run); th.start(); ts.append(th)
    [t.join() for t in ts]
    print("结果分布:", results)
    # 重试预算生效：下游劣化时 503-fast-fail 占比上升，而不是 200 次全量重试打爆下游
```

**追问**：1) Retry-After 的单位有哪些？——秒数或 HTTP-date；客户端解析两种并取「更保守」的值；忽略它硬重试是对方熔断你的直接理由。2) 为什么预算比率 20%？——经验值（Finagle/Envoy 惯例）：正常偶发失败下重试占比远低；一旦接近 20% 说明下游系统性劣化，继续重试只会放大故障。3) 服务端背压信号除了 429 还有什么？——503、连接拒绝、响应变慢（延迟本身就是背压信号，延迟驱动的客户端熔断见 A106）。

## 背诵要点
1. 客户端三闸门：令牌桶速率（×0.9 余量）+ in-flight 并发上限 + 有界排队超时。
2. 429 处理协议：服从 Retry-After + **全局共享**重试预算（≤ 近期总量 20%），预算耗尽直接快速失败。
3. 重试风暴 = 失败×立即重试×N 线程倍增；退避+抖动+预算三件套是标准解。
