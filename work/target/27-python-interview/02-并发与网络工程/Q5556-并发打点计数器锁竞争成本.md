### Q5556 · 热路径指标打点的锁竞争成本工程

> 难度:★★★★ | 标签:锁竞争, metrics, threading.Lock, 分片, 成本工程

**问**：给每请求加"计数器+1"打点后，压测 QPS 掉了 30%。一次 `with lock: counter += 1` 到底贵在哪？为什么改成 4 个分片锁收益不明显？热路径指标的正确写法是什么？

**答**：先拆成本：裸的 `counter += 1` 在 GIL 下本身不安全但也不"慢"（字节码几条）；慢的是**锁的语义**——`with lock` 的 acquire/release 各是一次原子操作加可能的内核级等待，且 `counter += 1` 临界区里的 LOAD/STORE 会在锁内串行化。QPS 掉 30% 的真正放大器通常不是锁本身，而是：a) 临界区里混进了 IO（先确认没有）；b) **锁保护的对象成了共享热点**，所有线程在同一条缓存行上 bouncing（伪共享）；c) 打点函数里做了格式化/字典分配（比锁贵）。分片锁收益不明显的实证：纯内存递增下 4 分片与单锁实测几乎持平（GIL 本来就把执行串行化了，锁竞争只在临界区含阻塞或释放 GIL 的 C 调用时才真贵）。正确姿势按热度分档：a) 中低频（每秒千次以内）——单锁足够，别过度设计；b) 高频——**每线程/每协程局部累计，读时合并**（完全无锁，GIL 下 += 在纯 Python 对象上虽有竞态但局部累计连竞态都没有）；c) 跨进程/释放 GIL 的 C 层——分片锁或原子（C 扩展）。迁移到成熟库就是 prometheus_client 的多进程模式/直方图聚合。一句话：**先证明锁是瓶颈再优化锁；GIL 时代多数"锁竞争"是伪瓶颈**。

```python
# file: code/02_并发与网络工程/q5556_metrics_cost.py
import threading, time

WORKERS, PER = 4, 20_000

# 1) 基线: 单锁计数
def bench_lock():
    c, lock = 0, threading.Lock()
    def inc():
        nonlocal c
        for _ in range(PER):
            with lock:
                c += 1
    ts = [threading.Thread(target=inc) for _ in range(WORKERS)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    return time.perf_counter() - t0, c

# 2) 分片锁: 4 个独立锁
def bench_shard():
    shards = [[0, threading.Lock()] for _ in range(WORKERS)]
    def inc(w):
        for _ in range(PER):
            with shards[w][1]:
                shards[w][0] += 1
    ts = [threading.Thread(target=inc, args=(w,)) for w in range(WORKERS)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    return time.perf_counter() - t0, sum(s for s, _ in shards)

# 3) 正解: 每线程局部累计, 读时合并(无锁无竞态)
def bench_local():
    totals = [0] * WORKERS
    def inc(w):
        c = 0
        for _ in range(PER):
            c += 1
        totals[w] = c
    ts = [threading.Thread(target=inc, args=(w,)) for w in range(WORKERS)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    return time.perf_counter() - t0, sum(totals)

t1, c1 = bench_lock(); t2, c2 = bench_shard(); t3, c3 = bench_local()
print(f"纯递增 {PER*WORKERS} 次: 单锁 {t1*1000:.0f}ms | 分片4锁 {t2*1000:.0f}ms | 局部累计 {t3*1000:.0f}ms")
print("计数一致性:", c1 == c2 == c3 == PER * WORKERS)
print("GIL 下纯内存递增三档差距小: 锁竞争大头在临界区混入 IO/释放 GIL 的 C 调用或跨进程")
print("热路径结论: 局部累计+读时合并; 中低频直接单锁; 分片锁留给多进程/无 GIL 场景")
```

**追问**：1) GIL 下 `counter += 1` 不加锁会怎样？——`+=` 是多字节码（LOAD/ADD/STORE），线程切换可插在中间丢更新；虽然 CPython 3.10+ 的 eval breaker 时机让小函数里更难复现，这是**时序巧合不是保证**，竞态代码必须锁或局部累计。2) prometheus_client 的 Counter 在多线程/多进程下怎么工作？——线程内用锁/聚合，多进程模式靠每个进程写自己的 exposition 文件由抓取端合并；这也是"局部累计+读时合并"的工程化版本。3) 怎么证明打点是瓶颈而不是业务？——对照压测：同一分支开关打点跑 A/B；py-spy 看锁等待栈（GIL wait 占比）；把打点改成局部累计后 QPS 恢复即是实锤。

## 背诵要点
- `with lock` 贵在 acquire/release 原子操作+串行化，热点缓存行 bouncing 与临界区 IO 才是 30% 掉速的真凶。
- GIL 下纯内存递增：单锁≈分片锁≈局部累计（实测几十 ms 档），分片锁的真实收益在多进程/释放 GIL/C 层。
- 热路径正确姿势：每线程局部累计、读时合并（无锁无竞态）；先 A/B 证明锁是瓶颈再优化。
