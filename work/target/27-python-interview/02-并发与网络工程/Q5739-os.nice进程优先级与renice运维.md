### Q5739 · os.nice 与进程优先级：谦让值、调度份额与 renice 运维

难度：P5 ｜ 标签：os.nice、nice 值、getpriority、进程优先级、CPU 争抢、renice、容器配额、调度

**问**：nice 值的方向是"越 nice 越让"，还是越大越优先？`os.nice(n)` 与 `os.getpriority(os.PRIO_PROCESS, 0)` 怎么用？为什么"提高优先级（负 nice）"需要 root？后台批处理进程怎么用 nice 让出在线服务？容器/K8s 里 nice 与 CPU limit 的关系是什么？

**答**：
结论：nice 是 Unix 调度的**谦让值**：范围 -20（最不谦让、优先级最高）到 +19（最谦让、优先级最低），默认 0——**越大越让**，普通进程只能"变谦让"（os.nice(n)，n>0），要"变强势"（负值、降低现有值）需要 root 权限（CAP_SYS_NICE），这个单向性是刻意的自我保护设计：进程只能自愿让，不能抢。Python 侧两个 API：`os.nice(increment)` 以**增量**调整当前进程（返回新值），`os.getpriority(os.PRIO_PROCESS, pid)` 读取目标进程 nice（PRIO_PROCESS=0 表示自身）。工程用途分层：①**同机混部**：批处理/离线计算进程 `os.nice(10)` 起步，让 CPU 调度器在争抢时优先喂在线服务——这是不引入 cgroup 时的最轻量"错峰"手段；②**监控诊断**：`getpriority` 巡检各 worker 的 nice 是否被误设；③**运维视角**：renice 命令对已跑进程改值，"正在失控的进程"先 nice 再 kill，给它邻居留活路。关键边界：nice 只在 **CPU 争抢时生效**——CPU 空闲时高 nice 进程照样吃满核，它不是限速器；容器里 CPU limit（CFS quota）与 nice 是两层不同机制：quota 硬截总量、nice 只决定"谁多让谁"。

取舍：a) 单机多服务（无容器）：在线服务默认 0、离线任务 nice(10-19)——最简单有效的混部治理；b) K8s 内：Pod 内进程建议用 nice 做 Pod 内多进程的相对让度（如 sidecar 让主容器），跨 Pod 隔离交给 cgroup（CPU request/limit，Q5657）；c) 想真正限制 CPU 量：nice 不是答案——cpu limit/cgroup/cpu-time 预算（Q5657/Q6042）才是；d) 提升优先级：root + os.setpriority，或调度策略 SCHED_BATCH/SCHED_IDLE（Linux 专属）表达"我接受更晚被调度"——比负 nice 语义更干净；e) 线程与进程：nice 是进程（或 Linux 上的线程组）级属性，Python 线程共享 nice——想给某线程让度做不到，要隔离就拆进程。

实战：事故形态是"同一台机器跑在线 API 与夜间画像计算，白天画像任务没退出，在线接口 CPU 排队延迟飙升——给画像任务 os.nice(15) + 运维 renice 巡检后，争抢时调度器优先喂在线进程，P99 恢复；同时发现 nice 在 CPU 空闲时无效的预期误差，补了'nice 不是限速器'的容量认知到 runbook"。下面实测 nice 的读写与权限边界。

```python
# os.nice 与进程优先级
import os
import subprocess
import sys

print("[1] 读当前进程 nice: getpriority(PRIO_PROCESS, 0)")
base = os.getpriority(os.PRIO_PROCESS, 0)
print("    当前 nice =", base, "(默认 0, 范围 [-20, +19], 越大越谦让)")

print("[2] os.nice 是增量: 正数=更谦让(无需特权), 负数=更强势(需要 root)")
new = os.nice(5)
print("    os.nice(5) ->", new, "(普通用户只能变谦让)")
try:
    os.nice(-5)                                   # 降低 nice 需要 root
    os.nice(5)                                    # 若成功, 复位演示继续用谦让值
    print("    os.nice(-5) -> 成功 (当前是 root)")
except PermissionError as e:
    print("    os.nice(-5) -> PermissionError:", e, "(非 root 不能抢; 单向谦让是刻意设计)")

print("[3] 子进程继承父进程 nice: 批处理降级的传承链")
r = subprocess.run([sys.executable, "-c", "import os; print(os.getpriority(os.PRIO_PROCESS, 0))"],
                   capture_output=True, text=True)
print("    父进程 nice =", os.getpriority(os.PRIO_PROCESS, 0), "| 子进程继承 =", r.stdout.strip())
print("[4] nice 只在 CPU 争抢时生效: 它不是限速器")
print("    空闲机器: nice(19) 的进程照样吃满核; 争抢时: 调度器优先喂低 nice 进程")
print("    真要限制 CPU 量 -> cgroup cpu limit (K8s 的 CPU limit), 与 nice 是两层机制")

print("[5] 运维组合拳: renice 对已跑进程改值, '先让再杀'")
print("    失控进程处理: renice +15 -p <pid> 给邻居留活路 -> 定位 -> 再 kill")
print("[6] 边界: nice 是进程级属性, Python 线程共享 nice; 线程级隔离只能拆进程")
```

**追问一**：nice 的"谦让份额"在 CFS 调度器下到底怎么量化？+5 与 +10 的差距是多少？—— CFS（完全公平调度器）把 nice 转成**权重**：每级 nice 约差 1.25 倍权重（Linux 内核 `sched_prio_to_weight` 表，nice 0=1024、+5≈335、+10≈110、+19≈15）。两个进程争抢同一 CPU 时，分到的 CPU 时间 ≈ 各自权重占比——nice 0 对 nice 10 的份额约 1024:110 ≈ 10:1，即"谦让 10 级 ≈ 让出约 90% 的争抢份额"。理解量化关系就能精确治理：想让批处理只拿"在线服务 1/10 的争抢份额"，nice(10)；想要更彻底让度（几乎白给），nice(19)（权重 15，≈1:68）。这也解释了"nice 不是限速器"：份额比例只在**有争抢**时起作用，独占窗口期谁都能跑满。

**追问二**：容器里 nice 与 cgroup CPU limit/weight 的关系？K8s 上该在哪一层做"让度"？—— 两层正交机制：①**cgroup 层**（K8s 的 CPU request/limit、cpu.weight）：控制"这个 Pod 相对其它 Pod 能拿多少"——limit 硬截单 Pod 总量（quota 用满即被 throttle，Q6042 OOMKilled 同族的 throttle 行为），weight（由 request 推导）管争抢份额；②**进程层 nice**：控制 Pod **内部**多进程的相对让度——sidecar、日志压缩、备份任务用 nice(10+) 让主进程优先。K8s 上的分层原则：跨 Pod 治理用资源配额（request/limit + Pod QoS class），Pod 内治理用 nice/调度策略——在 Pod 内用 nice 想跨 Pod 让度是无效的（namespace 下各 Pod 由 cgroup 分配）；反过来用 limit 做 Pod 内进程间细分也做不到（limit 是 Pod 总量）。边界认知：Nice 在容器内默认可设（CAP_SYS_NICE 不必需，因为只谦让不抢），但会受 Pod securityContext 限制——平台差异进 runbook。

## 背诵要点
- nice 范围 [-20,+19]，越大越让；os.nice(increment) 只能谦让（负增量需 root）；getpriority(PRIO_PROCESS, 0) 读自身。
- CFS 量化：每级 nice ≈ 1.25 倍权重，nice0:nice10 ≈ 10:1；nice 只在 CPU 争抢时生效，不是限速器（限速用 cgroup limit）。
- 子进程继承 nice；nice 是进程级属性线程共享；K8s 分层：跨 Pod 用 request/limit，Pod 内用 nice。

## 复盘追问
- 混部机器在线服务被批处理挤慢，怎么用 nice 治理？（批处理 os.nice(10~19)，CFS 权重让出争抢份额；renice 巡检已跑进程）
- 为什么说 nice 不是限速器？（CPU 空闲时高 nice 进程照样吃满核；只有争抢时份额比例生效，限量要 cgroup）
