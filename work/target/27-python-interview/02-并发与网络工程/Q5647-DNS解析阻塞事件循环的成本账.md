### Q5647 · DNS 解析阻塞事件循环的成本账

难度：P6 ｜ 标签：DNS、getaddrinfo、asyncio、成本工程

**问**：asyncio 服务高峰期整个事件循环间歇性停顿 1-5 秒，py-spy 显示栈在 `socket.getaddrinfo`。为什么"IO 密集"的 asyncio 会被 DNS 拖住？`getaddrinfo` 的成本构成是什么？工程上怎么把这笔账算清楚并消除毛刺？

**答**：
结论：`getaddrinfo`（解析主机名→地址族候选列表）是**阻塞 C 调用**，不经事件循环调度；asyncio 的 `loop.create_connection` 底层仍走它（默认在 executor 线程池跑，但若你直接在协程里调 `socket.getaddrinfo` 就是裸阻塞）。它的成本构成：① 本地 hosts/缓存命中 <1ms；② resolv 链路超时（nameserver 无响应时，默认策略可累计 5s×重试次数）；③ IPv6/IPv4 双栈串行尝试（AF_UNSPEC 返回候选但连接阶段可能逐个试）；④ musl/glibc 解析器差异（容器里 Alpine 的 musl 不读 nscd、并发查询行为不同）。

取舍：消除路径优先级——① 进程内 DNS 缓存（TTL 尊重 + 上限）；② 用 IP 直连 + 服务发现层做解析（K8s 下 Service DNS 已有 kube-dns 缓存，业务层再缓存要防"漂移期过长"）；③ 把解析放独立 executor/进程隔离毛刺；④ aiodns（c-ares）真异步解析，注意 c-ares 不走 nsswitch（hosts 文件等差异）。

实战：成本账方法——压测期打点 `getaddrinfo` 耗时分布（P50/P99），与请求总耗时相减看占比；解析 QPS 与缓存命中率推导"每秒真实出网查询数"，对照 resolv.conf 的 nameserver 容量。告警线：解析 P99 > 200ms 即排入治理。

```python
import asyncio
import socket
import time
import statistics

# 1) 阻塞成本打点：localhost 命中本地配置，毫秒级；真实外网域名才暴露超时链路
def probe(host: str) -> float:
    t0 = time.perf_counter()
    infos = socket.getaddrinfo(host, 443, proto=socket.IPPROTO_TCP)
    dt = (time.perf_counter() - t0) * 1000
    print(f"getaddrinfo({host}): {dt:.2f}ms, {len(infos)} candidates")
    return dt

probe("localhost")
probe("example.com")

# 2) asyncio 正确姿势：loop.getaddrinfo 落到默认 executor，不阻塞循环
async def amain():
    loop = asyncio.get_running_loop()
    t0 = time.perf_counter()
    infos = await loop.getaddrinfo("example.com", 443)
    print(f"async loop.getaddrinfo: {(time.perf_counter()-t0)*1000:.2f}ms")

asyncio.run(amain())

# 3) 进程内 TTL 缓存（带条数上限），削掉重复解析
class DnsCache:
    def __init__(self, ttl: float = 60.0, cap: int = 1024):
        self.ttl, self.cap, self._d = ttl, cap, {}

    def get(self, host: str):
        hit = self._d.get(host)
        if hit and hit[0] > time.monotonic():
            return hit[1]
        return None

    def put(self, host: str, addrs):
        if len(self._d) >= self.cap:            # 简单过期清扫，防缓存无界
            now = time.monotonic()
            self._d = {k: v for k, v in self._d.items() if v[0] > now}
        self._d[host] = (time.monotonic() + self.ttl, addrs)

cache = DnsCache()
def resolve_cached(host):
    r = cache.get(host)
    if r is None:
        r = [i[4][0] for i in socket.getaddrinfo(host, 443, proto=socket.IPPROTO_TCP)]
        cache.put(host, r)
        print("miss -> resolved:", r[:2])
    else:
        print("hit ->", r[:2])
    return r

resolve_cached("example.com")
resolve_cached("example.com")

# 4) 批量解析的耗时分布（毛刺观测）
times = []
for h in ["localhost"] * 20:
    t0 = time.perf_counter()
    socket.getaddrinfo(h, 443)
    times.append((time.perf_counter() - t0) * 1000)
print(f"p50={statistics.median(times):.2f}ms p100={max(times):.2f}ms over {len(times)} lookups")
```

**追问一**：为什么 asyncio 默认把 getaddrinfo 丢线程池仍可能拖慢全局？——默认 executor 容量有限（min(32, cpu+4)），解析高峰把线程池占满，其他 `to_thread`/`run_in_executor` 任务排队，表现为"循环没死但整体变慢"；要给 DNS 单独一个 executor 隔离。

**追问二**：aiodns（c-ares）与系统解析器的语义差异会踩什么坑？——c-ares 不完全遵循 nsswitch（`/etc/hosts` 行为要额外配、不支持某些 NSS 插件如 LDAP 解析）；容器/办公网环境切换前必须做解析一致性对照测试。

**追问三**：K8s 里 5s DNS 超时五连击是什么？——musl 的并行查询是修复，glibc 串行 + `ndots:5` 展开导致大量无意义查询；治理：缩短 `ndots`、Service FQDN 尾点、NodeLocal DNSCache，属于平台层与代码层配合的容量工程。

## 背诵要点
- `getaddrinfo` 是阻塞 C 调用；协程里直调会冻结事件循环，`loop.getaddrinfo` 默认走共享 executor，高峰会挤占其他任务。
- 成本四项：本地缓存命中、resolv 超时链（可累计 5s×重试）、双栈串行、musl/glibc 差异。
- 治理优先级：TTL 缓存 > IP 直连/服务发现 > 独立 executor 隔离 > aiodns（注意 nsswitch 差异）。
