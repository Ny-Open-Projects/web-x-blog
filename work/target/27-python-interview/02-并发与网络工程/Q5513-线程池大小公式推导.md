### Q5513 · 线程池大小的公式化推导

> 难度:★★☆ | 标签:线程池, 容量规划

**问**：「线程池开多大」被问烂了，但面试官要的是推导过程：I/O 密集与 CPU 密集的公式分别是什么？公式给出 N 后为什么还要实测校准——Python 下 GIL/no-GIL 两个构建怎么改这套公式？

**答**：经典推导：**CPU 密集**：`threads = cores + 1`（+1 是为了在偶发页错误/缓存失效时填满流水线）；**I/O 密集**：`threads = cores × (1 + wait/compute)`（等待时间占比越高，可并发越多）。但公式只是**起点**，实测校准看三个指标：① 下游 P99（线程多了把下游打挂）；② 自身队列积压与延迟分布（线程少了排队暴涨）；③ 上下文切换成本（`cs`/s 暴涨说明超开）。Python 特殊性：**GIL 构建下 CPU 密集线程根本不并行**，公式退化为「线程数对 CPU 任务无意义，换 multiprocessing」；I/O 密集在等待时释放 GIL，公式近似成立但 wait/compute 要按「释放 GIL 的等待」算（纯 Python 的 sleep/协程切换不算）。no-GIL 构建下 CPU 公式重新成立但锁争用会吃掉理论收益，超开要更保守。

```python
# 全部标准库；demo 实测 GIL 下 CPU 任务的线程「假并行」与 I/O 任务真收益
import time, threading
from concurrent.futures import ThreadPoolExecutor

def cpu_task(n=2_000_000):
    s = 0
    for i in range(n):
        s += i * i
    return s

def io_task():
    time.sleep(0.1)            # 等待时释放 GIL（真睡眠是 C 级释放）
    return "ok"

def bench(pool_size, task, jobs=8):
    with ThreadPoolExecutor(max_workers=pool_size) as ex:
        t0 = time.perf_counter()
        list(ex.map(lambda _: task(), range(jobs)))
        return time.perf_counter() - t0

if __name__ == "__main__":
    import os
    cores = os.cpu_count() or 4
    # CPU 密集：GIL 下 1 线程 ≈ 8 线程（无收益），证明公式在 GIL 构建失效
    t1, t8 = bench(1, cpu_task), bench(8, cpu_task)
    print(f"CPU 任务: 1线程={t1:.2f}s 8线程={t8:.2f}s（GIL 下 ≈，no-GIL 下应 <）")
    # I/O 密集：wait/compute ≈ 99，理论上 8 线程应把 8 个任务压到 ~0.1s
    t1io, t8io = bench(1, io_task), bench(8, io_task)
    print(f"I/O 任务: 1线程={t1io:.2f}s 8线程={t8io:.2f}s（≈ 单任务耗时，真并行）")
    assert t8io < t1io
    # 推导记录：wait=0.1 compute≈0 → threads = cores×(1+99)；但下游限流才是真实上限，
    # 实测校准看下游 P99，本例 io_task 没有下游，纯 sleep 只演示「等待释放 GIL」。
```

**追问**：1) 为什么 CPU 密集是 `cores+1` 而不是 `cores`？——经典解释是「偶发阻塞时保持 CPU 满载」，现代多级缓存下收益趋零，公式是历史口径；真正要实测让 CPU 利用率到 90%+ 且 cs 不爆。2) 队列怎么配？——`ThreadPoolExecutor` 用无界队列（危险：上游不限速时 OOM）；生产用有界队列 + 满时拒绝策略（快速失败/降级），见 Q5506 背压。3) no-GIL 下这套公式怎么改？——CPU 公式成立但热临界区锁争用主导，实测看 `perf` 里的 lock contention；I/O 公式不变。

## 背诵要点
1. CPU 密集 cores+1、I/O 密集 cores×(1+wait/compute)——公式是起点，实测校准看下游 P99/队列/上下文切换。
2. GIL 构建下 CPU 公式失效（线程假并行），换 multiprocessing；I/O 收益来自等待释放 GIL。
3. 无界队列是 OOM 陷阱：有界 + 拒绝策略才完整。
