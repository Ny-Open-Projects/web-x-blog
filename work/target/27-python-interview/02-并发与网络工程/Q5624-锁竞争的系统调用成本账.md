### Q5624 · 锁竞争的系统调用成本账：fast path 与 futex

> 难度:★★★★☆ | 标签:成本工程, threading, 锁

**问**:`with lock:` 看似只是几次字节码，什么情况下它便宜、什么情况下贵一个数量级？无竞争锁为什么几乎免费？竞争升级到 futex 后每一次 acquire 多付什么？临界区"越短越好"的量化依据是什么？

**答**:结论：`threading.Lock` 在 C 层是"快速路径 + 内核回退"两级设计：**无竞争时** acquire 只做一次原子 CAS（用户态，约 10-20ns），**不进内核**；竞争出现后线程通过 futex 系统调用挂起等待，一次挂起+唤醒 ≈ 1-5μs，再叠加调度延迟——竞争态比无竞争态贵 100 倍以上。推导出的三条成本规律：a) **锁的摊销成本 ≈ 竞争概率 × futex 成本**：把锁从"热点全局锁"改成"分片锁"（16 片），冲突概率按分片数近似线性下降；b) **临界区长度决定吞吐**：吞吐 ≈ 池大小 / (临界区时间 + futex 开销×竞争比)，临界区里塞一次日志写盘会把 10ns 的锁变成 1ms 的锁；c) **交替读写的伪竞争**：即使临界区极短，多线程高频 acquire 同一把锁仍会触发内核回退——计数器场景用 `per-thread 计数 + 汇总读取` 归零锁竞争。实战：GIL 程序里锁更常防的是"check-then-act 竞态"而非数据撕裂（见 Q5556 打点计数器的账），所以先问"这个锁到底保护哪个不变量"，再谈优化。

```python
import threading, timeit

lock = threading.Lock()

# ---- 1) 无竞争：fast path，纯用户态 ----
def uncontended(n):
    for _ in range(n):
        with lock:
            pass
t0 = min(timeit.repeat(lambda: uncontended(100_000), number=5, repeat=3))
print(f"无竞争 acquire/release 全路径: {t0/5/1e5*1e9:.0f} ns/次（C 层 fast path 为用户态 CAS，Python 层含字节码开销）")

# ---- 2) 竞争态：8 线程抢同一把锁，短临界区（futex 回退被放大） ----
def contended(nthread=8):
    barrier = threading.Barrier(nthread)
    hits = [0]
    def worker():
        barrier.wait()
        for _ in range(20_000):
            with lock:
                hits[0] += 1
    ts = [threading.Thread(target=worker, daemon=True) for _ in range(nthread)]
    [t.start() for t in ts]; [t.join() for t in ts]
    return hits[0], nthread * 20_000

(hits, total), t1 = contended(), timeit.timeit(lambda: contended(), number=3) / 3
print(f"8 线程竞争: {t1:.3f}s, 单次 acquire 摊到 ~{t1/total*1e9:.0f} ns/次"
      f"（短临界区 + GIL 串行下回退有限；Linux 真并发/长临界区才见 futex 量级成本）")

# ---- 3) 分片锁：把全局锁改成 16 片，冲突概率骤降 ----
N_SHARD = 16
shard_locks = [threading.Lock() for _ in range(N_SHARD)]
shard_counts = [0] * N_SHARD
def sharded():
    barrier = threading.Barrier(8)
    def worker(k):
        barrier.wait()
        for i in range(20_000):
            s = i % N_SHARD
            with shard_locks[s]:
                shard_counts[s] += 1
    ts = [threading.Thread(target=worker, args=(k,), daemon=True) for k in range(8)]
    [t.start() for t in ts]; [t.join() for t in ts]
    return sum(shard_counts)

t2 = timeit.timeit(sharded, number=3) / 3
print(f"16 片分片锁: {t2:.3f}s vs 全局锁 {t1:.3f}s（每片冲突概率降 16 倍；临界区越长/线程越多差距越大）")

# ---- 4) 临界区里做 IO = 锁的死刑 ----
print("反模式: with lock: logging.info(...) —— 把 20ns 的锁变成 1ms+ 的锁，吞吐按千倍下降")
```

**追问一层**:GIL 本身也是锁，为什么用户态 `Lock` 还需要？（GIL 保证字节码级原子性，不保证"check-then-act"复合操作；Lock 保护的是跨多条指令的不变量）。
**追问二层**:`threading.RLock` 比 `Lock` 贵在哪？（可重入需要记录 owner 与计数，快速路径多一次 owner 判断；非重入场景用 RLock 是无谓税）。
**追问三层**:如何在监控上发现锁竞争升级？（py-spy 的 lock 栈、`sys.setswitchinterval` 试验、线程状态分布（wait 时光占比）；3.14 的 `sys.monitoring` 也可挂 acquire 事件）。

## 背诵要点
- 无竞争锁 = 用户态 CAS（~10-20ns，无系统调用）；竞争后 futex 挂起/唤醒 ~1-5μs，差 100 倍。
- 成本 ≈ 竞争概率 × futex 开销：分片锁降冲突、临界区禁 IO、计数器用 per-thread + 汇总。
- GIL 防撕裂不防 check-then-act；Lock 保护的是不变量，先立不变量再谈性能。
