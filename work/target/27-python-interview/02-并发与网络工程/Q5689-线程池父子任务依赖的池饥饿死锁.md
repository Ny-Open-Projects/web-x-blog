### Q5689 · 线程池内的父子任务依赖：池饥饿死锁

难度：P7 ｜ 标签：ThreadPoolExecutor、死锁、资源池、嵌套提交、超时

**问**：一个接口在线程池里并行查两个下游，实现上"在池内的任务里再往同一个池提交子任务并 `result()` 等结果"。压测时全站接口一起卡住，重启才恢复。为什么？它和普通死锁有什么不同？加个 `timeout` 算修复吗？

**答**：
结论：线程池容量固定，父任务占满所有 worker 后，子任务只能排队；而父任务在等子任务完成 → 循环等待，永远不前进。`max_workers=1` 时是必然死锁；`max_workers=N` 且有 N 个父任务同时等待时同样是必然。本质是"池内任务依赖同一个池的资源"，属于资源死锁：持有者等待自己所需的资源被释放，而释放它的任务永远排不上。

取舍：三条修法按优劣排序——a) 父子分池（IO 等待型 vs 计算型，或按下游分池），从结构上消灭依赖环；b) 池内不要同步等待，返回 Future / 协程让调用方组合（`gather`），把等待放在不占 worker 的地方；c) 加有界并发 + 超时 + 熔断，只能把"全站卡死"降级成"部分请求失败"，不能根治。asyncio 里对应的问题是"协程里递归 acquire 同一个 Semaphore"，表现是 hang 而不是报错。

实战：事故形态是"QPS 一过阈值就雪崩，重启立刻恢复，火焰图上看线程全在 `Future.result`"。判断信号：线程数打满、任务队列长度单调上涨、下游其实很健康。下面用 1 个 worker 复现必然死锁，再演示拆分池与"返回嵌套 Future"两种修法。

```python
from concurrent.futures import ThreadPoolExecutor
from concurrent.futures import TimeoutError as FutureTimeout

ex = ThreadPoolExecutor(max_workers=1, thread_name_prefix="api")


def inner():
    return "inner-done"


def outer():
    # 在池内再提交子任务并同步等结果：唯一的线程正被自己占着
    return ex.submit(inner).result(timeout=0.5)


try:
    print("[1] 拿到:", ex.submit(outer).result(timeout=1))
except FutureTimeout:
    print("[1] 池被自己占满：子任务永远排不上，同步等待必然死锁")

# 修复一：拆成两个池，避免同一池内的父子依赖
sep = ThreadPoolExecutor(max_workers=1, thread_name_prefix="io")


def outer2():
    return sep.submit(inner).result(timeout=1)


print("[2] 子任务交给独立池:", ex.submit(outer2).result(timeout=2))

# 修复二：不要在池内同步等，直接返回 Future 让调用方组合
def outer3():
    return ex.submit(inner)


fut = ex.submit(outer3).result(timeout=1)
print("[3] 返回嵌套 Future 交给调用方:", fut.result(timeout=1))

ex.shutdown(wait=True)
sep.shutdown(wait=True)
```

**追问一**：为什么给 `result()` 加 timeout 不算修复？—— 它把"永久死锁"变成"每个请求等 500ms 后 500"，但在这 500ms 里 worker 仍被占着，池会持续饱和，队列继续堆积，最终全站超时。超时只能保护调用方，保护不了池本身；真正的修复必须是"不让池内任务等池内资源"。

**追问二**：asyncio 里会有同样的问题吗？—— 会，只是形态不同：`asyncio.Semaphore(1)` 在已持有它的协程里再次 `await acquire()`（不可重入）会永久挂起；`run_in_executor` 的默认池里再向默认池提交并等待也是如此。协程的好处是"等待不占线程"，所以同样的结构在 IO 密集场景下危害小得多，但一旦配了并发上限（Semaphore/连接池），环依然会死。

## 背诵要点
- 池内任务同步等待同池的子任务 = 资源死锁；`max_workers=1` 必然，`max_workers=N` + N 个父任务同样必然。
- 修法：父子分池、返回 Future/协程让调用方组合、至少要有有界并发 + 熔断；timeout 只是降级。
- asyncio 对应形态：不可重入 Semaphore 递归 acquire、默认 executor 内再提交默认池。

- 为什么 timeout 不能修复池饥饿？请给出两种结构性修法。（池饱和持续、分池/异步组合）
