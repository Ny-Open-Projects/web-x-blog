### Q5541 · 锁内调下游 RPC 的持有放大事故复盘

> 难度:★★★★ | 标签:锁, 事故复盘, 持有放大, 竞态

**问**：一次事故：下游支付网关 P99 从 50ms 涨到 2s，自家服务几乎所有请求线程卡死。根因是在 `with lock:` 保护的临界区里同步调用了该网关。为什么"锁内做 IO"会引发级联放大？正确的临界区设计原则是什么？如何观测锁持有时间？

**答**：机制叫**持有放大（lock hold-time amplification）**：临界区时长 = 锁内所有操作时长之和，锁内做 IO 后临界区时长被下游延迟决定。级联链条：下游变慢 → 每个线程持锁时间变长 → 锁竞争队列（等待线程）堆积 → 全部请求线程耗尽 → 上游超时风暴，甚至拖死本机线程池与内存（每等待线程一个栈）。设计原则四条：1) **临界区只做内存操作**：进入临界区前把需要的数据备齐、临界区内只读改共享结构、IO 移到锁外，"准备-提交"两段式；2) 确需跨 IO 的一致性时改用**乐观并发**（版本号/CAS、try-lock+超时）而不是长持锁；3) 锁必须**可超时**（`lock.acquire(timeout=)`），临界区异常路径保证释放（with/finally）；4) 锁粒度按业务键分片（分段锁）而不是全局一把。观测：用装饰器记录锁持有时长分位数（P99 持有时间应远小于 P99 请求时间），配合 Q2389 的排队时间分布区分"竞争大"与"持锁久"。事故复盘时先看两个数：锁持有 P99 和等待队列长度，就能定位放大源头。

```python
# file: code/02_并发与网络工程/q5541_lock_hold_amplify.py
import threading
import time
import random

random.seed(7)

class PaymentCacheBad:
    """事故版: 锁内同步调下游(模拟), 持有时间被下游延迟决定"""
    def __init__(self):
        self.lock = threading.Lock()
        self.data = {}
        self.hold_times = []

    def pay(self, oid, downstream_ms):
        t0 = time.perf_counter()
        with self.lock:
            time.sleep(downstream_ms / 1000)      # 锁内 IO: 事故根源
            self.data[oid] = "done"
        self.hold_times.append((time.perf_counter() - t0) * 1000)

class PaymentCacheGood:
    """修复版: 两段式——锁外调下游, 锁内只提交结果"""
    def __init__(self):
        self.lock = threading.Lock()
        self.data = {}
        self.hold_times = []

    def pay(self, oid, downstream_ms):
        t0 = time.perf_counter()
        result = self._call_downstream(downstream_ms)   # 锁外
        with self.lock:                                  # 锁内纯内存
            self.data[oid] = result
        self.hold_times.append((time.perf_counter() - t0) * 1000)

    def _call_downstream(self, ms):
        time.sleep(ms / 1000)
        return "done"

def p99(xs):
    return sorted(xs)[int(len(xs) * 0.99) - 1]

for cls in (PaymentCacheBad, PaymentCacheGood):
    c = cls()
    ts = [threading.Thread(target=c.pay, args=(f"o{i}", 50)) for i in range(8)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    total = (time.perf_counter() - t0) * 1000
    print(f"{cls.__name__}: 总耗时 {total:.0f} ms | 单次持锁 P99 {p99(c.hold_times):.0f} ms")

# 可超时获取: 防止临界区异常路径把线程永久挂住
lock = threading.Lock()
lock.acquire()
ok = lock.acquire(timeout=0.05)
print("带超时获取失败返回 False:", ok, "(而不是永久阻塞)")
lock.release()
```

**追问**：1) 下游调用真的需要"全局互斥"吗？怎么改造既保正确又不长持锁？——多数场景互斥的对象是"同一订单/账户"而不是全局，改成按 key 分片锁或 striped lock；全局唯一性约束下沉到 DB 唯一索引兜底。2) 乐观并发失败重试如何避免活锁？——加随机退避与重试上限，失败率高时退化为短期互斥（hybrid），并监控重试率作为告警信号。3) 为什么等待线程堆积还会拖垮内存？——每个线程栈占 MB 级虚拟内存（Q5542 的账），千级等待即 GB 级；且线程切换本身消耗 CPU，让本机 GC/调度进一步恶化。

## 背诵要点
- 锁内做 IO = 持有放大：下游延迟 × 并发数直接决定锁队列长度，可级联耗尽线程池。
- 临界区只做内存操作：两段式（锁外准备、锁内提交）+ 可超时 acquire + 按 key 分片。
- 观测锁持有 P99 与排队分布，持锁 P99 应远小于请求 P99。
