### Q5618 · urllib3 1.x → 2.0 的迁移演进

> 难度:★★★☆☆ | 标签:版本演进, urllib3, HTTP 客户端

**问**:urllib3 2.0（2023 年发布）是客户端栈的一次"安全默认值收紧"式大版本。它改了哪些默认行为？存量代码里最常见的迁移爆炸点是什么？requests/httpx 生态怎么被它牵动？

**答**:结论：urllib3 2.0 的主线是**把"默认不安全"改成"默认安全"**，迁移事故集中在默认值翻转处：a) **证书校验不可关闭降级**：`cert_reqs='CERT_NONE'` 后再想关 hostname 校验的写法收紧，`assert_hostname` 移除，装错证书的环境直接报错而不是警告；b) **默认 TLS 版本抬升**：最低 TLS 1.2，老服务（1.0/1.1）连不上；c) **默认编码与头部处理更严格**：请求头必须 str/bytes 洁净，非法头直接抛；d) `method_whitelist` → `allowed_methods`、`Retry` 参数更名（`raise_on_status` 语义微调）；e) body 处理：不再隐式 encode，bytes/str/文件对象边界显式化。生态牵动：requests 自 2.32 起拆出 `urllib3-future`（2.x 内核），老 requests 2.x 拆的是 `urllib3<2` 的版本 pin——**一个环境里同时出现 requests 与直连 urllib3 的两套连接池**是内存与配置漂移的隐性来源。迁移方法论：先在 CI 用 2.0 跑全量集成测试收集 `TypeError/SSLError` 爆点；对 `cert_reqs`/`assert_hostname` 类"关安全"的存量 hack 逐个改造为显式配置；灰度上按"无 TLS 定制 → 有 Retry 定制 → 有 TLS 定制"的顺序分批切。降级路径：无法短期改造的环境 pin `urllib3<2`（并用 pip-audit 跟踪 CVE），不要长期停在 1.x——1.26 系列已进入仅安全修复模式。

```python
# 基线: urllib3>=2.0（演示用 try 导入，缺库降级说明）
try:
    import urllib3
    print("urllib3:", urllib3.__version__)
except ImportError:
    print("缺 urllib3，pip install 'urllib3>=2.0'")
    raise SystemExit(0)

from urllib3 import PoolManager
from urllib3.util.retry import Retry

# 2.0 姿势：Retry 参数新名 + 默认安全 TLS
retry = Retry(
    total=3, connect=3, read=2,
    allowed_methods=frozenset(["GET", "HEAD"]),   # 2.0 起的参数名（旧: method_whitelist）
    backoff_factor=0.5,
    status_forcelist={500, 502, 503},
)
http = PoolManager(retries=retry)                  # 默认: TLS1.2+、证书校验强制

try:
    r = http.request("GET", "https://www.python.org/", timeout=5.0)
    print("状态:", r.status, "| TLS:", r.connection.sock.version() if r.connection else "n/a")
except Exception as e:
    print("网络受限（跳过实测）:", type(e).__name__)

# 事故点演示：试图关校验在 2.0 的报错形态
try:
    bad = PoolManager(cert_reqs="CERT_NONE")
    print("CERT_NONE 可构造（校验仍默认 hostname 走 check_hostname 逻辑，务必显式管理）")
except Exception as e:
    print("构造失败:", e)

# 1.x → 2.0 的检查清单（代码审计项）
checks = [
    "method_whitelist -> allowed_methods",
    "assert_hostname 已移除 -> 用自定义 SSLContext",
    "CERT_NONE 需同时显式处理 check_hostname=False",
    "header 必须为 str/bytes，None 头会抛",
    "body 不再隐式 encode，bytes/str/文件对象显式传",
    "默认 TLS>=1.2，老服务需显式降级或升级对端",
]
print("\n迁移检查清单:")
for c in checks:
    print(" -", c)
```

**追问一层**:为什么 2.0 选择"硬默认"而不是像 requests 那样用警告+过渡期？这类"安全默认收紧"的版本演进有没有通用迁移模式（对照 Q5544 TLS 版本演进）？
**追二层**:requests 2.32 拆 `urllib3-future` 后，同一进程里 requests 连接池与自建 PoolManager 的池参数（maxsize、超时）怎么统一治理？配置漂移会造成什么可观测问题？

**背诵要点**
- urllib3 2.0 主线是安全默认收紧：TLS≥1.2、强制证书校验、参数更名（method_whitelist→allowed_methods）、body/头显式化。
- 迁移爆炸点集中在关校验 hack 与老 TLS 对端；灰度顺序按 TLS/Retry 定制程度分批。
- 无法速改的环境 pin urllib3<2 并跟踪 CVE，勿长期滞留 1.x。

**复盘追问**
- 升级后部分内网老服务握手失败，止血与根治各是什么？提示：临时显式降级 SSLContext 并加迁移工单，根治是升级对端 TLS。
- 依赖树里同时出现 urllib3 2.x 与 pin<2 的包，pip 解析失败怎么办？提示：用 uv/pip 的冲突报告定位 pin 方，推动其解除或找替代依赖。
