### Q5668 · 心跳相位同步惊群与抖动容量账

难度：P7 ｜ 标签：心跳、jitter、惊群、长连接、容量账

**问**：百万长连接都用"固定 30 秒心跳"，为什么会在每 30 秒整点出现 CPU/带宽尖峰、而平均值看起来不高？这就是惊群（thundering herd）吗？给心跳加 jitter（抖动）为什么能削峰，代价是什么？请给出一个能算清"峰值/均值比 + 单心跳成本 × 连接数"的容量账，并说明 TCP keepalive 与应用心跳在这件事上的差别。

**答**：
结论：固定间隔心跳若相位对齐（例如所有连接都在服务启动时建、然后每 30 秒发一次），会形成**周期性同步**：每秒钟的心跳量在某一刻远高于均值，其余时刻接近零——这是"定时型惊群"（herd），与"多个进程抢一个 accept"的经典惊群同源：**大量主体在同一时刻被同一个时钟唤醒**。峰值/均值比可接近 1（全挤在一个 tick）到 N（分散 N 个 tick），取决于初始相位分布；尖峰会打到 CPU、锁、连接池、下游监控上，让"平均 QPS 不高"的系统在整点抖动甚至超时。加 jitter（在间隔上叠加随机偏移，如 `interval ± 30%` 或全周期均匀散步）能把相位摊平到多个 tick，峰值/均值比显著下降——代价是**单个连接的心跳时刻不确定**，故障发现时间的上界变大（要按 `interval + jitter` 算），且 jitter 必须是"每连接首次相位随机 + 每次重算"，不能所有连接用同一个随机种子。

取舍：jitter 的三种常见形态——① 固定偏移（启动时随机相位一次，之后固定周期）：简单、峰值摊平但会随连接生命周期再次聚集；② 每次全抖动（在上次心跳后 `interval ± rand`）：抗聚集最好，但发现时间方差大；③ 分桶抖动（把连接 hash 到 N 个时间桶）：可控、可观测，适合超大规模。选择依据是"能容忍多大的发现延迟上界"——金融交易类宁可承受尖峰也要短上界，普通 IM/推送用全抖动换取平稳。TCP keepalive 的内核默认间隔通常是**小时级**（Linux 默认 7200s），根本不用于"分钟级发现死连接"，所以它既救不了半开检测、也不会造成秒级惊群；秒级心跳必须应用层自己发，jitter 也要在应用层做。

实战：事故形态是"服务每 30 秒 CPU 冲高、下游 QPS 尖刺，但日均 QPS 很平稳"——用"相位分布直方图"看峰值/均值比即可确认。下面用模拟跑出：固定相位（全挤同一 tick）与加 jitter 后的峰值对比，并给出容量账公式。

```python
import random

N = 10000                       # 长连接数
INTERVAL = 30                   # 心跳周期（tick，这里 1 tick=1s）

def phase_buckets(n, jitter=0):
    buckets = {}
    for _ in range(n):
        phase = random.randint(0, INTERVAL - 1) if jitter else 0
        buckets[phase] = buckets.get(phase, 0) + 1
    return buckets

# 1) 固定相位：全部落在同一 tick -> 峰值 = 全部连接
random.seed(1)
fixed = phase_buckets(N, jitter=0)
print("fixed: peak=%d avg=%.0f ratio=%.1f" % (
    max(fixed.values()), N / INTERVAL, max(fixed.values()) / (N / INTERVAL)))

# 2) 全周期抖动：相位均匀散布 -> 峰值接近均值
random.seed(1)
jittered = phase_buckets(N, jitter=INTERVAL)
print("jitter: peak=%d avg=%.0f ratio=%.2f" % (
    max(jittered.values()), N / INTERVAL, max(jittered.values()) / (N / INTERVAL)))

# 3) 容量账：峰值 QPS = 峰值连接数 / 周期；单心跳成本 × 峰值
cost_per_hb = 0.0002            # 秒，假设单次心跳 CPU 成本
print(f"fixed  peak QPS = {max(fixed.values())/INTERVAL:.0f}/s  CPU={max(fixed.values())*cost_per_hb:.2f}s/s")
print(f"jitter peak QPS = {max(jittered.values())/INTERVAL:.0f}/s  CPU={max(jittered.values())*cost_per_hb:.2f}s/s")
print("discovery upper bound: fixed=%ds jitter=%ds" % (INTERVAL, INTERVAL + INTERVAL))
```

**追问一**：加了 jitter 为什么"发现死连接的最坏时间"变长了？——固定 30 秒心跳时，最坏情况是刚错过一次心跳就断网，要等 30 秒后才发下一次、再等一个超时窗口才判定；加了 ±30% 抖动后，下一次心跳可能落在 21~39 秒之间，上界变成 39 秒 + 超时窗口；若用全周期均匀抖动，上界接近 60 秒 + 超时窗口。所以"削峰"与"快速发现"是一对矛盾，jitter 幅度要按 SLA 里"最大允许发现时间"倒推。

**追问二**：为什么"每连接启动时随机一个固定相位"在大规模长运行后还会再次聚集？——因为连接的生命周期不是同步结束/重连的：批量重连（如发布后全部 worker 重启）会让新一批连接又在同一时刻建连、拿到相近的固定相位，于是再次同步。解决是"每次心跳后都重新抖动下一次间隔"（形态②），或在重连时从全局相位池里按连接 ID 哈希分桶（形态③），避免"新建连批次"把相位重新聚拢。

## 背诵要点
- 固定间隔 + 相位对齐 → 定时惊群：峰值/均值比高，均值不高但整点尖峰打爆 CPU/下游。
- jitter 摊平相位、削峰，代价是发现时间上界变大（按 interval+jitter 算）；分桶抖动可控可观测。
- TCP keepalive 默认小时级，不用于秒级半开检测；秒级心跳与 jitter 都在应用层做，容量账 = 峰值连接数/周期 × 单心跳成本。
