### Q5666 · TLS 1.3 0-RTT 重放风险与幂等白名单

难度：P7 ｜ 标签：TLS 1.3、0-RTT、early data、重放攻击、幂等

**问**：TLS 1.3 的 0-RTT（early data）为什么能省一个 RTT，又为什么伴随"重放风险"？攻击者没有解密能力，凭什么能把同一份 early data 再发一次？服务端有哪三层防线——协议层（single-use ticket / 反重放窗口）、接入层（幂等白名单）、应用层（幂等键）？Python 标准库 `ssl` 对 0-RTT 的暴露程度如何，怎么做兼容降级？

**答**：
结论：0-RTT 用**上次会话的 PSK** 在 ClientHello 里直接带上加密的 early data，省掉"等 ServerHello 再发请求"的一个 RTT；但它依赖的是**旧会话密钥**，服务端在收到 early data 时还没贡献新的随机性，因此无法判断这份数据是"本次真实请求"还是"攻击者重放的旧请求"——攻击者只要录下同一份 early data 字节流原样重发，服务端用同一个 PSK 就能解密并**再执行一次**。风险的本质是"缺少新鲜性保证"，不是密钥泄露。三层防线：① **协议层**——服务端用一次性 session ticket（用后即失效）或维护反重放窗口（记录已见的 ticket/ClientHello，窗口内拒绝重复），代价是牺牲部分 0-RTT 命中率与需要跨节点共享状态；② **接入层白名单**——只允许幂等方法（GET/HEAD/OPTIONS 等）走 0-RTT，POST/PUT 这类有副作用的请求回退到 1-RTT；③ **应用层幂等键**——即便重放到达，用业务幂等键保证"执行多次效果等同一次"。

取舍：不要为了省一个 RTT 把非幂等接口开放 0-RTT——重放的代价（重复扣款、重复下单）远大于那点延迟收益。多节点场景反重放状态必须共享（Redis 等），否则攻击者在不同节点重放就能绕过单节点窗口；若不愿维护共享状态，最稳的策略是**直接禁用 0-RTT**（`ssl.OP_NO_TICKET` 关闭 ticket 或接入层不接受 early data），把安全默认值放在"不重放"一侧。

实战：Python 标准库 `ssl` 在 3.12 暴露 `HAS_TLSv1_3` 与支持 TLS 1.3 握手，但**不直接提供 early data 的收/发 API**（需要 pyOpenSSL 或底层库），所以 Python 服务侧通常由反向代理（nginx/Envoy）处理 0-RTT，应用只做"白名单 + 幂等键"两层。下面用本地模拟把"无防护重放执行两次、反重放窗口拒绝、幂等白名单判定"跑清楚。

```python
import ssl
print("TLS 1.3 available:", ssl.HAS_TLSv1_3)

class ReplayGuard:
    """反重放窗口：窗口内同一 ticket 只接受一次（示意，生产需跨节点共享）。"""
    def __init__(self, window):
        self.seen = {}
        self.window = window
    def check(self, ticket, now):
        last = self.seen.get(ticket)
        if last is not None and now - last <= self.window:
            return False
        self.seen[ticket] = now
        return True

def handle(early_data, ticket, guard=None, now=0):
    if guard is not None and not guard.check(ticket, now):
        return "REPLAY REJECTED"
    return f"EXECUTED: {early_data}"

# 1) 无防护：同一 0-RTT 载荷被重放执行两次
print("no guard :", handle("POST /pay", "ticket-A"),
      "|", handle("POST /pay", "ticket-A"))

# 2) 反重放窗口：窗口内第二次被拒
g = ReplayGuard(window=60)
print("guarded  :", handle("GET /index", "ticket-B", g, now=1),
      "|", handle("GET /index", "ticket-B", g, now=2))
print("outside  :", handle("GET /index", "ticket-B", g, now=100))

# 3) 接入层幂等白名单：只允许幂等方法用 0-RTT
IDEMPOTENT = {"GET", "HEAD", "OPTIONS", "TRACE"}
def zero_rtt_ok(method):
    return method in IDEMPOTENT
for mtd in ("GET", "HEAD", "POST", "PUT", "DELETE"):
    print(f"  0-RTT allow {mtd:7}: {zero_rtt_ok(mtd)}")

# 4) 应用层兜底：幂等键让重复执行等效一次
applied = {}
def pay(key, amount):
    if key in applied:
        return "duplicate ignored"
    applied[key] = amount
    return "charged"
print("app idem :", pay("order-1", 100), "|", pay("order-1", 100))
```

**追问一**：攻击者没有 PSK 私钥，为什么还能重放？——他不需要解密或伪造，只需**原样重发截获的密文字节**；服务端持有 PSK，能正常解密，且 early data 里没有"本次独有的随机数/计数器"可供校验新鲜性——除非服务端额外维护"这个 ticket 已用过"的状态。所以重放是"录制回放"级别的简单攻击，防御靠服务端状态而非密码学本身。

**追问二**：关闭 session ticket（`OP_NO_TICKET`）能彻底消除 0-RTT 风险吗？——能消除 0-RTT 本身（没有 ticket 就没有 PSK 恢复、也就没有 early data），代价是所有连接都退回完整 1-RTT 握手，握手延迟与 CPU 上升。对金融/支付这类"重复执行代价极高"的服务，这是合理的默认选择；对读多写少的 CDN/静态资源，则保留 0-RTT + 幂等白名单更划算。取舍点在于"一次 RTT 的延迟收益"与"一次重复副作用的损失"之比。

## 背诵要点
- 0-RTT 用旧 PSK 在 ClientHello 带 early data 省 1 RTT；缺新鲜性 → 录制回放即可重放执行。
- 三防线：协议层一次性 ticket/反重放窗口（需跨节点共享）、接入层幂等白名单（只 GET/HEAD）、应用层幂等键。
- Python ssl 不直接暴露 early data API，多由反代处理；高价值写接口宁可关 ticket 禁用 0-RTT。
