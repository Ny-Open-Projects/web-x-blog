### Q5654 · 线程轮询与事件驱动的唤醒频率容量账

难度：P6 ｜ 标签：线程、轮询、Event、唤醒、容量规划

**问**：100 个后台线程各自 `Event.wait(timeout=0.05)` 轮询，系统的实际唤醒频率与成本怎么算？为什么"sleep 轮询"在低负载下看起来正常、在多线程规模下突然恶化？轮询间隔、线程数、每次唤醒成本的预算公式是什么，事件驱动如何替代？

**答**：
结论：`Event.wait(t)` 轮询的成本模型：每线程每间隔一次唤醒 = 一次内核态往返（futex/kevent 等待超时唤醒）+ Python 层检查 + 可能的 GIL 争抢。预算公式：`唤醒频率 ≈ 线程数 / 轮询间隔`，100 线程 × 50ms 间隔 = 2000 次唤醒/秒；每次唤醒含约 5–20µs 内核成本 + Python 解释循环开销（无 GIL 时还要乘缓存一致性流量），空闲 CPU 从此有底噪。恶化的机理是**双重过载**：唤醒本身与"醒来后抢 GIL 串行化"叠加——100 线程同时醒来对同一把 GIL 排队，单次唤醒成本随线程数上升（切换抖动），延迟毛刺与 CPU 空转同时出现。

取舍：轮询不是原罪，要按"事件延迟要求"配比——能容忍秒级延迟的巡检任务轮询完全合理（间隔放宽到 1-5s，唤醒频率即降一个量级）；需要毫秒级响应的必须事件驱动：`Event.wait()` 无超时挂起（0 空闲成本）、`queue.get(timeout)` 阻塞消费、或由调度器单线程统一 `select`。折中方案是**指数退避轮询**（空闲期间隔翻倍、有事立刻回短间隔），把平均唤醒率压到事件率量级。

实战：审计后台线程清单时把每个线程的 `(间隔, 醒来做什么)` 登记成表，算全进程唤醒预算（如 ≤200 次/秒）；共享同一个轮询循环（一个调度线程 + 定时器堆）替代 N 个独立轮询线程，唤醒次数与线程数解耦；指标上把"每秒上下文切换数（vmstat cs）"与线程数关联看基线漂移。

```python
import threading, time

def poll_wakeup_rate(n_threads=100, interval=0.05, observe=0.5):
    """统计轮询线程的实测唤醒频率（短观察窗，避免真打满机器）"""
    wakeups = [0] * n_threads
    stop = threading.Event()

    def poller(i):
        while not stop.is_set():
            wakeups[i] += 1
            stop.wait(interval)            # 轮询式：空等 interval 再醒

    threads = [threading.Thread(target=poller, args=(i,), daemon=True) for i in range(n_threads)]
    for t in threads: t.start()
    time.sleep(observe)
    stop.set()
    for t in threads: t.join(timeout=1)
    rate = sum(wakeups) / observe
    print(f"{n_threads} threads x {interval*1000:.0f}ms -> {rate:.0f} wakeups/s")
    return rate

r1 = poll_wakeup_rate(100, 0.05)
r2 = poll_wakeup_rate(100, 0.5)
print("10x 间隔 -> 唤醒率降一个量级:", r1 > r2 * 5)

# 事件驱动替代：0 空闲成本，唤醒次数 == 事件次数
event = threading.Event()
count = 0
def driven():
    global count
    while True:
        event.wait()                        # 无超时挂起：不空转
        event.clear()
        count += 1
        if count > 3:
            return

t = threading.Thread(target=driven, daemon=True); t.start()
for _ in range(4):
    time.sleep(0.01)
    event.set()
t.join(timeout=1)
print("event-driven wakeups == events:", count)

# 指数退避：空闲拉长间隔、有事件回短
def backoff_poller(max_interval=1.0):
    interval = 0.01
    while True:
        if check_work():                    # 有活干
            interval = 0.01
            return
        interval = min(interval * 2, max_interval)
        time.sleep(interval)

def check_work():
    return False
print("backoff: 0.01->0.02->... capped at", max(1.0, 0), "s")
```

**追问一**：为什么线程醒来后还要抢 GIL，抢不到的会怎样？——等待在 GIL 的条件变量上再睡（这就是 `sys.setswitchinterval` 影响的切换粒度来源），表现为"唤醒了但没干活"的空转切换；线程数远超核数时，轮询间隔越短这种无效切换占比越高，CPU 空转与延迟毛刺同源。

**追问二**：如何把"N 个独立轮询线程"改造成"单调度线程"且不漏事件？——调度线程维护最小堆（到期时间 → 回调/事件），每次 `Event.wait(next_deadline)`；事件到达用 `set()` 立即打断重算堆。语义等价的前提是各轮询任务无独立线程局部状态、超时/异常路径收敛到调度器统一处理。

## 背诵要点
- 唤醒频率 ≈ 线程数 / 轮询间隔；`wait(t)` 轮询每次唤醒有内核往返 + GIL 排队双重成本。
- 毫秒级响应用事件驱动（无超时 wait / queue.get），秒级巡检可轮询；折中用指数退避。
- 工程动作：登记线程唤醒预算（如 ≤200 次/s）、单调度线程定时器堆替代 N 轮询线程。

## 复盘追问
