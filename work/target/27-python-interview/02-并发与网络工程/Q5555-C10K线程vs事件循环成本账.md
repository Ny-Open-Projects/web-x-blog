### Q5555 · C10K：线程模型与事件循环的每连接成本账

> 难度:★★★★ | 标签:C10K, threading, asyncio, selectors, 成本工程

**问**："一个连接一个线程"的 TCP 服务，2000 连接就内存告警、CPU 切换打满。线程模型和事件循环的每连接成本差在哪？数字大概是多少？什么场景必须线程、什么场景必须事件循环？

**答**：两条路线的账完全不同量级。**线程模型**：每线程默认栈 8MB（虚拟内存，实际提交约 0.3-1MB）+ 内核 task struct + 调度开销，创建 100 线程实测约 80-90ms（每线程 ≈1ms），上下文切换依赖 GIL 还要排队——千级连接内存 GB 级、切换成本线性涨，这就是 C10K 在线程模型下的墙。**事件循环**：每连接 ≈ socket 对象 + 缓冲 + 几 KB 协程/task 对象，1000 个 asyncio task 调度实测 <10ms，万级连接单核可扛（前提是每连接逻辑不阻塞）。所以纯 IO 高并发（网关、聊天、长连接推送）唯一正解是事件循环。线程不可替代的场景：a) 调**阻塞 C 扩展**（很多 DB driver/SDK）——它们持有 GIL 或根本不兼容 loop；b) CPU 密集分片——事件循环里跑 CPU 任务会饿死其他连接，得让给进程池；c) 生态是同步 API。混合架构是常态：asyncio 主循环 + `run_in_executor` 桥接阻塞段（但要给 executor 设 max_workers 上限形成背压，否则"线程池饱和"是新事故源——见 Q5506 的放大版）。决策一句话：**连接数 × 每连接阻塞度决定模型，先算账再选型，不按习惯**。

```python
# file: code/02_并发与网络工程/q5555_c10k_cost.py
import threading, time, asyncio

def cpu_busy():
    s = 0
    for i in range(10_000):
        s += i
    return s

# 1) 线程模型: 100 线程的创建+join 成本
t0 = time.perf_counter()
ts = [threading.Thread(target=cpu_busy) for _ in range(100)]
for t in ts: t.start()
for t in ts: t.join()
t_thread = time.perf_counter() - t0
print(f"100 线程创建+join: {t_thread*1000:.1f}ms (每线程≈1ms, 栈提交≈0.3-1MB)")

# 2) 事件循环: 1000 个 task 的调度成本
async def main():
    t0 = time.perf_counter()
    tasks = [asyncio.create_task(asyncio.sleep(0)) for _ in range(1000)]
    await asyncio.gather(*tasks)
    return time.perf_counter() - t0
t_loop = asyncio.run(main())
print(f"1000 个 asyncio task 调度: {t_loop*1000:.1f}ms (每 task≈KB 级内存)")

# 3) 混合架构: asyncio 主循环 + executor 桥接阻塞段(带上限)
async def serve():
    loop = asyncio.get_running_loop()
    loop.set_default_executor(
        type(loop.get_default_executor())(max_workers=8)  # 有限线程池=背压
    ) if False else None
    print("桥接姿势: await loop.run_in_executor(pool, blocking_fn), pool 带 max_workers 上限")
asyncio.run(serve())

# 4) 决策表
print("纯 IO 高并发 -> 事件循环; 阻塞 C 扩展/CPU 分片 -> 线程/进程池; 都要 -> 混合+背压")
```

**追问**：1) "每线程 8MB 栈"为什么实际提交不是 8MB？——栈是虚拟内存预留，物理页按触碰提交（lazy）；但 `threading.stack_size` 可调小、深递归任务要按真实使用算，容量账按"提交页"估而不是预留额。2) asyncio 单核扛万连接，CPU 被什么吃掉？——epoll 系统调用 + 协程切换 + 回调执行；心跳/定时器风暴（Q5537）和每连接大缓冲是常见放大器，用批量 recv/合并定时器压。3) free-threading 构建会改变这笔账吗？——真并行线程消除了 GIL 排队，切换成本模型变化，但每线程内存与内核调度开销不变——"线程比协程贵一个数量级"的结论仍成立，只是 CPU 密集多线程任务收益变正。

## 背诵要点
- 线程：创建 ≈1ms/个、栈提交 0.3-1MB/个，千级连接内存 GB 级；asyncio task：KB 级、1000 个调度 <10ms，差两个数量级。
- 必须线程/进程的场景：阻塞 C 扩展、CPU 密集、同步生态；纯 IO 高并发必选事件循环；混合用 run_in_executor + max_workers 背压。
- 容量按"每连接成本 × 目标连接数"先算账再选型；8MB 是栈预留不是提交，账按物理页算。
