### Q5584 · TCP 粘包拆包与消息帧设计的原理深挖

难度：★★★★☆ ｜ 标签：TCP / 原理深挖 / 协议设计 / 消息帧

**问**：客户端连发两条 `"hello"` 和 `"world"`，服务端一次 `recv` 却收到 `"helloworld"`；有时反过来一条消息分两次到达。"粘包"是 TCP 的 bug 吗？Python 里正确的消息帧（framing）方案有哪些，各适合什么场景？

**答**：
- **结论**：不是 bug——TCP 是**字节流协议**，只保证字节有序可靠到达，不保留应用层消息边界；Nagle 合并、MSS 分段、接收缓冲区读出时机都会把"写"与"读"的次数错位。"粘包/拆包"是应用层没做 framing 的表现。三个标准方案：1）**定长帧**（简单、浪费带宽）；2）**长度前缀**（N 字节长度 + payload，主流选择，天然支持二进制）；3）**分隔符**（文本协议如 Redis RESP/HTTP header，payload 必须转义）。UDP 则相反：天然有消息边界（数据报），但要自己处理 MTU 分片丢失。
- **取舍**：长度前缀选 2/4/8 字节要算最大消息（2 字节 64KB 上限，1MB 级消息用 4 字节）；字节序固定 network order（`struct.pack("!I", n)`）；流式解帧必须维护**缓冲区状态机**（攒够头部读长度、攒够长度交 payload、剩余字节留给下一条），不能假设 recv 的返回就是"一条完整消息"。asyncio 的 `StreamReader.readexactly(n)` 就是这个状态机的标准库实现，`readuntil(b"\\n")` 是分隔符版。
- **实战**：协议演进要留版本字段与最大长度上限（防恶意长度攻击：收到 4GB 长度声明直接断连）；压测必须包含"发送方 flush 节奏随机化"的用例，否则粘包只在生产偶现。

```python
"""长度前缀 framing 状态机：本机 TCP 演示粘包现象与正确解帧（标准库）"""
import socket, struct, threading

def send_msgs(sock, msgs):
    """把多条消息塞进同一次发送，制造粘包条件（兼容 socket 与 StreamWriter）"""
    payload = b"".join(struct.pack("!I", len(m)) + m for m in msgs)
    if hasattr(sock, "sendall"):
        sock.sendall(payload)
    else:                                          # asyncio StreamWriter
        sock.write(payload)

class FrameReader:
    """流上的长度前缀解帧状态机：recv 返回多少都无所谓"""
    def __init__(self, sock):
        self.sock, self.buf = sock, b""
    def read_frame(self):
        while len(self.buf) < 4:
            self.buf += self.sock.recv(4096)
        (n,) = struct.unpack("!I", self.buf[:4])
        if n > 1 << 20:
            raise ValueError("帧超上限，疑似攻击")
        body_start = 4
        while len(self.buf) < 4 + n:
            self.buf += self.sock.recv(4096)
        frame, self.buf = self.buf[body_start:body_start + n], self.buf[4 + n:]
        return frame

listener = socket.socket()
listener.bind(("127.0.0.1", 0))
listener.listen(1)
port = listener.getsockname()[1]

received = []
def server():
    conn, _ = listener.accept()
    fr = FrameReader(conn)
    for _ in range(3):
        received.append(fr.read_frame())
    conn.close()

threading.Thread(target=server, daemon=True).start()
c = socket.create_connection(("127.0.0.1", port))
send_msgs(c, [b"hello", b"world", b"!"])   # 三条一次发出 → 服务端必然粘
c.close()

import time; time.sleep(0.3)
print("粘包条件下逐帧还原:", received)

# asyncio 版：readexactly 就是标准库给的状态机
import asyncio

async def aio_demo():
    async def client_task(reader_port):
        r, w = await asyncio.open_connection("127.0.0.1", reader_port)
        send_msgs(w, [b"alpha", b"beta"])          # 一次 write，两条消息
        await w.drain()
        w.close()
    async def server_task():
        async def serve(reader, writer):
            head = await reader.readexactly(4)     # 状态机第一步：攒够头
            (n,) = struct.unpack("!I", head)
            body = await reader.readexactly(n)     # 第二步：攒够体
            print("asyncio readexactly 解出:", body)
            writer.close()
        srv = await asyncio.start_server(serve, "127.0.0.1", 0)
        await client_task(srv.sockets[0].getsockname()[1])
        srv.close(); await srv.wait_closed()
    await asyncio.wait_for(server_task(), timeout=5)

asyncio.run(aio_demo())
listener.close()
```

**追问链**
1. 粘包在什么时序下必然发生、什么时序下几乎不发生？为什么测试环境常常测不出来？
   1. 发送方两次 write 间隔小于 RTT 且接收方 read 晚于两段到达 → 合并读出；接收方读得比发送方写得快则可能一次只收到半条。本机 loopback 延迟趋近 0、线程调度快，反而更易复现粘包；而"恰好逐条 read"只是运气，不是协议保证。
   2. 追问：`recv(4096)` 的参数意味着"最多 4096"还是"至少"？——最多；返回 0 表示对端关闭，循环里必须处理 b"" 否则死循环。
2. 分隔符方案与长度前缀方案在安全与性能上的差异？
   1. 分隔符需转义扫描（Redis RESP 按行、HTTP 用 CRLF），payload 出现分隔符必须编码，扫描成本 O(n)；长度前缀零扫描、可预分配，但长度字段可伪造——必须设上限并先收头再收体，超过即断连（防内存炸弹）。
   2. 追问：HTTP/1.1 怎么同时用了两种？——header 用 CRLF 分隔，body 用 Content-Length（长度前缀）或 chunked（分块自带长度行），这正是真实协议混合使用两种 framing 的例子。

## 背诵要点
- TCP 是字节流，无消息边界：粘包/拆包是应用层没做 framing；recv 返回多少与 send 次数无关。
- framing 三方案：定长 / 长度前缀（!I + 状态机缓冲，主流）/ 分隔符（需转义）；asyncio 用 readexactly/readuntil。
- 长度字段必须设上限防伪造攻击；测试要含随机 flush 时序，否则粘包只在生产偶现。
