### Q5587 · 进程池 × 线程池混合架构的配比容量推导

难度：★★★★☆ ｜ 标签：容量规划 / ProcessPoolExecutor / ThreadPoolExecutor / GIL

**问**：一个网关服务同时有三类工作：CPU 密集（压缩/校验）、IO 密集（HTTP 下游调用，阻塞 SDK 不能协程化）、轻量异步（快查）。进程数、线程数怎么定？"进程里再开线程池"的账怎么算才不翻车？

**答**：
- **结论**：分层配比公式——**进程数**按 CPU 任务吞吐定：`ceil(CPU 秒需求 / 目标核时)`，上限 = 物理核数（超配只争抢不增益）；**每进程线程池**按 IO 任务并发定：线程数 ≈ 期望并发 × (1 + 平均阻塞时长/计算时长)，线程是等待槽不是算力；**协程**承接轻量异步。混合翻车点通常有两个：① 进程池里再开大线程池——每进程 RSS 翻倍（线程栈 + 连接池 per-process 复制），总内存 = 进程数 × (基础 + 线程数 × 栈 + 连接池)；② CPU 任务误投线程池，GIL 下互相拖累，整体吞吐低于单线程串行排队。
- **取舍**：多进程 + 每进程多线程的结构里，连接池/缓存/配置全部 per-process 重复（进程隔离的代价）；跨进程共享要走 shared_memory（Q5509）或 IPC。替代方案：CPU 任务剥离成独立 worker 部署（K8s 里单独 Deployment），让网关进程保持纯 IO 型——多数情况下比"混合进程内调度"更可观测、更好扩缩容。选混合的正当理由：任务粒度小、剥离后 IPC 序列化成本反超计算成本。
- **实战**：推导步骤：1）压测拿单线程基准（每任务 CPU ms、阻塞 ms）；2）CPU 池：核数 ÷ 单任务 CPU 占用；3）IO 池：目标并发 × 阻塞占比；4）总核占用 = 进程数 × (CPU 线程数 × 100% + IO 线程的 CPU 片)，须 ≤ 物理核数；5）内存账 = 进程数 ×（解释器 + 池 + 连接池）对齐容器 limit。

```python
"""混合池配比推导与实测（macOS spawn，Python 3.12，标准库）"""
import os, time, math, hashlib
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor

def cpu_task(n):
    """CPU 密集：哈希迭代"""
    h = b"seed"
    for _ in range(20_000):
        h = hashlib.sha256(h).digest()
    return h[0]

def io_task(ms):
    """IO 密集模拟：sleep（真实场景是阻塞 SDK 调用）"""
    time.sleep(ms / 1000)
    return ms

CPU_N = os.cpu_count() or 4
print(f"物理核数: {CPU_N}")

# 第 1 步：单基准
t0 = time.perf_counter(); cpu_task(0); t_cpu = (time.perf_counter() - t0) * 1000
t0 = time.perf_counter(); io_task(20); t_io = (time.perf_counter() - t0) * 1000
print(f"单任务基准: cpu≈{t_cpu:.1f}ms io≈{t_io:.0f}ms")

# 第 2 步：CPU 池 = 核数；IO 池按阻塞占比放大
n_proc = CPU_N
n_io_thread = int(CPU_N * (1 + t_io / t_cpu))   # 期望并发按阻塞比放大
print(f"推导: 进程数={n_proc}  每进程 IO 线程数≈{n_io_thread}")

# 第 3 步：实测混合执行（spawn 守卫必须有）
if __name__ == "__main__":
    import multiprocessing as mp
    ctx = mp.get_context("spawn")
    t0 = time.perf_counter()
    with ProcessPoolExecutor(max_workers=n_proc, mp_context=ctx) as pp, \
         ThreadPoolExecutor(max_workers=n_io_thread) as tp:
        futs_cpu = [pp.submit(cpu_task, i) for i in range(n_proc * 2)]
        futs_io = [tp.submit(io_task, 20) for _ in range(n_io_thread * 2)]
        done_cpu = sum(1 for f in futs_cpu if f.result() is not None)
        done_io = sum(1 for f in futs_io if f.result() is not None)
    dt = time.perf_counter() - t0
    print(f"混合执行: cpu 任务 {done_cpu} + io 任务 {done_io}，总耗时 {dt:.2f}s")

    # 内存账提醒：进程池 = n_proc × (解释器 ~20MB + 连接池)，容器 limit 要按此对齐
    print(f"内存粗账: {n_proc} 进程 × (解释器~20MB + 线程栈{n_io_thread}×0.5MB) ≈ "
          f"{n_proc * (20 + n_io_thread * 0.5):.0f} MB（不含业务对象）")
```

**追问链**
1. 为什么 CPU 任务误投线程池会"比串行还慢"？
   1. GIL 下线程无法并行执行字节码，切换/调度反而加开销；实测常见现象：4 线程跑 CPU 任务 ≈ 1 线程耗时 × 1.1-1.3。识别信号：py-spy 火焰图全是 `GIL` 等待与 `ceval` 互斥。
   2. 追问：free-threading 3.13+ 构建下还成立吗？——GIL 移除后 CPU 任务线程池可真并行，但每对象同步开销使扩展比 < 核数，且生态兼容要逐库确认（Q5002 的语义边界），不能默认迁移。
2. IO 线程数的公式在什么前提下失效？
   1. 前提是"阻塞时长与线程数无关"（下游无限承载）；当下游有连接池上限或限流，并发超过下游容量后阻塞时长随并发上升，线程数再大吞吐不变只涨内存——公式要改成"下游容量 × 每并发吞吐"约束。
   2. 追问：为什么连接池是 per-process 的？——进程不共享内存，各自持有连接句柄；下游看到的连接数 = 进程数 × 池大小，DB max_connections 要按这个乘积规划，否则网关扩容打爆数据库。

## 背诵要点
- 配比：进程数 = CPU 核数（按 CPU 任务吞吐定）；IO 线程数 = 并发 × (1 + 阻塞/计算比)；轻量任务给协程。
- 两大翻车：CPU 任务投线程池（GIL 串行化）、连接池/内存 per-process 复制（下游连接数 = 进程数 × 池大小）。
- 更优解常是"CPU 任务独立 Deployment 剥离"，混合架构仅在任务粒度小、IPC 反超计算成本时选。
