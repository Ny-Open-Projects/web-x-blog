### Q5711 · UDP 乱序重组：序号、缓存窗口与按序交付协议设计

难度：P6 ｜ 标签：UDP、乱序、重组、序号、滑动窗口、去重

**问**：UDP 包到达顺序和发送顺序无关（多路径、路由抖动、重传并存），要在 UDP 上做"可靠有序"交付，最少需要哪些机制？乱序包怎么缓存、怎么判定丢包？序号回绕怎么办？与 TCP 的"可靠有序"差在哪一层？

**答**：
结论：最小机制三件套：①**每包序号**（单调递增，用于排序与去重）；②**接收缓存窗口**——乱序到达的包不能直接交付，先按序号入缓存表，只有"下一个期望序号"到位才推进交付游标，连续把缓存里能交付的都吐出；③**丢包判定与重传请求**——期望序号之后的空洞超过阈值（如收到 seq+2 而 seq+1 未到）即判丢，发重传请求（NACK）或等超时。序号用模运算回绕，比较必须用**回绕安全比较**（如 RFC 1982：序差在半空间内视为"更晚"），直接用整数大小比较会在回绕点倒转。与 TCP 的差异：TCP 的有序交付在内核协议栈（重传/RTT 估计/拥塞控制全套），UDP 上自建只能拿你要的那一层——"只要有序不要拥塞控制"（实时音视频）或"要确认不要有序"（遥测）都可裁剪，这正是 QUIC 重新在 UDP 上造 TCP 的原因：把每一层做成可选项。

取舍：a) 缓存窗口大小 = 乱序容忍度 × 带宽时延积：太小频繁 NACK、太大占内存；b) 交付游标推进 O(1) 用 dict + while（本卡实现），O(n) 用有序数组插入；c) 去重靠"游标前的序号直接丢弃"即可，不必全量集合——前提是游标只前进；d) 重传策略：NACK（收到更高序号即报空洞，快但要求双向信道）vs 超时重传（单工信道，慢）；e) 有序交付是双刃剑——音视频场景反而要"尽力交付"（跳过丢失帧），协议设计先问要不要严格有序。

实战：事故形态是"行情推送改 UDP 广播后，客户端偶发行次错乱：多路径路由让快慢包交错，裸 recvfrom 直接交付；加 16 槽乱序缓存 + NACK 后，P99 交付延迟反而下降（不再等超时重传整段）"。下面实现一个可跑的重组器并喂乱序包。

```python
import random

WINDOW = 16


class Reassembler:
    def __init__(self):
        self.next_seq = 0
        self.buffer = {}
        self.delivered = []
        self.lost_detected = []

    def on_packet(self, seq, payload):
        if seq < self.next_seq:                      # 回绕前的旧包: 去重
            return "dup"
        self.buffer[seq] = payload
        if seq >= self.next_seq + WINDOW:            # 超出缓存窗口: 判丢
            missing = [s for s in range(self.next_seq, seq) if s not in self.buffer]
            self.lost_detected.append(tuple(missing))
            return f"nack:{missing}"
        out = []
        while self.next_seq in self.buffer:          # 按序推进交付游标
            out.append(self.buffer.pop(self.next_seq))
            self.next_seq += 1
        self.delivered.extend(out)
        return f"deliver:{len(out)}"

    def inject_missing(self, seq, payload):
        return self.on_packet(seq, payload)


payloads = {i: f"p{i}".encode() for i in range(8)}
order = list(range(8))
random.Random(7).shuffle(order)
r = Reassembler()
for seq in order:
    print(f"[seq {seq}] ->", r.on_packet(seq, payloads[seq]))
r.inject_missing(2, payloads[2])
print("[1] 乱序到达顺序:", order)
print("[2] 按序交付:", [d.decode() for d in r.delivered])
print("[3] NACK 记录:", r.lost_detected)
```

**追问一**：序号 32 位回绕点附近，`seq > last` 为什么不可靠？怎么写回绕安全比较？—— 序号域是模 2^32 环：发送侧到 0xFFFFFFFF 后回到 0。直接大小比较会把"回绕后的 0"判为最旧。安全写法是差值语义：`d = (seq - last) & 0xFFFFFFFF`，`0 < d < 2^31` 视为"seq 更新"，`d >= 2^31` 视为"seq 更旧"（远差值视为乱序异常丢弃）。这套规则就是 RFC 1982 的序列空间算术，TCP/QUIC 的内核实现同理，应用层自建协议必须照抄，否则长跑服务在回绕瞬间必然错序。

**追问二**：为什么"缓存窗口 + NACK"比纯超时重传更适合低延迟场景？—— 超时重传要等 RTT 级别的定时器，丢一个包整段流都要空转一个 RTT；NACK 在**收到未来包的瞬间**就能断定空洞存在（序号已知），重传请求零等待，恢复时间从 1 个 RTO 缩到 1 个 RTT。代价是需要双向信道与接收端逻辑复杂度；且 NACK 有风暴风险——多个接收端同时丢同一包会齐发 NACK，要加随机延迟（组播场景必配）或发送端组播修复包。这也是 FEC（前向纠错）的选型边界：丢包率稳定且低时 FEC 免往返，突发丢包时 NACK 更省带宽。

## 背诵要点
- 可靠有序三件套：序号 + 乱序缓存窗口 + 丢包判定（NACK/超时）；游标只前进，游标前序号即去重。
- 序号回绕必须用模半空间差值比较（RFC 1982），裸大小比较在回绕点倒转。
- 交付游标推进用 dict+while O(1)；窗口大小取乱序容忍×带宽时延积；TCP 的拥塞控制层 UDP 自建协议默认没有。
