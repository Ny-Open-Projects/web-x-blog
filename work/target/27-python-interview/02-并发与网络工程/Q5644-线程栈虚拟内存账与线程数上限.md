### Q5644 · 线程栈虚拟内存账与线程数上限推导

难度：P6 ｜ 标签：threading、栈内存、容量规划、resource

**问**：容器 2GB 内存，服务创建 500 个线程后 OOMKilled。为什么"每个线程 8MB"的常识在容器里会害人？线程栈的虚拟内存 vs 物理内存账怎么算？如何用 `threading.stack_size` 与系统配额推导线程数上限？

**答**：
结论：默认线程栈（Linux pthread 默认 8MB，macOS 主线程 512MB/次线程 512KB 级）首先是**虚拟地址空间预留**，只有真正写到的页才占物理内存（RSS）——所以裸算 500×8MB=4GB 是错的；但容器里它仍通过两条路杀死你：① glibc malloc 的 arena 与栈守卫页使实际 RSS 远大于"只算已写页"的乐观值；② 若通过 `ulimit -v`/`RLIMIT_AS` 限虚拟内存，或 JVM 式按 VmSize 告警的监控，预留即爆。Python 侧可控参数：`threading.stack_size(n)`（后续新线程生效，最小值平台相关，Linux 通常 ≥32KB，macOS ≥512KB 且需 4KB 对齐）。

取舍：小栈省虚拟内存但深递归/C 扩展易段错误；生产上 Python 线程栈 256KB~1MB 通常够（Python 帧在堆上，栈主要给 C 层）。线程数上限公式：`上限 ≈ min( 虚拟内存预算 / stack_size, RLIMIT_NPROC - 预留, 实际有意义并发 )`——最后一条是重点：线程受 GIL 与 IO 阻塞占比约束，500 个多数是浪费，应转进程池/协程。

实战：容量账示例——2GB 容器留 512MB 给堆，线程预算 512MB ÷ 512KB = 1024 虚拟上限；真实并发需求 200，则池设 200 + 显式 `stack_size(512*1024)`，并监控 `/proc/self/status` 的 VmSize 与 RSS 双指标。

```python
import threading
import resource

# 当前进程限额与默认栈
print("soft/hard NOFILE:", resource.getrlimit(resource.RLIMIT_NOFILE))
try:
    soft_as, hard_as = resource.getrlimit(resource.RLIMIT_AS)
    print("RLIMIT_AS (virtual mem cap):", soft_as, hard_as)
except (ValueError, OSError) as e:
    print("RLIMIT_AS not available:", e)

# 平台最小栈约束：设过小会抛 ValueError（macOS 底线 512KB、需对齐）
try:
    threading.stack_size(512 * 1024)         # 后续创建的线程生效，不影响已有线程
    print("stack_size set to 512KB")
except ValueError as e:
    print("stack_size rejected:", e)
    threading.stack_size(0)                  # 0 = 回到系统默认

results = []

def worker(i):
    # Python 帧在堆上；栈只承载 C 层（解释器 C 代码、扩展调用）
    results.append(i * 2)                    # list.append 由 GIL 保护，线程安全

barrier = threading.Barrier(20)
def barrier_worker(i):
    barrier.wait()                           # 同批并发，测栈设置下的行为
    worker(i)

threads = [threading.Thread(target=barrier_worker, args=(i,)) for i in range(20)]
for t in threads:
    t.start()                                # 用刚设的 512KB 栈
for t in threads:
    t.join()
print("workers done:", len(results))

# 容量推导演示（纯账面计算）
budget_mb = 512
stack_kb = 512
virtual_cap = budget_mb * 1024 // stack_kb
print(f"formula: {budget_mb}MB budget / {stack_kb}KB stack -> {virtual_cap} threads max")
```

**追问一**：为什么 Python 线程的栈需求主要来自 C 而不是 Python 递归？——Python 函数调用走解释器帧（堆分配），栈上只留一层 C 调用；但 `json`、`lxml`、正则引擎等 C 实现的递归直接吃栈，512KB 栈下 C 递归爆得比 `sys.setrecursionlimit` 更早。

**追问二**：`stack_size(0)` 与不设置的区别？——0 表示恢复平台默认；注意它只影响"设置之后创建"的线程，主线程栈由 OS 决定不可改；这也是为什么池化线程要在创建 executor 前设置。

**追问三**：如何在线上区分"栈不够"与"堆泄漏"？——栈溢出表现为 segfault/`threading` 线程静默死亡（C 层）或 RecursionError（Python 层），RSS 平稳；堆泄漏 RSS 单调涨；用 py-spy dump + VmSize/RSS 分离指标定位。

## 背诵要点
- 线程栈默认 8MB（Linux）是虚拟预留，RSS 只算已写页；但 RLIMIT_AS/容器监控按 VmSize 算时预留即爆。
- `threading.stack_size(n)` 只对之后新建线程生效，macOS 底线 512KB 且需对齐；Python 帧在堆上，栈压力来自 C 扩展递归。
- 上限公式 = min(虚拟内存预算/栈大小, RLIMIT_NPROC, 有效并发)；GIL 下 500 线程多数是浪费，改池/协程。
