### Q5655 · 应用层微批聚合的延迟吞吐成本账

难度：P7 ｜ 标签：微批、批量接口、延迟、吞吐、成本工程

**问**：把逐条写 RPC/日志/DB 改成"攒 N 条或 T 毫秒"的微批，吞吐提升与延迟代价怎么定量？`N 上限` 与 `T 窗口` 两个旋钮在不同流量下如何联动（低流量时 T 主导、高流量时 N 主导）？批内部分失败、批次超时放大这些新故障怎么治理？

**答**：
结论：微批的本质是**用延迟换固定开销的摊销**。单条成本 `c0`（RPC 往返/连接占用/序列化），批量成本 `c1 + c0'·b`（一次提交 + 每条边际），批大小 b 的收益 = `c0/c1` 的摊销比。批大小实际由两旋钮竞争决定：`b = min(N_max, 到达率 × T)`——低流量时 T 窗口凑不满，延迟固定增加约 `T/2`（均匀到达假设），吞吐收益趋零；高流量时 T 内轻松超过 N_max，延迟增加压到 `N_max/(2×到达率)`，收益由 N 主导。所以**容量规划要分流量档分别算账**：夜间低峰微批几乎纯负收益（白加延迟），可按流量动态关断（到达率低于阈值直接逐条发）。

取舍：微批引入三类新故障：① 批内部分失败——要么整批重试（幂等+去重成本）、要么逐条回执（协议复杂度），必须在协议层定死；② 超时放大——下游故障时一批全超时，重试又整批放大流量，重试要按"单条预算"而非"批预算"；③ 攒批缓冲自身成了新的持久性风险（进程崩了批里数据全丢），对强一致写要落盘先行。

实战：日志/指标/埋点类容忍秒级延迟的最适合微批（N=100–500，T=200ms–1s）；交易写链路慎用，若用必须 WAL 先行；观察指标用"批填充率分布"（`批大小/N_max` 的 P50/P90）判断旋钮是否配错——填充率长期 ~1 说明 N 主导可再加大，长期 ~0 说明 T 主导应关断或降 T。

```python
import random, time

# 1) 解析模型：批大小 = min(N_max, 到达率 x T)，延迟增量 = 批内平均等待
def batch_model(rate, T, N_max, c0=1.0, c1=8.0):
    b = min(N_max, rate * T)
    if b < 1:                                   # 低流量：T 主导，几乎无收益
        per_item_cost = c0
        extra_latency = T / 2
        return dict(mode="T-dominated", b=0, cost_per_item=c0, extra_latency=extra_latency)
    extra_latency = b / (2 * rate)              # 均匀到达：平均攒批等待
    cost_per_item = (c1 + c0 * b) / b
    return dict(mode="N-dominated" if rate * T > N_max else "mixed",
                b=round(b, 1), cost_per_item=round(cost_per_item, 3),
                extra_latency=round(extra_latency, 4))

for rate in (5, 50, 5000):
    m = batch_model(rate, T=0.2, N_max=200)
    print(f"rate={rate:>5}/s -> {m}")

# 2) 微批缓冲器：满 N 或超 T 即 flush，演示填充率与关断
class MicroBatcher:
    def __init__(self, n_max=5, t_window=0.05, rate_floor=None, sink=print):
        self.n, self.t, self.sink = n_max, t_window, sink
        self.rate_floor = rate_floor
        self.buf, self.last, self.fills = [], time.monotonic(), []

    def add(self, item, rate=None):
        if self.rate_floor and rate is not None and rate < self.rate_floor:
            self.sink([item])                   # 低流量关断：逐条直发
            return
        self.buf.append(item)
        if len(self.buf) >= self.n or time.monotonic() - self.last >= self.t:
            self.flush()

    def flush(self):
        if self.buf:
            self.fills.append(len(self.buf) / self.n)
            self.sink(self.buf)
            self.buf, self.last = [], time.monotonic()

sent = []
mb = MicroBatcher(n_max=5, t_window=0.05, sink=sent.append)
for i in range(12):                             # 快速到达：N 主导
    mb.add(i); time.sleep(0.005)
mb.flush()
print("batches:", len(sent), " fill rates:", [round(f, 2) for f in mb.fills])

# 3) 批内部分失败：整批重试前先按条去重（模拟幂等回执）
delivered, batch = set(), sent[0]
def deliver(items):
    ack = [it for it in items if random.random() > 0.2]
    delivered.update(ack)
    return [it for it in items if it not in delivered]

retry = deliver(batch)
print("partial fail -> retry only:", retry, " delivered:", sorted(delivered))
```

**追问一**：为什么"批填充率"是比"平均批大小"更好的旋钮校准指标？——平均批大小被高低流量混合稀释，填充率直接暴露旋钮与到达率的错配方向：长期低填充 → N 太大或流量太低（考虑关断/降 N），长期贴顶 → N 太小（限流瓶颈），且它对突发流量敏感，能提前暴露"攒批层成为限速器"。

**追问二**：下游批量接口的"批超时"应该怎么定，与单条超时什么关系？——批超时 ≈ 单条超时 + 批处理边际时间，不能简单 × 批大小；正确做法是让下游支持部分回执（per-item status），超时后已提交部分按回执处理、未确认部分按单条幂等键重试，避免"整批重来"的流量放大。

## 背诵要点
- `b = min(N_max, rate×T)`：低流量 T 主导纯加延迟（可关断），高流量 N 主导收益摊销比 c0/c1。
- 新故障三件套：批内部分失败（幂等回执协议）、超时放大（按单条预算重试）、缓冲丢失（WAL 先行）。
- 校准看批填充率分布：贴顶加 N、长期低填充降 T 或关断。
