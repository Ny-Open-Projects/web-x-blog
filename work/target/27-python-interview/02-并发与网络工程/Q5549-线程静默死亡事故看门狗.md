### Q5549 · 线程静默死亡的事故复盘与看门狗设计

> 难度:★★★★ | 标签:threading, excepthook, 事故复盘, 看门狗

**问**：一次事故：后台同步线程某晚抛了未捕获异常后"悄悄死了"，主进程健康检查全绿，数据同步停摆 12 小时才发现。为什么线程内的未捕获异常不会让进程崩溃？`threading.excepthook`（3.8+）如何兜底？如何设计看门狗让"线程死了"变成分钟级告警？

**答**：机制：线程的未捕获异常只走该线程的收尾（`threading.excepthook`，默认打印 traceback 到 stderr 后线程终止），**进程与其他线程不受影响**——这与主线程不同（主线程未捕获异常 → 进程退出）。所以"worker 死了、进程活着"是结构性盲区：健康检查探的是进程/端口，探不到内部线程的存活性。三层防线：1) **兜底钩子**：全局替换 `threading.excepthook`，把线程名、栈、异常接入告警与 metrics（线程死亡计数）；2) **看门狗**：每个关键 worker 注册心跳（最近成功时间戳），独立监控线程定期检查 `now - last_beat > SLA` 即触发告警/重启线程——重启要重建资源（连接、上下文）而不是裸 respawn；3) **根因防御**：worker 主循环顶层 `except Exception` 留痕并继续（把"预期异常"变成可恢复），只对不可恢复状态（如认证失效）主动退出并触发重建。注意两个坑：a) `Future` 的异常在 `concurrent.futures` 里被"存起来"，不调用 `result()` 就无人感知（Q418 的 asyncio 对应物同理）——池化任务要在 done callback 里统一检异常；b) excepthook 在 interpreter 关闭期可能不被调用，不能作为唯一防线。

```python
# file: code/02_并发与网络工程/q5549_silent_thread_death.py
import threading
import time

def default_hook(args):
    print(f"[excepthook] 线程 {args.thread.name} 死亡: {args.exc_type.__name__}: {args.exc_value}")

threading.excepthook = default_hook              # 3.8+ 全局兜底, 真实环境接告警

class Watchdog:
    """心跳看门狗: 关键 worker 定期报活, 超时告警并重启"""
    def __init__(self, sla=0.5):
        self.beats = {}
        self.sla = sla
        self.lock = threading.Lock()

    def register(self, name):
        with self.lock:
            self.beats[name] = time.monotonic()

    def beat(self, name):
        with self.lock:
            self.beats[name] = time.monotonic()

    def check(self):
        now = time.monotonic()
        with self.lock:
            return {n: now - t for n, t in self.beats.items() if now - t > self.sla}

wd = Watchdog()
STOP = threading.Event()

def sync_worker(wd):
    """事故原型: worker 主循环顶层兜底 + 心跳; 兜不住的异常走 excepthook"""
    wd.register("sync-worker")
    while not STOP.is_set():
        try:
            time.sleep(0.1)                     # 模拟同步一步
            wd.beat("sync-worker")
        except Exception:                       # 预期异常: 留痕继续
            pass
    # 只有不抛异常的退出才到这里

def sync_worker_broken():
    time.sleep(0.1)
    raise RuntimeError("认证过期, 不可恢复")     # 未捕获: 线程静默死亡

t_good = threading.Thread(target=sync_worker, args=(wd,), name="sync-worker")
t_good.start()
t_bad = threading.Thread(target=sync_worker_broken, name="sync-worker-v2")
t_bad.start()

time.sleep(0.3)
print("坏线程存活:", t_bad.is_alive(), "(False = 已静默死亡, 进程仍健康)")
stale = wd.check()
print("看门狗检查 -> 超时项:", stale, "(重启 worker + 告警)")
STOP.set(); t_good.join(timeout=1)
print("好线程优雅退出:", not t_good.is_alive())
```

**追问**：1) 为什么 `concurrent.futures` 的异常不会触发 `threading.excepthook`？——池 worker 会捕获任务异常存入 Future（设计如此，Q418 对应 asyncio 的 done callback 缺失问题），excepthook 只管"真的没人接"的异常；所以池化任务必须配 done callback 或强制遍历 `as_completed` 收异常。2) 看门狗心跳应该打在循环哪一层？——"一步成功完成"处而不是循环开头，否则 worker 死循环但实际不干活（假活）也能骗过心跳；关键路径要区分"活着"与"在产出"（如带进度计数的心跳）。3) 线程重启如何避免状态污染？——重建式重启：新线程持有全新连接/上下文，旧线程资源显式回收；共享可变状态要经过队列交接而不是直接复用。

## 背诵要点
- 线程未捕获异常只杀自己（走 threading.excepthook 默认打 stderr），进程健康检查全绿——结构性盲区。
- 三层防线：全局 excepthook 接告警 + 心跳看门狗（超时重启）+ 主循环 except Exception 留痕续跑。
- Future/Task 的异常存起来不报，必须 done callback / as_completed 显式收割。

## 复盘追问
- 健康检查"全绿"但功能停摆 12 小时，如何设计能探到"内部线程活性"的深度探针？（提示：readiness 里带上各关键 worker 的心跳年龄，超龄即 NotReady）
- 不可恢复异常（认证过期）与可恢复异常在 worker 里应分别走什么路径？（提示：可恢复留痕续跑，不可恢复主动退出 + 触发重建式重启 + 区分告警级别）
