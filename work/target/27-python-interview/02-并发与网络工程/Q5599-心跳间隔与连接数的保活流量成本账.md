### Q5599 · 心跳间隔与连接数的保活流量成本账

难度：P6-P7 | 标签：成本工程 | keepalive | 容量推导

**问**：50 万条长连接的推送网关，产品要求"30 秒内感知死链"。心跳方案怎么定间隔？间隔定了之后每秒包量、带宽、服务端 CPU 的账怎么算？TCP keepalive 三参数和应用层心跳的取舍是什么？

**答**：
结论：感知延迟上限 ≈ 心跳间隔 + 超时判定次数，两者是"检测速度"与"成本"的兑换关系。成本账公式：每秒心跳包 = 连接数 / 间隔；50 万连接、间隔 30s = 约 1.7 万包/秒，每包按 64 字节（IP20+TCP32 或 WS 帧 6B 头+payload）≈ 1.1MB/s 出口流量，服务端 CPU 主要是每包的 epoll 唤醒 + 协议解析——真正贵的不是带宽而是**每包固定开销**。缩短间隔到 5s = 10 万包/秒，唤醒成本×6，容量直接翻档。TCP keepalive 的三参数（`TCP_KEEPIDLE`/`KEEPINTVL`/`KEEPCNT`，Python 3.11+ 有 `socket` 常量可直接 setsockopt）默认 2 小时起步，要改到"30s 感知"需 idle=25/intvl=5/cnt=1；内核心跳零应用 CPU，但穿过 NAT/代理时可能被丢弃，且无法携带鉴权与业务状态。
取舍：公网移动端用应用层心跳（可带序号/鉴权/时钟），内网机器间用内核 keepalive 省应用 CPU；间隔自适应（弱网加密、空闲加长）能把均值成本降一半。
实战：推导表进设计文档：`间隔 → 包率 → 带宽 → CPU 唤醒上限`；网关按"心跳包率 = 核数 × 每核包预算"反推最大连接数。

```python
import socket, math

def heartbeat_cost(conns, interval_s, pkt_bytes=64,
                   per_pkt_cpu_us=8, cores=8):
    pkt_rate = conns / interval_s                 # 包/秒（客户端发起、服务端响应）
    bw_mbps = pkt_rate * pkt_bytes * 8 / 1e6      # 双向约 ×2，此处算单边
    cpu_util = pkt_rate * per_pkt_cpu_us / 1e6 / cores
    print(f"{conns:>7,} 条 × {interval_s:>2}s 间隔 → "
          f"{pkt_rate:>10,.0f} pkt/s, 单边 {bw_mbps:6.1f} Mbps, "
          f"CPU 唤醒占比 ≈ {cpu_util*100:5.1f}%")
    return pkt_rate, bw_mbps, cpu_util

print("成本账：")
for iv in (30, 15, 5):
    heartbeat_cost(500_000, iv)
print("\n结论：间隔 30→5s，包率 ×6，CPU 唤醒成本同倍数上涨；感知延迟与成本线性兑换")

# TCP keepalive 三参数（3.11+ 常量齐全；Linux 支持，macOS 部分）
def set_keepalive(sock, idle=25, intvl=5, cnt=1):
    sock.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
    try:
        sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPIDLE, idle)
        sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPINTVL, intvl)
        sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPCNT, cnt)
        return f"kernel keepalive: {idle}s 空闲后每 {intvl}s 探测 {cnt} 次 → 感知 ≤30s"
    except (AttributeError, OSError) as e:
        return f"内核参数受限({e})，降级应用层心跳"

print(set_keepalive(socket.socket()))
# 感知时间公式：idle + intvl*cnt ≤ 目标
target = 30
idle, intvl, cnt = 25, 5, 1
assert idle + intvl * cnt <= target
print(f"内核方案感知上限 {idle + intvl*cnt}s ≤ 产品目标 {target}s")

# 自适应间隔的均值收益
def adaptive_cost(conns, active_ratio=0.3, hot_iv=15, idle_iv=60, pkt=64):
    rate = conns * (active_ratio / hot_iv + (1 - active_ratio) / idle_iv)
    print(f"自适应间隔：均值 {rate:,.0f} pkt/s（固定 15s 方案 {conns/15:,.0f}）")
adaptive_cost(500_000)
```

**追问 1**：为什么服务端不应该由客户端心跳完全决定死链判定？
- 追问 2 层：服务端要独立维护"最后收到包时刻"的读超时（比如 2.5×间隔），客户端心跳丢失但链路假活（半开）时只有服务端超时能收线。
- 追问 3 层：半开连接的回收还要防"重连风暴"——超时踢线与客户端重连退避联动，否则 30s 间隔下网络抖动会造成同步踢+同步重连的尖峰。

**追问 2**：WebSocket 心跳的帧级成本和裸 TCP 有什么不同？
- 追问 2 层：WS Ping/Pong 控制帧最小 2 字节头部，小 payload 成本低且协议层规定 pong 必答，检测语义内建；裸 TCP 应用层心跳要自己定义帧格式。
- 追问 3 层：代理/网关对 WS idle 连接有自有超时（常 60s），心跳间隔必须小于链路上最短的 idle 超时，取链路 min 而不是单跳配置。

## 背诵要点
1. 包率 = 连接数/间隔，成本大头是每包 epoll 唤醒+解析 CPU，间隔减半成本翻倍，感知延迟与成本线性兑换。
2. TCP keepalive 三参数 idle/intvl/cnt 之和 ≤ 感知目标（如 25+5×1≤30s），零应用 CPU 但穿 NAT 可能被丢。
3. 间隔必须小于链路最短 idle 超时（取 min）；自适应间隔把均值成本降一半。

## 复盘追问
1. 网关 CPU 飙高为什么先查心跳配置？——心跳是"恒定唤醒源"，间隔激进时 epoller 每秒唤醒次数直接上量级。
2. 50 万连接感知 30s 的下限怎么算？——包率 1.7 万/s × 每包 CPU 预算反推核数，若不达标先调间隔或换内核 keepalive 分流。
