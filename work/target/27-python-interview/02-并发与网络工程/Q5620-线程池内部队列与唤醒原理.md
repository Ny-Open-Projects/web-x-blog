### Q5620 · ThreadPoolExecutor 的内部队列与 worker 唤醒原理

> 难度:★★★★★ | 标签:原理深挖, concurrent.futures, 线程池

**问**:`ThreadPoolExecutor` 的 `submit` 为什么"无界"——没人提交上限，队列可以无限涨？空闲线程怎么被"叫醒"？worker 数怎么随任务动态伸缩（`_adjust_thread_count`）？理解这套内部结构能解释哪些线上现象？

**答**:结论：ThreadPoolExecutor（3.9+ 实现）的骨架是三件套：a) **无界 `SimpleQueue` 任务队列**：`submit` 把 `_WorkItem(future, fn, args, kwargs)` 丢进队列就返回——没有容量上限，所以"提交快于消费"时内存无界增长（Q5506 的背压设计要在 submit 侧自建 semaphore 才能兜住）；b) **懒建线程 + 唤醒**：每 submit 都会调 `_adjust_thread_count`，当队列非空且 `len(threads) < max_workers` 就 `Thread()` 再建一个；空闲 worker 阻塞在 `work_queue.get(block=True)` 上——Python 的 `SimpleQueue` 内部用 **lock 的条件通知**（C 层 `_thread.lock` 的 acquire 阻塞），submit 的 `put` 会唤醒一个等待线程，没有 select/epoll 那种批量唤醒；c) **动态退场**：worker 取任务前先 `_work_queue.get(block=True, timeout=None)`，3.9+ 引入空闲退出——取任务带 `timeout`，超时拿不到就把线程从 `threads` 集合摘除自然死亡（`_idle_semaphore` 记录空闲数），所以**线程数会在任务洪峰后回落**，回落节奏由空闲超时（较短的秒级）决定。可解释的线上现象：① 为什么第一波任务的延迟高（线程懒建，首批并发受建线程成本，对照 Q5597）；② 为什么 `shutdown(wait=True)` 能排空（直到队列空且线程退出）；③ 为什么高峰内存涨不落（无界队列里的 `_WorkItem` 与其闭包引用在排队期间都活着）。

```python
import threading, time
from concurrent.futures import ThreadPoolExecutor

ex = ThreadPoolExecutor(max_workers=4)

def task(i):
    time.sleep(0.05)
    return i

# 1) 懒建线程：submit 后线程数逐步逼近 max_workers
first = ex.submit(task, 0).result()
print("首个任务完成后线程数:", len(ex._threads), "/", ex._max_workers)

# 2) 提交 8 个任务，观察线程与队列的动态
futs = [ex.submit(task, i) for i in range(8)]
print("提交后瞬间线程数:", len(ex._threads), "（懒建，逐步逼近 4）")
print("队列仍在消化:", ex._work_queue.qsize() >= 0, "| 空闲信号量:", ex._idle_semaphore._value if hasattr(ex._idle_semaphore, '_value') else '?')
[f.result() for f in futs]

# 3) 空闲线程退场：空闲超时（秒级）到达后，多余线程逐个自然死亡
time.sleep(1.5)
print("空闲 1.5s 后线程数:", len(ex._threads), "（线程集合只减不增，全部退场后才为 0）")

# 4) 唤醒语义验证：get 阻塞的 worker 会被 put 直接唤醒（无轮询周期）
t0 = time.perf_counter()
probe = ex.submit(task, 99)
print(f"submit 返回耗时: {(time.perf_counter()-t0)*1e3:.1f}ms（仅入队+唤醒，微秒级）")
print("result:", probe.result())
ex.shutdown(wait=True)
print("shutdown 排空后线程数:", len(ex._threads))
```

**追问一层**:`_adjust_thread_count` 为什么放在 `submit` 里而不是定时器？如果任务抛异常，`_WorkItem` 里的 future 如何把异常带回、worker 会不会死掉？
**追二层**:`SimpleQueue` 的 get 阻塞在 C 层 lock 上与 `queue.Queue` 的 Condition 链有什么成本差异（对照 Q5517 队列选型）？为什么这个"每任务一个对象、无界队列"设计在 GIL-free（PEP 703）下要重做（对照 Q5577）？

**背诵要点**
- submit 进无界 SimpleQueue 即返回：无背压，提交快于消费时内存无界增长。
- 每次submit 调 `_adjust_thread_count` 懒建线程；空闲 worker 阻塞在 C 层 lock get，put 唤醒一个。
- 空闲超时后线程退场收缩；shutdown(wait=True) 排空队列等线程退出。

**复盘追问**
- 线上服务高峰 RSS 涨不落，profile 显示 `_WorkItem` 大量滞留，治理顺序是什么？提示：先加提交侧背压（信号量），再压下游耗时，最后看线程数配置。
- 为什么"测出线程池 QPS 固定在 N×单线程吞吐"与预期并发不符？提示：检查任务里是否有 GIL 阻塞段与锁内 IO（引 Q5541）。
