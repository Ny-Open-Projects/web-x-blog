### Q5524 · 事件循环空转复盘：CPU 100% 但没有慢回调

> 难度:★★★★☆ | 标签:事件循环, 空转, 事故复盘

**问**：asyncio 进程 CPU 打满，但 `loop.set_debug(True)` 的慢回调日志一条没有——回调明明都很快，循环为什么烧满 CPU？空转的典型成因有哪几类？"循环被撑快的证据"怎么量化？

**答**：慢回调检测（Q2401）只抓"单次回调耗时长"，抓不住**回调极快但无限重排**的空转——每次 callback 都是微秒级，debug 日志永远安静，循环却在高速自旋。四类典型成因：1) **call_soon 自引用循环**：任务在回调/无 await 循环里重新 `call_soon` 自己，或 `while True` 里只做同步逻辑不产生任何阻塞点；2) **fd 注册残留**：`add_writer` 忘了 remove（socket 缓冲未满时几乎恒可写），selector 每轮都报就绪（Q1586 的经典 fd bug）；3) **timeout=0 / sleep(0) 轮询**：把等待写成 `await asyncio.sleep(0)` 轮询标志位；4) **定时器堆毒**：`call_later(0, ...)` 自我重排形成 0 延迟定时器风暴。量化证据：用 `time.process_time()` 测"空闲事件循环的 CPU 增速"——健康循环在无事件时接近 0，空转循环 0.5 秒烧满 0.5 秒 CPU；再配合 py-spy（Q840）看火焰图热点落在 `_run_once`/`epoll.poll(0)` 即可归因。修复方向都是"变轮询为事件驱动"：Event/Queue 挂起等待、发完必 remove_writer、sleep(0) 换成真正会挂起的 await。

```python
# file: code/02_并发与网络工程/q5524_loop_spin.py
import asyncio, time

def measure(seconds, spin):
    """在事件循环里待 seconds 秒,返回 CPU 时间增速(空转循环接近 1.0)"""
    async def runner():
        start_cpu = time.process_time()
        start_wall = time.perf_counter()
        if spin:
            def spinner():              # 成因 1: call_soon 自引用,回调极快但无限重排
                asyncio.get_running_loop().call_soon(spinner)
            asyncio.get_running_loop().call_soon(spinner)
        await asyncio.sleep(seconds)
        return (time.process_time() - start_cpu) / (time.perf_counter() - start_wall)
    return asyncio.run(runner())

idle = measure(0.5, spin=False)
spin = measure(0.5, spin=True)
print(f"健康循环 CPU 增速: {idle:.3f} (无事件时接近 0)")
print(f"空转循环 CPU 增速: {spin:.3f} (接近 1.0,回调全都很'快')")
assert spin > 0.3 and idle < 0.15, "空转特征未复现(机器负载干扰,重跑)"

# 成因 3 的反面教材: sleep(0) 轮询标志位 -> 让渡点变热点
flag = False
async def poller():
    n = 0
    t0 = time.perf_counter()
    while not flag and time.perf_counter() - t0 < 0.05:
        await asyncio.sleep(0)          # 每 0 让渡一次,空转同款
        n += 1
    return n
n = asyncio.run(poller())
print(f"sleep(0) 轮询 50ms 让渡次数: {n} (每毫秒数百次,纯烧 CPU)")
print("修复: sleep(0) -> asyncio.Event.wait(),轮询变事件驱动")
```

**追问**：1) 为什么 debug 模式抓不到？——`slow_callback_duration` 只计**单个回调执行时长**；自旋回调每次都极快，不超标；且 call_soon 重排不经过回调计时入口。2) 生产上第一时间怎么确认是空转而不是 CPU 密集计算？——py-spy dump：空转的热点在循环框架函数（`_run_once`/`selector.poll`），CPU 密集热点在业务函数栈（Q840/Q810）；再看该进程是否有慢请求响应正常。3) fd 注册残留与自旋怎么区分？——空转伴随大量 ready 事件（strace 可见 epoll_wait 立即返回），call_soon 自旋则 epoll_wait 全是超时返回、ready 计数为 0。

## 背诵要点
1. 空转 = 回调极快但无限重排，慢回调检测（slow_callback_duration）天然抓不到。
2. 四成因：call_soon 自引用、add_writer 残留、sleep(0) 轮询、call_later(0) 风暴。
3. 量化：process_time 增速接近 1.0 即空转；py-spy 热点落在 _run_once/epoll.poll 归因。
