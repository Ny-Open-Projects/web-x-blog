### Q5645 · fd 配额与 asyncio 连接上限容量账

难度：P6 ｜ 标签：fd、RLIMIT_NOFILE、asyncio、容量规划

**问**：长连接网关压测到 8 万连接后大面积 `OSError: Too many open files`。为什么每个连接/每个上游调用都占一个 fd？`RLIMIT_NOFILE` 在容器与 systemd 下各归谁管？连接数上限的容量账怎么推导？

**答**：
结论：fd 是 Unix 下一切 IO 的句柄——socket、打开的文件、eventfd/pipe（asyncio 自身还占几个：self-pipe 唤醒、selector）、日志文件、DB 连接都消耗同一个配额池。`Too many open files` 常在压测尖峰才爆，是因为空闲期 fd 回收得快。容量账：`可服务连接数 ≈ soft RLIMIT_NOFILE − 基础占用（日志/DB/event loop 内部，一般 <200）− 每请求临时 fd 峰值`。Python 里 `resource.getrlimit(RLIMIT_NOFILE)` 可读，`setrlimit` 提 soft 值（≤hard）；容器里由 Docker/K8s 的 `ulimits/nofile` 与 systemd 的 `LimitNOFILE` 双层管辖，进程内 raise 超不过容器给的 hard 上限。

取舍：把 NOFILE 调到百万级不是免费的——epoll 本身 O(1) 但每连接的内核 socket 缓冲（约 2×~64KB）、Python 对象（约每连接 KB 级）都是内存账；百万连接要 C10M 级工程（SO_REUSEPORT 多进程 + 每连接对象瘦身）。另有 `RLIMIT_NPROC`（线程数）、`tcp_mem` 内核级水位各管一段。

实战：三步落地——① 启动时自检 `getrlimit` 并把"预期连接数 + 30% 余量"与 soft 值比对，不足即 fail-fast；② 打点当前 fd 使用量（`/proc/self/fd` 计数或 `len(os.listdir('/proc/self/fd'))`）作为容量指标；③ 排查泄漏：连接未 close、`urllib`/数据库游标未关闭都会沉淀 fd，用 lsof 按类型聚类。

```python
import os
import resource
import socket
import contextlib

soft, hard = resource.getrlimit(resource.RLIMIT_NOFILE)
print(f"RLIMIT_NOFILE soft={soft} hard={hard}")

def open_fd_count() -> int:
    """当前进程 fd 使用量（macOS 无 /proc，用 socket 计数演示）"""
    try:
        return len(os.listdir("/proc/self/fd"))
    except OSError:                      # macOS 降级：估算基础占用
        return -1

base = open_fd_count()
print("open fds now:", base)

# 可服务连接数账面推导
reserved = 200                          # 日志/DB/event loop 内部基础占用
serving_cap = soft - reserved
print(f"serving cap ≈ {serving_cap} connections (soft={soft})")

# 演示：批量开 socketpair 计数直到接近账面上限（只开 50 个，安全演示）
pairs = []
try:
    for _ in range(50):
        a, b = socket.socketpair()
        pairs.append((a, b))
    print("opened socketpairs:", len(pairs), "fd delta:", open_fd_count() - base if base >= 0 else "n/a")
finally:
    for a, b in pairs:
        a.close(); b.close()
print("fd delta after close:", open_fd_count() - base if base >= 0 else "n/a")

# 启动自检模板：预期连接数与 soft 对比，不足则 fail-fast
EXPECTED_CONNS = 80_000
if soft < EXPECTED_CONNS + reserved:
    print(f"[fail-fast] raise RLIMIT_NOFILE: need {EXPECTED_CONNS + reserved}, have {soft}")
else:
    print("[ok] quota sufficient")

# 尝试在进程内抬高 soft（受 hard 限制，容器内常见 hard 也是 65536+）
try:
    resource.setrlimit(resource.RLIMIT_NOFILE, (min(hard, 65536), hard))
    print("soft raised to", resource.getrlimit(resource.RLIMIT_NOFILE)[0])
except (ValueError, PermissionError) as e:
    print("cannot raise in-place:", e, "-> 由容器/systemd 层配置")
```

**追问一**：为什么 asyncio 自己也要"偷"几个 fd？——事件循环需要 self-pipe/socketpair 把"跨线程 call_soon"转成 IO 事件（与 Q5639 self-pipe 唤醒原理同源），子进程通信、信号处理也各占一对；这部分是常驻基线。

**追问二**：`OSError: Too many open files` 抛出后服务还能自愈吗？——accept 新连接、建上游连接全部失败，但**已建立的连接**仍可服务；正确姿势是告警 + 主动丢弃低价值连接（负载削减），等 fd 回落；直接重启会放大雪崩。

**追问三**：epoll 到 10 万 fd 后事件循环会退化吗？——epoll_wait 本身可扩展，退化点通常在 Python 层：每回调的协程调度、对象开销；用 selector 抽样耗时打点确认，必要时分片多 reactor。

## 背诵要点
- socket/文件/DB 连接/event loop 内部结构共享 RLIMIT_NOFILE 一个池；容量账 = soft − 常驻基线 − 每请求峰值。
- 配额三层管辖：进程内 setrlimit ≤ hard，hard 由容器 ulimits/K8s 与 systemd LimitNOFILE 决定。
- 爆 fd 后服务进入"拒新保旧"状态：告警 + 负载削减，不要重启放大雪崩。
