### Q5562 · 多线程锁顺序死锁事故复盘与预防

> 难度:★★★★ | 标签:事故复盘, 死锁, Lock, 锁排序

**问**：转账服务偶发"全体线程挂起、接口全超时"，重启恢复。jstack 类排查确认是两个线程各持一把锁等对方——经典 AB-BA 死锁。Python 里死锁怎么定位？为什么 RLock 救不了？锁排序、超时、防死锁检查器各怎么落地？

**答**：复盘：死锁四条件（互斥、持有并等待、不可剥夺、循环等待）全满足——线程 1 先锁 A 再锁 B，线程 2 先锁 B 再锁 A，两边各拿到第一把后在第二把上永久 block。CPython 的 `Lock.acquire()` 默认无超时且不抛错，**挂起是静默的**，表现为"接口超时但 CPU 空闲"（区别于死循环）。定位：py-spy dump 看各线程栈顶都停在 `lock_acquire`；或 `faulthandler.dump_traceback_later` 定期落栈。修复三件套按优先级：a) **锁全序（lock ordering）**：全局规定按对象 id/名字排序加锁，所有路径先锁 A 后锁 B，循环等待结构性不可能——这是根治，零运行时成本；b) **acquire 超时 + 指标**：`lock.acquire(timeout=5)` 失败告警并释放已持锁重试，治标但把死锁从"永久挂起"降级为"可观测的失败"；c) **RLock 救不了 AB-BA**：RLock 只解决"同线程重入"，两个不同线程互相等照样死——误用 RLock 防死锁是常见误区。工程预防：锁封装成 context manager 统一走"多锁获取函数"（内部排序）；持锁时长打点（超过 P99 告警）；code review 清单加"一把函数里拿两把锁？排序了吗？"。

```python
# file: code/02_并发与网络工程/q5562_deadlock.py
import threading, time, contextlib

lock_a = threading.Lock()
lock_b = threading.Lock()

def transfer_ab(amount):     # 危险: A->B 顺序
    with lock_a:
        time.sleep(0.01)     # 制造窗口
        with lock_b:
            return amount

def transfer_ba(amount):     # 危险: B->A 顺序 (AB-BA 死锁源)
    with lock_b:
        time.sleep(0.01)
        with lock_a:
            return amount

# 1) 根治: 锁全序封装 -- 多锁获取内部按 id 排序
LOCKS = {"account": threading.Lock(), "ledger": threading.Lock(), "wallet": threading.Lock()}

@contextlib.contextmanager
def multi_lock(*names, timeout=2.0):
    """按固定顺序获取多把锁, 超时则报错 (避免持有并等待形成环)"""
    order = sorted(names, key=lambda n: id(LOCKS[n]))
    acquired = []
    try:
        for n in order:
            if not LOCKS[n].acquire(timeout=timeout):
                raise TimeoutError(f"获取锁 {n} 超时, 告警并重试")
            acquired.append(n)
        yield
    finally:
        for n in reversed(acquired):
            LOCKS[n].release()

def transfer_safe(amount):
    with multi_lock("account", "ledger"):
        return amount

# 两个"相反顺序"调用现在都走同一全序, 不死锁
t1 = threading.Thread(target=transfer_safe, args=(1,))
t2 = threading.Thread(target=transfer_safe, args=(2,))
t1.start(); t2.start(); t1.join(timeout=5); t2.join(timeout=5)
print("全序加锁无死锁, 线程存活:", not (t1.is_alive() or t2.is_alive()))

# 2) 对照: acquire 带超时把死锁降级为可观测失败
def bad_pair_demo():
    got_a = lock_a.acquire(timeout=0.1)
    try:
        got_b = lock_b.acquire(timeout=0.1)
        if not got_b:
            print("拿不到 lock_b -> 告警, 释放回滚, 不永久挂起")
        else:
            lock_b.release()
    finally:
        if got_a: lock_a.release()
bad_pair_demo()
print("铁律: RLock 只防重入不防 AB-BA; 多锁必须全序; acquire 一律带 timeout")
```

**追问**：1) 为什么死锁线程不占 CPU 却拖垮服务？——block 的线程不消耗 CPU，但线程池被占满，新请求排队直到全超时；定位信号是"超时激增 + CPU 空闲 + 线程栈停在 acquire"。2) 锁排序在分布式下怎么推广？——单进程内按对象 id 排序；跨服务/跨资源用"资源名字典序"作为全局全序（数据库行锁按主键排序加锁同理）；配合数据库死锁检测（InnoDB 自动回滚一个事务）兜底。3) faulthandler 怎么用？——`faulthandler.dump_traceback_later(60, repeat=True)` 每 60s 落全部线程栈到文件，或 SIGUSR1 触发；比事后 py-spy 抓现场更可靠（进程已挂死时 py-spy 也可能失败）。

## 背诵要点
- AB-BA 死锁条件：两条路径以相反顺序获取两把锁；表现"接口超时+CPU 空闲+栈停在 acquire"；Lock.acquire 默认无超时静默挂起。
- 根治是锁全序（按对象 id/资源名字典序），多锁获取封装成 context manager；RLock 只防同线程重入，防不了跨线程 AB-BA。
- 治标配 acquire(timeout)+告警+释放重试；faulthandler.dump_traceback_later 定期落栈优于事后抓现场。
