### Q5730 · 批量事件与连接饥饿：每轮每 fd 读一次的公平性设计

难度：P6 ｜ 标签：selector、epoll、批量事件、连接饥饿、公平性、EAGAIN、吞吐

**问**：selector/epoll 一次返回一批就绪事件，事件循环该怎么消费——对着一个 fd 贪心读到 EAGAIN 才换下一个，还是每轮每个 fd 只读一次？两种策略各自什么时候出问题？"某条连接吞吐巨大时其他连接响应变慢"的根因是什么？工程上怎么兼顾公平与吞吐？

**答**：
结论：消费策略决定**连接间的公平性**。①**贪心排空**（读到 EAGAIN/数据耗尽才下一个）：单连接吞吐最优、系统调用最省，但一个吞吐大户（批量导出、慢消费端堆积大量上行数据）会让它独占整个事件循环轮次，其他连接的请求排队等待——表现为"个别连接很快、其他连接超时"，即连接饥饿；②**每轮每 fd 读一次**（最多读 N 字节就换下一个 fd）：每个就绪连接在一个轮询窗口内都被服务一次，公平性最好，代价是系统调用次数增多、单连接的批量读优化失效；③epoll 还有第二层饥饿：`epoll_wait` 一次最多返回 maxevents 个事件，事件量大时**排在就绪列表尾部的 fd 当轮根本看不到**，要等下一轮 select——事件风暴时尾部连接的延迟天然有一个轮次的波动；④工程折中：每轮每 fd 设**读取上限**（如 64KB），读满就记住"没读完"，本轮不再管它，下一轮继续——公平性与吞吐兼顾，避免被单连接吸干。

取舍：a) 所有连接地位均等（RPC 网关、IM 服务）：每轮限额读，公平优先——尾部延迟 P99 靠这个压住；b) 连接地位明确分层（管理连接 vs 数据连接）：可以对管理通道每轮必读一次、数据通道贪心排空，把分层写进调度策略而不是靠通用循环猜；c) 事件风暴场景：maxevents 上调（Python selectors 的 select 无显式上限，epoll 后端默认 512）+ 读限额，双管齐下；d) 饿死的极端反面是"轮转太碎"：每 fd 只读 4KB 系统调用开销吃掉收益，限额要按 MTU/应用报文量调（一般 64KB 量级）；e) 与 per-connection 队列配合：限额读到的数据进各连接自己的缓冲队列，由下游线程池消费——事件循环保持轻，饥饿问题转移给队列调度（那是另一个故事）。

实战：事故形态是"网关大促时偶发超时集中在少数用户：某个用户在做大文件上传/导出，其连接在事件循环里被贪心读排空持续占用毫秒级轮次，同轮其他连接的 ping 超时断连；修复为每 fd 每轮 64KB 读取上限，超量延迟到下轮，P99 从 3s 压到 200ms"。下面实测"每轮每 fd 读一次"的公平交付。

```python
# 批量事件与连接饥饿: 每轮处理上限 vs 贪心排空
import selectors
import socket
import time

srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 0))
srv.listen(16)
srv.setblocking(False)
port = srv.getsockname()[1]
sel = selectors.DefaultSelector()
sel.register(srv, selectors.EVENT_READ)

conns = {}
def accept() -> None:
    conn, _ = srv.accept()
    conn.setblocking(False)
    sel.register(conn, selectors.EVENT_READ)
    conns[conn] = {"served": 0, "order": []}

# 3 个客户端先建连
clients = []
for _ in range(3):
    c = socket.create_connection(("127.0.0.1", port))
    clients.append(c)
    time.sleep(0.03)
    for key, _ in sel.select(timeout=0.05):
        if key.fileobj is srv:
            accept()

print("[1] 3 个连接各自发一条消息; 每轮每个 fd 最多读 1 次 -> 轮转公平")
for i, c in enumerate(clients):
    c.send(f"msg-{i}".encode())
    time.sleep(0.03)

served_order = []
deadline = time.monotonic() + 1.0
while len(served_order) < 3 and time.monotonic() < deadline:
    for key, _ in sel.select(timeout=0.05):
        sock = key.fileobj
        if sock is srv:
            accept()
            continue
        data = sock.recv(64)                    # 每轮只读一次: 不贪心
        if not data:
            continue
        served_order.append(data.decode())
        conns[sock]["served"] += 1
print("    交付顺序:", served_order, "<- 三个客户端都在同一轮窗口内被服务")

print("[2] 反模式: 单连接贪心读到 EAGAIN 才罢休 -> 慢场景下其他连接长时间饥饿")
print("    事件量大(批量 maxevents 截断)时, 尾部 fd 要等下一轮 select 才被看到")
print("[3] 取舍: 每轮每 fd 读一次(公平, 系统调用多) vs 读到 EAGAIN(吞吐高, 饥饿风险)")
print("    工程解法: 每轮每 fd 设读取上限(如 64KB), 超量注册 EPOLLOUT/下轮继续, 兼顾公平与吞吐")
for c in clients:
    c.close()
for s in list(conns):
    sel.unregister(s)
    s.close()
srv.close()
```

**追问一**：Nginx/Envoy 这类生产代理用的是哪种策略？它们的 worker_processes 和 reuseport 跟这件事什么关系？—— 生产代理普遍采用**限额 + 多 worker 分摊**的混合：Nginx 的 `worker_connections` 之外有 `multi_accept`（一次 accept 尽量多的 pending 连接）与事件处理总量控制的平衡；Envoy 的事件循环同样对单次事件处理设预算（disruption 预算/每轮处理上限），避免单连接拖垮整个 worker。多 worker + SO_REUSEPORT 让内核把连接哈希分摊到多个事件循环实例——单循环内的饥饿问题被"连接分散到多个循环"稀释，但同一个大流量连接仍然在一个循环里，所以**单循环内的每 fd 限额仍然必要**；reuseport 解决的是 accept 争抢和 worker 负载均衡，不是单连接饥饿，两个机制是叠加关系而不是替代。

**追问二**：level-triggered 和 edge-triggered 模式跟"读到 EAGAIN"的绑定关系是什么？为什么 edge-triggered 强制要求贪心排空？—— level-triggered（默认 poll/select/epoll 默认模式）下，只要缓冲区还有数据，每轮 select 都会**再次报告**该 fd——所以"每轮读一次"是安全的，没读完下轮还会通知；edge-triggered（EPOLLET）只在状态**变化**时报告一次，如果读了一次不读到 EAGAIN，剩余数据不会再触发通知——连接数据滞留、客户端等响应，这就是"ET 必须配非阻塞 + 循环读到 EAGAIN"铁律的来源（Q5544/Q5720 的 EPOLLONESHOT/ET 语义族）。所以本文的"每轮每 fd 读一次"公平策略**天然只适用 LT**；ET 下要公平，得在应用层模拟限额：读到限额后重新 arm 事件（oneshot 重注册/手动往事件队列塞回该 fd），复杂度明显更高——公平性与 ET 的低系统调用开销本质上有张力。

## 背诵要点
- 贪心读到 EAGAIN = 吞吐优先但单连接可吸干事件循环 → 其他连接饥饿；每轮每 fd 限额读 = 公平优先。
- epoll maxevents 批量截断：事件风暴时尾部 fd 当轮不可见，天然多一轮延迟。
- 限额读（64KB 量级）+ 未读完下轮继续，是公平与吞吐的工程折中；ET 模式强制读到 EAGAIN，公平要靠应用层重新 arm。
