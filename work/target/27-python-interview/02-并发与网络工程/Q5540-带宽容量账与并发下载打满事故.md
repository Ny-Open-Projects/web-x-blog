### Q5540 · 带宽容量账：并发下载打满内网的事故与推导

> 难度:★★★★ | 标签:容量规划, 带宽, 事故复盘, 限速

**问**：100 个并发下载大文件的服务把整台宿主机网络打满、连健康检查都超时——这类事故怎么推导预算？带宽、并发、对象大小、RTT 之间的公式是什么？应用层限速怎么做？

**答**：容量账三公式：1) **稳态带宽**：`吞吐(Gbps) = 并发数 × 对象大小(MB) ÷ 平均下载时长(s)`，反推 `并发上限 = 带宽预算 × 时长 ÷ 对象大小`；2) **延迟下限**（传输时间不低于 RTT+握手开销，Q1602 拥塞控制起步）：小文件场景真正瓶颈是 RTT×往返次数而非带宽；3) **共享面**：宿主机/交换机上行是所有租户共享的，单服务打满后邻居的 DNS、监控、日志上报全部劣化——这就是"健康检查超时"的机制（不是进程死了，是 ACK 都挤不进来）。事故复盘要点：a) 症状优先级错乱——先修"健康检查超时"，但根因是下载无预算；b) 正确的修法是**分层预算**：出口总量限速（令牌桶，Q101/Q5518）+ 单请求并发上限 + 大对象走旁路（对象存储直传/下载，走公网或独立 NIC）；c) 应用层限速实现：令牌桶按字节发放（不是按请求数！），配合流式下载逐块 consume；d) 监控指标要预先存在：网卡 pps/带宽利用率、重传率（打满后 TCP 重传飙升是放大器）。

```python
# file: code/02_并发与网络工程/q5540_bandwidth_budget.py
"""带宽预算推导 + 字节级令牌桶限速器."""
import asyncio
import time

# --- 1) 容量账: 从预算反推并发上限 ---
def concurrent_limit(budget_gbps: float, size_mb: float, duration_s: float) -> dict:
    need_gbps = size_mb * 8 / duration_s / 1000      # 单流所需带宽
    limit = max(1, int(budget_gbps / need_gbps))
    return {"单流需求Gbps": round(need_gbps, 3), "并发上限": limit}

print("预算 2Gbps, 500MB 文件, 期望 10s 下载:",
      concurrent_limit(2.0, 500, 10))
print("预算 2Gbps, 1MB 文件, 期望 0.1s 下载:",
      concurrent_limit(2.0, 1, 0.1), "<- 小文件瓶颈在 RTT/连接数, 带宽公式失真")

# --- 2) 字节级令牌桶: 限速的是字节/秒, 不是请求数 ---
class ByteTokenBucket:
    def __init__(self, rate_bps: float, burst: float) -> None:
        self.rate = rate_bps                # 字节/秒
        self.tokens = burst
        self.burst = burst
        self.last = time.monotonic()

    def _refill(self) -> None:
        now = time.monotonic()
        self.tokens = min(self.burst, self.tokens + (now - self.last) * self.rate)
        self.last = now

    async def consume(self, n: int) -> None:
        self._refill()
        if self.tokens < n:                 # 不足则等到攒够
            need = (n - self.tokens) / self.rate
            await asyncio.sleep(need)
            self._refill()
        self.tokens -= n

# --- 3) 流式下载 + 逐块限速 (块大小与限速粒度的关系) ---
async def download_limited(chunks: int, chunk_mb: float,
                           bucket: ByteTokenBucket) -> float:
    t0 = time.monotonic()
    total = 0
    for _ in range(chunks):
        await bucket.consume(int(chunk_mb * 1024 * 1024))
        total += chunk_mb                    # 真实场景这里是 aiohttp 流式读一块
    return time.monotonic() - t0

async def main() -> None:
    # 每块 8MB: 限速发放粒度=8MB, 太粗会"走走停停"; 256KB-1MB 是常用粒度
    bucket = ByteTokenBucket(rate_bps=50 * 1024 * 1024,   # 50MB/s
                             burst=16 * 1024 * 1024)      # 允许 16MB 突发
    elapsed = await download_limited(chunks=8, chunk_mb=8, bucket=bucket)
    print(f"64MB @50MB/s 限速: 实测 {elapsed:.2f}s (理论≈1.28s+突发)")
    print("粒度建议: chunk 256KB-1MB, 限速平滑; 8MB 块+burst 会整段跳变")

asyncio.run(main())

# --- 4) 共享面监控指标清单 ---
for m in ("nic_bandwidth_util(%)", "nic_pps", "tcp_retrans_rate",
          "healthcheck_latency_p99", "download_concurrency_gauge"):
    print("指标:", m)
```

**追问**：1) 为什么小文件场景带宽公式失真？——传输时间被 RTT×往返次数与拥塞窗口爬升主导（慢启动 Q1602），吞吐远低于带宽上限，此时瓶颈是连接数/RTT，公式要换成"每对象往返次数 × RTT"。2) 限速粒度（chunk 大小）怎么选？——块太大令牌发放跳变（突发-空窗交替），太小 syscall/协程切换开销占比升高；256KB-1MB 是常见平衡点，配合 burst 吸收抖动。3) 打满后的重传率为什么是放大器？——缓冲区排队 → RTT 膨胀 → 超时重传 → 有效吞吐进一步下降（Q700/Q1602），拥塞失控是自增强回路，所以重传率要先于带宽利用率告警。

## 背诵要点
- 公式：并发上限 = 带宽预算 × 期望时长 ÷ 对象大小；小文件瓶颈换成 RTT×往返次数。
- 限速限"字节/秒"不是请求数；chunk 256KB-1MB + burst 平滑发放。
- 共享面监控：带宽利用率、pps、重传率、健康检查 p99；重传率是拥塞失控的先行指标。
