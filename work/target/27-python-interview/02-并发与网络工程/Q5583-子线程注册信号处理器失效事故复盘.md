### Q5583 · 子线程注册信号处理器失效的事故复盘

难度：★★★★☆ ｜ 标签：signal / 事故复盘 / asyncio / 优雅停机

**问**：优雅停机代码放在后台初始化线程里跑，`signal.signal(SIGTERM, handler)` 直接 `ValueError`；改到主线程注册后又能跑，但 asyncio 程序里还要换 `loop.add_signal_handler`。这套限制的底层逻辑是什么？两边混用会发生什么？

**答**：
- **结论**：POSIX 信号处理是**进程级**概念，内核要求 handler 安装在进程的某条线程上，CPython 规定只能在**主线程**调用 `signal.signal`——非主线程直接 `ValueError`（这正是事故现场）。信号到达后 CPython 不在内核 handler 里做复杂工作，而是设置标志位，等主线程回到字节码评估循环（eval breaker）再执行 Python 层 handler——所以**主线程阻塞在 C 扩展或长系统调用时 handler 迟迟不跑**。asyncio 用 `loop.add_signal_handler` 把信号接进事件循环的自建管道（self-pipe），由循环统一调度，语义是"信号也是一种就绪事件"。
- **取舍**：两套机制不能混：`signal.signal` 的 handler 在主线程任意字节码边界执行，可能与事件循环的回调并发，破坏 asyncio 的单线程假设；`loop.add_signal_handler` 只能在**运行中的 loop** 上装（且类 Unix 平台，Windows 的 Proactor 不支持 SIGTERM 优雅停机是老坑）。混合使用的正确姿势：程序入口（主线程）先创建 loop 并用 `add_signal_handler` 挂接；同步库不要自己抢注信号。
- **实战**：复盘要点：1）初始化线程里装信号 = 设计错误，信号注册必须回到"进程入口"层；2）asyncio 里用 `signal.signal` 会发生"handler 与 loop 回调交错"的未定义行为，且 `signal.signal` 返回的 old handler 恢复时会**卸掉 loop 的注册**；3）K8s 场景 SIGTERM 只发 PID 1，多进程程序只有主进程收得到，子进程要靠父进程转发或进程组。

```python
"""信号注册的线程限制与两种机制（macOS/Linux，Python 3.9+）"""
import signal, threading, asyncio, time

def handler(signum, frame):
    print(f"[signal.signal handler] 收到 {signal.Signals(signum).name}")

# 1) 非主线程注册 → ValueError（事故现场）
err = []
def try_register_in_thread():
    try:
        signal.signal(signal.SIGTERM, handler)
    except ValueError as e:
        err.append(str(e))
t = threading.Thread(target=try_register_in_thread)
t.start(); t.join()
print("子线程注册结果:", err[0][:60] if err else "意外成功")

# 2) 主线程注册 OK：处理时机是主线程回到字节码循环时
signal.signal(signal.SIGTERM, handler)
print("主线程注册 OK，handler:", signal.getsignal(signal.SIGTERM).__name__)

# 3) asyncio 侧：loop.add_signal_handler（类 Unix；必须 loop 运行中安装）
async def main():
    loop = asyncio.get_running_loop()
    got = asyncio.Event()
    def aio_handler():
        print("[loop handler] SIGUSR1 → loop 调度执行")
        got.set()
    loop.add_signal_handler(signal.SIGUSR1, aio_handler)
    import os
    os.kill(os.getpid(), signal.SIGUSR1)   # 自发信号，模拟运维动作
    await asyncio.wait_for(got.wait(), timeout=2)
    loop.remove_signal_handler(signal.SIGUSR1)
    print("loop 侧信号 → 事件统一调度，无并发交错")

asyncio.run(main())
signal.signal(signal.SIGTERM, signal.SIG_DFL)  # 复位，避免影响后续演示
print("done")
```

**追问链**
1. CPython 怎么实现"信号在 Python 层安全执行"？长 C 调用时信号会丢吗？
   1. 内核 handler 只置全局标志 + 写 wakeup fd，主线程在 eval breaker 检查标志后执行 Python handler；主线程卡在 numpy 长计算/`read()` 系统调用里时，Python handler 延迟到调用返回——不丢（fd 有缓冲）但明显迟滞，这就是"优雅停机等了 30 秒"的形态。
   2. 追问：time.sleep 能被信号打断吗？——3.x 中 time.sleep 收到信号会提前返回（PEP 475 后自动重试除非 handler 抛异常），行为与直觉有差，停机逻辑别依赖 sleep 可中断。
2. `loop.add_signal_handler` 的 self-pipe 机制是怎么工作的？为什么主线程忙等时它更灵敏？
   1. loop 内部建 pipe，内核 handler 往 pipe 写字节，pipe 与业务 fd 一起进 epoll/kevent——信号被"翻译"成一次 IO 就绪事件，与其他回调同队列串行执行；只要 loop 在 select/kevent 上，信号即刻被处理，不存在"字节码边界"等待。
   2. 追问：Windows 上怎么办？——Proactor loop 不支持 add_signal_handler，用 `signal.signal`（主线程）+ `loop.call_soon_threadsafe` 投递，或直接依赖服务进程管理器的硬超时。

## 背诵要点
- signal.signal 仅主线程可装（否则 ValueError）；Python handler 在主线程 eval breaker 执行，长 C 调用期间迟滞。
- asyncio 用 loop.add_signal_handler（类 Unix、loop 运行中）：self-pipe 把信号变 IO 事件，与回调串行无交错；两机制不可混用。
- SIGTERM 只发 PID 1；多进程要转发；Windows Proactor 不支持 add_signal_handler。
