### Q5616 · 空闲连接维持成本账

> 难度:★★★★☆ | 标签:成本工程, keep-alive, 连接治理

**问**:HTTP 客户端连接池配了 500 条 keep-alive 连接，出网高峰才用 50 条——那 450 条空闲连接在"免费"维持吗？每条空闲连接的服务端/中间设备成本是什么？什么时候该主动关？

**答**:结论：空闲连接**不是免费**的，成本分三层：a) **本机 fd 与内存**：每条连接占 1 个 fd + 内核两侧 socket 缓冲（默认各几十 KB，见 Q5586）+ 应用层读缓冲对象，纯 Python 侧单连接常驻约几十 KB，450 条 ≈ 十几 MB 起，不算大头但是 fd 上限的直接消耗（Q5553）；b) **对端成本**：你的 450 条空闲连接在服务端就是 450 个"占着连接槽但没流量"的会话，服务端 keep-alive 超时（如 nginx keepalive_timeout 75s）会先一步把它们关掉——于是出现"以为在复用、实际在重建"的隐性成本：每请求又变回三次握手+TLS（对照 Q1597），错误日志里还会积累 BrokenPipe；c) **中间设备成本**：NAT/LB 的会话表条目按空闲超时回收（常见 60-900s），空闲连接被中间设备静默丢弃后，下次写会收到 RST——这正是"长连接隔夜必断"的经典事故。治理动作：客户端池的 `max_idle`/空闲回收 TTL 要**小于**服务端与中间设备的最小空闲超时（留 30% 余量），发请求前校验连接活性（`is_connected` 探测或写时重试幂等）；服务端把 `Keep-Alive: timeout=N` 响应头发出来，让客户端按约定时间回收，而不是猜。

```python
import http.client, socket, time

# 1) 一条空闲 keep-alive 连接的本机账：fd + 缓冲
conn = http.client.HTTPConnection("www.python.org", 443, timeout=10)
# 标准库 http.client 不做 TLS 透明化，这里用非加密端口演示结构成本
host, port = "example.com", 80
conn = http.client.HTTPConnection(host, port, timeout=10)
conn.request("GET", "/")
resp = conn.getresponse()
print("响应头 Keep-Alive 约定:", resp.getheader("Keep-Alive"), "| Connection:", resp.getheader("Connection"))
sock = conn.sock
print("本地 fd:", sock.fileno() >= 0,
      "| TCP 缓冲:", sock.getsockopt(socket.SOL_SOCKET, socket.SO_SNDBUF),
      sock.getsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF), "字节")

# 2) 服务端空闲超时的实战确认：发送后 sleep 超过服务端 keepalive 超时再写
def probe_idle_timeout(host, port, idle=2.0):
    c = http.client.HTTPConnection(host, port, timeout=10)
    c.request("GET", "/"); r = c.getresponse(); r.read()
    time.sleep(idle)
    try:
        c.request("GET", "/")             # 空闲后写 → 可能 RST/EOF
        r2 = c.getresponse(); r2.read()
        return f"空闲 {idle}s 后复用 OK"
    except (OSError, http.client.RemoteDisconnected) as e:
        return f"空闲 {idle}s 后复用失败: {type(e).__name__}"
print(probe_idle_timeout(host, port, idle=1.0))

# 3) 池化治理参数示例（口径：urllib3>=1.26，httpx>=0.24 同思路）
#    pool_maxsize / max_idle 按下游容量定，空闲 TTL < min(服务端, NAT) 超时
print("治理公式: max_idle = 峰值并发 × 1.2；idle_ttl ≤ 0.7 × min(服务端 keepalive, NAT 会话超时)")
conn.close()
```

**追问一层**:服务端已经主动关了空闲连接，客户端下次 `request` 为什么有时拿到 `RemoteDisconnected` 有时拿到正常响应？TCP 半关闭在这里扮演什么角色（对照 Q1599 FIN/RST、Q5571 半开探测）？
**追二层**:HTTP/2 下"空闲连接"的概念为什么变成"空闲 stream 与空闲 connection"两层？Go/grpc 的 `keepalive` 参数与 Python 客户端治理参数怎么对应（引 Q5523）？

**背诵要点**
- 空闲连接三层成本：本机 fd+缓冲、对端连接槽（先超时的是服务端）、NAT/LB 会话表静默回收。
- 治理公式：max_idle≈峰值并发×1.2；idle_ttl ≤ 0.7×min(服务端超时， NAT 超时)，防"假复用"。
- 服务端下发 `Keep-Alive: timeout=N` 让客户端按约回收；写前探测或幂等重试兜半开连接。
