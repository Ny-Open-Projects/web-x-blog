### Q5580 · TLS 记录协议的分帧原理

> 难度:★★★★ | 标签:原理深挖, TLS, 协议

**问**：一次 `ssl sock.sendall(b"x"*100000)` 在网络上实际怎么走？TLS record 的结构（type/version/length + 密文）与 16KB 上限为什么存在、对小包与大流量各意味着什么成本？为什么 TLS 不保证应用消息边界，Python 客户端拿 `sslsock.recv(65536)` 读 HTTP 该怎么处理？`ssl.MemoryBIO`/`SSLObject` 为什么是理解分帧的正确入口？

**答**：结论：TLS 记录协议把应用字节流切成**最多 2^14（16384）字节的明文记录**，每条记录加 5 字节头（type=23 应用数据 / version / 16bit length）+ AEAD 认证标签（TLS1.2 GCM 16B、1.3 再加显式 nonce 覆盖 5B）后整体加密发送——`sendall` 的大 buffer 在 TLS 层被强制分帧，`recv` 收到的是"若干记录解密后的明文拼接"，**与对端 send 的边界无关**（TLS 是流语义，同 TCP）。成本两侧：a) 小包消息（如 64B 指令）每条都要付记录头+标签+一次加解密与一次 syscall，账面放大 ~30-40%，高频小消息协议要么应用层攒批要么直接换 0-RTT 复用连接（Q5534）；b) 大流量受 16KB 上限约束是**历史安全设计**（限制单记录重加密 oracle 与内存峰值），吞吐瓶颈常变成"每 16KB 一次加解密 + syscall"，Python 侧无解、靠内核与网络层扛。Python 视角：`ssl.wrap_socket` 后的 socket 收发都过 SSLObject（读：SSLObject→MemoryBIO→明文；写：明文→记录→底层 socket），这就是为什么 SSL socket 的 recv 返回大小与记录不对齐、`sock.send` 在握手期会抛 Want* 异常。`MemoryBIO`+`SSLObject` 是无 socket 的裸协议层（`ssl.MemoryBIO` 两个管道：incoming/outgoing），用它可以直接观测记录字节形态——面试里能写出 handshake 用 BIO 驱动的代码，基本等于真懂分帧。

```python
# file: code/02_并发与网络工程/q5580_tls_record.py
import ssl, os, tempfile, subprocess, sys

# 1) 自签证书 + BIO 驱动的 TLS: 不用 socket, 直接观测记录层字节
d = tempfile.mkdtemp()
key, cert = os.path.join(d, "k.pem"), os.path.join(d, "c.pem")
subprocess.run(["openssl", "req", "-x509", "-newkey", "rsa:2048", "-nodes",
                "-keyout", key, "-out", cert, "-days", "1", "-subj", "/CN=t"],
               check=True, capture_output=True)

sctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER); sctx.load_cert_chain(cert, key)
cctx = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
cctx.check_hostname = False; cctx.verify_mode = ssl.CERT_NONE

so, co = ssl.MemoryBIO(), ssl.MemoryBIO()       # 服务端 BIO 对
c_in, c_out = ssl.MemoryBIO(), ssl.MemoryBIO()  # 客户端 BIO 对
server = sctx.wrap_bio(so, co, server_side=True)
client = cctx.wrap_bio(c_in, c_out, server_hostname="t")

def pump(src_bio, dst_ssl):                      # 把一端输出字节灌进另一端输入
    while True:
        try: dst_ssl.bio_write(src_bio.read()); continue
        except ssl.SSLWantReadError: return
        except ssl.SSLWantWriteError: return

# 2) BIO 驱动握手状态机: Want* 表示"需要对方字节/需要先吐出我的字节"
for _ in range(10):
    pump(c_out, server); pump(co, client)
    try: client.do_handshake(); break
    except ssl.SSLWantReadError: pass
    try: server.do_handshake(); break
    except ssl.SSLWantReadError: pass
print("BIO 握手完成:", client.session_established() and server.session_established())

# 3) 明文进 -> 记录层分帧 -> 另一端收明文: sendall 100KB 实际多记录
client.write(b"y" * 100_000)
pump(c_out, so)                                   # 客户端密文 -> 服务端输入
server.read(16_384)                               # 服务端一次最多吐一条记录的明文
total = 0
while True:
    try:
        chunk = server.read(16_384)
        if not chunk: break
        total += len(chunk)
    except ssl.SSLWantReadError:
        break
print("100KB 明文分帧后, 服务端累计读回:", total + 16384 if False else total + 0, "+16384(首读)字节")
print("TLS 记录上限: 2^14=16384B 明文/记录, 头5B+AEAD tag 16B(TLS1.2 GCM)")

# 4) 小消息成本: 64B 指令的线上字节放大
client.write(b"C" * 64); pump(c_out, so)
wire = len(c_out.read())                          # 线上密文字节
print(f"64B 应用消息 -> 线上 {wire}B (放大 {wire/64:.2f}x)")
print("python:", sys.version.split()[0])
```

**追问**：1) 为什么 record 上限是 2^14 而不是更大？——RFC 8446 固定 2^14 可协商上限（1.3 可到 2^16），上限保障：单记录只重放/重加密有限数据（防 oracle 放大）、解密端内存有界；TLS1.2 时代 LUCKY13 等计时攻击也促使 1.3 让加解密时间与记录内容无关。2) `SSLObject.read` 的返回与记录一一对应吗？——不对应：read 返回"当前已解密可用明文"，可能一次返回多条记录拼成的数据（受 maxsize 限制），也可能 Want*；消息边界只能由应用协议（HTTP 的 Content-Length/chunked、gRPC 的长度前缀）恢复，这正是 Q1892 trailer 校验与 HTTP 分帧存在的原因。3) Python 侧有没有办法控制记录大小攒批？——SSLSocket 没有暴露 record 合并开关（OpenSSL 有 SSL_MODE_ENABLE_PARTIAL_WRITE 等模式但不直接控制），攒批只能应用层做：多个小消息攒成大 buffer 一次 write，TLS 自然切成满记录，降低记录头/标签占比。

## 背诵要点
- TLS 记录=5B 头+≤16384B 明文+AEAD tag，sendall 大包被强制分帧，recv 拿到的是多记录明文拼接——TLS 是流语义，消息边界靠应用协议恢复。
- 成本两向：小消息放大 ~30-40%（头+tag+加解密），大流量受 16KB 上限约束；攒批是唯一应用层优化。
- 理解分帧的正确入口是 MemoryBIO+SSLObject：BIO 驱动 Want* 状态机，能直接量出线上字节放大。
