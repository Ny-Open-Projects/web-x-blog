### Q5749 · TLS SNI 回调：servername_callback 与动态证书选择

难度：P6 ｜ 标签：SNI、servername_callback、动态证书、热轮换、多域名、SSLContext、证书热更新、TLS 握手

**问**：一台服务器服务多个 HTTPS 域名时，TLS 层怎么知道该出示哪张证书（HTTP Host 头在握手之后才到）？Python 的 `set_servername_callback` 回调签名与返回值语义是什么？"证书热轮换"为什么必须走 SNI 回调 + 动态 context 而不是重启进程？回调里能做什么、不能做什么（阻塞/异常/返回值约定）？

**答**：
结论：SNI（Server Name Indication，RFC 6066）是客户端在 **ClientHello 里**携带的"我要连的域名"——它必须在证书出示之前到达，服务器才能按域名选证书（HTTP 的 Host 头是解密后才可见，救不了 TLS 层的选择）。Python 服务端的实现钩子是 `SSLContext.set_servername_callback(callback)`，回调签名 `cb(sslobj, server_name, ctx)`：`server_name` 是客户端 SNI（**可能为 None**——老客户端/直连 IP 不带 SNI，Q5612 的缺失事故同族）；返回值语义：**返回 None** 沿用当前 context 的证书继续握手，**返回另一个 SSLContext** 切换到该 context 的证书链继续握手，**抛出异常/返回 ssl.ALERT_DESCRIPTION_* 触发握手失败**（如 SNI 不认识的域名直接 fatal handshake_failure）。典型分派架构：启动时为每个域名构建独立 context（加载各自证书链与私钥，缓存复用——每请求新建 context 的成本账见 Q5606），回调里查表返回对应 context；**未命中的域名返回默认 context 或抛异常**（宁可握手失败也不能出示错域名证书——浏览器会报证书与域名不匹配）。热轮换价值：证书自动续期（certbot/ACME，60-90 天周期）要求"换证书不重启进程"——重启丢连接池/缓存/优雅期成本高，SNI 回调让"重新加载证书的 context"成为数据结构操作：**回调查表返回新 context，进程不重启、存量连接不受影响**，配合原子替换表项实现无缝轮换（Q1603 的原子替换同思路）。注意回调边界：它在握手线程执行、应**非阻塞且轻量**（查内存表），不能做 IO（读磁盘加载证书——那是启动时/后台刷新的事）；回调抛非 ssl 异常会被 OpenSSL 层捕获为握手失败。

取舍：a) context 数量：每域名一 context（干净、独立配置）vs 共享 context + 动态换证书（OpenSSL SSL_CTX_use_certificate 级操作，Python 层不直接暴露）——Python 生态标准是**多 context + 回调分派**；b) 默认证书：SNI 缺失/未知时出示"通用默认证书"（通配符或主域名）还是拒绝——面向公网的 API 网关给默认证书+正常握手（HTTP 层 404），内部 mTLS 服务拒绝（Q695）；c) 热轮换实现纪律：证书加载**一次成功才替换表项**（新 context 加载失败保持旧证书服务，日志告警）、替换是 dict 原子赋值（GIL 保证引用切换原子）、回调永不触碰加载过程；d) 性能：回调每次握手执行一次，查 dict 是纳秒级，但**TLS 会话复用（session ticket/resumption）可以完全跳过证书出示**——SNI 仍会进回调（会话恢复也要选 context），热点场景注意回调幂等；e) 测试：SNI 分派要有"单测覆盖所有域名字典 + 缺 SNI + 未知域名"三路用例，集成测试用 `openssl s_client -servername` 或 ssl 客户端真连。

实战：事故形态是"证书自动续期脚本用 stop/restart 方式换证书，重启窗口内连接池雪崩；后来改成 SNI 回调 + 后台 reload，但 reload 里直接在回调中读磁盘加载新证书——握手延迟从 5ms 涨到 80ms（每次握手都读盘），证书大时偶发握手超时。终态：后台定时线程加载新 context → 成功后原子替换 dict 表项 → 回调只查表；续期零重启、握手 P99 不受轮换影响"。下面实现 SNI 分派路由与热轮换骨架（回环握手需要证书，演示聚焦分派逻辑与表替换）。

```python
# SNI 回调: 分派路由、缺失/未知处理与热轮换骨架
import ssl
import threading

class CertTable:
    """SNI -> SSLContext 的分派表: 查表在握手线程, 加载在后台线程, 原子替换"""

    def __init__(self, default_ctx: ssl.SSLContext) -> None:
        self._default = default_ctx
        self._table: dict = {}
        self._lock = threading.Lock()

    def register(self, server_name: str, ctx: ssl.SSLContext) -> None:
        with self._lock:
            self._table[server_name] = ctx          # 单条注册 (启动期)

    def get(self, server_name):
        # dict.get 是原子的 (GIL 下引用读取); 热轮换只替换表项, 不动握手路径
        if server_name is None:
            return self._default, "无 SNI -> 默认证书"
        ctx = self._table.get(server_name)
        if ctx is None:
            return None, f"未知域名 {server_name} -> 握手失败 (不出示错域证书)"
        return ctx, f"{server_name} -> 专属证书"

def make_ctx(cn: str) -> ssl.SSLContext:
    """服务端 context 骨架; 真实部署: 这里 load_cert_chain(证书链, 私钥)"""
    ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)   # 服务端专用: 才允许挂 sni_callback
    return ctx

print("[1] 分派表: 每域名一个 context, 回调查表返回")
table = CertTable(make_ctx("default"))
table.register("api.example.com", make_ctx("api"))
table.register("www.example.com", make_ctx("www"))

for name in ("api.example.com", "www.example.com", "unknown.net", None):
    ctx, why = table.get(name)
    verdict = "切换专属 context" if name else "默认证书"
    print(f"    SNI={name!r} -> {'沿用默认' if (ctx and name is None) else (verdict if ctx else '握手失败')} ({why})")

print("[2] 回调签名与返回值语义 (真实接线示意, 不做真握手)")
def sni_callback(sslobj, server_name, ctx):
    picked, why = table.get(server_name)
    if picked is None:
        return ssl.ALERT_DESCRIPTION_UNRECOGNIZED_NAME       # fatal: unrecognized_name
    return picked                                            # None=沿用, 返回 context=切换

outer = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)          # TLS_CLIENT context 挂回调会 ValueError
outer.set_servername_callback(sni_callback)
print("    set_servername_callback 已挂接; 返回 context=切换 / ALERT=握手失败 / None=沿用")

print("[3] 热轮换骨架: 后台加载成功才替换表项, 握手路径零感知")
new_ctx = make_ctx("api-v2")
table.register("api.example.com", new_ctx)                  # 原子替换表项
print("    api.example.com ->", table.get("api.example.com")[1])
print("    轮换纪律: 加载失败保持旧证书; 回调永不读磁盘; 存量连接不受影响")

print("[4] 三个边界: SNI 可能缺失(None) / 未知域名宁可握手失败 / 回调内禁 IO")
print("[rule ] SNI 在 ClientHello 里先于证书到达; 多 context 分派 + 原子表替换 = 无重启热轮换")
```

**追问一**：SNI 缺失（直连 IP/老客户端）与 SNI 欺诈（ClientHello 里谎报域名）分别怎么处理？"以 SNI 分派 + 证书校验"的组合里，攻击者谎报 SNI 能得到什么？—— SNI 缺失：服务端要么出示默认证书（公网网关形态，握手继续、HTTP 层兜底），要么拒绝（内部服务/mTLS 形态，Q5612 的教训是"校验逻辑假设 SNI 存在"导致 AttributeError 级崩溃——任何 SNI 处理路径的第一行都要容 None）。SNI 欺诈的分析：客户端谎报 `bank.com` 的 SNI 连我的服务器——①服务器没有该域名证书：回调拒绝，握手失败，攻击者一无所获；②服务器**恰好有**该域名的证书（多租户网关托管了 bank.com）：会出示 bank.com 证书并继续握手——**但客户端真正的 TLS 校验发生在它自己的信任体系里**：攻击者作为"客户端"不会校验自己收到的证书，谎报 SNI 只是让服务器出示那张证书，攻击者拿到的是**证书本身**（公开信息，任何人 CT 日志都能查到）——没有私钥，无法冒充。真正的风险不在"谎报拿到证书"，而在**服务端日志与路由按 SNI 分流**：SNI 是客户端可控输入，进入日志/限流键/路由决策时要当不可信输入处理（长度限制、编码校验），否则是日志注入/限流绕过面。结论：SNI 是"路由信号"不是"身份证明"——身份永远由证书校验与私钥持有决定。

**追问二**：热轮换时"存量连接"与"新建连接"的证书是什么关系？轮换窗口内的两端版本不一致（客户端拿到新证书、连接池里的旧握手）有什么隐患？—— 证书只影响**握手时刻**：存量连接的 TLS 会话在握手时已协商完成（对称密钥已就位），服务器换证书不影响已建立的加密通道——它们继续用旧会话直到自然断开/排空；新建连接走新 context 的证书。隐患点在**会话复用**与**证书过期窗口**：①session ticket/resumption 复用旧握手参数——旧证书到期瞬间，持旧 ticket 的客户端复用会话成功但**证书实际已过期**（复用路径不重新出示证书），严格校验方（如需要证书新鲜度的中间件）可能报错；工程解：轮换时主动清空 ticket 密钥（新 context 换 ticket key），强制走完整握手拿新证书；②两端不一致的中间态：LB 与后端分别轮换时，LB 侧验后端证书的信任链若钉了旧 SPKI（Q5744）——先换后端再换 LB 校验配置，顺序错误即拒连；③OCSP staple：新 context 要重新装订 OCSP 响应（Q5723），忘装订则客户端软失败面扩大。轮换 SOP：后台加载→原子替换→清 ticket key→监控握手成功率与证书校验错误率→旧 context 延迟释放（存量连接排空后再释放，防 use-after-free 式的 context 回收竞态）。

## 背诵要点
- SNI 在 ClientHello 里先于证书到达，是 TLS 层选证书的唯一依据（Host 头在解密后才可见）；Python 钩子 = set_servername_callback(cb(sslobj, server_name, ctx))，返回 None 沿用 / 返回 SSLContext 切换 / ALERT 拒绝。
- server_name 可能为 None（必须容空）；未知域名宁可握手失败不出示错域证书；SNI 是路由信号不是身份证明，进日志/限流键前按不可信输入消毒。
- 热轮换 = 后台加载新 context 成功后原子替换表项，回调只查表禁 IO；轮换要清 session ticket key、按"先换证书链再换校验方"顺序、旧 context 延迟释放。

## 复盘追问

- 攻击者谎报 SNI 能得到什么、防什么？（能拿到公开的证书本身，无私钥无法冒充；风险在服务端把 SNI 当可信输入进日志/限流/路由——按不可信输入消毒）
