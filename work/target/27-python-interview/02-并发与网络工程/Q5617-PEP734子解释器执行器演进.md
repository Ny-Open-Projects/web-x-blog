### Q5617 · PEP 734 与 InterpreterPoolExecutor 的演进

> 难度:★★★★☆ | 标签:版本演进, 子解释器, 并行模型

**问**:3.13 引入 `_interpreters`、3.14 出了 `concurrent.interpreters` 与 `InterpreterPoolExecutor`——子解释器这条路从 PEP 554 到 PEP 734 走了什么演进？它和进程池/线程池的适用边界怎么划（并行模型概览另见 Q5501）？

**答**:结论：演进主线是**从"解释器原语"到"执行器抽象"**：PEP 554（未通过，2017-2020 阶段）提议的是标准库 `_interpreters` 原语模块；3.12 的 PEP 684 给**每个子解释器独立 GIL**（per-interpreter GIL），使子解释器间真正并行；3.13 的 PEP 734 提供官方 `concurrent.interpreters`（3.14 落地为公开模块），并配套 `concurrent.futures.InterpreterPoolExecutor`——用 Executor 的任务模型封装"创建解释器→队列分发任务→结果回传"，用法与进程池对齐，心智成本骤降。三者边界：a) **CPU 并行**：子解释器与进程池都能绕过 GIL；b) **隔离度**：进程池最彻底（崩溃不传染、内存完全独立），子解释器中间态（同进程内存，但解释器状态隔离、不能共享可变对象，通信靠 channel/序列化，PickleShare 历史方案被否）；c) **成本**：子解释器创建 ~ms 级、无 import 重跑，spawn 进程 ~50-150ms——高频短任务的 CPU 并行是子解释器的甜点区。坑：C 扩展必须声明 `Py_mod_multiple_interpreters` 支持（旧扩展在子解释器里 import 会失败或隐式共享全局），GIL-free 与解释器隔离是两条独立战线（对照 Q5577 free-threading）。降级：3.12 及以下无此 API，等价方案只能进程池。

```python
import sys, textwrap

print("Python:", sys.version.split()[0])

if sys.version_info >= (3, 14):
    from concurrent import interpreters                     # PEP 734 公开模块
    from concurrent.futures import InterpreterPoolExecutor

    interp = interpreters.create()
    rc = interp.exec(textwrap.dedent("""                    # 在子解释器里跑一段代码
        data = [i * i for i in range(5)]
    """))
    print("exec 返回码:", rc)
    result = interp.call(lambda_name := "len", "abcd")      # 调子解释器内置函数
    print("call len('abcd') =", result)
    interp.close()

    with InterpreterPoolExecutor(max_workers=2) as ex:     # 执行器封装，用法对齐进程池
        f = ex.submit(str, 42)
        print("executor submit:", f.result())
elif sys.version_info >= (3, 13):
    import _interpreters                                    # 3.13 仍是内部模块
    print("3.13: _interpreters 可用，公开 API 未定；降级用进程池")
else:
    print("3.12-: 无子解释器并行 API；per-interpreter GIL 从 PEP 684(3.12) 起具备底层能力")
    print("等价替代: ProcessPoolExecutor（完全隔离）或线程池（仅 IO 并行）")

# 不可跨解释器共享可变对象的演示（隔离语义的核心约束）
print("约束: 子解释器间不能直接共享 list/dict，通信必须走 channel/序列化")
```

**追问一层**:per-interpreter GIL（PEP 684）与 PEP 703 free-threading 都解决并行，为什么两条路都要走？子解释器对"内存占用"的账怎么算（对照 Q5546 每协程账）？
**追二层**:`InterpreterPoolExecutor` 的任务参数怎么序列化传给子解释器？它为什么要求任务函数与参数可 pickle——这与进程池的限制是同一层吗？

**背诵要点**
- 演进链：PEP 554（未过）→ PEP 684（3.12 per-interpreter GIL）→ PEP 734（3.13/3.14 concurrent.interpreters + InterpreterPoolExecutor）。
- 边界：进程池隔离最强、创建最贵；子解释器 ms 级创建、同进程隔离、不能共享可变对象；线程池仅 IO 并行。
- C 扩展需声明多解释器支持；GIL-free 与解释器隔离是两条独立演进线。

**复盘追问**
- 把 CPU 密集任务从进程池迁到 InterpreterPoolExecutor 后个别任务报 "cannot import in subinterpreter"，根因是什么？提示：C 扩展全局状态未声明支持，找扩展作者或回退进程池。
- 为什么 PEP 554 推了七年才落地？提示：缺 per-interpreter GIL 前子解释器仍共享 GIL 无并行价值，依赖 PEP 684 先行。
