### Q5637 · TLS 后量子混合密钥交换（X25519MLKEM768）的演进

难度：P7 | 标签：TLS、后量子密码、X25519MLKEM768、OpenSSL、版本演进

**问**："先存后解"（harvest now, decrypt later）威胁是什么？后量子 TLS 为什么采用"混合密钥交换"而不是直接替换？Python 侧（ssl 模块/openssl 基线）如何跟进与验证 X25519MLKEM768 这类算法组？

**答**：

**结论**：威胁模型：攻击者现在记录加密流量，等未来量子计算机成熟后用 Shor 算法分解当时协商的 ECDH/RSA 密钥，回溯解密长期敏感数据。对策是把经典算法与后量子算法（ML-KEM，即 Kyber）组合：混合密钥交换 `X25519MLKEM768` 同时做 X25519 与 ML-KEM-768 两路协商，共享密钥 = 两者输出拼接进 KDF——任一算法被攻破前仍安全，避免单独依赖未经充分验证的新算法（这是"先双双安全再逐步去经典"的迁移策略）。标准化侧 IETF 已将 ML-KEM 发布为 RFC（draft-ietf-tls-ecdhe-mlkem 及 FIPS 203），主流 CDN/浏览器 2024-2025 已默认启用 X25519MLKEM768。

**取舍**：Python 层自己不实现密码原语，跟进的是编译时的 OpenSSL 基线：OpenSSL 3.5 起内置 ML-KEM 支持，之前版本需 oqs-provider。实际工程点：(1) 检查运行环境的 `ssl.OPENSSL_VERSION`，3.5+ 才能协商 MLKEM 组；(2) 用 `SSLContext.set_ciphersuites`/组配置控制协商顺序；(3) 握手报文变大（ML-KEM-768 公钥 ~1.2KB）可能触发中间设备 MTU/分帧兼容问题——这正是灰度验证的意义。降级路径：不支持 MLKEM 的客户端/服务端自动回落 X25519，连接仍安全只是不抗量子。

**实战**：验证方法：用 openssl s_client 或 Python 客户端连启用了 MLKEM 的端点，检查协商出的组名；内网服务灰度时按"支持/不支持"分桶观测握手失败率与 RTT 变化。

```python
import ssl, socket, sys

print("python", sys.version.split()[0])
print("openssl", ssl.OPENSSL_VERSION)          # >= 3.5 才内置 ML-KEM

ctx = ssl.create_default_context()

# 观察：与公网端点握手，看实际协商的 TLS 版本与密钥交换组
# （MLKEM 是否被选中取决于两端能力，握手失败自动降级 X25519）
try:
    with socket.create_connection(("www.cloudflare.com", 443), timeout=8) as raw:
        with ctx.wrap_socket(raw, server_hostname="www.cloudflare.com") as s:
            print("TLS 版本   ->", s.version())
            proto = s.selected_alpn_protocol()
            print("ALPN      ->", proto)
            # 3.12 ssl 尚无直接读取 "group" 的 API，用 openssl 命令行旁证：
except Exception as e:
    print("网络不可用，跳过在线握手 ->", type(e).__name__)

# 能力探测：标准库无 MLKEM API 时的降级思路——探测 OpenSSL 命令行
import subprocess, shutil
if shutil.which("openssl"):
    r = subprocess.run(["openssl", "version"], capture_output=True, text=True)
    print("cli openssl ->", r.stdout.strip())
    print("若为 3.5+：openssl s_client -groups X25519MLKEM768 可验证协商")
```

**追问 1**：为什么混合而不是直接用 ML-KEM？
答：ML-KEM 相对年轻（Kyber 2017 提出，2024 FIPS 定稿），单独依赖一旦被找到攻击将全线失守；经典算法的置信度兜底，等生态验证充分后再移除经典部分。

**追问 2**：后量子签名（ML-DSA）与后量子 KEM 的迁移节奏为何不同？
答：签名用于证书链与代码签名，证书体积膨胀数倍且 CA 轮换周期长，迁移更慢；KEM 只影响握手，服务端改配置即可，所以 TLS 密钥交换先落地——两条线节奏由"部署成本"决定。

**追问 3**：harvest 威胁下应用层还能做什么？
答：缩短数据机密时效（分段加密密钥、定期轮换对称密钥不影响历史）、对超敏感链路叠加应用层 PQC 加密（如 liboqs 方案），以及明确数据保密期 < 量子成熟期的数据可暂缓迁移。

## 背诵要点

- 威胁是"先存后解"；对策是混合密钥交换 X25519MLKEM768（RFC/ML-KEM=FIPS 203），单算法被破前整体安全。
- Python ssl 不实现原语，能力取决于 OpenSSL 基线（3.5+ 内置 ML-KEM），先查 ssl.OPENSSL_VERSION 再验证协商组。
- MLKEM 公钥 ~1.2KB 使握手变大，中间盒兼容要灰度；不支持时自动降级 X25519 不中断服务。
