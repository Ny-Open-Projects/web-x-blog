### A283 · 并发安全的环形缓冲：固定容量、覆盖最旧与丢帧总账

> 难度:★★★★ | 标签:环形缓冲, 并发安全, threading, Condition, 生产者消费者, 丢帧

**问**（笔试·编程题）：实时采样的监控流水线，生产端突发峰值时**不能停、不能崩，宁可丢最旧的样本也要保最新**——实现固定容量并发安全的环形缓冲：① `put` 满时覆盖最旧（记录丢帧数与全局流水号），`get` 空时阻塞等待、带超时空读返回 None；② 生产消费多线程跑通：`threading.Condition` 一把锁同时管互斥与等待唤醒，notify 必须在锁内；③ **丢帧总账**：生产数 = 消费数 + 覆盖丢弃数 + 在存数，且消费到的流水号严格递增、不重不漏——覆盖最旧只允许「跳号」，不允许「乱序/重复」；④ 断言空读超时语义与容量边界（capacity ≤ 0 拒绝构造）；⑤ 说清与 Q5604（shared_memory 跨进程环形缓冲的容量推导与槽位协议）、Q2359（deque(maxlen) 的滚动窗口自动淘汰）、Q2360（deque 单操作的线程安全边界）的分工——本题只回答「**线程内环形缓冲的并发语义：覆盖最旧策略、阻塞消费与丢帧可审计**」。

**答**：① 分工：Q5604 回答「跨进程共享内存的段容量怎么推、槽位协议怎么定」，Q2359 回答「deque(maxlen) 开箱即用的滚动窗口」，Q2360 回答「deque 哪些单操作原子」——没有一张卡回答「固定容量 + 覆盖最旧 + 多线程阻塞消费 + 丢帧可对账」这个完整语义包。② 为什么不直接用 deque(maxlen)：`append` 到 maxlen 自动淘汰最旧且单操作原子，但它**没有「取走消费」语义**——迭代中淘汰有竞态、无阻塞等待、无丢帧计数：监控账本要求「这一夜丢了多少条可审计」，maxlen 的静默淘汰给不了；本题用 Condition 把「互斥」与「等待」合并成一把锁，`wait_for` 谓词式等待天然处理虚假唤醒（醒来重查条件，不依赖单次 notify）。③ 覆盖最旧的实现顺序：满时先推 head（逻辑上丢弃最旧）再写入新槽——**丢弃发生在写入前**，保证任何时刻缓冲里都是最新的 size 条；流水号 seq 全局递增，覆盖只产生「消费到的 seq 跳号」，FIFO 顺序由环形结构天然保证（总账断言里严格递增 + 无重复就是在验这个）。④ 账要平：`produced = delivered + dropped + buffered` 是这类「允许丢弃」系统的总账恒等式——只有 dropped 计数器没有 seq 答不了「丢的是哪一段」，只有 seq 没有 dropped 计数器算不出丢帧率，两者合起来才是可审计的丢帧账。⑤ 满策略是产品决策不是技术细节：覆盖最旧（保最新：监控采样/行情推送）、背压阻塞（不丢：订单/交易）、拒绝新来（保旧：审计日志）——同一结构换一个 if，语义天差地别，笔试必须说清自己选的是哪种、为什么。

```python
# 全部标准库；并发安全环形缓冲：固定容量、覆盖最旧、Condition 阻塞消费 + 丢帧总账
import threading
import time


class RingBuffer:
    """固定容量环形缓冲：满时覆盖最旧（保最新），生产消费多线程安全。"""

    def __init__(self, capacity):
        if capacity <= 0:
            raise ValueError("capacity 必须 > 0")
        self.capacity = capacity
        self._buf = [None] * capacity
        self._head = 0          # 最旧元素槽位
        self._size = 0
        self._seq = 0           # 全局流水号：丢帧检测的尺子
        self.dropped = 0        # 被覆盖的条数（丢帧账）
        self._cond = threading.Condition()

    def put(self, item):
        with self._cond:
            if self._size == self.capacity:            # 满：覆盖最旧
                self._head = (self._head + 1) % self.capacity
                self._size -= 1
                self.dropped += 1
            self._buf[(self._head + self._size) % self.capacity] = (self._seq, item)
            self._seq += 1
            self._size += 1
            self._cond.notify_all()                    # 锁内唤醒等待的消费者
            return self._seq - 1

    def get(self, timeout=None):
        with self._cond:
            ok = self._cond.wait_for(lambda: self._size > 0, timeout)
            if not ok:
                return None                            # 超时空读：非错误
            item = self._buf[self._head]
            self._head = (self._head + 1) % self.capacity
            self._size -= 1
            return item


if __name__ == "__main__":
    # 1) 覆盖最旧的语义账：容量 5 塞 8 条 -> 存活 4..8，丢 3 条，FIFO 不乱
    rb = RingBuffer(5)
    for i in range(1, 9):
        rb.put(i)
    assert rb.dropped == 3 and rb._seq == 8
    drained = []
    while True:
        got = rb.get(timeout=0.1)
        if got is None:
            break
        drained.append(got)
    assert [s for s, _ in drained] == [3, 4, 5, 6, 7]
    assert [v for _, v in drained] == [4, 5, 6, 7, 8]
    print("覆盖最旧: 8 进 5 出，丢 3 条，序号与值序全保 ✅")

    # 2) 空读阻塞与超时：wait_for 超时返回 None，不空转
    rb2 = RingBuffer(2)
    t0 = time.monotonic()
    assert rb2.get(timeout=0.05) is None
    assert time.monotonic() - t0 >= 0.04
    print("空读超时: 50ms 返回 None（阻塞消费不忙等）✅")

    # 3) 容量边界
    try:
        RingBuffer(0)
        raise AssertionError("capacity=0 应拒绝构造")
    except ValueError:
        pass
    print("边界: capacity<=0 拒绝构造 ✅")

    # 4) 多线程生产消费：总账 produced = delivered + dropped + 在存(已被收尾清空)
    rb3 = RingBuffer(64)
    TOTAL = 2000
    consumed = []
    done = threading.Event()

    def producer():
        for i in range(TOTAL):
            rb3.put(i)
        done.set()                                 # 生产完毕信号

    def consumer():
        while not (done.is_set() and rb3._size == 0):
            got = rb3.get(timeout=0.05)            # 短超时轮询，兼顾收尾信号
            if got is not None:
                consumed.append(got)

    prod_t = threading.Thread(target=producer)
    cons_t = threading.Thread(target=consumer)
    prod_t.start()
    cons_t.start()
    prod_t.join()
    cons_t.join()
    leftover = []                                  # 收尾：主线程兜底清仓
    while True:
        got = rb3.get(timeout=0.2)
        if got is None:
            break
        leftover.append(got)
    total_out = consumed + leftover
    assert rb3.dropped + len(total_out) == TOTAL   # 总账恒等式
    seqs = [s for s, _ in total_out]
    assert seqs == sorted(seqs) and len(set(seqs)) == len(seqs)  # 严格递增不重
    print("并发总账: 生产 %d = 消费 %d + 覆盖丢帧 %d + 清仓 %d，序号严格递增不重 ✅"
          % (TOTAL, len(consumed), rb3.dropped, len(leftover)))
```

**追问**：1) 多消费者场景为什么必须 `notify_all`，`notify()` 会有什么事故？—— notify() 只随机唤醒一个等待者：若它醒后条件已被别的线程抢空（size 归零），其余消费者全部继续沉睡，错过之后所有新数据——「唤醒数量必须覆盖可能竞争的等待者」是 Condition 的铁律；单消费者可用 notify() 省一点惊群开销，多消费者省不得，惊群在 Python 层成本可忽略而睡死是事故。2) get 返回 `(seq, item)` 元组把内部流水号泄漏给了调用者，怎么收口？—— 两种收口：get 只返回 item、seq 进消费侧的对账回调（生产级常见）；或缓冲自带 `drain()` 返回 (items, 账单)。取舍是「可审计性」vs「调用方简洁」——监控场景审计压倒简洁，背压型交易队列没有丢帧、seq 只剩排障用途，可以收进日志层。3) 多消费者怎么扩展？—— 单锁多游标：每个消费者一个独立读游标 + 全局只增写游标；覆盖策略下慢消费者的游标可能被写游标追上——此时跳号继续读（Kafka 分区消费的简化版）或显式踢出告警，语义要先在章程里定死。这正是 Q5604 跨进程版「每槽自旋标志/无锁协议」要解决的问题——线程版一把锁加每游标便宜得多，跨进程才需要无锁设计；同一结构在线程内与跨进程的复杂度差一个数量级，别把线程版过度设计成无锁版。
