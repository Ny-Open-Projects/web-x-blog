### A208 · 灰度全量收尾

> 难度:★★☆ | 标签:灰度, 全量发布, 场景题

**问**（笔试·场景题）：灰度 10% 两周全绿——「剩下 90% 一次性放量」还是「继续阶梯」（25→50→100）？「全量」的判定标准（灰度多干净才能全量——样本量/指标置信度），全量后的「灰度基础设施回收」（旧版本实例/双写通道/影子表什么时候删），「全量后发现灰度期没暴露的问题」（90% 用户行为与 10% 用户不同）怎么处理？

**答**：① 全量节奏：阶梯继续（25→50→100，Q135 步进同构）而非一次 90%——10% 灰度验证的是「基本可用」，50% 验证的是「容量与依赖」（用户群特征变化：后 90% 用户的行为分布可能与前 10% 不同），100% 验证「峰值容量」——每步过护栏。② 全量判定标准：样本量置信（10% 灰度的样本已足够统计显著——Q7013 置信区间）+ 分层指标全绿（按地域/用户等级拆分看，总量绿分层红=隐藏问题）+ 容量验证（全量 QPS 下压测通过，Q121）。③ 基础设施回收节奏：旧版本实例保留 1 周（回滚保险）→ 双写通道保留到数据对账一致（Q6519）→ 影子表 30 天归档删——**回收也是分批的**，每项有独立时间线。④ 90% 用户暴露新问题：10% 灰度用户是「早期采用者分布」，全量后普通用户触发新路径（新用户没历史数据/低配设备/不同地域网络）——处理：预案先行（全量前声明「已知盲区」+ 监控加强这些维度）+ 快速回滚能力保留（全量后 48h 内回滚通道保持热备）。

```python
# 全部标准库；demo 实现「全量发布判定器」
import math

def can_go_full(gray_pct: int, gray_samples: int, layer_metrics: dict[str, float],
               baseline: float, capacity_tested: bool) -> tuple[bool, list[str]]:
    """全量判定：样本量 + 分层指标 + 容量三关。"""
    issues = []
    # ① 样本量置信：比例检验的近似样本需求
    need = math.ceil(385 / (0.05 ** 2)) if gray_pct <= 10 else 1000   # 简化口径
    if gray_samples < need:
        issues.append(f"样本量不足: {gray_samples} < {need}（置信度不够）")
    # ② 分层指标：任一层错误率超基线 2 倍即拦
    for layer, err in layer_metrics.items():
        if err > baseline * 2:
            issues.append(f"分层异常: {layer} 错误率 {err:.1%}（总量绿但分层红）")
    # ③ 容量
    if not capacity_tested:
        issues.append("全量 QPS 未压测验证")
    return not issues, issues

class InfraDecommission:
    """灰度基础设施分批回收时间线。"""
    TIMELINE = [("旧版本实例", "1 周"), ("双写通道", "对账一致后"), ("影子表", "30 天归档删")]
    def plan(self) -> list[str]:
        return [f"{n}: 保留 {w}" for n, w in self.TIMELINE]

if __name__ == "__main__":
    ok, issues = can_go_full(10, 5000, {"north": 0.004, "south": 0.012},
                             baseline=0.005, capacity_tested=False)
    print("全量判定:", "GO" if ok else "NO-GO", issues)
    assert not ok and any("分层" in i for i in issues)      # south 层红被拦
    ok2, _ = can_go_full(10, 20000, {"north": 0.004, "south": 0.006},
                         baseline=0.005, capacity_tested=True)
    assert ok2
    print("修复后 GO ✅")
    for p in InfraDecommission().plan():
        print("回收计划:", p)
    # 口径：阶梯到 100（25→50→100）；分层指标是总量绿的必要补充；
    # 回收分批（实例 1 周/双写对账后/影子 30 天）；全量 48h 回滚热备。
```

**追问**：1) 为什么分层指标是「总量绿」的必要补充？——总量绿可能掩盖某层红（south 层 1.2% 被 north 的 0.4% 平均掉）——分层（地域/用户等级/设备）是「辛普森悖论」的标准防线，分层红哪怕总量绿也不全量。2) 「全量后 48h 回滚热备」的窗口依据？（提示：新问题暴露高峰在前 48h（全量用户行为冲击）+ 48h 后问题已显形处理（要么修要么已回滚）——48h 后回滚通道冷却（旧实例已回收），改为前滚修复）3) 灰度期「样本量足够」的严格计算？（提示：按效应量与显著性水平做检验功效计算（Q7008 样本量公式）——简化版 385/δ² 是比例检测的经验值，正式实验按公式；样本不足时宁可延长灰度）

## 背诵要点
1. 全量走阶梯（25→50→100）非一次放量——10% 验可用、50% 验容量依赖、100% 验峰值。
2. 全量判定三关：样本量置信 + **分层指标**（防辛普森悖论，总量绿分层红不全量）+ 容量压测通过。
3. 基础设施分批回收（旧实例 1 周/双写对账后/影子 30 天）；全量 48h 回滚热备防「90% 用户新路径」问题。

## 复盘追问
1. 全量后 south 地区错误率飙升（灰度期 south 用户只有 2 个）——灰度设计哪里漏了？（提示：灰度分桶未按地域分层（10% 用户全是 north）——灰度分桶要按关键分层维度**分层抽样**（每层都进灰度），这是实验设计（Q7021 SRM 同源）的灰度版）
2. 灰度两周指标全绿，全量后发现性能问题（90% 用户并发下连接池耗尽）——灰度验证的容量盲区？（提示：10% 流量的连接池用量是 10%，耗尽问题在全量才触发——容量验证不能只看「灰度期指标」，必须做「全量 QPS 折算压测」（Q121 折算）——灰度绿≠容量够）
