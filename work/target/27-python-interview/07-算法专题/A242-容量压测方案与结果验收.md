### A242 · 容量压测的结果验收

> 难度:★★★ | 标签:压测, 容量验收, 拐点

**问**（笔试·场景题）：季度容量评审要拿一份压测报告来「证明单实例能扛 3000 QPS」——压测模型怎么选（**开环固定到达率** vs **闭环固定并发**，两者测出的「容量」为什么不是一回事，思考时间要不要设），指标口径怎么统一（P99 客户端测还是服务端测、集群 P99 能不能把各实例 P99 平均、错误请求算不算进吞吐、预热段怎么剔），拐点怎么判（吞吐平台、延迟斜率突变、错误率抬头三个信号不同时出现时信谁；哪些是**假拐点**），验收结论怎么写（二值 PASS/FAIL 的判据是什么、余量系数怎么定、没通过能不能「记录风险后上线」）？它与 A121（压测组织与容量公式）、A217（生产流量反推容量）、A234（基线年度复审）分别差在哪？

**答**：① 分工先说清：A121 解决「压测怎么组织、调用树怎么推导实例数」，A217 解决「不主动压测、用生产流量拟合拐点」，A234 解决「基线一年后漂了多少」——本题只解决一件事：**一次压测做完，数据能不能作为容量承诺被签字验收**（压测是手段，验收是闸门）。（注：实盘 A186 是发布日历，不含容量口径；容量账主线是 A200/A217/A234。）② 模型选型：**开环**（按固定到达率/泊松发压，不等上一个响应）才能压出饱和——闭环（固定并发、收到响应才发下一个）有**自限效应**：服务一变慢，客户端自动降速，系统稳定在拐点左侧，永远测不到崩溃点；生产流量本质是开环的（用户不会因为你慢就不来），所以容量验收必须用开环；闭环只适合测「N 并发下的吞吐/延迟」。闭环还必须把思考时间设为 0 或极小，否则并发数与到达率双重失真。③ 指标口径四条硬规矩：延迟以**客户端**测量为准（含网络与客户端排队，对齐用户体感；服务端只用于定位）、集群 P99 **不可对实例 P99 求平均**（分位数不可加，必须合并直方图后重算，或用各实例最大值做保守上界）、吞吐**只计 2xx**（5xx 计进吞吐等于把失败当产能）、分母用「发出的请求数」而非「成功请求数」（否则错误越多分母越小，越压越「好看」）。另外预热段（前 30-60 秒：连接池建立、JIT/字节码特化、缓存冷启动）必须单独标注并从稳态统计里剔除。④ 拐点三信号：**吞吐平台**（相邻档吞吐增益 <5%）、**延迟斜率突变**（P99 涨幅 >20%，或 ΔP99%/Δ负载% > 1.5）、**错误率抬头**（超预算）。三者同现 = 真饱和；只有延迟涨而吞吐还涨 = 接近未到，可继续加档；只有错误率涨 = 优先怀疑压测侧问题而非服务容量。假拐点四源：压测机 CPU/网卡打满（测到的是施压端上限）、连接池/文件描述符等**配置上限**（不是服务上限）、限流/熔断没关或阈值过低（测的是限流器容量）、下游被 mock（真瓶颈在第三方，压不挂）。⑤ 验收结论：二值，三条**全过**才算 PASS——目标档 SLI 达标（P99 ≤ SLO 且错误率 ≤ 预算）、拐点 ≥ 目标 × 余量系数（1.2-1.5，按扩容滞后与故障冗余定）、数据有效性零问题。任一条不过即 FAIL，**不允许「综合评估后通过」**；FAIL 的处置是优化/加机器/调参后重压，报告必须附带压测模型、代码版本、依赖配置与数据版本，保证下次可复现。

```python
# 全部标准库；阶梯压测结果验收：有效性校验 → 拐点判定 → 二值结论
from dataclasses import dataclass


@dataclass
class Stage:
    load: float        # 施加负载（目标 QPS，开环到达率）
    tput: float        # 服务端实测吞吐（仅统计 2xx）
    p99: float         # 客户端视角 P99（ms）
    err: float         # 错误率 0-1，分母 = 发出的请求数
    client_cpu: float  # 压测机 CPU（%），用来识别「压的是压测机」


def validity_problems(stages):
    """有效性校验：客户端不是瓶颈、错误率没失控（饱和期吞吐低于负载属正常）。"""
    if not stages:
        return ["无压测数据"]
    problems = []
    for s in stages:
        if s.client_cpu >= 80:
            problems.append(
                f"load={s.load:.0f}: 压测机 CPU {s.client_cpu:.0f}% 打满，测到的是施压端上限")
        if s.err >= 0.02:
            problems.append(
                f"load={s.load:.0f}: 错误率 {s.err:.1%} >= 2%，该档吞吐不能当产能")
    return problems


def find_knee(stages):
    """饱和拐点：吞吐增益 <5% 且 P99 涨幅 >20% 的第一档负载。"""
    for prev, cur in zip(stages, stages[1:]):
        gain = (cur.tput - prev.tput) / max(prev.tput, 1e-9)
        blow = (cur.p99 - prev.p99) / max(prev.p99, 1e-9)
        if gain < 0.05 and blow > 0.20:
            return cur.load
    return None


def accept(stages, target, p99_slo, err_slo=0.005, headroom=1.2):
    """验收：数据有效 + 目标档 SLI 达标 + 拐点留足余量，三条全过才 PASS。"""
    problems = validity_problems(stages)
    if problems:
        return False, [f"数据无效: {p}" for p in problems]
    covered = [s for s in stages if s.load >= target]
    if not covered:
        return False, [f"未覆盖目标负载 {target:.0f}（最高只到 {stages[-1].load:.0f}）"]
    at = min(covered, key=lambda s: s.load)
    reasons = []
    if at.p99 > p99_slo:
        reasons.append(f"目标档 P99 {at.p99:.0f}ms > SLO {p99_slo:.0f}ms")
    if at.err > err_slo:
        reasons.append(f"目标档错误率 {at.err:.2%} > 预算 {err_slo:.2%}")
    knee = find_knee(stages)
    if knee is None:
        reasons.append("未压出拐点：无法给出容量上限，只能证明目标档可用")
    elif knee < target * headroom:
        reasons.append(
            f"拐点 {knee:.0f} < 目标 {target:.0f} × 余量 {headroom}，扩容前无缓冲")
    return (not reasons), reasons


if __name__ == "__main__":
    healthy = [
        Stage(1000, 1000, 40, 0.001, 25),
        Stage(2000, 1995, 46, 0.001, 38),
        Stage(3000, 2980, 62, 0.002, 52),
        Stage(4000, 3950, 120, 0.004, 66),
        Stage(5000, 3970, 900, 0.012, 74),      # 吞吐停涨、P99 起飞 = 真饱和
    ]
    assert validity_problems(healthy) == []
    assert find_knee(healthy) == 5000
    ok, why = accept(healthy, target=3000, p99_slo=150, headroom=1.2)
    assert ok, why
    print("healthy: PASS（目标 3000，P99 62ms，拐点 5000 = 1.67× 余量）")

    saturated = [
        Stage(1000, 1000, 40, 0.001, 20),
        Stage(2000, 1990, 50, 0.001, 34),
        Stage(3000, 2960, 80, 0.002, 48),
        Stage(4000, 2985, 420, 0.010, 62),
    ]
    assert find_knee(saturated) == 4000        # 吞吐 +0.8%、P99 +425%
    ok, why = accept(saturated, target=4000, p99_slo=150, headroom=1.2)
    assert not ok and len(why) == 3            # P99 超 + 错误率超 + 无余量
    print("saturated: FAIL ->", " | ".join(why))

    client_bound = [
        Stage(1000, 1000, 40, 0.001, 30),
        Stage(2000, 1980, 50, 0.001, 55),
        Stage(3000, 2600, 300, 0.003, 78),
        Stage(4000, 2620, 600, 0.004, 93),      # 压测机打满，人为造出「拐点」
    ]
    assert find_knee(client_bound) == 4000      # 单看曲线会误判为饱和
    ok, why = accept(client_bound, target=3000, p99_slo=900)
    assert not ok and why[0].startswith("数据无效")
    print("client_bound: 假拐点被有效性校验拦下 ->", why[0][:30] + "...")
```

**追问**：1) 为什么闭环模型永远压不出容量上限？——自限反馈：服务变慢 → 响应回来得晚 → 客户端下一个请求发得晚 → 实际到达率自动下降，系统被「客户端」稳在拐点左侧。要看到饱和必须开环固定到达率（或用足够长的发压队列 + 无限并发），并且思考时间归零，否则你测的是「客户端节奏」不是「服务容量」。2) 集群 P99 为什么不能对实例 P99 取平均？——分位数不可加：10 个实例各 P99=100ms，合并后 P99 可能是 300ms（少数慢实例决定了尾部），平均值只会把长尾抹平、系统性低估（A131 的同一数学）。正确做法是合并指数桶直方图后重算，或用 max(实例 P99) 做保守上界。3) 报告写「目标 5000，实测 5200」能直接签吗？——不能，吞吐是结果不是证据：要看 5200 是在什么错误率/P99 下达到的（5% 错误率下的 5200 毫无意义）、压测机是否打满、拐点在哪。吞吐达标但拐点 5300（余量 6%）不能签；拐点 8000 但 P99 超 SLO 也不能签。

## 背诵要点
1. 容量验收必须开环固定到达率：闭环有自限效应，永远停在拐点左侧；生产流量是开环的。
2. 口径四规矩：客户端测延迟、P99 不可平均（合并直方图）、吞吐只计 2xx、错误率分母是发出请求数；预热段剔除。
3. 拐点三信号同现才算饱和（吞吐平台 + 延迟斜率突变 + 错误率抬头）；假拐点四源：压测机、配置上限、限流未关、下游 mock。验收二值、三条全过、无余量不签。

## 复盘追问
1. 压测报告全绿，上线后第一天就雪崩，最可能漏了什么？（提示：压测的流量**配比**与真实不符——压测常打最便宜的读接口，真实流量里下单/搜索这类重接口占比更高；或是缓存命中率在压测里被人为抬高（参数化不足），真实流量穿透到 DB）
2. 为什么「余量系数 1.2」不能一刀切用在全公司？（提示：余量要覆盖扩容滞后 + 故障冗余 + 预测误差三项（A200），无状态服务扩容快可小、有状态/依赖配额扩容慢必须大；统一系数会让快扩容的服务浪费钱、慢扩容的服务不够用）
