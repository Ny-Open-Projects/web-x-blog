### A233 · 多渠道触达矩阵

> 难度:★★☆ | 标签:通知, 触达, 治理

**问**（笔试·编程+场景题）：一条「紧急维护通知」要触达 500 人——通知渠道矩阵（IM/邮件/短信/电话/状态页）按「紧急度 × 受众」怎么选（半夜 P0 用电话、日常变更用 IM），「触达确认」（已读/已 ack）怎么追踪（读了没动作 vs 没收到），通知轰炸（一次事故 30 条通知）的合并与抑制（Q7039 联动），「关键人失联」（手机关机）的兜底链怎么设计？

**答**：① 渠道矩阵：**紧急度**（P0 电话+IM+SMS 三打）/ **受众**（值班员即时、全员的 IM 群、客户的邮件+状态页）——矩阵的行是渠道、列是场景，每格预写「用不用/延迟多少」——半夜 P0 必须电话（IM 会被免打扰吞掉），日常变更禁用电话（狼来了）。② 触达确认：**已送达 ≠ 已读 ≠ 已行动**三层——电话是天然 ack（接了才算）、IM 要显式 ack 按钮（读了没行动要区分：ack=「我知道了并会处理」）——15 分钟无 ack 自动升级（Q145 升级链）。③ 轰炸合并：同根因合并（Q7039）、30 分钟窗口内同服务限一条、群发通知低频化（每日摘要代替逐条）——轰炸的根因多数是「每条告警都通知」而非「合并缺失」。④ 失联兜底：升级链本身就是兜底（Q145）——再加**通道健康监控**（短信网关故障时自动切 IM——通道故障也是告警）。

```python
# 全部标准库；demo 实现「渠道矩阵 + 三层确认追踪」
import time

MATRIX = {
    # (紧急度, 受众) -> 渠道列表
    ("P0", "oncall"):    ["phone", "im", "sms"],
    ("P0", "team"):      ["im", "sms"],
    ("P1", "oncall"):    ["im"],
    ("routine", "all"):  ["im_digest"],          # 日常：每日摘要
    ("routine", "customer"): ["email", "status_page"],
}

class Notifier:
    def __init__(self):
        self.sent: dict[str, float] = {}         # notification_id -> 发送时刻
        self.acked: set[str] = set()
        self.read_but_no_ack: set[str] = set()
    def notify(self, nid: str, urgency: str, audience: str) -> list[str]:
        channels = MATRIX.get((urgency, audience), ["im"])
        self.sent[nid] = time.monotonic()
        return channels                          # 按矩阵发渠道
    def mark_read(self, nid: str):
        if nid in self.sent and nid not in self.acked:
            self.read_but_no_ack.add(nid)        # 已读未行动：区分追踪
    def ack(self, nid: str):
        self.acked.add(nid)
    def pending_escalation(self, timeout_s: float = 900) -> list[str]:
        now = time.monotonic()
        return [nid for nid, t in self.sent.items()
                if nid not in self.acked and now - t > timeout_s]  # 15min 无 ack 升级

if __name__ == "__main__":
    n = Notifier()
    ch = n.notify("N1", "P0", "oncall")
    assert ch == ["phone", "im", "sms"], ch
    n.mark_read("N1")                             # 已读但没 ack
    pending = n.pending_escalation(timeout_s=0)   # demo 即时判定
    assert "N1" in pending
    print("渠道矩阵: P0 oncall →", ch)
    print("三层确认：已送达/已读/已 ack 分离，已读未行动 15 分钟自动升级 ✅")
    ch2 = n.notify("N2", "routine", "customer")
    assert ch2 == ["email", "status_page"]
    print("日常变更 → 邮件+状态页（不打电话）✅")
    # 口径：矩阵预写「渠道×场景」；已送达≠已读≠已行动三层分离；
    # 同根因合并+每日摘要防轰炸；失联兜底=升级链+通道健康监控。
```

**追问**：1) 为什么「已读」和「已 ack」要分离追踪？——已读（IM 的已读回执）只说明「看到了」，没 ack 说明「没打算处理或漏了」——值班场景里「看到了没动」比「没看到」更危险（自觉性缺口）；分离追踪让升级策略精确（已读未 ack 15 分钟升级=点名提醒）2) 「每日摘要」会不会让重要变更被淹没？（提示：摘要只装 routine 级——P0/P1 永远即时单独通知；摘要里条目按影响排序+链接直达详情——「重要即时+琐碎摘要」的分流是标准做法，全即时才是轰炸根源）3) 通知渠道本身故障（短信网关挂了）怎么发现？（提示：通道投递失败率监控（Q145 DeliveryMonitor 同构）+ 通道故障自动切换备用渠道（SMS 挂切 IM 群发+电话）——通知系统的告警是「告警的告警」，同样要监控）

## 背诵要点
1. 渠道矩阵按「紧急度 × 受众」预写每格渠道——半夜 P0 电话三打，日常变更 IM 摘要。
2. 三层确认分离：已送达/已读/已 ack——已读未行动 15 分钟自动升级；电话天然 ack。
3. 轰炸治理：同根因合并 + 30 分钟限频 + routine 级每日摘要——「重要即时+琐碎摘要」分流。

## 复盘追问
1. 通知系统对接了 5 个渠道，渠道配置散落在各服务里（每服务自己发通知），怎么治理？（提示：收敛到统一通知服务（模板+渠道矩阵集中管理）——散装通知的轰炸与漏发无法全局治理；统一服务的成本是引入一个 Tier-1 依赖（自身要高可用））
2. 客户抱怨「维护通知半夜 2 点发到手机」，触达时段也要治理？（提示：对客户的通知按「客户本地时区」的合理时段发送（Q165 时区口径）；内部 P0 通知不分时段——受众与时段的组合是矩阵的第三维：紧急即时、非紧急按时区工作时段）
