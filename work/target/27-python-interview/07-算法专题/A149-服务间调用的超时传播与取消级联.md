### A149 · 超时传播与取消级联

> 难度:★★★ | 标签:超时, deadline, 场景题

**问**（笔试·编程+场景题）：调用链 A(8s)→B(5s)→C(3s)，C 慢到 6s——A 的 8s 到期时 B/C 还在算（白干），Q6019 讲了预算分配；本卡补「取消级联」：上游 deadline 到期后**下游能不能感知并取消**（grpc deadline 的自动传播 vs HTTP 手动 header），「取消传播断了」（C 不知道 A 已放弃）的事故形态，C 的「取消后仍完成的事务」怎么处理（完成不可撤回的写操作）？

**答**：① 传播机制两代：**grpc** 协议级 deadline（`grpc-timeout` metadata），每一层 RPC 自动继承剩余预算并向上游报告取消——链路天然级联；**HTTP** 无原生机制，靠约定 header（`X-Deadline`，Q6019）+ 每层中间件**手动检查**（收到请求先算剩余，剩余不足直接快速失败）——任何一层忘了检查就断链。② 取消传播断了的事故形态：A 返回 504 给用户，但 B→C 的调用还在跑完——C 的写操作照常生效（「幽灵写」，Q6019 已提）→ 用户以为失败重试 → 双倍副作用；根因：B/C 不检查 deadline 且写操作非幂等。③ 「取消后仍完成」的处理：写操作与「客户端感知」解耦——C 完成的事务**落库并登记**（saga_id/deadline 过期标记），A 层对账发现「超时但实际成功」→ 给客户端补发成功事件（或幂等重试返回原结果，A102）——原则：**资源类副作用以实际完成为准，响应只是通知**。

```python
# 全部标准库；demo 实现「deadline 传递 + 到期检查 + 完成对账」
import time

def effective_timeout(cfg: float, deadline_left: float | None) -> float:
    """每层实际超时 = min(自身配置, 剩余预算)。"""
    if deadline_left is None:
        return cfg
    return max(0.05, min(cfg, deadline_left))

class Deadline:
    def __init__(self, total_s: float):
        self.expire_at = time.monotonic() + total_s
    def left(self) -> float:
        return self.expire_at - time.monotonic()

LEDGER = {}                        # 「取消后仍完成」的对账台账

def service_c(dl: Deadline, work_s: float, op_id: str) -> str:
    """最底层服务：deadline 到期时——a) 未开始则拒绝；b) 进行中事务完成并登记对账。"""
    left = dl.left()
    if left <= 0:
        return "rejected-early"                       # 快速失败，不开始
    started = time.monotonic()
    time.sleep(min(work_s, max(left, 0.05)))          # 模拟工作
    finished = work_s <= left
    if finished:
        LEDGER[op_id] = "completed-after-deadline"    # 完成即登记（幂等键=op_id）
        return "completed-but-deadline-passed"        # 幽灵写已登记，待对账
    return "cancelled-by-deadline"

if __name__ == "__main__":
    dl = Deadline(total_s=0.1)                        # A 层预算 100ms
    # 场景1：C 快速完成但已超 deadline（幽灵写）
    r1 = service_c(dl, work_s=0.15, op_id="op-1")
    assert r1 == "completed-but-deadline-passed" and LEDGER["op-1"] == "completed-after-deadline"
    print("幽灵写登记对账:", r1, "→ A 层对账发现实际成功，补发成功事件 ✅")
    # 场景2：deadline 已耗尽，C 直接拒绝
    dl2 = Deadline(total_s=0.01); time.sleep(0.05)
    r2 = service_c(dl2, work_s=0.15, op_id="op-2")
    assert r2 == "rejected-early"
    print("剩余预算为零 → 快速失败不开始 ✅")
    # 口径：每层 timeout=min(配置,剩余)；写操作完成即登记（幂等键），响应只是通知；
    # A 层对账把「超时但成功」补发给客户端（幂等重试返回原结果，A102）。
```

**追问**：1) 为什么「幽灵写」不能靠「取消时回滚 C 的事务」解决？——回滚时机不可控（C 可能已 commit）；且跨层回滚就是分布式事务（2PC 陷阱，Q129）——正解是「完成即登记 + 幂等对账」，把一致性交给最终一致而非强一致。2) grpc deadline 传播的「每层继承剩余」具体语义？（提示：子 RPC 的 deadline = 父剩余（不是父总额）——每层用掉的时间自动从下游预算里扣；开发者只需设根 deadline，中间层不设也会被继承约束——这是 grpc 对 HTTP 的最大体验优势）3) 「剩余不足直接快速失败」的阈值怎么定？（提示：剩余 < 单次调用 P99 + 安全余量时放弃——明知必超时还发出去 = 白耗下游；阈值按下游 P99 动态化而非写死）

## 背诵要点
1. 每层实际超时 = min(自身配置, deadline 剩余)；grpc 自动级联，HTTP 靠手动 header+检查——断链即幽灵写。
2. 幽灵写处理：写完成即登记对账台账（幂等键），A 层补发成功事件——副作用以实际完成为准，响应只是通知。
3. 剩余预算不足 → 快速失败不开始；「明知必超时还发」= 白耗下游。

## 复盘追问
1. 用户收到 504 重试，重试请求带同幂等键到 C，C 发现「op-1 已完成」返回原结果——这正是幂等键+对账的组合拳，画出这条链。（提示：504 → 重试（同键）→ C 幂等表命中原结果 → 返回 200——用户无感；前提 C 的幂等表按 op_id 建（A102））
2. 「每层都检查 deadline」的代码怎么不写成到处重复的样板？（提示：中间件/SDK 统一实现（拦截器一处写），业务代码无感——deadline 检查是基础设施职责不是业务职责）
