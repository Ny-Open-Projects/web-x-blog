### A114 · 慢任务诊断场景题

> 难度:★★★ | 标签:性能诊断, 排查方法论, 场景题

**问**（笔试·场景题）：周一上午导出任务 P99 从 30s 劣化到 8 分钟，用户投诉工单爆了——给出完整诊断流程：先看什么（分层定位：入口/应用/依赖/资源）、用什么工具（trace 火焰图慢 SQL 日志的先后顺序）、常见的「周一早高峰特有」根因有哪些，以及修复后怎么证明「真的修好了」？

**答**：诊断流程四层收敛：① **入口分层**（trace 定位耗时段）：trace_id 全链路一看——80% 时间在 DB 查询 / 在下游调用 / 在应用计算，30 秒内把嫌疑面从「整个系统」缩到一个段；② **段内工具链**：DB 段→慢 SQL 日志 + `EXPLAIN`（执行计划回归，Q6508）；应用段→py-spy 火焰图（CPU 栈，Q6010 口径）；下游段→下游自己的 P99 与限流指标；资源段→CPU/内存/IO（top/iostat）。③ **周一早高频根因**（按概率排）：周末数据量增长（回填任务把大表翻倍，执行计划从索引扫退化到全表扫——统计信息过期）；周一批量任务挤兑（定时任务全配了周一 9 点，连接池/线程池被打满）；缓存自然过期（周末无访问，周一缓存全冷，Q6020 冷启动形态）；上游客户端行为变化（报表用户周一集中拉全量）。④ **修复证明**：修复前后同口径对比（同一查询集、同时段、隔离变量）；执行计划 diff（修复前后 EXPLAIN 输出比对）；持续观察 3 个周一（排除偶然），并把「该案例的检测指标」固化成告警（防止同类复发无声回来）。

```python
# 全部标准库；demo 实现「耗时归因 + 慢查询执行计划回归检测」骨架
import time, hashlib

def attribute_latency(trace: dict) -> dict:
    """trace 归因：各段耗时占比，定位嫌疑段。"""
    spans = trace["spans"]                       # [(name, ms)]
    total = sum(ms for _, ms in spans)
    ranked = sorted(spans, key=lambda x: -x[1])
    return {"total_ms": total, "top": ranked[0],
            "pct": ranked[0][1] / total}

PLAN_CACHE: dict[str, str] = {}                  # 查询指纹 -> 上次执行计划摘要
def plan_regression(sql: str, explain: str) -> str | None:
    """执行计划回归：同 SQL 指纹计划变化 → 告警（统计过期/索引失效信号）。"""
    fp = hashlib.md5(" ".join(sql.split()).encode()).hexdigest()[:8]
    prev = PLAN_CACHE.get(fp)
    PLAN_CACHE[fp] = explain
    return f"计划回归: {prev} → {explain}" if prev and prev != explain else None

def monday_root_causes() -> list[str]:
    return ["周末数据增长→统计信息过期→计划退化", "周一批量任务挤兑连接池",
            "缓存全冷（周末无访问）", "报表用户集中拉全量"]

if __name__ == "__main__":
    trace = {"spans": [("app", 500), ("db.query", 40000), ("downstream", 800),
                       ("db.query2", 8000)]}
    attr = attribute_latency(trace)
    print(f"归因: {attr['top'][0]} 占 {attr['pct']:.0%}（嫌疑面收敛到 DB 段）")
    assert attr["top"][0] == "db.query"
    regress = plan_regression(
        "SELECT * FROM orders WHERE created > :d",
        "Seq Scan on orders (cost=0..999999)")   # 周一发现退化到全表扫
    print("执行计划回归:", regress)
    assert regress
    print("周一高频根因:", monday_root_causes()[:2], "…")
    # 修复证明口径：同口径前后对比 + EXPLAIN diff + 连续 3 个周期观察 + 固化告警。
```

**追问**：1) 为什么「执行计划回归」要按 SQL 指纹存？——同一模板 SQL 参数不同指纹不同（防误报），归一化后模板指纹才稳定；计划变化是「性能突降」最前置的信号（早于用户投诉）。2) py-spy 和 cProfile 的选择？——py-spy 附加在生产进程零侵入看火焰图（线上诊断首选）；cProfile 侵入但精确（复现环境用）；线上先 py-spy 定热点函数，再复现环境 cProfile 精确归因。3) 修复了但下一个周一又慢，说明什么？——修复打的是症状不是根因（如加了索引但统计信息仍过期）；系统性解法 = 统计信息定期刷新任务 + 周一批量任务错峰编排 + 容量按周一峰值规划。

## 背诵要点
1. 诊断四层收敛：trace 分段（30s 缩嫌疑面）→ 段内工具（EXPLAIN/py-spy/下游指标/资源）→ 高频根因清单 → 修复证明。
2. 周一特有根因：数据增长统计过期、批量任务挤兑、缓存全冷、报表集中拉全量。
3. 修复证明 = 同口径前后对比 + EXPLAIN diff + 3 周期观察 + 固化告警防复发。

## 复盘追问
1. trace 显示 80% 在 DB，但慢 SQL 日志没有超 1s 的查询——矛盾怎么解释？（提示：N+1（单条快但调 1000 次）、连接池等待（查询快但排队久）——「段内总耗时」与「单查询耗时」口径差）
2. 用户工单说「上周还好的」，怎么用数据回应？（提示：拉同口径 P99 周对比曲线定位劣化拐点，拐点对齐某次发布/数据增长事件——用时间线说话）
