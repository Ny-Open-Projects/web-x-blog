### A218 · 跨团队专家库

> 难度:★★☆ | 标签:专家库, 值班, 知识管理

**问**（笔试·场景题）：故障涉及 Kafka（但 Kafka 是数据团队的）——「跨团队专家」怎么找（不翻通讯录/不靠人情），专家库的字段设计（除了姓名还要什么：时区/响应承诺/擅长子领域），专家的「响应承诺」怎么管理（专家也是人，被半夜叫醒的边界），专家库的信息过期（专家离职/转岗）怎么自动发现？

**答**：① 专家库字段：`姓名+团队+时区+响应承诺（工作时间内 15 分钟响应/夜间 next-day）+擅长子领域（Kafka：生产者调优 vs 消费者积压——粗粒度「懂 Kafka」不够用）+验证状态（能力经演练验证过 vs 自报）`——响应承诺分级（Q166 路由矩阵对齐：T0 故障可叫醒/其他 next-day）。② 响应承诺管理：**专家贡献配额**（每人每月被叫醒次数上限——超限后自动轮到下一位专家，防单点骚扰）+ 演练验证（专家「能力」要经演练验证——A144 体系，自报的专家不可靠）——专家是稀缺资源，机制要保护专家（Q172 非打扰升级同构）。③ 过期自动发现：专家离职（HR 系统联动移除）、转岗（团队变更触发复审）、**响应失效**（被 call 后响应超承诺 → 自动降级该专家的响应承诺/标记待复审）——专家库是活文档（与 Q190 能力矩阵同源）。

```python
# 全部标准库；demo 实现「跨团队专家库路由」
import time

EXPERTS = [
    {"name": "kafka-king", "team": "data", "tz": "UTC+8", "domain": "consumer-lag",
     "commit": "15min-worktime", "verified": True, "monthly_calls": 4, "quota": 5},
    {"name": "kafka-jr", "team": "data", "tz": "UTC+8", "domain": "consumer-lag",
     "commit": "next-day", "verified": False, "monthly_calls": 0, "quota": 5},
]

def find_expert(domain: str, severity: str, hour_utc8: int) -> dict:
    """专家路由：子领域匹配 → 配额/验证过滤 → 响应承诺分级。"""
    cands = [e for e in EXPERTS if e["domain"] == domain]
    worktime = 9 <= hour_utc8 < 21
    for e in sorted(cands, key=lambda x: -x["verified"]):
        if e["monthly_calls"] >= e["quota"]:
            continue                            # 配额耗尽：轮下一位（防单点骚扰）
        if severity == "P0" and e["verified"] and (worktime or e["commit"].startswith("15min")):
            return {**e, "route": "page-now"}
        if worktime:
            return {**e, "route": "worktime-notify"}
    return {"route": "no-expert-available → 升级社区/厂商支持"}

def on_response(expert_name: str, responded_within: bool) -> str:
    """响应失效自动发现：超承诺响应 → 标记待复审。"""
    if not responded_within:
        return f"{expert_name} 超响应承诺 → 响应承诺降级 + 待复审"
    return "ok"

if __name__ == "__main__":
    r = find_expert("consumer-lag", "P0", hour_utc8=14)
    print("工作日 P0 路由:", r["name"], r["route"])
    assert r["route"] == "page-now" and r["verified"]
    print("响应失效:", on_response("kafka-king", responded_within=False))
    # 口径：专家库字段含子领域/时区/响应承诺/验证状态；配额轮换防单点骚扰；
    # 响应失效自动降级——专家库是活文档（Q190 能力矩阵同源）。
```

**追问**：1) 为什么「子领域」粒度比「懂 Kafka」重要？——「懂 Kafka」路由到的人可能只懂部署不懂消费者积压调优——故障场景需要精确匹配（消费者积压 → 找调优过积压的人）；粗粒度专家库 = 找到人但解决不了问题——子领域粒度决定路由有效性。2) 专家「能力自报」vs「演练验证」的差距？（提示：自报的「专家」可能只读过文档（没处理过真实积压）——演练验证（A144 故障注入+处置）是能力的实证；自报专家标 unverified，P0 路由只派 verified——路由优先级里验证状态是硬过滤）3) 专家库的冷启动（公司第一次建）怎么积累？（提示：从历史故障处置记录反推（谁解决过什么——Q176 知识库同源）+ 团队 lead 提名 + 首批专家做「演练验证」固化能力——冷启动靠历史数据，持续靠验证闭环）

## 背诵要点
1. 专家库字段：子领域（精确匹配路由）/时区/响应承诺分级/验证状态（演练实证优先于自报）。
2. 响应承诺管理：贡献配额（月上限超限轮换）防单点骚扰；P0 路由只派 verified 专家。
3. 过期自动发现三源：HR 离职联动/团队变更复审/响应失效自动降级——专家库是活文档。

## 复盘追问
1. 专家库建好后没人查（还是习惯问同事），怎么推动使用？（提示：路由闭环强制（值班升级链自动走专家库，不经手记通讯录）+ 专家库结果反馈（找到的专家确实解决了问题 → 正循环）——Q176「先搜再问」同构：把库嵌入流程而非另建体系）
2. 某领域只有一位专家且他休长假，故障来了怎么办？（提示：专家单点=覆盖缺口（Q190 覆盖矩阵同构）——缺口期故障走「社区/厂商支持」兜底路由 + 缺口登记（招人/培养第二专家的行动项）——专家库的覆盖缺口管理要与能力矩阵联动）
