### A228 · 跨团队值班协同

> 难度:★★☆ | 标签:值班, 跨团队, 场景题

**问**（笔试·场景题）：5 个团队各自值班，但故障常跨团队（一次故障涉及 3 个团队的服务）——「各自值班」的跨团队协同问题（谁牵头/重复排查/口径不一），「共享值班」模式（一个值班池覆盖所有服务——值班人处理不了非本团队服务怎么办），「协同值班」的折中设计（值班池+领域专家快线 A218），跨团队值班的「能力要求」与「责任边界」怎么定？

**答**：① 各自值班的三问题：**牵头真空**（故障跨 3 团队，谁当 IC（A150）？——没人牵头各修各的）、**重复排查**（3 个团队各自排查自己的服务——同样的排查做 3 遍）、**口径不一**（对客户/管理层的说法不同）。② 三模式光谱：各自值班（自治强协同弱）→ 协同值班（值班池+专家快线：值班池处理「通用响应」（告警确认/初步归因/按 runbook 止血），非本团队故障升级到领域专家快线——值班人不需要会所有服务，需要「快速找到会的人」）→ 共享值班（最高效但值班人能力要求极高）——团队规模与故障跨域率决定模式。③ 能力要求：协同值班的值班人要求 = 「通用响应能力（告警确认/止血动作/升级判断）+ 服务地图熟练（Q123 知道找谁）」——**不要求会修所有服务**（这是共享值班失败的常见原因：要求值班人全能）。④ 责任边界：值班池的响应责任（确认/止血/升级在 15 分钟内）与领域团队的修复责任（专家介入后的修复）分开——值班池不是「修所有问题的团队」，是「快速分诊与止血的团队」。

```python
# 全部标准库；demo 实现「协同值班值班池 + 领域专家快线」
import time

class CollabOncall:
    def __init__(self, pool: list[str], experts: dict[str, str]):
        self.pool = pool                        # 值班池（跨团队轮换）
        self.experts = experts                  # 服务 -> 领域专家（A218）
        self.routed: list[dict] = []
    def handle_alert(self, alert: dict, runbook_ok: bool) -> str:
        """值班池三步：确认 → runbook 止血 → 升级判断。"""
        if not runbook_ok:
            expert = self.experts.get(alert["service"])
            self.routed.append({"alert": alert["name"], "routed_to": expert,
                                "within_min": 15})
            return f"15 分钟内升级至领域专家 {expert}（值班池不修非本域故障）"
        return "值班池按 runbook 止血完成"
    def responsibility(self) -> dict:
        return {"pool_duty": "确认/止血/升级（15 分钟内）",
                "team_duty": "领域修复（专家介入后）",
                "boundary": "值班池是分诊止血团队，不是修所有问题的团队"}

if __name__ == "__main__":
    pool = CollabOncall(pool=["li", "wang", "zhao"],
                        experts={"payment": "pay-expert", "db": "dba-lead"})
    r1 = pool.handle_alert({"name": "db_lock", "service": "db"}, runbook_ok=True)
    print(r1)
    r2 = pool.handle_alert({"name": "pay_500", "service": "payment"}, runbook_ok=False)
    print(r2)
    assert "15 分钟内升级" in r2 and r2.endswith("pay-expert）")
    print(pool.responsibility())
    # 口径：值班池=通用响应（确认/止血/升级 15min），领域修复归专家快线；
    # 团队规模与故障跨域率决定模式选择。
```

**追问**：1) 为什么「值班池不修非本域故障」是设计而不是能力缺陷？——值班人学会所有 5 个团队的修复=能力要求极高（招不到/培养成本爆炸）；值班池的定位是「分诊+止血」（快但浅），修复深度由专家快线补——定位清晰才可执行；「要求全能」是共享值班失败的头号原因。2) 值班池人员从哪来？（提示：各团队轮流派（每团队出 1 人轮值池）——好处：值班人只精通自己团队的服务（其余靠快线），轮换自然覆盖 5 团队；坏处：轮换频率高（5 人一池每周轮）——轮换成本与覆盖收益的平衡）3) 跨团队值班的「值班补偿」怎么算公平？（提示：值班负担按团队分摊（Q221 负担口径跨团队化）——某团队故障多导致值班人负担重，负担归因到故障 owner 团队（不是值班人忍）——跨团队公平需要负担核算（故障归属数据）支撑）

## 背诵要点
1. 各自值班三问题：牵头真空/重复排查/口径不一——跨团队故障是常态场景，协同机制必需。
2. 协同值班折中：值班池（通用响应：确认/止血/升级 15 分钟）+ 领域专家快线（A218 深度修复）——值班人不需要全能，需要会分诊。
3. 责任边界：池=分诊止血，团队=深度修复；负担跨团队核算归因到故障 owner 团队。

## 复盘追问
1. 值班池模式跑了半年，领域团队抱怨「升级来的都是低质量告警」（值班池乱升级）——怎么治？（提示：升级质量反馈（专家对升级评分：必要/不必要）+ 值班池培训（分诊准确率提升）+ 升级标准校准（什么该升级写进 runbook，Q142）——反馈闭环让值班池分诊能力持续提升）
2. 协同值班模式需要「服务目录+runbook+专家库」三大基础设施，冷启动怎么排优先级？（提示：先 runbook（值班池止血的前提）→ 服务目录（升级路由前提）→ 专家库（快线前提）——runbook 是第一优先（没有 runbook 值班池无法止血，模式不成立）——基础设施按依赖序建设）
