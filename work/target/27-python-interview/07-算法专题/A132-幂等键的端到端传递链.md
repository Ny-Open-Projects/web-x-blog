### A132 · 幂等键端到端传递

> 难度:★★★ | 标签:幂等, 链路传播, 场景题

**问**（笔试·场景题）：客户端带了 `Idempotency-Key`，但链路是「网关 → 订单服务 → 库存服务 → 支付服务」——每个服务各自「新生成幂等键」会发生什么（一次客户端重试放大成 N 次下游重复）？幂等键怎么跨服务传递（透传 vs 派生键），派生键的构造规则（父键+步骤号），网关层的幂等缓存（同键返回缓存响应）要存什么？

**答**：① 透传纪律：客户端幂等键必须**全链路透传**（header 一路带下去），下游服务若因内部重试需再生成，必须用**派生键**（`parent_key + ":" + step_name`）——不能随机新生成：新生成 = 客户端一次重试 → 每层各执行一次 → N 倍重复副作用。② 派生键构造：步骤号固定（`abc123:deduct_stock`），同一次调用内多次重试命中同一键；跨步骤不同键（各自独立幂等域）。③ 网关幂等缓存：`key -> (status, response_body, fingerprint)` 三元组——**响应也缓存**（同键重放返回首次响应而非再执行），响应指纹防「同键不同请求体」的误用（客户端 bug：改了内容复用同键 → 422 拒绝）；TTL 与存储（Redis，24h 常规）。④ 失败语义：首次请求处理中（占位锁，Q6060 并发抢占）→ 第二请求返回 409/202 而非排队执行。

```python
# 全部标准库；demo 实现「派生键 + 网关幂等缓存 + 指纹防误用」
import hashlib, json

def derive(parent_key: str, step: str) -> str:
    return f"{parent_key}:{step}"

def fingerprint(body: dict) -> str:
    return hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest()[:16]

class GatewayIdempotency:
    """网关幂等缓存：key -> (status, response, fingerprint)。"""
    def __init__(self):
        self.store: dict[str, tuple] = {}
        self.inflight: set[str] = set()
    def handle(self, key: str, body: dict, executor) -> tuple[int, dict]:
        fp = fingerprint(body)
        if key in self.store:
            status, resp, stored_fp = self.store[key]
            if stored_fp != fp:
                return 422, {"error": "同键不同请求体（客户端 bug）"}
            return status, resp                      # 重放首次响应
        if key in self.inflight:
            return 409, {"error": "处理中，请稍后重试"}   # 并发抢占
        self.inflight.add(key)
        try:
            resp = executor(body)
            self.store[key] = (200, resp, fp)
            return 200, resp
        finally:
            self.inflight.discard(key)

ORDERS = []
def order_executor(body: dict) -> dict:
    """订单服务：内部对下游用派生键。"""
    key = body["Idempotency-Key"]
    stock_key = derive(key, "deduct_stock")          # 派生键：透传纪律
    pay_key = derive(key, "charge")
    ORDERS.append({"id": key, "stock_key": stock_key, "pay_key": pay_key})
    return {"order": ORDERS[-1]}

if __name__ == "__main__":
    gw = GatewayIdempotency()
    body = {"Idempotency-Key": "abc123", "item": "sku-9", "qty": 1}
    s1, r1 = gw.handle("abc123", body, order_executor)
    s2, r2 = gw.handle("abc123", body, order_executor)   # 客户端重试
    assert s1 == 200 and s2 == 200 and r1 == r2          # 重放首次响应
    assert len(ORDERS) == 1                              # 只执行一次 ✅
    print("幂等键重放：重试返回首次响应，下游只执行一次 ✅")
    body2 = dict(body, qty=5)                            # 同键不同内容
    s3, msg = gw.handle("abc123", body2, order_executor)
    assert s3 == 422
    print("指纹防误用：同键不同请求体 → 422 ✅")
    body3 = {"Idempotency-Key": "abc124", "item": "sku-9", "qty": 1}
    print("派生键示例:", derive("abc124", "deduct_stock"))
    # 口径：透传 or 派生（parent:step），绝不新生成；缓存三元组含响应+指纹；
    # 处理中并发请求返回 409 而非排队执行。
```

**追问**：1) 为什么下游不能「直接用客户端键查自己的幂等表」？——可以且应该（透传），但下游还有**自己的内部重试**（调它自己的下游失败重试）——内部重试若新生成键就破了链路；派生键让「内部重试」与「上游重试」命中同一键域。2) 幂等缓存的 TTL 怎么定？——覆盖客户端最大重试窗口（通常 24h）；过期后同键再来的请求会执行新操作——业务上接受（超 24h 的重试已经无意义），金融场景可延长。3) 处理中请求返回 409 还是 202？——202（处理中，稍后查询）体验更好但要客户端轮询逻辑；409 简单粗暴适合低频场景——网关统一约定一种并写进 API 文档。

## 背诵要点
1. 幂等键全链路透传，内部重试用派生键（parent:step）——新生成键 = N 倍重复副作用。
2. 网关缓存三元组 key→(status, response, fingerprint)：重放首次响应 + 422 拦同键不同体。
3. 处理中并发请求返回 409/202 而非排队执行；TTL 覆盖客户端重试窗口（24h 常规）。

## 复盘追问
1. 链路中间某服务不配合透传（SDK 里读不到 header），怎么兜底？（提示：网关把键注入内部 header（X-Gateway-Idem）+ 该服务的幂等表由网关代管（代理模式）——或推动 SDK 更新，短期用代理兜底）
2. 「同键不同请求体」被 422 拒绝但客户端确实想改数量重新下单，正确姿势？（提示：改内容 = 新业务操作 = 新键；同键语义就是「同一操作的重试」——客户端设计要在文档里明确「键的生命周期=一次业务操作」）
