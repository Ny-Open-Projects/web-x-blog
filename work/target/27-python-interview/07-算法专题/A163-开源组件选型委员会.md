### A163 · 开源组件选型

> 难度:★★☆ | 标签:选型, 评审, 生命周期

**问**（笔试·场景题）：团队想引入一个新的开源库（比如新的队列框架）——「引入评审」要审什么（活跃度/许可证/成熟度/退出成本），「star 数」为什么是最不可靠的指标，组件的「生命周期状态」怎么标记（活跃/维护模式/弃坑）与年审机制，「引入容易移除难」的退出成本怎么在选型时就评估（抽象层 vs 直接依赖）？

**答**：① 评审四维：**活跃度**（最近 commit/release 频率、issue 响应时长——比 star 靠谱：star 是一次性投票，commit 是持续承诺）、**许可证**（AGPL/SSPL 对商用的影响——Q6609 Redis 许可证变更的教训）、**成熟度**（生产案例/测试覆盖/破坏性变更频率）、**退出成本**（封装一层抽象？API 面多宽？数据格式绑定多深？）。② star 不可靠：刷 star、热度≠质量（明星项目也可能弃坑）、star 反映「关注度」不反映「维护意愿」——可靠指标：contributor 数量与分布（>10 个活跃 contributor 而非 1 人独扛）、release 节奏、breaking change 频率。③ 生命周期年审：引入时标记状态（active/maintenance/deprecated），**每年复审**——维护模式（只修安全不添功能）的组件要评估替代品；弃坑组件（2 年无 release）进迁移清单（Q163 zombie 组件就是事故源）。④ 退出成本前置评估：选型时就写「退出方案」（替换成本/数据迁移/接口适配层厚度）——直接深度依赖（用了它的全部特性）退出成本极高，薄抽象层（只用核心 API）退出容易——但抽象层也有成本（性能/维护），权衡点在「组件被替换的概率 × 抽象层成本」。

```python
# 全部标准库；demo 实现「选型评分卡 + 年审清单」
import time

def score_component(repo: dict) -> dict:
    """四维评分：活跃度/许可证/成熟度/退出成本（0-10 分）。"""
    commits_recent = repo.get("commits_last_year", 0)
    contributors = repo.get("active_contributors", 0)
    license_ok = repo["license"] in ("MIT", "Apache-2.0", "BSD")
    breaking = repo.get("breaking_changes_last_year", 0)
    activity = min(10, commits_recent / 50 + contributors)
    maturity = max(0, 10 - breaking * 2 - (0 if repo.get("prod_cases") else 3))
    exit_cost = 10 - repo.get("api_surface_width", 5)      # API 面越宽退出越难
    return {"activity": round(activity, 1), "license_ok": license_ok,
            "maturity": maturity, "exit_cost": max(0, exit_cost),
            "verdict": "adopt" if license_ok and activity >= 5 and maturity >= 5
                       else "trial" if activity >= 3 else "avoid"}

def yearly_audit(registry: list[dict]) -> list[str]:
    """年审：维护模式/弃坑组件评估替代品。"""
    actions = []
    now = time.time()
    for c in registry:
        age_years = (now - c["last_release_ts"]) / (365 * 86400)
        if age_years > 2:
            actions.append(f"{c['name']} 2 年无 release → 进迁移清单")
        elif c.get("status") == "maintenance":
            actions.append(f"{c['name']} 维护模式 → 评估替代品")
    return actions

if __name__ == "__main__":
    repo = {"name": "some-queue", "license": "Apache-2.0", "commits_last_year": 300,
            "active_contributors": 12, "breaking_changes_last_year": 1,
            "prod_cases": True, "api_surface_width": 6}
    score = score_component(repo)
    print("选型评分:", score)
    assert score["verdict"] == "adopt"
    # 反例：万星但单人维护
    hot = {"name": "hot-lib", "license": "MIT", "commits_last_year": 30,
           "active_contributors": 1, "breaking_changes_last_year": 4,
           "prod_cases": False, "api_surface_width": 8}
    print("万星单人库评分:", score_component(hot)["verdict"], "—— star 不救生命周期")
    registry = [{"name": "old-lib", "last_release_ts": time.time() - 3 * 365 * 86400}]
    print("年审:", yearly_audit(registry))
    # 退出成本口径：选型时写「退出方案」（抽象层厚度 × 替换概率权衡）。
```

**追问**：1) 为什么「active_contributors」比 commit 数更关键？——commit 数可以刷（bot/单人高频），但 contributor 分布反映「社区可持续性」：单人项目 = 人走项目死（xz 事件模式，Q7020）；>10 个活跃 contributor 的项目死掉的概率显著低。2) 薄抽象层的成本什么时候不值得？（提示：组件替换概率极低（如 Python 解释器本身）时抽象层是纯开销（性能+维护）；高概率替换（存储/云 SDK——商业变动频繁）才值得抽象——抽象的判断依据是替换概率，不是教条）3) 「许可证年审」要审什么？（提示：项目自身许可证变更（Redis RSALV2 事件——社区版改许可）+ 传递依赖的许可证（依赖树的许可证污染）——引入时审一次不够，依赖升级时重审）

## 背诵要点
1. 选型四维评审：活跃度（commit+contributor 分布）/许可证/成熟度/退出成本——star 是最不可靠指标。
2. 生命周期年审：维护模式评估替代品、2 年无 release 进迁移清单——弃坑组件是事故源。
3. 退出成本前置：抽象层厚度 × 替换概率权衡；替换概率高的组件才值得薄抽象。

## 复盘追问
1. 团队引入了评审通过的组件，但半年后核心维护者跑了——评审漏了什么？（提示：评审看的是「当下状态」，缺「_BUS 模型集中度风险」（bus factor）——单人核心 = 高风险项应在评分卡里一票否决或要求后备方案；年审也应追踪 contributor 变化趋势）
2. 两个组件评分相同（都能用），怎么选？（提示：加维度决胜——团队已有经验（学习成本）、社区与我方技术栈匹配度、生态集成（周边工具）、公司已有组件先例（运维熟悉度）——评分卡决胜维度可以按场景加权重）
