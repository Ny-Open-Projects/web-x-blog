### A175 · 值班轮岗覆盖

> 难度:★★☆ | 标签:轮岗, 能力矩阵, 团队

**问**（笔试·编程+场景题）：值班表里「永远只有 2 个人会处理支付故障」——能力矩阵（谁会处理什么故障）怎么建与更新，「轮岗覆盖」怎么排（每个故障类型至少 N 人会处理——覆盖矩阵的行列约束），「能力培养」怎么嵌入轮岗（shadow 制度的进阶版：从 shadow 到 solo 的晋级标准），能力矩阵的老化（人离职/新故障类型）怎么更新？

**答**：① 能力矩阵：行=故障类型（服务×故障模式），列=人员，格=熟练度（solo 可独立处置 / assisted 需协助 / none）——矩阵来源：历史处置记录 + 值班后自评 + 演练验证（A144）——「熟练度」要有客观口径（solo=近半年独立处置过 ≥2 次）。② 覆盖约束：**每个故障类型 ≥2 人 solo**（总线因子防护，Q149 同构）+ ≥1 人可 7×24 联系到——排班时作为硬约束（覆盖不足的类型优先安排 shadow 培养而不是排班）。③ 培养嵌入：shadow → assisted → solo 的晋级路径（shadow 看处置、assisted 参与处置、solo 独立处置+验证演练）——晋级标准客观化（assisted 处置 ≥3 次且一次演练 solo 通过）——「从没处理过」的人永远不排班 → 永远不会处理（培养要靠排班制造机会）。④ 矩阵老化：季度复审（离职/转岗的人移除、新故障类型加行）+ 演练结果更新（演练失败的降级熟练度）——矩阵是活文档。

```python
# 全部标准库；demo 实现「覆盖矩阵校验 + 轮岗推荐」
from collections import defaultdict

SKILLS = {                                  # 故障类型 -> {人: 熟练度}
    "payment_timeout": {"alice": "solo", "bob": "assisted", "carol": "none"},
    "db_lock": {"alice": "assisted", "bob": "solo", "dave": "solo"},
    "cache_storm": {"carol": "solo", "dave": "none"},
}
SOLO_REQUIRED = 2

def coverage_gaps(skills: dict, required: int = SOLO_REQUIRED) -> list[str]:
    """覆盖缺口：solo 人数 <required 的故障类型。"""
    gaps = []
    for fault, people in skills.items():
        solo = sum(1 for lv in people.values() if lv == "solo")
        if solo < required:
            gaps.append(f"{fault}: solo 仅 {solo} 人（需 {required}）→ 优先排 shadow")
    return gaps

def shadow_recommend(gaps: list[str], skills: dict) -> list[tuple[str, str, str]]:
    """培养推荐：给缺口类型配 shadow（mentor=solo, trainee=assisted/none）。"""
    recs = []
    for gap in gaps:
        fault = gap.split(":")[0]
        people = skills[fault]
        mentor = next(p for p, lv in people.items() if lv == "solo")
        for p, lv in people.items():
            if lv in ("assisted", "none") and p != mentor:
                recs.append((fault, mentor, p))
                break
    return recs

if __name__ == "__main__":
    gaps = coverage_gaps(SKILLS)
    for g in gaps: print("覆盖缺口:", g)
    assert len(gaps) == 2                   # payment/cache 都缺 solo
    recs = shadow_recommend(gaps, SKILLS)
    print("培养推荐:", recs)
    assert ("payment_timeout", "alice", "bob") in recs
    # 口径：每故障类型 solo ≥2（总线因子防护）；培养嵌入排班（shadow→assisted→solo）；
    # 矩阵季度复审 + 演练结果更新——活文档。
```

**追问**：1) 为什么「solo ≥2 人」是硬约束而「≥1 人可联系」是软要求？——solo=能独立处置（不依赖特定人在线）；1 人可联系=依赖那个人 7×24 在线（单点人）——值班连续性要求处置能力冗余至少 2，与代码总线因子（Q149）同源。2) 「培养要靠排班制造机会」与「值班质量」怎么平衡？（提示：培养时段安排在低风险班次（工作日白天+mentor 在线）——shadow 不是「新手独自值班」而是「新手参与处置」——排班给机会但不拿生产环境赌新手；solo 晋级靠演练验证（A144）兜底）3) 能力矩阵的「熟练度」自评会虚高吗？（提示：会——solo 标准客观化（近半年独立处置 ≥2 次 + 演练 solo 通过）代替自评；自评只做参考，历史记录与演练做判定——客观口径防虚高）

## 背诵要点
1. 能力矩阵：行=故障类型、列=人员、格=熟练度（solo/assisted/none），solo 口径客观化（近半年独立处置 ≥2 次+演练通过）。
2. 覆盖硬约束：每故障类型 solo ≥2（总线因子防护）——覆盖缺口优先排 shadow 培养而非硬排班。
3. 培养路径 shadow→assisted→solo 嵌入排班（低风险班次造机会）；矩阵季度复审+演练更新——活文档。

## 复盘追问
1. 培养计划跑了半年，「assisted→solo」一个都没晋级——培养机制哪里断了？（提示：晋级标准是否可达（机会数不够——assisted 班次太少）、mentor 是否投入（带新人无激励）、演练是否提供（solo 演练机会缺失）——三个断点逐一排查，通常是「机会与激励双缺」）
2. 某故障类型只有 1 个 solo 且他马上离职——离职前的应急知识转移怎么排？（提示：离职前密集 shadow（每周 N 次跟班）+ 知识转移清单（A149 问题库式）+ 离职后缺口期「该故障告警升级快线直连他（顾问期）」——应急转移是轮岗制度的最后防线，制度化之前靠人情兜底）
