### A182 · 单测断言与边界

> 难度:★★☆ | 标签:单元测试, 断言, 边界

**问**（笔试·编程+场景题）：「测试全绿」但线上炸了——弱断言的形态有哪些（只断言不抛异常/断言实现而非行为/浮点直接 ==），边界覆盖清单（空/零/负/极大/Unicode/并发），「测试断言的等价性」（`assert result == expected` 里 expected 怎么来——从实现抄 vs 独立推导），测试代码自身的维护成本（脆弱断言）怎么控制？

**答**：① 弱断言三形态：**只断不炸**（`assert func(x) is not None`——任何返回都过）、**断言实现**（`assert result == {"items": [...], "total": 2}` 硬编码内部结构——重构即碎，而行为没变）、**浮点直等**（`assert 0.1 + 0.2 == 0.3` False——用 `math.isclose`/pytest.approx）。正确姿势：**断言行为契约**（输入 → 可观察输出/副作用），用「独立推导的期望值」（手算或另一实现交叉验证，不从被测实现抄——抄实现 = 永远绿的废测试）。② 边界清单：空集合/0/负数/极大值（溢出）/Unicode（emoji/组合字符）/空字符串/None/并发重复——每个边界一个用例（参数化批量跑）。③ 脆弱断言控制：断言「稳定字段」（不断言时间戳/随机 id——用 matcher/忽略字段）、快照测试谨慎用（快照更新要 review，不能一键接受）。

```python
# 全部标准库 + pytest 口径；demo 展示强弱断言对比与边界参数化
import math, pytest

def calc_discount(price: float, vip: bool) -> float:
    """被测函数：VIP 9 折，满 100 减 10（不可叠加）。"""
    if vip:
        price *= 0.9
    elif price >= 100:
        price -= 10
    return price

# 弱断言（反面教材）
def test_weak():
    assert calc_discount(200, False) is not None        # 只断不炸：任何实现都过

# 强断言：行为契约 + 独立推导期望
@pytest.mark.parametrize("price,vip,expected", [
    (100, False, 90),          # 满减边界：恰好 100
    (99.99, False, 99.99),     # 差一分不满
    (100, True, 90),           # VIP 优先且不可叠加（200 VIP = 180 不是 170）
    (200, True, 180),
    (0, False, 0),             # 零边界
    (1e9, True, 9e8),          # 极大值
])
def test_contract(price, vip, expected):
    assert math.isclose(calc_discount(price, vip), expected), (price, vip)

def test_float_assert():
    # 浮点直等错误示范 vs 正确
    assert not (0.1 + 0.2 == 0.3)
    assert math.isclose(0.1 + 0.2, 0.3)

def test_unicode_boundary():
    s = "café\u0301"            # 组合字符 é
    assert len(s) == 5          # len 数的是码点——测试把 Unicode 边界钉住

if __name__ == "__main__":
    test_contract.__wrapped__ if False else None
    # pytest 运行口径：pytest test_x.py -v；无 pytest 降级：直接断言循环调用
    cases = [(100, False, 90), (100, True, 90), (200, True, 180), (0, False, 0)]
    for price, vip, expected in cases:
        got = calc_discount(price, vip)
        assert math.isclose(got, expected), (price, vip, got)
    print("边界参数化（含 VIP 优先不可叠加契约）全绿 ✅")
    test_unicode_boundary()
    print("Unicode 码点边界钉住 ✅")
```

**追问**：1) 为什么「从实现抄期望值」的测试是废测试？——期望值来自被测实现 = 永远通过（实现错了期望跟着错）；期望必须独立来源（手算/需求文档/第二实现）——测试的本质是「交叉验证」，同源验证没有信息量。2) 「VIP 优先且不可叠加」这种业务规则怎么从需求里挖出来？（提示：需求文档常写「VIP 9 折、满 100 减 10」没写叠加关系——边界用例 (100, True) 会暴露歧义（90 还是 80？），写测试时发现歧义本身就是测试的价值（逼需求方澄清）；这正是 property-based/hypothesis 的补充价值）3) 快照测试（snapshot）一键更新为什么危险？（提示：一键接受 = 把回归的输出当成新期望（与「抄实现」同病）——快照更新必须人工 review diff（变化是预期的吗），CI 禁止自动更新快照）

## 背诵要点
1. 弱断言三形态：只断不炸/断言实现（硬编码内部结构）/浮点直等——正解是断言行为契约+独立推导期望。
2. 边界清单：空/零/负/极大/Unicode 码点/并发重复——恰好踩线的用例（99.99 vs 100）最能逼出需求歧义。
3. 脆弱断言控制：不断言时间戳/随机字段（matcher），快照更新必须人工 review。

## 复盘追问
1. 团队的测试「覆盖率 90% 但线上 bug 不断」，覆盖率与质量的脱节根因？（提示：覆盖率测「代码被执行」不测「断言质量」——弱断言的测试跑过也白跑（本卡反面教材）；变异测试（Q7148 相关）能测断言质量：改坏实现看测试会不会红——测试的测试）
2. 遗留代码没有测试，补测试时「按现状写测试」（把 bug 固化成期望）还是「按应有行为写」（测试全红）？（提示：分两步：先「现状快照测试」钉住行为（防重构破坏），bug 单独建 issue + 「应有行为」的红测试标注 xfail——重构时把 xfail 转正；不要一上来写全红测试阻塞 CI）
