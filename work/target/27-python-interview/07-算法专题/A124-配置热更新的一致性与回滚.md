### A124 · 配置热更新

> 难度:★★☆ | 标签:配置管理, 一致性, 场景题

**问**（笔试·编程+场景题）：配置中心推了个参数（超时从 3s 改 30s），集群 20 个实例——「一半实例新配置一半旧配置」的行为不一致怎么处理（配置版本快照 vs 逐项生效），配置合法性校验（改错值服务起不来）在哪层做，热更新误操作的回滚怎么做到秒级？

**答**：① 一致性：配置推送是**异步的**（20 实例收到有先后），「读到半新半旧」不可避免——应用侧要求配置**按版本快照生效**（实例要么整套 v12 要么 v11，不逐项混用——同 A118 评估快照同构）；对一致性敏感的配置（限流阈值/路由表）加「版本指纹」，多实例版本不一致超 5 分钟告警。② 合法性校验双层：**写入侧**（配置中心提交时 schema 校验+范围检查：超时 ∈ [0.1s, 60s]——拦截 90% 误操作）+ **应用侧**（加载时校验失败 → 保留旧版本运行 + 告警——绝不用非法配置重启，宁可旧配置也不要起不来）。③ 回滚：配置中心保存历史版本，回滚 = 指回 v11（秒级）——但应用侧要防「回滚风暴」（20 实例同时重载引发抖动），加滚动生效（分批 5 实例/批）。④ 配置分级的更新语义：静态配置（连接池大小——需重启生效，写清文档）vs 动态配置（阈值/开关——热生效），混放一起热更 = 「改了没生效」的事故来源。

```python
# 全部标准库；demo 实现「版本快照 + 双层校验 + 滚动回滚」
import time

SCHEMA = {"timeout_s": (0.1, 60.0), "rate_limit": (1, 100000), "flags": (None, None)}

def validate_config(cfg: dict) -> list[str]:
    errs = []
    for k, v in cfg.items():
        if k not in SCHEMA:
            errs.append(f"未知配置项: {k}")          # deny-by-default
        elif SCHEMA[k][0] is not None and not (SCHEMA[k][0] <= v <= SCHEMA[k][1]):
            errs.append(f"{k}={v} 超范围 {SCHEMA[k]}")
    return errs

class ConfigStore:
    def __init__(self):
        self.history: dict[int, dict] = {1: {"timeout_s": 3.0, "rate_limit": 100, "flags": {}}}
        self.current = 1
    def publish(self, cfg: dict) -> tuple[bool, str]:
        errs = validate_config(cfg)                   # 写入侧校验：拦截误操作
        if errs:
            return False, "; ".join(errs)
        self.current += 1
        self.history[self.current] = cfg
        return True, f"v{self.current}"

class AppConfig:
    """应用侧：版本快照生效，非法配置保留旧版。"""
    def __init__(self, store: ConfigStore):
        self.store = store
        self.version = 1
        self.snapshot = store.history[1]
        self.rollout_batch = 0                        # 滚动生效游标（模拟 5 实例/批）
    def reload(self, version: int | None = None):
        v = version or self.store.current
        cfg = self.store.history.get(v)
        errs = validate_config(cfg) if cfg else ["版本不存在"]
        if errs:
            return f"拒绝加载 v{v}: {errs}（保留旧版 v{self.version} 运行 + 告警）"
        self.version, self.snapshot = v, cfg
        return f"已生效 v{v}"
    def rollback(self, to_version: int):
        r = self.reload(to_version)
        self.rollout_batch = min(self.rollout_batch + 1, 4)   # 滚动：每批 5/20 实例
        return r, f"滚动批次 {self.rollout_batch}/4"

if __name__ == "__main__":
    store = ConfigStore()
    ok, msg = store.publish({"timeout_s": 30.0, "rate_limit": 200, "flags": {}})
    print("发布:", ok, msg)
    assert ok
    bad_ok, bad_msg = store.publish({"timeout_s": 3000.0, "rate_limit": 200, "flags": {}})
    assert not bad_ok and "超范围" in bad_msg         # 写入侧拦截 ✅
    print("写入侧拦截:", bad_msg)
    app = AppConfig(store)
    store.history[3] = {"timeout_s": 999, "rate_limit": 200, "flags": {}}   # 模拟漏网非法配置
    print(app.reload(3))                              # 应用侧兜底：保留旧版
    print(app.rollback(1))                            # 秒级回滚 + 滚动
    assert app.version == 1
    # 口径：版本快照防半新半旧；双层校验（写入拦 90%，应用兜底拒绝非法配置）；
    # 回滚秒级但滚动生效防抖。
```

**追问**：1) 为什么配置中心校验了应用还要再验？——绕路写入（脚本直改存储）、schema 更新不同步、配置中心 bug——信任边界永远在应用侧；「非法配置导致服务起不来」比「配置没生效」严重一个量级。2) 版本不一致告警（多实例版本分叉）的处置？（提示：先查推送通道（MQ 堆积/网络分区），不是查配置本身——分叉是通道问题不是配置问题）3) 静态 vs 动态配置的边界怎么定？（提示：改了需要重建资源（连接池/线程池）的 = 静态（重启生效）；纯读取值 = 动态（热更）——边界写进配置项元数据，不支持「改了没生效」的模糊状态）

## 背诵要点
1. 配置按版本快照整套生效（不逐项混用），多实例版本分叉超 5 分钟告警（通道问题）。
2. 双层校验：写入侧 schema+范围拦截（deny-by-default 未知项），应用侧加载校验失败保留旧版运行。
3. 回滚 = 版本指回（秒级）+ 滚动生效防抖；静态（重启生效）/动态（热更）边界写进元数据。

## 复盘追问
1. 「改了没生效」的事故怎么系统性消灭？（提示：配置项元数据标注生效方式（热更/重启）+ 生效后回读比对（apply 验证）+ 「改了未生效」的实例清单进巡检）
2. 20 实例里 1 个因本地缓存没刷新一直旧配置，读请求行为不一致怎么排查？（提示：实例自曝配置版本（healthz 返回 version）→ 对比集群版本分布 → 定位该实例重载机制故障）
