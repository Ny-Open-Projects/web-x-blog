### A185 · 回滚后兼容性

> 难度:★★★ | 标签:回滚, 兼容性, 事故恢复

**问**（笔试·场景题）：发布新版本写了「新格式」数据（用户表加了新列/缓存写了新结构），2 小时后回滚到旧版本——「新数据还在」旧代码读不懂会怎样（三种形态：忽略/崩溃/误读），回滚前的兼容性检查清单（数据格式/缓存/消息队列/外部副作用），「回滚脚本」与「回滚代码」的区别（回滚代码够吗——数据也要回滚），回滚后「修复后重新发布」的前置条件比首次发布多了什么？

**答**：① 新数据三形态：**忽略**（旧代码跳过未知字段——forward compatible，无害）、**崩溃**（旧代码对新列 NOT NULL 约束失败/解析失败）、**误读**（旧代码把新语义当旧语义——最危险，静默错误：新格式的「金额单位分」被旧代码当「元」，账目差 100 倍）。② 回滚前检查清单：**数据格式**（新写入的数据旧代码能否读——建新列是否带默认值、新缓存结构是否旧代码可解析）、**消息队列**（队列里积压的新格式消息，回滚后消费者怎么处理——死信暂存）、**外部副作用**（新版本已发的通知/已扣的款——回滚代码不撤回副作用）、**缓存双版本**（回滚后新旧缓存共存——读旧写旧但残留新键，清理策略）。③ 回滚代码 ≠ 回滚状态：**数据回滚**（新列填充默认值/新结构转换回旧结构——通常用「兼容读」替代物理回滚——便宜且安全）、**副作用清单**（逐项确认或撤销）。④ 重新发布前置：修复验证（针对根因的测试——不是重跑原测试集）+ 数据兼容确认（修复版本能处理「回滚期间的混合数据」）+ 灰度重启（不是全量——上次刚炸过）。

```python
# 全部标准库；demo 实现「兼容性检查 + 混合数据读取」
import json

def compat_check_new_data(records: list[dict], old_reader) -> dict[str, int]:
    """回滚后：旧代码视角逐条读新数据，分类三种形态。"""
    ignored = crashed = misread = 0
    for r in records:
        try:
            old_reader(r)
            if "unit" in r and r["unit"] == "cents":   # 新语义字段
                misread += 1                            # 旧代码把分当元 → 误读
            else:
                ignored += 1
        except Exception:
            crashed += 1
    return {"ignored": ignored, "crashed": crashed, "misread": misread}

def legacy_reader(record: dict) -> float:
    """旧版本读取逻辑：只认 amount（元）。"""
    return record["amount"]

def compat_shim(record: dict) -> float:
    """兼容垫片：识别新字段并转换（替代物理数据回滚）。"""
    if record.get("unit") == "cents":
        return record["amount"] / 100
    return record["amount"]

if __name__ == "__main__":
    records = [
        {"amount": 10, "unit": "cents"},        # 新版本写的：单位是分
        {"amount": 10},                          # 旧版本写的：单位是元
    ]
    result = compat_check_new_data(records, legacy_reader)
    print("回滚后混合数据读取分类:", result)
    assert result["misread"] == 1 and result["crashed"] == 0
    # 兼容垫片：旧代码加一层识别（便宜且安全，替代物理回滚数据）
    for r in records:
        print("垫片读取:", compat_shim(r), "←", r)
    # 口径：回滚前查四项（数据格式/队列/副作用/缓存）；兼容垫片优于物理数据回滚；
    # 重新发布前置：根因专项测试+混合数据兼容确认+灰度重启。
```

**追问**：1) 为什么「兼容垫片」优于「物理数据回滚」？——物理回滚（改数据）有风险（改错=二次事故）且量大（百万行改写），垫片只改读取路径（代码层，可测试可回退）；原则：数据不可逆操作能不做就不做——「读时兼容」是把不可逆变成可逆。2) 「外部副作用」回滚不了怎么办？（提示：逐项清单化（已发通知→补发更正；已扣款→退款流程；已发货→拦截/召回）——副作用撤回的成本远高于「不产生副作用」，所以高危副作用（支付/外发）必须在工具链入口设「确认门」（Q7516）而非事后撤）3) 「重新发布灰度重启」的灰度比例？（提示：比首次发布更保守（5% 起，Q7013）——上次刚在同一区域炸过；且灰度用户尽量避开「上次受影响用户」（信任修复期）——发布系统的用户标签灰度支持「排除集合」）

## 背诵要点
1. 回滚后新数据三形态：忽略（无害）/崩溃（显性）/误读（最危险静默错误——语义变化比格式变化毒）。
2. 回滚前四查：数据格式/消息队列积压/外部副作用/缓存双版本；兼容垫片优于物理数据回滚。
3. 重新发布前置：根因专项测试 + 混合数据兼容确认 + 更保守灰度（5% 起，避开上次受影响用户）。

## 复盘追问
1. 回滚后新格式数据一直在库里（垫片兼容着读），半年后垫片还在——这是债吗？（提示：是——垫片是「回滚应急产物」应登记债务台账（A140）：真正的还法是「完成旧格式数据迁移（Q6515 归档/转换流水线）后删除垫片」——垫片常驻会稀释新格式的存在感，两套读逻辑永远是坑）
2. 回滚 30 分钟后新版本又发布了（带修复），这期间用户经历了「新→回滚→再新」三个版本，数据形态三种——垫片能撑住吗？（提示：垫片设计要支持「多版本共存识别」（unit 字段就是版本标记），三种形态各走各的转换；教训：发布/回滚/再发布循环会叠加数据形态——兼容层要按「版本矩阵」设计而非单一 if）
