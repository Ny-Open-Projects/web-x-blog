### A227 · 值班制度年度审视

> 难度:★★☆ | 标签:制度, 年度审视, 治理

**问**（笔试·场景题）：值班制度三年没改过（业务翻了 5 倍）——制度年度审视的清单（哪些制度项要审视：冻结策略/告警分级/轮换周期/升级链），审视的输入（一年来的事故教训/值班数据/团队反馈——三个数据源），「制度的变革阻力」（老员工习惯旧制度/新制度有磨合成本）怎么管理，制度变更的「灰度」怎么做（制度变更也是变更，A133 同构）？

**答**：① 年度审视清单：**冻结策略**（L1/L2/L3 分级是否还匹配业务风险）、**告警分级**（T0/T1/T2 的预算假设是否还成立——业务量翻 5 倍预算厚度变了）、**轮换周期**（值班频率与团队规模的匹配）、**升级链**（路径是否还反映组织架构）——每项问「制度设计时的假设还成立吗」（假设失效=制度过期）。② 审视输入三源：事故教训（年内事故复盘的「制度层行动项」——A138 行动项里有制度类）、值班数据（负担/疲劳/覆盖率——Q221/Q225 的量化指标）、团队反馈（匿名调研——制度痛点只有执行者知道）。③ 变革阻力管理：变革理由数据化（新制度解决什么量化问题）+ 试点先行（1-2 个团队先跑一个季度，数据说话再推广）+ 保留旧制度的回滚通道（新制度磨合失败可回退——制度变更也有回滚预案，A174 同构）。④ 制度变更灰度：试点团队 → 数据对比（新旧制度的值班 KPI）→ 全团队推广 → 旧制度废弃——制度是「最上层的配置」，变更同样要灰度验证。

```python
# 全部标准库；demo 实现「制度年度审视器」
import time

REVIEW_ITEMS = [
    {"item": "告警分级", "design_assumption": "月告警量 <5000",
     "current_metric": 25000, "stale": True},
    {"item": "轮换周期", "design_assumption": "团队 8 人",
     "current_metric": 20, "stale": True},
    {"item": "升级链", "design_assumption": "组织架构未变",
     "current_metric": 0, "stale": False},
]

def annual_review(items: list[dict], feedback: dict) -> list[dict]:
    """年度审视：设计假设 vs 现实指标 → 过期制度清单 + 数据源标注。"""
    out = []
    for it in items:
        if it["stale"] or feedback.get(it["item"], {}).get("pain_score", 0) >= 4:
            out.append({**it, "verdict": "STALE: 设计假设失效，需修订",
                        "inputs": ["事故教训行动项", "值班数据", "团队反馈"]})
        else:
            out.append({**it, "verdict": "HEALTHY"})
    return out

def rollout_stages(new_policy: str) -> list[str]:
    """制度变更灰度：试点 → 数据对比 → 推广 → 旧制度废弃。"""
    return [f"{new_policy}: ① 1-2 个团队试点一季度",
            "② 新旧制度值班 KPI 对比（MTTR/疲劳调研）",
            "③ 数据支持则全团队推广",
            "④ 保留旧制度回滚通道一季度后废弃"]

if __name__ == "__main__":
    fb = {"告警分级": {"pain_score": 5}, "轮换周期": {"pain_score": 4}}
    out = annual_review(REVIEW_ITEMS, fb)
    for o in out:
        print(o["item"], "→", o["verdict"])
    assert sum(1 for o in out if o["verdict"].startswith("STALE")) == 2
    for s in rollout_stages("告警分级 v2"):
        print("制度灰度:", s)
    # 口径：年度审视问「设计假设还成立吗」；输入三源（事故/数据/反馈）；
    # 制度变更也是变更——试点先行+数据对比+回滚通道。
```

**追问**：1) 为什么「设计假设失效」是制度过期的判据？——制度是围绕假设设计的（告警分级假设月 5000 条——现在 25000 条，分级的预算模型全错）——审视的本质是「验证假设」而非「检查条文」——假设还成立则条文不用改（Q6012 兼容分级同构：假设=schema，条文=实现）。2) 「试点先行」的试点团队怎么选才不偏？（提示：选「代表性团队」（业务量中等+配合意愿）而非「最配合的团队」（配合意愿高的团队数据会偏乐观）——试点数据要可比（试点前后的对照+与其他团队的对照）——试点偏差会让坏制度通过验证）3) 制度回滚通道怎么设计？（提示：旧制度文档保留（不是删除）+ 回滚触发条件预定义（新制度 KPI 恶化连续一个月）+ 回滚的执行人明确（制度 owner）——与代码回滚（A174）同构：回滚预案是制度变更的一部分）

## 背诵要点
1. 年度审视判据：「制度设计时的假设还成立吗」（业务量/团队规模/组织架构变化=假设失效）——审视验证假设而非检查条文。
2. 输入三源：事故教训的制度层行动项 + 值班量化数据（Q221/Q225）+ 团队匿名反馈——三个数据源缺一不可。
3. 制度变更灰度：试点团队（代表性）→ KPI 对比 → 推广 → 旧制度回滚通道保留——制度是最高层配置，变更同样要灰度。

## 复盘追问
1. 年度审视做了，新制度发布了，但「没人按新制度执行」（执行率 0）——发布≠执行，缺了什么？（提示：制度发布缺「配套执行机制」（流程工具内嵌/owner 检查/违规可见性）——制度执行的难点从来不是「写出来」而是「嵌入日常流程」（Q7039 手册治理同构）；发布后 30 天执行率是制度变更的验收指标）
2. 新制度试点数据「看起来更好」但其实是因为试点团队恰好遇到淡季——试点偏差怎么防？（提示：对照周期拉长（跨淡旺季）+ 与其他团队同期对照（排除季节因素）+ 试点的「效应量」显著才推广（Q7008 统计口径）——试点数据的季节性偏差是制度灰度的常见坑）
