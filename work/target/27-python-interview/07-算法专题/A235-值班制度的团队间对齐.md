### A235 · 跨团队制度对齐

> 难度:★★☆ | 标签:制度, 跨团队, 治理

**问**（笔试·场景题）：5 个团队的值班制度各不相同（有的 7×24、有的只有工作时间）——跨团队协同（共享值班/跨团队升级）需要「公共标准」——哪些制度必须对齐（响应承诺/升级链语义/告警分级/交接格式），哪些可以团队自治（轮换细节/补偿方式/排班工具），公共标准的「制定与修订」流程（谁投票/多久复审），「不对齐的代价」（跨团队升级时语义错位）的具体形态？

**答**：① 必须对齐的四项（协同的「接口协议」）：**响应承诺分级**（T0/T1/T2 的语义统一——A 团队的 T0 ≠ B 团队的 T0 时，跨团队升级期望错位）、**升级链语义**（升级=拉资源≠甩锅的统一理解，A172）、**告警分级命名**（P0/P1/P2 统一定义）、**交接格式**（结构化模板统一——跨团队交接用同一模板，A184/A215）。② 可自治项：轮换细节（几人一轮）、补偿方式（调休/奖金）、排班工具——自治项是「不影响协同接口」的内部实现。③ 制定与修订流程：公共标准由「值班委员会」（各团队代表+平台团队）制定与季度复审——修订需要提案+试点+投票（制度变更灰度，Q227 同构）——**公共标准的修订门槛高于团队自治**（接口协议改了影响所有团队）。④ 不对齐的代价：跨团队升级时「升级方以为是 page（立即响应），被升级方以为是 ticket（次日看）」——响应期望错位 → 升级方等待 → MTTR 拉长 → 升级方失望 → 「以后直接叫 leader」（绕过机制）——不对齐的代价是**机制被绕过**。

```python
# 全部标准库；demo 实现「跨团队制度对齐检查器」
import time

COMMON_STANDARD = {
    "response_tiers": {"T0": "page-7x24", "T1": "page-worktime", "T2": "ticket"},
    "escalation_semantics": "拉资源非甩责，15min 无进展自动升",
    "alert_naming": {"P0": "资损/全站", "P1": "核心受损", "P2": "体验问题"},
    "handoff_template": "三节结构化（在途/风险/变更）",
}

def alignment_check(team_policy: dict) -> list[str]:
    """跨团队制度对齐检查：公共标准四项逐一对齐。"""
    issues = []
    if team_policy.get("response_tiers") != COMMON_STANDARD["response_tiers"]:
        issues.append("响应分级未对齐（跨团队升级期望错位风险）")
    if team_policy.get("alert_naming", {}).get("P0") != COMMON_STANDARD["alert_naming"]["P0"]:
        issues.append("P0 定义不一致（分级路由会错位）")
    if team_policy.get("handoff_template") != COMMON_STANDARD["handoff_template"]:
        issues.append("交接模板不同（跨团队交接质量不可比）")
    return issues

def misalignment_incident(mismatch: bool) -> str:
    return ("升级方期望 page（立即），被升级方按 ticket 次日处理 → MTTR 拉长，"
            "机制被绕过（以后直接叫 leader）" if mismatch else "对齐：升级语义一致，协作顺畅")

if __name__ == "__main__":
    teamB = {"response_tiers": {"T0": "page-7x24", "T1": "ticket-always",  # 未对齐
             "T2": "ticket"}, "alert_naming": COMMON_STANDARD["alert_naming"],
             "handoff_template": COMMON_STANDARD["handoff_template"],
             "escalation_semantics": COMMON_STANDARD["escalation_semantics"]}
    issues = alignment_check(teamB)
    print("对齐检查:", issues)
    assert any("响应分级" in i for i in issues)
    print("不对齐代价:", misalignment_incident(mismatch=True))
    # 口径：必须对齐=响应分级/升级语义/告警命名/交接格式（协同接口协议）；
    # 自治=轮换细节/补偿/工具；委员会制定+季度复审+灰度修订。
```

**追问**：1) 为什么「响应分级」是必须对齐的第一项？——跨团队升级的所有交互都基于「对方会多快响应」的期望——分级语义错位=所有升级交互的期望错位——它是协同的「最底层协议」（类似网络协议的传输层，错了全错）。2) 「委员会制定」怎么避免变成官僚流程？（提示：委员会季度复审（有固定节奏）+ 修订提案的门槛低（任何团队可提）+ 默认通过时限（提案 2 周无反对即生效）——官僚化的反面是「提案成本高+决策慢」——流程设计要「提案易、否决难」而非相反）3) 公共标准与团队自治的「边界」随业务演进会漂移，怎么管理？（提示：边界本身要定期审视（新增跨团队场景→需要新的公共标准项）——边界的演化也是委员会职责（季度复审的一部分）——边界清单是活的，不是一次定死）

## 背诵要点
1. 必须对齐四项：响应分级语义/升级链语义/告警命名/交接模板——协同的「接口协议」，错位即失效。
2. 可自治项：轮换细节/补偿方式/排班工具——不影响协同接口的内部实现留给团队。
3. 委员会制定+季度复审+灰度修订（提案易、否决难）；不对齐的代价 = 升级期望错位 → 机制被绕过。

## 复盘追问
1. 公共标准定了但「新团队加入时不知道有标准」（标准没传到），怎么防？（提示：新团队 onboarding 清单包含「值班公共标准确认」（Q149 新人就绪清单扩展到团队级）+ 标准文档的权威入口唯一（wiki 里只放指针，正文在值班平台）——标准的「可发现性」与内容同等重要）
2. 5 个团队中 2 个「拒绝对齐」（各自理由充分），公共标准怎么落地？（提示：分级推进——先对齐 3 个团队（跨这 3 团队的协同立即受益）+ 2 个不齐团队标记「协同降级」（与其协作时显式确认语义）+ 数据积累（不对齐团队的协同事故记录）作为后续对齐的论据——半数对齐优于全员不对齐，渐进收敛）
