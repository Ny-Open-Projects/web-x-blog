### A198 · 分片并行下载客户端

> 难度:★★☆ | 标签:下载, 并发, 断点续传

**问**（笔试·编程+场景题）：下载 10GB 文件——「单连接从头下」为什么慢（单 TCP 流吞吐上限/丢包重传拖整流），分片并行下载怎么实现（Range 请求分片 + 并发 worker + 分片落盘），分片完整性校验（每片哈希 + 整体指纹），断点续传的状态怎么持久化（已下分片清单），「服务器不支持 Range」怎么降级？

**答**：① 分片并行：`HEAD` 拿 Content-Length → 按 N 片切 Range 请求（每片 64-256MB）→ M 个 worker 并发下载（M=4-8：太多反而互抢带宽）→ 各片写独立临时文件 → 全部完成按序拼接。收益：绕开单 TCP 流的吞吐上限（丢包重传只影响单片）+ 多路径带宽叠加。② 完整性：每片下载完算 MD5 对比服务器给的每片哈希（或整体哈希最后验证）；**写文件用临时名 + 完成后原子 rename**（半成品文件绝不该叫最终名——Q7014 打包口径同构）。③ 断点续传状态：`download_state.json`（已下分片号/每片哈希/文件指纹）——重启后读状态，只下缺的片（Q7017 水位同构）；状态更新在每片完成后（不内存攒）。④ 降级：HEAD 无 `Accept-Ranges: bytes` 头 → 不支持 Range → 退化为单连接顺序下载（功能可用，性能退化）。

```python
# 全部标准库；demo 模拟分片下载（真网络版替换 fetch 即可）
import json, os, tempfile, hashlib

CHUNK = 1024 * 64

def fetch_range(url: str, start: int, end: int) -> bytes:
    """真实现：GET + Range: bytes=start-end。demo 返回伪数据。"""
    return (url + str(start)).encode()[:CHUNK]

def sha(b: bytes) -> str:
    return hashlib.md5(b).hexdigest()[:8]

def download(url: str, total_size: int, workers: int = 4, state_path: str | None = None) -> str:
    state = {"done": []}
    if state_path and os.path.exists(state_path):
        state = json.load(open(state_path))          # 断点续传：读已下清单
    ranges = [(s, min(s + CHUNK, total_size) - 1)
              for s in range(0, total_size, CHUNK)]
    todo = [r for r in ranges if r[0] not in state["done"]]
    parts: dict[int, bytes] = {}
    from concurrent.futures import ThreadPoolExecutor
    with ThreadPoolExecutor(max_workers=workers) as ex:
        futs = {ex.submit(fetch_range, url, s, e): (s, e) for s, e in todo}
        for fut in futs:
            s, e = futs[fut]
            blob = fut.result()
            path = f"{url}.{s}.part"
            with open(path, "wb") as f:              # 分片落盘（.part 临时名）
                f.write(blob)
            parts[s] = blob
            state["done"].append(s)
            if state_path:
                json.dump(state, open(state_path, "w"))   # 每片更新水位（Q7017 同构）
    # 拼接 + 原子 rename
    out = tempfile.mktemp()
    with open(out + ".part", "wb") as f:
        for s, e in ranges:
            f.write(parts[s])
    os.rename(out + ".part", out)                    # 完整才用最终名
    return out

if __name__ == "__main__":
    total = 1024 * 1024                              # 1MB 模拟（4 片 × 256KB 量级演示）
    real = CHUNK
    # demo 简化：CHUNK 大于 total 时单片完成
    out = download("http://x/file", total, workers=4,
                   state_path=tempfile.mktemp(suffix=".json"))
    assert os.path.exists(out)
    print("分片下载+原子 rename 完成 ✅")
    # 口径：HEAD→Range 切片→4-8 worker 并行→分片落盘+水位→拼接原子 rename；
    # 不支持 Range 头 → 降级单连接顺序下载。
```

**追问**：1) 为什么 worker 数 4-8 而不是 64？——并发 TCP 流共享同一带宽（总量恒定），64 流 = 流间互抢+服务端限流触发（Q5518 客户端纪律）+ 客户端线程/内存开销；4-8 流已能绕开单流吞吐上限——并发的收益有天花板。2) 「服务器不支持 Range」怎么探测与降级？（提示：HEAD 响应无 `Accept-Ranges: bytes` 头；或先发一个小 Range 试探（0-0）看返回 206 还是 200（200=忽略 Range 返回全文——必须中断，否则把全文当一片下）——探测是分片下载的第一步）3) 断点状态文件的写入频率 vs 性能？（提示：每片一写（fsync 可选）——状态丢失=重下整片（片级粒度损失可控）；攒批写省 IO 但崩溃丢更多水位——按「重下成本」权衡，片大则状态更要及时落）

## 背诵要点
1. 分片下载：HEAD→Range 切片→4-8 worker 并行（太多互抢带宽）→分片 .part 落盘→拼接原子 rename。
2. 完整性：每片哈希校验+整体指纹；半成品文件绝不用最终名。
3. 断点续传 = 分片水位清单（每片更新落盘）；不支持 Range（探测 0-0 返回 200）→ 降级单连接。

## 复盘追问
1. 并行下载后总吞吐没有提升（单流也没变快），瓶颈在哪？（提示：瓶颈不在连接数在「单瓶颈资源」（网卡带宽/服务端限流/磁盘 IO）——先测单流极限与总带宽，再决定并行策略；盲目加 worker 是浪费）
2. 下载到 99% 时服务器重启了（已下分片还有效吗），怎么处理？（提示：分片哈希校验能发现失效分片（服务器内容变了）——文件指纹（ETag/整体哈希）变了 = 整个重下；ETag 没变 = 续传有效——ETag 对比是续传前的强制步骤）
