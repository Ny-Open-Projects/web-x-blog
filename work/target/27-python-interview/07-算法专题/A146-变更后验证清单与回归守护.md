### A146 · 变更后验证清单

> 难度:★★☆ | 标签:发布验证, 回归守护, 场景题

**问**（笔试·场景题）：「部署完成」和「发布成功」的区别是什么——变更后验证清单要验什么（功能冒烟/指标护栏/依赖健康/业务探针），验证的自动化程度怎么定（全自动 vs 人工点检的分工），「验证通过但 2 小时后炸了」的潜伏型失败怎么防（观察窗与延迟指标），验证失败的自动回滚阈值怎么定才不误伤？

**答**：① 「部署完成 = 代码在新实例上跑起来」；「发布成功 = 部署完成 + 验证清单全绿 + 观察窗度过」。验证清单四层：**功能冒烟**（核心路径探针自动跑，Q7019 合成监控）、**指标护栏**（错误率/P99 对比基线，Q7013）、**依赖健康**（新版本连的 DB/缓存/队列都正常——依赖配置错误是发布事故高发）、**业务探针**（下单成功率等业务指标——技术全绿业务跌的形态，Q7013 三组指标）。② 自动化分工：全自动（探针/护栏/依赖检查——确定性规则）；人工点检（视觉效果/新功能的业务合理性——机器判不了的）——点检项要**限时**（15 分钟内完成，超时自动放行灰度 10% 而非无限等待）。③ 潜伏型失败：缓存在新版本下逐渐过期（2 小时后命中率崩）、数据积累触发边界（行数过千才崩）、上游版本协同发布（两小时后对方也发了）——防法：**观察窗**（发布后 1-2 小时保持增强监控频率）+ 延迟指标进清单（缓存命中率/队列积压这类「慢性病」指标）。④ 回滚阈值不误伤：同 Q7013——最小样本量 + 连续窗口 + σ 判定；发布本身造成的「预期抖动」（实例重启连接重建）要排除在判定外（发布窗口内的基线漂移补偿）。

```python
# 全部标准库；demo 实现「验证清单执行器 + 观察窗判定」
import time, statistics

CHECKLIST = [
    ("smoke", "auto", lambda: True),                       # 核心路径探针
    ("guardrail", "auto", lambda: (0.003, 0.15)),          # (错误率, P99)
    ("deps", "auto", lambda: {"db": True, "cache": True, "mq": True}),
    ("business", "auto", lambda: {"order_success": 0.995}),
    ("visual", "manual", None),                            # 人工点检：限时
]

class PostReleaseVerify:
    def __init__(self, base_err: float = 0.005, window_min: int = 90):
        self.base_err = base_err
        self.window = window_min
        self.samples: list[float] = []
    def run_checklist(self) -> dict:
        results = {}
        for name, mode, fn in CHECKLIST:
            if mode == "auto":
                results[name] = "pass" if fn() else "FAIL"
            else:
                results[name] = "manual-pending(限时 15min)"
        return results
    def sample(self, err_rate: float):
        self.samples.append(err_rate)
    def verdict(self, n_just_deployed_restart: bool) -> str:
        """观察窗判定：排除发布重启抖动，连续超阈才 FAIL。"""
        if n_just_deployed_restart and len(self.samples) <= 5:
            return "warming-up（重启窗口，基线漂移补偿中）"
        recent = self.samples[-5:]
        if len(recent) < 5:
            return f"observing {len(recent)}/{self.window}min"
        exceed = statistics.mean(recent) > self.base_err * 3
        return "ROLLBACK" if exceed else "healthy"

if __name__ == "__main__":
    v = PostReleaseVerify()
    print("验证清单:", v.run_checklist())
    # 重启窗口：前 5 个样本不计入判定（连接重建抖动）
    for i in range(5):
        v.sample(0.02)                          # 重启期错误率高
    print("重启窗口:", v.verdict(n_just_deployed_restart=True))
    v.sample(0.004); v.sample(0.005); v.sample(0.004)
    print("观察窗:", v.verdict(n_just_deployed_restart=False))
    for _ in range(5):
        v.sample(0.03)                          # 持续劣化
    print("判定:", v.verdict(n_just_deployed_restart=False))
    assert "ROLLBACK" in v.verdict(n_just_deployed_restart=False)
    print("验证+观察窗+补偿基线+连续窗口判定 全链路 ✅")
    # 口径：部署完成≠发布成功；验证四层+观察窗 1-2h+重启抖动补偿；潜伏失败靠慢性病指标。
```

**追问**：1) 「依赖健康」为什么单列一层？——新版本常带**新依赖或新配置**（新缓存键/新队列），旧依赖健康不代表新链路健康；发布事故的高频根因是「新版本指向了错误配置的依赖」——清单显式检查新版本实际连上的依赖（连接串/配置版本）。2) 观察窗 1-2 小时的依据？（提示：覆盖缓存过期周期（常见 1h TTL）+ 一次完整业务周期（如订单结算流）——潜伏型失败的显形时间；窗口太长占用人力，太短漏慢性病）3) 人工点检超时自动放行灰度 10% 的逻辑？（提示：验证阻塞主流量是更大的业务损失；自动放小量 + 点检继续（发现问题的半径已被 10% 限制）——验证体系的原则是「验证失败降级而非卡死」）

## 背诵要点
1. 部署完成 ≠ 发布成功；验证四层：功能冒烟/指标护栏/依赖健康/业务探针，人工点检限时放行。
2. 潜伏型失败防法：观察窗 1-2h 增强监控 + 慢性病指标（缓存命中率/队列积压）进清单。
3. 回滚判定：最小样本 + 连续窗口 + 重启抖动基线补偿——不误伤也不漏杀。

## 复盘追问
1. 验证全绿但客户报错（特定机型/特定参数），清单为什么没拦住？（提示：清单覆盖「典型路径」——长尾参数/机型是盲区；对策：客户报错样本回灌进验证清单（新的探针用例），清单是活的测试集不是固定模板）
2. 每次发布都要 15 分钟人工点检，发布频率高了之后成为瓶颈——怎么演进？（提示：点检项逐个自动化化（视觉用截图对比、业务合理性用业务探针）——人工点检是过渡态，自动化率是发布效率的 KPI）
