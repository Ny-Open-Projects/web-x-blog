### A109 · 优雅停机场景题：SIGTERM 到连接排空

> 难度:★★☆ | 标签:停机, K8s, 场景题

**问**（笔试·场景题）：K8s 滚动更新时，Pod 被杀的瞬间用户请求会失败吗？写出从 SIGTERM 到安全退出的完整时序（含 preStop、readiness、drain），并实现一个 asyncio 服务的优雅停机骨架。

**答**：不做处理就会失败。完整时序：① K8s 同时做两件事：Endpoint 摘除该 Pod（readiness 生效）+ 向容器发 SIGTERM 并启动 preStop；② **摘除≠断流**：其他节点/ingress 的连接缓存可能还在发请求（最长一个同步周期），所以 preStop 里先 `sleep 5s` 等摘除传播，再开始 drain；③ **drain**：服务停止 accept 新请求，已收请求继续处理完（含超时上限），在途请求数归零或有界退出；④ 超过 `terminationGracePeriodSeconds`（默认 30s）直接 SIGKILL——所以 drain 上限必须小于它。两个经典坑：只 sleep 不 drain（请求照样断）；进程不处理 SIGTERM 直接被 SIGKILL（3 秒强杀，最差）。

```python
import asyncio, signal, os

class App:
    def __init__(self):
        self.draining = False
        self.inflight = 0
        self.server: asyncio.Server | None = None

    async def handle(self, reader, writer):
        if self.draining:                       # drain 中拒绝新请求（连接已被 stop accept 挡住，双保险）
            writer.close()
            return
        self.inflight += 1
        try:
            data = await asyncio.wait_for(reader.read(1024), timeout=5)
            await asyncio.sleep(0.05)           # 模拟业务处理
            writer.write(b"ok:" + data)
            await writer.drain()
        finally:
            self.inflight -= 1
            writer.close()

    async def shutdown(self):
        self.draining = True
        self.server.close()                     # 停止 accept 新连接
        await self.server.wait_closed()
        deadline = asyncio.get_event_loop().time() + 20   # drain 上限 < grace 30s
        while self.inflight > 0 and asyncio.get_event_loop().time() < deadline:
            await asyncio.sleep(0.05)           # 等在途请求处理完
        print(f"drained, inflight={self.inflight}")

async def main():
    app = App()
    app.server = await asyncio.start_server(app.handle, "127.0.0.1", 8080)
    stop = asyncio.Event()
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGTERM, signal.SIGINT):
        loop.add_signal_handler(sig, stop.set)  # 信号 → 事件，进入统一停机路径
    await stop.wait()
    await app.shutdown()                        # SIGTERM 后：不再 accept、排空在途

if __name__ == "__main__":
    # 真实 K8s 时序：preStop: sleep 5（等 Endpoint 摘除传播）→ SIGTERM → 本骨架 drain → 退出
    asyncio.run(main()) if os.environ.get("DEMO") else print("骨架就绪；DEMO=1 可起服务实测")
```

**追问**：1) 为什么 preStop 要 sleep？——SIGTERM 与「LB/Endpoint 完全摘除」是并行的，摘除有传播延迟，不 sleep 的话 drain 开始时仍会收到新请求，只能靠拒绝连接兜底（体验差）。2) 长连接（WebSocket）怎么排空？——HTTP 请求能 drain，WS 要发「服务下线」帧让客户端主动迁移，并把等待时间计入 grace 预算；见 Q6005 粘性问题。3) 多进程 gunicorn/uvicorn 下谁负责？——master 收 SIGTERM 后向 worker 逐个转发并 wait，grace 由 master 统一控制，worker 内部同样实现 drain。

## 背诵要点
1. 停机四步：preStop sleep（等摘除传播）→ 停 accept → drain 在途（上限 < terminationGracePeriod）→ 退出。
2. 不处理 SIGTERM = 被 SIGKILL 强杀 = 最差结局；drain 不做 = 请求直接断。
3. 长 WS 连接靠「下线通知帧 + 客户端迁移」，drain 排不掉。
