### A260 · 消息队列积压治理

> 难度:★★★★ | 标签:消息队列, 积压, 分区倾斜, 死信, 削峰

**问**（笔试·场景题）：大促次日凌晨，订单履约队列积压 300 万条，P99 履约延迟 2 小时，值班同学的第一反应是「加消费者」。要求：① 给出**病因判定**方法——如何用 1 分钟粒度的 `(生产速率, 消费速率, 总 lag, 各分区 lag, 单条处理耗时 p95, 在册/存活消费者数)` 区分「生产突增 / 消费变慢 / 分区倾斜 / 毒消息卡死 / 消费组整体失效 / 消费者假活」；② 解释**为什么加消费者经常无效**，并给出「有效并行度」的算法；③ 积压之后的**死信重放**怎么限速，才能不把刚恢复的下游二次打挂；④ 削峰该在入口做还是消费端做，入口限流与「先收下来慢慢消化」的取舍是什么；⑤ 告警该看 lag 绝对值还是别的指标。请说清与 Q6073（异步队列的容量账与降级水位）、Q7070（积压该看排空时长而不是深度）、Q6626（数据库任务队列 SKIP LOCKED 的吞吐）、Q1246（死信队列与退避重试队列）、A250（大促降级阶梯）的分工——那些卡给的是「结论与水位」，本题要给的是「可计算的判定树」。

**答**：① 分工：Q6073 算的是「**容量账**」（Little's Law：并发 = 到达率 × 停留时间，降级水位设在哪）；Q6626 是**存储型队列**（DB 表 + `SKIP LOCKED`）的吞吐建模；Q1246 是死信队列的**结构**（重试队列 + TTL + 最大次数）；A250 是**降级动作的编排**。本题是**诊断层**：给定一组观测，判断「病因是哪一类」，因为不同病因的处置完全相反——生产突增该扩消费或限入口，消费变慢该查下游，分区倾斜扩消费者纯属浪费，毒消息加人只会让所有消费者一起卡在同一条上。**先分类，再动手**，这是积压治理的第一原则。Q7070 已经点破「排空时长才是度量、只加消费者不够」，本题不重复那条结论，增量在于把它拆成**可计算的判据**：四道吞吐天花板、六种病因的形态学特征、以及重放/合批的量化。② 判定的关键是把「速率的差」与「速率的形」分开看：`lag` 的**一阶差分**才是净流入（`produced - consumed`），累计 lag 只能告诉你「欠了多少」，不能告诉你「还在不在恶化」。形态上有三种典型：**线性上升**（净流入持续为正）、**阶跃后走平**（一次性生产高峰已过，只需排空）、**锯齿**（消费能力周期性掉底，通常是定时任务/GC/下游抖动）。分区维度是第二个判据：`max(part_lag)/sum(part_lag) > 50%` 基本可以断定顺序键热点（比如按 `seller_id` 分区，某个大卖家的订单全在一个分区）；单分区位点不动而其他分区正常 = 毒消息；全部分区位点不动 = 消费组失效（鉴权过期、被踢出组、网络分区）。第三个判据是「在册 vs 存活」：`consumers` 是分配了分区的实例数，`alive` 是位点真在推进的实例数，两者不等就是假活——这类故障最迷惑人，因为监控上「消费者在线」，实际消费速率是 0。③ 为什么加消费者无效，有四道天花板，按命中概率排序：**(a) 分区数**——并行度上限就是分区数，16 个消费者抢 8 个分区，多出来的 8 个纯空转；**(b) 顺序键热点**——就算有 64 个分区，只要某个 key 的消息全在一个分区，这个分区的吞吐就锁死在单线程；**(c) 下游容量**——消费者不是瓶颈时，加人只是把更多并发压到数据库/下游 API 上，把「积压」换成「超时 + 重试放大」，总吞吐反而下降（这是最危险的，因为指标会先好看几分钟然后崩）；**(d) 单条耗时**——吞吐 ≈ 并行度 × 1000 / 单条毫秒数，单条从 20ms 涨到 200ms，扩 10 倍消费者才勉强打平。所以「有效并行度 = min(消费者数, 分区数)」，而「有效吞吐 = 有效并行度 × 并发度 × 1000 / p95」，两个都要算完再决定加不加。④ 毒消息的识别特征是「重启后仍卡在同一个 offset」，消费逻辑对同一条消息必然抛异常，`max_retries` 用尽后进死信，位点才继续。这里要区分两类异常：**业务异常**（金额为负、状态不合法）必须立刻死信 + 告警，重试一万次也不会成功；**系统异常**（下游超时、连接断开）才值得退避重试（A120 的白名单）。把业务异常当系统异常重试，就是「一条脏数据卡死整个分区几小时」的标准剧本。⑤ 死信重放的限速不能拍脑袋：`rate = min(下游余量 × 安全系数, 消费端能力)`。下游余量 = 下游当前 QPS 上限 - 正常业务已占用；安全系数取 0.2~0.3（重放是额外负载，且下游刚恢复时余量估计往往偏乐观）；消费端能力 = 并发 × 1000 / 单条毫秒。重放还必须满足三条：**幂等**（重放的消息可能已经被部分处理过）、**按 key 保序**（同一订单的多条消息不能乱序）、**可中断**（随时能停，不能一开就跑到底）。⑥ 削峰的位置选择：**入口限流**牺牲的是「新请求的可用性」，**队列缓冲**牺牲的是「延迟 + 丢消息风险」。队列不是无限缓冲——它有 retention（比如 72 小时），积压超过 retention 就是**数据丢失**，不是延迟；而且积压期间所有消息都在超时边缘，下游一旦抖动就会大面积重试。所以正确顺序是：**先限入口保住 SLO → 再扩有效并行度 → 再合批/降级 → 最后才是丢消息**（丢也要丢可丢的：日志、埋点、推荐曝光，绝不丢订单与支付）。⑦ 告警口径：`lag` 绝对值在不同流量下不可比，1000 条在 1000/s 的队列里是 1 秒，在 10/s 的队列里是 100 秒。应该告警的是**预计排空时间**（`lag / (consume - produce)`，净速率 ≤ 0 时直接判死）和 **retention 剩余时间**（还有多久会开始丢消息）。本题代码里把这两个都算了出来：300 万积压、消费 1200/s、生产 1000/s → 15000 秒 ≈ 4.2 小时；一旦生产追平消费，返回值直接是 `None`（永远排不空），这时候加多少消费者都没用，必须动入口。⑧ 最后一条经验：积压治理要**先止血再清理**。止血 = 让 `produced <= consumed`（限流/降级/暂停非核心生产），清理 = 把存量吃掉。顺序反了就是「一边灌一边舀」，永远排不空——这是大促复盘里出现频率最高的一句结论。

```python
# 全部标准库；积压病因判定 + 排空时间 + 扩容上限 + 死信重放限速 + 合批削峰
from dataclasses import dataclass, field


@dataclass
class Window:
    """一个采样窗口（建议 1 分钟）的原始观测，全部来自 broker 与消费端埋点。"""
    minute: int
    produced: int                 # 本窗口写入条数
    consumed: int                 # 本窗口成功 ack 条数
    lag: int                      # 窗口末总积压
    part_lags: list = field(default_factory=list)
    p95_ms: float = 0.0           # 单条处理耗时 p95
    consumers: int = 0            # 已分配的分区消费者数（含假活）
    alive: int = 0                # 近期有心跳且位点在动的消费者数


class Diagnoser:
    def __init__(self, partitions, base_produce, base_consume, base_p95):
        if partitions <= 0:
            raise ValueError("分区数必须 > 0")
        self.partitions = partitions
        self.bp, self.bc, self.b95 = base_produce, base_consume, base_p95

    # ---------- 病因判定：先排除「一条都消费不动」，再看是量的问题还是速的问题 ----------
    def classify(self, w):
        notes = []
        if w.lag > 0 and w.consumed == 0 and w.consumers > 0:
            if w.alive < w.consumers:
                return "ZOMBIE_CONSUMER", ["消费者在册但位点不动：假活/被限流/鉴权失败"]
            hot = [i for i, l in enumerate(w.part_lags) if l > 0]
            if len(hot) == 1 and len(w.part_lags) > 1:
                return "POISON_PARTITION", ["单分区位点卡死：毒消息或该分区消费者挂死"]
            return "CONSUMER_STALL", ["全部位点不动：消费组整体失效（连不上/被踢/无权限）"]

        if w.produced >= 1.5 * self.bp and w.consumed >= 0.8 * self.bc:
            notes.append("生产速率是基线 %.1f 倍，消费未同步下降" % (w.produced / self.bp))
            if w.p95_ms > 1.3 * self.b95:
                notes.append("但单条耗时也在涨，注意下游已被拖慢")
            return "PRODUCE_SPIKE", notes

        slow = w.p95_ms >= 1.5 * self.b95 or w.consumed <= 0.7 * self.bc
        if slow:
            notes.append("消费速率 %.0f/s（基线 %.0f/s），p95 %.0fms（基线 %.0fms）"
                         % (w.consumed, self.bc, w.p95_ms, self.b95))
            if w.p95_ms >= 1.5 * self.b95:
                notes.append("单条变慢是主因：查下游 RT/锁/大事务，而不是加消费者")
            else:
                notes.append("单条不变但吞吐下降：查消费者线程数/批大小/被限流")
            return "SLOW_CONSUMER", notes

        total = sum(w.part_lags) or 1
        share = max(w.part_lags) / total if w.part_lags else 0.0
        if self.partitions > 1 and share > 0.5 and w.lag > 0:
            notes.append("最热分区占积压 %.0f%%：顺序键热点，扩消费者无效" % (share * 100))
            return "SKEWED_PARTITION", notes

        if w.consumers > self.partitions:
            notes.append("消费者 %d > 分区 %d：多出来的实例空转"
                         % (w.consumers, self.partitions))
            return "PARTITION_CAP", notes
        return "BALANCED", ["生产与消费基本匹配，积压可能只是历史尾巴"]

    # ---------- 排空时间：净消费速率 <= 0 时永远排不空 ----------
    @staticmethod
    def drain_seconds(lag, produce_ps, consume_ps):
        net = consume_ps - produce_ps
        if net <= 0:
            return None
        return lag / net

    # ---------- 扩容上限：并行度受分区数约束，吞吐还受单条耗时约束 ----------
    def effective_consumers(self, consumers):
        return min(consumers, self.partitions)

    def max_throughput(self, consumers, per_msg_ms, concurrency_per_consumer=1):
        eff = self.effective_consumers(consumers)
        return eff * concurrency_per_consumer * 1000.0 / per_msg_ms

    # ---------- 死信重放：速率由下游余量决定，不是由积压量决定 ----------
    @staticmethod
    def replay_plan(dead_count, downstream_qps, headroom=0.3,
                    per_msg_ms=5.0, concurrency=8):
        budget = downstream_qps * headroom
        capability = concurrency * 1000.0 / per_msg_ms
        rate = max(1.0, min(budget, capability))
        return {
            "rate_per_sec": rate,
            "eta_sec": dead_count / rate,
            "bounded_by": "downstream" if budget < capability else "consumer",
        }

    # ---------- 合批：把 N 次单条写压成 1 次，瓶颈在 RTT 时收益近似线性 ----------
    @staticmethod
    def batch_gain(msgs_per_sec, batch_size, rtt_ms, work_ms_per_msg):
        single = msgs_per_sec * (rtt_ms + work_ms_per_msg) / 1000.0
        batched = (msgs_per_sec / batch_size) * (rtt_ms + batch_size * work_ms_per_msg) / 1000.0
        return single / batched


if __name__ == "__main__":
    d = Diagnoser(partitions=8, base_produce=1000, base_consume=1000, base_p95=50)

    # 1) 生产突增：消费侧一切正常，只是进来的量翻了三倍
    w = Window(1, produced=3200, consumed=1000, lag=220000,
               part_lags=[27000] * 8, p95_ms=52, consumers=8, alive=8)
    code, notes = d.classify(w)
    assert code == "PRODUCE_SPIKE", (code, notes)
    print("判定 1: %s —— %s ✅" % (code, notes[0]))

    # 2) 消费变慢：量没变，单条耗时从 50ms 涨到 400ms（下游被拖慢）
    w = Window(2, produced=1000, consumed=380, lag=300000,
               part_lags=[37000] * 8, p95_ms=420, consumers=8, alive=8)
    code, notes = d.classify(w)
    assert code == "SLOW_CONSUMER", (code, notes)
    print("判定 2: %s —— %s ✅" % (code, notes[0]))

    # 3) 分区倾斜：8 个分区里 1 个吃掉 90% 积压（顺序键热点）
    w = Window(3, produced=1000, consumed=990, lag=180000,
               part_lags=[1000, 900, 800, 700, 1000, 900, 800, 174000],
               p95_ms=55, consumers=8, alive=8)
    code, notes = d.classify(w)
    assert code == "SKEWED_PARTITION", (code, notes)
    print("判定 3: %s —— %s ✅" % (code, notes[0]))

    # 4) 毒消息 vs 消费组整体失效：两者都是 consumed=0，但分区形态不同
    poison = Window(4, produced=900, consumed=0, lag=90000,
                    part_lags=[0, 0, 0, 90000], p95_ms=0, consumers=4, alive=4)
    stall = Window(4, produced=900, consumed=0, lag=90000,
                   part_lags=[22000] * 4, p95_ms=0, consumers=4, alive=4)
    assert d.classify(poison)[0] == "POISON_PARTITION"
    assert d.classify(stall)[0] == "CONSUMER_STALL"
    print("判定 4: 单分区卡死=POISON_PARTITION，全分区卡死=CONSUMER_STALL ✅")

    # 5) 假活：消费者在册但心跳/位点不前进
    w = Window(5, produced=900, consumed=0, lag=90000,
               part_lags=[11000] * 4, p95_ms=0, consumers=4, alive=0)
    assert d.classify(w)[0] == "ZOMBIE_CONSUMER"
    print("判定 5: ZOMBIE_CONSUMER —— 在册但位点不动（扩容只会增加空转实例）✅")

    # 6) 扩容上限：16 个消费者 / 8 个分区，有效并行度仍是 8
    assert d.effective_consumers(16) == 8 and d.effective_consumers(3) == 3
    tp_8 = d.max_throughput(8, per_msg_ms=20)
    tp_16 = d.max_throughput(16, per_msg_ms=20)
    assert tp_8 == tp_16 == 400.0
    print("扩容: 16 消费者 / 8 分区，吞吐仍为 %.0f/s（被分区数与 20ms/条 夹住）✅" % tp_16)

    # 7) 排空时间：300 万积压、消费 1200/s、生产 1000/s -> 4.17 小时；生产追平则永不排空
    assert d.drain_seconds(3_000_000, 1000, 1200) == 15000.0
    assert d.drain_seconds(3_000_000, 1200, 1200) is None
    print("排空: 净消费 200/s -> %.1f 小时；生产=消费 -> 永远排不空 ✅"
          % (15000 / 3600))

    # 8) 死信重放：受下游余量约束；把 5ms/条 改成 200ms/条 时受消费能力约束
    p1 = d.replay_plan(500_000, downstream_qps=3000)
    p2 = d.replay_plan(500_000, downstream_qps=3000, per_msg_ms=200)
    assert p1["bounded_by"] == "downstream" and abs(p1["rate_per_sec"] - 900) < 1e-9
    assert p2["bounded_by"] == "consumer" and abs(p2["rate_per_sec"] - 40) < 1e-9
    print("重放: 3000 QPS 余量 30%% -> 900/s（约 %.0f 分钟）；慢消息退化为 40/s ✅"
          % (p1["eta_sec"] / 60))

    # 9) 合批削峰：1000 条/s、RTT 2ms、单条 0.2ms -> 批 100 收益约 10 倍
    gain = d.batch_gain(1000, 100, rtt_ms=2.0, work_ms_per_msg=0.2)
    assert 9.5 < gain <= 10.5, gain
    print("合批: 批大小 100 时理论收益 %.1f 倍（瓶颈从 RTT 转回 CPU）✅" % gain)
```

**追问**：1) 积压时「先扩消费者」为什么会把故障放大？—— 因为积压往往意味着下游已经慢了（`p95` 上升），此时加消费者等于给已经过载的下游再加并发：连接池被打满 → 超时率上升 → 客户端重试 → 有效负载翻倍 → 吞吐进一步下降。这是典型的正反馈。正确顺序是先看 `p95` 与下游 RT：若是「消费变慢」，第一步是**降并发/限速**，甚至主动缩减消费者，等下游恢复再放量。只有判定为「生产突增且消费侧健康」时，扩消费者才是正解，而且要先确认分区数与单条耗时允许。2) 分区数能不能在线加？—— 技术上多数 MQ 支持增加分区，但**语义会变**：按 key 哈希的分区映射从 `hash % N` 变成 `hash % (N+k)`，同一个 key 的历史消息与新消息可能落在不同分区，**顺序保证被打破**。所以顺序敏感的业务要么预留足够分区（一次性开够，比如 128），要么用「逻辑分区 + 消费端按 key 再排序」。这也是「扩容上限」这条规则在架构期就要想清楚的原因。3) 积压 300 万条、retention 只剩 6 小时，怎么排优先级？—— 先算「会不会丢」：`retention 剩余时间 < 排空时间` 就意味着有消息会在被消费前过期。此时优先级变成：**保数据**（把即将过期的消息转存/转发到备份队列，或临时调大 retention）> **保核心**（限流非核心生产、把消费并行度全部让给订单）> **保延迟**（牺牲次要业务的时效）。注意「转存」本身也会消耗带宽与下游容量，属于用存储换时间，必须和重放限速一起算，别把「救火」变成「二次事故」。

## 背诵要点
1. 先分类再动手：生产突增 / 消费变慢 / 分区倾斜 / 毒消息 / 消费组失效 / 消费者假活；判据是「速率差 + 分区 lag 形态 + 在册 vs 存活」。
2. 扩容有四道天花板：分区数、顺序键热点、下游容量、单条耗时；有效吞吐 = `min(消费者, 分区) × 并发 × 1000/p95`。
3. 告警看预计排空时间 `lag/(c-p)`（净速率 ≤0 即永远排不空）与 retention 剩余时间；死信重放速率 = `min(下游余量×0.2~0.3, 消费端能力)`。

## 复盘追问
1. 加了一倍消费者，lag 短暂下降后创新高，最可能是什么？（提示：下游被打满 → 超时 → 客户端重试放大；先看 p95 与重试率，正确动作是降并发而不是继续加人）
2. 顺序键热点把单个分区撑爆，除了拆 key 还有什么招？（提示：key 加盐打散（牺牲同 key 顺序）、消费端按 key 二次聚合、把大 key 业务拆独立 topic；在线加分区会改变 hash 映射，顺序不保）
