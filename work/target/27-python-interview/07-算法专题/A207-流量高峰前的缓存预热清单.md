### A207 · 缓存预热清单

> 难度:★★☆ | 标签:缓存预热, 大促, 自动化

**问**（笔试·编程+场景题）：大促开始前 1 小时要预热哪些缓存——预热清单怎么生成（TopN 商品/热点页/依赖数据——从历史流量预测），预热流量怎么控制（预热本身不能把源站打挂——限速），预热的「有效性验证」（预热完成后怎么确认缓存已就绪），「预热了没用的数据」（实际热点与预测不符）怎么动态修正？

**答**：① 清单生成：**历史 TopN**（去年同期/近 7 天热销 TopN 商品 + 活动页 + 配置数据——多来源合并去重）× **预热深度**（页面级/接口级/数据级分层——页面预热覆盖多接口但粒度粗）；「活动商品」单独清单（运营提报的活动商品——历史数据不包含新品）。② 预热限速：预热是「可控的自找流量」——限速在「源站剩余容量」内（源站 QPS 余量 × 50% 给预热），批量拉取 + 间隔控制；预热时间窗（高峰前 1 小时开始——太早会被 TTL 过期（预热完就过期=白预热），太晚来不及）。③ 有效性验证：预热完成后**抽样验证命中率**（预热清单抽样请求，确认缓存命中而非回源——预热脚本自己验证自己）+ 指标验证（缓存命中率曲线应提前抬升）。④ 动态修正：大促开始后实时监控「未预热命中」（回源请求的商品 ID 频次——TopN 预测遗漏的），动态补预热（发现即拉取）——预测不可能完美，修正机制兜底。

```python
# 全部标准库；demo 实现「预热清单生成 + 限速编排 + 有效性验证」
import time, collections

def build_list(hist_top: list[str], promo_items: list[str], depth: int = 50) -> list[str]:
    """清单 = 历史 TopN ∪ 活动商品（去重截断）。"""
    merged = list(dict.fromkeys(hist_top + promo_items))   # 去重保序
    return merged[:depth]

def preheat(items: list[str], source_spare_qps: float = 500,
            rate_per_item: float = 1.0, ttl_guard_s: float = 3600) -> dict:
    """限速编排：预热 QPS ≤ 源站余量 × 50%；时长 ≤ TTL 防白预热。"""
    qps = min(source_spare_qps * 0.5, 100)
    est_seconds = len(items) / qps
    return {"qps": qps, "est_seconds": round(est_seconds, 1),
            "ttl_ok": est_seconds + 300 < ttl_guard_s}   # 预热+缓冲 < TTL

def verify_hit(items: list[str], cache_get) -> dict:
    """有效性验证：抽样确认命中。"""
    sample = items[:: max(1, len(items) // 20)][:20]
    hits = sum(1 for i in sample if cache_get(i) is not None)
    return {"sampled": len(sample), "hit_rate": hits / max(len(sample), 1)}

class DynamicFixer:
    """动态修正：监控回源请求的 item 频次，遗漏热点补预热。"""
    def __init__(self, preheated: set):
        self.preheated = preheated
        self.miss_counter = collections.Counter()
    def observe_miss(self, item: str):
        if item not in self.preheated:
            self.miss_counter[item] += 1
    def fix_list(self, threshold: int = 50) -> list[str]:
        fix = [i for i, c in self.miss_counter.items() if c >= threshold]
        for i in fix:
            self.preheated.add(i)
            self.miss_counter.pop(i)
        return fix                                  # 补预热清单

if __name__ == "__main__":
    hist = [f"p{i}" for i in range(100, 200)]       # 历史 TopN
    promo = [f"p{i}" for i in range(150, 160)]      # 活动新品（与历史部分重叠）
    lst = build_list(hist, promo, depth=60)
    assert lst[0] == "p100" and "p159" in lst       # 去重保序+新品包含
    plan = preheat(lst)
    print(f"预热 {len(lst)} 项 @ {plan['qps']} QPS ≈ {plan['est_seconds']}s，TTL 合规: {plan['ttl_ok']}")
    assert plan["ttl_ok"]
    cache = {i: "data" for i in lst}                # 预热完成
    v = verify_hit(lst, cache.get)
    print("有效性验证:", v, "—— 命中率应 ≈1.0")
    assert v["hit_rate"] == 1.0
    fixer = DynamicFixer(set(lst))
    for _ in range(60): fixer.observe_miss("p999")  # 预测遗漏的热点
    print("动态修正:", fixer.fix_list(50))
    # 口径：清单=历史∪活动去重；限速=源站余量×50% 且时长<TTL；
    # 预热自验证命中率 + 实时回源监控动态修正——预测不完美靠修正兜底。
```

**追问**：1) 为什么预热时长要「< TTL」？——预热完到高峰开始的间隔若超过 TTL，预热数据已过期（白预热，高峰时照旧回源）——预热时间窗的约束是「预热完成时刻 → 高峰开始」必须小于缓存 TTL，或预热时刷新 TTL。2) 「预热 QPS ≤ 源站余量 50%」为什么只给一半？——预热期间还有正常流量（预热的源是源站/DB），余量的一半给预热、一半留给正常流量的波动——预热把「可控流量」用满余量而非打满（打满=自己制造故障，Q6020 预热风暴同源）。3) 「历史 TopN」在全新业务（无历史）场景怎么替代？（提示：运营提报 + 类比业务（相似活动的历史数据）+ 小流量试探（开始后动态修正为主的模式）——历史缺失时动态修正机制权重更高，预测权重降低）

## 背诵要点
1. 清单三来源合并：历史 TopN + 活动提报 + 配置数据，去重保序分深度——新品单独提报。
2. 预热限速：QPS ≤ 源站余量 × 50%，时间窗约束「预热完成 → 高峰开始」< TTL——预热本身不能成为故障源。
3. 有效性验证（抽样命中率自检）+ 实时回源监控动态修正（预测不完美，修正兜底）。

## 复盘追问
1. 预热把源站打挂了（预热风暴），复盘根因常见错误？（提示：限速没算「并发预热 worker 的总 QPS」（单 worker 限速 × N worker = 总量失控）——限速要在总量层做，不是单 worker 层；A101 的并发口径）
2. 大促命中率达标但「首屏加载仍慢」，缓存预热漏了什么？（提示：预热了数据缓存但没预热「页面级/CDN 级」缓存（静态资源/页面片段）——预热分层（数据/接口/页面/CDN）要与用户请求路径对齐，不是只预热数据库查询）
