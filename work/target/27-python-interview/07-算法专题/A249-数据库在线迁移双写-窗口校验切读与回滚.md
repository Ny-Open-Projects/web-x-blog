### A249 · 在线迁移双写方案

> 难度:★★★★★ | 标签:数据迁移, 双写, 对账, 灰度切读

**问**（笔试·场景题）：订单主表 8 亿行、平均 1KB（约 800GB），要从 MySQL 5.7 迁到新集群（同构，版本与硬件升级），要求用户无感、随时可回滚。请给出可直接执行的方案，重点回答五件事：① **双写窗口到底多长**——给出公式，并说明为什么大多数团队估短了；② **双写的顺序与失败语义**——先写新库还是先写旧库、新库失败要不要让用户请求失败、幂等怎么做；③ **校验口径**——全量怎么比、增量怎么比、差异怎么分类，为什么「只报不一致」不够用；④ **切读怎么灰度**——按什么维度切、每档的放量闸门是什么、影子双读放在哪一步；⑤ **回滚的决策树**——什么时候能秒回、什么时候回不去、停旧写该放在哪个时刻。Q1253 已给四阶段状态机、Q309 给了灰度双写、Q1254 给了校验方法，本题不重复清单，只算数字与判定。

**答**：① 与已有卡的分工：A108 讲的是「缓存与 DB 双写一致性」（先删缓存还是先写库），是同一份数据的两种投影；本题是**两份存储之间的整体搬迁**，双写是过渡手段而不是常态，所以关注点从「一致性的失败矩阵」换成「窗口、对账与可回滚」。Q1253 已给四阶段状态机、Q309 给了灰度双写、Q1254 给了校验方法，本题不重复清单，只算数字与判定。 ② 窗口公式：`T_dual = T_copy + T_catchup + n × T_verify`，三项分别是「搬存量 / 追平增量 / 验证正确」，任何一项估错都会让窗口失控。**T_copy** = 总字节 / 有效拷贝带宽（800GB ÷ 300MB/s ≈ 0.72h）。**T_catchup** = 拷贝期间堆积的 binlog 量 ÷（回放能力 − 写入速率）；关键是分母必须为正：写入峰值 2 万行/s 时，回放只有 8k/s 就永远追不平（数学上是无穷大），工程上表现为「延迟曲线一直涨、切读永远等不到」。经验门槛 **drain ≥ 1.3 × write**，留 30% 余量吸收大促尖峰。可行配置（4 万行/s）下 backlog = 2 万 × 0.72h，追平同样 0.72h。**T_verify** = 行数 ÷ 校验吞吐 × 轮数 = 8 亿 ÷ 5 万行/s × 2 ≈ 8.89h。合计双写 10.34h，加 5 档灰度（150 分钟）≈ 12.84h。**为什么总估短**：所有人都盯着「拷数据多快」，而实际 86% 的时间花在校验上——校验要全表扫、要跨集群比、要在业务高峰避让，还要在发现差异后重跑。 ③ 顺序与失败语义：**旧库是唯一权威，先旧后新**。旧库事务提交成功即对用户返回成功；新库写失败降级为「进补偿队列 + 打点」，绝不让用户请求失败——否则新库一抖动，故障面从「数据延迟」扩大到「下单不可用」。补偿有两种实现：本地消息表（同库同事务写入 outbox，异步投递，可重放）或 binlog 反查（按主键回查旧库当前值再 upsert）。幂等靠**版本号/更新时间戳**做条件更新（`UPDATE ... WHERE version < ?` / upsert 带版本比较），否则重试会把旧值盖回去，形成「数据越修越错」。 ④ 校验口径：分三层——**分片 checksum**（按主键区间算 `COUNT(*)` + `SUM(CRC32(整行))`）先粗筛，只对不一致的分片下钻逐行比；**增量比对**（消费 binlog，对每条变更在主库读快照、新库读现值，当场 diff）；**采样比对**（高峰期降频，按 1% 抽样保底）。差异必须分三类：**缺失**（新库没有这行 = 漏同步，重放即可）、**值不一致**（写错了/并发覆盖，要以旧库为准覆盖）、**陈旧**（新库还是上一版值 = 这次双写丢了）。没有同步位点信息时，第二类和第三类长得一模一样，只能统一报「不一致」；带了位点（记录每个 key 上次同步到的版本）才能区分，而两类修复动作完全不同——陈旧是重放这次变更，不一致是整行覆盖。这就是「只报不一致」不够用的原因：它无法指导修复，也无法判断是不是双写链路本身有 bug。 ⑤ 切读：按 `user_id` 哈希分桶（不是按流量比例随机，否则同一个用户会在新旧库之间来回跳，读到自己的旧数据）。档位 1% → 5% → 25% → 50% → 100%，每档最小观察窗 30 分钟且必须覆盖一次业务波峰。**影子双读在切读之前**：读请求同时打新旧库，新库结果只记录不返回，跑一周把差异率压到 1e-5 以下。每档放量闸门四件套：影子差异率、对账残差（必须为 0）、新库错误率、P99 涨幅。任何一项不过就停在当前档——闸门是「与」不是「或」。 ⑥ 回滚决策树：旧库仍可写时，回滚 = 改路由，秒级，这是唯一真正安全的回滚。一旦停掉旧写，回滚要反向同步新库增量回旧库，成本 ≈ 停写时长 × 写入量，而且反向同步本身会丢写（新库有的、旧库结构装不下的字段）。所以**停旧写必须放在最后**，且在停写前至少观察一个完整业务周期（日切 + 周结/月结对账），确认无残差、无补偿积压、无慢查询回潮。有残差时不许回滚——先修残差，否则回滚后两边都不对。 ⑦ 三个容易被忽略的细节：**迁移期间的双写放大**——写入 QPS 翻倍，新库还没建完索引就会被打爆，要先建索引再开双写；**DDL 与迁移并发**——迁移窗口内冻结表结构变更，否则 binlog 解析对不上列；**迁移工具自身的幂等**——中断重跑必须能从位点续传，不能从头再来（8 亿行重来一次就是一天）。

```python
# 全部标准库；迁移窗口计算 + 差异分级 + 切读闸门 + 回滚判定
from dataclasses import dataclass


@dataclass
class Capacity:
    """把「能不能搬完」算成数字，而不是拍脑袋定两周窗口。"""
    rows: int
    avg_row_bytes: int
    copy_mbps: float        # 全量拷贝有效吞吐（B/s，含压缩与并行）
    write_qps: float        # 业务写入峰值（行/s，双写期间照样进 binlog）
    drain_qps: float        # binlog 回放能力（行/s）
    verify_qps: float       # 单轮全量校验吞吐（行/s）
    safety: float = 1.3     # 回放能力必须超过写入的这个倍数


def plan(c, verify_passes=2, gray_minutes=150):
    total_bytes = c.rows * c.avg_row_bytes
    copy_h = total_bytes / c.copy_mbps / 3600
    backlog = c.write_qps * copy_h * 3600          # 拷贝期间新写入堆积的行数
    headroom = c.drain_qps - c.write_qps
    if c.drain_qps < c.write_qps * c.safety:
        catch_h = float("inf")                     # 回放追不上写入，窗口永远收不了口
    else:
        catch_h = backlog / headroom / 3600
    verify_h = c.rows / c.verify_qps / 3600 * verify_passes
    dual_h = copy_h + catch_h + verify_h
    return {"copy_h": round(copy_h, 2), "catchup_h": round(catch_h, 2),
            "verify_h": round(verify_h, 2), "dual_h": round(dual_h, 2),
            "total_h": round(dual_h + gray_minutes / 60, 2),
            "feasible": catch_h != float("inf"),
            "min_drain_qps": round(c.write_qps * c.safety, 0)}


def classify(old, new, changed):
    """差异分三类：缺失 / 值不一致 / 陈旧（旧库已更新而新库还是老值）。"""
    res = {"missing": [], "mismatch": [], "stale": [], "ok": 0}
    for k in changed:
        if k not in new:
            res["missing"].append(k)
        elif new[k] != old[k]:
            res["mismatch"].append(k)
        else:
            res["ok"] += 1
    return res


def classify_with_history(old, new, changed, last_synced):
    """带同步位点：新库值等于「上一版」说明这次双写丢了，属于陈旧不是不一致。"""
    res = {"missing": [], "mismatch": [], "stale": [], "ok": 0}
    for k in changed:
        if k not in new:
            res["missing"].append(k)
        elif new[k] == old[k]:
            res["ok"] += 1
        elif k in last_synced and new[k] == last_synced[k]:
            res["stale"].append(k)
        else:
            res["mismatch"].append(k)
    return res


GATES = {"shadow_mismatch": 1e-5, "diff_rows": 0, "new_error_rate": 1e-3, "p99_growth": 0.10}


def cutover_gate(bucket, m):
    """灰度切读闸门：任何一项不过，这一档就不许放量。"""
    bad = []
    if m["shadow_mismatch"] > GATES["shadow_mismatch"]:
        bad.append("影子双读差异率 %.2e > %.0e" % (m["shadow_mismatch"], GATES["shadow_mismatch"]))
    if m["diff_rows"] > GATES["diff_rows"]:
        bad.append("对账残差 %d 行未清零" % m["diff_rows"])
    if m["new_error_rate"] > GATES["new_error_rate"]:
        bad.append("新库错误率 %.2f%% > %.1f%%" % (m["new_error_rate"] * 100,
                                                GATES["new_error_rate"] * 100))
    if m["p99_growth"] > GATES["p99_growth"]:
        bad.append("P99 涨幅 %.0f%% > %.0f%%" % (m["p99_growth"] * 100, GATES["p99_growth"] * 100))
    return (len(bad) == 0), bad


def rollback_decision(window, old_writable, hours_since_freeze):
    """回滚不是「按一下按钮」：旧库已停写就得反向补数。"""
    if old_writable:
        return "秒级回滚：改路由，旧库仍是权威", 0.0
    if window["diff_rows"] > 0:
        return "先修残差再谈回滚（否则回滚后数据也不对）", float("inf")
    reverse_h = max(0.0, hours_since_freeze)
    return "反向同步新库增量回旧库后再切", round(reverse_h, 2)


if __name__ == "__main__":
    base = Capacity(rows=800_000_000, avg_row_bytes=1024, copy_mbps=300 * 1024 * 1024,
                    write_qps=20_000, drain_qps=8_000, verify_qps=50_000)
    p_bad = plan(base)
    assert p_bad["feasible"] is False
    assert p_bad["min_drain_qps"] == 26000
    print("回放能力 8k/s < 写入 20k/s: 追平时间无穷 -> 窗口永远收不了口 ❌")
    print("  最低要求 %.0f 行/s（写入的 1.3 倍）" % p_bad["min_drain_qps"])

    ok = Capacity(rows=800_000_000, avg_row_bytes=1024, copy_mbps=300 * 1024 * 1024,
                  write_qps=20_000, drain_qps=40_000, verify_qps=50_000)
    p = plan(ok)
    assert p["feasible"] and p["copy_h"] == 0.72 and p["catchup_h"] == 0.72
    assert p["verify_h"] == 8.89
    print("可行方案: 全量 %.2fh + 追平 %.2fh + 两轮校验 %.2fh = 双写 %.2fh，"
          "加灰度共 %.2fh" % (p["copy_h"], p["catchup_h"], p["verify_h"],
                              p["dual_h"], p["total_h"]))
    print("  注意：校验占比 %.0f%%，窗口长短由它决定，不由拷贝决定"
          % (p["verify_h"] / p["dual_h"] * 100))

    old = {"o1": 1, "o2": 2, "o3": 3, "o4": 4, "o5": 5}
    new = {"o1": 1, "o2": 99, "o3": 3, "o5": 4}       # o4 缺失，o2 写错，o5 丢了这次写
    hist = {"o3": 3, "o2": 2, "o5": 4}   # o5 的上一版是 4
    changed = ["o1", "o2", "o3", "o4", "o5"]
    d1 = classify(old, new, changed)
    assert d1["missing"] == ["o4"] and d1["mismatch"] == ["o2", "o5"] and d1["ok"] == 2
    d2 = classify_with_history(old, new, changed, hist)
    assert d2["missing"] == ["o4"] and d2["stale"] == ["o5"] and d2["mismatch"] == ["o2"]
    print("无同步位点: 缺失 %s / 值不一致 %s" % (d1["missing"], d1["mismatch"]))
    print("带同步位点: 缺失 %s / 值不一致 %s / 陈旧 %s（陈旧=丢写，可回放 binlog 修复）"
          % (d2["missing"], d2["mismatch"], d2["stale"]))

    good = {"shadow_mismatch": 0.0, "diff_rows": 0, "new_error_rate": 0.0004, "p99_growth": 0.05}
    okflag, bad = cutover_gate(0.01, good)
    assert okflag and bad == []
    print("灰度 1% 闸门: 全绿，可放量 ✅")

    leaky = {"shadow_mismatch": 3e-5, "diff_rows": 12, "new_error_rate": 0.002, "p99_growth": 0.22}
    okflag2, bad2 = cutover_gate(0.05, leaky)
    assert not okflag2 and len(bad2) == 4
    print("灰度 5%% 闸门: %d 项拦截 -> %s" % (len(bad2), bad2[0]))

    print("回滚(旧库可写):", rollback_decision({"diff_rows": 0}, True, 0)[0])
    print("回滚(旧库停写 6h):", rollback_decision({"diff_rows": 0}, False, 6)[0])
    print("回滚(有残差):", rollback_decision({"diff_rows": 7}, False, 6)[0])
```

**追问**：1) 回放能力只比写入高一点（比如 2.2 万 vs 2 万），能不能跑？—— 能追平，但追平时间被 `backlog / 0.2万` 放大到数十小时，而且期间任何一次写入尖峰（大促、批量任务）都会让延迟反弹，等价于窗口无限延长。经验线是 1.3 倍，目的不是「能追上」而是「尖峰时也能追上」。如果补不上回放能力，另一条路是**限速写入**或**分批迁移**（按主键区间分多轮，每轮只锁一段的写），而不是硬等。2) 切读为什么必须按 user_id 哈希，不能按请求随机？—— 用户的一次会话里会多次读同一份数据（列表 → 详情 → 刷新），随机切会让同一用户在新旧库之间来回跳，看到「下单成功但订单列表没有」这种自相矛盾的界面；按 user 哈希保证单个用户始终命中同一侧，一致性体验可解释。代价是灰度比例只能是桶粒度的近似值（1% 桶可能实际是 1.07%），这个偏差要在容量评估里算进去。3) 停旧写之后才发现新库有慢查询，能回滚吗？—— 技术上能，但要先反向同步窗口内的增量，且反向同步只能补「新库有的、旧库结构能装下」的字段，属于有损回滚。所以正确做法是**在切读 100% 但旧库仍可写的观察期内**把慢查询打完（至少一个完整业务周期），把「停旧写」当成迁移的最后一个动作，而不是切读完成就顺手做了。

## 背诵要点
1. 窗口公式 `T = T_copy + T_catchup + T_verify`，门槛 `drain ≥ 1.3 × write`（否则追平是无穷大）；800GB/8 亿行实测校验占 86%，窗口由校验决定，不由拷贝决定。
2. 旧库是权威、先旧后新、新库失败不阻塞用户；幂等靠版本号条件写，补偿靠 outbox 或 binlog 反查。
3. 差异分缺失/不一致/陈旧三类（需要同步位点才能区分后两者）；切读按 user 哈希桶灰度，闸门四项取「与」；停旧写是最后一步，停之前回滚才是秒级。

## 复盘追问
1. 双写期间新库写入延迟升高，把应用线程池拖满，怎么办？（提示：双写必须是「旁路」——异步线程池/独立连接池 + 有界队列 + 超时熔断，绝不复用业务线程；队列满就丢弃并打点，靠补偿队列兜底，不能反压主链路）
2. 迁移完成后旧库要下线，怎么证明「真的没人读了」？（提示：不是看配置，看证据——旧库的 QPS 曲线、连接来源 IP、慢查询日志三处同时归零并持续一个业务周期；再加一道「只读账号回收 + 网络 ACL 拒绝」的硬隔离，配置会骗人，连接不会）
