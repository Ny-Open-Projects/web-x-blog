### A102 · 幂等下单场景题

> 难度:★★★ | 标签:幂等, 唯一约束, 事务, 场景题

**问**（笔试·场景题）：客户端下单，网络抖动时客户端会重试，同一次点击可能产生 2~3 个相同请求；服务端还可能「处理成功但响应超时」。设计下单接口的幂等方案：客户端带什么、服务端存什么、哪一层兜底、如何区分「重复请求」与「新请求」？写核心表结构与处理伪码。

**答**：四层防线：① 客户端生成 `request_id`（UUID，一次点击固定），重试时**原样携带**——这是唯一能区分「同一次操作」的锚点；② 网关/应用层用 Redis `SET NX EX` 做快速去重挡（挡住瞬时重放，TTL=业务超时×2），但**它不是真相源**（Redis 可能丢）；③ 真相源是 DB 的**唯一约束**：`idempotency_key` 建唯一索引，并发插入冲突 = 重复，捕 `IntegrityError` 后查已有订单返回原结果——这层由数据库保证，宕机也不丢；④ 响应超时场景：处理已成功，客户端重试进来，走③返回**原订单**而非报错。关键取舍：Redis 层只做性能挡板，正确性全部押 DB 约束。

```python
# 表结构（伪 DDL）
# CREATE TABLE orders (
#   id BIGINT PRIMARY KEY,
#   request_id CHAR(36) NOT NULL,
#   user_id  BIGINT NOT NULL,
#   amount   DECIMAL(12,2) NOT NULL,
#   status   TINYINT NOT NULL DEFAULT 0,   -- 0待支付 1已支付 2已取消
#   created_at DATETIME NOT NULL,
#   UNIQUE KEY uk_request (user_id, request_id)   -- 幂等真相源
# ) ENGINE=InnoDB;

import sqlalchemy as sa
from sqlalchemy.exc import IntegrityError

meta = sa.MetaData()
orders = sa.Table(
    "orders", meta,
    sa.Column("id", sa.BigInteger, primary_key=True),
    sa.Column("request_id", sa.String(36), nullable=False),
    sa.Column("user_id", sa.BigInteger, nullable=False),
    sa.Column("amount", sa.Numeric(12, 2), nullable=False),
    sa.Column("status", sa.SmallInteger, nullable=False, server_default="0"),
    sa.UniqueConstraint("user_id", "request_id", name="uk_request"),
)

def place_order(conn, user_id: int, request_id: str, amount: str) -> dict:
    # ① Redis 挡板（可选，纯性能优化；SET NX EX 5s）；此处演示 DB 兜底主线
    try:
        r = conn.execute(orders.insert().values(
            request_id=request_id, user_id=user_id, amount=amount))
        return {"order_id": r.inserted_primary_key[0], "replayed": False}
    except IntegrityError:
        # ② 唯一键冲突 = 重复请求（可能并发，也可能上一次已成功）
        conn.rollback()
        row = conn.execute(
            sa.select(orders.c.id, orders.c.status)
            .where(orders.c.user_id == user_id, orders.c.request_id == request_id)
        ).one()
        return {"order_id": row.id, "status": row.status, "replayed": True}

if __name__ == "__main__":
    # 缺库降级：无 sqlalchemy 时改为理解表结构 + IntegrityError 语义即可
    eng = sa.create_engine("sqlite://")
    meta.create_all(eng)
    with eng.begin() as c:
        a = place_order(c, 1, "uuid-111", "99.00")
    with eng.begin() as c:
        b = place_order(c, 1, "uuid-111", "99.00")     # 客户端重试同 request_id
    assert a["order_id"] == b["order_id"] and b["replayed"] is True
    print(a, b)
```

**追问**：1) 为什么 `uk_request` 是 `(user_id, request_id)` 而不是单列？——不同租户/用户撞到同一 UUID 理论可能且隔离域更清晰；同时复合唯一键还能避免恶意用户用别人的 request_id 探测订单（返回前再校验归属）。2) Redis 挡板返回 False 但 DB 里其实没有单，怎么办？——说明 TTL 内曾被挡过但首单可能还在途：改为挡板只挡 200ms 内的重放，TTL 要短；或挡板失败直接放行到 DB 层，让唯一约束裁决——**挡板宁可漏放，不可错杀**。3) 订单状态机与幂等怎么配合？——重复请求若订单已取消，返回「订单已取消」而非复活新单，幂等返回的是**最新终态**。

## 背诵要点
1. 幂等四层：客户端 request_id → Redis NX 性能挡板 → DB 唯一约束（真相源）→ 冲突后查原单返回终态。
2. 挡板宁漏放不错杀：正确性只押 DB 约束，Redis 丢了也不会重复下单。
3. IntegrityError 捕获后必须查回原单返回 replayed=True，而不是报 500。
