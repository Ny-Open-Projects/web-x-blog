### A136 · 熔断恢复验证

> 难度:★★☆ | 标签:熔断, 恢复, 可靠性

**问**（笔试·编程+场景题）：熔断器（A106）冷却后进入 half-open——「一次探测成功就恢复」的风险是什么（下游抖动恢复，马上又挂），半开探测的设计参数（探测请求数/判定标准/探测间隔），「信任重建」为什么要渐进（10%→50%→100% 流量恢复），熔断期间的请求怎么处理（排队重放 vs 直接失败）？

**答**：① 一次成功即恢复的风险：抖动恢复（下游刚恢复 1s 又抖）→ 全量流量打过去 → 再熔断 → 震荡；正确设计 = **多次探测判定**（连续 K 次探测成功才恢复）+ **渐进放量**（恢复后先 10% 流量，观察窗再 50%、100%——信任重建，同 Q135 步进同构）。② 探测参数：探测请求数（半开期允许 N 个真实请求当探测，非合成探针——真实流量才代表真实行为）、判定标准（N 个中成功率 ≥ 阈值）、探测间隔（冷却期内多次探测而非一次）。③ 熔断期间请求处理：**直接失败**（快速失败，客户端走降级——推荐，因为排队 = 假装熔断没发生，恢复瞬间排队洪峰打崩刚恢复的下游）vs **排队重放**（仅幂等+低价值操作，且队列有界）；混合策略：读请求直接失败走缓存降级，写请求 409 让客户端稍后重试。

```python
# 全部标准库；demo 实现「多次探测 + 渐进放量」熔断恢复
import time

class RecoveryBreaker:
    """A106 三态扩展：half-open 需连续 K 次探测成功 + 渐进放量。"""
    def __init__(self, probes_required: int = 5, ramp: list[int] = (10, 50, 100),
                 ramp_window_s: float = 30):
        self.probes_required = probes_required
        self.ramp = list(ramp)
        self.ramp_window = ramp_window_s
        self.state = "closed"
        self.probe_ok = 0
        self.ramp_idx = 0
        self.ramp_start = 0.0
    def allow(self) -> bool:
        if self.state == "open":
            return False
        if self.state == "half-open":
            return True                          # 探测期放行
        if self.state == "ramping":              # 渐进放量期
            return (time.monotonic() - self.ramp_start) % self.ramp_window_s < \
                   self.ramp_window_s * self.ramp[self.ramp_idx] / 100 or \
                   random_true(self.ramp[self.ramp_idx] / 100)
        return True
    def on_probe_result(self, ok: bool):
        if self.state != "half-open":
            return
        if ok:
            self.probe_ok += 1
            if self.probe_ok >= self.probes_required:
                self.state, self.ramp_idx, self.ramp_start = "ramping", 0, time.monotonic()
                print(f"  → ramping（流量 {self.ramp[0]}% 起步）")
        else:
            self.probe_ok = 0                    # 一次失败清零重来（防抖动恢复）
    def on_ramp_window(self, error_rate: float):
        """每个放量窗口结束检查：无恶化则升档，恶化回 half-open。"""
        if self.state != "ramping":
            return
        if error_rate > 0.02:
            self.state, self.probe_ok = "half-open", 0
            print("  ← 放量窗口错误率超阈 → 回 half-open 重新探测")
        elif self.ramp_idx < len(self.ramp) - 1:
            self.ramp_idx += 1
            print(f"  ↑ 放量升至 {self.ramp[self.ramp_idx]}%")
        else:
            self.state = "closed"
            print("  ✓ 恢复 closed（100% 流量）")

def random_true(p: float) -> bool:
    import random
    return random.random() < p

if __name__ == "__main__":
    import random; random.seed(1)
    b = RecoveryBreaker(probes_required=3)
    b.state = "half-open"
    for ok in (True, True, False, True, True, True):   # 中途一次失败清零
        b.on_probe_result(ok)
    assert b.state == "ramping"                        # 连续 3 次成功才 ramping ✅
    print("半开探测：连续 3 次成功才恢复（一次失败清零防抖动）✅")
    for err in (0.005, 0.005, 0.005, 0.03):            # 三个窗口正常，第四恶化
        b.on_ramp_window(err)
    assert b.state == "half-open"
    print("渐进放量：恶化窗口回滚到 half-open（信任重建失败重来）✅")
    # 口径：熔断期请求直接失败走降级（排队=恢复瞬间洪峰）；恢复=多次探测+渐进放量。
```

**追问**：1) 为什么探测用「真实流量」而非合成探针？——合成探针（固定请求）走的是最优路径（小请求、热缓存），下游对真实流量的表现可能完全不同（大请求、冷数据）；真实流量探测=恢复能力的真实检验——代价是探测期部分真实请求可能失败（可接受，量小）。2) 熔断期「写请求 409」的用户体验怎么兜底？（提示：409 附带 Retry-After + 前端友好提示（「系统繁忙稍后重试」）+ 关键写操作入队稍后自动执行（有幂等键才可入队））3) 「渐进放量」和 Q135 灰度步进什么关系？（提示：同构机制——灰度步进切流量、恢复步进切回流量；护栏判定标准一致（错误率/P99）——一套基础设施两种用途）

## 背诵要点
1. 半开恢复 = 连续 K 次真实流量探测成功（一次失败清零），拒绝「一次成功即全量恢复」。
2. 恢复后渐进放量 10%→50%→100%，每窗口查错误率，恶化回 half-open 重来。
3. 熔断期请求直接失败走降级（排队=恢复瞬间洪峰）；写请求 409+Retry-After。

## 复盘追问
1. 恢复到 50% 流量时下游又挂了，回 half-open——这次探测期要不要拉长？（提示：重复失败说明下游不稳定——冷却时长指数退避（第二次熔断冷却 ×2），避免震荡循环）
2. 下游是「部分恢复」（比如 3 个实例恢复了 1 个），全量恢复会怎样？（提示：1/3 容量接 100% 流量=必挂——探测期错误率会自然拦住，但更好的做法是探测期也按实例健康度加权放量）
