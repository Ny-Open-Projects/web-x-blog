### A202 · 文档失效检测

> 难度:★★☆ | 标签:文档治理, 失效检测, 自动化

**问**（笔试·编程+场景题）：内部文档 500 篇，三分之一写着「已过时的架构」——过时文档怎么**自动发现**（代码与文档的 diff 关联/文档时效元数据/访问与反馈信号），文档「权威度」怎么分级（权威文档 vs 过期参考 vs 待删），文档治理的成本怎么控制（500 篇全修不现实——分级投入），「文档即代码」（docs-as-code）的落地方式？

**答**：① 自动发现三信号：**代码 diff 关联**（文档描述的接口/配置变更了——文档引用的代码路径/配置键与当前仓库 diff 对比，A168 文档时效机制）、**时效元数据**（`last_verified` 字段过期告警——「上次验证时间」比「最后修改时间」可靠——文档可能长期没改也没过时，也可能昨天改完就过时）、**反馈信号**（读者点踩/提问集中 = 可疑文档——「这篇文档对你有帮助吗」的轻量反馈是失效探测器）。② 权威度分级：**权威**（owner 维护+定期验证——是唯一真相源）、**参考**（可能过时，标注「未验证」——读者自行判断）、**归档**（明确过时，从检索中隐藏但保留历史）——分级让「投入」有的放矢：权威文档重点维护，归档文档不投入。③ 成本控制：分级投入（权威文档 N 篇 × 定期验证，其余靠自动化标记）+ 「顺手修」机制（改到相关代码时顺手更新文档——CI 提示关联文档）+ 批量处理（过时文档按「访问量」排序——高访问的优先修，无人访问的归档）。④ docs-as-code：文档进仓库（与代码同 review 流程）+ 文档变更触发关联代码的提醒（反向：改代码提醒改文档——Q7053 文档时效）。

```python
# 全部标准库；demo 实现「文档分级 + 失效信号聚合」
import time

class DocGovernance:
    def __init__(self, verify_ttl_days: int = 180):
        self.ttl = verify_ttl_days * 86400
        self.docs: list[dict] = []
    def register(self, title: str, owner: str, last_verified: float,
                 refs_code: str | None = None, views: int = 0):
        self.docs.append({"title": title, "owner": owner, "verified": last_verified,
                          "refs": refs_code, "views": views, "status": "unknown"})
    def audit(self, code_changed_keys: set[str]) -> dict[str, list[str]]:
        now = time.time()
        expired, stale = [], []
        for d in self.docs:
            aged = now - d["verified"] > self.ttl
            ref_changed = d["refs"] and d["refs"] in code_changed_keys
            if ref_changed:
                d["status"] = "likely-stale"    # 引用的代码变了 = 失效强信号
                stale.append(f"{d['title']}（引用代码已变更）")
            elif aged and d["views"] > 100:
                expired.append(f"{d['title']}（未验证 {int(aged/86400)} 天，月访问 {d['views']} → 优先修）")
            elif aged:
                d["status"] = "archive-candidate"  # 低访问过期 → 归档不修
        return {"stale": stale, "expired_high_view": expired}

if __name__ == "__main__":
    now = time.time()
    gov = DocGovernance(verify_ttl_days=180)
    gov.register("架构总览", "li", now - 10 * 86400, views=500)          # 新近验证
    gov.register("支付接入指南", "wang", now - 200 * 86400,
                 refs_code="payment/client.py", views=300)              # 引用代码已变
    gov.register("老版部署手册", "zhao", now - 400 * 86400, views=10)   # 低访问过期
    result = gov.audit(code_changed_keys={"payment/client.py"})
    print("失效强信号:", result["stale"])
    print("过期高访问（优先修）:", result["expired_high_view"])
    assert len(result["stale"]) == 1 and "支付接入" in result["stale"][0]
    # 口径：三信号（代码 diff 关联/时效元数据/读者反馈）；权威度三级（权威/参考/归档）；
    # 分级投入：高访问优先修，低访问归档不修——500 篇全修不现实，分级才可持续。
```

**追问**：1) 为什么「last_verified」比「last_modified」可靠？——文档长期没改可能仍然正确（架构没变）、「刚改」也可能改错——「验证过是准确的」这个动作与「修改」是两件事；验证可以是轻量的（扫一遍确认无误+更新时间戳），比强制改写成本低——验证字段让「没坏的东西」不被误判。2) 「文档即代码」的落地阻力？（提示：写文档的人不习惯 git 流程——降低门槛：文档变更走简化 review（不需要代码级严格）+ CI 检查文档格式/链接有效性 + 代码 PR 自动提醒关联文档变更（改 payment/client.py 提醒更新支付文档）——阻力靠「嵌入现有流程」化解）3) 归档文档「从检索隐藏」会不会丢失有价值的历史？（提示：归档≠删除——保留全量历史+明确「归档」标识；隐藏的是「默认检索」——需要历史的人明确搜索可以找到；防止的是「新人按过时文档操作」——访问入口的默认排序就是治理）

## 背诵要点
1. 失效三信号：代码 diff 关联（最强）/时效元数据（last_verified 过期）/读者反馈（点踩集中）。
2. 权威度三级：权威（owner 维护定期验证）/参考（未验证标注）/归档（隐藏检索保留历史）——分级投入。
3. docs-as-code：文档进仓库同 review + 代码变更提醒关联文档——阻力靠嵌入现有流程化解。

## 复盘追问
1. 「owner 离职后文档无主」，owner 字段怎么治理？（提示：owner 离职自动触发文档 owner 转移（Q174 SSO 接 HR 联动）或团队认领——无主文档降级为「参考」（不算权威）——owner 是文档权威度的核心字段，无主=不可信）
2. 自动检测说「文档过时」但人工复核发现文档仍然正确（代码变了但行为没变），误报怎么治？（提示：强信号（引用代码变更）只是「可能过时」不是「一定过时」——复核后标记「已验证仍准确」（更新 verified 时间戳）——检测系统的输出是「候选清单」不是「结论」，人工确认闭环（Q7040 质量规则误报治理同构））
