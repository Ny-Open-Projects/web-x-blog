### A121 · 大促容量压测场景题

> 难度:★★★ | 标签:压测, 容量规划, 场景题

**问**（笔试·场景题）：大促预估峰值 5 万 QPS（日常 8 千）——容量怎么算（不是「按峰值 × 2 加机器」的正确姿势），压测怎么组织（生产影子压测 vs 压测环境模拟，各自失真在哪），压测数据（参数化/数据隔离）怎么造，「压不出问题」的三种常见假象怎么识破？

**答**：① 容量推导链：峰值 QPS → **分解到各服务/依赖**（调用树：1 个下单 = 网关 1 + 库存 2 + 订单 1 + 缓存 3 次……每层放大系数不同）→ 每层按「P99 目标下的单实例容量」（压测实测，不是拍）→ 实例数 = 层 QPS ÷ 单实例容量 × 冗余系数（1.5×，机房级冗余再算）→ 依赖侧同推导（DB 连接/缓存带宽/第三方配额）。② 压测组织：**生产影子压测**（真实流量复制到影子链路，数据隔离标记）——失真点：影子链路共享真实依赖时可能污染生产（写操作要 mock 或影子表）；**压测环境**失真更多：机器规格不同、数据量级不同、网络拓扑不同——结论：关键链路必须生产影子压，环境压测只做功能验证。③ 数据构造：参数化（真实分布的参数，别用同一个 URL 打——缓存会掩盖问题）、数据隔离（压测标记 + 影子表/测试账号）、场景回放（真实流量录制回放比脚本模拟真实）。④ 三种假象：**压测缓存热了**（反复打同一 URL，命中率 100%，掩盖缓存穿透/击穿——参数化解决）；**压测限流没关/关错**（压出来的是限流器容量不是服务容量）；**下游 mock 掉了**（真实瓶颈在第三方，mock 后永远压不挂——真瓶颈测不出来，上线后爆）。

```python
# 全部标准库；demo 实现「调用树容量推导 + 假象检测器」
import collections

CALL_TREE = {                       # 服务 -> (自身放大系数, [下游])
    "gateway": (1, ["stock", "order", "cache"]),
    "stock": (2, ["db"]),
    "order": (1, ["db", "mq"]),
    "cache": (3, ["redis"]),
    "db": (0, []), "mq": (0, []), "redis": (0, []),
}

def derive_load(entry_qps: float, root: str = "gateway") -> dict[str, float]:
    """调用树推导：入口 QPS → 各层负载（放大系数相乘）。"""
    load = collections.defaultdict(float)
    def walk(svc, qps):
        factor, downs = CALL_TREE[svc]
        load[svc] += qps
        for d in downs:
            walk(d, qps * factor)
    walk(root, entry_qps)
    return dict(load)

def instances_needed(load: dict, per_instance: dict[str, float], redundancy: float = 1.5) -> dict:
    """实例数 = 层 QPS / 单实例容量 × 冗余。"""
    return {svc: math.ceil(q / per_instance[svc] * redundancy)
            for svc, q in load.items() if per_instance.get(svc)}

def detect_artifacts(params_used: set[str], limiter_hits: int, mocked: set[str]) -> list[str]:
    """压测假象检测：单参数/限流命中/mock 下游。"""
    issues = []
    if len(params_used) < 100:
        issues.append("参数单一：缓存热身掩盖真实穿透行为")
    if limiter_hits > 0:
        issues.append("限流器被触发：压的是限流容量不是服务容量")
    if mocked:
        issues.append(f"下游被 mock：真实瓶颈可能未测（{mocked}）")
    return issues

import math
if __name__ == "__main__":
    load = derive_load(50000)
    print("各层 QPS 推导:", {k: f"{v:.0f}" for k, v in load.items()})
    assert load["cache"] == 150000 and load["stock"] == 100000   # 放大系数生效
    plan = instances_needed(load, {"gateway": 3000, "stock": 5000,
                                    "order": 4000, "cache": 20000})
    print("实例规划:", plan)
    assert plan["cache"] >= 12        # 150000/20000×1.5
    issues = detect_artifacts(params_used={f"/item/{i}" for i in range(5)},
                              limiter_hits=500, mocked={"thirdpay"})
    print("假象检测:", issues)
    assert len(issues) == 3
    # 口径：容量 = 调用树推导 × 实测单实例容量 × 冗余；生产影子压测才可信。
```

**追问**：1) 为什么冗余系数 1.5× 而不是 2×？——1.5× 覆盖流量预估误差（±30%）；2× 成本翻倍且掩盖「容量长期不足」的问题（靠堆机器回避架构优化）；超预期流量靠降级（A106）兜底而非无限冗余。2) 影子压测怎么防污染生产数据？——压测流量带标记（header/账号白名单）→ 依赖侧识别标记走影子表/空操作；漏标记的写操作是最大事故源——压测前「标记穿透检查」必须全链路验证。3) 第三方依赖（支付渠道）压不了怎么办？——签配额侧扩容（提前申请大促配额）+ mock 延迟建模（按历史 P99 注入延迟测自己这侧的排队行为）+ 降级预案（渠道挂了切备用渠道）。

## 背诵要点
1. 容量推导链：峰值 QPS × 调用树放大系数 → 每层 QPS ÷ 实测单实例容量 × 1.5 冗余——不是「峰值×2 加机器」。
2. 关键链路必须生产影子压测（数据隔离标记）；环境压测只验功能——三种失真各有对策。
3. 三假象：参数单一缓存热身、限流器被触发、下游 mock 掉真瓶颈——压测报告必须附假象自检。

## 复盘追问
1. 压测通过了大促还是挂了，复盘压测哪里失真？（提示：峰值形态失真（真实是脉冲不是匀速）、依赖组合失真（多条故障同时发生）、数据分布失真——压测目标要按「故障场景」设计不只按 QPS）
2. 大促容量规划中「第三方配额」怎么提前数周确认？（提示：配额申请走商务流程（提前 2-4 周）、压测前用 mock 验证我方排队行为、预案含配额耗尽的降级路径）
