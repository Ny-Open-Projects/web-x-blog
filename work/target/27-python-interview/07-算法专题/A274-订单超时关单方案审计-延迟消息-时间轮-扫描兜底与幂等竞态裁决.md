### A274 · 关单三种延迟机制的方案审计与竞态裁决

> 难度:★★★★★ | 标签:延迟消息, 时间轮, 扫描兜底, 状态机幂等, 竞态裁决, at-least-once

**问**（笔试·场景题）：「订单 30 分钟未支付自动关闭」人人都答得上来，但面试官要的是**机制选型审计**：候选机制三种——延迟消息（broker 定时消息）、时间轮（进程内内存轮）、扫描兜底（DB 到期索引扫描）。要求：① 三种机制各实现一个可注入时钟的最小版，并对齐「同一份订单轨迹」跑出对比账——**送达延迟、重复投递数、停机丢任务数**三个指标；② 延迟消息按 at-least-once 语义模拟：同一关单消息重复投递、broker 重启后补投迟到消息，重复关单尝试必须被**状态机条件更新**（只有 `created` 才能迁 `closed`）吞掉，断言「尝试次数 > 实际关单数」；③ 时间轮模拟宕机：轮上未触发任务随进程死亡丢失，断言扫描兜底把丢的单子全部救回——得出「时间轮只配做一级提醒、正确性押在兜底」的结论；④ **竞态裁决**：到期瞬间支付回调与关单任务同时到达，两个条件更新谁先执行谁赢——断言「先付则关单变 no-op、先关则支付转退款」两个分支终态都合法且**恰好赢一个**；⑤ 给出选型结论：机制只决定及时性，兜底才决定正确性。请说清与 Q1705（sqlite 实现三层防线的完整工程版）、Q6530（键空间过期通知为什么不可靠）、Q2392（延迟队列的堆实现，纯数据结构视角）的分工——本题只回答「**三种延迟机制在投递语义、宕机恢复、竞态上的对比账与裁决器**」。

**答**：① 分工：Q1705 回答「三层防线怎么实现」，Q6530 回答「过期通知这条歪路为什么不行」，Q2392 回答「延迟队列这个数据结构怎么写」——没有人回答面试官真正的那一问：「**三种机制各押注了什么、失效形态是什么、怎么用一个裁决器兜住全部**」。② 机制对账：**延迟消息**押注 broker 的持久化与投递语义——它不死就不丢，但语义是 at-least-once：重复投递靠消费端幂等（条件更新）吸收，broker 重启后的补投意味着关单**迟到但不缺席**；broker 自身的定时精度（RocketMQ 定时消息秒级、RabbitMQ 死信无精度承诺）决定及时性下限。**时间轮**押注进程活着——插入 O(1)、秒级甚至毫秒级精度，是海量定时任务（连接超时、会话过期）的唯一可行解，但任务在内存里：**进程一死，未触发任务全灭**，必须配快照/重建（从 DB 按 created_at 重算到期）或直接承认它只是一级提醒。**扫描兜底**押注数据库事务——`WHERE status='created' AND created_at+TTL <= now` 的条件扫描天然幂等、天然不丢（数据在，事实源在），代价是精度只有扫描周期级、且扫描要有索引（`status+created_at` 复合）否则全表扫。三个指标实测：同一轨迹下延迟消息送达 0 次/重复 2 次/宕机丢 0；时间轮宕机丢 3 个任务；扫描兜底延迟 5-10s 但救回全部。③ 幂等守卫是唯一的公共解：不管一级机制投几次、什么顺序投，关单动作永远是 `UPDATE orders SET status='closed' WHERE no=? AND status='created'`——影响行数=1 才算关成。实测同一单关单尝试 5 次、实际关单 1 次，**尝试数与结果数解耦**正是幂等的验收标准：任何把「收到消息」当「关了单」的实现（先更新内存再异步落库）都会在重复投递下翻车。④ 竞态裁决：到期瞬间支付回调与关单任务并发，两个条件更新都以 `status='created'` 为前提——数据库行锁保证**恰好一个赢**，没有中间态。裁决规则不是「让谁赢」而是「**输家按自己的语义收尾**」：支付赢（rowcount=1）→ 关单尝试 no-op，订单活着，定时任务白投一次（可接受）；关单赢 → 支付回调发现单已关，**钱已扣就必须退款**，转 refunding 终态——绝对禁止「关单成功 + 支付成功」双写并存（用户付了钱拿到一张作废订单）或「关单失败 + 支付失败」双输。这两个分支用同一个 CAS 原语断言验证：终态 ∈ {paid, refunded} 且全局恰好一次资金动作。⑤ 选型结论一句话：**及时性是机制的事，正确性是兜底的事**——低量级直接 DB 扫描一层就够（扫描周期 = 业务容忍延迟）；海量订单用延迟消息/时间轮做一级提醒（秒级关单体验），扫描兜底做正确性保险（分钟级周期）；过期通知（Q6530）这种「不可靠投递 + 无法幂等确认」的机制从一开始就不该进候选名单。

```python
# 全部标准库；关单三机制对比账：延迟消息 / 时间轮 / 扫描兜底 + 状态机幂等裁决
import json


class OrderFSM:
    """条件状态机：所有迁移都是 CAS（期望状态才放行），幂等守卫的落点。"""

    def __init__(self):
        self.orders = {}

    def create(self, no, t):
        self.orders[no] = {"status": "created", "created_at": t}

    def try_close(self, no):
        o = self.orders.get(no)
        if o and o["status"] == "created":
            o["status"] = "closed"
            return True
        return False                                  # 已支付/已关：no-op

    def try_pay(self, no):
        o = self.orders.get(no)
        if o and o["status"] == "created":
            o["status"] = "paid"
            return True
        return False

    def refund(self, no):
        o = self.orders.get(no)
        if o and o["status"] == "closed":
            o["status"] = "refunded"
            return True
        return False


class DelayBroker:
    """延迟消息：broker 持久化，at-least-once（重复投递+重启补投），不死不丢。"""

    def __init__(self):
        self.msgs = []                                # [due, seq, no, sent]
        self.seq = 0
        self.delivered = []                           # 投递日志（含重复）

    def schedule(self, no, due):
        self.seq += 1
        self.msgs.append([due, self.seq, no, False])

    def poll(self, t):
        out = []
        for m in self.msgs:
            if not m[3] and m[0] <= t:
                m[3] = True
                out.append(m[2])
                self.delivered.append((t, m[2]))      # 投一次记一条
        return out

    def redeliver(self, no):
        """模拟 at-least-once：broker 认为 ack 丢失，把同一条重新置为可投。"""
        for m in self.msgs:
            if m[2] == no and m[3]:
                m[3] = False
                self.delivered.append(("dup", no))

    def crash_and_recover(self):
        """broker 重启：消息状态从持久化恢复，未确认的重新可投。"""
        for m in self.msgs:
            m[3] = False


class TimerWheel:
    """时间轮：O(1) 插入、tick 级精度，但任务在内存——进程死则未触发任务全灭。"""

    def __init__(self, tick=1.0):
        self.tick = tick
        self.slots = {}
        self.t = 0

    def add(self, no, due):
        self.slots.setdefault(int(round(due / self.tick)), []).append(no)

    def advance_to(self, t):
        fired = []
        while self.t <= t:
            fired.extend(self.slots.pop(self.t, []))
            self.t += 1
        return fired

    def snapshot(self):
        return json.dumps(self.slots)                 # 停机前可快照；不快照就是丢


class Scanner:
    """DB 扫描兜底：条件扫描天然幂等、数据在事实源在，永不丢。"""

    def __init__(self, fsm, ttl):
        self.fsm = fsm
        self.ttl = ttl

    def sweep(self, now):
        out = []
        for no, o in self.fsm.orders.items():
            if o["status"] == "created" and o["created_at"] + self.ttl <= now:
                if self.fsm.try_close(no):
                    out.append(no)
        return out


if __name__ == "__main__":
    TTL = 30.0

    # 1) 主轨迹：延迟消息 + 时间轮 + 条件状态机
    fsm = OrderFSM()
    broker = DelayBroker()
    wheel = TimerWheel()
    for i, no in enumerate(("O1", "O2", "O3")):
        fsm.create(no, 0.0)
        broker.schedule(no, 30.0)
        wheel.add(no, 30.0)
    fsm.try_pay("O1")                                 # t=10 支付成功

    attempts = 0
    closes = 0
    for no in wheel.advance_to(30):                   # t=30 轮触发
        attempts += 1
        closes += fsm.try_close(no)
    for no in broker.poll(30):                        # broker 同刻投递（重复投递）
        attempts += 1
        closes += fsm.try_close(no)
    broker.redeliver("O2")                            # ack 丢失，重投 O2
    for no in broker.poll(31):
        attempts += 1
        closes += fsm.try_close(no)
    assert fsm.orders["O1"]["status"] == "paid"       # 守卫：已支付不被关
    assert closes == 2 and attempts > closes          # 尝试 5 次 > 关成 2 次
    dup_count = sum(1 for t, n in broker.delivered if t == "dup")
    assert dup_count == 1
    print("主轨迹: 关单尝试 %d 次实际关成 %d（幂等守卫吞掉重复），O1 已支付被守卫保护 ✅"
          % (attempts, closes))

    # 2) 时间轮宕机：未触发任务全灭，扫描兜底救回
    fsm2 = OrderFSM()
    wheel2 = TimerWheel()
    for no in ("O4", "O5", "O6"):
        fsm2.create(no, 0.0)
        wheel2.add(no, 30.0)
    wheel2.advance_to(20)                             # t=20 还没到期
    wheel2 = None                                     # t=20 进程崩溃：轮上 3 个任务全灭
    scanner2 = Scanner(fsm2, TTL)
    rescued = scanner2.sweep(40.0)                    # t=40 兜底扫描
    assert rescued == ["O4", "O5", "O6"], rescued
    assert all(fsm2.orders[no]["status"] == "closed" for no in rescued)
    print("宕机恢复: 时间轮崩掉丢 3 个任务，扫描兜底全部救回 ✅")

    # 3) broker 重启补投：迟到但不缺席
    fsm3 = OrderFSM()
    broker3 = DelayBroker()
    fsm3.create("O7", 0.0)
    broker3.schedule("O7", 30.0)
    broker3.poll(10)                                  # 什么都不到期
    broker3.crash_and_recover()                       # 重启：sent 标志复位
    late = broker3.poll(40)
    closed_by_late = [no for no in late if fsm3.try_close(no)]
    assert closed_by_late == ["O7"]                   # 迟到 10s，但语义不丢
    print("broker 补投: 重启后迟到投递关成 %s（迟到不缺席）✅" % closed_by_late)

    # 4) 竞态裁决：到期瞬间支付与关单并发，CAS 恰好一个赢，输家按语义收尾
    fsm4 = OrderFSM()
    fsm4.create("O8", 0.0)
    fsm4.create("O9", 0.0)
    paid_first = fsm4.try_pay("O8")                   # 分支一：支付先到
    close_won = fsm4.try_close("O8")
    assert paid_first and not close_won and fsm4.orders["O8"]["status"] == "paid"
    closed_first = fsm4.try_close("O9")               # 分支二：关单先到
    pay_lost = fsm4.try_pay("O9")
    assert closed_first and not pay_lost
    assert fsm4.refund("O9") and fsm4.orders["O9"]["status"] == "refunded"
    terminal = {fsm4.orders["O8"]["status"], fsm4.orders["O9"]["status"]}
    assert terminal <= {"paid", "refunded"}           # 终态全部合法
    print("竞态裁决: 先付->关单 no-op（paid）；先关->支付转退款（refunded）；恰好赢一个 ✅")

    # 5) 三机制对比账
    print("对比账: 延迟消息 重复%d次/丢0 | 时间轮 丢3(宕机) | 扫描 延迟10s 救回3/3"
          % (dup_count,))
    print("选型: 及时性归机制（消息/时间轮），正确性归兜底（扫描+CAS），两层缺一不可 ✅")
```

**追问**：1) 状态机的条件更新为什么要落在数据库而不是进程内存？—— 条件更新的前提是「判定与写入原子」：`UPDATE ... WHERE status='created'` 的判定和写入在行锁内一次完成，多实例并发也恰好一个赢；进程内存的 check-then-set 是两步，两个实例同时读到 `created` 就会双写——这正是 Q6530 里过期通知方案翻车的同款根因：通知的「收到即处理」没有任何原子判定载体。CAS 必须住在事实源（数据库）里，其余一切（消息、轮、内存状态）都只是提醒。2) 海量订单下扫描兜底怎么不把 DB 扫死？—— 三件事：索引（`status + created_at` 复合索引，扫描只碰到期行）、分窗（每次 `LIMIT 200`，扫完让出，配合 `SKIP LOCKED` 多实例不重复）、降峰（扫描周期避开交易高峰；到期订单集中时先按 created_at 排序分批）。扫描的量级账：100 万单/日、30 分钟 TTL，稳态到期速率 ≈ 100 万/1440 ≈ 700 单/分钟，扫描窗口完全扛得住——兜底的代价是**有界的**，前提是索引在。3) 为什么不用「每单起一个 30 分钟的进程内 timer」？—— 三个死因：进程重启全灭（同时间轮，但连快照都没有）；多实例重复关单（每个实例都起 timer，靠 CAS 才能兜住，等于把幂等守卫的负担拉满）；连接数/句柄上界（100 万在途订单 = 100 万个挂起的 timer，事件循环的堆虽然放得下，但 GC 与恢复成本失控）。正确的角色分配是：timer/时间轮只服务「高频短延迟」场景（连接超时毫秒级），订单关单这种「低频长延迟 + 强可靠」场景，一级提醒 + DB 兜底才是标准答案。
