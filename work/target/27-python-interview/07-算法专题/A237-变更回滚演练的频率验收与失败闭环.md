### A237 · 变更回滚演练

> 难度:★★☆ | 标签:回滚, 演练, 变更

**问**（笔试·场景题）：每周上线几十次变更，回滚预案每单都写了，但「真正回滚过一次」没人记得——回滚演练的频率怎么定（每次都演练不现实，核心服务与边缘服务怎么分级），回滚演练的验收标准是什么（不是「回滚命令跑完没报错」就算通过），演练失败（回滚卡住 / 数据回退后不兼容）怎么进入行动项闭环？它和变更依赖排序（A188）、灰度转全量（A208）、预案清单（A196）、单次变更的预案三验收（A187）到底差在哪？

**答**：① 定位差异：A188 解决「多服务先发谁」，A208 解决「灰度怎么转全量」，A196/A187 解决「这一单的预案字段合不合格」——A237 解决的是**回滚能力本身是否真的可用**：预案是纸面承诺，演练是把纸面变成可复现的肌肉记忆，是独立于「这次怎么发」的周期性能力建设。② 频率分级 + 随机抽检：核心服务**月度全量回滚**（真的切回旧版），重要服务**月度从已上线变更里随机抽 2 次**，边缘服务**季度抽检**；频率与「变更频次 × 回滚失败代价」成正比（与 A148 的频率分级同构，但对象不同——备份保数据，回滚保发布可逆）；不每次都演练是因为真实切换有流量风险与人力成本。③ 验收四层（比 A187 的三验收更硬，四层全过才算 PASS）：**耗时** ≤ 事故容忍时间（A187 时长约束的演练版）、**流量无损**（切换期错误率不超阈值，A185 兼容性的演练版）、**数据一致**（回滚后数据与旧版本兼容，配置/数据结构回退要验算，A108 延伸）、**业务指标回归**（不能只看 /healthz——探针通但下单成功率为 0 的情况真实存在）。④ 失败闭环：失败按 P1（回滚根本不可用 / 数据不兼容）与 P2（慢但能回）分级，每条生成带 owner + 截止日（P1 三天、P2 七天）+ 复验门禁的行动项；下次演练**先复验上期行动项**再开新演练（防「演练-发现-遗忘」），连续两次失败或 P1 逾期未修 → 触发该服务变更冻结（A133），回滚能力恢复才解冻——失败必须有后果，否则演练沦为走过场。

```python
# 全部标准库；demo 实现「演练频率调度 + 四层验收 + 失败转行动项 + 复验门禁」
from datetime import date, timedelta

RISK_FREQ = {"core": ("monthly", 30), "important": ("monthly-sample", 30),
             "edge": ("quarterly-sample", 90)}

def drill_due(tier: str, last_drill: date, today: date) -> bool:
    """演练到期判定：核心月度全量、重要月度抽检、边缘季度抽检。"""
    interval = RISK_FREQ[tier][1]
    return (today - last_drill).days >= interval

def verify_drill(result: dict, tolerance_min: float) -> list[dict]:
    """回滚验收四层：耗时/流量无损/数据一致/业务指标回归。"""
    failed = []
    if result["elapsed_min"] > tolerance_min:
        failed.append({"level": "P1", "item": "rollback_time",
                       "detail": f"回滚 {result['elapsed_min']}min > 容忍 {tolerance_min}min"})
    if result["error_rate_pct"] > 1.0:
        failed.append({"level": "P1", "item": "traffic_loss",
                       "detail": f"切换期错误率 {result['error_rate_pct']}% > 1%"})
    if not result["data_consistent"]:
        failed.append({"level": "P1", "item": "data_consistency",
                       "detail": "回滚后数据与目标版本不兼容"})
    if not result["biz_metric_recovered"]:
        failed.append({"level": "P2", "item": "biz_metric",
                       "detail": "健康探针通但核心业务指标未回归"})
    return failed

def to_action_items(failed: list[dict], owner: str, today: date) -> list[dict]:
    """失败 → 行动项：P1 三天、P2 七天，带 owner 与复验标记。"""
    return [{"item": f["item"], "level": f["level"], "owner": owner,
             "due": today + timedelta(days=3 if f["level"] == "P1" else 7),
             "detail": f["detail"], "verified": False} for f in failed]

def pending_gate(items: list[dict], today: date) -> list[dict]:
    """下次演练门禁：上期未复验且已到期的行动项必须先复验。"""
    return [i for i in items if not i["verified"] and i["due"] <= today]

if __name__ == "__main__":
    today = date(2026, 11, 23)
    assert drill_due("core", date(2026, 10, 20), today)
    assert not drill_due("core", date(2026, 11, 20), today)
    assert drill_due("edge", date(2026, 8, 1), today)
    bad = {"elapsed_min": 25, "error_rate_pct": 2.5,
           "data_consistent": False, "biz_metric_recovered": True}
    failed = verify_drill(bad, tolerance_min=10)
    assert [f["item"] for f in failed] == ["rollback_time", "traffic_loss", "data_consistency"]
    items = to_action_items(failed, "owner-zhang", today)
    assert all(i["due"] > today for i in items)
    print("核心服务演练到期:", drill_due("core", date(2026, 10, 20), today))
    print("验收失败项:", [(f["level"], f["item"]) for f in failed])
    print("行动项:", [(i["item"], i["level"], str(i["due"])) for i in items])
    print("未复验门禁:", [i["item"] for i in pending_gate(items, today)])
    # 口径：频率按风险分级+随机抽检；验收四层而非「命令跑了」；
    # 失败带 owner+截止日成行动项，下次演练先复验，连续失败触发变更冻结（A133）。
```

**追问**：1) 为什么演练要「随机抽检」而不是每次变更都演练？——每次真实回滚都有切换期流量风险与人力成本；随机抽检让团队无法「提前为演练补预案」（知道哪次要演就会临时抱佛脚），测出的是日常真实能力——与混沌工程的随机注入（A151/A169）同理，可预期演练只能证明「准备过」。2) 「探针通但业务指标没恢复」为什么是真实陷阱？——/healthz 只证明进程活着、端口通，不证明业务正确（回滚后的旧版配置可能让下单链路读不懂新数据）——验收必须挂业务黄金指标而非基础设施指标，这是 A146 变更后验证清单的演练版。3) 演练失败进了行动项，但下月演练又同样失败，说明什么？——行动项只写了「优化回滚脚本」却没落地，或环境已漂移（镜像/参数变了，A187 复盘追问的 dry-run 保鲜问题）——复验门禁 + 连续失败冻结就是让「失败有后果」，否则行动项沦为台账装饰。

## 背诵要点
1. 回滚演练是独立于单次变更的能力建设：区别 A188 发布排序、A208 灰度全量、A187 单单调案验收。
2. 频率按风险分级 + 随机抽检：核心月度全量、重要月度抽检、边缘季度抽检，成本与回滚失败代价权衡。
3. 验收四层全过才 PASS（耗时/流量无损/数据一致/业务指标回归）；失败分级成带 owner 行动项，复验门禁 + 连续失败冻结。

## 复盘追问
1. 演练PASS 但真实事故回滚还是失败，最可能漏了什么？（提示：演练环境≠生产（数据规模/依赖版本不同）+ 演练时没注入真实流量——演练要尽量贴近生产流量与数据，否则只是仪式）
2. 团队嫌「月度全量回滚」影响可用率，只想做 dry-run，怎么权衡？（提示：dry-run 验证命令可执行（A187），但不验证数据兼容与业务指标——分层：dry-run 高频做、真实回滚按风险低频做，两者不可替代）
