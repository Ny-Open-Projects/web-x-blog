### A259 · 灰度分流与流量染色

> 难度:★★★★ | 标签:灰度发布, 流量染色, 稳定分流, contextvars, 回滚闸门

**问**（笔试·场景题）：支付链路要上 `pay-v2`，从 1% 起步逐步放量到 10%，中间随时可能回滚。要求：① 按**用户维度**稳定分流（同一用户在同一档位内恒定同组），未登录时按**设备维度**兜底，登录后不能出现「刚才是新版、刷新变旧版」的体验抖动；② 扩档（1%→5%→10%）必须**只增不减**，一个已经在新版上的用户绝不能被踢回旧版；③ 染色要跨 **RPC / MQ / 线程池 / 协程** 全链路透传，且**不能串色**（A 请求的灰度标记泄漏给 B 请求，是这类系统最典型的生产事故）；④ 回滚要有明确闸门与**动作顺序**，回滚后残留的染色消息必须被判回基线，而不是继续按新版执行。请说清与 A128（分桶稳定性与队列效应）、A245（回滚的统计判定与观测窗口）、Q1251（流量染色的概念）的分工，并给出「取模扩档」为什么必然踢人。

**答**：① 分工：A128 回答「**怎么分才没有偏**」（分桶键选谁、队列效应、多实验分层正交）；A245 回答「**什么时候该回滚**」（双比例检验、观测窗口、样本量与 peeking）；Q1251 是概念层。本题是**实现层**：把「1% 的哪些用户」算出来、把「这单是新版还是旧版」这个事实沿调用链传下去、并在回滚时把在途流量收干净。三者缺一不可：分流有偏则实验结论错，判据不严则误回滚，染色泄漏则**回滚不干净**——最后一类最危险，因为它在监控上表现为「回滚后错误率仍不降」。② 分流的唯一正确姿势是**固定总桶 + 阈值比较**：`bucket = H(flag|salt|key) % 10000`，灰度条件 `bucket < p × 100`。这样 p 从 100 变到 500 时，新集合是旧集合的**超集**，天然满足「不踢人」。反过来，如果按「`% (100/p) == 0`」实现档位：2% 是 `%50==0`、3% 是 `%33==0`，两套模数毫无关系——代码里实测 420 个 2% 用户中 **405 个被踢出** 3% 档。这是「扩档」与「重新洗牌」的区别：换模数、换 salt、换 flag_id 都是**重新洗牌**，只能用于「开一个新实验」，绝不能用于推进同一个实验。③ 分辨率先定死：总桶 10000 意味着最小档位 0.01%，再细就没有意义（1 万用户里 1 个人）。桶数还决定了**同 salt 下的实验容量**——如果同一条链路上有 5 个实验共用 salt，它们的相关性会把「正交」变成「共振」，所以每个实验必须有独立 salt（或把 flag_id 拼进哈希），实测两个 10% 实验的交集 0.95%，接近理论 1%，这才叫正交。④ 多维键的取舍要写进契约：`uid` 优先、`did` 兜底、两者都没有就不进实验（**绝不按请求随机**，那是最常见的「抖动 + 数据污染」源头）。但登录瞬间会发生键切换：匿名时按 did 落在 gray，登录后按 uid 可能落回 baseline。两种策略：**freeze**（设备首次进入时记下分桶键，登录后继续沿用，体验优先，代价是多账号共用设备时会「跟着设备走」）、**user**（以账号为准，归因干净，代价是登录瞬间跳一次组）。本题默认 freeze，并把跳变显式演示出来——因为「体验抖动」比「归因偏差」更难被容忍，且归因可以在分析时按首次曝光口径修正。⑤ 染色的本质是**请求作用域的事实**，不是全局变量，也不是缓存键的一部分。三条铁律：**出站必须带**（RPC header、MQ message property、HTTP header），**入站必须覆盖**（缺 header 时显式置空，而不是「有才 set」），**用完必须 reset**（`finally` 里 reset token）。用 `contextvars` 而不是 `threading.local` 的原因：协程里一个线程跑多个任务，`threading.local` 会串；`contextvars` 随 Task 复制，天然对齐请求边界。但要注意 `ThreadPoolExecutor` **不会**自动复制上下文——裸 submit 读到的永远是 `None`，必须 `copy_context().run` 显式携带；而 `asyncio.to_thread` 与 `run_in_executor` 在新版本里也不自动传播，别想当然。⑥ 串色事故的机理：线程池复用线程，若中间件只在「有 header 时 set」且从不 reset，处理完灰度请求的线程会带着旧 tag 去处理下一个无 header 的请求。后果是「一部分本该走基线的用户莫名进了新版」，而且日志里的 tag 与用户 ID 对不上，排查时人会怀疑分流算法，实际是上下文没清。本题用同一个 `read_tag` 复现了这条链路：不 reset 时第二个请求读到 `'gray#7'`，正确 reset 后读到 `None`。⑦ 回滚的动作顺序比判定更重要：**停推进（不调 percent）→ 摘流量（percent=0，注意桶号不变所以随时可恢复）→ 收在途（MQ 里带旧 tag 的消息要么丢弃、要么强制走基线）→ 冻结版本（改参数不许重新灰）**。第③步最容易被忘：消息可能积压两小时，回滚时队列里还有几万条「gray」消息，消费侧如果信消息里的 tag，就会在回滚后继续跑新版——监控上表现为「回滚无效」。正确做法是消费侧**以当前的灰度状态为准**（tag 只是线索，路由表才是事实），或给消息带上版本号并由消费侧查版本开关。⑧ 还有一个隐蔽污染：**染色值不能进共享缓存 key、DB 唯一键、分布式锁名**。否则灰度期间写进去的 key 会永久带着 `gray` 前缀，回滚后基线流量读不到、重复写入，甚至造成「同一业务实体两条记录」。染色只允许出现在「路由决策」与「指标维度」两处；指标维度也要收敛成 `group=gray|baseline` 这种低基数标签，绝不能把用户级 tag 当 label（基数爆炸，Prometheus 直接被打挂）。

```python
# 全部标准库；固定桶号分流 + 扩档单调 + 设备固化 + contextvars 染色透传 + 回滚闸门
import contextvars
import hashlib
import math
from concurrent.futures import ThreadPoolExecutor

TOTAL = 10000                      # 万分位分辨率：0.01% 一档
TAG = contextvars.ContextVar("gray_tag", default=None)


def bucket_of(flag, salt, key, total=TOTAL):
    """固定总桶数 + 阈值比较：扩档时只增不减，这是「不踢老用户」的唯一正确姿势。"""
    h = hashlib.blake2b(("%s|%s|%s" % (flag, salt, key)).encode("utf-8"),
                        digest_size=8).digest()
    return int.from_bytes(h, "big") % total


class GrayRouter:
    """percent 用百分数（支持 0.1），内部换算成「前 threshold 个桶为灰度」。"""

    def __init__(self, flag, percent=0.0, salt="s1", mode="freeze", total=TOTAL):
        if mode not in ("freeze", "user"):
            raise ValueError("mode 只能是 freeze / user")
        self.flag, self.salt, self.total, self.mode = flag, salt, total, mode
        self.percent = 0.0
        self._frozen = {}                       # did -> 首次进入时用的分桶键
        self.set_percent(percent)

    def set_percent(self, percent):
        if not 0 <= percent <= 100:
            raise ValueError("percent 必须在 [0,100]")
        self.percent = float(percent)
        self.threshold = int(round(percent / 100.0 * self.total))

    # ---------- 分流键：用户优先，设备兜底，冻结模式下设备一旦立约就不再变 ----------
    def resolve_key(self, uid=None, did=None):
        if uid is not None:
            key = "u:%s" % uid
            if self.mode == "freeze" and did is not None:
                return self._frozen.setdefault(did, key)   # 匿名期的约定继续生效
            return key
        if did is not None:
            key = "d:%s" % did
            if self.mode == "freeze":
                self._frozen.setdefault(did, key)
            return key
        return None

    def bucket(self, uid=None, did=None):
        key = self.resolve_key(uid, did)
        return None if key is None else bucket_of(self.flag, self.salt, key, self.total)

    def group(self, uid=None, did=None):
        b = self.bucket(uid, did)
        if b is None:
            return "baseline"                   # 无任何维度：不进实验，绝不按请求随机
        return "gray" if b < self.threshold else "baseline"


class Gate:
    """回滚闸门：只做「连续窗口 + 双显著」的判定，统计细节留给 A245。"""

    def __init__(self, consecutive=2, min_samples=2000, min_abs=0.005, z_crit=3.09):
        self.consecutive, self.min_samples = consecutive, min_samples
        self.min_abs, self.z_crit = min_abs, z_crit
        self.streak = 0

    def observe(self, samples, err, base_err):
        if samples < self.min_samples:
            return "HOLD"                       # 样本不足：没证据不等于没问题
        se = math.sqrt(max(base_err * (1 - base_err), 1e-12) / samples)
        z = (err - base_err) / se if se > 0 else 0.0
        breach = (err - base_err) >= self.min_abs and z >= self.z_crit
        self.streak = self.streak + 1 if breach else 0
        if self.streak >= self.consecutive:
            return "ROLLBACK"
        return "HOLD" if breach else "ADVANCE"


def handle(headers, fn, leak=False):
    """入站请求：染色只在本请求生命周期内有效，必须 reset，否则线程复用即串色。"""
    tag = headers.get("x-gray-tag")
    if leak:
        if tag is not None:                    # 有 header 才 set，且永不 reset
            TAG.set(tag)
        return fn()
    tok = TAG.set(tag)                         # 正常路径：无 header 也要显式置 None
    try:
        return fn()
    finally:
        TAG.reset(tok)


def pool_probe(executor, n=2):
    """线程池默认不继承 contextvars，父上下文的 tag 在新线程里读不到。"""
    return list(executor.map(lambda _: TAG.get(), range(n)))


if __name__ == "__main__":
    # 1) 分流稳定性 + 比例准确：同一个 key 恒定同组，10% 档的占比在统计误差内
    r = GrayRouter("pay-v2", percent=10.0)
    ids = ["u%d" % i for i in range(20000)]
    g1 = [r.group(uid=i) for i in ids]
    g2 = [r.group(uid=i) for i in ids]
    assert g1 == g2
    ratio = g1.count("gray") / len(ids)
    assert 0.093 < ratio < 0.107, ratio
    print("稳定性: 2 万用户重复判定零抖动；10%% 档实际占比 %.2f%% ✅" % (ratio * 100))

    # 2) 扩档单调：1% -> 5% -> 10%，老用户绝不能被踢出实验
    sets = {}
    for p in (1, 5, 10, 50):
        r.set_percent(p)
        sets[p] = {i for i in ids if r.group(uid=i) == "gray"}
    assert sets[1] < sets[5] < sets[10] < sets[50]
    print("扩档单调: |1%%|=%d ⊂ |5%%|=%d ⊂ |10%%|=%d ⊂ |50%%|=%d ✅"
          % (len(sets[1]), len(sets[5]), len(sets[10]), len(sets[50])))

    # 3) 反例：按「100/p 取模」实现档位，扩档会把老用户踢出去（2% -> mod 50，3% -> mod 33）
    old = {i for i in ids if bucket_of("pay-v2", "s1", i) % int(100 / 2) == 0}
    new = {i for i in ids if bucket_of("pay-v2", "s1", i) % int(100 / 3) == 0}
    assert not old <= new
    print("反例: 取模扩档把 %d/%d 个老用户踢出实验（2%% -> 3%%）✅"
          % (len(old - new), len(old)))

    # 4) 加盐隔离：两个实验各取 10%，交集应接近 1%（正交），不是完全重合
    ra = GrayRouter("exp-a", percent=10.0, salt="layer1")
    rb = GrayRouter("exp-b", percent=10.0, salt="layer2")
    both = sum(1 for i in ids
               if ra.group(uid=i) == "gray" and rb.group(uid=i) == "gray")
    share = both / len(ids)
    assert 0.005 < share < 0.016, share
    print("正交: 两个 10%% 实验交集 %.2f%%（理论 1%%）✅" % (share * 100))

    # 5) 登录态跳变：freeze 模式保组，user 模式按用户重算（会跳一次）
    did, uid = "d-777", "u-999"
    fr = GrayRouter("cart", percent=50.0, mode="freeze")
    ur = GrayRouter("cart", percent=50.0, mode="user")
    anon_fr, login_fr = fr.group(did=did), fr.group(uid=uid, did=did)
    assert anon_fr == login_fr
    print("设备固化: 匿名(%s) -> 登录(%s) 不跳变 ✅" % (anon_fr, login_fr))
    jump = None
    for i in range(200):
        u, d = "u-%d" % i, "d-%d" % i
        if ur.group(did=d) != ur.group(uid=u, did=d):
            jump = (ur.group(did=d), ur.group(uid=u, did=d))
            break
    assert jump is not None
    print("用户优先: 未做绑定时会跳变 %s（这就是 freeze 存在的理由）✅" % (jump,))

    # 6) 染色串色：不 reset 时，同一线程的下一个请求会继承上一个请求的 tag
    def read_tag():
        return TAG.get()

    leak1 = handle({"x-gray-tag": "gray#7"}, read_tag, leak=True)
    leak2 = handle({}, read_tag, leak=True)
    ok2 = handle({}, read_tag)
    assert leak1 == "gray#7" and leak2 == "gray#7" and ok2 is None
    print("串色: 不 reset 时无 header 的请求读到 %r；正确 reset 后读到 %r ✅"
          % (leak2, ok2))

    # 7) 线程池透传：默认丢失，copy_context().run 才能带过去
    TAG.set("gray#7")
    with ThreadPoolExecutor(max_workers=2) as ex:
        plain = pool_probe(ex)
        fixed = [ex.submit(contextvars.copy_context().run, read_tag).result()
                 for _ in range(2)]
    assert plain == [None, None] and fixed == ["gray#7", "gray#7"]
    print("线程池: 裸 submit 读到 %s，copy_context().run 读到 %s ✅" % (plain, fixed))
    TAG.set(None)

    # 8) 回滚闸门：样本不足 HOLD、单窗 breach HOLD、连续两窗 ROLLBACK 并摘流量
    g = Gate(consecutive=2, min_samples=2000)
    assert g.observe(100, 0.05, 0.01) == "HOLD"
    assert g.observe(5000, 0.02, 0.01) == "HOLD"
    assert g.observe(5000, 0.02, 0.01) == "ROLLBACK"
    r.set_percent(0)
    assert all(r.group(uid=i) == "baseline" for i in ids[:2000])
    print("回滚: 连续 2 窗显著劣化 -> ROLLBACK，摘流量后 2000 用户全部回 baseline ✅")

    # 9) 回滚后染色必须同步失效，否则灰度逻辑还在后台按旧 tag 走
    disabled = {"gray#7"}
    TAG.set("gray#7")
    routed = "baseline" if TAG.get() in disabled else "gray"
    assert routed == "baseline"
    print("染色清理: tag 进入失效集后，携带旧 tag 的异步任务被判回 baseline ✅")
```

**追问**：1) 为什么不直接把「用户 → 组」存 Redis 查？—— 三个理由：**延迟**（每个请求多一次 RTT，且在核心链路上）、**容量与成本**（千万级用户 × 多实验）、**依赖放大**（分流失效会拖垮全站，而纯函数哈希不依赖任何外部服务）。映射表只用于「必须固化的例外」——设备绑定、白名单、强制分组，且必须带 TTL 与容量上限。这也是所有实验平台的标准做法：**默认无状态计算，例外走覆盖表**。2) 消息队列积压了两小时，回滚时队列里还有几万条灰度消息怎么办？—— 消费侧不能信消息里的 tag，必须以**当前路由表**为准：回滚后 `percent=0`，所有消息都按基线处理，灰度数据由消费逻辑自行丢弃（或按版本号路由到旧实现）。如果业务上必须「消息按产生时的版本执行」，那要在消息里带**不可变的版本号**并保证新旧实现都能读同一份数据——这已经变成兼容性问题，不是染色问题。3) 多机房同时灰度，hash 需要一致吗？—— 需要，而且很容易做到：`H(flag|salt|key)` 是纯函数，只要 salt 与 flag 版本由配置中心统一下发，任何节点算出的组别都相同。真正会出事的是**各机房独立 salt**（比如按 region 加盐做「局部实验」）：用户跨境漫游会跳组，跨机房指标也不可合并。所以 salt 必须全局唯一且带版本，配置变更要像发布一样走灰度。

## 背诵要点
1. 分流的唯一正确姿势是「固定总桶 + 阈值比较」（`bucket < p×10000`），扩档天然单调；换模数、换 salt 是重新洗牌，实测 2%→3% 会踢掉 96% 老用户。
2. 染色三铁律：出站必带、入站必覆盖（没有 header 也要显式置空）、`finally` 里 reset token；线程池要 `copy_context().run`，同一 Task 内的协程自动继承。
3. 回滚顺序：停推进 → 摘流量（percent=0，桶号不变可随时恢复）→ 收在途染色消息 → 冻结版本；消费侧以当前路由表为准，不信消息里的 tag。

## 复盘追问
1. 回滚后错误率不降、日志里还在打灰度 tag，先查哪里？（提示：MQ 在途消息按旧 tag 执行，以及线程池未 copy_context 导致的串色；用 request_id 对齐 tag 与用户即可定位）
2. 同一设备换了账号，freeze 模式会怎样？（提示：跟着设备走，新账号继承旧账号的实验组；要么给绑定关系加时效与多账号策略，要么改 user 模式并接受一次跳变）
