### A145 · 夜间告警升级链

> 难度:★★★ | 标签:升级矩阵, oncall, 场景题

**问**（笔试·场景题）：P0 告警叫醒值班员，15 分钟没响应怎么办（自动升级矩阵的设计：升级给谁/间隔几轮/升级到什么渠道），「叫醒」的成本（夜间误叫的信任损耗）怎么控制（二次确认/多信号合并），升级链的终点是什么（CTO？还是止于团队 lead），升级超时的兜底（值班员手机没电）怎么设计？

**答**：① 升级矩阵设计：P0 → 值班员（push+电话）→ 5 分钟无 ack → 备份值班员 → 5 分钟 → 服务 owner → 5 分钟 → 团队 lead → 15 分钟 → 部门级（值班经理）——每级间隔短（5 分钟），总升级时长 ~30 分钟封顶；**渠道递进**：push → 短信 → 电话（响铃不断直到 ack）——凌晨的 P0 值得电话，P2 不值得。② 叫醒成本控制：**多信号合并**（单条告警不叫人，同根因 ≥2 条或指标持续 2 分钟才触发——防单点抖动夜间误叫）；夜间误叫率进 oncall 健康 KPI（>20% = 告警规则要修，Q7039 联动）——信任损耗的本质是「狼来了」：真事故时响应变慢。③ 升级链终点：**值班经理**（有权拉人/做业务决策）而非 CTO——CTO 被叫醒解决不了问题且不可持续；终点原则：**能做出「下一步正确动作」的人**。④ 兜底：值班员无响应 ≠ 无人处理——升级链本身就是兜底；再加**投递确认**（电话未接/短信未读的通道级失败告警给平台管理员——告警系统的告警）。

```python
# 全部标准库；demo 实现升级矩阵（间隔/渠道递进/终点）
import time

class EscalationPolicy:
    def __init__(self):
        # P0 升级链：(角色, 渠道, 等待分钟)
        self.chain = [
            ("oncall", "phone", 5),
            ("oncall_backup", "phone", 5),
            ("service_owner", "phone+sms", 5),
            ("team_lead", "phone", 15),
            ("duty_manager", "phone", None),      # 终点
        ]
    def escalate(self, alert: dict, ack_after_min: float | None = None) -> list[str]:
        fired, path = [], []
        for role, channel, wait in self.chain:
            fired.append(role)
            path.append(f"呼叫 {role} via {channel}")
            if ack_after_min is not None and ack_after_min <= sum(
                    w for _, _, w in self.chain[:len(path) - 1] if w) + 5:
                break                              # 在该级被 ack
            if wait is None:
                path.append("终点：值班经理接管（拉人/业务决策）")
                break
        return path

def merge_signals(signals: list[dict], window_s: float = 120) -> bool:
    """多信号合并：同根因 ≥2 条或持续 2 分钟才叫人（防单点抖动）。"""
    if len(signals) >= 2:
        return True
    return signals and signals[0].get("duration_s", 0) >= window_s

class DeliveryMonitor:
    """通道级失败兜底：告警系统的告警。"""
    def __init__(self):
        self.failures: list[str] = []
    def report(self, channel: str, delivered: bool):
        if not delivered:
            self.failures.append(f"{time.strftime('%H:%M')} {channel} 投递失败 → 通知平台管理员")

if __name__ == "__main__":
    pol = EscalationPolicy()
    print("15 分钟才 ack 的升级路径:")
    for step in pol.escalate({"name": "db_down"}, ack_after_min=15):
        print("  ", step)
    assert len(pol.escalate({"name": "db_down"})) == 5          # 无人 ack → 走满链到值班经理
    print("多信号合并:", merge_signals([{"n": 1}]), "/", merge_signals([{"n": 1}, {"n": 2}]))
    assert merge_signals([{"n": 1}]) is False and merge_signals([{"n": 1}, {"n": 2}]) is True
    mon = DeliveryMonitor()
    mon.report("phone", delivered=False)
    assert mon.failures
    print("投递失败兜底:", mon.failures[0], "✅")
    # 口径：P0 渠道递进 5 分钟/级、30 分钟封顶到值班经理；多信号合并防误叫；
    # 升级终点=能做下一步正确动作的人；投递失败有兜底告警。
```

**追问**：1) 为什么升级间隔是 5 分钟而不是 1 分钟？——1 分钟内值班员可能正在看（手机解锁/打开笔记本），过早升级造成两人同时响应（混乱+重复操作）；5 分钟平衡「快速恢复」与「单一响应者」——但 P0 的总封顶（30 分钟）限制链路总时长。2) 「值班经理」能解决技术问题吗？（提示：不需要——他解决「组织问题」：拉人（叫醒任何团队成员）、决策（是否停服/降级/赔偿）、资源（开会通道）——技术归 oncall+owner，组织归经理，分工明确）3) 升级链每级「等待时长」在夜间和白天要不同吗？（提示：夜间响应慢（要起床）→ 夜间间隔可放宽（5→8 分钟）但渠道更强（电话必打）；白天聊天工具优先——时段化配置是升级矩阵的成熟做法）

## 背诵要点
1. P0 升级链：值班员→备份→owner→lead→值班经理，5 分钟/级、30 分钟封顶，渠道递进（push→短信→电话）。
2. 叫醒成本控制：多信号合并（≥2 条或持续 2 分钟才叫人）+ 夜间误叫率进 KPI。
3. 升级终点 = 能做下一步正确动作的人（值班经理拉人/决策）；投递失败有兜底告警（告警系统的告警）。

## 复盘追问
1. 一次 P0 值班员 3 分钟就 ack 并处理了，但升级链已经叫醒了备份——怎么减少这种「双叫」？（提示：升级触发与 ack 传播的延迟竞争——ack 状态实时同步到升级调度器（ack 后立即取消后续级）+ 首级等待略拉长给 ack 留窗口）
2. 团队拒绝把 P0 升级到值班经理（「我们自己能搞定」），风险是什么？（提示：单点依赖值班员的手机与状态（没电/睡着了=全站无人管）；升级链是保险不是不信任——「叫醒经理」的成本远低于「30 分钟无人处置资损事故」）
