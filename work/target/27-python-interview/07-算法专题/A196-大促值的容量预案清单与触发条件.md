### A196 · 大促预案清单

> 难度:★★★ | 标签:大促, 预案, 场景题

**问**（笔试·场景题）：大促预案文档 20 页但事故时没人翻——预案的「可执行性」标准（触发条件量化/执行步骤命令化/执行人到人），预案的「触发条件」怎么写才不依赖人的判断（指标+阈值+持续时长三要素），预案间冲突（两个预案同时触发打架）怎么协调（预案编排/优先级），预案演练的「分层验证」（单预案演练 vs 全链路推演）怎么安排？

**答**：① 可执行性三标准：**触发条件量化**（「错误率 >5% 持续 3 分钟」——不是「明显异常时」）、**步骤命令化**（具体命令/开关位置/执行脚本——不是「进行降级」）、**执行人到人**（大促值班矩阵里写死执行人（A187 特编梯队），不写「值班同学」）——三标准同 Q189 回滚预案验收。② 触发条件三要素：指标+阈值+持续时长（防瞬时抖动误触发，A110 迟滞同构）——条件由「历史故障复盘」反推（上次故障的指标特征），不是拍脑袋。③ 预案冲突协调：预案声明「前置条件与互斥」（预案 A（降级缓存）与预案 B（直连 DB）互斥——同时触发选优先级高的）+ 编排层（预案间依赖：A 触发后 B 自动抑制——Q7039 抑制语义同构）。④ 演练分层：单预案演练（每预案单独验证可执行性）+ 全链路推演（桌面推演：多预案并发场景的决策流）+ 真实演练（影子流量触发，Q151 混沌）——频率递减但都要做。

```python
# 全部标准库；demo 实现「预案触发引擎（量化条件+冲突协调）」
import time

PLANS = [
    {"name": "缓存降级", "metric": "cache_err_rate", "th": 0.05, "hold_s": 180,
     "mutex": "db_direct", "priority": 2, "owner": "cache-oncall"},
    {"name": "db_direct", "metric": "db_err_rate", "th": 0.10, "hold_s": 180,
     "mutex": "cache_err", "priority": 1, "owner": "dba"},
]

class PlanEngine:
    def __init__(self, plans: list[dict]):
        self.plans = plans
        self.active: dict[str, float] = {}     # plan -> 触发时刻（hold 计时）
        self.log: list[str] = []
    def evaluate(self, metrics: dict) -> list[str]:
        triggered = []
        for p in self.plans:
            v = metrics.get(p["metric"], 0)
            if v >= p["th"]:
                if p["name"] not in self.active:
                    self.active[p["name"]] = time.monotonic()   # 开始 hold 计时
                elif time.monotonic() - self.active[p["name"]] >= p["hold_s"]:
                    triggered.append(p)         # 持续时长达成 → 触发
            else:
                self.active.pop(p["name"], None)                 # 恢复，hold 清零
        # 冲突协调：互斥预案都触发 → 优先级高者执行，低者抑制
        winners = []
        for p in sorted(triggered, key=lambda x: x["priority"]):
            if any(x["name"] in p.get("mutex", "") for x in winners):
                self.log.append(f"抑制 {p['name']}（与 {winners[-1]['name']} 互斥，优先级低）")
            else:
                winners.append(p)
        return [f"执行 {p['name']}（owner: {p['owner']}）" for p in winners] + self.log

if __name__ == "__main__":
    eng = PlanEngine(PLANS)
    for _ in range(3):                          # 3 次评估模拟 180s hold
        out = eng.evaluate({"cache_err_rate": 0.08, "db_err_rate": 0.15})
    print("最终触发:", out)
    assert any("db_direct" in o for o in out)   # 优先级 1 的 db_direct 执行
    assert any("抑制" in o for o in out)        # 缓存降级被抑制 ✅
    # 口径：触发=指标+阈值+持续时长三要素；互斥预案按优先级协调；
    # 执行人到人（owner 字段）；演练三层：单预案/桌面推演/真实触发。
```

**追问**：1) 为什么触发条件必须「三要素」（指标+阈值+时长）？——缺时长=瞬时抖动误触发（每分钟乱执行）；缺阈值量化=靠人判断（半夜判断力差）；三要素让触发可自动化——预案自动化执行的前提是条件无歧义。2) 「互斥预案优先级」怎么定才公平？（提示：按「影响的业务关键度+资源代价」排（db_direct 保核心但耗资源、cache 降级轻量）——优先级在预案评审时定（冷静时刻），不是事故时临时拍板——同 Q171 审批分级前置逻辑）3) 20 页预案文档怎么压缩到「可用」？（提示：正文=预案卡片（触发/步骤/owner 一页一个）+ 背景/原理放附录——值班要的是「卡片」不是「论文」；文档分层（Q168 文档即代码边界））

## 背诵要点
1. 预案可执行性三标准：触发条件量化（三要素）/步骤命令化/执行人到人——20 页文档压成一页卡片。
2. 触发三要素（指标+阈值+持续时长）自动化执行；互斥预案按优先级协调（评审时定级）。
3. 演练三层：单预案验证 / 桌面推演（多预案决策流）/ 真实触发（影子流量）——频率递减都要做。

## 复盘追问
1. 预案触发了但执行人「没看到」（值班忙别的事），怎么保证预案被执行？（提示：预案触发=告警直达 owner（A166 路由矩阵）+ 执行确认闭环（触发后 5 分钟未确认升级）——「触发即通知+未确认即升级」是执行到人的保障）
2. 预案清单越来越长（50 个预案），互相之间关系复杂到没人理得清——怎么治理？（提示：预案也做归并（同根因的预案合并）+ 依赖图可视化（互斥/前置关系画出来）+ 长期未触发未演练的预案进过期审查（Q168）——预案库与代码一样需要治理）
