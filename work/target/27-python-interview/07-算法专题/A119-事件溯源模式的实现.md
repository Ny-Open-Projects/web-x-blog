### A119 · 事件溯源与投影重建

> 难度:★★★ | 标签:事件溯源, CQRS, 场景题

**问**（笔试·编程+场景题）：用事件溯源实现账户余额系统：只存事件（存入/取出/透传手续费），余额是投影（replay 算出来）——「当前状态查询」为什么不能每次 replay？快照（snapshot）怎么插进事件流，事件 schema 演进（新增字段/改语义）怎么兼容，和「状态表+审计日志」方案相比什么时候值得上事件溯源？

**答**：① 查询性能：replay 全量事件是 O(事件数)，查询频繁时不可行——**快照**：每 N 个事件存一次状态快照，查询 = 最近快照 + 之后的少量事件重放（O(N mod snapshot_interval)）；快照本身是派生数据可随时重建（损坏无妨）。② 事件 schema 演进：**加字段要带默认值/可缺省**（旧事件没有新字段，投影处理时给默认）、**改语义必须新事件类型**（`fee_changed_v2`，绝不改旧事件含义——旧事件是历史事实不可变）、投影代码版本化（同一事件流可以有多种投影并存）。③ 事件溯源 vs 状态表+审计日志的选型：需要**时间旅行/多投影/审计即业务**（金融对账、风控回放）→ 事件溯源值得；普通 CRUD + 审计需求 → 状态表+审计日志简单 10 倍。判据：**你是否真的会读历史**——只写不读的事件流是负担不是资产。

```python
# 全部标准库；demo 实现事件流 + 快照重建 + schema 演进兼容
import json, time

class AccountStream:
    def __init__(self, snapshot_every: int = 3):
        self.events: list[dict] = []
        self.snapshots: dict[int, dict] = {}    # 事件序号 -> 快照
        self.every = snapshot_every
    def append(self, etype: str, **payload):
        ev = {"seq": len(self.events), "ts": time.time(), "type": etype, **payload}
        self.events.append(ev)
        if len(self.events) % self.every == 0:
            self.snapshots[len(self.events)] = self._rebuild(len(self.events), use_snapshots=False)
        return ev
    def _apply(self, state: dict, ev: dict) -> dict:
        """单事件应用（投影逻辑）；schema 演进兼容在此处理。"""
        state = dict(state)
        if ev["type"] == "deposit":
            state["balance"] = state.get("balance", 0) + ev["amount"]
        elif ev["type"] == "withdraw":
            state["balance"] = state.get("balance", 0) - ev["amount"]
        elif ev["type"] == "fee_charged":        # v2 新事件类型（不改旧语义）
            state["balance"] = state.get("balance", 0) - ev.get("fee", 0)
        # 旧事件缺字段给默认值（加字段兼容口径）
        if "currency" not in ev:
            state.setdefault("currency", "CNY")
        return state
    def _rebuild(self, upto: int, use_snapshots: bool = True) -> dict:
        """快照 + 事件重放：O(快照间隔) 而非 O(全量)。"""
        state = {}
        start = 0
        if use_snapshots:
            for seq in sorted(self.snapshots, reverse=True):
                if seq <= upto:
                    state = dict(self.snapshots[seq]); start = seq
                    break
        for ev in self.events[start:upto]:
            state = self._apply(state, ev)
        return state
    def balance(self) -> dict:
        return self._rebuild(len(self.events))    # 查询 = 快照 + 尾部重放

if __name__ == "__main__":
    a = AccountStream(snapshot_every=3)
    a.append("deposit", amount=100)
    a.append("withdraw", amount=30)
    a.append("deposit", amount=20)               # seq=3 触发快照
    a.append("fee_charged", fee=5)               # v2 新事件
    a.append("withdraw", amount=10)
    cur = a.balance()
    assert cur["balance"] == 100 - 30 + 20 - 5 - 10 == 75
    print("余额投影:", cur, "（快照+尾部重放，非全量 replay）✅")
    # 时间旅行：第 3 个事件时刻的余额
    past = a._rebuild(3)
    assert past["balance"] == 90
    print("时间旅行（seq=3 时余额 90）✅ —— 事件溯源的核心能力")
    # 演进口径：加字段给默认、改语义开新事件类型、投影代码版本化并存。
```

**追问**：1) 快照损坏怎么办？——快照是派生数据：删除后从事件流全量重建即可（这正是事件溯源的恢复语义）；快照存储失败不阻塞写入（降级为无快照查询，变慢不变错）。2) 事件的「消费侧」投影和查询侧快照什么关系？——同一事件流多个投影（余额/风控画像/对账明细）各自维护游标（同 Q7017 水位），快照只是余额投影的查询优化——投影多≠快照多。3) 什么情况下事件溯源是过度设计？——无时间旅行需求、事件类型少且稳定、团队无 CQRS 经验——事件溯源的复杂度税（schema 演进纪律/投影游标管理）远高于审计日志方案；判据是「真的会读历史」。

## 背诵要点
1. 查询 = 最近快照 + 尾部事件重放（O(间隔) 而非 O(全量)）；快照是派生数据，损坏可重建不阻塞写入。
2. schema 演进：加字段带默认、改语义开新事件类型（旧事件是历史事实不可变）、投影版本化并存。
3. 选型判据「真的会读历史」：时间旅行/多投影/审计即业务才上事件溯源，否则状态表+审计日志简单 10 倍。
