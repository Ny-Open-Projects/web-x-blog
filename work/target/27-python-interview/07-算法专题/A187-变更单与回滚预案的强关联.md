### A187 · 回滚预案强关联

> 难度:★★☆ | 标签:回滚, 变更单, 治理

**问**（笔试·编程+场景题）：变更单里「回滚方案」一栏永远写着「回滚到上一版本」——这种废话预案怎么治理（回滚方案的验收标准：可执行/已验证/时间可估），「预案演练」怎么强制（变更单里回滚命令的 dry-run），「回滚时长」的估算与事故 RTO 的关系（预案时长 > 事故容忍 = 预案无效），配置类变更的回滚预案（配置回滚 ≠ 代码回滚）怎么单独要求？

**答**：① 废话预案治理：回滚方案三验收——**可执行**（具体命令/开关位置，不是「回滚到上一版本」这种描述）、**已验证**（dry-run 通过：回滚命令在预发跑过——从未执行的回滚命令是祈祷）、**时间可估**（回滚分钟数 ≤ 事故容忍时间——超容忍的预案=无效预案，要改方案不是改数字）。② 演练强制：变更单提交时 CI 跑「回滚 dry-run」（回滚命令在预发环境实际执行一遍——失败的变更单拒绝提交）——dry-run 成本（预发跑一次分钟级）vs 事故时发现回滚不工作的代价——不对称风险强制演练。③ 回滚时长 vs RTO：变更单声明预估回滚时长，与该服务的「事故容忍时间」（SLA 推导）比对——回滚 30 分钟但服务容忍 10 分钟 = 预案无效，需改发布方式（蓝绿/金丝雀使回滚秒级）。④ 配置类变更单独要求：配置回滚 ≠ 代码回滚（配置回滚可能涉及数据兼容——A108 双写、参数联动）——配置变更单的回滚预案要包含「配置回滚后的数据/行为验证步骤」。

```python
# 全部标准库；demo 实现「回滚预案验收器」
import re, time

GENERIC = re.compile(r"回滚到上一(版本|配置)|待定|TBD")

def validate_rollback_plan(plan: dict, service_rto_min: float) -> list[str]:
    """回滚预案三验收：可执行/已验证/时间可估。"""
    issues = []
    plan_text = plan.get("rollback_plan", "")
    if not plan_text or GENERIC.search(plan_text):
        issues.append("预案是废话（模板语句/待定）——需要具体命令与开关位置")
    if not plan.get("dry_run_passed"):
        issues.append("回滚命令未 dry-run（从未执行的回滚是祈祷）")
    est = plan.get("estimated_minutes", 9999)
    if est > service_rto_min:
        issues.append(f"回滚时长 {est}min > 事故容忍 {service_rto_min}min → 预案无效，改发布方式")
    if plan.get("kind") == "config" and "data_check" not in plan_text:
        issues.append("配置回滚缺数据/行为验证步骤（配置回滚≠代码回滚）")
    return issues

if __name__ == "__main__":
    bad = {"rollback_plan": "回滚到上一版本", "dry_run_passed": False,
           "estimated_minutes": 30, "kind": "code"}
    good = {"rollback_plan": "helm rollback order-svc --version -1; 验证: curl /healthz",
            "dry_run_passed": True, "estimated_minutes": 3, "kind": "code"}
    cfg_bad = {"rollback_plan": "console 恢复 rate_limit=100; data_check: 对账订单量",
               "dry_run_passed": True, "estimated_minutes": 2, "kind": "config"}
    for p, name in ((bad, "废话预案"), (good, "合格预案"), (cfg_bad, "缺数据验证的配置预案")):
        issues = validate_rollback_plan(p, service_rto_min=10)
        print(f"{name}: {issues or '通过'}")
    assert validate_rollback_plan(bad, 10)
    assert not validate_rollback_plan(good, 10)
    assert any("配置" in i for i in validate_rollback_plan(cfg_bad, 10))
    print("三验收（可执行/已验证/时间可估）+ 配置特殊要求 全部生效 ✅")
    # 口径：废话预案 CI 拒绝；dry-run 强制；时长>容忍=改发布方式（蓝绿/金丝雀）；
    # 配置回滚单独要求数据验证步骤。
```

**追问**：1) 为什么「从未执行的回滚命令是祈祷」？——回滚命令依赖的环境（镜像存在/参数正确/权限有效）从未验证过——事故时才第一次跑，任何一步失败都在放大故障；dry-run 把「祈祷」变「验证」——成本分钟级，收益是回滚确定性。2) 「回滚时长 > 事故容忍 → 改发布方式」的选项？（提示：蓝绿部署（回滚=切流量秒级）/金丝雀（影响面小回滚快）/灰度 flag（A118 秒回）——「回滚慢」的解法是换发布方式不是把数字改小——时长估算暴露的是架构问题）3) 配置回滚为什么需要「数据/行为验证步骤」？（提示：配置回滚可能引发行为变化（限流阈值回退→流量冲击）或数据兼容问题（格式开关回退后新数据读不懂，A108）——配置回滚是「行为变更」不只是「参数还原」——验证步骤保证回滚后系统一致）

## 背诵要点
1. 回滚预案三验收：可执行（具体命令）、已验证（dry-run 强制）、时间可估（≤事故容忍时间）——废话预案 CI 拒绝。
2. 回滚时长 > 事故容忍 = 预案无效 → 改发布方式（蓝绿/金丝雀/flag 秒回），不是改数字。
3. 配置回滚 ≠ 代码回滚：需数据/行为验证步骤（配置回滚是行为变更）。

## 复盘追问
1. 事故中按预案回滚了，但发现「预案的 dry-run 是三个月前做的」（环境已变），预案还是失效了——dry-run 的保鲜机制？（提示：dry-run 随每次变更单跑（不是一次性）+ 预案与环境的关联校验（镜像/参数存在性）——预案保鲜=与变更流绑定（A143 自动变更单同构），漂移即过期）
2. 「服务容忍时间」怎么从 SLA 推导出来？（提示：容忍时间 = 错误预算（Q179）按当前流量折算的可容忍 downtime——SLO 99.9% 月预算 43 分钟——回滚 30 分钟意味着一次回滚吃掉大半预算；容忍时间的动态化（预算剩余多少就容忍多久）是进阶做法）
