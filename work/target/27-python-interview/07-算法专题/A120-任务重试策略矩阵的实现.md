### A120 · 重试策略矩阵

> 难度:★★☆ | 标签:重试, 退避, 可靠性

**问**（笔试·编程+场景题）：实现一个可配置重试器：指数退避+全抖动（full jitter）、可重试错误白名单、重试预算（联动 A101）、幂等前提检查（非幂等操作禁止自动重试）。「重试风暴」和「重试不足」的边界怎么量化——什么时候该承认失败而不是再试一次？

**答**：① 全抖动公式：`sleep = random(0, min(cap, base × 2^attempt))`——比「固定退避+小抖动」更能打散同步重试（AWS 经验口径）；退避基值与上限按下游恢复时间定（cap 常为探测到的恢复周期）。② 可重试白名单：**错误分类决定重试与否**——超时/连接类可重试，4xx 业务错误不可重试（重试也是同样结果），5xx 可重试（下游自身问题）但要看 Retry-After（Q5518）；**非幂等操作（POST 创建类）默认禁自动重试**，除非携带幂等键（A102）——盲目重试非幂等操作 = 重复下单。③ 预算：调用方重试次数 × 并发调用方数 ≤ 下游承受余量——全局预算（A101）而非每调用者独立预算；预算耗尽 = 快速失败（这是「承认失败」的量化边界：预算空 + 错误率超阈 + 无 Retry-After 引导 = 停）。④ 量化边界：重试充足 = 重试成功率高且总成功率 ≈ 理论可达；重试不足 = 首次失败后直接放弃的比例高但下游其实已恢复；监控「重试成功率」和「放弃后下游恢复时间分布」校准。

```python
# 全部标准库；demo 实现 Retryer（全抖动+白名单+预算+幂等检查）
import random, time

RETRYABLE = ("timeout", "connection", "5xx", "throttle")

class Retryer:
    def __init__(self, base: float = 0.05, cap: float = 1.0, max_attempts: int = 4,
                 budget: float = 10.0, idempotent: bool = False):
        self.base, self.cap, self.max_attempts, self.idempotent = base, cap, max_attempts, idempotent
        self.budget_left = budget               # 全局预算（秒级等待预算，简化口径）
    def run(self, op, op_id: str = "") -> tuple[str, object]:
        if not self.idempotent and op_id == "": # 非幂等操作必须有幂等键才允许重试
            pass                                 # demo：幂等检查不阻塞首次执行，重试时拦截
        last_err = None
        for attempt in range(self.max_attempts):
            try:
                return "ok", op()
            except Exception as e:
                last_err = str(e)
                if not any(k in last_err for k in RETRYABLE):
                    return "fatal", last_err     # 白名单外：立即放弃
                if attempt > 0 and not self.idempotent and not op_id:
                    return "no-retry-non-idempotent", last_err   # 幂等闸
                if self.budget_left <= 0:
                    return "budget-exhausted", last_err          # 预算闸：承认失败
                sleep = random.uniform(0, min(self.cap, self.base * 2 ** attempt))
                if sleep > self.budget_left:
                    return "budget-exhausted", last_err
                self.budget_left -= sleep
                time.sleep(sleep)
        return "exhausted", last_err

def make_flaky(succeed_at: int, counter: dict):
    def op():
        counter["n"] += 1
        if counter["n"] < succeed_at:
            raise Exception(f"timeout attempt {counter['n']}")
        return "result"
    return op

if __name__ == "__main__":
    random.seed(7)
    r = Retryer(idempotent=True)
    c = {"n": 0}
    status, result = r.run(make_flaky(3, c))
    assert status == "ok" and result == "result" and c["n"] == 3
    print(f"全抖动重试：第 {c['n']} 次成功 ✅")
    # 非幂等闸：无幂等键的重试被拒
    r2 = Retryer(idempotent=False)
    c2 = {"n": 0}
    status2, msg2 = r2.run(make_flaky(999, c2))     # 永远失败
    assert status2 == "no-retry-non-idempotent" and c2["n"] == 1
    print(f"非幂等操作只执行 1 次（无幂等键禁止重试）✅")
    # 业务错误立即放弃
    def bad_req():
        raise Exception("400 invalid param")
    r3 = Retryer(idempotent=True)
    status3, _ = r3.run(bad_req)
    assert status3 == "fatal"
    print("白名单外错误立即放弃（fatal）✅")
    # 口径：全抖动 random(0, min(cap, base×2^n))；预算耗尽=承认失败；
    # 重试安全性 = 幂等键前置。
```

**追问**：1) full jitter 为什么优于 equal jitter（`d/2 + random(d/2)`）？——full 让重试在 [0, d] 均匀散开，多调用方完全去同步；equal 保留半固定间隔仍会形成节拍共振——AWS 实测 full 的总完成时间最优。2) 「重试预算」和 A101 限流的区别？——限流管「正常流量入口」（主动控制），重试预算管「故障时的放大系数」（被动兜底）；两者数值要联动：预算 ≈ 下游正常容量 × 可接受放大率（常 20%）。3) 什么信号说明「该承认失败」而非继续试？——预算空、错误率持续超阈（下游系统性劣化）、连续多次重试错误类型相同（不是偶发抖动）——三条件任一即可停，避免「再试最后一次」的沉没成本谬误。

## 背诵要点
1. 全抖动 `random(0, min(cap, base×2^attempt))` 完全去同步；错误白名单决定重试资格。
2. 非幂等操作禁自动重试（除非幂等键，A102）；业务 4xx 立即放弃不重试。
3. 承认失败的量化边界：预算空 / 错误率超阈 / 同型错误连续——三条件任一即停。

## 复盘追问
1. 你的重试器在下游 30 秒恢复后成功率回到 95%，但用户已经流失——重试参数哪里错了？（提示：cap/总时长超过用户耐心（同步场景总重试时长应 < 用户等待预算）；异步场景 cap 才能放长）
2. 重试成功了但结果不对（下游处理了两次但返回同一个响应），这是哪层问题？（提示：下游不幂等但返回幂等假象——重试成功≠业务正确，幂等键必须在请求里让下游去重，A102）
