### A209 · 资源隔离四层

> 难度:★★☆ | 标签:资源隔离, 混部, 架构

**问**（笔试·编程+场景题）：「隔离」在架构里有四层实现——物理隔离（独立集群）、进程隔离（独立进程/容器）、线程/协程隔离（线程池划分）、逻辑隔离（配额/优先级/权重），各挡什么、成本梯度、什么场景用哪层（「线程池划分」为什么对 CPU 密集任务无效——GIL），隔离层的「穿透」风险（共享资源在层下漏过去——缓存/连接池/时钟）怎么查？

**答**：① 四层梯度：**物理**（不同集群/机器——最贵最彻底，挡一切包括硬件故障）、**进程/容器**（cgroup 限额——挡 CPU/内存，共享内核与 IO 有漏）、**线程/协程池**（划分并发额度——挡并发竞争，GIL 下对 CPU 密集无效（A122 混部）、IO 密集有效）、**逻辑**（配额/优先级/权重——最便宜，挡的是「分配不公」不是「资源竞争」）。② 选型规则：故障爆炸半径大 → 物理隔离；资源竞争激烈 → 进程/cgroup；并发额度公平 → 池划分；只是优先级问题 → 逻辑配额。③ 穿透排查：四层之下的共享资源常常穿透隔离——**缓存**（多租户共享 Redis，热租户挤占——Q6518 分实例）、**连接池**（共享池被慢租户占满——Q6512 分池）、**时钟/随机数**（全局单例——测试污染 Q7186）、**事件循环**（共享 loop 一个慢任务全停——Q122）。排查方法：画「资源清单 × 隔离层」矩阵，逐格确认「这层隔离挡不挡这个资源」。

```python
# 全部标准库；demo 实现「隔离矩阵审计」
ISOLATION_MATRIX = {
    # 资源 -> 各层是否有效隔离（True=该层挡得住）
    "CPU": {"physical": True, "container": True, "pool": False, "logical": False},
    "memory": {"physical": True, "container": True, "pool": False, "logical": False},
    "disk_io": {"physical": True, "container": False, "pool": False, "logical": False},
    "network": {"physical": True, "container": False, "pool": False, "logical": False},
    "cache": {"physical": True, "container": False, "pool": False, "logical": False},
    "conn_pool": {"physical": True, "container": True, "pool": True, "logical": False},
}

def audit_isolation(resources: list[str], layers_used: list[str]) -> list[str]:
    """审计：所用隔离层对该资源是否有效（穿透即告警）。"""
    gaps = []
    for r in resources:
        effective = [l for l in layers_used if ISOLATION_MATRIX.get(r, {}).get(l)]
        if not effective:
            gaps.append(f"{r}: 现有隔离层 {layers_used} 全部穿透——需升级隔离层")
    return gaps

def pool_isolation_example():
    """池划分正确用法：IO 密集任务线程池隔离（GIL 下 CPU 密集无效）。"""
    return {
        "io_pool": "requests/db 查询用 —— 线程池隔离有效（等待释放 GIL）",
        "cpu_pool": "重计算用进程池 —— 线程池隔离无效（GIL 串行，Q122）",
    }

if __name__ == "__main__":
    gaps = audit_isolation(["cache", "disk_io"], layers_used=["container", "pool"])
    for g in gaps:
        print("穿透告警:", g)
    assert len(gaps) == 2
    print(pool_isolation_example())
    # 口径：四层梯度（物理>容器>池>逻辑）各挡不同资源；
    # 「资源×隔离层」矩阵审计穿透——缓存/连接池是最常被漏的两格。
```

**追问**：1) 为什么「线程池划分」对 CPU 密集任务无效？——GIL 下线程池隔离只隔离「并发额度」，CPU 计算仍串行（一个池的满载计算抢走 GIL，另一个池照样慢）；CPU 密集隔离要用进程池（真并行）或 cgroup——「池隔离 ≠ 资源隔离」，池隔离的是调度不是算力。2) 「连接池共享」穿透的典型事故？（提示：慢租户的慢查询占满共享池 → 其他租户排队等连接（Q6512 连接池耗尽）——分池（每租户/每等级独立池+各自上限）或按租户加权；共享池的公平性问题在「池」这一层无解，要靠更上层隔离）3) 「逻辑隔离」（配额）什么时候就够？（提示：资源竞争不存在时（总量远小于容量）——配额只是「分配规则」不是「保护机制」；资源紧张时逻辑配额挡不住竞争（大家都超配额用），需要升级到容器/物理层——配额是「公平工具」不是「防护墙」）

## 背诵要点
1. 四层梯度：物理（挡一切）> 容器（CPU/内存）> 池（并发额度，GIL 下 CPU 密集无效）> 逻辑（配额=公平工具非防护墙）。
2. 选型按爆炸半径：故障大→物理，资源竞争→cgroup，公平→池/配额。
3. 穿透排查 = 「资源×隔离层」矩阵逐格审计——缓存/连接池是最常被漏的两格。

## 复盘追问
1. 团队说「我们已经做了逻辑配额隔离」，但慢租户还是拖垮了服务——审计矩阵会指出什么？（提示：逻辑配额对「资源竞争」穿透（矩阵：logical 全 False）——配额限的是「请求发放」不限「资源占用」；真正要的是容器级隔离（cgroup）——「做了隔离」与「隔离有效」是两件事，矩阵审计区分它们）
2. 多个业务共用一个 asyncio 事件循环，隔离怎么实现？（提示：事件循环无法池隔离（单线程本质，Q122）——隔离手段：多 loop 多线程（每线程独立 loop，Q122 多 loop 分片）或多进程——loop 内「慢回调拖全队」无池可解，只能从回调本身治理（分片/限时长，Q5560））
