### A183 · 状态页与对外公告

> 难度:★★☆ | 标签:状态页, 沟通, 事故响应

**问**（笔试·场景题）：故障发生 5 分钟——对外公告什么时候发（等根因明确还是立即说「知道了」），状态页的标准更新节奏（首次/进展/解决三段各写什么），「公告里的时间承诺」怎么写（说「1 小时恢复」结果 3 小时，信誉损失比故障本身大），事故后的事后报告（postmortem 公开版）写什么不写什么？

**答**：① 公告节奏：**10 分钟内首条**（「我们已发现问题正在调查」——不用等根因，让用户知道「我们知道」）、之后每 30 分钟进展、恢复后「已解决+复盘报告链接」——沉默的 30 分钟里社交媒体会替你写故事（猜测性传播比事实伤害大）。② 内容纪律：**不写时间承诺**（说「正在积极修复」不说「预计 1 小时」——估算不可靠，承诺跳票的双倍信誉损失）、不猜根因（说「部分服务受影响」不说「数据库问题」——猜错了再改口更糟）、不隐瞒影响面（受影响的功能/数据明确列出）。③ 事后报告（公开版）：时间线（分钟级）、影响面（哪些功能/多少用户/多长时间）、根因（系统层）、修复与预防措施（行动项）——**不写**：个人责任（blameless，Q138）、内部敏感信息（架构细节给攻击者递刀）、未验证的猜测。④ 状态页本身的高可用：状态页要独立部署（独立域名/独立基础设施——主站挂了状态页必须活着，否则「故障了连状态页都打不开」是二次事故）。

```python
# 全部标准库；demo 实现「公告发布器 + 时间承诺禁用检查」
import re, time

BANNED_PATTERNS = [
    (re.compile(r"预计.{0,6}(恢复|修复)"), "时间承诺（跳票双倍信誉损失）"),
    (re.compile(r"（?可能是|应该?是）.{0,20}(问题|故障)"), "未验证的根因猜测"),
]

def publish_check(body: str) -> list[str]:
    issues = []
    for pat, reason in BANNED_PATTERNS:
        if pat.search(body):
            issues.append(reason)
    return issues

STATUS_UPDATE_TEMPLATE = {
    "initial": "我们检测到部分服务异常，团队已介入调查。受影响功能：{services}。下一步更新时间：{next_update}。",
    "progress": "调查进行中。已定位到影响范围：{scope}。缓解措施：{mitigation}。下一步更新时间：{next_update}。",
    "resolved": "服务已全部恢复。影响窗口：{window}。事后报告：{postmortem_link}。",
}

def make_update(kind: str, **ctx) -> str:
    body = STATUS_UPDATE_TEMPLATE[kind].format(**ctx)
    issues = publish_check(body)
    assert not issues, f"公告违规: {issues}（承诺/猜测禁用）"
    return body

if __name__ == "__main__":
    first = make_update("initial", services="订单查询、支付回调", next_update="30 分钟后")
    print("首条公告（10 分钟内）:", first)
    # 违规示例检测
    try:
        make_update("progress", scope="支付服务", mitigation="切换备用通道",
                    next_update="预计 1 小时恢复")          # 含时间承诺
    except AssertionError as e:
        print("违规拦截:", e, "✅")
    resolved = make_update("resolved", window="14:02-14:47",
                           postmortem_link="status.example.com/incidents/101")
    print("解决公告:", resolved)
    # 口径：10 分钟首条+30 分钟节奏；禁时间承诺/禁根因猜测/隐瞒影响面；
    # postmortem 公开版四件套（时间线/影响/根因/预防），不写个人责任。
```

**追问**：1) 为什么「预计 1 小时恢复」是双倍信誉损失？——估算不可靠（复杂故障修复时间方差极大），跳票后用户的第二次失望比首次故障更伤信任（第一次是能力问题，跳票是态度问题）；写「下一步更新时间」（承诺沟通节奏而非修复结果）是可控承诺。2) 状态页独立部署的「独立」到什么程度？（提示：独立域名（status.xxx.com 不受主域 DNS 故障影响）+ 独立供应商（不同云/不同 CDN——同云故障时状态页也挂）+ 静态化（状态页本身零依赖）——三层独立，A113 容灾口径的状态页版）3) postmortem 公开版「不写内部架构细节」的边界？（提示：写「某数据库组件的配置问题」不写「PostgreSQL 15.2 的 pg_hba.conf 第 3 行」——透明针对影响与修复，不递刀给攻击者；安全类事故的根因更要模糊化（攻击者看公告学攻击））

## 背诵要点
1. 公告节奏：10 分钟首条（「已知悉」）→ 30 分钟进展 → 解决+复盘链接——沉默 30 分钟社媒替你写故事。
2. 内容三禁：时间承诺（跳票双倍信誉损失）/未验证根因猜测/隐瞒影响面；写「下一步更新时间」写可控承诺。
3. postmortem 公开版四件套（时间线/影响/根因/预防）不写个人责任与架构细节；状态页三层独立部署。

## 复盘追问
1. 故障是客户自己网络问题导致的（我方无责），状态页要不要发公告？（提示：要——「监测到部分客户访问异常，经排查为客户侧网络问题」——不发公告客户以为是我方故障（投诉照来）；公告也是免责记录（SLA 口径，Q144 联动））
2. 状态页显示「一切正常」但用户疯狂投诉——状态页与真实状态脱节怎么防？（提示：状态页组件状态必须由探针自动驱动（Q7019 合成监控接入）而非人工手改——人工更新会有延迟与遗漏；自动+人工确认的混合模式）
