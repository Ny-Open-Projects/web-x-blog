### A250 · 大促容量预案与降级编排

> 难度:★★★★★ | 标签:容量模型, 降级阶梯, 滞回, 大促

**问**（笔试·场景题）：双十一级大促，预估峰值是日常的 8-10 倍。请给出容量预案与降级编排：① **容量模型**——从日常峰值推出实例数，公式里每个系数代表什么，单机安全水位怎么定；② **瓶颈在哪一层**——为什么「CPU 打满」经常不是第一个崩的，用 Little 定律说明连接数怎么先炸；③ **降级阶梯**——L1 到 L5 每级降什么、影响面多大、用什么指标触发、哪些能自动、恢复条件是什么；④ **编排的三个坑**——降级项互相影响、指标失真、自动降级震荡，各怎么解；⑤ **演练与验收**——容量演练和降级演练分别怎么跑，验收口径怎么写。请与 A242（压测方案与验收）、A241（多租户配额仲裁）、Q1238（容量估算模型）区分开，本题重点在**编排**：什么时候降、降多深、怎么退回来。

**答**：① 与已有卡的分工：A106 给的是「开关矩阵 + 半开熔断器」——**降什么**与**怎么兜**；A242 给的是压测方案与结果验收——**容量测得准不准**；A241 给的是多租户之间的配额仲裁——**额度怎么分**；Q1238 给的是容量估算的基本模型。本题补的是它们之间那段**编排**：什么时候降（触发指标与判定窗口）、降多深（阶梯与影响面预算）、怎么退回来（滞回、冷却、恢复条件），以及一个几乎没被单独讨论的问题——**降级项之间的流量转移会把压力挪到别的链路**。 ② 容量模型三层：**峰值推算**（`峰值 = 日常峰值 × 大促倍数 × 集中度`，集中度是「开场 5 分钟占全天比例」的放大，实测开场那一分钟常常是均值的 3-5 倍，所以 8 倍大促要按 12 倍准备）；**单机承载**（取压测拐点的 70%，不是取平均值也不是取「还没报错的最大值」——拐点是 RT 开始非线性上升的位置，贴着拐点跑等于没有余量）；**实例数**（`峰值 / 单机安全 × (1 + 冗余)`，本 demo 90000 / 420 × 1.3 = 279 台）。冗余不是越高越好：为一年一周的峰值买全量冗余，成本是常年的 3 倍，正确做法是「弹性扩容 + 降级兜底」，用降级能力换掉 30-40% 的冗余。③ 先崩的通常不是 CPU，是**连接**。Little 定律：并发 = QPS × RT。9 万 QPS、RT 80ms 时需要 7200 个在途请求；一旦 RT 劣化到 400ms（下游慢、锁等待、GC），同样 QPS 需要 36000 个并发——连接池、线程池、文件描述符、下游连接数会依次耗尽，而 CPU 可能只有 60%。这就是「过载的自我强化」：RT 上升 → 并发需求上升 → 排队更长 → RT 再上升。所以容量核对必须**按层做**：接入连接、工作线程/协程、DB 连接池、下游配额、缓存带宽，任何一层先到顶，整体容量就是那一层的容量。④ 降级阶梯的设计原则：**按影响面从小到大排，按「钱」划线决定谁能自动**。L1 关非核心（推荐位、实时榜单、同步埋点，影响 2%，自动）；L2 读降级（详情页缓存兜底、库存返回近似值、关实时销量，影响 8%，自动）；L3 写降级（非核心写异步化、评价积分丢弃、下单排队，影响 20%，**必须人工**，因为涉及数据完整性）；L4 功能熔断（关优惠券叠加、跨店满减，只保下单支付，影响 45%，人工）；L5 只读兜底（影响 100%，需业务方共同决策）。触发指标必须是**前置指标**：连接池使用率、P99、队列深度、下游错误率——用 CPU 当触发器已经晚了几十秒，那时排队已经形成，降级也追不回来。恢复条件必须写成「连续 N 个采样低于阈值的 70%」，而不是「低于阈值」——后者会在阈值附近反复横跳。⑤ 三个坑：**（a）降级项互相影响**——关掉首页个性化后，用户转去手动搜索，搜索 QPS 反而 +15%（本 demo 2300 vs 2000）；降级清单必须配一张依赖/转移图，每降一级就按「转移后的流量」重算容量，否则救了一个链路打挂另一个。**（b）指标失真**——降级后错误率下降，可能不是「恢复了」，而是「请求被拒了/被限流了」，比率类指标必须配绝对量（成功单量、支付笔数）一起看，否则会出现「各项指标全绿、成交额腰斩」。**（c）震荡**——无滞回时系统会在阈值附近每 30 秒降一级、升一级。三件套：滞回带（回落阈值 = 触发阈值 × 0.7）、冷却期（切换后 N 分钟不再动作）、最小停留（新档至少待 M 分钟）。本 demo 实测相邻动作间隔 5-7 分钟，全程零抖动。⑥ 演练：容量演练用影子流量/线上压测（读流量复制，写流量按比例放大，A242 的验收口径）+ 降级演练（真实把系统打到 L2，季度一次）。验收四项：**到阈值后 X 秒内完成降级**（自动档 ≤ 60s）、**影响面在预算内**（比如 L2 允许 8% 的功能不可用，实际观测 6%）、**恢复后指标回到基线**（不是「大致恢复」，是 P99/错误率回到前 7 天同期的 ±10%）、**无震荡**（切换次数 ≤ 档位数）。最容易漏的是「只练降不练升」——升不回来等于永久降级，很多事故的二次伤害就发生在恢复阶段。⑦ 一个组织层面的硬约束：自动降级必须有**全局总开关**和**单次授权时长**（比如自动降级 30 分钟后必须由人复核续期），否则自动化会在没人看的情况下把系统一路降到底，而值班同学以为是「流量太大」。

```python
# 全部标准库；容量模型 + 降级阶梯编排（滞回带 / 冷却期 / 人工闸门）
import math
from dataclasses import dataclass


def peak_qps(daily_peak, promo_mult, concentration=1.0):
    """大促峰值 = 日常峰值 × 大促倍数 × 开场集中度（前 N 分钟占比放大）。"""
    return daily_peak * promo_mult * concentration


def instances(peak, per_instance_safe, headroom=0.3):
    """实例数 = 峰值 / 单机安全水位 × (1+冗余)，向上取整。"""
    return math.ceil(peak / per_instance_safe * (1 + headroom))


def conns_needed(qps, p99_ms):
    """Little 定律：在途请求数 = QPS × RT。过载时 RT 涨，连接需求成倍涨。"""
    return qps * p99_ms / 1000.0


@dataclass
class Level:
    idx: int
    name: str
    action: str
    impact: float          # 影响面（% 的流量/功能）
    auto: bool
    metric: str            # 触发依据：用前置指标，不看已经饱和的 CPU
    threshold: float
    offload: float         # 本层生效后回落到下层的流量折减


LEVELS = [
    Level(0, "L0 正常", "无", 0.0, True, "pool_util", 1.0, 0.0),
    Level(1, "L1 关非核心", "关个性化推荐位/实时榜单/同步埋点", 2.0, True,
          "pool_util", 0.75, 0.06),
    Level(2, "L2 读降级", "详情页缓存兜底、库存返回近似值、关实时销量", 8.0, True,
          "p99_ms", 110.0, 0.15),
    Level(3, "L3 写降级", "非核心写异步化、评价/积分写丢弃、下单排队", 20.0, False,
          "err_rate", 0.015, 0.25),
    Level(4, "L4 功能熔断", "关优惠券叠加/跨店满减，只保下单支付", 45.0, False,
          "err_rate", 0.06, 0.25),
]


class Orchestrator:
    """降级编排：滞回带 + 冷却 + 最小停留 + 人工闸门。"""

    def __init__(self, confirm=2, calm=3, cooldown=3, min_dwell=4):
        self.level = 0
        self.confirm, self.calm = confirm, calm
        self.cooldown, self.min_dwell = cooldown, min_dwell
        self._streak = self._calm_streak = 0
        self._cool = self._dwell = 0
        self.pending = None
        self.changes = 0
        self.max_level = 0
        self.log = []

    def tick(self, minute, m):
        if self._cool > 0:
            self._cool -= 1
            self._dwell += 1
            return
        self._dwell += 1
        nxt = LEVELS[self.level + 1] if self.level + 1 < len(LEVELS) else None
        cur = LEVELS[self.level]

        if nxt and self.pending is None and m[nxt.metric] > nxt.threshold:
            self._streak += 1
            if self._streak >= self.confirm:
                if nxt.auto:
                    self.level += 1
                    self.max_level = max(self.max_level, self.level)
                    self.changes += 1
                    self._streak = 0
                    self._cool, self._dwell = self.cooldown, 0
                    self.log.append((minute, "自动降级 -> %s" % nxt.name))
                else:
                    self.pending = nxt.idx
                    self.log.append((minute, "待人工确认 %s" % nxt.name))
        else:
            self._streak = 0

        if self.level > 0 and m[cur.metric] < cur.threshold * 0.7 \
                and self._dwell >= self.min_dwell:
            self._calm_streak += 1
            if self._calm_streak >= self.calm:
                self.level -= 1
                self.changes += 1
                self._calm_streak = 0
                self._cool, self._dwell = self.cooldown, 0
                self.pending = None
                self.log.append((minute, "自动回落 -> %s" % LEVELS[self.level].name))
        else:
            self._calm_streak = 0

    def approve(self, minute, yes):
        if self.pending is None:
            return
        if yes:
            self.level = self.pending
            self.max_level = max(self.max_level, self.level)
            self.changes += 1
            self.log.append((minute, "人工批准 -> %s" % LEVELS[self.level].name))
            self._cool, self._dwell = self.cooldown, 0
        else:
            self.log.append((minute, "人工否决，维持 %s" % LEVELS[self.level].name))
        self.pending = None


def metrics_for(level, qps, read_cap=60000.0, write_cap=10500.0, max_conns=8000):
    """读降级只削读流量；写流量来自下单支付，砍不动——这是 L3 独有的理由。"""
    reads = qps * 0.82 * (1 - LEVELS[level].offload)
    writes = qps * 0.18
    read_util = reads / read_cap
    write_util = writes / write_cap
    p99 = 40.0 * (1 + 6 * max(0.0, read_util - 0.6))       # RT 随水位抬升
    conns = conns_needed(reads, p99)
    return {"qps": round(reads + writes), "read_util": round(read_util, 3),
            "write_util": round(write_util, 3), "p99_ms": round(p99, 1),
            "pool_util": round(conns / max_conns, 3),
            "err_rate": round(max(0.0, write_util - 1.0) * 0.3, 4)}


def simulate(o, minutes=64, base=9000.0):
    trace = []
    for t in range(minutes):
        if t < 12:
            mult = 1.0 + (t / 12.0) * 7.0
        elif t < 24:
            mult = 8.0
        elif t < 44:
            mult = 8.0 - ((t - 24) / 20.0) * 7.0
        else:
            mult = 1.0
        m = metrics_for(o.level, base * mult)
        trace.append((t, m, o.level))
        o.tick(t, m)
    trace.append((minutes, metrics_for(o.level, base), o.level))
    return trace


if __name__ == "__main__":
    daily, promo, conc = 6000, 10, 1.5
    peak = peak_qps(daily, promo, conc)
    assert peak == 90000
    per_safe = 600 * 0.7                 # 压测拐点 600 QPS，取 70% 作安全水位
    n = instances(peak, per_safe)
    assert n == 279
    print("容量: 日常 %d QPS × %d 倍 × 集中度 %.1f = 峰值 %d QPS" % (daily, promo, conc, peak))
    print("  单机安全 %d QPS + 30%% 冗余 -> %d 台（按天买弹性，不按月买固定）" % (per_safe, n))
    print("  Little: 9 万 QPS × 80ms = %d 并发；RT 劣化到 400ms 就是 %d 并发"
          % (conns_needed(90000, 80), conns_needed(90000, 400)))

    o = Orchestrator()
    trace = simulate(o)
    hot = max(trace, key=lambda x: x[1]["qps"])
    print("峰值 t=%d: qps=%d 读水位=%.2f 写水位=%.2f p99=%.0fms 连接池=%.2f"
          % (hot[0], hot[1]["qps"], hot[1]["read_util"], hot[1]["write_util"],
             hot[1]["p99_ms"], hot[1]["pool_util"]))

    assert o.max_level == 2                  # 自动档只到 L2（读降级）
    assert any("待人工确认 L3" in a for _, a in o.log)
    assert o.level == 0                      # 流量回落后自动恢复
    print("编排结果: 最高自动到 L2，L3 卡在人工闸门；收尾回到 %s ✅"
          % LEVELS[o.level].name)
    for t, act in o.log:
        print("  t=%02d %s" % (t, act))

    gaps = [b[0] - a[0] for a, b in zip(o.log, o.log[1:])]
    assert all(g >= 3 for g in gaps), gaps    # 冷却期保证不抖动
    print("抖动检查: 相邻动作间隔 %s 分钟，全部 >= 冷却期 ✅" % gaps)

    # 人工批准后进 L3
    o2 = Orchestrator()
    simulate(o2, minutes=26)
    assert o2.pending == 3
    o2.approve(27, True)
    assert o2.level == 3 and o2.max_level == 3
    print("人工批准 L3: 当前 %s，影响面 %.0f%%（只保下单支付）"
          % (LEVELS[o2.level].name, LEVELS[o2.level].impact))

    # 降级的副作用：关个性化后用户转手动搜索，压力转移到搜索链路
    home, search = 8000 * 0.88, 2000 * 1.15
    print("副作用: 关个性化后 首页 %.0f / 搜索 %.0f —— 容量表必须按「转移后」的链路算"
          % (home, search))
```

**追问**：1) 自动降级该不该直接降到「够用为止」（一次跳两级）？—— 不该。跳级意味着跳过观察，你可能在 L1 已经缓解的情况下多降一级，白白损失功能；而且跳级后无法归因「是哪一级起了作用」，下次预案就是拍脑袋。正确做法是**逐级 + 冷却**：每级生效后至少观察一个冷却窗口，看指标是否回到滞回带内，没回到才继续。代价是响应慢一点（本 demo 每级 5 分钟），对大促这种可预测的峰值，可以提前按时间表预降（开场前 10 分钟主动到 L1），把「应急」变成「计划」。2) 大促当天各项指标全绿，但成交额掉了 20%，怎么查？—— 典型的「指标失真 + 隐性降级」：先看降级面板的实际档位（是不是被自动降过又自动升回来了，日志里有没有 L2/L3 记录），再看成功率对应的**绝对量**（QPS 是不是本身掉了，而不是成功率变高），最后按漏斗拆分（曝光→详情→加购→下单→支付）找出转化率断崖的那一步。经验：成交额是结果指标，出问题时至少已经在系统里存在 5-15 分钟的隐性劣化。3) 降级预案写好了，怎么证明它真的有效？—— 只能演练，而且必须**真实触发**（打到 L2 并观测影响面），纸面评审不算。演练时记录三件事：从「指标越线」到「降级生效」的耗时（自动化水平）、生效后的指标改善幅度（预案是否对症）、恢复后是否有残留（缓存没预热、队列积压、限流没解除）。这三项直接对应验收口径，也是下次大促前唯一能拿出来的证据。

## 背诵要点
1. 容量三层：峰值 = 日常 × 倍数 × 集中度；单机取压测拐点 70%；实例 = 峰值/单机安全 × (1+冗余)。冗余用「弹性 + 降级」换，别为一天买全年。
2. 先崩的是连接不是 CPU：并发 = QPS × RT，RT 从 80ms 到 400ms 连接需求 ×5，过载自我强化；容量要按层核对（连接/线程/DB 池/下游配额）。
3. 降级按影响面排、按「是否动钱」划自动边界；触发器用前置指标；滞回 0.7 + 冷却 + 最小停留防震荡；演练必须真实触发且包含「升回来」这一段。

## 复盘追问
1. 大促前扩容到 279 台，压测也过了，为什么开场还是挂了？（提示：压测通常是「稳态负载」，而开场是「阶跃 + 冷启动」——JIT/连接池/缓存都是冷的，第一批请求的 RT 是稳态的数倍，正好撞在连接数最紧的时刻；预案要包含预热（提前打流量暖缓存、暖连接池）和「开场限流」而不是只扩容）
2. 降级开关加了，但某个下游团队拒绝配合降级，怎么办？（提示：降级是跨团队的契约，不是单方面能力——要么在调用侧做（超时/熔断/返回兜底值，不依赖对方），要么事先把「可降级接口清单 + 兜底语义」写进 SLA 与联调用例；等到大促当天再谈，对方只会说「我们没问题」）
