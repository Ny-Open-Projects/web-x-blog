### A137 · 服务下线审查

> 难度:★★☆ | 标签:下线, 依赖回收, 治理

**问**（笔试·场景题）：老服务要下线（被新服务替代）——下线审查清单里「容量缺口」指什么（新服务接得住老服务的量吗），依赖怎么回收（老服务的调用方清单与迁移验证），数据怎么处置（迁移/归档/销毁的合规口径），「下线失败回滚」的窗口怎么定？

**答**：① 容量缺口审查：新服务**单实例容量 × 计划实例数 ≥ 老服务当前峰值 QPS × 1.5 冗余**——缺口 = 差额；还有隐性容量：新服务的依赖（新连接池/新缓存）是否按新流量重规划（老服务的 DB 配额不能直接继承）。② 依赖回收四步：调用方清单（Q123 依赖地图反查）→ 逐个迁移验证（契约测试 + 双跑对拍 Q7548）→ 旧调用方摘除（流量归零确认）→ 服务停机（不是删代码——停机观察期 30 天，无复活需求再删）。③ 数据处置三轨：迁移（业务数据进新服务的库，双写期已同步）、归档（审计要求保留的进冷存储 WORM）、销毁（含 PII 的按合规销毁+销毁凭证）——**删除服务实例 ≠ 删除数据**，数据生命周期独立处理（Q6515 冷热分层）。④ 回滚窗口：停机后 30 天内可「复活」（数据还在迁移库、调用方还能切回——依赖摘除但路由可恢复）；30 天后数据清理启动 → 回滚窗口关闭。

```python
# 全部标准库；demo 实现「容量缺口计算 + 下线检查清单」
import math

def capacity_gap(old_peak_qps: float, new_per_instance: float,
                 new_instances: int, redundancy: float = 1.5) -> dict:
    need = old_peak_qps * redundancy
    have = new_per_instance * new_instances
    gap = max(0, need - have)
    return {"need": need, "have": have,
            "gap": gap, "add_instances": math.ceil(gap / new_per_instance) if gap > 0 else 0}

CHECKLIST = [
    ("调用方清单", lambda deps: len(deps) == 0, "依赖地图反查=0 才可停机"),
    ("双跑对拍", lambda ok: ok, "新旧服务同流量对拍一致率 >99.9%"),
    ("数据迁移校验", lambda ok: ok, "行数+抽样哈希对账"),
    ("回滚窗口", lambda days: days >= 30, "停机后 30 天内可复活"),
]

def shutdown_review(deps_left: int, dual_run_ok: bool, data_ok: bool, days: int) -> list[str]:
    issues = []
    checks = [
        (f"调用方残留 {deps_left} 个", deps_left == 0),
        ("双跑对拍未通过", dual_run_ok),
        ("数据迁移未校验", data_ok),
        (f"回滚窗口 {days} 天 <30", days >= 30),
    ]
    for name, ok in checks:
        if not ok:
            issues.append(f"❌ {name}")
    return issues or ["✅ 全部通过，可停机"]

if __name__ == "__main__":
    gap = capacity_gap(old_peak_qps=5000, new_per_instance=1200, new_instances=4)
    print("容量缺口:", gap)
    assert gap["gap"] > 0 and gap["add_instances"] == 3   # 7500 需求 vs 4800 现有
    issues = shutdown_review(deps_left=2, dual_run_ok=False, data_ok=False, days=10)
    for i in issues: print(i)
    assert len(issues) == 4
    print("下线审查：容量/依赖/数据/回滚 四闸全绿才可停机 ✅")
    # 口径：停机≠删代码（30 天观察期）；数据生命周期独立于服务生命周期。
```

**追问**：1) 为什么「停机后 30 天可复活」而不是「随时可复活」？——复活能力依赖三件事的成本窗口：迁移库数据保留（占存储）、调用方路由可恢复（配置保留）、团队上下文新鲜——30 天是成本与安全的平衡点，超期后复活成本接近重写。2) 老服务有个「只有月底跑一次」的定时任务调用方，怎么发现？（提示：依赖地图按 QPS 排序会漏掉超低频调用（月度任务）——反查要按「代码引用+配置引用」全量扫，不按流量；或观察期设为覆盖一个完整业务周期（如 31 天））3) 「新服务依赖按新流量重规划」的具体坑？（提示：老服务的 DB 连接数/Redis 键模式/下游配额都绑在老服务身份上——新服务用新身份申请，忘了申请 = 上线即配额耗尽）

## 背诵要点
1. 容量缺口 = 老峰值 ×1.5 冗余 − 新服务实际供给；隐性容量（DB 配额/缓存键模式/下游配额）按新身份重新规划。
2. 依赖回收四步：清单 → 迁移验证（双跑对拍）→ 摘除（流量归零）→ 停机观察 30 天（不删代码）。
3. 数据处置三轨独立于服务生命周期；回滚窗口 30 天后关闭（清理启动）。

## 复盘追问
1. 下线 60 天后发现老服务有个「年报计算」任务还是唯一实现——怎么办？（提示：从归档库恢复（数据+代码在 git tag）+ 重部署为一次性任务跑完再删——观察期设计要覆盖最长业务周期，年报=35 天窗口不够）
2. 「双跑对拍一致率 99.9%」但差的 0.1% 是金额尾差，能下线吗？（提示：不能——金额差哪怕 1 分也是资损/对账事故；尾差根因（浮点/舍入口径）修到 100% 才下线，金融场景零容忍）
