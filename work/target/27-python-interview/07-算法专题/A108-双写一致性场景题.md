### A108 · 缓存-DB 双写一致性场景题

> 难度:★★★ | 标签:缓存一致性, 双写, 场景题

**问**（笔试·场景题）：写路径「先更新 DB 还是先删缓存」、读路径要不要回填、Binlog 订阅方案和延迟双删分别解决什么失败？把所有失败模式列成矩阵并给出最终推荐链路。

**答**：先定原则：**缓存只删不更**（更新易并发覆盖旧值），**DB 为主缓存为投影**。失败矩阵——① 先删缓存后写 DB：删后另一读请求把**旧值**回填，脏到下次过期，**最差**；② 先写 DB 后删缓存：写后删前有窗口读到旧值，但删成功即收敛；删失败才脏 → 需重试兜底；③ **先写 DB + 删缓存 + binlog 订阅兜底**：应用只管删，订阅 binlog 的组件（Canal 思路）发现「DB 已变但缓存还旧」就再删一次，删失败的最终兜底；④ 延迟双删（写后 sleep 数百 ms 再删一次）专治①的回填脏数据，但 sleep 是魔法数，只适合读写比极端不均衡的场景。**推荐：②+③ 组合**——先写 DB 后删缓存，删除失败进重试队列，binlog 订阅做最终兜底；不采用先删缓存。

```python
import threading, time

class Store:
    def __init__(self):
        self.db: dict[str, str] = {}
        self.cache: dict[str, str] = {}
        self.del_fail_log: list[str] = []      # 删除失败重试队列的模拟

    def write(self, key: str, value: str):
        # ① DB 先行：主数据落定
        self.db[key] = value
        # ② 删缓存（失败不抛，进重试）
        if not self._try_del(key):
            self.del_fail_log.append(key)
        # ③ binlog 兜底（模拟）：发现 DB 与缓存不一致 → 再删一次
        self._binlog_probe(key, value)

    def _try_del(self, key) -> bool:
        try:
            del self.cache[key]; return True
        except KeyError:
            return True                        # 本来就没有 = 删除成功（幂等）
        except Exception:
            return False

    def _binlog_probe(self, key, value):
        if self.cache.get(key) == value: return   # 一致
        if key in self.cache and self.cache[key] != self.db[key]:
            self._try_del(key)                    # 脏缓存强制收敛
        self.del_fail_log.clear()                 # 模拟重试队列被兜底清空

    def read(self, key):
        v = self.cache.get(key)
        if v is not None: return v
        v = self.db.get(key)                      # miss 回源
        if v is not None:
            self.cache[key] = v                   # 回填（读路径回填是允许的）
        return v

if __name__ == "__main__":
    s = Store()
    s.cache["k"] = "old"                          # 预热旧值
    s.db["k"] = "old"
    s.write("k", "new")
    assert s.read("k") == "new"                   # 写后读一致 ✅
    s.cache["k"] = "stale"; s.db["k"] = "real"    # 模拟删失败留下脏缓存
    s._binlog_probe("k", "real")
    assert s.cache.get("k") is None               # binlog 兜底删掉脏值 ✅
    print("写后一致 + 脏缓存兜底收敛 OK")
```

**追问**：1) 为什么缓存只删不更？——两路并发更新（A 写 DB→B 写 DB→B 更缓存→A 更缓存）会把缓存定在 A 的旧值；删除操作幂等丢单向，谁后删谁生效，收敛性质好得多。2) 读路径回填会不会造成①的脏回填？——会，但②的顺序下回填源是**已提交的 DB**，脏窗口只剩「写 DB 与删缓存之间」，由 binlog 兜底收敛；若要极致一致可短 TTL 控制脏时长。3) 删缓存重试队列怎么实现可靠？——本地表/MQ 投递 + 指数退避，重试也有上限，最终靠 binlog 组件巡检。

## 背诵要点
1. 原则：DB 为主、缓存只删不更、删除幂等；先删缓存是明确反模式。
2. 推荐链路：先写 DB → 删缓存（失败进重试）→ binlog 订阅兜底收敛。
3. 延迟双删只治「先删后写」的回填脏数据，魔法 sleep 是补丁不是方案。
