### A184 · 变更摘要机器可读化

> 难度:★★☆ | 标签:发布, 公告, 自动化

**问**（笔试·编程+场景题）：每次发布后人工写公告（写给客户/写给自己人/写值班员三份）——三份公告的内容重叠 80%，怎么从**结构化的变更数据**自动生成三份（模板+受众裁剪），变更数据结构要哪些字段（类型/影响面/用户可见性/breaking 标记），「breaking change 没进公告」的事故怎么防（发布闸校验公告覆盖 breaking 项）？

**答**：① 单一事实源：PR 元数据（`type: feat/fix/breaking`、`user_visible: bool`、`services` 影响面）在 PR 标签里结构化标注 → 发布时自动聚合（A143 机器可读变更单的下游）→ 三份公告 = 同一数据 × 三个受众模板（客户版：只含 user_visible+breaking；内部版：全量+服务细节；值班版：只含运维相关+开关位置）。② breaking 防漏：发布闸校验——数据里有 `breaking: true` 的 PR，公告必须包含对应条目（机器 diff 校验），缺了拒绝发布公告（不是拒绝发布——发布可以走，公告补发但告警）。③ 模板分层：标题（一句话，客户视角）、影响（谁受影响）、动作（用户要做什么）、时间（何时生效）——四段式固定结构，受众裁剪只调「详略与语言」，结构不变（可机器消费）。

```python
# 全部标准库；demo 实现「PR 元数据聚合 → 三受众公告生成 → breaking 防漏闸」
import json

def aggregate(prs: list[dict]) -> dict:
    return {"breaking": [p for p in prs if p.get("breaking")],
            "user_visible": [p for p in prs if p.get("user_visible")],
            "ops": [p for p in prs if p.get("ops_related")],
            "all": prs}

def customer_announcement(agg: dict) -> str:
    lines = ["【更新公告】"]
    if agg["breaking"]:
        lines.append("⚠ 重要变更（需要您调整）：")
        for p in agg["breaking"]:
            lines.append(f"  - {p['title']}：{p['action_needed']}")
    if agg["user_visible"]:
        lines.append("✨ 新功能与优化：")
        for p in agg["user_visible"]:
            lines.append(f"  - {p['title']}")
    return "\n".join(lines)

def oncall_announcement(agg: dict, flags: dict[str, str]) -> str:
    lines = ["【值班摘要】", f"变更数: {len(agg['all'])}"]
    for p in agg["ops"]:
        lines.append(f"  - {p['title']} | 开关: {flags.get(p['id'], '无')}")
    if agg["breaking"]:
        lines.append(f"  ⚠ {len(agg['breaking'])} 个 breaking 变更，观察窗加密（Q7013）")
    return "\n".join(lines)

def breaking_gate(agg: dict, announcement: str) -> bool:
    """发布闸：breaking 项必须在公告中覆盖（title 出现即算）。"""
    missing = [p["title"] for p in agg["breaking"] if p["title"] not in announcement]
    return not missing

if __name__ == "__main__":
    prs = [
        {"id": "PR-1", "title": "API 返回格式调整", "breaking": True,
         "user_visible": True, "ops_related": True, "action_needed": "使用 SDK 2.0+",
         "type": "feat"},
        {"id": "PR-2", "title": "新增导出 Excel 功能", "breaking": False,
         "user_visible": True, "ops_related": False, "type": "feat"},
        {"id": "PR-3", "title": "内部连接池调优", "breaking": False,
         "user_visible": False, "ops_related": True, "type": "fix"},
    ]
    agg = aggregate(prs)
    cust = customer_announcement(agg)
    print(cust)
    assert breaking_gate(agg, cust)                  # breaking 已覆盖 ✅
    # 事故模拟：公告漏了 breaking 项
    partial = "【更新公告】\n✨ 新功能与优化：\n  - 新增导出 Excel 功能"
    assert not breaking_gate(agg, partial)
    print("breaking 防漏闸：漏报公告被拦截 ✅")
    print(oncall_announcement(agg, {"PR-3": "FLAG_POOL_TUNE"}))
    # 口径：PR 元数据结构化标注 = 单一事实源；三受众 = 同数据 × 三模板；
    # breaking 防漏闸校验公告覆盖（漏报告警不拒发布）。
```

**追问**：1) 为什么 breaking 防漏闸「告警不拒发布」？——公告补发可补救（用户晚知道几小时），但发布被公告阻塞会让团队把公告当发布障碍而绕过系统（造假公告应付闸）——闸的目的是「保证最终有公告」而非「卡发布」；拒绝发布留给「真硬性条件」（测试全绿类）。2) 「PR 标签结构化标注」靠人自觉会漏标怎么办？（提示：模板 PR 强制字段（缺标签 CI 拒绝）+ AI 辅助标注（从 diff 推断 user_visible/breaking，人确认）——标注成本降到 10 秒，自觉变成习惯）3) 三份公告的「受众裁剪」还有第四受众吗？（提示：支持团队（FAQ 视角：客户会问什么怎么答）——客服话术与公告同源生成，公告发布后 10 分钟内支持团队拿到 FAQ，避免客服口径不一）

## 背诵要点
1. 单一事实源：PR 元数据结构化标注（type/user_visible/breaking/ops_related）→ 聚合 → 三受众模板。
2. 客户公告结构四段式（标题/影响/动作/时间）固定不变可机器消费；受众裁剪只调详略。
3. breaking 防漏闸：公告必须覆盖 breaking 条目（缺了告警不拒发布）——漏报可补，绕过不可饶恕。

## 复盘追问
1. 公告自动生成后「没人审就直接发」，机器生成的公告出错谁负责？（提示：生成 ≠ 发布——发布前保留人工确认一步（1 分钟扫一眼），长期向「高置信自动发」（非 breaking 变更自动、breaking 人工确认）演进——自动化程度与风险分级挂钩）
2. 客户反馈公告「全是技术术语看不懂」，模板怎么改进？（提示：客户模板的 title 用「用户视角」语言（「导出格式更稳定」而非「修复 jsonable_encoder 序列化」）——PR title 与公告 title 分离（公告 title 单字段，PR 里标注），术语翻译进模板映射表）
