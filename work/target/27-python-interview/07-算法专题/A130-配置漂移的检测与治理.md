### A130 · 配置漂移

> 难度:★★☆ | 标签:配置漂移, IaC, 治理

**问**（笔试·编程+场景题）：「期望配置在配置中心，实际跑在机器上的不知道是什么」——配置漂移（drift）怎么检测（声明式 vs 实际态的 diff），漂移的来源有哪些（手工改线上/热修未回写/实例跳过更新），检测到漂移后「强制收敛」和「接受漂移」怎么决策，漂移治理怎么从「救火」变「例行」？

**答**：① 检测：**期望态**（配置中心/IaC 仓库版本）vs **实际态**（实例运行时上报：healthz 返回生效版本+关键参数）周期 diff——diff 粒度到字段（不是版本号对齐就完事：实例可能版本对但参数被热改）。② 漂移来源：**热修**（线上直接改没回写配置中心——流程漏洞）、**跳过更新**（实例滚动更新时漏网/失败重试放弃）、**环境差异**（special-case 配置用 if 硬编码而非参数化）。③ 收敛 vs 接受决策：**接受**（漂移是救火行为且已记录，事后把热修回写配置中心再收敛——先回写后收敛，顺序反了会覆盖救火修复）；**强制收敛**（无记录的漂移 = 未知变更，直接推期望态——但推之前 diff 告警确认不是误报）。④ 例行化：漂移检测进巡检（每日），漂移率（漂移实例/总实例）是治理 KPI；收敛动作自动化（一键推期望态+滚动），救火回写流程简化到「一条命令」——回写成本决定漂移率。

```python
# 全部标准库；demo 实现「漂移检测器 + 收敛决策」
import time

DESIRED = {"timeout_s": 3.0, "rate_limit": 100, "flags": {"dark": False}}
ACTUAL = {                                            # 实例运行时上报
    "inst-1": {"version": 12, "timeout_s": 3.0, "rate_limit": 100, "flags": {"dark": False}},
    "inst-2": {"version": 12, "timeout_s": 3.0, "rate_limit": 500, "flags": {"dark": False}},  # 热修漂移
    "inst-3": {"version": 11, "timeout_s": 30.0, "rate_limit": 100, "flags": {"dark": True}},  # 跳过更新
}

def detect_drift(desired: dict, actual: dict[str, dict],
                 hotfix_registry: dict[str, str]) -> dict[str, dict]:
    """字段级 diff + 来源分类（热修记录在案 vs 未知变更）。"""
    drift = {}
    for inst, state in actual.items():
        diffs = {k: {"want": desired[k], "got": v}
                 for k, v in state.items() if k != "version" and desired.get(k) != v}
        if diffs:
            src = "hotfix-documented" if inst in hotfix_registry else "unknown"
            drift[inst] = {"diffs": diffs, "source": src,
                           "action": "accept-then-converge" if src == "hotfix-documented"
                                     else "force-converge"}
    return drift

def converge(inst: str, drift_entry: dict, hotfix_registry: dict[str, str]) -> str:
    """收敛：热修先回写期望态再推（顺序铁律），未知变更直接推期望态。"""
    if drift_entry["source"] == "hotfix-documented":
        for k, d in drift_entry["diffs"].items():
            DESIRED[k] = d["got"]                     # ① 先回写（救火成果不丢）
        hotfix_registry.pop(inst, None)
        return f"{inst}: 热修回写完成 → 推新期望态"
    return f"{inst}: 未知漂移 → 强制推期望态（diff 已告警确认）"

if __name__ == "__main__":
    registry = {"inst-2": "hotfix-2026-11-20"}        # inst-2 的热修有记录
    drift = detect_drift(DESIRED, ACTUAL, registry)
    for inst, d in drift.items():
        print(f"{inst} [{d['source']}] {d['diffs']} → {d['action']}")
        print("  →", converge(inst, d, registry))
    # 收敛后终态 = 热修成果（rate_limit 500）全量生效，无跳过实例
    assert DESIRED["rate_limit"] == 500
    print("最终期望态 rate_limit=500（救火成果被制度化而非丢失）✅")
    # KPI：漂移率 = 漂移实例/总实例；例行巡检 + 回写命令化 → 漂移率趋零。
```

**追问**：1) 为什么「先回写后收敛」顺序不能反？——先收敛会把救火修改覆盖掉（实例被打回旧值），线上故障复现——热修成果是「未记录的正确状态」，必须先制度化再统一；这和「代码 hotfix 先进 main 再发版」同构。2) healthz 上报什么内容才够漂移检测？（提示：生效配置版本号 + 关键参数值 + 加载时间——版本号粗、参数细，两层都要）3) IaC（Terraform/Ansible）和配置中心的双体系漂移怎么管？（提示：各自域内检测+收敛，跨界字段（infra 层改了端口影响应用配置）靠「单一真相源」划界——每个配置项只有一个 owner 系统）

## 背诵要点
1. 漂移检测 = 期望态（配置中心）vs 实际态（healthz 上报）字段级 diff，按来源分类（热修在案/未知变更）。
2. 收敛顺序铁律：热修先回写期望态再统一收敛（顺序反了覆盖救火成果）；未知漂移直接推期望态。
3. 漂移率是治理 KPI：例行巡检 + 回写命令化——回写成本决定漂移率。

## 复盘追问
1. 团队抱怨「回写太麻烦所以总漂移」，机制上怎么降低回写成本？（提示：热修入口直接内置回写（改线上=改中心+生效原子操作，禁止裸改）——把流程约束做成工具约束）
2. 漂移检测发现某实例配置「应该漂移但没漂」（热修没生效），这说明什么？（提示：热修失败但记录在案——比未知漂移更危险（以为修了实际没修）——热修后必须验证生效，Q124 apply 验证同构）
