### A255 · 慢查询治理专项

> 难度:★★★★ | 标签:慢查询, 执行计划, 索引代价, 灰度验证

**问**（笔试·场景题）：大促前一周，DBA 发来一张「慢查询 Top 50」，开发只有三天时间。要求交付一套可执行的治理方案，并回答五个带数字的问题：**① 怎么排序**——Top 50 是按平均耗时排的，为什么直接照着修会翻车，正确的排序口径是什么；**② 指纹怎么归一**——`WHERE id = 12345` 与 `WHERE id = 67890` 是同一条 SQL，`IN (1,2,3)` 和 `IN (1..500)` 是不是同一条，不归一会导致什么误判；**③ 索引怎么选**——给一个「等值 + 范围 + 排序」的查询，如何估算加索引后的扫描行数、回表次数、写放大，为什么区分度低的列放在复合索引最左边是灾难；**④ SQL 怎么改写**——深分页、函数包列、隐式类型转换、`OR` 四类的改法与预期收益各是多少，哪些改写会改变语义（必须拒绝）；**⑤ 灰度怎么验**——新旧 SQL 怎么分桶、为什么前 5% 样本必须扔掉、样本量不足时能不能下结论、P99 恶化多少必须回滚。约束：给出的模型要能跑出数字，不接受「看情况」。请说明与 Q838（事故复盘的修复路径）、Q6134（LIKE 前缀通配）、Q6145（复合索引最左前缀）、Q6053（深分页容量账）的分工。

**答**：① 分工：Q838 给的是**单条事故**的排查路径（慢日志 → EXPLAIN → 分类修复 → 上线观察）；Q6134/Q6145/Q6053 各自把「索引失效的某一类原因」算成了容量账。本题是**专项治理**：面对 50 条候选，怎么排出修复顺序、怎么把 50 条收敛成 5 条（同一指纹）、怎么证明改完真的好了。差别在于「单条修对」和「一批修对且可验证」，后者要的是排序模型、代价模型和灰度闸门。② 排序：按**平均耗时**排是错的，因为它忽略了次数。一条 2000ms 每天跑 10 次（总耗时 20s）和一条 8ms 每秒 5000 次（总耗时 40s/秒）在 Top 50 里可能相邻，但后者才是把 CPU 打满的元凶。正确口径是**总耗时占比** `sum(ms) / 窗口总耗时`——它直接对应「修掉它能释放多少数据库容量」，也是唯一能和「要不要扩容」放在同一张表里比较的量。P99 高但次数极少的查询（报表导出、月末结算）应该单独成表，用「限流 + 挪到离线」处理，而不是加索引——加索引只会让它更快地打满 IO。③ 指纹归一：必须把**字面量**替换成占位符（数字、字符串、`IN` 列表长度），否则 5000 条同构 SQL 会散成 5000 个指纹，每条都只有 1 次，永远进不了 Top 50——这是慢日志平台最常见的失效原因。`IN (1,2,3)` 与 `IN (1..500)` 必须归一到同一个指纹：执行计划完全不同（后者可能放弃索引走全表），如果分开统计，你会看到「同一条 SQL 有时快有时慢」却找不到规律。归一也有代价：指纹抹掉了参数分布，**同一指纹下可能藏着快慢两极**（热门商户 100 万行、冷门商户 10 行），所以平台要同时保留「指纹维度」和「单条最慢样本」，前者排序、后者定位。④ 索引：代价模型三层——**等值列**按 `1/NDV` 连乘（区分度越高过滤越狠）；**范围列**只能吃一列，后面的索引列失效；**排序**要利用索引有序性避免 filesort，但前提是排序列在索引里且前面全是等值条件。扫描行数估算之后还要算**回表**：非覆盖索引每命中一行都要回主键索引再取一次，代价约为顺序扫描的 3 倍，所以「过滤出 10 万行再回表」比「全表扫 100 万行」更慢——这就是「加了索引反而变慢」的经典场景，解法是**覆盖索引**（把 select 列塞进索引）或**延迟关联**（先用索引拿主键再 join 回表）。区分度低的列（`status`、`is_deleted`、`type`）放最左边是灾难：`status='paid'` 占 80% 时，以它为首的复合索引等于一张全表，优化器干脆不用，白付写放大。⑤ 改写四类与收益：**深分页** `LIMIT 100000, 20` 要扫 100020 行，改 keyset（`WHERE id > ? LIMIT 20`）只扫 20 行，量级差 5000 倍，但要求排序键唯一且不能跳页——产品上必须接受「只能下一页」；**函数包列** `WHERE date(created_at) = '2026-11-24'` 让索引失效，改成范围 `>= '2026-11-24' AND < '2026-11-25'`，语义等价、可走索引；**隐式类型转换**（`varchar` 列与数字比较）会让优化器放弃索引，改传字符串即可，但**必须在应用层统一类型**，否则下次又变回去；**`OR`** 跨列时索引往往用不上，改 `UNION ALL` 两次索引查询，注意 `UNION` 会去重（多一次排序），`UNION ALL` 不会——用哪个取决于业务是否允许重复。风险最高的是「改写改变语义」：把 `LEFT JOIN` 改 `INNER JOIN`、把 `LIMIT` 去掉、把 `COUNT(DISTINCT)` 改 `COUNT(*)`，这三类在治理里必须**明确拒绝**，收益再大也不能做。⑥ 灰度：SQL 改写不能一把全量，按 `user_id` 哈希分桶（和 A249 的切读同理，保证同一用户行为一致），1% → 10% → 50% → 100%，每档观察 P99、错误率、扫描行数、锁等待。**前 5% 样本必须扔掉**：新 SQL 首次执行要预热 buffer pool、解析计划、建立连接，前几秒的数据一定偏慢，不剔除会把「预热成本」误判成「改写退化」，导致好好的优化被回滚。**样本量不足不能下结论**：P99 在 100 个样本上毫无统计意义（它其实就是最大值附近的两个点），每档至少 200 次且覆盖一次波峰；样本不足时的正确结论是「继续观察」，不是「通过」。回滚阈值要事先写死：P99 涨幅 > 10%、错误率翻倍、扫描行数没降（说明索引没生效），任一触发立即回滚——不要现场讨论「再等等看」。⑦ 最后是**机制**而不是这一批：治理做完如果不留下门禁，三个月后同样的慢查询会回来。三件事最有效——上线前 `EXPLAIN` 门禁（扫描行数超阈值直接拒发）、慢查询阈值分级告警（>100ms 采样、>1s 全量、>5s 立刻通知）、索引使用率季度回收（`sys.schema_unused_indexes`，未被使用的索引只贡献写放大）。⑧ 一个反直觉结论：**慢查询治理的收益上限由「最热的那条」决定，不是由「最慢的那条」决定**。修掉 50 条里的 45 条冷查询，CPU 可能只降 3%；而把一条占总耗时 40% 的热查询从 8ms 降到 2ms，直接释放 30% 容量。所以排序口径决定了这件事的投入产出比，比任何单条优化技巧都重要。

```python
# 全部标准库；指纹归一 + 影响面排序 + 索引代价估算 + 灰度闸门
import re
from collections import defaultdict
from dataclasses import dataclass, field

LITERAL = re.compile(r"'(?:[^']|'')*'|\b\d+(?:\.\d+)?\b")
IN_LIST = re.compile(r"in\s*\(\s*\?(?:\s*,\s*\?)*\s*\)", re.I)
WS = re.compile(r"\s+")


def fingerprint(sql):
    """字面量归一 + IN 列表折叠 + 空白压缩：同构 SQL 必须落进同一个指纹。"""
    s = LITERAL.sub("?", sql)
    s = IN_LIST.sub("in (?)", s)
    s = WS.sub(" ", s).strip().rstrip(";").lower()
    return s


@dataclass
class Sample:
    sql: str
    ms: float
    scanned: int
    ok: bool = True


def pct(vals, q):
    if not vals:
        return 0.0
    s = sorted(vals)
    return s[min(len(s) - 1, int(q * (len(s) - 1)))]


def aggregate(samples, window_s, db_busy_ratio=0.7):
    """按指纹聚合，用「总耗时占比」排序，而不是平均耗时。"""
    agg = {}
    total_ms = 0.0
    for x in samples:
        fp = fingerprint(x.sql)
        a = agg.setdefault(fp, {"n": 0, "sum": 0.0, "ms": [], "scanned": 0, "err": 0})
        a["n"] += 1
        a["sum"] += x.ms
        a["ms"].append(x.ms)
        a["scanned"] += x.scanned
        a["err"] += 0 if x.ok else 1
        total_ms += x.ms
    capacity_ms = window_s * 1000 * db_busy_ratio     # 窗口内 DB 可用 CPU 时间
    rows = []
    for fp, a in agg.items():
        rows.append({
            "fp": fp, "n": a["n"], "avg": a["sum"] / a["n"],
            "p99": pct(a["ms"], 0.99), "sum": a["sum"],
            "share": a["sum"] / capacity_ms,
            "rows_per_call": a["scanned"] / a["n"],
        })
    rows.sort(key=lambda r: r["sum"], reverse=True)
    return rows, capacity_ms


def index_cost(table_rows, eq_ndv, has_range, covering, limit_ratio=None):
    """代价模型：等值列 1/NDV 连乘，范围列吃 0.1，非覆盖回表 ×3。"""
    sel = 1.0
    for ndv in eq_ndv:
        sel *= 1.0 / max(ndv, 1)
    if has_range:
        sel *= 0.1
    scanned = max(1, int(table_rows * sel))
    if limit_ratio is not None:
        scanned = min(scanned, max(1, int(scanned * limit_ratio)))
    cost = scanned * (1.0 if covering else 3.0)     # 单位：行代价，回表 3 倍
    return {"scanned": scanned, "cost_rows": round(cost, 1)}


def write_amplification(write_qps, index_count, per_index_us=20):
    """每多一个索引，写路径多一次 B+ 树维护：返回每秒额外代价（ms）。"""
    return write_qps * index_count * per_index_us / 1000.0


def keyset_gain(offset, limit):
    return {"offset_scan": offset + limit, "keyset_scan": limit,
            "ratio": (offset + limit) / limit}


def gray_verdict(ctrl, exp, warmup=0.05, min_n=200, p99_slack=0.10, scan_drop=0.5):
    """ctrl/exp = [(ms, scanned, ok)]。前 warmup 比例样本丢弃；样本不足不下结论。"""
    def trim(xs):
        cut = int(len(xs) * warmup)
        return xs[cut:]
    c, e = trim(ctrl), trim(exp)
    if len(c) < min_n or len(e) < min_n:
        return "样本不足（%d/%d < %d），继续观察" % (len(c), len(e), min_n), {}
    c_ms = [x[0] for x in c]
    e_ms = [x[0] for x in e]
    c_p99, e_p99 = pct(c_ms, 0.99), pct(e_ms, 0.99)
    c_err = sum(1 for x in c if not x[2]) / len(c)
    e_err = sum(1 for x in e if not x[2]) / len(e)
    c_scan = sum(x[1] for x in c) / len(c)
    e_scan = sum(x[1] for x in e) / len(e)
    m = {"p99_ctrl": c_p99, "p99_exp": e_p99, "p99_growth": e_p99 / max(c_p99, 1e-9) - 1,
         "err_ctrl": c_err, "err_exp": e_err,
         "scan_drop": 1 - e_scan / max(c_scan, 1e-9)}
    bad = []
    if m["p99_growth"] > p99_slack:
        bad.append("P99 涨 %.0f%% > %.0f%%" % (m["p99_growth"] * 100, p99_slack * 100))
    if e_err > c_err:
        bad.append("错误率 %.3f%% > %.3f%%" % (e_err * 100, c_err * 100))
    if m["scan_drop"] < scan_drop:
        bad.append("扫描行数只降 %.0f%%（索引可能没生效）" % (m["scan_drop"] * 100))
    return ("放量" if not bad else "回滚"), {"metrics": m, "reasons": bad}


if __name__ == "__main__":
    # 1) 指纹归一：5000 条同构 SQL 必须收敛成 1 个指纹
    assert fingerprint("SELECT * FROM orders WHERE id = 12345;") == \
           fingerprint("select *  from orders where id = 999")
    assert fingerprint("SELECT * FROM o WHERE id IN (1,2,3)") == \
           fingerprint("SELECT * FROM o WHERE id IN (1,2,3,4,5,6,7)")
    print("指纹归一: id=12345 与 id=999 同指纹；IN(3 项) 与 IN(7 项) 同指纹 ✅")

    # 2) 真实样本：按平均排 vs 按总耗时排，结论完全不同
    samples = []
    for _ in range(5000):                                   # 热点小查询：8ms × 5000
        samples.append(Sample("SELECT * FROM orders WHERE user_id = %d" % 42, 8.0, 200))
    for _ in range(5):                                      # 冷报表：1200ms × 5
        samples.append(Sample("SELECT * FROM orders WHERE created_at > '2026-01-01'", 1200.0, 900000))
    for _ in range(50000):                                  # 主键点查：0.4ms × 50000
        samples.append(Sample("SELECT * FROM users WHERE id = 7", 0.4, 1))
    rows, cap = aggregate(samples, window_s=120, db_busy_ratio=0.7)
    assert rows[0]["fp"].startswith("select * from orders where user_id")
    by_avg = sorted(rows, key=lambda r: r["avg"], reverse=True)
    assert by_avg[0]["fp"].startswith("select * from orders where created_at")
    print("120s 窗口 / 可用 %.0fms：按总耗时榜首=%s（占比 %.1f%%）；按均值榜首=报表查询（总占比 %.1f%%）"
          % (cap, rows[0]["fp"][:38], rows[0]["share"] * 100, by_avg[0]["share"] * 100))
    assert rows[0]["share"] > 0.4 and rows[0]["share"] > by_avg[0]["share"] * 5, "冷查询不该占用治理优先级"

    # 3) 索引代价：低区分度列打头 vs 高区分度打头，差两个数量级
    table_rows = 100_000_000
    bad = index_cost(table_rows, eq_ndv=[2], has_range=True, covering=False)
    good = index_cost(table_rows, eq_ndv=[200_000, 4], has_range=True, covering=True)
    assert bad["scanned"] > good["scanned"] * 1000
    assert good["cost_rows"] < bad["cost_rows"] / 1000
    print("1 亿行表：status(NDV=2) 打头扫 %d 行 / 代价 %.0f；user_id(NDV=20万)+status 覆盖索引扫 %d 行 / 代价 %.0f ✅"
          % (bad["scanned"], bad["cost_rows"], good["scanned"], good["cost_rows"]))
    wa = write_amplification(write_qps=3000, index_count=4)
    print("写放大: 3000 写 QPS × 4 个索引 = 每秒 %.0fms 额外维护成本（索引不是免费的）" % wa)
    assert wa > 200

    # 4) 深分页：OFFSET 10 万 vs keyset，扫描量差 5000 倍
    g = keyset_gain(offset=100_000, limit=20)
    assert g["offset_scan"] == 100020 and g["keyset_scan"] == 20
    print("深分页: offset=%d 扫 %d 行 -> keyset 扫 %d 行，%.0f 倍差距 ✅"
          % (100_000, g["offset_scan"], g["keyset_scan"], g["ratio"]))

    # 5) 灰度验证：预热样本会骗人，样本不足不能下结论
    ctrl = [(12.0, 5000, True)] * 300
    exp_warm = [(90.0, 5000, True)] * 10 + [(4.0, 30, True)] * 300   # 前 10 条是冷缓存
    verdict, info = gray_verdict(ctrl, exp_warm)
    assert verdict == "放量" and info["metrics"]["scan_drop"] > 0.9
    print("灰度(含预热): 剔除前 5%% 后 P99 %dms -> %dms，扫描降 %.0f%%，结论=%s ✅"
          % (info["metrics"]["p99_ctrl"], info["metrics"]["p99_exp"],
             info["metrics"]["scan_drop"] * 100, verdict))

    verdict2, _ = gray_verdict(ctrl[:50], exp_warm[:50])
    assert "样本不足" in verdict2
    print("灰度(50 样本): %s ✅" % verdict2)

    bad_exp = [(18.0, 5000, True)] * 300          # 改写后 P99 涨 50%，且索引没生效
    verdict3, info3 = gray_verdict(ctrl, bad_exp)
    assert verdict3 == "回滚" and len(info3["reasons"]) == 2
    print("灰度(退化): %s（%s）✅" % (verdict3, "；".join(info3["reasons"])))
```

**追问**：1) 加了索引，`EXPLAIN` 显示走了索引，为什么查询反而更慢？—— 因为「走索引」不等于「少读数据」。如果索引过滤后仍有大量行，每一行都要回表随机读，成本约为顺序扫的 3 倍；而全表扫虽然读得多，但是顺序 IO 且能预读。判断依据是「过滤后的行数 × 回表代价」与「全表行数」比较，不是看 `type` 字段。解法有二：覆盖索引（把 select 列放进索引，彻底不回表）或延迟关联（先用索引拿主键再 join，把随机读变成一次有序回表）。2) 灰度时新 SQL 的 P99 一直比旧的高 3%，但平均值更低，能放量吗？—— 不能直接放，先看 P99 高的那部分样本长什么样。常见原因是新 SQL 引入了「参数敏感」的执行计划（某个热点参数下退化成全表扫），平均值被大量快样本拉低、P99 被少数慢样本拉高。正确动作是按参数分桶再看 P99（比如按 user_id 的哈希区间），找到退化区间；如果退化区间正好是热点商户，那就是事故前兆，绝不能因为「平均更快」就放量。3) 治理完三个月，同样的慢查询又回来了，怎么防？—— 慢查询是「数据分布变化 + 代码演进」的必然产物，靠人盯不住，只能靠门禁：上线前的 `EXPLAIN` 检查（估算扫描行数超阈值拒发）、慢查询阈值分级告警、索引使用率季度回收。还有一个常被忽略的点是**统计信息**：表数据量翻倍后优化器可能选错索引，定期 `ANALYZE` 比加索引更便宜，也更容易被忘。

## 背诵要点
1. 排序口径是**总耗时占比**（`sum(ms)/窗口容量`），不是平均耗时也不是 P99；修最热的一条比修 45 条冷查询收益大一个量级。
2. 指纹必须归一（字面量、`IN` 列表、空白），否则同构 SQL 散成几千个指纹；但指纹会抹掉参数分布，要同时保留单条最慢样本。
3. 索引代价 = 过滤行数 × 回表系数（非覆盖约 3 倍）；低区分度列打头等于全表；灰度的前 5% 样本必须丢、每档 ≥200 次、P99 涨 10% 或扫描没降就回滚。

## 复盘追问
1. 同一指纹的 P99 是 2s、P50 是 3ms，这说明什么，怎么查？（提示：参数敏感型执行计划——少数热点参数（大商户、宽时间范围）让优化器改走全表；按参数分桶统计，再看这些参数下的 `EXPLAIN`，通常解法是强制索引、拆分查询或对热点参数做缓存，而不是给整条 SQL 加索引）
2. 大表加索引本身是重操作，怎么做到「业务无感」？（提示：MySQL 8 用 `ALGORITHM=INPLACE, LOCK=NONE` 在线 DDL，但仍有 IO 与复制延迟代价；先在只读副本上建、观察复制延迟，再用 invisible index 建好但不生效、验证执行计划后 `VISIBLE` 切换；低峰执行 + 限速 + 随时可 `DROP`，三步缺一不可）
