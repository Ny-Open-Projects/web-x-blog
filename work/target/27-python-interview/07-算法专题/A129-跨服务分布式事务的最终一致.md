### A129 · 分布式事务最终一致

> 难度:★★★ | 标签:分布式事务, SAGA, 场景题

**问**（笔试·场景题）：订单服务扣库存、支付服务扣款、物流服务创建运单——三个服务三个数据库，「2PC」为什么在生产几乎不用（协调者阻塞/锁跨网络），SAGA 编排型 vs 协同型的取舍是什么，补偿失败的终极兜底是什么，TCC（Try-Confirm-Cancel）适合什么场景？

**答**：① 2PC 生产不可用的三个原因：协调者单点（挂了参与者全锁）、参与者锁跨网络持有（其他事务排队——吞吐崩）、网络分区下「不确定态」 participants 无法自行决断——生产用最终一致替代。② SAGA：长事务拆成本地事务序列 + 每步对应补偿；**编排型**（中心 orchestrator 顺序调用，逻辑集中、易监控、单点风险）vs **协同型**（服务间事件链式触发，去中心化但流程分散难追踪）——步骤 ≤5 且流程稳定用编排，服务自治强用协同。③ 补偿失败兜底：补偿也有重试预算（A120），耗尽后**人工介入工单**（赔偿自动化：预授权+对账差额补偿）——终极兜底不是技术是流程（补偿设计目标：把「需要人工的案例」压到极小概率）。④ TCC：Try（资源预留：冻结额度）→ Confirm（确认扣减）→ Cancel（释放预留）——适合「不可补偿操作」的资源占用（冻结资金/锁库存），比 SAGA 多一次交互但预留语义避免「扣了再退」的用户感知。

```python
# 全部标准库；demo 实现编排型 SAGA + 补偿 + 人工兜底工单
import time, random

class SagaOrchestrator:
    """编排型 SAGA：步骤列表 + 补偿栈；补偿失败进人工工单。"""
    def __init__(self):
        self.steps = []                        # [(name, do, undo)]
        self.done_stack = []                   # 已完成步骤（倒序补偿）
        self.manual_tickets: list[str] = []
    def step(self, name, do, undo):
        self.steps.append((name, do, undo))
    def execute(self) -> str:
        for name, do, _ in self.steps:
            try:
                do()
                self.done_stack.append(name)
                print(f"  ✓ {name}")
            except Exception as e:
                print(f"  ✗ {name} 失败: {e} → 开始补偿")
                self.compensate()
                return "rolled-back"
        return "completed"
    def compensate(self):
        for name in reversed(self.done_stack):
            undo = next(u for n, _, u in self.steps if n == name)
            for attempt in range(3):           # 补偿也有重试预算（A120）
                try:
                    undo()
                    print(f"  ↩ 补偿 {name} (attempt {attempt+1})")
                    break
                except Exception:
                    if attempt == 2:
                        self.manual_tickets.append(f"补偿失败: {name} → 人工介入")
                        print(f"  ⚠ 补偿 {name} 三次失败 → 人工工单")

if __name__ == "__main__":
    random.seed(2)
    state = {"order": None, "stock": 10, "pay": 0, "logistics": None}
    saga = SagaOrchestrator()
    saga.step("create_order",
              lambda: state.update(order="ORD-1"),
              lambda: state.update(order=None))
    saga.step("deduct_stock",
              lambda: state.update(stock=state["stock"] - 1),
              lambda: state.update(stock=state["stock"] + 1))
    def pay_fail():
        if random.random() < 0.5:
            raise ConnectionError("payment gateway timeout")
        state.update(pay=99)
    saga.step("charge_payment", pay_fail,
              lambda: state.update(pay=0))
    saga.step("create_logistics",
              lambda: state.update(logistics="LOG-1"),
              lambda: state.update(logistics=None))
    result = saga.execute()
    print("结果:", result, "| 状态:", {k: v for k, v in state.items()})
    assert state["stock"] == 10 and state["pay"] == 0    # 补偿还原 ✅
    print("人工工单:", saga.manual_tickets or "无")
    # TCC 口径：Try=冻结额度（资源预留）→ Confirm/Cancel；适合「不可补偿」资源占用。
```

**追问**：1) 为什么「扣款」步骤用 TCC 而不是 SAGA 补偿（扣了再退）？——用户感知：SAGA 补偿=扣款成功又退款（短信轰炸/账单闪烁）；TCC 的 Try 只冻结不扣，Cancel 无感——资金类操作的用户体验优先 TCC。2) 编排器的「执行位置」怎么保证不单点？（提示：编排器状态持久化（每步落库）+ 崩溃后从断点重放（同 Q7017 水位）——编排单点不在进程在状态）3) 事件驱动协同型怎么防「事件乱序导致的脏补偿」？（提示：事件带实体版本号，乱序事件被丢弃（Q6013 webhook 语义）；补偿执行前重查实体当前状态，状态机条件更新）

## 背诵要点
1. 2PC 生产不可用三因：协调者单点、锁跨网络、分区不确定态——生产用最终一致。
2. SAGA 编排型（集中易监控）vs 协同型（自治难追踪），步骤 ≤5 且流程稳定用编排。
3. 补偿失败 → 重试预算 → 人工工单（把人工案例压到极小概率）；资金类用 TCC（冻结语义无感回滚）。

## 复盘追问
1. SAGA 中途用户查订单状态（部分完成），怎么展示才不误导？（提示：状态机暴露「处理中」而非「成功/失败」二态，部分完成步骤的中间态对用户透明（「已锁定库存，支付处理中」））
2. 跨服务的「扣库存 + 扣款」能不能合并成一个本地事务？（提示：同库才能本地事务；跨服务用「库存服务扣+支付服务扣」即跨库——除非把两域合库（代价：服务边界破坏），否则只能最终一致）
