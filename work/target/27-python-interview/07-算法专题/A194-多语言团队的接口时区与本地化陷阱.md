### A194 · 全球化服务陷阱

> 难度:★★★ | 标签:时区, i18n, 场景题

**问**（笔试·场景题）：服务要出海（美/欧/日用户）——「时间字段」存储与传输的统一口径（UTC 存储、本地展示），「自然日」的口径问题（「今天的订单」是哪个时区的今天——日报按什么时区切），多语言文本的存储与排序（UTF-8 够吗——排序要 locale），货币与数字格式化（千分位/小数点的地区差异）怎么处理？

**答**：① 时间三口径：**存储 UTC**（数据库统一 UTC，绝不用本地时间——Q7057 夏令时教训）、**传输 ISO8601+偏移**（API 返回带时区的 ISO 字符串或 epoch）、**展示本地化**（前端按用户时区渲染；用户时区要显式存（浏览器时区≠用户所在时区——出差的人））。② 「自然日」陷阱：「今日订单」在不同时区是不同的时间段——**业务口径时区**：日报按哪个时区切要业务定（全球产品常按 UTC 切日报 + 各地区本地日切运营报表——两个口径并存且都标注时区）；DST 切换日的一天 23/25 小时（Q7057 联动）。③ 文本与排序：UTF-8 只解决「存储」，**排序与比较要 locale**（中文拼音序/日文五十音/德语 ä——`ICU` 库（PyICU）做 collation；数据库用 UTF-8 编码但 ORDER BY 语义靠列的 collation 配置）。④ 货币/数字：**存最小单位整数**（分/仙），格式化交给前端 locale 库（`Intl.NumberFormat`）——后端不做「1,000.00」字符串格式化（后端格式化=前端无法本地化）。

```python
# 全部标准库；demo 实现「UTC 存储 + 业务日切 + locale 排序思路」
from datetime import datetime, timezone, timedelta, date
import zoneinfo

def store_utc(local_dt: datetime, tz_name: str) -> datetime:
    """本地时间 → UTC 存储（显式时区，防 naive）。"""
    tz = zoneinfo.ZoneInfo(tz_name)
    return local_dt.replace(tzinfo=tz).astimezone(timezone.utc)

def business_day(utc_ts: datetime, biz_tz: str = "Asia/Shanghai") -> date:
    """「今日订单」的业务口径：按业务时区切自然日（日报口径）。"""
    return utc_ts.astimezone(zoneinfo.ZoneInfo(biz_tz)).date()

def dst_day_length(year: int, tz_name: str = "America/New_York") -> int:
    """DST 切换日的一天不是 24 小时（23/25 小时）。"""
    tz = zoneinfo.ZoneInfo(tz_name)
    d = date(year, 3, 9)                       # 3 月第二个周日（美东春令时）
    start = datetime(d.year, d.month, d.day, 12, tzinfo=tz)
    nxt = datetime(d.year, d.month, d.day + 1, 12, tzinfo=tz)
    return int((nxt - start).total_seconds() // 3600)

# locale 排序思路：Unicode 码点序 ≠ 词典序（中文拼音/德语变音符）
names = ["张三", "李四", "Anton", "Ärger"]
codepoint_sorted = sorted(names)               # 默认码点序：Ärger 排最后（语义错误）
# 生产口径：数据库列 collation（utf8mb4_0900_ai_ci 语言规则）或 PyICU Collator
print("码点序（错误）:", codepoint_sorted)
print("正确做法: DB collation / PyICU locale 排序（拼音/五十音/变音符）")

if __name__ == "__main__":
    utc = store_utc(datetime(2026, 11, 20, 9, 0), "America/New_York")
    assert utc.hour == 14                       # 美东 9 点 = UTC 14 点
    print("UTC 存储: 美东 09:00 →", utc.isoformat())
    day = business_day(utc)
    print("业务日切（上海口径）:", day)          # 上海次日 03:00 → 归上海次日
    print(f"DST 日长度: {dst_day_length(2026)} 小时（≠24）✅")
    # 金额口径：store int cents，前端 Intl.NumberFormat 格式化（后端不做千分位字符串）。
```

**追问**：1) 为什么「存 UTC」而不是「存本地时间+时区字段」？——本地时间+时区在 DST 回拨时会**歧义**（同一本地时间出现两次，无法反推 UTC）；UTC 单调无歧义，本地展示是纯渲染问题——「存 UTC 是唯一无歧义选择」。2) 「用户时区」为什么要显式存而不是用浏览器时区？（提示：浏览器时区=物理位置（出差就变），用户期望=常用时区（出差也想看家乡时间/不想会议提醒乱跳）——显式设置+默认浏览器时区兜底，用户可改）3) 多币种存储怎么设计？（提示：每笔交易记录 `amount_cents + currency`（ISO4217），汇率快照随交易存储（结算时点汇率）——跨币种汇总按快照汇率折算到结算币种，绝不实时汇率回算历史）

## 背诵要点
1. 时间三口径：UTC 存储、ISO8601+偏移传输、本地化展示；用户时区显式存（浏览器时区≠用户期望）。
2. 「自然日」按业务口径时区切（日报 UTC、运营本地日），DST 日 23/25 小时要显式处理。
3. UTF-8 只管存储，排序靠 locale collation（DB 列配置/PyICU）；货币存最小单位整数，格式化交给前端。

## 复盘追问
1. 全球化服务的「短信发送时间」要不要跟随用户时区？（提示：营销短信必须（凌晨 3 点发=骚扰+退订）；验证码不跟（即时性优先）——按消息类型分级：时效性消息即时、体验性消息本地化时段）
2. 「按 UTC 切日报」导致欧洲团队每天看的日报是「昨天下午到现在」的错位数据，怎么平衡全球统一口径与本地体验？（提示：双口径并存：全球统一 UTC 口径（跨区对比）+ 本地口径视图（区域团队），每个报表显式标注时区口径——消灭「默认时区」的隐式假设）
