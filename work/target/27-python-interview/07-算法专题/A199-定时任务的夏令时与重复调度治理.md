### A199 · 定时任务调度治理

> 难度:★★☆ | 标签:定时任务, 调度, 治理

**问**（笔试·编程+场景题）：50 个 cron 任务散在各机器上——「同一分钟全触发」的挤峰（Q7116）、「执行机重启错过触发」（misfire 怎么补）、重复部署导致双实例双跑（Q7114）——调度治理的统一方案是什么（收敛到调度平台/任务注册表/幂等三件套），「任务该不该再跑一次」的判定规则是什么？

**答**：① 三坑统一方案：**收敛到调度平台**（集中调度：去重注册（任务指纹防双注册）、misfire 策略可配、挤峰错峰自动排布——散装 cron 的三坑一次解决）；平台三件套：任务注册表（谁/何时/幂等否）、misfire 策略（`fire_once`（错过立即补跑一次）/`skip`（跳过）/`coalesce`（合并多次为一次）——按任务幂等性选：幂等任务 fire_once、非幂等 skip+告警）、分布式锁（Q7114 双跑防）。② 「该不该再跑」判定：**幂等 → 补跑无脑安全**；非幂等 → 看窗口语义（「给用户发券」错过窗口补发用户可能已不活跃——skip+记录，业务判定要不要手动补）；判定规则预写在任务注册表（`misfire_policy` 字段），运行时机器执行不靠人当场判断。③ 挤峰治理：错峰（同分钟任务自动散布到 ±5 分钟）+ 优先级（关键任务先跑）+ 资源组（重任务分到独立 runner）。

```python
# 全部标准库；demo 实现「misfire 策略机 + 任务注册表 + 双跑锁」
import time, json

REGISTRY = {
    "send_daily_report": {"misfire": "fire_once", "idempotent": True},
    "charge_overdue_users": {"misfire": "skip", "idempotent": False, "notify": "billing-lead"},
    "refresh_cache": {"misfire": "coalesce", "idempotent": True},
}

def handle_missed(task: str, missed_count: int, registry: dict) -> str:
    policy = registry[task]["misfire"]
    if policy == "fire_once":
        return "补跑 1 次（幂等任务安全）"
    if policy == "coalesce":
        return f"合并 {missed_count} 次为 1 次（只跑最新状态）"
    # skip：非幂等任务跳过 + 业务通知
    who = registry[task].get("notify", "owner")
    return f"跳过 {missed_count} 次 + 通知 {who}（非幂等，是否手动补由业务判定）"

class DistributedRunLock:
    """双跑防：任务指纹注册 + 抢占锁（Q6535 信号量简化）。"""
    def __init__(self):
        self.locks: dict[str, float] = {}
    def acquire(self, task_fingerprint: str, ttl: float = 300) -> bool:
        now = time.monotonic()
        holder_ts = self.locks.get(task_fingerprint, 0)
        if now < holder_ts:
            return False                            # 别的实例持有中
        self.locks[task_fingerprint] = now + ttl    # 抢到：TTL 内其他实例拒绝
        return True

if __name__ == "__main__":
    for task in REGISTRY:
        print(f"{task}: 错过 3 次 →", handle_missed(task, 3, REGISTRY))
    lock = DistributedRunLock()
    assert lock.acquire("send_daily_report:v3")         # 实例 A 抢到
    assert not lock.acquire("send_daily_report:v3")     # 实例 B 双跑被拒 ✅
    print("分布式双跑锁：同指纹任务同时刻只有一实例执行 ✅")
    # 口径：散装 cron 收敛到调度平台（注册表+misfire 策略+分布式锁）；
    # misfire 策略按幂等性预写；skip 类要通知业务方人工判定。
```

**追问**：1) 为什么 misfire 策略要按幂等性预写而不是运行时人判？——错过触发时往往是深夜/事故期（人的判断力最差），预写策略让机器按登记执行；「先跑再说」的非幂等补跑是重复资损的常见来源（给用户发两次券）2) 「coalesce 合并多次为一次」适合什么任务？（提示：状态刷新类（缓存刷新/汇总表重建——只关心最新状态，中间次数无意义）；计数累加类不行（每次都要执行才能算对——次数有语义）3) 任务注册表的「任务指纹」怎么构造才稳定？（提示：任务名+参数摘要（调度器分配的任务标识）——用脚本路径当指纹在多实例路径不同时会误判双跑（实际是同一任务）——指纹与「任务逻辑身份」绑定而非部署位置）

## 背诵要点
1. 散装 cron 三坑（挤峰/misfire/双跑）统一解：收敛调度平台——注册表 + misfire 策略 + 分布式锁三件套。
2. misfire 策略按幂等性预写（幂等 fire_once / 状态类 coalesce / 非幂等 skip+业务通知）——机器执行不靠人当场判断。
3. 双跑防 = 任务指纹抢占锁（TTL），指纹绑任务逻辑身份而非部署路径。

## 复盘追问
1. 调度平台本身挂了，50 个任务怎么办？（提示：调度平台是 Tier-0（自身高可用 + 本地 cron 兜底降级（关键任务保留本机 crontab 副本，双跑靠分布式锁防）——平台不是单点，是协调点）
2. 任务「偶尔成功偶尔失败」（flaky 任务）在调度平台上怎么治理？（提示：失败率统计+连续失败升级（Q7032 SLA 口径）+ flaky 任务不准配 fire_once（幂等假象）——先修任务稳定性再谈调度策略）
