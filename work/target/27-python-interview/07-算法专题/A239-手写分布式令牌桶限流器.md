### A239 · 分布式令牌桶限流器

> 难度:★★★ | 标签:限流, 令牌桶, Redis, 时钟漂移

**问**（笔试·编程题）：现场写一个多实例共享的分布式令牌桶限流器。A101 已经给出令牌桶四连（单机惰性补给 / 滑动窗口 / Redis Lua / 预热），本题专攻分布式里最容易翻车的两点：① 用 `INCR + EXPIRE` 做窗口记账时，**突发容量**怎么控制（固定窗口的 2× 边界突发问题）；② 多机**时钟漂移**怎么不破坏限流判定（客户端时钟 +10s / −10s 各会发生什么，时钟回拨怎么办）。给出核心代码并说明取舍。

**答**：① 与 A101 的分工：A101 的 Lua 方案用客户端传入的 `now` 补币——这正是漂移的入口；本题把补币时钟换成服务端权威时钟并处理回拨，是 A101 的「分布式正确性补丁」。② `INCR+EXPIRE` 固定窗口：`INCR key` 计数，首次 `EXPIRE key window` 设 TTL，窗口过期自动归零——简单、原子（Redis 单线程）、无需脚本；代价是**窗口边界 2× limit 突发**（窗口末放行 limit + 新窗初再放行 limit），突发上限不受控。令牌桶里 `capacity` 才是真正的突发天花板，`rate` 只控长期均值。③ 时钟漂移：补币时间若取客户端本地时钟，+10s 漂移的机器能把空桶瞬间补满（多放 `10 × rate` 个令牌），−10s 的机器误拒正常请求——必须改用 **Redis TIME 服务端权威时钟**；并做**时钟回拨钳制**：当存储 ts > 当前 now（回拨残留）时按 `elapsed=0` 处理（不补币），并把 ts 拉回 now，否则回拨期间会疯狂补币。④ 取舍：固定窗口实现最简、适合容忍 2× 突发的数量级限流；令牌桶（权威时钟 + 回拨钳制）适合突发容量要精确控制的核心接口；限流器自身故障按业务分级 fail-open / fail-close（A115 同构）。

```python
# 全部标准库；本地模拟 Redis（确定性时钟），演示 INCR+EXPIRE + 令牌桶 + 漂移钳制
import threading

class FakeRedis:
    """仅模拟用到的原语：TIME / INCR+EXPIRE / HSET / HGETALL（时钟手动推进）。"""
    def __init__(self):
        self.now = 0.0                        # 服务端权威时钟
        self.hashes: dict[str, dict] = {}
        self.counters: dict[str, int] = {}
        self.expires: dict[str, float] = {}
        self.lock = threading.Lock()
    def time(self) -> float:
        return self.now
    def advance(self, dt: float) -> None:
        self.now += dt
    def expire(self, key: str, ttl: float) -> None:
        with self.lock:
            self.expires[key] = self.now + ttl
    def hset(self, key: str, **kv) -> None:
        with self.lock:
            self.hashes.setdefault(key, {}).update(kv)
    def hgetall(self, key: str) -> dict:
        with self.lock:
            if self.expires.get(key, float("inf")) <= self.now:
                self.hashes.pop(key, None)
                return {}
            return dict(self.hashes.get(key, {}))
    def incr(self, key: str, window: float) -> int:
        """INCR + 首次 EXPIRE：固定窗口，过期自动归零。"""
        with self.lock:
            if self.expires.get(key, 0.0) <= self.now:
                self.counters[key] = 0
                self.expires[key] = self.now + window
            self.counters[key] += 1
            return self.counters[key]

def fixed_window_allow(redis: FakeRedis, key: str, limit: int, window: float) -> bool:
    """方案一：INCR+EXPIRE 固定窗口（简单，但边界有 2× 突发）。"""
    return redis.incr(key, window) <= limit

def bucket_allow(redis: FakeRedis, key: str, rate: float, capacity: float,
                 cost: float = 1.0) -> bool:
    """方案二：令牌桶——补币用服务端 TIME，时钟回拨时钳制为不补币。"""
    now = redis.time()                        # 权威时钟，忽略各客户端本地时钟
    b = redis.hgetall(key)
    tokens = float(b.get("tokens", capacity))
    ts = float(b.get("ts", now))
    elapsed = max(0.0, now - ts)              # now<ts（回拨）→ elapsed=0，不补币
    tokens = min(capacity, tokens + elapsed * rate)
    ok = tokens >= cost
    if ok:
        tokens -= cost
    redis.hset(key, tokens=tokens, ts=now)    # ts 拉回权威 now
    redis.expire(key, max(2 * capacity / rate, 1.0))
    return ok

def naive_allow(tokens: float, ts: float, rate: float, capacity: float,
                client_now: float) -> float:
    """反面教材：用客户端本地时钟补币——漂移直接放大突发。"""
    return min(capacity, tokens + max(0.0, client_now - ts) * rate)

if __name__ == "__main__":
    r = FakeRedis()
    assert sum(bucket_allow(r, "u1", 5, 10) for _ in range(10)) == 10  # 突发=capacity
    assert bucket_allow(r, "u1", 5, 10) is False                        # 桶空拒绝
    r.advance(1.0)                                                      # 1s 补 5 个
    assert all(bucket_allow(r, "u1", 5, 10) for _ in range(5))
    assert bucket_allow(r, "u1", 5, 10) is False
    print("令牌桶：突发容量 10 + 速率 5/s，越界即拒 ✅")

    r4 = FakeRedis()
    first = sum(fixed_window_allow(r4, "u4", 10, 60) for _ in range(10))
    r4.advance(60)
    second = sum(fixed_window_allow(r4, "u4", 10, 60) for _ in range(10))
    assert first + second == 20                 # 窗口边界 2×limit 突发
    print("固定窗口边界:", first + second, "= 2×limit（需令牌桶 capacity 控突发）")

    r2 = FakeRedis()
    r2.now = 100.0
    r2.hset("u2", tokens=5.0, ts=200.0)          # ts 在未来 = 时钟回拨残留
    r2.expire("u2", 10.0)
    assert bucket_allow(r2, "u2", 5, 10) is True # 用现有 5 个，不因回拨狂补
    assert r2.hgetall("u2")["ts"] == 100.0       # ts 被拉回权威时钟
    print("时钟回拨钳制: ts 200 → 100，不补币 ✅")

    assert naive_allow(0.0, 0.0, 5, 10, client_now=10.0) == 10.0  # +10s 漂移补满空桶
    print("客户端 +10s 漂移：空桶被误补满（反面教材）→ 必须用服务端 TIME ✅")
```

**追问**：1) 为什么 Redis Lua 方案里也不能直接用客户端传的 `now`？——多实例部署时每个客户端时钟独立漂移，同一个桶被不同时钟的机器补币，突发上限被放大 N 倍；Lua 只保证「读-补-扣-写」原子，**不保证传入参数可信**——时间必须来自 `redis.call('TIME')`（Redis 6.2+ 可在脚本里调用），不能来自 ARGV。2) 时钟回拨为什么要「钳制为不补币」而不是「按回拨量补更多」？——回拨（now < 存储 ts）意味着系统时间倒退，正常物理时间没流逝，按负数 elapsed 补币会变「扣币」或按绝对值狂补——钳制 `elapsed=0` 是保守正确（最多少补、不放行更多），配合把 ts 拉回 now 让时钟恢复后正常补币。3) 不引入令牌桶，怎么缓解固定窗口的 2× 边界突发？——滑动窗口计数（当前窗 + 上一窗按剩余时间比例加权，A101 的近似）或双缓冲计数——把「窗口边界瞬时重叠」平滑成「加权累计」，代价是维护两个计数器，精度比令牌桶的连续补币略粗但实现仍简单。

## 背诵要点
1. INCR+EXPIRE 固定窗口简单原子，但边界有 2×limit 突发；令牌桶 capacity 才是真正突发上限，rate 控长期均值。
2. 分布式补币必须用服务端 TIME（Redis 6.2+ 脚本内 `TIME`），客户端时钟漂移 +10s 会补满空桶、−10s 误拒。
3. 时钟回拨钳制：now<ts 时 elapsed=0 不补币并把 ts 拉回 now——保守正确（宁可少补不多放）。

## 复盘追问
1. 限流器读到 Redis 超时了（网络抖动），应该放行还是拒绝？（提示：按业务分级 fail-open/fail-close（A115 同构）——核心计费接口 fail-close（宁可误拒不可超额），普通浏览 fail-open（可用性优先）；超时阈值要远小于业务容忍）
2. 令牌桶的 ts 也存在 Redis，为什么不用担心 Redis 本身时钟回拨？（提示：Redis 进程时钟也受 NTP 影响，理论上会回拨——生产用 `TIME` 命令返回的是系统墙钟，仍要钳制；更稳的做法是用单调时钟源（Redis 不暴露），或接受回拨钳制带来的短暂少补——这是分布式限流的固有精度上限）
