### A193 · 多租户公平性

> 难度:★★★ | 标签:多租户, 公平性, 资源治理

**问**（笔试·编程+场景题）：共享计算池上 100 个租户——「吵闹租户」（1 个租户吃掉 60% 资源）怎么限制（硬上限/权重公平/公平排队），「保底配额」（每个租户至少保证多少）与「总保底超容量」的矛盾怎么解，吵闹租户的「降级 vs 限流 vs 隔离」三选一怎么决策，「合法的重户」（业务确实需要量大）怎么与恶意刷量区分？

**答**：① 限制工具光谱：**权重公平**（WFQ：按套餐权重分配——重户付更多得更多，是商业模型不是公平性问题）、**硬上限**（单租户 max QPS——防失控而非防公平）、**公平排队**（无权重时每人等份额，A117 同构）。② 保底配额矛盾：100 租户 × 保底 10 QPS = 1000 QPS 总保底——**保底之和 ≤ 容量的 80%**（留 20% 余量给突发与系统开销），保底之和超容量时降低单租户保底（保底承诺必须数学上成立，超额承诺是事故源）；突发的超保底使用「尽力而为」（容量有余就给，不足时按权重挤回保底内）。③ 三选一决策：降级（吵闹租户的任务降参/降批——保留服务但降质量，适合内部任务）、限流（超保底部分拒绝——适合外部 API）、隔离（迁到专用池——适合持续重负载的大客户，商业上是「升级套餐」）。④ 重户 vs 刷量区分：**业务关联性**（重户的用量与其业务指标（订单量）成正比=合法；用量无业务解释且突增=可疑）——对账视角：合法重户是「可预测的预算膨胀」，刷量是「无法解释的异常」——风控+配额双防线。

```python
# 全部标准库；demo 实现「加权公平 + 保底配额 + 重户判别」
import hashlib, time

def weighted_share(tenants: dict[str, int], capacity: float) -> dict[str, float]:
    """按权重分容量（套餐权重）。"""
    total_w = sum(tenants.values())
    return {t: capacity * w / total_w for t, w in tenants.items()}

def check_floor_promise(floors: dict[str, float], capacity: float,
                        reserve_pct: float = 0.2) -> tuple[bool, float]:
    """保底之和 ≤ 容量 80% 才可承诺。"""
    total_floor = sum(floors.values())
    ok = total_floor <= capacity * (1 - reserve_pct)
    return ok, total_floor

def classify_heavy(usage_qps: float, biz_orders_per_day: float,
                   usage_baseline: float) -> str:
    """重户 vs 刷量：用量与业务关联性判别。"""
    if usage_qps > usage_baseline * 5:
        expected = biz_orders_per_day / 86400 * 3     # 业务量推导的合理用量
        if usage_qps > expected * 10:
            return "SUSPECT-ABUSE: 用量无法用业务量解释 → 风控介入"
        return "LEGIT-HEAVY: 用量与业务量成比例 → 走扩容/升级路径"
    return "normal"

if __name__ == "__main__":
    tenants = {"free-1": 1, "free-2": 1, "pro": 4}
    shares = weighted_share(tenants, capacity=1000)
    print("权重公平分配:", {k: round(v) for k, v in shares.items()})
    assert abs(shares["pro"] - 666) < 2
    ok, total = check_floor_promise({"free-1": 5, "free-2": 5, "pro": 50}, capacity=1000)
    print(f"保底之和 {total} ≤ 800（容量 80%）: {ok}")
    assert ok
    ok2, total2 = check_floor_promise({f"t{i}": 10 for i in range(100)}, capacity=800)
    assert not ok2 and total2 == 1000
    print("超额保底承诺拦截: 100 租户 × 10 = 1000 > 800×80% → 拒绝承诺 ✅")
    print(classify_heavy(usage_qps=500, biz_orders_per_day=100000, usage_baseline=80))
    print(classify_heavy(usage_qps=500, biz_orders_per_day=10, usage_baseline=80))
    # 口径：保底之和≤容量 80%；重户=业务可解释走扩容，刷量=不可解释走风控；
    # 降级/限流/隔离按「内部任务/外部 API/持续大客户」三选一。
```

**追问**：1) 为什么「保底之和超容量」的承诺是事故源？——所有租户同时用到保底（大促/月末集中）时容量必不足——要么全员劣化要么随机拒绝；保底承诺必须数学可满足（这是「承诺」的定义）——超卖逻辑只适用于可容忍降级的场景且需明示。2) 「合法重户」的扩容路径为什么必须顺滑？（提示：重户是最好客户（付得多）——扩容路径卡顿（审批三天）会把它逼走或逼向「压垮共享池」；自动化扩容（配额随套餐即时调整，Q115）+ 容量预留机制——大客户的成长路径就是平台的收入路径）3) 吵闹租户限流后投诉「服务不可用」，话术与兜底？（提示：限流非故障——明确告知触达套餐上限+升级路径（Q115 分级话术）；兜底=限流前 24h 预警（用量趋势触顶提醒）——告而后再限，投诉减半）

## 背诵要点
1. 限制三工具：权重公平（商业模型）、硬上限（防失控）、公平排队（无权重等份额）——吵闹租户三选一按「内部/外部/大客户」决策。
2. 保底之和 ≤ 容量 80%（留突发余量）——超额承诺是事故源；超保底使用「尽力而为+权重挤回」。
3. 重户 vs 刷量 = 用量与业务量关联性判别；合法重户走顺滑扩容路径，可疑刷量走风控。

## 复盘追问
1. 一个租户的批处理任务打爆了共享池（它有合法保底但任务失控放大了 10 倍），事后怎么防？（提示：租户侧也要限幅（单租户单任务上限）+ 失控检测（租户用量分钟级突增告警给租户自己）+ 「合法但失控」按 Q115 软限流处理而非硬切——保底保护的是正常用量不是失控用量）
2. 100 个租户的公平排队实现复杂，有更简单的近似吗？（提示：分桶轮转（租户按套餐分桶，桶内轮转）——公平性近似（桶内公平）但实现 O(桶数)；精度要求不高时是大数定律的好 trade-off）
