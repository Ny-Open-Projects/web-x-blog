### A279 · 秒杀全链路的状态账：从预热到异步落单的对账闭环

> 难度:★★★★★ | 标签:秒杀, 库存预扣, 异步落单, 削峰, 对账, 幂等

**问**（笔试·场景题）：「秒杀库存 100、开抢瞬间涌进 5 万请求」——A105 已经回答了「扣减动作本身怎么防超卖」（条件更新 CAS），本题往下挖一层，要**全链路的状态账**：① **预热**：活动前把库存从 DB 灌进 Redis，脚本可安全重放（重跑不重复灌）；② **准入削峰**：令牌桶限流 + 资格检查（每人限购 1、黑名单）两级过滤，大量请求在最便宜的门出局——断言「放行数 ≪ 请求总数」；③ **库存预扣**：Redis 原子预扣（`if stock > 0` 语义），扣成功才发进落单队列，扣失败直接「已售罄」——预扣数必须 ≤ 库存（超卖在源头不可能发生）；④ **异步落单**：落单 worker 消费队列，消息按 at-least-once 模拟重复投递，落单幂等（消息 ID 去重表）；未支付超时的订单关单回补库存——**每个预扣都有且只有一个终态**（成交或回补）；⑤ **对账闭环**：跑完断言 `redis 终态库存 = 初始库存 − 预扣 + 回补`、`成交数 = 预扣 − 回补 ≤ 库存`、`每用户成交 ≤ 1`、队列清空零遗漏——这就是秒杀的「账平」。请说清与 A105（扣减 CAS 本身）、Q2951（热点行在 DB 层怎么拆分）、A250（大促容量预案与降级阶梯）、A274（关单三机制）的分工——本题只回答「**预热到落单的全链路流水账与对账断言**」。

**答**：① 分工：A105 回答「UPDATE ... WHERE stock >= n 这一行怎么写才不超卖」，Q2951 回答「这一行太热在 DB 层怎么拆」，A250 回答「整个大促的容量怎么编排」，A274 回答「关单用什么延迟机制」——没有一张卡回答面试官真正的那一问：「**请求从进门到变成订单，中间每一层各改变哪些计数器，最后这些计数器怎么互相咬合证明没丢没重**」。本题的答案形态就是一本流水账 + 一组对账断言。② 四层的职责与记账：**预热层**只做数据搬家（DB → Redis），幂等键是 SKU（重跑前先查在位就跳过，Q1419 的预热工程化同款）；**准入层**不碰库存，只做便宜判断——令牌桶按 QPS 放行（削峰的第一刀，砍掉 90%+ 洪峰）、限购与黑名单按用户砍重复（同一用户第二次进来直接拒绝），放行数远小于请求总数是断言点：**让 99% 的请求在碰库存之前死掉，是秒杀设计的第一原则**；**预扣层**只改 Redis 一个数（`DECR` 语义，扣完 < 0 就回滚报售罄）——注意预扣成功 ≠ 成交，只是拿到「进场资格」，请求被推入落单队列后立刻返回「排队中」，用户端体验是秒回、真实结果异步出，这正是「秒杀接口为什么 50ms 就返回」的原理层答案；**落单层**是唯一的 DB 写入方：消费消息、插订单（`(user, sku)` 唯一约束兜底防重）、支付超时关单回补。③ 幂等的三处落点要分清：消息重复投递靠**消息 ID 去重表**（同一扣减消息投两次只落一次单）；用户重复点击靠**唯一约束**（第二条 INSERT 被数据库拒绝）；预扣与回补靠**流水号对账**（每个预扣流水号最终对应成交或回补之一，不允许悬空）。④ 对账闭环是本题的灵魂：`redis_final = stock - deduct + restock`、`sold = deduct - restock ≤ stock`、`每用户成交 ≤ 1`、队列末态清空——四个断言分别堵「Redis 账实不符」「超卖」「一人多件」「消息丢失」。账平了，链路里任何一层宕机重启都能靠这本账恢复（A274 的兜底思想在这里表现为「预扣流水是事实源」）。⑤ 真实系统还要补三件事本题刻意不做：Redis 与 DB 的最终一致性靠「预扣流水表 + 定时对账」而非强事务；热点 SKU 的 Redis 单 key 打满时用分段库存（Q2951 的 DB 拆分思想前移到 Redis）；全链路压测要影子库存（A269），压真实库存等于自毁活动。

```python
# 全部标准库；秒杀全链路模拟：预热/准入削峰/Redis 预扣/异步落单 + 四条对账断言
import collections


class SeckillPipeline:
    def __init__(self, sku, stock, bucket=300):
        self.sku = sku
        self.db_stock = stock
        self.redis_stock = None        # None = 未预热
        self.warmed = False
        self.bucket_tokens = bucket    # 令牌桶余量：容量即洪峰放行上限
        self.admitted = {}             # user -> 放行时间（资格闸依据）
        self.bluelist = set()          # 黑名单
        self.queue = collections.deque()          # 预扣成功待落单 (msg_id, user)
        self.seen_msgs = set()         # 落单幂等：消息 ID 去重表
        self.orders = {}               # order_no -> [user, status]
        self.user_sold = collections.Counter()    # 每用户成交数（唯一约束的镜像）
        self.ledger = collections.Counter()       # 流水账
        self._seq = 0

    # ① 预热：可重放，幂等
    def warmup(self):
        if self.warmed:
            self.ledger["warmup_skip"] += 1
            return False
        self.redis_stock = self.db_stock
        self.warmed = True
        self.ledger["warmup"] += 1
        return True

    # ② 准入：令牌桶 + 资格闸（黑名单/已放行限购），不碰库存
    def admit(self, user, t):
        if user in self.bluelist:
            self.ledger["reject_black"] += 1
            return False
        if user in self.admitted:                  # 已放行过：重复点击直接拦
            self.ledger["reject_dup"] += 1
            return False
        if self.bucket_tokens < 1:                 # 令牌桶空：限流拦截
            self.ledger["reject_rate"] += 1
            return False
        self.bucket_tokens -= 1
        self.admitted[user] = t
        self.ledger["admit"] += 1
        return True

    # ③ 预扣：Redis 原子扣减，扣成功才进队列；此步不落单
    def reserve(self, user, t):
        if not self.warmed:
            raise RuntimeError("未预热")
        if user not in self.admitted:              # 未过准入层：不可能扣库存
            self.ledger["reject_no_admit"] += 1
            return None
        if self.redis_stock <= 0:
            self.ledger["reject_soldout"] += 1
            return None
        self.redis_stock -= 1
        self.ledger["deduct"] += 1
        self._seq += 1
        msg_id = "M%d" % self._seq
        self.queue.append((msg_id, user))
        return msg_id

    # ④ 落单 worker：at-least-once 投递 + 消息 ID 幂等 + 唯一约束兜底
    def consume(self, msg_id, user):
        if msg_id in self.seen_msgs:              # 重复投递：直接吞掉
            self.ledger["msg_dup"] += 1
            return
        self.seen_msgs.add(msg_id)
        if user in self.user_sold:                # 唯一约束兜底（不应走到）
            self.ledger["uniq_block"] += 1
            return
        self.ledger["order_created"] += 1
        self.orders["ORD-%s" % msg_id] = [user, "unpaid"]

    def pay(self, order_no):
        u, st = self.orders[order_no]
        if st == "unpaid":
            self.orders[order_no][1] = "paid"
            self.user_sold[u] += 1
            self.ledger["paid"] += 1

    def close_unpaid(self, order_no):
        u, st = self.orders[order_no]
        if st == "unpaid":                        # 关单回补库存
            self.orders[order_no][1] = "closed"
            self.redis_stock += 1
            self.ledger["restock"] += 1


if __name__ == "__main__":
    STOCK = 100

    # 主链路：预热可重放
    sk = SeckillPipeline("SKU1", STOCK)
    assert sk.warmup() is True
    assert sk.warmup() is False                   # 重放被幂等闸吞掉
    assert sk.ledger["warmup"] == 1 and sk.redis_stock == STOCK
    print("预热: 首跑灌库 100，重跑跳过（幂等）✅")

    # ② 准入削峰：5000 请求涌进，令牌桶容量 300 → 只放行 300
    admitted = 0
    users = ["u%d" % i for i in range(5000)]
    for u in users:
        if sk.admit(u, t=0.0):
            admitted += 1
    for u in users[:50]:
        sk.admit(u, 0.0)                          # 已放行用户重复点击：资格闸拦
    assert admitted == 300
    assert sk.ledger["admit"] == 300              # 5000 用户只放行 300
    assert sk.ledger["reject_rate"] == 4700 and sk.ledger["reject_dup"] == 50
    print("准入: 5000 用户放行 300（限流拦 4700），50 人重复点击被资格闸拦 ✅")

    # ③ 预扣：300 人抢 100 库存 → 100 扣成、200 售罄；预扣数 ≤ 库存
    msgs = []
    for u in users[:300]:
        mid = sk.reserve(u, t=1.0)
        if mid:
            msgs.append((mid, u))
    assert len(msgs) == 100 and sk.ledger["deduct"] == STOCK
    assert sk.redis_stock == 0
    assert sk.ledger["reject_soldout"] == 200
    print("预扣: 300 抢 100 → 扣成 100、售罄拒绝 200，预扣数 == 库存（源头不超卖）✅")

    # ④ 异步落单：worker 取件后 at-least-once 重复投递，被去重表吞掉
    deliveries = []
    while sk.queue:                               # worker 从队列取件
        mid, u = sk.queue.popleft()
        deliveries.append((mid, u))
        deliveries.append((mid, u))               # 每条投两次：模拟重复投递
    for mid, u in deliveries:
        sk.consume(mid, u)
    assert sk.ledger["order_created"] == 100 and sk.ledger["msg_dup"] == 100
    assert len(sk.seen_msgs) == 100
    print("落单: 200 次投递只落 100 单（消息 ID 幂等），去重表 100 条 ✅")

    # 支付与超时关单：70 单支付、30 单超时关单回补（按落单顺序取，dict 保插入序）
    order_nos = list(sk.orders)                   # 插入序 == 消息序
    for no in order_nos[:70]:
        sk.pay(no)
    for no in order_nos[70:]:
        sk.close_unpaid(no)
    assert sk.ledger["paid"] == 70 and sk.ledger["restock"] == 30
    assert all(sk.user_sold[u] == 1 for _, u in msgs[:70])

    # ⑤ 对账闭环：四条断言咬合
    assert sk.redis_stock == STOCK - sk.ledger["deduct"] + sk.ledger["restock"]
    sold = sk.ledger["deduct"] - sk.ledger["restock"]
    assert sold == 70 and sold <= STOCK
    assert all(v <= 1 for v in sk.user_sold.values())
    assert not sk.queue and len(sk.seen_msgs) == sk.ledger["deduct"]
    print("对账: redis终态 %d = %d - 预扣%d + 回补%d；成交 %d = 预扣 - 回补 ≤ 库存；"
          "每用户 ≤ 1；队列清空 ✅"
          % (sk.redis_stock, STOCK, sk.ledger["deduct"],
             sk.ledger["restock"], sold))
```

**追问**：1) 为什么「预扣成功」不等于「成交」，中间隔一层异步会不会让用户拿到假票？—— 预扣只发放「资格」，队列才是通往 DB 的唯一通道：用户拿到的是「排队中」状态页，前端轮询/推送最终结果——这不是假票，是**把用户可见的成功与系统内的成功解耦**：DB 落单可能因唯一约束失败、支付可能超时，任何一个都需要时间裁决，同步接口等不起。代价是「扣了库存但订单失败」的窗口期（未支付关单回补），对应账上的 `restock` 流水——只要预扣流水是事实源、每个流水号有终态，窗口期就是可控成本而非漏洞。2) Redis 挂了预扣数据全丢怎么办？—— 预扣的**事实源是流水不是 Redis 余量**：每次扣减都追加流水（消息/日志），Redis 只是热状态的缓存视图——重启后重放流水即恢复余量（`stock - deduct + restock` 这个公式本身就是恢复程序）。对账任务分钟级跑一遍这个公式，账不平立即告警人工介入——这与 A274「兜底决定正确性」同源：Redis 层为速度押注、流水账为正确性兜底。若担心流量峰值把流水 MQ 压垮，本地先落盘再异步发送（WAL 思路），宁可落单慢不可流水丢。3) 限购为什么在准入层拦（已放行不再放行）而不是在落单层靠唯一约束拦？—— 两层都要，但**准入层先拦是省命的钱**：放行即意味着一次预扣尝试与一次队列消息，重复点击若放进去，会在队列里产生大量注定失败的落单（唯一约束拒绝），洪峰下这些垃圾消息就是压垮 consumer 的那根稻草。唯一约束是数据库侧的最后防线（防并发竞态穿透准入层），不是常规路径——分层过滤的原则：越便宜的门越往前放，贵的门只处理漏网之鱼（Q1885 的五道门排序在秒杀场景的具体化）。
