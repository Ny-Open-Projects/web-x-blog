### A162 · 灾备切换数据对账

> 难度:★★★ | 标签:对账, 容灾, 一致性

**问**（笔试·场景题）：主库切换（A113）后 10 分钟完成，但切换窗口内有 200 笔订单「旧主已确认、新主缺失」——对账怎么发现这 200 笔（按什么口径比对），发现后怎么修复（从哪恢复数据：旧主的 binlog？客户端重传？），「对账系统的数据源」用什么（三方权威源的思想），对账频率与覆盖面怎么平衡（全量对账跑不完）？

**答**：① 发现口径：**三方对账**——订单服务本地表 vs 支付渠道流水（权威外部源）vs DB 主从快照——单方对账（A vs B）说不清谁对谁错，外部权威源（钱真正动没动）是裁决方；按「切换窗口时间片」先扫窗口内（高危区），再扫全量（背景任务）。② 修复优先级：**先补偿用户**（资损类：缺的订单从旧主 binlog 导出 → 重放到新主或按业务语义重建——订单补建 + 用户通知），修复动作幂等（唯一约束兜底，A102）；**后修数据**（衍生表/报表重算）。③ 对账系统数据源原则：「以资金流向为准」（支付渠道流水不可篡改且独立于我方系统）——内部系统互相抄不算对账（同一 bug 会同时污染两边）。④ 全量对账跑不完：**分级对账**——窗口期/高危操作实时对账（分钟级），关键表每日全量（离线跑），全库月度抽样对账（覆盖面分层）；增量对账用「水位+摘要」（Q7017 水位 + 分块哈希），不全量比行。

```python
# 全部标准库；demo 实现「三方对账 + 窗口优先 + 修复幂等」
import hashlib, json

def reconcile_three_way(orders: dict[str, dict],    # 订单服务本地
                        channel: dict[str, dict],   # 支付渠道流水（权威）
                        snapshot: dict[str, dict],  # DB 快照（新主）
                        window: tuple[int, int] | None = None) -> dict:
    """三方对账：以渠道流水为裁决方。窗口 = (ts_start, ts_end) 过滤高危区。"""
    mismatches = []
    for pay_id, ch in channel.items():
        if window and not (window[0] <= ch["ts"] <= window[1]):
            continue
        o = orders.get(pay_id)
        s = snapshot.get(pay_id)
        if o is None:
            mismatches.append({"pay_id": pay_id, "issue": "本地缺单",
                               "fix": "从旧主 binlog 重建", "amount": ch["amount"]})
        elif o["amount"] != ch["amount"]:
            mismatches.append({"pay_id": pay_id, "issue": f"金额不符 {o['amount']} vs {ch['amount']}",
                               "fix": "以渠道为准修正", "amount": ch["amount"]})
        elif s is None or s["status"] != o["status"]:
            mismatches.append({"pay_id": pay_id, "issue": "快照状态不一致",
                               "fix": "重放该订单到快照", "amount": ch["amount"]})
    return {"checked": len(channel), "mismatches": mismatches,
            "escalate_资损": sum(1 for m in mismatches if m["amount"] > 0)}

def idempotent_rebuild(store: dict, order: dict) -> bool:
    """修复幂等：唯一键兜底，重放 N 次结果一致。"""
    key = order["pay_id"]
    if key in store:
        return False                                 # 已存在：幂等跳过
    store[key] = order
    return True

if __name__ == "__main__":
    orders = {"P1": {"pay_id": "P1", "amount": 99, "status": 1},
              "P3": {"pay_id": "P3", "amount": 50, "status": 1}}
    channel = {"P1": {"ts": 100, "amount": 99},
               "P2": {"ts": 105, "amount": 200},     # 切换窗口丢失的订单
               "P3": {"ts": 300, "amount": 50}}
    snapshot = {"P1": {"status": 1}}                 # 新主缺 P2
    r = reconcile_three_way(orders, channel, snapshot, window=(90, 120))
    assert r["checked"] == 2 and r["mismatches"][0]["pay_id"] == "P2"
    print("三方对账（窗口优先）:", r["mismatches"])
    print("资损级:", r["escalate_资损"], "笔")
    store = {}
    for m in r["mismatches"]:
        rebuilt = idempotent_rebuild(store, {"pay_id": m["pay_id"], "amount": m["amount"]})
        idempotent_rebuild(store, {"pay_id": m["pay_id"], "amount": m["amount"]})  # 重放
    assert len(store) == 1
    print("幂等修复：重放 2 次只建 1 单 ✅")
    # 口径：三方对账以外部权威源裁决；窗口优先+分级覆盖；修复动作幂等唯一键兜底。
```

**追问**：1) 为什么「内部系统互相抄」不算对账？——订单服务和支付服务都读同一个有 bug 的上游（同一 bug 同时污染两边，比对结果永远一致）；外部权威源（银行/渠道流水）独立生成，才有裁决力——对账的可信度取决于数据源的独立性。2) 修复时「从旧主 binlog 重放」会不会把切换后的新写入覆盖？（提示：重放按 pay_id 定向单笔（唯一键 upsert），不整段重放——整段重放会覆盖新主上切换后写入的其他数据；单笔幂等重放是安全的，Q6512 切换语义）3) 对账发现的不一致「是渠道错不是我们错」怎么办？（提示：渠道也有错的时候（回调丢失/重复）——双向对账：渠道多单（我方无单但渠道有流水）走退款/补单流程，渠道少单（我方有单渠道无流水）发渠道工单——对账系统的输出是「差异清单」不是「我方错误清单」）

## 背诵要点
1. 三方对账以外部权威源（渠道流水）裁决——内部互相抄无裁决力；窗口期优先+分级覆盖（实时/每日全量/月度抽样）。
2. 切换窗口丢失订单：旧主 binlog 定向单笔重放（唯一键幂等），绝不整段重放覆盖新写入。
3. 对账输出是「差异清单」（双向：我方多/渠道多都记），不是单方面错误清单。

## 复盘追问
1. 对账任务本身挂了三天没人发现（对账系统没有自己的监控），怎么办？（提示：对账系统要「自证存活」（心跳+最近一次对账时间进监控，Q7032 数据任务 SLA 同构）——对账系统的失明比不对账更危险（虚假安全感））
2. 老板问「我们对账覆盖了多少资金流」，怎么量化回答？（提示：按金额覆盖率（已对账流水金额/总流水金额）+ 时效分层（实时 X%、T+1 Y%、月度抽样 Z%）——给出「分层覆盖矩阵」而不是「都覆盖了」）
