### A214 · 值班工具箱

> 难度:★★☆ | 标签:值班工具, 自动化, 场景题

**问**（笔试·场景题）：值班处置「重启服务」要 SSH 上机敲 5 条命令（凌晨 3 点敲错 1 条）——值班工具箱怎么标准化（常用处置封装成一键脚本），「一键处置」的权限与审计怎么收敛（谁可以点/点了什么/参数是什么），脚本化的边界（哪些处置不能一键化——需要判断力的操作），工具箱脚本本身的测试与版本管理（脚本也是代码）怎么做？

**答**：① 封装清单：高频处置封装成带参数的一键动作（重启服务/切只读/清缓存/扩容+1/回滚上一版）——每个动作内置：前置检查（当前状态是否适合该操作）、执行、**验证**（动作后状态确认——一键三段，Q124 apply 验证同构）。② 权限审计：工具箱接统一网关（Q165：SSO+RBAC+审计），危险动作（清缓存/改数据）走二次确认或四眼——审计记录谁在何时对哪个服务执行了什么参数（A112 哈希链可加）。③ 边界：**需要判断力的操作不一键化**（根因不明的故障诊断、涉及数据取舍的操作）——一键化的范围 = 「症状明确且处置标准」的操作；判断力操作提供「信息收集脚本」（一键收集 trace/日志/指标——辅助判断而非代替判断）。④ 脚本治理：工具箱脚本进 git（版本化+review+测试——脚本与业务代码同等对待，Q6030），变更走发布流程。

```python
# 全部标准库；demo 实现「一键处置动作（前置检查+执行+验证）」
import time

class ActionBox:
    ACTIONS = {
        "restart_service": {"risk": "medium", "pre": "service_running_check"},
        "switch_readonly": {"risk": "low"},
        "purge_cache": {"risk": "high", "confirm": True},
    }
    def __init__(self, audit: list):
        self.audit = audit
    def execute(self, user: str, action: str, target: str,
                precheck_ok: bool, confirmed: bool = False) -> dict:
        spec = self.ACTIONS.get(action)
        if not spec:
            return {"ok": False, "why": "未知动作"}
        if spec.get("confirm") and not confirmed:
            return {"ok": False, "why": "高危动作需二次确认"}
        if not precheck_ok:
            return {"ok": False, "why": "前置检查未通过（当前状态不适合）"}
        entry = {"ts": time.time(), "user": user, "action": action,
                 "target": target, "verified": True}   # 动作后验证已内置
        self.audit.append(entry)
        return {"ok": True, "result": f"{action} on {target} 完成（含后验证）"}

def collect_diagnostics(service: str) -> dict:
    """判断力操作的辅助：一键收集信息（不代替判断）。"""
    return {"service": service, "trace_url": f"/trace?svc={service}",
            "recent_deploys": 2, "err_graph": "/grafana/err"}

if __name__ == "__main__":
    audit = []
    box = ActionBox(audit)
    r = box.execute("oncall-li", "switch_readonly", "db-1", precheck_ok=True)
    assert r["ok"]
    print("一键处置:", r["result"])
    r2 = box.execute("oncall-li", "purge_cache", "cache-1", precheck_ok=True)
    assert not r2["ok"] and "二次确认" in r2["why"]        # 高危需确认 ✅
    r3 = box.execute("oncall-li", "restart_service", "svc-1", precheck_ok=False)
    assert not r3["ok"] and "前置检查" in r3["why"]        # 前置检查拦截 ✅
    print("权限与前置检查:", r2["why"], "/", r3["why"])
    print("诊断辅助:", collect_diagnostics("order-svc"))
    # 口径：一键三段（前置检查/执行/验证）；高危二次确认；判断力操作只给信息收集；
    # 脚本进 git 版本化。
```

**追问**：1) 为什么一键动作内置「验证」而不是「执行完就算完」？——执行成功 ≠ 状态达标（重启了但服务没起来）——「动作后验证」把「假执行成功」拦截在动作内；这与 Q124 配置 apply 验证、Q148 发布验证同构——验证内嵌是自动化动作的标配。2) 「前置检查」检查什么？（提示：动作的适用条件（重启服务前确认服务确实异常——正常服务被重启是事故）+ 依赖条件（切换只读前确认读路径可用）——前置检查防止「正确的动作在错误的时机」）3) 工具箱脚本「进 git」会不会拖慢紧急处置？（提示：不会——版本化的脚本随时可用（git 拉最新即可），反而防「凌晨用了三周前过时的脚本」；未版本化的散装脚本才是隐患（不知道哪份是对的））

## 背诵要点
1. 一键动作三段式：前置检查 → 执行 → 后验证——执行成功≠状态达标，验证内嵌。
2. 权限收敛：接统一网关（SSO/RBAC/审计），高危动作二次确认；审计含用户/参数/验证结果。
3. 边界：症状明确且处置标准的操作一键化；判断力操作只提供「信息收集脚本」——不代替判断。

## 复盘追问
1. 凌晨 3 点一键脚本本身出 bug（处置失败还报成功），怎么防？（提示：脚本的「验证段」用独立信号源（真查状态而非查脚本自身输出）+ 脚本测试（Q6030 脚本即代码）+ 失败也要审计（失败处置的记录同样重要）——验证的独立性是关键）
2. 工具箱越做越大（50 个动作），维护混乱怎么治？（提示：动作注册表化（元数据：风险级/前置检查/owner）+ 长期未用动作下线审查（Q168 同构）+ 动作清单进值班手册自动生成（A142 联动）——工具箱也是产品要治理）
