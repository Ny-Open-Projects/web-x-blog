### A147 · 行动项验证与防复发

> 难度:★★☆ | 标签:复盘, 验证, 演练

**问**（笔试·场景题）：复盘行动项「给 DB 连接池加告警」标了已完成——「完成」和「有效」怎么区分（完成=代码合入，有效=故障场景下真的起作用），防复发验证怎么设计（故障注入演练），「同型事故复发 ≥3 次」的升级机制怎么设计，行动项的「验证成本」过高（要真宕机一次）时怎么办？

**答**：① 完成 vs 有效：完成 = 变更合入（代码存在）；有效 = **目标故障场景下按预期工作**（告警真的响了/熔断真的断了/幂等真的挡了）——验证方式必须是「复现故障条件」而不是「看代码存在」。② 防复发验证 = 故障注入演练：把事故的触发条件做成可重复的演练脚本（chaos：拔连接池/打满磁盘/模拟慢查询），在预发或影子环境定期跑——演练通过 = 行动项验证有效；演练失败 = 行动项回炉（重新打开）。③ 同型复发 ≥3 次升级专项：单次复盘修的是「这次的洞」，同型复发说明「这一类洞」的根因在更上层（流程/架构模式）——升级为专项治理（横切所有服务，如「所有服务统一加超时预算」），并复盘「为什么上次复盘没修到这一层」。④ 验证成本过高（要真宕机）的处理：降级为「准生产演练」（预发环境断真依赖）+ 大促前统一演练窗口（把多个高成本验证合并到一次窗口分摊）——绝不「因为难验证就不验证」。

```python
# 全部标准库；demo 实现「行动项验证器 + 复发升级」
import time

class ActionVerifier:
    def __init__(self):
        self.items: dict[str, dict] = {}       # title -> {status, drills, recurrences}
        self.recurrence_count: dict[str, int] = {}
    def register(self, title: str, verify_drill: str):
        self.items[title] = {"status": "pending",   # pending→merged→verified
                             "drill": verify_drill, "drill_ok": False}
    def mark_merged(self, title: str):
        self.items[title]["status"] = "merged"      # 代码合入 ≠ 有效
    def run_drill(self, title: str, drill_passes: bool) -> str:
        item = self.items[title]
        assert item["status"] == "merged", "演练前提：变更已合入"
        if drill_passes:
            item.update(status="verified", drill_ok=True)
            return "VERIFIED: 故障注入通过，行动项有效"
        item["status"] = "reopened"                 # 演练失败回炉
        return "REOPENED: 演练未通过，行动项重新打开"
    def record_recurrence(self, pattern: str):
        self.recurrence_count[pattern] = self.recurrence_count.get(pattern, 0) + 1
        n = self.recurrence_count[pattern]
        if n >= 3:
            return f"ESCALATE: 「{pattern}」复发 {n} 次 → 升级专项治理"
        return f"logged: {pattern} 第 {n} 次"

if __name__ == "__main__":
    av = ActionVerifier()
    av.register("连接池告警", "预发拔掉一半连接 → 告警 5 分钟内触发")
    av.mark_merged("连接池告警")
    assert av.items["连接池告警"]["status"] == "merged"
    r1 = av.run_drill("连接池告警", drill_passes=False)   # 演练失败
    assert r1.startswith("REOPENED")
    av.mark_merged("连接池告警")
    r2 = av.run_drill("连接池告警", drill_passes=True)    # 修复后重演
    assert r2.startswith("VERIFIED")
    print(r1, "→", r2, "（完成≠有效，演练才闭环）✅")
    for _ in range(3):
        print(av.record_recurrence("超时预算缺失"))
    # 口径：完成=合入，有效=故障注入通过；同型复发≥3 次升级专项；
    # 高成本验证降级为准生产演练+合并演练窗口，绝不免验证。
```

**追问**：1) 为什么「演练失败回炉」比「下次注意」有效？——回炉把行动项状态打回 pending（系统追踪），「下次注意」是无状态的口头承诺；可追踪的状态机才有闭环——这正是 A138 行动项系统的延伸。2) 「同型复发」的归组怎么定才不滥用？（提示：按「故障模式」归组（超时缺失/幂等缺失/容量不足），不按「涉及服务」归组（否则什么都算同型）——归组规则进复盘章程，同 A138 豁免边界）3) chaos 演练误伤生产怎么办？（提示：演练只在预发/影子环境 + 生产演练走「受控爆炸半径」（先低流量环境验证脚本）+ 演练负责人 on-call 在场——生产 chaos 是高级阶段，不是起步动作）

## 背诵要点
1. 完成 = 代码合入；有效 = 故障注入演练通过——验证方式必须「复现故障条件」。
2. 演练失败 → 行动项回炉（状态机 reopen），不是口头「下次注意」。
3. 同型复发 ≥3 次升级专项治理（横切所有服务）+ 复盘「为什么上次没修到这一层」；高成本验证用准生产演练+合并窗口。

## 复盘追问
1. 团队以「演练成本高」为由拒绝所有故障注入，行动项验证怎么办？（提示：区分「验证不可省」与「验证方式可选」——最低成本也要在预发复现一次；完全拒绝验证的行动项不许标完成（状态机卡住）——制度倒逼而非说服）
2. 复盘行动项越积越多（200 项 open），系统本身变噪声了怎么办？（提示：行动项也分优先级（与风险挂钩）+ 过期未完成项升级机制（A138）+ 定期合并同型项——追踪系统自己也要治理，避免追踪噪声掩盖真风险）
