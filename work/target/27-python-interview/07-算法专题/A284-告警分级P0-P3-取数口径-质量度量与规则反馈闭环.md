### A284 · 监控告警分级 P0-P3：取数口径、质量度量与规则反馈闭环

> 难度:★★★★ | 标签:监控告警, 分级, SLA, MTTA, 告警治理, 值班

**问**（笔试·场景题）：值班一夜告警 400 条没人看，P0 电话半夜响全是误报——面试官要的不是「背出 P0-P3 四行定义」，而是**分级判定的取数口径与分级体系自身的质量度量闭环**：① P0-P3 判定标准落成可执行代码：影响面（all/majority/partial/single，取数来源要在章程写死）、SLO 燃烧倍速分档（≥14 快烧 / ≥6 中速 / ≥1 慢烧 / <1 正常）、可缓解性（自动预案**生效**则整体降一级）——三者合成定级，影响面与燃烧率**取严者**；② 定级到 SLA/渠道的映射（P0 电话 15 分钟 / P1 短信 30 分钟 / P2 工单当日 / P3 周报汇总），断言各档时限严格递增；③ 用一夜告警流水算**质量度量**：按规则算可行动率（真实/触发）、按分级算精准率与 MTTA 对标 SLA；④ 度量反馈闭环：可行动率 <50% 的规则自动列入「降阈值或下线」治理清单——分级不是一次定死，是靠度量持续修剪；⑤ 说清与 Q1117（分级规则表与响应 SLA 的概念版）、A145（P0 响应超时的升级矩阵与叫醒成本）、Q2284（确认超时的自动升级）、Q7249（告警噪音盘点台账）、Q7008（SLO 燃烧率告警窗口公式）的分工——本题只回答「**定级的取数口径合成 + 分级体系自身的质量度量与反馈修剪**」。

**答**：① 分工：Q1117 给出「影响 × 紧急度」的四行规则表（概念正确但停在规则），A145 回答「定级之后叫不醒人怎么办」，Q2284 回答「升级怎么自动化」，Q7249 回答「噪音台账怎么盘点」，Q7008 给出燃烧率的窗口公式——没有一张卡回答「**这几个输入到底怎么取数、怎么合成，合成之后分级体系自己怎么被度量**」。② 取数口径是分级的命门：影响面四档的判定来源必须写进章程（all=核心链路错误率超阈值且受影响占比 >90%，majority=主要区域/机型受损，partial=单模块单租户，single=个例），口径不清的分级规则上线第一周就会被「这次算 P0 还是 P1」的撕扯磨平；燃烧倍速 = 实际消耗预算的速度 ÷ 允许速度，≥14 表示 1 小时烧光 30 天预算（Q7008 的 1h 快烧档），它把「紧急度」从主观判断变成可计算的分档。③ 合成规则取严者：影响面 P1 × 燃烧快烧 → P0（错误还在快速扩散）；影响面 all × 自动预案**已生效** → 降一级（预案兜住的部分不算用户受损）——注意生效要有证据（降级开关状态回读 + 核心指标回落两个信号都在），只验证配置不验证生效的降级是纸面降级；这条规则防止「预案明明兜住了还电话叫人」的信任损耗。④ 度量闭环的三个口径：**按规则**算可行动率——低于 50% 的规则降阈值或删掉，告警数量只减不增；**按分级**算精准率与 MTTA——P0 的 MTTA 超 15 分钟说明电话链路或排班出了问题（A145 的升级矩阵是超时后的执行器，本题度量是发现问题的温度计）；**按体系**算整体可行动率——低于 70% 说明章程本身松了。三个口径混成一个平均值，三条问题全部失去行动指向。⑤ 笔试答题结构：先章程（定义+取数口径）→ 再合成（代码可执行）→ 再度量（一夜流水算出三个数）→ 再反馈（治理清单）——这个闭环就是「告警分级」从文档变成系统的方式。

```python
# 全部标准库；告警分级：取数口径合成定级 + SLA 映射 + 一夜流水质量度量与反馈清单
SCOPE_GRADE = {"all": 3, "majority": 2, "partial": 1, "single": 0}

SLA = {
    "P0": ("15 分钟响应", "电话", 15),
    "P1": ("30 分钟响应", "短信+群", 30),
    "P2": ("当日处理", "工单", 1440),
    "P3": ("周报汇总", "周报", 10080),
}


def burn_grade(burn):
    """SLO 燃烧倍速分档：<1 正常 / >=1 慢烧 / >=6 中速 / >=14 快烧。"""
    if burn >= 14:
        return 3
    if burn >= 6:
        return 2
    if burn >= 1:
        return 1
    return 0


def grade(scope, burn, auto_mitigated=False):
    """影响面与燃烧率取严者定级；自动预案生效（有证据）则整体降一级。
    严重度档位 0-3（single->all）映射到 P3->P0：P0 最严重。"""
    level = max(SCOPE_GRADE[scope], burn_grade(burn))
    if auto_mitigated and level > 0:
        level -= 1
    return "P%d" % (3 - level)


NIGHT = [
    # 一夜告警流水：(规则, 定级, 触发分钟, ack 分钟, 是否误报)
    {"rule": "pay_error_rate", "tier": "P0", "fired": 0, "ack": 4, "false": False},
    {"rule": "login_failing", "tier": "P0", "fired": 30, "ack": 39, "false": False},
    {"rule": "db_lag", "tier": "P1", "fired": 60, "ack": 80, "false": False},
    {"rule": "db_lag", "tier": "P1", "fired": 90, "ack": 95, "false": False},
    {"rule": "db_lag", "tier": "P1", "fired": 120, "ack": None, "false": True},
    {"rule": "db_lag", "tier": "P1", "fired": 150, "ack": 160, "false": False},
    {"rule": "cache_hit_drop", "tier": "P2", "fired": 200, "ack": None, "false": True},
    {"rule": "cache_hit_drop", "tier": "P2", "fired": 240, "ack": None, "false": True},
    {"rule": "cache_hit_drop", "tier": "P2", "fired": 280, "ack": 300, "false": False},
    {"rule": "cron_delay", "tier": "P3", "fired": 400, "ack": None, "false": False},
]


def quality_report(ledger):
    """按分级算：触发数、精准率（真实/触发）、MTTA 对标 SLA。"""
    out = {}
    for tier in ("P0", "P1", "P2", "P3"):
        rows = [r for r in ledger if r["tier"] == tier]
        real = [r for r in rows if not r["false"]]
        acked = [r for r in real if r["ack"] is not None]
        out[tier] = {
            "fired": len(rows),
            "precision": len(real) / len(rows) if rows else None,
            "mtta": (sum(r["ack"] - r["fired"] for r in acked) / len(acked))
                    if acked else None,
            "sla_min": SLA[tier][2],
        }
    return out


def rule_feedback(ledger):
    """按规则算可行动率：<50% 的规则（触发 >=3 次）进治理清单。"""
    rules = {}
    for r in ledger:
        st = rules.setdefault(r["rule"], [0, 0])
        st[0] += 1
        if not r["false"]:
            st[1] += 1
    moves = []
    for rule, (fired, real) in rules.items():
        if fired >= 3 and real / fired < 0.5:
            moves.append("%s 触发 %d 次仅 %d 次真实：降阈值或下线" % (rule, fired, real))
    return moves


if __name__ == "__main__":
    # 1) 合成定级：取严者 + 预案生效降一级（降级下限锁 P1 以上语义见追问）
    assert grade("all", 20) == "P0"                       # 全量受损 + 快烧
    assert grade("all", 0.5, auto_mitigated=True) == "P1"  # 全量受损但预案兜住
    assert grade("majority", 7) == "P1"                   # 部分受损 + 中速燃烧
    assert grade("partial", 0.5) == "P2"
    assert grade("single", 0.5) == "P3"
    assert grade("single", 20, auto_mitigated=True) == "P1"  # 快烧取严 P0，降一级到 P1
    print("合成定级: 取严者 + 生效预案降一级（P0 兜底变 P1 不跨级）✅")

    # 2) SLA 映射：时限严格递增
    mins = [SLA[t][2] for t in ("P0", "P1", "P2", "P3")]
    assert mins == sorted(mins) and len(set(mins)) == 4
    print("SLA 映射: %s 时限严格递增 ✅" % (mins,))

    # 3) 一夜流水的质量度量
    rep = quality_report(NIGHT)
    assert rep["P0"]["fired"] == 2 and rep["P0"]["precision"] == 1.0
    assert abs(rep["P0"]["mtta"] - 6.5) < 1e-9
    assert rep["P1"]["fired"] == 4 and abs(rep["P1"]["precision"] - 0.75) < 1e-9
    assert abs(rep["P2"]["precision"] - 1 / 3) < 1e-9
    assert rep["P3"]["mtta"] is None                      # P3 无人即时 ack：正常
    for tier in ("P0", "P1", "P2", "P3"):
        m = rep[tier]
        mtta = "无 ack" if m["mtta"] is None else "%.1f min" % m["mtta"]
        print("  %s: 触发 %d, 精准率 %.2f, MTTA %s (SLA %d min)"
              % (tier, m["fired"], m["precision"], mtta, m["sla_min"]))
    assert rep["P0"]["mtta"] <= SLA["P0"][2]              # P0 MTTA 兑现 SLA
    print("度量: P0 精准率 1.0 / MTTA 兑现 SLA；P2 精准率仅 0.33 ✅")

    # 4) 反馈闭环：低可行动率规则进治理清单
    moves = rule_feedback(NIGHT)
    assert any("cache_hit_drop" in m for m in moves)
    assert not any("db_lag" in m for m in moves)          # 0.75 达标不进清单
    assert moves[0].endswith("降阈值或下线")
    print("反馈闭环: %s ✅" % moves)
```

**追问**：1) 「自动预案生效降一级」会不会把真 P0 压成 P1 延误处置？—— 降级的置信度来自**生效证据**（降级开关状态回读成功 + 核心指标回落，两个信号都在）而非预案「配了」就算；且只降一级不跨级：P0 兜底变 P1 仍在电话/短信链路内，P2/P3 之间再松也不影响叫人——降级梯子的下限锁在 P1 是安全设计，考的是「灵活性与兜底」的平衡而不是二选一。2) 度量为什么按规则、按分级、按体系三个口径拆开？—— 三个口径回答三个不同问题：规则级回答「这条规则该不该留」（一条 20% 精准率的烂规则会被 80% 的体系平均精准率掩盖）；分级级回答「这个 SLA 承诺兑现没有」（MTTA 超标是排班/链路问题，不是规则问题）；体系级回答「章程本身松紧是否合适」（可行动率整体低说明定级口径太宽）——混算则三条问题全失去行动指向。3) P3「信息级」要不要也接升级链？—— 不要：P3 的消费场景是周报与人查，进升级链等于把噪音重新灌回 IM；但 P3 要有**批量异常检测**——某规则一周触发 5000 条 P3，大概率是它本该是 P2/P1 而定级错了，这个检测本身进 P2 工单：分级的自纠错靠「错级也要被看见」，这正是 Q7249 台账与本卡反馈闭环的接口。
