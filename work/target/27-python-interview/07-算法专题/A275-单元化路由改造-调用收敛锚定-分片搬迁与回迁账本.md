### A275 · 单元化路由改造：调用收敛、搬迁与回迁的迁移工程

> 难度:★★★★★ | 标签:异地多活, 单元化, 路由改造, 调用收敛, 分片搬迁, 数据回迁

**问**（笔试·场景题）：A254 已回答多活的「数据归属、冲突裁决与回切闸门」——那是数据层。本题做**路由改造的迁移工程**：老单元 A 独跑多年，要长出单元 B 并把部分用户切过去。要求：① **路由表与数据物理位分离建模**：`route[]`（流量该去哪）与 `data[]`（数据实际在哪）是两张不同的表——路由先切、数据未迁时，进入 B 的用户请求会逐服务跨单元回 A 取数，实测算出「单元内闭环率」从 0% 起步；② **跨单元调用收敛（锚定）**：一条请求链上 order/inventory/coupon 三个服务各自独立寻址数据时，最坏跨单元 3 次；引入「锚定单元」——请求内第一次发现数据不在本单元后，整条链钉在数据所在单元——断言跨单元调用从 3 降到 1；③ **分片搬迁**：把 B 名下分片的数据搬过去，双写窗口 + checksum 校验通过后 `data[]` 才对齐 `route[]`，账本逐片记录（迁移前后闭环率、搬运行数），断言「route 名下分片 == 账本分片 == data 名下分片」零遗漏；④ **数据回迁**：B 缩容时把部分分片搬回 A，演示同一套账本复用，并指出回迁与 A254「故障回切」的区别（一个是主动缩容的搬迁，一个是故障恢复的数据补齐）；⑤ 全程不做取模归属（A247 已实证取模扩容搬 75%），只用分片表。请说清与 A254（数据冲突裁决与回切闸门）、Q2193（就近路由的会话亲和）、Q7175（跨 AZ 流量成本账）的分工——本题只回答「**路由改造的施工顺序：先路由后数据、调用收敛锚定、搬迁账本与回迁**」。

**答**：① 分工：A254 的模型是「数据已经在两边、怎么裁决冲突」——它默认改造已完成；本题回答改造**施工期**的三个必答题：路由和数据谁先动、跨单元调用怎么不发散、搬迁怎么不出错。施工顺序有一条铁律：**先切路由表（逻辑归属），再搬数据（物理位置），最后收敛**——反过来先搬数据后切路由，会出现「数据已在 B、流量还全打 A」的长尾跨单元期，比前者更糟，因为前者至少路由表能精确枚举受影响用户。② 闭环率是改造期的核心验收指标：`闭环率 = 1 - 跨单元调用数/总调用数`。路由切完、数据未迁的窗口里，进入 B 的用户每个服务都要跨洲回 A 取数——实测 3 服务全跨、闭环率 0%，跨洲 RTT 150ms 意味着 P99 从 80ms 涨到 500ms+，这不是「过渡期忍一忍」，而是**必须压缩到天级的窗口**（窗口越长，A/B 互相拖垮的风险越大）。③ 锚定收敛：不治理时，请求链上每个服务独立按 `route[]` 寻址，数据没到的服务各自跨一次——3 服务最坏 3 次跨洲往返。锚定的规则是：**一次请求只允许跨一次**——网关按路由表把请求送进 entry 单元，链上第一个发现「我的数据不在 entry」的服务，把后续所有服务钉在数据所在单元执行（请求头透传 `anchor_unit` 标记），跨单元次数从 3 降到 1。这不是发明新机制，是把「就近路由」的语义从「每跳各自就近」改成「**请求级锚定**」——代价是锚定单元上的服务是「替别的单元打工」，CPU 是别人的、数据是本地的，比「CPU 是本地的、数据在 150ms 外」划算得多（网络等待远大于计算时间）。实测：锚定前闭环率 0%，锚定后 66.7%（3 次调用跨 1 次），数据搬迁完成后再到 100%——三段曲线对应三个施工阶段。④ 搬迁账本：分片搬迁的工程约束是「**逐片、可校验、可回滚**」——每片走「双写窗口（写 A 必同步写 B）→ 增量追平 → checksum 校验 → 路由表原子切换 → 停写旧单元」五步，账本记录每一片的 `(shard, from, to, rows, checksum)`。断言三连：route 名下 B 分片、账本分片、data 名下 B 分片三个集合相等（零遗漏零多搬）；账本里 checksum 全绿才允许切换；搬迁后 B 用户闭环率 100%。这套账本同时是**回滚依据**：某片校验失败就单独回滚该片，不影响其余片——这正是分片表相对取模的全部工程红利（A247 实测取模扩容要搬 75%，且无法逐片校验）。⑤ 回迁与回切的区分：回迁是**主动缩容**——B 容量冗余或归属调整，把部分分片搬回 A，走的是同一套「双写-校验-切换」流程，风险是低而慢的；A254 的回切是**故障恢复**——故障单元带着缺失写入回来，必须先补数（对端 replay）再过四闸门（积压 0/冲突率/复制延迟/P99），风险是高而急的。两者的共同底座都是「搬迁账本 + checksum」，但回切多一个闸门层——把这两个概念混着答（比如把「回迁」说成「回切」）是面试里常见的露脸点。

```python
# 全部标准库；单元化路由改造：route/data 双表 + 锚定收敛 + 分片搬迁账本 + 回迁
import hashlib


def h64(s):
    return int.from_bytes(hashlib.md5(s.encode()).digest()[:8], "big")


SERVICES = ("order", "inventory", "coupon")
OLD, NEW = "unitA", "unitB"
RTT_MS = 150.0                                        # 跨单元单程 RTT


class RouteTable:
    """路由表（流量该去哪）与数据位（实际在哪）分离：改造期两者必然错位。"""

    def __init__(self, shards=256):
        self.shards = shards
        self.route = {s: OLD for s in range(shards)}   # 逻辑归属
        self.data = {s: OLD for s in range(shards)}    # 物理位置

    def shard_of(self, uid):
        return h64(uid) % self.shards

    def assign(self, shard, unit):
        self.route[shard] = unit


def request(uid, rt, anchor):
    """一条请求链：网关按 route 进单元，链上逐服务取数。
    anchor=False 每个服务独立寻址；True 则第一次跨单元后整链钉在数据单元。"""
    s = rt.shard_of(uid)
    entry = rt.route[s]
    cur, calls, cross = entry, 0, 0
    for _ in SERVICES:
        home = rt.data[s]
        if cur != home:
            cross += 1
            if anchor:
                cur = home                              # 锚定：后续服务钉在数据单元
        else:
            cur = home                                  # 本地命中，锚点不漂移
        calls += 1
    cost = cross * RTT_MS
    return calls, cross, cost


def closure_rate(uids, rt, anchor):
    calls = cross = 0
    for uid in uids:
        _, c, _ = request(uid, rt, anchor)
        calls += len(SERVICES)
        cross += c
    return 1.0 - cross / calls


class MigrationLedger:
    """搬迁账本：逐片 (shard, frm, to, rows, checksum)，回滚与审计的依据。"""

    def __init__(self):
        self.records = []

    def move(self, rt, shard, rows, checksum_ok):
        assert checksum_ok, "shard %d checksum 失败，禁止切换" % shard
        frm = rt.data[shard]
        rt.data[shard] = rt.route[shard]
        self.records.append((shard, frm, rt.data[shard], rows, True))

    def ledger_shards(self):
        return {r[0] for r in self.records}


if __name__ == "__main__":
    rt = RouteTable(256)
    uids = ["user:%d" % i for i in range(2000)]
    b_uids = [u for u in uids if rt.route[rt.shard_of(u)] == NEW]

    # 1) 改造第一步：路由表先切 32 片给 B（分片表，不取模）
    for s in range(0, 256, 8):                          # 32 片
        rt.assign(s, NEW)
    b_uids = [u for u in uids if rt.route[rt.shard_of(u)] == NEW]
    assert len(b_uids) > 0
    calls, cross, cost = request(b_uids[0], rt, anchor=False)
    assert cross == len(SERVICES) and cost == 3 * RTT_MS
    rate0 = closure_rate(b_uids, rt, anchor=False)
    assert rate0 == 0.0
    print("阶段一: 路由已切数据未迁 -> B 用户闭环率 %.0f%%，单请求跨洲 %.0fms ✅"
          % (rate0 * 100, cost))

    # 2) 锚定收敛：一次请求只跨一次，跨单元调用 3 -> 1
    calls_a, cross_a, _ = request(b_uids[0], rt, anchor=False)
    calls_b, cross_b, cost_b = request(b_uids[0], rt, anchor=True)
    assert (calls_a, cross_a) == (3, 3) and (calls_b, cross_b) == (3, 1)
    rate1 = closure_rate(b_uids, rt, anchor=True)
    assert abs(rate1 - 2 / 3) < 1e-9
    print("阶段二: 锚定后跨单元 %d->%d 次，闭环率 %.1f%%，单请求跨洲 %.0fms ✅"
          % (cross_a, cross_b, rate1 * 100, cost_b))

    # 3) 分片搬迁：逐片双写+checksum 过后 data 对齐 route，账本留痕
    ledger = MigrationLedger()
    plan = sorted(s for s in range(256) if rt.route[s] == NEW)
    for i, s in enumerate(plan):
        ledger.move(rt, s, rows=10000 + i, checksum_ok=True)
    assert ledger.ledger_shards() == set(plan)          # 账本 == 计划
    assert all(rt.data[s] == rt.route[s] for s in plan) # 数据位对齐路由
    assert closure_rate(b_uids, rt, anchor=False) == 1.0
    total_rows = sum(r[3] for r in ledger.records)
    print("阶段三: 搬迁 %d 片 / %d 行，checksum 全绿，B 用户闭环率 100%% ✅"
          % (len(plan), total_rows))

    # 4) 回迁（主动缩容）：同一账本复用，8 片搬回 A
    back = plan[:8]
    for s in back:
        rt.assign(s, OLD)                               # 路由先切回
    for s in back:
        ledger.move(rt, s, rows=10000, checksum_ok=True)
    assert all(rt.data[s] == OLD for s in back)
    assert set(back) <= ledger.ledger_shards()
    print("回迁: %d 片搬回 unitA（主动缩容，同一账本），route/data 保持对齐 ✅" % len(back))

    # 5) 施工顺序总账：三段闭环率曲线
    print("施工总账: 路由先切(0%%) -> 锚定收敛(66.7%%) -> 数据搬迁(100%%)，全程分片表可逐片回滚 ✅"
          % ())
```

**追问**：1) 「先切路由、后搬数据」的窗口里，B 上有没有能提前做的优化？—— 有三件：锚定收敛（本题实测 3→1）是立刻能做的；**读多写少的旁路缓存**——B 把热点用户的读数据按 TTL 缓存在本地，跨单元只剩写路径（写必须回数据单元，因为一致性锚在那里）；**预搬迁只读数据**——商品目录、配置这类广播读数据在切路由前先同步到 B，改造窗口里这部分天然零跨单元。剩下的订单/库存这类强一致数据，只能靠压缩窗口（搬迁工具并行度、增量追平速率）解决。2) checksum 校验怎么做才不会成为搬迁的瓶颈？—— 全量逐行比对在亿级分片上不可行，工程做法是分层的：行数计数比对（`COUNT` + 汇总校验值，如 `SUM(hash(pk+updated_at))`）先过，发现差异再二分定位到区间逐行比对——checksum 的目的是「**发现不一致**」而不是「证明一致」，正常情况下双写窗口追平后一次计数比对就该全绿；连续两轮计数不一致的片要停下来查双写链路，而不是反复重迁。3) 为什么改造期也不允许「双活写」长期存在？—— 双写窗口是搬迁手段，不是架构状态：两个单元同时可写同一分片，就必须回到 A254 的冲突裁决世界（LWW/版本向量/人工裁决）——那是为「容灾不可控性」付的税，而搬迁窗口是**自己计划出来的**，完全可以设计成「窗口内 B 名下分片的写被路由层临时拒绝（用户看到『系统繁忙』几秒）或代理回 A」，用几秒的体验代价换掉整个冲突裁决的复杂度。判断标准：**计划的变更用停写/代理收敛，不可计划的故障才用裁决器**——把裁决器当日常工具用，说明搬迁设计已经失败。
