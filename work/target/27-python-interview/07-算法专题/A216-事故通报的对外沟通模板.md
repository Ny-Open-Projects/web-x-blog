### A216 · 对外事故通报

> 难度:★★☆ | 标签:对外沟通, 事故响应, 场景题

**问**（笔试·场景题）：事故影响外部客户，客服/销售被客户轰炸——对外通报模板（状态/影响/措施/下次更新）与对内更新（A150）的差异（对外不含技术细节与根因猜测），「口径管理」（客服话术与工程进展同步——客服说的与工程做的不一致），通报的发送时机与频率，「事后通告」（postmortem 摘要对外公开吗）怎么决策？

**答**：① 对外模板四要素+两禁：状态（受影响/已恢复）、影响范围（哪些客户哪些功能——不要「部分用户」的模糊表述，尽量可定位）、已采取措施、下次更新时间——**禁技术细节**（内部架构信息）、**禁根因猜测**（猜错的根因被客户引用会变成事实）——对外语言是「状态+行动+承诺」，不是技术报告。② 口径管理：**单一事实源**（工程侧的对内更新（A150）是唯一事实源，客服话术从它派生（翻译成客户语言）——comms 角色（A150）负责「翻译」而非各自编话术）；客服收到客户问题不知道答案 → 不编造，回复「工程师正在处理，X 点前更新」——统一话术卡片随每次更新同步下发。③ 时机频率：对外更新频率低于对内（对外 30-60 分钟/次，对内 15-30 分钟/次——对外更新太频繁显得慌乱，太稀疏显得失控）；首次通报要快（事故确认 30 分钟内首条——「我们知道了，正在处理」比沉默好）。④ 事后通告决策：对外公开 postmortem 摘要（影响+原因+改进项）是行业信任建设实践（大厂常态），但需法律/合规审查（数据泄露类有披露义务与口径）——内部客户 vs 外部消费者，口径不同。

```python
# 全部标准库；demo 实现「对外通报模板 + 口径同步」
import time

class ExternalComms:
    TEMPLATE = ["status", "impact", "actions", "next_update"]
    def __init__(self):
        self.updates: list[dict] = []
        self.tech_root_cause_leak = False
    def publish(self, state: str, impact: str, actions: str, nxt: str,
                root_cause_guess: str = "") -> dict:
        assert not root_cause_guess, "对外禁根因猜测"
        upd = dict(zip(self.TEMPLATE, [state, impact, actions, nxt]))
        self.updates.append(upd)
        return upd
    def sync_to_support(self, internal_update: dict) -> list[dict]:
        """口径同步：从对内更新派生客服话术卡片（comms 负责翻译）。"""
        card = {"话术": f"工程师已定位并正在处理，预计 {internal_update['next_update']} 前更新",
                "禁语": "不要猜测原因与恢复时间"}
        return [card]

if __name__ == "__main__":
    comms = ExternalComms()
    upd = comms.publish(state="部分功能受损，正在恢复",
                        impact="华东区域订单创建功能受影响",
                        actions="已切换备用链路",
                        nxt="30 分钟后更新")
    print("对外通报:", upd)
    assert "根因" not in str(upd)
    card = comms.sync_to_support({"next_update": "14:30"})
    print("客服话术卡片:", card)
    # 口径：对外四要素（状态/影响/措施/下次更新）+两禁（技术细节/根因猜测）；
    # 对内更新为唯一事实源，客服话术由 comms 派生；首次通报 30 分钟内。
```

**追问**：1) 为什么对外「禁根因猜测」？——猜测一旦说出就被客户当成承诺/事实（「你们说是缓存问题，那什么时候彻底解决？」）；说错的猜测需要二次更正（信任双损）——对外只说「确定的事实+确定的行动」，根因在内部确认后随下次更新或事后通告发布。2) 「影响范围可定位」怎么做到？（提示：故障系统按租户/区域标注影响面（Q181 租户感知同构）——「部分用户」→「华东区域、2026-11-20 之后注册的商户」——可定位让客户自查「我在不在影响内」，减少客服压力）3) 事后通告公开的取舍？（提示：公开摘要（影响/原因/改进项）是信任建设（SRE 行业惯例）——但数据泄露类有法定披露义务与口径（法务先行）；取舍标准：披露的信息是否帮助客户自保与决策——帮助则公开，纯内部细节不公开）

## 背诵要点
1. 对外模板四要素+两禁：状态/影响/措施/下次更新；禁技术细节、禁根因猜测。
2. 口径管理：对内更新（A150）为唯一事实源，comms 负责派生客服话术卡片——不编造不猜测。
3. 频率：首次通报 30 分钟内，对外 30-60 分钟/次（低于对内频率）；事后通告公开与否按合规与信任价值决策。

## 复盘追问
1. 首条对外通报发出后发现影响范围说小了（实际更大），二次更正的信任损失怎么控？（提示：首条用保守表述（「部分功能可能受影响，正在评估」）+ 30 分钟内修正更新——首条宁小勿大（说大收回容易，说小更正难）——但「宁小」不等于隐瞒，第二次更新必须完整）
2. 客户在社交媒体抱怨比官方通报快，公关被动怎么破？（提示：官方首条通报的时间窗（30 分钟）要快于社交媒体发酵（通常 1 小时+）——通报链路的演练（发布演练含对外通报演练）确保 30 分钟内能出首条；实时监听社交渠道作为通报触发信号）
