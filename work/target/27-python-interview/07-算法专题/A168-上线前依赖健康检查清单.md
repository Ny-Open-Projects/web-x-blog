### A168 · 上线前依赖健康检查

> 难度:★★☆ | 标签:发布验证, 依赖检查, 清单

**问**（笔试·编程+场景题）：新版本连的依赖（DB/缓存/队列/第三方 API）——上线前清单要核什么（连接串指向/凭据版本/配额余量/下游版本兼容），「连了错的依赖」（测试库连生产/生产连测试）的事故形态，依赖检查自动化到什么程度（预检脚本 vs 人工核对），第三方依赖的「配额突然不够」怎么提前发现？

**答**：① 清单五项：**指向正确**（连接串/URL 指向目标环境的实例——测试连生产是最危险的事故）、**凭据匹配**（凭据与环境配对，Q6565 双账号口径）、**配额余量**（DB 连接数/Redis 内存/第三方 API 日配额——新版可能消耗更多）、**版本兼容**（依赖的组件版本满足新代码要求——QL 区分）、**降级路径可用**（依赖挂了时的降级配置真的生效）。② 「连错环境」防呆：凭据与环境的**化学绑定**（生产凭据只能在生产网络解析/使用——DNS/网络层隔离），应用启动时打印「当前环境标识」并校验（配置声明 prod 但连的是 staging → 启动失败），绝不静默继续。③ 自动化程度：预检脚本全自动（启动闸门，Q7177 配置闸门联动：连接串环境标识校验/凭据环境匹配/配额余量 API 查询——机器能查的全自动）；人工只核对「语义正确」（这个 key 是给这个功能用的吗——机器判不了语义）。④ 配额提前发现：**配额水位监控**（第三方 API 日配额用量的 80% 告警）+ 大促前配额申请流程（Q121 压测联动）——「突然不够」多因「新版本消耗翻倍」（新版本多调了 3 倍下游 API），版本发布前的下游调用次数对比（压测数据）能提前发现。

```python
# 全部标准库；demo 实现「环境绑定校验 + 配额水位检查」
import os

ENV_BOUND = {                     # 凭据指纹 → 允许的环境（凭据与环境化学绑定）
    "prod-db-credential": {"env": "prod"},
    "staging-db-credential": {"env": "staging"},
}

def preflight(app_env: str, config: dict) -> list[str]:
    """上线预检：环境绑定 + 指向 + 配额。启动失败即拦截。"""
    issues = []
    for name, cred in config.get("credentials", {}).items():
        bound = ENV_BOUND.get(cred)
        if bound is None:
            issues.append(f"{name}: 未知凭据（不在注册表）")
        elif bound["env"] != app_env:
            issues.append(f"{name}: 凭据绑定 {bound['env']} 但应用环境是 {app_env} → 拒绝启动")
    for url in config.get("endpoints", []):
        if app_env == "prod" and ("staging" in url or "test" in url):
            issues.append(f"endpoint 指向非生产环境: {url}")
    quota = config.get("third_party_quota_used_pct", 0)
    if quota >= 80:
        issues.append(f"第三方配额已用 {quota}% → 大促前申请扩容（Q121）")
    return issues

if __name__ == "__main__":
    prod_cfg = {"credentials": {"db": "prod-db-credential"},
                "endpoints": ["https://api.internal/"],
                "third_party_quota_used_pct": 85}
    issues = preflight("prod", prod_cfg)
    print("预检问题:", issues)
    assert any("配额" in i for i in issues)
    # 连错环境：声明 prod 但凭据是 staging
    wrong = {"credentials": {"db": "staging-db-credential"},
             "endpoints": ["https://staging-api.internal/"],
             "third_party_quota_used_pct": 10}
    issues2 = preflight("prod", wrong)
    assert len(issues2) == 2                          # 凭据绑定 + endpoint 指向双重拦截
    print("连错环境双重拦截:", issues2, "✅ 启动失败优于静默连错")
    # 口径：凭据与环境化学绑定（网络层隔离）+ 应用启动校验（声明 vs 实际比对）；
    # 配额水位 80% 告警 + 版本发布前下游调用次数对比。
```

**追问**：1) 为什么「启动失败优于静默连错」？——静默连错（测试连生产）的爆炸半径是数据污染/生产事故（发现时已造成损害）；启动失败只影响这一次发布（回滚即可）——不对称风险选「快的失败」；同理「连不上拒绝启动」优于「连错但能跑」。2) 「凭据与环境化学绑定」怎么实现？（提示：网络层：生产凭据只在生产网络可解析（内部 DNS 分域）/ KMS 按环境密钥加密（staging 解不开生产密文）；应用层：凭据元数据带环境标签，启动校验声明环境==标签环境——双层绑定）3) 「新版本下游调用翻倍」的提前发现，压测数据怎么用？（提示：压测时统计各依赖的调用次数（trace 数据，Q7519 口径），与旧版本对比——调用次数变化是容量规划输入（Q121 调用树），新版本调用 ×3 → 配额与容量同步扩）

## 背诵要点
1. 上线清单五项：指向正确/凭据匹配/配额余量/版本兼容/降级路径可用——启动闸门全自动。
2. 「连错环境」双重拦截：凭据与环境化学绑定（网络层）+ 应用启动校验（声明 vs 实际）——启动失败优于静默连错。
3. 配额水位 80% 告警 + 版本发布前下游调用次数对比（压测 trace 数据）提前发现消耗翻倍。

## 复盘追问
1. 依赖检查全绿但上线后还是「连错」了（DNS 解析变了），静态检查的盲区？（提示：静态检查看的是配置文件，实际连接发生在运行时（DNS 可变/负载均衡指向变）——运行时锚定：连接后回读对端身份（数据库 `SELECT current_database()`/证书 CN 校验——「连接后验证对端身份」是最终防线）
2. 清单 20 项每次上线人工过一遍太慢，自动化率怎么提？（提示：能机器查的全自动（连接串/凭据/配额 API 查询）——人工只留「语义判断」（这个依赖该不该被这个功能用）；清单条目按「自动化成熟度」标注，自动化率是发布效率 KPI）
