### A173 · 故障时刻重建

> 难度:★★★ | 标签:复盘, 时间线, 可观测性

**问**（笔试·编程+场景题）：事故后写复盘，时间线拼不出来（各人记的时间对不上、缺关键分钟）——时间线怎么「客观重建」（trace/日志/metric 交叉校准，Scribe 人工记录只是补充），三个时间源（人记/机器记/监控图）的时间偏差怎么校准（时钟漂移/NTP 跳变），「故障起点的精确判定」（第一滴血的信号是什么）怎么找？

**答**：① 客观重建优先级：**机器记录 > 人工记录**——trace（调用链时间戳）、日志（结构化事件）、metric（曲线拐点）三类机器源按事件对齐；人工记录（Scribe/聊天记录）只用于补充「决策与动作」（谁在何时做了什么操作——机器不知道人的动作）。② 时钟校准：NTP 跳变/漂移会让跨机时间线错位（Q5075 perf_counter 同源坑）——校准方法：用**同一台机器的时间戳**（如日志聚合器接收时间）做基准，各机器记录与其偏差校正；事件顺序用逻辑时钟（trace span 父子关系）兜底——绝对时间错了顺序也不能错。③ 故障起点判定：「第一滴血」= **最早的异常信号**（不是最早告警——告警有延迟）——从 metric 找拐点（哪个指标最先偏离基线）、从 trace 找首个错误 span、从日志找首个错误行——三者交叉的最小时刻 = 起点；常见误判：把「最先告警」当起点（告警滞后于故障数分钟）。

```python
# 全部标准库；demo 实现「多源时间线对齐 + 起点判定」
import time

MACHINE_EVENTS = [                    # 机器源：(绝对时间戳, 源, 事件)
    (100.00, "metric", "error_rate 开始上升（拐点）"),
    (100.02, "trace", "首个 5xx span（service=C）"),
    (100.05, "log", "首个 ERROR 行（C: connection refused）"),
    (101.10, "chat", "值班发现告警"),           # 人工源：滞后
    (102.00, "chat", "Scribe 记录开始修复"),    # 人工源：动作
]

def rebuild_timeline(events: list[tuple], skew: dict[str, float] | None = None) -> list[tuple]:
    """多源对齐：机器源按时间排序；人工源校准后并入；标注信号类型。"""
    calibrated = []
    for ts, src, ev in events:
        adj = ts + (skew or {}).get(src, 0)   # 时钟偏差校正
        kind = "machine" if src in ("metric", "trace", "log") else "human"
        calibrated.append((adj, src, kind, ev))
    return sorted(calibrated, key=lambda x: x[0])

def find_first_blood(events: list[tuple]) -> tuple:
    """故障起点 = 最早的机器异常信号（非最早告警）。"""
    machine = sorted((e for e in events if e[2] == "machine"), key=lambda x: x[0])
    return machine[0]

if __name__ == "__main__":
    skew = {"chat": -1.0, "metric": 0.0, "trace": 0.0, "log": 0.0}
    timeline = rebuild_timeline(MACHINE_EVENTS, skew)
    for t, src, kind, ev in timeline:
        print(f"  t={t:.2f} [{kind:7s}|{src:6s}] {ev}")
    first = find_first_blood(timeline)
    assert first[3].startswith("error_rate"), "起点是 metric 拐点而非告警"
    print(f"\n故障起点（第一滴血）: t={first[0]:.2f} {first[3]}——比人工发现早 ~1 分钟 ✅")
    # 口径：机器源客观重建优先、人工源补动作；时钟偏差校正+逻辑顺序兜底；
    # 起点=最早机器异常信号，不是最早告警。
```

**追问**：1) 为什么「人工记录只补动作」而不是全弃？——机器不知道「谁做了切换开关的操作」与决策动机（人的动作是时间线的关键节点）；弃人工记录=时间线只有机器视角，复盘里「为什么当时这么做」断链——两者互补：机器管「系统发生了什么」，人记管「团队做了什么」。2) 时钟偏差校正的基准选择为什么用「聚合器接收时间」？（提示：应用时间戳在生成时刻可能错（时钟漂移），但「到达聚合器的时刻」是聚合器单钟——单基准消除多钟差异；代价是忽略网络传输延迟（毫秒级，对分钟级复盘无影响））3) 「第一滴血」判定漏了更早的根因信号怎么办？（提示：复盘时向「拐点之前」扩展搜索（根因动作可能在故障显现前数小时——如一次发布）；时间线的「起点」分两段：故障显现起点（metric 拐点）与根因引入起点（变更事件）——两条都要标）

## 背诵要点
1. 时间线客观重建：机器源（trace/log/metric）排序优先，人工源校准后只补「人的动作与决策」。
2. 时钟校准用单基准（聚合器接收时间），事件顺序用 trace 逻辑关系兜底——绝对时间错顺序不能错。
3. 故障起点 = 最早机器异常信号（metric 拐点），告警滞后数分钟不可当起点；「显现起点」与「根因引入起点」两段分别标注。

## 复盘追问
1. 某关键服务的日志级别是 INFO（错误没打出来），时间线断了一截怎么办？（提示：用 trace（该服务的 span 状态）与 metric（错误率曲线）补——三源互备正是多源重建的价值；复盘行动项加「关键服务 ERROR 级别保证」）
2. 时钟跳变 5 分钟的机器上事件被排到「未来」，时间线乱了怎么修？（提示：单基准校正后仍异常的事件标「时钟异常」并按逻辑关系（trace 父子）重排——Q5075 NTP 跳变案例的复盘应用）
