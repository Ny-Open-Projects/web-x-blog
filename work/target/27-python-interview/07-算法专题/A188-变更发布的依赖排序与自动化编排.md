### A188 · 多服务发布编排

> 难度:★★★ | 标签:发布编排, 依赖排序, 场景题

**问**（笔试·编程+场景题）：一次功能要同时发 5 个服务（SDK/网关/订单/库存/前端）——发布顺序怎么定（依赖图拓扑序+兼容窗口），「兼容窗口」（新版本向下兼容旧版本的时间）怎么设计（为什么先发被依赖方），发布顺序错了会发生什么（真实事故形态），编排自动化到什么程度（全自动编排的风险）？

**答**：① 顺序原则：**先发被依赖方**（库存先于订单——库存的新接口先存在，订单的新调用才不会 404）+ 接口向下兼容（新接口兼容旧调用——则顺序可以任意，兼容窗口内两版共存）。② 兼容窗口：先发的服务保留旧接口/旧行为一个窗口期（如 2 周），等所有调用方升级后下线旧行为——「发布顺序错了」的事故形态：订单先发调用库存新接口 → 404 → 下单全挂；前端先发（依赖新网关路由）→ 白屏。③ 自动化程度：**半自动**——编排器自动算顺序+逐步执行+每步验证（A146 清单），但每步之间留人工确认点（发布是高风险动作，全自动 = 出错时自动化加速了事故）；全自动只用于「完全向下兼容」的发布（这类不需要顺序编排）。

```python
# 全部标准库；demo 实现「发布依赖排序 + 兼容窗口检查」
from collections import defaultdict

RELEASE_DEPS = {                       # 服务 -> 依赖哪些服务先发
    "sdk": [],
    "gateway": ["sdk"],
    "stock": ["sdk"],
    "order": ["gateway", "stock"],
    "frontend": ["gateway"],
}

def release_order(deps: dict[str, list[str]]) -> list[str]:
    """拓扑排序：被依赖方先发。"""
    order, done, tmp = [], set(), set()
    def visit(s):
        if s in done: return
        if s in tmp:
            raise ValueError(f"循环依赖: {'→'.join(tmp)}→{s}")
        tmp.add(s)
        for d in deps[s]:
            visit(d)
        tmp.discard(s); done.add(s); order.append(s)
    for s in deps:
        visit(s)
    return order

def compat_window_check(released: dict[str, float], now: float, window_s: float = 14*86400) -> list[str]:
    """兼容窗口：先发的服务旧行为保留期检查。"""
    expiring = []
    for svc, ts in released.items():
        if now - ts > window_s:
            expiring.append(svc)       # 窗口到期：可下线旧行为
    return expiring

def wrong_order_incident() -> str:
    return ("订单先发调用库存新接口 → 404 → 下单全挂；"
            "教训：先发被依赖方，或接口向下兼容（Q6012 契约分级）")

if __name__ == "__main__":
    order = release_order(RELEASE_DEPS)
    print("发布顺序:", " → ".join(order))
    assert order.index("stock") < order.index("order")
    assert order.index("gateway") < order.index("frontend")
    print("兼容窗口检查: sdk/网关 旧行为保留 14 天 →", 
          compat_window_check({"sdk": 0}, now=15*86400), "可下线旧行为")
    print("错误顺序事故:", wrong_order_incident())
    # 口径：拓扑序先发被依赖方；接口向下兼容则顺序自由（兼容窗口共存）；
    # 编排半自动（每步验证+人工确认点），全自动只用于向下兼容发布。
```

**追问**：1) 为什么「接口向下兼容」能让发布顺序自由？——每个服务独立发布且新旧接口共存，调用方升级时机自选——没有顺序约束；代价是兼容代码的维护期（Q6012 契约分级的 backward 模式），窗口结束统一下线旧接口（Q150 废弃流程）。2) 编排器每步「人工确认点」会不会让发布太慢？（提示：确认点是「看一眼验证结果+点确认」（10 秒级），不是人工执行；全自动的收益（省 10 分钟）vs 风险（自动化加速事故）不成比例——高频低风险发布才全自动）3) 5 个服务里 2 个发布了、3 个卡住了（发现问题暂停），已发的 2 个怎么办？（提示：向下兼容设计下：已发服务行为兼容旧版（新接口没人调也无害），无需回滚——这正是「先兼容后发布」的价值；若不兼容则必须回滚已发的）

## 背诵要点
1. 发布顺序 = 依赖图拓扑序，先发被依赖方；接口向下兼容（backward）则顺序自由。
2. 兼容窗口：先发服务旧行为保留 2 周，调用方升级完统一下线旧接口（Q150 废弃流程）。
3. 编排半自动：自动算序+逐步执行+每步验证，人工确认点保留；全自动仅限向下兼容发布。

## 复盘追问
1. 「兼容窗口」到期下线旧行为时，发现还有 1 个调用方没升级，下线吗？（提示：下线——窗口内多次通知未迁移（Q150 默认弃权口径），再等就是无限期兼容；410+指引让其失败可见，比永远兼容更健康）
2. 拓扑序有多个合法顺序（sdk→gateway→stock→order 与 sdk→stock→gateway→order 都合法），怎么选？（提示：按风险升序（低风险先发验证基础设施）+ 按业务价值（核心链路后发，观察前期发布）——拓扑序是约束不是计划，编排器在约束内按风险排）
