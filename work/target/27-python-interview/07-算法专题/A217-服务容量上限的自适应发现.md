### A217 · 容量上限自适应发现

> 难度:★★★ | 标签:容量规划, 压测, 自适应

**问**（笔试·编程+场景题）：「单实例容量 3000 QPS」是半年前压测的——容量数字的失效方式（依赖变慢/代码变更/数据增长都会让真实容量漂移），「自适应发现」怎么实现（从生产流量本身反推容量：延迟-负载曲线的拐点检测），「水位触发扩容」的阈值怎么定（70% 还是 80%——与「负载-延迟曲线的非线性」的关系），生产压测（影子流量）与离线压测的容量数字为什么差 30%？

**答**：① 容量漂移三因：依赖变慢（下游 P99 涨了，等的时间变长，单实例可处理并发数下降——Little's Law：并发 = QPS × 延迟，延迟涨容量降）、代码变更（新版本单请求成本变化）、数据增长（查询扫描量涨）——**静态容量数字必然漂移**。② 自适应发现：生产流量本身是探针——记录「负载-延迟」散点（每天不同时段负载不同，天然覆盖不同负载水平），拟合曲线找拐点（延迟开始超线性增长的负载点=实际容量）——无需主动压测，流量就是压测。③ 水位阈值：负载-延迟曲线在容量点附近是**非线性拐点**（排队理论：利用率 80% 后延迟指数涨）——扩容触发应设在拐点之前（70-75% 利用率），80% 触发就已经在非线性区内（扩容追不上恶化）——阈值与曲线形状绑定而非拍脑袋。④ 离线 vs 影子差 30% 的原因：离线环境依赖是 mock/局域网/数据量小——影子压测（Q121）在生产真实依赖上测，数字才可信；两者差异本身是「环境不等价」的度量（Q141）。

```python
# 全部标准库；demo 实现「负载-延迟拐点检测」
import math

def find_capacity_knee(load_latency: list[tuple]) -> dict:
    """负载-延迟散点找拐点：延迟/负载比首次显著上升的负载点。"""
    pts = sorted(load_latency)
    ratios = [(load, lat / max(load, 1)) for load, lat in pts]
    base = statistics_median([r for _, r in ratios[:len(ratios)//3]])  # 低负载区基准比
    knee = None
    for load, ratio in ratios:
        if ratio > base * 1.5:                 # 比值超基线 1.5 倍 = 进入非线性区
            knee = load
            break
    return {"knee_load": knee or pts[-1][0], "base_ratio": round(base, 4),
            "safe_threshold": int((knee or pts[-1][0]) * 0.72)}   # 扩容触发 = 拐点 × 72%

def statistics_median(xs):
    xs = sorted(xs)
    n = len(xs)
    return xs[n // 2] if n % 2 else (xs[n//2 - 1] + xs[n//2]) / 2

def littles_law_capacity(avg_latency_s: float, concurrency: int = 200) -> float:
    """Little's Law：容量 = 并发数 / 平均延迟（延迟涨容量降）。"""
    return concurrency / avg_latency_s

if __name__ == "__main__":
    # 模拟生产负载-延迟散点：2000 QPS 后延迟开始超线性
    pts = [(q, 0.02 + 0.000003 * q ** 1.8 / 10) for q in range(500, 5000, 250)]
    r = find_capacity_knee(pts)
    print("拐点负载:", r["knee_load"], "| 扩容触发阈值:", r["safe_threshold"])
    assert r["safe_threshold"] < 2500
    # Little's Law 演示：延迟从 50ms 涨到 100ms，容量减半
    c50 = littles_law_capacity(0.05); c100 = littles_law_capacity(0.10)
    assert c100 == c50 / 2
    print(f"Little's Law: 延迟 50ms→100ms，容量 {c50:.0f}→{c100:.0f}（依赖变慢即容量漂移）✅")
    # 口径：流量即压测（负载-延迟曲线找拐点）；扩容阈值=拐点×72%（非线性区前）；
    # 离线 vs 影子差 30% = 环境不等价的度量。
```

**追问**：1) 为什么扩容触发「拐点 × 72%」而不是拐点本身？——拐点是「延迟开始恶化」的起点，到达拐点时已经踩进非线性区（排队理论下恶化速度指数涨）；72% 留出「扩容动作完成前」的余量（扩容要分钟级，流量还在涨）——阈值必须为「扩容延迟」预留空间。2) 「流量即压测」的局限？（提示：生产流量永远达不到「故障场景」的负载（未测试过的异常峰值）——自适应发现覆盖「日常负载范围」，极端峰值仍需主动压测；两者互补：日常自适应校准 + 周期性主动压测验证极端）3) Little's Law 在容量规划里怎么用？（提示：并发上限（线程池/连接池大小）÷ 目标延迟 = 理论 QPS 上限——反推：目标 QPS 需要的并发数 = QPS × 延迟——连接池 sizing（Q6046）的理论基础）

## 背诵要点
1. 容量数字必然漂移（依赖变慢/代码变更/数据增长）——静态数字半年必失效，Little's Law 解释漂移机制。
2. 自适应发现 = 生产流量当探针，负载-延迟曲线找拐点（比值超基线 1.5 倍）；扩容阈值 = 拐点 × 72%（非线性区之前）。
3. 离线 vs 影子压测差 30% = 环境不等价的度量；日常自适应校准 + 周期性主动压测互补。

## 复盘追问
1. 自适应发现显示容量只剩 1500 QPS（半年前 3000），但流量已经 2000——这是已经超载了，怎么办？（提示：立即应急（限流/扩容止血）+ 根因排查（延迟为何翻倍：依赖慢？代码退化？）——自适应发现的价值正是「在事故前发现容量已缩水」；发现即超载说明监测起步晚了，扩容先行排查并行）
2. 拐点检测在流量平稳期失效（负载范围窄，曲线无拐点）怎么办？（提示：平稳期负载范围窄→主动补充「梯度探针」（可控的小幅加压扫描负载空间）——自适应+主动探针混合；纯被动发现的边界在「流量多样性不足」）
