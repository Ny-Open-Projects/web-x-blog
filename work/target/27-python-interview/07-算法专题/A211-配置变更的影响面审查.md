### A211 · 配置变更影响审查

> 难度:★★☆ | 标签:配置变更, 影响面, 场景题

**问**（笔试·场景题）：把「缓存 TTL 从 3600s 改成 86400s」（24 小时）——改之前影响审查清单：谁在读这个 TTL（读路径行为变化）、容量影响（缓存内存涨 24×？命中率变化）、失效语义（批量过期窗口变化）、回滚方案（改回来就完事吗——缓存里已有 24h TTL 的键怎么清）、依赖的隐式假设（代码里有没有写死 3600）？

**答**：① 审查五问：**谁消费**（代码里读该配置的所有路径——grep 配置名）、**容量影响**（TTL ×24 = 缓存内存峰值 ×24（同写入速率下），Redis 内存余量够吗，Q6518）、**失效语义**（过期窗口从 1 小时变 24 小时——数据更新后最长脏 24 小时，业务能接受吗）、**集群效应**（TTL 拉长后原有过期分布改变——不会集中过期反而降低雪崩风险，Q6114）、**回滚完整性**（配置改回 3600 后，**已写入的 24h TTL 键仍是 24h**——回滚不回溯存量，需要主动清理或等待自然过期——这是配置回滚最常被忽略的部分）。② 隐式假设排查：代码里 `TTL = 3600` 硬编码（配置只改了一处，代码里另一处没跟着变——半新半旧行为）、监控阈值假设（告警规则写死「缓存命中率 <90% 告警」——TTL 拉长后命中率基线变化，误报/漏报）。③ 审查的自动化：配置变更 diff 自动触发「消费方扫描」（grep 配置名全库）+ 「容量模拟」（新 TTL 下内存峰值估算）——审查清单机器生成，人工判断结论。

```python
# 全部标准库；demo 实现「配置影响审查器」
import re

CONSUMERS = {                      # 配置名 -> 消费方代码位置（真实由 grep 生成）
    "cache_ttl_s": ["cache/set.py:42", "monitor/rules.py:88"],
}

def review_ttl_change(old: int, new: int, redis_free_gb: float,
                      write_qps: float, avg_value_kb: float) -> dict:
    report = {}
    # ① 容量影响：TTL ×倍数 = 存活键数 ×倍数 → 内存峰值
    peak_mult = new / old
    extra_gb = write_qps * new * avg_value_kb / 1024 / 1024
    report["memory_peak_extra_gb"] = round(extra_gb, 2)
    report["memory_ok"] = extra_gb <= redis_free_gb
    # ② 脏数据窗口：更新后最长脏 new 秒
    report["stale_window_s"] = new
    # ③ 隐式假设：消费方代码里的硬编码值
    for loc in CONSUMERS["cache_ttl_s"]:
        if "monitor" in loc:
            report.setdefault("implicit_assumptions", []).append(
                f"{loc}: 监控基线假设 TTL={old}，变更后需复核告警阈值")
    # ④ 回滚完整性：存量键仍是 new TTL
    report["rollback_note"] = f"改回 {old} 后存量键 TTL 仍为 {new}s——需 TTL 重写或等自然过期"
    return report

if __name__ == "__main__":
    r = review_ttl_change(old=3600, new=86400, redis_free_gb=2.0,
                          write_qps=500, avg_value_kb=8)
    print(r)
    assert not r["memory_ok"] or r["memory_peak_extra_gb"] <= 2.0
    # demo: 500 qps × 86400s × 8KB ≈ 33GB >> 2GB → 内存不 OK
    assert r["memory_peak_extra_gb"] > 30, "TTL×24 后内存峰值应显著上涨"
    assert any("监控基线" in a for a in r.get("implicit_assumptions", []))
    print("影响审查：容量/脏窗/隐式假设/回滚完整性 四维齐备 ✅")
    # 口径：改配置前过五问（谁消费/容量/失效语义/集群效应/回滚完整性）；
    # 回滚不回溯存量——TTL 类变更需主动清理或等自然过期。
```

**追问**：1) 为什么「回滚不回溯存量」是配置回滚最容易踩的坑？——配置回滚只改「未来写入的参数」，已产生的效果（已写入的长 TTL 键/已扩的连接池/已发的通知）不会自动消失——「回滚配置 = 恢复参数」是错觉，恢复的是「参数」不是「状态」；需要配套的「存量清理动作」。2) 「监控基线假设」怎么系统性防？（提示：告警阈值与配置联动（阈值引用配置中心值而非硬编码——配置变更自动重算基线），或告警规则评审时检查「该告警依赖的配置最近有没有变更」——隐式假设靠 diff 工具暴露）3) TTL 拉长 24 倍的业务动机通常是「省回源」，有没有更好的替代方案？（提示：TTL 拉长治标——数据更新后脏窗口也拉长；正解：更新事件主动失效（写时删除，Q6508）+ TTL 只做兜底——「TTL 兜底 + 主动失效」优于「纯 TTL 拉长」）

## 背诵要点
1. 配置变更五问：谁消费/容量影响/失效语义（脏窗口）/集群效应/回滚完整性——审查清单机器生成人工判断。
2. 回滚不回溯存量：TTL 类变更改回参数后存量键仍是新值——需主动清理或等自然过期。
3. TTL 治脏数据的正解：「更新事件主动失效 + TTL 兜底」优于「纯 TTL 拉长」。

## 复盘追问
1. TTL 从 1h 改 24h 后「命中率提升明显」，团队想再改到 7 天——怎么劝？（提示：命中率提升 ≠ 收益——脏窗口同步拉长（数据更新后 7 天旧值），用「脏数据投诉」换「回源成本」要业务方拍板；正解是主动失效机制而非无限拉长 TTL）
2. 影响审查发现「有 3 处代码硬编码 3600 没走配置中心」，这是债务吗？（提示：是——「配置应走配置中心」的债（A140 台账口径：有意识妥协），且本次变更已造成「半新半旧」行为——先修硬编码再改配置，顺序不能反）
