### A256 · 任务重试与退避调度器

> 难度:★★★★ | 标签:任务调度, 指数退避, 抖动, 幂等键, 死信

**问**（笔试·编程题）：实现一个可嵌入服务进程的重试调度器，要求：① **单线程 tick 驱动**，用最小堆按 `due` 排序，不能用「每个任务一个线程 + `sleep`」；② **指数退避 + 抖动**，支持 `full` / `equal` / `none` 三种抖动模式，退避上限可配，且抖动必须可注入随机源（同 seed 结果可复现）；③ **幂等键去重**——同一个业务键重复提交只能执行一次，执行完成后一段时间内重复提交仍要拒绝（终态保留期），过期后才允许重新提交；④ **并发上限**——同时在跑的任务不超过 N 个，超出的排队而不是丢弃，且要能算出 makespan（4 个耗时 1s 的任务在 2 个 worker 下必须是 2s，不是 4s）；⑤ **死信**——超过最大尝试次数进死信队列，不允许无限重试；⑥ **可持久化/可恢复**——说明重启后堆怎么重建、为什么 `due` 必须存墙钟而不是 `monotonic`。请说明与 A120（重试策略矩阵：白名单/预算/幂等前提）、A204（跨服务重试纪律与放大系数）的分工，并给出调度器自身的三个必踩坑。

**答**：① 分工：A120 回答「**该不该重试**」（错误分类白名单、非幂等禁止自动重试、全局预算），A204 回答「**每层重试几次**」（3×3×3 的放大、每层递减、预算联动）。两者都是策略层，产出是一组参数。本题是**执行层**：拿到「可重试 + 最多 4 次 + 基值 0.5s + 上限 8s + full jitter」这组参数之后，怎么在进程里准时、不重复、不堆积地把任务再跑一遍。策略定错了会放大故障，执行写错了会**重复执行**——后者对非幂等操作（扣款、发券）是直接的资损，比放大严重得多。② 为什么不能用线程 + sleep：1 万个待重试任务就是 1 万个线程（或 1 万个 `Timer`），栈内存 ~8MB/线程直接 OOM，而且线程唤醒依赖内核调度，精度差、不可观测、进程重启全丢。正确结构是**一条时间线**：所有任务放在按 `due` 排序的最小堆里，一个调度线程算出「下一个到期时刻」，`wait` 到那个时刻再批量取出所有 `due <= now` 的任务。这样不管多少任务，线程数恒为 1（或 1 个调度 + N 个 worker），内存是 O(任务数) 的记录而不是 O(任务数) 的栈。③ 退避与抖动：`delay = min(cap, base × 2^attempt)` 解决「越失败越慢点试」，但**不解决同步**——下游一挂，1 万个客户端在同一毫秒失败，退避后仍在同一毫秒重试，形成脉冲式雪崩。抖动的三种常见做法：`none`（不抖，用于单测和确定性回放）、`equal`（`delay/2 + rand(0, delay/2)`，保留最小间隔，适合需要保序的补偿）、`full`（`rand(0, delay)`，AWS 推荐，打散最彻底，代价是可能立刻重试——所以**重试下限**要单独设，比如不低于 50ms，否则失败后 0.1ms 就再来一次，等于没退避）。抖动必须**注入随机源**，否则「线上重试时间不可复现」会让所有事故复盘变成猜谜；测试里同一个 seed 必须得到同一条时间线。④ 幂等键：去重表要有**三态**——`inflight`（已提交未完成，重复提交直接拒绝）、`done`（终态，保留期内拒绝）、`gone`（保留期过，允许重新提交）。只做「提交时查一下」是不够的：任务在队列里、正在执行、执行成功这三个时刻都可能收到重复提交，其中**执行成功后的重复**最危险（业务方超时重试，而你这边其实已经扣款成功）。保留期长度由业务定：支付类 24 小时以上（跨日对账），通知类几分钟即可；保留期过长会让去重表无限膨胀，必须有 GC。更强的一层是**数据库唯一约束**兜底——去重表只能挡住「同一个调度器实例」，多实例或跨进程必须靠 `UNIQUE(idem_key)`，两次防线缺一不可。⑤ 并发上限：用「worker 空闲时刻的最小堆」建模，取最早空闲的 worker，`start = max(due, slot_free)`，`finish = start + cost`。这样 4 个 1s 任务在 2 个 worker 下 makespan 恰好 2s，而「串行执行」是 4s、「不限并发」是 1s，三个数字都能被断言。生产里还有一种更隐蔽的拥塞：**队头阻塞**——一个长任务占着 worker，后面 100 个短任务全等它，表现为「P99 突然飙升但 CPU 不高」。解法是按任务时长分池（快慢隔离）而不是无脑加 worker。⑥ 死信：`attempts >= max_attempts` 必须停，且要**记录最后一次错误 + 完整尝试历史**，否则死信队列只是一堆「失败了」的孤儿记录，没人能修。死信率是核心告警指标：正常应 < 0.1%，突然升高说明下游挂了或重试参数不合理（比如把 4xx 也当可重试，永远重试不成功）。⑦ 持久化：内存堆重启即丢，所以任务在入堆前必须先落库（`idem_key`, `due_at`, `attempts`, `payload`, `state`），调度器只是「数据库的加速视图」——启动时 `SELECT ... WHERE state='ready' AND due_at <= now + 5min` 重建堆，过期的立刻执行，未来的按序等。这里有个必须点破的细节：**`due` 必须存墙钟（UTC 毫秒），不能存 `monotonic`**，因为 `monotonic` 的起点是进程/机器启动时间，重启后完全不可比；进程内计时用 `monotonic` 防时钟回拨，跨重启的持久化时间必须用墙钟，两者不要混。⑧ 三个必踩坑：**堆里的僵尸条目**——同一个 key 重试多次会在堆里留多条记录（旧 due 已出队但状态已变），出队时必须校验「这条记录的 due 与任务当前 due 一致」，否则会把已经成功的任务再跑一遍；**重复投递**——worker 执行成功但写回状态失败（进程被杀），重启后任务仍是 `ready`，会再执行一次，所以**执行侧必须幂等**（唯一约束/状态机条件更新），调度器的去重表救不了这种情况；**队头阻塞与饥饿**——纯按 due 排序时，一个每秒重试的失败任务会持续占据 worker，长任务永远排不上，需要按优先级/租户做多队列或加权公平（A117 的公平性同构）。⑨ 可观测性：至少要暴露四个数——`ready` 队列深度、`inflight` 数、重试次数分布（第 1/2/3 次各多少）、死信率。只看「成功率」会被掩盖：成功率 99% 但重试次数分布右移，说明下游在恶化，此时离雪崩只差一次流量高峰。

```python
# 全部标准库；最小堆时间线 + 三种抖动 + 幂等键三态 + worker 槽位 + 死信
import heapq
import random
import time


class Scheduler:
    """单线程 tick 驱动的重试调度器：due 最小堆 + worker 空闲时刻堆。"""

    def __init__(self, *, base=0.5, cap=8.0, jitter="full", max_attempts=4,
                 max_workers=2, min_delay=0.05, clock=time.monotonic, rng=None):
        self.base, self.cap = base, cap
        self.jitter = jitter
        self.max_attempts = max_attempts
        self.max_workers = max_workers
        self.min_delay = min_delay
        self.clock = clock
        self.rng = rng or random.Random()
        self._heap = []          # (due, seq, key)
        self._tasks = {}         # key -> dict(state/attempts/due/cost/fn/finished_at)
        self._seq = 0
        self._dead = []
        self.timeline = []       # (start, key, attempt, ok, finish)

    def _next_seq(self):
        self._seq += 1
        return self._seq

    def _push(self, key):
        t = self._tasks[key]
        heapq.heappush(self._heap, (t["due"], self._next_seq(), key))

    # ---------- 提交与去重 ----------
    def submit(self, key, fn, *, cost=0.1, now=None):
        """返回 True=新任务入队；False=重复提交（inflight 或终态保留期内）。"""
        if key in self._tasks:
            return False                      # 三态去重：inflight / done 都拒绝
        now = self.clock() if now is None else now
        self._tasks[key] = {"state": "ready", "attempts": 0, "due": now,
                            "cost": cost, "fn": fn, "finished_at": None,
                            "last_error": None}
        self._push(key)
        return True

    def gc(self, now, keep=60.0):
        """终态保留期到期后清理，否则去重表只增不减。"""
        gone = [k for k, t in self._tasks.items()
                if t["finished_at"] is not None and now - t["finished_at"] > keep]
        for k in gone:
            del self._tasks[k]
        return len(gone)

    # ---------- 退避 ----------
    def backoff(self, attempts):
        raw = min(self.cap, self.base * (2 ** attempts))
        if self.jitter == "none":
            d = raw
        elif self.jitter == "equal":
            d = raw / 2 + self.rng.uniform(0, raw / 2)
        elif self.jitter == "full":
            d = self.rng.uniform(0, raw)
        else:
            raise ValueError("未知抖动模式: %s" % self.jitter)
        return max(self.min_delay, min(d, self.cap))   # 下限防「秒回」，上限防无限拖

    # ---------- 执行 ----------
    def run_until(self, until):
        free = [0.0] * self.max_workers            # 每个 worker 的空闲时刻
        heapq.heapify(free)
        while self._heap:
            due, _, key = heapq.heappop(self._heap)
            t = self._tasks.get(key)
            if t is None or t["state"] != "ready":
                continue                           # 僵尸条目：状态已变，直接丢弃
            if due != t["due"]:
                continue                           # 旧 due 的记录，任务已被重新排期
            if due > until:
                heapq.heappush(self._heap, (due, self._next_seq(), key))
                break
            slot = heapq.heappop(free)
            start = max(due, slot)
            if start > until:
                heapq.heappush(free, slot)
                heapq.heappush(self._heap, (due, self._next_seq(), key))
                break
            finish = start + t["cost"]
            heapq.heappush(free, finish)           # 释放时刻 = 本任务跑完的时刻
            ok = False
            try:
                ok = bool(t["fn"](t["attempts"]))
            except Exception as e:                 # 异常也要走重试/死信，不能炸掉调度线程
                t["last_error"] = repr(e)
            self.timeline.append((start, key, t["attempts"], ok, finish))
            if ok:
                t["state"], t["finished_at"] = "done", finish
            elif t["attempts"] + 1 >= self.max_attempts:
                t["attempts"] += 1
                t["state"], t["finished_at"] = "dead", finish
                self._dead.append(key)
            else:
                t["attempts"] += 1
                t["due"] = finish + self.backoff(t["attempts"])
                self._push(key)
        return self.makespan()

    def makespan(self):
        return max([x[4] for x in self.timeline], default=0.0)

    def state(self, key):
        t = self._tasks.get(key)
        return None if t is None else (t["state"], t["attempts"])

    @property
    def dead(self):
        return list(self._dead)

    def ready_depth(self):
        return sum(1 for t in self._tasks.values() if t["state"] == "ready")


if __name__ == "__main__":
    fake = [0.0]

    # 1) 幂等键：重复提交只执行一次；终态保留期内仍拒绝，GC 后才允许重提
    calls = []

    def once(attempt):
        calls.append(attempt)
        return True

    sc = Scheduler(rng=random.Random(0), clock=lambda: fake[0])
    assert sc.submit("order:1", once) is True
    assert sc.submit("order:1", once) is False
    sc.run_until(10)
    assert calls == [0] and sc.state("order:1") == ("done", 0)
    assert sc.submit("order:1", once) is False, "终态保留期内必须拒绝"
    assert sc.gc(now=100, keep=60) == 1
    assert sc.submit("order:1", once) is True, "保留期过后应允许重提"
    print("幂等键: 重复提交被拒、执行 1 次、GC 后可重提 ✅")

    # 2) 重试后成功：前两次失败，第三次成功，attempt 从 0 递增
    seq = {"n": 0}

    def flaky(attempt):
        seq["n"] += 1
        return seq["n"] >= 3

    sc2 = Scheduler(base=0.5, cap=8, jitter="none", max_attempts=5, max_workers=1)
    sc2.submit("flaky", flaky, cost=0.1, now=0.0)
    sc2.run_until(100)
    att = [x[2] for x in sc2.timeline]
    assert att == [0, 1, 2] and sc2.state("flaky") == ("done", 2)
    gaps = [round(sc2.timeline[i + 1][0] - sc2.timeline[i][4], 6)
            for i in range(len(sc2.timeline) - 1)]
    assert gaps == [1.0, 2.0], gaps          # base*2^1 与 base*2^2：退避从第 1 次失败开始翻倍
    print("重试: 尝试 %s 次，失败间隔 %s 秒（指数退避，none 抖动）✅" % (att, gaps))

    # 3) 死信：永远失败必须停在上限，不许无限重试
    sc3 = Scheduler(base=0.1, cap=1, jitter="none", max_attempts=3, max_workers=1)
    sc3.submit("poison", lambda a: False, cost=0.05, now=0.0)
    sc3.run_until(100)
    assert sc3.state("poison") == ("dead", 3) and sc3.dead == ["poison"]
    print("死信: 3 次后进死信队列，state=%s ✅" % (sc3.state("poison"),))

    # 4) 抖动：full jitter 必须落在 [min_delay, raw] 内，且能打散同步重试
    sc4 = Scheduler(base=1, cap=8, jitter="full", min_delay=0.05, rng=random.Random(1))
    ds = [sc4.backoff(1) for _ in range(2000)]
    assert all(0.05 <= d <= 2.0 for d in ds)
    assert min(ds) < 0.4 and max(ds) > 1.6
    spread = len({round(d, 3) for d in ds})
    sc5 = Scheduler(base=1, cap=8, jitter="none", rng=random.Random(1))
    same = len({round(sc5.backoff(1), 3) for _ in range(2000)})
    assert spread > 500 and same == 1
    print("抖动: full jitter 2000 次得到 %d 个不同延迟；不抖动只有 %d 个（同步重试潮）✅"
          % (spread, same))

    # 5) 并发上限：4 个 1s 任务，2 worker -> 2s，4 worker -> 1s，1 worker -> 4s
    for workers, expect in ((1, 4.0), (2, 2.0), (4, 1.0)):
        s = Scheduler(max_workers=workers, max_attempts=1)
        for i in range(4):
            s.submit("t%d" % i, lambda a: True, cost=1.0, now=0.0)
        ms = s.run_until(100)
        assert abs(ms - expect) < 1e-9, (workers, ms)
        print("并发: 4×1s 任务 / %d worker -> makespan %.0fs ✅" % (workers, ms))

    # 6) 同一 seed 完全可复现；时间线单调不减
    def run_once(seed):
        s = Scheduler(base=0.2, cap=2, jitter="full", max_attempts=4,
                      max_workers=3, rng=random.Random(seed))
        for i in range(50):
            s.submit("job%d" % i, lambda a: a >= 2, cost=0.05, now=0.0)
        s.run_until(50)
        return s.timeline

    t1, t2 = run_once(7), run_once(7)
    assert t1 == t2
    assert all(t1[i][0] <= t1[i + 1][0] for i in range(len(t1) - 1))
    print("确定性: seed=7 两次运行时间线完全一致（%d 条），起始时刻单调 ✅" % len(t1))

    # 7) 恢复语义：due 用墙钟才能重建；下次运行只跑 due<=until 的任务
    sc7 = Scheduler(max_workers=1, max_attempts=1)
    sc7.submit("late", lambda a: True, cost=0.1, now=1000.0)
    sc7.submit("early", lambda a: True, cost=0.1, now=900.0)
    sc7.run_until(950.0)
    assert [x[1] for x in sc7.timeline] == ["early"] and sc7.ready_depth() == 1
    print("按 due 截断: 只执行 1 条到期任务，剩余队列深度 %d ✅" % sc7.ready_depth())
```

**追问**：1) 为什么重试间隔不能直接用 `base × 2^attempt`，而一定要加抖动？—— 因为失败是**相关的**：下游一挂，所有客户端几乎同时失败、同时退避、同时重试，退避只改变了「下一次脉冲」的时间点，没有改变「大家同时」这个事实。1 万个任务在同一毫秒重试，等于对刚恢复的下游做了一次 1 万倍的压测，把它第二次打挂。full jitter 把重试时刻均匀撒在 `[0, delay]` 上，峰值被摊平到整个区间；代价是可能「立刻重试」（delay 很小时），所以还要设一个下限（本题 50ms），否则抖动的收益被「秒回」抵消。2) 幂等键去重表放在本地内存里，多实例部署时会怎样？—— 完全失效：同一个 `idem_key` 打到两个实例，两边各自查本地表都查不到，于是执行两次。所以本地表只能作为「同一实例内的快速去重」，跨实例必须依赖共享存储（Redis `SET NX` 带 TTL，或数据库唯一约束）。更关键的是——即使有 Redis，也存在「写 Redis 成功、业务执行成功、但写回状态前进程被杀」的窗口，最终仍然要靠**业务侧的幂等**（唯一约束、状态机条件更新）兜底。调度器的去重是优化，不是正确性保证。3) 调度器重启后，怎么保证「已经发出去但结果未知」的任务不重复执行？—— 不能保证，只能收敛。正确姿势是**把状态写进任务记录**：执行前先 `UPDATE ... SET state='running', lease_until=now+30s`（带 version 条件），执行完写 `done`；重启后扫到 `running` 但 `lease_until` 已过期的任务，视为「结果未知」，重新执行——这就要求业务操作本身幂等（比如「扣款 10 元」用唯一流水号，重复执行只生效一次）。所以「至少一次投递 + 业务幂等」是唯一可行的组合，「恰好一次」在分布式里只是特定条件下的近似。

## 背诵要点
1. 调度内核 = `due` 最小堆 + 单线程 tick（或 worker 空闲时刻堆），线程数恒定；出队必须校验「记录的 due == 任务的当前 due」，否则会把已成功的任务再跑一遍。
2. 退避 `min(cap, base×2^attempt)` 必须有抖动：`full`（`rand(0,delay)`，打散最彻底）与 `equal`（保留最小间隔）按业务选，另设下限防「秒回」；抖动源必须可注入，否则线上不可复现。
3. 幂等键三态（inflight/done/gone）+ 终态保留期 + GC；本地表只防单实例，跨实例必须靠唯一约束；`due` 持久化用墙钟，进程内计时用 `monotonic`。

## 复盘追问
1. 调度器里 `ready` 队列深度一直涨、CPU 却不高，最可能是什么？（提示：worker 槽位被长任务占满 + 重试任务持续回队——典型的队头阻塞；看 `inflight` 与单任务耗时分布，解法是按耗时/租户分池，而不是加 worker，加 worker 只会把下游打得更狠）
2. 某个任务的 `attempts` 一直是 0，但业务方说「已经重试了很多次」，怎么解释？（提示：业务方的重试打在**上游入口**，每次都是新请求、新 `idem_key`（或没有键），调度器根本没收到重试——这类「重试发生在错误层次」的问题，症状就是重试次数统计与用户感受完全对不上，必须先把幂等键从入口透传到执行侧，A132 的端到端链路同理）
