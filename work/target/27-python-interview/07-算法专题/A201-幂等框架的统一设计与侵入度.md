### A201 · 幂等框架统一设计

> 难度:★★★ | 标签:幂等, 框架设计, 场景题

**问**（笔试·编程+场景题）：幂等逻辑散落在 30 个服务里（各写各的：有的 Redis、有的 DB 唯一键、有的根本没做）——统一幂等框架怎么设计（装饰器/中间件/SDK 三种形态的侵入度），幂等键的「作用域」怎么定义（服务级/业务级），「框架统一了但业务语义不同」（有的幂等要返回原结果、有的要拒绝）怎么配置化，框架自身的可用性（幂等组件挂了怎么办）怎么设计？

**答**：① 三形态侵入度光谱：**SDK/装饰器**（`@idempotent(key="...", ttl=86400)`——侵入低但只能管单函数）、**中间件**（HTTP 层统一拦截，按 header 提取键——完全无侵入但只适合 API 层）、**显式 API**（`idem.check(key)` / `idem.complete(key, result)`——侵入最高但语义最灵活，适合复杂流程）。选型：API 层用中间件，服务内部用装饰器，复杂业务流程显式 API。② 作用域与语义配置：幂等键格式 `service:operation:business_key`（防跨服务键冲突）+ 每操作配置语义（`on_dup: return_original / reject_409 / return_in_progress`——A102 查回原单 vs A118 拒绝，语义不同配置不同）。③ 框架自身可用性：幂等组件（Redis/DB）挂了 = **fail-open with 告警**还是 fail-close？——按操作风险分级：资金类 fail-close（拒绝请求，宁可不服务不能重复扣）、普通类 fail-open（放行+告警+对账兜底）——分级配置而非全局一刀切。

```python
# 全部标准库；demo 实现「装饰器形态幂等框架 + 语义配置 + 分级降级」
import functools, json, time, hashlib

class IdempotencyStore:
    """幂等存储抽象：demo 用 dict；生产 = Redis（快）+ DB（真相源）双层。"""
    def __init__(self, healthy: bool = True):
        self.store: dict[str, dict] = {}
        self.healthy = healthy
    def get(self, key: str) -> dict | None:
        return self.store.get(key) if self.healthy else None   # 挂了返回 None
    def put(self, key: str, payload: dict):
        if self.healthy:
            self.store[key] = payload

def idempotent(store: IdempotencyStore, operation: str,
               key_from: str = "body.idempotency_key",
               on_dup: str = "return_original",           # return_original|reject|in_progress
               fail_mode: str = "fail_open",              # fail_open|fail_close
               risk: str = "normal"):                     # normal|money
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            body = kwargs.get("body") or (args[0] if args else {})
            key = body.get(key_from.split(".")[-1])
            if not key:
                if risk == "money":
                    raise ValueError("资金操作必须携带幂等键")
                return fn(*args, **kwargs)               # 无键且非资金：直接执行
            full_key = f"{operation}:{key}"
            try:
                prev = store.get(full_key)
                if prev:
                    if on_dup == "return_original":
                        return {"replayed": True, "result": prev["result"]}
                    if on_dup == "reject":
                        raise ValueError("重复请求")
                result = fn(*args, **kwargs)
                store.put(full_key, {"result": result, "ts": time.time()})
                return result
            except Exception as e:
                # 存储故障时：资金类 fail-close，普通类 fail-open + 告警
                if "store" in str(e).lower() or not store.healthy:
                    if fail_mode == "fail_close" or risk == "money":
                        raise RuntimeError("幂等组件不可用（资金操作拒绝执行）")
                    return fn(*args, **kwargs)           # fail-open：放行+对账兜底
                raise
        return wrapper
    return deco

if __name__ == "__main__":
    store = IdempotencyStore()
    @idempotent(store, operation="order:create", on_dup="return_original")
    def create_order(body):
        return {"order_id": "ORD-1"}
    body = {"idempotency_key": "k-1"}
    r1 = create_order(body)
    r2 = create_order(body)                              # 客户端重试
    assert r1 == {"order_id": "ORD-1"} and r2["replayed"] and r2["result"] == r1
    print("装饰器幂等：重试返回原结果 ✅")
    # 语义配置：reject 模式
    @idempotent(store, operation="coupon:claim", on_dup="reject")
    def claim(body):
        return {"claimed": True}
    try:
        claim(body); claim(body)
    except ValueError as e:
        print("reject 语义:", e, "✅")
    # 资金类 + 存储挂 → fail-close
    broken = IdempotencyStore(healthy=False)
    @idempotent(broken, operation="pay:refund", risk="money")
    def refund(body):
        return "refunded"
    try:
        refund(body)
    except RuntimeError as e:
        print("fail-close:", e, "✅")
    # 普通类 + 存储挂 → fail-open
    @idempotent(broken, operation="notify:send", fail_mode="fail_open")
    def notify(body):
        return "sent"
    assert notify(body) == "sent"
    print("fail-open：普通操作放行 + 对账兜底 ✅")
    # 口径：键=service:operation:business_key；on_dup 语义配置化；
    # 框架自身故障按 risk 分级 fail-open/close（资金 fail-close）。
```

**追问**：1) 为什么幂等键要带 `service:operation` 前缀？——不同业务用同一个业务键（如订单号在「创建订单」和「取消订单」都传）语义完全不同——无前缀的键冲突会让「取消订单」命中「创建订单」的幂等记录返回错误结果；前缀 = 幂等域隔离（Q6014 租户隔离同构）。2) 「资金类 fail-close」的用户体验代价怎么缓解？（提示：fail-close 只在幂等组件故障时触发（罕见）——缓解：组件高可用（Redis+DB 双层）、fail-close 窗口内请求入队延迟执行（而非丢弃）+ Retry-After 头——拒绝也要给用户出路）3) 「装饰器管理单函数」的局限？（提示：跨多函数的业务流程（A102 四层防线）不能用单函数装饰器表达——显式 API 形态；且装饰器只拦截「函数入口」，副作用发生在函数深处（嵌套调用）时装饰器管不到——幂等边界要和副作用边界对齐）

## 背诵要点
1. 三形态按侵入度：中间件（API 层零侵入）→ 装饰器（单函数）→ 显式 API（复杂流程）；幂等边界与副作用边界对齐。
2. 键格式 `service:operation:business_key` 做幂等域隔离；on_dup 语义配置化（return_original/reject/in_progress）。
3. 框架自身故障按 risk 分级：资金 fail-close、普通 fail-open+对账——分级配置非全局一刀切。

## 复盘追问
1. 统一框架推广后，团队抱怨「框架管不了我的场景」（幂等逻辑与业务流程深度耦合），怎么办？（提示：框架提供「显式 API 逃生舱」（check/complete 手动编排）——统一框架覆盖 80% 场景，显式 API 兜 20% 特殊场景；禁止「框架覆盖不了就自己造」（散装幂等回归）——逃生舱的存在正是防绕过的设计）
2. 幂等存储的 Redis→DB 双层一致性（Redis 命中但 DB 没有）怎么处理？（提示：Redis 是快挡板 DB 是真相源（A102 口径）——Redis 命中返回原结果、未命中查 DB 再回填；双层写序：先 DB 后 Redis（Redis 可丢不可错）；对账任务兜底双层漂移）
