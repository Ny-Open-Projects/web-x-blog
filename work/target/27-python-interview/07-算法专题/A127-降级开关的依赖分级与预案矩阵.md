### A127 · 依赖分级与预案矩阵

> 难度:★★☆ | 标签:降级, 依赖治理, 场景题

**问**（笔试·编程+场景题）：一个下单页面依赖 8 个下游（库存/价格/推荐/评论/积分/风控/短信/物流查询）——哪些是「必须依赖」（挂了不能下单）哪些是「可降级依赖」（挂了体验差但能卖货），分级依据是什么？给每个可降级依赖写降级预案（返回什么/谁来决策/怎么恢复），「推荐服务挂了页面 500」这种事故怎么从架构上杜绝？

**答**：① 分级两轴：**业务关键度**（下单主链路 vs 体验增强）× **数据可替代性**（无缓存可用 vs 有快照可回）。判据问题只有一个：**它挂了，用户能不能完成下单？** 能 → 可降级。矩阵：库存/价格/风控 = 必须依赖（阻塞主链路）；推荐/评论/积分/物流查询 = 可降级（缺省值/隐藏模块/稍后补）。② 降级预案四要素：**降级值**（推荐→返回热门默认列表；评论→隐藏入口；积分→标记「稍后入账」不阻塞）、**决策者**（自动熔断 A106 触发 + 手动开关兜底）、**恢复条件**（探测恢复 → 自动回切 + 数据补偿）、**用户告知**（降级提示文案，不装正常）。③ 架构杜绝：「推荐挂了页面 500」= 同步强依赖了体验增强服务——治理手段：**超时预算**（推荐调用 200ms 预算，超时直接降级不等待，Q6019）+ **异步化**（积分入账改消息驱动，下单路径不等它）+ **降级路径也是代码路径**（默认值的代码和测试与主路径同级对待——降级代码没测试，故障时降级路径自己是坏的）。

```python
# 全部标准库；demo 实现「依赖分级 + 降级预案执行器」
import time
from enum import Enum

class Level(Enum):
    MUST = "must"                # 必须依赖：挂了阻塞主链路
    DEGRADABLE = "degradable"    # 可降级：挂了体验差

# 依赖注册表：名称 -> (分级, 降级值工厂, 超时预算ms)
REGISTRY = {
    "stock":     (Level.MUST, None, 300),
    "price":     (Level.MUST, None, 200),
    "risk":      (Level.MUST, None, 500),
    "recommend": (Level.DEGRADABLE, lambda: {"items": ["热门1", "热门2"]}, 200),
    "comments":  (Level.DEGRADABLE, lambda: None, 200),   # None = 隐藏模块
}

def call_with_budget(name: str, deps: dict) -> dict:
    """带预算调用：可降级依赖超时/异常即走预案；必须依赖失败向上抛。"""
    level, fallback, budget_ms = deps[name]
    t0 = time.monotonic()
    result = f"real-data({name})"            # 模拟真实调用
    if time.monotonic() - t0 > budget_ms / 1000:
        raise TimeoutError("budget exceeded")
    return {"name": name, "data": result, "degraded": False}

def call_real(name: str, deps: dict, fail: bool = False) -> dict:
    level, fallback, _ = deps[name]
    if fail:
        if level == Level.MUST:
            raise ConnectionError(f"{name} down")     # 必须依赖：失败阻塞主链路
        return {"name": name, "data": fallback() if fallback else None,
                "degraded": True}                     # 可降级：预案值接管
    return call_with_budget(name, deps)

def order_page(deps: dict, failures: set[str] = frozenset()) -> dict:
    sections = {}
    for name in deps:
        try:
            sections[name] = call_real(name, deps, fail=name in failures)
        except Exception as e:
            sections[name] = {"name": name, "blocked": True, "error": str(e)}
            break                          # 必须依赖挂了：整页快速失败（不下单）
    return sections

if __name__ == "__main__":
    page = order_page(REGISTRY)
    assert all(not s.get("degraded") for s in page.values())
    print("全依赖健康:", {k: v["name"] for k, v in page.items()})
    degraded = order_page(REGISTRY, failures={"recommend", "comments"})
    assert degraded["recommend"]["degraded"] and degraded["recommend"]["data"]
    assert degraded["comments"]["data"] is None            # 隐藏模块
    print("可降级依赖故障 → 预案值接管 ✅:", degraded["recommend"]["data"])
    blocked = order_page(REGISTRY, failures={"stock"})
    assert blocked["stock"]["blocked"]
    print("必须依赖故障 → 主链路快速失败（不下单）✅")
    # 口径：判据一句话「它挂了用户能不能下单」；降级四要素（值/决策/恢复/告知）；
    # 降级路径必须有测试——没测过的降级路径在故障时是第二事故。
```

**追问**：1) 为什么「必须依赖失败要快速失败」而不是等待重试？——主链路阻塞时用户在转圈，等待通常无果（下游可能真挂）；快速失败 + 用户可重试比挂 30s 好——但风控类例外（宁可慢等风控结果也不能跳过风控放单）——分级内部还要按「能否绕过」细分。2) 「稍后入账」的补偿语义怎么保证不丢？（提示：本地消息表/事务发件箱（Q6544/A108），恢复后重放——降级不是丢弃业务事实）3) 降级开关误开（依赖其实正常却降级了）怎么发现？（提示：降级态指标（降级时长/占比）进监控 + 依赖健康探测自动回切 + 手动开关到期自动复审）

## 背诵要点
1. 分级判据一句话：「它挂了用户能不能完成主链路」——能=可降级，不能=必须依赖。
2. 降级预案四要素：降级值 / 决策者（自动熔断+手动开关）/ 恢复条件 / 用户告知。
3. 架构杜绝「体验服务拖垮主链路」：超时预算+异步化；降级路径要有同级测试。

## 复盘追问
1. 8 个依赖都是「必须」级，说明设计有什么问题？（提示：依赖颗粒度太粗或产品边界不清——细分接口（下单只需库存校验不需库存列表页），或把体验增强拆出主链路）
2. 降级期间积压的「稍后入账」补偿失败率 5%，怎么兜底？（提示：补偿重试+死信（A120）+ 最终对账任务——补偿链路本身也要可靠性设计，降级债务要清偿）
