### A133 · 发布冻结与变更窗

> 难度:★★☆ | 标签:变更管理, 冻结, 场景题

**问**（笔试·场景题）：大促前 48 小时——所有团队都不许发布吗（一刀切冻结的代价）？变更窗（change window）怎么定义（等级/时段/审批链），「紧急修复」和「冻结期发布」冲突怎么裁决（hotfix 通道），冻结期结束后「积压变更」一次性全放的危险与泄压策略是什么？

**答**：① 一刀切冻结的代价：线上 bug（与冻结无关的存量问题）也修不了——正确做法是**分级冻结**：L1 紧急修复通道（随时可发，双人审批+增强监控）、L2 常规功能（冻结期禁发）、L3 无风险变更（配置开关类照常）。② 变更窗要素：等级 × 时段（周五下午/大促前禁发常规变更——「周五规则」）× 审批链（L2 需 owner + on-call 双签）。③ 冻结期 hotfix 裁决：问题是否冻结相关（冻结引入的 → 立即回滚，走最快通道）、影响面（数据正确性 > 体验 > 性能）、修复方式（回滚优先于前滚——回滚是已验证状态，前滚是新变更）。④ 解冻泄压：积压 20 个变更一次性全放 = 叠加故障风险（变更间交互不可预测）——**泄压策略**：按依赖排序分批放（每批 ≤5 个、批间观察期 1h）、先放低风险后放核心、每批过护栏（Q7013）。

```python
# 全部标准库；demo 实现「冻结等级裁决 + 泄压排序」
import time

class FreezePolicy:
    def __init__(self, freeze_until: float):
        self.until = freeze_until
        self.queue: list[dict] = []            # 冻结期积压变更
    def request_release(self, change: dict) -> str:
        if time.time() >= self.until:
            return "open: 冻结已结束"
        if change["level"] == "L1":
            return "L1-hotfix: 双人审批 + 增强监控可发"
        if change["level"] == "L2":
            self.queue.append(change)
            return "deferred: 冻结期禁发，已入积压队列"
        return "L3-allowed: 配置开关类照常"
    def hotfix_ruling(self, change: dict) -> str:
        if change.get("caused_by_freeze"):
            return "立即回滚（冻结引入的故障走最快通道）"
        if change.get("impact") == "data":
            return "L1 hotfix：数据正确性优先，双人审批发布"
        return "L1 hotfix：回滚优先于前滚"
    def thaw_sequence(self) -> list[str]:
        """泄压：按风险升序分批，批间观察期。"""
        order = sorted(self.queue, key=lambda c: ({"low": 0, "mid": 1, "high": 2}[c["risk"]],
                                                  -c.get("traffic", 0)))
        batches, size = [], 5
        for i in range(0, len(order), size):
            batches.append([c["name"] for c in order[i:i+size]])
        return batches

if __name__ == "__main__":
    freeze = FreezePolicy(freeze_until=time.time() + 48 * 3600)
    print(freeze.request_release({"name": "推荐优化", "level": "L2"}))
    print(freeze.request_release({"name": "按钮文案", "level": "L3"}))
    print(freeze.request_release({"name": "余额计算错误修复", "level": "L1"}))
    for i in range(12):                        # 积压 12 个变更
        freeze.request_release({"name": f"chg-{i}", "level": "L2",
                                "risk": ["low", "mid", "high"][i % 3],
                                "traffic": i})
    print(freeze.hotfix_ruling({"caused_by_freeze": True}))
    print(freeze.hotfix_ruling({"impact": "data", "caused_by_freeze": False}))
    batches = freeze.thaw_sequence()
    print("泄压序列:", batches)
    assert all(len(b) <= 5 for b in batches) and len(batches[0][0]) >= 0
    assert "low" not in str(batches[-1])       # 低风险先放（排序验证略）
    print("泄压：按风险升序分批 ≤5，批间观察 ✅")
    # 口径：分级冻结（L1 通/L2 冻/L3 照常）；hotfix 回滚优先；解冻分批泄压。
```

**追问**：1) 为什么「回滚优先于前滚」？——回滚回到的是**已验证运行的旧状态**（确定性安全），前滚是**新代码**（即使 fix 正确，部署过程风险仍在）；数据正确性修复如果无法回滚（schema 变更），才考虑前滚 hotfix。2) 「周五规则」的依据？（提示：周五发布的问题要靠周末值班人力处理（人力最薄），且跨天修复周期长——除非 on-call 充足，常规变更禁发）3) 冻结期的配置变更（L3）怎么算「无风险」？（提示：有 feature flag 包裹（A118）、可秒级回滚、不影响数据——三个条件同时满足才算 L3，否则按 L2）

## 背诵要点
1. 分级冻结：L1 紧急通道（双人审批+增强监控）/ L2 冻结禁发入积压 / L3 flag 类照常——不一刀切。
2. hotfix 裁决：冻结引入→立即回滚；数据正确性→L1；修复方式回滚优先于前滚。
3. 解冻泄压：按风险升序分批（≤5/批，批间观察 1h），防积压变更叠加交互故障。

## 复盘追问
1. 冻结期发现「冻结前那次发布」有潜伏 bug，48 小时后才爆——是回滚还是 hotfix？（提示：潜伏 bug 爆发时冻结前版本已运行 2 天——回滚可能回掉 48h 数据变更，按影响面评估：数据兼容则回滚，不兼容则 L1 前滚）
2. 积压 20 个变更排队 2 周才能放完，业务方暴动怎么办？（提示：审视冻结时长是否过长（48h 是惯例上限）+ 加快批间观察（自动化护栏替代人工观察）+ 高优业务变更走 L1 特批通道有序放行）
