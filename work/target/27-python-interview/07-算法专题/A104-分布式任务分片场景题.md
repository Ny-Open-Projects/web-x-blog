### A104 · 分布式任务分片场景题

> 难度:★★★ | 标签:任务队列, SKIP LOCKED, 租约, 场景题

**问**（笔试·场景题）：500 万条待处理订单要平滑迁移，多个 worker 进程消费，要求：不重复处理、worker 宕机后任务不丢、能水平扩容、不引入 Kafka/RabbitMQ。只用 PostgreSQL 怎么实现？写取任务的 SQL 与 Python 主循环，并说明租约超时怎么定。

**答**：DB 当队列的三件套：① `SELECT ... FOR UPDATE SKIP LOCKED`——多 worker 并发取任务互不阻塞、互不重复（被锁的行直接跳过，天然分片）；② **租约（lease）**：任务被取走时写 `lease_until = now + 60s` 并置 `status='running'`，worker 定期心跳续租；worker 宕机则租约到期，由回收进程把过期 running 任务重置回 `pending`（处理不丢）；③ **处理幂等**兜底：租约回收可能在「实际已处理成功但没来得及确认」时重复投递，所以 worker 侧业务操作必须幂等（唯一键/状态机），队列语义是 **at-least-once**。租约时长 = 正常处理时长的 P99 × 2~3，太短会误回收导致重复处理，太长则宕机恢复慢。

```sql
-- 取任务（每个 worker 独立事务）
UPDATE tasks SET status='running', lease_until=now() + interval '60 seconds',
                 worker_id=$1, attempts=attempts+1
WHERE id IN (
  SELECT id FROM tasks
  WHERE status='pending'
     OR (status='running' AND lease_until < now())   -- 顺手回收过期租约
  ORDER BY priority DESC, id
  FOR UPDATE SKIP LOCKED
  LIMIT 10
)
RETURNING id, payload;
```

```python
import os, time
import sqlalchemy as sa

eng = sa.create_engine(os.environ.get("DB_URL", "postgresql+psycopg2://"))
# 缺库降级：无 psycopg2 时重点掌握上方 SQL 的 SKIP LOCKED 语义即可
CLAIM = """
UPDATE tasks SET status='running', lease_until=now() + interval '60 seconds',
                 worker_id=:wid, attempts=attempts+1
WHERE id IN (
  SELECT id FROM tasks WHERE status='pending'
     OR (status='running' AND lease_until < now())
  ORDER BY priority DESC, id FOR UPDATE SKIP LOCKED LIMIT 10)
RETURNING id, payload
"""
RENEW = "UPDATE tasks SET lease_until=now() + interval '60 seconds' WHERE worker_id=:wid AND status='running'"
DONE  = "UPDATE tasks SET status='done' WHERE id=:id AND worker_id=:wid"

def run_worker(wid: str):
    claimed = []
    last_renew = 0.0
    while True:
        with eng.begin() as c:                       # 短事务取任务，立即提交释放锁
            rows = c.execute(sa.text(CLAIM), {"wid": wid}).mappings().all()
        if not rows:
            time.sleep(1); continue
        for r in rows:
            claimed.append(r["id"])
            handle(r["payload"])                     # 业务处理，必须幂等
            with eng.begin() as c:
                c.execute(sa.text(DONE), {"id": r["id"], "wid": wid})
        if time.monotonic() - last_renew > 20:       # 心跳：批量续租本 worker 全部在跑任务
            last_renew = time.monotonic()
            with eng.begin() as c:
                c.execute(sa.text(RENEW), {"wid": wid})

def handle(payload) -> None:
    ...  # 幂等业务：唯一键 upsert 或状态机条件更新

if __name__ == "__main__":
    pass  # 需真实 PG 实例；sqlite 无 SKIP LOCKED，勿用 sqlite 演示
```

**追问**：1) 为什么取任务用「UPDATE ... WHERE id IN (子查询 FOR UPDATE SKIP LOCKED)」而不是先 SELECT 再 UPDATE？——两步之间有窗口，另一个 worker 会取到同一行再 UPDATE，变成互相覆盖；单条 UPDATE+SKIP LOCKED 在行级锁内原子完成「挑+占」。2) 为什么不用 `sleep` 重试的 `FOR UPDATE NOWAIT`？——NOWAIT 立刻报错，热行时 worker 空转；SKIP LOCKED 静默跳过直接拿下一批，吞吐平滑。3) 和 Kafka 对比的取舍？——PG 队列优点：事务一致（任务和业务同库同事务）、运维零新增；缺点：高吞吐（>1 万/秒）下表膨胀与 vacuum 压力，超过就换专业 MQ。

## 背诵要点
1. PG 当队列三件套：FOR UPDATE SKIP LOCKED（互斥分片）+ 租约 lease_until + 心跳续租，宕机后过期任务回收重投。
2. 队列语义 at-least-once，业务侧必须幂等兜底；租约 = P99 处理时长 × 2~3。
3. 取任务必须单条 UPDATE+SKIP LOCKED，先 SELECT 再 UPDATE 有并发覆盖窗口。

2. 任务优先级是怎么进 SQL 的？（提示：ORDER BY priority DESC 在锁定子查询里，讲清与公平性的权衡）
