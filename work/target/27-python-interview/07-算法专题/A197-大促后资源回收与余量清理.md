### A197 · 大促后资源回收

> 难度:★★☆ | 标签:成本, 资源治理, 场景题

**问**（笔试·场景题）：大促扩容了 3 倍资源（400 台机器/临时配额/临时账号）——「活动结束了资源还在烧钱」的清理清单（机器/配额/账号/数据/配置），清理的时机（活动结束立即 vs 观察期后），「清理漏了」的发现机制（成本对账），临时资源的「常态化漂移」（临时配额用了半年）怎么治？

**答**：① 清理清单五类：**计算资源**（扩容机器/临时集群——缩回基线）、**配额**（临时 API 配额/云服务限额——恢复常量）、**账号权限**（大促临时开通的账号/白名单——回收，Q165 僵尸账号同源）、**数据**（临时表/压测数据/影子表——清理或归档）、**配置**（大促专用开关/限流参数——回常规值）。② 时机：**分两波**——活动结束立即缩「纯大促资源」（确定不再用的），保留 1 周观察期资源（防长尾流量/退换货高峰），观察期后全部回收——立即全清的风险：退换货/结算高峰（大促后 3-7 天）还有流量尾巴。③ 漏清发现：**成本对账**（本月成本 vs 大促前基线 diff——多出来的就是漏网资源）；自动化：临时资源登记表（创建时打标 `promo-202611` + 自动过期时间）→ 过期自动提醒/回收——「登记时定生死」比「事后找」可靠。④ 常态化漂移治理：临时配额变永久 = 无主资源——治理：临时资源必须带 TTL（到期未续自动回收+提醒 owner 续期），续期要有理由（业务上为什么还需要）——TTL 机制让「临时」真正临时。

```python
# 全部标准库；demo 实现「临时资源 TTL 登记 + 对账发现」
import time

class TempResourceRegistry:
    """临时资源登记表：创建打标 + TTL 自动过期 + 成本对账。"""
    def __init__(self):
        self.resources: dict[str, dict] = {}
    def register(self, rid: str, kind: str, owner: str, ttl_days: int):
        self.resources[rid] = {"kind": kind, "owner": owner,
                               "expires": time.time() + ttl_days * 86400,
                               "daily_cost": {"machine": 200, "quota": 50,
                                              "account": 0}.get(kind, 10)}
    def sweep(self) -> dict:
        now = time.time()
        expired = {rid: r for rid, r in self.resources.items() if r["expires"] <= now}
        for rid in expired:
            self.resources.pop(rid)
            print(f"  ♻ 回收 {rid}（{expired[rid]['kind']}，owner={expired[rid]['owner']}）")
        return expired
    def daily_cost(self) -> float:
        return sum(r["daily_cost"] for r in self.resources.values())

def cost_reconcile(current_daily: float, baseline_daily: float,
                   promo_over: bool) -> str | None:
    """成本对账：大促结束后的日成本应回落到基线附近。"""
    if promo_over and current_daily > baseline_daily * 1.3:
        return (f"成本未回落: {current_daily} vs 基线 {baseline_daily} "
                f"→ 检查漏网资源（机器/配额/账号）")
    return None

if __name__ == "__main__":
    reg = TempResourceRegistry()
    reg.register("promo-machines", "machine", "ops-zhang", ttl_days=7)
    reg.register("promo-api-quota", "quota", "biz-li", ttl_days=3)     # 3 天期已过
    reg.register("core-db", "machine", "dba", ttl_days=3650)           # 常驻资源
    expired = reg.sweep()
    assert set(expired) == {"promo-api-quota"}                         # 只回收过期的
    print(f"每日成本（未回收余量）: {reg.daily_cost()}（promo-machines 7 天后自动回收）")
    print(cost_reconcile(current_daily=4500, baseline_daily=3000, promo_over=True))
    # 口径：五类清理清单（机器/配额/账号/数据/配置）；分两波回收（立即+观察期）；
    # 临时资源 TTL 登记「创建时定生死」+ 成本对账兜底发现漏网。
```

**追问**：1) 为什么清理分两波而不是立即全清？——大促后 3-7 天有「尾巴流量」（退换货/结算/售后咨询高峰）——立即全清会让尾巴流量打在基线容量上（正好是最脆弱时刻）；分波=确定性资源立即清、有不确定性风险的资源观察一周。2) 「TTL 到期自动回收」会不会误杀正在用的资源？（提示：回收前提醒（TTL 前 3 天通知 owner 续期+理由）——回收的是「无回应的过期资源」；误杀成本（重新申请几分钟）远低于漂移成本（每天白烧钱）——不对称风险选自动化）3) 大促临时账号里有「表现优秀申请转正」的（比如新的自动化脚本好用），正规路径是什么？（提示：转正=重新评估+走正式开通流程（权限/owner/TTL 重设为正式值）——不是「不回收就等于转正」；转正评估和清理流程并存，让「留下来」也是显式决策）

## 背诵要点
1. 清理五类清单：计算/配额/账号/数据/配置——大促扩容的每一份资源都要有回收对应项。
2. 分两波回收：确定性资源立即清，有风险资源观察 1 周（大促后尾巴流量）再清。
3. 临时资源 TTL 登记「创建时定生死」+ 到期前提醒 + 成本对账兜底——临时变常态是漂移，TTL 治理。

## 复盘追问
1. 成本对账发现「多花了 50%」但找不到是哪个资源——资源台账缺口怎么补？（提示：所有云资源打标（promo-xxx/owner/ttl）强制化（IaC 模板内置标签）+ 未打标资源扫描告警——打标覆盖率是成本治理的前置条件）
2. 「临时配额」转正后业务方反对回收（已经依赖了），怎么处理？（提示：依赖临时资源本身就是治理问题——转正走正式评估（容量/成本/owner 重申）并重设 TTL 为正式值；临时依赖要给出迁移路径，否则拒绝转正——显式决策代替既成事实）
