### A200 · 容量规划方法论

> 难度:★★★ | 标签:容量规划, 方法论, 场景题

**问**（笔试·场景题）：新季度预算评审要给出「下季度资源需求」——容量规划的系统方法：峰值画像（历史流量的日/周/季节形态提取），增长预测（线性外推 vs 业务输入驱动），余量设计（冗余系数怎么定不拍脑袋），「容量不足」的早期信号（什么指标先亮红灯），容量规划与成本优化的矛盾（要余量还是要省钱）怎么量化仲裁？

**答**：① 峰值画像：不是「峰值 QPS 一个数」而是**形态提取**——日形态（早晚峰）/周形态（工作日 vs 周末）/季节形态（大促/月末），三者叠加出「下周三上午 10 点的预期负载区间」——规划对象是「形态」不是「点值」。② 增长预测：**业务输入驱动**（新功能上线计划/用户增长目标/大促日程——业务方给的输入比线性外推可靠）+ 外推做交叉验证（历史增速与业务输入矛盾时追问）——纯外推的容量规划在「业务突变」时全部失效。③ 余量设计：冗余系数 = 覆盖「预测误差 + 实例损失（单机房故障）+ 扩容滞后」三项之和——量化：预测误差 ±20%（历史统计）+ 单机房损失 50% × 该机房流量占比 + 扩容滞后期间的缓冲 10%——不是拍 2 倍。④ 早期信号：延迟 P99 先涨（容量耗尽的最早信号，Q6063）> 错误率 > 队列积压 > CPU——P99 是「容量红色警报」的第一指标。⑤ 与成本仲裁：余量的每一层标价（物理隔离最贵）——按「该层挡住的故障的期望损失」比较（A106/A195 分级口径），数据说话。

```python
# 全部标准库；demo 实现「峰值画像提取 + 冗余系数计算」
import statistics
from collections import defaultdict

QPS_SAMPLES = {                     # 历史按 (weekday, hour) 聚合的 QPS 样本
    (0, 10): [8200, 8500, 8100],    # 周一上午 10 点样本
    (0, 14): [6100, 6300],
    (5, 10): [5000, 5200],          # 周五上午（明显低）
    (0, 10): None,                  # 覆盖重复 key 演示（真实实现按 list append）
}

def peak_profile(samples: dict) -> dict:
    """形态提取：按 (weekday, hour) 聚合出均值与 P99。"""
    agg = defaultdict(list)
    for key, vals in samples.items():
        if vals:
            agg[key] += vals
    profile = {}
    for key, vals in agg.items():
        profile[key] = {"mean": statistics.mean(vals),
                        "p99": max(vals) * 1.1}      # 样本少时 P99 近似
    return profile

def redundancy_factor(pred_err_pct: float = 20, dc_loss_pct: float = 50,
                      dc_traffic_share: float = 0.5, scale_lag_pct: float = 10) -> float:
    """冗余系数 = 三项之和，不拍脑袋：
    预测误差 + 机房损失折算 + 扩容滞后缓冲。"""
    dc_term = dc_loss_pct * dc_traffic_share          # 50% × 50% = 25%
    return 1 + (pred_err_pct + dc_term + scale_lag_pct) / 100

if __name__ == "__main__":
    profile = peak_profile(QPS_SAMPLES)
    print("峰值画像（周一 10 点）:", profile[(0, 10)])
    rf = redundancy_factor()
    print(f"冗余系数: {rf:.2f}（预测误差 20% + 机房折算 25% + 滞后 10%）")
    assert 1.5 < rf < 1.6                              # 1.55 —— 不是拍 2 倍
    base = profile[(0, 10)]["mean"]
    need = base * rf
    print(f"下季度需求 = 峰值均值 {base:.0f} × {rf:.2f} ≈ {need:.0f} QPS")
    # 口径：规划对象是形态（日/周/季叠加）非点值；增长预测以业务输入为准外推交叉验证；
    # 冗余 = 预测误差 + 机房损失 + 扩容滞后，三项量化不加和拍脑袋。
```

**追问**：1) 为什么规划对象是「形态」而非「峰值点值」？——峰值点值只回答「要多少机器」，形态回答「什么时候要、什么时候能省（夜间缩容）」——形态化容量可调度（夜间缩容省 30% 成本，Q151 余量清理），点值容量只能常驻浪费。2) 「业务输入驱动」怎么防业务方虚报？（提示：虚报有成本约束——申请的容量计入团队成本账（Q7633 showback），虚报的资源闲置季度审计（Q7135 僵尸资源清扫）+ 申请与实际使用偏差率进团队 KPI——虚报在透明成本下自然收敛）3) 「P99 先亮红灯」作为容量信号的理论依据？（提示：容量耗尽时排队延迟先于资源耗尽显形（Little's Law：队列深度涨→等待时间涨），且 P99 比 CPU 敏感（CPU 70% 时 P99 可能已翻倍）——延迟是「用户体验视角」的容量信号，资源指标是「机器视角」——两者背离时信用户视角）

## 背诵要点
1. 容量规划对象 = 峰值形态（日/周/季节叠加的负载区间），不是峰值点值——形态可调度省成本。
2. 增长预测 = 业务输入驱动为主 + 历史外推交叉验证——纯外推在业务突变时全部失效。
3. 冗余系数量化：预测误差 20% + 机房损失折算 + 扩容滞后 10%，按故障期望损失与成本比较仲裁——P99 是容量红色警报第一指标。

## 复盘追问
1. 业务方说「下季度用户翻倍」，按翻倍规划后发现只涨了 20%——虚报成本巨大，怎么治？（提示：翻倍承诺写进业务 OKR 并季度复盘（承诺与实际的偏差率公开）+ 容量申请分批释放（先按 50% 增长扩，达标再补——分批对冲虚报风险）；容量规划的错误要双向复盘（工程高估与业务虚报都追））
2. 容量规划做了三年，规划偏差率一直是 ±30% 以上——方法论哪里失效？（提示：偏差大的常见根因：形态样本不够长（只看一个月漏了季节性）、业务输入缺失（纯外推）、冗余拍脑袋掩盖真实误差——逐项审计方法论本身（预测误差历史统计是否做了、业务输入是否收集、冗余是否量化），方法论也要复盘）
