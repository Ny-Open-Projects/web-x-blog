### A148 · 备份恢复演练

> 难度:★★☆ | 标签:备份, 演练, RTO

**问**（笔试·场景题）：「备份每天都在跑」但恢复一次要 6 小时且发现缺了 3 张表——备份制度的核心为什么是「恢复演练」而不是「备份成功」，演练的验证口径（RTO/RPO 实测、数据完整性抽样、应用连通性）怎么定，演练频率怎么按系统分级（核心/重要/边缘），「演练发现的问题」怎么闭环（和 A144 行动项打通）？

**答**：① 「备份成功 ≠ 可恢复」：备份任务成功只证明「文件写出来了」——恢复时才发现缺表（备份范围漏了）、权限丢了、依赖服务起不来、版本不兼容。**演练是唯一验证**：把备份在新环境（隔离 VPC）真实恢复到「应用可用」才算通过——口径四层：① RTO 实测（从启动恢复到应用可服务的时间）；② RPO 实测（恢复出的最新数据 vs 故障时刻——丢了多少）；③ 完整性抽样（表数/行数/关键哈希比对——Q6515 校验同构）；④ 应用连通（应用真的连上恢复库跑通核心链路——数据在但应用不认等于没恢复）。② 频率分级：核心系统（支付/订单）月度全量演练 + 季度真机切换；重要系统季度演练；边缘系统半年演练——频率与「数据丢失的业务代价」成正比。③ 闭环：演练发现的问题（缺表/超时/权限）登记行动项（A138/A144 体系），下月演练先验证上月行动项——「演练-发现-修复-再演练」是备份制度的发动机。

```python
# 全部标准库；demo 实现「演练验证器（四层口径）」
import time, hashlib, json

class RestoreDrill:
    def __init__(self, rto_sla_min: int = 60, rpo_sla_min: int = 5):
        self.rto_sla, self.rpo_sla = rto_sla_min, rpo_sla_min
        self.findings: list[str] = []
    def run(self, backup_meta: dict, restored: dict) -> dict:
        t0 = time.monotonic()
        # ① RTO：恢复到应用可用
        rto = restored["rto_min"]
        if rto > self.rto_sla:
            self.findings.append(f"RTO {rto}min 超 SLA {self.rto_sla}min（优化恢复脚本/预占资源）")
        # ② RPO：最新数据 vs 故障时刻
        rpo = backup_meta["gap_min"]
        if rpo > self.rpo_sla:
            self.findings.append(f"RPO {rpo}min 超 SLA（补增量备份/缩短间隔）")
        # ③ 完整性：表数与关键表哈希
        if restored["table_count"] != backup_meta["source_tables"]:
            self.findings.append(f"缺表 {backup_meta['source_tables'] - restored['table_count']} 张（备份范围漏了）")
        for tbl, h in backup_meta.get("key_hashes", {}).items():
            if hashlib.sha1(tbl.encode()).hexdigest()[:8] != h and False:  # 演示骨架
                pass
        # ④ 应用连通
        if not restored.get("app_ok"):
            self.findings.append("应用连不上恢复库（配置/权限/版本不兼容）")
        verdict = "PASS" if not self.findings else "FAIL"
        return {"verdict": verdict, "findings": self.findings}
    def to_action_items(self) -> list[dict]:
        """发现的问题闭环进行动项（A144 体系）。"""
        return [{"title": f, "status": "pending"} for f in self.findings]

if __name__ == "__main__":
    d = RestoreDrill(rto_sla_min=60, rpo_sla_min=5)
    result = d.run(
        backup_meta={"source_tables": 42, "gap_min": 10, "key_hashes": {"orders": "abc"}},
        restored={"rto_min": 360, "table_count": 39, "app_ok": False})
    print("演练结论:", result["verdict"])
    for f in result["findings"]:
        print("  -", f)
    assert result["verdict"] == "FAIL" and len(result["findings"]) == 3
    items = d.to_action_items()
    print("闭环行动项:", [i["title"][:20] for i in items])
    # 口径：备份成功≠可恢复，演练四层口径（RTO/RPO/完整性/连通）；
    # 发现→行动项→下月复验，是备份制度的发动机。
```

**追问**：1) 为什么「应用连通」是独立一层？——数据完整但应用不认（schema 版本漂移/账号权限/依赖服务未起）是最常见的恢复陷阱——「恢复数据」和「恢复服务」是两件事，演练必须验到最后一层。2) 演练环境的成本怎么控？（提示：隔离 VPC + 按需起（演练完销毁）+ 用最小规格机器（只验正确性不验性能——性能压测另测）；核心系统季度真机切换的成本单独预算）3) 「RPO 实测 10 分钟超 SLA 5 分钟」的修复动作是什么？（提示：缩短备份间隔（全量改增量）或补 binlog/流复制实时性——RPO 由复制机制决定，不是靠更努力备份）

## 背诵要点
1. 备份成功 ≠ 可恢复；演练四层口径：RTO 实测、RPO 实测、完整性抽样、应用连通。
2. 频率分级：核心月度+季度真机切换、重要季度、边缘半年——与数据丢失代价成正比。
3. 演练发现 → 行动项 → 下月复验：演练-发现-修复-再演练是备份制度的发动机。
