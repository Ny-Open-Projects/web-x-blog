### A123 · 依赖地图与爆炸半径

> 难度:★★★ | 标签:依赖分析, 变更管理, 场景题

**问**（笔试·场景题）：要改「用户服务」的一个接口——怎么知道「炸了会影响谁」？服务依赖地图怎么自动生成（不是手画），爆炸半径（blast radius）怎么量化（一跳/二跳依赖 + 流量权重），「变更影响分析」怎么进发布流程（改了 A 强制通知 B），循环依赖在地图上怎么处理？

**答**：① 地图自动生成三来源：**trace 数据**（真实调用链聚合：谁调谁、QPS 多少——最真实但只有被调用过的路径）、**代码/配置**（服务发现配置、SDK 引用——静态全量但含死链）、**运行时探测**（定期主动调用验证路径存活）——三者合并成带权重的有向图，trace 权重最高。② 爆炸半径量化：改服务 X 的接口 → 一跳直接调用方（数量+它们的 QPS+重要性等级）→ 二跳（下游的下游）——半径 = 受影响 QPS 占总量比例 + 关键路径（支付链路上）标记；半径超阈值（如 >30% 流量）的变更强制评审。③ 变更影响进发布：发布单带「变更的服务/接口」，地图反查受影响方 → 自动建通知（webhook Q6013 语义）+ 受影响方确认（或超时放行记录在案）——契约测试（Q6012）在发布前跑一遍受影响方的兼容性用例。④ 循环依赖：地图上标红但不强拆（拆环成本高），降级为「环上变更需双方确认」+ 共享库抽提的长期重构项。

```python
# 全部标准库；demo 实现依赖图构建 + 爆炸半径计算 + 变更影响通知
from collections import defaultdict, deque

class DepGraph:
    def __init__(self):
        self.edges: dict[str, dict[str, float]] = defaultdict(dict)  # caller -> callee -> qps
    def add_trace(self, caller: str, callee: str, qps: float):
        self.edges[caller][callee] = self.edges[caller].get(callee, 0) + qps
    def blast_radius(self, changed: str, total_qps: float, hops: int = 2) -> dict:
        """爆炸半径：一跳/二跳受影响方 + QPS 占比 + 关键路径标记。"""
        affected, frontier, radius = {}, {changed}, []
        for hop in range(hops):
            nxt = set()
            for svc in frontier:
                for callee, qps in self.edges.get(svc, {}).items():
                    if callee not in affected:
                        affected[callee] = {"hop": hop + 1, "qps": qps}
                        nxt.add(callee)
            frontier = nxt
            if not nxt:
                break
        total_affected = sum(a["qps"] for a in affected.values())
        critical = [s for s in affected if s in ("payment", "order")]  # 关键路径清单
        return {"affected": affected, "qps_ratio": total_affected / total_qps,
                "critical": critical}
    def cycles(self) -> list[list[str]]:
        """环检测（DFS）。"""
        color, cyc = {}, []
        def dfs(u, path):
            color[u] = 1
            for v in self.edges.get(u, {}):
                if color.get(v) == 1:
                    cyc.append(path + [v])
                elif color.get(v, 0) == 0:
                    dfs(v, path + [v])
            color[u] = 2
        for s in list(self.edges):
            if color.get(s, 0) == 0:
                dfs(s, [s])
        return cyc

if __name__ == "__main__":
    g = DepGraph()
    g.add_trace("web", "user", 10000)
    g.add_trace("web", "order", 8000)
    g.add_trace("user", "cache", 12000)
    g.add_trace("order", "payment", 7000)
    g.add_trace("order", "user", 3000)          # 循环：user ↔ order
    r = g.blast_radius("user", total_qps=30000)
    print("受影响:", {k: f"hop{v['hop']} qps{v['qps']:.0f}" for k, v in r["affected"].items()})
    print(f"爆炸半径: {r['qps_ratio']:.0%} QPS | 关键路径: {r['critical']}")
    assert r["qps_ratio"] > 0.5                  # user 挂影响过半流量 → 强制评审
    assert r["critical"] == ["payment"]
    print("环检测:", g.cycles())
    # 口径：半径 >30% 流量或含关键路径 → 变更强制评审 + 受影响方通知。
```

**追问**：1) 为什么「trace 为主、配置为辅」而不是反过来？——trace 反映真实依赖（配置里的调用可能从未发生或已废弃），配置补 trace 的盲区（低频路径/灾备路径）；合并时 trace 权重高、冲突以 trace 为准——地图是「活文档」要持续校准。2) 二跳半径要不要继续展开到三跳？——边际价值递减（三跳影响往往被二跳的降级挡住，A106），且图规模爆炸；惯例 2-3 跳 + 关键路径全跳追踪。3) 循环依赖「标红不强拆」的长期风险？（提示：环会放大故障（互相拖死）——标红只是记录，重构排期（共享库抽提）才是解；不排期的标红等于没标）

## 背诵要点
1. 依赖地图三来源合并：trace（真实，权重高）+ 静态配置（补盲区）+ 运行时探测——活文档持续校准。
2. 爆炸半径 = 受影响 QPS 占比 + 关键路径标记；>30% 或含关键路径强制评审。
3. 变更发布自动反查受影响方 → 通知 + 契约测试；循环依赖标红进重构排期不即时强拆。

## 复盘追问
1. 地图说 A 调 B，但 B 团队说从没听过 A——谁的地图错了？（提示：可能是 A 的 SDK 直连 B 的旧接口（配置有但 B 不知情），trace 会显示真实调用——地图争议以 trace+联调验证裁决，并暴露文档债）
2. 「受影响方确认」超时未回怎么办？（提示：超时放行 + 记录在案（应急联系人清单）——阻塞发布 vs 放行风险取决于变更等级，高危变更必须人工确认到人）
