### A234 · 基线漂移检测

> 难度:★★☆ | 标签:容量基线, 漂移, 复审

**问**（笔试·场景题）：「容量基线」定的 5000 QPS 用了一年——基线本身会过时（业务形态变化：直播功能让晚峰形态改变/用户结构变化让峰值倍率漂移），基线漂移怎么**检测**（当前实际峰值 vs 基线的偏差趋势），年度复审的输入清单（形态重提取/增长复盘/成本审计），基线更新后「下游引用」怎么联动（限流值/告警阈值/预留实例都绑着旧基线）？

**答**：① 漂移检测：**季度对账**——实际峰值（各时段 P99）vs 基线的偏差率，连续两季偏差 >30% 即「基线漂移」告警——漂移方向双向（涨了=容量低估风险，降了=冗余浪费成本）。检测的数据基础是 Q121 峰值形态持续采集（不是一年采一次）。② 年度复审输入：形态重提取（最近一年的完整形态重新叠加）、增长复盘（上季预测 vs 实际的偏差统计——验证预测模型）、成本审计（冗余系数三项的真实值复核，A200 口径）。③ 下游联动清单：**限流值**（静态限流引用基线——基线更新后限流值重算，A101）、**告警阈值**（P99 告警基于基线倍数——漂移不联动则误报，Q189 隐式假设）、**预留实例配比**（Q6637 成本口径）、**容量告警水位**（CPU 70% 告警线对应的 QPS 也漂了）——联动靠「基线 ID 引用」（下游配置引用基线版本，基线更新自动提示重算，而非硬编码值）。

```python
# 全部标准库；demo 实现「基线漂移检测 + 下游联动清单」
import statistics

BASELINE = {"peak_qps": 5000, "evening_shape": "flat", "version": 3}

def drift_check(actual_peaks: list[float], baseline: int,
                threshold: float = 0.30) -> dict:
    """季度对账：实际峰值 vs 基线偏差（连续两季 >30% 告警）。"""
    mean_actual = statistics.mean(actual_peaks)
    drift = (mean_actual - baseline) / baseline
    return {"mean_actual": mean_actual, "drift": round(drift, 2),
            "direction": "capacity-underestimated" if drift > 0 else "over-provisioned",
            "alert": abs(drift) > threshold}

def downstream_refs(baseline_version: int) -> list[str]:
    """基线的下游引用清单（应引用版本号而非硬编码值）。"""
    return [f"rate_limit (ref baseline v{baseline_version})",
            f"p99_alert_threshold (ref baseline v{baseline_version})",
            f"reserved_instances (ref baseline v{baseline_version})"]

if __name__ == "__main__":
    # 基线 5000，实际峰值漂到 7000（直播功能改变晚峰形态）
    r = drift_check([6800, 7100, 6900, 7200], BASELINE["peak_qps"])
    print(r)
    assert r["alert"] and r["direction"] == "capacity-underestimated"
    print("下游引用（联动重算）:", downstream_refs(3))
    # 口径：季度对账偏差 >30% 告警（双向）；下游引用基线版本号而非硬编码值；
    # 年度复审输入 = 形态重提取 + 预测偏差复盘 + 成本审计。
```

**追问**：1) 为什么「偏差 >30% 连续两季」才告警而不是单季？——单季偏差可能是异常波动（一次大促），连续两季才是形态漂移（结构性变化）；误报的代价是「无谓的基线重算+下游联动」（成本高），从严阈值减少误报——漂移检测同样适用「最小信号+持续确认」原则（Q116 统计口径）2) 「下游引用基线版本号」的实现？（提示：配置项存 `baseline_ref: v3` 而非 `5000`——基线发布 v4 时下游收到「引用过期」告警自动提示重算（值由引用关系算出）；实现同 Q1174 引用溯源——值是派生的，源头唯一）
3) 基线漂移「向下」（流量萎缩 30%）的危害比向上大吗？（提示：不同性质——向下=冗余浪费（成本损失可量化但不直接出事故）；向上=容量低估（事故风险）——实践中向上漂移响应优先级更高，但向下漂移的累计成本（常年多跑的实例）往往更大——都 alerts，分级响应）

## 背诵要点
1. 基线漂移检测：季度对账实际峰值 vs 基线，连续两季偏差 >30% 告警——双向检测（低估与浪费）。
2. 下游联动靠「引用基线版本号」而非硬编码值——基线更新自动提示限流/告警/预留实例重算。
3. 年度复审输入三件：形态重提取 + 预测偏差复盘 + 成本审计——基线是活文档不是常量。

## 复盘追问
1. 基线更新到 v4 后，团队说「别更新了，每次更新都要改一堆配置」——联动成本怎么降？（提示：联动成本高说明下游是硬编码值（改 N 处）——治理方向是「引用制改造」（一次性把 N 处改为 baseline_ref 引用），此后更新零成本——引用制改造本身就是消除未来的重复劳动）
2. 基线漂移检测发现「晚峰形态从平顶变成尖峰」（直播拉动），容量规划要怎么变？（提示：平顶→尖峰意味着「峰值更陡但平均更低」——容量按尖峰值规划（不能按平均），但尖峰时段短 → 弹性扩容（Q135 预热+步进）比常驻扩容更经济——形态变化会改变「常驻 vs 弹性」的成本权衡，这正是形态化规划的价值）
