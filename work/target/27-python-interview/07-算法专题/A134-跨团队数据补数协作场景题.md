### A134 · 数据补数

> 难度:★★★ | 标签:补数, 数据修复, 场景题

**问**（笔试·场景题）：上游发现昨日订单表有 2 小时数据错误（金额少算了优惠券）——补数流程：影响面怎么评估（哪些下游表/报表/模型被污染），补数顺序怎么定（依赖图的拓扑序），补数与增量任务并发怎么处理（写到同一张表的冲突），「补数期间下游能不能读」怎么决策？

**答**：① 影响面评估：从坏表出发沿**血缘图**（Q7014 数据血缘）正向遍历——所有直接/间接消费方按「数据新鲜度敏感度」分级（实时接口 > 日报 > 月报 > 离线模型训练集）；量化口径：受影响行数 × 下游消费频率 = 修复紧迫度。② 补数顺序：依赖图拓扑序（上游先修，下游重算逐层来）+ **并行补数**按无关节点分组（图染色分组，同组可并行）；幂等前提：每个补数任务必须可重跑（幂等写入，Q7017）。③ 并发冲突：补数（重写昨日分区）与增量任务（写今日分区）写同一表——**分区隔离**天然免冲突（不同分区），同分区则补数任务独占（暂停增量 + 补完恢复）；下游读取决策按「中间态可见性」：读旧值（一致但过期）vs 读半新半旧（不可接受）——用「版本切换」（补完原子切 alias/分区名，A108 逻辑同构）让下游永远读到一致版本。

```python
# 全部标准库；demo 实现「血缘影响面 + 拓扑补数 + 版本切换」
from collections import defaultdict, deque

LINEAGE = {                       # 表 -> 下游消费方
    "orders": ["dws_order_daily", "report_weekly", "ml_features"],
    "dws_order_daily": ["report_weekly", "ml_features"],
    "report_weekly": [], "ml_features": [],
}

def blast_surface(bad: str) -> dict[str, int]:
    """血缘正向遍历 + 敏感度分级（越小越紧急）。"""
    urgency = {"realtime": 0, "daily": 1, "weekly": 2, "ml": 3}
    out, q = {}, deque([bad])
    while q:
        t = q.popleft()
        for d in LINEAGE.get(t, []):
            if d not in out:
                out[d] = urgency.get("ml" if "ml" in d else
                                     "weekly" if "report" in d else "daily", 3)
                q.append(d)
    return dict(sorted(out.items(), key=lambda x: x[1]))

def topo_batches(nodes: dict[str, list[str]]) -> list[list[str]]:
    """补数分组：拓扑序 + 无关节点并行（图染色近似——按层级分批）。"""
    depth = {}
    def d(n):
        if n in depth: return depth[n]
        depth[n] = 0
        for up in nodes.get(n, []):
            depth[n] = max(depth[n], d(up) + 1)
        return depth[n]
    for n in nodes: d(n)
    layers = defaultdict(list)
    for n, lv in depth.items(): layers[lv].append(n)
    return [sorted(v) for _, v in sorted(layers.items())]

if __name__ == "__main__":
    surface = blast_surface("orders")
    print("影响面（按紧迫度排序）:", surface)
    assert list(surface) == ["dws_order_daily", "report_weekly", "ml_features"]
    DEPS = {"dws_order_daily": ["orders"], "report_weekly": ["dws_order_daily"],
            "ml_features": ["dws_order_daily"]}
    batches = topo_batches(DEPS)
    print("补数批次（拓扑+并行分组）:", batches)
    assert batches[0] == ["dws_order_daily"] and len(batches[1]) == 2
    # 版本切换口径：补数写 shadow 分区 → 校验通过 → 原子改名切换 → 下游无感读一致版本。
    print("决策：补数期间下游读旧值（一致），补完原子切换 ✅")
```

**追问**：1) 为什么「下游读旧值」而不是「读半新半旧」？——一致性是数据可信的底线：半新半旧（订单新、日报旧）会让跨表对账失败、报表口径打架；版本切换让「切换瞬间前旧后新」，永远内部一致。2) 补数把昨日报表改对了，但老板上周看过的截图已经发出去了怎么办？（提示：历史不可篡改是展示层现实——补救=发布更正公告+更正版快照链接；治理=关键报表带「数据截止时间」水印，从源头防止「截图即终局」）3) 大范围补数（2 小时错数据 × 10 张下游表）跑到一半失败？（提示：分批补数+每批校验（Q6515 归档流水线同构）+ 水位断点——失败从断点续，不重做整批）

## 背诵要点
1. 影响面 = 血缘正向遍历 × 敏感度分级（实时>日报>周报>模型），量化修复紧迫度。
2. 补数顺序 = 拓扑序 + 无关节点并行分组；任务必须幂等可重跑。
3. 补数期间下游读旧值（一致性优先），补完原子版本切换——绝不半新半旧。

## 复盘追问
1. 补数后下游模型指标反而变差了（用了修复后的数据重训练），怎么向业务解释？（提示：修复后的数据是「真相」，旧模型是拟合在错误数据上——指标变差暴露的是模型对脏数据的过拟合；重训练+双跑对比（Q7548）给业务信心）
2. 上游说「错误只影响 2 小时」，你怀疑影响全天——怎么验证？（提示：抽样全天数据与权威源（支付流水）对账，按小时粒度 diff 出真实污染边界——影响面靠对账实证不靠上游口径）
