### A241 · 多租户配额仲裁与降级

> 难度:★★★ | 标签:多租户, 配额, 仲裁, 降级

**问**（笔试·场景题）：100 个租户共享一个容量池，大促瞬间需求是容量的 3 倍——配额耗尽的那一刻，谁拿到最后的容量、谁被降级、按什么规则裁决？要求说清：① 「仲裁」的三要素（保底 / 优先级 / 权重与防饥饿）；② 拿不到全额的租户走什么**降级阶梯**（不是一刀切 429）；③ 怎么证明「公平」（可观测指标）。并说明它和 A115 配额记账、A193 稳态公平性、A235 跨团队制度对齐的区别。

**答**：① 边界：A115 管「配额怎么记账」（窗口口径 / 预扣结算 / 超额策略），A193 管「稳态公平与重户判别」，A235 管「跨团队制度对齐」——A241 管**配额耗尽那一瞬间的裁决**：共享池被抢空时谁拿最后容量（仲裁）与拿不到的怎么退化（降级阶梯），是事件驱动而非稳态模型。② 仲裁三要素：**保底硬约束**（先满足每租户 floor，不可抢占；保底之和 ≤ 容量 80%，A193 延续，超额承诺直接拒绝仲裁——数学上兑现不了的承诺是事故源）、**优先级分层**（套餐 tier / 关键业务先满足）、**权重 × aging**（同 tier 内按套餐权重分，连续未满足轮数放大权重，防小租户长期饥饿——公平不是平均，是「承诺可兑现 + 不会被饿死」）。③ 降级阶梯：拿不到全额不直接 429，按未满足比例逐级退化——**同步 → 异步队列 → 降参（降采样/降精度）→ 只读 → 明确拒绝**（429 + Retry-After + 升级引导）；高优先级租户多留一档同步额度。原则「能不拒就不拒」，降级保住租户关系，硬拒是最后手段。④ 公平可观测：不看「分得平均」，看三条——保底兑现率 100%、小租户最大饥饿轮数有上界（aging 保证）、超额分配与权重成正比；三条能打点才算「仲裁公平」可验收。

```python
# 全部标准库；demo 实现「保底 + 优先级 + aging 仲裁 + 降级阶梯」
from dataclasses import dataclass

@dataclass
class Tenant:
    name: str
    tier: int                 # 数字越小优先级越高
    weight: int               # 套餐权重
    floor: float              # 不可抢占保底
    used: float = 0.0
    wait_rounds: int = 0      # 连续未满足轮数（aging 用）

def arbitrate(tenants: list[Tenant], capacity: float,
              demand: dict[str, float]) -> dict:
    """仲裁：保底先满足，剩余按 tier→weight×aging 分配。"""
    granted = {t.name: 0.0 for t in tenants}
    remain = capacity
    for t in tenants:                              # ① 保底硬约束（不可抢占）
        give = min(demand[t.name], t.floor)
        granted[t.name] += give
        remain -= give
    if remain < 0:
        raise ValueError("保底之和超容量：承诺不成立，拒绝仲裁")  # A193 防线
    def urgency(t: Tenant) -> tuple:
        return (-t.tier, t.weight * (1 + 0.25 * t.wait_rounds))  # ② aging 放大小租户
    for t in sorted(tenants, key=urgency, reverse=True):
        want = max(0.0, demand[t.name] - granted[t.name])
        give = min(want, remain)
        granted[t.name] += give
        remain -= give
        t.wait_rounds = t.wait_rounds + 1 if give < want else 0   # 未满足则 aging++
    unmet = {t.name: max(0.0, demand[t.name] - granted[t.name]) for t in tenants}
    return {"granted": granted, "unmet": unmet}

LADDER = ["sync", "async-queue", "degraded-params", "read-only", "reject-429"]

def degradation(unmet: float, demand: float, tier: int) -> str:
    """降级阶梯：能不拒就不拒；高优先级多留一档同步额度。"""
    ratio = unmet / demand if demand else 0.0
    level = 0 if ratio <= 0 else 1 if ratio <= 0.25 else 2 if ratio <= 0.5 \
            else 3 if ratio <= 0.75 else 4
    if tier == 0 and level > 0:                    # VIP 降一级（更温和）
        level -= 1
    return LADDER[level]

if __name__ == "__main__":
    tenants = [Tenant("free-a", 2, 1, 5), Tenant("free-b", 2, 1, 5),
               Tenant("pro", 1, 4, 20), Tenant("vip", 0, 2, 10)]
    demand = {"free-a": 40, "free-b": 40, "pro": 30, "vip": 15}
    totals = {t.name: 0.0 for t in tenants}
    for _ in range(3):                              # 三轮：验证 aging 防饥饿
        r = arbitrate(tenants, capacity=100, demand=demand)
        assert abs(sum(r["granted"].values()) - 100) < 1e-9
        assert all(r["granted"][t.name] >= t.floor for t in tenants)
        for name, v in r["granted"].items():
            totals[name] += v
    print("仲裁分配:", {k: round(v) for k, v in r["granted"].items()})
    assert totals["free-a"] > 5 and totals["free-b"] > 5   # 小租户轮流吃到超额份额
    print("三轮总额:", {k: round(v) for k, v in totals.items()}, "—— 无饥饿 ✅")
    print("降级阶梯:", degradation(0, 10, 2), "/", degradation(3, 10, 2),
          "/", degradation(9, 10, 2), "/", degradation(9, 10, 0))
    assert degradation(0, 10, 2) == "sync"
    assert degradation(9, 10, 2) == "reject-429"
    assert degradation(9, 10, 0) == "read-only"             # VIP 不直接拒
    try:                                                    # 保底超卖防线
        arbitrate([Tenant("x", 1, 1, 60), Tenant("y", 1, 1, 60)],
                  100, {"x": 60, "y": 60})
    except ValueError:
        print("保底超额承诺拦截 ✅")
    else:
        raise AssertionError("超额保底未被拦截")
```

**追问**：1) 为什么保底不可被高优先级抢占？——保底是平台对租户的契约承诺（花钱买的最低保障），一旦允许抢占，「VIP 突发把免费租户的保底吃了」会让小租户在关键时刻完全不可用——契约被破坏的信任损失远大于让 VIP 多等一会；保底之和 ≤ 容量 80% 正是为抢占留的缓冲。2) aging 系数（+25%/轮）怎么定、会不会过头？——系数太小防不住饥饿（小租户永远排在重户后），太大则退化成「谁饿最久谁优先」丢掉套餐权重（VIP 失去应得优先级）——做法是设饥饿轮数上限（封顶 aging，如最多翻倍）+ 用「最大饥饿轮数」指标监控，超过阈值告警人工介入。3) 降级和限流有什么区别，为什么先降级后拒绝？——限流是「超了就拒」（硬边界），降级是「还在服务但降质量」（软退化）——先把同步转异步（用户可接受延迟）、再降参（结果精度下降但可用），每级都保住「服务还在」，最后才 429；对租户而言体验是连续退化而非断崖，对平台而言争取了扩容/自愈的时间窗口。

## 背诵要点
1. A241 管耗尽瞬间的仲裁+降级（事件驱动），区别于 A115 记账、A193 稳态公平、A235 制度对齐。
2. 仲裁三要素：保底硬约束（不可抢占、保底和≤容量80%）+ 优先级 tier + 权重×aging 防饥饿。
3. 降级阶梯：同步→异步→降参→只读→429（能不拒就不拒）；公平可观测=保底兑现率100% + 饥饿轮数有界 + 超额按权重。

## 复盘追问
1. 仲裁逻辑上线后 VIP 投诉「我付最多却没拿到最多」，怎么排查？（提示：查保底之和与 aging 封顶——若小租户 aging 被放大过头盖过 VIP 权重，说明 aging 系数/上限设置失衡；仲裁要同时满足 VIP 权重优势与小租户不饥饿，是双目标优化）
2. 降级阶梯走到 reject-429 了，用户还是投诉「比直接报错还糟」，可能哪里错？（提示：429 缺 Retry-After 与升级引导（用户反复重试打满）+ 降级前的阶梯用户无感知（不知道正在异步/降参，以为功能坏了）——降级要可观测、拒绝要给明确指引）
