### A254 · 多活架构的数据冲突与流量切换

> 难度:★★★★★ | 标签:单元化, 多活, 冲突裁决, 就近路由, 回切

**问**（笔试·场景题）：出海业务要做三单元多活（新加坡 / 法兰克福 / 弗吉尼亚），目标：① 单元内闭环，用户读写 95% 不出单元；② 任一单元整体故障，另外两个单元在 5 分钟内接管；③ 同一用户绝不能被两个单元同时写。请回答五个必须落数字的问题：**① 数据怎么归属**——按 `user_id` 取模还是按固定分片表，迁移时差别在哪，哪些数据天生没有 `user_id`（全局唯一键、运营配置、库存）；**② 同一份数据被两个单元写了怎么办**——LWW、版本向量、增量合并（PN-counter）、状态机单调合并，四者各适用什么字段，LWW 在时钟漂移下会丢什么；**③ 跨单元读怎么写**——运营后台要按商户聚合，fan-out 的成本怎么算，什么时候必须建异构索引；**④ 故障切换的决策链**——怎么防止「两个单元都以为自己该接管」；**⑤ 回切为什么比切换更危险**——回切闸门要有哪几个数字，缺一个会出什么事故。A113 给了 RTO/RPO 与脑裂仲裁、A135 给了流量权重步进、A162 给了切换后对账，本题不重复这些，专攻「数据归属 + 冲突裁决」这一层。要求给出可运行的裁决器与路由计算。

**答**：① 与已有卡的分工：A113 回答「切多快、会不会脑裂」（RTO 由流程决定、RPO 由复制方式决定、多数派仲裁）；A135 回答「切多少、每步看什么指标」；A162 回答「切完发现数据缺了怎么找回」。它们都把「数据」当成一个整体在搬。多活真正难的是**数据本来就在两边各有一份，而且都被人写过**——这时候切换不是搬数据，是**裁决冲突**。本题补的就是这一层：归属规则、四类冲突裁决、跨单元读成本、回切闸门。② 归属：**固定分片表，不要取模**。取模的映射是 `hash(uid) % N`，N 从 3 变 4 时几乎所有 key 都要搬家（A247 实测取模扩容迁移 75%）；分片表的映射是「1024 个逻辑分片 → 哪个单元」，扩容只搬受影响的那些分片，而且**可以一片一片搬、一片一片校验**，出问题只回滚一片。代价是多一层间接（`uid → shard → unit`）和一张必须强一致的元数据表——这张表就是整个多活架构的单点，必须放在「三单元都能读、写入走多数派」的配置中心里，且变更要人工双人复核。③ 天生没有 `user_id` 的数据有三类，处理方式完全不同：**全局唯一键**（订单号、支付流水）用「号段 + 单元前缀」在本地生成，绝不跨单元取号，否则取号服务就是单点；**运营配置/商品目录**是读多写少，用「单主写 + 广播读」，写永远回主单元，读走本地副本，容忍秒级延迟；**库存**是最难的——它既要全局准确又要本地低延迟，答案通常是「本地预扣 + 全局对账 + 超卖补偿」，而不是分布式事务，因为跨洲 2PC 的延迟（RTT 150ms × 2 阶段）在大促下等于自杀。④ 冲突裁决四选一，按字段语义分，不能全局统一：**LWW（最后写入胜）**适合「用户昵称、头像、主题」这类谁赢都行的字段，实现最简，但它有个致命缺陷——比较的是**时间戳**，而多单元的时钟天然有漂移（NTP 通常 ±几十毫秒，异常时能到秒级），时钟慢 5 秒的单元即使**后写**也会输，用户刚改的昵称被旧值覆盖，而且**没有任何报错**。修法不是换 LWW，是换判定源：用 HLC（混合逻辑时钟，物理时间 + 逻辑计数）保证单节点内单调，跨节点仍要靠「写入方带版本号」而不是本地时钟。**版本向量**适合「不能悄悄丢写」的字段（收货地址、发票信息），它能判断两次写是「有因果关系」还是「真并发」——真并发就抛给业务裁决（给用户弹「你在两个设备上改了地址，选哪个」），代价是每个字段要维护一个 `{node: counter}`，存储和比较成本随单元数增长。**PN-counter**（正负增量分开记）适合「余额、积分、计数」这类**可交换**的量：单元 A `+5`、单元 B `-3`，合并结果一定是 `+2`，与顺序无关；而 LWW 会直接丢掉其中一笔，表现为「用户充值成功但余额没变」。**状态机单调合并**适合订单状态：只允许前进（`created < paid < shipped < done`），`shipped` 与 `paid` 合并取 `shipped`，`cancelled` 只能从 `created/paid` 进入；两个单元一个说已支付一个说已取消，这是**真冲突**，必须人工介入并退款，不能让规则自动选一个。⑤ 跨单元读：运营后台按商户聚合，商户的用户散在三个单元，只能 fan-out——成本 = 单元数 × 单单元 P99 + 合并耗时，三单元 80ms 就是 240ms，还要处理「某个单元超时」的部分失败（返回部分结果并标注不完整，绝不能把超时当 0）。当 fan-out 的 QPS × 成本超过阈值，就必须建**异构索引**（CDC 把三个单元的数据同步到 ES/ClickHouse，查询走索引），代价是延迟（秒级）和又一条要维护的同步链路；判断标准很简单：**在线事务走单元内，离线/运营分析走异构索引**，不要让后台报表的 fan-out 打到在线库上。⑥ 切换决策链：核心是「谁有资格宣布接管」。三单元用多数派（2/3）投票，只有拿到多数派租约的单元才能把只读副本提升为主；单单元故障时另外两个本来就有多数派，5 分钟内可以自动切；**跨洲网络抖动导致「互相看不见」时，任何一方都拿不到多数派，正确行为是全部降级只读**，而不是各自宣布接管——后者就是双写脑裂，数据修复成本是切换的几十倍。另外要区分「单元故障」与「单元变慢」：变慢时切走流量会让剩下的单元承受 1.5 倍负载，可能连锁雪崩，所以切换前要先确认「剩余容量 ≥ 故障前总流量 × 1.2」。⑦ 回切为什么更危险：切走时，故障单元的写入是**缺失**的（它没参与），回切时它带着**旧数据**回来，如果直接接流量，用户会看到「我昨天下的单不见了」。所以回切必须过四道闸门：**反向同步积压 = 0**（故障期间其他单元产生的变更要补给它）、**冲突率 < 阈值**（补数过程中发现同一记录两边都改过，要人工裁决完）、**复制延迟 < 秒级**（它得先追平才能接写）、**容量与 P99 已回到基线**（冷缓存 + 冷连接池直接接流量必炸，A135 的预热同样适用）。四道闸门是「与」关系，缺一条就会出现「回切后部分用户数据回退」的事故——这类事故的症状极其迷惑：只有故障单元的用户受影响，而且只在回切后的几分钟内。⑧ 一个必须点破的取舍：**多活的成本不在机房，在冲突**。三单元全活意味着任何一份数据都可能有三个版本，每加一个单元，冲突组合数按 `C(n,2)` 增长，裁决逻辑和人工介入工单同步增长。所以真实架构通常是「单元内闭环 + 关键数据单主写 + 非关键数据多活」，而不是「所有数据三地都可写」——后者在数学上要求 CRDT 化所有字段，工程上几乎不可维护。

```python
# 全部标准库；分片归属 + 就近路由 + 四类冲突裁决 + 回切闸门
import hashlib


def h64(s):
    return int.from_bytes(hashlib.md5(s.encode()).digest()[:8], "big")


class UnitRouter:
    """uid -> 1024 逻辑分片 -> 单元。分片表可逐片迁移，取模不行。"""

    def __init__(self, units, shards=1024):
        self.shards = shards
        self.table = {s: units[s % len(units)] for s in range(shards)}
        self.latency = {}                       # (src, dst) -> ms，跨单元代价

    def shard(self, uid):
        return h64(str(uid)) % self.shards

    def unit(self, uid):
        return self.table[self.shard(uid)]

    def route(self, uid, alive, here=None):
        home = self.unit(uid)
        if home in alive:
            return home, False, 0
        nearest = min(alive, key=lambda u: self.latency.get((here, u), 999))
        return nearest, True, self.latency.get((here, nearest), 999)

    def move_shard(self, shard, to, alive):     # 单分片迁移，影响面可枚举
        if to not in alive:
            raise ValueError("目标单元不可用")
        frm, self.table[shard] = self.table[shard], to
        return frm, to


class HLC:
    """混合逻辑时钟：物理毫秒 + 逻辑计数，单节点内严格单调，跨节点可比。"""
    __slots__ = ("wall", "seq", "node")

    def __init__(self, wall, seq, node):
        self.wall, self.seq, self.node = wall, seq, node

    def key(self):
        return (self.wall, self.seq, self.node)

    def __repr__(self):
        return "HLC(%d,%d,%s)" % (self.wall, self.seq, self.node)


def hlc_tick(last, wall_ms, node):
    if last is None or wall_ms > last.wall:
        return HLC(wall_ms, 0, node)
    return HLC(last.wall, last.seq + 1, node)   # 时钟没前进也要保证单调


def lww(a, b):
    """a/b = (value, HLC)。谁的时间戳大谁赢——时钟漂移会悄悄丢写。"""
    return a if a[1].key() >= b[1].key() else b


def dominates(a, b):
    return all(a.get(k, 0) >= v for k, v in b.items()) and a != b


def concurrent(a, b):
    return not dominates(a, b) and not dominates(b, a)


class PNCounter:
    """增量合并：+5 与 -3 无论谁先合并都是 +2，LWW 会丢一笔。"""

    def __init__(self):
        self.pos, self.neg = {}, {}

    def add(self, node, delta):
        book = self.pos if delta >= 0 else self.neg
        book[node] = book.get(node, 0) + abs(delta)

    def merge(self, other):
        for src, dst in ((other.pos, self.pos), (other.neg, self.neg)):
            for k, v in src.items():
                dst[k] = max(dst.get(k, 0), v)
        return self

    @property
    def value(self):
        return sum(self.pos.values()) - sum(self.neg.values())


RANK = {"created": 0, "paid": 1, "shipped": 2, "done": 3}


def merge_state(a, b):
    """订单状态只许前进；cancelled 只能从 created/paid 进，真冲突要人裁。"""
    if a == b:
        return a, None
    if "cancelled" in (a, b):
        other = b if a == "cancelled" else a
        if RANK.get(other, 99) <= 1:
            return "cancelled", None
        return None, "取消与履约冲突: %s vs %s" % (a, b)
    return (a, None) if RANK[a] >= RANK[b] else (b, None)


GATES = {"sync_backlog": 0, "conflict_rate": 1e-4, "replica_lag_s": 1.0, "p99_growth": 0.10}


def failback_ready(metrics):
    bad = []
    if metrics["sync_backlog"] > GATES["sync_backlog"]:
        bad.append("反向同步积压 %d 行" % metrics["sync_backlog"])
    if metrics["conflict_rate"] > GATES["conflict_rate"]:
        bad.append("补数冲突率 %.2e 未裁决完" % metrics["conflict_rate"])
    if metrics["replica_lag_s"] > GATES["replica_lag_s"]:
        bad.append("复制延迟 %.1fs" % metrics["replica_lag_s"])
    if metrics["p99_growth"] > GATES["p99_growth"]:
        bad.append("P99 涨幅 %.0f%%（冷缓存未预热）" % (metrics["p99_growth"] * 100))
    return len(bad) == 0, bad


if __name__ == "__main__":
    # 1) 分片表扩容：只搬受影响的 256 片，取模则几乎全搬
    units = ["sg", "fra", "iad"]
    r = UnitRouter(units, shards=1024)
    for a in units:
        for b in units:
            r.latency[(a, b)] = 0 if a == b else {"sg": {"fra": 160, "iad": 210},
                                                  "fra": {"sg": 160, "iad": 90},
                                                  "iad": {"sg": 210, "fra": 90}}[a][b]
    before = dict(r.table)
    for s in range(1024):
        if s % 4 == 3:                       # 模拟新单元接手 1/4 分片
            r.move_shard(s, "iad", units)
    changed = sum(1 for s in before if before[s] != r.table[s])
    assert 150 <= changed <= 256, changed
    print("模拟新单元接手 1/4 分片: 实际搬 %d/1024 片（%.0f%%），取模要搬约 75%% ✅"
          % (changed, changed / 1024 * 100))

    # 2) 就近路由：本单元优先，故障时去最近单元并标记跨单元代价
    uids = ["user:%d" % i for i in range(3000)]
    home = sum(1 for u in uids if not r.route(u, units, here="sg")[1])
    assert r.route("user:1", units, here="sg")[0] == r.unit("user:1")
    down = ["sg", "fra"]
    crossed = [(u, r.route(u, down, here="sg")) for u in uids]
    assert all(x[1][0] in down for x in crossed)
    assert all(x[1][1] == (r.unit(x[0]) not in down) for x in crossed)   # 归谁谁不跨
    assert all(x[1][2] >= 0 for x in crossed)                             # 本地接入则为 0
    assert all(x[1][0] != r.unit(x[0]) for x in crossed if x[1][1])
    print("三单元在线: %d/3000 用户本地命中；iad 故障后全部路由到 sg/fra ✅" % home)

    # 3) LWW 的时钟漂移陷阱：后写的反而输，且完全静默
    a = ("nick=Alice", HLC(1_000_000, 0, "sg"))
    b = ("nick=Bob", HLC(995_000, 0, "fra"))     # 物理时间慢 5 秒，但这是更晚的真实写入
    win = lww(a, b)
    assert win[0] == "nick=Alice", win
    print("时钟慢 5s 的单元后写: 结果 %r（Bob 被静默覆盖）❌ 必须换成带版本号的写入" % win[0])
    c = ("nick=Bob", hlc_tick(a[1], 990_000, "fra"))   # 收到 a 的版本后再写，逻辑计数让它更大
    assert lww(a, c)[0] == "nick=Bob"
    print("按 HLC 续写: %r 胜出（因果序优先于本地时钟）✅" % lww(a, c)[0])

    # 4) 版本向量：区分「有因果关系」与「真并发」
    vv1 = {"sg": 2, "fra": 1}
    vv2 = {"sg": 1, "fra": 2}
    vv3 = {"sg": 3, "fra": 1}
    assert concurrent(vv1, vv2) and dominates(vv3, vv1)
    print("版本向量: %s 与 %s 并发（交人工裁决）；%s 覆盖 %s ✅" % (vv1, vv2, vv3, vv1))

    # 5) 余额用增量合并：+5 与 -3 得 +2，LWW 会丢一笔
    c1, c2 = PNCounter(), PNCounter()
    c1.add("sg", 5)
    c2.add("fra", -3)
    merged = PNCounter().merge(c1).merge(c2)
    assert merged.value == 2
    lww_bad = lww((5, HLC(1000, 0, "sg")), (-3, HLC(1001, 0, "fra")))
    assert lww_bad[0] == -3
    print("PN-counter: +5 与 -3 合并 = +2 ✅；同一对值用 LWW 得到 -3（丢了充值）❌")

    # 6) 订单状态：单调前进；取消与发货是真冲突，不许自动选
    assert merge_state("paid", "shipped")[0] == "shipped"
    assert merge_state("created", "cancelled")[0] == "cancelled"
    st, err = merge_state("paid", "cancelled")
    assert st == "cancelled" and err is None
    st2, err2 = merge_state("shipped", "cancelled")
    assert st2 is None and "冲突" in err2
    print("状态合并: paid+shipped->shipped；shipped+cancelled->%s（人工介入）✅" % err2)

    # 7) 回切闸门：四项全绿才放行，缺一项就是数据回退事故
    ok = {"sync_backlog": 0, "conflict_rate": 0.0, "replica_lag_s": 0.3, "p99_growth": 0.05}
    good, bad = failback_ready(ok)
    assert good and bad == []
    print("回切闸门（全绿）: 允许回切 ✅")
    leaky = {"sync_backlog": 1200, "conflict_rate": 3e-4, "replica_lag_s": 8.0, "p99_growth": 0.4}
    good2, bad2 = failback_ready(leaky)
    assert not good2 and len(bad2) == 4
    print("回切闸门（带病）: %d 项拦截 -> %s" % (len(bad2), bad2[0]))
```

**追问**：1) 为什么不能所有字段都用版本向量，一劳永逸地「不丢写」？—— 版本向量的成本是每个字段一个 `{node: counter}`，三单元下每条记录的元数据就是字段数 × 3 个整数；一张 10 亿行的表，光元数据就几十 GB，而且每次读写都要合并向量，延迟和存储都不可接受。更重要的是它只**检测**并发，不**解决**并发——检测出来还是要人来选，工单量会随写入量线性增长。所以工程上是分层：能交换的字段（计数）用增量和，能单调的字段（状态）用状态机，只有真正需要保真的少数字段（地址、发票）才上版本向量 + 人工裁决。2) 单元故障时把流量切到最近单元，跨洲 RTT 150ms，能接受吗？—— 短期能，长期不能。切换后的跨洲写会让每次请求多 2 个 RTT（读 + 写），P99 从 80ms 涨到 400ms，用户侧表现为「页面转圈」；而且跨单元流量会打到对端的连接池和数据库，故障会从「一个单元」扩散成「两个单元都慢」。所以故障切换要配三件事：跨单元流量限速（不超过对端剩余容量的 30%）、非核心功能降级（推荐、历史订单先关掉）、以及**明确的时间盒**——超过 N 小时必须决定是修复原单元还是正式迁移数据，不能长期靠跨洲兜底。3) 回切时发现 `conflict_rate` 一直降不下来，多半是什么原因？—— 通常是「补数用的是 LWW 覆盖，而不是逐条比对」：反向同步工具为了快，直接把故障单元的整行覆盖成对端的值，于是每一行都被记为「冲突」，但其实是同一条数据被重复搬运。正确做法是先按主键 + 版本号做差集，只同步「对端版本更新」的行，冲突只应该出现在「两边版本不可比」的少数记录上（正常应 < 1e-4）。如果差集算出来冲突率还是高，那说明分片归属表在故障期间被改过——这是更严重的问题，必须先停回切、核对元数据。

## 背诵要点
1. 归属用**分片表**不用取模：扩容只搬 1/N 的分片且可逐片校验；分片表本身是单点，必须多数派可写 + 双人复核。
2. 冲突按字段语义分四类：LWW（谁赢都行的展示字段，但时钟漂移会静默丢写）、版本向量（不能丢写的字段，只检测不解决）、PN-counter（余额/计数，可交换）、状态机单调（订单状态，取消与履约冲突必须人工）。
3. 回切四闸门取「与」：反向同步积压 0、冲突率 < 1e-4、复制延迟 < 1s、P99 涨幅 < 10%；缺一条就是「故障单元用户数据回退」的隐蔽事故。

## 复盘追问
1. 三单元里有一个单元只是变慢（P99 从 80ms 到 2s），没宕机，要不要切走？（提示：先算剩余容量——切走后另外两个各扛 1.5 倍，若余量不足 20% 会连锁雪崩；正确动作是限流 + 摘除部分流量（A135 的步进），并确认是「本单元内部问题」还是「跨单元依赖变慢」，后者切走也没用）
2. 运营后台要查「某商户下所有订单」，商户的用户散在三个单元，怎么做到 200ms 内返回？（提示：fan-out 三单元 = 3×P99 + 合并，超时就只能建异构索引——CDC 汇到 ES/ClickHouse 按商户建宽表；在线事务永远留在单元内，跨单元聚合只服务运营场景，且要能接受秒级延迟与「数据截止到 T-1」的口径声明）
