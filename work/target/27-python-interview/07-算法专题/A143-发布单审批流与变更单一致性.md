### A143 · 发布单与变更单

> 难度:★★☆ | 标签:变更管理, 审批流, 场景题

**问**（笔试·场景题）：「发布了 v2.3 但变更单写的 v2.2 的内容」——发布单与实际变更不一致的事故形态有哪些（忘记更新变更单/变更单合并了多个发布/发布内容与审核内容漂移），审批流怎么设计才不「橡皮图章」（审批人看什么），「低风险变更免审批」的准入标准怎么定，变更单系统与发布系统打通（自动生成/自动关闭）的收益是什么？

**答**：① 不一致事故三形态：**漂移**（开发到发布之间代码变了，变更单还是审核时的 diff）、**合并单**（一次发布带 N 个变更但只写了一个）、**口头追加**（「顺手把 XX 也发了」——最危险，未经审核的内容上线）。根因共同点：变更单是**手工维护的文档**，与发布事实脱钩。② 审批防橡皮图章：审批人看的是**三件套**——变更内容 diff（机器生成的）、影响面（Q123 爆炸半径）、回滚方案（一键回滚命令可执行验证）——审批耗时中位数监控（审批 <30 秒 = 图章嫌疑，抽检）。③ 免审批准入（A133 L3 同构）：feature flag 包裹 + 可秒级回滚 + 不动数据 schema + 自动化测试全绿——四条同时满足才免审，且免审也要**事后登记**（免审不等于免记录）。④ 系统打通收益：发布系统自动生成变更单（从 PR/commit 自动汇总内容——消灭漂移）、发布成功自动关闭变更单（消灭漏关）、未关联变更单的发布被 CI 拒绝（消灭口头追加）——一致性由系统保证而非人保证。

```python
# 全部标准库；demo 实现「发布单自动生成 + 一致性校验 + 审批质量抽检」
import hashlib, time

def auto_change_record(prs: list[dict]) -> dict:
    """从 PR 列表自动汇总变更单（消灭漂移与合并单）。"""
    return {"version": f"v2.{max(p['minor'] for p in prs)}",
            "prs": [{"id": p["id"], "summary": p["summary"], "risk": p["risk"]} for p in prs],
            "hash": hashlib.sha256(str(sorted(p['id'] for p in prs)).encode()).hexdigest()[:8],
            "rollback": "helm rollback release --version -1"}

def audit_approved(reviews: list[float], threshold_s: float = 30) -> list[str]:
    """审批质量抽检：耗时 <30s 的审批标记图章嫌疑。"""
    return [f"review@{i} 耗时 {t}s → 图章嫌疑，抽检"
            for i, t in enumerate(reviews) if t < threshold_s]

def ci_gate(release: dict, change_record: dict) -> str:
    """CI 闸：发布的 PR 集合必须与变更单完全一致（消灭口头追加）。"""
    release_ids = sorted(p["id"] for p in release["prs"])
    record_ids = sorted(p["id"] for p in change_record["prs"])
    if release_ids != record_ids:
        return f"REJECT: 发布包含变更单外内容（口头追加拦截）"
    return "PASS"

if __name__ == "__main__":
    prs = [{"id": "PR-1", "summary": "修复金额精度", "minor": 3, "risk": "mid"},
           {"id": "PR-2", "summary": "新增导出字段", "minor": 3, "risk": "low"}]
    rec = auto_change_record(prs)
    print("自动变更单:", rec["version"], "| PR:", [p["id"] for p in rec["prs"]], "| rollback:", rec["rollback"][:20], "...")
    release = {"prs": prs + [{"id": "PR-9", "summary": "口头追加的危险改动", "minor": 3}]}
    verdict = ci_gate(release, rec)
    print("CI 闸:", verdict)
    assert "REJECT" in verdict                     # 口头追加被拦截 ✅
    suspect = audit_approved([5.0, 12.0, 25.0])
    print("审批抽检:", suspect or "无图章嫌疑")
    assert suspect == []
    # 口径：一致性由系统保证（自动生成/自动关闭/CI 拦截口头追加）；
    # 审批三件套（diff/影响面/回滚方案），免审四条件+事后登记。
```

**追问**：1) 为什么「口头追加」最危险？——它是**完全未经审核**的代码（不在任何变更单/测试计划里），出问题无人预判影响面；且出事后变更单无法追溯（查不到它怎么上线的）——系统闸（CI 拒绝）是唯一可靠防线。2) 「审批 <30 秒」抽检会不会误伤（资深审批人就是快）？（提示：抽检不是处罚——标记后人工复核「该审批是否真的看了 diff」（评论记录佐证）；连续多次 <30s 且无评论才升级谈话——数据引发对话而非直接定罪）3) 免审变更的事后登记被遗忘怎么治？（提示：登记动作嵌入发布流程（发布必填变更单号，免审单系统自动生成草稿待补摘要）——流程内嵌优于事后催办）

## 背诵要点
1. 不一致三形态：漂移/合并单/口头追加——根因都是手工维护文档与发布事实脱钩。
2. 审批三件套（机器 diff/爆炸半径/回滚方案）+ 审批耗时中位数监控防图章；免审四条件 + 事后登记。
3. 一致性由系统保证：自动生成变更单、自动关闭、CI 拒绝变更单外内容。

## 复盘追问
1. 变更单系统打通做了，但团队觉得「填单麻烦」，怎么优化不放松管控？（提示：自动化承担填写（PR 信息自动汇总，人只补风险标注）——管控强度不变、人力成本降到最低；麻烦的从来不是管控是手工）
2. 「发布成功自动关闭变更单」可能关闭一个其实失败的发布（虚报成功），怎么防？（提示：关闭条件绑定「健康指标过观察窗」（发布后 N 分钟错误率正常）而非「部署完成」——发布完成≠发布成功，Q7013 灰度口径）
