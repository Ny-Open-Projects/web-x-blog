### A178 · 读多写少优化

> 难度:★★☆ | 标签:读写比, 缓存, 架构

**问**（笔试·场景题）：商品详情页读写比 1000:1（读 10 万 QPS 写 100 QPS）——读多写少的优化阶梯（缓存/读副本/预计算，按 ROI 排序），「写时预计算」vs「读时计算」的取舍（写多读少的反向场景怎么处理），缓存命中率到 99% 后「剩余 1% 回源」的优化（还有什么可挖），「读写比随时间变化」（早高峰读、晚间写）的自适应架构怎么设计？

**答**：① 优化阶梯（ROI 排序）：**缓存**（10 万 QPS 读中 99% 可缓存——成本最低收益最大）→ **CDN/边缘**（静态部分推到边缘，回源再降一档）→ **读副本**（缓存挡不住的读，副本扩展）→ **预计算**（读时算太贵的场景：汇总表/宽表物化）。② 写时 vs 读时预计算：读多写少 → **写时预计算**（写 100 QPS 时把读需要的视图算好，读时 O(1) 取——写承担计算成本划算）；反向（写多读少，如日志摄入）→ 读时计算或流式预聚合——方向由读写比定，做反了就是把成本放错位置。③ 剩余 1% 回源：分类降档——缓存 miss 的原因分析（过期/淘汰/首次访问），过期集中 → TTL 抖动（Q6114）、冷 key → 本地缓存二级（Q6604）、首次访问 → 预热（A158）；挖完剩下的是「真随机 miss」——用读副本承接即可，别追求 100%（边际收益递减）。④ 读写比自适应：早高峰读（扩缓存+读副本权重）晚间写（缩读扩写队列）——HPA 按指标弹性 + 缓存容量日级调度。

```python
# 全部标准库；demo 实现「读写比分析 + 优化阶梯建议器」
import json

def optimize_advice(read_qps: float, write_qps: float,
                    cache_hit_rate: float, is_static: bool) -> list[str]:
    ratio = read_qps / max(write_qps, 1)
    advice = []
    if ratio > 100 and cache_hit_rate < 0.9:
        advice.append(f"读写比 {ratio:.0f}:1 → 缓存优先（命中率 {cache_hit_rate:.0%} 有巨大空间）")
    if ratio > 100 and cache_hit_rate >= 0.99 and is_static:
        advice.append("命中率 99% 且内容静态 → CDN/边缘缓存（再降回源一档）")
    if cache_hit_rate >= 0.99 and not is_static:
        advice.append("剩余 1% miss 分类降档：TTL 抖动/本地二级/预热 TopN（A158）")
    if write_qps > 1000 and ratio < 1:
        advice.append("写多读少 → 读时预计算改为写时预聚合（成本换位）")
    if 0.2 < cache_hit_rate < 0.9 and ratio > 10:
        advice.append("命中率中位 → 检查 TTL/键设计（A189），而非盲目加副本")
    return advice

def cost_position_check(write_qps: float, read_qps: float,
                        precompute_at: str) -> str:
    """预计算位置检查：成本应放在「频率低」的一侧。"""
    if precompute_at == "write" and write_qps < read_qps / 100:
        return "✅ 写时预计算正确（写频率低，读 O(1)）"
    if precompute_at == "write" and write_qps > read_qps:
        return "❌ 位置错误：写多读少还写时预计算 = 成本放错边"
    return "需结合查询复杂度判断"

if __name__ == "__main__":
    print("商品详情页（100000:100）:")
    for a in optimize_advice(100000, 100, 0.85, is_static=False):
        print("  -", a)
    print("\n审计日志（100:10000 写多读少）:",
          cost_position_check(10000, 100, "write"))
    assert "位置错误" in cost_position_check(10000, 100, "write")
    # 口径：优化阶梯 ROI 排序（缓存>CDN>副本>预计算）；预计算放频率低的一侧；
    # 命中率 99% 后按 miss 分类降档，不追求 100%。
```

**追问**：1) 为什么优化阶梯是「缓存 > CDN > 副本 > 预计算」的顺序？——按「单位成本的削减量」：缓存每 GB 减掉的回源 QPS 最大（命中即免回源）、CDN 次之（只覆盖静态）、副本要维护（成本线性）、预计算最贵（开发+存储+一致性）——ROI 由成本收益比排序，顺序不是教条是成本函数。2) 「读写比随时间变化」的自适应有什么实际坑？（提示：伸缩的滞后性（扩缓存 10 分钟、流量涨 1 分钟——峰值期必然缺口）——自适应不能替代「余量设计」（日常水位留 30%，A121 容量口径）；自适应管「常规波动」，容量管「极端峰值」）3) 「命中率 99% 后的 1%」值得优化吗？（提示：10 万 QPS 的 1% = 1000 QPS 回源——量级仍可观，分类降档（过期抖动/冷 key/预热）能再砍一半；但边际收益递减——到「真随机 miss」就停，用副本承接，别为最后 0.1% 重构架构）

## 背诵要点
1. 读多写少优化阶梯 ROI：缓存 > CDN/边缘 > 读副本 > 预计算——按单位成本削减量排序。
2. 预计算放「频率低的一侧」：读多写少写时算（读 O(1)），写多读少读时算/流式聚合——方向由读写比定。
3. 命中率 99% 后按 miss 成因分类降档（TTL 抖动/冷 key 二级/TopN 预热），真随机 miss 用副本承接。

## 复盘追问
1. 缓存命中率 85% 但「提升到 95% 加了内存却没降回源 QPS」——为什么？（提示：剩余 miss 是「首次访问/冷 key」（内存救不了）而非「容量不足」——先分析 miss 构成（过期/淘汰/首次）再定向投入（A158 预热/A110 热点），盲目加内存是常见浪费）
2. 「读写比 1000:1」的产品做了「写时预计算」后写入延迟翻倍，写方团队抗议——怎么仲裁？（提示：写入延迟是读方收益的成本转移——业务方拍板：写入延迟可接受（异步预计算不阻塞写主流程）→ 预计算改异步（写完成后触发，Q7175 中间结果缓存）——跨团队成本转移必须业务拍板+异步化缓解）
