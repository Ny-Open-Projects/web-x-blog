### A225 · 能力梯队老化检测

> 难度:★★☆ | 标签:能力矩阵, 梯队, 治理

**问**（笔试·场景题）：能力矩阵显示「所有人都 solo」，但实际值班频频求救——能力矩阵的「老化」（solo 认证是半年前的，系统已变化），老化的检测信号（处置时长变长/求救频率上升/演练失败率上升），「重新认证」的机制（solo 认证随系统版本过期），「能力梯队」的健康的量化指标（覆盖矩阵的退化率）怎么算？

**答**：① 老化的本质：solo 认证绑定的是「当时的系统状态」——系统演进（新服务/新依赖/新故障模式）后，认证的能力覆盖面缩水（会处理旧故障，不会处理新故障）。② 老化检测信号：**处置时长趋势**（同类型故障的 MTTR 逐月上升——熟练度在退步或系统变复杂）、**求救频率**（solo 人员主动求救的比例上升）、**演练失败率**（同型演练失败率上升，A144）——三信号任一触发即「能力矩阵待复审」。③ 重新认证：solo 认证带**有效期**（6 个月，或系统大版本发布后强制重认证——关键变更（新依赖/新架构）触发全量重认证）；重认证 = 演练 solo 通过（不是重新培训——验证而非教学）。④ 梯队健康量化：**覆盖矩阵退化率** = （认证数 − 验证有效数）/ 认证数 + 覆盖缺口数变化——退化率上升说明梯队健康在恶化（行动项：补充演练/培训）。

```python
# 全部标准库；demo 实现「老化检测 + 重新认证」
import time

class CapabilityMatrix:
    def __init__(self, solo_valid_days: int = 180):
        self.solo_valid = solo_valid_days * 86400
        self.certs: dict[str, dict] = {}       # (person, fault) -> {certified_at, drills}
    def certify(self, person: str, fault: str):
        self.certs[(person, fault)] = {"certified_at": time.monotonic(),
                                       "drill_pass": True}
    def is_stale(self, person: str, fault: str, major_release_since_cert: bool) -> bool:
        c = self.certs.get((person, fault))
        if c is None:
            return True
        age = time.monotonic() - c["certified_at"]
        return age > self.solo_valid or major_release_since_cert   # 过期或大版本后重认证
    def drill_result(self, person: str, fault: str, passed: bool):
        c = self.certs[(person, fault)]
        if not passed:
            c["drill_pass"] = False             # 演练失败 → 认证降级
            return f"{person}/{fault} 演练失败 → solo 降级为 assisted，重认证"
        return f"{person}/{fault} 演练通过 → solo 维持"

def degradation_rate(total_cert: int, valid_cert: int, coverage_gaps: int) -> float:
    """梯队退化率 = (失效认证 + 覆盖缺口) / 总认证。"""
    return ((total_cert - valid_cert) + coverage_gaps) / max(total_cert, 1)

if __name__ == "__main__":
    m = CapabilityMatrix(solo_valid_days=180)
    m.certify("alice", "db_lock")
    stale = m.is_stale("alice", "db_lock", major_release_since_cert=True)
    assert stale                                # 大版本发布 → 强制重认证 ✅
    print("老化检测: 大版本发布后强制重认证 ✅")
    print(m.drill_result("alice", "db_lock", passed=False))
    dr = degradation_rate(total_cert=10, valid_cert=6, coverage_gaps=2)
    print(f"梯队退化率: {dr:.0%}（>30% 即行动项：补演练/补培训）")
    # 口径：solo 认证 6 个月有效或大版本后强制重认证；演练失败降级；
    # 退化率 =（失效认证+覆盖缺口）/总认证——梯队健康量化。
```

**追问**：1) 为什么「大版本发布后强制重认证」？——大版本（新架构/新依赖）改变故障模式与处置方法——旧 solo 的能力覆盖面失效；重认证=演练 solo 通过（验证新系统下的处置能力），不是重新培训——认证是「验证」机制不是「教育」机制。2) 「处置时长趋势上升」怎么与「系统变复杂」区分？（提示：同型故障 MTTR 上升可能因故障本身复杂化（新依赖引入）——对比「系统变更前后同型故障的处置差异」+ 演练基线（演练中同型处置的时长，演练环境系统可控）——区分「人的退步」与「系统的复杂化」，行动项不同）3) 退化率 30% 的阈值依据？（提示：>30% 意味着 1/3 的认证不可信——值班时「谁会处理」的判断失真；阈值不是魔法数，是「值班时求救率上升」与「退化率」的历史相关性标定——阈值随团队校准）

## 背诵要点
1. 能力认证老化 = solo 绑定当时系统状态，系统演进后覆盖面缩水——三信号检测（MTTR 趋势/求救频率/演练失败率）。
2. 重新认证 = solo 有效期 6 个月 + 大版本发布强制重认证（演练通过，非培训）；演练失败 solo 降级。
3. 梯队退化率 =（失效认证 + 覆盖缺口）/ 总认证——退化率是梯队健康的量化指标（>30% 行动项）。

## 复盘追问
1. 重认证运动（全员重新演练）搞了一次，三个月后又老化了——一次性运动的问题在哪？（提示：老化是持续过程（系统持续演进）——一次性运动治标，机制治本：认证有效期自动过期 + 演练排入值班轮换（每季度轮到即演）——把重认证变成值班轮换的一部分而非独立运动）
2. 能力矩阵/退化率这些「治理数据」谁看谁用？（提示：值班 owner 月度看（梯队健康是值班可持续性的核心指标）+ 与排班系统联动（退化率高→排班加 shadow 培养班）——治理数据要有消费者才有生命力（Q220 周报治理信号同构））
