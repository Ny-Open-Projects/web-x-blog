### A186 · 发布日历

> 难度:★★☆ | 标签:发布排期, 协调, 场景题

**问**（笔试·场景题）：6 个团队都要发布，同一周内——「各自想发就发」的冲突形态有哪些（共享依赖竞争/同时变更难归因/值班过载），发布日历怎么排（时间槽分配/优先级仲裁），「大发布」（多服务联动的变更，A159 编排）和小发布的资源怎么错开，发布日历本身的维护成本怎么控制（没人更新就失效）？

**答**：① 冲突三形态：**共享依赖竞争**（同时发布都改 DB schema，迁移冲突）、**归因灾难**（同时发 3 个变更，故障无法归因——Q7013 灰度判定失效）、**值班过载**（同时发布 = 值班员盯 N 个发布+护栏）。② 日历排期：**时间槽制**（每天上午 2 个发布槽 + 下午 2 个，先到先得 + 冲突调停）；「大发布」独占日（多服务联动的变更占一整天，其他团队禁发）；周五/节前禁发（Q133 周五规则）。③ 大小错开：大发布（联动编排）排「发布周」固定日（周二/周四），小发布（单服务/flag）随时槽；大发布前 24h 冻结相关服务的小发布（防止交互故障）。④ 维护成本：日历由发布系统**自动登记**（发布即占槽，不需要人维护日历文档——手工日历必然失效）；冲突检测自动（同槽两个发布依赖同一服务 → 自动提示调停）；空槽可视化（本周剩余槽位一目了然）。

```python
# 全部标准库；demo 实现「发布槽管理 + 冲突检测」
from collections import defaultdict
import json

class ReleaseCalendar:
    def __init__(self, slots_per_day: int = 4, freeze_related_hours: int = 24):
        self.slots = defaultdict(list)          # day -> [(team, services, level)]
        self.slots_per_day = slots_per_day
        self.freeze_hours = freeze_related_hours
    def request(self, day: str, team: str, services: list[str],
                level: str = "small") -> str:
        day_slots = self.slots[day]
        if level == "big":
            if day_slots:                       # 大发布独占日
                return "REJECT: 大发布需独占日（当日已有其他发布）"
            self.slots[day].append((team, services, level))
            return "BOOKED: 大发布独占日"
        if len(day_slots) >= self.slots_per_day:
            return "REJECT: 当日槽满"
        for _, svcs, _ in day_slots:
            overlap = set(svcs) & set(services)
            if overlap:
                return f"REJECT: 与已排发布共享服务 {overlap}（防交互故障）"
        self.slots[day].append((team, services, level))
        return f"BOOKED: {day} 槽 {len(day_slots)}/{self.slots_per_day}"
    def freeze_before_big(self, big_day: str) -> str:
        return f"大发布前 {self.freeze_hours}h：相关服务小发布冻结（A133 联动）"

if __name__ == "__main__":
    cal = ReleaseCalendar()
    print(cal.request("2026-11-24", "orders", ["order", "stock"], "big"))   # 大发布占日
    print(cal.request("2026-11-24", "search", ["search"], "small"))         # 同日被拒
    print(cal.request("2026-11-25", "orders", ["order"], "small"))          # 依赖服务重叠
    print(cal.request("2026-11-25", "ml", ["ml"], "small"))
    print(cal.request("2026-11-25", "infra", ["infra"], "small"))
    print(cal.freeze_before_big("2026-11-24"))
    # 口径：大发布独占日；同槽共享服务冲突自动检测；槽位自动登记（发布即占槽）；
    # 周五/节前禁发（Q133）；日历由系统维护非人工文档。
```

**追问**：1) 为什么大发布要「独占日」？——多服务联动的发布本身消耗全部协调资源（编排/验证/值班专注），叠加其他发布 = 归因灾难 + 值班过载；独占日的代价（其他团队停一天）远小于叠加故障——且独占日集中了全团队的注意力（大发布值得）。2) 「共享服务冲突自动检测」的服务清单从哪来？（提示：发布单声明的 services + Q123 依赖地图扩展（发布的服务会影响哪些下游）——纯声明的清单会漏（忘记列出），依赖地图补全；冲突规则可配置（强依赖拒绝/弱依赖告警））3) 发布槽满了紧急变更怎么办？（提示：紧急变更不走日历（L1 通道 Q133），但事后必须补登记（占槽审计）——日历管「计划内」，紧急通道独立存在但留痕）

## 背诵要点
1. 冲突三形态：共享依赖竞争/归因灾难/值班过载——同一周多团队发布的三大风险。
2. 发布日历：时间槽制（先到先得+冲突调停）+ 大发布独占日 + 大发布前 24h 相关服务冻结。
3. 日历由发布系统自动登记（发布即占槽）——手工日历必然失效，冲突检测自动化（依赖地图补全）。

## 复盘追问
1. 团队嫌日历流程慢，直接发了（绕过日历），发现机制？（提示：发布系统是唯一发布入口（CI/CD 强制走系统）——绕过日历=无法部署；事后发现的绕过发布自动登记+通报——「不可绕过」比「要遵守」可靠）
2. 发布槽长期被一个强势团队占满，其他团队排不上，怎么仲裁？（提示：槽位配额（每团队每周上限）+ 优先级仲裁（变更高优走 L1 通道）+ 定期审视（槽位占用率数据公开——资源分配透明化，强势占用是治理问题不是调度问题））
