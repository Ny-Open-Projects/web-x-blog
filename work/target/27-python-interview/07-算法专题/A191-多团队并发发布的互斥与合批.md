### A191 · 多团队并发发布

> 难度:★★★ | 标签:发布调度, 并发, 场景题

**问**（笔试·场景题）：3 个团队同一小时都要发布（改同一个服务）——「并发发布同服务」的冲突类型（代码合并冲突只是最浅层，配置冲突/依赖版本冲突/行为交互），发布调度怎么设计（同服务串行+跨服务并行），「合批发布」（多团队的变更一起发）的收益与风险（出问题谁的锅——变更归因），发布排队时的优先级怎么定（紧急程度/业务价值/变更风险）？

**答**：① 冲突三层：**代码层**（合并冲突——git 解决，最浅）；**配置层**（团队 A 改配置项 X、团队 B 也改 X——合并后语义互相打架）；**行为层**（A 的变更假设 B 的行为、B 同时改了——分别测试都绿、合起来炸——交互 bug）。② 调度设计：**同服务串行**（服务级锁：同一服务的发布队列化，上一个的护栏过了才发下一个）；**跨服务并行**（无依赖关系的发布同时进行——互斥段思想，Q50 派工同构）；依赖链上的服务发布按拓扑序（Q123 依赖地图）。③ 合批的归因方案：合批发布配**变更标记**（每个变更独立 flag/独立提交，可单独回滚）+ 出问题时二分回滚（git bisect 语义：批量回滚定位到罪魁变更）——合批的收益（发布频率降低、批间稳定）与归因能力必须同时存在。④ 排队优先级：紧急修复 > 业务价值（收入相关）> 风险（低风险先发占容量）——紧急插队要有代价（插队者下批降权），防止所有人自称紧急。

```python
# 全部标准库；demo 实现「服务级发布锁 + 合批二分归因」
import time, threading

class ReleaseScheduler:
    def __init__(self):
        self.locks: dict[str, threading.Lock] = defaultdict(threading.Lock)
        self.queue: dict[str, list] = defaultdict(list)
    def request(self, service: str, team: str, change: dict):
        self.queue[service].append({"team": team, "change": change})
    def try_release(self, service: str) -> str | None:
        lock = self.locks[service]
        if not lock.acquire(blocking=False):       # 服务级互斥：同服务串行
            return f"{service} 正在被其他团队发布，排队"
        try:
            item = self.queue[service].pop(0) if self.queue[service] else None
            return f"{item['team']} 发布 {service}: {item['change']['name']}" if item else None
        finally:
            lock.release()

def bisect_rollback(changes: list[dict], bad_check) -> dict:
    """合批出问题 → 二分回滚定位罪魁变更。"""
    lo, hi = 0, len(changes)
    while lo < hi:
        mid = (lo + hi) // 2
        if bad_check(changes[:mid + 1]):           # 前半含罪魁
            hi = mid
        else:
            lo = mid + 1
    return changes[lo]

from collections import defaultdict

if __name__ == "__main__":
    sched = ReleaseScheduler()
    sched.request("order-svc", "team-A", {"name": "加优惠券"})
    sched.request("order-svc", "team-B", {"name": "改运费计算"})
    print(sched.try_release("order-svc"))          # team-A 拿到锁
    print(sched.try_release("order-svc"))          # team-B 被互斥排队
    changes = [{"id": 1}, {"id": 2}, {"id": 3}, {"id": 4}]
    culprit = bisect_rollback(changes, lambda subset: any(c["id"] == 3 for c in subset))
    print("二分定位罪魁:", culprit)
    assert culprit["id"] == 3
    # 口径：同服务串行（锁）+ 跨服务并行；合批必须配独立 flag 可单独回滚；
    # 排队优先级：紧急 > 业务价值 > 低风险先发。
```

**追问**：1) 为什么「合批发布」需要每个变更独立可回滚？——合批省的是发布频率，出问题时「整批回滚」会把无辜变更一起撤（业务中断扩大）——独立 flag 回滚=精准摘除罪魁、保留无害变更；无独立回滚能力的合批是赌博。2) 服务级锁的「锁粒度」争论：锁服务还是锁模块？（提示：锁服务（粗）简单可靠但吞吐低；锁模块（细）吞吐高但交互 bug 风险（同服务内模块行为交互）——默认粗粒度，模块间确证无交互（契约测试覆盖）才允许细粒度——粒度演进要有证据）3) 「紧急插队」的代价机制怎么设计？（提示：插队=当前排队变更延后（它们是受害者）——插队者下一批降权（排到队尾）+ 插队次数进报表（频繁插队=发布规划有问题，治理信号）——让紧急的真实成本可见）

## 背诵要点
1. 冲突三层：代码（最浅）/配置项互踩/行为交互（分别测绿合起来炸）——同服务发布串行化是底线。
2. 调度：服务级锁串行 + 跨服务并行 + 依赖链拓扑序；合批必须配独立 flag 回滚 + 二分归因。
3. 排队优先级：紧急 > 业务价值 > 低风险先发；紧急插队带代价（下批降权+报表）防人人紧急。

## 复盘追问
1. 合批发布后二分回滚定位到罪魁，但罪魁变更「单独测是绿的」——交互 bug 怎么系统性防？（提示：交互 bug 只能靠「合批后的集成测试」（合批 batch 的契约测试+核心链路探活）+ 同服务变更的变更前沟通（调度器在排队时提醒同服务多团队）——分别测试绿≠合批绿，这是并发发布的本质风险）
2. 团队抱怨「锁太严发布效率低」，怎么用数据对话？（提示：锁排队时长分布（P95 排队 <30min 则锁不是瓶颈）+ 交互事故数对比（锁前 vs 锁后）——用「锁省下的事故成本」对话「排队损失」，数据齐全后可讨论细粒度）
