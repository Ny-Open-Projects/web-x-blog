### Q7248 · 补数和定时任务撞了同一个分区：回填窗口与增量的互斥

难度：P6 ｜ 标签：回填 backfill、增量任务、窗口互斥、分区锁、重复处理

基线：Python 3.12；模拟增量任务与按日期补数任务对同一天窗口的并发写入，对比无互斥与租约互斥的重复/丢失。

**问**：数据质量发现某天指标算错了，发起补数（backfill）重跑 11 月 20 日的分区；同一时刻每小时的定时任务也在跑 11 月 20 日 22 点的窗口（迟到数据重刷）。两个任务都写同一张结果表，产出翻倍、指标忽高忽低。补数与增量任务对同一分区的并发写入，应该怎么互斥？

**答**：
- **结论**：根因是**窗口租约缺失**：增量任务和补数任务各自"自扫门前雪"，谁也不知道对方正在写哪个分区。互斥方案是给"表 × 窗口"粒度发租约（Q1310 的租约思路、Q1732 的调度防重入同理）：任务开跑前先注册"我持有 table/ds=2026-11-20"，冲突方要么等待、要么跳过并告警；租约带 TTL + 心跳，任务死了租约自动过期，不会永久锁死。另外补数要声明**版本**：重跑产出 `partition_version=v2`，下游读到新版本才切换，避免一边写一边读的中间态（Q2273 分区级回滚的配套）。
- **取舍**：① 粗粒度互斥（锁整张表）实现简单但吞吐差——补数 30 天窗口期间增量全部停摆；细粒度（表 × 分区/小时窗口）吞吐好但注册表维护复杂；② 等待 vs 跳过：增量任务遇冲突建议"跳过 + 延迟重试"（它的下轮会覆盖补数结果），补数任务建议"独占 + 让增量等待"（补数优先级高且窗口明确）；③ 幂等兜底：就算互斥失效，产出表 upsert 写入 + 版本号也能把损失压到"多算一次"而不是"数据错乱"。
- **实战**：① 互斥注册表用平台已有的元数据库实现即可（表、窗口、owner、TTL、心跳时间）；② 补数任务开跑前 diff"待补窗口 × 增量任务排期"，预估冲突并提示错峰；③ 冲突事件的日志要成体系——谁等了谁、跳了哪个窗口，复盘时才能还原当时写序。

```python
"""回填与增量的窗口租约互斥：表 x 窗口粒度 + TTL + 跳过/等待策略。"""
import time


class WindowLease:
    def __init__(self, ttl_s: float = 300.0) -> None:
        self.holders: dict[tuple[str, str], tuple[str, float]] = {}
        self.ttl = ttl_s

    def acquire(self, table: str, window: str, owner: str) -> bool:
        key = (table, window)
        cur = self.holders.get(key)
        if cur and cur[0] != owner and time.time() - cur[1] < self.ttl:
            return False                           # 他人持有且未过期
        self.holders[key] = (owner, time.time())
        return True

    def release(self, table: str, window: str, owner: str) -> None:
        if self.holders.get((table, window), ("",))[0] == owner:
            self.holders.pop((table, window), None)

    def heartbeat(self, table: str, window: str, owner: str) -> None:
        if self.holders.get((table, window), ("",))[0] == owner:
            self.holders[(table, window)] = (owner, time.time())


def run_job(lease: WindowLease, table: str, window: str, owner: str,
            writes: int, mode: str) -> int:
    """mode: backfill=独占必须拿到 | incremental=拿不到就跳过(等下轮)"""
    if lease.acquire(table, window, owner):
        print(f"  {owner:<12} 拿到 {table}/{window} -> 写入 {writes} 条")
        lease.release(table, window, owner)
        return writes
    if mode == "incremental":
        print(f"  {owner:<12} 窗口被占 -> 跳过本窗，下轮重试")
        return 0
    time.sleep(0)                                  # backfill 真实场景中等待重试
    return run_job(lease, table, window, owner, writes, mode)


if __name__ == "__main__":
    lease = WindowLease(ttl_s=300)
    print("场景: 补数重跑 11-20 全天，增量任务也在刷 11-20 的 22 点窗口")
    total_backfill = run_job(lease, "dws.dau", "ds=2026-11-20", "backfill-1", 9600, "backfill")
    total_incr = run_job(lease, "dws.dau", "ds=2026-11-20", "incr-hourly", 400, "incremental")
    print(f"产出: backfill={total_backfill:,} 条(独占重算) | incr={total_incr} 条(跳过待重试)")
    print("无互斥对照: 两任务同窗各写一次 -> DAU 翻倍 + 指标抖动")
    print("\n租约 TTL 兜底: 任务被杀后 ttl 到期自动释放, 不会永久锁死窗口")
    stale = WindowLease(ttl_s=0.0)
    stale.holders[("dws.dau", "ds=2026-11-21")] = ("dead-task", 0)
    print("死任务残留租约可被新任务接管:", stale.acquire("dws.dau", "ds=2026-11-21", "incr-2"))
    print("结论：互斥粒度选 表x窗口；幂等 upsert 是互斥失效时的最后防线")
```

**追问一**：为什么增量任务冲突时选择"跳过"而不是"等待"？

→ 解析：增量任务通常按固定节奏反复运行（每小时/每分钟），跳过一轮只是延迟一个周期，下轮自然会覆盖该窗口（它是 upsert 幂等的）；如果选择等待，一是补数 30 天窗口会让增量排队几小时甚至更久，二是多个等待者同时醒来还会造成写风暴。而补数任务是低频、明确窗口的一次性动作，让它独占等待更合理——两种任务角色不同，策略不对称。这类策略差异应该写进平台规范，而不是每个任务自己拍。

**追问二**：补数重跑期间下游正在读这个分区，会读到什么？

→ 解析：取决于写入方式。直接覆盖写（先 DELETE 再 INSERT 或 INSERT OVERWRITE）会有一个"半新半旧"的可见窗口——下游可能读到不一致的中间态。规范做法是**版本化分区**：补数写到 `ds=... ,v=2` 的新版本，写完原子地把"当前版本指针"切到 v2，下游要么显式订阅最新版本、要么读视图（视图定义指向当前版本）。这样补数期间下游读到的始终是完整的旧版本，切换是瞬时的。这与 Q2273 的分区级回滚、Q1975 的影子表切换共享同一套思想：**写不可见的副本，原子切换指针**。
