### Q7087 · 调度器元数据库压力的容量账

难度：P6/P7 ｜ 标签：调度系统 / 元数据 / 容量规划

**问**：数据平台调度器（Airflow 类）管着 5 万个 DAG 任务实例/天，最近调度延迟越来越大，scheduler 进程 CPU 不高。瓶颈会在哪？容量怎么规划？

**答**：
- **结论**：调度器的隐性瓶颈通常不在 scheduler CPU 而在元数据库：scheduler 心跳/查询循环（每 1-5 秒轮询任务状态、抢占执行槽）、海量 task_instance 行的状态更新、历史清理滞后导致行数无界增长——QPS 与行数双涨后 DB 慢查询拖慢调度循环，表现为"调度延迟上升"。容量账：`元数据库 QPS ≈ 调度循环频率 × 每循环查询数 + 任务实例数 × 每实例状态变更次数`，5 万实例/天 × 每实例 5 次变更 ≈ 3000 QPS 稳态，峰值随重试放大。
- **取舍**：三种治理路线的取舍：① 历史数据定期清理/归档（删除是大事务，要分批，避免又打挂 DB）；② scheduler 与元数据库分离部署 + 读写分离（读扩散到副本，状态更新走主库）；③ 缩短调度循环间隔换取延迟，代价是 DB QPS 上升——方向反了，正确的是减少每循环的查询量（批量抢占、索引优化）而不是提频。
- **实战**：规划动作：① 元数据库独立实例，不与业务库混部；② 关键索引审查（task_instance 按 dag_id+execution_date+state 的复合索引）；③ 保留策略：运行历史保留 30-90 天，XCom/日志立即归档对象存储；④ 监控调度延迟（dag 创建到首任务启动的间隔）作为北极星指标，DB P99 做先行指标。

```python
# 调度器元数据库容量估算器（纯标准库）
# 基线：Python 3.9+


def metadata_qps(daily_instances: int, state_changes_per_task: int = 5,
                 loop_interval_s: float = 5, queries_per_loop: int = 20,
                 schedulers: int = 2) -> float:
    task_qps = daily_instances * state_changes_per_task / 86400
    loop_qps = schedulers * queries_per_loop / loop_interval_s
    return task_qps + loop_qps


def retention_rows(daily_instances: int, retention_days: int,
                   xcom_ratio: float = 0.3) -> int:
    return int(daily_instances * retention_days * (1 + xcom_ratio))


def main() -> None:
    qps = metadata_qps(50_000)
    print(f"元数据库稳态 QPS ≈ {qps:,.0f}")
    assert 3000 < qps < 5000
    for days in (30, 365):
        rows = retention_rows(50_000, days)
        print(f"保留{days}天: task_instance+XCom ≈ {rows/1e6:.0f}M 行")
    assert retention_rows(50_000, 365) > 200 * 1e6  # 一年不清理就是两亿行
    # 缩短循环间隔反而抬升 QPS
    assert metadata_qps(50_000, loop_interval_s=1) > metadata_qps(50_000, loop_interval_s=5)


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"调度延迟"比"任务成功率"更适合做调度系统的北极星？
→ 一句话提示：成功率只反映任务质量，调度延迟反映系统健康（DB 压力、抢占竞争、心跳超时都会先表现为延迟上升），它是容量问题的先行指标。

**追问 2**：多 scheduler 抢占任务如何避免 DB 热点行竞争？
→ 一句话提示：抢占用 `SELECT ... FOR UPDATE SKIP LOCKED` 或按 DAG 分片（每个 scheduler 只管一部分 DAG），避免所有循环撞同一批未锁行。

## 背诵要点
- 调度器瓶颈常在元数据库：QPS ≈ 实例数×状态变更数/86400 + 调度循环查询；缩短循环间隔是反方向优化。
- 行数容量：实例数 × 保留天数 × (1+XCom 比例)，一年不清理即亿级行，清理必须分批。
- 北极星指标：调度延迟；先行指标：元数据库 P99 与心跳超时。

## 复盘追问
- 为什么历史清理自己做分批比依赖 DB 大事务删除好？提示：一次性 DELETE 千万行会产生巨量 WAL/undo 与锁竞争，分批 + 低峰执行 + 每批限速。
- 如果业务量翻 10 倍，调度架构怎么演进？提示：DAG 分片多 scheduler 水平扩展 + 元数据库按分片拆库或换云托管分区方案，单库终会到顶。
