### Q7116 · 定时任务挤峰的错峰容量规划

难度：P6 ｜ 标签：容量规划 / 调度 / 错峰

**问**：一台 8C 的调度机上排了 40 个 crontab 任务，其中 23 个都配在整点 0 分。每到整点机器 load 飙高、任务互相拖慢、有的超时重试进一步加剧。这道挤峰账怎么算？错峰怎么排才不是"把时间随手挪一挪"？依赖链任务怎么排？

**答**：
- **结论**：挤峰账：把每个任务的"启动时刻 × CPU/内存占用 × 预估时长"投影到时间轴上求峰值并发资源需求，与机器容量（8C×某安全系数）比较。挤峰的次生灾害比峰值本身更糟：任务慢 → 重叠加深 → 重试叠加 → 雪崩（Q7042 重试风暴同源）。错峰不是随手挪：① **按依赖分层**——有依赖链的任务按 DAG 拓扑层级分配时段（下游等待上游完成信号而非固定时间，避免"排晚了被上游超时拖死"）；② **按资源画像分组**——CPU 密集与 IO 密集互补排布，同类错开；③ **按业务窗口约束**——对账类必须在数据就绪后（Q7032 就绪探测），不能为错峰违反 SLA；④ **均匀摊布**——无约束任务用"哈希/取模"摊到整点内的分钟槽（如 `0-23 * * * *` 配 task_id mod 60 的 delay），消灭整点尖峰。容量结论：错峰后峰值并发需求应 ≤ 机器容量的 70%，留超时重试与突发余量；否则要么削任务（合并轻任务、降频）要么加资源。
- **取舍**：实现选型：crontab 手排（小规模、漂移难维护）→ 调度平台（Airflow/APScheduler，天然 DAG 化解决依赖分层）→ 容器化并发池（K8s CronJob + 资源 request，让平台做排队）。轻量场景保留 crontab 但加两件套：任务启动前抢机器级信号量（可用 flock 文件锁限制同类并发数）+ 时长与重叠监控（每任务记 start/end，重叠率 >0 报警）。
- **实战**：落地步骤：① 采集 40 个任务的时长/资源画像（历史监控或跑一轮实测）；② 按依赖分层+资源互补重排，输出新的调度表；③ 给"整点家族"里的轻任务做分钟槽摊布；④ 上线后观察峰值 load、任务 P95 时长与重叠率，回归校准；⑤ 新任务上调度表前过一道"容量占位评审"（预估资源×时段与当前峰值余量比对）。

```python
# 挤峰账：任务资源投影到时间轴，求峰值并发与错峰分槽
# 基线：Python 3.9+ 标准库；真实数据来自任务时长/资源监控
from dataclasses import dataclass


@dataclass
class Task:
    name: str
    start_min: int      # 距 0 点的分钟
    duration_min: float
    cpu: float


def peak_cpu(tasks: list[Task], horizon_min: int, step: int = 1) -> tuple[float, int]:
    """返回 (峰值并发CPU, 峰值时刻)。"""
    timeline = [0.0] * (horizon_min // step + 1)
    for t in tasks:
        for m in range(int(t.start_min), int(t.start_min + t.duration_min)):
            timeline[m] += t.cpu
    peak = max(timeline)
    return peak, timeline.index(peak)


def stagger(task_id: int, span_min: int = 120, count: int = 23) -> int:
    """轻任务均匀摊进一个错峰窗口（槽距 = 窗口/任务数）。"""
    return task_id * span_min // count


def main() -> None:
    # 23 个任务挤在 0 分，各 0.5C、平均 8 分钟
    crowd = [Task(f"t{i}", start_min=0, duration_min=8, cpu=0.5) for i in range(23)]
    peak, at = peak_cpu(crowd, horizon_min=60)
    assert peak == 23 * 0.5 and at == 0
    cap = 8 * 0.7   # 8C 机器留 30% 余量
    assert peak > cap
    print(f"整点峰值 {peak:.1f}C > 容量红线 {cap:.1f}C -> 必然挤峰")

    # 错峰：23 个任务均匀摊进 120 分钟窗口，槽距约 5.2 分钟
    staggered = [Task(f"t{i}", start_min=stagger(i), duration_min=8, cpu=0.5)
                 for i in range(23)]
    peak2, _ = peak_cpu(staggered, horizon_min=180)
    assert peak2 <= 2 * 0.5    # 槽距<时长仍有少量重叠，但峰值 <= 2 个并发
    assert peak2 < cap
    print(f"分槽后峰值 {peak2:.1f}C，回到容量红线内（槽距 120/23≈5.2 分钟）")

    # 重排铁律：依赖链按 DAG 层排时段，不能只挪时间
    print("OK: 错峰=依赖分层+资源互补+分槽摊布；峰值须 <= 容量x70%")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么依赖任务要"信号触发"而不是"排晚一点"？
→ 一句话提示：固定偏移无法吸收上游时长波动，上游慢 10 分钟下游就跑空或读半成品；就绪信号/依赖调度（DAG）把正确性交给事件而不是运气，错峰只负责资源维度。

**追问 2**：重叠率监控怎么定义才算有效信号？
→ 一句话提示：按任务对统计"同时运行"的占比与时长，重点盯"同一任务自己与自己重叠"（上一轮没跑完下一轮已启动）——这是容量不足或任务退化的最直接信号。

## 背诵要点
- 挤峰账 = 任务(启动时刻×资源×时长)投影到时间轴求峰值并发，红线 = 机器容量 × 70%；挤峰的次生灾害（超时重试叠加雪崩）比峰值本身更致命。
- 错峰四法：依赖分层（DAG 信号触发）、资源画像互补、分钟槽取模摊布消灭整点尖峰、业务窗口约束不可违反。
- 轻量防线两件套：flock/信号量限同类并发 + 任务重叠率监控（自重叠是容量不足的直接信号）；新任务上表先过容量占位评审。

## 复盘追问
- 为什么"把 23 个任务随手挪开几分钟"通常不管用？提示：没有资源画像的挪动只是随机化重叠，CPU 密集任务可能恰好又叠到一起；必须按时长×CPU 投影重排，且分槽要保证槽距大于典型时长。
- 调度机上"任务超时重试"为什么是雪崩放大器？提示：重试把失败任务的负载再压回已经饱和的窗口，与正常任务叠加推高峰值——所以容量红线留 30% 余量、重试要进错峰预算一起算。
