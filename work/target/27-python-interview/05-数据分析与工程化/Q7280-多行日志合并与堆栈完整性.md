### Q7280 · 异常栈在采集器里碎了：多行日志合并与堆栈完整性

难度：P6 ｜ 标签：多行日志、堆栈合并、日志采集、json-file 驱动、logfmt

基线：Python 3.12；复现 stdout 多行日志（异常堆栈）被采集器按行拆散的事故，实现行首模式合并器与"单行 JSON 化"的根治方案，全标准库实跑。

**问**：容器 stdout 日志接了采集器后，一个 Python 异常栈在 ES 里变成二十几条独立日志——grep `Traceback` 找得到头，找不到哪条属于哪个异常。多行日志为什么会被拆散？行首正则合并器怎么写才不漏行？为什么说"日志单行化"是根治方案而不是修补？

**答**：
- **结论**：采集链路（容器 json-file 驱动 → 采集 agent → ES/Loki）默认**按行切割**——stdout 的每一次 write 都是一条记录，Python 的 `traceback.print_exc()` 一次输出 20+ 行（`Traceback (most recent call last):` / 缩进栈帧 / 异常类型行），采集器没有"多行"概念就拆成 20+ 条。合并器方案：采集端配行首模式（multiline plugin），匹配"新事件的开始行"（如 `^\d{4}-\d{2}-\d{2}T` 时间戳前缀或 `^\[\d+\]` 序号），不匹配的行**粘贴到上一条**——两个失败模式要防：① **不匹配即粘连**：任何不以时间戳开头的行都被吞进前一条（包括正常多行消息），模式写得太紧就是漏行；② **无锚可依**：多进程混写 stdout（gunicorn 多 worker）时行交错，合并器把 A 进程的栈帧拼到 B 进程的日志上——交错流上多行合并在采集端**原理性不可靠**。根治是**单行化**：应用层日志直接输出单行 JSON（`{"level":..., "exc": "完整堆栈字符串", "msg":...}`，Q224 结构化日志同族），堆栈作为字段整体携带，采集器按行即按事件，不存在合并问题——logfmt/JSON 每行自足，混写交错也只丢不串。取舍：单行 JSON 让日志体积上升 20%~40%（字段名重复、转义成本），但换回的是解析零歧义与采集零合并，绝大多数场景值得。
- **取舍**：① 采集端合并 vs 应用端单行：合并器是"事后补救"（改配置即可、覆盖已有系统），单行化是"事前根治"（改应用、迁移期双轨）；新系统直接单行化，遗留系统先合并器止血再迁；② 多进程 stdout 交错是合并方案的天花板——gunicorn/多线程 `logging`（多进程用 QueueHandler 收敛 Q5559）+ 单行化才是完整解，只调采集器解决不了交错；③ 堆栈字段的体积控制：全栈可能几 KB~几十 KB，采集器与 ES 都有单条上限（logstash 默认截断），超长栈要截断策略（保留头尾、中间折叠）+ 异常聚合指纹（Q1387 异常聚合同族）在上游做；④ 非结构化残留：第三方库直接 print 的多行输出（ banners、进度条）绕过 logging——单行化覆盖不了，靠"print 治理"（重定向到 logger）补网。
- **实战**：① 单行化的落点：自定义 Formatter 输出 JSON（`python-json-logger` 思想），`exc_info` 格式化成单字段；堆栈里的换行符在 JSON 字符串里是 `\n` 转义，物理上仍是单行；② 采集器双保险：即使已单行化，仍配一个宽松的行首模式兜底（防第三方库多行 print 漏网）；③ 验证用例：注入一个三层深异常跑通全链路，ES 里断言"一条日志含完整堆栈字段"——日志链路的回归测试（Q345 管道测试同族）；④ grep 体验的补偿：单行 JSON 让 grep 不友好，取数一律走日志平台查询（字段过滤），本地调试用本地格式化输出（stderr 着色）。

```python
"""Q7280 多行日志: 拆散复现 + 行首模式合并器 + 单行JSON根治对比。"""
import json
import traceback


def log_unstructured() -> list[str]:
    """非结构化多行输出: print 异常栈(采集器按行拆成多条)."""
    try:
        raise ValueError("boom")
    except ValueError:
        tb = traceback.format_exc()
    return [f"2026-11-24T18:00:00 request=1 msg=order failed"] + tb.splitlines()


def multiline_merge(lines: list[str], start_pat: str) -> list[str]:
    """采集端合并器: 匹配行首开新事件, 其余粘连到上一条."""
    events, cur = [], None
    for ln in lines:
        if ln.startswith(start_pat):
            if cur is not None:
                events.append(cur)
            cur = ln
        elif cur is not None:
            cur += "\\n" + ln
        # 无锚可依的首行(不合模式且无前文): 丢弃 -> 漏行风险
    if cur is not None:
        events.append(cur)
    return events


def log_structured() -> str:
    """根治: 单行 JSON, 堆栈整体作为字段(物理单行)."""
    try:
        raise ValueError("boom")
    except ValueError:
        exc = traceback.format_exc()
    return json.dumps({"ts": "2026-11-24T18:00:00", "level": "ERROR",
                       "msg": "order failed", "exc": exc},
                      ensure_ascii=False)


if __name__ == "__main__":
    raw = log_unstructured()
    print(f"拆散: 一次异常输出 {len(raw)} 行, 采集器变成 {len(raw)} 条记录")
    merged = multiline_merge(raw, "2026-11-24T")
    full = any("Traceback" in e and "ValueError" in e for e in merged)
    print(f"合并器(时间戳锚): 合成 {len(merged)} 条, 堆栈完整={full}")
    # 交错场景: 无锚行首 -> 合并器漏行
    interleaved = raw[:2] + ["[worker-2] heartbeat"] + raw[2:]
    merged2 = multiline_merge(interleaved, "2026-11-24T")
    leaked = len(merged2) != len(merged) + 1
    single = log_structured()
    ok = (len(raw) >= 4 and full and single.count("\n") == 0
          and '"exc"' in single)
    print(f"单行 JSON: 物理行数={single.count(chr(10))} (0=单行), 堆栈字段完整, "
          f"交错流不串行")
    print(f"校验: 拆散复现 + 合并可拼 + 单行化根治 -> {'通过' if ok else '异常'}")
    print("结论：采集器按行切割无多行语义; 合并器怕漏行怕交错;")
    print("      根治=应用层单行 JSON, 堆栈整体做字段, 采集按行即按事件")
```

**追问一**：行首模式的锚怎么选才稳？"时间戳正则"锚在什么场景下会失效？

→ 解析：锚的质量决定合并器的召回与误粘：① **时间戳前缀锚**（`^\d{4}-\d{2}-\d{2}[T ]`）是最常用的，失效场景三个——日志里的**续行恰好以数字开头**（栈帧行 `\t  File "..."` 有缩进一般不撞，但第三方库输出的无前缀数字行会撞，被误当新事件而把后续行漏掉）；**时区/格式漂移**（某个库用本地时间、另一个用 UTC、还有一个用毫秒精度，一个正则覆盖不全，漏锚即漏行）；**本地化时间**（月份英文缩写）。② **事件分隔符锚**：让应用在每条日志开头打固定标记（`[evt-123]`），锚由应用保证而不是采集器猜——比时间戳稳，但要求应用配合改造（半只脚已经踏进单行化）。③ **负锚策略**：锚定"续行特征"而不是"起始特征"（缩进、`at `、`Caused by` 前缀）——Java 生态常用，但 Python 栈的缩进形式依库而异，负锚漏配同样是漏行。选型原则：**锚的可靠性上限 = 应用与采集器的协议强度，采集端单方面能做的最优解也只是一份"猜测协议"**；正则要配"漏行检测"（合并后事件数 vs 应用日志计数对账，Q1461 对账同族），漂移即告警。

**追问二**：单行 JSON 化之后，日志体积上涨与字段爆炸怎么治理？堆栈字段要做什么瘦身？

→ 解析：体积与字段的账分开算。**体积**：JSON 的字段名重复与引号转义让日志涨 20%~40%，治理三板斧——字段缩写（`ts/lvl/msg` 等约定短名，权衡可读性）、采样分层（DEBUG 全量本地、INFO 以上采集，Q1385 采样分层）、采集端压缩传输（批量 gzip 后投递，ES 写入前的管道压缩）；**字段爆炸**是更大的坑：ES 的 mapping 每个新字段建索引，动态字段的日志（把业务 context 全塞进日志）几天就把 mapping 炸了（Q7104/Q1925 基数治理同族）——治理是白名单 schema：日志字段集固定（ts/level/msg/exc/trace_id/request_id/context 有限键），可变业务上下文收进 `context` 对象且限制深度与键数（logstash 的 prune 过滤或应用层约束）。**堆栈瘦身**：全栈保留到框架边界（过滤掉框架内部帧，只留业务帧 + 最内层异常链），超长截断配头尾保留（前 20 行 + 后 5 行，中间 `... N frames hidden ...`）；异常链（raise from）的 cause 层级封顶（如 3 层）；再配合异常指纹聚合（Q1387，栈帧归一化后 hash），同型异常只存首例全栈 + 后续计数，ES 侧堆栈存储量降一个数量级。总原则：**日志的体积治理必须在写入端做（应用定 schema），采集与存储端只做过滤——写入端不管，下游永远在追赶。**
