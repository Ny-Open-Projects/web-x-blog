### Q7019 · 合成监控与冒烟巡检

> 难度:★★☆ | 标签:监控, 主动探测, SLO

**问**：指标监控全是绿的，用户却报「登录不了」——为什么被动监控会漏（哪些故障形态指标上看不出来），合成监控（Synthetic Monitoring）和冒烟巡检怎么补这个盲区？探测脚本怎么写才「像真实用户」且不误报？

**答**：被动监控的盲区：① **依赖级故障**：第三方支付/短信网关挂了，你自己的错误率指标正常（只是业务转化掉），只有真实走一遍才能发现；② **渲染/前端链路**：接口 200 但前端 bundle 加载失败，服务端指标全绿；③ **区域/链路级**：某地域 CDN 节点故障，聚合指标被平均掩盖。合成监控三层次：**可用性探测**（HTTP 拉健康端点，1 分钟级）、**关键旅程探测**（Playwright/requests 脚本走「登录→下单→支付回调」全链路，5-10 分钟级）、**区域探测**（多地域探针跑同一脚本）。防误报三设计：探测脚本对时间敏感的断言要宽松（只断「响应结构对」不断「内容对」）、失败重试（2 次失败才算真告警，单次抖动不算）、探测数据隔离（专用测试账号，幂等清理，避免污染生产数据）。

```python
# 全部标准库；demo 实现「关键旅程冒烟巡检器」（可脱离浏览器跑 API 级旅程）
import time, random, hashlib

class SmokeRunner:
    """冒烟巡检：多步旅程，任一步失败即 trip 失败，带重试与专用账号。"""
    def __init__(self, retries: int = 2):
        self.retries = retries
        self.results: list[dict] = []
    def run_trip(self, name: str, steps: list[tuple[str, object]]):
        for attempt in range(self.retries + 1):
            ok, detail = self._try(steps)
            self.results.append({"trip": name, "ok": ok, "detail": detail,
                                 "attempt": attempt, "ts": time.time()})
            if ok:
                return
            time.sleep(0.1)                    # 指数退避的简化版
    def _try(self, steps) -> tuple[bool, str]:
        for step_name, step_fn in steps:
            try:
                result = step_fn()
                if result is False:
                    return False, f"step 失败: {step_name}"
            except Exception as e:
                return False, f"step 异常: {step_name}: {e}"
        return True, "all steps ok"

# 旅程步骤：断「结构对」不断「内容对」（防误报的关键设计）
def step_login():
    return random.random() > 0.05              # 模拟 95% 成功的登录接口
def step_order():
    order_id = hashlib.md5(str(time.time()).encode()).hexdigest()[:8]
    return bool(order_id)                      # 断「返回了订单号」而非「特定值」
def step_callback():
    time.sleep(0.02)
    return True

if __name__ == "__main__":
    random.seed(2)
    runner = SmokeRunner(retries=1)
    runner.run_trip("下单主链路", [("login", step_login), ("order", step_order),
                                    ("callback", step_callback)])
    r = runner.results[-1]
    print(f"巡检结果: {r['trip']} ok={r['ok']} ({r['detail']}, 第 {r['attempt']} 次尝试)")
    # 探测纪律：① 专用测试账号 + 幂等清理（订单打 test 标记回收）
    #           ② 告警阈值：连续 2 次失败才告警（重试已含）
    #           ③ 5-10 分钟周期，覆盖「登录/下单/支付回调/搜索」四条核心旅程
    #           ④ 多地域探针跑同一脚本，区分「服务挂了」vs「某区域网络挂了」
```

**追问**：1) 合成监控和真实用户监控（RUM）的关系？——合成管「链路可用性」（主动、提前、可控），RUM 管「真实体验分布」（被动、真实样本、覆盖盲区设备/网络）；合成先报警，RUM 验证影响面——两者互补不可互替。2) 探测脚本的「数据污染」怎么治理？——测试账号 + 环境标记（订单打 synthetic 标签）+ 幂等清理任务 + 下游风控白名单；漏做会在 BI 报表里看到「幽灵订单」。3) 探测间隔的成本权衡？——过密=下游被探测流量干扰（QPS 影响真实用户），过疏=MTTR 变长；按业务容忍度倒推（支付旅程 5 分钟级、官网 1 分钟级）。

## 背诵要点
1. 被动监控盲区：依赖故障/前端链路/区域问题——指标绿≠用户可用。
2. 三层次探测：HTTP 可用性（1min）→ 关键旅程（5-10min）→ 多地域探针；告警要连续 2 次失败。
3. 防误报：断结构不断内容、重试后告警、专用账号 + 幂等清理防数据污染。

## 复盘追问
1. 合成监控脚本自己坏了（误报风暴），怎么自保？（提示：脚本版本化 + 探测器自身心跳监控（监控的监控）+ 变更走发布流程）
2. 用户报障但四个探针全绿，下一步查什么？（提示：RUM 找该用户 trace（版本/设备/地域维度），定位探针覆盖不到的盲区（特定机型 JS 兼容/特定运营商网络））
