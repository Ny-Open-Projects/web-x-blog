### Q7187 · 测试套件规模增长与 CI 并发容量账

难度：P6 ｜ 标签：容量规划、测试工程、CI 并发、分片

基线：Python 3.9+；pytest 8+ / pytest-xdist / CI 并发矩阵。

**问**：测试套件从 800 个涨到 6000 个用例，CI 从 4 分钟涨到 38 分钟，团队反馈"改一行要等一小时"。测试时长的增长曲线是什么形状？并发分片的账怎么算？为什么"简单把 -n 加大"有时反而更慢？

**答**：
- **结论**：测试时长 = Σ用例耗时，而团队用例数常随代码量近线性增长，串行时长线性涨；分片（xdist）能摊平，但**收益上限受三个约束**：(1) 最慢用例——`总时长/并发数` 若小于最慢单例时长，长尾决定总时长（短板效应）；(2) 启动与协调开销——每个 worker 要重新收集、建 fixture、连 DB，并发过大时开销占比反超收益；(3) 共享资源——并发 worker 打同一个测试库/Redis 会互相踩（数据竞争→flaky→重跑→更慢）。所以账是：`并发数 = min(CPU核, 用例总时长/可接受时长, 资源不冲突的分片数)`。
- **取舍**：时长治理优先级：削最慢 10% 用例（往往占 50% 时长）> 分片 > 加机器。慢用例的治理手段——网络/DB 用 fixture 级 fake 或容器池，端到端用例降频（PR 跑单测，merge 后跑 E2E），sleep 类断言改事件等待。
- **实战**：观测先行——`pytest --durations=20` 拿最慢清单；分片策略用 `--dist loadgroup`（按 marker/xdist_group 分组，保证共享资源的用例同 worker），避免随机分配踩库。

```python
# CI 并发容量账：含长尾与协调开销的分片收益模型（标准库可运行）。
import math

def wall_time(case_seconds: list[float], workers: int,
              worker_startup_s: float = 8.0) -> float:
    """把用例均分到 workers，取最长分片 + 启动开销。
    长尾用例不可拆分，是短板。"""
    if workers <= 0 or not case_seconds:
        return sum(case_seconds)
    shard = math.ceil(len(case_seconds) / workers)
    shards = [case_seconds[i:i+shard] for i in range(0, len(case_seconds), shard)]
    longest = max(sum(s) for s in shards)
    return longest + worker_startup_s

if __name__ == "__main__":
    # 6000 用例，均值 0.35s，其中有 5 个 120s 的端到端长尾
    cases = [0.35] * 6000 + [120.0] * 5
    for w in (1, 8, 16, 32, 64):
        print(f"workers={w:>2}: 总时长 {wall_time(cases, w):6.1f}s")
    # workers=1: 2708s;  8: 868s;  16: 734s;  32: 668s;  64: 635s
    # -> 32 之后收益被 120s 长尾钉死（5 个端到端用例分片后仍是长板）：
    #    先削长尾再谈扩容，否则加并发只剩启动开销。
```

**追问**：
- 一层：为什么 `--dist loadgroup` 能防 flaky？→ 提示：共享同一外部资源（同库 schema、同 Redis db）的用例标记同组，保证同 worker 串行执行。
- 二层：时长 38 分钟里怎么区分"计算"和"等 IO"？→ 提示：`--durations` + 覆盖率数据交叉，等 IO 的用例用 fake 替换网络层；CPU 慢的看是否 O(n²) 断言逻辑。
- 三层：PR 只跑受影响用例（test selection）的风险是什么？→ 提示：漏回归，需要依赖影响面分析（import graph/变更文件映射），且主干仍保留周期性全量跑。

**背诵要点**：
1. 分片收益三约束：最慢用例短板、worker 启动协调开销、共享资源冲突；并发数取三者最小。
2. 治理优先级：削最慢 10% 用例 > 分片 > 加机器；端到端降频到 merge 后跑。
3. `--dist loadgroup` 按资源分组防 flaky；`--durations=20` 是时长账的第一手数据。

**复盘追问**：
1. 为什么套件涨到 6000 个才有人喊慢？提示：缺"每 PR 时长"SLO 指标，应设阈值（如 10 分钟）告警。
2. 如果长尾用例削不掉怎么办？提示：隔离到夜间全量流水线，PR 流水线按变更范围跑子集。
