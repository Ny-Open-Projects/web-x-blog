### Q7085 · 数仓按扫描量计费的分区裁剪成本账

难度：P6/P7 ｜ 标签：数仓 / 成本工程 / BigQuery/Snowflake

**问**：团队用 BigQuery/Snowflake 这类按扫描量计费的数仓，月账单环比涨了 3 倍。这类"按字节计费"的成本模型下，Python 侧该怎么治理？

**答**：
- **结论**：按扫描量计费意味着成本 = 扫描字节数 × 单价，而扫描字节数由查询读的列与分区决定，与结果行数无关。最典型的浪费：`SELECT *`（读全部列）、不带分区过滤（扫全历史）、每次全表 distinct。治理抓手按收益排序：① 列投影（Parquet 列存下只读需要的列，常省 50-90%）；② 分区/聚簇键过滤（时间条件能裁掉 99% 数据）；③ 中间结果物化成小表复用；④ `dry run` 预估字节作为上线门禁。
- **取舍**：成本与时效的取舍： BI 报表用 `BI Engine`/结果缓存几乎免费但要钱；物化视图预计算用存储换扫描，高频查询划算、低频查询反而多付存储费。Python 侧框架层的取舍：让所有查询走统一查询层（一个内部 SQL 封装），才能集中挂 dry-run 门禁与账单标签（按团队/项目分账），放任工程师直连则治理无从谈起。
- **实战**：落地三件：① 查询层强制 dry-run（BigQuery `dry_run=True` 返回 totalBytesProcessed，超阈值拒绝并提示改写）；② 所有查询带成本标签（团队/用途），月度按标签出成本榜；③ 给高频大查询建物化视图/汇总表，用"查询频次 × 单次字节"排序治理 top 10。注意 dry-run 的字节估算对 UDF/脚本不完全准确，阈值要留余量。

```python
# 查询层 dry-run 成本门禁（纯标准库模拟）
# 基线：Python 3.9+

import re

PRICE_PER_TB = 6.25  # BigQuery 按需价 $/TB（2025 基线，示例）
TB = 2**40


def estimate_bytes(table_bytes: int, column_ratio: float, partition_prune: float) -> int:
    """列存投影 × 分区裁剪后的扫描量"""
    return int(table_bytes * column_ratio * partition_prune)


def dry_run_gate(sql: str, est_bytes: int, limit_bytes: int) -> tuple[bool, str]:
    has_time_filter = bool(re.search(r"WHERE\s+.*(?:dt|date|created_at)\s*>=", sql, re.I))
    if not has_time_filter:
        return False, "缺少分区键过滤，拒绝执行"
    if est_bytes > limit_bytes:
        return False, f"扫描 {est_bytes/TB:.2f}TB 超限额 {limit_bytes/TB:.2f}TB"
    return True, f"pass cost=${est_bytes/TB*PRICE_PER_TB:.4f}"


def main() -> None:
    table = 50 * 2**40  # 50TB 表
    bad_sql = "SELECT * FROM events WHERE country='US'"
    est = estimate_bytes(table, column_ratio=0.9, partition_prune=1.0)
    print(dry_run_gate(bad_sql, est, 2 * TB)[1])

    good_sql = "SELECT user_id, cnt FROM events WHERE dt >= '2026-11-19'"
    est2 = estimate_bytes(table, column_ratio=0.01, partition_prune=1/1095)
    print(dry_run_gate(good_sql, est2, 2 * TB)[1])
    assert est2 < 2 * TB < est


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"结果缓存"能让查询免费，什么条件下失效？
→ 一句话提示：BigQuery 对相同 SQL 且引用表未变化的查询走缓存不收费，但源表任何写入都会失效——高频查询打在持续更新的表上时缓存命中率趋近 0，治理要配合物化视图。

**追问 2**：按需计费和槽位（capacity）计费怎么选？
→ 一句话提示：查询少而重的团队按需便宜且简单；查询并发量大且稳定的团队槽位固定成本更优，可用 slot 使用率曲线判断临界点。

## 背诵要点
- 按扫描量计费：成本=扫描字节×单价，`SELECT *` 与无分区过滤是两大浪费源。
- 治理抓手排序：列投影 > 分区裁剪 > 物化复用 > dry-run 门禁 > 成本标签分账。
- 所有查询走统一查询层挂 dry-run（totalBytesProcessed）与标签，散连无法治理。

## 复盘追问
- 为什么 dry-run 的字节估算可能偏差？提示：UDF/脚本任务按引用表全量估算，且不含缓存命中，阈值要留安全余量。
- 治理后如何避免工程师绕过查询层直连？提示：最小权限只授予查询层服务账号，个人账号不给表级读权限。
