### Q7073 · CI 坏缓存投毒事故复盘

难度：P6 ｜ 标签：CI / 缓存 / 事故复盘 / pytest

**问**：某天起 CI 上 30% 的 job 随机失败，重跑偶尔能过，本地永远过不了。排查半天发现是 pip/pytest 缓存的问题。复盘：CI 缓存怎么会"坏"？怎么设计缓存键与自愈机制？

**答**：

**结论**：CI 缓存的"坏"有三种典型成因：① 键不完整——缓存键只用 lockfile hash，不含 Python 版本/平台/架构，跑 3.12 和 3.13 的 job 命中同一份 wheel 缓存，装错二进制包后 import 失败；② 内容陈旧——依赖锁更新了但缓存写入失败（并发 job 竞争），恢复了旧快照；③ 状态污染——pytest 缓存目录（.pytest_cache）里的 last-failed 记录把上次失败的用例选择带到了新 run。共同根因是：缓存把"不可复现的状态"变成了"稳定的错误"。

**取舍**：缓存粒度与命中率的权衡——键越精确（含版本/平台/lock hash）命中率越低但越安全；键越粗命中率高但投毒面大。生产级做法是"精确键 + 分层缓存"：精确键保证正确性，另外挂一个 fallback 键（同 lock 不同平台）加 `cache-hit != exact` 时强制 revalidate（对比 lock hash）。自愈机制必须自动化：失败 job 重跑一次带 `--no-cache`，如果过了就在 PR 上自动留言"缓存投毒嫌疑"并触发缓存清空。

**实战**：缓存键公式：`{runner_os}-{py_version}-{lockfile_hash}-{workflow_id}`；pytest 加 `--cache-clear` 到定时任务而非每次（牺牲一点速度保稳定）；venv 不进缓存只缓存 wheel 目录（pip cache），下载快但安装重放可复现。监控上把"缓存命中率"与"失败率按缓存命中分组"放进 CI 仪表盘——失败率在命中缓存的 job 上系统性偏高就是投毒信号。

```python
# CI 缓存键设计 + 投毒自愈决策模拟（仅标准库，Python 3.9+）
from __future__ import annotations

import hashlib


def cache_key(os_name: str, py: str, lock_hash: str, workflow: str) -> str:
    raw = f"{os_name}-{py}-{lock_hash}-{workflow}"
    return hashlib.sha1(raw.encode()).hexdigest()[:12]


def install_decision(exact_hit: bool, fallback_hit: bool,
                     lock_hash_on_disk: str, lock_hash_now: str) -> str:
    """根据命中层级决定是否信任缓存。"""
    if exact_hit and lock_hash_on_disk == lock_hash_now:
        return "trust"          # 精确命中且 lock 校验一致
    if fallback_hit and lock_hash_on_disk == lock_hash_now:
        return "revalidate"     # 近似命中：重装但用 wheel 缓存
    return "cold"               # 全量重装


def main() -> None:
    lock_hash = hashlib.sha1(open(__file__, "rb").read()).hexdigest()[:12]
    k1 = cache_key("ubuntu", "3.12", lock_hash, "test.yml")
    k2 = cache_key("ubuntu", "3.13", lock_hash, "test.yml")
    assert k1 != k2, "不同 Python 版本必须不同键（防装错 wheel）"

    cases = [
        (True, False, lock_hash, lock_hash),   # 精确命中
        (False, True, lock_hash, lock_hash),   # fallback 命中 → revalidate
        (False, False, lock_hash, lock_hash),  # 冷启动
        (True, False, "OLD", lock_hash),       # 键命中但 lock 变了 → 不信任
    ]
    got = [install_decision(*c) for c in cases]
    print(dict(zip(["exact", "fallback", "cold", "stale"], got)))
    assert got == ["trust", "revalidate", "cold", "cold"]

    # 自愈：失败 job 带 --no-cache 重跑 → 过了 → 判投毒并清缓存
    retried_pass_with_no_cache = True
    if retried_pass_with_no_cache:
        print("自愈判定：缓存投毒，清空缓存 + 通知 PR")
    assert retried_pass_with_no_cache


if __name__ == "__main__":
    main()
```

**追问链**：

- 追问 1：为什么"缓存 wheel 目录而不缓存 venv"更安全？——venv 里散落着按构建机器路径编译的 entry-point shebang、`.pth`、绝对路径链接，跨 runner 恢复后行为不确定；wheel 是标准化产物，重装路径确定，只有"下载"被加速，"安装"始终现场重放。
- 追问 1.1：pytest 的 .pytest_cache 会造成哪些隐性失败？——`lastfailed` 让 `--lf` 只跑失败子集（覆盖率口径漂移）、`nodeids` 缓存过期导致收集错误；还会把平台相关的临时路径写进缓存。所以共享 runner 上要么 `--cache-clear` 要么把该目录排除出缓存。
- 追问 2：如果投毒源不是缓存而是被污染的第三方 wheel（供应链），同一套自愈能发现吗？——发现不了：`--no-cache` 重跑从 PyPI 拉的还是坏包。这需要另一层防线（hash 校验 pip `--require-hashes` + SBOM 比对），缓存自愈只针对"本地状态错"不针对"源头错"。

**背诵要点**：

1. 缓存键四要素：OS + Python 版本 + lockfile hash + workflow；键不全是投毒主因（跨版本装错 wheel）。
2. 缓存 wheel 不缓存 venv：安装现场重放、只有下载被加速；pytest 缓存目录定时 --cache-clear。
3. 自愈闭环：失败重跑带 --no-cache，过了即判投毒、清缓存、留痕；但供应链类污染需要 --require-hashes 另防。

**复盘追问**：

1. 如果 CI 失败率与缓存命中的相关性数据没留存，你怎么事后验证"缓存是主因"这个结论？
2. 缓存精确键化后 job 时长增加 40%，你如何向团队论证这 40% 买的是什么？
