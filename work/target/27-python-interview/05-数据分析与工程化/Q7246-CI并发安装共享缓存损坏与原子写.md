### Q7246 · CI 并发 job 共享 pip 缓存：损坏的 wheel 与原子写入修复

难度：P6 ｜ 标签：CI、并发安装、共享缓存竞态、原子写入、pip

基线：Python 3.12；threading 模拟两个并发安装线程写同一缓存条目，对比"直接写"与"临时文件 + os.replace"两种写法。

**问**：CI 里多个 job 并行跑，共享同一个 pip 缓存目录（或内网 devpi 镜像的落盘缓存）。偶发安装失败，报 `ZIP file is corrupt` 或 hash 校验不过，重跑就成功，一天遇到一两次没法稳定复现。共享缓存为什么会损坏？怎么让并发安装安全地共享缓存？

**答**：
- **结论**：损坏的根因是**非原子的"写-读"竞态**：安装方 A 还在往缓存文件里写 wheel（没写完），并发方 B 已经按文件名找到了它并开始读取/校验，读到半截文件自然报 corrupt。缓存系统通常按"最终文件名"判定命中，不保证文件已完整。修法是**原子发布**：先写到唯一的临时名（带 PID/随机后缀），写完 `os.replace` 到最终名——`rename` 在同一文件系统上是原子的，读方要么看到旧的不存在、要么看到完整的新文件，绝不会读到半截。多个写方同时写同一版本时，各自写各自临时文件，replace 先后无害（内容相同）。
- **取舍**：① 每个并发 job 用**独立缓存目录**（`PIP_CACHE_DIR=$(mktemp -d)`）最省心，代价是缓存命中率降为每 job 一次；② 共享缓存 + 原子写是命中率与安全的平衡，但要保证写方工具支持原子落盘（pip 自身实现正确，自建镜像/缓存层要自己实现）；③ 临时文件写失败要清理，否则垃圾越攒越多（Q7147 磁盘写满）；④ 损坏已被写入的缓存条目要能被"按 hash 校验失败即驱逐"机制自动清掉。
- **实战**：① 偶发 corrupt 的自查顺序：先确认是不是共享缓存（复跑失败 job 用干净缓存成功即坐实）；② 自建缓存/镜像层必须实现"临时名 + rename"与"校验和失败驱逐"；③ CI 里对安装步骤加 `--require-hashes` 可把损坏文件变成显式报错而不是静默装上坏包；④ 缓存目录挂盘注意文件系统——NFS 上的 `rename` 原子性不保证，跨机共享缓存要慎用 rename 语义。

```python
"""并发安装共享缓存：直接写 vs 原子 replace 的竞态对比。"""
import hashlib
import os
import threading
import tempfile
import zipfile

PAYLOAD = b"wheel-content-" + os.urandom(64)


def corruptable_write(cache_dir: str, name: str, content: bytes) -> None:
    """反例：直接写最终名，读方可能读到半截。"""
    path = os.path.join(cache_dir, name)
    for i in range(0, len(content), 64):
        with open(path, "ab") as f:
            f.write(content[i:i + 64])


def atomic_write(cache_dir: str, name: str, content: bytes) -> None:
    """正解：唯一临时名 + os.replace 原子发布。"""
    tmp = os.path.join(cache_dir, f".tmp-{threading.get_ident()}-{name}")
    with open(tmp, "wb") as f:
        f.write(content)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp, os.path.join(cache_dir, name))


def reader(cache_dir: str, name: str, results: list[str]) -> None:
    for _ in range(200):
        path = os.path.join(cache_dir, name)
        if os.path.exists(path):
            with open(path, "rb") as f:
                data = f.read()
            if hashlib.sha256(data).hexdigest() == hashlib.sha256(PAYLOAD).hexdigest():
                results.append("ok")
            else:
                results.append("corrupt")
        else:
            results.append("miss")


if __name__ == "__main__":
    for writer, label in ((corruptable_write, "直接写最终名"),
                          (atomic_write, "临时名+os.replace")):
        with tempfile.TemporaryDirectory() as d:
            results: list[str] = []
            t = threading.Thread(target=reader, args=(d, "pkg-1.0.whl", results))
            t.start()
            writer(d, "pkg-1.0.whl", PAYLOAD)
            t.join()
            from collections import Counter
            print(f"{label:<16} 读方 200 次探测: {dict(Counter(results))}")
    print("结论：共享缓存的安全性取决于写方是否原子发布；rename 是同一文件系统上的原子操作")
    print("      兜底层：--require-hashes 让坏文件显式报错 + 按 hash 失败驱逐坏条目")
```

**追问一**：pip 自己已经写得很安全了，为什么还会出事？

→ 解析：pip 对**自己的缓存**（wheel cache）实现是原子且带校验的；出事的地方通常是三类自建环节：① 内网镜像/代理（devpi、nexus）的落盘缓存层自研了下载缓存，没做原子发布；② CI 把缓存目录持久化后多 job 并发挂载同一目录（NFS/云盘），rename 语义或锁行为不可靠；③ 构建脚本自己往缓存目录拷文件。所以排查方向不是怀疑 pip，而是沿着"谁写了这个缓存条目"找自研写入方。

**追问二**：为什么 hash 校验失败不应该自动重试安装就完事？

→ 解析：重试装上坏包有两种更危险的形态：一是损坏是**确定性的**（缓存条目本身坏了，重试读到的还是它），重试永远失败或偶尔成功一次下次又坏，问题被掩盖；二是坏包能通过安装但运行时崩溃，把问题从"安装期显式报错"推迟到"运行期隐性故障"，排查成本翻倍。正确姿势是：hash 失败 → 驱逐该缓存条目并告警 → 用干净缓存重装；同时统计驱逐频率，缓存层写方有 bug 时频率会持续非零，是比单次报错更有价值的信号。
