### Q7165 · 小文件问题：存储、元数据与计算的三重成本账

难度：P6/P7 ｜ 标签：成本工程、数据湖、对象存储

**问**：每小时一个分区、每分区几十个几百 KB 的 Parquet 文件，一年下来几万个文件。查询越来越慢、对象存储账单越来越怪。小文件问题的成本账怎么算？合并的时机与代价是什么？

**答**：**结论**：小文件的代价不是"文件多"本身，而是三重账：① **存储账**——对象存储按对象计费 + 每对象最小尺寸计费（如 S3 最小 128KB 计费单位），1KB 文件按 128KB 收钱；② **元数据账**——Hive Metastore/清单文件/`ls` 列表操作随文件数线性恶化，`list` 是按请求收费且限速的；③ **计算账**——每个文件一次 open/decode/调度任务，查询的固定开销 = 文件数 × 单文件开销，Spark/duckdb 读 1 万个 100KB 文件比读 10 个 100MB 文件慢几十倍且调度器先崩。

**取舍**：合并（compaction）的代价是"写一次全量 + 合并窗口内的读写一致性"，所以不是越频繁越好。经验分界：单文件 < 128MB 且单分区文件数 > 50 触发合并；写入频率高的实时链路用"写时缓冲 + 定时物化"，离线链路直接分区级合并。合并的隐性收益还包括压缩率提升（列块更大、编码效率更高）。

**实战**：给数据湖加"文件数巡检"指标：每分区文件数、平均文件大小、`list` 延迟三项入看板；合并任务本身按分区增量跑、留 dry-run 预览（合并前后文件数与字节数），避免合并任务自己变成大文件生产者。

```python
# 小文件成本账：计费、元数据与计算三重模型
import statistics

def small_file_audit(objects: list[int]) -> dict:
    """objects: 每个文件的字节数"""
    n = len(objects)
    billed = sum(max(sz, 128 * 1024) for sz in objects)   # 最小计费尺寸
    total = sum(objects)
    overpay = billed - total
    # 计算账：每个文件的固定 open+schedule 开销（毫秒级，这里取 15ms）
    fixed_scan = n * 15 / 1000
    return {
        "files": n,
        "avg_kb": round(statistics.mean(objects) / 1024, 1),
        "billing_overpay_mb": round(overpay / 1024**2, 2),
        "scan_fixed_overhead_s": round(fixed_scan, 1),
    }

# 每小时任务每次吐 40 个 200KB 小文件，一天 24 次
hourly = [200 * 1024] * 40
day = hourly * 24
print("单小时分区:", small_file_audit(hourly))
print("一天的数据:", small_file_audit(day))
# 960 个 200KB 文件：计费超额 + 固定扫描开销 14.4 秒

# 合并决策：按"分区文件数 > 50 且均大小 < 128MB"触发
def needs_compaction(files_per_partition: int, avg_bytes: int) -> bool:
    return files_per_partition > 50 and avg_bytes < 128 * 1024**2

print("是否触发合并:", needs_compaction(40, 200 * 1024))

# 合并收益估算：合并成 10 个大文件后的计算开销
merged = [day_size := sum(day) // 10] * 10
print("合并后一天:", small_file_audit(merged))
# 文件数 960 -> 10，扫描固定开销 14.4s -> 0.15s，计费超额归零
```

**追问 1**：为什么压缩率也会随合并提升？
提示：列式编码（字典/RLE）以列块为单位，块太小字典编码撑不起来、页头占比高；合并后单文件内连续大块，压缩率通常提升 10-30%。

**追问 2**：实时链路"写时缓冲"的缓冲区放哪？丢了怎么办？
提示：本地盘/内存缓冲意味着进程挂了丢数据，必须配 checkpoint 或写入 WAL（或直接写小文件 + 异步合并），这是"少小文件"与"可靠性"的取舍。

**追问 3**：合并任务和查询任务抢同一个分区会出什么问题？
提示：读方可能读到合并中半新半旧的文件清单——需要清单原子替换（manifest swap）或临时分区+rename，这正是 iceberg/delta 这类表格式解决的核心问题。

## 背诵要点
1. 小文件三重账：存储计费超额（最小计费尺寸）、元数据 list 恶化、计算端每文件固定开销 × 文件数。
2. 合并触发线：单文件 < 128MB 且分区文件数 > 50；合并收益含压缩率提升。
3. 合并要防"半新半旧"读到：清单原子替换或临时分区，表格式（iceberg/delta）为此而生。
