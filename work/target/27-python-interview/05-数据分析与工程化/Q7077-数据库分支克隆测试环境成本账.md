### Q7077 · 测试环境数据库分支克隆的成本账

难度：P6 ｜ 标签：成本工程 / 测试环境 / 数据库克隆 / CI

**问**：团队想给每个 PR 一个独立测试数据库（类似 Neon 分支 / PG template clone），替代共享测试库。听起来美好，但存储与计算成本怎么算才不会翻车？

**答**：

**结论**：分支克隆的成本模型是"母本 1 份 + 增量写放大"：COW（copy-on-write）分支初始近乎免费，但每个分支的写入会不断分配新页，长生命周期分支的存储趋近于完整副本。真正的账不是"克隆快"，而是三笔：① 存储账：分支数 × 平均生命周期 × 日写入增量，50 个活跃 PR × 7 天 × 日 200 MB = 70 GB 级，可控；但忘了回收的僵尸分支（PR 关了没删）几个月就是 TB 级。② 计算账：每分支一个 PG 实例还是共享实例多 schema？独立实例贵 10 倍但隔离彻底。③ 数据准备账：克隆只复制结构+种子数据的话，测试用例要的是"有代表性数据"，回填成本可能比克隆本身高。

**取舍**：三种隔离级别的成本阶梯——① 共享库 + schema 隔离：最便宜，但测试互相污染、迁移冲突；② COW 分支库：存储便宜、隔离好，适合 90% 团队，注意生命周期回收；③ 独立实例 + 真实数据子集：最强隔离与真实性，但每分支一个实例的闲置成本高。决策变量是 PR 并发数与数据敏感度：并发 >30 且含敏感数据 → ②；金融强合规 → ③ 但用脱敏子集。

**实战**：成本控制三件套：① 生命周期绑定 CI（PR close/merge 自动删分支，TTL 7 天兜底清扫）；② 母本数据分"结构 + 热种子表"两层，冷表只建结构；③ 存储监控按分支打标，超过母本 20% 的分支告警（说明写放大异常，通常是测试跑了真批量任务）。Python 侧把账做成模拟器：输入 PR 并发曲线与生命周期分布，输出月存储/计算成本，对比方案阶梯。

```python
# 分支克隆测试库成本模拟器（仅标准库，Python 3.9+）
from __future__ import annotations

import random


def monthly_cost(active_prs: int, avg_life_days: float, daily_write_gb: float,
                 master_gb: float, storage_per_gb: float = 0.10,
                 instance_per_branch_month: float = 0.0) -> dict:
    # 存储近似：每分支平均存活期为母本快照 + 生命周期一半的增量
    branches = active_prs * (avg_life_days / 30)  # 并发存活的平均分支数
    branch_gb = master_gb * 0.05 + daily_write_gb * avg_life_days / 2
    storage = (master_gb + branches * branch_gb) * storage_per_gb
    compute = branches * instance_per_branch_month
    return {"live_branches": round(branches, 1),
            "storage_cost": round(storage, 1),
            "compute_cost": round(compute, 1),
            "total": round(storage + compute, 1)}


def main() -> None:
    # 方案 ②：COW 分支共享实例（计算不按分支计费）
    cow = monthly_cost(active_prs=50, avg_life_days=7, daily_write_gb=0.2,
                       master_gb=400, instance_per_branch_month=0)
    print("COW 共享实例:", cow)
    assert cow["total"] < 80  # 存储为主，计算不按分支计费

    # 方案 ③：每分支独立小实例（隔离强但计算贵）
    inst = monthly_cost(active_prs=50, avg_life_days=7, daily_write_gb=0.2,
                        master_gb=400, instance_per_branch_month=18)
    print("独立实例:", inst)
    assert inst["compute_cost"] > cow["total"] * 3, "独立实例计算成本应显著更高"

    # 僵尸分支失控：30% PR 忘删，存活 90 天
    zomb = monthly_cost(active_prs=50 * 0.3, avg_life_days=90,
                        daily_write_gb=0.2, master_gb=400)
    print("僵尸分支:", zomb)
    assert zomb["total"] > cow["total"] * 2.5, "僵尸分支成本应失控"
    print("结论：COW 共享实例 + 生命周期自动回收是默认解")


if __name__ == "__main__":
    main()
```

**追问链**：

- 追问 1：为什么"克隆里有代表性数据"常常比克隆本身难？——COW 克隆复制的是母本的当前状态，但测试需要的往往是特定组合：订单状态机跑到一半的数据、跨天的时间序列；回填这些要写数据构造器或从生产脱敏子集导入，工程量稳定大于克隆配置本身。预算里"数据准备"应单列。
- 追问 1.1：从生产导脱敏子集的合规风险点？——子集必须按"不可重识别"标准脱敏（k-匿名或确定性假名化 + 断链接），导出通道要走审批；最容易被审计揪出的是"唯一索引列没假名化导致用户可被关联"。
- 追问 2：分支写放大超过母本 20% 告警的阈值怎么定？——正常测试写入应是种子级（几十 MB）；超阈值基本是测试跑了批量任务或分页拉全表。阈值太低误报（合法的 ETL 测试）、太高漏掉失控，20% 是初值，按第一个月的分布校准到 P95。

**背诵要点**：

1. 分支克隆成本 = 存储（母本 + 增量写放大）+ 计算（按分支计费的独立实例贵一个量级）+ 数据准备三笔账。
2. 僵尸分支是存储失控主因：生命周期绑 CI（merge/close 即删）+ TTL 兜底清扫。
3. 决策阶梯：共享 schema 最便宜、COW 分支是默认解、独立实例仅强合规场景；写放大 >母本 20% 告警抓失控测试。

**复盘追问**：

1. 如果 PR 合并后分支没删，团队又没有 TTL 清扫，三个月后存储账单涨 5 倍，治理从哪里入手？
2. 测试用例依赖生产数据形状（分布），但合规不允许整库导出——你怎么设计"最小够用"的种子集？
