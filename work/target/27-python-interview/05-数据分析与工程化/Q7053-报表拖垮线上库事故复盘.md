### Q7053 · 报表拖垮线上库的事故复盘与资源隔离

难度：P6 | 标签：事故复盘、资源隔离、读写分离、连接池

**问**：周一下午全站下单接口突然超时，排查发现一个运营报表正在跑大聚合。一个"只读的报表查询"是怎么把 OLTP 主库拖垮的？事后加固为什么必须做"资源隔离"而不是"优化那条 SQL"？

**答**：
- **结论**：报表的杀伤路径是连接槽位：大聚合占住连接几十秒，OLTP 的连接池槽位被共享池慢慢抽干，正常请求等不到连接表现为接口超时——慢的不是 SQL 本身，是它把共享资源（连接、CPU、IO）和交易流量绑在了一起。加固的核心是隔离爆炸半径：报表走只读副本 + 独立小连接池 + 独立账号（只读、单查询超时 30s），主库连接池只留给 OLTP。只"优化那条 SQL"只是把这次拖垮变成下次更大数据量下的拖垮。
- **取舍**：只读副本要钱、数据有秒级延迟——报表能容忍延迟（大盘数字晚几秒无感），交易不能容忍抖动，这笔账很划算。反方向是"所有查询都上副本"：读己之写场景（下单后立刻查订单）会被复制延迟坑，所以隔离要配白名单治理，不是一刀切。
- **实战**：隔离清单：① 连接池分池（OLTP 独占额度，报表池单独 max、单独超时）；② 账号分权（报表账号 READ 权限 + 语句超时）；③ 上线守门（报表 SQL 估算扫描量超阈值走汇总层）；④ 巡检监控（主库连接池占用来源打标签，报表连接占比告警）。

```python
"""报表拖垮线上库的复盘与资源隔离：共享连接池 vs 池隔离的 OLTP 延迟对比。"""
import threading
import time
from concurrent.futures import ThreadPoolExecutor

class Pool:
    """信号量连接池：统计每个请求的等待时长。"""

    def __init__(self, size: int, name: str):
        self.sem = threading.BoundedSemaphore(size)
        self.name = name
        self.waits: list[float] = []

    def run(self, dur: float) -> float:
        t0 = time.perf_counter()
        self.sem.acquire()
        waited = time.perf_counter() - t0
        self.waits.append(waited)
        time.sleep(dur)                  # 占用连接的"查询执行"
        self.sem.release()
        return waited

def p99(xs: list[float]) -> float:
    xs = sorted(xs)
    return xs[max(0, int(len(xs) * 0.99) - 1)]

REPORTS, OLTP = 8, 24

def run_scenario(shared: bool):
    oltp_pool = Pool(10, "oltp")
    report_pool = oltp_pool if shared else Pool(2, "report")  # 隔离：报表走只读副本小池
    jobs = []
    with ThreadPoolExecutor(max_workers=REPORTS + OLTP) as ex:
        for _ in range(REPORTS):
            jobs.append((ex.submit(report_pool.run, 0.20), True))
        for _ in range(OLTP):
            jobs.append((ex.submit(oltp_pool.run, 0.01), False))
        oltp_waits = [f.result() for f, is_report in jobs if not is_report]
    return p99(oltp_waits)

# 等价场景：8 个慢报表（各占连接 0.2s）+ 24 个快请求（0.01s）
w_shared = run_scenario(shared=True)
w_isolated = run_scenario(shared=False)
print(f"共享池（10 连接混用）：OLTP P99 等待 {w_shared * 1000:.0f} ms——"
      f"被报表排队拖高 {w_shared / w_isolated:.0f} 倍")
print(f"池隔离（OLTP 独占 10 连接 + 报表副本 2 连接）：OLTP P99 等待 {w_isolated * 1000:.0f} ms")
print("配套：报表账号只读 + 单查询超时 30s + 汇总层；"
      "隔离的意义是把'慢'限制在报表池里，不再占用 OLTP 的连接槽位")
```

**追问链**：
1. 追问一层：为什么"报表查询是只读的"也能拖垮主库？——只读不产生锁冲突，但聚合要吃 CPU、IO 和 buffer pool，还会挤占连接槽位；SELECT 的大扫描把热数据挤出缓存，OLTP 点查从内存访问退化为磁盘读，延迟全面上涨。
2. 追问二层：报表池的超时为什么必须比 OLTP 严？——报表超时 30s 快速失败只损失一张报表，可以重跑；OLTP 请求没有"重跑"概念（用户在等）。资源隔离的原则是"谁可重跑谁先被牺牲"，这是池隔离 + 分级超时的共同逻辑。

**背诵要点**：
1. 杀伤路径是共享资源：连接槽位、CPU、buffer pool——只读查询照样能拖垮 OLTP。
2. 加固核心是隔离爆炸半径：副本 + 分池 + 分账号 + 分级超时，而非只优化一条 SQL。
3. 配套守门：报表扫描量阈值 + 主库连接打标签巡检，防止报表流量悄悄回流主库。

**复盘追问**：
1. 事故后只把那条 SQL 加了索引，为什么一个月后又拖了一次？（新报表复用同一模式：共享池 + 大聚合；缺的是结构性防线——分池分账号，任何"下一条慢 SQL"都会重演）
2. 运营临时要"实时精确数字"不走汇总层怎么办？（引导到只读副本的报表池 + 硬超时；主库精确读必须走审批并限并发，把例外变成显式清单而非潜规则）
