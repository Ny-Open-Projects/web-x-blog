### Q7072 · 流式 P95 的近似账：分桶 sketch 的精度与口径

难度：P5 | 标签：分位数、近似算法、监控口径、内存成本

**问**：监控大盘的接口 P95 是 180ms，财务按 SLA 结算用的精确 P95 是 202ms，两个"正确的数字"打架了。为什么流式场景的 P95 大多是近似值？分桶 sketch 的误差怎么控？两个口径怎么共处？

**答**：
- **结论**：精确 P95 要全量排序（内存 O(N)），接口日志每秒几十万条时根本存不起；监控管道普遍用近似 sketch——固定分桶（对数分界）或 t-digest/HDR 类结构，流式更新只记计数，内存 O(桶数)。代价是误差：分桶估计取桶中点，桶越宽误差越大，本例 40 个对数桶在 20 万样本上误差 3.1%。两个数字都"对"——口径不同：大盘用近似口径（实时性优先），结算用精确口径（准确性优先）。工程纪律是口径标注与分层：近似值用于告警与趋势，精确值用于 SLA 结算与复盘归因；大盘上必须写明"近似口径"，否则每次对不上都是一场"谁算错了"的会议。
- **取舍**：桶边界是精度与内存的旋钮：对数分界让高尾段（P99 之后）有足够分辨率——延迟分布的长尾恰好是最关心的区域；线性分界在尾段分辨率不足。要更高精度就上 t-digest（自适应合并桶，内存 O(百级) 误差 <1%），代价是实现复杂度与 CPU。
- **实战**：落地要点：① 监控与结算各用各的口径并在看板标注；② sketch 参数进配置并版本化（改桶边界会让历史曲线口径漂移）；③ SLA 复盘时用离线精确计算复核，把近似口径的系统性偏差量化出来（本例 -3.1%），作为换算依据。

```python
"""流式 P95 的近似账：精确排序 vs 固定分桶 sketch 的误差与内存。"""
import math
import random

random.seed(2)

N = 200_000
# 接口延迟：对数正态（毫秒）
lat = [math.exp(random.gauss(4.0, 0.8)) for _ in range(N)]

# 精确口径：全量排序（内存 O(N)，200k 个 float ≈ 1.6MB，十亿级就不可行）
exact_p95 = sorted(lat)[int(N * 0.95)]

# 近似口径：对数分桶 sketch（内存 O(桶数)，流式更新，只记计数）
BOUNDS = [math.exp(x * 0.5) for x in range(0, 26)]   # e^0, e^0.5, ... e^12.5
counts = [0] * (len(BOUNDS) + 1)
for v in lat:                                        # 流式：来一个数只记一次
    idx = next((i for i, b in enumerate(BOUNDS) if v <= b), len(BOUNDS))
    counts[idx] += 1

target = int(N * 0.95)
acc, sketch_p95 = 0, None
for i, c in enumerate(counts):
    acc += c
    if acc >= target:
        lo = BOUNDS[i - 1] if i > 0 else 0.0
        hi = BOUNDS[i] if i < len(BOUNDS) else BOUNDS[-1] * 2
        sketch_p95 = (lo + hi) / 2                   # 桶中点作估计
        break

err = abs(sketch_p95 - exact_p95) / exact_p95
print(f"精确 P95 = {exact_p95:.1f} ms（内存 O(N)：{N * 8 / 1e6:.1f} MB）")
print(f"sketch P95 = {sketch_p95:.1f} ms（内存 O(40 桶)，误差 {err:.1%}）")
print("口径纪律：监控大盘用 sketch 标注『近似口径』，财务/SLA 结算用精确口径——"
      "两个数字打架时先对口径，而不是先怀疑有人算错")
```

**追问链**：
1. 追问一层：为什么分桶边界要取对数而不是等宽？——延迟分布是长尾的：等宽桶在 P95 之后只有 1-2 个桶，分辨率崩塌；对数分界让每个数量级都有固定桶数，长尾段的相对误差均匀可控。分桶设计跟着分布形状走，不是跟着数值范围走。
2. 追问二层：t-digest 相比固定分桶好在哪、贵在哪？——t-digest 按分位点密度自适应合并桶：中位数附近合并（反正不关心）、尾部保持细粒度（SLA 关心的区域），同内存下误差低一个量级；代价是要维护合并逻辑与 CPU 开销，且不同实现（Java/Python 库）的 sketch 不可互换——换实现等于换口径，历史曲线要重标。

**背诵要点**：
1. 精确 P95 内存 O(N) 流式不可行；sketch 内存 O(桶数)，代价是分桶内误差。
2. 桶边界跟分布形状走：长尾用对数分界，P99 之后才保有分辨率。
3. 近似与精确是两个口径：大盘标"近似"、结算用精确，看板不标注就是事故温床。

**复盘追问**：
1. 为什么"两个都对"的数字打架仍要当成事故处理？（口径未标注会让每次对数都消耗信任并触发无效排查；修复方式是看板口径标注 + 口径登记表，而不是让某一方改数字）
2. 换监控系统后 P95 曲线整体抬了 5%，是性能劣化还是口径变了？（先查 sketch 参数与分位算法差异——换系统等于换口径；口径变更必须版本化并在图上画变更线）
