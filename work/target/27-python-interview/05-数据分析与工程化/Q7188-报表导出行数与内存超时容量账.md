### Q7188 · 报表导出行数与内存/超时容量账

难度：P6 ｜ 标签：容量规划、报表导出、流式处理、分页

基线：Python 3.9+；pandas 2.x（可选）/ 标准库 csv；Web 框架同步流式响应。

**问**：运营后台一个"导出订单明细"接口，平时几万行很快，某天有人选了"全部历史 800 万行"，接口 90 秒超时，同时进程内存涨到 4GB 触发 OOM。这类导出接口的容量账怎么算？修复方案的正确形状是什么？

**答**：
- **结论**：导出的两个硬约束：内存 = 单次物化的行数 × 行宽（`fetchall` + pandas 全量 DataFrame 是最贵的做法）；时长 = 行数 × 每行序列化成本 + 网络传输。800 万行 × 250B/行 ≈ 2GB 级别物化，任何同步 HTTP 接口都不该走这条路。正确形状是**流式管道**：DB 服务端游标分批读 → 逐批写 CSV/XLSX 到临时文件或对象存储 → 返回下载链接；再叠加"超上限直接拒绝/异步化"的产品约束。
- **取舍**：同步流式（简单，但占住 worker 数分钟）vs 异步任务（Celery/队列生成文件，用户等通知，资源可控）vs 产品限流（单次上限 10 万行，引导用户分批/加过滤条件）。行数超过阈值一律异步；XLSX 格式流式写出要用 write-only workbook（openpyxl），CSV 天然流式。
- **实战**：账的公式——`批次行数 = 内存预算 / 行宽`（如 200MB 预算 / 250B ≈ 80 万行一批）；每批用 `cursor.fetchmany(n)` 或 `yield_per`；导出任务加"行数预估"预检（先 `COUNT` 带同样 WHERE），超过阈值直接返回"数据量过大，已转异步任务"。

```python
# 流式导出管道：服务端游标分批 + 逐批写 CSV（标准库可运行）。
import csv
import io
from itertools import islice

def fake_db_query(total_rows: int, batch: int):
    """模拟服务端游标：分批产出，绝不一次物化全量。"""
    for start in range(0, total_rows, batch):
        yield [{"id": i, "amount": i * 1.5, "status": "paid"}
               for i in range(start, min(start + batch, total_rows))]

def estimate_check(total_rows: int, row_bytes: int,
                   mem_budget_mb: float, async_threshold: int) -> str:
    """预检：行数超阈值转异步；否则算批次大小。"""
    if total_rows > async_threshold:
        return f"{total_rows} 行 > {async_threshold}：拒绝同步导出，转异步任务"
    batch = int(mem_budget_mb * 2**20 / row_bytes)
    return f"同步流式导出：批大小 {batch} 行，内存预算 {mem_budget_mb}MB"

def stream_export(total_rows: int, batch: int) -> io.StringIO:
    buf = io.StringIO()
    writer = csv.DictWriter(buf, fieldnames=["id", "amount", "status"])
    writer.writeheader()
    n = 0
    for rows in fake_db_query(total_rows, batch):
        writer.writerows(rows)          # 逐批写，内存里永远只有一批
        n += len(rows)
    print(f"已写出 {n} 行，缓冲区大小 {len(buf.getvalue()) // 1024}KB")
    return buf

if __name__ == "__main__":
    print(estimate_check(total_rows=8000_000, row_bytes=250,
                         mem_budget_mb=200, async_threshold=100_000))
    print(estimate_check(total_rows=50_000, row_bytes=250,
                         mem_budget_mb=200, async_threshold=100_000))
    stream_export(total_rows=50_000, batch=10_000)
```

**追问**：
- 一层：为什么 pandas 读 CSV/SQL 比流式贵好几倍？→ 提示：DataFrame 要物化全部列类型推断与副本，pandas 2.x 的 chunked 迭代（`read_csv(chunksize=)`）或 Arrow 后端可降峰。
- 二层：异步导出任务本身超时/失败怎么办？→ 提示：任务幂等（重跑覆盖同一文件）、进度可查（进度表/进度字段）、失败给用户明确反馈而非静默；文件设 TTL 定期清理，别把对象存储再堆爆。
- 三层：导出接口还要防什么安全问题？→ 提示：越权导出（行级权限在 SQL 里兜底而不是前端）、注入（导出内容做 CSV 公式注入转义，防 `=cmd()` 类攻击）。

**背诵要点**：
1. 导出两约束：内存=物化行数×行宽，时长=行数×单行成本；正确形状是流式管道 + 预检。
2. 预检先 COUNT 同 WHERE 行数，超阈值转异步任务（幂等、可查进度、文件 TTL）。
3. 批大小 = 内存预算/行宽；服务端游标 fetchmany/yield_per，XLSX 用 write-only 模式。

**复盘追问**：
1. 为什么接口没有行数上限？提示：产品与工程缺"数据量分级"约定，导出应有明确的同步/异步分界线。
2. 如果业务方坚持要一次拿全量怎么办？提示：异步 + 对象存储 + 数据完整性校验（行数/校验和），而不是放宽同步路径。
