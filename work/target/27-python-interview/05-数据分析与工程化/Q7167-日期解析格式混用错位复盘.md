### Q7167 · 日期解析格式混用导致数据错位的复盘

难度：P6 ｜ 标签：事故复盘、pandas、日期
基线：pandas 2.x/3.0（`pd.to_datetime` 的 `format` 显式化趋势，3.0 对混合格式更严格）。

**问**：某报表某天起所有订单日期整体偏移（日和月互换），金额按天汇总全部错位。根因是什么？如何在管线里让"解析歧义"不再靠运气？

**答**：**结论**：根因是 `pd.to_datetime`（或 `dateutil`）对**歧义日期串的猜测式解析**：`03/04/2025` 究竟是 3 月 4 日还是 4 月 3 日，取决于 `dayfirst` 参数与行内的"看起来更合理"的猜测。当上游把导出格式从 `DD/MM` 改成 `MM/DD`（或混入新格式行），猜测规则悄悄变化，历史段错位、新数据对齐——这类事故的特点是**不报错、只错位**，全靠下游对账兜底发现。

**取舍**：三条修复路线：① 显式 `format="%d/%m/%Y"`——唯一能消灭歧义的做法，代价是格式真的会变时直接抛错（这正是想要的 fail-fast）；② 继续猜 + `errors="coerce"` + 事后校验（解析日期落在业务区间外即告警）——宽容但藏雷；③ 上游契约化：数据交换一律 ISO 8601（`2025-04-03`），歧义根本不产生，这是长期正解。

**实战**：解析层的纪律：任何 `to_datetime` 必须带 `format` 或 `format="mixed"`+显式声明；解析后校验三件套——非空率、区间合理性（订单日期不早于开业日期不晚于今天）、与行数的守恒；跨源对账加"日粒度金额分布 diff"，错位日会立刻显形。

```python
import pandas as pd

raw = pd.Series(["03/04/2025", "12/03/2025", "25/12/2025"])

# 事故复现：默认猜测（dayfirst=False）下 "25/12" 被判为 12 月 25 日，
# 但 "03/04" 被判为 3 月 4 日 —— 同一列内格式猜测不一致
default_parsed = pd.to_datetime(raw, format="%m/%d/%Y", errors="coerce")
print("按 MM/DD 解析:", list(default_parsed.dt.strftime("%m-%d")))
# 25/12 无法按 MM/DD 解析 -> NaT，暴露列内格式混用

# 反面教材：完全靠猜（老 pandas 会猜出混合结果，不报错）
guessed = pd.to_datetime(raw, errors="coerce")
print("猜测解析:", [str(x.date()) for x in guessed])

# 修复 1：显式 format + fail-fast
fixed = pd.to_datetime(raw, format="%d/%m/%Y")
print("显式 DD/MM:", list(fixed.dt.strftime("%m-%d")))

# 修复 2：解析后区间校验（订单日期必须在业务窗口内）
def validate_dates(s: pd.Series, lo: str, hi: str) -> None:
    out_of_range = s[(s < lo) | (s > hi)]
    if len(out_of_range):
        raise ValueError(f"{len(out_of_range)} 行日期越界: "
                         f"{list(out_of_range[:3])} —— 疑似格式错位")
    if s.isna().any():
        raise ValueError("存在 NaT：解析失败行必须显式处理")
    print("区间校验通过:", s.min().date(), "~", s.max().date())

validate_dates(fixed, "2025-01-01", "2025-12-31")

# 修复 3（长期）：契约化为 ISO 8601，歧义消失
iso = fixed.dt.strftime("%Y-%m-%d")
print("ISO 8601:", list(iso))
```

**追问 1**：为什么"猜"在 pandas 3.0 里更危险？
提示：新版对混合格式倾向直接抛错或严格化处理，老代码升级后可能从"静默猜对"变成"批量抛错"——依赖猜测本身就是技术债，升级即爆。

**追问 2**：`dayfirst=True` 全局设置是不是就安全了？
提示：只对 dayfirst 风格的源安全；一旦混入 ISO 格式或另一种习惯的源，仍会错位。参数是按"整个数据源"声明契约的，不是按"希望它是对的"。

**追问 3**：错位已经发生、历史数据已入库，怎么修？
提示：定位污染边界（格式变更的时间戳/批次号）→ 只重解析该边界内的原始串（这也是要求保留原始列的原因）→ 回写后跑日粒度分布 diff 验证；没有原始列就只能靠业务规则重建，成本高一个量级。

## 背诵要点
1. 歧义日期串（DD/MM vs MM/DD）靠猜解析：不报错、只错位，是最隐蔽的数据事故。
2. 纪律：to_datetime 必带显式 format；解析后校验非空率 + 区间合理性 + 行数守恒。
3. 长期正解是 ISO 8601 契约化；修复错位必须依赖保留的原始列。
