### Q7168 · 特征宽表的列数与内存容量账：列多到什么程度会失控

难度：P6 ｜ 标签：容量规划、特征工程、内存

**问**：特征平台迭代三年，宽表从 50 列涨到 3000 列，训练任务内存翻了几十倍。列数增长的内存账怎么算？容量失控的第一个信号是什么？

**答**：**结论**：宽表内存 = 行数 × 列数 × 单元格字节 × 类型放大系数。numpy float64 单元 8B，但 pandas 的 object 字符串列单元格只有指针 8B + 每个独立字符串对象几十 B（去重少时放大 10-100 倍）；列数涨 10 倍、行数涨 5 倍，名义 50 倍，实际可能 200 倍。**失控的第一个信号不是 OOM，而是类型劣化**：新特征为图省事塞成 object/str，内存突然上一个台阶——所以容量账要按"列 × dtype"记账，而不是按"列数"。

**取舍**：治理路线的成本对比：① dtype 优化（object→category/int8/float32）几乎零成本，通常省 50-80%；② 列裁剪（按特征重要性/缺失率下线僵尸列）省最多但要特征治理流程；③ 物理重排（Parquet 列存 + 只读需要的列）把"内存里的宽表"变成"磁盘上的宽表"，训练侧按列下推读取。多数团队只需要 ①+③ 就能再活两年。

**实战**：给宽表建"列账本"：每列的 dtype、内存、缺失率、最近使用时间四元组入表，每月审计一次；新特征上线必须登记 dtype 预算，object 列要说明为什么不走 category。

```python
# 宽表内存账：按列 dtype 记账（sys.getsizeof 近似）
import sys
import numpy as np

CELL = {"float64": 8, "float32": 4, "int8": 1, "int16": 2, "int64": 8,
        "bool": 1}

def column_memory(rows: int, dtype: str, distinct: int = 0,
                   avg_str_bytes: int = 0) -> int:
    """返回该列的内存字节数。object 列 = 指针 + 字符串对象。"""
    base = rows * CELL.get(dtype, 8)
    if dtype == "object":
        base = rows * sys.getsizeof("x" * 8)   # 指针约 57+str 长度
        base += distinct * (49 + avg_str_bytes)  # 独立字符串对象
    return base

def wide_table_budget(rows: int, columns: list[dict]) -> dict:
    def mem(c: dict) -> int:
        return column_memory(rows, **{k: v for k, v in c.items()
                                      if k != "name"})
    total = sum(mem(c) for c in columns)
    return {"rows": rows, "cols": len(columns),
            "memory_mb": round(total / 1024**2, 1),
            "top_offenders": sorted(
                ((c.get("name", "?"), round(mem(c) / 1024**2, 1))
                 for c in columns), key=lambda x: -x[1])[:3]}

rows = 2_000_000
cols = [
    {"name": "f_numeric_1", "dtype": "float64"},
    {"name": "f_float32_1", "dtype": "float32"},
    {"name": "f_cat_city",  "dtype": "object", "distinct": 300,
     "avg_str_bytes": 12},
    {"name": "f_cat_free",  "dtype": "object", "distinct": 1_500_000,
     "avg_str_bytes": 24},   # 高基数自由文本列
]
budget = wide_table_budget(rows, cols)
print(budget["memory_mb"], "MB, 头部大户:", budget["top_offenders"])
# 高基数 object 列独占大头：这是"类型劣化"的典型信号

# 优化对照：object -> category（列存编码，内存 = 去重数 + 指针）
def category_memory(rows: int, distinct: int, avg_bytes: int) -> int:
    return distinct * (49 + avg_bytes) + rows * 4   # codes 用 int32

print("free 文本列 category 化后:",
      round(category_memory(rows, 50_000, 24) / 1024**2, 1), "MB")
# 若业务上可接受：区分度高的做 category，真自由文本列考虑哈希/移出宽表
```

**追问 1**：为什么 object 列的放大系数可能到 100 倍而 category 列不会？
提示：object 每个单元格是独立 Python str 对象（49B 头 + 内容），重复值不共享；category 先建字典再存 int32 codes，重复越多收益越大——高基数低重复是 category 最差场景。

**追问 2**：列裁剪和 Parquet 列下推是不是一回事？
提示：不是。裁剪是删列（特征治理决策，影响训练语义）；列下推是按需读列（物理 IO 优化，语义不变）。宽表可以既保留 3000 列又通过下推让训练只读 200 列。

**追问 3**：3000 列的特征宽表，读取 Parquet 时哪一步最慢？
提示：元数据（footer/parquet 行组统计）与列块寻址；列数多时 row group 的 statistics 膨胀，`pyarrow` 读元数据可能秒级——这就是"列数也吃 IO 预算"的账。

## 背诵要点
1. 宽表内存 = 行 × 列 × 单元字节 × 类型放大；object 高基数列放大 10-100 倍，是失控首因。
2. 失控信号是类型劣化（新特征塞 object），账要按"列 × dtype"记，不按列数。
3. 治理三件套：dtype 优化（省 50-80%）、僵尸列下线、Parquet 列下推；配"列账本"月度审计。
