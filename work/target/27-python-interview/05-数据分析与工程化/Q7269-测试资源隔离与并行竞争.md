### Q7269 · 并发一开测试互相打：端口/临时目录/schema 的资源隔离矩阵

难度：P5 ｜ 标签：测试隔离、并行测试、端口冲突、临时目录、资源租约

基线：Python 3.12；用锁保护的租约注册表模拟端口分配（固定端口撞车 vs 临时端口复用），全标准库实跑。

**问**：测试本地全绿，一开 xdist 并行就互相失败：端口被占、临时目录互写、数据库里对方的测试数据混进来。并行测试需要隔离哪些资源？每类资源的正确隔离姿势是什么？"可隔离性"应该在设计阶段怎么预留？

**答**：
- **结论**：并行测试的三类经典冲突资源与对应隔离姿势：① **网络端口**：硬编码 `localhost:8080` 并行必撞——服务 bind **端口 0** 让内核分配临时端口，真实端口（`sock.getsockname()`）写进 fixture 返回给用例；② **临时目录**：`tempfile.TemporaryDirectory()` 每用例/每 worker 独立目录，finalizer 清理（Q7147 磁盘账管上限）；③ **数据库状态**：每 worker 独立 schema/database（xdist 的 worker id 命名），或每用例事务回滚——绝不共享一套表随便删。共同机制是**资源租约**：申请-独占-释放，冲突在申请时就显式失败，而不是运行中互相踩。隔离失败的症状有迷惑性：两个 worker 撞端口表现为随机 502，数据互踩表现为"单独跑过、一起挂"——归因方向要先对准资源而不是代码逻辑。
- **取舍**：① 隔离粒度：每 worker 隔离（建库成本 × worker 数）vs 每用例隔离（更干净更慢）——数据库类每 worker、纯内存状态每用例是常见配比；② 外部依赖的真实 vs 容器 vs mock：端口隔离让"每 worker 起一个真实服务"成为可能，比 mock 保真；③ 租约的清理兜底：worker 崩溃不释放租约会泄漏资源，注册表要有 TTL/会话绑定（TestContext 关闭时统一回收）；④ 隔离不是免费：建库/起服务的前置成本可能超过用例本身，session 级 fixture + worker 级复用是平衡点。
- **实战**：① 测试配置禁硬编码资源标识（端口/路径/库名），全部走 fixture 注入——grep 检查作为 CI 门禁；② 起服务的 fixture 统一返回 (端口, 关闭钩子)，用例只认参数；③ 数据库测试的模板：worker 级建库 → 用例级事务/快照 → finalizer 回滚或 drop；④ 并行度可调（`-n` 参数），资源隔离审计时按最大并行度做容量预算（每个 worker 的端口数 × 服务数）。

```python
"""Q7269 测试资源隔离: 固定端口并行必撞, 端口0+租约注册表解决。"""
import threading

DEFAULT_PORT = 8080              # 硬编码端口: 并行 worker 的灾难
USED_PORTS: set[int] = set()
lock = threading.Lock()


def bind_fixed(port: int) -> str:
    with lock:
        if port in USED_PORTS:
            return f"OSError: [Errno 98] address already in use :{port}"
        USED_PORTS.add(port)
        return f"listening :{port}"


def acquire_ephemeral() -> int:
    """bind 端口 0: 内核分配空闲端口; 这里模拟为最小空闲端口分配."""
    with lock:
        port = 1024
        while port in USED_PORTS:
            port += 1
        USED_PORTS.add(port)
        return port


def release(port: int) -> None:
    with lock:
        USED_PORTS.discard(port)


if __name__ == "__main__":
    # 反例: 两个 worker 都 bind 8080
    r1 = bind_fixed(DEFAULT_PORT)
    r2 = bind_fixed(DEFAULT_PORT)
    print(f"worker1 bind {DEFAULT_PORT}: {r1}")
    print(f"worker2 bind {DEFAULT_PORT}: {r2}")

    # 正解: 每个测试申请临时端口, 用完释放
    p1 = acquire_ephemeral()
    p2 = acquire_ephemeral()
    print(f"worker1 拿到临时端口 {p1}, worker2 {p2} (互不相等)")
    release(p1)
    p3 = acquire_ephemeral()        # 释放后端口可复用
    print(f"worker1 释放 {p1} 后, {p3} 可复用: {p3 == p1}")
    ok = ("OSError" in r2 and p1 != p2 and p3 == p1)
    print(f"校验: 固定端口撞车复现 + 临时端口隔离 -> {'通过' if ok else '异常'}")
    print("结论：测试里禁硬编码端口, 服务 bind 0 拿临时端口并把真实端口写进 fixture;")
    print("      数据库/临时目录同理: 每 worker 独立 schema/dbname, 清理挂在 fixture finalizer")
```

**追问一**：为什么"bind 端口 0"是标准解法而不是"每个测试写不同端口"？内核怎么保证 0 号端口分配唯一？

→ 解析：手动分配端口的本质是**应用层重复实现内核已经做好的并发安全分配**：内核的 ephemeral 端口分配在 bind(0) 时原子完成（检查占用 + 标记分配在同一临界区），且与系统其他进程共享占用视图——你的测试进程和 IDE 里挂着的服务也查得到。手动写死"测试用 18081、18082"：① worker 数变化就加端口清单，维护成本线性涨；② 与系统上其他服务的偶然撞车没法防；③ 分配逻辑分散在每个测试文件里，审计困难。bind(0) 的唯一注意点是**拿真实端口的时机**：`listen()` 之后 `getsockname()` 才有确定值，fixture 要在 yield 前把端口写进上下文。数据库类资源没有"端口 0"等价物，所以 schema/database 命名要自己做租约——这正是 worker id + 时间戳命名 + 清理注册表的由来：**内核解决不了的隔离，才轮到应用层租约**。

**追问二**：数据库测试"每用例事务回滚"隔离有什么失效场景？什么数据必须用物理隔离？

→ 解析：事务回滚隔离的实现：用例在一个事务里跑，finalizer `rollback()`——快且干净，但有失效面：① **被测代码自己 commit/rollback**：测试事务和业务事务是同一个连接还好，一旦被测代码拿自己的连接池连接（新建连接、独立事务），测试的回滚管不到它，数据落库残留——这是最常见的失效；② **DDL 不参与事务回滚**（部分数据库）：被测代码建了表/索引，回滚后残留，下一用例建表直接撞 already exists；③ **隐式提交**（autocommit 模式、某些驱动默认设置）让"事务里"的假设不成立；④ 跨连接可见性测试（隔离级别验证类用例）本来就要求第二个连接看到未提交数据，回滚模型不适用。所以规则是：**纯读 + 单连接 + 无 DDL 的用例可用事务回滚；涉及多连接、DDL、外部副作用（发消息、写文件）的必须物理隔离**——每 worker 独库/独 schema + 用例级数据命名空间（唯一前缀），代价换确定性。隔离策略要在"快"和"确定"之间选，而确定性永远是底线。
