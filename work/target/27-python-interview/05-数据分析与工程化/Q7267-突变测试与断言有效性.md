### Q7267 · 覆盖率 100% 还漏了边界：突变测试与断言有效性

难度：P6 ｜ 标签：突变测试、mutation testing、断言有效性、测试质量、CI 门禁

基线：Python 3.12；实现最小突变测试框架（对被测函数注入 4 类突变，用旧/新两套测试集跑杀灭率），全标准库实跑。

**问**：一个函数覆盖率 100%，线上还是出了 `>=` 写成 `>` 的边界 bug——覆盖率不是说明"代码都被测过"吗？"执行过"和"验证过"差在哪？突变测试（mutation testing）是怎么量化断言有效性的？成本和门禁怎么设？

**答**：
- **结论**：覆盖率只回答"测试运行时**执行了**这行代码"，不回答"断言**验证了**行为正确"。突变测试补的正是这一层：**对被测代码做微小变异**（比较符反转、阈值 ±1、返回值取反、语句删除），每个变异体（mutant）跑一遍测试集——测试仍全过 = 突变**存活** = 有一个行为差异逃过了断言；测试挂掉 = 突变**被杀死** = 断言抓住了这个差异。**突变杀灭率（mutation score）= 杀死数/总突变数**，是断言有效性的直接量化。本卡演示：无边界用例的旧测试集杀灭率 2/4（`>=`→`>` 和阈值 19 的突变都存活），补上 17/18/19 三点边界后 4/4——同样的行覆盖率，断言强度完全不同。
- **取舍**：① 全量突变测试太贵（每突变全跑测试集）：只对核心模块/资金路径跑，或用"仅跑覆盖到突变点的用例"（mutmut 类工具的优化）；② 存活突变不是都要杀：等价突变（行为实际无差异的变异，如 `x*1`）杀不死是理论正常，人工 triage 一次成本不低；③ 突变算子集合要审：业务敏感型代码自定义算子（金额取整规则、时区偏移）比通用算子更有价值；④ 与 review 的分工：突变测试抓"断言缺失"，review 抓"语义错误"，两者互补不可替代。
- **实战**：① CI 分层门禁：行覆盖率（快、每次跑）→ 核心包突变杀灭率（慢、夜间跑），阈值从当前基线 +2% 起步防倒退；② 新增资金/风控函数必须附边界三点用例（n-1/n/n+1）——本卡杀灭率缺口恰好全在边界；③ 存活突变列表进 backlog，与 bug 归因对照：存活突变多的模块往往是线上 bug 高发区；④ 别给突变测试设"100% 杀灭"目标，85-95% 是工程现实，剩余留给 review。

```python
"""Q7267 突变测试: 覆盖率 100% 的用例挡不住多少突变, 断言有效性才见真章。"""


def is_adult(age: int) -> bool:
    """被测函数: 成年判定 (>=18)."""
    return age >= 18


def run_tests(impl) -> bool:
    """现有测试集: 3 个用例, 覆盖了所有分支但边界断言不足."""
    cases = [(20, True), (17, False), (30, True)]
    return all(impl(x) == want for x, want in cases)


MUTANTS = {
    "原函数": is_adult,
    "突变1: >= 改 >": lambda a: a > 18,
    "突变2: return 取反": lambda a: not (a >= 18),
    "突变3: 阈值 18 改 19": lambda a: a >= 19,
    "突变4: 恒真": lambda a: True,
}


def strengthen_tests(impl) -> bool:
    """补边界后的测试集: 17/18/19 三点边界 + 30."""
    cases = [(17, False), (18, True), (19, True), (30, True)]
    return all(impl(x) == want for x, want in cases)


if __name__ == "__main__":
    print("旧测试集(无 18 边界用例):")
    killed, total = 0, 0
    for name, fn in MUTANTS.items():
        if name == "原函数":
            continue
        total += 1
        survived = run_tests(fn)      # 测试仍全过 = 突变存活
        if not survived:
            killed += 1
        print(f"  {name}: {'被杀死' if not survived else '存活(!)'}")
    print(f"  突变杀灭率 {killed}/{total}")

    print("\n补边界用例后:")
    killed2 = sum(not strengthen_tests(fn) for n, fn in MUTANTS.items() if n != "原函数")
    print(f"  突变杀灭率 {killed2}/{total}")
    ok = killed == 2 and killed2 == total
    print(f"校验: 边界用例提升杀灭率 {killed}->{killed2} -> {'通过' if ok else '异常'}")
    print("结论：突变测试量化'断言有效性', 覆盖率只说明'执行过'不说明'验证过';")
    print("      关键函数的阈值/边界/取反突变是杀灭率主要缺口, CI 对核心模块设杀灭率门槛")
```

**追问一**：什么是"等价突变"？它为什么在理论上杀不死，工程上怎么处理？

→ 解析：等价突变（equivalent mutant）指**变异后的程序与原程序在所有输入上行为一致**：比如对 `abs(x)` 注入 `x*1`、对不可达分支里的语句做反转。测试集再强也杀不死它——因为它根本没改变可观察行为，杀灭率存在理论上限 < 100%。工程处理：① 自动检测等价性不可判定（停机问题），只能人工 triage；② 实践中标记"确认存活-已知等价"清单，下次突变报告排除它，避免每次都人工看一遍；③ 成本控制是关键：等价突变占比高说明突变算子设计不佳（太多无意义变异），收紧算子集合（只变异条件表达式/常量边界）能同时降成本和等价率。认识这一点才不会掉进"追杀灭率 100%"的兔子洞——那是一个不可达且不可判定的目标。

**追问二**：突变测试与 property-based testing（如 hypothesis）是什么关系？能不能互相替代？

→ 解析：不能替代，方向相反。突变测试**固定测试集，变异被测代码**，回答"我的断言强不强"；property-based testing**固定被测代码，生成海量输入**，回答"我的实现稳不稳"（对随机输入找不变量违反）。组合拳的用法：先用 hypothesis 找出实现 bug（输入空间覆盖），修完后用突变测试验证测试集质量——hypothesis 生成器本身也是突变质量的一部分：如果突变体活着但 hypothesis 也没打中它，说明**生成器缺输入域**（比如没生成边界整数）。反过来突变测试可以评估 property 的断言强度：property 只查 `abs(x)>=0` 这类弱不变量时，取反突变会存活——提示 property 该加具体值断言。两者共用一个哲学：**测试质量是可测量的对象**，而不是"写了多少条测试"的体力指标。
