### Q7254 · 口径改了历史怎么办：数据回溯重算的成本模型与决策阈值

难度：P7 ｜ 标签：回溯重算、成本模型、口径变更、增量修补、分区策略

基线：Python 3.12；实现回溯重算的成本模型（分区成本 × 依赖扇出 × 窗口长度），对三种策略输出决策与临界点。

**问**：指标口径改了（比如"活跃"的定义从打开 App 改成产生任意行为），未来分区按新口径算没问题，**历史数据怎么办**？全量重算要烧多少计算资源、下游要重建多少表；不重算看板上历史和未来口径断裂。有没有一个结构化的决策方法，而不是拍脑袋"全量重跑一遍"？

**答**：
- **结论**：回溯重算是"**历史正确性**与**重算成本**的交易"，决策要素五项：① **回溯窗口**：口径变化影响多少天/分区（有的指标只影响当日，有的影响全历史——比如累计指标）；② **单分区重算成本**：计算时长 × 资源单价 × 并发上限（决定墙钟时间）；③ **下游扇出**：该表被 N 个下游依赖，重算=触发 N 路下游重建，扇出越大总成本指数放大（Q1742 影响面）；④ **增量修补的可能性**：口径变化只影响"部分行/部分维度"时，可只重算受影响子集（如只重算某几个渠道），成本按选择性打折；⑤ **业务容忍度**：断裂期与修复期的体验代价。三者可选：**全量重算**（历史统一、成本高）、**增量修补**（便宜但新旧口径过渡期复杂）、**口径分界线**（历史封版+新口径从切换日起算，看板标注，成本为零但历史未来两条线）。用成本模型算出临界点再决策，而不是按"重算一台集群跑一晚上也还好"的直觉。
- **取舍**：① 重算必须写影子分区后原子切换（Q2005 结果原子发布），失败回滚，不能覆盖线上；② 重算期间新旧口径并存，读路由按日期分界（分界日前老口径、之后新口径），分界日在看板加断点标注；③ 重算窗口与在线任务错峰（Q7631/Q6690 的错峰账），夜里跑但留追赶容量；④ "口径分界线"最被低估：多数业务场景根本不需要重算历史，只需诚实标注——重算的冲动常常来自"看板上不好看"而非"决策要用历史"。
- **实战**：① 口径变更评审单固定五要素表（窗口/成本/扇出/选择性/容忍度），评审时填齐；② 成本模型参数（单分区时长、单价）从历史任务运行记录取，别拍脑袋；③ 重算任务复用回填框架（Q1405 灰度回填限速、Q7248 互斥租约），不自写调度；④ 决策结论与理由写入指标字典（Q7255 口径字典），下次同类争议直接引用。

```python
"""回溯重算成本模型: 三策略决策与临界点计算。"""
from dataclasses import dataclass


@dataclass
class BackfillParams:
    window_days: int          # 回溯窗口(天)
    cost_per_day: float       # 单天分区重算成本(元)
    downstream: int           # 下游扇出数(每个下游按 0.4 天成本联动重建)
    selectivity: float        # 选择性: 受影响数据占比(0~1), 增量修补按此打折


def cost_full(p: BackfillParams) -> float:
    """全量重算: 主表 + 下游联动重建。"""
    return p.window_days * p.cost_per_day * (1 + 0.4 * p.downstream)


def cost_partial(p: BackfillParams) -> float:
    """增量修补: 只算受影响子集, 但下游要双读合并(加固定复杂度成本)。"""
    return p.window_days * p.cost_per_day * p.selectivity * (1 + 0.4 * p.downstream) \
        + 150                  # 过渡期双口径读路由的开发与维护成本


def cost_boundary(p: BackfillParams) -> float:
    """口径分界线: 历史封版, 只在分界日标注。"""
    return 30                    # 一次标注+文档成本


def decide(p: BackfillParams) -> str:
    f, w, b = cost_full(p), cost_partial(p), cost_boundary(p)
    best = min((f, "全量重算"), (w, "增量修补"), (b, "口径分界线"), key=lambda x: x[0])
    return (f"全量={f:.0f}元 增量={w:.0f}元 分界={b:.0f}元 -> "
            f"建议: {best[1]}"), best[1]


if __name__ == "__main__":
    # 场景A: 大幅改活跃定义, 影响 730 天, 选择性高(全量行为), 下游 8 个
    a = BackfillParams(730, 40, 8, 0.9)
    msg_a, choice_a = decide(a)
    print(f"场景A (活跃定义大改, 730天, 扇出8):\n  {msg_a}")

    # 场景B: 只改某渠道归因, 影响同 730 天, 选择性 8%, 下游 3 个
    b = BackfillParams(730, 40, 3, 0.08)
    msg_b, choice_b = decide(b)
    print(f"场景B (单渠道归因修正, 选择性8%):\n  {msg_b}")

    # 场景C: 内部看板小口径微调, 下游仅 1 个看板
    c = BackfillParams(365, 40, 1, 0.5)
    msg_c, choice_c = decide(c)
    print(f"场景C (看板小口径微调):\n  {msg_c}")

    # 临界点: 全量 vs 增量的选择性临界值
    for d in (1, 3, 8):
        p = BackfillParams(730, 40, d, 1.0)
        # 增量 < 全量 当 selectivity < 1 - 150/(window*cost*(1+0.4*downstream))
        base = p.window_days * p.cost_per_day * (1 + 0.4 * p.downstream)
        crit = 1 - 150 / base
        print(f"下游={d}: 增量优于全量的选择性临界值 {crit:.0%}")
    ok = choice_a == "口径分界线" and choice_b == "增量修补"
    print(f"校验: 场景A走分界线(成本压倒正确性收益), 场景B走增量 -> {'通过' if ok else '复核'}")
    print("\n结论：回溯重算是成本换历史一致性; 先算五要素账,")
    print("      分界线是合法选项, 重算冲动常来自'看板不好看'而非'决策要用'")
```

**追问一**：重算期间新旧口径并存，下游读路由怎么写才不出错？

→ 解析：规则化：**按分区日期路由**——口径切换日 D 之前的分区读旧口径表、D 之后读新口径表，路由逻辑封装在统一的数据访问层（一个函数），禁止下游各自判断（各自判断必然有人把 `<` 写成 `<=`）。分界日当天如果两口径都有数据（比如过渡重算），以"分区元数据里的口径版本字段"为准而不是日期推断——日期推断在补数据时会失效。看板层同步加断点标注：切换日前后的趋势图断开或加注释，防止"指标突然掉/涨"被误读为业务变化（Q1473 发布前后快照对比的思路）。这段过渡逻辑打上清理计划：全历史统一后删除路由分支，别让兼容代码永生。

**追问二**：为什么增量修补的"双读合并"经常演变成事故源？

→ 解析：增量修补意味着**过渡期内同一指标有两部分数据源**：修补的子集来自新口径、其余来自旧口径，读的时候要合并。事故高发在三点：合并键没对齐（修补表用渠道 id、主表用渠道名）；覆盖关系写反（修补表应覆盖主表的受影响行，写成叠加就翻倍）；修补批次与日常重跑竞争（没有互斥租约，日常任务把修补结果又刷回旧口径——Q7248 互斥租约正是为这个）。所以增量修补的隐性成本不是计算，是**过渡期的正确性维护**：双读路由、合并规则、互斥、清理，每一项都要有测试。成本模型里那 +150 元固定项就是在为这些买单；当选择性不高时它摊得开，选择性接近 1 时增量反而不如全量干净——临界点公式说的就是这个。
