### Q7253 · 千万行 dict 存爆内存：结构化记录的定长二进制布局账

难度：P6 ｜ 标签：struct、二进制布局、列式存储、内存容量账、numpy 结构化数组思想

基线：Python 3.12；用标准库 struct 演示同构记录的定长打包（行式布局）、内存对比与按列访问，对应 numpy 结构化数组的核心思想。

**问**：要把 1000 万条设备心跳记录放内存里算特征：每条四个字段（设备 id int32、时间戳 int64、温度 float32、状态 uint8）。有人用 `dict` 或 `json` 存，内存先爆；有人上 numpy 结构化数组。numpy 的 structured dtype 到底是什么？它省内存的原理是什么？不依赖 numpy，这个原理能不能用标准库讲清楚？

**答**：
- **结论**：结构化数组（structured dtype）的本质是**同构记录的定长二进制连续布局**：先定义字段类型表（如 `<i4,<i8,<f4,<u1`），每条记录被 pack 成固定 21 字节，1000 万条就是约 200MB 的连续缓冲区——没有 Python 对象头、没有指针、没有 dict 的哈希表开销。对比参考：一个 dict 条目轻则数百字节，同量数据差 10~20 倍。字段访问两种模式：按行读（偏移 = 行号 × 记录长度，`struct.unpack_from`）与按列读（第 j 列的字节都在 `行号 × 长度 + 偏移j` 的等差位置上，扫一遍缓冲区即可）。numpy 是把这个布局做成向量化的数组对象，布局本身用标准库 `struct` 就能演示——面试讲清"定长同构 + 连续 + 偏移寻址"这三点就通了。
- **取舍**：① 行式 vs 列式：按行取整条记录快（局部性），按列聚合也够快（步长固定，可线性扫），真正列式引擎会把列再分块压缩（Q7201 列式零拷贝），结构化数组介于两者之间；② 可变长字段（字符串）不能直接定长——定长填充（比如 8 字节定长）或变长字段另存+偏移索引；③ 写入成本：pack 一次换长期读取的内存与速度，写多读少的场景不划算；④ 与 dict 相比失去的是"字段自描述"，格式演化要版本号（Q952 字段语义变更），读写两端对齐 dtype。
- **实战**：① 数据密集场景先算内存账：类型窄化（int64 够用别上 int64→int32）、对象换标量、再谈结构化布局（Q7023 dtype 瘦身）；② 共享内存多进程时结构化布局是首选（定长可直接 memoryview/mmap 切片，Q5091）；③ 网络传输同构批量数据时，定长记录流比 JSON 数组小一个数量级（Q2907 长度前缀帧的组合）；④ 压缩后落盘（zlib）再取时解压回缓冲区，一进一出的成本可控。

```python
"""结构化记录布局模拟：struct 定长打包 + 行/列访问 + 内存对比。"""
import struct
import sys

# 字段类型表: 设备id(int32) 时间戳(int64) 温度(float32) 状态(uint8)
REC_FMT = "<iQfB"                # 小端: 4+8+4+1 = 17 字节
REC_SIZE = struct.calcsize(REC_FMT)
FIELDS = ("device", "ts", "temp", "status")


class RecordBuffer:
    """同构记录的定长连续缓冲区 (numpy structured dtype 的标准库原型)。"""

    def __init__(self):
        self.buf = bytearray()

    def append(self, device: int, ts: int, temp: float, status: int) -> None:
        self.buf += struct.pack(REC_FMT, device, ts, temp, status)

    def row(self, i: int) -> dict:
        """按行读: 偏移 = i * REC_SIZE。"""
        vals = struct.unpack_from(REC_FMT, self.buf, i * REC_SIZE)
        return dict(zip(FIELDS, vals))

    def column(self, idx: int) -> list:
        """按列读: 等差偏移扫描同一字段的所有值。"""
        offsets = struct.Struct(REC_FMT)          # 各字段在记录内的偏移
        off = offsets.size and sum(struct.calcsize(REC_FMT[:idx + 1])
                                   - struct.calcsize(REC_FMT[idx:idx + 1])
                                   for _ in ())
        # 直接取第 idx 字段的偏移: 前缀长度
        prefix = struct.calcsize(REC_FMT[:idx]) if idx else 0
        fmt = REC_FMT[idx]
        n = len(self.buf) // REC_SIZE
        out = []
        for i in range(n):
            out.append(struct.unpack_from(fmt, self.buf, i * REC_SIZE + prefix)[0])
        return out

    def memory_bytes(self) -> int:
        return len(self.buf)


def build_dict_rows(n: int) -> list[dict]:
    """对照物: dict 行存储 (对象头+哈希表开销)。"""
    return [{"device": i % 65536, "ts": 1700000000 + i, "temp": 25.5, "status": 1}
            for i in range(n)]


if __name__ == "__main__":
    N = 100_000
    rb = RecordBuffer()
    for i in range(N):
        rb.append(i % 65536, 1700000000 + i, 25.5, 1)

    print(f"单条记录 {REC_SIZE} 字节 (定长) | {N} 行缓冲区 {rb.memory_bytes() / 1e6:.1f} MB")
    # dict 版只取小样本估算 (全量太慢太占内存), 按 1000 行外推
    sample = build_dict_rows(1000)
    per_row = sys.getsizeof(sample[0]) + sys.getsizeof(25.5) + sys.getsizeof(1)
    est = per_row * N / 1e6
    print(f"dict 估算(单行 {per_row}B 外推): ~{est:.0f} MB  -> 差 {est / (rb.memory_bytes() / 1e6):.0f} 倍")

    r0 = rb.row(0)
    print(f"\n按行读 row(0): {r0}")
    temps = rb.column(2)
    print(f"按列读 temp: 前5个 {temps[:5]} | 数量 {len(temps)}")
    print(f"校验: 行列一致 -> {r0['temp'] == temps[0]}")

    # 追加一致性: 定长布局支持随机访问
    r99999 = rb.row(N - 1)
    print(f"随机访问 row({N - 1}): {r99999}")
    print("\n结论：结构化布局=定长同构+连续+偏移寻址; 内存省一个数量级,")
    print("      代价是格式自描述性(要 dtype 版本)与写入的 pack 成本")
```

**追问一**：为什么列式聚合比逐行 dict 快得多？

→ 解析：两个来源。一是**局部性**：列式布局里同字段字节连续，CPU 缓存行利用率高，扫描 1000 万个 float 只顺序读 40MB；dict 里每个 float 是一个独立对象，散布在堆上，逐个访问都在缓存 miss。二是**指令开销**：列扫描是"固定偏移 + unpack"的紧凑循环，dict 访问每步要哈希查找 + 指针跳转。numpy 把列扫描下沉到 C 的向量化循环再快一个量级。所以分析场景的演进路线是：dict → 结构化缓冲区 → numpy/polars 列式，每一步都是同一原理的加深（Q333/Q7170 的对比卡）。

**追问二**：格式要加字段了，老缓冲区怎么兼容？

→ 解析：结构化布局的演化纪律与 protobuf 一致：**只加不改不删**，新字段 append 在 dtype 末尾——老数据的记录长度不变，读端用"记录长度 + 版本号"识别老格式，按老 dtype 解读后再补新字段默认值。如果新字段插在中间，所有偏移全变，老数据必须整批迁移。工程落地三件套：dtype 定义集中一处（单一事实源）、缓冲区头写版本号、读写端按版本分发解读函数（Q952 的版本兼容思路在二进制层的映射）。相比 JSON 的"字段名自描述"，二进制布局省内存但把兼容责任全压到版本管理上，这是取舍的另一半。
