### Q7131 · pip 2020 新解析器（回溯式解析）的演进与 CI 迁移要点

难度：P6 ｜ 标签：版本演进 / 依赖管理 / pip

**问**：pip 20.3 起"新解析器"成为默认：装包时不再允许"装出一个不一致的环境"，但 CI 里常出现 `ResolutionImpossible` 或安装突然慢几十秒（回溯）。新解析器的核心语义变化是什么？回溯为什么会慢？迁移期（旧 requirements 文件 + 新解析器）最常见的破坏点是什么？

**答**：
- **结论**：语义变化的本质是**把"装完再发现冲突"改成"装之前证明一致"**：旧解析器按顺序逐个装（先装的包"占坑"，后装的与之冲突时报错或已产生不一致环境）；新解析器在安装前把全依赖闭包当约束求解问题处理，回溯（backtracking）——某分支失败就退回去尝试该依赖的旧版本，保证结束时环境满足所有版本约束。回溯慢的机制：候选版本按新旧线性尝试，每次尝试都要下载元数据/构建 wheel 计算依赖，约束写得松（如 `requests` 不带上限、依赖链深）时组合爆炸，表现为"装一个包卡几分钟"。迁移破坏点三类：① 旧 requirements 里**版本未钉死的传递依赖**突然被解到与现状不同的版本（解析器有权选别的旧版，行为漂移）；② 依赖声明**自相矛盾**的老环境（以前靠"先到先得"侥幸工作）现在直接 ResolutionImpossible；③ 不完整元数据的老包（setup.py 动态依赖）回溯时代价更高。工程解法就是锁文件：`pip-compile`/`uv pip compile` 把解析结果钉死（Q7102 锁文件缺失同源），CI 里从"每次现解"变成"复用锁文件 + 校验"，回溯成本一次付清。
- **取舍**：锁文件全钉还是只钉直接依赖？全钉（传递依赖也固定）保证 CI 完全可复现，但升级时要主动跑 compile；只钉直接依赖保留解析弹性，代价是每次安装都可能回溯。`--no-deps + 显式清单`是极端流派，一般不推荐。回溯慢的临时解法：`--use-deprecated=legacy-resolver` 只能救急（已弃用路线），正解是收窄约束（给易漂移的包加上限）或上锁。
- **实战**：① CI 安装步骤改 `pip install -r requirements.lock`，变更入口是 compile 步骤而非手改；② ResolutionImpossible 时读 pip 输出的"约束链"（它会给冲突双方），优先修上游约束而不是 pin 死一切；③ 网络慢的环境配 `PIP_FIND_LINKS` 本地 wheelhouse（Q7115）+ `--only-binary=:all:` 减少回溯时的构建成本；④ 升级 pip 前 diff 一次解析结果（`pip compile` 前后对比），把行为漂移显性化。

```python
# 回溯解析模型: 约束求解, 失败回退候选版本; 松约束 -> 组合爆炸
# 基线: Python 3.9+ 标准库
from itertools import product


def resolve(packages: dict[str, list[str]],
            constraints: dict[str, set[str]]) -> dict[str, str] | None:
    """简化解析器: 按 package 顺序尝试候选(新->旧), 冲突则回溯。
    packages: 名字->候选列表; constraints: 名字->与其它包的兼容映射集合。"""
    names = list(packages)
    def bt(i: int, chosen: dict[str, str]) -> dict[str, str] | None:
        if i == len(names):
            return dict(chosen)
        name = names[i]
        for cand in packages[name]:                      # 新版本优先
            if cand in constraints.get(name, set()) or name not in constraints:
                chosen[name] = cand
                r = bt(i + 1, chosen)
                if r:
                    return r
            # 回溯: 尝试下一个(更旧的)候选
        chosen.pop(name, None)
        return None
    return bt(0, {})


def attempts(packages: dict[str, list[str]]) -> int:
    """最坏情形尝试组合数: 松约束时组合爆炸。"""
    n = 1
    for c in packages.values():
        n *= len(c)
    return n


def main() -> None:
    pkgs = {"a": ["3.0", "2.0"], "b": ["9.0", "8.0"], "c": ["1.4", "1.3"]}
    ok = resolve(pkgs, constraints={})               # 全兼容: 首选组合成功
    assert ok == {"a": "3.0", "b": "9.0", "c": "1.4"}
    conflict = resolve(
        {"a": ["3.0", "2.0"], "b": ["9.0"]},
        constraints={"a": {"2.0"}},                   # b 与 a==3.0 冲突
    )
    assert conflict == {"a": "2.0", "b": "9.0"}      # 回溯成功
    assert attempts(pkgs) == 8
    print(f"冲突时回溯到 a==2.0; 松约束最坏组合 {attempts(pkgs)} 种 x 元数据下载")
    print("OK: 新解析器=装前证明一致; 正解是锁文件钉死, 回溯成本一次付清")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"回溯"在 pip 里比在通用 SAT 求解器里慢得多？
→ 一句话提示：pip 的每次候选尝试要下载/解析该版本的元数据（网络 IO），不是内存里的约束传播——组合数 × 元数据获取成本，所以约束收紧和 wheel 缓存（Q7113/Q7115 同源）才是对症药。

**追问 2**：锁文件（pip-compile）和"给依赖加上限"这两个手段各解决什么？为什么不能互相替代？
→ 一句话提示：上限是约束层面让解析器不选坏候选（治"会解错"），锁文件是结果层面把一次成功解析固化（治"每次解得不一样"）；CI 复现性靠锁，兼容性表达靠约束，缺一就有回溯或漂移。

## 背诵要点
- 新解析器（pip 20.3+）= 安装前求解全依赖闭包，杜绝不一致环境；代价是回溯：候选从新到旧线性尝试 × 元数据下载成本。
- 三类迁移破坏：未钉传递依赖漂移、旧"侥幸一致"环境变 ResolutionImpossible、动态元数据老包回溯更慢。
- 正解 = 锁文件（CI 只装 lock，变更入口是 compile）+ 收窄约束 + wheel 缓存；legacy-resolver 仅救急已弃用。

## 复盘追问
- 为什么 ResolutionImpossible 时"pin 死所有包"往往是错误修复？提示：它把冲突藏进锁文件而不是修依赖声明，下次任何人升级都要重新撞一次墙；先读 pip 给出的冲突链，修源头约束。
- 锁文件方案下"传递依赖的安全更新"怎么进 CI？提示：定期（如每周）重跑 pip-compile 生成 diff 评审，而不是让每次安装隐式漂移——更新是显式事件，解析是确定性过程。
