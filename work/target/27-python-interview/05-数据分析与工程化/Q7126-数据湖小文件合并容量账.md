### Q7126 · 数据湖/表格式的小文件问题：元数据开销与合并（compaction）容量账

难度：P6 ｜ 标签：容量规划 / 数据湖 / Parquet

**问**：小时级任务每天往对象存储写 144 个分区、每分区几十个 5-20MB 的小 Parquet 文件，三个月后查询越来越慢，list 操作都超时。小文件的代价到底在哪一层？合并（compaction）的触发条件和目标大小怎么算？

**答**：
- **结论**：小文件的代价分三层叠加：① **元数据层**——每个文件都要 list（对象存储的 LIST 是分页 API，百万文件一次 list 要数万次请求）、每份 manifest/snapshot 记录文件数与统计，规划器做文件级裁剪的开销与文件数成正比；② **读取层**——每个文件一次打开/解析/预读，5MB 文件的读效率远低于 128MB（footer 解析、网络往返、列组统计摊薄不足）；③ **调度层**——下游 spark/pandas 的 task 数 = 文件数，task 开销（进程/线程启动、shuffle）淹没实际计算。合并账：目标文件大小通常 128-512MB（行组/压缩统计的摊薄拐点，Q7106 行组账同源）；触发条件 = 分区平均文件大小低于目标的 1/3 或文件数超阈值（如单分区 > 1000 个）。合并本身要容量：重写一个分区 = 读全分区 + 写全分区，峰值存储 ×2、集群 IO 双份，所以合并窗口要错峰（Q7116 挤峰同源）且按分区滚动，不能一次全表。
- **取舍**：预防（写入端攒批）还是治理（定时合并）？写入端把小时任务改成攒 4 小时一批写入，文件数直接降 4 倍，但数据新鲜度下降；治理（定时 compaction）保住新鲜度但常付集群成本。决策变量是"下游读多还是写多"：读多写少的报表表选预防+强合并，流水表选治理+弱合并（只合并热分区）。Compaction 本身的延迟与成本也要进 SLA：合并落后于写入就是"冻结的湖"。
- **实战**：① 监控三指标：单分区文件数中位数、平均文件大小、list P99；② 合并任务按分区滚动+并发上限，与大任务错峰；③ 写入端统一 parquet 目标大小与压缩参数（zstd level 前后一致），避免合并后再碎；④ 表格式（Iceberg/Delta）的 expire_snapshots/rewrite_data_files 定期跑，元数据不清理照样膨胀。

```python
# 小文件账: list 请求/读开销/task 数都与文件数成正比; 合并 = 读+写双份 IO
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class Partition:
    files: int
    avg_mb: float
    target_mb: float = 256.0

    def needs_compaction(self, file_cnt_thresh: int = 1000) -> bool:
        return (self.avg_mb < self.target_mb / 3
                or self.files > file_cnt_thresh)

    def list_requests(self, page: int = 1000) -> int:
        return -(-self.files // page)          # ceil 分页请求


def compaction_io_tb(p: Partition, partitions: int, compression: float = 3.0) -> float:
    """合并峰值 IO: 读+写 = 分区数据量 x2 (压缩后对象存储口径)。"""
    raw_tb = p.files * p.avg_mb * partitions / 1e6
    return raw_tb / compression * 2


def main() -> None:
    bad = Partition(files=1800, avg_mb=8.0)
    assert bad.needs_compaction()              # 8MB << 85MB 且 1800 > 1000
    good = Partition(files=6, avg_mb=280.0)
    assert not good.needs_compaction()
    # 90 天 = 90x1800 个文件, list 分页请求线性恶化
    total_files = bad.files * 90
    assert total_files == 162_000 and bad.list_requests() == 2
    peak = compaction_io_tb(bad, partitions=10)
    assert peak > 0
    print(f"单分区 {bad.files} 文件 x{bad.avg_mb:.0f}MB -> 合并; "
          f"90 天累计 {total_files:,} 文件")
    print(f"OK: 合并峰值 IO ≈ {peak:.2f}TB(读+写双份), 按分区滚动并错峰")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么对象存储上"文件数"比"文件大小"更早成为瓶颈？
→ 一句话提示：LIST 是分页请求、manifest 按 条目 记账、task 数按文件展开——三层开销都是 O(文件数)，而大小只影响单次读效率；所以 list 超时往往是膨胀的第一个信号。

**追问 2**：Iceberg/Delta 这类表格式里，为什么只合并数据文件还不够？
→ 一句话提示：元数据文件（manifest、snapshot）本身也在累积，不定期 expire_snapshots/清理孤儿文件，规划器照旧背着历史版本走路——数据 compaction 与元数据维护是两套清理账。

## 背诵要点
- 小文件三层代价：list/manifest 元数据 O(文件数)、读取效率、下游 task 数；第一个信号常是 list P99 超时。
- 合并触发：平均文件 < 目标 1/3 或单分区 > 1000 文件；目标 128-512MB；合并 IO = 分区数据 ×2，按分区滚动并错峰。
- 预防（写入攒批，损失新鲜度）vs 治理（定时 compaction，常付集群成本）按"读多还是写多"选；表格式元数据清理（expire snapshots）不可省。

## 复盘追问
- 为什么"每个任务写几十个小文件"在小规模时没暴露？提示：几百文件时 list 与 task 开销都在噪声内，代价是 O(文件数) 的线性增长，三个月的累积才越过阈值——容量账要按增长率提前算。
- 合并落后于写入会怎样收敛？提示：查询越来越慢 → 更多人补合并任务 → 集群更挤 → 合并更慢，正反馈恶化；所以 compaction 有 SLA 与并发上限，宁可排队也不挤爆窗口。
