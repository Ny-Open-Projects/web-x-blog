### Q7062 · 指标口径治理与单一事实源

难度：P6 | 标签：指标治理、数据口径、工程化

**问**：同一个"转化率"，增长团队算出 5%，商业化算出 8%，谁对？指标口径漂移的机制是什么？"单一事实源"在代码层怎么落地？

**答**：
- **结论**：大概率都对——各自分子分母口径不同（去重窗口、是否含测试订单、时区边界）。口径漂移的机制：指标定义散落在各报表的临时 SQL/notebook 里，业务规则变了只改了一处。代码层落地：指标注册表（name → 计算函数 + 单位 + owner + 版本）作为唯一事实源，所有报表从注册表取口径；同名指标重复定义直接报错，逼口径冲突在代码评审阶段暴露，而不是在周会上对数时。
- **取舍**：注册表放代码仓库（评审可控、随代码发布）vs 放指标平台/数仓语义层（非技术同学可查）。Python 工程常见组合：核心指标定义在仓库 + 定期同步到 BI 语义层；临时分析允许"探索口径"，但只要被两个以上报表引用就必须晋级为注册指标。
- **实战**：治理抓手：① 每个指标强制 owner 与文档（分母分子定义、去重窗口）；② 上线前跑"口径回归"：用固定事件流算指标快照，规则变更时 diff 显式确认；③ 看板标注数据来源与口径版本，杜绝截图对比传播的"数字打架"。

```python
"""指标口径单一事实源：指标只定义一次，报表全部从注册表取。"""
from dataclasses import dataclass
from typing import Callable

@dataclass(frozen=True)
class Metric:
    name: str
    unit: str
    fn: Callable[[list[dict]], float]     # 事件流 -> 指标值
    owner: str

REGISTRY: dict[str, Metric] = {}

def metric(name, unit, owner):
    def deco(fn):
        if name in REGISTRY:
            raise ValueError(f"指标重复定义: {name}")
        REGISTRY[name] = Metric(name, unit, fn, owner)
        return fn
    return deco

@metric("pay_conversion", "%", "growth")
def pay_conversion(events):
    pv = sum(1 for e in events if e["type"] == "pv")
    pay = sum(1 for e in events if e["type"] == "pay")
    return round(pay / pv * 100, 2) if pv else 0.0

@metric("arpu", "yuan", "monetize")
def arpu(events):
    users = {e["uid"] for e in events if e["type"] == "pay"}
    return round(sum(e["amount"] for e in events if e["type"] == "pay") / max(len(users), 1), 2)

events = [
    {"type": "pv", "uid": "u1", "amount": 0},
    {"type": "pv", "uid": "u2", "amount": 0},
    {"type": "pay", "uid": "u1", "amount": 30},
    {"type": "pay", "uid": "u1", "amount": 20},
]
print({n: m.fn(events) for n, m in REGISTRY.items()})

try:
    metric("pay_conversion", "%", "ads")(lambda e: 0)   # 另一团队重新定义同名指标
except ValueError as e:
    print("口径冲突拦截:", e)
print("报表取口径:", pay_conversion(events))
```

**追问链**：
1. 追问一层：指标口径变更怎么做灰度？——注册表带版本号，新口径先以 `metric_v2` 双跑一个周期，报表标注版本，确认后再切换并在周报说明口径变化原因。
2. 追问二层：为什么"去重窗口"是最常见的口径分歧点？——转化率涉及"多长时间内付费算转化"（7 日 vs 30 日），分子分母窗口不同差异可达数倍，且都不算错——所以窗口必须写进指标文档并成为定义的一部分。

**背诵要点**：
1. 数字打架多因口径不同，不是有人算错；分歧点常在去重窗口与时区。
2. 指标注册表 = 单一事实源：name+fn+unit+owner，重名即报错。
3. 口径变更走版本化双跑回归，报表标注口径版本。

**复盘追问**：
1. 两个报表的转化率差 3 个点，你怎么在半天内定位口径差异？（追分子分母的 SQL 到源头 diff 过滤条件与去重窗口）
2. 为什么"临时 SQL 跑出来的数"不允许直接进汇报？（无口径版本与 owner，无法复现与审计）
