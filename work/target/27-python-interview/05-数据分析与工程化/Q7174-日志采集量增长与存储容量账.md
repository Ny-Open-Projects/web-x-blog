### Q7174 · 日志量三年涨十倍：采集、存储与索引的容量账

难度：P6 ｜ 标签：容量规划、日志体系、保留策略
基线：通用观测体系（采集代理 filebeat/vector，存储按 GB/月计费）；Python logging 基线。

**问**：业务从 100 台实例涨到 800 台，日志平台月账单从 2 万涨到 25 万，最近开始丢日志、查询超时。日志的容量账应该按哪几个维度算？哪些杠杆能把账压下来而不丢关键信息？

**答**：**结论**：日志容量账分三段算：① **产生端**——每实例每秒日志条数 × 平均条长 × 实例数；② **传输端**——采集代理的批处理吞吐与背压（丢日志多发生在代理批满或下游限流时）；③ **存储端**——原始量 × 保留天数 × 索引开销（全文索引的存储通常是原始量的 2-3 倍）。压账杠杆按收益排序：**分级采样**（DEBUG 级按 1-10% 采样）> **结构化瘦身**（去掉重复上下文字段，条长常能砍 40%）> **冷热分层**（7 天热查询全文索引，31 天后转对象存储只存原文）> **保留期治理**（多数 DEBUG 日志 3 天就该死）。丢日志的根因常不是容量不够，而是**代理背压被静默丢弃**——采集层要有 dropped 计数并报警。

**取舍**：采样有代价：低频异常恰好被采掉的概率上升，排障时"日志刚好没有"比没有日志系统更恼人。缓解是**异常不采样**——错误级与 trace 上有标记的请求全量保留，只采样成功路径的 INFO/DEBUG。冷分层的代价是查询慢（分钟级拉取）与格式迁移成本，因此分层决策必须按"查询频率分布"数据定，不是拍一个天数。

**实战**：日志容量账与杠杆收益模拟（标准库）：

```python
# 日志容量账：产生 -> 传输 -> 存储 三段
import statistics

INSTANCES, EPS, LINE_B = 800, 5, 900        # 台数、每秒条数、平均条长
daily_raw_gb = INSTANCES * EPS * LINE_B * 86400 / 1e9
print(f"产生端: {daily_raw_gb:,.0f} GB/日 原始日志")

INDEX_OVERHEAD, RETAIN_HOT, RETAIN_COLD = 2.0, 7, 31
hot_gb = daily_raw_gb * (1 + INDEX_OVERHEAD) * RETAIN_HOT
cold_gb = daily_raw_gb * RETAIN_COLD
hot_price, cold_price = 2.5, 0.12           # 元/GB/月 示例
month_cost = hot_gb * hot_price + cold_gb * cold_price
print(f"存储端: 热索引 {hot_gb:,.0f} GB + 冷存 {cold_gb:,.0f} GB "
      f"-> {month_cost:,.0f} 元/月")

# 杠杆 1：DEBUG 采样 5%，条长瘦身 40%
debug_ratio, slim = 0.05, 0.6
sampled_daily = daily_raw_gb * (0.4 + 0.6 * debug_ratio) * slim  # 40% INFO 全量+60%部分采样
save = (daily_raw_gb - sampled_daily) / daily_raw_gb
new_cost = sampled_daily * (1 + INDEX_OVERHEAD) * RETAIN_HOT * hot_price \
         + sampled_daily * RETAIN_COLD * cold_price
print(f"采样+瘦身: 量降 {save*100:.0f}%，账单 {month_cost:,.0f} -> {new_cost:,.0f} 元/月")

# 传输端：代理背压与丢弃计数（必须监控的信号）
BATCH, FLUSH_S, PIPELINE = 8000, 5, 4       # 每批条数、刷写间隔、管道数
agent_cap = BATCH * PIPELINE / FLUSH_S
print(f"代理吞吐上限 {agent_cap:,.0f} 条/s，需求 {INSTANCES*EPS:,.0f} 条/s "
      f"-> {'余量充足' if agent_cap > INSTANCES*EPS*2 else '接近瓶颈，需扩代理'}")

# 异常不采样：错误级全量保留的存储增量
err_ratio = 0.002
err_extra = daily_raw_gb * err_ratio * (1 + INDEX_OVERHEAD) * RETAIN_HOT * hot_price
print(f"错误级全量保留增量仅 {err_extra:,.0f} 元/月 —— 排障保险值得买")
```

**追问 1**：为什么全文索引的存储开销是 2-3 倍？有没有更省的索引结构？
提示：倒排索引要为每个分词建 posting list 且常驻内存映射；可改列存+分区剪枝（如 ClickHouse/对象存储 + Parquet），代价是查询模式受限、模糊搜索弱。

**追问 2**：采集代理的"背压丢弃"和"下游限流拒绝"怎么区分监控？
提示：代理侧 dropped 计数（读追不上）与发送侧 429/timeout 计数（下游拒绝）分开打点；两者叠加的才是端到端丢失率。

**追问 3**：保留期治理怎么用数据决策而不是拍脑袋？
提示：统计历史日志的查询时间分布（P90 查询落在几天内）、按 trace-id 关联的回溯深度；多数体系 P99 查询 <14 天，超过 14 天的查询量通常 <1%，据此定热层 7-14 天。

## 背诵要点
1. 三段账：产生（条数×条长×实例）→ 传输（代理吞吐与背压）→ 存储（原始量×保留×索引 2-3 倍开销）。
2. 杠杆排序：分级采样（DEBUG 1-10%）> 结构化瘦身 > 冷热分层（7 天热/31 天冷）> 保留期治理；错误级全量保留的保险成本极低。
3. 丢日志先查代理背压：dropped 计数与下游 429 计数分开监控，端到端丢失率才可信。
