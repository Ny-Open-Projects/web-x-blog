### Q7048 · 成本工程：一套预发布环境一年 40 万，但有效使用率不到 8%

> 难度:★★★ | 标签:成本工程, 环境管理, 按需拉起

**问**：团队的预发布（staging）环境是完整复刻生产的一套服务，24 小时常驻，年度云成本 40 万。统计发现工作日 9-19 点之外几乎无人使用，真实使用率约 8%。有哪些成本结构可选？"按需拉起"的主要技术障碍是什么？为什么环境数不能无限增加？

**答**：结论：环境成本结构有三个档位——**常驻（最快反馈，利用率低是必然）**、**定时启停（把 24h 压到工作时间，成本立省 60-70%）**、**按需拉起（ephemeral 环境，每 PR/每分支一套，用完即毁，成本最低但冷启动要治理）**。选择依据是"反馈时长要求 × 使用集中度"；按需拉起的主要障碍是**依赖的共享有状态服务**（数据库、消息队列）不能每 PR 一套，解法是"无状态服务按需 + 有状态共享池/临时容器"。

机理与实战：
- **使用率的真相**：环境是给"人验证"用的，人的使用天然集中在工作时间；8% 使用率的常驻环境等于 92% 的钱在买空转。定时启停（夜间/周末缩容到 0）是把成本对齐使用分布的第一刀，实现只要 CI 定时任务改实例状态，零架构改动。
- **按需拉起的架构**：以 PR 为单位拉起一套带环境标识（`pr-1234` 前缀的命名空间/子域）的完整栈，合并即销毁。技术要点：① 配置注入用环境变量/overlay 而非改配置文件；② 数据依赖用"临时 DB 容器 + 种子数据"或共享 DB 的独立 schema；③ 冷启动治理——镜像预热（节点池提前拉取常用镜像）、依赖服务延迟拉起、健康检查并行化，把拉起时间从 15 分钟压到 3 分钟内，否则开发者宁可共用常驻环境。
- **共享有状态服务的坑**：临时环境共写一套 staging DB 会互相污染测试数据——要么每 PR 独立 schema + 种子回灌，要么明确"数据只读 + 变更走 mock/录制回放"。这是按需拉起方案里最容易被低估的工程量。
- **环境数治理**：每环境都有隐性成本（配置漂移检查、证书、监控接入），环境数 × 隐性成本线性增长；上限原则：环境数不超过"能在 15 分钟内从零拉起"的数量——拉不起来的环境就该合并。

```python
# 基线:Python 3.10+;纯标准库,三种环境成本结构对比与按需拉起账
from __future__ import annotations
from dataclasses import dataclass


@dataclass
class EnvProfile:
    monthly_cost: float          # 常驻月成本(元)
    use_ratio: float             # 有效使用率
    work_hours: int = 10         # 每日有效使用小时
    cold_start_min: float = 15.0 # 按需拉起冷启动
    prs_per_day: int = 12        # 需要环境的 PR 数


def always_on(p: EnvProfile) -> float:
    return p.monthly_cost * 12


def scheduled(p: EnvProfile, active_frac: float = 10 / 24 * (5 / 7)) -> float:
    """定时启停:只在工作时间+工作日供电(近似 ~30%)。"""
    return p.monthly_cost * 12 * active_frac


def ephemeral(p: EnvProfile, avg_env_hours: float = 3.0,
              spot_discount: float = 0.35, k8s_frac: float = 0.25) -> float:
    """按需拉起:每 PR 环境 3 小时生命周期,平均并发栈数折算月成本。"""
    fte_stacks = p.prs_per_day * avg_env_hours * (5 / 7) / 24   # 平均同时存在的环境栈数
    compute = p.monthly_cost * fte_stacks * spot_discount       # 按需实例单价≈常驻 0.35 折
    overhead = p.monthly_cost * k8s_frac                        # 控制面/存储/共享 DB 常驻
    return (compute + overhead) * 12


def demo() -> None:
    p = EnvProfile(monthly_cost=34000, use_ratio=0.08, prs_per_day=12)
    a, s, e = always_on(p), scheduled(p), ephemeral(p)
    print(f"常驻 24h:      {a:,.0f} 元/年 (使用率 {p.use_ratio:.0%})")
    print(f"定时启停:      {s:,.0f} 元/年 (省 {(1 - s / a):.0%})")
    print(f"按需拉起:      {e:,.0f} 元/年 (省 {(1 - e / a):.0%},冷启动 {p.cold_start_min}min)")
    assert s < a * 0.4 and e < a * 0.7
    # 冷启动治理:15min 无人愿等,压到 3min 才有采用率
    cold_ok = p.cold_start_min <= 3
    print(f"冷启动 {'达标,按需方案可行' if cold_ok else '过长,开发者会绕回常驻环境'}")
    assert not cold_ok  # 现状 15 分钟不可用,推动镜像预热+并行健康检查
    p2 = EnvProfile(monthly_cost=34000, use_ratio=0.08, cold_start_min=2.5, prs_per_day=12)
    assert ephemeral(p2) <= ephemeral(p)
    print("环境成本三档:常驻/定时/按需;冷启动 <3min 是按需方案的采用门槛 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：按需环境与生产"环境漂移"风险怎么控？
答：按需环境最大的漂移源是"配置 overlay 与生产不同步"——治理手段：① 环境定义即代码（同一份 Helm/Kustomize base + 参数 overlay），生产与预发布共用 base，禁止 fork；② 关键配置（副本数、资源额度）按环境比例缩放而非手写；③ 用 Q7019 的合成冒烟在拉起后自动验证核心链路，把"环境对不对"变成拉起流程的一部分。

**追问二**：为什么"多建几套常驻环境给不同团队"是反模式？
答：每套常驻环境的显性成本只有云账单，隐性成本（配置漂移、数据不同步、运维接入、安全面扩大）随环境数超线性增长；且团队间环境版本漂移会造成"A 环境能复现 B 环境不能"的诡异 bug 排查成本。正解是"一套基座 + 按需实例化"，把"多环境"的诉求转化为"多实例"——实例是无状态的、可销毁的，环境是有惯性的、会腐烂的。

## 背诵要点
- 环境成本三档：常驻（利用率 8% 是常态）→ 定时启停（对齐工作时间省 60-70%）→ 按 PR 按需拉起（省 70%+，用完即毁）。
- 按需拉起的门槛：冷启动 <3min（镜像预热+并行健康检查）；最大障碍是共享有状态依赖——独立 schema+种子回灌或 mock 回放。
- 环境定义即代码（共享 base+overlay）；环境数上限原则 = 15 分钟内能从零拉起的数量；"多环境"诉求转化为"多实例"。

## 复盘追问
- 为什么这套 40 万的常驻环境过去两年没人提出质疑？（提示：成本没有按团队/环境分摊记账，"公共成本"无人认领；成本治理第一步是把账单按环境维度打标签归因，让每个环境有 owner 和月度账单）
- 按需环境上线后，有人抱怨"环境里第三方回调（支付 webhook）打不通"怎么办？（提示：出站回调是按需环境的天然盲区——解法是回调录制回放（生产采样脱敏）+ 本地回调网关；复盘这类"依赖方向倒置"的用例要在方案设计期枚举，而不是上线后补）
