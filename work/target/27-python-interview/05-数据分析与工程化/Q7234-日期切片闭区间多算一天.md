### Q7234 · loc['11-23':'11-24'] 是闭区间：日报多算了一整天

难度：P6 ｜ 标签：pandas、DatetimeIndex、切片语义、区间

基线：Python 3.12；用 `datetime` 列表模拟 DatetimeIndex 的 partial string 切片与布尔掩码。

**问**：日报脚本写 `df.loc['2026-11-23':'2026-11-24']`，本意是取 23 号一天，结果每天的总量都比对账系统多一倍。同事说「pandas 切片是左闭右开」，于是换成 `df['2026-11-23':'2026-11-24']`，还是多；又试了 `df.loc['2026-11-23':'2026-11-24'].iloc[:-1]` 才对。到底是闭还是开？

**答**：
- **结论**：`.loc` 的标签切片是**两端都包含**的。对于 `DatetimeIndex`，字符串 "2026-11-24" 会被解析成"这一天的整个区间"（00:00:00 ~ 23:59:59.999…），所以 `'11-23':'11-24'` 取到的是 **23 日 00:00 到 24 日 23:59**，整整两天。它和 Python 列表切片、`range`、以及 numpy 的位置切片（左闭右开）语义不同，是 pandas 里最容易记混的一处。
- **取舍**：四种写法按场景选：① 单日就用 `df.loc['2026-11-24']`（partial string 直接命中一天），最不容易错；② 多日闭区间用 `df.loc['2026-11-23':'2026-11-24']` 并明确"含 24 日"；③ 需要半开区间（对齐 SQL 的 `>= AND <`）就用布尔掩码 `df[(df.index >= a) & (df.index < b)]`；④ 按列过滤用 `query` 时同样要注意日期边界。跨系统对账时统一用半开区间，能消掉"最后一天算不算"的扯皮。
- **实战**：① 把"日期区间"封装成一个函数（`date_range_mask(df, start, end_inclusive)`），全项目只走这一个入口；② 单测固定三条断言：边界日的 00:00 与 23:59 各一条记录，验证是否被包含；③ 对账差一倍时先怀疑"多算一天/少算一天"，再怀疑数据；④ 时区感知的索引上，partial string 还会先本地化再切片，跨时区报表要显式 `tz_convert` 到报表时区后再切。

```python
"""partial string 切片是闭区间：多算一天是怎么发生的。"""
from datetime import datetime, timedelta

START = datetime(2026, 11, 22)
ROWS = [(START + timedelta(hours=h), 1) for h in range(24 * 4)]   # 22~25 日，每小时 1 单


def loc_partial(rows, start_label: str, end_label: str):
    """模拟 df.loc['2026-11-23':'2026-11-24']：端点解析为整天，且两端都含。"""
    lo = datetime.fromisoformat(start_label)
    hi = datetime.fromisoformat(end_label) + timedelta(days=1) - timedelta(microseconds=1)
    return [r for r in rows if lo <= r[0] <= hi]


def loc_single_day(rows, day_label: str):
    """df.loc['2026-11-24']：只取一天。"""
    lo = datetime.fromisoformat(day_label)
    hi = lo + timedelta(days=1)
    return [r for r in rows if lo <= r[0] < hi]


def half_open(rows, start: datetime, end: datetime):
    """SQL 口径：>= start AND < end。"""
    return [r for r in rows if start <= r[0] < end]


if __name__ == "__main__":
    two_days = loc_partial(ROWS, "2026-11-23", "2026-11-24")
    one_day = loc_single_day(ROWS, "2026-11-24")
    sql_style = half_open(ROWS, datetime(2026, 11, 23), datetime(2026, 11, 24))

    print("loc['11-23':'11-24'] 行数:", len(two_days),
          "| 首条", two_days[0][0], "| 末条", two_days[-1][0])
    print("loc['11-24']          行数:", len(one_day),
          "| 首条", one_day[0][0], "| 末条", one_day[-1][0])
    print("半开 [11-23, 11-24)   行数:", len(sql_style),
          "| 末条", sql_style[-1][0])

    print("\n按日聚合同一份数据:")
    for label, subset in (("loc 闭区间", two_days), ("单日", one_day)):
        total = sum(v for _, v in subset)
        print(f"  {label:<10} 总量={total} -> 日报口径 {'翻倍' if total == 48 else '正确'}")
    print("结论：.loc 两端都含；要半开区间就自己写掩码，别指望切片语义")
```

**追问一**：为什么 `df[0:10]` 是左闭右开，`df['a':'b']` 却是两端都含？

→ 解析：`[]` 在 pandas 里是"重载到模糊"的入口：传入整数切片时走**位置**语义（跟 Python 列表一致，左闭右开），传入标签时走**标签**语义（`.loc` 等价，两端都含）。同一个 `df[a:b]` 因为 `a`/`b` 的类型不同而语义不同，这就是坑的根源。规避办法：永远显式写 `.iloc`（位置）或 `.loc`（标签），不要用裸 `[]` 做区间切片。

**追问二**：时区感知的 DatetimeIndex 上，partial string 切片的边界是本地时间还是 UTC？

→ 解析：切片字符串按**索引的时区**解释，先 `tz_localize` 到索引时区，再比较绝对时刻。所以 `df.loc['2026-11-24']` 在 `Asia/Shanghai` 索引上取的是 UTC 的 11-23 16:00 到 11-24 16:00。如果报表口径是 UTC 日、索引却是本地时区，就会整体错 8 小时、跨日数据错位。正确做法：报表前统一 `tz_convert('UTC')`（或报表时区）再切，并且把"口径时区"写进字段名/注释，别靠默契。
