### Q7190 · 多环境常驻与按需启停的成本分界账

难度：P6 ｜ 标签：成本工程、多环境、预览环境、启停调度

基线：K8s / 云主机；dev/staging/prod 环境拓扑；开源替代方案基线（如 vcluster/knative）。

**问**：公司有 dev、staging、QA 三个非生产环境，7×24 常驻，月底发现它们占了云账单的 40%，但工作时段利用率不到 15%。非生产环境这笔账怎么算？怎么在不破坏"随时能测"的前提下省下来？

**答**：
- **结论**：非生产环境的工作负载是"人驱动的"——每周 5 天 × 10 小时 ≈ 30% 的时间轴，实际利用率更低。账的分界点：**常驻月成本 = 机器价 × 720 小时；按时启停 ≈ 常驻 × 30%+冷启动开销**。168 小时/周里只用 50 小时，纯按需理论省 70%，实际因为"数据要保留、服务要预热、有定时任务"打七折，仍可省 40%~60%。手段梯度：定时启停（最简单，crontab/云调度器停 dev 和 QA 夜间周末）→ 按需拉起（PR 预览环境，merge 关闭）→ 环境合并（QA+dev 共用一套，用 namespace/feature flag 隔离）。
- **取舍**：启停的代价是"状态恢复时间"——数据库要保留数据就不能停（改用小型快照/降配实例），带状态中间件（Redis/ES）要么用托管降配要么接受重建；对"随时能测"的破坏用 SLA 补偿：启停自动化后从触发到可用 < 5 分钟，比"人肉找环境"更快。staging 若承载"发布前验证"的强需求，保持常驻但降配（流量只有生产 5%，不需要同规格）。
- **实战**：分界公式——`环境月成本 = Σ(实例规格×小时价×有效时长)`；先做"停机审计"：给每台非生产机器打标（谁在用/最近一次请求时间），30 天无流量的直接回收而不是继续启停。

```python
# 非生产环境成本分界：常驻 vs 定时启停 vs 按需（标准库可运行）。
def env_cost(instances: list[dict], mode: str,
             hourly_rate: float, work_hours_week: float = 50,
             overhead: float = 0.3, idle_recycle_days: int = 30) -> float:
    """instances: [{'spec':..., 'last_use_days': 最近使用距今天数, 'no_stop': 是否不能停}]"""
    total_core_hours = sum(i["spec"] for i in instances)
    # 30 天无流量实例直接回收
    active = [i for i in instances if i["last_use_days"] < idle_recycle_days]
    cost_cores = sum(i["spec"] for i in active)
    if mode == "常驻":
        return cost_cores * hourly_rate * 720
    if mode == "定时启停":
        # 不能停的（有状态）仍常驻
        nostop = sum(i["spec"] for i in active if i["no_stop"])
        stoppable = cost_cores - nostop
        return (nostop * 720 + stoppable * work_hours_week * 4.33 * (1 + overhead)) \
            * hourly_rate
    # 按需：所有可停的按实际使用时长（人触发，取 work_hours 的一半）
    nostop = sum(i["spec"] for i in active if i["no_stop"])
    stoppable = cost_cores - nostop
    return (nostop * 720 + stoppable * work_hours_week * 4.33 * 0.5 * (1 + overhead)) \
        * hourly_rate

if __name__ == "__main__":
    envs = [
        {"spec": 8, "last_use_days": 1, "no_stop": False},   # dev
        {"spec": 8, "last_use_days": 0, "no_stop": True},    # staging(带状态)
        {"spec": 4, "last_use_days": 45, "no_stop": False},  # QA: 45天没人用
    ]
    rate = 0.12
    for mode in ("常驻", "定时启停", "按需"):
        print(f"{mode}: {env_cost(envs, mode, rate):.0f} 元/月")
    # 常驻 1382 -> 定时启停 961 -> 按需 826；45 天无流量的 QA 实例被回收。
    # staging 带状态无法停，占掉大头——"环境合并/降配"是下一刀。
```

**追问**：
- 一层：为什么"利用率 15%"不能直接按 15% 算成本？→ 提示：实例按小时计费不按利用率；利用率说明的是"启停的可行性"，不是折扣系数。
- 二层：预览环境（每 PR 一套）的成本怎么控？→ 提示：TTL 自动销毁 + 共享数据层（一套库多 namespace）+ 资源配额上限，防止 PR 堆积成"隐形常驻"。
- 三层：非生产数据怎么处理才又省又合规？→ 提示：生产数据脱敏快照定期刷新替代全量常驻同步，小规格实例 + 大数据快照按需挂载。

**背诵要点**：
1. 非生产负载是人驱动的：时间轴可用率 ~30%，定时启停省 40%~60%，SLA 用"5 分钟可用"补偿。
2. 手段梯度：定时启停 > 按需/预览环境 > 环境合并；带状态服务降配常驻，无状态的停。
3. 先做停机审计：30 天无流量的实例直接回收，比任何优化都省。

**复盘追问**：
1. 为什么 40% 账单没人质疑过？提示：非生产成本没有 owner，按团队分摊的账目缺失；应给每个环境挂成本标签。
2. 启停自动化后"测不了"的投诉会来自哪里？提示：定时任务/数据刷新依赖常驻假设，启停清单要逐服务确认依赖。
