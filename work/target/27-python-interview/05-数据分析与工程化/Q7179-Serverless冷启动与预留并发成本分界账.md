### Q7179 · Serverless 的账：冷启动、预留并发与按量调用的成本分界

难度：P6 ｜ 标签：成本工程、Serverless、冷启动
基线：通用 FaaS 计费模型（按调用次数 + GB-秒；预留并发按秒计费不看调用量）；Python 3.12 运行时。

**问**：一个 Python 函数服务，白天 QPS 200、夜间几乎为 0，P99 延迟要求 300ms，而冷启动要 2s。全按量会炸延迟，全预留又会白烧钱。怎么算"预留多少、按量兜多少"的分界账？

**答**：**结论**：账的三个变量：**流量曲线形状、冷启动概率预算、单价差**。预留并发的单价通常是按量计费的"下限保障"——按 GB-秒全额计费（不管有没有调用），按量模式在无调用时不计费但每实例闲置超时后回收、下次请求吃冷启动。分界公式：设流量 P95 为 X QPS，要保 P99 延迟就必须让"预热实例数 ≥ 突发涌入的并发"，低于它的部分由按量+冷启动兜底。权衡点在**夜间零流量时段**：按量在这段近乎免费，预留却是 24 小时全额烧——所以最省的混合策略是**时段化预留**（白天预留 N 实例，夜间降为 0 靠按量），再配一个定时预热函数消掉"早晨第一波冷启动"。Python 的冷启动大头是 import：优化导入（懒加载重依赖、压缩部署包、避免顶层读盘）能把冷启动从 2s 压到 500ms 内，直接缩小必须预留的数量。

**取舍**：预留换来的不只是延迟还有**稳定性**：突发流量下按量扩容有实例创建速率限制，容易触发节流；预留实例不受扩容速率影响。混合策略的运维代价是"时段化"要跟业务日历走（节假日流量形状不同），漏调整就会出现预算内的延迟毛刺。另一个对冲：Provisioned 配置了 Neuron/GPU 的场景单价高一个数量级，时段化的收益也随之放大。

**实战**：预留/按量的分界账与冷启动优化账（标准库）：

```python
# Serverless 成本分界账：时段化预留 vs 全按量 vs 全预留
GB_SEC_PRICE, PROV_PREMIUM = 0.0000165, 1.0    # GB-秒单价；预留溢价系数
MEM_GB = 1.5
req_s, cold_s = 0.3, 2.0                        # 单请求 GB-秒、冷启动惩罚

HOURS = [(h, 200 if 9 <= h < 21 else 2) for h in range(24)]

def cost(hrs, prov_qps: dict[int, int]) -> float:
    """按量计全量；预留实例按 GB-秒 全额计费（含闲置）。"""
    total = 0.0
    for h, qps in hrs:
        p = prov_qps.get(h, 0)
        # 预留部分：p 个实例常驻整小时
        total += p * GB_SEC_PRICE * (1 + PROV_PREMIUM) * MEM_GB * 3600
        burst = max(0, qps - p * 50)            # 每实例承载 50 QPS
        total += burst * 3600 * req_s * GB_SEC_PRICE * MEM_GB
    return total

print(f"全按量（夜间也按量）: {cost(HOURS, {}):,.0f}")
full = {h: 200 for h in range(24)}
print(f"全预留 200 实例常驻: {cost(HOURS, full):,.0f}")
day_only = {h: 200 for h, _ in HOURS if 9 <= h < 21}
print(f"时段化预留（白天 200/夜间 0）: {cost(HOURS, day_only):,.0f}")

# 冷启动概率账：按量兜底部分的冷启动率
arrival_rate = 50                    # 突发超出预留的 QPS
instance_reuse_s = 300               # 实例闲置 5 分钟回收
cold_prob = arrival_rate * instance_reuse_s / (arrival_rate * instance_reuse_s + 1_000)
print(f"按量兜底部分冷启动概率 ~{cold_prob*100:.0f}%，"
      f"P99 = {req_s*1000:.0f}ms + {cold_prob*100:.0f}%×{cold_s*1000:.0f}ms")

# 冷启动优化账：import 懒加载把 cold_s 压到 0.5
print(f"若 import 优化把冷启动压到 0.5s，可少预留 "
      f"~{int((2.0-0.5)/0.3)} 成实例 -> 再省一笔")
```

**追问 1**：Python FaaS 冷启动的时间构成是什么？最大头通常在哪？
提示：拉容器镜像/沙箱创建 < import 依赖 < 首次初始化（建连接、加载模型）；重依赖（pandas/numpy/ML 库）的 import 常占 1s+，懒加载与分层包（层缓存）是第一杠杆。

**追问 2**：为什么预留实例不受扩容节流影响？扩容速率限制的触发条件是什么？
提示：FaaS 的实例创建有每秒新增实例上限（保护底层资源）；流量斜率超过该上限时新请求排队（表现为 P99 尖刺），预留实例已存在故绕过。

**追问 3**：时段化预留怎么和发布流程兼容？
提示：发布替换实例时段要保持预热（新版本实例需重新预热）；用版本别名 + 预热函数在发布后立刻按目标并发调用一次，避免发布后第一波冷启动。

## 背诵要点
1. 分界由流量曲线、延迟预算、单价差决定：预留按 GB-秒全额计（含闲置），按量无调用不计费但吃冷启动——时段化预留通常最省。
2. Python 冷启动大头是重依赖 import：懒加载、部署包分层、压缩包体可把 2s 压到 0.5s，直接缩小预留数量。
3. 预留实例绕过扩容节流；发布后要重新预热新版本实例，时段化配置须跟业务日历联动。
