### Q7041 · 事故复盘：一次"随手 pip install"是怎么弄挂生产数据管道的？

> 难度:★★★ | 标签:事故复盘, 环境隔离, 依赖管理

**问**：运维在跑定时数据管道的机器上为验证一个脚本随手 `pip install requests`，之后该管道每隔几天随机失败一次。事故链条是什么？"共享环境里装包"为什么是高危操作？怎么从流程和工具上根治？

**答**：结论：事故链条是 **pip 把某个已被管道依赖的包升级到了不兼容版本**（pip 默认 resolver 会为满足新包依赖而升级已装的传递依赖，如把 pydantic 1.x 升到 2.x），定时管道下一次启动即加载失败或行为漂移；失败"每隔几天"是因为不同任务 import 顺序不同、部分任务对版本敏感部分不敏感——典型的环境漂移事故。根治三板斧：**一切安装进独立 venv、锁定文件作为唯一事实源、共享机器上的临时操作用一次性容器**。

机理与实战：
- **pip 的升级语义**：`pip install X` 默认会升级 X 的依赖以解析冲突（除非 `--no-deps` 或先装约束文件），所以"只装一个小包"在共享环境里等价于"随机升级若干包"。PEP 668（externally-managed-environment）正是为此让系统 Python 拒绝 pip 直接安装。
- **为什么复现难**：失败是"下次进程启动才发生"，且不同入口 import 链不同；故障时间与安装时间脱钩，复盘靠审计 pip 历史日志（pip 9+ 的 install log）才能对上。
- **流程根治**：① 生产机器禁止人手 pip install，变更走 CI 构建出的 wheel/镜像；② 每个 systemd 定时任务声明自己的 venv（`ExecStart=/opt/jobs/venv-etl/bin/python job.py`），环境随任务锁死；③ 应急验证用 `uv run --with requests script.py` 或一次性 docker run，用完即弃、零残留。
- **检测兜底**：定时任务启动时校验 lock 文件哈希与环境实际安装 diff（环境漂移检查），不一致直接拒绝启动并告警——把"静默漂移"变成"显式失败"。

```python
# 基线:Python 3.10+;纯标准库,任务启动前的环境锁定校验(lock 哈希比对)
from __future__ import annotations
import hashlib
import json
from pathlib import Path


def lock_fingerprint(requirements_txt: str) -> str:
    """锁定文件指纹:pip freeze 输出做哈希,作为环境契约。"""
    lines = sorted(l.strip() for l in requirements_txt.splitlines() if l.strip())
    return hashlib.sha256("\n".join(lines).encode()).hexdigest()[:16]


def installed_snapshot(site_packages: Path) -> dict[str, str]:
    """读取 dist-info 目录得到实际安装版本(模拟 pip freeze)。"""
    out: dict[str, str] = {}
    for d in site_packages.glob("*.dist-info"):
        stem = d.name[: -len(".dist-info")]
        name, _, ver = stem.rpartition("-")
        out[name.replace("_", "-").lower()] = ver
    return out


def verify(lock_path: Path, site_packages: Path) -> bool:
    """定时任务启动门禁:锁定文件与实际安装 diff,不一致拒绝启动。"""
    lock_text = lock_path.read_text(encoding="utf-8")
    lock = dict(
        line.split("==", 1) for line in lock_text.splitlines() if "==" in line
    )
    actual = installed_snapshot(site_packages)
    drift = {k: (lock.get(k), actual.get(k))
             for k in set(lock) | set(actual)
             if lock.get(k) != actual.get(k)}
    if drift:
        print(f"[拒绝启动] 环境漂移: {json.dumps(drift, ensure_ascii=False, indent=1)}")
        return False
    print("环境与锁定文件一致,放行启动")
    return True


def demo(tmp_path: Path) -> None:
    lock = tmp_path / "requirements.lock"
    lock.write_text("pydantic==1.10.13\nrequests==2.31.0\n", encoding="utf-8")
    site = tmp_path / "site-packages"
    site.mkdir()
    (site / "pydantic-1.10.13.dist-info").mkdir()
    (site / "requests-2.31.0.dist-info").mkdir()
    assert verify(lock, site) is True

    # 事故现场:有人 pip install 把 pydantic 顶到 2.x(旧版本被卸载)
    (site / "pydantic-1.10.13.dist-info").rmdir()
    (site / "pydantic-2.5.0.dist-info").mkdir()
    assert verify(lock, site) is False   # 启动门禁拦下
    fp = lock_fingerprint(lock.read_text(encoding="utf-8"))
    assert len(fp) == 16
    print("环境锁定门禁:漂移显式失败,不再静默 ✅")


if __name__ == "__main__":
    import tempfile
    with tempfile.TemporaryDirectory() as td:
        demo(Path(td))
```

**追问一**：为什么 pip 的依赖解析结果不稳定，而 uv/pip-tools 可以？
答：pip 经典 resolver 是"按当前环境现状 + 顺序"解析，同一组 requirements 在不同机器上可能得到不同版本集；uv/pip-tools 先做完整约束求解并**输出锁定文件**（精确到版本的传递依赖闭包），后续安装只按 lock 还原——求解一次、复用 N 次，这才是"可复现"的定义。

**追问二**：PEP 668 的 externally-managed-environment 标记解决什么问题？
答：让发行版管理的系统 Python（如 apt 装的 python3）直接拒绝 pip install，强制用户走 venv/pipx/发行版包。它把"装包弄坏系统工具链"（比如把系统 pip 自身升级到不兼容版本）从常见事故变成被禁止的操作——是生态层面对本类事故的制度化响应，3.11+ 的主流发行版镜像都已带此标记。

## 背诵要点
- `pip install X` 会为解析依赖升级已装包：共享环境随手装包 = 随机升级传递依赖，故障在"下次进程启动"才爆发，时间与操作脱钩。
- 根治三板斧：每任务独立 venv（systemd ExecStart 指定）、锁定文件为唯一事实源、临时验证用 `uv run --with` / 一次性容器零残留。
- 启动门禁：lock 文件指纹 vs 实际安装 diff，漂移即拒绝启动——把静默漂移变成显式失败。

## 复盘追问
- 为什么这台机器的"环境漂移检查"形同虚设？（提示：检查只对比了直接依赖没对比传递依赖，或检查频率是每天一次而任务重启是分钟级；门禁必须做在"每次启动"且比对完整闭包）
- 应急要立刻装一个包验证问题，但流程要走审批怎么平衡？（提示：给出免审批的一次性通道——容器或 uv 临时环境，操作不落盘不改变任何持久环境；合规靠"通道存在且被允许"而不是靠事后追责）
