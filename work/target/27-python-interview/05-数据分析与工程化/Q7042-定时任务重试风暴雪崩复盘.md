### Q7042 · 事故复盘：上游抖 2 分钟，我方 500 个定时任务怎么就雪崩了？

> 难度:★★★★ | 标签:事故复盘, 重试风暴, 熔断

**问**：某下游服务抖动 2 分钟后恢复，但本方 500 个每 5 分钟调度一次的数据采集任务在之后 40 分钟持续失败，最终把自己的 worker 池和数据库连接全部占满。重试风暴的放大机制是什么？重试策略和熔断该怎么配才是正确姿势？

**答**：结论：放大机制是**固定周期调度 × 无退避重试 × 任务排队**的三重叠加：抖动期积压的任务全部进入重试，恢复瞬间所有重试同步洪峰打向上游；同时每个任务重试占着 worker 与连接池，新的调度周期继续堆积，队列无限增长——上游已恢复但我方自己把自己打死。正确姿势：**指数退避 + 抖动（jitter）+ 上限次数 + 调度器侧并发预算与任务新鲜度淘汰（超龄任务直接丢弃）+ 上游级熔断**。

机理与实战：
- **同步重试是定时炸弹**：所有任务在同一时刻被上游同一个错误触发，重试天然同步化（thundering herd）；退避必须加随机抖动把重试时间摊开，退避上限要封顶（否则 2 分钟抖动变成 10 分钟才恢复）。
- **新鲜度淘汰**：数据采集类任务的价值随时间衰减，排队 40 分钟的任务做出来也没意义——队列满/任务超龄时丢新保旧（或丢旧保新，按业务定），而不是无限排队。"宁可少产出不许错产出"在调度层的表达就是 TTL。
- **熔断与半开**：失败率超过阈值（如 50%/30s 窗口）时熔断整个"对上游 X"的重试域，熔断期间任务标记为 skipped 并产生补偿任务；半开期放小流量探测。注意熔断粒度是"上游"不是"任务"——500 个任务共享熔断状态才能拦住群死群伤。
- **预算闭环**：worker 池按"上游 QPS 预算"反推并发数，而不是按任务数；重试流量单独计数并在预算里预留 30%，保证重试不挤占首跑。

```python
# 基线:Python 3.10+;纯标准库,指数退避+抖动重试与全局熔断的调度骨架
from __future__ import annotations
import random
import time
from collections import deque


class CircuitBreaker:
    """上游级熔断:500 个任务共享一个状态。"""

    def __init__(self, window: int = 30, fail_rate: float = 0.5,
                 open_seconds: float = 20.0) -> None:
        self.events: deque[tuple[float, bool]] = deque()
        self.window, self.fail_rate = window, fail_rate
        self.open_seconds = open_seconds
        self.opened_at = -1e12  # 初始未熔断

    def allow(self, now: float) -> bool:
        if now - self.opened_at < self.open_seconds:
            return False  # open:全拒
        return True

    def record(self, now: float, ok: bool) -> None:
        self.events.append((now, ok))
        while self.events and self.events[0][0] < now - self.window:
            self.events.popleft()
        recent = [ok for _, ok in self.events]
        if len(recent) >= 5 and recent.count(False) / len(recent) > self.fail_rate:
            self.opened_at = now  # 熔断打开


def backoff(attempt: int, base: float = 1.0, cap: float = 8.0) -> float:
    """指数退避 + 抖动:2^n 封顶,抖动把洪峰摊开。"""
    return min(cap, base * 2 ** attempt) * random.uniform(0.5, 1.5)


def run_task(name: str, upstream: "callable", clock: list[float],
             breaker: CircuitBreaker, due_time: float = 0.0,
             max_retry: int = 3, queue_ttl: float = 300.0) -> str:
    if clock[0] - due_time > queue_ttl:
        return "expired"  # 新鲜度淘汰:排队超龄直接丢弃并登记补偿
    for attempt in range(max_retry + 1):
        now = clock[0]
        if not breaker.allow(now):
            return "skipped-by-breaker"   # 熔断期直接跳过,产生补偿任务
        ok = upstream(now)
        breaker.record(now, ok)
        if ok:
            return f"ok@attempt{attempt}"
        if attempt < max_retry:
            clock[0] += backoff(attempt)  # 退避后再试
    return "failed"


def demo() -> None:
    random.seed(7)
    br = CircuitBreaker(open_seconds=15.0)
    # 上游抖动期:连续失败 → 30s 窗口失败率超 50% → 熔断打开
    for i in range(5):
        br.record(0.5 * i, ok=False)
    assert not br.allow(1.0)          # open:整个上游域全拒,任务跳过而非重试
    assert br.allow(17.5)             # 超过 open_seconds 后恢复放行(半开)
    # 熔断期进入的任务被跳过,而不是叠加重试
    t = [2.0]
    def upstream(now: float) -> bool:
        return now >= 25.0            # 上游 25s 后才恢复
    r = run_task("job-a", upstream, t, br)
    assert r == "skipped-by-breaker"
    # 恢复后:退避+抖动可用,且指数封顶生效
    assert backoff(10) <= 8.0 * 1.5
    t2 = [100.0]
    r2 = run_task("job-b", lambda now: True, t2, br)
    assert r2.startswith("ok")
    print("重试风暴防御:退避+抖动+上游级熔断跳过+TTL 淘汰 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：为什么退避封顶很重要，"无上限指数退避"会出什么问题？
答：无上限退避让第 n 次重试延迟 2^n 秒，10 次重试就是 17 分钟——上游 2 分钟就恢复了，任务却在按天文退避干等，恢复时间反而被自己的重试策略拉长；且队列里堆积的长退避任务让"新鲜度"全部过期。封顶（如 8-30s）保证恢复后能快速收敛，抖动保证收敛过程不形成新的同步洪峰。

**追问二**：熔断期间被跳过的任务怎么保证不丢数据？
答：跳过 ≠ 丢失：熔断跳过的任务要登记为"补偿任务"（记一笔到补偿队列/表），熔断恢复后按新鲜度策略决定重跑或跳过；同时补偿任务的优先级要低于常规调度，避免恢复瞬间的补偿洪峰再次打崩上游。这是"宁可少产出不许错产出"的完整闭环。

## 背诵要点
- 风暴放大公式：固定周期调度 × 同步重试 × 无限排队——上游恢复后我方持续自伤；退避必加 jitter 摊开洪峰且封顶（8-30s）。
- 队列要有 TTL 新鲜度淘汰：超龄任务丢弃并登记补偿，不无限排队；重试流量单独计数预留 30% 预算。
- 熔断粒度是"上游"不是单任务：500 任务共享一个断路器，open 期全跳过+登记补偿，半开小流量探测。

## 复盘追问
- 为什么上游恢复 2 分钟后我方又持续崩了 40 分钟？（提示：画时间线——积压队列×固定调度周期×无退避重试的正反馈环；任何一个环节加上限都能止血，复盘要指出三个都缺失）
- 这类事故的告警应该设在哪个指标上？（提示：不是任务失败率（抖动期必然高），而是"队列积压深度/任务等待时长"——积压是自伤的前兆信号，比失败率早 10 分钟发现）
