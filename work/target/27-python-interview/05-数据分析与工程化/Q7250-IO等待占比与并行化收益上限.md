### Q7250 · 任务变慢先问一句：IO 等待还是 CPU 计算，值不值得并行化

难度：P6 ｜ 标签：性能定位、IO 等待占比、CPU 密集、GIL、并行化收益

基线：Python 3.12；用计时样本分解任务各阶段的 CPU/IO 时间，估算线程池与进程池的收益上限。

**问**：ETL 任务的运行时长从 40 分钟涨到 90 分钟。同事第一反应是"加 worker 并行"，加到 16 个进程后几乎没变快。怎么判定任务到底慢在哪？怎么在动手并行化之前，算出并行的收益上限？IO 等待占比和 CPU 占比分别指向什么优化？

**答**：
- **结论**：判定工具是**阶段计时分解**：把任务拆成下载/解析/转换/写库等阶段，每阶段记录 CPU 时间与墙钟时间，墙钟远大于 CPU 的就是 IO 等待。收益估算遵循两条铁律：① **IO 等待型**（占比高）→ 线程池/asyncio 可重叠等待，收益上限 ≈ 1/(CPU 占比)；② **CPU 型** → 受 GIL 限制线程无用武之地，必须进程池，收益上限 ≈ CPU 核数，且要扣除进程间数据序列化的税（Q2666 pickle 税）。如果单阶段就吃掉 80% 时长（比如慢 SQL），并行化其他阶段是无效功——先修单点（A131 的热点任务与长尾延迟同理）。
- **取舍**：① 并行度不是越大越好：IO 型并行度受下游连接数限制（Q7122 的 worker 与上游限流匹配），CPU 型受核数与内存限制；② 先消除串行点（单阶段占大头）再加并行，顺序反了白忙；③ 数据序列化成本会吃掉进程池收益：传大 DataFrame 给进程池前先算 pickle 账；④ 涨慢的原因常是数据量增长让某阶段从 O(内存) 变 O(磁盘)，并行掩盖不了复杂度问题。
- **实战**：① 在任务框架里内置阶段计时与占比输出，跑完自动打一行"CPU 32% / IO 61% / 瓶颈=写库"；② 并行化前先跑一版"收益上限估算"，低于 1.5 倍直接放弃，别空耗改造工时；③ 改完用固定数据集回归对比（Q7142 性能基线的思路），防止并行引入的调度开销把收益吃回去。

```python
"""阶段计时分解 + 并行收益上限估算（IO 型 vs CPU 型）。"""
import time
import os

Stage = dict


def profile_stages() -> list[Stage]:
    """模拟一次任务运行的阶段画像（真实场景由埋点采集）。"""
    wall = {"download": 600, "parse": 120, "transform": 900, "write_db": 1500}
    cpu = {"download": 30, "parse": 110, "transform": 850, "write_db": 60}
    return [{"stage": k, "wall_s": wall[k], "cpu_s": cpu[k],
             "wait_s": wall[k] - cpu[k]} for k in wall]


def estimate_gain(stages: list[Stage], cores: int = 8) -> list[Stage]:
    total_wall = sum(s["wall_s"] for s in stages)
    for s in stages:
        wait_ratio = s["wait_s"] / s["wall_s"] if s["wall_s"] else 0
        if wait_ratio > 0.5:                     # IO 等待型：线程可重叠等待
            s["type"] = "IO型"
            s["gain_cap"] = round(total_wall / (s["wall_s"] + s["cpu_s"] / 16), 2)
            s["tool"] = "线程池/asyncio（受下游连接数约束）"
        else:
            s["type"] = "CPU型"
            serial = s["wall_s"]
            best = max(1, cores - 0)             # 进程池上限≈核数
            s["gain_cap"] = round(serial / (serial / best + 0), 2)
            s["tool"] = "进程池（扣 pickle 税后打折）"
    return stages


if __name__ == "__main__":
    stages = estimate_gain(profile_stages())
    total = sum(s["wall_s"] for s in stages)
    total_cpu = sum(s["cpu_s"] for s in stages)
    print(f"总时长 {total}s | 总 CPU {total_cpu}s | 整体 IO 等待占比 "
          f"{(total - total_cpu) / total:.0%}\n")
    print(f"{'阶段':<10}{'墙钟':>7}{'CPU':>6}{'等待':>6}{'类型':>6}{'并行收益上限':>8}  建议")
    for s in sorted(stages, key=lambda x: -x["wall_s"]):
        print(f"{s['stage']:<10}{s['wall_s']:>6}s{s['cpu_s']:>5}s"
              f"{s['wait_s']:>5}s{s['type']:>6}{s['gain_cap']:>8}x  {s['tool']}")

    bottleneck = max(stages, key=lambda x: x["wall_s"])
    print(f"\n单点瓶颈: {bottleneck['stage']} 占 {bottleneck['wall_s'] / total:.0%} "
          f"-> 并行其他阶段收益有限, 先修它")
    print("结论：先分解再并行；IO 型收益上限=1/CPU占比, CPU 型上限=核数, 单点瓶颈优先")
```

**追问一**：为什么"CPU 32% / IO 61%"的任务，16 线程也没有跑到理论收益？

→ 解析：IO 型收益上限 1/CPU占比 ≈ 3x 是在"等待完全可重叠"的假设下，现实中会被三件事压低：① 下游连接数/限流——16 个并发写库撞上 `max_connections` 或上游限流，排队把重叠抵消（Q7122）；② 共享资源竞争——并发解析同一批大文件的内存翻倍，触发交换或 GC 风暴；③ 依赖链——下载分页之间有先后约束，重叠窗口本来就小。估算给的是上限，实测给的才是真值，两者差一倍以上时要查约束而不是调大并发。

**追问二**：怎么在任务框架里低成本地采集阶段画像？

→ 解析：一个上下文管理器就够：`with stage("write_db")` 记录进入/退出时刻，退出时输出墙钟；CPU 时间的采集用 `time.process_time()` 差值（进程级 CPU 时间），就能算出每阶段的等待占比。对 SQL 阶段再加一层驱动级 hook（Q6521 的 SQLAlchemy 事件钩子思路）把查询耗时单列。关键工程点：画像输出要固定格式进日志/指标，让"任务变慢"可以从历史画像直接对比出"哪个阶段占比变了"，而不是每次现场加 print 重跑。
