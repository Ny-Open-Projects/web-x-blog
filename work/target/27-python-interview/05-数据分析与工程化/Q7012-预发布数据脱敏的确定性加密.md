### Q7012 · 预发布数据脱敏

> 难度:★★★ | 标签:数据安全, 脱敏, FPE

**问**：预发布环境用生产数据副本做联调——「把手机号打星号」为什么不够？可逆映射（确定性加密/FPE）和不可逆脱敏（掩码/置空）各自适合什么字段，「关联字段脱敏后还能 join 吗」怎么保证，重放攻击（彩虹表）风险怎么压？

**答**：打星号的问题：① **破坏功能**：联调要真实格式的手机号（下游校验、短信 mock 都挂）；② **破坏关联性**：同一用户在 A 表打星、B 表没打（漏一处）或两表掩码方式不同 → join 不上，测试数据一致性崩。方案光谱：① **掩码/置空**（不可逆）：日志、展示类字段，无关联需求；② **确定性加密**（可逆，同输入→同密文）：关联字段（手机号/身份证）用它保持 join 能力——AES-SIV（合成 IV 防模式泄漏）优于普通 AES-ECB；③ **FPE（格式保留加密，FF1/FF3-1）**：密文仍像手机号/卡号，下游格式校验全通过——测试体验最好。彩虹表风险：确定性加密的字典空间小（11 位手机号 10^11），攻击者拿密文表爆破映射 → 缓解：**密钥分层**（每字段+每环境不同密钥）、盐加租户维度、密文禁出内网。架构上：脱敏做成**流水线任务**（ETL 一环）而非人工脚本——可审计、可重跑、规则版本化。

```python
# demo：确定性加密保 join + 手机号 FPE 风格映射（纯标准库模拟，生产用 FF3-1 库）
import hmac, hashlib

def det_encrypt(value: str, key: str, field_salt: str) -> str:
    """确定性加密（HMAC 模拟 AES-SIV 语义）：同输入同输出，跨表可 join。"""
    return hmac.new((key + field_salt).encode(), value.encode(), hashlib.sha256).hexdigest()[:16]

def fpe_phone(phone: str, key: str) -> str:
    """FPE 风格：输出仍是 11 位手机号形态（前 3 运营商位 + 随机化后 8 位）。"""
    h = hmac.new(key.encode(), phone.encode(), hashlib.sha256).digest()
    tail = str(int.from_bytes(h[:4], "big")).zfill(10)[-8:]
    return phone[:3] + tail            # 生产实现用 FF3-1（NIST SP 800-38G-1）

MASKS = {"email": lambda v: v.split("@")[0][:2] + "***@" + v.split("@")[1]}

def scrub_row(row: dict, key: str, rules: dict) -> dict:
    """流水线规则引擎：mask（不可逆）/ det（确定性可逆）/ fpe（保格式）。"""
    out = {}
    for field, v in row.items():
        rule = rules.get(field, "keep")
        if rule == "mask":
            out[field] = MASKS.get(field, lambda x: "***")(v)
        elif rule == "det":
            out[field] = det_encrypt(v, key, field)          # 关联字段
        elif rule == "fpe":
            out[field] = fpe_phone(v, key)
        else:
            out[field] = v
    return out

if __name__ == "__main__":
    key = "env-staging-key-v1"
    rules = {"phone": "fpe", "email": "mask", "user_id": "det"}
    rows = [{"phone": "13812345678", "email": "zhang@x.com", "user_id": "u42"},
            {"phone": "13899990000", "email": "li@x.com", "user_id": "u42"}]
    out = [scrub_row(r, key, rules) for r in rows]
    # 断言 1：确定性字段跨行可 join（同 user_id → 同密文）
    assert out[0]["user_id"] == out[1]["user_id"]
    # 断言 2：FPE 保格式（11 位、运营商段保留）
    assert len(out[0]["phone"]) == 11 and out[0]["phone"][:3] == "138"
    # 断言 3：掩码字段不可逆且格式正确
    assert "***" in out[0]["email"]
    print("脱敏流水线:", out[0])
    print("join 保持 / 格式保留 / 不可逆掩码 三断言全过 ✅")
    # 彩虹表缓解口径：字段级密钥（user_id 与 phone 不同 key）、密钥按环境隔离、
    # 密文值不出内网（测试数据平台内 join，前端展示层再 mask）。
```

**追问**：1) 为什么用 HMAC 而不是直接 AES 加密做确定性映射？——演示用 HMAC（单向，泄漏密文不可逆推出原文）比可逆 AES 更保守；真正需要解密回真实值（如客服排障）的场景才用可逆方案且密钥隔离。2) FPE 的域大小问题？——FF 算法要求域大小适中（NIST FF1 最低 radix^minlen），手机号 10^11 域小 → 理论可穷举映射，但配合强密钥与值域内盐成本可控；卡号 PAN 有 Luhn 约束更要专用 FPE 变体。3) 脱敏流水线怎么验证「没漏字段」？——schema 驱动：字段清单来自表结构（而非人工列表），新字段默认脱敏（deny-by-default），diff 报告进审计。

## 背诵要点
1. 掩码破坏功能与关联：联调数据用确定性加密（保 join）或 FPE（保格式），展示用掩码。
2. 确定性加密 = 同输入同密文（AES-SIV 优于 ECB 防模式泄漏）；彩虹表靠字段级密钥+盐+密文不出内网压。
3. 脱敏必须是 schema 驱动的 ETL 流水线（deny-by-default 新字段），不是人工脚本。

## 复盘追问
1. 测试环境泄漏了「已脱敏」数据却被还原，复盘根因会是什么？（提示：确定性映射 + 密钥进了仓库/CI 日志——密钥管理（KMS/注入）是脱敏方案的另一半）
2. 生产数据副本下发给第三方联调，策略差异？（提示：不可逆为主（无需 join 还原）、FPE 辅助 + 合同约束 + 水印埋点溯源）
