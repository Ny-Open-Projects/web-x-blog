### Q7185 · 日志 PII 脱敏遗漏导致数据泄露复盘

难度：P7 ｜ 标签：事故复盘、PII、日志治理、合规

基线：structlog 24+ / logging；日志平台检索权限模型。

**问**：安全团队在日志平台里检索出了用户手机号和身份证号——一次"排查方便"的 debug 日志把整个请求体打了出来，且已经留存 90 天。这类 PII 泄露事故怎么复盘？怎么从机制上保证"下一个 debug 日志不会再犯"？

**答**：
- **结论**：泄露链路是"打日志的人不知道字段是 PII + 日志系统没有出站门禁"。复盘归因不能停在"个人失误"，要落到三层机制：(1) **写入侧**：统一日志器对已知敏感字段（手机号/身份证/邮箱/token）做自动掩码，新增字段进敏感字典评审；(2) **出站侧**：日志采集管道加正则/分类器扫描，命中 PII 告警并可配置阻断；(3) **留存侧**：PII 字段短保留期（如 7 天）+ 检索权限最小化。debug 级日志默认不进生产采集，临时开加 TTL。
- **取舍**：自动掩码的代价是"误伤"——把正常业务字段也打码会影响排障；所以用"结构化日志 + 字段级白名单"而不是对整条消息做正则替换（自由文本里的 PII 只能靠扫描兜底）。完全消灭 PII 入日志不现实，目标是"可检测、短留存、窄权限"。
- **实战**：急救顺序——确认泄露范围（哪些字段/多久/谁检索过）→ 从日志平台删除或熔断该字段 → 评估是否触发合规上报 → 复盘会上把"敏感字段字典 + 掩码实现 + 出站扫描"列为整改项并给验收标准。

```python
# 结构化日志 PII 掩码处理器（标准库可运行，可平移到 structlog processor）。
import re

MASK_RULES = {
    "phone": re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)"),
    "id_card": re.compile(r"(?<!\d)\d{17}[\dXx](?!\d)"),
    "token": re.compile(r"(?i)(bearer\s+)[a-z0-9._-]{16,}"),
}

def mask_value(s: str) -> str:
    s = MASK_RULES["phone"].sub(lambda m: m.group()[:3] + "****" + m.group()[-4:], s)
    s = MASK_RULES["id_card"].sub(lambda m: m.group()[:4] + "**********" + m.group()[-2:], s)
    s = MASK_RULES["token"].sub(lambda m: m.group(1) + "***", s)
    return s

def process(event: dict, sensitive_keys: set[str]) -> dict:
    """字段级掩码：命中敏感键的值整体掩码；自由文本走正则兜底。"""
    out = {}
    for k, v in event.items():
        if k in sensitive_keys:
            out[k] = "***"
        elif isinstance(v, str):
            out[k] = mask_value(v)
        else:
            out[k] = v
    return out

def scan_pii(msg: str) -> list[str]:
    """出站扫描：返回命中的 PII 类型，管道据此告警/阻断。"""
    return [n for n, rx in MASK_RULES.items() if rx.search(msg)]

if __name__ == "__main__":
    event = {"msg": "user login ok", "phone": "13812345678",
             "detail": "Bearer abcdefghijklmnop1234"}
    print(process(event, sensitive_keys={"phone"}))
    print(scan_pii("收件人身份证 11010119900307425X 请查收"))
    # {'msg': 'user login ok', 'phone': '***', 'detail': 'Bearer ***'}
    # ['id_card']
```

**追问**：
- 一层：为什么字段级掩码比整条消息正则替换更可靠？→ 提示：结构化字段有明确语义，正则对变体（带空格/分隔符的手机号）漏报率高；文本兜底只做第二层。
- 二层：日志平台"删除已泄露数据"能做到什么程度？→ 提示：热存可删，冷备/对象存储副本与检索索引的清理要逐层确认，无法完全删除时以"权限收紧+合规记录"补偿。

**背诵要点**：
1. 泄露链路归因三层：写入侧字段掩码、出站侧扫描告警/阻断、留存侧短保留+窄权限。
2. 字段级掩码为主、文本正则兜底；debug 日志默认不进生产，临时开加 TTL。
3. 应急顺序：定范围 → 删数据/熔断字段 → 合规评估 → 机制整改带验收标准。

**复盘追问**：
1. 为什么 debug 日志能带着请求体进生产 90 天？提示：日志级别门禁与采集配置脱节，检查 level→采集 的映射策略。
2. 敏感字段字典怎么维护才不会腐化？提示：新表新字段接入 schema 评审时强制标注 PII 等级，日志器从标注自动生成掩码键。
