### Q7099 · 跨区/跨云数据传输出区流量成本账

难度：P6 ｜ 标签：成本工程 / 网络流量 / 数据管道

**问**：月底账单里"数据传输出区（Egress）"一项占了计算和存储总和的一半。排查发现一个数仓任务每天把 2TB 中间结果跨可用区拉取。出区流量费怎么算？架构上怎么消掉这笔钱？

**答**：
- **结论**：云厂商流量的价格梯度是：同可用区 < 跨可用区 < 跨区域 < 出公网（有的还有"出云到互联网"最贵）。出区费的可恶之处是"双向计费不对称"——入区免费、出区收费，导致把数据"拉"过来的架构（下游 pull 上游）比"推"过去的架构（上游 push 下游）天然多花钱，因为拉的方向总是从收费侧出。治理三板斧：① **计算靠近数据**——把计算任务调度到数据所在区域/可用区（数据重力原则），中间结果不跨区；② **压缩与列裁剪**——Parquet+zstd 通常能把传输量砍 5-10 倍，只传需要的列；③ **CDN/对等连接审价**——出公网的用户流量走 CDN、跨云对等连接按 GB 审价后可能比"先出公网再入"便宜（也有相反的，要逐价目表核对）。
- **取舍**：跨区冗余（灾备）与流量费的冲突：双活跨区副本每月流量费可能超过"单区 + 快速恢复"的损失期望，多数业务用"主区 + 跨区异步快照"而不是实时双写。中间结果共享：若多个下游都拉同一份上游数据，把"每次拉取"改成"一次性物化到下游侧"，传输次数从 N 降到 1。
- **实战**：步骤：① 从云账单 API 拉出区流量按"源-目的"维度分解，找 top 10 流量对；② 对每对流量标注业务归属与必要性（很多是历史架构遗留的每日全量同步）；③ 改造优先级 = 月流量费 × 改造难度倒数；④ 复盘项：数据平台新增跨区数据流要过"流量费评审"，把价格表做成内部工具而非口头约定。

```python
# 出区流量成本分解与改造收益计算器（纯标准库）
# 基线：Python 3.9+

PRICE = {  # 元/GB（示意）
    "same_az": 0.02, "cross_az": 0.10, "cross_region": 0.50, "internet": 0.80,
}


def monthly_cost(flows: list[dict]) -> dict:
    """flows: [{"name", "kind", "daily_gb"}]"""
    detail = {}
    for f in flows:
        c = f["daily_gb"] * 30 * PRICE[f["kind"]]
        detail[f["name"]] = round(c, 2)
    return detail


def optimize_savings(flows: list[dict]) -> list[dict]:
    """按改造收益排序的省钱建议"""
    plans = []
    for f in flows:
        cur = f["daily_gb"] * 30 * PRICE[f["kind"]]
        if f["kind"] == "internet" and f.get("cdn_ratio", 0) > 0:
            new = cur * (1 - f["cdn_ratio"] * 0.7)  # CDN 命中部分不走出区
            plans.append({"name": f["name"], "action": "上CDN",
                          "save": round(cur - new, 2)})
        elif f["kind"] in ("cross_az", "cross_region") and f.get("colocate"):
            new = f["daily_gb"] * 30 * PRICE["same_az"]
            plans.append({"name": f["name"], "action": "计算靠近数据",
                          "save": round(cur - new, 2)})
        elif f.get("compress"):
            new = cur / f["compress"]  # 压缩比
            plans.append({"name": f["name"], "action": "列裁剪+压缩",
                          "save": round(cur - new, 2)})
    return sorted(plans, key=lambda p: -p["save"])


def main() -> None:
    flows = [
        {"name": "dw中间结果跨区拉取", "kind": "cross_az", "daily_gb": 2000,
         "colocate": True},
        {"name": "报表数据出公网", "kind": "internet", "daily_gb": 100,
         "cdn_ratio": 0.8},
        {"name": "跨云同步", "kind": "cross_region", "daily_gb": 50,
         "compress": 6},
    ]
    cost = monthly_cost(flows)
    print(cost)
    assert cost["dw中间结果跨区拉取"] == 6000.0  # 2000*30*0.1
    plans = optimize_savings(flows)
    for p in plans:
        print(p["name"], "->", p["action"], "省", p["save"])
    # 计算靠近数据收益最大：省 6000-1200
    assert plans[0]["action"] == "计算靠近数据"
    assert plans[0]["save"] == 4800.0
    print("OK")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"数据重力"决定了架构成本结构？
→ 一句话提示：数据量大且只增不减，移动它永远比移动计算贵；调度器/管道设计的第一性问题就是"计算放数据旁边还是数据放计算旁边"，答案几乎总是前者。

**追问 2**：同可用区也有流量费的云厂商里，"零流量费"的极限是什么？
→ 一句话提示：同节点（本机进程间管道/共享内存）才真正免费，所以极致成本架构会把 ETL 与存储引擎合置（存储计算一体，如湖仓本地缓存），但可扩展性随之下降——这是成本与弹性的又一笔交换。

## 背诵要点
- 流量价格梯度：同 AZ < 跨 AZ < 跨区 < 出公网；入区免费出区收费，pull 型架构天然多付费。
- 治理三板斧：计算靠近数据（数据重力）、列裁剪 + 压缩（Parquet+zstd 砍 5-10 倍）、CDN/对等连接审价。
- 改造优先级 = 月流量费 × 改造难度倒数；新跨区数据流过"流量费评审"。

## 复盘追问
- 为什么跨区"每日全量同步"往往是历史遗留？提示：最初数据量小时全量同步够用，数据涨 100 倍后没人重审流量模式；增量同步/物化下游是结构性修复，账单分解才能暴露这类沉睡成本。
- 双活跨区的流量费与灾备 RPO 怎么交换？提示：实时双写 RPO 趋近 0 但跨区复制流量按月付费，异步快照 RPO 小时级但流量费低 1-2 个数量级；按业务损失期望选档位，别默认"越实时越好"。
