### Q7255 · 两个看板的 DAU 差 15%：指标口径字典与治理闭环

难度：P6 ｜ 标签：指标字典、口径治理、指标注册表、对账、数据质量

基线：Python 3.12；实现指标注册表（定义/owner/公式版本）+ 双实现对账，输出差异归因，全标准库实跑。

**问**：运营看板和分析师报表上的 DAU 差了 15%，查了三天才发现一个算"打开 App"、一个算"任意行为"，时间窗边界还差一小时。这类扯皮反复出现——问题不在某次实现，而在没有"口径的唯一事实源"。指标口径字典应该长什么样？怎么防止"字典写了没人看、SQL 里还是各自实现"？

**答**：
- **结论**：指标口径字典是**指标级注册表**，每个指标登记五件事：① **业务定义**（用非技术语言描述"数什么"：活跃=当日产生任意埋点行为的去重用户）；② **技术口径**（对应的过滤条件、时间窗边界、去重维度、时区）；③ **owner**（谁对口径负责、变更找谁）；④ **版本与变更记录**（口径什么时候改的、为什么改、历史口径指回哪里）；⑤ **标准实现**（生成 SQL/函数的模板，而不是一段描述文字）。治理闭环的关键是**字典可执行**：注册表里的技术口径直接驱动 SQL 生成，看板和报表引用同一个注册表函数——字典不是文档，是代码。对账机制兜底：同指标不同实现的两个数定期跑对账（本卡代码），差异超阈值自动归因到"时间窗/去重维度/过滤条件"三个高频差异源。
- **取舍**：① 字典的粒度：核心指标（DAU/GMV/留存）必进字典全登记，长尾指标允许"最小登记"（定义+owner），全量登记的维护成本会拖垮治理；② 标准实现 vs 描述文字：只有文字的字典一定会漂移，但强制所有指标可执行对简单指标过重——分级：核心指标可执行、其余登记描述；③ 口径变更要走评审（它改变所有人的数字），变更记录与双跑期（Q7034 口径钉死、Q7254 回溯成本）联动；④ 差异对账的成本：全指标天天对账太重，按指标重要性分层——核心指标日对账，其余周对。
- **实战**：① 新指标上线门禁：进字典+有 owner 才能上生产看板；② "字典双写"是漂移源头：注册表改了、实现函数没改，对账告警即暴露——对账不只是防下游野实现，也防注册表自己腐化；③ 差异归因模板化：先比对时间窗（最常见），再比对过滤条件，最后比对去重维度，三层排查脚本化；④ 治理周报：本周口径变更、对账差异、无主指标清单，让漂移可见。

```python
"""指标口径字典: 注册表 + 双实现对账 + 差异归因。"""
from dataclasses import dataclass, field


@dataclass
class MetricDef:
    name: str
    owner: str
    biz_def: str
    tech_def: dict                # 技术口径: 时间窗/过滤/去重
    version: int = 1
    history: list = field(default_factory=list)


REGISTRY: dict[str, MetricDef] = {
    "dau": MetricDef(
        name="dau", owner="data-team",
        biz_def="当日产生任意埋点行为的去重用户数",
        tech_def={"window": ("00:00", "24:00", "utc+8"),
                  "filter": "any_event", "dedup": "user_id"},
    ),
}


def dau_dashboard(events: list, tech: dict) -> set:
    """看板实现: 天然日窗(本地时区边界), 任意行为去重。"""
    return {e["user"] for e in events if e["ts_local"].date() == tech["day"]}


def dau_analyst(events: list, tech: dict) -> set:
    """分析师实现: 会话窗口(把 23:30 后的行为归入次日), 任意行为去重。"""
    out = set()
    for e in events:
        t = e["ts_local"]
        day = t.date() if t.hour < 23 else (t.date().toordinal() + 1)
        if day == tech["day"].toordinal() + (0 if t.hour < 23 else 1):
            out.add(e["user"])
    return out


def reconcile(events: list, day, a: set, b: set) -> dict:
    """对账: 双实现结果差异 + 三层归因。"""
    only_a, only_b = a - b, b - a
    reasons = []
    if only_a or only_b:
        # 归因第一层: 时间窗边界 (23 点后的行为归属)
        edge = [e for e in events if e["ts_local"].hour >= 23
                and (e["user"] in only_a or e["user"] in only_b)]
        if edge:
            reasons.append(f"时间窗边界: {len(edge)} 条 23 点后行为归属不一致")
        # 第二层: 过滤条件, 第三层: 去重维度 本例数据不触发
        if not reasons:
            reasons.append("过滤条件或去重维度差异")
    return {"dash_users": len(a), "analyst_users": len(b),
            "diff": len(only_a | only_b),
            "diff_ratio": len(only_a | only_b) / max(len(a | b), 1),
            "reasons": reasons}


if __name__ == "__main__":
    import datetime as dt
    D = dt.date(2026, 11, 23)

    def ts(h: int, m: int = 0) -> dict:
        return {"user": f"u{h}", "ts_local": datetime_local(h, m)}

    def datetime_local(h: int, m: int = 0):
        import datetime as d
        return d.datetime(D.year, D.month, D.day, h, m)

    events = [ts(h) for h in range(8, 24)]      # 8~23 点每点一个用户

    tech = dict(REGISTRY["dau"].tech_def, day=D)
    a = dau_dashboard(events, tech)
    b = dau_analyst(events, tech)
    rep = reconcile(events, D, a, b)
    print(f"看板 DAU={rep['dash_users']} | 分析师 DAU={rep['analyst_users']} "
          f"| 差异 {rep['diff']} 人 ({rep['diff_ratio']:.0%})")
    print(f"归因: {rep['reasons']}")
    print(f"owner: {REGISTRY['dau'].owner} | 口径版本: v{REGISTRY['dau'].version}")
    print("\n治理动作: 差异超阈值 -> 归因到时间窗 -> 统一进注册表技术口径 -> 版本+1")
    ok = rep["diff"] > 0 and rep["reasons"]
    print(f"校验: 双实现对账捕获口径漂移 -> {'通过' if ok else '异常'}")
    print("\n结论：口径字典=可执行的注册表而非文档; 核心指标日对账,")
    print("      差异归因按'时间窗->过滤->去重'三层脚本化排查")
```

**追问一**：字典如何驱动 SQL 生成，而不是让人看一眼再手写？

→ 解析：注册表的技术口径是结构化的（时间窗/过滤/去重/时区都是字段），模板引擎把它们映射成 SQL 片段：时间窗生成 `WHERE ts >= ... AND ts < ...`（注意右开区间，Q7234 闭区间多算一天的教训）、过滤生成 WHERE 条件、去重生成 `COUNT(DISTINCT ...)`。看板与报表调用同一个生成函数，口径变更只改注册表一处、版本号加一、重新发布——实现与定义从"两个世界"变成"一个世界"。执行起来的现实阻力是长尾指标太杂，所以分级策略：能结构化的进可执行通道，暂时不能的登记描述+owner+对账兜底，让"不可执行区"逐年收缩。

**追问二**：口径变更的评审要审什么？

→ 解析：五问：① 变更的业务动因是什么（决策需要还是看板美化）；② 影响面：哪些下游看板/报表/告警引用该指标（注册表的引用计数直接拉清单，Q1742）；③ 历史数据处理：回溯重算还是分界线（Q7254 的成本模型）；④ 双跑期怎么定：新口径先并行跑一段、与旧口径对账确认后切换，防"新口径实现本身有 bug"；⑤ 沟通：所有 owner 提前通知切换日与差异幅度。评审的产出物是变更记录写回注册表 history 字段——三个月后有人问"为什么 DAU 突然变了 8%"，答案直接可查，不用再考古三天。
