### Q7142 · 性能基线采集与噪声控制的容量账方法

难度：P6 ｜ 标签：容量规划 / 基准测试 / 统计

**问**：团队用"感觉快了/慢了"做容量与优化决策，偶尔拿压测数字对比却发现同一台机器同一份代码两次跑差 20%。怎么科学地建立性能基线：噪声从哪来、采样与统计口径怎么定、什么差异才可信到能写进容量决策？

**答**：
- **结论**：性能数字的噪声源四类：① **机器层**：CPU 频率漂移（省电/睿频）、其他进程抢占、页缓存温度（冷热缓存跑分差 2-10 倍）；② **Python 层**：GC 时机、JIT/pyc 缓存状态、随机数据分布；③ **环境层**：容器 CPU limit 抖动、同宿主邻居（云上 noisy neighbor）；④ **方法层**：样本太少、用均值被长尾绑架、预热不足把首次分配计入。科学口径五条：**预热**（丢掉前 N 次）、**多轮中位数**（median 比 mean 抗长尾）、**报告分位数与方差**（P50/P95 + 标准差，只报单值就是埋雷）、**固定变量**（同机同限同数据集，或随机化顺序对抗漂移）、**显著性判断**：两版本差异小于 2 倍测量方差时不可信——`信噪比 = (均值差/合并标准差) > 2` 才能写进决策。工具：`timeit`（内部已做重复与取最优，适合微基准）+ `statistics` 模块（stdev/median/quantiles）做自建宏基准。容量决策必须用"保守分位数"（如 P95 上再加 20% 余量），用最快一次跑分做容量账是系统性低估。
- **取舍**：timeit 的"取最优"口径与生产 P95 口径是两回事——微基准（算法层面比较）用 timeit 可接受，容量账必须用端到端多轮分布；自建宏基准（起真实服务打流量）成本高但口径对，微基准便宜但容易测了个寂寞。基准数据要长期留存（每版本 CI 跑基线，Q7047 CI 成本允许范围内），趋势比单次绝对值有用。
- **实战**：① CI 基线只跑冒烟级基准（防抖动烧 CI 分钟数），大基准跑在专用标定机（固定规格裸金属，消邻居噪声）；② 报告模板固定：P50/P95/σ/n/机器规格/温度条件，缺项的报告不进决策；③ 优化 PR 必须附"差异 > 2σ"的证据，否则合并理由不成立。

```python
# 性能基线采集: 预热 + 多轮中位数 + 显著性(信噪比>2) 判定
# 基线: Python 3.9+ 标准库 (statistics/timeit)
import random
import statistics
import time
from dataclasses import dataclass


@dataclass
class Bench:
    samples: list[float]        # 每轮耗时(ms), 已含预热剔除

    def report(self) -> dict:
        return {
            "p50": statistics.median(self.samples),
            "p95": statistics.quantiles(self.samples, n=20)[-1],
            "stdev": statistics.stdev(self.samples),
            "n": len(self.samples),
        }


def significant(a: Bench, b: Bench) -> bool:
    """两版本差异 > 2 倍合并标准差 才可信。"""
    ra, rb = a.report(), b.report()
    pooled = (ra["stdev"] ** 2 + rb["stdev"] ** 2) ** 0.5
    if pooled == 0:
        return ra["p50"] != rb["p50"]
    return abs(ra["p50"] - rb["p50"]) / pooled > 2


def run(fn, warmup: int = 3, rounds: int = 20,
        jitter: float = 0.2) -> Bench:
    """模拟真实环境的采样噪声 (+-jitter), 让显著性判定有意义。"""
    for _ in range(warmup):          # 预热: 剔除缓存温度/首次分配
        fn()
    out = []
    for _ in range(rounds):
        t0 = time.perf_counter()
        fn()
        base = (time.perf_counter() - t0) * 1000
        out.append(base * (1 + random.uniform(-jitter, jitter)))
    return Bench(out)


def work_v1() -> None:
    return sum(i * i for i in range(2000))


def work_v2() -> None:               # 优化版: 预计算平方
    return sum(x * x for x in range(2000))


def main() -> None:
    b1 = run(work_v1)
    b2 = run(work_v2)
    r = b1.report()
    assert r["n"] == 20 and r["stdev"] > 0
    # 同函数自比: 差异应在噪声内 -> 不可信为"优化"
    assert not significant(b1, run(work_v1)), "自比应被判为噪声"
    # 人为构造真实差异: 放大 5 倍耗时
    slow = Bench([x * 5 for x in b1.samples])
    assert significant(slow, b1), "5x 差异应显著"
    # 容量账用保守分位数: P95 加 20% 余量, 不用最快值
    capacity_input = r["p95"] * 1.2
    assert capacity_input > r["p50"]
    print(f"p50={r['p50']:.2f}ms p95={r['p95']:.2f}ms σ={r['stdev']:.2f} "
          f"n={r['n']}")
    print("OK: 预热+中位数+2σ 显著性; 容量按 P95x1.2 不按最快值")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 timeit 的"取最优"口径不能用于容量账？
→ 一句话提示：取最优代表"理想无干扰下限"，生产系统要在噪声中持续服务 P95/P99；容量账按保守分位数（P95×1.2），两者口径差数倍。

**追问 2**：云上共享宿主的 noisy neighbor 怎么处理？
→ 一句话提示：基准跑专用标定机（同规格裸金属或独占实例），或同一宿主内做 A/B 同跑（两版本交替运行对抗时间漂移）；跨机器比较差异毫无意义。

## 背诵要点
- 噪声四源：CPU 频率/抢占、GC/缓存温度、容器 limit 与邻居、样本不足用均值。
- 口径五条：预热丢前 N 轮、中位数 + P95 + σ 多指标、固定变量或交替 A/B、差异 > 2 倍合并标准差才显著、容量按 P95×1.2。
- 微基准 timeit（取最优）与容量宏基准（分位数分布）是两种口径，不混用；基线长期留存看趋势。

## 复盘追问
- 两次同代码跑分差 20%，先查什么？提示：n 是否太少（σ 大）、冷热缓存、CPU 频率策略与其他进程；先量化 σ 再谈差异，没有 σ 的对比就是猜。
- 如何防止"优化 PR 附的跑分"是 cherry-pick？提示：强制 CI 基线流水线产出（固定数据/机器/轮数），报告必须含 σ 与 n，人肉跑分不进评审依据。
