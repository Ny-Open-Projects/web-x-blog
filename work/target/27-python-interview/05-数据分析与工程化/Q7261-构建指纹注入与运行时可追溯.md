### Q7261 · 线上跑的到底是哪个版本：构建指纹注入与运行时可追溯

难度：P6 ｜ 标签：构建指纹、版本追溯、发布工程、构建时注入、部署对账

基线：Python 3.12；实现构建时生成 _build_info.py（commit+时间+依赖摘要）、运行时读取并与台账比对，全标准库实跑。

**问**：排查线上问题时要回答"这台实例跑的是哪个 commit 的代码"。看容器 tag 是 1.2.3，但 1.2.3 构建过几次（Q7259 的覆盖事故），源码目录可能被 checkout 到别的分支，`git log` 在部署产物里也不存在（镜像里根本没带 .git）。怎么让"运行中的进程"能**自证**自己的版本？构建指纹要包含什么？在哪一步注入？

**答**：
- **结论**：构建指纹是**构建产物里烙下的自我描述**：构建流水线的最后一步生成 `version.py`/`_build_info.py`（git commit SHA、构建时间、分支、依赖锁文件摘要、CI 构建号），打进包里；运行时模块直接 import 它，`/healthz` 或日志启动头把它暴露出来。四要素缺一不可：① **commit SHA** 定位代码；② **依赖摘要**（lock 文件 hash）——代码没变依赖变了的事故同样常见（Q7043 漂移）；③ **构建号/构建时间**——同一 commit 重复构建的区分；④ **注入时机在打包内**（build 阶段写文件进产物），不是运行时探测（运行时环境不可信：没有 .git、容器 tag 可重打）。有了指纹，三件事变可能：启动日志自报版本、健康端点可查、与发布台账（Q7259）做部署对账。
- **取舍**：① 注入文件 vs 环境变量：文件随产物走（镜像里天然存在、离线可查），环境变量依赖部署配置的正确性——文件为准、env 补充；② 指纹的粒度：monorepo 多包时要每个包独立指纹（对齐各自变更），别用仓库级一个指纹糊弄（Q1095 monorepo）；③ 构建可复现性：指纹里含时间戳会破坏"同输入同输出"的可复现构建——严格可复现场景把时间戳移出台账哈希部分，只做展示；④ 指纹泄露面：commit SHA 与内部结构对外暴露的安全考量，对外产物可只留版本号，指纹只进内部镜像。
- **实战**：① CI 模板固定一步"stamp build info"，漏打的构建在发布门禁拒绝（无指纹不上线）；② 启动日志第一行打印指纹，事故时 grep 日志秒定位版本；③ 部署对账巡检：每实例的指纹 vs 台账最新发布指纹，漂移即告警（Q7259 的幽灵 bug 侦测）；④ 依赖指纹与 lock 文件校验（Q7197 uv export 哈希锁定）联动，指纹不一致=依赖漂移。

```python
"""构建指纹注入与运行时追溯: 生成 version.py -> 运行时读取 -> 台账对账。"""
import hashlib
import json


def make_build_info(commit: str, branch: str, lock_hash: str, build_no: int) -> str:
    """构建末步: 生成可 import 的版本文件 (烙进产物)。"""
    info = {"commit": commit, "branch": branch,
            "deps": lock_hash, "build_no": build_no}
    payload = json.dumps(info, sort_keys=True)
    fingerprint = hashlib.sha256(payload.encode()).hexdigest()[:12]
    body = (
        f'FINGERPRINT = "{fingerprint}"\n'
        f'BUILD_INFO = {json.dumps(info, ensure_ascii=False, indent=4)}\n'
    )
    return body


class RuntimeProbe:
    """运行时: import 版本文件 (模拟 import), 提供自证接口。"""

    def __init__(self, fingerprint: str, build_info: dict):
        self.fingerprint = fingerprint
        self.build_info = build_info

    def healthz(self) -> dict:
        return {"version": self.fingerprint,
                "commit": self.build_info["commit"],
                "build_no": self.build_info["build_no"]}


class DeployLedger:
    """发布台账: 指纹 -> 发布记录。"""

    def __init__(self):
        self.records: dict[str, dict] = {}

    def register(self, fingerprint: str, note: str) -> None:
        self.records[fingerprint] = {"note": note}

    def reconcile(self, probe: RuntimeProbe) -> tuple[bool, str]:
        rec = self.records.get(probe.fingerprint)
        if rec is None:
            return False, f"指纹 {probe.fingerprint} 不在台账 -> 未知产物在运行!"
        return True, f"运行版本 {probe.fingerprint} 对应发布: {rec['note']}"


if __name__ == "__main__":
    # 构建侧: 同一 commit 两次构建 (依赖变更), 指纹应不同
    lock_v1 = hashlib.sha256(b"flask==2.3.0\nredis==5.0").hexdigest()[:8]
    lock_v2 = hashlib.sha256(b"flask==2.3.0\nredis==5.1").hexdigest()[:8]
    b1 = make_build_info("a1b2c3d", "main", lock_v1, 137)
    b2 = make_build_info("a1b2c3d", "main", lock_v2, 141)

    ns1, ns2 = {}, {}
    exec(b1, ns1)
    exec(b2, ns2)
    print(f"同 commit, 依赖变更: 指纹 {ns1['FINGERPRINT']} vs {ns2['FINGERPRINT']}")
    print(f"  指纹可区分 -> {'通过' if ns1['FINGERPRINT'] != ns2['FINGERPRINT'] else '异常'}")
    print(f"  构建信息: {ns1['BUILD_INFO']}")

    # 运行侧: healthz 自证 + 台账对账
    ledger = DeployLedger()
    ledger.register(ns1["FINGERPRINT"], "v1.2.3 build#137 (构建机A)")
    probe = RuntimeProbe(ns2["FINGERPRINT"], ns2["BUILD_INFO"])
    print(f"\nhealthz: {probe.healthz()}")
    ok, msg = ledger.reconcile(probe)
    print(f"对账: {ok} -> {msg}")

    # 负例: 未登记的指纹在运行 (Q7259 覆盖发布/手工替换产物)
    rogue = RuntimeProbe("deadbeef0000", {"commit": "?", "build_no": 0})
    ok2, msg2 = ledger.reconcile(rogue)
    print(f"未知产物: {ok2} -> {msg2}")
    print("\n结论：指纹在构建时烙进产物 (commit+依赖摘要+构建号),")
    print("      运行时自证 + 台账对账; 运行时探测 .git/tag 不可信")
```

**追问一**：为什么不能在运行时用 `git rev-parse` 或读容器 tag 自证？

→ 解析：三个不可信。① **产物里没有 .git**：Dockerfile 常规做法不拷贝 .git 目录（瘦身 + 不泄露历史），git 命令在容器里根本跑不了；② **容器 tag 可变**：同一个 tag 可以被重新指向新镜像（Q7259 覆盖发布的另一形态），tag 是可变引用，不是指纹；③ **部署环境的漂移**：镜像拉取有缓存、旧实例还跑着旧版本，环境"当前状态"与"这个进程"不是一回事。指纹必须在**构建时**从构建环境（有 .git、有 CI 上下文）采集，随产物烙死——产物自描述才不依赖环境。这也是为什么"指纹在健康端点"优先于"指纹在日志"：端点可被巡检脚本批量拉取，日志要翻。

**追问二**：monorepo 多服务怎么组织指纹？

→ 解析：每服务（包）独立指纹，构成"服务 → commit → 依赖摘要"三层：服务 A 和 B 可能同 commit 但依赖摘要不同（各自 requirements），必须能区分。联调事故里高频出现"A 调 B 报错，B 说代码没改"——对账时 A 的指纹显示依赖摘要变了，才是真凶。组织方式：构建系统在每个包的产物里写各自的 version.py，CI 发布清单记录"本次发布 = {serviceA: fp1, serviceB: fp2}"的映射，对账巡检按服务逐个核对。另外多服务共用一个"仓库级指纹"做粗对齐、包级指纹做细归因，两层都要——粗对齐回答"这次发布动了什么"，细归因回答"哪个服务的行为变了"。
