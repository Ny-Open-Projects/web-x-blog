### Q7047 · 成本工程：CI 月账单 6 万分钟，缓存命中率每提升 10% 省多少钱？

> 难度:★★★ | 标签:成本工程, CI 缓存, 账单归因

**问**：CI 月账单 6 万分钟、按分钟计费折合数万元，团队想优化。CI 成本怎么归因到"可优化的桶"？缓存命中率、并发矩阵、触发策略三个杠杆各省多少？为什么"把缓存调到 100%"通常是错误目标？

**答**：结论：CI 分钟账 = **Σ(每次触发 × 各阶段时长 × 并行度 × 单价系数)**，归因要按阶段拆桶：依赖安装（可缓存）、测试执行（可并行度调优/用例瘦身）、构建打包（可增量）、环境准备（可镜像固化）。缓存命中率 h 的节省 ≈ 安装阶段分钟数 × h 提升 × 触发次数，是最大且最便宜的桶；但"缓存 100%"意味着缓存了不该缓存的（带时效数据的步骤、会掩盖 flaky 的步骤），优化目标是**单位验证成本**不是命中率本身。

机理与实战：
- **归因先行**：从 CI 平台导出"阶段时长分布"（不是平均值，要看 P50/P99），找出"高频 × 长时长"的交叉项。典型发现：安装占 40% 分钟数（命中率仅 60%）、一个 20 分钟的 e2e 套件占了 30% 且大多在验证与本次变更无关的路径。
- **三大杠杆排序**：① 缓存（pip/uv cache、Docker layer cache）：安装从 8 分钟到 1 分钟，命中率 60%→90% 可省总账单 20-30%；② 触发策略：PR 上跑全套 e2e 是浪费——按变更影响面跑（Q7063 思路），paths-filter + 分层测试金字塔，可省 30-50%；③ 并行度：矩阵不是越大越好，xdist 分片要把"分片启动开销"算进去，4 分片不一定快过 2 分片。
- **并行度的隐性成本**：并发矩阵 n 路会把峰值并发压高，runner 排队又增加墙钟时间；且云上按分钟计费的"并发×时长"双线性——并行化省墙钟但可能涨账单，决策要看"总分钟数"与"开发者等待时长"两个指标同时优化。
- **缓存调到 100% 为什么错**：① 部分步骤天然不可缓存（拉最新数据做冒烟）；② 缓存 key 设计过粗会复用脏缓存，掩盖真实失败（flaky 变"稳定假绿"）；③ 缓存恢复时间随缓存体积增长，超大缓存的 restore 本身就要几分钟。正确目标是"命中率×恢复时长×正确性"三者的乘积最优。

```python
# 基线:Python 3.10+;纯标准库,CI 分钟账单分桶归因与杠杆收益估算
from __future__ import annotations
from dataclasses import dataclass


@dataclass
class Stage:
    name: str
    minutes: float          # 单次时长
    parallel: int = 1       # 并行度
    cacheable: bool = False
    cache_hit_rate: float = 0.0
    cost_factor: float = 1.0  # 计费系数(e2e 上真机 x2)


def stage_minutes(s: Stage) -> float:
    """缓存命中的阶段按命中率比例免跑(近似:命中即跳过)。"""
    eff = (1 - s.cache_hit_rate) if s.cacheable else 1.0
    return s.minutes * s.parallel * s.cost_factor * eff


def bill_per_run(stages: list[Stage]) -> float:
    return sum(stage_minutes(s) for s in stages)


def demo() -> None:
    stages = [
        Stage("install", 15.0, cacheable=True, cache_hit_rate=0.6),
        Stage("unit", 6.0, parallel=1),
        Stage("e2e", 15.0, parallel=1, cost_factor=2.0),
    ]
    base = bill_per_run(stages)
    # 杠杆一:缓存命中率 0.6 -> 0.9
    stages[0].cache_hit_rate = 0.9
    after_cache = bill_per_run(stages)
    # 杠杆二:e2e 按影响面只在命中路径跑,触发比例降到 30%(近似乘 0.3)
    after_e2e = after_cache - stage_minutes(stages[2]) * 0.7
    print(f"单次流水线分钟: {base:.1f}")
    print(f"缓存 0.6->0.9: {after_cache:.1f} (省 {(1 - after_cache / base):.0%})")
    print(f"e2e 影响面触发: {after_e2e:.1f} (累计省 {(1 - after_e2e / base):.0%})")
    assert after_cache < base                     # 缓存命中率提升必有节省
    assert after_e2e < base * 0.6                 # 影响面触发是更大杠杆
    # 反例:缓存 100% 不可达,且恢复时间随体积增长
    @dataclass
    class CacheCost:
        size_gb: float
        restore_min_per_gb: float = 0.08

        def restore_minutes(self) -> float:
            return self.size_gb * self.restore_min_per_gb
    cc = CacheCost(size_gb=30)
    assert cc.restore_minutes() >= 2  # 超大缓存恢复 2 分钟+,吃掉节省
    print("成本账:分桶归因->缓存->触发策略->并行度;目标是单位验证成本不是命中率 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：为什么归因要看 P99 而不是平均值？
答：账单按总分钟数算（均值敏感），但优化决策要看结构——P99 长尾通常来自少数几类任务（大矩阵 e2e、无缓存冷启动），抓住它们能一次砍掉大头；均值会被海量 2 分钟小任务稀释，掩盖"一小时级"的长尾浪费。账单优化是帕累托问题：按 P99 找高杠杆点，按总量验证收益。

**追问二**：并行化省了墙钟时间但账单涨了，怎么向管理层解释？
答：CI 有两个被优化对象：开发者等待时长（影响交付速度）与账单（成本）。并行化是拿钱换时间，方向正确但要控制边界——设定"单次流水线分钟数预算"，超过预算的任务强制 shard 化或影响面筛选；同时用"每 PR 平均分钟数"而非"月总分钟数"做趋势，因为月总量随人数增长是正常业务量，不是成本恶化。

## 背诵要点
- 分钟账 = Σ(触发 × 阶段时长 × 并行度 × 计费系数)，先按阶段分桶归因（看 P99 找长尾浪费），抓"高频×长时长"交叉项。
- 杠杆排序：缓存（安装 8→1 分钟，60%→90% 省账单 20-30%）→ 触发策略（影响面筛选省 30-50%）→ 并行度（省墙钟可能涨账单，双指标同看）。
- 缓存不是命中率越高越好：不可缓存步骤、脏缓存掩盖失败、超大缓存 restore 时间吃收益；目标是单位验证成本最优。

## 复盘追问
- 为什么团队总觉得"CI 慢"但账单分桶后安装只占 15%？（提示：人的体感是"我等待的那次"（排队+长尾），账单是全体均值；要用"开发者视角墙钟 P99"与"账单视角总分钟"两套指标分别归因，别混用）
- 缓存 key 用了 `requirements.txt` 哈希，为什么命中率只有 60%？（提示：锁文件里一个无关包变更就失效整个 key；正确做法是按 lock 分层缓存（基础层+变更层）或用 uv 的内容寻址缓存——缓存 key 粒度与依赖变更频率要匹配）
