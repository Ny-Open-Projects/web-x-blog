### Q7089 · 对象存储小文件泛滥的请求费成本账

难度：P6 ｜ 标签：对象存储 / 成本工程 / 数据管道

**问**：上游把数据按分钟切成小 Parquet 文件写入 S3/OSS，一年下来 8000 万个小文件。存储费看着不高，但月账单里"请求费"和"管理费"超了存储费。为什么？怎么治理？

**答**：
- **结论**：对象存储的成本模型是"存储单价 × 容量 + 请求单价 × 次数"。小文件让请求费暴走的路径有三条：① 下游扫描任务每个文件一次 LIST/GET，8000 万文件 × 每天多轮扫描 = 请求次数天文数字；② 生命周期管理/清单（inventory）计费按对象数，小文件数量 × 单价；③ 元数据压力使 LIST 分页次数暴涨。典型量级：1 个 100KB 小文件的年存储费不足 1 分钱，但每月 30 次 GET + LIST 摊派的请求费可超过存储费 10 倍。
- **取舍**：治理路线取舍：① 上游合并（攒批 5-15 分钟或按 128-512MB 目标大小合并）——改上游最有效但上游可能不受你控制；② 下游 Compaction（定期把小文件合并成大文件）——不动上游但引入计算成本与数据新鲜度延迟；③ 分区/前缀规划让 LIST 更快——只降延迟不降请求数。首选 ①，退而求 ②，且合并目标大小要匹配下游并行度（每个文件应约等于一个下游并行任务的处理量，太大反而造成倾斜）。
- **实战**：成本账公式：`月成本 = 容量 × 存储单价 + Σ(操作次数 × 单价) + 清单/管理费`。治理动作：给数据湖建"文件画像"任务（每周统计文件大小分布、平均大小 <32MB 告警）；按表建 Compaction 预算（合并计算费 vs 节省的请求费 ROI）；写下游时用分页+并发控制避免 LIST 风暴。

```python
# 小文件成本账与 Compaction ROI（纯标准库）
# 基线：Python 3.9+


def monthly_cost(files: int, avg_mb: float, storage_per_gb: float = 0.023,
                 get_per_million: float = 0.4, gets_per_file_month: int = 30) -> dict:
    storage = files * avg_mb / 1024 * storage_per_gb
    requests = files * gets_per_file_month / 1e6 * get_per_million
    return {"storage": storage, "requests": requests, "total": storage + requests}


def compaction_roi(files: int, avg_mb: float, target_mb: int = 256,
                   compute_cost_per_tb: float = 5.0) -> dict:
    compacted = files * avg_mb / target_mb
    data_tb = files * avg_mb / 1e6  # 读写两遍近似 2x
    compute = data_tb * 2 * compute_cost_per_tb
    before = monthly_cost(files, avg_mb)
    after = monthly_cost(compacted, target_mb)
    return {"monthly_saved": before["total"] - after["total"],
            "one_off_compute": compute,
            "payback_months": compute / max(0.01, before["total"] - after["total"])}


def main() -> None:
    c = monthly_cost(80_000_000, avg_mb=0.5)
    print({k: round(v) for k, v in c.items()})
    assert c["requests"] > c["storage"] * 5  # 请求费远超存储费
    roi = compaction_roi(80_000_000, 0.5)
    print(f"月省 {roi['monthly_saved']:,.0f}，回本 {roi['payback_months']:.1f} 月")
    assert roi["payback_months"] < 3


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"目标文件大小"要匹配下游并行度而不是越大越好？
→ 一句话提示：每个文件≈一个并行任务的调度单元，文件过大导致并行度不足与数据倾斜，过小回到请求费问题；通常取"下游单任务处理 60-120 秒"的数据量。

**追问 2**：Hive 风格分区对 LIST 请求费有什么影响？
→ 一句话提示：好分区前缀能把 LIST 范围裁剪到分区目录，避免全桶分页扫描；但分区本身过细（每分钟一个分区）会反向制造小文件，两者要一起设计。

## 背诵要点
- 对象存储成本 = 容量费 + 请求费 + 管理费；平均文件 <32MB 即小文件病，请求费可超存储费 10 倍。
- 治理优先级：上游攒批合并（128-512MB）> 下游 Compaction（算 ROI）> 前缀优化（只降延迟）。
- 目标文件大小按"下游单任务 60-120s 处理量"定，过大倾斜、过小费请求。

## 复盘追问
- 为什么这个成本问题常被"存储费不高"掩盖？提示：账单默认按服务汇总，请求费藏在操作计费行里，必须按表/桶拆解画像才能暴露。
- 上游团队不受你控制时如何推动改造？提示：出示按表的成本分账数据 + 给出下游 Compaction 兜底方案，把"上游改造"变成有数据支撑的跨团队议题。
