### Q7245 · tmp_result 表冲突：中间任务的临时表命名冲突、泄漏与清理

难度：P6 ｜ 标签：临时表、任务并发、资源泄漏、清理策略

基线：Python 3.12；sqlite3 实测同名临时表冲突与带任务后缀的隔离，配合 TTL 清理台账回收孤儿表。

**问**：数据平台的 DAG 任务里，几十个任务都爱建 `tmp_result` 这类"通用名"中间表。A 任务跑到一半报 `table already exists`；重构成"先 DROP 再建"后，并发任务互相把对方的中间表删了；更麻烦的是任务失败退出时中间表没人管，三个月攒下几千张 `tmp_*` 表把元数据和存储拖垮。中间临时表的命名、生命周期和清理到底该怎么管？

**答**：
- **结论**：临时表的问题本质是**共享命名空间里的无主资源**：① 命名冲突——`tmp_result` 是全局名，两个任务并发即冲突，"先 DROP 再建"把冲突升级成互删；② 生命周期无主——任务失败/被杀时不走清理分支，临时表变成孤儿；③ 清理无依据——没有台账就不知道哪张 tmp 表是活跃的、哪张可以删。规范做法是**任务级唯一名 + 创建即登记 + 到期回收**：名字带任务 ID 与日期（`tmp_result__task20261123__p3`），元数据台账记录 (表名, 任务, 创建时间, TTL)，清扫任务按 TTL 删除，删除前再核对登记表避免误删活跃表。
- **取舍**：① 会话级 TEMPORARY 表隔离最好但跨任务/跨连接不可见，复杂数据管道仍要物理中间表；② 唯一名 + 登记表有轻微元数据开销，换来可追溯与安全清理；③ TTL 按"任务最大重跑时长 × 2"设定，宁晚勿早——误删活跃表是数据事故，晚删几天只是存储；④ 清扫动作本身要幂等且限速（大批量 DROP 也会压元数据）。
- **实战**：① 平台层统一封装 create_tmp_table()，强制命名规范 + 自动登记，禁止手写 CREATE TABLE tmp_*；② DAG 收尾钩子（成功/失败都执行）负责删登记表里的本任务条目，失败路径的清理比成功路径更重要；③ 周度清扫报告输出"孤儿表数量/占用"，把泄漏率当平台健康指标（Q7135 僵尸资源盘活的思路同理）。

```python
"""临时表治理：唯一命名 + 登记台账 + TTL 清扫。sqlite3 实测。"""
import sqlite3
import time


def setup(conn: sqlite3.Connection) -> None:
    conn.execute("CREATE TABLE IF NOT EXISTS tmp_registry("
                 "name TEXT PRIMARY KEY, task TEXT, created REAL, ttl_s REAL)")


def create_tmp(conn: sqlite3.Connection, task: str, suffix: str,
               ttl_s: float = 3600.0) -> str:
    """平台层封装：任务级唯一名 + 登记台账。"""
    name = f"tmp_result__{task}__{suffix}"     # 唯一命名空间
    conn.execute(f"CREATE TABLE IF NOT EXISTS {name}(k TEXT, v TEXT)")
    conn.execute("INSERT OR REPLACE INTO tmp_registry VALUES (?,?,?,?)",
                 (name, task, time.time(), ttl_s))
    return name


def drop_tmp(conn: sqlite3.Connection, name: str, task: str) -> bool:
    """任务收尾钩子：只允许 owner 任务删除自己的表。"""
    row = conn.execute("SELECT task FROM tmp_registry WHERE name=?", (name,)).fetchone()
    if not row or row[0] != task:
        return False                            # 拒绝误删他人表
    conn.execute(f"DROP TABLE IF EXISTS {name}")
    conn.execute("DELETE FROM tmp_registry WHERE name=?", (name,))
    return True


def sweep(conn: sqlite3.Connection, now: float) -> list[str]:
    """TTL 清扫：到期 + 仍登记的才删，先核对台账防误删。"""
    rows = conn.execute("SELECT name, task, created, ttl_s FROM tmp_registry").fetchall()
    dropped = []
    for name, task, created, ttl in rows:
        if now - created > ttl:
            drop_tmp(conn, name, task)
            dropped.append(name)
    return dropped


if __name__ == "__main__":
    conn = sqlite3.connect(":memory:")
    setup(conn)
    n1 = create_tmp(conn, "taskA", "20261123")
    n2 = create_tmp(conn, "taskB", "20261123")   # 并发任务不再冲突
    print("并发创建:", n1, "|", n2, "-> 命名隔离，无冲突")

    print("taskA 误删 taskB 表:", drop_tmp(conn, n2, "taskA"), "(被拒绝)")
    print("taskB 自删:", drop_tmp(conn, n2, "taskB"))

    # 泄漏场景：taskA 失败退出未清理，3 小时后清扫
    conn.execute("UPDATE tmp_registry SET created=created-10800 WHERE name=?", (n1,))
    dropped = sweep(conn, now=time.time())
    print("TTL 清扫:", dropped, "| 剩余登记:",
          conn.execute("SELECT COUNT(*) FROM tmp_registry").fetchone()[0])
    print("结论：唯一命名防冲突，登记台账让清理有依据；失败路径的清理钩子是关键")
```

**追问一**：为什么不用数据库自己的 TEMPORARY 表，一劳永逸？

→ 解析：TEMPORARY 表的可见范围是**会话**，任务结束/连接断开自动消失——隔离和清理都免费。但数据管道常常跨连接、跨进程协作：DAG 的 A 步骤写、B 步骤读，两个连接看不到同一张 TEMP 表；而且大中间表放 TEMP 里会被强制放内存/临时目录（Q7147 的磁盘写满事故常见于此）。所以跨步骤管道只能用物理表承载中间态，代价就是要自己管命名与生命周期——这正是封装与台账存在的理由。

**追问二**：清扫任务怎么避免把"正在被读"的活跃表删掉？

→ 解析：三重防线：① TTL 设得宽（大于任务最大运行+重跑时长），让"活跃"定义不依赖实时状态；② 删除前核对登记表——登记在案的说明有 owner，只清"登记了但超期"的，对"没登记的野表"走人工审核；③ 大批量删除限速分批，观察主库/元数据库压力。可以再加一层"软删除"：先 RENAME 成 `trash_原名`（ rename 是元数据操作，瞬时完成），观察 24 小时无引用再真删，误删时还能改回来。
