### Q7281 · 三个实例 P99 一平均：分位数聚合的正确性事故

难度：P6 ｜ 标签：分位数聚合、P99、SLI口径、监控告警、上卷错误

基线：Python 3.12；构造倾斜延迟分布复现"实例级 P99 平均"的双重失真（夸大系统级、掩盖局部灾难），对比直方图合并重算的全局口径与分实例告警的正确组合，全标准库实跑。

**问**：监控大盘把三个实例的 P99 延迟平均了一下当成全局口径——预算判定与真实分布完全脱节：既会把"系统级其实达标"误判成濒临超标，又会把"某实例用户的灾难长尾"平均成风平浪静。分位数为什么不能平均？正确的聚合口径有哪几档（原始样本重算、直方图合并、分实例保留）？各错了多少、各花多少钱？

**答**：
- **结论**：分位数是**分布的函数**不是数值的函数：P99 的定义是"99% 的样本小于该值"，两个 P99 之间没有任何可加性——平均得到的是"不对应任何真实样本统计"的数字，且误差是**双向的**：本卡实验（A/B 两实例健康 P99=120ms，C 实例 1% 请求 8000ms）里，三实例平均 = 2746ms（比全局真实 P99=120ms 夸大 23 倍，系统级误判濒临超标），同时它比 C 实例用户的真实体验（8000ms）低估 66%（灾难被平均抹平）——同一个口径，两个方向都在撒谎。正确做法三档：① **直方图合并重算**（SLI 全局口径）：每实例上报分桶计数而非算好的分位数，全局合并桶计数后重算——Prometheus `histogram_quantile(sum by (le) (rate(...)))` 的正确用法；② **原始样本重算**（金标准/仲裁用）：访问日志或 trace 的原始延迟离线重算，校准直方图误差；③ **分实例/分人群保留 + max 哨兵**：全局 P99 达标不代表每个实例达标——C 实例的长尾必须靠"实例级 P99 的最大值"或逐实例告警暴露，`max(per-instance P99)` 方向保守（≥ 真实最差体验），可做告警哨兵但不当对外 SLI。通用纪律同族错误：率值上卷用平均而非重算（Q2801）——**上卷一律重算可加量（计数/字节/错误数），永远不平均比率与分位数。**
- **取舍**：① 直方图的桶设计：对数间距覆盖延迟范围（10/50/100/250/500ms/1s/2.5s/5s），分位误差上界≈桶宽；桶太多基数与存储涨，太少 P99 误差 >20%；② Prometheus 生态的高频翻车：`avg(histogram_quantile(...))` 与 `histogram_quantile(avg(...))` 都是错的——**必须先对每桶速率 sum（聚合原始计数）再算分位**，分位函数永远在聚合的最外层；③ 客户端聚合是错误温床：SDK 预聚合出 P99 再上报，服务端只能错误组合——原始计数出端，分位数只在终点算（Q7072 流式分位口径的端到端账）；④ 告警与 SLI 双口径：告警走"逐实例判断 + max 哨兵"快速通道（宁可误报不漏报），对外 SLI 走"全局重算"口径——两套数字两个用途，写进 SLO 文档（Q7520 预算口径同源）。
- **实战**：① 算术审计进大盘治理：全公司看板 grep "p99.*avg / avg.*p99 / p95.*mean" 类组合逐个修正——这类错误 review 抓不全，要靠规则审计；② SLI 书面化写死口径："全局 P99 = 合并原始延迟分布计算；实例级健康 = 逐实例 P99 + max 哨兵"，排除任何实例级组合；③ 桶边界是口径的一部分：改桶 = 口径变更，走评审与历史标注（Q7062 口径治理）；④ 长尾健康度元监控：单实例 P99 与全局 P99 的差值（分位差）监控——差值突增就是"某实例掉队"，这是平均口径永远看不见的信号。

```python
"""Q7281 分位数聚合: 实例P99平均(双重失真) vs 直方图合并重算 + max哨兵。"""
import bisect

HIST_EDGES = [10, 25, 50, 100, 200, 350, 500, 1000, 2500]   # 对数间距(ms)


def p99_sorted(samples: list[int]) -> int:
    s = sorted(samples)
    return s[min(int(len(s) * 0.99), len(s) - 1)]      # ceil 语义取上界


def to_hist(samples: list[int]) -> list[int]:
    counts = [0] * (len(HIST_EDGES) + 1)
    for v in samples:
        counts[bisect.bisect_right(HIST_EDGES, v)] += 1
    return counts


def p99_from_hist(counts: list[int]) -> int:
    """直方图上重算 P99: 桶内取中点, 误差<=桶宽."""
    total = sum(counts)
    need = total * 0.99
    acc = 0
    for i, c in enumerate(counts):
        acc += c
        if acc >= need:
            lo = HIST_EDGES[i - 1] if i > 0 else 0
            hi = HIST_EDGES[i] if i < len(HIST_EDGES) else 5000
            return (lo + hi) // 2
    return HIST_EDGES[-1]


def merge_hists(hists: list[list[int]]) -> list[int]:
    """正确上卷: 各实例同桶计数相加(计数可加), 分位数在终点重算."""
    out = [0] * (len(HIST_EDGES) + 1)   # 边界数+1 个桶(含溢出桶)
    for h in hists:
        for i, c in enumerate(h):
            out[i] += c
    return out


if __name__ == "__main__":
    # 每实例 1000 样本: 基线 80ms; A/B 健康(尾部 120ms); C 有 1% 灾难(8000ms)
    base = [80] * 985
    inst_a = base + [120] * 15
    inst_b = base + [120] * 15
    inst_c = base + [120] * 5 + [8000] * 10
    insts = [inst_a, inst_b, inst_c]
    per_p99 = [p99_sorted(s) for s in insts]
    avg_p99 = sum(per_p99) / len(per_p99)
    merged = merge_hists([to_hist(s) for s in insts])
    global_p99 = p99_from_hist(merged)
    worst = max(per_p99)
    print(f"实例级 P99: {per_p99} -> 平均 {avg_p99:.0f}ms (错: 不对应任何样本)")
    print(f"直方图合并重算 全局P99: {global_p99}ms  <- 平均口径夸大 "
          f"{avg_p99 / global_p99:.0f} 倍 (系统级误判)")
    print(f"max 哨兵: {worst}ms  <- 平均把 C 实例灾难低估 "
          f"{1 - avg_p99 / worst:.0%} (局部长尾被抹平)")
    ok = (avg_p99 > global_p99 * 5 and avg_p99 < worst * 0.5
          and global_p99 <= 200)
    print(f"校验: 夸大系统级 + 掩盖局部灾难 双向失真复现 -> {'通过' if ok else '异常'}")
    print("结论：分位数是分布的函数, 平均既不等于全局也不代表最差实例;")
    print("      全局口径=合并桶计数终点重算, 局部健康=逐实例P99+max哨兵")
```

**追问一**：为什么 Prometheus 的 `histogram_quantile(0.99, sum by (le) (rate(...)))` 是对的，而 `avg(histogram_quantile(...))` 是错的？从 PromQL 执行顺序讲清楚。

→ 解析：关键在**分位数在哪一层求值**。正确写法的执行序：`rate(bucket[5m])` 对**每个实例每个桶**算出"每秒落桶次数"（仍是原始计数语义）→ `sum by (le)` 把所有实例的**同桶计数相加**——这一步聚合的是计数不是分位数，数学合法（计数可加）→ `histogram_quantile` 在**合并后的全局直方图**上重算分位——分位数只在终点求值一次。错误写法 `avg(histogram_quantile(0.99, rate(bucket[5m]))) by (instance)` 的执行序：每个实例**先**各自算出 P99（分布信息在此刻坍缩成一个数）→ `avg` 对这些数平均——坍缩后的数不可加，结果不对应任何样本。本卡实验里的双向失真在两种写法下都会出现：实例级数字坍缩的瞬间，"C 实例的 1% 灾难"与"A/B 实例的健康尾部"被压成同一量纲的标量，之后的任何算术都救不回来。这个差别在 PromQL 里不显眼（都是几个函数嵌套），所以靠 review 挡不住，要靠**算术审计规则**（分位函数必须出现在聚合函数的**外层**）+ 大盘治理专项。延伸到通用监控口径设计：所有"上卷"操作只允许对**可加量**（计数、字节、错误数）进行；比率与分位数永远"合并原始计数后在终点重算"——这句话应该写进团队监控规范的第一页。

**追问二**：全局 P99 重算之后是 120ms 达标，但 C 实例 1% 用户在 8000ms——全局口径为什么会掩盖局部灾难？SLI 的"分层保留"怎么设计？

→ 解析：全局 P99 的数学性质决定了它对**少数人群的灾难天然免疫**：C 实例的灾难请求只占全局样本的 0.33%，低于 1% 分位线，全局 P99 完全看不见——这不是直方图的锅，换成原始样本重算全局 P99 仍是 120ms。这是聚合口径的固有盲区：**分位数定义在人群分布上，人群混得越均匀，局部灾难被稀释得越彻底**。所以 SLI 设计必须分层：① **全局层**（对外承诺）：合并重算的 P99/错误率，回答"系统整体是否达标"；② **分段层**（内部健康）：按实例/可用区/租户分组的 P99 逐个保留并独立告警，回答"谁掉队了"——分段维度是 SLI 设计的一部分而非事后补充，维度选择要与"灾难会局部化"的拓扑对齐（实例、AZ、版本灰度组）；③ **哨兵层**（快速反应）：`max(per-instance P99)` 与"分位差"（最差实例与全局之差）做告警哨兵，方向保守宁可误报；④ **仲裁层**：SLO 争议或异常追查时用原始样本离线重算，校准直方图误差并做按 segment 的分布对比（Q2538 重放校验同族）。四层共享同一份原始计数，只是聚合终点不同——口径分层的本质是承认"一个分位数只能回答一个问题"，想让仪表盘回答四个问题就要四个口径，而不是把一个口径平均来平均去。
