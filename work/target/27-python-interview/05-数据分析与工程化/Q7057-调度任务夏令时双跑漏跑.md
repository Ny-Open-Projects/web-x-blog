### Q7057 · 调度任务夏令时双跑/漏跑的复盘与 UTC 规范

难度：P6 | 标签：调度系统、夏令时、时区、幂等

**问**：一个每天凌晨 1:30 的对账任务，一年有两天行为异常：某天跑了两次，某天没跑。为什么"每天 1:30"在夏令时地区不是每天一次？调度系统的正确时间语义是什么？

**答**：
- **结论**：墙钟时间（本地 naive 时间）在夏令时切换日不连续：春季拨快，2:00-3:00 这段墙上时间不存在——排在这里的任务被跳过；秋季拨回，1:00-2:00 出现两次——同一份 naive 时间对应两个不同的绝对时刻，任务跑两遍。正确语义是三层：① 调度器内部一律存 UTC 绝对时刻；② cron 表达式必须显式声明时区（"本地 1:30"要翻译成"America/New_York 的 1:30"再换算）；③ 触发幂等键用 UTC 绝对时刻而非墙钟，双跑被账本拦下。Python 侧 `zoneinfo`（3.9+）配合 `fold` 参数能显式区分歧义时刻。
- **取舍**：有人主张"全用 UTC，报表按 UTC 出"——调度侧必须 UTC，但展示侧的业务日切要按业务时区算（谁的今天），两层各自显式，混在一层才是事故温床。另有一个细节：`datetime` 两个同 `tzinfo` 对象直接相减会忽略 fold 差异（naive 减法），比较绝对时刻必须先 `astimezone(UTC)`——这是个反直觉的语言级陷阱。
- **实战**：巡检清单：① 调度配置里 grep 无时区的 cron；② 夏令时切换日前跑"未来 7 天触发时刻推演"，春季找跳过、秋季找双触发；③ 任务侧加幂等账本（UTC 键），让"调度层漏拦"还有最后一道闸。

```python
"""调度任务的夏令时事故：本地时间 2:30 有时不存在、有时出现两次。"""
from datetime import datetime, timedelta  # noqa: F401
from zoneinfo import ZoneInfo

NY = ZoneInfo("America/New_York")   # 3.9+ 标准库 zoneinfo，macOS/Linux 自带 tz 数据
UTC = ZoneInfo("UTC")

def localize(naive: datetime, tz: ZoneInfo) -> datetime:
    """把本地墙上时间解释为 tz 时刻（朴素的 attach 语义）。"""
    return naive.replace(tzinfo=tz)

# 春季拨快：2026-03-08 02:30 在美国东部不存在（02:00 直接跳到 03:00）
spring = localize(datetime(2026, 3, 8, 2, 30), NY)
print(f"春季 2:30 -> UTC {spring.astimezone(UTC)}（实际落到了 3:30）")

# 秋季拨回：2026-11-01 01:30 出现两次，fold=0/1 是两个不同的绝对时刻
first = localize(datetime(2026, 11, 1, 1, 30), NY).replace(fold=0)
second = localize(datetime(2026, 11, 1, 1, 30), NY).replace(fold=1)
gap = second.astimezone(UTC) - first.astimezone(UTC)
# 注意：同 tzinfo 对象直接相减走 naive 语义会忽略 fold，必须经 UTC 计算
print(f"秋季 1:30 两次相差 {gap}，"
      f"UTC 分别是 {first.astimezone(UTC).time()} 与 {second.astimezone(UTC).time()}")

# naive 墙钟调度的事故：秋季拨回日，本地 1:30 对应两个 UTC 绝对时刻
scheduled_wall = [datetime(2026, 11, 1, 1, 30), datetime(2026, 11, 1, 1, 30)]
naive_fires = len(scheduled_wall)
utc_keys = {localize(t, NY).astimezone(UTC) for t in scheduled_wall}
dedup_fires = len(utc_keys)
print(f"墙钟调度触发 {naive_fires} 次，按 UTC 绝对时刻做幂等键去重后 {dedup_fires} 次"
      f" -> 双跑被幂等键拦下")

# 正确姿势：调度器内部一律存 UTC + 触发幂等键
utc_cron = datetime(2026, 11, 1, 5, 30, tzinfo=UTC)  # 对应本地 1:30(EDT)
print(f"UTC 存储：{utc_cron} -> 本地 {utc_cron.astimezone(NY)}，绝无二义")
print("纪律：cron 表达式的时区必须显式声明；幂等键用 UTC 绝对时刻而非本地墙钟")
```

**追问链**：
1. 追问一层：为什么幂等键必须用 UTC 绝对时刻而不是"任务日期"？——秋季双触发的两次执行落在同一个"任务日期"上，日期键能去重双跑；但春季跳过的任务补跑时，日期键会拒绝合法补跑。UTC 绝对时刻键的语义是"这个物理时刻只执行一次"，补跑用新时刻自然通过。
2. 追问二层：`datetime` 同 tzinfo 直接相减忽略 fold，这还有什么坑？——凡是比较/间隔计算涉及时区都要先归一到 UTC：日志排序、超时计算、限速窗口都会踩。工程纪律是"边界处转换、内部只存 UTC"，naive datetime 只允许出现在展示层。

**背诵要点**：
1. 夏令时日墙钟不连续：春季小时不存在（漏跑）、秋季小时重复（双跑）。
2. 三层规范：内部存 UTC、cron 显式时区、触发幂等键用 UTC 绝对时刻。
3. 语言陷阱：同 tzinfo 对象相减忽略 fold，跨时区比较必须先 astimezone(UTC)。

**复盘追问**：
1. 只有美国客户报"任务没跑"，国内团队一切正常，怎么定位？（夏令时地区特有故障：查该时区切换日与任务排期重叠；推演未来触发时刻即可复现"跳过/双跑"）
2. 为什么说"调度器存 UTC"不能替代"幂等键"？（调度器升级、人肉补触发、多调度器并存都会产生计划外触发，UTC 键兜住一切重复执行；调度器只是第一道防线）
