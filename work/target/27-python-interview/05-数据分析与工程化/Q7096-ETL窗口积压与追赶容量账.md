### Q7096 · ETL 窗口积压与追赶容量账

难度：P7 ｜ 标签：数据工程 / 容量规划 / 背压

**问**：数仓的 T+1 ETL 正常 4 小时跑完，某天上游延迟让任务 2 小时后才启动，当天又叠加数据量翻倍，管道第二天 06:00 才追上，下游报表全部延迟。窗口任务的"积压-追赶"容量账怎么算？允许追赶的前提是什么？

**答**：
- **结论**：窗口任务的健康标准不是"平均时长 < 窗口"，而是**追赶系数**：`追赶速率 / 正常产出速率 ≥ 1` 且追赶期间不与下一窗口重叠。追赶时间估算：`T_追 = 积压量 / (产能 - 下一窗口新增速率)`——注意分母是剩余产能而非全产能，否则会算出"追赶但永远追不上"的假象。容量账要按 P99 数据量 × 1.5 留余量：日均 4 小时的管道遇到大促日数据翻倍就变 8 小时，窗口只有 6 小时时直接吞掉下一个窗口，形成滚雪球积压。触发翻倍的常见源：上游补数据（backfill）、大促、重跑风暴。
- **取舍**：处理积压的三个层级：① 横向扩容（worker 加副本）——受限于有状态资源（DB 连接、分区锁），不是线性加速；② 纵向切分（把大窗口切成小时级微批）——改造大但根治"长窗口"问题；③ 降级跳过（非关键表延后）——保护关键链路。追赶上限要设硬性告警（积压 > 2 个窗口就告警 + 决策介入），而不是让系统自己慢慢追。
- **实战**：步骤：① 每任务记录"数据量-时长"曲线（线性拟合出单批吞吐）；② 用 P99 数据量反推产能需求：`产能 ≥ P99量 × 1.5 / 窗口时长`；③ 补数据/大促前做容量预演（按预估量 × 2 压测）；④ 复盘项：追赶期间下游的 SLA 通信模板提前写好，报表延迟要有自动通知而不是靠人肉发现。

```python
# ETL 窗口积压追赶计算器（纯标准库）
# 基线：Python 3.9+

def catchup_hours(
    backlog_rows: float,      # 积压行数
    throughput_rows_per_h: float,   # 全产能吞吐
    next_window_rate: float,        # 下一窗口新增速率（行/小时）
) -> float | None:
    """追赶所需小时数；产能不足返回 None（永远追不上）"""
    net = throughput_rows_per_h - next_window_rate
    if net <= 0:
        return None
    return backlog_rows / net


def required_throughput(
    p99_rows: float, window_h: float, margin: float = 1.5,
) -> float:
    """按 P99 数据量与余量反推产能需求"""
    return p99_rows * margin / window_h


def main() -> None:
    # 积压 3M 行，产能 2M/h，下一窗口每小时新增 0.5M
    t = catchup_hours(3_000_000, 2_000_000, 500_000)
    print(f"追赶需 {t:.1f} 小时")
    assert abs(t - 2.0) < 1e-9   # 3M / 1.5M = 2h
    # 产能被下一窗口吃满 → 永远追不上
    assert catchup_hours(3_000_000, 500_000, 500_000) is None
    # P99 数据量 5M、窗口 6h → 需要产能 1.25M/h
    need = required_throughput(5_000_000, 6)
    print(f"需要产能 {need:.2f}M 行/h")
    assert abs(need - 1.25e6) < 1
    print("OK")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"追赶吞吐"不能按全产能算？
→ 一句话提示：追赶期间下一窗口的数据还在流入（或下一窗口任务已启动），消耗同一份产能；分母要用"产能 - 新增速率"，否则算出的是不可能完成的乐观值。

**追问 2**：微批化（窗口从日切小时）后哪个成本会显著上升？
→ 一句话提示：调度与元数据开销、小文件数量、每批固定成本（连接建立、统计信息更新）都随批数线性上升；微批是"用固定开销换追赶能力"的交易，批数下限由固定成本占比决定。

## 背诵要点
- 健康标准是追赶系数 ≥1 且不与下一窗口重叠；追赶时间 = 积压 / (产能 − 下一窗口新增速率)，分母 ≤0 意味永远追不上。
- 产能需求按 P99 数据量 × 1.5 余量反推，不按日均；大促与补数据是积压两大触发源。
- 积压 > 2 个窗口即告警决策：扩容（受有状态资源限制）/ 微批化（固定成本上升）/ 关键链路保护式降级。

## 复盘追问
- 为什么横向扩 worker 常常加速不了 ETL？提示：瓶颈在有状态资源——DB 连接数、分区写锁、单文件处理串行段；扩容前先 profile 找串行段，否则加机器只是加钱。
- 重跑风暴是什么，怎么防？提示：失败任务自动重试 × 上游数据变更触发级联重跑，叠加成容量尖峰；防法是重试限流、重跑窗口错峰、以及把"重跑"纳入容量账而非视为免费操作。
