### Q7068 · 按日期参数化的补数扇出

难度：P6 | 标签：backfill、参数化任务、幂等、容量规划

**问**："把最近 90 天的日汇总表按新口径重算"的补数任务，怎么设计才安全？"重跑安全"靠什么保证？并发上限怎么定？

**答**：
- **结论**：补数 = 参数化扇出 + 分区账本幂等 + 并发上限。① 按日期把任务参数化成 N 个独立分区任务（date 作为唯一参数）；② 每个分区查"已完成分区账本"（元数据表），已完成跳过——重跑永远安全；③ 分区任务输出写死自己的分区路径（`output/date=2026-01-01/`），重跑即覆盖，天然幂等；④ 并发上限按下游资源定（同时打同一个 DB 的分区任务数 = DB 能承受的并发），不是机器核数。
- **取舍**：扇出粒度：按天太粗（单日跑不完）、按小时太碎（调度开销大）——数据量差异大的管道按"数据量自适应"再切分。补数与在线任务共抢资源，要用独立资源组/低峰窗口，否则补数高峰挤掉在线报表。
- **实战**：事故高发点：补数任务"幂等但读到了半成品"——上一轮失败留下部分输出，重跑覆盖前有人读了脏分区。防线：分区输出用"临时目录 + 原子 rename 提交"或写 manifest 就绪标记；下游只读带就绪标记的分区。账本更新时机：任务成功后写账本，写在同一个事务里保证账实一致。

```python
"""按日期参数化的补数扇出：生成任务图 + 幂等跳过已完成分区 + 并发上限。"""
from concurrent.futures import ThreadPoolExecutor
from datetime import date, timedelta

done_partitions = {"2026-01-01"}                 # 已成功分区账本（生产=元数据表）

def build_backfill(start, end, max_workers=3):
    days, d = [], start
    while d <= end:
        days.append(d.isoformat())
        d += timedelta(days=1)
    todo = [x for x in days if x not in done_partitions]     # 幂等：已完成跳过
    with ThreadPoolExecutor(max_workers=max_workers) as ex:  # 并发上限=资源保护
        list(ex.map(run_partition, todo))
    return days, todo

def run_partition(day):
    # 每个分区任务：输出写死分区路径，重跑即覆盖 -> 天然幂等
    return f"output/date={day}"

days, todo = build_backfill(date(2026, 1, 1), date(2026, 1, 5))
print("全部分区:", days)
print("本次执行:", todo, "(2026-01-01 已完成，跳过)")
print("要点：补数=日期参数扇出 + 分区账本幂等 + 并发上限；重跑永远安全")
```

**追问链**：
1. 追问一层：为什么分区输出要"临时目录+原子提交"而不是直接写？（直接写会产生可被下游读到的半成品分区；原子提交让分区要么旧版要么新版，没有中间态）
2. 追问二层：90 天补数跑到一半口径又改了怎么办？（杀掉剩余任务、清账本、按新口径重扇出；账本里要记录口径版本，口径变更自动使账本失效）

**背诵要点**：
1. 补数三件套：日期参数扇出、分区账本幂等、按下游资源定并发上限。
2. 分区输出写死路径 + 原子提交/就绪标记，杜绝半成品被读。
3. 账本记口径版本，口径变更使账本失效重扇出。

**复盘追问**：
1. 补数期间在线报表延迟了 2 小时，资源隔离哪里没做？（补数与在线任务共抢 DB/计算资源，要独立资源组或低峰窗口）
2. 为什么"重跑覆盖"必须配合"就绪标记"？（无标记时下游读到覆盖中途的半成品）
