### Q7008 · SLO 燃烧率告警的窗口公式与误报压测

> 难度:★★★ | 标签:SRE, SLO, 告警

**问**：我们用错误率 > 1% 告警，结果白天微毛刺天天叫，真出事时反而因为"平均掉了"不触发。SRE 教科书里的燃烧率（burn rate）多窗口告警到底怎么算？上之前怎么压测误报率？

**答**：结论：燃烧率告警回答的问题是"按当前错误消耗速度，预算多久烧完"。公式：`burn_rate = 实际错误率 / SLO 允许错误率`。Google SRE 的经典多窗口组合：**快窗 5m + 慢窗 1h，burn rate ≥ 14.4 → page**（对应 30 天预算 2% 在 1 小时内烧掉 1/30×14.4≈2%，即"一小时烧掉一天预算"）；中窗 30m+6h ≥ 6 → page；慢窗 6h+3d ≥ 1 → ticket。单窗口的错误率阈值（1%）没有时间维度，天然误报——这就是你们白天毛刺叫个不停的原因。

设计与误报压测：
- 为什么必须双窗：单快窗对毛刺过敏，单慢窗漏真事故且滞后；快窗触发条件 + 慢窗确认条件同时满足才 page，毛刺（1 分钟尖峰）烧不满 1 小时慢窗就被过滤。
- 上线前压测误报的方法不是拍脑袋：拿 30~90 天历史指标**回放**，统计这套规则会产生的 page 数与"事后确认是事故"的比例（信噪比），再调 burn 阈值。要同样回放"漏报测试"：注入历史真实事故的指标曲线，验证规则能在目标时间内（如 5 分钟内）触发。
- 实战细节：窗口要对齐（两个窗口的起点同步，避免半窗伪影）；`burn_rate = (1 - good_ratio)` 用 good events ratio（如成功请求占比）算，比 error_count/total 更稳（低流量时段误报爆炸——流量小于阈值时段要静默，如"1h 窗口请求 < 100 则抑制"）。多服务共享 SLO 预算时按错误预算分配，别让单服务毛刺吃光全局。

```python
# 基线:Python 3.9+ 标准库;燃烧率告警评估器 + 历史回放压测(可运行)
def burn_rate(errors: int, total: int, slo_target: float = 0.999) -> float:
    """burn = 实际错误率 / 允许错误率。slo_target=99.9% → 允许 0.1%。"""
    if total == 0:
        return 0.0
    return (errors / total) / (1 - slo_target)

def alert(errors_5m: tuple[int, int], errors_1h: tuple[int, int],
          fast_th: float = 14.4, slow_th: float = 14.4, min_traffic: int = 100) -> str:
    """双窗 page 规则:快窗&慢窗同时超阈,且 1h 流量达标。"""
    e5, t5 = errors_5m
    e1, t1 = errors_1h
    if t1 < min_traffic:                      # 低流量抑制,防分母小误报
        return "suppressed(low-traffic)"
    if (burn_rate(e5, t5) >= fast_th and burn_rate(e1, t1) >= slow_th):
        return "PAGE"
    return "ok"

if __name__ == "__main__":
    print(alert((15, 1000), (200, 200_000)))   # 5m 错误率 1.5% -> burn=15 >= 14.4, 1h 也超 -> PAGE
    print(alert((10, 1000), (12, 200_000)))    # 毛刺:快窗超但慢窗不足 -> ok
    print(alert((5, 50), (8, 90)))             # 低流量 -> suppressed
```

**追问**：
- 一层追问：14.4 这个数怎么来的？——30 天预算内"1 小时烧掉 2%"等效：预算允许总错误 0.1%×30d=4320 分钟错误额度，1h 烧 2% 即 14.4 倍速（(30×24×60×0.02)/60=14.4）。同理 6 窗口 6 对应"6 小时烧 5%"。
- 二层追问：燃烧率告警和服务错误率告警会不会重复？——会重叠但语义不同：错误率告警是"现在坏了"（面向用户症状），burn 告警是"预算消耗速度异常"（面向 SLO 管理）；实践中 burn 告警上线后应逐步替代裸错误率阈值，避免双重 page。
- 三层追问：多窗口规则延迟触发的代价怎么评估？——用回放测 MTTD（从事故注入到首次 page 的分钟数）：快组合（5m+1h）MTTD 约数分钟但信噪比略低，慢组合（30m+6h）MTTD 10+ 分钟但更安静；按事故分级配两档，P0 走快组合。
