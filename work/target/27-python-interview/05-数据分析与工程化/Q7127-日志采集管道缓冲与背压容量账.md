### Q7127 · 日志采集端（filebeat/vector 类）缓冲队列与背压丢弃的容量账

难度：P6 ｜ 标签：容量规划 / 可观测 / 日志管道

**问**：事故复盘时最痛的是"关键日志没采集到"——下游日志平台故障期间，采集 agent 缓冲打满开始丢日志，恢复后丢了 40 分钟现场。缓冲该给多大？满了该阻塞还是丢？怎么让"日志管道故障"不变成"事故现场消失"？

**答**：
- **结论**：采集端缓冲容量 = **下游恢复时间 × 峰值产出速率 × 安全系数**。如果下游可接受 30 分钟故障、日志峰值 5 万条/s × 1KB，缓冲要 ≥ 90GB 级——磁盘缓冲（disk buffer）是唯一现实选项，内存缓冲（几十 MB）只能扛秒级抖动。满了的策略按**日志等级分层**：ERROR/WARN 永不丢（满了宁可阻塞采集、日志文件反而成为天然缓冲——agent 追 file offset 的模型天然支持"暂停追赶"）；DEBUG/INFO 可丢弃（采样或计数丢弃，丢弃量要计数上报）。关键认知：日志文件本身在源端就是一个免费的持久缓冲，"阻塞采集"= 不推进 offset = 日志留在源盘，只要源盘容量够、采集恢复后能追上（追赶速率 = 下游恢复后带宽 - 常态速率）。所以真正要预算的是两件事：源端磁盘余量（事故期日志继续写）与恢复后的追赶带宽（追赶期下游又要扛平时 + 积压双份流量，下游容量要留余量）。
- **取舍**：磁盘缓冲给多大？给"下游最长可容忍故障 × 峰值速率"太多数团队算不出下游 SLA——退而求其次给固定额度（如 10GB）+ 高水位告警（80% 时自动降 DEBUG 采样）。丢弃策略的哲学：观测数据的丢失要"可知、可控、可计量"——丢 DEBUG 可以，丢 ERROR 不行，"均匀地丢一部分"比"随机丢一堆"事后归因价值高得多（丢失计数本身就是指标）。
- **实战**：① agent 配置分层缓冲：ERROR 走独立队列（大缓冲/不丢），普通日志共享池；② 丢弃必须计数（dropped_events 指标），告警阈值按丢弃率设；③ 源端磁盘水位监控与日志轮转兜底（防止阻塞采集把业务机磁盘写满——阻塞策略的反作用力）；④ 演练：手动断下游 30 分钟验证 ERROR 零丢失与追赶时长。

```python
# 采集缓冲账: 缓冲 = 恢复时间x峰值速率; 阻塞(留源盘) vs 丢弃(计数) 分层
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class LogPipe:
    peak_eps: float                 # 峰值 events/s
    entry_kb: float
    downstream_outage_min: float    # 下游最长故障
    disk_buffer_gb: float

    def outage_volume_gb(self) -> float:
        return self.peak_eps * self.entry_kb * self.downstream_outage_min * 60 / 1e6

    def policy(self) -> str:
        if self.outage_volume_gb() <= self.disk_buffer_gb:
            return "缓冲足够: ERROR 阻塞式保留, DEBUG 允许采样丢"
        return "缓冲不足: 提额 / 自动降 DEBUG 采样 / ERROR 仍走独立队列"


def catchup_minutes(p: LogPipe, restored_bandwidth_eps: float) -> float:
    backlog = p.peak_eps * p.downstream_outage_min * 60
    return backlog / max(restored_bandwidth_eps - p.peak_eps, 1) / 60


def main() -> None:
    p = LogPipe(peak_eps=50_000, entry_kb=1.0, downstream_outage_min=30,
                disk_buffer_gb=10)
    assert abs(p.outage_volume_gb() - 90.0) < 1e-6   # 30min 需 90GB
    assert "不足" in p.policy()
    # ERROR 独立队列: 只占 2% 流量, 2GB 即可零丢失
    err_pipe = LogPipe(50_000 * 0.02, 1.0, 30, 2.0)
    assert abs(err_pipe.outage_volume_gb() - 1.8) < 1e-6
    assert "足够" in err_pipe.policy()
    # 追赶: 下游恢复后 2x 带宽 -> 30 分钟追完
    assert abs(catchup_minutes(p, 100_000) - 30.0) < 1e-6
    print(f"全量 30min={p.outage_volume_gb():.0f}GB 爆缓冲; "
          f"ERROR 分层 2GB 零丢失")
    print("OK: 阻塞=留在源盘(需磁盘水位监控); 丢弃必须计数; 演练验证追赶时长")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"阻塞采集"不能无脑选？它的反作用力是什么？
→ 一句话提示：阻塞期间源端日志继续写、业务机磁盘持续消耗，磁盘写满会打挂业务进程本身——所以阻塞策略必须配源盘水位监控与轮转兜底，观测组件不能反过来威胁业务。

**追问 2**：丢失计数为什么是"丢弃策略"的核心而不只是补偿？
→ 一句话提示：计数让丢失变成可观测的事实（丢多少、丢哪层、什么时段），事后归因能区分"没发生"和"丢了没采到"；无计数的丢弃等于把观测系统的盲区伪装成系统的好状态。

## 背诵要点
- 缓冲 = 下游可容忍故障时长 × 峰值速率 × 安全系数；30min × 5 万 eps ≈ 90GB，只有磁盘缓冲现实，内存缓冲只扛秒级抖动。
- 分层策略：ERROR 独立队列永不丢（占比小，缓冲便宜），DEBUG/INFO 可采样丢但必须计数上报。
- 阻塞采集 = 日志留在源盘，需源盘水位兜底；恢复后追赶时长 = 积压/(恢复带宽−常态速率)，下游容量要留余量。

## 复盘追问
- 为什么"日志文件是天然持久缓冲"这个认知改变了缓冲设计？提示：agent 追 offset 模型下不推进就是持久化，预算从"agent 内存"转移到"源盘余量+追赶带宽"，架构上更便宜也更可靠。
- 怎么验证管道的丢失承诺而不是纸面承诺？提示：故障注入演练——断下游 30 分钟，核对源端文件行数 vs 端侧到达行数，ERROR 零丢失、丢弃计数准确即通过。
