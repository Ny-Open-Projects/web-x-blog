### Q7046 · 容量规划：制品仓库 5TB 里 4.3TB 是没人下载的旧镜像

> 难度:★★★ | 标签:容量规划, 制品管理, 生命周期

**问**：团队把 Docker 镜像和 wheel 包推到自建制品仓库（Harbor/Nexus 思路），两年涨到 5TB，其中 4.3TB 超过一年无人拉取。制品的容量账怎么算？清理策略怎么定才不会误删正在被生产引用的制品？不可变 tag 为什么既是优点也是容量灾难？

**答**：结论：制品容量账 = **每次发布的制品大小 × 发布频率 × 环境份数**，且镜像层共享让"逻辑总量"远大于"物理增量"，但旧层一旦失去引用者就永远无人回收——所以账要按"分层引用图"算而不是按 tag 数算。清理策略的核心是**保留集（retention set）+ GC**：先算出"生产在用 + 回滚窗口 + 审计要求"三者的并集作为不可删集，其余进入宽限期回收；不做引用分析的裸删 tag 是事故制造机。

机理与实战：
- **不可变 tag 的代价**：`sha256` digest 或版本号 tag 不可覆盖保证了"今天部署的和明天部署的绝不相同"（供应链安全基石），但每个 CI 提交都产出一份完整制品，两年几万次提交就是几万份制品——没有保留策略的不可变仓库是线性膨胀的垃圾场。
- **保留集三要素**：① 生产正在引用（从部署记录/k8s 集群实况采集 image digest）；② 回滚窗口（最近 N 个版本，如 10 个）；③ 审计留存（出过事故的版本、合规要求的发布留痕，如 1 年）。三者并集之外的制品进入"宽限期"（如 30 天）再物理删除，删除前再次 diff 引用快照。
- **镜像层的 GC 特殊性**：删 tag 只是删"引用"，层（layer）要等仓库跑 GC 才释放；且多镜像共享基础层，只有所有引用者都删除后层才可回收——所以"仓库满"的治理要同时看 tag 数与 dangling layer 数。
- **源头减量**：多阶段构建把运行镜像从 1.2GB 压到 180MB、基础镜像统一（共享层复用率提升）、CI 只推有部署意义的制品（PR 构建产物不推仓库）——容量账里"每次发布大小"这一项的优化杠杆最大。

```python
# 基线:Python 3.10+;纯标准库,制品保留集计算与宽限期 GC 模拟
from __future__ import annotations
from dataclasses import dataclass, field
from datetime import datetime, timedelta


@dataclass
class Artifact:
    digest: str
    pushed_at: datetime
    size_gb: float
    in_production: bool = False   # 生产引用
    in_rollout_window: bool = False  # 回滚窗口
    audit_hold: bool = False      # 审计留存


@dataclass
class Registry:
    artifacts: list[Artifact] = field(default_factory=list)
    grace_days: int = 30

    def retention_set(self) -> set[str]:
        return {a.digest for a in self.artifacts
                if a.in_production or a.in_rollout_window or a.audit_hold}

    def gc_candidates(self, now: datetime) -> list[Artifact]:
        """宽限期:不在保留集且超过 grace_days 未被引用 -> 可物理删除。"""
        keep = self.retention_set()
        cutoff = now - timedelta(days=self.grace_days)
        return [a for a in self.artifacts
                if a.digest not in keep and a.pushed_at < cutoff]

    def reclaim_gb(self, now: datetime) -> float:
        return sum(a.size_gb for a in self.gc_candidates(now))


def demo() -> None:
    now = datetime(2026, 11, 20)
    reg = Registry()
    # 两年产出 200 份制品,只有 3 个在用、5 个在回滚窗口、1 个审计留存
    for i in range(200):
        reg.artifacts.append(Artifact(
            digest=f"sha256:{i:04d}",
            pushed_at=now - timedelta(days=730 - i * 3.5),
            size_gb=1.2,
            in_production=(i >= 197),
            in_rollout_window=(192 <= i < 197),
            audit_hold=(i == 150),   # 出过事故的版本永久留
        ))
    total = sum(a.size_gb for a in reg.artifacts)
    reclaim = reg.reclaim_gb(now)
    print(f"总占用 {total:.0f}GB,可回收 {reclaim:.0f}GB,保留 {total - reclaim:.0f}GB")
    assert reclaim > total * 0.9                       # 绝大多数可回收
    assert len(reg.gc_candidates(now)) == 191          # 200-9(保留集)
    kept = {a.digest for a in reg.artifacts} - {a.digest for a in reg.gc_candidates(now)}
    assert "sha256:0150" in kept                       # 审计留存不被删
    assert reg.retention_set() <= kept                 # 保留集必在
    print("GC 规则:保留集=生产+回滚窗口+审计留存的并集,宽限期后物理回收 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：怎么知道"生产正在引用哪些 digest"？引用快照采集有什么坑？
答：从各集群实况采集（kubectl get pods 的 image 字段/部署系统数据库）并定期快照；坑有三：正在滚动更新的新旧两个 digest 都在用（快照要连续采多次取并集）、定时任务镜像只在新月才实例化（要扫 cron 定义而非运行时）、跨集群/边缘节点延迟更新——所以引用采集宁可误保留，且删除前做二次快照 diff。

**追问二**：为什么"PR 构建产物不推仓库"能省一半容量？
答：CI 里绝大多数构建是 PR 验证（一次构建多次提交），其镜像只在验证期有价值，验证完成即无引用——把它们推入仓库等于把"最短暂的制品"放进"最持久的存储"。正确做法：PR 构建产物走 CI 内部临时存储（构建机本地或带短 TTL 的缓存），只有 merge 后、发版前的制品进仓库。容量账里"发布频率"要按"进仓库的频率"算，不是 CI 触发频率。

## 背诵要点
- 制品容量账 = 单制品大小 × 进仓库频率 × 环境份数；镜像层共享使物理增量小于逻辑总量，但失去引用的层永不自动回收。
- 清理核心是保留集（生产实况引用 ∪ 回滚窗口 ∪ 审计留存）+ 宽限期 GC（30 天+二次引用 diff）；裸删 tag 是事故制造机。
- 源头减量杠杆最大：多阶段构建压镜像、统一基础镜像提共享层复用、PR 临时制品不进仓库。

## 复盘追问
- 某次回滚失败提示 digest 不存在，复盘引用采集漏了什么？（提示：回滚目标是"上一个部署版本"，若采集只看当前运行实况、没包含部署系统的版本历史，回滚窗口制品就会被 GC；保留集必须以部署系统记录为准，运行实况只是交叉验证）
- 仓库从 5TB 治理到 800GB 后，为什么半年后又涨回 2TB？（提示：只做了清理没做入口治理——CI 仍在推 PR 产物；容量治理必须"入口配额+GC"双闭环，按团队/项目配额并在超限时阻断推送，才能维持稳态）
