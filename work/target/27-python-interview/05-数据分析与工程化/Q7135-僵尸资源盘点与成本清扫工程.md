### Q7135 · 僵尸资源盘点与云成本清扫工程

难度：P6 ｜ 标签：成本工程 / 工程化 / 治理

**问**：季度账单复盘发现 20% 的云成本花在"没人承认的资源"上：最后一次部署的实验环境、孤儿磁盘、没人订阅的队列、跑完不删的快照。怎么用 Python 工程化地做"僵尸资源盘点"？清扫怎么做到既省钱又不误杀？

**答**：
- **结论**：僵尸资源治理 = **盘点 → 定级 → 宽限 → 清扫** 的闭环流水线。盘点：用云厂商 SDK（boto3 等）拉全量资源清单，与三类事实源交叉：① 活跃度信号（磁盘无挂载、队列无消费者、镜像无运行实例引用、快照无备份策略引用）；② 元数据年龄（创建者、创建时间、最后使用时间——磁盘的 attached/last_attach、对象的 last_modified）；③ 组织事实源（CMDB/IaC 仓库里存在的资源 vs 云上实际资源，差集就是孤儿）。定级：按"年龄 × 成本 × 危险度"打分，`unused_days > 30 且月成本 > 阈值` 进入清扫队列。宽限与清扫：**默认不删除，先打标签降级**（`zombie-candidate` + 通知 owner），宽限期后无人认领才执行"软删除"（快照/归档一层，可恢复）——误杀的代价远大于晚一周省钱。
- **取舍**：全自动删除 vs 人工确认：全自动省人力但有误杀风险（测试环境被假期暂停误判），折中是"自动降级 + 清单审批 + 定期自动清扫已降级项"。信号选择上，"最后使用时间"比"创建时间"准，但很多资源没有该信号（如未挂载磁盘要靠 CloudWatch 无 IO 佐证）——多信号交叉是关键，单一信号定罪会误杀。
- **实战**：① 把盘点脚本做成定时任务输出差异报告（IaC 差集 + 成本 TOP），进周会；② 清扫动作幂等且留审计（资源 ID、依据信号、执行人）；③ 与 Q7129 的按需环境空闲成本、Q7117 的生命周期策略打通：能靠生命周期规则自动过期的（对象存储）优先用规则，SDK 清扫只处理规则覆盖不到的类型。

```python
# 僵尸资源盘点流水线: 多信号交叉定级 -> 宽限标签 -> 软删除
# 基线: Python 3.9+ 标准库 (生产用 boto3 等拉取真实清单)
import datetime as dt
from dataclasses import dataclass, field


@dataclass
class Resource:
    rid: str
    kind: str                 # disk / snapshot / queue / env
    monthly_cost: float
    created: dt.datetime
    signals: list[str] = field(default_factory=list)  # 僵尸信号

    def zombie_score(self, now: dt.datetime) -> float:
        age_days = (now - self.created).days
        # 信号数 x 成本 x 年龄 -> 定级分
        return len(self.signals) * self.monthly_cost * min(age_days, 90) / 30


def triage(resources: list[Resource], now: dt.datetime,
           cost_threshold: float) -> tuple[list[str], list[str]]:
    """返回 (立即清扫队列, 降级观察队列)。误杀防护: 低分只降级。"""
    sweep, watch = [], []
    for r in resources:
        if len(r.signals) < 2:            # 单信号不定罪
            watch.append(r.rid)
            continue
        score = r.zombie_score(now)
        if r.monthly_cost >= cost_threshold and score >= 60:
            sweep.append(r.rid)
        else:
            watch.append(r.rid)
    return sweep, watch


def main() -> None:
    now = dt.datetime(2026, 11, 21)
    res = [
        Resource("vol-orphan", "disk", 120, now - dt.timedelta(days=120),
                 ["no-attach", "no-io-90d"]),
        Resource("snap-old", "snapshot", 10, now - dt.timedelta(days=400),
                 ["no-policy"]),
        Resource("env-exp", "env", 300, now - dt.timedelta(days=60),
                 ["no-deploy-45d", "no-traffic-30d", "not-in-cmdb"]),
    ]
    sweep, watch = triage(res, now, cost_threshold=50)
    assert sweep == ["vol-orphan", "env-exp"]   # 双信号+高成本
    assert watch == ["snap-old"]                # 单信号: 只降级观察
    # 软删除排序: 按可回收月成本降序, 立即收益最大化
    sweep_sorted = sorted([r for r in res if r.rid in sweep],
                          key=lambda r: -r.monthly_cost)
    assert [r.rid for r in sweep_sorted] == ["env-exp", "vol-orphan"]
    assert sum(r.monthly_cost for r in sweep_sorted) == 420
    print(f"清扫队列 {sweep_sorted[0].rid} 先行, 共省 420 元/月; "
          f"观察 {watch}")
    print("OK: >=2 信号才定罪; 高分进软删除, 低分降级观察防误杀")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"单信号不定罪"？
→ 一句话提示：任何单一信号都有误报（磁盘临时卸载维护、环境假期暂停），两三个独立信号（无 IO + 不在 CMDB + 无流量）交叉才能把误杀率压到可接受。

**追问 2**：软删除（先归档后清）与直接删除的成本差怎么算？
→ 一句话提示：归档层存储约为热存储 1/5-1/10 且可恢复，宽限期（如 30 天）的归档成本远低于误杀一个含唯一数据资源的业务损失，是廉价保险。

## 背诵要点
- 治理闭环 = 盘点（SDK 清单 × 三事实源交叉）→ 定级（信号数 × 成本 × 年龄）→ 宽限标签 → 软删除。
- 定罪规则：≥2 个独立信号 + 月成本达阈值；单信号只降级观察——误杀代价远大于晚省钱。
- 优先用生命周期规则自动过期，SDK 清扫兜底；清扫动作幂等 + 审计留痕。

## 复盘追问
- "最后使用时间"信号缺失的资源类型怎么处理？提示：用代理信号（无 IO 日志、无访问日志、无 tag owner）组合替代，并把"补元数据"作为治理产出之一。
- 盘点流水线如何防止"扫到一半 owner 恰好开始使用"？提示：降级标签机制天然容忍——误降级的资源在使用中会触发告警快速恢复，软删除宽限期提供回滚窗口。
