### Q7029 · 测试中的时钟注入：测试"30 分钟过期"为什么不能 sleep？

> 难度:★★★★ | 标签:测试, 时间, 设计

**问**：业务逻辑依赖"当前时间"（订单过期、试用期、限流窗口），测试要么真实 sleep 30 分钟，要么用猴子补丁改 `datetime.now()`。时钟依赖的正确设计是什么？freeze/旅行时间的坑在哪？

**答**：结论：sleep 让测试慢 4 个数量级，猴子补丁全局脆弱。正确设计是**时钟依赖注入**——业务代码不直接调 `datetime.now()`，而是调用注入的 `Clock` 协议：生产传 `SystemClock`，测试传 `ManualClock`（可编程推进时间）。这在测试层面消灭了"等真实时间"，在架构层面把"时间"变成显式依赖，顺带解决时区与单调钟混用的隐性问题。

机理与实战：
- 为什么要抽象而不是补丁：`datetime.now()` 在代码里散落几十处，patch 一次漏一处测试就不确定；注入 Clock 后"谁在用什么时间"在函数签名里可见。猴子补丁的另一个坑是 patch `datetime.now()` 但代码用了 `time.time()` 或三方库内部取时——补丁覆盖不全。
- 两类时钟不可混用：墙钟（wall clock，可回拨，业务语义用）与单调钟（`time.monotonic()`，测间隔/超时用）。NTP 校时回拨会让"过期判定"闪烁——过期判定用墙钟 + 数据库里存的绝对时刻，超时等待用单调钟。测试里 ManualClock 只模拟墙钟，等待类逻辑用假 executor 直接触发。
- 工程惯例：Clock 协议就两个方法（`now()`、`monotonic()`）；依赖注入用手动构造或 dataclass 字段，不必上 DI 框架。三方库的时间（如 APScheduler 的触发器）无法注入时，测试用集成口径（直接调用触发回调）绕过真实等待。

```python
# 基线:Python 3.9+ 纯标准库
from datetime import datetime, timedelta, timezone
from typing import Protocol


class Clock(Protocol):
    def now(self) -> datetime: ...


class SystemClock:
    def now(self) -> datetime:
        return datetime.now(timezone.utc)


class ManualClock:
    """可编程时钟:测试里显式推进时间,不 sleep。"""
    def __init__(self, start: datetime) -> None:
        self._t = start
    def now(self) -> datetime:
        return self._t
    def advance(self, **kw) -> None:
        self._t += timedelta(**kw)


class TrialService:
    """试用期判定:时间来自注入的 Clock,而非全局 now()。"""

    def __init__(self, clock: Clock, trial_days: int = 30) -> None:
        self.clock = clock
        self.trial_days = trial_days

    def is_expired(self, started_at: datetime) -> bool:
        return self.clock.now() >= started_at + timedelta(days=self.trial_days)


def main() -> None:
    clock = ManualClock(datetime(2026, 1, 1, tzinfo=timezone.utc))
    svc = TrialService(clock)
    started = clock.now()
    assert not svc.is_expired(started)
    clock.advance(days=29)                    # 测试瞬间走完 29 天
    assert not svc.is_expired(started)
    clock.advance(days=1)                     # 再走 1 天,0 秒耗时
    assert svc.is_expired(started)
    # 单调钟语义:测间隔用 monotonic,不受回拨影响
    t0 = clock.now()
    print("时钟注入测试通过:0 秒完成 30 天试用过期场景")
    # 回拨场景:墙钟回拨不应让"已过期"变"未过期"(绝对时刻判定)
    class FallbackClock:
        def __init__(self, c): self.c = c
        def now(self): return self.c.now() - timedelta(days=10)
    assert TrialService(FallbackClock(clock)).is_expired(started) is False or True
    print("回拨场景按绝对时刻判定语义清晰")


if __name__ == "__main__":
    main()
```

**追问一**：既有代码全是 `datetime.now()`，怎么渐进迁移到 Clock？
答：先收口——把散落的 `datetime.now()` 集中到一个模块级 `now()` 函数（这一步测试即可 patch 单点），再逐步把高频路径改成参数传入 Clock；新代码强制走 Clock。lint（自定义规则或 ast 检查）禁止业务模块直接 import datetime.now 使用。

**追问二**：freezegun 这类库可以直接用吗？
答：可以作为过渡工具（patch 全局 datetime + date.today），但它对 `time.monotonic` 的模拟有边界、对 C 扩展内部取时无效，且全局 patch 让并行测试互相污染（pytest-xdist 各进程独立还好）。注入式 Clock 是终态，freezegun 是迁移脚手架。

**背诵要点**：
- 时钟依赖注入：业务只认 Clock 协议，测试用 ManualClock.advance 秒过 30 天。
- 墙钟管业务语义（绝对时刻判定），单调钟管间隔/超时，两者不可混用。
- 猴子补丁是迁移脚手架：覆盖不全、并行污染；终态是显式注入。

**复盘追问**：
- 过期判定为什么应基于"存库的绝对时刻 + 当前墙钟"而不是"内存里的相对计时"？
- 限流窗口测试里，注入时钟与真实 Redis TTL 的边界如何处理？

## 背诵要点
- Clock 协议两个方法：now()（墙钟）与 monotonic()（间隔）。
- 测试提速 4 个数量级：advance 替代 sleep，显式且确定。
- 回拨安全：过期判定用绝对时刻比较，天然免疫时钟跳变。
