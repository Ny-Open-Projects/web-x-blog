### Q7045 · 容量规划：一次排查打开 DEBUG 级别，三周后磁盘满了

> 难度:★★★ | 标签:容量规划, 日志工程, 保留策略

**问**：为了排查一个偶发问题，把某服务日志调到 DEBUG，排查完忘了关，三周后这台集群日志磁盘打满、连带日志采集组件 OOM。日志的容量账怎么算？分级保留策略怎么设计？为什么 DEBUG 日志必须带"自动回落"机制？

**答**：结论：日志容量账的公式是 **GB/天 = 请求量 × 每请求条数 × 平均条长 × 副本/采集倍数**，DEBUG 相对 INFO 通常放大 5-20 倍——一次"临时排查"就能把日增从 20GB 推到 200GB，而磁盘是按 INFO 基线采购的。分级保留（TRACE 级小时、DEBUG 天、INFO 周、审计类年）+ 采样 + DEBUG 自动回落（定时或容量触发）是标准防线。

机理与实战：
- **账要算四层**：应用写入量 → 采集转储量（filebeat/otlp 通常再 ×1.2）→ 存储副本量（ES 1 副本 ×2）→ 保留期总量。任何一层按错误基线估算，三周后都会爆——"临时开 DEBUG"就是最常见的第一层漂移。
- **分级保留**：按日志价值分层定 TTL：TRACE/DEBUG 24-72h（排障窗口过了就没价值）、INFO 14-30 天、安全审计类 180 天起（合规要求）。TTL 是成本旋钮：保留期减半 = 存储成本减半，比换存储引擎的收益直接得多。
- **采样与降级**：高 QPS 服务全量 INFO 也不便宜，正常期按 1%-10% 采样、错误全量保留（尾部采样思路）；DEBUG 打开时配套容量熔断——日志目录水位超 80% 自动回落 INFO 并告警。
- **DEBUG 自动回落**：动态日志级别要有 TTL（"DEBUG 级别持续 4h 后自动回落"），实现靠配置中心下发 + 进程内定时器，或日志框架的 scheduled 级别切换。忘关是人性的默认项，工程要对默认行为兜底。

```python
# 基线:Python 3.10+;纯标准库,日志容量账估算器与分级保留策略计算
from __future__ import annotations
from dataclasses import dataclass
from enum import Enum


class Level(Enum):
    DEBUG = ("debug", 24)     # (层级, 保留小时)
    INFO = ("info", 14 * 24)
    AUDIT = ("audit", 180 * 24)


@dataclass
class LogProfile:
    req_per_day: int           # 日请求量
    lines_per_req: float       # 每请求平均条数
    line_bytes: float          # 平均条长
    level_ratio: float         # 相对 INFO 基线的放大系数(DEBUG 取 8-20)
    copies: int = 2            # 存储副本数


def daily_gb(p: LogProfile) -> float:
    raw = p.req_per_day * p.lines_per_req * p.line_bytes / 1e9
    return raw * p.level_ratio * p.copies


def retention_gb(p: LogProfile, level: Level) -> float:
    """该级别的稳态占用 = 日增 GB × 放大系数 × 保留天数。"""
    return daily_gb(p) * p.level_ratio * (level.value[1] / 24)


def plan_tiered(p: LogProfile) -> dict[str, float]:
    return {lvl.value[0]: round(retention_gb(p, lvl), 1) for lvl in Level}


def demo() -> None:
    base = LogProfile(req_per_day=20_000_000, lines_per_req=15,
                      line_bytes=300, level_ratio=1.0)
    debug = LogProfile(req_per_day=20_000_000, lines_per_req=15,
                       line_bytes=350, level_ratio=12.0)
    base_daily, debug_daily = daily_gb(base), daily_gb(debug)
    print(f"INFO 日增: {base_daily:.0f} GB/天")
    print(f"开 DEBUG 后日增: {debug_daily:.0f} GB/天 (x{debug_daily / base_daily:.0f})")
    assert debug_daily / base_daily > 10
    tiered = plan_tiered(debug)
    print(f"分级保留稳态占用: {tiered}")
    # DEBUG 只留 1 天,审计 180 天:分级让总盘按价值而非峰值采购
    assert tiered["debug"] < tiered["audit"] / 100
    # 容量熔断:水位超 80% 自动回落
    disk_gb = 1500
    used = debug_daily * 20 / 86400 * 86400  # 三周累计
    assert used > disk_gb * 0.8              # 三周必爆:还原事故现场
    print("容量账:日增=请求×条数×条长×副本;分级保留按价值分层,DEBUG 带 TTL ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：为什么说"保留期减半"比"换更便宜的存储引擎"是更优先的成本手段？
答：保留期是乘在总量上的线性系数，减半立省 50% 存储与相应检索资源，且实现是改一个 TTL 配置；换引擎（ES→Loki/ClickHouse）省的是单 GB 单价（通常 30-60%），但要付迁移、双跑、查询语法迁移的工程成本。成本优化的顺序永远是"先砍无价值数据的量，再优化单位价"。

**追问二**：高 QPS 服务的 INFO 全量日志能不能也采样？
答：可以且推荐：正常期按路由键采样（如按 trace_id 哈希保留 5%），错误与慢请求全量保留（尾部采样）；聚合指标（QPS/延迟分位数）从指标系统来，不依赖日志全量。日志的定位从"记录一切"变成"记录指标解释不了的细节"——这个定位转变让日志量通常降一个数量级。

## 背诵要点
- 容量公式：日增 GB = 请求量×每请求条数×条长×副本×放大系数；DEBUG 相对 INFO 放大 5-20 倍，"临时排查"三周即可打爆按基线采购的磁盘。
- 分级保留按价值分层 TTL：DEBUG 24-72h、INFO 14-30 天、审计 180 天+；保留期减半=存储成本减半，优先于换单价更低的引擎。
- DEBUG 必须带自动回落（配置中心下发+TTL 定时回落）与容量熔断（水位 80% 回落告警）；高 QPS 服务 INFO 采样+错误全量（尾部采样）。

## 复盘追问
- 为什么 DEBUG 开关没有 TTL 就没人发现？（提示：动态配置变更没有过期语义是配置中心的治理缺口；所有"临时开关"都应登记 owner+到期时间，到期自动回落或提醒——把人的遗忘变成系统的默认行为）
- 日志磁盘打满时最先挂的为什么常是采集组件而不是应用？（提示：采集组件要在本地排队缓冲（磁盘队列），盘满后无法缓冲→内存堆积 OOM；应用日志写入走 append 大多仍可用，但 stdout 类采集断流——故障链要按组件的缓冲模型推演）
