### Q7189 · CI 分钟数与触发策略成本账

难度：P6 ｜ 标签：成本工程、CI、触发策略、缓存

基线：GitHub Actions / GitLab CI 计费口径（按 runner 分钟数或并发额度）。

**问**：团队 CI 账单一个月 3000 元，流水线单次 25 分钟，每天 200 次触发。老板要求砍一半成本但不能牺牲质量。CI 成本账怎么拆？哪些手段最有效？

**答**：
- **结论**：CI 成本 = 触发次数 × 单次时长 × runner 单价。砍成本三板斧按杠杆排序：(1) **降单次时长**——缓存（pip/uv wheel、pytest 缓存）通常省 30%~60%，但注意缓存投毒与失效策略；用 `--changed`/affected 检测只测受影响模块；分层流水线（快速 lint+单测挡 PR，重回归只跑主干与 nightly）。(2) **降触发次数**——PR 加 merge queue 合并触发（同分支多次 push 只跑最后状态），`[ci skip]`/路径过滤（改文档不跑重流水线）。(3) **降单价**——自建 runner（规模大了后边际便宜，但运维是隐性成本）与 spot 实例。
- **取舍**：路径过滤与 affected 检测有"漏跑"风险，必须保留主干全量兜底；merge queue 提升成本效率但增加排队延迟，团队小时要权衡。缓存把"装依赖 8 分钟"变"30 秒"，是单次时长最大的一刀，但缓存 key 设计不当（太粗/太细）都会让命中率归零。
- **实战**：算账表——把流水线拆成阶段耗时（checkout/装依赖/lint/单测/E2E），对每阶段问"能否缓存、能否并行、能否延后"。本案：25 分钟里装依赖 8 分钟（缓存后 1 分钟）、E2E 12 分钟（移到 merge 后）→ PR 流水线降到 ~7 分钟，月成本降 70%。

```python
# CI 成本账：阶段耗时模型与优化杠杆模拟（标准库可运行）。
def pipeline_cost(stages: dict[str, float], triggers_per_day: int,
                  price_per_min: float, days: int = 22,
                  cache_hit: dict[str, float] | None = None) -> float:
    """stages: 阶段->分钟；cache_hit: 阶段->缓存命中率(0~1)。"""
    cache_hit = cache_hit or {}
    total_min = sum(t * (1 - cache_hit.get(s, 0.0)) for s, t in stages.items())
    return round(triggers_per_day * days * total_min * price_per_min)

def report(name: str, stages: dict, cache: dict, triggers: int,
           price: float = 0.008) -> None:
    cost = pipeline_cost(stages, triggers, price, cache_hit=cache)
    print(f"{name}: 单次 {sum(t*(1-cache.get(s,0)) for s,t in stages.items()):.0f}min"
          f"，月费 {cost} 元")

if __name__ == "__main__":
    stages = {"checkout": 1, "install_deps": 8, "lint": 2,
              "unit": 2, "e2e": 12}
    report("现状", stages, {}, triggers=200)
    # 现状: 25min -> 880 元/月
    report("缓存后", stages, {"install_deps": 0.85, "checkout": 0.8},
           triggers=200)
    report("缓存+分层(merge queue)", stages,
           {"install_deps": 0.85, "checkout": 0.8, "e2e": 0.92},
           triggers=200)
    # e2e 92% 由 merge queue 摊薄：PR 上只有少数触发带 E2E
```

**追问**：
- 一层：缓存 key 怎么设计才不会"太粗全失效、太细零命中"？→ 提示：依赖缓存用 lock 文件哈希做 key（依赖不变即命中），构建产物缓存用 commit sha 前缀 + 分支回退链（restore-keys）。
- 二层：merge queue 为什么能省成本？→ 提示：N 个 PR 合并只跑 N 次队列验证，替代每个 PR 各自跑全量 + 冲突后重跑；代价是入队排队与"队列失败要二分定位"。
- 三层：自建 runner 的隐性成本有哪些？→ 提示：机器维护、扩容高峰、安全隔离（PR 代码跑在你的机器上，fork 场景需隔离）。

**背诵要点**：
1. 成本 = 触发次数 × 单次时长 × 单价；三板斧按杠杆：缓存/affected 降时长 > merge queue/路径过滤降次数 > 自建/spot 降单价。
2. 依赖缓存 key 用 lock 哈希；路径过滤与 affected 必须保留主干全量兜底防漏跑。
3. 先拆阶段耗时再优化：本案 25 分钟里装依赖 8 + E2E 12，两刀下去 PR 流水线 ~7 分钟。

**复盘追问**：
1. 为什么第一反应总是"自建 runner"？提示：自建把成本变成运维债，先用免费杠杆（缓存/分层）再考虑。
2. 如果砍掉 E2E 后线上回归变多怎么办？提示：E2E 降频≠删除，主干 merge 后 + nightly 全量是兜底，另用契约测试补层。
