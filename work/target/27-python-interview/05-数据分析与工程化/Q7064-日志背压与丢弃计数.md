### Q7064 · 日志管道背压与丢弃计数

难度：P6 | 标签：logging、背压、日志风暴、事故复盘

**问**：一次下游故障触发 10 万 QPS 的 ERROR 日志风暴，把应用线程拖死了——为什么 logging 能拖垮业务？日志管道的背压应该在哪一层做？

**答**：
- **结论**：logging 默认是同步的：emit → handler 格式化 → 网络/磁盘 IO，全在业务线程里执行。日志风暴时每条日志 1ms 的远端写入就把 worker 全部时间吃掉——日志从"旁路"变成了"主路"。背压三件套：① QueueHandler+QueueListener：业务线程只做无阻塞入队，IO 移到独立线程；② 有界队列：满了就丢（`put_nowait` + 丢弃计数），绝不阻塞也不无限堆积；③ 丢弃计数与降级采样进监控——丢日志要有数，也要有"每 N 条保 1 条"的采样策略保住样本。
- **取舍**：丢弃违背"日志完整性"，但对可用性是正确取舍：宁可丢 ERROR 也不能拖垮交易线程。分级缓解：风暴场景先降级别（ERROR→采样）、再限源（对重复错误做指纹聚合，同签名每秒只记 1 条——聚合比丢弃更保信息量）。
- **实战**：事故复盘三步：① 确认 handler 是同步的且目标是远端；② 换 QueueHandler + 有界队列 + 计数；③ 加错误指纹聚合（同一异常签名限速）。另外 Python 3.12+ 的 `logging.getHandlerByName` 与 QueueListener 冷却/停止要进优雅停机流程，否则丢尾日志。

```python
"""日志管道背压：非阻塞投递 + 丢弃计数，日志风暴不拖垮业务线程。"""
import logging, logging.handlers, queue

q = queue.Queue(maxsize=100)                     # 有界队列 = 背压的第一道闸
dropped = {"count": 0}

class CountingQueueHandler(logging.handlers.QueueHandler):
    def enqueue(self, record):
        try:
            self.queue.put_nowait(record)
        except queue.Full:
            dropped["count"] += 1                # 丢弃计数是容量告警的依据

h = CountingQueueHandler(q)
logger = logging.getLogger("app")
logger.setLevel(logging.INFO)
logger.addHandler(h)
logger.propagate = False

for i in range(1000):                            # 模拟日志风暴
    logger.info("event %d", i)

print(f"队列深度 {q.qsize()}/100，丢弃 {dropped['count']} 条")
print("要点：日志 handler 永远不阻塞业务线程；有界队列+丢弃计数，宁可丢日志不可拖垮服务")
```

**追问链**：
1. 追问一层：为什么不用"无限队列"扛风暴？（内存无界增长 OOM，只是把拖死变成延迟爆；有界+丢弃才是背压语义）
2. 追问二层：错误指纹聚合怎么做才不丢关键差异？（签名含异常类型+规范化位置，聚合窗口内第一条全文记录、后续只计数；窗口结束若计数异常高再升级告警）

**背诵要点**：
1. logging 默认同步，远端 handler 会在日志风暴时拖死业务线程。
2. 背压三件套：QueueHandler 移 IO、有界队列丢弃、丢弃计数进监控。
3. 同签名限速聚合优于裸丢弃；优雅停机要处理 QueueListener 尾巴。

**复盘追问**：
1. 丢弃计数打满后告警没人配，等于白丢，怎么补？（丢弃率作为独立告警项，与错误率同等地位）
2. 为什么风暴期间"降日志级别"比"扩日志服务"见效快？（级别是源头节流，秒级生效；扩容是下游扛量，分钟级且有限）
