### Q7070 · 队列积压的可观测与积压处置

难度：P6 | 标签：任务队列、积压、容量规划、告警设计

**问**：告警"队列深度 10 万条"要不要半夜起来扩容？积压的正确度量是深度还是别的？"积压处置"为什么不能只靠加消费者？

**答**：
- **结论**：积压的正确度量是"排空时长"，不是深度：10 万条深度、消费速率 1 万/秒是 10 秒的正常波动，5 千条深度但出速 < 入速则永远排不完。排空时长 = 深度 / max(出速 − 入速, ε)；当出速 ≤ 入速时任何告警都只是等死——必须动容量（扩消费者/提单消费者吞吐）或动源头（上游降速、削峰）。告警分级：按排空时长分级（>SLA 告警，>SLA×2 呼人），而不是按绝对深度。
- **取舍**：扩消费者的边界：队列是分区的（Kafka 类）时消费者数 ≤ 分区数，加再多人也没用——分区数是并行度上限，这是"加机器解决不了"的经典场景。上游降速的代价是业务延迟，要有租户级公平（不能只降小客户）。丢弃：低价值任务（日志型、统计型）允许超龄丢弃，任务带 deadline，出队时过期即弃。
- **实战**：观测三指标：深度（瞬时）、入速/出速（速率差是趋势）、最老消息年龄（等价于端到端等待时间，用户视角最真实）。处置清单按序：查消费者是否卡死（慢任务/死循环）→ 提并发 → 扩实例 → 上游降速 → 丢弃超龄低价值任务。复盘要点：积压事故的根因往往是"消费速率没有随上游增长重新评估"。

```python
"""队列积压的可观测：深度、排空时长与降速处置。"""
RATE_IN, RATE_OUT = 10, 8          # 条/秒：入速 > 出速 => 积压持续增长
ALERT_DEPTH = 5000

depth = 0
for _ in range(10):                # 模拟 10 秒
    depth += RATE_IN - RATE_OUT
print(f"10 秒后积压 {depth} 条；出速 {RATE_OUT} < 入速 {RATE_IN}，永不清零，只能动容量")

def drain_hours(depth):
    if RATE_IN >= RATE_OUT:
        return float("inf")
    return depth / (RATE_OUT - RATE_IN) / 3600

def handle(depth):
    if RATE_IN >= RATE_OUT:
        return "扩容消费者 / 上游降速（排队解决不了负差距）"
    if depth > ALERT_DEPTH:
        return "告警：排空需 %.1f 小时" % drain_hours(depth)
    return "正常"

print(depth, "->", handle(depth))
print("要点：积压看'排空时长'而非深度；出速追不上入速时告警只是等死，必须动容量")
```

**追问链**：
1. 追问一层：为什么"最老消息年龄"比深度更贴近用户感受？（用户感知的是自己那条消息等多久；深度平均会掩盖长尾，最老年龄直接是端到端等待的上界）
2. 追问二层：消费者数已等于分区数还不够快，还有什么路？（提单消费者吞吐：批量化消费、把重 IO 移出消费线程、任务瘦身；再不够才分区扩容——那是有状态变更，成本高）

**背诵要点**：
1. 度量排空时长 = 深度/(出速−入速)；出速≤入速时告警无意义，必须动容量。
2. 分区队列的消费者并行度上限是分区数，加机器有天花板。
3. 观测三指标：深度、速率差、最老消息年龄；低价值任务可按 deadline 丢弃。

**复盘追问**：
1. 扩容后积压没降，查什么？（消费者数已到分区上限，或慢任务卡住部分分区）
2. 为什么"积压告警阈值按深度"是错误设计？（不同时段正常深度差异巨大，按排空时长才与 SLA 对齐）
