### Q7074 · 生产日志 PII 泄漏事故复盘

难度：P6 ｜ 标签：日志 / PII / 脱敏 / 事故复盘 / 合规

**问**：安全扫描发现生产日志里存了大量用户手机号与身份证号——某同事调试时 `logger.info(f"user={user}")` 把 ORM 对象整包打了出去，且日志平台保留 180 天。复盘：怎么让这类事故从"靠自觉"变成"结构上不可能"？

**答**：

**结论**：根因是日志出口缺少一层"强制脱敏"：日志语句直接格式化业务对象，序列化行为不可控。正确架构是在 handler/formatter 层做统一拦截（structlog 的 processor 链 / logging.Filter），对敏感 key（phone/id_card/token/email）做掩码或丢弃；再配 CI 门禁：静态扫描日志语句里的可疑字段名与裸 f-string 打对象模式。合规侧还差半步：泄漏已发生的，要按保留策略清历史日志（从日志平台按 trace 删除或整卷过期重配），并走数据安全事件上报流程——很多人只改代码不处理已泄漏存量。

**取舍**：拦截层放哪里有讲究——① formatter 层：覆盖所有输出但只能看最终字符串，正则误杀/漏杀风险高；② processor/filter 层：能看结构化字段，精确但要维护字段字典；③ 序列化层（ORM `__repr__` 打码）：最彻底但影响调试体验。生产上选 ② 为主 + ③ 给最敏感模型兜底，① 的正则只做最后一道网（对非结构化文本兜住漏网模式）。性能账：脱敏 processor 必须快（<0.1ms/条），热路径上不能做全量正则回溯。

**实战**：字段字典要"allowlist 反向思维"维护：默认所有 `*_phone/*_id_card/token/authorization` 打码，新增敏感字段靠 dataclass 元数据标注（`field(metadata={"pii": True})`）自动进字典，不靠人记得更新列表。日志分级策略：DEBUG 在生产关闭是第一道闸（事故正是 debug 级调试语句被留开）；结构化日志里 user 一律记 `user_id` 不记整个对象。

```python
# structlog 风格的 PII 脱敏 processor（纯标准库实现核心逻辑）
# 仅标准库，Python 3.9+；生产建议 structlog>=24
from __future__ import annotations

import re

PII_KEY_RE = re.compile(r"(phone|mobile|id_card|idcard|token|secret|password)", re.I)
PHONE_RE = re.compile(r"(1[3-9]\d)\d{4}(\d{4})")
ID_RE = re.compile(r"(\d{6})\d{8}(\w{4})")


def mask_value(v: str) -> str:
    v = PHONE_RE.sub(r"\1****\2", v)
    v = ID_RE.sub(r"\1********\2", v)
    return v


def pii_processor(logger, method_name, event_dict):  # noqa: ANN001
    """structlog processor：敏感 key 打码，字符串值兜底扫描。"""
    out = {}
    for k, v in event_dict.items():
        if PII_KEY_RE.search(k):
            out[k] = "***"
        elif isinstance(v, str):
            out[k] = mask_value(v)  # 兜底：值里藏了手机号也打掉
        else:
            out[k] = v
    return out


def main() -> None:
    event = pii_processor(
        None, "info",
        {"event": "user login", "user_id": 42,
         "mobile": "13812345678", "note": "backup phone 13987654321"},
    )
    print(event)
    assert event["mobile"] == "***"
    assert "13812345678" not in event["note"]
    assert event["note"] == "backup phone 139****4321"
    assert event["user_id"] == 42  # 非敏感字段不受影响

    # 门禁：模拟扫描日志语句，裸打对象应告警
    bad_stmts = [
        'logger.info(f"user={user}")',          # 裸对象 → 高危
        'logger.info("login", user_id=uid)',    # 结构化 → OK
    ]
    flagged = [s for s in bad_stmts
               if re.search(r"f\".*\{[a-z_]+\}\"", s)]
    print("门禁拦截:", flagged)
    assert len(flagged) == 1


if __name__ == "__main__":
    main()
```

**追问链**：

- 追问 1：为什么"默认敏感字段字典"会过时，dataclass metadata 标注更好？——字典靠人维护，新字段上线忘加就漏；metadata 标注跟字段定义同文件同 commit，review 时天然可见，漏标成本显性化。反向兜底（值内正则）再补一层。
- 追问 1.1：已泄漏的 180 天历史日志怎么合规处置？——三条路径按平台能力选：按 trace/用户 ID 检索删除（精确但可能漏）、时间点之后整卷删除（粗暴但可审计）、调短保留期让数据自然过期（最慢）。要走事件上报与影响评估（多少用户、多久），不能静默处理。
- 追问 2：脱敏 processor 的性能红线怎么保证？—— processor 里禁止无界回溯正则、禁止递归处理深层嵌套大对象；对热路径 logger 用懒计算（惰性格式化），压测 P99 增量 <0.1ms/条，超出就降级为"敏感 key 全丢而非打码"。

**背诵要点**：

1. 脱敏必须在 handler/processor 层强制拦截，不能靠日志语句自觉；敏感 key 默认打码 + 字符串值正则兜底。
2. 敏感字段字典用 dataclass metadata 标注随字段定义走，避免人工字典过时。
3. 事故处置含存量：历史日志按 trace 删除/整卷过期/缩短保留期三选一，并走数据安全上报流程。
