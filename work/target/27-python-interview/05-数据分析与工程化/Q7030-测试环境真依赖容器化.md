### Q7030 · 测试环境真依赖容器化：mock 掉数据库的集成测试还测了什么？

> 难度:★★★★ | 标签:测试, Docker, 集成测试

**问**：团队把集成测试里的 PostgreSQL/Redis 全 mock 掉，"测试全绿但线上炸"的事故频发。testcontainers 思路怎么在 CI 里给测试起真依赖？真依赖测试的慢与不稳定怎么治理？

**答**：结论：mock 只验证"你假设的行为"，不验证"依赖的真实行为"——SQL 方言差异、事务隔离、TTL 精度、连接池握手这些事故源头 mock 全都看不见。testcontainers 思路：测试启动时在 CI 里拉起一次性真容器（随机端口、自动等待 ready、测试结束销毁），集成层用真库跑。慢与不稳的治理靠三层：**会话级容器复用**（同一测试 session 共用一个容器，不是每个用例起一个）、**数据隔离用事务回滚/独立 schema** 而不是重建容器、**ready 等待用依赖自身的探针**（pg_isready/ping）而不是 sleep。

机理与实战：
- 分层原则不变：单测照旧 mock（快、隔离），集成测试必须真依赖。问题是团队常用 mock 顶替集成层；容器化后集成测试的数量应该"少而准"——覆盖关键 SQL、事务边界、缓存 TTL 语义，而不是复制全部用例。
- 速度账：一次容器冷启动 3-10 秒，session 级复用后整个集成套件只付一次；数据清理用"每个测试类一个独立 schema + drop"或事务回滚，比 TRUNCATE 快且不怕并发。CI 缓存容器镜像（docker layer cache）后冷启动进秒级。
- 稳定性账：真依赖引入新故障面（端口冲突、镜像拉取失败、ready 竞态）。对策：随机端口由容器框架分配（不要写死 5432）、ready 探针带重试上限、镜像 tag 固定版本（不追 latest），失败重试只允许在基础设施层（拉镜像），不允许吞测试断言失败。

```python
# 基线:Python 3.9+ 标准库 ;演示容器生命周期管理与 ready 探针骨架
import socket
import time
import subprocess


class OneShotContainer:
    """一次性依赖容器:随机端口 + 探针等待 + session 级复用。"""

    def __init__(self, image: str, internal_port: int,
                 ready_probe: "callable") -> None:
        self.image = image
        self.internal_port = internal_port
        self.ready_probe = ready_probe
        self.container_id: str | None = None
        self.host_port: int | None = None

    def start(self, timeout_s: float = 30) -> None:
        r = subprocess.run(
            ["docker", "run", "-d", "-P", self.image],      # -P 随机宿主端口
            capture_output=True, text=True, check=True)
        self.container_id = r.stdout.strip()
        mp = subprocess.run(
            ["docker", "port", self.container_id, str(self.internal_port)],
            capture_output=True, text=True, check=True)
        self.host_port = int(mp.stdout.strip().split(":")[-1])
        deadline = time.monotonic() + timeout_s             # 探针等待,不用 sleep
        while time.monotonic() < deadline:
            try:
                if self.ready_probe("127.0.0.1", self.host_port):
                    return
            except OSError:
                pass
            time.sleep(0.2)
        self.stop()
        raise TimeoutError(f"{self.image} 未在 {timeout_s}s 内就绪")

    def stop(self) -> None:
        if self.container_id:
            subprocess.run(["docker", "rm", "-f", self.container_id],
                           capture_output=True)
            self.container_id = None


def tcp_probe(host: str, port: int) -> bool:
    """最小 ready 探针;生产换 pg_isready / redis ping。"""
    with socket.create_connection((host, port), timeout=1):
        return True


def demo() -> None:
    if subprocess.run(["docker", "info"], capture_output=True).returncode != 0:
        print("docker 不可用,降级演示探针逻辑:")
        # 探针语义:拒绝连接=未就绪,连接成功=就绪
        try:
            tcp_probe("127.0.0.1", 1)
        except OSError:
            print("端口 1 拒绝连接 -> 判定未就绪(符合预期)")
        s = socket.socket()
        s.bind(("127.0.0.1", 0))                             # 随机端口模拟服务
        s.listen(1)
        port = s.getsockname()[1]
        assert tcp_probe("127.0.0.1", port)
        print(f"随机端口 {port} 探针就绪 -> 容器等待协议可复用")
        s.close()
        return
    c = OneShotContainer("redis:7-alpine", 6379, tcp_probe)
    c.start()
    try:
        print(f"redis 容器就绪,宿主端口 {c.host_port}")
    finally:
        c.stop()                                             # 测试结束必清理
        print("容器已销毁")


if __name__ == "__main__":
    demo()
```

**追问一**：集成测试用真库后，"测试间数据隔离"怎么做最稳？
答：优先级：独立 schema（快，全量清理）> 事务回滚（最快，但应用层自己管理事务时不可用）> TRUNCATE（慢且要处理外键顺序）。禁用"共享表 + 手动清理"——清理失败会级联污染后续用例，是 flaky 的最大来源。

**追问二**：CI 里没有 docker 环境时怎么办？
答：退路依次是：CI 提供的 service 容器（GitHub Actions services，生命周期由平台管）、内存替身（SQLite/fakeredis，但仅限语义兼容的用例并明确标注）、最后才是 mock。关键纪律：**用内存替身跑过的用例不能再声称是"集成测试"**，报告里要分层标注。

**背诵要点**：
- mock 测的是假设，真依赖测的是事实；集成层必须容器化真库。
- 速度治理三招：session 级容器复用、schema/事务级数据隔离、探针等待不 sleep。
- 稳定性纪律：随机端口、固定镜像 tag、ready 探针带超时、结束必清理。
