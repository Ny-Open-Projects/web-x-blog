### Q7196 · 构建隔离与依赖约束漂移事故复盘

难度：P6 ｜ 标签：事故复盘、PEP 517、构建隔离、可复现构建

基线：Python 3.12；pip 23+；pyproject.toml `[build-system]`；re 标准库演示。

**问**：CI 上 `pip install .` 突然开始拉新版 setuptools 并构建失败，本地却一切正常。代码没改，为什么构建行为变了？`--no-build-isolation` 和 `PIP_CONSTRAINT` 分别能解决什么？

**答**：
- **结论**：PEP 517/518 的**构建隔离**让 pip 在临时环境里按 `pyproject.toml [build-system].requires` 安装构建依赖（如 `setuptools>=61`、`wheel`），而不使用当前环境的版本。这保证了构建不受本机污染，但如果 `requires` 写的是下限（`>=61`）而非精确版本，每次构建都可能拉到更新的版本，行为随之上漂——今天新版 setuptools 改了行为，CI 就红了。
- **取舍**：`--no-build-isolation` 直接用当前环境构建、快且可控，但前提是环境里预装了正确版本的构建依赖，否则更难复现；`PIP_CONSTRAINT` 环境变量可以给构建依赖也施加约束文件，实现"既隔离又可复现"，是更稳的做法。另一个要求是 `requires` 尽量给出上界或精确版本。
- **实战**：在 `pyproject.toml` 里锁构建依赖版本范围；CI 里用 `PIP_CONSTRAINT=constraints.txt pip install .`；把构建依赖纳入 lock/镜像管理；构建失败时先打印实际使用的 setuptools 版本定位漂移。

```python
import re


def will_drift(requires: list[str], pinned: dict[str, str]) -> list[str]:
    """检查构建依赖里哪些没被约束，可能在隔离构建时拉到新版本。"""
    drift = []
    for req in requires:
        m = re.match(r"^([A-Za-z0-9_.-]+)", req)
        name = m.group(1) if m else req
        # 只有 == 精确版本才算锁定；>= / ~= 等下限约束仍可能拉到新版本
        if "==" not in req and name not in pinned:
            drift.append(f"{name}: 未精确锁定，构建时可能拉到新版本")
    return drift


if __name__ == "__main__":
    reqs = ["setuptools>=61", "wheel"]
    print("无约束:", will_drift(reqs, {}))
    print(
        "PIP_CONSTRAINT 锁定:",
        will_drift(reqs, {"setuptools": "68.0.0", "wheel": "0.41.0"}),
    )
```

**追问一**：构建隔离的收益和风险分别是什么？
→ 解析：收益是构建环境与本机解耦、结果更一致、不受用户全局包污染；风险是 `requires` 若浮动，构建依赖本身成为新的漂移源，需要用约束文件或版本上界锁住。

**追问二**：`pip install .` 和 `pip install -e .` 在构建隔离上有什么差异？
→ 解析：可编辑安装（PEP 660）同样会走构建隔离来准备后端，但会把源文件以挂钩方式暴露而非拷贝到 site-packages；两者都要注意构建依赖锁定，差别主要在产物形态而非隔离机制。
