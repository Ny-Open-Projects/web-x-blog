### Q7130 · PEP 695 类型参数语法（`class C[T]` / `def f[T]` / `type` 语句）的演进与迁移点

难度：P6 ｜ 标签：版本演进 / 类型系统 / Python 3.12

**问**：Python 3.12 落地 PEP 695，泛型写法从 `Generic[T]`/`TypeVar` 换成 `class Box[T]:` 和 `type Vec[T] = list[tuple[T, T]]`。新语法解决了旧写法的什么痛点？迁移要注意哪些版本下限和工具链适配？变体（variance）为什么从手写 covariant/contravariant 变成自动推断？

**答**：
- **结论**：旧语法的三个痛点被解决：① **TypeVar 泄漏**——`T = TypeVar("T")` 是模块级全局变量，同一个 T 被多个类/函数复用时语义纠缠（运行时只是个字符串标记，作用域全靠自觉）；新语法 `def f[T](x: T) -> T` 让类型参数**作用域限定在声明处**，作用域由解释器静态维护（types.GenericAlias 的隐式作用域）。② **变体手写易错**——旧 `TypeVar("T", covariant=True)` 手写错会导致检查器报出奇怪的不兼容；新语法由检查器（pyright/mypy ≥ 相应版本）自动推断变体，声明更短且不易错。③ **递归类型别名**——旧写法 `JSON = Union[dict, list, str, int, ...]` 无法自引用，要靠前向引用字符串拼；新 `type Json = dict[str, Json] | list[Json] | str | int | float | None | bool` 原生支持递归惰性求值。迁移点：语法本身 **3.12+ 才能运行**（不是仅注解，是运行时语法），库代码要用新语法则 `requires-python >= 3.12`，或维持旧写法双轨；typing_extensions 提供 `TypeAliasType` 给旧版本近似 `type` 语义但类/函数方括号语法无 polyfill；mypy 需要 ≥1.7、pyright 全程支持，ruff 有 `UP040` 规则自动把旧别名改写为新语法。
- **取舍**：库作者该不该切新语法？判定标准是 `requires-python` 下限：库用户还有 3.10/3.11 时不能切（运行时语法，import 即炸），应用代码（自家 3.12+）放心切、ruff UP040 一键迁移。另一个取舍：类型别名 `type X = ...` 是惰性求值（用到才解析），大量互引别名的模块 import 时间反而下降——这为 3.14 的 PEP 649 注解惰性化铺路。
- **实战**：① 迁移脚本：ruff `--select UP040` 扫别名 + 人工过泛型类/函数；② `pyproject.toml` 固化 requires-python 与 ruff/mypy 版本矩阵；③ 变体交给检查器：删掉手写 covariant 后跑全量类型检查对比，防推断差异；④ 团队规约新代码直接新语法、旧代码不专门回头改（搭车迁移）。

```python
# PEP 695 基线: Python 3.12+; 旧写法对比仅注释演示
import sys

if sys.version_info < (3, 12):
    raise SystemExit("PEP 695 语法需要 Python 3.12+")

# 新语法: 类型参数作用域限定在声明处
type Json = dict[str, "Json"] | list["Json"] | str | int | float | bool | None


class Box[T]:
    def __init__(self, value: T) -> None:
        self.value = value

    def get(self) -> T:
        return self.value


def identity[T](x: T) -> T:
    return x


def main() -> None:
    b: Box[int] = Box(42)
    assert b.get() == 42
    assert identity("x") == "x"
    # 递归别名可用: 嵌套结构直接通过
    doc: Json = {"a": [1, "x", {"b": None}]}
    assert doc["a"][2]["b"] is None
    # 每次泛型实例化产生独立作用域, 不共享模块级 TypeVar
    assert Box[str]("s").get() == "s"
    print("OK: PEP695 作用域内联/自动变体/递归别名(type语句, 惰性求值)")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么说旧 TypeVar 的作用域是"靠自觉"而新语法是真作用域？
→ 一句话提示：旧 `T = TypeVar("T")` 是模块级对象，多个类复用同一个 T 在语义上无任何隔离，冲突时检查器才能发现；新语法的 `[T]` 由解释器建立词法作用域（3.12 起 types 泛型类自带 `__type_params__`），声明即边界。

**追问 2**：`type` 别名的惰性求值对大型代码库有什么实际收益？
→ 一句话提示：别名右侧的注解在首次使用时才解析，互相引用的别名链不会在 import 时全量展开——import 时间与循环引用问题同时缓解，也是向 PEP 649（注解全面惰性化）过渡的语义准备。

## 背诵要点
- PEP 695（3.12+）：`class C[T]`/`def f[T]` 类型参数词法作用域化、变体自动推断、`type` 语句支持递归惰性别名——旧 TypeVar 三痛点全解。
- 语法是运行时语法：切新语法 = requires-python ≥ 3.12；旧版本靠 typing_extensions.TypeAliasType 近似，方括号语法无 polyfill。
- 迁移工具链：ruff UP040（别名一键改写）+ mypy ≥1.7；库代码随下限，应用代码放心切、旧代码搭车迁移。

## 复盘追问
- 为什么库作者切新语法的约束比应用严格得多？提示：库的 requires-python 是对用户环境的承诺，运行时语法在旧解释器 import 即 SyntaxError——兼容性账在发布时一次算清，不能靠 try/except。
- 自动变体推断后，"手写 covariant=True 写错"这类 bug 如何被消除？提示：变体由检查器从使用位置推导，声明错误在类型检查期直接报出；团队规约删手写变体后跑全量检查对比，可暴露旧声明里的隐性错误。
