### Q7109 · 测试覆盖率工具与 CI 时长的成本账

难度：P6 ｜ 标签：成本工程 / 测试 / CI

**问**：CI 流水线单次 22 分钟，其中 `pytest --cov --cov-branch` + 覆盖率合并报告占 9 分钟。有人建议"全量 PR 都跑覆盖率"，有人建议"只在主干跑"。这笔 CI 时间账怎么算？覆盖率数据真正值钱的地方在哪？

**答**：
- **结论**：覆盖率采集的成本结构：`--cov` 让 pytest 用 tracing/sys.monitoring 钩住每一行执行，通常拖慢测试 30-100%（数据科学栈的 pandas/numpy 调用多，C 扩展部分影响小，纯 Python 层影响大）；报告合并与上传再加固定几分钟。所以账要按"两列"算：**PR 流水线**（几百次/天，开发者等结果）追求分钟级，覆盖率全量跑 = 每人每天多等几十分钟，是重复付费；**主干/夜间流水线**（几十次/天，机器等机器）跑全量覆盖率 + 趋势存档，成本可忽略。覆盖率数据真正值钱的是**趋势与缺口地图**（哪些模块长期 <40%、diff 覆盖率是否下降），不是 PR 门禁那一刻的数字。
- **取舍**：策略矩阵：① PR 级：只跑受影响路径的测试（pytest-testmon/按目录映射），覆盖率不跑或只算 **diff 覆盖率**（coverage 只对新增行，快且是门禁真正要的语义）；② 主干/夜间：全量覆盖率 + HTML/JSON 报告入库，画趋势；③ 3.12+ 可用 `sys.monitoring` 后端的 coverage 7.4+，开销显著下降（升级覆盖率工具本身就是降本）；④ 门禁语义定清楚：`--cov-fail-under` 用在主干趋势线（如周环比不降），PR 用 diff 覆盖率阈值（新增行 ≥80%）。反模式：全量 PR 跑覆盖率但没人看报告——纯烧 CI 分钟数（见 Q7047）。
- **实战**：落地步骤：① profile 拆账：把 CI 22 分钟分解到 job/步骤，覆盖率 9 分钟里多少是 tracing、多少是报告合并；② PR 流水线去 `--cov`，加 testmon/目录映射定向测试，目标 <10 分钟；③ 主干夜间跑 `coverage run -m pytest` + `coverage json`，报告存对象存储/制品库，趋势图接内部看板；④ diff 覆盖率用 `coverage json --fail-under` 结合 git diff 解析实现；⑤ 季度复盘：CI 分钟数账单 vs 测试逃逸率，验证覆盖率趋势是否真的拦住了坏变更。

```python
# CI 时间账：PR 定向测试 vs 全量覆盖率的成本模型（标准库模拟）
# 基线：Python 3.9+；真实数据来自 CI API（GitHub Actions / GitLab）

from dataclasses import dataclass


@dataclass
class Pipeline:
    name: str
    runs_per_day: float
    base_minutes: float
    cov_overhead_minutes: float     # 覆盖率额外开销
    cov_enabled: bool

    def daily_minutes(self) -> float:
        cov = self.cov_overhead_minutes if self.cov_enabled else 0.0
        return self.runs_per_day * (self.base_minutes + cov)


def overhead_factor(base_test_minutes: float) -> float:
    """coverage tracing 对纯 Python 测试的典型放大 1.3-2.0×"""
    return 1.7


def main() -> None:
    unit_test_min = 5.0
    factor = overhead_factor(unit_test_min)
    assert 1.2 <= factor <= 2.5

    pr_full = Pipeline("PR 全量+覆盖率", runs_per_day=300, base_minutes=22 + unit_test_min * (factor - 1),
                       cov_overhead_minutes=9, cov_enabled=True)
    pr_targeted = Pipeline("PR 定向测试(无覆盖率)", runs_per_day=300, base_minutes=8,
                           cov_overhead_minutes=0, cov_enabled=False)
    nightly = Pipeline("主干夜间全量覆盖率", runs_per_day=1, base_minutes=30,
                       cov_overhead_minutes=9, cov_enabled=True)

    for p in (pr_full, pr_targeted, nightly):
        print(f"{p.name}: {p.daily_minutes():,.0f} CI 分钟/天")

    assert pr_targeted.daily_minutes() < pr_full.daily_minutes() * 0.5
    saving = pr_full.daily_minutes() - pr_targeted.daily_minutes()
    print(f"OK: PR 侧省 {saving:,.0f} 分钟/天，覆盖率数据只留在夜间主干（每天 {nightly.daily_minutes():.0f} 分钟）")


if __name__ == "__main__":
    main()
```

**追问 1**：diff 覆盖率和全量覆盖率作为 PR 门禁，哪个语义更对？
→ 一句话提示：门禁要回答的是"这次变更有没有被测到"，diff 覆盖率（新增/修改行的覆盖）直接对应这个语义且计算便宜；全量数字被存量债务污染，做门禁会把历史包袱算到新变更头上。

**追问 2**：coverage.py 7.4+ 用 `sys.monitoring`（3.12+）为什么能大幅降开销？
→ 一句话提示：CPython 3.12 的 sys.monitoring 是解释器原生的事件回调机制，替代逐字节码的 settrace/tracing 慢路径，开销从数倍降到接近几十个百分点以内——所以"升 Python + 升 coverage"本身就是一笔 CI 降本。

## 背诵要点
- 覆盖率开销 30-100%：PR 流水线（人等）不跑全量覆盖率，主干/夜间（机器等）跑全量存趋势。
- 门禁语义用 diff 覆盖率（新增行 ≥80%），趋势门禁用主干周环比不降；全量数字不是门禁素材。
- 降本顺序：先 CI 拆账 profile → 定向测试（testmon/目录映射）→ coverage 7.4+ / Python 3.12+ sys.monitoring。

## 复盘追问
- 覆盖率趋势看板上线后，怎么防止团队"刷覆盖率"？提示：刷覆盖率（写无断言测试）靠质量抽检与突变测试（mutmut）反制——变异数 killed ratio 才是测试有效性的真实口径。
- 如果覆盖率 9 分钟里大头其实是"报告合并上传"而不是 tracing？提示：拆账后对症下药——报告合并并行化/只在主干跑、PR 只传 JSON 摘要；工具开销与流水线编排开销是两类账。
