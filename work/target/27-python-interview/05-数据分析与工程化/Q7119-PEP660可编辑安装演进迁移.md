### Q7119 · PEP 660 可编辑安装（editable install）的演进与迁移点

难度：P6 ｜ 标签：版本演进 / 打包 / PEP 660

**问**：团队从 `pip install -e .`（setup.py develop 时代）迁移到 PEP 660 的 editable wheel 后，部分同事反馈"IDE 跳转/pytest 收集行为变了"。PEP 660 到底改了什么？新旧机制的本质差异是什么？迁移要审哪些点？

**答**：
- **结论**：机制差异：① **旧机制**——`setup.py develop`/legacy `pip install -e` 在 site-packages 写 `.egg-link` + easy-install.pth，把**源码目录**直接塞进 `sys.path`；包内任何文件变动即时生效，但目录以"非包"形态暴露，命名空间包、data files、入口点都靠 setuptools 特殊处理；② **PEP 660**——构建后端生成一个 `*.editable-*.whl`，里面是一个**重定向层**（.pth 文件或 `__editable__` finder 模块），pip 当普通 wheel 装。收益：与正式安装同构（卸载干净、data files/入口点正确）、后端中立（hatch/pdm/flit 都支持）、不再依赖 setup.py。行为变化点：重定向有**两种模式**——strict（finder 按模块精确映射，子包/动态生成的文件可能找不到）与 lenient（.pth 加目录，行为接近旧机制）；pytest 的 rootdir/importmode 交互、IDE 静态解析（`__editable__` finder 对 IDE 是黑盒，跳转可能失灵，需 IDE 支持 .pth 解析）；monorepo 多包 editable 间的相对导入与命名空间包边界。迁移审点：CI 里 editable 与普通安装各跑一遍测试（防"只在 editable 下能过"的路径依赖）；检查 data files/入口点是否仍生效；IDE 配置指向 src 布局源码目录。
- **取舍**：布局选择：src 布局（`src/pkg/`）与 PEP 660 配合最好——测试默认 import 安装版本而非就地目录，消灭"本地过、CI 挂"的 import 分叉；扁平布局下 pytest 会把就地目录插进 sys.path（rootdir conftest 机制），editable 重定向可能与就地包冲突（strict 模式找不到、lenient 模式加载两次）。要不要全面迁：legacy `setup.py develop` 已被 setuptools 弃用，长期必须迁；短期可 lenient 模式兜底（行为等价旧机制），再逐仓库转 strict + src 布局。
- **实战**：落地清单：① pyproject.toml 声明 build-backend 与 editable 模式（setuptools 64+ 的 `[tool.setuptools] package-data`/`editable-mode` 配置）；② CI 双模式测试矩阵（editable + wheel install）；③ IDE（PyCharm/VSCode）升级到支持 PEP 660 的版本，或对 IDE 加 src 路径；④ pytest 配置 `importmode=importlib` 消除就地导入歧义；⑤ 锁 setuptools >= 64（PEP 660 支持起点）。

```python
# PEP 660 editable 重定向 vs legacy egg-link 的行为差异模拟
# 基线：Python 3.9+ 标准库；真实验证 pip install -e .（setuptools>=64）
from dataclasses import dataclass


@dataclass
class InstallMode:
    name: str
    strict: bool


def resolves(mode: InstallMode, path: str, src_files: set[str]) -> bool:
    """strict=精确模块映射; lenient=目录级 pth。"""
    if mode.strict:
        return path in src_files
    return any(path == f or path.startswith(f.rsplit("/", 1)[0] + "/")
               for f in src_files)


def audit(mode: InstallMode, src_files: set[str], extra_files: set[str]) -> list[str]:
    issues = []
    for f in extra_files:                      # 运行期动态生成/未在构建时登记的文件
        if not resolves(mode, f, src_files):
            issues.append(f"strict 模式解析不到: {f}")
    if mode.strict and any("plugin" in f for f in extra_files):
        issues.append("插件/入口点文件须在构建清单中显式登记")
    return issues


def main() -> None:
    src = {"pkg/core.py", "pkg/utils.py", "pkg/plugin.py"}
    runtime_gen = {"pkg/generated_table.py"}   # 运行期生成的模块

    legacy = InstallMode("legacy-develop", strict=False)
    p660_strict = InstallMode("pep660-strict", strict=True)
    p660_lenient = InstallMode("pep660-lenient", strict=False)

    assert audit(p660_strict, src, runtime_gen), "strict 应报动态文件缺失"
    assert audit(p660_lenient, src, runtime_gen) == []
    print("strict 精确映射会漏运行期生成文件 -> 登记构建清单或退 lenient")

    # 迁移矩阵：legacy 行为 == lenient，CI 两者都过才算迁移安全
    for f in src | runtime_gen:
        assert resolves(legacy, f, src) == resolves(p660_lenient, f, src)
    print("OK: PEP660 与正式安装同构; 迁移审点=动态文件登记/双模式CI/IDE路径")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 src 布局 + editable 组合能消灭"本地过、CI 挂"？
→ 一句话提示：src 布局下就地目录不在 import 路径上，测试必然走安装版本（editable 重定向或真 wheel），本地与 CI 的 import 来源一致；扁平布局会让 pytest 把就地目录插进 sys.path 造成两份包。

**追问 2**：`__editable__` finder 为什么会让 IDE 跳转失灵？
→ 一句话提示：strict 模式的 finder 是运行时 hook，IDE 静态分析不走 Python 解释器，看不到映射关系；解法是 IDE 版本支持 .pth/finder 解析，或项目配置里把 src 目录显式加为 source root。

## 背诵要点
- 旧 editable = egg-link 把源码目录塞 sys.path；PEP 660 = 构建后端产出 editable wheel（重定向层），与正式安装同构、卸载干净、后端中立（setuptools>=64 起）。
- 两种重定向模式：strict 精确映射（漏运行期生成文件，需登记构建清单）、lenient 目录 pth（行为等价 legacy）；迁移审点：data files/入口点、双模式 CI、IDE 跳转。
- 最佳组合：src 布局 + strict editable + pytest importmode=importlib，从机制上消灭本地/CI 的 import 分叉。

## 复盘追问
- "只在 editable 下能过的测试"暴露什么问题？提示：测试 import 到了就地源码而非安装包——测试断言的可能是未构建的资源/相对路径行为；双模式 CI 矩阵是检出手段，根治靠 src 布局。
- 迁到 PEP 660 后 data files 失效怎么排查？提示：strict/lenient 对非 Python 文件的映射策略不同，检查构建清单（package-data/MANIFEST）与重定向层实际内容（解包 editable wheel 看 .pth/finder 源）。
