### Q7108 · 本机开发与云开发环境的成本账

难度：P5 ｜ 标签：成本工程 / 开发环境 / 云计算

**问**：数据团队 15 人抱怨本地跑批太慢，申请给每人配一台 16 核 64GB 云开发机（按需约 ¥1200/月/人）。这笔钱该不该批？云开发环境和本机+远端计算的成本分界怎么算？

**答**：
- **结论**：先算三个账再回答批不批：① **利用率账**——开发机真实利用率通常 20-40%（下班、开会、写代码时闲置），按需计费下 ¥1200 买的是"24 小时 × 30 天"里的 8 小时有效使用，单位有效算力成本是共享集群的 3-5 倍；② **替代账**——本机跑不动的那部分负载（重跑批、大数据 join）应该走远端**计算集群**（按作业计费）而不是常驻开发机；常驻机器解决的是"环境一致性 + 交互式探索"，计算密集需求两者要分开；③ **折损账**——云开发机省下的等待时间 × 人均时薪也要入账，但只有当"等待"真实发生在开发主路径上才成立，跑批等 20 分钟往往可以去喝咖啡，不是有效损失。结论倾向：配 **共享的按需云开发平台**（K8s 上按 workspace 拉起、闲置自动回收、GPU 按需），而不是 15 台常驻 VM。
- **取舍**：方案对比：① 15 台常驻云 VM：体验最好、账单最差，利用率是死穴；② 本机 + 远端作业集群：账单最优，但环境漂移（本机可复现性差）要靠容器/uv 锁链兜底（见 Q7014）；③ 共享云 workspace（按需拉起 + 自动休眠）：折中——利用率由调度器保证，闲置 30 分钟回收，冷启动用快照预热；④ 自建小集群（跑批转内部 Airflow/Dask）：数据量大且稳定时长期最省，但运维成本入账。分界线公式：`月成本(常驻) = 人数 × 单价 × 30 天` vs `月成本(按需) = 人均有效时长 × 单价 + 平台固定成本`，有效时长 < 100 小时/月/人时按需必赢。
- **实战**：落地动作：① 先统计现状：本机跑批耗时分布、有多少是"等待阻塞开发主路径"；② 试点 3 人用按需 workspace，记录拉起频次/单次时长/利用率；③ 三个月对比账单与开发吞吐（不是感觉），再定推广范围；④ 规则化：交互探索用按需 workspace，重跑批一律提交队列，本机只保留 IDE 与轻量测试；⑤ 把"环境镜像"做成统一资产，三条路线共享，避免各自漂移。

```python
# 开发环境成本账：常驻 vs 按需 vs 本机+远端作业（标准库模拟）
# 基线：Python 3.9+

from dataclasses import dataclass


@dataclass
class DevEnvPlan:
    name: str
    headcount: int
    unit_cost_per_hour: float        # 单人每小时算力单价
    monthly_effective_hours: float   # 人均月有效使用小时
    fixed_cost_month: float = 0.0    # 平台固定成本

    def monthly(self) -> float:
        return self.headcount * self.monthly_effective_hours * self.unit_cost_per_hour + self.fixed_cost_month


def main() -> None:
    n = 15
    always_on = DevEnvPlan("15台常驻VM", n, unit_cost_per_hour=1200 / (24 * 30),
                           monthly_effective_hours=24 * 30)     # 全时段计费
    on_demand = DevEnvPlan("按需workspace", n, unit_cost_per_hour=2.0,
                           monthly_effective_hours=80, fixed_cost_month=1500)
    local_plus_remote = DevEnvPlan("本机+远端作业", n, unit_cost_per_hour=1.2,
                                   monthly_effective_hours=25, fixed_cost_month=800)

    for p in (always_on, on_demand, local_plus_remote):
        print(f"{p.name}: ¥{p.monthly():,.0f}/月")

    assert always_on.monthly() > on_demand.monthly() > local_plus_remote.monthly()
    # 折算有效算力单价：常驻被闲置成本吞噬
    eff_cost = always_on.unit_cost_per_hour * (24 * 30) / 80
    assert eff_cost > on_demand.unit_cost_per_hour * 3, "常驻折算后单价应为按需的 3 倍以上"
    print(f"OK: 常驻折算有效单价 ¥{eff_cost:.1f}/h ≈ 按需的 {eff_cost / on_demand.unit_cost_per_hour:.0f} 倍")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"跑批等待 20 分钟"不应全额折算成人力成本？
→ 一句话提示：只有阻塞开发主路径（改代码→验证闭环）的等待才计入折损，提交队列后并行做其他事的等待是零成本；折损账要用"被打断次数 × 重新进入心流的成本"更诚实。

**追问 2**：共享 workspace 怎么保证"闲置回收"不误伤长任务？
→ 一句话提示：回收判据用"无活跃会话 + 无运行中进程"双条件，长任务先转后台队列；快照预热把冷启动压到分钟级，回收才有底气激进。

## 背诵要点
- 成本分界公式：常驻月成本 = 人数×单价×720h vs 按需 = 人均有效时长×单价+平台固定；人均有效 <100h/月时按需必赢。
- 计算需求与环境需求分开：交互探索用按需 workspace，重跑批提交队列，本机只留 IDE/轻测试。
- 决策先看利用率账：开发机利用率 20-40% 是常态，常驻方案的有效算力单价是按需的 3-5 倍。

## 复盘追问
- 怎么量化"环境不一致"的成本来支撑共享平台投入？提示：统计因环境差异返工的 bug/事故次数（如本地可复现、CI 复现不了），折成修复工时；统一镜像的固定投入要在三个月内由返工节省覆盖。
- GPU 需求出现在团队里时账怎么变？提示：GPU 常驻更不可行（单价高一个量级），按需 GPU workspace + 队列排队是唯一 sane 方案，并用"GPU 有效时长占比"做月度复盘。
