### Q7032 · "任务跑完了"不等于"数据可用了"：SLA 与就绪探测怎么设计？

> 难度:★★★ | 标签:SLA, sensor, 数据编排

**问**：日报 8 点必须出，上游任务 7:50 显示"成功"但下游拿到的还是空数据。数据任务的 SLA 怎么定义？下游启动前的"就绪探测"（sensor）怎么实现？为什么"文件存在"不算就绪？SLA miss 的告警与升级怎么设计才不变成狼来了？

**答**：结论：SLA 要分两层——**时间 SLA**（任务在 HH:MM 前完成）与**数据就绪 SLA**（分区不仅存在、还通过质量校验：行数/水位/关键指标）。就绪探测的核心是 **done-flag 模式**：上游任务末尾且仅当质量校验通过时落标记（标记带校验结果），下游 sensor 只认标记；sensor 必须带 poke 间隔与 timeout，超时转 SLA miss 流程而不是无限等待。

机理与实战：
- **为什么"文件存在"不算就绪**：写半截、重命名竞态、空文件、旧分区残留都会假阳性；就绪信号必须是业务级（标记带 rows/校验结果/版本），文件只是载体。上游"成功"指进程退出码，质量校验是另一道闸。
- **sensor 参数纪律**：`poke_interval` 退避轮询防止打爆元数据；`timeout` 到点显式失败——**隐式 skip 是事故源**（下游拿昨天的分区静默跑完，报表发出旧数据没人知道）。
- **SLA miss 处理链**：临近 miss 预警 → miss 自动处置（重跑失败分区 1 次）→ 升级值班（P1/P3 分级）→ **影响面通告**（列出会延迟的下游与降级方案）。SLA 时间要按下游真实依赖时刻反推，不是拍脑袋统一 8:00。
- **告警防狼来了**：每条 SLA 带业务优先级（核心报表 vs 内部探查）、miss 后必须带影响面说明与建议动作；连续 miss 的任务要触发"治理"而不是重复告警（要么修要么降 SLA）。

```python
# 基线:Python 3.10+;纯标准库模拟数据任务的 SLA 监控与就绪探测(done-flag + sensor)
# 真实场景:Airflow sensors(poke/timeout) + SLA miss 告警分级 + 影响面通告
from __future__ import annotations
from dataclasses import dataclass


@dataclass
class Partition:
    day: str
    rows: int = 0
    quality_ok: bool = False


class UpstreamJob:
    """上游任务:只有通过质量校验才落 done 标记(标记带校验结果)。"""

    def __init__(self) -> None:
        self.flags: dict[str, dict] = {}                 # day -> {"ok": bool, "rows": int}

    def run(self, p: Partition, sla_at: str = "08:00") -> None:
        if p.quality_ok:
            self.flags[p.day] = {"ok": True, "rows": p.rows}
        else:
            print(f"质量校验失败({p.day} rows={p.rows}):不落 done 标记"
                  f" -> 下游 sensor 不放行,SLA({sla_at})风险升级")


class Sensor:
    """就绪探测:轮询标记,poke 间隔退避,超时转 SLA miss。"""

    def __init__(self, job: UpstreamJob, poke_interval: float = 5.0,
                 timeout: float = 30.0) -> None:
        self.job, self.interval, self.timeout = job, poke_interval, timeout
        self.clock = 0.0

    def wait_ready(self, day: str) -> bool:
        while self.clock < self.timeout:
            flag = self.job.flags.get(day)
            if flag and flag["ok"]:                      # 只认标记,不认"分区存在"
                print(f"t={self.clock:.0f}s 就绪:{day} rows={flag['rows']} ✅")
                return True
            self.clock += self.interval                  # 退避轮询
        return False                                     # 超时 -> SLA miss 处理流程


def demo() -> None:
    job = UpstreamJob()

    # 场景一:上游写了一半(quality 未过) -> 无标记,sensor 拦住下游
    sensor = Sensor(job, poke_interval=5.0, timeout=20.0)
    ready = sensor.wait_ready("2026-11-20")
    assert not ready
    print("空跑分区无 done 标记,sensor 超时拦截 ✅ -> 下游不会消费半成品")

    # 场景二:SLA miss 处理链:重跑 -> 通过 -> 下游放行
    job.run(Partition("2026-11-20", rows=0, quality_ok=False))
    job.run(Partition("2026-11-20", rows=1_240_000, quality_ok=True))
    ready = Sensor(job, poke_interval=5.0, timeout=30.0).wait_ready("2026-11-20")
    assert ready
    print("重跑通过校验落标记,sensor 放行下游 ✅")

    # 场景三:miss 分级:临近 miss 预警,超时升级,带影响面
    impact = {"日报:8:10 发布延迟", "增长看板:8:30 依赖", "推荐特征:实时回退旧版"}
    level = "P1-升级值班"
    print(f"SLA miss 处理链 [{level}]:自动重跑(1 次)失败 -> 人工介入;"
          f"影响面通告:{sorted(impact)} ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：sensor 轮询和事件驱动（消息/回调）怎么选？
答：轮询简单、可观测（每跳都有日志），但延迟粒度=poke 间隔、且对元数据有压力；事件驱动延迟低，但要处理"消息丢失/乱序/重复"，最终还是要落回标记表对账。工程上常用折中：事件触发立即 poke（推拉结合），标记表仍是唯一事实源。

**追问二**：上游 SLA 快 miss 了，下游任务"先跑能跑的部分"可行吗？
答：可行且常用——把下游 DAG 拆成"不依赖上游延迟分区的分支"先行执行，依赖延迟分区的分支由 sensor 卡住；但要防止"部分跑完"被当成"全部完成"发布：发布动作本身必须挂在整条链的聚合标记之后，而不是任何单分支的完成。

## 背诵要点
- SLA 两层：时间 SLA（HH:MM 前完成）+ 就绪 SLA（分区过质量校验）；done-flag 是唯一就绪事实源，文件存在不算。
- sensor 必须 poke_interval 退避 + timeout 显式失败；隐式 skip 会静默发旧数据，是典型事故源。
- SLA miss 链：预警 → 自动重跑 → 分级升级 → 影响面通告；SLA 时刻按下游真实依赖反推，告警带影响面才不是狼来了。

## 复盘追问
- 一次"报表发了昨天的数据"事故，sensor 该怎么改？（提示：检查 timeout 后是 skip 还是 fail、发布是否挂在整链聚合标记后、标记是否带了分区校验结果而非仅存在性）
- 如何评估一条 SLA 定得合不合理？（提示：统计该任务 P50/P95 完成时刻分布与 miss 率，SLA 应设在 P95+缓冲；长期 miss 的 SLA 要么优化任务要么重定时刻，不能靠告警沉默）
