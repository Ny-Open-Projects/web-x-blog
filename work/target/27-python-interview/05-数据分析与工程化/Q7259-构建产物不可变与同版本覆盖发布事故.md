### Q7259 · 同版本号覆盖发布后的幽灵 bug：构建产物不可变与发布台账

难度：P6 ｜ 标签：发布工程、不可变产物、语义化版本、发布台账、构建指纹

基线：Python 3.12；模拟版本登记台账与重复发布拒绝，演示"同版本覆盖"导致的运行内容与仓库不一致，全标准库实跑。

**问**：1.2.3 版本发出去发现有小 bug，同事直接在同一个 tag 上改了代码重新构建，把制品仓库里的 1.2.3 **覆盖**了。结果：A 机器上跑的 1.2.3 是旧的，B 机器重新部署拉到的是新的——同一个版本号两种行为，线上"幽灵 bug"（有人复现不了有人天天见）。为什么"重新打 tag 覆盖"在 git 里没事、在制品上就是事故？发布侧应该立什么规矩？

**答**：
- **结论**：版本号是**内容的承诺**：消费方（部署系统、下游依赖、pip 缓存）把"1.2.3"当作不变的引用，各自缓存了不同时间取到的产物——覆盖发布后，同一版本号在不同机器/缓存里对应不同内容，行为不一致且不可归因。git 里 force tag 覆盖之所以"看起来没事"，是因为源码仓库通常只有一个、大家都看同一份；而制品被**多副本分发**（镜像仓库、CDN、本机 pip 缓存），覆盖只更新一个源头，副本世界分裂。规矩三条：① **产物不可变**：同版本号禁止重新构建上传（registry 开 immutable tag / 制品库只增不改）；② 发布台账记录"版本 → 构建指纹（digest/哈希）"，部署前校验实际产物的 digest 与台账一致（Q2550 校验和清单的发布侧延伸）；③ 修 bug 走 1.2.4 递增，哪怕只改一行——版本号的"廉价"正是它可信的前提。
- **取舍**：① 不可变的代价是"永远发新版本"，版本号膨胀（1.2.3 到 1.2.40）——但这正是版本系统的用途，比排查幽灵 bug 便宜几个量级；② digest 校验的接入成本：每个部署环节加一步校验，自动化的 CI 里几乎为零，手工部署是最薄弱环节；③ 台账与制品库的注册表职责重叠：制品库本身就是事实源，台账的价值是**流程层记录**（谁、什么时候、为什么发布），二者都指向同一 digest；④ 缓存清理（pip/镜像层）在覆盖发布后是补救手段——但依赖人工且不彻底，不可变才是根治。
- **实战**：① 制品仓库开启不可变 tag（Nexus/Harbor/PyPI 都支持）；② CI 发布步骤产出 digest 写入台账，部署脚本第一步校验 digest，不一致直接失败；③ "hotfix 覆盖发布"这个操作从 SOP 里删除，替换为"hotfix = patch 版本 + 快速通道评审"；④ 存量检查脚本：定期对账线上运行版本指纹与制品库当前 digest（与 Q7261 构建指纹注入配合）。

```python
"""发布台账与不可变产物：覆盖发布事故的机理与校验。"""
import hashlib
import json


def digest(content: str) -> str:
    return hashlib.sha256(content.encode()).hexdigest()[:16]


class ReleaseLedger:
    """发布台账: 版本 -> 内容指纹, 只增不改。"""

    def __init__(self):
        self.ledger: dict[str, str] = {}

    def publish(self, version: str, content: str) -> tuple[bool, str]:
        d = digest(content)
        if version in self.ledger:
            if self.ledger[version] == d:
                return False, f"{version} 相同内容重复发布 (幂等, 跳过)"
            return False, (f"拒绝: {version} 已发布且内容不同\n"
                           f"    台账指纹 {self.ledger[version]} != 本次 {d}\n"
                           f"    正确动作: 递增 patch 版本发布")
        self.ledger[version] = d
        return True, f"发布成功: {version} @ {d}"

    def verify_deploy(self, version: str, local_content: str) -> tuple[bool, str]:
        """部署侧: 运行内容指纹必须与台账一致。"""
        d = digest(local_content)
        expected = self.ledger.get(version)
        if expected is None:
            return False, f"{version} 不在台账中 (来源不明的产物, 禁止部署)"
        if expected != d:
            return False, (f"幽灵 bug 检出: {version} 本地指纹 {d} "
                           f"!= 台账 {expected} -> 本地是旧副本, 拒绝部署")
        return True, f"{version} 指纹一致, 允许部署"


if __name__ == "__main__":
    ledger = ReleaseLedger()
    v123_v1 = "app code 1.2.3 (bug: off-by-one)"
    print("第一次发布:", ledger.publish("1.2.3", v123_v1)[1])

    print("\n事故尝试: 在同 tag 上改代码后覆盖发布")
    v123_v2 = "app code 1.2.3 (bug fixed)"
    ok, msg = ledger.publish("1.2.3", v123_v2)
    print("  ", msg)

    print("\n幽灵 bug 现场: 机器 A 部署于覆盖前, 机器 B 部署于覆盖后")
    print("  机器A 校验:", ledger.verify_deploy("1.2.3", v123_v1)[1])
    print("  机器B 校验:", ledger.verify_deploy("1.2.3", v123_v2)[1])

    print("\n正确路径: hotfix 递增 patch")
    print("  ", ledger.publish("1.2.4", v123_v2)[1])

    # 负例: 未登记版本
    print("\n来源不明产物:", ledger.verify_deploy("9.9.9", "whatever")[1])
    ok = not ledger.ledger.get("1.2.3") == digest(v123_v2)
    print(f"\n校验: 台账保证 1.2.3 指向首次内容 -> {'通过' if ok else '异常'}")
    print("\n结论：版本号是内容承诺; 覆盖发布让多副本世界分裂;")
    print("      不可变 tag + 发布台账 + 部署前指纹校验三件套根治")
```

**追问一**：制品库已经有 hash，为什么还需要发布台账？

→ 解析：制品库的 hash 回答"这个文件是什么"，台账回答"我们发布过什么、为什么"。事故排查时需要的是后者：1.2.3 被谁、何时、基于哪个 commit 发布——制品库只保留最终状态（覆盖后只剩新内容），**发布过程的历史需要独立记录**（审计与回溯）。台账的第二个价值是流程闸门：重复版本校验、发布审批状态、灰度进度都挂在台账上，制品库只管存储与分发。两者通过 digest 关联：台账里的每次发布记录指向制品库中的唯一 blob，制品库的不可变策略保证指向永不失效。分工一句话：**制品库管内容的真，台账管流程的账**。

**追问二**：已经发生了覆盖发布，存量机器怎么收敛？

→ 解析：三步收敛：① **盘点**：对全部存量机器采集运行版本指纹（Q7261 的构建指纹注入在这里生效——没注入过指纹的版本连盘点都做不了，只能按部署时间推断），区分"覆盖前内容"与"覆盖后内容"两批；② **统一**：以最新合法版本（1.2.4）为目标，分批重发覆盖全部旧副本——分批限速走发布窗口（Q6113），避免一次性全量重启；③ **补漏**：清理各层缓存（镜像层、pip cache、CDN）里的旧 1.2.3 副本，防止新部署又拉到旧的。事后把"运行指纹 vs 台账 digest"的对账巡检常态化（Q2779 巡检清单），任何漂移当天发现。这次事故的成本要记入复盘：覆盖发布省下的一次版本号，换来的是全集群重发与三天排查。
