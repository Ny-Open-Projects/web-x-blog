### Q7102 · 锁文件缺失导致版本漂移事故复盘

难度：P6 ｜ 标签：依赖管理 / 事故复盘 / 可复现构建

**问**：某个周一早上发布，服务在 CI 全绿、预发正常，生产一启动就报 `TypeError: Message.__init__() got an unexpected keyword argument`——一个间接依赖（protobuf）在周五被上游发了新版本，requirements.txt 里写的是 `protobuf>=3.19`，生产构建时拉到了 4.x。这类"版本漂移"事故的机理与根治手段是什么？

**答**：
- **结论**：`>=` 风格的 requirements 是"约束"不是"快照"：每次构建重新解析依赖树，间接依赖（传递依赖）的版本随上游发布漂移。CI 与生产构建时间不同、缓存状态不同，就会"CI 测的版本 ≠ 生产跑的版本"。根治：锁文件（pip-tools 的 requirements.lock / uv.lock / poetry.lock / PDM lock）把完整闭包（含间接依赖与哈希）固化，构建只消费快照不重新解析。第二层防护：范围上限（`protobuf>=3.19,<4`）是对抗解析器失控的护栏，但它是手工维护的——漏写上限的间接依赖照漂不误；第三层是哈希校验（`--require-hashes`），防止上游包被投毒或缓存损坏时静默装入异常版本。
- **取舍**：锁文件的代价：升级依赖从"改一行"变成"跑 lock 更新 + 全量回归"，惯性上让团队回避升级、依赖越锁越旧。平衡：锁文件 + 定期（每月）自动升级 PR（bot 更新 lock + CI 回归），把"漂移事故"转换成"受控升级"。monorepo 多项目共享锁文件 vs 各自独立：共享锁减少解析冲突但放大升级爆炸半径，一般按部署单元各自锁。
- **实战**：事故剧本：① 生产镜像固化 last good lock 文件，先回滚恢复；② `pip download` 复现解析结果 diff 出漂移的间接依赖；③ 建 lock 文件 + `--require-hashes`，CI 校验 lock 与 requirements.in 一致性；④ 复盘项：把"requirements.in（意图约束）→ lock（快照）"的双文件模式定为团队标准，禁止生产构建直接消费 in 文件。

```python
# 依赖解析漂移检测器（纯标准库模拟）
# 基线：Python 3.9+


def parse_lock(text: str) -> dict[str, str]:
    """lock 文件: 'name==version' 行"""
    out = {}
    for line in text.splitlines():
        line = line.strip()
        if line and not line.startswith("#") and "==" in line:
            name, ver = line.split("==")
            out[name.lower()] = ver
    return out


def drift_report(lock_a: str, lock_b: str) -> list[str]:
    """两个环境构建产物之间的版本 diff"""
    a, b = parse_lock(lock_a), parse_lock(lock_b)
    report = []
    for pkg in sorted(set(a) | set(b)):
        va, vb = a.get(pkg), b.get(pkg)
        if va != vb:
            report.append(f"{pkg}: {va} -> {vb}"
                          + ("  [新引入]" if va is None else "")
                          + ("  [移除]" if vb is None else ""))
    return report


def main() -> None:
    ci_env = """protobuf==3.20.3
requests==2.31.0
"""
    prod_env = """protobuf==4.25.0
requests==2.31.0
"""
    rep = drift_report(ci_env, prod_env)
    print(rep)
    assert rep == ["protobuf: 3.20.3 -> 4.25.0"]
    # lock 快照比对：重建漂移检测是可自动化的
    lock = parse_lock(ci_env)
    assert lock["protobuf"] == "3.20.3"
    print("OK: CI 与生产构建 lock diff 可定位漂移依赖")


if __name__ == "__main__":
    main()
```

**追问 1**：`--require-hashes` 为什么必须配合 lock 文件才能用？
→ 一句话提示：哈希模式要求每个被安装的包都有明确哈希来源，间接依赖不进 lock 就没有哈希记录，安装直接失败——它强迫你把闭包完整固化，顺带防供应链投毒。

**追问 2**：间接依赖漂移与"语义化版本不靠谱"什么关系？
→ 一句话提示：protobuf 3→4 这类破坏发生在 major 边界，但很多包 minor 也夹带破坏（semver 执行不严）；lock 让你信任的是"上次验证过的精确版本"而不是上游的版本承诺，这是唯一可验证的信任锚。

## 背诵要点
- `>=` 约束不是快照：构建时重新解析传递依赖，CI 与生产解析结果可不同 → "CI 绿生产崩"。
- 三层防护：lock 文件（闭包快照）+ 范围上限（手工护栏）+ `--require-hashes`（防投毒/坏缓存）。
- 平衡锁死与升级：bot 每月自动升级 PR + CI 回归，把漂移事故转换为受控升级。

## 复盘追问
- 为什么"pin 全部直接依赖"仍然不够？提示：漂移常发生在传递依赖——只 pin 直接依赖等于只锁树的第一层；lock 的价值是把整棵闭包树哈希固化。
- 锁文件冲突（多项目 monorepo）怎么治理？提示：按部署单元分锁 + 共享约束文件（约束 pip 的 constraints.txt 统一公共版本），既保独立升级又防公共组件版本分裂。
