### Q7279 · 生产镜像里装着测试全家桶：dev 依赖泄漏与分层锁定

难度：P6 ｜ 标签：依赖分层、requirements 分组、镜像瘦身、供应链攻击面、pyproject

基线：Python 3.12；模拟分层依赖解析（runtime/dev 分组）与"单文件全量安装"的攻击面/体积账，实现分层锁定的校验器与泄漏检测，全标准库实跑。

**问**：生产镜像里发现 pytest、ipython、faker 全在里面——requirements.txt 一把梭装的。dev 依赖进生产除了镜像变大还有什么真实风险？requirements 怎么分层、锁定在哪一层？多阶段构建之外，怎么在 CI 里把"dev 依赖泄漏"做成门禁？

**答**：
- **结论**：dev 依赖进生产的三重账：① **攻击面扩大**：pytest 的插件加载、ipython 的代码执行入口、faker 的模板引擎——生产进程里任何一个代码执行漏洞都可能借道这些"开发工具自带的危险面"升级（Q7088 pickle 事故、Q1126 供应链审计的同族视角），依赖越多审计越难穷尽；② **体积与启动**：镜像每 100MB 都在拉取/部署/冷启动里计价（Q7182 镜像体积账），数据科学全家桶（pandas/numpy/scipy 的 dev 副本、jupyter 栈）轻松让镜像翻倍；③ **行为漂移**：dev 依赖与 runtime 依赖争抢解析——requirements 一把梭时，测试新加的库可能把生产库降级/升级（依赖解析漂移 Q7043 的专门形态），生产行为被测试需求牵着走。分层方案：`pyproject.toml` 的 dependency-groups（PEP 735）或 extras 分组——`[project.dependencies]` 是 runtime 唯一事实源，`[dependency-groups] dev/test/lint` 各自独立；锁定分层：runtime 锁文件（uv lock/pip-tools compile 的 prod 约束）进生产构建，dev 锁文件只进 CI/本地；**生产构建命令只装 runtime 组**，从构建命令层面消灭"顺手全装"。CI 门禁：构建产物里跑"导入审计"——扫描 site-packages 对照 dev 分组清单，泄漏即红；比人工看 Dockerfile 靠谱得多。
- **取舍**：① 分层的粒度：runtime/test/lint 三层是甜点，过细（每类工具一组）维护成本超过收益；② 多阶段构建是手段不是保证——builder 阶段装 dev 依赖、runtime 阶段只 COPY site-packages 里的 runtime 子集，漏 COPY 一个就带进生产；阶段隔离 + 导入审计双保险；③ 锁定层级：只在顶层锁（uv lock 全链）vs 分层锁（prod/dev 各自约束文件）——uv/pip-tools 的全链锁 + 构建时分组安装（`--group prod`/`-r requirements-prod.txt`）是当前主流，"一个锁文件、两个安装面"；④ 意外收益：dev 依赖剥离后，生产依赖解析更快、升级评审面缩小，供应链审计（SBOM Q7020）的清单也干净了。
- **实战**：① 迁移路径：先把现有 requirements.txt 拆成两文件（prod/dev），CI 里生产构建切到 prod 文件，观察一周再上 pyproject 分组——小步迁移不破 CI；② 门禁三件套：构建后镜像的 `pip list` 快照与 prod 锁文件比对（多余包即红）+ site-packages 目录扫描 + 镜像体积预算告警（Q1127 性能预算同族思路）；③ 本地开发与生产的依赖差异要"显式声明"：文档里写清 dev 组的职责，别让人为了"图省事"把调试工具加进 runtime；④ 审计联动：SBOM 生成从 prod 锁文件出，dev 工具的 CVE 噪音从生产审计里消失。

```python
"""Q7279 依赖分层: runtime/dev 分组解析 + 泄漏检测门禁。"""
from dataclasses import dataclass, field

# 声明式分组(pyproject dependency-groups 的模拟)
GROUPS = {
    "runtime": {"fastapi": "0.115", "pydantic": "2.9", "redis": "5.0"},
    "dev": {"pytest": "8.3", "faker": "30.0", "ipython": "8.27"},
}
DANGEROUS_DEV = {"ipython", "faker"}          # dev 工具自带的执行面


@dataclass
class Image:
    tag: str
    installed: dict[str, str] = field(default_factory=dict)

    def install_group(self, name: str):
        self.installed.update(GROUPS[name])


def build_image(tag: str, groups: list[str]) -> Image:
    img = Image(tag)
    for g in groups:
        img.install_group(g)
    return img


def leak_audit(img: Image) -> list[str]:
    """门禁: 生产镜像只许装 runtime 分组; dev 包出现即泄漏."""
    leaks = []
    for pkg, ver in img.installed.items():
        if pkg in GROUPS["dev"]:
            marks = " (+执行面)" if pkg in DANGEROUS_DEV else ""
            leaks.append(f"dev 泄漏: {pkg}=={ver}{marks}")
    return leaks


def size_mb(img: Image) -> int:
    """演示: dev 全家桶比 runtime 贵 3 倍."""
    return len(img.installed) * (120 if img.installed.keys() & set(GROUPS["dev"])
                                 else 40)


if __name__ == "__main__":
    bad = build_image("svc:bad", ["runtime", "dev"])     # 一把梭
    good = build_image("svc:good", ["runtime"])          # 分层锁定
    leaks = leak_audit(bad)
    print(f"镜像 {bad.tag}: 装了 {len(bad.installed)} 包, 体积~{size_mb(bad)}MB")
    print(f"泄漏审计: {leaks or '无'}")
    print(f"镜像 {good.tag}: 装了 {len(good.installed)} 包, 体积~{size_mb(good)}MB, "
          f"审计={leak_audit(good) or '通过'}")
    ok = (leaks and len(leaks) == 3 and not leak_audit(good)
          and size_mb(bad) > size_mb(good))
    print(f"校验: 泄漏检测 + 体积差 + 分层构建通过 -> {'通过' if ok else '异常'}")
    print("结论：dev 依赖进生产=攻击面/体积/解析漂移三重账;")
    print("      分组声明+分层锁定+导入审计门禁, 生产构建只认 runtime 组")
```

**追问一**：为什么"多阶段构建"不能单独解决问题？COPY 到 runtime 阶段的粒度该怎么定？

→ 解析：多阶段构建把"安装"与"运行"分开，但它的隔离强度完全取决于 COPY 的粒度：① **粗粒度 COPY**（整个 venv/site-packages 目录）：builder 阶段装的 dev 依赖原样带进 runtime 阶段——隔离只在"编译工具链"层面生效（gcc 不在了），Python 层的 pytest/faker 全在；② **细粒度 COPY**（按包名逐个 COPY 或构建后重新 pip install --no-deps -r prod 锁）：真正隔离，但维护重，漏一个包就破防；③ **runtime 阶段重装派**（builder 只产出 wheel，runtime 阶段用 `pip install` 从 wheelhouse 装 prod 锁）：安装行为本身就是"分组感知"的，隔离最彻底，代价是 runtime 阶段还要有 pip（或用离线 wheelhouse + uv）。所以多阶段构建的正确定位：**它是分层锁定的执行机制之一，而不是分组语义本身**——分组语义必须先在依赖声明里成立（pyproject groups / 分离的锁文件），构建阶段才有的放矢。判别方法很朴素：构建完进容器 `pip list` 或扫 site-packages，与 prod 锁文件 diff——镜像说话，Dockerfile 不说话。

**追问二**：分层锁定之后，dev 依赖自身的版本漂移要不要管？测试环境和生产环境"版本不同"会不会造成"测的不是跑的"？

→ 解析：两个问题分开看。① **dev 依赖漂移**：测试工具链的版本漂移影响的是"测试行为的可复现性"（pytest 8 的告警语义变了、faker 生成的数据模式变了会让金样测试飘红 Q7277），所以 dev 组也要锁（uv lock 全链覆盖 dev 组），只是锁的更新频率可以更松——"全链锁 + 分组安装"既管生产也管测试的可复现性。② **"测的不是跑的"风险真实存在**，它的三种形态与对策：解析结果不同（dev 环境的依赖解析把生产库装出了不同版本——生产锁文件在本地 dev 安装时也要生效，`uv sync --group dev` 保证 runtime 组按 prod 锁精确装）；行为差异（测试代码用到了 dev 环境才有的库——lint 规则禁止测试代码 import dev 专有库，或用 CI 的"prod-only 安装跑冒烟测试"验证）；环境差异（本地 macOS / 生产 linux 容器——镜像即环境的纪律，Q7124 跨平台差异的同族）。终极解法是**生产镜像进测试**：集成测试直接跑在待发布的生产镜像里（镜像构建→镜像测试→镜像发布一条线），环境差异从根上消失。原则：**分层分的是"安装面"，不是"事实源"——一个锁文件是唯一版本事实，分组只是决定谁被装到哪里。**
