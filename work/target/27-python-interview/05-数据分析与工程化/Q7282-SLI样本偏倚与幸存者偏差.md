### Q7282 · 成功率 99.9% 的假象：SLI 的样本偏倚与幸存者偏差

难度：P6 ｜ 标签：SLI口径、样本偏倚、幸存者偏差、超时剔除、错误预算

基线：Python 3.12；构造"超时/熔断请求不进成功率分母"的偏倚模型，复现偏倚导致的错误率低估与错误预算虚高，实现带缺失样本惩罚的修正口径，全标准库实跑。

**问**：监控大盘成功率 99.95%，用户投诉不断，事后复盘发现故障高峰期大量请求**超时未计**——网关超时直接断开，没有响应就没有状态码，自然不进"成功率"的分子分母。SLI 的样本偏倚有哪几类？"没有记录 = 没发生"的陷阱怎么堵？错误预算被偏倚虚高后怎么修正？

**答**：
- **结论**：SLI 最危险的不是算错，是**样本在源头就缺了**——幸存者偏差的反面：只有"走完全程"的请求才有状态码，而**超时、断连、熔断拒绝、限流拦截、客户端放弃**这些最坏体验恰恰最容易被排除在口径外。本卡实验：1000 请求中 60 个超时被剔除，"已记录成功率" 98.9% 达标，"真实成功率"（超时全算失败）93.4% 严重不达标——**偏倚幅度 5.5 个百分点，正好是故障最严重的时段**。堵法三招：① **完整性对账**：入口请求计数（网关/CDN 层）与出口响应计数（应用层）做差，差值 = 缺失样本，缺失率超阈值即 SLI 降级为"数据不完整"而不是照常报绿（Q2020 元监控的思想用在 SLI 上）；② **缺失惩罚口径**：`成功率 = 成功数 / 入口总数`（入口计数是更靠近用户的分母事实源），或显式给出双口径——"已响应成功率"与"含缺失的保守成功率"，对外承诺用保守值；③ **事件化补充**：超时/熔断/限流这些"无响应事件"单独打点（超时计数器、熔断拒绝计数器 Q2551），与响应成功率合并成完整体验口径——网关层打点比应用层更全，SLI 的采集点要选在"请求寿命的最早点"。错误预算（Q7520 错误预算思想）用被虚高的成功率算，会多花掉一倍预算还不自知——预算的分母口径必须与 SLI 同源同审。
- **取舍**：① 采集点的位置账：网关/负载均衡层计数全（含 502/504/超时）但缺业务语义；应用层有语义但漏"没到达的"；两层都要有且对账——单层 SLI 必偏；② 客户端视角缺失：用户侧的失败（弱网、DNS 失败、连接被 RST）服务端永远看不到，SLI 的天花板是"服务端可见的体验"，对外承诺要写清口径边界（Q144 SLA 条款的同族严谨性）；③ 修正口径的博弈：保守口径（缺失算失败）会引发"要不要把限流拒绝算失败"的争议——限流是**主动降级**还是**体验失败**取决于产品语境，口径决策必须走评审留档（Q7062 口径治理流程），不能工程师拍脑袋；④ 监控先于承诺：SLI 口径没经过完整性对账验证前，错误预算不给对外承诺用。
- **实战**：① SLI 上线 checklist 三问：分母从哪层来、缺失样本去哪了、双口径差值监控有没有——三问答不上就不上线；② 故障复盘必查项：故障期间的"缺失率曲线"（入口-出口差值），偏倚在故障时最大，正是最需要真实数字的时候；③ 告警联动：缺失率突增本身是独立告警（网关挂了/采集断了），别让它悄悄污染成功率；④ 修正后的预算重算：口径修正当天重算历史错误预算，向消费方（业务/承诺方）通报口径变更与重算结果（口径变更的历史标注纪律）。

```python
"""Q7282 SLI 样本偏倚: 超时剔除造成的幸存者偏差与修正口径。"""
from dataclasses import dataclass


@dataclass
class Outcome:
    ok: int = 0            # 成功
    err: int = 0           # 失败(有响应)
    timeout: int = 0       # 超时(无响应 -> 旧口径不进分母)
    rejected: int = 0      # 熔断拒绝(无响应)


def sli_naive(o: Outcome) -> float:
    """旧口径: 只看已响应的请求 -> 超时/拒绝被剔除(偏倚来源)."""
    resp = o.ok + o.err
    return o.ok / resp if resp else 1.0


def sli_conservative(o: Outcome) -> float:
    """保守口径: 入口总数做分母, 无响应全算失败."""
    total = o.ok + o.err + o.timeout + o.rejected
    return o.ok / total if total else 1.0


def completeness(o: Outcome, ingress_total: int) -> float:
    """完整性对账: 出口已响应数 / 入口总数 -> 缺失率."""
    responded = o.ok + o.err
    return responded / ingress_total if ingress_total else 0.0


def error_budget_naive(slo: float) -> float:
    return 1 - slo


def error_budget_conservative(slo: float, o: Outcome) -> float:
    """被偏倚虚高的预算: 旧口径算出的失败率远小于真实."""
    return (1 - sli_naive(o)) / (1 - slo)      # 预算消耗比例


if __name__ == "__main__":
    o = Outcome(ok=880, err=10, timeout=60, rejected=50)
    n1, n2 = sli_naive(o), sli_conservative(o)
    bias = n2 - n1
    comp = completeness(o, 1000)
    print(f"真实构成: 成功 880 / 失败 10 / 超时 60 / 拒绝 50 (共 1000)")
    print(f"旧口径(已响应): {n1:.1%}   <- 达标假象, 剔除了 110 个最差样本")
    print(f"保守口径(入口分母): {n2:.1%}  <- 偏差 {abs(bias):.1%} 个百分点")
    print(f"完整性: 出口/入口 = {comp:.1%} (缺失 {1 - comp:.1%} -> 应触发降级告警)")
    print(f"错误预算消耗: 旧口径 {error_budget_conservative(0.99, o):.2f}x "
          f"(SLO=99%) <- 虚高 {error_budget_conservative(0.99, o) / 1:.1f} 倍")
    ok = (n1 > 0.985 and n2 < 0.9 and comp < 0.9)
    print(f"校验: 偏倚复现 + 完整性对账暴露缺失 -> {'通过' if ok else '异常'}")
    print("结论：无响应=最坏体验却最易被剔除; SLI 分母取入口层, 缺失率独立告警;")
    print("      成功率/错误预算必须带完整性对账, 否则故障期数字最假")
```

**追问一**：缺失惩罚口径"缺失算失败"在限流场景有争议——主动降级的请求算不算失败？口径争议的正确决策流程是什么？

→ 解析：这是口径治理的典型裁决，流程比结论重要：① **先分层**：把"无响应"拆成语义不同的三类——超时/断连（体验失败，用户感知差，算失败无争议）；熔断拒绝（保护机制触发，用户收到快速失败或降级响应——**有响应**的降级走响应口径，**无响应**的拒绝算失败）；限流拦截（429 有响应，语义上是"保护性拒绝"——争议点在此）。② **按产品语境裁决**：核心交易链路上限流=体验失败（用户没买到东西），边缘读接口上限流=可接受的降级——同一事件在不同 SLI 里答案不同，所以口径按**业务场景分册**（Q7062 口径字典分册化），不做全局一刀切；③ **决策留档**：每次裁决写入口径字典（谁裁决、依据、生效版本、历史口径标注），下次争议先查字典再讨论——没有留档的口径决策三个月后必然重吵一遍；④ **双口径并行期**：口径切换先双轨运行一个月，差值曲线给决策者看实际影响，再正式切换并通报消费方。总原则：**口径争议的本质是"SLI 为谁服务"——对外承诺口径从严（保守），内部诊断口径从真（分细节），两个口径都保留，用场景选。**

**追问二**：客户端视角的失败（弱网、DNS 失败、RST）服务端看不到，SLI 的边界怎么向业务解释？要不要推客户端埋点？

→ 解析：先讲清边界的物理原因：服务端 SLI 的观测起点是"请求到达入口"，而用户旅程从"发起请求"开始——发起失败的请求（DNS 解析失败、TCP 连不上、TLS 握手断）从未到达服务端，服务端任何监控都看不见；到达后中途断开（客户端超时放弃、RST）服务端能看到部分痕迹（半开连接计数）但难归因到用户。向业务解释用"漏斗图"最有效：发起 1000 → 到达 950 → 响应成功 920 → 用户确认成功 905，服务端 SLI 只覆盖第二层以后，第一层的流失是"用户连不上"级别的更严重故障——这正是拨测（Q1389 主动拨测）与真实用户监控（RUM）的存在意义。要不要推客户端埋点的决策账：① 客户端埋点成本：SDK 侵入所有端（Web/App/小程序）、隐私合规（数据采集授权）、上报可靠性（弱网下埋点自己都发不出去——用批量缓存+指数退避）；② 收益：覆盖发起失败与端上渲染体验，SLI 从"服务端视角"升级为"用户旅程视角"，与拨测互补（拨测是合成流量探针、RUM 是真实流量）；③ 折中路线：先拨测后 RUM——拨测无侵入、可快速覆盖"能不能连上"的盲区，RUM 作为二期立项；④ 口径诚实性：对外 SLA 写明"以服务端可用性为准"还是"以用户可达性为准"，口径边界白纸黑字（Q144 SLA 条款的教训）。核心认知：**SLI 的完整性上限由观测点的物理位置决定，扩观测点（拨测/RUM）是架构投资，不是监控配置。**
