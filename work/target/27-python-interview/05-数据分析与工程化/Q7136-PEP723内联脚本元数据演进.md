### Q7136 · PEP 723 内联脚本元数据与 uv run 的演进

难度：P6 ｜ 标签：版本演进 / 工程化 / 依赖管理

**问**：数据团队有几百个一次性脚本（`analyze_2024.py`、`fix_orders.py`），长期靠 README 里一句"先 pip install x y z"来保证能跑。PEP 723 解决了什么问题？工具链演进到什么程度，怎么安全地迁移存量脚本？

**答**：
- **结论**：PEP 723（2023，Inline script metadata）定义了在单文件脚本顶部用 `# /// script` TOML 块声明 `dependencies` / `requires-python` 的标准格式。它解决的是"**脚本级依赖无人管理**"：一个脚本该用哪个解释器、哪些包、什么版本，以前散落在 README/口头/环境里；有了内联元数据，`uv run script.py`（1.4+ 支持）、`python-script` 类工具会自动创建隔离环境、安装依赖再执行——脚本从"在某人环境里碰巧能跑"变成**自描述可复现**。工具演进：pip 侧长期无官方执行器（PEP 723 是元数据标准不含执行器），第三方 python-launcher/脚本运行器各自实现；uv（2024）把它变成一等公民：`uv init --script` 生成、`uv run` 自动装依赖、`uv add --script` 添加依赖、`uv build` 无关。迁移存量脚本三步：① 用 `uv add --script` 或手工把 README 依赖搬进头块；② 加 `requires-python` 锁下限（结合 Q7121 的下限缺失教训）；③ CI 里对脚本目录跑 `uv run --dry-run` 或直接执行冒烟，验证元数据完整。
- **取舍**：内联元数据 vs 建正式包：脚本多而轻（几百个独立小工具）时，每脚本一个包是灾难，内联是正确粒度；但脚本一旦要被 import 复用或依赖复杂（本地包路径），就该升级成项目（pyproject）。另一个坑：内联依赖与项目依赖重复漂移——公共依赖版本应在团队层面对齐（内部约定或共享基线锁文件）。
- **实战**：① 脚本头块放在 docstring 之前且格式严格（`# /// script` 开闭标记），写错工具会静默忽略；② `requires-python` 与公司基线对齐（如 `>=3.11` 用 tomllib）；③ 一次性脚本也建议提交到固定目录 + CI 冒烟，配合"临时脚本不入共享环境"（Q7041）的纪律。

```python
# 解析 PEP 723 内联脚本元数据 (3.11+ tomllib; 3.9/3.10 降级 pip>=21.1 的 vendored 或 tomli)
# 基线: Python 3.11+ 标准库 tomllib; 3.9-3.10 需 tomli (第三方)
import re
import sys

SCRIPT = '''# /// script
# requires-python = ">=3.11"
# dependencies = [
#   "pandas>=2.2",
#   "requests<3",
# ]
# ///
"""fix_orders: 一次性订单修复脚本。"""
import requests  # noqa
'''


def parse_inline_meta(source: str) -> dict:
    """按 PEP 723 规范提取 # /// 块并解析 TOML。"""
    m = re.search(r"(?m)^# /// script\n((?:^# .*\n?)*?)^# ///$", source)
    if not m:
        raise ValueError("无内联元数据: 工具会当作普通脚本(依赖缺失风险)")
    toml_text = "\n".join(line[2:] for line in m.group(1).splitlines())
    try:
        import tomllib
    except ModuleNotFoundError:               # 3.9/3.10 降级
        import tomli as tomllib
    return tomllib.loads(toml_text)


def main() -> None:
    meta = parse_inline_meta(SCRIPT)
    assert meta["requires-python"] == ">=3.11"
    assert meta["dependencies"] == ["pandas>=2.2", "requests<3"]
    # 门禁: 脚本必须有 requires-python 下限 (Q7121 下限缺失教训)
    assert meta["requires-python"].startswith(">=")
    print(f"deps={meta['dependencies']}, py={meta['requires-python']}")
    print("OK: uv run script.py 会按元数据建隔离环境执行; 存量脚本逐步搬运")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 PEP 723 只定义元数据格式而不定义执行器？
→ 一句话提示：元数据是标准（任何工具都能读），执行器是产品竞争位（uv/pdm/hatch 各自实现），分层标准让生态不绑死某家工具——类似 pyproject 定义格式、pip/uv 实现安装。

**追问 2**：内联脚本的依赖解析每次运行都做，启动成本怎么控制？
→ 一句话提示：uv 等执行器按脚本内容哈希缓存环境（只首次创建），依赖不变则复用；对比每脚本一个 venv 的手工维护，缓存键失效才重建。

## 背诵要点
- PEP 723 = 脚本顶部 `# /// script` TOML 块声明 dependencies/requires-python；`uv run script.py` 自动建隔离环境执行（uv 1.4+ 一等支持）。
- 存量迁移三步：依赖搬进头块、锁 requires-python 下限、CI 冒烟验证元数据；头块格式错误会被静默忽略。
- 粒度选择：独立轻脚本用内联；要被 import/依赖复杂则升级为 pyproject 项目。

## 复盘追问
- 内联依赖和项目依赖版本漂移怎么办？提示：团队共享基线（内部约定版本策略）+ 对账脚本定期 diff 脚本头与主项目锁文件，公共依赖强制对齐。
- 为什么脚本也要 `requires-python`？提示：Q7121 的下限缺失事故同理——环境漂移到不兼容解释器时给出明确失败而非运行期怪异错误；执行器会直接拒绝不满足的版本。
