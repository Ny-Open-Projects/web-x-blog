### Q7093 · 定时任务 DST/时区重复执行事故复盘

难度：P6 ｜ 标签：调度 / 时区 / 事故复盘

**问**：一个每天 02:30 跑的结算任务，在夏令时切换日（秋令时）凌晨跑了两次，下游结算重复入账。为什么 crontab "每天 02:30" 会一天跑两次？调度器怎么正确处理？

**答**：
- **结论**：crontab 的 02:30 是"本地墙上时间"。秋令时那天，本地时间从 02:59:59 拨回 02:00:00，于是 02:00-02:59 这个区间在物理时间上出现两次，cron 两次都命中 → 任务跑两遍。反向（春令时）则 02:00-02:59 不存在，任务当天漏跑。系统级解法是把调度锚点换成语义明确的时间：① 任务调度统一用 UTC 表达（cron 用 UTC 时区运行，或用 systemd timer 的 `OnCalendar=UTC`）；② 必须按"本地营业日"跑的任务，用支持 DST 语义的调度器（Airflow/Prefect 的 cron 用 pendulum/pytz 解析）并明确"缺失时刻跳过、重复时刻只跑一次"策略；③ 幂等兜底：任务以"业务日期（business date）"为幂等键（`run_id = business_date`），重复触发直接跳过。
- **取舍**：全 UTC 的代价是"业务日切"不再与本地日历对齐（UTC 00:00 = 北京 08:00），报表口径要单独处理；按本地时间跑的代价就是 DST 的重复/缺失，必须配幂等键。两者的取舍本质是"调度简单"换"正确性保证"，对结算类任务永远选正确性。
- **实战**：步骤：① 盘点所有 cron/Airflow 任务的时区语义，结算类改 business-date 幂等键；② 调度器显式声明时区（`timezone='Asia/Shanghai'`，不要依赖宿主机 /etc/localtime）；③ DST 切换日做一次"任务触发矩阵"演练（该日每个任务的触发次数断言）；④ 复盘项：重复入账的修复走幂等去重表，而不是手工对账。

```python
# 业务日期幂等去重器：DST 重复触发的兜底（纯标准库）
# 基线：Python 3.9+

import datetime as dt


class IdempotentScheduler:
    """按 business_date 去重：同一天重复触发只跑一次"""

    def __init__(self) -> None:
        self.done: dict[str, str] = {}

    def trigger(self, task: str, business_date: str, trigger_note: str) -> str:
        key = f"{task}:{business_date}"
        if key in self.done:
            return f"SKIP: 已执行于 {self.done[key]}（本次: {trigger_note}）"
        self.done[key] = trigger_note
        return f"RUN: {task}@{business_date} ({trigger_note})"


def business_date(ts_utc: dt.datetime, tz_offset_hours: int) -> str:
    """按本地营业日切（这里简化为固定偏移，DST 场景换 zoneinfo）"""
    local = ts_utc + dt.timedelta(hours=tz_offset_hours)
    return local.strftime("%Y-%m-%d")


def main() -> None:
    sched = IdempotentScheduler()
    # 秋令时 02:30 两次触发，业务日期相同
    r1 = sched.trigger("settle", "2026-10-25", "02:30 第一次(拨回前)")
    r2 = sched.trigger("settle", "2026-10-25", "02:30 第二次(拨回后)")
    print(r1); print(r2)
    assert r1.startswith("RUN") and r2.startswith("SKIP")
    # 跨日任务：UTC 17:00 = 本地次日 01:00，业务日归属次日
    ts = dt.datetime(2026, 3, 27, 17, 0)
    assert business_date(ts, 8) == "2026-03-28"
    print("OK: business_date 幂等键挡住 DST 重复触发")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 Airflow 官方文档强调 `execution_date` 与"实际运行时间"是两个概念？
→ 一句话提示：Airflow 的调度区间语义是"跑数据时间区间结束后才触发"，DST 日的 interval 计算交给 pendulum 的时区算术处理，而不是墙上时间字符串比较——这正是避开 cron 陷阱的机制。

**追问 2**：zoneinfo 的 `fold` 参数和这有什么关系？
→ 一句话提示：Python 3.9+ zoneinfo 对回拨重叠时段用 `fold=0/1` 区分第一次/第二次出现的同一墙上时间；不处理 fold 的"本地时间 + offset"算术会算错 UTC 时间，正是重复执行的根因之一。

## 背诵要点
- cron 按本地墙上时间触发：秋令时 02:00-03:00 出现两次 → 重复执行；春令时缺失 → 漏跑。
- 兜底三板斧：调度锚点 UTC 化 / 调度器显式时区 + business_date 幂等键 / DST 日触发矩阵演练。
- zoneinfo `fold=0/1` 区分重叠时段；不处理 fold 的本地时间算术是根因级 bug。

## 复盘追问
- 为什么"任务有唯一 run_id"不能替代 business_date 幂等？提示：run_id 唯一挡的是调度器重试，挡不住"DST 产生两个合法 run_id 跑同一段业务逻辑"；幂等键必须落在业务语义上。
- 漏跑（春令时缺失）比重复跑更难发现吗？提示：是——重复跑有对账/报错暴露，漏跑是静默的业务空窗；要用"任务成功心跳表 + 期望日期比对"的巡检兜住漏跑面。
