### Q7204 · pandas 纳秒时间戳的 2262 年上限

难度：P6 ｜ 标签：pandas、Timestamp、datetime64[ns]、溢出

基线：Python 3.12；pandas 2.x `datetime64[ns]` 范围；纯 Python 计算 ns 边界。

**问**：合同系统要存"到期日"，有份合同写的是 2300 年。读进 pandas 后整列变成 `datetime64[ns]`，一做日期运算就报 `OutOfBoundsDatetime: Out of bounds nanosecond timestamp`。年份只到 2300，离 9999 还很远，为什么就溢出了？

**答**：
- **结论**：pandas 默认的 `datetime64[ns]` 用 **64 位有符号整数存"从 1970 年起的纳秒数"**，可表示范围约 **1677-09-21 到 2262-04-11**。2300 年超出上限，转换/运算就溢出。这不是年份太大，而是**纳秒精度 + 64 位**的物理限制：2⁶³ 纳秒 ≈ 292 年。
- **取舍**：要表示更远的日期，可以：① 用 `datetime64[us]`/`datetime64[ms]`/`datetime64[s]`（pandas 2.0+ 支持非纳秒单位），范围扩大到几十万年，代价是丢失纳秒精度；② 用 Python `date`/`datetime` 对象列（object dtype），灵活但失去向量化；③ 用 `Period` 表示年/月粒度。业务上"合同到期日"根本不需要纳秒，选 `datetime64[us]` 或 `date` 更合适。
- **实战**：① 读入时用 `dtype="datetime64[us]"` 或转换后 `astype("datetime64[us]")`；② 对日期列做范围断言（1677-2262），超界数据在入口拦截并告警；③ 不要用 `pd.to_datetime` 的默认 ns 精度处理历史/未来日期；④ 跨系统传输用 ISO 字符串，避免精度假设。

```python
import datetime as dt

NS_MAX = 2 ** 63 - 1
NS_MIN = -(2 ** 63)
EPOCH = dt.datetime(1970, 1, 1, tzinfo=dt.timezone.utc)


def ns_to_dt(ns: int) -> dt.datetime:
    return EPOCH + dt.timedelta(microseconds=ns // 1000)


def fits_ns(year: int) -> bool:
    point = dt.datetime(year, 1, 1, tzinfo=dt.timezone.utc)
    delta = point - EPOCH
    ns = int(delta.total_seconds()) * 1_000_000_000
    return NS_MIN <= ns <= NS_MAX


if __name__ == "__main__":
    print("ns 上限:", ns_to_dt(NS_MAX).date())
    print("ns 下限:", ns_to_dt(NS_MIN).date())
    for year in (2026, 2262, 2300, 9999):
        print(year, "可存入 datetime64[ns]:", fits_ns(year))
    print("结论：纳秒精度只覆盖约 292 年，远期日期要降精度或用 date 对象")
```

**追问一**：为什么 `datetime64[us]` 能表示更远的日期？
→ 解析：同样的 64 位整数，单位从纳秒变成微秒，可表示的跨度扩大 1000 倍（约 29 万年）。代价是精度从纳秒降到微秒——对合同到期日、账单日期完全够用，对高频交易时间戳才需要纳秒。

**追问二**：`pd.to_datetime` 遇到超界值会怎样？怎么安全处理？
→ 解析：默认 `errors="raise"` 抛 `OutOfBoundsDatetime`；`errors="coerce"` 会把它变成 `NaT`，等于静默丢日期，必须配合"转换前后非空数对账"才能发现。更稳的是先按字符串年份做范围校验，再转换。
