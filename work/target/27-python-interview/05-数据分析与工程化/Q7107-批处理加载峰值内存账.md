### Q7107 · 批处理数据加载的峰值内存账：chunk size 与 GC 的关系

难度：P6 ｜ 标签：内存容量 / 分块处理 / GC

**问**：一个 ETL 任务把 40GB CSV 读进 pandas 处理，机器 64GB 内存，却 OOM 了。把 `chunksize` 从 200 万行降到 20 万行也没完全解决——RSS 依然缓慢爬升直到触发 OOM。分块读为什么挡不住 OOM？峰值内存账应该怎么算？

**答**：
- **结论**：分块读只控住**加载**这一段，OOM 的内存在别处：① CSV 解析的临时峰值——pandas 读取过程中字符串先以 Python str 对象存在，转 dtype（category/箭头）前同一份数据以两种形态共存，单 chunk 峰值是稳态的 2-3 倍；② 结果累积——`pd.concat([chunk_results...])` 每次都生成新对象，旧引用若还在列表/闭包里（如错误处理、日志装饰器捕获），GC 不能回收；③ **碎片化**——反复分配/释放大块让 glibc malloc 的 arena 留下空洞，RSS 不降（Python 对象进了 pymalloc 小块则更散），`tracemalloc` 看到的"活对象"很小但 RSS 很大；④ 引用泄漏——chunk 循环里的变量被异常栈、全局缓存、matplotlib 引用捕获。所以峰值账 = `chunk 峰值 × 转换放大 + 累积结果 + 碎片余量(1.3-1.5×)`，只调 chunksize 是漏项的账。
- **取舍**：工程选项：① 列裁剪/早转 dtype——读前 `usecols` + `dtype` 声明（category/float32），把"解析临时形态"压到最小；② 结果流式落盘——每 chunk 直接 append 到 parquet/数据库，全程不 concat 累积；③ 换引擎——Polars lazy/streaming 或 DuckDB 让引擎管外存（但要重新做它的内存预算，见 Q7084）；④ 治碎片——大 chunk 用 numpy/bytes 走 `malloc_trim`（ctypes 调 glibc）或干脆改用整数块数固定的工作流；⑤ 监控——进程内定期 `gc.collect()` + `RSS/活对象`双指标，RSS 爬升而活对象平稳即碎片或泄漏。
- **实战**：峰值账步骤：① 用 `tracemalloc` 测单 chunk 的加载峰值与转换后大小，算放大系数；② 确认累积路径（grep concat/append/全局容器）；③ 设预算：`chunk_size = (内存预算 × 0.5) / (单行峰值 × 放大系数 × 1.4 碎片余量)`；④ 上线后 RSS 采样进日志，爬升曲线异常就告警。验证方法：本地用 1/100 数据量模拟，RSS 曲线应呈锯齿状（chunk 间回收）而非单调爬升。

```python
# 峰值内存账：单 chunk 放大系数 + 碎片判定（标准库 tracemalloc + 模拟 RSS）
# 基线：Python 3.9+

import gc
import tracemalloc


def chunk_peakAMPLifier(rows: int) -> tuple[float, float]:
    """模拟单 chunk：解析形态（str 对象）与转换形态（紧凑数值）共存"""
    tracemalloc.start()
    parse_form = [f"row-{i}-payload-{i*7}" for i in range(rows)]     # 解析形态
    converted = [float(i % 997) for i in range(rows)]                # 转换形态
    peak = tracemalloc.get_traced_memory()[1]
    del parse_form
    gc.collect()
    steady = tracemalloc.get_traced_memory()[0]
    tracemalloc.stop()
    return peak / 1024, steady / 1024


def budget_chunk_rows(memory_budget_mb: float, peak_per_row_b: float,
                      amplify: float, safety: float = 1.4) -> int:
    """chunk 行数预算 = 可用内存 / (单行峰值 × 放大 × 碎片余量)"""
    usable = memory_budget_mb * 1024**2 * 0.5    # 一半预算给单 chunk
    return int(usable / (peak_per_row_b * amplify * safety))


def main() -> None:
    peak_kb, steady_kb = chunk_peakAMPLifier(200_000)
    amplify = peak_kb / steady_kb
    print(f"单 chunk：峰值 {peak_kb:.0f}KB / 稳态 {steady_kb:.0f}KB，放大 {amplify:.1f}×")
    assert amplify > 1.0, "解析与转换形态共存必然有放大"

    rows = budget_chunk_rows(memory_budget_mb=1024, peak_per_row_b=peak_kb * 1024 / 200_000,
                             amplify=amplify)
    assert 100_000 < rows < 10_000_000
    print(f"预算内 chunk 行数 ≈ {rows:,}")

    # 碎片/泄漏判定：活对象平稳而 RSS 单调爬升
    rss_curve = [300, 320, 360, 410, 470, 540]   # MB：锯齿失效
    live_curve = [180, 175, 182, 178, 181, 179]
    rising = all(b > a for a, b in zip(rss_curve, rss_curve[1:]))
    stable_live = max(live_curve) - min(live_curve) < 15
    if rising and stable_live:
        print("判定：RSS 单调爬升 + 活对象平稳 → 碎片或外部泄漏，不是 chunk 太大")
    print("OK: 峰值账 = chunk 峰值×放大 + 累积 + 碎片余量，分块只是账的一行")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 `tracemalloc` 显示内存不大、RSS 却很高？
→ 一句话提示：tracemalloc 只统计 Python 层分配，看不到 glibc malloc 的碎片空洞与 mmap 阈值行为——大块释放后 RSS 不立即还给 OS；对照指标是活对象字节数 vs `/proc/self/statm` RSS 的差值。

**追问 2**：`pd.concat` 累积结果的正确替代是什么？
→ 一句话提示：每 chunk 直接写目标（parquet append / DB insert），或在"列对齐一致"的前提下用 PyArrow 的 `Table` 流式拼接（Arrow 内存格式无 pandas 对象放大），从根上消灭 Python 对象累积。

## 背诵要点
- 分块读只控加载段：峰值账 = chunk 峰值 ×（解析/转换形态放大 2-3×）+ 结果累积 + 碎片余量 1.3-1.5×。
- 先裁剪再分块：usecols + dtype 早声明，结果流式落盘不 concat；RSS 单调爬升 + 活对象平稳 = 碎片/泄漏信号。
- 验证方法：1/100 数据量跑 RSS 曲线，锯齿状（回收）为健康，单调爬升为异常。

## 复盘追问
- 为什么 64GB 机器跑 40GB 数据必 OOM？提示：40GB CSV 解析成 Python 对象形态轻松破 150GB（字符串对象头 + 指针 + 装箱），不是"数据 40GB 内存 64GB"的简单比较——CSV 行数才是账的驱动因子。
- 怎么把内存预算写进调度系统的资源申请？提示：按实测峰值 ×1.3 申请容器 memory limit，并区分申请值与 limit（limit 触顶 OOMKill，申请值影响调度），任务分档复用（见 Q7076 worker 容量）。
