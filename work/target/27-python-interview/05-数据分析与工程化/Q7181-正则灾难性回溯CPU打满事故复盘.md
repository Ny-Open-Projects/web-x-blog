### Q7181 · 一条日志打挂整个服务：正则灾难性回溯事故复盘

难度：P6 ｜ 标签：事故复盘、正则回溯、CPU 容量
基线：Python `re`（回溯型引擎，无 RE2 线性保证）；3.11+（`re` 性能无质变，仍可回溯）。

**问**：日志清洗服务接到一条特殊格式的用户日志后 CPU 单核打满 30 秒、worker 线程池排队雪崩。根因是一条正则 `^(\w+)*@\d+$`。什么是灾难性回溯？为什么改写模式顺序或加非捕获组都救不了？

**答**：**结论**：灾难性回溯 = 模式有**多种匹配路径**且失败发生在长输入尾部：`(\w+)*` 对每个切分位置都尝试组合，输入长度 n 时路径数指数级（2^n 量级）。Python `re` 是带回溯的实现，不保证线性时间——不是"写得不好"，是这类模式天然会炸。单点修复方向：① **消除歧义路径**——把 `(\w+)*@` 改成 `[a-zA-Z0-9]+@`（贪婪一次切分，无组合），这是唯一根治法；② 改用**线性引擎**——RE2（`google-re2`）或 Rust regex（`regex` 包经 PyO3），保证 O(n)，代价是丢弃回溯能力（反向引用/环视部分受限）；③ **运行时保险**——把"外部输入的正则/长文本匹配"放进子进程并设超时（`signal.alarm` 或 ProcessPool + timeout），炸了只杀单个任务。

**取舍**：RE2 的取舍是功能换时间：支持的正则语法子集更小（不支持反向引用），迁移前要先审计存量模式是否用到受限特性。子进程超时的取舍是成本换兜底：进程冷启动与 IPC 开销（毫秒级）在清洗路径上可接受，但池化常驻的方案要控 worker 内存。团队规范层面：**所有对用户输入执行的正则必须过代码评审的复杂度检查**（嵌套量词、可空重复是红旗），并加单测用 10KB 的"对抗输入"验证耗时。

**实战**：用标准库实测回溯爆炸与安全改写：

```python
# 灾难性回溯实测：小 n 看翻倍趋势，大 n 交给超时兜底
import re, subprocess, sys, time, textwrap

def timed(pattern: str, text: str) -> str:
    t0 = time.perf_counter()
    re.search(pattern, text)
    return f"{(time.perf_counter()-t0)*1000:.2f}ms"

dangerous = r"^(\w+)*@\d+$"
safe = r"^[a-zA-Z0-9]+@\d+$"

prev = None
for n in (12, 14, 16, 18):
    text = "a" * n + "#"            # 尾部不匹配 -> 全量回溯
    dt = timed(dangerous, text)
    ratio = f"  x{float(dt[:-2])/prev:.1f}" if prev else ""
    print(f"n={n:2d} 危险版 {dt}{ratio}   安全版 {timed(safe, text)}")
    prev = float(dt[:-2])
print("耗时随 n 每加 2 翻 ~4 倍（指数）——事故日志 30KB 直接把核打满")

# 运行时保险：子进程 + 硬超时（超时自动 kill，不拖累主进程）
if __name__ == "__main__":          # spawn 平台守卫
    script = textwrap.dedent(r"""
        import re
        m = re.search(r"^(\w+)*@\d+$", "a" * 30 + "#")
        print("match:", bool(m))
    """)
    t0 = time.perf_counter()
    try:
        subprocess.run([sys.executable, "-I", "-c", script],
                       capture_output=True, timeout=1.5)
        print("1.5s 内完成（罕见：机器过快，调大 n）")
    except subprocess.TimeoutExpired:
        print(f"子进程 {time.perf_counter()-t0:.1f}s 超时被 kill —— "
              f"主进程无伤，单任务降级")

# 评审红旗清单：嵌套量词/可空重复
RED_FLAGS = [r"(\w+)*", r"(\s+)*", r"(a*)*", r"(.+)+"]
for pat in RED_FLAGS:
    print(f"红旗模式 {pat!r}: 含嵌套可空重复 -> 评审需改写或换线性引擎")
```

**追问 1**：为什么把 `*` 改成 `+`、或加非捕获组 `(?:...)` 不解决回溯爆炸？
提示：回溯爆炸来自"多种路径组合"，非捕获组只省捕获开销不减少路径数；可空重复的嵌套仍是指数。必须把歧义消除（单段贪婪）或换线性引擎。

**追问 2**：RE2 为什么能保证线性？它放弃了什么？
提示：RE2 用 NFA 模拟（并行跟踪所有路径），路径数不随输入指数化；代价是不支持反向引用与部分环视——审计存量模式再迁移。

**追问 3**：signal.alarm 超时和子进程超时各适合什么场景？
提示：signal.alarm 只在主线程生效、仅 Unix，适合单进程工具脚本；服务内多 worker 场景必须用子进程/线程隔离（C 扩展正则若释放 GIL 可用线程超时，re 不释放 GIL 则线程超时救不了）。

## 背诵要点
1. 回溯爆炸根因：模式存在指数级匹配路径（嵌套可空重复 `(\w+)*`），re 引擎回溯不保证线性时间。
2. 根治是消除歧义（单段贪婪 `[a-zA-Z0-9]+`）或换线性引擎 RE2/Rust regex（代价：不支持反向引用）；运行时兜底用子进程超时。
3. 评审红旗：嵌套量词、可空重复；对用户输入的正则必须带对抗输入单测（10KB 级）。
