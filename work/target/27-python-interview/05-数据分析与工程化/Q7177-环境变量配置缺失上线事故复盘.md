### Q7177 · 少一个环境变量就白屏：配置缺失事故复盘与启动闸门

难度：P6 ｜ 标签：事故复盘、配置管理、12-factor
基线：pydantic-settings 2.x（BaseSettings）；12-factor 配置原则。

**问**：新服务发布到生产，流量一进来就 500——排查两小时发现是 K8s Deployment 少配了一个环境变量，本地和预发都有所以没拦住。这类配置缺失事故的完整复盘应该怎么写？如何在"启动阶段"而不是"请求阶段"失败？

**答**：**结论**：事故结构是**配置校验时机错位**：配置缺失的正确响应是"进程拒绝启动"（fail fast），而事故里代码用的是 `os.getenv("X", default)` 式的惰性取值，缺失被默认值掩盖，直到某个请求路径才炸。复盘要产出三层修复：① **启动闸**——所有必需配置在 import/启动期校验（pydantic-settings 的 `BaseSettings` 声明必填字段，缺了直接抛错退出），K8s 的 liveness/startup 探针会立刻暴露；② **环境差异账**——预发与生产的配置做 diff 审计（把两边实际生效的配置键集合导出对比），缺失键在发布前就被发现；③ **默认值治理**——`getenv` 带默认值只允许用于"可安全降级"的配置，敏感/结构性配置禁止默认值，lint 或评审门禁检查。

**取舍**：全量 fail fast 与可用性有张力：如果配置中心短暂抖动，启动闸会不会把整个集群"误杀重启"？缓解是区分**来源**：环境变量/静态文件在启动期严格校验；动态配置中心（Nacos/Apollo）允许启动后热加载、带"最后已知 good value"兜底。另一个取舍是 schema 的维护成本：pydantic Settings 类要随配置演进，团队要接受"加配置必改类"的纪律，否则闸门形同虚设。

**实战**：启动配置闸与环境 diff 审计（标准库演示 pydantic 模式的语义）：

```python
# 启动期配置闸：缺失即拒绝启动
import os, sys

REQUIRED = {  # 键: (说明, 示例)
    "DATABASE_URL": ("主库连接串", "postgresql+psycopg://u:p@h/db"),
    "REDIS_URL": ("缓存地址", "redis://h:6379/0"),
    "JWT_SECRET": ("签名密钥", None),
}
OPTIONAL_WITH_SAFE_DEFAULT = {"LOG_LEVEL": "INFO", "TIMEOUT_S": "30"}

class ConfigError(Exception): pass

def load_config(env: dict[str, str]) -> dict[str, str]:
    cfg, missing = {}, []
    for key, (desc, _) in REQUIRED.items():
        v = env.get(key)
        if not v:
            missing.append(f"  {key}: 必填（{desc}）")
        else:
            cfg[key] = v
    cfg.update({k: env.get(k, d) for k, d in OPTIONAL_WITH_SAFE_DEFAULT.items()})
    if missing:
        raise ConfigError("启动中止，缺配置:\n" + "\n".join(missing))
    return cfg

# 模拟生产环境（少了 JWT_SECRET）
prod_env = {"DATABASE_URL": "pg://..", "REDIS_URL": "redis://.."}
try:
    load_config(prod_env)
except ConfigError as e:
    print(f"[fail fast] {e}")

# 环境差异审计：预发 vs 生产的键集合 diff
staging_keys = set(prod_env) | set(OPTIONAL_WITH_SAFE_DEFAULT)
missing_in_prod = (set(REQUIRED) | set(OPTIONAL_WITH_SAFE_DEFAULT)) - set(prod_env)
print(f"\n预发有而生产缺失的键: {sorted(missing_in_prod)} <- 发布前就该拦住")

# 默认值治理：哪些键允许 getenv 默认值（lint 规则示意）
def lint_default(key: str) -> str:
    if key in OPTIONAL_WITH_SAFE_DEFAULT:
        return f"{key}: 允许默认值 {OPTIONAL_WITH_SAFE_DEFAULT[key]}"
    return f"{key}: 禁止默认值（结构性/敏感配置）"

print(lint_default("LOG_LEVEL"), "|", lint_default("JWT_SECRET"))
```

**追问 1**：为什么"请求阶段才发现配置缺失"比"启动失败"严重得多？
提示：启动失败在发布流水线就拦截，影响面是单实例；请求阶段失败是线上 500+ 告警+人工排障，且负载均衡可能把流量持续打到每个新实例上重复炸。

**追问 2**：配置中心（Nacos/Apollo）热加载场景下，启动闸怎么设计？
提示：分两层——环境变量里的"引导配置"（配置中心地址、命名空间）启动期必填校验；业务配置启动后加载，加载失败用最后已知 good value 兜底并告警，不阻塞启动。

**追问 3**：pydantic-settings 相比裸 `os.getenv` 的核心收益是什么？
提示：声明式 schema + 类型转换 + 必填校验一次性完成，`model_config` 可切 env 文件/secrets 目录；代价是配置演进要改类——这份纪律正是闸门有效的前提。

## 背诵要点
1. 配置缺失必须 fail fast：必需配置在启动期校验（pydantic-settings 必填字段），拒绝启动比请求期 500 便宜几个量级。
2. 三层修复：启动闸、预发/生产配置键集合 diff 审计、默认值治理（getenv 默认值仅限可降级项）。
3. 动态配置中心区分来源：引导配置启动期严格，业务配置热加载 + 最后已知 good value 兜底，防止配置抖动误杀重启。
