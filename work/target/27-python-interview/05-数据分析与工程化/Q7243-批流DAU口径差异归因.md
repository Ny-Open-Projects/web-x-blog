### Q7243 · 同一个 DAU 实时 103 万、离线 102 万：批流口径差异的归因清单

难度：P7 ｜ 标签：批流一体、指标口径、迟到数据、对账归因

基线：Python 3.12；用同一份事件流分别按"批处理（全量重算）"与"流处理（水位线增量）"算 DAU，输出差异归因。

**问**：数据日报的 DAU 和实时看板的 DAU 每天都对不上，误差 0.5%~1%，运营拿两个数问"哪个是真的"。批流架构（Q360 的 Lambda/Kappa）下两条链路为什么必然有差？这个差能不能收敛到零？验收口径该以谁为准？

**答**：
- **结论**：差异来自三个结构性原因：① **窗口边界**——流处理的窗口按处理时间切片，跨零点事件归属可能不同；② **迟到数据**——水位线（Q1452）之后的迟到事件不再计入当天窗口，批处理是隔天全量重算，迟到事件全部计入；③ **去重口径**——流式去重靠"状态里是否见过该设备"（状态有 TTL），批处理按天全量去重。这三项都是**结构性偏差**，不是 bug，所以两数永远不会自然相等；能做的是把差值项逐项量化并归因。
- **取舍**：① 看板/运营决策用实时数，财务结算/考核用离线数——把"以谁为准"写进口径字典（Q1073）而不是靠口头默认；② 收敛策略：流式链路补一个"次日修正任务"，水位线关闭后用批处理结果覆写当天值，看板短时展示实时值、次日展示修正值并打标；③ 也可以选"实时链路只做近似展示、对账周报用离线"，接受噪声；④ 消除窗口边界差最有效的办法是**事件时间窗口**（按事件时间戳切片），而不是调水位线参数。
- **实战**：① 对账自动化：每天跑批后 diff（实时值、离线值、差值、差值率），差值超阈值告警并输出归因表；② 归因至少三列：迟到事件量、窗口跨界事件量、去重差异量——有了量化才能区分"正常结构性差异"与"链路故障"；③ 监控差值率的**趋势**而不是绝对值，趋势突变才是链路坏了的信号。

```python
"""批流 DAU 差异归因：窗口边界 + 迟到数据 + 去重口径三项量化。"""
import datetime as dt

Event = tuple  # (ts, device_id, arrive_ts)


def batch_dau(events: list[Event], day: str) -> int:
    """离线链路：按事件时间全量重算，迟到事件全部计入。"""
    return len({d for ts, d, _a in events if ts.startswith(day)})


def stream_dau(events: list[Event], day: str, watermark_delay_min: int = 10):
    """实时链路：按到达序处理，窗口关闭（超过水位线）后的迟到事件丢弃。"""
    seen: dict[str, dt.datetime] = {}
    closed_events = []
    for ts, dev, arrive in events:
        t = dt.datetime.fromisoformat(ts)
        a = dt.datetime.fromisoformat(arrive)
        window_end = t.replace(hour=23, minute=59, second=59) \
            if t.date().isoformat() == day else None
        # 简化水位线：事件时间窗口关闭 = 窗口结束 + delay 后才接受
        deadline = window_end + dt.timedelta(minutes=watermark_delay_min) \
            if window_end else None
        if deadline and a > deadline:
            closed_events.append((ts, dev))
            continue
        if ts.startswith(day):
            seen.setdefault(dev, a)
    return len(seen), closed_events


if __name__ == "__main__":
    events: list[Event] = []
    day = "2026-11-23"
    base = dt.datetime.fromisoformat(day + "T08:00:00")
    for i in range(10_000):
        t = base + dt.timedelta(minutes=i % 900)              # 900 分钟 > 一天，跨界
        events.append((t.isoformat(), f"dev{i}", t.isoformat()))
    # 迟到事件：数据管道延迟 40 分钟才到
    late = base.replace(hour=22) + dt.timedelta(minutes=30)
    for i in range(300):
        events.append(((late - dt.timedelta(minutes=i)).isoformat(),
                       f"late{i}", (late + dt.timedelta(minutes=40)).isoformat()))
    # 跨设备共用（去重口径压力）
    for i in range(200):
        events.append(((base + dt.timedelta(minutes=i)).isoformat(),
                       "shared_dev", (base + dt.timedelta(minutes=i)).isoformat()))

    b = batch_dau(events, day)
    s, closed = stream_dau(events, day)
    cross = sum(1 for ts, _, _ in events
                if ts.startswith(day) and dt.datetime.fromisoformat(ts).hour >= 23
                and dt.datetime.fromisoformat(ts).minute >= 50)
    print(f"离线 DAU={b:,}  实时 DAU={s:,}  差值={b - s:,} ({(b - s) / b:.1%})")
    print(f"归因-迟到丢弃: {len(closed)} 台设备")
    print(f"归因-窗口边界跨零点未归入实时窗口: ~{cross} 条")
    print(f"归因-状态去重与全量去重的口径差: shared_dev 共用设备")
    print("结论：三项都是结构性差异；次日修正任务 + 归因表是标准收敛姿势")
```

**追问一**：为什么不用"实时链路直接全量重算当天"来消除差异？

→ 解析：实时链路的价值是低延迟高吞吐，全量重算与批处理无异，还因为高频触发而烧资源；且流式引擎对"当天全量重算"的语义支持（回撤流）实现复杂、成本高。工程上的主流就是"实时看趋势、离线定事实 + 次日修正"的组合。真正追求批流一致的技术路线是流批一体引擎（同一套 SQL、同一套语义跑两种模式），但它要求把口径严格定义在事件时间与确定性窗口上，改造成本高，多数团队仍走"实时 + 次日修正"的务实路线。

**追问二**：差值率突然从 0.5% 跳到 5%，怎么快速定位是链路坏了还是口径变了？

→ 解析：先看归因表三列的变化方向：迟到丢弃量暴涨 → 上游管道延迟变大（消费者积压）；窗口边界事件量暴涨 → 上游时钟漂移或时区配置变更；差值率涨但三项都平稳 → 去重状态被清（作业重启丢状态）或埋点 schema 变了。再对照变更记录：当天有没有发版、有没有改水位线/窗口参数、有没有上游服务重启。结构化差异是"稳定的噪声"，链路故障是"某一项突然放大"——归因表就是用来区分这两种情况的。
