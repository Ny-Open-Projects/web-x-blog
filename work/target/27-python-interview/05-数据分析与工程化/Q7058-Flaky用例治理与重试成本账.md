### Q7058 · Flaky 用例治理与重试成本账

难度：P6 | 标签：测试治理、flaky、重试策略、CI 成本

**问**：CI 天天红灯，团队最后都学会了"重跑一下就绿"。为什么"失败自动重试一次"看似解决了 flaky，实际上让真回归活得更久？重试的隐性成本怎么算？flaky 该怎么治理而不是掩盖？

**答**：
- **结论**：自动重试的问题不是成本而是语义：flaky（天然不稳定）与间歇回归（真 bug 但不是每次失败）在单次结果上无法区分——重试对两者一视同仁地放行。量化后果：重试让绿灯率从 10% 涨到 52%，但其中 44% 的绿灯运行里真回归被洗绿，团队的"修 bug 时钟"被拉长数周。治理正解是分类处置：统计每个用例的历史失败率，进隔离区（不阻断、带修复 SLA）；重试白名单只放行"已确认 flaky 清单"里的用例，新面孔失败永远红灯——把区分做在策略层，而不是赌单次结果。
- **取舍**：完全禁重试会放大 flaky 对 CI 的干扰（绿灯率太低，团队开始手动重跑，纪律更差）；完全放开重试则掩盖回归。中间态是"白名单重试 + 隔离区 SLA"：重试成本可控（只重跑失败用例，本例每轮多 0.8s），隔离区给 flaky 一个"不阻断但必须修"的出口，两周修不完就删测试——没有 SLA 的隔离区会变成垃圾场。
- **实战**：识别 flaky 用统计不用直觉：连续 30 次运行的用例失败率在 1%-90% 之间波动的是 flaky，固定失败是新回归；flaky 的常见根因按命中率排：共享 fixture 状态、时间/随机数依赖、异步等待不足、外部依赖抖动——前三个都能修，修不了才进隔离区。

```python
"""Flaky 用例治理：自动重试的成本账与"重试掩盖间歇回归"的量化。"""
import random

random.seed(5)

N_TESTS, FLAKY_RATE, RUNS = 200, 0.005, 400
TEST_SECONDS = 0.5          # 单用例耗时（CI 时间单位）

def run_suite(day: int) -> set[int]:
    """跑一轮：0.5% 概率的天然 flaky；第 10 天起 t42 出现间歇回归（失败概率 0.7）。"""
    failed = {i for i in range(N_TESTS) if random.random() < FLAKY_RATE}
    if day >= 10 and random.random() < 0.7:
        failed.add(42)          # 真 bug：与 flaky 表现相同，无法用单次结果区分
    return failed

for retry in (0, 1):
    greens, masked, extra_cost = 0, 0, 0.0
    for day in range(RUNS):
        failed = run_suite(day)
        had_regression = 42 in failed
        for _ in range(retry):                       # 自动重试 N 次
            extra_cost += len(failed) * TEST_SECONDS
            failed = {t for t in failed if t in run_suite(day)}
        if not failed:
            greens += 1
            if had_regression:
                masked += 1                          # 红灯被重试洗绿，回归被掩盖
    print(f"重试 {retry} 次：绿灯率 {greens / RUNS:.0%}，"
          f"被洗绿的真回归 {masked} 次，重试额外耗时 {extra_cost:.0f}s")
print("治理：flaky 隔离区（不阻断但带修复 SLA）+ 重试只放行'历史 flaky 清单'里的用例，"
      "新面孔失败永远红灯")
```

**追问链**：
1. 追问一层：为什么"重跑就绿"会让团队最终停止信任 CI？——CI 的价值是"红灯即回归"的确定性；当红灯 44% 是噪声时，人会建立"重跑一下就好"的肌肉记忆，真回归的红灯也被同样对待。信任一旦塌了，测试再多也是摆设——所以治理 flaky 不是测试质量问题，是信号质量问题。
2. 追问二层：重试白名单怎么防止"真回归混进白名单"？——白名单按"用例级历史失败率"动态准入与退出：进入要求失败率长期波动且根因已定位（如时钟依赖）；一旦某用例的失败模式从"随机"变成"持续"，自动摘出白名单并标红。白名单本身要有 owner 与复审周期。

**背诵要点**：
1. 重试无法区分 flaky 与间歇回归：绿灯率上升的代价是真回归被洗绿、修复时钟拉长。
2. 治理 = 隔离区（不阻断 + 修复 SLA，修不完就删）+ 白名单重试 + 新失败永远红灯。
3. flaky 靠统计识别（失败率波动区间），根因前四名：状态泄漏、时钟/随机、异步等待、外部抖动。

**复盘追问**：
1. 团队已经在用"失败自动重试三次"，怎么安全收紧？（保留重试但只对白名单生效；先用两周统计用例失败率建清单，再切换策略——直接关掉会引发"CI 又坏了"的反噬）
2. 为什么"隔离区没有 SLA"比没有隔离区更糟？（隔离区测试从此无人看、无人修，真正的回归在里面静默腐烂；SLA 到期删测试是强制决策点——要么修要么承认它没有价值）
