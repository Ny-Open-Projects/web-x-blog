### Q7061 · 失败用例聚类与回归集最小化

难度：P6 | 标签：测试工程、失败聚类、回归效率

**问**：CI 一次红了 40 个用例，是 40 个 bug 吗？怎么用聚类把"修复验证"的成本从 40 次压到 2 次？聚类签名的粒度怎么定？

**答**：
- **结论**：一次提交导致的大面积红几乎总是少数根因的连锁反应。失败聚类：给每个失败用例生成签名（异常类型 + 规范化的错误位置：文件:行号去数字、栈帧取业务层最深一帧），签名相同归为一簇，每簇修复后只跑一个代表用例验证，其余用例随整批回归。40 个失败常聚成 2-3 簇——工程价值是反馈速度：工程师修一个根因即可让一簇全绿。
- **取舍**：签名粒度：太粗（只按异常类型）会把"超时"和"断言失败"以外的不同根因混一簇，修复验证会漏；太细（含具体数字/参数）会同一根因拆多簇，聚类失效。实践是"异常类型 + 规范化调用位置"，并允许人工合并/拆分簇（聚类结果进报告，不自动吞掉用例）。
- **实战**：落点：CI 报告加"失败簇视图"；簇的代表用例进修复者的 PR 检查项；长期看，簇统计能暴露"常驻失败簇"（flaky 区域）——某签名每周都出现就该立项治理。注意区分"同一根因"与"同一症状"：两个用例都在 db.py:120 挂但断言目标不同，可能各自独立，代表用例要覆盖两边断言。

```python
"""失败用例聚类：按错误签名聚合，同一根因只保留代表用例。"""
import re, hashlib

failures = [
    ("test_order_refund", "AssertionError: expected 200 got 500", "db.py:120 conn.execute"),
    ("test_order_cancel", "AssertionError: expected 200 got 500", "db.py:120 conn.execute"),
    ("test_user_login",   "TimeoutError: read timeout 3s",        "http.py:88 request"),
    ("test_cart_add",     "AssertionError: expected 200 got 500", "db.py:120 conn.execute"),
    ("test_sms_send",     "TimeoutError: read timeout 3s",        "http.py:88 request"),
]

def signature(case):
    _name, err, loc = case
    return hashlib.sha1(f"{err.split(':')[0]}|{re.sub(r'\d+', 'N', loc)}".encode()).hexdigest()[:8]

clusters = {}
for case in failures:
    clusters.setdefault(signature(case), []).append(case[0])

for sig, names in clusters.items():
    print(f"根因 {sig}: {names}  -> 修复后跑代表用例 {names[0]}，其余回归")
print("2 个失败签名 ≈ 2 类根因：5 个用例的修复验证压缩为 2 次重跑")
print("要点：失败聚类按'异常类型+规范化位置'签名；签名粒度太粗会掩盖不同根因")
```

**追问链**：
1. 追问一层：为什么"代表用例"要覆盖该簇全部断言目标？——同签名可能是同位置的不同症状；代表用例只验证一部分，其余失败会在整批回归时再冒出来，浪费一轮 CI。
2. 追问二层：聚类与"定向测试"（按变更选测试）是什么关系？（两者正交：定向测试决定"跑哪些"，聚类决定"失败后怎么看"；一起把 CI 时长和修复杂音同时压下来）

**背诵要点**：
1. 签名 = 异常类型 + 规范化位置（去数字、取业务层帧）。
2. 每簇一个代表用例做修复验证，其余随整批回归。
3. 常驻失败簇暴露 flaky 区域，是治理立项的信号。

**复盘追问**：
1. 聚类把两个真实不同根因并成一簇，修复验证会漏什么？（代表用例过了但另一根因还在——所以要人工可合并/拆分）
2. 为什么"40 红"反而比"1 红"好修？（聚类后根因少、面大，单点修复收益高；最难的是孤例）
