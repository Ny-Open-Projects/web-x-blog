### Q7091 · 同名临时文件并发写导致下游读到半成品事故复盘

难度：P6 ｜ 标签：文件系统 / 并发 / 事故复盘

**问**：两个调度任务偶发重叠时，下游读到的 CSV 时而是半截文件、时而是列数不对。为什么"先写临时文件再 rename"也会出事？

**答**：
- **结论**：常见反模式是用固定临时名（`out.csv.tmp`）：任务 A 和 B 重叠时两个进程写同一个 tmp 文件互相穿插，而且各自 rename 都会把半成品提升为正式文件。正确做法是"每进程唯一临时名 + 原子 rename"：`tmp = f"{final}.tmp.{os.getpid()}.{uuid4()}"`，写完 `os.replace(tmp, final)`——同目录 rename 在 POSIX 上是原子操作，下游要么看到完整旧文件要么看到完整新文件。还有一个隐蔽坑：rename 之前必须 `flush()` + `os.fsync(fd)`，否则断电/kill 时 rename 落盘但数据还在页缓存里，下游读到空/半截。
- **取舍**：写入协议的取舍：单写者假设（调度保证同一目标只有一个写入者）依赖调度系统正确性，重叠时靠"文件锁/抢占锁"兜底；多写者场景则必须改成"唯一目录写入 + 目录级原子切换"（symlink swap 或 manifest 指针），成本更高但彻底消除覆盖。别用 flock 的场景：跨机器（NFS 上 flock 语义不可靠）要改用对象存储的 put-if-none-match 或 manifest。
- **实战**：复盘三件：① 给所有写文件的工具函数收敛到一个 `atomic_write`（临时名唯一 + fsync + replace），全库 grep `open(...'w'` 检查直写路径；② 调度层加互斥锁（同目标任务的锁）；③ 下游读取端加完整性标记（写 manifest 校验行数/校验和，读前验证）。

```python
# 原子写入工具 + 并发正确性验证（纯标准库）
# 基线：Python 3.9+；macOS/POSIX 均支持 os.replace 原子性

import os
import tempfile
import uuid


def atomic_write(path: str, data: str) -> None:
    """唯一临时名 + fsync + 原子 replace"""
    d = os.path.dirname(os.path.abspath(path)) or "."
    tmp = os.path.join(d, f".{os.path.basename(path)}.tmp.{os.getpid()}.{uuid.uuid4().hex[:8]}")
    fd = os.open(tmp, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o644)
    try:
        os.write(fd, data.encode())
        os.fsync(fd)  # 数据先落盘
    finally:
        os.close(fd)
    os.replace(tmp, path)  # 同目录 rename 原子


def reader_never_sees_partial(path: str, attempts: int = 200) -> bool:
    """并发写-读交叉下验证读者只见完整内容"""
    bad = 0
    for _ in range(attempts):
        try:
            with open(path) as f:
                content = f.read()
            if content and not content.endswith("END\n"):
                bad += 1
        except FileNotFoundError:
            bad += 1
    return bad == 0


def main() -> None:
    with tempfile.TemporaryDirectory() as d:
        p = os.path.join(d, "out.csv")
        atomic_write(p, "col1,col2\n1,2\nEND\n")
        with open(p) as f:
            print(f.read().splitlines()[-1])
        assert reader_never_sees_partial(p)
        # 固定 tmp 名反模式演示（两个写者写同名 tmp 会互相覆盖）
        bad_tmp = os.path.join(d, "out.csv.tmp")
        with open(bad_tmp, "w") as f:
            f.write("half")  # 只写一半，另一个进程的写入会穿插
        print("固定 tmp 名：内容", open(bad_tmp).read(), "→ 可能被提升为正式文件")
    print("原子写验证通过")


if __name__ == "__main__":
    main()
```

**追问 1**：`os.replace` 和 `os.rename` 在目标存在时的差异？
→ 一句话提示：POSIX 上两者都原子覆盖目标，`os.replace` 是跨平台正确的选择——Windows 上 `os.rename` 目标存在会抛错，`os.replace` 才等价 POSIX 语义。

**追问 2**：对象存储（S3）上怎么实现等价的原子发布？
→ 一句话提示：S3 单对象 put 本身原子，但"多文件数据集"没有目录级 rename，惯用法是 manifest 指针对象（写新 manifest 用条件 put 或版本号），下游读 manifest 获得一致视图。

## 背诵要点
- 原子写三件套：唯一临时名（pid+uuid）、fsync 后再 rename、os.replace 跨平台原子覆盖。
- 固定 tmp 名是反模式：并发写穿插 + 半成品被提升为正式文件。
- 多文件数据集用 manifest/目录切换发布；跨机器文件锁不可靠（NFS flock）。

## 复盘追问
- 为什么 fsync 不能省？提示：rename 只保证目录项原子可见，不保证数据已从页缓存写到磁盘，崩溃恢复时会看到 rename 后的空/半截文件。
- 下游怎么不依赖写者自律也能自保？提示：读前校验 manifest（行数/校验和）+ 校验失败重试读旧版本，读者侧兜底。
