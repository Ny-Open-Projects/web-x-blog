### Q7054 · 数据倾斜加盐拆分与作业耗时账

难度：P6 | 标签：数据倾斜、加盐、分布式聚合、容量规划

**问**：一个 group-by 作业 99% 的任务 2 分钟跑完，整体却要 40 分钟。为什么分布式聚合的时长由"最慢的一台"决定？加盐（salting）怎么把热 key 摊平？代价是什么？

**答**：
- **结论**：hash(key) 分区下，占比 60% 的热 key 全部落到同一台 reducer——其他机器早早跑完空等，作业时长被最慢一台钉死（木桶效应）。加盐解法是两阶段聚合：先把 `key -> key#0..key#N` 打散到多台并行做局部聚合，再把局部结果按原 key 二次汇总。热 key 的负载从 1 台摊到 N 台，作业时长从"热 key 的时间"降到"单台 1/N 热key + 均摊普通 key"。代价是多一轮 shuffle + 二次聚合，以及代码复杂度——所以只对检测到的倾斜 key 加盐，普通 key 走原路径。
- **取舍**：加盐数 N 不是越大越好：N 台并行要 N 份任务调度开销，N 超过"热 key 实际可拆的并行度"后收益递减；经验是从 N=8 试起，观察最慢一台的行数占比逼近 1/(N+普通key数) 再加。另一个方向是热点预聚合（上游写时合并），把倾斜消灭在写入侧，但要求能改上游。
- **实战**：发现手段：任务耗时基线里"单任务耗时漂移超 40%"优先查数据倾斜；定位后看该 key 的行数分布（Top10 key 行数占比）。通用性：倾斜是分布式 join/聚合的通病，大表 join 小表时优先考虑广播小表（map-side join）绕开 shuffle，加盐是兜底。

```python
"""数据倾斜加盐拆分：一个热 key 如何拖长整个作业的尾延迟。"""
import random

random.seed(11)

# 事件流：hot_key 占 60%，其余分散在 200 个普通 key
events = [("hot_key", 0)] * 6000 + \
         [(f"k{i}", 0) for i in range(200) for _ in range(20)]
random.shuffle(events)

PARTITIONS = 4

def reduce_by_hash(salted_keys: list[str]) -> list[int]:
    """按 hash(key) % PARTITIONS 分到 reducer，统计每台承担的行数。"""
    load = [0] * PARTITIONS
    for k in salted_keys:
        load[hash(k) % PARTITIONS] += 1
    return load

# 方案 A：直接按 key 分区——hot_key 全部落到同一台 reducer
load_a = reduce_by_hash([k for k, _ in events])
print(f"不加盐：各 reducer 行数 {load_a}，最慢一台承担 {max(load_a) / len(events):.0%}"
      f" ——作业时长由最慢一台决定")

# 方案 B：两阶段加盐——key#0..9 打散聚合，再二次汇总
SALT = 10
salted = [f"{k}#{random.randrange(SALT)}" for k, _ in events]
load_b = reduce_by_hash(salted)
print(f"加盐后：各 reducer 行数 {load_b}，最慢一台承担 {max(load_b) / len(events):.0%}")

# 二次汇总：把 salted 计数还原成原始 key
merged: dict[str, int] = {}
for k in salted:
    base = k.rsplit("#", 1)[0]
    merged[base] = merged.get(base, 0) + 1
print(f"二次汇总还原：hot_key = {merged['hot_key']}（应为 6000），"
      f"总 key 数 {len(merged)}（应为 201）")
print("代价：两阶段多一轮 shuffle + 二次聚合；只对倾斜 key 加盐可把开销压到最小")
```

**追问链**：
1. 追问一层：为什么"加机器"不能解决倾斜？——倾斜时瓶颈是单台机器单 key 的串行处理，加机器只是让其他机器更快地空等；hash 分区下同一 key 永远同台，扩容不改变负载分布，只有改变 key 分布（加盐/广播）才有效。
2. 追问二层：count 聚合能加盐二次汇总，哪些聚合不能？——可合并（结合律）的聚合（sum/count/min/max）能两阶段；不可合并的（median、distinct 去重明细）加盐后二次聚合不等价，需要换算法（近似分位 sketch、HyperLogLog）或在单台内换数据结构。

**背诵要点**：
1. 作业时长由最慢 reducer 决定：热 key 60% = 一台承担 60%，其余空等。
2. 加盐 = 两阶段聚合：key#0..N 打散局部聚合，再按原 key 汇总；只对倾斜 key 用。
3. 先诊断后加盐：耗时基线漂移 + Top key 行数分布；可结合律聚合才可两阶段。

**复盘追问**：
1. 作业从 40 分钟降到 8 分钟后，怎么防止下个热 key 再来？（把"单任务耗时漂移 + Top key 占比"固化成例行诊断告警；倾斜检测进作业基线，而不是靠人盯时长）
2. 为什么加盐数 N=10 时最慢一台仍占 34% 而不是 10%？（普通 key 的均摊负载还在每台上；最慢一台 = 热key的1/10 + 全部普通key的1/4，理论下限受 reducer 台数限制）
