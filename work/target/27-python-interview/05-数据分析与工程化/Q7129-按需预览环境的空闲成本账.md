### Q7129 · 每个分支一个预览环境：空闲实例的成本账与生命周期治理

难度：P6 ｜ 标签：成本工程 / 预览环境 / 生命周期

**问**：团队上了"每个 PR 自动部署预览环境"的流程，很爽但云账单翻倍：30 个分支 × 数据库 + 缓存 + 服务，其中一半分支几天没人访问。预览环境的钱花在哪？怎么设计生命周期让"随手起环境"不变成"随手烧钱"？

**答**：
- **结论**：预览环境的成本结构是**数量 × 每份成本 × 空闲时长**：30 个环境 × 每份含服务实例 + 独立数据库/缓存（最贵）× 每天 24h 计费，而典型使用窗口只有工作时段几小时——**利用率不足 20%**。治理优先级：① **生命周期自动回收**——PR 合并/关闭即销毁，长时间无访问（如 48h 无请求）自动休眠或销毁，回收是最大杠杆；② **环境瘦身**——预览环境不复制全部中间件，共享基座 + 只隔离有 schema 变更的部分（数据库用分支克隆按需起，Q7077 克隆成本账同源），缓存/队列用共享实例+namespace 隔离；③ **按需起停**——访问触发冷启动（休眠态→首次请求拉起）替代常驻，代价是首请求延迟；④ 计费可见性——每个环境打成本标签（分支名/owner），月度账单按分支聚合，让"起环境的人看到环境的价格"。
- **取舍**：自动休眠（保留状态，慢）还是自动销毁（干净，重建要 10 分钟）？有状态的环境（装了数据、断点调试中）休眠友好；无状态重建快的服务销毁更干净。另一个关键取舍：预览环境要不要连真实数据？连生产快照最能暴露问题但合规与成本双贵，脱敏子集（Q341 脱敏）是折中——预览环境的价值是"像生产"，不是"是生产"，按验证目标裁剪。
- **实战**：① 平台层强约束：PR 关闭 webhook → 销毁流程必须存在且经演练；② 空闲探测用入口请求数而不是 CPU（休眠的服务 CPU 为零）；③ 成本标签从创建时刻打上，平台拒绝无标签部署；④ 每月报表：环境数、平均存活时长、每分支成本 top10，把治理做成可见数字。

```python
# 预览环境成本账: 数量x每份成本x利用率; 回收/瘦身/按需起停三杠杆
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class PreviewFarm:
    envs: int
    monthly_per_env: float      # 每份 $/月(常驻)
    idle_hours: float           # 每天无访问时长
    daily_hours: float = 24.0

    def utilization(self) -> float:
        return 1 - self.idle_hours / self.daily_hours

    def monthly_cost(self) -> float:
        return self.envs * self.monthly_per_env


def cost_after_recovery(p: PreviewFarm, kill_ratio: float,
                        scale_per_env: float) -> float:
    """回收 kill_ratio 比例环境 + 其余按需起停(按利用率折算)。"""
    kept = p.envs * (1 - kill_ratio)
    return kept * p.monthly_per_env * p.utilization() * scale_per_env


def main() -> None:
    p = PreviewFarm(envs=30, monthly_per_env=200, idle_hours=19)
    assert abs(p.utilization() - 5 / 24) < 1e-9        # ~21%
    base = p.monthly_cost()
    assert base == 6000
    # 治理: 回收 60% + 按需起停(利用率折算) -> 降 ~92%
    after = cost_after_recovery(p, kill_ratio=0.6, scale_per_env=1.0)
    assert after / base < 0.1
    print(f"常驻 ${base:,.0f}/月, 利用率 {p.utilization():.0%}")
    print(f"治理后 ${after:,.0f}/月 (回收60% + 按需起停)")
    print("OK: 最大杠杆=自动回收; 环境瘦身(共享基座+分支克隆DB)与标签计费支撑")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"空闲探测"用请求数而不是 CPU 利用率？
→ 一句话提示：休眠/待机服务的 CPU 恒为零无法区分"刚创建还没流量"和"真的没人用"，入口请求数直接反映"有没有人需要这个环境"，且阈值语义清晰（48h 无请求即销毁）。

**追问 2**：共享基座（共享缓存/队列 + namespace 隔离）引入了什么新风险？
→ 一句话提示：多分支共享实例后，一个分支的压测流量或脏数据会串扰其他预览环境（隔离边界从物理降到逻辑），必须配 namespace 硬隔离与配额（Q7619 串库同源教训），并保留"高危变更走独立环境"的豁免通道。

## 背诵要点
- 成本 = 环境数 × 每份成本 × 24h 计费，而利用率常不足 20%；最大杠杆是生命周期自动回收（PR 关闭即销毁、48h 无请求休眠）。
- 瘦身三板斧：共享基座 + 分支克隆 DB 按需起、访问触发冷启动替代常驻、成本标签（分支/owner）让账单可归因。
- 休眠（保状态、慢）vs 销毁（干净、重建 10min）按状态依赖选；数据用脱敏子集，目标是"像生产"不是"是生产"。

## 复盘追问
- 为什么预览环境流程上线时没人觉得贵，账单月度报表才暴露？提示：单份成本（$200）低于个人预算感知阈值，30 份乘起来才显著——成本可见性必须按"创建者视角"聚合（标签），不能只有总账。
- "每个分支一个环境"和"每个团队一个共享 staging"怎么选？提示：分支级价值在隔离与并行验证，团队级价值在成本与数据一致性；混合策略 = 日常分支走轻量共享 + 发版候选分支走完整独立环境。
