### Q7038 · 数据契约与下游兼容

> 难度:★★★ | 标签:数据契约, schema 演进, ETL

**问**：数据管道的上游改了表结构（加列/改类型/删列），下游三个消费方一起炸——「数据契约」（data contract）怎么定义与执行，schema 变更的兼容分级（forward/backward/full compatible）各允许什么操作，契约违反是「上游拦截」还是「下游适配」？

**答**：① 契约内容：schema（字段/类型/语义）、SLA（新鲜度/完整性：每日 X 点前必须到、行数波动阈值）、质量规则（空值率/枚举值域）——契约是**机器可校验的文档**（JSON Schema/Protobuf 定义），不是 wiki 页面。② 兼容分级（借鉴 schema registry 语义）：**backward**（新数据能被旧消费者读：只允许加可选字段/加默认值）；**forward**（旧数据能被新消费者读：只允许删可选字段）；**full**（两者都要：最严，字段只加不减不类型变更）。分级决定上游能做什么：生产管道默认 backward——上游加列必须可选，否则契约校验直接拒绝提交。③ 拦截 vs 适配：**结构性变更上游拦截**（契约校验在发布流程里，CI 阶段拒绝破坏性变更——事后发现太贵）；**语义漂移下游适配**（字段含义变化无法机器拦截，靠契约文档 + 下游订阅变更通知主动适配）。落地：schema registry 集中管理 + 兼容性检查进 CI + 变更通知（webhook Q6013）推给订阅方。

```python
# 全部标准库；demo 实现「契约校验器（兼容分级）+ 变更通知」
import json

CONTRACTS = {"orders": {"schema": {"id": "int", "amount": "float", "memo": "str|null"},
                        "sla": {"freshness_min": 60}, "mode": "backward"}}

def diff_schema(old: dict, new: dict) -> list[tuple[str, str]]:
    """schema diff：added/removed/changed 三类。"""
    out = []
    for k, v in new.items():
        if k not in old:
            out.append(("added", f"{k}: {v}"))
        elif old[k] != v:
            out.append(("changed", f"{k}: {old[k]} → {v}"))
    for k in old:
        if k not in new:
            out.append(("removed", k))
    return out

def check_compatible(old: dict, new: dict, mode: str = "backward") -> list[str]:
    """兼容分级校验：backward = 只许加可选字段（可空）+ 禁类型变更。"""
    issues = []
    for kind, detail in diff_schema(old, new):
        if kind == "added":
            if mode == "backward" and "null" not in detail and "default" not in detail:
                issues.append(f"非兼容新增（旧读者会拿到缺列）: {detail}")
        elif kind == "removed":
            issues.append(f"非兼容删除: {detail}")
        elif kind == "changed":
            issues.append(f"非兼容类型变更: {detail}")
    return issues

def notify_subscribers(change: str, subs: list[str]) -> list[dict]:
    """变更通知：webhook 语义（Q6013），接收方按通知适配。"""
    return [{"sub": s, "payload": {"change": change, "ts": "now"}} for s in subs]

if __name__ == "__main__":
    old = {"id": "int", "amount": "float", "memo": "str|null"}
    ok_new = {"id": "int", "amount": "float", "memo": "str|null", "tag": "str|null"}
    bad_new = {"id": "int", "amount": "str"}                  # 类型变更+删列
    assert check_compatible(old, ok_new) == []                # 加可空字段兼容 ✅
    issues = check_compatible(old, bad_new)
    assert len(issues) == 2                                   # 改类型+删 memo
    print("兼容分级校验:", issues)
    print("变更通知:", notify_subscribers("orders.add tag(str|null)", ["bi", "risk"]))
    # 口径：结构性变更 CI 拦截（上游），语义漂移靠契约文档+通知（下游适配）。
```

**追问**：1) 为什么「加必填字段」对 backward 不兼容？——旧消费者按旧 schema 解析新数据时遇到未知必填约束会拒绝或崩；加**可空/带默认值**字段才是安全的（旧读者忽略未知字段即可）。2) 契约 SLA 的「新鲜度」怎么机器校验？——管道完成时间戳与承诺时刻 diff，超时告警；「行数波动阈值」防上游静默丢数（行数突降 30% = 上游 bug 而非业务波动）。3) 契约由谁签署与仲裁？——数据平台团队仲裁（中立第三方），上游（生产者）维护 schema、下游（消费者）登记依赖——没有仲裁方的契约就是口头约定。

## 背诵要点
1. 契约 = 机器可校验的 schema + SLA（新鲜度/行数阈值）+ 质量规则，不是 wiki 页面。
2. 兼容分级：backward（新读旧消费者：只加可空字段）/ forward（只删可选）/ full（最严）；结构性变更 CI 拦截在上游。
3. 语义漂移无法机器拦：靠契约文档 + 变更通知（webhook）下游主动适配；平台团队仲裁。

## 复盘追问
1. 下游拒接「契约修订」，但它依赖的字段正是你要删的，怎么破？（提示：分阶段：新字段并存（Q6017 expand-contract 心智）→ 通知迁移期（2 个版本并行）→ 只读期 → 删旧——给下游迁移时间窗口）
2. 「行数波动阈值」怎么设不误报？（提示：按星期/季节基线（周一通常高）动态阈值（同环比 band），静态阈值周一必误报）
