### Q7212 · dbt 增量模型的迟到数据：append 与 merge 的分界

难度：P6 ｜ 标签：dbt、增量模型、迟到数据、幂等

基线：Python 3.12；dbt 1.7+ 增量物化策略（append/merge/delete+insert）；纯 Python 模拟。

**问**：订单增量模型用 `materialized='incremental'` + `append` 策略，每天只跑 `where dt = '{{ ds }}'`。某天渠道补传了三天前的订单，模型重跑后当天的报表多了这些订单，但三天前的分区仍然是旧数据；再跑一次又重复了一遍。为什么 append 处理不了迟到数据？改成 merge 就万事大吉了吗？

**答**：
- **结论**：`append` 只做插入，不做更新/删除：迟到数据写进"跑批当天"的分区，历史分区不会回填；重复跑同一天会重复插入（除非上游按分区幂等覆盖）。`merge`（或 `delete+insert`）按 `unique_key` 做 upsert，能修正历史记录，但要求：① 增量条件能覆盖到迟到数据（只看 `ds` 会漏掉旧分区）；② `unique_key` 真正唯一；③ 源端能提供"变更/更新时间"或全量快照，否则无法知道哪些旧行变了。
- **取舍**：`append` 最便宜，适合只追加、不回改的事件流；`merge` 正确性更好但每次要扫描/匹配目标表，成本高，且在大数据量下容易产生小文件；`delete+insert` 按分区替换，适合"整分区重算"，但要求分区边界清晰。迟到数据的根本解法是**按事件时间分区 + 可重放的源**，而不是在物化策略上打补丁。
- **实战**：① 增量条件用"事件时间 +  ingestion 时间"双水位，别只用一个；② 明确 `unique_key` 并做唯一性测试；③ 对迟到数据设 SLA（允许多晚），超窗走全量回刷；④ 每次跑批记录影响分区与行数，重复跑要幂等。

```python
def incremental_append(rows: list[dict], target: list[dict]) -> int:
    target.extend(rows)                 # 物理追加：不更新、不去重
    return len(rows)


def incremental_merge(rows: list[dict], target: dict[int, dict]) -> int:
    changed = 0
    for row in rows:
        old = target.get(row["id"])
        if old != row:
            target[row["id"]] = row     # 按 unique_key upsert
            changed += 1
    return changed


if __name__ == "__main__":
    target_append: list[dict] = []
    day1 = [{"id": 1, "amount": 100, "dt": "2026-11-20"}]
    late = [{"id": 1, "amount": 150, "dt": "2026-11-20"}]
    incremental_append(day1, target_append)
    incremental_append(late, target_append)
    incremental_append(late, target_append)      # 重跑再来一遍
    print("append 目标行数:", len(target_append), "-> 重复与旧值并存")

    target_merge: dict[int, dict] = {}
    incremental_merge(day1, target_merge)
    print("merge 修正迟到:", incremental_merge(late, target_merge),
          target_merge)
    print("merge 幂等重跑:", incremental_merge(late, target_merge))
```

**追问一**：为什么"每天只看 `where dt = 当天`"的增量条件一定会漏迟到数据？
→ 解析：增量条件假设"数据只会在当天产生"，但渠道补传、时区差异、上游延迟都会让事件时间落在过去。只按跑批日期过滤，旧分区永远不会被重算，迟到数据要么丢失，要么被错误地归到当天分区。

**追问二**：merge 策略在大表上为什么会越跑越慢？
→ 解析：merge 需要按 `unique_key` 与目标表做匹配（join/shuffle），目标表越大成本越高；频繁小批量 merge 还会产生大量小文件，拖慢后续读取。常见优化是按分区做 `delete+insert`、控制批次大小、定期 compaction。
