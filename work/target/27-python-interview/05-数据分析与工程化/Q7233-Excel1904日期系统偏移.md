### Q7233 · Mac 导出的 Excel 日期差 4 年：1904 日期系统

难度：P6 ｜ 标签：Excel、日期序列号、1904、openpyxl

基线：Python 3.12；`datetime.date + timedelta` 手算两种 Excel 纪元，不依赖 openpyxl。

**问**：运营给的一份 xlsx（同事用 Mac 版 Excel 导出）读进来后，所有日期都往后错了 4 年零 1 天：2023-03-15 变成 2027-03-16。用 Windows 同事重导一份就正常。代码只是 `pd.read_excel(...)` 之后 `pd.to_datetime`，没做任何日期运算。差 4 年这种量级，不像是时区问题——Excel 的日期到底是怎么存的？

**答**：
- **结论**：xlsx 里的日期**不是字符串，而是浮点序列号**（整数部分是"从纪元起的天数"，小数部分是当天时刻）。Excel 有两套纪元：**1900 日期系统**（Windows 默认，序列号 1 = 1900-01-01，且为兼容 Lotus 1-2-3 把 1900-02-29 当成存在，多算一天）和 **1904 日期系统**（Mac Excel 旧默认，序列号 0 = 1904-01-01）。同一个序列号在两套系统下正好差 **1462 天**（4 年 + 1 天，含 1904 闰年）。xlsx 的 `workbook.xml` 里有一个 `date1904="1"` 属性，openpyxl 会据它设置 `wb.epoch`；但如果读取链路（导出成 CSV、或某些库的旧版本）丢掉了这个标记，按 1900 解释就会整体偏移。
- **取舍**：① 读 xlsx 用 openpyxl 并检查 `wb.epoch`（`CALENDAR_WINDOWS_1900` / `CALENDAR_MAC_1904`），不要假定 1900；② pandas 的 `read_excel` 对日期列做类型推断，**不暴露 epoch**，需要自己用 openpyxl 打开 workbook 读标记，或在读入后按 1462 天做校正；③ 数据交换优先让对方导出 CSV 并显式指定 `YYYY-MM-DD` 格式，从根上避开序列号；④ 别用"日期看起来在未来"来猜——业务里真有未来日期（合同生效日），要靠标记而不是启发式。
- **实战**：① 入库前做**合理性校验**：订单/日志这类历史数据不允许未来日期，落在 `[2000-01-01, 今天]` 之外就拒绝并打样本；② 单测固定两个样本（序列号 45000 在两套纪元下的值），把换算函数钉死；③ 记录文件来源与 epoch 到元数据，出问题能追溯是哪一批、哪台机器导的；④ 时间部分同样要处理：`0.5` = 12:00，序列号浮点误差会导致 23:59:59.999，落库前 `round` 到秒。

```python
"""Excel 序列号在两套纪元下的换算：差 1462 天。"""
from datetime import date, datetime, timedelta

WINDOWS_EPOCH = date(1899, 12, 30)   # 含 1900-02-29 的历史 bug，故用 12-30
MAC_EPOCH = date(1904, 1, 1)


def from_serial(serial: float, epoch: date) -> datetime:
    """整数部分是天数，小数部分是当天时刻。"""
    days = int(serial)
    seconds = round((serial - days) * 86400)
    return datetime.combine(epoch + timedelta(days=days), datetime.min.time()) \
        + timedelta(seconds=seconds)


def to_serial(dt: datetime, epoch: date) -> float:
    delta = dt - datetime.combine(epoch, datetime.min.time())
    return delta.days + delta.seconds / 86400


if __name__ == "__main__":
    serial = 45000.5
    win = from_serial(serial, WINDOWS_EPOCH)
    mac = from_serial(serial, MAC_EPOCH)
    print(f"序列号 {serial} 在 1900 系统:", win)
    print(f"序列号 {serial} 在 1904 系统:", mac)
    print("相差天数:", (mac - win).days, "-> 1462 天 = 4 年 + 1 天")

    # 反向：同一个日期在两套系统里的序列号也不同
    d = datetime(2023, 3, 15, 12, 0)
    print("\n2023-03-15 12:00 的序列号:",
          round(to_serial(d, WINDOWS_EPOCH), 2),
          "/", round(to_serial(d, MAC_EPOCH), 2))

    # 读取时按标记选择纪元
    def convert(serial: float, date1904: bool) -> datetime:
        return from_serial(serial, MAC_EPOCH if date1904 else WINDOWS_EPOCH)

    print("\n同一文件标记 date1904=True  ->", convert(45000.5, True))
    print("同一文件标记 date1904=False ->", convert(45000.5, False))

    # 合理性校验：偏移 4 年的数据会直接越界
    today = datetime(2026, 11, 24)
    def check(dt: datetime) -> str:
        if not (2000 <= dt.year <= today.year):
            return f"可疑年份 {dt.year}（订单表不允许未来日期）"
        return "ok"

    print("\n校验:", check(win), "/", check(mac))
    print("结论：日期错 4 年先查 date1904；不要用时区解释 1462 天")
```

**追问一**：1900 系统里"1900-02-29"这个不存在的日期是怎么来的？

→ 解析：Lotus 1-2-3 为了简化闰年判断，错误地把 1900 年当成闰年（能被 4 整除），于是序列号 60 对应 1900-02-29。Excel 为兼容它保留了这个 bug：1900 系统里序列号 60 是"假日期"，61 之后才与真实日历对齐。这就是为什么换算基准要用 **1899-12-30** 而不是 1899-12-31——相当于提前一天，把多出来的那个假日子抵消掉。1904 系统没有这个历史包袱，直接从 1904-01-01 = 0 开始。

**追问二**：为什么 CSV 导出能"治好"这个问题，但不是万能药？

→ 解析：CSV 里日期通常已经格式化成字符串（`2023-03-15`），序列号与纪元都不复存在，自然没有偏移。但 CSV 会丢三样东西：**时区/时刻精度**（可能只到日）、**类型信息**（读回来全是 str，需要自己 parse）、**格式歧义**（`03/04/2023` 是 3 月 4 日还是 4 月 3 日）。所以导出 CSV 时要求固定 `YYYY-MM-DD HH:MM:SS` + 明确时区，才是真正可交换的格式；靠"让对方用 Windows 导"只是把问题藏起来。
