### Q7124 · 开发 macOS 与生产 Linux 环境差异导致配置/数据丢失事故复盘

难度：P6 ｜ 标签：事故复盘 / 环境一致性 / 跨平台

**问**：脚本在 macOS 开发机上跑得好好的，上到 Linux 容器后：配置读不到（文件名大小写）、写文件挂载点路径不存在、临时文件互相覆盖。为什么"本地能跑"不等于"生产能跑"？跨平台差异清单应该包含哪些项、怎么工程化验证？

**答**：
- **结论**：根因是**文件系统与运行时语义的平台差异**被本地开发掩盖：① 文件名大小写——macOS 默认 APFS 大小写不敏感（`Config.JSON` 与 `config.json` 同文件），Linux ext4 敏感，读配置直接 FileNotFoundError；② 路径分隔符与绝对路径——Windows 风格路径混进配置、或写死 `/Users/xxx`；③ 临时目录并发——`/tmp` 下固定文件名在多实例容器里共享，互相覆盖（Q7091 同名临时文件同源）；④ 环境变量大小写——Linux 进程环境区分大小写，`DATABASE_URL` 与 `database_url` 是两个变量，本地 shell 里 alias 掩盖了；⑤ 时区与 locale——容器默认 UTC，`date` 相关逻辑口径漂移。工程化验证不能靠"记得"，要靠两层：开发期用容器跑测试（Q7030 真依赖容器化），CI 里至少一个 Linux 矩阵必选；运行期启动时做环境自检（路径存在性/大小写探测/env 完整性），fail-fast 报清单而不是跑到一半挂。
- **取舍**：自检做得太严会把合法的多环境差异也拦下（dev 有但 prod 没有的可选项）。分层：**必须项**（缺失即拒启：数据库 URL、关键路径可写性）与**警告项**（仅提示）。另一个取舍：大小写问题的根治是团队规约"文件名一律小写+下划线"，加 pre-commit 钩子检查——比在每个 os.path 调用处防御便宜。
- **实战**：① 启动自检函数列 checklist：关键 env、挂载点 `os.access(path, W_OK)`、大小写探测（目录里 `os.listdir` 对照）；② 开发机也用容器/或至少在 CI 强制 Linux runner 跑全量测试；③ 临时文件用 `tempfile.NamedTemporaryFile`+pid 后缀（Q7091）；④ 本地开发脚本里出现的绝对路径进 code review 黑名单（grep `/Users/|C:\`）。

```python
# 启动自检: 大小写/env/可写路径 fail-fast; macOS 不敏感掩盖 Linux 敏感
# 基线: Python 3.9+ 标准库
import os
from dataclasses import dataclass, field


@dataclass
class EnvCheck:
    required_env: list[str]
    required_dirs: list[str]
    env: dict = field(default_factory=dict)

    def run(self) -> list[str]:
        errs = []
        for k in self.required_env:
            if k not in self.env:
                # 抓大小写邻居: DATABASE_URL vs database_url
                near = [e for e in self.env if e.lower() == k.lower()]
                hint = f" (发现近邻 {near}, 疑似大小写错)" if near else ""
                errs.append(f"缺少环境变量 {k}{hint}")
        for d in self.required_dirs:
            if not os.path.isdir(d):
                errs.append(f"目录不存在: {d}")
            elif not os.access(d, os.W_OK):
                errs.append(f"目录不可写: {d}")
        return errs


def coexisting_case_names(names: list[str]) -> bool:
    """目录里是否存在仅大小写不同的同名文件:
    Linux(ext4) 可共存(敏感), macOS(APFS 默认) 后者覆盖前者(不敏感)。"""
    lower = [n.lower() for n in names]
    return len(set(lower)) < len(lower)


def main() -> None:
    prod_env = {"database_url": "pg://..."}        # 运维配了小写
    chk = EnvCheck(["DATABASE_URL"], ["/data/out"], env=prod_env)
    errs = chk.run()
    assert any("疑似大小写" in e for e in errs)     # fail-fast 报近邻
    assert coexisting_case_names(["Config.JSON", "config.json"])  # ext4 共存
    assert not coexisting_case_names(["config.json"])
    print(f"{len(errs)} 个致命项, 启动拒绝而非半途崩溃")
    print("OK: 自检清单化 + 容器化开发/CI Linux 矩阵是验证层, 不靠记得")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"配置文件名大小写"这类问题在测试环境常常漏掉？
→ 一句话提示：测试环境与开发环境往往同为 macOS 或共享代码打包（whl/镜像内路径规范化），只有生产容器挂载/解包才暴露；所以 Linux 验证必须进 CI 矩阵而不是依赖某个环境"恰好是 Linux"。

**追问 2**：环境自检发现的"近邻提示"（database_url vs DATABASE_URL）为什么比直接报错更能缩短排障时间？
→ 一句话提示：报错只说"缺什么"，近邻提示说"它在附近但名字不对"——运维一看就知道是配置下发口径错了，把一次跨团队定位变成一次改名，这是 fail-fast 信息设计的价值。

## 背诵要点
- 跨平台差异五项：文件名大小写（APFS 不敏感 vs ext4 敏感）、绝对路径写死、/tmp 并发、env 大小写、时区/locale。
- 验证两层：CI 强制 Linux 矩阵/容器化开发（结构层）+ 启动自检 fail-fast（运行层），自检分必须项/警告项。
- 根治靠规约+钩子（文件名小写、绝对路径进 review 黑名单），不在调用点逐个防御。

## 复盘追问
- 为什么本地开发机"永远验证不到生产"？提示：本地验证的是 macOS+开发者权限组合，生产是 Linux+受限权限+挂载拓扑，交集之外全是盲区——容器化开发的意义就是把生产形态搬到本地。
- 启动自检和"跑到一半才挂"的成本差在哪？提示：自检在启动期一次给出全部致命项清单（分钟级修复），半途崩溃则每次只暴露一个（N 次重部署），且可能在半途产生脏数据。
