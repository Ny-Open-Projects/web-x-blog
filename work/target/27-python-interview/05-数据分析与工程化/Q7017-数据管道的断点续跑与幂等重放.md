### Q7017 · 数据管道断点续跑

> 难度:★★★ | 标签:ETL, 断点续跑, 幂等

**问**：ETL 管道跑 6 小时挂在第 4 小时——重跑要从头来吗？「水位」怎么设计（时间水位/主键水位/offset 水位各自的适用场景），下游写怎么做到「重放 N 次结果一样」（幂等写入的 upsert 口径），管道反压（下游慢拖垮上游）怎么解？

**答**：① **水位三型**：时间水位（按 created，适合 append-only 源）、主键水位（按自增 id > last，高吞吐且无时钟问题）、offset 水位（消息队列位点，Kafka 专属）——水位必须**持久化在管道外**（DB/编排系统），且只有**下游确认后**才推进（先写后推水位 = 崩溃时丢数据，先推后写 = 重复读但幂等写能兜，后者安全）。② 幂等写入：目标表唯一键 + upsert（`ON CONFLICT DO UPDATE`，Q6517 口径）；或分区覆盖写（按日期分区整体 replace，天然幂等）——重放 N 次结果一致。③ 反压：下游写慢 → 上游内存堆积 → OOM；解法：**有界队列 + 生产者阻塞**（天然反压）、分批拉取（cursor 分页，Q6515）、下游熔断降批（写不进就睡），绝不用无界队列硬扛。

```python
# 全部标准库 + sqlite（模拟源与目标）；缺库降级看口径注释
import sqlite3, time, json

def setup(src: sqlite3.Connection, dst: sqlite3.Connection):
    src.execute("CREATE TABLE src(id INTEGER PRIMARY KEY, v TEXT)")
    src.executemany("INSERT INTO src VALUES(?,?)", [(i, f"d{i}") for i in range(10000)])
    src.commit()
    dst.execute("""CREATE TABLE dst(id INTEGER PRIMARY KEY, v TEXT,
                    updated_at REAL, run_id TEXT)""")
    dst.commit()

class Pipeline:
    def __init__(self, src, dst, state_path: str = "pipeline_state.json", batch=1000):
        self.src, self.dst, self.state_path, self.batch = src, dst, state_path, batch
        self.state = self._load()             # 水位持久化在管道外
    def _load(self):
        try:
            return json.load(open(self.state_path))
        except FileNotFoundError:
            return {"watermark": -1}
    def _save(self):
        json.dump(self.state, open(self.state_path, "w"))

    def run(self):
        moved = 0
        while True:
            rows = self.src.execute(
                "SELECT id, v FROM src WHERE id > ? ORDER BY id LIMIT ?",
                (self.state["watermark"], self.batch)).fetchall()   # 主键水位 + 游标分页
            if not rows:
                break
            # 幂等写入：INSERT OR REPLACE（= upsert）；重放 N 次结果一致
            self.dst.executemany(
                "INSERT OR REPLACE INTO dst(id, v, updated_at, run_id) VALUES(?,?,?,?)",
                [(i, v, time.time(), "run-1") for i, v in rows])
            self.dst.commit()                 # 先确认写成功
            self.state["watermark"] = rows[-1][0]
            self._save()                      # 再推水位（安全顺序）
            moved += len(rows)
        return moved

def backpressure_demo():
    """反压口径：有界队列让生产者自动等待，不 OOM 不丢数据。"""
    import queue
    q: "queue.Queue" = queue.Queue(maxsize=10)   # 有界 = 反压
    def producer():
        for i in range(50):
            q.put(i)                          # 满时阻塞（天然反压）
    def slow_consumer():
        import time as _t
        while True:
            _t.sleep(0.001)
            q.get()
    import threading
    threading.Thread(target=slow_consumer, daemon=True).start()
    threading.Thread(target=producer).start()
    return "有界队列：下游慢 → 生产者阻塞 → 内存有界"

if __name__ == "__main__":
    src = sqlite3.connect(":memory:"); dst = sqlite3.connect(":memory:")
    setup(src, dst)
    p = Pipeline(src, dst)
    n1 = p.run()                               # 第一次跑完
    n2 = Pipeline(src, dst).run()              # 模拟重跑：水位后无新数据
    assert n1 == 10000 and n2 == 0
    print(f"断点续跑 OK：首轮 {n1} 行，重跑水位增量 {n2} 行")
    dst.execute("DELETE FROM dst WHERE id > 5000").fetchall(); dst.commit()
    n3 = Pipeline(src, dst).run()              # 模拟第 4 小时挂了：水位回退重放
    assert n3 == 4999
    print(f"水位回退重放 {n3} 行 → 幂等 upsert，结果与一次跑完一致 ✅")
    print(backpressure_demo())
```

**追问**：1) 为什么「先推水位后写」不行？——崩溃窗口在写之前：水位已推进但数据没落 → 永久丢数据；「先写后推」最坏是重复读，幂等写兜住——**重复优于丢失**是管道设计第一原则（与 A104 租约同构）。2) 时间水位 vs 主键水位怎么选？——主键水位零时钟问题但要求源单调自增；时间水位处理「迟到数据」（事件时间早于水位）需要出界策略（水位延迟 + 允许重扫窗口，Flink watermark 语义）。3) 编排系统（Airflow/Prefect）和自写水位什么关系？——编排器自带重试与任务状态，但数据水位仍要自己管（编排管「任务跑没跑」，水位管「数据走到哪」）；任务失败重试依赖你的水位设计才正确。

## 背诵要点
1. 水位三型（时间/主键/offset），持久化在管道外，**先写后推水位**——重复优于丢失。
2. 幂等写入 = upsert 或分区覆盖写，重放 N 次结果一致；重跑从水位增量推进。
3. 反压 = 有界队列让生产者阻塞，禁无界队列硬扛。

## 复盘追问
1. 源表数据被上游修正（历史 UPDATE），主键水位管道怎么同步？（提示：CDC（binlog 订阅）替代水位扫描，或定期重扫校验对账——水位只适合 append-only 的局限）
2. 管道 6 小时任务在 Airflow 里怎么拆才合理？（提示：按分片拆子任务（时间/主键区间）并行 + 各自水位，单任务粒度小到重试代价可接受）
