### Q7043 · 事故复盘：同一个 requirements.txt，为什么测试环境和生产装出不同版本？

> 难度:★★★ | 标签:事故复盘, 依赖锁定, 可复现性

**问**：requirements.txt 里只写了 `pandas` 和 `numpy`（没写版本），测试环境一直正常，新部署的生产节点上报表数值错乱。根因是什么？"只锁直接依赖"为什么不够？从 requirements.txt 到 lock 文件再到离线 wheelhouse，标准锁链怎么搭？

**答**：结论：根因是 **requirements.txt 是"意图"不是"事实"**——没写版本时安装结果取决于安装时刻的 PyPI 最新版本与当时的解析环境，测试环境装于三个月前、生产装于今天，pandas/numpy 及其传递依赖各不相同，数值行为（默认 dtype、精度、API 弃用）随之漂移。"只锁直接依赖"不够是因为**传递依赖同样在漂移**：锁了 pandas==2.2 却没锁它依赖的 numpy/pytz 版本闭包，复现性仍是伪的。

机理与实战：
- **三层锁链标准姿势**：① `pyproject.toml` 声明意图（语义版本范围）；② lock 文件（`uv lock`/`pip-compile` 生成）记录**完整传递依赖闭包**+哈希，是唯一事实源；③ wheelhouse/离线源锁定制品（CI 构建时 `pip download -d wheelhouse` 或 uv 缓存），生产机不接触 PyPI 实时状态。部署命令永远是 `uv sync --frozen` / `pip install -r requirements.lock --no-deps`。
- **数值库漂移的危害**：numpy 2.x 与 1.x 二进制不兼容（ABI 断裂）、pandas 2.x 默认 dtype 推断变化——同一份代码在两个版本上产出不同结果且不报错，这类"静默数值漂移"比报错更危险。所以数据管道的 lock 还要配合 Q7033 的 dtype 门禁与回归金样本。
- **事故复盘要点**：为什么没 lock？因为"直接依赖少写版本省事"；为什么测试没发现？因为测试环境从未重建过环境（漂移从未发生），新节点首次重建才引爆——**复现性没有被持续验证就等于没有**。治理：CI 里加"全新环境 from-lock 重建 + 金样本回归"步骤。
- **哈希校验**：lock 带 `--require-hashes` 可防供应链篡改，同时强制完全锁定（装任何未锁包直接失败）。

```python
# 基线:Python 3.10+;纯标准库,锁定闭包 diff 工具:比较两份环境快照找漂移
from __future__ import annotations
import re
from pathlib import Path


def parse_lock(text: str) -> dict[str, str]:
    """解析 requirements.lock / uv.lock 摘要出 name==version 闭包。"""
    out: dict[str, str] = {}
    for line in text.splitlines():
        m = re.match(r"^([A-Za-z0-9_.-]+)==([0-9][^ ;]*)", line.strip())
        if m:
            out[m.group(1).lower().replace("_", "-")] = m.group(2)
    return out


def diff_locks(old: dict[str, str], new: dict[str, str]) -> dict[str, tuple[str, str]]:
    """找出漂移的传递依赖:这是数值错乱的嫌疑名单。"""
    return {k: (old.get(k, "-absent-"), new.get(k, "-absent-"))
            for k in set(old) | set(new) if old.get(k) != new.get(k)}


def guard_direct_only(req_txt: str, lock: dict[str, str]) -> list[str]:
    """门禁:requirements 只写意图,lock 必须覆盖全部传递依赖。"""
    direct = [l.split("==")[0].lower().replace("_", "-")
              for l in req_txt.splitlines() if "==" in l]
    missing = [d for d in direct if d not in lock]
    advice: list[str] = []
    if missing:
        advice.append(f"lock 未覆盖直接依赖: {missing}")
    # 检测"意图文件裸版本"反模式:pandas 无版本约束
    bare = [l.strip() for l in req_txt.splitlines()
            if l.strip() and "==" not in l and not l.startswith(("#", "-"))]
    if bare:
        advice.append(f"意图未锁版本(反模式): {bare}")
    return advice


def demo(tmp: Path) -> None:
    old = (tmp / "old.lock")
    old.write_text("numpy==1.26.4\npandas==2.1.4\npytz==2023.3\n", encoding="utf-8")
    new = (tmp / "new.lock")
    new.write_text("numpy==2.0.1\npandas==2.1.4\npytz==2023.3\n", encoding="utf-8")
    drift = diff_locks(parse_lock(old.read_text()), parse_lock(new.read_text()))
    print(f"传递依赖漂移: {drift}")
    assert drift == {"numpy": ("1.26.4", "2.0.1")}  # numpy ABI 断裂点
    req = "pandas\nnumpy==1.26.4"
    adv = guard_direct_only(req, parse_lock(old.read_text()))
    assert any("pandas" in a for a in adv)      # 裸意图告警
    assert not any("未覆盖" in a for a in adv)  # lock 已覆盖直接依赖
    print(f"门禁输出: {adv}")
    print("锁链标准:意图(pyproject)->lock 闭包->wheelhouse 制品,部署一律 --frozen ✅")


if __name__ == "__main__":
    import tempfile
    with tempfile.TemporaryDirectory() as td:
        demo(Path(td))
```

**追问一**：`pip freeze > requirements.txt` 为什么常被称为"伪锁定"？
答：freeze 记录的是某台机器当前环境的快照，包含平台相关包、`-e` 本地安装、版本混乱的临时状态，且不含哈希、无法跨平台复现；真正的 lock 是求解器在声明意图下推导的规范化闭包（uv.lock 还带跨平台 universal 解）。freeze 可以做应急取证，不能做日常锁定。

**追问二**：monorepo 多个子项目共享部分依赖时，锁定策略怎么设计？
答：两种流派：每项目独立 lock（隔离强、磁盘大、公共依赖版本可能分叉）vs 工作区级统一 lock（uv workspace 模式，一个闭包服务全仓，版本强一致）。数据类仓库通常选统一 lock + 按项目入口校验，代价是任何一个项目升级都要全仓回归——所以统一 lock 必须配合金样本回归才有工程意义。

## 背诵要点
- requirements.txt 是意图不是事实：不锁版本=安装时刻决定版本；只锁直接依赖不够，传递依赖闭包才是复现性的事实源。
- 三层锁链：pyproject 意图 → uv lock/pip-compile 完整闭包+哈希 → wheelhouse 离线制品；部署一律 `uv sync --frozen`。
- 数值库漂移（numpy 1→2 ABI 断裂、pandas dtype 推断变化）是静默错乱高危源；复现性必须被 CI 持续验证（全新环境重建+金样本回归）。

## 复盘追问
- 为什么事故发生前"环境漂移检查"显示一切正常？（提示：检查可能在既有环境上比对，而事故发生在"新节点首次重建"；漂移检测必须模拟全新环境，或直接强制 from-lock 重建）
- 团队以"lock 太难合"为由不提交 lock 文件，怎么论证必须提交？（提示：lock 冲突用工具自动合并（uv lock 重新求解）解决，人只解决意图冲突；不提交 lock 相当于把求解结果交给"部署时刻的运气"，事故成本远高于合并成本）
