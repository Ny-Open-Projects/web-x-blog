### Q7271 · 两套日报对不上：数据管道的日切窗口与跨时区边界

难度：P6 ｜ 标签：日切、时区、日切窗口、对账口径、数据管道

基线：Python 3.12；用 timezone-aware datetime 演示 UTC 分桶与业务时区分桶在日切边界的漂移，全标准库实跑。

**问**：同一天的交易数据，数据管道算出的日报和业务系统算出的日报差了几十单——订单在"北京时间 11-24 00:30"完成，管道归入 11-23，业务归入 11-24。日切（day cut）的口径是怎么形成的？存储、分桶、调度三个层面的时区规则各是什么？跨时区运营的系统怎么定口径？

**答**：
- **结论**：日切差异的根源是**三个层面各自默认了不同时区**：① 存储层：事件时间戳必须统一存 UTC（带偏移的 aware datetime），这是唯一不随部署位置漂移的锚；② 分桶层：`DATE(timestamp)` 按什么时区取整决定了"一天"的边界——UTC 分桶在 UTC+8 业务眼里，每天的 00:00-08:00 属于"昨天"；③ 调度层：批处理作业"每天 2 点跑前一天"的 2 点是哪个时区的 2 点、跑的是哪个口径的前一天。两边报表各按自己的默认时区分桶，数字自然对不上。修复不是"改代码对齐某一侧"，而是**显式定义口径**：存储 UTC → 分桶函数带显式时区参数（本卡 bucket_biz vs bucket_utc）→ 调度窗口与分桶口径绑定并写进指标字典（Q7255 口径治理）→ 对账任务按口径映射核对。
- **取舍**：① 全链路 UTC 简单但业务报表反直觉（"我的半夜订单跑到前一天"），中国业务通常要 UTC+8 业务日；跨时区运营（美欧都有用户）则可能要按用户所在地分桶——多口径并存时**每张报表必须标注口径**，指标字典是唯一事实源；② DST（夏令时）地区（美/欧）的"一天"在切换日不是 24 小时：固定 24 小时窗口会少/多算一小时，分桶必须按"本地日历日"而非"间隔 24h"；③ 窗口重叠与迟到数据（上游延迟到达的边界事件）：日切作业跑完后迟到事件落入哪天要事先定义（重算昨日 or 归入今日+打标记，Q2262 乱序修正的姊妹题）。
- **实战**：① 代码规范：禁止 `datetime.now()` 裸调用（naive 时间），统一 `now_utc()` 帮助函数；`DATE()`/`strftime("%Y-%m-%d")` 的调用点全部带时区参数 review；② 日切作业的自检：跑完打印"窗口 [start, end) 与桶标签"确认口径；③ 对账任务：管道日报 vs 业务库按业务口径重算，差异明细按"事件时间+两边归属"打印——漂移会精确暴露在边界小时；④ 夏令时切换日单独出回归用例（11 月第一个周日 01:00-02:00 重复时段）。

```python
"""Q7271 数据管道日切窗口: UTC 存储与业务时区分桶, 边界记录的归属账。"""
import datetime as dt

TZ = dt.timezone(dt.timedelta(hours=8))     # 业务时区 UTC+8


def bucket_utc(ts: dt.datetime) -> str:
    """UTC 分桶 (数据管道默认)."""
    return ts.astimezone(dt.timezone.utc).strftime("%Y-%m-%d")


def bucket_biz(ts: dt.datetime) -> str:
    """业务时区分桶 (报表口径)."""
    return ts.astimezone(TZ).strftime("%Y-%m-%d")


# e1/e2 在北京 11-23 晚; e3 在北京 11-24 00:30 = UTC 11-23 16:30
EVENTS = [
    ("e1", dt.datetime(2026, 11, 23, 19, 0, tzinfo=TZ)),
    ("e2", dt.datetime(2026, 11, 23, 23, 50, tzinfo=TZ)),
    ("e3", dt.datetime(2026, 11, 24, 0, 30, tzinfo=TZ)),
]


def daily_count(bucket_fn) -> dict[str, int]:
    out: dict[str, int] = {}
    for _, ts in EVENTS:
        d = bucket_fn(ts)
        out[d] = out.get(d, 0) + 1
    return dict(sorted(out.items()))


if __name__ == "__main__":
    print("事件: e1/e2 在北京 11-23 晚, e3 在北京 11-24 凌晨 00:30")
    utc_b = daily_count(bucket_utc)
    biz_b = daily_count(bucket_biz)
    print(f"UTC  桶: {utc_b}")
    print(f"业务桶: {biz_b}")
    diff = (biz_b.get("2026-11-24", 0) - utc_b.get("2026-11-24", 0))
    print(f"差异: e3 被 UTC 口径归入 11-23, 业务口径归入 11-24 -> 11-24 两口径差 {diff} 单")
    # 规范: 存储层永远 UTC, 桶层用业务时区且偏移显式声明
    stored = EVENTS[2][1].astimezone(dt.timezone.utc).isoformat()
    print(f"e3 落库规范: {stored} (UTC 带偏移)")
    ok = (utc_b.get("2026-11-24", 0) == 0 and biz_b.get("2026-11-24", 0) == 1
          and utc_b.get("2026-11-23") == 3)
    print(f"校验: 双口径边界漂移复现 -> {'通过' if ok else '异常'}")
    print("结论：存储 UTC、分桶业务时区、偏移显式声明, 三条缺一不可;")
    print("      日切对账先定口径归属(业务日 or 自然日 UTC), 再谈数字对不上")
```

**追问一**：为什么"存储层永远 UTC"不能通融？存"北京时间字符串"省掉一次转换不行吗？

→ 解析：存本地时间字符串会在三个地方慢性失血：① **不可逆歧义**：`"2026-11-01 01:30"` 在有 DST 的时区对应两个 UTC 时刻（回拨日的一小时出现两次），存了本地时间就永远分不清；中国虽无 DST，但历史数据/海外扩展随时引入；② **转换成本前置了但没消失**：每个读取方都要自己猜时区——猜错就是新一轮对账灾难，而猜的动作散落在无数下游脚本里无法审计；③ **调度漂移**：服务器 TZ 环境变量变化（容器迁移、CI 与生产不同 TZ，Q7260 环境泄漏）让"本地时间"就地漂移。UTC + 显式转换把"猜"压缩到分桶层一处，转换函数可测可审。唯一合理例外：纯展示层缓存（已按业务时区渲染的字符串），但它不是数据，不参与再计算。

**追问二**：日切作业在边界时刻跑，"未完成窗口"的问题怎么处理？幂等重跑怎么设计？

→ 解析：日切作业 02:00 跑"昨天的数据"，但昨天 23:59 完成的支付可能 00:01 才从支付网关回调到达——**窗口内的事件在窗口结束后仍会迟到**。处理方案分两层：① **水位与重算窗口**：每日作业实际覆盖 `[D-1, D)` 的主窗口 + 近 N 小时的迟到补偿窗口（数据按事件时间落桶，迟到事件落 D-1 桶并触发 D-1 重算），重算幂等靠分区级覆盖写（当日分区整块重建而非增量 append，Q7248 回填与增量互斥租约防并发重算）；② **口径声明**：报表明确"D 日数据 T+1 02:30 定稿，之后迟到数据计入补偿报表"——让业务知道数字什么时候可信，比追求"永远准"更工程化。幂等设计三件套：分区覆盖写（重跑不改结果）、调度去重锁（同一窗口只跑一次，Q7248）、迟到事件的路由规则显式配置。日切的本质是**把连续流切成离散账本**，切法（口径）与缝合（迟到处理）都要写成契约，不能靠"跑一次看起来对"。
