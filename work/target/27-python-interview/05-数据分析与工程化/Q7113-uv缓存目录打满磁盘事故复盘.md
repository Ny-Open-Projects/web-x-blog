### Q7113 · uv/pip 缓存目录打满构建机磁盘事故复盘

难度：P6 ｜ 标签：事故复盘 / 包管理缓存 / CI 磁盘

**问**：CI 构建机连续出现 `No space left on device`，排查发现 `~/.cache/uv`（及老的 `~/.cache/pip`）占了 400GB。缓存为什么"只进不出"？这次事故的完整链路与治理方案是什么？和"坏缓存"（Q7073）是两类不同的问题，怎么分别设防？

**答**：
- **结论**：链路：① 缓存**只写不清**——uv/pip 的 wheel 缓存按包版本持续累积，无自动淘汰；② CI 场景放大——每条流水线装不同版本组合（矩阵测试、多分支），缓存键爆炸，一个 monorepo 日常每天可产生数 GB 新 wheel；③ 长期无人维护的 Runner 磁盘 500GB 被吃满，磁盘满后不只是构建失败——uv 回退到临时目录全量下载、并发任务互相踩、甚至影响同机其他服务。两类问题要分开：**磁盘满**是容量问题（缓存无界），**坏缓存**是一致性问题（缓存内容与预期不符导致构建不可复现）；治理分别对应"生命周期清理"与"缓存键设计 + 校验"。uv 的缓解点：硬链接/写时复制安装使安装快且省空间（同一个 wheel 多环境共享），但缓存目录本身仍是累积的。
- **取舍**：治理层次：① 定期清理——`uv cache prune`（清未使用条目）/ `uv cache clean`（全清），CI 上每次跑完 `pip cache purge` 或按磁盘水位触发；Runner 加 systemd timer / cron 周清理；② 空间上界——把缓存放独立分区/独立磁盘卷，满了只影响缓存不影响系统；③ 构建临时目录（`TMPDIR`）与缓存同盘时，磁盘满的爆炸面更大，尽量分离；④ 自建 wheelhouse/镜像仓的团队，把"缓存瘦身"转为"内网仓拉取"（带宽便宜、磁盘可控）；⑤ 监控——Runner 磁盘水位 >70% 告警，把"磁盘满导致的构建失败"单独打标签，与代码失败区分。
- **实战**：落地清单：① CI 模板里内建"job 结束清缓存"步骤（可配置保留高频包）；② `uv cache dir` 迁到独立卷并设配额；③ 周任务跑 prune + 报告缓存 Top 占用包，发现"某个包每天产生 20 个版本缓存"之类的异常（多半是分支里 pin 了临时版本）；④ 复盘时把 pip 与 uv 两个时代的缓存目录都查一遍——历史上 pip 缓存常常是更大的元凶。

```python
# 缓存目录容量模型：按水位触发的 prune 策略
# 基线：Python 3.9+ 标准库；真实清理用 uv cache prune / pip cache purge
from dataclasses import dataclass


@dataclass
class CacheVol:
    used_gb: float
    quota_gb: float
    daily_growth_gb: float


def weekly_growth(c: CacheVol) -> float:
    return c.daily_growth_gb * 7


def prune_decision(c: CacheVol, warn: float = 0.7, critical: float = 0.85) -> str:
    ratio = c.used_gb / c.quota_gb
    if ratio >= critical:
        return "full_clean"      # 全清，构建速度让位于可用性
    if ratio >= warn:
        return "prune_unused"    # 只清未使用条目，保留热缓存
    return "noop"


def days_to_critical(c: CacheVol, after_prune_gb: float | None = None) -> int:
    used = c.used_gb if after_prune_gb is None else after_prune_gb
    remain = c.quota_gb * 0.85 - used
    return max(0, int(remain / c.daily_growth_gb))


def main() -> None:
    c = CacheVol(used_gb=430, quota_gb=500, daily_growth_gb=3)
    assert prune_decision(c) == "full_clean"          # 86% 已到 critical
    assert weekly_growth(c) == 21

    # prune 未使用条目后回落到 74%：可估出下次 critical 到来的天数
    after = 370.0
    assert prune_decision(CacheVol(after, c.quota_gb, c.daily_growth_gb)) == "prune_unused"
    d = days_to_critical(c, after_prune_gb=after)
    assert d == int((500*0.85 - 370) / 3) == 18
    print(f"prune 后到 85% 水位约 {d} 天 -> 清理周期必须短于三周")

    # 教训：清理周期按"天数到 critical"倒推，而不是拍脑袋一月一次
    assert days_to_critical(c) == 0    # 当前已越线
    print("OK: 磁盘满=容量问题(prune/配额/独立卷)，坏缓存=一致性问题(缓存键+校验)，分开设防")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"每月全清一次"不如"按水位 prune"？
→ 一句话提示：全清一次浪费所有热缓存（接下来几天构建全量回源），prune 只删未引用条目保留热数据；水位触发还天然适应增长速率变化，固定周期在高增长周会失守。

**追问 2**：uv 的硬链接安装对这道账有什么影响？
→ 一句话提示：同一缓存 wheel 硬链接进各虚拟环境，安装目录几乎不占额外空间（同盘），磁盘压力集中在缓存目录本身；但跨磁盘卷会退化为复制，容量规划时要确认构建目录与缓存同卷还是分卷。

## 背诵要点
- 磁盘满与坏缓存是两类问题：容量治理靠水位触发 prune（`uv cache prune` 保留热缓存）+ 独立卷配额；一致性治理靠缓存键设计与校验（Q7073）。
- 清理周期用"天数到 85% 水位"倒推：示例 3GB/日增速、prune 到 370GB 后约 18 天到 critical——月清必失守，双周起步。
- Runner 磁盘 70% 告警 + 构建失败按"磁盘满/代码失败"分标签统计，历史 pip 缓存目录要一并排查。

## 复盘追问
- 为什么事故持续数周才被发现？提示：构建失败归因到代码/依赖噪音里，"No space left" 偶发且各 job 表现不同；可观测性缺口是磁盘水位没有进监控——容量类故障的第一定律。
- 缓存目录独立卷后"满"的爆炸面怎么变？提示：只影响缓存命中的收益消失（构建变慢），系统盘与 TMPDIR 不受影响——用可控的性能退化替代不可控的故障。
