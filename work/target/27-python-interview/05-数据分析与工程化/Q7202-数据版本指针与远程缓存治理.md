### Q7202 · 数据版本指针与远程缓存治理

难度：P6 ｜ 标签：版本迁移、数据版本、DVC、可复现性

基线：Python 3.12；DVC / lakeFS 为概念对照；hashlib 标准库演示内容寻址。

**问**：三个月前的一次模型实验，代码有 git commit，但训练数据和权重找不到对应版本，复现不出来。git 明明能管版本，为什么管不了数据？DVC 和 lakeFS 分别怎么解决？

**答**：
- **结论**：git 适合管文本 diff，但把 GB 级数据塞进 git 会撑爆仓库、克隆极慢。DVC 的做法是：git 里只存一个 `.dvc` **指针文件**（记录内容哈希、大小、远程位置），数据本体放远程缓存（S3/OSS），`dvc push/pull` 按内容寻址同步——代码 commit 与数据指针 commit 对齐即可复现。lakeFS 则在对象存储之上提供 git 风格的分支/提交语义：commit 是瞬时快照（写时复制），分支间数据隔离，适合数据湖规模。
- **取舍**：DVC 轻量、与 git 天然配合，但分支在 git 侧、数据在远程，需要 `dvc` 命令串起来；lakeFS 提供数据层的原子提交与分支，能力更强但多一个服务要运维。两者都依赖"内容哈希"识别重复、避免冗余存储。
- **实战**：实验元数据把 `git commit + 数据指针 hash + 代码版本` 绑定记录；CI 复现实验时先 `dvc pull` 再训练；远程缓存要配置生命周期和去重，避免无限膨胀（这是数据版本维度的容量账）。

```python
import hashlib


def make_pointer(path: str, data: bytes) -> dict[str, str | int]:
    """模拟 .dvc 指针：内容哈希 + 大小，git 只跟踪这个。"""
    return {
        "path": path,
        "md5": hashlib.md5(data).hexdigest(),
        "size": len(data),
    }


if __name__ == "__main__":
    data = b"feature,label\n1,0\n2,1\n"
    p1 = make_pointer("data/train.csv", data)
    p2 = make_pointer("data/train.csv", data)
    print("相同内容 -> 相同哈希:", p1["md5"] == p2["md5"], p1["md5"])
    changed = make_pointer("data/train.csv", data + b"3,1\n")
    print("内容改变 -> 哈希改变:", changed["md5"] != p1["md5"])
```

**追问一**：为什么内容哈希能同时解决版本识别和去重？
→ 解析：相同内容必然得到相同哈希，所以哈希既是版本的唯一标识（内容变则哈希变），又能作为去重 key（相同哈希只存一份），这就是内容寻址存储的核心。

**追问二**：lakeFS 的"瞬时提交/写时复制"相比 DVC 的指针文件优势在哪？
→ 解析：lakeFS 的 commit 是元数据层的快照、不复制实际数据，分支间共享底层对象，因此大规模数据的分支/回滚瞬时完成；DVC 的指针更轻但需要 `dvc pull` 把数据具体同步到工作区。
