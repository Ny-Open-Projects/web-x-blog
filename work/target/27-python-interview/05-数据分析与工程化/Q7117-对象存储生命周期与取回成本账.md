### Q7117 · 对象存储生命周期策略与取回成本账

难度：P6 ｜ 标签：成本工程 / 对象存储 / 数据生命周期

**问**：数仓备份与导出文件堆在对象存储里已经 300TB，月账单只按"标准存储"算。有人建议全转归档层（单价降 80%），有人警告"取回费用会反杀"。生命周期分层的账怎么算？访问模式数据怎么采集才能让策略不拍脑袋？

**答**：
- **结论**：账的分项：① **存储单价**——标准 : 低频 : 归档 : 深度归档 ≈ 1 : 0.8 : 0.4 : 0.15，但低频/归档层有**最短存储时长**（30/90/180 天，提前删除按最短时长计费）与**取回费**（归档层按 GB 取回 + 取回加急档价差数倍）；② **取回账**——关键在访问模式：月读率低于"盈亏平衡点"（取决于取回费与存储差价的比价，示例系数下约 30%，实价下通常个位数百分比）归档才划算；反杀场景是"归档后还要频繁读"——取回费 + 取回后数据还要暂存（临时副本费用）远超省下的存储差价；③ **容量与删除账**——生命周期规则要管"删"不只是"转"：90 天转低频、180 天转归档、365 天删除，缺删除规则就是无限累积；提前删除罚金让"短命对象进归档层"纯亏。分层的正确姿势：**按访问模式分桶**，而不是按"看起来不重要"分。审计手段：对象存储的访问日志/清单（inventory）+ 90 天访问统计，算每个前缀的"月读次数/对象数"，把 <0.5% 的前缀转归档，把 90 天零访问且无合规要求的前缀直接短 TTL 删除。
- **取舍**：策略矩阵：数仓备份（按保留期决定，通常合规要求长保留零访问 → 深归档 + 删旧版本）；业务导出文件（用户会下载 → 标准层 + 30 天转低频）；中间产物（pipeline 可重算 → 短 TTL 直接删，不进低层）。例外处理：归档层的"恢复演练"（Q6563 备份恢复演练同源）会产生集中取回——演练预算单列，用批量取回档（ hours 级）控制单价。云厂商还有"智能分层"自动档：免维护但单价略高于手动最优，300TB 规模下手动分桶通常更省，多前缀访问模式混乱的场景智能分层省心。
- **实战**：落地：① 按前缀/桶拆访问统计（对象清单 + 90 天日志），产出分层建议表；② 生命周期规则版本化在 IaC 里，变更走评审（删规则是数据安全事故高发点，删除规则必须带"最小保留天数 + 双人确认"）；③ 月度账单按"层 × 桶"拆分对比策略预期，偏差 >10% 复查访问模式漂移；④ 取回操作统一走工具函数（记录原因与预算），禁止散装 boto3/oss2 调用直接 get 归档对象。

```python
# 生命周期分层账：按月访问率选层，取回费反杀检测
# 基线：Python 3.9+ 标准库；单价为相对系数，落地读云厂商实价
from dataclasses import dataclass


@dataclass
class Tier:
    name: str
    storage_price: float     # 相对标准层
    retrieve_price: float    # 取回 相对标准层存储价的每GB系数
    min_days: int


STANDARD = Tier("standard", 1.0, 0.0, 0)
ARCHIVE = Tier("archive", 0.4, 2.0, 90)   # 取回每GB价约为标准存储每GB价的2倍


def monthly_cost(tb: float, tier: Tier, monthly_read_ratio: float) -> float:
    storage = tb * tier.storage_price
    retrieve = tb * monthly_read_ratio * tier.retrieve_price
    return storage + retrieve


def best_tier(tb: float, monthly_read_ratio: float) -> str:
    s = monthly_cost(tb, STANDARD, monthly_read_ratio)
    a = monthly_cost(tb, ARCHIVE, monthly_read_ratio)
    return "archive" if a < s else "standard"


def main() -> None:
    tb = 100
    # 冷数据 3% 月读：归档省一半以上
    assert best_tier(tb, 0.03) == "archive"
    assert monthly_cost(tb, ARCHIVE, 0.03) < monthly_cost(tb, STANDARD, 0.03) * 0.5

    # 反杀场景：月读 70%，取回费反超存储差价
    assert best_tier(tb, 0.7) == "standard"
    assert monthly_cost(tb, ARCHIVE, 0.7) > monthly_cost(tb, STANDARD, 0.7)
    print(f"月读70%时归档层月费 {monthly_cost(tb, ARCHIVE, 0.7):.1f} "
          f"> 标准 {monthly_cost(tb, STANDARD, 0.7):.1f} -> 取回反杀")

    # 盈亏平衡月读率: 1 = 0.4 + r*2.0 -> r = 30%
    balance = (STANDARD.storage_price - ARCHIVE.storage_price) / ARCHIVE.retrieve_price
    assert abs(balance - 0.3) < 1e-9
    print(f"盈亏平衡月读率 {balance:.0%}；策略按访问模式分桶而非'看起来不重要'")

    # 删除规则：短命对象进归档层按最短 90 天计费 = 纯亏
    print("OK: 分层+删除双规则；删除规则变更双人确认")


if __name__ == "__main__":
    main()
```

**追问 1**：怎么防"把还在活跃使用的前缀误转归档"？
→ 一句话提示：访问统计取 90 天窗口（覆盖季度性业务），新前缀设 30 天观察期不进自动策略；转层前先做一次"按前缀的最近 7 天访问"快检，且策略上线后用取回费告警兜底（取回费突增=误判信号）。

**追问 2**：删除规则的治理为什么比转层规则更严？
→ 一句话提示：转错层可逆（多花取回费），删错不可逆；删除必须最小保留天数 + 备份层双副本确认 + 变更双人审批，并把"删除总量"做日级监控，异常突增立即暂停规则。

## 背诵要点
- 分层账三件：存储单价（标准:归档≈1:0.4）、取回费（示例系数下约为标准存储每GB的2倍，反杀线 = 盈亏平衡月读率，示例系数下 30%）、最短存储时长（提前删除按最短计费）。
- 分层依据是**访问模式数据**（90 天访问日志+清单按前缀统计），不是直觉；月读率高于平衡点留标准层，归档后用取回费突增告警兜底误判。
- 生命周期必须含删除规则（365 天删除），但删除治理最严：最小保留 + 双人审批 + 删除总量日监控。

## 复盘追问
- 为什么"智能分层自动档"在 300TB 规模下不一定最优？提示：自动档按对象级访问自动转层省心，但单价带溢价且对"整桶模式一致"的数据手动分桶更便宜；模式混乱的长尾才值得交给自动档。
- 备份恢复演练的集中取回怎么不打破账？提示：演练预算单列、用批量/低优先级取回档（单价最低、小时级延迟）、错峰执行，并把演练取回量写进月度成本模型而不是当作异常。
