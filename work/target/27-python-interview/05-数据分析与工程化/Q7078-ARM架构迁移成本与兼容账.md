### Q7078 · x86 到 ARM 迁移的成本与兼容账

难度：P6 ｜ 标签：成本工程 / ARM / Graviton / 兼容性

**问**：云厂商宣称 ARM 实例（Graviton/倚天）性价比高 20-40%，团队想迁移。Python 服务栈里哪些东西会挡路？怎么算清这笔迁移账？

**答**：

**结论**：纯 Python 代码零兼容问题——字节码跨架构。挡路的是三件事：① 带 C/Rust 扩展且不发布 arm64 wheel 的第三方包（需要自己编译，gcc 工具链 + 系统库就进镜像）；② base 镜像与工具链的多架构可用性（alpine 的 musl 在 ARM 上某些包无预编译）；③ CI runner 架构（x86 runner 构建出的镜像在 ARM 节点跑不了，需要 buildx 多架构构建或 ARM runner）。成本账两笔：迁移一次性成本（镜像多架构化 + 依赖矩阵测试 + 回归）对冲每月节省（实例单价差 × 用量）；临界点通常在"月节省 > 3-6 个月分摊的迁移成本"。

**取舍**：全量迁移与灰度迁移——灰度（无状态服务先迁）风险低但两套架构并存期运维复杂（监控维度、镜像 tag 分 arm64/amd64）；全量一步到位决策干脆但回滚难。还有个隐性收益别漏算：ARM 实例常常也省碳排放/配额，且部分厂商 ARM 配额比 x86 宽松。反例也别忽略：某些闭源依赖（SaaS agent、私有 so）不支持 ARM，这类服务永远留在 x86——所以账要按服务逐个算，不是全公司一刀切。

**实战**：迁移前跑"依赖兼容扫描"：对 requirements.lock 里每个包查 PyPI 是否有 `manylinux2014_aarch64` wheel；没有的标红并试本地编译。镜像用 `docker buildx --platform linux/amd64,linux/arm64` 出多架构 manifest，CI 双架构各跑一次测试矩阵。性能账必须实测：同任务 ARM 与 x86 各跑 benchmark（部分 Rust 扩展在 ARM 上更快，部分 vec 优化依赖 x86 指令集的更慢），不要信厂商宣传倍数。

```python
# ARM 迁移依赖兼容扫描 + 成本临界点账（仅标准库，Python 3.9+）
from __future__ import annotations

import re


def scan_wheels(requirements: list[str],
                have_arm64: set[str]) -> tuple[list[str], list[str]]:
    ok, fail = [], []
    for req in requirements:
        name = re.split(r"[>=<\[]", req)[0].strip().lower()
        (ok if name in have_arm64 else fail).append(name)
    return ok, fail


def breakeven_months(migrate_cost: float, monthly_saving: float) -> float:
    assert monthly_saving > 0
    return migrate_cost / monthly_saving


def main() -> None:
    reqs = ["numpy>=1.26", "pandas>=2.1", "torch>=2.2",
            "some-private-agent>=1.0", "cffi>=1.16"]
    # 假设 PyPI 上 aarch64 wheel 可用性
    have_arm64 = {"numpy", "pandas", "cffi"}
    ok, fail = scan_wheels(reqs, have_arm64)
    print("可直接迁移:", ok)
    print("需处理:", fail)
    assert "torch" in fail and "some-private-agent" in fail

    # 成本账：100 台 4C16G，月省 30%；迁移一次性 2 人周 ≈ $6000
    monthly_saving = 100 * 40 * 0.30   # $/月（40$/台·月 × 30%）
    be = breakeven_months(6000, monthly_saving)
    print(f"月节省 ${monthly_saving:.0f}，回本 {be:.1f} 个月")
    assert be < 6, "回本周期应小于 6 个月才值得迁"

    # 闭源依赖不可迁 → 该服务留 x86，双架构并存
    assert "some-private-agent" in fail
    print("结论：开源栈迁 ARM，闭源 agent 服务留 x86，按服务逐个决策")


if __name__ == "__main__":
    main()
```

**追问链**：

- 追问 1：为什么"纯 Python 跨架构"但生产仍可能翻车？——生产路径上的非 Python 成分：C 扩展 wheel、Docker 基础镜像里的系统库（openssl 版本差异）、entrypoint 里的 shell 工具、以及第三方编译产物（自带 so 的包）。任何一环没有 arm64 变体就断。
- 追问 1.1：buildx 多架构构建的性能代价怎么处理？——x86 runner 上用 QEMU 模拟构建 arm64 镜像慢 5-20 倍；正确解是原生 ARM runner 构建 arm64 层 + x86 runner 构建 x86 层，manifest 合并。别让构建慢成为否决迁移的理由，那只是工具链问题。
- 追问 2：厂商宣传"性价比高 40%"为什么实测可能只有 15%？——宣传基于特定 benchmark（多为计算密集）；真实服务里网络 IO、内存带宽、GC 占比高，架构优势被稀释。所以账要用自家服务的 P95 时延与单实例 QPS 实测折算，实际需要的实例数才是省钱基数。

**背诵要点**：

1. 纯 Python 字节码跨架构，挡路的是 C/Rust 扩展 wheel（查 manylinux aarch64）、多架构镜像 buildx、CI runner 架构。
2. 成本账：月节省 = 实例单价差 × 实测所需实例数；回本 < 3-6 个月才值得，闭源依赖服务留 x86 双栈并存。
3. 性能收益必须自家 benchmark 实测，宣传倍数基于计算密集场景，IO 型服务收益常被稀释到 10-20%。
