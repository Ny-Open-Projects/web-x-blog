### Q7121 · 依赖下限缺失导致新装环境崩溃事故复盘

难度：P6 ｜ 标签：事故复盘 / 依赖解析 / 版本下限

**问**：项目锁文件齐全，但一个新同事 `pip install -e .` 装开发环境直接崩：某依赖装到了一个"比生产锁文件更新"的版本，与另一个包不兼容。锁文件明明保护了生产，为什么新装环境还会崩？这道"下限缺失"的账怎么复盘与设防？

**答**：
- **结论**：根因链：① 锁文件（uv.lock/requirements.freeze）只保护"按锁装"的路径——生产部署、CI 固定 job；而 `pip install -e .`/`pip install pkg` 这类**不读锁**的路径按 pyproject.toml 的约束区间解析——如果约束只写了 `sqlalchemy` 或 `sqlalchemy>=1.4`（**缺下限/下限过松**），resolver 会拿最新版，而最新版可能与锁内其他组件不兼容；② 事故链具体化：pyproject 写 `pydantic` 无下限 → 新同事装到 pydantic 3.x（假设性大版本）→ 依赖它的内部库不兼容 → import 崩；③ 为什么历史干净——老环境都是锁文件时代装的，只有"新装"触发；④ 本质是**约束声明 = 对下游环境的承诺**：你声明的区间就是允许别人（同事环境、下游项目、pip resolver）进入的版本空间，下限缺失等于承诺"任何版本都行"。另一形态：上限缺失让"最新版"进入区间——两者都是约束区间工程，Q7102 锁文件缺失是"没锁"，本题是"锁外路径的区间失守"，互补。
- **取舍**：设防层次：① **声明纪律**——pyproject 里每个直接依赖写"已验证的区间"：`>=X.Y,<Z`，下限来自"实际测试过的最老版本"，上限来自已知破坏点（大版本）；② **机器校验**——CI 加"区间验证 job"：按 pyproject 约束（不读锁）装一遍环境并跑冒烟测试，模拟新同事路径；`pip install --dry-run --report` 或 uv 的解析报告核对区间内最新版可用；③ **下限实测**——定期用"区间下限 + 锁内其他包"跑测试（min-version 测试，nox 矩阵 Q7024 同源），证明下限真实成立，防止"下限写了但从未验证"；④ 上游修复——发现不兼容后，第一时间**收紧自己项目的下限**（把事故版本排除在区间外），而不是等依赖方修复。
- **实战**：落地：① 新依赖入库模板强制填区间 + 注明依据（哪次测试验证了下限）；② CI 双轨：lock 安装轨（生产等价）+ 约束解析轨（新装路径模拟）；③ 事故后新增门禁：`pip check`（依赖冲突检测）进 CI 与开发环境预检脚本；④ 文档：贡献指南明确"装环境必须用 uv sync/锁路径"，裸 `pip install` 只在 CI 校验轨里出现。

```python
# 依赖约束区间模型：下限缺失 -> 新装路径解析到不兼容版本
# 基线：Python 3.9+ 标准库；真实校验用双轨 CI + pip check
from dataclasses import dataclass


@dataclass
class Constraint:
    pkg: str
    lo: tuple[int, int] | None   # None = 无下限(危险)
    hi: tuple[int, int] | None


@dataclass
class Release:
    pkg: str
    version: tuple[int, int]
    # 与哪些包的哪个版本区间冲突: {pkg: (lo, hi)}，lo/hi 为 None 表示开区间
    conflicts: dict[str, tuple[tuple[int, int] | None, tuple[int, int] | None]]


def newest_in_range(rels: list[Release], c: Constraint) -> Release | None:
    ok = [r for r in rels if r.pkg == c.pkg
          and (c.lo is None or r.version >= c.lo)
          and (c.hi is None or r.version < c.hi)]
    return max(ok, key=lambda r: r.version) if ok else None


def install_env(rels: list[Release], cons: list[Constraint]) -> dict[str, Release]:
    env = {}
    for c in cons:
        r = newest_in_range(rels, c)
        if r:
            env[c.pkg] = r
    return env


def env_broken(env: dict[str, Release]) -> list[str]:
    issues = []
    for pkg, r in env.items():
        for other, (lo, hi) in r.conflicts.items():
            o = env.get(other)
            if o and (lo is None or o.version >= lo) and (hi is None or o.version < hi):
                issues.append(f"{pkg}{r.version} 不兼容 {other}{o.version}")
    return issues


def main() -> None:
    rels = [
        Release("pydantic", (2, 9), {}),
        # pydantic>=3 与 internal-lib<2 冲突
        Release("pydantic", (3, 0), {"internal-lib": (None, (2, 0))}),
        # internal-lib 与 pydantic>=3 冲突
        Release("internal-lib", (1, 2), {"pydantic": ((3, 0), None)}),
    ]
    # 下限缺失：pydantic 无下限 -> 新装路径拿到 3.0 -> 环境崩
    loose = [Constraint("pydantic", None, None),
             Constraint("internal-lib", (1, 0), (2, 0))]
    env = install_env(rels, loose)
    assert env["pydantic"].version == (3, 0)
    assert env_broken(env), "应检出 pydantic3 与 internal-lib 1.2 冲突"

    # 收紧下限后：新装路径同样安全
    tight = [Constraint("pydantic", (2, 0), (3, 0)),
             Constraint("internal-lib", (1, 0), (2, 0))]
    env2 = install_env(rels, tight)
    assert env_broken(env2) == []
    print("OK: 锁文件保护锁内路径; pyproject区间约束保护新装路径, 下限必须实测")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"下限写了但从未验证"比不写更危险？
→ 一句话提示：未验证的下限给团队虚假安全感——CI 只测锁内版本，下限版本可能早已不兼容某其他依赖；min-version 测试 job（区间下限环境跑冒烟）是唯一能让下限"为真"的机制。

**追问 2**：发现事故版本后，收紧自己项目的约束还是等依赖修复？
→ 一句话提示：立即收紧自己的区间（排除事故版本），下游环境秒级安全；等上游修复是异步的，且你无法控制其他团队的新装路径——约束区间是自己项目的防线，不是依赖的。

## 背诵要点
- 锁文件只保护"按锁装"路径；`pip install -e .`/裸 pip 按 pyproject 区间解析——无下限或区间过松 = 允许最新版进入，新装环境与锁内组件冲突崩。
- 双轨 CI：lock 轨（生产等价）+ 约束解析轨（模拟新装，区间内最新版跑冒烟）；`pip check` 进 CI 预检。
- 约束声明是对下游的承诺：每个直接依赖写 `>=实测下限,<已知破坏点`，下限用 min-version 测试验证；出事故先收紧自己的区间再等上游。

## 复盘追问
- 为什么事故只发生在"新同事装环境"而不是任何发布？提示：发布全走锁文件，唯一不走锁的日常路径是新装开发环境；事故面 = 区间空间 × 不走锁的路径数，平时无人踩所以长期潜伏。
- 依赖区间与锁文件的责任边界怎么向团队讲清？提示：区间=对外承诺（下游/新装能进入的安全空间），锁=对内固化（我们验证过的精确组合）；两者都要真，缺一就是本题或 Q7102 的故事。
