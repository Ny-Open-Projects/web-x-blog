### Q7251 · 摄取重复率从 0.2% 跳到 3%：上游重发的第一现场怎么抓

难度：P6 ｜ 标签：摄取监控、重复率、幂等、上游重试、批次指纹

基线：Python 3.12；模拟批量摄取的批次指纹台账，输出重复率时间序列与"良性/有害"重复的分类统计。

**问**：数据平台做批量摄取，管道都是幂等的，重复数据理论上会被挡住。但监控发现某天的"重复率"从 0.2% 跳到 3%，指标本身没算错。这个"重复率"监控有什么用？重复分良性（被幂等挡住）和有害（穿透了幂等）两种，怎么区分？重复率暴涨说明上游发生了什么？

**答**：
- **结论**：重复率是**上游健康度的探针**：上游每次重试（网络超时后重发、任务平台重复调度、消息队列 at-least-once 投递）都会造成重复摄取，幂等管道把它挡住不产生错误数据，但**挡住的次数本身就值得监控**。分类看：① **良性重复**——同批次指纹重放，被批次台账挡住，说明上游在重试；② **有害重复**——不同批次指纹但内容行重复（上游没带幂等键就重造了批次），靠行级指纹/主键挡，成本更高。重复率暴涨的常见上游事件：任务平台把超时任务重复调度、上游消费组 rebalance 导致重复消费、上游 bug 重放了历史批次。抓到"哪类重复暴涨"就抓到了上游的第一现场。
- **取舍**：① 台账粒度：批次级指纹（快、便宜）在前，行级指纹（贵）只在批次级重复率异常时抽查；② 告警阈值要区分水位：0.2%~1% 是常态噪声（上游重试正常存在），>2% 告警，>10% 直接熔断暂停摄取（上游大概率在风暴式重发）；③ 台账带 TTL 滚动（Q1881 思路），避免台账本身膨胀；④ 只告警不熔断的风险：上游风暴式重发会把摄取带宽打满，挤掉正常批次。
- **实战**：① 重复率按"批次指纹重复"与"行级指纹重复"两个指标分开上报；② 每次告警自动附带Top 重复批次的指纹与到达时间序列，给上游排查直接证据；③ 与上游约定幂等键传递规范（批次 ID + 时间窗），消灭"无键重造批次"这类有害重复的源头。

```python
"""摄取重复率监控：批次指纹台账 + 良性/有害分类 + 阈值分级处置。"""
import hashlib
import json

BENIGN, HARMFUL, FIRST = "良性重复", "有害重复", "首次"


def batch_fingerprint(rows: list[dict]) -> str:
    payload = json.dumps(rows, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(payload.encode()).hexdigest()[:16]


def ingest(batches: list[list[dict]], ledger: dict[str, list],
           row_ledger: dict[str, int]) -> list[str]:
    verdicts = []
    for rows in batches:
        fp = batch_fingerprint(rows)
        if fp in ledger:
            verdicts.append(BENIGN)              # 同指纹重放：批次台账挡住
            ledger[fp].append(len(verdicts))
            continue
        ledger[fp] = []
        harmful = 0
        for r in rows:
            rk = r["order_no"]
            if rk in row_ledger and row_ledger[rk] != fp:
                harmful += 1                     # 不同批次携带相同业务行
            row_ledger.setdefault(rk, fp)
        verdicts.append(HARMFUL if harmful else FIRST)
    return verdicts


def classify_rate(verdicts: list[str]) -> dict:
    n = len(verdicts)
    return {"首次": verdicts.count(FIRST) / n,
            BENIGN: verdicts.count(BENIGN) / n,
            HARMFUL: verdicts.count(HARMFUL) / n}


if __name__ == "__main__":
    row = {"order_no": "A100", "amount": 99}
    day_normal = [[{"order_no": f"A{i}", "amount": 50 + i} for i in range(500)]
                  for _ in range(200)]
    day_storm = day_normal + [day_normal[10]] * 5      # 上游超时重发同批次 5 次
    day_bug = [[{"order_no": "A100", "amount": 99}] for _ in range(8)]  # 无键重造

    for name, batches in (("正常日", day_normal), ("重发风暴日", day_storm),
                          ("上游bug日", day_bug)):
        ledger: dict[str, list] = {}
        row_ledger: dict[str, int] = {}
        v = ingest(batches, ledger, row_ledger)
        r = classify_rate(v)
        rate = r[BENIGN] + r[HARMFUL]
        level = ("正常" if rate < 0.02 else
                 "告警" if rate < 0.10 else "熔断暂停摄取")
        print(f"{name:<6} 重复率 {rate:5.1%} "
              f"(良性 {r[BENIGN]:.1%} / 有害 {r[HARMFUL]:.1%}) -> {level}")
    print("\n结论：重复率是上游健康度探针；批次级指纹在前，行级指纹只在异常时兜底")
    print("      良性暴涨=上游在重试(超时/重复调度)；有害暴涨=上游丢了幂等键")
```

**追问一**：既然行级指纹能挡住一切重复，为什么不直接全用行级？

→ 解析：行级指纹要对每行做 hash + 台账查询，摄取吞吐高时（百万行/分钟）CPU 与台账存储成本显著；且行级台账需要 TTL 管理，窗口外的行重放（跨天重发一个月前的批次）会被漏掉。批次级指纹一次 hash 挡掉整批重放，覆盖了 90%+ 的实际重复场景。分层的目的就是把贵的那一层留给需要的时候——这不是偷懒，是成本结构决定的探针设计。

**追问二**：重复率监控和"指标对账"（Q1068 数据对账）是什么关系？有了对账还需要它吗？

→ 解析：需要。对账回答"最终对不对"，重复率回答"过程健康不健康"：有害重复如果被行级挡住，对账全绿，但上游 bug 依然存在，某天换个没被挡住的形式就会爆；重复率漂移在对账爆掉之前就给出信号，且它直接指向上游行为（重试风暴/丢幂等键），对账只能告诉你"两边的数不一致"。两者是"过程指标 + 结果校验"的组合：重复率做预警和归因，对账做最终兜底，都不能省。
