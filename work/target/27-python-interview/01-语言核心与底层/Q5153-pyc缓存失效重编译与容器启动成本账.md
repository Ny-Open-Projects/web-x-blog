### Q5153 · pyc 缓存失效重编译与容器启动成本账

难度：P6 ｜ 标签：pyc、`__pycache__`、sys.pycache_prefix、冷启动、成本工程

**问**：一次大型服务冷启动要 import 上千个模块，pyc 缓存在哪些情况下会失效？只读容器镜像里 `__pycache__` 写不进去会发生什么？`sys.pycache_prefix`、`compileall`、hash-based pyc（PEP 552）分别解决什么问题？如何做这笔启动成本账？

**答**：
结论：pyc 的默认校验是**源文件 mtime+size**，任何"构建时改写 mtime、运行时只读文件系统"的场景都会让缓存失效或写失败：① 镜像里没预编译 → 每个 pod 冷启动都对上千个源文件重复 tokenize+compile，纯 CPU 浪费（大仓库秒级）；② 镜像只读 → 解释器**静默跳过写 pyc**（无报错），每个 pod 每次启动都重编译；③ 挂载卷 mtime 漂移（git checkout、打包工具）→ 缓存反复失效。对应解法：镜像构建期跑 `python -m compileall`（并 `--invalidation-mode` 选 hash-based 校验绕开 mtime 依赖）；文件系统只读时设 `PYTHONPYCACHE_PREFIX` 把 pyc 写到可写卷，多 pod 还能共享。

取舍：`--invalidation-mode checked-hash`（源 hash 记录在 pyc，运行时算源文件 hash 比对）用每次 import 多一次读源文件+hash 的成本，换 mtime 不敏感性，适合源文件 mtime 不可信的环境；unchecked-hash 更快但源改动后不失效，只适合不可变镜像。`compileall` 预编译收益 = 冷启动频率 × 重编译成本，一次性构建成本可摊销；若服务常驻（月级重启），收益低。

实战：成本账公式：`冷启动浪费 ≈ Σ(import 每模块编译耗时) × pod 启动次数`，可用 `python -X importtime` 对比有无 pyc 的累计差；预编译时要保证与运行时 Python 小版本一致（pyc 魔数跨 minor 版本不兼容），多版本镜像需分别 compileall。

```python
import importlib.util, os, py_compile, sys, tempfile, time

src_dir = tempfile.mkdtemp(prefix="pycdemo_")
src = os.path.join(src_dir, "heavy_module.py")
with open(src, "w") as f:
    f.write("def add(a, b):\n    return a + b\n" * 200)   # 模拟一个较大的模块

# 1) 编译产物与缓存路径
pyc = py_compile.compile(src, doraise=True)
print("cache file  :", os.path.basename(pyc))                 # heavy_module.cpython-312.pyc（魔数含小版本）
print("cache dir   :", importlib.util.cache_from_source(src))

# 2) pyc 头：魔数(4) + flags(4) + mtime/size 或 source hash(8)
with open(pyc, "rb") as f:
    header = f.read(16)
flags = int.from_bytes(header[4:8], "little")
print("flags bit0 (hash-based):", flags & 1, " bit1 (checked):", (flags >> 1) & 1)

# 3) 有 pyc vs 无 pyc 的 import 成本（同进程删 sys.modules 后 reload 不公平，用子进程 -X importtime 对比）
import subprocess
def import_cost(with_cache: bool) -> float:
    if not with_cache:
        # 让校验失败：改 mtime 触发重编译（默认 timestamp 校验）
        os.utime(src, (0, 0))
    out = subprocess.run(
        [sys.executable, "-X", "importtime", "-c",
         f"import sys; sys.path.insert(0, {src_dir!r}); import heavy_module"],
        capture_output=True, text=True)
    total = 0.0
    for line in out.stderr.splitlines():
        parts = line.split("|")               # 格式: import time: self | cumulative | module
        if len(parts) == 3 and parts[2].strip() == "heavy_module":
            total = float(parts[1].strip().split()[0]) / 1000.0   # us -> ms
    return total

print("import with valid pyc    : %.2f ms" % import_cost(True))
print("import with stale mtime  : %.2f ms (重编译)" % import_cost(False))
```

**追问一**：hash-based pyc 为什么不是默认？——checked-hash 每次 import 都要读源文件并算 hash，对"mtime 可信"的主流开发场景是纯开销；timestamp 模式 miss 时只读 size/mtime 元数据（stat，不读内容），快得多。默认选择是给开发迭代让路。

**追问二**：`PYTHONDONTWRITEBYTECODE=1` 和只读文件系统对运行时性能影响有何不同？——前者只是不写 pyc（读仍可用已存在的），影响的是**下一次**启动；后者连读没问题（镜像里已带 pyc），只是"写失败静默跳过"，真正的坑是镜像没预编译 + 只读，二者叠加=永久重编译。

## 背诵要点
- pyc 默认 mtime+size 校验；只读镜像写 pyc 静默失败，没预编译则每 pod 每次启动重编译全部模块。
- 解法：构建期 compileall（多 Python 版本分别跑）+ checked-hash 校验模式 + PYTHONPYCACHE_PREFIX 共享缓存。
- 成本账：`python -X importtime` 量差；pyc 魔数绑定小版本，跨版本不通用。

## 复盘追问
