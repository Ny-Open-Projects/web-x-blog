### Q5251 · 3.12 sum() 的补偿求和：Neumaier 实现与 fsum 的误差账

难度：P6 ｜ 标签：sum、Neumaier、math.fsum、浮点误差、补偿求和、正确舍入、升级变更

基线：CPython 3.12 重写了 `sum()` 的浮点累加路径（gh-100425），这是少数"升级小版本后计算结果会变"的语言核心变更。

**问**：一次对账服务升级到 3.12 后，同一批流水算出来的总额从 `10000.000000018848` 变成了 `10000.0`，快照测试全红；而另一个服务用 `sum()` 累加 10 万条金额，仍然和财务系统对不上。`sum()` 到底改了什么？它现在和 `math.fsum()` 的误差还差多少？什么情况下它依然不准、必须换算法或换数据类型？

**答**：

- **结论**：3.12 的 `sum()` 对 `float` 走**Neumaier（Kahan-Babuška-Neumaier）补偿求和**：同时维护主累加和 `f_result` 与补偿项 `c`，每一步先算 `t = f_result + x`，再按 `|f_result| >= |x|` 与否，把这一步被舍入掉的低位补进 `c`（`c += (f_result - t) + x` 或 `c += (x - t) + f_result`），最后返回 `f_result + c`。空间是 O(1)，误差从朴素累加的 O(nε) 降到接近 O(ε)，所以 `[1e16, 1.0, -1e16, 1.0]` 从 `1.0` 变成正确的 `2.0`。但它是**补偿**不是**正确舍入**：`math.fsum()` 用的是 Shewchuk 展开（partials 数组），每一步都不丢位，结果接近"无限精度求和后一次舍入"，代价是更慢、最坏需要 O(n) 个部分和。3.12 的 `sum()` 只在中间结果溢出为 `inf` 时才退回 partials 路径，正常情况下不会付 fsum 的成本。

- **取舍**：a) 默认用 `sum()`：3.12 之后它对绝大多数统计、指标、聚合已经够准，且比 `fsum` 快数倍（无需维护 partials，逐项只多两次浮点运算）；b) 需要可复现、可审计的"正确舍入"时用 `math.fsum()`：它的结果与加法顺序基本无关，适合做校验和对账，但仍是 float，不能表达十进制金额；c) 金额/费率一律不要用任何 float 求和：用 `Decimal`（显式上下文精度）或整数最小货币单位（分），否则补偿算法只是把误差压小，不会把二进制无法表示的 0.1 变成精确值；d) 顺序仍然影响结果：补偿求和减少了顺序敏感，但没有消除，回归测试应带容差而不是死比对字符串。
  一个常被忽略的边界是 `start` 参数的类型：`sum(xs, 0)` 与 `sum(xs)` 一样走 float 补偿；`sum(xs, Decimal("0"))` 遇到 float 元素会直接 `TypeError`，不会"顺便帮你转成十进制"。

- **实战**：事故形态是"升级 3.12 后对账差异消失，但报表快照全挂"——团队把 `sum()` 的结果直接序列化进快照做逐字节比对，语言层的精度提升变成了测试红灯。修复分三步：①对账逻辑显式写 `math.fsum()`，把"要正确舍入"这件事写进代码而不是依赖解释器版本；②快照测试改成 `math.isclose(rel_tol=1e-12)`；③金额链路整体改整数分，float 只留在监控指标里。另一类事故是"以为 3.12 之后 sum 万无一失"：把 `2**53` 这种超出 float 精确整数范围的值混进 float 求和，补偿项救不了转换阶段的丢位。
  还有一个迁移细节：灰度和回滚期间，同一份数据可能被 3.11 与 3.12 的 worker 分别处理；如果结果要写进同一条账，必须在入口统一算法（fsum 或整数），否则回滚一次就多一批"对不上"的记录。
  验收时不要只比最终值，还要记录"朴素值 / sum 值 / fsum 值"三个数，出现偏差时能立刻判断是哪一层的问题。

```python
# 3.12 sum() 的补偿求和: 与朴素累加、math.fsum 的误差对照
import math
from decimal import Decimal

vals = [1e16, 1.0, -1e16, 1.0]
naive = 0.0
for v in vals:
    naive += v
print("→ 朴素顺序累加:", naive)
print("→ 3.12 sum():", sum(vals), "| math.fsum():", math.fsum(vals))
assert naive == 1.0                 # 1.0 被 1e16 吃掉, 后面的 1.0 也救不回来
assert sum(vals) == 2.0             # 补偿项把两次丢掉的低位都捞回来
assert math.fsum(vals) == 2.0

batch = [0.1] * 100_000
naive2 = 0.0
for x in batch:
    naive2 += x
print("→ 1e5 次 0.1: 朴素", repr(naive2), "| sum", repr(sum(batch)))
assert naive2 != 10000.0            # 朴素累加漂了 1.8e-11
assert sum(batch) == 10000.0
assert sum(batch) == math.fsum(batch)

print("→ Decimal 不走 float 补偿:", sum([Decimal("0.1")] * 3))
assert sum([Decimal("0.1")] * 3) == Decimal("0.3")
assert sum([10**20, 1, -10**20]) == 1      # int 路径本来就精确

lost = sum([2**53, 1, 1.0])
print("→ 超大 int 先转 float 再补偿:", repr(lost), "精确值应为", 2**53 + 2)
assert lost == float(2**53)         # 2^53+1 转 float 时就丢了 1, 补偿无从下手

print("→ 溢出后补偿无效:", sum([1e308, 1e308]))
assert math.isinf(sum([1e308, 1e308]))
assert math.isnan(sum([float("nan"), 1.0]))
```

**追问一**：为什么用 Neumaier 而不是经典的 Kahan 求和？两者的误差界差在哪？—— Kahan 的补偿公式是 `y = x - c; t = sum + y; c = (t - sum) - y; sum = t`，它在"加数比当前累计和小"时有效；当 `|x| > |sum|`（比如刚从小数跳到大数）时，`(t - sum)` 这一项本身就会丢掉 `x` 的低位，补偿失效。Neumaier 增加一个分支：`|sum| >= |x|` 时用 `c += (sum - t) + x`，否则用 `c += (x - t) + sum`，保证被舍入的是**两者中较小的那个**，误差界从 Kahan 的"依赖顺序"变成对任意顺序都有接近 O(ε) 的保证。代价是每步多一次比较和一次分支预测，但在 Python 层这点成本被解释器开销淹没。要注意：Neumaier 仍然只有一个补偿项，遇到极端级差（1e300 与 1e-300 交替）时 `c` 自己也会被舍入，这时只有 fsum 的展开算法能保住所有位。

**追问二**：3.12 的这个变更会让哪些线上逻辑"静默改变结果"？怎么迁移？—— 三类高风险点：①**逐字节比对**：把 `sum()` 结果写进快照、缓存键、幂等键、报表文件哈希，精度变化直接变成 cache miss 或测试失败；②**阈值判定**：`sum(xs) >= limit` 在边界值附近可能翻转，尤其是限流、配额、风控打分；③**跨版本一致性**：同一批数据在 3.11 worker 和 3.12 worker 上算出不同结果，灰度期间出现"同一请求两次结果不同"。迁移纪律：需要稳定语义的地方显式写 `math.fsum()`（并在注释里说明"依赖正确舍入，不依赖解释器版本"），比较一律用 `isclose`，金额改 `Decimal`/整数分。反过来，如果只是监控指标，接受 3.12 的新结果并把快照更新一次即可——不要为了"和历史一致"去手写朴素循环，那是把已知的误差请回来。
  一个可操作的自检：在 CI 里跑一组"病态输入"（大数吃小数、正负抵消、10 万次 0.1），把 `sum`/`fsum` 的结果差打印出来；差值突然变大通常意味着有人改了数据类型（比如把 Decimal 换回 float），而不是解释器升级。
  这条自检也能反过来验证升级：3.11 上 sum 与朴素循环的差值应该与 3.12 上明显不同，把两边的数值记进发布说明，比"精度提升了"这种描述有用得多。

## 背诵要点

- 3.12 `sum()` 对 float 用 Neumaier 单补偿项：O(1) 空间，把 `[1e16, 1.0, -1e16, 1.0]` 从 1.0 修正到 2.0，误差接近 O(ε) 但不是正确舍入。
- `math.fsum()` 用 partials 展开做近乎正确舍入、结果与顺序基本无关，代价是更慢；要可复现的对账就用它，金额用 Decimal 或整数分。
- 补偿只覆盖 float 路径：`2**53` 级大 int 转 float 先丢位、`inf`/`nan` 照常传播、Decimal/Fraction 走自己的精度，都不是 sum 能救的。

## 复盘追问

- 为什么 `sum([1e16, 1.0, -1e16, 1.0])` 在 3.12 得到 2.0，而 Kahan 求和可能仍然得到 1.0？（Kahan 在加数远大于累计和时补偿项自己丢位；Neumaier 按大小分支，总是补较小的那个）
- 升级 3.12 后哪些地方会因 sum 结果变化而炸？（快照/缓存键/幂等键的逐字节比对、阈值边界、灰度期跨版本不一致；用 fsum 固定语义 + isclose + 整数分）
