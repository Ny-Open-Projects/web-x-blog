### Q5165 · f-string 生成代码/模板的定界符事故

难度：P6 ｜ 标签：f-string、PEP 701、定界符转义、代码生成、事故复盘

**问**：用 f-string 生成一段"包含花括号的代码/JSON/模板"时，为什么字面 `{` `}` 必须写成 `{{` `}}`，否则轻则 `KeyError` 重则语法错误？3.12 的 PEP 701 解禁了"嵌套同引号 f-string"，为什么这反而让代码生成器更容易踩坑？当被生成的文本里**本身含有 markdown 围栏**时，怎么用 `chr(96)*3` 之类手法避免"裸围栏"把外层文档撑破？

**答**：
结论：f-string 是**先按定界符切词、再把 `{...}` 当表达式编译**的模板语言，所以生成"含花括号的目标文本"时，花括号是**双重身份**：字面量必须 `{{`/`}}` 转义，单个 `{` 会被当表达式起点——生成 `{"k": 1}` 这类文本时写成单花括号，表达式部分 `"k": 1` 不合法直接 `SyntaxError`，或变成求值后 `KeyError`。PEP 701（3.12）把表达式 grammar 改成递归解析，允许 `f"{f'{x}'}"` 这种**同引号嵌套**和表达式内反斜杠——能力变强但可读性更差：嵌套层级一深，哪个 `{` 属于外层、哪个属于内层极难肉眼判断，代码生成器拼接时极易错位。生成 markdown/代码围栏时，"裸写 ``` 到字符串里"会和外层的 markdown 围栏冲突，正确手法是用 `chr(96)*3` 动态构造反引号串——这样源码里不出现裸围栏，文档解析与代码生成互不干扰。

取舍：生成结构化文本时，f-string 适合"变量少、结构固定"的场景；一旦目标文本自身有复杂定界符（多层花括号、混合引号、围栏），应改用**专用模板引擎**（`string.Template` 只认 `$`、或 Jinja2 显式定界符），把"数据插值"与"目标语法"彻底分离。坚持用 f-string 时遵守三条：① 字面花括号一律双写；② 嵌套不超过一层，超了就先算到局部变量再插值；③ 任何"围栏/引号"这类会与外层冲突的定界符都用 `chr()` 构造而不是裸写。

实战：事故常见于"用 f-string 生成 f-string"的脚手架、或"把 JSON 样例拼进文档"——生成时没双写花括号，`KeyError` Reported 成"模板渲染失败"，排查半天才发现是定界符冲突。下面跑出三种形态：正确转义、单花括号语法错误（用 `eval` 隔离，避免撑破本卡围栏）、同引号嵌套与 `chr(96)*3` 构造围栏。

```python
value = 7

# 1) 正确：字面花括号双写，表达式用单花括号
print("escaped  :", f'{{"k": {value}}}')       # {"k": 7}

# 2) 单花括号的事故：用 eval + chr(39) 构造源码，避免本卡出现裸定界符
broken_src = "f" + chr(39) + '{"k": 7}' + chr(39)
try:
    eval(broken_src)
except Exception as e:
    print("single   :", type(e).__name__, "->", str(e)[:50])

# 3) PEP 701（3.12）：同引号嵌套可解析，但可读性差
x = 41
print("nested   :", f"{f'{x + 1}'}")           # 42

# 4) 生成带 markdown 围栏的文本：用 chr(96)*3 构造反引号，源码无裸围栏
fence = chr(96) * 3
md = f"{fence}python\nprint('ok')\n{fence}"
print("generated:\n" + md)

# 5) 更稳的方案：string.Template 只认 $，不与花括号/围栏冲突
from string import Template
tpl = Template('def $name(x):\n    return {"x": x}')
print("template :", tpl.substitute(name="handler"))
```

**追问一**：PEP 701 允许表达式内反斜杠后，`f"{\"a\"}"` 这类写法算"解禁"还是"新坑"？——算解禁（3.11 会因反斜杠在表达式里报 `SyntaxError`），但属于"能写不该写"：表达式里的字符串引号、转义、外层围栏叠在一起，静态检查与人工 review 都难判断边界；工程上宁可把表达式抽成变量 `key = "a"; f"{key}"`，可读性换取零收益的风险不值得。

**追问二**：为什么生成"代码"时更推荐 `string.Template` 而不是 f-string？——模板引擎把**定界符收敛到一种**（`$var`），目标语言的花括号/引号/围栏都变成普通字符，不再需要转义；f-string 的定界符 `{`（以及 3.12 后同引号嵌套）与目标语言语法高度同构，越生成越容易撞车。取舍是 `Template` 表达力弱（无格式化迷你语言、无转换标志），所以只在"目标是代码/文档"时用，普通日志/消息仍用 f-string。

## 背诵要点
- f-string 先按定界符切词：字面 `{`/`}` 必须 `{{`/`}}`，单花括号会触发表达式求值 → `KeyError`/`SyntaxError`。
- PEP 701（3.12）递归解析允许同引号嵌套与表达式内反斜杠，但可读性差、坑更深，嵌套超一层就抽变量。
- 生成代码/文档时定界符冲突用专用模板（`string.Template`）或 `chr(96)*3` 构造围栏，避免裸写与外层冲突。

## 复盘追问
- 用 f-string 生成 JSON 样例拼进文档时渲染失败，如何复盘并建立规范？（花括号双写规则、同引号嵌套边界、改用 Template/围栏构造，讨论代码生成器测试要覆盖"目标文本含定界符"）
- 为什么"用 f-string 生成 f-string"的脚手架在 3.11 报语法错、3.12 却能跑但更难维护？（PEP 701 递归解析的解禁与可读性取舍，讨论何时该禁止嵌套）
