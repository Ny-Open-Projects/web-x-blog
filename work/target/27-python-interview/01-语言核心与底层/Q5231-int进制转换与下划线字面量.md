### Q5231 · int 进制转换与下划线字面量：base 参数与自动前缀识别

难度：P5 ｜ 标签：int、进制、base 参数、0x/0b/0o 前缀、下划线字面量、base=0、解析规则

**问**：`int("ff", 16)` 与 `int("0xff", 0)` 的解析规则差在哪？base 参数什么时候允许前缀、什么时候报错？字符串里的下划线 `int("1_000")` 会不会解析？为什么配置解析里推荐 `int(s, 0)` 而不是手写 `replace("0x", "")`？二进制/十六进制字面量 `0b101`、`0xff` 与字符串转换的边界在哪？

**答**：
结论：`int(s, base)` 的解析规则有一条主线——**base 显式给出时，前缀可有可无但不能冲突**：`int("ff", 16)` 与 `int("0xff", 16)` 都合法，但 `int("0b101", 16)` 报 ValueError（前缀与 base 不匹配）；**`base=0` 时启用自动识别**：按前缀 `0x/0o/0b` 判定十六/八/二进制，无前缀则按十进制——`int("0xff", 0)` = 255、`int("101", 0)` = 101（注意无前缀时是十进制不是八进制，这是与 C 语言 `0` 前缀八进制的最大差异）。三条高频坑：①**下划线在字面量与字符串里都合法**：`1_000_000` 字面量、`int("1_000")` 都等于 1000（下划线只是视觉分组，不能在首尾/贴着前缀）；②**base 与前缀的组合矩阵要背**：`int("10", 0)` 十进制、`int("010", 0)` 报错（`0` 前缀在 base=0 下不是合法八进制写法，八进制必须 `0o`）；③**前后空白会 strip，但正负号只允许一个**。工程建议：配置里的数字解析统一 `int(s, 0)`，让 `0x` 前缀的表达成为可能，同时拒绝手写 `strip("0x")`——那会把 `0x10` 变成 `10`（静默错值），是真实的对账事故形态。

取舍：a) 解析用户输入的掩码/端口类配置：`int(s, 0)` 最灵活，但要不要允许十六进制是**产品决策**——安全敏感参数应锁死 `base=10`；b) 输出侧：`format(x, '#x')` 生成带前缀字符串、`bin()/oct()/hex()` 是便捷函数，round-trip 用 `int(hex(x), 16)` 或 `int(s, 0)`；c) 大整数无所谓，但高频循环里 `int(s, base)` 的 base 参数走泛化路径，十进制用 `int(s)`（无 base）最快；d) 别用 `eval("0x" + s)` 解析——那是代码执行不是解析；e) Windows 的注册表 DWORD、Redis 配置这类"外来数字"，先确认它们的进制约定再选 base，别默认十进制。

实战：事故形态是"配置中心把子网掩码存成 `0xffffff00`，解析层用 `s.replace("0x", "")` 后按十进制 parse，`ffffff00` 超过 int 上限直接异常；而另一处 `0x0a` 被替换成 `a` 报 ValueError，两处行为不一致难排查——统一改为 `int(s, 0)` 后行为收敛"。下面实测 base/前缀组合矩阵与下划线解析。

```python
# int 进制转换与下划线字面量
print("[1] base 显式给出时, 前缀可有可无但不能冲突")
print("    int('ff', 16)     =", int("ff", 16))
print("    int('0xff', 16)   =", int("0xff", 16))
try:
    int("0b101", 16)
except ValueError as e:
    print("    int('0b101', 16)  -> ValueError:", e)

print("[2] base=0 自动识别前缀; 无前缀按十进制 (不是八进制)")
print("    int('0xff', 0) =", int("0xff", 0), "| int('0o17', 0) =", int("0o17", 0),
      "| int('0b101', 0) =", int("0b101", 0))
print("    int('101', 0)  =", int("101", 0), "(十进制!)")
try:
    int("010", 0)
except ValueError as e:
    print("    int('010', 0)  -> ValueError: 0 前缀在 base=0 下不合法, 八进制必须 0o")

print("[3] 下划线分组: 字面量与字符串都合法, 不能贴边")
print("    1_000_000 =", 1_000_000, "| int('1_000') =", int("1_000"), "| int('1_0', 0) =", int("1_0", 0))
for bad in ("_100", "100_", "0_x1"):
    try:
        int(bad)
        print(f"    int('{bad}') 可解析")
    except ValueError:
        print(f"    int('{bad}') -> ValueError (下划线不能在首尾/贴前缀)")

print("[4] 前后空白会 strip, 符号只允许一个")
print("    int('  42 ') =", int("  42 "), "| int('  -0x1f ', 0) =", int("  -0x1f ", 0))

print("[5] round-trip: format 带 # 前缀生成, int(s, 0) 逆解析")
x = 255
s = format(x, "#x")
print(f"    format(255, '#x') = {s!r} -> int({s!r}, 0) =", int(s, 0))
print("[6] 工程纪律: 配置解析统一 int(s, 0); 禁止 replace('0x','') 再按十进制 parse (静默错值)")
```

**追问一**：`int()` 还能解析非 ASCII 数字，比如 `int("١٢٣")` 返回 123——这算特性还是坑？—— 算特性但也是坑：Python 的 `int()` 接受**任意 Unicode 十进制数字**（Nd 类别），阿拉伯-印度数字、全角数字 `１２３` 都能转。来源是语言规范"按 Unicode 数字值解析"。坑在两处：①输入校验若用 `s.isdigit()` 放行，全角数字混进业务数据，后续按 ASCII 断言（正则 `[0-9]+`）失败——校验与解析用的字符类必须一致；②安全过滤若依赖"字符串里没有十进制就拒绝"，Unicode 数字是绕过面（同类还有 U+200B 零宽字符对等值判断的干扰）。工程纪律：入参归一化（NFKC）后再解析，解析结果再与原始字符串的字符集断言双保险。

**追问二**：为什么 `int("010", 0)` 报错而 C 家族语言里 `010` 是八进制？—— 这是 Python 3 的刻意修正：Python 2 沿袭 C 的 `0` 前缀八进制，`010 == 8`，生产事故频发（配置里补零对齐就变值）；PEP 3127 在 Python 3 里废除 `0` 前缀，八进制强制 `0o` 前缀，使 `base=0` 的自动识别变得**无歧义**——看到 `0` 开头只能拒绝而不是猜。这条设计的工程意义：`base=0` 从"危险的猜进制"变成"安全的按前缀识别"，才敢作为配置解析的推荐姿势。代价是从 Python 2 迁移时 `010` 这类老字面量会直接 SyntaxError，是迁移检查单的固定条目。

## 背诵要点
- base 显式：前缀可有可无但不能冲突；base=0：按 0x/0o/0b 自动识别，无前缀按十进制。
- `int("010", 0)` 报错（0 前缀八进制已在 Py3 废除，PEP 3127）；下划线字面量/字符串都合法但不能贴边。
- 配置解析统一 `int(s, 0)`；`int()` 接受 Unicode 十进制数字，归一化后再解析。

## 复盘追问
- 为什么不能用 replace("0x","") 解析十六进制配置？（0x0a 变 a 报错、0x10 变 10 静默错值；int(s,0) 才是无歧义路径）
- base=0 下 "101" 是什么进制？（十进制；前缀决定进制，无前缀永远十进制——与 C 的 0 前缀八进制划清界限）
