### Q5254 · PEP 393 的三档内部表示：getsizeof 内存账、切片复制与编码成本

难度：P6 ｜ 标签：PEP 393、str 内部表示、latin1、UCS2、UCS4、getsizeof、切片复制、UTF-8 编码

**问**：一条日志里混进一个 emoji，整条字符串的内存从 200 字节涨到 400 字节；另一个服务把 10 万条纯 ASCII 的 JSON 字符串缓存在内存里，`sys.getsizeof()` 加起来只有几十 MB，进程 RSS 却是三倍。`str` 的内存到底怎么算？一个字符占几个字节是由什么决定的、会不会中途变？切片和 `encode()` 又各自复制了多少？

**答**：

- **结论**：CPython 的 `str` 用 PEP 393 的"**按需选宽度**"表示：创建时扫描内容取 `maxchar`，小于 256 用 latin1（每字符 1 字节，kind=1），小于 65536 用 UCS2（2 字节，kind=2），否则 UCS4（4 字节，kind=4）。宽度在对象创建时**一次定死**，因为 `str` 不可变，之后不会升级也不会降级。`sys.getsizeof(s)` 在 3.12 上是"头部 + n×width"，头部随 kind 不同：latin1 41 字节、UCS2 58、UCS4 60（都含结尾的 `\0`），所以 `""` 是 41、`"a"*10` 是 51、`"中"*10` 是 78、`"😀"*10` 是 100。切片 `s[a:b]` **不是视图**，它新建一个 str 并把字符拷过去（O(k)），而且新串按自己的内容重新选宽度——`("a" + "中"*5)[1:]` 会从 UCS2 的 70 字节变成纯 UCS2 的 68 字节，纯 ASCII 切片则落回 latin1。拼接按两个操作数里更宽的 kind 决定结果，代价是 O(n+m) 复制。3.12 还移除了旧版的 legacy Unicode 对象（PEP 623），不再有按需生成的 `wstr` 缓存，`encode()` 每次都要重新走一遍编码器。

- **取舍**：a) 内存换操作：latin1 让 ASCII 文本的存储只有 UCS4 的四分之一，代价是每次创建都要扫一遍取 maxchar（O(n)），并且一旦遇到一个宽字符，整串都按宽字符存——日志里一个 emoji 让整行翻倍就是这个原因；b) 切片适合"取一小段"，不适合"反复切大串"：每次切片都复制，循环里 `s = s[1:]` 是 O(n²)；需要零拷贝视图只能用 `memoryview`（仅 bytes）或自己维护 `(buf, start, end)`；c) `encode()` 必然分配新 `bytes`：ASCII 走快路径近似 memcpy，非 ASCII 要从 UCS2/UCS4 转 UTF-8（变长，逐字符），成本 O(n) 且结果长度不等于字符数；d) 缓存字符串时不要只算 `getsizeof`：它不含对象头之外的引用、不含 dict/list 的槽位、不含 allocator 的碎片，RSS 三倍是正常的，容量规划要用 `tracemalloc` 或按"字符数×宽度+头部+容器开销"估算。

- **实战**：事故形态是"把用户昵称（含 emoji）拼进 1KB 的定长日志缓冲"——代码按 `len(s)` 算字节数，实际 UCS4 下每字符 4 字节，缓冲区溢出后截断在 UTF-8 序列中间，下游解析出乱码。修复：所有"按字节限长"的地方改用 `len(s.encode("utf-8"))` 或直接对 `bytes` 截断并处理边界；缓存层按 `getsizeof` 估算时给容器和碎片留 30% 余量；日志脱敏用切片而不是反复 `replace`，避免每条日志多次全量复制。
  另一个隐性成本是 `sys.intern`：它只共享对象、不改变字符数据宽度，把大量唯一的长字符串 intern 反而会让驻留表永久持有它们。
  验收标准可以写成两条断言：`len(s)` 只用于字符语义的上限（如"标题最多 80 字"），字节语义的上限（如"一行最多 4KB"）必须走 `len(s.encode())`。

```python
# PEP 393: kind 决定每字符宽度, getsizeof = 头部 + n*width
import sys

samples = [("empty", ""), ("latin1", "a" * 10), ("ucs2", "中" * 10), ("ucs4", "😀" * 10)]
for name, s in samples:
    print("→", name, "len =", len(s), "getsizeof =", sys.getsizeof(s))

assert sys.getsizeof("") == 41          # latin1 头: 40 字节 + '\0'
assert sys.getsizeof("a" * 10) == 51    # 41 + 10*1
assert sys.getsizeof("中" * 10) == 78   # 58 + 10*2
assert sys.getsizeof("😀" * 10) == 100  # 60 + 10*4

assert sys.getsizeof("a" * 100) - 41 == 100
assert sys.getsizeof("中" * 100) - 58 == 200
assert sys.getsizeof("😀" * 100) - 60 == 400

# 宽度由内容定死: 一个宽字符把整串拉宽
mixed = "a" * 5 + "😀"
print("→ 5 个 ASCII + 1 个 emoji:", len(mixed), "字符,", sys.getsizeof(mixed), "字节")
assert sys.getsizeof(mixed) == 60 + 6 * 4
assert not mixed.isascii()

# 切片是复制, 且新串按自己的内容重新选宽度
s = "a" + "中" * 5
t = s[1:]
print("→ 切片:", len(t), "字符,", sys.getsizeof(t), "字节, 与原串同一对象?", t is s)
assert t is not s and t == "中" * 5
assert sys.getsizeof(t) == 58 + 5 * 2

ascii_slice = ("abc" * 10)[:3]
assert sys.getsizeof(ascii_slice) == 41 + 3      # 降回 latin1

# encode 必然新建 bytes: 非 ASCII 是变长转码
b_ascii = ("a" * 10).encode()
b_cn = "中".encode()
b_emoji = "😀".encode()
print("→ encode 后长度:", len(b_ascii), len(b_cn), len(b_emoji))
assert len(b_ascii) == 10 and len(b_cn) == 3 and len(b_emoji) == 4
assert len(b_cn) != len("中")                     # 字符数 != 字节数
assert sys.getsizeof(b_ascii) == 43               # bytes 头 33 + 10
```

**追问一**：为什么 `str` 不做成"按需升级"的可变宽度缓冲，像某些语言那样？—— 因为 Python 的 `str` 是**不可变对象**，一旦发布出去，任何持有者都期望它的 `len`、索引、切片永远不变；如果允许内部宽度变化，`hash` 缓存、`dict` 的键、切片视图、C 扩展拿到的缓冲区指针全部要失效。PEP 393 的取舍是"创建时定宽 + 不可变"，换来 O(1) 的 `len` 和索引、稳定的哈希、简单的内存布局；代价是创建时 O(n) 扫描、以及"一个宽字符污染整串"的空间放大。旧版（3.2 以前）用固定 UCS2/UCS4 或 legacy 对象，宽字符在窄表示下会触发转换和缓存，逻辑更复杂且内存更差；PEP 623（3.12）干脆删掉了 legacy 的 `wstr`，只保留 compact 表示。

**追问二**：既然 `getsizeof` 不等于真实占用，容量规划应该怎么算？—— 分三层：①**对象本身**：`getsizeof(s)` 含头部与字符数据，但不含 allocator 的对齐/碎片（pymalloc 按 size class 分配，实际可能多 10%–25%）；②**容器与引用**：list 的 `getsizeof` 只算指针数组，不含元素对象，每个指针 8 字节；dict 还要算哈希表负载因子；③**进程实际**：用 `tracemalloc` 看 Python 层分配，用 `resource.getrusage` / `ps` 看 RSS，两者差值就是碎片、C 扩展、mmap 的部分。工程上给"字符数 × 4 + 头 + 容器"做上界估算，再用 tracemalloc 校准；不要用 `sum(map(getsizeof, objs))` 直接当内存预算，它系统性偏低。

## 背诵要点

- PEP 393 三档按 maxchar 选宽度：<256 每字符 1 字节（头 41）、<65536 为 2 字节（头 58）、否则 4 字节（头 60）；宽度创建时定死，`str` 不可变。
- `getsizeof = 头 + n×width`，切片是 O(k) 复制并按新内容重新选宽度；拼接按较宽者复制，循环里 `s = s[1:]` 是 O(n²)。
- `encode()` 必分配新 bytes，非 ASCII 是变长转码；容量规划用 tracemalloc/RSS 校准，别把 getsizeof 之和当真实占用。

## 复盘追问

- 为什么日志里一个 emoji 会让整行内存翻倍？（UCS4 宽度由 maxchar 决定，整串每字符 4 字节；不是只有那一个字符变宽）
- 切片为什么不能是零拷贝视图？（str 不可变但切片要独立对象语义；零拷贝会让原串无法释放，且宽度可能不同；bytes 才有 memoryview）
