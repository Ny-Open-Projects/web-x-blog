### Q5263 · 整数与字符串互转的 4300 位闸门：set_int_max_str_digits 的 DoS 边界

难度：P6 ｜ 标签：int、int_max_str_digits、DoS、进制转换、CVE-2020-10735

基线：CPython 3.12.2，纯标准库；用 `sys.set_int_max_str_digits` 实测十进制解析/格式化的上限、最小值与关闭方式。

**问**：一个对账接口接收商户上传的"订单号"，代码里 `order_id = int(body["id"])`。攻击者传了一个 120 万位的十进制串，单个请求把 8 核机器的一核打满 6 秒，50 并发直接把服务拖垮；运维临时把 `sys.set_int_max_str_digits(0)` 关掉，攻击面反而更大。Python 3.11 为什么要加这个限制？它到底限制哪些操作？为什么十六进制解析不受影响？设成 0 和设成 100000 分别意味着什么？

**答**：

- **结论**：CPython 的 `int` 是任意精度，十进制字符串转 `int` 用的是超线性算法（接近 O(n²)），长度翻倍、耗时约四倍；一个几 MB 的十进制串就能让单核跑几十秒，这是典型的算法复杂度 DoS（CVE-2020-10735）。3.11 起加了 `sys.set_int_max_str_digits(n)`，默认 4300 位，限制的是**非 2 的幂进制**的双向转换：`int(s)`、`int(s, 10)`、`str(i)`、f-string 格式化、`repr` 都受限；`int(s, 16)`、`int(s, 2)`、`hex()` 不受限，因为 2 的幂进制可以按位分组、线性时间完成。合法值只能是 0 或 ≥640：0 表示**关闭限制**（不是"最小"），640 是下限，防止把闸门调到没有防护意义的值。
- **取舍**：把上限调到 100000 能兼容"合法的大整数"（如加密公钥十进制、科学计算），但也把单次转换的成本放大到几百毫秒，攻击者仍然可以用少量请求打满 CPU；正确做法是**按业务定上限**（订单号 20 位、雪花 ID 19 位，根本不需要 4300），超限直接 400，而不是调大全局阈值。另一个取舍是全局性：这个设置是解释器级的，库作者不应擅自改；应用应该在启动时显式设置并在配置里审计。对确实需要超长十进制的外部输入，改用十六进制/Base64 传输，或在流式解析时按块处理，而不是关掉闸门。
- **实战**：事故接口的对账文件允许"任意长度数字"，`int()` 直接吃外部输入。修复：① 先把 JSON 里的 ID 当字符串校验 `^\d{1,32}$`，不匹配直接 400；② 启动时 `sys.set_int_max_str_digits(640)`，把全局兜底压到业务上限附近；③ 监控里加 `decimal_conversion_rejected` 计数，上线一周拦下 1.7 万次超长输入，P99 从 4.8s 回到 23ms。注意：`str(huge_int)` 也会触发同样的限制，日志里打印超大整数同样会抛 `ValueError`，不要只防入口不防出口。

下面实测默认值、641 位触发、640 位通过、`str()` 反向也受限、十六进制不受限、0 表示关闭，以及小于 640 的非法设置。

```python
# 十进制转换闸门: int() 与 str() 双向受限, 2 的幂进制不受限
import sys

original = sys.get_int_max_str_digits()
print("[0] 默认上限:", original)
assert original == 4300

try:
    sys.set_int_max_str_digits(640)

    # 1) 641 位十进制解析失败, 640 位成功
    try:
        int("9" * 641)
        raise AssertionError("641 位本应被拒绝")
    except ValueError as exc:
        print("[1] 641 位 int() ->", exc)
        assert "640 digits" in str(exc)

    value = int("9" * 640)
    print("[2] 640 位 int() 通过, 末三位:", value % 1000)
    assert value % 1000 == 999

    # 2) 反方向 str() 同样受限
    try:
        str(10 ** 700)
        raise AssertionError("701 位整数格式化本应被拒绝")
    except ValueError as exc:
        print("[3] str(10**700) ->", exc)

    # 3) 十六进制是 2 的幂进制, 线性可算, 不受限制
    big_hex = int("f" * 1000, 16)
    print("[4] 1000 位十六进制 bit_length:", big_hex.bit_length())
    assert big_hex.bit_length() == 4000

    # 4) 0 表示关闭限制, 不是"最小"
    sys.set_int_max_str_digits(0)
    print("[5] 设为 0 后:", sys.get_int_max_str_digits(), "位数:", len(str(10 ** 5000)))
    assert sys.get_int_max_str_digits() == 0
    assert len(str(10 ** 5000)) == 5001

    # 5) 640 是下限, 100 非法
    try:
        sys.set_int_max_str_digits(100)
        raise AssertionError("小于 640 的设置本应被拒绝")
    except ValueError as exc:
        print("[6] 设为 100 ->", exc)
        assert "640" in str(exc)
finally:
    sys.set_int_max_str_digits(original)

print("[7] 已恢复默认:", sys.get_int_max_str_digits())
assert sys.get_int_max_str_digits() == 4300
```

**追问一**：为什么 `int("ff", 16)` 不需要这个限制？—— 十六进制每位对应 4 bit，解析时可以按机器字长分组，把字符串线性折叠成 limb，时间复杂度 O(n)；十进制不是 2 的幂，无法直接按位对齐，CPython 只能用分治/乘法类的超线性算法。同理，`bin()`、`oct()`、`hex()` 以及 `int(s, 2/4/8/16/32)` 都不受限。这也给出了一条工程规避路径：外部协议如果必须传超长整数，用十六进制或 Base64，而不是关掉十进制闸门。

**追问二**：这个限制是进程级还是解释器级？子解释器/子进程会继承吗？—— 它挂在解释器状态上，同一解释器内全局生效；`multiprocessing` 的子进程是新的解释器，**不会**自动继承父进程运行时改过的值，需要在子进程初始化函数里重新设置。子解释器（3.12 的 `interpreters`）各自有独立状态，同理。因此"在 `__main__` 里设一次"对 fork 出来的 worker 不一定有效，配置要放在每个进程的启动路径上。

## 背诵要点

- 默认 4300 位，限制 `int(s)`/`str(i)` 等**非 2 的幂进制**双向转换；`hex`/`bin`/`int(s,16)` 线性算法不受限。
- 合法值是 0 或 ≥640；0 表示关闭限制，640 是下限，调大只是把 DoS 成本往后推。
- 外部输入先按业务做长度/字符集校验，启动时按业务上限设置，子进程要重新设置。

## 复盘追问

- 为什么攻击者用十进制而不是十六进制打 DoS？（十进制转换超线性，十六进制线性；同样的字节数，十进制解析代价高几个数量级）
- 日志里 `print(huge_int)` 为什么也会抛异常？（`str`/`format` 与 `int()` 共用同一闸门，出口同样受限）
