### Q5089 · int 的内部存储与海量整数内存容量账

难度：★★★☆☆ ｜ 标签：int 内部表示 / 内存容量 / 容量规划

**问**：id 序列化方案把 64 位雪花 ID 当 Python int 缓存了 5000 万个，内存比预估翻倍还多。int 在 CPython 里怎么存的？`sys.getsizeof` 的账怎么算？为什么 `2**64` 和 `2**100` 的开销一样？

**答**：
- **结论**：CPython 的 `PyLongObject` = 对象头 + `ob_digit` 数组，**3.12 起每 digit 存 30 bit**（3.11 及以前 30 bit 位宽、uint16 数组；3.12 改为 uint32 数组仍是 30 bit 有效位）。位数规则：`|v| < 2^30` 一个 digit；`2^30 ≤ |v| < 2^60` 两个 digit，以此类推。所以 `2**64`（2 个 digit）和 `2**100`（4 个 digit）都比小整数大，且 sizeof 按 4 字节对齐取整——`2**63` 与 `2**64` 一样大，因为"位数"按 30 bit 分段而不是按 8 字节直觉。小整数 [-5, 256] 有全局缓存（不朽对象，3.12+ PEP 683），id 方案的大整数享受不到。
- **取舍**：单 int 的账：3.12 下 28 字节（1 digit，含头）起步，每多 30 bit 加 4 字节。64 位雪花 ID 实际 2 digit ≈ 32 字节，再加 dict/list 槽位与指针开销（每条引用 8 字节 + 桶表）。容量敏感时选 `array('q')`（每元素 8 字节，见 Q5054 的账）或 numpy；但注意 array 元素是裸 C 值，**没有对象身份**，不能当 dict key 使用同一语义。
- **实战**：估算口径：`sys.getsizeof(int)` + 引用结构开销；`-X int_max_str_digits` 与 4300 位转换限制（另见 Q5031）说明超大整数的攻防是真实场景。压测时用 `tracemalloc` 校准，别用理论值乘条数就定容量。

```python
"""int 内部存储位数与内存账（Python 3.12：30 bit/digit, uint32 数组）"""
import sys

def bits_of(v): return v.bit_length()

for v in [1, 256, 257, 2**30 - 1, 2**30, 2**60 - 1, 2**60, 2**63, 2**64, 2**100]:
    digits = -(-bits_of(v) // 30)          # 30 bit 一段向上取整（v>0）
    print(f"bit_length={bits_of(v):>4} digits={digits} sizeof={sys.getsizeof(v)}")

print("bool 是 int 子类，True/False 走缓存:", sys.getsizeof(True))
print("小整数缓存: (271,) is not (271,)" , (271,) is not (271,))

# 海量 64 位 ID 的两种存法账本对比
N = 5_000_000
ids = [0x1F2E3D4C5B6A7988 + i for i in range(N)]   # 雪花风格 64 位

t_int = sum(sys.getsizeof(i) for i in ids[:100_000]) / 100_000 * N
print(f"list[int] 纯对象账  ≈ {t_int/1e9:.2f} GB（不含 list 槽位/引用）")
print(f"list 本身槽位       ≈ {sys.getsizeof(ids)/1e9:.2f} GB")

from array import array
arr = array("q", ids)
print(f"array('q')          ≈ {arr.buffer_info()[1] * 8 / 1e9:.2f} GB")
print("array 元素无对象身份:", (arr[0] == ids[0], ids[0] is ids[0]))

# 大整数运算的隐性成本：乘方/进制转换是 O(n^2) 级别（还有 4300 位 str 转换限制）
big = 2**3000
print("3000bit 整数 sizeof:", sys.getsizeof(big), "str 转换受 4300 位限制保护")
```

**追问链**
1. 为什么 3.12 把 digit 数组从 uint16 改成 uint32 但仍保留 30 有效位？
   1. uint32 数组让乘法等内层循环走 SIMD/更好的对齐，同时 30 bit 保证中间积不溢出 32 位、进位逻辑不变——是性能重构而不是语义变更；后果是跨版本 `sys.getsizeof` 的账不可直接对比。
   2. 追问：`int.bit_length()` 与 digit 数有什么关系？——bit_length 决定 digit 数（30 bit 一段），位运算/比较的复杂度都按 digit 数线性，这就是"大整数运算成本 ≈ O(位数)"的来源。
2. `array('q')` 与 `list[int]` 在 dict key、跨进程传输上有什么语义差？
   1. array 元素取出来才装箱成 int 对象，两次取出的值相等但对象身份不同，做 key 没问题（按值 hash）但不能用 `is`；跨进程用 array 可走 pickle 协议 5 的 out-of-band buffer 零拷贝，比逐个 pickle int 便宜一个量级。
   2. 追问：numpy int64 与内置 int 混算的坑？——溢出回绕（内置 int 任意精度）与类型提升规则不同，金融/ID 边界混用要显式转 int。

## 背诵要点
- int = 对象头 + 30 bit/digit 数组（3.12 起 uint32 数组）；位数按 30 bit 分段，sizeof 阶梯 +4B。
- 小整数 [-5,256] 全局缓存且不朽（3.12+ PEP 683）；64 位 ID ≈ 2 digit ≈ 32B 对象账，海量场景换 array('q') 8B/个。
- 跨版本 sizeof 不可直接对比（digit 数组实现变过）；大整数 str 转换有 4300 位限制保护。
