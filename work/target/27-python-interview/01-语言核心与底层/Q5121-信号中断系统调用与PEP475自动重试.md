### Q5121 · 信号中断系统调用与 PEP 475 自动重试

> 难度:★★★★☆ | 标签:事故复盘, signal, 系统调用

**问**:一次生产事故里，加了信号处理器的 Python 进程在阻塞读 socket 时偶发 `InterruptedError`，C 服务同场景却不会报错。PEP 475 给 Python 带来了什么语义？"处理器返回就自动重启"和"处理器抛异常就中断"这两条规则分别如何工作？还有哪些场景不受自动重启保护？

**答**:结论：C 层面被信号打断的系统调用返回 `EINTR`，glibc 的 `SA_RESTART` 只覆盖部分场景，Python 在 PEP 475（3.5 起）做了统一收口——**信号处理器正常返回时，被打断的系统调用自动重试**（且 `time.sleep` 会补足剩余时长），所以"处理器只置标志位"的正确写法下，应用层几乎看不到 `InterruptedError`。取舍：这不是免费的——自动重启意味着**处理器不能依赖"打断阻塞"来改变控制流**；想让阻塞立刻返回，必须让处理器抛异常（异常会在系统调用处重新抛出）或用 self-pipe/`loop.add_signal_handler` 把信号转成事件。实战铁律：a) 处理器只做"置 flag + 写 self-pipe"两件事，复杂逻辑放主循环；b) 仍有漏网场景——`socket.recv` 在**超时+信号**组合、`os.read` 之外的部分 C 扩展、以及 `InterruptedError` 在 `except` 捕获链中显式出现的老代码（3.5 前的兼容写法反而成了死代码），评审时要识别；c) 线程信号只有主线程收（见 Q5583），多线程程序里"信号打断"语义天然残缺。

```python
import os, signal, time, threading

def main():
    r, w = os.pipe()

    # ---- 场景一：处理器只置标志 -> PEP 475 自动重启，阻塞读"感觉不到"信号 ----
    fired = []
    def quiet_handler(signum, frame):
        fired.append(time.perf_counter())

    old = signal.signal(signal.SIGALRM, quiet_handler)
    threading.Thread(target=lambda: (time.sleep(0.15), os.write(w, b"ok")), daemon=True).start()
    signal.setitimer(signal.ITIMER_REAL, 0.05)      # 0.05s 打断正在阻塞的 read
    t0 = time.perf_counter()
    data = os.read(r, 16)                            # 被 SIGALRM 打断 -> EINTR -> 自动重试
    cost = time.perf_counter() - t0
    signal.setitimer(signal.ITIMER_REAL, 0)
    signal.signal(signal.SIGALRM, old)
    print(f"处理器正常返回: 读到 {data!r}, 总耗时 {cost:.2f}s（远大于 0.05s 说明被自动重启）")
    print(f"信号确实触发了 {len(fired)} 次，但未产生任何异常")

    # ---- 场景二：处理器抛异常 -> 中断传播，阻塞点立刻抛出 ----
    def raising_handler(signum, frame):
        raise KeyboardInterrupt("由信号注入的中断")

    signal.signal(signal.SIGALRM, raising_handler)
    signal.setitimer(signal.ITIMER_REAL, 0.05)
    t1 = time.perf_counter()
    try:
        os.read(r, 16)                               # 没有数据，会一直阻塞
        print("不应到达")
    except KeyboardInterrupt as e:
        cost2 = time.perf_counter() - t1
        print(f"处理器抛异常: 约 {cost2:.2f}s 即抛出 KeyboardInterrupt（≈定时器间隔）")
    finally:
        signal.setitimer(signal.ITIMER_REAL, 0)
        signal.signal(signal.SIGALRM, raising_handler)
        os.close(r); os.close(w)

if __name__ == "__main__":
    main()
```

**追问一层**:为什么 PEP 475 要让 `time.sleep` 也"补时"而不是简单重启？（否则信号频繁时 sleep 实际睡的时间被截短，定时逻辑整体漂移——重启语义以"总时长不变"为目标）。
**追问二层**:`asyncio` 程序里信号处理为什么推荐 `loop.add_signal_handler` 而不是 `signal.signal`？（后者处理器在解释器主线程任意字节码边界执行，会和事件循环竞争；前者把信号转成 loop 回调，天然串行且可取消）。
**追问三层**:sigwait/sigmask 与 Python 多线程结合时为什么常"故意屏蔽全部信号"？（把信号统一导向一个用 sigwait 阻塞等待的管理线程，消除主线程任意性）。

## 背诵要点
- PEP 475（3.5）：信号处理器正常返回 → 系统调用自动重试、sleep 补足剩余时间；抛异常 → 阻塞点立刻抛出。
- 处理器只写"置 flag + self-pipe"，复杂逻辑进主循环；asyncio 用 `loop.add_signal_handler`。
- 信号只送达主线程，多线程信号语义残缺；自动重启使"打断阻塞"必须靠抛异常实现。
