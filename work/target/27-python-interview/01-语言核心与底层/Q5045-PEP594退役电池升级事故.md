### Q5045 · PEP 594 退役电池与升级事故复盘

> 难度:★★★ | 标签:PEP 594, 标准库, 版本演进, 升级, 事故复盘

**问**：把服务从 3.10 升到 3.13，`import cgi`、`import imp`、`distutils` 全炸了。PEP 594"退役电池"移除了哪些模块、为什么移除？标准库模块的退役流程是什么？升级前如何把这类炸点一次性扫出来而不是逐个撞？

**答**：PEP 594 把标准库里"历史上收编、如今有更好替代或已僵死"的模块分批移除：3.11 弃用、3.13 移除一大波——`cgi`/`cgitb`（CGI 已死，替代：web 框架的 multipart 解析）、`telnetlib`（替代：第三方 telnetlib3/pexpect）、`imghdr`/`sndhdr`（魔数识别不可靠，替代：filetype 等第三方）、`nntplib`、`msilib`；3.12 移除 `distutils`（被 setuptools 接管，这是打包生态最大的一次搬家）；更早的 `imp`（3.12 移除，替代 `importlib`）。退役流程遵循统一节奏：**文档标记 deprecated → 发 DeprecationWarning → 两个 minor 版本窗口 → 移除**（与 Q5044 的生命周期一致），PEP 594 特殊之处是给每个模块指明了**社区替代品**，所以迁移是"换依赖"不是"重写"。事故复盘根因通常是：CI 只跑新版本安装成功、没跑全量 import 路径；或这些模块在懒加载分支里，主流程测试覆盖不到。系统性扫描三招：1) CI 加全量 `python -W error::DeprecationWarning -c "import 包"` 冒烟；2) 静态扫描 import 表（ast/grep）对照 PEP 594 移除清单；3) 升级前用 3.12/3.13 解释器跑测试套件，让 DeprecationWarning 提前暴露（弃用窗口期就是给你的升级准备期）。

```python
# file: code/01_语言核心与底层/q5045_dead_batteries.py
import importlib
import sys
import warnings

print("python:", sys.version_info[:3])

# PEP 594 移除清单与替代方案(实战核对表)
REMOVED = {
    "cgi":       "Web 框架的 multipart 解析 / email.parser",
    "cgitb":     "traceback 模块 + 自定义 handler",
    "telnetlib": "第三方 telnetlib3 / pexpect",
    "nntplib":   "第三方 (NNTP 已边缘化)",
    "imghdr":    "filetype / python-magic (魔数识别)",
    "sndhdr":    "同上, 按音频格式专用库",
    "imp":       "importlib (3.12 移除)",
    "distutils": "setuptools / sysconfig (3.12 移除)",
}

# 1) 全量 import 冒烟: 模拟升级扫描脚本
def scan_imports(module_names):
    broken = []
    with warnings.catch_warnings(record=True) as w:
        warnings.simplefilter("always")
        for name in module_names:
            try:
                importlib.import_module(name)
            except ModuleNotFoundError:
                broken.append((name, "已移除"))
            except Exception as e:
                broken.append((name, f"导入异常 {type(e).__name__}"))
    return broken, w

broken, warns = scan_imports(list(REMOVED))
print("3.13 上的炸点:", broken or "(无)")

# 2) 从源码 AST 扫描 import, 对照移除清单(升级前静态防线)
import ast
SAMPLE_SRC = "import imp\nimport os\nfrom distutils import util\ncgi_ok = None\n"
tree = ast.parse(SAMPLE_SRC)
hits = set()
for node in ast.walk(tree):
    if isinstance(node, ast.Import):
        hits |= {a.name.split(".")[0] for a in node.names}
    elif isinstance(node, ast.ImportFrom) and node.module:
        hits.add(node.module.split(".")[0])
print("AST 发现的退役模块:", sorted(hits & REMOVED.keys()))

# 3) 弃用期预警: 在 3.11/3.12 上这些模块会发 DeprecationWarning
print("模块数与警告数:", len(REMOVED), "->", len(warns), "(3.13 已移除故无警告)")
```

**追问**：1) 为什么 `distutils` 的移除影响面远大于其他模块？——它被 setup.py 生态与大量库间接 import（`from distutils import util`），且 setuptools 安装顺序（bootstrap）本身依赖它，造成"装 setuptools 之前就炸"的鸡生蛋问题；解法是构建工具链整体切到 pyproject.toml + setuptools>=60。2) `typing` 里也有类似的退役（如 `typing.io`、`typing.re` 3.12 移除）——为什么类型模块退役更激进？——它们是"转发壳"，运行时零依赖、静态工具早已适配，移除不影响运行时 import 主路径。3) 如何防止"退役模块在懒加载分支里漏扫"？——扫描不能只 grep 顶层 import；用覆盖率导向（全量测试 + import 钩子 `sys.meta_path` 记录实际 import 表）或 `modulefinder` 静态展开。

## 背诵要点
- PEP 594：3.13 移除 cgi/cgitb/telnetlib/nntplib/imghdr/sndhdr/msilib，3.12 移除 distutils/imp。
- 退役节奏：弃用 → DeprecationWarning → 两个 minor 版本 → 移除；每模块指明社区替代。
- 升级防线：全量 import 冒烟 + AST 扫描 import 对照清单 + 新解释器提前跑测试吃满弃用窗口。

## 复盘追问
- distutils 移除后你们的构建链是哪一步炸的？（提示：setup.py 里 `from distutils` 与 CI 的"先装 setuptools 再 build"顺序，bootstrap 鸡生蛋）
- 设计一个"标准库升级兼容门禁"：每次新解释器发布，门禁应该跑哪三件事？（提示：import 冒烟、弃用告警清零、替换清单核对）
