### Q5046 · re 模块编译缓存的容量账

> 难度:★★★ | 标签:re, 缓存, 容量规划, 成本工程

**问**：`re.match(pattern, ...)` 每次调用都编译正则吗？`re` 模块的内部缓存容量是多少、满了会怎样？动态拼接 pattern（比如按租户 ID 拼正则）的服务为什么会出现"缓存全灭 + CPU 飙升"？容量账怎么算？

**答**：`re` 模块用 `_cache`（一个 dict，**上限 512 条**）缓存编译产物：`re.match` 每次调用先查缓存，未命中才走 `sre_compile`（正则编译是几百微秒级，远贵于匹配本身）。关键坑：3.12 之前 `_cache` 是**简单 dict、无淘汰策略**——超过 512 条时执行 `_cache.clear()` **整表清空**（3.12 起改为 LRU 式逐条淘汰，但 512 上限不变）。所以"按租户/按用户动态拼 pattern"的服务，pattern 基数一旦超过 512，缓存命中率从 100% 跌到接近 0，且 3.12 前还会整表清空导致集体回编译——CPU 飙升事故的经典根因。容量账：**pattern 基数 × 单条编译成本** 决定缓存收益；基数不可控时，绕过模块缓存的唯一正路是**自己持有 `re.compile` 产物**（Pattern 对象本身就是最好的缓存单元，可放 LRU/连接上下文里），或收敛 pattern（参数化正则、用 `str.startswith` 等字符串方法替代）。另一个成本项：编译产物还包含反斜杠转义后的子模式展开，复杂 pattern 编译内存也不小，但相对 CPU 成本通常可忽略。

```python
# file: code/01_语言核心与底层/q5046_re_cache.py
import re
import time
import sys

print("python:", sys.version_info[:3])

# 1) 确认缓存存在: 重复编译同一 pattern, 命中缓存后耗时骤降
p = r"^(a|b)+-\d{4}$"
re.match(p, "abc-1234")                    # 第一次: 触发编译进 _cache
print("缓存条数(含其他):", len(re._cache))

t0 = time.perf_counter()
for _ in range(100_000):
    re.match(p, "abc-1234")                # 全部命中缓存
print(f"命中缓存 10 万次: {(time.perf_counter()-t0)*1000:.0f} ms")

# 2) 缓存击穿: 让 pattern 基数超过 512, 观察 3.12 前的整表清空行为
before = dict(re._cache)                    # 记下已有条目
for i in range(600):
    re.match(rf"tenant-{i}-\d+", f"tenant-{i}-42")
after = dict(re._cache)
survived = sum(1 for k in before if k in after)
print(f"塞入 600 个动态 pattern 后: 缓存 {len(after)} 条 | 原有条目存活 {survived}")
print("上限说明: 512 (3.12 前超限整表 clear, 3.12+ 逐条淘汰)")

# 3) 复盘修复: 自己持有编译产物, 基数再大也不走模块缓存
compiled = re.compile(p)
t0 = time.perf_counter()
for _ in range(100_000):
    compiled.match("abc-1234")
print(f"持有 Pattern 对象 10 万次: {(time.perf_counter()-t0)*1000:.0f} ms (无缓存查找)")

# 4) 成本账: 编译 vs 匹配的单价差
t0 = time.perf_counter()
for i in range(1000):
    re.compile(rf"one-off-{i}-[a-z]+")     # 每次都真编译
compile_ms = (time.perf_counter() - t0) / 1000 * 1e6
t0 = time.perf_counter()
for _ in range(1000):
    compiled.match("abc-1234")
match_us = (time.perf_counter() - t0) / 1000 * 1e6
print(f"单次编译 ≈ {compile_ms:.0f} us | 单次匹配 ≈ {match_us:.1f} us (差 {compile_ms/max(match_us,0.1):.0f} 倍)")
```

**追问**：1) 为什么 `re` 不用 `functools.lru_cache` 而是自己维护 `_cache`？——缓存键是 (pattern, flags) 元组但value 是编译产物，且早期实现早于 functools 生态；自己维护还允许在 3.12 做 `re._cache` 的逐条淘汰（兼容老行为是 `lru_cache` 做不到的整表 clear 语义变更）。2) Pattern 对象的线程安全性？——`Pattern` 与 `Match` 的匹配操作是无状态的，多线程共享同一编译产物安全（Q5002 的自由线程语义下同样成立），这使"预编译注册表"可以全局共享。3) 动态正则除了缓存问题还有什么更严重的风险？——把用户输入拼进 pattern = 注入面 + 回溯爆炸（Q2626），正确做法是把动态部分作为**数据**用 `re.escape` 转义、固定部分作为 pattern。

## 背诵要点
- `re._cache` 上限 512；3.12 前超限整表 clear，3.12+ 改逐条淘汰；编译单价是匹配的百倍以上。
- pattern 基数 > 512（动态拼接）→ 缓存全灭 + CPU 事故；修复 = 自己持有 re.compile 产物。
- 用户输入拼 pattern 必须 re.escape：防注入与回溯爆炸（Q2626）。

- 如果动态 pattern 的基数天生就巨大（每请求一个），除了预编译还有哪些路线？（提示：改字符串前缀匹配、trie，或把匹配下沉到固定 pattern + 捕获组）
