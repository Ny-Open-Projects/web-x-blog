### Q5242 · 装饰器堆叠顺序：def 时求值、自底向上包装与元数据链

难度：P6 ｜ 标签：装饰器堆叠、执行顺序、def 求值时机、functools.wraps、元数据链、__wrapped__、参数化装饰器

**问**：三个装饰器堆叠 `@A @B @C` 时包装顺序与调用顺序分别是什么？为什么装饰器代码在 `def` 时就执行而非调用时？参数化装饰器 `@deco(args)` 与 `@deco` 的三重嵌套结构里，每一层各执行几次？堆叠链上漏写 `functools.wraps` 的元数据损失会怎么放大？

**答**：
结论：堆叠求值规则是"**执行自底向上、包裹自内向外**"：`@A`、`@B`、`@C` 依次写在函数上方，Python 先取原始函数交给最靠近 def 的 `C` 包装，再拿 `C` 的结果交给 `B`，最后交给 `A`——所以**装饰器副作用日志顺序是 C→B→A**，而**调用时最外层 `A` 的 wrapper 先跑**（A(before)→B(before)→C(before)→原函数→C(after)→B(after)→A(after)）。第二个关键事实：**装饰器在 def 语句执行时运行**（模块导入时），不是函数调用时——`@trace("C")` 的 `trace("C")` 部分在 def 那一刻求值出装饰器对象，包装动作也立刻完成；这意味着装饰器里做重量级工作（注册路由、扫描签名、预热表）是"导入时间成本"，导入慢或装饰器抛错都会让整个模块不可用。参数化装饰器的三重结构里各层执行频次：工厂 `deco(args)` **每次被装饰执行一次**（def 时）、内层装饰器函数执行一次（def 时）、wrapper **每次调用执行一次**——把"每函数一次"的昂贵计算（编译正则、构建映射表）放在外两层闭包里缓存，是装饰器性能纪律。元数据链：漏 `functools.wraps` 时 wrapper 的 `__name__/__doc__/__module__/__qualname__/__wrapped__` 全部丢失，堆叠三层后 `help()` 与 introspection（inspect.signature、调试器、序列化层按函数名路由）拿到的是 `wrapper`——链条上**任何一层**漏 wraps，向上所有层看到的就是断点（Q2088 实测过缺席后果）。

取舍：a) 堆叠顺序即行为顺序：`@retry` 应在 `@timeout` 外层还是内层——外层 retry 包 timeout 则每次重试都有完整超时；内层则总预算由 retry 控制——**顺序是语义的一部分，不是风格**；`@cache` 与 `@validate` 堆叠时，validate 在内层则缓存命中的输入必已校验，顺序错了缓存会绕过校验；b) 参数化装饰器要不要写成双态（`@deco` 与 `@deco()` 通吃）：兼容写法增加复杂度，团队内统一一种形态更划算；c) 类实现装饰器（`__call__` + 显式 `__get__` 或不用闭包）vs 闭包：闭包够用，需要在 wrapper 上挂状态又怕闭包不可见时用类；d) 注册器模式（装饰器收集函数进表）要在 def 时副作用最小化——只做登记，不做 IO（Q442）；e) 调试入口：`wrapper.__wrapped__` 一路 `functools.unwrap` 可穿透到原函数，堆叠链排查靠它。

实战：事故形态是"限流装饰器在 `@auth` 外层，未登录流量也消耗限流配额，攻击者用垃圾 token 打满配额导致正常用户 429——修复为交换堆叠顺序让 `@auth` 在最外层先跑；顺带补齐三层装饰器的 functools.wraps，之前日志层拿到的函数名全是 wrapper，按名采样统计全串了"。下面实测堆叠求值顺序、调用顺序与元数据链。

```python
# 装饰器堆叠: def 时求值、自底向上包装、wraps 元数据链
import functools

def make(name: str) -> "装饰器工厂":
    def deco(fn):
        print(f"[def 时] 包装 {fn.__name__} <- {name}")   # def 执行时输出
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            print(f"[调用] {name} before")
            result = fn(*args, **kwargs)
            print(f"[调用] {name} after")
            return result
        return wrapper
    return deco

@make("A")
@make("B")
@make("C")
def work(x: int) -> int:
    """原始 docstring"""
    return x * 2
# 上方三行 def 已触发输出: C 先包(最靠 def), 再 B, 再 A

print("--- 调用阶段 ---")
print("work(21) =", work(21), "(A 的 wrapper 在最外层, 先跑 A)")

print("--- 元数据链 ---")
print("__name__ =", work.__name__, "| __doc__ =", work.__doc__)
print("__wrapped__ 一路穿透:", work.__wrapped__.__wrapped__.__name__)

print("--- 对照: 漏 wraps 的断点 ---")
def bare(fn):
    def wrapper(*args, **kwargs):        # 没有 @functools.wraps
        return fn(*args, **kwargs)
    return wrapper

@bare
def real_fn():
    pass
print("漏 wraps: __name__ =", real_fn.__name__, "(元数据在这里断掉)")

print("--- 参数化装饰器的三层执行频次 ---")
def route(prefix: str):                       # 工厂: 每次被装饰执行一次 (def 时)
    table = {"compiled": prefix.upper()}      # 昂贵计算放这里, 每函数一次
    def deco(fn):                             # 装饰器: 每函数一次 (def 时)
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):         # wrapper: 每次调用一次
            return (table["compiled"], fn(*args, **kwargs))
        return wrapper
    return deco

@route("/api")
def handler():
    return "ok"
print("handler() =", handler(), "| 再调一次共享同一闭包表:", handler() == handler())
print("[rule ] 堆叠=自底向上包装; 顺序即语义; wraps 是元数据链的通行证")
```

**追问一**：`@cache` 与 `@validate`（校验装饰器）堆叠时顺序错会出什么真实事故？推导一下两种顺序的行为差异。—— 设代码写成 `@cache`（外）`@validate`（内）：调用先命中缓存——**校验根本不执行**，因为缓存的 key 由 wrapper 收到的原始参数决定，validate 的 wrapper 在 cache 的 wrapper 内层，只有 cache 未命中才轮到它；若 validate 会做规范化（如 `"  ABC " -> "ABC"`、类型收窄），缓存里存的可能是"未规范化输入 → 结果"的多份冗余条目（同一业务值因空白差异被当成不同 key），还会把本应被拒的非法输入与合法输入**共用同一缓存键**（规范化后恰好同值），污染扩散。正确顺序是 `@validate`（外）`@cache`（内）：先校验规范化、再以规范形态查缓存，命中必是合法输入的结果。推导口径：**调用顺序=堆叠列表从上到下（外层先跑）**，把"必须先发生的事"放在列表更上方即可；每次堆叠都自问一遍"外层的输出会不会绕过内层的假设"。

**追问二**：为什么"装饰器在 def 时执行"会导致导入期事故？工程上怎么把导入成本与运行成本分开？—— def 语句执行 = 装饰器立刻运行，所以装饰器里的异常会让**模块导入失败**（整个应用起不来），装饰器里的慢 IO（扫目录、连注册中心、编译大正则）会算进启动时间——灰度发布时"新实例导入卡住"的经典事故就来自这里（Q1920 预热期判据的隐形成本）。工程纪律：①装饰器只做**纯计算与登记**（签名解析、构建闭包表），重 IO 延迟到首次调用（懒初始化 + 双检锁，Q1572）或 lifespan 启动钩子（Q6161）；②注册类装饰器（路由表、插件表）在 def 时只 append，真正的构建（排序、校验重复）放在应用启动阶段统一做，错误能集中报告；③测试策略：导入期行为要用"模块导入冒烟测试"单独覆盖——普通单元测试 fixture 导入一次通过，不代表导入顺序敏感的模块全绿。原则：**def 时只花钱买元信息，运行时才花时间做业务**。

## 背诵要点
- 堆叠求值：自底向上包装（最靠 def 的先包）、调用自上而下执行（最外层 wrapper 先跑）；装饰器在 def 语句时执行，副作用是导入时间成本。
- 参数化装饰器三层频次：工厂与装饰器层每函数一次（def 时）、wrapper 每次调用一次——昂贵计算放闭包外两层。
- functools.wraps 是元数据链通行证：链上任何一层漏写，向上全是 wrapper；排查用 __wrapped__/functools.unwrap 穿透。

## 复盘追问
- @retry 和 @timeout 谁在外层？推导行为差异。（外层先跑：retry 在外=每次重试带独立超时；timeout 在外=总预算死磕一次，顺序是语义不是风格）
- 为什么装饰器里不能做 IO？（def 时即执行，IO 异常导致模块导入失败、慢 IO 拖垮启动；只做纯计算与登记，重活延到懒初始化或 lifespan）
