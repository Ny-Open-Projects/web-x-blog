### Q5063 · 热循环微优化成本账：属性查找与局部变量

> 难度:★★★★ | 标签:成本工程, 字节码, 微优化, 热路径

**问**：一段每秒调用十万次的热循环，同事把 `obj.method()` 提出循环外、把全局函数绑成局部变量，P95 降了 15%。这些优化的字节码原理是什么？哪些微优化在 3.11+ 已经失效？什么时候该做、什么时候不该做？

**答**：结论：每条字节码指令都有成本，微优化本质是**减少指令数与查找深度**。四个经典手段的字节码账：a) **全局函数绑成局部变量**：`LOAD_GLOBAL` 要查全局 dict（3.11 后有内联缓存但仍比 `LOAD_FAST` 慢），循环前 `f = len` 一次，循环内 `LOAD_FAST` 是栈槽直接索引；b) **属性查找提出循环**：`obj.append` 每次走 `LOAD_ATTR`（实例 dict → 类 → MRO，即使有自适应特化也有缓存查找成本），`append = obj.append` 绑定方法提出来；c) **方法绑定**：每次 `obj.m()` 都创建 bound method 对象（一次分配），预绑定省掉；d) **`x < y` vs 比较+分支减少**：用 min/max/tuple 比较把逻辑下沉到 C。**3.11+ 失效清单**：PEP 659 自适应特化让 LOAD_GLOBAL/LOAD_ATTR 有 inline cache，BINARY_OP 特化后很多老技巧收益缩水到 <5%；3.13 JIT 进一步吃掉微优化空间。决策原则：先 cProfile/perf 确认热点占比，**单点收益 <5% 且伤可读性就不做**；真正的大头永远是算法复杂度、IO 批量化、少分配对象。实战：把"热循环绑定局部变量"当团队 style 可接受，把"用 += 拼 int 换位运算"这类黑魔法禁掉。

```python
# file: code/01_语言核心与底层/q5063_hot_loop_cost.py
import timeit, sys

data = list(range(10_000))

def v_naive(xs):
    total = 0
    for x in xs:
        total = total + x      # 每次重解析 BINARY_OP
    return total

def v_bound(xs):
    total = 0
    for x in xs:
        total += x             # INPLACE_ADD 少一次名字绑定
    return total

def v_local(xs, _sum=sum):     # 全局函数绑成局部默认参数
    return _sum(xs)            # 下沉到 C, 通常最快

def v_attr(xs):
    out = []
    ap = out.append            # LOAD_ATTR 提出循环, 省每次 MRO 查找
    for x in xs:
        ap(x * 2)
    return out

def v_attr_naive(xs):
    out = []
    for x in xs:
        out.append(x * 2)      # 每次 LOAD_ATTR + bound method 分配
    return out

for name, fn in [("naive_add", v_naive), ("inplace", v_bound),
                 ("builtin_sum", v_local), ("append_bound", v_attr),
                 ("append_naive", v_attr_naive)]:
    t = min(timeit.repeat(lambda: fn(data), number=100, repeat=3))
    print(f"{name:14s} {t*10:6.2f} ms/100runs")

# 字节码对比: LOAD_GLOBAL vs LOAD_FAST
import dis
print("--- 全局查找 ---")
dis.dis(compile("len(data)", "<t>", "eval"))
print("--- 局部槽查找 ---")
def f():
    data = []
    list(data)
dis.dis(f)

print("结论: 3.11+ 自适应特化后差距收窄, 先测占比再动手")
print("python:", sys.version_info[:2])
```

**追问**：1) 为什么 `sum(xs)` 比手写循环快不止指令数？——循环主体下沉到 C，Python 层只剩一次调用，省掉每元素的字节码派发（这是"数量级"优化，与 5% 微优化是两档）。2) `LOAD_ATTR` 的 inline cache 在 3.11 怎么工作？——字节码后跟缓存槽记录类型版本号与 dict 偏移，命中免查 MRO；多态调用点（同一行喂多种类型）会退化并触发特化失效，这也是"热循环里保持类型单一"的理论依据。3) 默认参数绑定 `_sum=sum` 有什么坑？——绑定发生在 def 时，若模块内有 monkeypatch len/sum 会绕过；且对读者像魔法，评审成本高，团队要写进 style 注释。

## 背诵要点
- 微优化字节码账：LOAD_GLOBAL/LOAD_ATTR 有查找成本，循环外绑定成局部（LOAD_FAST 栈槽）省查找与 bound method 分配。
- 3.11+ PEP 659 inline cache 与 3.13 JIT 吃掉大部分微优化收益（<5%），先 cProfile 定占比，收益小且伤可读性不做。
- 两个数量级的真优化：算法复杂度、主体下沉到 C（sum/sort/join），微优化只做锦上添花。
