### Q5264 · 自定义编解码错误处理器：codecs.register_error 的返回契约

难度：P6 ｜ 标签：codecs、register_error、surrogateescape、UnicodeDecodeError、数据丢失

基线：CPython 3.12.2，纯标准库；注册自定义 decode/encode 错误处理器，观察调用次数、返回元组与非法替换的后果。

**问**：CSV 导入用 `data.decode("utf-8", errors="ignore")` 处理历史脏数据，结果 3 万行里 412 行的客户名变成空串，业务方以为是"客户没填名字"，对账时才发现是编码问题。后来改成自定义 handler，把坏字节记成 `<ff>` 并计数，但第一次写成了返回 `bytes`，整个导入直接 `TypeError`；另一次 encode 时返回了一个目标编码不支持的字符，处理器被反复调用，最后抛的还是原始 `UnicodeEncodeError`。错误处理器的返回契约到底是什么？decode 和 encode 有区别吗？

**答**：

- **结论**：`codecs.register_error(name, handler)` 注册的 handler 接收一个异常对象（`UnicodeDecodeError` 或 `UnicodeEncodeError`），必须返回二元组 `(replacement, new_position)`。对 decode：`replacement` 必须是 **`str`**，`new_position` 是原 `bytes` 中"下一个待处理字节"的下标（通常取 `exc.end`）；对 encode：`replacement` 也必须是 **`str`**，且这个 `str` 必须能被目标编码器编码，否则会再次触发错误处理器，形成"处理器处理自己的替换结果"的循环，最终仍抛原始异常。handler 的 `exc.object` 是原始输入（decode 时是 bytes，encode 时是 str），`exc.start/exc.end` 标出出错区间；`ascii` 这类单字节编码会**逐字节**调用，`utf-8` 则可能一次覆盖一个多字节序列。
- **取舍**：`errors="ignore"` 最省事但**静默丢数据**，且不留下位置；`errors="replace"` 用 `�` 占位，能看出有问题但无法还原原始字节；`surrogateescape` 把非法字节映射到 `U+DC80..U+DCFF`，可以无损 round-trip 回原 bytes，代价是得到的 `str` **不是合法 UTF-8**，一旦写进 JSON 或数据库就会炸；自定义 handler 最灵活（可计数、可映射 cp1252、可保留十六进制），但每个错误一次 Python 调用，脏数据比例高时成本明显。生产上应该"先检测、再决策"：用 `errors="strict"` 快速失败并采样，确认脏数据分布后再选 `surrogateescape`（需要 round-trip）或自定义映射（需要可读性），不要一上来就 `ignore`。
- **实战**：事故 CSV 是 Windows 导出的 cp1252，`0x80-0x9f` 区间被 UTF-8 判为非法。修复：① 先按行 `strict` 解码，捕获 `UnicodeDecodeError` 记录行号与字节；② 对确认是 cp1252 的文件整体 `decode("cp1252")`，而不是逐字节打补丁；③ 对混合编码的历史文件，用自定义 handler 把坏字节转成 `<0xNN>` 并累加计数器，导入报告里输出"修复 412 处"，让业务方可见。上线后空名字归零，导入耗时从 8.2s 增到 9.1s（多了一次扫描），可接受。

下面验证 decode handler 的逐字节调用与返回下标、encode handler 的"替换必须可编码"约束、以及 `surrogateescape` 的无损 round-trip 与非 UTF-8 属性。

```python
# 自定义错误处理器: decode 返回 str + 新位置; encode 的替换必须能被目标编码器编码
import codecs

decode_calls = []


def hex_decode_handler(exc):
    chunk = exc.object[exc.start:exc.end]
    decode_calls.append((exc.start, exc.end, chunk))
    return (f"<{chunk.hex()}>", exc.end)


codecs.register_error("hexdump", hex_decode_handler)

raw = b"ok\xff\xfeend"
text = raw.decode("ascii", "hexdump")
print("[1] 解码结果:", text)
print("[2] handler 调用:", decode_calls)
assert text == "ok<ff><fe>end"
assert len(decode_calls) == 2, "ascii 是单字节编码, 每个坏字节调用一次"
assert decode_calls[0][:2] == (2, 3) and decode_calls[1][:2] == (3, 4)


def unicode_escape_handler(exc):
    ch = exc.object[exc.start:exc.end][0]
    return (f"<U+{ord(ch):04X}>", exc.end)


codecs.register_error("unicode_escape", unicode_escape_handler)

encoded = "café".encode("ascii", "unicode_escape")
print("[3] 编码结果:", encoded)
assert encoded == b"caf<U+00E9>"


def bad_encode_handler(exc):
    # 替换成 é 本身: ascii 仍然编不出来, 处理器会被再次调用/最终失败
    return ("é", exc.end)


codecs.register_error("bad_encode", bad_encode_handler)
try:
    "café".encode("ascii", "bad_encode")
    raise AssertionError("替换字符不可编码时本应失败")
except UnicodeEncodeError as exc:
    print("[4] 非法替换 -> 仍抛原始异常:", exc.reason)

# surrogateescape: 可无损 round-trip, 但不是合法 UTF-8
surrogate_text = b"a\xffb".decode("ascii", "surrogateescape")
restored = surrogate_text.encode("ascii", "surrogateescape")
print("[5] surrogateescape round-trip:", repr(surrogate_text), restored)
assert restored == b"a\xffb"
try:
    surrogate_text.encode("utf-8")
    raise AssertionError("surrogate 不应能直接编码成 UTF-8")
except UnicodeEncodeError:
    print("[6] surrogate 写入 UTF-8 -> UnicodeEncodeError（必须显式处理）")
```

**追问一**：`new_position` 为什么不能随便返回 `exc.start + 1`？—— 对多字节编码，`exc.start/end` 覆盖的是一个完整非法序列；如果你只前进 1 字节，剩余字节会被当成新的错误继续处理，日志里会出现大量碎片，甚至把合法的后续字节拆坏。正确做法是返回 `exc.end`（跳过整个非法区间），除非你的处理器确实想逐字节重扫。对 encode 同理，`new_position` 是原 `str` 的下标，不是输出 bytes 的下标。

**追问二**：`surrogateescape` 和 `surrogatepass` 有什么区别？—— `surrogateescape` 处理的是**解码时遇到的非法字节**，把 `0x80-0xFF` 映射到 `U+DC80-U+DCFF`，只用于 `utf-8`/`ascii` 等，编码时再映射回原字节；`surrogatepass` 处理的是**本来就包含代理对（`U+D800-U+DFFF`）的字符串**，允许它们通过 UTF-8 编解码（得到 CESU-8 风格的字节），常用于需要保留非法 Unicode 的协议。两者都产出"不是标准 UTF-8"的结果，不能直接塞进 JSON；JSON 序列化前必须清洗或改用 Base64。

## 背诵要点

- handler 返回 `(replacement, new_position)`；decode/encode 的 `replacement` 都必须是 `str`，encode 的替换还必须能被目标编码器编码。
- `exc.object/start/end` 给出原始输入与出错区间；`ascii` 逐字节调用，多字节编码按序列调用，恢复时用 `exc.end` 跳过整个区间。
- `ignore` 静默丢数据、`replace` 丢原始字节、`surrogateescape` 可 round-trip 但不是合法 UTF-8；先检测再选策略。

## 复盘追问

- 自定义 handler 返回的替换串里又包含目标编码不支持的字符，会发生什么？（再次触发 handler，可能循环，最终仍抛原始异常）
- 为什么 `surrogateescape` 的结果不能直接 `json.dumps`？（JSON 要求合法 Unicode，代理码点编码 UTF-8 会抛 `UnicodeEncodeError`）
