### Q5255 · dict 合并运算符 | 与 |=：PEP 584 语义、update 差异与 ChainMap 分工

难度：P5 ｜ 标签：dict、PEP584、合并运算符、|=、update、ChainMap、浅合并、覆盖优先级、求值顺序

**问**：3.9 的 `d1 | d2` 与 `d1.update(d2)`、`{**d1, **d2}` 各差在哪——优先级方向、是否原地、返回值、类型宽进怎么比？为什么 `d1.update(d2)` 不能写成 `d = d1.update(d2)`？`|=` 与 `|` 的类型要求为什么不一样？动态多层配置为什么该用 ChainMap 而不是反复 `|`？嵌套 dict 的"深合并"`|` 为什么做不了？

**答**：
结论：PEP 584 给 dict 补上 `|`（合并产生**新 dict**）与 `|=`（**原地**合并），四个维度分清：①**优先级**——`d1 | d2` **右侧赢**（重复键取 d2 的值），`ChainMap` 是**前面赢**（第一个映射优先）——两个"合并"直觉相反，读别人代码时这是头号误读点；②**是否原地**——`|` 不动两侧、返回新对象（可链式 `a | b | c`，从左到右求值，右侧永远赢）；`|=` 与 `update` 等价（原地改、返回 None）——`d = d1.update(d2)` 这个经典 bug 就是把 None 赋给变量，`update` 有返回值但不是 dict；③**类型宽进**——`|` 要求**两侧都是 dict**（`d | [("k",1)]` 直接 TypeError，因为位运算符协议按类型分派）；`|=` 对齐 `update` 的宽进（接受任意键值对可迭代：键值列表、关键字参数都能吃）——所以 `|` 更严格、`|=` 更宽容，这个不对称是刻意的（PEP 584 的设计权衡：`|` 模仿集合运算的类型纪律，`|=` 模仿 update 的既有契约）；④**快照 vs 视图**——`|`/`{**a, **b}` 是**一次性拷贝快照**，ChainMap 是**零拷贝动态视图**（底层 dict 改动即时可见，查找顺序按映射列表从前往后）——配置分层（默认值 + 环境变量 + 命令行）反复 `|` 会产生多份快照且丢失"层级可变性"，ChainMap 一次组装、逐层覆盖、底层改动自动生效。**深合并的边界**：`|` 是浅合并——嵌套 dict 的同键是"整体覆盖"而非"递归合并"（`{"cfg": {"a":1}} | {"cfg": {"b":3}}` 得 `{"cfg": {"b":3}}`，a 字段静默丢失），PEP 584 明确不做深合并（深合并语义不唯一：列表拼接还是覆盖？None 算显式清空还是跳过？），需要深合并要自己写递归函数或用工具库。

取舍：a) 可读性收益：`d1 | d2` 比 `{**d1, **d2}` 表意更直接（"合并"语义 vs "解包拼装"），与 set 的 `|` 心智一致；代价是与 `update` 的"右侧赢"vs ChainMap 的"左侧赢"共存，团队要统一约定；b) 性能：`|` 与 `{**a, **b}` 同量级（都要建新 dict），原地 `|=` 避免拷贝（大 dict 热路径用 `|=`/update）；ChainMap 的查找是逐层穿透（命中第一层即停），层多时单次查找 O(层数)，但免拷贝的收益通常远超；c) 深合并的自研纪律：递归合并函数要定义清楚边界（嵌套 dict 递归、列表/标量覆盖、None 是覆盖还是清空）并写进文档——"看起来对"的深合并最常见的坑就是 None 语义（上层传 None 想清空配置项，深合并却跳过了它）；d) dataclass/Pydantic 场景：模型配置合并优先用构造器参数而不是 dict 合并（类型校验在构造期兜住）。

实战：事故形态是"配置中心客户端用 `defaults | env | cmdline` 组装配置，后来有人把 cmdline 改成动态重读（热更配置 Q707 类需求），`|` 的快照在启动时固化——热更后新 cmdline 值永远不生效，排查半天发现是'合并了三次的快照'；换成 ChainMap(defaults, env, cmdline) 后动态生效，但踩了第二个坑：ChainMap 是'前面赢'，把层级顺序写反导致生产模式被 dev 覆盖"。修复为：热更需求一律 ChainMap + 层级顺序单测固定，快照合并只用于启动期一次性装配。下面实测四个维度的差异与 ChainMap 分工。

```python
# dict 合并运算符 | 与 |= (PEP 584): 与 update/{**a,**b}/ChainMap 的边界
print("[1] | 产生新 dict, 右侧优先覆盖")
d1 = {"a": 1, "b": 2}
d2 = {"b": 20, "c": 30}
merged = d1 | d2
print("    d1 | d2 =", merged, "| 原对象未动:", d1["b"] == 2 and "c" not in d1)

print("[2] |= 原地合并, 等价 update, 返回 None 的 update 不能链式")
d3 = {"x": 1}
ret = d3.update({"y": 2})
print("    update 返回:", ret, "(None, 不能 d = d1.update(...))")
d3 |= {"z": 3}
print("    d3 |= 后 =", d3)

print("[3] | 要求两侧都是 dict: 与 {**a, **b} 的宽进差异")
try:
    d1 | [("k", 1)]
except TypeError as e:
    print("    d1 | [(k,1)] -> TypeError:", e)
from_pairs = dict(d1) | dict([("k", 1)])
kw = {**d1, **{"k": 1}}
print("    显式转换后 |:", from_pairs, "| {**d1, **kv}:", kw)

print("[4] |= 更宽: 接受任意键值可迭代 (对齐 update)")
d4 = {"a": 1}
d4 |= [("b", 2), ("c", 3)]                  # |= 接受键值对列表, | 不行
print("    d4 |= [(b,2),(c,3)] =", d4)

print("[5] 链式合并的求值顺序: 从左到右, 右侧永远赢")
d5 = {"k": "L1"} | {"k": "L2"} | {"k": "L3"}
print("    L1|L2|L3 的 k =", d5["k"])

print("[6] ChainMap 对比: 不拷贝、动态视图、优先级在前")
from collections import ChainMap
base = {"mode": "prod", "region": "cn"}
over = {"mode": "dev"}
cm = ChainMap(over, base)                   # 第一个映射优先
print("    cm['mode'] =", cm["mode"], "(前面赢, 与 | 的后面赢相反)")
base["extra"] = "auto"
print("    修改 base 后 cm['extra'] =", cm["extra"], "(动态视图, | 是快照)")

print("[7] 递归合并: | 是浅合并, 嵌套 dict 直接整体覆盖")
a = {"cfg": {"a": 1, "b": 2}}
b = {"cfg": {"b": 3}}
print("    a | b =", a | b, "(嵌套字段 a 被覆盖丢失, 深合并要自己写)")
print("[rule ] | 新对象右侧赢; |= 原地且可接键值对; update 返回 None; 动态优先级用 ChainMap; 嵌套深合并手工写")
```

**追问一**：为什么 PEP 584 把 `|` 设计成"右侧赢"、和 set 的 `|`（并集对称）在语义上怎么对齐？`+` 为什么被否决？—— PEP 584 的论证：dict 的键是"值集合"，值是"附着载荷"——`|` 对齐 set 的并集语义（键的并集），重复键的值归属选择"后来者赢"，与 `update` 既有行为一致（向后兼容压倒一切：如果 `|` 是"先者赢"，同一个表达式在 `update` 与 `|` 之间就有两套优先级，比方向选择本身更伤）。`+` 被否决的理由：dict 的"加法"语义不明确（是 concatenate？merge？），且与 list 的 `+`（顺序拼接、允许重复）冲突——dict 键唯一，拼接语义对不上；`|` 的集合心智（"两个键集合的并"）最贴切。`|=` 同理对齐 set 的 `|=`（原地并）同时兼容 update 参数形态。面试口径：知道"右侧赢、与 update 一致"是 P5；能复述 PEP 584 否决 `+` 的论据与"对齐 set 语义"的设计逻辑是 P6。

**追问二**：深合并的正确实现要注意哪些边界？为什么标准库不提供 deep_merge？—— 边界清单：①**None 语义**——上层传 None 是"跳过"还是"显式清空"？两派都要，函数签名给参数（如 `none_clears=False`）并文档化；②**列表策略**——拼接、去重拼接、按索引覆盖、整体覆盖，四种都合理，默认"整体覆盖"最不出意外；③**类型不一致**——一侧是 dict 一侧是标量，递归会 AttributeError，要在入口类型检查后整体覆盖；④**循环引用**——自引用 dict 深合并会无限递归，加深度上限或引用集合；⑤**不可变源**——合并过程不得写穿源 dict（先 copy 再递归）。标准库不提供的原因：语义不唯一（上面每一条都有多个"正确"答案），一旦内置就固化为"官方语义"，错的那一半场景会变成事故——与 `pathlib` 这种语义明确的 API 不同，深合并是**策略问题**不是机制问题，留白是设计决策。工程形态：配置合并用 ChainMap（分层不深合并）优先于深合并；真需要深合并时固定一份团队实现 + 单测锁死五个边界行为，禁止各处手写递归合并。

## 背诵要点
- `|` 产生新 dict 且**右侧赢**（与 update 一致、与 ChainMap 的"前面赢"相反）；`|=` 原地合并且接受键值对可迭代；`update` 返回 None（`d = d.update(...)` 是经典 bug）。
- `|` 两侧必须都是 dict（TypeError），`{**a, **b}` 宽进任意 mapping；动态分层配置用 ChainMap（零拷贝动态视图），快照合并只用于启动期。
- `|` 是浅合并，嵌套 dict 整体覆盖；标准库不做深合并是语义不唯一的刻意留白，自研深合并要锁死 None/列表/类型不一致/循环/不可变五边界。

## 复盘追问
- `|` 与 ChainMap 的优先级方向为什么相反、各适合什么场景？（`|` 对齐 update 的右侧赢做一次性快照合并；ChainMap 对齐"默认值被高层覆盖"做动态分层视图，热更配置必须 ChainMap）
- 为什么 `|` 收 TypeError 而 `|=` 接受键值列表？（`|` 对齐 set 位运算的类型纪律；`|=` 对齐 update 既有契约的宽进——PEP 584 的刻意不对称）
