### Q5147 · 生成器半途异常与部分写入事故

难度：P6 ｜ 标签：生成器、惰性求值、异常时序、数据一致性

**问**：数据管道把"校验 + 写库"改成生成器链做惰性处理，上线后 DB 里出现一半成功一半失败的事务碎片，而上游以为整批失败了。生成器的惰性求值如何改变异常的**时序与可见性**？怎么设计才能既省内存又不产生半成品？

**答**：
结论：生成器把"取数"变成"拉取时逐步执行"，三个事故根源：① **异常延迟**——构造生成器不执行任何代码，坏数据/网络错误的异常在消费端第一次 `next()` 时才爆，调用方常在 try 块外层构造、里层消费，根本没包住；② **半途中断**——消费循环跑到一半抛异常，之前已写入的行不会自动回滚，除非消费方自己包事务；③ **停止语义**——生成器被 GC 提前关闭时在挂起处抛 `GeneratorExit`，cleanup 逻辑若以为会继续 yield 就会出错。

取舍：惰性省内存 vs 一次性全量拿结果的事务原子性。解法是**把事务边界留在消费端**：生成器只产出"待写单元"，消费方在 `with conn:` 块内整段消费，异常时整体回滚；或者生成器内部产出成功/失败标记，消费端按标记决定提交批次（微批 + 幂等重放）。

实战：规范三条——① 生成器链的第一个 `next()` 永远放在 try 里（或用 `list(itertools.islice(g, 1))` 预热探错）；② 消费循环与事务 BEGIN/COMMIT 严格对齐，禁止"循环里逐条 commit 又期望原子"；③ 生成器内不放无法重放的副作用（外部计数、非幂等 HTTP 调用）。

```python
import sqlite3

def read_rows(bad_index):
    """模拟源数据：第 2 行会抛异常（惰性：构造时不执行，next 到才爆）"""
    for i, row in enumerate([("a", 1), ("b", 2), ("c", 3)]):
        if i == bad_index:
            raise ValueError(f"bad row {i}")
        yield row

# 反例：构造在 try 外，异常在消费时才爆——本例特意包住消费演示时序
def consume_all(rows, conn):
    with conn:                       # 事务边界包住整段消费
        conn.executescript("CREATE TABLE IF NOT EXISTS t (k TEXT, v INT)")
        conn.execute("DELETE FROM t")
        for r in rows:               # 半途异常 -> with __exit__ 回滚
            conn.execute("INSERT INTO t VALUES (?, ?)", r)
    return True

conn = sqlite3.connect(":memory:")
try:
    consume_all(read_rows(bad_index=2), conn)   # 第 3 行才抛
except ValueError as e:
    print("failed lazily:", e)

n = conn.execute("SELECT count(*) FROM t").fetchone()[0]
print("rows after rollback:", n)                 # 0：事务整体回滚，无半成品

# 正例二：生成器产出标记，消费端微批提交 + 失败计数
def safe_rows(items):
    for i, it in enumerate(items):
        try:
            yield ("ok", i, it)
        except Exception as e:               # 生成器内兜底可预知的错误
            yield ("err", i, repr(e))

bad = [1, 2, None, 4]
batch: list[int] = []
for status, i, it in safe_rows(bad):
    if status == "ok":
        batch.append(it)
print("collected:", batch)                   # None 行被标记跳过而非中断
```

**追问一**：`GeneratorExit` 与普通异常在清理上有什么不同要求？——它继承自 `BaseException`（不会被子句 `except Exception` 捕获），生成器收到后必须**重新抛出或直接结束**，不允许再 yield（否则 RuntimeError）；所以生成器内清理用 `try/finally`，不要用"捕获后继续产出"。

**追问二**：为什么 `yield from` 会让异常时序更隐蔽？——异常沿子生成器向上传播时会穿透多层委托，调用方 traceback 里的帧都是生成器内部帧，"是谁消费到一半"的信息在栈顶丢失；3.11+ 的 `Exception.add_note` / PEP 657 精细 traceback 能缓解定位成本。

**追问三**：微批提交方案如何保证"失败批次可重放"？——每批带单调递增 batch_id，下游以 (batch_id, offset) 幂等去重；讨论与 Q6060 Idempotency-Key 在 HTTP 层的同构性。

## 背诵要点
- 生成器构造不执行代码，异常延迟到首次 next；第一个 next 必须在异常防线内。
- 惰性 + 循环内副作用 = 半成品；事务边界包住整段消费，或微批 + 幂等重放。
- GeneratorExit 是 BaseException，清理用 try/finally，禁止捕获后再 yield。
