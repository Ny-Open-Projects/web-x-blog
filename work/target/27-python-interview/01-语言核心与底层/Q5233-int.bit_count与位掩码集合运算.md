### Q5233 · int.bit_count 与位掩码：3.10+ 的 popcount 与集合运算降维

难度：P5 ｜ 标签：bit_count、popcount、bit_length、位掩码、位运算、权限位、布隆过滤、3.10+

**问**：`int.bit_count()`（3.10+）是什么、比 `bin(x).count("1")` 好在哪？`bit_length()` 与 `bit_count()` 的区别？位掩码表示权限/标签集合时，`& | ^ ~` 对应哪些集合运算？为什么大集合场景 set 反而比 int 掩码快？什么时候该把 set 降维成位掩码？

**答**：
结论：`int.bit_count()` 返回二进制表示中 **1 的个数**（population count），对应 C 语言的 popcount 指令；3.10 前的写法是 `bin(x).count("1")`——先构造完整二进制字符串再数，大整数场景内存与时间都翻倍，`bit_count()` 是单遍计数无中间字符串。`bit_length()` 是**最高有效位位置**（不含符号位的位数），`x.bit_length() == len(bin(x)) - 2`，用途是"存储这个数需要多少位"（如定长编码、序列化缓冲预算）。位掩码把集合运算**降维成按位运算**：`&` 交集、`|` 并集、`^` 对称差（异或）、`~x & mask` 补集（无限位宽下 `~x` 是负数，必须配合掩码范围截断）、成员判定 `x & flag`、置位 `x |= flag`、清位 `x &= ~flag`——权限系统、特性开关、周历（每周哪几天营业）的经典表达。关键取舍认知：int 掩码的运算复杂度是 O(位数)，set 是 O(1) 单次但常数大——**小集合（<64 个元素）int 掩码更快更省，大集合 set 更快**；掩码真正的杀手级优势是"单个不可变整数可哈希、可序列化、可比对"，把整个权限快照存成一个字段。

取舍：a) 权限/开关位：int 掩码 + 命名常量枚举（或 IntFlag 枚举，Q477 家族），序列化友好、DB 一个 int 列搞定；b) 集合上千元素：set/dict，别自建多字掩码——除非 profiling 证明值得；c) 需要"数量"而非"集合"：bit_count 数投票位、布隆过滤的置位计数、校验位奇偶性，都是 O(1) 语义的表达；d) `~` 陷阱：Python 整数是任意精度带符号数，`~0b10` = -3 不是预期补集——补集必须 `full_mask & ~x`；e) 位掩码的可读性代价：`flags & 0b1000` 是反人类写法，必须配命名常量或 IntFlag，裸魔法数是 code review 红灯。

实战：事故形态是"周历营业日字段用 7 个布尔列存储，新增'时段'维度后列爆炸；迁移为 int 掩码（7 位+时段位扩展）后单列表达、比对与索引都简化；但同事用 `~mask` 做取反，负数落库导致比对全错——修复为 `FULL_MASK & ~mask` 并在 review 清单加位运算检查"。下面实测 bit_count/bit_length 与掩码集合运算。

```python
# int.bit_count 与位掩码集合运算
print("[1] bit_count (3.10+): 二进制中 1 的个数, 无中间字符串")
x = 0b1011_0111
print(f"    bin(x) = {bin(x)} -> x.bit_count() =", x.bit_count())
print("    bin(x).count('1') =", bin(x).count("1"), "(3.10 前的写法, 多一次字符串构造)")

print("[2] bit_length: 最高有效位, '存这个数要几位'")
for v in (0, 1, 255, 256):
    print(f"    {v}.bit_length() = {v.bit_length()}", f"(bin: {bin(v)})")

print("[3] 掩码集合运算: & 交集 | 并集 ^ 对称差 ~+mask 补集")
READ, WRITE, EXEC, ADMIN = 0b0001, 0b0010, 0b0100, 0b1000
FULL = READ | WRITE | EXEC | ADMIN
perm = READ | EXEC
print(f"    perm = {perm:#06b}")
print(f"    perm & WRITE  (有写权限?)   = {perm & WRITE:#b} ->", bool(perm & WRITE))
print(f"    perm | WRITE  (追加写权限)  = {perm | WRITE:#06b}")
print(f"    perm & ADMIN  (超管判定)    =", bool(perm & ADMIN))
print(f"    FULL & ~perm  (缺失的权限)  = {FULL & ~perm:#06b}")
print(f"    perm ^ (READ | EXEC | WRITE) (对称差/翻转) = {perm ^ (READ | EXEC | WRITE):#06b}")

print("[4] 裸 ~ 的陷阱: 无限位宽下 ~perm 是负数, 补集必须截断")
print("    ~perm =", ~perm, "(负数! 不能直接落库)")
print("    FULL & ~perm =", FULL & ~perm, "(这才是补集)")

print("[5] 常用位技巧: 清最低位 1 求循环次数, 提取最低位 1")
n, steps = x, 0
while n:
    n &= n - 1
    steps += 1
print(f"    x = {x:#b} 低速清位计数 = {steps} (与 bit_count 一致)")
low = x & -x
print(f"    x & -x 提取最低位 1 = {low:#b}")
print("[6] 选型: 小集合掩码快且可哈希; 大集合用 set; 裸魔法数必须换命名常量/IntFlag")
```

**追问一**：`bit_count` 与 Hamming 校验、布隆过滤器的关系是什么？为什么"数 1 的个数"在高频路径上值得一个专用方法？—— Hamming 距离就是两个编码 `xor` 后的 `bit_count`（奇偶校验：`bit_count(x) & 1`），布隆过滤器判"可能存在"看的是位数组中 k 个探针位是否全为 1（数 1 次数），位图 GC 里"活对象密度"也靠 popcount 估算。高频路径上 `bin(x).count("1")` 的问题不只是慢：大整数会先物化一个 O(n) 的字符串（`0b1010...` 前缀还带 2 字符垃圾），内存峰值在热路径上是事故放大器；`bit_count()` 走 C 级单遍计数（常见实现是按 64 位字分组 SWAR 或硬件 popcnt 指令），零中间分配。这条 API 的设计动机就是"把指令级操作还给 Python 用户"，与 `math.isqrt`（Q2630）同族——都是"以前要手写循环，现在一个内建方法"。

**追问二**：IntFlag 枚举与裸 int 掩码怎么选？IntFlag 的哪些行为是坑？—— 裸 int 掩码优点是零依赖、序列化直接是整数、运算语义透明；缺点是可读性与类型安全。IntFlag（`enum.IntFlag`）给掩码加名字、repr 与类型门槛，组合运算返回 IntFlag 成员、`__contains__` 支持 `in` 语义。三个坑：①**0 值成员**：`Flag.A in flags` 对空掩码恒 False 没问题，但 `flags == Flag.NONE` 与 `flags is NONE` 混用出 bug；②IntFlag 的组合值可能**超出已声明成员**（READ|WRITE 是合法成员但不在 `_member_map_` 里），遍历 `list(perm)` 拆的是位分量——语义是"按位分解"不是"按声明枚举"；③3.11 把 IntFlag 的语义调正（不再是 int 的完整子类行为、`int(perm)` 显式转换才回退整数），跨版本序列化要固定行为基线。选型建议：团队大、成员多、有跨语言序列化（前端要位值）用 IntFlag + 显式 int 转换；小工具链裸 int + 命名常量即可。

## 背诵要点
- bit_count() = popcount（3.10+，无中间字符串）；bit_length() = 最高有效位位数。
- & 交集 / | 并集 / ^ 对称差 / 补集必须 FULL & ~x（裸 ~ 在无限位宽下是负数）；x & -x 提取最低位 1。
- 小集合 int 掩码快且可哈希可单列存储；大集合用 set；位运算配命名常量或 IntFlag。

## 复盘追问
- 大集合场景为什么 set 反而比位掩码快？（掩码运算是 O(位数)，稀疏大集合位宽暴涨；set 是哈希 O(1)）
- Python 整数是任意精度，~x 有什么坑？（~x = -x-1 为负数；补集必须与全掩码与运算截断）
