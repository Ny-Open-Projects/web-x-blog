### Q5248 · 单下划线与双下划线：名称改编机制与继承中的访问路径

难度：P6 ｜ 标签：名称改编、name mangling、单下划线、双下划线、私有属性、继承冲突、__getattr__、import *

**问**：`self.__balance` 存到实例里叫什么名字？名称改编发生在什么时机、改编规则是什么（哪些标识符改编、哪些不改编）？子类定义同名 `__balance` 为什么不会覆盖父类的？单下划线 `_x` 与双下划线的防护力差异、`import *` 与 `__all__` 的关系、改编对 `__getattr__`/pickle/调试器的影响？

**答**：
结论：`self.__balance` 在类体内会被编译期**名称改编（name mangling）**为 `self._Account__balance`——规则是：**双前导下划线且至多一个尾下划线的标识符**，在类体内出现时统一改写为 `_ClassName__name`；改编发生在**编译期**（字节码里 LOAD_ATTR 的名字已经是改编后的），不是运行时查找。目的只有一个：**防止继承链上的命名冲突**——子类 `Premium.__balance` 改编为 `_Premium__balance`，与父类的 `_Account__balance` 是两个独立槽位，谁也不覆盖谁，这是"伪私有"设计的真实动机（避免子类无意踩父类状态），而**不是安全机制**——`a._Account__balance` 照样访问，改编名还是明文可推。单下划线 `_x` 是纯约定：无改编，只靠 linter/`from module import *` 的跳过规则（import * 默认跳过所有 `_` 开头的名字，模块定义了 `__all__` 则只导出 `__all__`）表达"内部使用"语义。边界细节：①**类体之外不改编**——模块级/函数体内的 `__x` 不改写（函数局部变量本来就不共享）；②**双尾下划线不改编**——`__x__`（dunder）保持原样，因为它们是协议名；③改编对 `__getattr__` 有交互陷阱：改编只发生在"访问点所在的类体"里——在**另一个类的方法内**写 `obj.__missing` 会编译成 `_该方法所在类__missing`，而模块级访问保持原名；`__getattr__` 收到的正是访问点编译后的字面名，动态属性若用原名注册就会查找落空（Q5212 的协议误触发同族）；④改编给 pickle/序列化带来的类名耦合：改编名含类名，**改名类会破坏已序列化数据与 vars() 调试预期**。

取舍：a) 防护力排序：`_x`（约定）< `__x`（改编防继承冲突）< property 只读（拒绝写）< 不可变设计——团队规范通常是：公开 API 不带下划线、内部用 `_x`、只在"子类很可能无意重名"的场景用 `__x`；b) `__x` 的真实代价：改编名与类名耦合（继承、改名、反射都变脆），测试访问私有属性要写改编名或走公开契约——**优先设计公开接口，`__x` 是最后手段**；c) `__all__` 与 `_x` 的配合：`__all__` 是显式公共 API 白名单（也让 IDE/readdir 更准），没有 `__all__` 时 import * 的下划线跳过规则兜底；d) 数据类/dataclass：`__x` 字段可以正常声明（字段名改编由 dataclass 处理好），但 `field()` 与序列化框架对改编名的支持参差——跨框架场景用 `_x` 更省事；e) 调试：vars()、repr 里看到的是改编名，团队排查文档要写清楚映射。

实战：事故形态是"支付 Account 类的 `__balance` 被子类 Premium 重定义加锁逻辑，代码评审以为覆盖了校验——实际两个改编名并存，父类路径绕过了子类校验直接写入；排查靠 vars() 看到两个槽位才定位。修复为：共享状态显式走父类提供的 property/方法，子类不再声明同名 `__x`；规范层面把 '__x 使用需评审说明继承冲突动机' 写进 checklist（Q2894 命名红线）"。下面实测改编规则、继承隔离与交互边界。

```python
# 名称改编: 规则、继承隔离与交互边界
import pickle

class Account:
    def __init__(self) -> None:
        self.__balance = 100          # 改编为 _Account__balance
        self._internal = "约定私有"    # 单下划线: 无改编
        self.__audit_id__ = "协议名"   # 双尾下划线: dunder, 不改编

    def deposit(self, n: int) -> None:
        self.__balance += n           # 类体内: 编译期已改编

    def get_balance(self) -> int:
        return self.__balance

a = Account()
print("[1] 改编发生在编译期: 实例里存的是改编名")
print("    vars(a) =", vars(a))

print("[2] 三种访问路径")
try:
    print("    a.__balance =", a.__balance)          # 模块级无类体, 按原名找
except AttributeError as e:
    print("    a.__balance -> AttributeError:", e, "(原名不存在)")
print("    a._Account__balance =", a._Account__balance, "(改编名明文可访问, 无安全防护)")
print("    a.get_balance() =", a.get_balance(), "(公开契约路径)")
print("    a.__audit_id__ =", a.__audit_id__, "(dunder 不改编, 原样可访问)")

print("[3] 继承隔离: 子类同名 __balance 是独立槽位")
class Premium(Account):
    def __init__(self) -> None:
        super().__init__()
        self.__balance = 999          # 改编为 _Premium__balance, 不覆盖父类
p = Premium()
print("    vars(p) =", vars(p))
print("    p.get_balance() =", p.get_balance(), "(父类校验路径未被踩)")

print("[4] __getattr__ 收到的是改编后的名字")
class Tracked(Account):
    def __getattr__(self, name):
        print(f"    __getattr__ 收到: {name!r}")
        raise AttributeError(name)

t = Tracked()
try:
    t.__balance
except AttributeError:
    pass

print("[5] 改编名与 pickle 的类名耦合")
data = pickle.dumps(a)
print("    pickle 载荷里含类名痕迹:", b"_Account__balance" in data)
print("[rule ] 双前导=改编防继承冲突; 单前导=纯约定; dunder 不改编; __x 不是安全机制")
```

**追问一**：为什么说名称改编是"编译期"的？这与运行时动态访问 `getattr(obj, "__balance")` 的行为差异是什么？—— 编译期意味着：源码→字节码阶段，类体内 AST 上的 `__balance` 节点被改写为 `_ClassName__balance`，`dis` 反汇编看到的 LOAD_ATTR 属性名就是改编后的；运行时不存在"改编查找"这个动作。两个推论：①**动态字符串访问不走改编**——`getattr(a, "__balance")` 找的就是字面名 `__balance`，实例里根本没有这个键，返回 AttributeError；要拿值必须 `getattr(a, "_Account__balance")` 或在**类体内**写访问代码（那里才编译期改编）；②**exec/exec_method 的 class-cell 问题（Q5193）同族教训**——凡是"绕过编译器语义"的动态机制（exec、getattr、vars 修改）都看不到改编，混合使用时行为与源码直觉不一致。工程纪律：反射访问私有状态（测试钩子、调试器）要么走改编名常量（`f"_{type(obj).__name__}__balance"`），要么干脆走公开契约——动态路径里散落改编名猜测是脆弱代码。

**追问二**：`import *`、`__all__` 与下划线约定三者怎么协作？模块作者如何精确控制公共表面？—— 协作规则：`from m import *` 的导入集由 **`__all__` 优先**——定义了就只导 `__all__` 里的名字（可以显式包含 `_x`，但强烈不推荐）；未定义 `__all__` 则导入所有**不以下划线开头**的全局名。所以两套机制覆盖不同场景：`__all__` 是"白名单精确声明"（IDE/类型检查/文档工具都吃它），下划线跳过是"无 `__all__` 时的默认防线"。模块作者的精确控制清单：①公共 API 进 `__all__`，内部实现一律 `_x`（哪怕也要进 `__all__` 之外的代码路径）；②`__all__` 与实际导出保持同步（测试里 `set(m.__all__) == set(公共名)` 断言）；③子模块 re-export 时用显式 import 而不是 `from .sub import *`（避免白名单意外扩大）；④改编名（`_Cls__x`）自然不在任何导入面——但**模块级 `__x` 不改编**，若模块顶层有 `__cache` 这类全局，它会被 import * 跳过（下划线规则）却仍可被 `m.__cache` 直接访问——模块级"私有"同样只是约定。边界：import * 本身在大型工程里被 lint 禁用（命名空间污染），真正的公共表面靠 `__all__` + 显式 import 维持。

## 背诵要点
- 名称改编是编译期改写：类体内双前导（且至多一尾）下划线 → _ClassName__name，目的是防继承命名冲突；_Cls__name 明文可访问，不是安全机制。
- 不改编的三处：类体外（模块/函数）、dunder __x__、动态字符串 getattr；__getattr__ 收到的是"访问点编译后的字面名"（类体内访问点=改编名，模块级=原名），动态注册要与之一致。
- _x 纯约定 + __all__ 白名单：import * 无 __all__ 时跳过下划线名；公开表面靠 __all__ 精确声明并与导出同步。

## 复盘追问
- 子类声明同名 __balance 为什么不会覆盖父类？（编译期各自改编为 _子类__x/_父类__x，两个独立槽位；共享状态必须走父类公开契约）
- getattr(obj, "__balance") 为什么拿不到值？（动态字符串不经过编译期改编，实例里只有 _Cls__balance；反射要么拼改编名要么走公开接口）
