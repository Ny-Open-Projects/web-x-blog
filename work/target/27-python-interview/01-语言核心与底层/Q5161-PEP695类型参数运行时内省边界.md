### Q5161 · PEP 695 类型参数的运行时内省边界

难度：P7 ｜ 标签：PEP 695、TypeVar、TypeAliasType、__type_params__、运行时内省

**问**：PEP 695 的 `type X = ...` 和 `class C[T]` 在运行时分别留下什么对象？为什么说"泛型参数在运行时存在一个可内省的载体，但内省能力有明确边界"？`typing.get_type_hints` 拿到的是别名本身还是被展开的实参？用编程方式构造的 `TypeAliasType` 与语法糖产物在 `__name__`/`__value__`/`__type_params__` 上有哪些可观测差异，哪些东西**根本无法**在运行时反查？

**答**：
结论：PEP 695 把"类型层"的信息落成了**运行时可访问的对象**：`type X = ...` 产生一个 `typing.TypeAliasType` 实例，暴露 `__name__`/`__value__`/`__type_params__`；`class C[T]`/`def f[T]()` 则在函数/类上挂 `__type_params__` 元组，元素是 `typing.TypeVar`。但边界很硬：① `__value__` 在**定义时即求值**，写 `type Alias = LaterDefined` 得到的 `__value__` 是字符串前向引用而不是对象，后续不会自动修复；② `get_type_hints` 对别名**不递归展开**——拿到的是 `TypeAliasType` 本身，消费者要自己判 `isinstance(h, TypeAliasType)` 再读 `.value`；③ 类型参数只是 `TypeVar` 的"语法糖载体"，运行时**无法反查"它是从哪条 `class C[T]` 语句来的"**（无源码位置、无绑定作用域信息），`TypeVar.__bound__`/`__constraints__` 只有约束没有来源。

取舍：框架作者要用"鸭子类型 + 显式展开"而不是指望类型系统替你递归：解析注解时先按 `isinstance(h, TypeAliasType)` 展开一层，再用 `get_args(h)` 拆泛型别名，同时用 `getattr(obj, "__type_params__", ())` 兼容新旧写法。不要把 `repr(TypeAliasType)` 当稳定契约（其 repr 只是 `name`），也不要假设 `__value__` 一定是真正的类型对象——前向引用、字符串、嵌套别名都会让它是别的东西，必须在边界处做类型判定。

实战：一个典型事故是框架按"旧假设"读 `hints["x"].__origin__`——对普通泛型 `list[int]` 能拿到 `list`，但对 `TypeAliasType` 拿不到（它没有 `__origin__`），必须 `if isinstance(h, TypeAliasType): h = h.__value__` 后再拆。下面用编程式构造复现这套内省边界，不依赖 3.12 语法糖本身。

```python
from typing import TypeAliasType, TypeVar, get_type_hints, get_args
import typing

# 语法糖（text 示意）：type Vec = list[int]；class Box[T]: ...
# 本机用运行时对象构造，等价地观察其可内省属性。
Vec = TypeAliasType("Vec", list[int])
print("alias name :", Vec.__name__)
print("alias value:", Vec.__value__, " value type:", type(Vec.__value__).__name__)
print("type params:", getattr(Vec, "__type_params__", None))

# 1) get_type_hints 不展开别名：拿到的是别名对象本身
def scale(x: Vec) -> Vec: ...
hints = get_type_hints(scale)
print("hints      :", hints)
print("is alias   :", isinstance(hints["x"], TypeAliasType))
print("has origin :", hasattr(hints["x"], "__origin__"))   # 别名没有 __origin__

# 2) 先展开一层再拆泛型，才是稳定写法
def unfold(h):
    seen = 0
    while isinstance(h, TypeAliasType) and seen < 10:
        h = h.__value__; seen += 1
    return h
u = unfold(hints["x"])
print("unfolded   :", u, " args:", get_args(u), " origin:", getattr(u, "__origin__", None))

# 3) __value__ 是"定义时求值"：前向引用停留为字符串，不会事后修复
Lazy = TypeAliasType("Lazy", "NotYetDefined")
print("lazy value :", repr(Lazy.__value__), type(Lazy.__value__).__name__)

# 4) 普通函数没有 __type_params__，泛型语法糖才会有（边界：无源码来源信息）
T = TypeVar("T")
def plain(x: T) -> T: ...
print("plain params:", len(getattr(plain, "__type_params__", ())))
print("TypeVar source info:", [a for a in dir(T) if "source" in a or "module" in a])
```

**追问一**：为什么 `TypeAliasType.__value__` 对前向引用保留字符串，而不是像 `get_type_hints` 那样用 `globalns` 解析？——别名构造发生在**表达式求值时**，那时还没有"注解 consumer 的命名空间"上下文；`get_type_hints` 是在函数定义完成后以函数 `__globals__` 为命名空间事后解析的，两者时机不同。后果是：把别名导出给跨模块消费者时，字符串前向引用可能在消费者模块里解析失败，正确做法是在定义别名时就让它指向已定义对象。

**追问二**：PEP 695 泛型类的 `__type_params__` 与类自身 `__parameters__` 有什么区别、为什么两者都要保留？——`__type_params__` 是**定义级**的语法信息（哪个 TypeVar 出现在这条 `class C[T]` 声明里），`__parameters__` 是 `types.GenericAlias` 在**下标实例化**后记录的实际参数绑定；前者服务于内省"这段声明引入了哪些类型变量"，后者服务于运行期 `C[int]` 这类实例化。框架做序列化 schema 推导时通常只看 `__parameters__`，做静态/运行期一致性检查时才看 `__type_params__`。

## 背诵要点
- PEP 695 把类型信息落成运行时对象：`type X=...` → `TypeAliasType(__name__/__value__/__type_params__)`，泛型声明 → `__type_params__` 元组。
- `get_type_hints` 不展开别名、别名也没有 `__origin__`：必须先 `isinstance(h, TypeAliasType)` 再读 `.value` 拆实参。
- 内省边界硬：`__value__` 定义时求值、前向引用停留为字符串；运行时无源码位置/绑定作用域信息可反查。

## 复盘追问
- 框架升级到 3.12 后对 `TypeAliasType` 注解做 `get_args()` 返回空、schema 推导失败，如何定位并给出兼容新旧写法的展开函数？（isinstance 判定 + 循环展开 + 前向引用兜底）
- 为什么不能靠 `repr()` 或字符串匹配来识别类型别名、而必须用 `isinstance`？（repr 只是 name、不携带结构，且别名与裸类 repr 可能同形，讨论契约稳定性）
