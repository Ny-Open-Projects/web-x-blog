### Q5047 · 三种字符串格式化的成本与选择（f-string / format / %）

> 难度:★★☆ | 标签:str, 格式化, 成本工程, timeit

**问**：`f"{x}"`、`"{}".format(x)`、`"%s" % x` 三套格式化并存，语义与性能各有什么差异？日志参数为什么必须用 `%s` 惰性格式化（Q503 的延伸）？模板与用户输入拼接时各有什么注入面？

**答**：语义差异三层：1) **f-string**（3.6+）在编译期解析为字节码（FORMAT_VALUE/BUILD_STRING），无运行时解析，最快；3.12 起 PEP 701（Q5010）进一步解禁嵌套、复用同一套解析器，表达式能力与 str.format 对齐。2) **str.format** 运行时解析格式串，支持索引/关键字复用（`"{0} {0}".format(x)`），但每次调用都要解析模板，慢约 2-4 倍。3) **%** 最老但**惰性最友好**：`log.debug("%r", obj)` 只在日志真正输出时才格式化（logger 持有 args 不持有字符串），f-string 写日志则每调用点都付出格式化成本——被级别过滤丢弃时纯浪费，这就是日志规范坚持 %s 的成本理由（Q503）。注入面：f-string/% 直接内插，值来自用户输入时只是普通字符串拼接（无 shell 语义，但 SQL/HTML 层面仍需参数化与转义）；`str.format` 的坑是 **format string 注入**：模板字符串可被用户控制时，`"{0.__class__}"` 能沿属性链内省（Q520 的 Template 就为此而生），未受信模板一律用 `string.Template` 或白名单字段映射。成本账方法：hot path（每秒百万级）用 f-string/手动拼接；日志点用 % 惰性；模板复用（同一模板万次渲染）用预解析的 Template 或 Jinja2（第三方，基线 3.1）。

```python
# file: code/01_语言核心与底层/q5047_format_cost.py
import timeit
import sys

name, n = "order", 42

def bench(stmt, N=200_000):
    return timeit.timeit(stmt, globals=globals(), number=N) / N * 1e9

print(f"python {sys.version_info[:3]}")
print(f"f-string    : {bench('f\"order:{name}:{n}\"'):>6.0f} ns")
print(f"str.format  : {bench('\"order:{}:{}\".format(name, n)'):>6.0f} ns")
print(f"% 格式化    : {bench('\"order:%s:%s\" % (name, n)'):>6.0f} ns")
print(f"+ 拼接      : {bench('\"order:\" + name + \":\" + str(n)'):>6.0f} ns")

# 惰性格式化: 日志级别过滤时, % 只存 args 不付格式化成本
import logging
logging.basicConfig(level=logging.WARNING)
log = logging.getLogger("demo")

def log_fstring():                          # f-string: 每次都先格式化再传给 debug
    log.debug(f"order {name}:{n}")

def log_percent():                          # % : 被过滤时零格式化成本
    log.debug("order %s:%s", name, n)

N = 100_000
t = timeit.timeit(log_fstring, number=N)
print(f"f-string 日志(被丢弃) {t/N*1e9:.0f} ns/次")
t = timeit.timeit(log_percent, number=N)
print(f"% 惰性日志(被丢弃)   {t/N*1e9:.0f} ns/次")

# 注入面: format string 注入 vs Template 隔离
evil = "{0.__class__.__mro__}"              # 用户控制的"模板"
try:
    print("format 注入面:", evil.format(name)[:40], "...")
except Exception as e:
    print("format 内省被拦:", type(e).__name__)

import string
safe = string.Template("$name 的订单 $n")
print("Template 隔离:", safe.safe_substitute(name=name, n=n))  # 只替换占位符
print("Template 对恶意串:", string.Template(evil).safe_substitute(name=name)[:40])
```

**追问**：1) 为什么 f-string 不能做惰性日志？——f-string 在调用 logger 之前已在调用方求值完毕，logger 收到的是成品字符串；惰性要求把"求值"推迟到确认输出之后，只能靠传参（%s + args）或惰性对象（实现 `__str__` 的包装器）。2) 3.12 的 PEP 701 对 f-string 成本有什么改变？——解析器统一后 f-string 的编译期表达式能力追平 format（可任意嵌套引号、多行），运行时路径仍是 BUILD_STRING，性能基本不变；变化主要在语法层面而非成本。3) 什么时候反而该用 str.format？——模板外置（配置文件/i18n 资源串）场景：模板在运行时才到手，f-string 写不了；此时应缓存解析结果或用 Template。

## 背诵要点
- f-string 编译期求值最快；format 运行时解析慢 2-4 倍；% 日志惰性化免费丢弃。
- 日志规范：`log.debug("%s", x)` 而非 f-string——级别过滤时不付格式化成本。
- 用户可控的 format 模板 = 内省注入面（`{0.__class__}`）；未受信模板用 string.Template。

## 复盘追问
- 一次性能复盘发现某服务 CPU 有 8% 花在 debug 级 f-string 日志上，如何在不改日志内容语义的前提下修复？（提示：全量改 % 惰性 + 级别开关，监控"被丢弃日志"的节省量）
- i18n 场景模板外置后，如何兼顾性能与注入安全？（提示：启动期预编译全部模板 + 白名单字段，运行期只做替换）
