### Q5084 · str 的三种存储形态与海量文本内存容量账

难度：★★★★☆ ｜ 标签：str 内部表示 / 内存容量 / 容量规划

**问**：服务要缓存 2000 万条用户昵称，预估内存时按"每字符 1 字节"算出 2GB，结果 RSS 涨了 8GB。CPython 的 str 内部是怎么存字符的？容量估算应该用什么公式？

**答**：
- **结论**：3.3 起 str 是 **PEP 393 紧凑（compact）表示**：按字符串内最大码点选三种内部宽度之一——纯 ASCII 用 1 字节/字符（kind=1），含 BMP 内字符用 2 字节（kind=2），含增补平面字符（如 emoji）用 4 字节（kind=4）。整个字符串统一宽度，没有每字符 flag。所以"中文昵称"是 2 字节/字符而非 1；一旦混入一个 emoji，整条串跳到 4 字节/字符。
- **取舍**：单条串的账 = 对象头（约 49 字节：hash、长度、状态、指针等）+ `len(s) * kind`（compact 无终止符）。估算要分桶：ASCII 桶、CJK 桶、emoji 混排桶分别用 1/2/4 系数，再乘条数加对象头。2000 万条短昵称的账大头往往是 **49 字节对象头**而不是字符本体——100 条 5 字符 ASCII 串的" overhead 率"接近 200%。若要压内存，把散串聚合成大块（如 `"\n".join` 后切片、或 Arena 化），或接受 trade-off 转 bytes/编码字典压缩。
- **实战**：测量口径必须用 `sys.getsizeof`（含对象头）+ 抽样分桶，而不是 `len` 乘系数；跨进程共享热字符串可用 `sys.intern` 去重（另见 Q5076 的账）；若数据来自网络是 UTF-8 bytes，"解码成 str 再缓存"通常膨胀 1-4 倍，容量敏感时可考虑"缓存 bytes、按需解码"。

```python
"""PEP 393 三种存储形态的实测容量账（Python 3.3+，标准库）"""
import sys

def account(label, s):
    size = sys.getsizeof(s)
    per_char = (size - 49) / max(len(s), 1)   # 49 ≈ CPython 3.12 str 对象头
    print(f"{label:<14} len={len(s):<4} sizeof={size:<5} 字节/字符≈{per_char:.1f}")

account("纯ASCII", "hello world")            # kind=1：1 字节/字符
account("纯中文", "你好世界这是个测试")        # kind=2：2 字节/字符
account("混入emoji", "hello 你好🚀")          # kind=4：整串升 4 字节
account("空串", "")

# 混入一个 emoji 的代价：整串从 1-2 字节跳到 4 字节/字符
ascii_ = "user nickname text"
with_emoji = ascii_ + "🚀"
print(f"加 1 个 emoji 后 sizeof: {sys.getsizeof(ascii_)} -> {sys.getsizeof(with_emoji)}")

# 海量短串的对象头占比（容量规划的真实大头）
sample = ["nick_%05d" % i for i in range(200_000)]
total = sum(sys.getsizeof(s) for s in sample)
chars = sum(len(s) for s in sample)
print(f"20万条短昵称: 字符本体 {chars} B, 实际 {total/1e6:.1f} MB, 对象头占比 {1 - chars/total:.0%}")

# 聚合存储的降本对比：拼接成大块后按行切片（切片是共享，不复制字符数据）
blob = "\n".join(sample)
offsets, pos = [], 0
for s in sample:
    offsets.append(pos); pos += len(s) + 1
total2 = sys.getsizeof(blob) + 8 * len(offsets)
print(f"大块方案粗账: blob {sys.getsizeof(blob)/1e6:.1f} MB + 偏移表 {8*len(offsets)/1e6:.1f} MB（切片只建 str 头，字符不复制）")
first = blob[offsets[0]:offsets[0] + len(sample[0])]
print("切片取回一致:", first == sample[0])
```

**追问链**
1. 为什么混入一个 emoji 会让整串升到 4 字节/字符？有办法局部化这个代价吗？
   1. PEP 393 要求整条串单一宽度以便 O(1) 索引，不做混合宽度；要局部化就把 emoji 拆到附属字段（如昵称主体 + 装饰段分开存），或缓存层保留 UTF-8 bytes 按需解码。
   2. 追问：`s.encode('utf-8')` 后的 bytes 和原 str 谁小？——UTF-8 对中文 3 字节/字符、emoji 4 字节，通常小于 kind=4 的 str，且 bytes 无宽度升级问题。
2. `sys.getsizeof` 估算缓存容量还漏了什么？
   1. 漏了 dict/索引结构的桶表开销（每个槽 8-16 字节 × 负载因子）、分配器 arena 碎片（小对象来回释放后的空洞）、以及副本持有（同一串被多处 list/dict 引用不会重复字符数据，但表项重复）。生产容量账要拿 tracemalloc 实测曲线校准。

## 背诵要点
- PEP 393：str 按 max 码点统一取 1/2/4 字节宽度；混入 1 个 emoji 整串升 4 字节/字符。
- 单串账 = 49 字节对象头 + len×kind；海量短串的大头是对象头，聚合大块 + 切片可降本。
- 容量估算用 getsizeof 分桶实测，勿按"1 字节/字符"拍脑袋；UTF-8 bytes 缓存通常更省。
