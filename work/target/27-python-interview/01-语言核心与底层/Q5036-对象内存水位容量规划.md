### Q5036 · 对象内存水位容量规划：从对象模型推 RSS

> 难度:★★★★ | 标签:内存, 容量规划, getsizeof, RSS

**问**：怎么在写代码阶段估算"一千万条记录会占多少内存"？`sys.getsizeof` 的问题在哪？从对象到 RSS 中间还隔着哪几层？

**答**：容量规划 = **单对象画像 × 对象数 × 系数**。单对象画像必须用"深大小"而非 getsizeof 的浅大小：容器对象本身只记指针，元素另行分配——一个空 dict 约 64B，10 键 dict 约 360B，str 在 ASCII 下约 49+len（compact 布局，Q1264），int 小值 28B。从对象到 RSS 隔三层：1) **对齐与池浪费**——pymalloc 按 16B 对齐分块，碎片系数 1.1-1.4；2) **GC 头与引用**——每对象 16B 头（3.12+ 部分对象 immortal 化后共享）；3) **arena 不还**——分配峰值决定水位下限（Q6029/Q5030）。所以工程公式：`RSS ≈ Σ深大小 × 1.3（池系数）+ 峰值临时对象 + 解释器基线（~15-30MB）`。验证闭环必须做：先 `tracemalloc` 快照拿 Python 层账本，再对比进程 RSS，差值就是分配器/非 Python 内存（第三方 C 库）。取舍：架构上与其精算，不如**给每条记录建"字节预算"**（如 ≤1KB/记录），超预算先改结构（slots、array、Column 存储）而不是扩机器。

```python
# file: code/01_语言核心与底层/q5036_memory_watermark.py
"""深内存画像: 递归求深大小 -> 估算千万级记录水位."""
import sys

def deep_size(obj, seen: set | None = None) -> int:
    """深大小: 对象浅大小 + 可达唯一子对象的浅大小(去共享)."""
    seen = set() if seen is None else seen
    if id(obj) in seen:
        return 0
    seen.add(id(obj))
    total = sys.getsizeof(obj)
    if isinstance(obj, dict):
        for k, v in obj.items():
            total += deep_size(k, seen) + deep_size(v, seen)
    elif isinstance(obj, (list, tuple, set, frozenset)):
        for item in obj:
            total += deep_size(item, seen)
    elif hasattr(obj, "__dict__"):
        total += deep_size(vars(obj), seen)
    return total

# 1) 单条记录画像: dict 版 vs slots 类版
def rec_dict(i: int) -> dict:
    return {"id": i, "name": f"user-{i}", "score": i * 1.5, "tags": ["a", "b"]}

class RecSlots:
    __slots__ = ("id", "name", "score", "tags")
    def __init__(self, i):
        self.id, self.name, self.score, self.tags = i, f"user-{i}", i * 1.5, ["a", "b"]

d, s = rec_dict(1), RecSlots(1)
size_dict, size_slots = deep_size(d), deep_size(s)
print(f"dict 记录深大小: {size_dict}B | slots 记录: {size_slots}B "
      f"(dict 额外付 key/hash 结构)")

# 2) 千万级水位估算: 深大小 × 池系数1.3 × 记录数 + 基线
BASE_MB = 25.0
POOL_FACTOR = 1.3
N = 10_000_000
for name, size in (("dict", size_dict), ("slots", size_slots)):
    est_mb = size * POOL_FACTOR * N / 1024 / 1024 + BASE_MB
    print(f"{name:6s} 千万条估算 RSS ≈ {est_mb/1024:.2f} GB")

# 3) tracemalloc 校准: Python 层真实值 vs 估算
import tracemalloc
tracemalloc.start()
data = [rec_dict(i) for i in range(50_000)]
cur, peak = tracemalloc.get_traced_memory()
per = (cur - BASE_MB * 1024 * 1024) / len(data)
tracemalloc.stop()
print(f"tracemalloc 实测每条 ≈ {per:.0f}B, 推算千万条 Python 层 ≈ "
      f"{per*N/1024/1024/1024:.2f} GB (RSS 还要 ×池系数~1.3)")
del data
```

**追问**：1) 为什么估算要乘 1.3 这个系数、怎么校准到自己的服务？——pymalloc 池内块按 16B 对齐 + arena 碎片驻留；校准方法就是第 3 步：tracemalloc 账本 vs 稳态 RSS 的比值，拿生产三台机器的中位数。2) 引用共享为什么在 deep_size 里要去重？——同一对象被多处引用只占一份内存（浅结构各记 8B 指针），不去重会把 100 万元素列表重复计入每个持有者。3) slots 类省在哪、为什么 tags 列表没省？——省的是实例 `__dict__`（key 共享结构，Q1262），元素本身（list 与其内容）照旧；所以画像要分"结构税"与"数据税"两部分看。

## 背诵要点
- 容量公式：RSS ≈ Σ深大小 × 1.3 + 峰值临时 + 25MB 基线；getsizeof 是浅大小，容器必算元素。
- 对象→RSS 隔三层：16B 对齐池浪费、GC 头、arena 不还 OS。
- 校准闭环：tracemalloc 账本 × 记录数 → 对比稳态 RSS，差值即分配器与非 Python 内存。
