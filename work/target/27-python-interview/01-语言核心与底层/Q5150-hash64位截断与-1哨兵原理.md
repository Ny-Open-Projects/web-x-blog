### Q5150 · hash 值的 64 位截断与 -1 哨兵原理

难度：P7 ｜ 标签：hash、dict、CPython 原理、PYTHONHASHSEED

**问**：自定义 `__hash__` 返回超大整数或 `-1` 时 dict 行为有什么反直觉？CPython 的 hash 值在对象生命周期里如何存储与截断（Py_hash_t、2⁶¹-1 模数、-1 哨兵）？这与 `PYTHONHASHSEED` 随机化如何配合？

**答**：
结论：`hash()` 的返回类型标注是 int，但 C 层契约是 `Py_hash_t`（64 位有符号）。三个关键事实：① **str/bytes 等 hash 被截断**为 `x mod (2⁶¹ - 1)`（保留 SipHash 的分布性、避免符号位问题），所以超大整数 hash 不是"更均匀"；② **`-1` 是 C API 的错误哨兵**——自定义 `__hash__` 返回 `-1` 时 CPython 会替换为 `-2`（`Py_HashPointer` 同理），否则无法区分"hash 是 -1"和"hash 计算出错"；③ hash 值在 `__hash__` 首次调用后缓存在对象头（`ob_hash` 字段，随不可变对象生命周期固定），dict 插入时直接读缓存，这就是"可变对象必须禁止 hash"的底层原因之一——缓存值会与内容漂移。

取舍：自定义 `__hash__` 应输出"分布均匀的整数"（如返回元组的 hash 组合），不需要也不应该自己 mod `2⁶¹-1`；跨进程持久化 hash 值（写入文件/DB 做去重键）是错的——str 的 SipHash 受 `PYTHONHASHSEED` 随机化影响，重启后必然漂移。

实战：对象去重/分片键不要用 `hash()`，用 `hashlib` 的稳定摘要；PYTHONHASHSEED=0 仅用于复现测试环境顺序，生产禁用固定种子（会重建 hash flood 攻击面）。

```python
class Weird:
    def __hash__(self):
        return -1                 # 命中哨兵替换规则

w = Weird()
print("hash(-1 class):", hash(w))          # -2，CPython 替换 -1 -> -2
assert hash(w) != -1

# 64 位截断：str 的 hash 是 SipHash 后 mod (2**61 - 1)
big = 2**61 - 2
s = "hello"
print("hash('hello')      :", hash(s))
print("mod 2**61-1 scheme :", hash(s) % (2**61 - 1))
# 大整数自身的 hash：hash(n) == n mod (2**61 - 1)（保证 hash(n)==hash(int(n)) 不截断为错值）
print("hash(big)          :", hash(big), "== big?", hash(big) == big % (2**61 - 1))

# hash 缓存与 PYTHONHASHSEED：同进程内稳定，跨进程随机（str/bytes/datetime 等）
import subprocess, sys
code = "print(hash('stable-across-run?'))"
out1 = subprocess.run([sys.executable, "-c", code], capture_output=True, text=True).stdout.strip()
out2 = subprocess.run([sys.executable, "-c", code], capture_output=True, text=True).stdout.strip()
print("run1:", out1, "run2:", out2, "equal:", out1 == out2)   # 通常 False
# int 的 hash 跨进程稳定（不受 SipHash 种子影响）
code2 = "print(hash(123456))"
o1 = subprocess.run([sys.executable, "-c", code2], capture_output=True, text=True).stdout.strip()
print("int hash stable:", o1, hash(123456) == int(o1))
```

**追问一**：为什么选 `2⁶¹-1` 这个模数而不是 `2⁶⁴`？——它是梅森素数，mod 运算可用 `x & p` + 移位技巧低成本实现；同时避免取模后的值触及 `Py_hash_t` 无法表达的区间，并让 -1 哨兵语义保持独立。

**追问二**：hash 缓存对"对象复活"/`__hash__` 动态修改有什么影响？——首次 `hash()` 后值挂在对象头不再调用 `__hash__`（int/str/tuple 等内置类型）；自定义类每次调用都进 Python 层（无缓存），所以自定义 `__hash__` 要便宜；`__eq__` 相等必须同 hash 的契约在 dict 扩容 rehash 时被全量验证。

**追问三**：如何设计"Python 内 hash 与存储层 key"的映射规范？——进程内索引用 `hash()`/tuple hash（快、可随机）；跨进程/持久化 key 用 sha256 摘要或业务唯一键（稳定、可迁移），两层命名区分（如 `_mem_key` vs `disk_key`）。

## 背诵要点
- C 层 hash 是 64 位 `Py_hash_t`；str/bytes 结果 mod (2⁶¹-1)（梅森素数），自定义超长返回值不会更均匀。
- `__hash__` 返回 -1 会被 CPython 替换成 -2：-1 是 C API 错误哨兵。
- str/bytes hash 受 PYTHONHASHSEED 随机化，跨进程不稳定；持久化去重键必须用 hashlib/业务键。

## 复盘追问
- 一个用 `hash(str)` 做分片键的作业重启后数据分布漂移，如何根治并灰度迁移？（迁移到 sha256 前缀分片 + 双读期兼容，讨论再平衡成本）
- 为什么 dict 不缓存"槽位"而只缓存 hash 值？扩容 rehash 时利用了什么？（开放式寻址只依赖 hash 重算探针，值缓存让 rehash 免去重复调用 `__hash__`）
