### Q5239 · 负零 -0.0：相等不等位、copysign 与序列化坑

难度：P6 ｜ 标签：-0.0、负零、signbit、copysign、IEEE 754、JSON 序列化、除零方向、相等性

**问**：`-0.0 == 0.0` 返回 True，那负零"存在感"在哪？怎么区分一个浮点数是 +0.0 还是 -0.0？负零从哪里来（`round(-0.1)`、`-0.0`、除零方向）？`1.0 / -0.0` 是什么？负零在 JSON/跨语言序列化、统计口径、风控金额里会出什么事故？

**答**：
结论：IEEE 754 里零有两个符号位变体——`+0.0` 与 `-0.0`，**数值上相等（== 恒 True）、哈希相同、作为 dict 键互相覆盖（Q5160 同族），但位表示不同**。区分它的唯一正确姿势是**符号位**：`math.copysign(1.0, x)` 返回 ±1.0（对 ±0.0 也可靠），或 `math.copysign(1, x)`，而 `x < 0` 对 -0.0 返回 False（它不"小于"零）、`math.sign(x)` 对两个零都返回 0。负零的来源面：字面量 `-0.0`、`round(-0.1)`（→ -0.0）、`-0.0 * 正数`、`-1.0 * 0.0`、`0.0 * -1`、向零截断 `-0.4 → -0.0`；除零方向：IEEE 754 层面 `1.0 / -0.0` = **-inf**、`1.0 / 0.0` = +inf——但 Python 在 IEEE 之上主动加了一层：**float 除零同样抛 ZeroDivisionError**，要拿"有符号无穷"得显式走 `math.copysign(math.inf, -0.0)` 这类位语义 API，符号信息并未丢失。事故面集中在**边界穿越**：①JSON 序列化 `json.dumps(-0.0)` 输出 `-0.0`，下游 C/Java 解析器可能拒绝或变字符串；②统计口径：盈亏归零时 -0.0 与 0.0 在前端展示、四舍五入分组、绝对值比较上"行为不一致"（`str(-0.0)` = '-0.0'）；③金额：-0.0 参与符号判断 `copysign` 后被当负数记账。工程纪律：展示/序列化前 `x + 0.0`（加正零归一化：-0.0 + 0.0 = 0.0），或明确用 signbit 判断。

取舍：a) 判断符号：`math.copysign(1, x)` 是零安全的；`x > 0` / `x < 0` 会把 -0.0 归入"非负"——这是特性还是坑取决于业务，风控金额场景必须显式处理；b) 归一化：`x or 0.0` 不行（-0.0 真值为 False 会归到 0.0 但丢失其他语义？——实际 -0.0 + 0.0 = +0.0 是无损归一）；c) 序列化：跨语言边界建议 `round(x, 12) + 0.0` 后输出，或金额改整数分（Q538）；d) 数学意义：负零不是 bug，是连续函数"从负方向逼近零"的合法极限表达——cmath 的分支切割依赖符号零（`cmath.log(complex(-1, 0.0))` 与 `cmath.log(complex(-1, -0.0))` 结果差一个 π 的符号）；e) 别在 int 域担心：int 没有 -0（只有一个 0），这是"金额用整数分"的又一好处。

实战：事故形态是"盈亏报表把浮点盈亏 round 到 2 位，恰好归零的行得到 -0.0，JSON 下发给前端展示为 -0.00，同时按 `copysign` 判方向的记账逻辑把它记入'亏损'分桶——修复为序列化层 `value + 0.0` 归一化 + 业务层金额整数化，报表与记账口径一致"。下面实测负零的产生、判定与序列化行为。

```python
# 负零 -0.0 的产生、判定与序列化
import cmath
import json
import math
import struct

print("[1] 负零在数值上等于正零, 但位表示不同")
z, nz = 0.0, -0.0
print("    -0.0 == 0.0 ->", nz == z, "| -0.0 is 0.0 ->", nz is z)
print("    bit 表示: +0.0 =", struct.pack(">d", z).hex(), "| -0.0 =", struct.pack(">d", nz).hex(),
      "(仅符号位不同)")

print("[2] 判定符号的唯一可靠姿势: copysign (比较运算对 -0.0 失效)")
print("    -0.0 < 0 ->", nz < 0, "| -0.0 > 0 ->", nz > 0, "(两个零都'不算负')")
print("    math.copysign(1, 0.0)  =", math.copysign(1.0, z))
print("    math.copysign(1, -0.0) =", math.copysign(1.0, nz), "(唯一能区分的常规 API)")
print("    struct 符号位判定: bool(struct.pack('>d', nz)[0] & 0x80) =", bool(struct.pack(">d", nz)[0] & 0x80), "(signbit 真值)")

print("[3] 负零的来源: round/截断/乘法方向")
print("    round(-0.1)  =", repr(round(-0.1)), "| int(-0.4) =", repr(float(int(-0.4))),
      "| -1.0 * 0.0 =", repr(-1.0 * 0.0), "| abs(-0.0) =", repr(abs(-0.0)), "(abs 归正)")

print("[4] 除零方向: Python 层 float 除零也抛异常, IEEE 有符号无穷要走位语义 API")
try:
    _ = 1.0 / 0.0
except ZeroDivisionError as e:
    print("    1.0 / 0.0 -> ZeroDivisionError:", e, "(Python 在 IEEE 之上加了这层)")
print("    math.copysign(math.inf, 0.0)  =", math.copysign(math.inf, 0.0))
print("    math.copysign(math.inf, -0.0) =", math.copysign(math.inf, -0.0), "(IEEE 754 的除零方向在此显式化)")

print("[5] 序列化事故: JSON 直接输出 -0.0, 下游可能不认")
s = json.dumps({"profit": -0.0, "zero": 0.0})
print("    json.dumps ->", s)
print("    归一化: -0.0 + 0.0 =", repr(-0.0 + 0.0), "-> json:", json.dumps(-0.0 + 0.0), "(加正零无损归一)")

print("[6] 相等性特例: 两个零与 NaN 的区别")
print("    (-0.0 == 0.0) =", -0.0 == 0.0, "而 (nan == nan) =", float("nan") == float("nan"), "(零相等, NaN 不相等)")
print("    dict 键: {0.0: 'a'}[-0.0] ->", {0.0: "a"}[-0.0], "(两零同桶互相覆盖)")

print("[7] 数学意义: 符号零是'从负方向逼近零'的合法极限 (cmath 分支切割依赖它)")
print("    cmath.log(complex(-1, 0.0))  =", cmath.log(complex(-1, 0.0)))
print("    cmath.log(complex(-1, -0.0)) =", cmath.log(complex(-1, -0.0)), "(虚部零的符号决定分支侧!)")
print("[8] 工程纪律: 展示/序列化前 x + 0.0 归一化; 符号判定用 copysign; 金额改整数分")
```

**追问一**：为什么 IEEE 754 要设计两个零？废除负零会怎样？—— 两个零是**符号-数值表示法**（sign-magnitude）的自然产物：浮点由符号位+指数+尾数组成，符号位独立于数值，0 只有一个数值却有 ± 两个位型。数学动机：①**符号连续性**——负数下溢/负侧逼近零时结果保持"负的"语义（-1e-300 下溢成 -0.0 而不是 +0.0），`1/x` 因此仍得 -inf 而不是 +inf，方向信息不丢；②**复变函数分支切割**——`log(z)` 在负实轴的分支需要用符号零区分"从上方逼近负轴"（+0 虚部）与"从下方"（-0 虚部），cmath 的分支选择依赖它。若废除负零，所有"从负方向趋零"的计算在边界处方向翻转，数值分析里大量边界定理失效。所以负零不是历史包袱，是**方向信息的存续机制**——Python 侧要做的不是消灭它，而是在业务边界（展示/记账/序列化）把"数学语义"与"业务语义"显式解耦。

**追问二**：`-0.0` 作为 dict 键与 `0.0` 互相覆盖，这和 True/1/1.0 同键合并（Q5160）是同一机制吗？工程上怎么统一防御？—— 同一机制：dict/set 的等值与哈希遵循**数值等值规则**——IEEE 754 规定 -0.0 == 0.0，Python 又规定哈希必须与等值一致，所以两个零必须同桶；True == 1 == 1.0 是 int→float 提升的跨类型等值，零的两个符号是 IEEE 内部的跨位型等值——都是"== 说相等就同键"的必然结果，覆盖规则都是后写者赢。统一防御三层：①**键域收口**：dict 键只用 str/int，浮点/布尔/Decimal 混合值不进键（先显式规范化，如金额键用整数分字符串）；②**归一化入口**：所有数值入键前 `+ 0.0` 消符号零、`round` 消精度噪声；③**计数类场景**（Counter/分组统计）：浮点作键统计是反模式——先桶化（区间分桶）再计数，因为 ULP 级差异（Q5234）会让"相同"值散落到多个键。这三层本质都是同一句话：**等值语义要在进入哈希容器之前被业务显式定义**。

## 背诵要点
- -0.0 == 0.0 为 True 但位表示不同（仅符号位）；比较运算把 -0.0 归入"非负"，判定符号唯一可靠姿势是 math.copysign。
- 来源：round(-0.1)/int(-0.4)/-1.0*0.0；IEEE 除零方向 1.0/-0.0=-inf，但 Python 层 float 除零同样抛异常，符号无穷走 copysign(math.inf, ±0.0)。
- 序列化边界：json 直接输出 -0.0；归一化 x + 0.0；两零与 True/1/1.0 同为"== 相等即同键"，dict 后写者赢。
