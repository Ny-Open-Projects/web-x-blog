### Q5222 · PEP 526 注解的求值与存储边界：局部注解被丢弃

难度：P6 ｜ 标签：PEP 526、变量注解、__annotations__、局部注解、延迟求值、get_type_hints

**问**：`x: int = 1` 在模块、类、函数三种位置分别发生了什么？为什么函数体内的注解"写了却拿不到"？局部注解引用不存在的名字为什么也不报错？运行时想读回注解该用什么？这与 `from __future__ import annotations`（Q2104）和 PEP 649（Q5003）的关系是什么？

**答**：
结论：PEP 526 的规则是**位置决定存储**：①模块级注解存进模块的 `__annotations__` 字典；②类体注解存进类的 `__annotations__`；③**函数体内的局部变量注解既不求值也不存储**——它只进入编译器的符号表供静态检查用，运行时彻底消失，函数对象的 `__annotations__` 里只有返回值注解（`return` 键）。两个关键推论：局部注解的表达式**不会被求值**（写 `" DefinitelyUndefined "` 这种不存在的名字也不炸），所以它不是运行时断言；模块/类级注解在默认模式下**会立即求值**（这正是 Q2104 里框架兼容事故的根源，未来求值才改了这一点）。运行时读取要用 `typing.get_type_hints()`：它负责对字符串注解求值、解析前向引用、合并 MRO 上的注解链——直接翻 `__annotations__` 只能拿到原始形态（字符串就是字符串）。

取舍：a) 想给"局部变量"挂运行时元信息：注解做不到，改用临时对象属性、专用容器或 dataclass 字段；b) 框架做依赖注入/字段校验：只扫模块与类级 `__annotations__` + `get_type_hints`，不要指望函数局部注解；c) 库代码读用户类的注解一律走 `get_type_hints`，手写求值会在前向引用、Optional 语法糖、局部类上全踩坑；d) 注解的求值时机默认是"定义即求值"，对重 IO/重计算的注解是启动成本（Q5138 的 typing 运行时成本账），`from __future__ import annotations` 把求值推迟到显式读取；PEP 649/749（3.14+）进一步用惰性求值把边界重划，三套模式的差异是版本升级清单里的必查项；e) 局部注解对 mypy/pyright 是一等公民——它的价值在静态层，运行时读不到是设计不是缺陷。

实战：事故形态是"同事在 handler 里写 `user: CurrentUser = request.user`，指望框架按注解自动转换，结果注解根本没进任何字典，转换永远不生效；修复为在类级声明转换契约并用 `get_type_hints` 扫描"。下面演示三种位置的存储差异与读取方式。

```python
# PEP 526 注解求值与存储边界: 局部注解被丢弃
import typing

class Config:
    retries: "list[int]" = []      # 类体注解: 存入 Config.__annotations__, 字符串原样保存
    name: str

print("[1] 类体注解进 __annotations__, 未求值的字符串原样保存:")
print("   ", Config.__annotations__)

def load() -> None:
    n: int = 10                    # 局部注解: 仅作元信息, 不求值不存储
    missing: " DefinitelyUndefined " = 1   # 引用不存在的名字也不会报错
    return None

print("[2] 局部注解既不求值也不存储(函数 __annotations__ 只有 return 注解):")
print("    load.__annotations__ =", load.__annotations__)

print("[3] 运行时读取注解要用 typing.get_type_hints 求值:")
hints = typing.get_type_hints(Config)
print("   ", hints)

x: int = 1                        # 模块级注解: 存入模块 __annotations__
if "__annotations__" in globals():
    print("[4] 模块级注解进模块 __annotations__:", __annotations__.get("x"))

print("[5] 规则小结: 类体/模块级注解 -> __annotations__; 函数局部注解 -> 直接丢弃")
```

**追问一**：为什么局部注解"不求值"反而是正确设计？—— 函数每次调用都执行，注解若参与求值就会成为每次调用的隐藏成本（表达式里可能有函数调用、属性访问），而它对运行时毫无作用——纯属浪费。CPython 编译期直接把局部注解剥掉，只保留静态检查语义。同理它也不能当"运行时校验"用：`n: int = "abc"` 运行期不会报错。这一设计让"类型注解"与"运行时断言"的职责彻底分开，混淆两者的代码（拿注解当 assert）本身就是 bug。

**追问二**：`get_type_hints` 什么时候会炸？怎么防御？—— 三个已知爆点：①注解字符串里的名字在**类/模块命名空间**找不到（局部类型、循环导入半成品），抛 `NameError`；②`from __future__ import annotations` 下延迟求值，读取时机从"类定义时"挪到"调用 get_type_hints 时"，原来不炸的引用现在炸（Q5162 的框架兼容事故）；③嵌套类/局部类的引用无法解析。防御：库入口包 `try/except NameError` 降级 + 提供显式类型注册表替代纯字符串引用；业务侧避免在注解里引用"将来才存在的名字"，必要时局部 import 放进 `TYPE_CHECKING` 块并用字符串注解。

## 背诵要点
- PEP 526 三位置：模块/类注解进 __annotations__ 且默认立即求值；函数局部注解不求值不存储，仅静态层有效。
- 运行时读取用 typing.get_type_hints（求值字符串、解析前向引用、合并 MRO），手翻 __annotations__ 拿到的是原始形态。
- get_type_hints 爆点：不可解析的名字 NameError、future 注解下读取时机后移（Q5162 事故）、局部类引用。

## 复盘追问
- 为什么函数里写 `n: int = "abc"` 运行期不报错？（局部注解不求值不存储；类型检查是静态层职责）
- 框架扫描注解为什么必须用 get_type_hints 而不是直接读 __annotations__？（字符串求值/前向引用/MRO 合并，手写必漏）
