### Q5262 · 异步生成器的终结钩子：set_asyncgen_hooks 的 firstiter 与 finalizer

难度：P7 ｜ 标签：async generator、set_asyncgen_hooks、finalizer、asyncio、资源泄漏

基线：CPython 3.12.2，纯标准库；手动驱动异步生成器，用自定义 `firstiter`/`finalizer` 记录生命周期事件。

**问**：一个异步任务用 `async for` 消费上游分页生成器，客户端中途断开，任务被取消。监控显示上游连接池的占用一直不回落，但代码里明明写了 `finally: await conn.close()`。排查发现生成器对象被 GC 了，`finally` 却没执行。另一次团队自己调 `sys.set_asyncgen_hooks` 做泄漏检测，结果所有异步生成器都不再自动关闭，泄漏更严重。`firstiter` 和 `finalizer` 分别在什么时机触发？显式 `aclose()` 会走 `finalizer` 吗？自定义钩子为什么能把清理逻辑"挡掉"？

**答**：

- **结论**：异步生成器的生命周期有两个钩子：`firstiter(agen)` 在它**第一次被迭代**（第一次 `__anext__`/`asend` 真正开始执行）时调用一次；`finalizer(agen)` 在它**已被启动、但还没关闭就被 GC** 时调用。关键点是：`finalizer` 不是"帮你关闭生成器"，它只是**通知你去调度关闭**——asyncio 注册的 finalizer 会 `loop.create_task(agen.aclose())`，所以 `finally` 里的 `await conn.close()` 才有机会跑；如果你用自己的钩子只记日志、不调用 `aclose()`，生成器帧会被丢掉，`finally` 永远不执行。显式 `await agen.aclose()` **不会**触发 `finalizer`，它直接注入 `GeneratorExit` 并执行 `finally`，这是两条不同的路径。
- **取舍**：自定义 `firstiter` 可以做泄漏归因（记录谁创建了生成器、挂在哪个请求上），但**必须委托**给原钩子或自己调度 `aclose`，否则就是"监控把清理顶掉了"。生产上更推荐用 `asyncio` 自带机制：`loop.shutdown_asyncgens()` 在停机时统一关闭仍存活的异步生成器；应用层用 `contextlib.aclosing` 或 `AsyncExitStack` 把生成器绑定到请求作用域，做到"作用域结束即关闭"，不要依赖 GC 时机。另一个取舍是 `finalizer` 里不能 `await`（它是同步回调），只能 `create_task`/`call_soon_threadsafe`，而且事件循环可能已经关闭，必须处理 `RuntimeError`。
- **实战**：事故里的生成器在 `yield` 处挂起，客户端断开后外层任务被取消，但生成器被一个全局缓存强引用着，直到 LRU 淘汰才 GC；此时事件循环还在，asyncio 的 finalizer 调度了 `aclose`，但 `finally` 里的 `await conn.close()` 又因为连接已被外层关闭而抛 `RuntimeError`，异常被 finalizer 的 task 吞掉，监控只看到连接数不降。修复：① 生成器改为在 `finally` 里用 `contextlib.suppress` 包住关闭；② 请求结束时显式 `await agen.aclose()`（`aclosing`），不再等 GC；③ 自定义 `firstiter` 记录创建栈，`finalizer` 里只打点并 `create_task(agen.aclose())`，不再"只记录不关闭"。

下面用最小异步生成器验证：创建时不触发、首次迭代触发 `firstiter`、显式 `aclose` 只走 `finally`、启动后被 GC 才走 `finalizer`。

```python
# 异步生成器钩子: firstiter 在首次迭代, finalizer 在"已启动但未关闭就被 GC"
import asyncio
import gc
import sys

events = []


def firstiter(agen):
    events.append(("firstiter", agen.__name__))


def finalizer(agen):
    # 注意: 这里只是记录. 真正的 asyncio 钩子会 create_task(agen.aclose())
    events.append(("finalizer", agen.__name__))


async def agen():
    try:
        yield 1
        yield 2
    finally:
        events.append(("finally", "agen"))


async def main():
    # 必须在事件循环启动后安装, 否则会被 loop 自己的钩子覆盖
    sys.set_asyncgen_hooks(firstiter=firstiter, finalizer=finalizer)

    g = agen()
    assert events == [], "创建异步生成器不会触发 firstiter"
    print("[1] 创建后事件:", events)

    value = await g.__anext__()
    assert value == 1
    print("[2] 首次 __anext__ 后:", events)
    assert events == [("firstiter", "agen")]

    await g.aclose()
    print("[3] 显式 aclose 后:", events)
    assert events[-1] == ("finally", "agen")
    assert ("finalizer", "agen") not in events, "aclose 不走 finalizer"

    # 启动后不关闭, 交给 GC: finalizer 被调用, 但我们的钩子没有 aclose
    g2 = agen()
    await g2.__anext__()
    del g2
    gc.collect()
    print("[4] 启动后 GC:", events)
    assert events[-1] == ("finalizer", "agen")
    assert events.count(("finally", "agen")) == 1, "自定义 finalizer 没有关闭生成器"

    print("[5] 结论: finalizer 只是通知, 关闭动作必须由钩子自己调度")


asyncio.run(main())
```

**追问一**：`loop.shutdown_asyncgens()` 和 `finalizer` 是什么关系？—— `shutdown_asyncgens` 会遍历事件循环弱集合里所有仍存活的异步生成器，逐个 `await agen.aclose()`，走的是显式关闭路径，因此执行 `finally`、不触发 `finalizer`。它适合停机时兜底，但依赖生成器在第一次迭代时被 `firstiter` 注册进 `loop._asyncgens`——如果应用自己替换了 `firstiter` 且没有委托给 loop 的钩子，这个弱集合就是空的，`shutdown_asyncgens` 什么也关不掉。这就是"自定义钩子导致泄漏更严重"的根因。

**追问二**：为什么 `finalizer` 里不能直接 `await agen.aclose()`？—— 钩子是同步 C 回调，没有协程上下文，不能 `await`；而且它常在 GC 期间被调用，此时可能位于任意栈帧，甚至事件循环已经关闭。正确姿势是 `loop.create_task(agen.aclose())`（在循环仍运行时），或者 `loop.call_soon_threadsafe`；同时要捕获 `RuntimeError`（循环已关闭）与 `GeneratorExit` 相关的异常，避免在 GC 期间再抛异常导致 `Exception ignored in` 噪音。

## 背诵要点

- `firstiter` 在异步生成器**第一次真正迭代**时触发；创建对象本身不触发。
- 显式 `aclose()` 直接执行 `finally`，**不触发** `finalizer`；`finalizer` 只在"已启动、未关闭就被 GC"时触发。
- `finalizer` 是通知而非关闭；asyncio 的钩子会调度 `aclose`，自定义钩子必须委托或自己 `create_task`，否则清理被静默跳过。
