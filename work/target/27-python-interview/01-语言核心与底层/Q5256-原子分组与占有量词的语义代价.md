### Q5256 · 原子分组与占有量词：灾难性回溯的语义代价与防御写法

难度：P7 ｜ 标签：正则、原子分组、占有量词、灾难性回溯、re、3.11、ReDoS

**问**：一个校验邮箱/URL 的接口被一条 30 字符的输入打满 CPU，正则形如 `^(\w+)+@`，日志显示单次匹配跑了十几秒。把内层改成 `(?>...)` 或 `*+` 之后确实快了，但另一条规则开始漏匹配合法输入。原子分组到底做了什么？它为什么能消除指数回溯？什么情况下"加原子"会改变语言、把正确匹配变成不匹配？

**答**：

- **结论**：`(?>...)`（原子分组，3.11+）和 `a*+`、`a++`、`a?+`、`a{m,n}+`（占有量词，3.11+）都表达同一件事：**这段匹配一旦成功，就不再为后续失败让出字符**。普通量词是"贪婪 + 可回退"：`a+` 先吃到最多，后面匹配失败时逐个吐字符重试；占有量词是"吃到最多就锁死"，后续失败直接整体失败。嵌套量词 `^(a+)+$` 的指数爆炸来自"把同一段 a 切成不同层数的组合"，每多一个 a 就多一倍分法；原子化后第一层就把所有 a 吃完，外层没有可回退的分支，搜索树从指数塌缩成线性。但代价是**匹配语言变小**：`a++a` 永远匹配不了任何以 a 结尾的串（a++ 吃完所有 a，后面还要 a），`(?>a+)a` 同理。原子化不是"性能开关"，而是"放弃一部分回溯能力"的语义修改。

- **取舍**：a) 能证明"这段不需要回退"时才原子化：分隔符之前的字段（`(?>\w+)@`）、固定前缀、已经用先行断言校验过的片段；b) 需要"整体校验但允许内部回退"时，用先行断言 + 反向引用 `(?=(a+))\1` 把"试探"和"消费"分开，或者重写结构（用 `[^@]+@` 代替 `(\w+)+@`）；c) 占有量词只作用于**单个量词**，原子分组作用于**整个组**（包括 alternation）：`(?>ab|a)b` 在 `ab` 上失败，因为组内选了 `ab` 后不允许改选 `a`；d) 防御 ReDoS 的根本手段是"限制输入长度 + 结构化解析"，原子化只是把已知的坏分支剪掉；对不可信 pattern（用户自定义正则）必须加超时或换线性引擎，不能靠肉眼原子化。
  还有一个反直觉的点：原子化对**没有嵌套量词**的模式几乎不带来性能收益，因为本来就没有指数树可剪；它只在你已经把热点定位到"同一段字符被反复重新划分"时才有意义，否则只是徒增不匹配风险。

- **实战**：事故形态是"URL 校验正则被 30 字符的 `aaaa...!` 打崩"，P99 从 5ms 到 12s，线程池被占满拖垮整个服务。第一步把 `^(\w+)+@` 改成 `^(?>\w+)+@`，耗时从秒级降到微秒级；第二步发现同一份规则里 `^(.+)\.example\.com$` 被"顺手原子化"成 `^(?>.+)\.example\.com$`，所有域名都不匹配了——`.+` 吃完整个域名后不允许回退，`\.example\.com` 永远等不到字符。最终方案：协议/后缀这类"后面还有固定尾巴"的片段保持普通分组，只对"分隔符之前的字段"（`(?>\w+)@`）原子化；路径部分用"否定字符类 + 原子组"限制回溯，并在网关层加 2KB 输入上限与正则超时。
  上线前用"坏输入集 + 好输入集"双向回归：坏输入验证耗时上限，好输入验证没有因为原子化而漏匹配，缺一不可。

```python
# 原子分组/占有量词: 消除指数回溯, 同时改变匹配语言
import re
import time

assert re.fullmatch(r"a++", "aaa")            # 占有量词本身能匹配
assert re.match(r"a*a", "aaa")                # 普通量词: 回退一个 a 给末尾
assert re.match(r"a*+a", "aaa") is None       # 占有量词: 不吐, 整体失败
assert re.match(r"a++a", "aaa") is None

assert re.match(r"(a+)a", "aaa")              # 普通组: 可回退
assert re.match(r"(?>a+)a", "aaa") is None    # 原子组: 锁死
print("→ 原子化改变了语言: (a+)a 匹配 aaa, (?>a+)a 不匹配")

assert re.match(r"(ab|a)b", "ab")             # 普通 alternation: 回退到 a
assert re.match(r"(?>ab|a)b", "ab") is None   # 原子组锁住整个分支选择
print("→ 原子组锁的是整组, 不只是量词")

assert re.fullmatch(r"(?>\d+)\.\d+", "12.34")
assert re.fullmatch(r"<(?>\w+)>", "<abc>")

# 指数回溯 vs 原子化: 同一条输入, 同一条模式, 只差一个 ?>
n = 22
payload = "a" * n + "!"
t0 = time.perf_counter()
assert re.match(r"^(a+)+$", payload) is None
slow = time.perf_counter() - t0

t0 = time.perf_counter()
assert re.match(r"^(?>a+)+$", payload) is None
fast = time.perf_counter() - t0

print("→ 嵌套量词:", round(slow, 4), "s | 原子分组:", round(fast, 6), "s | 倍数:", round(slow / fast, 1))
assert slow > fast * 20                       # 指数 vs 线性, 差距随 n 拉大
assert fast < 0.05

# 占有量词与单量词原子组在单分支上等价
assert bool(re.fullmatch(r"(?>a*)", "aaa")) == bool(re.fullmatch(r"a*+", "aaa"))
```

**追问一**：为什么 `^(a+)+$` 是指数级，而 `^(?>a+)+$` 是线性？—— 前者把 n 个 a 划分成"外层每组多少个 a"的所有组合：第一组 1 个、第二组 n-1 个，或第一组 2 个……每个划分失败后都要重试，复杂度约 2^(n-1)；回溯引擎按深度优先枚举这棵树，输入每多一个字符，树就翻一倍。后者在第一次 `(?>a+)` 就把所有 a 吃光并锁定，外层 `+` 只有"再开一组"这一条路，而剩余字符为空，立刻失败；没有分支可枚举，复杂度 O(n)。注意：原子化只是剪掉了"重新划分"的能力，如果模式里还有别的可回退点（比如前后各有一个 `.*`），仍可能组合爆炸——所以它只能治"已知的嵌套量词"，不能给任意正则上保险。
  判断能否原子化的一句话标准：这段匹配成功后，后续**不可能**因为需要更多/更少字符而要求它吐回来；只要有一丝"可能要让出"的可能，就不要原子化。

**追问二**：为什么 `(?=...)` + 反向引用能"既校验又不锁死"？什么时候必须用这种写法？—— `(?=(a+))\1` 的工作方式是：先行断言在当前位置尝试 `a+`，把结果捕获到组 1，但**不消费**输入；然后 `\1` 精确消费与组 1 相同的文本。这样"试探"只发生一次，后续匹配失败时不需要重新划分 `a+`，既避免了嵌套回溯，又保留了"用捕获内容做后续约束"的能力。必须用它的场景是"需要回头引用前面匹配到的具体内容"——比如配对标签 `<(\w+)>.*?</\1>`、重复词检测、模板占位符；原子组做不到"引用刚匹配的内容"，因为它根本不保存可回退的中间状态。代价是可读性差、组号易错，工程上应封装成带注释的常量。
  还有一个实践差异：先行断言里的捕获组会影响 `group()` 编号，重构时插入一个新组就可能让 `\1` 指错对象；这也是很多团队宁愿写两个正则、分两步校验的原因。

## 背诵要点

- 原子分组 `(?>...)` 与占有量词 `*+`/`++`/`?+`/`{m,n}+` 都是"匹配后不吐字符"，把嵌套量词的指数搜索树剪成线性。
- 它们改变匹配语言：`a++a`、`(?>a+)a` 永不匹配；原子组锁整个分组（含 alternation），占有量词只锁单个量词。
- 防御 ReDoS 靠"长度上限 + 结构重写 + 超时/线性引擎"，原子化只对可证明不需回退的片段使用；需要引用匹配内容时用 `(?=(...))\1`。
