### Q5125 · ast 模块版本演进与源码分析工具兼容

> 难度:★★★★☆ | 标签:版本演进, AST, 静态分析

**问**:团队维护的代码扫描工具在 3.12 上崩了，报 `ast.Num` 不存在。ast 模块这些年怎么变的？"AST 是版本锁定物"对工具链意味着什么？3.9 的 `ast.unparse`、3.8 的 `end_col_offset` 各解决了什么痛点？

**答**:结论：ast 节点是**没有兼容承诺的内部表示**——3.8 加 `end_col_offset`（错误定位/重构工具的基础）、3.9 加 `ast.unparse`（AST→源码回写）、3.8 起弃用的 `ast.Num/ast.Str/ast.Bytes/ast.NameConstant/ast.Ellipsis` 原计划 3.12 删除，实际**推迟到 3.14 才移除**（统一为 `ast.Constant`）——弃用延期本身就是"AST 无兼容承诺"的证据，别赌截止日期、3.13/3.14 继续为 PEP 649/701 调整注解与 f-string 的节点结构。教训链：这些变更 3.8→3.12 期间一直有 warning，工具链若"吞掉弃用告警"，升级时就会一次性爆雷——静态分析工具必须把"目标 Python 版本"当一等输入。实战要点：a) 位置参数/`type_comment` 等构造参数也在变，构造节点用关键字参数并只依赖 `_fields`；b) 想拿"当前解释器的稳定视图"用 `ast.parse(..., feature_version=(3, 9))` 限制语法版本，但它只限语法、不锁节点结构；c) `ast.unparse` 是"反编译"不是还原（注释、格式全丢），round-trip 校验要用 compile+eval 语义对等，别比字符串。

```python
import ast, sys, warnings

SRC = "x = 1 + 2 * len('hi')  # 注释"
tree = ast.parse(SRC)

# ---- 1) 节点结构：3.8 起 end_col_offset ----
add = tree.body[0].value
print(f"BinOp 位置: {add.lineno}:{add.col_offset} -> {add.end_lineno}:{add.end_col_offset}")
print("BinOp 字段:", add._fields)      # 只依赖 _fields，别依赖构造签名

# ---- 2) 弃用节点：ast.Num 已在 3.12 移除，写法要统一到 Constant ----
print("Constant 节点占位:", isinstance(add.right.args[0], ast.Constant) if isinstance(add, ast.Call) else isinstance(tree.body[0].value.right, ast.BinOp))
with warnings.catch_warnings(record=True) as wlist:
    warnings.simplefilter("always")
    try:
        ast.parse(SRC) and getattr(ast, "Num", None)   # 探测是否存在
        print(f"ast.Num 存在性: {getattr(ast, 'Num', '已移除(3.14+)')}，"
              f"当前 {sys.version_info.major}.{sys.version_info.minor}")
    except Exception as e:
        print("探测异常:", e)
    print("捕获告警数:", len(wlist), "（旧版本此处会出现 DeprecationWarning）")

# ---- 3) 3.9 ast.unparse：AST -> 源码（注释/格式丢失） ----
print("unparse:", ast.unparse(tree))

# ---- 4) feature_version 只锁语法，不锁节点 ----
try:
    ast.parse("x := 1", feature_version=(3, 7))
    print("feature_version=(3,7) 仍解析了 walrus? 不应到达")
except SyntaxError as e:
    print("feature_version=(3,7) 拒绝 walrus:", e.msg)

# ---- 5) 语法版本边界检测：工具链按目标版本校验 ----
def check_compat(code: str, target=(3, 8)):
    try:
        ast.parse(code, feature_version=target)
        return True
    except SyntaxError as e:
        return f"不兼容 {target}: {e.msg}"
print("match 语句 vs (3,8):", check_compat("match x:\n    case 1: pass", (3, 8)))
print("match 语句 vs (3,10):", check_compat("match x:\n    case 1: pass", (3, 10)))
```

**追问一层**:为什么 CPython 不给 ast 节点做向后兼容承诺？（AST 与编译器实现强耦合，语法演进必然改节点；稳定层是 `compile`/字节码语义与 tokenize API，工具应订阅"语法"而非"节点"）。
**追问二层**:3.12 f-string 解禁（PEP 701）后 tokenize 和 ast 的输出有什么结构变化？（f-string 从"单字符串 token"变为可内嵌任意表达式的 `FString`/`TemplateStr` 节点，旧版按字符串处理的格式化器/安全扫描器会漏检嵌套表达式）。
**追问三层**:如何让扫描工具同时支持 3.9-3.13？（入口用 `feature_version` 归一语法、遍历只走 `ast.walk`+`_fields`、对 Constant 归一化旧节点、CI 矩阵跑全版本并用 unparse 对拍）。

## 背诵要点
- ast 节点无兼容承诺：3.8 end_col_offset、3.9 unparse、3.8 弃用 Num/Str/Bytes/NameConstant（推迟到 3.14 才删），统一 Constant。
- `feature_version` 只限语法不限节点；工具遍历只依赖 `_fields`/`ast.walk`。
- unparse 是反编译（丢注释与格式），round-trip 校验看语义对等不看字符串。

## 复盘追问
- 升级 3.12 后内部 lint 工具崩溃，除了补丁，如何建立"AST 兼容回归矩阵"防止下次升级再爆？
- 安全扫描器用 ast 检测 eval 调用，3.12 前后 f-string 内嵌 `eval(x)` 的行为差异如何被 PEP 701 暴露？
