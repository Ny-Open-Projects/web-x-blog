### Q5003 · PEP 649/749 延迟注解求值（3.14 默认）对 typing 生态的影响

> 难度:★★★ | 标签:PEP 649, PEP 749, annotationlib

**问**：3.14 把 PEP 649 延迟注解求值设为默认，它和 3.7 时代的 `from __future__ import annotations`（PEP 563）有什么本质区别？运行时访问 `__annotations__` 的行为变了什么？`typing.get_type_hints` / dataclass / Pydantic 这类「注解消费者」要改什么？

**答**：结论：PEP 563 是「存字符串、永不求值」（消费者各自 eval，碎片化且丢语义），PEP 649 是「编译成惰性求值函数，按需求值且结果可缓存」——注解变成 `__annotations__` 上一个延迟对象（annotate function，PEP 749 定义其内省协议），首次求值成功后缓存，错误在使用点才暴露但保留完整异常链。对消费者的影响：1) `obj.__annotations__` 直接访问拿到的是**延迟求值代理**（`annotationlib.Format.VALUE` 才是真实值），旧代码「假设它是 dict」在 3.14 会拿到 `typing.ForwardRef` 风格的惰性对象——消费方要改用 `annotationlib.get_annotations(obj, format=...)` 显式选格式；2) 前向引用不再是字符串拼凑：引用未来名字的注解在求值时名字已绑定，`get_type_hints` 的全局/局部命名空间拼接这种老 hack 大幅退化；3) dataclass、Pydantic 这类「靠注解驱动」的框架从「解析字符串」变成「调 annotate 函数」，Pydantic v2 后续版本已跟进 `annotationlib`。取舍：懒求值让「注解里写昂贵表达式」的成本从定义期挪到首次访问，库作者要注意别在导入路径上意外触发全量求值。实战：迁移期用 `from __future__ import annotations` 写法与 3.14 行为并存，消费代码统一走 `annotationlib.get_annotations` 是兼容两个时代的稳妥路径。

```python
# 基线:Python 3.14(PEP 649 默认)。3.13 及以下缺库降级:用
# typing.get_type_hints 前向引用字符串方案,行为差异见注释。
import sys

class Node:
    # 前向引用:3.14 下求值时 Link 已绑定,天然可行
    nxt: "Link | None" = None

class Link:
    prev: "Node | None" = None

if sys.version_info >= (3, 14):
    import annotationlib
    # 直接访问 __annotations__ 得到延迟代理;显式选格式取真值:
    hints = annotationlib.get_annotations(Node, format=annotationlib.Format.VALUE)
    print(hints)            # {'nxt': Link | None} —— 已是真实对象,非字符串
    # 求值失败时的行为:raise 时带完整链,不再是被 eval 吃掉的裸 NameError
else:
    import typing
    print(typing.get_type_hints(Node))   # 3.13-:靠字符串 eval 展开
```

**追问**：
1) PEP 563 为什么最终没被采纳为默认？——字符串注解丢失求值时机：运行时框架（dataclass、Pydantic、FastAPI）各自 eval 字符串，作用域规则各写一套，且 `X | None` 这种表达式在字符串态无法校验；PEP 649 把「求值」还给语言本身，协议统一。
2) 注解求值失败（名字不存在）在 3.14 什么时候暴露？——首次访问 `__annotations__` 时；定义类时不报错。与 3.13 前字符串注解行为相似，但异常是真实求值异常且带链，可定位。
3) 对「运行时校验框架」的性能影响？——懒求值意味着导入一个带海量注解的模块不再立刻求值所有注解，冷启动更快；但框架在首个请求时集中求值，可能造成首请求抖动——预热路径要显式触发（如 Pydantic 构建模型时已强制展开）。
