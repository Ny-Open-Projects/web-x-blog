### Q5160 · True/1/1.0 同 key 合并事故复盘

难度：P6 ｜ 标签：bool、hash、dict、事故复盘、类型边界

**问**：`{True: 'a', 1: 'b'}` 的结果是什么、为什么 True 和 1 共享一个槽位？一次"状态统计字典把 0 和 False 合并"的事故是如何发生的？哪些值会跨类型同 hash，如何设计 key 边界防住？

**答**：
结论：`bool` 是 `int` 的子类，`hash(True) == hash(1) == hash(1.0) == hash(Decimal(1))`，且 `==` 全等——dict 按 (hash, ==) 判同，所以这些 key **指向同一个槽位**，后写覆盖前写，`{True: 'a', 1: 'b'}` 得 `{True: 'b'}`（repr 显示首个 key 的形式）。事故模式：用原始输入类型做统计/开关字典的 key——API 返回 0/1，网关某处转成 `bool`，两条路径写同一个字典，`stats[1]` 和 `stats[True]` 互相覆盖；JSON 里 `false` 落到 Python 是 `False`，与上游发的 `0` 合并成一条。同类陷阱还有 `1 == 1.0 == Fraction(1)`、字符串与 bytes **不**合并（不跨类型相等）。

取舍：修边界比修 bug 重要——跨层传输的 key 统一成单一类型规范（推荐 str）：① 入口把 bool/int/float 归一化成 `"true"/"1"/"1.0"` 这类带形态前缀的规范串；② 确实需要保留类型区分时用 `(type_tag, value)` 元组当 key；③ 统计字典禁止裸接外部输入，加一层 `normalize_key()`。不要指望 hash 随机化或 dict 实现变化——(hash, ==) 判同是协议级约定，子类相等就必须合并（这是 LSP 的一致性要求，也是`bool` 设计的历史决定）。

实战：对账/统计类代码加不变量测试：`len(set(keys)) == len(expected)`；mypy 开 `strict` 后 `dict[int, int]` 接 `True` 会被静态拦截（bool 可赋给 int 但 dict key 语义告警有限，需配合 `strict-equality` 与代码评审）；日志里把 stats 字典的 key 类型分布打出来，快速发现混型。

```python
# 1) 同槽位合并演示
d = {True: "a", 1: "b", 1.0: "c"}
print(d)                                   # {True: 'c'} —— 三个 key 同一槽位，后写覆盖
print(hash(True) == hash(1) == hash(1.0), True == 1 == 1.0)
print("key type:", type(list(d)[0]).__name__)   # bool（保留首次插入的 key 对象形式）

# 2) 事故复现：状态统计被 bool/0 合并
stats = {}
def report(code, ok):                      # 两条路径写同一 key
    stats[code] = stats.get(code, 0) + 1
report(200, ok=True); report(200, ok=True)
report(True, ok=True)                      # 某处误把 ok 当 code 传入
print("stats:", stats, " —— 200 与 True 合并")

# 3) 跨类型同 hash 的家族
from decimal import Decimal
from fractions import Fraction
same = {1, True, 1.0, Decimal(1), Fraction(1)}
print("set size (all equal):", len(same))          # 1
print("str/bytes 不合并:", {"x"} == {b"x"}, hash("x") != hash(b"x"))

# 4) 规范化 key 边界
def normalize_key(k):
    if isinstance(k, bool):
        return f"bool:{k}"
    if isinstance(k, int):
        return f"int:{k}"
    if isinstance(k, float):
        return f"float:{k!r}"
    return f"str:{k}"

norm = {}
norm[normalize_key(True)] = 1
norm[normalize_key(1)] = 1
print("normalized:", norm)
```

**追问一**：为什么 dict 保留"首次插入 key 的形式"（`{1: 'x'}` 再 `d[True]=2` 后 repr 显示 1）？——判同后只更新 value，key 对象不替换（省一次写入、保持引用稳定性）；这使 repr 具有不确定性（插入顺序决定显示哪个等价形式），所以**不要对 dict repr 的 key 形态做断言测试**，用 key 的语义值断言。

**追问二**：JSON 的 `true` 与 Python 的 `1` 在 round-trip 中怎么互相污染？——`json.loads('{"a": 1}')` 得 int，序列化回去仍是 `1`；但如果中间某层把数值当布尔解释（如 `if payload["flag"]:` 对 `0` 判假），再 `json.dumps({"flag": bool(...)})` 就变成 `false`——类型漂移发生在"语义解释"而非编解码层，治理靠 schema 校验（Pydantic 严格模式 `StrictBool/StrictInt`）在入口定死。

## 背诵要点
- bool 是 int 子类：`hash(True)==hash(1)==hash(1.0)==hash(Decimal(1))`，dict/set 按 (hash,==) 合并、后写覆盖。
- dict 合并时保留首次插入的 key 形态，repr 形态不可作为断言依据。
- 防线：key 规范化为单一类型（str）或 (type_tag, value) 元组；JSON 联动用 Pydantic 严格模式。

## 复盘追问
- 风控规则字典里 `0` 与 `False` 合并导致一条规则被静默关闭，如何复盘并建立防回归测试？（合并链路还原、normalize_key 边界、len 不变量测试）
- 为什么不能靠"自定义 hash 让 True 和 1 不同"解决？（== 仍相等，dict 判同要求 hash 相同是必要条件而非充分，自定义必须保持 hash(相等对象) 一致的契约）
