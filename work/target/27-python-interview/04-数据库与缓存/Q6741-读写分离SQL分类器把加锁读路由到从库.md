### Q6741 · 读写分离的 SQL 分类器：`SELECT ... FOR UPDATE` 被当成只读路由到从库

难度：P6 ｜ 标签：读写分离、SQL 解析、悲观锁、路由

基线：Python 3.12；正则 + 词法粗分模拟中间件（ProxySQL / ShardingSphere / 自研路由）的语句分类。

**问**：读写分离中间件按"`SELECT` 开头走从库，其余走主库"分流。上线后发现两类怪事：① 秒杀扣库存偶发"超卖"，日志里 `SELECT ... FOR UPDATE` 明明执行成功；② 一个 `WITH ... UPDATE` 的批量订正语句偶尔报 `The MySQL server is running with the --read-only option`。SQL 语法都没错，问题出在哪？

**答**：
- **结论**：`SELECT` 开头不等于只读。至少四类语句会被首词规则误判：① **加锁读**——`SELECT ... FOR UPDATE` / `FOR SHARE` / `LOCK IN SHARE MODE`，它在从库上拿不到主库的行锁，两个事务各自在自己的从库快照上读到同一库存，扣减全部"成功"，超卖；② **CTE 写语句**——`WITH t AS (...) UPDATE/DELETE ...`，首词是 `WITH`；③ **`SELECT ... INTO OUTFILE`** 有写副作用；④ **注释前缀**——`/* trace_id=... */ SELECT ...` 首字符不是 `SELECT`，被误发到主库（安全但白吃主库容量）。反过来 `EXPLAIN UPDATE`、`SHOW` 这类首词非 SELECT 却被发到主库，也是容量浪费。
- **取舍**：三种做法：① 词法分类（去注释 + 取首关键字 + 扫描锁/写提示词），零依赖、微秒级，但永远有漏判（存储过程、`/*!50000 ... */` 版本注释、多语句）；② 真正解析 AST（`sqlglot`/`vitess sqlparser`），准确但要维护方言，且每条 SQL 多几百微秒；③ **事务感知**：连接一旦 `BEGIN`，后续所有语句强制走主库——这条最便宜也最有效，因为事务里读从库本来就会破坏一致性快照。生产上组合用：事务内粘主 + 语句分类器兜事务外。
- **实战**：① 分类器必须"失败即主库"（默认拒绝走从库），而不是"看不懂就当只读"；② 对 `FOR UPDATE`/`FOR SHARE`/`INTO OUTFILE`/`NEXT VALUE FOR` 做关键词兜底；③ 上线前用 `performance_schema` 或代理日志回放一周的真实 SQL，跑分类器对账误判率；④ 从库开启 `super_read_only`，让误路由**立刻报错**而不是静默写坏数据——这是最后一道闸。

```python
"""首词分类 vs 词法分类：谁把加锁读送去了从库。"""
import re

WRITE_WORDS = {"insert", "update", "delete", "replace", "merge", "create",
               "alter", "drop", "truncate", "rename", "grant", "call"}
READ_HEADS = {"select", "show", "explain", "desc", "describe"}
# 出现即代表有写语义或需要主库锁
PRIMARY_PHRASES = (
    "for update", "for share", "lock in share mode",
    "for no key update", "for key share",
    "into outfile", "into dumpfile", "next value for",
)


def strip_comments(sql: str) -> str:
    sql = re.sub(r"/\*.*?\*/", " ", sql, flags=re.S)     # 含 /*!50000 */ 版本注释
    sql = re.sub(r"--[^\n]*", " ", sql)
    sql = re.sub(r"#[^\n]*", " ", sql)
    return sql


def naive_route(sql: str) -> str:
    """首词规则：中间件里最常见、也最容易翻车的那种。"""
    return "replica" if sql.lstrip().lower().startswith("select") else "primary"


def smart_route(sql: str, in_txn: bool = False) -> str:
    if in_txn:
        return "primary"                  # 事务内一律主库，别让快照分裂
    toks = re.findall(r"[a-z_]+", strip_comments(sql).lower())
    if not toks:
        return "primary"                  # 看不懂就主库：fail-closed
    body = " ".join(toks)
    if any(p in body for p in PRIMARY_PHRASES):
        return "primary"                  # 加锁读 / 导出 / 取序列
    if toks[0] in WRITE_WORDS:
        return "primary"
    if toks[0] == "with":                 # CTE 可能是 WITH ... UPDATE
        return "primary" if any(t in WRITE_WORDS for t in toks) else "replica"
    if toks[0] in ("explain", "desc", "describe"):
        # EXPLAIN ANALYZE UPDATE 会真的执行写，不能在从库跑
        return "primary" if any(t in WRITE_WORDS for t in toks) else "replica"
    if toks[0] in READ_HEADS:
        return "replica"
    return "primary"


CASES = [
    "SELECT id, stock FROM item WHERE id = 1",
    "SELECT id, stock FROM item WHERE id = 1 FOR UPDATE",
    "/* trace_id=9f2a */ SELECT id FROM item WHERE id = 1",
    "WITH stale AS (SELECT id FROM item WHERE stock = 0) "
    "UPDATE item SET status = 'sold' WHERE id IN (SELECT id FROM stale)",
    "SELECT * FROM item INTO OUTFILE '/tmp/x.csv'",
    "EXPLAIN ANALYZE UPDATE item SET stock = stock - 1 WHERE id = 1",
]

if __name__ == "__main__":
    print(f"{'场景':<44}{'首词规则':<10}{'词法分类':<10}{'结论'}")
    for sql in CASES:
        n, s = naive_route(sql), smart_route(sql)
        verdict = "一致" if n == s else "误判"
        print(f"{sql[:42]:<44}{n:<10}{s:<10}{verdict}")

    # 事务感知：同一个 SELECT，在事务里必须回主库
    q = "SELECT stock FROM item WHERE id = 1"
    print("\n事务外 :", smart_route(q, in_txn=False))
    print("事务内 :", smart_route(q, in_txn=True), "-> 快照必须与后续 UPDATE 同源")

    # 从库 super_read_only 是最后一道闸：误路由要炸，不要静默成功
    misrouted = "SELECT id FROM item FOR UPDATE"
    print("\n误路由到从库的语句:", misrouted)
    print("从库开启 super_read_only 后 -> ERROR 1290 (HY000): read-only")
    print("结论：首词规则只能做兜底；事务粘主 + 加锁读识别 + 从库只读，三层一起上")
```

**追问一**：为什么"事务内所有语句走主库"比逐条精准分类更可靠？

→ 解析：读写分离破坏的是**快照一致性**：同一事务里先读从库（旧快照）再写主库，等于在旧数据上做决策（典型是"读库存 10 → 扣 1 → 写 9"，把别人已扣的覆盖掉）。事务边界天然是"一致性作用域"，在 `BEGIN` 时选一次路由，比在每条 SQL 上猜语义更省也更对。代价是事务里的大报表查询会压主库——那就把报表拆出事务，而不是让分类器去赌。

**追问二**：`/*!50000 ... */` 这种版本注释为什么能绕过大部分正则分类器？

→ 解析：MySQL 会执行版本号 ≥ 50000 的注释内容，也就是说**注释本身可能是 SQL**（`/*!50000 UPDATE ... */`）。只做 `re.sub(r"/\*.*?\*/", ...)` 会把它整段删掉，分类器看到空语句或只剩 `SELECT`，于是一条写语句被当成只读。防法是：分类前先识别 `/*!` 前缀并保留其内容参与词法分析，或者干脆在代理层禁用版本注释（`--skip-version-comment` 不可行时用白名单校验 SQL 模板）。
