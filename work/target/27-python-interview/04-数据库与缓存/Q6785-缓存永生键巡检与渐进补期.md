### Q6785 · 内存又悄悄涨了：缓存永生键的巡检与渐进补期治理

难度：P6 ｜ 标签：永生键、TTL巡检、内存缓涨、SCAN分桶、渐进补期

基线：Python 3.12；模拟无 TTL 键的漏写路径、按前缀分桶的 TTL 巡检盘点、渐进补期（分批补 TTL 避免过期风暴）与回滚台账，全标准库实跑。

**问**：Redis 内存水位每周涨一点，重启前从不回落，看 bigkeys 又没有单个大键——最后发现一堆业务键压根没设 TTL。永生键是怎么被批量生产出来的？怎么在不影响线上的前提下盘点和治理？为什么补 TTL 不能一次全补？

**答**：
- **结论**：永生键（无 TTL 键）的三大来源：① 代码漏写——`SET` 而不是 `SET EX`，常见于"先存了再说"的过渡代码；② 命令原子性坑——INCR 后 EXPIRE 分两步，中间异常就成了永生（Q6740 专卡）；③ 数据演化——原来是会话缓存（有 TTL），后来被运维"为保稳定"手动 PERSIST 掉，或业务把 Redis 当主存储用，语义从缓存漂移成存储。治理的三步：**盘点**（SCAN 遍历 + 对每键读 TTL，按前缀分桶统计无 TTL 键的数量与内存占比）、**裁决**（每个前缀过一遍业务语义：该过期的补期、该迁移的迁走、确实要持久的迁出 Redis）、**渐进补期**——一次性给百万键补上同一 TTL，到期瞬间集体过期，回源风暴与过期风暴（Q1420）会再来一次；正确做法是给存量键加**随机化 TTL**（基期 + 0~N 小时抖动），把过期悬崖摊成缓坡，且分批执行、每批间隔观察内存与回源曲线。
- **取舍**：① 巡检的成本控制：SCAN 是 O(1) 每步、全库遍历对主线程无阻塞（Q1002/Q1696），但逐键 TTL 是 N 次 RTT——用 pipeline 批量（Q6662 批量大小账）把百万键巡检压到分钟级，且只跑从库或低峰跑主库；② "补 TTL" 的白名单制：只有业务明确"这是缓存"的前缀才补，拿不准的前缀先进台账人工裁决，机器不替业务做语义决定；③ 治理的落地钩子：巡检脚本进日常巡检（Q2785 巡检报告）与 CI——新代码评审加"SET 必带 EX"的 lint 规则（封装统一 cache client 是最有效的根因手段，Q2956 封装层的同族思路）；④ 内存缓涨的归因顺序：先看键数增长（永生键）再看单键增长（大 key）再看碎片率（Q1414），三者曲线形态不同。
- **实战**：① 统一封装缓存客户端，强制 `set(key, value, ttl)` 签名——没有无 TTL 的入口，这是把"漏写"从依赖人的自觉变成结构性不可能；② 建立前缀登记表：每个前缀的 owner、语义（缓存/计数/去重）、期望 TTL，巡检脚本对照登记表出差异报告；③ 告警口径：`无TTL键数周环比` + `内存水位周环比` 双指标，前者是因后者是果；④ 治理灰度：先对"明显是缓存语义"的前缀小批量（1%）补期，观察回源 QPS 无尖峰再放量。

```python
"""Q6785 永生键治理: SCAN 巡检盘点无TTL键 -> 渐进补期(随机抖动+分批)。"""
import random
from collections import defaultdict

# 模拟 Redis: key -> (value_size_kb, ttl_seconds)  ttl=None 即永生键
STORE: dict[str, tuple[int, int | None]] = {}


def seed():
    for i in range(60):                       # 50 个正常 session 键
        STORE[f"sess:{i}"] = (2, 3600)
    for i in range(120):                      # 120 个漏写 TTL 的订单快照
        STORE[f"order:detail:{i}"] = (8, None)
    for i in range(20):                       # 30 个计数器 (语义是持久)
        STORE[f"cnt:page:{i}"] = (1, None)


def scan_audit(store: dict) -> dict[str, dict]:
    """按前缀分桶盘点: 每桶的键数 / 无TTL数 / 内存占比."""
    buckets = defaultdict(lambda: {"n": 0, "no_ttl": 0, "kb": 0})
    for k, (kb, ttl) in store.items():        # SCAN 遍历语义: 无阻塞全量
        p = k.split(":")[0]
        b = buckets[p]
        b["n"] += 1
        b["kb"] += kb
        if ttl is None:
            b["no_ttl"] += 1
    return dict(buckets)


def gradated_patch(store: dict, prefix: str, base_ttl: int,
                   jitter_s: int, batch: int, ledger: list[str]) -> int:
    """渐进补期: 随机化 TTL 摊平过期悬崖, 分批执行并留台账."""
    targets = [k for k in store
               if k.startswith(prefix) and store[k][1] is None]
    patched = 0
    for i in range(0, len(targets), batch):   # 分批: 批间观察内存/回源
        for k in targets[i:i + batch]:
            ttl = base_ttl + random.randint(0, jitter_s)
            v, _ = store[k]
            store[k] = (v, ttl)
            ledger.append(f"{k} -> ttl={ttl}")
            patched += 1
    return patched


if __name__ == "__main__":
    random.seed(11)
    seed()
    audit = scan_audit(STORE)
    print("巡检盘点(按前缀):")
    for p, b in sorted(audit.items()):
        print(f"  {p:<6} 键数={b['n']:>4} 无TTL={b['no_ttl']:>4} "
              f"内存={b['kb']}KB")
    ledger: list[str] = []
    n = gradated_patch(STORE, "order", base_ttl=86400, jitter_s=43200,
                       batch=50, ledger=ledger)
    print(f"渐进补期: order:* 共 {n} 键, TTL=86400+rand(43200), 分批={len(ledger)} 条台账")
    after = scan_audit(STORE)
    cnt_kept = after["cnt"]["no_ttl"]          # 计数器语义持久, 不动
    ok = (after["order"]["no_ttl"] == 0 and cnt_kept == 20
          and len(set(v[1] for k, v in STORE.items() if k.startswith('order'))) > 1)
    print(f"校验: order 前缀清零 + cnt 前缀保留 + TTL 已随机化 -> {'通过' if ok else '异常'}")
    print("结论：永生键来自漏写/非原子/语义漂移; 治理=盘点分桶+业务裁决+渐进补期;")
    print("      统一缓存客户端强制带 TTL 是结构性根因解法")
```

**追问一**：为什么"给存量键统一补一个固定 TTL"会引发二次事故？随机化抖动的幅度怎么定？

→ 解析：补 TTL 本质是把"没有过期的键"变成"将有一批键同时过期"——如果 120 万键统一补 24h TTL，24 小时后这批键在同一时间窗集体失效，回源请求瞬间砸向数据库（就是当初建缓存想躲开的回源风暴，Q1420/Q6114 的账），同时 Redis 自身要在同一窗口驱逐/释放上百万键，主线程压力叠加。随机化把一次悬崖摊成缓坡：TTL = 基期 + rand(0, 抖动窗口)，键的到期时间均匀散开，每秒过期的键数从"百万/秒"降到"百万/抖动窗口秒"。抖动幅度的定法：**至少大于"回源系统能安全吸收的过期速率 × 键总数"的倒数**——比如 DB 能扛每秒 2000 次额外回源、100 万键，抖动窗口 ≥ 500 秒，工程上常直接取键期望 TTL 的 10%~20%（如 24h±2h），让过期速率自然贴平业务写入速率。更精细的做法是按"原键的写入时间戳"分桶错峰（写入时就散布了，补期跟着写入时间分布走），但多数场景纯随机已够用。

**追问二**：盘点 Redis 里所有键的 TTL，除了逐键 SCAN+TTL，有没有更便宜的方法？两种方法各漏什么？

→ 解析：三条路径的成本与盲区：① **逐键 SCAN + pipeline TTL**：信息最全（每个键的精确 TTL），成本 O(N) 次 RTT（pipeline 压成 O(N/批)），跑从库可完全卸载主库——缺点是键总数上亿时耗时小时级，且是"静态瞬间快照"，巡检期间新写入的键会漏；② **redis-cli --bigkeys / --memkeys**：官方内置，SCAN 采样式遍历，开销低，但它的维度是"类型与大小"，**不输出 TTL 分布**，只能定位大 key 不能定位永生键；③ **RDB 离线分析**（rdb-tools / rdb-cli 解析 dump 文件）：对生产零影响、可反复分析，RDB 里带键的过期时间戳，能算出精确的无 TTL 键清单与内存占比——盲区是"RDB 是历史时刻"（最近一次 BGSAVE），刚写入未落盘的永生键漏掉，且 fork 瞬间的 COW 内存抖动要避开高峰（Q1421）。工程组合拳：RDB 离线分析做周级全量盘点（便宜、可存档对比周环比），从库 pipeline TTL 抽样校准，两者交叉出"永生键台账"。通用原则：**生产实例上的全量遍历永远是最后手段，能落到快照/副本上的分析不下主库。**
