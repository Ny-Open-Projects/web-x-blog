### Q6564 · 二级索引数量与写放大的容量账

难度：P6 ｜ 标签：索引 / 写放大 / 容量规划 / B+Tree

**问**：一张核心订单表被业务方陆续加了 14 个二级索引，写入 TPS 3000 时 IOPS 和磁盘带宽开始扛不住。怎么把"索引数量"换算成写放大账，给索引治理定预算？

**答**：

**结论**：每个二级索引都让一次 UPDATE/INSERT 变成多份写入：行数据 + 每个含变更列的索引 B+Tree 项，还可能触发页分裂。写放大 ≈ 1（聚簇）+ Σ(涉及该索引列的写入)，再乘以 redo/binlog 的日志放大（通常再 ×2~×3）。14 个索引不是"占点空间"，而是把每次写变成 5-15 次物理写——这是容量账里最容易被漏乘的系数。

**取舍**：索引不是免费的查询加速器，是"读性能换写成本+存储"的交易。治理原则：① 未命中查询的索引（`sys.schema_unused_indexes` / `pg_stat_user_indexes.idx_scan=0`）直接下线，观察期 2-4 周覆盖业务周期；② 合并可替代索引（最左前缀覆盖：有 `(a,b)` 就不需要单列 `(a)`）；③ 大批量写入场景（ nightly ETL）考虑先删索引后重建（PG 支持并发 `CREATE INDEX CONCURRENTLY`）。防御上：新索引上线要走"读写收益 + 写放大代价"的评审，不许业务方随手加。

**实战**：容量账公式化：`IOPS_write ≈ TPS × (1 + 索引命中数 × 页写因子)`。页写因子取决于变更分布——写热点集中在尾部页时每次写只碰 1 页；随机分布时可能每索引 2-3 页（分裂+上层更新）。用 Python 把索引清单、变更列、TPS 代入，输出 IOPS 与每日写入量，直接对照磁盘规格，并输出"砍掉 N 个冷索引能省多少"。

```python
# 二级索引写放大容量账：算 IOPS 与每日写入 GB，评估砍冷索引收益
# 仅标准库，Python 3.9+
from __future__ import annotations

PAGE_BYTES = 16 * 1024  # InnoDB 页


def write_amplification(indexes: list[dict], tps: int,
                        log_factor: float = 2.0) -> dict:
    """indexes: [{'name','hot':变更是否高频,'pages_per_write':每写触页数}]"""
    idx_factor = sum(i["pages_per_write"] for i in indexes if i["hot"])
    amp = 1 + idx_factor  # 聚簇 + 索引项
    iops = tps * amp
    daily_gb = iops * PAGE_BYTES * 86400 / 1024**3
    return {"amp": amp, "write_iops": round(iops), "daily_write_gb": round(daily_gb, 1),
            "log_write_gb": round(daily_gb * log_factor, 1)}


def main() -> None:
    indexes = [
        {"name": f"idx_{i}", "hot": True, "pages_per_write": 1}
        for i in range(14)
    ]
    r = write_amplification(indexes, tps=3000)
    print("治理前:", r)
    assert r["write_iops"] >= 3000 * 15  # 1 + 14

    # 砍掉 6 个冷索引（observation: idx_scan=0），剩 8 个
    slim = indexes[:8]
    r2 = write_amplification(slim, tps=3000)
    print("治理后:", r2)
    saved = r["daily_write_gb"] - r2["daily_write_gb"]
    print(f"每日节省数据写入 {saved:.0f} GB（日志再乘 2 倍）")
    assert saved > 500, "砍冷索引应显著降写入量"


if __name__ == "__main__":
    main()
```

**追问链**：

- 追问 1：为什么 UPDATE 未被索引覆盖的列也可能触碰索引？——二级索引叶子存的是索引列+主键，但 InnoDB 的二级索引项里还可能因 MVCC/变更列包含在联合索引里而更新；另外任何行更新都会在聚簇索引产生新版本。精确口径要用 `sys.schema_index_statistics` 的 insert/update/delete 计数看。
- 追问 1.1：PG 的 HOT update 是怎么打破这个账的？——更新列不涉及索引且新版本能放进同页时，PG 跳过所有索引插入，写放大骤降；所以 PG 上"把大字段挪出表、给热更新表留 fillfactor"直接改变容量账。
- 追问 2：怎么证明一个索引是"冷"的而砍它不翻车？——统计周期 ≥ 业务全周期（月账要覆盖月初），叠加灰度下线：先用优化器开关/隐藏索引（MySQL 8 invisible index）观察 1-2 周，查询计划无回退再物理删除，删除本身留 DDL 回滚脚本。

**背诵要点**：

1. 写放大 ≈ (1 + Σ热索引页写数) × 日志系数 2-3；14 个索引能把 3000 TPS 变成 4.5 万 IOPS、每日 TB 级写入。
2. 冷索引判定：pg_stat_user_indexes.idx_scan=0 / schema_unused_indexes，观察期覆盖完整业务周期，用 invisible index 灰度下线。
3. 最左前缀可合并冗余索引；PG 上 HOT update 与 fillfactor 是写放大的架构级优化。
