### Q6543 · 时钟跳变事故复盘：NTP 校时后，缓存提前过期、锁提前失效

> 难度:★★★★ | 标签:事故复盘, 时钟, 分布式锁

**问**：某次 NTP 大步长校时把应用机时间回拨了 30 秒，随后出现两类故障：一批缓存 key 提前失效引发回源风暴；两台机器的分布式锁"同时"持有导致数据双写。时钟和 TTL/租约到底是什么关系？怎么写代码才能免疫本机时钟跳变？

**答**：结论：带 TTL 的系统里，**到期判定依赖"时间源"**——用墙上时钟（time.time / datetime.now）算过期，时钟回拨就会把还没到期的 key/锁判成"已过期"；时钟前跳则反过来让过期判定推迟、锁超时释放变慢。免疫方案是**到期判定统一用单调时钟**（time.monotonic）或让 TTL 只存"到期时刻"由权威存储（Redis/DB 服务器时钟）判定，应用本机时钟只做展示。

机理与实战：
- **事故链条一（缓存）**：本地缓存模块把 `expires_at = time.time() + ttl` 存进去，回拨后 `time.time() < expires_at` 恒为假 → 全部判过期 → 同步回源打爆 DB。正确做法：本地缓存存 `deadline = time.monotonic() + ttl`，monotonic 不随 NTP 回拨。
- **事故链条二（锁）**：锁租约 `lease_until = time.time() + 30`，回拨让 A、B 两台都认为"对方已超时"，同时抢锁成功。修复优先级：① 到期判定改 monotonic；② 锁的权威判定放 Redis（`SET NX PX` + Lua 检查），本机只做乐观判断；③ 关键写入带 fencing token，时钟异常时宁可拒绝服务。
- **运维配合**：NTP 用 slewing（渐变步进，默认就是 slew）而非 step；跳变超阈值告警；对时钟极度敏感的服务上时钟监控（chronyc tracking / offset 指标）。
- **边界**：monotonic 不能跨进程比较、重启后无意义，所以"跨机租约"永远不能只靠本机 monotonic——这正好引出 Redis/DB 做权威方的分层设计。

```python
# 基线:Python 3.10+;纯标准库,演示墙上时钟 vs 单调时钟在 TTL 判定上的差异
from __future__ import annotations
import time


class WallClockCache:
    """反例:用 time.time() 判过期,时钟回拨即误判。"""

    def __init__(self) -> None:
        self.store: dict[str, tuple[str, float]] = {}
        self.now = 1000.0  # 模拟墙上时钟,可人为拨动

    def put(self, key: str, value: str, ttl: float) -> None:
        self.store[key] = (value, self.now + ttl)

    def get(self, key: str) -> str | None:
        item = self.store.get(key)
        if item is None:
            return None
        value, expires_at = item
        return value if self.now < expires_at else None  # 回拨后误判过期


class MonotonicCache:
    """正解:过期判定用单调时钟,免疫 NTP 回拨/前跳。"""

    def __init__(self) -> None:
        self.store: dict[str, tuple[str, float]] = {}
        self.now = 1000.0  # 模拟单调时钟:只会前进,不受校时影响

    def put(self, key: str, value: str, ttl: float) -> None:
        self.store[key] = (value, self.now + ttl)

    def get(self, key: str) -> str | None:
        item = self.store.get(key)
        if item is None:
            return None
        value, deadline = item
        return value if self.now < deadline else None


def demo() -> None:
    wall = WallClockCache()
    mono = MonotonicCache()
    wall.put("k", "v", ttl=60)   # 写入时刻墙上时钟=1000,deadline=1060
    mono.put("k", "v", ttl=60)   # 单调时钟同样从 1000 起算

    # 真实流逝 65 秒(>TTL,该过期了),但 NTP 回拨 30 秒
    wall.now = 1035.0            # 墙上时钟 = 1000 + 65 - 30
    assert wall.get("k") == "v", "回拨让过期判定被推迟:脏数据多活 30 秒"
    # 单调时钟只看流逝时长:65 > 60,正确过期
    mono.now = 1065.0
    assert mono.get("k") is None, "单调时钟按流逝时长正确判定过期"
    # 前跳场景:NTP 前跳 30 秒 → 墙上时钟把 TTL 提前判死,回源风暴
    wall2 = WallClockCache()
    wall2.now = 2000.0
    wall2.put("k2", "v2", ttl=60)   # deadline=2060
    wall2.now = 2065.0              # 真实只流逝 35 秒,但时钟前跳 30
    assert wall2.get("k2") is None, "前跳让未到期 key 被批量判过期 → 回源风暴"
    print("回拨:脏数据多活 30s ❌ / 前跳:未到期批量回源 ❌ / 单调时钟均正确 ✅")
    print("结论:TTL 到期判定一律 time.monotonic() 或交给权威存储判定")


if __name__ == "__main__":
    demo()
```

**追问一**：Redis 的 TTL 过期是按谁的时钟算的？
答：按 Redis 服务器自身时钟算（惰性删除 + 定期抽样），且 Redis 对时钟回拨有防御：过期轮询主要比较毫秒时间戳，主从同步场景下从库用服务器侧判定。但客户端 setex 的"到期后主动查"逻辑若在应用层用本地时钟再判一次，就会重新引入本事故——所以应用层二次判过期同样要 monotonic 或干脆不做二次判定。

**追问二**：fencing token 是怎么彻底解决时钟问题下的双写的？
答：锁服务每次发锁发放单调递增 token，存储端只接受"携带更大 token"的写入；即便两台机器因时钟跳变都自认为持锁，旧 token 的写会被存储层拒绝——把"对时间的信任"换成"对单调序的信任"，这是时钟类故障的终极兜底。

## 背诵要点
- 到期判定用 time.time/datetime.now 就会吃 NTP 回拨/前跳：回拨→提前"过期"回源风暴；前跳→锁释放延迟。
- 修复分层：进程内 TTL 用 time.monotonic；跨机租约/锁的权威判定放 Redis/DB；关键写入加 fencing token（单调序替代时钟信任）。
- 运维配合：NTP 用 slew 不用 step，offset 超阈值告警；monotonic 不可跨进程/重启，故只做本机判定。

## 复盘追问
- 为什么事故复盘时发现"两台机同时持锁"但日志时间戳看起来正常？（提示：日志时间戳回拨会出现乱序/重复，排查时要按 monotonic 序号或事件序排日志，不能只信墙上时间）
- 如果 Redis 主从切换恰逢时钟跳变，锁的权威判定还可靠吗？（提示：不可靠——Redlock 类方案在时钟异常时正确性降级，需 fencing token + 存储端 token 校验兜底，并限制锁用途为"效率"而非"正确性"）
