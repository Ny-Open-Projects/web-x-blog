### Q6624 · 逻辑复制初始表同步的带宽与主库负载容量账

难度：P6 ｜ 标签：容量规划 / PostgreSQL / 逻辑复制

**问**：用逻辑复制（publication/subscription）把 2TB 主库同步到新机房，初始同步（COPY 阶段）计划在业务高峰前完成。窗口只有 8 小时，怎么算这条管线跑不跑得完？初始同步对主库的冲击怎么估？

**答**：
- **结论**：初始同步的吞吐天花板 = **主库读吞吐（顺序扫+序列化）与专线带宽的较小值**。2TB = 2048GB，8 小时跑完需要 ≥ 71 MB/s 的持续端到端速率；COPY 导出是顺序扫，主库侧通常能跑到数百 MB/s，所以**瓶颈几乎总在带宽**（专线 100Mbps ≈ 12.5 MB/s，直接判死）。且 COPY 并不是纯增量成本：它挤占主库磁盘 IO 与缓冲池，热数据被扫出缓存会让线上查询命中率下滑。三条硬规矩：① 表级并行复制（subscription 的 max_sync_workers_per_subscription）只能加速多张小表，单张大表无法并行；② 复制槽在同步期间照常积压 WAL，带宽被 COPY 占满时 WAL 发送也走同一条线，相互挤压；③ 冲击对冲 = 主库读副本上做导出或限速（pq 导出带 `--max-rate` 思路/逻辑复制的 max_replication_slots 配合限流）。
- **取舍**：限速跑 8 小时完不成怎么办？三个选项排序：扩带宽（贵但一劳永逸）> 拆窗口按表分批同步（每批追平增量再下一批，总时长变长但每批可控）> 换物理流复制/快照做初始底座、逻辑复制只追增量（最快但需要两边版本与参数兼容）。决策看"是否要求一次性切流"：允许分表灰度就选拆窗口，必须整库原子切换就选扩带宽或物理底座。
- **实战**：① 先跑一张中表（10GB）实测端到端速率，用实测值外推总量，不要用规格表；② 监控三条线：COPY 速率、主库缓存命中率、复制槽 WAL 延迟，任一越线自动降 worker 数；③ 同步期间冻结大 DDL（初始 COPY 会因表结构变更失败重跑）；④ 切流前做行数+抽样校验和核对。

```python
# 初始同步容量账: 吞吐 = min(主库读, 带宽); 用实测中表速率外推
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class SyncPlan:
    total_gb: float
    bandwidth_mbps: float          # 专线带宽
    source_read_mbps_mb_s: float   # 主库侧导出速率 MB/s
    hours: float                   # 窗口


def mbps_to_mbs(mbps: float) -> float:
    return mbps / 8


def throughput(plan: SyncPlan) -> float:
    return min(plan.source_read_mbps_mb_s, mbps_to_mbs(plan.bandwidth_mbps))


def finish_hours(plan: SyncPlan) -> float:
    return plan.total_gb * 1024 / throughput(plan) / 3600


def main() -> None:
    p = SyncPlan(total_gb=2048, bandwidth_mbps=100,
                 source_read_mbps_mb_s=300, hours=8)
    assert throughput(p) == 12.5                # 带宽是瓶颈
    assert finish_hours(p) > 45                 # 8h 窗口判死
    p2 = SyncPlan(total_gb=2048, bandwidth_mbps=1000,
                  source_read_mbps_mb_s=300, hours=8)
    assert abs(throughput(p2) - 125) < 1e-6
    assert finish_hours(p2) < 5                 # 千兆专线 5h 内跑完
    print(f"100M: {finish_hours(p):.0f}h(不可行) -> 1000M: "
          f"{finish_hours(p2):.1f}h, 瓶颈=带宽")
    print("OK: 先用10GB中表实测速率再外推; 同步期冻结DDL并监控命中率/WAL延迟")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么初始同步期间"复制槽 WAL 延迟"和 COPY 速率会互相挤压？
→ 一句话提示：初始 COPY 与 WAL 发送共用同一出口带宽，COPY 打满后 WAL 发不出去，槽位积压在主库磁盘；反过来为保 WAL 挂了限速，COPY 又拖时间——所以带宽账要按"COPY + WAL 双份流量"预留。

**追问 2**：max_sync_workers_per_subscription 开大有什么反效果？
→ 一句话提示：worker 并行扫表叠加主库读放大，挤占缓存与 IO 使线上查询劣化，且每个 worker 独占一个槽相关连接；并行只摊小表，对单张大表无效。

## 背诵要点
- 吞吐 = min(主库导出速率, 带宽)，瓶颈几乎总在带宽；2TB/8h 需 ≥71MB/s 持续端到端。
- 容量决策三选一：扩带宽 / 拆表分批窗口 / 物理流复制做底座+逻辑复制追增量。
- 先实测中表速率再外推；同步期监控 COPY 速率、缓存命中率、复制槽 WAL 延迟并冻结 DDL。

## 复盘追问
- 为什么"用规格表算速率"会严重失真？提示：端到端速率受主库 IO、序列化、专线实际可用带宽、WAL 挤压多重折损，规格值是理论上限，实测中表外推才有决策价值。
- 分表分批同步的总时长为什么比一次全量长？还值得选吗？提示：每批要等增量追平再切下一批，串行批次叠加；换来的是每批可灰度可回滚、主库冲击可控——允许分表切换时是更稳的选择。
