### Q6569 · 先读后写导致的丢失更新事故复盘

难度：P6 ｜ 标签：事务 / 隔离级别 / 丢失更新 / 事故复盘

**问**：积分系统在 Read Committed 下运行，两个并发请求各自 `SELECT balance` 后 `UPDATE balance = 读到的值 + 100`，用户积分少了 100。复盘：为什么 RC 挡不住这种丢失更新？修复方案怎么排序？

**答**：

**结论**：Read Committed 只保证"读到的都是已提交数据"，不保证"读和写之间没人插队"——SELECT 是快照读不加锁，两个事务都能读到同一旧值，后提交的 UPDATE 会覆盖先提交的结果，这就是丢失更新（lost update）。RC 下"读→计算→写回"模式天生不安全，修复优先级：① 原地更新 `UPDATE ... SET balance = balance + 100`（让计算进 SQL，依赖行锁串行化）；② SELECT ... FOR UPDATE 显式行锁再计算；③ 乐观并发：带版本号 `WHERE version = ?` 更新，失败重试。方案 ① 改动最小且无死锁增量，是首选。

**取舍**：① 原地更新：原子但表达力受限（复杂业务逻辑放不进一条 SQL）；② FOR UPDATE（Pessimistic）：语义直白，但锁窗口拉长、锁顺序管理不当引死锁，且持锁期间事务不能太长；③ 乐观锁：无锁等待、吞吐好，但冲突率高时重试风暴（对热点账户重试次数与冲突概率成正比）。热点行（秒杀库存、大 V 账户）的正确解是 ①+内存聚合/队列化，而不是任何一种行锁。

**实战**：排查存量代码里的危险模式：grep `SELECT.*balance|SELECT.*stock` 后跟 UPDATE 的服务代码；ORM 层面 SQLAlchemy 的 `query.get()` + 属性赋值 + commit 是高危写法，改用 `update()` 表达式。加防线：对关键计数列加 CHECK 约束防负值、写审计流水表（每笔变动留 before/after），让下次事故能快速定位是并发覆盖还是业务 bug。

```python
# 模拟 RC 下两种写法的并发结果差异（协程交错模拟，无第三方依赖）
# 仅标准库，Python 3.9+
from __future__ import annotations

import threading


def read_modify_write(balances: dict, lock_free_reads: bool) -> int:
    """模拟：读余额（快照读，不加锁）→ 算 → 写回绝对值。"""
    b = balances["b"]  # 两个事务都读到同一个旧值
    balances["b"] = b + 100  # 后写覆盖先写
    return balances["b"]


def in_place_update(balances: dict) -> int:
    """模拟：UPDATE SET b = b + 100（行锁内原子执行）。"""
    # 用锁模拟行锁串行化
    with threading.Lock():
        balances["b"] += 100
    return balances["b"]


def main() -> None:
    # 丢失更新：两个并发事务，读同值 100，各自 +100，最终 200（应 300）
    b1 = {"b": 100}
    r1 = read_modify_write(b1, True)
    b_snap = 100  # 第二个事务读到的快照（第一个提交前）
    r2 = b_snap + 100  # 第二个事务写回 200，覆盖 200
    b1["b"] = r2
    print(f"先读后写：期望 300，实际 {b1['b']} → 丢失更新")
    assert b1["b"] == 200

    # 原地更新：行锁串行，结果正确
    b2 = {"b": 100}
    in_place_update(b2)
    in_place_update(b2)
    print(f"原地更新：期望 300，实际 {b2['b']}")
    assert b2["b"] == 300

    # 乐观锁示意：版本不匹配则重试
    row = {"balance": 100, "version": 5}
    stale = {"v": 4}
    assert stale["v"] != row["version"], "CAS 失败应重试而非写回"
    print("乐观锁：WHERE version=4 不命中 → 读新值重试")


if __name__ == "__main__":
    main()
```

**追问链**：

- 追问 1：Repeatable Read（PG 的默认级别）能解决丢失更新吗？——PG 的 RR 对"写写冲突"会在提交时报 `could not serialize access`（因为 PG 的 RR 用 SSI 更严格），反而把问题暴露出来；MySQL 的 RR 则仍会静默丢失更新（UPDATE 是当前读，读到最新已提交行）。所以答案依赖具体数据库语义，不能一概而论——这正是面试官想听的分界。
- 追问 1.1：为什么"UPDATE ... SET b = b + 100"在 RC 下就安全？——UPDATE 是当前读，行锁在 UPDATE 语句内原子完成读改写；并发 UPDATE 会等前一个事务释放行锁后基于最新值加，不存在覆盖窗口。
- 追问 2：审计流水表怎么设计才能事后定位并发覆盖？——流水记 (业务键, before, after, 变更原因/trace_id, 事务时间戳)，外加全局递增的版本或 LSN；对账任务校验 `sum(流水增量) == 当前值 - 期初值`，不等即发生了未走流水的覆盖写。

**背诵要点**：

1. RC 只保证读已提交，不保证读后写之间无插队；"读→算→写回绝对值"在 RC 下必然可丢失更新。
2. 修复优先级：原地 UPDATE（计算进 SQL）> FOR UPDATE > 乐观版本号重试；热点行应队列化/内存聚合而非行锁。
3. PG RR 会报 serialize 失败而 MySQL RR 仍静默丢失更新——隔离级别语义必须按具体数据库核对。
