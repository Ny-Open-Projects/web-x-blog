### Q6559 · 数据库列加密的成本账：信封加密与密钥轮换

难度：P6 | 标签：列加密、信封加密、密钥轮换、成本工程

**问**：合规要求"身份证号必须加密存储"，但落地后查询接口全线变慢、按尾号搜索直接失效。列加密的查询代价怎么量化？密钥轮换为什么有的只要几毫秒、有的要重写全表？

**答**：
- **结论**：列加密的核心权衡是"查询能力矩阵"：确定性加密（同明文同密文）保住等值查询和 JOIN，但 BETWEEN/LIKE 全部失效且泄露频率信息；随机化加密安全性高但只支持取回后应用层过滤。轮换代价取决于轮换哪层密钥：信封加密里 KEK（主密钥）轮换只需让 KMS 重裹 DEK（毫秒级），DEK 轮换才要解密+加密+回写全表（5000 万行 × 30µs ≈ 0.4 小时，还要在线分批限速）。所以把高频轮换放在 KEK 层、DEK 按租户/表拆分以缩小重写面。
- **取舍**：不加密的检索需求（按尾号查手机号）用"冗余脱敏列"解——存 `hash(尾4位)` 或尾4位明文，牺牲一点信息量换检索能力；全部塞进加密列再"取回解密后过滤"等于全表扫描，成本不可接受。加密列上建普通索引是无效的（密文分布≠明文分布），等值索引要用密文列或确定性加密的盲索引。
- **实战**：落地清单：① DEK 按"表×用途"拆分，泄露爆炸半径可控；② KMS 调用加本地缓存（DEK 明文只在内存，TTL 分钟级），否则每行加解密一次 KMS 往返能把接口打爆；③ 密钥轮换演练：先在影子表跑一遍重写脚本，测准全表重写的真实时长再排窗口。

```python
"""数据库列加密的成本账：信封加密、查询能力矩阵与密钥轮换代价。"""
import hashlib

rows = 50_000_000          # 身份证号 5000 万行
REWRAP_MS = 5              # KMS 重裹一个 DEK 的耗时
PER_ROW_REWRITTEN_US = 30  # 明文重写：解密+加密+回写单行成本

def det_encrypt(value: str, dek: bytes) -> str:
    """确定性加密（SIV 思路）：同明文同密文，可建等值索引。"""
    return hashlib.sha256(dek + value.encode()).hexdigest()[:24]

dek = b"k" * 32
print("确定性加密可等值匹配：",
      det_encrypt("110101199003077512", dek) == det_encrypt("110101199003077512", dek))
print("查询能力矩阵：= 可(确定性) | BETWEEN/LIKE 不可 | JOIN 可(确定性)")
print("反直觉点：手机号 LIKE '%138' 这类查询在加密列上直接失效，"
      "要么冗余一列尾号哈希，要么把检索挪到脱敏副本")

# 密钥轮换的两种代价：换 KEK 只重裹 DEK；换 DEK 才要重写全表
kek_rotation = REWRAP_MS / 1000                    # 秒级
dek_rotation = rows * PER_ROW_REWRITTEN_US / 1e6 / 3600   # 小时级
print(f"轮换 KEK（只重裹 DEK）：≈ {kek_rotation * 1000:.0f} 毫秒")
print(f"轮换 DEK（全表重写）：≈ {dek_rotation:.1f} 小时（在线分批+限速）")
print("结论：信封加密把'高频轮换'放在便宜的 KEK 层，DEK 尽量按租户/表拆分以缩小重写面")
```

**追问链**：
1. 追问一层：为什么加密列上 LIKE '%138' 失效、连前缀索引也帮不上忙？——密文的字节序与明文无关（尤其随机化加密），前缀匹配的前提"密文前缀=明文前缀"不成立；确定性加密保等值但保不了子串。方案是冗余一个可检索的脱敏列（尾号/哈希），把检索与存储安全分层。
2. 追问二层：KMS 不加本地缓存会发生什么？——每次加解密都走一次 KMS 网络往返（几十毫秒），单行查询变成百毫秒级，且 KMS 的 QPS 配额先被打爆；缓存 DEK 明文（内存、分钟级 TTL）把成本降到进程内计算，代价是"内存里有明文密钥"的攻击面——所以缓存的 TTL 与进程生命周期要绑定。

**背诵要点**：
1. 查询能力矩阵：确定性加密保 =/JOIN，丢 BETWEEN/LIKE；检索需求用冗余脱敏列分层。
2. 信封加密：KEK 轮换毫秒级（重裹 DEK），DEK 轮换小时级（全表重写），高频轮换放 KEK 层。
3. DEK 按租户/表拆分缩小重写面；KMS 调用必须本地缓存，否则配额与延迟双爆。

**复盘追问**：
1. 加密上线后"按尾号搜索"接口超时，怎么补救？（加密列不可子串检索——补尾号哈希冗余列 + 历史数据批量回填，检索走冗余列，密文列只做存储）
2. 为什么密钥轮换演练必须在影子表先跑？（全表重写的真实时长受锁、IO、复制延迟影响，估算与实测差一个数量级是常态；先测准才能排停写窗口或设计限速）
