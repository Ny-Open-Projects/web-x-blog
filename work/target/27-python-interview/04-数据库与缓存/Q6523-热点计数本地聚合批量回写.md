### Q6523 · 热点计数本地聚合与批量回写：把每秒 50 万次 INCR 压到 500

> 难度:★★★★ | 标签:Redis, 计数, 热点

**问**：一个"视频播放量"场景，单 key 每秒 50 万次 INCR，Redis 单节点已到瓶颈。直接拆分多 key 再求和可以吗？还有什么更省的办法？

**答**：结论：拆 key（sharded counter）能把写打散，但读侧要聚合 N 个 key，成本转嫁到了读；更省的是**本地聚合**——每个应用实例先在进程内累加，按时间窗口或阈值批量回写一次 INCRBY，把 Redis QPS 从"请求量级"降到"实例数 × 窗口数"量级。50 万 QPS 打到 100 个实例、每 100ms 回写一次，Redis 只承受约 1000 写/秒。

取舍与实战：
- 代价是**计数不实时**：实例崩溃时丢失窗口内未回写的增量，精度损失 = 窗口时长 × 该实例流量。播放量、浏览数这类"可容忍近似"的场景完全值得；积分、库存等强一致计数不能用（库存请回原子扣减方案）。
- 读侧补偿：读路径上"Redis 值 + 本实例未回写增量"先加起来返回，展示层几乎无感；多实例读各自补各自的增量，全局读仍有窗口级偏差，对展示类指标可接受。
- 窗口选择：阈值 + 时间双触发（每 200ms 或每累计 1000 次就回写），防止低流量长窗口把误差拉大；回写用 INCRBY 保证原子，不需要 Lua。宕机丢数据窗口与回写频率成正比，监控"未回写增量"的 P99 作为精度指标。

```python
# 基线:Python 3.9+ 纯标准库 ;redis-py 可选(演示用字典模拟 INCRBY)
import threading
import time


class LocalAggCounter:
    """进程内聚合计数器:本地累加,按阈值/时间批量回写。"""

    def __init__(self, key: str, flush_interval: float = 0.2,
                 flush_threshold: int = 1000) -> None:
        self.key = key
        self._delta = 0            # 未回写增量
        self._last_flush = time.monotonic()
        self._lock = threading.Lock()
        self._interval = flush_interval
        self._threshold = flush_threshold
        self.flushed_to_remote = 0  # 模拟远端累计值

    def incr(self) -> int:
        """本地 +1;返回本地可见值(远端值+本地未回写增量)。"""
        with self._lock:
            self._delta += 1
            visible = self.flushed_to_remote + self._delta
            if (self._delta >= self._threshold
                    or time.monotonic() - self._last_flush >= self._interval):
                self._flush_locked()
            return visible

    def _flush_locked(self) -> None:
        if self._delta:
            # 生产:redis.incrby(self.key, self._delta) 原子回写
            self.flushed_to_remote += self._delta
            self._delta = 0
        self._last_flush = time.monotonic()

    def flush(self) -> None:
        """定时任务兜底回写,防低流量时增量长期滞留。"""
        with self._lock:
            self._flush_locked()


if __name__ == "__main__":
    c = LocalAggCounter("video:123:plays", flush_threshold=5)
    for _ in range(10):
        c.incr()
    print("阈值触发后远端值:", c.flushed_to_remote)   # 10
    c.incr()
    print("本地可见值(远端+未回写):", c.incr())       # 12
    c.flush()
    print("flush 后远端值:", c.flushed_to_remote)     # 12
```

**追问一**：多实例各自聚合，会不会互相覆盖丢计数？
答：不会——回写用 INCRBY（相对增量）而非 SET 绝对值，每个实例只提交自己窗口内的 delta，INCRBY 原子性保证多实例并发回写可交换、无覆盖。绝对值回写（SET）才是覆盖丢失的来源。

**追问二**：读侧要把"全局精确值"给广告结算用怎么办？
答：展示用聚合计数，结算用另立的强一致链路（比如异步落库 + 对账），或者低频调用精确聚合（SCAN 拆分 key 求和 + 事务冻结窗口）。原则：同一份数据按用途分精度，不要让结算需求绑架展示热路径。

**背诵要点**：
- 本地聚合 + INCRBY 批量回写：写 QPS 从请求量级降到 实例数/窗口 量级。
- 阈值 + 时间双触发回写，防低流量长窗口误差；宕机丢失窗口 = 未回写增量。
- 只适用于可容忍近似的展示型计数，强一致计数（库存/积分）不适用。

**复盘追问**：
- 如果实例数只有 3 个，聚合降载效果不佳，下一步该做什么（拆 key？多级聚合？）？
- "未回写增量 P99"这个指标怎么采集与告警？

## 背诵要点
- INCRBY 相对增量回写天然可并发合并，SET 绝对值才会覆盖丢失。
- 展示读 = 远端值 + 本实例未回写增量，全局读有窗口级偏差。
- 强一致计数走原子扣减链路，聚合计数只服务展示型指标。
