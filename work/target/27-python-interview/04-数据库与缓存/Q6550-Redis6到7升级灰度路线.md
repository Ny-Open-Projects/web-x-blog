### Q6550 · 版本演进：Redis 6 升 7 怎么做才敢按按钮？兼容审计与灰度路线

> 难度:★★★ | 标签:版本演进, Redis, 升级灰度

**问**：一个 40 个分片的 Redis Cluster 要从 6.2 升级到 7.2，怎么排升级顺序？升级前必须审计哪些兼容项？7.x 的 Functions、listpack 等新特性会不会破坏存量数据？

**答**：结论：Redis 6→7 兼容性总体良好，但有三类必须事前审计：**命令行为变更**（`expire` 时间参数溢出报错、`GETSET` 标记 deprecated、`redis-cli` 解析变化）、**RDB/AOF 版本兼容**（7.x 的 RDB 版本号旧版本读不了——意味着升级后无法直接回退到 6.2 读新持久化文件）、**脚本/Functions**（7.x Functions 取代了部分 Lua 使用方式，存量脚本语义需回归验证）。灰度路线：从库先行 → 单分片影子 → 按批轮转 → 全量，且每步保留"回退窗口"。

机理与实战：
- **升级顺序**：先升所有副本（副本挂了不影响主），再逐批升主（走主从切换，业务感知秒级抖动）。每批之间观察慢日志、命中率、内存碎片率、错误率指标 24h，异常即把该批流量回切。
- **回退窗口的关键**：7.x 写入产生的 RDB/AOF 6.2 读不了，所以"可回退"的定义是**回退到切换前的最后一份 6.2 快照 + 接受这之间的数据丢失**，或者接受从 7.x 主库 dump 兼容子集。审计时就要回答：这个丢失窗口业务能接受吗？不能就先做双写或缩短窗口。
- **客户端兼容**：redis-py 4.x+ 对 RESP3、`CLIENT TRACKING` 的支持差异；连接池参数（`health_check_interval`、socket 超时）在升级后的重连行为要用压测验证——大版本升级事故一半出在客户端而不是服务端。
- **新特性不背锅**：listpack 编码替代 ziplist 对存量 key 只在新写入/重编码时生效，读路径兼容；Functions 是新增能力不取代 EVAL 存量语义——所以"新特性"本身不构成回退理由，"行为变更清单"才是。

```python
# 基线:Python 3.10+;纯标准库,Redis 版本升级灰度状态机与兼容审计清单
from __future__ import annotations
from dataclasses import dataclass, field


@dataclass
class ShardGroup:
    name: str          # 批次:replicas-first / batch-1 / batch-2 / ...
    state: str = "pending"   # pending->audited->upgraded->soaked->promoted
    soak_hours: float = 24.0
    errors: list[str] = field(default_factory=list)


@dataclass
class CompatAudit:
    driver_ok: bool = True          # redis-py>=4.1
    resp3_needed: bool = False
    lua_scripts: int = 0            # 存量 Lua 脚本数(需回归)
    rdb_fallback_ok: bool = False   # 回退窗口数据丢失可接受?


def audit(a: CompatAudit) -> list[str]:
    issues: list[str] = []
    if not a.driver_ok:
        issues.append("阻断:升级 redis-py 至 4.1+ 并压测重连行为")
    if a.lua_scripts:
        issues.append(f"告警:{a.lua_scripts} 个存量 Lua 脚本需在 7.x 上回归确定性语义")
    if not a.rdb_fallback_ok:
        issues.append("阻断:7.x 的 RDB/AOF 6.2 无法读,确认回退窗口丢失是否可接受")
    return issues


def rollout(groups: list[ShardGroup], issues: list[str]) -> dict:
    """灰度状态机:有阻断项则全链路不动;每批浸泡 24h 才进下一批。"""
    if any(i.startswith("阻断") for i in issues):
        return {"status": "blocked", "reason": issues}
    for g in groups:
        g.state = "upgraded"
        if g.errors:
            g.state = "rolled-back"
            return {"status": "partial-rollback", "group": g.name, "errors": g.errors}
    return {"status": "done", "groups": [f"{g.name}:{g.state}" for g in groups]}


def demo() -> None:
    a = CompatAudit(lua_scripts=3, rdb_fallback_ok=False)
    issues = audit(a)
    assert any("RDB" in i for i in issues)      # 回退窗口未确认,不允许动
    print("审计输出:")
    for i in issues:
        print(f"  {i}")
    a2 = CompatAudit(lua_scripts=3, rdb_fallback_ok=True)
    groups = [ShardGroup("replicas-first"), ShardGroup("batch-1"), ShardGroup("batch-2")]
    r = rollout(groups, audit(a2))
    assert r["status"] == "done"
    print("灰度执行:", r["groups"])
    # 回退路径:batch-1 出错即停在部分回滚,不进 batch-2
    g2 = [ShardGroup("replicas-first"), ShardGroup("batch-1", errors=["latency-spike"])]
    r2 = rollout(g2, audit(a2))
    assert r2["status"] == "partial-rollback"
    print("升级灰度:副本先行→分批主库→每批浸泡,阻断项一票否决 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：升级期间主从切换是怎么做到业务几乎无感的？
答：对每个分片先升副本，等副本数据追平后用 `CLUSTER FAILOVER TAKEOVER`（或哨兵 failover）把主角色切给新版本副本——切换只影响该分片毫秒级的连接重连，客户端（redis-py 集群模式）收到 MOVED 后自动重路由。关键在切换前确认副本复制延迟为 0，否则切换窗口会丢写。

**追问二**：为什么说"回退窗口能接受多少数据丢失"是升级方案的第一个问题而不是最后一个？
答：回退路径在升级后立刻变窄：6.2 无法读 7.x 持久化文件意味着回退=回到旧快照；如果业务写入不能容忍丢失（如交易态数据），就必须升级前搭建反向同步（双写或用 6.2 副本只读追流）——很多团队把这个问题放到出事之后才发现回退根本不存在，这是版本演进类复盘里最高频的教训。

## 背诵要点
- Redis 6→7 审计三类：命令行为变更清单、RDB/AOF 版本兼容（7.x 文件 6.2 读不了→回退=回到旧快照）、存量 Lua 语义回归；客户端 redis-py 4.1+ 重连压测。
- 灰度顺序：副本先行→逐批主库（CLUSTER FAILOVER）→每批浸泡 24h 看慢日志/命中率/错误率；有阻断项一票否决。
- 升级方案的第一个问题是"回退窗口能丢多少数据"：不可丢则先搭反向同步，可丢则明确窗口时长并写进方案。

## 复盘追问
- 升级后某分片内存涨了 15%，是 7.x 的问题还是数据自身增长？（提示：先看 info memory 的 fragmentation ratio 与键数量对比，排除碎片率变化；再 diff 大 key——编码从 ziplist→listpack 的重编码会改变小对象内存占用，属于预期行为但要在容量账里留余量）
- Lua 脚本在 7.x 上"跑得通"但结果偶发不一致，怎么系统性排查？（提示：脚本复制语义在集群+副本场景下的确定性要求——脚本内必须只用 KEYS[] 访问 key、不读系统时间/随机数；用脚本回放对拍工具跑全量存量脚本比人工抽查可靠）
