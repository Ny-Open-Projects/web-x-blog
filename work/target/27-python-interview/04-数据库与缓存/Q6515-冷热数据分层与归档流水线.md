### Q6515 · 冷热数据分层与归档

> 难度:★★☆ | 标签:数据生命周期, 归档, 成本

**问**：订单表 5 年 20 亿行，在线库扛不动了——冷热分层的判定标准是什么？归档流水线怎么设计（切割/搬运/校验/删除四步），「归档后用户还要查历史订单」怎么兜底？为什么删除比搬运更容易出事故？

**答**：判定标准三轴：**访问频率**（90 天无查询 = 冷）、**业务时效**（订单完成且无退款窗口 = 可归档）、**合规留存**（财务数据 7 年，归档≠删除）。归档流水线四步：① **切割**：按时间边界切增量（`WHERE created < :watermark`，水位表记录已归档到哪，断点续跑）；② **搬运**：分批 SELECT→批量 INSERT 到归档库（OLAP/压缩存储），每批几千行 + 主键切片（`WHERE id BETWEEN`，别 OFFSET 翻页）；③ **校验**：搬运后行数+抽样哈希+SUM 对账，不一致回滚水位；④ **删除**：**最后且最小批**（删除是最大的事故源：删了没归档全的、删了正在被引用的、删完事务超时回滚一半），在线库删完即 vacuum（PG）/optimize（MySQL）回收空间。历史查询兜底：路由层按时间分流（近期→在线库，历史→归档库 API），用户无感；「归档库要能查」决定了归档目标必须是查询友好存储，不是直接丢对象存储完事。

```python
# 全部标准库 + sqlalchemy（SQLite 模拟归档库）；缺库降级看流程注释
import sqlalchemy as sa, time, hashlib

meta = sa.MetaData()
def make_table(name, eng):
    t = sa.Table(name, meta,
        sa.Column("id", sa.Integer, primary_key=True),
        sa.Column("created", sa.Integer, nullable=False),   # unix ts
        sa.Column("payload", sa.String(64)))
    t.create(eng)
    return t

eng_live = sa.create_engine("sqlite://", pool_pre_ping=True)
eng_arch = sa.create_engine("sqlite://")
live = make_table("orders", eng_live)
arch = make_table("orders_arch", eng_arch)

WATERMARK = {"until": 0}                     # 水位表：断点续跑的真相源

def archive_batch(eng_live, eng_arch, before_ts, batch=4):
    """切割→搬运→校验→删除：一批一批走，每步可断点重试。"""
    with eng_live.begin() as c:
        rows = c.execute(sa.select(live.c).where(
            live.c.created < before_ts).order_by(live.c.id).limit(batch)).mappings().all()
    if not rows:
        return 0
    with eng_arch.begin() as c:
        c.execute(arch.insert(), [dict(r) for r in rows])
    # 校验：行数 + 抽样哈希
    with eng_arch.begin() as c:
        got = c.execute(sa.select(arch.c.id).where(
            arch.c.id.in_([r["id"] for r in rows]))).scalars().all()
    assert sorted(got) == sorted(r["id"] for r in rows), "搬运校验失败，回滚水位"
    with eng_live.begin() as c:               # 删除最小批：只删已校验的这批
        c.execute(live.delete().where(live.c.id.in_([r["id"] for r in rows])))
    WATERMARK["until"] = max(r["created"] for r in rows)
    return len(rows)

def route_query(created: int) -> object:
    """查询路由：90 天内查在线库，历史查归档库（用户无感）。"""
    now = int(time.time())
    return eng_live if now - created < 90 * 86400 else eng_arch

if __name__ == "__main__":
    now = int(time.time())
    with eng_live.begin() as c:
        c.execute(live.insert(), [ {"id": i, "created": now - i * 86400 * 30,
                 "payload": f"d{i}"} for i in range(1, 9)])   # 最近 8 个月数据
    while archive_batch(eng_live, eng_arch, before_ts=now - 90 * 86400) > 0:
        pass                                  # 只归档 90 天前的（冷判定）
    with eng_live.begin() as c:
        left = c.execute(sa.select(sa.func.count(live.c.id))).scalar()
    with eng_arch.begin() as c:
        done = c.execute(sa.select(sa.func.count(arch.c.id))).scalar()
    print(f"在线剩 {left} 行 / 归档 {done} 行（90 天冷热切割）")
    target = now - 91 * 86400                 # 查 4 个月前订单 → 路由到归档库
    eng = route_query(target)
    assert eng is eng_arch
    print("历史查询自动路由到归档库 ✅")
```

**追问**：1) 为什么按主键切片而不是 OFFSET？——`LIMIT 10000 OFFSET 5000000` 要扫过前 500 万行（延迟线性涨），主键 `WHERE id > last_id LIMIT 10000` 恒定代价（游标分页）；归档千万行时差 100 倍。2) 归档库选型？——只读分析类：ClickHouse/压缩列存；偶发点查：MySQL 从库/PG + 分区表；海量不可查：对象存储 + 每日检索走重放。选型先问「归档数据还有多少查询 QPS」。3) 删除的事故三连怎么防？——先校验后删（同事务/同水位）、删除限速（批量+sleep 防主从延迟爆炸）、灰度先删一天的量验证。

## 背诵要点
1. 冷判定三轴：访问频率、业务时效、合规留存——归档≠删除，留存有法律口径。
2. 四步流水线：切割（水位断点）→ 搬运（主键切片游标）→ 校验（行数+哈希）→ 删除（最后、最小批、限速）。
3. 历史查询兜底 = 时间路由层（在线/归档双库），归档目标必须是查询友好存储。

## 复盘追问
1. 归档跑一半发现搬运口径错了（少归档了一列），怎么补救？（提示：水位回退重跑 + 已删数据从归档库补列（归档保留原始行），这就是「先校验后删」的价值）
2. 在线库删除 500 万行后磁盘没变小？（提示：PG vacuum 只标记复用、不归还 OS（要 vacuum full/pg_repack）；MySQL innodb_file_per_table optimize；运维预期要对齐）
