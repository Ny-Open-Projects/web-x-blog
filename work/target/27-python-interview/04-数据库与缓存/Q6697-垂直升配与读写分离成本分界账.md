### Q6697 · 数据库垂直升配与读写分离的成本分界账

难度：P6 ｜ 标签：成本工程、垂直扩展、读写分离、选型

基线：云 RDS（按规格计费）；通用成本模型。

**问**：数据库 CPU 日常 65%，老板问"升配还是加读副本便宜"？8 核 400 元/月、16 核 800 元/月、32 核 1600 元/月，读副本同规格。这笔账怎么算？什么情况下"升配"反而更便宜？

**答**：
- **结论**：分界点在**读流量占比与扩容倍数**。读占比 70% 以上、需要 2 倍以上吞吐时，读写分离的总价 = 主(升一档) + 副本(同档)，成本 ≥ 2×单机价；如果一档升配（+1 倍价格 ≈ +1.5~2 倍性能，规格越大越贵但性价比较平）就能撑过下一个增长期，升配更便宜。反之写也在涨、或读请求单次成本降不下来时，升配只能买 6~12 个月时间，不如早做分离/缓存/分片的结构性投资。
- **取舍**：升配还有隐性成本——变更要主从切换或重启（几分钟不可写）、规格上限存在（云厂商最大规格），且大规格的单机故障域更大。读写分离的隐性成本——复制延迟引入旧读 bug、应用要改路由、强一致读回主库。
- **实战**：算账三步——(1) 拆 QPS 到 CPU：用 perf/慢查询数据得出"每 1000 读 QPS ≈ x 核、每 1000 写 QPS ≈ y 核"；(2) 按目标 CPU（建议 50%）反推所需核数，比较"升配总价" vs "分离总价"；(3) 加上增长曲线：若 6 个月内还得再翻倍，把结构性方案的迁移成本也摊进来比。

```python
# 升配 vs 读写分离成本账（标准库可运行）。
import math

def plan(read_qps: int, write_qps: int,
         core_cost: int,            # 每核每月基准价格
         per_core_read: float,      # 每核可承载读 QPS
         per_core_write: float,
         big_premium: float = 1.5): # 超过 16 核的大规格单价溢价
    need_cpu = read_qps / per_core_read + write_qps / per_core_write
    need = math.ceil(need_cpu / 0.5)          # 目标利用率 50%
    premium = big_premium if need > 16 else 1.0
    vertical_cost = need * core_cost * premium
    # 分离方案：主库扛全部写 + 20% 强一致读；副本扛其余读
    main_cpu = write_qps / per_core_write + read_qps * 0.2 / per_core_read
    replica_cpu = read_qps * 0.8 / per_core_read
    main_cores = max(2, math.ceil(main_cpu / 0.5))
    repl_cores = max(2, math.ceil(replica_cpu / 0.5))  # 含冗余的副本总核数
    split_cost = (main_cores + repl_cores) * core_cost   # 各规格均低于 16 核无溢价
    return {"所需核数": need, "升配月费": vertical_cost,
            "分离拓扑核数": f"主{main_cores} + 副本{repl_cores}",
            "分离月费": split_cost,
            "更便宜": "升配" if vertical_cost <= split_cost else "读写分离"}

if __name__ == "__main__":
    print(plan(6000, 800, core_cost=50, per_core_read=1000, per_core_write=800))
    # 读 6000/写 800：升配 700 元 vs 分离 750 元 -> 升配
    print(plan(15000, 800, core_cost=50, per_core_read=1000, per_core_write=800))
    # 读 15000：升配进 32 核大规格档吃 1.5 倍溢价 2400 元 vs 分离 1600 -> 读写分离
```

**追问**：
- 一层：为什么升配的性能增长不是线性的？→ 提示：锁竞争、共享 buffer、NUMA，核数翻倍吞吐通常只增 1.3~1.7 倍。
- 二层：云 RDS 升配为什么有停机窗口？怎么规避？→ 提示：规格变更需主备切换；用只读节点先升 + 应用路由灰度，或选支持热升配的规格系列。
- 三层：什么信号告诉你"该停止买时间、开始做分片"？→ 提示：写 QPS 增速 + 单表行数进入重整/DDL 痛苦区 + 升配已到顶配。

**背诵要点**：
1. 分界点=读占比×扩容倍数：读 70%+ 且要 2 倍吞吐时分离，一档升配能撑 6-12 个月时升配。
2. 升配隐性成本：切换停写窗口、顶配上限、故障域变大；分离隐性成本：旧读 bug、路由改造、强一致回主。
3. 账的核心参数是"每核读/写承载"，用监控数据标定，目标利用率按 50% 反推。

**复盘追问**：
1. 为什么账里没算"迁移到读写分离的研发成本"？提示：一次性研发成本要摊到 12 个月对比月费差。
2. 如果升配后 CPU 反而更高了怎么办？提示：说明瓶颈不是算力而是低效 SQL/锁，升配掩盖问题。
