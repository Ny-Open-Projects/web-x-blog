### Q6650 · 数据库故障降级预案与只读模式

难度：P7 | 标签：降级预案、故障演练、只读模式、容量规划

**问**：主库宕机、预计 10 分钟才能切主。这段时间应用层做什么？"降级预案"应该包含哪些已经定义好的动作，而不是临场发挥？

**答**：
- **结论**：预案是预先定义好的状态机：① 进入降级——读切只读快照（本地缓存的最近一致快照，明确标注允许陈旧）；② 写缓冲——可延迟的写进有界缓冲队列（上限防内存爆，如 1k 条），不可延迟的写（支付）直接快速失败并给用户明确文案；③ 关键功能矩阵——预先列出每个功能在"无 DB"下的行为（可降级/必须拒绝），上线前评审过；④ 恢复——DB 回来后按序回放写缓冲、刷新快照、逐步放开流量。核心原则：降级行为是产品决策（哪些数据可以旧、哪些请求可以拒），必须提前和业务对齐并演练，不是工程师临场设计。
- **取舍**：写缓冲的取舍：缓冲的写没有幂等保证的执行环境（回放时可能重复/失败），所以缓冲只该收"可重算"的写（计数、点赞），交易类写宁拒不缓冲。只读快照的取舍：快照越新鲜内存成本越高，刷新频率与业务容忍度对齐。
- **实战**：预案演练：每季度做一次"拔数据库网线"演练，验证降级动作真的会被触发（开关、快照刷新、缓冲回放），演练发现的"预案没生效"比真实事故便宜一百倍。监控降级期间的缓冲水位与回放成功率，回放失败要有对账兜底。

```python
"""数据库故障降级预案：只读快照兜底 + 写缓冲 + 降级矩阵。"""
from collections import deque

class DegradedApp:
    def __init__(self):
        self.db = {"greeting": "hello"}
        self.snapshot = dict(self.db)          # 定期刷新的只读快照
        self.write_buffer = deque()            # 写缓冲（上限防内存爆）
        self.degraded = False

    def set_db_state(self, up):
        if up and self.degraded:               # 恢复：按序回放写缓冲
            self.degraded = False
            while self.write_buffer:
                k, v = self.write_buffer.popleft()
                self.db[k] = v
            self.snapshot = dict(self.db)

    def read(self, key):
        if self.degraded:
            return f"stale:{self.snapshot.get(key)}"      # 允许陈旧
        return self.db.get(key)

    def write(self, key, val):
        if self.degraded:
            if len(self.write_buffer) >= 1000:
                return "rejected(over cap)"            # 超上限快速失败
            self.write_buffer.append((key, val))
            return "buffered"
        self.db[key] = val
        self.snapshot = dict(self.db)
        return "ok"

app = DegradedApp()
app.degraded = True                                   # DB 故障进入降级
print(app.read("greeting"), app.write("k1", "v1"), app.write("k2", "v2"))
app.set_db_state(True)                                # 恢复
print("恢复后:", app.read("k1"), app.read("k2"), app.read("greeting"))
print("要点：降级预案要提前定义（允许陈旧读/写缓冲上限/拒绝哪些写），恢复按序回放")
```

**追问链**：
1. 追问一层：为什么交易类写不进缓冲？（缓冲回放时业务上下文已失效，可能重复执行或校验失败；交易宁可明确拒绝让用户重试，也不做语义不明的延迟执行）
2. 追问二层：降级开关本身存哪里？（不能存数据库——用配置中心/本地兜底配置；降级依赖链要保证"DB 挂了开关还能翻"）

**背诵要点**：
1. 预案是预定义状态机：只读快照、有界写缓冲、功能降级矩阵、按序回放。
2. 缓冲只收可重算写，交易写快速失败给明确文案。
3. 每季度拔线演练验证预案真的生效；降级开关不能依赖 DB。

**复盘追问**：
1. 演练发现降级开关翻不动，最可能的原因？（开关配置存在数据库或依赖了 DB 的鉴权链路）
2. 回放写缓冲时 10% 失败，怎么兜底？（失败落对账表人工/自动重放，回放幂等键设计）
