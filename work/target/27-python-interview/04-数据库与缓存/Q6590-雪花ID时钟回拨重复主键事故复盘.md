### Q6590 · 雪花 ID 时钟回拨导致重复主键事故复盘

难度：P7 ｜ 标签：分布式 ID / 时钟 / 事故复盘

**问**：某服务用雪花算法生成订单 ID，NTP 校时导致宿主机时钟回拨了几百毫秒，之后出现了主键冲突报错和"两条不同订单共用一个 ID"的数据问题。时钟回拨为什么会击穿雪花 ID？如何设计防护？

**答**：
- **结论**：雪花 ID = 时间戳(41bit) + 机器ID + 序号。序号在同一毫秒内递增，依赖"时钟单调前进"这一假设；回拨后时间戳变小，生成器会重复发出与回拨前相同的 (ts, seq) 组合——如果内存里缓存了"上一毫秒用过的序号"且实现不严（比如回拨后把 seq 清零），就会直接撞上历史 ID。事故放大器：ID 不是只进数据库，还进了消息队列、日志、下游幂等键，重复 ID 让幂等逻辑把"新订单"当成"重试"丢弃，造成丢单。
- **取舍**：防护方案对比：① 回拨等待——检测到回拨小于阈值（如 2 秒）就自旋等待时钟追上，简单可靠但主线程被卡（要放到生成器层而不是业务层）；② 回拨超阈值则拒绝服务/告警——宁可用 ID 缺口换正确性；③ 换不依赖物理时钟的方案（号段模式 DB 取号、TGO 类租约）——彻底规避但引入新依赖与单点。多数团队的正确组合是：雪花生成器内置回拨检测 + 等待/拒绝逻辑，关键路径（订单）用号段模式兜底或 DB 唯一索引兜底 + 冲突时重试。
- **实战**：事故剧本：① 用 DB 唯一索引兜住写入（冲突报错可见，而不是静默丢消息）；② 排查重复 ID 的传播面（MQ/日志/下游幂等键），撤回或重放被误丢的"重试"；③ 生成器改造：保留 last_ts，若 `current < last_ts` 则等待或抛错，绝不静默重置 seq；④ 复盘项：NTP 配置改成平滑校时（slew 而非 step），并把"时钟回拨告警"加进宿主机监控。

```python
# 带回拨防护的雪花 ID 生成器（纯标准库，单进程演示）
# 基线：Python 3.9+

import itertools
import os
import time


class Snowflake:
    def __init__(self, machine_id: int, max_backoff_ms: int = 2000) -> None:
        self.machine_id = machine_id
        self.last_ts = -1
        self.seq = 0
        self.max_backoff_ms = max_backoff_ms

    def next_id(self, now_ms: int) -> int:
        """真实实现用 time.time_ns()//1e6；参数化 now_ms 便于测试回拨"""
        if now_ms < self.last_ts:
            drift = self.last_ts - now_ms
            if drift <= self.max_backoff_ms:
                # 小回拨：按旧时间戳继续分配（时钟等待策略的确定性模拟）
                now_ms = self.last_ts
            else:
                raise RuntimeError(f"clock moved back {drift}ms, refuse to mint")
        if now_ms == self.last_ts:
            self.seq = (self.seq + 1) & 0xFFF
            if self.seq == 0:  # 同毫秒 4096 个用尽：等待下一毫秒
                now_ms += 1
                self.seq = 0
        else:
            self.seq = 0
        self.last_ts = now_ms
        return (now_ms << 22) | (self.machine_id << 12) | self.seq


def main() -> None:
    s = Snowflake(machine_id=1)
    t = 1_700_000_000_000
    ids = [s.next_id(t + i) for i in range(10)]
    assert len(set(ids)) == 10
    # 回拨 100ms：小回拨，重复时间戳但序号继续递增 → 不重复
    back = t + 5  # 回拨到 t+5（此前已到 t+9）
    ids2 = [s.next_id(back) for _ in range(5)]
    assert len(set(ids + ids2)) == 15, "小回拨不应产生重复 ID"
    # 回拨 1 小时：超阈值拒绝
    s2 = Snowflake(machine_id=1)
    s2.next_id(t)
    try:
        s2.next_id(t - 3_600_000)
        raise AssertionError("should refuse")
    except RuntimeError as e:
        print("拒绝:", e)
    print("OK: 小回拨等待、大回拨拒绝")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"回拨后重置 seq=0"是错误实现？
→ 一句话提示：回拨前的 (ts, seq) 已经发出过，回到同一时间戳再从 0 递增必然复现历史组合；正确做法是沿用 last_ts 并让序号继续前进，或干脆拒绝发号。

**追问 2**：号段模式（DB 取号段）和雪花 ID 各自的故障面是什么？
→ 一句话提示：号段模式的瓶颈在 DB 取号段的一次写入与号段服务可用性（双 buffer 缓解），但无时钟依赖；雪花依赖每台机器时钟与机器 ID 分配唯一性（机器 ID 重复会产生跨机重复 ID，是另一类经典事故）。

## 背诵要点
- 雪花 ID 单调性假设：同毫秒序号递增；回拨击穿的是 (ts, seq) 组合的唯一性，DB 唯一索引是最后防线。
- 防护两级：小回拨（≤2s）等待/沿用 last_ts 续发，大回拨拒绝发号；NTP 配置用 slew 平滑校时。
- 重复 ID 的危害在幂等链路：MQ 消费把新业务当重试丢弃 → 丢单；排查要覆盖 MQ/日志/下游幂等键传播面。

## 复盘追问
- 机器 ID 是怎么分配的？提示：手工配置会重复，自动分配（如基于 IP/注册中心）则要处理回收与重启复用；机器 ID 冲突是和时钟回拨并列的雪花事故源。
- 为什么说"雪花 ID 里内嵌时间戳"还有隐私与安全隐患？提示：可从 ID 反推服务上线时间与发号速率（业务量），对外暴露的 ID 常要再做一层不可逆编码（如 hashids）或对外序列号。
