### Q6619 · 数据迁移双写窗口的不一致事故复盘

难度：P6 ｜ 标签：事故复盘 / 双写 / 数据迁移

**问**：把订单库从 MySQL 迁到新集群（分库分表改造），采用"双写过渡"：应用同时写旧库与新库，跑两周后切换读路径。切换后发现两边数据有差异，部分订单状态不一致。双写为什么会必然产生不一致？正确的双写设计与验收标准是什么？

**答**：
- **结论**：双写不一致的三个机制性来源：① **非原子性**——两个库不在一个事务里，写旧库成功、写新库失败（或进程在两写之间崩溃）产生缺失；失败的补偿（重试/异步补）本身又可能重复或乱序；② **顺序性**——同一订单的两次状态更新（created → paid），新库写入了但顺序颠倒（重试导致后发先至），终态错；③ **语义漂移**——新库的 schema/触发器/默认值与旧库有差异（如新库状态机校验拒绝了旧库接受的值），双写结果集天然分叉。事故链路：补偿异步任务重试时没有幂等键 → 重复插入被唯一键拦掉但状态更新乱序 → 少量订单终态错。双写的正确设计：写路径顺序固定（先旧后新，旧为主），新库写入失败只告警+落补偿队列、**不阻塞主流程**；补偿以新库 upsert（按唯一业务键 + 版本号/时间戳单调），乱序更新用版本号拒绝旧值覆盖新值；读切换前必须过"双读比对"（Q1410 同源思路）达到差异率达标且连续稳定 N 天。
- **取舍**：双写 vs 其他方案的取舍：数据可停机迁移的量级直接停写切换（窗口短、一致性天然）；不可停的用双写但要接受"过渡期新库是近似实时副本 + 补偿最终一致"的定位；更稳的替代是**基于 binlog 的同步**（canal/逻辑复制，Q6507 同源）：应用只写旧库，新库由 binlog 订阅写入——消灭了双写的非原子性，代价是引入复制链路运维与延迟。工程上常"binlog 同步为主 + 双写验证为辅"混合。
- **实战**：验收标准量化：① 全量比对 + 增量比对（按更新时间分片对账）差异率 < 0.01% 且差异行均可归因（时间窗口内）；② 状态机字段按业务终态比对而非中间态；③ 双写开关做成配置中心灰度（按订单 ID 尾号双写），回滚 = 关开关；④ 切换读路径后旧库保留只读 N 周，兜底查询。

```python
# 双写一致性：版本号单调更新 + 补偿幂等模拟
# 基线：Python 3.9+ 标准库；真实场景用 binlog 同步 + 对账平台
import itertools
from dataclasses import dataclass, field


@dataclass
class Replica:
    state: dict[str, tuple[int, str]] = field(default_factory=dict)  # key -> (version, status)

    def apply(self, key: str, version: int, status: str) -> bool:
        """版本号单调：旧版本拒绝覆盖新值（乱序更新防线）。"""
        cur = self.state.get(key)
        if cur and version <= cur[0]:
            return False  # 幂等/乱序拒绝
        self.state[key] = (version, status)
        return True


def dual_write(replica: Replica, events: list[tuple[str, int, str]]) -> tuple[int, int]:
    """返回 (applied, rejected)：补偿队列重放时乱序事件被版本号拦住。"""
    applied = rejected = 0
    for key, ver, status in events:
        if replica.apply(key, ver, status):
            applied += 1
        else:
            rejected += 1
    return applied, rejected


def main() -> None:
    r = Replica()
    # 正常顺序：created(v1) -> paid(v2)
    a, _ = dual_write(r, [("o1", 1, "created"), ("o1", 2, "paid")])
    assert a == 2 and r.state["o1"] == (2, "paid")

    # 补偿重放乱序：重试把 v1 事件后发 -> 必须拒绝，终态不被旧值覆盖
    a2, rej = dual_write(r, [("o1", 1, "created"), ("o1", 2, "paid")])
    assert a2 == 0 and rej == 2 and r.state["o1"] == (2, "paid")
    print("乱序/重复补偿被版本号拒绝，终态保持 paid")

    # 事故反例：无版本号直接覆盖 -> 终态回退
    bad = Replica()
    bad.apply("o1", 2, "paid")
    bad.state["o1"] = (1, "created")   # 模拟无版本控制的重试覆盖
    assert bad.state["o1"] == (1, "created")
    print("OK: 双写不一致三源=非原子/乱序/语义漂移；版本号单调+幂等键是止血线")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"binlog 同步为主 + 双写验证为辅"比纯双写稳？
→ 一句话提示：binlog 同步把两库一致性下沉到复制链路（顺序、原子性由 binlog 位点保证），应用不感知；双写只留给少量需要"新库侧业务定制写入"的场景，一致性验收仍走双读比对。

**追问 2**：双读比对的差异怎么算"可归因"？
→ 一句话提示：按更新时间划窗口，只比"窗口已封闭（超出复制延迟上界）"的行；差异要能映射到已知机制（窗口内、乱序补偿中、语义差异清单），无法归因的差异哪怕 1 行也要停下排查。

## 背诵要点
- 双写不一致三源：非原子（半写）、乱序（重试后发先至）、语义漂移（两侧约束不同）；补偿必须带幂等键 + 版本号单调，旧版本拒绝覆盖。
- 更稳替代：应用只写旧库 + binlog 订阅同步新库，一致性由复制链路保证；双写降级为验证手段。
- 切换验收：全量+增量对账差异率 <0.01% 且全部可归因、状态机按终态比对、双写开关按 ID 尾号灰度可秒级回滚。

## 复盘追问
- 为什么事故往往在"切换读路径后"才爆发？提示：双写期间新库没有承载读，没人看它的数据；差异持续累积到读切换才可见——所以对账必须从双写第一天就跑，而不是切换前突击。
- 双写期间新库的 DDL 怎么管理？提示：冻结新库 schema 变更或走同一条迁移流水线，两侧 schema 差异是"语义漂移"分叉的主要来源，schema 变更要与对账差异率联动观察。
