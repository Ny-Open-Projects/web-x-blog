### Q6661 · Redis AOF everysec 磁盘慢导致的写延迟与丢数据窗口复盘

难度：P6-P7 | 标签：Redis、持久化、事故复盘

**问**：云上 Redis 开了 `appendfsync everysec`，某天监控出现大量客户端写超时，`INFO persistence` 里 `aof_delayed_fsync` 持续增长，日志反复出现 "Asynchronous AOF fsync is taking too long"。复盘这条事故链：为什么会从"磁盘慢"放大成"所有写都慢"？丢数据窗口到底多大？

**答**：结论：everysec 的承诺是"fsync 由后台线程做，主线程最多等 2 秒"。事故链是：宿主机磁盘 IO 打满（如快照、日志洪峰、同宿主邻居）→ 后台 fsync 一次耗时超过 2 秒 → 主线程检测到上次 fsync 还没完成，会**阻塞等待磁盘写操作完成**（这正是 aof_delayed_fsync 增长的来源）→ 所有写命令在主线程排队 → 客户端超时。丢数据窗口是 1-2 秒（everysec 设计值），但如果事故中进程崩溃发生在"积压未 fsync"时刻，丢失量等于积压的写命令数。

取舍与实战：
1. `aof_delayed_fsync` 是关键哨兵指标：它增长说明 fsync 已经落后，写延迟即将放大；告警阈值设在连续 N 个采样周期非零增长。
2. 治理手段按优先级：把 AOF 与 RDB 分盘（消除 fork + fsync 抢 IO）、避开整点快照窗口、必要时降级为 `appendfsync no`（交内核，延迟小但丢失窗口变大）——这是**可用性换持久性**的降级开关，要在预案里写清。
3. 与 Q1421（fork COW）区分：那是持久化 fork 引发的内存与延迟问题；这条是 fsync IO 路径本身的阻塞，`INFO persistence` 的 `aof_current_size` 与磁盘 util 是定位分叉点。
4. 大流量写入时用 pipeline 摊薄命令数但不能解决 fsync 瓶颈——fsync 是磁盘级动作，客户端侧无法缓解。

```python
"""AOF fsync 健康度检查器：模拟 INFO persistence 读数与告警判定"""
from dataclasses import dataclass


@dataclass
class AofHealth:
    delayed_fsync_series: list[int]   # 每 10s 采样的 aof_delayed_fsync
    fsync_latency_ms: float           # 最近一次 fsync 耗时
    disk_util_pct: float              # AOF 所在盘 util

    def diagnose(self) -> list[str]:
        out = []
        s = self.delayed_fsync_series
        growing = all(s[i + 1] > s[i] for i in range(len(s) - 1)) and s[-1] > 0
        if self.fsync_latency_ms > 2000:
            out.append("[事故] fsync > 2s：主线程开始阻塞等待，写延迟全面放大")
        if growing:
            out.append("[告警] aof_delayed_fsync 持续增长，fsync 已落后于写入速率")
        if self.disk_util_pct > 90:
            out.append("[根因候选] AOF 磁盘 util > 90%：检查快照/邻居争抢，考虑分盘")
        if not out:
            out.append("[OK] fsync 健康度正常")
        return out


# 事故现场读数
h = AofHealth(delayed_fsync_series=[0, 12, 45, 120, 260],
              fsync_latency_ms=3100, disk_util_pct=97)
for line in h.diagnose():
    print(line)
```

**追问 1**：everysec 下进程崩溃，最多丢多少数据？和 `appendfsync always` 的代价差在哪？
**提示**：最多 1-2 秒的写命令；always 每条命令都 fsync，吞吐被磁盘 IOPS 封顶（大约每秒几千到几万条），QPS 高时写延迟直接吃磁盘 P99。

**追问 2**：为什么 pipeline 写入 1 万条命令，AOF 也只需要一次 fsync？
**提示**：fsync 刷的是 AOF 缓冲区文件偏移量，与命令条数无关只与写入字节量相关；everysec 周期内所有写入合并进同一次磁盘刷盘，这正是 everysec 能扛住高 QPS 的原因。

## 背诵要点
- everysec 丢数据窗口 1-2 秒；fsync 超 2 秒主线程阻塞，aof_delayed_fsync 是先导指标。
- 事故链：磁盘 IO 打满 → fsync 落后 → 主线程阻塞 → 全部写延迟放大；治理靠分盘、错峰快照、降级 appendfsync no。
- fsync 成本与命令条数无关只与字节量相关，pipeline 不解决 fsync 瓶颈。
