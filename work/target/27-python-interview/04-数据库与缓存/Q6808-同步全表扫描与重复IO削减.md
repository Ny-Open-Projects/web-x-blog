### Q6808 · 同步全表扫描：为什么新来的大查询不从第一页开始

难度：P7 ｜ 标签：PostgreSQL、synchronize_seqscans、全表扫描、预读、buffer pool

基线：库知识库外知识卡，用"多个扫描的起始偏移 + 环形重叠页数"模拟 PG 的 `synchronize_seqscans` 对重复 IO 的削减。

**问**：凌晨跑 5 个报表，都是对同一张 200GB 表做全表扫描，错峰 2 分钟启动。监控显示磁盘读流量是单条查询的 3.8 倍，buffer pool 命中率却没升，5 条查询总耗时比串行还长。DBA 说 PG 有个 `synchronize_seqscans`，让后来的扫描"从别人当前位置开始"，这是怎么做到的？为什么它能减少重复读，却不会让结果少行？

**答**：

- **结论**：PG 的 `synchronize_seqscans=on`（默认）会让**新启动的全表扫描**先看当前是否已有扫描在同一张表上；如果有，就从那个扫描的**当前块位置**开始，读完尾部再**环形回绕**到开头。这样多个并发全表扫描在时间上"结伴"读同一段页，buffer pool 只缓存一份，磁盘只读一遍；没有这个机制时，每个新扫描都从 block 0 开始，前面已经读过的页可能已被挤出缓存，于是重复读。它不改变结果：每个扫描仍然遍历全部页，只是**起始点不同 + 回绕**，可见性和谓词过滤不变。
- **取舍**：① 并发大表扫描：开启同步能显著降 IO，但会把多个查询的进度"绑"在一起，长查询拖慢新查询的启动阶段；② 单条扫描：没有同步对象，行为不变；③ 如果表很小、全在缓存里，同步的收益接近 0，反而增加一点协调开销；④ 同步只对**全表扫描**有效，索引扫描/位图扫描不走这条路径。
- **实战**：① 并发报表错峰不如"同向"：让它们在同一时间段跑，反而共享 IO；② 监控 `pg_stat_all_tables.seq_scan` 与 `pg_stat_io` 的 reads，对比逻辑扫描页数与物理读，重复读比例高说明同步没生效或缓存太小；③ 大表分析尽量走分区裁剪/列存/只读副本，别让 5 条全表扫同时打主库；④ 需要稳定延迟的在线查询，避免和长全表扫描共享 buffer pool，用资源组/副本隔离。

下面用环形重叠页数模拟：无同步时 5 个扫描都从 0 开始，有同步时错开起始点。

```python
# synchronize_seqscans: 后启动的扫描从领先者当前位置开始, 读完回绕
SCAN_PAGES = 1000


def duplicate_pages(starts, scan=SCAN_PAGES):
    """两两扫描在环形空间上的重叠页数, 近似重复物理读"""
    total = 0
    for i in range(len(starts)):
        for j in range(i):
            d = abs(starts[i] - starts[j]) % scan
            total += max(0, scan - d)
    return total


no_sync = [0, 0, 0, 0, 0]                 # 每个都从第 0 页开始
synced = [0, 200, 400, 600, 800]          # 从领先者当前位置起步

dup_no = duplicate_pages(no_sync)
dup_sync = duplicate_pages(synced)
print(f"[1] 无同步: 5 条扫描, 重复页读 {dup_no}")
print(f"[2] 有同步: 5 条扫描, 重复页读 {dup_sync}")
assert dup_no == 10000
assert dup_sync == 6000
assert dup_sync < dup_no
print("    → 实测 同步把重叠从 100% 降到 60%, 逻辑扫描量不变, 物理读减少")

# 每条扫描仍然覆盖全部页: 起始点 + 回绕 = 完整集合
def visited(start, scan=SCAN_PAGES):
    return {(start + i) % scan for i in range(scan)}


for s in synced:
    assert len(visited(s)) == SCAN_PAGES
print(f"[3] 任意起始点回绕后仍覆盖 {len(visited(600))} 页, 结果不会缺行")

# 收益与错峰程度: 启动越接近, 重叠越高, 省得越多
def saving_ratio(starts):
    return 1 - duplicate_pages(starts) / duplicate_pages([0] * len(starts))


for gap in (50, 100, 200):
    starts = [i * gap for i in range(5)]
    print(f"[4] 领先者已推进 {gap} 页: 重复读下降 {saving_ratio(starts) * 100:.0f}%")
assert saving_ratio([0, 200, 400, 600, 800]) > saving_ratio([0, 50, 100, 150, 200])
print("    → 实测 领先者越靠前, 后来者起点越分散, 重叠越少; 几乎同时启动时同步省不了多少")
```

**追问一**：同步扫描会不会让新查询读到"旧页"？—— 不会。同步只调整**物理读取起点**，每个扫描仍然按自己的 MVCC 快照判断元组可见性；页里是最新版本，可见性由快照决定。回绕也不会漏页，因为扫描覆盖整个环形区间。它优化的是 IO 顺序，不是可见性语义。

**追问二**：为什么索引扫描没有类似机制？—— 索引扫描的访问路径由索引顺序决定，多个查询的索引范围可能完全不同，强行同步起点会破坏索引有序性、增加随机 IO；而且索引扫描通常命中页少，重复读的绝对量小。同步全表扫描的收益来自"顺序读同一段"，索引扫描没有这个前提。

## 背诵要点

- `synchronize_seqscans=on`：新全表扫描从已有扫描的当前位置起步，读完回绕，多个扫描共享 buffer pool 页，减少重复物理读。
- 不改变结果与可见性，只改物理读取起点；逻辑扫描页数不变。
- 并发大表扫描越接近同时启动，收益越大；索引/位图扫描不走这条路径。
