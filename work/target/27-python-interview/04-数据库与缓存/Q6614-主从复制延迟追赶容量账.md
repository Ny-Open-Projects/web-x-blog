### Q6614 · 主从复制延迟的追赶容量账

难度：P6 ｜ 标签：容量规划 / 复制延迟 / 读写分离

**问**：读写分离架构下，主库写入 8k TPS（行级 binlog 事件约 25k/s），单条 SQL 重放约 0.2ms。一次批量任务把写入抬到 3 倍持续 10 分钟，从库延迟会到多少？多久能追平？读流量切换阈值与"追账模型"怎么建？

**答**：
- **结论**：核心是排队模型：`lag(t) = lag(t-1) + (生产速率 - 重放速率) × dt`，其中重放速率上限 = 单线程 SQL 线程的每秒重放能力（MySQL 默认单线程重放；8.0+ 可 `replica_parallel_workers` 按 watershed 并行）。取一组自洽参数：稳态生产 25k 事件/s，并行度 4 × 单线程 15k/s = 重放能力 60k 事件/s，稳态余量 35k/s。批量任务把生产抬到 75k/s 持续 10 分钟：每秒净积压 15k 事件，结束时积压 900 万事件；批量结束后生产回落稳态，追平速率 35k/s，约 257 秒（4 分钟级）追平——期间读流量持续读旧数据，延迟秒数先冲高再回落。若有效并行度只有 2（30k/s），积压变成 45k/s × 600s = 2700 万事件，追平 27 分钟——**并行度参数直接决定爆炸半径**。容量结论：批量任务必须限速到"生产速率 < 重放能力 × 0.8"（本例放大倍数红线 = 48k/25k = 1.92），或提前扩只读副本并接受延迟窗口。
- **取舍**：工程决策链：① 先看重放能力上限（并行度、单条成本），它决定全库写入预算——这是写入侧的硬容量；② 读侧按延迟阈值摘除/摘回（Q6646 已谈摘除），阈值取"业务可容忍旧读窗口"如 5s；③ 批量任务限速是首选（令牌桶按重放余量动态调），牺牲任务时长换全站读一致性；④ 会话级刚需读走强制主库（读写粘性），比例控制在个位数，避免把主库读压垮。
- **实战**：监控直接采 `Seconds_Behind_Master`/PG 的 `pg_stat_replication` replay lag 的**事件数**而非秒数（秒数在写入停止后会瞬间归零、掩盖积压）；把"重放能力"做成季度压测项（用真实流量回放），模型里的 0.2ms/条要用实测校准；批量任务平台强制带"限速参数"并预演追账。

```python
# 复制延迟追赶模型：积压事件数 ODE + 追平时间
# 基线：Python 3.9+ 标准库；真实参数用生产回放压测校准
from dataclasses import dataclass


@dataclass
class ReplBudget:
    steady_events: float     # 稳态写入事件/s
    batch_factor: float      # 批量任务放大倍数
    batch_minutes: float
    replay_capacity: float   # 并行重放能力（事件/s）= 并行度 x 单线程能力


def simulate(b: ReplBudget, dt: float = 1.0) -> tuple[float, float]:
    """返回 (批量结束时刻积压事件数, 追平所需分钟数)。"""
    lag = 0.0
    prod = b.steady_events * b.batch_factor
    for _ in range(int(b.batch_minutes * 60 / dt)):
        lag += (prod - b.replay_capacity) * dt
        lag = max(lag, 0.0)
    catchup_s = lag / (b.replay_capacity - b.steady_events)
    return lag, catchup_s / 60


def safe_batch_factor(b: ReplBudget, headroom: float = 0.8) -> float:
    """限速后允许的最大放大倍数：生产 <= 重放能力 x headroom。"""
    return b.replay_capacity * headroom / b.steady_events


def main() -> None:
    b = ReplBudget(steady_events=25_000, batch_factor=3.0,
                   batch_minutes=10, replay_capacity=60_000)
    lag, catchup = simulate(b)
    assert lag == (75_000 - 60_000) * 600      # 900 万事件
    assert abs(catchup - 9_000_000 / 35_000 / 60) < 0.1  # 追平期生产回落稳态：余量 60k-25k=35k
    print(f"批量10分钟后积压 {lag/1e4:.0f} 万事件，稳态回落下追平约 {catchup:.0f} 分钟")

    safe = safe_batch_factor(b)
    assert abs(safe - 0.8 * 60_000 / 25_000) < 1e-9   # 1.92
    print(f"限速结论：放大倍数须 <= {safe:.2f}（重放能力x0.8），3 倍必爆")

    # 并行度退化场景：有效并行度 2 -> 重放 30k，追平 27 分钟
    b2 = ReplBudget(steady_events=25_000, batch_factor=3.0,
                    batch_minutes=10, replay_capacity=30_000)
    lag2, catchup2 = simulate(b2)
    assert lag2 == 27_000_000 and abs(catchup2 - 27e6 / 5e3 / 60) < 0.1
    print(f"并行度退化(30k): 积压 {lag2/1e4:.0f} 万事件，追平 {catchup2:.0f} 分钟")
    print("监控口径：采积压事件数而非 Seconds_Behind，避免写入停止后假归零")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 `Seconds_Behind_Master` 在写入停止后会"假归零"？
→ 一句话提示：它衡量的是"当前时间 - 正在重放事件的时间戳"，写入停止后重放快速追到最新事件，秒数归零，但按事件数口径的积压还没消化完——切换判断要看事件数/GTID 差值。

**追问 2**：MySQL 8 的并行重放（writeset/LOGICAL_CLOCK）什么时候提不上去？
→ 一句话提示：单事务内修改行过多（事务是并行度的最小单元）、热点行冲突使 watershed 分组退化、从库单盘 IO 跟不上——压测要覆盖真实事务形态而不是均匀小事务。

## 背诵要点
- 追账模型：lag(t) += (生产速率 − 重放能力)×dt；重放能力 = 并行度 × 单线程重放速率，是全库写入预算的硬上限。
- 示例账：稳态 25k 事件/s、重放 60k、批量 3 倍 10 分钟 → 积压 900 万事件，约 4 分钟追平；并行度退化到 30k 时积压 2700 万、追平 27 分钟——并行度决定爆炸半径；限速红线 = 重放能力 × 0.8。
- 监控用积压事件数/GTID 差值，不用 Seconds_Behind（写入停止后假归零）；刚需旧读 intolerant 的会话强制主库但比例控制在个位数。

## 复盘追问
- 批量任务限速与"拆小事务"哪个先做？提示：先限速（不动代码、立即生效），拆事务改变并行分组质量但引入业务改造与失败重试复杂度，两者常组合。
- 追平期间读流量完全摘除该副本还是降级部分读？提示：按接口旧读容忍度分级——账务类强制主库、feed 类可接受分钟级旧读，全摘会打爆主库。
