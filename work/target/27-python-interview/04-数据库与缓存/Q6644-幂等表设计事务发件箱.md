### Q6644 · 幂等表设计与事务发件箱

难度：P6 | 标签：幂等、事务发件箱、唯一约束、事故复盘

**问**：下单接口超时后客户端重试，怎么保证不重复扣库存、不重复发 MQ 事件？"唯一约束兜底 + 状态机 + 事务发件箱"三件套分别解决什么问题？

**答**：
- **结论**：三层各挡一类事故。① 幂等表：`req_id` 做唯一约束，重放请求先撞唯一索引，查已有结果直接返回——挡重复业务执行；② 状态机：订单状态只在合法迁移上更新（`UPDATE ... WHERE state='PENDING'`），挡异步回调乱序/重复；③ 事务发件箱：业务写与事件写在同一本地事务提交，派发器轮询 outbox 再发 MQ——挡"DB 提交了但 MQ 没发出去"的双写不一致。
- **取舍**：发件箱把"同步发 MQ"变成"最终一致"，引入派发延迟与轮询成本；换来的是绝不丢事件、绝不 DB-MQ 脑裂。消费方仍需幂等（at-least-once 语义下事件可能重发），唯一键要带业务语义而不是全局随机。
- **实战**：事故复盘：下单超时 → 客户端重试 → 两笔订单。根因通常是"先查后插"的检查-插入窗口——必须把判重做成唯一约束的数据库级行为，应用层检查只做优化。req_id 由客户端在重试间保持稳定（请求指纹：路径+关键参数哈希），网关层再加 TTL 去重缓存挡最外层流量。

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE orders (id TEXT PRIMARY KEY, amount INT);
CREATE TABLE idem (req_id TEXT PRIMARY KEY, order_id TEXT, state TEXT);   -- 幂等表
CREATE TABLE outbox (seq INTEGER PRIMARY KEY AUTOINCREMENT, event TEXT, sent INT DEFAULT 0);
""")

def create_order(req_id, amount):
    cur = db.cursor()
    try:
        cur.execute("BEGIN IMMEDIATE")
        cur.execute("INSERT INTO idem (req_id, order_id, state) VALUES (?, '', 'PENDING')", (req_id,))
    except sqlite3.IntegrityError:
        db.rollback()                       # 同 req_id 重放：唯一约束挡住，查已有结果
        row = db.execute("SELECT order_id, state FROM idem WHERE req_id=?", (req_id,)).fetchone()
        return ("replay", row)
    cur.execute("INSERT INTO orders (id, amount) VALUES (?, ?)", (req_id, amount))
    cur.execute("UPDATE idem SET order_id=?, state='DONE' WHERE req_id=?", (req_id, req_id))
    # 发件箱：业务写 + 事件写，同一事务原子提交
    cur.execute("INSERT INTO outbox (event) VALUES (?)", (f"order.created:{req_id}",))
    db.commit()
    return ("created", (req_id, "DONE"))

print(create_order("R1", 100))
print(create_order("R1", 100))              # 重放：不再扣减、不再发事件
print("事件数:", db.execute("SELECT COUNT(*) FROM outbox").fetchone()[0])

# 派发器：只读 outbox，失败可重发（消费方靠 req_id 幂等）
for seq, event in db.execute("SELECT seq, event FROM outbox WHERE sent=0").fetchall():
    print("deliver", event)
    db.execute("UPDATE outbox SET sent=1 WHERE seq=?", (seq,))
db.commit()
```

**追问链**：
1. 追问一层：幂等表会无限膨胀，怎么清？——状态终态 + 超过保留窗口（如 7 天）后归档删除；TTL 的依据是上游最大重试窗口，窗口外重放应拒绝而非幂等。
2. 追问二层：发件箱派发器怎么保证不重复发也不漏发？——轮询按 seq 游标 + 标记 sent 前先发送，崩溃在"已发未标"会重发，所以消费必须幂等；漏发靠 seq 连续性对账兜底。

**背诵要点**：
1. 判重必须落在数据库唯一约束，应用层"先查后插"有竞态窗口。
2. 状态机用条件 UPDATE 保证迁移合法性，挡乱序重复回调。
3. 发件箱 = 业务与事件同事务提交 + 派发器轮询，消费方仍需幂等。

**复盘追问**：

2. 如果把幂等表换成 Redis SETNX（7 天过期），丢失了哪些数据库级保证？（TTL 与业务窗口错配、无事务联动）
