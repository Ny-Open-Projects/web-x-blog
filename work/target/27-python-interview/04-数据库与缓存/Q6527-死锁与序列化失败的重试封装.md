### Q6527 · 死锁与序列化失败：哪些异常值得重试？重试封装怎么写才不放大问题？

> 难度:★★★★ | 标签:PostgreSQL, MySQL, 重试

**问**：高并发下偶发 `deadlock detected`（PG）或 `1213 Deadlock found`（MySQL），代码里 `except Exception: retry` 一把梭行不行？怎么设计一个"只重试该重试的"事务重试框架？

**答**：结论：不行。可重试的异常有明确白名单：PG 的 ` deadlock_detected / serialization_failure（40001）/ lock_not_available`，MySQL 的 1213/1205，连接层 `OperationalError` 里的瞬态类；`IntegrityError`（唯一冲突）通常不该盲重试——重试只会再撞一次唯一约束，它要走的是幂等分支而不是重试分支。白名单之外的异常重试等于把确定性 bug 放大成随机故障，且事务重试必须**整个事务从头发起**（含读），不是只重放最后一条语句。

机理与实战：
- 重试必须配合"有界退避 + 抖动"，并对**同 key 的重试风暴**做护栏：死锁的本质是加锁顺序冲突，无脑重试会让互撞双方同时醒来再撞，形成活锁。抖动让撞锁对错峰；更根治的是统一加锁顺序（按主键排序批量更新）。
- 幂等前提：事务体必须可重放——所有写基于"读到的值 + 增量"而不是"本地缓存"；事务里有外部副作用（发消息、调下游）必须移出事务或用 outbox，否则重试会重复副作用。
- 序列化失败（SSI 下 40001）与死锁不同：它是"提交时发现依赖被人改了"，重试语义是天然的（重新执行一遍可能就通过了），所以 serializable 隔离级别的应用必须内建这个循环，否则 SSI 根本没法用。

```python
# 基线:Python 3.9+ 纯标准库 ;接入 psycopg2/pymysql 时替换异常映射即可
import random
import time
from typing import Callable, TypeVar

T = TypeVar("T")

RETRYABLE_CODES = {       # 生产:psycopg2 errors 与 pymysql.err 的映射
    "40001": "serialization_failure",
    "40P01": "deadlock_detected",
    "55P03": "lock_not_available",
}


class Retryable(Exception):
    def __init__(self, code: str) -> None:
        self.code = code


class Fatal(Exception):
    """不可重试:唯一冲突、语法错误、约束违例等。"""


def retry_transaction(fn: Callable[[], T], max_attempts: int = 4,
                      base_delay: float = 0.05) -> T:
    """只重试白名单异常;每次重试整事务重跑;有界退避+抖动防活锁。"""
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except Retryable as e:
            if e.code not in RETRYABLE_CODES or attempt == max_attempts:
                raise                      # 非白名单/重试耗尽:原样抛出
            delay = base_delay * (2 ** (attempt - 1))
            time.sleep(delay * (0.5 + random.random()))  # 抖动错峰
    raise RuntimeError("unreachable")


def demo() -> None:
    state = {"attempts": 0, "balance": 100, "order_committed": False}

    def transaction() -> int:
        """模拟会死锁一次的事务:第一次撞锁,第二次成功。"""
        state["attempts"] += 1
        if state["attempts"] == 1:
            raise Retryable("40P01")              # 第一次死锁
        state["balance"] -= 30                    # 基于读值+增量,可安全重放
        state["order_committed"] = True
        return state["balance"]

    bal = retry_transaction(transaction)
    assert bal == 70 and state["order_committed"]
    print("死锁重试后提交成功,余额:", bal)

    # 唯一冲突走幂等分支,不进重试
    try:
        retry_transaction(lambda: (_ for _ in ()).throw(Fatal("23505")))
    except Fatal as e:
        print("唯一冲突不重试,直接走幂等兜底:", e)


if __name__ == "__main__":
    demo()
```

**追问一**：为什么死锁重试不能只重放最后一条 UPDATE？
答：死锁时整个事务已回滚，事务内先前语句的锁和修改全部作废；只重放最后一条会基于"未生效的前置修改"写数据，造成半事务。重试单元必须是整个事务函数。

**追问二**：重试 4 次仍死锁怎么办？
答：说明冲突结构是稳定的（典型：两批相互交叉的加锁顺序）。重试耗尽后该异常应上抛并触发对账/人工介入，同时把死锁日志（PG 的 `pg_stat_activity` 等待链、MySQL `SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK）作为例行分析输入，从顺序上根治。

**背诵要点**：
- 可重试白名单：40001 / 40P01 / 55P03（PG）、1213/1205（MySQL）；IntegrityError 走幂等不重试。
- 重试单元 = 整个事务函数；退避 + 抖动防互撞双方同时醒来的活锁。
- 事务体内外部副作用必须移出（outbox），否则重试重复副作用。

## 背诵要点
- except Exception 盲重试把确定性 bug 放大成随机故障，必须白名单。
- 死锁后整事务回滚，重试单元是整个事务函数而非最后语句。
- 退避抖动防活锁；重试耗尽上抛并对账，根治靠统一加锁顺序。
