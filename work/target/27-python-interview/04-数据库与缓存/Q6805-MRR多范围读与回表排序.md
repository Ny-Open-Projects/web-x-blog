### Q6805 · MRR 多范围读：把随机回表排成顺序 IO 的账

难度：P7 ｜ 标签：MySQL、MRR、回表、随机 IO、二级索引、优化器

基线：库知识库外知识卡，用"二级索引命中 → 主键回表"的页序列模拟普通回表与 MRR 的页切换次数，不依赖 MySQL。

**问**：一条 `WHERE city_id = 42 AND created_at BETWEEN ...` 的查询，二级索引命中 20 万行，`EXPLAIN` 显示 `Using MRR`，耗时从 9 秒降到 3 秒；但另一条只命中 300 行的查询开了 MRR 反而慢了 15%。MRR 到底做了什么？为什么行数少的时候它不划算？`read_rnd_buffer_size` 调大是不是一定能更快？

**答**：

- **结论**：普通二级索引回表是"**按索引顺序拿主键，再按主键随机回表**"：索引里 `created_at` 相邻的行，主键可能散落在不同页，20 万次回表 ≈ 20 万次随机页读。**MRR（Multi-Range Read）**先把一批主键收进 `read_rnd_buffer`，**按主键排序后再回表**，把随机 IO 变成"页内连续、页间近似有序"的批量读，页切换次数从"行数"降到"涉及页数"。收益与命中行数、页局部性成正比；300 行的查询本来就只有 300 次读，排序和缓冲的固定开销盖过收益，所以变慢。`read_rnd_buffer_size` 不是越大越好：太大增加排序内存与单次延迟，太小则批次不足、收益有限。
- **取舍**：① 大范围、低选择性的二级索引查询：开 MRR，收益最大；② 小结果集、主键本身有序（如自增且索引顺序与主键一致）：MRR 无收益甚至负收益；③ 覆盖索引能完全避免回表，优先级高于 MRR；④ MRR 只优化"回表 IO"，不减少扫描行数——`WHERE` 选择性差时，先把索引设计对，再谈 MRR。
- **实战**：① 看 `EXPLAIN` 的 `Using MRR` 与 `Handler_read_rnd`/`Handler_read_rnd_next` 的变化；② 大查询用 `EXPLAIN ANALYZE` 对比开/关 `optimizer_switch='mrr=on/off'` 的 actual time；③ `read_rnd_buffer_size` 从 256KB 起调，按"单批主键数 × 主键宽度"估算，不要超过 `sort_buffer_size` 的量级；④ 分页/限流场景让 `LIMIT` 尽量下推到索引，减少进入 MRR 的行数。

下面用页序列模拟：同一批主键，普通回表按索引顺序读，MRR 先排序再读。

```python
# MRR: 主键排序后再回表, 把随机页读变成按页批量读
import random


def page_switches(pages):
    return sum(1 for i in range(1, len(pages)) if pages[i] != pages[i - 1])


random.seed(7)
rows = 200
pages_per_row = [random.randrange(100) for _ in range(rows)]   # 索引顺序下的主键所在页

base_switches = page_switches(pages_per_row)

# MRR: 按主键(这里用页号近似)排序后回表, 同页的行聚在一起
ordered = sorted((page, i) for i, page in enumerate(pages_per_row))
mrr_switches = page_switches([page for page, _ in ordered])

print(f"[1] 普通回表: {rows} 行, 页切换 {base_switches} 次, 涉及 {len(set(pages_per_row))} 页")
print(f"[2] MRR 回表: {rows} 行, 页切换 {mrr_switches} 次")
assert base_switches > mrr_switches
assert mrr_switches == len(set(pages_per_row)) - 1

# IO 时间账: 随机页 1.0ms, 同页命中 0.1ms
def io_ms(switches, rows, random_ms=1.0, hit_ms=0.1):
    return switches * random_ms + (rows - switches) * hit_ms


base_ms = io_ms(base_switches, rows)
mrr_ms = io_ms(mrr_switches, rows)
print(f"[3] 估算 IO: 普通={base_ms:.1f}ms, MRR={mrr_ms:.1f}ms, 降幅={(1 - mrr_ms / base_ms) * 100:.0f}%")
assert mrr_ms < base_ms

# 小结果集: 排序与缓冲的固定开销盖过收益
small_rows = 300
small_switches = small_rows
overhead_ms = 2.5
normal_small = io_ms(small_switches, small_rows)
mrr_small = io_ms(len(set(range(small_switches))), small_rows) + overhead_ms
print(f"[4] 300 行: 普通={normal_small:.1f}ms, MRR={mrr_small:.1f}ms (含固定开销)")
assert mrr_small > normal_small
print("    → 实测 MRR 的收益来自页局部性; 小结果集会被固定开销吃掉")
```

**追问一**：MRR 排序后回表，为什么结果顺序还是对的？—— MRR 只改变**回表读取顺序**，不改变最终结果的逻辑顺序；执行器会在回表后按索引顺序/排序要求重新组织，或者由上层 `ORDER BY` 保证。对没有 `ORDER BY` 的查询，SQL 本来就不承诺行序。应用如果依赖"无 ORDER BY 的行序"，无论开不开 MRR 都是错的。

**追问二**：MRR 和覆盖索引冲突吗？—— 不冲突，但覆盖索引是更优解：不回表就没有随机 IO，MRR 也就无事可做。工程顺序应该是"先看能不能覆盖 → 再看索引顺序能否与主键对齐 → 最后才用 MRR 优化残余回表"。把 MRR 当第一选择，往往会掩盖索引设计问题。

## 背诵要点

- MRR 把二级索引命中的主键先收进 `read_rnd_buffer`，排序后批量回表，页切换从"行数"降到"页数"。
- 收益与命中行数、页局部性成正比；小结果集有排序/缓冲固定开销，可能负优化。
- 优先级：覆盖索引 > 索引顺序与主键对齐 > MRR；`read_rnd_buffer_size` 按批大小估算，不是越大越好。

## 复盘追问

- 为什么"索引顺序与主键顺序一致"时 MRR 几乎没有收益？此时随机 IO 去哪了？
- MRR 的批次越大越好吗？批次大小如何影响单次延迟与内存峰值？
