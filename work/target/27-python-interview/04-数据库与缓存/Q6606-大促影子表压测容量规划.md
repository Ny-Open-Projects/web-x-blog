### Q6606 · 大促前影子表压测的数据量与容量规划

难度：P7 ｜ 标签：压测 / 容量规划 / 数据库

**问**：大促前要做数据库压测，团队直接把线上订单表复制了 10% 的数据到一个"影子表"压。压测结果 5000 TPS 很漂亮，大促真实流量一来，800 TPS 就把库打挂了。为什么压测数字和真实容量差了几个数量级？压测容量账应该怎么建？

**答**：
- **结论**：压测失真的三个来源：① **数据分布失真**——只复制 10% 数据，B+ 树层级浅、buffer pool 全装得下热页，压出来的是"全内存库"的性能；真实库几亿行，热页/冷页混布，一次随机读穿透到磁盘就是几毫秒。② **访问模式失真**——影子表上跑的是均匀随机 key，真实流量是长尾热点（头部 5% 商品占 50% 读），热点行为与锁竞争完全不同。③ **链路失真**——只压了单表 SQL，没有压"事务组合"（下单 = 扣库存 + 订单 + 积分 + 消息记录），锁交叉、连接池占用、undo 增长都没被覆盖。
- **取舍**：正确姿势：① 数据量级对齐——影子库按**全量等比**造数（行数、索引分布、碎片率对齐），不必是真数据但要"统计等价"；② 访问模型对齐——从线上 binlog/慢日志采样出真实 key 访问分布（Zipf 热点系数），压测脚本按分布采样；③ 指标对齐——不是看 TPS 数字，而是看"目标流量 × 2 倍冗余下的 P99 延迟、锁等待、IO 水位"；④ 压测环境隔离——影子库在独立实例，压测流量绝不打线上库。
- **实战**：容量账流程：① 取大促预估峰值 RPS × 峰值系数 3-5 倍作为目标；② 造数工具按真实分布生成影子库（Python 脚本 + 真实 binlog 采样）；③ 阶梯加压记录拐点（P99 突然抬升的 TPS 即有效容量）；④ 与线上容量差值 = 需要的扩容量（升配/加副本/分片）；⑤ 压完清理影子库并归档报告，压测数据要标脏避免误入生产链路。

```python
# 压测容量账：分布对齐 + 阶梯加压找拐点（标准库模拟判定逻辑）
# 基线：Python 3.9+；真实压测用 sysbench/pgbench + 采样脚本

import random


def sample_hot_keys_zipf(n_items: int, size: int, skew: float = 1.2) -> list[int]:
    """按 Zipf 分布采样访问 key，模拟真实热点长尾"""
    rng = random.Random(42)
    weights = [1.0 / (i + 1) ** skew for i in range(n_items)]
    return rng.choices(range(n_items), weights=weights, k=size)


def latency_model(tps: int, hot_ratio: float, buffer_hit: float) -> float:
    """简化延迟模型：buffer pool 命中率随热点比例变化，P99 = 基线 + 磁盘穿透代价"""
    base = 2.0
    disk_penalty = (1 - buffer_hit) * hot_ratio * tps / 1000 * 8.0
    queue_penalty = max(0.0, (tps - 4000) / 1000) * 3.0
    return base + disk_penalty + queue_penalty


def find_capacity(max_tps: int = 20000, p99_sla: float = 50.0, *, uniform: bool = False) -> int:
    """阶梯加压，P99 突破 SLA 前一档即有效容量"""
    for tps in range(1000, max_tps, 500):
        if uniform:
            # 均匀随机 + 全内存：影子表压测看到的漂亮世界
            p99 = latency_model(tps, hot_ratio=0.05, buffer_hit=1.0)
        else:
            # 真实分布：热点集中 → 行锁竞争、冷数据占比高 → 命中率低
            p99 = latency_model(tps, hot_ratio=0.6, buffer_hit=0.85)
        if p99 > p99_sla:
            return tps - 500
    return max_tps


def main() -> None:
    keys = sample_hot_keys_zipf(5_000_000, 100_000)
    top100 = len([k for k in keys if k < 100]) / len(keys)
    print(f"头部 100 个 key 占访问比 {top100:.1%}（真实流量的热点倾斜）")
    assert top100 > 0.15, "Zipf 热点应显著倾斜"

    uniform_cap = find_capacity(uniform=True)
    real_cap = find_capacity()
    print(f"影子表均匀压测容量 {uniform_cap} TPS vs 真实分布容量 {real_cap} TPS（P99=50ms SLA）")
    assert real_cap < uniform_cap, "分布对齐后的容量必然低于均匀全内存压测"
    print("OK: 压测容量账——数据分布、访问模式、指标口径三对齐")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"复制 10% 数据"会得到远高于真实的 buffer pool 命中率？
→ 一句话提示：数据量小于内存时索引几乎全在热页，物理读趋近于零；真实库远大于内存，命中率取决于热点与内存的比例——所以压测库的行数、碎片率都要与线上对齐。

**追问 2**：怎么从线上采到真实的访问分布？
→ 一句话提示：解析 binlog 的 WHERE key / 慢日志的 query 模板，聚合成"key 频次直方图 + SQL 模板占比"，再据此造数和编排压测脚本；通用压测工具的默认均匀模型一律要替换。

## 背诵要点
- 压测失真三源：数据量级（内存命中失真）、访问分布（均匀 vs Zipf 热点）、链路组合（单 SQL vs 事务组合）。
- 有效容量看"目标流量 × 3-5 倍冗余下的 P99/锁等待/IO 水位"，不是 TPS 峰值数字；拐点 = P99 突破 SLA 前一档。
- 影子库独立实例、数据标脏、采 binlog 造统计等价数据；压测报告与线上扩容差值直接挂钩容量决策。

## 复盘追问
- 压测脚本自身怎么避免成为瓶颈？提示：压测端连接数、CPU、GC 停顿要单独监控，结论里区分"库到极限"还是"压测机到极限"，通常压测端 CPU 超过 70% 的数据不可信。
- 影子表方案与全量克隆环境方案的取舍？提示：影子表便宜但分布/碎片难对齐，适合回归与 SQL 层对比；容量结论要用全量等比库或克隆库，成本靠按需拉起（快照恢复）控制。
