### Q6557 · B+Tree 尾页写热点：单调主键的写入放大与打散

难度：P6 | 标签：B+Tree、写热点、主键设计、吞吐容量

**问**：秒杀库存扣减把主键索引的"最后一页"写成了单点瓶颈——CPU 没满、磁盘没满，写入吞吐却卡死在 12 万行/s。为什么递增主键会把所有写压到一个页上？打散的代价是什么？

**答**：
- **结论**：B+Tree 按键序存放，递增主键（auto_increment/时间戳）的新插入永远落在最右叶页——所有并发写竞争同一个页 latch，页内串行化，吞吐上限 = 1/单页插入耗时，与线程数无关（128 个线程和 1 个线程一样快）。散列打散后写压到 128 个页，页间并行，上限乘以页数。但打散牺牲范围扫描局部性：按主键范围查要读满所有页。折中是类雪花键：时间前缀保证"近期数据集中"（热页随时间自然轮转），尾部随机位打散并发。
- **取舍**：单调键的另一面是页分裂少、填充率高、顺序写对 Buffer Pool 友好——它不是坏设计，只是在"写并发极高"时变成单点。判断标准：单页写入吞吐（本例 12.5 万行/s）是否逼近业务峰值；逼近才打散，否则保留单调键的局部性收益。
- **实战**：观测手段：页级写入分布（InnoDB 没直接暴露，可用 latch 等待与 insert buffer 指标间接推断）；秒杀这类"热点行"问题另有一层行锁竞争（拆桶/合并扣减），页热点与行热点是两件事，先分清是哪一层卡住。

```python
"""B+Tree 尾页写热点：单调主键的页竞争与散列打散的吞吐对比。"""
import time  # noqa: F401  (占位：真实测量用 latch 等待时间)

PAGES = 128
INSERTS = 200_000
SERVICE_US = 8          # 单个叶页一次插入（含页内 latch）约 8 微秒

def page_traffic(kind: str) -> list[int]:
    traffic = [0] * PAGES
    for i in range(INSERTS):
        if kind == "monotonic":
            page = PAGES - 1                     # 递增主键永远命中最右叶页
        elif kind == "hash":
            page = (i * 2654435761) % PAGES      # 斐波那契散列打散
        else:                                     # 毫秒级时间前缀：每毫秒换一页
            page = (i // 1000) % PAGES
        traffic[page] += 1
    return traffic

for kind in ("monotonic", "hash", "time_prefix"):
    tr = page_traffic(kind)
    hot, total = max(tr), sum(tr)
    print(f"{kind:12s} 最热页承担 {hot / total:.1%} 的写入")

# 吞吐上限：页间可以并行，同一页内被 latch 串行化
print(f"单调主键写吞吐上限 ≈ {1e6 / SERVICE_US:,.0f} 行/s（单页串行，与线程数无关）")
print(f"散列打散后上限 ≈ {PAGES * 1e6 / SERVICE_US / 10000:.0f} 万行/s（页间并行）")
print("代价权衡：打散牺牲范围扫描的局部性——按主键范围查要打满全部页；"
      "类雪花键（时间前缀+散列尾）是折中：近期数据仍集中，热页随时间自然轮转")
```

**追问链**：
1. 追问一层：为什么"CPU 没满"但吞吐上不去？——瓶颈是页内 latch 的串行化，不是计算资源；128 个写线程排队等同一把页锁，CPU 大部分时间在自旋/上下文切换。这是典型的"串行化点"瓶颈，加机器无效。
2. 追问二层：页热点和行热点（秒杀库存扣减）怎么区分？——页热点是"所有写挤在同一索引页"（换键分布可解）；行热点是"所有事务更新同一行"（行锁排队，要拆桶/缓存预扣/合并写）。现象都是写入上不去，但前者看 latch 等待，后者看行锁等待链。

**背诵要点**：
1. 递增主键 → 写永远落最右叶页 → 页 latch 串行化 → 吞吐 = 1/单页耗时，与并发无关。
2. 打散换并行、丢局部性；类雪花键（时间前缀+随机尾）是热页轮转的折中。
3. 判断依据：单页写吞吐是否逼近业务峰值；先分清页热点与行热点。

**复盘追问**：
1. 订单表写入高峰 8 万行/s，单调主键撑得住吗？——撑得住（上限 12.5 万/s，余量 56%）；但要做余量监控，业务峰值增长到 11 万/s 前完成键改造，临界点改造是事故。
2. 为什么 UUID 完全随机键也有问题？（页分裂频繁、填充率低、索引体积膨胀、范围扫全页——打散不是免费的，方向是"可控打散"而非"完全随机"）
