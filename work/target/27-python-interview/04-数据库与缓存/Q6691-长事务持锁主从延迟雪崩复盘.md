### Q6691 · 长事务持锁导致主从延迟雪崩事故复盘

难度：P7 ｜ 标签：事故复盘、长事务、主从延迟、锁

基线：MySQL 8.0（information_schema.innodb_trx / performance_schema）；SQLAlchemy 2.0。

**问**：凌晨一次报表任务在主库跑了一个 40 分钟的大事务，期间一个普通的 UPDATE 业务语句连续超时，随后从库延迟从 2 秒涨到 400 秒，读流量大量报旧数据。这种"一个长事务打穿全链路"的事故怎么复盘？应用侧和 DB 侧各要加什么防线？

**答**：
- **结论**：长事务的破坏是三连击——(1) 持有行锁/gap lock，让普通 DML 排队超时；(2) 其产生的 binlog 在事务提交时才整体写入并传给从库，从库（单线程/单 worker 回放同一库）要一次性追 40 分钟的量，延迟瞬间拉爆；(3) undo 链被拉长，期间所有快照读都要沿旧版本回溯，全库读都变慢。根因不是"SQL 慢"，而是"事务边界错误"：把批处理塞进了一个事务。
- **取舍**：批处理的正确形态是"小事务 + 幂等 + 可重跑"，牺牲"整体原子性"换取锁持有时间可控；如果业务真要整体一致，应该用"写临时表 + 原子 RENAME"或"逻辑标记 + 双阶段切换"，而不是长事务。
- **实战**：应用侧三道防线——(1) ORM 层禁用 `autocommit=False` 长连接空转，事务里禁止 RPC/HTTP 调用；(2) 对后台任务设置事务超时（`SET SESSION max_execution_time` 或代码侧计时器）；(3) 监控 `innodb_trx` 中 `trx_started` 超过阈值（如 60s）的事务并告警 + 自动 kill。DB 侧：`innodb_lock_wait_timeout` 调小（如 5s）让排队的语句快速失败而非堆积。

```python
# 长事务监控器：模拟扫描 information_schema.innodb_trx，
# 找出超过阈值的活跃事务并输出处置决策（标准库可运行）。
from datetime import datetime, timedelta

LOCK_WAIT_TIMEOUT_S = 5      # innodb_lock_wait_timeout
ALERT_THRESHOLD_S = 60       # 长事务告警阈值
KILL_THRESHOLD_S = 600       # 自动 kill 阈值

# 模拟一次扫描结果（字段对齐 innodb_trx 关键列）
trx_rows = [
    {"trx_id": 1101, "trx_started": "03:00:00", "trx_state": "RUNNING",
     "trx_rows_modified": 2_100_000, "trx_query": "UPDATE report SET ..."},
    {"trx_id": 1102, "trx_started": "03:41:02", "trx_state": "LOCK WAIT",
     "trx_rows_modified": 0, "trx_query": "UPDATE orders SET status=1 ..."},
]
NOW = datetime.strptime("03:41:40", "%H:%M:%S")

def scan(now: datetime) -> list[str]:
    actions = []
    waiting = 0
    for r in trx_rows:
        dur = (now - datetime.strptime(r["trx_started"], "%H:%M:%S")).total_seconds()
        if r["trx_state"] == "LOCK WAIT":
            waiting += 1
            if dur >= LOCK_WAIT_TIMEOUT_S:
                actions.append(f"trx {r['trx_id']} 等锁超时将报 1205，快速失败")
            continue
        if dur >= KILL_THRESHOLD_S:
            actions.append(f"trx {r['trx_id']} 已跑 {int(dur)}s，自动 kill 并记审计")
        elif dur >= ALERT_THRESHOLD_S:
            actions.append(f"trx {r['trx_id']} 已跑 {int(dur)}s，告警："
                           f"已改 {r['trx_rows_modified']} 行，从库将一次性回放")
    if waiting:
        actions.append(f"提示：{waiting} 条语句在排队，排队本身不解决锁竞争")
    return actions

if __name__ == "__main__":
    for line in scan(NOW):
        print(line)
# 输出示例：
# trx 1101 已跑 2499s，自动 kill 并记审计
# trx 1102 等锁超时将报 1205，快速失败
# 提示：1 条语句在排队，排队本身不解决锁竞争
```

**追问**：
- 一层：为什么 kill 长事务后从库延迟不能立刻恢复？→ 提示：主库回滚本身也要时间（undo 应用），且回滚过程同样产生 binlog/读压力。
- 二层：为什么 RR 隔离级别下长事务对"只读业务"也有伤害？→ 提示：快照读要沿 undo 链回溯到事务开始时的版本，链条越长读越慢。
- 三层：如何从框架层根治？→ 提示：SQLAlchemy 事件钩子监听 `after_begin`/`after_commit` 计时，超阈值直接抛异常。

**背诵要点**：
1. 长事务三连击：持锁阻塞 DML、提交时 binlog 集中导致从库延迟突增、undo 链拉长拖慢全库快照读。
2. 防线组合：事务超时阈值（告警 60s / kill 600s）+ `innodb_lock_wait_timeout` 调小 + 事务内禁止 RPC。
3. 批处理正确形态：小事务 + 幂等可重跑，整体一致性用临时表原子 RENAME 实现，不用长事务。

**复盘追问**：
1. 为什么当时没有更早发现事务在变长？提示：检查监控是否只看 QPS/慢查询，漏了 `innodb_trx` 时长维度。
2. 如果这个大事务是"必须整体一致"的业务怎么办？提示：讨论临时表+RENAME、逻辑标记双阶段切换与补偿对账的取舍。
