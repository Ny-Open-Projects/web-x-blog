### Q6571 · 统计信息过期导致执行计划翻转事故复盘

难度：P6/P7 ｜ 标签：PostgreSQL / 查询优化器 / 事故复盘

**问**：某天下午一批原本 50ms 的查询突然变成 40s，数据库 CPU 打满，但代码、索引、数据量都没明显变化。你如何定位并复盘这类"执行计划翻转"事故？

**答**：
- **结论**：优先怀疑优化器统计信息（statistics）过期或采样失真，导致 planner 在索引扫描与顺序扫描之间翻转。定位路径：抓一条慢 SQL → `EXPLAIN (ANALYZE, BUFFERS)` 对比实际行数（actual rows）与估算行数（estimated rows），估算偏差超过一个数量级基本可断定统计失真。
- **取舍**：`ANALYZE` 采样是抽样不是全量，大表低选择性列（如状态字段只有 3 个值但分布极端倾斜）默认采样容易估错，需要对该列提高 `ALTER TABLE ... ALTER COLUMN ... SET STATISTICS` 或建扩展统计 `CREATE STATISTICS`（关联列相关性）。这是"自动维护"与"手动调参"的取舍：默认 autovacuum analyze 的阈值 `scale_factor=0.1` 对亿级大表意味着要变化 1000 万行才触发，必须改 `autovacuum_analyze_scale_factor` 或按分区单独设。
- **实战**：事故后三件事——① 立即手动 `ANALYZE` 恢复；② 把该表纳入"统计新鲜度"监控（`last_analyze` 与行变更数 `n_mod_since_analyze` 告警）；③ 应用侧给关键 SQL 加 `pg_hint_plan` 或 plan guard（对比 plan hash），计划翻转时告警而不是等用户报障。

```python
# 用统计信息模拟"估算偏差"如何让 planner 翻转（纯标准库，可直接运行）
# 基线：Python 3.9+；仅用标准库模拟决策逻辑，不依赖数据库

THRESHOLD = 0.05  # 优化器经验：估算随机读代价 > 全表扫描 5% 行数时，翻转成 seq scan


def estimate_rows(sample_ratio: float, distinct_hint: dict, total: int) -> int:
    """模拟 ANALYZE 抽样：抽样没采到的稀有值会被估成平均分布"""
    avg = total / len(distinct_hint)
    # 抽样命中率低的稀有值，planner 会高估其行数
    return int(avg * max(0.1, sample_ratio))


def choose_plan(estimated_rows: int, total: int) -> str:
    return "seq_scan" if estimated_rows > total * THRESHOLD else "index_scan"


def main() -> None:
    total = 100_000_000
    status_values = {"ok": 99_900_000, "failed": 100_000}
    # 事故态：默认采样率下稀有值 failed 被高估
    est = estimate_rows(sample_ratio=0.3, distinct_hint=status_values, total=total)
    plan = choose_plan(est, total)
    print(f"estimated={est:,} plan={plan}")
    assert plan == "seq_scan", "估算偏差应导致计划翻转为全表扫描"

    # 恢复态：提高统计目标后估算贴近真实
    est2 = int(total * 0.001)  # SET STATISTICS 1000 后接近真实 0.1%
    plan2 = choose_plan(est2, total)
    print(f"estimated={est2:,} plan={plan2}")
    assert plan2 == "index_scan"


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 MySQL 的 `ANALYZE TABLE` 和 PG 的采样行为不同，对事故定位有什么影响？
→ 一句话提示：MySQL InnoDB 是在索引上随机 dive 估算（`n_distinct_pages`），持久化统计页数少，对大表同样有翻页估算失真问题，可用 `ANALYZE TABLE ... UPDATE HISTOGRAM` 补直方图。

**追问 2**：如果 `ANALYZE` 之后计划仍然不对，下一步查什么？
→ 一句话提示：查参数干扰（`work_mem`/`random_page_cost` 被 session 级改掉）、扩展统计缺失（多列相关性）、以及 prepared statement 的 generic plan 触发（PG 12+ `plan_cache_mode`）。

## 背诵要点
- 定位公式：`EXPLAIN (ANALYZE, BUFFERS)` 里 estimated rows 与 actual rows 偏差 >10 倍 ≈ 统计失真。
- PG 默认 `autovacuum_analyze_scale_factor=0.1`，亿级表要变化 10% 行才触发，大表必须调小或分区级覆盖。
- 事后三件套：手动 ANALYZE 恢复 + 统计新鲜度监控（n_mod_since_analyze）+ plan hash 告警。

## 复盘追问
- 为什么"代码没改动也会翻转"？提示：数据分布变化本身就是输入，优化器是按数据重新决策的。
- 如果业务高峰期不能直接 ANALYZE（IO 代价），有什么折中？提示：分区分批 analyze / 低峰窗口 / `SET STATISTICS` 只调关键列。
