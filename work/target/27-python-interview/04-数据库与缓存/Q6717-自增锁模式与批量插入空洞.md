### Q6717 · innodb_autoinc_lock_mode 与批量插入的自增空洞

难度：P6 ｜ 标签：自增锁、批量插入、主从复制、AUTO_INCREMENT

基线：Python 3.12；MySQL 8.0（默认 `innodb_autoinc_lock_mode=2`）；纯 Python 模拟三种自增锁模式。

**问**：订单表用自增主键。一次 `INSERT ... SELECT` 批量导入 10 万行，结束后发现主键从 100 万直接跳到 110 万，中间空了 9 万个号；更奇怪的是从库重放同样的 binlog 后，同一批数据的主键居然和主库一致。自增主键为什么会跳号？为什么主从还能对上？

**答**：
- **结论**：InnoDB 的自增分配有三种锁模式：`0`（传统表锁，语句级持有，最安全但并发差）、`1`（连续模式，简单插入用轻量锁、批量插入退化为表锁）、`2`（交错模式，MySQL 8.0 默认，分配即释放，不等待语句结束）。`=2` 下多个批量插入可以交错拿号，语句回滚或插入失败时已分配的号不会回收，于是产生**空洞**；但 binlog 记录的是**具体的主键值**（ROW 格式），从库按值重放，所以主从一致。
- **取舍**：`=2` 并发最好，适合不依赖连续 ID 的业务；`=1` 保证单语句内自增连续（批量语句仍可能跳），适合需要"号段连续"的报表；`=0` 最保守，高并发下自增锁成为瓶颈。空洞本身不是 bug，依赖"ID 连续"才是设计错误。
- **实战**：① 业务不要用自增 ID 表达"第几单/连续编号"，需要连续号用独立发号器或按日重排；② 批量导入用 `=2` + ROW binlog，避免自增锁拖住并发；③ 监控 `AUTO_INCREMENT` 与最大 ID 的差距，异常跳变可能是批量失败或回滚；④ 自增列用 `BIGINT`，`INT` 在高写入表上会提前耗尽。

```python
def allocate(
    mode: int, batches: list[int], fail_at: int, rows_per_ms: int = 10_000
) -> dict[str, object]:
    """mode: 0 表锁 / 1 连续 / 2 交错；返回分配区间、空洞与预估持锁时间。"""
    next_id, assigned, gaps, lock_ms = 1, [], 0, 0
    for idx, rows in enumerate(batches):
        start = next_id
        next_id += rows
        if idx == fail_at:
            gaps += rows                   # 已分配的号不回滚，成为空洞
            lock_ms += rows // rows_per_ms  # 失败也要等语句结束才放锁
            continue
        assigned.append((start, start + rows - 1))
        # mode 2 分配即释放；mode 0/1 要持锁到语句结束
        lock_ms += 0 if mode == 2 else rows // rows_per_ms
    return {"assigned": assigned, "next_id": next_id,
            "gaps": gaps, "lock_ms": lock_ms}


if __name__ == "__main__":
    batches = [30_000, 50_000, 20_000]
    for mode in (0, 1, 2):
        print(f"mode={mode}:", allocate(mode, batches, fail_at=1))
    print("结论：三种模式都会有空洞；mode=2 不留语句级自增锁，并发最好")
```

**追问一**：为什么 `INSERT ... SELECT` 在 `=1` 下仍然可能跳号？
→ 解析：连续模式只能保证"简单插入（行数已知）"的连续性；`INSERT ... SELECT` 的行数在语句开始时不确定，InnoDB 只能按批预留，预留多了就留下空洞。`=2` 更是每行独立分配，跳号是常态。

**追问二**：自增主键用完了会怎样？为什么线上更常见的是 `INT` 溢出而不是 `BIGINT`？
→ 解析：到达上限后插入报 `Duplicate entry ... for key 'PRIMARY'`（自增回绕或冲突），业务写入全挂。很多老表建表时用 `INT`（上限 21 亿），高写入量表几年就到顶；迁移到 `BIGINT` 需要 Online DDL 与主从切换窗口，必须提前规划。
