### Q6819 · 数据库视图做权限收口：列级砍敏感列、行级砍越权行

难度：P6 ｜ 标签：视图、权限收口、行级隔离、列级脱敏、视图泄漏、查询展开

基线：SQLite 3.45（VIEW 只读语义）；用视图实测列级/行级权限收口与"漏 WHERE 全表泄漏"事故形态，全标准库实跑。

**问**：多租户系统要求"每个租户只能看自己的行、任何角色都看不到身份证和薪资"。应用层 WHERE 过滤写得到处都是，一次 code review 漏了就泄漏。用数据库视图收口权限的原理是什么？视图漏了 WHERE 会怎样？视图会不会影响性能？为什么说"视图是权限的最后防线而不是唯一防线"？

**答**：

- **结论**：视图是**存储在数据库里的命名查询**，权限收口有两种用法：① **列级视图**——对外只暴露安全列（`CREATE VIEW emp_public AS SELECT id, name, dept FROM emp`），敏感列根本不在视图的输出 schema 里，任何走视图的角色拿不到 id_card/salary；② **行级视图**——视图里固化隔离条件（`WHERE dept='eng'` 或租户条件），用户被授权查询视图而非底表，越权行在存储层就不可见。它的价值是**把"必须记得写 WHERE"从应用层的千万个调用点收敛到 DB 的一个定义点**。但视图的两个边界必须清楚：一是视图漏了 WHERE（或底表被直接授权）就是全表泄漏——视图是定义级的防线，定义错了错得比应用层更彻底；二是视图**默认只读**（SQLite 一律不可更新，PG 部分简单视图可自动更新），写路径需要 INSTEAD OF 触发器或独立写入口。
- **取舍**：视图收口 vs 应用层 ORM 过滤（如 Django manager 过滤、SQLAlchemy 全局 filter）：视图在 DB 层，DBA/任何直连客户端也被拦住，权限模型与数据同生命周期；ORM 过滤在应用层，绕过 ORM 的脚本全失守。实践是双层防线：ORM 全局过滤保日常开发体验，视图 + 最小授权（应用账号只授视图 SELECT、不授底表）保越权底线。性能上视图**不是魔法**：查询视图 = 展开(内联)视图定义后再优化，复杂视图（多层嵌套、聚合、窗口函数）叠加业务 WHERE 后优化器可能给出糟糕计划——简单单表视图零成本，多层聚合视图要像 SQL 一样评审，必要时物化视图（PG）预计算。还有一点常被忽视：视图定义里的 `SELECT *` 是**定义时刻展开**的列快照，底表加列不会出现在旧视图里，反而造成"以为有权限其实列悄悄变了"的口径漂移。
- **实战**：一次数据合规整改，要求导出接口对身份证/薪资做角色隔离。原实现靠 ORM 里 14 处 `.options()` 手工列裁剪，审计发现 2 处遗漏（财务导出接口漏了 id_card）。改造：建 `emp_public`（无敏感列）与 `emp_hr`（含薪资，授权给 hr 角色）两个视图，应用账号只授视图；直连数据的 BI 账号只授 `emp_public`；DBA 加监控（对底表 emp 的 SELECT 全审计，非白名单来源告警）。上线后合规审计通过。同时踩过一个性能坑：报表视图三层嵌套聚合，某租户查询把整库拖慢——拆成两个单层视图 + 物化视图后恢复。规范沉淀：**视图只做单层过滤/裁剪，聚合视图必须评审执行计划**。

下面用 SQLite 实测列级/行级视图的收口效果与泄漏形态。

```python
# Q6819 数据库视图做权限收口: 行级/列级视图 + 视图漏 WHERE 的全表泄漏
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE emp(id INTEGER PRIMARY KEY, name TEXT, dept TEXT, salary INT, id_card TEXT)")
conn.executemany("INSERT INTO emp VALUES(?,?,?,?,?)", [
    (1, "甲", "eng", 30000, "110101199001011234"),
    (2, "乙", "eng", 26000, "110101199002022345"),
    (3, "丙", "hr",  20000, "110101199003033456"),
])
conn.commit()

# [1] 列级视图: 对外只暴露安全列, 身份证与薪资不进视图
conn.execute("""CREATE VIEW emp_public AS
                 SELECT id, name, dept FROM emp""")
cols = [r[1] for r in conn.execute("PRAGMA table_info(emp_public)")]
print(f"[1] 列级视图列: {cols}; 直接 SELECT * 拿不到 id_card/salary")
assert "salary" not in cols and "id_card" not in cols

# [2] 行级视图: 参数化租户/部门隔离, 应用只授视图权限
conn.execute("""CREATE VIEW emp_eng AS
                 SELECT id, name, salary FROM emp WHERE dept = 'eng'""")
n = conn.execute("SELECT count(*) FROM emp_eng").fetchone()[0]
hr = conn.execute("SELECT count(*) FROM emp WHERE dept='hr'").fetchone()[0]
print(f"[2] 行级视图 emp_eng: 可见 {n} 行; 底表 hr 行 {hr} 行不可见")
assert n == 2 and hr == 1

# [3] 事故: 视图里漏了隔离条件, 或应用对视图 SELECT 加了旁路
conn.execute("""CREATE VIEW emp_leak AS
                 SELECT id, name, dept, salary FROM emp""")   # 忘了 WHERE dept
leak = conn.execute("SELECT count(*) FROM emp_leak WHERE dept='hr'").fetchone()[0]
print(f"[3] 漏 WHERE 的'隔离视图': hr 行竟可见 {leak} 行 → 全租户泄漏")
assert leak == 1

# [4] 视图默认只读: 更新需 INSTEAD OF 触发器, 误以为可写会静默失败面
try:
    conn.execute("UPDATE emp_eng SET salary = 1 WHERE id = 1")
    print("[4] 简单视图可直接 UPDATE")
except sqlite3.OperationalError as e:
    print(f"[4] 视图默认只读: {e} (PG 部分简单视图可自动更新, sqlite 一律不可, 需 INSTEAD OF 触发器)")

# [5] 视图的执行语义: 每次展开查询, 复杂视图叠加复杂 WHERE 可能拖慢底表
import time
conn.execute("CREATE TABLE big(id INTEGER PRIMARY KEY, dept TEXT, v INT)")
conn.executemany("INSERT INTO big(dept, v) VALUES(?, ?)",
                 (("eng" if i % 2 else "hr", i) for i in range(100_000)))
conn.commit()
conn.execute("CREATE VIEW v_eng AS SELECT * FROM big WHERE dept='eng'")
t0 = time.perf_counter()
conn.execute("SELECT count(*) FROM v_eng WHERE v > 50000").fetchone()
t_view = (time.perf_counter() - t0) * 1000
t0 = time.perf_counter()
conn.execute("SELECT count(*) FROM big WHERE dept='eng' AND v > 50000").fetchone()
t_base = (time.perf_counter() - t0) * 1000
print(f"[5] 视图 {t_view:.1f} ms vs 等价底表查询 {t_base:.1f} ms (语义等价, 无魔法加速)")
assert True
print("    → 实测 视图是权限收口利器: 列级砍敏感列、行级砍越权行; 但视图漏 WHERE 就是全表泄漏, 且不自动更快")
```

**追问一**：视图、RLS（行级安全策略）、应用层过滤，三层的防线顺序怎么排？—— 防线深度：RLS（PG）> 视图 > 应用层过滤。RLS 在引擎内核按会话变量强制过滤，用户根本无法绕过；视图靠"只授视图不授底表"的授权纪律，底表误授权即失守；应用层过滤靠代码纪律，任何直连/旁路都绕过。生产多租户的推荐组合：RLS 做强制底线（PG 场景）、视图做 DBA/BI 工具的统一出口、ORM 过滤做开发体验——三层各拦一类绕过。MySQL 没有 RLS，视图 + 底表只授权限就更关键，且要配"对底表的 SELECT 审计"补漏。

**追问二**：视图定义里的 `SELECT *` 为什么危险？—— 建视图时 `*` 就被展开成定义时刻的具体列清单，之后底表加列不会自动出现在视图里（不同引擎行为有差异，PG 会保留定义时列集）；反过来底表删列/改列会让视图失效。危险在于"以为视图总是全列"：新加的敏感列没进旧视图是好事，但新加的授权判断列（如 `is_deleted`）也没进视图，过滤条件就漏了。规范：视图定义永远显式列名，列变更随底表 DDL 一起评审；这和"SQL 禁止 SELECT *"是同一条纪律——视图只是把这条纪律的责任从查询侧移到了定义侧。

## 背诵要点

- 列级视图砍敏感列（不在输出 schema 就拿不到）、行级视图固化隔离条件；权限从"千万个调用点"收敛到一个定义点。
- 视图漏 WHERE = 全表泄漏，比应用层错得更彻底；视图默认只读，SQLite 一律不可 UPDATE。
- 视图 = 展开定义后优化，无魔法加速；定义禁 SELECT *（定义时刻列快照），聚合视图必须评审执行计划。

## 复盘追问

- 合规审计发现导出接口漏了身份证列，为什么视图方案能根治？（列不在视图 schema 里，任何走视图的路径都拿不到；把授权只授视图、底表对应用账号收回 SELECT 即成强制约束）
- 报表视图三层嵌套把库拖慢，怎么治理？（拆单层 + 物化视图预计算；复杂视图当 SQL 评审，EXPLAIN 看展开后计划；这也是"视图不是抽象层而是查询"的体现）
