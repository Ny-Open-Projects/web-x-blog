### Q6548 · 成本工程：读流量涨了 5 倍，是加从库还是加缓存？

> 难度:★★★★ | 标签:成本工程, 读写分离, 架构决策

**问**：一个读多写少的系统，读 QPS 从 2 万涨到 10 万，DBA 提了两个方案：加 3 个读从库（每台实例费 8000 元/月），或者把热点读全量上缓存。怎么算这笔账？"加从库"这个直觉解法在什么条件下是错的？

**答**：结论：决策公式是**单位读成本比较**——缓存方案的单位读成本（内存/命中数）通常是从库方案的 1/10 以下，所以默认先缓存；但从库方案的优势是**一致性**（永远读到已提交数据）和**零代码改造**。正确决策顺序：读放大能被缓存吃掉的（热点集中）先缓存；读集合太大无法缓存的（大范围扫描、随机翻页）才加从库；两者都要算"从库加一台只能线性扩多少读"的真实容量。

机理与实战：
- **从库的真实容量**：一台从库不是等价加法——读 QPS 扩展受限于网络带宽（大结果集）、buffer pool 命中率（随机读穿透到盘）与复制延迟（从库回放占用资源）。经验上单从库安全读承载 ≈ 主库同规格的 0.7 倍，因为还要留回放与备份的资源。
- **缓存单位成本账**：热点 key 占读流量 80% 的业务，缓存 20GB 内存 ≈ 实例费几百元/月，就把 80% 读挡在 DB 外；而同样的 80% 读用从库扛需要 4-5 台从库。**命中率是成本杠杆**：命中率从 90% 提到 99%，从库需求从 10 台降到 1 台。
- **什么时候必须加从库**：① 读集合本身太大（全量列表、分析查询）缓存内存装不下；② 业务要求"读自己写"强一致；③ 缓存失效风暴的风险大于从库成本（如秒杀类不能接受缓存抖动）。这三种情况缓存不是替代品。
- **成本三角**：一致性（复制延迟、缓存失效窗口）— 成本（实例费/内存费）— 复杂度（缓存失效逻辑、路由）。任何决策都要在评审里说清牺牲哪一角，而不是只说"加机器"。

```python
# 基线:Python 3.10+;纯标准库,加从库 vs 上缓存的单位读成本对比
from __future__ import annotations
from dataclasses import dataclass


@dataclass
class ReadScale:
    read_qps: int
    hot_ratio: float          # 热点 key 覆盖的读流量比例
    replica_qps: int = 20_000   # 单从库安全读承载
    replica_cost: int = 8000    # 元/月/台
    cache_gb: float = 20
    cache_cost_per_gb: int = 400  # 元/月/GB(内存型实例折算)


def replica_plan(r: ReadScale, hit_ratio: float = 0.0) -> dict:
    db_qps = r.read_qps * (1 - hit_ratio)
    replicas = -(-db_qps // r.replica_qps)  # ceil
    return {"DB承接QPS": int(db_qps), "从库数": int(replicas),
            "月成本": int(replicas) * r.replica_cost}


def cache_plan(r: ReadScale) -> dict:
    hit_qps = r.read_qps * r.hot_ratio
    db_qps = r.read_qps - hit_qps
    replicas = -(-db_qps // r.replica_qps)
    cost = r.cache_gb * r.cache_cost_per_gb + replicas * r.replica_cost
    return {"缓存挡掉的QPS": int(hit_qps), "仍需从库": int(replicas), "月成本": int(cost)}


def demo() -> None:
    r = ReadScale(read_qps=100_000, hot_ratio=0.8)
    pure = replica_plan(r)                 # 全读走 DB:5 台从库
    cached = cache_plan(r)                 # 80% 命中:1 台从库 + 缓存
    print(f"  纯从库方案: {pure}")
    print(f"  缓存+从库:  {cached}")
    print(f"  缓存命中率 0.9 时纯从库: {replica_plan(r, 0.9)}")
    assert pure["从库数"] == 5 and pure["月成本"] == 40000
    assert cached["月成本"] < pure["月成本"] / 2    # 缓存方案省一半以上
    assert replica_plan(r, 0.9)["从库数"] == 1     # 99% 命中只需 1 台
    # 反例:读集合不可缓存(hot_ratio=0.1)时缓存方案不成立
    r2 = ReadScale(read_qps=100_000, hot_ratio=0.1)
    assert cache_plan(r2)["月成本"] > cache_plan(r)["月成本"]
    print("决策公式:单位读成本比较,命中率是成本杠杆 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：加了缓存后为什么读 QPS 涨 5 倍时"从库延迟"反而恶化了？
答：缓存命中率下降的时段（促销、缓存抖动）回源读瞬时打穿到 DB 和从库，从库既要承接读回源又要回放主库积压的写 binlog，延迟放大后健康检查摘除从库，压力再转移到其余从库形成正反馈。所以容量账要按"缓存失效时的穿透峰值"算 DB 承载量，而不是按平均命中率算。

**追问二**："读自己写"的一致性需求怎么用低成本方案满足？
答：不需要读写分离强一致，常用三板斧：写后短 TTL 内该用户读路由主库（会话级粘滞）、关键读带版本号校验（写返回版本，读不到该版本则走主库）、或前端写成功后对写路径的数据直接用写时返回值渲染。三种方案成本都远低于"为一致性多买从库"，面试里要能写出方案取舍。

## 背诵要点
- 决策公式：单位读成本 = 月成本/承接 QPS；热点集中（hot_ratio 高）先缓存，缓存 80% 读可把从库从 5 台降到 1 台。
- 命中率是成本杠杆：90%→99% 命中，从库 10 台→1 台；但容量要按缓存失效穿透峰值算，不是平均命中率。
- 必须加从库的三情形：读集合太大缓存装不下、读自己写强一致、不能接受缓存失效风暴；成本三角=一致性/成本/复杂度，决策要明说牺牲哪角。

## 复盘追问
- 复盘一次"加从库没用"的扩容：读压测没变快，为什么？（提示：瓶颈在 buffer pool 未命中的磁盘随机读或大结果集带宽，加从库是复制瓶颈不是读瓶颈；扩容前要定位读慢的真实资源维度）
- 缓存实例和从库实例的"故障半径"在成本账里怎么量化？（提示：缓存全挂=读穿透风暴需要限流预案；从库挂=读容量降级；两者的故障概率×影响面要折算进月成本做 TCO 比较，不能只看账单）
