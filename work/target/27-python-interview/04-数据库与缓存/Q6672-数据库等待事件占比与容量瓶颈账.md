### Q6672 · 用等待事件占比定位容量瓶颈：IO、锁还是 CPU

难度：P6/P7 ｜ 标签：容量规划、等待事件、性能诊断

**问**：数据库慢了，有人说加内存、有人说加 CPU、有人说优化索引。如何用"等待事件占比"做出有数据支撑的容量决策？

**答**：**结论**：容量规划的依据不是资源使用率（CPU 80% 不代表 CPU 是瓶颈），而是**等待时间在各类事件上的分布**。把数据库总时间拆成 `CPU + IO等待 + 锁等待 + 网络等待`，谁占比高谁吃掉扩容收益：IO 等待 60% 才考虑内存/盘，锁等待高扩容毫无作用。

**取舍**：MySQL 用 performance_schema 的 `events_waits_summary` 或 PG 的 `pg_stat_activity` 采样；采样法的代价是自身开销（高频采样打满源库），所以要低频（1-5s）+ 只在慢期间开启。资源水位账（buffer pool 命中率、CPU run queue）作为旁证，不能单独决策。

**实战**：把"等待占比"做成巡检指标：每 5 分钟聚合一次，连续 3 个窗口 IO 等待 > 50% 触发容量评审；锁等待 > 20% 转给应用层治理（索引、事务长度），而不是扩容。

```python
# 等待事件聚合：从 pg_stat_activity 风格的采样序列算占比并给容量建议
from collections import defaultdict
from datetime import datetime

def classify(state: str, wait_type: str | None) -> str:
    """把一次采样归类到容量维度。"""
    if state == "active":
        if wait_type is None:
            return "CPU"          # active 且无等待事件 = 真在算
        return wait_type          # IODataFileRead / LWLock / Lock 等
    return "Idle"

def wait_profile(samples: list[tuple[str, str | None]]) -> dict:
    total = len(samples)
    buckets: dict[str, int] = defaultdict(int)
    for state, wt in samples:
        buckets[classify(state, wt)] += 1
    return {k: v / total for k, v in buckets.items()}

def capacity_verdict(profile: dict) -> list[str]:
    advice = []
    if profile.get("IODataFileRead", 0) + profile.get("IODataFileWrite", 0) > 0.5:
        advice.append("IO等待>50%：优先内存/磁盘升级，扩CPU无效")
    if profile.get("Lock", 0) + profile.get("LWLock", 0) > 0.2:
        advice.append("锁等待>20%：转应用层治理（索引/事务长度），不扩容")
    if profile.get("CPU", 0) > 0.7 and profile.get("IODataFileRead", 0) < 0.1:
        advice.append("CPU型负载：可水平扩读副本或升规格")
    if not advice:
        advice.append("无单一主导瓶颈：先看慢查询采样再谈容量")
    return advice

# 模拟 20 次采样（生产上来自定时 SELECT pg_stat_activity）
samples = (
    [("active", "IODataFileRead")] * 11
    + [("active", "Lock")] * 4
    + [("active", None)] * 3
    + [("idle in transaction", None)] * 2
)
profile = wait_profile(samples)
print({k: f"{v:.0%}" for k, v in sorted(profile.items())})
for line in capacity_verdict(profile):
    print("-", line)
# -> IO 等待 55% 触发内存/盘建议；锁 20% 触发治理建议
```

**追问 1**：为什么"CPU 使用率 90%"不能直接得出扩 CPU 的结论？
提示：CPU 90% 里可能大半是在自旋等锁（spinlock）或压缩解压 IO 数据；只有"active 且无等待事件"的 CPU 才是有效计算。

**追问 2**：`idle in transaction` 占比高时该归入哪个容量桶？
提示：它不耗 CPU 但锁住版本与缓冲池、拖垮 VACUUM/checkpoint，应单独建"事务卫生"桶并告警，混入 Idle 会漏判。

**追问 3**：采样本身会不会改变结论（观察者效应）？
提示：会——对 `pg_stat_activity` 的全量查询自身持有 LWLock；对策是限制采样频率、只在慢窗口开启，并把采样耗时计入自己的指标。

## 背诵要点
1. 容量决策看等待事件占比，不看资源水位：IO>50% 才扩内存盘，锁>20% 转治理，扩容对锁等待无效。
2. "active 且无等待事件"才是真 CPU 计算；`idle in transaction` 单独建桶。
3. 采样有观察者效应：低频（1-5s）+ 只在慢窗口开启。
