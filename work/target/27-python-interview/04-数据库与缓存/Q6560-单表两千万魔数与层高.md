### Q6560 · 单表两千万魔数：B+Tree 层高推算与容量账

难度：P5 | 标签：B+Tree、容量规划、索引原理、分表时机

**问**："单表超过 2000 万行就要分表"是面试和评审里的高频魔数，但它有依据吗？换一张行宽 100B 的表，阈值还是 2000 万吗？层高从 3 变 4 真实代价是什么？

**答**：
- **结论**：两千万是"16KB 页 + 1KB 行宽"下的推算值：非叶节点扇出 ≈ 16384/(8+6) ≈ 1170，叶页每页 16 行，3 层 B+Tree 容量 = 1170² × 16 ≈ 2190 万——超过就涨到 4 层。层高 +1 的真实代价是每次点查多读一个非根页：buffer pool 命中时只是内存访问，未命中时是一次磁盘 IO；真正要担心的是 IO 放大与缓存命中率下滑，不是行数本身。行宽 100B 时 3 层能装 2.2 亿行——魔数必须换成"自己行宽的推算"。
- **取舍**：分表/分区不是唯一解：归档冷数据（行数下去了）、覆盖索引让查询不回表（IO 没涨）、加大 buffer pool（未命中变命中）都能把"涨到 4 层"的代价消化掉。反过来，点查为主的小表哪怕 5000 万行，如果热数据全在内存，4 层也无感——先测缓存命中率再决定动不动表结构。
- **实战**：容量评审三步：① 用真实行宽算 3/4 层容量边界；② 看业务增速推"什么时候到边界"；③ 到边界前一年开始归档/分区方案选型（改造需要时间），而不是等到监控告警。

```python
"""单表两千万的魔数：B+Tree 层高推算与"魔数"的真实来源。"""
PAGE_BYTES = 16 * 1024     # InnoDB 页大小
FANOUT = PAGE_BYTES // (8 + 6)   # 非叶节点：bigint 主键 8B + 页指针 6B ≈ 1170

def tree_capacity(row_bytes: int, height: int) -> float:
    """height 层 B+Tree 能装多少行：扇出^(height-1) × 叶子行数。"""
    leaf_rows = PAGE_BYTES // row_bytes
    return FANOUT ** (height - 1) * leaf_rows

print(f"扇出 ≈ {FANOUT}（每页可容纳的主键+指针数）")
print(f"{'行宽':>8} | {'2层容量':>12} | {'3层容量':>14} | {'4层容量':>16}")
for row_bytes in (1024, 256, 100):
    caps = [tree_capacity(row_bytes, h) for h in (2, 3, 4)]
    print(f"{row_bytes:>6}B | {caps[0]:>12,.0f} | {caps[1]:>14,.0f} | {caps[2]:>16,.0f}")

cap_1k = tree_capacity(1024, 3)
print(f"\n行宽 1KB 时 3 层容量 ≈ {cap_1k / 1e4:,.0f} 万行——"
      f"'两千万'魔数正是这个推算，是经验值不是硬限制")
# 层高的真实代价：根节点常驻内存，层数增加一次 = 每次查询多读一个页
print("层高 3->4：每次点查多一次非根页读取；buffer pool 命中时是内存访问，"
      "未命中时是一次磁盘 IO——所以'两千万要拆表'真正担心的是 IO 放大而非行数本身")
print("正确姿势：算自己行宽下的层数容量，配合访问模式（点查/范围扫）决定分区或归档，而不是背魔数")
```

**追问链**：
1. 追问一层：为什么根节点不算 IO？——B+Tree 的根页（以及第 2 层的大部分）是热点页，长期驻留 buffer pool；层数增加实际多的是"最深一层的非叶页"访问，所以 3→4 层的增量是每查询约一次页访问，命中率决定它是内存访问还是磁盘 IO。
2. 追问二层：为什么"行宽 100B 的表 2 亿行也不一定要分"？——容量推算只回答"会不会涨层"；涨层的代价要看访问模式：纯点查且热数据在内存，代价趋近于零；范围扫描大或缓存命中率低，代价才会兑现。分表决策 = 层高推算 × 访问模式 × 增速，三个变量缺一不可。

**背诵要点**：
1. 两千万 = 16KB 页 × 1KB 行宽 × 3 层 B+Tree 的推算值：1170² × 16 ≈ 2190 万。
2. 层高 +1 的代价 = 每点查多读一个非根页，是 IO 放大问题，命中率决定痛感。
3. 解法不止分表：归档、覆盖索引、加大 buffer pool 都能消化层高代价。

**复盘追问**：
1. 评审时怎么快速估算某张表"离 4 层还有多远"？（取平均行宽 → 叶页行数 → 3 层容量 → 当前行数占比；再乘业务增速得"到期时间"）
2. 为什么很多"2 亿行单表"的库没有事故？（热点数据集中在最近数据且 buffer pool 足够大，点查全程内存命中；它们的风险在备份/DDL/统计信息这类全表操作上，而非日常查询）
