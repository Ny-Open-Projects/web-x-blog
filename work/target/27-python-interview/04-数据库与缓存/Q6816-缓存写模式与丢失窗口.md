### Q6816 · 缓存写模式：cache-aside、write-through 与 write-behind 的丢失窗口

难度：P6 ｜ 标签：缓存写模式、cache-aside、write-through、write-behind、丢失窗口、批量刷盘

基线：Python 3.12 标准库模拟三种写模式；用 100 次写入实测写延迟与未刷盘窗口，不依赖外部缓存。

**问**：写缓存的姿势常被说成"先更新数据库再删缓存"一句话，但真实系统里有 cache-aside、write-through、write-behind 三种模式。write-behind 写入快 100 倍代价是什么？丢失窗口怎么算？什么业务敢用？三种模式各自的延迟、一致性、复杂度账怎么算？

**答**：

- **结论**：三种写模式的本质区别是"**缓存与 DB 谁先谁后、是否同步**"。① **cache-aside（旁路缓存）**：应用直写 DB，然后删缓存（或失效），下次读时回填——写路径只有 DB 成本，读路径未命中时多一次回源；一致性靠"删缓存 + TTL"近似保证，是绝大多数业务默认选择。② **write-through（写穿透）**：缓存作为唯一门面，写请求同步双写（缓存与 DB 都写成功才返回）——读永远命中缓存、强一致，但写延迟 = 缓存 + DB 之和，写放大也最高。③ **write-behind（写后异步）**：只写缓存并标脏，异步批量刷 DB——写延迟最低（实测约为同步双写的 1/100），代价是**丢失窗口**：崩溃时所有未刷盘的脏数据丢失，窗口上限 = 刷盘间隔（或脏数据量阈值触发）。丢失窗口不是 bug 而是设计参数，必须与业务可容忍丢失量对账。
- **取舍**：write-behind 的收益（写延迟、写吞吐、DB 压力削峰）与风险（窗口内崩溃丢数据、脏区间复杂性、缓存与 DB 短暂不一致）必须一起算。敢用的场景：计数器/点赞/浏览量这类"丢了可接受、丢了能重算"的数据；不敢用的：账户余额、订单状态——这类用 write-behind 等于把可丢失窗口写进 SLA。批量刷盘还有顺序问题：同一 key 多次写只刷最新值（合并），跨 key 不能乱序覆盖 DB 里的更新数据——刷盘要按 key 合并而不是 FIFO 重放。另一个常见误区是"write-behind 崩溃可以靠重放请求恢复"——上游不一定保留原始请求，恢复链路本身要设计（写前日志/事件溯源）。
- **实战**：一篇热点文章的计数器（浏览/点赞）QPS 冲到 3 万，直写 DB 把主库写 IOPS 打满。改造：计数走 Redis（write-behind，每 2 秒或脏超 1 万条刷一次 DB，`HINCRBY` 累加后 SET 回写），崩溃最多丢 2 秒计数——业务接受（计数是统计性质）。同时点赞这类"用户可感知"的操作保留 cache-aside 直写。改造后主库写 IOPS 降 92%。复盘规范：**凡是 write-behind 必须写明三个数**——刷盘间隔、最大脏量、崩溃丢失上限，并作为架构文档必填项评审。

下面用 100 次写入实测三种模式的延迟与丢失窗口。

```python
# Q6816 缓存写模式: cache-aside / write-through / write-behind 丢失窗口
import time

class DB:
    def __init__(self):
        self.data, self.writes = {}, 0
    def write(self, k, v):
        time.sleep(0.002)              # 模拟 2ms 落盘成本
        self.data[k] = v
        self.writes += 1

class Cache:
    def __init__(self):
        self.data = {}

# [1] cache-aside: 应用先写库再删缓存, 读时回填
class CacheAside:
    def __init__(self, db, cache):
        self.db, self.cache = db, cache
    def put(self, k, v):
        self.db.write(k, v)
        self.cache.data.pop(k, None)           # 删而非写, 让下次读回填
        return "db-first-invalidate"
    def get(self, k):
        if k in self.cache.data:
            return self.cache.data[k], "hit"
        v = self.db.data.get(k)
        if v is not None:
            self.cache.data[k] = v
        return v, "miss->refill"

db, c = DB(), Cache()
ca = CacheAside(db, c)
ca.put("x", 1)
got, path = ca.get("x")
print(f"[1] cache-aside: put 后 get={got}({path}); DB writes={db.writes}")
assert got == 1 and db.writes == 1

# [2] write-through: 缓存是门面, 同步双写, 读永远走缓存
class WriteThrough:
    def __init__(self, db, cache):
        self.db, self.cache = db, cache
    def put(self, k, v):
        self.db.write(k, v)          # 同步写库
        self.cache.data[k] = v       # 同步写缓存
        return "sync-both"
    def get(self, k):
        return self.cache.data.get(k), "cache"

db2, c2 = DB(), Cache()
wt = WriteThrough(db2, c2)
t0 = time.perf_counter()
for i in range(100):
    wt.put(f"k{i}", i)
elapsed = (time.perf_counter() - t0) * 1000
print(f"[2] write-through: 100 次同步双写 {elapsed:.0f} ms (受 DB 2ms/次拖累)")
assert elapsed > 150 and db2.writes == 100, "同步双写应被 DB 写入拖慢到 >150ms"

# [3] write-behind: 只写缓存, 异步批量刷库; 崩溃丢窗口 = 未刷盘区间
class WriteBehind:
    def __init__(self, db, cache):
        self.db, self.cache = db, cache
        self.dirty = {}
    def put(self, k, v):
        self.cache.data[k] = v
        self.dirty[k] = v            # 标脏, 不立即落库
        return "cache-only"
    def flush(self):
        n = len(self.dirty)
        for k, v in self.dirty.items():
            self.db.write(k, v)
        self.dirty.clear()
        return n

db3, c3 = DB(), Cache()
wb = WriteBehind(db3, c3)
t0 = time.perf_counter()
for i in range(100):
    wb.put(f"k{i}", i)
elapsed_fast = (time.perf_counter() - t0) * 1000
pending = len(wb.dirty)
print(f"[3] write-behind: 100 次写 {elapsed_fast:.0f} ms (≈{200/elapsed_fast:.0f}x 提速), 未刷盘 {pending} 条")
assert elapsed_fast < 50 and pending == 100
n = wb.flush()
print(f"    批量刷库 {n} 条; 若此刻进程崩溃, 丢失窗口 = 未刷盘区间")
assert n == 100

# [4] 丢失窗口量化: 崩溃发生在两次 flush 之间, 未刷盘即丢失
wb2 = WriteBehind(db3, c3)
wb2.put("a", 1)
lost_before_flush = len(wb2.dirty)
print(f"[4] 崩溃时未刷盘 {lost_before_flush} 条即丢失; 丢失窗口上限 = 刷盘间隔")
assert lost_before_flush == 1
print("    → 实测 cache-aside 简单但读路径慢一次; write-through 一致但写延迟高; write-behind 快但必须算清可丢窗口")
```

**追问一**：write-behind 的刷盘为什么要"按 key 合并"而不是按写入顺序重放？—— 同一 key 在窗口内可能被写 100 次，逐次重放会做 100 次 DB 写（写放大），而合并后只写最终值 1 次；更重要的是跨 key 重放如果按到达顺序排队，可能把旧值覆盖到 DB 中已被直写路径更新的行（不同 key 之间无序、同一 key 也不保序到 DB）。正确姿势：脏表以 key 为粒度合并（保留最新值），刷盘时用 `SET`（绝对值）或带版本的条件写，DB 侧已是新值的 key 跳过。计数器场景则相反——必须把增量（如 +37）刷下去，合并成绝对值会在并发直写下互相覆盖，所以计数类用增量累计、状态类用绝对值合并。

**追问二**：write-through 在什么场景下值得忍受双写延迟？—— 两个条件同时满足时值得：① 读远多于写且读必须强一致（配置、库存可售量这类读侧绝对不能脏的场景）；② 写 QPS 不高，双写延迟可接受。它换来的最大好处是**读路径零 miss、零回源风暴**：DB 永远和缓存同步，缓存失效不会引发击穿。反过来说，写多读少或写延迟敏感的场景，write-through 的同步 DB 写就是瓶颈本身。混合模式也常见：热点读走 write-through 的小容量强一致层，大容量历史数据走 cache-aside——按数据的"一致性敏感度"分层选模式，而不是全系统一个模式。

## 背诵要点

- cache-aside：写 DB 后删缓存、读回填；write-through：同步双写读强一致；write-behind：只写缓存异步刷盘，最快但有丢失窗口。
- 丢失窗口上限 = 刷盘间隔或脏量阈值；write-behind 必须文档化三个数（间隔、最大脏量、丢失上限）。
- 刷盘按 key 合并：状态类刷绝对值、计数类刷增量；write-behind 只用于"丢了可接受/可重算"的数据。

## 复盘追问

- 点赞计数用 write-behind，崩溃后 Redis 里丢了 2 秒数据，怎么补救？（计数可重算：从明细事件流/DB 明细重新聚合；这正说明 write-behind 要选"可重算"数据）
- 为什么 write-behind 不适合订单状态？（订单状态丢失 = 资损与对账事故；且状态变更需被下游订阅感知，脏区间会让 binlog 与缓存出现语义级不一致）
