### Q6663 · 缓存扩容与数据库扩容的成本交叉点账

难度：P6-P7 | 标签：成本工程、容量规划、缓存

**问**：读 QPS 涨了 60%，数据库 CPU 从 45% 爬到 75%。方案 A：数据库主实例升一档规格（月成本 +40%）；方案 B：缓存集群扩容提升命中率（月成本 +8%）。这笔账怎么算出"该扩谁"？什么情况下算完发现该扩数据库？

**答**：结论：账的核心是**每 1% 命中率折算的数据库 QPS 与规格阶梯**。方案 B 每提升 1% 命中率，回源量按当前回源基数下降；只有当"命中率提升带来的数据库降载 × 数据库规格涨价"大于"缓存涨价"时才选 B。反过来，如果命中率已经 95%+（剩余 miss 是长尾 key，加内存也缓不到），或者瓶颈是写路径/连接数（缓存帮不上），算完就该扩数据库。

取舍与实战：
1. 先量化回源函数：回源 QPS = 读 QPS × (1 - 命中率)。命中率 90%→95%，回源减半，数据库 CPU 大约等比例下降（CPU 与查询数近似线性）。
2. 规格阶梯的不连续性：云数据库规格是倍增阶梯（如 8C32G→16C64G 翻倍涨价），缓存节点可以小步加（加一个分片）；**当所需降载小于半档数据库规格时，几乎总是缓存更便宜**；当降载跨过整档且命中率已接近上限时，扩库。
3. 隐藏成本要入账：缓存扩容有数据预热期（预热期间命中率暂降，Q6149/冷缓存爬坡），DB 扩容有主从切换闪断窗口；两者的变更风险成本要写进比价表。
4. 长尾判定：按 key 访问频率画 Zipf 曲线，top N key 占比如果已到 99%，加缓存内存边际收益趋零——这是"算完该扩库"的最常见原因。

```python
"""缓存 vs 数据库扩容成本交叉点计算（标准库，可运行）"""

def compare_cost(
    read_qps: int,
    hit_rate_now: float,       # 当前命中率
    hit_rate_after: float,     # 扩缓存后预期命中率
    db_cpu_now: float,         # 当前 DB CPU 利用率
    db_cpu_limit: float,       # 目标安全水位
    cache_cost_delta: float,   # 缓存扩容月成本增量（元）
    db_upgrade_cost: float,    # DB 升档月成本增量（元）
) -> dict:
    miss_saved = read_qps * (hit_rate_after - hit_rate_now)
    # 查询数近似线性折算 CPU 降幅
    cpu_drop = db_cpu_now * (miss_saved / max(read_qps * (1 - hit_rate_now), 1))
    cpu_after = db_cpu_now - cpu_drop
    cache_ok = cpu_after <= db_cpu_limit
    # 折算：缓存方案每节省 1 点 CPU 的单价 vs DB 升档摊到每点 CPU
    cache_unit = cache_cost_delta / max(cpu_drop, 0.01)
    db_unit = db_upgrade_cost / max(db_cpu_now - db_cpu_limit, 0.01)
    return {
        "扩缓存后DB_CPU": round(cpu_after, 1),
        "缓存方案可行": cache_ok,
        "缓存每降1点CPU成本": round(cache_unit, 1),
        "DB每降1点CPU成本": round(db_unit, 1),
        "结论": "扩缓存" if cache_ok and cache_unit < db_unit else "扩数据库或双管齐下",
    }

r = compare_cost(read_qps=50_000, hit_rate_now=0.90, hit_rate_after=0.96,
                 db_cpu_now=75, db_cpu_limit=60,
                 cache_cost_delta=2_000, db_upgrade_cost=30_000)
for k, v in r.items():
    print(f"{k}: {v}")
```

**追问 1**：为什么命中率从 90% 提到 95% 比从 95% 提到 98% 便宜得多？
**提示**：回源量分别减半和降 40%，但前者基线是 10% 的 miss、后者是 5%；更重要的是后 5% 往往是长尾 key，需要的缓存内存按长尾全集算，边际成本陡增（Zipf 分布）。

**追问 2**：写多读少的场景为什么这笔账直接判"扩库"？
**提示**：命中率只作用于读路径；写 QPS 的 CPU、WAL/binlog IO、主从复制带宽缓存都帮不上，瓶颈在写时缓存扩容是无效支出。

## 背诵要点
- 核心公式：回源 QPS = 读 QPS × (1 - 命中率)，CPU 降幅近似线性折算。
- 交叉点判定：降载小于半档 DB 规格→扩缓存；命中率 95%+ 或写路径瓶颈→扩库。
- 隐藏成本入账：缓存预热期命中率暂降、DB 扩容切换闪断，变更风险写进比价表。
