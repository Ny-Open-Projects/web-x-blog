### Q6540 · SQL 审核工单：哪些 SQL 该被门禁拦下、哪些只该建议？

> 难度:★★★ | 标签:SQL 审核, 规则引擎, 工程规范

**问**：大厂的 SQL 变更为什么要过审核工单平台（Archery/Yearning 思路）？自动审核的规则分几级？"UPDATE 不带 WHERE"为什么必须阻断？怎么设计规则引擎避免误杀 ORM 生成的正常 SQL？

**答**：结论：SQL 审核工单 = 变更 SQL 上线前的"**静态规则 + 影响面预估 + 分级审批**"门禁。规则分四级：**阻断**（不可逆事故：UPDATE/DELETE 无 WHERE、无 WHERE 全表扫描进生产）、**DBA 审批**（有损 DDL：DROP/MODIFY，双人确认+备份）、**建议**（SELECT *、无 LIMIT——放行但留痕）、**通过**。误杀控制靠分级放行 + 豁免工单 + 对参数化 SQL 做"模板+样例参数"审核。

机理与实战：
- **阻断级为什么不容商量**：UPDATE/DELETE 无 WHERE 在 autocommit 下立即生效、影响全表，回滚要靠 binlog 反解（大表代价小时级到天级）；这类规则没有"提醒后放行"的空间，必须连工单都开不出来。
- **影响面预估**：规则引擎之外还要跑 EXPLAIN——预估扫描行数、锁范围（是否上 GAP/表锁）、是否命中索引；大表 DDL 自动检查行数与在线变更工具可用性。
- **规则引擎实现**：真实平台用 sqlparse（第三方，基线 sqlparse 0.4+）解析 AST 做结构化规则；标准库可以用分词+模式做轻量版，但嵌套子查询/注释/字符串常量会误判，所以轻量版只适合做"粗筛+提示"，门禁级决策要 AST。
- **防绕过**：审核对象是"语句模板"而非开发者手抄的 SQL——接入 ORM 日志/schema 快照，参数化 SQL 用样例参数渲染后再 EXPLAIN；大 IN 列表按上限折叠后再评估。
- **豁免通道**：任何规则都可能有合法例外（数仓拉全表），豁免必须留痕（豁免工单+审批人+有效期），而不是规则里加白名单文件。

```python
# 基线:Python 3.10+;纯标准库实现轻量 SQL 审核规则引擎(工单门禁思路)
# 真实场景:sqlparse 解析 + 规则表;上线前自动审核 + 分级审批 + 豁免工单
from __future__ import annotations
import re
from dataclasses import dataclass

BLOCK, DBA, WARN, OK = "阻断", "DBA审批", "建议", "通过"


@dataclass
class Finding:
    level: str
    rule: str
    detail: str


def tokens(sql: str) -> list[str]:
    """轻量分词(真实实现用 sqlparse 的 AST,支持嵌套子查询)。"""
    return re.split(r"\s+|,", sql.strip().rstrip(";"))


def audit(sql: str) -> list[Finding]:
    toks = [t.upper() for t in tokens(sql)]
    head = toks[0]
    findings: list[Finding] = []
    if head in ("UPDATE", "DELETE") and "WHERE" not in toks:
        findings.append(Finding(BLOCK, "dml-no-where", f"{head} 无 WHERE:全表变更,不可逆大事故"))
    if head == "SELECT" and "*" in toks:
        findings.append(Finding(WARN, "select-star", "SELECT * 妨碍列裁剪与 TOAST 优化"))
    if head == "SELECT" and "LIMIT" not in toks:
        findings.append(Finding(WARN, "no-limit", "无 LIMIT 的自由查询建议人工确认"))
    if head == "ALTER" and any(k in toks for k in ("DROP", "MODIFY", "CHANGE")):
        findings.append(Finding(DBA, "ddl-lossy", "DDL 含 DROP/MODIFY:需 DBA 双人审批+备份确认"))
    if head == "SELECT" and "WHERE" not in toks:
        findings.append(Finding(BLOCK, "full-scan", "无 WHERE 的全表扫描查询拒绝进入生产"))
    return findings or [Finding(OK, "clean", "规则通过")]


def gate(sql: str) -> bool:
    """门禁:阻断/DBA 级不通过;豁免需另开工单。"""
    fs = audit(sql)
    level = max((f.level for f in fs), key=lambda x: [OK, WARN, DBA, BLOCK].index(x))
    print(f"[{level}] {sql[:52]}...")
    for f in fs:
        print(f"   - {f.rule}: {f.detail}")
    return level in (OK, WARN)


def demo() -> None:
    assert not gate("UPDATE users SET status = 1")                    # 无 WHERE 阻断
    assert not gate("DELETE FROM orders")                             # 无 WHERE 阻断
    assert not gate("ALTER TABLE big_table DROP COLUMN extra")        # DBA 审批
    assert not gate("SELECT * FROM user_profiles")                    # 全表扫描阻断
    assert gate("SELECT id, name FROM users WHERE id = 42 LIMIT 1")   # 通过
    assert gate("SELECT * FROM t WHERE id = 1")                       # 建议级放行(不误杀)
    print("门禁判定:阻断/审批级拒收,建议级放行不误杀 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：规则审核过了，为什么还要单独的"影响面预估"？
答：规则只能看语法形态，看不了数据规模——`DELETE ... WHERE status=0` 语法合规但可能命中 8000 万行。影响面预估用 EXPLAIN 预估行数 + 备份策略联动（超过阈值的变更强制先备份/分批），这是静态规则给不了的安全网。

**追问二**：审核平台怎么与 CI/发布流程衔接？
答：工单状态机（草稿→审核→批准→执行→归档）与发布流水线绑定：发布包含 SQL 变更时必须引用"已批准工单号"，执行器按窗口（低峰）与熔断（执行超时/受影响行数超限自动终止回滚）落地，事后把实际影响行数回写工单形成审计闭环。

## 背诵要点
- 门禁四级：阻断（DML 无 WHERE、无 WHERE 全表查询）/ DBA 审批（有损 DDL）/ 建议（SELECT *、无 LIMIT）/ 通过；豁免走留痕工单。
- 静态规则 + EXPLAIN 影响面预估双层：规则管语法，预估管规模（行数/锁范围/备份联动）。
- 审核对象是语句模板+样例参数（接 ORM 日志防手抄绕过）；执行器带窗口与熔断，影响行数回写审计。

## 复盘追问
- 有人用 `WHERE 1=1` 绕过"无 WHERE"规则做了全表 UPDATE，规则该怎么补？（提示：规则要升级为语义级——WHERE 条件必须可走索引/有限定行数预估，纯常量条件按无 WHERE 处理）
- 审核平台误杀率高导致大家走豁免通道，怎么治理？（提示：统计各规则的拦截/豁免/事后事故率，把长期高豁免的规则降级为建议，把豁免后出事故的规则升级并追责流程）
