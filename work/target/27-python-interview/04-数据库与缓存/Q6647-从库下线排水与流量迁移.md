### Q6647 · 从库下线排水与流量迁移

难度：P6 | 标签：读写分离、排水、容量规划、变更工程

**问**：要下线一台从库换新实例。直接改配置重启应用还是"先排水再摘除"？计划内摘除一个读节点的标准动作清单是什么？排水期间读延迟上升怎么办？

**答**：
- **结论**：标准动作是"排水优先"：① 该从库在路由层标记 draining——不再接新连接，存量已借出的连接自然归还（排水期 = 最长单次请求持连接时间 × 余量）；② 排水期间其读流量自动摊到其他从库，要先确认其余从库有余量（容量账：摘掉 1/3 读容量后剩余节点延迟是否可接受）；③ 水位归零后从路由摘除、停止复制、下线。直接改配置重启会造成该节点上的请求硬断——正在跑的长查询被杀，用户收到 500。
- **取舍**：排水时长与"摘除果断"的取舍：排水等太久（长查询拖 30 分钟）影响变更窗口；可以设排水超时（如 5 分钟后主动断开剩余连接并重试请求）。容量侧取舍：高峰期摘节点会让剩余从库延迟上升，宁可低峰执行或提前扩容——摘除的容量账要先算后做。
- **实战**：清单化：变更平台把"drain 标记 → 水位监控 → 容量确认 → 摘除 → 下线"做成带卡点的流水线，每步可回退。演练：从库排水逻辑每季度随故障演练跑一次（模拟节点失联时的路由收敛时间）。监控排水期其余从库的 lag——摘除引发的连锁延迟是最常见的次生事故。

```python
import time

class ReadPool:
    def __init__(self):
        self.nodes = {"r1": {"state": "active", "checked_out": 0},
                      "r2": {"state": "active", "checked_out": 0}}
    def acquire(self):
        actives = [n for n, s in self.nodes.items()
                   if s["state"] == "active"]
        return min(actives, key=lambda n: self.nodes[n]["checked_out"])
    def drain(self, node, timeout_s=2.0):
        self.nodes[node]["state"] = "draining"      # 不再接新连接
        t0 = time.monotonic()
        while self.nodes[node]["checked_out"] > 0:  # 等存量连接归还
            time.sleep(0.1)
            if time.monotonic() - t0 > timeout_s:   # 排水超时：果断断开
                self.nodes[node]["checked_out"] = 0
                return "drained(force)"
        return "drained(clean)"
    def release(self, node):
        self.nodes[node]["checked_out"] -= 1

pool = ReadPool()
node = pool.acquire(); pool.nodes[node]["checked_out"] += 1
print("借出节点:", node, "状态:", pool.nodes[node]["state"])
pool.release(node)
print(pool.drain(node), pool.nodes[node])
print("新请求路由:", pool.acquire(), "(draining 节点不再接新连接)")
print("要点：排水=拒绝新请求+等存量归还+超时兜底；摘除前先算剩余节点容量")

```
