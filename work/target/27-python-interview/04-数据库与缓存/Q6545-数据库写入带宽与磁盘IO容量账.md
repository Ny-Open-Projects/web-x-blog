### Q6545 · 写入型业务上线前的磁盘 IO 容量账：WAL/binlog 每天写多少 GB？

> 难度:★★★★ | 标签:容量规划, WAL, 磁盘 IO

**问**：订单系统峰值 8000 TPS、平均每行变更 200 字节、两个从库。上 PostgreSQL/MySQL 之前，磁盘 IO 容量账怎么算？为什么"数据文件 200GB 就配 200GB 磁盘"一定出事故？fsync 与组提交在账里占什么位置？

**答**：结论：写入型业务的磁盘账要算四本——**WAL/binlog 流量账**（每天 GB 数，决定磁盘吞吐选型）、**保留期账**（binlog/归档留存几天决定磁盘容量）、**fsync IOPS 账**（每次提交至少一次刷盘，决定云盘 IOPS 规格）、**峰值放大账**（索引放大、双副本同步）。典型账目：8000 TPS × 200B ≈ 1.6MB/s 逻辑写入，加上索引/undo/复制放大 ×3，峰值 WAL 流量约 5MB/s，一天全量写入约 400GB——磁盘必须按顺序写吞吐与 IOPS 双指标采购，而不是按数据量采购。

机理与实战：
- **WAL 流量 ≈ 逻辑变更 × 放大系数**：放大来自索引页写、full_page_write/页级写、undo（MySQL）、主从各一份落盘。放大量随索引数、随机写比例上升，2-5 倍是经验区间，新业务上线前用真实流量压测校准。
- **fsync 是提交延迟地板**：每次 commit 至少一次 fsync（MySQL group_commit/PG commit_delay 可合并），云盘单次 fsync 1-3ms 意味着单连接理论上限仅几百 TPS——高 TPS 靠**组提交**（多事务合并一次 fsync），所以容量账要算"fsync 次数/秒"而不是只算 GB。
- **保留期账**：binlog 保留 3 天 × 每天 400GB = 1.2TB；加备份、归档、双倍临时空间（DDL/重建），磁盘容量通常是数据量的 3-5 倍起步。
- **验证手段**：上线前用 pgbench/pgio 或 fio 实测目标盘的 fsync 时延 P99 与顺序写吞吐；云盘"标称 IOPS"在小 IO + fsync 场景经常打折。

```python
# 基线:Python 3.10+;纯标准库,写入型业务的磁盘 IO 容量估算器
from __future__ import annotations
from dataclasses import dataclass


@dataclass
class WriteProfile:
    peak_tps: int          # 峰值 TPS
    row_bytes: float       # 平均每行变更字节
    indexes: int           # 涉及的二级索引数(放大)
    replicas: int          # 从库数(各留一份 binlog)
    binlog_keep_days: int  # binlog 保留天数


def io_budget(p: WriteProfile, group_commit: int = 20) -> dict:
    peak = p.peak_tps * p.row_bytes / 1e6                     # 逻辑 MB/s
    amplify = 1 + 0.6 * p.indexes + 0.5                        # 索引+页级/undo 放大
    wal_peak = peak * amplify                                  # 主库 WAL 峰值 MB/s
    daily_gb = wal_peak * 86400 / 1024                         # 每天 GB
    keep_gb = daily_gb * (1 + p.replicas) * p.binlog_keep_days  # 主+从各留一份
    fsync_per_s = p.peak_tps / group_commit                    # 组提交合并后的 fsync 次数
    return {
        "逻辑写入峰值MB/s": round(peak, 2),
        "放大系数": round(amplify, 2),
        "WAL峰值MB/s": round(wal_peak, 2),
        "每天WAL GB": round(daily_gb, 1),
        "binlog保留占用GB(主+从)": round(keep_gb, 1),
        "fsync次数/秒": round(fsync_per_s, 1),
    }


def demo() -> None:
    p = WriteProfile(peak_tps=8000, row_bytes=200, indexes=2, replicas=2, binlog_keep_days=3)
    r = io_budget(p)
    for k, v in r.items():
        print(f"  {k}: {v}")
    assert r["fsync次数/秒"] == 400  # 8000/20,组提交把 fsync 从 8000 压到 400
    assert r["每天WAL GB"] > 300    # 远超"按数据量"直觉
    # 不组提交的对比:fsync 次数=TPS,云盘 1ms/fsync 即打满
    r_nogc = io_budget(p, group_commit=1)
    assert r_nogc["fsync次数/秒"] == 8000
    print("磁盘 IO 容量账:吞吐/保留/fsync 三本账,组提交是 TPS 地板 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：为什么高 TPS 系统普遍把 `synchronous_commit` 或组提交参数当容量杠杆调？
答：每次 commit 一次 fsync 意味着 TPS 上限 ≈ 盘的 fsync IOPS，8000 TPS 就需要 8000 fsync/s——普通云盘根本给不了。组提交把 N 个事务合并成 1 次 fsync，用毫秒级延迟换数量级吞吐；PG 的 `synchronous_commit=off` 更激进，最多丢最近几百毫秒已确认事务，适合可容忍丢失的日志类写入。这是"延迟换容量"的典型取舍。

**追问二**：full_page_write（FPW）为什么让 WAL 流量翻倍，怎么压？
答：检查点后每个数据页首次修改时要把整页（PG 8KB/MySQL 16KB）写进 WAL，防止部分页写坏，页级写入远大于行级变更量。压缩手段：缩短 checkpoint 间隔（减少首改页数量）、`wal_compression`/页压缩开启。容量账里 FPW 就是放大系数里那个 0.5-1.5 的来源，压测校准必不可少。

## 背诵要点
- 磁盘账四本：WAL 流量（逻辑×2-5 放大）、binlog 保留期、fsync IOPS、峰值/复制放大；磁盘按吞吐+IOPS 采购，不按数据量。
- 单事务一次 fsync = TPS 地板 ≈ 盘的 fsync IOPS；高 TPS 靠组提交（8000 TPS/20 = 400 fsync/s），极端可 synchronous_commit=off 换丢失窗口。
- 磁盘容量按数据量 3-5 倍起步：binlog 主从各一份 ×保留天数 + DDL 临时空间；上线前 fio/pgbench 实测 fsync P99。

## 复盘追问
- 大促前压测发现 TPS 卡在 2000 上不去，磁盘吞吐还有富余，瓶颈可能在哪？（提示：fsync IOPS 没富余或 group_commit 未生效；看 pg_stat_bgwriter/innodb 日志等待，把组提交窗口调大或升级云盘 IOPS 规格）
- 复制从库拉 binlog 的带宽要单独算账吗？（提示：要——跨机房复制会把 WAL 流量原样变成机房间出口流量，既要算带宽费也要算追平延迟；同机房直连 vs 异地同步的成本差一个数量级）
