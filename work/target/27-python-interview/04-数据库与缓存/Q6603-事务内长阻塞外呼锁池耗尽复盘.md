### Q6603 · 事务内长阻塞外呼导致行锁持有与连接池耗尽事故复盘

难度：P7 ｜ 标签：事务边界 / 连接池 / 事故复盘

**问**：一次支付回调依赖的外部网关变慢（平均 RT 从 200ms 涨到 8s），紧接着数据库大量行锁等待、应用连接池全满，整站下单失败。为什么外部接口变慢会击穿数据库？事务边界应该怎么设计？

**答**：
- **结论**：根因是把外部 HTTP 调用写进了事务里：`BEGIN → UPDATE 库存 → requests.post(外部网关) → COMMIT`。外呼变慢后每个事务从 200ms 拉长到 8s，行锁持有时间同步放大，同一条商品行的后续事务排队；连接池连接被长事务占住不还，池耗尽后新请求连 `BEGIN` 都拿不到连接，故障从"网关慢"放大成"全站下单失败"。这是一类典型的**事务内含非数据库副作用**反模式。
- **取舍**：修复选项：① 事务瘦身——事务里只做"扣减+写事件记录"，外呼挪到事务外/异步（事务发件箱模式），一致性用补偿或对账保证；② 若必须同步，外呼放在读连接、事务外，拿结果后再开短事务写库；③ 兜底——给外呼设严格超时（如 1s）+ 熔断，且给事务设 `innodb_lock_wait_timeout` 上限，让失败快速可见。注意：只加超时是止血，不缩事务边界的话下次换个依赖还会复发。
- **实战**：事故剧本：① 从 `innodb_trx` 看到事务时长分布从 0.2s 变 8s，确认锁等待链头是商品行；② 应用侧 kill 慢外呼连接、熔断该依赖，写停部分 SKU 保住其他流量；③ 重构为事务发件箱：短事务落"扣减+待发送事件"，后台 worker 外呼后回调更新状态；④ 复盘项：代码扫描门禁——事务作用域内禁止出现 HTTP/重任务调用（AST/装饰器检查），连接池监控区分"占用中的事务时长"。

```python
# 事务边界重构：短事务 + 发件箱外呼（标准库模拟核心流程）
# 基线：Python 3.9+；真实实现 SQLAlchemy 2.0 + httpx（超时 1s）

import time


class FakeSession:
    """模拟连接池会话：占住即计数"""
    pool_size, in_use = 20, 0

    def __init__(self) -> None:
        self.in_tx = False
        FakeSession.in_use += 1
        self._dirty = []

    def begin(self) -> None:
        assert not self.in_tx, "同一会话不可嵌套事务"
        self.in_tx = True

    def execute(self, op: str) -> None:
        assert self.in_tx, "事务外禁止写"
        self._dirty.append(op)

    def commit(self) -> None:
        self.in_tx = False
        self._dirty.clear()
        FakeSession.in_use -= 1

    def rollback(self) -> None:
        self.in_tx = False
        self._dirty.clear()
        FakeSession.in_use -= 1


def place_order_good(gateway_ok: bool) -> None:
    """正确姿势：事务只含 DB 操作，外呼在事务外（发件箱模式）"""
    s = FakeSession()
    s.begin()
    s.execute("UPDATE stock SET n=n-1")
    s.execute("INSERT INTO outbox(event='notify_gateway', status='PENDING')")
    s.commit()          # 短事务立即归还连接
    # 外呼在事务外失败也无损：发件箱里的事件由后台 worker 重试
    if not gateway_ok:
        print("外呼失败，事件留在发件箱待重试（事务已提交，无锁持有）")


def main() -> None:
    assert FakeSession.in_use == 0
    t0 = time.perf_counter()
    place_order_good(gateway_ok=False)   # 即使外挂挂了，事务仍瞬间结束
    cost = time.perf_counter() - t0
    assert FakeSession.in_use == 0, "事务提交后必须归还连接"
    assert cost < 0.01, "事务时长不应被外呼放大"
    print(f"OK: 短事务 {cost*1000:.2f}ms，连接已归还，外呼异步补偿")


if __name__ == "__main__":
    main()
```

**追问 1**：连接池参数上怎么缓解这类事故？（max_overflow / timeout）
→ 一句话提示：`pool_timeout` 设短让请求快速失败而非排队堆积、`max_overflow` 是应急缓冲不是常态容量、按"事务平均时长 × RPS"估算池大小；但池参数是止血，事务瘦身才是根治。

**追问 2**：事务发件箱模式引入了什么新问题？
→ 一句话提示：事件至少一次投递 → 下游要幂等；发件箱表本身需要清理与索引治理；"事件投递成功"与"业务真正生效"仍需下游回调或对账确认，复杂度从锁转移到异步链路。

## 背诵要点
- 反模式识别：事务内出现 HTTP/RPC/重计算 → 行锁持有时间被外呼 RT 放大，连接池随之耗尽，故障跨依赖放大。
- 修复顺序：先熔断+超时止血，再事务瘦身（发件箱/异步化）根治；门禁扫描"事务作用域内禁止非 DB 副作用"。
- 池参数只缓解不根治：pool_timeout 快速失败、max_overflow 应急、容量按"事务时长×RPS"估算。

## 复盘追问
- 为什么读操作也不该和长外呼共用一个事务连接？提示：PG 下长事务阻止 vacuum 清理死元组（膨胀），MySQL 下拉长 read view，即使不写行也是慢性毒药。
- 怎么在 CI 里自动发现"事务内外呼"？提示：装饰器/上下文管理器标记事务作用域，静态检查（AST/grep）其中是否 import 或调用 requests/httpx；或运行期用 SQLAlchemy 事件钩子检测事务期间创建的外部连接。
