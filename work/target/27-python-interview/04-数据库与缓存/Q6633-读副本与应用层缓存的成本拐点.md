### Q6633 · 读副本扩容与应用层缓存加机器的成本拐点账

难度：P6 ｜ 标签：成本工程 / 容量规划 / 架构取舍

**问**：读流量涨了 3 倍，方案 A 是给数据库加读副本，方案 B 是给应用加一层 Redis 缓存。两边都要花钱：副本是"每份读都付费"，缓存是"固定成本换命中率"。怎么算这笔账？拐点在哪个命中率？

**答**：
- **结论**：把两条成本线写成命中率的函数再比较。副本线：`成本_副本 = 单副本价 × ceil(读QPS_缓存外 / 单副本承载)`——线性于**未命中流量**；缓存线：`成本_缓存 = 固定实例价 + 回源DB成本`，其中回源 DB 又可能要 1 个副本兜底。关键洞察：缓存是**阶梯+固定**成本、副本是**线性**成本，所以低命中率时副本便宜、高命中率时缓存便宜，拐点可以用"缓存成本 = 副本成本"解出来。实际决策还要加三项修正：① 缓存引入的一致性风险与失效逻辑的**工程成本**（人日）；② 副本复制延迟的业务容忍度（读己之写？）；③ 缓存命中率本身有爬坡期（Q2773），冷启动期回源洪峰会反噬 DB——所以缓存方案的 DB 侧仍要保底副本。经验区间：读占比 > 90%、热点集中（幂律）、命中率可稳定在 85%+ 时，缓存方案通常赢；长尾均匀、强一致读多时，副本更稳。
- **取舍**：这不是二选一而是次序问题——先确认读 QPS 是否真的需要扩（慢查询治理、索引、连接池账先做，Q6540/Q6607），再谈加机器；上了缓存也不该把副本全撤（回源兜底），所以账里要算"缓存+1 小副本"的组合线。
- **实战**：① 用真实访问日志算幂律集中度（top 1% key 占读比例），决定命中率上限；② 拐点计算代入**包年折扣价**与缓存实例的真实规格（内存账 Q1014），别用官网标价；③ 上缓存后把"命中率跌破阈值"做成成本告警——命中率掉了 10 个点等于副本账重新翻盘。

```python
# 读副本 vs 缓存的成本拐点模型
# 基线: Python 3.9+ 标准库 (价格单位: 元/月, 数值为演示口径)
import math


def replica_cost(read_qps: int, per_replica_qps: int,
                 replica_price: int, base_db: int) -> int:
    n = max(1, math.ceil(read_qps / per_replica_qps))
    return base_db + n * replica_price


def cache_cost(read_qps: int, db_per_replica_qps: int,
               hit_ratio: float, cache_price: int,
               base_db: int, replica_price: int) -> int:
    miss_qps = read_qps * (1 - hit_ratio)
    # 回源 DB 仍保底 1 副本兜底冷启动/击穿
    n = max(1, math.ceil(miss_qps / db_per_replica_qps))
    return base_db + cache_price + n * replica_price


def main() -> None:
    read_qps, per_rep = 50_000, 15_000
    base_db, rep_price, cache_price = 3_000, 2_500, 1_800
    full_replica = replica_cost(read_qps, per_rep, rep_price, base_db)
    assert full_replica == 3_000 + 4 * 2_500          # 13000
    pts = {h: cache_cost(read_qps, per_rep, h, cache_price,
                         base_db, rep_price)
           for h in (0.0, 0.5, 0.8, 0.95)}
    assert pts[0.0] > full_replica                    # 低命中率: 缓存更贵
    assert pts[0.95] < full_replica                   # 高命中率: 缓存赢
    # 拐点: 缓存成本线 <= 全副本成本线的最低命中率
    need = lambda h: math.ceil(read_qps * (1 - h) / per_rep)
    breakeven = next(h for h in [x / 100 for x in range(100)]
                     if cache_cost(read_qps, per_rep, h, cache_price,
                                   base_db, rep_price) <= full_replica)
    assert need(breakeven) <= 4                       # 回源副本数未超全量
    assert cache_cost(read_qps, per_rep, breakeven, cache_price,
                      base_db, rep_price) <= full_replica
    print(f"全副本 {full_replica} 元; 命中率0.5={pts[0.5]} "
          f"0.8={pts[0.8]} 0.95={pts[0.95]}; 拐点≈{breakeven:.0%}")
    print("OK: 缓存=固定成本换命中率, 副本=线性成本; 拐点由真实价格与幂律定")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么缓存方案里仍要保留至少一个副本？
→ 一句话提示：缓存失效/击穿/冷启动爬坡期回源洪峰必须有人兜底（配合 Q1017 singleflight 与预热），撤光副本等于把可用性押在命中率上。

**追问 2**：幂律集中度怎么影响这个账？
→ 一句话提示：top 1% key 占 80% 读时命中率上限高、缓存划算；均匀长尾命中率天花板低（可能只有 40-60%），永远够不到拐点，选副本。

## 背诵要点
- 副本成本线性于未命中流量，缓存成本 = 固定实例价 + 保底副本；拐点用两函数相等解出，通常在命中率 70-90% 区间（依真实价格）。
- 决策前置：先治理慢查/索引/连接池，再算加机器；缓存方案必保 1 副本兜底击穿与冷启动。
- 命中率跌破阈值要做成成本告警：掉 10 个点 = 副本账翻盘。

## 复盘追问
- 用官网标价和用包年折扣价算出的拐点可能不同，采购上怎么处理？提示：按实际采购价重算拐点，缓存实例规格弹性小（内存定死）、副本可升配，价格结构影响结论。
- 缓存上了之后命中率爬坡期（Q2773）怎么防止回源打垮 DB？提示：预热 + singleflight 合并回源 + 保底副本限流，冷启动期临时限读。
