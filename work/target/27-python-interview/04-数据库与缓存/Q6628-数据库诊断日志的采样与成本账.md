### Q6628 · 数据库诊断日志（慢查询日志/auto_explain）的采样率与成本账

难度：P6 ｜ 标签：成本工程 / 可观测 / PostgreSQL

**问**：为了抓慢查询，DBA 把 `log_min_duration_statement` 调到 200ms、开了 `auto_explain`，高峰期数据库日志每天产出几十 GB，日志采集和存储费用跟着涨，而且回写日志本身也影响性能。怎么设计诊断日志的采样策略，让"抓到问题"和"成本可控"同时成立？

**答**：
- **结论**：诊断日志的总量 = **QPS × 采样率 × 单条体积 × 时长**，慢查询风暴时这条公式会爆：一条被锁拖住的 SQL 30s 超时、重试放大 ×N，每个实例都写一条带 explain 的 KB 级日志，采集管道先被冲垮。控制变量四个：① **采样率**——auto_explain 的 `sample_rate`（如 0.01 只抽 1% 语句），慢查询日志靠阈值天然过滤，但阈值太低（200ms）在故障期全是候选，要配合 `log_min_duration_sample` 采样版参数；② **体积**——explain 的 `verbose/analyze` 别全开（analyze 真执行一遍），关掉解释树里的冗余字段；③ **保留分层**——热日志（7 天，可检索）转冷归档（30-90 天，对象存储），检索成本降一个数量级；④ **触发式采集**——平时低采样，`pg_stat_activity` 里长事务/锁等待超阈值时自动把对应会话临时提采样，把"常态高采样"变成"事件驱动高采样"。回写性能账：日志写入是同步 IO（stderr），高峰开 verbose explain 可见延迟抖动，采集走 sidecar/filebeat 异步缓解但不消除，这就是为什么宁可采样也别全量。
- **取舍**：`pg_stat_statements`（聚合视图）与逐条日志怎么分工？定位"哪些 SQL 类慢"用聚合视图——零日志成本、自带指标；定位"具体哪一次为什么慢"才开逐条+explain。把逐条日志当常态监控是成本失控的开始：常态监控走聚合，日志只做取证。
- **实战**：① 采样参数变更像代码一样走评审与灰度（Q6558 参数灰度同源）；② 按 QPS 估算日志量再设阈值：`峰值QPS × 单条KB × 采样率` 要小于采集管道容量；③ 日志体积指标进监控（logs 产出 GB/h），异常膨胀自动降采样；④ 取证场景用"复现脚本 + 临时高采样窗口"，而不是长期高采样。

```python
# 诊断日志成本账: 总量 = QPS x 采样率 x 单条体积; 事件驱动 > 常态高采样
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class LogBudget:
    peak_qps: float
    sample_rate: float
    entry_kb: float
    pipeline_gb_per_hour: float   # 采集管道容量

    def gb_per_hour(self) -> float:
        return self.peak_qps * self.sample_rate * self.entry_kb * 3600 / 1e6

    def fits(self) -> bool:
        return self.gb_per_hour() <= self.pipeline_gb_per_hour


def storm_gb_per_hour(qps: float, entry_kb: float = 8.0) -> float:
    """风暴场景: 全量命中(采样率=1) + 重试放大 x3。"""
    return qps * 3 * entry_kb * 3600 / 1e6


def main() -> None:
    normal = LogBudget(peak_qps=5000, sample_rate=0.05, entry_kb=4.0,
                       pipeline_gb_per_hour=15)
    assert abs(normal.gb_per_hour() - 3.6) < 1e-6   # 5000*0.05*4KB = 1MB/s
    assert normal.fits()
    tuned = LogBudget(5000, 0.01, 2.0, 15)
    assert tuned.gb_per_hour() < 1 and tuned.fits()
    assert storm_gb_per_hour(5000) > normal.pipeline_gb_per_hour * 20
    print(f"常态5%: {normal.gb_per_hour():.1f}GB/h 可控 -> 1%+瘦身: "
          f"{tuned.gb_per_hour():.2f}GB/h")
    print(f"OK: 风暴全量+放大={storm_gb_per_hour(5000):.0f}GB/h 爆管, "
          f"取证改事件驱动高采样窗口")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 auto_explain 的 `analyze` 参数在生产要慎开？
→ 一句话提示：analyze 会真实执行被采样的语句拿行数与耗时，等于对慢 SQL 又跑一遍（可能再翻倍耗时），只排障窗口开启；常态用 explain（估计划）+pg_stat_statements 实测耗时组合就够。

**追问 2**：聚合视图（pg_stat_statements）能完全替代逐条日志吗？
→ 一句话提示：不能——聚合没有参数值、没有单次执行上下文（锁等待、当时的计划），它回答"哪类 SQL 慢"，逐条日志回答"这一次为什么慢"，取证需要后者，常态监控用前者。

## 背诵要点
- 诊断日志总量 = QPS × 采样率 × 单条体积 × 时长；风暴期重试放大 ×N 是爆管主因，常态 2% 采样也可能超管道容量。
- 分工：pg_stat_statements 聚合做常态监控（零日志成本），逐条+explain 只做取证；analyze 参数生产慎开（真执行）。
- 策略：常态低采样 + 事件驱动高采样窗口 + 热/冷分层保留，日志产出 GB/h 进监控并自动降采样。

## 复盘追问
- 采样参数灰度为什么必须像 DDL 一样走评审？提示：log_min_duration 这类参数直接改变日志流量形态，一次误配置能让采集管道当天爆掉（Q6558 参数灰度同源）。
- "事件驱动高采样"的触发器怎么设计才不会漏掉真事故？提示：以 pg_stat_activity 的锁等待/长事务阈值和 pg_stat_statements 耗时回归为触发源——聚合视图先发现异常，再开高采样取证，形成两级漏斗。
