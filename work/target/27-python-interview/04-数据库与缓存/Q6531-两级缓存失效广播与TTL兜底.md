### Q6531 · 两级缓存失效广播：进程内 LRU + Redis 的一致性怎么守？

> 难度:★★★★ | 标签:多级缓存, 失效广播, pub/sub

**问**：应用是多实例部署，每台进程内有一份 LRU 本地缓存，前面还有一层 Redis。某台实例改了数据，其他实例的本地缓存怎么失效？广播消息丢了怎么办？本地缓存的 TTL 该怎么定？

**答**：结论：两级缓存的一致性靠"**失效广播 + 短 TTL 兜底**"两条腿，天然是最终一致，不要追求强一致。写路径：更新 DB → 删 Redis → `PUBLISH` 失效消息（带版本号）；各实例订阅后按版本比较 evict 本地 key。读路径：本地 LRU → Redis → 回源（回源要 singleflight 防击穿）。

机理与实战：
- **TTL 是最后防线**：Redis pub/sub 是 fire-and-forget，订阅者掉线期间消息全丢、无重放。丢失窗口 = 掉线时长 + 本地 TTL。所以本地 TTL 必须显著小于业务可容忍的旧数据窗口（如业务容忍 1 分钟，TTL 取 5-10 秒），这是兜底而不是装饰。
- **版本闸防乱序**：失效消息带数据版本号，本地缓存条目记录版本，`旧版本消息 <= 本地版本` 时拒绝 evict——防止迟到的旧广播把刚回源的新值删掉引发回源风暴。
- **广播成本是 O(N)**：N 台实例每人都要处理一次失效；key 粒度要小（按对象而非按列表），超大集合改用"版本戳+整体失效"或实例分组订阅。
- **监控口径**：对比 DB 写入次数、广播发布数、各实例 evict 数——三者偏差放大说明有实例长期漏收（订阅断连），TTL 兜底在悄悄扛旧数据。
- **数据分级**：本地缓存只放"读多写少、可容忍秒级旧"的数据；权限/定价类数据宁可不开本地缓存（失效窗口内的越权/错价风险大于收益）。

```python
# 基线:Python 3.10+(用到 X | None 语法);纯标准库模拟两级缓存与失效广播
# 真实场景:进程内 LRU(每实例一份) + Redis 缓存层 + Redis pub/sub 失效广播
from __future__ import annotations


class Clock:
    """可注入时钟,让 TTL 演进确定性可测。"""

    def __init__(self, now: float = 0.0) -> None:
        self.now = now

    def __call__(self) -> float:
        return self.now

    def advance(self, seconds: float) -> None:
        self.now += seconds


class LocalLRU:
    """进程内 LRU:条目带版本号与 TTL。"""

    def __init__(self, name: str, capacity: int = 100, ttl: float = 5.0,
                 clock: Clock | None = None) -> None:
        self.name = name
        self.cap, self.ttl = capacity, ttl
        self.clock = clock or Clock()
        self.data: dict[str, tuple[float, int, str]] = {}  # key -> (expire_ts, version, value)
        self.hits = self.evicted_by_broadcast = 0

    def get(self, key: str) -> str | None:
        item = self.data.get(key)
        if item is None:
            return None
        expire_ts, _version, value = item
        if self.clock() > expire_ts:          # TTL 兜底:广播丢失时最多旧 ttl 秒
            self.data.pop(key, None)
            return None
        self.data[key] = self.data.pop(key)   # 触碰即移到最新端(有序 dict 的 LRU 技法)
        self.hits += 1
        return value

    def put(self, key: str, value: str, version: int) -> None:
        self.data.pop(key, None)
        if len(self.data) >= self.cap:
            self.data.pop(next(iter(self.data)))          # 淘汰最旧端
        self.data[key] = (self.clock() + self.ttl, version, value)

    def evict_if_older(self, key: str, msg_version: int) -> bool:
        """带版本比较的失效:旧广播(乱序/重放)不会误删新缓存。"""
        item = self.data.get(key)
        if item is not None and item[1] <= msg_version:
            self.data.pop(key, None)
            self.evicted_by_broadcast += 1
            return True
        return False


class Broker:
    """失效广播总线:真实场景 = Redis pub/sub(送而不保达,每实例一个订阅线程)。"""

    def __init__(self) -> None:
        self.subs: list[LocalLRU] = []
        self.offline: set[int] = set()        # 模拟订阅者掉线(消息全丢)
        self.published = 0

    def publish(self, key: str, version: int) -> None:
        self.published += 1
        for i, cache in enumerate(self.subs):
            if i in self.offline:
                continue                      # pub/sub 无重放:掉线实例收不到
            cache.evict_if_older(key, version)


def demo() -> None:
    clock = Clock()
    caches = [LocalLRU(f"实例{i}", ttl=5.0, clock=clock) for i in range(3)]
    broker = Broker()
    broker.subs.extend(caches)

    for c in caches:
        c.put("item:42", "价格=100", version=1)
    assert all(c.get("item:42") == "价格=100" for c in caches)
    print("三实例本地缓存命中 ✅")

    # 写者(实例0)更新后广播:DB 更新 -> 删 Redis -> publish(key, 新版本)
    caches[0].put("item:42", "价格=101", version=2)
    broker.publish("item:42", version=2)
    assert all(c.get("item:42") is None for c in caches)
    print("广播后三实例本地缓存全部失效 ✅")

    # 乱序旧广播防御:实例1 重新缓存 v2,再收到迟到的 v1 广播不应误删
    caches[1].put("item:42", "价格=101", version=2)
    assert caches[1].evict_if_older("item:42", msg_version=1) is False
    assert caches[1].get("item:42") == "价格=101"
    print("迟到旧版本广播被版本闸拦下,不误删新值 ✅")

    # 广播丢失兜底:实例2 掉线漏收,靠 TTL 兜底淘汰旧值
    caches[2].put("item:42", "价格=100", version=1)   # 模拟漏收后仍持旧值
    clock.advance(6.0)                                # 快进 6s > TTL 5s
    assert caches[2].get("item:42") is None
    print("漏收实例的旧值被 TTL 兜底淘汰 ✅ -> 本地 TTL 必须 < 可容忍旧窗口")


if __name__ == "__main__":
    demo()
```

**追问一**：为什么广播"失效"而不是广播"新值"？
答：多写者并发下推新值有乱序风险——实例 A 推 v2、实例 B 后推 v1，收到 v1 的实例会把旧值当新值缓存，且再也等不来修正信号；失效+回源永远回到权威数据源，广播带版本号只是把乱序伤害限制在"多回一次源"。只有"单写者、有全局版本、值很小"的场景才考虑推值。

**追问二**：pub/sub 换成 Redis Stream 做失效广播能得到什么、付出什么？
答：Stream 有持久化与消费组，实例掉线重连后可从 `LAST-ID` 补收积压失效消息，丢失窗口从"掉线全程"缩到"补收延迟"；代价是每实例要维护读位点、Stream 需 MAXLEN 控内存，且补收风暴（长时间掉线后成千上万条失效重放）要做合并去重——补收时按 key 去重后批量 evict，而不是逐条处理。

## 背诵要点
- 两级缓存一致性 = 失效广播（带版本号防乱序误删）+ 短 TTL 兜底（丢失窗口=掉线时长+TTL）。
- pub/sub 不保达不掉线补偿，要求更强换 Stream 消费组补收；广播成本 O(N)，key 粒度要小。
- 本地 TTL 必须 < 业务可容忍旧窗口（如容忍 1 分钟 → TTL 5-10 秒）；权限/定价类数据慎用本地缓存。

## 复盘追问

- 广播 key 设计成 `user:*` 通配失效会发生什么？（提示：O(N)×key 数的广播风暴 + 本地全量清空引发回源风暴，应退化为精确 key 或版本戳整体失效）
