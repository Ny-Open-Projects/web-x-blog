### Q6612 · 隐式类型转换导致索引失效的事故复盘

难度：P6 ｜ 标签：事故复盘 / 索引 / 类型转换

**问**：订单表 `order_no` 是 varchar 且有索引，上线一个新查询后该表 CPU 飙升，`EXPLAIN` 显示走了全表扫描，类型是 ALL。SQL 里传的参数来自 Python。根因是什么？为什么类型不匹配会拖垮整张表？如何从工程上杜绝？

**答**：
- **结论**：根因是**隐式类型转换**：SQL 里写 `WHERE order_no = 12345`（参数是 int，列是 varchar），MySQL 会把**列**转换成数字再做比较（字符串转数字这一侧是列而非常量），等价于 `CAST(order_no AS DOUBLE) = 12345`。对列套函数后，B+ 树索引无法按序定位，优化器只能全表扫描。事故链路：Python 侧 ORM/驱动参数绑定类型跟随 Python 对象——前端把订单号传成了数字（或代码里 `int(order_no)`"顺手"清洗了），驱动按 int 绑定，SQL 语义变化；小表无感，订单表几千万行后 CPU 打满。另一个高频形态：int 列与字符串常量比较（`id = '123'`）——这时常量被转换、列不动，索引不失效，所以团队容易产生"类型不匹配也没事"的错觉，直到遇到反向的 varchar 列 = 数字。
- **取舍**：应急与根治：① 应急：参数显式加引号/改绑定类型，让常量与列类型一致，`EXPLAIN` 确认回到 ref/range；② 根治三层：SQL 层——code review 门禁 `EXPLAIN` 附件；驱动层——SQLAlchemy 用 `String` 类型声明参数、避免裸 f-string 拼接数字；架构层——对"人输的、外部传的"编号类字段统一入口清洗（str 化 + 格式校验），不让 int 流进查询层；③ 监控：`pg_stat_statements` / MySQL 慢日志按"全表扫描次数"而非只按耗时告警，类型转换类慢查询在数据小的时候不会被耗时告警发现。
- **实战**：把检查自动化：CI 里对关键 SQL 跑 `EXPLAIN`（或 PG 的 `EXPLAIN (FORMAT JSON)` 提取 Node Type），出现 Seq Scan/ALL 且表行数超阈值即 fail；Python 侧用 `str` 值对象类型标注订单号（`OrderId = NewType("OrderId", str)`），mypy 能在传 int 时报错；事故后补一条守门规则：所有 `= %s` 参数在 DAO 层声明类型并校验。

```python
# 隐式类型转换导致索引失效的机理模拟：对列套函数 -> 有序结构无法二分
# 基线：Python 3.9+ 标准库；真实验证用 EXPLAIN 看到varchar列=int常量时 type=ALL
import bisect
import time


class FakeIndex:
    """模拟 varchar 列上的 B+ 树索引：按键有序，支持二分定位。"""

    def __init__(self, rows: list[tuple[str, int]]):
        self.entries = sorted(rows)  # (order_no, row_id)，字符串序
        self.keys = [k for k, _ in self.entries]

    def lookup_str(self, val: str) -> int | None:
        i = bisect.bisect_left(self.keys, val)
        if i < len(self.keys) and self.keys[i] == val:
            return self.entries[i][1]
        return None  # 索引命中，O(log n)

    def lookup_with_cast(self, val: int) -> int | None:
        # CAST(col AS DOUBLE)=val 后有序性失效，只能全扫（模拟 O(n)）
        for order_no, rid in self.entries:
            if order_no.lstrip("0") and int(float(order_no)) == val:
                return rid
        return None


def main() -> None:
    n = 400_000
    rows = [(str(10_000_000 + i), i) for i in range(n)]
    idx = FakeIndex(rows)

    t0 = time.perf_counter()
    assert idx.lookup_str("10012345") is not None
    t1 = time.perf_counter()
    assert idx.lookup_with_cast(10012345) is not None
    t2 = time.perf_counter()

    indexed = t1 - t0
    full_scan = t2 - t1
    assert full_scan > indexed * 10, (indexed, full_scan)  # 差距应为数量级
    print(f"OK: str参数走索引 {indexed*1000:.2f}ms；int参数触发CAST全扫 {full_scan*1000:.2f}ms")
    print("  教训：列被CAST后B+树有序性失效，优化器只能选全表扫描")


if __name__ == "__main__":
    main()
```

**追问 1**：int 列与字符串常量比较为什么通常不失效？
→ 一句话提示：MySQL 的转换规则偏向把常量转成列的类型，`id='123'` 是常量被转换，列的索引仍可用——所以团队容易漏掉"varchar 列 = 数字"这个反向 case，事故往往在数据量放大后才暴露。

**追问 2**：除了索引失效，隐式转换还有什么隐患？
→ 一句话提示：比较语义变化（`'1e3'`、`'12abc'` 转 DOUBLE 的舍入与截断）、字符集混合比较导致 collation 报错或更差的执行计划，以及 PG 里直接报 `operator does not exist` 反而更快暴露——MySQL 的宽容让它更隐蔽。

## 背诵要点
- varchar 列 = int 常量时 MySQL 把**列** CAST 成数字，索引有序性失效走全表扫；int 列 = '123' 是常量转换，索引不失效——方向不同结果完全不同。
- 根治靠类型入口收口：`NewType` 值对象 + DAO 层参数类型声明 + CI 里 EXPLAIN 门禁（Seq Scan/ALL 超阈值即 fail）。
- 监控按"全表扫描次数"告警而非只按耗时：类型转换类慢查询在小表阶段不会被耗时告警发现。

## 复盘追问
- 为什么事故发生在上线新查询后而不是表变大时？提示：老查询参数一直是字符串，新功能从 JSON 里拿到的是数字（JSON number），同一张表只有新查询触发 CAST；表大小只决定爆炸烈度。
- ORM（SQLAlchemy）里怎么避免参数类型漂移？提示：`Column(String)` + 显式 `bindparam(type_=String)`，避免 `text()` 裸拼；类型不匹配时让驱动层报错而不是数据库隐式兜底。
