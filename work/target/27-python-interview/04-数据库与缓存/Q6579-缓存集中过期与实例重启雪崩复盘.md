### Q6579 · 缓存集中过期与实例重启雪崩事故复盘

难度：P6/P7 ｜ 标签：Redis / 缓存雪崩 / 事故复盘

**问**：Redis 主从切换后，数据库 QPS 瞬间涨了 8 倍直接过载。代码里 TTL 设得很均匀，为什么还会雪崩？

**答**：
- **结论**：TTL 均匀只防"时间性集中过期"，防不了"事件性同时失效"——故障切换、实例重启、集群 reshard 都会让全部 key 在同一瞬间从"命中"变"未命中"，这就是与过期雪崩并列的失效雪崩（cold start crash）。量化账：假设命中率 90%，QPS 1 万的回源只有 1 千；切换后 100% 回源是 1 万，DB 若容量只有 2 千就是 5 倍过载。所以容量规划必须按"缓存全失效"的最坏情形做 DB 容量预算，而不是按稳态命中率。
- **取舍**：防雪崩手段的取舍：① 启动预热（脚本慢速回填）最有效但恢复时间长；② 单飞/锁（same-key 只放一个请求回源）防击穿不防洪峰总量；③ DB 侧限流/降级 + 请求队列排队，是兜底不是预防；④ TTL 加随机抖动只对过期型雪崩有效。正确组合：预热（恢复期）+ 单飞（击穿）+ DB 容量按最坏值（底线）。
- **实战**：事故后改造：应用启动时注册"预热模式"（读请求先进队列，后台按热度梯度回填，热度用切换前的访问统计）；DB 前加信号量限流（Python 侧 `asyncio.Semaphore` + 超时快速失败），宁可部分 5xx 也不许 DB 被打死；演练化——每月主动做一次 failover 演练验证预热生效。

```python
# 雪崩量化 + 单飞预热模拟（纯标准库）
# 基线：Python 3.9+

import random
import threading


def db_qps_under_failover(total_qps: int, hit_ratio: float) -> int:
    return int(total_qps * (1 - hit_ratio))


class SingleFlight:
    """同 key 并发回源只放一个，其余等待结果"""

    def __init__(self):
        self.locks: dict[str, threading.Lock] = {}
        self._mux = threading.Lock()
        self.inflight: dict[str, object] = {}

    def load(self, key: str, db: dict, db_cost: int = 0) -> object:
        with self._mux:
            lk = self.locks.setdefault(key, threading.Lock())
        with lk:
            if key in self.inflight:
                return self.inflight[key]
            val = db.get(key)  # 模拟回源
            self.inflight[key] = val
            return val


def main() -> None:
    total, hit = 10_000, 0.9
    print(f"稳态回源={db_qps_under_failover(total, hit)}, 切换后={db_qps_under_failover(total, 0.0)}")
    assert db_qps_under_failover(total, 0.0) == 10_000

    sf = SingleFlight()
    db = {"hot": 42}
    results = [sf.load("hot", db) for _ in range(50)]
    assert all(r == 42 for r in results)

    # TTL 抖动：只对过期型雪崩有效
    base, jitter = 3600, 600
    random.seed(7)
    ttls = [base + random.randint(0, jitter) for _ in range(3)]
    print("TTL样本:", ttls)


if __name__ == "__main__":
    main()
```

**追问 1**：单飞在多实例部署下为什么不够？
→ 一句话提示：进程内锁只合并本实例请求，100 个实例仍可能有 100 个并发回源，跨实例合并要用 Redis SETNX/分布式锁（参考单飞卡），或网关层 request coalescing。

**追问 2**：预热时"按热度梯度回填"怎么排顺序？
→ 一句话提示：用切换前的访问计数（本地 LRU 统计或 Redis 键访问统计）排序，先回填 top 热点小集合（秒级救回大部分命中），再批量回填长尾，避免预热本身打挂 DB。

## 背诵要点
- 两类雪崩：时间性（TTL 集中，用抖动防）与事件性（切换/重启，用预热防），TTL 抖动防不了后者。
- 容量底线公式：DB 容量按命中率 0% 的最坏回源设计，而不是稳态命中率的回源。
- 组合拳：预热（热度梯度：先热点小集合）+ 单飞（击穿）+ DB 侧限流快速失败。

## 复盘追问
- 为什么"命中率监控"在这类事故中没用？提示：命中率跌到 0 是事故结果不是前兆，前兆是 failover 事件本身，要监控切换事件并自动进入预热模式。
- 演练 failover 时如何不真打挂 DB？提示：影子流量或预限流状态下演练，验证的是预热路径而非 DB 承受极限。
