### Q6750 · 分片排行榜取周榜：ZUNIONSTORE 的临时键把内存顶到 700MB

难度：P7 ｜ 标签：Redis、ZSet、分片、ZUNIONSTORE、内存峰值

基线：Python 3.12；用字典 + `heapq` 模拟 ZSet 分片、`ZUNIONSTORE` 的全量合并与 top-k 归并。

**问**：积分榜按天分片存 `rank:20261122`、`rank:20261123`…（ZSet，约 100 万成员/天）。周榜需求要用 `ZUNIONSTORE week:tmp 7 rank:20261122 ... rank:20261128` 再 `ZREVRANGE week:tmp 0 9`。上线后每到整点算周榜，Redis 内存瞬间涨 700MB、主线程卡顿 2~3 秒，`maxmemory` 逼近上限触发淘汰，把缓存里的热 key 淘汰了一片。除了加机器，还能怎么算？

**答**：
- **结论**：`ZUNIONSTORE` 是**先全量物化再排序**：它要新建一个包含所有并集成员的临时 ZSet（7 天 × 100 万去重后仍有几百万成员），每个成员约 100+ 字节（skiplist 节点 + SDS），峰值就是几百 MB；整个过程在 Redis 单线程里跑，O(N log N) 的合并会阻塞所有命令。算完还要 `DEL` 临时键，删除本身又是一次大 key 释放（异步删除才不阻塞）。
- **取舍**：① **写时聚合**：每次加分同时 `ZINCRBY rank:week 1 uid`（总榜），周榜读取 O(log N + k)，代价是写放大 2 倍、需要每周 `DEL` 重建；② **读时归并**：客户端并发 `ZREVRANGE` 取每个分片的前 K（K 取 100~200），在应用内做 k 路归并，内存 O(天数 × K)，但如果"每天都不在前 K、累计却很高"的用户会漏（见代码）；③ 用 Redis 7 的 `ZUNION`（不落盘、返回给客户端）代替 `ZUNIONSTORE`，省掉临时键但结果集仍在客户端内存；④ 大数据量用离线数仓算好周榜再写回一个小 ZSet，Redis 只做展示。
- **实战**：① 需要精确总榜就用方案 ①，并接受"写放大"；② 用读时归并必须在候选集上做**覆盖度校验**（对比一次精确结果，估算漏检率）；③ 临时键加短 TTL（`EXPIRE 60`）防止异常残留；④ 大 key 删除用 `UNLINK`；⑤ 监控 `INFO memory` 的 `used_memory_peak`，把"整点算榜"错峰到低峰期。

```python
"""ZUNIONSTORE 的全量物化 vs 写时聚合 vs 读时 k 路归并（含漏检）。"""
# 三天分片：u9 每天都不在前三，但累计最高
DAILY = {
    "20261122": {"u1": 100, "u2": 90, "u3": 80, "u9": 70},
    "20261123": {"u4": 95, "u5": 85, "u6": 75, "u9": 70},
    "20261124": {"u7": 99, "u8": 89, "u3": 79, "u9": 70},
}


def union_store(shards: dict[str, dict[str, int]], top: int) -> list[tuple[str, int]]:
    """等价 ZUNIONSTORE：先物化全部成员，再排序。"""
    tmp: dict[str, int] = {}
    for shard in shards.values():
        for uid, score in shard.items():
            tmp[uid] = tmp.get(uid, 0) + score
    peak = len(tmp)                       # 临时键的成员数 = 内存峰值的主要项
    ranked = sorted(tmp.items(), key=lambda kv: (-kv[1], kv[0]))
    print(f"  ZUNIONSTORE 临时键成员数={peak}，"
          f"按 100B/成员估算 {peak * 100 / 1024:.0f} KiB（真实规模放大 100 万倍）")
    return ranked[:top]


def merge_top_k(shards: dict[str, dict[str, int]], k: int, top: int):
    """每个分片只取前 k，客户端归并；内存 O(分片数 × k)。"""
    per_shard = [sorted(s.items(), key=lambda kv: (-kv[1], kv[0]))[:k]
                 for s in shards.values()]
    total: dict[str, int] = {}
    for rows in per_shard:
        for uid, score in rows:
            total[uid] = total.get(uid, 0) + score
    ranked = sorted(total.items(), key=lambda kv: (-kv[1], kv[0]))
    return ranked[:top], len(total)


def write_through(events: list[tuple[str, str, int]], top: int):
    """写时聚合：每次加分同时更新总榜。"""
    total: dict[str, int] = {}
    for _, uid, delta in events:
        total[uid] = total.get(uid, 0) + delta
    return sorted(total.items(), key=lambda kv: (-kv[1], kv[0]))[:top]


if __name__ == "__main__":
    print("精确结果（近似全量物化）:")
    exact = union_store(DAILY, 3)
    print("  top3 =", exact)

    print("\n读时归并 k=3（每片只取前 3）:")
    approx, candidates = merge_top_k(DAILY, k=3, top=3)
    print("  候选集大小 =", candidates, "| top3 =", approx)
    missed = [u for u, _ in exact if u not in dict(approx)]
    print("  漏掉的用户:", missed, "-> 每天都不在前 3，累计却是第二")

    print("\n读时归并 k=4（候选放宽）:")
    approx4, cand4 = merge_top_k(DAILY, k=4, top=3)
    print("  候选集大小 =", cand4, "| top3 =", approx4, "| 与精确一致:",
          approx4 == exact)

    events = [(d, u, s) for d, shard in DAILY.items() for u, s in shard.items()]
    print("\n写时聚合（ZINCRBY 总榜）:")
    print("  top3 =", write_through(events, 3), "| 读取 O(logN + k)，无临时键")

    # 容量账：7 天 × 100 万成员
    members = 7 * 1_000_000
    print(f"\n真实规模：{members:,} 成员 × 100B ≈ {members * 100 / 1024 / 1024:.0f} MiB 峰值")
    print("结论：精确总榜用写时聚合；读时归并只能近似，k 要按漏检率调，不能拍脑袋")
```

**追问一**：为什么 `ZUNIONSTORE` 的内存峰值比"结果集大小"还高？

→ 解析：它要同时存在**输入、临时结果、以及 skiplist 的结构开销**。ZSet 每个成员是"skiplist 节点（约 32~64B 的层指针数组）+ SDS 字符串 + dict 条目"，100 字节只是保守估计；合并过程中旧节点释放、新节点分配，`used_memory_peak` 会记录到瞬时最高点。再叠加 `maxmemory` 的淘汰逻辑，就可能出现"算榜把热数据挤掉"的连锁反应。所以评估这类命令要看 `MEMORY USAGE` + 峰值，不是只看 `ZCARD`。

**追问二**：Redis Cluster 下 `ZUNIONSTORE` 多键聚合会遇到什么问题？

→ 解析：`ZUNIONSTORE` 要求所有输入键在**同一个 slot**，否则直接报 `CROSSSLOT Keys in request don't hash to the same slot`。按天分片的 key（`rank:20261122` 等）几乎必然落在不同 slot。解法：① 用 hash tag 把同一业务的多天分片强制同槽（`rank:{weekly}:20261122`），但同槽意味着同节点，热点与容量都集中；② 客户端 `MGET`/`ZRANGE` 拉回本地归并（就是上面的读时归并）；③ 干脆把聚合放到数仓/离线任务，Redis 只存结果。分布式下"多键原子聚合"基本等于"单点"，要和分片的目标做取舍。
