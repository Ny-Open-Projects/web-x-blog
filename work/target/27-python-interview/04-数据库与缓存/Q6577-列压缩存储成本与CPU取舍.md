### Q6577 · 数据库列压缩的存储成本与 CPU 取舍

难度：P6/P7 ｜ 标签：PostgreSQL / 存储成本 / 成本工程

**问**：一张 20TB 的日志表存储费用占了大头。把大字段改成压缩存储（PG 的 LZ4/原生 pglz、或列式压缩扩展）能省多少？CPU 会不会成为新的瓶颈？

**答**：
- **结论**：压缩收益取决于数据冗余度：JSON/日志文本典型压缩比 3-8x，随机会话数据（已加密/已压缩）接近 1x。PG 原生 TOAST 支持 `pglz`（默认）与 12+ 的 `lz4`（解压快 2-4x，压缩率略低），列级选择 `ALTER TABLE t ALTER COLUMN payload SET COMPRESSION lz4`。成本账核心是"存储单价 vs CPU 单价"：写入路径多一次压缩 CPU，读取路径多一次解压 CPU，只有当存储成本降幅 > CPU 成本增幅（折算成相同货币）时才净赚。
- **取舍**：pglz vs lz4 vs 外置列存（如 Parquet 归档到对象存储）：热数据用 lz4（读放大最小）；温冷数据（月访问 <1 次）直接导出 Parquet+zstd 归档，存储成本比在线压缩再降一个量级，代价是查询要走导出通道、实时性归零。
- **实战**：评估流程：抽样 1 万行真实数据测压缩比与耗时 → 算出每 GB 月成本节省与每百万次查询的 CPU 增量（换算为需要增加的副本数）→ 小流量灰度新写入，验证 vacuum/备份链路不因压缩回归变慢。注意压缩列参与索引的代价：表达式索引建立在解压结果上，写入放大翻倍。

```python
# 压缩 ROI 计算：存储节省 vs CPU 增量（纯标准库）
# 基线：Python 3.9+


def compression_roi(
    size_gb: float, ratio: float, storage_cost_per_gb_month: float,
    queries_per_month: float, decompress_ms_per_mb: float,
    cpu_cost_per_core_hour: float,
) -> dict:
    saved_storage = size_gb * (1 - 1 / ratio) * storage_cost_per_gb_month
    read_mb = queries_per_month * 1  # 每查询读 1MB 明文
    extra_cpu_h = read_mb * ratio * decompress_ms_per_mb / 1000 / 3600
    extra_cost = extra_cpu_h * cpu_cost_per_core_hour
    return {"storage_saved": saved_storage, "cpu_cost": extra_cost,
            "net": saved_storage - extra_cost}


def main() -> None:
    r = compression_roi(
        size_gb=20_000, ratio=5.0, storage_cost_per_gb_month=0.1,
        queries_per_month=10_000_000, decompress_ms_per_mb=2.0,
        cpu_cost_per_core_hour=0.05,
    )
    for k, v in r.items():
        print(f"{k}={v:,.0f}")
    assert r["net"] > 0, "压缩比 5x 时应为正收益"

    r2 = compression_roi(size_gb=20_000, ratio=1.2, storage_cost_per_gb_month=0.1,
                         queries_per_month=10_000_000, decompress_ms_per_mb=2.0,
                         cpu_cost_per_core_hour=0.05)
    print("低冗余数据 net=", round(r2["net"]))
    assert r2["net"] < 0  # 已压缩数据压缩不划算


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"数据已经加密后再入库"压缩基本无效？
→ 一句话提示：加密输出熵接近随机分布，压缩算法找不到冗余，通常反而略增大小，所以顺序应是先压缩后加密（或在传输层 TLS 内压缩）。

**追问 2**：TOAST 压缩和 ETOH（Extended）与 EXTERNAL 的选择？
→ 一句话提示：`SET STORAGE EXTERNAL` 关闭压缩保 rand access 快、`EXTENDED` 允许压缩+out-of-line；大字段若总是整读用 EXTERNAL 省解压，随机部分读才受益于 EXTENDED。

## 背诵要点
- 压缩 ROI = 存储节省 − CPU 增量；冗余文本 3-8x 净赚，已加密/已压缩数据 ≈1x 必亏。
- PG 12+ 列级 `SET COMPRESSION lz4`：解压快 2-4x，热数据优先；冷数据走 Parquet+zstd 归档。
- 抽样实测三步：压缩比、每查询解压耗时、换算副本增量；压缩列建表达式索引会翻倍写放大。

## 复盘追问
- 为什么压缩评估必须用真实数据抽样？提示：压缩比与 CPU 耗时完全由数据分布决定，官方数字不可迁移。
- 备份/恢复链路为什么会被压缩影响？提示：逻辑备份导出的是明文，物理备份压缩有限；恢复时解压 CPU 成为恢复 RTO 的新瓶颈。
