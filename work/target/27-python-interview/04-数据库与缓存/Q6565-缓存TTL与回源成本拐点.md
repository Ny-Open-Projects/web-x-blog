### Q6565 · 缓存 TTL 拉长的回源成本拐点账

难度：P6 ｜ 标签：缓存 / TTL / 成本工程 / 命中率

**问**：团队想通过拉长缓存 TTL 从 60s 提到 600s 来给数据库减压，但没人说得清"数据变旧"的代价。怎么把 TTL、命中率、回源 DB 成本和内存成本放进同一本账，找出拐点？

**答**：

**结论**：TTL 的收益边际递减：命中率随 TTL 增长是凹曲线，TTL 从 60s→600s 可能只把命中率从 92% 提到 97%，但 DB QPS 降到原来的 1/2.7；而数据新鲜度从"最多旧 60s"退化到"最多旧 600s"。拐点在于：当命中率曲线进入平台期（再加 TTL 命中率几乎不动），继续拉长只付新鲜度成本不收减负收益——应停止。真正划算的组合往往是"中等 TTL + 主动失效（binlog 订阅/写后删）"，用一致性换长 TTL 的必要性。

**取舍**：账要同时算三边：① DB 成本 = miss QPS × 单次查询成本（含慢查询的长尾风险）；② 内存成本 = 活跃 key 数 × 平均 value 大小，TTL 越长同时在线 key 越多、内存水位越高，可能触发淘汰反噬命中率；③ 新鲜度成本 = 业务能容忍的最大 staleness（商品价格 5s 都嫌长，推荐榜单 10min 无所谓）。三边交点才是合理 TTL，没有普适值。

**实战**：先用压测/回放拿到"命中率-TTL"曲线（对热点 key 做访问间隔分布统计，理论命中率 = 1 - (平均请求间隔/TTL) 超过部分的占比）；再算内存账确认不触顶；最后给不同 key 类别定不同 TTL（价格类短 TTL + 主动失效，榜单类长 TTL + 随机抖动防过期风暴）。Python 建模可以直接用访问间隔分布模拟不同 TTL 的命中与回源量。

```python
# 用访问间隔分布模拟 TTL-命中率曲线，算回源成本与内存账
# 仅标准库，Python 3.9+
from __future__ import annotations

import random


def hit_rate(intervals: list[float], ttl: float) -> float:
    """key 上次访问后隔了 t 再访问：t < ttl 则命中（理想化，忽略淘汰）。"""
    hits = sum(1 for t in intervals if t < ttl)
    return hits / len(intervals)


def main() -> None:
    random.seed(42)
    # 访问间隔：98% 指数分布（均值 30s）+ 2% 长尾冷访问（6~120 分钟才回访）
    intervals = []
    for _ in range(200_000):
        if random.random() < 0.02:
            intervals.append(random.uniform(600, 7200))  # 冷回访
        else:
            intervals.append(random.expovariate(1 / 30))
    total_qps = 10_000

    print(f"{'TTL':>5} {'命中率':>7} {'回源QPS':>8} {'DB相对成本':>10}")
    base = None
    for ttl in (30, 60, 120, 300, 600, 1200):
        hr = hit_rate(intervals, ttl)
        miss_qps = total_qps * (1 - hr)
        if base is None:
            base = miss_qps
        print(f"{ttl:>5} {hr:>7.1%} {miss_qps:>8.0f} {miss_qps / base:>10.2f}")

    hr600 = hit_rate(intervals, 600)
    hr1200 = hit_rate(intervals, 1200)
    gain = (hr1200 - hr600) / (1 - hr600)  # 回源量再降多少
    print(f"TTL 600→1200s：回源量仅再降 {gain:.1%}，但 staleness 翻倍 → 停在 600s")
    assert gain < 0.15, "平台期收益应很小"
    assert hit_rate(intervals, 60) < hit_rate(intervals, 600) < 1.0


if __name__ == "__main__":
    main()
```

**追问链**：

- 追问 1：为什么 TTL 拉太长反而可能让命中率下降？——长 TTL 让同时在线 key 增多，内存触顶后 LRU 淘汰加剧，冷热 key 一起被逐，出现"越存越缺"的反噬；所以内存账必须和命中率账联算。
- 追问 1.1：主动失效（写后删/binlog 订阅）和长 TTL 是替代还是互补？——互补：主动失效负责"数据变了别用旧的"，TTL 只兜"主动失效链路挂了"的底。有了可靠主动失效，TTL 可以设得比业务容忍 staleness 长得多。
- 追问 2：指数分布假设不成立时会怎样？——真实访问多呈重尾（热点 key 被高频刷），热点 key 上短 TTL 命中率就很高，长 TTL 主要改善的是长尾 key；所以分位数建模（按 key 热度分层）比单一分布更准，别用一条曲线给全库定 TTL。

**背诵要点**：

1. 命中率-TTL 是凹曲线，平台期后继续拉长只付新鲜度不收减负收益；理想命中率可用访问间隔分布模拟。
2. 三边账：回源 DB 成本、内存水位成本（长 TTL 淘汰反噬）、业务容忍 staleness，交点定 TTL。
3. 可靠主动失效让 TTL 只做兜底，可设远超容忍值；不同 key 类别分层定 TTL + 抖动防过期风暴。
