### Q6689 · 数据库时区参数不一致事故复盘：8 小时偏移与"谁的今天"

难度：P6 ｜ 标签：事故复盘、时区、TIMESTAMP
基线：MySQL 8.0（`time_zone`/`system_time_zone`，TIMESTAMP 存储 UTC）；PyMySQL 连接参数 `init_command`。

**问**：服务从自建机房迁到云托管，第二天日报表全部少算 8 小时的订单——凌晨 0 点到 8 点的单子被归到了前一天。事故根因是什么？TIMESTAMP 与 DATETIME 在这里的差别为什么致命？

**答**：**结论**：根因是**三层时区不一致**：旧库 `time_zone=SYSTEM`（系统是 UTC+8），云实例默认 `time_zone=UTC`；应用连接串没有显式指定会话时区；报表 SQL 用 `DATE(created_at)` 做日切。关键在列类型：**TIMESTAMP 列存 UTC，读出时按会话时区转换**——写入方会话 UTC+8、读出方会话 UTC，同一行数据读出的本地时间差 8 小时；**DATETIME 存的是字面量**，不做转换，但它只是"谁写进去就是谁的说法"。迁移把读出方的会话时区改了，TIMESTAMP 列的读出值全部偏移。事故链：云实例默认 UTC → ORM 连接未设 `time_zone` → 报表按会话时区渲染 → 日切窗口平移。

**取舍**：两条治理路线：① **全链路显式 UTC**——应用写 aware datetime、连接参数锁 `time_zone='+00:00'`、报表层把 UTC 转业务时区再日切；最干净，但要审计所有"本地时间"写点。② **全链路锁业务时区**——连接与会话全部 `'+08:00'`，DATETIME 存字面量；简单，但跨时区业务（海外用户）会把"谁的今天"问题固化进数据。工程上推荐 ①，与 Python 的 `datetime.now(timezone.utc)` 生态一致。

**实战**：三层时区一致性检测脚本（标准库演示账）：

```python
# 时区错位的账：同一行 TIMESTAMP 在不同会话时区下读出的差异
from datetime import datetime, timezone, timedelta

UTC8 = timezone(timedelta(hours=8))
stored_utc = datetime(2026, 11, 21, 16, 0, tzinfo=timezone.utc)  # TIMESTAMP 存储值

read_old = stored_utc.astimezone(UTC8)   # 旧库会话 time_zone=+08:00
read_new = stored_utc.astimezone(timezone.utc)  # 云库会话 time_zone=UTC
print(f"旧库读出: {read_old}  日切归属 2026-11-22")
print(f"新库读出: {read_new}  日切归属 2026-11-21  <- 少算 8 小时的订单")

# 日切账：凌晨订单按 UTC 归属错误的天
def day_bucket(dt: datetime, session_tz) -> str:
    return dt.astimezone(session_tz).date().isoformat()

orders = [stored_utc + timedelta(hours=h) for h in range(10)]
mismatch = sum(
    day_bucket(o, UTC8) != day_bucket(o, timezone.utc) for o in orders)
print(f"10 小时窗口内归属错位的小时数: {mismatch}/10")

# 一致性检测：应用、连接、DB 三层各报时区
def tz_audit(app_tz: str, conn_tz: str, db_tz: str) -> list[str]:
    issues = []
    if conn_tz != db_tz:
        issues.append(f"连接时区 {conn_tz} != DB time_zone {db_tz}")
    if app_tz.upper() != "UTC":
        issues.append(f"应用未用 UTC 写入（当前 {app_tz}）")
    return issues

print(tz_audit("+08:00", "+08:00", "UTC"))  # 迁移后的真实配置

# 修复后的正确姿势：应用侧 aware UTC + 报表层业务时区渲染
now = datetime.now(timezone.utc)
print(f"写入: {now.isoformat()} | 报表渲染: {now.astimezone(UTC8).date()}")
```

**追问 1**：为什么 DATETIME 列在这次迁移中"看起来没事"，风险反而更隐蔽？
提示：DATETIME 不转换、字面量原样读出，报表数值没变；但写入方的"本地时间"含义在新环境（容器 TZ）变化后会开始写错——风险被延迟到下一次写入环境变更。

**追问 2**：MySQL 驱动层（PyMySQL/SQLAlchemy）会话时区在哪一层设置最稳？
提示：连接串/引擎层 `init_command="SET time_zone = '+00:00'"` 或驱动参数（PyMySQL 的 `init_command`、SQLAlchemy 的 `connect_args`）；在应用代码里每次 `SET` 不可靠，连接池复用会漏。

**追问 3**：已入库的历史数据怎么修正？
提示：TIMESTAMP 存储值是 UTC 无需改，只需修读路径会话时区；DATETIME 若曾受写方时区漂移污染，要按"写入环境变更时间点"分段换算，一次性回填脚本 + 双写对账。

## 背诵要点
1. TIMESTAMP 存 UTC 读出按会话时区转换，DATETIME 存字面量不转换——会话时区变了 TIMESTAMP 读值全偏移。
2. 治理首选全链路显式 UTC：应用 aware datetime + 连接层锁 `time_zone='+00:00'` + 报表层转业务时区日切。
3. 检测三层一致性：应用写入时区、驱动会话时区、DB `time_zone`，任何两层不一致都是事故预备役。
