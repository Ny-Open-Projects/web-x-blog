### Q6704 · 逻辑解码变更捕获与复制槽堆积的定位

难度：P7 ｜ 标签：事故复盘、CDC、逻辑复制、LSN 水位

基线：Python 3.12；PostgreSQL 10+（pgoutput/wal2json）；纯 Python 演示确认位点推进。

**问**：用逻辑复制把订单库的变更同步到数仓，平时延迟几秒，某天开始延迟几小时，主库 `pg_wal` 目录暴涨。业务查询一切正常，问题出在哪？怎么定位是解码侧还是消费侧？

**答**：
- **结论**：逻辑复制靠复制槽（replication slot）记录消费者已确认的 LSN。只有消费者确认后的 WAL 才能被回收。延迟的本质是**确认位点不推进**：要么是消费者反序列化/落库变慢，要么是中途报错卡在旧 LSN 上反复重试。此时 `pg_replication_slots.confirmed_flush_lsn` 停滞、`restart_lsn` 不前进，WAL 无限堆积直至打满磁盘（与"复制槽打满磁盘"是同类事故，但这里深挖解码侧的确认位点机制）。wal2json 这类插件还在数据库服务器端做 JSON 序列化，CPU 吃紧时也会拖慢解码。
- **取舍**：wal2json 输出格式灵活、含旧值，但 CPU 开销大；pgoutput 是原生格式、性能好但格式固定。确认策略上，"每条确认"最稳但往返多，"批量确认"吞吐高但崩溃时要重放更多。
- **实战**：监控 `confirmed_flush_lsn - restart_lsn` 的差值与增长速率、slot 的 active 状态、walsender 的 CPU；给消费端设消费延迟告警而非磁盘爆了才发现；确认批量要设上限（防止一次重放过大）；异常时要能跳过错数据而不是无限重试卡死水位。

```python
from dataclasses import dataclass


@dataclass
class Slot:
    confirmed: int = 0
    restart: int = 0


def ack(slot: Slot, flushed: int) -> int:
    """模拟复制槽水位推进：返回相对 restart_lsn 的 WAL 堆积量。"""
    slot.confirmed = flushed
    return slot.confirmed - slot.restart


if __name__ == "__main__":
    slot = Slot()
    for lsn in (10, 20, 35, 35, 35):
        print(f"flushed={lsn}, wal_lag={ack(slot, lsn)}")
    # flushed 卡在 35 不再前进时，堆积量恒定在高位，WAL 无法回收。
```

**追问一**：为什么复制槽会导致 WAL 无法回收，而普通流复制不会？
→ 解析：复制槽是"显式承诺保留 WAL 直到消费者确认"的机制，消费者不确认就一直保留；物理流复制若无槽，备库断开后主库会按 keepalive 自行回收。

**追问二**：确认位点推进但延迟仍高，该往哪查？
→ 解析：往解码侧和下游侧查——wal2json 的 CPU 占用、消费端单条落库耗时、下游限流。确认位点前进说明 WAL 能回收，瓶颈在端到端处理速度而非堆积。
