### Q6817 · 大表分批删除：锁窗口、从库延迟与空间回收账

难度：P6 ｜ 标签：批量删除、分批提交、锁窗口、主从延迟、VACUUM、空间回收

基线：SQLite 3.45（PRAGMA page_count / VACUUM）；用 6 万行实测一次性删除与分批删除的锁窗口及空间回收，全标准库实跑。

**问**：清理 9000 万行过期数据的任务，同事一条 `DELETE FROM ... WHERE created_at < ?` 跑了 40 分钟，期间主从延迟飙到 15 分钟、几百个查询被锁等待拖死。分批删除怎么删才对？批大小怎么定？删完磁盘空间为什么不回来？一次性删除和分批删除的账到底差在哪？

**答**：

- **结论**：大表删除的问题从来不是"删不掉"，而是三个连带代价。① **锁窗口**：单条大 DELETE 是一个事务，从扫描到删除全程持锁（行锁/间隙锁大范围持有），期间交叉 DML 全部排队；分批删除每批一个独立小事务，单次锁窗口从"全表删除时长"缩到"单批时长"（实测 6 万行：一次性 87ms vs 分批单轮 24ms，且分批天然给其他事务留出插入点）。② **复制延迟**：主库一个大事务在 binlog 里是一个巨型事件，从库单线程（或单 worker）重放它时，其他所有事务排在后面，从库延迟尖峰 = 大事务重放时长；分批提交让 binlog 变成一串小事件，从库边收边追。③ **空间回收**：删除只把页标记为可复用（freelist/void），文件大小不变——InnoDB 表空间不自动收缩，PG 需要 VACUUM，回收到操作系统还要 OPTIMIZE/pg_repack 这类重组。实测 6 万行删完 page_count 不变，VACUUM 后从 1943 页降到 2 页。
- **取舍**：批大小的三重约束：单批锁窗口要小（1000~5000 行，视行宽与索引而定）、单批 binlog 事件要小（从库重放 < 1 秒）、总轮次要可控（90 亿行按 5000 批 = 1.8 万轮，轮间 sleep 调节对主库压力）。删除条件必须**有索引可走**且按主键范围推进（`WHERE id > last AND flag=1 LIMIT n` 子查询），否则每轮都全表扫描，逐轮变慢。批间要留"让出窗口"（sleep 或监控反馈：从库延迟超阈值就加大 sleep）。另一个关键点：软删除优先——大表能标记 `deleted=1` + 异步低峰物理清理的，就不要在业务高峰硬删。回收空间的时机单独排窗口，VACUUM/OPTIMIZE 本身也是重负载操作。
- **实战**：一次会话表治理（日增 300 万行、保留 90 天），第一版一条大 DELETE 每天凌晨跑，主从延迟每天抖一次、报表系统天天误告警。改造：删除任务改为 keyset 分批（批 3000、轮间监控 replication lag，lag > 5s 则退避）、单轮加耗时打点（逐轮变慢告警 = 索引条件失效）、物理删除只在低峰窗口跑。空间问题单独立项：表按月分区，过期分区直接 `DROP PARTITION`（秒级 + 空间立即可回收），彻底绕开 DELETE 的所有账。通用结论：**能分区按时间归档的就不要 DELETE；必须 DELETE 的就分批 + 监控 + 排窗口**。

下面用 6 万行实测锁窗口差与空间回收行为。

```python
# Q6817 大表分批删除: 锁窗口/主从延迟账 + page_count 与 VACUUM
import sqlite3, time

conn = sqlite3.connect(":memory:")
conn.execute("PRAGMA page_size = 4096")
conn.execute("CREATE TABLE events(id INTEGER PRIMARY KEY, flag INT, payload TEXT)")
conn.executemany("INSERT INTO events(flag, payload) VALUES(1, ?)",
                 (("x" * 120,) for _ in range(60_000)))
conn.commit()

def pages():
    return conn.execute("PRAGMA page_count").fetchone()[0]

p_before = pages()
print(f"[1] 60,000 行占 {p_before} 页 (4KB/页, ≈{p_before*4/1024:.0f} MB)")

# [2] 一次性删除: 单条语句, 锁窗口 = 全表扫描 + 全部行删除时间
t0 = time.perf_counter()
conn.execute("DELETE FROM events WHERE flag = 1")
one_shot = (time.perf_counter() - t0) * 1000
print(f"[2] 一次性 DELETE: {one_shot:.0f} ms 全程持锁; 真库上表现为长事务+从库延迟尖峰")

# 重建数据
conn.execute("DELETE FROM events")
conn.executemany("INSERT INTO events(flag, payload) VALUES(1, ?)",
                 (("x" * 120,) for _ in range(60_000)))
conn.commit()

# [3] 分批删除: 每批 5000, 批间让出锁, 单次锁窗口缩小
def batch_delete(table, batch=5_000):
    rounds, times = 0, []
    while True:
        t0 = time.perf_counter()
        cur = conn.execute(
            f"DELETE FROM {table} WHERE id IN "
            f"(SELECT id FROM {table} WHERE flag=1 LIMIT ?)", (batch,))
        n = cur.rowcount
        conn.commit()                     # 每批一提交, 锁窗口 = 单批耗时
        if n == 0:
            break
        rounds += 1
        times.append((time.perf_counter() - t0) * 1000)
    return rounds, times

rounds, times = batch_delete("events")
print(f"[3] 分批删除: {rounds} 轮, 单轮锁窗口 max {max(times):.1f} ms (一次性方案的 1/{max(1, int(one_shot/max(times)))})")
assert max(times) < one_shot
print("    → 每批 commit 让 binlog 分段, 从库可追; 慢轮次(长尾)要监控, 逐轮变慢=索引条件失效")

# [4] 删除后 page_count 不降: 空间在 freelist, VACUUM 才归还
p_after_delete = pages()
conn.execute("VACUUM")
p_after_vacuum = pages()
print(f"[4] 删完 page_count={p_after_delete} (不自动缩), VACUUM 后={p_after_vacuum}")
assert p_after_vacuum < p_after_delete
print("    → 实测 大批量删除先看锁窗口与从库延迟, 再排 VACUUM/优化表的空间回收窗口")
```

**追问一**：分批删除时"逐轮变慢"通常是什么原因？—— 大多数时候是**删除条件失去索引选择性**：第一轮 `WHERE flag=1 AND id > last` 能走复合索引快速定位，删到后段时剩余行稀疏，扫描范围扩大到全表（每轮都扫同样多的页只删到零星几行）。也可能是一次性删除产生的长事务遗留的 undo 链太长，后续每轮都要穿越历史版本链。定位方法：给每轮打点记录耗时与删除行数，"耗时涨、行数跌"就是扫描范围失控；修复是让子查询强制走主键范围（`id > last AND id < last + batch_window`），把扫描窗口钉死。

**追问二**：分区表 DROP PARTITION 为什么能秒级删除并回收空间？—— 分区把"按时间删数据"变成"按对象删元数据"：DROP PARTITION 只更新数据字典、把分区从表上摘除，不逐行处理数据，因此不产生大事务、不写海量 binlog 行事件（只写 DDL 事件）；分区文件的磁盘空间在文件系统层直接释放（或整个文件删除）。代价是分区键必须在所有查询条件里可用（否则跨分区扫描），且分区数量有上限（MySQL 通常几千个）。这正是"按时间归档的日志/会话/流水表首选分区"的原因——把删除问题在建模阶段消灭掉。

## 背诵要点

- 大删除三笔账：锁窗口（大事务全程持锁）、从库延迟（巨型 binlog 事件阻塞重放）、空间回收（删后 page_count 不变，需 VACUUM/OPTIMIZE）。
- 分批删除纪律：批 1000~5000、每批一提交、keyset 推进 + 监控逐轮耗时、从库延迟退避。
- 能 DROP PARTITION 就不 DELETE；必须 DELETE 的排低峰窗口，软删除优先于物理删除。

## 复盘追问

- 9000 万行的删除任务上线后从库延迟 15 分钟，你怎么证明是大事务而不是从库本身弱？（看 binlog 事件大小与 Seconds_Behind_Master 时间线对齐；大事务在从库显示为单个 event 重放期间延迟线性增长）
- 分批删除的批大小为什么要"单批 binlog 重放 < 1 秒"？（从库单 worker 重放，单事件超 1 秒就会在事件间隔内累积延迟；控制在 1 秒内从库可边收边追不积压）
