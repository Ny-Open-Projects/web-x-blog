### Q6763 · 备份文件在对象存储上裸奔：备份加密与密钥隔离的账

难度：P6 ｜ 标签：备份加密、密钥管理、KMS、数据安全、合规

基线：Python 3.12；标准库（hashlib/hmac/secrets）演示密钥派生、备份完整性验签、密钥与备份分离存储的流程。加密本体用异或占位示意流程，生产必须换 AES-GCM 等标准算法。

**问**：安全审计发现数据库备份直接落在对象存储的私有桶里，谁都可能被一枚泄露的 AK 拖走。给备份加"加密"听起来一句话的事，做起来发现一堆问题：密钥放哪？密钥和备份放同一个桶是不是等于没加密？备份加密后恢复演练还能跑吗？恢复时的密钥从哪来？

**答**：
- **结论**：备份加密的正确结构是**三层分离**：① 加密在**客户端/备份机侧完成**（落存储前已加密），对象存储侧只是搬运 ciphertext；② **密钥走独立通道**（KMS/HSM），与备份不同账号、不同权限、不同生命周期——密钥与密文同桶、同账号、同权限，泄露时一起被拖走，等于没加密；③ 每个备份文件带 **HMAC 完整性校验**，恢复前先验签再解密，防止"备份被篡改/半截"混进恢复流程（Q2959 的指纹校验升级为密码学校验）。加密本身不是难点，**密钥的存储、轮换、恢复演练**才是——恢复演练必须连同"从 KMS 取密钥→解密→验签"全链路跑通，只验文件存在性的演练在真事故里跑不起来。
- **取舍**：① 应用层加密 vs 存储层加密（对象存储 SSE）：SSE 只防"存储介质物理泄露"，防不了"持有桶权限的人"——AK 泄露场景必须客户端加密；② 加密的性能成本：备份本来就慢，加密再加 10%~20% CPU，备份机要余量，别把加密放主库上做；③ 密钥轮换：轮换只影响新备份，历史备份用加密时密钥解密——密钥不能删，只能停用，保留策略与备份保留期对齐（Q6566）；④ 压缩与加密的顺序：先压缩后加密（密文不可压缩，顺序反了既浪费 CPU 又白加密）。
- **实战**：① 备份流水线固定五步：导出 → 压缩 → 加密 → HMAC → 上传，每步产出物可独立验证；② 恢复演练脚本里加"密钥获取失败"与"HMAC 不匹配"两个负例演练（Q2018 的验证清单扩展）；③ 密钥访问审计进监控：谁在非演练/非恢复时段取过备份密钥，立刻告警；④ 桶策略与 KMS 策略交叉校验自动化——"备份桶无人可读、密钥仅恢复角色可取"用配置巡检固化（Q2779）。

```python
"""备份加密流程模拟：密钥派生 -> 加密 -> HMAC 验签 -> 密钥分离存储 -> 恢复验签。
注意：加密本体用 XOR 占位演示流程；生产必须用 AES-GCM 等标准库外的认证加密。"""
import hashlib
import hmac
import secrets


def derive_key(master_key: bytes, backup_id: str) -> bytes:
    """每份备份独立派生密钥（PBKDF2），主密钥泄露也不横向波及。"""
    return hashlib.pbkdf2_hmac("sha256", master_key, backup_id.encode(), 100_000)


def xor_stream(data: bytes, key: bytes) -> bytes:
    """流程占位用异或：演示'密文与密钥分离后不可读'的结构关系。
    生产实现必须替换为 AES-GCM / ChaCha20-Poly1305。"""
    return bytes(b ^ key[i % len(key)] for i, b in enumerate(data))


def encrypt_backup(plain: bytes, backup_id: str, master_key: bytes) -> dict:
    key = derive_key(master_key, backup_id)
    ciphertext = xor_stream(plain, key)
    mac = hmac.new(key, ciphertext, hashlib.sha256).hexdigest()
    return {"id": backup_id, "ciphertext": ciphertext, "hmac": mac}


def verify_and_decrypt(pkg: dict, master_key: bytes) -> tuple[bool, str]:
    key = derive_key(master_key, pkg["id"])
    if not hmac.compare_digest(
            hmac.new(key, pkg["ciphertext"], hashlib.sha256).hexdigest(),
            pkg["hmac"]):
        return False, "HMAC 不匹配: 文件被篡改或传输损坏"
    return True, xor_stream(pkg["ciphertext"], key).decode()


if __name__ == "__main__":
    master = secrets.token_bytes(32)
    payload = b"order_backup_20261124: rows=5,000,000 checksum=ok"
    pkg = encrypt_backup(payload, "bk-20261124-full", master)

    # 密钥与备份分离存储：模拟"攻击者只拿到备份桶"
    stolen_bucket = {"bk-20261124-full": pkg["ciphertext"], "bk.hmac": pkg["hmac"]}
    print("攻击者拖走备份桶, 拿到密文+HMAC, 无主密钥:")
    print(f"  密文片段: {stolen_bucket['bk-20261124-full'][:24]!r}")
    print("  无法解密 -> 数据不泄露 (密钥在 KMS, 不同账号不同权限)")

    # 正常恢复: KMS 取主密钥 -> 派生 -> 验签 -> 解密
    ok, result = verify_and_decrypt(pkg, master)
    print(f"\n正常恢复: 验签+解密 = {ok}, 内容 {result!r}")

    # 负例: 篡改一个字节
    tampered = dict(pkg, ciphertext=bytes([pkg["ciphertext"][0] ^ 1]) + pkg["ciphertext"][1:])
    ok2, msg2 = verify_and_decrypt(tampered, master)
    print(f"篡改密文后恢复: {ok2} -> {msg2}")

    # 负例: 错误主密钥 (轮换后旧密钥丢失)
    ok3, msg3 = verify_and_decrypt(pkg, secrets.token_bytes(32))
    print(f"密钥丢失后恢复: {ok3} -> 密钥派生不一致, HMAC 不匹配, 无法恢复")
    print("\n结论：备份加密的价值=密文+密钥+校验三者分离；")
    print("      恢复演练必须含'取密钥->验签->解密'全链路与两个负例")
```

**追问一**：密钥轮换后，三个月前的备份还能恢复吗？

→ 解析：能，前提是**旧密钥只停用不删除**。轮换的语义是"新备份用新密钥"，不是"所有备份重加密"——重加密等于全量重写备份（IO/费用双炸），正确做法是版本化密钥：每个备份记录加密时用的 key 版本，恢复时按版本取对应密钥。KMS 侧对停用密钥保留到"备份保留期 + 恢复演练期"之后再物理删除，两段窗口都要覆盖。这里有个容易漏的点：**演练用的密钥权限**和**生产恢复的密钥权限**要走同一条审批路径，否则会出现"演练能恢复、真事故取不到密钥"的剧本偏差。

**追问二**：用了存储层加密（SSE/TDE），还需要客户端加密吗？

→ 解析：看威胁模型。SSE/TDE 防的是"磁盘/介质被物理带走"和"存储服务内部泄露"，但**持有桶读权限的凭证**依然能读到明文——AK 泄露、内部人员、错误授权都在这条线上。所以生产敏感数据的标准答案是**两层都要**：客户端加密管"谁能拿到密文"，存储层加密管"介质与内部"。成本敏感时至少做到：备份桶加密 + 桶策略最小化 + 访问审计三件套。判断标准一句话：攻击者拿到你的对象存储 AK，看到的应该是密文还是明文？是明文就是裸奔。
