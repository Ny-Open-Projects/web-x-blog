### Q6639 · 备份恢复误连生产实例的事故复盘与防呆设计

难度：P6 ｜ 标签：事故复盘 / 备份恢复 / 防呆设计

**问**：一次恢复演练里，工程师把"恢复到演练库"的脚本改了个 host 就跑，结果 host 改漏了——恢复脚本直连**生产主库**执行 `RESTORE/DROP+CREATE`，线上数据被备份文件覆盖。事故为什么会发生，防呆应该做在哪几层？

**答**：
- **结论**：根因是"恢复操作天然携带破坏性（DROP/覆盖），而目标地址只是脚本里的一个字符串"。事故链条：复制脚本改 host 漏改 → 凭据正确（生产凭据就在配置中心）→ 恢复命令直接执行无确认 → 覆盖完成才发现。防呆四层（由内到外）：① **协议层**：恢复工具只接受带显式 `--target-verify` 参数的目标，连接后先查 `role/版本/数据指纹` 并断言目标标记为"可覆盖"（如演练库有 `restore_enabled=1` 标记表），无标记直接拒绝；② **账号层**：生产实例对恢复专用账号不授予 DROP/ALTER（ACL 最小权限），恢复账号只在演练库存在；③ **环境层**：恢复操作只允许在隔离网络/跳板机执行，生产库所在网段对恢复工作站不可达（网络可达性就是权限）；④ **流程层**：恢复命令需双人确认 + 输出目标全名回显（`You are about to restore into PROD-order-db (wss-host-3), type full name`）。
- **取舍**：网络隔离最硬但建设成本高；账号权限层性价比最高（一次配置永久生效），但防不住"用超级管理员账号手滑"——所以四层都要有，防线深度的意义是任何单层失效不致死。恢复演练（Q6563）本身也要演练"防呆是否生效"：故意指错目标，验证会被拒绝。
- **实战**：① 恢复脚本里禁止出现生产 host 字面量（CI 扫描脚本内容）；② 恢复目标一律走逻辑名（`restore-target: staging-1`），物理地址由配置中心解析，配置中心里生产库标 `restorable=false`；③ 事故后补 "恢复操作审计日志"：谁、何时、目标指纹、恢复来源备份 ID；④ 对被覆盖的生产库：立即停写、从 binlog 找覆盖点前的位点做 point-in-time 恢复（Q2233）。

```python
# 恢复防呆模型: 四层守卫中前两层(协议断言 + 账号权限)的参考实现
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class Target:
    name: str
    is_prod: bool
    restore_enabled: bool      # 演练库标记表
    can_drop: bool             # 账号是否有 DROP 权限


def verify_target(t: Target, typed_confirm: str | None = None) -> str:
    if t.is_prod:
        if typed_confirm != t.name:
            return f"BLOCKED(prod): 输入完整名称确认, 目标={t.name}"
    if not t.restore_enabled:
        return "BLOCKED(flag): 目标无 restore_enabled 标记"
    if not t.can_drop:
        return "BLOCKED(acl): 恢复账号无 DROP 权限"
    return f"OK: 可以恢复到 {t.name}"


def main() -> None:
    staging = Target("staging-1", False, True, True)
    prod = Target("prod-order-db", True, False, True)
    prod_no_acl = Target("prod-order-db", True, True, False)  # 有标记但账号无 DROP
    assert verify_target(staging) == "OK: 可以恢复到 staging-1"
    assert "prod" in verify_target(prod)               # 确认层拦截
    assert "flag" in verify_target(prod, "prod-order-db")  # 确认后仍无标记
    assert "acl" in verify_target(prod_no_acl, "prod-order-db")  # 权限层
    # 生产库要恢复必须逐层放开, 且演练脚本拿不到
    print("OK: 防呆顺序 = prod确认 -> restore标记 -> ACL; 演练库默认全绿")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"网络可达性"是比 ACL 更硬的一道防线？
→ 一句话提示：ACL 依赖凭据正确配置且可能被超级账号绕过，网络不可达则无论什么凭据都连不上；隔离网络把"人犯错"从流程问题变成拓扑问题。

**追问 2**：覆盖事故发生后，point-in-time 恢复的窗口取决于什么？
→ 一句话提示：binlog/WAL 的保留时长与备份频率（Q6587 binlog 保留账）；覆盖点到最近一次全备之间的 binlog 必须完整，所以保留期要 > 最大恢复窗口需求。

## 背诵要点
- 恢复事故根因：破坏性操作 + 目标只是个字符串；防呆四层 = 协议断言（restore 标记 + 名称确认）、账号无 DROP、网络隔离、双人流程。
- 防线深度：任一单层失效不致死；演练库默认全绿、生产库默认全红（默认拒绝）。
- 事后恢复靠 binlog point-in-time，保留时长必须 > 最大恢复窗口（Q6587/Q6563）。

## 复盘追问
- 为什么恢复脚本里禁止生产 host 字面量还不够？提示：host 可从变量/配置注入，真正防线是目标侧的标记与权限；脚本扫描只是降低概率的一层。
- 演练如何验证防呆有效？提示：红队式故意指错目标（含带正确凭据的情形），断言全部被拦截；防呆本身进 Q6563 的演练清单。
