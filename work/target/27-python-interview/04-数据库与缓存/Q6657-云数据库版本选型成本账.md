### Q6657 · 云数据库版本/许可选型成本账

难度：P6-P7 | 标签：成本工程、云数据库、选型

**问**：同样规格的 MySQL/PostgreSQL，云厂商有"基础版（单节点）/高可用版/集群版"三档，价格差 1-4 倍；开源数据库还有企业版许可（如 PG 商业发行版、MySQL 企业版线程池）。选型账怎么算？

**答**：结论：版本选型是**可用性 SLA × RPO × 运维人力 × 许可费**的四因子账。基础版便宜但单点，故障恢复=重建实例+从备份恢复（RTO 小时级）；高可用版买的是"分钟级 RTO + 准零 RPO"；企业版特性（如 MySQL Thread Pool、PG 商业版工具链）只有当**省下的人力/硬件 > 许可差价**才值。常见误区：只比实例单价，不算"故障一次的业务损失"与"为高可用自建所花的运维人力"。

实战要点：
1. 分环境分档：开发/预发用基础版或共享实例（Q6615 定时启停再省一层），生产核心库高可用，边缘业务读副本可降档。
2. 自建 vs 托管的隐性成本：备份验证、补丁窗口、故障演练的人力，通常 0.5-1 人/库/年——低于这个投入密度就别自建核心库。
3. 许可陷阱：云上"企业版"按核计费溢价可达 30-50%，先验证需要的特性（如线程池、加密、审计）基础版是否已覆盖，再决定升档。

```python
"""数据库版本档位成本账（标准库，可运行）"""
from dataclasses import dataclass


@dataclass
class Tier:
    name: str
    monthly: int          # 实例月费（元）
    rto_minutes: int      # 故障恢复时长
    sla: float            # 可用性


@dataclass
class Business:
    name: str
    revenue_per_minute: int  # 宕机每分钟业务损失
    expected_fails_per_year: int = 2


def downtime_cost(tier: Tier, biz: Business) -> int:
    per_fail = tier.rto_minutes * biz.revenue_per_minute
    return per_fail * biz.expected_fails_per_year


def year_cost(tier: Tier, biz: Business) -> tuple[int, int]:
    infra = tier.monthly * 12
    return infra, infra + downtime_cost(tier, biz)


basic = Tier("基础版", 800, 180, 0.995)
ha = Tier("高可用版", 2400, 5, 0.9995)
core = Business("订单核心", revenue_per_minute=50000)
edge = Business("后台报表", revenue_per_minute=200)

for biz in (core, edge):
    for t in (basic, ha):
        infra, total = year_cost(t, biz)
        print(f"{biz.name:6s} {t.name:5s} 基础设施={infra:>6} "
              f"含损失总账={total:>9,}")
    print()

# 结论演示：报表业务高可用溢价（19200/年）远大于宕机损失，选基础版
```

**追问 1**：如果基础版年度"含损失总账"反而更低，是不是核心业务也能选基础版？
**提示**：不能只看期望值——尾部风险（一次长故障 + 数据丢失）不可保险化，RPO 要求会否决低档版本。

**追问 2**：为什么企业版线程池这类特性要用"人力账"评估？
**提示**：高并发下线程抖动需要专人调参与值守，许可费若低于这部分人力折算就是正收益，否则是白买。

## 背诵要点
- 版本选型四因子：SLA × RTO/RPO × 运维人力 × 许可差价，只比实例单价必错。
- 分环境分档：预发基础版、核心生产高可用；宕机损失=RTO × 每分钟收入 × 年故障次数。
- 自建核心库要背 0.5-1 人/库/年的运维人力账，低于这个密度就选托管。
