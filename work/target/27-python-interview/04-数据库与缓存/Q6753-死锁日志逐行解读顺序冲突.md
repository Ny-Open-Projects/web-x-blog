### Q6753 · 死锁日志逐行解读：从 LATEST DETECTED DEADLOCK 读出谁先动手

难度：P7 ｜ 标签：MySQL、InnoDB、死锁排查、SHOW ENGINE INNODB STATUS

基线：Python 3.12；用正则解析一段合成的死锁日志文本，输出双方持锁/等锁与牺牲者。

**问**：线上偶发 `Deadlock found when trying to get lock`，频率低、复现难，`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段落密密麻麻。这段日志该怎么逐行读？为什么只显示"最近一次"？死锁不是错误，MySQL 会自动挑一个事务回滚，那我们到底要修什么？

**答**：
- **结论**：死锁日志是**双方对账单**：每方四要素——① 当前执行到的 SQL；② **HELD LOCKS**（已持有的锁，字段里 `lock_mode X` 表示排他、`locks rec but not gap` 表示记录锁）；③ **WAIT FOR**（正在等谁的哪把锁）；④ MySQL 挑中的**牺牲者**（WE ROLL BACK TRANSACTION (1)）。死锁的本质是**加锁顺序冲突**：事务 A 持有 X 等 Y，事务 B 持有 Y 等 X。日志只保留最近一次，所以要靠 `innodb_print_all_deadlocks=ON` 把每次死锁打进 error log 才能统计频率。
- **取舍**：① 修复目标是**消灭顺序冲突**，不是消灭死锁本身——回滚重试是兜底（Q2230 死锁重试退避矩阵），顺序统一才是根治（Q954）；② `SELECT ... FOR UPDATE` 与普通 UPDATE 的加锁点不同、批量更新的行序不同，都算"顺序不一致"；③ 降低隔离级别或拆小事务能降低死锁概率，但会连带改变语义（Q6752 的 gap 行为），要评估；④ 频繁死锁且无法改顺序时，用应用层分布式锁把冲突方串行化。
- **实战**：① 复盘模板：日志 → 两条 SQL → 画出各自的持锁/等锁环 → 找出顺序差 → 给出统一顺序方案；② 监控 `Innodb_deadlocks` 计数器的增速，而不是只在用户报错时看；③ Python 侧捕获死锁错误（如 pymysql 的 `OperationalError` errcode 1213）后必须**整事务重试**，半提交状态继续跑会留下脏数据。

```python
"""死锁日志解析：拆出两个事务的 SQL/持锁/等锁与牺牲者，生成顺序冲突结论。"""
import re

LOG = """
------------------------
LATEST DETECTED DEADLOCK
------------------------
*** (1) TRANSACTION:
TRANSACTION 42101, ACTIVE 0 sec inserting
mysql tables in use 1, locked 1
LOCK WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 58 lock_mode X insert intention waiting
INSERT INTO orders(order_no, user_id) VALUES ('A2026', 1001)
*** (2) TRANSACTION:
TRANSACTION 42102, ACTIVE 0 sec updating
RECORD LOCKS space id 58 lock_mode X locks rec but not gap
HELD LOCK(S): RECORD LOCKS lock_mode X on `orders`
UPDATE orders SET status='paid' WHERE order_no='A2026'
*** WE ROLL BACK TRANSACTION (1)
"""


def parse_deadlock(log: str) -> dict:
    txns = {}
    blocks = re.split(r"\*\*\* \((\d)\) TRANSACTION:", log)[1:]
    for i in range(0, len(blocks), 2):
        num, body = blocks[i], blocks[i + 1]
        sqls = re.findall(r"(INSERT|UPDATE|DELETE|SELECT)[^\n]*", body)
        held = "HELD LOCK" in body
        waiting = "WAITING" in body or "WAIT FOR" in body
        txns[num] = {"sql": sqls, "held": held, "waiting": waiting}
    victim = re.search(r"WE ROLL BACK TRANSACTION \((\d)\)", log)
    return {"txns": txns, "victim": victim.group(1) if victim else None}


def build_ring(txns: dict) -> str:
    """持锁而等另一方的锁 -> 顺序冲突环。"""
    ids = sorted(txns)
    return " <-> ".join(f"T{n}" for n in ids)


if __name__ == "__main__":
    r = parse_deadlock(LOG)
    for num, t in r["txns"].items():
        role = []
        if t["held"]:
            role.append("已持锁")
        if t["waiting"]:
            role.append("在等锁")
        print(f"T{num}: SQL={t['sql']} | {'/'.join(role)}")
    print(f"牺牲者: T{r['victim']}（被回滚，需整事务重试）")
    print(f"顺序冲突环: {build_ring(r['txns'])}")
    print("修复方向:")
    print("  1) 统一加锁顺序：先 SELECT FOR UPDATE 再 INSERT/UPDATE，双方一致")
    print("  2) 开启 innodb_print_all_deadlocks 统计频率")
    print("  3) 应用层捕获 errcode 1213 后整事务重试，不做半提交续跑")
    print("结论：读日志是为了找顺序差；死锁回滚是引擎兜底，根治靠调用方收敛顺序")
```

**追问一**：为什么这个案例里死锁发生在 INSERT 与 UPDATE 之间，而不是两条 UPDATE？

→ 解析：INSERT 需要的"插入意向锁"要与已有记录锁兼容才能落位；对账事务先 `FOR UPDATE` 锁了 `order_no='A2026'`，订单创建事务随后 INSERT 同一订单号的行时，插入意向锁被已有记录锁挡住，而对方又在等新行的插入完成——形成环。两条 UPDATE 之间也会死锁，但通常是"更新顺序不同"（A 先改 1 号再改 2 号，B 先改 2 号再改 1 号）。日志里 `lock_mode X insert intention waiting` 这个字样就是判别 INSERT 卷入死锁的信号。

**追问二**：开了重试就够了吗？什么情况下重试会放大问题？

→ 解析：不够。重试要满足三个前提：① **幂等**——重放的是完整事务，不能带着上次半提交的状态继续；② **退避+抖动**——两个死锁方都立即重试会立刻再次相撞，形成互踢循环，吞吐不升反降；③ **上限与告警**——重试超限要把错误抛回并计数，否则系统性顺序缺陷会被重试掩盖。判断是否"该修而不是该重试"的简单标准：死锁率随并发线性上涨、或某个业务路径贡献了大部分死锁，就该改顺序。
