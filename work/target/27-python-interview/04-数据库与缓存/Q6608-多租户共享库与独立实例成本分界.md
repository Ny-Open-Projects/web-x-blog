### Q6608 · 多租户：共享库与独立实例的成本分界

难度：P7 ｜ 标签：多租户 / 成本工程 / 数据库架构

**问**：SaaS 平台从 50 个客户涨到 800 个，目前架构是"每客户一个数据库实例"，月数据库账单 12 万，CTO 要求降本。是全部迁到"共享库 + tenant_id 列"吗？共享与隔离的成本分界线怎么定？

**答**：
- **结论**：成本分界不是"客户数"，而是**噪声比与合规约束**。共享库（行级 tenant_id）摊薄成本最狠：800 个实例合到 10-20 个大实例，月账单可降 60-80%；但代价是① **噪声租户**——一个大客户的报表查询拖慢所有小客户的 P99（无实例级隔离）；② **故障半径**——一个库 OOM/迁移，全员受影响；③ **合规硬约束**——金融/医疗客户要独立库（数据属地、审计、备份隔离），这一部分客户根本不适用共享。成熟分法是三层：小客户共享池（几十租户/库）+ 中客户独立 schema + 大客户/合规客户独立实例。
- **取舍**：三方案对比：① 独立实例：隔离最好，成本线性、运维（备份/升级/监控）× 客户数爆炸，800 个实例本身也是成本；② 共享库 + tenant_id：成本最优，但应用层必须全 SQL 带租户过滤（漏过滤 = 越权事故），连接池/分页/索引都要按复合键 `(tenant_id, ...)` 设计；③ 独立 schema：介于两者，权限与备份可按 schema 划分，但 PG 下 schema 数量多了目录表与迁移工具都会变慢。迁移策略：先给噪声租户单拎，再批量合并小租户，大客户最后动。
- **实战**：落地账单分账：共享库上用 `pg_stat_statements`/慢日志按 tenant 维度聚合算力占比，转成内部计价——大租户在共享池里占算力超阈值就升级到独立 schema/实例（成本跟着用量走）。迁移 Checklist：行级防越权用 PostgreSQL RLS（见 Q6554）或 ORM 全局租户过滤器双保险；共享库的连接池按租户配额限制（防单租户占满）；容量按"租户算力分位 + 增长曲线"重算。

```python
# 多租户算力分账与升降级判定（标准库模拟）
# 基线：Python 3.9+；真实数据源 pg_stat_statements / 慢日志聚合

from dataclasses import dataclass


@dataclass
class Tenant:
    name: str
    cpu_minutes_day: float      # 日均占用算力
    compliant_required: bool    # 合规要求独立库


SHARED_POOL_FEE = 8000        # 共享池总月费
STANDALONE_FEE = 2600         # 独立小实例月费
NOISE_PCT = 0.35              # 单租户占共享池算力超 35% → 升级


def classify(tenants: list[Tenant]) -> dict[str, str]:
    total = sum(t.cpu_minutes_day for t in tenants)
    plan = {}
    for t in tenants:
        if t.compliant_required:
            plan[t.name] = "standalone(合规)"
        elif t.cpu_minutes_day / total > NOISE_PCT:
            plan[t.name] = "standalone(噪声)"
        else:
            plan[t.name] = "shared"
    return plan


def monthly_bill(tenants: list[Tenant], plan: dict[str, str]) -> float:
    n_standalone = sum(1 for v in plan.values() if v.startswith("standalone"))
    n_shared = len(plan) - n_standalone
    # 共享池按租户数分 3 档每池
    import math
    pools = max(1, math.ceil(n_shared / 60))
    return pools * SHARED_POOL_FEE / 3 + n_standalone * STANDALONE_FEE


def main() -> None:
    tenants = [
        Tenant("big-corp", 9000, False),      # 噪声租户
        Tenant("fin-bank", 600, True),        # 合规
        *[Tenant(f"small-{i}", 200 + i, False) for i in range(40)],
    ]
    plan = classify(tenants)
    assert plan["big-corp"] == "standalone(噪声)"
    assert plan["fin-bank"].startswith("standalone")
    assert plan["small-0"] == "shared"
    bill = monthly_bill(tenants, plan)
    print(f"分账后月账单 ≈ ¥{bill:.0f}（原 800 实例 ¥120000）")
    assert bill < 120000 * 0.5
    print("OK: 噪声/合规租户单拎，其余入共享池，账单减半以上")


if __name__ == "__main__":
    main()
```

**追问 1**：共享库架构下"单租户占满连接池"怎么防？
→ 一句话提示：按租户做连接配额（每租户最大连接数）或入口限流 + 慢查询熔断，把噪声租户的算力账也折进它的计价，让升级决策有数据依据。

**追问 2**：从独立实例迁共享库，最大的工程风险是什么？
→ 一句话提示：应用层漏租户过滤造成越权读——除了全局过滤器（ORM session 级强制注入 tenant_id），要靠 RLS 或全量 SQL 审计兜底；另外迁移期的数据核对与回滚窗口要按租户分批走。

## 背诵要点
- 分界线是噪声比 + 合规，不是客户数：噪声租户/合规客户单拎独立，长尾客户进共享池，账单可降 60-80%。
- 共享库三件套：全链路租户过滤（ORM 全局过滤器 + RLS 兜底）、复合键索引 `(tenant_id, ...)`、租户级连接/算力配额。
- 分账靠租户维度的算力聚合（stat_statements/慢日志），成本跟着用量走，"占用超 35% 就升级"把噪声租户变成正收入。

## 复盘追问
- 独立 schema 方案在 PG 里规模上限出在哪？提示：catalog 表（pg_class/pg_depend）与 autovacuum 的对象数上限、迁移工具逐 schema 执行的时长，几百上千 schema 后 DDL 变慢，是它不如行级共享可扩展的原因。
- 共享库上怎么做租户级的容量规划？提示：按租户算力分位数（P95 而非均值）预留余量，因为共享池的性能是全体共担，头部租户的增长曲线决定整体规格。
