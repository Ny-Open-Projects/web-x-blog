### Q6804 · 索引跳跃扫描：缺最左列时优化器怎么还能用上索引

难度：P7 ｜ 标签：MySQL 8.0、skip scan、最左前缀、基数、优化器代价

基线：库知识库外知识卡，用有序 `(a, b)` 索引项列表 + 二分定位模拟 MySQL 8.0.13 的 index skip scan，并做代价对比。

**问**：有一张 1000 万行的表，联合索引 `(status, created_at)`。查询 `WHERE created_at > '2026-11-01'` 不带 `status`，按最左前缀原则应该用不上索引，可 `EXPLAIN` 显示走了 `range` 且 `Extra` 是 `Using index for skip scan`，从 40 秒降到 2 秒。什么情况下跳跃扫描能救场？为什么同一个索引，`status` 只有 3 个值时很快，`status` 有 5 万个值时反而比全表扫还慢？

**答**：

- **结论**：**skip scan** 是"用最左列的少量不同值，把一次大范围扫描拆成若干次小范围探测"：优化器先枚举 `status` 的每个 distinct 值，再对每个值做 `(status, created_at > ...)` 的索引 range seek。代价 ≈ `NDV(status) × (定位成本 + 该分支的扫描量)`。当 `status` 基数很低（3 个值），相当于只做 3 次 seek，远小于全表扫；当 `status` 基数很高（5 万个值），要探测 5 万次，每次都可能回表，代价超过全表扫，优化器就会放弃。它**不是**"违反了最左前缀也能用索引"的魔法，而是把"缺最左列"转成"枚举最左列"，用低基数换取可用性。
- **取舍**：① skip scan 适合"最左列基数低 + 后续列选择性高 + 表大"的组合；② 如果最左列基数高，正确做法是建 `(created_at)` 或 `(created_at, status)` 的索引，而不是指望 skip scan；③ skip scan 的随机 IO 比全表扫多，SSD 上收益明显，机械盘上可能更慢；④ 优化器是否选它取决于统计信息和 `cost` 模型，统计过期时会误选——上线前用 `EXPLAIN ANALYZE` 实测，不要只看"有没有 skip scan"。
- **实战**：① 看到 `Using index for skip scan` 先算 `NDV(最左列)`，超过几千就要警惕；② 高频查询按真实过滤列建索引，别让优化器每次都做"枚举最左列"的兜底；③ 大表范围查询配 `LIMIT` 与 `ORDER BY` 对齐索引，减少 skip scan 的分支回表；④ 用 `EXPLAIN FORMAT=JSON` 看 `rows_examined_per_scan` 与 `cost_info`，对比全表扫的代价再决定是否加 hint。

下面用有序索引与二分定位模拟 skip scan，并对比低基数/高基数两种代价。

```python
# skip scan: 枚举最左列 distinct 值, 每个值做一次 range seek
import bisect
import math


def build_index(ndv, per=10):
    return sorted((a, b) for a in range(ndv) for b in range(per))


def full_scan(index, target):
    return sum(1 for _, b in index if b == target)


def skip_scan(index, target):
    keys = sorted({a for a, _ in index})
    hits, seeks = 0, 0
    for a in keys:
        pos = bisect.bisect_left(index, (a, target))
        seeks += 1
        if pos < len(index) and index[pos] == (a, target):
            hits += 1
    return hits, seeks


def skip_cost(ndv, n):
    return ndv * (math.ceil(math.log2(n)) + 1)     # 每次 seek 的定位成本


low = build_index(10)          # 最左列 10 个值, N=100
high = build_index(1000)       # 最左列 1000 个值, N=10000

h1, s1 = skip_scan(low, 5)
h2, s2 = skip_scan(high, 5)
c1, c2 = skip_cost(10, len(low)), skip_cost(1000, len(high))
print(f"[1] 低基数: 命中={h1}, seek={s1}, 代价={c1}, 全扫={len(low)}")
print(f"[2] 高基数: 命中={h2}, seek={s2}, 代价={c2}, 全扫={len(high)}")
assert h1 == full_scan(low, 5) == 10
assert h2 == full_scan(high, 5) == 1000
assert c1 < len(low), "低基数时 skip scan 应优于全扫"
assert c2 > len(high), "高基数时 skip scan 应劣于全扫"
print("    → 实测 同一个索引, 基数决定 skip scan 是加速还是拖慢")

# 真正的最左前缀: 带上 status 后是按 (status, created_at) 的普通 range
def range_seek(index, a, lo):
    start = bisect.bisect_left(index, (a, lo))
    end = bisect.bisect_left(index, (a, float("inf")))
    return end - start


print(f"[3] 带最左列 status=3 的 range 读取: {range_seek(high, 3, 5)} 条")
assert range_seek(high, 3, 5) == 5
print("    → 实测 能补最左列就别依赖 skip scan, 直接 range 更省")
```

**追问一**：skip scan 和"分开查每个 status 再 UNION"有什么区别？—— 本质代价模型相同，但 skip scan 在**一个执行计划内**完成，优化器可以共享回表、排序和 LIMIT，不必把结果物化多次；手写 UNION 会产生多次独立扫描和去重，SQL 也更难维护。反过来说，如果业务能接受"只查某几个 status"，手写 `IN` 或分拆查询反而更可控。

**追问二**：为什么 `status` 基数高时优化器还会偶尔选 skip scan？—— 统计信息是采样估算，`NDV` 可能被低估；或者 `created_at` 的选择性极高，优化器认为每个分支只回表几行，综合代价仍低于全表扫。这类"看起来不合理"的计划要用 `EXPLAIN ANALYZE` 的 `actual rows` 对照 `rows` 估算，必要时更新统计信息或加索引提示，而不是直接怪优化器。

## 背诵要点

- skip scan = 枚举最左列 distinct 值 + 每个值做一次 range seek，代价 ≈ `NDV(最左列) × 定位成本`。
- 低基数最左列 + 高选择性后续列才划算；基数上万时通常不如全表扫，应补建以过滤列开头的索引。
- 判断依据是 `EXPLAIN ANALYZE` 的 actual rows 与 `cost_info`，不是 `Extra` 里有没有 skip scan。
