### Q6665 · 行锁等待链排队雪崩复盘：一个慢事务拖垮整条写路径

难度：P6-P7 | 标签：MySQL、InnoDB、事故复盘

**问**：一个后台补偿任务在事务里先调外部 HTTP（耗时 8 秒）再更新热门商品行，上线 10 分钟后所有下单接口超时。`SHOW ENGINE INNODB STATUS` 里 LOCK WAIT 数百个。复盘：为什么 1 个慢事务能放大成全站雪崩？锁等待超时应该怎么设？

**答**：结论：事故结构是**锁等待链 + 队头阻塞**。慢事务持有热点行的 X 锁 8 秒，期间所有竞争同一行的请求进入 lock wait 队列；默认 `innodb_lock_wait_timeout=50` 秒意味着这些请求会**各挂 50 秒**才失败——50 秒足够让上游连接池、线程池、超时熔断全部连锁过载。雪崩不是锁本身，而是"等待时长 × 到达速率"的排队论：8 秒持锁窗口内到达的请求每个都要等到锁释放或 50 秒超时，连接被占死，新请求连进来排队。

取舍与实战：
1. 事务铁律：事务内禁止外部 IO（HTTP/RPC/MQ 发布）。补偿类任务改为"先提交事务 + 事务发件箱异步补偿"（Q6644 幂等表方案），或用 `SELECT ... FOR UPDATE SKIP LOCKED` 分片认领避免全挤同一行。
2. 超时参数分级：OLTP 写路径把 `innodb_lock_wait_timeout` 降到 3-5 秒，宁可快速失败走重试/降级，也不要 50 秒挂连接；长批处理会话单独设置会话级超时。
3. 监控哨兵：`SHOW ENGINE INNODB STATUS` 的 `LOCK WAITS` / `information_schema.INNODB_TRX` 里 `trx_started` 超 5 秒的事务即告警；事务时长 P99 是比 QPS 更早的信号。
4. 死锁与锁等待的区别（Q6527/Q874 讲死锁检测）：死锁由 InnoDB 主动回滚一方秒级解除；锁等待链是"受害者等待"，没有自动解药，只能靠参数与治理兜底。

```python
"""锁等待链风险静态检查：标记事务内外部调用与热点行等待"""
from dataclasses import dataclass


@dataclass
class TxnRisk:
    has_external_io: bool          # 事务内是否调外部 IO
    holds_hot_row: bool            # 是否锁热点行（高并发更新目标）
    lock_wait_timeout_s: int       # innodb_lock_wait_timeout
    arrival_per_s: int             # 竞争该行的请求到达率

    def avalanche_estimate(self) -> list[str]:
        out = []
        if self.has_external_io and self.holds_hot_row:
            io_s = 8.0  # 事务内 IO 耗时
            backlog = self.arrival_per_s * io_s
            out.append(f"[高危] 事务内 IO {io_s}s 持有热点行："
                       f"积压 ≈ {backlog} 个请求进入锁等待")
        if self.lock_wait_timeout_s > 10:
            out.append(f"[高危] lock_wait_timeout={self.lock_wait_timeout_s}s："
                       "失败过慢，连接池将先于锁超时耗尽")
        if not out:
            out.append("[OK] 风险可控")
        return out

t = TxnRisk(has_external_io=True, holds_hot_row=True,
            lock_wait_timeout_s=50, arrival_per_s=200)
for line in t.avalanche_estimate():
    print(line)
```

**追问 1**：`SKIP LOCKED` 和 `NOWAIT` 分别适合什么场景？
**提示**：`SKIP LOCKED` 适合任务队列式认领（跳过被锁行拿别的）；`NOWAIT` 适合"锁不上就立刻放弃"的快路径；普通等待适合真要排队且持锁短的场景。

**追问 2**：把热点行更新拆成"先 update 内存队列再批量落库"是解法吗？
**提示**：是方向但引入新问题：内存队列丢数据风险与多实例一致性，通常落地为 Redis 原子扣减 + 异步落库（Q1005 秒杀方案），落库侧再配幂等。

## 背诵要点
- 雪崩公式：持锁时长 × 到达速率 = 锁等待积压；默认 lock_wait_timeout=50s 会先耗尽连接池。
- 事务内禁止外部 IO；补偿走事务发件箱，任务类用 SKIP LOCKED 认领。
- OLTP 写路径 lock_wait_timeout 降到 3-5 秒快速失败；trx_started 超 5 秒告警。
