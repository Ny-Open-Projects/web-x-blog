### Q6613 · 时序分区表保留窗口与磁盘增长容量账

难度：P6 ｜ 标签：容量规划 / 分区表 / 保留策略

**问**：埋点事件表按天 RANGE 分区，写入日均 40GB（含索引），要规划保留窗口。业务说"留一年"，磁盘预算只给了 8TB。这道容量账怎么算？保留窗口、DROP PARTITION 节奏、索引与 TOAST 开销分别怎么进模型？

**答**：
- **结论**：容量模型五项：① 数据日增量 = 峰值系数 × 日均值，埋点类要按周内波动与大促峰值取 P99 日增量（不能按月均）；② 索引与膨胀开销——表数据、二级索引（通常 +30%~50%）、fillfactor 与死元组膨胀（+10%~20%）、TOAST 与 WAL 临时占用；③ 保留窗口 = 预算 / 单日全成本，8TB ÷ (40GB × 1.6 开销系数 × 峰值 1.3) ≈ 97 天，所以"留一年"在 8TB 内做不到，要么压缩/归档要么加预算；④ 回收节奏——DROP PARTITION 是元数据操作、秒级且空间立即归还文件系统，而 DELETE 大范围删除空间不归还还要 vacuum（见 Q6542），所以保留策略必须按分区裁剪设计，单分区大小控制在 daily 量级、分区总数留意 planner 开销（Q6576）；⑤ 归档层——过期分区先 `DETACH`/导出到对象存储（Parquet+压缩后通常压到原 1/5~1/10）再 drop，归档存储成本远低于在线块存储。
- **取舍**：窗口选择：热数据在线（可查、可 join）+ 冷数据归档（SQL on Parquet/对象存储按扫描计费）双层。窗口不是越长越好：90% 查询落在最近 30~60 天，把保留窗口从 365 砍到 90 天，在线存储成本降 75%，少数长尾查询走归档层。DROP PARTITION 调度放低峰期且限并发（同时 drop 多个大分区会引发大量文件 unlink 与 checkpoint 压力）。
- **实战**：模型代码化并每日巡检：用 `pg_total_relation_size` 按分区聚合实测单日全成本，与模型偏差 >15% 触发复核；磁盘水位双阈值（70% 预警/85% 停写演练）；容量评审每季度重跑，埋点增长率（新 App 版本、新事件）单独列项，避免"按去年线性外推"低估。

```python
# 分区保留窗口容量账：峰值系数 + 存储开销系数 + 归档压缩比
# 基线：Python 3.9+ 标准库；真实环境用 pg_total_relation_size 按分区实测校准
from dataclasses import dataclass


@dataclass
class Budget:
    daily_gb: float          # 日均写入（表数据）
    peak_factor: float       # P99 日增量/日均
    index_overhead: float    # 二级索引+膨胀综合系数
    budget_gb: float
    archive_ratio: float     # 归档压缩比（Parquet+zstd）
    archive_price_factor: float  # 归档单价/在线单价


def full_cost_per_day(b: Budget) -> float:
    return b.daily_gb * b.peak_factor * (1 + b.index_overhead)


def retention_days(b: Budget) -> float:
    return b.budget_gb / full_cost_per_day(b)


def annual_cost_gb(b: Budget, hot_days: int) -> tuple[float, float]:
    """返回 (在线占用, 归档占用)，热窗内在线、其余归档。"""
    per_day = full_cost_per_day(b)
    hot = per_day * hot_days
    cold = per_day * (365 - hot_days) * b.archive_ratio
    return hot, cold


def main() -> None:
    b = Budget(daily_gb=40, peak_factor=1.3, index_overhead=0.5,
               budget_gb=8 * 1024, archive_ratio=0.12, archive_price_factor=0.25)

    r = retention_days(b)
    assert 90 < r < 110, r            # 8TB 只能撑 ~97 天，"留一年"不成立
    print(f"纯在线可留 {r:.0f} 天 —— 留一年需 {(full_cost_per_day(b)*365)/1024:.1f}TB，超预算")

    hot, cold = annual_cost_gb(b, hot_days=90)
    assert hot <= b.budget_gb
    # 90 天热窗 + 其余归档：在线 8.3TB 边缘，需把预算抬到 10TB 或热窗收到 60 天
    hot60, cold60 = annual_cost_gb(b, hot_days=60)
    assert hot60 < hot
    print(f"热窗90天: 在线 {hot/1024:.1f}TB + 归档 {cold/1024:.1f}TB(压缩{b.archive_ratio})")
    print(f"热窗60天: 在线 {hot60/1024:.1f}TB，长尾查询走归档按扫描计费")

    # DROP PARTITION 回收是秒级元数据操作，与 DELETE 的对比写在复盘追问里
    assert full_cost_per_day(b) == 40 * 1.3 * 1.5
    print("OK: 每日全成本 = 日均 x 峰值系数 x (1+索引开销)")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么保留策略必须靠 DROP PARTITION 而不是定时 DELETE？
→ 一句话提示：DELETE 只标死元组，空间要 vacuum 才归还且期间产生大量 WAL；DROP/DETACH PARTITION 是删文件级操作，秒级完成、空间立即归还，且不产生逐行 WAL。

**追问 2**：归档层用什么格式与查询方案，成本怎么再压一档？
→ 一句话提示：分区导出为 Parquet（列存+zstd，压缩比 8~12x）放对象存储冷层，DuckDB/Trino 按扫描计费查询；生命周期规则自动转储，取回费用在模型里单列，避免"归档了却频繁取回"反亏。

## 背诵要点
- 单日全成本 = 日均写入 × 峰值系数(P99 非月均) × (1 + 索引/膨胀开销 ~0.5)；示例账：40GB 日均 → 8TB 只能撑约 97 天。
- 保留策略用分区裁剪（DROP/DETACH，秒级、空间立即归还），不用大范围 DELETE（不还空间 + WAL 放大 + vacuum 压力）。
- 双层结构：热窗 60~90 天在线，其余 Parquet 归档对象存储（压缩 8~12x），长尾查询按扫描计费；容量模型用实测分区大小每日校准。

## 复盘追问
- "按去年线性外推"为什么会低估？提示：埋点增长率来自新版本埋点上线、新事件维度、用户新增三个非线性因子，容量评审要按来源分项预测而不是总量外推。
- 同时 DROP 多个大分区会有什么次生影响？提示：大量文件 unlink + checkpoint/fsync 压力 + 备份任务恰好扫到空分区，回收要错峰限并发并在备份窗口外执行。
