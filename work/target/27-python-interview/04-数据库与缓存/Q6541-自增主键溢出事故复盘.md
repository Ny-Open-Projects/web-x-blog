### Q6541 · 自增主键溢出事故复盘：一张日志表的 id 用完了怎么办？

> 难度:★★★ | 标签:事故复盘, 主键设计, 容量规划

**问**：某张按月写入 3 亿行的日志表用 INT UNSIGNED 做自增主键，某天深夜开始写入全部失败。为什么会发生？怎么提前发现？应急与长期方案分别是什么？

**答**：结论：INT UNSIGNED 上限是 **42.9 亿**，自增计数器触顶后 INSERT 报 "Duplicate entry / Out of range value"，写入停滞——这是"增长曲线没进容量规划"的经典事故。应急用 `ALTER TABLE ... MODIFY id BIGINT`（InnoDB 在线 DDL，注意大表仍有时长与磁盘翻倍风险）；长期方案是 BIGINT 或提前换雪花 ID，且监控必须盯**自增剩余比例**而不是只盯行数。

机理与实战：
- **为什么突然全挂**：自增是单调的，触顶是" cliff 不是 slope"——前 99.9% 一切正常，最后一条之后全失败。监控行数对触顶没有预警价值，必须监控 `AUTO_INCREMENT 列的最大值 / 类型上限`。
- **改列的代价**：MySQL 8.0 的 INSTANT DDL 不适用于改列类型，COPY 路线意味着锁表时长 = 全表重建时长；PG 里改 int→bigint 也是全表重写。所以应急顺序是：先限流/停非关键写入 → 低峰窗口改列 → 验证自增计数器延续。
- **预防口径**：日增量 × 剩余空间 = 剩余天数，剩余天数 < 180 天就要立项迁移；新表一律 BIGINT，日志/流水类预估超 40 亿行直接上雪花 ID + 分表。
- **关联坑**：自增接近上限时 `MAX(id)+1` 类手工赋值、binlog 里 int 截断、下游消费端按 int 解析都会先炸——迁移要连 DTO/协议一起改。

```python
# 基线:Python 3.10+;纯标准库,模拟自增主键剩余寿命估算与触顶检测
from __future__ import annotations

LIMITS = {
    "INT": 2**31 - 1,            # 有符号 21.4 亿
    "INT_UNSIGNED": 2**32 - 1,   # 无符号 42.9 亿
    "BIGINT": 2**63 - 1,
}


def remaining_days(auto_inc: int, col_type: str, daily_rows: int) -> int:
    """按日增量估算主键剩余天数。"""
    cap = LIMITS[col_type]
    left = cap - auto_inc
    if left <= 0:
        return 0
    return left // daily_rows


def check(auto_inc: int, col_type: str, daily_rows: int, threshold_days: int = 180) -> str:
    """门禁:剩余天数低于阈值即告警。"""
    ratio = auto_inc / LIMITS[col_type]
    if auto_inc >= LIMITS[col_type]:
        return f"触顶!写入失败,立即应急改 BIGINT"
    days = remaining_days(auto_inc, col_type, daily_rows)
    if days < threshold_days:
        return f"[告警] 已用 {ratio:.1%},剩余 {days} 天(<{threshold_days}),立项迁移"
    return f"健康:已用 {ratio:.1%},剩余 {days} 天"


def demo() -> None:
    # 事故现场:INT UNSIGNED,已写到 42.5 亿,日增 3 亿
    print(check(4_250_000_000, "INT_UNSIGNED", 300_000_000))  # 剩不足 1 天,告警
    print(check(4_294_967_295, "INT_UNSIGNED", 300_000_000))  # 触顶
    # 换 BIGINT 后同水位
    print(check(4_294_967_295, "BIGINT", 300_000_000))        # 健康
    # 门禁演示
    assert "告警" in check(4_250_000_000, "INT_UNSIGNED", 300_000_000)
    assert "触顶" in check(LIMITS["INT_UNSIGNED"], "INT_UNSIGNED", 1)
    print("自增主键寿命估算:盯剩余天数而非行数 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：为什么不用 "UPDATE id = id + 偏移" 把现有 id 平移腾出空间？
答：改 id 会级联更新所有外键引用和二级索引，等于全表重写加业务数据变更，风险远高于 MODIFY 成 BIGINT；且 UPDATE 期间自增计数器行为不可控。平移只适合小表救急，大表一律改类型。

**追问二**：分表后自增 ID 怎么保证全局唯一？
答：要么每张分表用不同自增步长/起始值（步骤 2、起始 1/2），要么放弃数据库自增改应用层发号（雪花 ID、号段模式从发号表批量取区间）。雪花要处理时钟回拨，号段模式要处理发号服务单点——两条路线都要在面试里给出取舍。

## 背诵要点
- INT UNSIGNED 上限 42.9 亿，触顶是"断崖"不是"缓坡"：监控自增剩余比例与剩余天数（日增量×剩余空间，<180 天立项）。
- 应急 = 低峰 MODIFY 成 BIGINT（COPY 路线全表重建，先停写/限流）；UPDATE id 平移不可取（外键级联+索引重写）。
- 新表一律 BIGINT；日志流水类预估超 40 亿行直接雪花/号段发号，并连带改下游 DTO 解析位宽。

## 复盘追问
- 事故当晚写入已经失败 2 小时，为什么告警没响？（提示：监控只盯 QPS 与行数增长率，没有"自增剩余天数"指标；触顶后 QPS 归零反而落在正常波动区间里）
- 改 BIGINT 的 DDL 跑到一半主库负载飙升怎么处置？（提示：DDL 前估时长与磁盘翻倍空间，设 kill 阈值，走 gh-ost/pt-osc 类工具控速并保留回退点）
