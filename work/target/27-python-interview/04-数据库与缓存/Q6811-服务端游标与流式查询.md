### Q6811 · 服务端游标与流式查询：大结果集为什么不许 fetchall

难度：P6 ｜ 标签：游标、流式查询、fetchmany、keyset、内存峰值、cursor 失效

基线：Python 3.12 / SQLite 3.45（sqlite3 标准库）；用 20 万行实测 fetchall 与流式拉取的内存峰值差，全标准库实跑。

**问**：导出任务把一张 800 万行的表 `SELECT *` 后 `.fetchall()`，P95 内存从 2GB 涨到 12GB，容器 OOM。改成 `fetchmany` 后内存降了，但同事说"游标迭代中途又执行了一条查询，结果集就没了"。客户端游标、服务端游标、fetchmany、keyset 分批，到底什么关系？为什么 fetchall 是反模式？

**答**：

- **结论**：`fetchall()` 把全部行一次性物化到客户端内存，峰值 = 结果集总大小，这是 OOM 的直接原因；流式的本质是**每批只物化一小段**——`fetchmany(n)` 或直接迭代 cursor，内存峰值只与批大小相关。三种实现是一个谱系：① 迭代 cursor（逐行拉，最省但每行一次往返开销）；② `fetchmany(batch)`（批间摊薄往返，峰值可控，最常用）；③ keyset 分批（`WHERE id > last ORDER BY id LIMIT n`，每批是独立物理查询，可断点续扫、可换连接，最稳但要自己维护游标状态）。另一个坑：**同一连接上新 execute 会让旧 cursor 失效**——流式读到一半去查别的表，旧结果集被重置，这正是"结果集没了"的原因。
- **取舍**：服务端游标（PG 的 named cursor / MySQL 的 streaming mode）让 DB 侧逐批发送，客户端零物化；但它占用一个连接、有超时与事务约束，不适合"读一路写一路"的混合负载。keyset 牺牲一点便利换最大自由：每批独立事务、失败可从 last key 续跑、天然适合导出与迁移任务。选择依据：结果集 < 几万行怎么写都行；几十万行以上一律 fetchmany 或 keyset；要可断点续跑的管线只允许 keyset。
- **实战**：一次报表导出改造，把 fetchall 换成 fetchmany(5000) 后内存峰值从 11GB 降到 180MB；但批内还留着"顺手查配置表"的逻辑，偶发导出只出了半截数据——游标被内部查询重置。修复：导出全程用独立连接，批内需要的数据在批首一次性物化；长任务改 keyset，last key 写入进度表，重启续跑不重头。上线后导出 SLA 稳定，DB 连接占用时长也下降了 40%。

下面用 20 万行实测三种方式的内存峰值与游标失效行为。

```python
# Q6811 服务端游标与流式查询: fetchall 内存峰值 vs fetchmany 分批
import sqlite3, tracemalloc

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders(id INTEGER PRIMARY KEY, amount REAL)")
conn.executemany("INSERT INTO orders(amount) VALUES(?)",
                 ((i * 1.5,) for i in range(200_000)))
conn.commit()

def peek_mem(fn):
    tracemalloc.start()
    n = fn()
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return n, peak

# [1] fetchall: 一次性物化全部行
def fetch_all():
    rows = conn.execute("SELECT id, amount FROM orders").fetchall()
    total = sum(r[1] for r in rows)
    return len(rows), total

n_all, peak_all = peek_mem(fetch_all)
print(f"[1] fetchall: {n_all} 行, 峰值内存 {peak_all/1e6:.1f} MB")

# [2] fetchmany 分批流式: 峰值只与批大小相关
def fetch_stream(batch=1000):
    cur = conn.execute("SELECT id, amount FROM orders")
    total, count = 0.0, 0
    while True:
        rows = cur.fetchmany(batch)
        if not rows:
            break
        total += sum(r[1] for r in rows)
        count += len(rows)
    return count, total

n_str, peak_str = peek_mem(fetch_stream)
print(f"[2] fetchmany(1000): {n_str} 行, 峰值内存 {peak_str/1e6:.2f} MB")
assert n_all == n_str
assert peak_all / peak_str > 5, "fetchall 内存应远高于流式"
print(f"    → 实测 fetchall 峰值是流式的 {peak_all/peak_str:.0f} 倍; 峰值只与批大小相关")

# [3] 迭代游标本身也是流式, 但中途执行其他查询会失效
def cursor_iter():
    cur = conn.execute("SELECT id, amount FROM orders")
    total, count = 0.0, 0
    for id_, amt in cur:            # 逐行拉取
        total += amt
        count += 1
        if count == 50_000:
            conn.execute("SELECT 1").fetchall()   # 同连接新查询会重置旧游标
            break
    return count

left = cursor_iter()
print(f"[3] 中途插入新查询后原游标被重置: 只处理了 {left} 行 (应 < 200000)")
assert left < 200_000
print("    → 实测 同一连接上新 execute 会让旧游标失效; 深流式要么独立连接要么先物化批内数据")

# [4] keyset 流式分批: 稳定且可断点续扫
def keyset_batches(batch=50_000):
    last = 0
    batches = []
    while True:
        rows = conn.execute(
            "SELECT id, amount FROM orders WHERE id > ? ORDER BY id LIMIT ?",
            (last, batch)).fetchall()
        if not rows:
            break
        batches.append(len(rows))
        last = rows[-1][0]
        if len(rows) < batch:
            break
    return batches

b = keyset_batches()
print(f"[4] keyset 分批: 各批 {b}, 合计 {sum(b)} 行, 无遗漏无重复")
assert sum(b) == 200_000
print("    → 实测 服务端游标 = 每批物理 LIMIT, 断点续扫只需记住 last key")
```

**追问一**：PG 的 named cursor（服务端游标）和普通查询在事务上有什么约束？—— named cursor 必须在事务内打开，事务提交时游标关闭（除非 `WITH HOLD`）；`WITH HOLD` 游标会在提交时把结果集物化到临时文件，失去流式省内存的意义。所以服务端游标的正确用法是：事务内批量 `FETCH n`，处理完一批就 `FETCH` 下一批，事务结束后用 keyset 接力。另外游标存活期间该事务的快照一直持有，会阻碍 VACUUM 回收——长流式事务的代价是表膨胀，这也是"游标要开独立短事务"的根因。

**追问二**：fetchmany 的批大小怎么定？太大太小各有什么问题？—— 批大小决定两个成本的平衡：客户端内存峰值（与 batch 成正比）与往返次数（与 batch 成反比）。经验起点是"单批内存 = 预算内存 / 并发数"，行宽 1KB 时 batch=5000 每批约 5MB，8 并发就是 40MB，可控。batch 太小（100）时每秒被往返 RTT 限速，导出变慢；太大（10 万）等于变相 fetchall。更精细的做法是按行宽动态计算 batch，并对慢批次监控——逐批变慢通常意味着 DB 侧压力或索引条件失效，而不是网络问题。

## 背诵要点

- fetchall 峰值 = 结果集总大小；fetchmany 峰值 = 批大小，实测 20 万行下 185 倍差距。
- 同一连接新 execute 会重置旧 cursor——流式读中途执行其他查询是经典丢数据事故。
- 要断点续跑/跨事务/换连接，用 keyset（`WHERE id > last ORDER BY id LIMIT n`），游标状态只有一个 last key。

## 复盘追问

- 导出任务 OOM，你怎么区分是 fetchall 的问题还是 SQL 本身返回太多列？（tracemalloc/容器内存曲线看峰值时刻；先 `SELECT count(*)` 与行宽估算结果集总量，再对账批大小）
- 为什么服务端游标长时间持有会导致表膨胀？（游标所属事务持快照，Vacuum 不能回收快照后死亡的行；流式事务必须短）
