### Q6780 · 凌晨写入集体报错：分区滚动 TTL 的预建断供事故

难度：P6 ｜ 标签：分区表、TTL、滚动分区、预建调度、写入失败

基线：Python 3.12；模拟分区表的预建窗口调度、调度作业断供导致的写入失败与恢复剧本、过期分区 DROP 回收，全标准库实跑。

**问**：日志表按天分区 + TTL 十天，某天凌晨业务写入突然集体报错 `no partition of table found for row`——前一天还一切正常。分区表的滚动 TTL 为什么要"预建未来分区"？预建调度作业挂掉时为什么不会立刻炸、而是延迟数天后才炸？恢复与防复发的完整剧本是什么？

**答**：
- **结论**：分区 TTL 的日常运转是两个异步作业：**预建作业**（每天创建未来 N 天的分区）与**过期作业**（DROP 超过保留期的旧分区）。预建是"提前几天下单"，所以调度挂掉**不会立刻暴露**——未来分区有存量余量，写入照常成功；余量按天耗尽，数天后第一个"写入今天分区"的请求撞上不存在的分区，**集中报错**。这就是它比"调度挂了立刻报错"更凶险的原因：故障与根因间隔数天，事发时调度日志早被滚动清掉。与行级删除对比：DROP 分区是秒级元数据操作、不产生行级碎片（Q6759/Q6770 的页级回收账），这是分区 TTL 的核心收益；但收益的另一面就是**可用性依赖预建作业的健康度**——分区表把"磁盘回收"变成了"一个必须永远健康的小作业"。
- **取舍**：① 预建窗口 N=3~7 天：窗口越长抗作业故障越久，但分区元数越多（PG 分区数千个后 planner 锁开销可感）；② 自动补建兜底：写入侧捕获"no partition"错误后自动建分区重试（PG 写触发器/中间件层做），是最后的保险丝，不该是唯一防线；③ 过期 DROP 也要监控：DROP 大分区持锁（PG 父表锁）可能阻塞写入，低峰执行；④ 直接用原生分区生命周期（MySQL 无原生，PG 用 pg_partman）：第三方调度器本身又成为依赖，其失败要纳入同一套告警。
- **实战**：① **核心告警是"剩余覆盖天数"**（未来 N 天内每天是否都有分区），预建作业失败告警只是前置信号；② 预建作业幂等：重复执行不重复建（本卡 ensure_window 的 if-not-exists 语义）；③ 写入失败的用户体验预案：报错信息里带分区缺失日期与修复 SQL，值班能秒级补；④ 演练：把预建作业停掉一次，验证"剩余覆盖天数"告警的触发时间早于写入故障（Q6563 RTO/RPO 演练同族）。

```python
"""Q6780 分区滚动 TTL: 预建窗口断供 -> 未来写入报 no partition found, 恢复剧本。"""
import datetime as dt

DAY = dt.timedelta(days=1)
PRECREATE_AHEAD = 3              # 预建未来 3 天分区


class PartitionedTable:
    def __init__(self, now: dt.date):
        self.partitions: set[dt.date] = set()
        self.now = now

    def ensure_window(self, *, healthy: bool) -> int:
        """预建调度: healthy=False 模拟调度器挂掉."""
        if not healthy:
            return 0
        created = 0
        for i in range(1, PRECREATE_AHEAD + 1):
            d = self.now + i * DAY
            if d not in self.partitions:
                self.partitions.add(d)
                created += 1
        return created

    def insert(self, ts: dt.datetime) -> str:
        d = ts.date()
        if d not in self.partitions:
            return f"ERROR: no partition of table for row ({d})"
        return "OK"

    def drop_expired(self, retention_days: int) -> list[dt.date]:
        dropped = [d for d in sorted(self.partitions)
                   if d < self.now - dt.timedelta(days=retention_days)]
        for d in dropped:
            self.partitions.discard(d)
        return dropped


if __name__ == "__main__":
    t = PartitionedTable(now=dt.date(2026, 11, 20))
    # 历史存量: 11-08/11-09 的旧分区
    t.partitions |= {dt.date(2026, 11, 8), dt.date(2026, 11, 9)}
    t.ensure_window(healthy=True)
    print(f"11-20 预建: 分区覆盖 {sorted(d.isoformat() for d in t.partitions)}")

    # 预建作业挂了 4 天
    for _ in range(4):
        t.now += DAY
        t.ensure_window(healthy=False)
    r = t.insert(dt.datetime(2026, 11, 25, 8, 0))
    print(f"预建断供 4 天后写入 11-25: {r}")

    # 恢复: 手动补建当天分区 + 重启调度
    t.partitions.add(dt.date(2026, 11, 25))
    t.ensure_window(healthy=True)
    r2 = t.insert(dt.datetime(2026, 11, 25, 9, 0))
    coverage = (max(t.partitions) - t.now).days
    print(f"补建后写入: {r2}, 预建覆盖 {coverage} 天 (告警阈值参考)")
    dropped = t.drop_expired(retention_days=10)
    print(f"TTL 滚动: 过期 DROP 分区 {sorted(d.isoformat() for d in dropped)} "
          f"(秒级, 不产生行级删除)")
    ok = ("ERROR" in r and r2 == "OK" and coverage >= PRECREATE_AHEAD
          and dt.date(2026, 11, 8) in dropped)
    print(f"校验: 断供复现 + 补建恢复 + 滚动回收 -> {'通过' if ok else '异常'}")
    print("结论：分区表 TTL 的死穴是'预建断供'——分区不存在直接写入失败;")
    print("      预建窗口 N 天 + 剩余覆盖天数是最关键告警, 作业挂了要在窗口耗尽前被找到")
```

**追问一**：为什么不在"写入失败后自动建分区重试"这一层就把问题全解决，还要靠预建作业？

→ 解析：写入侧自动补建是保险丝，不能当主防线，三个原因：① **并发竞态**：多个会话同时撞上缺失分区，都去 CREATE，需要处理"分区已存在"的并发冲突（PG 的 CREATE IF NOT EXISTS 在高并发下仍有锁排队），错误处理路径本身要高可用；② **权限面扩大**：应用账号需要 DDL 权限（建分区），账号分级（Q6555）的原则被打破，且自动化 DDL 是故障放大器（写错分区边界直接污染数据布局）；③ **掩盖**：自动补建让预建作业挂了"无感知"，等哪天补建路径自己也坏了（权限回收、锁超时），故障直接爆发且更难查。正确的层次：预建作业是主防线（有告警、有台账），补建是熔断兜底（触发即告警"主防线已失守"）。任何"自动兜底"都要有"兜底被触发"的可见性，否则兜底就变成静默依赖。

**追问二**：DROP 过期分区与 DELETE 旧数据，在大表上除了速度还有什么账要算？

→ 解析：① **空间回收**：DELETE 是页级标记 + 复用（Q6770），文件不缩；DROP 分区直接释放表文件，空间立即可用——磁盘水位紧张时这是决定性差异；② **复制与备份**：DELETE 百万行产生的 binlog/WAL 会让从库延迟飙升、备份窗口拉长；DROP 只产生一条 DDL，复制秒过（Q6542 同族账）；③ **锁影响**：DROP 分区要父表锁（PG），瞬间阻塞新查询进入，但比 DELETE 的长时间行锁+间隙锁温和得多；④ **代价**：分区粒度固定——TTL 不再是任意天数而是整分区（按天分区最细天级），且分区数本身有 planner 成本。所以选型判据：删除模式与分区边界对齐（整段过期）用分区 TTL，删除模式散乱（按用户 GDPR 删除）只能行级删——先看删除的形状，再选工具。
