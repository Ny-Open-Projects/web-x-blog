### Q6800 · 数据库时钟与应用时钟的口径事故：谁的时间才算数

难度：P6 ｜ 标签：时钟、时间戳、时区、NOW()、timestamptz、单调时钟、窗口查询

基线：PostgreSQL 12+/MySQL 8.0；Python 3.12 用多源时间戳模型复现窗口漏计与排序倒挂，全标准库实跑。

**问**：订单表里 `created_at` 有的一行是应用 `datetime.now()` 写的，有的是 DB `DEFAULT CURRENT_TIMESTAMP` 填的；上线后发现"最近 5 分钟订单"报表偶尔漏单，偶尔又把两分钟前的单算成"未来"，按时间排序的分页还会来回跳。只是时间戳来源不同，为什么能同时造成"漏"和"多"？`NOW()`、`CURRENT_TIMESTAMP`、应用时钟、单调时钟，各自该用在哪？

**答**：

- **结论**：时间戳有四种语义，混用就出事故。① **墙上时钟**（`time.time()`、`datetime.now()`）会因 NTP 校时跳变、且带时区，只适合"给人看的时间"，不适合排序与窗口判定；② **数据库时钟**（`NOW()`/`CURRENT_TIMESTAMP`）是写入时刻的权威源，但 PG 的 `NOW()` 返回**事务开始时间**（同一事务内多次调用不变，见 Q6743），MySQL 的 `CURRENT_TIMESTAMP` 是**语句开始时间**，批量插入/长事务里会得到大量相同值；③ **单调时钟**（`time.monotonic()`）只保证"不倒退"，只适合测间隔，不能当日期；④ **时区**是独立维度：`timestamp` 存字面量、`timestamptz` 存 UTC 按会话时区显示，两者混用会让"同一时刻"比较出 8 小时偏差。事故的根因不是"某个时钟不准"，而是**同一列里混了多个权威源**：写入方时钟偏 +120 秒，它的行会"来自未来"被窗口包含；偏 -2 秒的行会提前掉出窗口；排序键不单调，分页自然跳。
- **取舍**：最稳的方案是**单一权威源 + UTC 存储**：写入时间一律用 DB 的 `CURRENT_TIMESTAMP`（列上 `DEFAULT`），应用只读不写；需要"语句级精确时刻"用 `clock_timestamp()`；跨时区展示在会话层转换，存储层不动。应用生成时间戳的唯一正当理由是"减少一次 DB 依赖/写入路径要脱离 DB"，这时必须满足三条：所有机器同一 NTP 源、启动时用 DB 校准一次偏移并周期校正、存 UTC 且带时区信息。单调时钟只用于超时、耗时、限流窗口这些"间隔"语义，不要拿它生成 `created_at`。
- **实战**：某订单服务的容器镜像里 NTP 没配，三台机器分别漂 -20s、0、+120s。风控的"近 5 分钟交易"查询用应用写入的 `created_at` 与 DB 的 `NOW()` 比较：+120s 那台的单子一写入就"来自两分钟后"，被算进未来窗口且排在列表最前；-20s 那台的单子在 4 分 40 秒时已经掉出窗口，漏了一单。对账时又发现按 `created_at` 排序的分页在翻页时顺序抖动。修复：`created_at` 改为 `DEFAULT CURRENT_TIMESTAMP`、应用不再传值；报表统一用 DB 时间做窗口边界；容器基础镜像加 NTP 并监控偏移。上线后漏单归零，分页也稳定了。

下面用"真实写入时刻 + 各机器偏移"复现漏计、多计与排序倒挂，再对比单一 DB 时钟。

```python
# 多源时间戳: 窗口漏计/多计 + 排序倒挂
DB_NOW = 1_000_000                 # DB 当前时刻(秒)
WINDOW = 300                       # 近 5 分钟
SKEW = {"app-a": -20, "app-b": 0, "app-c": 120}
SERVERS = ["app-a", "app-b", "app-c"]

# 每 30 秒一笔, 真实年龄 0..450 秒; 轮转三台应用机
rows = []
for i, age in enumerate(list(range(0, 451, 30)) + [290, 291, 292]):
    srv = SERVERS[i % 3]
    rows.append({
        "id": i,
        "true_age": age,
        "app_ts": DB_NOW - age + SKEW[srv],
        "srv": srv,
    })

# 真实应命中: 年龄 <= 300
truth = {r["id"] for r in rows if r["true_age"] < WINDOW}
mixed = {r["id"] for r in rows if r["app_ts"] > DB_NOW - WINDOW}
missing = truth - mixed
extra = mixed - truth
print(f"[1] 近 5 分钟窗口: 应命中 {len(truth)} 笔, 混用时钟命中 {len(mixed)} 笔")
print(f"    漏计 {sorted(missing)}, 多计 {sorted(extra)}")
for r in rows:
    if r["id"] in missing or r["id"] in extra:
        print(f"    id={r['id']} 真实年龄 {r['true_age']}s, {r['srv']} 偏移 "
              f"{SKEW[r['srv']]:+d}s → app_ts 相对 DB {r['app_ts'] - DB_NOW:+d}s")
assert missing and extra, "混用时钟必然同时出现漏与多"

# 排序倒挂: 按 app_ts 排 vs 按真实年龄排
by_app = [r["id"] for r in sorted(rows, key=lambda r: -r["app_ts"])]
by_true = [r["id"] for r in sorted(rows, key=lambda r: r["true_age"])]
inv = sum(1 for i in range(len(by_true)) for j in range(i + 1, len(by_true))
          if by_app.index(by_true[i]) > by_app.index(by_true[j]))
print(f"[2] 按应用时间排序与真实顺序的逆序对: {inv} 对")
assert inv > 0

# 单一 DB 时钟: 窗口与排序都精确
db_only = {r["id"] for r in rows if DB_NOW - r["true_age"] > DB_NOW - WINDOW}
print(f"[3] 全部用 DB CURRENT_TIMESTAMP: 命中 {len(db_only)} 笔, "
      f"与真实一致 {db_only == truth}, 逆序对 0")
assert db_only == truth

# 时区口径: naive local(+8) 与 UTC 直接比较, 差 8 小时
TZ_OFFSET_H = 8
naive_local = 1_700_000_000          # 某地墙上时间(当成 UTC 存)
utc_value = naive_local - TZ_OFFSET_H * 3600
print(f"[4] 同一字面量按本地(+8)与 UTC 存储, 相差 "
      f"{abs(naive_local - utc_value) / 3600:.0f} 小时")
assert abs(naive_local - utc_value) == 8 * 3600
print("    → 实测 时间戳事故多半不是'钟不准', 而是同一列混了权威源与时区")
```

**追问一**：既然 DB 时钟权威，为什么 PG 的 `NOW()` 在长事务里会"停住"？什么时候必须用 `clock_timestamp()`？—— `NOW()`/`CURRENT_TIMESTAMP` 返回的是**事务开始时刻**（`transaction_timestamp()` 的别名），PG 这样设计是为了让同一事务内的多个语句看到一致的时间视图，便于可重复读。副作用是：一个开了 10 分钟的事务里批量插入 10 万行，所有行的 `DEFAULT NOW()` 都是 10 分钟前；用 `NOW()` 做"处理耗时"或"分批时间"会得到全相同值。需要"这条语句真实执行的时刻"时用 `clock_timestamp()`（每次调用都取当前），需要"事务一致性时间"时用 `NOW()`。这不是"谁对谁错"，是两种语义，列上默认值应明确选一个。

**追问二**：`timestamp` 和 `timestamptz` 到底怎么选？为什么"都存 UTC"还会错？—— PG 的 `timestamptz` 内部存 UTC 微秒数，写入时按会话 `TimeZone` 解释输入、读取时按会话 `TimeZone` 渲染；`timestamp` 存的是字面量，不带时区语义。选 `timestamptz` 的条件是"这个时刻是全球唯一的一个瞬间"（订单创建、事件发生），它能让不同时区的会话比较出正确结果。`timestamp` 适合"当地时间本身就是语义"的场景（门店 9 点开门、航班当地起飞时间）。"都存 UTC"仍会错的情形是：用 `timestamp` 存了 UTC 字面量，但某个会话按本地时区去比较/渲染，或者应用用 naive datetime 与 DB 的 `timestamptz` 混算——类型系统不会报错，结果偏 8 小时。纪律是：**存储层只用 `timestamptz`（或统一 UTC 的整数微秒），应用层进出都带 tzinfo，展示层才转本地**。

## 背诵要点

- 四种语义别混：墙上时钟会跳变带时区、DB 时钟是写入权威、`NOW()` 是事务开始时间、单调时钟只测间隔。
- 混源的后果是对称的：偏移为正的行"来自未来"被窗口多计，偏移为负的行提前掉出窗口漏计，排序键不单调导致分页抖动。
- 纪律：写入时间单一权威源（DB `DEFAULT CURRENT_TIMESTAMP`）+ 存储 UTC（`timestamptz`）+ 展示层转时区；应用生成时间戳必须 NTP + 偏移校准。
