### Q6555 · 数据库账号分级与密码滚动：双账号零停机换密码

难度：P6 | 标签：权限分级、密码轮换、密钥管理、零停机

**问**：安全审计要求"数据库密码每季度轮换"，但服务 24 小时在线，直接 `ALTER USER ... IDENTIFIED BY` 会导致什么？账号权限为什么要分级？怎么做到换密码不停机、可回滚？

**答**：
- **结论**：直接改密码的瞬间，存量连接池里已认证的连接还能用（认证在建立时完成），但新连接全部认证失败——连接池一收缩或一重启就是全站故障。正确姿势是双账号滚动：创建 `app_v2`（同权限、新密码）→ 此时新旧两把钥匙并行有效 → 逐实例改连接串切到 v2 → 观察认证失败率与连接数 → 禁用（而非删除）`app_v1` 留作回滚通道。账号分级是滚动的 amigo：应用账号只有 DML、报表账号只读、迁移账号才有 DDL——出事的爆炸半径随权限收窄。
- **取舍**：并行窗口期两个账号都能连，安全团队常嫌"不干净"；但这个窗口正是零停机的本钱，压缩手段是提高切换并发度而不是砍掉窗口。禁用优于删除：回滚是 `enable + 改回连接串`，分钟级；删了账号的回滚要走审批重建。
- **实战**：① 密码进密管（Vault/KMS），连接串启动时注入，仓库里只有引用；② 滚动期监控 `auth_fail` 率——突增说明有实例切漏了或用了旧密码重启；③ 权限分级用 `GRANT SELECT ON ... TO report_ro` 这类白名单，禁止"图省事给 ALL PRIVILEGES"。

```python
"""数据库账号分级与密码滚动：双账号并行窗口实现零停机换密码。"""
from dataclasses import dataclass

@dataclass
class Account:
    name: str
    password: str
    roles: frozenset           # 权限分级：读写 / 只读 / 迁移专用
    enabled: bool = True

class Db:
    """模拟数据库的认证与账号表。"""

    def __init__(self):
        self.accounts = {
            "app_v1": Account("app_v1", "pw-old", frozenset({"DML"})),
            "report_ro": Account("report_ro", "pw-ro", frozenset({"READ"})),
            "migrator": Account("migrator", "pw-mg", frozenset({"DDL"})),
        }
        self.auth_fail = 0
        self.active = "app_v1"

    def authenticate(self, name: str, password: str) -> bool:
        acct = self.accounts.get(name)
        if acct and acct.enabled and acct.password == password:
            return True
        self.auth_fail += 1
        return False

db = Db()
print("分级账本：", {n: sorted(a.roles) for n, a in db.accounts.items()})

# 滚动三步：1) 创建 app_v2（同权限、新密码）——此刻两把钥匙都有效
db.accounts["app_v2"] = Account("app_v2", "pw-new", frozenset({"DML"}))
ok1 = db.authenticate("app_v1", "pw-old") and db.authenticate("app_v2", "pw-new")
print(f"并行窗口：新旧账号同时可用 = {ok1}")

# 2) 逐实例把连接串切到 app_v2（先灰度一台，观察认证失败率与连接数）
db.active = "app_v2"
print(f"应用当前账号 = {db.active}")

# 3) 旧账号禁用而非立刻删除——留 7 天作为回滚通道
db.accounts["app_v1"].enabled = False
print("回滚通道：重新 enable + 改回连接串即可分钟级回滚")
print("两条红线：密码进密管不进仓库；auth_fail 突增要告警"
      "（滚动期最常见的事故就是切漏了一个实例）")
```

**追问链**：
1. 追问一层：为什么已建立的连接在改密码后还能用？——MySQL/PG 的认证发生在连接建立（握手）时，服务端改密码不追溯已建立的会话；所以"改完没报错"是错觉，池子收缩或重启才会引爆。这也是为什么滚动要按"实例 × 连接池重建"推进。
2. 追问二层：应用账号为什么不该有 DDL 权限？——DDL 会隐式提交当前事务并绕过 ORM 的迁移门禁；一旦应用代码里有"启动时顺手建表"的逻辑，多实例并发启动会对同一张表并发 DDL 直接锁冲突。迁移权集中到 migrator 账号、由 CI 单点执行。

**背诵要点**：
1. 改密码不追溯存量连接：池子收缩/重启才爆，所以必须双账号并行窗口。
2. 滚动四步：建 v2 → 逐实例切 → 观察 auth_fail → 禁用（非删除）v1 留回滚。
3. 权限分级缩小爆炸半径：应用 DML、报表 READ、迁移 DDL，密管管密码。

**复盘追问**：
1. 滚动完成后第三天夜里出现认证失败风暴，最可能的原因？（某个定时任务/灾备实例还在用旧密码重连——禁用 v1 后它的重连全失败；靠 auth_fail 监控的实例指纹定位）
2. 为什么"密码写进配置中心加密存储"仍不算合规终态？（加密存储只是静态防护，轮换仍要人手改配置；密管 + 运行时注入才能做到轮换无需改任何配置文件）
