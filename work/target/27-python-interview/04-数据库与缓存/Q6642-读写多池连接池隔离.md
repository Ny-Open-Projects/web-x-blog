### Q6642 · 读写多池连接池隔离与路由后治理

难度：P6 | 标签：连接池、读写分离、容量规划

**问**：接了读写分离之后，一个连接池还够用吗？为什么要拆"读池/写池"？拆完之后每个池的参数怎么定、水位怎么看？

**答**：
- **结论**：读写分离后必须拆池。理由：读流量走从库（可水平扩展），写流量只能打主库（容量刚性）——共用一个池时，读高峰把池占满，写请求借不到连接，主库明明空闲业务却写不进去。写池按"主库写并发上限"定（小而稳，比如 10-20），读池按"从库总读容量"定（大而弹）。每个池独立配 `pool_size/max_overflow/pool_timeout`，独立看水位。
- **取舍**：双池的成本是应用代码必须显式选择路由（或依赖中间件）；事务内一旦写了就必须锁死主库连接——"事务里先读后写"的连接漂移是拆池后最常见的 bug，要求事务入口就绑定写池。多从库场景进一步拆"每从库一池"，配合健康摘除。
- **实战**：水位监控三件套：`pool.status()`（in pool / checked out）、获取等待次数、pool_timeout 异常率；告警阈值定在"checkedout 接近 size+overflow"而不是打满之后。压测定参：灰度压测下读池 P99 借还时间，池大小 = 峰值并发 × 单次借还时长。

```python
import os, tempfile
from sqlalchemy import create_engine, text
from sqlalchemy.pool import QueuePool

db = os.path.join(tempfile.mkdtemp(), "t.db")
write_engine = create_engine(f"sqlite:///{db}", poolclass=QueuePool,
                             pool_size=2, max_overflow=0, pool_timeout=1)
read_engine = create_engine(f"sqlite:///{db}", poolclass=QueuePool,
                            pool_size=8, max_overflow=4, pool_timeout=1)
with write_engine.begin() as c:
    c.execute(text("CREATE TABLE t (x INT)"))
    c.execute(text("INSERT INTO t VALUES (1)"))

def read_all():
    with read_engine.connect() as conn:
        return conn.execute(text("SELECT * FROM t")).fetchall()

def write(v):
    with write_engine.begin() as c:
        c.execute(text("INSERT INTO t VALUES (:v)"), {"v": v})

write(2)
print("读路径:", read_all())
print("写池水位:", write_engine.pool.status())
print("读池水位:", read_engine.pool.status())
print("要点：读写分池让写池不被读流量挤占；pool.status() 是水位告警的数据源")
```

**追问链**：
1. 追问一层：事务里"先读后写"的连接漂移具体怎么发生？（读时从读池借连接、写时又向写池借——两个连接看不到彼此未提交的数据，事务语义被破坏；必须事务入口绑定单池）
2. 追问二层：PgBouncer 事务池化模式下还能再拆应用侧池吗？（中间件已做池化，应用侧应缩小 pool_size 甚至用 1，否则双重池化导致连接风暴）

**背诵要点**：
1. 读写分离必须拆池：写池小而稳，读池大而弹。
2. 事务入口绑定写池，防"先读后写"的连接漂移。
3. 水位看 pool.status() + 等待次数，告警在接近上限而非打满。

**复盘追问**：
1. 主库 CPU 空闲但写入超时，写池和读池你会先查哪个？（读流量挤占共享池/写池参数过小）
2. 双池后为什么等待次数反而上升？（路由错误把写打到读池，读池拒绝写连接）
