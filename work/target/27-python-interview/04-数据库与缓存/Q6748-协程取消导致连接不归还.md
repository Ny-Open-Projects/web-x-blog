### Q6748 · 协程被取消，连接没归还：asyncpg 池三天耗尽

难度：P7 ｜ 标签：asyncio、CancelledError、连接池、超时

基线：Python 3.12；`asyncio.Semaphore` + `Task.cancel()` 模拟 asyncpg/aiomysql 的池语义。

**问**：异步服务用 `conn = await pool.acquire()` … `await pool.release(conn)` 的写法，接入了请求超时（`asyncio.wait_for`）后，池的"在用连接数"每天涨一点，三天后打满，所有请求卡在 `acquire`。日志里没有任何异常，只有一堆 `TimeoutError`。连接去哪了？

**答**：
- **结论**：`asyncio.wait_for` / `asyncio.timeout` 超时会向协程**注入 `CancelledError`**，它在 `await` 点抛出，直接跳过后面的 `release`。更关键的是 `CancelledError` 在 3.8+ 继承自 `BaseException`，**`except Exception` 捕获不到**，所以"我明明包了 try/except"也会漏。每次超时就漏一条连接，直到 `pool_size` 用完，后续 `acquire` 永远等不到。
- **取舍**：正确写法只有一种：`try/finally` 释放（`finally` 对 `BaseException` 也生效），或者用异步上下文管理器 `async with pool.acquire() as conn:`。不要在 `finally` 里再 `await` 长时间操作（取消状态下再次 await 可能立刻再抛）；`release` 必须是同步的或被 `shield` 保护。另一个坑：`asyncio.shield` 保护的是"不被取消"，不是"一定执行完"，在事件循环关闭时仍可能丢。
- **实战**：① 池的 `acquire` 用 `asyncio.timeout` 包住并设上限，拿不到就快速失败而不是无限排队；② 监控 `pool.get_size() - pool.get_idle_size()` 的曲线，单调上升就是泄漏；③ 在 `release` 里打点，对比 `acquire` 次数，差值即泄漏数；④ 代码规范禁止裸 `acquire`，CI 里用 grep/ast 检查 `pool.acquire()` 是否在 `async with` 或 `try/finally` 内。

```python
"""取消点跳过 release：bad vs good，以及反复超时如何打满池。"""
import asyncio
from contextlib import suppress


class Conn:
    def __init__(self, pool: "Pool") -> None:
        self.pool = pool
        self.closed = False

    def close(self) -> None:
        if not self.closed:
            self.closed = True
            self.pool.release()


class Pool:
    def __init__(self, size: int) -> None:
        self.size = size
        self.in_use = 0
        self._sem = asyncio.Semaphore(size)

    async def acquire(self) -> Conn:
        await self._sem.acquire()
        self.in_use += 1
        return Conn(self)

    def release(self) -> None:
        self.in_use -= 1
        self._sem.release()

    @property
    def idle(self) -> int:
        return self.size - self.in_use


async def handler_bad(pool: Pool, started: asyncio.Event) -> None:
    conn = await pool.acquire()
    started.set()
    await asyncio.sleep(10)          # 这里被取消 -> 下一行永远不执行
    conn.close()


async def handler_good(pool: Pool, started: asyncio.Event) -> None:
    conn = await pool.acquire()
    started.set()
    try:
        await asyncio.sleep(10)
    finally:
        conn.close()                 # finally 对 BaseException 也生效


async def cancel_after_start(handler, pool: Pool) -> None:
    started = asyncio.Event()
    task = asyncio.create_task(handler(pool, started))
    await started.wait()
    task.cancel()
    with suppress(asyncio.CancelledError):
        await task


async def main() -> None:
    for handler in (handler_bad, handler_good):
        pool = Pool(size=3)
        for _ in range(3):           # 连续三次超时
            await cancel_after_start(handler, pool)
        print(f"{handler.__name__:<14} in_use={pool.in_use} idle={pool.idle}")

    # 泄漏到打满后，acquire 永远拿不到
    pool = Pool(size=2)
    for _ in range(2):
        await cancel_after_start(handler_bad, pool)
    print("\n泄漏后 in_use =", pool.in_use)
    try:
        conn = await asyncio.wait_for(pool.acquire(), timeout=0.1)
        print("意外拿到连接", conn)
    except asyncio.TimeoutError:
        print("acquire 超时 -> 池已打满，且没有任何异常日志")
    print("结论：CancelledError 是 BaseException；释放只能写在 finally 或 async with 里")


if __name__ == "__main__":
    asyncio.run(main())
```

**追问一**：`async with pool.acquire()` 就万无一失了吗？

→ 解析：它等价于 `try/finally`，确实能覆盖取消，但释放动作本身可能是异步的（`await pool.release(conn)`）。如果协程已处于取消状态，`finally` 里的 `await` 会立刻再抛 `CancelledError`，导致"释放到一半"。asyncpg 的 `pool.release()` 是同步的，aiomysql 的 `conn.close()` 也不是协程，所以通常安全；但若封装层在 `release` 里做了 `await`，就必须 `await asyncio.shield(release_task)` 并考虑事件循环关闭时的兜底。原则：**finally 里只做不依赖 await 的清理**。

**追问二**：为什么"泄漏"通常没有异常堆栈，排查特别慢？

→ 解析：取消是**正常的控制流**，`CancelledError` 被 `wait_for` 吞掉并转成 `TimeoutError` 返回给调用方；上层看到的就是"这次请求超时了"，符合预期。连接对象还活着（被池的 `in_use` 集合引用），GC 不会回收，`__del__` 也不会触发。唯一的信号是池的计数曲线。所以异步服务的可观测性里，"池 in_use / 排队数"必须是第一屏指标，比错误率更早暴露这类问题。
