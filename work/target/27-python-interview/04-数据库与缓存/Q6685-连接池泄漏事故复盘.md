### Q6685 · 连接池泄漏事故复盘：rows_in_use 单调增长三天后打满

难度：P6 ｜ 标签：事故复盘、连接池、资源泄漏
基线：SQLAlchemy 2.0（`QueuePool`，`pool_size`/`max_overflow`/`pool_timeout`）；psycopg/PyMySQL。

**问**：上线一个新服务三天后突然全量报 `QueuePool limit of size 10 overflow 20 reached, connection timed out`。监控里"在用连接数"从上线起就是一条**单调上升直线**。什么是连接池泄漏？如何定位到具体泄漏代码？

**答**：**结论**：泄漏 = 取出的连接**从未归还**。连接池是租借模型：`acquire` 后必须 `release`（或由上下文管理器归还），异常路径忘了归还、长事务一直握着、session 在闭包里被引用住，都会让"在用数"只增不减。定位三招：① 看**在用数曲线形状**——随请求量线性增长且从不回落的是泄漏，随流量波动的是容量不足，区分这两者是第一判断；② SQLAlchemy 打开 `pool` 的日志或用 `QueuePool.status()` 采样在用/排队数，对持有最久的连接打"借出时长"分布；③ 若池支持，注册 checkout/checkin 事件记录 `traceback`，借出超过阈值未归还的栈直接指到泄漏代码行。

**取舍**：两个止血手段要分清：`pool_timeout` 报错是"租不到"而不是"没连接"——临时调大 `max_overflow` 只能拖时间，泄漏不修复最终仍打满。`pool_recycle` 与重置也救不了泄漏（泄漏的连接一直"在用"，不进回收）。根因修复路径：所有获取连接的代码强制走上下文管理器（`with engine.connect() as conn:` / `async with session.begin()`），代码评审门禁禁掉裸 `engine.connect()` 赋值给局部变量后跨函数传递。

**实战**：用标准库实现一个带泄漏检测的最小连接池，直观看到泄漏信号：

```python
# 带泄漏检测的最小连接池（模拟 QueuePool 语义）
import time, threading
from collections import deque

class LeakyPool:
    def __init__(self, size=3, timeout=2):
        self._free = deque(f"conn{i}" for i in range(size))
        self._in_use = {}          # conn -> (借出时刻, 借出栈摘要)
        self._timeout = timeout
        self._lock = threading.Lock()

    def checkout(self, caller: str):
        deadline = time.monotonic() + self._timeout
        while True:
            with self._lock:
                if self._free:
                    c = self._free.popleft()
                    self._in_use[c] = (time.monotonic(), caller)
                    return c
            if time.monotonic() > deadline:
                raise TimeoutError(
                    f"pool exhausted: in_use={len(self._in_use)} "
                    f"最久持有: {max(self._in_use.items(), key=lambda kv: kv[1][0])[0]}")
            time.sleep(0.05)

    def checkin(self, c):
        with self._lock:
            self._in_use.pop(c, None)
            self._free.append(c)

    def leak_report(self, threshold_s=1.0):
        now = time.monotonic()
        return {c: (now - t0, caller)
                for c, (t0, caller) in self._in_use.items()
                if now - t0 > threshold_s}

if __name__ == "__main__":
    pool = LeakyPool(size=3)

    # 正常路径：上下文管理器保证归还
    def good_query(i):
        with lease(pool, f"svc{i}"):
            time.sleep(0.01)

    # 泄漏路径：异常时忘了归还
    def bad_query(i):
        c = pool.checkout(f"leaky{i}")
        if i % 2 == 0:
            raise ValueError("业务异常，连接没还")
        pool.checkin(c)

    import contextlib
    @contextlib.contextmanager
    def lease(p, caller):
        c = p.checkout(caller)
        try:
            yield c
        finally:
            p.checkin(c)

    for i in range(10):
        good_query(i)
    print("正常请求后 pool status：在用 =", len(pool._in_use))

    for i in range(3):
        try:
            bad_query(i)
        except ValueError:
            pass
    print("3 次含异常的请求后：在用 =", len(pool._in_use),
          "（每 2 次请求漏 1 条）")
    for c, (held, caller) in pool.leak_report().items():
        print(f"  泄漏嫌疑: {c} 由 {caller} 借出，已持有 {held:.2f}s")
```

**追问 1**：异步应用（asyncpg/SQLAlchemy async）的连接泄漏有什么不同的表现形式？
提示：同步表现为 pool_timeout 报错，异步常见表现为事件循环被占满的假死或 `InvalidRequestError: This session is provisioning`；async 情境下忘 `await session.close()` 更隐蔽，因为异常栈在 task 里被吞。

**追问 2**：为什么说"在用数随流量波动"是容量问题而非泄漏？判定阈值怎么定？
提示：波动的上界与并发峰值一致、请求结束即回落；泄漏是单调增且与累计请求数相关。经验阈值：借出时长 P99 超过业务最长事务时长的 2 倍即报警。

**追问 3**：如果泄漏发生在第三方库内部（比如 ORM 的 identity map 长期持有），怎么处理？
提示：升级/降级库版本对照复现，session 生命周期改为请求级作用域（scoped_session / contextvar），无法修复时用定期 `dispose()` 兜底但要评估进行中事务。

## 背诵要点
1. 泄漏判定看曲线：随累计请求单调增且不回落是泄漏；随并发波动且请求后回落是容量不足。
2. 根因治理：获取连接一律走上下文管理器，禁裸 `engine.connect()` 跨函数传递；checkout 事件记录栈做借出时长监控。
3. 调大 overflow 只是拖延；pool_recycle 救不了泄漏（泄漏连接不进空闲回收）。
