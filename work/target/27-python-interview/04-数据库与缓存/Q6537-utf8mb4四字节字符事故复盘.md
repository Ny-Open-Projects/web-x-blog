### Q6537 · utf8mb4 事故复盘：emoji 存不进、索引建不上、问号读出来

> 难度:★★★ | 标签:MySQL, 字符集, 事故复盘

**问**：用户昵称带 emoji，写入 MySQL 报 `Incorrect string value`，或者"写成功"了但读出来是问号——链路上一共几个坑？utf8 和 utf8mb4 差在哪？为什么改成 utf8mb4 之后，原来能建的字段索引反而建不上了？排序规则选错了有什么连锁反应？

**答**：结论：MySQL 的 `utf8` 实际是 utf8mb3（单字符最多 3 字节），装不下 4 字节的 emoji/生僻字/部分 CJK 扩展字。事故是一条链：**连接字符集 → 列/表字符集 → sql_mode（截断还是报错）→ 索引字节账 → 排序规则语义**，五个点都要对齐才安全。

机理与实战：
- **截断还是报错由 sql_mode 决定**：非严格模式（缺 `STRICT_TRANS_TABLES`）下 4 字节字符被静默替换成 `?`——数据已损、无告警；严格模式才报 `Incorrect string value`。所以 Python 侧要在写入前做编码校验，不能指望 DB 拦。
- **连接字符集要显式声明**：Python 驱动连接串 `charset=utf8mb4`；否则连接层用 latin1/mb3 做转码，列是 mb4 也白搭。
- **索引字节账**：utf8mb4 下 VARCHAR(255) 索引键 = 255×4=1020B，超过老 InnoDB（COMPACT 行格式）767B 上限，建索引直接失败；需 DYNAMIC 行格式 + large prefix（上限 3072B）或缩短列/前缀索引。mb3→mb4 迁移必须连带核查所有索引。
- **排序规则的连锁反应**：`ai`（重音不敏感）排序规则下 `cafe` 与 `café` 是同一个键，唯一约束直接冲突；`general_ci` 与 `0900_ai_ci` 的排序/比较结果不同，换排序规则 = 键语义变化，影响唯一索引、GROUP BY、ORDER BY。
- **排查路径**：`SHOW CREATE TABLE` 看列字符集 → `information_schema.COLUMNS` 全表扫描字符集 → 驱动连接参数 → `SELECT @@sql_mode` → 索引字节账。

```python
# 基线:Python 3.10+;纯标准库模拟 utf8mb3/mb4 的字节账与索引前缀账
# 真实场景:MySQL 字符集链路(连接/列/索引) + sql_mode 严格性决定截断还是报错
from __future__ import annotations

MB3_MAX = 3                              # utf8(mb3) 单字符最多 3 字节
MB4_MAX = 4                              # utf8mb4 单字符最多 4 字节
OLD_INDEX_LIMIT = 767                    # 老 InnoDB(COMPACT 行格式)索引前缀字节上限
NEW_INDEX_LIMIT = 3072                   # DYNAMIC/COMPRESSED + large prefix 的上限


def encode_char(ch: str, max_bytes: int) -> bytes | None:
    """按字符集最大字节数编码;超限返回 None(等价于 DB 拒绝/截断)。"""
    raw = ch.encode("utf-8")
    return raw if len(raw) <= max_bytes else None


def store_column(text: str, max_bytes_per_char: int, strict: bool) -> str:
    """模拟写入 VARCHAR:4 字节字符在 mb3 下报错(严格)或静默替换(非严格)。"""
    out = []
    for ch in text:
        enc = encode_char(ch, max_bytes_per_char)
        if enc is None:
            if strict:
                raise ValueError(f"Incorrect string value: {ch!r} 超出 "
                                 f"{max_bytes_per_char} 字节(需 utf8mb4)")
            out.append("\ufffd")             # 非 strict:静默替换为问号,数据已损
        else:
            out.append(ch)
    return "".join(out)


def index_bytes(varchar_len: int, max_bytes_per_char: int) -> int:
    return varchar_len * max_bytes_per_char


def index_verdict(varchar_len: int, charset_max: int) -> str:
    size = index_bytes(varchar_len, charset_max)
    if size <= OLD_INDEX_LIMIT:
        return f"{size}B <= 767B 老行格式可建"
    if size <= NEW_INDEX_LIMIT:
        return f"{size}B > 767B 需 DYNAMIC 行格式/large prefix(或 3072B 内可建)"
    return f"{size}B > 3072B 必须前缀索引或缩短列"


def demo() -> None:
    nickname = "张三😀"                                  # 😀 = U+1F600,4 字节

    # 事故一:列是 utf8(mb3),严格模式报错 / 非严格模式静默丢数据
    try:
        store_column(nickname, MB3_MAX, strict=True)
    except ValueError as e:
        print("mb3 + 严格模式:", e, "✅")
    stored = store_column(nickname, MB3_MAX, strict=False)
    assert stored == "张三\ufffd"
    print(f"mb3 + 非严格模式:静默替换,存进去 '{stored}'(数据已损,读出来就是问号) ✅")

    ok = store_column(nickname, MB4_MAX, strict=True)
    assert ok == nickname
    print("mb4 完整存取 ✅(Python 端 utf-8 本就是 4 字节超集,连接 charset 要声明 utf8mb4)")

    # 事故二:索引字节账,mb4 让 VARCHAR(255) 索引超老限制
    for charset, label in ((MB3_MAX, "utf8mb3"), (MB4_MAX, "utf8mb4")):
        print(f"VARCHAR(255) @{label}: {index_verdict(255, charset)}")
    assert index_bytes(255, MB4_MAX) > OLD_INDEX_LIMIT
    print("mb3 换 mb4 后老行格式建索引直接失败 -> 迁移要连带升级行格式/前缀索引 ✅")

    # 排序规则影响唯一性:'e' 与 'é' 在 accent-insensitive 下视为相同
    ai_collation = lambda s: s.casefold().replace("é", "e")   # 模拟 ai(重音不敏感)
    assert ai_collation("cafe") == ai_collation("café")
    print("ai 排序规则下 'cafe'/'café' 键冲突 ✅ -> 唯一约束语义随排序规则变化")


if __name__ == "__main__":
    demo()
```

**追问一**：线上已经出现"问号"数据了，能恢复吗？
答：不能无损恢复——问号替换发生在写入时，原始码点已丢失，只能从上游（客户端日志/消息队列/备份）重放；这决定了修复顺序：先改链路（连接+列+sql_mode），再从数据源头回填受影响行，而不是直接 UPDATE 问号字段。

**追问二**：Python 侧 `len()` 校验为什么不可靠？
答：`len()` 是字符数不是字节数，VARCHAR(n) 虽按字符计长，但应用要校验的是"编码后不超过列字符集的字节语义 + 4 字节字符是否被支持"；更可靠的写入前校验是 `s.encode('utf-8')` 逐字符检查字节数，或干脆在入口用正则白名单拦截辅助平面字符（U+10000 以上）。

## 背诵要点
- MySQL "utf8"=utf8mb3（3 字节上限），emoji/生僻字必须 utf8mb4；链路五点：连接、列、sql_mode、索引字节账、排序规则。
- 非严格模式静默替换成问号（数据已损），严格模式才报 Incorrect string value；应用侧须写入前编码校验。
- mb4 让 VARCHAR(255) 索引键 1020B 超 767B 老上限，需 DYNAMIC 行格式/large prefix/前缀索引；ai 排序规则改变唯一约束语义。
