### Q6772 · 主库没报错数据却丢了：半同步复制的超时静默退化

难度：P7 ｜ 标签：MySQL、半同步复制、rpl_semi_sync_master_timeout、RPO、静默降级

基线：Python 3.12；模拟 master 逐笔提交等待 slave ack 的状态机，复现超时次数达到阈值后的静默退化与未确认窗口，全标准库实跑。

**问**：配了半同步复制（AFTER_SYNC），某天主库宕机重启后丢了最近几分钟的数据——半同步不是保证"至少一个从库收到才返回"吗？`rpl_semi_sync_master_timeout` 到期时 MySQL 做了什么？为什么这被称为"静默退化"，应用层和监控层分别怎么兜住它？

**答**：
- **结论**：半同步的语义是**条件性承诺**：每笔事务提交时 master 等从库 ack，**等待时长受 `rpl_semi_sync_master_timeout`（默认 10 秒）约束**；到期仍未收到 ack，master **放弃等待、直接提交并返回成功，此后持续以异步模式运行**（`rpl_semi_sync_master_status` 翻成 OFF）——从库网络抖动/从库 hang/半同步插件积压都会触发。退化不报错、不改应用返回值、不产生任何 SQL 层错误，应用完全无感，这就是"静默"：**从那一笔起，RPO 从 0 悄悄变成了"主库磁盘上还没复制出去的部分"**。主库随后宕机，这部分未复制的事务就丢。与 Q6713 的分界互补：Q6713 讲 ack 在 AFTER_SYNC/AFTER_COMMIT 哪个点位记（丢多少的语义），本卡讲"等不到 ack 时降级"（承诺何时失效）。
- **取舍**：① timeout 设短（如 1 秒）：退化更快、提交延迟小，但偶发抖动就掉异步，半同步形同虚设；设长（如 10 秒）：更扛抖动，但退化前的每笔提交都吃满等待——正常路径 P99 被拖爆；② 退化为异步后**不会自动回到半同步**（部分版本需从库追平+插件状态恢复），要靠监控确认；③ 监控三件套：`Rpl_semi_sync_master_status`（是否 OFF）、`Rpl_semi_sync_master_no_tx`（无 ack 提交数，增长即告警）、`Rpl_semi_sync_master_timeout` 到期计数——**退化必须告警而不是事后查**；④ 对 RPO=0 硬需求：timeout 到期时选择阻塞或 failover（用 `rpl_semi_sync_master_wait_point=AFTER_SYNC` + 告警人工介入），而不是接受降级。
- **实战**：① 半同步配置必须与告警同批上线——只配插件不配监控等于裸奔；② 容量规划时把从库 ack 路径当成关键依赖：从库磁盘 IO 抖动会拖慢 ack（ack 在事务落盘后），从库与主库的磁盘规格别降级；③ 演练：故意断从库网络，验证告警触发时间与业务延迟表现（Q6563 RTO/RPO 演练的子项）；④ 应用层兜底：RPO=0 场景的关键写操作走应用侧双写确认（写 Redis 队列副本 + DB），把"复制层承诺"转成"应用层承诺"，代价是一致性代码复杂度。

```python
"""Q6772 半同步复制超时退化: slave 慢时 master 静默降级为异步, RPO 窗口悄悄放大。"""
ACK_TIMEOUT = 0.05          # rpl_semi_sync_master_timeout (演示: 50ms)
DEGRADE_AFTER = 3           # 连续超时次数阈值后进入退化状态(真实 MySQL 立即退化)


class Slave:
    def __init__(self, ack_delay: float):
        self.ack_delay = ack_delay
        self.received: list[int] = []   # 实际收到的事务


class Master:
    def __init__(self, slave: Slave):
        self.slave = slave
        self.semi_sync = True           # 是否处于半同步状态
        self.timeout_count = 0
        self.degraded_at: int | None = None
        self.committed_unacked: list[int] = []   # 已提交但无 ack(降级窗口)

    def commit(self, xid: int) -> str:
        if self.semi_sync:
            acked = self.slave.ack_delay <= ACK_TIMEOUT
            if not acked:
                self.timeout_count += 1
                if self.timeout_count >= DEGRADE_AFTER:
                    self.semi_sync = False          # 静默退化
                    self.degraded_at = xid
                return "timeout"
            self.slave.received.append(xid)
            return "acked"
        # 异步模式: 只落 binlog 不等 ack
        self.committed_unacked.append(xid)
        return "async"


if __name__ == "__main__":
    slave = Slave(ack_delay=0.08)              # 从库响应劣化, 超过 50ms 阈值
    m = Master(slave)
    results = []
    for xid in range(1, 11):
        results.append((xid, m.commit(xid)))

    print("逐笔提交结果:", results)
    print(f"退化发生在 xid={m.degraded_at}, 之后全部 async")
    lost_window = len(m.committed_unacked)
    print(f"降级后已提交未确认事务: {lost_window} 笔 -> 主库宕机这 {lost_window} 笔丢失")
    ok = (m.degraded_at == 3 and lost_window == 7
          and all(r == "async" for xid, r in results if xid > m.degraded_at))
    print(f"校验: 超时退化路径复现 -> {'通过' if ok else '异常'}")
    print("结论：半同步不是承诺, 超时后静默退化——高可用语义悄悄变弱;")
    print("      监控 Rpl_semi_sync_master_status 与超时计数, 退化必须告警而非靠查")
```

**追问一**：半同步退化后，为什么很多版本不会自动恢复？恢复的正确姿势是什么？

→ 解析：退化后 master 进入异步模式的判断逻辑是"超时即降、追平不自动升"——因为自动升级有隐藏风险：从库刚追平时若 ack 路径仍不稳，立刻切回半同步会造成提交延迟反复抖动（忽快忽慢），且升级瞬间如果从库再次 hang，退化-恢复-退化的振荡比稳定异步更伤。正确姿势：先解决根因（从库 IO、网络、插件积压），确认 `Rpl_semi_sync_master_status=OFF` 的根因消失、从库延迟归零，然后由人工（或受控的自动化）执行 `SET GLOBAL rpl_semi_sync_master_enabled` 翻转重启用，恢复后观察一个高峰时段。把"恢复"也做成受控动作而不是自动动作，是把振荡风险关进变更流程里。

**追问二**：应用层"双写确认"兜底和半同步的 AFTER_SYNC 有什么本质区别？什么时候值得做？

→ 解析：AFTER_SYNC 保证的是"binlog 落到从库后才给客户端成功"——复制层内的强承诺，但 master 进程返回成功到客户端之间仍有一段（客户端视角的）窗口，且退化后承诺整体失效。应用层双写（如先写一份事件到独立持久层再写主库）把承诺上移到应用协议：**哪怕主库连同它的复制链一起丢，应用层副本还在**——它防的不只是复制退化，还包括主库磁盘损坏、误操作 DROP 这类复制会忠实复制的灾难。本质区别：复制层保证防"主从之间的丢失"，应用层副本防"主库自身不可恢复的丢失"。值得做的场景：金融账务、订单支付等 RPO=0 硬需求且灾难半径要求覆盖主库本身；不值得的场景：内容、日志类数据——异步复制的丢失窗口可接受，双写复杂度纯属浪费。
