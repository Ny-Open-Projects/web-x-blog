### Q6504 · 分区表路由与查询裁剪:pruning 为什么失效

> 难度:★★★ | 标签:PostgreSQL, 分区表, 性能

**问**：订单表按月做了 RANGE 分区，本想"查询只扫一个月"，但 EXPLAIN 显示还是全分区扫。分区裁剪（partition pruning）生效的条件是什么？哪些写法会让它静默失效？

**答**：结论：pruning 生效的前提是**计划期或执行期能把谓词里的分区键收敛成确定区间**。范围分区按分区键（如 created_at）的区间切，查询带 `created_at >= A AND created_at < B` 才裁得动。四类典型失效写法：对分区键包函数（`date(created_at) = '2026-11-01'`）、跨列运算、绑定参数在计划期未知（PG 11 前无法 init-plan 裁剪）、以及 ORM 生成的条件里分区键与常量分居 OR 两侧。失效的代价不是"慢一点"，是 planner 把所有分区当候选，几百个分区时计划时间本身就秒级。

实战与设计取舍：
- 分区键必须落在绝大多数查询的 WHERE 里，这是设计承诺而不是实现细节；如果业务一半查询按 user_id、一半按时间，考虑二级组合（分区键时间 + 分区内 user_id 索引），而不是幻想 PG 自动裁剪。
- 计划期裁剪（planner 在生成计划时剔除分区）vs 执行期裁剪（prepared/参数化语句在执行时按实际参数裁）：应用层务必用参数化并保持 PG 12+，让执行期裁剪兜住绑定参数。
- 运维红线：单表分区数建议 < 几百；默认 `enable_partition_pruning=on` 别关；`DEFAULT` 分区会接管不匹配数据，但它会成为并发插入的热点锁点，删除历史分区（`DETACH PARTITION`）前先确认没有长事务引用。
- 事故复盘：报表查询把 `where date(created_at)=%s` 写在 ORM 的 `func.date()` 里，740 个分区全扫 + 计划 1.8 秒。改写成半开区间 `>= 当日 AND < 次日` 后，EXPLAIN 只剩 1 个分区，P95 从 4.2s 降到 120ms。

```python
# 基线:Python 3.9+ 标准库;演示 pruning 生效/失效的谓词改写(可运行)
from datetime import date, timedelta

def safe_day_range(day: date) -> tuple[date, date]:
    """把'某天'改写成半开区间,保住分区裁剪。"""
    nxt = day + timedelta(days=1)
    return day, nxt

def build_where(day: date, bad: bool) -> str:
    if bad:  # 失效写法:函数包裹分区键,planner 无法映射区间
        return f"date(created_at) = '{day.isoformat()}'"
    lo, hi = safe_day_range(day)
    return (f"created_at >= '{lo.isoformat()}' AND "
            f"created_at < '{hi.isoformat()}'")   # 生效写法:半开区间

def partitions_scanned(bad: bool, total: int = 740) -> int:
    """粗模型:坏谓词全分区候选,好谓词只命中当天所在月分区。"""
    return total if bad else 1

if __name__ == "__main__":
    d = date(2026, 11, 1)
    print(build_where(d, bad=False), "->", partitions_scanned(False), "分区")
    print(build_where(d, bad=True), "->", partitions_scanned(True), "分区")
```

**追问**：
- 一层追问：hash 分区和 range 分区怎么选？——range 契合时间序列的"冷热+归档"诉求（可直接 DETACH 掉旧分区归档）；hash 解决单一键值倾斜，但没有时间语义、扩分区数要重分布，归档困难。订单类业务通常 range 时间为主。
- 二层追问：分区键必须包含在主键里（PG 约束）带来的业务别扭怎么解？——主键从 `(id)` 变 `(id, created_at)`，全局唯一性靠"雪花 ID + 应用层查重"或唯一索引局部保证，要向业务方明确"跨月 id 重复不可能（id 含时间戳）"这一前提。
- 三层追问：为什么分区多到几百个时连 INSERT 都变慢？——每个分区都是独立继承子表，路由、锁、relcache 全线性放大；需要几千分区时该上分库/TimescaleDB 这类按 chunk 管理的方案。
