### Q6509 · 服务端游标(server-side cursor)流式读取与内存曲线

> 难度:★★★ | 标签:PostgreSQL, 性能, 内存

**问**：导出一个两千万行的结果集，用 `fetchall` 直接 OOM，改成 ORM 的 `yield_per` 好了一些但还是不稳。服务端游标和客户端 fetch 循环的本质区别是什么？内存曲线应该长什么样？

**答**：结论：默认协议下，客户端执行 SELECT 后**驱动会把整个结果集一口气拉到客户端**再分批喂给你，`yield_per`/`fetchmany` 只是控制"业务侧消费节奏"，服务端结果已经在客户端内存里——这就是 OOM 根因。服务端游标（PG 的 DECLARE CURSOR / psycopg 的 named cursor / SQLAlchemy 的 `stream_results=True`）让服务端持有游标位置，客户端每次 `fetchmany(n)` 只拉 n 行，内存曲线是平的（O(batch)），而不是前高后低的锯齿。

取舍与实战：
- 代价一：连接被独占——游标生命周期内这条连接不能执行其他语句，连接池容量要按"并发流式任务"预留；事务也必须保持打开，长游标 = 长事务 = 快照膨胀风险，所以导出任务要限并发并设 `statement_timeout`/游标超时。
- 代价二：`ITERSIZE`/batch 太小会放大往返次数（2000 万行 × itersize=1 就是 2000 万次 RTT），批量一般 1000~10000 行，配 keyset 分页语义更稳。
- 事故复盘：导服务曾用 `yield_per(1000)` 但没开 stream_results，两千万行导入 Python 进程 3GB 内存触发 OOM Kill，还因为长事务拖住 vacuum。修复：`execution_options(stream_results=True, max_row_buffer=5000)`（SQLAlchemy 2.0 走 psycopg named cursor）+ 任务级并发闸门 + 内存水位自检（rss 超 512MB 主动失败）。
- 与 COPY 的取舍：纯导出（无业务加工）首选 `COPY ... TO STDOUT (FORMAT csv)`，单连接单事务、服务端直出、内存恒定且比游标快数倍；游标方案留给"边读边算"的流式处理。

```python
# 基线:Python 3.9+ / SQLAlchemy 2.0+(stream_results) / psycopg2 named cursor
# 缺库降级:demo 用生成器模拟服务端分批,核心语义相同
import resource, itertools

FAKE_ROWS = ({"id": i, "name": f"u{i}"} for i in range(1_000_000))

def stream_export(rows, batch: int = 5000, rss_limit_mb: float = 512):
    """服务端游标语义:每批只持 O(batch) 内存,超水位即熔断。"""
    it = iter(rows)
    sent = 0
    while True:
        chunk = list(itertools.islice(it, batch))   # 模拟 fetchmany
        if not chunk:
            return sent
        rss_mb = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss / 1024
        if rss_mb > rss_limit_mb:                   # 生产中换成 psutil.Process().memory_info().rss
            raise MemoryError(f"RSS {rss_mb:.0f}MB 超水位,主动熔断")
        yield chunk
        sent += len(chunk)

if __name__ == "__main__":
    total = 0
    for i, chunk in enumerate(stream_export(FAKE_ROWS, batch=100_000)):
        total += len(chunk)
        if i >= 2:                                   # demo 只跑 3 批
            break
    print(f"已流式处理 {total} 行,峰值内存 <512MB")
```

**追问**：
- 一层追问：`yield_per` 和 `stream_results` 什么关系？——SQLAlchemy 2.0 中 `yield_per(n)` 等价于启用 stream_results 并设 `yield_per` 行数；但对不支持服务端游标的驱动（如 MySQLdb 默认）只是客户端缓冲下的分批，要换 `SSCursor`/mysqlclient 的 SSCursor 才真服务端流式。
- 二层追问：长事务持有服务端游标对 PG 的影响？——游标在其事务内可见快照，vacuum 无法回收该快照后的 dead tuple，大导出期间全库膨胀；解法是 statement_timeout + 错峰 + 可重复小事务（keyset 分页多事务，牺牲一致性快照换膨胀安全）。
- 三层追问：怎么测"内存曲线是不是真的平"？——导出任务里按批次采样 RSS 画时间序列；真流式的特征是 RSS 与总行数无关只与 batch 相关，锯齿上升说明客户端缓冲在吞数据。
