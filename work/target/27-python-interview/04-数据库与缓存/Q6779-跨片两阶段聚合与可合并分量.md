### Q6779 · 分片 AVG 直加全错了：跨片两阶段聚合与可合并分量

难度：P6 ｜ 标签：分库分表、两阶段聚合、可合并性、跨片 GROUP BY、对账

基线：Python 3.12；用 4 分片订单数据对比"片级直加"与"两阶段合并"在 AVG、去重计数、GROUP BY 上的正确性，全标准库实跑。

**问**：分库分表后统计"全局平均客单价"，有人把各分片算出的 AVG 直接相加/取平均，报表数字对不上总账。哪些聚合函数可以在分片内先算、哪些必须拆成两阶段？去重计数跨片怎么办？跨片 GROUP BY + ORDER BY + LIMIT 的正确合并姿势是什么？

**答**：
- **结论**：判据是**聚合函数的可合并性（associative + commutative）**。SUM/COUNT/MIN/MAX 可合并：各分片算完直接再 SUM/COUNT/MIN/MAX 一次即得全局值。**AVG 不可合并**：分片 AVG 的平均不等于全局 AVG（各分片行数不同权重不同），必须拆成 **sum 和 count 两个可合并分量**，分片回传 (sum, count)，中心合并后 `sum/count`。**COUNT(DISTINCT) 不可合并**：分片各自去重后相加会把跨片重复用户数重复计，必须**回传成员集合（或 HLL/Sketch 近似结构）**，中心求并集再计数。跨片 GROUP BY：分片按分组键局部聚合（产出可合并分量），中心按键合并——两阶段聚合（map-reduce 的最小形态）。ORDER BY + LIMIT 跨片：分片回传 top-N 时**每行必须带上排序所需的全部分量**，中心归并取全局 top-N，只回传"自己排完的行"而分量不全时归并结果错序。
- **取舍**：① 全局去重的精确成本高（集合跨网传输），大数据量换 HLL/Count-Min Sketch 近似（误差率 ~1-2%），对账类需求必须精确、指标看板类可接受近似——先把精度需求问清楚；② 中间件（ShardingSphere 类）的两阶段聚合自动做，但 COUNT DISTINCT 的中间件实现常退化为"拉明细到中心去重"——大结果集直接打爆中心节点，要看执行计划；③ 中心合并的内存账：GROUP BY 分组键基数大时（千万用户），合并表要落盘/流式归并，不能全内存（Q6750 排行榜内存峰值同族账）；④ 分片内预聚合表（宽表/汇总表）是另一条路：牺牲实时性换中心计算量（Q6655 汇总表账）。
- **实战**：① 报表对账时先写"跨片等价性断言"：全局直查（导出明细重算）vs 两阶段结果，偏差必须为零（近似算法除外，给误差容差）；② 分片回传接口按 (sum, count) 等分量设计，禁止直接回传聚合终值——接口契约决定对账能力；③ 去重指标在报表上明确标注"近似/精确"，别让业务拿 HLL 数字对账；④ 监控中心合并节点的内存与耗时，分组基数增长时提前改流式。

```python
"""Q6779 跨片两阶段聚合: AVG/去重计数不能直加, 必须拆可合并分量。"""
from collections import defaultdict

SHARDS = {
    "s0": [("u1", 100), ("u2", 200), ("u3", 300)],
    "s1": [("u2", 400), ("u4", 500)],
    "s2": [("u1", 600), ("u2", 700)],
    "s3": [("u5", 800)],
}


def wrong_avg() -> float:
    """反例: 每片算 AVG 再直接相加."""
    return sum(sum(v for _, v in rows) / len(rows) for rows in SHARDS.values())


def two_phase_avg() -> float:
    """正解: 每片回传 (sum, count), 全局合并."""
    s = c = 0
    for rows in SHARDS.values():
        s += sum(v for _, v in rows)
        c += len(rows)
    return s / c


def wrong_distinct() -> int:
    return sum(len({u for u, _ in rows}) for rows in SHARDS.values())


def two_phase_distinct() -> int:
    """正解: 每片回传成员集合, 全局求并集."""
    union: set[str] = set()
    for rows in SHARDS.values():
        union |= {u for u, _ in rows}
    return len(union)


def per_user_total() -> dict[str, int]:
    """跨片 GROUP BY: 每片局部聚合 -> 全局按用户合并 (可合并分量 sum)."""
    merged: defaultdict[str, int] = defaultdict(int)
    for rows in SHARDS.values():
        for u, v in rows:
            merged[u] += v
    return dict(merged)


if __name__ == "__main__":
    wa, ta = wrong_avg(), two_phase_avg()
    wd, td = wrong_distinct(), two_phase_distinct()
    truth = sum(v for rows in SHARDS.values() for _, v in rows) / 8
    print(f"AVG  : 片级直加 {wa:.0f} vs 两阶段 {ta:.0f} (真值 {truth:.0f})")
    print(f"去重 : 片级计数直加 {wd} vs 并集 {td} (真用户数 {td})")
    totals = per_user_total()
    print(f"跨片 GROUP BY 合并: {totals}")
    ok = (abs(wa - ta) > 1 and abs(ta - truth) < 1e-9
          and wd > td and td == 5
          and totals["u2"] == 1300)
    print(f"校验: 直加错、两阶段对 -> {'通过' if ok else '异常'}")
    print("结论：分片聚合先拆可合并分量(sum/count/min/max/集合), 中心只做二次合并;")
    print("      AVG 拆 sum+count, 去重计数传集合或 HLL 近似, ORDER BY+LIMIT 合并要带分量")
```

**追问一**：既然 AVG 拆 sum/count 就对了，为什么去重计数不能同样拆成"可精确合并的分量"？

→ 解析：因为 distinct 的信息量是**集合的幂集结构**，不存在固定大小的可合并摘要能精确表达它：两个分片的去重集合合并时必须知道"哪些成员在对方片里也出现过"，而成员本身的基数可能比全量行数还大（用户 ID 全集），精确合并的最小信息单位就是成员集合本身。数学上，精确去重的可合并摘要被证明需要与基数线性相关的空间——这就是 HLL 这类近似算法存在的根本原因：HLL 用固定几 KB 的寄存器给出 ~1-2% 误差，且寄存器可精确合并（OR 操作）。工程分界：**对账/计费走集合精确合并（钱的事不容近似），看板/趋势走 HLL（快与省优先）**——误差预算是架构决策不是实现细节，要在指标定义阶段就定死。

**追问二**：跨片 ORDER BY + LIMIT 的归并为什么容易错？分片回传时最容易漏掉什么？

→ 解析：错误模式是"分片各自排好序取 N 条，中心直接按分片顺序拼接"。两个必错点：① **全局 top-N 未必在各分片的局部 top-N 里**——若分片回传条数恰等于 N，全局第 k 名可能藏在某分片第 N+1 名；正确做法分片回传自己的 top-N（N 不小于全局 N），中心归并后取全局 N，条数 N 越靠尾部越要留余量；② **排序键分量不全**：排序用 ORDER BY price DESC, created_at DESC 时，price 相同的行顺序由 created_at 决定，分片只回传 price 不回传 created_at，中心归并的稳定性由"分片遍历顺序"决定——同 price 行的相对顺序随机，报表每次刷新顺序都变（分页还会重复/丢行，Q2212 分页漂移）。契约：**回传行 = 展示字段 + 排序全部分量 + 唯一标识**，归并用 (排序分量, 唯一键) 做决定论排序——这样跨片分页才可重放、可对账。
