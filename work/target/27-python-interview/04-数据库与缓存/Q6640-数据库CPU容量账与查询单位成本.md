### Q6640 · 数据库 CPU 容量账与查询单位成本模型

难度：P6 ｜ 标签：容量规划 / 成本工程 / 性能

**问**：磁盘 IO 和内存都有明确容量账（Q6545/Q6546），但"CPU 够不够"经常被拍脑袋。怎么给数据库建一个 CPU 容量账：单条查询的 CPU 开销怎么估、实例能扛多少 QPS、再进一步换算成"每千次查询的 CPU 成本"用于架构决策？

**答**：
- **结论**：CPU 容量账三步。第一步**单位开销**：单条查询的 CPU 时间 ≈ 扫描行数相关项（每行处理约 0.1-1 微秒量级，取决于列宽与函数）+ 固定开销（解析/优化约 50-200 微秒，复杂 join 更高）；用 `EXPLAIN ANALYZE`（Q6638）或 pg_stat_statements 的 `total_exec_time`/calls 得到实测均值，别用理论值。第二步**容量上限**：`可用QPS = 核数 × 1e6微秒 / 单查询微秒 × 目标利用率`，目标利用率取 60-70%——数据库 CPU 长期 >80% 会出现排队放大（调度延迟让 P99 恶化远快于线性），且要给备份、vacuum、binlog dump 等后台任务留 20-30% 余量。第三步**单位成本**：`每千次查询CPU成本 = 实例月价 / (可用QPS × 86400 × 30) × 1000`，这个数字用于决策"哪些查询值得优化"——单位成本高 10 倍的报表查询就是优化优先级。反直觉结论：**优化单位 CPU 开销比加核数划算**，因为利用率上限约束下容量是超线性的（排队论），且查询开销小 1 倍 = 副本/核数省一半。
- **取舍**：按峰值规划还是按均值？数据库按 P95 负载规划（峰值日靠限流/降级扛），因为 CPU 排队是雪崩型的；账里还要区分"可延迟负载"（报表、统计）与"不可延迟负载"（交易），错峰（Q7116）能把峰值容量需求砍 30%+。
- **实战**：① pg_stat_statements 按 `total_exec_time` 排序出 TOP 查询单位成本清单，每周复盘；② 用 `taskset`/cgroup 把后台任务绑到独立核，保护在线查询的容量账不被后台侵蚀；③ 扩容前先算"优化收益 vs 加核成本"：TOP1 查询单位开销降一半通常等于加 4 核的钱。

```python
# 数据库 CPU 容量账模型
# 基线: Python 3.9+ 标准库 (微秒口径, 数值为演示量级)
from dataclasses import dataclass


@dataclass
class CpuAccount:
    cores: int
    per_query_us: float       # 单查询实测 CPU 时间
    target_util: float = 0.65 # 给后台任务留余量

    def capacity_qps(self) -> float:
        # 每核每秒 1e6 微秒
        return self.cores * 1e6 * self.target_util / self.per_query_us

    def unit_cost_per_1k(self, instance_month_price: int) -> float:
        qps = self.capacity_qps()
        return instance_month_price / (qps * 86400 * 30) * 1000


def main() -> None:
    oltp = CpuAccount(cores=8, per_query_us=2_000)     # 点查+索引回表
    report = CpuAccount(cores=8, per_query_us=200_000) # 报表大查询
    cap_oltp = oltp.capacity_qps()
    assert 2_000 < cap_oltp < 3_000                    # 8核*0.65/2ms
    cap_report = report.capacity_qps()
    assert cap_report < 30
    # 单位成本对比: 报表查询每千次成本高 100 倍
    price = 4_000
    ratio = (report.unit_cost_per_1k(price)
             / oltp.unit_cost_per_1k(price))
    assert ratio > 90, ratio
    # 排队放大: 利用率 0.9 时有效容量 < 线性外推
    linear = CpuAccount(8, 2_000, target_util=1.0).capacity_qps()
    tuned = CpuAccount(8, 2_000, target_util=0.65).capacity_qps()
    assert tuned < linear * 0.66
    print(f"OLTP 容量 {cap_oltp:.0f}qps, 报表 {cap_report:.1f}qps, "
          f"单位成本差 x{ratio:.0f}")
    print("OK: 容量=核数/单位开销/0.65余量; 优化单位开销比加核划算")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么目标利用率定 65% 而不是 90%？
→ 一句话提示：CPU 排队延迟在 >80% 后非线性恶化（P99 放大数倍），且要给备份/vacuum/复制 dump 留 20-30% 后台余量；90% 时的"容量"是纸面容量。

**追问 2**：pg_stat_statements 的 total_exec_time 除以 calls 得到的单位开销有什么偏差？
→ 一句话提示：它含等待 IO 的时间且被参数分布平均（热点参数与非热点混在一起），需要按 queryid 分参数采样或结合 EXPLAIN ANALYZE 交叉验证。

## 背诵要点
- 容量公式：`可用QPS = 核数 × 1e6 / 单查询微秒 × 0.65`；单位开销用 pg_stat_statements/EXPLAIN ANALYZE 实测。
- 每千次查询 CPU 成本用于优化优先级排序；单位开销降一半 ≈ 副本/核数省一半，比加核划算。
- 按 P95 负载规划 + 可延迟负载错峰（Q7116），CPU >80% 排队雪崩，纸面 90% 容量不可用。

## 复盘追问
- 后台任务（备份/vacuum）为什么会侵蚀在线容量账？提示：它们同样吃 CPU 与 IO，不定峰则白天备份撞上晚高峰；用 cgroup/taskset 隔离核与定时错峰两招。
- 如何说服业务方优化报表查询？提示：把"每千次查询 CPU 成本"换算成月度实例费用占比，TOP 查询单位成本常是点查的百倍量级，直接对应可省的副本/核数预算。
