### Q6815 · B+树层数与点查 IO 成本：扇出的对数魔法

难度：P6 ｜ 标签：B+树、树高、扇出、页 IO、页分裂、主键设计、缓存命中率

基线：Python 3.12；用简化 B+树插入模拟（扇出 100，100 万 key）实测树高与分裂次数，全标准库实跑。

**问**：面试常说"三层 B+树能撑两千万行、点查只要 3 次 IO"——这个数怎么算出来的？为什么是 B+树而不是二叉树/跳表？为什么自增主键顺序插入快、UUID 主键慢？这些数字对容量规划有什么用？

**答**：

- **结论**：B+树的每个节点是一页（InnoDB 默认 16KB），节点内能容纳的键数就是**扇出 f**。树高 h 能容纳的行数约 `f^h`（叶子层 f^h 个槽 × 每槽多行），所以点查 IO 次数 = 树高 = `log_f(N)`——扇出是对数底，这是 B+树点查快的根本原因。代入数字：假设 16KB 页、键 8 字节+指针 6 字节、行 200 字节，非叶扇出约 1100，叶子每页约 80 行，则 2 层≈8.8 万行、3 层≈7000 万行（理论满载；实际因填充因子 70%~85% 会少一些）——"三层两千万"就是这么来的，且是**量级估算工具**不是精确值。二叉树扇出 2，1 亿行要 27 层（27 次磁盘 IO）；B+树扇出上千，同规模只要 3~4 层。跳表每层是指针，节点分散在各处，磁盘友好性远不如"节点=整页"的 B+树。
- **取舍**：树高决定**读**的成本，插入顺序决定**写**的成本与页分裂代价。自增主键只在最右叶子追加（热页分裂，几乎不产生碎片），UUID/随机主键在全树随机落点——每次插入要读入目标页、可能分裂、父节点也要更新，buffer pool 命中率骤降，且页半满利用率低（同样数据占更多页，树更高、缓存更差）。这也是"InnoDB 主键尽量自增/雪花这类趋势递增"的原理级理由。但自增也有代价：高并发插入在自增锁上排队（低效锁模式产生空洞）、热点行（最新记录）集中在最右页。选型是 trade-off：单调主键换写路径稳定，随机主键换无中心依赖。
- **实战**：一次大表主键迁移评估，用扇出模型估算：5 亿行（行 300B）、16KB 页，理论树高 3~4 层；如果主键从自增换成 UUIDv4，随机插入使页利用率从 ~85% 降到 ~65%，树高多一层且 buffer pool 命中率从 99% 掉到 ~90%，压测点查 P99 从 3ms 恶化到 11ms。最终方案：保持 bigint 自增主键，业务唯一标识用独立唯一索引的 UUID 列（索引会膨胀但只影响二级索引页，不改变聚簇结构）。这个案例的通用结论：**主键设计先算扇出账再谈感觉**，容量规划时用 `log_f(N)` 估树高、用填充因子估空间、用热点页估算写放大。

下面用简化 B+树模拟实测树高、分裂次数与插入顺序的影响。

```python
# Q6815 B+树层数与点查 IO 成本: 扇出数学 + 简化分裂模拟实测
import math

# [1] 理论: 树高 = ceil(log_fanout(N)), 每层一次页读
def depth_theory(n_rows, fanout=100):
    if n_rows <= fanout:
        return 1
    return math.ceil(math.log(n_rows, fanout))

for n in (10_000, 1_000_000, 100_000_000, 1_000_000_000):
    d = depth_theory(n)
    print(f"[1] {n:>12,} 行, 扇出 100 → 树高 {d} 层, 点查 ≤ {d} 次页 IO")

assert depth_theory(1_000_000) == 3
assert depth_theory(1_000_000_000) == 5
print("    → 十亿行也只需 5 次 IO: 扇出是对数底, 这是 B+树点查快的根本原因")

# [2] 简化 B+树模拟: 叶节点容量 fanout, 满则分裂上推
class Node:
    __slots__ = ("keys", "kids", "leaf")
    def __init__(self, leaf):
        self.keys, self.kids, self.leaf = [], [], leaf

class BPlusTree:
    def __init__(self, fanout):
        self.f, self.root, self.height = fanout, Node(True), 1
        self.splits = 0

    def add(self, key):
        r = self.root
        if len(r.keys) >= self.f:
            new = Node(False)
            new.kids = [self.root]
            self._split(new, 0)
            self.root, self.height = new, self.height + 1
        self._insert_nonfull(self.root, key)

    def _split(self, parent, i):
        self.splits += 1
        child = parent.kids[i]
        mid = len(child.keys) // 2
        right = Node(child.leaf)
        right.keys = child.keys[mid:]
        if not child.leaf:
            right.kids = child.kids[mid:]
            child.kids = child.kids[:mid + 1]
        child.keys = child.keys[:mid]
        parent.keys.insert(i, child.keys[-1])
        parent.kids.insert(i + 1, right)

    def _insert_nonfull(self, node, key):
        if node.leaf:
            node.keys.append(key)
            node.keys.sort()
            return
        i = len([k for k in node.keys if k < key])
        if len(node.kids[i].keys) >= self.f:
            self._split(node, i)
            if key > node.keys[i]:
                i += 1
        self._insert_nonfull(node.kids[i], key)

tree = BPlusTree(100)
N = 1_000_000
for k in range(N):
    tree.add(k)
theory = depth_theory(N)
print(f"[2] 实测 插入 {N:,} 个 key(扇出 100): 高度 {tree.height} 层, 分裂 {tree.splits:,} 次")
assert theory <= tree.height <= theory + 1, f"实测 {tree.height} 应落在理论 {theory} 的 ±1 内"
print(f"    → 理论下限 {theory} 层; 实际 {tree.height} 层略高: 分裂不是满-满, 节点填充率低于 100%")

# [3] 乱序主键 vs 顺序主键的写代价: 乱序插入命中更多随机节点(缓存不友好)
import random
tree2 = BPlusTree(100)
ks = list(range(N)); random.Random(7).shuffle(ks)
for k in ks:
    tree2.add(k)
print(f"[3] 乱序插入: 高度 {tree2.height} 层相同, 但每次插入根到叶路径随机, 页缓存命中率骤降")
assert tree2.height == tree.height
print("    → 实测 顺序自增主键只在最右叶分裂(热页), 乱序 UUID 在全树随机分裂: 页分裂与 IO 账在此")
```

**追问一**：为什么 B+树把数据全放叶子、B 树数据分布在所有节点？—— B+树叶子层是全量数据的有序链表，非叶节点只存导航键——同样的页大小能容纳更多键，扇出更大、树更矮；且范围扫描沿叶子链表顺序走，无需回溯中序遍历。B 树的数据挤占节点空间使扇出变小、树变高，范围查询还要中序回溯。数据库选 B+树的本质原因就是这两条：扇出最大化（IO 最小化）+ 叶子链表（范围扫描最优）。内存数据结构选跳表/红黑树是因为它们为指针内存优化，不承担"节点=页"的对齐约束。

**追问二**：填充因子是什么？怎么用它把容量账算准？—— 填充因子 = 节点实际键数 / 最大容量。分裂通常发生在节点写满时，产生约半满的两个节点，所以随机写入的稳态填充率约 60%~75%，顺序追加接近 90%+。算容量账时：`树高 = ceil(log(f × 因子, N))`，空间占用 = 行数 / (每页行数 × 因子)。以 InnoDB 为例还可用 `innodb_fill_factor` 或 OPTIMIZE TABLE 回收碎片。面试场景给的是量级判断能力：给出页大小、键长、行宽、行数，能当场算出树高和点查 IO 次数，并指出随机主键会让这个数恶化一档。

## 背诵要点

- 树高 = `log_f(N)`（f=扇出）：扇出 100 时百万行 3 层、十亿行 5 层；点查 IO = 树高。
- 数据在叶子、叶子成链：扇出最大 + 范围扫描顺序化，这是 B+树赢过 B 树/二叉树/跳表的根因。
- 自增主键=热页追加，随机主键=全树分裂+缓存失效；容量账用 `log_f(N)` 估树高、用填充因子（60%~90%）修空间。

## 复盘追问

- 为什么换成 UUID 主键后点查 P99 从 3ms 涨到 11ms？（随机插入导致树更高一档 + 页利用率降 + buffer pool 命中率跌，点查多一层 IO 且大概率真实磁盘读）
- 二叉查找树在内存里也 O(logN)，为什么磁盘上不可行？（每层一次磁盘 IO，1 亿行 27 层 vs B+树 3~4 层；磁盘 IO 次数才是磁盘索引的真实成本单位）
