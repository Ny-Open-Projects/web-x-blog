### Q6547 · 数据库成本工程：跨可用区流量费怎么把"读副本架构"变得很贵？

> 难度:★★★ | 标签:成本工程, 拓扑设计, 云成本

**问**：把数据库读副本和应用分到不同可用区（AZ），月账单里多出一笔"跨 AZ 流量费"，为什么这笔钱经常比副本实例本身还贵？拓扑怎么设计才能省钱又不牺牲高可用？同城双 AZ 和三 AZ 的成本差在哪？

**答**：结论：云厂商对**跨 AZ 入/出流量双向计费**（常见 0.5-1 元/GB 双向），而数据库复制流量是 7×24 持续的：一个每天 400GB binlog 的主库，跨 AZ 给 2 个从库复制就是每天 800GB-1.6TB 计费流量，月账单轻松超过实例费。成本工程三板斧：**复制流量同 AZ 内走、应用读写按 AZ 亲和路由、跨 AZ 只保真读容灾路径**。

机理与实战：
- **流量从哪来**：① 主→从复制流（持续、可预测、最大头）；② 应用→DB 的查询结果流（SELECT 返回的大结果集）；③ 备份/归档上传。第一项完全可以用"从库与主库同 AZ"消灭，且不牺牲可用性——AZ 级故障时哨兵把从库提升为主，应用重连即可。
- **应用亲和路由**：读请求优先路由到与该应用实例同 AZ 的副本（拓扑感知的 DNS/服务发现），跨 AZ 读只作为兜底；一个日均 100GB 查询结果集的应用，全跨 AZ 读每月多 3-6 万元，而亲和路由把它压到接近零。
- **高可用的钱花在哪**：同城双 AZ（复制流同 AZ 不出费、备节点放另一 AZ 收容灾保险费）是性价比最优；三 AZ 双副本用于金融级 RPO，复制流量费 ×2 不可省——这是用钱买 RPO，不是浪费。
- **账单化验证**：把流量成本公式做成表格进架构评审：`月流量费 ≈ 日 binlog GB × (副本数-1) × 2 × 30 × 单价 + 日查询流量 GB × 跨AZ比例 × 2 × 30 × 单价`，让拓扑决策有数字可辩。

```python
# 基线:Python 3.10+;纯标准库,跨 AZ 流量费成本账与拓扑方案对比
from __future__ import annotations
from dataclasses import dataclass


@dataclass
class Topology:
    name: str
    binlog_cross_az: bool      # 主从复制是否跨 AZ
    query_cross_az_ratio: float  # 应用读流量跨 AZ 比例
    replicas: int = 2
    daily_binlog_gb: float = 400
    daily_query_gb: float = 100


PRICE_PER_GB = 0.8   # 元/GB 双向综合价(示例)


def monthly_traffic_cost(t: Topology) -> float:
    """月跨 AZ 流量费:复制流 + 查询流,双向 ×2,30 天。"""
    repl = t.daily_binlog_gb * t.replicas * (2 if t.binlog_cross_az else 0)
    query = t.daily_query_gb * t.query_cross_az_ratio * 2
    return (repl + query) * PRICE_PER_GB * 30


def demo() -> None:
    plans = [
        Topology("全跨AZ:从库异AZ+读不亲和", binlog_cross_az=True, query_cross_az_ratio=1.0),
        Topology("省钱版:复制同AZ+读同AZ亲和", binlog_cross_az=False, query_cross_az_ratio=0.05),
        Topology("三AZ金融版:双副本跨AZ", binlog_cross_az=True, query_cross_az_ratio=0.05, replicas=2),
    ]
    for t in plans:
        print(f"  {t.name}: 月流量费 ≈ {monthly_traffic_cost(t):,.0f} 元")
    save = monthly_traffic_cost(plans[0]) - monthly_traffic_cost(plans[1])
    print(f"  亲和路由每月省 {save:,.0f} 元")
    assert monthly_traffic_cost(plans[0]) > monthly_traffic_cost(plans[1]) * 10
    # 复制流是最大头:400GB×2副本×2方向×0.8×30=38400 元/月
    assert monthly_traffic_cost(Topology("x", True, 0.0)) > 38000
    print("拓扑成本账:复制流同AZ化+读亲和,高可用费花在容灾节点上 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：把从库放同 AZ 后，AZ 故障时怎么保证不丢读服务？
答：同 AZ 从库在 AZ 故障时一起失效，此时读流量要切换到"平时不跨 AZ"的跨 AZ 副本——所以正确架构是**主副本同 AZ（省复制费）+ 一台跨 AZ 冷副本（只复制不服务读，保容灾）**，冷副本的复制流仍会产生跨 AZ 费，但只有 1 份而非 2 份；这就是"跨 AZ 费从 2 份压到 1 份"的中间态，比全同 AZ 的 RPO 风险小得多。

**追问二**：为什么很多团队上线半年才发现这笔流量费？
答：跨 AZ 费不在实例单价里、按用量后结算，且开发期流量小无感知；规模化后 binlog 随写入线性增长，费用也线性增长却没有预算告警。治理手段是给"AZ 间流量"建独立成本科目+月度环比告警，并把它写进容量规划模板——成本指标要像延迟指标一样有 owner 和回归口径。

## 背诵要点
- 跨 AZ 流量双向计费，数据库流量三大头：主从复制流（最大头）、应用查询结果流、备份流；复制流同 AZ 化每月可省数万元。
- 性价比拓扑：主+副本同 AZ（复制不出费）+ 一台跨 AZ 冷副本保容灾；三 AZ 双副本是拿流量费买 RPO，金融级才用。
- 应用读按 AZ 亲和路由（拓扑感知服务发现），跨 AZ 读只做兜底；AZ 间流量要立独立成本科目+月度环比告警。

## 复盘追问
- 亲和路由把某 AZ 的读全压到本地副本，AZ 均衡性怎么保？（提示：亲和不是唯一性——本地副本过载时按权重把溢出流量打到远 AZ，容量账要按"单 AZ 故障时全量跨 AZ"的峰值计费预演，避免省钱方案在故障日爆账单）
- 备份走对象存储的同区域复制（CRR）也在跨 AZ 费里吗？（提示：是，CRR 按复制流量单独计费；备份策略设计时把"每日全备 vs 增量+定期全备"的复制量算进去，增量方案往往省 80% 复制费）
