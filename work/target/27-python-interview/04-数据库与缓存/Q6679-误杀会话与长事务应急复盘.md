### Q6679 · 应急 KILL 会话误杀了长事务：复盘与安全清单

难度：P6/P7 ｜ 标签：事故复盘、应急响应、事务

**问**：高峰期 DBA 为清理堆积的连接，按"执行时间最长"批量 KILL 会话，结果误杀了几个跑了 40 分钟的关键长事务，数据回滚引发下游补偿风暴。如何建立"杀会话"的安全决策清单？

**答**：**结论**：按执行时间排序杀会话是危险启发式——**执行时间长的会话往往是最不能杀的**（长事务持有大量行锁/已写入的数据）。安全决策必须按"会话在做什么 + 杀掉的代价"判断，而不是按"它多久了"。误杀长事务的代价：事务回滚（回滚本身可能比原事务还慢）+ 已发出的副作用（消息、外部调用）无法撤回 + 下游补偿风暴。

**决策清单（按优先级）**：
1. 只杀 `Sleep` 且无未提交事务的空闲连接（零代价）；
2. 杀"只读长查询"（SELECT 大报表）——丢的只是查询结果；
3. 写事务绝不进批量 KILL 名单，单独评审：先看它持有的锁是否是当前阻塞源头，是则考虑 `KILL QUERY`（只杀语句保留事务？注意：InnoDB 中 KILL QUERY 不会释放锁）；
4. 每次杀之前留痕：`SHOW PROCESSLIST` 快照 + binlog 位点，便于复盘。

**实战**：把清单做成脚本 dry-run：先输出"候选杀名单 + 各自事务状态 + 杀掉代价分级"，人工确认后才执行；`information_schema.innodb_trx` 里 `trx_rows_modified` 大的事务标红禁杀。

```python
# 安全杀会话 dry-run：按"事务状态 + 修改行数"分级，而不是按执行时长
from dataclasses import dataclass

@dataclass
class Session:
    id: int
    user: str
    command: str            # Sleep / Query / Execute
    seconds: int
    trx_state: str | None   # 'RUNNING' 表示有未提交事务
    trx_rows_modified: int = 0

def kill_verdict(s: Session) -> tuple[str, str]:
    """返回 (动作, 理由)。动作: safe_kill / review / forbid"""
    if s.command == "Sleep" and s.trx_state != "RUNNING":
        return "safe_kill", f"空闲{ s.seconds }s 且无事务，杀掉零代价"
    if s.command == "Query" and s.trx_state is None:
        return "safe_kill", "只读长查询，丢的只是结果集"
    if s.trx_state == "RUNNING":
        if s.trx_rows_modified > 1000:
            return "forbid", (f"已修改 {s.trx_rows_modified} 行的大事务，"
                              "杀=回滚风暴+副作用不可撤回")
        return "review", "小写事务：确认是否阻塞源头后人工决策"
    return "review", "其他：人工看 SQL 文本"

sessions = [
    Session(1, "app", "Sleep", 900, None),               # 空闲连接
    Session(2, "report", "Query", 600, None),            # 只读长查询
    Session(3, "batch", "Query", 2400, "RUNNING", 50000),# 大事务！
    Session(4, "app", "Execute", 30, "RUNNING", 5),      # 小写事务
]
for s in sorted(sessions, key=lambda x: -x.seconds):
    act, why = kill_verdict(s)
    print(f"#{s.id} {s.command:>7} {s.seconds:>5}s -> {act}: {why}")
# 时间最长的 #3 恰恰是 forbid —— 按时长排序杀就是这次事故的根因
```

**追问 1**：`KILL QUERY` 与 `KILL CONNECTION` 的区别为什么救不了大事务？
提示：KILL QUERY 只中止当前语句、事务仍保持打开且锁不释放——既没清掉阻塞源，又留下半死状态；要彻底处理只能回滚整个事务（KILL CONNECTION）并承担回滚代价。

**追问 2**：长事务为什么回滚可能比执行还慢？
提示：undo 链回放按修改行数计价，且回滚期间锁仍在持有、阻塞照旧；40 分钟写入的回滚可能占用更高——所以大事务的止损是"预防"（`innodb_rollback_on_timeout`、事务超时、拆小），不是"应急杀"。

**追问 3**：如何让"长事务"根本不出现？
提示：应用侧事务守卫——事务里禁止外部调用（Q6603 同源问题）、设置 `max_execution_time`/`innodb_lock_wait_timeout`、巡检 `innodb_trx` 时间超阈值告警。

## 背诵要点
1. 杀会话按"事务状态 + 修改行数"决策，绝不按执行时长排序：跑最久的往往最不能杀。
2. Sleep 无事务/只读长查询可批量杀；大写事务（rows_modified 大）禁杀——回滚代价高于阻塞代价。
3. KILL QUERY 不释放锁；大事务治理靠预防（事务禁外呼、超时参数、innodb_trx 巡检）。
