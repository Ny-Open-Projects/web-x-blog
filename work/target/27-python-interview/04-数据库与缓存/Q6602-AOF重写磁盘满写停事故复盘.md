### Q6602 · AOF 重写期间磁盘打满写停事故复盘

难度：P7 ｜ 标签：Redis / 持久化 / 事故复盘

**问**：某 Redis 实例磁盘使用率 85%，运维以为还有余量，晚上触发了 AOF 重写（BGREWRITEAOF），结果 Redis 开始拒绝写入并报错 "no space left on device"。AOF 重写为什么会让磁盘突然不够用？怎么治理？

**答**：
- **结论**：AOF 重写的磁盘账是**新旧两份 AOF 叠加**：重写期间旧 AOF 继续追加（写流量不中断），fork 出的子进程把"当前内存态"写成一份新的临时 AOF 文件，写完再原子替换。峰值磁盘占用 ≈ 旧 AOF + 新 AOF（最坏接近旧 AOF 大小）+ fork 的 COW 内存换页（如果 swap 在同一盘）。磁盘余量低于旧 AOF 大小时，重写写到一半失败，Redis 检测到持久化失败会按 `stop-writes-on-bgsave-error`/aof 策略拒绝写入——数据安全优先，宁可写停。
- **取舍**：治理选项：① 磁盘容量规划按"AOF 重写峰值 = 2×AOF 体积 + 写入增速"预留，低于 50% 使用率再触发重写；② `auto-aof-rewrite-percentage` 调高降低重写频率，代价是恢复时间变长；③ 重写期间用 `aof-use-rdb-preamble`（混合持久化）显著缩小新文件体积；④ 紧急恢复：停写后清理临时文件/扩容磁盘，再手动 `bgrewriteaof`。
- **实战**：事故剧本：① 确认写停原因是磁盘而非 OOM（dmesg 与 `INFO persistence` 的 aof_last_write_status）；② 清理同盘的旧 RDB/日志/临时 aof 文件腾出空间；③ 恢复写入后核算 AOF 体积与写入速率，重算重写峰值；④ 复盘项：把"磁盘可用空间 < 2×AOF 体积"做成告警，重写任务改为手动触发+前置磁盘检查；Python 侧巡检脚本在低水位时拒绝触发重写。

```python
# AOF 重写磁盘峰值测算与重写门禁（标准库模拟）
# 基线：Python 3.9+

from dataclasses import dataclass


@dataclass
class RedisDisk:
    disk_total_gb: float
    disk_used_gb: float
    aof_size_gb: float
    write_rate_gb_per_hour: float   # AOF 追加速率
    rewrite_hours: float            # 预计重写耗时

    def rewrite_peak_gb(self) -> float:
        """峰值 = 旧 AOF 继续增长 + 新临时 AOF（按当前内存态≈旧 AOF 上限）"""
        grow = self.write_rate_gb_per_hour * self.rewrite_hours
        return self.aof_size_gb + grow + min(self.aof_size_gb, grow + self.aof_size_gb)

    def can_rewrite(self) -> tuple[bool, str]:
        free = self.disk_total_gb - self.disk_used_gb
        need = self.rewrite_peak_gb()
        if free < need:
            return False, f"free={free:.1f}GB < rewrite peak {need:.1f}GB, refuse"
        return True, f"free={free:.1f}GB >= peak {need:.1f}GB"


def main() -> None:
    # 事故现场：磁盘 85%，AOF 40GB
    bad = RedisDisk(200, 170, 40, 2, 1.5)
    ok, msg = bad.can_rewrite()
    assert not ok
    print("事故现场:", msg)

    # 扩容/清理后
    good = RedisDisk(400, 170, 40, 2, 1.5)
    ok, msg = good.can_rewrite()
    assert ok
    print("扩容后:", msg)
    print("OK: 重写前置磁盘门禁")


if __name__ == "__main__":
    main()
```

**追问 1**：AOF 重写和 RDB bgsave 的磁盘与内存峰值有何异同？
→ 一句话提示：两者都 fork + COW（内存峰值翻倍风险相同），磁盘上 RDB 是单文件一次性写（峰值≈RDB 大小），AOF 重写是新旧两份叠加且旧文件还在按写入速率增长，磁盘峰值更高。

**追问 2**：`stop-writes-on-bgsave-error` 对 AOF 也生效吗？为什么要"宁可写停"？
→ 一句话提示：AOF 侧对应的是 aof 持久化失败后的拒绝写策略（appendfsync 出错/aof 文件损坏）；持久化链路断掉时继续写意味着故障时刻会丢掉整个窗口的数据，对当作事实源用的 Redis 必须写停逼人介入。

## 背诵要点
- AOF 重写磁盘峰值 ≈ 旧 AOF + 新临时 AOF + 写入增速；磁盘余量不足 2×AOF 体积时不该触发重写。
- 持久化失败 Redis 会拒绝写入（数据安全优先），处置顺序：确认原因 → 腾空间/扩盘 → 恢复写入 → 重算峰值。
- 混合持久化 `aof-use-rdb-preamble` 缩小重写产物；巡检脚本把"可用空间 vs 重写峰值"做成门禁而非告警。

## 复盘追问
- fork 的 COW 在这次事故里扮演什么角色？提示：COW 换出页如果落在同一块盘（swap），会同时吃内存带宽和磁盘空间，重写峰值测算要把 swap 分区也算进磁盘账。
- 为什么 `auto-aof-rewrite-percentage` 不宜设得太小？提示：阈值小=重写频繁，频繁 fork 引发延迟毛刺和 COW 峰值；通常 100%（翻倍）起步，配合最小尺寸下限。
