### Q6522 · Lua 脚本确定性与脚本复制：为什么脚本里不能用 TIME？为什么不能写再读？

> 难度:★★★★ | 标签:Redis, Lua, 复制

**问**：有人在 Lua 脚本里用 `redis.call('TIME')` 做过期判断、用 `math.random` 生成 ID，上线后在主从/集群环境出现了主从不一致。根因是什么？Redis 7 之后情况变了吗？

**答**：结论：Redis 复制 Lua 脚本时，默认复制的是"脚本本身"而不是"脚本产生的写效果"——副本会重新执行同一份脚本。如果脚本含非确定因素（时间、随机数、读后再写），副本执行结果可能与主不同，造成主从漂移。早期 Redis 用 `redis.replicate_commands()` 切换为"效果复制"，Redis 7 起**效果复制成为默认且不可回退**（脚本模式已移除），同时引入 Functions 让脚本有版本化管理。所以脚本的铁律是：确定性输入 → 确定性输出；要时间用 `redis.call('TIME')` 也得意识到它是非确定源（7 前必须显式效果复制），要随机先在客户端生成再作为 KEYS/ARGV 传入。

机理与实战：
- 写后再读的陷阱：脚本内 `SET` 之后 `GET`，主上读到的是自己写的值；脚本模式下副本重放时理论上也是同序执行所以多数场景一致，真正的坑在**集群下脚本的 key 全在副本上重放但故障切换后新主的历史可能不同**，以及 `redis.call('TIME')` 这类调用在旧版本副本上直接报错或漂移。
- 集群约束：脚本访问的所有 key 必须落在同一 slot（用 hash tag 保证），否则 `CROSSSLOT` 错误——这与 EVAL 原子性无关，是数据分布约束。
- 实战规范：脚本只做"以 KEYS/ARGV 为输入的纯函数"；TTL 判断用 `PTTL`/`PEXPIREAT` 由客户端计算传入；随机数、当前时间一律客户端生成。脚本要保存版本（`SCRIPT LOAD` + `EVALSHA`），发版时先预热 sha 再切流量，避免 NOSCRIPT 风暴。

```python
# 基线:Python 3.9+ / redis-py 4.x / Redis 7.x(效果复制默认) ;缺库走纯脚本模拟
try:
    import redis
    HAS_REDIS = True
except ImportError:
    HAS_REDIS = False

# 确定性脚本:输入只有 KEYS/ARGV,无 TIME/随机/写后读
DETERMINISTIC_LUA = """
local current = redis.call('GET', KEYS[1])
local inc = tonumber(ARGV[1])
local next_val = (tonumber(current) or 0) + inc
redis.call('SET', KEYS[1], next_val)
return next_val
"""

# 反例:把当前时间烧进值里(非确定源,复制语义下禁止)
NONDETERMINISTIC_LUA = """
redis.call('SET', KEYS[1], ARGV[1] .. ':' .. ARGV[2])  -- ARGV[2]=客户端时间
return 1
"""

def real_client():
    """redis-py 可用且本机有 Redis 才返回真客户端,否则 None 走模拟。"""
    if not HAS_REDIS:
        return None
    try:
        r = redis.Redis(decode_responses=True, socket_connect_timeout=1)
        r.ping()
        return r
    except Exception:
        return None


def demo() -> None:
    r = real_client()
    if r is None:
        # 纯 Python 模拟确定性:同输入同输出,副本重放必然一致
        class MemRedis:
            def __init__(self) -> None:
                self.data: dict[str, str] = {}
            def eval_like(self, key: str, inc: int) -> int:
                v = int(self.data.get(key) or 0) + inc
                self.data[key] = str(v)
                return v
        m, replica = MemRedis(), MemRedis()
        # 副本重放 = 对同样输入执行同样逻辑
        for inc in (1, 2, 3):
            m.eval_like("k", inc)
            replica.eval_like("k", inc)
        assert m.data == replica.data, "确定性脚本重放后主从一致"
        print("模拟通过:确定性脚本主从一致 ->", m.data)
        return
    sha = r.script_load(DETERMINISTIC_LUA)
    out = r.evalsha(sha, 1, "counter", 5)
    print("EVALSHA 结果:", out)          # 5
    out = r.evalsha(sha, 1, "counter", 2)
    print("第二次:", out)                # 7,重放到副本必得同值
    # 时间由客户端生成后作为 ARGV 传入,脚本本体保持确定性
    import time
    r.eval(NONDETERMINISTIC_LUA, 1, "ts", "order", str(int(time.time() * 1000)))

demo()
```

**追问一**：既然 Redis 7 默认效果复制，脚本里是不是就可以随便用 TIME 了？
答：主从复制层面安全了，但仍然不建议：一是低版本副本/兼容集群会踩雷；二是时间进了数据后脚本不再可重放（比如用于故障排查的脚本重跑），工程上"确定性脚本"依然是团队规范，Functions 也支持 no-writes 标注来声明只读脚本。

**追问二**：EVALSHA 报 NOSCRIPT 怎么处理？
答：捕获 `NoScriptError` 后降级回 `EVAL` 全文发送，并异步 `SCRIPT LOAD` 预热；主从切换/FAILOVER 后脚本缓存不共享，NOSCRIPT 是常态而非异常，客户端必须内建这个降级路径。

**背诵要点**：
- 脚本复制默认"重放脚本"，非确定源（TIME/随机/写后读）会主从漂移；Redis 7 起效果复制为默认。
- 确定性铁律：时间与随机客户端生成传 ARGV，脚本只是 KEYS/ARGV 的纯函数。
- 集群下脚本 key 必须同 slot（hash tag）；EVALSHA 失败 NOSCRIPT 降级 EVAL 并重新 LOAD。

- 集群脚本 key 需同 slot；NOSCRIPT 用 EVAL 降级并重预热。
