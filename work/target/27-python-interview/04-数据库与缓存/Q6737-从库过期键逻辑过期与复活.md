### Q6737 · 从库上的过期键：主库已删，副本仍能扫到，切换后还"复活"

难度：P7 ｜ 标签：Redis、过期策略、主从复制、逻辑过期

基线：Python 3.12；Redis 3.2+ 副本逻辑过期语义；纯 Python 模拟主库删除与复制流。

**问**：主库 `SET k v EX 60`，60 秒后主库 `GET k` 是 nil；但直连从库 `GET k` 还能拿到值，`TTL` 也显示正数在递减。主从切换后这个 key 又"复活"了一小段时间。过期不是主库删了就会同步吗？

**答**：
- **结论**：Redis 的过期删除**只由主库驱动**（被动删除：访问时发现过期；主动删除：定期抽样）。删掉后向副本传播一条 `DEL`。副本**不会按自己的时钟删键**，而是标记"逻辑过期"：3.2+ 起读请求命中逻辑过期键返回 nil，但键**仍占内存**，`SCAN`/`KEYS`/`RANDOMKEY` 依然能看到。主库若长期没访问该键、抽样也没抽到，就不会发 `DEL` → 副本上"逻辑过期但存在"会一直挂到下一次访问或内存淘汰。
- **取舍**：把删除权收敛到主库，换来复制流的**确定性**（副本执行 `DEL` 而不是各自按本地时钟删，避免时钟漂移导致主从分叉）；代价是副本内存滞留过期键、`DBSIZE`/`SCAN` 统计偏高、切换瞬间状态不确定。反过来若允许副本自治删除，主从时钟不同步时同一个 `EXPIRE` 在两边的到期时刻不同，切换后数据状态取决于谁的时钟快。
- **实战**：① 读副本的业务把"逻辑过期即 nil"当契约，不要用 `EXISTS`/`TTL` 判断业务状态；② 监控副本 `expired_keys` 远低于主库 → 说明过期没传播，检查主库是否长期冷 key；③ 内存告警时用 `SCAN` + `TTL` 批量清理，别用 `KEYS`；④ 业务不要依赖 TTL 做严格到期，用数据里的时间戳字段 + 主动过滤。

```python
"""主库驱动过期、副本逻辑过期：GET 返回 nil 但键仍在。"""


class Primary:
    def __init__(self) -> None:
        self.store: dict[str, list] = {}        # key -> [value, expire_at]
        self.repl_stream: list[tuple[str, str]] = []

    def set(self, key: str, value: str, ttl: float, now: float) -> None:
        self.store[key] = [value, now + ttl]

    def get(self, key: str, now: float):
        item = self.store.get(key)
        if item is None:
            return None
        if item[1] <= now:                      # 被动删除
            del self.store[key]
            self.repl_stream.append(("DEL", key))
            return None
        return item[0]

    def scan(self) -> list[str]:
        return list(self.store)


class Replica:
    def __init__(self, primary: Primary) -> None:
        self.primary = primary
        self.store: dict[str, list] = {}
        self.offset = 0

    def sync(self) -> None:
        while self.offset < len(self.primary.repl_stream):
            op, key = self.primary.repl_stream[self.offset]
            if op == "DEL":
                self.store.pop(key, None)       # 只有主库发 DEL 才真删
            self.offset += 1

    def load(self, key: str, value: str, expire_at: float) -> None:
        self.store[key] = [value, expire_at]    # 全量同步/RDB 带来的过期时刻

    def get(self, key: str, now: float):
        item = self.store.get(key)
        if item is None:
            return None
        if item[1] <= now:
            return None                          # 逻辑过期：返回 nil，但不删
        return item[0]

    def ttl(self, key: str, now: float) -> int:
        item = self.store.get(key)
        if item is None:
            return -2
        return max(0, int(item[1] - now))         # 逻辑过期仍可能返回 0/正数

    def scan(self) -> list[str]:
        return list(self.store)


if __name__ == "__main__":
    now = 1000.0
    p = Primary()
    r = Replica(p)

    p.set("session:1", "u=42", ttl=60, now=now)
    r.load("session:1", "u=42", expire_at=now + 60)

    # 61 秒后：主库被访问 -> 被动删除并发 DEL
    later = now + 61
    print("主库 GET:", p.get("session:1", later))
    r.sync()
    print("副本 GET:", r.get("session:1", later), "| 副本 SCAN:", r.scan())

    # 另一个 key：到期后主库没人访问 -> 不发 DEL
    p.set("cold:1", "v", ttl=10, now=now)
    r.load("cold:1", "v", expire_at=now + 10)
    later2 = now + 100
    print("冷 key 主库未访问，副本 GET:", r.get("cold:1", later2))
    print("  副本 SCAN 仍能看到:", r.scan(), "| TTL:", r.ttl("cold:1", later2))

    # 切换：副本升主，若本地时钟偏慢，键看起来又活了
    replica_clock = later2 - 100
    print("副本时钟慢 100 秒，升主后 TTL:",
          max(0, int((now + 10) - replica_clock)), "-> 键复活")
    print("结论：过期删除权在主库；副本只做逻辑过期，别拿 EXISTS/TTL 当业务判断")
```

**追问一**：副本上 `TTL` 返回什么？
→ 解析：按本地时钟算剩余秒数，键已逻辑过期也可能返回 0 或正数（取决于时钟），而 `GET` 已经返回 nil。两者语义不一致，所以不能"看到 TTL > 0 就认为还有效"。业务判断一律用 `GET` 的结果。

**追问二**：为什么不让副本自己按本地时钟删？
→ 解析：主从时钟不同步时，同一个 `EXPIRE` 在两边的到期时刻不同，副本先删后再收到主库的 `DEL` 找不到键（无害），但一旦副本升主，数据状态就取决于谁的时钟快，无法保证一致。Redis 选择"删除只由主库发起 + 副本逻辑过期"，本质是用一点内存冗余换复制语义的确定性。
