### Q6530 · 键空间过期通知：用它做"订单超时自动取消"为什么不靠谱？

> 难度:★★★★ | 标签:Redis, 过期, 可靠性

**问**：想实现"订单 30 分钟未支付自动取消"。有人建议监听 Redis 键空间过期通知（`notify-keyspace-events Ex`），key 过期时订阅端收到事件就去关单。这个方案的问题在哪？正确姿势是什么？

**答**：结论：键空间过期通知是 **fire-and-forget 的 pub/sub**——不持久化、不确认、断线丢消息；且过期事件在 Redis **实际执行过期**时才发（惰性删除或定期抽样删除），不是"到点即发"，从 TTL 到期到事件产生可能有可观测的延迟，甚至 key 到期后一直没被访问就长期不发。所以它只能当"加速触发器"，绝不能当唯一事实源。正确姿势：**数据库层的定时扫描兜底**（状态 + 过期时间的索引扫描）为主，过期通知/延迟队列做加速，取消动作本身幂等（状态机：只有"待支付"才允许转"已取消"）。

机理与实战：
- 三类丢失场景：订阅端断线重连期间的消息全丢；Redis 重启/pub-sub 不落盘全丢；惰性过期导致事件迟到或不来（用不活跃的 key 时，定期删除每轮只抽样，可能很久不触发）。
- 加速器选型：到期量小用通知；量大且要有序用 ZSET 时间轮（`score=到期时间戳`，轮询 `ZRANGEBYSCORE`）——它比通知可靠（可重复扫描不丢）但仍是缓存层，必须与 DB 兜底扫描并存。
- 兜底扫描设计：`WHERE status='pending' AND expire_at < now() LIMIT 100 FOR UPDATE SKIP LOCKED`，多实例并发扫描靠 SKIP LOCKED 分工；扫描频率就是"最坏取消延迟"，通知把典型延迟压到秒级，扫描保证最坏分钟级。

```python
# 基线:Python 3.9+ 纯标准库 ;redis-py/DB 可选,演示状态机+扫描兜底骨架
import time


class OrderStateMachine:
    ALLOWED = {"pending": {"paid", "cancelled"}}

    def __init__(self) -> None:
        self.orders: dict[str, dict] = {}

    def cancel_if_expired(self, order_id: str, now: float) -> str:
        """幂等取消:仅 pending 且到期才转 cancelled,重复调用安全。"""
        o = self.orders.get(order_id)
        if o is None:
            return "not_found"
        if o["status"] != "pending":        # 状态机守卫:非 pending 一律拒绝
            return o["status"]
        if o["expire_at"] > now:
            return "pending"                # 未到期,扫描兜底不误杀
        o["status"] = "cancelled"
        return "cancelled"

    def scan_expired(self, now: float, limit: int = 100) -> list[str]:
        """DB 兜底扫描:事实源层的过期关闭,不依赖任何通知。"""
        due = [oid for oid, o in self.orders.items()
               if o["status"] == "pending" and o["expire_at"] <= now]
        return due[:limit]


def demo() -> None:
    sm = OrderStateMachine()
    now = time.time()
    sm.orders["A"] = {"status": "pending", "expire_at": now - 10}
    sm.orders["B"] = {"status": "paid", "expire_at": now - 10}
    sm.orders["C"] = {"status": "pending", "expire_at": now + 600}

    # 过期通知丢了也没关系:扫描兜底总能捞到
    due = sm.scan_expired(now)
    print("扫描兜底捞出:", due)                     # ['A']
    for oid in due:
        print(oid, "->", sm.cancel_if_expired(oid, now))
    # 幂等:重复取消
    print("重复取消:", sm.cancel_if_expired("A", now))  # cancelled,非 pending 守卫
    print("已支付不被误杀:", sm.cancel_if_expired("B", now))
    print("未到期不取消:", sm.cancel_if_expired("C", now))


if __name__ == "__main__":
    demo()
```

**追问一**：为什么不用"客户端起定时器到点关单"？
答：进程重启丢定时器、多实例重复关单（靠状态机幂等可解）、实例数大时定时器数量爆炸。定时器方案把可靠性押在应用进程上，而扫描兜底押在数据库事务上，后者是正确的事实源。

**追问二**：ZSET 时间轮方案里，消费者崩溃后 ZSET 里的到期任务会怎样？
答：不会丢——任务还在 ZSET 里，下个消费者轮询 `ZRANGEBYSCORE` 会再次拿到并重新处理，靠业务幂等去重即可；这也是时间轮比 pub/sub 通知可靠的根本原因：**可重扫**。代价是轮询频率与扫描批量的资源开销。

**背诵要点**：
- 过期通知 = pub/sub：不持久化、断线丢、惰性过期导致迟到或不发，只能做加速器。
- 可靠关单 = DB 状态 + 过期时间索引扫描兜底 + 状态机幂等守卫。
- 加速器选型：小量用通知，大量有序用 ZSET 时间轮（可重扫不丢）。

**复盘追问**：
- 扫描兜底的 LIMIT 100 + SKIP LOCKED 如何保证多实例不重复关单也不漏单？
- "最坏取消延迟"由什么参数决定？如何对它做监控与 SLA 承诺？

## 背诵要点
- 惰性/抽样过期使通知可能永远不发，业务绝不能以通知为唯一触发。
- 时间轮（ZSET+score）可重扫，可靠性高于 pub/sub 通知。
- 状态机守卫（仅 pending 可取消）使触发源重复或乱序都安全。
