### Q6671 · SSL证书过期导致数据库连接全量失败的复盘

难度：P6/P7 ｜ 标签：事故复盘、TLS、运维、MySQL/PG

**问**：某天凌晨应用全量报 SSL 握手失败、数据库不可用，但 DBA 侧实例正常。排查思路是什么？如何在代码与运维两侧建立证书过期防线？

**答**：**结论**：这类"应用全挂、DB 正常"的不对称故障，第一嫌疑是应用与数据库之间的 TLS 证书过期（服务端证书或客户端 CA 链）。握手在 TCP 之后、认证之前失败，所以监控上表现是连接数归零 + 应用侧 `ssl.SSLCertVerificationError`/`certificate verify failed`，而实例进程、磁盘、CPU 全部健康。

**取舍**：三种常见根因要按概率排序——① 服务端证书到期（最常见，证书默认 90 天~1 年）；② 应用侧 CA 包更新后旧链失效；③ 中间代理（云 LB、sidecar）替换证书但客户端 pin 了旧指纹。复盘要点不是"续证书"，而是为什么没有提前 30 天告警。

**实战**：
1. 证书有效期纳入监控：`ssl` 标准库可离线解析 PEM 读 `notAfter`，配 30/14/7 天三档告警；
2. 客户端连接串里 `ssl_verify_identity` 类参数指向的 CA 与服务端证书一起登记台账；
3. 演练：在测试环境故意挂一张过期证书，验证告警链路与降级开关（临时 `sslmode=require` 关校验要有审批留痕，不能直接关到 verify 全关）。

```python
# 证书过期预警：不依赖网络，直接解析 PEM 文本（标准库 ssl + 裸解析 notAfter）
import ssl
import re
from datetime import datetime, timezone, timedelta

def days_until_expiry(pem_text: str, now: datetime | None = None) -> int:
    """从 PEM 文本提取 notAfter 并计算剩余天数。"""
    now = now or datetime.now(timezone.utc)
    # 证书正文里 notAfter 行形如 Not After : Nov 21 00:00:00 2027 GMT
    m = re.search(r"Not After\s*:\s*(.+?GMT)", pem_text)
    if not m:
        raise ValueError("PEM 中未找到 notAfter")
    # OpenSSL 日期格式解析
    fmt = "%b %d %H:%M:%S %Y GMT"
    expiry = datetime.strptime(m.group(1).strip(), fmt).replace(tzinfo=timezone.utc)
    return (expiry - now).days

def alert_level(days: int) -> str:
    if days < 0:
        return "P0-已过期"
    if days <= 7:
        return "P1-立即续期"
    if days <= 14:
        return "P2-本周处理"
    if days <= 30:
        return "P3-列入台账"
    return "OK"

fake_cert = """Certificate:
    Not Before : Nov 21 00:00:00 2026 GMT
    Not After  : Dec 21 00:00:00 2026 GMT"""
print(alert_level(days_until_expiry(fake_cert)))  # 30 天整 -> P3

# 已过期的场景（把 now 设到证书之后）
expired_now = datetime(2027, 1, 5, tzinfo=timezone.utc)
print(alert_level(days_until_expiry(fake_cert, expired_now)))  # P0-已过期

# 实际线上检查握手（目标库可达时）：
def probe(host: str, port: int):
    ctx = ssl.create_default_context()
    with socket_conn(host, port, ctx) as (sock, _):
        not_after = ssl.cert_time_to_seconds(sock.getpeercert()["notAfter"])
        return int((not_after - datetime.now().timestamp()) // 86400)

def socket_conn(host, port, ctx):
    import socket
    raw = socket.create_connection((host, port), timeout=3)
    s = ctx.wrap_socket(raw, server_hostname=host)
    return s, raw
# probe 在内网可用；磁盘上的 PEM 用 days_until_expiry 离线巡检更稳
```

**追问 1**：为什么证书过期常发生在周末或凌晨？
提示：证书批量签发日期趋同（Let's Encrypt 90 天周期），过期时间落在签发对应时刻；凌晨是续期脚本与变更窗口重合点。

**追问 2**：连接池让证书问题更隐蔽还是更明显？
提示：池中长连接在证书过期后仍存活，故障是"滚动式"的——新连接全失败、老连接逐渐断开重建，故障呈缓升曲线，容易被当成应用问题。

**追问 3**：`sslmode=require` 与 `verify-full` 的差别在这次事故里意味着什么？
提示：require 只加密不校验身份（不防中间人），verify-full 校验主机名与 CA；应急降级只能降到 require，并留 24 小时回滚标记。

## 背诵要点
1. 证书过期故障特征：应用侧握手失败、DB 侧全健康、故障呈滚动式恶化（池内老连接掩盖问题）。
2. 防线三件套：PEM 离线解析 `notAfter` 巡检 + 30/14/7 天分档告警 + 过期证书演练。
3. 应急降级只有一档：`verify-full` → `require`（加密不验身份），并留审批与回滚时间窗。
