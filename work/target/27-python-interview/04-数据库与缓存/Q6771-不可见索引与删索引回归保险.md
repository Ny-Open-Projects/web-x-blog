### Q6771 · 删索引不敢删：INVISIBLE INDEX 的回归保险与秒级回滚

难度：P6 ｜ 标签：MySQL、INVISIBLE INDEX、索引治理、执行计划回滚、索引冗余

基线：Python 3.12；模拟优化器在索引可见/不可见两种状态下的计划选择与写路径维护成本，全标准库实跑。

**问**：库里有几十个疑似冗余索引，写路径白白多付维护成本，但谁都不敢删——删了之后某条长尾查询的计划突变，回滚要重建索引（小时级）。MySQL 8.0 的 INVISIBLE INDEX 是怎么解决"不敢删"的？可见性开关影响哪些路径、不影响哪些路径？正确的索引下线剧本是什么？

**答**：
- **结论**：INVISIBLE INDEX 把"删"拆成两步：`ALTER TABLE ... ALTER INDEX idx INVISIBLE` 让**优化器在选计划时完全忽略它**，但**索引物理上仍在、写路径照常维护**——相当于给这条索引做了一次"有真实流量、无真实代价转移"的灰度下线。观察窗口内如果有查询因失去它而劣化（长尾查询没进慢日志快照、计划缓存里有隐式依赖），只需一条 ALTER 恢复 VISIBLE，**秒级生效**；确认无依赖再 DROP，此时 DROP 的风险已经被窗口吸收。写代价在可见/不可见两种状态下完全一致——这是它和"禁用索引"类误解的关键分界：INVISIBLE 只关优化器，不关维护。
- **取舍**：① 观察窗口要覆盖周期性流量：周报、月结、季度任务用到该索引的概率不低，至少观察一个完整业务周期（通常两周）；② 不可见期间写路径成本不变，多个候选索引排队下线时逐个来，别一次全隐——排查计划劣化的归因会被污染；③ sys/schema_unused_indexes 是"未被使用"的证据，但 statistics 更新、外键、唯一约束对索引的隐式依赖不进 usage 计数，下线前先查依赖；④ 主从版本差异：8.0 以下从库不支持时，DDL 顺序要先升级从库，否则半程状态不一致。
- **实战**：① 建立"索引下线台账"：索引名、INVISIBLE 时间、观察到期时间、到期结论——没有台账的灰度等于白灰；② 观察期挂计划突变告警（慢日志中该表的新模式扫描）；③ 降序：先 INVISIBLE 两个周期 → 无劣化再 DROP → DROP 后的 disk 空间回收另算（Q6770 页合并账）；④ 新上的 ORACLE/pg 也同理：PG 没有原生 INVISIBLE，用 `pg_index.indisvalid=false` 或扩展模拟，语义差异要先确认。

```python
"""Q6771 不可见索引: 删索引前先 INVISIBLE 观察, 优化器忽略但写路径仍维护。"""
# 候选执行计划: (名称, 扫描代价, 依赖索引)
PLANS = [
    ("走 idx_status 回表", 120, "idx_status"),
    ("走 idx_status_created 复合", 45, "idx_status_created"),
    ("全表扫描", 900, None),
]


class Table:
    def __init__(self, invisible: set[str]):
        self.indexes = {"idx_status", "idx_status_created"}  # 物理上仍维护全部索引
        self.invisible = set(invisible)

    def choose_plan(self) -> tuple:
        visible_plans = [p for p in PLANS if p[2] is None or p[2] not in self.invisible]
        return min(visible_plans, key=lambda p: p[1])

    def write_row(self) -> int:
        # 写路径按"物理存在的索引"计费, 与可见性无关
        return 10 + 8 * len(self.indexes)


if __name__ == "__main__":
    t = Table(invisible=set())
    plan = t.choose_plan()
    write_cost_visible = t.write_row()

    # ALTER TABLE ... INDEX idx INVISIBLE: 只挡优化器, 不动写维护
    t.invisible.add("idx_status_created")
    plan2 = t.choose_plan()
    write_cost_invisible = t.write_row()

    print(f"可见时  : 优化器选 {plan[0]} (代价 {plan[1]})")
    print(f"置 INVISIBLE 后: 优化器选 {plan2[0]} (代价 {plan2[1]})")
    print(f"写路径代价: 可见 {write_cost_visible} vs 不可见 {write_cost_invisible} "
          f"(不变? {write_cost_visible == write_cost_invisible})")
    # 恢复可见 = 一条 ALTER 秒级回滚; DROP 则要重建索引(小时级)
    t.invisible.discard("idx_status_created")
    plan3 = t.choose_plan()
    print(f"恢复可见后: 优化器回到 {plan3[0]} (代价 {plan3[1]})")
    ok = (plan[0] == "走 idx_status_created 复合"
          and plan2[0] == "走 idx_status 回表"
          and plan3[0] == "走 idx_status_created 复合"
          and write_cost_visible == write_cost_invisible)
    print(f"校验: 优化器忽略+写路径仍维护+秒级回滚 -> {'通过' if ok else '异常'}")
    print("结论：INVISIBLE 是删索引的保险丝——只关优化器不关写维护;")
    print("      观察窗口过确认无计划依赖再 DROP, 回滚一条 ALTER 秒级生效")
```

**追问一**：INVISIBLE 期间写路径成本不变，那"下线索引"省写成本发生在哪一步？

→ 解析：发生在 DROP 之后。INVISIBLE 阶段只收获"计划安全性验证"，不收获任何写性能——这是很多人误以为"置 INVISIBLE 就省了写成本"的原因。真正的收益链：DROP 释放写维护开销 + 页空间，但 DROP 是不可逆的（回滚=重建索引，大表小时级）。所以经济账是：INVISIBLE 用两周的"白付维护成本"换 DROP 的风险验证，冗余索引数量大时这笔观察成本远小于一次误删的事故成本。批量治理时优先下线"宽索引/长字符列索引"——它们每行的维护成本最高，验证收益同样最高。

**追问二**：为什么不能用"影子环境跑全量流量回放"代替 INVISIBLE 观察窗口？

→ 解析：影子回放（Q2948 索引对比实验）能覆盖录制的流量，但覆盖不了"录制时刻不存在的查询"：新版本代码上线的查询、参数值落在录制分布之外的长尾、定时任务的新一轮取值。INVISIBLE 的本质优势是在**生产环境上让真实流量自己投票**——任何一条被漏掉的查询劣化都会以慢查询/超时形式暴露，且秒级可回滚。影子回放适合"删索引前的粗筛"（筛掉明显没人用的），INVISIBLE 窗口是"删索引前的终审"，两者是漏斗的两级而不是替代关系。只有读写比极高、流量可全量录制且变更窗口紧贴录制时间的场景，才可以用影子回放缩短窗口。
