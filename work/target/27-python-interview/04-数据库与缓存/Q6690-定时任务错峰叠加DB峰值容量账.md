### Q6690 · 每天整点一堆定时任务：叠加洪峰与数据库峰值容量账

难度：P6 ｜ 标签：容量规划、错峰调度、峰值叠加
基线：APScheduler / Celery beat；通用容量模型（峰值 QPS 预算）。

**问**：平时数据库 QPS 稳定在 3000，每天 10:00 整点必有一次尖峰冲到 12000，触发慢查询告警甚至连接池打满。排查发现十几个定时任务都配在整点。这类"调度叠加"的容量账怎么算？怎么排？

**答**：**结论**：账的分母不是日均 QPS 而是**峰值叠加 QPS = 业务峰值 + Σ(任务峰值)**。每个定时任务都是一个隐形负载源，把它的"执行时长内平均 QPS"加到业务曲线的同一时间点上。整点叠加是经典反模式：crontab/APScheduler 默认以整点、整分钟对齐，十几个任务自然同相位。治理三步：① **盘点**——把所有 beat/crontab 任务的触发时间、峰值 QPS、时长列成表；② **错峰**——按业务曲线低谷排布，把整点散开成 10:00/10:07/10:13...（用质数偏移避免再次对齐）；③ **限额**——任务侧限速（令牌桶）+ 连接池侧每任务独立池，保证任何任务失效不挤占业务连接。

**取舍**：错峰的代价是运维心智变化：任务时间不再"整齐"，监控告警按任务名聚合而不再按时间聚合；批处理窗口（对账类任务之间有依赖顺序）不能乱挪，要用 DAG 编排而不是简单错峰。另外限速值不是拍脑袋：任务允许占用 DB 的 QPS 配额 = (DB 峰值预算 − 业务 P95) × 任务占比，写进任务配置并监控超限。

**实战**：叠加账与错峰排布的模拟：

```python
# 定时任务叠加的容量账与错峰排布
import math

DB_PEAK_BUDGET = 9000          # DB 可承受峰值 QPS
biz_curve = {10: 3000, 11: 2800, 2: 500}   # 业务高峰在上午

tasks = {                       # 任务名: (整点时刻, 任务自身 QPS, 时长min)
    "报表聚合": (10, 1500, 20),
    "缓存预热": (10, 1200, 10),
    "对账扫描": (10, 900, 15),
    "积分结算": (10, 600, 30),
    "画像更新": (10, 500, 25),
}

peak_hour = max(biz_curve, key=biz_curve.get)
stack = biz_curve[peak_hour] + sum(q for t, q, _ in tasks.values())
print(f"10:00 整点叠加: 业务 {biz_curve[peak_hour]} + 任务 "
      f"{stack - biz_curve[peak_hour]} = {stack} QPS "
      f"(预算 {DB_PEAK_BUDGET} -> {'超限!' if stack > DB_PEAK_BUDGET else 'OK'})")

# 错峰排布：按业务低谷 + 质数分钟偏移
PRIMES = [7, 11, 13, 17, 19]
offsets = dict(zip(tasks, PRIMES))
for name, (_, q, dur) in tasks.items():
    minute = offsets[name]
    print(f"  {name}: 10:{minute:02d} 起，QPS {q}，时长 {dur}min")

def stacked_qps_at(minute: int) -> int:
    """某分钟正在运行的任务总 QPS（按分钟推进的简化模型）。"""
    running = 0
    for name, (_, q, dur) in tasks.items():
        start = offsets[name]
        if start <= minute < start + dur:
            running += q
    return biz_curve[peak_hour] + running

worst = max(stacked_qps_at(m) for m in range(60))
print(f"错峰后 10 点内最大叠加: {worst} QPS "
      f"(预算 {DB_PEAK_BUDGET} -> {'OK' if worst <= DB_PEAK_BUDGET else '仍超限'})")

# 任务配额与限速：剩余预算按占比分配
remaining = DB_PEAK_BUDGET - biz_curve[peak_hour]
total_task_q = sum(q for _, q, _ in tasks.values())
for name, (_, q, _) in tasks.items():
    quota = int(remaining * q / total_task_q * 0.9)
    print(f"  {name} DB 配额上限: {quota} QPS（超出则令牌桶限速）")
```

**追问 1**：为什么用质数偏移而不是均匀间隔错峰？
提示：均匀间隔（如每 5 分钟）在任务数增多后仍可能与其他系统的整 5 分钟任务对齐；质数偏移在不同任务集合、不同系统间重复相遇的周期被拉长。

**追问 2**：任务有依赖顺序（对账必须在结算前完成）怎么排？
提示：错峰之外引入 DAG 编排（Airflow/Celery chain），把"顺序约束"与"错峰约束"分开建模；不要用定时时间硬编码顺序。

**追问 3**：如果任务执行时长不可控（数据量波动），静态错峰失效怎么办？
提示：加自适应限速——任务运行时按 DB 等待事件/连接池水位动态调整并发；或分片调度器按 DB 负载信号放行批次。

## 背诵要点
1. 峰值叠加公式：DB 峰值预算 = 业务峰值 + Σ任务峰值；整点对齐是调度默认行为的叠加陷阱。
2. 治理三步：盘点任务清单（时刻/QPS/时长）→ 质数偏移错峰 → 任务侧限速配额（剩余预算×占比×0.9）。
3. 有依赖顺序的任务用 DAG 编排表达顺序，错峰只管负载均衡，两者别混在一个维度。
