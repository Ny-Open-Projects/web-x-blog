### Q6646 · 从库延迟监控与自动摘除

难度：P6 | 标签：读写分离、健康度路由、容量规划

**问**：读路由层挂在多个从库前，从库延迟多少该摘除？摘除后流量去哪？"自动摘除"和"告警人工介入"怎么取舍？

**答**：
- **结论**：摘除判据用双指标：复制健康（IO/SQL 线程正常）+ 延迟水位（lag > 阈值即摘）。阈值按业务定：能容忍读旧数据的展示类业务 500ms-1s，金额相关的读必须走主或 GTID 追踪路由。摘除后流量重分配到健康从库，全摘时回落主库并触发告警——回落主库必须有并发上限保护，否则把主库打死是二次事故。恢复是自动的：lag 回到阈值内自动回归流量池。
- **取舍**：自动摘除换来无人工值守，代价是摘除抖动（延迟在阈值边缘反复横跳）——要加滞回区间（摘除 1s、回归 300ms）与冷却时间。人工介入的好处是能结合"为什么延迟"（大查询？DDL？）判断摘除是否合理，代价是深夜无人。生产方案是自动摘除 + 分级告警：单从库摘除告警 P3，全摘告警 P1。
- **实战**：延迟采集别依赖 `Seconds_Behind_Master`（它是 0/NULL 语义陷阱，IO 断开时可能一直是 0），用位点差换算（binlog 位置或 GTID 事务数差 × 平均事务率）。路由层要保留"强制主库"的逃生通道（灰度开关、指定用户），处置延迟类事故时随时可切。

```python
import time

replicas = [
    {"name": "r1", "lag_ms": 120, "healthy": True},
    {"name": "r2", "lag_ms": 8000, "healthy": True},   # 刚被大查询拖住
    {"name": "r3", "lag_ms": 90,  "healthy": False},   # 复制断开
]
MAX_LAG_MS = 500

def pick_read():
    ok = [r for r in replicas if r["healthy"] and r["lag_ms"] <= MAX_LAG_MS]
    return min(ok, key=lambda r: r["lag_ms"])["name"] if ok else "primary"

def health_tick():
    """健康度巡检：延迟超阈值摘除；恢复后自动回归。"""
    for r in replicas:
        r["circuit"] = r["healthy"] and r["lag_ms"] <= MAX_LAG_MS
    return [r["name"] for r in replicas if r.get("circuit")]

print("当前路由到:", pick_read(), "可用从库:", health_tick())
replicas[0]["lag_ms"] = 900                       # r1 延迟劣化
replicas[2]["healthy"] = True; replicas[2]["lag_ms"] = 100   # r3 恢复
print("巡检后可用:", health_tick(), "路由到:", pick_read())
print("要点：延迟/健康双指标摘除，恢复自动回归；全摘时回落主库并触发告警")
```

**追问链**：
1. 追问一层：为什么 Seconds_Behind_Master 不可信？（IO 线程断开时值可能停在 0 或 NULL，它度量的是 SQL 线程相对 IO 的延迟而非真实主从差；生产用位点差自算）
2. 追问二层：全摘回落主库时怎么防止打死主库？（回落流量加并发上限与排队，同时读路径请求排队超时快速失败，给主库留出写容量）

**背诵要点**：
1. 摘除双指标：复制健康 + lag 阈值；滞回区间防抖动。
2. Seconds_Behind_Master 有语义陷阱，用位点差自算延迟。
3. 全摘回落主库要限流保护；恢复自动回归 + 分级告警。

**复盘追问**：
1. 摘除了延迟从库后用户投诉反而变多，可能是什么？（路由到了 lag 刚过阈值的从库，阈值过松；或主库回落导致主库延迟上升）
2. 为什么"告警发了没人处理"的从库延迟最终演变成全站事故？（延迟从库持续承接读流量，读旧数据只是表象，复制断开才是终局）
