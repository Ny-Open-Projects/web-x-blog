### Q6622 · 备份恢复后序列落后导致主键冲突事故复盘

难度：P6 ｜ 标签：事故复盘 / PostgreSQL / 序列

**问**：从逻辑备份（pg_dump）恢复一份库到新环境，业务一写入就报主键冲突；或者在主库上执行过大批量 INSERT 后手动把某些行"改 id"搬走，之后插入也偶发冲突。根因是什么？恢复和搬数场景各怎么防？

**答**：
- **结论**：根因是**序列（sequence）当前值落后于表中实际最大 id**。序列是独立于表数据的计数器：pg_dump 恢复时先建序列再 COPY 数据，若 dump/restore 流程或版本差异导致 `setval` 步骤漏掉/错位（或从部分数据、手工搬数的表恢复），序列值可能停在旧位置，下一次 `nextval()` 生成的 id 与已存在行撞车。MySQL 的 AUTO_INCREMENT 在 InnoDB 8.0 前重启后会按表最大值重算（5.7 重启丢当前值），PG 序列则**完全不会自动校准**。修复：`setval('t_id_seq', (SELECT max(id) FROM t))`，并留缓冲。防复发：恢复完成后做"序列 vs max(id)"的一致性校验，任何手工搬数（改 id、抽行合并）之后必须显式 setval。
- **取舍**：setval 设到 max(id) 还是 max+余量？设到 max(id) 是标准做法（下一值为 max+1）；但若恢复后立即有并发写入，先停写再 setval，否则校验瞬间到 setval 生效之间的写入已经在撞。批量导入场景（COPY 大量预置 id 的行）宁可校验后 setval，也不要在导入前"预留"大号段——号段预留会破坏 id 连续性审计假设。校验 SQL 要对**所有带序列的表**跑一遍，不是只查出事的这张。
- **实战**：① 恢复脚本末尾固化"序列校验步骤"，输出所有 `abs(seq_last - max_id)` 不为零的表；② 搬数 SOP 里把 setval 写成必做清单项；③ 监控插入主键冲突错误率——新环境灰度期第一个报错往往就是它；④ MySQL 5.7 场景额外注意重启后 AUTO_INCREMENT 重算带来的"值空洞"，与序列落后是两类问题但都会表现为冲突。

```python
# 序列一致性校验: 找出 seq 落后于 max(id) 的表并给出 setval 方案
# 基线: Python 3.9+ 标准库; 真实场景对接 information_schema/pg_catalog
from dataclasses import dataclass


@dataclass
class SeqTable:
    table: str
    seq_last: int      # 序列当前值 (last_value)
    max_id: int        # 表内实际最大 id
    is_used_by_rows: bool = True


def drift(t: SeqTable) -> int:
    """负数=序列落后(会冲突); 正数=序列超前(只空洞,不冲突)。"""
    return t.seq_last - t.max_id


def setval_statement(t: SeqTable) -> str:
    return f"SELECT setval('{t.table}_id_seq', {t.max_id});"


def audit(tables: list[SeqTable]) -> list[str]:
    return [setval_statement(t) for t in tables if drift(t) < 0]


def main() -> None:
    rows = [
        SeqTable("orders", seq_last=10234, max_id=10590),   # 恢复场景: 落后
        SeqTable("payments", seq_last=800, max_id=800),     # 正常
        SeqTable("ids_audit", seq_last=9900, max_id=9700),  # 超前: 只空洞
    ]
    assert drift(rows[0]) == -356     # 下一次 nextval 生成 10235 -> 冲突
    assert audit(rows) == [f"SELECT setval('orders_id_seq', 10590);"]
    assert drift(rows[2]) > 0 and not audit([rows[2]])
    print("落后表:", [t.table for t in rows if drift(t) < 0],
          "-> 全量 setval 到 max(id), 先停写再校准")
    print("OK: 序列不会自动校准, 恢复/搬数后必须显式 setval")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么"序列超前"无害而"序列落后"致命？id 空洞为什么通常可以接受？
→ 一句话提示：超前只浪费号段（下一值仍不与现有行冲突），落后必然撞已有主键；InnoDB 写入回滚/重启也会造成空洞，业务键唯一性靠唯一约束保证而不是靠连续性，所以空洞可接受、冲突不可接受。

**追问 2**：如果主键冲突已经写进去了几条重复 id（搬数场景没有唯一约束），怎么修？
→ 一句话提示：先按业务键找出真正的重复行并合并/删除，再补唯一约束，最后 setval 到修复后的 max(id)——顺序错了会把重复行永久固化在"看起来合法"的状态里。

## 背诵要点
- 序列独立于表数据，恢复/搬数后不会自动校准：seq_last < max(id) 必主键冲突。
- 修复 = 停写 + `setval(seq, max(id))` + 全表审计；超前只空洞、落后必冲突。
- MySQL 5.7 重启 AUTO_INCREMENT 重算与 PG 序列落后是两类同症状问题，都靠"插入冲突错误率"监控兜底。

## 复盘追问
- 为什么校验要对所有带序列的表跑而不是只查出事那张？提示：dump/restore 的 setval 缺失通常是全局性流程问题，只修一张等于给其余表埋雷。
- 逻辑复制（subscription）场景序列怎么同步？提示：序列不进逻辑复制流，订阅端序列需要故障切换时手动对齐（setval 到发布端当前值），这是切换演练清单项。
