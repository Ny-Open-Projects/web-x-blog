### Q6698 · 备份快照保留周期与存储成本账

难度：P6 ｜ 标签：成本工程、备份策略、快照、保留周期

基线：云 RDS 自动备份/快照；对象存储分层（标准/低频/归档）。

**问**：一个 2TB 的数据库，现在的备份策略是"每天一个全量快照、保留 30 天"，月底账单一算备份存储比数据库本身还贵。这笔账哪里错了？科学的备份保留策略怎么定？

**答**：
- **结论**：错误在于"每天全量 × 线性保留"——2TB × 30 = 60TB 的账（即使云厂商做了增量去重，跨快照的独占存储仍随保留天数线性涨）。科学做法是 **祖-父-子（GFS，Grandfather-Father-Son）**：日备保 7 天、周备保 4~5 份、月备保 12 份、年备 1~2 份，总留存 ≈ 7×2TB 等效（增量后实际更小），却覆盖"昨天的误删/上周的误删/上月的合规需求"不同恢复粒度。再叠加分层：老快照转归档存储（价格 1/5~1/10，恢复慢）。
- **取舍**：保留天数不是越长越好——RPO 决定"最近多频繁"（日备 + binlog 增量做到分钟级 RTO 数据点），RTO 决定"恢复要多快"（归档存储恢复可能按小时计费且耗时数小时，不能当主力恢复通道）。合规要求（如金融 5 年）用"少量年备 + 归档/不可变存储（WORM）"满足，不用堆高频快照。
- **实战**：账的公式：月存储成本 = Σ(各层快照数 × 平均独占增量) × 单价。增量快照的独占量 ≈ 两次快照间的变更页比例（写占比高的库增量独占大，去重收益小——这笔也要入账）。

```python
# 备份保留成本账：线性保留 vs GFS + 分层（标准库可运行）。
def linear_cost(db_tb: float, days: int, unit_per_tb_month: float) -> float:
    return days * db_tb * unit_per_tb_month

def gfs_cost(db_tb: float, unit_per_tb_month: float,
             daily: int = 7, weekly: int = 4, monthly: int = 12,
             yearly: int = 1, archive_ratio: float = 0.0,
             archive_discount: float = 0.15, incr_share: float = 0.4):
    """GFS：日备为全量参考，周/月/年按增量独占比例 incr_share 折算。
    archive_ratio: 月备/年备中转归档存储的份额。"""
    cost = daily * db_tb * unit_per_tb_month               # 日备：全量
    cost += weekly * db_tb * incr_share * unit_per_tb_month  # 周备：增量独占
    long_term = monthly * db_tb * incr_share + yearly * db_tb
    cost += long_term * (1 - archive_ratio) * unit_per_tb_month
    cost += long_term * archive_ratio * unit_per_tb_month * archive_discount
    return round(cost, 1)

if __name__ == "__main__":
    price = 30.0     # 每 TB 每月
    print("线性30天全量:", round(linear_cost(2, 30, price)), "元/月")   # 1800
    print("GFS 不分层:", gfs_cost(2, price), "元/月")
    print("GFS 月年备归档 80%:", gfs_cost(2, price, archive_ratio=0.8), "元/月")
    # 1800 -> 864 -> 627 量级，且覆盖日/周/月/年完整恢复粒度。
```

**追问**：
- 一层：为什么写占比高的库，增量快照省不了多少？→ 提示：两次快照间变更页比例高，独占增量接近全量。
- 二层：binlog/事务日志备份在 RPO 账里扮演什么角色？→ 提示：快照定基线、日志补增量，分钟级 RPO = 日备 + 持续日志，日志存储量按写带宽×保留小时另算。
- 三层：怎么验证备份真的可用？→ 提示：定期恢复演练（每月拉一个快照到隔离环境跑校验），备份的 SLA 是"能恢复"不是"有文件"。

**背诵要点**：
1. 每天×30 的线性全量保留是成本黑洞；GFS（7 日/4 周/12 月/1 年）+ 归档分层可降一个数量级。
2. RPO 决定频率（日备+日志增量=分钟级），RTO 决定通道（归档恢复慢，不能当主力）。
3. 增量收益与写占比反相关；备份有效性靠每月恢复演练，不是文件存在。

**复盘追问**：
1. 当初为什么定 30 天全量？提示：策略抄默认值，没人做过恢复场景拆解（谁要恢复、恢复到何时）。
2. 如果合规要求"任意一天可回溯 5 年"，怎么设计？提示：年备+WORM 归档+关键日历点快照，而不是 1825 个日快照。
