### Q6593 · Cache-Aside 的残余竞态：读旧值回写与版本化缓存条目

> 难度:★★★★ | 标签:缓存一致性, 竞态, Redis

**问**：都说"先更库再删缓存"基本安全，为什么线上还是偶发缓存里是旧值？教科书方案剩下的那个竞态窗口长什么样，怎么彻底关掉？

**答**：结论："先更库后删缓存"仍有一个残余竞态：**读请求在删缓存之后、从旧主从库读到旧值，再回写缓存**——此后缓存长期停留旧值。教科书讨论的"更新库与删缓存交错"之外，真正的高发根因是"读旧库（从库延迟）+ 回写"。彻底关掉的三板斧：① 缓存条目带数据版本号（value 里嵌 `updated_at`/binlog 位点），回写时 `SET only-if-newer`（Lua 比较）拒绝旧版本覆盖新版本；② 读路径只用写路径同源的主库/强一致副本；③ binlog 订阅兜底再删一次（延迟窗口对冲）。①是核心，它把"时序正确性"从"删得及时"转嫁到"写入时版本可比较"。

竞态时序（最小窗口）：
- t1 读请求 miss，查从库得 v1 → t2 写请求更新主库为 v2 并删缓存 → t3 读请求把 v1 SET 进缓存 → 之后所有读命中 v1，直到 TTL 过期。从库延迟越大、TTL 越长，脏得越久。
- 版本化条目解法：SET 时带 v2，t3 回写 v1 时 Lua 里 `if new.ver < old.ver then reject`——旧值进不去。比对键可用数据自带的 `updated_at`，无需额外发号。

```python
# 基线:Python 3.9+ / redis-py 4.x(真实 SET 用 Lua 比较);缺库降级见 MemCache
try:
    import redis
    HAS_REDIS = True
except ImportError:
    HAS_REDIS = False

COMPARE_LUA = """
local old = redis.call('HGET', KEYS[1], 'ver')
if old and tonumber(ARGV[1]) < tonumber(old) then return 0 end
redis.call('HSET', KEYS[1], 'ver', ARGV[1], 'val', ARGV[2])
return 1
"""

class MemCache:                              # 缺库降级:同样语义的进程内实现
    def __init__(self) -> None:
        self.d: dict[str, dict] = {}
    def set_if_newer(self, key: str, ver: int, val: str) -> int:
        old = self.d.get(key)
        if old and ver < old["ver"]:
            return 0
        self.d[key] = {"ver": ver, "val": val}
        return 1
    def get(self, key: str):
        return self.d.get(key)

def put(client, key: str, ver: int, val: str) -> int:
    if HAS_REDIS:
        r = redis.Redis()
        return r.eval(COMPARE_LUA, 1, key, ver, val)
    return client.set_if_newer(key, ver, val)

if __name__ == "__main__":
    c = MemCache()
    print(put(c, "item:1", ver=2, val="v2"))     # 新版本先到
    print(put(c, "item:1", ver=1, val="v1"))     # 迟到的旧值回写被拒
    print("缓存终值:", c.get("item:1")["val"])
    assert c.get("item:1")["val"] == "v2"
```

**追问**：
- 一层追问：版本号从哪来？——优先复用业务数据自带的 `updated_at`（秒级精度可能撞，用毫秒/微秒）；严格序列用 binlog 位点或 DB 序列；分布式无时钟可用写序号表。版本源本身必须与写入同事务产生，否则又是新的竞态。
- 二层追问：等值版本怎么处理？——同版本两次写入值可能不同（非幂等写），规则应写成"新版本覆盖，等版本看内容哈希，旧版本拒绝"；多数业务把写做成幂等后，等版本覆盖无害。
- 三层追问：为什么不干脆读写都走主库？——主库扛全部读的容量代价大；工程折中是"写后短窗口内该用户的读粘主库"（会话粘主）+ 其余走从库，配合版本化条目，把一致性成本只花在需要的人身上。
