### Q6626 · 数据库任务队列表（SKIP LOCKED 轮询）积压与消费吞吐的容量账

难度：P6 ｜ 标签：容量规划 / 队列表 / SKIP LOCKED

**问**：用 PG 一张任务表当队列（`FOR UPDATE SKIP LOCKED` 轮询），高峰入队 500 任务/s，20 个 worker 每轮 `LIMIT 10`、任务平均处理 200ms，队列还是越积越多。积压增长速率怎么算？调大 LIMIT、加 worker、缩轮询间隔哪个有效？

**答**：
- **结论**：先算账。单 worker 吞吐 = 每轮任务数 / (轮询周期) 但受任务时长约束：worker 每 200ms 完成一份任务，即 5 任务/s；20 worker = 100 任务/s < 入队 500/s，缺口 400/s，积压每秒 +400。判断瓶颈次序：worker 吞到 100 说明**消费速率 = worker 数 / 单任务时长**，轮询间隔和 LIMIT 都不是当前瓶颈——它们只在"每轮拿不满"时才影响。有效手段排序：加 worker（到数据库扛得住的连接与锁竞争上限）> 降单任务时长（批量处理、异步化外部调用）> 入队侧限流/削峰（上游排队）。轮询成本账也别忽略：每轮 SELECT ... FOR UPDATE SKIP LOCKED 是一次索引扫+锁探测，`interval=1s × 20 worker = 20 QPS` 空轮询可接受，但如果 interval 50ms 且 LIMIT 大，空转流量会成为 DB 的额外负担。积压增速公式：`dQ/dt = 入队速率 − min(worker/时长, DB 上限)`。
- **取舍**：加 worker 到多少停？两个约束：连接数（每 worker 一池连接，20→100 worker 就是 100 级并发连接，叠加其他业务池要过 Q6584 连接数账）与行锁竞争（SKIP LOCKED 避免了互相阻塞，但同一批待领任务的索引扫竞争随 worker 数上升，轮询 QPS = worker/interval）。更好的路径常常是降时长：任务内 200ms 里若 150ms 是同步外呼，改异步回调后单任务 50ms，20 worker 就有 400 任务/s，不加机器先翻 4 倍。
- **实战**：① 队列表必须有 `status + created_at` 索引，领任务查询 `WHERE status='pending' ORDER BY created_at LIMIT n FOR UPDATE SKIP LOCKED`，否则每次扫描全表；② 加"领取时间"字段做租约，worker 崩溃任务可回收；③ 监控 backlog 曲线斜率与领取延迟（created_at 到 start 的时差），斜率转正是扩容信号；④ 积压超阈值自动降级：非关键任务延迟入队或丢弃计数。

```python
# 队列容量账: dQ/dt = 入队 - min(worker/时长, DB上限); 轮询成本 = worker/interval
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class QueuePlan:
    enqueue_rps: float
    workers: int
    task_s: float
    interval_s: float

    def consume_rps(self) -> float:
        return self.workers / self.task_s

    def backlog_slope(self) -> float:
        return self.enqueue_rps - self.consume_rps()

    def poll_qps(self) -> float:
        return self.workers / self.interval_s


def main() -> None:
    p = QueuePlan(enqueue_rps=500, workers=20, task_s=0.2, interval_s=1.0)
    assert p.consume_rps() == 100
    assert p.backlog_slope() == 400          # 每秒积压 +400
    # 缩 interval 到 0.2: 吞吐不变, 轮询 QPS 从 20 涨到 100(白烧)
    p2 = QueuePlan(500, 20, 0.2, 0.2)
    assert p2.consume_rps() == p.consume_rps()
    assert p2.poll_qps() == 100
    # 降单任务时长到 50ms: 20 worker -> 400/s, 不加机器补齐缺口
    p3 = QueuePlan(500, 20, 0.05, 1.0)
    assert p3.consume_rps() == 400 and p3.backlog_slope() == 100
    print(f"20w: {p.consume_rps():.0f}/s 缺口{p.backlog_slope():.0f}; "
          f"任务降时长 -> {p3.consume_rps():.0f}/s")
    print("OK: 轮询间隔/LIMIT 不是瓶颈时调它白烧; 顺序=降时长>加worker>限流入队")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 SKIP LOCKED 能让多 worker 不互相阻塞？它没解决的问题是什么？
→ 一句话提示：被锁住的行直接跳过，各领各的；但它不解决"领取后崩溃任务卡死"（需要租约+超时回收）与"重复入队幂等"（需要业务唯一键），这两个是队列表方案的另一半工程。

**追问 2**：什么时候应该放弃队列表改用真消息队列？
→ 一句话提示：积压长期存在且需要削峰/扇出/多消费者模型，或任务要与 DB 事务外的系统交互——队列表强在"与业务数据同事务入队"（事务发件箱同源，Q6644），弱在横向扩展与重投递语义，超过这个边界就换 MQ。

## 背诵要点
- 积压斜率 = 入队 − worker/单任务时长；消费瓶颈在任务时长时，调轮询间隔/LIMIT 是白烧轮询 QPS（= worker/interval）。
- 提速优先级：降单任务时长（异步化外呼）> 加 worker（受连接数与锁竞争约束）> 入队限流。
- 队列表三件套：status+created_at 索引、租约超时回收、业务唯一键幂等；与业务同事务入队是它对 MQ 的核心优势。

## 复盘追问
- 怎么用"领取延迟"指标区分是消费慢还是入队突发？提示：领取延迟（created_at→start）长期上升是消费能力不足；平时低、突发尖峰后回落是入队脉冲，解法在削峰而不是常态扩容。
- worker 崩溃后租约回收怎么避免任务双跑？提示：回收只把任务回 pending，执行端必须幂等（唯一键/状态机），租约机制只负责"不丢"，幂等负责"不重"。
