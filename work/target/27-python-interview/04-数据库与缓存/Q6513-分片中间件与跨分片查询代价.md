### Q6513 · 数据库分片：分片键与跨分片代价

> 难度:★★★ | 标签:分库分表, 分片键, 扩容

**问**：订单表 10 亿行要分 64 片——分片键选 user_id 还是 order_id？「广播查询」的代价怎么估？分片扩容（hash 一致性 / range 重平衡）的迁移怎么做，Python 应用层路由中间件的职责边界在哪？

**答**：① 分片键原则：**最高频查询路径上的等值条件**当分片键。订单业务「按 user 查订单」占 90% 流量 → user_id 分片；用 order_id 分片则 user 维度查询变 64 分片广播（64 倍连接与排序合并），业务等于废掉。跨分片场景（admin 按时间查全部订单）是低频后台查询，可走异构方案（ES/数仓同步），不拖 OLTP。② 分片算法：**hash(取模) vs range**——hash 均匀但扩容要迁数据（一致性哈希减量，Q2329/1218 已覆盖理论）；range 按时间自然滚动但热点集中。③ 扩容迁移：双写新旧分片 → 回填 → 切读 → 删旧（同 A109/Q6017 的 expand-contract 心智）；④ 应用层路由中间件职责：SQL 解析取分片键 → 路由计算 → 执行合并；**它不做**：跨分片事务协调（交给业务幂等/SAGA，Q7509）、跨分片 JOIN（禁止，应用层组装）。

```python
# 全部标准库；demo 实现一致性哈希路由 + 双写迁移模拟
import hashlib, bisect

class ConsistentRouter:
    """一致性哈希分片路由：虚拟节点减数据迁移量。"""
    def __init__(self, shards: list[str], vnodes: int = 100):
        self.ring = []                          # (hash, shard) 有序表
        self.shards = set(shards)
        for s in shards:
            for v in range(vnodes):
                h = int(hashlib.md5(f"{s}#vn{v}".encode()).hexdigest()[:8], 16)
                self.ring.append((h, s))
        self.ring.sort()

    def route(self, key: str) -> str:
        h = int(hashlib.md5(key.encode()).hexdigest()[:8], 16)
        i = bisect.bisect(self.ring, (h, ""))
        return self.ring[i % len(self.ring)][1]

    def migration_cost(self, new_shards: list[str]) -> float:
        """扩容时需要迁移的数据比例：一致性哈希 ≈ N/(N+M)。"""
        old = ConsistentRouter(sorted(self.shards))
        new = ConsistentRouter(sorted(self.shards | set(new_shards)))
        moved = sum(1 for k in (f"key{i}" for i in range(10000))
                    if old.route(k) != new.route(k))
        return moved / 10000

def broadcast_cost(n_shards: int, qps: int, per_query_ms: float) -> dict:
    """跨分片广播代价估算：分片数 × 连接与合并成本。"""
    return {"fanout": n_shards,
            "connections": n_shards * (qps // 100),
            "merge_ms": per_query_ms * n_shards}

if __name__ == "__main__":
    r = ConsistentRouter([f"shard{i}" for i in range(8)])
    loc = {}
    for u in ("alice", "bob", "carol"):
        loc[u] = r.route(u)
    print("路由:", loc)
    print("8→10 片迁移比例:", f"{r.migration_cost(['shard8', 'shard9']) * 100:.1f}%",
          "（理论 ≈ 2/10=20%）")
    print("64 分片广播:", broadcast_cost(64, 1000, 2))
    # 口径：跨分片广播是设计污点——90% 流量必须落在单分片；低频广播走数仓。
    # 中间件职责：解析分片键→路由→合并；跨片事务/JOIN 不做，业务侧幂等+SAGA。
```

**追问**：1) 没有天然分片键的业务怎么办？——合成键：全局 ID 嵌入分片位（Snowflake 变体：高位分片号），按 ID 查直达、按 user 查走冗余索引表（user_id→id 列表）；「写扩散」（每个 user 的 order_id 写入 user 索引分片）是经典代价转移。2) 分片后再想按时间清理数据怎么办？——range 分片天然按时间删分区；hash 分片要靠 TTL 列 + 各分片后台扫描（删除也是写，注意批量控制，Q6503 vacuum 联动）。3) 为什么跨分片 JOIN 不做？——中间件做 JOIN = 分布式执行计划引擎（成本极高且易错），业务层「先查 A 片取 id → 按 id 路由查 B」的应用组装在 95% 场景足够。

## 背诵要点
1. 分片键 = 最高频等值查询条件；跨分片广播是设计污点，低频广播走 ES/数仓。
2. 扩容迁移比例：一致性哈希 ≈ M/(N+M)；迁移走双写→回填→切读→删旧。
3. 中间件三职责（解析/路由/合并）与三不做（跨片事务/JOIN/DDL 协调）。

## 复盘追问
1. user_id 分片后「商家查自己所有订单」这种第二个维度的查询怎么办？（提示：异构索引表（写扩散到商家维度分片）或 ES，读路径冗余是分片的必然代价）
2. 分片键写错了（按 order_id 分了片）还能救吗？（提示：只能重迁移；教训是分片键决策要按「读流量分布」数据化评审）
