### Q6792 · 索引统计采样与执行计划漂移：20 个采样页如何决定走哪个索引

难度：P6 ｜ 标签：InnoDB、统计信息、采样、执行计划漂移、ANALYZE、optimizer_trace

基线：MySQL 5.7/8.0；Python 3.12 用页级分层抽样复现估算方差与计划翻转率，全标准库实跑。

**问**：没人改 SQL、没人加索引，一条查询白天走 `idx_a` 晚上走 `idx_b`，耗时差 5 倍。`innodb_stats_persistent=ON` 不是把统计信息落盘了吗，为什么还会漂？统计信息到底怎么"采样"出来的？两个真实成本只差 2% 的索引，估算误差有多大？线上怎么定位"这次计划变化是统计噪声还是数据真的变了"？

**答**：

- **结论**：持久化只解决"重启后统计不从零开始"，**不解决估算精度**。InnoDB 统计信息的核心是**页级随机采样**：`innodb_stats_persistent_sample_pages`（默认 20）决定从索引里随机取多少页，在这些页上数记录、数不同值，再按页数比例外推整表。20 页对一张几万页的表是 0.1% 量级的样本，遇到**值聚集**（同一状态码集中在少数页）时，估算误差轻松到 2～5 倍。优化器拿这个估算行数乘代价系数选索引，当两个候选索引的真实代价接近（差 2%），估算噪声就足以让计划在两个索引之间来回翻——这就是"计划漂移"。非持久化模式更差：`innodb_stats_transient_sample_pages` 默认 8 页，且统计随元数据变化被重置。
- **取舍**：把 `sample_pages` 从 20 提到 200 能把估算标准差压到约 1/3，但 `ANALYZE TABLE` 的耗时近似线性上涨（每页都是随机 IO，大表上从秒级到分钟级），而且对**极度倾斜**的列仍然不够——这时正确手段是直方图（`ANALYZE TABLE ... UPDATE HISTOGRAM`）或改写查询消掉对该列的依赖，而不是无限加采样页。另一条路是**钉住计划**：MySQL 8.0 用 `/*+ INDEX(t idx) */` 这类 hint 或 `SET_VAR` 固定关键 SQL，代价是数据分布变了也不会自动变好，需要人跟着复查。
- **实战**：某订单表在晚高峰前跑了一次定时 `ANALYZE`，`status='PAID'` 的查询从 `idx_status_time` 切到 `idx_user_status`，QPS 掉 40%。对比 `EXPLAIN` 的 `rows` 与 `EXPLAIN ANALYZE` 的 actual rows：估算 3200、实际 41000，差了 12 倍；查 `mysql.innodb_index_stats` 发现 `stat_value` 在两次 ANALYZE 之间从 4.1 万跳到 3.2 千——不是数据变了，是两次采样抽到的页不同。最后把该表的采样页提到 128、给 `status` 建直方图，并对这条 SQL 加了 `INDEX` hint；同时把"ANALYZE 后自动比对关键 SQL 的 rows 估算与实际"做成巡检项。

下面用分层页采样复现：同样的数据、不同的随机种子，估算值能差多少，计划能翻多少次。

```python
# 页级采样方差 → 计划翻转率
import math
import random
import statistics

PAGES = 1000
ROWS_PER_PAGE = 100
TRUE_ROWS = 108          # 目标值真实行数: 100k 行里的 0.108%


def make_pages():
    """构造聚集分布: 20 个页装了 90 行, 另 180 页零星 18 行, 其余页为 0。"""
    sel = [0.0] * PAGES
    for i in range(20):
        sel[i] = 0.045
    for i in range(20, 200):
        sel[i] = 0.001
    return sel


PAGE_SEL = make_pages()
assert abs(sum(PAGE_SEL) * ROWS_PER_PAGE - TRUE_ROWS) < 1e-6


def estimate(k, rnd):
    """无放回抽 k 页, 用样本均值外推行数。"""
    idx = rnd.sample(range(PAGES), k)
    return sum(PAGE_SEL[i] for i in idx) / k * PAGES * ROWS_PER_PAGE


def trial(k, n=400, seed=7):
    rnd = random.Random(seed)
    return [estimate(k, rnd) for _ in range(n)]


for k in (8, 20, 200):
    est = trial(k)
    print(f"[1] 采样 {k:>3} 页: 均值 {statistics.mean(est):.0f} 行, "
          f"标准差 {statistics.pstdev(est):.0f}, 极差 {max(est) - min(est):.0f}")
s8, s20, s200 = (statistics.pstdev(trial(k)) for k in (8, 20, 200))
print(f"    → 实测 标准差比 s8/s200 = {s8 / s200:.1f}, 接近 sqrt(200/8)={math.sqrt(25):.1f}")
assert 4 < s8 / s200 < 6

# 两个索引真实成本几乎相同: A = 100 + n, B = 120 + 0.8n
def cost_a(n):
    return 100 + n


def cost_b(n):
    return 120 + 0.8 * n


print(f"[2] 真实行数 {TRUE_ROWS}: costA={cost_a(TRUE_ROWS):.0f}, costB={cost_b(TRUE_ROWS):.0f}, "
      f"差 {abs(cost_a(TRUE_ROWS) - cost_b(TRUE_ROWS)) / max(cost_a(TRUE_ROWS), cost_b(TRUE_ROWS)):.1%}"
      f" → 真实最优是 B")
# 决策分界: 100+n = 120+0.8n → n=100; 估算低于 100 就会误选 A
print(f"[3] 决策分界 n_est=100, 真实行数 {TRUE_ROWS} 只比它高 8%, 余量极薄")

for k in (8, 20, 200):
    est = trial(k)
    wrong = sum(1 for n in est if cost_a(n) <= cost_b(n))
    print(f"    采样 {k:>3} 页: 偏离真实最优选 A 的比例 {wrong / len(est):.0%}")
    if k == 20:
        flip20 = wrong / len(est)
est8, est200 = trial(8), trial(200)
f8 = sum(1 for n in est8 if cost_a(n) <= cost_b(n)) / len(est8)
f200 = sum(1 for n in est200 if cost_a(n) <= cost_b(n)) / len(est200)
print(f"    → 实测 8 页误选 {f8:.0%}, 200 页误选 {f200:.0%}; 采样越少, 计划越像掷硬币")
assert f8 > f200
assert 0.15 < flip20 < 0.85, "接近同价的两个索引, 默认采样下计划本就该不稳定"
print("    → 实测 估算标准差超过两索引真实代价差时, 计划切换与数据变化无关")
```

**追问一**：`innodb_stats_persistent` 落盘了，为什么重启后 `rows` 还是会变？—— 落盘的是**上一次采样结果**，重启不重算，所以理论上应稳定。会变的场景有三类：① `innodb_stats_auto_recalc=ON` 时表数据变动超过约 10% 会触发后台重算，重算就是重新抽 20 页；② DDL（加索引、改列、`OPTIMIZE`）会重置/重算统计；③ 从库回放或 `ALTER TABLE ... ALGORITHM=INPLACE` 重建表后统计重建。所以"落盘"保证的是启动稳定性，不保证运行期稳定。定位时要看 `mysql.innodb_table_stats.last_update` 和 `innodb_index_stats.last_update` 的时间戳，和计划变化的时间点对齐。

**追问二**：既然采样噪声这么大，为什么优化器不干脆精确统计？—— 精确统计要全索引扫描，一张十亿行的表扫一遍是分钟级 IO，且 `ANALYZE` 期间占资源；统计信息是"给优化器用的近似"，追求的是**足够好且便宜**，不是精确。工程上的正解是分层：默认采样保证大多数查询够用；对少数关键 SQL 用直方图补倾斜列的分布；对已经验证过最优计划的 SQL 用 hint 钉住；再用"估算 vs 实际行数"的巡检发现哪些表需要特殊对待。把 `sample_pages` 全局调到几千是拿所有表的 ANALYZE 时间换少数表的精度，不划算。

## 背诵要点

- 持久化 ≠ 精确：`innodb_stats_persistent` 只把上次采样结果落盘，默认 `sample_pages=20`，非持久化 `transient_sample_pages=8`。
- 估算标准差随采样页数按 `1/sqrt(k)` 下降；值聚集时误差可达数倍，两个索引真实代价差小于噪声时计划必然翻来翻去。
- 定位三件套：`EXPLAIN` 的 rows vs `EXPLAIN ANALYZE` 的 actual、`mysql.innodb_index_stats.stat_value/last_update` 的时间线、`optimizer_trace` 看各候选的估算代价。

## 复盘追问

- 同一条 SQL 白天走 A 索引晚上走 B 索引，怎么证明是统计噪声而不是数据倾斜变化？（比对两次 `innodb_index_stats.last_update` 与 `stat_value`，再用 `EXPLAIN ANALYZE` 看估算/实际比）
- 采样页从 20 调到 200 有什么代价、什么情况下调了也没用？（ANALYZE 随机 IO 线性上涨；极度倾斜列需直方图或改写，采样再多也只是逼近一个本就失真的页均值）
