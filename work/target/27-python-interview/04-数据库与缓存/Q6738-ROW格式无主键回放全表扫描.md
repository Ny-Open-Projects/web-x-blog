### Q6738 · ROW 格式下没有主键的 UPDATE：从库回放退化成全表扫描

难度：P7 ｜ 标签：MySQL、binlog、ROW 格式、主从延迟、无主键表

基线：Python 3.12；MySQL 8.0 `binlog_format=ROW`、`binlog_row_image`、`slave_rows_search_algorithms`。

**问**：一张日志表没建主键，只有一个普通索引 `idx_biz(biz_id)`。主库上 `UPDATE log SET status = 2 WHERE biz_id = 7` 很快，但从库延迟一路涨到几十分钟，`SHOW PROCESSLIST` 里回放线程跑的是 `UPDATE log SET ... WHERE 所有列 = ...` 的全表扫描。同一条改动，为什么主库快、从库慢？

**答**：
- **结论**：`ROW` 格式的 binlog 记录的是**行变更前后的镜像**，回放时从库必须定位到具体那一行。有主键 → 直接用主键 `WHERE id = ?` 精确定位（一次索引查找）；没主键 → 只能用 `slave_rows_search_algorithms` 指定的策略在**整行所有列**上找匹配：普通索引不唯一，命中后还要逐列比对，退化路径就是全表扫。开启 `HASH_SCAN` 能把多行查找合并成一次扫描，但依然是"扫全表 + 哈希比对"。
- **取舍**：`ROW` 最安全（不依赖执行上下文，`NOW()`/`RAND()`/`@@session` 都确定），代价是行镜像体积与回放成本；`STATEMENT` 体积小、回放走原 SQL 能用索引，但有不确定性函数风险，已被主流弃用。无主键表在 `ROW` 下几乎是"复制性能杀手"，尤其高频 UPDATE、宽表、大表。
- **实战**：① 所有表必须有主键（没有业务主键就自增/雪花），这是复制、在线 DDL、CDC 的硬前提；② 存量无主键表用 gh-ost/pt-osc 在线补主键；③ 监控 `performance_schema` 里回放线程的慢语句与 `Handler_read_*`；④ `binlog_row_image=minimal` 可减小镜像体积，但要确认 CDC 订阅方不依赖完整行。

```python
"""ROW 回放定位：有主键一次查找，无主键退化为全列比对。"""


def find_by_pk(rows: list[dict], pk: dict) -> tuple[int | None, int]:
    """主键定位：模拟 B 树一次查找，返回 (行下标, 比较次数)。"""
    key, val = next(iter(pk.items()))
    for i, row in enumerate(rows):
        if row[key] == val:
            return i, 1
    return None, len(rows)


def find_by_full_image(rows: list[dict], image: dict) -> tuple[int | None, int]:
    """无主键：扫描所有行，逐列比对 before-image。"""
    comparisons = 0
    for i, row in enumerate(rows):
        match = True
        for col, val in image.items():
            comparisons += 1
            if row[col] != val:
                match = False
                break
        if match:
            return i, comparisons
    return None, comparisons


if __name__ == "__main__":
    rows = [{"biz_id": i % 50, "status": 1, "note": f"n{i}"} for i in range(20000)]
    target = 19999
    before = dict(rows[target])

    idx, pk_cost = find_by_pk([{"row_id": i} for i in range(20000)], {"row_id": target})
    print("有主键定位: 命中行", idx, "| 比较次数", pk_cost)

    idx2, cost = find_by_full_image(rows, before)
    print("无主键全列定位: 命中行", idx2, "| 列比较次数", cost)
    print("  行数 20000 -> 比较次数随行数线性增长，这就是回放慢的根因")

    # 加上 HASH_SCAN：一次扫描建哈希，但仍要扫全表
    def hash_scan(rows: list[dict], images: list[dict]) -> tuple[int, int]:
        table = {}
        scans = 0
        for i, row in enumerate(rows):
            scans += 1
            table.setdefault(tuple(sorted(row.items())), []).append(i)
        hits = 0
        for img in images:
            hits += len(table.get(tuple(sorted(img.items())), []))
        return scans, hits

    scans, hits = hash_scan(rows, [before])
    print("HASH_SCAN: 扫描行数", scans, "| 命中", hits, "-> 仍是一次全表扫")

    print("结论：无主键 + ROW = 从库按全列定位；补主键才是根治")
```

**追问一**：`binlog_row_image` 的三个取值区别？
→ 解析：`full`（默认）记录所有列的前后镜像；`minimal` 只记录主键 + 被修改的列，体积小，但 CDC 订阅方拿不到未修改列的完整行；`noblob` 不记录未修改的 TEXT/BLOB。用 `minimal` 前必须确认下游不依赖完整行镜像。

**追问二**：无主键还会拖慢什么？
→ 解析：在线 DDL——gh-ost/pt-osc 按主键分块拷贝与校验，没主键只能全表 chunk 或退到唯一键，冲突检测也难；还有 `UPDATE`/`DELETE` 影响行数统计不准、触发器方案容易漏行、按主键分页导出无法实现。所以"补主键"是收益最广的一次整改。
