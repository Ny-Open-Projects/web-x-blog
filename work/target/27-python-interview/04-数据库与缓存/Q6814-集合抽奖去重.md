### Q6814 · 集合抽奖去重：差集候选、唯一约束兜底与并发互斥

难度：P6 ｜ 标签：集合运算、差集、抽奖去重、唯一约束、并发互斥、事务

基线：SQLite 3.45（复合主键 + 手动事务）；用差集子查询 + 唯一约束实测抽奖去重的并发互斥，全标准库实跑。

**问**：营销活动的抽奖功能要求"一个用户在同一奖池最多中一次"。同事的实现是"先查已中奖名单，从候选里排除，再随机抽、插入中奖记录"——压测时同一用户中了两奖。集合运算（差集）在 SQL 里怎么表达？"先查后插"的竞态窗口到底有多大？为什么说唯一约束是唯一可靠的防线？

**答**：

- **结论**：抽奖去重本质是**集合差集**问题：可中奖集合 = 全体候选 − 已中奖集合，SQL 里 `WHERE id NOT IN (SELECT user_id FROM winners WHERE pool=?)`（或 NOT EXISTS / LEFT JOIN ... IS NULL）一步算出。但"算出候选再插入"是两步操作，两笔并发事务在**同一时刻读差集**（此时彼此都还没提交插入），看到同一个候选集，于是都抽中同一人——这就是竞态窗口，它的大小不是毫秒级而是"从读差集到提交插入"的整个事务期。**唯一防线只有数据库约束**：`winners(user_id, pool)` 上建复合唯一键，插入时撞键即失败（PG 可用 `ON CONFLICT DO NOTHING` 平滑吸收），"先查后插"的查询结果只能用于**展示**，永远不能用于**判定**。
- **取舍**：差集的三种写法语义有别：`NOT IN` 在子查询含 NULL 时整个返回空集（经典陷阱，列上有 NOT NULL 约束时才安全）；`NOT EXISTS` 半连接语义最稳且能吃索引；`LEFT JOIN ... IS NULL` 在旧版 MySQL 上有时更优。去重的兜底层级也要分清：应用内存去重是第一层（挡住明显重复请求），唯一约束是最后一层（并发下的真值），中间任何"先查后插"都不是防线。跨奖池的语义用键设计表达：`UNIQUE(user_id, pool)` 允许同一人中多个奖池，`UNIQUE(user_id, activity)` 则限制一活动一奖——语义放键里，不要放代码 if 里。随机抽取本身用 `ORDER BY RANDOM() LIMIT k` 对大候选集代价高，生产上应把随机性放在应用层（随机起点 + keyset 取段）或用确定性伪随机（如对 user_id 做散列排序）以便审计复现。
- **实战**：一次大促抽奖，压测发现 0.3% 的用户中了两个奖：抽奖服务是三副本部署，三副本同时读到"该用户未中奖"的差集。修复链：中奖表加 `(user_id, pool)` 复合唯一键（存量数据先清洗重复）；插入改 `INSERT ... ON CONFLICT DO NOTHING` 并以受影响行数判断成败，撞键的用户自动回退重抽下一个候选；对外发奖以"插入成功"为唯一凭证（发奖消息由插入成功的事件驱动），不再信任内存里的"我抽中了"。上线后双中奖归零，且撞键率成为监控指标（异常撞键率上升 = 出现脚本刷奖）。

下面用差集子查询 + 复合唯一约束实测完整的抽奖去重与并发互斥。

```python
# Q6814 集合抽奖去重: 差集候选计算 + 唯一约束兜底 + 并发互斥
import sqlite3

conn = sqlite3.connect(":memory:")
conn.executescript("""
CREATE TABLE users(id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE winners(                                  -- 中奖记录: 唯一约束守门
  user_id INTEGER, pool TEXT,
  PRIMARY KEY(user_id, pool)                           -- 同一用户同一奖池只中一次
);
INSERT INTO users(name) VALUES('u1'),('u2'),('u3'),('u4'),('u5');
""")
conn.commit()

def draw(pool, k):
    """从『未在该奖池中奖』的候选差集里随机抽 k 人"""
    rows = conn.execute("""
        SELECT id, name FROM users
        WHERE id NOT IN (SELECT user_id FROM winners WHERE pool = ?)   -- 差集
        ORDER BY (id * 2654435761) % 97                                -- 确定性伪随机
        LIMIT ?
    """, (pool, k)).fetchall()
    ins = """INSERT INTO winners(user_id, pool) VALUES(?,?)"""
    for uid, _ in rows:
        try:
            conn.execute(ins, (uid, pool))
        except sqlite3.IntegrityError as e:
            print(f"    守门生效: user {uid} 已中奖被拒 ({e})")
    conn.commit()
    return rows

a1 = draw("pool-a", 3)
print(f"[1] pool-a 首抽 3 人: {[r[1] for r in a1]}")

# [2] 重抽差集: 已中奖者自动从候选中消失
a2 = draw("pool-a", 5)
print(f"[2] pool-a 补抽: 只能再中 {[r[1] for r in a2]} (前 3 人已不在候选)")
assert {r[1] for r in a2}.isdisjoint({r[1] for r in a1})
allw = conn.execute("SELECT count(*) FROM winners WHERE pool='pool-a'").fetchone()[0]
assert allw == 5

# [3] 并发互斥: 两笔事务同时抽同一人 → 唯一约束拦截第二笔
conn2 = sqlite3.connect(":memory:")
conn2.executescript("""
CREATE TABLE users(id INTEGER PRIMARY KEY);
CREATE TABLE winners(user_id INTEGER, pool TEXT, PRIMARY KEY(user_id, pool));
INSERT INTO users VALUES(1),(2);
""")
conn2.isolation_level = None                      # 手动事务
conn2.execute("BEGIN")
conn2.execute("INSERT INTO winners VALUES(1,'p')")   # 事务 A 插入 user1
try:
    # 另一路并发: 先查差集发现 user1 未中(读不到未提交数据), 也插 user1
    pend = conn2.execute("SELECT id FROM users WHERE id NOT IN (SELECT user_id FROM winners)")
    conn2.execute("INSERT INTO winners VALUES(1,'p')")
    conn2.execute("COMMIT")
    print("[3] 并发双插未拦截 (异常)")
except sqlite3.IntegrityError as e:
    print(f"[3] 并发双插被唯一约束拦截: {e}")
    conn2.execute("ROLLBACK")
n = conn2.execute("SELECT count(*) FROM winners").fetchone()[0]
print(f"    事务内未提交可见性: 另一路读差集时 user1 {'不在' if n else '在'} 已中集合, 插入仍被主键拦下")

# [4] 多奖池互斥语义: 同一用户可中不同奖池, 但同池重复被拒
try:
    conn.execute("INSERT INTO winners(user_id, pool) VALUES(1,'pool-a')")
except sqlite3.IntegrityError:
    print("[4] 同池重复被拒; 跨池(pool-b)不受影响")
conn.execute("INSERT INTO winners(user_id, pool) VALUES(1,'pool-b')")
print("    → 实测 候选=差集子查询, 兜底=复合唯一约束; 先查后插永远有竞态窗口, 唯一支路是 INSERT 守门")
```

**追问一**：为什么"先查后插"在单机单事务里也可能出错？READ COMMITTED 与 REPEATABLE READ 下这个窗口有什么差别？—— 单事务内先查后插，如果只有这一个事务在跑，没有竞态；问题永远来自**两笔并发事务**。READ COMMITTED 下每条语句读最新已提交快照，A 插入未提交时 B 的差集查询看不到它，窗口最大；REPEATABLE READ 下 B 用事务开始时的快照，A 已提交的插入也可能看不到（快照陈旧），窗口同样存在——差异只是窗口的形状，不是有无。唯一可靠的是约束级防线：唯一键冲突在存储层判定，与快照隔离级别无关。

**追问二**：抽奖要求"可审计可复现"，随机性怎么设计？—— `ORDER BY RANDOM()` 每次结果不同且无法复现，审计时无法证明"当时确实抽的是这几个人"。可复现的做法：把随机种子（活动 ID + 开奖时间戳 + 服务端 nonce）先落库公示，再以种子驱动确定性伪随机（对候选 ID 做散列排序取前 k），开奖后任何人可以用同一候选集 + 同一种子重放验证。候选集快照（开奖时刻的差集结果）也要留存，否则事后候选变化（有人提前退出）会导致重放不一致。这两个留存物合起来构成完整的抽奖审计链。

## 背诵要点

- 可中奖集合 = 差集子查询（NOT IN 有 NULL 陷阱，NOT EXISTS 最稳）；差集结果只能用于展示，不能用于判定。
- 并发互斥唯一可靠防线是复合唯一约束（user_id, pool）+ INSERT 撞键处理；"先查后插"的窗口 = 从读差集到提交的全事务期。
- 可审计抽奖：种子先落库公示 + 候选集快照留存 + 确定性伪随机重放；发奖以插入成功为唯一凭证。

## 复盘追问

- 压测发现 0.3% 用户中两个奖，你怎么复现并证明是竞态而不是重复请求？（用两线程并发执行"读差集→插入"并注入延迟放大窗口，稳定复现撞键；再对比加唯一约束后归零）
- `INSERT ... ON CONFLICT DO NOTHING` 吸收了撞键，怎么区分"正常重复参与"与"脚本刷奖"？（撞键率按用户/设备维度监控，正常活动撞键率应接近 0，持续非零上升即刷奖特征）
