### Q6625 · 数据库超时阶梯（statement_timeout / lock_timeout / 请求预算）与积压容量规划

难度：P7 ｜ 标签：容量规划 / 超时 / PostgreSQL

**问**：线上出现过一次慢查询风暴：一条统计 SQL 变慢后，应用侧 30s 超时重试，DB 连接瞬间被占满，整个库雪崩。为什么不"给数据库设个超时"就能防住？超时阶梯应该怎么设计、怎么和请求预算对齐？

**答**：
- **结论**：超时是**分层预算分配**问题：一次用户请求 1s 预算，要被 HTTP 网关 → 应用 → 数据库三层瓜分，且每层必须给上游留收尾余量（应用收到取消还要写日志/释放连接）。核心阶梯（从内到外递增）：`lock_timeout`（毫秒级，拿不到锁快失败）< `statement_timeout`（秒级，单条 SQL 上限）< 应用侧 statement 预算 < 请求总预算。不设 DB 超时的恶果：慢 SQL 只靠应用 30s 超时退出，但**连接还挂在数据库里执行**（客户端超时不通知服务端），池被耗尽；设了阶梯后慢 SQL 在 DB 侧几百毫秒就被终止，连接归还，故障半径是一条 SQL。经验基线：`lock_timeout` 100-500ms、`statement_timeout` 按角色分级（OLTP 1-3s、报表会话单独放宽到分钟级并限制并发数）。
- **取舍**：statement_timeout 设多短？设太短会误杀合理慢查询（复杂 join、扫历史分区）。做法是按"角色/业务"分档而不是全局一刀切：OLTP 角色严、分析角色宽且限并发；用 `SET LOCAL`（事务级）下发，避免改全局参数。重试策略与超时联动：被 statement_timeout 杀掉的查询不值得原样重试（大概率再超时），要降级走预聚合/缓存或拒绝。
- **实战**：① SQLAlchemy 层用 `options={"options": "-c statement_timeout=3000"}` 在连接串下发；② 每类请求定义预算表：请求 1s = 网关 0.05 + 应用编排 0.2 + DB 0.5 + 余量；③ 监控被 timeout 终止的 SQL 计数（pg_stat_statements + 日志 `canceling statement due to statement timeout`），超时率突增就是计划回归的信号；④ 重试封装区分"锁超时可重试（短退避）"与"语句超时不原样重试"。

```python
# 超时阶梯: 内层必须严格小于外层预算并留收尾余量
# 基线: Python 3.9+ 标准库
from dataclasses import dataclass


@dataclass
class TimeoutLadder:
    request_budget_s: float
    gateway_s: float
    app_overhead_s: float          # 编排/序列化
    statement_timeout_s: float
    lock_timeout_ms: int

    def check(self) -> list[str]:
        errs = []
        db_budget = self.request_budget_s - self.gateway_s - self.app_overhead_s
        if self.statement_timeout_s >= db_budget:
            errs.append("statement_timeout 吃掉了应用收尾余量")
        if self.lock_timeout_ms >= self.statement_timeout_s * 1000:
            errs.append("lock_timeout 必须 << statement_timeout")
        return errs


def reserve_ratio(l: TimeoutLadder) -> float:
    """DB 可用预算占请求预算比例, 应 <= 0.6 留余量。"""
    usable = l.request_budget_s - l.gateway_s - l.app_overhead_s
    return l.statement_timeout_s / l.request_budget_s


def main() -> None:
    ok = TimeoutLadder(1.0, 0.05, 0.2, 0.5, 300)
    assert not ok.check()
    assert reserve_ratio(ok) == 0.5                # 留 0.25s 收尾
    bad = TimeoutLadder(1.0, 0.05, 0.2, 0.9, 1000)
    assert any("余量" in e for e in bad.check())   # 0.9 > 0.75 可用预算
    assert any("lock_timeout" in e for e in bad.check())
    print(f"OK 阶梯: lock 300ms < stmt 0.5s < 请求 1s, DB 预算占比 "
          f"{reserve_ratio(ok):.0%}")
    print("OK: 客户端超时不通知服务端 -> 慢 SQL 必须由 DB 侧阶梯终止")


if __name__ == "__main__":
    main()
```

**追问 1**：应用侧超时退出后，数据库里那条 SQL 会怎样？为什么"客户端超时"防不了连接耗尽？
→ 一句话提示：SQL 继续在服务端跑到自然结束（除非发 cancel），连接不归还池——所以防雪崩的关键阶梯在 DB 侧（statement_timeout）而不在客户端。

**追问 2**：为什么 lock_timeout 与死锁重试策略要联动设计？
→ 一句话提示：lock_timeout 快失败让持锁等待变成可重试错误（短退避+抖动），比在锁队列里硬等（阻塞自己也阻塞后面排队者）更快释放锁队列，整体吞吐反而更高。

## 背诵要点
- 超时阶梯：lock_timeout(100-500ms) < statement_timeout(OLTP 1-3s) < 应用预算 < 请求预算，内层 ≤ 外层 60% 留收尾余量。
- 客户端超时不终止服务端 SQL——防连接耗尽必须靠 DB 侧阶梯；按角色分档用 SET LOCAL 下发，不一刀切。
- 语句超时不值得原样重试：降级（预聚合/缓存）或拒绝；锁超时可短退避重试。

## 复盘追问
- 慢查询风暴里"重试放大"和"超时缺失"哪个是主因？提示：两者叠加——没有 DB 侧阶梯时重试把池占满（Q7541 重试风暴同源），但根修是加阶梯让故障半径缩到单条 SQL。
- 报表会话怎么"宽而不失控"？提示：独立角色放宽 statement_timeout 到分钟级 + 会话级并发上限 + 走只读副本，宽是读预算宽、不是连接预算宽。
