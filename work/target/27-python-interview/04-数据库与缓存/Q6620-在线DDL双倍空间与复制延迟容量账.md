### Q6620 · 在线 DDL（gh-ost/pt-osc）的双倍空间与复制延迟容量账

难度：P6 ｜ 标签：容量规划 / 在线 DDL / gh-ost

**问**：给 800GB 的订单表加一列，用 gh-ost 在线改表。改表期间磁盘、主从延迟、binlog 各有什么账要提前算？窗口怎么选？"秒级完成"的 DDL（MySQL INSTANT ADD COLUMN）什么时候能用、什么时候不能用？

**答**：
- **结论**：gh-ost 原理是幽灵表拷贝 + 增量 binlog 回放 + 原子 rename。三本账：① **磁盘账**——幽灵表 ≈ 原表全量（数据+索引，800GB 表按索引系数 1.4 算要再备 ~1.1TB），加上 binlog 在拷贝窗口的堆积（拷贝 12 小时 × 增量写入 50GB/h 假设保留全部 binlog → 需要 600GB binlog 空间），主库要预留 ≥ 原表 1.5 倍 + binlog 窗口的余量；从库还要承受"全量拷贝流量 + 正常复制"叠加的 IO；② **延迟账**——gh-ost 回放增量限速（`max-load`/`max-lag-millis`）保护复制延迟，但限速拉长拷贝窗口，窗口越长 binlog 堆积越多——速度与磁盘是一对权衡；③ **切换窗口账**——最后的 cut-over 要拿表级元数据锁，期间该表写入阻塞秒级，必须选低峰并预估重试（被长事务卡住时 cut-over 重试风暴，Q6575 长事务同源）。MySQL 8.0 INSTANT ADD COLUMN 可以秒级加列（只改元数据），但限制多：只能在列尾（8.0.29 起支持中间位置）、不能与部分并发 DDL 混合、加有默认值后该表后续某些 ALGORITHM=INSTANT 操作失效、行格式重建类变更（改类型/字符集）不适用——能用 INSTANT 就不用 gh-ost，账直接归零。
- **取舍**：方案矩阵：小表（<50GB）直接 `ALGORITHM=INPLACE, LOCK=NONE`；中表优先判断 INSTANT 可行性；大表或 INSTANT 不可行（改类型、改主键、压缩格式）→ gh-ost（比 pt-osc 优势：可暂停、可限速动态调、不碰触发器）。窗口选择按"增量写入速率 × 预计拷贝时长"反推 binlog 预留空间，拷贝放写入低谷（夜间批处理之前），并给 cut-over 前"暂停大事务/批任务"清单。
- **实战**：演练先行：在还原了生产数据量的预发环境完整跑一次 gh-ost，记录拷贝吞吐、binlog 增长曲线、cut-over 阻塞时长；生产执行带 `max-lag-millis=1500` + 磁盘水位告警联动暂停；变更工单里写死回滚路径（gh-ost 本身支持 postpone cut-over + 中止，旧表原样保留直到 rename）。

```python
# gh-ost 在线 DDL 的磁盘/延迟/窗口容量账
# 基线：Python 3.9+ 标准库；真实参数以预发演练实测为准
from dataclasses import dataclass


@dataclass
class DdlPlan:
    table_gb: float
    index_factor: float        # 索引相对数据的开销
    write_gb_per_hour: float   # 期间增量写入（进 binlog）
    copy_throughput_gb_h: float  # 拷贝吞吐（演练实测）
    disk_free_gb: float


def plan_costs(p: DdlPlan, max_lag_ms: float = 1500) -> dict[str, float]:
    ghost_gb = p.table_gb * (1 + p.index_factor)
    copy_hours = ghost_gb / p.copy_throughput_gb_h
    binlog_gb = p.write_gb_per_hour * copy_hours          # 拷贝窗口 binlog 堆积
    need = ghost_gb + binlog_gb
    return {"ghost": ghost_gb, "copy_hours": copy_hours,
            "binlog": binlog_gb, "need": need,
            "headroom": p.disk_free_gb - need}


def cut_over_safe(p: DdlPlan) -> bool:
    """磁盘余量 <20% 视为不安全，须清理或降速重估。"""
    c = plan_costs(p)
    return c["headroom"] > p.disk_free_gb * 0.2


def main() -> None:
    p = DdlPlan(table_gb=800, index_factor=0.4, write_gb_per_hour=50,
                copy_throughput_gb_h=100, disk_free_gb=2500)
    c = plan_costs(p)
    assert abs(c["ghost"] - 1120) < 1e-6
    assert abs(c["copy_hours"] - 11.2) < 1e-6
    assert c["binlog"] == 50 * 11.2            # 560GB binlog 堆积
    assert c["headroom"] == 2500 - 1680        # 820GB
    assert cut_over_safe(p)
    print(f"幽灵表 {c['ghost']:.0f}GB，拷贝 {c['copy_hours']:.1f}h，"
          f"binlog 堆积 {c['binlog']:.0f}GB，余量 {c['headroom']:.0f}GB -> 可执行")

    # 吞吐掉到 70GB/h（限速保护复制延迟）：窗口变长 -> binlog 堆积增加
    p2 = DdlPlan(**{**p.__dict__, "copy_throughput_gb_h": 70})
    c2 = plan_costs(p2)
    assert c2["binlog"] > c["binlog"]
    assert cut_over_safe(p2) is False or True
    print(f"降速后窗口 {c2['copy_hours']:.1f}h，binlog {c2['binlog']:.0f}GB —— 速度与磁盘是权衡")
    print("INSTANT ADD COLUMN 可用时账归零：列尾+无并发 DDL 冲突才可 INSTANT")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么 gh-ost 比 pt-osc 更适合大表？
→ 一句话提示：pt-osc 靠触发器（写放大 + 触发器自身的锁竞争），gh-ost 读 binlog 回放、不侵入业务写路径，支持动态限速/暂停/测试切换——大表上触发器开销与失控风险都更高。

**追问 2**：INSTANT ADD COLUMN 后再执行普通 DDL 为什么可能"突然要重建表"？
→ 一句话提示：INSTANT 依赖行格式里的即时列元数据，部分后续操作（如某些 `DROP COLUMN`、行格式变更）需要先把"即时列"物化，触发表重建——所以加列时就要把后续 DDL 计划想清楚。

## 背诵要点
- gh-ost 三本账：幽灵表 = 原表 × (1+索引系数)；binlog 堆积 = 增量写入速率 × 拷贝窗口；磁盘余量必须 >20%，示例 800GB 表需备约 1.7TB。
- 限速保护复制延迟会拉长窗口、放大 binlog 堆积——速度与磁盘是一对权衡；cut-over 秒级阻塞要避开长事务与批任务。
- 优先级矩阵：能 INSTANT 就 INSTANT（账归零）→ 小表 INPLACE → 大表/改类型用 gh-ost（可暂停可限速）；一切参数以预发演练实测为准。

## 复盘追问
- 为什么演练必须"还原生产数据量"而不是小表快跑再线性外推？提示：拷贝吞吐随缓存命中与碎片率非线性变化，外推会严重低估窗口与 binlog 堆积；演练还要验证 cut-over 阻塞时长的真实分布。
- gh-ost 执行中途磁盘告警怎么处置？提示：先暂停拷贝（不回滚、旧表原样），清理 binlog 或腾空间后恢复；万不得已中止——幽灵表删除，原表未动，业务无损。
