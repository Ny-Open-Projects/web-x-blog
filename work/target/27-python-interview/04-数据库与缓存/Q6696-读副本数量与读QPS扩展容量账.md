### Q6696 · 读副本数量与读 QPS 扩展容量账

难度：P6 ｜ 标签：容量规划、读写分离、读副本、复制延迟

基线：MySQL 8.0 主从/半同步；读写分离中间件或应用侧路由。

**问**：主库写 2000 QPS、读 20000 QPS，单机读 QPS 承载上限约 8000。加读副本能线性扩吗？副本要加到几台？加副本有什么隐藏代价？

**答**：
- **结论**：读副本扩的是"读吞吐"，不是线性免费——每加一个副本，主库要多承担一份 binlog 传输与 dump 线程，且副本要重放全部写入：**副本上的读容量 = 副本单机承载 - 该机回放写所占的资源**。写越多，每个副本能分出的净读容量越少，所以"写重的系统加副本收益递减"。上限还受两个约束：(1) 复制延迟约束——业务能容忍的旧读窗口决定副本不能落后多少；(2) 成本约束——N 副本 = N 倍存储费用。
- **取舍**：读扩容的替代方案优先级：加缓存（挡 80%+ 点查）> 优化慢查询（降单请求成本）> 加副本。副本还有非读用途：延迟副本做误操作防线、专副本跑报表隔离。
- **实战**：账的算式——净读容量 = 单机总承载 ×(1 - 回放写占比)；需要副本数 = ceil(读 QPS / 净读容量) + 1 冗余；同时验证复制延迟 SLO：高峰写带宽 (MB/s) 与副本回放单线程能力（8.0 并行回放依赖 WRITESET/逻辑时钟）匹配。

```python
# 读副本扩容账：写占比、缓存分流、延迟约束一起算（标准库可运行）。
import math

def replica_plan(read_qps: int, write_qps: int, per_node_total_qps: int,
                 cache_hit: float = 0.0, repl_write_cost_per_node: float = 0.0):
    """per_node_total_qps: 单机可承载 QPS 上限（读写混合口径）
    cache_hit: 缓存挡掉的读比例
    repl_write_cost_per_node: 副本上回放写占用本机承载的比例(0~1)"""
    read_after_cache = read_qps * (1 - cache_hit)
    # 副本回放写占比：写量与主库相同，相对单机承载的比例
    repl_cost = max(repl_write_cost_per_node, write_qps / per_node_total_qps)
    net_read_per_replica = per_node_total_qps * (1 - repl_cost)
    n = math.ceil(read_after_cache / net_read_per_replica)
    return {
        "读(缓存后)": int(read_after_cache),
        "副本净读容量": int(net_read_per_replica),
        "所需副本数": n,                       # +1 冗余由调用方决定
        "副本数(含1冗余)": n + 1,
    }

if __name__ == "__main__":
    print(replica_plan(read_qps=20000, write_qps=2000, per_node_total_qps=8000))
    # 无缓存：读 20000 / 副本净读 6000 -> 需要 4 副本（含冗余 5）
    print(replica_plan(read_qps=20000, write_qps=2000, per_node_total_qps=8000,
                       cache_hit=0.75))
    # 加 75% 命中缓存：读降到 5000 -> 1 副本即可（含冗余 2）
    print(replica_plan(read_qps=20000, write_qps=6000, per_node_total_qps=8000))
    # 写涨到 6000：副本净读只剩 2000，读扩容收益被写吃掉 -> 提示走分库分表
```

**追问**：
- 一层：为什么写占比高时加副本无效？→ 提示：每个副本都要全量回放写，写是"广播成本"，读是"分摊收益"。
- 二层：复制延迟怎么纳入这笔账？→ 提示：延迟窗口 ≈ 写带宽/回放速率，读一致性要求高的请求路由回主库（会读命中反噬主库，需要单独预留容量）。
- 三层：8.0 什么参数让回放并行化？→ 提示：`replica_parallel_workers` + ` binlog_transaction_dependency_tracking=WRITESET`（8.0.26 后默认行为变化）。

**背诵要点**：
1. 副本净读容量 = 单机承载 ×(1-回放写占比)；写是广播成本，写重系统加副本收益递减。
2. 读扩容优先级：缓存 > 慢查询优化 > 加副本；强一致读回主库要单独预留容量。
3. 副本数公式 ceil(缓存后读QPS/净读容量)+1 冗余；并行回放靠 WRITESET 依赖追踪。

**复盘追问**：
1. 为什么当时先加了两台副本而不是先查慢查询？提示：复盘"加机器反射"，检查是否有单请求成本数据。
2. 强一致读流量占比多大时读写分离开始失效？提示：做主库读流量占比监控，超阈值重新分账。
