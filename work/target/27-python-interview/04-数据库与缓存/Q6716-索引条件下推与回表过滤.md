### Q6716 · 索引条件下推：回表前先过滤掉多少行

难度：P6 ｜ 标签：ICP、回表、联合索引、执行计划

基线：Python 3.12；MySQL 5.6+ 索引条件下推（ICP）；纯 Python 模拟引擎层与 Server 层过滤。

**问**：联合索引 `(city, age, name)`，查询 `WHERE city='杭州' AND age > 20 AND name LIKE '%张%'`。`name` 不在索引的最左前缀里，按老经验这个条件只能回表后过滤。但 `EXPLAIN` 显示 `Using index condition`，扫描行数比回表行数大很多。这个 `Using index condition` 到底省了什么？

**答**：
- **结论**：`Using index condition` 是 **索引条件下推（ICP）**：把本来要回表后才能判断的条件下推到存储引擎，在索引页上先过滤，只有通过的行才回表。例子里 `name LIKE '%张%'` 虽然不能用于定位（无法走索引范围），但可以在索引记录上先判断，过滤掉大量不匹配的行，减少随机回表次数。
- **取舍**：ICP 只对**二级索引**有效，且条件下推后仍要回表取其他列；它能显著减少回表，但不减少索引扫描量（该扫的索引页还是要扫）。如果条件本身选择性差，ICP 省的回表有限；如果 `name` 是前缀匹配 `'张%'`，那它能参与索引范围，根本不需要 ICP。
- **实战**：① 看 `EXPLAIN` 的 `rows`（预估扫描）与 `filtered`（过滤后比例），两者差距大说明 ICP/过滤有效；② 高频的模糊查询考虑全文索引/倒排，而不是指望 ICP；③ 联合索引列顺序按等值→范围→剩余过滤排列，让更多条件能在索引内完成；④ 用 `EXPLAIN ANALYZE` 对比开/关 `optimizer_switch='index_condition_pushdown=off'` 的实际回表次数。

```python
def scan_without_icp(index_rows: int, match_ratio: float) -> dict[str, int]:
    return {"index_scanned": index_rows, "rows_back_to_table": index_rows,
            "rows_returned": int(index_rows * match_ratio)}


def scan_with_icp(index_rows: int, match_ratio: float) -> dict[str, int]:
    # 索引页上先过滤，只有匹配的才回表
    return {"index_scanned": index_rows,
            "rows_back_to_table": int(index_rows * match_ratio),
            "rows_returned": int(index_rows * match_ratio)}


if __name__ == "__main__":
    n, ratio = 200_000, 0.02
    a = scan_without_icp(n, ratio)
    b = scan_with_icp(n, ratio)
    print("无 ICP:", a)
    print("有 ICP:", b)
    print(f"回表次数下降 {a['rows_back_to_table'] / b['rows_back_to_table']:.0f} 倍")
```

**追问一**：ICP 为什么不能用在聚簇索引（主键）上？
→ 解析：聚簇索引的叶子节点就是整行数据，不存在"先过滤再回表"的两阶段——读到索引记录时已经拿到了全部列，条件下推没有额外收益。ICP 的价值只在"二级索引 + 需要回表"的场景。

**追问二**：`Using index condition` 和 `Using index` 有什么区别？
→ 解析：`Using index` 是**覆盖索引**，查询所需列全在索引里，根本不回表；`Using index condition` 只是把条件下推到索引层，仍然要回表取未覆盖的列。前者省的是回表，后者省的是"不必要的回表"，量级不同。
