### Q6607 · 慢查询治理的算力成本账：索引 ROI 与升配取舍

难度：P6 ｜ 标签：成本工程 / 慢查询 / 索引

**问**：DBA 月报说某云数据库 CPU 常年 75%，报价单：升级规格到下一档月费 +3000 元；另一个方案是花两周治理 Top 20 慢查询。老板问：治理的"省钱账"怎么算？什么情况下直接升配更划算？

**答**：
- **结论**：算力成本账的核心公式：`DB 总成本 ≈ 规格费 × (CPU/IO 利用率决定的冗余系数)`。CPU 75% 意味着实际有效算力只用了规格的 1/1.33；慢查询通常贡献了大部分无效算力——一条被调用量大的全表扫描查询，可能占掉总 CPU 的 20-30%。治理 ROI 账：`月节省 ≈ (慢查询 CPU 占比 × 升配成本增量)`，如果 Top 20 慢查询占 30% 算力，治理掉一半等于省下 15% 规格 = 每月几百到上千，且随业务增长持续复利；升配则是把账推给下个季度。
- **取舍**：决策框架：① **结构差的查询**（缺索引、回表翻倍、隐式转换）→ 治理优先，边际成本一次、收益永久，还降 IO/锁风险；② **结构性增长**（业务量翻倍导致全部查询等比变慢）→ 升配/分片是正解，治理只是拖延；③ 紧急窗口（大促前两周）→ 升配保平安，治理排期到大促后。混合策略：先升配止血 + 治理降本，治理见效后再降配回收。注意"降配验证"：治理后 CPU 降下来要真降配才算省到钱，否则账是纸面的。
- **实战**：账目拆解步骤：① 从 `pg_stat_statements`/慢日志按 `total_exec_time × 调用量` 排序，算每类查询的 CPU/IO 占比；② 对 Top 查询逐条估修复收益（EXPLAIN 前后 cost/rows 差 × 频次）；③ 折算成规格档位：`目标利用率 = 当前 CPU × (1 - 治理收益占比)`，看能否落到下一档；④ 把"索引新增/修改"走工单评审（写放大是代价，见 Q6564），治理清单按"收益/风险"排序两周内落地；⑤ 月度复盘账：云账单变化 vs 治理投入人力。

```python
# 慢查询算力成本账：按 CPU 占比排序 + 规格档位测算（标准库模拟）
# 基线：Python 3.9+

from dataclasses import dataclass


@dataclass
class SlowQuery:
    name: str
    cpu_share: float      # 该查询占总 CPU 的比例（0-1）
    fixable: bool         # 是否可治理（缺索引/可改写）
    fix_gain: float       # 治理后自身耗时降低比例


def spec_ladder(cpu_pct: float, tiers: list[tuple[str, float]]) -> tuple[str, float]:
    """按利用率 70% 上限选最小规格，返回 (档位, 月费)"""
    for name, fee in tiers:
        if cpu_pct <= 0.70:
            return name, fee
        cpu_pct /= 2.2   # 下一档约 2.2 倍算力
    return tiers[-1][0], tiers[-1][1]


def cost_account(queries: list[SlowQuery], tiers: list[tuple[str, float]]) -> None:
    total_bad = sum(q.cpu_share for q in queries if q.fixable)
    total_gain = sum(q.cpu_share * q.fix_gain for q in queries if q.fixable)
    cur_cpu = 0.75
    now_name, now_fee = spec_ladder(cur_cpu, tiers)
    after_cpu = cur_cpu * (1 - total_gain)
    after_name, after_fee = spec_ladder(after_cpu, tiers)
    print(f"可治理算力占比 {total_bad:.0%}，治理收益 {total_gain:.0%}")
    print(f"治理前: {now_name} ¥{now_fee}/月（CPU {cur_cpu:.0%}）")
    print(f"治理后: {after_name} ¥{after_fee}/月（CPU {after_cpu:.0%}）")
    print(f"年化节省 ¥{(now_fee - after_fee) * 12}")


def main() -> None:
    tiers = [("small", 800), ("mid", 1700), ("large", 3800), ("xlarge", 8600)]
    queries = [
        SlowQuery("订单列表无索引全扫", 0.22, True, 0.9),
        SlowQuery("报表 COUNT(*) 大表", 0.08, True, 0.8),
        SlowQuery("业务增长型 OLTP", 0.30, False, 0.0),
        SlowQuery("其他杂项", 0.15, False, 0.0),
    ]
    cost_account(queries, tiers)
    # 结构差的查询占 30% 算力，治理收益 22% → 应能降一档
    total_gain = 0.22 * 0.9 + 0.08 * 0.8
    assert total_gain > 0.15
    print("OK: 治理收益折算成规格档位与月费差")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么新增索引不是"免费"的降本手段？
→ 一句话提示：索引拖慢写入（写放大）、占磁盘与内存（挤占 buffer pool 热页）、增加备份与迁移时长，所以要用工单评审权衡读收益与写代价，并监控索引使用率清理无用索引。

**追问 2**：CPU 利用率提到多高该触发升配？
→ 一句话提示：常态 70% 左右是留峰值余量的通用线，但要结合 P99 延迟与队列等待看——利用率高而延迟平稳说明还有余量，利用率 60% 但 P99 抖动说明瓶颈可能不在 CPU（IO/锁），升配无效。

## 背诵要点
- 算力成本账公式：慢查询治理的月节省 ≈ 治理收益的 CPU 占比 × 升配档位差；结构差的查询一次治理永久复利，结构性增长只能升配/分片。
- 排序口径用 `total_exec_time × 频次`（CPU/IO 占比），不是单次耗时；治理后必须真降配才算省到钱。
- 索引是双刃剑：读收益 vs 写放大/内存挤占，走工单评审 + 使用率监控回收。

## 复盘追问
- 怎么区分"CPU 不够"还是"IO 不够"？提示：看 iostat/云监控的磁盘 util 与 iops、buffer pool 命中率；IO 瓶颈升 CPU 无效，要先加内存（更大热页）或上读副本/缓存。
- 治理清单里为什么要留"不治理"的项？提示：低频复杂查询（月度报表）单次慢但算力占比小，治理投入产出比差，标明"接受现状"比无限优化更专业。
