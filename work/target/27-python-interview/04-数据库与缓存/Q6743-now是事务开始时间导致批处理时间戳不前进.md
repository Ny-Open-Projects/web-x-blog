### Q6743 · now() 是事务开始时间：批处理里 5 万行拿到同一个时间戳

难度：P6 ｜ 标签：PostgreSQL、时间函数、增量同步、事务快照

基线：Python 3.12；用事务对象模拟 PG 的 `now()` / `statement_timestamp()` / `clock_timestamp()` 三种语义。

**问**：一张日志表 `created_at DEFAULT now()`，离线任务用 `WHERE created_at > :watermark ORDER BY created_at LIMIT 5000` 做增量拉取，`watermark` 取上一批的 `max(created_at)`。跑了一个月发现**每天稳定丢几千行**，而且丢的行集中在批量写入的时段。表里数据明明都在，为什么增量拉不到？

**答**：
- **结论**：PG 的 `now()` / `CURRENT_TIMESTAMP` / `transaction_timestamp()` 返回的是**事务开始时刻**，整个事务内恒定不变。一个事务里灌 5 万行，这 5 万行的 `created_at` 完全相同（精确到微秒都一致）。增量拉取用 `>` 严格大于上一个 `max(created_at)`，而上一批的 watermark 恰好等于这个批次的时间戳 → **整批被跳过**；如果改用 `>=` 又会重复拉取。根因是"用时间戳当游标，但时间戳的粒度比行粗"。
- **取舍**：三条修法：① 写入侧改用 `clock_timestamp()`（真实时钟，每条语句都变）或 `statement_timestamp()`（每条语句开始时刻），保证同一批内也有单调递增的微秒；② 增量游标改成 `(created_at, id)` 复合键，用 `WHERE (created_at, id) > (:ts, :id)` 做 keyset 分页——**同一时间戳内靠 id 也能严格推进**，这是最稳的；③ 用单调递增的 `bigserial` 或逻辑复制的 LSN 做游标，时间只用来展示。注意 `clock_timestamp()` 不保证严格单调（NTP 回拨会倒退），所以游标仍建议带 id。
- **实战**：① 审计/事件类表默认值用 `clock_timestamp()`，业务"创建时间"可以用 `now()`（同事务一致有时是优点）；② 所有增量同步统一 keyset 分页，禁止 `OFFSET` + 单列时间游标；③ 监控"写入行数 vs 下游拉取行数"的差值，按小时对账；④ `ORDER BY created_at` 在大量相同值时排序不稳定，必须补 `, id` 才有确定顺序。

```python
"""now() 恒定、clock_timestamp() 前进：同一事务里 5 行的三种时间。"""
import time
from datetime import datetime, timezone


def ts(t: float) -> str:
    return datetime.fromtimestamp(t, tz=timezone.utc).strftime("%H:%M:%S.%f")[:-3]


class Transaction:
    """模拟 PG：now() 取事务开始时刻，clock_timestamp() 取真实时钟。"""

    def __init__(self, label: str) -> None:
        self.label = label
        self.started = time.time()

    def now(self) -> float:                 # transaction_timestamp() / CURRENT_TIMESTAMP
        return self.started

    def statement_timestamp(self, stmt_started: float) -> float:
        return stmt_started

    def clock_timestamp(self) -> float:     # 真实时钟，读一次变一次
        return time.time()


if __name__ == "__main__":
    tx = Transaction("batch-2026-11-24")
    rows = []
    for i in range(5):
        stmt_started = time.time()
        rows.append({
            "id": i + 1,
            "now": tx.now(),
            "stmt": tx.statement_timestamp(stmt_started),
            "clock": tx.clock_timestamp(),
        })
        time.sleep(0.02)

    print(f"{'id':<4}{'now()':<16}{'stmt_ts':<16}{'clock_ts':<16}")
    for r in rows:
        print(f"{r['id']:<4}{ts(r['now']):<16}{ts(r['stmt']):<16}{ts(r['clock']):<16}")
    print("-> now() 五列完全相同；statement/clock 每条语句都在前进\n")

    # 增量同步：watermark = 上一批 max(created_at)
    batch1_watermark = rows[-1]["now"]
    batch2 = [{"id": 6, "created_at": tx.now()}, {"id": 7, "created_at": tx.now()}]
    pulled_gt = [r for r in batch2 if r["created_at"] > batch1_watermark]
    pulled_ge = [r for r in batch2 if r["created_at"] >= batch1_watermark]
    print("用 now() 写的下一批:", [ts(r['created_at']) for r in batch2])
    print("上一批 watermark  :", ts(batch1_watermark))
    print(">  拉到的行:", [r["id"] for r in pulled_gt], "-> 全丢")
    print(">= 拉到的行:", [r["id"] for r in pulled_ge], "-> 全重复\n")

    # keyset 分页：同一时间戳也能严格推进
    cursor = (rows[-1]["now"], rows[-1]["id"])
    candidate = [{"id": 6, "created_at": tx.now()}, {"id": 8, "created_at": tx.now()}]
    nxt = [r for r in candidate if (r["created_at"], r["id"]) > cursor]
    print("(created_at, id) keyset 拉到的行:", [r["id"] for r in nxt])
    print("结论：时间戳只做展示与粗筛；游标用 (时间, 唯一 id) 复合键才不丢不重")
```

**追问一**：`clock_timestamp()` 就能保证增量游标不丢数吗？

→ 解析：不能保证。它只是"读时时钟"，而系统时钟会被 NTP/闰秒调整**回拨**，回拨期间写入的行时间戳可能小于已保存的 watermark，照样漏。另外并发事务提交顺序与时间戳顺序不一致（事务 A 10:00:00 开始、10:00:05 提交；事务 B 10:00:01 开始、10:00:02 提交，A 的行会晚于 B 可见但时间戳更早）。所以"时间戳游标"只能做近似；要么带 id 做复合游标 + 重叠回看窗口（每次多拉 5 分钟并幂等去重），要么直接用单调的 WAL LSN / 自增序列。

**追问二**：为什么 `ORDER BY created_at LIMIT 5000` 分页在批量写入时会"漏行"？

→ 解析：几千行时间戳完全相同，数据库对相同排序键的行没有稳定顺序保证——两次查询、不同执行计划、甚至不同并行 worker，返回的"第 5001~10000 行"可能是同一批行。翻页的正确做法是 keyset：`WHERE (created_at, id) > (last_ts, last_id) ORDER BY created_at, id LIMIT 5000`，把唯一键并入排序与游标，顺序才确定。`OFFSET` 在大表上还有 O(offset) 的扫描代价，两个问题一起由 keyset 解决。
