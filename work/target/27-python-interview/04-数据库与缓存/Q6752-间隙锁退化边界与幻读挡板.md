### Q6752 · 间隙锁的退化边界：唯一索引等值命中只锁一行，锁不到就封住整段 gap

难度：P7 ｜ 标签：MySQL、InnoDB、Next-Key Lock、幻读、RR 隔离级别

基线：Python 3.12；用有序键 + 区间模型模拟加锁范围与"插入是否被阻塞"。

**问**：RR 隔离级别下，`SELECT * FROM t WHERE id = 20 FOR UPDATE` 有时只锁一行，有时把 20 前后的空隙全锁住；一个批量插入任务在白天没事、撞上"先查后插"的对账脚本就大面积 `Lock wait timeout`。Next-Key Lock 到底什么时候退化成记录锁？幻读到底被挡在哪条边界上？

**答**：
- **结论**：加锁单位是 **Next-Key Lock = 记录锁 + 前面的 gap**，但有两条退化规则：① **唯一索引（含主键）等值查询且命中**：只退化为记录锁，不锁 gap——因为唯一性保证不会冒出第二条 id=20，无需防幻读；② **等值未命中**（如查 id=25，不存在）：锁住左右两个邻接记录之间的 gap（此处是 (20,30) 的整段），专门防"有人插一条 25 出来"。非唯一索引的等值命中会**同时锁记录 + 两侧 gap**（因为值可重复，仍可能冒出同值行）。范围查询则按 Next-Key 扫到第一个不满足的记录为止，右边界常多锁一个 gap。
- **取舍**：① "先 SELECT 看有没有、没有再 INSERT"这种对账逻辑在 RR 下等值未命中即封 gap，并发插入全部排队——要么改成靠唯一索引 + `INSERT ... ON DUPLICATE` 直插，要么把查询降级为快照读（不加锁的普通 SELECT）+ 唯一约束兜底；② 锁是锁在**索引**上的：条件没有可用索引时，等值查询退化为扫全表，把沿途所有 gap 都封掉，表现成"锁全表"；③ RC 隔离级别没有间隙锁（只有记录锁 + 半一致读），并发更好但放弃了防幻读。
- **实战**：① 给并发热点表做"查无则插"前，先确认等值列有唯一索引，否则必封大 gap；② 复盘锁等待时用锁范围模型推演"谁封了哪段 gap"，比看 `SHOW ENGINE INNODB STATUS` 更快定位；③ 批量插入按主键升序排好再插，能减少 gap 分裂引起的死锁（Q874 的互相卡位多数源于乱序）。

```python
"""Next-Key 锁退化模型：唯一索引等值命中->记录锁；未命中->封 gap；范围->next-key。"""
Record = tuple  # (id,)


class LockModel:
    def __init__(self, ids: list[int]) -> None:
        self.ids = sorted(ids)

    def neighbors(self, x: int) -> tuple[int, int]:
        """x 落在哪个 (left, right) 邻接记录之间（右开）。"""
        left = max((i for i in self.ids if i <= x), default=-1)
        right = min((i for i in self.ids if i > x), default=10**9)
        return left, right

    def lock_range(self, cond: str, x: int, unique: bool = True) -> tuple:
        """返回被锁住的键区间 (lo, hi, include_right_gap)。"""
        if cond == "eq":
            if x in self.ids:
                # 唯一索引等值命中：退化为记录锁，不封 gap
                return (x, x, False) if unique else (x, x, True)
            # 等值未命中：封住所在 gap（防幻读插队）
            left, right = self.neighbors(x)
            return (left, right, False)
        if cond == "range":
            # 范围查询：next-key 扫到第一个不满足的记录，并多锁右 gap
            left, right = self.neighbors(x)
            return (left, right, True)
        raise ValueError(cond)

    def insert_blocked(self, x: int, locks: list[tuple]) -> bool:
        for lo, hi, gap_right in locks:
            if lo < x < hi:
                return True                      # 落在封住的 gap 内
            if x == hi and gap_right:
                return True                      # 右端 gap 也要挡
        return False


if __name__ == "__main__":
    m = LockModel([10, 20, 30])

    cases = [
        ("eq", 20, True, "唯一索引等值命中"),
        ("eq", 25, True, "唯一索引等值未命中"),
        ("eq", 20, False, "非唯一索引等值命中"),
        ("range", 25, True, "范围查询 id < 25"),
    ]
    for cond, x, unique, desc in cases:
        locks = [m.lock_range(cond, x, unique)]
        lo, hi, gap = locks[0]
        ins15 = m.insert_blocked(15, locks)
        ins22 = m.insert_blocked(22, locks)
        print(f"{desc:<14} 查 {x}: 锁区间 ({lo},{hi}){' +右gap' if gap else ''}"
              f" | 插15:{'阻塞' if ins15 else '放行'} 插22:{'阻塞' if ins22 else '放行'}")

    print()
    print("批量插入排序 vs 乱序（gap 分裂引发死锁的概率）:")
    print("  升序插入: 锁沿右边界推进, 前后事务几乎不交叉")
    print("  乱序插入: 每个事务各封一段 gap, 交叉等待 -> 死锁")
    print("结论：等值命中才退化记录锁；未命中封 gap 是防幻读的代价，也常是锁等待的元凶")
```

**追问一**：普通 SELECT（不加 FOR UPDATE）为什么不会阻塞插入，它看到的又是哪个版本？

→ 解析：普通 SELECT 是快照读，走 MVCC 读事务开始时的版本链，根本不加锁，所以不会封 gap、不会挡插入。代价是它在 RR 下看到的是"事务开始那一刻"的一致视图——先普通 SELECT 再 FOR UPDATE 会看到两个不同的世界（前者旧快照、后者当前最新）。防幻读的"锁"只存在于当前读（FOR UPDATE/FOR SHARE）路径上，把这两条读路径混用是很多"为什么我查到了又插不进"问题的根源。

**追问二**：为什么 RC 隔离级别敢不要间隙锁，MySQL 默认却选 RR？

→ 解析：RC 每条语句用最新已提交快照（半一致读），不加间隙锁，并发度和吞吐更好，PostgreSQL 默认就是 RC；但代价是同一事务内两次同样的 SELECT 可能看到不同结果（不可重复读 + 幻读），审计、对账类逻辑会算错账。MySQL 默认 RR 是历史与 statement 复制的共同产物——statement 格式下语句级重放要求更强的隔离保证。实践中很多互联网公司把 OLTP 库调成 RC + row binlog，用唯一约束和应用层幂等替代"锁 gap 防幻读"，这是理解退化规则后做出的主动取舍，而不是不知道 RR 的存在。
