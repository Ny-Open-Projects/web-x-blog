### Q6695 · 表行数估算与索引膨胀容量账

难度：P6 ｜ 标签：容量规划、表膨胀、索引空间、估算

基线：MySQL 8.0 / PostgreSQL 15+；information_schema / pgstattuple。

**问**：订单表预计一年 3 亿行，单行约 200 字节，另有 4 个二级索引。DDL 和磁盘采购前，怎么估这张表一年后占多大空间？为什么"200 字节 × 3 亿 = 57GB"这个算法是错的？

**答**：
- **结论**：真实占用 ≈ 行数据 ×(1 + 页填充浪费) + 主键 + Σ二级索引 ×(1+膨胀) + binlog/备份的放大。原始行大小只是地板：InnoDB 16KB 页有填充率（随机写通常 70%~85%）、每行还有 20+ 字节头部；二级索引每个都存"索引列 + 主键"，且"索引列越长，所有行都背一遍"；VARCHAR 存的是实际值但页分配按块；再加上碎片（删除不还空间给 OS）。工程上一张"200B 行"的表，落盘常是估算值的 2~3 倍。
- **取舍**：估算用"上限思路"做采购（多留 50%），用"实测思路"做监控——`information_schema.TABLES.DATA_LENGTH/INDEX_LENGTH`、PG 的 `pg_relation_size` + `pgstattuple` 的 dead_tuple 比例。膨胀治理：MySQL 靠 OPTIMIZE/gh-ost 重整，PG 靠 autovacuum 调参（另一卡已覆盖）。
- **实战**：索引是最大的隐藏变量——4 个索引如果包含一个 64 字节的长字段，索引体积可能超过行数据本身；时间序列类的表要提前规划分区，让"删旧数据"变成"DROP 分区"而不是 DELETE 留碎片。

```python
# 表空间估算模型（标准库可运行）：把行、页、索引、碎片四个系数显式化。
def estimate_table(rows: int, row_bytes: int, indexes: list[dict],
                   page_bytes: int = 16384, fill_factor: float = 0.8,
                   frag: float = 0.15, row_header: int = 24) -> dict:
    """indexes: [{'name': 'idx_a', 'entry_bytes': 40}, ...]
    二索引条目 = 索引列 + 主键指针，页内同样有填充率。"""
    row_real = row_bytes + row_header
    n_pages = rows * row_real / (page_bytes * fill_factor)
    data = n_pages * page_bytes * (1 + frag)
    idx_total = 0.0
    per_idx = {}
    for ix in indexes:
        entry = ix["entry_bytes"] + row_header
        p = rows * entry / (page_bytes * fill_factor) * (1 + frag) * page_bytes
        per_idx[ix["name"]] = round(p / 2**30, 1)   # GB
        idx_total += p
    return {
        "data_gb": round(data / 2**30, 1),
        "index_gb": round(idx_total / 2**30, 1),
        "total_gb": round((data + idx_total) / 2**30, 1),
        "per_index_gb": per_idx,
    }

if __name__ == "__main__":
    idx = [
        {"name": "uk_order_no", "entry_bytes": 40},   # 订单号 32B+主键8B
        {"name": "idx_user_time", "entry_bytes": 24},
        {"name": "idx_status", "entry_bytes": 17},
        {"name": "idx_merchant", "entry_bytes": 26},
    ]
    r = estimate_table(rows=300_000_000, row_bytes=200, indexes=idx)
    print(r)
    # data_gb≈90, index_gb≈82, total≈172 —— 约"裸算 57GB"的 3 倍
    # 若其中一个索引含 64B 长字段，index_gb 再涨近一倍。
```

**追问**：
- 一层：为什么删除一半数据，表文件不缩小？→ 提示：页内空间标记为可复用但不还 OS，需要重整（OPTIMIZE/重建）。
- 二层：怎么在线重整 3 亿行的大表？→ 提示：gh-ost/pt-osc 触发器或 binlog 回放 + 原子 RENAME，注意双倍瞬时空间。
- 三层：分区表对这笔账的改变是什么？→ 提示：DROP PARTITION 秒级回收空间且不产生大事务，但查询必须带分区键裁剪。

**背诵要点**：
1. 表空间 = 行×(1+头部/填充/碎片) + Σ索引（索引条目含主键），实际常是裸算的 2~3 倍。
2. 监控用 information_schema.TABLES 的 DATA_LENGTH/INDEX_LENGTH；治理靠在线重整（gh-ost）或分区 DROP。
3. 时间序列表提前分区：把"删除"变"卸载分区"，同时避免 DELETE 碎片和大事务。

**复盘追问**：
1. 当初的磁盘预算为什么按裸算做的？提示：评审清单缺"页填充/索引放大"系数项。
2. 如果索引里混进了一个 128B 的 JSON 摘要字段，账怎么变化？提示：索引体积反超行数据，应改前缀索引或哈希列。
