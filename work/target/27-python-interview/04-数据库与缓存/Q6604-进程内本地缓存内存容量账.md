### Q6604 · 进程内本地缓存的内存容量账与命中分层

难度：P7 ｜ 标签：缓存 / 内存容量 / 本地缓存

**问**：为了给 Redis 减压，团队在每个 FastAPI 进程里加了进程内 LRU 缓存热点商品（最多 10 万条）。上线后 Pod RSS 从 300MB 涨到 1.2GB，触发 K8s OOMKill 重启风暴。10 万条上限听起来不大，内存为什么会超预算？本地缓存的容量账应该怎么算？

**答**：
- **结论**：容量账翻车在两处：① Python 对象的**内存放大**——一条商品 dict（含图片 URL 列表、长描述）在内存里不是"业务大小"，dict 头、key 字符串、list、float 装箱叠加，实测单条 20KB 级，10 万条直接上 GB，加上 GC 峰值与碎片还要再乘安全系数；② **副本数乘法**——本地缓存按进程算，20 个副本每个都缓存全量热点，集群总内存 = 单进程预算 × 副本数，K8s 的 limit 是按单 Pod 算的，峰值波动（LRU 扫描、GC 前峰值）再乘 1.3 安全系数就爆 limit。另一个隐性放大：TTL 到期只是逻辑过期，LRU 不主动整理，`getsizeof` 不算共享 key 的引用去重。
- **取舍**：分层方案：① 缩量——本地缓存只放"每进程真实访问的热点 Top N"（比如 1 万条），命中率 80% 的代价远小于内存翻 10 倍；② 存压缩形态——进程内只存序列化字节串（或 msgpack），用的时候反序列化，用 CPU 换内存，体积降 3-5 倍；③ 换共享缓存——多副本共用一个 Redis/local Redis，牺牲微秒级延迟换集群账可控；④ 控制器化——用带 `maxmemory`/字节预算的缓存库（cachetools TTLCache 是条数不是字节，要自己按条数×均值换算）。
- **实战**：容量账公式：`单进程预算 = 条数 × (对象均重 × 放大系数 + 开销) × 峰值系数`，先在压测环境用 `tracemalloc`/`pympler` 实测均重再定条数；上线把 RSS、缓存条数、命中率三联指标一起看，RSS 涨幅与条数不线性说明有泄漏或放大误判。

```python
# 本地缓存内存容量账：对象放大实测 + 条数预算（标准库 tracemalloc）
# 基线：Python 3.9+

import tracemalloc
from collections import OrderedDict


def make_product(i: int) -> dict:
    return {
        "id": i,
        "title": f"商品标题-{i}-新款热卖限时特惠",
        "price": 99.9,
        "stock": 1234,
        "tags": ["数码", "热门", "自营"],
        "desc": "这是一段商品描述包含参数颜色尺寸售后" * 600,
    }


class LruCache:
    def __init__(self, maxsize: int) -> None:
        self.maxsize = maxsize
        self._d: OrderedDict[int, dict] = OrderedDict()

    def put(self, k: int, v: dict) -> None:
        if k in self._d:
            self._d.move_to_end(k)
        self._d[k] = v
        while len(self._d) > self.maxsize:
            self._d.popitem(last=False)


def measure_avg_bytes(n: int) -> float:
    tracemalloc.start()
    cache = LruCache(maxsize=n)
    for i in range(n):
        cache.put(i, make_product(i))
    cur, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return cur / n, peak


def budget(max_entries: int, peak_rss_mb: float, pod_limit_mb: float, safety: float = 1.3) -> None:
    total = peak_rss_mb * safety
    verdict = "PASS" if total <= pod_limit_mb else "OOMKill 风险"
    print(f"条数={max_entries}: 峰值RSS≈{peak_rss_mb:.0f}MB × {safety} = {total:.0f}MB / limit {pod_limit_mb}MB → {verdict}")


def main() -> None:
    avg, peak10k = measure_avg_bytes(10_000)
    print(f"单条均值 {avg/1024:.1f} KB（含 dict/字符串装箱放大）")
    # 线性外推 10 万条（演示预算逻辑；真实账还要加 GC 峰值与碎片）
    peak100k = peak10k / 1024 / 1024 * 10
    budget(100_000, peak100k, pod_limit_mb=1024)  # 事故配置：爆
    budget(10_000, peak10k / 1024 / 1024, pod_limit_mb=1024)  # 修正配置
    print("OK: 容量账结论——先实测均重，再定条数，RSS 与 limit 之间留安全系数")


if __name__ == "__main__":
    main()
```

**追问 1**：cachetools 的 `TTLCache(maxsize=N)` 为什么挡不住这次事故？
→ 一句话提示：maxsize 是条数不是字节，条数上限对不代表内存上限；要按"条数 × 实测均重"换算，或改存序列化字节串让均重可控可测。

**追问 2**：本地缓存的一致性问题怎么处理？
→ 一句话提示：进程间无法精准广播失效，常用"短 TTL（秒级）+ 版本号轮询/Redis pub-sub 通知 + 容忍脏读窗口"的组合；要求强一致的读根本不该进本地缓存。

## 背诵要点
- 本地缓存容量账 = 条数 × 实测均重（对象放大 5-10 倍）× 峰值系数 1.3，且乘进程副本数才是集群账。
- 减内存三板斧：缩条数（Top 热点）、存序列化字节串（CPU 换内存）、换共享缓存。
- K8s limit 是单 Pod 账：RSS 涨到 limit 的 80% 就该告警，OOMKill 后重启还有冷启动缓存重建风暴。

## 复盘追问
- 为什么重启风暴会自我放大？提示：OOMKill → 副本重启 → 缓存全空 → 回源 Redis/DB 流量突增 → 上游压力叠加 → 更多 Pod 被打挂，所以本地缓存还要配"启动预热限速"。
- `sys.getsizeof` 为什么算不出真实占用？提示：它不算引用对象（字符串、list 元素），也不算解释器开销与碎片；要用 tracemalloc/pympler 做聚合计量。
