### Q6546 · 数据库内存容量账：为什么 work_mem = RAM/连接数 一定算错？

> 难度:★★★★ | 标签:容量规划, 内存分配, PostgreSQL

**问**：一台 64GB 的 PG/MySQL，200 个并发连接，"每个连接分 300MB work_mem 正好 64GB"这种算法为什么是错的？内存容量账正确的模型是什么？OOM 事故是怎么从算错账开始的？

**答**：结论：数据库内存不能做加法账，因为 **work_mem 是"每个操作"的预算而不是"每个连接"的固定占用**——一个连接里的一个复杂查询可以有多个排序/哈希节点并行占用多份 work_mem，且大部分时间连接根本不用这么多。正确模型是：**共享内存（shared_buffers/buffer pool，固定）+ 会话私有内存（按"最坏并发 × 每连接峰值操作数"估算）+ OS/进程其他开销**，并给私有内存留 30-50% 的突发余量。算成加法账的直接后果是高并发大查询一起跑时 OOM 被 kill。

机理与实战：
- **账目三分**：① 共享区：PG shared_buffers 建议 RAM 的 25%（剩余给 OS page cache），MySQL buffer pool 60-75%；② 私有区：PG work_mem/maintenance_work_mem，MySQL sort_buffer/join_buffer/read_buffer（MySQL 这几个是"需要就分配全额"更危险）；③ 固定开销：连接结构、复制、监控 agent，每连接几 MB 到几十 MB。
- **正确估算式**：最坏情况内存 ≈ shared_buffers + 并发活跃查询数 × 每查询排序节点数 × work_mem × 2（hash 用两份）+ 连接数 × 每连接基础开销。200 连接不等于 200 并发大查询——按 P95 活跃查询数（如 20）算，而不是按连接数算。
- **OOM 防御**：① work_mem 保持 4-64MB 区间，大排序靠临时文件而非内存（磁盘排序慢 2-3 倍但可控）；② 用 cgroup/容器内存上限把 DB 与应用隔离；③ PG 上 `max_parallel_workers × parallel worker × work_mem` 也是隐藏乘数。
- **MySQL 特别提醒**：sort_buffer_size 是会话级按需全额分配，调大到 256MB × 500 连接一旦同时排序直接 OOM——所以 MySQL 账要按"触发排序的连接占比"估。

```python
# 基线:Python 3.10+;纯标准库,数据库内存容量估算:加法账 vs 分位数账对比
from __future__ import annotations
from dataclasses import dataclass


@dataclass
class MemProfile:
    ram_gb: float
    shared_buffers_gb: float   # 共享区(固定)
    connections: int           # 连接数
    p95_active_queries: int    # P95 同时活跃大查询数(经验值或监控取)
    sort_nodes_per_query: float  # 每查询平均排序/哈希节点数
    work_mem_mb: float         # 单节点内存预算
    conn_base_mb: float = 10   # 每连接基础开销 MB


def additivity_budget(p: MemProfile) -> float:
    """错误算法:连接数 × work_mem 的加法账(以为刚好用满)。"""
    return p.shared_buffers_gb + p.connections * p.work_mem_mb / 1024


def worst_case_budget(p: MemProfile) -> float:
    """正确算法:共享区 + P95 活跃查询 × 节点数 × work_mem × 2(hash 双份) + 连接基础开销。"""
    private = (p.p95_active_queries * p.sort_nodes_per_query
               * p.work_mem_mb * 2) / 1024
    base = p.connections * p.conn_base_mb / 1024
    return p.shared_buffers_gb + private + base


def oom_risk(p: MemProfile) -> str:
    need = worst_case_budget(p)
    headroom = p.ram_gb - need
    if headroom < p.ram_gb * 0.15:
        return f"高风险:最坏需求 {need:.1f}GB / {p.ram_gb}GB,余量 {headroom:.1f}GB <15%,降 work_mem 或限并发"
    return f"安全:最坏需求 {need:.1f}GB,余量 {headroom:.1f}GB"


def demo() -> None:
    p = MemProfile(ram_gb=64, shared_buffers_gb=16, connections=200,
                   p95_active_queries=60, sort_nodes_per_query=3, work_mem_mb=32)
    print(f"加法账(错): {additivity_budget(p):.1f}GB —— 按连接数×单份 work_mem,低估峰值")
    print(f"最坏账(对): {worst_case_budget(p):.1f}GB —— 按 P95 活跃大查询×节点数×双份 hash")
    print(oom_risk(p))
    assert abs(additivity_budget(p) - (16 + 200 * 32 / 1024)) < 0.01   # 22.25
    assert worst_case_budget(p) > additivity_budget(p)                  # 多节点并发超加法账
    # 故意算错的版本:200 连接全配 256MB sort_buffer
    bad = MemProfile(ram_gb=64, shared_buffers_gb=16, connections=500,
                     p95_active_queries=200, sort_nodes_per_query=2, work_mem_mb=256)
    assert "高风险" in oom_risk(bad)
    print("内存账模型:共享区固定 + 私有按最坏并发×操作数,留 15% 余量 ✅")


if __name__ == "__main__":
    demo()
```

**追问一**：PG 的 `max_connections` 调大为什么对内存账是乘法效应？
答：每个连接除了私有工作内存还有固定的后端进程基础开销（连接结构、catalog 缓存等几 MB 起步），max_connections 从 200 提到 2000 光基础开销就多出数 GB，且放大了"高并发同时触发大排序"的尾部概率——所以 PG 的正解是上 PgBouncer 把连接数与后端进程数解耦（事务级池化），而不是把 max_connections 当并发容量旋钮。

**追问二**：为什么说"work_mem 调大让报表查询快 10 倍"可能埋下 OOM 雷？
答：work_mem 是按节点发放、按需全额使用的，报表大查询通常有多个大排序/哈希节点；白天业务高峰与报表跑批重叠时，几个报表就占满私有内存配额，与业务查询一起触发 OOM killer。正解是给报表单独的只读副本/独立实例配大 work_mem，线上主库保持小 work_mem + 磁盘排序兜底。

## 背诵要点
- 内存账三分：共享区（PG 25% RAM / MySQL buffer pool 60-75%）+ 私有区（按 P95 活跃查询数×排序节点数×work_mem×2）+ 每连接基础开销；不做连接数×work_mem 的加法账。
- work_mem 是"每个操作"的预算不是每连接固定占用；MySQL sort_buffer 是按需全额分配，500 连接×256MB 必 OOM。
- 防御：work_mem 保持 4-64MB 用磁盘排序兜底、cgroup 隔离、连接数用 PgBouncer 解耦、留 15% 内存余量。
