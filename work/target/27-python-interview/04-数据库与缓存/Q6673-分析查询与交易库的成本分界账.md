### Q6673 · 分析查询留在交易库还是拆 OLAP：成本分界怎么算

难度：P6/P7 ｜ 标签：成本工程、OLAP、架构选型

**问**：报表团队在交易库上跑聚合 SQL，偶发拖慢线上。什么时候值得拆出独立分析库？拆与不拆的成本账怎么算？

**答**：**结论**：成本分界由三个变量决定——① 分析查询的**资源占比**（CPU/IO 时间占交易库总时间的比例）；② 分析负载**增速**；③ 交易库**故障代价**（P99 抖动换来的损失）。资源占比 < 10% 且稳定时，用限流 + 低峰窗口留在交易库最便宜；占比超过 20% 或增速超过交易库扩容速度时，独立 OLAP 实例的固定成本开始低于"反复给交易库升配 + 故障损失"。

**取舍**：拆 OLAP 引入的新成本 = 实例费用 + 同步链路（CDC/ETL）开发运维 + 数据延迟带来的口径不一致风险。很多团队漏算"口径漂移"：分析库 T+1，报表数字与线上实时数字对不上，对账人力是隐性大头。

**实战**：用查询审计（pg_stat_statements / MySQL slow log 聚合）算出分析类 SQL 的资源占比月度曲线，把分界点写进架构决策记录；先给报表 SQL 上查询超时与内存限额（PG `statement_timeout`、MySQL `max_execution_time`），这是零成本的止损，再做拆分决策。

```python
# 成本分界模型：留在交易库(限流+升配) vs 拆独立 OLAP
def split_decision(
    oltp_monthly: float,        # 交易库月成本（元）
    analytics_cpu_share: float, # 分析查询占用资源占比 0-1
    analytics_growth: float,    # 分析负载月增速 0-1
    olap_monthly: float,        # 独立OLAP实例+同步链路月成本
    incident_cost: float,       # 分析拖慢交易库的单次故障代价（元）
    incident_freq_monthly: float,
) -> dict:
    # 留在交易库：为扛分析负载而升配的溢价 + 故障期望损失
    stay_cost = oltp_monthly * analytics_cpu_share * 2 + \
        incident_cost * incident_freq_monthly
    # 拆出去：OLAP 固定成本 + 对账人力（口径漂移风险折算）
    split_cost = olap_monthly + oltp_monthly * 0.05
    verdict = "拆独立OLAP" if split_cost < stay_cost else "留在交易库"
    # 增速哨兵：增速高时固定成本迟早被追平
    horizon = None
    if analytics_growth > 0:
        k = 0
        while k < 24 and oltp_monthly * analytics_cpu_share * (1 + analytics_growth) ** k * 2 < split_cost:
            k += 1
        horizon = f"{k}个月后拆分更划算" if k < 24 else "24个月内无需拆分"
    return {"stay": stay_cost, "split": split_cost,
            "verdict": verdict, "horizon": horizon}

r = split_decision(
    oltp_monthly=20000,
    analytics_cpu_share=0.18,
    analytics_growth=0.15,      # 每月 15% 增长
    olap_monthly=6000,
    incident_cost=50000,
    incident_freq_monthly=1,
)
print(r["verdict"], f"stay={r['stay']:.0f} split={r['split']:.0f}")
print(r["horizon"])
# 故障代价 5 万/次时当下就该拆；增速 15% 会持续拉大差距
```

**追问 1**：为什么升配溢价系数取 2 而不是 1？
提示：分析负载是突发的，为峰值扛量必须按峰值规格付费，平均利用率低，实际溢价通常是 1.5~3 倍，取 2 是折中，要用真实资源占比曲线校准。

**追问 2**：如果只有一张大报表拖慢线上，拆 OLAP 合算吗？
提示：不合算——单条 SQL 的治理手段很多（物化视图、汇总表、`statement_timeout`、错峰调度），拆库是为"一类负载"设计的，不是为一条 SQL。

**追问 3**：CDC 同步链路本身的故障算谁的？
提示：算进拆分方案的总成本——同步延迟、断流、重复数据都是新故障面，账里至少按月度人力 0.1~0.2 人折算。

## 背诵要点
1. 分界三变量：分析资源占比（<10% 留守，>20% 拆）、增速、交易库故障代价。
2. 先止损后决策：查询超时 + 内存限额零成本，拆库是为"一类负载"不是一条 SQL。
3. 拆库隐性成本 = 同步链路运维 + 口径漂移对账人力，月账要计入。
