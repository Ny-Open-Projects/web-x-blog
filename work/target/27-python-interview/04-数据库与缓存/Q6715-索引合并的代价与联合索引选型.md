### Q6715 · 索引合并的代价：两个索引不等于一条好路径

难度：P6 ｜ 标签：执行计划、index merge、回表、优化器

基线：Python 3.12；MySQL 8.0；纯 Python 演示优化器在单列索引与联合索引之间的成本选择。

**问**：一张 500 万行的表，`status` 和 `city` 各有一个单列索引。查询 `WHERE status='paid' AND city='杭州'`，优化器选了 `index_merge`（两个索引取交集再回表），结果比预期慢 8 倍。明明两个条件都有索引，为什么反而慢？什么时候该建联合索引？

**答**：
- **结论**：`index_merge` 要分别扫描两个二级索引、取出主键集合、在内存里做交集/并集，再按主键**逐行回表**。它的成本 ≈ 两个索引的扫描量 + 主键集合物化 + 回表次数，而且回表是随机 IO。当单个条件的选择性都不高（比如 `status` 命中 30% 的行），两个索引各自都要扫上百万行，交集后仍有几十万行要回表，成本远高于一条联合索引的范围扫描。
- **取舍**：联合索引 `(status, city)` 能一次定位、顺序回表，通常完胜 index merge；但联合索引的列顺序要按"等值列在前、范围列在后"和实际查询模式设计，且会增加写放大与存储。index merge 并非无用：当两个条件各自都很强、且没有合适的联合索引时，它能避免全表扫描——问题是优化器对它的成本估算经常偏乐观（统计信息过期、相关性未建模）。
- **实战**：① 用 `EXPLAIN ANALYZE` 看实际行数与 `Using intersect(...)`，别只看 `key`；② 高频组合查询建联合索引，并用 `EXPLAIN` 门禁防止计划回退；③ 统计信息要定期更新，尤其大表批量导入后；④ 必要时用 `/*+ NO_INDEX_MERGE(t) */` 或改写查询做兜底，但优先修索引。

```python
def scan_cost(rows: int, selectivity: float, back_to_table: bool) -> float:
    """粗略成本：索引扫描行数 + 回表随机 IO 惩罚。"""
    index_rows = rows * selectivity
    cost = index_rows
    if back_to_table:
        cost += index_rows * 3.0        # 随机回表按 3 倍放大
    return cost


def choose_plan(rows: int, status_sel: float, city_sel: float) -> str:
    merge = (scan_cost(rows, status_sel, False)
             + scan_cost(rows, city_sel, False)
             + scan_cost(rows, status_sel * city_sel, True))
    composite = scan_cost(rows, status_sel * city_sel, True)
    return f"index_merge={merge:,.0f}, composite={composite:,.0f}"


if __name__ == "__main__":
    print("低选择性:", choose_plan(5_000_000, 0.30, 0.20))
    print("高选择性:", choose_plan(5_000_000, 0.02, 0.01))
    print("结论：单条件选择性差时，index merge 的回表成本会压过联合索引")
```

**追问一**：为什么 `index_merge` 的回表比联合索引贵这么多？
→ 解析：联合索引在索引页里已经按 `(status, city)` 有序，命中后回表的主键也相对集中，接近顺序 IO；index merge 得到的主键集合来自两个独立索引，顺序散乱，回表是随机 IO，且要去重、排序，Buffer Pool 命中率也差。

**追问二**：有了联合索引 `(status, city)`，查询只带 `city` 还能用吗？
→ 解析：不能有效使用（只能跳过前导列做全索引扫描，通常不如全表）。所以联合索引不能替代 `city` 的单列索引；如果 `city` 单独查询也高频，两个索引都要保留，代价是写放大。索引设计是查询模式的函数，不是越多越好。
