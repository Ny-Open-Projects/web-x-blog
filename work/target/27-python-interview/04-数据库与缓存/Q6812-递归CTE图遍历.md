### Q6812 · 递归 CTE 图遍历：WITH RECURSIVE 的防环与深度账

难度：P6 ｜ 标签：递归 CTE、WITH RECURSIVE、图遍历、防环、深度限制、依赖图

基线：SQLite 3.45（原生支持 WITH RECURSIVE）/ PostgreSQL 12+；用依赖图实测路径剪枝、限深与 UNION 去重三种防环手段，全标准库实跑。

**问**：权限继承、组织架构、依赖解析都是图——应用层拉全表到内存再递归遍历，10 万节点直接 OOM；改 SQL 写 `WITH RECURSIVE`，同事警告"图里有环会死循环，必须加深度限制"。到底该怎么写？路径剪枝、深度上限、UNION 去重三种防环手段各防什么？会不会把数据库拖垮？

**答**：

- **结论**：递归 CTE 的结构是"锚点（起点）UNION ALL 递归部分"，递归部分从上轮结果继续扩展，数据库把它跑成代际迭代。环图不防护时无限代际直到达到 DB 的递归上限（PG 默认报错或无限，SQLite 有编译上限），所以防环是**必选项**而非优化项。三种手段防不同的事：① **路径剪枝**（`WHERE instr(path, dst)=0`）保证每条 DFS 路径不重复经过同一节点，防死循环，但同一节点可在多条路径重复展开，节点数指数增长；② **深度上限**（`WHERE depth < N`）是最后的兜底保险，任何图都不会跑飞，代价是深度超过 N 的真实路径被截断；③ **UNION（非 ALL）去重**让相同 (节点, 状态) 行只出现一次，适合"求可达集合"类查询，天然收敛。
- **取舍**：防环手段要按查询语义选。求"可达集合"（谁继承了谁的全部权限）用 UNION 去重，结果天然无重复且收敛；求"路径列表"（报错链、依赖链）必须路径剪枝+限深双保险，因为路径数可能指数爆炸——一个 4 层完全图就有天文数字条路径，DB 内存与 CPU 直接被拖死。图规模大（百万边）时递归 CTE 不是首选：逐层物化到临时表的应用层 BFS，或者物化路径表（闭包表）才是正解；递归 CTE 适合万级节点的查询型场景。
- **实战**：一次权限继承改造，用递归 CTE 求用户全量权限，测试环境没问题，上线后某团队把三个部门互相挂了父节点（环），查询跑满 CPU 直到超时告警。修复三件套：path 剪枝防死循环、depth<8 兜底、以及**写入侧约束**（挂父节点时校验新祖先链不含自己，环在写入时就拒绝）。另外把全量权限同步改为闭包表增量维护，查询退化成一次 JOIN。结论：递归 CTE 查询型遍历可以上生产，但环治理必须同时做在读取侧与写入侧。

下面用带环的依赖图实测三种防护的行为差异。

```python
# Q6812 递归 CTE 图遍历: 组织架构/依赖图, 防环与深度限制
import sqlite3

conn = sqlite3.connect(":memory:")
conn.executescript("""
CREATE TABLE edge(src TEXT, dst TEXT);           -- 有向边: src 依赖 dst
INSERT INTO edge VALUES
 ('app','lib-a'),('app','lib-b'),
 ('lib-a','lib-c'),('lib-b','lib-c'),('lib-c','lib-d'),
 ('lib-d','lib-a');                              -- 人工埋一个环 lib-a -> ... -> lib-a
""")

# [1] 不防环的递归 CTE: 环上无限递归, 用深度上限强行截断
safe_sql = """
WITH RECURSIVE walk(node, depth, path) AS (
    SELECT 'app', 0, 'app'
  UNION ALL
    SELECT e.dst, w.depth + 1, w.path || '>' || e.dst
    FROM walk w JOIN edge e ON e.src = w.node
    WHERE w.depth < 6                             -- 深度硬上限兜底
)
SELECT node, depth, path FROM walk ORDER BY depth
"""
rows = conn.execute(safe_sql).fetchall()
print(f"[1] 深度上限 6: 产出 {len(rows)} 行 (环被上限截断, 不会跑飞)")
assert len(rows) > 0 and max(r[1] for r in rows) == 6
for r in rows:
    if r[1] >= 4:
        print(f"    depth={r[1]}  path={r[2]}")

# [2] 防环: path 包含检查, 环上节点只展开一次
acyclic_sql = """
WITH RECURSIVE walk(node, depth, path) AS (
    SELECT 'app', 0, 'app'
  UNION ALL
    SELECT e.dst, w.depth + 1, w.path || '>' || e.dst
    FROM walk w JOIN edge e ON e.src = w.node
    WHERE instr(w.path || '>', '>' || e.dst || '>') = 0   -- 已在路径上则剪枝
)
SELECT count(*), max(depth) FROM walk
"""
total, deepest = conn.execute(acyclic_sql).fetchone()
print(f"[2] path 剪枝: 共 {total} 个路径节点, 最深 {deepest}; 每条 DFS 路径不重复经过同一节点")
assert total == 8 and deepest == 4, f"path 剪枝应为 8 节点 4 层: {total}/{deepest}"
print("    → 路径级防环: lib-a→lib-c→lib-d→lib-a 在第二条路径(app>lib-b>…)中未被剪, 因该路径没走过 lib-a")

# [3] 环检测: 找出会回到起点的边
cycle_sql = """
WITH RECURSIVE walk(node, depth, path) AS (
    SELECT 'app', 0, 'app'
  UNION ALL
    SELECT e.dst, w.depth + 1, w.path || '>' || e.dst
    FROM walk w JOIN edge e ON e.src = w.node
    WHERE depth < 10 AND instr(path || '>', '>' || e.dst || '>') = 0
)
SELECT path FROM walk
 WHERE node IN (SELECT src FROM edge WHERE dst IN (
                   SELECT node FROM walk WHERE depth > 0))
"""
hits = conn.execute(cycle_sql).fetchall()
print(f"[3] 检出环相关路径 {len(hits)} 条")
assert hits, "应检出环"

# [4] 逐层展开: 只取每层一次 (去重中间节点), 适合依赖安装顺序
level_sql = """
WITH RECURSIVE lvl(node, depth) AS (
    SELECT 'app', 0
  UNION
    SELECT e.dst, l.depth + 1          -- UNION(非 ALL) 自动按整行去重
    FROM lvl l JOIN edge e ON e.src = l.node
    WHERE l.depth < 10
)
SELECT node, min(depth) AS first_seen FROM lvl
 GROUP BY node ORDER BY first_seen
"""
seen = conn.execute(level_sql).fetchall()
names = [r[0] for r in seen]
print(f"[4] 去重展开: {names}")
assert names == ["app", "lib-a", "lib-b", "lib-c", "lib-d"]
print("    → 实测 UNION 去重 + min(depth) = 拓扑展开; 环图必须剪枝或限深, 否则 CTE 死循环")
```

**追问一**：递归 CTE 与应用层 BFS 在内存与 CPU 上怎么比？什么时候必须下放到应用层？—— 递归 CTE 在 DB 内做代际迭代，省去了数据搬运，但每代都是一次 JOIN 且中间结果全在 DB 内存/临时表里；路径类查询中间结果可能指数增长，DB 的 temp 空间是共享资源，拖垮的是整个实例而不是单个查询。经验线：万级节点、层数 < 10 的查询型遍历用递归 CTE；百万边或需要自定义访问顺序/复杂累积状态（如最短路）时下放应用层；读多写少的继承关系干脆用闭包表把递归变成静态 JOIN。还有一个工程点：递归 CTE 不好做分页，DB 会先算完整个遍历再排序。

**追问二**：UNION 去重的递归 CTE 遇到环会怎样？它真的能自己收敛吗？—— 能收敛，因为 UNION 会对"整行"去重：环图里 (node, depth) 组合有限，新产生的行一旦重复就不再进入下一轮，迭代自然停止。但注意去重键必须包含"状态"：如果递归列里带 path，path 每轮都在变长，整行永远不同，UNION 就失去收敛能力——这也是为什么"求可达集合"时递归列只留 (node, depth) 这类有界状态，而把 path 留给路径剪枝版本。写错去重键是"加了 UNION 还是死循环"的常见原因。

## 背诵要点

- 递归 CTE = 锚点 UNION ALL 递归部分；环图不防护会跑到 DB 递归上限，防环是必选项。
- 三种防护：path 剪枝（防死循环但可能指数）、depth 上限（兜底截断）、UNION 去重（可达集合天然收敛，去重键必须有界）。
- 百万边或复杂累积状态 → 应用层 BFS / 闭包表；环治理要写入侧拒绝，不能只靠查询侧兜底。

## 复盘追问

- 线上递归 CTE 把 CPU 打满，你怎么快速止血并定位环？（先 kill 会话限流；用自环/双环检测 SQL（src=dst 或 src 在 dst 的祖先链）快速定位；修复后写入侧加祖先链校验）
- 为什么"求可达集合"用 UNION、"求路径列表"用 UNION ALL+剪枝？（可达集合只要节点有界去重即收敛；路径列表每条 path 唯一，UNION 无法去重，必须靠 path 剪枝+限深）
