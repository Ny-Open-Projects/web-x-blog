### Q6615 · 开发/测试数据库实例定时启停的成本账

难度：P6 ｜ 标签：成本工程 / 非生产环境 / 云计费

**问**：团队有 12 套开发/测试用云数据库实例（8C32G，按量单价约 2.0 元/小时/套），7×24 常驻月账单约 2.6 万元（计算费 1.73 万、存储 0.43 万、快照/备份 0.4 万）。有人说"晚上自动停机能省一半"。这道账的真实节省上限是多少？哪些费用停机不省？为什么生产要排除在这套机制外？

**答**：
- **结论**：分项拆账：① **计算费**随启停省——按小时计费实例停机后不收计算费，若每天只运行 10 小时（9:00-19:00），月省 12 × 2.0 × 14h × 30 ≈ 1.0 万元，即省掉计算费的 58%；② **存储费照收**——云盘按容量月费与启停无关，12 套 × 800GB × 0.45 元/GB/月 ≈ 0.43 万继续付；③ **快照与备份费照收**——保留的自动快照、跨区备份存储不随停机减免，且停机前还要多打一次快照（短暂峰值）；④ **隐性成本**——启停耗时（RDS 停机/启动各 3~8 分钟）、运维复杂度（定时任务、豁免名单、有人加班要临时开机）、以及"停了忘开"导致的次日团队阻塞（一个 10 人团队阻塞 1 小时的机会成本往往超过当日节省）。综合：总账 2.6 万中省 1.0 万 ≈ **39%**，远低于"省一半"的直觉——上限公式 = 计算费占比 × 停机时长占比。
- **取舍**：替代方案对比：① 常驻降配（8C→4C，非峰值性能需求本就低）省约 50% 计算费且无启停风险，往往是更优解；② 按需快照 + 用时重建（开发环境数据可从模板快照 10 分钟拉起）适合低频使用的分支环境，节省 80%+；③ 预留/包年折扣对确定常驻的环境覆盖；④ 定时启停适合"确定没人用的大块时段"（夜间+周末），周末停机能把 10/24 提到 10+32/168≈25% 占用率。组合拳通常是：核心测试环境降配常驻 + 分支环境快照按需拉起 + 夜间停机兜底。
- **实战**：实现要点：启停策略用 IaC（标签 `auto-stop: true`）声明，豁免走 PR 审批；停机前自动快照并校验最近备份成功；"忘记开机"防护——工作日 8:30 兜底开机 + Slack 机器人手动唤起命令；账单分项（计算/存储/快照）按月导出对比，验证实际节省率与模型偏差；生产与预发布实例一律打 `auto-stop: false`。

```python
# 数据库实例启停成本模型：分项拆账（计算/存储/快照）
# 基线：Python 3.9+ 标准库；单价为示例，落地时读云账单 API 实价
from dataclasses import dataclass


@dataclass
class Fleet:
    count: int
    hourly_price: float      # 计算费 元/小时/套
    running_hours_day: float
    disk_gb: float
    disk_month_price: float  # 存储费 元/GB/月（启停不省）
    snapshot_month: float    # 快照/备份费 元/月（启停不省）


def monthly_cost(f: Fleet) -> float:
    compute = f.count * f.hourly_price * 24 * 30
    return compute + f.count * f.disk_gb * f.disk_month_price + f.snapshot_month


def saved_by_schedule(f: Fleet, off_hours_day: float) -> float:
    return f.count * f.hourly_price * off_hours_day * 30


def main() -> None:
    f = Fleet(count=12, hourly_price=2.0, running_hours_day=10,
              disk_gb=800, disk_month_price=0.45, snapshot_month=4000)
    total = monthly_cost(f)
    save = saved_by_schedule(f, off_hours_day=14)   # 夜间 14h 停机

    assert abs(total - (12*2.0*24*30 + 12*800*0.45 + 4000)) < 1e-6  # ~2.56万
    # 真实节省率 = 计算费节省 / 总账单；存储+快照 ~0.83万 完全不动
    rate = save / total
    assert 0.35 < rate < 0.45, rate
    print(f"月账单 {total/1e4:.1f} 万；夜间停机月省 {save/1e4:.1f} 万（{rate:.0%}），非'省一半'")

    # 替代方案：降配 8C->4C 省计算费 50%，且无启停风险
    save_downsize = 12 * 2.0 * 0.5 * 24 * 30
    assert save_downsize > save * 0.8
    print(f"降配省 {save_downsize/1e4:.1f} 万/月，接近停机收益且零运维风险")

    # 快照按需拉起：分支环境月均使用 30h
    ondemand = 12 * 2.0 * 30 + 12 * 800 * 0.45 + 4000
    assert ondemand < total * 0.4
    print(f"按需拉起月成本仅 {ondemand/1e4:.1f} 万（含存储+快照刚性部分）")


if __name__ == "__main__":
    main()
```

**追问 1**：为什么存储与快照费停机照收？怎么压这部分？
→ 一句话提示：存储是持久化资源不随计算启停；压缩手段是缩减数据盘（归档冷数据）、快照生命周期规则（保留 7 天 + 增量快照），以及删除"僵尸"分支环境的快照。

**追问 2**：为什么生产实例绝不进定时启停，预发布呢？
→ 一句话提示：生产的可用性损失一次远超全年节省；预发布可进但要错开发布窗口（发版日豁免），且停机策略必须与"预发布冒烟巡检"（见 Q7019）联动避免巡检打到停机实例。

## 背诵要点
- 真实节省上限 = 计算费占比 × 停机时长占比：示例 12 套 8C32G 月账 2.6 万，夜间停 14h 只省 39%——存储与快照费刚性不动。
- 组合拳优于单一手段：核心环境降配常驻（省 50% 计算费、零风险）+ 分支环境快照按需拉起（省 80%+）+ 夜间停机兜底。
- 防护三件套：停机前自动快照、工作日兜底开机 + 手动唤起命令、账单分项（计算/存储/快照）按月验证实际节省率。

## 复盘追问
- "停了忘开"的机会成本怎么进这道账？提示：一次团队阻塞（N 人 × 平均时薪 × 阻塞时长）大概率超过当日节省数百元，所以兜底开机与告警是必备项，而不是可选项。
- 什么信号说明该把某套实例从"定时启停"升级为"按需拉起"？提示：月运行时长曲线——若实际使用 < 60h/月（工作时段占比低、需求方经常手动唤起），快照拉起模式总成本与体验都更优。
