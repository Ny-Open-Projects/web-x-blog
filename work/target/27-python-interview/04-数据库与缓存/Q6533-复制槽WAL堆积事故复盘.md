### Q6533 · 复制槽与 WAL 堆积：pg_wal 把磁盘撑爆的事故复盘

> 难度:★★★★ | 标签:PostgreSQL, WAL, 事故复盘

**问**：主库凌晨告警 pg_wal 目录几百 GB、磁盘写满、业务写入开始报错。这和复制槽（replication slot）是什么关系？应急怎么做？为什么说"删掉不用的槽"是巡检重点？`max_slot_wal_keep_size` 设置后会发生什么？

**答**：结论：WAL 能否回收由"**最慢的消费者**"决定——每个复制槽（逻辑订阅槽、备库物理槽）记录 restart_lsn，PG 必须保留所有槽最早位点之后的 WAL。消费端挂了、位点不动，WAL 就无限堆积，直到磁盘满、主库停摆。这是一条经典事故链：**订阅端宕机 → 槽滞后 → WAL 堆积 → 磁盘满 → 主库写路径雪崩**。

机理与实战：
- **应急优先级**：① 恢复消费端最快（重启订阅进程，位点还在，续传即可）；② 消费端数据可弃则 `pg_replication_slot_advance` 强推位点——WAL 立即可回收，订阅端丢增量需重建；③ 极端时 `DROP SLOT` 直接放行。注意：**每个滞后槽独立拖住 WAL**，只 advance 一个不够，要按 `pg_replication_slots` 全量排查。
- **预防（PG 13+）**：`max_slot_wal_keep_size` 给单槽 WAL 保留封顶，超出即回收并标记槽为 `lost`——订阅端无法续传必须重建（重新快照同步）。取舍原则：**宁可订阅端重建，不可主库停摆**。
- **巡检重点**：`active=false` 且 `restart_lsn` 长期不动的槽是头号嫌疑——应用下线/重构后槽没人删是最常见来源；删槽即弃位点，删除前需人工确认。
- **监控口径**：`wal_status`（reserved/lost）、`safe_wal_size`（还能写多少才触发限制）、pg_wal 目录字节数与磁盘水位三线告警；订阅端进程的心跳与位点上报延迟。

```python
# 基线:Python 3.10+;纯标准库模拟复制槽滞后导致 WAL 堆积的事故与处置
# 真实场景:PG pg_replication_slots / pg_wal 目录监控 + max_slot_wal_keep_size
from __future__ import annotations
from dataclasses import dataclass

SEG_BYTES = 16 * 1024 * 1024            # WAL 段大小 16MB


@dataclass
class Slot:
    name: str
    restart_lsn: int                    # 槽要求保留的最早 WAL 位点
    active: bool = True
    lost: bool = False                  # 超过 max_slot_wal_keep_size 被标记


class Primary:
    def __init__(self, disk_bytes: int, max_slot_wal_keep_size: int | None = None) -> None:
        self.lsn = 0
        self.disk = disk_bytes
        self.cap = max_slot_wal_keep_size
        self.slots: list[Slot] = []

    def write_wal(self, nbytes: int) -> int:
        self.lsn += nbytes
        kept = self.wal_kept()
        if self.cap is not None:        # PG13+:单槽 WAL 保留上限,超出即回收并标记 lost
            for s in self.slots:
                if not s.lost and self.lsn - s.restart_lsn > self.cap:
                    s.restart_lsn = self.lsn - self.cap
                    s.lost = True
            kept = self.wal_kept()
        return kept

    def wal_kept(self) -> int:
        """WAL 保留必须覆盖所有未丢失槽的 restart_lsn(取最小),落后越多堆积越多。"""
        live = [s.restart_lsn for s in self.slots if not s.lost]
        if not live:
            return 0
        return self.lsn - min(live)

    def disk_pressure(self) -> int:
        return self.wal_kept() - self.disk

    def advance_slot(self, name: str, to_lsn: int | None = None) -> None:
        """pg_replication_slot_advance:弃位点换取 WAL 立即可回收(订阅端需重建)。"""
        for s in self.slots:
            if s.name == name:
                s.restart_lsn = to_lsn if to_lsn is not None else self.lsn
                return
        raise KeyError(name)


def demo() -> None:
    disk_cap = 100 * SEG_BYTES                       # pg_wal 目录可用 100 段
    p = Primary(disk_bytes=disk_cap, max_slot_wal_keep_size=None)

    sub = Slot("sub_analytics", restart_lsn=0)       # 逻辑订阅槽
    bk = Slot("standby_1", restart_lsn=0)            # 备库物理槽
    p.slots = [sub, bk]

    # 正常:消费端活着,位点跟随
    for _ in range(50):
        p.write_wal(SEG_BYTES)
        sub.restart_lsn = bk.restart_lsn = p.lsn
    print(f"正常运行 wal_kept={p.wal_kept() // SEG_BYTES} 段 ✅")

    # 事故:订阅端进程挂了,槽位不动,写流量继续
    for _ in range(60):                              # 消费端失联期间主库持续写
        p.write_wal(SEG_BYTES)
    print(f"订阅端失联:wal_kept={p.wal_kept() // SEG_BYTES} 段,磁盘压力 "
          f"{'超限!' if p.disk_pressure() > 0 else '未超限'}")

    for _ in range(50):                              # 继续写直到磁盘满
        p.write_wal(SEG_BYTES)
        if p.disk_pressure() > 0:
            print(f"磁盘满告警 ✅:wal_kept={p.wal_kept() // SEG_BYTES} 段 > 容量 "
                  f"{disk_cap // SEG_BYTES} 段,主库写路径即将停摆")
            break

    # 应急一(次优):advance 弃位点 -> 该槽不再拖住 WAL,订阅端丢增量需重建
    p.advance_slot("sub_analytics")
    print(f"advance 订阅槽后 wal_kept={p.wal_kept() // SEG_BYTES} 段 ✅"
          "(仍按备库位点保留:每个滞后槽都在独立拖住 WAL)")
    p.advance_slot("standby_1")
    print(f"备库槽也 advance 后 wal_kept={p.wal_kept() // SEG_BYTES} 段 ✅")

    # 预防:PG13+ max_slot_wal_keep_size 封顶 -> 槽标记 lost 而不是撑爆磁盘
    p2 = Primary(disk_bytes=disk_cap, max_slot_wal_keep_size=120 * SEG_BYTES)
    s2 = Slot("sub_lazy", restart_lsn=0)
    p2.slots = [s2]
    for _ in range(300):                             # 大量写入,远超单槽上限
        p2.write_wal(SEG_BYTES)
    assert s2.lost and s2.restart_lsn <= 120 * SEG_BYTES
    print("max_slot_wal_keep_size 生效 ✅:槽 restart_lsn 被强制推进(弃位点)"
          "并标记 lost,WAL 不再无限堆积")
    print("lost 槽的订阅端无法再续传,必须重建订阅(重新快照同步)")


if __name__ == "__main__":
    demo()
```

**追问一**：为什么消费端明明用事务内确认位点，重启后还是会重放一部分事件？
答：`send_feedback(flush_lsn)` 是异步确认——服务端把 WAL 写下盘与订阅端确认之间存在窗口；订阅端崩溃重启后从最后确认的位点重放，所以消费端必须按事件幂等设计（唯一键 upsert），这是协议约束而不是实现缺陷。

**追问二**：备库场景下不开复制槽、只靠 `wal_keep_size` 会怎样？
答：无槽时备库掉队超过 keep 窗口，主库直接回收所需 WAL，备库只能重新 basebackup（代价大但主库安全）；有槽则主库为备库无限保留（主库安全换来的磁盘风险）。这是"丢备库"与"撑爆主库"的取舍，生产建议槽 + max_slot_wal_keep_size 双保险。

## 背诵要点
- WAL 回收看最慢消费者：每个复制槽的 restart_lsn 独立拖住 WAL，消费端宕机 = 主库 WAL 无限堆积 = 磁盘满停摆。
- 应急：先复活消费端 → `pg_replication_slot_advance` 弃位点 → `DROP SLOT`；预防：PG13+ `max_slot_wal_keep_size` 封顶 + `wal_status/safe_wal_size` 三线监控。
- 巡检 `active=false` 且位点长期不动的闲置槽（应用下线未删槽是最常见事故源）；删槽即弃位点，需人工确认。
