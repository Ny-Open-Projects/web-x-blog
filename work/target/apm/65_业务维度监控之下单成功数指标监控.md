# 65. Go APM 监控系统实战: 业务维度监控 —— 下单成功数指标监控

## 纲要

- 前面几节把**应用系统层面**的指标监控建得差不多了，但还缺一个维度：**业务维度的指标监控**
- 业务指标举例：每小时登录人数、每天下单成功数/失败数、失败原因分类
- 让 dogAPM 暴露业务指标的第一步：给框架加一个方法，让业务系统把**自定义指标**注册进 **registry（指标注册中心）**
- 业务侧的规范：指标统一写在 **`metrics` 目录**下，包内提供统一的 `Work` 方法把指标一次性暴露出去
- 下单成功数指标用 **Counter** 类型，维度给 **商品（skuID）**，这样能看出"哪段时间、哪个商品卖得最火爆"
- 埋点：业务代码里 `WithLabelValues(skuID).Inc()`
- **新增指标时 main 不用改**，只动 `metrics` 文件——代码影响面最小化
- Grafana 侧新建「业务维度」面板层；Counter 用 `rate` 看速率、`increase` 看区间总量；下单不连续，所以**拉长到 5 分钟用 `increase`**

## 正文

### 为什么还要一个"业务维度"

通过前面几个小节，我们已经把整个应用系统的指标监控建得七七八八了，但**还有一个维度没有监测到——业务维度的指标监控**。

因为通常我们的业务系统会有各种各样的指标，比如：

- 每个小时的登录人数；
- 每天的下单成功数或者失败数、失败原因分类；
- ……

这些指标和"CPU 多少、QPS 多少"不是一回事——它们是**业务自己的语言**。这一节要解决两件事：

1. 这些业务维度的指标，应该怎么在应用系统当中**引入**进去？
2. 我们的 **dogAPM 框架**又应该怎么让业务系统**更优雅地接入**这些指标？

### 第一步：让业务系统的指标注册进 registry

要让业务系统用上 dogAPM 中所注册的 **registry（指标注册中心）**，就得让业务系统把它定义好的指标**注册到 registry 这个结构体里面来**，然后我们才能通过这个注册中心去**暴露业务指标**。

所以我们在这里增加一个方法，让业务系统去调用——业务系统调用这个方法，就是把它自己的自定义指标注册进来。

这个方法放在 **`info` 文件**里，因为我们想让业务系统能够通过**统一的方式**去引用 dogAPM 下面的代码：通过返回 `InfoOption`，让业务系统用类似这样的代码在 `Init` 方法当中对相关组件去进行初始化。方法内部则去调用注册中心，将业务系统的指标注册进来。

```go
// info.go —— 让业务系统把自定义指标注册进 registry
// 返回 InfoOption，使业务系统能在统一的 Init 流程里完成初始化
func WithMetrics(ms ...prometheus.Collector) InfoOption {
	return func(i *Info) {
		// 调用 dogAPM 的指标注册中心，把业务指标注册进来
		for _, m := range ms {
			i.Registry.MustRegister(m)
		}
	}
}
```

> 设计要点：框架只暴露一个"注册入口"，业务系统不需要知道 registry 在哪、怎么拿，更不需要关心 Prometheus 的初始化细节。

### 第二步：业务系统怎么定义自己的业务指标

接着就是业务系统这边要怎么定义自己的业务指标。由于我们模拟的是**用户下单**的流程，所以这里就建一个业务指标，叫做**下单成功数**。

**规范是这样的**：每个业务系统所要建的指标，都在 **`metrics` 目录**下新建一个 `metrics` 文件，业务系统自己的指标就在这个文件里自己去写。

```go
// metrics/metrics.go —— 业务指标统一定义处
package metrics

import (
	"github.com/prometheus/client_golang/prometheus"
)

var (
	// 下单成功数：Counter 类型，只增不减
	// 维度给一个"商品"，这样就能知道哪一段时间、哪个商品卖得最火爆
	OrderSuccessTotal = prometheus.NewCounterVec(
		prometheus.CounterOpts{
			Name: "order_service_total_order_success_total",
			Help: "下单成功数",
		},
		[]string{"sku_id"}, // 商品维度
	)
)

// Work 把业务系统所有的指标一次性暴露出去
// 以后新增指标：在这里定义 + 在这里添加即可
func Work() []prometheus.Collector {
	return []prometheus.Collector{
		OrderSuccessTotal,
	}
}
```

这里的关键是两点：

1. **给指标一个维度**——比如商品维度（`sku_id`）。有了它，我们就能知道**哪一段时间、哪个商品是卖得最火爆的**；
2. **在 `metrics` 包下定义一个 `Work` 方法**——目的是把业务系统所有的指标到时候都能够通过这个方法给暴露出来。这里我们仅仅定义了一个业务指标；**如果以后有其他业务指标，依然在这里定义、在这里添加**，最终都能通过 `Work` 方法吐出去。

这样就**把"业务系统如何去使用、定义 Prometheus 指标"规范化起来，让整个代码结构形成了一套标准**。

### 第三步：main 里注册进去

然后我们就需要在 `main` 方法这个地方去进行调用，将业务系统自身的指标给注册进来：

```go
// main.go
apm.Init(
	apm.WithMetrics(metrics.Work()...), // 一行搞定
)
```

**这样后续我们新增指标的时候，`main` 方法这里也是可以不用动的**，我们只需要去动 `metrics` 这个文件就可以了。

这背后是一条写代码的原则——**能不动就不动，尽量让你的代码的影响面更小**。新增一个业务指标，只改一处（metrics 文件），而不是在 main 里再加一行注册。

### 第四步：在业务代码里埋点

改好这部分代码之后，就应该往 `orderService` 这个业务代码的地方，把指标监控**显式地建立起来**：

```go
// orderService 下单成功后埋点
metrics.OrderSuccessTotal.
	WithLabelValues(skuID). // 维度：目前只设了一个，就是商品 skuID
	Inc()                   // 计数 +1
```

- 调用 `OrderSuccessTotal` 这个 Counter 的 **`WithLabelValues`** 方法；
- 使用 **`Inc`（increase）** 自增；
- 维度目前只设了一个，就是 **`skuID`**。

这样就将业务系统的指标监控建立起来了。

### 第五步：编译、启动、发请求验证

```bash
# 1) 重新编译 orderService
go build -o ./bin/orderService ./cmd/orderService

# 2) 进 Docker 把 orderService 启动起来
docker-compose up -d orderService

# 3) 用 Postman 向 orderService 发送一个下单请求
```

启动完成之后，用 Postman 向 `orderService` 发一个下单请求。成功之后，先去看 `orderService` 暴露出来的指标：

```bash
curl http://localhost:8080/metrics | grep order_success
# order_service_total_order_success_total{sku_id="1001"} 1
```

可以看到刚才定义的 `orderServiceTotalOrderSuccessTotal` 现在有了，并且**数量为 1**。再多下几单，计数会正常往上走。

### 第六步：Grafana 上建「业务维度」面板

现在我们就去 Grafana 上把这个指标建立起来。

在此之前，我们已有 **mysql 应用维度的监控**以及**应用服务维度的监控**。现在我们新建一个——名称就叫**业务维度的监控**。

为什么要单独分一层？这是为了**让整个监控是分层的**：在不同的层次，有不同的监控指标。这样**在出问题的时候，能够快速定位到对业务的影响面，以及出现问题的根因**。

```text
监控分层（出问题时的定位路径）
├── 业务维度   → 下单成功数/失败数、登录人数  ← 先看到"业务有没有受影响"
├── 应用服务维度 → QPS、错误数、耗时          ← 再看"哪个服务出问题"
├── 组件维度   → MySQL 慢查询、连接池          ← 再看"哪个依赖出问题"
└── 运行时维度 → CPU、内存、协程、GC           ← 最后看"机器/进程层面"
```

#### 先建变量 APP 和 host

首先还是要往面板上面去建立变量 **APP** 和 **host**。这两个维度基本是固定的，我们要取整个指标当中的一个标签值。

具体取哪个标签？这里还是去取 **CPU 或者内存相关的这些标签**——因为它们是**一定会有**的，不会因为你在下单这段时间以内没有下单数就不给你展示。

```text
变量取值建议
├── app  = label_values(cpu_usage{app=~"$APP"}, app)     # 一定有值
├── host = label_values(cpu_usage{app=~"$APP"}, host)    # 一定有值
└── ❌ 不要用 label_values(order_success_total, sku_id)
        没下单时这个指标根本不存在，下拉框会是空的
```

#### 再建监控面板

APP 和 host 有了之后，接着就可以去建立监控面板。

因为我们的 `orderServiceTotal` 是一个 **Counter 类型**，所以**用 `rate` 函数其实是很合适的**——可以算出每秒钟的下单成功数：

```promql
# 每秒下单成功速率
sum(rate(order_service_total_order_success_total{app=~"$APP", host=~"$host"}[5m])) by (sku_id)
```

但要注意一个现实问题：**在业务上下单的数量很可能并不是每时每刻都发生的**，如果你通过"每秒"这个量级去看，可能很难发现一些问题。

所以这里干脆改用 **`increase`**，并**把时间间隔拉得长一点**（比如 5 分钟）——这样每一个点看到的就是**从这个点开始、过去 5 分钟内的下单数是多少**：

```promql
# 过去 5 分钟内的下单成功数，按商品维度
sum(increase(order_service_total_order_success_total{app=~"$APP", host=~"$host"}[5m])) by (sku_id)
```

最后修改一下展示出来的维度，我们希望看到的是 **`app`、`host` 以及 `sku_id`**。这样就完成了下单成功数的监控。

```text
面板配置速记
├── 指标类型: Counter
├── 看速率   → rate(metric[5m])
├── 看区间量 → increase(metric[5m])   ← 下单不连续时用这个
└── 展示维度: app / host / sku_id
```

## Demo 示例

```bash
# ① 定义指标（metrics/metrics.go）
#    OrderSuccessTotal = NewCounterVec(..., []string{"sku_id"})

# ② main 里注册（一行，之后新增指标不用再改 main）
apm.Init(apm.WithMetrics(metrics.Work()...))

# ③ 业务代码埋点
metrics.OrderSuccessTotal.WithLabelValues(skuID).Inc()

# ④ 重新编译并启动
go build -o ./bin/orderService ./cmd/orderService
docker-compose up -d orderService

# ⑤ 用 Postman 发一个下单请求，然后看指标
curl -s http://localhost:8080/metrics | grep order_success
# order_service_total_order_success_total{sku_id="1001"} 1

# ⑥ Grafana 面板查询（按商品看过去 5 分钟下单数）
# sum(increase(order_service_total_order_success_total{app=~"$APP",host=~"$host"}[5m])) by (sku_id)
```

### 运行说明

1. 埋点后必须**重新编译并重启** `orderService`，否则 `/metrics` 上看不到新指标；
2. 第一次看指标时 `order_success_total` 可能**不存在**（标签只有在 `WithLabelValues` 被调用后才产生）——**发一笔真实下单请求**它才会出现；
3. Grafana 变量建议取 CPU/内存这类**恒定存在的指标**的标签，避免业务没流量时下拉框为空；
4. 时间区间选 5 分钟还是 1 分钟，取决于业务发生频率——**低频业务把区间拉长**才看得出趋势。

### 代码说明

- **`WithMetrics(ms ...prometheus.Collector) InfoOption`**：框架侧的注册入口。业务系统只传实现了 `prometheus.Collector` 的对象进来，不接触 registry 细节；
- **`metrics.Work()`**：业务侧的指标清单。**新增指标只改这里**，main 不动——这是"影响面最小化"的落地方式；
- **`prometheus.NewCounterVec`**：带标签的 Counter。`Counter` 只增不减，适合"累计成功数"这类单调增长的量；
- **`WithLabelValues(skuID).Inc()`**：指定标签值并自增。**标签值必须是有限集合**（商品 ID 可以，用户 ID 不行——会 cardinality 爆炸）。

### 技术点总结

- **业务维度监控是另一个层级**：和 CPU、QPS 不同，它用业务语言表达（登录人数、下单成功数、失败原因），建面板时也要**单独分层**，目的是出问题时先看"业务受没受影响"；
- **框架侧只暴露一个注册入口**（返回 `InfoOption` 的 `WithMetrics`），业务侧在统一的 `Init` 流程里接入，**不感知 registry**；
- **业务侧规范化**：指标统一写在 `metrics` 目录，包内一个 `Work` 方法把全部指标吐出去；**新增指标只动这一个文件，main 不用改**——遵循"能不动就不动"；
- **维度要选得有意义**：给下单数加商品维度，就能回答"哪个商品最火爆"；但维度值必须是**有限集合**，否则会把 Prometheus 打爆；
- **Counter 用 `rate` 还是 `increase`**：看每秒速率用 `rate`，看区间总量用 `increase`。**下单不是每时每刻都发生，所以拉长到 5 分钟用 `increase` 更合适**；
- **Grafana 变量取值要挑一定存在的标签**（如 CPU/内存的 `app`/`host`），不要取业务指标的标签——没业务流量时下拉框会是空的；
- 这一节只举了一个指标的例子。真实业务环境会有很多业务指标需要监控，但**只要你在应用程序里定好了"怎么建立、怎么暴露"，剩下的就是在 Grafana 上建对应的监控面板**——而建面板无外乎**四种指标类型**，根据不同类型选不同的函数，就能绘制出不同的面板。
