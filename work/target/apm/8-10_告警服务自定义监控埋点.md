# Go APM 监控系统实战: dogalarm 自身指标埋点与 Prometheus 接入

## 纲要

- 原则：告警服务自身不能是黑盒，必须像业务服务一样被监控。
- 两个自定义指标：
  - `dogalarm_discard_alert_total`（Counter）：被限流排重丢弃的告警数，标签为 app / host / 通知类型。
  - `dogalarm_service_alive`（Gauge）：服务存活状态，1 为存活、0 为宕机。
- 埋点位置：限流命中处 Counter 自增；保活探测处按结果设置 Gauge。
- 接入方式：与业务服务一致，由 Prometheus 抓取，Grafana 展示。
- Gauge 用常量定义状态值，避免魔法数字散落各处。

## 为什么告警服务必须监控自己

这里有一个容易陷入的悖论：**告警系统是所有服务的最后一道防线，但它自己挂了没人知道**。

想象这个场景：dogalarm 因为内存泄漏被 OOM 杀掉，此时 order-service 真的宕机了。指标告警发不出来，日志告警发不出来，保活探测也停了——整个 APM 系统静默失效，而所有人的直观感受是"今天真安静"。

所以告警服务必须把自己也当成被监控对象，暴露至少两类信息：

- **它自己做得怎么样**：发了多少告警、丢了多少告警、有没有触发限流。
- **它看到的别人怎么样**：探测到的各服务存活状态。

## 指标选型：Counter 与 Gauge

Prometheus 的指标类型选择有明确语义，选错会让后续查询很别扭：

| 类型 | 语义 | 特征 | 本服务用例 |
| --- | --- | --- | --- |
| Counter | 单调递增的累计值 | 只增不减，重启归零 | 被丢弃的告警总数 |
| Gauge | 可任意上下波动的瞬时值 | 可读可写 | 服务存活状态（1/0） |
| Histogram | 采样分桶，算分位数 | 需要 bucket 配置 | 告警发送耗时（可选） |
| Summary | 客户端算分位数 | 不能被聚合 | — |

**丢弃告警数用 Counter**。它是一个只增不减的累计量，关心的是"过去五分钟丢了多少"，用 `rate()` 或 `increase()` 求增量即可。

**服务存活状态用 Gauge**。它需要在 1 和 0 之间来回切换，而且我们关心的是"当前值是多少"，不是累计量。Gauge 的 `Set` 方法正好对应这种"随时改状态值"的场景。

## 定义指标

```go
// 根据讲稿逻辑补充：dogalarm 自定义指标
package metrics

import (
	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promauto"
)

// 服务存活状态常量，避免魔法数字散落在探测代码里。
const (
	// StatusAlive 服务存活
	StatusAlive = 1
	// StatusDown 服务宕机
	StatusDown = 0
)

var (
	// DiscardAlertTotal 因限流排重而被丢弃的告警数量。
	// 标签维度：服务名、主机、通知类型（dingtalk / phone）。
	DiscardAlertTotal = promauto.NewCounterVec(
		prometheus.CounterOpts{
			Name: "dogalarm_discard_alert_total",
			Help: "因限流或排重被丢弃的告警总数",
		},
		[]string{"app", "host", "notify_type"},
	)

	// ServiceAlive 服务存活状态，1 存活 / 0 宕机。
	// 标签维度：服务名、主机。
	ServiceAlive = promauto.NewGaugeVec(
		prometheus.GaugeOpts{
			Name: "dogalarm_service_alive",
			Help: "服务存活状态，1 表示存活，0 表示宕机",
		},
		[]string{"app", "host"},
	)
)
```

标签设计遵循一个原则：**标签取值集合必须有限**。这里 `app` 是几十个服务名，`host` 是几百台机器，`notify_type` 只有两三种，都在可控范围。绝不要把 TraceID、错误文本、用户 ID 这类高基数值塞进标签——每个标签组合都是一个独立时间序列，基数爆炸会直接拖垮 Prometheus。

## 埋点：限流丢弃处

在限流命中的分支上自增 Counter：

```go
// 根据讲稿逻辑补充：限流命中处埋点
func AlertWithLimit(ctx context.Context, rdb *redis.Client, n *Notifier, content string) {
	fp := redislimiter.Fingerprint(content)
	key := "apm:alert:limit:" + n.App + ":" + fp

	if redislimiter.IsLimit(ctx, rdb, key, alertLimitCount, alertLimitWindow) {
		// 被丢弃的告警按服务、主机、通知类型三个维度计数
		metrics.DiscardAlertTotal.
			WithLabelValues(n.App, n.Host, "dingtalk").Inc()
		return
	}

	_ = SendDingTalk(n.DingTalkWebhook, content)
}
```

这个指标的价值在于**让限流阈值有数据可依**。长期为 0 说明阈值太松，钉钉配额其实没被充分利用；持续走高说明要么业务在持续报错，要么阈值太紧，需要调整。没有这个指标，阈值永远是拍脑袋定的。

## 埋点：保活探测处

探测成功设 1，探测失败设 0：

```go
// 根据讲稿逻辑补充：保活探测处埋点
func (p *Probe) checkAlive(app string, host string, url string, maxRetry int) {
	failCount := 0

	for i := 0; i < maxRetry; i++ {
		resp, err := p.client.Get(url)
		if err != nil || (resp != nil && resp.StatusCode != http.StatusOK) {
			failCount++
			if resp != nil {
				resp.Body.Close()
			}
			continue
		}
		resp.Body.Close()
		failCount = 0
		break
	}

	if failCount == 0 {
		metrics.ServiceAlive.WithLabelValues(app, host).Set(metrics.StatusAlive)
		return
	}

	metrics.ServiceAlive.WithLabelValues(app, host).Set(metrics.StatusDown)
	p.alert.Phone(app, host, "服务宕机: "+app+" @ "+host)
}
```

Gauge 的标签组合在首次 `Set` 时才被创建，因此每个服务的每台机器都会有一条独立时间序列，在 Grafana 上可以按服务逐行展示存活状态。

## 暴露指标端点

与业务服务完全一致，挂上 Prometheus 的 HTTP handler：

```go
// 根据讲稿逻辑补充：暴露 /metrics
package main

import (
	"log"
	"net/http"

	"github.com/prometheus/client_golang/prometheus/promhttp"
	_ "dogalarm/metrics" // 触发指标注册
)

func main() {
	go func() {
		// 独立的 metrics 端口，与告警业务端口分离
		mux := http.NewServeMux()
		mux.Handle("/metrics", promhttp.Handler())
		log.Println("dogalarm metrics on :9091")
		log.Fatal(http.ListenAndServe(":9091", mux))
	}()

	// 告警服务主逻辑...
	select {}
}
```

对应的 Prometheus 抓取配置：

```yaml
# 根据讲稿逻辑补充：prometheus.yml 新增 job

  - job_name: dogalarm
    scrape_interval: 15s
    static_configs:
      - targets: ["192.168.1.20:9091"]
```

## 与 APM SDK 的分工

这里要区分两类指标：

- **自定义业务指标**（本节内容）：`dogalarm_discard_alert_total`、`dogalarm_service_alive`，需要手写埋点代码，反映告警服务自身的业务语义。
- **通用运行时指标**：CPU、内存、协程数、GC 次数等。这些不需要手写——只要服务调用了 dogapm 的 `EnableAPM()` 方法，SDK 会自动采集并暴露，Prometheus 照常抓取即可。

换句话说，`EnableAPM()` 解决的是"所有 Go 服务都需要的基础指标"，手写埋点解决的是"只有这个服务才有的业务指标"。两者叠加才构成完整的自监控视图。

## API 速览

| API | 签名 | 说明 |
| --- | --- | --- |
| `promauto.NewCounterVec` | `(opts CounterOpts, labelNames []string) *CounterVec` | 创建带标签的 Counter，自动注册到默认注册表 |
| `CounterVec.WithLabelValues(...).Inc()` | `(v ...string)` | 按标签取值自增 1 |
| `promauto.NewGaugeVec` | `(opts GaugeOpts, labelNames []string) *GaugeVec` | 创建带标签的 Gauge |
| `GaugeVec.WithLabelValues(...).Set(v)` | `(lvs ...string, v float64)` | 设置瞬时值 |
| `promhttp.Handler()` | `() http.Handler` | 暴露 `/metrics` 的 HTTP handler |

## Demo 示例

**运行说明**：`go run .` 后访问 `http://localhost:9091/metrics`，可以看到 `dogalarm_discard_alert_total` 与 `dogalarm_service_alive` 两个指标。配合本地 Prometheus 抓取即可在 Grafana 上绘图。

**代码说明**：示例依赖 `github.com/prometheus/client_golang`。指标定义放在独立 `metrics` 包并用 `promauto` 自动注册，主程序只需匿名导入即可完成注册，避免在 main 里堆砌注册代码。

**技术点总结**：

- 告警服务必须自监控，否则它自己失效时整个 APM 系统会静默瘫痪。
- Counter 用于单调递增的累计量（配合 `rate()` 看速率），Gauge 用于可上可下的瞬时状态值。
- 状态值用常量定义，避免魔法数字。
- 标签基数必须可控，绝不把 TraceID、错误文本等高基数字段放进标签。
- 通用运行时指标由 `EnableAPM()` 自动提供，自定义埋点只关注业务语义，两者互补。
