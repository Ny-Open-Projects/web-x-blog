# Go APM 监控系统实战: 确定需要追踪的调用链路

## 纲要

- 链路追踪不是"全采就完事"：数据量不可接受，必须有选择地采集最有排查价值的链路
- 六类值得全量保留的链路（最佳实践）：含错误的链路、数据库慢查询 / 长事务、Redis 慢查询、慢 HTTP 接口、慢 gRPC 接口、慢第三方 HTTP 请求
- 采集目标统一为"能还原一次慢或出错请求的完整参数与耗时分布"，用于事后定位与优化
- 这六条直接决定了后续 APM 框架要往哪些切入点插桩

## 为什么先定范围，再写代码

在动手给系统加链路追踪之前，先回答一个问题：我们到底要为哪些调用链路埋点？

全量采集在成本上不可行——一条请求穿过十几个服务，每个服务再访问几次 DB / Redis，全采下来存储与网络开销都扛不住。真正有价值的是"出了问题、或者慢得不正常"的那部分链路。把它们完整保留下来，才能在排障时还原当时的参数、耗时与依赖关系。

讲稿给出的六类最佳实践，可以直接搬上生产：

| 类别 | 采集动机 | 典型切入点 |
| --- | --- | --- |
| 含错误的链路 | 出错时希望能看到整条请求为什么错、错在哪 | 错误日志、RPC / DB 返回的错误 |
| 数据库慢查询 / 长事务 | 数据库最常见的两个性能瓶颈就是慢 SQL 与长事务 | SQL 执行前后计时、事务起止计时 |
| Redis 慢查询 | 与 MySQL 类似，基础组件耗时过长最该被记录 | Redis 命令前后计时 |
| 慢 HTTP 接口 | 对外接口慢，需要知道慢在哪一段 | HTTP 中间件 / 拦截器 |
| 慢 gRPC 接口 | 服务间内部通信慢，要拿请求参数定位 | gRPC 拦截器 |
| 慢第三方 HTTP 请求 | 依赖外部服务变慢时，要确认慢在第三方 | 出向 HTTP 客户端包装 |

这六类的共同点是：**它们都对应"一次请求里，某个环节慢了或错了"**。只要命中其中任意一条，整条 Trace 就值得被完整保留。

## 把"采集策略"落成可维护的配置

把这些最佳实践显式地表达成一份策略配置，比散落在各处的 magic number 更容易维护。下面是一份自补的、可直接运行的示例（根据讲稿逻辑补充），把六类开关集中管理：

```go
package main

import "fmt"

// TracePolicy 描述"哪些链路值得全量保留"的最佳实践开关
type TracePolicy struct {
	CaptureErrorChain       bool // 含错误的链路
	CaptureSlowDBQuery      bool // 慢 SQL / 长事务
	CaptureSlowRedis        bool // 慢 Redis 命令
	CaptureSlowHTTP         bool // 慢 HTTP 接口
	CaptureSlowGRPC         bool // 慢 gRPC 接口
	CaptureSlow3rdPartyHTTP bool // 慢第三方 HTTP 请求
}

// DefaultTracePolicy 返回生产环境推荐的全开策略
func DefaultTracePolicy() TracePolicy {
	return TracePolicy{
		CaptureErrorChain:       true,
		CaptureSlowDBQuery:      true,
		CaptureSlowRedis:        true,
		CaptureSlowHTTP:         true,
		CaptureSlowGRPC:         true,
		CaptureSlow3rdPartyHTTP: true,
	}
}

func main() {
	policy := DefaultTracePolicy()
	fmt.Printf("需要追踪的链路类型: %+v\n", policy)
}
```

实际框架里，这份策略会进一步和 Collector 的后置采样器（tail sampling）配合：只要某条 Trace 命中上述任一条件（含 `error` 属性、或超过慢查询阈值），就在 Collector 侧把整条 Trace 完整落库。

## 技术点总结

- 链路追踪要"有选择地采"，而不是无脑全量
- 六类值得保留的链路都对应"慢或错"这一核心诉求
- 把采集策略集中成配置，便于与后置采样器联动
- 明确范围后，后面 4-11（错误链路）、4-12~4-16（MySQL 慢查询）、4-18（Redis 慢查询）的插桩才有明确目标
