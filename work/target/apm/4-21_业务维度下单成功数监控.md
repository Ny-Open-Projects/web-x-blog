# Go APM 监控系统实战: 业务维度监控之下单成功数指标监控

## 纲要

- 业务维度指标的必要性：登录人数、下单成功 / 失败数、失败原因分类等，是前述「机器 / 中间件 / 应用服务」三层都覆盖不到的视角
- 框架侧接入方式：业务系统通过框架提供的「指标注册中心（metrics registry）」统一注册自定义指标
- 规范化目录：每个业务系统在 `metric` 包下新建 `metric.go` 定义自己的指标，并由一个 `Work`（暴露）方法统一导出
- 示例指标 `order_success_total`：Counter 类型，带 `sku_id` 维度，用于统计不同商品的下单火爆程度
- 业务埋点位置：在 `orderservice` 的业务代码里调用 `order_success_total.WithLabelValues(skuID).Inc()`
- 面板分层：新建独立的「业务维度」Dashboard，变量 `app`、`host` 取自必定存在的标签（如 CPU / 内存相关标签），避免无数据时面板空白
- 绘图选择：`order_success_total` 是 Counter，用 `increase()[5m]` 拉长窗口看「每 5 分钟下单数」，展示维度 `app`、`host`、`sku_id`

## 正文

### 为什么要做业务维度监控

前面几节我们把应用系统的指标监控建得七七八八了，但还有一个维度没覆盖到——**业务维度**。一个真实的业务系统往往有大量业务指标：每小时登录人数、每天的下单成功 / 失败数、失败原因分类等等。这些指标和「机器 CPU 高不高」「接口延迟大不大」无关，却最贴近老板和运营真正关心的事。

dogAPM 框架要解决的问题是：让业务系统用一种**优雅、统一**的方式，把自己的业务指标接进来，并自动暴露给 Prometheus。

### 框架侧：提供指标注册中心

要让业务系统的指标被采集，首先得让业务系统能访问到 dogAPM 已经注册好的「指标注册中心（metrics registry）」。框架提供一个方法，业务系统调用它，就能把自己的自定义指标注册进这个 registry，之后才能通过 `/metrics` 暴露出去。

为了保持「统一引用框架代码」的风格，这个方法放在 `info` 文件里，返回一个 `info option` 类型。业务系统像下面这样初始化对应组件即可，无需关心 registry 的内部细节：

```go
// 根据讲稿逻辑补充：框架暴露注册入口，业务系统通过 option 把自定义指标注册进 registry
type Option func(*MetricsRegistry)

// RegisterBusinessMetrics 让业务系统把自定义指标注册到框架的注册中心
func RegisterBusinessMetrics(collectors ...prometheus.Collector) Option {
	return func(r *MetricsRegistry) {
		for _, c := range collectors {
			r.reg.MustRegister(c) // 真实实现内部调用 prometheus 注册
		}
	}
}
```

### 业务侧：规范化定义指标

由于讲稿模拟的是用户下单流程，就建一个名为「下单成功数」的指标。约定每个业务系统都在 `metric` 包下新建 `metric.go`，自己的指标写在里面：

```go
// metric/metric.go  —— 业务系统自己的指标定义（根据讲稿逻辑补充）
package metric

import "github.com/prometheus/client_golang/prometheus"

// OrderSuccessTotal 下单成功数，按商品维度切分
var OrderSuccessTotal = prometheus.NewCounterVec(
	prometheus.CounterOpts{
		Name: "order_success_total",
		Help: "下单成功数统计",
	},
	[]string{"sku_id"}, // 商品维度：看哪段时间哪个商品卖得最火
)

// Work 统一导出业务系统的全部指标
func Work() {
	prometheus.MustRegister(OrderSuccessTotal)
}
```

这里的关键是「标准化」：以后新增业务指标，只需在 `metric.go` 里再定义一个，并补到 `Work` 方法里；框架侧注册入口和面板逻辑都不用动。这正好呼应了写代码的原则——**能不动就不动，把改动影响面降到最低**。

### 业务代码里埋点

`orderservice` 的业务代码里，在下单成功后调用计数方法即可。因为只设了 `sku_id` 一个维度，埋点非常轻量：

```go
// 根据讲稿逻辑补充：下单成功后 +1，按 sku_id 切分
metric.OrderSuccessTotal.WithLabelValues(skuID).Inc()
```

把 `orderservice` 重新编译、扔到 docker 里启动，用 Postman 发几个下单请求，再去 `/metrics` 里搜 `order_success_total`，应当能看到指标且数量为 1；多发几次数值随之增长，说明埋点链路通了。

### 在 Grafana 建业务维度面板

前面已经有了 MySQL 维度、应用服务维度的监控，现在新建一个名为「业务维度」的 Dashboard，继续贯彻**监控分层**：不同层有不同指标，出问题能快速定位影响面与根因。

面板变量沿用 `app` 和 `host` 两个基本维度，标签值取自**必定存在**的标签（如 CPU / 内存相关标签），而不是 `sku_id`——否则在没有下单发生的时段，面板会因为没有数据而一片空白。

绘图表达式的选择：

```promql
increase(order_success_total{app=~"$app", host=~"$host"}[5m])
```

为什么用 `increase` 而不是 `rate`？`order_success_total` 是 Counter，`rate` 算的是「每秒」速率。但下单并非每时每刻都发生，用每秒量级很难发现问题。改用 `increase` 并把窗口拉到 5 分钟，每个点代表「过去 5 分钟的下单数」，业务含义更直观。最后把展示维度设为 `app`、`host`、`sku_id`，就能看到每个商品在这段时间的下单分布。

```mermaid
flowchart TD
    A[业务系统在 metric 包定义 order_success_total] --> B[Work 方法统一注册到 registry]
    B --> C[orderservice 业务代码 Inc 埋点]
    C --> D[/metrics 暴露给 Prometheus]
    D --> E[Grafana 业务维度 Dashboard]
    E --> F[increase[5m] 按 app/host/sku_id 展示]
```

## Demo 示例

下面给出一个可独立运行的完整示例，演示「定义 CounterVec → 业务埋点 → 通过 `/metrics` 暴露」的全过程。

```go
package main

import (
	"fmt"
	"log"
	"net/http"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promhttp"
)

// OrderSuccessTotal 下单成功数（根据讲稿逻辑补充）
var OrderSuccessTotal = prometheus.NewCounterVec(
	prometheus.CounterOpts{
		Name: "order_success_total",
		Help: "下单成功数统计",
	},
	[]string{"sku_id"},
)

func init() {
	prometheus.MustRegister(OrderSuccessTotal)
}

// placeOrder 模拟一次下单：成功后按 sku_id 计数
func placeOrder(skuID string) {
	// ... 真实业务逻辑 ...
	OrderSuccessTotal.WithLabelValues(skuID).Inc()
}

func main() {
	// 模拟 3 次 sku-1001、2 次 sku-2002 的下单成功
	for i := 0; i < 3; i++ {
		placeOrder("sku-1001")
	}
	for i := 0; i < 2; i++ {
		placeOrder("sku-2002")
	}

	fmt.Println("已写入示例指标，访问 http://localhost:8080/metrics 查看 order_success_total")
	log.Fatal(http.ListenAndServe(":8080", promhttp.Handler()))
}
```

### 运行说明

```bash
go mod init order-metric-demo
go get github.com/prometheus/client_golang/prometheus
go run main.go
# 另开终端
curl -s http://localhost:8080/metrics | grep order_success_total
```

在 Grafana 中添加 Panel，PromQL 填 `increase(order_success_total[5m])`，即可看到与讲稿一致的下单成功数趋势。

### 代码说明

- `order_success_total` 是 CounterVec，标签 `sku_id` 决定时间序列条数；基数 = sku 数量
- 埋点放在「下单成功」的业务分支里，只统计成功数（失败数可另建 `order_failed_total` 并带原因标签）
- 面板变量优先取必定存在的标签，避免无数据时段面板空白

### 技术点总结

- 业务指标通过框架的 metrics registry 统一注册，业务侧只需在 `metric` 包按规范定义
- 监控分层：业务维度单独成 Dashboard，和机器 / 中间件 / 应用服务层互不混杂
- Counter 类指标看「区间增量」用 `increase`，看「每秒速率」用 `rate`，按业务语义选择
- 面板变量要取自必定存在的标签，保证任何时段都有数据可展示
