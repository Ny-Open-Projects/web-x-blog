### 2-4 跳槽面试官对技术选型的考察点 — 需修（轻）

1. 【P2】案例一参考回答第 4 点，原句：「短信验证码需写入 Redis，涉及『写入验证码』和『写入过期时间』两个操作。这两个操作必须同时成功或同时失败……用原子性操作保证存入 Redis 的验证码不受异常影响。」
   → 建议：改为「Redis 是单线程处理命令的，单条命令天然原子；验证码写入与过期设置应合成一条命令（`SET key value EX 60`），避免分两条命令执行时中间失败留下无过期时间的脏 key」。
   理由：原表述把「存值 + 设过期」说成"两个操作需要事务原子性"，在 Redis 语境下不准确——Redis 无跨命令事务保证（MULTI/EXEC 才有），工程上正确做法正是用一条原子命令解决。面试官若追问细节，这个说法反而露怯。防重提交的"原子性"本质是"比对-写入"用原子命令防并发重复，与 MySQL 事务类比也应弱化。

其余：面试考察点四角度（依据/决策过程/兼容影响/可持续性）专业；案例二的 Gitee/云效/Docker 选型理由成立。

### 2-5 龙争虎斗—前端开发必学框架之 Vue 和 React — 需修

1. 【P1】Diff 算法对比 React 小节，原句：「React 用 `mountIndex`（旧索引）与 `lastIndex`（新遍历中的最大索引）比较：当 `mountIndex >= lastIndex` 不移动，否则右移。通过一次遍历完成节点排序，**同样保证最小移动次数**。」
   → 建议：改为「React 遍历新列表，用每个节点在旧列表中的下标（`oldIndex`）与已处理节点的最大下标（`lastPlacedIndex`）比较：`oldIndex >= lastPlacedIndex` 不移动，否则标记移动。」并删除/改写"同样保证最小移动次数"——如「React 的策略实现简单、只需一次遍历，但**不保证**最小移动次数（极端乱序时可能多移），这也是 Vue 3 引入最长递增子序列的原因」。
   理由：① 命名错误：React 源码中是 `oldIndex`/`lastPlacedIndex`，没有 `mountIndex`（mountIndex 是 vue-diff 教程混入的叫法）；② 事实错误："保证最小移动次数"是 Vue LIS 的性质，React 的算法恰好是反例——它只避免不必要的移动，不追求最少移动。这句是本篇唯一较硬的技术伤，面试场景会被追问翻车。

2. 【P2】React 特点段，原句：「18 版本起默认**函数组件**，摒弃 class 类组件，降低学习曲线」
   → 建议：加限定「（class 组件仍可用，只是官方主推函数式，与《大展经纶》篇的表述保持一致）」。
   理由：2-9 已写了正确限定（"并非 18 之后不能用 class"），2-5 却说"摒弃"，两篇口径不一；且"摒弃"不符合官方口径（class 组件未废弃）。实际官方文档现在主推的更是 RSC/框架方案，"18 起默认函数组件"本身也建议改成"Hooks（16.8）成熟后，18 时代函数组件已是绝对主流"更准确，至少删掉"摒弃"。

其余：Vue 3 首尾对比 + LIS 的示例（B C D → D B C，保 B/C 动 D）推导正确；Star 数、2014/2013 年份、"React 严格说是库"均公允；Next.js ≠ NestJS 的提示到位。
