# 低代码项目平台编辑模块—页面头部草稿功能开发

> **导语**：编辑器刷新一次就丢掉辛辛苦苦摆好的组件，是 low-code 平台最不能忍的体验问题。本文讲清"存至草稿"如何把 store 里的三份状态序列化进 localStorage、页面初始化时又如何读回并覆盖 store，以及为什么额外存一个时间戳用于和发布时间比对。读完你能实现一套可自动恢复、且能与服务端发布结果正确取舍的草稿机制。

## 前置知识

建议先读《低代码项目平台编辑模块—页面头部动态标题开发》，了解 EditHeader 的结构拆分；再熟悉《低代码项目平台编辑模块—页面组件拖拽排序功能开发》中 store 维护的组件配置与排序数组，以及 MobX 的 toJS 用法。

## 正文

### 头部中间的按钮区

EditHeader 左侧是动态标题，中间是预览、草稿、发布三个功能。这一集把中间区域抽离成 header 目录下的 Center 组件：用 Ant Design 的 Space 包裹一组 Button，其中预览与发布先只写出样式，本集集中实现"存至草稿"。

点击"存至草稿"要保存的是当前页面的完整配置，而它们都维护在 store 里，一共三份状态：

- componentConfigs：所有已配置组件的属性信息；
- sortableComponentConfig：组件排序，即由每个组件 ID 组成的数组；
- currentComponentConfig：当前默认选中的组件。

只要把这三份状态原样搬进浏览器缓存，刷新后就能还原出和离开前一模一样的画布。

### 存入草稿：store → localStorage

storeInLocalStorage 定义在 useStoreComponents 里，逻辑分三步：

1. 从 store 取出三份状态。MobX 响应式数据是 Proxy，要用 toJS 先转成普通对象。
2. localStorage 只能存字符串，因此每份都要经 JSON.stringify 序列化。
3. 用 localStorage.setItem 分别以 componentConfig、sortableComponentConfig、currentComponentConfig 为 key 写入。

```ts
const storeInLocalStorage = () => {
  const componentConfig = JSON.stringify(toJS(storeComponents.compConfigs));
  const sortableComponentConfig = JSON.stringify(
    toJS(store.components.sortableComponentConfig),
  );
  const currentComponentConfig = JSON.stringify(
    toJS(store.components.currentComponentConfig),
  );
  localStorage.setItem('componentConfig', componentConfig);
  localStorage.setItem('sortableComponentConfig', sortableComponentConfig);
  localStorage.setItem('currentComponentConfig', currentComponentConfig);
  // 记录操作时间戳，供后续与发布时间比对
  localStorage.setItem('store_time', String(Date.now()));
};
```

最后还要额外写入一个 store_time——当前操作的时间戳。它现在看似多余，实则是为后续逻辑铺路：等发布接口联调完成后会再存一个 release_time，两个时间谁更晚，就说明哪一份数据更新，应该用哪一份来渲染。写完提示"保存成功"。

### 读取草稿：localStorage → store

只存不读是没有意义的。读取逻辑放在外层 Edit 父组件的 useEffect 里，页面初始化时执行 localStorageInStore：

- 用 localStorage.getItem 取回三份配置、store_time，以及（后续才会有的）release_time；
- 先判断 componentConfig 有值且不是空对象——为空说明本地没有草稿，得转而向服务端请求页面组件信息；
- 把 store_time 与 release_time 都转成 number 再比较。若本地缓存时间大于发布时间，说明草稿更晚、更新，就用本地数据：JSON.parse 反序列化三份配置，覆盖回 store 的对应 state，并提示"已自动从草稿中读取数据"；
- 若缓存时间小于发布时间，则说明服务端发布的内容更新，走从服务端获取页面组件信息的分支（该方法本集先占位，等发布接口联调后补齐）。

至此形成闭环：存草稿是 store → localStorage，恢复草稿是 **localStorage → store**，画布只认 store 这一份数据源。

### 演示中的验证

新增一批组件后点击存至草稿，右侧缓存面板里三个 key 的值和操作时间都会刷新；此时刷新页面，画布自动还原出刚才的配置。再把组件删到只剩一个卡片、重新存草稿，可以看到缓存里的值（例如 video 相关内容）与 store_time 又发生变化，再刷新得到的就是最新一次操作的结果——草稿始终跟随最后一次编辑。

### 配套工程

```json
{
```

## 小结

- 头部中间抽成 Center 组件（Space + Button）；本集只实现"存至草稿"，预览与发布先留样式。
- 草稿要存三份 store 状态：componentConfigs、sortableComponentConfig、currentComponentConfig。
- MobX 数据先用 toJS 转普通对象，再 JSON.stringify 序列化写入 localStorage；额外记 store_time 时间戳。
- 恢复时在 Edit 的 useEffect 里 getItem + JSON.parse 覆盖回 store；通过 store_time 与 release_time 的大小决定用本地草稿还是服务端发布内容。
- 缓存为空或本地时间更早时，走服务端获取分支（待发布接口联调后补齐）。
