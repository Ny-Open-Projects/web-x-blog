# Jmeter实战压测结果之响应断言

> **导语**：结果树里"打勾=成功"默认只看 HTTP 状态码 200，但状态码 200 不代表业务正确。本文讲 **响应断言（Response Assertion）**，教你按响应代码或响应文本自定义校验规则，让压测自动识别"假成功"。

## 前置知识

本文建立在《Jmeter实战之压测结果聚合报告分析》之上，需要已会用结果树查看请求明细，并理解 HTTP 响应由状态行、响应头、响应体组成。

## 正文

### 默认的成功判定有多"浅"

在查看结果树里，每条请求成功会显示绿色对勾、失败显示红叉。JMeter 默认是根据 **响应头里的状态码** 判断的——只要返回 200，它就认为成功。

但状态码 200 只能说明"服务器收到了请求并正常响应"，**不能保证业务正确**。比如登录接口返回 200，但响应体是 `{"code":-1,"data":null,"msg":"密码错误"}`，结果树仍会打勾，这就属于"假成功"。所以我们需要断言来进一步校验。

### 什么是响应断言

**断言（Assertion）** 的本质是：定义一个你期望满足的约束条件，当条件不满足时就标记为失败。JMeter 中最常用的是 **响应断言（Response Assertion）**，它只作用于**所在的那一个取样器**。

右键 **取样器 → 添加 → 断言 → 响应断言** 即可。

### 断言的两个关键配置

响应断言主要靠两项决定"校验什么、怎么校验"：

1. **要测试的响应字段**
   - 响应文本（Response Body 的内容）
   - 响应代码（如 200、202）
   - 响应信息（状态描述，如 OK）
   - 响应头 / 请求头 / URL 样本等

2. **模式匹配规则**（前三种最常用）
   - **包括（Contains）**：响应内容里**包含**指定字符串即算通过。
   - **匹配（Matches）**：用正则表达式**完全匹配**。
   - **相等（Equals）**：与指定字符串**完全一致**。
   - 此外还有"字符串""否""或者"等，日常较少用。

### 实战一：按响应代码断言（校验 202）

把"要测试的响应字段"设为**响应代码**，匹配规则用"相等"，测试模式填 `202`，并写上自定义失败消息（如"响应的状态码有误"）。

运行后，本来正常返回 200 的接口会**全部失败**，展开任意一条能看到"响应断言"抛出的错误提示——因为它要求必须等于 202，而实际返回的是 200。这证明断言确实在按你定义的规则校验，而非只看 HTTP 状态。

> 注意：这里只是演示"如何自定义规则"。真实业务里，如果你的接口正常就是返回 200，就不该把期望改成 202，否则会把正确的接口判错。

### 实战二：按响应文本断言（校验内容包含）

把"要测试的响应字段"改为**响应文本**，匹配规则用"包括（Contains）"，测试模式填一段你期望返回的业务文本，例如课程接口返回的 `小滴低代码开发页面`。

运行后接口全部成功——因为响应体里确实包含了这段文本。如果某次响应缺失这段内容，断言就会失败，从而在海量并发中精准揪出异常请求。

### 断言使用的性能注意点

压测往往是高并发场景，而断言本身要消耗压测机 CPU。原则：

- **优先用简单断言**（响应断言 + 包括/相等），避免每个请求都跑**正则表达式匹配**（Matches），后者开销明显更大。
- 复杂正则断言会拖累压测机，导致测出来的吞吐量偏低、数据失真。

## 小结

- 结果树默认仅凭 HTTP 状态码 200 判成功，无法识别业务层"假成功"。
- 响应断言作用于单个取样器，可自定义"校验字段 + 匹配规则 + 期望模式"。
- 常用匹配规则：包括（Contains）、匹配（Matches）、相等（Equals）。
- 可校验响应代码（如 202）、响应文本（如包含某业务字段）等。
- 高并发下尽量用简单断言，少用正则，避免拖垮压测机。
