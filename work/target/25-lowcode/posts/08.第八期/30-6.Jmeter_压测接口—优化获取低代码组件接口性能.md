# Jmeter_压测接口—优化获取低代码组件接口性能

> **导语**：前面把「获取低代码组件」接口压测过一轮，这一集给它加上 Redis 缓存再压一次做对比。本文讲清缓存封装 `getCachedData` 的三个参数、命中与未命中两条路径、TTL 与强制刷新，以及回调里 `Promise.all` + `filter` 组装组件数据的逻辑，最后用 QPS 数据说明优化效果，并把这个公共方法推广到其它接口。注意：该缓存版本在最终仓库源码中处于注释状态，课堂演示后未合入主线，线上接口仍走无缓存版。

## 正文

### 先定基线，再谈优化

压测对比要公平，讲师的做法值得照抄：

- 每次跑之前**清空聚合报告**；
- **禁用其他取样器**，只留目标接口；
- 线程组设置固定的线程数（演示里是 4）；
- 分别请求「无缓存」和「有缓存」两版代码，对比 QPS。

对比结果：使用 Redis 缓存后 QPS 约 **428~440**，无缓存约 **410**，提升稳定但幅度不大——讲师也点明了原因：**样本只有 800 个**，量级太小，缓存优势还没完全拉开。这个诚实的说明比单纯报一个漂亮数字更有价值。

### 缓存入口：getCachedData 的三个参数

优化的核心是把「查数据库」包进一个带缓存的公共方法。接口里先定义一个 `cacheKey`，再调用 Redis 依赖的 `getCachedData`：

```ts
const data = await this.redis.getCachedData(
  cacheKey,                  // 1. 缓存键
  async () => {              // 2. 回源回调：Redis 没命中才执行
    return this.fetchComponentsFromDB();
  },
  { ttl: 60 * 10, force: false }  // 3. 选项：TTL 与是否强制刷新
);
```

- 参数一 `cacheKey`：在 Redis 里查找 / 储存数据的键；
- 参数二回调：真正去数据库取数据的逻辑。**Redis 里有缓存时直接跳过它**，没有才执行；
- 参数三 options：含 `TTL`（过期时间）与 `force`（强制刷新）。`force` 为 true 时置空 data 后回源重查并覆盖写回，用于主动失效缓存（并非显式 del）。

（方法名与字段以 课程配套代码（30-6） 下源码为准。）

### 方法内部：命中走捷径，未命中回源并回填

`getCachedData(key, fetchFunction, options)` 的逻辑分两支：

```ts
async getCachedData(key, fetchFunction, options) {
  let data = await this.get(key);
  if (options.force) {
    data = null;
  }
  if (!data) {
    data = await fetchFunction();            // 回源查库
    await this.redis.set(key, JSON.stringify(data), 'EX', options?.ttl ?? 3600)（ioredis 原生 set，非本模块三参封装）;  // 回填进 Redis
  }
  return data;                              // 命中则直接返回缓存
}
```

- **未命中**：执行传进来的 `fetchFunction`（从数据库查低代码组件），再用 Redis 的 `set` 把结果按 TTL 存进去；
- **命中**：直接返回 Redis 里的数据，就近获取，不再碰数据库。

这样一来，第一次请求稍慢（要回源并写缓存），后续大量请求都走内存，正是 QPS 提升的来源。

### 回源回调里做了什么

回调函数本身就有一段数据组装逻辑：

- 先判断有没有页面，没有就直接当无数据返回；
- 有页面则用 `Promise.all` 并发遍历执行每个异步方法，拿到各项 `components`；
- 用 `filter` 筛掉空值后作为最终的 `components`，并整理出对应的 id 数组；
- 去掉 components 之外，还能取出 TDK 等其它页面级数据。

这段逻辑和原来无缓存版本几乎一致——**优化只在外层套了一层缓存，没有改动业务查询本身**，这也是它值得推广的原因。

### 推广到其它接口与配套资料

`getCachedData` 是封装好的公共方法，**其它接口照样可以调用**来做 Redis 缓存，作为接口级私有缓存提升性能。本节只拿「获取低代码组件」做示范，其余接口可以按同一套路自行尝试。以最终仓库为准，该缓存入口当前仅以注释形式保留在 `low-code.service.ts` 中。

## 小结

- 压测对比要清空聚合报告、禁用其他取样器、固定线程数，保证口径一致。
- 有缓存 QPS 约 428~440、无缓存约 410；样本仅 800 个，提升有限但稳定。
- `getCachedData(cacheKey, callback, { ttl, force })`（课程示例 TTL 为 600 秒）：命中直接返回，未命中回源查库并 set 回填；force 为置空 data 后回源覆盖写回，并非显式 del。
- `force` 用于强制刷新（跳过缓存、回源覆盖写回，并非显式 del）；回调里用 `Promise.all` + `filter` 组装 components 与 id 数组。
- 该公共方法可复用到其它接口，优化不改业务查询本身。
