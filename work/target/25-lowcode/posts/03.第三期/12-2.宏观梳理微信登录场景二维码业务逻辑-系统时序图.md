# 宏观梳理微信登录场景二维码业务逻辑-系统时序图

> **导语**：本文用**时序图**从宏观上梳理 PC 端微信扫码登录的完整链路——从用户点击登录、后端对接微信服务器生成二维码与 ticket、用户扫码、到前端轮询拿到 token。理清对象、生命线、控制焦点与消息四个要素，后续代码开发将逐条对照实现。

## 前置知识

- 已阅读《微信登录的方式和微信公众号开发》，了解场景二维码登录形态。
- 无需画过 UML 时序图，本文会先解释基本概念。
- 了解 Redis 与 Node（NestJS）后端的基本概念即可。

## 正文

### 时序图的四要素

- **对象（Object）**：扮演角色，用大矩形表示。本系统有：客户端（前端）、Node 后端（NestJS）、微信服务器、Redis、MySQL。
- **生命线（Lifeline）**：对象下方的虚线，表示该对象存活/参与的时段。
- **控制焦点（Activation）**：虚线上的小矩形，表示某时间段内正在执行操作。
- **消息（Message）**：分为发送消息（实线箭头）、返回消息（响应）、自身处理消息（自调用）。

### 整体流程拆解

对应到微信扫码登录，核心步骤如下：

1. **用户点击登录**：前端触发，调用后端「获取二维码」接口。
2. **后端对接微信服务器（接入验证）**：需先在微信平台完成资质与回调配置，平台才允许你调用其 API。
3. **微信生成 ticket + 二维码地址**：后端拼接后返回给前端，前端用二维码插件展示图片，同时拿到 `ticket`。
4. **Node 后端把 ticket 存入 Redis**：value 为 `{ isScan: 'no' }`，过期时间约 120 秒。
5. **用户扫码**：微信服务器收到扫码事件，推送携带 `ticket`（第 3 步已生成）与用户 `openId` 的回调（微信用户的唯一标识，对应 `user` 表的 `openId` 字段）。
6. **微信回调后端接口**：把 `ticket` 与 `openId` 回传给我们配置的回调地址。
7. **后端处理回调**：查用户是否注册（按 `openId`）——没注册就插入一条并生成 token；已注册则直接查到用户生成 token。然后把 Redis 中该 ticket 的 `isScan` 改为 `'yes'`，并把 token 一起存入。
8. **前端轮询**：前端没有用 WebSocket，而是通过定时请求「轮询接口」，传回 `ticket` 查询 Redis 中 `isScan` 与 token。
9. **返回登录态**：若 `isScan === 'yes'`，轮询接口返回 token，前端完成登录；否则提示「等待用户扫码」。

### 为什么需要 isScan 与轮询

微信扫码后并不会主动推送给前端，因此用 Redis 中的 `isScan`（取值 `'no'`/`'yes'`）作为「是否已扫码」的中转状态。前端定时轮询该状态，拿到 `'yes'` 的同时取出后端已生成的 token，即可登录。`ticket` 在整个过程中充当前后端识别同一次扫码会话的 key。

## 小结

- 时序图四要素：对象、生命线、控制焦点、消息。
- 完整链路：点击登录 → 接入验证 → 微信生成 ticket/二维码 → 后端存 Redis(`isScan:'no'`) → 用户扫码 → 微信回调 → 后端查/建用户并签发 token、更新 `isScan:'yes'` → 前端轮询拿到 token。
- `ticket` 是识别一次扫码会话的 key；`openId` 是微信用户唯一标识，存入 `user.openId`。
- 前端用轮询而非 WebSocket 获取扫码状态。
