# React项目部署配置—Docker-compose文件上传至公共存储空间

> **导语**：在前端 React 编辑平台完成打包构建并上传 OSS 之后，整套自动化部署还差一个"总指挥"文件——`docker-compose.yml`。本文讲解如何把这个编排文件归档到云效公共存储空间，并理清它在"云效服务器 → 自有服务器"这条链路中的角色。

## 前置知识

- 已完成《React项目部署配置—打包构建》，前端代码已能构建出线上运行的 `dist`。
- 已完成《React项目部署配置—线上代码上传OSS配置》，构建产物已上传阿里云 OSS Bucket。
- 了解 `docker-compose.yml` 的作用，建议先读《项目部署上线—运行容器Docker-compose的介绍和使用》。

## 正文

### 为什么要把 docker-compose 文件单独上传

我们的低代码平台最终要在自己的服务器上同时跑起四个服务：后端服务、后端 Nginx、前端发布（Next.js）服务、前端发布 Nginx。这四个服务由一个 `docker-compose.yml` 统一编排。问题在于：流水线当前执行的机器是**云效的服务器**，而真正要起容器的机器是**我们自己的服务器**。

所以链路是：先在云效流水线里把 `docker-compose.yml` 暂存到"云效公共存储空间"，等后面的部署阶段再把它拉取到自己的服务器，最后在自己的服务器上执行 `docker compose up` 一把启动四个服务。先把文件"寄存"到一个公共空间，再搬回自己的服务器，是最省事的做法。

### 在流水线里添加"构建物上传"步骤

回到云效流水线编辑页，新增一个步骤，选择**构建物上传**：

- 步骤名称改为：`Docker-compose.yml文件上传`；
- 上传方式选择**归档至云效的公共存储空间，供后续任务拉取并部署**。

这一步和前面的"打包构建""OSS 上传"都属于构建阶段，会在云效服务器上先后执行完成。

### 制品名称（Artifact）的作用

"制品名称"相当于给上传的文件取一个**别名 / 标签**。比如我们给它起名叫 `docker-compose`。后续步骤要拿到这个文件时，凭这个制品名称即可从云效公共存储空间取回，而不用关心它的物理路径。打包路径直接填 `docker-compose.yml` 即可，因为该文件就放在仓库根目录。

### 整体链路回顾

- 云效服务器上依次执行：打包构建 → OSS 上传（前端静态资源）→ `docker-compose.yml` 上传（归档到公共存储空间）；
- 后续构建出的后端、前端镜像，会推送到**阿里云容器镜像服务 ACR（镜像仓库）**；
- 部署阶段把 `docker-compose.yml` 拉到自己的服务器，再从 ACR 拉取四个镜像，`docker compose up` 一键启动。

## 小结

1. `docker-compose.yml` 是启动四个服务的编排文件，需要先寄存到云效公共存储空间。
2. 通过"构建物上传"步骤归档文件，本质是把它做成可后续拉取的**制品**。
3. 区分两类存储：OSS 存前端静态资源；ACR 镜像仓库存后端 / 前端四个镜像。
4. 文件放在仓库根目录，打包路径直接填文件名即可。
5. 这一步只是"寄存"，真正执行启动要等部署阶段在自己的服务器上完成。
