# 跳槽面试官对技术选型的考察点

> **导语**：很多同学八股文没问题，一到项目经验就被问住：「你这个项目为什么选这个技术栈？有没有可替换方案？两者原理和性能有什么差异？」本文用两份真实简历描述，手把手教你如何把技术选型讲到面试官满意。

## 前置知识

建议先看《互联网大厂技术 Leader+高级前端技术组长之技术选型》，理解项目/团队/技术三维度选型标准。

## 正文

### 面试官在考什么

技术选型类问题考察的是：你是否真正做过选型决策。常见提问角度包括：

- 技术选择的依据（项目需求、团队技能、性能要求、可拓展性、安全性等）；
- 提供合理依据并解释决策过程；
- 技术兼容性、对后续开发/部署/维护的影响；
- 技术选型的可持续性（是否仍在维护，会不会项目跑着跑着技术栈就废了）。

光讲理论很虚，下面用两个简历案例拆解。

### 案例一：图形验证码 + 短信验证码 + Redis 原子性防重提交

简历描述：「负责图形和短信验证码模块，封装第三方短信运营商 SDK 发送短信，结合 Redis 实现原子性防重提交。」

**面试官可能的追问**：为什么做图形验证码？SDK 怎么封装的？为什么结合 Redis 做原子性防重提交？怎么实现的？

**参考回答思路**：

1. **需求背景**：项目要支持手机号注册登录，所以需要短信验证码。
2. **为什么选阿里云短信 SDK**：大厂商，稳定、安全、可维护性好。
3. **为什么要图形验证码**：短信套餐是要购买的，若被人为恶意或机器频繁刷接口会白白增加成本。图形验证码用来过滤非人为操作——此外还有滑动验证、点选「含路灯图片」等交互验证方式。再加 60 秒（或 120 秒）倒计时，进一步防刷。
4. **为什么用 Redis 做原子性防重提交**：短信验证码需写入 Redis，涉及「写入验证码」和「写入过期时间」两个操作。工程上应合成一条原子命令（`SET key value EX 60`）完成写入与过期设置，与 MySQL 事务一致性同理。若服务器崩溃导致只完成其中一个，就会出现数据不一致。用原子性操作保证存入 Redis 的验证码不受异常影响。

### 案例二：DevOps 自动构建 CI/CD 一键部署

简历描述：「负责 DevOps 自动构建 CI/CD 流水线，通过 Docker + Gitee + 阿里云 ECS 实现项目一键部署。」

**面试官可能的追问**：为什么用 Docker？为什么用 Gitee？为什么用阿里云？一键部署的好处？Docker 和源码安装有什么区别？为什么不用 GitHub？

**参考回答思路**：

1. **用 Gitee 做代码托管与一键上线**：避免 GitHub 的国内外网络问题（无「科学上网」时访问不稳，导致发布异常）；配合阿里云**云效**做自动化流水线。
2. **用 Docker 容器化部署**：一行命令即可拉起 Redis 等第三方应用；相比之下源码安装会有各种环境依赖问题，且切换版本极其繁琐——要重装一遍。
3. **选阿里云 ECS**：大厂服务器，稳定安全，且自带可视化监控面板。

### 给自己做模拟面试

准备面试时，针对简历里每一条亮点，先「反向提问」自己：面试官会怎么问？再输出一段准备好的回答。这样现场应对更流利。

## 小结

1. 选型面试题考的是「是否真做过决策」，不是背概念。
2. 回答要讲清：需求背景 → 为什么选它 → 对比替代方案 → 原理/性能差异。
3. 案例一关键是防短信盗刷（图形/滑动验证 + 倒计时）+ Redis 原子性保证两个写入操作一致。
4. 案例二关键是 Gitee 避 GitHub 网络问题、Docker 免环境烦恼、阿里云 ECS 稳定可监控。
5. 简历每条亮点都要能自圆其说，否则是减分项。
6. 准备面试 = 用面试官视角反向拷问自己的简历。
