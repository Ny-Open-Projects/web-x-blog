# TypeORM 框架：实现数据库改 + 删操作

> **导语**：上一节跑通了增和查，这一节补齐改和删。核心不在 API 名字，而在「条件」：同样的 `update` / `delete`，条件宽一点就会误伤多条数据。本文用「两条都叫老王、号码不同」的数据，对比原生 SQL 与 TypeORM 的写法，讲清两个参数各自的作用、affected 影响条数怎么读，以及为什么精确条件在生产里是底线。

## 正文

### 先看原生 SQL：没有条件会改一片

数据库里当前有两条数据，`name` 都是「老王」，只有 `phone` 不同。如果直接执行原生的 `update user set name = '老六'` 而不带 `where` 条件，一执行**两条都会变成老六**。这个演示直观说明：更新操作最需要小心的不是改成什么，而是「改哪些行」。

### update：条件 + 新字段

TypeORM 里把上一节的 `save` / `find` 换成 `update`，它接收**两个参数**：

- 第一个参数：查询条件，决定改哪条数据。
- 第二个参数：要更新的字段。

因为前面用原生 SQL 把两条都改成了「老六」，所以这里反过来，用精确条件把其中一条改回「老王」：

```ts
await this.userRepository.update(
  { name: '老六', form: '111' },
  { name: '老王' },
);
```

请求接口后返回「影响的条数为 1」，刷新数据库能看到只有 `phone` 为 `111` 的那条变成了老王，另一条保持不动。如果把 `phone` 这个条件去掉、只按 `name` 匹配，就会一次性把两条都更新掉——想批量更新时正是这么做的，差别全在条件宽窄。

### delete：同样靠条件控制范围

删除把方法换成 `delete`，条件对象的写法完全一致：

```ts
await this.userRepository.delete({ name: '老六', form: '111' });
```

只按 `name` 会一次删掉两条；加上 `phone` 精确条件就只删一条，affected 为 1。演示里有两处细节值得留意：前面的操作已经把数据都改成了老王，所以删除条件要跟着改成库里实际存在的值，否则删不到；另外一定**等项目启动成功再发请求**，启动未完成时请求会报错。

### 四个方法其实是一套 Repository API

`save`（增）、`find`（查）、`update`（改）、`delete`（删）都挂在同一个 `Repository` 上，条件对象里用到的 `name`、`phone` 就是实体里定义的列。把上一节和本节连起来，就是完整的 CRUD 基础：写法统一，区别只是方法与参数个数——`update` 需要「条件 + 新字段」两个参数，其余多为单个参数。

## 小结

- 原生 `update` 不带 `where` 会改掉全部匹配数据，条件范围是第一要务。
- `update(条件, 新字段)` 接收两个参数，`delete(条件)` 接收一个；两者都靠条件对象控制影响范围。
- 返回的 affected 影响条数可用来确认是否误改、误删；精确条件（如同时带 `name` 与 `phone`）只命中一条。
- 条件里的值要与库中实际数据一致，且等启动完成后再请求接口。
- `save` / `find` / `update` / `delete` 是同一套 `Repository` API，字段来自实体定义。
