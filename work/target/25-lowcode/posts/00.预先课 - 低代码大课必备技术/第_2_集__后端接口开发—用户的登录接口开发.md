# 后端接口开发—用户的登录接口开发

> **导语**：注册接口能签发 token 之后，登录接口要做的就是「验明正身再发牌」。这一集在 user 模块里新增 `POST /user/login`，讲清如何按用户名查库、如何把前端密码加密后与库里比对、以及校验通过后如何用 JwtService 签发 token。重点还包括一个容易忽略的安全细节：账号不存在和密码错误必须返回同一句提示。

## 正文

### 接口约定与代码清理

登录接口是 `POST http://localhost:3000/user/login`。因为要接收前端传来的用户名和密码，用 POST 而不是 GET。动手前先把脚手架生成的模板清干净：`user.controller.ts`、`user.service.ts` 里多余的 RESTful 练习方法、测试文件和暂时用不上的 DTO 都删掉，只留最小结构，避免干扰。

有一点和注册接口不同：**登录接口这里没有引入 DTO**。讲师明确说明本集不做参数校验，若实际项目里需要（比如限制用户名长度、密码格式），自行补一个 DTO 即可。这也提示了一个工程习惯——参数校验不是可有可无，只是本集为聚焦登录逻辑先省略。

### 控制器：新增 login 方法

在 `user.controller.ts` 里再复制出一个 POST 方法，路径改为 `login`，把请求体中的 `userName`、`password` 交给 Service 层处理：

```ts
@Post('login')
async login(@Body() body: { userName: string; password: string }) {
  return this.userService.login(body.userName, body.password);
}
```

（具体是用 `@Body()` 还是请求对象透传、字段命名以 `代码（已8期）/9-1/lowcode/packages/server` 下的源码为准；这里展示的是整理后的调用关系。）

### Service：三步校验，缺一不可

登录的核心逻辑在 `user.service.ts`，顺序非常关键：

1. **查用户**：按 `userName` 查库，确认账号注册过；
2. **验密码**：把前端传来的密码用「注册时同一个加密工具」加密，再与数据库里存的 `password` 比对；
3. **签 token**：两项都通过，才用 `JwtService.sign` 把查出来的用户 `id` 放进载荷签发 token。

```ts
async login(userName: string, password: string) {
  const findUser = await this.userRepository.findOne({ where: { userName } });
  if (!findUser) {
    throw new BadRequestException('账号或密码错误');
  }

  const isPasswordValid =
    this.secretTool.getSecret(password) === findUser.password;
  if (!isPasswordValid) {
    throw new BadRequestException('账号或密码错误');
  }

  const token = this.jwtService.sign({ id: findUser.id });
  return { token };
}
```

这里有两个值得记住的设计：

- **密码不能明文比**。库里存的是加密后的值，所以要把前端密码先过一遍同一个加密工具（工程里是 MD5 相关的 `SecretTool`，具体命名以源码为准），再比较，否则永远对不上。
- **提示语要统一**。账号不存在时不要写「用户不存在」，而是和「密码错误」一样返回「账号或密码错误」。否则接口等于在告诉调用方「哪个账号存在」，会被拿来枚举用户；统一提示后，没账号的人自然会去注册。

### 用 Apifox 验证三种情况

启动后在接口调试工具里按三组用例跑一遍：

- 先调注册接口建一个账号（例如 `大招 / 111`），注册成功会返回 token；
- 用同一组账号密码调 `/user/login`，登录成功，同样返回 token；
- 把密码改错、或把账号改错，都应返回「账号或密码错误」，而不是两种不同的报错。

第三步正是上一节「统一提示」的验收点。工程里的启动脚本见 `代码（已8期）/9-1/lowcode/package.json`（`run:server` 对应 `pnpm --filter server run start:dev`）。

### 和后续接口的关系

登录本身不复杂，但它产出的 token 是后面所有需要鉴权接口的「通行证」。紧接着的查询用户信息接口，就是拿这个 token 交给后端解密、取出 id 再查库。所以登录接口的载荷里放 `id`、而不放密码等敏感字段，是有意为之——token 会长期在前端和请求头里流转，放进去的东西必须尽量少、尽量不敏感。

## 小结

- 登录用 `POST /user/login`，接收 `userName` 与 `password`，交给 Service 处理。
- 校验顺序固定：先查账号是否存在，再比对加密后的密码，最后签发 token。
- 前端密码必须用注册时的同一加密工具处理后再与库里比对。
- 账号不存在与密码错误统一返回「账号或密码错误」，避免账号枚举。
- token 载荷只放必要的 `id`，不携带敏感信息，供后续鉴权接口使用。
