### 题 6.3.1：Redis 主从复制原理？哨兵怎么选主？

**【参考回答（可背）】**
复制：
1. **全量**：从库发 psync → 主库 bgsave RDB 传输 → 期间新写命令进 **replication buffer** → RDB 加载完补发 buffer；
2. **增量**：repl_backlog（环形缓冲区）+ offset，断线重连 offset 还在 backlog 内则部分重同步（psync 增量），否则退全量——**backlog 大小影响闪断恢复成本**（默认 1M，生产按"写入速率×容忍断线时长"调）；
3. 主从复制是**异步**的 → 存在丢失窗口（min-replicas-to-write 可缓解：至少 N 个从延迟 <M 秒才接受写）。

哨兵（Sentinel）：
- 三个定时任务：每 1s ping、每 2s 交换信息（__sentinel__:hello）、每 10s/1s（故障时）获取拓扑；
- 主观下线（单个 sentinel 认为）→ **客观下线**（quorum 个同意）→ 选举 leader sentinel（Raft 思想）→ 执行故障转移；
- **从库选主四步**：优先级 replica-priority → 复制 offset 最大（数据最全）→ runid 最小。

**【追问链】**
1. 哨兵数量？→ 至少 3 个奇数（防脑裂的多数派）；部署在与 Redis 不同故障域。
2. 脑裂（split brain）？→ 网络分区时旧主仍在接受写，恢复后这些写丢失；缓解 min-replicas-to-write=1。

**【P10 加分项】**
Cluster 与哨兵的选型：哨兵+主从适合"数据量小、扩展靠客户端分片"场景；Cluster（16384 slot、CRC16(key) mod、MOVED/ASK 重定向、gossip 协议）适合水平扩展与自动化——但**多 key 操作受限（hash tag）、运维复杂**。给出"何时不上 Cluster"的判断（数据量 <50G 哨兵足够）是加分信号。
