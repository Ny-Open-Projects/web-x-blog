### 题 6.3.2：热 key 与大 key 问题怎么治理？

**【参考回答（可背）】**
**热 key**（单 key QPS 极高打爆单分片）：
- 发现：客户端埋点统计、redis-cli --hotkeys（需 LFU）、监控 proxy 维度；
- 治理：① **本地缓存兜底**（热 key 推送到各应用本地 Caffeine）；② key 打散（加随机后缀分片成 N 个，读随机取一，写双写/广播）；③ 读写分离读扩展（接受秒级延迟）；④ 集群热分片问题：slot 迁移或专用副本组。
**大 key**（value 过大：string >10KB、集合元素 >5000 经验阈值）：
- 危害：慢查询阻塞单线程（删除 100 万元素的 set 阻塞秒级）、网络带宽打满、迁移卡顿、内存倾斜；
- 治理：拆分（hash 分桶：field 取模）、压缩（value gzip/snappy）、**异步删除 UNLINK**（后台线程释放，4.0+ lazy-free）、过期用 SCAN 分批删而不是 KEYS。
- 防复发：写入前代码层检查（尺寸门禁）、定期 --bigkeys/rdb 分析巡检。

**【P10 加分项】**
大促热 key 预案完整叙事：压测发现 top10 hot key → 推送本地缓存 + 接口限流 + 集群分片手工均衡 → 大促值班实时看板。**"热 key 是预测出来的，不是故障时发现的"**——预案文化是 P10 信号。
