### 题 6.2.4：Redis 分布式锁怎么实现？RedLock 有争议？

**【参考回答（可背）】**
**单实例正确姿势（必背）**：
```
SET lock_key unique_value NX PX 30000
```
- NX 互斥、PX 过期防死锁、**value 存唯一值（UUID+线程 ID）**用于安全释放；
- 释放用 **Lua 脚本**原子校验 value 再删（防删别人的锁）；
- 业务超时风险：锁过期但业务没执行完 → **看门狗**（Redisson watchdog：持锁线程定期续期，默认锁 30s 每 10s 续）。
- Redisson 实现：Lua + hash 结构（记录持有者与重入次数，支持可重入）+ Pub/Sub 唤醒等待者。

**RedLock 争议（P10 必聊）**：向 N 个独立主节点依次加锁，多数派成功才算获取。Martin Kleppmann 批评：GC 停顿/时钟跳变下锁语义失效，且没解决 fencing token（令牌递增校验）；antirez 反驳依赖时钟单调与正确实现。**工程结论：RedLock 复杂且未达真正共识，要么接受单实例+看门狗的"效率锁"语义，要么用支持 fencing 的方案（ZK 顺序节点/etcd lease + 版本校验）。关键资源（资金）不依赖"效率锁"，用 DB 乐观锁兜底。**

**【追问链】**
1. 锁与 DB 的关系？→ 分布式锁是**效率优化**（防重复计算）不是**正确性保证**（fencing 缺失）；正确性始终应当由存储层的原子条件更新兜底。
2. 主从切换锁丢失？→ 主节点加锁未同步到从就宕机，新主没有锁 → 双持有。这是 RedLock 试图解决又没彻底解决的问题。

**【P10 加分项】**
给出锁选型矩阵：效率锁（缓存重建）用 Redisson；正确性锁（扣库存）用 DB 乐观锁/原子操作；协调锁（选主）用 ZK/etcd。**"锁的正确性分级"是面试官想听的架构判断。**
