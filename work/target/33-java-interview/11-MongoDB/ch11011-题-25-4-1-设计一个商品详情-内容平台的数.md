### 题 25.4.1：设计一个商品详情/内容平台的数据架构（混合存储）

**【参考回答（框架可背）】**
1. **存储分工**：账务/库存 MySQL（强事务）；商品详情 MongoDB（schema 多变：不同类目不同属性结构，嵌入整体读）；搜索 ES；缓存 Redis 多级。
2. **商品建模**：主文档 = 基础字段 + `attributes` 嵌套数组（类目异构属性）+ `skus` 嵌套（SKU 数量有限）；评价/浏览历史引用拆集合（1:多且独立增长，避免 16MB 与无限嵌入）；热点字段**冗余**进主文档（如类目名，免 $lookup）。
3. **一致性**：MySQL 库存扣减（强事务）与 MongoDB 商品状态通过**领域事件/CDC** 同步（最终一致）；对账兜底。
4. **索引**：ESR——`{categoryId: 1, status: 1, updatedAt: -1}`；TTL 索引清理过期秒杀缓存文档；partial 索引只索引"上架"商品。
5. **规模演进**：商品集合按 categoryId 分片（查询必带类目）或 hashed productId（写均匀）；预估迁移路径先于数据量到达。
6. **Java 集成**：Spring Data MongoDB——MongoRepository 简单 CRUD，**复杂聚合用 MongoTemplate**（更显式可控）；连接池（maxConnectionPoolSize 与服务实例数联动）；事务走 @Transactional（副本集即可用）。

**【追问链】** 16MB 文档上限会撞吗？→ 评价/日志独立集合；大字段（图文）拆 GridFS 或对象存储存 URL。聚合管道性能？→ $match 前置走索引、$lookup 是性能黑洞（能冗余就冗余）、$facet 注意内存限制（allowDiskUse）。

**【P10 加分项】** 混合架构的真相："我们最终没有'替换 MySQL'，而是**按数据特征分工**——账务留 MySQL，商品与内容迁 MongoDB，搜索走 ES。中间的同步层（CDC）才是整个架构最脆弱也最值得投入的地方。"——混合架构最难的不是单库选型而是边界与同步。
