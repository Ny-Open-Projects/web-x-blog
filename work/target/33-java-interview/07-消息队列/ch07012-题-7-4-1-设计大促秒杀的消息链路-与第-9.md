### 题 7.4.1：设计大促秒杀的消息链路（与第 9 章联动）

**【参考回答（框架可背）】**
1. **前置过滤**：静态资源 CDN、按钮防重、风控限流（网关层把 100 万 QPS 压到 1 万）；
2. **库存预扣**：Redis lua 原子扣减（防超卖），扣成功才进 MQ——**MQ 不是第一道闸，Redis 才是**；
3. **异步下单**：下单消息进 RocketMQ（削峰），消费端按 DB 能力拉取（消费者限速），DB 行锁扣真实库存 + 创建订单同事务；
4. **失败闭环**：消费失败重试 → 死信 → 自动回补 Redis 库存（**回补幂等：以订单维度记录已回补标记**）；
5. **用户体验**：排队中状态轮询（前端轮询订单状态接口，结果落 Redis）；
6. **兜底**：MQ 积压监控、Redis 预扣与 DB 实扣差异对账、活动结束二次对账。
量化示例：10 万库存、100 万请求 → Redis 扛 100 万 QPS → MQ 消费速率设为 DB 可承受的 5000 TPS → 20 秒内售罄。

**【追问链】**
1. Redis 预扣和 DB 实扣不一致怎么办？→ 以 DB 为准做对账；预扣是"资格闸门"不是账本，差异通过回补与对账收敛。
2. 为什么不用 DB 直接扛？→ 行锁串行化，100 万并发扣同一行 = 连接池爆炸与锁等待雪崩；MQ 把"并发扣减"转成"排队扣减"。

**【P10 加分项】**
"削峰的度"：削峰不是无限延迟——用户等待超过 30s 就流失，所以**限速值 = 业务可接受的最大售罄时间**推导而来。把技术参数翻译成业务指标（售罄时间、转化率），是 P10 的语言。
