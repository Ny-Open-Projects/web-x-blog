### 题 8.2.3：Nacos/Eureka/ZooKeeper 作为注册中心的区别？服务发现选什么？

**【参考回答（可背）】**
- **ZooKeeper**：CP。选主/分区时不可用——服务发现场景反而致命（宁可给旧列表也别没列表）；会话依赖心跳，网络抖动误摘除。
- **Eureka**：AP。自我保护机制（心跳丢失比例高时暂停摘除），返回可能过期的列表；已进维护模式。
- **Nacos**：AP/CP 双模——临时实例（默认，Distro 协议，AP，心跳续约）与持久实例（Raft，CP）；配置中心一体，国内主流。
- 工程结论：**服务发现选 AP**（可用性 > 短暂不一致，客户端可做失败转移兜底）；**选主/元数据协调选 CP**（ZK/etcd）。一个系统两个都要：服务发现 Nacos AP + 分布式锁 etcd。

**【追问链】**
1. 客户端怎么做故障容错？→ 本地缓存服务列表（注册中心挂了也能跑）、负载均衡重试、熔断。**"客户端韧性"是服务发现真相：注册中心挂掉不该立刻影响线上流量。**
2. 推 vs 拉发现？→ 拉（轮询，简单有延迟）vs 推（长连接推送，实时）vs Nacos 混合（UDP 推 + 定时拉兜底）。

**【P10 加分项】**
服务网格视角：Istio 把服务发现/流量治理下沉 Sidecar，Java SDK 退化为纯业务——成本是 Sidecar 资源与运维复杂度；判断："规模不大时 Spring Cloud + Nacos 性价比更高，Mesh 适合多语言异构团队与规模化平台团队。"
