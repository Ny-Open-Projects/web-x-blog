### 题 8.2.2：分布式事务方案全景对比？

**【参考回答（必背对比矩阵）】**
| 方案 | 一致性 | 性能 | 侵入性 | 适用 |
|------|--------|------|--------|------|
| 2PC/XA | 强 | 低（同步阻塞、协调者单点） | 低（JTA） | 传统数据库间短事务，互联网少用 |
| TCC | 强（业务级） | 中（资源预留） | **高**（Try/Confirm/Cancel 三接口） | 资金类核心链路 |
| SAGA | 最终 | 高 | 中（每步要补偿） | 长流程、跨多服务（下单→扣库存→物流） |
| 本地消息表 | 最终 | 高 | 中（一张表+扫描） | 快速落地、依赖本地事务 |
| 事务消息 | 最终 | 高 | 中 | RocketMQ 生态 |
| 最大努力通知 | 弱 | 高 | 低 | 通知类（支付结果通知外部商户） |

**选型心法（背）**：
1. **能不用就不用**：拆服务时按"事务边界"聚合（能一个库解决不拆）；
2. 资金强一致 → TCC（Try 预留资源，Confirm/Cancel 补偿，要处理空回滚/悬挂/幂等三大坑）；
3. 一般业务 → SAGA/消息最终一致；
4. 2PC 在互联网规模基本不用（阻塞+协调者故障放大）。

**【追问链】**
1. TCC 三大坑怎么防？→ **空回滚**（Try 没到 Cancel 先到：Cancel 检查有无 Try 记录，无则记空回滚标记）；**悬挂**（Cancel 后 Try 才到：Try 检查回滚标记直接拒绝）；**幂等**（Confirm/Cancel 可能重试多次，以事务 ID 去重）。
2. SAGA 补偿失败怎么办？→ 补偿也要重试+人工兜底；设计时让每步补偿"可成功"（预留/标记代替真扣）。

**【P10 加分项】**
"不引入分布式事务"的架构手段清单：业务聚合（订单+流水同库）、状态机 + 异步补偿、对账兜底、用户补偿交互（可撤销的体验设计）。**最好的分布式事务是设计掉它**——这句话必须有案例支撑（举一个自己拆事务的真实设计）。
