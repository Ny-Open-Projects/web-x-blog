# 1-4 准备工作：百度地图API秘钥(AK)

## 【学习目标】

- 独立完成百度地图开放平台的应用创建与 AK 申请；
- 理解应用类型、启用服务、请求校验方式三个选项的含义与选型；
- 建立「调试全放行、上线收敛白名单」的凭证安全习惯。

## 【正文】

### 1. AK 是什么，课程为什么需要它

百度地图的 API 在后面的项目中会被直接调用，课程第 11 章「路线制定专员 Agent 挂载百度地图 MCP」中，地图能力正是由百度地图开放平台提供的：地理编码、路线规划、天气查询这些工具，最终都落到对百度地图 API 的调用上。调用之前，需要到百度地图开放平台申请一个 API Key，缩写就是 AK。

放在课程架构里看，该 AK 的流转路径是：百度地图开放平台（申请）→ MCP 服务端（持有并调用）→ 路线制定专员 Agent（挂载 MCP 工具）→ 主管 Agent（经 A2A 调度成员）→ 用户。凭证在链路的最底层，却影响着最上层的输出质量，地图数据不准，路线规划就离谱，用户拿到的行程建议也就失去意义。准备篇把这些底层凭证备齐，后面的框架学习才能心无旁骛。

```mermaid
flowchart LR
    A["百度地图开放平台<br/>申请 AK"] --> B["MCP 服务端<br/>持有并调用"]
    B --> C["路线制定专员 Agent<br/>挂载 MCP 工具"]
    C --> D["主管 Agent<br/>经 A2A 调度成员"]
    D --> E["用户"]
```

AK 是应用调用百度地图 API 的身份凭证：请求里带上它，平台才能识别调用方、按应用统计用量与配额。可以把它理解成「应用级别的账号」，同一个账号下可以建多个应用，每个应用一份 AK，额度与校验策略按应用隔离，互不影响。

地图能力在旅游规划链路里的位置，也值得先建立全景：用户给出目的地后，Agent 先把地址文本转成坐标（地理编码），再基于坐标算两点间的通行方案（路线规划），同时把目的地天气纳入行程建议（天气查询）。三类能力串起来，才是第 11 章路线制定专员的完整工具箱；它们的输入输出形态，第 5 节有明细表。

### 2. 创建应用

进入百度地图开发平台的控制台 `https://lbs.baidu.com/apiconsole/center`，登录后打开「应用管理」里的「我的应用」，点击「创建应用」。创建应用时有几个选项需要注意。

**应用名称**：可以随便填写自己的应用名称，仅用于控制台展示与区分，不影响调用。建议起个能认出用途的名字，例如带上课程名，方便日后配额告警时知道是哪个应用在报。

**应用类型**：这里选择「服务端」即可。选型依据是调用发生的场所：课程里调用百度地图 API 的是服务端进程，MCP 服务端在服务器上发起请求，而不是浏览器里的页面。浏览器端页面调用地图 JavaScript API 属于另一类凭证，二者不通用，详见第 4 节的公告解读。

**应用所启用的服务**：也就是该 AK 能够使用哪些 API。服务分为基础 API 与高级 API 两种类型：基础 API 全选即可；而高级 API 如果是以个人身份申请的开放平台账号，基本上申请不下来，只有企业级账号才能申请，申请不了就不用管它。课程用到的地理编码、路线规划、天气查询都在基础 API 的覆盖范围内，全选基础 API 已经够用。反过来说，启用列表里没有勾选的服务，AK 是调不动的，排障时这是一个容易漏查的点。

**请求校验方式**：这是比较关键的一项，这里选择「白名单」，也就是只有列入白名单的 IP 地址才能调用该 API。

几项都确认之后点击提交，就会生成应用及其对应的 API Key，后续课程中调用百度地图 API 时直接使用该 API Key 即可。生成后的 Key 同样建议当场复制保存。

提交之后还有两件小事值得做：一是回到「我的应用」列表，确认新应用已经在列、AK 完整可见，列表页是后续管理（改白名单、看配额、轮换 Key）的入口，现在认个门；二是看一眼应用详情页的配额信息，了解日调用量与并发上限的量级，做到心里有数。很多排障时间，花的就是「当初没看这两眼」。

### 3. 白名单机制讲透

白名单是百度地图对 AK 的一道调用方身份校验：服务端收到带 AK 的请求时，会检查请求来源 IP 是否落在该 AK 的白名单内，不在则拒绝调用。它把「凭证」与「调用方地址」绑定在一起，AK 被拷贝到别处也无法使用。

通常开发环境下调用方只有我们自己的服务器 IP，而课程阶段只是做测试，所以白名单直接设置为 `0.0.0.0/0`，表示任何 IP 地址都能调用该 API。平台下方也给出了说明：如果不想对调用 IP 做任何限制，就设置为全放行的值。这里的 `0.0.0.0/0` 是 CIDR 写法，斜杠后的 0 表示前缀长度为 0，即覆盖全部 IPv4 地址空间。

两个细节必须注意：

- **格式**：白名单的格式是英文半角逗号分隔的条目，每条可以是一个具体 IP，也可以是一个 CIDR 网段，例如 `202.198.16.3,202.0.0.0/8`。写成中文逗号、或者条目间加了空格，都可能导致解析失败；
- **边界**：`0.0.0.0/0` 仅适用于调试，上线时必须设置合理的 IP 白名单。全放行意味着任何人拿到该 AK 都能调用，消耗的是你的配额，调试期图方便可以放行，上线前务必收敛。

举个填写演算：假设开发机出口 IP 是 `202.198.16.3`，测试服务器在 `202.0.0.0/8` 网段，调试阶段的白名单可以写 `202.198.16.3,202.0.0.0/8`，两台机器都能调，其余地址被挡在外面。如果只知道服务器在某个云厂商的网段，向运维确认出口 IP 或网段后再填，比先填 `0.0.0.0/0` 再想起来收要安全。

### 4. 平台公告解读：服务端 AK 与浏览器端 AK

平台上有一条系统公告：系统升级后「服务端 AK」不再支持浏览器端使用，JavaScript API 只支持浏览器端 AK，旧的「服务端 AK」仍可使用，但更新之后将不再支持浏览器场景。

解读：百度地图把 AK 按使用场景拆成了两类，服务端 AK 供服务器进程调用（本课程的选择），浏览器端 AK 供网页 JavaScript API 使用。这次升级强化了二者的边界：拿着服务端 AK 到浏览器里调 JavaScript API 将不被支持。

为什么要分？因为两类场景的暴露面完全不同：服务端 AK 藏在服务器里，泄露面小；浏览器端 AK 会随页面下发到用户浏览器，任何人都能查看，因此通常按 referer 白名单做校验，容忍度与策略都不同。把两类凭证混用，等于把服务端的额度暴露给浏览器场景的校验体系，所以平台选择收紧边界。对本课程没有影响：调用发生在服务端，选「服务端」类型、配白名单校验即可。反过来，若误选成浏览器端类型，则与服务端调用场景不匹配，排障时应首先回到这里检查。

公告里还提到「旧的服务端 AK 仍可使用」，这意味着已经申请过的 Key 不会因为升级立即失效，但新接入的代码不应再依赖服务端 AK 的浏览器能力。课程作为新接入方，按新规则选型即可，不必为兼容旧行为做任何事。

### 5. 与课程工程的对应

课程配套工程 981-demo 对地图能力做了离线复刻：`src/main/java/com/travel/agent/tool/RouteMakingTools.java` 中的 `map_geocode`（地理编码）、`map_directions`（路线规划）、`map_weather`（天气查询）三个工具，对应百度地图 MCP 暴露的工具形态；离线演示用本地桩返回同构数据，不填真实 AK 也能把「工具挂载 → 工具调用 → 结果回传」的链路跑通。真实环境下这些工具由百度地图 MCP 服务端提供，此时 AK 才是必需凭证，先本地跑通形态，再接真实凭证，是课程工程一贯的节奏。

三个工具的职责与输入输出值得先认个脸熟，第 11 章还会详细展开：

| 工具 | 职责 | 典型输入 | 输出形态 |
|---|---|---|---|
| map_geocode | 地理编码：地址转坐标 | 地址文本，如「杭州西湖」 | 经纬度坐标及精度信息 |
| map_directions | 路线规划：两点通行方案 | 起点、终点 | 距离、耗时、路线摘要、费用估算 |
| map_weather | 天气查询：目的地天气 | 城市名 | 未来若干天的天气预报 |

可以看到，地图能力对 Agent 而言就是一组结构化工具：输入文本或坐标，输出 JSON。Agent 在 ReAct 循环中按需调用，把结果作为观察纳入下一步推理，这也是 MCP 工具挂载的基本形态。

离线桩与真实凭证的分工，反映的是课程工程「先形态、后真实」的组织思路：`RouteMakingTools` 里的三个工具用固定规则生成同构 JSON，参数与字段跟真实 MCP 返回对齐，因此链路上「工具怎么挂、怎么调、结果怎么回传」与生产一致；差别只在数据来源，一个是本地规则，一个是百度地图的真实服务。这种分层让第 11 章的挂载逻辑可以在无 Key、无网络的环境下开发调试，把接入真实凭证的时刻推迟到验证完形态之后，风险小得多。

从 Agent 侧看，工具挂载的代码形态也是一致的：无论是本地桩工具还是 MCP 客户端工具，都是先注册进工具箱，再把工具箱挂到智能体上。课程工程中 `TeamMembers` 给路线制定专员注册地图工具、给景点推荐成员注册景点工具，用的都是同一套挂载动作，工具来源可以替换，挂载逻辑不变，这正是「工具标准化」想达到的效果：换工具不改架构。

### 6. 常见坑

1. **调试期全放行忘回收**：`0.0.0.0/0` 方便了本地测试，但上线前不收敛就等于把 Key 公开，配额会被无谓消耗；
2. **高级 API 执念**：个人账号申请高级 API 基本无果，课程用到的基础 API 已覆盖地理编码、路线规划、天气查询，不必纠结；
3. **IP 变动**：家用宽带与云服务器的出口 IP 可能变动，IP 一变调用就被拒绝，表现为「昨天还好好的今天全失败」，先查白名单，再查配额；
4. **应用类型选错**：课程调用发生在服务端，误选浏览器端类型会导致校验方式与调用场景都不匹配；
5. **分隔符用中文逗号**：白名单条目必须是英文半角逗号分隔，从文档里复制示例时尤其注意这一点；
6. **服务没勾全**：启用列表漏勾的服务调不动，报错信息却不一定直白，按「应用类型 → 启用服务 → 白名单 → 配额」的顺序逐项查更高效；
7. **配额被打满**：免费额度有日限与并发上限，批量回归时容易触顶。先在控制台看用量曲线，确认是配额问题再申请提额或错峰调用；
8. **把 AK 提交进仓库**：与 1-3 篇的模型 Key 同理，AK 同样属于环境变量。它是配额载体，泄露后别人刷的是你的量；
9. **拿服务端 AK 去浏览器场景试**：平台公告已明确服务端 AK 不支持浏览器端使用，拿错类型的 AK 做实验，只会得到「明明有 Key 却调不通」的困惑。选型先看调用发生在哪，这是本节最值得带走的一句话。

## 【易错点 / 面试题】

1. **面试题：为什么调试时白名单设 `0.0.0.0/0`，上线却不行？**
   答：白名单的作用是把 AK 绑定到可信调用方 IP。`0.0.0.0/0` 放弃了这道校验，任何拿到 AK 的人都能调用，消耗额度且可能被恶意刷量。调试期图方便可以全放行，上线必须收敛为服务器出口 IP，这是凭证安全的基本纪律。

2. **面试题：服务端 AK 和浏览器端 AK 的区别？**
   答：按调用场景划分：服务端 AK 供服务器进程调用 API，配合 IP 白名单校验；浏览器端 AK 供网页 JavaScript API 使用。二者不通用，平台升级后服务端 AK 已不支持浏览器端使用。选型时先看「调用发生在哪」，服务端进程就选服务端 AK。

3. **面试题：AK 校验有哪几种常见方式，各适合什么场景？**
   答：课程用到的是 IP 白名单，把调用方 IP 收敛到可信范围，适合服务端场景：出口 IP 固定、校验简单。此外浏览器端场景常用 referer 白名单（限制来源域名），对安全性要求高的场景还会用 AK + SK 签名校验。选型看调用场景与暴露面，没有一概而论的最优解。

4. **易错点：认为 AK 只是「一个字符串」，随便填在哪都行。**
   AK 是配额与计费的载体：填错应用、超配额调用、白名单失效，都会直接表现为接口不可用。排障时按「应用类型 → 启用服务 → 白名单 → 配额」的顺序检查，比盲目重填更高效。

## 【小结】

本节完成了第三项准备工作：在百度地图开放平台创建应用、申请 AK，并讲透了应用类型、启用服务、白名单三个选项的含义，核心习惯是「调试全放行、上线收敛白名单」。回顾申请全流程：登录控制台 → 应用管理 → 我的应用 → 创建应用 → 填名称、选服务端类型、勾选基础 API、配白名单 → 提交 → 复制 AK。步骤不多，但每一步的选项都与后续调用行为直接相关，填错了不会立刻报错，只会在某个调用场景下莫名失败，这正是准备篇值得慢下来的原因。该 AK 是第 11 章百度地图 MCP 的直接输入；配套工程 981-demo 用 `tool/RouteMakingTools.java` 对其做了离线复刻，没有 AK 也能先跑通链路形态。下一篇安装 Nacos 3，它是 A2A 通信的服务注册发现基础。
