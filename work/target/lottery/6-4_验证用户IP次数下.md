# Go 企业级抽奖项目: 验证用户IP今日参与次数（下）

## 纲要

- 本篇聚焦 **IP 维度**的今日参与次数，与用户维度目的相同，但实现侧重点不同。
- 同一 IP 下可能挂大量客户端（公司、学校、网吧），请求更密集，因此**直接用 Redis 缓存做原子递增**，不落数据库。
- 为避免单个大 hash 热点，用"散列分桶"把 IP 均摊到多个 key：`day_ips_<i>`，其中 `i = ip % ipFrameSize`。
- 递增用 Redis 的 `HINCRBY`，field 为 IP 的整型值，value 为当天次数。
- 跨天需要清零：服务启动时立即清一次，并借助 `time.AfterFunc` 在"下一个零点"定时重置，每天凌晨循环执行。
- 校验阈值：`conf.IpLimitMax`（默认 300000）超过即拒绝；`conf.IpPrizeMax`（默认 30000）超过则触发"疑似黑名单"。

## 为什么 IP 维度走缓存

用户维度我们用 MySQL 表 `lt_userday` 持久化；但 IP 维度请求量可能大得多，且只为做"今日次数"限制，没必要每次都打数据库。所以 IP 计数直接放在 Redis，用 `HINCRBY` 原子递增，性能更好。这个"放缓存"的优化思路，在后续 Redis 专项优化章节会反复出现。

## 散列分桶（避免单 key 热点）

把所有 IP 的次数都堆在一个 Redis key 里，会让这个 key 成为热点且体积膨胀。工程用 `ipFrameSize`（默认 2）做分桶：

- 把字符串 IP 转成整型 `ip`（`comm.Ip4toInt`）。
- 桶号 `i = ip % ipFrameSize`。
- 每个桶一个 hash key：`day_ips_<i>`，field 是 IP 整型，value 是当天次数。

```go
package utils

import (
	"fmt"
	"log"
	"math"
	"time"

	"imooc.com/lottery/comm"
	"imooc.com/lottery/datasource"
)

const ipFrameSize = 2

func init() {
	// 本地开发测试时，每次启动先把统计数归零
	resetGroupIpList()
}

// 重置单机 / 集群 IP 今天次数
func resetGroupIpList() {
	log.Println("ip_day_lucky.resetGroupIpList start")
	cacheObj := datasource.InstanceCache()
	for i := 0; i < ipFrameSize; i++ {
		key := fmt.Sprintf("day_ips_%d", i)
		cacheObj.Do("DEL", key)
	}
	log.Println("ip_day_lucky.resetGroupIpList stop")
	// 设定在下一个零点再次重置
	duration := comm.NextDayDuration()
	time.AfterFunc(duration, resetGroupIpList)
}

// 今天的IP抽奖次数递增，返回递增后的数值
func IncrIpLuckyNum(strIp string) int64 {
	ip := comm.Ip4toInt(strIp)
	i := ip % ipFrameSize
	return incrServIpLucyNum(i, ip)
}

func incrServIpLucyNum(i, ip int64) int64 {
	key := fmt.Sprintf("day_ips_%d", i)
	cacheObj := datasource.InstanceCache()
	rs, err := cacheObj.Do("HINCRBY", key, ip, 1)
	if err != nil {
		log.Println("ip_day_lucky redis HINCRBY err=", err)
		return math.MaxInt32
	}
	return rs.(int64)
}
```

## 零点定时重置

缓存在当天是不断累加的，跨天必须清零。`resetGroupIpList` 做了两件事：

1. 立即 `DEL` 掉所有 `day_ips_<i>` 桶，重新从 0 计。
2. 用 `comm.NextDayDuration()` 算出"距离下一个零点还有多久"，交给 `time.AfterFunc` 在那一刻再次调用自己，从而形成**每天凌晨自动重置**的循环。

> 之所以"启动时也清一次"，是因为本地测试服务并不总是常驻，手动清零能保证测试数据干净。

## 在抽奖主流程中的校验

回到 `luckyDo`，IP 次数递增后做两级判断（`web/controllers/index_lucky_api.go`）：

```go
// 步骤4：验证IP今日的参与次数
ipDayNum := utils.IncrIpLuckyNum(ip)
if ipDayNum > conf.IpLimitMax {
	return 104, "相同IP参与次数太多，明天再来参与吧", nil
}

// limitBlack：IP次数超过 IpPrizeMax，则视为疑似黑名单（详见 6-5）
limitBlack := false
if ipDayNum > conf.IpPrizeMax {
	limitBlack = true
}
```

阈值含义：

- `IpLimitMax`（300000）：硬上限，超过直接拒绝参与。
- `IpPrizeMax`（30000）：软阈值，超过不直接拒绝，但把 `limitBlack` 置位，后续匹配奖品时会限制其只能中"非实物大奖"（见 6-5、6-6）。

## 用户维度缓存计数同源

用户今日次数也用同样思路（`web/utils/user_day_lucky.go`）：`IncrUserLuckyNum(uid)` 用 `day_users_<i>`（`i = uid % userFrameSize`）做 `HINCRBY`，同样在 `init` 里启动即清零 + 零点定时重置。`checkUserday` 在上限判断时通过 `utils.InitUserLuckyNum` 把数据库准确值同步回缓存，避免两边不一致。
