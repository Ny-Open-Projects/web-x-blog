# Go 企业级抽奖项目: 摇一摇越界 Bug 修复与压测

## 纲要

- 动态券 `datalist` 越界 Bug：剩余数与切片长度不一致导致取下一张券时越界
- 两种修复：补齐 `DataList` 数据，或在取券前校验长度
- 用 `wrk` 做压测：线程数、连接数、持续时间三参数
- 压测暴露"超发"（线程不安全），加互斥锁后精确控量

## 越界 Bug 定位

在微信摇一摇的发奖实现中，动态券（`sendCouponDiff`）需要从 `DataList` 切片里按剩余数取下一张券编码。问题出现在配置阶段：某个动态券把 `Total` 和 `Left` 设成了 50，但 `DataList` 里实际只放了 5 张券的编码。当剩余数递减后，用 `g.Left` 作为下标去 `DataList` 取券时，下标超过了切片长度，于是抛出了数组越界错误。

## 两种修复方案

- **方案一（数据一致）**：把 `DataList` 填充到与 `Left` 等长（要 50 张就填 50 个编码），从源头保证长度一致，自然不会越界。
- **方案二（代码校验）**：在取券前加一道校验——若 `len(g.DataList) < g.Left`，直接 `return false` 表示发奖失败。双重校验更稳妥，即便配置出错也不会让服务崩溃。

推荐两者结合：既保证数据合理，又在代码层兜底。

修复后的安全取券逻辑（即上一节 `sendCouponDiff` 中已采用的写法）：

```go
func sendCouponDiff(g *Gift) (bool, string) {
	// 关键校验：剩余数不能超过切片长度，否则取下一张编码会越界
	if g.Left > 0 && len(g.DataList) >= g.Left {
		g.Left--
		return true, g.DataList[g.Left]
	}
	return false, "奖品已发完"
}
```

## 压测暴露超发

修复越界后，还需验证并发安全性。这里使用独立的压测工具 `wrk`，常用三个参数：

- `thread`：压测线程数
- `connection`：连接数
- `duration`：持续时间

为了排除干扰，把其它奖品状态置为不可用，仅保留手机大奖且中奖概率设为 100%、库存 20000。若程序线程安全，压测结束后日志里的手机中奖记录应当恰好 20000 行。

实测结果却是 **20094 行**——多出 94 部手机。这就是典型的**超发**：多个并发请求同时读到 `Left > 0`，各自扣减后都判定"还有库存"，最终发出数量超过了真实库存。在摇一摇这类系统里，超发是严重事故（程序员替公司买单）。

## 互斥锁修复超发

修复方法与年会抽奖一致：在共享变量 `giftList` 被读写的临界区加互斥锁。具体到抽奖接口 `GetLucky`，一进入就 `mu.Lock()`，退出前 `mu.Unlock()`：

```go
func (c *lotteryController) GetLucky() map[string]interface{} {
	code := luckyCode()
	result := map[string]interface{}{"success": true, "message": "ok"}
	mu.Lock()         // 进入临界区加锁
	defer mu.Unlock() // 退出解锁
	for i := range giftList {
		g := &giftList[i]
		if !g.Useful || (g.Total > 0 && g.Left <= 0) {
			continue
		}
		if code >= g.RateMin && code < g.RateMax {
			ok, sendData := sendGift(g)
			if ok {
				result["gift_id"] = g.Id
				result["gift_name"] = g.Name
				result["send_data"] = sendData
				saveLuckyData(code, g, sendData)
			}
			break
		}
	}
	return result
}
```

加锁后再次压测，日志精确为 20000 行，不多不少；多次运行均稳定。

## 性能观察

压测时接口吞吐量约在 1 万 QPS 左右。尝试把奖品数量从 20000 降到 200、再降到 2，吞吐量变化并不明显——说明主要开销集中在抽奖逻辑本身以及 HTTP 请求处理上，而非库存规模。

技术点总结：

- 数组越界往往源于"配置数量"与"数据长度"不一致，代码层校验是必要的兜底。
- `wrk` 是验证接口性能与并发安全的利器，三参数即可覆盖核心压测场景。
- 超发是库存类抽奖的致命问题，互斥锁（`sync.Mutex`）是最简且有效的防护手段。
- 后续活动还会引入除互斥锁外的其它并发方案并做性能对比。
