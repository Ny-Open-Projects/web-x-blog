# Go 企业级抽奖项目: 六种抽奖活动总结

## 纲要

- 六种抽奖活动的共性：不同奖品类型、奖品数量可能无限量也可能有限量、需合理设置中奖概率、不同奖品有不同发奖规则。
- 抽奖系统最大的技术挑战是并发安全性问题，六种活动分别实践了互斥锁、队列、原子递减三类解法。
- 系统优化核心思路：当数据集合很大且需保证并发安全时，用散列把单个大集合拆成多个小集合，可极大降低冲突、提升性能。
- 更完整、更全面的抽奖系统将在后续章节以完整项目形态设计、开发与完善。

## 活动关键要素回顾

无论哪种抽奖形式，都离不开以下关键点：

- **奖品类型**：不同活动奖品形态不同（福卡、红包、实物奖品等）。
- **数量限制**：奖品可能是无限制，也可能是有限量，有限量才需要库存扣减。
- **中奖概率**：需要合理设置，避免过高或过低的体验失衡。
- **发奖规则**：不同类型奖品发奖逻辑存在差异，需要针对性处理。

## 并发安全性：三类解法

针对并发读写共享状态的问题，六种活动分别用到了不同手段：

| 解法 | 适用场景 | 代表活动 |
| --- | --- | --- |
| 互斥锁（`sync.Mutex`） | 通用，保护任意临界区 | 年会抽奖、大转盘 |
| 队列 + Channel | 把状态修改收敛到单消费者 | 微博抢红包 |
| 原子递减（`atomic`） | 简单计数/库存递减 | 大转盘库存 |

没有一种解法是"万能"的：互斥锁直观通用但竞争开销大；队列用通信替代共享内存、便于横向扩展；原子操作基于 CPU 特性、性能最优却只适用于简单计数。选型应依据读写比例、集合规模与临界区复杂度。

## 优化：散列拆分集合

当数据集合很大（如千万级红包），即使加了锁，单集合的锁竞争仍是瓶颈。优化办法是**散列**：用关键 ID 取模，把单个大集合拆成多个小集合（如 16 个），每个集合的冲突随之大幅下降，性能提升明显。这一思想在红包活动的多队列、多集合改造中已经体现。

## 从 Demo 到实战

六种活动目前都是独立的单程序 Demo，重点演示了随机数处理、库存处理与发奖逻辑。后续实战课程会以抽奖大转盘为主线，把这些零散能力整合为一个完整的、可运营、可维护的抽奖系统——后台管理、缓存优化、服务化（Thrift）、压测调优都会在后面逐章展开。
