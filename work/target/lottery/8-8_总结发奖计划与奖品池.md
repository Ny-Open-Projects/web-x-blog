# Go 企业级抽奖项目: 总结发奖计划与奖品池

## 纲要

- 发奖计划核心：把奖品总量合理分配到发奖周期的「天 → 小时 → 分钟」，时间逻辑理清即水到渠成。
- 难点之一：一天内不同时段需按访问量预设概率，高峰时段机会更多、低谷更少，权重配置要结合自身业务。
- 奖品池填充服务：重度依赖发奖计划，每分钟把「当前时间及之前」的计划量放进奖品池。
- 并发要点：Redis `HINCRBY` 原子递增/递减，但并发减量可能导致库存损失，因此引入二次补偿逻辑。
- 价值：奖品池作为缓冲地带，让奖品「有节奏、合理、不超发」地流出。

## 发奖计划：把总量合理铺开

发奖计划的本质，是把一个奖品的「总数量」与「发奖周期（天数）」翻译成一份可执行的发放时间表：

- 先算每天平均值，余数随机撒到任意一天；
- 每天再分到 24 小时，按 `PrizeDataRandomDayTime` 的权重区分高峰/低谷；
- 每小时再分到 60 分钟，多则平均、少则随机；
- 最后 `formatGiftPrizeData` 把三层结构拍平成有序的 `[时间,数量]` 数组，序列化进 `LtGift.PrizeData`。

理清「天 / 小时 / 分钟」三层时间关系后，重置逻辑并不复杂。难点在于一天内不同时段的权重预设——必须根据真实访问规律把机会分给高峰时段，这部分需要结合业务自身特点来规划，没有通用答案。

## 奖品池：按计划节奏兑现库存

奖品池（`Redis Hash gift_pool`）是发奖计划与用户抽奖之间的缓冲。填充服务 `DistributionGiftPool` 每分钟运行一次，按当前时间把发奖计划里「到期应发」的部分兑现成池中库存，并同步截断已消费的计划。发奖时则对池中库存做 `HINCRBY -1`，返回值小于 0 即代表无库存、不可发奖。

并发场景下的两个关键设计：

- 单条增减都走 Redis 原子命令 `HINCRBY`，天然避免单操作竞态。
- 但填充（递增）与发奖（递减）并发时，递减不判负可能把库存拉到负数，导致递增后返回值小于预期增量——即库存损失。因此 `incrServGiftPool` 在检测到「实际增量 < 预期增量」时会再做一次差额补偿。

## 价值总结

引入奖品池与发奖计划后，抽奖系统获得了两个收益：

1. **有节奏**：奖品按预设时间表逐步放量，避免开场瞬间被薅空，活动全程都能保持参与度。
2. **更合理**：高峰时段多放、低谷少放，贴合真实流量，提升运营效果。

这套「计划计算（每 5 分钟自愈）+ 池子填充（每分钟兑现）+ 池子扣减（抽奖时原子递减 + 补偿）」的组合，正是企业级抽奖在高并发下保证「不超发、发放平滑」的核心机制。
