# Go 企业级抽奖项目: 奖品数据全量缓存分析

## 纲要

- 缓存优化的目标：为抽奖系统引入 Redis，降低对 MySQL 的读写依赖与压力。
- 奖品数据的特点：数量少、后台更新频率低，适合做**全量缓存**。
- 数据结构选型：奖品集合选用最简的 `string`（JSON 序列化整体存储），不使用 `hash` 或 `list`。
- 库存数据另行优化：库存通过后续的「奖品池」单独维护，不在本次全量缓存范围内。
- 代码改动范围：`giftService` 新增三个内部方法 `getAllByCache`、`setAllByCache`、`updateByCache`；已有读取方法增加 `useCache bool` 参数；写操作先删缓存再更新数据库。
- 封装原则：缓存的读取与写入全部收敛在 `service` 层，外部调用方无需感知底层用的是 MySQL 还是 Redis。

## 为什么需要缓存优化

第 6 章的抽奖逻辑每一次请求都会频繁读取奖品列表、用户当日次数、IP 黑名单等数据，这些读操作最终都落到 MySQL 上。当并发量上升时，数据库会成为瓶颈。第 3 章缓存设计里已经讨论过各类数据的缓存利弊，第 7 章则是真正的落地实践：无论是全量缓存，还是基于散列（hash）的部分数据缓存，都逐一实现一遍。

## 奖品数据为什么适合全量缓存

奖品数据集合有两个关键特征，决定了它的缓存方式：

1. **有顺序且数量有限**：奖品通常只是几十条记录，整体序列化成一个 JSON 字符串即可一次性存入 Redis。
2. **更新频率极低**：奖品的标题、时间、状态等字段基本只在后台运营时修改，不会在抽奖请求链路里被高频变更。

基于这两点，选用 `string` 结构而不是 `hash` 或 `list` 的理由如下：

- 用 `hash` 需要把每个奖品拆成独立字段分别维护，反而增加复杂度，且奖品是有序集合，`hash` 并不体现顺序优势。
- 用 `list` 同样体现不出任何优势。
- 用 `string` + JSON 一次性序列化，读取时一次 `GET` 即可拿回全部奖品，写入时一次 `SET` 即可覆盖，简单高效。

> 关于库存：`PrizeLeftNum` 这类每次发奖都要递减的字段，并不放在本次全量缓存里更新，而是留到第 8 章通过「奖品池」单独做库存优化，避免每次发奖都重写整个奖品缓存。

## 缓存设计的三个内部方法

`giftService` 在 `service` 包内部新增三个不对外暴露的方法（接口之外，仅包内可见），由 service 层封装屏蔽外部可见性：

- `getAllByCache() []models.LtGift`：从 Redis 读取全量奖品。
- `setAllByCache(gifts []models.LtGift)`：将全量奖品序列化后写入 Redis。
- `updateByCache(data *models.LtGift, columns []string)`：数据变更时删除缓存（延迟到下次读取再回源数据库）。

同时，对已有的读取方法增加 `useCache bool` 参数，让调用方自行决定走缓存还是直连数据库，提升灵活性。

## 写操作的缓存一致性策略

对于 `Create`、`Update`、`Delete` 这类会修改数据的操作，采用「**先删缓存，再更新数据库**」的惯例做法：

- 先调用 `updateByCache` 删除 Redis 中 `allgift` 这个 key。
- 再调用 DAO 更新数据库。
- 下次读取时缓存未命中，自动从数据库回源并重新写入缓存，从而保证最终一致。

相比「先更新数据库再删缓存」或「双写」，删除缓存的实现复杂度最低，且奖品更新频率极低，短暂缓存失效窗口不会带来压力问题。

## Demo 示例

下面用 `go-redis/v9` 实现一个最小可运行的全量缓存读写示例，演示「读缓存 → 未命中回源 → 写缓存」的核心流程。

运行说明：

```bash
go mod init demo
go get github.com/redis/go-redis/v9
go run main.go
```

代码说明：

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

// Gift 奖品模型（精简）
type Gift struct {
	Id    int    `json:"Id"`
	Title string `json:"Title"`
	Left  int    `json:"Left"`
}

var (
	rdb = redis.NewClient(&redis.Options{Addr: "127.0.0.1:6379"})
	ctx = context.Background()
)

const cacheKey = "allgift"

// GetAll 先读缓存，未命中则从数据库（此处用模拟数据）回源并写回缓存
func GetAll() ([]Gift, error) {
	// 1. 读缓存
	str, err := rdb.Get(ctx, cacheKey).Result()
	if err == redis.Nil {
		// 2. 缓存未命中，模拟数据库读取
		gifts := []Gift{
			{Id: 1, Title: "iPhone", Left: 5},
			{Id: 2, Title: "优惠券", Left: 100},
		}
		// 3. 写回缓存
		b, _ := json.Marshal(gifts)
		if e := rdb.Set(ctx, cacheKey, b, time.Hour).Err(); e != nil {
			return nil, e
		}
		return gifts, nil
	} else if err != nil {
		return nil, err
	}
	// 4. 命中缓存，反序列化返回
	var gifts []Gift
	if e := json.Unmarshal([]byte(str), &gifts); e != nil {
		return nil, e
	}
	return gifts, nil
}

// Invalidate 数据变更时删除缓存
func Invalidate() error {
	return rdb.Del(ctx, cacheKey).Err()
}

func main() {
	gifts, err := GetAll()
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println("first read:", gifts)

	// 模拟后台修改奖品后失效缓存
	if err := Invalidate(); err != nil {
		log.Fatal(err)
	}
	gifts, _ = GetAll()
	fmt.Println("after invalidate:", gifts)
}
```

技术点总结：

- 全量缓存用 `string` + JSON 整体存取，结构简单、读写都在一次命令内完成。
- 缓存未命中时回源数据库并写回，是典型「Cache Aside」读路径。
- 写路径采用「先删缓存，再更新数据库」，实现成本低且能保证最终一致。
