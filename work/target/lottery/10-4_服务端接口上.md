# Go 企业级抽奖项目: 实现 Thrift 服务端接口（上）

## 纲要

- 服务端需要一个 Controller 来承载 Thrift 的 HTTP 入口，并注册路由 `/rpc`
- 定义 `rpcServer` 结构体实现自动生成的 `LuckyService` 接口（DoLucky、MyPrizeList 两个方法）
- 业务依赖（UserService、GiftService 等）通过 Controller 注入，避免在每个请求里重复创建
- 理清“Controller 负责 HTTP 收发 + Thrift 编解码”与“rpcServer 负责业务实现”的分工

## 服务端整体结构

Thrift 的服务端实现放在 `web/controllers/rpc.go` 里。它既是一个 Iris 的 Controller（处理 HTTP 请求），又通过组合一个 `rpcServer` 来真正落地 `LuckyService` 接口。整体调用链路是：Iris 收到 `/rpc` 的 POST 请求 → Controller 读取请求体并交给 Thrift 解码 → 调用 `rpcServer` 实现的方法 → 将结果编码后写回响应。

## RpcController：HTTP 入口与依赖注入

`RpcController` 持有各类 Service 依赖。由于这些对象在请求间可以复用，我们在 Iris 注册路由时把它们注入到 Controller 上，而不是在每次方法调用里临时 `new`：

```go
type RpcController struct {
	Ctx            iris.Context
	ServiceUser    services.UserService
	ServiceGift    services.GiftService
	ServiceCode    services.CodeService
	ServiceResult  services.ResultService
	ServiceUserday services.UserdayService
	ServiceBlackip services.BlackipService
}
```

在路由注册处把 `/rpc` 路径绑定到该 Controller（例如 `app.Party("/rpc").Handle(new(RpcController))`），这样外部应用就可以通过 `http://localhost:8080/rpc` 访问到抽奖 RPC 接口。

## rpcServer：实现 LuckyService 接口

真正去实现 Thrift 生成接口的是下面这个空结构体。因为所有数据访问都通过注入的 Service 完成，它本身不需要保存状态：

```go
type rpcServer struct{}
```

它要实现 `rpc.LuckyService` 接口定义的两个方法。方法签名必须与生成代码严格一致（第一个参数是 `context.Context`）：

## 为什么 Controller 与 rpcServer 要分开

这里有两层职责：

- `RpcController` 只关心“如何接收 HTTP 请求、如何把请求体喂给 Thrift、如何把 Thrift 的响应写回”。它和具体业务无关，是通用的 RPC 接入层。
- `rpcServer` 只关心“DoLucky / MyPrizeList 的业务逻辑怎么落地”。它依赖 Service 层，与 HTTP 框架解耦。

这种拆分的好处是：如果以后更换 HTTP 框架，只要替换 Controller 那一层；如果业务规则变化，只改 `rpcServer`。两者通过 `rpc.LuckyService` 接口衔接，互不污染。
