# Go 企业级抽奖项目: 优惠券全量缓存设计分析

## 纲要

- 背景：抽奖系统里有一类"优惠券"奖品，每个券有唯一的编码（如兑换码），发奖时从一批编码里弹出一个给用户。
- 缓存选型：这类数据适合用 Redis 的 **Set（集合）** 结构，每个编码是集合中的唯一成员，无需考虑顺序。
- 四个核心方法规划（落在 `web/utils/prizedata.go`）：
  - `ImportCacheCodes(id, code)`：把单个券编码导入缓存 Set。
  - `RecacheCodes(id, codeService)`：用数据库里的有效编码重建缓存（先写临时 Set 再 `RENAME` 覆盖），保证与 DB 一致。
  - `GetCacheCodeNum(id, codeService)`：统计数据库有效编码数与缓存剩余数，供后台展示。
  - `prizeServCodeDiff(id, codeService)`：发奖时从 Set 弹出一个编码（`SPOP`），替代原 MySQL 实现。

## 文本修正与整合

前面我们已经把奖品全量缓存、奖品池、用户 IP 黑名单、用户今日抽奖次数都搬到了 Redis。第 7 章最后一个要缓存的数据，是**优惠券**。

这里的优惠券特指"带唯一编码"的优惠券（兑换码）。只有这种券才需要做数据导入：运营先把一批编码导入数据库，抽奖中奖后再从中分配一个给用户。导入的编码可以整体缓存进 Redis，发奖时直接从缓存弹出一个，避免每次都查 MySQL。

为什么选择 **Set（集合）** 结构？

- 每个券编码都是唯一的，Set 天然去重，不会出现重复编码。
- 导入就是往 Set 里 `SADD` 一个编码；发奖就是从 Set 里 `SPOP` 弹出一个，语义完全贴合。
- 不需要顺序，也不需要按编码排序取，Set 足够且高效。

```mermaid
flowchart LR
    A[运营导入一批券编码] -->|SADD| B[Redis Set: gift_code_{id}]
    C[用户中奖发券] -->|SPOP| B
    B -->|弹出的编码| D[更新数据库状态为已发放]
    E[后台统计] -->|SCARD| B
```

主要代码改动点在 `web/utils/prizedata.go`，需要新增上述三个公开方法和一个私有方法；另外需要对后台管理功能做适配，把"导入""重整""统计"接到缓存上（下一篇实现）。

关于 `RecacheCodes` 为什么要"先写临时 Set 再 `RENAME`"：假设数据库手动删除了 10 个编码，如果直接在正式 key 上 `SADD`，那 10 个已被删的编码仍然残留在正式 key 里（因为 `SADD` 只增不删）。改用临时 key 导入有效编码、再用 `RENAME` 原子覆盖正式 key，就能保证缓存与数据库完全一致。

## API 速览（规划）

| 方法（规划） | 作用 | 对应 Redis 命令 |
| --- | --- | --- |
| `ImportCacheCodes(id, code) bool` | 导入单个券到缓存 | `SADD gift_code_{id} code` |
| `RecacheCodes(id, svc) (suc, err int)` | 用 DB 有效编码重建缓存 | `SADD tmp_key code` + `RENAME tmp_key gift_code_{id}` |
| `GetCacheCodeNum(id, svc) (dbNum, cacheNum int)` | 统计数据库与缓存数量 | `SCARD gift_code_{id}` |
| `prizeServCodeDiff(id, svc) string` | 发奖弹出一个编码 | `SPOP gift_code_{id}` |
