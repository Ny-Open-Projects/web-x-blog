# Go 企业级抽奖项目: 压力测试方案与工具选型

## 纲要

- 压测工具对比：`wrk`（默认长连接）与 `ab`（Apache Bench，默认短连接）
- `wrk` 核心三参数：`-t` 线程数、`-c` 并发连接数、`-d` 持续时间，末尾跟测试 URL
- 对比维度：不同奖品数量、不同中奖概率、不同用户/IP 今日抽奖限制值
- 目标不止看 QPS 差异，还要定位时间开销来源（程序资源调用、各阶段耗时）

## 为什么再做一次压测

结合前面关于奖品设置合理性的总结，本章用压力测试来量化验证：不同的奖品数量与中奖概率设置，性能差异到底有多大。同时把第 6~8 章的 Redis 缓存、发奖计划、奖品池等优化成果，放到真实并发下检视。

## 工具选型：wrk 与 ab

常用的两款 HTTP 压测工具：

- `wrk`：默认使用长连接（keep-alive），单机即可打出很高并发，适合评测高并发服务的吞吐。
- `ab`（Apache Bench）：默认使用短连接，用法同样简单，适合快速验证。

两者都可通过参数切换长/短连接，运行参数都很简洁。本系列统一使用 `wrk`。

## wrk 核心参数

`wrk` 最关注的三个参数：

- `-t <N>`：启动多少个线程（thread）
- `-c <N>`：创建多少个并发连接（connection）
- `-d <时间>`：压力测试持续多长时间（duration），如 `5s`、`30s`

命令末尾跟上被压测的 URL 即可。

```shell
# 10 个线程、10 个并发连接、持续 5 秒，压测抽奖接口
wrk -t10 -c10 -d5s http://127.0.0.1:8080/lucky
```

## 本次压测的对比维度

1. 奖品数量：不限量 vs 限量（如 1000），观察发奖链路负载差异。
2. 中奖概率：100% 中奖 vs 1% 中奖，观察进入发奖环节请求占比对吞吐的影响。
3. 用户/IP 今日抽奖限制：放开 vs 收紧，观察「早期跳出」对 QPS 的提升。

## 不止看结果，要看原因

对比测试中不仅要得出「哪种设置 QPS 更高」的结论，还要分析差异产生的根因：程序的资源调用、时间到底花在哪一环（Redis？数据库？业务逻辑？）。只有定位到耗时来源，优化才有方向。

## 小结

压测方案确定：用 `wrk` 以 `-t/-c/-d` 三个参数控制并发模型，围绕「数量 / 概率 / 限制值」三组变量做对照，并以定位时间开销为目标。具体执行与数据见 9-6。
