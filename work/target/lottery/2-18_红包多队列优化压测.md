# Go 企业级抽奖项目: 红包服务多队列优化与压测

## 纲要

- 并发改造后压测：发红包（单接口）在十万级请求下不再报错，性能良好；抢红包用大红包（十万元、十万个小红包）5 秒可抢四万余次。
- 压测工具按时间断开请求，服务端仍会处理完，导致统计数有个位数差异，属正常现象。
- 单任务队列是性能瓶颈：所有抢红包请求挤在一个消费者里串行处理。
- 优化一：把单队列扩展为 16 个队列（`taskNum=16`），按红包 ID 取模分散任务，启动时拉起多个消费服务。
- 优化二（留作练习）：把 `packageList` 也拆成 16 个集合，配合多队列进一步降低冲突。
- 多核服务器上，任务/集合的横向拆分能带来明显性能提升；双核笔记本上对比不明显。

## 压测验证

改造完成后先验证功能：清空状态后做并发压测，发红包单接口稳定不报错；再重启验证抢红包——发放一个十万元、十万个小红包的大红包，5 秒内可抢四万多次，剩余约五万。统计数与服务端实际处理数的个位数差异，源于压测工具到点断开但服务端仍在收尾，不影响正确性。

在如此大规模（几万次）并发下，若未解决并发安全问题，很容易出现十几次甚至几十次错误；改造后则稳定。

## 单队列的瓶颈与多队列拆分

当前只有一个任务队列、一个消费者，所有抢红包请求都串行排队。改成多个队列后，按红包 ID 取模把任务分散到不同队列，由多个消费者并行处理。

```go
package main

import "math/rand"

// taskNum 队列/消费者数量，静态常量
const taskNum = 16

// taskQueues 多个抢红包任务队列
var taskQueues = make([]chan chanTask, taskNum)

func init() {
	for i := range taskQueues {
		taskQueues[i] = make(chan chanTask, 1024)
	}
}

// StartGrabServices 启动多个消费者，每个队列一个
func StartGrabServices() {
	for i := 0; i < taskNum; i++ {
		go GrabServiceOn(taskQueues[i])
	}
}

// GrabServiceOn 在指定队列上常驻消费
func GrabServiceOn(q chan chanTask) {
	r := rand.New(rand.NewSource(time.Now().UnixNano()))
	for task := range q {
		task.Callback <- grabOne(task.TaskID, r)
	}
}

// GrabPacketV2 按红包 ID 取模选择队列投递任务
func GrabPacketV2(id int) (int, string) {
	cb := make(chan int, 1)
	q := taskQueues[id%taskNum]
	q <- chanTask{TaskID: id, Callback: cb}
	money := <-cb
	if money <= 0 {
		return money, "很遗憾，没有抢到红包"
	}
	return money, "恭喜你抢到一个红包"
}
```

改动很小：把单个 `taskQueue` 换成 `[]chan chanTask`；启动阶段循环拉起 `taskNum` 个 `GrabServiceOn`；投递任务时 `id % taskNum` 选队列。

## 集合拆分（练习）

除了任务队列，红包集合本身也可按同样思路拆成 16 个 `sync.Map`/普通 `map`，通过 ID 取模定位。这样"任务队列"与"数据集合"都从 1 变成 16，多核服务器上冲突大幅降低，性能提升显著。该改造留作动手练习，在后续实战章节中还会涉及。

## 性能对照

| 方案 | 并发安全 | 多核扩展 | 实现复杂度 |
| --- | --- | --- | --- |
| 单队列 + 单消费者 | 安全 | 差 | 低 |
| 16 队列 + 16 消费者 | 安全 | 好 | 中 |
| 16 队列 + 16 集合 | 安全 | 优 | 中高 |

## API 速览

- `const taskNum = 16`：队列与消费者数量。
- `StartGrabServices()`：启动 `taskNum` 个消费服务。
- `GrabServiceOn(q chan chanTask)`：在指定队列常驻消费。
- `GrabPacketV2(id int) (int, string)`：按 `id % taskNum` 选队列投递，等待回调。

## Demo 示例

运行说明：将 `taskQueues`、`StartGrabServices`、`GrabServiceOn`、`GrabPacketV2` 与本系列前几篇的 `sync.Map` 红包集合、`grabOne`、`removeAt` 合并，`main` 中调用 `StartGrabServices()` 后并发调用 `GrabPacketV2` 即可对比多队列效果。

代码说明：多队列的核心只有三步——数组化队列、循环启动消费者、按 ID 取模投递；集合拆分同理，是"分而治之"降低锁竞争的通用手法。

技术点总结：当单集合/单队列成为瓶颈，按关键 ID 取模散列成 N 份是低成本高收益的横向扩展手段，尤其契合多核服务器。
