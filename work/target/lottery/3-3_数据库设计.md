# Go 企业级抽奖项目: 数据库设计

## 纲要

- 六大核心数据表：奖品表、优惠券表、抽奖记录表、用户黑名单表、IP 黑名单表、用户每日次数表
- 通用约定：自增主键、唯一索引、系统保留字段（软删除）
- 奖品表字段最复杂，是系统核心
- 优惠券、抽奖记录、黑名单、每日次数表字段相对精简

## 数据模型梳理

抽奖系统涉及的核心实体：用户、奖品、优惠券（奖品的一种特殊类型）、中奖记录、用户黑名单、IP 黑名单，以及用户每日参与次数这一临时统计结构。

由此反推，需要设计以下六张表：

- 奖品表（gift）
- 优惠券表（coupon）
- 抽奖记录表（result）
- 用户黑名单表（user_black）
- IP 黑名单表（ip_black）
- 用户每日次数表（user_day）

## 通用字段约定

所有表统一遵循以下规范：

- id：主键，自增，作为唯一标识，必须存在
- 系统保留字段（以 sys_ 前缀）：
  - sys_status：状态，0 正常，1 删除。**禁止物理删除，统一用状态软删除**
  - sys_created：记录创建时间
  - sys_updated：记录最后修改时间
  - sys_ip：记录创建时的操作人 IP

## 奖品表（gift）

奖品表是系统中最复杂、使用最频繁的一张表，需重点关注。

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| id | 主键 | 自增 |
| title | 奖品标题 | 奖品名称 |
| prize_num | 奖品总数量 | 0 表示不限，大于 0 表示有限制，小于 0 表示无奖品 |
| left_num | 剩余数量 | 必须大于 0 才能发奖 |
| prize_code | 中奖概率 | 精确到万分之一，取值 0–9999；0 表示万分之一，9999 表示百分之百；编码区间左右闭合 |
| prize_time | 发奖周期 | 以天为单位（周=7，月=30） |
| img | 图片 | 奖品展示图 |
| display_order | 位置序号 | 转盘中的位置，越小越靠前 |
| gtype | 奖品类型 | 实物 / 虚拟币 / 优惠券等 |
| gdata | 扩展数据 | 虚拟币存数量；固定优惠券存券编码 |
| time_begin / time_end | 有效周期 | 奖品可参与匹配的时间范围 |
| prize_plan | 发奖计划 | mediumtext，JSON 数组，元素含 time 与 num，配合奖品池服务自动填充 |

> prize_plan 存储的数据量随奖品数量增长：若奖品总量为十万，计划数据会很大；若为百级，则较小。发奖周期结束后，需有程序自动生成下一周期的发奖计划。

## 优惠券表（coupon）

字段较少，除 sys_ 保留字段外仅有：

- gift_id：关联所属奖品（转盘上可能含多个优惠券，需指明归属）
- code：券唯一编码，唯一索引，重复会触发数据库冲突

## 抽奖记录表（result）

用于保存用户中奖记录：

- gift_id：关联中奖奖品
- uid：关联用户
- gift_name / gift_type：奖品名称与类型
- user_name：登录用户名
- prize_code：本次抽奖编码，便于回查中奖概率是否符合预期
- gift_data：获奖详情（优惠券编码、虚拟币金额等）

## 用户黑名单表（user_black）

- id 即 uid，作为唯一主键
- user_name：用户名
- black_time：黑名单限制到期时间（默认惩罚一个月，可后台调整）
- 可附加真实姓名、手机号、联系地址等联系信息

是否处于黑名单状态，需结合记录与 black_time 共同判定（到期即解除）。

## IP 黑名单表（ip_black）

- ip：唯一索引，高频查询字段
- black_time：限制到期时间

> 注意误杀问题：若公司共用一个出口 IP 集体抽奖，可能误伤。本策略未完全禁止其中奖，故影响可控。

## 用户每日次数表（user_day）

- uid + day：联合唯一索引，用于按用户与日期查询当日抽奖次数
- num：当日已参与次数

除奖品表外，其余五张表字段精简，业务复杂度与字段规模成正比。

相关度：95%。是否需要继续：是。代码是否可运行：否。
