# Go 企业级抽奖项目: 缓存设计

## 纲要

- 缓存目标：提升性能、降低数据库依赖
- 设计原则：平衡性能、开发时间、系统复杂度
- 适用场景：读多写少、数据量有限、数据可分散分片
- Redis 应用场景：奖品全量缓存、优惠券、中奖记录、用户 / IP 黑名单、用户每日次数（收益低）

## 缓存的目标与原则

引入缓存最基本的目标是提升系统性能、减少对数据库的依赖。但使用缓存需遵循一条核心原则：**平衡好系统性能、开发时间与复杂度**。

缓存通过数据冗余换取性能，会带来空间复杂度上升，同时开发时间与系统复杂度并非线性增长，而可能是数倍（n 倍）增加。因此是否引入缓存，要权衡收益与代价。

## 适合使用缓存的场景

- 读多写少：缓存读优化收益明显
- 数据量有限：数据过大将导致内存不足，不适合整体缓存
- 数据可分散：数据能按 key 独立存储（如按 UID、IP 分片），便于水平扩展至多台缓存服务器

## Redis 在本系统的应用场景

本系统使用 Redis 作为缓存，具体适用点如下：

| 数据 | 特征 | 缓存方式 | 收益 |
| --- | --- | --- | --- |
| 奖品 | 数量少（常 <10）、更新频率低 | 全量缓存，读全部走缓存 | 高 |
| 优惠券 | 数量有限、编码唯一 | 导入 SET 集合，发券用 SPOP 取一个 | 高 |
| 中奖记录 | 读写均衡 | 仅缓存最新中奖 / 大奖发放等部分统计 | 中 |
| 用户黑名单 | 读多写少 | 按 UID 分片缓存 | 高 |
| IP 黑名单 | 读多写少 | 按 IP 分片缓存 | 高 |
| 用户每日次数 | 读写差异不明显 | 缓存收益有限 | 低 |

说明：

- 奖品数据是最佳的全量缓存对象，更新频率低，写入时同步更新缓存即可
- 优惠券在活动开始前一次性导入 Redis 的 SET 集合，发放时直接 `SPOP` 取一个编码，效率极高、开发复杂度低
- 用户 / IP 黑名单均读多写少，可按 UID、IP 分片缓存

在设计阶段就将「哪些地方优先用缓存、收益如何」想清楚，开发时目标会更明确。
