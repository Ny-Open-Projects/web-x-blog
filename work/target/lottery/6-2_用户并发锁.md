# Go 企业级抽奖项目: 用户并发操作的锁

## 纲要

- Web 应用中用户行为不可控，抽奖接口的"重入"会带来脏读、重复写入等并发安全问题。
- 解决思路：在用户维度加一把**分布式锁**，保证同一用户同一时刻只能进入一次抽奖流程。
- 锁基于 Redis 实现，使用 `SET key value EX 3 NX` 一条指令完成"加锁 + 设置过期时间 + 不存在才写入"。
- 必须避免死锁：通过过期时间兜底，即使程序异常未显式解锁，锁也会在 3 秒后自动释放。
- 封装为 `utils.LockLucky(uid)` / `utils.UnlockLucky(uid)`，加锁失败即提示"正在抽奖，请稍后重试"。

## 为什么需要分布式锁

在抽奖接口里，同一个用户的请求可能是并发的：用户快速连点，或者脚本直接发包刷接口。如果不加约束，会出现两类问题：

1. **脏数据**：并发下读取"剩余库存 / 今日次数"时拿到过期值。
2. **写入重复 / 丢失更新**：两个请求同时通过校验，导致库存被多减、记录被重复插入。

因此在进入用户验证逻辑之前，先对当前用户加锁。这把锁只锁定单个用户，不会阻塞其他用户的请求，对全局性能影响极小。

## 基于 Redis 的加锁实现

工程把锁相关公共能力放到 `web/utils/locker.go`。核心是用 Redis 的 `SET` 指令，一次性带上三个参数：

- `EX 3`：设置 3 秒过期时间。
- `NX`：只有当 key 不存在时才写入（保证原子性，解决并发冲突）。
- value 写 `1` 即可，真正起作用的是 key 的存在性。

```go
package utils

import (
	"fmt"

	"imooc.com/lottery/datasource"
)

// 加锁，抽奖时用到的锁，避免一个用户并发多次抽奖
func LockLucky(uid int) bool {
	return lockLuckyServ(uid)
}

// 解锁，抽奖时用到的锁，避免一个用户并发多次抽奖
func UnlockLucky(uid int) bool {
	return unlockLuckyServ(uid)
}

func getLuckyLockKey(uid int) string {
	return fmt.Sprintf("lucky_lock_%d", uid)
}

func lockLuckyServ(uid int) bool {
	key := getLuckyLockKey(uid)
	cacheObj := datasource.InstanceCache()
	// SET key 1 EX 3 NX：原子加锁，3 秒自动过期
	rs, _ := cacheObj.Do("SET", key, 1, "EX", 3, "NX")
	if rs == "OK" {
		return true
	}
	return false
}

func unlockLuckyServ(uid int) bool {
	key := getLuckyLockKey(uid)
	cacheObj := datasource.InstanceCache()
	rs, _ := cacheObj.Do("DEL", key)
	if rs == "OK" {
		return true
	}
	return false
}
```

要点说明：

- `datasource.InstanceCache()` 返回 Redis 连接池对象（redigo 的 `redis.Conn`），`Do` 方法直接下发 RESP 指令。
- `EX 3` 就是过期时间。若加锁后的逻辑在某处卡住、异常退出，没调用到 `UnlockLucky`，3 秒后 key 也会自动消失，从而**避免死锁**。
- `NX` 保证"已存在则写入失败"，正好用来检测"同一用户是否正在抽奖"。
- 过期时间取 3 秒是经验值：太短可能在正常逻辑执行中途就过期失效；太长则异常时用户要等很久才能再抽。实际项目按自身业务调整。

## 在抽奖接口中如何使用

回到 `luckyDo`，加锁配合 `defer` 保证函数任何返回路径都能解锁；加锁失败直接返回错误码 `102`。

```go
func (api *LuckyApi) luckyDo(uid int, username, ip string) (int, string, *models.ObjGiftPrize) {
	// 步骤2：用户抽奖分布式锁定
	ok := utils.LockLucky(uid)
	if ok {
		defer utils.UnlockLucky(uid)
	} else {
		return 102, "正在抽奖，请稍后重试", nil
	}
	// ... 后续步骤 3~12
	return 0, "", prizeGift
}
```

> 说明：以上 `locker.go` 代码即工程真实实现（参考 `web/utils/locker.go`），与讲稿逻辑一致。

## Demo 示例

以下片段演示如何最小地使用这把锁（节选自抽奖主流程，按讲稿逻辑整理）：

```go
// 运行说明：需要已初始化 Redis 连接池（datasource.InstanceCache）
// 代码说明：演示 加锁-业务-defer解锁 的标准写法
func tryDraw(uid int) {
	if !utils.LockLucky(uid) {
		fmt.Println("正在抽奖，请稍后重试")
		return
	}
	defer utils.UnlockLucky(uid)

	// 此处执行抽奖校验与发奖逻辑
	fmt.Println("进入抽奖流程，uid =", uid)
}
```

技术点总结：

- 用 Redis 单条 `SET ... NX EX` 实现原子加锁，避免"先查后写"的竞态。
- `EX` 过期时间兜底，杜绝死锁。
- `defer Unlock` 确保任何返回路径都能释放锁。
