# Go 企业级抽奖项目: 微博抢红包活动分析与设计

## 纲要

- 微博抢红包与微信红包机制高度相似，但微博红包是公开红包：只要在有效期内看到红包即可"先到先得"地抢，不受群成员限制，覆盖面更广。
- 一个用户可以发多个红包，多个用户可以发更多红包，抢红包的用户也没有数量限制，从而能吸引大量用户参与。
- 所有红包需要统一保存在集合对象中（可能是 `map` 或 `slice`），而单个红包内部的金额又是一个集合，这些集合都会面临并发读写。
- 并发安全性问题不可避免，处理思路与前面几种活动一致，但集合规模更大，需要更谨慎。
- 优化方向：通过散列（hash）把单个大集合拆成多个小集合，降低单集合的并发冲突。

## 活动规则与差异

微信红包是现金形式、在微信群内传播，只有群成员能抢，范围小；微博红包则是公开形式，任何看到红包信息的人都能参与。这种"公开 + 无限制"的特性，让微博红包成为各类产品中更普遍的一种玩法。

规则要点：

- 一个用户可发出多个红包；多个用户可发出更多红包。
- 抢红包的用户无数量限制，先到先得。
- 红包有有效期，有效期内可抢。

## 数据结构与并发挑战

要保存"很多人发的很多红包"，必须有一个全局集合对象来承载所有红包。从讲稿描述看，这里既可以用 `map` 也可以用 `slice`。课程选择用 `map`，键为随机生成的正整数红包 ID，值为一个 `[]int` 切片，切片里保存该红包内每一个小红包的金额。

```go
// 全局红包集合：key 为红包 ID，value 为该红包内各小红包金额的切片
var packageList = make(map[int][]int)
```

为什么会有并发安全性问题：

- `packageList` 本身会被多个请求同时读写（发红包写入、抢红包读取并删除）。
- 单个红包内部的 `[]int` 切片在抢红包时也会被修改（拿走一个金额后更新切片）。
- 这两层集合都存在并发读写，必须用锁、原子操作或队列等手段保护。

## 优化思路

当集合很大（例如上千万人发红包，红包集合达到千万级）时，把所有数据塞进单个 `map` 会放大并发冲突。优化办法是**散列**：用红包 ID 取模，把数据分散到多个小集合里。每个集合的锁粒度变小，冲突随之大幅下降，性能提升明显。

```go
// 将单个大集合拆成 16 个小集合，按 ID 取模分散
const bucketNum = 16

var packageBuckets = make([]map[int][]int, bucketNum)

func bucketOf(id int) int {
	return id % bucketNum
}
```

## 小结

微博抢红包是六种活动中"集合规模 + 并发强度"都较高的一种，它复用前面处理并发安全性的经验，同时引入了"按 ID 散列拆分集合"的优化思想。具体发红包、抢红包的接口实现与金额随机分配算法，在后续篇章中展开。
