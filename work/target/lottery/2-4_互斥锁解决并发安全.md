# Go 企业级抽奖项目: 用互斥锁解决并发安全问题

## 纲要

- 引入 `sync.Mutex` 保护共享变量 `userList`
- 在 `/import` 与 `/lucky` 读写切片前后加锁、解锁
- 用 `defer mu.Unlock()` 确保任何分支都能正确释放锁
- 加锁后同样的 WaitGroup 并发测试 100% 通过，变为线程安全

## 互斥锁改造思路

上一节用单元测试暴露了 `userList` 的数据竞争。修复方法非常简单：给共享变量的读写加一把互斥锁（`sync.Mutex`）。原则只有一条——**对任何会被并发读写的共享变量，在其读/写前后加锁与解锁**，让所有并发操作在该变量上排队，而不是各自为政地把数据写坏、写成脏值。

需要加锁的位置正是会改变 `userList` 的两个地方：`PostImport`（追加用户）与 `GetLucky`（抽走用户）。更早地加锁更安全，因此直接在方法入口 `Lock()`，并用 `defer Unlock()` 保证函数任何返回路径都会释放锁，避免死锁。

代码说明（关键差异取自 `annualMeeting/safe/main.go`）：

```go
package main

import (
	"fmt"
	"math/rand"
	"strings"
	"sync"
	"time"

	"github.com/kataras/iris"
	"github.com/kataras/iris/mvc"
)

var userList []string
var mu sync.Mutex // 互斥锁，保护 userList

func newApp() *iris.Application {
	app := iris.New()
	mvc.New(app.Party("/")).Handle(&lotteryController{})
	return app
}

func main() {
	app := newApp()
	userList = make([]string, 0)
	mu = sync.Mutex{}
	app.Run(iris.Addr(":8080"))
}

// POST http://localhost:8080/import
func (c *lotteryController) PostImport() string {
	strUsers := c.Ctx.FormValue("users")
	users := strings.Split(strUsers, ",")
	mu.Lock()         // 进入临界区前加锁
	defer mu.Unlock() // 任何返回路径都解锁
	count1 := len(userList)
	for _, u := range users {
		u = strings.TrimSpace(u)
		if len(u) > 0 {
			userList = append(userList, u)
		}
	}
	count2 := len(userList)
	return fmt.Sprintf("当前总共参与抽奖的用户数: %d，成功导入用户数: %d\n", count2, (count2 - count1))
}

// GET http://localhost:8080/lucky
func (c *lotteryController) GetLucky() string {
	mu.Lock()
	defer mu.Unlock()
	count := len(userList)
	if count > 1 {
		seed := time.Now().UnixNano()
		index := rand.New(rand.NewSource(seed)).Int31n(int32(count))
		user := userList[index]
		userList = append(userList[0:index], userList[index+1:]...)
		return fmt.Sprintf("当前中奖用户: %s, 剩余用户数: %d\n", user, count-1)
	} else if count == 1 {
		user := userList[0]
		userList = userList[0:0]
		return fmt.Sprintf("当前中奖用户: %s, 剩余用户数: %d\n", user, count-1)
	} else {
		return fmt.Sprintf("已经没有参与用户，请先通过 /import 导入用户 \n")
	}
}
```

## 验证结果

重新启动 Web 应用并运行测试，所有断言均通过（数十毫秒内完成）。多次运行结果稳定，用户数精确为 100，抽奖后精确为 99，不再出现数据丢失。

技术点总结：

- 互斥锁是解决共享变量读写竞态的最直接手段。
- 加锁范围应覆盖"读—改—写"的完整临界区，而非只锁写。
- `defer Unlock()` 能避免在某条分支忘记解锁导致死锁。
- 后续其他抽奖活动（如微信摇一摇）同样会面对并发安全，仍可用互斥锁，也会引入其它方案对比。
