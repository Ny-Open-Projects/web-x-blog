# Go 企业级抽奖项目: 实现 Thrift 服务端接口（下）

## 纲要

- 把抽奖业务逻辑从 `IndexController` 抽离成独立的 `LuckyApi.luckyDo`，供 Web 与 RPC 复用
- `DoLucky` 的实现：调用 `luckyDo` 执行业务，再把结果映射到 `rpc.DataResult_`
- `MyPrizeList` 的实现：查询用户中奖记录并转换为 `[]*rpc.DataGiftPrize`
- 大量代码本质是“业务模型 ↔ Thrift 模型”的类型转换
- 对比 gRPC：实现方式高度相似，甚至更简单（因为不需要与 Web 框架耦合）

## 为什么需要重构

在引入 Thrift 之前，抽奖逻辑写在 Web 的 `IndexController` 里（`GetLucky`）。但 RPC 服务端也要做同样的事情，如果各写一遍就会重复。于是我们做一次重构：把抽奖过程抽离成一个独立的方法，封装到 `controllers` 包下的 `LuckyApi` 结构里。

抽离的原则是：所有依赖 Controller 的东西（比如从 Session 取登录用户）都不能留在封装里，必须由调用方传进来。抽奖需要的输入是 `uid`、`username`、`ip`，返回三样东西——`code`（状态码）、`msg`（消息）、`gift`（中奖信息）。

## LuckyApi.luckyDo：可复用的抽奖核心

```go
type LuckyApi struct{}

func (api *LuckyApi) luckyDo(uid int, username, ip string) (int, string, *models.ObjGiftPrize) {
	// 2 用户抽奖分布式锁定
	ok := utils.LockLucky(uid)
	if ok {
		defer utils.UnlockLucky(uid)
	} else {
		return 102, "正在抽奖，请稍后重试", nil
	}

	// 3 验证用户今日参与次数
	userDayNum := utils.IncrUserLuckyNum(uid)
	if userDayNum > conf.UserPrizeMax {
		return 103, "今日的抽奖次数已用完，明天再来吧", nil
	} else if ok := api.checkUserday(uid, userDayNum); !ok {
		return 103, "今日的抽奖次数已用完，明天再来吧", nil
	}

	// 4 验证 IP 今日参与次数
	ipDayNum := utils.IncrIpLuckyNum(ip)
	if ipDayNum > conf.IpLimitMax {
		return 104, "相同IP参与次数太多，明天再来参与吧", nil
	}

	limitBlack := ipDayNum > conf.IpPrizeMax
	// 5 验证 IP 黑名单
	if !limitBlack {
		if ok, _ := api.checkBlackip(ip); !ok {
			limitBlack = true
		}
	}
	// 6 验证用户黑名单
	if !limitBlack {
		if ok, _ := api.checkBlackUser(uid); !ok {
			limitBlack = true
		}
	}

	// 7 获得抽奖编码，8 匹配奖品
	prizeCode := comm.Random(10000)
	prizeGift := api.prize(prizeCode, limitBlack)
	if prizeGift == nil || prizeGift.PrizeNum < 0 ||
		(prizeGift.PrizeNum > 0 && prizeGift.LeftNum <= 0) {
		return 205, "很遗憾，没有中奖，请下次再试", nil
	}

	// 9 有限制奖品发放
	if prizeGift.PrizeNum > 0 {
		if utils.GetGiftPoolNum(prizeGift.Id) <= 0 {
			return 206, "很遗憾，没有中奖，请下次再试", nil
		}
		if ok := utils.PrizeGift(prizeGift.Id, prizeGift.LeftNum); !ok {
			return 207, "很遗憾，没有中奖，请下次再试", nil
		}
	}

	// 10 不同编码的优惠券发放
	if prizeGift.Gtype == conf.GtypeCodeDiff {
		if code := utils.PrizeCodeDiff(prizeGift.Id, services.NewCodeService()); code == "" {
			return 208, "很遗憾，没有中奖，请下次再试", nil
		} else {
			prizeGift.Gdata = code
		}
	}

	// 11 记录中奖，12 返回结果
	result := models.LtResult{
		GiftId: prizeGift.Id, GiftName: prizeGift.Title, GiftType: prizeGift.Gtype,
		Uid: uid, Username: username, PrizeCode: prizeCode,
		GiftData: prizeGift.Gdata, SysCreated: comm.NowUnix(), SysIp: ip, SysStatus: 0,
	}
	if err := services.NewResultService().Create(&result); err != nil {
		return 209, "很遗憾，没有中奖，请下次再试", nil
	}
	if prizeGift.Gtype == conf.GtypeGiftLarge {
		api.prizeLarge(ip, uid, username, nil, nil)
	}
	return 0, "", prizeGift
}
```

抽离之后，`luckyDo` 不再依赖任何 Controller 状态，Web 的 `IndexController` 和 RPC 的 `rpcServer` 都可以直接调用它。重构过程就是把原本散落在 Controller 里的 `loginUser`、`service.xxx` 调用全部替换成参数传入或 `api.` 方法调用，工作量主要在“消除依赖、统一签名”。

## DoLucky：业务结果映射到 Thrift 返回

`rpcServer.DoLucky` 调用 `luckyDo` 拿到业务结果，再转换成 Thrift 的 `DataResult_`：

```go
func (serv *rpcServer) DoLucky(ctx context.Context, uid int64, username string,
	ip string, now int64, app string, sign string) (r *rpc.DataResult_, err error) {

	if err = serv.checkParams(uid, username, ip, now, app, sign); err != nil {
		return nil, err
	}
	// 执行业务（rpcServer 自己不持有 Service，统一委托给 LuckyApi）
	api := &LuckyApi{}
	code, msg, gift := api.luckyDo(int(uid), username, ip)

	// 把业务模型转换为 Thrift 的 DataGiftPrize
	var prizeGift *rpc.DataGiftPrize
	if gift != nil && gift.Id > 0 {
		prizeGift = &rpc.DataGiftPrize{
			ID:           int64(gift.Id),
			Title:        gift.Title,
			Img:          gift.Img,
			Displayorder: int64(gift.Displayorder),
			Gtype:        int64(gift.Gtype),
			Gdata:        gift.Gdata,
		}
	}
	rs := &rpc.DataResult_{
		Code: int64(code),
		Msg:  msg,
		Gift: prizeGift,
	}
	if code > 0 {
		return rs, errors.New(msg)
	}
	return rs, nil
}
```

注意 `Gift` 字段在 `DataResult_` 里是 `*DataGiftPrize` 指针类型，所以需要做一次显式转换：业务侧的 `models.ObjGiftPrize` 字段逐一映射到 Thrift 结构。这类“把内部模型转成对外 RPC 模型”的转换代码，是服务端开发里占比最大的一部分。

## MyPrizeList：查询并转换集合

`MyPrizeList` 查询用户的中奖记录，并逐个转换成 `[]*rpc.DataGiftPrize`：

```go
func (serv *rpcServer) MyPrizeList(ctx context.Context, uid int64, username string,
	ip string, now int64, app string, sign string) (r []*rpc.DataGiftPrize, err error) {

	if err = serv.checkParams(uid, username, ip, now, app, sign); err != nil {
		return nil, err
	}
	list := services.NewResultService().SearchByUser(int(uid), 1, 100)
	rData := make([]*rpc.DataGiftPrize, len(list))
	for i, data := range list {
		rData[i] = &rpc.DataGiftPrize{
			ID:           int64(data.Id),
			Title:        data.GiftName,
			Img:          "",
			Displayorder: 0,
			Gtype:        int64(data.GiftType),
			Gdata:        data.GiftData,
		}
	}
	return rData, nil
}
```

返回值是 `[]*rpc.DataGiftPrize`，对应 IDL 里 `list<DataGiftPrize>`。同样是循环做字段映射。

## 开发体验小结

引入 Thrift 后真正要写的业务代码非常少：服务端接口里大部分代码要么是自动生成的，要么就是像上面这种“模型 A ↔ 模型 B”的类型转换。而且如果改用 gRPC，实现方式与此几乎一致，甚至更简单——因为 gRPC 的输出不必像本例这样和 Iris（HTTP 框架）做结合。

## 总结

本讲落地了 Thrift 服务端的业务实现：通过把抽奖逻辑抽离为 `LuckyApi.luckyDo` 实现 Web 与 RPC 复用；`DoLucky` 与 `MyPrizeList` 调用它并把业务模型转换为 Thrift 返回结构。可见 RPC 开发的主要工作量在于类型转换而非业务逻辑。
