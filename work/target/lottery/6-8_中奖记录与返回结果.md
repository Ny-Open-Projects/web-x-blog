# Go 企业级抽奖项目: 中奖记录和返回结果

## 纲要

- 中奖后要把记录持久化到 `lt_result`，奖品信息以"快照"形式写入，后台改奖品也不影响历史记录。
- 中奖记录字段包含奖品 ID / 名称 / 类型 / 用户 / 编码 / IP / 时间等。
- 隐藏规则：中了**实物大奖**（`GtypeGiftLarge`）的用户及其当前 IP，要被设为黑名单一段时间（工程默认 30 天），让其"关小黑屋"。
- 黑名单写入 `prizeLarge`：用户写 `lt_user.Blacktime`，IP 写 `lt_blackip.Blacktime`，不存在则 `Create`、已存在则 `Update`。
- 基础 MySQL 版本到此形成完整闭环；后续章节在此基础上做 Redis 缓存优化（数据库是性能瓶颈）。

## 保存中奖记录

无论是否中奖，最终返回结构都要一致（都含 `code` / `msg`）。中奖时先把奖品信息快照写入 `lt_result`，因为后台可以改奖品，而历史中奖记录里的奖品描述不应随之变化（`web/controllers/index_lucky_api.go`）：

```go
// 步骤11：记录中奖记录
result := models.LtResult{
	GiftId:     prizeGift.Id,
	GiftName:   prizeGift.Title,
	GiftType:   prizeGift.Gtype,
	Uid:        uid,
	Username:   username,
	PrizeCode:  prizeCode,
	GiftData:   prizeGift.Gdata,
	SysCreated: comm.NowUnix(),
	SysIp:      ip,
	SysStatus:  0,
}
if err := services.NewResultService().Create(&result); err != nil {
	log.Println("index_lucky GetLucky ServiceResult.Create", result, ", error=", err)
	return 209, "很遗憾，没有中奖，请下次再试", nil
}
```

`lt_result` 表结构（`models/lt_result.go`）：

```go
type LtResult struct {
	Id         int    `xorm:"not null pk autoincr INT(10)" json:"-"`
	GiftId     int    `xorm:"not null default 0 comment('奖品ID') INT(10)" json:"gift_id"`
	GiftName   string `xorm:"not null default '' comment('奖品名称') VARCHAR(255)" json:"gift_name"`
	GiftType   int    `xorm:"not null default 0 comment('奖品类型') INT(10)" json:"gift_type"`
	Uid        int    `xorm:"not null default 0 comment('用户ID') INT(10)" json:"uid"`
	Username   string `xorm:"not null default '' comment('用户名') VARCHAR(50)" json:"username"`
	PrizeCode  int    `xorm:"not null default 0 comment('抽奖编号(4位随机数)') INT(10)" json:"-"`
	GiftData   string `xorm:"not null default '' comment('获奖信息') VARCHAR(255)" json:"-"`
	SysCreated int    `xorm:"not null default 0 comment('创建时间') INT(10)" json:"-"`
	SysIp      string `xorm:"not null default '' comment('用户抽奖IP') VARCHAR(50)" json:"-"`
	SysStatus  int    `xorm:"not null default 0 comment('状态，0正常，1删除，2作弊') SMALLINT(5)" json:"-"`
}
```

`ResultService.Create` 直接透传到 `ResultDao.Create`（XORM `Insert`），返回错误即记日志并返回 `209`。

## 实物大奖的黑名单惩罚

若本次中的是实物大奖（`conf.GtypeGiftLarge`），需要把该用户及其 IP 拉入黑名单一段时间，让其"关小黑屋"。工程默认 30 天：`blackTime = 30 * 86400`。

`prizeLarge` 逻辑（`web/controllers/index_lucky_11prizelarge.go`，与讲稿逻辑一致）：

```go
func (api *LuckyApi) prizeLarge(ip string,
	uid int, username string,
	userinfo *models.LtUser,
	blackipInfo *models.LtBlackip) {

	userService := services.NewUserService()
	blackipService := services.NewBlackipService()
	nowTime := comm.NowUnix()
	blackTime := 30 * 86400

	// 用户黑名单：不存在则创建，已存在则更新 Blacktime
	if userinfo == nil || userinfo.Id <= 0 || userinfo.Username == "" {
		userinfo = &models.LtUser{
			Id:         uid,
			Username:   username,
			Blacktime:  nowTime + blackTime,
			SysCreated: nowTime,
			SysIp:      ip,
		}
		userService.Create(userinfo)
	} else {
		userinfo = &models.LtUser{
			Id:         uid,
			Blacktime:  nowTime + blackTime,
			SysUpdated: nowTime,
		}
		userService.Update(userinfo, nil)
	}

	// IP黑名单：同理
	if blackipInfo == nil || blackipInfo.Id <= 0 {
		blackipInfo = &models.LtBlackip{
			Ip:         ip,
			Blacktime:  nowTime + blackTime,
			SysCreated: nowTime,
		}
		blackipService.Create(blackipInfo)
	} else {
		blackipInfo.Blacktime = nowTime + blackTime
		blackipInfo.SysUpdated = nowTime
		blackipService.Update(blackipInfo, nil)
	}
}
```

主流程中触发：

```go
if prizeGift.Gtype == conf.GtypeGiftLarge {
	// 获得实物大奖，将用户、IP 设为黑名单一段时间
	api.prizeLarge(ip, uid, username, userInfo, blackipInfo)
}
```

> 说明：即便被拉黑，该用户 / IP 仍可以正常抽小奖、优惠券、虚拟币等，只是"一段时间内无法再中实物大奖"，对体验影响很小。

## 返回结果

最后一步把结果返回给调用方（`luckyDo` 末尾）：

```go
// 步骤12：返回抽奖结果
return 0, "", prizeGift
```

`prizeGift` 是 `*ObjGiftPrize`，经由 `GetLucky` 写入 `rs["gift"]` 序列化返回。整个基础 MySQL 版本至此形成完整闭环。

## 基础版本的瓶颈

运行验证时可以看到：中奖概率、库存递减、黑名单等都符合预期。但完全依赖 MySQL，数据库本身会成为最大瓶颈——并发与性能都偏弱。后续章节正是围绕"用 Redis 缓存把数据库隔离"来做优化（奖品全量缓存、用户 / IP 部分缓存、奖品池等）。

## API 速览

| 方法 / 常量 | 包 | 说明 |

| `UserService.Create/Update` | `services` | 更新 `lt_user.Blacktime` |

| `conf.GtypeGiftLarge` | `conf` | 实物大奖类型值，触发黑名单惩罚 |
