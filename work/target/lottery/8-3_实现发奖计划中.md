# Go 企业级抽奖项目: 实现发奖计划（中）

## 纲要

- `clearGiftPrizeData`：构造空的发奖计划写回数据库，并把奖品池数量置 0；更新空字段时必须显式指定 `columns`。
- `setGiftPool`：把奖品池库存写入 Redis，使用 Hash 结构，key 为 `gift_pool`，field 为奖品 ID（`HSET`）。
- `PrizeDataRandomDayTime`：在 `conf/project.go` 中定义的 24 小时权重数组（长度 100），用于区分高峰/低谷时段。
- `getGiftPrizeDataOneDay`：把一个奖品数量合理分配到「24 小时」再到「60 分钟」，数量多时按权重精确分摊，数量少或余数用随机概率分摊。

## 清空旧发奖计划

当奖品不该再走发奖计划时（状态异常、时间不对、库存不足等），需要把旧的 `PrizeData` 清空，并把奖品池数量置 0：

```go
// 清空奖品的发放计划
func clearGiftPrizeData(giftInfo *models.LtGift, giftService services.GiftService) {
	info := &models.LtGift{
		Id:        giftInfo.Id,
		PrizeData: "",
	}
	err := giftService.Update(info, []string{"prize_data"})
	if err != nil {
		log.Println("prizedata.clearGiftPrizeData giftService.Update",
			info, ", error=", err)
	}
	setGiftPool(giftInfo.Id, 0)
}
```

这里有一个容易踩的坑：**要强制把一个字段更新成空值，必须显式传入 `columns`（如 `[]string{"prize_data"}`）**。否则 ORM 在做更新时通常会忽略零值/空值字段，导致空数据写不进库，旧计划残留。

## 设置奖品池数量（Redis Hash）

奖品池库存存在 Redis 里，key 固定为 `gift_pool`，是一个 Hash，field 是奖品 ID，value 是该奖品在池中的剩余数量：

```go
// 设置奖品池的数量，redis缓存
func setServGiftPool(id, num int) {
	key := "gift_pool"
	cacheObj := datasource.InstanceCache()
	_, err := cacheObj.Do("HSET", key, id, num)
	if err != nil {
		log.Println("prizedata.setServGiftPool error=", err)
	}
}
```

后续发奖时对这个 Hash 做 `HINCRBY` 递减，填充服务做 `HINCRBY` 递增，全部基于 Redis 原子命令，天然规避并发安全问题。

## 24 小时权重配置

要把奖品分配到一天的不同时段，先得有「每个小时发奖机会大小」的预设。项目在 `conf/project.go` 用一个长度为 100 的数组来表达 100% 的概率分布：

```go
// 定义24小时的奖品分配权重
var PrizeDataRandomDayTime = [100]int{
	// 24 * 3 = 72   平均3%的机会
	// 100 - 72 = 28 剩余28%的机会
	// 7 * 4 = 28    剩下的分别给7个时段增加4%的机会
	0, 0, 0,
	1, 1, 1,
	2, 2, 2,
	// ... 每个基础时段 3 个名额（3%）
	9, 9, 9, 9, 9, 9, 9,       // 9 点高峰 +4%
	10, 10, 10, 10, 10, 10, 10, // 10 点高峰 +4%
	// ...
	20, 20, 20, 20, 20, 20, 20, // 20 点高峰 +4%
	21, 21, 21, 21, 21, 21, 21, // 21 点高峰 +4%
	22, 22, 22,
	23, 23, 23,
}
```

设计思路：

- 24 个小时各给 3 个基础名额，合计 72%（平均 3% 的机会）。
- 剩下 28% 分配给 7 个高峰时段（9、10、15、16、17、20、21 点），每个再加 4 个名额。
- 数组长度是 100，所以 `conf.PrizeDataRandomDayTime[随机索引]` 就能按权重「随机落到某个小时」——某个小时在数组里出现的次数越多，它被抽中的概率就越大。

这套配置可以根据自身业务访问特征调整：如果你的站点深夜活跃，就把权重集中到凌晨。

## 一天内的分配：getGiftPrizeDataOneDay

核心是把一个数量 `num` 分配到 `[hour][minute]num` 的两层结构里：

```go
// 将给定的奖品数量分布到这一天的时间内
// 结构为： [hour][minute]num
func getGiftPrizeDataOneDay(num int) map[int][60]int {
	rs := make(map[int][60]int)
	hourData := [24]int{}
	// 分别将奖品分布到24个小时内
	if num > 100 {
		// 奖品数量多的时候，直接按照百分比计算出来
		for _, h := range conf.PrizeDataRandomDayTime {
			hourData[h]++
		}
		for h := 0; h < 24; h++ {
			d := hourData[h]
			n := num * d / 100
			hourData[h] = n
			num -= n
		}
	}
	// 奖品数量少的时候，或者剩下了一些没有分配，需要用到随机概率来计算
	for num > 0 {
		num--
		// 通过随机数确定奖品落在哪个小时
		hourIndex := comm.Random(100)
		h := conf.PrizeDataRandomDayTime[hourIndex]
		hourData[h]++
	}
	// 将每个小时内的奖品数量分配到60分钟
	for h, hnum := range hourData {
		if hnum <= 0 {
			continue
		}
		minuteData := [60]int{}
		if hnum >= 60 {
			avgMinute := hnum / 60
			for i := 0; i < 60; i++ {
				minuteData[i] = avgMinute
			}
			hnum -= avgMinute * 60
		}
		// 剩下的数量不多的时候，随机到各分钟内
		for hnum > 0 {
			hnum--
			m := comm.Random(60)
			minuteData[m]++
		}
		rs[h] = minuteData
	}
	return rs
}
```

算法拆解：

- **数量大（num > 100）**：用权重精确分摊。先把 100 个权重位置展开到 `hourData` 上，再按 `num * d / 100` 算出每小时应得数量，并递减剩余 `num`。这部分是确定性分配，保证整体比例贴合权重。
- **随机兜底**：无论大数量的余数，还是小数量的全部，都走 `comm.Random(100)` 取一个权重索引，落到对应小时并 +1。这一步保证「所有奖品都必须被发出去」且按概率分布。
- **小时 → 分钟**：对每小时的数量，若 ≥ 60 则先按平均 `hnum/60` 填到每分钟，余数再随机撒到各分钟；若 < 60 则全部随机到 60 分钟里的某些分钟。

这样每一天的「每小时、每分钟」奖品数量就都算出来了。
