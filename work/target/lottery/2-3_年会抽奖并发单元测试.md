# Go 企业级抽奖项目: 年会抽奖并发单元测试

## 纲要

- 用 `iris/httptest` 对 Web 应用做接口级测试，无需启动独立进程
- 用 `sync.WaitGroup` 启动 100 个协程并发调用 `/import`
- 线程不安全时预期导入 100 人，实际仅 97 人，暴露数据竞争
- 协程内引用循环变量必须通过参数传入，否则存在竞态

## 为什么需要并发测试

上一节的年会抽奖程序用浏览器刷新或 curl 脚本测试，都只是"顺序"场景，无法复现并发问题。要验证共享切片 `userList` 在并发写入下是否安全，需要编写单元测试，真正并发地打接口。

## 测试实现要点

Iris 提供了 `httptest` 工具，可以在测试中直接持有应用实例并发起请求，非常方便。测试思路：

1. 先请求首页，断言返回 `当前总共参与抽奖的用户数: 0`，确认初始为空。
2. 用 `sync.WaitGroup` 启动 100 个协程，每个协程并发 `POST /import` 一个不同用户。
3. 等待所有协程结束（`wg.Wait()`）后，再次请求首页，断言用户数应为 `100`。

注意一个关键细节：协程里引用 `for` 循环变量 `i` 必须通过参数传入（`go func(i int){...}(i)`）。如果直接在协程里读外部共享的循环变量，会因为共享变量被并发读写而产生竞态，传入参数则把当时的值"固化"进协程。

## Demo 示例

运行说明：

```bash
cd code/lottery/_demo/annualMeeting
go test -v
```

代码说明（取自 `annualMeeting/main_test.go`）：

```go
package main

import (
	"fmt"
	"sync"
	"testing"

	"github.com/kataras/iris/httptest"
)

func TestMVC(t *testing.T) {
	e := httptest.New(t, newApp())

	var wg sync.WaitGroup
	e.GET("/").Expect().Status(httptest.StatusOK).
		Body().Equal("当前总共参与抽奖的用户数: 0\n")

	// 启动 100 个协程并发执行用户导入，期望最终导入 100 个用户
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func(i int) { // 循环变量通过参数传入，避免竞态
			defer wg.Done()
			e.POST("/import").WithFormField("users", fmt.Sprintf("test_u%d", i)).
				Expect().Status(httptest.StatusOK)
		}(i)
	}

	wg.Wait()

	e.GET("/").Expect().Status(httptest.StatusOK).
		Body().Equal("当前总共参与抽奖的用户数: 100\n")
	e.GET("/lucky").Expect().Status(httptest.StatusOK)
	e.GET("/").Expect().Status(httptest.StatusOK).
		Body().Equal("当前总共参与抽奖的用户数: 99\n")
}
```

## 测试结果

运行后断言失败：期望用户数为 `100`，实际只有 `97`（甚至更少）。原因是 100 个协程并发向 `userList` 执行 `append` 时，存在数据竞争——多个协程同时读写切片底层数组与长度字段，部分写入被覆盖，导致最终数量少于 100。

这明确证明了当前程序是**线程不安全**的。下一节将用互斥锁改造，使其变为线程安全。
