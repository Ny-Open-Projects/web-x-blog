# Go 企业级抽奖项目: 实现奖品池（上）

## 纲要

- `DistributionGiftPool`：遍历所有奖品，按发奖计划把「当前时间及之前应发」的数量放入奖品池，并消费（截断）已执行的计划。
- 入参校验：状态正常、限量奖品、时间在活动区间内、发奖计划长度合法。
- 反序列化 `[][2]int` 计划，按时间顺序累加应发数量，用 `index` 记录消费偏移。
- `incrGiftPool` / `incrServGiftPool`：基于 Redis `HINCRBY` 做原子递增，并对「返回值小于预期」做二次补偿。
- 更新数据库时只写 `prize_data` 列，并在有变更后预加载缓存。

## DistributionGiftPool 主体

项目源码（`web/utils/prizedata.go`）：

```go
// 根据奖品的发奖计划，把设定的奖品数量放入奖品池
// 需要每分钟执行一次
func DistributionGiftPool() int {
	totalNum := 0
	now := comm.NowUnix()
	giftService := services.NewGiftService()
	list := giftService.GetAll(false)
	if list != nil && len(list) > 0 {
		for _, gift := range list {
			// 是否正常状态
			if gift.SysStatus != 0 {
				continue
			}
			// 是否限量产品
			if gift.PrizeNum < 1 {
				continue
			}
			// 时间段是否正常
			if gift.TimeBegin > now || gift.TimeEnd < now {
				continue
			}
			// 计划数据的长度太短，不需要解析和执行
			// 发奖计划，[[时间1,数量1],[时间2,数量2]]
			if len(gift.PrizeData) <= 7 {
				continue
			}
			var cronData [][2]int
			err := json.Unmarshal([]byte(gift.PrizeData), &cronData)
			if err != nil {
				log.Println("prizedata.DistributionGiftPool Unmarshal error=", err)
			} else {
				index := 0
				giftNum := 0
				for i, data := range cronData {
					ct := data[0]
					num := data[1]
					if ct <= now {
						// 之前没有执行的数量，都要放进奖品池
						giftNum += num
						index = i + 1
					} else {
						break
					}
				}
				// 有奖品需要放入到奖品池
				if giftNum > 0 {
					incrGiftPool(gift.Id, giftNum)
					totalNum += giftNum
				}
				// 有计划数据被执行过，需要更新到数据库
				if index > 0 {
					if index >= len(cronData) {
						cronData = make([][2]int, 0)
					} else {
						cronData = cronData[index:]
					}
					// 更新到数据库
					str, err := json.Marshal(cronData)
					if err != nil {
						log.Println("prizedata.DistributionGiftPool Marshal(cronData)", cronData, "error=", err)
					}
					columns := []string{"prize_data"}
					err = giftService.Update(&models.LtGift{
						Id:        gift.Id,
						PrizeData: string(str),
					}, columns)
					if err != nil {
						log.Println("prizedata.DistributionGiftPool giftService.Update error=", err)
					}
				}
			}
		}
		if totalNum > 0 {
			// 预加载缓存数据
			giftService.GetAll(true)
		}
	}
	return totalNum
}
```

## 入参校验

每个奖品都要过四道门槛，任何一道不过就 `continue`：

1. `SysStatus != 0`：不是正常状态（如已删除）。
2. `PrizeNum < 1`：不限量奖品（`0` 或负数），不需要走计划填充。
3. 时间不在 `[TimeBegin, TimeEnd]` 区间内。
4. `PrizeData` 长度 `<= 7`：发奖计划是 `[[t,n],[t,n]]` 形态，时间字符串本身就超过 7 位，长度过短说明是残缺数据，直接跳过解析。

## 按时间顺序消费计划

因为 `ResetGiftPrizeData` 生成计划时保证了有序，这里直接从头遍历即可：

- `ct <= now`：该时间点及其之前应发的，全部累加进 `giftNum`，并把 `index` 推进到 `i+1`。
- `ct > now`：遇到第一个未来时间点就 `break`（后面的更晚，无需再看）。

随后：

- `giftNum > 0`：调用 `incrGiftPool(gift.Id, giftNum)` 把数量放进奖品池，并把本次总量累加进 `totalNum`。
- `index > 0`：说明有已执行的计划需要消费掉。若已消费到末尾则置空，否则用 `cronData[index:]` 截断保留未执行的尾部，序列化后只更新 `prize_data` 列。

## 更新缓存的一致性

当 `totalNum > 0`（本批次确实有奖品被放入池子、且计划数据被改写）时，主动调用一次 `giftService.GetAll(true)` 重建缓存。因为填充服务改写了数据库、使缓存失效，与其等下一次查询被动回源，不如在这里显式预加载一次——定时服务环境并发压力不高，这点开销可以接受，但能把「缓存重建」这件事处理得干净。

## incrGiftPool：原子递增与二次补偿

往奖品池增加库存，本质是对 Redis Hash `gift_pool` 做 `HINCRBY`：

```go
// 根据计划数据，往奖品池增加奖品数量
func incrGiftPool(id, num int) int {
	return incrServGiftPool(id, num)
}

// 往奖品池增加奖品数量，redis缓存，根据计划数据
func incrServGiftPool(id, num int) int {
	key := "gift_pool"
	cacheObj := datasource.InstanceCache()
	rtNum, err := redis.Int64(cacheObj.Do("HINCRBY", key, id, num))
	if err != nil {
		log.Println("prizedata.incrServGiftPool error=", err)
		return 0
	}
	// 保证加入的库存数量正确的被加入到池中
	if int(rtNum) < num {
		// 加少了，补偿一次
		num2 := num - int(rtNum)
		rtNum, err = redis.Int64(cacheObj.Do("HINCRBY", key, id, num2))
		if err != nil {
			log.Println("prizedata.incrServGiftPool2 error=", err)
			return 0
		}
	}
	return int(rtNum)
}
```

关键点：

- **原子性**：`HINCRBY` 是 Redis 单命令原子操作，单条递增/递减不存在并发竞态。
- **二次补偿**：`HINCRBY` 返回的是递增后的「当前值」。如果因为并发发奖把库存减到负数，再递增值可能仍小于预期增量 `num`。此时 `int(rtNum) < num` 成立，就用 `num - rtNum` 的差额再做一次 `HINCRBY`，把欠的库存补上。
- 发奖侧的递减 `prizeServGift` 同样用 `HINCRBY key id -1`，返回 `< 0` 即视为池中已无库存、本次不能发奖。两者配合，保证奖品「有节奏、不超发」。
