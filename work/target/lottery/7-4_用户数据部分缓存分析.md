# Go 企业级抽奖项目: 单个用户数据部分缓存分析

## 纲要

- 用户数据不适合全量缓存：数量大、更新频率高于奖品，因此改为**单个用户数据**缓存。
- 数据结构选型：使用 Redis `hash`（`HGETALL` / `HMSET`），可按字段部分读写，免 JSON 序列化。
- 代码改动范围：`userService` 新增 `getByCache`、`setByCache`、`updateByCache` 三个方法。
- 复用同一套缓存骨架：`Get` 走缓存优先 + 未命中回源（并写入空对象防穿透），写操作先删缓存再写库。
- 与奖品全量缓存的差异：奖品是整体 `string`，用户是单条 `hash`；用户数据无 `GetAll`/`CountAll` 缓存，因为只处理单条。

## 为什么用户数据不做全量缓存

奖品数据「少且稳定」，可以整体塞进一个 `string`。但用户数据有两个相反特征：

1. **数量多**：用户表规模远大于奖品表，全量缓存内存与网络成本高。
2. **更新相对频繁**：用户状态、黑名单时间等会在请求链路中被修改。

因此只对「单个用户」做缓存：业务里几乎只按 UID 读取单个用户，命中率高，且缓存体积可控。

## 为什么用 hash 而不是 string

奖品用 `string` 是因为整体序列化最省事；用户数据改用 `hash` 是因为：

- `hash` 可以只读取或只更新需要的若干字段，不必每次都做 JSON 序列化/反序列化。
- 单条用户数据的字段更新（如 `Blacktime`）可以局部完成，减少传输量。

对应的 Redis 命令是 `HGETALL`（读全部字段）与 `HMSET`（多字段写入），以及失效用的 `DEL`。

## 缓存方法规划

`userService` 新增三个方法，与奖品缓存逻辑同构，仅数据结构和 key 拼接方式不同：

- `getByCache(id int) *models.LtUser`：用 `info_user_<id>` 作为 key，`HGETALL` 读取并转换。
- `setByCache(data *models.LtUser)`：把模型字段拼成 `HMSET` 参数写入。
- `updateByCache(data, columns)`：删除 `info_user_<id>` 这个 key。

## 一致性策略与防穿透

用户缓存同样遵循「先删缓存再写库」。但在 `Get` 路径上多做了一件事：**数据库也没有时，构造一个仅含 ID 的空对象写入缓存**，避免后续每次都击穿到数据库。

## 与奖品缓存的对比

| 维度 | 奖品全量缓存 | 用户单条缓存 |
| --- | --- | --- |
| 数据结构 | `string`（JSON） | `hash` |
| 缓存粒度 | 全部奖品一个 key | 每个用户一个 key |
| 读取命令 | `GET` | `HGETALL` |
| 写入命令 | `SET` | `HMSET` |
| 失效命令 | `DEL` | `DEL` |
| 是否缓存列表 | 是（`GetAll`/`CountAll`） | 否（仅单条 `Get`） |

## API 速览

| 方法 | 命令 | key 形式 |
| --- | --- | --- |
| `getByCache` | `HGETALL` | `info_user_<id>` |
| `setByCache` | `HMSET` | `info_user_<id>` |
| `updateByCache` | `DEL` | `info_user_<id>` |

> 项目源码使用 `github.com/gomodule/redigo/redis` 的 `rds.Do("HGETALL"|"HMSET"|"DEL", ...)`；下方 Demo 改用 `go-redis/v9`。
