# Go 企业级抽奖项目: IP 黑名单数据缓存分析

## 纲要

- IP 黑名单缓存与用户数据缓存**高度同源**：都是单条数据缓存，都用 Redis `hash` 结构。
- 唯一区别：用户缓存以 UID 为 key 组件，IP 黑名单以 **IP 字符串** 为 key 组件。
- 代码改动范围：`blackipService` 新增 `getByCache`、`setByCache`、`updateByCache` 三个方法。
- 读取入口是 `GetByIp(ip)`：内存/缓存优先，未命中回源，库无则写空对象防穿透。
- 写操作（`Update`）同样「先删缓存，再写数据库」。
- 本章作为单条 hash 缓存的复习，代码逻辑与前一节 `userService` 几乎一致。

## 与用户缓存的异同

| 维度 | 用户缓存 | IP 黑名单缓存 |
| --- | --- | --- |
| key 组件 | UID（整数） | IP（字符串） |
| key 形式 | `info_user_<id>` | `info_blackip_<ip>` |
| 数据结构 | `hash` | `hash` |
| 读取命令 | `HGETALL` | `HGETALL` |
| 写入命令 | `HMSET` | `HMSET` |
| 失效命令 | `DEL` | `DEL` |
| 读取入口 | `Get(id)` | `GetByIp(ip)` |

可以看到，除了 key 的拼装字段不同、读取入口方法名不同，其余实现完全同构。因此本节在源码层面直接复用前一套范式，无需重新讲解命令细节。

## 为什么用 hash 缓存黑名单

IP 黑名单同样是「按 IP 单条查询」的场景：每次抽奖请求都要判断来源 IP 是否在黑名单内。用 `hash` 可以按字段读取（`Ip`、`Blacktime`、`SysCreated`、`SysUpdated`），无需整体 JSON 序列化，与用户缓存保持一致的工程范式，便于维护。

## 一致性策略

与前面的奖品、用户缓存一致：写操作 `Update` 先 `updateByCache` 删缓存，再 `dao.Update` 写库；`GetByIp` 在缓存/数据库都未命中时，构造一个仅含 `Ip` 的空对象写回，防止缓存穿透。

## API 速览

| 方法 | 命令 | key 形式 |
| --- | --- | --- |
| `getByCache(ip)` | `HGETALL` | `info_blackip_<ip>` |
| `setByCache(data)` | `HMSET` | `info_blackip_<ip>` |
| `updateByCache(data)` | `DEL` | `info_blackip_<ip>` |
| `GetByIp(ip)` | 组合调用 | 缓存优先 + 回源 |
