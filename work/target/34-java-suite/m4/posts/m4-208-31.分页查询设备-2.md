# 亿可控设备分页查询收官：布尔组合条件、分页排序与结果封装

分页查询设备的需求上一篇已经梳理完：设备管理与数据详情两个页面共用一个底层方法，条件是设备编号、标签，数据详情多一个状态。本篇把这条实现走完——repository 里条件、分页、排序一次配齐，查询结果封装成 Pager 返回，service 与 controller 补上 GET 问号传参的接口，最后造出五条测试数据，实测标签筛选。

## 先给结论

- 方法签名 searchDevice(page, pageSize, deviceId, tags, state)，返回自定义的 Pager<DeviceDTO>（com.eco.vo 包下的分页类，属性有总条数、每页条数、总页数、当前页数、当前页数据）。
- 多条件用 BoolQueryBuilder 组合，must 相当于查询语句里的 and；设备编号用 wildcardQuery(deviceId + "*") 匹配开头，标签用 wildcardQuery("*" + tags + "*") 类似 like %x%，两个条件都要先过 Strings.isNullOrEmpty 判断。
- state 不是索引库里的 status（那是设备开关），它是综合值：0 在线、1 离线、2 一般告警、3 严重告警，分别换算成对 online 或 level 字段的 termQuery。
- 分页三句话：from((page-1)*pageSize)、size(pageSize)、trackTotalHits(true)——最后一个保证分页结果里也能拿到全部记录数；排序按 level 降序，告警级别高的排前面。
- 结果封装：search 拿到 SearchResponse，getHits().getHits() 得到 SearchHit 数组，逐条 getSourceAsString 反序列化成 DeviceDTO 收进 List，new Pager(count, pageSize) 后 setItems 返回，异常 log.error 返回 null。
- controller 用 @GetMapping 问号传参，@RequestParam 全部 required = false，page 默认 1、pageSize 默认 10；设备管理页没有 state 条件，调用 service 时传 null。

## 条件构建：布尔查询把三个条件装进 must

ESRepository 里定义 searchDevice，返回值用 Pager——项目自己提供的分页结果类，泛型指明元素类型 DeviceDTO。第一个参数是页码 page，第二个是页大小 pageSize，这就是分页本身；后面跟条件：deviceId 设备编号、tags 查询标签、state 状态。

SearchRequest 指定要查的 devices 索引；真正干活的是 SearchSourceBuilder，它是一次查询的总封装——条件、分页、排序全部加在它身上，最后通过 searchRequest.source(sourceBuilder) 传进去，等于告诉这次查询按什么条件、怎么分页、怎么排序走。

三个条件用布尔查询组合。must 相当于 and 关系：

```java
BoolQueryBuilder boolQueryBuilder = QueryBuilders.boolQuery();
// 设备编号：匹配开头的模糊搜索
if (!Strings.isNullOrEmpty(deviceId)) {
    boolQueryBuilder.must(QueryBuilders.wildcardQuery("deviceId", deviceId + "*"));
}
// 标签：包含匹配
if (!Strings.isNullOrEmpty(tags)) {
    boolQueryBuilder.must(QueryBuilders.wildcardQuery("tag", "*" + tags + "*"));
}
```

设备编号的需求是匹配开头的模糊搜索：传 a，所有以 a 开头的设备都要查出来，通配符只加在尾部。标签是全字符包含匹配，前后都加星——传「商」，标签里含「商」的都能查到，相当于 SQL 里 like %商% 的形式。两个条件都要先判断非 null 且非空串，没传就不加这条。

状态条件最绕。state 有四个值，但索引库里并不直接存它：在线离线对应 online 字段，告警对应告警级别 level 字段，所以要做换算——0 在线是 termQuery("online", true)，1 离线是 termQuery("online", false)，2 一般告警是 termQuery("level", 1)，3 严重告警是 termQuery("level", 2)。在线本身包含告警设备，告警也是一种在线状态：

```java
if (state != null) {
    if (state.intValue() == 0) {
        boolQueryBuilder.must(QueryBuilders.termQuery("online", true));
    } else if (state.intValue() == 1) {
        boolQueryBuilder.must(QueryBuilders.termQuery("online", false));
    } else if (state.intValue() == 2) {
        boolQueryBuilder.must(QueryBuilders.termQuery("level", 1));
    } else if (state.intValue() == 3) {
        boolQueryBuilder.must(QueryBuilders.termQuery("level", 2));
    }
}
```

条件齐了装进 sourceBuilder，接着配分页与排序：

```java
sourceBuilder.query(boolQueryBuilder);
sourceBuilder.from((page.intValue() - 1) * pageSize.intValue());
sourceBuilder.size(pageSize.intValue());
sourceBuilder.trackTotalHits(true);
sourceBuilder.sort("level", SortOrder.DESC);
searchRequest.source(sourceBuilder);
```

from 表示从哪一条索引开始查：传 0 从第一条开始，传 9 从第十条开始。参数传过来的是页码，所以要换算——页码减 1 乘页大小。size 就是页大小。trackTotalHits 传 true 的意思是：即便是分页结果，也要把这次查询的所有记录数查出来，前端翻页算总页数靠它。排序一句话：按告警级别 level 倒序，保证告警级别高的排在前面。至此条件查询、分页、排序全部配完。

## 执行查询与 Pager 封装

方法后半段是执行与封装。还是 RestHighLevelClient 的 search(searchRequest, RequestOptions.DEFAULT)，返回 SearchResponse，所有查询结果都在里面。提取分三步：getHits() 拿到 SearchHits；SearchHits 上再调 getHits() 得到 SearchHit 数组，一个 SearchHit 就是一条记录；循环里 hit.getSourceAsString() 取出 JSON 字符串（也可以用 getSourceAsMap 拿 Map，这里选字符串），用 JsonUtil 工具类转成 DeviceDTO，塞进集合：

```java
SearchResponse searchResponse = restHighLevelClient.search(searchRequest, RequestOptions.DEFAULT);
SearchHit[] searchHits = searchResponse.getHits().getHits();
List<DeviceDTO> devices = Lists.newArrayList();
for (SearchHit hit : searchHits) {
    String hitResult = hit.getSourceAsString();
    DeviceDTO deviceDTO = JsonUtil.parseBean(hitResult, DeviceDTO.class);
    devices.add(deviceDTO);
}
```

最终返回的是 Pager。Pager 提供了接收 count 和 pageSize 两个参数的构造方法，直接用构造方法构建，总记录数从 searchResponse.getHits().getTotalHits().value 拿；再把集合装进去 pager.setItems(devices)，return pager。异常分支 catch IOException，log.error 查询设备失败，返回 null。最后补注释：这是分页查询设备，参数依次是页码、页大小、设备编号、标签、状态。

## 服务层一行调用，控制层问号传参

服务层简单：DeviceService 定义 queryPage(page, pageSize, deviceId, tags, state)，返回 Pager<DeviceDTO>，实现类直接调 esRepository.searchDevice，参数原样透传。

控制层先看 API 文档「查询设备列表」：page、pageSize、sn、tag 都是可选参数——sn 就是底层的 deviceId，前端封装时按 sn 命名；请求参数标的是 query，即问号传参；返回是与 Pager 结构一致的分页数据。据此写 controller 方法 findPage：

```java
@GetMapping
public Pager<DeviceDTO> findPage(
        @RequestParam(value = "page", required = false, defaultValue = "1") Integer page,
        @RequestParam(value = "pageSize", required = false, defaultValue = "10") Integer pageSize,
        @RequestParam(value = "sn", required = false) String sn,
        @RequestParam(value = "tag", required = false) String tag) {
    return deviceService.queryPage(page, pageSize, sn, tag, null);
}
```

每个参数前面加 @RequestParam：value 必须和文档里的参数名一致；required = false 表示不是必传参数；defaultValue 提供缺省值——page 不传按 1，pageSize 不传按 10。调用 service 时 state 传 null：这个方法对应的是设备管理页，它没有状态条件；数据详情页的状态筛选，后面会基于这个需求再做代码叠加，眼下先实现设备管理的列表。

## 造数实测：五条数据按标签筛选

测试之前索引库里只有一条记录，先用之前写的 testAdd 改造出四条新数据：一条告警、标签学校、级别 1、告警名称温度告警；一条湿度告警、级别 2、标签商场；一条不告警但离线、级别 0；一条在线告警、温度告警、级别 1、标签商场。连同原来的 123456，一共五条，跑完测试后到 Kibana 查询确认总数是 5。

启动工程，在脚本里找到「获取设备列表」这段测试代码，它用问号传参的方式指定条件。先传标签为学校，返回里学校标签的数据出来了；再把条件换成商场，商场的结果也出来了。条件、分页、排序、封装到 GET 接口，整条分页查询链路验证完成。

## 小结

分页查询五讲至此收官，设备管理列表页的底层实现、服务层、控制层与接口测试全部走通。

- SearchSourceBuilder 是一次查询的总封装：条件、分页、排序在它身上配好，再 source 进 SearchRequest。
- 三个条件走 BoolQueryBuilder 的 must（and 关系）：编号通配符尾部加星、标签前后加星、state 四值换算成 online/level 的 termQuery，空条件一律跳过。
- from = (page-1)*pageSize，size = pageSize，trackTotalHits(true) 保证总条数可取，sort 按 level 降序让告警靠前。
- 结果封装三板斧：SearchHit.getSourceAsString 反序列化进 List，new Pager(count, pageSize) 加 setItems；异常 log 后返回 null。
- controller 的 GET 接口问号传参，@RequestParam 的 value 对齐文档参数名（sn 对应底层 deviceId），required = false 加 defaultValue（page=1、pageSize=10），state 暂传 null 留给数据详情页。
