# 账户资金总览收官：昨收价获取、当日持仓盈亏计算、交易时间控制与全链路验证

账户资金总览是智牛股第十六章的收尾工程。前面已经把资金服务搭好、接口数据结构定义完，业务层主接口 `getFinanceOverview` 也实现了账户概要信息的计算，这一部分要把剩下的关联逻辑补齐：昨收价怎么取、当日持仓盈亏怎么算、昨收价怎么在收盘时自动生成，最后经由代理服务转发、客户端模拟终端调用，用真实波动的行情数据做一次端到端验证。

## 先给结论

- 昨收价获取采用"缓存优先、数据库兜底"：先从 Redis 缓存 `STOCK_QUOTE_CLOSE_PRICE_LAST_KEY` 里取，取不到再查数据库昨天最后一口报价，再取不到就置 0 兜底。
- 缓存里的昨收价是"收盘价|日期"的拼接字符串，用 `split("\\|")` 分割后取第一段；竖线是正则关键字，必须转义。
- 当日持仓盈亏由三部分组成：原持仓收益 + 当日卖出收益 + 当日买入收益，核心变量是"最新价 − 昨收价"这个价差，所有平台都无法保证它 100% 精确，因为最新价一直在变。
- 第三方行情服务通常不标记收盘价，所以昨收价要靠交易时间自行判断生成：在收盘时间上再加 5 分钟缓冲窗口，确保能收到真正的最后一口报价。
- 昨收价缓存只维护"当天"和"昨日"两份，用日期标记防止 5 分钟缓冲期内的重复更新，既不会缓存泛滥，也不会横跨两个交易日。
- 全链路验证结果：中国平安跌 2 分、美的集团跌 6 分，手工核算的盈亏差值 −474336 与资金总览返回的差值完全一致。

## 昨收价的获取：缓存优先，数据库兜底

昨收价是计算当日持仓盈亏的基准，获取逻辑封装在业务层的私有方法 `getStockQuoteClose` 里，入参是股票产品 ID，返回 `Long` 型收盘价。讲义里明确了两点：昨收价从缓存获取；缓存的数据格式由"收盘价 + 日期"组成，中间用竖线分割。为什么是这个格式，要到后面讲昨收价生成机制时才揭晓，这里先专注"取"。

```java
private Long getStockQuoteClose(Long stockId) {
    Long closePrice = null;
    // 昨日收盘价缓存
    Cache lastPriceCache = redisCacheManager.getCache(GlobalConstants.STOCK_QUOTE_CLOSE_PRICE_LAST_KEY);
    Cache.ValueWrapper quoteLastWrapper = lastPriceCache.get(stockId);
    if (null != quoteLastWrapper) {
        // 格式：收盘价|日期
        String closePriceStr = (String) quoteLastWrapper.get();
        closePrice = Long.valueOf(closePriceStr.split("\\|")[0]);
    } else {
        // 缓存未取到，查数据库：昨日 00:00:00 至今日 00:00:00
        closePrice = tradeQuoteDao.getLastPrice(stockId, DateUtils.getLastDayTime(), DateUtils.getCurDay());
    }
    if (null == closePrice) {
        closePrice = 0L;
    }
    return closePrice;
}
```

几个容易踩坑的细节：

| 细节 | 说明 |
| --- | --- |
| 竖线转义 | `String.split` 的参数是正则表达式，`|` 是正则关键字，必须写成 `\\|`，分割后取下标 0 就是收盘价 |
| 时间范围 | 比如今天是 8 月 22 号，查询区间就是 2019-08-21 00:00:00 到 2019-08-22 00:00:00，只指定前一天日期，时间点全部默认为零，由 `DateUtils` 工具生成时间戳 |
| 倒序取值 | 数据库接口 `getLastPrice` 对应的 SQL 做了倒序处理，目的是拿到昨天最后一口行情报价作为收盘价 |
| 置 0 兜底 | 数据库也没查到时重置为 0。实际这种情况几乎不会出现——它意味着服务刚启动、还没收到任何行情报价；做判空是为了后面计算时不抛空指针 |

## 当日持仓盈亏：三段收益的公式与实现

当日浮动盈亏的计算公式由三部分组成，先用表格把它钉死：

| 组成部分 | 公式 |
| --- | --- |
| 买入收益 | Σ（最新价格 − 成交价格）× 买入数量 |
| 卖出收益 | Σ（成交价格 − 昨日收盘价）× 卖出数量 |
| 原持仓数量 | 当前持仓数量 + 当日卖出数量 − 当日买入数量 |
| 原持仓收益 | 原持仓数量 ×（最新价格 − 昨日收盘价） |
| 当日持仓盈亏 | 原持仓收益 + 卖出收益 + 买入收益 |

注意"原持仓数量"的反推方式：当前仓位里已经混入了今天的买卖，把今天卖掉的加回来、今天买入的减掉，才得到昨天收盘时点的持仓基数。实现上对应 `calcTodayTradeDealProfits` 方法，入参有四个：按股票 ID 分组的当日成交记录、最新行情报价、持仓记录、昨收价。

```java
private long calcTodayTradeDealProfits(Map<Long, List<TradeDeal>> groupByDeals,
                                       TradeStockQuoteLast quoteLast,
                                       TradePosition position, long lastClosePrice) {
    long buyProfits = 0, buyVolumes = 0, sellProfits = 0, sellVolumes = 0;
    List<TradeDeal> tradeDeals = groupByDeals.get(position.getStockId());
    if (null != tradeDeals) {
        for (TradeDeal tradeDeal : tradeDeals) {
            if (tradeDeal.getDirection() == GlobalConstants.ORDER_DIRECTION_BUY) {
                // 买入：(最新价 - 成交价) * 买入数量
                long diffPrice = MathUtils.sub(quoteLast.getLastPrice(), tradeDeal.getExecPrice());
                buyProfits += MathUtils.mul(diffPrice, tradeDeal.getExecVolume());
                buyVolumes += tradeDeal.getExecVolume();
            } else {
                // 卖出：(成交价 - 昨收价) * 卖出数量
                long diffPrice = MathUtils.sub(tradeDeal.getExecPrice(), lastClosePrice);
                sellProfits += MathUtils.mul(diffPrice, tradeDeal.getExecVolume());
                sellVolumes += tradeDeal.getExecVolume();
            }
        }
    }
    // 原持仓数量 = 当前持仓 + 卖出数量 - 买入数量
    long initPositionVolume = position.getVolume() + sellVolumes - buyVolumes;
    // 原持仓收益 + 卖出收益 + 买入收益
    long dayProfits = MathUtils.mul(initPositionVolume,
            MathUtils.sub(quoteLast.getLastPrice(), lastClosePrice));
    dayProfits += sellProfits + buyProfits;
    return dayProfits;
}
```

这段实现背后还有几条贯穿全章的设计约束：

- **按产品 ID 分组的原因**：每个用户对每个股票产品只会有一条持仓记录，用户 + 股票产品构成唯一性，所以成交记录可以按产品 ID 分组汇总，逐条持仓独立计算后再累加。
- **一次性查询**：根据账户获取当天全部交易记录时用一次查询完成，减少多次接口查询带来的 IO 开销，这是资金总览接口对处理性能的考虑。
- **PG 的时间类型**：PostgreSQL 的 SQL 查询里时间参数要转换为 Timestamp 类型才能正常查询，这点和之前用日期字符串直接查的写法不一样，由日期工具统一转换。
- **数值精度**：全程用 `MathUtils` 做加减乘，系统内部按长整型计算。也正因为公式里处处用到不断变化的最新价，当日盈亏是个动态值——各交易平台都会提示该数据不保证 100% 精确，各家公式略有差异，只要结果差距不大（几块钱以内）都可以接受。

## 昨收价的生成：交易时间控制与双缓存设计

昨收价是收盘产生的最后一口报价，是当天的最终交易价格。但订阅的第三方实时行情服务并不会标记"这就是收盘价"，所以只能自己根据交易时间判断、生成。

第一步是交易时间范围的控制。每个交易市场的开休市时间不同：A股 9:30 开盘、15:00 休市；港股 9:30 开盘、16:00 休市。这些设置存在股票产品分类表里，对应 `TradeStockCategory` 实体的两个属性：

```java
private Long startMins; // 交易开始时间（分钟）
private Long endMins;   // 交易结束时间（分钟）
```

行情推送侧由 `GlobalSystemConfiguration` 的 `run` 方法起一个无限循环线程，每 3 秒拉取一次有效股票产品的行情。要加交易时间控制，只需在拉取前加一层判断：

```java
if (isopenTime && closediffMins <= 5) {
    // 交易时间内，异步获取产品行情
    taskExecutor.execute(() ->
        marketStockList.parallelStream()
            .forEach(stock -> stockQuoteService.fetchStockQuote(stock, closediffMins)));
}
```

关键在 `closediffMins <= 5` 这个收盘时间差：如果时间恰好卡在交易结束那一秒，最后一口报价可能还没真正到达，进不了内部处理逻辑，昨收价就丢了。所以给一个容错缓冲——不能太长，控制在 5 分钟之内。判断结果 `closediffMins` 还会作为参数一路传给内部逻辑，供后续判断"是否进入收盘价更新窗口"。

第二步是昨收价的缓存生成，这里先想清楚两个被否掉的方案：

| 方案 | 问题 |
| --- | --- |
| 每天生成一份收盘价缓存 | 缓存泛滥，越积越多 |
| 设置 24 小时超时自动回收 | 从交易时间内起算 24 小时会横跨两个交易日，不合适 |
| 设置 48 小时超时 | 能解决泛滥，但系统出问题要过两三天才能发现，修复麻烦 |

最终方案是只维护两份缓存：**昨日收盘价缓存**（key 为股票产品 ID，value 为"收盘价|日期"，带日期是为了防止 5 分钟缓冲窗口造成的频繁覆盖）和**当天收盘价缓存**（key 为股票 ID，value 只存当天收盘价，不需要日期，因为它永远保存当天的值）。做结算、统计报表时这两份都会用到。更新入口在行情服务 `StockQuoteServiceImpl` 的发送实时行情方法里，收盘价窗口期内调用 `updateClosePrice`：

```java
private void updateClosePrice(TradeStockQuoteLast quoteLast) {
    // 判断是否到达收盘时间
    if (isCloseTime(quoteLast.getMarketNo())) {
        Cache curLastPriceCache = redisCacheManager.getCache(GlobalConstants.STOCK_QUOTE_OPEN_PRICE_CUR_KEY);
        Cache lastPriceCache = redisCacheManager.getCache(GlobalConstants.STOCK_QUOTE_CLOSE_PRICE_LAST_KEY);
        if (null != lastPriceCache.get(quoteLast.getStockId())) {
            String lastClosePriceStr = (String) lastPriceCache.get(quoteLast.getStockId()).get();
            String[] lastClosePriceArr = lastClosePriceStr.split("\\|");
            // 日期不等于今天，说明当天首次更新；等于则跳过，避免缓冲期内重复覆盖
            if (!DateUtils.getFmtToday().equals(lastClosePriceArr[1])) {
                Long curLastPrice = (Long) curLastPriceCache.get(quoteLast.getStockId()).get();
                // 昨收价缓存 ← 当天收盘价缓存的值 + 今日日期标记
                lastPriceCache.put(quoteLast.getStockId(),
                        curLastPrice + "|" + DateUtils.getFmtToday());
            }
        } else {
            // 昨收价缓存不存在，直接将当前收盘价放入
            lastPriceCache.put(quoteLast.getStockId(),
                    quoteLast.getLastPrice() + "|" + DateUtils.getFmtToday());
        }
        // 更新当天收盘价缓存
        curLastPriceCache.put(quoteLast.getStockId(), quoteLast.getLastPrice());
    }
}
```

这里的核心是"轮转"：每个交易日收盘时，把昨收价缓存更新成当天收盘价缓存里的值（并盖上当天日期），再把当天收盘价缓存更新为最新收盘价。用讲义里的例子过一遍：10 号收盘价 20.22，此时 cur 为 20.22、last 为 20.12；到 11 号收盘价变为 20.32，轮转后 last 变成 20.22、cur 变成 20.32。日期标记保证 5 分钟缓冲窗口内这段逻辑只生效一次，其余的报价更新直接跳过。

## 代理转发、客户端接入与全链路验证

服务端齐活之后是调用链的补全。代理服务里新增资金服务处理器 `StockFinanceProcessor`，继承抽象父类、实现公用接口，加 `@Service` 注解，通过 `@GrpcClient("grpc-finance-server")` 注入资金服务的 gRPC 客户端；请求处理就是构造携带交易账户 ID 的参数、远程调用资金总览接口、把结果包装为 Netty 响应结构、组装成功报文后经 channel 输出给客户端。接着在处理器工厂 `StockProcessorFactory` 里增加 `GET_FINANCE_OVERVIEW` 到该处理器的分支（处理器名称不能写错，否则无法正常路由），并在 `bootstrap-dev.yml` 中仿照行情、挂单等服务的配置增加 `grpc-finance-server` 一项，服务名与资金服务的 `finance` 保持一致，走 `discovery://` 服务发现。

客户端模拟终端的接入更简单：`BusinessHandler` 下追加 `getAccountFinanceSummary` 调用，不需要传任何业务参数，只需标示接口名；交互菜单增加编号 7 的菜单项，指令处理里把 7 号指令映射到该接口，响应输出里对 `GET_FINANCE_OVERVIEW` 的返回直接打印——它是单个对象而不是集合。

验证环节做了一处务实调整：实时行情价格变化太小，不利于对比，所以改用模拟行情测试，并在模拟行情逻辑里补了一行"更新最新行情报价缓存"的代码（模拟行情之前没有更新缓存）。测试流程与核算结果如下：

| 步骤 | 数据 |
| --- | --- |
| 第一次查询（指令 7） | 中国平安 lastPrice 7042、仓位 219168；美的集团 5705、仓位 6000 |
| 行情再次推送后查询 | 中国平安 7040（跌 2 分）、美的集团 5699（跌 6 分） |
| 总市值差值 | −474336 |
| 持仓盈亏、当日盈亏差值 | 均为 −474336，与总市值差值一致 |
| 手工核算 | 中国平安 −2 × 219168 = −438336；美的集团 −6 × 6000 = −36000；合计 −474336 |

手工核算的实际价差影响与资金总览返回的差值完全对上，说明盈亏计算链路正确。因为内部是长整型计算，价格与数量都以长整型呈现，核算时按同一口径即可。

## 小结

回顾整个第十六章：搭建资金服务并集成核心组件；掌握总资产、总市值、持仓盈亏、当日持仓盈亏、可用资金等计算公式，其中当日持仓盈亏最复杂，是重中之重；定义对外传输与 gRPC 内部通讯两套数据结构；资金服务实现总览接口时兼顾性能，一次查询拿到当天全部成交记录；昨收价按"收盘价|日期"格式从缓存获取，缓存未命中查数据库、再置 0 兜底；昨收价生成依赖交易时间控制，收盘后留 5 分钟缓冲窗口，用当天与昨日两份缓存加日期标记实现每天一次的轮转更新；最后经代理服务处理器、客户端模拟终端完成全链路验证。

还有一点业务认知值得记住：当日浮动盈亏随实时行情变化，特殊情况下会出现误差，券商一般会提示"仅供参考，不作为账户资产的清算和结算依据"——账户的最终清算以交割单为准，交割单与对账单会在结算时生成。功能实现层面，把业务规则和公式理解透，再按公式落地代码，复杂功能其实并不难；测试验证则尽量从多个维度模拟场景，本章覆盖的是最核心的主干场景。
