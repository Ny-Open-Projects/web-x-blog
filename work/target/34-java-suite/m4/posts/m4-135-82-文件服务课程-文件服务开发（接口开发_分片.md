# 分片上传（终）：合并收尾、Controller 接口与三种存储策略联调

上一篇把分片合并的策略骨架和本地实现的主体写完了，这一篇收掉剩下的尾巴：merge 方法成功分支的返回值封装与 URL 拼接、Controller 上的合并接口，然后是完整联调，包括本地策略里真实踩到并修复的三个 bug，以及 FastDFS 与阿里云 OSS 两种策略各自的合并实现与验证。分片合并测试全部通过后，文件服务整章到此收官。

## 先给结论

- 合并走到成功分支，要封装的是项目自定义的 File 对象（不是 java.io.File），核心属性就两个：relativePath 相对路径（对应日期目录层次）和 url（用于查看、下载文件），最后 R.success(file) 返回。
- url 是分段拼接：uriPrefix + bucketName + 日期目录 + 文件名，段间用 StrPool.SLASH 补斜线，最终形态如 http://localhost:8080/2020/05/abc.avi。
- Controller 面向最高层接口 FileChunkStrategy 注入和调用，不写死具体实现类，策略类是按配置动态选择的；接口用 @PostMapping("/merge") 加 @ApiOperation，参数是前端封装好的 FileChunksMergeDTO。
- 本地联调修了三个真 bug：读分片的通道误写成 FileOutputStream 抛 NonReadableChannelException（合并出 0 字节文件）、Windows 反斜杠混进 URL、URL 少拼 bucketName 一层目录导致 404。
- FastDFS 合并靠追加式客户端：第一片 uploadAppenderFile（组名传空），后续片 appendFile 追加，成败看 StorePath 是否为 null；阿里云 OSS 走分片上传 API，completeMultipartUpload 由 OSS 服务端完成合并。
- 分片上传没法用 Swagger 接口文档测，必须配合前端 webuploader 页面联测（每片 10MB 由前端设定）；下载验证可以走 nginx 地址直接访问，也可以走接口文档按文件 id 下载，后者自动使用原始文件名。

## 合并收尾：封装 File 对象与拼 URL

merge 的主流程和失败分支上一篇已经写完：所有异常情况都返回 R.fail("分片文件合并失败")并记日志；目标文件已存在的分支打 log.warn("文件[{}]已经存在", fileName)。程序能执行到最后，就说明分片合并成功，接下来要封装返回值：

```java
// 分片合并成功，需要封装File对象相关属性
File file = File.builder()
        .relativePath(relativePath)
        .url(url)
        .build();
return R.success(file);
```

注意这个 File 不是 java.io.File，是自定义的实体，主要就两个属性：relativePath 对应目录层次，前面创建日期目录时已经算好；url 用于查看和下载文件。

url 的构成要拆开看：第一段是配置里的 uriPrefix，第二段是日期目录（也就是相对路径），第三段是文件名。用 StringBuilder 拼：

```java
String url = new StringBuilder(properties.getUriPrefix())
        .append(relativePath).append(StrPool.SLASH)
        .append(fileName)
        .toString();
```

uriPrefix 是带占位符的配置，IP 和端口运行时从配置取，比如 localhost 和 8080，最终拼出来的形态就是 http://localhost:8080/2020/05/abc.avi 这样的地址。这段逻辑写完，本地策略的 merge 就完整了，接着补 Controller，然后整体测试。

## Controller：面向策略接口的薄封装

Controller 里的合并方法非常短，因为接口、抽象类、具体子类前面都已经写好，直接调用即可：

```java
@ApiOperation(value = "分片合并", notes = "分片合并")
@PostMapping("/merge")
public R<File> merge(FileChunksMergeDTO fileChunksMergeDTO) {
    R<File> fileR = fileChunkStrategy.chunkMerge(fileChunksMergeDTO);
    return fileR;
}
```

参数就是前端 JS 封装好提交上来的 FileChunksMergeDTO，请求方式是 POST。注入时不直接引 LocalChunkServiceImpl，而是用最高层的 FileChunkStrategy 接口：存储策略是动态选择的，写死实现类就把策略模式的意义丢掉了。真正干活的仍是那套策略链，chunkMerge 在抽象父类 AbstractFileChunkStrategy 里走通用流程，差异逻辑下放给子类的 merge。以本地策略为例，LocalChunkServiceImpl 从 FileServerProperties 读出本地的 endpoint（如 D:/uploadFiles）和 bucketName（如 oss-file-service），再执行 FileChannel 的分片写出。

## 本地策略联调：三个真实 bug

测试前的环境口径：存储策略是 local，分片放在 D:/chunks，合并结果放在 D:/uploadFiles；为了观察方便，把这两个目录和数据库里的旧数据全部清掉。服务启动日志里能看到 file type=local 和 storage path 的值，说明配置加载正常。nginx 服务也起着，但它只为后面的下载验证服务，只上传文件的话并不需要它。

测试方式有个限制：分片上传不能用接口文档测，必须用前端页面（百度提供的 webuploader 插件）。分片逐个传完后，前端会自动调用分片合并接口，参数封装进 DTO，这些都是前端做的事。传一个 30 多 MB 的文件，按前端设定的每片 10MB，分成 4 片。

第一轮测试的现象很有代表性：目录创建正常、合并文件也出现了，控制台却报"分片合并失败"，数据库没有插入数据。看合并出的文件，是 0 字节，文件创建了但数据没写进去。打断点跟一遍：files 集合 4 个元素，按 0、1、2、3 排好序；DTO 里 name、原始文件名、md5、分片数、后缀、文件夹 id、文件大小、contentType 都正常；createNewFile 之后文件 0 字节，问题出在写数据。再往下走，inChannel 抛的是 NonReadableChannelException，通道不可读。原因是从上面拷代码忘了改：输出通道是 FileOutputStream，读分片的通道也写成了 FileOutputStream，而读文件必须用 FileInputStream：

```java
try (FileChannel outChannel = new FileOutputStream(outputFile).getChannel()) {
    for (java.io.File chunkFile : files) {
        try (FileChannel inChannel = new FileInputStream(chunkFile).getChannel()) {
            inChannel.transferTo(0, inChannel.size(), outChannel);
        } catch (Exception ex) {
            log.error("分片文件合并失败");
            return R.fail("分片文件合并失败");
        }
    }
}
```

改成 FileInputStream 后重测：合并成功，文件大小 32.3MB 正常，数据库插入了记录。但新问题跟着来：URL 里带反斜杠。relativePath 在 Windows 下用反斜杠做目录分隔符，而 URL 里一律用正斜杠。修法是把 url 里的反斜线统一替换成正斜线（StringUtils.replace，替换目标是 StrPool.SLASH 常量），再设置到 File 的 url 属性上，这是第二个 bug。

替换后再访问，变成 404。这回不是 nginx 的问题：看拼出的地址，IP、端口后面直接进了年月两层目录，而文件实际存储还差一层 oss-file-service（bucketName）目录，URL 拼接时忘了把这一段拼进去。补上 bucketName 和段间斜线，这是第三个 bug：

```java
String url = new StringBuilder(properties.getUriPrefix())
        .append(bucketName).append(StrPool.SLASH)
        .append(relativePath).append(StrPool.SLASH)
        .append(fileName)
        .toString();
```

一次性写这么多代码，出现这类小问题在所难免，靠的就是逐轮测试一点点修。修复后整体重测：17MB 文件上传合并成功，数据库两条记录，浏览器访问拼出的 URL，经 nginx 正常下载 17.3MB；再用接口文档按文件 id 调下载接口，同样能下载，而且用的是原始文件名，比较人性化（接口里还支持多个文件打包下载）。到这里，本地策略的分片合并测试通过。

## FastDFS 与阿里云 OSS：两种托管式合并

剩下两个策略的 merge 思路一致，实现都更薄，因为合并细节被存储服务封装了。先看 FastDFS，在 FastDfsAutoConfigure 配置类里定义 FastDfsChunkServiceImpl（加 @Service，继承 AbstractFileChunkStrategy）：普通上传用 FastFileStorageClient.uploadFile 一步到位，分片合并不能用它，要用专门支持追加的存储客户端（AppendableStorageClient），核心就两个方法，第一片用 uploadAppenderFile，后续片用 appendFile 追加：

```java
@Override
protected R<File> merge(List<java.io.File> files, String fileName,
                        FileChunksMergeDTO fileChunksMergeDTO) throws Exception {
    StorePath storePath = null;
    for (int i = 0; i < files.size(); i++) {
        java.io.File chunkFile = files.get(i);
        if (i == 0) {
            // 第一片：组名传空，由服务端自动分配
            storePath = storageClient.uploadAppenderFile(null,
                    FileUtils.openInputStream(chunkFile),
                    chunkFile.length(), fileChunksMergeDTO.getExt());
        } else {
            // 后续片：按 StorePath 里的组和路径追加
            storageClient.appendFile(storePath.getGroup(), storePath.getPath(),
                    FileUtils.openInputStream(chunkFile), chunkFile.length());
        }
    }
    if (storePath == null) {
        // 分片合并失败
        log.error("分片合并失败");
        return R.fail("分片合并失败");
    }
    // 合并成功后需要封装File对象返回
    String url = new StringBuilder(fileProperties.getUriPrefix())
            .append(storePath.getFullPath()).toString();
    File filePo = File.builder()
            .url(url)
            .group(storePath.getGroup())
            .path(storePath.getPath())
            .build();
    return R.success(filePo);
}
```

这里用普通 for 而不是增强 for，因为要靠下标 i 区分第一片和后续片，两次调用的方法不同。第一片上传时组名传 null，FastDFS 会自动分配组，返回的 StorePath 里带着组和路径；后续片就按它追加，追加参数依次是组名、路径、输入流、文件大小。成败判断也简单：storePath 为 null 就是合并失败，不为空则用 FastDFS 类型对应的 uriPrefix 拼 StorePath 的 fullPath 作为 url，连同 group、path 一起封装进 File 对象返回。

阿里云 OSS 的 AliChunkServiceImpl 放在 AliOSSAutoConfigure 里，同样继承抽象策略。先用配置里的 endpoint、accessKeyId、accessKeySecret 构建 OSS 客户端，properties 提成成员变量，避免局部变量出了方法就失去作用域：

```java
private OSS buildClient() {
    properties = fileServerProperties.getAli();
    return new OSSClientBuilder().build(properties.getEndpoint(),
            properties.getAccessKeyId(),
            properties.getAccessKeySecret());
}
```

这个方法虽然叫分片合并，实际调用的是 OSS 的分片上传 API：阿里云把合并封装掉了，我们只负责把分片传上去，它按 API 的要求在服务端完成合并。讲义代码是从阿里云官方示例改造来的，官方示例非常繁琐，这类代码没必要手写也没必要背，抓住关键步骤、把示例拿来改造就够了。整个流程是：

1. 构建客户端，读出 bucketName；日期目录用 LocalDate.now().format(DateTimeFormatter.ofPattern(DEFAULT_MONTH_FORMAT_SLASH)) 生成（如 2020/05），拼上文件名得到 objectKey；
2. ObjectMetadata 里设 contentDisposition（attachment;filename=原始文件名）和 contentType，都是常规配置；
3. InitiateMultipartUploadRequest(bucketName, objectKey, metadata) 发起初始化，拿 uploadId。它是分片上传事件的唯一标识，几十位的长串，取消分片上传、查询分片上传等操作都靠它；
4. for 循环逐片上传：UploadPartRequest 设 bucketName、objectKey、uploadId、输入流（FileUtils.openInputStream）、分片大小（file.length()）、分片号（i+1），uploadPart 返回 PartETag 收进 partTags，这一步只是给后续合并做记号；
5. partTags 按分片号排序：partTags.sort(Comparator.comparingInt(PartETag::getPartNumber))；
6. CompleteMultipartUploadRequest(bucketName, objectKey, uploadId, partTags) 调 completeMultipartUpload，OSS 在服务端把分片合并成一个文件，返回结果里带 key 和 location，是完整的访问路径；
7. 自己拼 url，用 File.builder() 封装属性返回，最后 client.shutdown() 关闭客户端。

OSS 测试前先改配置：把 Nacos 上文件服务配置里的 type 从 local 改成阿里并发布，重启服务。传一个 20 多 MB 的文件，分成 3 片。断点跟进去：files 里是 0、1、2 三个元素，DTO 属性都没问题；client 创建要连网络，稍慢；uploadId 生成了几十位的长串；for 循环 3 次 uploadPart，每次走网络上传都有一点卡；排序后 completeMultipartUpload 让 OSS 在服务端把三片合并成一个文件。放行之后本地 chunks 里的临时分片被清空，控制台发出 insert 语句，数据库多出一条记录。复制 url 直接访问能下载，但浏览器里文件名显示乱码；走接口文档按 id 下载则用原始文件名，大小 22.2MB，与原文件一致。阿里云策略测试通过。

三种策略的合并方式放在一起看：

| 存储策略 | 核心方法 | 合并由谁完成 |
|---|---|---|
| local | FileChannel.transferTo 逐片写出 | 服务端自己循环写 |
| FastDFS | uploadAppenderFile + appendFile | 客户端追加，细节已封装 |
| 阿里云 OSS | uploadPart + completeMultipartUpload | OSS 服务端合并 |

## 小结

到这里，文件服务整章收官。这一章从需求背景和课程介绍起步，搭建工程环境后先用策略模式抽象出文件处理策略层，然后依次实现单文件上传、按 id 下载与多文件打包下载，最后是分片上传与合并这条完整链路。存储侧 local、FastDFS、阿里云 OSS 三种策略实现同一套接口，靠配置动态切换，文件服务的配置由 Nacos 统一下发，文件元数据落库保存；下载既可以拿 url 经 nginx 直接访问，也可以走接口文档按 id 下载并还原原始文件名。分片合并作为整个文件服务里最复杂的接口，三种存储策略全部实现并测试通过，这一章到此收束。
