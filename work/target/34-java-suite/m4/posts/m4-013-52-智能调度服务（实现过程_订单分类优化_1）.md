# 智能调度·订单分类优化与调度服务收尾（含其他功能代码导入）

订单分类跑通之后，回头看 calculate 有一个业务层面的隐患：它按"距离最近"选网点，而业务上真正负责取派件的，是作业范围覆盖这个地址的网点——两者在两个网点的交界地带会得出不同答案。这一单元四讲先把这个漏洞修掉：引入 JDK 自带的 Path2D 做"点是否在多边形内"的判断，重构 calculate；随后梳理智能调度的完整执行流程，把订单分类之后的路线规划、运输任务等功能代码直接导入，智能调度服务就此收尾。

## 先给结论

- 按"最近距离"选网点会选错：地址明明落在 A 网点的作业范围内，却因为离 B 网点的某个顶点更近，被算给了 B。正确逻辑是判断地址是否被某网点的作业范围（多边形）覆盖，距离只是参考，不是依据。
- JDK 自带现成方案 java.awt.geom.Path2D：moveTo 落起点、lineTo 依次连线、closePath 封闭成多边形，contains(x, y) 返回布尔。ScopeTest 用 (0,0)(1,0)(1,1)(0,1) 画正方形，contains(0.1,0.1) 输出 true，测试点改成 (1.5,1.5) 输出 false。
- 封装成工具方法 EntCoordSyncJob.isInScope(List<Map> polygon, longitude, latitude)：第一个点 moveTo，polygon.remove(0) 防止重复起点，剩余点循环 lineTo，最后再 lineTo 连回起点并 closePath，contains 判定经纬度——x 对应经度、y 对应纬度。
- calculate 重构后反而瘦身：删掉算距离的内层循环、保最小值的 agencyMap 和排序逻辑，降为两层循环——对每个网点的每个区域调 isInScope，命中直接返回该网点 id；全部未命中返回 Result.error(5000, "获取网点失败")，基础数据缺失时可能出现这种情况。
- 完整执行链是：定时任务触发执行 executeInternal，反射拿到 dispatchTask bean 调 run；run 里依次调订单分类、路线规划、创建运输任务、车次车辆司机规划、完善运输任务并创建司机作业任务，每个环节封装成独立 service。
- 订单分类之后的代码量更大，不在课上手敲，直接从资料目录导入：service 接口与实现类复制覆盖、controller 包整体复制、DispatchTask 整类覆盖，导入后调度链即完整可用。

## 问题：最近的网点不一定是"管你的"网点

先看被优化的对象。现有 calculate 的算法是三层循环：遍历网点集合，取每个网点的 getMultiPoints()（List<List<Map>>），最内层拿每个坐标顶点算它到收件人地址 location 的距离；同一个网点有多个顶点，用 preDistance == null || distance < preDistance 只保最小值；全部算完再按距离升序排序，get(0).getKey() 拿到"最近"的网点 id。语法对、逻辑对，验证也通过了，但它建立在一个未经审视的假设上：距离最近的网点就是负责该地址的网点。

反例就在网点交界地带。地图上 A、B 两个网点相邻，各自覆盖一个多边形范围的作业区域，范围内所有地址的客户都归这个网点负责取件、派件。现在有一个地址明明落在 A 网点覆盖的图形之内，但它恰好处于两个网点交接的地方，按"顶点到地址的距离"来算，它离 B 网点多边形的某个顶点直线距离更近——现有代码把这个单子判给了 B，而按业务规则它应该归 A。

问题出在"按距离找"从来没检查过 B 网点的覆盖区域是否真的包含这个点。所以逻辑要调整：不再计算距离，而是查找"哪个网点的作业范围覆盖了这个地址"——把每个网点范围的顶点连成一个封闭图形，逐个判断地址是否落在图形之内。这是更严谨的处理方式，命中即找到负责网点。

## Path2D：JDK 自带的"点在区域内"判断

"如何确定某个点是否在某个范围内"，JDK 里已有现成答案：java.awt.geom.Path2D。用法是先用路径把若干点连成封闭图形，再调 contains 判断点是否被包含。test 目录下写个 ScopeTest 验证：

```java
import java.awt.geom.Path2D;

public class ScopeTest {
    public static void main(String[] args) {
        Path2D.Double generalPath = new Path2D.Double();
        // 绘制区域范围
        generalPath.moveTo(0, 0);      // 移动到起点 (0,0)
        generalPath.lineTo(1, 0);      // 连到 (1,0)
        generalPath.lineTo(1, 1);      // 连到 (1,1)
        generalPath.lineTo(0, 1);      // 连到 (0,1)
        generalPath.lineTo(0, 0);      // 连回起点
        generalPath.closePath();       // 封闭路径
        // 判断指定点是否在上面的区域范围内
        boolean contains = generalPath.contains(0.1, 0.1);
        System.out.println(contains);
    }
}
```

在坐标系里走一遍更直观：moveTo 把路径起点定在 (0,0)；之后每个 lineTo 从当前位置画一条直线到新坐标；四个点依次连完再连回 (0,0)，closePath 关闭子路径——一个单位正方形就画出来了。contains(0.1, 0.1) 问的是这个正方形是否覆盖平面上的点 (0.1, 0.1)，运行输出 true；把测试点改成 (1.5, 1.5)，落在正方形外，输出 false。整个判断零依赖、逻辑直观，接下来只需要把这里的抽象坐标换成网点作业范围的真实经纬度顶点。

## 封装 isInScope，重构 calculate

验证可行后，把这段代码封装成工具方法放进百度地图工具类 EntCoordSyncJob，方法名 isInScope——是否在范围之内。入参是一个坐标点集合 polygon（List<Map>，每个 Map 装一个经纬度顶点，key 为 lng/lat）和待判断的经度、纬度：

```java
public static boolean isInScope(List<Map> polygon, double longitude, double latitude) {
    Path2D.Double generalPath = new Path2D.Double();
    // 获取第一个起点经纬度的坐标
    Map first = polygon.get(0);
    // 通过移动到以double精度指定的坐标，把第一个起点添加到路径中
    generalPath.moveTo(Double.parseDouble(first.getOrDefault("lng", "").toString()),
            Double.parseDouble(first.getOrDefault("lat", "").toString()));
    // 把集合中的第一个点删除防止重复添加
    polygon.remove(0);
    // 循环集合里剩下的所有经纬度坐标，依次连线
    for (Map d : polygon) {
        generalPath.lineTo(Double.parseDouble(d.getOrDefault("lng", "").toString()),
                Double.parseDouble(d.getOrDefault("lat", "").toString()));
    }
    // 连回起点，将多边形封闭
    generalPath.lineTo(Double.parseDouble(first.getOrDefault("lng", "").toString()),
            Double.parseDouble(first.getOrDefault("lat", "").toString()));
    generalPath.closePath();
    // 指定坐标在边界内返回 true，否则为 false
    return generalPath.contains(longitude, latitude);
}
```

几个细节值得留意。moveTo 只对第一个点调用一次，它就是起点；起点取出来后立刻从集合里移除，避免后面循环时重复添加；剩余点循环 lineTo 连线；循环结束后还要再 lineTo 一次连回起点（first），最后 closePath，多边形才真正闭合。经纬度从 Map 里用 getOrDefault("lng"/"lat") 取出转 Double，x 对应经度、y 对应纬度，与地图坐标一一对应。

工具方法就位，回到 service 包下的 TaskOrderClassifyServiceImpl 改造 calculate。原先三层循环的最内层在算两点距离，这层直接删掉；保最小值的 agencyMap、entrySet 转 List 排序、get(0) 取最近网点，这些也全部不需要了——策略已经从"算最近"变成"命中即返回"：

```java
private Result calculate(List<AgencyScopeDTO> agencyScopes, String location) {
    try {
        for (AgencyScopeDTO agencyScopeDto : agencyScopes) {
            // 某个网点作业范围的多组坐标
            List<List<Map>> mutiPoints = agencyScopeDto.getMultiPoints();
            for (List<Map> list : mutiPoints) {
                // location 是逗号拼接的"经度,纬度"，先拆开
                String[] originArray = location.split(",");
                boolean flag = EntCoordSyncJob.isInScope(list,
                        Double.parseDouble(originArray[0]),
                        Double.parseDouble(originArray[1]));
                if (flag) {
                    // 命中即找到负责网点，直接返回
                    return Result.ok().put("agencyId", agencyScopeDto.getAgencyId());
                }
            }
        }
        return Result.error(5000, "获取网点失败");
    } catch (Exception e) {
        e.printStackTrace();
        return Result.error(5000, "获取网点失败");
    }
}
```

循环降到两层：外层还是网点集合，中层遍历 getMultiPoints() 拿到单个区域的坐标列表 list，交给 isInScope 判断 location 是否被覆盖。location 传进来的是拼接好的字符串，先按逗号 split，数组第一个元素是经度、第二个是纬度。isInScope 返回 true 就说明这个地址归当前网点管，直接把 agencyId 包进 Result 返回，后面的网点不必再看。异常提示也从"获取最短距离网点失败"改成"获取网点失败"——已经没有"最短距离"这回事了。

有一个前提值得点破：如果遍历完所有网点都没命中，就返回失败。正常情况下地址总会落在某个网点的作业范围内，但这个判断完全依赖网点范围这套基础数据，一旦基础数据缺失，把所有网点扫一遍也没有命中是完全可能的。

## 收尾：执行流程梳理与功能代码导入

订单分类优化完，智能调度的第一个环节彻底完工。此时把整个程序的执行流程再串一遍：智能调度由定时任务触发，任务触发时执行 executeInternal，其中通过反射从 Spring 容器拿到目标 bean（dispatchTask），调用它的 run 方法；run 里再依次调各个 service——订单分类是第一个环节，之后是路线规划、创建运输任务、关联运单，再往后是规划车次车辆司机、完善运输任务并创建司机作业任务。每个环节封装成独立 service，DispatchTask 只负责串流程：

```java
@Component("dispatchTask")
@Slf4j
public class DispatchTask {
    @Autowired
    private ITaskOrderClassifyService taskOrderClassifyService;
    @Autowired
    private ITaskRoutePlanningService routePlanningService;
    @Autowired
    private ITaskTripsSchedulingService truckSchedulingService;
    @Autowired
    private IBusinessOperationService businessOperationService;

    @SneakyThrows
    public void run(String businessId, String params, String jobId, String logId) {
        log.info("智能调度正在执行，参数为: {}, {}, {}, {}", businessId, params, jobId, logId);
        // 订单分类
        List<OrderClassifyGroupDTO> classifyGroupDTOs =
                taskOrderClassifyService.execute(businessId, jobId, logId);
        // 路线规划
        List<OrderLineSimpleDTO> orderLineSimpleDTOs =
                routePlanningService.execute(classifyGroupDTOs, businessId, jobId, logId, params);
        // 创建运输任务
        Map<String, TaskTransportDTO> transportTaskMap =
                businessOperationService.createTransportOrderTask(orderLineSimpleDTOs);
        // ……后续环节：规划车次车辆司机、完善运输任务、创建司机作业任务
    }
}
```

## 小结

四个视频做了两件事。优化这一刀切得干脆：把"算距离选最近"换成"判断点是否被作业范围覆盖"，Path2D 是 JDK 现成的类，moveTo、lineTo、closePath 三步建多边形，contains 一个方法出结论；isInScope 封进工具类，一次投入长期复用；calculate 从三层循环瘦身到两层，命中即返回，连错误文案都跟着改掉了"最短距离"。收尾这一半是工程动作：executeInternal 反射调 DispatchTask.run 的骨架不动，订单分类之后的路线规划、运输任务、车次车辆司机规划、司机作业任务各环节封装成独立 service，代码量大就整体导入覆盖，调度服务至此闭环。智能调度的代码篇结束，接下来转入数据聚合服务。
