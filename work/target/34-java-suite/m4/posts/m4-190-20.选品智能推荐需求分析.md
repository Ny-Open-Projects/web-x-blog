# 选品智能推荐：需求分析、实现思路、ES 聚合实现与测试

LBS 与选品一章的收束功能是选品智能推荐：当用户往商圈投放售货机时，系统按点位的商圈属性，给出同商圈近三个月内销量最好的十个商品，采纳后自动进入货道设置。本篇按需求分析、实现思路、代码实现、测试四步把这个功能讲透，它本质上是把一条 group by 统计 SQL 搬进了 Elasticsearch。

## 先给结论

- 选品在立可得系统里的具体操作就是货道设置：给每个货道安排放置什么商品。1.0 版本全靠人工，工作量大，且选中的商品极可能销量不佳。
- 推荐的两个硬条件：时间范围取近三个月，屏蔽季节因素和过气商品；空间范围取同一商圈，不同商圈的畅销品完全不同。
- 查询放在 Elasticsearch 而不是 MySQL：订单数据此前已经同步进 ES，ES 查询性能更好，还能给 MySQL 减压。
- ES 侧用 AggregationBuilders：terms 按 sku_id 分组，count 子聚合统计销量（售货机每笔订单的数量就是 1，直接 count 即可），order 按 count 降序，size(10) 取前十。
- 结果提取靠聚合名：terms("sku") 起的名字和 aggregations.get("sku") 要对上，bucket 的 key 就是 sku_id，Long.valueOf 转成 Long 收集为 List<Long>。

## 一、需求：三个月加同商圈

选品，通俗地讲就是选择商品。在立可得系统中，这个动作的具体形态是货道设置：对每一台售货机做货道设置，给每个货道安排放置的商品。1.0 版本只有一个简单的货道设置功能，全部人工操作。这带来两个问题：一是工作量大，逐个货道逐台机器去设置；二是人工选品全凭感觉，选中的商品极可能销量不佳，等于让运营人员自己不断选品、不断试错，时间成本注定浪费。

系统既然已经积累了历史销售数据，就该分析它：把历史数据中卖得最好的商品陈列出来，销量自然往上走。这就是智能排货，也叫选品的智能推荐。

但有两个细节必须处理。

第一，不能把所有历史数据都纳入统计。商品有生命周期：某种商品前几年卖得好，之后就慢慢滞销；市场不断推出新品，用户又想去尝试。不考虑时间范围的话，过气商品也会被持续推荐出来，这显然不对。产品给出的时间范围是三个月。三个月还有一个附带的好处：屏蔽季节因素。冰镇饮料夏天卖得非常好，入冬就卖不动，而三个月之内季节变化不明显，用它做统计窗口，季节的干扰就被压到很小。选三个月内的畅销商品是一个非常好的选择。

第二，商圈属性不能不考虑。售货机所在位置的商圈决定了什么商品畅销：学校里放一台机器卖钢笔，可能卖得很好；同一台机器放到公园里，一个月都卖不出两支。公园适合卖可乐饮料，逛公园的人正好买一瓶。不同场景的畅销商品必然不一样。

于是需求收敛为：当用户往商圈投放售货机时，通过点位的商圈属性，给出同商圈、近三个月内销量最好的十个商品。界面上对应的操作是：货道设置页面的右下角有"智能补货"按钮，点击后弹出窗口，提示"该区域属于写字楼商圈适合销售以下商品"并列出推荐商品，用户点确定采纳建议后，这些商品就自动进入货道设置。

## 二、实现思路：把 group by 搬进 Elasticsearch

订单数据此前已经通过 Logstash 同步进 Elasticsearch，MySQL 和 ES 里都有订单数据。查哪边？从性能角度，查 ES 更好：一是减少 MySQL 的压力，二是 ES 在查询性能上本来就比 MySQL 表现更好。所以聚合查询放在 ES 里实现。

统计逻辑如果写成 MySQL 的 SQL，长这样：

```sql
select sku_id, count(sku_id) as count
from `order`
where update_time >= 三个月前 and business_id = 商圈ID
group by sku_id
order by count desc
limit 0, 10
```

为什么 count(sku_id) 直接等于销量？因为售货机本身的业务性质决定了每笔订单记录的数量就是 1，记录数就是销量，不需要对数量字段再求和。

ES 侧对应的工具是 AggregationBuilders，逐项对照 SQL：

- .terms("sku").field("sku_id")——terms 指定一个自定义名称 sku，这个名字在提取聚合结果时要根据它来取；field 指定聚合字段，相当于 group by sku_id。
- .subAggregation(AggregationBuilders.count("count").field("sku_id"))——子聚合做计数，"count" 是聚合之后起的别名，相当于 SQL 里 select count(sku_id) as count 中 as 后面那部分。
- .order(BucketOrder.aggregation("count", false))——按聚合出来的数量排序，false 是降序，true 是升序；统计前十必须降序，把销量最大的排前面。
- .size(10)——相当于 limit，只取前十个。

## 三、代码实现：getTop10Sku 与 Controller 接口

订单微服务的 OrderService 接口里定义方法：获取商圈下销量最好的十个商品，返回 List<Long>，泛型是商品 ID，入参是商圈 ID：

```java
List<Long> getTop10Sku(Integer businessId);
```

实现分两大部分：查询条件的封装和结果的封装。先看条件的封装与聚合的构建：

```java
// 查询索引 order
SearchRequest searchRequest = new SearchRequest("order");
SearchSourceBuilder sourceBuilder = new SearchSourceBuilder();

// 范围查询：最近三个月
RangeQueryBuilder rangeQueryBuilder = QueryBuilders.rangeQuery("update_time")
        .gte(LocalDateTime.now().plusMonths(-3).format(DateTimeFormatter.ISO_DATE_TIME))
        .lte(LocalDateTime.now().format(DateTimeFormatter.ISO_DATE_TIME));

// bool 查询：时间范围 + 商圈
BoolQueryBuilder boolQueryBuilder = QueryBuilders.boolQuery();
boolQueryBuilder.must(rangeQueryBuilder);
boolQueryBuilder.must(QueryBuilders.termQuery("business_id", businessId));
sourceBuilder.query(boolQueryBuilder);

// 聚合：按 sku_id 分组，count 子聚合统计销量，降序取前十
AggregationBuilder orderAgg = AggregationBuilders.terms("sku").field("sku_id")
        .subAggregation(AggregationBuilders.count("count").field("sku_id"))
        .order(BucketOrder.aggregation("count", false))
        .size(10);
sourceBuilder.aggregation(orderAgg);
searchRequest.source(sourceBuilder);
```

时间条件用 rangeQuery：gte 是大于等于，值取 LocalDateTime.now().plusMonths(-3)，即向前推三个月，再用 DateTimeFormatter.ISO_DATE_TIME 格式化成字符串；lte 小于等于当前时间，写法相同，去掉推月的部分。商圈条件用 termQuery 精确匹配 business_id。两个条件一起装进 boolQuery，再由 sourceBuilder 的 query 方法装入。聚合部分就是上一节那四项，返回的 AggregationBuilder 通过 sourceBuilder.aggregation() 挂进去，最后 searchRequest.source(sourceBuilder) 组装完成。到这里，查询条件封装这块就写完了。

结果的封装要执行查询并从响应里提取聚合：

```java
try {
    SearchResponse searchResponse = esClient.search(searchRequest, RequestOptions.DEFAULT);
    Aggregations aggregations = searchResponse.getAggregations();
    if (aggregations == null) return Lists.newArrayList();

    // get 里的名字必须和 terms("sku") 定义的一致
    Terms terms = (Terms) aggregations.get("sku");
    List<? extends Terms.Bucket> buckets = terms.getBuckets();

    return buckets.stream()
            .map(b -> Long.valueOf(b.getKeyAsString()))  // bucket 的 key 就是 sku_id
            .collect(Collectors.toList());
} catch (IOException e) {
    e.printStackTrace();
}
return Lists.newArrayList();   // 出错返回空集合
```

esClient.search 的两个参数是 searchRequest 和 RequestOptions.DEFAULT，返回 SearchResponse，这一句需要 try-catch。提取聚合先判空，拿不到就返回空列表；aggregations.get("sku") 里的名字就是构建聚合时自定义的那个，取出来强转成 Terms，getBuckets 拿到分组结果。每个 bucket 的 key 就是聚合字段 sku_id 的值，具体每个 sku 的销量数这里并不关心，只要把前十的 ID 返回去。key 是字符串，方法要返回 List<Long>，所以用 Long.valueOf 包一层再收集；catch 里同样返回空集合。

Controller 层按管理后台的 API 文档建接口，售货机下有一个"获取商圈下销量前十的商品"：

```java
@GetMapping("/businessTop10Sku/{businessId}")
public List<Long> getBusinessTop10Sku(@PathVariable Integer businessId) {
    return orderService.getTop10Sku(businessId);
}
```

businessId 是路径参数，用 @PathVariable 接收，路径里用大括号占位；方法体一行，转发给 orderService.getTop10Sku，方法注释是"获取商圈下三个月内销量前十的商品"。

## 四、测试：脚本直连 9008

启动订单微服务即可。测试脚本访问的是 9008 端口，也就是说不走网关，直接访问微服务。脚本里已经有"获取商圈销量前十商品"这条请求，地址是现成的，路径里指定的 1 就是商圈 ID。

点击 send request，返回的就是销量前十的商品。当前数据库是测试库，商品数量比较少，只有 6 个商品，所以返回的是 6 个 ID，但顺序是按销量排好的。功能验证通过，选品智能推荐到此完成。

## 小结

选品智能推荐是 LBS 与选品一章的收束。需求侧用两个条件压住推荐质量："近三个月"压缩时间窗口，规避商品生命周期与季节波动；"同商圈"压缩空间范围，保证推荐符合点位人群。实现侧把一条 group by 加 limit 0,10 的统计 SQL 翻译成 ES 的 terms 聚合加 count 子聚合，order 按销量降序、size 取前十。代码侧 OrderServiceImpl 先封条件再建聚合，SearchRequest 指定 order 索引，从 buckets 里提取 sku_id 转成 List<Long>；Controller 暴露 /businessTop10Sku/{businessId} 接口；测试直连 9008 端口，返回按销量排序的商品 ID 列表。从 LBS 定位选点位，到点位产生订单，再到订单数据反哺选品建议，这一章的业务闭环到此走完。
