# 亿可控指标采集上半场：Eclipse Paho 收发 MQTT 消息与指标主题订阅

亿可控这个项目最核心的功能只有两件事：接收物联网设备发来的报文，解析出其中的指标数据，再基于指标做告警。要接收报文，第一步必须解决 Java 工程与 EMQ 之间的消息收发问题。这一篇用 Eclipse Paho 把发送、订阅完整跑通，再把订阅从写死的测试主题升级成由指标配置表驱动的动态订阅（含集群下的共享订阅与断线重连），最后进入指标数据解析的开篇——DTO 设计与解析方法的骨架。

## 先给结论

- Eclipse Paho 是 Eclipse 基金会下的开源项目，本质是基于 MQTT 协议的客户端，有多语言实现：Java、Python、JavaScript、GoLang、C、C++、C# 等；Java 版可以运行在 JVM 之上或其他兼容 Java 的平台（比如安卓）。Java 客户端提供两种 API：`MqttAsyncClient` 完全异步（启动时注册回调）、`MqttClient` 同步——亿可控选同步方式收发消息。
- 接入 EMQ 五步走：pom 引入 `org.eclipse.paho.client.mqttv3:1.2.2` → Consul 配置中心加 `emq.mqttServerUrl = tcp://192.168.200.128:1883` → 写 `EmqConfig` 配置类绑定该配置 → `EmqClient.connect()` 建立连接（clientId 用 `"monitor_" + UUID.randomUUID()` 保证每次连接唯一）→ `publish(topic, message)` 发布消息。
- 发布测试闭环：测试类调 connect + publish，同时用 EMQ 管理台的 Websocket 工具（连 192.168.200.128:8083）订阅 `test_topic`，跑一次单元测试，管理台消息列表收到 `test_content` 即验证成功。
- 订阅端三件套：`EmqClient.subscribe(topic)` 订阅方法；`EmqMsgProcess` 实现 `MqttCallback` 接口（`messageArrived` 处理消息、`connectionLost` 断线触发、`deliveryComplete` 发送完成触发）；连接前 `setCallback` 挂上回调。再用 `Monitor` 类的 `@PostConstruct` 方法保证启动即连接并订阅。
- 真实业务订阅的是指标配置表里的报文主题：启动时 `QuotaService.getAllSubject()` 取出全部主题循环订阅；新增指标的 `create` 方法里也要追加订阅；集群部署必须用共享订阅——主题前加 `$share/` 前缀，保证一条消息只被一个节点消费；连接丢失则在 `connectionLost` 里重连并重新订阅。
- 指标解析开篇：一条报文往往带多个指标（如 `{"sn":"123456","temp":1.2,"humi":50}`），于是设计两级 DTO——`QuotaDTO`（指标配置信息 + 指标值 value/stringValue/deviceId）和 `DeviceInfoDTO`（一个设备 + 指标列表）；解析方法 `analysis(topic, payloadMap)` 第一步按主题查指标配置，查不到直接返回 null。

## 一、Eclipse Paho：亿可控对接 EMQ 的客户端

先明确问题域：设备把指标报文发到 EMQ，亿可控后端要从 EMQ 把消息订阅过来（有时也要往里发消息），Java 工程需要一个 MQTT 协议的客户端库，这就是 Eclipse Paho 的位置。它是 Eclipse 基金会下的开源项目——Eclipse 不只是那个常用的 Java IDE，基金会旗下有很多开源项目，Paho 是其中之一。

选型上值得记住两点。第一，语言覆盖广，官方支持 Java、Python、JavaScript、GoLang、C、C++、C# 等，本项目自然用 Java 版，它可以运行在 JVM 之上，也能跑在安卓这类兼容 Java 的平台上。第二，Java 客户端有两种 API：`MqttAsyncClient` 完全基于异步实现，通过启动时注册回调（callbacks）来做消息的异步收发；`MqttClient` 则基于同步方式。两种都能用，亿可控按项目需求选了同步方式接收处理消息。

本章的路线图也在这里交代清楚：先做发送与订阅消息（1.2），再做订阅指标主题与系统启动自动订阅（1.3），然后进入指标数据解析（2.1），之后是告警判断与存储（3.1），最后是设备断连监控（4.1）。本篇覆盖到解析上半场。

## 二、发送消息：依赖、配置与 EmqClient

发送消息的实现分五步。

第一步，在亿可控工程的 pom 中加入 Paho 依赖：

```xml
<dependency>
    <groupId>org.eclipse.paho</groupId>
    <artifactId>org.eclipse.paho.client.mqttv3</artifactId>
    <version>1.2.2</version>
</dependency>
```

第二步，在 Consul 配置中心添加 emq 配置，目前只有一项——EMQ 的连接地址：

```json
{
  "emq": {
    "mqttServerUrl": "tcp://192.168.200.128:1883"
  }
}
```

第三步，创建配置类读取这段配置（`com.yikekong.config` 包下）：

```java
@Data
@Configuration
@ConfigurationProperties("emq")
public class EmqConfig {
    private String mqttServerUrl;
}
```

`@ConfigurationProperties("emq")` 的前缀与配置里的 key 对应，属性名与里层的 key 一致，配置就能自动绑定；`@Data` 是 Lombok 注解，省掉 getter/setter。

第四步，`com.yikekong.emq` 包下创建客户端连接类 `EmqClient`，核心的 `connect()` 方法长这样：

```java
@Component
@Slf4j
public class EmqClient {

    @Autowired
    private EmqConfig emqConfig;

    private MqttClient mqttClient;

    public void connect() {
        try {
            mqttClient = new MqttClient(emqConfig.getMqttServerUrl(),
                    "monitor_" + UUID.randomUUID());
            mqttClient.connect();
        } catch (MqttException e) {
            e.printStackTrace();
        }
    }
}
```

`MqttClient` 是连接 MQTT 服务器最核心的类，构造参数两个：服务器 URL（从配置读取）和 clientId。clientId 采用随机值，`monitor_` 前缀拼接 `UUID.randomUUID()`，保证每次连接的客户端 ID 都不一样——同一 ID 重复连接会被服务端拒绝，这是 MQTT 的常见坑。

第五步，写发布消息的方法。发送必然用到连接对象，所以把 `mqttClient` 提升为成员变量：

```java
public void publish(String topic, String message) {
    try {
        MqttTopic mqttTopic = mqttClient.getTopic(topic);
        MqttMessage mqttMessage = new MqttMessage(message.getBytes());
        mqttTopic.publish(mqttMessage);
    } catch (MqttException e) {
        e.printStackTrace();
    }
}
```

逻辑是先 `getTopic(topic)` 拿到主题对象，再把字符串内容转成 `MqttMessage`，由主题对象 `publish` 出去。

写完就测。单元测试类上加 `@SpringBootTest(classes = YkkApplication.class)` 和 `@RunWith(SpringRunner.class)`，注入 `EmqClient`：

```java
@Autowired
private EmqClient emqClient;

@Test
public void testSend() {
    emqClient.connect();
    emqClient.publish("test_topic", "test_content");
}
```

验证要用 EMQ 管理台的 Tools 里的 Websocket 工具：先填连接地址 192.168.200.128、端口 8083 点连接（注意这里是 8083 的 Websocket 通道，工程代码里用的 1883 是 TCP 通道，两个口都能连上同一个 EMQ），状态变为已连接后，在订阅区填上与测试代码一致的 `test_topic` 并订阅。回到 IDEA 运行测试方法，启动无报错，管理台右侧消息列表随即出现 EMQ 接收到的消息，内容正是 `test_content`——发布链路打通。

## 三、订阅消息：MqttCallback 回调与启动监听

订阅和发送方向相反：工程代码订阅一个主题，再从 EMQ 的 Websocket 工具向该主题发消息，看工程能不能收到。

第一步仍是封装方法，在 `EmqClient` 里加：

```java
/**
 * 订阅主题
 * @param topicName 主题名称
 */
public void subscribe(String topicName) throws MqttException {
    mqttClient.subscribe(topicName);
}
```

第二步是关键：得有一个"接收的地方"。外部系统往 EMQ 发消息、工程订阅了这个主题，消息到了之后由谁来处理？这靠回调。`com.yikekong.emq` 包下新建消息处理类 `EmqMsgProcess`，加 `@Component`，实现 `MqttCallback` 接口：

```java
@Component
@Slf4j
public class EmqMsgProcess implements MqttCallback {

    @Override
    public void connectionLost(Throwable throwable) {
        // 连接丢失时触发
    }

    @Override
    public void messageArrived(String topic, MqttMessage mqttMessage) throws Exception {
        // 接收到消息时触发：第一个参数就是消息所属主题
        String payload = new String(mqttMessage.getPayload());
        System.out.println("接收到的消息：" + payload);
    }

    @Override
    public void deliveryComplete(IMqttDeliveryToken iMqttDeliveryToken) {
        // 消息传送完成时触发
    }
}
```

接口强制实现三个方法，重点在中间的 `messageArrived`——接收到消息后的处理逻辑都写在这里，消息内容通过 `MqttMessage` 参数传入，第一个参数则是主题名。此处先把报文用 `new String(mqttMessage.getPayload())` 转成字符串打印到控制台，后续的业务处理放到后面的章节。

第三步，回到 `EmqClient` 改造连接方法：在 `mqttClient.connect()` 执行之前，把回调类注册进来——注入 `EmqMsgProcess`，然后 `mqttClient.setCallback(emqMsgProcess)`。这样只要执行了订阅方法，再有人向该主题发消息，回调类就能收到。

第四步，让订阅在工程启动时自动发生。新建一个 `Monitor` 类，加 `@Component`，用 `@PostConstruct` 标注初始化方法——容器启动时必然调用：

```java
@Component
@Slf4j
public class Monitor {

    @Autowired
    private EmqClient emqClient;

    @PostConstruct
    public void init() {
        System.out.println("初始化方法，订阅主题");
        emqClient.connect();
        try {
            emqClient.subscribe("mytopic");  // 暂时写死，仅用于测试
        } catch (MqttException e) {
            e.printStackTrace();
        }
    }
}
```

测试流程：启动工程，控制台输出"初始化方法，订阅主题"说明方法已执行，工程随后进入监听状态。打开 EMQ 管理台（账号 admin、密码 public），仍用 Websocket 工具先连接，然后向 `mytopic` 发一条消息——左侧列表出现已发送记录，IDEA 控制台同步打印出接收到的消息内容。收发闭环成立，订阅代码没有问题。

## 四、订阅指标主题：动态订阅、共享订阅与断线重连

前面订阅的 `mytopic` 是写死的，只是验证手段。亿可控真正的需求是订阅"指标配置中的主题"——添加指标时必须指定报文主题，指标数据就从该主题的报文中提取；所有指标都存在指标配置表里。实现思路两点：

1. 系统启动时，把库里存储的所有主题名称取出来，循环调用订阅方法；
2. 系统运行期新增指标时，新增指标的方法里也要调用订阅。

对应第一处，`QuotaService` 里已经有现成的 `getAllSubject()`（导入工程自带，内部已做筛选）：用 `QueryWrapper` 只查询 `subject` 列再映射成字符串列表：

```java
@Override
public List<String> getAllSubject() {
    QueryWrapper<QuotaEntity> wrapper = new QueryWrapper<>();
    wrapper.lambda().select(QuotaEntity::getSubject);
    return this.list(wrapper).stream()
            .map(q -> q.getSubject())
            .collect(Collectors.toList());
}
```

`Monitor` 里注入 `QuotaService`，把写死的订阅改成循环：

```java
@PostConstruct
public void init() {
    emqClient.connect();
    quotaService.getAllSubject().forEach(s -> {
        try {
            emqClient.subscribe("$share/" + s);
        } catch (MqttException e) {
            e.printStackTrace();
        }
    });
}
```

注意 `$share/` 前缀，这是为集群准备的。单机部署直接订阅没问题；但若亿可控部署集群，每个节点都订阅同一主题就变成广播——每条消息所有节点都收到，显然不行，必须保证一条消息只被一个节点消费。共享订阅（在主题名前加 `$share/`）就是干这个的：多个节点分摊消息，每个消息只有一个节点收到。

对应第二处，新增指标的入口在 `QuotaController` 的 `create` 方法。注入 `EmqClient`，在保存之前执行订阅：

```java
@PostMapping
public boolean create(@RequestBody QuotaVO vo) {
    QuotaEntity quotaEntity = new QuotaEntity();
    BeanUtils.copyProperties(vo, quotaEntity);
    try {
        emqClient.subscribe("$share/" + vo.getSubject());
    } catch (MqttException e) {
        e.printStackTrace();
    }
    return quotaService.save(quotaEntity);
}
```

还剩一个细节：网络抖动等因素可能导致连接丢失，连接丢了订阅自然失效。`EmqMsgProcess` 实现的 `MqttCallback` 里正好有 `connectionLost` 方法，连接丢失时自动触发——在这里重新 `emqClient.connect()`，再把启动时那段"取所有主题循环订阅"的逻辑复制过来执行，断线后就能自动恢复订阅。

测试走一遍完整流程。启动工程后，用 VS Code 的 `.http` 测试脚本调用创建指标接口：JSON 里指标名称"温度"、单位摄氏度、`subject` 填报文主题 temperature（温度的英文）、`valueKey` 填 tmp——对应报文里温度值所在的 key（例如设备报文 `{"sn":"123456","tmp":1.2}` 中 tmp 就是温度的 key）、`valueType` 是值类型、`snKey` 是设备标识的 key（与报文的 sn 相符）、webhook 本逻辑暂不涉及、参考值设 1-5。点 Send Request 返回 true 即成功；若出现 401 说明 token 过期，重新执行登录脚本，把新 token 复制替换即可。随后查库确认记录已落表，报文主题就是 temperature。

接着用 EMQ Websocket 工具连接后向 temperature 主题发送模拟报文 `{"sn":"123456","tmp":1.2}`，控制台立即收到数据——新增指标后订阅生效。把工程重启再发一次，依然能收到：重启走的是 `Monitor` 的初始化代码，它把库里全部主题取出循环订阅。而随便编一个没登记过的主题发消息，工程收不到——只有订阅了的主题才会收到消息。

## 五、指标数据解析上半场：DTO 设计与 analysis 骨架

订阅解决"报文进得来"，接下来是"报文读得懂"——按指标事先设定的解析规则，把必要的指标提取出来。先看指标配置都有什么：指标名称（系统里展示用）、单位（摄氏度、米等）、报文主题（MQTT 主题，接收解析的依据）、指标值字段（报文中需要解析的字段名）、指标数值类型（Double/String/Boolean）、设备标识码字段（区分设备方便存储）、web hook（指标数据需要透传到的外部 Web 接口地址）、安全值（指标数据安全的范围，给告警用）。

设计解析前必须认清报文形态：一条报文不一定只有一个指标。典型例子是一次上报带温度和湿度两个：

```json
{
  "sn": "123456",
  "temp": 1.2,
  "humi": 50
}
```

三个、四个指标也完全可能，数量不定。所以解析结果必须是"一个设备 + 多个指标"的结构。实现思路三步：定义封装设备和指标数据的 DTO；编写业务逻辑方法，入参为主题和报文转换成的 map，按主题提取数据；接收报文时调用该业务逻辑完成解析。

第一步建指标 DTO `QuotaDTO`（dto 包，`@Data` + 实现 `Serializable`），属性分两部分。一部分是指标配置信息，基本与指标配置表字段一致——只有把这些带上，后续处理时才能随手取用（比如要用 webhook 直接就能拿到）；另一部分是解析出来的指标值：

```java
@Data
public class QuotaDTO implements Serializable {
    private Integer id;            // 主键
    private String quotaName;      // 指标名称（为与设备信息区分而改名）
    private String unit;           // 单位
    private String subject;        // 报文主题
    private String valueKey;       // 报文中指标值所在的 key
    private String valueType;      // 值类型：Double/String/Boolean
    private String snKey;          // 设备标识码字段
    private String webhook;        // 透传的外部接口地址
    private String referenceValue; // 参考值

    private Double value;       // 数值型指标值
    private String stringValue; // 非数值型指标值
    private String deviceId;    // 设备编号
}
```

指标值用 Double 承载有个隐患：物联网报文的值不一定是数字，整型转 Double 没问题，可万一上报的是字符串或布尔值就麻烦了。办法是双字段兜底：数值存 `value`，非数值就存 `stringValue`。再加上 `deviceId` 标注这条指标属于哪个设备。

但单个 `QuotaDTO` 承载不了"一设备多指标"的报文，所以要再定义一个组合 DTO `DeviceInfoDTO`：

```java
@Data
public class DeviceInfoDTO implements Serializable {
    private DeviceDTO device;            // 设备信息
    private List<QuotaDTO> quotaList;    // 指标列表
}
```

第二步写解析逻辑。逻辑和指标相关，就定义在指标服务 `QuotaService` 里，方法名 `analysis`，返回 `DeviceInfoDTO`，入参两个：主题（根据什么主题来解析）和报文转换后的 Map（`payloadMap`，由接收到的 JSON 字符串转换而来）：

```java
/**
 * 解析报文
 * @param topic      主题
 * @param payloadMap 报文内容
 */
DeviceInfoDTO analysis(String topic, Map payloadMap);
```

第三步在 `QuotaServiceImpl` 中实现，整体三步：获取主题相关的指标配置、封装设备信息、封装指标列表信息。第一步先落地——注入 `QuotaMapper`，按主题查指标配置表：

```java
@Autowired
private QuotaMapper quotaMapper;

@Override
public DeviceInfoDTO analysis(String topic, Map payloadMap) {
    // 第一步：获取主题相关的指标配置
    QueryWrapper<QuotaEntity> wrapper = new QueryWrapper<>();
    wrapper.lambda().eq(QuotaEntity::getSubject, topic);
    List<QuotaEntity> quotaList = quotaMapper.selectList(wrapper);
    if (quotaList == null || quotaList.size() == 0) {
        // 主题查不到配置，没有继续解析的必要
        return null;
    }
    // 第二步：封装设备信息（下一篇继续）
    // 第三步：封装指标列表（下一篇继续）
    return null;
}
```

一个报文主题可能对应多条指标配置，所以按 `subject` 精确筛选出该主题的记录；查出来为空说明这个主题根本没登记过指标，直接返回 null，后面的解析无从谈起。设备信息与指标列表的封装，留到解析的下半场继续。

## 小结

这一篇把亿可控接入 EMQ 的完整链路铺完了。客户端选型：Eclipse Paho 的 Java 同步实现；发送侧五步：依赖、Consul 配置、`EmqConfig`、`connect()`（UUID 保证 clientId 唯一）、`publish()`，并用管理台 Websocket 工具完成发布验证；订阅侧三件套：`subscribe` 方法、实现 `MqttCallback` 的 `EmqMsgProcess`（`messageArrived` 收消息）、`setCallback` 挂接，`Monitor` 用 `@PostConstruct` 启动即订阅。真实业务再把写死主题换成指标配置表驱动：启动循环订阅 + 新增指标即时订阅，集群用 `$share/` 共享订阅防广播，`connectionLost` 里重连重订阅兜底。解析侧完成了 `QuotaDTO`/`DeviceInfoDTO` 两级 DTO 与 `analysis` 方法的骨架和第一步"按主题查配置"。下一篇接着走完设备与指标封装，让解析真正产出数据。
