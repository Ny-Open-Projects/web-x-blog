# 架构方法收尾与演进之路：系统、技术、数据、部署四张图，从单体杀到分布式

上一篇讲了业务架构和功能架构，这一篇把架构方法的剩下四种补齐：系统架构、技术架构、数据架构、部署架构，然后进入架构演进之路——系统架构不是一蹴而就的，它经历了从单体架构到分布式架构、再到微服务架构的演化。每种架构在什么阶段出现、解决了什么问题、又留下了什么新问题，是这一章的主线。

## 先给结论

- 系统架构的使用者是系统架构师，图按用户请求的层次来画：前端请求 → 网关层（应用/运营/支付/第三方网关，做路由和负载）→ 应用集群（用户、商品、订单等子系统）→ 公共服务层 → 数据层（数据库集群、分布式缓存、分布式会话、分布式消息队列）。
- 技术架构同样由系统架构师使用，回答"项目用了哪些技术"，技术必须分类分层：前端（Element UI、ECharts、Vue.js）、后端（Spring Boot/MyBatis/MyBatis-Plus）、服务（Kafka、Flink、Quartz）、存储（Redis、MySQL、Apache Druid）。
- 数据架构面向 CTO、系统架构师、数据架构师，两个层面：一是数据模型即数据库设计；二是大数据平台的数据流转——采集 → 存储分析 → 共享层 → 应用层。
- 部署架构面向运维架构师，展示部署后需要哪些服务、谁先谁后、调用关系，要落到每台服务器的 CPU、内存、操作系统这类配置信息。
- 单体架构的优点是投入少、管理/开发/测试都简单，但可用性差、稳定性差、性能差——应用和数据库全是单点，改一行代码也要重启。
- 分布式架构就是多个实例提供服务，表现形式有应用集群、分布式缓存、业务拆分、分库分表、读写分离、静态化和 CDN 等；其中业务拆分用得最多，分水平拆分（按业务分模块）和垂直拆分（抽公共服务）两个方向。

## 系统架构与技术架构：请求视角与技术视角

系统架构图的特点是站在用户请求的层次上展示——请求先到哪、再到哪。用户前端发请求，首先进入网关层，网关层主要做路由和负载，包括应用网关、运营网关、支付网关、第三方网关等；然后请求进入应用集群，对应一个个子系统：用户子系统、商品子系统、订单子系统等；子系统往下调用服务，比如文件公共服务、短信公共服务；再往下是更底层的公共基础设施——数据库集群、分布式缓存、分布式会话、分布式消息队列。

技术架构换了一个角度：从技术的角度看整个项目用到了哪些技术，这些技术也要分层。课程举了冷链项目的技术架构图，分成四层：

| 层次 | 典型技术 |
|---|---|
| 前端 | Element UI、ECharts、Vue.js、Node.js |
| 后端 | Spring MVC、Spring Boot、MyBatis、MyBatis-Plus |
| 服务 | Kafka、Flink、Quartz、Superset |
| 存储 | Redis、MySQL、Apache Druid |

课上还打开了一个 Spring Cloud 技术架构图，层次更多：展示层技术栈（安卓、iOS、微信小程序、H5 公众号、PC 端）、网关层技术栈（Nginx、Zuul、防火墙、Keepalived、VPN）、业务层和数据层。业务层里又有服务治理（配置中心、注册中心、集群监控、链路追踪、服务熔断、OAuth2 授权）和技术平台：Spring Boot 基础平台、Feign 远程调用、Ribbon 负载均衡、MyBatis 持久化、Swagger API 文档、Undertow（类似 Tomcat 的服务容器）。要点是：技术不是简单堆积，需要分类、分层。

## 数据架构与部署架构：数据怎么流，服务怎么放

数据架构的使用者是 CTO、系统架构师、数据架构师，从两个层面讲。第一个层面是数据模型，也就是数据库设计：产品、订单实例、渠道，每个模型对应一张表，表里有哪些字段（产品 ID、产品代码等）一目了然。每个项目都有数据库甚至不止一个，库里每张表有自己的结构，这些数据模型就属于数据架构的范畴。

第二个层面是大数据平台的数据架构，展示数据从哪来、怎么用：

| 层次 | 职责 |
|---|---|
| 数据采集层 | 从日志、RDBMS（关系型数据库）、HTTP/FTP 接口采集原始数据 |
| 存储与分析层 | 采集后先清洗，再存储分析：HDFS 做离线分析（Spark SQL、Spark MLlib），Kafka 做实时分析（Spark Streaming） |
| 数据共享层 | 存放分析产生的统计结果：RDBMS、Redis、Apache Kylin、HBase |
| 数据应用层 | 供上层调用：报表、接口、即席查询、数据可视化 |

旁边还有一条竖贯的"任务调度与监控"。下层是上层的基础，整张图就是数据处理全流程。

部署架构的使用者是运维架构师，展示的是系统部署之后：整个系统需要哪些服务，它们之间谁先谁后、调用关系是什么样。以冷链项目为例——用传感设备监测冷链车辆的温度、湿度等指标（运输药品时对车内环境要求严格），数据链路是：传感设备 → Nginx → Netty（报文采集）→ Kafka 消息中间件 → Flink 实时处理 → 处理好的数据存入 Redis 或 MySQL → 应用服务器集群对外展示 → 数据分析中心、报表中心以图形报表呈现。从这张图就能看出需要部署应用服务器、Redis、MySQL、Flink、数据分析中心、HDFS 数据存储中心等一整套东西。另一个示例更细：PC 客户端经互联网进来，先过 SLB 负载均衡，再到应用层（平台系统、API 网关），往下是基础服务层（Kafka 集群、PaaS Server）、数据层（MySQL、MongoDB），最后甚至列出每台服务器的 CPU、内存、操作系统配置。

## 演进的起点：单体架构

架构演进有三个阶段：单体架构 → 分布式架构 → 微服务架构。单体架构出现在公司发展初期：资金少、用户少，数据量和并发量都小，大多数系统只需要一台服务器就能满足需求。所有业务逻辑都在单一应用系统里，单应用单数据库；数据库可以和应用部署在同一台服务器上，也可以单独一台。

它的技术栈在今天看都很熟悉：操作系统是 Windows/Linux，应用服务器有 Tomcat、Jetty、JBoss、WebLogic 等，数据库有 MySQL、Oracle、DB2 等，应用系统用 Java、PHP、ASP 各种语言开发都行。优点很明显：投入少，一两台服务器搞定；管理简单，上线、部署、监控、问题排查都简单——整个系统可能就是一个 war 包扔进 Tomcat 启动就完事，不像微服务动辄几十台服务器；开发简单，创建一个项目就行，不用考虑服务依赖；测试也简单。

但业务快速发展后，单体架构从三个维度受到考验：用户要求高可用（随时能访问）、高性能（不能慢）；业务要求需求多、变更快、发布频繁；客观条件上用户多分布广、海量数据、网络复杂、安全环境恶劣。于是三个缺陷凸显：

| 缺陷 | 原因 |
|---|---|
| 可用性差 | 应用和数据库都是单点，无论哪个出问题，整个系统不可用 |
| 稳定性差 | 耦合度高，新增或修改任何功能、哪怕一行代码也要重启服务器，重启期间系统不可用 |
| 性能差 | 单一应用服务器和数据库服务器性能有上限，并发访问一多就慢甚至挂掉 |

单体架构如今越来越少，了解这个形态和它的局限就够了。

## 分布式架构：六种表现形式

分布式就是多个实例提供服务，最直观的是服务器数量变多了。它涵盖的面非常广：应用集群、分布式缓存、业务拆分、分库分表、读写分离、静态化和 CDN，还有异步解耦等，都属于分布式架构的范畴。

**应用集群**是最基础的形式：反向代理服务器（Nginx、HAProxy）部署两台解决单点，电商系统部署三节点集群，数据库做主从结构——操作主库，数据自动同步到从库。三个优点：可用性提高，某台机器挂掉后其他机器几乎无感地接替任务；性能比单体高，同配置下多台服务器对外服务，粗略认为接近单体的三倍（一般达不到）；安全性高，外网用户只能访问反向代理服务器，应用和数据库隔离在内网。集群的特点是每台服务器部署的程序完全一样——电商系统部署三份，功能一模一样。

**分布式缓存**解决的是内存瓶颈。缓存分多级：本地缓存在 JVM 中，访问速度快，但用的是应用服务器自己的内存，缓存数据量有限，还会和应用争用内存（内存不够用、内存泄露）；分布式缓存（Redis 集群）可以用集群方式扩展，理论上不受内存限制——不够就加硬件，部署大内存服务器做专门的缓存服务器。代价是有网络开销，但集群下开销很少，基本可忽略。常见的缓存服务器是 Redis（现在用得最多）和 Memcached。使用缓存后，数据访问压力得到有效缓解。

**业务拆分**是分布式架构里用得最多的形式。应用集群那三台虽然看着多，但项目本身还是单体——所有功能堆在一块。用户越来越多，系统又出现瓶颈，就要按业务拆分：水平拆分把电商系统拆成商品、订单、交易、用户、支付等多个系统，每个系统都是多台服务器构成的集群，各自保证高可用；垂直拆分则把跟业务关系不大的公共业务和服务剥离出来，比如注册登录中心、用户中心、短信、文件服务、消息服务——短信谁都可能发，商品、订单、交易模块都要调，单独拆成公共服务，谁需要谁调用。企业开发中水平拆分用得非常多，垂直拆分也常用。好处是应用系统增多、性能提高，公共服务供所有应用使用、达到服务复用的效果。但注意：这时数据库还是主从两个库，增删改都压在主库上，从库只提供查询、分担不了写压力，用户一多数据库就成了新瓶颈。

**分库分表和读写分离**就是冲着数据库瓶颈去的。读写分离基于主从结构：主流数据库基本都支持主从热备，应用服务器写数据访问主库，主库通过主从复制机制把数据同步到从库，读数据直接读从库，压力分摊到两台服务器；从库还能再做集群，读操作从多个从库走，性能进一步提高。分库分表则更进一步：商品模块操作商品库，订单模块操作订单库，交易模块操作交易库——按业务把数据库拆开，这是分库；单表数据量太大还可以分表，比如订单表按月份拆成 12 张表。拆的动机除了查询时间随数据量增长变长，还有故障半径：单库出意外要修复所有数据，多库中一个库出意外只需修复一个库。分库分表策略很多，通常按用户、订单、交易、商品等业务维度分库，再按时间分表；性能提升显著，但管理和维护成本也高。为便于程序访问，通常有专门的数据访问模块，对程序透明，代码不用关心数据到底存在哪张表。

**静态化和 CDN** 是面向用户的最后一层。原先客户端直接访问代理服务器再转发到内网，现在在代理服务器前面多了一个 CDN 服务器——相当于做了一层缓存：请求的资源在 CDN 上已经存在，就直接返回给客户端，后面的请求根本不会发生。CDN 按地理位置就近部署，在北京就请求北京的节点，在南京就请求南京的，响应最快。背景是用户规模越来越大，加上复杂的网络环境，不同地区访问速度差别极大，为了留住用户网站需要加速。做法是把动态页面静态化（如生成 HTML 页面），商品详情页在发布时生成静态页面，静态页面和静态资源放到 CDN 服务器、部署在网络服务提供商的机房，用户从距离自己最近的机房获取数据。绝大部分企业没有能力自建 CDN（全国布点成本太大），一般购买收费服务，比如阿里云的 CDN。

## 小结

四张架构图各管一个视角：系统架构画请求路径，技术架构画技术选型分层，数据架构画数据模型与数据流转，部署架构画服务器部署与调用顺序。架构演进则是被问题推着走的过程：单体架构便宜简单但三点全崩——可用性、稳定性、性能；分布式用"多个实例提供服务"逐一击破：应用集群消灭单点，分布式缓存突破内存限制，业务拆分化解功能堆砌，分库分表和读写分离纾解数据库瓶颈，静态化与 CDN 把静态资源推到离用户最近的节点。每一招都解决了上一阶段的问题，也埋下了新的复杂度——这正是下一站微服务和服务化要继续处理的话题。
