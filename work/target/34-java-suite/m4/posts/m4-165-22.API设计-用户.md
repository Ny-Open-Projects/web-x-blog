# 用户域 API 设计收官：只管 B 端用户的用户微服务

立可得第一章的 API 设计走到最后一站：用户域。这个微服务封装的是 B 端用户逻辑，范围划得非常干脆：管理员、配送员、维修员，仅此三类；至于扫码买货的 C 端消费者，它一概不管。为什么敢这么砍、三张核心表的字段怎么定、接口清单长什么样，这一篇把用户域一次说透，也算给第一章的 API 设计做个收尾。

## 先给结论

- 用户微服务里的"用户"专指 B 端：管理员、配送员、维修员；C 端购买者不在管理范围之内。
- C 端不管理的根因在业务形态：售货机本身就是一个柜子，购买者扫码即买，平台不知道购买者是谁，也不采集、不管理其信息，相当于一锤子买卖，每个购买者都是匿名的。
- 1.0 版本的下单入口是 H5 页面；如果扫码方换成小程序或 APP，平台才具备采集和管理 C 端用户的条件。
- 用户域一共三张表：tb_user（用户）、tb_role（角色）、tb_company（公司，也叫合作商表）。
- 用户归属靠 role_id 与 role_code 区分角色，靠 company_id 挂到公司；tb_company 的 business_type 用 0/1 区分平台方与加盟客户，合作商用户的 company_id 指向的那家公司，business_type 必为 1。
- API 设计分两组：用户 API（登录、维修员列表、配送员列表）与公司 API（合作商增删改查共 5 个接口）。

## C 端为什么不管：一锤子买卖

售货机的交易形态决定了用户域的边界。售货机本身就是一个柜子，购买者扫柜身上的二维码进入下单页面，完成支付、货掉出来，这笔交易就结束了。整个过程里，平台并不知道这个购买者是谁，也不会对他的信息做任何采集和管理。对平台而言，每一个购买者都是匿名的，正所谓一锤子买卖。

这是立可得项目的一个鲜明特点，而不是设计上的偷懒。业务上并非没有改进空间：如果扫码这一方是小程序或者 APP，用户登录之后平台就拿到了身份，可以顺理成章地采集和管理 C 端用户。但在 1.0 版本里，下单入口就是一个 H5 页面，没有这层承载登录态的载体，所以用户微服务只面向 B 端。想清楚这一点，后面的表结构才好理解：既然不管 C 端，表里的字段就全都围绕"后台里的人"展开，不会出现任何消费者身份信息。

## 三张表撑起用户域

用户域一共三张表，先把字段摆出来，再看它们之间的关联。

**tb_user 用户表**，存的是 B 端用户：

| 字段名称 | 字段含义 | 字段类型 |
| :--- | :--- | :--- |
| id | 主键 | INT |
| role_id | 角色 ID | INT |
| user_name | 用户名称 | VARCHAR |
| login_name | 登录名 | VARCHAR |
| password | 密码 | VARCHAR |
| area_id | 区域 ID | INT |
| secret | 私钥 | VARCHAR |
| role_code | 角色编号 | VARCHAR |
| mobile | 手机号 | VARCHAR |
| company_id | 公司 ID | INT |

有几个字段值得展开说：

- role_id 与 role_code 成对出现。role_id 对应角色表的系统分配 ID，role_code 是带业务含义的角色编号。一个用户到底属于管理员、配送员还是维修员，就靠这两个字段区分。
- user_name 是显示用的中文名称，login_name 是登录用的英文名称，一个管展示、一个管登录，职责分开。
- secret 是 JWT 登录时用于校验身份的私钥。
- area_id 表示这个用户属于哪个区域，区域域在第一章前面已经设计过，这里直接引用。
- company_id 关联另一张表 tb_company，也就是公司表，也叫合作商表。

**tb_role 角色表**，只有三个字段：

| 字段名称 | 字段含义 | 字段类型 |
| :--- | :--- | :--- |
| role_id | 主键 | INT |
| role_code | 角色编号 | VARCHAR |
| role_name | 角色名称 | VARCHAR |

**tb_company 公司表（合作商表）**，主要记录平台或合作商的名称：

| 字段名称 | 字段含义 | 字段类型 |
| :--- | :--- | :--- |
| id | 主键 | INT |
| business_type | 0:平台方;1:加盟客户 | INT |
| name | 合作商名称 | VARCHAR |

tb_company 里的 business_type 是个关键的业务类型字段：0 表示平台方，1 表示加盟商户（合作商）。平台自己这一方，对应的就是那条 business_type 为 0 的公司记录；如果某个用户是合作商的人，他在 tb_user 里的 company_id 所指向的那家公司，business_type 一定是 1。用户域和公司域的关系就靠这条约定打通：查用户时顺着 company_id 落到公司表，看一眼 business_type 就知道这个人背后是平台还是某个合作商。

## API 清单：用户 API 与公司 API

用户域的接口设计分两组。

用户 API 有三个：

- 登录：进入后台的入口逻辑。
- 维修员列表
- 配送员列表

后两个接口是给工单逻辑用的，维修单、配送单在派单和执行过程中需要调出对应角色的人员，所以在这里预先把列表接口设计好。

公司 API 围绕合作商的增删改查展开，一共五个：

- 全部合作商
- 分页查询
- 合作商修改
- 合作商新增
- 检索合作商

一个取全量的下拉数据源，一个管分页浏览，两个管写操作，一个管条件检索，合作商管理的常用姿势基本都覆盖了。

## 小结

用户域是第一章 API 设计的收官之作。这一章从区域、点位、售货机、货道、商品、工单、订单一路设计过来，最后落在用户域，各大业务域的接口边界到此全部划定。回顾这一域的设计思路，其实只有三步：先把"用户是谁"这个业务问题想透，B 端才叫用户，C 端因为 H5 一锤子买卖而天然匿名；再用三张表把角色、公司两层关系挂上去，role_id 定角色、company_id 定归属；最后按使用场景列接口，登录给后台，两个角色列表给工单逻辑，五个接口管合作商。表结构服务于业务边界，API 清单服务于后续开发排期，这正是 API 设计阶段该有的样子。
