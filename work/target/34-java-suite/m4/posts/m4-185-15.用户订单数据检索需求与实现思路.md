# 用户订单数据检索：需求思路、三段代码实现与测试

立可得 2.0 给微信小程序加了一个新功能：用户能查询自己的历史订单，还能按日期范围检索。实现层面这是一次典型的跨服务查询——订单数据此前已经同步进了 Elasticsearch，查询逻辑封装在订单微服务里，小程序微服务通过 Feign 远程调用。这一小节用三个视频依次讲完三段代码实现与最后的测试，这里按思路、条件封装、结果组装、接口与联调四段串成一篇。

## 先给结论

- 需求：用户在微信小程序中根据日期范围检索历史订单，界面上是订单列表加一个日期范围选择器。
- 查询逻辑封装在订单微服务里，直接查 Elasticsearch（订单数据已在前面小节同步过去）；小程序微服务用 Feign 远程调用，管理后台以后查订单也能复用这个方法。
- 接口六个参数全部走 query 传参：pageIndex、pageSize、orderNo、openId、startDate、endDate；日期前端传的是字符串，后端也按 String 接。
- 条件封装三件套：`new SearchRequest("order")` 定索引、`SearchSourceBuilder` 装分页和 query、`BoolQueryBuilder` 用 must 串条件；订单号、openId 用 termQuery 且都判空可选，时间范围用 rangeQuery 的 gte/lte，两端都传了才加。
- 分页 `from = (pageIndex - 1) * pageSize`，记得加 `trackTotalHits(true)`，否则数据量超过一万条时总数最多只统计到 9999。
- 结果组装逐条 JSON 转对象，create_time/update_time 用 `DateTimeFormatter.ISO_DATE_TIME` 解析；最后装进 Pager，异常兜底 `Pager.buildEmpty()`。

## 需求与实现思路：查 ES，而不是查库

需求描述只有一句话：用户在微信小程序中能够根据日期范围检索历史订单。对应的效果图是一个「订单管理」页面：订单列表里每条记录带订单号、金额、状态等信息，顶部有一个日期范围选择器，示例里选的是 2020-06-09 到 2020-07-09。这种查历史订单的业务场景在很多系统里都会出现，做法可以举一反三。

实现思路两条：

1. 查询逻辑封装到订单微服务中。第二小节已经把订单数据同步到了 Elasticsearch，所以查询直接查 ES 里的数据，更好更快。
2. 微信小程序微服务通过 Feign 远程调用订单微服务的查询方法。

还有一点值得注意：这个查询方法不一定只服务微信小程序。管理后台要查订单，同样可以重用这个方法——把逻辑沉在订单微服务里，多个端都能受益。

## 实现一：依赖、配置与查询条件封装

第一步，给订单微服务添加 Elasticsearch 相关的三个依赖，版本统一 7.7.1：

```xml
<dependency>
    <groupId>org.elasticsearch.client</groupId>
    <artifactId>elasticsearch-rest-high-level-client</artifactId>
    <version>7.7.1</version>
</dependency>
<dependency>
    <groupId>org.elasticsearch</groupId>
    <artifactId>elasticsearch</artifactId>
    <version>7.7.1</version>
</dependency>
<dependency>
    <groupId>org.elasticsearch.client</groupId>
    <artifactId>elasticsearch-rest-client</artifactId>
    <version>7.7.1</version>
</dependency>
```

第二步，加配置。Elasticsearch 的连接地址加在 Consul 配置中心订单服务的配置文件里、spring 节点下，和数据源、ribbon 超时等配置放在一起：

```yaml
spring:
  datasource:
    url: jdbc:mysql://192.168.200.128:3306/ikd_order?useUnicode=true&autoReconnect=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
    username: root
    password: root123
  ribbon:
    connectTimeout: 500
    readTimeout: 1000
```

第三步，定义接口。在订单微服务的 OrderService 接口里新增 search 方法，返回分页结果对象，泛型用订单视图模型 OrderViewModel；参数照着 API 文档来——页码、页大小、订单编号、openId、开始时间、截止时间。前端传来的开始和截止时间肯定是字符串，所以这两个参数也按 String 处理：

```java
Pager<OrderViewModel> search(Integer pageIndex, Integer pageSize,
                             String orderNo, String openId,
                             String startDate, String endDate);
```

实现类 OrderServiceImpl 里先把 ES 高级客户端对象注入进来，之后整个查询全靠它操作 Elasticsearch：

```java
private RestHighLevelClient esClient;
```

查询方法整体分两大部分：封装查询条件、封装查询结果。先写第一部分：

```java
SearchRequest searchRequest = new SearchRequest("order"); // 查 order 索引
SearchSourceBuilder sourceBuilder = new SearchSourceBuilder();
BoolQueryBuilder boolQueryBuilder = QueryBuilders.boolQuery();

// 订单号精确匹配：按文档不是必传，判空后再加条件
if (!Strings.isNullOrEmpty(orderNo)) {
    boolQueryBuilder.must(QueryBuilders.termQuery("order_no", orderNo));
}
// openId 精确匹配：同样可选
if (!Strings.isNullOrEmpty(openId)) {
    boolQueryBuilder.must(QueryBuilders.termQuery("open_id", openId));
}
// 时间范围：开始与截止都不为空才做范围查询
if (!Strings.isNullOrEmpty(startDate) && !Strings.isNullOrEmpty(endDate)) {
    RangeQueryBuilder rangeQueryBuilder = QueryBuilders.rangeQuery("update_time");
    rangeQueryBuilder.gte(startDate);
    rangeQueryBuilder.lte(endDate);
    boolQueryBuilder.must(rangeQueryBuilder);
}

// 分页：from 是从哪条开始查，从 0 起算
sourceBuilder.from((pageIndex - 1) * pageSize);
sourceBuilder.size(pageSize);
sourceBuilder.query(boolQueryBuilder);
// 突破一万条的统计上限
sourceBuilder.trackTotalHits(true);
searchRequest.source(sourceBuilder);
```

三个条件都加在 bool 查询构建器上，用 must 连接。订单号和 openId 参照文档是可选参数，有可能没传，所以先判空再加；时间范围查询用 rangeQuery，范围字段是 update_time，大于等于开始日期（gte）、小于等于截止日期（lte）。分页的 from 等于 `(pageIndex - 1) * pageSize`。trackTotalHits 值得单独记一笔：from 加 size 默认上限一万条，数据量大时总数最多只会反馈 9999，加上 `trackTotalHits(true)` 才能把超过一万条的记录也全部统计出来。

## 实现二：执行搜索并组装分页结果

第二部分是执行搜索，把返回的 JSON 数据转成分页对象：

```java
SearchResponse searchResponse = esClient.search(searchRequest, RequestOptions.DEFAULT);
SearchHits hits = searchResponse.getHits();
SearchHit[] searchHits = hits.getHits();

List<OrderViewModel> orderList = Lists.newArrayList();
for (SearchHit hit : searchHits) {
    String hitResult = hit.getSourceAsString(); // 每条文档的 JSON 字符串
    JsonNode jsonNode = JsonUtil.getTreeNode(hitResult);

    OrderViewModel order = new OrderViewModel();
    order.setId(jsonNode.findPath("id").asLong());
    order.setStatus(jsonNode.findPath("status").asInt());
    // 其余字段以此类推，对照讲义与索引数据逐个提取

    // 两个时间字段需要单独转换
    order.setCreateTime(LocalDateTime.parse(
            jsonNode.findPath("create_time").asText(),
            DateTimeFormatter.ISO_DATE_TIME));
    order.setUpdateTime(LocalDateTime.parse(
            jsonNode.findPath("update_time").asText(),
            DateTimeFormatter.ISO_DATE_TIME));
    orderList.add(order);
}
```

调用链路是：esClient.search 传入 searchRequest 和 RequestOptions.DEFAULT，拿到 SearchResponse；getHits 得到 SearchHits；再 getHits 得到 SearchHit 数组——这里面才是查到的数据。但数组不能直接返回，最终要封装成 Pager，主体是一个 List，所以先 new 一个空集合，再 for 循环逐条转换。

每条数据用 `hit.getSourceAsString()` 拿到 JSON 字符串，JsonUtil.getTreeNode 把它转成 JsonNode，然后 findPath("字段名") 取值、asLong/asInt 等方法做类型转换，set 进 OrderViewModel。字段名和查询结果里的一致，照着数据逐个对照即可，课堂上这段是直接从讲义里拿的代码。写完还可以打开 Kibana 看一眼 order 索引的 _mapping，确认 id、order_no、status、create_time、update_time 等字段的类型与映射关系，验证代码里用的字段名和实际存储一致。

两个时间字段是特例：create_time 和 update_time 在 ES 里是 ISO 格式的文本，先 asText 拿到字符串，再用 `LocalDateTime.parse(text, DateTimeFormatter.ISO_DATE_TIME)` 解析——只要文本符合这个时间格式，就能转成 LocalDateTime。

最后组装 Pager：

```java
Pager<OrderViewModel> pager = new Pager<>();
pager.setCurrentPageRecords(orderList);         // 当前页记录
pager.setTotalCount(hits.getTotalHits().value); // 总记录数
pager.setPageSize(searchHits.length);           // 本页条数
pager.setPageIndex(pageIndex);                  // 当前页码
return pager;
```

整个方法包在 try/catch 里，发生异常时返回 `Pager.buildEmpty()`——一个空的分页结果，方法里原先占位的 return null 删掉。到这里查询逻辑就完整了。

## 实现三：Controller、Feign 与降级，联调测试

业务方法写完，接下来是订单微服务的 OrderController。按接口文档定义 search 接口，一共六个参数，全部通过 query 方式传输，也就是问号传参：

```java
@GetMapping("/search")
public Pager<OrderViewModel> search(
        @RequestParam(value = "pageIndex", required = false, defaultValue = "1") Integer pageIndex,
        @RequestParam(value = "pageSize", required = false, defaultValue = "10") Integer pageSize,
        @RequestParam(value = "orderNo", required = false, defaultValue = "") String orderNo,
        @RequestParam(value = "openId", required = false, defaultValue = "") String openId,
        @RequestParam(value = "startDate", required = false, defaultValue = "") String startDate,
        @RequestParam(value = "endDate", required = false, defaultValue = "") String endDate) {
    return orderService.search(pageIndex, pageSize, orderNo, openId, startDate, endDate);
}
```

然后要在 service-common 工程的 Feign 接口 OrderService 里做定义，供小程序微服务远程调用。方法签名把刚才 Controller 的部分拿过来，路径加上 order 前缀：

```java
@FeignClient(value = "order-service", fallbackFactory = OrderServiceFallbackFactory.class)
public interface OrderService {

    @GetMapping("/order/search")
    Pager<OrderViewModel> search(
            @RequestParam(value = "pageIndex", required = false, defaultValue = "1") Integer pageIndex,
            @RequestParam(value = "pageSize", required = false, defaultValue = "10") Integer pageSize,
            @RequestParam(value = "orderNo", required = false, defaultValue = "") String orderNo,
            @RequestParam(value = "openId", required = false, defaultValue = "") String openId,
            @RequestParam(value = "startDate", required = false, defaultValue = "") String startDate,
            @RequestParam(value = "endDate", required = false, defaultValue = "") String endDate);
}
```

Feign 接口做好之后修改降级类 OrderServiceFallbackFactory，调用失败时记录日志并兜底空分页：

```java
@Override
public OrderService create(Throwable throwable) {
    log.error("订单服务调用失败", throwable);
    return new OrderService() {
        @Override
        public Pager<OrderViewModel> search(Integer pageIndex, Integer pageSize, String orderNo,
                                            String openId, String startDate, String endDate) {
            return Pager.buildEmpty();
        }
        // requestPay、cancel 维持原有兜底
    };
}
```

最后一步是微信小程序微服务：在它的 OrderController 里声明一个和订单微服务同名同参的方法，内部转手调 Feign 接口即可。至此用户订单数据检索的代码全部完成。

测试分两步。先依次启动订单微服务、微信小程序微服务和微信小程序网关三个服务，然后打开 VS Code 里的小程序测试脚本，找到一个「订单搜索」请求，点击 send request，查询结果直接返回——请求走的是网关 localhost:9000 的 /order/search。脚本测通后再用微信开发者工具联调：小程序主界面已经能看到「最近订单」，点「查看历史」进入订单列表，按日期范围筛选，效果与需求图一致。

## 小结

- 数据源的选择是小节的关键决策：订单数据已经同步进 ES，查询走 Elasticsearch 高级客户端，而不是回 MySQL 翻大表。
- 查询逻辑沉在订单微服务，小程序微服务只做 Feign 转发；管理后台查订单同样可以复用这个接口。
- 条件封装三件套：SearchRequest 定索引、SearchSourceBuilder 装分页与 query、BoolQueryBuilder 用 must 串条件；可选条件先判空。
- trackTotalHits(true) 别漏，否则默认最多只统计到 9999 条。
- 结果是 JSON 文本逐字段提取，时间字段用 DateTimeFormatter.ISO_DATE_TIME 解析，最后装 Pager，异常兜底 buildEmpty。
- Feign 定义在 service-common，路径 /order/search，降级工厂返回空分页，订单服务故障也不影响小程序端的整体可用。
