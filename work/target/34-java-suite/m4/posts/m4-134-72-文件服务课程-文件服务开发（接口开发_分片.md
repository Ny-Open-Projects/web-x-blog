# 分片上传（下）：FileChunkStrategy 策略体系、加锁校验与本地 FileChannel 合并

分片全部收上来只是半成品——磁盘上是 n 个用数字命名的碎片文件，旁边还躺着一个 .tmp 时间戳。这一篇完成把它们拼回原始文件的下半程：先照着文件处理策略的样子搭一套分片合并的策略体系，再把路径定位、数量校验、加锁、排序、清理这些通用流程收进抽象类，最后在本地策略的实现类里用 NIO 的 FileChannel 把分片真正写出原始文件。合并 Controller 接口的编写与跨策略测试，在课程后续部分收尾。

## 先给结论

- 合并不写在 Controller 里，而是复刻上传时的策略体系：FileChunkStrategy 顶层接口只声明一个 chunkMerge(FileChunksMergeDTO) 方法，下面挂 AbstractFileChunkStrategy 抽象类，再挂 LocalChunkServiceImpl、FastDfsChunkServiceImpl、AliChunkServiceImpl 三个子类，一种存储方式对应一个合并实现。
- FileChunksMergeDTO（name、submittedFileName、md5、chunks、ext、folderId、size、contextType）是合并的唯一入参：name 是原始文件名的 md5，用来定位分片目录；md5 是文件内容的 md5；分片上传接口返回的正是这个 DTO，全部分片传完后前端拿着它调合并接口。
- 抽象类收拢全部通用流程：拼合并文件名（name + 点 + ext）→ 定位年月目录 → 数量校验（目录实际文件数与 chunks 相等才继续）→ FileLock 加锁 → 分片按文件名数字升序排序 → 调子类 merge → cleanSpace 清理分片目录与 .tmp → 补齐属性后 fileService.save 入库。
- 并发安全靠资料提供的 FileLock 工具类：HashMap 存锁，synchronized 的 getLock/removeLock，以文件夹名（md5 值）为 key，finally 里先 unlock 再 removeLock，成败都要放锁。
- 排序是正确性的关键：分片文件名是 0、1、2 这样的数字字符串，字符串比较会乱序，必须用 NumberHelper.intValueOf 转成 int 相减，否则合并出来的文件内容错位。
- 本地策略的 LocalChunkServiceImpl 与已有的 LocalServiceImpl 一起写在 LocalAutoConfigure 配置类里，file type 配置为 local 时才注册进 Spring 容器；合并核心是 NIO FileChannel——FileOutputStream.getChannel 拿输入输出通道，一句 inChannel.transferTo(0, inChannel.size(), outChannel) 完成单分片搬运，每片读毕立即删除。

## 先铺策略体系：FileChunkStrategy 接口与三个实现类

分片合并的前提是明确"合并完存到哪"。不同存储方式下合并动作完全不同：本地就是把碎片按顺序读写到目标目录；FastDFS、阿里云 OSS 则要把合并结果推给对应的存储服务。这和文件上传时遇到的问题一模一样，所以接口设计直接照搬文件处理策略的结构——顶层一个 FileStrategy 接口、中间抽象类、底下 Local/FastDFS/阿里三个子类。分片合并如法炮制：FileChunkStrategy 顶层接口 → AbstractFileChunkStrategy 抽象类 → LocalChunkServiceImpl、FastDfsChunkServiceImpl、AliChunkServiceImpl 三个具体实现。

顶层接口只声明一个方法。返回值 R 的泛型是自定义的 File 对象——合并完成之后要把这个对象返回给前端展示；参数就是前面分片上传接口一路返回的 FileChunksMergeDTO：

```java
public interface FileChunkStrategy {
    /**
     * 分片合并
     * @param fileChunksMergeDTO 合并参数
     */
    R<File> chunkMerge(FileChunksMergeDTO fileChunksMergeDTO);
}
```

这个 DTO 的字段值得逐个过一遍：name 是 md5.js 对原始文件名计算的结果，与后端生成的分片目录名一致；submittedFileName 是原始文件名；md5 是 webuploader 自带算法对文件内容计算的值；chunks 是分片总数；ext 是后缀；folderId 是文件夹 id；size 是文件大小；contextType 是文件类型。前端在全部分片提交完成后发起合并请求，Controller 把请求参数封装成这个 DTO 传进来，合并所需的全部信息就都在了。

## FileLock 与抽象类：把通用流程收拢到一处

合并过程中有一段代码需要加锁，课程直接从资料"分片上传/后端"目录里拷来一个 FileLock 工具类放进 Utils 包。它的思路很朴素：一个 Map 保管所有锁对象，取锁时没有就 new 一个 ReentrantLock 放进去，用完按 key 删掉：

```java
@Component
public class FileLock {
    private static Map<String, Lock> LOCKS = new HashMap<>();

    // 获取锁：不存在就创建一个 ReentrantLock 存进 Map
    public static synchronized Lock getLock(String key) {
        if (LOCKS.containsKey(key)) {
            return LOCKS.get(key);
        }
        Lock one = new ReentrantLock();
        LOCKS.put(key, one);
        return one;
    }

    // 删除锁：执行完从 Map 里按 key 移除
    public static synchronized void removeLock(String key) {
        LOCKS.remove(key);
    }
}
```

接着在 impl 包下创建 AbstractFileChunkStrategy，让它 implements FileChunkStrategy。这个抽象类承担分片合并处理的整个流程：分片临时存储路径的获取、分片数量的检查、合并后临时文件的清理、合并后文件信息保存到数据库。真正"怎么把字节拼起来"的合并动作由子类完成——不同存储方式处理不同，抽象类里写不了。类上加 @Slf4j 方便记日志，但故意不加 @Service 或 @Component：抽象类不会被实例化，真正注册进 Spring 容器的是它的子类。另外类名虽然叫 Abstract，声明时别忘了补上 abstract 关键字。

接口方法的实现分两层。外层 chunkMerge(FileChunksMergeDTO) 是主流程：

```java
@Override
public R<File> chunkMerge(FileChunksMergeDTO fileChunksMergeDTO) {
    // 合并后的文件名：name（原始文件名的 md5）不带后缀，拼上点和 ext
    String fileName = fileChunksMergeDTO.getName()
            + StrPool.DOT + fileChunksMergeDTO.getExt();
    // 分片合并：定位路径、校验数量、加锁、调用子类合并、清理
    R<File> result = this.chunkMerge(fileChunksMergeDTO, fileName);

    if (result.getIsSuccess() && result.getData() != null) {
        // 合并成功，将文件信息保存到数据库
        File filePO = result.getData();
        fileService.save(filePO);
        return R.success(filePO);
    }
    // 合并失败，把失败结果原样返回给 Controller
    return result;
}
```

合并后的文件名有三部分拼成：DTO 的 name 本身不带后缀，加上 StrPool 常量类里的 DOT（就是一个点），再拼上 getExt 的后缀。合并动作委托给同名的重载方法，拿到结果后先判断：result.getIsSuccess() 为 true 且 getData() 不为空才算合并成功，此时 getData() 返回的就是一个 File 持久化对象（filePO），注入的 fileService.save 把它落库，最后 R.success(filePO) 返回给 Controller；失败时直接把 result 返回，前端调用 getIsSuccess 自然拿到 false。

入库之前还有一段属性补齐。合并方法里并没有设置 File 的全部字段，直接入库会缺很多值，所以在 save 之前要补一批属性——这段代码较长，课程直接从讲义拷贝（讲义里的变量名叫 info，这里改名 filePO）：setDataType 通过 contextType 借助工具类判断文件类型，落到 image、text、doc、video、audio、dir、other 之一；setCreateMonth、setCreateWeek 等时间维度字段；setSubmittedFileName 设置原始文件名（直接从 DTO 取）；setIsDelete 设为 false——刚合并完的文件当然没被删除；size、fileMd5、contextType、ext 都从 DTO 取；filename 用前面拼好的 fileName；icon 按后缀取文件图标。

## 校验、加锁、排序与清理：chunkMerge 的细节

内层 chunkMerge(FileChunksMergeDTO, String fileName) 负责所有脏活。第一步定位分片目录：注入 FileServerProperties，getStoragePath 拿到配置的分片存储目录（配置值形如 D:\chunks），再调 FileDataTypeUtil.getUploadPathPrefix(storagePath) 追加年、月两层目录，得到月份层路径——注意分片上传时目录已经创建过，这里只是确定位置，不是创建：

```java
public R<File> chunkMerge(FileChunksMergeDTO fileChunksMergeDTO, String fileName) {
    // 配置文件中配置的分片文件存储目录
    String storagePath = fileServerProperties.getStoragePath();
    // 追加年、月两层目录，如 D:\chunks\2020\05
    String path = FileDataTypeUtil.getUploadPathPrefix(storagePath);
    // 分片总数、文件 md5、分片目录名（分片上传时用的就是 name 作文件夹名）
    Integer chunks = fileChunksMergeDTO.getChunks();
    String md5 = fileChunksMergeDTO.getMd5();
    String folder = fileChunksMergeDTO.getName();

    // 检查分片数量是否足够
    int chunksNum = this.getChunksNum(Paths.get(path, folder).toString());
    if (chunks == chunksNum) {
        // 数量足够，可以进行分片的合并操作
        ...
    } else {
        log.error("分片数量不对，无法进行分片合并");
        return R.fail("分片数量不对，无法进行分片合并");
    }
}
```

数量校验的对照物来自两个方向：chunks 是前端传过来的声明值，chunksNum 是实际数出来的值。getChunksNum 用 java.io.File 的 API 完成，listFiles 时传一个过滤器把子目录排除掉——万一目录里混进一个文件夹，不过滤就会把数量数多：

```java
// 获得指定目录返回对应的文件数量
public int getChunksNum(String path) {
    java.io.File folder = new java.io.File(path);
    java.io.File[] files = folder.listFiles(file -> {
        if (file.isDirectory()) {
            return false;
        }
        return true;
    });
    return files.length;
}
```

数量对不上直接报错返回：传过来的 chunks 是 10、实际只有 8 片，即便合并也拼不出完整文件。对上了才进入合并段——这一段必须加锁。用 FileLock.getLock(folder) 拿锁，key 就是文件夹名，也就是那条 md5 长串；加锁、合并、清理放进 try，catch 里记"分片合并失败"并返回 fail，finally 里无论成败都先 lock.unlock() 释放锁、再 FileLock.removeLock(folder) 清理锁对象：

```java
Lock lock = FileLock.getLock(folder);
try {
    lock.lock();
    // 获得所有分片文件，转成集合方便排序
    List<java.io.File> chunkFiles =
            this.getChunks(Paths.get(path, folder).toString());
    // 按文件名（分片序号）升序排序
    chunkFiles.sort((f1, f2) -> NumberHelper.intValueOf(f1.getName())
            - NumberHelper.intValueOf(f2.getName()));
    // 调用子类的具体合并方法
    R<File> result = this.merge(chunkFiles, fileName, fileChunksMergeDTO);
    // 合并成功后删除分片文件、目录、临时文件
    this.cleanSpace(folder, path);
    return result;
} catch (Exception ex) {
    log.error("分片合并失败");
    return R.fail("分片合并失败");
} finally {
    try {
        lock.unlock();
    } catch (Exception ex) {
        log.error("释放锁失败", ex);
    }
    FileLock.removeLock(folder);
}
```

这段里有三个关键点。其一，抽象类里调用的 merge 是一个抽象方法——protected abstract R<File> merge(List&lt;java.io.File&gt; files, String fileName, FileChunksMergeDTO fileChunksMergeDTO)，这才是真正的分片合并，参数是排好序的分片文件对象集合（注意传的是文件对象不是文件名）、合并后的文件名和 DTO——合并时还要用到 DTO 里的属性。子类实现它，抽象类只管调度。其二，getChunks 与 getChunksNum 同构，只是返回值从数量换成 new ArrayList<>(Arrays.asList(files)) 的文件集合。其三，排序必须在 merge 之前做：分片文件名全是数字字符串，Comparator 是函数式接口，Lambda 里用 NumberHelper.intValueOf 把 f1.getName()、f2.getName() 转成 int 再相减——字符串没法按数值比大小，若顺序不对，合并时先拼第几片就乱了，最终文件内容必然错位。

合并完成后做清理。cleanSpace(folder, path) 的两个参数对着目录结构理解：path 是月份层目录（D:\chunks\2020\05），folder 是 md5 文件夹名，临时文件名恰好也是 folder 加 .tmp（当初用的同一个 md5 值）：

```java
// 清理分片相关文件：存放分片的目录 + 同名 .tmp 临时文件
public void cleanSpace(String folder, String path) {
    // 删除存放分片文件的目录，里面的分片一并删除
    java.io.File chunkFolder =
            new java.io.File(Paths.get(path, folder).toString());
    FileUtils.deleteQuietly(chunkFolder);
    // 删除临时文件：folder + ".tmp"
    java.io.File tmpFile =
            new java.io.File(Paths.get(path, folder + ".tmp").toString());
    FileUtils.deleteQuietly(tmpFile);
}
```

删除动作直接交给 FileUtils.deleteQuietly（commons-io 工具类），删掉整个文件夹，里面的分片文件自然一起消失，再单独把 .tmp 删掉。至此抽象类写完：路径定位、数量校验、加锁、排序、调度子类合并、清理，通用流程全部收拢在一处。

## LocalChunkServiceImpl：FileChannel 写出原始文件

第一个子类处理本地策略。LocalChunkServiceImpl 创建在 LocalAutoConfigure 配置类里，旁边就是已经写好的 LocalServiceImpl（本地上传、删除）。写在配置类里的好处是动态装配：配置文件中 file type 配置为 local 时，这个 Service 才会被创建并注册进 Spring 容器，表示当前生效的策略就是它。类继承 AbstractFileChunkStrategy 后报错，因为父类有一个抽象方法等着实现——就是那个 merge。它接收三个参数：files 是排好序的分片文件集合，fileName 是合并后文件的名字，fileChunksMergeDTO 装着合并相关的属性。

合并后的文件存到哪？本地策略沿用附件上传的同一套目录约定：endpoint 目录、bucketName 目录、年月两层目录。这些全在配置文件里动态配置，所以先加载配置信息——fileServerProperties 里封装了 file 模块下的所有配置（local、阿里、MinIO、七牛、腾讯等），属性名与配置项保持一致，getLocal 拿到本地配置对象：

```java
// 本地的分片文件策略处理类
@Override
protected R<File> merge(List<java.io.File> files, String fileName,
                        FileChunksMergeDTO fileChunksMergeDTO) throws Exception {
    // 加载配置文件相关信息
    FileServerProperties.Properties properties = fileServerProperties.getLocal();
    String endpoint = properties.getEndpoint();     // 如 D:\uploadFiles
    String bucketName = properties.getBucketName(); // 如 oss-file-service

    // 日期目录层次：年/月，格式用常量引用，不硬编码
    String format = LocalDate.now().format(
            DateTimeFormatter.ofPattern(DateUtils.DEFAULT_MONTH_FORMAT_SLASH));
    String relativePath = Paths.get(format).toString();

    // 分片合并后文件的存放目录
    String path = Paths.get(endpoint, bucketName, relativePath).toString();
    java.io.File uploadFolder = new java.io.File(path);
    // 目录不存在才创建
    if (!uploadFolder.exists()) {
        uploadFolder.mkdirs();
    }
    ...
}
```

路径拼接全部走 Paths.get，因为它足够智能：format 出来的是正斜线，Windows 下目录分隔却是反斜线，Linux 又是正斜线，不同操作系统的分隔符不同，交给 Paths 自动转换，比手工拼斜线稳得多。年月格式引用 DateUtils 里定义的 DEFAULT_MONTH_FORMAT_SLASH 常量。

目录就绪后进入真正的合并。先创建合并后的文件对象：new java.io.File(Paths.get(path, fileName).toString())——这只是构造了对象，磁盘上还没有这个文件，要调 createNewFile 才真正创建，它返回 boolean，true 表示创建成功。这里有两个分支要照顾：文件创建失败就 log.error("文件合并失败") 并返回 fail；如果文件已经存在，说明不需要合并了，log.warn("文件[{}]已经存在", fileName) 后直接返回。createNewFile 会抛异常，不在方法内处理、一路往外抛，父类的抽象方法签名同步加上 throws Exception，两边保持一致。

创建成功后就到了分片合并最核心的部分，用的是 NIO 里的 FileChannel（文件通道）：目标文件封装成输出通道，每个分片封装成输入通道，边读边写：

```java
try (FileChannel outChannel = new FileOutputStream(outputFile).getChannel()) {
    for (java.io.File file : files) {
        // 分片文件封装成输入通道
        try (FileChannel inChannel = new FileOutputStream(file).getChannel()) {
            // 核心一句：从 0 开始、按分片大小，写入输出通道
            inChannel.transferTo(0, inChannel.size(), outChannel);
        } catch (Exception ex) {
            log.error("分片文件合并失败");
            return R.fail("分片文件合并失败");
        }
        // 当前分片已读完写出，直接删除
        file.delete();
    }
} catch (Exception ex) {
    log.error("分片文件合并失败");
    return R.fail("分片文件合并失败");
}
```

最核心的就是 inChannel.transferTo(0, inChannel.size(), outChannel) 这一句：分片文件和目标文件各自封装成 FileChannel，从这个分片的 0 位置起、按它的 size 把字节直接搬运到输出通道。因为 files 已经排好序，for 循环按第 0 片、第 1 片的顺序依次写进同一个 outChannel，顺序不会乱。内层 try-catch 管单个分片读写出错，外层管通道级别的问题，任何一处进 catch 都是"分片文件合并失败"。每次循环读完一个分片，它的字节数据已经进了合并后的文件，随手 file.delete() 把这个分片删掉。合并完成后返回封装好的 File 对象，属性补齐与入库交给抽象类的统一流程。

## 小结

- 分片合并复刻了文件上传的策略体系：FileChunkStrategy 接口、AbstractFileChunkStrategy 抽象类、Local/FastDFS/阿里三个实现类，一种存储方式一个合并策略。
- 抽象类是流程的骨架：拼文件名、定位年月目录、数量校验、加锁、排序、调度子类 merge、清理临时文件、补齐属性入库，全部通用动作只写一次。
- FileLock 以"HashMap + synchronized"实现按文件夹名的互斥，finally 里 unlock 加 removeLock 双保险；数量校验靠 FileFilter 过滤目录后的实际文件数与前端 chunks 对照。
- 排序必须按文件名的 int 值进行，字符串序与数值序不一致是分片合并最常见的暗坑。
- 本地合并的核心是 FileChannel.transferTo：输入通道把分片字节零拷贝式地写进输出通道，每片读毕即删，最终文件落在 endpoint/bucketName/年月 目录，与附件上传共用同一套目录约定。
- 合并 Controller 接口与 FastDFS、阿里云两种策略的实测在课程后续完成，本篇把策略骨架与本地实现全部铺垫到位。
