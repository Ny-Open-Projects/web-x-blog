# 数据批量导入：EasyExcel 批量导入三步与测试、通用数据导入抽象

第七章合作商分账结算推进到第七小节"数据批量导入"。同一章第五小节刚用 EasyExcel 把对账数据导出成 Excel，这一节把方向反过来：管理员上传 Excel，系统解析后批量入库。动机很直接——提高用户录入效率、提升使用体验，很多系统都提供了同类功能。本节先在售货机微服务里实现商品批量导入，再把它抽象成能处理任何数据导入的通用组件。

## 先给结论

- 导出与导入互为逆操作：导出把系统数据转成 Excel，导入把 Excel 上传、解析、写库，两边用的是同一个 EasyExcel。
- 实现三步走：开放文件上传接口，用 EasyExcel 解析 Excel 数据，把解析结果批量导入数据库。批量指先攒进集合、攒够再一次保存，比逐条入库效率高得多。
- 映射类 SkuImport 有两个"一致"：@ExcelProperty 的值必须与 Excel 表头一字不差；属性名与实体类保持一致，后面属性复制才方便。类别列是下拉框，选中"饮料"实际取值是类别 ID，读到的不是文本。
- 监听器继承 EasyExcel 的 AnalysisEventListener：invoke 每提取一行触发一次，doAfterAllAnalysed 在全部读取完成时触发；批量保存一次别超过 500 条（BATCH_COUNT），攒够就提前保存，防止内存吃不消。
- 通用化改造三板斧：泛型 T extends AbstractEntity 保证实体通用，Class<T> 反射创建实例，Function<List<T>, Boolean> 把"怎么保存"交给调用方；监听器挪进 service-common，由 Spring 注入改为 new 出来。
- 重复导入不写代码拦截：sku 表的名称字段建了唯一约束，重复导入直接报"已存在此名称的对象"，数据库层兜底。

## 一、需求与实现思路：上传、解析、批量入库

系统给管理员提供了一个导入模板，列包括商品名称、类别、图片url、价格、净含量、品牌，都是数据库里的字段信息。管理员把填好的 Excel 上传，后台解析入库，商品就批量进库了。

实现思路三步：

1. 文件上传：把 Excel 文件上传到系统。
2. 解析：用 EasyExcel 解析 Excel 数据，转成要入库的商品数据。
3. 批量入库：不要一条一条 insert，而是先构建集合，攒到一定数量再一次保存，效率比逐条高得多。

与第五小节的导出正好构成一对：导出是系统数据到 Excel，导入是 Excel 到系统数据，技术栈都是 EasyExcel。

## 二、映射类与监听器：从空架子到 500 条一批

第一步建映射类。在售货机微服务的 http.viewModel 包下新建 SkuImport，加 @Data，用 @ExcelProperty 标注映射：

```java
@Data
public class SkuImport {
    @ExcelProperty("商品名称")
    private String skuName;

    @ExcelProperty("图片url")
    private String skuImage;

    @ExcelProperty("价格")
    private Integer price;

    @ExcelProperty("类别")
    private Integer classId;

    @ExcelProperty("净含量")
    private String unit;

    @ExcelProperty("品牌")
    private String brandName;
}
```

两个注意事项。一，@ExcelProperty 的值要和 Excel 表头的文字保持一致，这是一种对应关系，对不上解析就会错列。二，属性名要和实体类 SkuEntity 保持一致，后面用 BeanUtils 复制属性时可以直接拷，不用逐个 set。

类别列还有个隐藏点：模板里类别是下拉框，看到的是"饮料"这样的文本，实际取值是类别 ID（比如饮料是 1、零食是 2），和数据库里的类别数据保持对应，所以解析读过来的不是"饮料"这个文本，而是 1 这样的 ID 值。资料第七章里有现成的商品 Excel 模板，打开就能验证。

第二步建监听器。在售货机微服务的 file 包下新建 ExcelDataListener，继承 EasyExcel 提供的抽象类 AnalysisEventListener，泛型先用 E 占位，实际类型就是 SkuImport：

```java
@Component
public class ExcelDataListener<E> extends AnalysisEventListener<E> {

    @Override
    public void invoke(E e, AnalysisContext analysisContext) {
        // 提取数据时触发：e 就是解析出来的一行数据
    }

    @Override
    public void doAfterAllAnalysed(AnalysisContext analysisContext) {
        // 全部读取完成时触发
    }
}
```

两个方法的触发时机就是名字的含义：invoke 在提取每行数据时发生，参数是提取到的那条数据；doAfterAllAnalysed 在整个文件读取完成时触发。逻辑先空着，架子搭好再填。

第三步写上传接口。在 SkuController 新建 upload 方法，参照 API 文档"上传商品解析"来写，方法上抛 IOException，参数用 MultipartFile 接收——写法可以参照已有的图片上传接口，只是对象从图片换成了文件：

```java
@Autowired
private ExcelDataListener excelDataListener;

@PostMapping("/upload")
public void upload(@RequestParam("fileName") MultipartFile file) throws IOException {
    EasyExcel.read(file.getInputStream(), SkuImport.class, excelDataListener)
            .sheet()
            .doRead();
}
```

EasyExcel.read 三个参数各管一件事：第一个把上传的文件转成输入流传进去；第二个指定模型类 SkuImport.class，相当于为泛型明确类型；第三个是监听器实例，注入进来传过去。后面 .sheet() 读取工作表，.doRead() 真正执行读取。读取和解析都由 EasyExcel 完成，具体入库逻辑写在监听器里。

上传接口就绪，回头填监听器的逻辑。实现方式有两种：第一种是提取一条就往数据库存一条，简单但低效；第二种是先把每条数据放进集合，读取完成时一次性保存，效率明显更高，也是本节采用的"批量导入"。按第二种改造分几步。

先声明集合和批次常量：

```java
private static final int BATCH_COUNT = 500;

private List<SkuEntity> list = Lists.newArrayList();
```

集合泛型是实体类 SkuEntity，因为最终要入库的是实体；Lists.newArrayList() 来自 Guava。

invoke 里做转换和攒数。注意 invoke 拿到的 E 是模板类型 SkuImport，不是 SkuEntity，两个类的属性当初特意定义成一样，所以用 BeanUtils.copyProperties 复制即可：

```java
@Override
public void invoke(E e, AnalysisContext analysisContext) {
    SkuEntity skuEntity = new SkuEntity();
    BeanUtils.copyProperties(e, skuEntity);
    list.add(skuEntity);
    if (list.size() >= BATCH_COUNT) {
        // 攒够 500 条，提前执行保存
        doAfterAllAnalysed(analysisContext);
    }
}
```

doAfterAllAnalysed 里注入 SkuService 一次性保存，然后清空集合：

```java
@Override
public void doAfterAllAnalysed(AnalysisContext analysisContext) {
    skuService.saveBatch(list);
    list.clear();
}
```

saveBatch 是批量保存方法。保存完必须 clear：监听器实例会被复用，list 不清空，下次导入时上一次的数据还挂在里面，就成了脏数据。

BATCH_COUNT 的来历要单独说：如果一次导入的 Excel 有成千上万行，全攒在集合里再一次 saveBatch，内存很可能吃不消——批量保存本身也不是没有限制的，条数要控制。每批最多 500 条比较合适，攒够 500 就提前执行一次保存，再继续读。if 里直接调 doAfterAllAnalysed，传 analysisContext（传 null 也行），效果等价于执行保存加清空这两句话。

## 三、Postman 测试：正常导入与重复导入

测试前的准备：先看一眼系统里现有的商品数据，条数不多；资料第七章里有待导入的商品 Excel，四条测试商品——百事可乐、芬达、双汇、统一，当前数据库里都没有。

防重复靠数据库：sku 表上对名称建了唯一约束，名称不允许重复，代码层面就不用处理重复判断了。

测试步骤。启动售货机微服务，文件上传类接口要用 Postman 测。请求地址 localhost:9004/sku/upload（9004 是售货机微服务端口），body 选 form-data，key 填 fileName，就是 Controller 方法参数的名字，类型选 File，选择资料第七章里的商品 Excel，点 Send。

结果验证两轮。第一轮发送后没有报错信息，刷新数据库，商品表多了四条记录，导入逻辑成功。第二轮原样再发一次（重复导入），接口返回错误"已存在此名称的对象"——唯一约束生效，不允许重复导入，刷新数据库确认没有出现重复商品。EasyExcel 实现商品批量导入到此完成。

## 四、通用数据导入：泛型 + Function 抽走具体业务

商品导入刚落地，新需求马上就来：导入商品分类、导入区域、导入点位、导入合作商，类似的数据导入需求很多，每个都按上面三步写一遍监听器是重复劳动。所以要做一个通用的数据导入，一次写好，处处可用。

实现思路三条：做一个通用的数据监听类，能处理任何数据的导入；监听类里用 Function 封装批量保存的操作，Function 就是对一个函数的封装，"怎么保存"由使用方决定；实体类的类型也要通用，必然要用泛型。

通用监听类放到 service-common 工程里，新建 com.lkd.excel 包，把刚写的监听器拷过来改，改动围绕三个点。

第一，泛型化。在原有的 E 之外再添加一个泛型 T，T 必须继承抽象实体类 AbstractEntity，T 代表具体要操作的那个实体，集合里的 SkuEntity 全部换成 T：

```java
public class ExcelDataListener<E, T extends AbstractEntity> extends AnalysisEventListener<E> {
```

第二，invoke 里不能直接 new SkuEntity() 了，改用 Class<T> 反射创建实例。加一个私有属性 Class<T> clazz，创建实例用 clazz.getDeclaredConstructor().newInstance()——直接调 newInstance() 会提示方法已过期，新写法是先拿构造器再创建，没有构造参数就传空的；反射相关的几个受检异常统一用一个 Exception 接住，类上加 @Slf4j，出错时 log.error("读取excel出错", e) 记日志。invoke 拿到的 E 仍是映射类对象，用 BeanUtils.copyProperties 把属性拷进新建的实体 t，再放进集合：

```java
@Override
public void invoke(E e, AnalysisContext analysisContext) {
    try {
        T t = clazz.getDeclaredConstructor().newInstance();
        BeanUtils.copyProperties(e, t);
        list.add(t);
        if (list.size() >= BATCH_COUNT) {
            doAfterAllAnalysed(analysisContext);
        }
    } catch (Exception ex) {
        log.error("读取excel出错", ex);
    }
}
```

第三，保存动作交给 Function。doAfterAllAnalysed 里不能再用 SkuService，那是具体业务类。声明一个函数成员，入参是一个集合——底层批量保存方法接收的本来就是 Collection 集合，List 正好满足，返回类型 Boolean：

```java
private Function<List<T>, Boolean> saveFunc;

@Override
public void doAfterAllAnalysed(AnalysisContext analysisContext) {
    saveFunc.apply(list);
    list.clear();
}
```

clazz 和 saveFunc 通过构造方法传进来，监听器不再由 Spring 注入管理（@Component 去掉），而是使用方自己 new：

```java
public ExcelDataListener(Function<List<T>, Boolean> saveFunc, Class<T> clazz) {
    this.saveFunc = saveFunc;
    this.clazz = clazz;
}
```

Controller 侧同步改造。售货机微服务 file 包下原来的监听类删掉，SkuController 里注入监听器的语句也删掉，改为 new 一个，把保存函数和实体类型传进去：

```java
Function<List<SkuEntity>, Boolean> insertFunc = list -> skuService.saveBatch(list);
ExcelDataListener<SkuImport, SkuEntity> listener = new ExcelDataListener<>(insertFunc, SkuEntity.class);
EasyExcel.read(file.getInputStream(), SkuImport.class, listener).sheet().doRead();
```

insertFunc 是一个 lambda：list -> skuService.saveBatch(list)，相当于为"商品的批量保存"指定了 Function。read 的映射模型仍是 SkuImport.class，监听器的两个泛型分别对齐映射类与入库实体。监听器拿到 Function 和 Class 之后，整个流程就与具体业务解耦，通用性落地。

复测验证。先删掉之前导入的四条商品数据，重启售货机微服务，Postman 原样再发一次请求，没有报错，刷新数据库四条商品再次入库，通用化设计是 OK 的。

复用成本也说清楚：以后再接新的导入需求并不是完全零编码，还有两件事必须做。一是建一个 Excel 与实体对应的映射类，否则框架不知道 Excel 和数据库之间的对应关系；二是在 Controller 里写一个 upload 方法，固定那三句话（read 指定输入流、模型类、监听器，然后 sheet().doRead()）。监听器本体不用再写了。

## 小结

把这一节串起来：需求侧提供模板（商品名称、类别、图片url、价格、净含量、品牌），思路三步走，开放上传接口、EasyExcel 解析、批量入库；代码侧三件套，SkuImport 映射类（@ExcelProperty 对齐表头、属性名对齐实体）、ExcelDataListener 监听器（invoke 攒数、满 500 条提前保存、doAfterAllAnalysed 保存加清空）、SkuController 的 upload 接口（EasyExcel.read 三参数一条链）；测试用 Postman 打 localhost:9004/sku/upload，四条商品入库成功，重复导入被名称唯一约束拦下报"已存在此名称的对象"。随后一步抽象：T extends AbstractEntity 泛型化实体，Class<T> 反射建实例，Function<List<T>, Boolean> 把保存动作外置，监听器挪进 service-common 的 com.lkd.excel 包并改为调用方 new 出来，任何数据的导入都复用这一个监听器，新增需求只剩映射类加三句话的固定成本。到这里，数据批量导入与通用数据导入都已完成：EasyExcel 把 Excel 导回系统，与第五小节的导出（把系统数据导出成 Excel）一出一入，互为逆操作，正好对称。
