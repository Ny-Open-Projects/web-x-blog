# Logstash 订单数据同步：需求思路、环境搭建与配置实现

进入"新零售特性之 LBS 与选品"这一章，后面要做的用户订单检索、选品推荐和聚合统计，全都建立在一仟能被高效查询的订单数据上。所以开篇先解决数据问题：把订单数据从 MySQL 同步到 Elasticsearch。本篇讲清三件事：为什么同步、环境怎么搭、pipeline 配置怎么写。

## 先给结论

- 系统上线后设备数、用户数持续增加，订单数据成几何倍数增长；小程序端有用户查询订单列表的功能，后台也有订单查询和统计，这些操作继续压在 MySQL 上会拖垮整个系统的性能。
- 方案是把订单数据同步到 Elasticsearch，查询和后续聚合统计都走 ES；可选方案还有 MQ、Kafka 这类中间件，本项目选用更专业的 Logstash。
- Logstash 与 Elasticsearch、Kibana 出自同一家公司，三者版本必须保持一致，本项目采用 7.7.1。
- Logstash 是开源的服务端数据处理管道，本身不做存储，专职数据搬运，脚本分 input、filter、output 三段来写。
- 环境搭建的关键是 MySQL8 驱动包和 docker-compose.yml 里的四个目录映射：pipeline、日志、驱动 jar 包、last_values（增量同步的进度记录）。
- pipeline 核心配置：跟踪 update_time 字段做增量同步，last_run_metadata_path 记录同步位置，分页大小 5000，schedule 每 2 秒执行一次；新建或修改 pipeline 文件后必须重启容器才生效。

## 需求与方案：为什么选 Logstash

系统上线之后，设备数不断增加，用户数不断增加，订单数据就会成几何倍数地增长。而我们之后会经常对订单数据进行检索和查询，甚至统计分析：小程序端有用户查询订单列表的功能，后台也有对订单的查询和统计。如果这些操作全都基于 MySQL，必定会增加数据库的压力，上线后的系统性能也会被拖低。

通常的做法是把订单数据同步到 Elasticsearch，查询时直接查 ES，后续的聚合统计也基于 ES 来做，这样整个系统的性能会得到极大提升。

怎么把 MySQL 的数据同步过去？实现的方案其实很多：可以用 MQ 的方式做同步，也可以用 Kafka 这样的中间件。本篇采用的方案更专业——Logstash。它和 Elasticsearch、Kibana 是"亲兄弟"，出自同一家公司，所以使用时一定要注意让 Logstash 的版本与另外两者保持一致。

Logstash 本身是开源的服务端数据处理管道，它并不做存储，主要作用就是数据搬运：可以设置很多种数据源，比如从 MySQL 里提取，也可以从其他数据库采集；数据采集过来后做转换，再存储到你希望的地方，比如这里的 Elasticsearch。反过来从 ES 提取再写回 MySQL 也做得到，这方面相当灵活。它的主要功能分三块：输入（input）、过滤（filter）、输出（output），写脚本文件时也大体按这三部分来定义：怎么采集、怎么过滤、输出到什么地方。

## 环境搭建：驱动包加四个目录映射

课程提供的镜像文件里，Logstash 已经安装好并完成了配置。如果想自己搭一套环境，步骤如下。

第一步，准备好 MySQL8 的驱动包 mysql-connector-java-8.0.18.jar，拷贝到服务器的 /root/common/data/logstash/lib/ 目录。

第二步，在服务器上建立一个 docker-compose.yml 安装文件，指定 Logstash 的镜像、重启策略、容器名称、特权模式、环境变量和目录映射：

```conf
version: "3"
services:
  logstash:
    image: elastic/logstash:7.7.1
    restart: always
    container_name: logstash
    privileged: true
    environment:
      - TZ=Asia/Shanghai
    volumes:
      - /root/common/data/logstash/pipeline:/usr/share/logstash/pipeline
      - /root/common/data/logstash/log:/var/log/log
      - /root/common/data/logstash/lib/mysql-connector-java-8.0.18.jar:/resource/mysql-connector-java-8.0.18.jar
      - /root/common/data/logstash/order:/usr/share/logstash/last_values/
```

restart 指定 always，让容器一直启动。四个目录映射都很关键：

- pipeline：管道脚本文件所在目录，数据从哪来、到哪去的传输规则都定义在这里的文件中；
- log：日志目录；
- 驱动 jar 包：宿主机上的 MySQL 驱动被映射到容器内的 /resource/ 目录，Logstash 连接 MySQL 全靠它；
- last_values：增量数据同步的进度记录目录，里面存的是"同步到哪了"这类时间记录，都是临时数据。

文件建好之后，通过 docker-compose up 命令执行安装，环境搭建到此完成。

## 代码实现：索引库加 pipeline 三段式

### 第一步：创建订单索引库

同步之前，先在 Elasticsearch 里建好存储订单数据的索引库。在 Kibana 中执行下面这条现成语句，定义了商品名称、区域名称、品牌、售货机编号、点位名称、订单编号、第三方支付编号、地址、open_id、支付类型等字段，统一用 keyword 类型支持精确匹配：

```json
PUT order
{
  "mappings": {
    "properties": {
      "sku_name":      { "type": "keyword" },
      "region_name":   { "type": "keyword" },
      "business_name": { "type": "keyword" },
      "inner_code":    { "type": "keyword" },
      "node_name":     { "type": "keyword" },
      "order_no":      { "type": "keyword" },
      "third_no":      { "type": "keyword" },
      "open_id":       { "type": "keyword" },
      "pay_type":      { "type": "keyword" }
    }
  }
}
```

建完先执行 GET order/_search 查一下，此时索引里没有任何数据。

### 第二步：编写 pipeline 文件

pipeline 文件命名为 order.conf，放到宿主机的 /root/common/data/logstash/pipeline/ 目录。之所以放这里，是因为建容器时已经做了目录映射，文件放进这个目录就等于放进了容器内的 /usr/share/logstash/pipeline/ 目录，而那里正是 Logstash 存放传输规则的位置。

文件内容分三部分。input 部分用 jdbc 插件对接 MySQL 数据源，指定连接字符串、用户名密码、驱动包和驱动类，并做增量相关的配置：

```conf
input {
  jdbc {
    jdbc_connection_string => "jdbc:mysql://192.168.200.128:3306/lkd_order?serverTimezone=Asia/Shanghai"
    jdbc_user => "root"
    jdbc_password => "root123"
    jdbc_driver_library => "/resource/mysql-connector-java-8.0.18.jar"
    jdbc_driver_class => "com.mysql.cj.jdbc.Driver"
    jdbc_default_timezone => "Asia/Shanghai"
    record_last_run => "true"
    use_column_value => true
    tracking_column => "update_time"
    tracking_column_type => "timestamp"
    last_run_metadata_path => "/usr/share/logstash/last_values/order_info.txt"
    clean_run => "false"
    jdbc_paging_enabled => true
    jdbc_page_size => "5000"
    statement => "SELECT * FROM tb_order where update_time > :sql_last_value order by update_time asc"
    schedule => "*/2 * * * *"
  }
}
```

几个关键配置的作用：

- 驱动包路径指向容器内的 /resource/ 目录——环境搭建时映射进去的那个 jar 包；
- tracking_column 指定为订单的更新时间 update_time，因为要做的是增量更新：每次把增量更新的最后那个值通过 last_run_metadata_path 存到文件里，下次执行时把这个值提出来作为查询条件，只插入更新的数据；
- jdbc_paging_enabled 开启分页查询，jdbc_page_size 设为 5000：一旦按增量条件查出的数据量超过 5000 条，就分几次查询，防止一次查太多数据把整个系统压崩；
- statement 是具体的查询语句，查更新时间大于上次记录值的数据；
- schedule 是标准的 cron 表达式，*/2 * * * * 表示每间隔 2 秒执行一次，这个更新频率比较适中。

output 部分有两个节点：stdout 用来做控制台输出，把查询到的数据以 JSON 形式打印出来方便观察；elasticsearch 节点指定 ES 的主机和端口、要输出到的 order 索引，以及文档 ID——索引里每个文档都有 ID，这里取采集数据源的 id 列：

```conf
output {
  stdout {
    codec => json_lines
  }
  elasticsearch {
    hosts => ["192.168.200.128:9200"]
    index => "order"
    document_id => "%{id}"
  }
}
```

filter 部分定义了两个数据转换，针对 update_time 和 create_time 两个时间字段。为什么要改？库里应该存的是北京时间，北京是东八区，比 UTC 早八个小时，所以要在原有值的基础上加八个小时。写法是先把原有时间取出来，加上 8*60*60——正好是八个小时的秒数——再通过 set 放回去，create_time 同理：

```conf
filter {
  ruby {
    code => "event.set('update_time', event.get('update_time').time.localtime + 8*60*60)"
  }
  ruby {
    code => "event.set('create_time', event.get('create_time').time.localtime + 8*60*60)"
  }
}
```

### 第三步：部署并验证

三段写完，配置文件就齐了。把文件内容复制下来，在服务器的 pipeline 目录下用 vi 建文件、进入插入模式粘贴、保存。此时去查数据会发现配置并没有生效——新建的 pipeline 文件需要容器重新加载，执行 docker restart logstash 重启容器让它识别。重启完成后再执行 GET /order/_search，可以看到大量订单数据已经被灌了进去，数据同步链路就此跑通。

## 小结

这一节把订单数据的"搬运工"架了起来：需求侧是 MySQL 扛不住日益增长的检索与统计压力，方案侧选定与 ES 同门的 Logstash 做定期增量同步。环境上记住驱动 jar 包和四个目录映射；配置上抓住三条主线——input 里用 update_time 做增量跟踪、last_run_metadata_path 记录同步进度、分页加 cron 控制执行节奏；filter 里补上八小时时区差，output 里按 id 列写入 order 索引。配置落盘后记得重启容器。数据进了 ES，这一章后面的用户订单数据检索、选品智能推荐和聚合查询才有用武之地。
