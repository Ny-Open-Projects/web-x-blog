# 文件接口收尾：ZipUtils 下载内幕、按业务打包下载与网盘服务导入

FileBiz 把参数封装好之后，真正的下载动作全在 ZipUtils 工具类里，这一段先把这个工具类的内幕读透，再在阿里云与本地两种策略下把按 id 打包下载实测一遍；随后补齐按业务类型/业务 id 的打包下载接口，顺手消掉两个下载方法之间的重复代码；最后把不作为课程重点的纯数据库查询接口和整个网盘服务代码导入工程并验证——文件服务这一章就此收束。

## 先给结论

- ZipUtils 下载的根本是 HttpURLConnection：本地存储、FastDFS、阿里云 OSS 最终都归结为一个可访问的 URL，建立连接读输入流、往响应输出流写即可，与存储策略完全解耦。
- 下载文件名要做浏览器兼容转码：Firefox 走 Base64，其余浏览器 URLEncoder 编码后把特殊字符逐个 replaceAll 还原，否则中文文件名在客户端乱码；Content-Disposition 设为 attachment 触发浏览器下载。
- 双策略下载实测通过：阿里云策略下连 nginx 都不需要启动；本地策略下直接访问 URL 下载到的是 UUID 命名的文件，走接口打包下载才会还原原始文件名；两个同名文件打进同一个 zip 时自动加"(1)"区分。
- 按业务打包下载 GET /attachment/downloadBiz：bizTypes[]、bizIds[] 都是 query 数组、可以只传其一，断言两者不能同时为空；查库用 in 条件，与按 id 删除的 eq 区分开。
- download(ids) 与 downloadByBiz 的后半段代码完全重复，在 ServiceImpl 抽出私有 down(list, request, response)，两个下载方法都收敛成"查询 + down"两行。
- 分页查询、按业务查询属于纯数据库操作，直接导入不手敲，分页参数统一由 BaseController 的 getPage() 收集；网盘服务（pd_file 表）比附件服务多一个文件夹维度，整包导入后上传、查询、下载、新建文件夹、多维统计实测全部可用。

## ZipUtils：一次 URL 连接，两种下载形态

FileBiz 最终调用的 zipFilesByInputStream 接收四个参数：文件名到 URL 的映射 fileMap、总大小 fileSize、下载文件名、request/response。它做下载的出发点很简单：不管底层是本地存储还是 FastDFS、阿里云 OSS，上传完成后数据库里都保存着一个能访问到文件的 URL 地址，所以统一用 HttpURLConnection 建立连接、拿到输入流就够了。

方法开头先处理响应头和文件名：

```java
response.setContentType("application/octet-stream; charset=utf-8");
// 按浏览器类型转码：Firefox 走 Base64，其余 URL 编码后还原特殊字符
String agent = request.getHeader("USER-AGENT");
if (agent != null && agent.toLowerCase().indexOf(AGENT_FIREFOX) > 0) {
    downloadFileName = "=?UTF-8?B?"
            + new String(Base64.encodeBase64(extName.getBytes("UTF-8")));
} else {
    // URLEncoder.encode 后把 %20、括号、井号等特殊字符还原回来
}
response.setHeader("Content-Disposition", "attachment;filename=" + downloadFileName);
if (fileSize != null && fileSize > 0) {
    response.setHeader("Content-Length", String.valueOf(fileSize));
}
ServletOutputStream out = response.getOutputStream();
```

Content-Type 声明写回的是二进制流；文件名不能直接赋值了事——客户端多通过浏览器下载，文件名里出现中文或特殊字符会乱码，所以按 USER-AGENT 区分：Firefox 用 Base64 转码，其余浏览器先 URLEncoder.encode 再把允许出现在文件名里的字符逐个替换回来，那一长串 replaceAll 都是在打磨最终下载名。Content-Disposition 设为 attachment 表示以附件形式下载，文件名追加在后面；总大小已知时再补一个 Content-Length。

接下来的分支对应两种下载形态。fileMap 只有一个元素时是单文件下载：遍历 entry 拿到 URL，getConnection（new URL → openConnection → connect）连上远程文件，getInputStream 得到输入流，封装的 downloadFile 方法里输入流 read、输出流 write，直接写回客户端。

多个文件时把响应输出流包装成压缩流，逐个把远程文件压进同一个包：

```java
try (ZipOutputStream zos = new ZipOutputStream(out);
     BufferedOutputStream bos = new BufferedOutputStream(zos)) {
    for (Map.Entry<String, String> entry : fileMap.entrySet()) {
        String fileName = entry.getKey();
        String url = entry.getValue();
        HttpURLConnection connection = getConnection(url);
        BufferedInputStream bis = new BufferedInputStream(connection.getInputStream());
        zos.putNextEntry(new ZipEntry(fileName));
        int len;
        byte[] buf = new byte[10 * 1024];
        while ((len = bis.read(buf, 0, buf.length)) != -1) {
            bos.write(buf, 0, len);
        }
        bos.flush();
    }
}
```

每轮循环处理一个文件：putNextEntry 压入一个 ZipEntry，10KB 缓冲数组循环读写，单个文件下载失败只 log.warn 记录"打包下载多个文件异常"并继续，finally 里 disconnect、关流。职责分工由此很清晰：FileBiz 负责查库、过滤、对象封装这些"格式加工"，ZipUtils 负责连接、流、压缩这些"下载细节"。

实测先走阿里云策略：上传两个同名的 nginx.conf，两个 URL 都能直接下载——浏览器下载同名文件时自动在后面加括号 1 区分，正是 FileBiz 重名处理模仿的行为。调 GET /attachment/download，ids 传两个 id（逗号分隔），返回链接点开，下载到的压缩包名为"nginx等.zip"（第一个文件名截掉扩展名加"等"），打开后里面是 nginx.conf 和 nginx.conf(1)，同名区分生效。只传一个 id 重新发送，下载的就是原始文件本身。本地策略再验一遍：Nacos 把 file type 改成 local 发布，保证 nginx 处于启动状态，重启文件服务并从控制台日志确认策略已切到 local；上传后 URL 变成基于本地 nginx 服务的地址，直接访问 URL 下载到的是 UUID 命名的文件，而接口打包下载还原的是原始文件名——两种获取方式的差异值得记住。

## 按业务打包下载：in 查询与 down 方法抽取

第五个业务接口是"根据业务类型/业务 id 打包下载"，文档口径为 GET /attachment/downloadBiz，规则与按 id 打包下载一致：匹配到一个文件直接下载原始文件，匹配到多个则压缩后下载压缩包；响应类型同样是二进制流，接口文档的状态码一栏看不出这个细节。实现时参数变成了两个 query 数组：

```java
@ApiImplicitParams({
        @ApiImplicitParam(name = "bizIds[]", value = "业务id数组", dataType = "array", paramType = "query"),
        @ApiImplicitParam(name = "bizTypes[]", value = "业务类型数组", dataType = "array", paramType = "query")
})
@ApiOperation(value = "根据业务类型/业务id打包下载", notes = "根据业务id下载一个文件或多个文件打包下载")
@GetMapping(value = "/download/biz", produces = "application/octet-stream")
public void downloadByBiz(
        @RequestParam(value = "bizIds[]", required = false) String[] bizIds,
        @RequestParam(value = "bizTypes[]", required = false) String[] bizTypes,
        HttpServletRequest request, HttpServletResponse response) throws Exception {
    // 业务类型、业务id可以只传一个，但不能同时为空
    if (ArrayUtils.isEmpty(bizTypes) && ArrayUtils.isEmpty(bizIds)) {
        throw BizException.wrap("附件业务id和业务类型不能同时为空");
    }
    attachmentService.downloadByBiz(request, response, bizTypes, bizIds);
}
```

断言用的是 ExceptionCode 里定义的常量：两个条件允许其中一个为空，同时为空就无法确定要下载哪些附件，直接抛业务异常。Service 实现里查库条件从 eq 换成了 in，因为传进来的是数组：

```java
@Override
public void downloadByBiz(HttpServletRequest request, HttpServletResponse response,
        String[] bizTypes, String[] bizIds) throws Exception {
    List<Attachment> list = super.list(Wraps.<Attachment>lbQ()
            .in(Attachment::getBizType, bizTypes)
            .in(Attachment::getBizId, bizIds));
    down(list, request, response);
}
```

写完发现一个明显的重复：这段"判空抛异常 → 转 FileDO → 调 fileBiz.down"与按 id 打包下载的后半段一字不差。于是在 ServiceImpl 里抽出一个私有 down(List<Attachment>, request, response) 方法统一承载，download(ids) 与 downloadByBiz 都收敛成"查询 + 调 down"两句话；工具类的异常一路 throws Exception 往外抛，接口与实现类的异常声明保持一致，最终由 Controller 层统一异常处理兜底。

测试使用本地策略：上传文件时 bizId、bizType 都填 333，数据库多出一条 333 记录且 URL 可访问；按业务下载传 333、333，文件下载成功，用编辑器打开内容正确（就是一个 nginx 配置文件）。再传一份同样 333 的文件，两个条件同时匹配到两条记录，再调下载接口，这次拿到的是"nginx等.zip"压缩包。阿里云、FastDFS 策略的下载逻辑前面已分别验证过，存储策略只影响上传落点，下载统一走 URL，不必重测。

## 纯数据库接口直接导入：分页与按业务查询

课程的重点是上传、下载与文件处理策略，剩下一批纯数据库增删改查的接口——分页查询、按条件查询——不值得逐行手敲，直接从讲义导入。先导分页查询附件：

```java
@ApiOperation(value = "分页查询附件", notes = "分页查询附件")
@ApiImplicitParams({
        @ApiImplicitParam(name = "current", value = "当前页", dataType = "long", paramType = "query", defaultValue = "1"),
        @ApiImplicitParam(name = "size", value = "每页显示几条", dataType = "long", paramType = "query", defaultValue = "10")
})
@GetMapping(value = "/page")
public R<Page<Attachment>> page(FilePageReqDTO data) {
    Page<Attachment> page = getPage();
    attachmentService.page(page, data);
    return success(page);
}
```

值得注意的一处设计：FilePageReqDTO 里只有 folderId、submittedFileName（原始文件名）、dataType（IMAGE/VIDEO/AUDIO/DOC/OTHER）、startCreateTime、endCreateTime 这些查询条件，没有页码和每页条数——分页参数由 BaseController 的 getPage() 统一收集。BaseController 里注入了 request/response，把 current、size 及排序常量统一抽取封装，所有继承它的 Controller 都不必重复写分页参数收集代码。Service 实现就是一组动态条件加 baseMapper 的分页方法：

```java
public IPage<Attachment> page(Page<Attachment> page, FilePageReqDTO data) {
    Attachment attachment = dozerUtils.map(data, Attachment.class);
    Wrapper wrapper = Wraps.<Attachment>lbQ()
            .like(Attachment::getSubmittedFileName, attachment.getSubmittedFileName())
            .like(Attachment::getBizType, attachment.getBizType())
            .like(Attachment::getBizId, attachment.getBizId())
            .eq(Attachment::getDataType, attachment.getDataType())
            .orderByDesc(Attachment::getId);
    return baseMapper.page(page, wrapper);
}
```

原始文件名、业务类型、业务 id 都是 like 模糊查询，dataType 精确匹配，按 id 倒序。导入时把讲义里的 dozer 对象名对齐成工程里的 dozerUtils。重启后测试：库里共 6 条数据，只传 current=1、size=10，返回 total=6、一页装下；把 size 改成 2，total 仍是 6 但 pages 变成 3，每页两条，分页参数生效。

再导"根据业务类型/业务 id 查询附件"：Controller 上 bizTypes、bizIds 两个数组参数，参数校验沿用 ExceptionCode 里的常量断言；Service 只声明一个 find(bizTypes, bizIds)，实现直接调 baseMapper.find——两个组合条件的纯查询。测试传 333、333 查回 2 条记录；把 bizIds 里加个 4，控制台发出的是 WHERE bizId IN (...) AND bizType IN (...) 的 and 组合，匹配不上，一条都查不回来。

## 导入网盘服务：多出来的文件夹维度

附件服务把上传信息存进 pd_attachment 表；文件服务里还有一条网盘线，对应 pd_file 表。网盘服务与附件服务高度相似，差别是多了一个文件夹概念——可以先创建文件夹、再把文件传进文件夹。功能既然类似，整块代码直接导入，导入清单如下：

| 组件 | 职责 |
| --- | --- |
| FileController | 网盘文件增删改查与上传下载：按 id 查文件、分页查询、upload 上传、saveFolder 新建文件夹、改名、删除、下载/打包下载；继承 BaseController，依赖 FileService 与 FileRestManager |
| StatisticsController | 文件统计接口：网盘数据概览等，封装在 FileOverviewDTO——所有文件数量、总大小、文件夹数量、图片/文档等各类文件数量，本质是数据库聚合查询 |
| FileRestManager | 文件公共代码管理类，封装分页与下载方法，落在新建的 manager 包 |
| FileService / FileServiceImpl | 网盘业务接口与实现：saveFolder、download、removeList 删除、按文件夹 id 查询、两个上传方法、fileOverview 首页概览、findTop20 下载排行前 20 等；实现类复用了附件服务抽出的 FileBiz |
| FileMapper（含 ext/FileMapper.xml） | 扩展查询与统计方法，统计 SQL 已预先写在 XML 里 |

导入完成后重启，接口文档里多出"文件"与"统计"两个分组，与课上开发的"附件"分组并列。挑重点实测：上传一个压缩包，folderId 传 0（还没有任何文件夹），source 传 itcast——source 表示文件来源，作用类似附件服务的业务 id/业务类型；userId 不填，因为这套服务基于品达通用权限系统，正常要经过网关与权限服务认证后才持有用户 id，当前是直连文件服务、没有走网关认证，所以暂时没有用户 id。上传成功后 URL 可下载，pd_file 表多出一条记录：dataType 为 other，treePath 描述网盘的树形层次，grade 为一级，isDelete 为未删除，folderId 为 0 表示直接放在网盘根目录。

其余接口快速过一遍：查询文件用正确 id 能查到、随便填一个 id 查不到；下载传 id 能把压缩包拉下来；分页只传 current/size，返回 1 条、每页 10、共 1 页；新建文件夹传 id=0、排序号、名字"资料"，返回 code 0 OK，表里多出一条 dataType 为 dir、名字为"资料"的记录，此后文件就能传进这个文件夹。统计接口按时间维度、用户维度各测一次——userId 不填就统计网盘上全部文件，结果为：文件夹 1 个、其他类型文件 1 个（即上传的压缩包）、图片 0、视频 0、音频 0、文档 0，各维度数量与库中数据一一对应。这批导入代码本身就是整理并测试过的，挑核心接口演示确认可用即可。

## 小结

文件服务到此收尾。下载链路上，ZipUtils 用 HttpURLConnection 把所有存储策略抹平成一个 URL 读取问题，单文件直写、多文件压 zip，文件名的浏览器转码是中文场景绕不开的细节；按业务打包下载把查询条件从 id 换成 in 数组，并借机抽掉两个下载方法的重复段；分页、按业务查询这类纯数据库接口以及网盘服务整体导入，网盘只是比附件多出文件夹与统计两个维度。回看整章：接口开发始终遵循 Controller 管契约、Service 管编排、Strategy/Biz/工具类管执行的分层，能把相似接口做到"改条件即复用"、把不同存储做到"换配置即切换"，正是前几节把抽象抽对带来的红利。
