# 售货机端工程搭建：基础工程改造、集成 EMQ 测试与消息协议封装

售货机端是跑在设备侧的 Spring Boot 工程（lkd_client），它要连上 EMQ 收发消息，按协议执行出货、同步商品等动作。这一篇把工程搭建的几件事一次讲完：先把之前 MyBatis-Plus 操作 H2 的工程改造成基础脚手架，再集成 EMQ 并用 WebSocket 工具验证连通，最后把通信协议封装成枚举和一组协议类，为后续按协议分发业务打好地基。

## 先给结论

- 脚手架不用从零写：复制之前「MyBatis-Plus 操作 H2」的工程，改名 lkd_client，只保留 src 和 pom，pom 里同步改名。
- schema-h2.sql 补上货道、商品、版本、出货信息四张表；版本表建表后初始化一条数据，货道版本、商品版本、价格版本都是 0。
- 启动前必须删掉用户目录下的 lkd.lock 锁文件，否则 H2 不会重新构建表。
- 集成 EMQ 五步：加客户端依赖 → application.yml 配置 → EmqConfig 读配置 → EmqClient 封装连接/订阅/发布 → EmqMsgCallback 处理回调。
- 发布与消息回调都是异步执行：方法标 `@Async`，启动类加 `@EnableAsync` 开启；连接丢失休眠 10 秒自动重连重订阅。
- 协议侧建 MsgType 枚举管理协议名称，msg 包下按 BaseData（通用属性）+ req/resp（请求/响应）+ Data（属性类型）组织协议类。

## 基础工程搭建：H2 + MyBatis-Plus 脚手架改造

之前已经做过一个使用 MyBatis-Plus 操作 H2 的代码工程，直接基于它适当修改就是脚手架：复制一份，改名「立可得」（lkd_client），工程里其他文件夹都不要，只保留 src 和 pom 文件，pom 里把名字同步改掉。

接着补 SQL。原工程只有一个表，把讲义中的建表语句复制进 schema-h2.sql，新增四张表——货道表、商品表、版本表、出货信息表。版本表在建表之后还会初始化一条数据，把货道版本、商品版本和价格版本都置为 0；出货信息表则承担流水账的角色，每次出货记一条。

```sql
CREATE TABLE tb_version (
    version_id INT(11) NOT NULL COMMENT '版本ID',
    channel_version INT(11) NOT NULL DEFAULT 0 COMMENT '货道版本',
    sku_version INT(11) NOT NULL DEFAULT 0 COMMENT '商品版本',
    sku_price_version INT(11) NOT NULL DEFAULT 0 COMMENT '价格版本',
    PRIMARY KEY (version_id)
);

CREATE TABLE tb_sku (
    sku_id VARCHAR(64) NOT NULL COMMENT '商品ID',
    sku_name VARCHAR(64) NOT NULL COMMENT '商品名称',
    image VARCHAR(255) NULL DEFAULT NULL COMMENT '图片地址',
    price INT(11) NULL DEFAULT NULL COMMENT '商品原价',
    real_price INT(11) NULL DEFAULT NULL COMMENT '商品真实售价',
    class_id VARCHAR(64) NULL DEFAULT NULL COMMENT '商品类别ID',
    unit VARCHAR(32) NULL DEFAULT NULL COMMENT '商品净含量',
    discount INT(6) NULL DEFAULT NULL COMMENT '是否打折',
    PRIMARY KEY (sku_id)
);

CREATE TABLE tb_vendout_order (
    order_no VARCHAR(64) NOT NULL COMMENT '出货订单号',
    pay_type INT(11) NOT NULL DEFAULT 0 COMMENT '支付方式',
    channel_id VARCHAR(64) NOT NULL DEFAULT '' COMMENT '渠道ID',
    sku_id VARCHAR(64) NOT NULL DEFAULT '' COMMENT '商品ID',
    pay_price INT(11) NOT NULL DEFAULT 0 COMMENT '价格',
    out_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '出货时间',
    result_code INT(11) NOT NULL DEFAULT 0 COMMENT '出货结果：0-成功，1-货道真空，2-设备出错，3-连续支付，4-服务超时',
    PRIMARY KEY (order_no)
);
```

Mapper 和 POJO 不用手写，从课程资料的「导入代码」里直接拿，对应这四张表。例如货道的 Mapper 里就带了一个清空表的方法：

```java
public interface ChannelMapper extends BaseMapper<Channel> {

    @Update("truncate table tb_channel")
    void deleteAllChannels();
}
```

准备工作做完，启动工程前还有个坑：目录里已经存在一个创建工程时生成的锁文件 lkd.lock（在用户所在目录下）。必须把它删掉，H2 才会重新构建表信息。删掉后重启，LkdClientApplication 跑起来（Tomcat 端口 9093），连上 H2 控制台就能看到四张表已经自动生成，版本表里也躺着那条初始化数据。基础工程到此完成。

## 集成 EMQ：依赖、配置与客户端封装

基础工程就绪后开始集成 EMQ，按步骤走：

1. **加依赖**。在 pom 中加入 EMQ 客户端（MQTT 客户端）相关依赖，刷新 Maven。
2. **写配置**。在 application.yml 末尾加 emq 相关配置，包括：连接 EMQ 服务器的 URL、密码、当前设备号、发送消息的主题前缀、clientId、订阅消息的主题。
3. **读配置**。建一个 config 包，把资料中提供的 EmqConfig 拷过来，属性和配置一一对应，读取时直接注入即可：

```java
@Configuration
@ConfigurationProperties("emq")
public class EmqConfig {
    private String mqttServerUrl;      // EMQ 服务器地址
    private String mqttPassword;       // 密码
    private String innerCode;          // 当前设备号
    private String publisTopicPrefix;  // 发送消息的主题前缀
    private String clientId;
    private String subscribeTopic;     // 订阅消息的主题
}
```

4. **客户端类**。建 emq 包，放入 EmqClient：引入 EmqConfig 和 MQTT 客户端，封装三个方法——connect 连接、subscribe 订阅主题、publish 发布消息，把细节都收进来。publish 标了 `@Async` 异步注解，调用时不必等方法执行完成，提高调用效率。既然用了 `@Async`，启动类里要加 `@EnableAsync` 让它生效。
5. **回调类**。EmqMsgCallback 实现 MqttCallbackExtended，订阅主题之后所有消息都会经过它的 messageArrived 方法，同样用异步方式执行；方法里解析消息内容并取出协议名称，之后就能根据协议名称执行相应的业务逻辑。另外两个回调点：connectComplete 在连接成功后自动执行，里面调用订阅主题的方法；connectionLost 在连接丢失时自动执行，休眠十秒后重新连接、重新订阅主题。

最后一步是改造初始化 service（InitService）。它本来负责数据库初始化，现在还要做自动连接：注入 EmqClient 和 EmqMsgCallback，在其中调用 `emqClient.connect(callback)` 把回调传进去，应用启动时自动连上 EMQ。集成 EMQ 到此完成。

## 连通性测试：WebSocket 工具收发验证

测试前先把 EMQ 的 ACL 关掉——ACL 开着的话，还需要把做校验的服务端也一起跑起来。关掉后启动 lkd_client，观察控制台：经过 init 初始化方法后，客户端已经成功连接并订阅了主题。

然后用 EMQ Dashboard 里的 WebSocket 工具测试：先连接（演示环境是 192.168.200.128 的 8083 端口），连上后向设备订阅的主题发送测试消息，比如向 vm2vm0100001 发一条：

```json
{"msg": "Hello, World"}
```

点发送，IDE 控制台立刻收到这条消息，日志里能看到 connectComplete 之后自动订阅、以及收到的 payload：

```text
connectComplete subscribe /vm/town/91888801
==================MQTT null payload {"msg": "Hello, World"}
```

再换个其他主题发消息，控制台收不到——客户端只订阅了自己关心的那类主题，主题不匹配的消息不会进来。能收到订阅主题内的消息，就证明设备端与 EMQ 的连接已经建立成功。

## 消息协议封装：MsgType 枚举与协议类族

工程能收到消息之后，下一步就是解析各种协议、按不同协议做不同处理。为了让代码更清晰，先在 config 包下建一个枚举 MsgType 来管理协议：加 Lombok 的 `@Getter` 让属性自动带 getter；定义两个属性——type（协议名称）和 desc（描述）；构造方法接收这两个参数。枚举里的每个值实际上就是对构造方法的一次调用，第一个参数是协议名称，第二个是协议描述：

```java
@Getter
public enum MsgType {
    // 枚举常量按课程资料逐个补齐，每个值 = (协议名称, 描述)
    private final String type;   // 协议名称
    private final String desc;   // 描述

    MsgType(String type, String desc) {
        this.type = type;
        this.desc = desc;
    }
}
```

使用时取枚举的 type 属性值做判断即可。versionCfg、channelCfg 这类配置协议的常量，资料提供的导入代码里已逐个列好，直接拷入即可。

除了协议名称，还要封装每个协议的数据格式。在 emq 包下建一个 msg 包，里面所有类都是封装好的协议类，组织规律很清楚：

- **BaseData** 是父类，封装所有协议的通用属性：协议名称（msgType）、sn 码、设备编号、是否回传版本号等，msgType 字段用来标识这条消息的具体类型，是后续业务分发的依据。
- **req 结尾**的类代表请求，**resp 结尾**的类代表响应——也就是服务器端给设备端的响应。
- **Data 结尾**的类是协议里用到的属性类型。比如商品价格协议里就有一个集合属性，集合里的元素又是一个自定义类型，这类嵌套结构都用 Data 类表达。

这套封装之后，收到消息就能先解析出 msgType，再映射到对应的协议类去反序列化和处理，协议再多也不会乱。

## 小结

- 售货机端脚手架 = 旧 H2 工程改名 + 四张业务表 + 资料导入的 Mapper/POJO；启动前删 lkd.lock 才能重建表。
- 版本表初始化数据把货道/商品/价格版本置 0，是后续增量同步的基线；出货信息表按次记流水。
- 集成 EMQ 五步：依赖 → yml 配置 → EmqConfig → EmqClient（连接/订阅/发布）→ EmqMsgCallback（回调），启动类 `@EnableAsync` 配合 `@Async`。
- 断线自动重连：connectionLost 里休眠 10 秒后重连重订阅；connectComplete 里自动订阅主题。
- 测试链路：关 ACL → 启动工程看 init 连接订阅 → Dashboard WebSocket 按主题发消息 → 控制台确认收到，其他主题收不到。
- 协议封装三板斧：MsgType 枚举管名称、BaseData 管通用属性、req/resp/Data 管请求响应与嵌套结构。
