# 设备详情展示：ES 与 InfluxDB 跨库联查与最新指标聚合

设备详情展示是第三章的最后一个功能：分页展示设备详情列表，每台设备要展示当前所有指标的最新值和在线状态，还能按设备标签、设备编号筛选。前面两节已经把指标持久化进 InfluxDB、做出了报警日志查询，这一节把查询难度再抬一级：一次列表查询要同时跨越 Elasticsearch 和 InfluxDB 两个存储。这个功能做完，整个"指标数据持久化与设备详情展示"一章就完整了。

## 先给结论

- 这个功能表面看是一个列表，实际是跨数据库查询：设备编号、状态这些基本信息存 Elasticsearch，每个设备下面的指标数据存 InfluxDB，只能靠代码逻辑把两边的查询组织成一个返回结果。
- 实现思路：先按条件从 ES 查出设备列表，循环结果取出每台设备编号，再去 InfluxDB 查该设备的所有指标数据，最后合并返回。
- 取最新指标靠 InfluxDB 的 last 函数：select last(value),* from quota where deviceId='xxx' group by quotaId，先按指标分组，每组只取最新一条，温度、湿度各返回一条，速度非常快。
- QuotaService 新增 getLastQuotaList(deviceId) 封装这条语句，返回 List<QuotaInfo>，用单元测试验证通过。
- 组装用 DeviceQuotaVO：设备编号、在线状态、告警级别、指标列表四个属性。状态给前端两个值（online + level），前端综合展示：有告警只显示告警（告警视为特殊的在线状态），离线则直接显示离线。
- queryDeviceQuota 三步走：searchDevice 查设备列表 → forEach 逐台查指标灌进 VO → 封装新的 Pager 返回；Controller 对齐 API 文档，后端原叫 SN 的参数按文档约定改成 deviceId；state 传 4 或其他未定义值时条件不拼、等同查全部，不用单独处理。

## 需求分析：一次跨库的综合查询

先看最终效果：页面上方是查询条件，可以按设备状态、标签、设备编号查询设备；下方是一个列表，每台设备展示设备编号和状态：在线、离线、一般报警、严重报警等，前端会根据设备的最新告警状态给单元格上不同的颜色来区分，比如在线是绿色、严重告警是红色。每个设备下面还包含很多指标，温度、电压这样的具体数值都挂在设备卡片上。

难点藏在数据来源里。设备编号、状态这些信息存在 Elasticsearch 中，而每个设备包含的指标来自 InfluxDB。表面上这个功能比较简单，实际是一种跨数据库查询：外层方向查的是 ES，每台设备内部又嵌着 InfluxDB 查询。这种逻辑没有任何一个数据库能单独完成，只能通过代码来组织最终的返回结果。

实现思路：先按条件查询设备（这一步的 ES 查询在前面的章节已经完成，ES 包下 ESRepository 的 searchDevice 方法就满足外层这一层的需求）；查询设备之后循环结果，取出每一个设备编号，再去 InfluxDB 中查询。而且查询要取当前最新的数据：同一台设备的同一个指标会有很多很多记录，每次发报文都存了一条，页面上要的是最后一次发过来的那个值。好在这是 InfluxDB 的一个支持点，一个函数就能解决。

## 按设备 ID 取最新指标：group by 与 last 函数

第一步是按设备 ID 获取最新指标。先进终端验证语句。进入 InfluxDB 并切换到亿可控数据库后，先做最简单的查询：

```sql
select * from quota where deviceId='100001'
```

查询出来的结果非常多：这台设备的所有指标、每次发送过来的报文都经过存储，全都会被查出来。而设备有两种指标：温度和湿度，需要分别聚合：先做分组，每组里取最新数据，历史发生的过程数据并不关心。

分组用 group by，按指标的 id 分：

```sql
select * from quota where deviceId='100001' group by quotaId
```

结果变成了分组后的形式：温度一组，湿度一组。在此基础上再套 last 函数，取每个分组中的最新数据：

```sql
select last(value),* from quota where deviceId='100001' group by quotaId
```

last 括号里就是要取最新值的那个字段，后面再跟一个逗号加星号，把其余字段一并带出来。执行后速度非常快，一共只查出两条：一条温度、一条湿度。这正是页面要的数据，把这条语句记下来准备封装。

封装成业务逻辑方法放在 QuotaService 里，因为它和指标相关。返回一个列表，元素用 QuotaInfo：

```java
/**
 * 根据设备ID查询最新指标
 */
List<QuotaInfo> getLastQuotaList(String deviceId);
```

实现就是把语句拼出来执行：

```java
@Override
public List<QuotaInfo> getLastQuotaList(String deviceId) {
    String ql = "select last(value),* from quota where deviceId=\"" + deviceId + "\" group by quotaId";
    return influxRepository.query(ql, QuotaInfo.class);
}
```

设备号拼进语句，调用 InfluxRepository 的通用查询方法，传入 QuotaInfo.class，返回的结果就是想要的。

写个单元测试验证一下好不好用。Test 包下已有的 TestInfluxDb 测试类里加一个方法：

```java
@Test
public void testFindLast() {
    List<QuotaInfo> quotaList = quotaService.getLastQuotaList("100001");
    try {
        String json = JsonUtil.serialize(quotaList);
        System.out.println(json);
    } catch (JsonProcessingException e) {
        e.printStackTrace();
    }
}
```

注入 QuotaService，设备 ID 还用 100001，把查到的集合用 JsonUtil 序列化成 JSON 打出来。运行测试，结果出来了：是一个集合，里面有一条温度、一条湿度，两个指标的值都有，说明封装是对的。

## 组装分页设备列表并暴露接口

按设备查最新指标完成了，分页查询设备信息（ES 那一层）也是现成的，剩下的就是把两个查询结合到一起，形成完整的设备详情展示逻辑。

### 先定义 VO

第一步写一个 VO 类，它是前端所需要的结构，返回列表里的每一个元素就长这样。分析下来有四个属性：设备编号；状态，实际上是两个值（在线状态和告警级别）；指标列表。

关于状态有个设计细节：后端返回给前端两个值，但前端以一种形式展示出来。如果返回的是告警数据，就只显示告警、不显示在线，告警被当作一种特殊的在线状态；如果设备离线，就不用考虑告警不告警，直接显示离线。

```java
@Data
public class DeviceQuotaVO {
    private String deviceId;          // 设备编号
    private Boolean online;           // 在线状态
    private Integer level;            // 告警级别
    private List<QuotaInfo> quotaList; // 设备指标详情
}
```

### 再定义逻辑方法

第二步在 DeviceService 接口上定义逻辑方法，返回值是分页结果：

```java
/**
 * 查询设备详情
 */
Pager<DeviceQuotaVO> queryDeviceQuota(Long page, Long pageSize, String deviceId,
        String tag, Integer state);
```

参数就是设备查询分页的那几个：页码、页大小、设备编号、标签、状态。实现分三步。第一步查询设备列表，即一个不包含指标的设备列表，调 esRepository.searchDevice，参数直接透传，返回的 Pager 就是设备列表。第二步循环设备列表，逐台查指标灌进 VO：

```java
@Override
public Pager<DeviceQuotaVO> queryDeviceQuota(Long page, Long pageSize, String deviceId,
        String tag, Integer state) {
    // 1. 查询设备列表（不包含指标）
    Pager<DeviceDTO> pager = esRepository.searchDevice(page, pageSize, deviceId, tag, state);
    // 2. 循环设备列表，逐台查询最新指标
    List<DeviceQuotaVO> voList = Lists.newArrayList();
    pager.getItems().forEach(deviceDTO -> {
        DeviceQuotaVO deviceQuotaVO = new DeviceQuotaVO();
        // DeviceDTO 中有三个属性与 VO 定义一致，直接复制
        BeanUtils.copyProperties(deviceDTO, deviceQuotaVO);
        List<QuotaInfo> quotaList = quotaService.getLastQuotaList(deviceDTO.getDeviceId());
        deviceQuotaVO.setQuotaList(quotaList);
        voList.add(deviceQuotaVO);
    });
    // 3. 封装返回结果
    Pager<DeviceQuotaVO> result = new Pager<>(pager.getCounts(), pageSize);
    result.setItems(voList);
    return result;
}
```

循环用 forEach，和 for 循环效果一样。每台设备新建一个 DeviceQuotaVO，DeviceDTO 里有三个属性和 VO 定义的一模一样，用 BeanUtils.copyProperties 直接复制省事；再注入 QuotaService，用设备编号调 getLastQuotaList 拿到指标列表，setQuotaList 装进去。每次循环构建的 VO 要收集起来，最终要返回的是集合，所以外头先建一个列表，循环里 add。最后封装返回结果：构建新的 Pager，记录数用原来查询结果的 counts，页大小照传，items 放收集好的 VO 集合。

### Controller 对齐 API 文档

最后写 Controller。参照 API 文档找到"数据详情页"这个接口，五个参数：page、pageSize、tag、state 和 deviceId。方法签名和返回值：

```java
@GetMapping("/deviceQuota")
public Pager<DeviceQuotaVO> queryQuotaData(Long page, Long pageSize, String deviceId,
        String tag, Integer state) {
    return deviceService.queryDeviceQuota(page, pageSize, deviceId, tag, state);
}
```

映射地址按 API 文档来写；参数可以直接从工程里一个类似的方法复制过来，它只多了一个 state，类型是 Integer。这里有个命名细节：这个参数在后端定义时其实叫 SN，但 API 文档里约定的是 deviceId，前端和后端已经约好了这个名字，所以代码里要跟着改成 deviceId。写完直接调 deviceService 的查询方法，把参数依次传过去。

还有一个关于 state 的细节：文档里设备状态包括 0、1、2、3、4，其中 4 特殊，代表全部。底层拼条件的逻辑只写了 0、1、2、3，没有把 4 写进去。这无所谓：传 0123 时对应条件都能匹配；传 4 或者 0123 之外的任何值，条件逻辑不会执行，也就等同于全部。所以 4 不用单独处理。

### 接口测试

启动亿可控工程，用 VS Code 的插件测试。找到"获取设备详情"的测试脚本，地址就是刚写的接口。先把 tag 条件去掉，只传一个 state 条件来查：结果是所有在线设备，注意观察返回结构：每条里有 deviceId、online 等字段，指标列表也都挂上了。再测告警：一般告警传 2，当前没有这种告警数据；严重告警传 3，有数据，返回的 level 是 3，结果也正常。这样，整个获取设备详情的功能就完成了，本章的内容到此也全部落地。

## 小结

设备详情展示把前面所有环节串了起来：ES 存设备主数据并负责条件筛选与分页，InfluxDB 存指标明细并靠 group by quotaId 加 last 函数提供每台设备的最新指标，DeviceService 用循环把两个存储的结果组装成一个 VO 列表。技术上值得带走的三点：跨库联查没有捷径，只能靠逻辑组织返回结果；时序库里"取最新值"就是 last 函数加分组，一条语句解决，性能还非常好；对外参数名以 API 文档约定为准，后端内部的命名（SN）要主动对齐（deviceId）。至此，本章的 InfluxDB 入门、指标持久化、报警日志查询、设备详情展示四个功能全部完成。
