# 合作商分成金额计算：需求思路、代码实现与测试

立可得 2.0 把平台与合作商的合作方式从"付租金"改成了"按比例分成"，每笔订单生成时都要算出该分给合作商多少钱。本篇完成第七章合作商分账结算里最基础的一环：把创建订单逻辑中预留的 todo 补成真正的分账计算代码，再用一次完整联调验证金额落库正确。需求、思路、代码、测试，一次走完。

## 先给结论

- 1.0 是租赁模式：平台不拥有点位，机器放进公园、商场、学校，都要向点位所有者（合作商）付租金；机器卖不动时连租金都赚不回来，对平台是巨额成本也是巨大风险
- 2.0 增加分成合作：不付租金，按约定比例分成——10 元的饮料约定 10% 比例，每卖一瓶合作商得 1 元，多卖多得
- 计算时机在创建订单时：当初写 createOrder 时预留了一个 todo 占位，用 IDE 的 TODO 视图能快速定位这段没写完的逻辑
- 实现就两步：根据售货机所在点位的合作商 ID 查合作商信息，拿到分成比例；商品真实价格乘以比例再除以 100
- 金额运算用 BigDecimal：multiply 做乘法、divide 做除法，divide 用三参数重载——除数、保留小数位、舍入模式；金额单位为分，保留 0 位小数，RoundingMode.HALF_UP 四舍五入，结果转 int 存进订单实体的 bill 字段
- 联调测试验证：4.5 元（450 分）× 15% = 67.5，四舍五入后 bill = 68（六角八分），数据库订单表落值正确

## 一、从租金到分成：需求与计算时机

立可得 1.0 版本中，平台与合作商的合作方式基本是租赁模式。点位的所有权不在平台手里：机器放到公园，公园是点位所有者；放到商场，商场是；放到学校，学校是。这些商家不可能平白无故让机器摆在自己的位置上，所以平台要把机器放进点位，就得向合作商负担租金。

这种模式对平台是巨额成本，也是很大的风险——机器放到某个点位上，商品卖得特别少，连租金都赚不回来，钱就白花了。所以 2.0 版本增加了分成合作的方式：机器放到你的点位上，平台不付租金，改成按比例分成。一瓶饮料售价 10 元，约定分成比例 10%，每卖出一瓶合作商就有 1 元收入，多卖多得。这就是本篇要计算的"分成金额"。

分成金额在什么时间节点算？在创建订单的时候。写创建订单逻辑时，代码里预留了一个 todo——所谓 todo，就是预留出来、并未实现的逻辑占位。IDE 的 TODO 视图可以很方便地找到这类没写完的代码，OrderServiceImpl 里"合作商分账计算"这一处就是本篇要填补的部分。

课件把这件事拆成三节：1.1 需求分析——根据订单金额和合作商的分账比例，计算分账金额；1.2 实现思路——先根据售货机所在点位的合作商 ID 查询合作商信息（分账比例存在合作商表中），再把商品的真实价格乘以分账比例，商业运算一般使用 BigDecimal 的 multiply（乘法）和 divide（除法）方法，精度更准；1.3 代码实现——修改订单服务 OrderServiceImpl 的 createOrder 方法，在 this.save(orderEntity); 之前添加代码。

## 二、代码实现：补上 createOrder 里的 todo

实现思路落成代码只有四句。位置在 OrderServiceImpl.createOrder 方法内、this.save(orderEntity); 之前，把 `// todo: 合作商分账计算` 替换为：

```java
// 获取合作商信息，分成比例存在合作商信息里
PartnerViewModel partner = userService.getPartner(vm.getOwnerId());
// 商品真实价格是 int，先转成 BigDecimal
BigDecimal price = new BigDecimal(sku.getRealPrice());
// 分成金额 = 真实价格 × 分成比例 ÷ 100，四舍五入保留 0 位小数
BigDecimal bill = price
        .multiply(new BigDecimal(partner.getRatio()))
        .divide(new BigDecimal(100), 0, RoundingMode.HALF_UP);
// 转成 int 存入订单实体的 bill 字段
orderEntity.setBill(bill.intValue());
```

逐句拆解。

第一句先拿合作商。分成比例在合作商信息里，vm 的 ownerId 就是售货机所在点位的合作商 ID，调 userService.getPartner 按 ownerId 查询合作商，返回 PartnerViewModel 对象。

第二句转价格类型。sku.getRealPrice() 拿到商品真实价格，它是 int 类型，马上要做乘法运算，先 new BigDecimal 把它转成 BigDecimal，变量记作 price。

第三句做乘除。price 调 multiply 做乘法，乘的是提成比例（分成比例）；比例来自刚拿到的 partner 对象，它同样是数，也要 new BigDecimal 转一次类型。乘完还没完：分成比例是一个小于 100 的数，比例 15 的含义是 15%，把原价直接乘 15 等于放大了 15 倍，明显不对，还要再除以 100。除法用 divide，这里选三个参数的重载：第一个参数是除数，除以 100 就传 new BigDecimal(100)；第二个参数是保留几位小数——金额以分为单位，保留 0 位小数；第三个参数是舍入模式，BigDecimal 提供了很多种，这里选最常用的四舍五入（RoundingMode.HALF_UP）。

第四句落库。乘除的结果还是 BigDecimal 类型，最终要存进数据库。订单实体对应有一个 bill 字段，含义就是分成金额，调 orderEntity.setBill(bill.intValue()) 把 BigDecimal 转成 int 存进去。到这里，合作商分成计算的代码就完成了。

## 三、联调测试：450 × 15% = 68

测试环节一共启动五个工程：订单微服务、用户微服务、售货机微服务、小程序、小程序网关——要用微信开发者工具做联调，小程序也得跑起来。

动手前先看数据库的底子。打开订单库的订单表，已有测试记录的 bill 字段全是 0，因为之前没有分成金额计算逻辑；补上代码后 bill 应该有值，这就是本次测试要验证的事。

打开微信开发者工具，扫设备 0001 的二维码进入小程序。选商品时故意挑金额大的：金额太小，乘完分成比例会直接变成 0，看不出效果。选一瓶 4.5 元的饮料，点支付——这里不需要真正支付，不支付订单也会产生，金额也会正常计算。

支付后直接查数据库，刚才创建的订单 bill 字段已经是 68。这个 68 从哪来？反推一遍：

- 当前操作的机器是 0001，在售货机列表中找到它，它的合作商 ID 是 1
- 到用户表中找合作商 1，它的分成比例是 15，即 15%
- 450 分 × 0.15 = 67.5，四舍五入后就是 68，也就是六角八分

代码逻辑、数据库落值、业务规则三方对上，分成金额计算的测试就完成了。

## 小结

把本篇串起来：合作模式从 1.0 的租赁（平台付租金，成本与风险都压在平台身上）演进到 2.0 的分成（不付租金，按比例多卖多得）；分成金额的计算时机定在创建订单时，落在当初预留的 todo 上；实现是两步——按售货机点位的合作商 ID 查比例，再用 BigDecimal 的 multiply 与 divide 完成"真实价格 × 比例 ÷ 100"，HALF_UP 四舍五入、以分为单位转 int 写进订单表 bill 字段；最后用一次五工程联调验证了 450 × 15% = 68 的落库结果。

对第七章"合作商分账结算"来说，这个 todo 补完意味着分成金额计算这一环从需求、实现到测试完成闭环：每笔订单创建时都会同步算出应付给合作商的分成金额，订单表里那个 bill 字段，就是分账结算最底层的数据。
