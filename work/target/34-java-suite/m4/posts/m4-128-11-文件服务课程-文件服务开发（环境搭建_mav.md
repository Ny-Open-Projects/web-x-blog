# 文件服务开发收尾与文件处理策略实现（FastDFS/本地存储策略）

上一篇把数据库、Nacos、Nginx 和脚手架工程都备齐了，这一篇把 Maven 工程环境收尾：建 pd-file-server 服务模块、导入全套配置与启动类、编译安装验证跑通。环境确认无误后，进入课程真正的重头戏——文件处理策略：FileStrategy 接口、AbstractFileStrategy 抽象模板，以及以本地存储为例的第一个具体策略实现。

## 先给结论

- pd-file-server 聚合进 pd-file、继承 pd-file 父工程；POM 依赖量大：pd-file-entity 与 pd-tools-databases、pd-tools-log、pd-tools-validator、Swagger，加 OpenFeign、Nacos Discovery、Hystrix 熔断、XSS 过滤，以及阿里云 OSS、七牛云、FastDFS 等存储 SDK 和 spring-boot-configuration-processor。
- 配置文件五类整体导入复用：dozer（对象转换，只映射属性名不同的字段）、MyBatis 映射文件（base 抽公共字段、ext 写真正 SQL）、bootstrap、logback、p6spy（仅开发环境用，输出 SQL 与执行耗时）。
- bootstrap 里 Nacos 信息不写死：源头在 pd-apps 的 POM profile，bootstrap 用 `@xx@` 引用，环境变量优先于 POM；common/redis/mysql 三份公共配置所有服务共享，文件服务再叠加 pd-file-server 与 pd-file-server-dev 两份，启动共加载五份。
- 启动类注解组合固定：@SpringBootApplication、@EnableDiscoveryClient、@EnableHystrix、@EnableFeignClients、@EnableTransactionManagement、@EnableFormValidator（脚手架自定义注解）；配置类大多直接继承 pd-tools 里的基类，dev 环境下数据源会被包装成 P6DataSource。
- 验证方式：pd-tools 与 pd-apps 先后执行 install，再启动 FileServerApplication；日志依次加载 common.yml、redis.yml、mysql.yml、pd-file-server.yml、pd-file-server-dev.yml 五份配置，容器是 Undertow，Swagger 里已出现"文件服务"分组。
- 文件处理策略骨架：FileStrategy 只定义 upload 与 delete 两个方法；AbstractFileStrategy 固化校验、File 属性封装与批量删除流程，真正读写文件交给子类；策略切换靠 @ConditionalOnProperty(name = "pinda.file.type")，本地实现三步：UUID 文件名、年月日期目录（Paths 自适配分隔符）、endpoint + bucketName 拼绝对路径。

## 工程收尾：pd-file-server 模块与全套配置

在 pd-file 下再建一个模块 pd-file-server——文件服务的启动模块，后面启动就启动它。创建后 pd-file 的 POM 里聚合了 pd-file-entity 和 pd-file-server 两个子模块，pd-file-server 则通过 parent 继承 pd-file。

服务模块的 POM 依赖相当多：脚手架体系内的 pd-file-entity、pd-tools-databases、pd-tools-log（日志）、pd-tools-validator（表单校验），加上接口文档用的 Swagger、页面输入清理防攻击的 XSS 过滤；远程调用要 OpenFeign，注册与配置中心要 Spring Cloud Alibaba 的 Nacos Discovery，熔断用 Netflix Hystrix；存储相关的 SDK 有阿里云、七牛云、FastDFS 等客户端；最后是 Spring Boot starter 与 configuration-processor。Web 依赖里还通过 exclusions 排除了内嵌 Tomcat。

POM 之后是导入配置文件，课程直接把资料里整理好的一套拷进 pd-file-server 的 resources，实际开发也多是这么拿过来改。五类文件各司其职：

| 配置 | 作用 |
| --- | --- |
| dozer | 对象转换组件，底层基于 BeanUtils；globalDozer 全局的暂为空文件，bizDozer 写业务映射 |
| mapper | MyBatis 映射文件；base 里放 resultMap 与 Base_Column_List 公共字段抽取，ext 里放真正的 SQL，SQL 里 include 引用字段 |
| bootstrap | Spring Boot 启动最先加载的配置 |
| logback-spring | 日志配置 |
| p6spy | 数据源插件：把执行的 SQL 和执行时间输出到控制台，相当于 SQL 分析；有性能损耗，仅限开发环境，生产不建议用 |

dozer 值得一提的规则：两个类转换时，属性名相同的字段（如 md5、size、name）不用映射，只有属性名不一样的才需要显式对应，比如把 A 类的 type 映射到 B 类的 contextType。

bootstrap.yml 是其中最关键的一份。启动类名称、环境、Nacos 地址全都是引用，值一路追溯到 pd-apps 的 POM：

```yaml
pinda:
  nacos:
    ip: ${pom.nacos.ip}        #取不到环境变量时从 POM 取
    port: ${pom.nacos.port}
    namespace: ${pom.nacos.namespace}
spring:
  application:
    name: pd-file-server       #从 POM 读取
  profiles:
    active: dev
  cloud:
    nacos:
      config:
        server-addr: ${pinda.nacos.ip}:${pinda.nacos.port}
        file-extension: yaml
        namespace: ${pinda.nacos.namespace}
        shared-dataids: common.yaml,redis.yaml,mysql.yaml
        refreshable-dataids: common.yaml   #common 变动自动通知刷新
        enabled: true
      discovery:
        server-addr: ${pinda.nacos.ip}:${pinda.nacos.port}
        namespace: ${pinda.nacos.namespace}
```

读这种配置要熟悉"两层 @@ 或 ${} 引用"的用法，否则满屏引用看不到具体值。shared-dataids 里的 common、redis、mysql 是公共配置，脚手架自带的网关服务、权限服务都会加载；文件服务特有的两份是 pd-file-server 和 pd-file-server-dev——启动一共加载五份。

然后是启动类 FileServerApplication，注解组合相对固定：@SpringBootApplication 之外，@EnableDiscoveryClient 到注册中心发现服务，@EnableHystrix 开启熔断，@EnableFeignClients 扫描 com.itheima.pinda 包下接口（基于代理做 Feign 远程调用），@EnableTransactionManagement 开启事务，@Slf4j 提供日志对象，还有一个自定义注解 @EnableFormValidator——它定义在 pd-tools-validator 模块里，加上即开启表单校验。main 方法在 SpringApplication.run 之后从 Environment 动态取应用名、当前网络 IP、端口号，拼进占位符输出。

配置类与工具类同样直接从资料导入，放包时注意层次：pinda 下要先建一层 file 目录再放 config。要点有四个：

1. **数据源配置**里有两个 DataSource Bean：druidDataSource 与 dataSource。开发环境（dev）下会把 Druid 数据源包装成 P6DataSource（对应 p6spy，SQL 输出控制台），判断依据是 ArrayUtils.contains(DEV_PROFILES, profiles)；非 dev 直接返回原版 Druid 数据源。还有 SqlSessionFactory、事务管理器、事务拦截器与切面通知等一整套。
2. **MyBatis 配置**继承 BaseMybatisConfiguration——它来自 pd-tools-databases 模块，拦截器、注入器、ID 生成器都已备好。
3. **异常与 Web 配置**：ExceptionConfiguration 继承 pd-tools-common 的 DefaultGlobalExceptionHandler，通过 @ControllerAdvice 拦截加了 @RestController / @Controller 注解的控制器抛出的异常（BizException 等常用异常都已处理完）；WebConfiguration 继承 BaseConfig，内含 ObjectMapper 的 JSON 转换和一批日期转换器。这就是用脚手架的好处——公共能力直接继承复用。
4. **工具类与 Mapper**：FileDataTypeUtil 按文件类型识别（图片、视频、DIR、音频、文本），ZipUtil 服务于打包下载（传入输出流、文件名与输入流，读入写出完成下载）；dao 包下放 AttachmentMapper 与 FileMapper 两个接口，定义增删改查方法，与 resources 里的映射文件通过 namespace 一一对应。最后还有配置属性类 FileServerProperties，把配置文件里 pinda.file 前缀的属性封装成 Java 对象，type 属性指定存储类型，local、ali 各对应一种策略的配置。

## 安装验证：从 install 到服务启动

环境搭建涉及十一步，全部做完后先整体验证。为保险起见，先对工程做 Maven 安装：pd-tools 是父工程、模块很多，可以在 Maven 面板里按组显示，直接在它上面执行 install，编译、打包、安装到本地仓库一条龙，Build Success；再对 pd-apps 执行 install，它下面的 pd-auth（权限服务）、pd-file（文件服务）、pd-gateway（网关服务）等子模块依次安装。聚合工程的好处正在于此：统一清理、统一安装。

接着启动 FileServerApplication 验证环境。启动前必须保证 Nacos 处于启动状态，否则配置中心连不上。控制台日志能看到 Nacos 客户端依次 Loading nacos data：先 common.yml，再 redis.yml、mysql.yml（这三个是公共配置），然后是文件服务特有的 pd-file-server.yml 和 pd-file-server-dev.yml——正好五份。容器用的是 Undertow 而不是 Tomcat。

打开 Swagger 接口文档，已经能看到"文件服务"这个分组——它来自 pd-file-server.yml 里 pinda.swagger.docket.file 的配置（title 为"文件服务"）。controller 包还没创建，所以分组下只有文档自带页面、没有任何接口，等接口开发完就会展示在这里。到此可以确认基础工程没有问题，进入文件处理策略的开发。

## 文件处理策略：接口与抽象模板

文件服务要给客户端提供统一的接口，就必须屏蔽底层具体存储方式，这就是 5.2 文件处理策略要做的类与接口设计。在 pd-file-server 下新建 strategy 包，先写顶层接口 FileStrategy：

```java
public interface FileStrategy {
    //上传文件；返回的 File 是 pd-file-entity 里的实体，不是 java.io.File
    File upload(MultipartFile file);

    //文件删除；入参是删除条件的集合，支持批量
    boolean delete(List<FileDeleteDO> list);
}
```

两个方法的细节都有讲究。upload 的返回值用实体 File，因为上传完成后要把文件信息保存进数据库（附件表或 pd_file 表），需要把它带出去。delete 的入参是 List 而不是单个对象：单个 FileDeleteDO 一次只能删一个文件，封装成集合就能一次删多个，方法功能更强。FileDeleteDO 是删除条件封装：group 与 path 是 FastDFS 返回的组与远程路径（只在 FastDFS 时用）、fileName 唯一文件名、relativePath 相对路径、id 等。另外接口里不提供下载方法——下载在另外的工具类里提供。

接着是抽象类 AbstractFileStrategy（strategy/impl 包），实现 FileStrategy，固化能确定下来的上传与删除流程，真正读写文件留给子类。

upload 方法整体是个 try-catch 结构。进 try 先做合法性校验：取 getOriginalFilename 得到原始文件名，判断里面是否包含点号——没有点就等于没有后缀，而文件信息里要保存类型和后缀，这种情况拒绝处理，直接抛 BizException，提示"上传文件名称缺少后缀"；点号不直接写字面量，而是定义 private static final String FILE_SPLIT = "." 常量引用。抛出的异常最终由前面导入的 ExceptionConfiguration 统一处理。校验通过后封装 File 对象（builder 链式构建），上传完成后它就是要落库的数据：

```java
File file = File.builder()
        .isDelete(false)                                          //刚上传，未被删除
        .size(multipartFile.getSize())                            //文件大小
        .contextType(multipartFile.getContentType())              //文件类型
        .dataType(FileDataTypeUtil.getDataType(contextType))      //数据类型：DIR/IMAGE/VIDEO/AUDIO/DOC/OTHER
        .submittedFileName(originalFilename)                      //原始文件名
        .build();
//ext 从原始文件名截取（不要点）；icon 由 IconType.getIcon(ext) 按后缀给出
//createMonth/createWeek/createDay 用 DateUtils 格式化当前时间，供按月/周/日统计
```

dataType 通过 FileDataTypeUtil 的静态方法按 MIME（即 contextType）比对得出；图标用于云盘前端展示，IconType 枚举里每种后缀对应一个图标样式（mp3 对应 el-icon-microphone，bmp/jpg/jpeg/png/gif 对应图片图标）。到这里一共封装了 10 个属性，但还不够——url 这类属性只有真正完成上传才能确定，所以抽象类再声明一个抽象方法 uploadFile(File file, MultipartFile multipartFile)：把封装了一半的 File 和原始 MultipartFile 都传进去，由子类补齐剩余属性并完成真正的上传，返回后 upload 直接 return。catch 块里先 log.error 记录异常，再继续往外抛"文件上传失败"，否则全局异常处理接不到。

delete 方法相对简单：

```java
public boolean delete(List<FileDeleteDO> list) {
    if (list == null || list.isEmpty()) {
        return true;                       //没有可删的内容，视为操作完成
    }
    boolean flag = false;                  //删除操作是否成功的标志位
    for (FileDeleteDO fileDeleteDO : list) {
        try {
            delete(fileDeleteDO);          //抽象方法，子类实现真正的删除
            flag = true;
        } catch (Exception e) {
            log.error("e = {}", e);
        }
    }
    return flag;
}
```

它配套的抽象方法 void delete(FileDeleteDO) 同样交给子类实现，因为本地删除、FastDFS 删除、阿里云删除的处理方式完全不同。

抽象类还提前备好两个属性和一个方法供子类使用：@Autowired 注入 FileServerProperties（配置属性类，属性与配置文件一一对应，启动时封装成对象）；再声明一个 FileServerProperties.Properties 类型的 properties——不注入，只声明。这个内部类里有 uriPrefix、endpoint、accessKeyId、accessKeySecret、bucketName 几个字段，FileServerProperties 里 local、ali、minio、qiniu、tencent 每种存储方案各占一个 Properties 属性，具体用的是哪个，只有程序运行时按配置确定。getUriPrefix() 获取下载地址前缀：uriPrefix 非空直接用它，否则取 endpoint。对应配置文件 pd-file-server.yml 里的 pinda.file：type 指定当前存储类型（课程配置的是 FAST_DFS，可选 LOCAL、ALI、MINIO、FAST_DFS，课上只实现 local、ali、FastDFS 三种，其余可自行扩展）；local 段配 uriPrefix、bucketName（对应一层文件夹名）、endpoint（Windows 写盘符，Linux 按 Linux 目录写）；ali 段配 bucket-name、endpoint 与 access-key-id/secret（注册阿里云、申请空间后获得）。FastDFS 演示环境的 uriPrefix 是 http://172.17.0.115:8188/。本地存储配了 uriPrefix 就取它，阿里没配就落到 endpoint——不同存储方案特点不同，这个前缀是为后面的下载准备的。

## 策略动态切换与本地存储实现

具体策略类不直接暴露给程序，而是通过配置类动态选择。在 file 目录下再建 storage 包，创建 LocalAutoConfigure 配置类：

```java
@Configuration
@Slf4j
@EnableConfigurationProperties(FileServerProperties.class)
@ConditionalOnProperty(name = "pinda.file.type", havingValue = "LOCAL")
public class LocalAutoConfigure {

    @Service
    public class LocalServiceImpl extends AbstractFileStrategy {
        @Override
        public File uploadFile(File file, MultipartFile multipartFile) { /* ... */ }

        @Override
        public void delete(FileDeleteDO fileDeleteDO) { /* ... */ }
    }
}
```

关键是 @ConditionalOnProperty：name 必须与配置文件保持一致（pinda.file.type），havingValue 为 LOCAL——配置里 type 是 LOCAL 时这个配置类才生效，里面的 @Service 才会被创建并加入 Spring 容器；配置成别的值，配置类不生效，Service 也就不会实例化。程序就是通过这种方式间接控制策略处理类是否创建。LocalServiceImpl 继承 AbstractFileStrategy，负责本地策略的文件上传与删除，它要实现 uploadFile 和 delete 两个方法。

uploadFile 的第一件事是取配置：抽象类里声明的 properties 此时才有值，通过 fileProperties.getLocal() 拿到 local 段封装的 Properties 对象（要拿阿里配置就是 getAli()，每种策略各对应一个对象）。之后分三步生成存储路径：

```java
//1. 生成不重复的新文件名：UUID + 原始后缀（后缀在抽象类里已封装进 File）
String fileName = UUID.randomUUID().toString() + StrPool.DOT + file.getExt();
//2. 按年月生成日期目录；格式引用常量，Paths 自动适配正反斜线
String relativePath = LocalDate.now()
        .format(DateTimeFormatter.ofPattern(DateUtils.DEFAULT_MONTH_FORMAT_SLASH));
//3. endpoint + bucketName + 日期目录，拼出文件最终的绝对磁盘路径
String absolutePath = Paths.get(properties.getEndpoint(),
        properties.getBucketName(), relativePath).toString();
```

第一步是文件名防重复：原始文件名要保留记录，但磁盘上存的是 UUID 加后缀的新名字。第二步按日期划分目录——上传的文件多了不能都堆在一个目录，所以按年月分（比如 2020/05），格式不直接写字符串而引用 DateUtils.DEFAULT_MONTH_FORMAT_SLASH 常量，以后格式变化只改一处。这里有个跨系统细节：Windows 目录分隔符是反斜线、Linux 是正斜线，写死哪一种都不行，所以用 java.nio.file 的 Paths.get()，它会按当前操作系统智能选择分隔符。第三步把三段拼起来：endpoint（D 盘 uploadFiles 目录）+ bucketName（oss-file-service 文件夹）+ 日期目录，同样交给 Paths 处理分隔符。到此，本次上传文件的绝对磁盘路径就确定下来了，剩下的落盘动作和 delete 的本地删除逻辑随后补齐。

## 小结

这一篇完成了两件事。工程侧：pd-file-server 模块建好，五类配置文件与启动类、配置类、工具类、Mapper 接口全部就位，bootstrap 用引用链把 Nacos 信息收敛到 POM 一处；pd-tools 与 pd-apps 依次 install 后启动服务，日志确认加载五份配置、Swagger 出现文件服务分组，环境闭环。策略侧：FileStrategy 只留 upload/delete 两个口子，AbstractFileStrategy 把校验、属性封装、批量删除这些通用流程固化下来，真正的存储动作通过抽象方法下沉到子类；策略的激活由 pinda.file.type 配置配合 @ConditionalOnProperty 决定，本地策略的 uploadFile 已经走通"UUID 文件名 + 年月目录 + 绝对路径"三步。策略框架立住之后，FastDFS 与阿里云的策略类只是同样的模板换一套读写实现，后面的接口开发也都建立在这层抽象之上。
