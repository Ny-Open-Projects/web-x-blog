# 用户服务：地址簿管理全套接口与用户信息管理导入落地

配置文件就绪后，pd-user 的开发准备只剩启动类和配置类两件小事，随后进入本章主体：地址簿管理的五个接口与用户信息管理的五个接口。地址簿是 C 端用户维护的基础数据，增删改查本身不难，课程真正想演示的是在 CRUD 之上如何织入上一章的 j2cache——什么时候写缓存、什么时候清缓存。本篇把这两个模块的落地过程一次收拢。

## 先给结论

- pd-user 启动类 UserApplication 三个注解：@SpringBootApplication、@EnableDiscoveryClient（注册进注册中心做服务发现）、@EnableSwagger2；配置类两个：MybatisPlusConfig 注册分页插件 PaginationInterceptor，SwaggerConfig 用 Docket 扫描 controller 包生成 API 文档。
- 地址簿是 TMS 的 C 端用户维护的基础数据，寄件时从地址簿里选寄件人和收件人；原型覆盖列表页、空状态页和新增/编辑地址页（姓名、电话、分机号、省市区三级联动、详细地址、公司名称选填、是否默认地址）。
- 地址簿变动频率极低，录完之后很少修改，适合缓存：五个接口在纯增删改查基础上加入 j2Cache——新增/详情写缓存，更新/删除必须 evict 清缓存，漏清就是脏数据。
- 默认地址的唯一性在代码里保证：提交 isDefault=1 的地址时，先把该用户名下其他地址全部刷成 0 再保存。
- 省市区 id 是逻辑外键，基础数据来自通用权限系统的表结构；userId 指向 pd_member 表的 id，但两边都没建数据库层面的真实外键约束。
- 用户信息管理只管 C 端用户（快递员、后台管理员、司机属于物流公司内部员工用户，另一套体系）：验证码登录成功即自动注册，注册登录由通用组件完成，customer-auth 库存一份、pd_users 库的 pd_member 表存一份，auth_id 是指向 tb_auth 主键的逻辑外键。

## 开发准备收尾：启动类与两个配置类

启动类代码直接从讲义复制，核心就是三个注解：

```java
@SpringBootApplication
@EnableDiscoveryClient
@EnableSwagger2
public class UserApplication {
    public static void main(String[] args) {
        SpringApplication.run(UserApplication.class, args);
    }
}
```

配置类有两个，都建在 config 包下。MybatisPlusConfig 用到 MyBatis-Plus 的分页插件：

```java
@Configuration
public class MybatisPlusConfig {
    @Bean
    public PaginationInterceptor paginationInterceptor() {
        return new PaginationInterceptor();
    }
}
```

SwaggerConfig 承担文档功能。Docket 扫描 com.itheima.pinda.controller 包下的所有 controller 类，生成对应的 API 文档，方便后面做接口测试：

```java
@Configuration
@EnableSwagger2
public class SwaggerConfig extends WebMvcConfigurationSupport {
    @Bean
    public Docket createRestApi() {
        return new Docket(DocumentationType.SWAGGER_2)
                .apiInfo(apiInfo())
                .select()
                .apis(RequestHandlerSelectors.basePackage("com.itheima.pinda.controller"))
                .paths(PathSelectors.any())
                .build();
    }

    private ApiInfo apiInfo() {
        return new ApiInfoBuilder()
                .title("品达物流订单模块-Swagger文档")
                .version("1.0")
                .build();
    }
}
```

这套代码在 pd-base 里都出现过，直接拿过来即可。另有一个小坑：Swagger2 与静态资源路径冲突，需要重写 addResourceHandlers 把 swagger-ui.html 和 webjars 的资源路径补上：

```java
protected void addResourceHandlers(ResourceHandlerRegistry registry) {
    registry.addResourceHandler("/**").addResourceLocations("classpath:/static/");
    registry.addResourceHandler("/swagger-ui.html").addResourceLocations("classpath:/META-INF/resources/");
    registry.addResourceHandler("/webjars/**").addResourceLocations("classpath:/META-INF/resources/webjars/");
}
```

到这里开发准备全部完成，可以正式写业务接口了。

## 地址簿管理：五个接口与缓存同步

业务需求一句话：地址簿是 TMS 的 C 端用户负责维护的基础数据，用户寄件时从地址簿中选择寄件人、收件人。产品原型三块——列表页（搜索框、每条地址带编辑/删除图标、新增地址按钮）、空状态页（还没有记录，快去添加吧）、新增/编辑地址页（姓名、电话、分机号、省市区三级联动下拉、详细地址、公司名称选填、是否默认地址单选）。操作的数据模型就是前面看过的 pd_address_book 表。

实体类与表字段一一对应，导进 entity 包：

```java
@Data
@EqualsAndHashCode(callSuper = false)
@Accessors(chain = true)
@TableName("pd_address_book")
public class AddressBook implements Serializable {
    @TableId(value = "id", type = IdType.ASSIGN_UUID)
    private String id;
    @TableField("user_id")
    private String userId;
    @TableField("name")
    private String name;
    @TableField("phone_number")
    private String phoneNumber;
    @TableField("extension_number")
    private String extensionNumber;
    @TableField("province_id")
    private Long provinceId;
    @TableField("city_id")
    private Long cityId;
    @TableField("county_id")
    private Long countyId;
    @TableField("address")
    private String address;
    @TableField("company_name")
    private String companyName;
    @TableField("is_default")
    private Integer isDefault;
    @TableField("create_time")
    @DateTimeFormat(pattern = "yyyy-MM-dd HH:mm:ss")
    @JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")
    private LocalDateTime createTime;
}
```

注解逐个看：@TableName 指定映射的表；@TableId 指定主键且生成策略为 ASSIGN_UUID；@TableField 完成其余字段的映射；Lombok 三件套生成 getter/setter 等样板方法；createTime 上同时加 @DateTimeFormat 和 @JsonFormat，保证前后端时间格式统一。特别注意实体类要实现 Serializable——数据后面要进缓存、要做序列化传输。

要开发的接口一共五个：新增、根据 ID 查询详情、分页查询、更新、删除。整体思路是对地址簿表做增删改查，在这个基础上加入缓存操作，因为地址簿信息变动频率非常低，录入之后很少修改，天然适合缓存。Controller 的骨架如下，region 用的就是 caffeine.properties 里已经定义过的 addressBook 区域：

```java
@RestController
@RequestMapping("addressBook")
public class AddressBookController {
    @Autowired
    private IAddressBookService addressBookService;
    @Autowired
    private CacheChannel cacheChannel;
    private String region = "addressBook";
}
```

新增接口里藏着默认地址的唯一性处理：

```java
@PostMapping("")
public Result save(@RequestBody AddressBook entity) {
    if (1 == entity.getIsDefault()) {
        addressBookService.lambdaUpdate()
                .set(AddressBook::getIsDefault, 0)
                .eq(AddressBook::getUserId, entity.getUserId())
                .update();
    }
    boolean result = addressBookService.save(entity);
    if (result) {
        cacheChannel.set(region, entity.getId(), entity);
        return Result.ok();
    }
    return Result.error();
}
```

isDefault 等于 1 表示当前录入的这条要作为默认地址。同一个用户可以留多条地址，但默认地址只能有一条，所以先把该用户名下其他地址的 isDefault 全部刷成 0——lambdaUpdate 的条件限定在当前 userId 上，不能动其他用户的数据——然后再正常 save，保存成功后把整个 entity 对象载入 addressBook 缓存区域。

Service 与 Mapper 层完全按 MyBatis-Plus 的规范搭：IAddressBookService 继承 IService&lt;AddressBook&gt;；AddressBookServiceImpl 继承 ServiceImpl&lt;AddressBookMapper, AddressBook&gt; 实现该接口；AddressBookMapper 继承 BaseMapper&lt;AddressBook&gt; 并加 @Mapper 注解；resources/mapper 下的 AddressBookMapper.xml 是个空壳——通用增删改查由 MyBatis-Plus 直接搞定，只有框架提供不了的特殊 SQL 才需要在 XML 里写。

详情接口是"读缓存优先"的标准模板：

```java
@GetMapping("/detail/{id}")
public AddressBook detail(@PathVariable(name = "id") String id) {
    CacheObject cacheObject = cacheChannel.get(region, id);
    if (cacheObject.getValue() != null) {
        return (AddressBook) cacheObject.getValue();
    }
    AddressBook addressBook = addressBookService.getById(id);
    if (addressBook != null) {
        cacheChannel.set(region, id, addressBook);
    }
    return addressBook;
}
```

先查缓存，命中直接返回；未命中走 getById 查库——这个方法继承自 IService，不用在 service 层做任何扩展——查到后写回缓存。整个方法只写 controller 一层即可。

分页查询用 lambdaQuery 拼过滤条件，统一返回 PageResponse：

```java
@GetMapping("/page")
public PageResponse<AddressBook> page(Integer page, Integer pageSize, String userId, String keyword) {
    Page<AddressBook> iPage = new Page<>(page, pageSize);
    Page<AddressBook> pageResult = addressBookService.lambdaQuery()
            .eq(StringUtils.isNotEmpty(userId), AddressBook::getUserId, userId)
            .and(StringUtils.isNotEmpty(keyword), wrapper ->
                    wrapper.like(AddressBook::getName, keyword).or()
                            .like(AddressBook::getPhoneNumber, keyword).or()
                            .like(AddressBook::getCompanyName, keyword))
            .page(iPage);
    return PageResponse.<AddressBook>builder()
            .items(pageResult.getRecords())
            .page(page)
            .pageSize(pageSize)
            .pages(pageResult.getPages())
            .counts(pageResult.getTotal())
            .build();
}
```

以后所有分页数据都包装成 PageResponse 返回，里面封装 counts（总条数）、pageSize（每页记录数）、pages（总页数）、page（当前页码）和 items（列表数据）。MyBatis-Plus 返回的 IPage 分页对象需要转换，用 builder 把属性挨个设置好再 build。过滤条件里 userId 是等值查询；keyword 是个万能关键字，对 name、phoneNumber、companyName 三个字段做 like 模糊查询，任何一个匹配上就能查出来。

更新和删除的关键动作是清缓存：

```java
@PutMapping("/id")
public Result update(@PathVariable(name = "id") String id, @RequestBody AddressBook entity) {
    entity.setId(id);
    if (1 == entity.getIsDefault()) {
        addressBookService.lambdaUpdate()
                .set(AddressBook::getIsDefault, 0)
                .eq(AddressBook::getUserId, entity.getUserId())
                .update();
    }
    boolean result = addressBookService.updateById(entity);
    if (result) {
        cacheChannel.evict(region, id);
        return Result.ok();
    }
    return Result.error();
}

@DeleteMapping("/id")
public Result del(@PathVariable(name = "id") String id) {
    boolean result = addressBookService.removeById(id);
    if (result) {
        cacheChannel.evict(region, id);
        return Result.ok();
    }
    return Result.error();
}
```

update 里的 isDefault 处理与新增完全一致；entity.setId(id) 把路径上的 id 设置给实体，所以请求体里传不传 id 都没关系。核心是更新、删除成功之后必须 evict 清理原缓存——该清理的时候不清理，缓存和数据库就会不同步，出现脏数据。

接口测试按演示环境实录：服务端口 8189，打开 Swagger 文档。当前 controller 并没有加 @Api、@ApiOperation 这些注解，但只要能扫描到就会生成默认文档——类名按驼峰拆开、用横线连接变成 address-book-controller，方法说明直接用方法名，这是一套默认生成规则。先测新增：address 填北京，cityId 传 10，countyId 传 50，companyName 填传智播客，createTime 删掉让它自动生成，name 填小明，userId 随便造一个——省市区 id 来自通用权限系统那套表，是逻辑外键；userId 指向 member 表的 id，因为没有开发登录功能只能造一个，真正的生产环境取的是当前登录用户的 id。执行前表里 58 条数据、Redis 里没有内容；执行成功后 pd_address_book 变成 59 条，Redis 里出现 addressBook 区域，key 下存的就是整个 entity 对象。

重启服务再测其余四个接口：detail 用刚才那条数据的 id 查询，数据正常返回；page 传 page=1、pageSize=10，59 条数据分 6 页，pageSize 改成 5 就分 12 页，再加 keyword=小明，结果只剩一条——关键字对三个字段模糊匹配生效；update 直接执行，更新成功后 Redis 里对应的数据被清掉了，evict 生效；delete 传 id 执行，总数又回到 58 条。五个接口全部验证通过。

## 用户信息管理：分工与逻辑外键

用户信息管理先明确对象：TMS 的用户从大的方面分两类，一类是 C 端用户，另一类是物流公司内部用户——内部用户又分不同角色，快递员、后台系统管理员、司机都算员工用户。这个模块管的是 C 端用户。

注册登录的机制是：移动端登录页没有显式的注册入口，只做手机验证码登录，登录成功就自动完成注册。要注意这个注册登录功能不是 TMS 提供的，调用的是前面介绍过的通用注册登录服务，由它完成 C 端用户的注册与登录。登录成功后用户信息保存在它的 customer-auth 数据库里；同时用户服务这边还要在 pd_users 库的 pd_member 表里保存一份。两张表描述的是同一个用户，对应关系靠 auth_id 字段维系——pd_member.auth_id 存的就是 tb_auth 表的主键 id 值，属于逻辑外键。两边有明确分工：customer-auth 那边的表由通用注册登录组件操作，当前用户服务只操作 pd_member 这一张表。

pd_member 表就五个字段：id、auth_id、id_card_no（身份证号）、id_card_no_verify（身份证是否验证通过）、phone（手机号）。实体类 Member 导入 entity 包，同样要实现 Serializable，因为后期需要进行网络传输。

MemberController 的五个接口和地址簿同构，只是没有缓存操作，从讲义一次性导入：

```java
@RestController
@RequestMapping("member")
public class MemberController {
    @Autowired
    private IMemberService memberService;

    @PostMapping("")
    public Result save(@RequestBody Member entity) {
        boolean result = memberService.save(entity);
        if (result) {
            return Result.ok();
        }
        return Result.error();
    }

    @GetMapping("detail/{id}")
    public Member detail(@PathVariable(name = "id") String id) {
        return memberService.getById(id);
    }

    @GetMapping("page")
    public PageResponse<Member> page(Integer page, Integer pageSize) {
        Page<Member> iPage = new Page<>(page, pageSize);
        LambdaQueryWrapper<Member> queryWrapper = new LambdaQueryWrapper<>();
        Page<Member> pageResult = memberService.page(iPage, queryWrapper);
        return PageResponse.<Member>builder()
                .items(pageResult.getRecords())
                .page(page)
                .pageSize(pageSize)
                .pages(pageResult.getPages())
                .counts(pageResult.getTotal())
                .build();
    }

    @PutMapping("update/{id}")
    public Result update(@PathVariable(name = "id") String id, @RequestBody Member entity) {
        entity.setId(id);
        boolean result = memberService.updateById(entity);
        if (result) {
            return Result.ok();
        }
        return Result.error();
    }

    @DeleteMapping("delete/{id}")
    public Result del(@PathVariable(name = "id") String id) {
        boolean result = memberService.removeById(id);
        if (result) {
            return Result.ok();
        }
        return Result.error();
    }
}
```

分层同样走 MyBatis-Plus 规范：IMemberService 继承 IService&lt;Member&gt;，MemberServiceImpl 继承 ServiceImpl&lt;MemberMapper, Member&gt;，MemberMapper 继承 BaseMapper&lt;Member&gt; 加 @Mapper 注解，resources/mapper 下的 MemberMapper.xml 也是空壳。代码简单但必须有——后边项目里的其他服务都会调用到这些接口，一次性导入省事。

测试实录：重启服务，Swagger 页面刷新后多出 member-controller，五个接口。save 直接用默认假数据执行，pd_member 表从 35 条变成 36 条；detail 随便复制表里一个 id 查询，数据正常返回；page 传页码 1、pageSize 10，36 条数据分 4 页；update 改 authId 等字段——接口没有做校验，输入什么值都能保存进去，真正的更新依据是路径变量上的 id，请求体里的 id 传不传都可以，代码里会 setId；delete 删掉那条假数据，表里回到 35 条。五个接口全部测试通过。

## 小结

本篇把 pd-user 的两块基础功能落地。开发准备收尾就三个类：启动类三注解、MyBatis-Plus 分页插件、Swagger 文档（顺带解决静态资源冲突）。地址簿五个接口是"CRUD + j2cache"的标准样板——详情先读缓存、未命中回源并补缓存，新增成功 set 缓存，更新/删除成功 evict 清缓存，默认地址唯一性靠 lambdaUpdate 先清后存保证；keyword 三字段模糊查询与 PageResponse 统一分页对象都是后续可以直接复用的套路。用户信息管理接在通用注册登录服务上，pd_member 只存 C 端用户的补充信息，auth_id 以逻辑外键连向认证库，服务端五个纯 CRUD 接口一次导完。手写缓存 API 到此为止，下一篇把这些操作换成注解加拦截器的声明式实现。
