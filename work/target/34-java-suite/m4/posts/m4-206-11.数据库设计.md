# 亿可控落地准备：库表建表、虚拟机与配置中心、核心代码解析与添加设备（上）

需求与架构定下来之后，亿可控进入落地准备阶段：MySQL 一共就五张表，用来承载全部配置；环境靠一个预装好中间件的虚拟机镜像开箱即用；配置收敛到 Consul；再解析一遍基础工程里登录、JWT 校验、创建指标这三段核心代码。最后进入第一个功能开发——添加设备的上半场：需求分析、索引库设计与写入代码。

## 先给结论

- 亿可控用 MySQL、InfluxDB、Elasticsearch 三种数据库，MySQL 只设计五张表：管理员表、指标配置表、报警配置表、看板配置表、GPS 配置表，全是配置类预制数据。
- 环境用课程配套的虚拟机镜像：NAT 模式、IP `192.168.200.128`，Docker 里已装好 Elasticsearch、EMQ、Consul、MySQL、InfluxDB，建库 `ykk`（utf8mb4）后执行五张表的建表语句即可。
- 配置中心用 Consul：在 key/value 里创建 `config/backend-service/data`，value 为 MySQL 与 Redis 的连接配置 JSON，后续随功能叠加再补 InfluxDB、ES 的配置。
- 基础工程分 backend（主工程）与 common（公共模块）两个子工程，包结构是经典的 config/controller/entity/httpfilter/mapper/service/util/vo 分层。
- 登录逻辑返回管理员 ID，控制器用 `JwtUtil.createJWT(adminId)` 生成 token，`AuthFilter` 对除 `/login` 外的所有请求做 token 校验，失败返回 401。
- 设备不做手动添加：报文上报解析出设备编号，库里没有就自动入库；设备数据存 ES，索引 `devices` 七个字段，用高级 REST 客户端的 `index` 方法写入。

## MySQL 库表设计：五张表管住所有配置

亿可控一共用到三种类型的数据库——MySQL、InfluxDB、Elasticsearch，这里只讲 MySQL 的设计：五张表，数量不多，主要用来做基本配置。

第一张是管理员表 `tb_admin`：登录账号、密码，外加两个特殊字段。`type` 是预留字段，1 表示超级管理员、0 表示普通用户，目前系统里所有用户其实都是超级管理员。`board` 存看板列表：管理员登录后进入首页，首页会显示很多图表，而这些图表是可以定制的——编辑看板里把某个看板勾掉，它就隐藏起来，这个字段记录的就是每个管理员自己的看板列表。

第二张是指标配置表，也是最重要的一张。物联网设备上报的报文，不同行业、甚至不同设备都不一样，为了实现系统通用性，解析报文的规则被设计成写进数据库表里，而不是写死在代码里。它对应产品原型里"指标管理 → 添加指标"那个界面：指标名称、单位、主题、指标值字段类型、指标值字段、设备识别码字段、webhook、安全值，这些添加进去的数据就落在这张表上。

第三张是报警配置表 `tb_alarm`，对应原型里"添加报警"界面：报警名称、报警指标、webhook、报警阈值、报警级别、沉默周期，界面上的所有字段在表里都有对应字段。第四张是看板配置表 `board`，对应首页"添加看板"的操作：存 `admin_id`（每个管理员操作自己的面板）、面板名称、指标、设备，还有两个标志位——是否系统看板（区分内置看板和用户自建看板）和显示开关 `disable`。第五张是 GPS 配置表 `tb_gps`，对应指标管理里那个特殊的 GPS 指标：报文主题、设备识别码字段之外，关键是指标值类型分单字段和多字段——单字段意味着经纬度挤在一个字段里、必然有分隔符，表里用 `value_key` 加分隔符字段表达；多字段则分别存经度 `longitude` 和纬度 `latitude`。一张表同时兼容两种传法。

建库建表用现成的讲义语句，字符集选 `utf8mb4`、排序规则 `utf8mb4_bin`：

```sql
CREATE DATABASE ykk CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;

CREATE TABLE IF NOT EXISTS tb_alarm (
    id INT AUTO_INCREMENT COMMENT 'id' PRIMARY KEY,
    name VARCHAR(50) NULL COMMENT '报警名称',
    quota_id INT NULL COMMENT '指标id',
    operator VARCHAR(18) NULL COMMENT '运算符',
    threshold INT NULL COMMENT '报警阈值',
    level INT NULL COMMENT '报警级别 1一般 2严重',
    cycle INT NULL COMMENT '报警周期（分钟）',
    webhook VARCHAR(1000) NULL COMMENT 'web钩子',
    CONSTRAINT tb_alarm_name_uindex UNIQUE (name)
);
```

注意报警名称上有唯一约束，同一个名字的报警规则不允许重复。

## 环境准备：虚拟机、建库建表与 Consul 配置

环境准备的第一步是加载虚拟机镜像。课程配套资料的"环境"文件夹下有一个镜像压缩包，解压后双击虚拟机配置文件，用 VMware 打开挂载；网络连接方式用 NAT 模式；启动时选择"我已移动该虚拟机"。这套环境的代码 IP 是 `192.168.200.128`，如果你加载出来的 IP 不一样，后续配置里对应改掉即可。

这个镜像里已经装好 Docker 并拉取了所需镜像，Elasticsearch、EMQ、Consul、MySQL、InfluxDB 这些项目要用的软件全都开箱即用，后面的开发就跑在这套环境上。用客户端工具连虚拟机：SSH 客户端用 `root / 123456` 连接；MySQL 客户端新建连接，主机 `192.168.200.128`、用户名 `root`、密码 `root123`。连上后创建数据库 `ykk`，选好字符集，然后把讲义里提供的五张表建表语句整体复制执行，刷新后表就全出来了，数据库准备完成。

下一步是配置中心。亿可控用 Consul 做配置中心，它以容器方式跑在虚拟机里，浏览器打开 `http://192.168.200.128:8500/`，选中 key/value 点 Create 创建。key 用讲义里定义好的 `config/backend-service/data`，value 粘贴这段配置：

```json
{
  "spring": {
    "datasource": {
      "url": "jdbc:mysql://192.168.200.128:3306/ykk?useUnicode=true&autoReconnect=true&autoReconnectForPools=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai",
      "username": "root",
      "password": "root123",
      "driver-class-name": "com.mysql.jdbc.Driver"
    },
    "redis": {
      "host": "192.168.200.128",
      "port": 6379,
      "database": 0
    },
    "lettuce": {
      "pool": {
        "max-active": 10, "max-wait": -1, "max-idle": 5,
        "min-idle": 1, "shutdown-timeout": 100, "timeout": 1000

```

目前这份配置只包含 MySQL 和 Redis 两块，Redis 用 Lettuce 连接池。这一步很简单，点 Save 保存就完成了。后续随着功能叠加，还要往里添加 InfluxDB、Elasticsearch 等配置；想修改时，Consul 的 key 是三级目录结构，逐层点进去就能编辑，不需要的配置也可以直接删除。

## 工程结构与基础代码：登录、JWT 与创建指标

亿可控的开发方式是基于一套初始代码做核心功能开发——这套基础代码已经完成了五张表的增删改查，先解析它的结构和关键代码，后面开发时直接往上加。

初始代码从配套资料的"开发"文件夹里拿，解压后导入 IDEA。整个工程分两个子工程：`backend` 是后台主工程，`common` 是公共模块，与具体业务关联不大的通用类都放这里。主工程里是熟悉的分层结构：启动类之外，`config` 放配置类，`controller` 放控制器，`entity` 放实体类——对应刚建好的五张表；`httpfilter` 放过滤器（如 `AuthFilter`），`mapper` 是 MyBatis-Plus 的数据访问层接口，`service` 下是服务接口加 `impl` 实现类，`util` 放工具类（`JsonUtil`、`JwtUtil` 等），`vo` 放视图层实体对象——前端特有结构或前端向后端传递的特殊实体都用 VO 定义。后期还会引入 DTO：与前端打交道的叫 VO，与数据库无关、服务业务逻辑的实体类叫 DTO。

### 登录与 JWT 校验

登录逻辑在 `AdminService` 里定义一个 `login` 方法，接收登录名和密码。实现类里三步走：先对两个参数做非空校验，为空返回 -1；再按用户名查询，查不到说明用户不存在，返回 -1；最后用 BCrypt 做密码匹配（密码用现在主流的 BCrypt 加密存储），匹配成功返回管理员 ID——一个一定大于 0 的值。

```java
@Override
public Integer login(String loginName, String password) {
    if (Strings.isNullOrEmpty(loginName) || Strings.isNullOrEmpty(password)) {
        return -1;
    }
    QueryWrapper<AdminEntity> queryWrapper = new QueryWrapper<>();
    queryWrapper.lambda().eq(AdminEntity::getLoginName, loginName);
    AdminEntity admin = this.getOne(queryWrapper);
    if (admin == null) {
        return -1;
    }
    BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();
    if (!encoder.matches(password, admin.getPassword())) {
        return -1;
    }
    return admin.getId();
}
```

控制器里暴露 login 接口，接收一个 VO——它只有登录名和密码两个属性，因为实体类和数据库结构一致、字段很多，而登录用不了那么多。返回值小于 0 表示登录名不存在或密码错误，置 `loginSuccess=false`；大于 0 就调 `JwtUtil.createJWT(adminId)` 生成一个 JWT 标准的长串 token，存进返回对象并置 `loginSuccess=true`。前端拿到 token 后保存，之后所有需要登录才能完成的请求都要带上并校验它。

校验动作发生在过滤器 `AuthFilter` 里：它拦所有路径，`doFilter` 先取请求路径，`/login` 直接放行——否则永远登录不进来；然后从请求头取出 token 做非空校验，再用 `JwtUtil.parseJWT` 校验，校验失败抛异常、响应 401，成功则放行。以后想让某个地址免登录，照这个样子加一段放行代码即可。

### 创建指标与 VO 的价值

指标管理里的创建指标在 `QuotaController` 里，是个 POST 方法，接收一个指标的 VO：

```java
@PostMapping
public boolean create(@RequestBody QuotaVO vo) {
    try {
        QuotaEntity quotaEntity = new QuotaEntity();
        BeanUtils.copyProperties(vo, quotaEntity);
        return quotaService.save(quotaEntity);
    } catch (DuplicateKeyException e) {
        throw new BusinessException("已存在该名称");
    }
}
```

这段的看点是 `BeanUtils.copyProperties(vo, entity)`：只要属性名相同，就把 VO 的属性值拷给实体对象，然后走 service 保存。为什么传 VO 而不直接传实体类？直接传现在看也没问题，但这么做是为了让前后端对接更灵活：VO 面向前端，实体类和数据库结构一一对应；如果哪天前端需求变了要加属性，改 VO 无伤大雅，改实体就等于动数据库结构，得不偿失。实践约定是 VO 尽量与实体属性保持一致，这样靠 copyProperties 就免掉大量 set 方法，个别不一致的字段再单独复制。

插入重名会触发数据库的唯一键冲突 `DuplicateKeyException`，代码里捕获后转成业务异常"已存在该名称"，给前端友好提示。旁边还有个分页查询接口：`page` 默认 1、`pageSize` 默认 10，可按指标名 `quotaName` 过滤，结果包成 `PagerEntity` 返回。

## 添加设备（上）：自动添加、索引库与写入代码

设备管理包含设备的添加、分页查询、按 ID 查询、更新设备信息几块。但翻遍产品原型，设备管理里只有分页列表和搜索，根本没有添加设备的入口——因为亿可控不提供手动添加，而是自动添加。

原因在第一篇就提过：物联网设备数量非常多，共享单车动辄几百万上千万台，手动录入根本不现实。实际流程是设备报文报上来之后，系统从报文里解析出设备编号，查一下库里没有这台设备，就自动添加。所以代码层面只需要提供一个"添加设备"的方法，供报文解析等业务调用。

存储选型也由此决定：设备数量多、操作频繁、搜索频繁，不用 MySQL，用 Elasticsearch 存设备数据。动手前先梳理索引库结构。从产品原型里能提取出来的字段有三个：设备编号；设备标签——给设备打的标记，一个设备可以打多个标签，可以是位置属性（如商圈、学校），也可以是分类（如温度计、湿度计），主要为了按标签快速搜索；设备状态开关——手动更改，关掉之后这台设备发来的报文系统就不再存储、不再解析。界面上看不到但业务需要的还有四个：是否告警、告警名称、告警级别（来自设备详情里的告警信息，也要从索引库查），以及是否在线。注意在线和告警是两个独立维度：在线只分在线、离线，告警才分一般告警和严重告警，设备状态由多个字段共同决定，不是一个字段搞定。对应到 ES 的映射定义：

```json
PUT /devices
{
  "mappings": {
    "properties": {
      "deviceID":   { "type": "keyword" },
      "alarm":      { "type": "boolean" },
      "alarmName":  { "type": "keyword" },
      "level":      { "type": "integer" },
      "online":     { "type": "boolean" },
      "status":     { "type": "boolean" },
      "tag":        { "type": "keyword" }
    }
  }
}
```

落地分四步。第一步建索引库：浏览器打开 Kibana（`192.168.200.128:5601`），进开发工具（扳手图标），把上面的建库语句粘进去点执行，提示成功即完成。第二步引依赖：用的是 ES 高级 REST API，在后台工程 pom 里加 `elasticsearch-rest-high-level-client` 和 `elasticsearch` 两个依赖，版本 `7.7.1`。第三步加配置：把 ES 配置加进 Consul 的 key/value，放在 spring 节点下——`elasticsearch.rest.uris: http://192.168.200.128:9200`，保存。第四步创建实体类：注意它不放 `entity` 包，那个包和 MyBatis-Plus、MySQL 绑定；与数据库无关的业务实体单独放 `dto` 包：

```java
@Data
public class DeviceDTO implements Serializable {
    private String deviceID;   // 设备编号
    private Boolean alarm;     // 是否告警
    private String alarmName;  // 告警名称
    private Integer level;     // 告警级别
    private Boolean online;    // 是否在线
    private String tag;        // 标签
    private Boolean status;    // 开关
}
```

有了 DTO，再写数据访问层。新建一个 `es` 包，和 MyBatis-Plus 的 `mapper` 区分开，里面建 `ESRepository` 类，加上 `@Component` 注解，注入 `RestHighLevelClient`：

```java
public void addDevice(DeviceDTO deviceDTO) {
    if (deviceDTO == null || deviceDTO.getDeviceID() == null) {
        return;
    }
    try {
        Map map = JsonUtil.getByJson(JsonUtil.serialize(deviceDTO), Map.class);
        IndexRequest request = new IndexRequest("devices")
                .source(map)
                .id(deviceDTO.getDeviceID());
        client.index(request, RequestOptions.DEFAULT);
    } catch (Exception e) {
        log.error("设备添加发生异常", e);
    }
}
```

方法开头先做非空校验：对象为 null 或设备编号为 null 都直接返回，保证不带脏数据往下走。核心是 ES 高级客户端的 `index` 方法，它需要一个 `IndexRequest`（构造时传索引库名 `devices`）和一个请求选项对象。有个版本相关的坑要记下：新版 ES 的 `source` 方法不能直接传对象，会报错，传 Map 才没问题；而手动 `new HashMap` 再一个个 `put` 太啰嗦，工程里的工具类 `JsonUtil` 提供了捷径——先 `serialize` 把 DTO 转成 JSON 串，再 `getByJson` 反转成 Map，不管多少个属性两句话搞定。`request.id()` 用设备编号做文档 ID，保证同一设备重复写入时是覆盖而不是重复堆积。`RequestOptions.DEFAULT` 是目前唯一的选项，这么设计是为了便于以后扩展。异常统一 catch 住打日志"设备添加发生异常"，不让单条失败影响整体流程。到这一步，设备写入 ES 的能力就齐了，下一半是分页查询等其余设备管理功能。

## 小结

这一篇把亿可控从"图纸"推进到"能开工"：五张 MySQL 配置表覆盖管理员、指标规则、报警规则、看板、GPS 五类配置；虚拟机镜像自带全套中间件，Consul 收敛配置；基础工程的分层结构和登录/JWT/创建指标三段代码，把 VO、copyProperties、过滤器鉴权这几个日常会反复用到的模式都过了一遍；添加设备的上半场则确立了"报文解析自动入库 + ES 存储"的设备管理基调。下一半继续设备管理：分页查询、按 ID 查询与更新设备信息。
