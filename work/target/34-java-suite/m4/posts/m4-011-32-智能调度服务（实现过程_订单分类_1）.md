# 智能调度·订单分类实现上半：需求逻辑与代码推进（1-10 讲）

上篇把调度链路打通：schedule_job 表驱动 Quartz 触发，反射调用落到 DispatchTask.run，但 run 里还只有一行日志占位。这一篇开始填真正的核心逻辑——智能调度的第一个阶段"订单分类"。十个视频讲的是同一件事的前半程：把庞大流程拆成一个个 Service，写出订单分类的接口与实现类，把当前机构的新订单查出来，并推到目的地网点计算的关键五步。

## 先给结论

- 智能调度按处理流程拆阶段：订单分类 → 路线规划 → 创建运输任务 → 规划车次车辆 → 司机运输作业，整体几千行代码，不可能塞进一个 run 方法。每个阶段封装一对接口+实现类，订单分类的 ITaskOrderClassifyService 只声明一个 execute(agencyId, jobId, logId)。
- 三个参数都有明确来源：agencyId 来自任务实体的 businessId，真实数据对应 pd_auth 库组织机构表的主键——哪个网点（或转运中心）的任务就只分类谁的订单；jobId 是 schedule_job 主键；logId 是 executeInternal 里刚生成的日志实体 id。三者都在反射调用 run 时传入，DispatchTask 直接透传。
- 返回值 List<OrderClassifyGroupDTO>：每个分组对象里，key 由 startAgencyId、endAgencyId、currentAgencyId 三个机构 id 拼接，others 存这一类的原始订单集合。判断订单是不是新订单，标准就是 startAgencyId 等于 currentAgencyId。
- 实现思路固定三步：获取当前机构所有订单（分新订单和中转订单）→ 订单分类 → 分类结果落库（订单分类表 + 订单分类与订单的关联表）。新订单是本机构收上来的单子，状态为网点入库；中转订单是转运过来的，状态不同，所以分开查询再合并。
- 查新订单走 OrderFeign 远程调 OMS 服务，条件只有两个：当前机构 + 状态 OUTLETS_WAREHOUSE；查回来用 stream + Lombok 构建器转成 OrderClassifyDTO。
- endAgencyId（目的地网点）订单里没有，必须算：拼完整地址 → 百度地图取经纬度 → 逆地理编码拿 adcode（补六个 0 查 pd_area 并与下单区县比对）→ 查区县下所有网点 → 算距离最近的网点。每一步取值都判空，统一走封装的 exceptionHappend。

## 从空壳 run 到订单分类接口：参数从哪来

智能调度的完整流程——订单分类、路线规划、归好路线后创建运输任务、规划车次车辆、创建司机运输作业——代码量以千行计，全写进 run 方法这个方法就废了。处理办法是按流程的关键阶段做功能抽取与封装：一个阶段一个 Service，接口放 service 包，实现类放 impl 包。第一个阶段是订单分类，接口只声明一个方法，名字统一叫 execute：

```java
public interface ITaskOrderClassifyService {
    /**
     * 处理订单分类Service接口
     */
    List<OrderClassifyGroupDTO> execute(String agencyId, String jobId, String logId);
}
```

DispatchTask 本身以 @Component 注册、归 Spring 容器管理，直接注入并调用：

```java
@Autowired
private ITaskOrderClassifyService taskOrderClassifyService;

public void run(String businessId, String params, String jobId, String logId) {
    List<OrderClassifyGroupDTO> orderClassifyGroupDTOList =
            taskOrderClassifyService.execute(businessId, jobId, logId);
}
```

三个参数追根溯源，都在定时任务那条链路上。定时任务触发时，executeInternal 通过 context.getMergedJobDataMap() 取回创建任务时 put 进去的 ScheduleJobEntity，实体属性与 schedule_job 表字段一一对应：getId() 就是 jobId，即表主键；getBusinessId() 就是机构 id——测试数据里随手写的 123 只是占位，真实数据它对应 pd_auth 库里组织机构表某个网点或转运中心的主键；logId 则是同一个方法里刚 new 出来、id 已经生成的日志实体。所以 execute 拿到的是三样东西：分类谁的订单（agencyId）、哪次任务触发（jobId）、哪条执行日志（logId）。

返回值的设计直接体现分类语义。OrderClassifyGroupDTO 里有 id、key、others：key 由 startAgencyId、endAgencyId、currentAgencyId 三个维度拼接；others 是原始订单集合。分完之后一共有多少类，列表里就有多少个对象——同一类里的订单，起始机构、目的机构、当前机构三个维度完全相同。新订单的判定也随之清晰：startAgencyId 等于 currentAgencyId，即这个单子就是当前机构自己收的。

## 实现类三步走：先把当前机构的新订单捞出来

TaskOrderClassifyServiceImpl 放 impl 包，implements 接口、@Service 交容器管理、注释写明"订单分类核心逻辑"。execute 的骨架按三步走：

```java
@Service
public class TaskOrderClassifyServiceImpl implements ITaskOrderClassifyService {

    @Autowired
    private OrderFeign orderFeign;

    @Override
    public List<OrderClassifyGroupDTO> execute(String agencyId, String jobId, String logId) {
        // 收集当前机构下的所有订单（新订单 + 中转订单）
        List<OrderClassifyDTO> orderClassifyDTOS = new ArrayList<>();
        // 最终返回的分类结果
        List<OrderClassifyGroupDTO> orderClassifyGroupDTOS = new ArrayList<>();
        // 获取当前机构下的所有订单数据（分为新订单和中转订单）
        orderClassifyDTOS.addAll(buildNewOrder(agencyId));
        // 进行订单分类
        // 将分类结果保存到数据库
        return orderClassifyGroupDTOS;
    }
}
```

订单分两类。新订单：实际机构就是当前网点，网点自己收上来的单子；中转订单：单子不是本机构收的，从别处转运而来——比如一个转运中心，手里全是从其他地方转运过来的单子。两类订单状态不一样，获取方式也不同，所以要分别查再合并到一个集合。分类结果最终要落两张表：订单分类表，以及订单分类与具体订单的关联表。

buildNewOrder 专门负责新订单。订单数据不在 pd_dispatch 库，在 OMS 那边，所以注入 OrderFeign 远程调用：

```java
private List<OrderClassifyDTO> buildNewOrder(String agencyId) {
    OrderSearchDTO orderSearchDTO = new OrderSearchDTO();
    // 订单状态为网点入库
    orderSearchDTO.setStatus(OrderStatus.OUTLETS_WAREHOUSE.getCode());
    orderSearchDTO.setCurrentAgencyId(agencyId);
    // 调用 Feign 接口远程调用，查询当前机构下的新订单
    List<Order> orderList = orderFeign.list(orderSearchDTO);
    log.info("查询到新订单个数: {}", orderList.size());
    OrderClassifyDTO.OrderClassifyDTOBuilder builder = OrderClassifyDTO.builder();
    builder.currentAgencyId(agencyId); // 当前机构，每条都一样
    return orderList.stream().map(item -> {
        builder.order(item); // 原始订单
        builder.startAgencyId(agencyId); // 起始机构：新订单就是当前机构
        builder.endAgencyId(getEndAgencyId(item)); // 目的地机构，待计算
        builder.orderType(item.getOrderType()); // 订单类型
        builder.goodsType(item.getGoodsType()); // 商品类型
        return builder.build();
    }).collect(Collectors.toList());
}
```

查询条件两个就卡住了目标数据：当前机构 + 网点入库状态。网点入库之后是待装车、运输中、网点出库这些状态，都不属于新订单的范畴。DTO 上加了 @Builder 注解，所以用构建器组装：currentAgencyId 每条都相同，循环外设置一次；order 放原始订单；startAgencyId 对新订单而言就是当前机构；endAgencyId 是目的地机构——收件人地址最终由哪个网点派送，订单表里没有这个字段，只能算出来。getEndAgencyId 先 return null 占位，这是本篇剩下内容的全部重点。

## 目的地网点计算：地址 → 坐标 → 区域 → 网点

getEndAgencyId 的完整推演是五步，先看整体链路：

```mermaid
flowchart LR
    A[拼接收件人完整地址] --> B[百度地图取经纬度]
    B --> C[逆地理编码取 adcode]
    C --> D[补 6 个 0 查 pd_area<br>与下单区县比对]
    D --> E[查区县下所有网点]
    E --> F[计算距离收件地址最近的网点]
```

第一步，拼完整地址。订单表里省市区存的是 ID（receiverProvinceId / receiverCityId / receiverCountyId），receiverAddress 只存街道那段，比如"建材城西路金燕龙办公楼"。要给百度地图一个"北京市昌平区建材城西路金燕龙办公楼"，得先把 ID 换成名称。区域数据在 pd_auth server——品达物流外围的基础服务，管统一认证授权、区域管理、组织、角色岗位这些模块，操作的是 pd_auth 库（pd_area 区域表的数据细到村一级）。注入 AreaApi，但不直接调，走封装好的 PdCompletableFuture 异步查：

```java
@SneakyThrows
private String receiverFullAddress(Order order) {
    Long provinceId = Long.valueOf(order.getReceiverProvinceId()); // 省份id
    Long cityId = Long.valueOf(order.getReceiverCityId()); // 市id
    Long countyId = Long.valueOf(order.getReceiverCountyId()); // 区id
    Set<Long> areaSet = new HashSet<>();
    areaSet.add(provinceId);
    areaSet.add(cityId);
    areaSet.add(countyId);
    CompletableFuture<Map<Long, Area>> future =
            PdCompletableFuture.areaMapFuture(areaApi, null, areaSet);
    Map<Long, Area> areaMap = future.get();
    String provinceName = areaMap.get(provinceId).getName();
    String cityName = areaMap.get(cityId).getName();
    String countyName = areaMap.get(countyId).getName();
    StringBuffer stringBuffer = new StringBuffer();
    stringBuffer.append(provinceName).append(cityName)
            .append(countyName).append(order.getReceiverAddress());
    return stringBuffer.toString();
}
```

这个封装类内部替我们调 Feign：传进去 areaApi 和一组区域 ID（省市区三个，实体里的 String 要 Long.valueOf 转一下），回来一个 Map<Long, Area>——key 是区域 ID，value 是 Area 对象（内部 Collectors.toMap 以区域 id 作 key）。按 ID 取 getName 拿到省、市、区名称，StringBuffer 拼上详细地址返回。一个疑点：万一 receiverAddress 里本来就带着省市区，拼出来会重复——实际不影响，只要地址真实存在，百度地图都能正常解析，课上专门验证过。

地址为空直接调 exceptionHappend("收件人地址不能为空")。这个方法是本篇抽出来的统一异常出口：整个计算过程校验很多，凡是需要抛异常的地方都调它，把提示信息传进去，内部 throw 并打印堆栈，不用每个分支都写一遍 try-catch。

第二步，地址换坐标。pinda-common 里提供了百度地图工具类 EntCoordSyncJob，getCoordinate(address) 返回经纬度坐标；用 main 方法拿"北京市昌平区建材城西路金燕龙办公楼"实测，能拿到坐标值。但随便编的地址解析不出坐标，返回空，所以要接着判空：

```java
String location = EntCoordSyncJob.getCoordinate(address);
if (StringUtils.isBlank(location)) {
    exceptionHappend("收件人地址不正确");
}
log.info("根据地址[{}]获取对应的坐标值[{}]", address, location);
```

第三步，坐标换区域并校验。getLocationByPosition(location) 调百度官方逆地理编码，返回的 Map 里有 cityLevel、country、formattedAddress、distance 等一堆字段，我们只关心一个 key：adcode——行政区划编码。它和系统区域表 pd_area 的 area_code 是同一套编码，比如 110114 对应北京昌平。拿到 adcode 后查自己的库做比对：

```java
Map map = EntCoordSyncJob.getLocationByPosition(location);
if (ObjectUtils.isEmpty(map)) {
    exceptionHappend("根据经纬度获取区域信息为空");
}
String adcode = (String) map.get("adcode");
// 系统中统一存储：6 位区划编码 + 6 个 0
R<Area> areaR = areaApi.getByCode(adcode + "000000");
Area area = areaR.getData();
if (area == null) {
    exceptionHappend("没有查询到区域数据");
}
// 比对：根据坐标算出的区县 与 下单时选择的区县是否一致
if (!order.getReceiverCountyId().equals(area.getId())) {
    exceptionHappend("收货地址区域id和根据坐标计算出的区域不一致");
}
```

这里有个约定：库里存的是 12 位编码，6 位区划编码后面统一补 6 个 0，查询必须按这个格式传，pd_auth server 才解析得出来——getByCode 实际是 GET 请求 /area/code/{code}，浏览器里拼上 110114000000 直接请求，返回的 name 正是昌平区，说明两套编码一致。校验的两种失败——查不到区域、区域与下单时不一致——都说明地址有问题，后边没法正常处理；正常录入的数据一般都能对上。

第四步，查区县下所有网点。网点覆盖数据在 pd_base 库的 pd_agency_scope 机构作业范围表：agency_id 是网点 id，area_id 是所属区县的区域 id，muti_points 是一系列坐标点，围成该网点业务覆盖的图形。查询走 AgencyScopeFeign.findAllAgencyScope，以区域 id 为条件（前面校验通过，直接拿 area.getId()，注意转成 String），其余条件传空。课上先起好 pd_base 服务，在 Swagger 里实测了这个接口（GET /scope/agency/findALLAgencyScope）：传真实 areaId 能返回网点数组，要的就是里面的 agency_id；传不存在的 id 返回空——代码里照样判空兜底：

```java
// 根据区域id查询该区县下所有网点，其余查询条件传空
List<AgencyScopeDTO> agencyScope =
        agencyScopeFeign.findAllAgencyScope(area.getId().toString(), null);
if (agencyScope == null || agencyScope.size() == 0) {
    exceptionHappend("无法获取收件人所在网点信息");
}
```

```json

  {"lng":116.327566,"lat":40.067944},
  {"lng":116.362215,"lat":40.0741},
```

## 小结

这十个视频把订单分类从接口推到一半：接口、实现类、两个 DTO 定型，新订单查询靠 OrderFeign 两个条件查通；目的地网点计算走完"拼地址 → 取坐标 → 取区域比对 → 查网点"四步，最后一步 calculate 的距离计算留给下半篇，中转订单查询与分类结果落库也在后面。两条工程习惯贯穿始终：一是复杂流程按阶段拆 Service，run 方法只做分发；二是链路上每次取值都判空抛异常，地址空、坐标空、区域空、网点空各有各的提示，保证调度这种后台批处理出了问题能定位到具体环节。
