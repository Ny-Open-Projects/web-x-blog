# 用户工作量查询：需求思路、详情/列表查询实现与测试

立可得第八章「统计分析」开篇是并发异步编程 CompletableFuture，紧接着就用它做第一个实战功能：用户工作量查询。运营后台要一张表格，统计每个用户的完成工单、进行工单和拒绝工单数，支持按人员姓名和角色筛选；点开某个用户的详情，还要看到本周、本月、本年三个时间维度下的总工单数与各类状态工单数。这两个页面看着是两个功能，背后其实共用同一个核心查询。这篇把需求拆解、详情查询、列表查询和联调测试一次讲完，重点是四路并发统计的写法。

## 先给结论

- 两个功能一个核心方法：按用户 ID 加开始、截止时间查询工作量信息。详情页前端传不同时间段调三次（本周/本月/本年），列表页在循环里逐人调用，方法本身只写一次。
- 时间周期由前端传入：本周、本月、本年本质都是「开始时间 + 截止时间」，后端只提供时间段查询接口，不必为每个维度单独写逻辑。
- 核心统计是四路并发：CompletableFuture.supplyAsync 分别查完成、取消、进行中和总数，allOf().join() 汇合；比上一节更进一步，用 whenComplete 回调直接给返回对象赋值，免掉事后逐个 get()，异常时降级为 0 并记日志。
- 条件可空设计：统计方法里工单状态传 null 表示查全部，用户 ID 传 null 表示不限人；工单按指派人 assignorId 和 updateTime 时间窗过滤。
- 列表复用 UserWork 视图模型：补 userName、roleName、mobile 三个字段就能同时服务详情和列表，不必另建 VO；列表在用户微服务、工作量在工单微服务，中间走 Feign 接口加降级工厂，调用失败返回各计数为 0 的对象。
- 列表页统计的是本月数据：开始时间为当月一号零点，截止为当前时间，远程调用前要把 LocalDateTime 格式化成字符串。

## 需求与实现思路：两个关联的功能

需求分两个页面。列表页以表格展现每个用户的完成工单、进行工单、拒绝工单数，支持通过人员姓名和角色筛选。详情页在点「查看详情」后出现，一部分展现这个人的具体信息（姓名、角色、电话、负责区域），另一部分按本周、本月、本年三个时间维度，统计总工单数、拒绝工单、完成工单、进行工单。

实现思路上是两个功能，但关联紧密。第一个是业务逻辑方法：通过用户 ID、开始和截止时间查询用户的工作量信息，包括总工单数、拒绝工单、完成工单和进行工单。它主要服务详情页——本周也好本月也好，本质都是一个时间周期，都能用开始时间和截止时间表示，而且这个时间段由前端传递。所以后端只需要给前端一个按时间段查询的接口，前端要展现三个维度就调用三次，分别传不同的开始截止时间。

第二个是列表。列表要把所有人员都列出来，而人员数据在用户微服务里，所以这个功能应该在用户微服务实现：先做用户的分页列表查询，拿到每个人的信息之后，在循环中根据每个人的 ID，去工单微服务调用上面那个核心方法查出工作量，赋给实体，最后以整体结果返回前端。这个查询细节同样会用第一小节的 CompletableFuture 并发异步编程，把多个计数查询并发执行，极大提高查询效率。

API 文档里对应的定义是「管理后台 - 用户服务 - 获取用户工作量（工单统计）」，入参用户 ID、开始时间、截止时间，返回用户 ID、完成工单、进行中工单、取消工单、工单总数。

## 详情查询：一个计数方法加四路并发

先建视图模型。在 service_common 里定义 UserWork，五个属性对应 API 返回：

```java
public class UserWork {
    // 用户ID
    private Integer userId;
    // 完成工单数
    private Integer workCount;
    // 进行中工单数
    private Integer progressTotal;
    // 取消工单数
    private Integer cancelCount;
    // 工单总数
    private Integer total;
}
```

然后到工单微服务的 TaskService 里定义业务方法 getUserWork，参数是 userId、开始时间、截止时间，返回 UserWork。它的实现依赖一个私有统计方法——完成、取消、进行中、总数四个查询整体逻辑类似，只是条件不同，所以先封装一个「根据用户 ID 和工单状态查询工单数」的方法：

```java
private Integer getCountByUserId(Integer userId, Integer status,
                                 LocalDateTime start, LocalDateTime end) {
    var qw = new LambdaQueryWrapper<TaskEntity>();
    qw.ge(TaskEntity::getUpdateTime, start)
      .le(TaskEntity::getUpdateTime, end);
    // 状态可能不传：为 null 表示查全部数据
    if (status != null) {
        qw.eq(TaskEntity::getTaskStatus, status);
    }
    // 用户ID也可能传 null；按指派人ID查询
    if (userId != null) {
        qw.eq(TaskEntity::getAssignorId, userId);
    }
    return this.count(qw);
}
```

时间条件挂在 TaskEntity 的 updateTime 上，ge 起始、le 截止构成时间窗；工单按被指派的人（assignorId）统计。

getUserWork 的实现就是四路并发。先 new 一个 UserWork 把 userId 设进去，然后四个 CompletableFuture 各查一类计数：

```java
var workCountFuture = CompletableFuture.supplyAsync(
        () -> this.getCountByUserId(userId, VMSystem.TASK_STATUS_FINISH, start, end))
    .whenComplete((r, e) -> {
        if (e != null) {
            userWork.setWorkCount(0);
            log.error("user work error", e);
        } else {
            userWork.setWorkCount(r);
        }
    });
var totalFuture = CompletableFuture.supplyAsync(
        () -> this.getCountByUserId(userId, null, start, end))
    .whenComplete((r, e) -> {
        if (e != null) {
            userWork.setTotal(0);
            log.error("user work error", e);
        } else {
            userWork.setTotal(r);
        }
    });
// cancelCountFuture、progressTotalFuture 同理，
// 分别用 TASK_STATUS_CANCEL、TASK_STATUS_PROGRESS 查询并赋值
CompletableFuture.allOf(workCountFuture, totalFuture,
        cancelCountFuture, progressTotalFuture).join();
return userWork;
```

这里和第一小节的实现有一个关键区别。上一节的做法是拿到 future 之后在后面逐个调 get() 取值再赋值；这一节换成在 supplyAsync 之后直接挂 whenComplete 回调——它接收两个参数，第一个是返回值，第二个是异常对象，任务结束时回调里完成赋值，不再需要 get()。异常分支里把对应计数设成 0，算是一种降级操作，总比直接报错强，同时用 log.error 把异常日志打出来。这种写法的好处一是代码清晰，二是异常捕获非常方便。

四个 future 的创建顺序无所谓，allOf 会把它们全部并发执行，join() 等所有任务完成。最后在 TaskController 里按 API 文档加一个接口方法，接收 userId 和两个时间参数（加 @DateTimeFormat 指定 yyyy-MM-dd HH:mm:ss 格式），调用 getUserWork 返回即可。

## 列表查询：用户分页加远程调用

列表 API 的入参是页码、页大小、用户名称、角色 ID 和「是否是运维人员」，返回是分页类型，每条记录包括用户 ID、用户名称、角色名称、手机号，加上完成工单、进行工单、拒绝工单三个计数。

观察返回结构会发现：用户 ID 加三个工单计数，恰好就是 UserWork 已经具备的属性，所以不必新建视图模型，直接给 UserWork 扩展三个字段——userName、roleName、mobile——让详情和列表共用一个类。

第二步是打通远程调用。列表逻辑在用户微服务，工作量方法在工单微服务，所以要把 getUserWork 封装进 service_common 的 Feign 接口 TaskService；同时修改对应的服务降级类 TaskServiceFallbackFactory，扩展这个方法——调用失败时返回一个兜底对象：

```java
public UserWork getUserWork(Integer userId, String start, String end) {
    var userWork = new UserWork();
    userWork.setUserId(userId);
    userWork.setWorkCount(0);
    userWork.setProgressTotal(0);
    userWork.setCancelCount(0);
    userWork.setTotal(0);
    return userWork;
}
```

第三步在用户微服务的 UserService 里写业务方法 searchUserWork，返回 Pager&lt;UserWork&gt;，参数是 pageIndex、pageSize、userName、roleId、isRepair。实现分三段：

```java
// 1. 分页查用户，人员数据都在这一步拿到
var userPager = this.findPage(pageIndex, pageSize, userName, roleId, isRepair);
// 2. 当前页每个用户远程调工单微服务，转换成 UserWork
var items = userPager.getCurrentPageRecords().stream().map(u -> {
    var now = LocalDateTime.now();
    // 列表统计当月数据：开始时间是当月一号零点
    var start = LocalDateTime.of(now.getYear(), now.getMonth(), 1, 0, 0, 0);
    var pattern = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
    var userWork = taskService.getUserWork(u.getId(),
            start.format(pattern), now.format(pattern));
    userWork.setUserName(u.getUserName());
    userWork.setRoleName(u.getRoleName());
    userWork.setMobile(u.getMobile());
    return userWork;
}).collect(Collectors.toList());
// 3. 封装分页对象
var result = Pager.buildEmpty();
result.setPageIndex(userPager.getPageIndex());
result.setPageSize(userPager.getPageSize());
result.setTotalCount(userPager.getTotalCount());
result.setTotalPage(userPager.getTotalPage());
result.setCurrentPageRecords(items);
return result;
```

几个细节。列表显示的是当月的数据，所以开始时间用 LocalDateTime.of(now.getYear(), now.getMonth(), 1, 0, 0, 0)——年月取当前，日固定一号，时分秒全是零，即当月第一天凌晨；截止时间就是当前时间 now。而 Feign 接口的 getUserWork 收的是字符串，所以两个时间都要先 format 成 yyyy-MM-dd HH:mm:ss 再传。远程调用拿到工单计数后，用户名称、角色名称、手机号从循环变量 u 上补齐，map 之后的 collect(Collectors.toList()) 就是当前页的工作量列表。

分页封装没有黑魔法：新建一个空 Pager，pageIndex、pageSize、totalCount、totalPage 四个属性照搬用户分页对象，currentPageRecords 换成刚转换出来的 items。最后在 UserController 里按 API 文档新增 searchUserWork 接口，pageIndex 默认 1、pageSize 默认 10、userName 默认空串、roleId 默认 0、isRepair 默认 false，转发给业务方法即可。

## 联调测试

代码完成后启动三个微服务：工单微服务（要调它的方法）、用户微服务（列表接口在这）、微服务网关。测试用 task.http 脚本，里面已经写好用户工作量列表和用户工作量详情两个 API 的请求。

先测列表，只传页码和页大小，查第一页：

```http
GET http://{{hostName}}:{{port}}/user-service/user/searchUserWork?pageIndex=1&pageSize=10
Content-Type: application/json
Authorization: {{tokenValue}}
```

请求发出后能拿到分页结构的数据：pageIndex、pageSize、totalCount、currentPageRecords，每条记录里是人员信息加上工单统计。再测详情，测试数据里第六个用户是有工单数据的，脚本里传 userId=6 加开始时间、截止时间，单独查出这一个用户的工单量。两个接口都返回正常数据，这个功能就算测试通过。

## 小结

这一节把第一小节的 CompletableFuture 真正落到了业务里。需求上，详情页和列表页共用「用户 ID 加时间段查工作量」这个核心方法；实现上，私有方法 getCountByUserId 用可空的 status 和 userId 构造动态条件，getUserWork 用四路 supplyAsync 并发统计四类计数，whenComplete 回调内完成赋值和异常降级；列表侧在用户微服务里分页查人，循环里经 Feign 远程调用补工单计数，同时给 UserWork 扩展三个用户字段复用同一个视图模型，最后手动封装 Pager 返回。测试时工单微服务、用户微服务、网关三个服务要一起在场。这套「核心方法 + 并发聚合 + 远程组装」的组合，接下来还会出现在工单状态按日统计和人效排名里。
