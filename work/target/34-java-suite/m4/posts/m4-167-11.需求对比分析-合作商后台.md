# 立可得2.0升级收尾：三端需求对比、技术栈全面升级与短信服务落地

立可得2.0的需求分析来到最后一段：合作商后台、运营&运维管理APP、用户小程序三端的功能边界划定之后，就是技术升级对比、库表设计、工程结构调整。这篇把三端需求收尾，再过一遍技术选型、架构、环境准备和短信验证码实现，为多端登录鉴权打地基。

## 先给结论

- 合作商后台是2.0新增的查询型后台：看收益（今日/本周）、看收益趋势、按点位分账、支持筛选和对账导出。
- 运营&运维管理APP解决工单处理数字化：待办/进行中/历史工单三段式流转，接受后不能再拒绝、只能取消，最终回归的状态一致；运维APP多了选择定位，采集设备坐标为小程序"附近售货机"提供数据。
- 用户小程序替代H5工程：H5留不住用户，小程序依托微信用户体系登录极简，新增地图导航、微信支付、查看订单三个能力。
- 技术升级主线是"统一到MyBatis-Plus生态 + EMQ统一消息 + ES增强检索"：二级缓存、逻辑删除、公共字段填充、分表都换成MyBatis-Plus方案，netty和rabbitMQ被EMQ替代。
- 库表按售货机/工单/用户三库调整，新增商圈、区域、合作商、工单统计四张表，售货机表冗余合作商字段换查询效率，货道表加price支持同商品不同机不同价。
- 短信集成用spring-cloud-alicloud-sms四步完成：引依赖、配密钥与签名模板、写SmsConfig、写SmsSender；验证码Redis以手机号为key、五分钟过期兼防重复发送。

## 三端需求对比：把1.0的账补齐

### 合作商后台【新增】

1.0里合作商这个角色基本缺位，2.0补了一个完整的合作商后台，定位很明确：给合作商看收益。界面分几块：

- 顶部概览：今日/本周总收入与订单数，一眼看出经营状况；
- 中间一条收益趋势折线图，展示各时间点的收益变化；
- 下方是分账信息：合作商往往有多个点位，收益要区分到每个点位；
- 精细查询：点位多要能搜索定位，可按日期筛选对账区间，还能导出对账详情。

整个后台的功能本质就是各种查询。

### 运营&运维管理APP【新增】

这是2.0新增的另一块，核心目标是工单处理数字化：运营和运维人员在APP上有执行工单入口，可实时跟进工单进度、查看历史工单，便于平台调度与货品调配。登录走手机号快捷登录——后台人员管理里登记了手机号，登录即可识别到人。进去之后的主线是工单流转：

| 阶段 | 内容 | 关键点 |
| :--- | :--- | :--- |
| 待办工单 | 分派给我的工单列表 | 详情含设备号、地址、补货详情（哪个货道、补什么、补多少） |
| 拒绝/接受 | 接受前可以拒绝 | 拒绝必须填写理由 |
| 进行中工单 | 已接受正在处理的工单 | 想反悔只能取消，取消也要原因 |
| 历史工单 | 已完成的工单 | 可查询、可搜索 |

拒绝和取消是类似操作：拒绝发生在接受之前，接受后再想退出就只能取消，最终回归的工单状态一致。运维APP结构和运营APP基本对称，待办覆盖装机、维修、补货、撤机几类工单，区别是没有补货详情。运维APP多了"选择定位"：做投放类工单时自动采集设备位置存到后台，这正是小程序"搜索附近售货机"的数据基础。

### 用户小程序【替代H5】

1.0的用户端是H5工程，本质是个小电商：扫二维码在手机浏览器打开页面，浏览商品、下单支付。问题在于留不住用户——买完页面就关了，用户也很难再找到入口，等于持续流失。而新零售的出发点恰恰是线上线下相互导流，H5在这个关键点上不合格。

小程序在便捷性上不输H5：登录依托微信用户体系，点一下授权即可，还抓住了入口，后续可加入电商入口实现相互导流。相比H5有三个功能增量：

1. 地图导航：附近找不到售货机时，在小程序里做地图搜索，找到最近的售货机后导航过去购买——这是"线上向线下导流"的具体实现；
2. 下单支付：由原来的支付宝支付改为微信小程序支付；
3. 查看订单：在小程序里查看订单记录。

## 2.0技术升级：一张对比表看懂选型

需求定了，技术栈跟着调。2.0的升级对比表值得搬出来：

| 原有技术 | 变更后技术 | 变更原因 |
| :--- | :--- | :--- |
| mysql基础查询 | mybatis-plus二级缓存 | 提高查询效率，编码清爽 |
| 阿里云OSS图片存储 | MinIO对象存储 | 技术替换，免费开源；数据安全考虑 |
| mysql基础删除 | mybatis-plus逻辑删除 | 提高数据库可用性 |
| mysql基础插入、更新 | mybatis-plus公共字段填充 | 提高开发体验和效率 |
| 订单分表sharding-jdbc | mybatis-plus分表 | 原有技术兼容性问题 |
| Spring_schedule | XXL-job | 多任务分布式调度 |
| netty | EMQ ACL连接认证 | 提高安全性，新增物联网协议 |
| rabbitMQ | EMQ | 服务器端异步消息替换方案 |
| 基础搜索 | ES搜索 | 提高检索效率 |
| （新增） | logstash数据同步 | 同步mysql数据到ES |
| （新增） | ES geo搜索 | 搜索附近售货机；客户端导航实现方案 |
| （新增） | 售货机边缘计算方案 | 状态计算上报，分担服务器运算压力 |

几处值得展开的逻辑：

**逻辑删除**。直接物理删数据，误删就没了；逻辑删除只是把标记字段改成1（0表示保留），查询只取0的数据，误删的数据随时可恢复，类似操作系统的回收站；用MyBatis-Plus通过配置就能实现。

**公共字段填充**。很多表都有创建时间、更新时间，每次保存都要取当前时间塞进实体属性，写多了繁琐，MyBatis-Plus的自动填充用简单配置解决。

**netty+Redis 换 EMQ**。1.0用netty加Redis自己实现消息中间件，支撑物联网设备和系统间消息传输，定义了大量自定义协议，维护麻烦。2.0引入EMQ走MQTT发布订阅：更简便高效、并发支持更高，MQTT也是主流物联网协议；ACL连接认证用来识别接入设备的合法性。

**rabbitMQ 也换 EMQ**。不只设备侧，微服务之间的内部异步通信同样改用EMQ，一套中间件覆盖两类消息场景。

**XXL-job 替换 Spring_schedule**。Spring自带调度是单节点单任务，任务多、耗时长、量大时力不从心。XXL-job是分布式任务调度系统，平台上就能配置任务，还支持分片任务——大批量任务切分执行减少等待，比如给每台设备创建单任务。

此外，订单这类高频检索把数据放进ES提升效率，用logstash把MySQL数据同步到ES；ES的geo搜索支撑"查询附近售货机"；客户端导航可接百度、高德、腾讯地图；售货机端引入边缘计算，状态在设备侧算完直接上报，分担服务器压力。

### 库表设计：三库增量

2.0功能复杂了，原有库表不够用，调整集中在三库：

**售货机库**——新增两张表：

- 商圈表：标记点位属性（属于商场还是学校），为智能补货推荐提供数据基础，可给同商圈推荐卖得最好的商品；
- 区域表：精细化管理的概念，点位、人员都按区域归纳，区域内设备由这些人员管理维护。

已有表的变化：

| 表 | 变更 | 原因 |
| :--- | :--- | :--- |
| tb_channel（货道） | 新增 price | 同一商品在不同售货机价格可能不同，放商品表不合理 |
| tb_node（点位） | 新增 region_id、business_id、owner_id、owner_name | 点位归属区域、商圈、合作商（一对多），冗余名称便于查询 |
| tb_sku（商品） | 新增 brand_name | 按产品原型增加品牌字段 |
| tb_vending_machine（售货机） | 新增 business_id、region_id、owner_id、owner_name、longitudes、latitude | 冗余字段避免经点位表关联；经纬度支撑附近售货机搜索 |
| tb_vm_type（售货机类型） | 新增 model、image | 类型编码；图片地址链接 |

**工单库**——新增工单统计表存储统计数据；tb_task删掉执行时间列，改用XXL-job后在平台配置调度时间；工单表增加区域字段；工单详情表增加sku_id、sku_name。

**用户库**——新增合作商表tb_partner（点位主），合作商业务是全新的；tb_user增加mobile（接收登录验证码的手机号）、region_id/region_name（人员按区域归属）、image（用户头像）。

## 工程结构调整与环境准备

工程结构这次调整幅度很大。导入配套资料第2天的lkd_parent工程，它不是1.0的延续，而是按2.0需求调整过结构、完成部分基础功能的版本，后续开发就在它上面做业务。对比1.0，四个明显变化：

1. 所有微服务统一整理到一个文件夹（lkd_service）下，结构清晰；
2. 网关变成两个：通用网关之外，新增针对小程序的网关（lkd_gateway_microapp）；
3. 新增小程序工程lkd_microapp，包结构是典型的业务分层：business、config、dto、entity、excel、feignService、http、mybatis、redis、utils，resources下的viewmodel包放前端视图模型；
4. 新增service_common服务公共模块：放各微服务共用的DTO、配置类、公共实体类、mybatis和redis配置，以及前端传递对象所需的视图模型。

## 短信服务集成与验证码落地

### 集成spring-cloud-alicloud-sms

短信几乎是互联网应用的必备功能，最常见的是登录验证码，其次是短信通知。以前常用阿里云原生SDK自己写，能用但偏繁琐；这次用Spring Cloud Alibaba的短信组件，独立组件、主框架仍是Spring Cloud，写法更简洁，支持高并发和消息堆积。

集成四步走：

第一步，在要发短信的工程引入依赖：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-alicloud-sms</artifactId>
    <version>2.2.0.RELEASE</version>
</dependency>
```

第二步，加配置。必须配置阿里云密钥（access-key、secret-key，发短信按量扣费）；自定义配置是短信签名和模板编号——不配就只能硬编码，签名或模板号一变就得改代码重新编译，抽到配置里避免了硬编码：

```yaml
spring:
  cloud:
    alicloud:
      access-key: XXX
      secret-key: XXX
sms:
  operator:
    signName: 立可得
    templateCode: SMS_202816312
```

第三步，写配置类读取签名和模板编号：

```java
@Configuration
public class SmsConfig {
    @Value("${sms.operator.signName}")
    private String signName;
    @Value("${sms.operator.templateCode}")
    private String templateCode;

    public String getSignName() { return signName; }
    public String getTemplateCode() { return templateCode; }
}
```

第四步，写发送类SmsSender，对组件的ISmsService做一次上层封装：

```java
@Component
@Slf4j
public class SmsSender {
    @Autowired
    private SmsConfig smsConfig;
    @Autowired
    private ISmsService smsService;

    public void sendMsg(String telephone, String code) throws Exception {
        SendSmsRequest request = new SendSmsRequest();
        request.setPhoneNumbers(telephone);
        request.setSignName(smsConfig.getSignName());
        request.setTemplateCode(smsConfig.getTemplateCode());
        ObjectMapper mapper = new ObjectMapper();
        JsonNode rootNode = mapper.createObjectNode();
        rootNode.put("code", code);
        request.setTemplateParam(mapper.writeValueAsString(rootNode));
        smsService.sendSmsRequest(request);
    }
}
```

逻辑很直白：构造SendSmsRequest，设置手机号、签名、模板编号；模板动态参数是形如`{"code":"12345"}`的JSON字符串，用ObjectMapper把code塞进去再setTemplateParam；最后调smsService.sendSmsRequest(request)发送。业务里要发短信，注入SmsSender调sendMsg即可。因为涉及密钥，课堂不演示发送效果，自行在阿里云申请账号、开通服务、替换密钥即可测试。

### 发送验证码的业务逻辑

验证码发送落在用户微服务，UserService定义sendCode方法，入参手机号：

1. 非空校验：手机号是null或空串，往下走毫无意义；
2. 存在性校验：手机号必须是用户表里已存在的，否则发验证码没有意义。用LambdaQueryWrapper封装手机号查询条件，count小于等于0直接return；
3. 防重复发送：先查缓存，该手机号对应的验证码还在就return——验证码五分钟过期，五分钟内不允许重复发送；
4. 生成并发送：生成五位验证码后存入Redis（手机号为key，五分钟过期），再调SmsSender发送。

生成五位验证码用的是Stream写法：StringBuilder做容器，`generate`产生无限流，`nextInt(10)`随机出0-9个位数，`limit(5)`截取前五个，`forEach`逐个append拼成验证码。UserController提供"登录手机验证码"接口，直接调userService.sendCode即可。测试因密钥问题不在课堂演示，用自己的手机简单测试即可。

## 小结

这一篇完成了立可得2.0从需求到基建的铺垫：合作商后台补上收益查询与对账导出，运营运维APP把工单流转搬到线上并为附近售货机积累坐标数据，用户小程序以微信生态替代H5解决留存与导流。技术上，数据访问统一收敛到MyBatis-Plus（二级缓存、逻辑删除、公共字段填充、分表），EMQ同时接管设备消息和微服务内部异步通信，ES+logstash+geo撑起订单检索与附近售货机，XXL-job接手分布式调度，MinIO替换OSS省成本。库表按三库增量调整，工程上多出小程序服务、双网关和service_common公共层。短信服务四步集成，验证码走"非空→存在性→防重→生成入Redis→发送"链路，五分钟过期兜底。下一篇进入多端登录与网关鉴权。
