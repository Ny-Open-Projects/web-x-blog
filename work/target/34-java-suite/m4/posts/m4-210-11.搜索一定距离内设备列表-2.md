# 亿可控距离搜索收尾与数据透传：按距离排序、设备详情聚合、四类透传与报警前端推送

上一篇把 GPS 采集入库和 geo_distance 距离搜索的基础做完了。这一篇先收尾位置搜索：给搜索结果加"按距离排序"，再把坐标、在线状态、告警状态、最新指标聚合成完整设备信息，用 Controller 暴露给前端画地图。然后进入本章第三小节"数据透传"——亿可控的定位是物联网数据中台，只负责把解析好的数据递给外部业务系统，指标、告警、断连、GPS 四类数据各有各的传法。最后是第四小节"报警与离线的前端推送"：首页异常设备列表要实时更新，靠的不是轮询，而是后端把告警发到 EMQ、前端用 MQTT.js 订阅同主题实时接收。

## 先给结论

- 按距离排序用 `GeoDistanceSortBuilder`：指定 location 字段和圆心坐标，单位公里，`SortOrder.ASC` 即由近到远；距离算法 PLAN 快但精度欠缺、ARC 精度高但稍慢，一般选 ARC。
- 前端要的不只是坐标：`getDeviceFullInfo` 以 ES 范围查询打底，循环补齐在线/告警状态（按设备 ID 查 ES 设备文档，查不到视为离线）和最新指标（查 InfluxDB），再用 `GET /gps/deviceList/{lat}/{lon}/{distance}` 暴露。
- 透传就是把数据 POST 给外部系统预留的 URL；发送统一走 `HttpUtil`——新线程里发 RestTemplate 请求，调用方不等返回，不阻塞主流程。
- 指标透传判 webhook 非空直接 POST；告警透传多一层 Redis 沉默周期——key 是"前缀_设备ID_告警名称"，取不到（没发过或已过期）才发，发完写缓存并按沉默周期设过期时间。
- 断连与 GPS 的 webhook 在产品原型里没有配置入口，只能放进配置中心：`webhook.online`、`webhook.gps` 由 `WebHookConfig` 读取；断连不论联网、断网都要通知，否则业务系统会一直认为设备离线。
- 报警前端推送不走轮询：后端把 `AlarmMsg` 发到 EMQ 约定主题 `/device/alarm`，前端 MQTT.js 通过 WebSocket 订阅同一主题，收到即追加进列表。

## 一、距离搜索收尾：按距离排序与设备详情聚合

上一版 `searchDeviceLocation` 返回的结果没有排序。地图场景通常希望按"离圆心由近到远"排列，这要在 query 之后追加一个排序构建器：

```java
GeoDistanceSortBuilder distanceSortBuilder =
        new GeoDistanceSortBuilder("location", lat, lon);   // 排序字段 + 圆心
distanceSortBuilder.unit(DistanceUnit.KILOMETERS);          // 单位：公里
distanceSortBuilder.order(SortOrder.ASC);                   // ASC 由近到远
distanceSortBuilder.geoDistance(GeoDistance.ARC);           // 距离算法
searchSourceBuilder.sort(distanceSortBuilder);
```

`GeoDistanceSortBuilder` 的三个构造参数分别是排序字段、纬度、经度；order 指定升序还是降序，ASC 就是距离升序，即由近到远。ES 提供两种距离算法：PLAN 计算非常快但精度有所欠缺，ARC 精度高但计算稍慢，对精度有要求就选 ARC。排序器最后通过 `sort()` 装进 `SearchSourceBuilder`。

单元测试跑（40.722, -73.989, 半径 10 公里）：ASC 时第一条是 100002——它就是圆心自身，自然最近，第二条是 100003；把 order 改成 DESC 再跑，100003 跑到了最前面，顺序整体颠倒，排序生效。日常场景由近到远更常见，最终改回 ASC。

排序只是搜索的一半，前端真正要调的是"按坐标与范围查询设备详情"。看需求：地图上的点有颜色区分，灰色离线、绿色正常、红色告警，所以在线状态和告警状态要一起返回；鼠标停在设备上还要弹出最新的指标信息。现有的 DTO 都装不下这么多内容，新建 `DeviceFullInfo`：

```java
@Data
public class DeviceFullInfo implements Serializable {
    private String deviceId;             // 设备编号
    private String location;             // 位置
    private Boolean online;              // 在线状态
    private Boolean alarm;               // 告警状态
    private List<QuotaInfo> quotaList;   // 最新指标列表
}
```

在 `GpsService` 里定义 `List<DeviceFullInfo> getDeviceFullInfo(Double lat, Double lon, Integer distance)`——一个圆心加一个半径就划定了范围。实现分两步：

```java
@Override
public List<DeviceFullInfo> getDeviceFullInfo(Double lat, Double lon, Integer distance) {
    // 第一步：按范围查询设备位置
    List<DeviceLocation> deviceLocationList =
            esRepository.searchDeviceLocation(lat, lon, distance);
    List<DeviceFullInfo> deviceFullInfoList = Lists.newArrayList();
    // 第二步：循环查询每台设备的详情
    deviceLocationList.forEach(deviceLocation -> {
        DeviceFullInfo fullInfo = new DeviceFullInfo();
        fullInfo.setDeviceId(deviceLocation.getDeviceId());
        fullInfo.setLocation(deviceLocation.getLocation());
        // 在线、告警状态：按设备ID查ES设备文档
        DeviceDTO deviceDTO = esRepository.searchDeviceById(deviceLocation.getDeviceId());
        if (deviceDTO == null) {
            // gps索引里有位置、设备文档却查不到，视为离线
            fullInfo.setOnline(false);
            fullInfo.setAlarm(false);
        } else {
            fullInfo.setOnline(deviceDTO.getOnline());
            fullInfo.setAlarm(deviceDTO.getAlarm());
        }
        // 最新指标：从InfluxDB查询
        fullInfo.setQuotaList(
                quotaService.getLastQuotaList(deviceLocation.getDeviceId()));
        deviceFullInfoList.add(fullInfo);
    });
    return deviceFullInfoList;
}
```

位置来自 gps 索引，状态来自设备文档，指标来自 InfluxDB，一次循环把三种数据源捏合成一个对象。这里有个细节：文档查不到时在线状态设 false、告警随意——前端展示时会先判断在线状态，离线直接画灰色点，轮不到告警的红色。

最后写 Controller。API 文档里"根据经纬度获取设备信息"的地址以 gps 开头、后跟 deviceList 和三个参数，所以方法放进 `GpsController`，路径大小写与文档完全一致：

```java
@GetMapping("/deviceList/{lat}/{lon}/{distance}")
public List<DeviceFullInfo> getDeviceFullInfo(@PathVariable Double lat,
                                              @PathVariable Double lon,
                                              @PathVariable Integer distance) {
    return gpsService.getDeviceFullInfo(lat, lon, distance);
}
```

测试：启动工程，用 VS Code 里准备好的接口测试脚本（参数与单元测试一致）请求，返回 401 说明 token 过期，先调登录接口拿到 token 填回去再测——返回列表里有 100002、100003 两台设备，位置、在线状态、告警状态和最新指标（指标名、指标值）全都在，接口完成。

## 二、数据透传：中台定位、四类数据与HttpUtil

透传，就是把数据或信息发送给外部业务系统的某个 URL，前提是对方系统开放了可访问的接口。为什么要有这个需求？得看亿可控的定位：物联网数据中台。既然是中台，就不掺和业务——设备告警之后要不要通知维修人员、发短信还是发邮件、要不要生成工单产生工作流，这些都是业务系统的事，亿可控不碰。它做的事到"解析报文、判断告警"为止，然后把数据递给业务系统，对方拿去怎么用与它无关。就像快递员把快件送到手上就走了，你用剪刀拆还是用手撕，他不管。各干各的，中台递数据，业务系统做业务。

需要透传的数据有四类：

| 透传类型 | 触发时机 | 目标地址 | 特殊逻辑 |
| --- | --- | --- | --- |
| 指标透传 | 每次解析出指标 | 指标配置里的 webhook | 判空后直接 POST |
| 告警透传 | 指标处于告警（alarm=1） | 指标配置里的告警 webhook | Redis 沉默周期内不重复发 |
| 断连状态透传 | 设备联网/断网状态变化 | 配置中心 `webhook.online` | 联网、断网都要通知 |
| GPS 透传 | 解析出定位数据 | 配置中心 `webhook.gps` | 判空后直接 POST |

告警的沉默周期要特别说一下：指标可能连续多次上报都在告警，而两次上报的间隔可能只有四五秒，不加限制就会每条都往外发。沉默周期设为 5 分钟——5 分钟内同一设备的同一告警不重复发送，过期了才再发一次，好比闹钟响过你按掉，5 分钟后它再响一次。

实现工具是 util 包下的 `HttpUtil`，核心是 Spring 提供的 `RestTemplate`，注意它开了一个新线程再发请求，调用方发完立即返回，不用等 HTTP 响应，不阻塞主流程：

```java
@Slf4j
public class HttpUtil {
    public static void httpPost(String url, Object msg) {
        if (Strings.isNullOrEmpty(url)) return;
        Thread t = new Thread(() -> {
            RestTemplate restTemplate = new RestTemplateBuilder()
                    .defaultHeader(HttpHeaders.CONTENT_TYPE, MediaType.APPLICATION_JSON_VALUE)
                    .build();
            try {
                restTemplate.postForObject(url, msg, String.class);
            } catch (Exception e) {
                log.error("post alarm msg error", e);
            }
        });
        t.start();
    }
}
```

## 三、四类透传逐一实现：NoticeService里的四个方法

所有透传集中在一个通知服务里，逻辑上更清晰。先建 `NoticeService` 接口，再在 impl 包下建 `NoticeServiceImpl`（`@Service` 注解），四个方法对应四类数据。

指标透传最简单。`quotaTransfer(List<QuotaDTO>)` 直接收一个 List——因为一条报文解析出来可能是多个指标，把循环封在服务里，外部调用就省事。循环里对每个指标做 webhook 非空判断，非空才 POST，webhook 是 null 或空串时发了也白发。

告警透传不新增方法，就在 `quotaTransfer` 的同一个循环里追加逻辑，前提有两个：`alarm` 等于 1（确实在告警）且告警 webhook 非空。沉默周期用 Redis 的过期时间实现：

```java
String key = SystemDefinition.CYCLE_KEY + "_" + quotaDTO.getDeviceId()
        + "_" + quotaDTO.getAlarmName();    // 前缀_设备ID_告警名称
if (redisTemplate.boundValueOps(key).get() == null) {
    // 取不到：要么没发过，要么已过沉默周期，才真正透传
    HttpUtil.httpPost(quotaDTO.getAlarmWebhook(), quotaDTO);
    // 发完写缓存，过期时间就是沉默周期，单位分钟
    redisTemplate.boundValueOps(key).set(quotaDTO.getStringValue(),
            quotaDTO.getCycle(), TimeUnit.MINUTES);
}
```

key 由三段拼成：`SystemDefinition.CYCLE_KEY`（common 包常量类，值是"亿可控.cycle"这样的前缀）、设备 ID、告警名称。值存什么都行——这套机制只用 key 判断缓存是否有效，value 并不重要。取不到才透传，透传完立刻写入并按 `cycle`（分钟）设置过期；只要缓存还在期内，同样的告警再来就被跳过，过期后逻辑重新放行。

断连状态透传：设备从联网变断网、或从断网变联网，都要通知业务系统。第一步在配置中心追加 webhook 配置——产品原型里没有专门的断网 webhook 配置入口，只能进配置文件：

```yaml
webhook:
  online: http://www.lkd.com/device/online   # 演示地址，假设存在
  gps: http://www.lkd.com/device/gps
```

第二步写配置类读取：

```java
@Configuration
@ConfigurationProperties("webhook")
@Data
public class WebHookConfig {
    private String online;   // 断连透传地址
    private String gps;      // GPS透传地址
}
```

第三步在 `NoticeService` 里加 `onlineTransfer(String deviceId, Boolean online)`，实现也简单——拼个 Map（device、online 两个键）POST 到 `webHookConfig.getOnline()` 即可。调用点在之前写过的 `DeviceController` 那个接收 EMQ 断连事件的方法里：EMQ 检测到客户端连接或断开，会回调这个接口，方法里原本只按 action 更新 ES 里的在线状态，现在两个分支各加一行 `noticeService.onlineTransfer(deviceId, true)` 和 `onlineTransfer(deviceId, false)`。联网也要通知的原因很直接：只发断网通知的话，业务系统会始终认为设备是断的，哪怕它重新连上了也收不到消息。

GPS 透传：配置中心的 `webhook.gps` 已在上面加好，`WebHookConfig` 也补了 gps 属性，再加 `gpsTransfer(DeviceLocation)`——`DeviceLocation` 正好封装了设备 ID 和定位信息：

```java
@Override
public void gpsTransfer(DeviceLocation deviceLocation) {
    if (Strings.isNullOrEmpty(webHookConfig.getGps())) return;
    HttpUtil.httpPost(webHookConfig.getGps(), deviceLocation);
}
```

调用点在 `EmqMsgProcess` 解析 GPS 的分支里：`deviceLocation` 不为空时，除了 `esRepository.saveLocation` 入库，再调 `gpsTransfer` 透传出去。顺手把透传方法都按这个套路再严谨一遍——地址为空就 return，包括断连那次也一样，地址取不到时 POST 毫无意义。

## 四、报警与离线的前端推送：EMQ当消息总线

最后一个需求：亿可控首页要一个"异常设备列表"，包含报警时间、报警名称、等级、报警设备和数据。按常规做法是前端定时请求查询接口，但产品要求列表实时显示最新报警。定时刷新每秒请求一次，后端每秒都要做一次查询，服务端压力太大，不是好办法。换方向：后端先知道告警，那就由后端把告警推给前端——检测到告警后通过 MQTT 发到 EMQ 的一个约定主题，前端用 WebSocket 连 EMQ 订阅这个主题，收到消息就追加到列表。EMQ 本身就是消息中间件，它的 Dashboard 里那个 WebSocket 调试页，用的正是这套机制，现在只是自己做一个。

```mermaid
flowchart LR
    A[后端监测到告警] -->|publish /device/alarm| B[EMQ]
    B -->|MQTT over WebSocket| C[前端 MQTT.js]
    C --> D[追加到异常设备列表]
```

前端侧引入 MQTT.js，核心代码是连接、订阅、收消息三段：

```javascript
var client = mqtt.connect('ws://192.168.200.128/mqtt', {
  port: 8083,                                          // WebSocket端口
  clientId: 'webclient' + Math.floor(Math.random() * 1000),
  username: 'admin',
  password: '123456',
  clean: true
});

client.on('connect', function () {
  console.log('连接成功');
  client.subscribe('/device/alarm', { qos: 1 }, (error) => {
    if (error) {
      console.log('订阅失败', error);
    } else {
      console.log('订阅成功');                          // 前后端约定的告警主题
    }
  });
});

client.on('message', (topic, message) => {
  console.log('收到来自', topic, '的消息', message.toString());
});

client.on('reconnect', (error) => console.log('正在重连：', error));
client.on('error', (error) => console.log('连接失败：', error));
```

连接地址是 ws 协议加 EMQ 的 IP，端口 8083；clientId 用 `webclient` 开头加随机数，避免冲突；用户名密码必须有，连接要鉴权。connect 事件里订阅 `/device/alarm`——前后端约定的共同主题；message 事件把 topic 和消息内容打出来；断开重连、连接异常各有提示。测试很简单：资料文件夹里有现成的 mqttdemo 页面，浏览器按 F12 打开控制台，看到"连接成功、订阅成功"；再到 EMQ 的 WebSocket 工具连接后向 `/device/alarm` 发一条消息，页面控制台立刻收到——前端这条通路是通的。

后端这边，第一步定义告警消息 DTO `AlarmMsg`（`@Data` 加实现序列化接口）：deviceId、告警名称、指标名称、stringValue（文本指标值）、value（数值指标值）、level（告警级别）、online（联网状态——离线告警也走这条消息）、alarm（是否告警）。

第二步在 `NoticeServiceImpl` 里加私有方法 `sendAlarm(QuotaDTO)`，参数选 QuotaDTO 是因为调用点就在 `quotaTransfer` 的循环里，顺手做转换：

```java
private void sendAlarm(QuotaDTO quotaDTO) {
    if (!"1".equals(quotaDTO.getAlarm())) {
        return;                              // 不是告警，不推
    }
    AlarmMsg alarmMsg = new AlarmMsg();
    BeanUtils.copyProperties(quotaDTO, alarmMsg);
    // 告警级别在QuotaDTO里是String，转Integer
    alarmMsg.setLevel(Integer.valueOf(quotaDTO.getLevel()));
    alarmMsg.setOnline(true);                // 能产生告警，设备必然在线
    // 发到前后端约定的主题，与前端订阅一致
    emqClient.publish("/device/alarm", JsonUtil.serialize(alarmMsg));
}
```

先判断 alarm 是否等于 1，不是告警直接 return；告警则 new 一个 AlarmMsg，`BeanUtils.copyProperties` 批量拷贝属性，两处特殊处理：告警级别在 QuotaDTO 里是 String，要转成 Integer 再 set；online 在 QuotaDTO 里没有，既然是告警必然在线，直接 true。最后用 `emqClient.publish` 把序列化后的消息发到 `/device/alarm`——前端订阅的就是这个主题，主题两边必须一致。调用就一行：在 `quotaTransfer` 的循环里对每个 `quotaDTO` 调一次 `sendAlarm`，前端推送就挂在原有透传逻辑上了。

验证：打开 mqttdemo 页面订阅告警主题，启动工程——工程会随机产生虚拟报文，其中必有告警数据；一旦发生告警就触发前端推送。等一小会儿，页面控制台陆续收到多条消息，内容正是"温度过高"这类告警，后端到前端的推送链路验证完成。

## 小结

这一篇把第五章的搜索与透传都收了尾。搜索侧：`GeoDistanceSortBuilder` 给距离查询加上按远近排序（PLAN 快、ARC 准，一般选 ARC），`getDeviceFullInfo` 一次循环聚合 gps 索引的位置、设备文档的在线/告警状态、InfluxDB 的最新指标，Controller 按 `/gps/deviceList/{lat}/{lon}/{distance}` 暴露。透传侧：亿可控守住数据中台的边界，只递数据不做业务；`HttpUtil` 用新线程发 RestTemplate 请求保证不阻塞，四类数据四种传法——指标判空直发、告警叠加 Redis 沉默周期（key 拼前缀_设备ID_告警名称，过期时间即沉默周期）、断连联网断网都通知、GPS 解析成功即透传，断连和 GPS 的地址因原型缺失进了配置中心。推送侧：告警不再靠前端轮询，后端把 AlarmMsg 发到 EMQ 的 `/device/alarm`，前端 MQTT.js 走 WebSocket 订阅同主题实时接收。至此，设备的任何风吹草动——指标、告警、断连、位移——都能同时送达三个方向：ES/InfluxDB 存起来、业务系统 webhook 传出去、前端页面实时亮出来。
