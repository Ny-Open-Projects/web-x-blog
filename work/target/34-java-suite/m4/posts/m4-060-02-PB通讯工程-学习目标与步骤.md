# PB 通讯工程：grpc/Netty 双下单接口 proto 定义、编译流水线与交易服务搭建

进入智牛股的下单服务章节，动工前先把通讯层的地基打好：交易、行情、代理服务都会用到 Protobuf 通讯数据结构，所以先搭一个公用的 PB 数据工程，以简易下单接口为例把 grpc 和 Netty 两条 proto 线定义出来，再封装好编译脚本；然后搭建交易服务，实现下单的 gRPC 接口，并在代理服务侧完成 gRPC 调用。这一篇是整个下单链路的第一段工程。

## 先给结论

- 通讯方案分两条线：内部微服务之间用 gRPC（代理服务调交易服务），对外客户端用 Netty 长连接，数据载体统一是 Protobuf；整体集成是 Spring Boot 2.X + gRPC + Netty + WebSocket + PB。
- 公用 PB 数据工程 `stock-struct-proto` 独立存在，proto 脚本统一放 `resources/proto` 下，按 `grpc` 和 `netty` 两个目录区分内部与外部通讯结构。
- grpc 线定义 `StockTradeDealService.proto`（service + rpc placeOrder + 请求/响应消息体）；netty 线定义 `StockHead.proto`（包头）和 `StockMessage.proto`（完整包，`oneof` 区分不同接口的数据体）。
- 新版 protoc 不支持通配符、只能逐个编译，所以把编译命令封装成 `proto_grpc.bat` / `proto_netty.bat` 两个批处理脚本，一次跑完目录下所有 proto 文件。
- 交易服务 `bulls-stock-deal` 搭建完毕：Nacos 注册、RocketMQ 消费端（订阅 stock-quote，group 为 stock-deal）、双数据源、MyBatis 数据层、gRPC 服务端端口配置。
- 下单链路打通：`GrpcStockDealService` 落库订单并返回订单 ID；代理服务用工厂模式封装处理器，`@GrpcClient` 注入 BlockingStub 阻塞调用后拼装 PB 响应报文写回客户端。

## 公用 PB 数据工程：一次定义，三端复用

PB 公用通讯数据结构是整个交易平台的基础工程——交易服务、行情服务、代理服务都要用到；又因为内部服务通讯和外部数据交互会频繁调整，为了便于使用和维护，必须做成独立工程而不是散落在各服务里。

新建模块 `stock-struct-proto`（挂在 `com.itcast.trade.bulls-stock` 父工程下），再补上 protobuf 与 gRPC 相关依赖：protobuf-java 用 3.8.0；gRPC 通讯层基于 Netty 实现；grpc-stub 封装 gRPC 通讯涉及的相关接口，版本 1.22.1。要注意 gRPC 相关依赖需要排除它自带的 protobuf 组件，避免版本冲突：

```xml
<!-- Protobuf 插件 -->
<dependency>
    <groupId>com.google.protobuf</groupId>
    <artifactId>protobuf-java</artifactId>
    <version>3.8.0</version>
</dependency>

<!-- gRPC 通讯层，基于 Netty 实现 -->
<dependency>
    <groupId>io.grpc</groupId>
    <artifactId>grpc-netty-shaded</artifactId>
    <version>1.22.1</version>
</dependency>

<!-- gRPC proto 插件，排除自带的 protobuf，避免冲突 -->
<dependency>
    <groupId>io.grpc</groupId>
    <artifactId>grpc-stub</artifactId>
    <version>1.22.1</version>
</dependency>
```

proto 脚本统一存放在 `resources/proto` 目录，脚本分两部分：内部微服务 gRPC 通讯一份，外部客户端 Netty 长连接通讯一份，目录也随之分开：

```text
resources/proto
├── grpc
│   └── StockTradeDealService.proto   # 内部微服务 gRPC：交易下单接口
└── netty
    ├── StockHead.proto               # 包头：协议版本 / 请求类型 / 消息编号 / 状态
    └── StockMessage.proto            # 完整包：head + oneof 业务数据体
```

## 两条 proto 线：grpc 接口与 Netty 包结构

### grpc 线：下单服务接口定义

先定义内部服务（代理服务发起调用至交易服务）的 gRPC 通讯脚本 `StockTradeDealService.proto`。头部配置指定 proto3 编译版本；`java_multiple_files` 设为 true 表示可生成多个 Java 文件；再指定生成的包路径与类名（类名与脚本名保持一致，加 Proto 后缀标识这是 proto 生成的代码）：

```protobuf
syntax = "proto3";

option java_multiple_files = true;
option java_package = "com.itcast.bulls.stock.struct.grpc.trade";
option java_outer_classname = "StockTradeDealServiceProto";

// 交易服务的业务接口
service StockTradeDealService {
    rpc placeOrder (PlaceOrderRequest) returns (PlaceOrderResponse) {
    }
}
```

接着定义请求消息体 `PlaceOrderRequest`。注意 message 要定义在 service 外面，不要嵌套在 service 内部：

```protobuf
// 下单的请求对象
message PlaceOrderRequest {
    // 股票产品ID
    int64 stockId = 1;
    // 股票的买卖方向（0:买入，1:卖出）
    int32 direction = 2;
    // 委托类型（0:市价单，1:限价单）
    int32 type = 3;
    // 请求数量/挂单数量
    int32 execVolume = 4;
    // 请求价格/挂单/委托价格
    int64 execPrice = 5;
}

// 下单的返回对象
message PlaceOrderResponse {
    // 状态，处理结果的状态
    int32 status = 1;
    // 处理结果的提示消息
    string message = 2;
    // 订单的ID
    int64 dealId = 3;
    // 成交的数量
    int32 execVolume = 4;
    // 成交的价格
    int64 execPrice = 5;
}
```

这里藏着 PB 语法最核心的规则：等号后面的数字不是取值，而是**序号**，要保持有序连续、不重复不跳号，它用于数据的序列化与反序列化。对应到维护上：扩展新属性后要重新编译生成代码，否则新属性读不到；调整了序号则 PB 代码必须重新生成。

### netty 线：包头与完整包结构

外部通讯的 PB 数据结构以 Netty 包形式定义。先建 `StockHead.proto` 定义头部消息体，四个字段各司其职：协议版本（枚举 ProtocolVersion，定义了版本一、版本二，后续按业务扩展）、请求接口类型（枚举 RequestType，目前只实现了用户下单这一种）、消息编号（长整型，用于定位和追踪消息）、处理状态（标识整个接口的处理结果）：

```protobuf
message StockHead {
    // 协议版本
    ProtocolVersion protocolVersion = 1;
    // 请求接口类型
    RequestType requestType = 2;
    // 消息编号，用于定位和追踪
    int64 sequenceId = 3;
    // 处理状态
    ProcessStatus status = 4;
}
```

再建 `StockMessage.proto` 定义数据消息体：头部配置复制过来调整，`import` 导入 StockHead，加上允许生成多个 Java 文件的配置项。它才是一个完整的包——上面是 head，下面类似 body。

与 HTTP 有个明显差异：HTTP 传的是字符串，可以塞各种数据消息再经 JSON 转成具体对象；PB 必须是一个明确的对象，所有传输数据要预先定义好。后续接口众多、每个接口有自己的数据体，怎么在一个包里装下？答案是 `oneof`——它表示同时只传递其中一个消息数据类型：设了下单数据体就不能设获取用户资料的数据体，反之亦然，由此实现不同接口的数据消息传递：

```protobuf
message StockMessage {
    // 包头
    StockHead stockHead = 1;

    // 业务数据体，一次只能设置其中一个
    oneof stockData {
        // 下单传输的消息结构体
        PlaceOrderData placeOrderData = 2;
        // 获取用户资料的消息结构体（示例扩展）
        GetUserData getUserData = 3;
    }
}
```

响应报文同样定义外层完整消息体：头部公用 StockHead，扩展一个返回提示消息；业务数据体继续用 `oneof` 区分，目前定义了下单响应数据体 `PlaceOrderResp`（序号 3），下单返回数据包暂时只返回订单 ID。

## 编译流水线：从 protoc 命令到脚本封装

### 手动编译命令

编译前先下载 protoc 工具和 protoc-gen-grpc-java 插件（生成 gRPC 接口代码必需），protoc 加入环境变量，没加就要写完整路径（演示环境在 `d:/TestCode/`）。在 `resources/proto` 目录 Open in Terminal，执行 gRPC 编译命令：

```bash
protoc --proto_path=./grpc \
  --plugin=protoc-gen-grpc-java=d:/TestCode/protoc-grpc.exe \
  --grpc-java_out=../java \
  --java_out=../java \
  StockTradeDealService.proto
```

各参数含义：`--proto_path` 指定 proto 脚本的存放路径；`--plugin` 挂载 gRPC 插件——这是 gRPC 接口定义，必须靠它生成接口信息，配了 `--grpc-java_out` 才能把 gRPC 代码输出到指定目录（不配置默认生成在当前目录）；`--java_out` 是 message 数据消息体的生成路径。注意这里有两个输出路径：一条是 gRPC 接口，一条是数据消息体，都指向 Java 目录。

还有一个坑：`--proto_path` 指定了目录也不会批量生成——proto3 系列的 protoc 只能逐个生成，命令最后必须指定 proto 文件的具体名称。执行无报错即成功，刷新后 PlaceOrderRequest、PlaceOrderResponse 及 gRPC 接口代码与脚本定义一致。

Netty 侧的命令简化很多，因为不生成 gRPC 接口代码，不需要配置插件信息，`StockHead.proto` 和 `StockMessage.proto` 逐个执行：

```bash
protoc.exe --proto_path=./netty --java_out=../java ./netty/StockHead.proto
protoc.exe --proto_path=./netty --java_out=../java ./netty/StockMessage.proto
```

### 封装成脚本批量编译

手动敲命令的问题很明显：指令长，不同脚本的编译命令还不一样；新版 Protobuf 不支持通配符、不能同时编译多个文件，几十个脚本就要执行几十次。解法是把编译指令封装成自定义脚本，也便于数据结构维护——调整或扩展属性后重跑脚本即可。在 proto 目录下创建两个脚本：

```bat
@echo off
for %%i in (grpc/*.proto) do (
    d:/TestCode/protoc.exe --plugin=protoc-gen-grpc-java=d:/TestCode/protoc-grpc.exe --grpc-java_out=../java ../grpc/%%i
    echo generate %%i to java file successfully!
)
```

```bat
@echo off
for %%i in (netty/*.proto) do (
    d:/TestCode/protoc.exe --proto_path=./netty --java_out=../java ../netty/%%i
    echo generate %%i to java file successfully!
)
```

两个脚本都是遍历循环，分别处理各自目录下的所有脚本：grpc 侧带 gRPC 插件，netty 侧走普通编译路径；`%%i` 是遍历到的文件名，生成后输出提示。

测试时把之前生成的代码全部删掉，分别执行两个脚本，刷新后 StockTradeDealService、StockHead、StockMessage 的 Java 代码全部重新生成，与手动命令效果一致。此后不管有多少个 proto 脚本，执行一次对应脚本即可。

## 交易服务搭建与简易下单接口

### 交易服务工程与配置

新建模块 `bulls-stock-deal` 作为交易服务，依赖包含 Spring Boot、Nacos 注册发现、公用数据层工具、实体、RocketMQ 消息组件（groupId 调整为 `com.alibaba.cloud`，否则无法导入）、基于 Lettuce 的 Redis 缓存自动配置，以及公用 PB 数据工程依赖。包结构按规范划分：configure 配置目录、dao 数据层接口、service 层接口、startup 启动包。

工程配置要点：POM 加入多环境 profiles，resources 放多环境配置文件与日志文件。配置文件里 RocketMQ 作为消费端，订阅 `stock-quote` 主题，分组调整为 `stock-deal`（多节点用不同序号）；交易服务同样采用双数据源（交易数据源 + 业务数据源）；保留 Redis 缓存配置；Spring Session 可去除——交易服务没有 Controller 层的对外 HTTP 接口，用不到 Session；数据层主要用 MyBatis 实现，mapper 扫描路径要指向 dao 层所在包、配置正确；最后是 gRPC 服务端配置，交易服务要对外提供基于 gRPC 的交易接口，服务端配置很简单，只需设定对应的服务端口。启动类 `StockDealApplication` 加 `@SpringBootApplication`、`@EnableDiscoveryClient`、`@ComponentScan`（指向基础包 com.itcast）与数据层接口的 Mapper 扫描注解。

### 实体、数据层与 gRPC 接口实现

先建交易实体：`TradeDeal` 成交记录、`TradeOrder` 交易订单，都用 Swagger `@Api` 文档注解、JPA `@Entity` 实体映射（`@Table` 关联具体表）和 Lombok `@Data`。交易订单与成交记录是一对多关系——订单记整体概要信息，成交记录含交易订单号、券商 ID（成交记录与券商多对一）、交易账号、股票与成交明细等信息。

数据层按双数据源分两个包：业务数据源与交易数据源。成交记录接口提供保存方法，订单接口提供保存与按 ID 查询两个方法，均加 `@Repository` 注解，用 MyBatis 实现并配套 mapper XML——mapper 必须带上规范的文件头信息（从 User 服务的 mapper 复制），否则无法正常识别；文件里定义属性映射与 insert、按 ID 查询的具体语句。

接着引入 gRPC 服务端依赖组件，实现下单接口。类名以 Grpc 开头，继承 proto 生成的实现基类并重写 `placeOrder`——正是公用 PB 工程定义的 rpc 接口：

```java
@GrpcService
public class GrpcStockDealService extends StockTradeDealServiceImplBase {

    @Autowired
    private ITradeOrderDao tradeOrderDao;

    @Override
    public void placeOrder(PlaceOrderRequest request,
            StreamObserver<PlaceOrderResponse> responseObserver) {
        // 封装订单信息
        TradeOrder order = new TradeOrder();
        order.setStockId(request.getStockId());
        order.setAccountId(request.getAccountId()); // 登录接口未实现，账户ID先随意填写
        order.setExecPrice(request.getExecPrice());
        order.setExecVolume(request.getExecVolume());
        order.setType(request.getType());
        order.setStatus(GlobalConstants.INT_ENABLE); // 不写硬编码，用常量标识有效状态

        // 保存订单数据
        tradeOrderDao.insert(order);

        // 封装返回信息并输出给调用方
        PlaceOrderResponse response = PlaceOrderResponse.newBuilder()
                .setStatus(GlobalConstants.STATUS_OK)
                .setMessage("订单保存成功！")
                .setDealId(order.getId())
                .build();
        responseObserver.onNext(response);
        responseObserver.onCompleted();
    }
}
```

两个细节：状态等字段不写硬编码，用常量类标识；类上 `@GrpcService` 必须加，才会被扫描为 gRPC 接口、纳入服务管理，否则接口不生效，客户端无法调用。整个交互范式固定：request 取参、处理业务、封装 PB 对象、responseObserver 输出，最后 `onCompleted` 标记完成。

### 代理服务调用端：处理器 + 工厂模式

代理服务作为 gRPC 调用方，添加自研的 gRPC 依赖组件 `bulks-stock-starter-grpc`（内部封装了 gRPC 自动化配置），加依赖即可使用。然后新建处理器（Processor）：类似接入层 Controller 但不等同，介于 Controller 和 Service 层之间——处理请求参数、调用业务层接口、返回报文，不负责业务逻辑细节，负责整个流程的编排。

代理服务要调用内部多个微服务，请求进来如何识别、后续如何扩展新接口？这里引入工厂方法：抽象公用处理器接口，由工厂统一负责不同接口的调用、获取指定处理器。扩充新接口时不必修改调用端、不改动其他处理器，只加新处理器并在工厂封装一层，符合开闭原则。

```mermaid
flowchart LR
    C[外部客户端] -- Netty 长连接<br/>PB 报文 --> P[代理服务<br/>StockDealProcessor]
    P -- gRPC placeOrder<br/>BlockingStub 阻塞调用 --> D[交易服务<br/>GrpcStockDealService]
    D -- MyBatis insert --> DB[(交易数据源)]
    D -- PlaceOrderResponse --> P
    P -- ResponseMessage 报文 --> C
```

代码分三层落地：

```java
// 处理器接口：定义处理客户端请求的公用方法
public interface IBaseStockProcessor {
    void processRequest(ChannelHandlerContext channelHandlerContext, StockMessage stockMessage);
}

// 抽象处理器：封装各处理器的公用逻辑（统一头部返回、获取用户信息等）
public abstract class AbstractStockProcessor implements IBaseStockProcessor {

    // 生成返回的头部信息：每个接口都必须返回头部，统一封装
    protected StockHead generateStockHead(StockHead stockHead, ProcessStatus status) {
        return StockHead.newBuilder()
                .setRequestType(stockHead.getRequestType())
                .setSequenceId(stockHead.getSequenceId())
                .setStatus(status)
                .build();
    }
}
```

具体处理器继承抽象类并实现接口，注入 gRPC 客户端完成下单调用：

```java
public class StockDealProcessor extends AbstractStockProcessor {

    @GrpcClient("grpc-trade-server")
    private StockTradeDealServiceGrpc.StockTradeDealServiceBlockingStub stockTradeDealServiceBlockingStub;

    @Override
    public void processRequest(ChannelHandlerContext channelHandlerContext, StockMessage stockMessage) {
        // 从完整包中取出下单数据体，构造 gRPC 请求
        PlaceOrderData orderData = stockMessage.getPlaceOrderData();
        PlaceOrderRequest request = PlaceOrderRequest.newBuilder()
                .setDirection(orderData.getDirection())
                .setExecPrice(orderData.getExecPrice())
                .setStockId(orderData.getStockId())
                .setType(orderData.getType())
                .setExecVolume(orderData.getExecVolume())
                .build();

        // 阻塞方式调用 gRPC 服务端的下单接口（另有回调、异步方式可选）
        final PlaceOrderResponse response = stockTradeDealServiceBlockingStub.placeOrder(request);
        log.info("Process in StockDealProcessor.processRequest method. receive: " + response);

        // 生成包头 + 下单返回包体，组装响应报文写回客户端
        StockHead stockHead = generateStockHead(stockMessage.getStockHead(), GlobalConstants.STATUS_OK);
        PlaceOrderResp orderResp = PlaceOrderResp.newBuilder().setDealId(response.getDealId()).build();
        ResponseMessage responseMessage = ResponseMessage.newBuilder()
                .setStockHead(stockHead)
                .setPlaceOrderResp(orderResp)
                .build();
        channelHandlerContext.writeAndFlush(responseMessage);
    }
}
```

`@GrpcClient("grpc-trade-server")` 声明这是一个 gRPC 客户端，名称对应配置文件里的客户端配置（调用哪个服务、连接信息都在那里维护）；调用方式用阻塞式 BlockingStub，另有回调、异步可选。处理器从 `StockMessage` 取出 `PlaceOrderData` 构造请求，调用后用 `generateStockHead` 生成包头（请求类型、消息编号原样带回，状态置为处理成功），订单 ID 装进 `PlaceOrderResp`，连同头部组装成 `ResponseMessage`，经 Netty `writeAndFlush` 写回客户端——代理调用交易下单的完整链路就此打通。

## 小结

- 通讯两条线：内部微服务走 gRPC，外部客户端走 Netty + WebSocket 长连接，数据载体统一 Protobuf。
- 公用 PB 数据工程 `stock-struct-proto` 独立建库，protobuf-java 3.8.0 + grpc 1.22.1（排除自带 protobuf 防冲突），proto 脚本按 `grpc`/`netty` 两个目录组织。
- grpc 线定义 `StockTradeDealService` 下单接口与请求/响应消息体；netty 线定义 `StockHead` 包头与 `StockMessage` 完整包，`oneof` 区分不同接口数据体——PB 必须是明确对象，传输数据预先定义。
- PB 字段等号后是序号不是值：保持有序连续，新增属性要重新编译，调序号必须重新生成代码。
- 新版 protoc 不支持通配符、只能逐个编译，封装成 `proto_grpc.bat`/`proto_netty.bat` 后一次执行即可完成全量编译，也便于数据结构维护。
- 交易服务 `bulls-stock-deal` 完成 Nacos、RocketMQ 消费端（group: stock-deal）、双数据源、MyBatis、gRPC 服务端端口配置；`GrpcStockDealService` 加 `@GrpcService` 重写 `placeOrder`，落库后返回订单 ID。
