# 立可得 2.0 升级全景：六大子系统与逐域需求对比分析

第一章把 1.0 的功能和 API 设计走了一遍，第二章回到需求侧：立可得为什么升级 2.0，升级后的平台长什么样，每个域相对 1.0 新增、升级了什么。这些结论直接决定后面章节的开发内容。

## 先给结论

- 升级的根因是业务级增长：设备从几十台涨到几千台、运营区域向其他城市扩张、点位和合作商持续增加，1.0 撑不住了。
- 2.0 把系统宏观切分成六块：运营管理后台、合作商后台、运营管理 APP、运维管理 APP、用户小程序、设备端；两个 APP 开发上是同一个工程，只按登录界面区分。
- 合作模式从租赁制走向分成制，这是多个新功能的总源头：合作商后台、对账管理、合作商管理、分成比例都由此而来。
- 下单端从 H5 换成微信小程序，目的是拿到用户身份，之后可加电商入口，把线下 C 端流量导到线上，这正是新零售要做的事。
- 设备监控从原系统剥离，交给开源项目亿可控实现。
- 运营管理后台升级六大模块：点位、设备、人员、对账、统计分析（工作台）、工单；商品小改，策略订单基本没动；工单拆成运营与运维两类，补货与维修支持自动创建。

## 背景：从几十台到几千台，系统切六块

立可得创业初期只有几十台售货机，合作商家数得过来，点位也不多，1.0 完全够用。之后设备发展到几千台，运营区域向其他城市扩张，点位与合作商不断增加，业务级增长让原系统无法满足日常经营管理需要，公司决定做大版本升级。

宏观上，这次升级是对系统进行切分，一共六块：

1. **运营管理后台**：供管理人员使用，2.0 功能比 1.0 丰富、细化得多。
2. **合作商后台**：也叫点位主后台，点位主就是点位的主人，机器放到商场，商场就是点位主。
3. **运营管理 APP**：给运营人员用，核心工作是补货，会产生补货工单。
4. **运维管理 APP**：给运维人员用，三件事：投放、维修、撤机。
5. **用户小程序**：替代 1.0 的 H5。
6. **设备端**：封装售货机逻辑。

两个 APP 核心任务都是处理工单；业务上是两个，开发上是同一个工程，功能大多类似，只在登录界面区分。

合作商后台来自合作方式的变化。1.0 大多是租赁制：机器摆在合作商场地，付租金，线下交易即可，无需后台管理。规模扩张后立可得占据主动权，商家主动上门，合作变成分成制：地方给你用，不收租金，卖得多分得多。合作商每月挣多少钱、数据怎么来的必须透明，所以这个后台说白了就是查数据的。

架构图上还有三处：左侧的外部系统（ERP、硬件监控平台、权限管理平台、HR 等）不属于这六块，说明平台可与它们对接；设备端没有界面，是纯内核逻辑，用户付款后由消息队列通知它完成发货；监控端 1.0 自带但比较弱，2.0 抽离出来交给开源项目亿可控，它专门监控物联网设备。

## 产品原型与设计稿：开发依据长什么样

产品原型托管在 Mockplus 上，左侧五个文件夹对应五个子系统，设备端没有界面不在其中。逐个看：

- **运营管理后台**：工作台、工单管理、点位管理、设备管理、人员管理、商品管理、策略管理、订单管理、对账管理等功能，差异放到下面逐域细看。
- **合作商后台**：比较简单。工作台做分账统计、收益统计和趋势分析；分账信息表四列：分账日期、分账点位、订单数、分账金额。通俗说，就是给合作商点位主查分账金额的。
- **运营/运维管理 APP**：核心作用是处理工单，接受、拒绝、执行完标记完成都在 APP 上进行。
- **用户小程序**：商品列表延续 H5 风格，商品详情与 H5 类似（如可口可乐 500ml、4.00 元）；订单管理可查所有支付过的订单；还有一个搜附近功能。

设计稿是 UI 设计师按产品原型设计的，最终要被前端一比一还原，看它等于提前看成品的样子，成品运行效果理论上应与设计稿完全一致。设计稿覆盖运维 APP、运营 APP、立可得小程序三个端。运维 APP 有首页、待办工单、接受工单、选择定位（地图）、历史工单、工单详情、搜索等页面，整个 APP 就是对工单的管理，运维人员有一部手机就能处理工单，无需电脑登录后台；运营 APP 类似，多了取消原因等页面。小程序端有扫码按钮（扫售货机二维码看在售商品）、商品列表（售空商品有特殊图标）、附近货机（可唤起手机里已装的腾讯、百度、高德地图找售货机）、确认付款（唤醒微信支付模块）。

精力应主要放在产品原型上：原型是开发的最主要依据，UI 设计稿只是前端效果的中间产物。

## 逐域需求对比：什么升级了，什么没动

需求对比分析就是把 2.0 和 1.0 逐域对比，讲清哪些功能升级、哪些新增、为什么。先给一张总览表：

| 功能域 | 1.0 现状 | 2.0 变化 |
| :--- | :--- | :--- |
| 点位 | 只有点位表，记录地址 | 新增区域分组、商圈属性、合作商管理 |
| 设备 | 有设备类型表，无管理界面 | 新增设备类型管理、智能排货 |
| 人员 | 人员与设备直接绑定 | 人员归属区域，新增人效统计 |
| 商品 | 有商品类型表，无管理界面 | 新增商品类型维护、品牌列 |
| 策略 | 策略名称 + 折扣比例 | 无变化 |
| 订单 | 查询订单、查看详情 | 几乎无变化 |
| 对账 | 无（租赁制不需要） | 新增对账统计，分成计算 |
| 工作台 | 无 | 新增综合统计分析 |
| 工单 | 运营运维混在一起 | 拆成运营工单与运维工单 |

### 点位与区域：一次新增三个概念

2.0 抽象出区域概念，本质是对点位分组：点位多了分布在城市每个角落、彼此距离远，按 1.0 的方式管理很不方便；划成区域后按区域做运营分组，有利于规模迅速扩张。

这里要特别注意：此区域非彼区域。1.0 的区域是已存在的行政区域（省、市、区县三级，可改名叫"地区"）；2.0 的区域是新增概念，指运营需要划分的区域，可以是一个区县、村或街道，也可以大到一个行政区甚至两个行政区的组合，粒度由运营需要决定。

区域管理就是增删改查：有区域名称，点位数实时统计；区域名可能只是代号，比如 A，所以配一个备注说明 A 包含哪些区。

点位新增商圈属性（商场、写字楼、学校等），描述这个地方的性质。有了它就能智能推荐：按历史数据统计每个商圈哪种商品卖得最好，比如学校商圈农夫山泉卖得最多；之后给同类商圈的点位布货、设商品时优先考虑，让营业额和利润最大化。

点位域还新增了合作商（点位主）增删改功能。合作商和点位一对多，一个老板可能同时拥有几个商场和一个公园；但合作商和区域没有直接关系，他的多个点位可以分布在不同区域。合作商管理可重置密码、设置分成比例：合作商点位上的售货机卖出一瓶农夫山泉，就按售价比例给他提利润。

区域还有一个隐藏作用：对人员分组。设备故障时通知点位所属区域的运维人员维修，区域内运维人员可能很多，就靠类似外卖派单的轮询算法智能派单；补货也一样自动分给区域内运营人员。

### 设备与人员：效率两条线

设备侧，1.0 有设备类型的表但没有管理界面，因为当时设备类型非常单一（基本是饮料机等几种），很少修改。规模扩大后类型越来越丰富，再要改只能去数据库就很麻烦，2.0 于是加了设备类型管理，实现上就是增删改查，新增时指定型号名称、型号编码、货道行列数、每个货道容量（容纳多少个商品）、图片等。另一个变化是智能排货：货道设置时点智能排货，系统按设备所属点位的商圈，统计同类商圈最近一段时间哪种商品卖得最好，自动推荐商品，采纳后自动完成货道设置，既是效率提升，也是利益最大化途径。

人员侧最大的变化是人员归属区域：设备故障自动派给区域内运维人员，缺货自动派给区域内运营人员，一个区域可有多名运维人员和多名运营人员。相比 1.0 人员与设备直接绑定、设备只能由指定的人管理，人效被解放出来。

人效统计非常有用：运营人员的工单总数、完成工单、拒绝工单数量及人数都有统计，运维人员同样有；人效排名对两类人员的工作量分别排名；工单状态按天统计完成、进行中、取消的数量变化；工作量列表细到每个人，详情除本月外还有本周、本年。人的效率和经营业绩挂钩后，还能与 HR 系统对接，提供工作量数据，计算浮动类工资。原型文档原话："人效统计、人效排名，正向激励制度让公司良性发展"。

### 工单：一拆为二，支持自动创建

2.0 对工单做了很大细化，最明显的是拆成运营工单和运维工单分别管理。表面看都是工单，但隶属于不同的业务，甚至不太相关。

运营工单主要是补货：售货机缺货时通知运营人员，骑着三轮车把矿泉水、饮料装进柜子。创建方式两种：手动工单由管理人员直接创建，弹窗里手动输入补货数量；自动工单由系统定时扫描所有售货机，发现缺货按缺货量自动创建，属于智能化运营方案。

运维工单也分手动、自动两种创建方式，类型有三种：投放、维修、撤机。只有维修可以自动创建：系统对接物联网设备，检测到设备故障后自动创建维修工单，并智能指派某运维人员维修；投放和撤机只能手动。

工单流转路径也清晰：创建（手动或自动）、指派运营/运维人员、工单出现在对方 APP 上、对方接受、执行、完成。原型里运营工单列表可按编号、类型、状态筛选，状态有进行中、已完成、取消，取消后可重新创建，变更会记录原因。

### 对账、工作台与商品策略订单

对账就是平台方与合作商进行分成计算的功能。1.0 也有合作商、点位主，但多是租赁制，线下交易即可，无需软件管理；换成利益分成后，系统必须提供每个合作商分成金额的计算功能。对账统计页面顶部是当日与当月的销售量、销售额、分成；按合作商和日期区间筛选后，下面列出该合作商每天的收入、对应点位机器产生的收入笔数和应得分成金额；查看明细能看到每笔订单的记录和交易时间。演示数据正好对上分成比例：订单金额 15 元、分成 1.5 元，即 10% 比例。

工作台的核心是统计分析，聚合五块内容：销售数据（销售额、销售量、用户数、分成）、工单数据（工单总量、完成工单、未完成工单、进行工单）、销售数据趋势（每天销售量、销售额变化，可切换本周、本月、本年）、商品销量榜（哪些商品卖得最好，之后重点经营）、用户访问量统计（每天用户访问的变化，找规律），外加异常设备监控，可查询故障时间、设备地址、设备编号。

商品管理变化不大：一是增加商品类型维护，1.0 有表但没有管理界面，2.0 商品类型更丰富、会频繁增删改查；二是商品多了品牌这一列。策略管理没变，还是策略名称加折扣比例；订单管理几乎没变，查询订单、查看详情。

## 小结

把这一章捋一遍，2.0 新增功能背后只有两个根因：规模扩张与分成合作。规模扩张催生了区域分组、区域派单、设备类型管理、人效统计；分成合作催生了合作商后台、合作商管理、对账统计、分成比例。商圈推荐、智能排货、自动建单，则是在新数据基础上长出来的智能化能力。接下来的章节，就是把这些需求逐域落到代码上。
