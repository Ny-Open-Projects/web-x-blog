# 售货机「五脏六腑」收官：补偿处理与补货业务

立可得项目的售货机端和服务端之间靠 EMQ 传消息，但链路和两端本身都不可靠：上报途中售货机当机、服务端异常或宕机、网络抖动导致链路不通畅，任何一种情况都会让服务端和售货机端的数据不一致。这一节处理两个收尾问题：一是补偿处理，把上报失败的数据重新发一遍；二是补货业务，响应服务端下发的补货通知、更新本地库存。做完这两件事，售货机「五脏六腑」这一章就收官了。

## 先给结论

- 出货记录表（本地 H2 表）的语义就是「未上报成功的记录」：成功发给服务端的记录会被删掉，表里剩下的全是有问题的数据。
- 补偿处理的核心是 `checkVendOutOrder()`：查出整张出货记录表，逐条封装成协议对象，重新调用 `emqClient.publish` 上报。
- 补偿的触发点挂在 EMQ 的 `connectComplete` 回调里——网络抖动后重连成功就自动执行补偿，不需要人工干预。
- 补货业务对售货机端来说就是「修改 `tb_channel` 表」：服务端补货后下发 `supplyReq` 通知，售货机按货道更新库存。
- 协议里的 `capacity` 是补货后的总数量（现存数量），不是本次补了多少的增量。
- 更新完货道数据，还要把通知里的 `versionId` 写回版本表，保持数据版本同步。

## 补偿处理：把没上报成功的记录重发一遍

问题来源很实际。上报的过程中可能出现各种异常：售货机突然当机、服务端发生异常或宕机、网络抖动导致网络不够通畅。种种现象最终都指向同一个结果——服务端和售货机端的数据不一致。

而解决思路就藏在出货记录表本身的设计里。这张表里存的记录，都是没有成功发给服务端的数据；一旦成功发给服务端，记录就被删掉了。也就是说，表里留下来的都是有问题的记录，要做的操作只有一个：重新上报。这种操作就叫补偿处理。

具体做法是在接口里新增一个方法，语义是「售货机启动时检查是否有未上报的信息」：

```java
/**
 * 售货机启动时候检查是否未上报信息
 */
public void checkVendOutOrder();
```

实现分三步：查出本地出货记录表，遍历每条记录封装成 `VendOutResult` 协议对象，再调用 `emqClient.publish` 发布出去：

```java
@Override
public void checkVendOutOrder() {
    List<VendOutOrder> vendOutOrderList = vendOutOrderMapper.selectList(null);
    for (VendOutOrder vendOutOrder : vendOutOrderList) {
        VendOutResult vendOutResult = new VendOutResult();
        vendOutResult.setInnerCode(config.getInnerCode());
        vendOutResult.setSn(System.nanoTime());
        vendOutResult.setNeedResp(true);
        if (vendOutOrder.getResultCode() == 0) {
            vendOutOrder.setSuccess(true);
        }
        vendOutResult.setVendOutResult(vendOutOrder);
        emqClient.publish(vendOutResult.getMsgType(),
                JSON.toJSONString(vendOutResult));
    }
}
```

每条重发的记录都重新生成 `sn`（取 `System.nanoTime()`），并把 `needResp` 置为 true，等服务端的响应确认；`innerCode` 从配置里取本机编码。

更关键的是调用时机。EMQ 客户端回调里有一个连接成功的方法 `connectComplete`：发生网络抖动之后重连成功，就会经过这个方法。把补偿逻辑追加在这里（方法里原有订阅等代码保留），重连成功就自动补一次：

```java
@Override
public void connectComplete(boolean connectComplete, String topic) {
    //订阅服务器topic,及回调处理方法
    try {
        //....代码略 ....
        //检查是否未同步的出货信息
        dataProcessService.checkVendOutOrder();
    } catch (MqttException e) {
        log.info("connectComplete", e);
    }
}
```

补偿调用用 try-catch 包起来捕获 `MqttException`，出错就记日志，保证回调本身不被异常拖垮。

## 补货业务：响应 supplyReq，更新货道库存

补货业务是反方向的场景：服务端完成补货（比如添加商品）之后，要通知售货机进行库存更新。协议从服务端发往客户端，`msgType` 为 `supplyReq`，里面的 `supplyData` 是一个列表——一次传输会带很多个货道的数据，每个货道包含货道编号、商品和库存：

```json
{
  "msgType": "supplyReq",
  "sn": "342424343",
  "innerCode": "01012121",
  "needResp": true,
  "versionId": 1,
  "supplyData": [
    {
      "channelId": "1-1",
      "skuId": 112,
      "capacity": 5
    }
  ]
}
```

注意 `capacity` 的语义：它是补货之后的数量，也就是现存数量，不是本次补了多少。

实现思路和前面讲的数据同步是一样的。先定义封装补货协议的对象，继承 `BaseData`：

```java
@Data
public class SupplyReq extends BaseData {
    private List<ChannelRespData> supplyData;
}
```

服务接口里封装一个处理补货的方法：

```java
public void supplyReq(SupplyReq supplyReq);
```

实现类里把这个对象接收过来，提取补货数据。数据是个列表，循环处理即可：每条 `ChannelRespData` 对应一个 `Channel` 表实体，两边属性一致，直接用 `BeanUtils.copyProperties` 完成属性拷贝，然后 `channelMapper.updateById` 更新记录。货道全部更新完，再从通知数据里取出 `versionId`，更新版本表：

```java
@Override
public void supplyReq(SupplyReq supplyReq) {
    if (supplyReq.getSupplyData() != null && !supplyReq.getSupplyData().isEmpty()) {
        for (ChannelRespData channelRespData : supplyReq.getSupplyData()) {
            Channel channel = new Channel();
            BeanUtils.copyProperties(channelRespData, channel);
            channelMapper.updateById(channel);
        }
        Version version = versionMapper.selectById(1);
        version.setChannelVersion(supplyReq.getVersionId());
        versionMapper.updateById(version);
    }
}
```

触发点依然在消息回调里。在正确接收消息的处理之后加一个判断：如果消息类型是补货通知，就把 payload 解析成 `SupplyReq`，调用刚才封装的处理逻辑：

```java
if (MsgType.supplyReq.getType().equalsIgnoreCase(msgType)) {
    SupplyReq supplyReq = JSON.parseObject(payload, SupplyReq.class);
    dataProcessService.supplyReq(supplyReq);
}
```

## 小结

补偿处理和补货业务是售货机端可靠性的最后两块拼图。前者利用「出货记录表只存失败记录」的特点，在 EMQ 重连成功的 `connectComplete` 回调里整表重发，让宕机、抖动期间丢失的上报最终补齐；后者在服务端补货后通过 `supplyReq` 通知售货机，循环更新 `tb_channel` 货道库存并同步版本号。两个业务一个管「报上去」、一个管「改下来」，合在一起，售货机与服务端的数据最终一致性就有了着落，售货机「五脏六腑」一章到此收官。
