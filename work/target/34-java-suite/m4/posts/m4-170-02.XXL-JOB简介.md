# XXL-JOB从选型到落地：架构、开箱使用、阻塞处理策略三连测与立可得集成

立可得第四章"自动化运营与运维解决方案"从任务调度开篇：后面的自动维修工单、自动补货工单都依赖定时任务，原有Spring Task方案撑不住分布式场景，多方调研后选定XXL-JOB。这篇把它的落地路径走完整：认识架构、开箱部署、跑通官方示例、阻塞处理策略三种选择的实测对比，最后把XXL-JOB集成进立可得的用户微服务。

## 先给结论

- XXL-JOB是美团点评中间件研发工程师许雪里开发的分布式任务调度平台，核心设计目标是开发迅速、学习简单、轻量级、易扩展；课程环境使用2.2.0版本，大众点评、京东、优信二手车、北京尚德、360金融、联想、网易等都在用。
- 架构分两大块：调度中心（任务管理、执行器管理、日志管理、报表告警）和执行器——每个微服务就是一个执行器，通过注册线程注册到调度中心，机制类似ZooKeeper、Eureka这类注册中心。
- 部署三件事：执行源码doc/db下的tables_xxl_job.sql建出8张表，写docker-compose.yml指定镜像和数据库连接，docker-compose up启动，控制台用默认admin/123456登录。
- 跑通任务靠四个名字对齐：代码里@XxlJob注解的任务名=任务管理里的JobHandler，配置里的appname=执行器管理里的AppName；执行器与调度中心的通信端口（示例9999，立可得9981）和微服务自身的server.port是两回事。
- 阻塞处理策略应对"调度密于执行"：单机串行按FIFO排队全做完但会积压，丢弃后续调度保住当前任务、新请求标记失败，覆盖之前调度终止旧任务跑新的——实测10秒的任务每5秒调度一次时，覆盖策略没有一次能执行完。
- 立可得集成四步：pom加xxl-job-core依赖、Consul配置中心加xxl.job配置、拷源码XxlJobConfig改造、写UserJob任务类；调度中心新建执行器（自动注册）并配置任务，用户微服务一上线即注册成功。

## XXL-JOB是什么：调度中心加执行器

XXL不是衣服尺码，而是作者许雪里姓名的首字母，这个分布式任务调度平台由他在美团点评开发。开源产品里同类选项不少，比如当当开源的Elastic-Job、阿里早期的TBSchedule，立可得最终选了XXL-JOB来替换Spring Task。

架构图分两大块：

**调度中心**，也就是XXL-JOB服务端。管理界面提供任务管理、执行器管理、日志管理（调度日志加实时日志）、运行报表和告警邮件等功能；内核里最核心的组件是调度器，到了设定的时间节点，由它发起远程调用去触发执行器。

**执行器**，可以理解为之前写的各个微服务——立可得的用户微服务是一个执行器，工单微服务也是一个执行器。执行器内部这条链路值得看清：

1. 执行器通过注册线程把自己注册到调度中心的注册服务里；
2. 调度请求进来先进队列排队，请求密集时按顺序管理；
3. 任务线程取出请求，执行具体的JobHandler任务；
4. 执行过程通过日志服务写实时日志，调度中心里能看到正在执行的任务的完整过程；
5. 执行完成后通过回调线程调用回调服务，把结果报回调度中心。

## 开箱使用：建表、Docker Compose与控制台

课程提供的镜像已经装好了XXL-JOB，docker ps能看到xxl-job-admin容器在跑。想在自己的服务器上装一套，走三步。

第一步建库建表。官方提供了脚本tables_xxl_job.sql，在源码的doc/db目录下（github.com/xuxueli/xxl-job/blob/2.2.0/doc/db/tables_xxl_job.sql），连上MySQL执行后，xxl_job库里会有8张表。

第二步写docker-compose.yml：

```yaml
version: "3"
services:
  xxl-job-admin:
    image: xuxueli/xxl-job-admin:2.2.0
    container_name: xxl-job-admin
    privileged: true
    volumes:
      - /opt/middleware/xxljob/applogs:/data/applogs
    ports:
      - "8080:8080"
    environment:
      TZ: Asia/Shanghai
      PARAMS: "--spring.datasource.url=jdbc:mysql://192.168.200.128:3306/xxl_job?useUnicode=true&characterEncoding=UTF-8 --spring.datasource.username=root --spring.datasource.password=root123"
```

镜像用2.2.0版本，environment里的PARAMS指定时区和数据源连接——URL、用户名、密码对应第一步建好的库表。

第三步在文件所在目录执行：

```bash
docker-compose up
```

本机没有这个镜像会先自动下载，然后创建并启动容器。

启动后访问管理控制台http://192.168.200.128:8080/xxl-job-admin，默认账号admin、密码123456。界面上两处最常用：执行器管理里每个微服务对应一条记录，自带一个示例执行器；任务管理里定制每个任务的执行规则，点"新增"能看到完整表单——选执行器、填任务描述、选路由策略，Cron支持面板操作直接一选就自动生成，运行模式BEAN最常见，JobHandler填任务名称（要和代码注解里指定的名字一致），往下还有阻塞处理策略、失败重试次数、报警邮件等配置。

## 快速入门：跑通官方示例执行器

环境好了，代码可以先不写——XXL-JOB源码自带执行器示例。资料第四章文件夹里的xxl-job 2.2.0压缩包解开就是全部源码，执行器例子目录下有很多种，只需测试Spring Boot这一个。

这个示例是很标准的Spring Boot工程，配置文件里三处关键：

- 调度中心地址默认127.0.0.1，部署在虚拟机上就改成192.168.200.128；
- 执行器名字appname=xxl-job-executor-sample，要和调度中心执行器管理里的AppName一致。示例执行器这条记录数据库里自带，不用新增；注册方式选自动注册时机器地址留空，等执行器启动后自动注册上来；
- 端口9999是微服务和调度中心之间的通信端口，和微服务自己的server.port是两回事。

pom里引入xxl-job-core，版本2.2.0即可。配置类XxlJobConfig几乎是通用的，以后立可得要做XXL-JOB直接把这个类拷过去用：

```java
@Bean
public XxlJobSpringExecutor xxlJobExecutor() {
    XxlJobSpringExecutor xxlJobSpringExecutor = new XxlJobSpringExecutor();
    xxlJobSpringExecutor.setAdminAddresses(adminAddresses);
    xxlJobSpringExecutor.setAppName(appname);
    xxlJobSpringExecutor.setIp(ip);
    xxlJobSpringExecutor.setPort(port);
    xxlJobSpringExecutor.setAccessToken(accessToken);
    xxlJobSpringExecutor.setLogRetentionDays(logRetentionDays);
    return xxlJobSpringExecutor;
}
```

所有属性取自配置文件，@Bean返回XxlJobSpringExecutor实例，作用就是把执行器提交给调度中心，完成注册。

任务逻辑看SampleXxlJob里最简单的例子：

```java
@XxlJob("demoJobHandler")
public ReturnT<String> demoJobHandler(String param) throws Exception {
    XxlJobLogger.log("XXL-JOB, Hello World.");
    for (int i = 0; i < 5; i++) {
        XxlJobLogger.log("beat at:" + i);
        TimeUnit.SECONDS.sleep(2);
    }
    return ReturnT.SUCCESS;
}
```

方法上@XxlJob注解指定任务名，返回类型ReturnT用来标记成功与失败。

启动执行器之前，调度中心里它的online机器地址是空的；启动完成后刷新页面，出现"查看1"，点开是192.168.200.1:9999（讲师本机Windows地址）——注册成功，集群时这里会是多个地址。

任务管理里demoJobHandler这个任务已经配好，初始是STOP状态。只想测一次逻辑可以不启动任务，直接点"执行一次"，填任务参数（没有就留空）保存，提示执行一次成功。

这里有个容易踩的点：任务的日志输出不在微服务控制台里。控制台翻不到Hello World，是因为示例用的是XxlJobLogger.log，它写进的是调度中心的实时日志——去调度日志页面找到这次执行记录，点操作里的"执行日志"，能看到XXL-JOB, Hello World和beat at: 0到4的完整输出。想在微服务控制台打印，就用常规的logger.info；加一句logger.info("XXLjob Demo")再执行一次，控制台就有了。两种日志各管一头，要分清。

## 阻塞处理策略：三种策略与三连测

任务管理的新增窗口里有个"阻塞处理策略"，下拉三个选项：单机串行、丢弃后续调度、覆盖之前调度。它解决的是执行器忙不过来的场景——任务要跑5分钟，Cron却设成每3分钟调度一次，派发频率远高于执行速度，调度请求必然堆积。

| 策略 | 行为 | 后果 |
| :--- | :--- | :--- |
| 单机串行 | 调度请求进入单机执行器后进FIFO队列，排队逐个执行，派的任务最终都会完成 | 任务越积越多，越跑越慢 |
| 丢弃后续调度 | 发现执行器有正在运行的任务，本次请求直接丢弃并标记为失败 | 正在执行的能干完，中途插进来的不干 |
| 覆盖之前调度 | 发现正在运行的任务，终止它并清空队列，然后运行本次任务 | 调度间隔小于执行时长时，没有一个任务能跑完 |

拿示例代码实测。demoJobHandler循环5次、每次睡2秒，整个方法约10秒出头。先把Cron改成每15秒一次（0/15 * * * * ?），间隔大于执行时长，调度日志里每条都是成功，一切正常。

### 单机串行：排队全做完

把Cron改成每5秒一次，策略保持单机串行，启动。调度日志里开始堆积：有的记录正在执行，有的没有执行时间、没有输出——那是还在等待执行的任务。任务会一个接一个被做完，哪怕中途把任务停止，队列里剩下的那几条也依然会被执行完，只是慢。

### 丢弃后续调度：成功一失败二

策略改成丢弃后续调度，Cron仍每5秒。观察调度日志，呈现明显的频率：每成功一个，就失败两个——10秒的任务、5秒一调，执行期间来的两次调度都被拦回标记失败。当前任务一定干得完，只是部分调度请求被放弃。

### 覆盖之前调度：调度成功，执行全失败

策略改成覆盖之前调度再启动。调度日志出现奇观：调度结果全是"成功"，执行结果全是"失败"。每次新调度进来，都把正在执行的前一个任务终止掉自己上，任务永远执行到一半就被打断——没有一个能成功。

给三种策略各配一个人设：单机串行是老实人，派多少干多少，加班也要干完；丢弃后续调度是专注的人，手头的活干完，新派的活拦回去；覆盖之前调度是半途而废的人，干一半扔掉再干新的，永远没有一件事干成。实际项目中丢弃后续调度用得比较多，覆盖之前调度要慎重——很多场景下它意味着所有任务都完不成。

## 立可得集成：四步接入用户微服务

第二小节自动维修工单、第三小节自动补货工单都要用XXL-JOB，先把这项技术集成进立可得。演示加在用户微服务上，四步。

第一步，pom里加依赖：

```xml
<dependency>
    <groupId>com.xuxueli</groupId>
    <artifactId>xxl-job-core</artifactId>
    <version>2.3.2</version>
</dependency>
```

第二步，配置中心加配置。内容与源码里的properties一致，只是换成YAML格式。打开Consul配置中心的user-service，点开data，把配置复制进来：

```yaml
xxl:
  job:
    admin:
      addresses: http://192.168.200.128:8080/xxl-job-admin
    accessToken: admin
    executor:
      appname: user-service
      address: 192.168.200.128
      ip: 192.168.200.128
      port: 9981
      logretentiondays: 30
```

9981就是用户微服务与调度中心的通信端口。

第三步，配置类。不用手写，把源码里的XxlJobConfig直接拷到用户微服务新建的job包下，做两处小改造：原来的手工日志对象报错，改成@Slf4j注解直接用log更简洁；配置中心里没有提供日志路径的配置项，logpath这个属性用不到，把它删掉。

```java
@Slf4j
@Configuration
public class XxlJobConfig {

    @Value("${xxl.job.admin.addresses}")
    private String adminAddresses;
    @Value("${xxl.job.accessToken}")
    private String accessToken;
    @Value("${xxl.job.executor.appname}")
    private String appname;
    @Value("${xxl.job.executor.address}")
    private String address;
    @Value("${xxl.job.executor.ip}")
    private String ip;
    @Value("${xxl.job.executor.port}")
    private int port;
    @Value("${xxl.job.executor.logretentiondays}")
    private int logRetentionDays;

    @Bean
    public XxlJobSpringExecutor xxlJobExecutor() {
        XxlJobSpringExecutor xxlJobSpringExecutor = new XxlJobSpringExecutor();
        xxlJobSpringExecutor.setAdminAddresses(adminAddresses);
        xxlJobSpringExecutor.setAccessToken(accessToken);
        xxlJobSpringExecutor.setAppName(appname);
        xxlJobSpringExecutor.setAddress(address);
        xxlJobSpringExecutor.setIp(ip);
        xxlJobSpringExecutor.setPort(port);
        xxlJobSpringExecutor.setLogRetentionDays(logRetentionDays);
        return xxlJobSpringExecutor;
    }
}
```

第四步，写任务类：

```java
@Component
@Slf4j
public class UserJob {

    @XxlJob("testHandler")
    public ReturnT<String> testHandler(String param) throws Exception {
        log.info("立可得集成xxl-job");
        return ReturnT.SUCCESS;
    }
}
```

方法带一个String参数（有时用不上但签名要有），抛出Exception，返回ReturnT.SUCCESS。

代码就绪后配置调度中心。先新建执行器：AppName填user-service，和配置里的appname一致；名称写"立可得用户微服务"；注册方式选自动注册。再新增任务：执行器选用户微服务，任务描述填"测试"，路由策略选第一个，Cron设每5秒执行一次，运行模式BEAN，JobHandler填testHandler（必须和代码注解里的名字一致），阻塞处理策略用单机串行，负责人写xxl，保存。

验证闭环：启动用户微服务，回执行器管理刷新，"立可得用户微服务"这条已经出现online机器地址，点查看能看到9981端口——注册成功。任务当前是停止状态，先"执行一次"单测，控制台输出"立可得集成xxl-job"；清掉控制台后把任务启动，每5秒输出一条日志，调度日志里同步记录每次执行的成功结果。测试完把任务停止，集成完成。

## 小结

XXL-JOB的落地没有黑魔法：架构上记住"调度中心+执行器"这对角色和注册、队列、实时日志、回调这条链路；部署上是建表、docker-compose、默认账号三板斧；开发上抓四个名字的对齐——@XxlJob注解名、JobHandler、appname、AppName，再分清XxlJobLogger（进调度中心执行日志）和Logger（进微服务控制台）两种日志的去向。阻塞处理策略的三连测给出了直观答案：宁可丢弃部分调度，慎用覆盖——除非你能接受所有任务都半途而废。立可得的集成四步走完，后面的自动维修工单和自动补货工单就有了调度底座。
