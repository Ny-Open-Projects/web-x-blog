# 货物类型列表查询、更新删除与 hibernate-validator 数据校验落地

货物类型管理还剩最后几个接口：按多个 id 的列表查询、更新（连着关联关系一起改）、逻辑删除。收掉它们之后，本章进入数据校验小节：前面所有接口都只测过合法数据，名称、状态传空怎么办一直没管，这一节用 hibernate-validator 把合法性校验补上。

## 先给结论

- 查询货物类型列表本质是 in 条件查询：Controller 收 `List<String> ids`（required=false，不传就等于查所有），service 里 `LambdaQueryWrapper.in(PdGoodsType::getId, ids)` 一个条件搞定。
- 更新货物类型分两步：先 updateById 更新普通属性（DTO 拷到实体、路径变量来的 id 单独 set），再更新关联信息，操作的是中间关系表，套路是先清理旧关联、再按 truckTypeIds 批量重建。
- 删除关联关系的方法必须防「空条件全表删」：delete(truckTypeId, goodsTypeId) 里用 canExecute 标志位，两个条件都为空时不执行 baseMapper.delete，否则会把所有关联关系清光。
- 删除货物类型是逻辑删除，本质是更新：status 改成常量 DATA_DISABLE_STATUS（0）再调 updateById，返回统一结果对象 Result.ok()（code=0、msg=success）；关联表不动。
- hibernate-validator 在 pd-base 里靠 spring-boot-starter-web 依赖传递，不用显式导入；但 DTO 所在的 pd-service-api 没有 web 环境，要在父工程 pom 显式加坐标 org.hibernate:hibernate-validator:6.0.18.Final。
- 校验落地就两步：DTO 属性上加注解（name 加 @NotNull，status 加 @NotNull + @Max(1) + @Min(0)），Controller 方法参数前加 @Validated 开启校验。

## 按 ids 查询列表：一个 in 条件的标配写法

查询货物类型列表，方法定义一看就明白：前端或 pd-web 传过来多个货物类型 id，封装成 List 集合，按这批 id 查询，本质上就是 `select * from ... where id in (...)`。Controller 里方法名与查询所有的 findAll 同名重载，@GetMapping 值留空串，GET 请求打到类级路径 base/goodsType 就能命中；ids 参数 required=false，不传就相当于没加条件、查所有：

```java
@GetMapping
@ApiOperation(value = "查询货物类型列表")
public List<GoodsTypeDto> findAll(@RequestParam(name = "ids", required = false) List<String> ids) {
    List<PdGoodsType> list = goodsTypeService.findAll(ids);
    if (list != null && list.size() > 0) {
        return list.stream().map(pdGoodsType -> {
            // 查每个货物类型关联的车辆类型id
            List<String> truckTypeIds =
                    truckTypeGoodsTypeService.findAll(null, pdGoodsType.getId())
                            .stream()
                            .map(PdTruckTypeGoodsType::getTruckTypeId)
                            .collect(Collectors.toList());
            GoodsTypeDto goodsTypeDto = new GoodsTypeDto();
            BeanUtils.copyProperties(pdGoodsType, goodsTypeDto);
            goodsTypeDto.setTruckTypeIds(truckTypeIds);
            return goodsTypeDto;
        }).collect(Collectors.toList());
    }
    return null;
}
```

service 实现里的条件只有一个，LambdaQueryWrapper 的 in 方法直接对应 SQL 的 IN 关键字：

```java
@Override
public List<PdGoodsType> findAll(List<String> ids) {
    LambdaQueryWrapper<PdGoodsType> lambdaQueryWrapper = new LambdaQueryWrapper<>();
    if (ids != null && ids.size() > 0) {
        lambdaQueryWrapper.in(PdGoodsType::getId, ids);
        return baseMapper.selectList(lambdaQueryWrapper);
    }
    return null;
}
```

写到这里套路已经完全固定了：Controller 调 service，service 查出来的一律是实体（跟表有映射关系），Controller 再把实体转成 DTO 用于网络传输。Swagger 测试两步走：ids 什么都不传直接 execute，返回全部货物类型；然后从库里复制两个真实 id（如 1230685120449613824）逐个 add item，执行后只查出这两条，in 条件生效。

## 更新与删除：主表 updateById，关联表先清后建

更新货物类型比新增多一层含义：除了基本信息，关联的车辆类型也可能要改。方法用 PUT，id 走路径变量，DTO 走 @RequestBody（请求体是 JSON，由框架解析封装成 DTO）：

```java
@PutMapping("/{id}")
@ApiOperation(value = "更新货物类型信息")
public GoodsTypeDto updateById(@PathVariable(name = "id") String id,
                               @RequestBody GoodsTypeDto dto) {
    // 第一步：更新货物类型的普通属性
    PdGoodsType pdGoodsType = new PdGoodsType();
    BeanUtils.copyProperties(dto, pdGoodsType);   // 方向别写反：DTO 拷到实体
    pdGoodsType.setId(id);                        // 路径变量来的 id 单独设置
    goodsTypeService.updateById(pdGoodsType);     // IService 继承来的方法
    // 第二步：更新关联信息（操作的是中间关系表）
    List<String> truckTypeIds = dto.getTruckTypeIds();
    if (truckTypeIds != null && truckTypeIds.size() > 0) {
        // 清理原有关联：删掉该货物类型对应的全部关联记录
        truckTypeGoodsTypeService.delete(null, id);
        // 重新建立关联
        List<PdTruckTypeGoodsType> list = truckTypeIds.stream().map(truckTypeId -> {
            PdTruckTypeGoodsType pdTruckTypeGoodsType = new PdTruckTypeGoodsType();
            pdTruckTypeGoodsType.setGoodsTypeId(id);        // 货物类型id
            pdTruckTypeGoodsType.setTruckTypeId(truckTypeId); // 车辆类型id
            return pdTruckTypeGoodsType;
        }).collect(Collectors.toList());
        truckTypeGoodsTypeService.batchSave(list);
    }
    dto.setId(id);
    return dto;
}
```

普通属性和关联属性在这里分了界：truckTypeIds 之外的都算普通属性，走主表更新；truckTypeIds 是关联属性，走关系表。关系表的操作一般就一个套路：先把该货物类型的原有关联全部清掉，再按新传的车辆类型 id 重新建立，两步走而不是逐条比对差异。

清理用的 delete 方法在关联 service 里声明为 delete(String truckTypeId, String goodsTypeId)，两个条件都开放：可以只按货物类型删、只按车辆类型删，也可以同时传，功能更强。实现里 baseMapper.delete 接收的仍然是 LambdaQueryWrapper，同一个对象，封装的从查询条件换成了删除条件。这里有一个必须防的坑：两个条件都为空时绝不能执行 delete，没有 where 条件等于把整张关联表清空，所以用 canExecute 标志位把关：

```java
@Override
public void delete(String truckTypeId, String goodsTypeId) {
    LambdaQueryWrapper<PdTruckTypeGoodsType> lambdaQueryWrapper = new LambdaQueryWrapper<>();
    boolean canExecute = false;
    if (StringUtils.isNotBlank(truckTypeId)) {
        lambdaQueryWrapper.eq(PdTruckTypeGoodsType::getTruckTypeId, truckTypeId);
        canExecute = true;
    }
    if (StringUtils.isNotBlank(goodsTypeId)) {
        lambdaQueryWrapper.eq(PdTruckTypeGoodsType::getGoodsTypeId, goodsTypeId);
        canExecute = true;
    }
    if (canExecute) {
        baseMapper.delete(lambdaQueryWrapper);
    }
}
```

Swagger 验证更新接口分两轮。第一轮只改基本信息：id 用库里真实货物类型 id，name 改成 test、remark 改成 5、status 改 1，truckTypeIds 从请求体里删掉不传，执行后数据库里基本信息都改了，关联表一条没动。第二轮验证关联更新：先 `SELECT * FROM pd_truck_type_goods_type WHERE goods_type_id = <id>` 看到旧的两条关联，然后把请求体里 truckTypeIds 换成从 pd_truck_type 表新挑的两个车辆类型 id 再执行，重新查询关联表，旧的两条已经清掉、新加的两条进来了，主表字段同步更新。

最后一个接口是删除货物类型，注意它是逻辑删除：本质上是更新操作，把状态位 status 改成 0 即可，最终调的还是 updateById。代码从讲义直接复制，方法很短：

```java
@PutMapping("/{id}/disable")
@ApiOperation(value = "删除货物类型")
public Result disable(@PathVariable(name = "id") String id) {
    PdGoodsType pdGoodsType = new PdGoodsType();
    pdGoodsType.setId(id);   // 相当于删除条件
    pdGoodsType.setStatus(Constant.DATA_DISABLE_STATUS);
    goodsTypeService.updateById(pdGoodsType);
    return Result.ok();
}
```

状态值没有硬编码 0，而是用 constants 类里的常量：`DATA_DEFAULT_STATUS = 1`、`DATA_DISABLE_STATUS = 0`，好处是哪天状态语义调整（比如改成 1 表示禁用），只改常量一处就行。返回值用的是统一结果对象 Result，封装状态码和信息，Result.ok() 就是 code=0、msg=success。测试时 Swagger 里这个接口也是 PUT 请求（虽然叫删除，实际是更新），传 id 执行后返回 message=success、code=0；回数据库刷新，那条数据还在、status 已变成 0，逻辑删除生效，同时关联关系表完全没动。

## hibernate-validator：注解清单与两步落地

接口写完有个问题一直悬着：合法性校验。前面测试给的全是合法数据，假如名称、状态传空呢？数据校验一般分两方面：前端校验在页面或移动端提交请求前就提示「该字段不能为空」，靠 JavaScript 脚本，目的是提升用户体验，别让用户填了一大堆表单提交时才被打回；后端校验保证数据安全可靠，靠校验框架实现。本课程重点是后端，前端交给前端人员。

后端用的是 hibernate-validator，它提供一套注解，加在字段上就能优雅地完成校验：不用在已写好的 controller、service 里塞 if else。三个优势：验证逻辑与业务逻辑分离、降低耦合；统一且规范的验证方式，不用重复写验证代码；让人更专注于业务：哪个参数不能为空、哪个值必须在 10 到 20 之间这类判断全交给框架。

依赖方面有个细节。使用框架要导 maven 坐标：

```xml
<dependency>
    <groupId>org.hibernate</groupId>
    <artifactId>hibernate-validator</artifactId>
    <version>6.0.18.Final</version>
</dependency>
```

但 pd-base 已经引入了 spring-boot-starter-web，它依赖传递了 spring-boot-starter-validation，再往下传递就是 hibernate-validator，所以在 pd-base 里不用再显式导入。麻烦出在 DTO：GoodsTypeDto 放在 pd-service-api 这个父工程（具体在 pd-service-base-domain 子模块）里，它没导 web 环境，校验注解引不进来，所以要把上面的坐标显式加到 pd-service-api 的 pom 上，子模块就都能用了。导包时还要注意：@NotNull 这类注解应该选 javax.validation 包下的，那才是 hibernate-validator 使用的注解体系。

常用注解整体过一遍，字面含义基本能猜出校验方式：

| 注解 | 说明 |
|---|---|
| @AssertTrue | boolean 字段只能为 true |
| @AssertFalse | boolean 字段只能为 false |
| @CreditCardNumber | 对信用卡号进行大致验证 |
| @DecimalMax / @DecimalMin | 只能小于等于 / 大于等于该值 |
| @Email | 检查是否是有效的 email 地址（只校验格式，不验证是否真实存在） |
| @Future | 日期必须是将来日期，传过去的时间校验失败 |
| @Length(min=,max=) | 字符串长度在 min 和 max 之间，只能用于字符串 |
| @Max / @Min | 值只能小于等于 / 大于等于该值 |
| @NotNull | 不能为 null |
| @NotBlank | 不能为空，检查时会将空格忽略 |
| @NotEmpty | 不能为空，这里的空指空字符串 |
| @Pattern(regex=) | 必须符合指定的正则表达式 |
| @URL(protocol=,host=,port=) | 检查是否是有效 URL（含协议、主机、端口），提供了条件则还需满足 |

落地就两步。第一步在 DTO 属性上加注解，挑常用的加，按业务定。name 不能为空，加 @NotNull；status 是状态位，取值只有 0 和 1 两个选择，传 2、3、4 没有意义，所以 @NotNull 之外再加 @Max(1) 和 @Min(0) 卡死范围：

```java
@ApiModelProperty("物品类型名称")
@NotNull
private String name;

@ApiModelProperty("状态 0: 禁用 1: 正常")
@NotNull
@Max(value = 1)
@Min(value = 0)
private Integer status;
```

第二步开启校验：在需要校验的方法参数前加 @Validated，以新增货物类型为例：

```java
@PostMapping
@ApiOperation(value = "添加货物类型")
public GoodsTypeDto saveGoodsType(@Validated @RequestBody GoodsTypeDto goodsTypeDto) {
    // ...
}
```

加上之后框架就会检查 DTO 里的属性是否满足注解要求，具体校验什么取决于加了哪些注解。其余增删改查方法不逐个演示了，需要校验的位置照这个模式自己加即可。

## 小结

- 按 ids 查询列表是 in 条件查询的标配写法：@RequestParam 收 List&lt;String&gt;，service 里 LambdaQueryWrapper.in(PdGoodsType::getId, ids)，ids 不传就等于查所有；Controller 侧照旧查关联、实体转 DTO。
- 更新货物类型两步走：主表 updateById（BeanUtils 拷贝方向是 DTO 到实体，路径 id 单独 set），关联信息在关系表上先 delete 清理、再 batchSave 重建。
- 关联表删除方法用 canExecute 标志位兜底，两个条件都为空时拒绝执行，避免无条件 delete 清空全表。
- 删除货物类型是逻辑删除：status 置为常量 DATA_DISABLE_STATUS（0）后走 updateById，返回 Result.ok()；数据还在库里，关联表不动。
- hibernate-validator 靠 spring-boot-starter-web 在 pd-base 里传递引入，但 pd-service-api 没 web 环境要显式加坐标（6.0.18.Final）；导包选 javax.validation 下的注解。
- 校验落地两步：DTO 属性加注解（name @NotNull，status @NotNull + @Max(1) + @Min(0)），方法参数加 @Validated 开启。
