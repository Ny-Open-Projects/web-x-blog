# 人效排名月度统计：需求思路与代码实现

管理后台还有一张「人效排名」榜单：按区域统计当月完成工单量最多的前十名运营或运维人员，干得越多排得越靠前，公司据此对表现好的员工实施激励。这是立可得第八章「统计分析」里体量很小的一节，两个视频就讲完了需求与代码实现，核心是一个聚合查询，这里把它写透。

## 先给结论

- 需求：根据区域统计完成工单量最多的前 10 名实名运营/运维人员；可以不指定区域查全部，也可以指定某一区域。
- 运营和运维必须分开排名：两类岗位的工作量不具可比性，榜单要么运维、要么运营，界面上切换。
- 实现思路一句话：对工单表做聚合查询——按人分组统计工单数，按工单数降序排序，截取前 10。
- 接口是 GET /task-service/task/userWorkTop10/start/end/isRepair/regionId，四个路径参数；regionId 传 0 表示查全部区域；返回 List<UserWork>，每个元素只有 userName 和 workCount 两个属性。
- 实现里有个借用技巧：select 写 count(user_id) as user_id，拿数字字段 user_id 临时存放统计出的工单数，否则结果没法封装。
- 第一遍测试排名不对，原因是 group by 后少了降序排序，补上 orderByDesc 才是真正的排名。

## 需求：按区域排出工单量 Top10

需求本身很好理解：管理后台要能根据区域统计出该区域完成工作量最多的实名运营或运维人员。这里的「工作量」就是完成的工单量——完成工单越多，证明这个人干的活越多。用途也很直接：方便公司对干得比较好的员工实施激励或奖励。

效果是一张榜单图，两个查询维度可以灵活搭配。区域维度：可以不指定区域查全部范围，也可以指定某一个区域。人员维度：运营和运维肯定要分开，因为两类岗位的工作内容不同，工作量本身不具有可比性，所以榜单要么是运维的一个排名、要么是运营的一个排名，界面上可以切换。

实现思路一句话说得清：主要用聚合查询。对工单表根据每一个人进行聚合，统计出每个人的工单数，再根据工单数排序，截取前十。

## 实现：一个 QueryWrapper 搞定聚合

先解读 API 文档。管理后台的「人员排名」接口接收四个路径参数：开始日期 start、截止日期 end、是否运维工单 isRepair、区域 ID regionId。查全部区域时 regionId 传 0，指定区域就传具体的区域 ID。返回一个列表，每个元素两个属性：userName 用户名、workCount 完成工单数。这两个属性在之前定义的视图模型类 UserWork 里已经有了，直接返回 UserWork 的集合即可。

Service 方法定义在工单微服务的 TaskService 里：

```java
List<UserWork> getUserWorkTop10(LocalDateTime start, LocalDateTime end,
                                Boolean isRepair, Long regionId);
```

实现类 TaskServiceImpl 里用 MyBatis-Plus 的 QueryWrapper 构建聚合查询，主体骨架：

```java
QueryWrapper<TaskEntity> qw = new QueryWrapper<>();
qw.select("count(user_id) as user_id", "user_name")
  .lambda()
  .between(TaskEntity::getUpdateTime, start, end)             // 日期窗口
  .eq(TaskEntity::getTaskStatus, VMSystem.TASK_STATUS_FINISH) // 必须是已完成
  .groupBy(TaskEntity::getUserName)                           // 按人分组
  .orderByDesc(TaskEntity::getUserId)                         // 按工单数降序
  .last("limit 10");                                          // 只取前 10
```

select 里有讲究。统计的就是每个人完成的工单数，挑一列做 count 即可，这里选了 count(user_id)。但统计结果得存进一个字段，否则最后没法封装——于是借用了 user_id 这个数字类型字段，写成 count(user_id) as user_id。讲师也明说这是一种借用，会牺牲一点可读性：user_id 从此不再是用户 ID，而是完成工单数。select 同时带上 user_name，group by 也按 user_name 分组。

条件部分：状态必须是已完成（finish），别的状态的工单统计进去没有意义；日期窗口用 between 圈定 start 到 end；最后 limit 10，多了没用。

再补两个动态条件：

```java
// 区域筛选：null 或 0 都代表查全部区域，大于 0 才加条件
if (regionId != null && regionId > 0) {
    qw.lambda().eq(TaskEntity::getRegionId, regionId);
}
// 运维排名：把补货类型的工单排除掉
if (isRepair) {
    qw.lambda().ne(TaskEntity::getProductTypeId, VMSystem.TASK_TYPE_SUPPLY);
}
```

区域 ID 等于 null 或 0 都跳过条件，大于 0 才加 eq。isRepair 区分运营运维：统计运维时要把补货工单类型排除，补货工单不算进这个排名。

查询结果是 TaskEntity 列表，用 stream 转成 UserWork：

```java
List<UserWork> result = this.list(qw).stream().map(t -> {
    var userWork = new UserWork();
    userWork.setUserName(t.getUserName());
    userWork.setWorkCount(t.getUserId()); // user_id 是借用的，实际存的是工单数
    return userWork;
}).collect(Collectors.toList());
return result;
```

workCount 取的是 getUserId()，原因就是前面那个借用关系——user_id 里存的已经是完成工单数。Controller 按接口文档直接编写，四个路径参数原样接住，转手调 service，课堂上这部分是直接把讲义里的代码拿过来按 API 传参的。

## 联调测试：先踩一个「排名不对」的坑

测试流程：先启动工单微服务，再启动微服务网关，测试脚本从网关访问。数据库里准备数据：工单表里给张三、李四等人造好已完成的工单，并指定一个区域。VS Code 的 task.http 里有一个「人效排名月度统计」脚本，区域编号已经填进去，isRepair 传 true 表示统计运维，再带一个时间段。点击 send request，结果正常返回——返回 JSON 里很多属性是 null，不用管，最终只取 userName 和 workCount，因为其他字段本来就没赋值。

第一遍测试暴露了一个问题：排名不对，工单数 1 的排在前面、2 的反而排在后面。回头看代码，group by 后面少了一个排序——补上 orderByDesc 降序即可（就是上面骨架里那一行）。注意排序依据还是 getUserId()，这个 user_id 不是真的用户 ID，实际存的是工单数，按它降序就是按工单数从多到少排。

## 小结

- 人效排名是标准的聚合统计四件套：按人 group by、count 计数、order by 降序、limit 10，一条 QueryWrapper 全搞定。
- 借用字段技巧：count(user_id) as user_id，用数字字段临时承接聚合结果；可读性受损，封装时记得从 getUserId 里取的是工单数。
- 两个动态条件对应两个业务口径：regionId 为 0 或 null 查全部区域；运维排名要排除补货类型工单。
- 排名类需求里「分组、排序、截断」缺一不可，少一个 order by，排名就成了摆设。
