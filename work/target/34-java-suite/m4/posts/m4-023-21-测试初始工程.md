# TMS 初始工程跑通验收：pd-base 启动链路与 Nacos 鉴权排错

第 1 章环境搭建完成后还差最后一步验收：导入的初始工程到底能不能跑。课程用一个视频、以最简单的 pd-base 模块为样例，从写启动类到服务注册进 Nacos 走完整条链路，过程中正好撞上 Nacos 开启鉴权后的权限报错，把「用户 → 角色 → 命名空间授权」这条排错路径也一并演示了。这一篇把启动链路、配置加载规则和验证点拆开讲清。

## 先给结论

- 初始工程的 POM、包结构、bootstrap 配置全部预置完毕，开发阶段不需要再动这些文件；验收选 pd-base，因为它依赖最少、最容易拉起。
- 启动链路是：bootstrap.yml 激活 dev 环境 → 加载 bootstrap-dev.yml → 连接 Nacos（同时充当注册中心和配置中心）；Tomcat 端口 8185，应用名 pd-base。
- 启动类只要三步：类上 @SpringBootApplication 加 @EnableDiscoveryClient，main 方法里 SpringApplication.run 一行。
- 配置中心读哪个文件由「应用名 + 环境」决定：pd-base + dev 就只读 pd-base-dev.yml，配置中心里其他十几个配置一律不加载。
- 首次启动必报 NacosException（no right / authorization failed / forbidden）：bootstrap-dev.yml 里配了用户名密码，就要求 Nacos 中存在该用户、且对目标命名空间有权限；解法是创建用户 → 绑定角色 → 给角色授予命名空间读写权限。
- 验证闭环看三处：日志 Tomcat started on port 8185、Nacos 服务列表出现实例、停服后实例先转不健康再延迟消失。

## 初始工程里已经备好了什么

验收之前先确认工程里现成的部分。以 pd-base 为例打开 pom.xml，坐标全部已经写好，其中两个 Nacos 相关 starter 是这条链路的关键：spring-cloud-starter-nacos-discovery 负责服务注册与发现，spring-cloud-starter-nacos-config 负责从配置中心拉配置。导入的初始工程里所有模块的 POM 都提前配置完成，开发时基本不用再碰。

包结构也划分好了，Java 代码挂在 com.itheima.pinda 目录下；配置文件是 bootstrap 双文件结构：

- bootstrap.yml：入口配置，最先加载，负责激活环境；
- bootstrap-dev.yml：开发环境专属配置，存放 Nacos 连接信息。

bootstrap.yml 里 server.tomcat 指定 Tomcat 端口 8185，应用名 pd-base，激活的环境是 dev。dev 被激活意味着 bootstrap-dev.yml 也会被加载，服务启动时就会去连 Nacos。真正连 Nacos 的部分在 bootstrap-dev.yml：

```yaml
spring:
  cloud:
    nacos:
      username: tms
      password: itheima123
      discovery:                # 注册中心
        server-addr: 68.79.63.42:8848
        group: pinda-tms
        namespace: 6107f553-3214-48d8-89c3-945f8446c3d9
      config:                   # 配置中心
        server-addr: 68.79.63.42:8848
        file-extension: yml
        group: pinda-tms
        namespace: 6107f553-3214-48d8-89c3-945f8446c3d9
```

namespace 就是上一节在 Nacos 里新建「品达-TMS」命名空间时自动生成的 ID，group 为 pinda-tms，用户名密码是 tms/itheima123。文件里还有 jackson 时间格式化（time-zone、date-format）和 servlet 文件上传大小（max-file-size、max-request-size）等通用配置，值都从配置中心占位符引用。这套配置决定了服务启动时的全部外部行为：连哪台 Nacos、注册到哪个命名空间、拉哪份配置。

## 启动类与配置加载规则

启动类写在 pinda 目录下，命名为 BaseApplication，代码本身就三步：

```java
@SpringBootApplication
@EnableDiscoveryClient
public class BaseApplication {

    public static void main(String[] args) {
        SpringApplication.run(BaseApplication.class, args);
    }
}
```

@SpringBootApplication 是 Spring Boot 启动注解，@EnableDiscoveryClient 开启服务发现客户端，main 方法一行 SpringApplication.run 传入当前类。这是最简单的服务启动类，没有多余内容。

启动前还有个规则要先弄明白：Nacos 配置中心里已经有十几个配置文件（pd-user-dev.yml、pd-web-dev.yml 等一批），服务启动时具体读哪一个？由两个参数共同决定——应用名加环境。当前应用名是 pd-base、环境是 dev，所以只会读取 pd-base-dev.yml 这一个配置文件，其余配置一律不加载。这个规则反过来也解释了配置文件命名规范 pd-服务名-dev.yml 的用意：名字对得上，服务才能找到自己的配置。

## 首次启动失败：Nacos 鉴权报错与授权三步

按上面的配置直接启动，是会报错的，而且这个报错是故意留下的教学点。控制台抛出 NacosException，错误信息里能看到三处关键词：no right（没有权限）、authorization failed（授权失败）、forbidden（被禁止）。

原因在 bootstrap-dev.yml 的 username/password 上：这两个配置意味着 Spring Boot 项目与 Nacos 交互时要先做用户名密码验证。验证要过三道关——Nacos 里必须存在这个用户，密码要和配置一致，而且这个用户还必须拥有访问目标命名空间的权限。当前 Nacos 里根本没有给 tms 用户授过品达-TMS 命名空间的权限，第三道关卡住了，所以报 no right。

解决办法在 Nacos 控制台的「权限控制」菜单下，分三步走：

| 步骤 | 操作位置 | 操作内容 |
|---|---|---|
| 1. 创建用户 | 权限控制 → 用户列表 | 点创建用户，填用户名、密码、确认密码 |
| 2. 绑定角色 | 权限控制 → 角色管理 | 点绑定角色，填角色名称和用户名 |
| 3. 授予权限 | 权限控制 → 权限管理 | 点添加权限，选角色、选资源（命名空间）、选动作 |

课上先新建了一个 user001（密码 123456）演示完整流程：绑定角色 role-test，再到权限管理里添加权限——角色选 role-test，资源选前面新建的「品达-TMS」命名空间，动作选 rw（read/write 读写）。这样 user001 就通过角色获得了该命名空间的读写权限。把 bootstrap-dev.yml 的用户名密码临时换成 user001/123456 再启动，这次没有报错：日志里 Tomcat started on port 8185，服务成功注册，Nacos 服务列表的品达-TMS 命名空间下能看到这个实例。

## 验证点：日志、服务列表与下线延迟

启动成功的验证点有三处。第一处是控制台日志：Tomcat started on port 8185 说明内嵌容器起来了，BaseApplication 启动完成（课上环境耗时约 42 秒），期间没有报错就说明配置中心的那份配置已经正常读到。第二处是 Nacos 控制台的服务列表：品达-TMS 命名空间下出现新注册的服务实例，说明注册中心这条路也通了。启动过程中有一条无害的 WARN 可以忽略——Druid 提示 MySQL Driver 已弃用、建议改用 com.mysql.cj.jdbc.Driver，不影响启动。

第三处是反向验证：把服务停掉，观察服务列表的变化。实例不会立刻消失，因为 Nacos 要靠心跳判断存活，有一点延迟——先过一小段时间把它标记为不健康，再过一会儿才从注册表里彻底清除。看到「还在但不健康」到「消失」这个过程，说明对下线机制的理解和实际行为对上了。

最后把配置改回正式口径：课程环境里 tms 用户其实早就创建好了，也绑定了 Role-TMS 角色，之前报错缺的只是最后一步权限。到权限管理里给 Role-TMS 添加权限——资源选「品达-TMS」命名空间、动作选读写，然后 bootstrap-dev.yml 恢复成 tms/itheima123（注意用户名密码要与 Nacos 中预建用户完全一致），重新启动，服务再次注册成功。至此初始工程验收完成：POM、配置、启动类、注册中心、配置中心整条链路全部可用，第 2 章开始就能在这个工程上写真正的业务代码。

## 小结

- 初始工程验收以 pd-base 为样例：POM 已备好 nacos-discovery 与 nacos-config 两个 starter，包结构 com.itheima.pinda、bootstrap 双配置均已划分完成，开发阶段无需改动。
- 启动类三步走：@SpringBootApplication + @EnableDiscoveryClient + SpringApplication.run；端口 8185、应用名 pd-base、环境 dev。
- 配置中心按「应用名 + 环境」精确匹配：pd-base + dev 只读 pd-base-dev.yml，其余十几个配置文件不加载。
- Nacos 开启鉴权后，用户名密码必须同时满足三关：用户存在、密码一致、对命名空间有权限；报错特征是 NacosException 里的 no right / authorization failed / forbidden。
- 授权三步固定套路：用户列表创建用户 → 角色绑定 → 权限管理给角色授命名空间 rw 权限；正式环境用预建的 tms/itheima123，缺的就是给 Role-TMS 补权限这一步。
- 验收三处验证点：日志 Tomcat started on port 8185、服务列表出现实例、停服后实例先不健康再延迟清除。
