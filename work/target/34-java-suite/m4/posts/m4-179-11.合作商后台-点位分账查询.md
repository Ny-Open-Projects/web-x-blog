# 合作商后台点位分账查询：需求、代码实现与测试

在物联网新零售项目"立可得"中，合作商最关心的就是自己的点位每天卖了多少、能分到多少钱。第 7 章合作商分账结算里的这个小节，就把"合作商后台-点位分账查询"这个功能完整做一遍：先梳理需求与实现思路，再用 LambdaQueryWrapper 写完业务层与控制层，最后通过网关把两个接口测通。

## 先给结论

- 需求分两层：合作商工作台首页展示最近 12 条分账信息（某一天、某个点位产生的订单数与订单金额）；点击"更多"进入分页展示，支持按点位名称和日期范围查询。
- 数据不用重新聚合：订单汇总表 tb_order_collect 存的本身就是每个合作商、每个点位按天汇总的数据，直接查询即可。
- 业务层定义两个方法：getTop12 只按合作商 ID 过滤、返回 List；search 负责分页与条件过滤、返回 Pager 分页对象。
- 查询统一用 LambdaQueryWrapper：select 用双冒号方法引用指定字段，动态条件用 like / between，orderByDesc 按日期倒序，取前 12 条用 last("limit 12")。
- 测试前要启动用户微服务（合作商登录）、订单微服务（业务逻辑所在）和网关三个服务，测试脚本 partner.http 统一走网关 9007 端口。
- 登录依赖图形验证码：先调验证码接口，把识别出的验证码填进登录请求，再用返回的 token 替换脚本变量，之后逐个验证两个接口。

## 需求与实现思路：直接查汇总表

合作商后台的首页就是工作台，上面要展示最近 12 条分账信息。每一条分账信息都区分到点位维度：某一天、某个点位产生的订单数是多少，订单金额是多少。界面上以卡片形式呈现，每张卡片包含日期、分账金额、分账比例和业务类型。

最近 12 条显然是不完整的，所以界面上还有一个"更多"入口。点击更多之后进入分页展示，并且可以按点位名称和日期范围来查询。对应到接口文档，就是分账管理下的两个 API：合作商获取最近 12 条分账信息，以及合作商分账信息查询。

实现思路上没有花活。这些信息刚好就是订单汇总表 tb_order_collect 里存的数据：这张表存的本身就是每个合作商、每个点位的按天汇总数据，所以直接查询就行，不需要再做一次聚合。

## 代码实现：两个业务方法加两个接口

### 业务层：getTop12 与 search

在 ReportService 接口中定义两个方法。为什么是两个？第一个用来获取合作商前 12 条点位分账数据，对应首页的固定展示，参数只需要合作商 ID，返回 List；第二个对应"更多"里的分页搜索，需要传页码、页大小、合作商 ID、点位名称、开始时间和结束时间，返回 Pager 分页对象。

```java
List<OrderCollectEntity> getTop12(Integer partnerId);

Pager<OrderCollectEntity> search(Long pageIndex, Long pageSize,
                                 Integer partnerId, String nodeName,
                                 LocalDate start, LocalDate end);
```

实现 getTop12 时，这次不用一直用的 QueryWrapper，而是换成 LambdaQueryWrapper。原因在 select 子句：指定查询字段时要用方法引用的特殊写法，lambda 方式可以直接访问实体的 getter，不用手写字符串列名。

```java
@Override
public List<OrderCollectEntity> getTop12(Integer partnerId) {
    var qw = new LambdaQueryWrapper<OrderCollectEntity>();
    qw.select(OrderCollectEntity::getDate,
              OrderCollectEntity::getNodeName,
              OrderCollectEntity::getOrderCount,
              OrderCollectEntity::getTotalBill);
    qw.eq(OrderCollectEntity::getPartnerId, partnerId);
    qw.orderByDesc(OrderCollectEntity::getDate);
    qw.last("limit 12");
    return orderCollectService.list(qw);
}
```

select 里取四个字段：日期、点位名称、订单数量和分成金额 totalBill。条件只有一个 eq，按传进来的合作商 ID 过滤；再根据日期倒序排列；最后用 last 方法在 SQL 末尾拼上 limit 12，拿到的就是最近 12 条。

search 方法的第一步同样是构建 LambdaQueryWrapper，select 子句和合作商 ID 条件与 getTop12 完全一致，可以直接复用写法，之后再加上两组动态条件：

```java
if (Strings.isNotBlank(nodeName)) {
    qw.like(OrderCollectEntity::getNodeName, nodeName);
}
if (start != null && end != null) {
    qw.between(OrderCollectEntity::getDate, start, end);
}
qw.orderByDesc(OrderCollectEntity::getDate);
```

点位名称不为空就加 like 模糊匹配；开始和结束时间都不为空就加 between 日期范围。最后返回 Pager 对象，分页参数用配置里的 pageIndex 和 pageSize，参照项目里已经写好的分页方法构建即可。

### 控制层：按 API 文档定义参数

Controller 的两个方法就是分别调用这两个业务方法，按照上面两个 API 文档来定义参数：路径参数用 @PathVariable 接收合作商 ID，查询条件用 @RequestParam 接收页码、页大小、点位名称和起止日期，日期字符串通过 @DateTimeFormat(pattern = "yyyy-MM-dd") 转成 LocalDate。

```java
@GetMapping("/search/{partnerId}")
public Pager<OrderCollectEntity> search(
        @PathVariable Integer partnerId,
        @RequestParam("page_index") Long pageIndex,
        @RequestParam("page_size") Long pageSize,
        @RequestParam("node_name") String nodeName,
        @RequestParam("start") @DateTimeFormat(pattern = "yyyy-MM-dd") LocalDate start,
        @RequestParam("end") @DateTimeFormat(pattern = "yyyy-MM-dd") LocalDate end) {
    return reportService.search(pageIndex, pageSize, partnerId, nodeName, start, end);
}
```

## 测试：三个服务加一份 HTTP 脚本

代码完成后开始测试。先启动三个微服务：用户微服务要先跑起来，因为测试前得先完成合作商登录；订单微服务必须启动，刚写的逻辑就封装在里面；网关也要跑，因为测试脚本是基于网关来访问的。

测试脚本在 partner.http 中，所有合作商相关的请求都集中在这个文件里，统一走网关的 9007 端口。测试流程分三步：

1. 获取图形验证码。合作商登录需要图形验证码，先调用验证码接口，这次返回的验证码是 7xwc。
2. 登录拿 token。把 7xwc 填到登录请求的 code 位置，clientToken 与获取验证码时传的编号保持一致，执行登录后把响应里的 token 复制出来——注意不要把引号带过去——替换脚本里的 token 变量。
3. 依次执行两个接口：获取最近 12 条分账信息，以及分账信息的分页搜索。

当前数据库里只有一条汇总记录，所以第一个接口查出来的结果也只有一条；第二个接口以分页形式返回，能看到分页结构。两个接口都能正常执行，说明业务逻辑和接口定义没有问题，这个功能就算完成了。

## 小结

点位分账查询是合作商后台里典型的"汇总表直查"场景：需求上区分首页固定 12 条和"更多"分页搜索两层，实现上落在 ReportService 的 getTop12 和 search 两个方法里。用 LambdaQueryWrapper 加方法引用写 select，可选条件用 like 和 between 兜住，last("limit 12") 解决取前 N 条的问题。测试环节按"用户服务-订单服务-网关"的顺序起服务，用 partner.http 脚本先登录再逐个打接口。这套流程走完，合作商在自己的后台就能看到每个点位每天的分账明细了。
