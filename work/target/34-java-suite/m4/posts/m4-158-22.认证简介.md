# EMQ 认证体系与 ACL 访问控制：HTTP 认证配置、认证服务开发与授权接口实战

前一篇的所有演示都建立在一个前提上：随便填个 Client ID 就能连上 EMQX——那是匿名认证在兜底。本篇先补上 EMQX 的产品背景，再把安全这一层讲透：认证管"能不能连上来"，ACL 管"连上来之后能发布订阅什么"。两者的最终形态都是走 HTTP 插件，把认证和授权逻辑完全交给自己写的代码，立可得项目采用的正是这种方式。

## 先给结论

- EMQX 是 MQTT broker（早期叫 EMQ，后改名 EMQX，习惯简称 EMQ，两者一回事），国产软件；分开源版（单节点十万级连接）、企业版（百万级）、电信级（千万级），功能是增量关系，学习用开源版完全够用
- 认证方式三类：内置数据源（Username/Client ID，官方即将废弃）、外部数据库（MySQL/PostgreSQL/Redis/MongoDB/LDAP）、HTTP 与 JWT；认证方式不宜开太多，越多认证效率越低；HTTP 认证最灵活，逻辑用代码写，复杂场景都能兜住
- 认证结果三值：成功、失败、忽略（ignore）；多个认证方式组成认证链，拿到明确结果即终止，全程忽略最后落到 emqx.conf 的 allow_anonymous（默认 true，生产环境应改 false）
- HTTP 认证用 emqx_auth_http 插件，状态码约定：4xx 失败、200 成功、200 且响应体为 ignore 忽略；认证地址、方法、参数都在 etc/plugins/emqx_auth_http.conf 里配；EMQX 在虚拟机容器里，127.0.0.1 指向虚拟机自身，认证服务地址要写宿主机 200 网段 IP（192.168.200.1）
- ACL 是认证之后的发布/订阅权限控制，ACL 插件与认证插件是同一个；授权结果为允许/禁止/忽略，未匹配时的默认授权由 acl_nomatch 控制（默认 allow，生产环境改 deny）
- HTTP ACL 同一插件三段配置：auth_req 认证、super_req 超级用户、acl_req 授权；`%A` 表示操作类型（1 订阅、2 发布）；超级用户跳过一切 ACL 检查，相当于免死金牌

## 一、先认识 EMQX 本身

MQTT 协议有三种角色：消息的发布者、订阅者，以及消息的代理（broker）。EMQX 就是 MQTT 协议的一种消息服务器，也就是 broker。它早期叫 EMQ，后期改名 EMQX，现在大家习惯简称 EMQ，两种叫法是一回事。

它是国产软件，官网 emqx.io。产品线除了付费即可用的 Cloud 云平台，核心是三个版本：开源版 Broker、企业版、电信级 Platform。功能对比是增量关系——开源版的功能在企业版里都有，电信级又比企业版更强：

| 版本 | 连接规模 | 亮点 |
| :--- | :--- | :--- |
| 开源版 Broker | 单节点十万级 | 完全开源（Apache 2.0）、MQTT 5.0、分布式集群高并发低时延、扩展模块插件、跨平台 |
| 企业版 | 百万级 | 多物联网协议支持、强大规则引擎、消息数据存储、监控管理 |
| 电信级 | 千万级 | 电信级高可靠、跨多数据中心、超大规模集群、定制集成服务 |

选它的理由也充足：版本迭代快，一百多个版本，开源消息服务器里最活跃；性能好——基于 Erlang/OTP 平台（RabbitMQ 同款语言），软实时、高并发、容错，连接、会话、路由、集群分层设计，消息平面与控制平面分离，毫秒级响应；支持协议多，除 MQTT 外还有基于 UDP 的 MQTT-SN、CoAP、LwM2M、LoRaWAN、WebSocket；安装方式全（Shell 脚本、包管理器、二进制包、ZIP、Homebrew、Docker）；插件可随开关启停，扩展性强；国产软件，技术支持方便。企业版还支持桥接，可以把消息转发到 Kafka、RabbitMQ 或其他 EMQ 节点，共享订阅这种负载均衡机制也在其特性清单里（上一篇已专门讲过）。课程使用开源版，学习完全够用。

## 二、认证：从匿名登录到认证链

### 三类认证方式

认证就是身份验证。之前的测试里只指定一个 Client ID 就连上了，这是最宽松的方式——匿名认证。生产环境肯定不能这么干：客户端连接时必须判断它是不是合法客户端，连不上，后面的发布订阅就都免谈。

EMQX 支持的认证方式分三类：

- **内置数据源**：Username 认证、Client ID 认证，靠配置文件维护账号。官方后续版本要废弃它，配置写死在文件里极不灵活，实际也很少用，不必花时间
- **外部数据库**：LDAP、MySQL、PostgreSQL、Redis、MongoDB。库里存合法的 Client ID 或用户名，认证时执行查询语句比对。比内置方式灵活实用，方便和外部系统集成
- **HTTP 与 JWT**：JWT 和微服务里常见的一样，签发 token 验证；HTTP 认证是目前用得最多的——不管认证逻辑多复杂，都能用代码实现，其他方式搞不定的复杂逻辑它都能兜住。立可得项目就用 HTTP 认证

一个原则：认证方式不需要开太多，启动的认证方式越多，认证效率越低。每一种认证都是一个插件。

### 认证结果与认证链

不管哪种认证，都返回三种结果之一：

- **认证成功**：客户端合法，允许连接
- **认证失败**：客户端非法，连接被拒
- **忽略（ignore）**：模棱两可——该认证方式里没找到匹配的认证数据，无法判断成败，交给认证链的下一个认证方式

同时开启多个认证方式（比如 Username + MySQL + HTTP）就形成认证链，按顺序逐个走：某个方式返回成功或失败，链条立即终止；返回 ignore 就问下一个。如果整条链全部返回 ignore，最终由默认配置决定——etc/emqx.conf 里的 `allow_anonymous`，默认 true，即允许这些"无法判定"的客户端连接（之前一个 Client ID 就能连上，正是这个默认值在起作用）；改成 false 后，认证链走完仍无明确结果的客户端一律拒绝。

## 三、HTTP 认证：配置插件与开发认证服务

### 插件与配置

HTTP 认证由 emqx_auth_http 插件控制，插件默认 Stopped，在 Dashboard 的 Plugins 页点 start 开启。每个插件对应一个配置文件：进容器到 etc/plugins/ 目录（每个 conf 对应一个插件），打开 emqx_auth_http.conf，认证请求（authentication request）有三条关键配置：

```ini
# 认证请求地址：改成自己写的 Controller 地址
auth.http.auth_req = http://192.168.200.1:8991/mqtt/auth
# 请求方式：post | get | put，建议 post，相对安全
auth.http.auth_req.method = post
# 请求参数：要传什么自己加
auth.http.auth_req.params = client_id=%c,username=%u,password=%P
```

参数里的占位符：`%c` 是 Client ID，`%u` 是 username，`%P` 是 password（注意大写 P），此外还有 `%a`（客户端来源 IP）等。配置里传什么，Controller 里就接收什么。

EMQX 怎么判定认证结果？看你的服务返回的 HTTP 状态码：

| 你的服务返回 | EMQX 判定 |
| :--- | :--- |
| 4xx 状态码（401、404 等） | 认证失败 |
| 200 | 认证成功 |
| 200 且响应体为 ignore | 忽略认证，交给认证链下一个 |

### 认证服务：一个 Spring Boot Demo

配置里的地址要自己实现。提前准备的 demo 是个 Spring Boot 工程，端口 8991，只有一个 Controller，应用路径 /mqtt。私有成员变量是个 HashMap<String, String>——合法用户列表，键是用户名，值是密码；@PostConstruct 的 init 方法在启动后自动向里面添加几个合法用户，密码都是 123456，其中包含 admin。实际项目中这些数据不应写死，应该从数据库读取，demo 从简。

认证方法逻辑：

```java
@PostMapping("/auth")
public ResponseEntity<?> auth(@RequestParam("clientid") String clientid,
                              @RequestParam("username") String username,
                              @RequestParam("password") String password) {
    // users：@PostConstruct 预置的合法用户表
    String pwd = users.get(username);
    if (pwd == null || !pwd.equals(password)) {
        // 用户名不存在，或密码不符
        return new ResponseEntity<>(HttpStatus.UNAUTHORIZED); // 401
    }
    return new ResponseEntity<>(HttpStatus.OK);               // 200
}
```

### 关键：地址不能写 127.0.0.1

配置文件里默认示例是 `http://127.0.0.1:8991/mqtt/auth`，直接照抄是错的：EMQX 跑在虚拟机的 Docker 容器里，127.0.0.1 指向虚拟机自身，不是运行着认证服务的 Windows 宿主机。正确做法是在 Windows 上 ipconfig 查看 200 网段的地址（虚拟机在 200 网段），填 `192.168.200.1:8991`。路径名也不必和示例一样，写什么都行，两边对齐即可。

### 联调测试

改完配置保存，在 Plugins 页把插件停掉再开启使其生效，认证服务跑起来，然后用 WebSocket 工具测：

- 用户名密码随便填或不填 → 连不上；服务端控制台有请求日志输出，证明请求确实打到了认证方法
- 输入合法用户名和密码 123456 → 连接成功
- 用户名存在但密码错误 → 依然连不上
- 认证服务停掉再连 → 即使用户名密码全对，也连不上——找不到认证地址，认证无法完成

这就是 HTTP 认证的完整闭环：连接逻辑完全由自己的代码说了算。

## 四、ACL：认证之后的权限控制

ACL 是权限控制。认证相当于登录，控制客户端能不能连上 EMQX；ACL 是认证之后的事——能登录不代表能做任何事，发布某个主题、订阅某个主题都要受权限限制，否则一登录就为所欲为，同样不安全。认证和 ACL 分不开。

ACL 插件和认证插件是同一个：配置文件方式（内置 ACL，etc/acl.conf，适合变动较小的管理）、外部数据库（MySQL、PostgreSQL、Redis、MongoDB，适合大量数据、动态管理、与设备管理系统集成）、HTTP ACL（能实现最复杂的 ACL 管理）。改了配置要重启插件才生效；同时只启用一个 ACL 插件，能提高客户端 ACL 检查性能。

授权结果同样三个：**允许**、**禁止**、**忽略**（无法判断时交给下一个 ACL 插件）。所有插件都返回忽略时，落到默认配置——etc/emqx.conf 的：

```ini
# ACL 未匹配时默认授权
# Value: allow | deny
acl_nomatch = allow
```

默认 allow：没开启任何 ACL 插件或全部忽略时，操作放行。生产环境要改成 deny——全部无法判定就拒绝，整个环境更安全。改完同样要 `emqx restart` 才生效。这条链路的逻辑和认证链一模一样，一通过即允许，一失败即禁止，全程忽略看默认配置。

还有一个概念：**超级用户**。它拥有所有权限、不受控制，相当于 VIP 门票：认证通过超级用户判断规则的客户端，后续的 ACL 检查全部跳过。

## 五、HTTP ACL：配置与授权接口开发

### 三段请求配置

HTTP ACL 由 emqx_auth_http 插件支持（与 HTTP 认证同一个插件），同样通过响应状态码判定：无权限返回 4xx，授权成功返回 200，忽略授权返回 200 且响应体为 ignore。

配置文件里认证相关共三段：

```ini
# 认证请求（前文已配）
auth.http.auth_req = http://192.168.200.1:8991/mqtt/auth

# 超级用户请求：判定通过即为超级用户，跳过 ACL
auth.http.super_req = http://192.168.200.1:8991/mqtt/superuser
auth.http.super_req.method = post
auth.http.super_req.params = clientid=%c,username=%u

# ACL 请求：发布/订阅时的权限判断
auth.http.acl_req = http://192.168.200.1:8991/mqtt/acl
auth.http.acl_req.method = post
auth.http.acl_req.params = access=%A,username=%u,clientid=%c,ipaddr=%i,topic=%t,mountpoint=%m
```

ACL 请求参数里多了一个关键的 `%A`（大写 A）：表示这次是什么操作，值为 1 是订阅，值为 2 是发布；`%t` 是目标主题。你的服务就根据用户身份、主题和操作类型来放行或拒绝。

### 超级用户接口与 ACL 接口

还是那个 demo，Controller 里新增两个方法。超级用户判断：Client ID 或用户名包含 admin 就算超级用户，返回 200，否则 401：

```java
@PostMapping("/superuser")
public ResponseEntity<?> superuser(@RequestParam("clientid") String clientid,
                                   @RequestParam("username") String username) {
    if (clientid.contains("admin") || username.contains("admin")) {
        return new ResponseEntity<>(HttpStatus.OK);        // 是超级用户
    }
    return new ResponseEntity<>(HttpStatus.UNAUTHORIZED);   // 不是
}
```

ACL 接口按身份和主题精细化控制——emq-client1 只允许订阅 testtopic/#（access=1），emq-client2 只允许发布 testtopic/123（access=2），其余一律拒绝：

```java
@PostMapping("/acl")
public ResponseEntity<?> acl(@RequestParam("access") int access,
                             @RequestParam("username") String username,
                             @RequestParam("clientId") String clientId,
                             @RequestParam("ipaddr") String ipaddr,
                             @RequestParam("topic") String topic,
                             @RequestParam("mountpoint") String mountpoint) {
    if (username.equals("emq-client1") && topic.equals("testtopic/#") && access == 1) {
        return new ResponseEntity<>(HttpStatus.OK);         // 允许订阅
    }
    if (username.equals("emq-client2") && topic.equals("testtopic/123") && access == 2) {
        return new ResponseEntity<>(HttpStatus.OK);         // 允许发布
    }
    return new ResponseEntity<>(HttpStatus.UNAUTHORIZED);   // 其余拒绝
}
```

前提注意：这两个方法都要先通过认证才会被调到——认证没通过，根本走不到超级用户和 ACL 判断。

改配置：super_req 与 acl_req 的地址都改成 `192.168.200.1:8991/mqtt/...`；acl_req 配置文件里默认是 get，demo 接口是 post，要把 get 改成 post。保存后把插件停掉再开启，让新配置生效。

### 权限验证演示

服务跑起来后用 WebSocket 工具分角色测试：

- **admin 连接**：认证通过，日志输出"用户 admin 是超级用户"。随后随便订阅、随便发布，认证服务的控制台毫无输出——超级用户根本不走 ACL 方法，畅通无阻
- **user 连接**（合法普通用户）：日志输出"user 不是超级用户"。随便找个主题发布，WebSocket 页面显示"已发送"——但用另一个 admin 连接订阅同一主题却收不到任何消息。界面上的"已发送"只是本地记录，消息实际被 ACL 拦下了
- **有订阅权限的账号**：订阅 testtopic/# 成功（access=1 命中规则）
- **无发布权限的账号**：向 testtopic/aa 发布，看着成功了，订阅了 testtopic/# 的连接却收不到——权限不匹配，实际没发出去
- **有发布权限的账号**：向 testtopic/123 发布，订阅了 testtopic/# 的连接立刻收到（通配符匹配上了）

实际项目里当然不会这样硬编码，权限要从数据库、缓存里查，逻辑会复杂得多；demo 的写法只为把 ACL 的判定流程演示清楚。

## 小结

这一篇把 EMQX 的安全层补齐了。产品面：开源版、企业版、电信级是增量关系，课程与立可得项目都基于开源版。安全面是两道关卡加一条兜底规则：认证（登录）决定能不能连，ACL（授权）决定连上后能发布订阅什么，两道关卡都支持认证链/鉴权链式的多插件串联，拿不到明确结果时分别落到 allow_anonymous 和 acl_nomatch 这两个默认配置上。落地手段统一选 HTTP 插件 emqx_auth_http——认证、超级用户、ACL 三段配置指向自己写的三个接口，状态码就是协议：4xx 拒绝、200 放行、200 加 ignore 交给下一环。记住那个易错点：EMQX 在虚拟机容器里，回调地址要写宿主机网段 IP 而不是 127.0.0.1。
