# 收益统计趋势图：需求思路、曲线图封装类、代码实现与测试

合作商后台要回答一个很直接的问题：指定时间段里，我每天的收益是怎么变化的，哪天高、哪天低？本篇是第七章合作商分账结算的收束功能——用 ECharts 曲线图把收益趋势画出来。后端要做的事是从订单合并表按天聚合出每日收益，组装成前端图表需要的数据结构，经网关联调验证返回结果。

## 先给结论

- 前端选型 ECharts，图表本质只需要两组数据：X 轴日期序列 + 折线数值序列，两个 data 的元素个数必须一一对应
- 后端只返回 xAxis 和 series 两个数组，不返回整体 option 格式，前端自行组装更灵活
- 封装类 BarChartCollect 放在 service-common 的 viewmodel 包下，属性名第二个字母是大写（xAxis），JSON 序列化后会变小写，用 @JsonProperty 指定输出名解决
- 数据源是订单合并表：IFNULL(sum(total_bill), 0) 聚合，按日期 groupBy，条件是日期区间加 ownerId 等于合作商 ID
- 没数据的日子用 0 填充：JDK9 的 datesUntil 构建完整日期序列，逐日到 map 里取值，取不到补 0
- 测试经网关访问，partner.http 返回 19 日到 25 日的时间序列，167 是库中真实数据，其余 0 是填充值

## 一、需求与思路：把每天的收益画成一条线

需求本身不复杂：在合作商后台统计一个时间段内该合作商的收益趋势。指定一个时间段后，这期间每天的收益变化——哪一天高、哪一天低——通过一条曲线就可以非常直观地展现出来。前端图表工具很多，立可得采用的是 ECharts，具体用法可以参照 ECharts 官网（echarts.apache.org）的示例。

实现思路三步。第一步，构建一个用于封装 ECharts 曲线图的实体类——曲线图要接收一组数据，先通过官网示例确认这组数据是什么格式，再根据格式来定义实体。第二步，对订单合并表做聚合查询——订单合并表记录着每一个合作商每一个点位的信息，而这个需求不需要区分点位，要把每一天所有点位的数据汇总起来，所以必须聚合。第三步，查询出每天的收益之后，转换成曲线图实体类的数据返回给前端。

## 二、封装 BarChartCollect：两个数组与 @JsonProperty

先看前端要什么。通过阅读 ECharts 官网示例，折线图（柱状图同理）的数据格式分三块：xAxis、yAxis 和 series。重点在两个 data：xAxis 的 data 是 X 轴上每一个点的名称，在这里显示成日期；series 里那条折线的构成数据也通过 data 指定。要注意的是，X 轴的 data 和曲线的 data 元素个数必须相同——一个横轴刻度对应一个数值：

```json
{
  "xAxis": { "type": "category", "data": ["Mon", "Tue", "Wed", "Thu", "Fri", "Sat", "Sun"] },
  "yAxis": { "type": "value" },
  "series": [ { "data": [150, 230, 224, 218, 135, 147, 260], "type": "line" } ]
}
```

据此定义 API：GET 请求 /order-service/report/collectReport/{partnerId}/{start}/{end}，传入三个参数——合作商 ID、开始日期、截止日期。返回数据只有两个属性：xAxis 是日期数据，series 是 Y 轴数值。只返回这两个 data 部分，不返回整体的 ECharts 格式——前端拿到两个数组后可以自己构建完整的 option，这样设计相对更灵活。

实体类建在哪有讲究：放在 service-common 的 viewmodel 包下更合适，因为其他微服务也可能有统计的需要，或者生成折线图、柱状图的需要。折线图、柱状图、曲线图的数据结构一致，建一个类就能通用。类实现 Serializable，加 @Data 注解，两个属性都在声明时直接实例化：

```java
@Data
public class BarChartCollect implements Serializable {
    @JsonProperty("xAxis")
    private List<String> xAxisList = Lists.newArrayList();
    @JsonProperty("series")
    private List<Integer> seriesList = Lists.newArrayList();
}
```

这里有一个容易踩的坑。属性名 xAxisList 中包含大写字母，而且这个大写字母处在第二个位置——属性名序列化成 JSON 后会全部变成小写（xaxislist），而 API 文档的设计里要求的是 xAxis 这样的大写形式，转出来的 JSON 和前端要的名称对不上，显然不符合要求。解决办法是借助 @JsonProperty 注解，它专门用于指定属性最终转换的名称，让输出与 API 文档保持一致。

## 三、聚合查询与补零填充：getCollect 的实现

打开订单微服务，在 ReportService 中定义方法：返回值就是刚构建的 BarChartCollect，方法名 getCollect，参数参照 API 文档——合作商 ID、开始日期、截止日期，含义是获取一定日期内合作商的收益。

实现类里的查询用 QueryWrapper 构建。select 指定两列：第一列是聚合字段 IFNULL(sum(total_bill), 0) as total_bill——对 totalBill 求和，如果返回 null（区间内一条数据都没有）就指定为 0，取别名 total_bill；第二列是 date，两列的顺序可以颠倒。条件部分用 lambda 写三个：ge 日期大于等于开始日期、le 日期小于等于截止日期、eq ownerId 等于合作商 ID；最后 groupBy 按日期分组，一天一行：

```java
public BarChartCollect getCollect(Integer partnerId, LocalDate start, LocalDate end) {
    var qw = new QueryWrapper<OrderCollectEntity>();
    qw.select("IFNULL(sum(total_bill), 0) as total_bill", "date")
      .lambda()
      .ge(OrderCollectEntity::getDate, start)
      .le(OrderCollectEntity::getDate, end)
      .eq(OrderCollectEntity::getOwnerId, partnerId)
      .groupBy(OrderCollectEntity::getDate);
    var mapCollect = orderCollectService.list(qw).stream()
        .collect(Collectors.toMap(OrderCollectEntity::getDate, OrderCollectEntity::getTotalBill));
    var result = new BarChartCollect();
    start.datesUntil(end.plusDays(1), Period.ofDays(1)).forEach(date -> {
        result.getXAxisList().add(date.format(DateTimeFormatter.ISO_LOCAL_DATE));
        if (mapCollect.containsKey(date)) {
            result.getSeriesList().add(mapCollect.get(date));
        } else {
            result.getSeriesList().add(0);
        }
    });
    return result;
}
```

查询结果是一个 OrderCollectEntity 的 List，前端显然不能直接用，要转换成前端可以直接使用的格式，这里分两步走。第一步，把 List 转成一个 Map：以 date 作为 key、收益值作为 value，用 stream 的 collect(Collectors.toMap(...)) 完成，得到 mapCollect。第二步，构建返回对象 result，先构建一个从开始时间到截止时间的时间序列，再根据这个序列到 map 中去找值。

为什么不直接把查询结果排下去？因为有时候某一天是没有数据的：比如 17 日有数据、18 日 19 日都空着、20 日又有数据，这种情况下返回来的应该是 17、18、19、20 都有数——map 里不存在的日期要给它一个 0 做填充，必须保证有多少个横轴数据就有多少个曲线数据，一一对应。

时间序列用 JDK9 提供的 datesUntil 方法构建，原来手工做这件事挺麻烦，这个方法非常好用：传入 end.plusDays(1)——截止日期的后一天（datesUntil 含头不含尾），再用 Period.ofDays(1) 指定步长，产生的序列就是一天一个元素。循环里先构建 X 轴：因为构建实体类时属性已经实例化过，不是 null，直接 add；日期是 LocalDate 类型，要转成字符串，用 DateTimeFormatter.ISO_LOCAL_DATE 格式化。然后判断 map 中有没有这一天的数据：有就直接把值加进 seriesList，没有就加 0 占位，最后返回 result。

Controller 参照 API 文档构建，ReportController 新增一个方法，路径 /collectReport/{partnerId}/{start}/{end}，@PathVariable 接收三个路径参数，日期字符串用 @DateTimeFormat(pattern = "yyyy-MM-dd") 转成 LocalDate，方法体一行调用服务层：

```java
@GetMapping("/collectReport/{partnerId}/{start}/{end}")
public BarChartCollect getCollectReport(@PathVariable Integer partnerId,
        @PathVariable @DateTimeFormat(pattern = "yyyy-MM-dd") LocalDate start,
        @PathVariable @DateTimeFormat(pattern = "yyyy-MM-dd") LocalDate end) {
    return reportService.getCollect(partnerId, start, end);
}
```

## 四、联调测试：19 日到 25 日的曲线数据

测试的启动顺序：先启动订单微服务，再启动微服务网关——测试是通过网关进行访问的，这两个跑起来就可以。打开 partner.http 测试脚本，其中有一条"获取合作商一定日期范围的收益情况"，地址就是刚写的方法路径：路径参数 1 是合作商 ID，后面跟时间段。

请求发出，数据拿到，返回分两块看：下面的部分是 xAxis，是从 19 日到 25 日的时间序列，也就是 X 轴要显示的数据；上面的部分是折线数据。series 里很多 0——那些就是被填充的；其中有一个 167，这是数据库中已经存在的这条数据。返回结果再对照订单合并表里的实际记录核对，数值一致，收益统计趋势图的测试就完成了。

到这里，合作商分账结算一章的功能线也收束了：从创建订单时算出分成金额落库，到分账查询把账目查出来，再到本篇把每天的收益画成趋势曲线，合作商侧"算钱、对账、看趋势"的链路走通。

## 小结

把本篇串起来：需求是合作商后台的时间段收益曲线，前端用 ECharts 展示；图表格式决定后端契约——只返回 xAxis 与 series 两个数组，前端自行组装 option；封装类 BarChartCollect 建在 service-common 的 viewmodel 包，用 @JsonProperty 解决属性名第二个字母大写导致 JSON 键变小写的问题；数据层对订单合并表聚合查询——IFNULL(sum(total_bill), 0) 按日期分组，条件为日期区间加合作商 ID；组装时先 stream 转 Map，再用 JDK9 的 datesUntil 构建完整日期序列逐日取值，缺数据的日期补 0，保证横轴与数值一一对应；最后经网关用 partner.http 验证，序列完整、真实数据 167 与填充 0 并存。一个小功能，把聚合 SQL、Stream 收集、日期序列、JSON 序列化四个点串在了一条链上。
