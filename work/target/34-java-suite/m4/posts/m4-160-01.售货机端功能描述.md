# 售货机端功能描述、技术方案与数据库表结构设计

之前的章节都在服务端打转，第九章"售货机'五脏六腑'深度剖析"把镜头转向机器本身：售货机里面跑着什么、它和服务端怎么配合、数据存在哪。本篇覆盖开篇三节——功能描述、技术方案、数据库表结构设计，先把这台机器的骨架看清楚，后续的 EMQ 安全、H2 数据库、工程搭建与数据同步都建立在这三节之上。

## 先给结论

- 售货机端也是一个微服务，但不部署在服务器里，而是部署在每一台售货机之中；它没有操作界面，可以理解成一个逻辑运算的内核
- 三个功能：与服务端数据同步、出货（最核心）、补货（本质也是一次数据同步）；出货链路是服务器端向 EMQ 发出货指令就到此为止，售货机端订阅到消息后更新本地库存、调用硬件接口出货（涉及串口编程），成功后向服务器上报出货结果
- 操作系统选安卓：售货机端本身是一台电脑，安卓在软硬件上都是最低成本的选择；早期也用 Windows，造价非常高
- 技术栈五件套：Spring Boot 作框架（功能简单，不需要 Spring Cloud）、Aid Learning 作运行平台（一个可以运行在安卓系统中的 Linux 系统，Spring Boot 工程由此得以上去）、H2 嵌入式数据库存本地数据（MySQL 太重，终端越轻量越好）、paho 订阅发布 EMQX 消息、串口对接硬件（课程不展开：没有硬件设备做测试，也不作为学习方向）
- 本地库四张表：商品表 tb_sku、货道表 tb_channel、版本信息表 tb_version、出货记录表 tb_vendout_order
- 版本表拆出货道、商品、商品价格三个版本号，便于每次同步后与服务器端核对；价格版本独立，因为商品基本信息稳定、价格会随打折等策略变化，同步时可能只更新价格版本；出货结果编号共六种：0 成功、1 货道售空、2 设备故障、3 机器出货中、4 连续支付、5 服务器超时

## 一、售货机端：一个没有界面的微服务

功能描述开门见山：售货机端同样也是一个微服务，只不过它不部署在服务器之中，而是部署在每一个售货机之中。

盘点它的功能，一共三个。

第一，与服务端进行数据同步。服务器端要管理商品、货道这类数据，售货机端自己也存一套——因为售货机端本身要做逻辑运算，也需要数据；如果每次都从服务器抓取，效率非常低。所以它本地存了一套与终端运算相关的数据，比如商品、货道、价格等，这就引出数据要与服务器端同步的问题。

第二，出货，售货机最核心的功能。之前讲购物流程时说过服务器端做的事：向 EMQ 发一条出货指令，到此为止。但 EMQ 的消息最终被谁接收？就是售货机端。它拿到消息后执行真正的出货逻辑：接到指令，更新本地库存，调用硬件接口出货——这一步涉及串口编程——成功之后再向服务器上报出货结果。

第三，补货。补货其实也是一种数据同步：补货成功之后要更新本地的库存数据。更新动作同样由服务器端发起一条 EMQ 消息，售货机端订阅到消息后修改本地库存数字。

最后是它和"某某端"家族最大的不同：一般叫"端"的东西都有界面，售货机端没有界面，可以把它想成只是一个内核，一个做逻辑运算的内核。

本章的学习目标有两条：完成售货机和服务端数据同步、价格变动、出货、补货等业务开发；掌握售货机宕机等特殊业务场景的处理。

## 二、技术方案：让 Spring Boot 跑进售货机

讲技术方案前先回答一个问题：售货机端怎么会有操作系统？因为它本身是一台电脑，应用都部署在这台电脑上，电脑底层需要操作系统做支撑。售货机端一般采用安卓系统，最大的好处是节约成本——不管硬件还是软件，安卓都是最低成本的选择。早期售货机端也有用 Windows 的，但造价非常高。

操作系统定了，往下是五个技术点。

Spring Boot 作框架。前面说过，售货机端就是一个微服务、一个内核。既然是微服务，Spring Boot 是首选；它的功能相对简单，不需要用到 Spring Cloud。

Aid Learning 作运行平台。Spring Boot 工程能不能直接部署到安卓系统上？不能，要借助一个软件：Aid Learning。它是一个可以部署在安卓系统里的 Linux 系统——安卓里有了 Linux，Spring Boot 开发的工程就能部署到这个 Linux 之上，事情就简单了。

H2 存本地数据。之前开发的系统大多用 MySQL，但 MySQL 相对重，终端设备越轻量越好。所以选 H2——一种嵌入式数据库，体积小、运行内存占用非常少，大多数物联网终端采用这类数据库的比较多（后面会有详细介绍）。售货机的商品、货道、出货记录等本地数据都交给它。

paho 对接 EMQX。用 paho 订阅和发布 EMQX 消息，这就实现了与服务端的交互——功能盘点里的同步、出货、补货，消息通道都从这里走。

串口对接硬件。与硬件设备交互可以使用串口。这部分课程不讲解：一是没有硬件设备做测试，二是它不作为学习方向，不是今后工作要做的事情，简单了解即可。

## 三、本地数据库：四张表撑起终端业务

售货机端的表数量不多，一共四张：商品表存商品信息，货道表存货道信息，版本信息表记录同步版本，出货记录表记录每次出货的相关信息。

### 商品表 tb_sku

| 字段名 | 类型 | 长度 | 描述 |
| :--- | :--- | :--- | :--- |
| sku_id | VARCHAR | 64 | 商品ID |
| sku_name | VARCHAR | 64 | 商品名称 |
| image | VARCHAR | 64 | 图片地址 |
| price | int | 11 | 商品原价 |
| real_price | int | 11 | 商品真实售价 |
| class_id | int | 11 | 商品类别ID |
| class_name | VARCHAR | 64 | 商品类别名称 |
| discount | int | 1 | 是否打折 |
| unit | VARCHAR | 32 | 商品净含量 |
| index | int | 11 | 商品排序索引 |

### 货道表 tb_channel

| 字段名 | 类型 | 长度 | 描述 |
| :--- | :--- | :--- | :--- |
| channel_id | VARCHAR | 64 | 货道ID |
| sku_id | VARCHAR | 64 | 商品ID |
| capacity | int | 11 | 库存 |

货道表记录每个货道放置哪个商品、最后剩余多少库存。这个库存数主要用于出货：出货时要根据这张表的库存数来选择从哪一个货道出货。

### 版本信息表 tb_version

| 字段名 | 类型 | 长度 | 描述 |
| :--- | :--- | :--- | :--- |
| version_id | int | 11 | 版本ID（主键） |
| channel_version | int | 11 | 货道版本 |
| sku_version | int | 11 | 商品版本 |
| sku_price_version | int | 11 | 商品价格版本 |

每次与服务器端同步，都要区分是哪一次同步，所以要做版本记录，便于与服务器端核对。表里是三个版本号：货道版本对应同步的货道数据，商品版本对应商品数据，商品价格版本则和商品独立出来——商品的基本信息不会变，但价格会跟着策略变化（比如打折等），这类场景可能只更新价格版本。

### 出货记录表 tb_vendout_order

| 字段名 | 类型 | 长度 | 描述 |
| :--- | :--- | :--- | :--- |
| order_no | VARCHAR | 64 | 出货订单号 |
| pay_type | int | 11 | 支付方式 |
| channel_id | VARCHAR | 64 | 货道ID |
| sku_id | VARCHAR | 64 | 商品ID |
| pay_price | int | 11 | 价格 |
| out_time | TIMESTAMP | - | 售货机出货时间 |
| result_code | int | 11 | 售货机出货结果编号 |

每次出货都要把相关信息记录下来：哪个订单、什么支付方式、从哪个货道出货、出的什么商品、什么价格、什么时候出货，最重要的还有出货结果编号。编号有六种取值，相当于出货结果的状态：

- 0：成功
- 1：货道售空（没有货了）
- 2：设备故障
- 3：机器出货中
- 4：连续支付
- 5：服务器超时

## 小结

售货机端的画像在本篇拼完整了：它是部署进每台售货机的无界面微服务，只干三件事——数据同步、出货、补货；出货是核心，补货本质上也是同步。技术方案回答"怎么跑起来"：安卓系统之上，借 Aid Learning 提供的 Linux 环境跑 Spring Boot 微服务，数据用 H2 嵌入式数据库，消息通道用 paho 对接 EMQX，串口留给硬件层。四张表回答"数据放哪"：商品、货道、版本、出货记录；三个版本号为后续数据同步与价格变动铺路，result_code 的六个编号把出货结果说清。本章再往后的内容——EMQ 安全解决方案 ACL、嵌入式数据库 H2、售货机基础工程搭建、售货机数据同步，都从这几页骨架上展开。
