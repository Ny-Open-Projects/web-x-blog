# 自动补货工单全链路：扫描售货机、缺货统计、补货消息与自动建单

立可得第三章做过手动补货工单：由人工根据售货机的缺货状况创建工单，驱动运营人员去补货。售货机数量一多，每一笔工单都靠人工创建，就是纯粹的耗时耗力。本章把创建这个环节自动化：每天定时执行一个任务，对售货机进行扫描，发现缺货就自动创建补货工单。本篇按需求思路、扫描任务、缺货统计、消息发送、自动建单与测试的顺序，把整条链路讲透。

## 先给结论

- 自动补货工单与手动补货工单只在创建环节不同，后续的接收、取消、完成流程完全一样。
- 补货警戒线是百分比而不是具体数量：每台售货机货道容量不一样，固定值要么补得太频繁，要么失去预警意义。
- 整体链路是 XXL-JOB 触发定时任务，售货机微服务扫描所有运营中的售货机，发现缺货就构建补货协议数据发给 EMQ，工单微服务消费消息自动建单。
- 扫描任务的三个对齐点：执行器名称对齐配置里的 appName（vm-service），Cron 表达式 0 0 4 * * ? 即每天凌晨四点，JobHandler 名字对齐 @XxlJob 注解里的值。
- 缺货判断的核心在 inventory 方法：警戒值等于货道最大容量乘以百分比，count 条件是售货机 ID、skuId 不为 0、当前容量小于等于警戒值。
- 补货协议 SupplyCfg 必须改掉默认的 msgType，否则工单创建出来就会被当成补货完成，中间环节全部跳过。

## 一、需求与实现思路：警戒线为什么是百分比

手动补货工单的逻辑是"缺了才补、人工发起"。自动补货工单做的是同一件事的自动化版本：定时扫描，缺货自动建单。但扫描不能见缺就补。一个货道能装十个商品，只卖出去一个就单独为这一件商品跑一趟腿，显然不划算。所以要先设置一个缺货预警值，也叫补货警戒线：库存低于这条线才补，高于这条线就不动。

这条线必须是百分比，不能是具体数量。假如设成固定值 8：货道容量是 10 的机器，卖两个就触发一次补货，成本太高；容量是 20 的机器，8 又显得太小。换成百分比，不同容量的货道都能得到合理的触发时机。

需求描述收敛成一句话：每天定时任务扫描所有运营中的售货机，注意一定是运营状态的，未投放、撤机的没有必要扫描；只要某台售货机任何一个货道的商品数量小于等于这个比例，就为这台售货机自动创建补货工单，把所有货道全部补满。这里有个容易忽略的点：不是只补缺货的那几个货道。运营人员跑一趟就是一趟，缺一个货道和缺十个货道成本一样，所以干脆全部补满。

实现思路分三步走：

```mermaid
flowchart LR
    J[XXL-JOB 触发定时任务] --> V[售货机微服务<br>扫描所有运营中的售货机货道]
    V -->|发现缺货，构建补货协议数据| E[EMQ]
    E -->|补货主题| T[工单微服务<br>接收数据，自动创建补货工单]
```

定时任务写在售货机微服务里，由 XXL-JOB 调度。代码层面拆成两个方法：一个方法针对单台售货机，判断它是否存在缺货货道，存在就编写补货协议数据发给工单微服务；另一个方法查询所有运营状态的售货机，循环调用前一个逻辑。

## 二、扫描售货机任务：把逻辑挂上 XXL-JOB

第一步，售货机微服务的 pom.xml 添加 xxl-job-core 依赖，版本 2.2.6。第二步，配置文件，这部分项目里已经配好，不需要额外操作：

```yaml
xxl:
  job:
    accessToken: 
    admin:
      addresses: http://192.168.200.128:8080/xxl-job-admin
    executor:
      appName: vm-service
      address: 
      ip: 192.168.200.128
      port: 9980
      logretentiondays: 30
```

其中 appName 是执行器名称 vm-service，后面在调度中心配置执行器时要对齐这个名字；端口 9980。第三步，专建一个 job 包，把用户微服务里现成的 XxlJobConfig 配置类直接拷过来，它负责读取上面的配置并向调度中心注册。

任务类上用 @Component 加 @XxlJob("supplyJobHandler") 标记一个任务方法，返回值是 ReturnT<String>。把缺货判断和消息发送填进去之后，最终形态是：

```java
@Component
public class SupplyJob {

    @Autowired
    private VMService vmService;
    @Autowired
    private TaskService taskService;

    @XxlJob("supplyJobHandler")
    public ReturnT<String> supplyJobHandler(String param) throws Exception {
        // 警戒线比例来自工单微服务，远程调用，提到循环外只取一次
        Integer percent = taskService.getSupplyValue();

        QueryWrapper<VendingMachineEntity> qw = new QueryWrapper<>();
        qw.lambda().eq(VendingMachineEntity::getVStatus, VMSystem.VM_STATUS_RUNNING);
        List<VendingMachineEntity> vmList = vmService.list(qw);

        for (VendingMachineEntity vm : vmList) {
            XxlJobLogger.log("扫描售货机：" + vm.getInnerCode());
            int count = vmService.inventory(percent, vm);   // 缺货货道数
            if (count > 0) {
                XxlJobLogger.log("售货机" + vm.getInnerCode() + "缺货");
                vmService.sendSupplyTask(vm);               // 发送补货消息
            }
        }
        return ReturnT.SUCCESS;
    }
}
```

查询条件用 MyBatis-Plus 的 QueryWrapper 构建，eq 匹配 vmStatus 等于 VMSystem.VM_STATUS_RUNNING，只查运营状态的售货机。日志用 XXL-JOB 自带的 XxlJobLogger，它不输出到控制台，而是输出到调度中心的执行日志里。循环体里的 inventory 调用与 sendSupplyTask 调用是后面两节逐步填进去的，这里给出的是完整结果。其中有个刻意的优化：getSupplyValue() 是远程调用，放在循环里每台售货机调一次效率太低，必须提到循环外，取一次比例反复使用。

调度中心侧配置两件事。先加执行器：名称必须和配置文件里的 appName 一致，取名叫"立可得-售货机微服务"，注册方式选自动。再加任务：执行器选售货机微服务，任务描述"扫描售货机"，Cron 表达式填 0 0 4 * * ?，零秒零分、凌晨四点执行，日和月都是每天，周和年不指定；JobHandler 填 supplyJobHandler，与注解里配的名字一致。保存后任务处于 STOP 状态。

测试走一遍：启动售货机微服务，回到调度中心刷新执行器页面，9980 的地址已经自动注册成功。在任务管理里对该任务执行一次，调度日志显示成功，打开执行日志能看到打印出的售货机编号，当前数据库里只有一台售货机，所以只有一行。

## 三、缺货货道数统计与补货消息发送

缺货的判断标准：只要有一个货道缺货，这台售货机就算缺货。所以先统计缺货货道数，大于 0 即缺货，等于 0 就不缺。售货机服务接口里定义 inventory 方法，返回 int，参数是比例 percent 和售货机实体：

```java
@Override
public int inventory(int percent, VendingMachineEntity vmEntity) {
    // 货道最大容量挂在售货机类型上，实体本身带关联
    int maxCapacity = vmEntity.getChannelType().getMaxCapacity();
    // percent/100 是 int 除法，不转 float 永远等于 0
    int alertValue = (int) (maxCapacity * ((float) percent / 100));

    QueryWrapper<ChannelEntity> qw = new QueryWrapper<>();
    qw.lambda()
      .eq(ChannelEntity::getVid, vmEntity.getId())         // 该售货机的货道
      .ne(ChannelEntity::getSkuId, 0L)                     // skuId 为 0 表示未设置商品，排除
      .le(ChannelEntity::getCurrentCapacity, alertValue);  // 当前容量小于等于警戒值即缺货
    return channelService.count(qw);
}
```

三个条件各有讲究。第一个条件锁定这台售货机的货道。第二个条件排除 skuId 为 0 的记录：货道表里确实存在 skuId 为 0 的货道，表示它还没有设置商品，不该计入缺货，不排除的话统计就没法看了。第三个条件是关键：当前容量小于等于警戒值，计为缺货。count 是 MyBatis-Plus 提供的通用计数方法，传条件进去，返回值正好就是缺货货道数。

警戒值的计算有一个必须避开的坑。比例传进来是 int，如果直接写 percent / 100，整数除法的结果永远是 0，警戒值也跟着变成 0。所以除之前要把 percent 转成 float，算完再把整体转回 int。

有货道要补，下一步就是把补货信息发给工单微服务。售货机服务里再定义 sendSupplyTask 方法，返回 void，入参是售货机实体。实现分三步：查询货道、构建补货列表、发送。

查询货道复用上面的条件，去掉最后一个容量上限，因为补货列表要包含该售货机所有已设置商品的货道，把所有货道全部补满。构建列表用 Stream 写法，替代传统的"先建空集合再循环 add"：

```java
List<SupplyChannel> supplyChannelList = channelList.stream().map(c -> {
    SupplyChannel supplyChannel = new SupplyChannel();
    supplyChannel.setChannelId(c.getChannelCode());   // 字段名叫 channelId，存的是货道编号
    supplyChannel.setCapacity(c.getMaxCapacity() - c.getCurrentCapacity());  // 补货量 = 最大容量 - 当前容量
    supplyChannel.setSkuId(c.getSkuId());
    supplyChannel.setSkuName(c.getSku().getSkuName());
    supplyChannel.setSkuImage(c.getSku().getSkuImage());
    return supplyChannel;
}).collect(Collectors.toList());
```

map 里把每个货道实体转成协议里的 SupplyChannel：货道编号直接取 channelCode；补货量等于最大容量减当前容量，空余多少补多少；skuId、商品名称、商品图片从货道关联的 sku 里取。

接着构建协议数据 SupplyCfg，set 上售货机编号 innerCode 和补货列表，然后是最关键的一步：setMsgType("supplyTask")，修改协议本身的默认名称。SupplyCfg 原本是"补货完成协议"，即工单微服务完成工单时回传给售货机微服务用的。名称不改，消息发到 EMQ 之后，工单创建出来就会立刻被判定为完成，接收、取消、完成这些中间环节全被跳过。所以必须换个名字区分开：supplyTask 是售货机微服务传给工单微服务的自动补货消息，两者结构一模一样，只是协议名不同。

发送用 EMQ 的生产者，主题从 TopicConfig 里选补货主题，消息质量选 2，整体 try-catch 包起来，再打一条 XXL-JOB 日志，把序列化后的 JSON 输出到调度中心：

```java
try {
    mqttProducer.sendTopic(SupplyTopic, 2, supplyCfg);
    XxlJobLogger.log("发送补货数据：" + JsonUtil.serialize(supplyCfg));
} catch (JsonProcessingException e) {
    e.printStackTrace();
}
```

## 四、自动建单与测试

工单微服务侧，配置中心的配置里 MQTT consumer 已经订阅了补货主题，剩下的事就是从主题里取消息、解析、建单。在 com.lkd.business 包下创建 SupplyTaskHandler，@Component 加 @ProcessType("supplyTask")，注解值就是刚才改的那个协议名，框架靠它路由消息，再实现 MsgHandler 接口的 process 方法。方法体分三步，整体套 try-catch，出错时 log.error 记录"创建自动补货工单出错"：

```java
@Component
@ProcessType("supplyTask")
@Slf4j
public class SupplyTaskHandler implements MsgHandler {

    @Autowired
    private TaskService taskService;
    @Autowired
    private VMService vmService;

    @Override
    public void process(String jsonMsg) throws IOException {
        try {
            // 1.解析协议数据
            SupplyCfg supplyCfg = JsonUtil.getObjByJson(jsonMsg, SupplyCfg.class);
            if (supplyCfg == null) return;

            // 2.找出被指派人
            VendingMachineViewModel vm = vmService.getVMInfo(supplyCfg.getInnerCode());
            Integer userId = taskService.getLeastUser(vm.getRegionId().intValue(), false);

            // 3.创建补货工单
            TaskViewModel taskViewModel = new TaskViewModel();
            taskViewModel.setAssignorId(userId);
            taskViewModel.setCreateType(0);                          // 自动创建
            taskViewModel.setProductType(VMSystem.TASK_TYPE_SUPPLY); // 补货工单
            taskViewModel.setInnerCode(supplyCfg.getInnerCode());
            taskViewModel.setDesc("自动补货工单");
            taskViewModel.setDetails(supplyCfg.getSupplyData().stream().map(c -> {
                TaskDetailsViewModel details = new TaskDetailsViewModel();
                details.setChannelCode(c.getChannelId());
                details.setExpectCapacity(c.getCapacity());
                details.setSkuId(c.getSkuId());
                details.setSkuName(c.getSkuName());
                details.setSkuImage(c.getSkuImage());
                return details;
            }).collect(Collectors.toList()));

            taskService.createTask(taskViewModel);
        } catch (Exception e) {
            log.error("创建自动补货工单出错" + e.getMessage(), e);
        }
    }
}
```

第二步有个绕弯：getLeastUser 是做自动维修工单时已经实现的方法，找出当前工单量最少的人，第一个参数是区域 ID，第二个参数传 false 表示不是运维。但补货协议里拿不到区域 ID，只有设备编号，所以先用 innerCode 调 getVMInfo 查一次设备，再从设备上取区域 ID；区域 ID 本身是 Long 类型，方法参数是 int，要 intValue() 转一次。第三步的补货明细列表也要做一次转换：协议里的 SupplyChannel 和工单里的 TaskDetailsViewModel 是两个对象，用 stream map 逐个把货道编号、期望补货量 expectCapacity、skuId、名称、图片填过去，collect(Collectors.toList()) 收尾。

测试的准备动作有两步：货道数据里每个货道最大容量是 10，手动把当前容量改成 3，这样才会触发缺货；工单表里已有三条记录，都是之前生成的自动维修工单，用来对照。售货机微服务和工单微服务都要跑起来，缺货判断里有远程调用，两个都得在。调度中心对"扫描售货机"任务执行一次，调度日志里已经能看到缺货检测结果；刷新工单表，补货工单已经自动创建出来，工单明细表里也写入了货道与商品数据：

```sql
INSERT INTO tb_task_details ( task_id, channel_code, expect_capacity, sku_id, sku_image )
VALUES ( ?, ?, ?, ?, ? )
```

从调度日志到工单表，一次执行把整条链路全部走通。

## 小结

把本篇串起来：自动补货工单复用了手动工单的后续流程，只把"人工创建"换成"定时任务自动创建"。警戒线用百分比适配不同容量的货道；XXL-JOB 每天凌晨四点调度 vm-service 执行器扫描运营中的售货机；inventory 方法用最大容量乘百分比算出警戒值（int 除法先转 float），三个 count 条件统计缺货货道数；sendSupplyTask 用 Stream 把全部货道转成补货列表，SupplyCfg 改协议名为 supplyTask 后经 EMQ 以 QoS 2 发送；工单微服务的 SupplyTaskHandler 按 @ProcessType 路由消息，先查设备拿区域、再找工单量最少的被指派人，最后 createTask 建单。一个细节值得记住：协议名不改，工单会"出生即完成"，协议语义是两套服务对话的契约，结构相同不代表可以同名。
