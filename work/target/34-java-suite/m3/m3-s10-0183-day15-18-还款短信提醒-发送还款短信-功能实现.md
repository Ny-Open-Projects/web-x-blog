# 发送还款短信：QCloudSmsServiceImpl 对接腾讯云 SDK

还款提醒的编排侧已经完整：查到期计划、Feign 取手机号、调发送接口，一气贯通。链路的最后一环是发送接口的实现类，此前它一直空着，现在把腾讯云短信 SDK 填进去，让短信真正发到借款人手机上。这一课代码量不大，API 用法也简单，真正值得琢磨的是异常处理策略与没有真实密钥时的落地方案。

## 先给结论

- 实现类 `QCloudSmsServiceImpl` 落在 `sms` 包下，`@Service` 注册进容器，`@Slf4j` 提供日志，实现 `SmsService` 接口的 `sendRepaymentNotify` 方法。
- 四项凭证通过 `@Value` 从 Apollo 的 `sms` 名称空间注入：appId、appKey、templateId、sign，键名与上一课配置的四个键逐字对应。
- 发送动作只有两行核心代码：构造 `SmsSingleSender`，调用 `sendWithParam`，国家码 86、手机号、模板 ID、参数数组、签名五要素依次传入。
- 参数数组按模板占位符顺序填充，第一个元素填日期、第二个填金额转字符串，顺序与模板定义严格一致。
- 发送环节用 try-catch 包住，失败只记日志不抛出：提醒是旁路功能，单条失败不能中断还款计划遍历；没有真实密钥时，可用控制台输出模拟发送。

## 实现类骨架与配置注入

在 `com.study.finance.repayment.sms` 包下新建实现类，命名沿用课程约定：`QCloud` 指代腾讯云（QCloud 是其常用缩写），`QCloudSmsServiceImpl` 一看就知道是腾讯云短信的实现：

```java
package com.study.finance.repayment.sms;

import com.github.qcloudsms.SmsSingleSender;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;

import java.math.BigDecimal;

@Slf4j
@Service
public class QCloudSmsServiceImpl implements SmsService {

    @Value("${sms.qcloud.appId}")
    private int appId;

    @Value("${sms.qcloud.appKey}")
    private String appKey;

    @Value("${sms.qcloud.templateId}")
    private int templateId;

    @Value("${sms.qcloud.sign}")
    private String sign;

    @Override
    public void sendRepaymentNotify(String mobile, String date, BigDecimal amount) {
        // 实现在下文补全
    }
}
```

四个字段的类型有讲究：appId 与 templateId 在腾讯云侧都是整数，注入目标也用 `int`；appKey 与 sign 是字符串。`@Value` 的占位符与 Apollo `sms` 名称空间里的键逐字对应，大小写错一个字母启动即报解析失败。前提条件再复述一遍：`sms` 名称空间必须已挂进 `application.yml` 的 `apollo.namespaces`，这一步漏了，四个值统统取不到。

## 两行核心代码与五要素参数

发送逻辑参考腾讯云官方 SDK 文档的示例，核心就是构造发送器再调用方法：

```java
@Override
public void sendRepaymentNotify(String mobile, String date, BigDecimal amount) {
    log.info("给手机号 {}，发送还款提醒：{}，金额：{}", mobile, date, amount);
    SmsSingleSender sender = new SmsSingleSender(appId, appKey);
    try {
        sender.sendWithParam("86", mobile, templateId,
                new String[]{date, amount.toString()}, sign, "", "");
    } catch (Exception ex) {
        log.error("发送失败：{}", ex.getMessage());
    }
}
```

方法开头先打一条 info 日志，把手机号、日期、金额写进控制台，测试时一眼就能确认调用进来了、参数对不对。`SmsSingleSender` 构造时传入 appId 与 appKey，这两个值就是腾讯云用来核对发送方身份的。`sendWithParam` 的参数逐个说：第一个是国家码，国内手机号固定 86；第二个是手机号，从方法参数直接透传；第三个是模板 ID，指向此前审核通过的那份正文模板；第四个是字符串数组，给模板占位符按顺序供值，模板里 {1} 是还款日期、{2} 是应还金额，所以数组第一个元素放 `date`、第二个放 `amount.toString()`，金额是 `BigDecimal`，填模板前显式转成字符串；第五个是签名内容，也就是短信开头方括号里的署名；末尾两个参数 extend 与 ext 是渠道扩展字段，用不上就传空串。

整条发送链路的最终形态如下：

```mermaid
flowchart LR
    A[定时还款任务或测试入口] --> B[RepaymentService.sendRepaymentNotify date]
    B --> C[查到期还款计划]
    C --> D[Feign 调用户中心取手机号]
    D --> E[SmsService.sendRepaymentNotify mobile date amount]
    E --> F[QCloudSmsServiceImpl]
    F -->|SmsSingleSender.sendWithParam| G[腾讯云短信网关]
    G --> H[借款人手机收到提醒短信]
```

从触发入口到借款人手机，五段链路一次看完：查询与取号在前两课已就绪，F 到 G 这一段正是本课补齐的最后一跳。图上 E 与 F 之间隔着的只有接口抽象，将来换短信服务商，重写 F 这一格即可。

## 异常处理与失败日志为什么这么写

`sendWithParam` 声明了受检异常，网络超时、HTTP 错误、JSON 解析失败都可能抛出，调用处必须处理。这里的策略是 catch 住 Exception、记 error 日志、不向上抛。这个选择不是随手写的：还款提醒是主流程旁边的增强功能，方法被嵌在还款计划的遍历循环里，一条短信发送失败若把异常抛上去，循环当场中断，后面的借款人一条提醒都收不到。吞掉异常保住整批的可达性，失败原因通过 `ex.getMessage()` 落进日志，排查有据可查。

这条策略与验证码服务的实现形成一组对照。验证码是登录主流程的必要环节，发送失败登录就无法继续，所以验证码服务的实现里，异常与腾讯云返回的非零结果码都会抛业务异常，让调用方明确感知失败。还款提醒没有这种强制性，失败代价低，旁路功能旁路处理。同一个 SDK、两种失败策略，取舍的依据是功能在业务链路里的位置。

还有一层可以再进一步：`sendWithParam` 其实有返回值 `SmsSingleSenderResult`，里面的 result 字段为零表示腾讯云受理成功，非零说明被拒。课堂实现没有用这个返回值，日志输出已经够观察效果；生产化时可以补上结果码判断，把发送失败的计划收集起来做重试或落库补偿，把「尽量送达」升级成「最终送达」。

## 没有真实密钥怎么跑通效果

个人身份申请签名与模板很难通过，这是上一课说过的现实。没有可用凭证时，发送这一格可以临时换成控制台输出模拟：保留方法签名，方法体里只留开头那条 info 日志，SDK 调用整段注释掉，跑通整条链路看效果完全够用。项目里部署的验证码服务就内置了这种模式，它的实现类里除了真实发送的 `send` 方法，还有一个只打日志的 `sendOnConsole` 方法，用配置开关决定走哪个，这个设计可以直接借过来。等拿到审核通过的凭证，把 SDK 调用恢复，链路一行都不用改。

功能验证的入口有两个：一是手动触发，在还款服务加一个测试端点按日期调提醒接口，浏览器或接口工具发一次请求即可观察控制台；二是等定时还款任务自动触发，任务侧把还款日前一天的日期传进来，提醒就随每日调度自动发出。至此还款短信提醒整条链路完工：定时任务查到明天的到期计划，取到手机号，短信按模板填好日期与金额发出，借款人在还款日前收到提醒，充值、还款、提醒三件事在系统里闭环。

## 常见误区

- **发送异常不处理直接让程序崩。** 错例：`sendWithParam` 的受检异常随手 throws，循环里一条网络抖动把整批提醒打断。正解：提醒属旁路功能，异常在实现类内部 catch 并记 error 日志，保住遍历的连续性。
- **参数数组顺序与模板占位符对不上。** 错例：模板 {1} 是金额、{2} 是日期，代码却按日期在前传。正解：传参顺序以模板定义为准，上线前用测试模板逐字核对，填反了发出去就是「金额 2024-11-01 元」。
- **失败后无日志或只打印异常类名。** 错例：`catch` 里什么也不做，或只打 `ex.toString()` 排查不出原因。正解：error 日志带上手机号与异常消息，必要时效验 `SmsSingleSenderResult` 的结果码，失败原因可回溯。
- **把真实 AppKey 硬编码进实现类。** 错例：调试时图方便把凭证写死在代码里。正解：凭证只走 Apollo 注入，代码里永远是 `@Value` 占位符，泄露风险为零。

## 面试可能被问到的问题

1. 面试官追问：「发送短信失败，为什么选择吞异常而不是抛出去？」
   答：提醒是主流程旁的增强功能，方法嵌在还款计划遍历里，抛异常会中断整批，后面的借款人收不到提醒。吞异常加 error 日志保证整批可达性，失败原因留痕可查。若功能在主链路上，例如登录验证码，发送失败必须抛出，策略取决于功能所处的位置。
2. 面试官追问：「sendWithParam 的参数里哪些必须与腾讯云后台设置一致？」
   答：模板 ID 必须对应审核通过的模板，签名必须与申请通过的签名内容一致，AppID 与 AppKey 必须与创建的应用一致。手机号与占位参数是运行时数据。任何一项凭证对不上，腾讯云都会拒绝请求并在结果里返回错误码。
3. 面试官追问：「怎么判断短信真的发送成功了？」
   答：`sendWithParam` 返回 `SmsSingleSenderResult`，result 为 0 表示腾讯云受理成功，errMsg 给出失败原因。课堂实现只看日志，生产化时应效验结果码，失败收集重试或落库补偿。受理成功只代表运营商接单，最终到达状态可结合回执进一步跟踪。
4. 面试官追问：「没有可用的短信凭证时，这类外部依赖功能怎么开发测试？」
   答：先保证链路与逻辑：实现类保留方法签名，发送调用替换为日志输出模拟，验证查询、遍历、取号、调用的编排是否正确；参照验证码服务的做法，可用配置开关在真实发送与模拟输出之间切换，拿到凭证后只恢复 SDK 调用，上层一行不改。
5. 面试官追问：「凭证通过 @Value 注入，配置错了什么时候暴露？」
   答：占位符解析发生在 Spring 容器初始化阶段，键名写错或命名空间没挂上，服务启动时直接报占位符解析失败，属于 fail-fast。而值本身错误，比如 AppKey 不对，要到运行时调用 API 才返回错误码，这类错误需要日志与结果码检查兜底。
