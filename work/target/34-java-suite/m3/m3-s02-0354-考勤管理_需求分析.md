# 考勤管理需求分析：把考勤机的打卡数据一路做成月度归档

考勤设置把「几点算迟到、请假怎么批、加班怎么补」这些制度配进系统之后，制度本身还只是一堆静态规则。真正天天要看的数据是另一回事：某员工这个月哪天迟到、哪天缺卡、全公司有多少人全勤。考勤管理就是承载这份数据的模块，页面要能列出每个员工当月的考勤明细，还要能生成月度报表并归档。这一课先把需求和数据来源理清楚，代码实现留给后面几课。

## 先给结论

- 考勤管理由三块业务组成：展示考勤列表、修改考勤记录、月报表与数据归档，逻辑骨架与社保模块的「列表加归档」基本同款。
- 考勤数据不是员工在页面上点出来的，源头是企业里的考勤机；把数据搬进系统有两条路，课程选择「考勤机导出 Excel，再导入系统」这条折中路线。
- 全链路是：导入打卡数据，统计成考勤列表，人工修正错误记录，月度归档生成报表，归档结果给薪资计算当输入。
- 支撑这套业务的表共四张：`atte_attendance` 考勤记录表、`atte_archive_monthly` 归档主表、`atte_archive_monthly_info` 归档明细表、`atte_company_settings` 记录归档推进到哪个月份。

## 一、页面上能看到什么

打开考勤管理页面，主体就是一张考勤列表：员工、所属部门、考勤状态、考勤日期、当天上下班打卡时间。列表加载完，人事还能对当月数据发起报表生成与归档操作。初见这个页面最容易冒出的疑问不是「怎么写增删改查」，而是数据从哪来。系统里没有任何员工手动打卡的入口，列表里的每一行都必须有外部来源，这个来源就是每家公司都有的考勤机。

考勤机记录的是最原始的事实：某天上午几点上班打卡、下午几点下班打卡。人力资源系统要做的事，是把这份原始事实加工成制度语境下的结论，比如「迟到」「早退」「旷工」，再汇总成报表。所以整个模块的架构核心只有一个问题：打卡数据怎么进系统。

## 二、数据怎么进来：两条路的取舍

把考勤机和人力资源系统连起来，业界常见的方案有两种。

**方案一，两个系统直接连通。** 人力资源系统直接读考勤机的数据库，两边通过网络打通，数据实时共享。听起来干脆，实际门槛很高：考勤机必须有网络访问能力，而且市面上考勤机品牌型号五花八门，每家的表结构都不一样，适配了一号公司的机型，二号公司的就接不上。为一个客户写一套适配，下一家客户就得重写，SaaS 产品吃不下这种成本。

**方案二，考勤机导出 Excel，再导入系统。** 考勤机把数据导出成固定格式的 Excel 文件，人事在系统页面上传，系统解析后入库。这条路的通用性在于 Excel 是约定格式，与考勤机型号无关：任何机器只要能导出数据，人事就能整理成模板要求的列。代价是多了人工整理与上传的环节，实时性也差一些。多数企业实际采用的就是这种折中方案，课程同样选它。

```mermaid
flowchart LR
    A["考勤机<br/>记录上下班打卡"] -->|"方案一: 直连数据库(门槛高)"| C
    A -->|"方案二: 导出固定格式 Excel"| B["人事整理 Excel 模板"]
    B --> D["页面上传导入"]
    D --> C["atte_attendance 考勤记录表"]
    C --> E["考勤列表展示"]
    E --> F["修改考勤记录<br/>时间有误 / 忘打卡"]
    F --> G["月报表与数据归档"]
    G --> H["为薪资计算提供数据"]
```

两条路都通向考勤记录表，差别在中间环节的归属：方案一由系统直接面对考勤机的多样性，方案二把它交给人事整理模板。选型时方案一并非技术上做不到，而是适配成本随客户数量线性增长；方案二把「对接五花八门的考勤机」这个不确定性压缩到人工环节，系统侧从此只面对一种固定格式。

## 三、三块业务串成一条主线

数据进系统之后，考勤管理剩下三件事，彼此是流水线的前后工序。

**第一块，展示考勤列表。** 导入的打卡数据落进考勤记录表，页面按当月展示全员的考勤情况。这一步是后面所有操作的入口。

**第二块，修改考勤记录。** 导入的数据未必全对：有人记录时间有误，有人上午忘了打卡但人是到岗的。这些情况需要人事在列表里修正或补充打卡，否则错误记录会一路污染报表和薪资。

**第三块，月报表与数据归档。** 列表核对无误后，对当月数据做统计归档：企业本月一共多少人、多少人全勤、每个人各类假期的天数明细。归档完成后月份可以往下轮转，报表数据同时为薪资计算提供依据，迟到扣款、旷工扣款都以归档后的考勤结论为准。

这条主线和社保模块几乎复刻：社保也是「列表展示、人工调整、月度归档、切换统计月份」。做过一遍社保，考勤管理的骨架等于是第二次落地，差异只在数据来源多了「导入」这一环。

## 四、四张表怎么分工

需求落到存储上，考勤管理涉及四张表，全部带 `atte_` 前缀与考勤设置的配置表放在一起。

考勤记录表 `atte_attendance` 存最细粒度的打卡事实，对应实体如下：

```java
@Entity
@Table(name = "atte_attendance")
@Data
@EqualsAndHashCode(callSuper = true)
public class Attendance extends BaseEntity implements Serializable {

    @Id
    private String id;
    private String companyId;
    private String departmentId;

    private String userId;
    private Integer adtStatu;      // 考勤状态: 正常/旷工/迟到/早退/休息
    private long jobStatu;         // 在职状态

    private Date adtInTime;        // 上班打卡时间
    private String adtInPlace;
    private Date adtOutTime;       // 下班打卡时间
    private String adtOutPlace;
    private String day;            // 考勤日期, 方便按天查询与判重
}
```

企业、部门、用户三个 id 把记录挂到组织树上，`adtStatu` 是打卡时间对照出勤配置算出来的结论，`day` 单独存一份日期字符串，后面按天查重、按月统计都靠它。

归档是两张表配合的主子结构。归档主表 `atte_archive_monthly` 一行对应「某企业某年某月」的汇总结论：

```java
@Entity
@Table(name = "atte_archive_monthly")
@Data
@EqualsAndHashCode(callSuper = true)
public class ArchiveMonthly extends BaseEntity implements Serializable {

    @Id
    private String id;
    private String companyId;
    private String departmentId;

    private String archiveYear;          // 归档年份
    private String archiveMonth;         // 归档月份
    private Integer totalPeopleNum;      // 本月总人数
    private Integer fullAttePeopleNum;   // 全勤人数
    private Integer isArchived;          // 是否已归档
}
```

归档明细表 `atte_archive_monthly_info` 挂在主表下，记录每个员工的详细数据：工号、手机号、部门、各类假期天数（年假、事假、病假、婚丧产假等）逐字段铺开。主表回答「这个月整体怎么样」，明细表回答「每个人怎么样」，报表页两层钻取正是靠这个结构。

第四张表 `atte_company_settings` 记录企业把考勤设置推进到了哪个月份，字段与社保模块的企业设置表同构：企业 id、是否已设置、当前报表月份。月份轮转、判断「该归档哪个月」都查它。这张表看起来与社保的企业设置重复，单独再建一份是有意的取舍：社保与考勤的归档进度可以各自推进互不牵制，合并进一张表反而要在字段里区分业务域。当然，如果业务允许同步归档，合一张表也完全可行。

## 常见误区

- **以为考勤数据是员工在系统里打卡产生的**：本方案的系统里没有打卡入口，源头是考勤机导入的 Excel。设计表结构时要按「接收外部事实数据」来想，比如必须留出判重字段与导入批次的概念。
- **试图直连考勤机数据库**：考勤机型号五花八门，表结构各家不同，适配成本随客户数线性增长。用固定格式 Excel 做中间层，把不确定性挡在系统之外。
- **归档只建一张表**：只存汇总就没有员工明细，只存明细就得每次现算汇总。主表加明细表的主子结构让报表页可以两层展示，也固化了归档那一刻的统计口径。
- **把「修改考勤」当成普通编辑功能小看**：它承担着补卡、纠错两个职责，是导入数据质量问题唯一的修复窗口，修改入口关闭之前不能归档。

## 面试可能被问到的问题

1. 面试官追问：「考勤系统的数据源为什么选 Excel 导入，而不是直接对接考勤机？」
   答：直连要适配每家考勤机的数据库与型号，成本随客户数量增长，还要求考勤机具备网络访问能力。Excel 导入把适配问题转移为人事整理固定格式文件的人工环节，系统只面对一种格式，通用性和实施成本都可控，是多数企业的实际做法。

2. 面试官追问：「考勤归档为什么拆成主表和明细表两张？」
   答：主表按「企业加年月」存汇总结论，如总人数、全勤人数、是否已归档；明细表挂在主表下存每个员工的详细考勤数据。汇总用于报表首屏与归档状态判断，明细用于钻取查看，两层结构避免每次都从几十万条打卡记录现算汇总，也固化了归档时刻的口径。

3. 面试官追问：「归档之后原始打卡记录还能改吗？」
   答：不应该。归档的意义就是把当月结论固化下来供薪资计算与审计使用，已归档月份的记录必须锁定。若确有错误，要走显式的重算或冲正流程重新归档，而不是悄悄改明细，否则报表与薪资口径对不上。

4. 面试官追问：「企业设置表里的当前报表月份字段是干什么用的？」
   答：它记录企业的归档进度推进到哪个月。归档、报表展示、月份轮转都以它为基准：新员工进来看到的是当前统计月，完成归档后月份推进到下一个月。没有这个字段，系统就无法判断「该归档谁家的哪个月」。

5. 面试官追问：「考勤管理和社保模块在业务设计上有什么可以复用的？」
   答：两者的主线都是「明细列表、人工修正、月度归档、月份轮转」，归档的主子表结构、企业设置表的字段设计、归档状态机的推进方式可以直接复用。差异主要在数据来源（考勤多一步导入）和统计口径（社保看缴费基数，考勤看出勤结论），骨架代码可以按同一模板落地。
