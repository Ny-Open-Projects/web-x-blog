# 还款短信提醒功能测试：临时入口、启动清单与一个 MyBatis 重载坑

查到期计划、取借款人手机号、调腾讯云发短信，还款短信提醒的代码在上一课已经全部就位。代码写完不等于功能可用，这一课做两件事：把整条链路跑起来验证短信真的能发出去，以及处理测试过程中暴露出来的一个隐蔽问题。这个问题出在 `PlanMapper` 接口的方法定义上，与 MyBatis 对方法名的处理机制有关，值得单独讲透。

## 先给结论

- 测试方式沿用项目惯例：在 `RepaymentController` 里临时加一个测试端点，浏览器按日期发一次请求即可触发整条提醒链路。
- 需要启动的组件共四类：Apollo 配置中心、ZooKeeper（Elastic-Job 依赖）、还款微服务 `finance-repayment-service`（53080）、用户中心微服务 `finance-consumer-service`（53050），用户中心不能漏，手机号是经 Feign 从它那边取的。
- 请求路径里的日期必须与 `repayment_plan` 表中 `SHOULD_REPAYMENT_DATE` 的某个值一致，否则查询为空，整个测试看不到任何效果。
- 测试通过后顺带发现一个 bug：`PlanMapper` 里两个同名方法构成重载，MyBatis 把方法名当作 SQL 标识使用，导致三参数的分片查询实际执行的是单参数方法的 SQL。
- 解决办法是给方法改名，让两个方法名互不重复；改名后控制台 SQL 里出现了分片条件，问题确认修复。

## 临时测试端点怎么加

定时任务接入之前，项目里验证功能的标准做法是在 Controller 里加临时方法，浏览器直接发请求触发。在 `RepaymentController` 中追加：

```java
@ApiOperation("测试还款短信提醒")
@GetMapping("/repayment-notify/{date}")
public void testRepaymentNotify(@PathVariable String date) {
    repaymentService.sendRepaymentNotify(date);
}
```

路径里带一个日期参数，请求进来直接调业务层的 `sendRepaymentNotify`。这个方法只服务于测试，后续定时任务接上之后它的使命就结束了，所以不需要考虑鉴权与返回值封装。沿着调用往里跟一层就能看到完整编排：先调 Mapper 查询指定日期到期且状态为未还款的计划，遍历计划取出借款人标识，再经 Feign 代理到用户中心微服务换回手机号，最后调 `SmsService` 的实现把短信发出。

## 启动清单与测试数据

发请求前把依赖的服务逐个清点一遍，这一步漏一个都会以莫名报错收场：

| 组件 | 作用 | 端口 |
|---|---|---|
| Apollo 配置中心 | 下发还款服务全部配置 | 8070 |
| ZooKeeper | Elastic-Job 的注册中心 | 2181 |
| finance-repayment-service | 还款微服务，承载提醒链路 | 53080 |
| finance-consumer-service | 用户中心微服务，提供手机号查询 | 53050 |

Apollo 与 ZooKeeper 不必再解释，值得强调的是用户中心微服务：提醒功能里查借款人手机号走的是 Feign 代理，请求会真实地发往用户中心，这个服务不启动，链路在取手机号那一步直接断掉。Apollo 里注册中心地址也要一并就绪。

另一个细节是日期取值。请求传的日期会原样进入查询条件，与 `repayment_plan` 表的应还日期做等值匹配，用数据库工具先把表里的数据看一眼，挑一个真实存在的值传进去，例如表中某条计划的应还日期是 11 月 22 日，请求就发：

```bash
curl "http://127.0.0.1:53080/repayment/repayment-notify/2019-11-22"
```

日期与表里任何一条记录都对不上时，查询返回空列表，遍历一次都不执行，功能本身没有错，只是你观察不到现象。

## 测试现象与结果核对

请求发出后到控制台核对两处输出。一是业务日志，方法入口打印的那条信息带着手机号、还款日期与应还金额；二是 SQL 日志，能看到到期计划的查询语句。手机端同时会收到一条短信，内容与日志一致，日期和金额按模板占位符填好。到这一步，触发、查询、取号、发送四段链路全部验证通过。

整条验证路径如下：

```mermaid
flowchart LR
    A[浏览器按日期发请求] --> B[RepaymentController 测试端点]
    B --> C[sendRepaymentNotify date]
    C --> D[查询到期还款计划]
    D --> E[Feign 调用户中心取手机号]
    E --> F[腾讯云发送提醒短信]
    F --> G[控制台日志与手机短信双重核对]
```

图上 G 这一步是测试的落点：控制台日志证明代码走到了发送，手机收到短信证明外部依赖也通了，两边对上才算测试完成。

## 测试顺带揪出的 MyBatis 重载坑

链路通了，但观察 SQL 日志时发现一个不对劲的地方。`PlanMapper` 里定义了两个查询方法，一个参数的普通版本，与带分片参数的版本：

```java
@Select("SELECT * FROM repayment_plan WHERE DATE_FORMAT(SHOULD_REPAYMENT_DATE, '%Y-%m-%d') = #{date} AND REPAYMENT_STATUS = '0'")
List<RepaymentPlan> selectDueRepayment(String date);

@Select("SELECT * FROM repayment_plan WHERE DATE_FORMAT(SHOULD_REPAYMENT_DATE, '%Y-%m-%d') = #{date} AND REPAYMENT_STATUS = '0' AND MOD(period, #{shardingCount}) = #{shardingItem}")
List<RepaymentPlan> selectDueRepayment(String date, @Param("shardingCount") int count, @Param("shardingItem") int item);
```

Java 层面这是合法的方法重载，参数个数不同互不冲突。业务层调用的明确是三参数版本，可控制台打出来的 SQL 却不带分片过滤条件，等于单参数方法的那条语句被执行了。

原因在 MyBatis 的内部机制。MyBatis 把 Mapper 接口的每个方法映射成一条 `MappedStatement`，标识取的是「命名空间 + 方法名」，方法名直接充当 SQL 的 id。id 在同一命名空间里必须唯一，两个同名方法在语法上通过了编译，在 MyBatis 侧却指向同一个 id，后注册的语句覆盖了先注册的，于是无论按哪个签名调用，最终解析到的都是同一条 SQL。三个参数传进去，SQL 模板里却没有对应的占位符可填，分片条件就这样静默丢失了。

这类问题的危险之处在于它不报错。查询照常返回数据，业务照常往下走，只有对照 SQL 日志才会察觉条件没生效。定时任务按分片并行扫描时，每个实例都会扫到全量数据，分片的防重复设计完全落空。

修复方式是消除同名：给其中一个方法改名，让 id 唯一。把三参数版本改名为带业务含义的名字：

```java
@Select("SELECT * FROM repayment_plan WHERE DATE_FORMAT(SHOULD_REPAYMENT_DATE, '%Y-%m-%d') = #{date} AND REPAYMENT_STATUS = '0' AND MOD(period, #{shardingCount}) = #{shardingItem}")
List<RepaymentPlan> selectDueRepaymentList(String date, @Param("shardingCount") int count, @Param("shardingItem") int item);
```

名字一改，业务层的调用点跟着编译报错，把报错处的方法名同步替换即可，本例只有业务层一处引用。重启服务后定时任务再次触发，控制台 SQL 里出现了分片条件，确认走的是改名后的语句。把这条经验固化成习惯：Mapper 接口的方法不要重载，哪怕参数完全不同。

## 常见误区

- **认为 Java 允许重载，Mapper 接口也允许。** 错例：同一接口里定义两个同名方法，一个单参数一个带分片参数。正解：MyBatis 用方法名做语句 id，id 必须唯一，重载会导致语句互相覆盖，同名方法必须改名。
- **测试日期随手填今天或过去的时间。** 错例：请求里传一个表里不存在的日期，查询为空，误判功能有 bug。正解：先查 `repayment_plan` 表里真实的应还日期，用它作为请求参数。
- **只启动还款微服务就发请求。** 错例：漏掉用户中心微服务，取手机号时 Feign 调用失败。正解：按依赖关系清点启动清单，Apollo、ZooKeeper、还款微服务、用户中心微服务缺一不可。
- **功能跑通就不管 SQL 日志。** 错例：看到短信发出来就认定测试通过。正解：对照 SQL 日志确认执行的是预期语句、条件齐全，静默的条件丢失只能靠日志发现。

## 面试可能被问到的问题

1. 面试官追问：「MyBatis 的 Mapper 接口为什么不能定义重载方法？」
   答：MyBatis 把接口方法映射为 `MappedStatement`，标识是命名空间加方法名，方法名直接当作语句 id 使用，同一命名空间内 id 必须唯一。重载的两个方法同名，语句注册时后者覆盖前者，调用时无论按哪个签名都会解析到同一条 SQL，多余参数无处填充，条件静默失效。
2. 面试官追问：「这种分片条件丢失的问题，为什么不报错？怎么尽早发现？」
   答：查询本身合法，只是过滤条件少了，返回的是超集数据，业务不中断所以无异常。尽早发现的手段是核对 SQL 日志与预期语句是否一致，以及为分片查询写单测断言生成的 SQL 条件；生产上还可以通过数据重复的监控指标反推分片失效。
3. 面试官追问：「你的短信提醒功能是怎么测试的？」
   答：在 Controller 加临时测试端点，路径携带日期参数，直接调用业务层的提醒方法。启动 Apollo、ZooKeeper、还款微服务与用户中心微服务，按表里真实存在的应还日期发请求，控制台核对查询 SQL 与发送日志，手机端确认短信内容里的日期与金额正确。
4. 面试官追问：「测试请求里的日期为什么必须是表里已存在的值？」
   答：提醒功能按日期等值查询到期且未还款的计划，日期是查询条件。传入不存在的日期查询返回空，遍历不执行，短信不会发出，无法观察效果；这不是功能缺陷，而是测试数据与查询条件不匹配。
5. 面试官追问：「临时测试端点会带到生产环境吗？」
   答：不会。它只为在定时任务接入前提供人工触发手段，没有鉴权与参数校验。定时任务上线后触发完全由调度器完成，这类端点应删除或用配置开关限制在开发环境，避免成为无鉴权的业务触发入口。
