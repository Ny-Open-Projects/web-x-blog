# 批量保存导入的用户：默认属性补齐、事务兜底与两个差一错误

> 🔒 安全提示：文中示例的口令/密钥均为课程教学环境演示口径，生产环境的安全要求见《安全与合规须知》。

用户列表已经在内存里构造好了，离导入成功只差入库。保存这一步看上去就是一个循环调 save，真正跑一遍测试，三个问题接连冒出来：三条数据只进了两条、工号 2001 变成了 2001.0、部门字段里存着 DEPT-DEV 这串编码。把这三个问题的来龙去脉讲透，比保存本身更有价值。

## 先给结论

- 保存动作收进 `UserService.saveAll(list, companyId, companyName)`，Controller 只负责解析和传参，企业信息由基类从登录态里带出来。
- Excel 只有六列业务数据，主键、密码、企业归属、状态级别这些系统属性必须在保存前补齐：`IdWorker` 生成主键，`Md5Hash` 以手机号为盐加密默认密码 123456。
- 循环保存外层加 `@Transactional`，一条失败整批回滚，导入的完整性靠事务兜底。
- 行循环条件要用 `<=`：`getLastRowNum()` 返回最后一行的索引，`getLastCellNum()` 返回格子的个数，两个 API 语义差一，循环条件也跟着差一。
- 工号带 `.0` 是 Excel 数值格子的天性，用 `DecimalFormat` 格式化还原。

## 一、把保存逻辑从 Controller 挪进 Service

Controller 里解析完 Excel，最后一行交给 Service：

```java
//3.批量保存用户
userService.saveAll(list, companyId, companyName);
return new Result(ResultCode.SUCCESS);
```

`companyId` 与 `companyName` 不是从前端传来的。批量导入的请求由登录后的用户发起，解析请求头里的 JWT 之后，企业 ID 和企业名称已经放在了 `BaseController` 的成员变量里，子类直接用。逻辑也说得通：谁操作导入，这批用户就属于谁的企业，不需要也不会让前端来声明企业归属。

## 二、saveAll：补齐 Excel 给不了的字段

Service 层的方法声明与实现：

```java
/**
 * 批量保存用户
 */
@Transactional
public void saveAll(List<User> list, String companyId, String companyName) {
    for (User user : list) {
        //设置默认密码：123456，以手机号为盐，加密 3 次
        user.setPassword(new Md5Hash("123456", user.getMobile(), 3).toString());
        //设置主键
        user.setId(idWorker.nextId() + "");
        //设置企业归属
        user.setCompanyId(companyId);
        user.setCompanyName(companyName);
        //在职状态：正常
        user.setInServiceStatus(1);
        //账号状态：可用
        user.setEnableState(1);
        //用户级别：普通用户
        user.setLevel("user");
        userDao.save(user);
    }
}
```

这段代码里每一行都对应一类「Excel 模板给不了、系统又必须有」的属性：

**第一，主键。** 分布式微服务环境下数据库自增 ID 会冲突，用课程公共工具类 `IdWorker` 的 `nextId()` 生成趋势递增的长数字 ID，转字符串保存。

**第二，初始密码。** 导入进来的用户还没有设置过密码，给统一初始密码 123456，但不能明文入库：`Md5Hash("123456", user.getMobile(), 3)` 是 Shiro 提供的哈希工具，用手机号做盐、迭代 3 次，同一个密码不同用户得到的密文也不同，拖库后也难以反查。手机号本身就在模板里，盐是现成的。

**第三，状态与级别。** 在职状态置 1 表示正常在职，账号状态置 1 表示可以登录，级别置为普通用户。这些默认值属于业务规则，集中写在 Service 里，后续要改只动一处。

**逐条 save 与批量的取舍也在这里。** 严格意义上的批量插入应该减少与数据库的交互次数，JPA 的 `saveAll` 底层同样会逐条执行 `merge`，本项目的写法是显式循环加 `save`，条数在几十到几百的量级时瓶颈不在这里，而在于语义简单、事务清晰。数据量上到十万级，才需要换 JDBC 批处理或先落临时表再 `INSERT SELECT` 的方案，这个取舍在选型时心里要有数。

事务注解保证完整性：循环到第 80 条时某条数据非法抛了异常，前 79 条一起回滚，不会出现半批成功半批失败的中间态。

## 三、实测第一个坑：三条数据只进了两条

代码写完，重启服务，选好模板文件上传，页面提示导入成功。打开数据库一刷新，问题来了：Excel 里明明三行数据，表里只有两条。

回看解析循环就明白了。`sheet.getLastRowNum()` 返回的不是行数，而是**最后一行的索引**。三行数据加一行表头共四行，索引 0 到 3，它返回 3。循环条件写成 `rowNum < sheet.getLastRowNum()`， rowNum 走到 2 就停了，索引 3 的第三行永远没被读。

而内层循环用的 `row.getLastCellNum()` 返回的是**格子的个数**（相当于最后一列索引加一），所以列循环用 `<` 恰好正确。两个 API 只差一个词，语义一个是索引、一个是数量：

| API | 返回含义 | 循环条件 |
|---|---|---|
| `sheet.getLastRowNum()` | 最后一行的索引（0 起） | `<=` |
| `row.getLastCellNum()` | 格子个数（等于最后索引加一） | `<` |

```mermaid
flowchart LR
    A["第 1 行 表头 索引 0"] --> B["第 2 行 数据 索引 1"]
    B --> C["第 3 行 数据 索引 2"]
    C --> D["第 4 行 数据 索引 3"]
    D --> E["getLastRowNum 返回 3"]
    E --> F["循环条件写 lt 3 就丢掉索引 3 这一行"]
```

这张图讲的就是丢行的现场：行数四行、最大索引 3，条件 `< 3` 让最后一行从指缝里漏掉。修正方式是把行循环改成 `<=`：

```java
for (int rowNum = 1; rowNum <= sheet.getLastRowNum(); rowNum++) {
    Row row = sheet.getRow(rowNum);
    values = new Object[row.getLastCellNum()];
    // 内层列循环保持不变
}
```

改完重新上传（先把之前的两条脏数据删掉），数据库里三条记录整整齐齐。

## 四、实测第二个坑：工号 2001 变成了 2001.0

再看数据内容：部门字段暂且不论（那是下一篇的事），工号赫然是 `2001.0`。原因在前一篇已经埋过伏笔：Excel 的数值格子统一按 double 存储，POI 读出来就是 2001.0，`toString()` 原样带上了小数尾巴。

处理办法是格式化。`DecimalFormat` 是 JDK 自带的数字格式化工具，构造时传入模式串，`format` 之后再转字符串：

```java
public User(Object[] values) {
    //用户名
    this.username = values[1].toString();
    //手机号
    this.mobile = values[2].toString();
    //工号：Excel 数值格子读出来是 double，格式化去掉 .0
    this.workNumber = new DecimalFormat("#").format(values[3]).toString();
    //聘用形式
    this.formOfEmployment = ((Double) values[4]).intValue() + "";
    //入职时间
    this.timeOfEntry = (Date) values[5];
    //部门编码
    this.departmentId = values[6].toString();
}
```

模式串 `#` 表示只保留有效数字，2001.0 格式化后还原成 2001。手机号 13800000001 这类 11 位数值同理适用；如果业务要求工号固定位数、不足补零，把模式换成 `0000000000` 这类零占位写法即可，模式串本身就是格式规则的表达。再上传一次，工号干净了。

## 五、还剩一个尾巴：departmentId 里存的是编码

数据数量对了、格式对了，但 `departmentId` 字段里躺着的是 DEPT-DEV 这样的部门编码，真正的部门 ID 和部门名称还没就位。编码到部门的换算要去企业微服务查数据，属于跨服务调用，下一篇专门处理这最后一环。

## 常见误区

- **行循环条件沿用列循环的 `<`。** `getLastRowNum` 给索引、`getLastCellNum` 给数量，不加区分地套同一个条件，永远丢最后一行数据。
- **初始密码明文入库。** 批量导入的默认密码更要加密，而且要加盐：不加盐的 MD5 相同密码密文相同，彩虹表一查就破。以手机号为盐是本项目拿现成字段做差异化 salt 的做法。
- **循环 save 不加事务。** 中途失败时前面已入库的数据不会自动回滚，用户看到导入失败重传，库里却多出一批重复数据。`@Transactional` 要包住整批。
- **依赖数据库自增 ID。** 微服务多库环境下自增必然冲突，导入这种高并发写入场景应使用雪花算法一类的工作机 ID 生成器。

## 面试可能被问到的问题

1. 面试官追问：「`getLastRowNum()` 和 `getLastCellNum()` 有什么区别？」
   答：前者返回 Sheet 中最后一行的索引，从 0 起算，遍历行时条件用 `<=`；后者返回一行里格子的个数，等于最后一列索引加一，遍历列时条件用 `<`。两者名字相近语义不同，混用会丢行。

2. 面试官追问：「导入功能里的默认密码应该怎么设计？」
   答：给统一的初始密码并强制首次登录修改，入库前必须哈希加盐，比如用 `Md5Hash(密码, 手机号, 迭代次数)`，盐取用户特有字段保证相同密码不同密文。绝不能明文或不加盐存储。

3. 面试官追问：「循环单条 save 和真正的批量插入差在哪？怎么优化？」
   答：JPA 的 save 循环是逐条发 SQL，事务包裹后只是保证原子性，性能没有提升。要性能可以注入 `EntityManager` 后按批 flush 并 clear 一级缓存，或开启 Hibernate 的批处理参数，量再大直接走 JDBC batch 并配 `rewriteBatchedStatements`。

4. 面试官追问：「`@Transactional` 在批量导入里起什么作用？什么情况会失效？」
   答：作用是把整批写操作绑定成一个事务，任一条抛异常整批回滚，避免半批入库。失效的典型场景包括方法不是 public、同类内部自调用绕过代理、异常被 catch 吃掉、以及抛出的是默认不触发回滚的受检异常。

5. 面试官追问：「为什么导入数据不用数据库自增主键？」
   答：微服务架构下多个服务各自连库，自增 ID 跨库会重复，也不利于后续分库分表。用雪花算法一类的 ID 生成器在应用侧生成全局唯一且趋势递增的 ID，插入索引友好，课程里的 `IdWorker.nextId()` 就是这个思路。
