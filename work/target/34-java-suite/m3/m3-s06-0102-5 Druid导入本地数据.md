# 第一份数据进 Druid：用控制台向导导入本地 JSON

用惯了 MySQL 的人上手 Druid，第一个卡点往往不是查询而是入库：这里没有 INSERT 一行一行的写法，入库等于提交一份摄入任务。Druid 的数据来源分两类，离线数据走批量导入，实时数据走流式监听。先把离线这条路走通，从控制台的 Load data 向导开始，把一个本地 JSON 文件变成可查询的数据源；实时监听留给实时导入篇展开。

## 先给结论

- 入口在控制台 Load data 页选 Local disk；本地文件指 Druid 服务器上的文件，路径必须在所有 Druid 服务器本地盘上，不是操作者电脑上的路径。
- 向导七步：Connect 定位文件、Parse 选解析器、Parse time 解析时间列、Transform 与 Filter 转换过滤、Configure schema 定维度指标、Partition 选段粒度、Publish 命名提交。
- 时间列是第一公民：向导从原始列提取时间、选对格式，生成内置的 `__time` 列；时间解析错了后面所有统计全歪。
- 演示用 Druid 自带 quickstart/tutorial 目录下的 wikiticker 示例 JSON，每行一个 JSON 对象即一条记录，按小时分区发布成新数据源。
- 提交后到 Tasks 页盯任务状态，success 之后 DataSources 页多出一个数据源，Query 页用 SQL 验证。

## 一、向导全流程

```mermaid
flowchart LR
    LD["Load data 选 Local disk"] --> CN["Connect：目录与文件名"]
    CN --> PS["Parse：json 解析器"]
    PS --> PT["Parse time：时间列与格式"]
    PT --> TF["Transform 与 Filter"]
    TF --> SC["Configure schema"]
    SC --> PA["Partition：段粒度"]
    PA --> PB["Publish：数据源命名"]
    PB --> SB["Submit 提交任务"]
    SB --> TK["Tasks 页 running"]
    TK --> OK["success 后可查询"]
```

从左到右就是一次批量导入的全部动作，页面左侧导航与这条链一致，填完一步点 Next 进入下一步；表单较长时注意滚动页面找解析与下一步按钮。

## 二、Connect：定位文件

Load data 页提供 HTTP、AWS S3、Google 云存储与本地磁盘几类批量源，演示选 Local disk。表单三件事：Firehose type 选 local，Base directory 填目录，File filter 填文件名匹配。页面上有一行警告值得留意：此路径必须在所有 Druid 服务器的本地文件系统上。含义很直接，local 指服务端本地盘，文件要预先放到 Druid 服务器上，多机部署时每台都得有。

课程演示用的是 Druid 自带示例数据，路径在安装目录的 `quickstart/tutorial` 下，文件为 `wikiticker-2015-09-12-simple.json`，内容是维基百科的编辑记录，每行一个 JSON 对象：

```json
{"time":"2015-09-12T00:46:58.771Z","channel":"#en.wikipedia","cityName":null,"countryName":null,"countryCode":null,"page":"Wikipedia:Vandalism in progress","user":"Meno25","delta":-64,"added":0,"deleted":64,"isAnonymous":false}
```

点 Connect 后，向导按 base directory 加 filter 定位文件并预览样本，Preview 区能看到一条条解析出来的记录，time、channel、cityName、comment、countryName、delta、isAnonymous 这些列一目了然。

## 三、Parse time：把业务时间挂到 __time

Druid 一切按时间组织，向导专门设了 Parse time 一步。它自动识别出原始数据里的时间列 `time`，作为 timestampSpec 的来源，格式选 ISO，因为原始值是 `2015-09-12T00:46:58.771Z` 这种带 T 的 ISO 8601 格式。解析之后，这个时间写进每个 Druid 数据源都有的内置列 `__time`，后续的时间过滤与聚合粒度全部以它为基准。

这里最容易翻车的是格式选错：原始数据带 T 与时区，却手选成 `yyyy-MM-dd HH:mm:ss`，解析结果整体错位甚至任务直接失败。原则是格式跟着原始数据走，原始是 ISO 就选 ISO，自定义格式要与字符串严格一致。预览区的时间展示样式可以调整，那只是显示层的格式化，不影响存储。

## 四、Transform、Filter 与 schema

Transform 一步提供列转换，用表达式对原始列加工，比如拼接、截取、派生新列；Filter 提供列过滤与全局过滤，把不需要入库的行挡在门外。演示数据格式干净，这两步直接跳过。

Configure schema 一步决定每列的去向：字符串与业务标识类列进 dimensions 维度，数值类列配聚合器进 metrics 指标，count 聚合器默认就有。这一步的产物就是摄入配置里的 dimensionsSpec 与 metricsSpec，维度越全，可切分的统计角度越多，代价是存储与扫描成本，按业务需要的分析角度取舍。

## 五、Partition、Publish 与验证

Partition 一步选段粒度 segmentGranularity，决定 timeChunk 怎么切，演示按小时。粒度选择是数据量与查询模式的平衡：数据量大、查询集中在一小段时间就选细粒度；数据量小、查询跨度大，粗粒度段更少、元数据压力更小。

Publish 一步给数据源命名，演示沿用向导建议的 `tutorial`，也可以按业务起名；Append to existing 选 False 表示全新建源而不是追加。Submit 之后，向导把各步配置组装成摄入任务提交，等价于提交了下面这份 spec（按 0.15 批量摄入写法补全）：

```json
{
  "type": "index_parallel",
  "spec": {
    "dataSchema": {
      "dataSource": "tutorial",
      "parser": {
        "parseSpec": {
          "format": "json",
          "timestampSpec": { "column": "time", "format": "iso" },
          "dimensionsSpec": {
            "dimensions": ["channel", "cityName", "countryName", "countryCode", "page", "user", "isAnonymous"]
          }
        }
      },
      "metricsSpec": [
        { "type": "count", "name": "count" },
        { "type": "doubleSum", "name": "added", "fieldName": "added" },
        { "type": "doubleSum", "name": "deleted", "fieldName": "deleted" }
      ],
      "granularitySpec": {
        "type": "uniform",
        "segmentGranularity": "hour",
        "queryGranularity": "none",
        "rollup": true
      }
    },
    "ioConfig": {
      "type": "index_parallel",
      "firehose": {
        "type": "local",
        "baseDir": "/opt/druid/quickstart/tutorial",
        "filter": "wikiticker-2015-09-12-simple.json"
      }
    },
    "tuningConfig": { "type": "index_parallel" }
  }
}
```

任务在 Tasks 页显示 running，示例文件有几万行，跑了约一分钟转成 success。回到 DataSources 页刷新，列表里多出刚发布的数据源，Query 页随手验证：

```sql
select * from tutorial limit 30
```

能出数就说明离线导入这条链完整走通。实时导入走的是另一条路：创建 supervisor 监听 Kafka 队列，冷链监控平台的结果队列 all_device_message 就是那样进来的，两条路在后续章节分别展开。

## 常见误区

- **把操作电脑上的路径填进 Base directory。** 错例：本机桌面的路径直接贴上去，Connect 预览永远空。正解：local 指服务端本地盘，先把文件传到 Druid 服务器，多机时保证每台都有。
- **时间格式凭感觉选。** 错例：原始值是 ISO 格式却选自定义模板，任务失败或时间整体偏移。正解：格式与原始字符串严格对应，带 T 与时区的选 ISO。
- **提交后就关页面。** 错例：以为点了 Submit 数据就可查。正解：任务是异步执行的，到 Tasks 页等状态变 success，失败要读任务日志。
- **rollup 开着却不检查 metricsSpec。** 错例：数值列没配聚合器，导入完发现数值没了。正解：预聚合依赖聚合器，数值列要在 schema 步骤明确配进 metrics。

## 面试可能被问到的问题

1. 面试官追问：「离线导入和实时导入在 Druid 里有什么区别？」
   答：离线导入把本地文件或远程存储的批量数据一次性提交摄入任务，适合存量历史；实时导入由 supervisor 常驻监听 Kafka 队列持续写入，秒级可见。两者最终都生成数据段落到深度存储，查询侧无差别。
2. 面试官追问：「__time 列是怎么来的，为什么重要？」
   答：摄入时从原始数据的时间列解析出来，由 timestampSpec 指定列名与格式，生成每个数据源都有的内置列。Druid 按它切 timeChunk 与 Segment，时间过滤与聚合粒度都以它为基准，解析错了所有统计全歪。
3. 面试官追问：「控制台向导点 Submit 之后发生了什么？」
   答：向导把各步骤配置组装成一份 ingestion spec 提交给 Overlord，Overlord 派生摄入任务交 MiddleManager 执行，任务读取本地文件、按 schema 解析、按段粒度建段写入深度存储，状态从 running 走到 success 后数据可查。
4. 面试官追问：「segmentGranularity 怎么选？」
   答：看数据量与查询模式。每天上亿条、查询集中在近期就选小时或天；数据量小、查询跨度大可以选天以上。粒度越细段越多，并行度更高，但元数据与管理成本也更高。
5. 面试官追问：「local 批量导入对文件位置有什么要求？」
   答：路径必须是 Druid 服务器本地文件系统上的路径，且在所有执行摄入的服务器上可访问，多机部署要把文件分发到每台机器，否则任务调度到没有文件的节点就会失败。
