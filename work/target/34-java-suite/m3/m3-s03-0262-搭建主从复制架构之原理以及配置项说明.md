# 先懂原理再动手：主从复制的 binlog 流转与主从配置项逐条拆解

> 🔒 安全提示：文中示例的口令/密钥均为课程教学环境演示口径，生产环境的安全要求见《安全与合规须知》。

前几课把主从复制、中间件、负载均衡的架构画完了，这一课终于要动手搭。动手之前有一道必答题：主库的
变更到底是怎么「飞」到从库的？把 binlog、中继日志、数据重演这三步吃透，后面每一行配置都有了落点；
跳过原理直接抄配置，出问题时完全无从排查。环境沿用课程的设定：MySQL 的衍生版 Percona，版本
5.7.23，通过 Docker 搭建。

## 先给结论

- 复制原理三步走：主库把数据变更记录到二进制日志 `binary log`，从库的 IO 线程把日志事件拷贝到自己的
  中继日志 `relay log`，从库的 SQL 线程重做中继日志里的事件，完成数据重演。
- 整个机制的核心就是二进制日志，它由配置项 `log-bin` 开启并指定文件名。
- 动手前四条检查：主从 MySQL 版本一致、主从已有数据一致、主库开启二进制日志、主从 `server-id` 必须不同。
- 主库配置 `log-bin` 与 `server-id=1`，再创建一个带 `replication slave` 权限的同步账号；从库只配
  `server-id=2`，其余全部通过 SQL 完成。
- 从库的 `CHANGE MASTER TO` 里，`master_log_file` 与 `master_log_pos` 来自主库的
  `SHOW MASTER STATUS`，含义是从哪个日志文件的哪个位点开始同步。

## 一、复制三步曲：binlog、relay log、数据重演

主从复制有一张经典原理图，两个节点各司其职：master 是主节点，承接数据变更请求；slave 是从节点，
负责跟上主库的变化。

```mermaid
flowchart LR
    A["应用向 master 写入数据"] --> B["master 落盘变更"]
    B --> C["binary log 记录二进制日志事件"]
    C -->|"slave 的 IO 线程读取"| D["relay log 中继日志"]
    D -->|"slave 的 SQL 线程重做"| E["数据重演 与 master 一致"]
```

这张图是复制的全链路：master 收到新增、修改、删除请求时，除了在本机执行写操作，还要把这个写动作
以二进制日志的形式记录下来，日志里的每条记录称为二进制日志事件，`binary log events`。slave 侧
两个线程接力：IO 线程连上主库，把 master 的日志事件拷贝到本地的中继日志 `relay log`；SQL 线程
读取中继日志，把里面的事件重新执行一遍。同样的写操作在从库重演一次，两边数据自然保持一致。

整条链路最核心的载体就是二进制日志，没有它，主从之间没有任何同步的凭据。顺带补齐 binlog 的三种
记录格式，这属于同一知识块，按主流写法补充说明：

- `STATEMENT`：记录 SQL 语句本身，日志量小；但 `NOW()`、`UUID()`、`LIMIT` 这类结果不确定的语句
  在主从上重放可能得到不同结果。
- `ROW`：记录每一行数据的变更前后镜像，重放结果确定、数据最安全，代价是日志量大，MySQL 5.7 起为
  默认格式。
- `MIXED`：平时按 `STATEMENT` 记，遇到不确定语句自动切换成 `ROW`，兼顾体积与安全。

## 二、动手前先过四条检查

**版本一致。** 主从两个 db server 的 MySQL 版本要一致，主库用 5.7，从库也得是 5.7，不能一边 5.7
一边 5.6 或 5.5。复制协议对版本差异敏感，跨大版本搭建常常出现事件无法重放的问题。

**数据一致。** 开启复制前，主库与从库里已有的数据要一致。复制解决的是「从某个时刻起的增量」，基准
不一致，之后同步得再准，两边的差距始终摆在那里。

**主库开启二进制日志。** 主 db server 必须开启 binlog，这是复制的凭据来源，也是下一步配置的第一项。

**server-id 必须唯一。** 主库与从库的 `server-id` 不能相同，它在复制拓扑里标识每个节点，配重了
复制链路无法正常建立。

## 三、主库配置：三项配置加一个同步账号

主库的配置文件 `my.conf` 里写三项：

```properties
# 开启主从复制，主库的配置
log-bin = mysql-bin
# 指定主库 serverid
server-id=1
# 指定同步的数据库，如果不指定则同步全部数据库
binlog-do-db=my_test
```

`log-bin` 一项身兼两职：开启二进制日志，并指定日志文件名为 `mysql-bin`，实际生成的文件形如
`mysql-bin.000006`。`server-id` 指定主库的节点标识为 1，不配时默认 0，必须改成非零且唯一的值。
`binlog-do-db` 用来缩小同步范围，只同步指定数据库；不写它就同步全部数据库。

配置生效后，在主库执行一条 SQL 查看状态：

```sql
SHOW MASTER STATUS;
```

返回结果里会给出当前正在写入的日志文件名与位点，这两条信息稍后从库要用。主库还要创建一个专门用于
同步的账号：没有主库授权，随便一个从库都能来拉数据显然不安全，所以必须在主库建用户并授予复制权限：

```sql
-- 授权用户 slave01 使用 123456 密码登录 mysql
grant replication slave on *.* to 'slave01'@'127.0.0.1' identified by '123456';
-- 刷新配置
flush privileges;
```

从库稍后就用这个 `slave01` 账号来同步数据。`flush privileges` 不能省，授权写进内存需要刷新才生效。

## 四、从库配置：一个配置项加一段 SQL

从库的配置反而简单，`my.conf` 里只需要指定 `server-id`：

```properties
# 指定 server-id，只要不重复即可，从库也只有这一个配置，其他都在 SQL 语句中操作
server-id=2
```

注意这个值必须与主库的 1 不同，前面配的是 1，这里就指定 2，切记不能相同。其余工作全部在 SQL 里完成：

```sql
-- 指定从库要同步的主库信息
CHANGE MASTER TO
master_host='127.0.0.1',
master_user='slave01',
master_password='123456',
master_port=3306,
master_log_file='mysql-bin.000006',
master_log_pos=1120;
```

前四个参数好理解：主库地址、同步账号、密码与端口。问题在最后两个参数从哪来：它们必须来自前面在主库
执行的 `SHOW MASTER STATUS`，文件名 `mysql-bin.000006` 与位点 `1120` 都要从那张结果里抄。指定
位点的含义是告诉从库从哪个位置开始同步，位点对准了，复制才不会漏事件也不会重放已执行过的事件。

最后启动同步并检查状态：

```sql
-- 启动主从同步
START SLAVE;
-- 查看同步状态
SHOW SLAVE STATUS;
```

状态输出里重点看 IO 线程与 SQL 线程是否都处于运行状态，两个线程都正常，主从复制链路才算真正打通。

## 常见误区

- **主从 `server-id` 配成一样。** 两边都留默认值 0，或都配了同一个数字，从库连上主库后复制直接
  报错退出。主库 1、从库 2，各不相同是底线。
- **位点凭感觉填。** `master_log_file` 与 `master_log_pos` 不看 `SHOW MASTER STATUS` 的实际
  输出，随手填一个，从库要么漏掉一段事件，要么从错误位置重放，数据从此错位。
- **建完同步账号忘了 `flush privileges`。** 授权只在内存里挂了号，没有刷新生效，从库拿账号连接
  主库直接被拒，表现为 IO 线程起不来。
- **基线数据不一致就开同步。** 主库有存量数据、从库是空库，复制只管增量，空从库上执行针对存量数据的
  操作会报记录不存在，链路反复中断。先把存量数据对齐，再定位点开启复制。

## 面试可能被问到的问题

1. 面试官追问：「主从复制的完整流程是什么样的？」
   答：三步。主库把数据变更记录到二进制日志 `binary log`，即 `log-bin` 指定的文件，记录形式是
   `binary log events`；从库的 IO 线程把主库的日志事件拷贝到自己的中继日志 `relay log`；从库的
   SQL 线程重做中继日志里的事件，完成数据重演，两边达到一致。

2. 面试官追问：「`server-id` 是干什么的，为什么主从必须不同？」
   答：它是节点在复制拓扑中的身份标识，主库靠它区分连接上来的是哪个从库、事件由哪个节点产生。两个
   节点 id 相同，复制链路无法正确建立，所以主库配 1、从库配 2，必须唯一。

3. 面试官追问：「`CHANGE MASTER TO` 里的日志文件和位点从哪里来？」
   答：来自主库的 `SHOW MASTER STATUS` 输出，文件名如 `mysql-bin.000006`、位点如 1120。这对
   参数决定从库从哪个日志的哪个位置开始拉取与重放，抄错会导致漏事件或重复重放。

4. 面试官追问：「binlog 有哪三种格式，怎么选？」
   答：`STATEMENT` 记 SQL 语句，日志小但不确定函数可能导致主从结果不一致；`ROW` 记行级变更镜像，
   结果确定、最安全，日志量大，5.7 起是默认；`MIXED` 平时用语句记，遇到不确定语句自动切行。生产
   上追求数据正确性一般选 `ROW`。

5. 面试官追问：「搭建主从前要做哪些准备？」
   答：四条：主从 MySQL 版本一致；主从已有数据一致，保证复制基线相同；主库开启二进制日志；主从
   `server-id` 不同。另外要在主库创建带 `replication slave` 权限的同步账号并刷新权限。

6. 面试官追问：「从库配置文件里只写一个 `server-id` 就够了吗？」
   答：够了。从库的其他连接信息，主库地址、账号密码、端口、日志文件与位点，全部通过
   `CHANGE MASTER TO` 在 SQL 层指定，之后 `START SLAVE` 启动复制，`SHOW SLAVE STATUS` 观察状态。
