# 定时还款任务接入还款服务：依赖、Apollo 命名空间与四个调度配置项

Elastic-Job 的概念与入门案例到这里全部走完，学习的落点始终是同一个：让万信金融的还款服务自己按时干活。用户还款功能早已开发完毕，但它至今靠人工触发，测试用的 Controller 配上浏览器手工发请求，这套流程在真实业务里不成立。还款日到了，系统必须自动找到所有到期的还款计划并逐个执行还款，这一课把定时任务接进还款服务，先完成环境与配置层面的准备。

## 先给结论

- 定时任务的切入点是还款流程的第一步「查询到期的还款计划」，从这里开始由 Elastic-Job 自动触发，后续各阶段保持原逻辑不变。
- 分片规则选的是按期数拆分：还款计划表按期数字段过滤，期数为奇数与偶数各成一片，分片总数 2，对应启动两个还款服务实例。
- 分片规则没有标准答案，按期数、按主键 ID 都可以，判断依据是业务语义与数据分布，按期数取模的好处是同一合同的各期还款计划天然分散到不同实例。
- 环境准备两件事：检查还款服务是否已引入 `elastic-job-lite-spring` 依赖，在 Apollo 的 repayment-service 项目下新建 `micro_service.elasticjob` 命名空间并填入四个配置项。
- 配置项属于 Apollo，不落在本地文件里，这是与入门案例最大的差别，同时必须把新命名空间追加进 `application.yml` 的 `apollo.namespaces`，否则四个键一个都读不到。

## 为什么定时还款从查询到期计划切入

回顾还款流程的完整链路，它的起点是「查询到期的还款计划」，随后生成还款明细、调用存管系统确认还款、保存交易记录与处理结果。此前这一连串动作由人工请求触发，现在要做的只是把触发方式换掉：由定时任务在既定时刻自动执行这条链路，流程本身不动。

Elastic-Job 的作业类与配置类写法在入门案例里已经完整演练过，放到还款服务里无非是把作业逻辑换成「查询到期计划并执行还款」。真正需要设计的是分片规则：到期还款计划按期数分散在表里，查询时对期数字段做取模过滤，分片总数为 2 时，期数为奇数的计划归一个实例，偶数的归另一个，两个实例并行处理各自的半边数据，天然不会重复。分片规则也可以换成按记录 ID 取模，框架层面完全等价，取舍点在于哪种规则让查询条件写得自然、让数据分布更均匀，按期数拆分对还款业务来说最直观。

## 依赖检查：还款服务引入 Elastic-Job

第一步确认依赖。打开还款服务的 `pom.xml`，查找 `elastic-job-lite-spring`，之前引入过就跳过，没有就补上：

```xml
<!-- Elastic-Job-Lite 的 Spring 集成模块 -->
<dependency>
    <groupId>com.dangdang</groupId>
    <artifactId>elastic-job-lite-spring</artifactId>
    <version>2.1.5</version>
</dependency>
```

坐标与版本和入门案例完全一致。这个模块自带对 ZooKeeper 客户端与调度引擎的传递依赖，引入后配置类的 API 即可使用。

## Apollo 配置：新命名空间与四个键

还款服务的所有环境配置都由 Apollo 统一下发，Elastic-Job 的配置也不例外。登录 Apollo 配置中心，找到 repayment-service 项目，新建一个名称空间，名字为 `micro_service.elasticjob`，然后加入四个配置项：

```properties
# zookeeper服务地址
p2p.zookeeper.connString = localhost:2181
# 作业命名空间
p2p.job.namespace = p2p-elastic-job
# 分片总数
p2p.job.count = 2
# cron表达式(定时策略)
p2p.job.cron = 0/5 * * * * ?
```

四个键的用途与入门案例的 `myjob.` 系列一一对应：连接串指向 ZooKeeper 服务；作业命名空间换成 `p2p-elastic-job`，与入门案例的 `elastic-job-example` 区分开，两套作业在 ZooKeeper 里各占各的目录，互不污染；分片总数 2 对应两个还款服务实例；cron 仍是每 5 秒一次。

cron 的取值要单独强调。5 秒一次纯粹为了测试时能快速看到效果，真实上线的定时策略绝不可能是这个频率，还款本身按天为周期，合理取值是每天执行一次或最多两次，例如每天凌晨 3 点或凌晨 5 点扫一遍到期还款计划，具体时刻要结合业务节奏与系统负载来定。

## 别忘了在 yml 里挂上命名空间

新增的命名空间不会自动生效。Apollo 客户端只加载 `application.yml` 里声明过的命名空间，漏配的表现是四个键全部取不到，`@Value` 注入直接报占位符解析失败。在还款服务的 `application.yml` 中把 `micro_service.elasticjob` 追加到命名空间列表的最前面：

```yaml
app:
  id: repayment-service
apollo:
  bootstrap: true
  namespaces: micro_service.elasticjob, micro_service.springframework
```

`namespaces` 是逗号分隔的列表，原有的配置命名空间保留，新命名空间追加进去即可。还款服务下次启动时，客户端会连同新命名空间一起拉取配置，注入过程与本地 properties 文件没有任何区别。

整条配置链路如下：

```mermaid
flowchart LR
    A[Apollo 配置中心] -->|micro_service.elasticjob 命名空间| B[四个调度配置项]
    B -->|客户端拉取| C[application.yml 声明命名空间]
    C --> D[还款服务启动]
    D --> E[配置类 @Value 注入 connString namespace count cron]
    E --> F[注册中心与调度器初始化]
```

图上最值得盯的是 `application.yml` 那一步：它是命名空间的门禁，配置项再正确，门没开就读不进来。配置层面准备完毕后，剩下的就是编写作业类与两个配置类，让定时还款真正跑起来。

## 常见误区

- **把新配置直接写进本地 properties 文件。**错例：仿照入门案例在工程里建 `application.properties` 填四个键。正解：还款服务的配置统一由 Apollo 管理，Elastic-Job 的参数放在 `micro_service.elasticjob` 命名空间中，便于集中修改与多环境下发。
- **命名空间加了配置却没加进 `apollo.namespaces`。**错例：Apollo 界面上配置填好了，服务启动报 `${p2p.job.cron}` 无法解析。正解：客户端只加载 yml 里声明的命名空间，新增命名空间必须同步追加到 `namespaces` 列表。
- **照抄 5 秒的 cron 上生产。**错例：测试完忘了改，还款任务每 5 秒扫一遍数据库。正解：测试频率只为观察方便，生产按天调度，例如凌晨 3 点或 5 点执行一次，并评估触发时刻对数据库与存管系统的压力。
- **作业命名空间沿用入门案例的值。**错例：还款服务也用 `elastic-job-example`，与示例工程的作业节点混在同一个 ZooKeeper 目录下。正解：每个业务集群使用独立命名空间，还款服务用 `p2p-elastic-job`，实现作业数据的隔离与清理便利。
- **分片规则随手定。**错例：不做分析就把分片键设成某个分布极不均匀的字段，导致一个实例承担绝大部分数据。正解：分片键要求数据分布均匀且能写进查询条件，本课按期数取模，期数在还款计划表中分布自然，是合适的拆分依据。

## 面试可能被问到的问题

1. 面试官追问：「用户还款功能已经实现，为什么要再接一个定时任务？」
   答：原有实现依赖人工发请求触发，只能用于测试。还款有明确的时间属性，到期就必须处理，把触发方式换成 Elastic-Job 的定时调度，系统每天自动查询到期还款计划并执行后续还款流程，业务逻辑不变，触发从人工变成自动。
2. 面试官追问：「定时还款的分片规则为什么选按期数取模？」
   答：到期计划按期数分散存储，期数对分片总数取模后余数分布均匀，每个实例处理自己的余数区间，查询条件可直接写进 SQL。同一合同不同期数的计划被拆到不同实例，既并行又天然防重复；按 ID 取模在框架层也成立，但期数与还款业务语义贴合更紧。
3. 面试官追问：「微服务项目的 Elastic-Job 配置为什么不放本地配置文件？」
   答：还款服务接入 Apollo 配置中心，所有环境参数统一由 Apollo 下发，调度参数放在独立的 `micro_service.elasticjob` 命名空间便于修改与审计，改 cron 不需要重新打包发布。放本地文件则失去了多环境管理与热更新的能力。
4. 面试官追问：「Apollo 新建了命名空间，服务读不到配置，最可能的原因是什么？」
   答：`application.yml` 的 `apollo.namespaces` 列表没有包含新命名空间。客户端只加载声明过的命名空间，补上 `micro_service.elasticjob` 并重启即可。其次是检查键名拼写与 Apollo 项目环境是否匹配。
5. 面试官追问：「测试环境 cron 设成每 5 秒，上线前要考虑什么？」
   答：改成符合业务周期的频率，还款场景每天一到两次，凌晨低峰执行。同时评估单次执行的数据量，量大时增加分片总数配合多实例并行，并确认重复执行幂等性，避免调度重叠时同一笔计划被处理两次。
