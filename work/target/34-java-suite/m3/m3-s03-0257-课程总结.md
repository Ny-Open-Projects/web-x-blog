# day16 收官：把 Beats、Kibana、Logstash 串成一条完整的日志链路

四个组件逐个学完，每个单拎出来都认识，合在一起却容易糊：谁在采集、谁在加工、数据到底先到谁手里？收官这一课把 day16 的内容按数据流向重新串一遍，每个组件留一张配置快照，末尾给一条可以自查的标准：合上课件，能不能从零把整条链路搭起来。

## 先给结论

- 四个角色一句话记住：Beats 管采集，Logstash 管加工，Elasticsearch 管存储检索，Kibana 管可视化。
- Filebeat 学了七件事：部署安装、读取日志文件、自定义 tags 与 fields、输出到控制台与 ES、harvester 与 spooler 的工作原理、Module 模块化采集。
- Metricbeat 管指标：system 模块收 CPU、内存、磁盘，Redis 模块收中间件指标，官方仪表盘一条命令装进 Kibana。
- Kibana 有两种安装（安装包、Docker），核心入口是 Discover 数据探索与 Dashboard 仪表盘。
- Logstash 的采集职能让给了 Beats，它专注加工：接收 Filebeat 送来的日志，filter 解析，output 送入 ES，最终在 Kibana 里看见。

## 二、Filebeat：日志采集这一层的全部要点

**部署与读取。** tar 包解压即用，配置里 `filebeat.inputs` 声明盯哪些文件，`paths` 支持通配，新写入的行被持续采集，断点信息记在 registry 里，进程重启不丢不重。

**自定义标签与字段。** `tags` 打标签，`fields` 补自定义字段，`fields_under_root` 决定字段落在根节点还是 `fields` 子对象。课堂配置长这样：

```yaml
# haoke-log.yml 节选
filebeat.inputs:
  - type: log
    enabled: true
    paths:
      - /haoke/beats/logs/*.log
    tags: ["web"]           # 自定义 tag，便于后端处理
    fields:
      from: haoke-im
```

**输出两端。** 学习期用 `output.console` 加 `pretty: true` 在控制台直接看事件；生产用 `output.elasticsearch`，`hosts` 列集群节点，索引默认按天创建，分片数通过 `setup.template.settings.index.number_of_shards` 声明进索引模板。

**工作原理与 Module。** harvester 负责逐行读取单个文件，spooler 负责汇聚发往输出，registry 记录每个文件的读取偏移，这套机制保证不漏、不重。Module 把常见组件的采集配置做成开箱即用的模板，`./filebeat modules enable redis` 一条命令启用，路径、字段、仪表盘都替你配好，读取 Redis 日志的课堂实操走的就是 Module：

```yaml
# modules.d/redis.yml 节选
module: redis
log:
  enabled: true
  var.paths:
    - /haoke/redis-data/node01/*.log
    - /haoke/redis-data/node02/*.log
    - /haoke/redis-data/node03/*.log
slowlog:
  enabled: false
```

## 三、Metricbeat：指标数据与现成仪表盘

Metricbeat 与 Filebeat 同构，差别只在采什么：它按周期轮询指标而不是盯文件。system 模块开箱收 CPU、内存、磁盘、进程指标；Redis 模块收中间件的 info 与 keyspace 指标，三个 Redis 节点直接写在 hosts 数组里：

```yaml
# modules.d/redis.yml 节选
module: redis
metricsets:
  - info
  # - keyspace
period: 10s
hosts: ["192.168.1.7:6379", "192.168.1.7:6380", "192.168.1.7:6381"]
```

指标数据想直接看图，不用自己画：metricbeat 配置里把 `setup.kibana.host` 指向 Kibana 的 5601，然后一条命令把官方仪表盘整套装进去：

```bash
./metricbeat setup --dashboards
```

装完在 Kibana 的 Dashboard 里能看到 CPU 曲线、内存占比、Redis 连接数等现成图表，系统指标与中间件状态零代码可视化。

## 四、Kibana：两种安装与几个核心入口

安装两条路：安装包解压、配置 `kibana.yml` 后启动；Docker 一条 create 挂载配置文件，`--net host` 让容器与宿主机共享网络：

```bash
docker create --name kibana --net host \
  -v /haoke/beats/kibana:/usr/share/kibana/config/kibana.yml \
  kibana:6.5.4
docker logs -f kibana          # 跟日志确认启动
```

功能入口按用途记：Discover 做数据探索，条件查询、时间过滤都在界面上点；Visualize 把索引聚合成柱形图、饼图、折线图；Dashboard 把多张图拼成一屏大盘；Timelion 做时间序列的进阶分析。Metricbeat 仪表盘与 Filebeat 的 Redis 仪表盘装好后，查看指标不需要写一行查询代码。

## 五、Logstash：把加工层补进链路

Logstash 的功能牌子上写着采集与处理两件事，采集已经被 Beats 干得更好，它留下的是处理：input 收数、filter 加工、output 送达的三段管道。`-e` 在命令行里快速验证管道，`-f` 加载配置文件才是正路，`-t` 测语法，`--config.reload.automatic` 热加载。

与 Filebeat 的整合把链路补全：Filebeat 的 output 指向 5044，Logstash 的 input 用 beats 插件接住，filter 里 grok 把 Nginx 访问日志拆成结构化字段，output 送进 ES。最终版管道：

```conf
input {
  beats {
    port => 5044
  }
}

filter {
  grok {
    patterns_dir => "/haoke/logstash-6.5.4/nginx-patterns"
    match => { "message" => "%{NGINX_ACCESS}" }
    remove_tag => ["_grokparsefailure"]
    add_tag => ["nginx_access"]
  }
}

output {
  elasticsearch {
    hosts => ["192.168.1.7:9200", "192.168.1.7:9201", "192.168.1.7:9202"]
  }
}
```

数据从 Nginx 日志文件出发，经 Filebeat、Logstash 落进 `logstash-2019.01.15`，在 Kibana 建 `logstash-*` 索引模式查询、画柱形图。加上一直在直连写入的 Metricbeat，全章的最终形态是两条进数据的路、一个看数据的地方：

```mermaid
flowchart LR
    A ["Nginx 日志文件"] --> B ["Filebeat 采集"]
    B -->|"5044"| C ["Logstash beats 输入"]
    C --> D ["grok 解析"]
    D --> E ["Elasticsearch logstash 索引"]
    H ["Metricbeat 系统与 Redis 指标"] -->|"直连"| ES2 ["Elasticsearch filebeat 与 metricbeat 索引"]
```

## 六、自测标准：合上课件能不能搭出来

课件结尾给的标准很实在：能把这个最初状态的图全部搭起来，数据流向、每一块在做什么、下游是谁、数据怎么处理都清晰，Elastic Stack 就算入门。落到操作上是几个问题：日志文件在哪、采集器怎么配、加工管道怎么写、索引名是什么、Kibana 怎么看。每一段的输入输出都能答上来，链路就装在脑子里了。

## 常见误区

- **把四个组件的职责记串。** 采集归 Beats，轻、铺源头；加工归 Logstash，重、集中部署；存储检索归 Elasticsearch；可视化归 Kibana。让 Beat 做复杂解析或把 Logstash 装到每台业务机器上，都是用错工具。
- **版本混搭。** 全章组件统一在 6.5.4，Filebeat、Metricbeat、Logstash、ES、Kibana 大版本错开时，索引模板、通信协议、仪表盘的兼容性都会出问题。
- **只跟着敲命令，不看组件日志。** 链路断了先看断点两侧的日志：Filebeat 连不上看 output 重试信息，Logstash 配置问题先跑 `-t`，Kibana 空白先查索引模式与时间范围。
- **把 Kibana 当数据源。** 它只查询 ES，索引删了或索引模式没建，界面操作再熟练也查不出东西。

## 面试可能被问到的问题

1. 面试官追问：「Elastic Stack 里日志数据有哪两条链路，怎么选？」
   答：轻链路是 Beat 采集后直写 Elasticsearch，适合原文入库即可的场景；重链路是 Beat 先送 Logstash，经 filter 解析转换再入 ES，适合需要结构化加工的日志。按数据是否需要加工分流，两条链路可以并存。
2. 面试官追问：「Filebeat 怎么保证日志不漏采、不重采？」
   答：harvester 逐行读取文件，spooler 汇聚发送，registry 把每个文件的读取偏移落盘。进程重启后按 registry 里的偏移续传，输出端不可用时事件留在队列重试、恢复后补发，断点续传与不丢不重由这套机制保证。
3. 面试官追问：「Module 相比自己写采集配置好在哪？」
   答：Module 把常见组件的采集项做成模板，一条 enable 命令启用，文件路径、解析字段、自带仪表盘一起给到，例如 Redis Module 配好 hosts 就能收指标和日志。手写配置灵活但要自己踩每个细节，接入常见组件时 Module 明显更快。
4. 面试官追问：「Metricbeat 和 Filebeat 的区别是什么？」
   答：同为 Beats 家族，差别在数据源。Filebeat 盯日志文件，按行采集文本；Metricbeat 按周期轮询指标，system 模块收系统指标，各 service 模块收中间件指标。两者常同机部署，一个管日志一个管指标。
5. 面试官追问：「Filebeat、Logstash、Elasticsearch 这条链路为什么要这样排？」
   答：Filebeat 轻量，适合铺在每台业务机器上采集；Logstash 依赖 JVM 且加工能力强，适合集中部署做解析转换；Elasticsearch 负责存储检索并支撑 Kibana 的查询聚合。轻采集、重加工、集中存储，各组件站在自己成本最低的位置。
6. 面试官追问：「日志在 Kibana 里查不到，你怎么定位断在哪一环？」
   答：按数据流向逐段查。先在 head 或 API 确认索引存在且有文档，有数据就是 Kibana 侧索引模式或时间范围的问题；索引没数据再看 Logstash 输出日志与 Filebeat 重试信息，确认采集与加工两端；日志文件本身没增长则从业务侧查起。
