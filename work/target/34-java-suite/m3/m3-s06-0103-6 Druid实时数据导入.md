# 把 Kafka 队列接进 Druid：实时数据导入的完整接线

设备读数快照已经源源不断写进 Kafka 的结果队列，Druid 的数据源页面却还是空的。离线导入能补存量文件，却管不了持续增长的新消息；自己写一个消费者程序再逐条入库，offset 管理、故障恢复、数据分段全都要自己兜底。Druid 对这类问题的标准答案是 Kafka Indexing Service：提交一个 supervisor 任务，让它常驻监听队列，消息一进 Kafka 就自动进入 Druid。

## 先给结论

- 实时导入等价于提交一个 supervisor 任务：提交后常驻运行，自动派出并管理一批 indexing task，不需要人工反复触发。
- 操作上只有两步：在 Kafka 里创建 topic；在 Druid 管理台点 Submit supervisor，提交一份 JSON 摄入规格。
- 规格里最要紧的是三段：dataschema 定解析格式与维度，ioConfig 定监听哪个 topic 与 Kafka 地址，tuningConfig 定任务并行与段参数。
- 验证看三处：Supervisors 页任务 RUNNING，Datasources 页出现对应数据源，Query 页能查出刚投递的消息。
- 冷链监控平台里，cold-flink 工程把计算结果回投 all_device_message 队列，被 supervisor 监听后即成为可查询的历史数据。

## supervisor 是常驻的摄入管理者

用一句人话说：supervisor 是一个部门主管，自己不搬数据，负责持续派出 indexing task 去具体读队列、生成数据段；task 挂了它负责补位，队列里来了新消息它负责让数据继续流动。task 本体跑在 MiddleManager 进程里，产出 segment 后由 Historical 加载对外提供查询。

```mermaid
flowchart LR
    P["业务系统与 Flink 等生产者"] --> K["Kafka topic"]
    K --> S["supervisor 常驻监听"]
    S --> T["indexing task 读取分区"]
    T --> G["按时间生成 segment"]
    G --> H["Historical 加载后可查询"]
```

这张图是实时导入的主干：生产者只管往队列投消息，supervisor 与 task 在 Druid 侧完成拉取、解析、分段，Historical 加载后查询立即可见，全程没有人工介入。关键路径是从 topic 到 segment：只要时间字段解析正确，消息落地即完成一次完整摄入。

**第一，supervisor 与 task 是两层分工。** supervisor 保存摄入规格，按规格周期性派生 task；task 才真正消费 Kafka 分区并把数据写成段。task 运行到设定时长后，supervisor 再派新任务接续 offset。这个设计让摄入具备自动恢复能力，task 失败由 supervisor 重新派发，不需要人盯。

**第二，它替代的是手写消费者。** 自己写消费者要处理 offset 提交、重复消费、批量缓冲、段文件生成这些细节；Indexing Service 把这些内建，声明清楚一份规格即可。

## 第一步：创建 Kafka 队列

Kafka 自带 topic 管理脚本，在安装目录下执行（课程环境用 wikipedia 队列演示）：

```bash
# 创建 Kafka 队列
./bin/kafka-topics.sh --create --zookeeper localhost:2181 --replication-factor 1 --partitions 1 --topic wikipedia
# 查看已有队列，确认创建成功
./bin/kafka-topics.sh --zookeeper 172.17.0.143:2181 --list
mykafka
wikipedia
```

副本数与分区数都给了 1，演示环境够用。队列名要记住，下一步规格里 ioConfig 引用的就是它。

## 第二步：提交 supervisor 摄入规格

管理台 Tasks 页点 Submit supervisor，把 JSON 规格整份贴进去提交。规格逐段拆开看（ioConfig 与 tuningConfig 两段按画面并按 Druid 常用写法补全）：

```json
{
  "type": "kafka",
  "dataSchema": {
    "dataSource": "wikipedia",
    "parser": {
      "type": "string",
      "parseSpec": {
        "format": "json",
        "timestampSpec": { "column": "time", "format": "auto" },
        "dimensionsSpec": {
          "dimensions": [
            "channel", "cityName", "comment", "countryIsoCode", "countryName",
            "isAnonymous", "isMinor", "isRobot", "isSpam", "isUnpatrolled",
            "metroCode", "namespace", "page", "regionIsoCode", "regionName"
          ]
        }
      }
    },
    "granularitySpec": {
      "segmentGranularity": "HOUR",
      "rollup": false
    }
  },
  "ioConfig": {
    "topic": "wikipedia",
    "taskCount": 1,
    "taskDuration": "PT1H",
    "consumerProperties": { "bootstrap.servers": "172.17.0.143:9092" }
  },
  "tuningConfig": {
    "type": "kafka",
    "maxRowsInMemory": 1000000,
    "maxRowsPerSegment": 5000000
  }
}
```

**type 与 dataSchema 声明从哪类来源读、读成什么样。** type 是 kafka，表示这是 Kafka Indexing Service 的规格；dataSource 是落库后的数据源名 wikipedia，后续查询就按这个名字访问。

**parser 与 parseSpec 决定消息怎么解析。** parser 的 type 是 string，按纯文本一行一条读；parseSpec 的 format 是 json，每行消息本身就是一份 JSON。timestampSpec 指定时间列，column 是 time，format 用 auto，ISO 字符串与毫秒数都能识别。dimensionsSpec 罗列维度，示例数据里的十几个业务字段全部声明为维度，聚合统计时再从中指定指标。

**ioConfig 声明监听对象。** topic 指向刚创建的队列；consumerProperties 里 bootstrap.servers 写 Kafka 服务地址与 9092 端口；taskCount 控制并行任务数，taskDuration 控制单个任务的工作时长。

**tuningConfig 调摄入性能。** maxRowsInMemory 控制任务在内存里攒多少行再落盘，maxRowsPerSegment 控制单个段多大，演示环境保持默认量级即可。

提交成功后，Supervisors 页能看到这个 supervisor 状态为 RUNNING。

## 第三步：投递消息并验证

Kafka 自带控制台生产者，往队列里贴一条消息试试：

```bash
# 启动控制台生产者，向 wikipedia 队列投递消息
export KAFKA_OPTS="-Dfile.encoding=UTF-8"
./opt/software/kafka_2.12-2.3.0/bin/kafka-console-producer.sh --broker-list 172.17.0.143:9092 --topic wikipedia
```

消息取自 Druid 快速上手的维基百科样例数据，一行一条 JSON（截取部分字段）：

```json
{"added": "2015-09-12T00:00:00.000Z", "channel": "ru.wikipedia", "comment": "new section", "isAnonymous": "false", "isMinor": "false", "isRobot": "false", "isSpam": "false", "isUnpatrolled": "false", "metroCode": "null", "namespace": "Main", "page": "Александр", "user": "Александр", "time": "2015-09-12T00:00:00.000Z"}
```

投完可以用自带消费者回读一遍，确认消息确实进了队列：

```bash
# 回头消费一遍，确认消息确实进了队列
./opt/software/kafka_2.12-2.3.0/bin/kafka-console-consumer.sh --bootstrap-server 172.17.0.143:9092 --topic wikipedia --from-beginning
```

Druid 侧的验证：管理台 Query 页直接查 `select * from wikipedia`，刚投的那条立刻出现，从投递到可查通常在一分钟内；Supervisors 页对应行保持 RUNNING，Tasks 页能看到正在运行的 indexing task。

## 接回冷链监控平台

平台自己的 supervisor 监听的是 all_device_message 队列，数据来自 cold-flink 工程的主程序：计算结果一路覆盖写 MySQL 实时指标表，另一路把完整快照回投队列（真实代码节选，包名按规范改写）：

```java
// 将消息发送到 Kafka 队列
// Druid 监听此队列，将消息保存到 Druid 中
FlinkKafkaProducer<String> myProducer = new FlinkKafkaProducer<String>(
        "all_device_message", new SimpleStringSchema(), properties);
outStream.map(new MapFunction<MessageEntity, String>() {
    @Override
    public String map(MessageEntity value) throws Exception {
        return JSON.toJSONString(value);
    }
}).addSink(myProducer);
```

设备编码、仓库、温湿度、报警状态这些字段都在 MessageEntity 里，序列化成 JSON 投进队列后，由平台的 supervisor 自动摄入。wikipedia 演示队列与 all_device_message 业务队列可以并存，Supervisors 页里两个任务同时 RUNNING，互不影响。

## 常见误区

- **把 supervisor 当成一次性导入任务。** 错例：看到 Tasks 页任务长时间 RUNNING 就以为卡死了。正解：supervisor 常驻，task 到 taskDuration 就换新任务接续 offset，长期 RUNNING 才是正常状态。
- **时间列解析不当，数据整批消失。** 错例：timestampSpec 的 column 随手填一个。正解：column 必须与消息里的时间字段同名，format 选 auto 可同时兼容 ISO 字符串与毫秒数；时间解析失败，数据要么报错要么落进错误时段。
- **维度漏声明，字段查不出来。** 错例：以为没声明的列也会自动进维度。正解：string 解析下只有 dimensionsSpec 里列出的列才成为维度，过滤与聚合都依赖维度，漏了只能重新导入。
- **拿队列里有消息当导入成功的证据。** 错例：控制台消费者能读到消息就认为 Druid 已入库。正解：队列有消息只证明生产端正常，还要到 Datasources 页确认数据源出现、Query 页查询返回结果。

## 面试可能被问到的问题

1. 面试官追问：「Druid 实时导入 Kafka 的核心机制是什么？」
   答：Kafka Indexing Service。提交一份 JSON 摄入规格创建 supervisor，supervisor 常驻监听 topic，按规格周期性派出 indexing task 消费分区并生成数据段，消息投递后很快可查，不需要人工触发导入。
2. 面试官追问：「supervisor 和 indexing task 是什么关系？」
   答：supervisor 是管理者，保存摄入规格，负责任务生命周期与故障重派；task 是执行者，真正读 Kafka 分区、解析数据、生成 segment。task 运行到设定时长后由 supervisor 派新任务接续 offset，保证摄入连续。
3. 面试官追问：「摄入规格里 ioConfig 和 tuningConfig 分别管什么？」
   答：ioConfig 定数据来源，包括 topic 名、Kafka 地址、任务数与单任务时长；tuningConfig 定性能参数，比如内存攒批行数、单段最大行数。解析格式与维度由 dataSchema 一段负责。
4. 面试官追问：「怎么验证实时导入真的通了？」
   答：三处对照：Supervisors 页任务 RUNNING，Datasources 页数据源出现且行数增长，Query 页用 select 能查到刚投递的消息；消息内容与队列里回读的一致才算核对完成。
5. 面试官追问：「项目里为什么用 Kafka Indexing Service 而不是自己写消费者程序？」
   答：offset 管理、任务失败重派、数据分段这些运维细节框架内建，声明规格即可；自写消费者要自己兜底全部故障场景，还难以与 Druid 的段模型对齐，成本高可靠性差。
