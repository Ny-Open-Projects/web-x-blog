# Docker 迁移与备份：把改好的容器固化成镜像，再搬去另一台机器

在容器里部署好一套静态页面、改完一堆配置，正准备照着同样的步骤在另一台机器上再来一遍，却发现刚才那几十步操作的顺序已经记不全了。更现实的情况是：这套环境要交给同事，或者要迁到另一台服务器，你手上却只有一份「当初大概这么装的」口头说明。

Docker 的迁移与备份就是为了解决这件事。它把「容器里的改动」固化成镜像，把「镜像」打包成一个可以拷走的文件，到目标机器上再把文件还原成镜像，之后照常 `docker run`。全过程只有三个命令。

## 先给结论

- 三个命令各管一段：`docker commit` 把容器变成镜像，`docker save` 把镜像变成文件，`docker load` 把文件还原成镜像。
- `commit` 固化的是容器**可写层**的改动，也就是你在容器里新增、修改、删除过的文件，原始镜像的层不受影响。
- 迁移的本质是拷那个 `.tar` 文件：拷到另一台机器上 `docker load -i`，镜像就回来了，连名字和标签一起回来。
- 删镜像之前必须先删掉基于它创建的容器，否则会报容器正在引用该镜像的错误，正确顺序是 `stop` 到 `rm` 再到 `rmi`。
- `commit` 适合临时固化和快速迁移，长期可复现的环境应当用 Dockerfile 构建，不要依赖手工 commit。

## 一、三个命令的分工

把一次完整迁移拆开看，每一步的产物都很明确：

```mermaid
flowchart LR
    A["运行中的容器 mynginx"] -->|"docker commit"| B["新镜像 mynginx_1"]
    B -->|"docker save -o"| C["镜像文件 mynginx.tar"]
    C -->|"拷贝到另一台机器"| D["目标机器上的 tar 文件"]
    D -->|"docker load -i"| E["还原出的镜像"]
    E -->|"docker run"| F["新容器，含原有改动"]
```

图里最关键的一跳是 `commit`：它把「容器此刻的状态」拍成一张快照，变成一个新的镜像层。之后这个新镜像和任何普通镜像没有区别，可以 `run`、可以 `save`、可以传给别人。

## 二、容器保存为镜像：commit

课程里的场景很典型：一个正在运行的 `mynginx` 容器，里面已经部署好了静态页面。现在希望以后基于这套内容再创建容器，不用重新拷一遍页面：

```bash
# 语法：docker commit 容器名 新镜像名
docker commit mynginx mynginx_1

# 确认新镜像已经生成
docker images
```

`commit` 执行完，`docker images` 里就多出一个 `mynginx_1`。它包含的是原始 nginx 镜像的所有层，加上你在容器里做的那些改动。

固化之后基于新镜像再起一个容器，验证改动确实被带过去了：

```bash
# 宿主机 80 已被占用，换到 81
docker run -d --name=mynginx2 -p 81:80 mynginx_1
```

访问宿主机的 81 端口，看到的就是之前部署的静态页面，说明新镜像里确实带着那些内容。

**第一，`commit` 的参数顺序是「容器在前，镜像在后」。** 写反了会报找不到容器，课程演示里就出现过把容器名写错、报 `No such container` 的情况。

**第二，容器不必先停止。** `commit` 对运行中的容器同样有效，不过正在写的文件可能处于中间状态，追求一致性时可以先 `docker stop` 再提交。

**第三，改了配置也适用。** 不只是静态页面，容器内改过的任何配置文件、装过的任何包，都会被固化进新镜像，这是它最大的价值。

## 三、镜像备份成文件：save

要把镜像搬到另一台机器，就得先把它变成文件。`save` 的 `-o` 表示 output，后面跟输出文件名，最后写要导出的镜像名：

```bash
# 语法：docker save -o 输出文件 镜像名
docker save -o mynginx.tar mynginx_1

# 当前目录下多出一个 tar 文件
ls -lh mynginx.tar
```

这个 `mynginx.tar` 就是可以拷走的产物，`scp` 到目标机器即可。镜像体积通常不小，课程资料里给出的做法是直接接上 `gzip` 压缩：

```bash
# 保存时压缩
docker save mynginx_1 | gzip > mynginx.tar.gz

# 批量打包多个镜像
docker save nginx:latest redis:5.0.5 mysql:5.7.9 | gzip > images.tar.gz
```

压缩后的体积能小很多，跨机房传输时差别明显。加载时用 `docker load < mynginx.tar.gz` 即可，Docker 会自动识别压缩格式。

## 四、文件恢复成镜像：load

在目标机器上，用 `load` 把文件还原成镜像，`-i` 表示 input，后面跟文件名：

```bash
# 语法：docker load -i 镜像文件
docker load -i mynginx.tar

# 镜像回来了，名字和标签都在
docker images
```

还原出来的镜像和源机器上的是同一个，直接用它 `docker run` 即可，原先部署的内容、改过的配置都在。

**删除镜像要按正确顺序来。** 直接 `docker rmi mynginx_1` 会失败，因为已经有容器基于它创建并运行，Docker 会提示容器正在引用该镜像。正确顺序是先停容器、再删容器、最后删镜像：

```bash
docker stop mynginx2
docker rm mynginx2
docker rmi mynginx_1
```

课程演示里正是按这个顺序把镜像彻底删干净，再用 `docker load` 把它恢复回来的，用来验证备份文件确实可用。

## 五、什么场景用 commit，什么场景用 Dockerfile

`commit` 上手快，但它固化的是一次手工操作的结果，别人拿到镜像并不知道里面改了什么。可复现的环境应当把改动写进 Dockerfile，让镜像可以被重复构建出来。课程源码里的编排文件就体现了这个思路，镜像名是显式声明的，构建过程是 `build: .`：

```yaml
version: "3"

services:
  sailing:
    container_name: sailing
    build: .
    image: sailing:1.0-SNAPSHOT
    ports:
      - "56085:56085"
    restart: always
    depends_on:
      - redis
```

**第一，`image: sailing:1.0-SNAPSHOT` 这种带标签的命名值得养成习惯。** `commit` 出来不带标签的镜像会显示为 `<none>`，时间一长根本分不清哪个是自己提交的。提交时写上 `镜像名:标签` 就能避免这个问题。

**第二，镜像的价值在于可以被多个容器复用。** 课程里 Kubernetes 的资源清单就是典型例子，同一个镜像名声明出多个副本：

```yaml
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: nginx
        image: nginx
        ports:
        - containerPort: 80
```

先把容器固化成镜像，再让多个实例从同一个镜像启动，这才是一套环境能被复制、能被扩容的前提。

**第三，数据的迁移不走这条路。** `commit` 和 `save` 打包的是镜像的文件系统，容器挂载卷里的数据不在其中。数据库这类有状态服务，迁移要单独备份挂载目录或用数据库自身的导出工具。

## 常见误区

- **参数顺序写反**：`commit` 是「容器名 镜像名」，`save` 是「-o 文件 镜像名」，`load` 是「-i 文件」。写反了要么报找不到对象，要么会覆盖掉同名文件。
- **直接 `rmi` 删镜像**：只要还有容器引用它（包括已停止的容器）就删不掉，会提示 conflict。先 `stop`、再 `rm`、最后 `rmi`，或者用 `docker rm -f` 强制删除容器。
- **以为 `save` 会把挂载卷里的数据一起打包**：卷是独立于镜像文件系统的，`commit` 和 `save` 都不包含它。数据库数据要单独备份。
- **把 `save` 和 `export` 混为一谈**：`save` 面向镜像，保留层结构和历史，配合 `load` 使用；`export` 面向容器，导出的是扁平化的文件系统快照，配合 `import` 使用，会丢失镜像的元数据和历史层。
- **长期依赖 commit 产出生产镜像**：手工提交的镜像无法追溯改了什么，也无法重建。关键环境应该用 Dockerfile 描述构建过程，把 `commit` 只当作临时固化和应急迁移的手段。

## 面试可能被问到的问题

1. 面试官追问：「`docker commit`、`docker save`、`docker load` 分别是干什么的？」
   答：`commit` 把运行中的容器及其可写层的改动打包成一个新镜像；`save` 把一个镜像导出成 tar 文件，用于备份和跨机器传输；`load` 是 `save` 的逆操作，把 tar 文件还原成本地镜像，名字和标签都会保留。

2. 面试官追问：「`docker commit` 提交的是容器的哪一部分？」
   答：提交的是容器可写层相对原始镜像发生的改动，包括新增、修改和删除的文件，原始镜像的只读层被复用而不复制。因此提交产物体积通常只比改动量略大。

3. 面试官追问：「删镜像时提示有容器在引用，该怎么处理？」
   答：说明还有容器基于该镜像创建，哪怕是已停止的容器也算引用。按顺序执行 `docker stop 容器`、`docker rm 容器`、`docker rmi 镜像`，或者用 `docker rm -f` 强制删除容器后再删镜像。

4. 面试官追问：「`docker save` 和 `docker export` 有什么区别？」
   答：`save` 操作对象是镜像，导出结果保留镜像的层结构、历史、环境变量和启动命令，用 `load` 还原后与原来完全一致。`export` 操作对象是容器，导出的是一个扁平化的文件系统快照，会丢失层历史和镜像元数据，用 `import` 还原后需要重新指定启动命令。

5. 面试官追问：「容器里挂载的数据卷会被 `commit` 打包进去吗？」
   答：不会。数据卷的内容独立于容器的可写层，`commit` 只固化容器文件系统本身的改动。数据库、文件存储这类落盘数据必须单独备份挂载目录或使用服务自带的导出工具。

6. 面试官追问：「迁移环境时，用 commit 还是写 Dockerfile？」
   答：临时固化、快速把一台机器的环境搬到另一台机器，用 commit 加 save 最直接，几分钟就能完成。但要长期维护、可审计、可重复构建的环境，必须用 Dockerfile 把每一步改动显式写出来，commit 产出的镜像无法追溯改了什么，也不便于版本管理。
