# 实时数据查询的 Service 层：用 MyBatis-Plus 组装动态条件与分页

仓库监控页要的东西很朴素：实时指标表 `cz_message_realtime` 里每台设备的最新读数，按公司筛一筛，再分页翻一翻。查询服务 cold-monitor 承担的就是这件事，Service 层是它的腰部：对下靠 MyBatis-Plus 的单表套餐直连数据库，对上给 Controller 递一个带分页结果的 `IPage`。接口、实现、分页、动态条件四块代码逐层拆开，还有两个藏在细节里的坑要提前排掉。

## 先给结论

- 接口 MessageService 继承 MyBatis-Plus 的 `IService<MessageEntity>`，单表增删改查白拿，业务方法只需补一个 `queryMessageRealtime(Map<String, Object> params)`，返回 `IPage`。
- 实现类 MessageServiceImpl 继承 `ServiceImpl<MessageDao, MessageEntity>` 并实现接口，必须标注 `@Service`，否则 Controller 那边注入失败。
- 分页调用 `this.page(new Page<MessageEntity>(page, size), queryWrapper)`，页码与条数从前端参数取，`Integer.valueOf` 转成 int。
- 动态条件集中在私有方法 getMessageCondition：取值、判空、trim，再 `queryWrapper.eq` 追加；之后想加主机、仓库条件照这个模式续写。
- `page()` 真正生效的前提是容器里注册了分页拦截器 PaginationInterceptor，工程没配时 SQL 不带 LIMIT，分页会静默失效。

## 单表查询为什么走 MyBatis-Plus 套餐

实时查询查的是单表：`cz_message_realtime` 以设备编码为主键，一行就是一台设备的最新读数与告警结论。单表 CRUD 是 MyBatis-Plus 最拿手的场景，BaseMapper 已经备好了 selectPage、selectList 这些方法，Mapper 里一行 SQL 都不用写：

```java
@Mapper
public interface MessageDao extends BaseMapper<MessageEntity> {
}
```

MessageDao 挂 @Mapper 注解后，`BaseMapper<MessageEntity>` 给它注入了整套单表操作，泛型 MessageEntity 对应实时指标表的 23 列。Service 层的两件套再往上包一层：IService 是接口侧的单表能力声明，ServiceImpl 是实现侧的默认落地，它们内部的动作最终都会落到这个 Dao 上。

## 接口与实现：先定形状再填逻辑

接口声明放在 service 包里，继承 IService 并补上业务方法：

```java
public interface MessageService extends IService<MessageEntity> {

    IPage<MessageEntity> queryMessageRealtime(Map<String, Object> params);
}
```

继承 IService 之后，这个接口自动带上单表增删改查的全部方法声明，工程真正要补的只有一个 queryMessageRealtime：入参 `Map<String, Object>`，键值对就是前端传来的查询参数；返回 IPage，MyBatis-Plus 的分页结果容器，里面既有记录列表，也有总数、总页数这些分页元信息。

实现类把继承链搭完整：

```java
@Service("messageService")
public class MessageServiceImpl
        extends ServiceImpl<MessageDao, MessageEntity>
        implements MessageService {

    @Override
    public IPage<MessageEntity> queryMessageRealtime(Map<String, Object> params) {
        //组装查询条件
        QueryWrapper<MessageEntity> queryWrapper = getMessageCondition(params);

        //查询
        int page = Integer.valueOf(params.get("page").toString());
        int size = Integer.valueOf(params.get("pagesize").toString());
        return this.page(new Page<MessageEntity>(page, size), queryWrapper);
    }
}
```

三层关系一句话说清：继承 ServiceImpl 获得 page、list 这些现成方法，实现 MessageService 履行接口承诺，泛型 MessageDao 与 MessageEntity 把操作钉在实时指标表上。@Service 注解把实现类注册成 Spring 容器里的 bean，bean 名显式定为 messageService，Controller 里的 @Autowired 靠它完成装配。

开发顺序值得学一下：先把接口方法签名定下来，实现类里先返回一个空壳，跑通编译，再一层层往里填组装条件、分页查询的逻辑。业务代码一层递进一层，比一口气写完再调试省力得多。

## 分页：Page 对象与拦截器

page 方法的两个入参里，`new Page<MessageEntity>(page, size)` 第一个是当前页码，第二个是每页条数。页码与条数不该写死在代码里，从前端参数取：

```java
int page = Integer.valueOf(params.get("page").toString());
int size = Integer.valueOf(params.get("pagesize").toString());
```

前端传来的都是字符串形式的数字，Integer.valueOf 完成转换。键名 page 与 pagesize 是前后端的约定，拼写要严格对齐，取不到值时 toString 会直接抛空指针，这是参数契约里最脆的一环。

另一个隐含前提是分页拦截器。page() 生成的 SQL 要带 LIMIT 与 count 统计，靠的是 PaginationInterceptor 在 SQL 执行前改写，容器里必须有这个 bean：

```java
@Configuration
public class MybatisPlusConfig {

    @Bean
    public PaginationInterceptor paginationInterceptor() {
        return new PaginationInterceptor();
    }
}
```

这段配置是平台系统管理服务里的现成写法，查询服务引入同样的配置类即可。没有它，page 调用不报错、返回也不缺数据，SQL 却不带 LIMIT，一次把整表拉回来；数据量小时察觉不到，表一膨胀，分页就成了摆设。

## 动态条件：getMessageCondition 的组装模式

查询条件单独抽成私有方法，Service 主流程只留组装加查询两步：

```java
private QueryWrapper<MessageEntity> getMessageCondition(Map<String, Object> params) {
    QueryWrapper<MessageEntity> queryWrapper = new QueryWrapper<>();

    String companyid = params.get("companyId") == null
            ? null : params.get("companyId").toString().trim();
    if (companyid != null) {
        queryWrapper.eq("companyId", companyid);
    }
    //添加其他参数
    //...

    return queryWrapper;
}
```

QueryWrapper 是条件构造器，链式往里加条件，最终拼进 SQL 的 where 子句。这里只演示了公司维度：先从参数里取 companyId，三元表达式兜住空值，trim 去掉首尾空白；非空才 eq 追加条件，eq 的第一个参数是表的列名，第二个是期望值。列名与实体属性的对应关系取决于表设计，实时指标表的列就是驼峰风格，所以这里写 companyId 而不是下划线风格。

「非空才追加」这个判断是动态查询的灵魂：前端没传公司条件，where 里就没有这一条，查出的是全量分页数据；传了，条件自动生效。之后要加主机编码、仓库编码、时间范围，照这个模式往下续写就行，注释里的省略号正是留给这些条件的扩展位。

条件与分页在 Service 层汇合成一次 page 调用，真正落到数据库的，是 Dao 里由 BaseMapper 自动生成的分页 select。

## 常见误区

- **分页不配拦截器。** 错例是以为 page 方法天生分页。正解是确认容器里有 PaginationInterceptor bean，否则 SQL 不带 LIMIT，一次查全表，分页只是表面功夫。
- **直接取参数不做空值防护。** 错例是 `params.get("pagesize").toString()` 一路写到底，前端漏传就空指针。正解是页码与条数给默认值，业务条件先判空再追加。
- **eq 的列名随手写。** 错例是按数据库习惯补下划线写成 company_id。正解是对着实时指标表的真实列名写，这张表是驼峰列名，写错列名 SQL 直接报列不存在。
- **把条件拼进主流程。** 错例是在 queryMessageRealtime 里一路 if 加条件，方法越写越长。正解是条件组装独立成方法，主流程只留组装加查询，扩展条件时互不干扰。

## 面试可能被问到的问题

1. 面试官追问：「MyBatis-Plus 的 IService、ServiceImpl、BaseMapper 各自负责什么？」
   答：BaseMapper 挂在 Dao 上，提供单表的增删改查与分页方法，SQL 由框架按实体注解自动生成；IService 是 Service 接口层的单表能力声明；ServiceImpl 是它的默认实现，内部调用 Dao 完成动作。业务代码继承这套体系后只需写增量逻辑。
2. 面试官追问：「page 方法为什么会静默不分页？」
   答：MyBatis-Plus 的物理分页靠 PaginationInterceptor 拦截器改写 SQL，追加 LIMIT 并执行 count。容器里没注册这个 bean 时，Page 参数不会被处理，SQL 原样执行，返回的仍是全量数据，调用不报错，问题在数据量上来后才暴露。
3. 面试官追问：「为什么查询方法入参用 Map<String, Object> 而不是 DTO？」
   答：前端查询条件天然是键值对，Map 原样透传到 Service，新增查询条件不用改方法签名与调用链。代价是键名成了隐式契约，取值要判空，类型要自己转；规范团队里更适合封装成查询 DTO，用类型校验换灵活性。
4. 面试官追问：「动态查询条件怎么做到可选？」
   答：每个条件先取值、判空、trim，非空才往 QueryWrapper 里追加 eq、ge、le 这类条件，没传的条件不进 where 子句。条件多了可以按维度分组抽方法，避免一个方法里堆几十个 if。
5. 面试官追问：「QueryWrapper.eq 第一个参数写实体属性名还是数据库列名？」
   答：写数据库列名，它会原样拼进 SQL。驼峰列名的表写驼峰，下划线列名的表写下划线；开启映射配置后也可以用属性名，但要保证实体注解与全局配置一致，最稳妥的是直接对齐真实列名。
