# 六大数据库存储实战: 领域驱动设计落地的五条拆分原则

## 纲要

- 领域驱动设计（DDD）解决的真实问题：包结构与微服务边界怎么切
- 原则一：按领域职责拆分

## 为什么需要领域驱动设计

在做新零售电商这类包含社交内容的系统规划时，最先遇到的问题往往不是技术选型，而是：**Java 单体工程里的 package 怎么拆？微服务环境下服务边界怎么划？** 这两件事本质上都围绕领域驱动设计的思想展开。

DDD 对初学者来说比较抽象，难点在于拿到一个实际项目不知道从何下手。下面五条原则可以作为拆分的判断依据。

## 按领域职责拆分

这是最直观的一条。拿到产品需求之后，业务形态内部其实已经蕴含了领域的职责：传统电商里的商品、交易、营销、用户，每一个对象都可以作为领域模型拆分的第一准则。

DDD 的核心理念是**清晰地拆分出对象，并由这个对象承载背后的职责**。做软件开发永远不会把用户模块和交易模块放在同一个领域内——即便它们之间有千丝万缕的联系，实体模型本身就是两套体系。

需要强调的是，领域职责的划分不是研发单方面的事。如果产品的设计思路就是把用户与订单交易放在一起考虑，那么落到系统做领域建模时就会产生变形。**一个好的领域边界与领域模型，必须和产品同学讨论并达成共识**，这也是研发与产品合作中需要反复对齐的第一个点。

## 按应用能力拆分

新零售电商通常会有一个管理后台，里面有侧边栏、用户管理、订单管理、商品管理等模块。这个"应用侧的边界"反过来固化了领域边界——**领域边界往往和数据的使用态、管理态息息相关**。

判断标准是：在这个领域职责范围内，应用能力是否做到了足够的封装与闭环，而不至于把某一个应用能力渗透到外围领域去使用。好的拆分需要完整考虑应用场景，覆盖"页面元素 → 底层数据"的整条贯穿链路。

## 按安全边界拆分

安全边界在实际建模中不常见，但一旦遇到就是决定性的。假设同样一份订单数据，用户看自己的订单、商家看自己的订单，两者的领域边界是否要切开？

- **方案 A（一套存储 + 一套模型）**：订单只存一份，使用同一套领域模型，在外围接口上通过 userId / sellerId 过滤数据
- **方案 B（两套存储 + 两套模型）**：用户订单与商家订单是两套存储、两套微服务框架、两套接口，每个接口内部有独立的安全校验与数据存取逻辑

方案 B 就是典型的按安全边界拆分，得到"订单领域服务"与"商户订单领域服务"两套领域模型。判断依据是安全边界是否足够复杂——尤其在私有云环境、客户要求私有化部署的场景，安全边界必须纳入领域拆分的原则之中。

## 按技术异构拆分

存储选型的差异常常直接决定领域服务的拆分：一部分数据用 Elasticsearch 做全文检索，另一部分数据依赖关系型数据库保证强事务一致性，那么"订单搜索"和"订单详情"是否需要两套领域模型？

现实中的处理有两种：

- 把 ES 作为订单领域模型中的一种存储能力，以搜索接口的形态融入同一套领域模型
- 拆成两套微服务体系、两套领域驱动设计

关键不在于存储是否异构，而在于**另一套领域服务是否足够复杂，是否体现出与原有领域服务完全不同的模型结构设计**。如果只是存储选型的差异、业务功能大差不差，用一套领域设计即可；像商品与订单这种完全异构的体系，就必须拆成两套领域模型。

## 按组织效率拆分

效率上的拆分应对的是组织结构变更。大型公司通常有中台与业务的划分：某个阶段把中台建得很厚、业务做得很薄，另一个阶段又把业务做厚、中台做薄，本质上都是在应对当时不同的业务形态与公司战略。

出于效率考虑，需要动态决定哪一层做厚、哪一层做薄，甚至合并一层或拆分一层。这类调整的依据是组织结构与面向的业务形态，而不是技术本身。

## 五条原则的汇总

| 拆分维度 | 判断依据 | 典型产出 |
| --- | --- | --- |
| 领域职责 | 业务对象与实体模型是否自成体系 | 用户域、商品域、交易域 |
| 应用能力 | 页面元素到底层数据能否闭环 | 管理后台的能力边界 |
| 安全边界 | 安全校验逻辑是否复杂、是否需私有化部署 | 用户订单服务 / 商家订单服务 |
| 技术异构 | 另一套服务的模型复杂度是否与原有完全不同 | 搜索服务 / 交易服务 |
| 组织效率 | 组织结构与业务战略的变化 | 中台与业务的厚薄调整 |

## 领域模型与数据模型的关系

万变不离其宗，所有的拆分最终都要围绕**领域模型**做设计与沉淀。近年来常讲的贫血模型、充血模型，在 Java 体系内的落点其实很朴素：**领域模型就是 data model**，也就是应用层中与数据库关联的那一层领域模型对象。

由于 Spring 框架的天生优势，我们习惯用 Service 去串联领域模型的存取，因此往往采用贫血模型的做法，把领域模型完全当作数据对象来使用。

但需要明确：**领域模型与数据模型并不完全对等**。数据模型关心表结构与外键，领域模型关心实体与实体之间的关联关系。以属性名与属性值为例，它们在领域视角是多对多的实体关系，而落到数据库设计时，中间需要一张多对多的关系表来承载——领域模型不会去考虑这个具体实现方案，它站在领域视角描述模型体系，以此满足业务产品的需求。这是领域模型设计与数据库方案设计最大的不同。

## 总结

领域驱动设计的落地可以归纳为五条可执行的判断原则：领域职责、应用能力、安全边界、技术异构、组织效率。前四条来自业务与技术本身，第五条来自组织结构。所有拆分的沉淀物最终都落到领域模型上，而领域模型不等于数据模型——前者表达实体关系，后者表达存储结构。理解这个差异，才能在后续做 SKU、库存、订单等模型设计时既不丢业务语义，也不被表结构绑死。
