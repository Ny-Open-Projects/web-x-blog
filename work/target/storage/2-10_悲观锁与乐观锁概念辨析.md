# 六大数据库存储实战: 悲观锁与乐观锁的概念辨析

## 纲要

- 悲观锁与乐观锁并非 MySQL 独有，而是并发控制的两类通用思想，MySQL 的 SQL 只是其中一种实现
- 悲观锁：使用前先尝试加锁，拿不到锁就阻塞等待或超时失败，全程阻塞持有锁的线程
- 乐观锁：不加锁，仅取数据与修改，提交时比对版本号，冲突则失败，仅在提交瞬间有极短的串行
- 取舍：高并发且频繁冲突、且修改伴随多步操作的场景更适合悲观锁；冲突少、操作轻量更适合乐观锁

## 锁是一种通用思想，而非 MySQL 专利

悲观锁和乐观锁描述的是多个使用者并发访问同一「锁对象」时的两种控制策略。这里的锁对象可以是 Java 内存中的一个 `Object`，可以是 MySQL 的一行记录，也可以是 Redis 的一个 key。MySQL 只是用 SQL 语句给出了其中一种实现，理解时应当先脱离具体数据库。

## 悲观锁：先加锁，再使用

假设有一个锁对象，使用者一要使用该对象时，先尝试对其加锁：

- 若锁对象尚未被占用，使用者一加锁成功，锁进入「加锁中」状态。
- 此时使用者二也尝试加锁，发现锁已被占用，加锁动作失败。失败有两种表现：
  - **阻塞等待**：使用者二的线程进入阻塞状态，直到锁释放。
  - **超时返回**：给定一个超时时间（可为 0），时间内未拿到锁立即返回失败并抛出异常。

这种「不同使用者先对锁对象产生加锁行为，并悲观地等待其他使用者释放锁（或在超时内释放）」的方式，就是悲观锁。

## 乐观锁：不阻塞，提交时比对

乐观锁不使用加锁动作，流程是「数据获取 → 数据修改 → 提交比对」：

- 锁对象带有一个 `version` 版本号。使用者一获取时 `version=1`，修改后尝试写为 `version=2`。
- 使用者二同样基于 `version=1` 做修改，也试图写为 `version=2`。
- 若使用者一先提交，锁对象的 `version` 变为 2；使用者二提交时发现自己的原始版本 `1` 与当前 `2` 不一致，更新失败。

整个过程没有阻塞，仅依赖最后一步的版本比对，这就是乐观锁。

需要澄清一个常见误解：乐观锁提交的最后一步并非完全没有阻塞。在同一微秒或同一 CPU 周期内，两个 `UPDATE` 总有先后，数据修改永远串行——只是这个串行发生在 IO 上的极短瞬间，由操作系统的原子操作屏蔽了细节，不会在整个应用生命周期内阻塞进程。

## 两种锁的取舍

直觉上乐观锁对系统消耗更少，但悲观锁并非一无是处：

- **乐观锁不适合高冲突 + 多步操作**：若数据在同一并发瞬间被频繁更新，使用者二的第二步会反复冲突失败，并需要回滚、重新提交其所附带的一系列其他操作，代价反而更高。
- **悲观锁适合「拿到锁后一连串动作必须都成功」**：宁可等待固定周期，只要拿到锁，后续所有操作都能一气呵成。

实际工程中面对复杂场景，应当多思考、对比二者差异再选型。
