# 六大数据库存储实战: MongoDB 原理及优劣势

## 纲要

- 点赞评论场景对存储提出的两项硬要求：高并发写入、二级索引条件拉取
- MongoDB 被称为"最像关系型数据库的非关系型数据库"：支持二级索引，甚至唯一索引
- 优势一：可建二级索引，支持 `where` 条件与唯一性约束（防同一用户重复点赞）
- 优势二：文档式存储（BSON 扩展），schema 灵活，字段可随业务演进
- 劣势一：不支持跨文档事务（无 redo/undo 日志），只在文档级保证原子性
- 劣势二：依赖 mmap 把数据与索引映射进内存，内存消耗巨大
- 概念映射：database→database、collection→table、document→row、field→column；有索引、有 BSON，但无 join
- BSON：Binary JSON，把 JSON 字符串压缩为二进制，存取高效且内存友好

## 场景要求回顾

前面拆解过点赞评论场景：点赞是"双击即写"的高频操作，评论则是"带文本的引用关系"。二者共同要求存储具备两件事——

- 能扛住瞬时高并发写入；
- 能在非主键字段上做条件拉取（"某条 messageId 下的全部评论/点赞"）。

HBase 能满足前者，却因只有 RowKey 一种索引而无法优雅地满足后者。这正是选型的切入点：我们需要一个既快、又支持二级索引的存储，也就是 MongoDB。

## 优势一 二级索引与唯一约束

MongoDB 与 Redis（KV，只有一级主键索引）、HBase（只有 RowKey 索引）最大的不同，是它允许在任意字段上建立**二级索引**。

所谓一级索引就是主键——KV 存储靠 key 查、HBase 靠 RowKey 查，都只能按主键取数。二级索引则是"除了主键之外，还能按其他字段查"。这与关系型数据库的索引能力一致，但代价是索引的维护与存储成本更高（MySQL 同样如此）。MongoDB 的应对是把数据放进内存来换查询速度。

更关键的是，二级索引还能叠加**唯一性约束**。点赞场景要求"同一用户对同一条消息只能赞一次"，只要在 `userId + messageId` 上建唯一索引，第二次插入就会直接抛出 `duplicate key` 异常，约束由存储层强制保证，无需应用层先查后写。

## 优势二 文档式存储与 schema 灵活

MongoDB 是文档数据库，数据以 document（即一行记录）存储，而 document 本质是 JSON 的扩展体——BSON。

文档式存储意味着**不需要预先定义表结构**。以评论为例，今天只需一个 `content` 文本字段，明天要像朋友圈那样支持图片，只需往 BSON 里加一个图片字段即可，历史数据和原 schema 都不必重新定义或迁移。这种易扩展特性与 HBase 相通，是文档模型相对于严格关系表的天然优势。

## 劣势一 不支持事务

MongoDB 很快，但代价是**不支持跨文档事务**。

原因很直接：一旦支持事务，就要像关系型数据库那样维护 redo/undo 日志，要处理原子性、隔离级别、回滚等一整套机制，必然拖累存取速度。因此 MongoDB 只在**单个文档（document）级别**保证原子性操作，跨文档、跨集合的写入无法被一个事务包裹。

工程上的推论：一旦使用 MongoDB，尽量把需要原子完成的逻辑收敛到一张集合内；若两个集合必须同时写入，由于无事务保证，就需要额外的补偿或幂等设计。

## 劣势二 内存消耗巨大

MongoDB 之所以快，是因为它通过 **mmap** 把文件系统和内存做管道映射——实际操作的文件系统背后都是内存。索引同样常驻内存，这也是它索引查询极快的根本原因。

对等代价是内存消耗巨大。部署 MongoDB 通常需要配置较大内存的机器才能发挥优势，否则内存不足时优势很难体现。

## 概念映射 与 MySQL 类比

MongoDB 常被拿来和 MySQL 类比，二者概念可一一对应：

| MySQL | MongoDB | 说明 |
| --- | --- | --- |
| database | database | 库，承载账户权限与数据管理 |
| table | collection | 集合，即表 |
| row | document | 文档，一行记录 |
| column | field | 字段，即 JSON 的 key，支持嵌套结构（如 `a.b`） |
| index | index | 提高查询性能，二者都有 |
| join | 无 | MongoDB 无 join，这是它简单、快的根本原因之一 |

一个集合内的写操作能保证原子性；跨集合操作无法保证原子性，也就无法在 MongoDB 中支持事务。

## BSON 存储本质

MongoDB 的 document 使用 **BSON（Binary JSON）** 这种数据结构：写入时输入的是 JSON 字符串，MongoDB 会把它压缩成二进制数据存储。

这样做有两层收益：

- 二进制维度存取比纯字符串维度高效得多，整体存取效率显著提升；
- 即便把所有数据和索引都加载进内存，BSON 的二进制结构也不会对内存造成过度占用。

## 小结

- MongoDB 胜在"像关系型数据库"：支持二级索引与唯一约束，又能像文档库一样灵活扩展；
- 代价是放弃跨文档事务、且依赖大内存（mmap）换取速度；
- 与 MySQL 概念高度可类比，但去掉了 join，复杂关联需在应用层处理；
- BSON 的二进制压缩是它高效存取与内存友好的底层原因；
- 这些特性共同解释了：为什么点赞评论这种"高并发写 + 带条件拉取 + 需唯一约束"的场景适合落在 MongoDB。
