# 六大数据库存储实战: 用 Java High Level Client 构建全量索引

## 纲要

- 接入 ES 的第一步是引入与服务端版本严格对齐的依赖：`elasticsearch` + `elasticsearch-rest-high-level-client`
- 全量索引构建的核心是**分页捞库 + 批量写入**，绝不能一次性把全表读进内存
- 索引必须先建：ES 不会在数据写入时自动创建符合预期的索引
- 只把"需要被检索的字段"写进索引，其余字段留在 MySQL 里按需回查
- `BulkRequest` 是批量写入的标准 API，一条 `IndexRequest` 对应一个文档
- 验证手段：`match_all` 全量扫一遍，再用 `match` 做关键词回归

## 从 MySQL 到 ES 的数据通路

商品搜索要落地，前提是 ES 里有数据。全量索引构建要解决的就是这件事：把 MySQL 中的商品记录，按我们定义的 mapping 灌进 ES 的倒排索引。

```mermaid
flowchart LR
    A[MySQL item 表] -->|分页查询| B[Java 应用]
    B -->|组装 IndexRequest| C[BulkRequest 批量请求]
    C -->|RestHighLevelClient| D[(ES item 索引)]
    D -->|_search 验证| E[检索结果]
```

这条链路有三个关键约束：

- **分页**：全表数据一次性读进内存必然 OOM，必须分页拉取
- **批量**：一条一条写会产生大量网络往返，必须用 Bulk 批量提交
- **字段裁剪**：索引里只放检索需要的字段，避免索引膨胀

## 依赖与客户端初始化

第一步引入依赖，**版本号必须与 ES 服务端完全一致**（课程环境为 7.7.1）：

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.elasticsearch</groupId>
    <artifactId>elasticsearch</artifactId>
    <version>7.7.1</version>
</dependency>
<dependency>
    <groupId>org.elasticsearch.client</groupId>
    <artifactId>elasticsearch-rest-high-level-client</artifactId>
    <version>7.7.1</version>
</dependency>
```

两层依赖的分工：

| 依赖 | 作用 |
| --- | --- |
| `elasticsearch` | 核心模型与查询 DSL 的构建块 |
| `elasticsearch-rest-high-level-client` | 把 Java 对象封装成 HTTP 请求，省去手工拼 JSON |

High Level Client 帮我们用 Java 对象封装了原本需要手工拼接的 JSON。但在遇到非常复杂、Java API 难以表达的 query 时，退回到最基础的 HTTP Client，把 JSON 对象序列化成字符串 POST 上去，同样是可行方案——只是目前绝大多数场景 High Level API 已足够。

客户端初始化：

```java
// 建立到 ES 的 HTTP 连接（根据讲稿逻辑补充）
RestHighLevelClient client = new RestHighLevelClient(
        RestClient.builder(new HttpHost("localhost", 9200, "http"))
);
```

## 先建索引，再灌数据

如果 `item` 索引不存在，ES 不会帮我们按预期配置新建，而是用动态映射猜测字段类型——这对中文检索是灾难性的。所以必须**先显式建索引**：

```bash
curl -X PUT "http://localhost:9200/item" -H 'Content-Type: application/json' -d '{
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 1
  },
  "mappings": {
    "properties": {
      "id":   { "type": "long" },
      "name": {
        "type": "text",
        "analyzer": "ik_max_word",
        "search_analyzer": "ik_smart"
      }
    }
  }
}'
```

`name` 字段用 IK 分词器，索引时细切、查询时粗切，这是中文检索的标准配置。

## 分页捞库与批量写入

### 计算总页数

```java
// 分页参数：先取总数，再算页数（根据讲稿逻辑补充）
int size = 20;
int currentPage = 1;
long count = itemService.count();
int totalPage = (int) Math.ceil((double) count / size);
```

注意 `(double) count` 的强制类型转换——`long / int` 会直接丢掉小数，页数算少一页就会漏数据。

### 逐页组装 BulkRequest

```java
// 全量索引构建主流程（根据讲稿逻辑补充）
@GetMapping("/importitem")
@ResponseBody
public JsonReturnType importItem() throws IOException {
    int size = 20;
    long count = itemService.count();
    int totalPage = (int) Math.ceil((double) count / size);

    RestHighLevelClient client = new RestHighLevelClient(
            RestClient.builder(new HttpHost("localhost", 9200, "http")));

    for (int currentPage = 1; currentPage < totalPage + 1; currentPage++) {
        Page<Item> page = new Page<>(currentPage, size);
        List<Item> itemList = itemService.page(page).getRecords();

        // 批量请求：一次网络往返提交整页数据
        BulkRequest bulkRequest = new BulkRequest();
        for (Item item : itemList) {
            // 只把需要检索的字段放进索引
            Map<String, Object> map = new HashMap<>();
            map.put("name", item.getName());

            IndexRequest indexRequest = new IndexRequest("item")
                    .id(item.getId().toString())
                    .source(map);
            bulkRequest.add(indexRequest);
        }
        client.bulk(bulkRequest, RequestOptions.DEFAULT);
    }
    return JsonReturnType.success();
}
```

几个要点：

- **只写检索字段**：`item` 表可能有几十个字段，但用户只会按名称搜索，因此只把 `name` 建进索引。其余字段留在 MySQL，等搜索拿到 ID 后再回查。索引体积与重建速度都因此受益
- **文档 ID 用业务主键**：`item.getId()` 作为 ES 文档 ID，重复导入就是覆盖更新，天然幂等
- **异常向上抛出**：连接失败会抛 `IOException`，交给外层 controller 统一处理，不要在循环里吞掉异常导致部分导入失败却无感知

### 生产环境的触发方式

教学环境用一个 HTTP 接口手工触发导入更便于调试。生产环境应换成定时调度：

```java
// 定时全量重建：每天凌晨一点执行（根据讲稿逻辑补充）
@Scheduled(cron = "0 0 1 * * ?")
public void rebuildItemIndex() {
    // 与上文 importItem 相同逻辑，建议加上"重建到临时索引 + 别名切换"
}
```

全量重建期间直接写目标索引会导致短暂的数据不一致，更稳妥的做法是**写临时索引 + 别名切换**，切换瞬间完成，业务无感知。

## 验证索引结果

导入完成后，用两个查询验证：

```bash
# 1. 全量扫描，确认文档数量与内容
curl -X POST "http://localhost:9200/item/_search" -H 'Content-Type: application/json' -d '{
  "query": { "match_all": {} }
}'

# 2. 关键词回归，确认分词与检索生效
curl -X POST "http://localhost:9200/item/_search" -H 'Content-Type: application/json' -d '{
  "query": { "match": { "name": "iphone" } }
}'
```

`match_all` 返回的结果里，所有文档 `_score` 都是 1.0——因为没有设置任何检索关键字，不存在相关性评分差异。改用 `match` 后，命中的文档才带真实评分。

课程环境验证结果：两条商品记录（iPhone SE、iPad mini）成功入索引，搜 `iphone` 命中第一条，搜 `ipad` 命中第二条，全量索引构建完成。

## 全量与增量的分工

| 维度 | 全量索引构建 | 增量索引构建 |
| --- | --- | --- |
| 数据来源 | 全表分页扫描 | binlog / MQ 消息 |
| 触发时机 | 首次上线、索引结构变更、数据修复 | 商品创建、修改、下架 |
| 耗时 | 与数据量成正比 | 毫秒级 |
| 一致性 | 某一时刻的快照 | 近实时 |
| 风险 | 大批量写入冲击集群 | 消息丢失导致漏索引 |

生产上二者必须配合：全量负责"基线正确"，增量负责"持续保鲜"。

## API 速览

| API | 签名要点 | 说明 |
| --- | --- | --- |
| `RestClient.builder(HttpHost...)` | 传入 host、port、scheme | 构建低层 REST 客户端 |
| `new RestHighLevelClient(builder)` | 包装低层客户端 | 面向 Java 对象的高级客户端 |
| `new IndexRequest(index).id(id).source(map)` | 索引名、文档 ID、字段 Map | 单条索引/更新请求 |
| `new BulkRequest().add(IndexRequest)` | 累积多条请求 | 批量请求容器 |
| `client.bulk(bulkRequest, RequestOptions.DEFAULT)` | 抛出 `IOException` | 执行批量写入 |
| `new Page<>(currentPage, size)` | 分页参数 | MyBatis-Plus 分页对象 |

### 运行说明

```bash
# 1. 启动 ES（7.7.1）并确保 IK 插件已安装
# 2. 建索引（见上文 curl）

curl "http://localhost:9090/es/importitem"

curl -X POST "http://localhost:9200/item/_search" -H 'Content-Type: application/json' \
  -d '{"query":{"match":{"name":"iphone"}}}'
```

### 代码说明

- 用 `@GetMapping` 而非 POST，是为了能在浏览器地址栏直接触发，仅教学调试便利，生产应改为定时任务 + 鉴权
- `Map<String, Object>` 是 `source` 的最灵活形式，也可以直接传 Java Bean（客户端自动序列化）
- 每一页独立提交一次 `bulk`，批次大小由 `size` 控制，默认 20 条；生产可调到 500～1000 条以平衡内存与网络

### 技术点总结

- 客户端版本必须与 ES 服务端严格一致，否则序列化协议不兼容
- 全量导入的口诀是"先建索引、分页捞库、批量写入、只传检索字段"
- `Math.ceil((double) count / size)` 的强制转型不能省，否则漏最后一页
- 文档 ID 用业务主键可保证重复导入幂等
- 验证分两步：`match_all` 查数量，`match` 查分词效果
