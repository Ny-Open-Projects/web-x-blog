# 六大数据库存储实战: 商品名搜索的 LIKE 实现与索引优化取舍

## 纲要

- 商品搜索初版：用关系型数据库 `LIKE` 实现，复用 `getItem` 拼接详情
- `ItemServiceImpl.search`：`QueryWrapper.like` + `select("id")` 只取主键，再用 Stream 调 `getItem` 组装完整结果
- 性能优化：`like` 是全模糊（两侧 `%`）无法走索引；`likeRight` 仅拼右侧 `%` 走 `name` 索引的最左前缀
- 取舍结论：`LIKE` 仅适合小数据量；海量商品名的全文检索应交给 Elasticsearch（见后续章节）

## 用 LIKE 实现商品名搜索

在引入 Elasticsearch 之前，先用 MySQL 的 `LIKE` 快速验证搜索能力。`ItemService` 声明：

```java
public interface ItemService extends IService<Item> {
    Sku createSku(Sku sku);
    Item getItem(Long id, Long shopId);
    List<Item> search(String name, Long shopId);
}
```

实现思路分两步：先用模糊匹配捞出符合条件的 `id` 列表，再复用 `getItem` 拼装完整详情——因为直接 `SELECT *` 得到的 `Item` 没有 SKU/库存等信息，不能直接返回。

```java
@Override
public List<Item> search(String name, Long shopId) {
    QueryWrapper<Item> queryWrapper = new QueryWrapper<>();
    queryWrapper.like("name", name);
    queryWrapper.select("id");                  // 只取主键，减少内存加载
    List<Long> itemIdList = super.listObjs(queryWrapper);
    return itemIdList.stream()
                     .map(id -> getItem(id, shopId))
                     .collect(Collectors.toList());
}
```

`select("id")` 让查询只返回主键，借助主键唯一性做后续精确查询，避免一次性把整行数据加载进内存。控制器直接暴露为 GET 接口：

```java
@RequestMapping(value = "/search", method = {RequestMethod.GET})
@ResponseBody
public JsonReturnType search(@RequestParam(name = "name") String name,
                             @RequestParam(name = "shopId") Long shopId) {
    List<Item> itemList = itemService.search(name, shopId);
    return JsonReturnType.createType(itemList);
}
```

访问 `GET /item/search?name=iphone&shopId=2` 即可返回匹配商品的完整详情；搜 `ipad` 出 ipad，搜无关词返回空列表。

> 调试小记：首版因 `select("id")` 返回的是 `id` 列表而非 `Item`，误把 `listObjs` 结果当 `Item` 直传导致类型转换报错。修正为 `itemIdList` 后，再经 `getItem` 映射即可。同理 `shopId` 必须正确传入，否则库存统计会错位。

## LIKE 的索引优化取舍

`like` 与 `likeRight` 的区别决定了能否命中索引：

| 写法 | 实际 SQL 片段 | 是否走 `name` 索引 |
| --- | --- | --- |
| `like("name", keyword)` | `name LIKE '%keyword%'` | 否（全模糊，前置 `%` 阻断最左前缀） |
| `likeRight("name", keyword)` | `name LIKE 'keyword%'` | 是（最左前缀匹配） |

- **全模糊 `LIKE '%x%'`**：两侧都有 `%`，MySQL 无法利用 B+ 树索引的最左前缀，只能全表扫描，数据量大时性能急剧下降。
- **右模糊 `LIKE 'x%'`**：只有右侧 `%`，可走 `name` 索引的最左前缀，性能可控。

但右模糊牺牲了「中间匹配」能力——搜 `pad` 匹配不到 `ipad`。因此：

- 小数据量、对匹配精度要求不极致的场景，可用 `likeRight` 兼顾性能与体验。
- 需要「任意位置匹配」且数据量大的场景，`LIKE` 无论如何都慢，应当把搜索能力交给 Elasticsearch 做倒排索引（后续章节展开）。

## API 速览

| 方法 | 作用 | 备注 |
| --- | --- | --- |
| `QueryWrapper.like(col, val)` | 全模糊匹配 | 性能差，不推荐大数据量 |
| `QueryWrapper.likeRight(col, val)` | 右模糊，走最左前缀 | 可命中索引 |
| `queryWrapper.select("id")` | 限定只查指定列 | 减少内存与 IO |
| `super.listObjs(wrapper)` | 返回单列对象列表 | 此处即 `id` 列表 |
| `ItemService.search(name, shopId)` | 搜索并拼装详情 | 复用 `getItem` |

**技术点总结**：关系型数据库的 `LIKE` 是搜索能力的快速验证手段，但全模糊无法走索引，是性能瓶颈；右模糊可有限利用索引，真正的全文检索需下沉到 Elasticsearch。
